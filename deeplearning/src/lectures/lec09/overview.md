# 第 9 讲导览 · 大规模并行训练的秘诀

## 这一讲要解决的真实问题

前八讲都在回答同一个方向的问题：**怎么设计一个能学好的模型**。第 9 讲换了一个正交的问题：**当模型与数据大到一张卡装不下时，怎么把它训起来**。这不是「多买几张卡」那么简单——把 7B 参数的模型按混合精度 Adam 训练，光与优化器相关的静态状态就要 $16\times7\times10^{9}$ 字节 $\approx 112\ \text{GB}$（算式见 [9.1](sec91.md)），而一张主流训练卡的显存是 80 GB。**模型还没开始算，就已经装不下了。**

真实的大规模训练由两条线索驱动。

第一条是**切**：把数据切给多张卡（数据并行）、把单个权重矩阵切给多张卡（张量并行）、把层切成段分给多张卡（流水线并行），
三者正交，可组合成工业界的 3D 并行；再往前一步，激活也能沿序列维切（序列并行 / 上下文并行），
专家层还能沿专家维切（专家并行），于是有了「5D 并行」。

第二条是**省**：用低精度换显存与吞吐（BF16 / FP8）、用算力换显存（激活重计算）、
用通信换显存（ZeRO / FSDP 把冗余的模型状态分片），以及用「只训一小部分参数」换显存（LoRA / QLoRA）。

这两条线索的每一次取舍都要落在三个量上：**显存够不够、算力用满没有、通信扛不扛得住**。
本讲的全部公式与清单，都是为了让这三个量在动手之前就能被算出来——因为在大规模训练里，「先跑一次看看」的代价是几小时到几天。

母本 MIT 6.S191 在讲 Transformer 时提到过「大模型需要分布式训练」，但没有展开；本教程把这一讲补成一条可操作的工程线：

**先算账（9.1）→ 再切分（9.2 / 9.3 / 9.4）→ 同时省（9.5）→ 处理工程摩擦（9.6）→ 落到自己的硬件上（9.7）**。

凡是超出这本书能核实范围的地方（具体的框架内部实现、某次训练的确切吞吐），都会明确标注「需核实」，
而不是给一个好看的数字。

## 七节一览

| 节 | 核心问题 | 关键结论 | 典型陷阱 |
|:--|:--|:--|:--|
| **[9.1 问题设定：超过单卡容量](sec91.md)** | 显存到底被什么占满了？「放不下」有几种？ | 混合精度 Adam 下模型状态 $=16N$ 字节（参数 2 + 梯度 2 + fp32 主权重 4 + $m$ 4 + $v$ 4）；激活与批大小、序列长度成正比，且**不受分片影响** | 只算参数量、忘了优化器状态与激活；把「放不下」笼统当成一个问题，不分模型状态 / 激活 / 单层 |
| **[9.2 数据并行：从 DP 到 FSDP](sec92.md)** | 每卡一份完整副本为什么浪费？分片能省多少、代价是什么？ | 梯度 All-Reduce 通信量 $\approx2P$（字节，bf16）且**与批大小无关**；ZeRO-1/2/3 逐级分片后每卡模型状态 $16N\to11N\to7.75N\to2N$（8 卡） | 以为加大批大小会加大通信量（恰好相反）；以为分片越彻底越好（ZeRO-3 通信更多、可能更慢） |
| **[9.3 张量并行：把一层切开](sec93.md)** | 单层放不下时怎么切？为什么要列切与行切成对？ | 列切免通信、行切需一次 All-Reduce；MLP「列切 → 逐元素激活 → 行切」每块前向仅一次 All-Reduce；注意力按头切；通信密集 → 必须留在节点内 | 以为张量并行的通信量会随并行度下降（不会，只随消息变小）；跨节点硬上张量并行 |
| **[9.4 流水线并行：把网络切成段](sec94.md)** | 按层切分后，为什么卡在空转？怎么压掉？ | 朴素调度气泡占比 $\dfrac{P-1}{M+P-1}$（推导见 9.4.2）；三种手段：增大 micro-batch 数 $M$、交错调度、zero-bubble 拆分反向 | 以为流水线能缓解单卡显存（它降低单卡 batch，激活压力更小但每段要排队）；以为 1F1B 消除气泡 |
| **[9.5 显存优化：混合精度、重计算与分片](sec95.md)** | 不切模型能省多少？每种手段的代价是什么？ | BF16 靠宽指数范围免损失缩放；FP8 需缩放且需新硬件；激活重计算用约 1/3 的额外前向换亚线性激活显存；8-bit 优化器省 37.5% 静态显存；QLoRA 把 7B 微调压到「一张 24 GB 卡」量级 | 以为混合精度「白拿不掉点」；把 FP8 缩放与 FP16 的损失缩放搞混；把激活重计算当成能省参数显存 |
| **[9.6 通信、容错与工程实践](sec96.md)** | 通信量怎么估？万卡规模下坏了怎么办？ | 环状 All-Reduce 每卡 $\approx2S$；重叠与分桶是吞吐关键；故障是常态（checkpoint 策略与恢复时间要一起设计）；确定性与吞吐常常互斥，要先定口径 | 只算通信量不算通信时间（漏了带宽与延迟）；把「能重启」当成「不用做 checkpoint 策略」 |
| **[9.7 动手：为 Lab 3 选一套并行策略](sec97.md)** | 手上只有 1–8 张卡时，究竟该怎么配？ | 五步决策：显存估算 → 是否分片 → 是否 TP/PP → 批大小与梯度累积 → 精度与重计算；接着算吞吐与验收指标；受限显存下 LoRA / QLoRA 往往比任何并行都省 | 照搬大厂配置；只调一个旋钮（批大小 / 梯度累积 / 重计算要成套改）；不看扩展效率只看总吞吐 |

## 本讲与 Lab 3 的关系

[Lab 3](../../labs/lab3.md) 的任务是「加载一个预训练大语言模型，用 LoRA 在受限显存下微调」。它与本讲的关系是**互补而非重叠**：

- **Lab 3 走「省」路线**：冻结主干、只训低秩适配器 $W=W_0+BA$（[定义 9.5.1](sec95.md)），于是需要优化器照料的参数从 $N$ 降到 $O(r(d+k))$，显存账本从 $16N$ 变成「低精度主干 + 适配器」。这条路不需要多卡，也不需要通信。
- **本讲走「切」路线**：当真要改动全部参数（全参微调、预训练、继续预训练）时，$16N$ 的账本无法靠 PEFT 绕过，只能靠 [9.2](sec92.md)–[9.4](sec94.md) 的并行与 [9.5](sec95.md) 的省显存手段。
- **两讲的接点在 [9.7](sec97.md)**：那一节把「1–8 张卡」的所有情形列成一张表——什么规模该全参 + ZeRO、什么规模该 QLoRA、什么时候两者叠加，并给出排错清单。Lab 3 里的 OOM 排查（先降 batch、再上梯度累积、开混合精度、减 $r$ 或 max_length）正是那张表的简化版。

**一句话**：Lab 3 教你「不动大模型就能适配它」，本讲教你「非要动它时怎么动得起」。两者合起来才是完整的工程答案。

## 本讲不覆盖什么（避免期望错位）

1. **不讲集群运维的体力活**：机房、网络布线、驱动与 CUDA 版本矩阵、容器与调度器（Slurm / Kubernetes）只在本讲需要的地方点到，不展开。
2. **不给具体厂商硬件的选型建议**：所有带宽与算力数字都写成「量级 + 算式」，你可以用自己机器的实测值替换。
3. **不复述某个框架的完整文档**：本讲给接口片段与配置字段，用来锚定概念；真实项目请以对应版本的官方文档为准。
4. **不承诺任何数字能直接套在你的任务上**：账本是下界估算，通信与利用率依赖拓扑与实现，必须实测对账（[9.7](sec97.md) 的验收步骤）。
