前 12 章各自解决了一个局部问题：第 2 章把字符流变成 token 和 AST，第 4 章把语句降成三地址码（three-address code，TAC）与控制流图（control-flow graph，CFG），第 6 章在静态单赋值（static single assignment，SSA）上做常量传播和死代码消除（dead code elimination，DCE），第 8 章把中间表示（intermediate representation，IR）变成遵守 System V（SysV）调用约定的 x86-64。每一章都能单独跑实验，但它们拼在一起时会出现一类新的错误：每个 pass 单独看都对，边界处的合同却对不上。典型例子是 phi 节点消解：SSA 构造正确、常量传播正确、指令选择正确，但把 phi 复制放在分支的错误一侧，循环第二次迭代就会读到旧值。

这一章做一个完整的项目 <code>projects/minic/</code>，用 Python 3.11+ 标准库实现一个迷你 C 编译器。它只有一种类型（32 位有符号 int），支持变量、赋值、算术/比较/逻辑、<code>if/else</code>、<code>while</code>、函数、<code>return</code> 和 <code>print(expr);</code>。它不追求语言覆盖率，追求的是**每一层都能被独立观察和验证**：词法分析器（lexer）能打印词法单元（token）与行列号，语法分析器（parser）能打印抽象语法树（abstract syntax tree，AST），IR 能打印 TAC 与 CFG，SSA 能打印 phi 节点，后端能打印汇编并能用反汇编器核对栈帧。

项目的第一条验收线不是「能编译 fib」，而是**同一程序在四条执行路径上输出一致**：直接 TAC 解释器、优化后 SSA 解释器、未优化 x86-64 代码、优化后 x86-64 代码。第二条验收线是应用二进制接口（application binary interface，ABI）：任何一条返回路径上，<code>call</code> 前的 <code>rsp</code> 都是 0 mod 16，callee 入口是 8 mod 16，prologue 的 <code>subq</code> 是 16 的倍数。第三条验收线是**明确报错**：数组、指针、浮点、<code>for</code>、全局变量等不在子集里的东西必须在词法、语法或语义阶段拒绝，而不是悄悄生成错误代码。

一个具体的反例先放在这里。<code>loop.mc</code> 求 1 到 100 的和，正确答案是 5050。如果 SSA 只给 <code>if</code> 的合流插 phi，却漏掉 <code>while</code> 回边，循环头会一直使用进入循环时的 <code>sum</code> 值，输出会停在第一次迭代的结果上。这个错误不会被「编译成功」发现，也不会被单条指令的单元测试发现；它只能被**跨路径对拍**或 **SSA 验证器**抓住。本章的工具链就是为这类错误准备的。

本章的实验入口是 <code>experiments/ch13/run.sh</code>，项目根目录是 <code>projects/minic/</code>。所有命令默认在 <code>compilers/</code> 下执行。

## 13.1 项目目标、语言子集与验收标准 {#sec-compilers.4.13.1}

先明确「完成」是什么意思。一个玩具编译器很容易做到「对某个例子能跑」，难的是在输入变化、优化开关切换、目标平台切换时仍然给出同一语义。minic 的验收标准因此分成四组：结构、语义、代码生成、错误处理。每组都对应一条可以复制粘贴的命令，而不是一句主观判断。

| 组 | 验收问题 | 命令 | 通过标准 |
|:--|:--|:--|:--|
| 结构 | 每个阶段能否单独输出？ | <code>--emit=tokens/ast/ir/cfg/ssa/asm</code> | 退出码 0，输出非空且可读 |
| 语义 | 解释器与机器码是否一致？ | <code>bash projects/minic/run&#95;tests.sh</code> | 42 个用例；成功用例 4 种模式，错误用例 1 种入口 |
| 代码生成 | 栈帧与寄存器是否守约？ | <code>clang -target ... -c</code> + <code>llvm-objdump -d</code> | <code>subq</code> 是 16 的倍数，无 <code>movq</code> 写 32 位寄存器 |
| 错误处理 | 不支持的输入是否明确拒绝？ | 14 个 <code>err&#95;&#42;.mc</code> 用例 | 退出码 1，<code>file:line:col: error:</code>，信息含原因 |

这张表把「能跑」拆成了可检查的四个面。注意第三组：汇编能生成不等于代码正确；必须把生成物真的交给汇编器，再用反汇编器读回栈帧。第四组同样重要：一个编译器对不支持特性的态度，决定了它的错误是「诊断」还是「静默错编」。

::: def 定义 13.1.1 · minic 程序与语义契约 {#def-compilers.4.13.1.1}
一个 minic 程序是若干函数定义的序列，必须包含 <code>int main()</code>。所有值都是 32 位有符号整数。语义约定如下，解释器与代码生成必须共同遵守：

1. 算术按二进制补码回绕；<code>+ - &#42;</code> 的结果对 2^32 取模后再解释为有符号数。这与 C 的有符号溢出 UB 不同，是为了让两条执行路径可以逐位对拍。
2. 除法向零截断，余数符号与被除数一致；除数为 0 是运行期错误（解释器报错，机器码触发 <code>SIGFPE</code>）。
3. 局部变量在声明处零初始化；参数由调用者传入。C 中未初始化局部变量的值不确定，minic 选择确定值以消除对拍噪声。
4. 比较与逻辑运算的结果是 0 或 1；<code>&&</code> 与 <code>||</code> 短路求值。
5. 函数可以先用后定义：语义分析先收集所有签名，再检查函数体。C 需要显式原型，这是 minic 的有意放宽。
6. 非 <code>main</code> 函数必须在所有结构化路径上 <code>return</code>；<code>main</code> 走到末尾等价于 <code>return 0</code>。
:::

第 1 条和第 3 条是「为对拍而设计」的语义。真实 C 编译器不能这样规定，因为 C 标准把溢出让给实现，把未初始化值留给不确定性；但教学项目需要一个确定性的参考语义，否则解释器与机器码的差异会混入 UB，无法判断是编译器 bug 还是程序 bug。第 5 条则减少了初学者的负担，同时保留了一个真实问题：签名收集与函数体检查必须分两遍。

语言子集的文法如下。它省略了类型说明符的多样性，只保留 <code>int</code>；省略了声明符的复杂性，只保留单个标识符；省略了表达式语句中的赋值表达式，把赋值限制为语句。

```text
program   ::= function+
function  ::= 'int' IDENT '(' params? ')' block
params    ::= 'int' IDENT (',' 'int' IDENT)*        // 至多 6 个
block     ::= '{' stmt* '}'
stmt      ::= 'int' IDENT ('=' expr)? ';'
            | IDENT '=' expr ';'
            | 'if' '(' expr ')' stmt ('else' stmt)?
            | 'while' '(' expr ')' stmt
            | 'return' expr ';'
            | 'print' '(' expr ')' ';'
            | block
            | expr ';'
expr      ::= INT | IDENT | IDENT '(' args? ')'
            | '(' expr ')'
            | ('-' | '!') expr
            | expr ('*' | '/' | '%') expr
            | expr ('+' | '-') expr
            | expr ('<' | '<=' | '>' | '>=') expr
            | expr ('==' | '!=') expr
            | expr '&&' expr
            | expr '||' expr
args      ::= expr (',' expr)*
```

这张文法里没有数组、指针、结构体、浮点、字符串、全局变量、<code>for</code>、<code>switch</code>、<code>break</code>、<code>continue</code>。这不是「以后再加」，而是本章的边界：每增加一个特性，就要增加类型、布局、ABI 或控制流的一整套合同。项目的价值在于把已有子集做透，而不是把 C 复刻一遍。

| 特性 | 语法 | 语义 | 对应测试 |
|:--|:--|:--|:--|
| 变量与赋值 | <code>int x = e;</code>、<code>x = e;</code> | 块作用域，声明处零初始化 | <code>reassign.mc</code>、<code>shadowing.mc</code> |
| 算术 | <code>+ - &#42; / %</code> | 32 位回绕，除法向零截断 | <code>arith&#95;precedence.mc</code>、<code>division.mc</code> |
| 比较/逻辑 | <code>== != &lt; &lt;= &gt; &gt;= &amp;&amp; &#124;&#124; !</code> | 结果 0/1，短路 | <code>compare.mc</code>、<code>conditions.mc</code> |
| 控制流 | <code>if/else</code>、<code>while</code> | 结构化 CFG，循环回边 | <code>if&#95;else.mc</code>、<code>loop&#95;phi.mc</code> |
| 函数 | 至多 6 个 int 参数 | SysV 寄存器传参，递归 | <code>six&#95;args.mc</code>、<code>recursion&#95;fib.mc</code> |
| 输出 | <code>print(e);</code> | 十进制加换行 | <code>print.mc</code>、<code>call&#95;statement.mc</code> |
| 注释 | <code>//</code>、<code>/&#42; &#42;/</code> | 不嵌套，未闭合报错 | <code>comments.mc</code>、<code>err&#95;unterminated&#95;comment.mc</code> |

上表的测试名都在 <code>projects/minic/tests/cases/</code> 下。写文档时名字必须落到真实文件，这也是本章反复强调「证据」的原因。

::: note 与 C 的三处有意差异
第一，溢出回绕而不是 UB；第二，局部变量零初始化；第三，函数可以先用后定义。三处差异都写在 <code>projects/minic/README.md</code> 的「已知限制」里。它们让对拍有意义，但也意味着 minic 不是 C 的子集实现，而是一个**语义被固定下来的 C 风格语言**。不要把 minic 的程序直接当作 C 程序来推理。
:::

### 四条验收线分别防什么

结构线防的是「阶段不可观察」。如果只能看到最终输出，一旦解释器与机器码不一致，你无法判断是 TAC 降级、SSA 重命名还是指令选择出了问题。<code>--emit</code> 把每个中间形态变成可 diff 的文本，让错误定位从「猜」变成「缩小范围」。

语义线防的是「单点正确、组合错误」。每个 pass 都可以单独通过单元测试，但 pass 之间的合同可能被破坏：优化把活跃值删了，或者 phi 消解把复制放错了边。四条执行路径的对拍是端到端的合同测试，它不关心内部实现，只比较可观察行为。

ABI 线防的是「本机能跑、别的机器崩溃」。栈对齐错误常常不立即崩溃，而是在某个 libc 版本的 printf 里触发；如果测试只检查输出，可能会漏掉。把 <code>subq</code> 的对齐写成静态断言，再用 objdump 独立验证，才能把偶发问题变成稳定失败。

错误线防的是「静默错编」。一个编译器最危险的行为不是拒绝复杂输入，而是把不支持的输入编译成看似能跑、结果错误的程序。保留字提前拦截、错误用例断言诊断形状，都是为了让拒绝本身可测试。

| 模式 | 入口 | 谁调用 | 失败时先看 |
|:--|:--|:--|:--|
| 直接解释 | <code>--run</code> | 测试脚本、手工调试 | <code>--emit=ir</code> |
| 优化解释 | <code>--run --opt</code> | 差分测试 | <code>--emit=ssa --opt</code> |
| 生成代码 | <code>--run-compiled</code> | 差分测试、CI | <code>--emit=asm</code> + objdump |
| 只生成 | <code>--emit=asm</code> | 交叉目标检查 | <code>clang -c</code> |

## 13.2 架构：driver、lexer、parser、sema、IR、SSA、opt、codegen {#sec-compilers.4.13.2}

minic 的模块划分不是按「文件越小越好」，而是按**可替换的合同**：每个模块只依赖前一个模块的数据结构，不回头读源码文本。lexer 只认识字符，parser 只认识 token，语义分析（sema）只认识 AST，TAC 只认识已解析的符号，SSA 只认识 CFG，代码生成（codegen）只认识已消解 phi 的 TAC。这条单向依赖让每个阶段都能单独测试，也让错误定位有明确边界。

<pre class="layout">
source .mc
   │  lexer.py            字符 → token（行、列、注释）
   ▼
tokens ───────────────────► --emit=tokens
   │  parser.py           递归下降 + Pratt
   ▼
AST ──────────────────────► --emit=ast
   │  sema.py             函数表、作用域、符号解析、返回路径
   ▼
TAC（扁平指令 + 标签） ───► --emit=ir / --run（直接解释）
   │  tac.py: build_cfg + prune_unreachable
   ▼
CFG（基本块 + 前驱/后继） ─► --emit=cfg
   │  ssa.py: 支配树、支配边界、剪枝 phi、重命名
   ▼
SSA（每个名字单一定义） ──► --emit=ssa
   │  opt.py: 常量传播、折叠、DCE、清理不可达块
   ▼
optimized SSA
   │  lower.py: phi 消解（边块 + 两阶段并行复制）
   ▼
lowered TAC ──────────────► --run --opt（优化后解释）
   │  codegen.py: 栈槽分配 + 指令选择
   ▼
x86-64 汇编 ──────────────► --emit=asm / clang / ld
</pre>

读图：从左到右是数据形态的变化，从右到左是证据的回流。每一个 <code>--emit</code> 都把某一层的完整状态暴露出来；每一条箭头都可能失败，失败信息必须带源码位置。图中的 <code>--run</code> 走的是扁平 TAC，不经过 SSA；<code>--run --opt</code> 和 <code>--emit=asm</code> 走的是 SSA 与 phi 消解。这个分叉是故意保留的：它让「直接语义」与「优化后语义」成为两条独立路径。

各阶段的输入输出与失败模式：

| 阶段 | 模块 | 输入 → 输出 | 典型失败 | 诊断位置 |
|:--|:--|:--|:--|:--|
| 词法 | <code>lexer.py</code> | 字符 → token | 非法字符、未闭合注释、整数字面量越界 | 精确到列 |
| 语法 | <code>parser.py</code> | token → AST | 缺分号/括号、非法语句、嵌套过深 | 当前 token |
| 语义 | <code>sema.py</code> | AST → 带符号 AST | 未声明、重复声明、参数个数、缺 return | 声明/调用处 |
| 降级 | <code>tac.py</code> | AST → TAC | 内部不变量（未解析符号） | 不应发生 |
| CFG | <code>tac.py</code> | TAC → 基本块 | 跳到不存在的标签 | 内部错误 |
| SSA | <code>ssa.py</code> | CFG → SSA | phi 操作数与前驱不匹配、重复定义 | 内部错误 |
| 优化 | <code>opt.py</code> | SSA → SSA | 常量传播不收敛 | 内部错误 |
| 消解 | <code>lower.py</code> | SSA → TAC | phi 缺少前驱 | 内部错误 |
| 后端 | <code>codegen.py</code> | TAC → asm | 槽未分配、超过 6 参数 | 内部错误 |

这张表有一个重要设计：**用户错误与编译器错误分开**。前者用 <code>MiniError</code>，带 span，退出码 1；后者用 <code>InternalError</code>，退出码 3，表示「这是编译器的 bug，不是你的程序的问题」。如果不分开，SSA 验证失败会被误报成源码错误，排查方向就错了。

驱动器（driver）的核心只有十几行，但它决定了流水线的顺序：

```python
tac = lower_program(program)
ssa = [build_ssa(fn) for fn in tac]
for fn in ssa:
    problems = verify_ssa(fn)
    if problems:
        raise InternalError("; ".join(problems))
if args.opt:
    opt_funcs = []
    for fn in ssa:
        fn2, st = optimize(fn)
        problems = verify_ssa(fn2)
        if problems:
            raise InternalError("optimized SSA: " + "; ".join(problems))
        opt_funcs.append(fn2)
    ssa = opt_funcs
```

这段代码验证三件事：第一，SSA 构造后立刻验证，而不是等 codegen 崩了才检查；第二，优化后再验证一次，因为常量折叠和不可达块清理会改动 phi 的操作数；第三，验证失败是内部错误，不会伪装成用户错误。最后一点在团队协作里很关键：如果 agent 生成的 pass 破坏了 SSA，错误信息应该指向 pass，而不是用户的 <code>.mc</code> 文件。

::: def 定义 13.2.1 · pass 合同 {#def-compilers.4.13.2.1}
一个 pass 是函数 <code>P: S → S</code>，它必须满足三条合同：

1. **类型保持**：输出仍是同一层的合法结构；SSA pass 的输出必须通过 <code>verify&#95;ssa</code>。
2. **语义保持**：对每个输入程序，优化前后的可观察行为一致；minic 的可观察行为是 <code>print</code> 的输出序列、<code>main</code> 的返回值，以及运行期错误是否发生。
3. **可定位**：失败时报告违反的是哪条不变量、哪个函数、哪个块，而不是只抛一个 <code>KeyError</code>。
:::

第 2 条里的「运行期错误是否发生」常被忽略。DCE 如果删除一个未被使用的 <code>a / b</code>，而 <code>b</code> 可能为 0，就改变了可观察行为。minic 的处理是把 <code>/</code> 和 <code>%</code> 当作有副作用的指令，永远不因为结果未使用而删除。这个选择牺牲了一点优化机会，换来一条可以写进合同的保守规则。

CLI 的形状也按合同设计：

| 参数 | 作用 | 依赖的阶段 |
|:--|:--|:--|
| <code>--emit=tokens</code> | 只做词法 | lexer |
| <code>--emit=ast</code> | 解析并做语义检查 | parser + sema |
| <code>--emit=ir</code> | 扁平 TAC；配 <code>--opt</code> 时输出消解后的优化 TAC | 到 TAC / lower |
| <code>--emit=cfg</code> | 基本块与前驱/后继 | 到 CFG |
| <code>--emit=ssa</code> | SSA；配 <code>--opt</code> 时输出优化后 SSA | 到 SSA / opt |
| <code>--emit=asm</code> | x86-64 汇编 | 到 codegen |
| <code>--run</code> | 直接 TAC 解释器 | 到 TAC |
| <code>--run --opt</code> | 优化后 SSA 的解释器 | 到 lower |
| <code>--run-compiled</code> | 汇编、链接、执行 | 到 codegen + clang |

表中没有 <code>--emit=lexer</code> 这种别名，也没有隐式的默认动作：必须显式选择 <code>--emit</code>、<code>--run</code>、<code>--run-compiled</code> 或 <code>--build</code> 之一。这样脚本里的行为是可预测的，不会因为版本升级突然从「打印 IR」变成「执行程序」。


### pass 顺序的硬约束

流水线的顺序不是风格问题，而是数据依赖。sema 必须在 TAC 之前，因为 TAC 需要 <code>sym.tac&#95;name</code>；CFG 必须在 SSA 之前，因为 phi 插入要支配边界；优化必须在 phi 消解之前，否则常量传播看不到 phi 的合流信息；phi 消解必须在槽分配之前，因为复制会引入新的临时名。

| 约束 | 如果违反 | 现象 |
|:--|:--|:--|
| sema 在 TAC 前 | TAC 拿到未解析的 <code>Var</code> | 内部错误或名字猜测 |
| CFG 在 SSA 前 | 没有前驱/后继，无法算支配边界 | phi 插错位置 |
| 优化在消解前 | 优化器看到的是复制而不是 phi | 常量传播漏掉合流 |
| 消解在分配前 | 新临时量没有栈槽 | codegen 报 <code>no slot</code> |

因此 driver 不提供「跳过 sema」或「先分配后消解」的开关。可调试的是输出，不是阶段顺序；顺序错了，输出也会骗人。

## 13.3 Step 1：词法与 Pratt 表达式解析 {#sec-compilers.4.13.3}

词法分析要解决三个具体问题：token 的边界、注释的消除、位置的保留。minic 没有字符串和预处理，手写扫描器只需要一个字符的前瞻；真正的坑在 <code>/</code> 与注释的歧义，以及 <code>&amp;&amp;</code> 必须优先于单个 <code>&amp;</code>。

扫描循环按优先级排列：先跳空白，再识别 <code>//</code> 与 <code>/&#42; &#42;/</code>，再识别数字、标识符、双字符运算符、单字符运算符。顺序不能反：如果先匹配单字符 <code>/</code>，注释就永远进不去；如果先匹配 <code>&amp;</code>，<code>&amp;&amp;</code> 会被拆成两个 token。

```text
if ch == "/" and self._peek(1) == "/":
    self._line_comment()
    continue
if ch == "/" and self._peek(1) == "*":
    self._block_comment()
    continue
if ch.isdigit():
    self._number()
    continue
if ch.isalpha() or ch == "_":
    self._identifier()
    continue
two = ch + self._peek(1)
if two in TWO_CHAR:
    self._advance()
    self._advance()
    self.tokens.append(Token(two, two, self._span_from(line, col)))
    continue
```

这段代码验证「最大匹配」的实现方式：先看两个字符的组合，再退回单字符。块注释不嵌套，遇到第一个 <code>&#42;/</code> 结束；文件结束时仍未闭合，报 <code>unterminated block comment</code>，span 指向 <code>/&#42;</code> 的起始位置。注释内部的换行会更新行列号，因此注释之后的 token 仍然有正确位置。

token 的种类不多，但每种都要有稳定的显示形式：

| 类别 | 例子 | kind | 附加信息 |
|:--|:--|:--|:--|
| 关键字 | <code>int if else while return print</code> | 关键字本身 | 无 |
| 标识符 | <code>main fib x</code> | <code>IDENT</code> | 文本 |
| 整数字面量 | <code>0 42 2147483647</code> | <code>INT</code> | 解析后的值 |
| 双字符运算符 | <code>== != &lt;= &gt;= &amp;&amp; &#124;&#124;</code> | 运算符本身 | 无 |
| 单字符 | <code>+ - &#42; / % = &lt; &gt; ! ( ) { } , ;</code> | 字符本身 | 无 |
| 结束 | 文件末尾 | <code>EOF</code> | 最后的行列 |

词法阶段还承担一项「提前拒绝」的职责：C 的保留字 <code>for</code>、<code>char</code>、<code>struct</code>、<code>goto</code> 等一旦出现，立即报「minic does not support ...」。如果不在这里拦截，parser 会把它们当作标识符，错误信息会变成「expected ';'」，用户需要猜很久。错误信息应该尽量在最早知道原因的地方给出。

真实输出如下。命令只取前 18 行，避免刷屏：

```bash
python3 projects/minic/minic.py projects/minic/tests/cases/arith_precedence.mc --emit=tokens | sed -n '1,18p'
```

```text
int      int          3:1
IDENT    main         3:5
(        (            3:9
)        )            3:10
{        {            3:12
print    print        4:5
(        (            4:10
INT      2            4:11
+        +            4:13
INT      3            4:15
*        *            4:17
INT      4            4:19
)        )            4:20
;        ;            4:21
print    print        5:5
(        (            5:10
(        (            5:11
INT      2            5:12
```

注意第一行是 <code>3:1</code>，因为用例前两行是 <code>// expect:</code> 注释。行列号不是装饰：后面的 <code>file:line:col: error:</code> 直接使用这里的 span，caret 的位置也依赖它。如果 lexer 在跳过注释时忘记更新换行，所有后续诊断都会偏移。

表达式解析用 Pratt 算法。每个二元运算符有一个绑定力（binding power），循环里只做一件事：只要下一个运算符的绑定力不低于当前下界，就把它收进来。左结合通过「右操作数用 <code>bp + 1</code> 解析」实现，右结合则传 <code>bp</code>。minic 的所有二元运算符都是左结合，因此表里只需要一个数字。

```text
left = self.parse_prefix()
while True:
    op_tok = self.peek()
    bp = BIN_PREC.get(op_tok.kind)
    if bp is None or bp < min_bp:
        break
    self.advance()
    right = self.parse_expr(bp + 1)
    left = Binary(
        Span(left.span.line, left.span.col, right.span.end_line, right.span.end_col),
        op_tok.kind, left, right,
    )
return left
```

绑定力表把优先级集中在 <code>nodes.BIN&#95;PREC</code> 一处：

| 优先级 | 运算符 | 结合性 | 例子 |
|--:|:--|:--|:--|
| 1 | <code>&#124;&#124;</code> | 左 | <code>a &#124;&#124; b &#124;&#124; c</code> |
| 2 | <code>&amp;&amp;</code> | 左 | <code>a &amp;&amp; b &amp;&amp; c</code> |
| 3 | <code>== !=</code> | 左 | <code>a == b == c</code> |
| 4 | <code>&lt; &lt;= &gt; &gt;=</code> | 左 | <code>a &lt; b &lt; c</code> |
| 5 | <code>+ -</code> | 左 | <code>a - b - c</code> |
| 6 | <code>&#42; / %</code> | 左 | <code>a / b / c</code> |
| 7 | 前缀 <code>- !</code> | 右 | <code>-!a</code> |

::: ex 例 13.3.1 · 用绑定力走一遍 2 + 3 * 4 {#ex-compilers.4.13.3.1}
解析 <code>2 + 3 &#42; 4</code> 时，<code>parse&#95;expr(1)</code> 先读出 <code>2</code>，看到 <code>+</code>（bp=5），解析右操作数 <code>parse&#95;expr(6)</code>。右操作数读出 <code>3</code>，看到 <code>&#42;</code>（bp=6，不小于 6），于是把 <code>3 &#42; 4</code> 收进来，返回 <code>(3 &#42; 4)</code>。外层再把 <code>+</code> 收进来，得到 <code>(2 + (3 &#42; 4))</code>。如果右操作数用 <code>parse&#95;expr(5)</code>，<code>+</code> 也会被收进右子树，结果变成右结合，<code>10 - 3 - 2</code> 会算成 9 而不是 5。测试 <code>arith&#95;assoc.mc</code> 专门覆盖这一点。
:::

语法阶段还要处理两个边界：函数参数必须带 <code>int</code>（<code>int f(int x)</code>，不是 <code>int f(x)</code>），以及一元运算符的优先级高于所有二元运算符。<code>-a &#42; b</code> 解析成 <code>(-a) &#42; b</code>，而不是 <code>-(a &#42; b)</code>；两者在整数回绕下可能不同，例如 <code>a = -2147483648</code> 时。测试 <code>unary.mc</code> 覆盖了嵌套的一元运算。

Pratt 解析器还设置了嵌套上限 <code>MAX&#95;DEPTH = 200</code>。这不是为了限制正常程序，而是为了让恶意输入（两百层括号）得到一条诊断，而不是 Python 的 <code>RecursionError</code>。诊断的边界也属于合同：用户可以接受「嵌套太深」，不能接受「解释器崩了」。


### 词法边界用例

| 输入 | token 序列 | 说明 |
|:--|:--|:--|
| <code>1--2</code> | INT <code>-</code> <code>-</code> INT | 不是注释，也不是自减 |
| <code>a/&#42;x&#42;/b</code> | IDENT IDENT | 块注释等价于空白 |
| <code>12ab</code> | 错误 | 数字后紧跟标识符字符，报非法字面量 |
| <code>/&#42;/</code> | 错误 | 缺少配对的 <code>&#42;/</code> |
| <code>a/&#42;x&#42;/+b</code> | IDENT <code>+</code> IDENT | 注释不产生 token |

第 1 行说明为什么不能把 <code>--</code> 当注释：C 的 <code>--</code> 是自减运算符，minic 不支持自减，但两个减号仍然合法。<code>1 - -2</code> 的结果是 3，如果 lexer 把 <code>--</code> 吞掉，parser 会看到 <code>1 2</code>，报「expected ';'」，错误信息指向错误的位置。

第 3 行是最大匹配的反例：<code>12ab</code> 不能被拆成 <code>12</code> 和 <code>ab</code>，因为 C 的预处理数字是一个整体；minic 直接拒绝，避免用户以为它声明了一个叫 <code>ab</code> 的变量。词法阶段能做的边界判断，不要留给语法阶段。

## 13.4 Step 2：语句、函数与作用域/类型检查 {#sec-compilers.4.13.4}

minic 只有一种类型，所以「类型检查」在这一章被压缩成三件事：名字是否可见、调用参数个数是否匹配、非 <code>main</code> 函数是否在所有路径上返回。这不是偷懒，而是把类型系统的位置留出来：如果以后加入数组或结构体，检查器会在这里长出新的规则，而 lexer、TAC、codegen 的结构不需要重写。

AST 的节点分成表达式和语句两组：

| 节点 | 关键字段 | 语义 |
|:--|:--|:--|
| <code>IntLit</code> | <code>value</code> | 整数字面量 |
| <code>Var</code> | <code>name</code>、<code>sym</code> | 变量引用，sema 填入符号 |
| <code>Unary</code> | <code>op</code>、<code>operand</code> | <code>-</code> 或 <code>!</code> |
| <code>Binary</code> | <code>op</code>、<code>left</code>、<code>right</code> | 算术/比较/逻辑 |
| <code>Call</code> | <code>name</code>、<code>args</code> | 函数调用 |
| <code>Block</code> | <code>stmts</code> | 语句序列，引入作用域 |
| <code>Decl</code> | <code>name</code>、<code>init</code>、<code>sym</code> | 局部变量声明 |
| <code>Assign</code> | <code>name</code>、<code>value</code>、<code>sym</code> | 赋值语句 |
| <code>If</code> | <code>cond</code>、<code>then</code>、<code>otherwise</code> | 条件分支，else 可空 |
| <code>While</code> | <code>cond</code>、<code>body</code> | 循环 |
| <code>Return</code> | <code>value</code> | 返回值 |
| <code>Print</code> | <code>value</code> | 打印十进制加换行 |

sema 分两遍。第一遍收集函数签名：函数名不能重复，参数不能重名，参数不超过 6 个，<code>main</code> 必须存在且没有参数。第二遍逐个检查函数体：建立作用域栈，解析变量引用，检查调用，最后做「结构化返回」判断。两遍的必要性来自前向调用：<code>main</code> 可以调用在文件后面定义的 <code>twice</code>，所以检查 <code>main</code> 时签名表必须已经完整。

```python
def declare(self, name, span, kind="local"):
    if name in self.scopes[-1]:
        raise MiniError(f"duplicate declaration of '{name}' in this scope", span)
    self.uid += 1
    sym = Symbol(name, self.uid, kind, span)
    self.scopes[-1][name] = sym
    return sym

def lookup(self, name, span):
    for scope in reversed(self.scopes):
        if name in scope:
            return scope[name]
    raise MiniError(f"undeclared variable '{name}'", span)
```

这段代码验证两件事：重复声明只在**当前最内层作用域**报错，外层同名变量被合法遮蔽；查找从内向外，第一个匹配的符号胜出。符号带一个自增的 <code>uid</code>，TAC 名字是 <code>name.uid</code>，例如 <code>x.1</code>、<code>x.2</code>。这样即使源码里两个 <code>x</code> 分别位于不同块，后续阶段也不会混淆。

::: def 定义 13.4.1 · 作用域与绑定 {#def-compilers.4.13.4.1}
minic 的作用域规则与 C 的块作用域一致：

1. 函数参数位于函数体最外层作用域，函数体的大括号再引入一层。
2. 每个 <code>{ }</code> 引入一层作用域，退出时弹出。
3. <code>if</code>/<code>while</code> 的子语句即使没有大括号，也拥有独立作用域；这是 C 的规则，防止 <code>if (c) int x = 1;</code> 的 <code>x</code> 泄漏到外面。
4. 内层声明可以遮蔽外层同名变量；内层退出后，外层绑定恢复。
5. 引用未声明的名字是错误，不存在隐式全局变量。
:::

第 3 条很容易被忽略。很多手写编译器只在大括号处压栈，于是 <code>if (1) int x = 2;</code> 的 <code>x</code> 会被登记到外层，后面的 <code>print(x)</code> 竟然能通过检查。测试 <code>err&#95;scope.mc</code> 就是为这条规则准备的：它必须在 <code>print(x)</code> 处报 <code>undeclared variable 'x'</code>。如果实现漏了隐式作用域，这个用例会失败。

语义检查的完整清单：

| 检查 | 触发例子 | 错误信息（片段） |
|:--|:--|:--|
| 重复函数 | 两个 <code>int f()</code> | <code>duplicate function 'f'</code> |
| 参数过多 | 7 个参数 | <code>at most 6</code> |
| 参数重名 | <code>int f(int a, int a)</code> | <code>duplicate parameter 'a'</code> |
| 缺少 main | 只有 <code>f</code> | <code>missing entry point 'int main()'</code> |
| main 带参 | <code>int main(int argc)</code> | <code>main must take no parameters</code> |
| 未声明变量 | <code>print(x)</code> | <code>undeclared variable 'x'</code> |
| 重复声明 | 同一块内两个 <code>int x</code> | <code>duplicate declaration</code> |
| 未知函数 | <code>foo(1)</code> | <code>unknown function 'foo'</code> |
| 参数个数 | <code>add(1)</code>，add 收两个 | <code>expects 2 argument(s), got 1</code> |
| 缺返回 | 非 main 的某条路径无 return | <code>may reach the end without returning</code> |
| 调用 main | <code>main()</code> | <code>calling 'main' is not supported</code> |

「缺返回」用结构化的 <code>definitely&#95;returns</code> 判断，而不是跑一遍所有输入：<code>return</code> 为真；语句块的任意一条语句确定返回则为真；<code>if</code> 要求两个分支都确定返回；<code>while</code> 一律为假（可能一次都不执行，也可能不终止）。这是保守但可判定的规则。它不会接受「循环条件恒真所以后面不可达」这种需要值分析的写法，但也不会漏报。

```python
def definitely_returns(stmt):
    if isinstance(stmt, Return):
        return True
    if isinstance(stmt, Block):
        return any(definitely_returns(s) for s in stmt.stmts)
    if isinstance(stmt, If):
        return (stmt.otherwise is not None
                and definitely_returns(stmt.then)
                and definitely_returns(stmt.otherwise))
    return False
```

这段判断的代价是保守：<code>while (1) { }</code> 后面的代码不会被认定为不可达，函数仍会被要求返回。这是有意的取舍——要证明循环不终止，需要终止性分析，而本章的目标是把已有结构做对，不是引入一个新的研究问题。

作用域解析之后，AST 上每个 <code>Var</code>、<code>Decl</code>、<code>Assign</code> 都带有 <code>Symbol</code>。TAC 阶段不再查名字，直接用 <code>sym.tac&#95;name</code>。这条「解析一次，后面只读注解」的规则减少了重复实现，也让错误定位集中在 sema。如果 TAC 阶段还需要猜名字，说明 sema 的合同没有完成。

真实诊断如下。<code>err&#95;undeclared.mc</code> 的 <code>print(x)</code> 在第 3 行第 11 列：

```bash
python3 projects/minic/minic.py projects/minic/tests/cases/err_undeclared.mc --run
```

```text
projects/minic/tests/cases/err_undeclared.mc:3:11: error: undeclared variable 'x'
      print(x);
            ^
```

命令退出码是 1。注意 caret 对齐到 <code>x</code>，而不是整行；这依赖 lexer 的列号和 sema 传递的 span。诊断的可用性不是「有错误信息」就够了，位置错了会让人排查到错误的行。测试脚本对每个 <code>err&#95;&#42;.mc</code> 都检查 <code>file:line:col: error:</code> 的形状，防止某天退回成只有一句话。


### 单一类型下的检查边界

只有一个类型，不代表检查可以省。名字解析、调用元数、返回路径是三类独立错误，它们的修复方式不同：名字错误要改作用域栈，元数错误要改签名表，返回错误要改结构化判断。把它们混成一句「语义错误」，会让测试无法定位。

如果以后加入数组，检查器至少要多三件事：声明符的维度、下标表达式的类型、数组到指针的退化规则。如果加入指针，还要多别名与生命周期。本章不实现这些，但在 sema 里保留了「符号带类型字段」的位置；扩展时不需要重写 lexer 与 parser。

| 扩展 | 需要新增的检查 | 会影响的后端部分 |
|:--|:--|:--|
| 数组 | 维度、下标、退化 | 地址计算、栈布局 |
| 指针 | 解引用、取地址、别名 | 加载/存储宽度 |
| 结构体 | 成员查找、布局、对齐 | 偏移、聚合传参 |
| 浮点 | 类型转换、NaN 比较 | XMM 寄存器、调用约定 |

这张表也解释了为什么本章把「不支持」写得这么具体：每一条都对应一整块没有实现的工作，而不是一个可以临时补上的分支。

## 13.5 Step 3：TAC、CFG 与解释器 {#sec-compilers.4.13.5}

三地址码（three-address code，TAC）是本章的中间表示。它把每个表达式拆成「一个目标、一个运算符、至多两个源操作数」，控制流用标签和跳转表示。TAC 的选择不是为了接近机器码，而是为了**让每个中间值有名字**，这样 SSA 的重命名、活跃变量和代码生成的槽分配都有统一的对象。

minic 的指令集很小：

| 指令 | 形式 | 说明 |
|:--|:--|:--|
| 常量 | <code>t = const 42</code> | 目标必须是临时量或变量 |
| 复制 | <code>x = copy t</code> | 用于赋值和 phi 消解 |
| 二元 | <code>t = a + b</code> | 算术、比较 |
| 一元 | <code>t = -a</code>、<code>t = !a</code> | 取负、逻辑非 |
| 标签 | <code>L1:</code> | 基本块入口 |
| 跳转 | <code>jump L1</code> | 无条件 |
| 分支 | <code>branch t ? L1 : L2</code> | 条件为真去 L1，否则 L2 |
| 调用 | <code>t = call f(a, b)</code> | 无返回值时目标为空 |
| 返回 | <code>return t</code> | 函数出口 |
| 打印 | <code>print t</code> | 可观察副作用 |
| phi | <code>x = phi [P1: a], [P2: b]</code> | 仅 SSA，按前驱选择 |

TAC 的解释器直接执行扁平列表。它维护一个「标签 → 指令下标」的表，遇到 <code>jump</code>/<code>branch</code> 就改 <code>pc</code>，遇到 <code>call</code> 就递归调用另一个函数。所有值在写入环境时都经过 <code>to&#95;i32</code>，保证与机器码的 32 位回绕一致。

```python
def _bin(op, a, b, fn, pc):
    if op == "+":
        return to_i32(a + b)
    if op == "-":
        return to_i32(a - b)
    if op == "*":
        return to_i32(a * b)
    if op in ("/", "%"):
        if b == 0:
            raise MiniRuntimeError("division by zero", fn, pc)
        if a == INT_MIN and b == -1:
            raise MiniRuntimeError("integer division overflow", fn, pc)
        q = trunc_div(a, b)
        return q if op == "/" else a - q * b
    ...
```

这段代码验证语义契约里的前两条：算术回绕、除法向零截断。Python 的 <code>//</code> 是向下取整，<code>-17 // 5</code> 得 -4，而 C 的 <code>/</code> 得 -3；所以不能直接用 <code>//</code>，要先取绝对值再补符号。<code>-17 % 5</code> 在 C 中是 -2，在 Python 中是 3，同样需要自己算。测试 <code>division.mc</code> 覆盖了这几种符号组合。

控制流降级用标签。规则只有两条：

```text
if (c) S1 else S2:
    eval c -> t
    branch t ? Lthen : Lelse
  Lthen:
    S1
    jump Lend
  Lelse:
    S2
  Lend:

while (c) S:
  Lhead:
    eval c -> t
    branch t ? Lbody : Lend
  Lbody:
    S
    jump Lhead
  Lend:
```

这两张图是 CFG 构造的输入。CFG 的基本块划分规则是：第一条指令是入口；每个标签开始一个新块；每个 <code>jump</code>/<code>branch</code>/<code>return</code> 之后开始一个新块。块的最后一条指令是终止指令；如果最后一条不是终止指令，就有一条落到下一个块的后继边。这个「fallthrough」规则让 <code>Lelse</code> 不需要显式跳转。

看一个真实的循环。命令：

```bash

```

输出（完整函数；末尾两行是不可达的隐式返回）：

```text
fn main() {
entry:

  t0 = const 1
  i.1 = copy t0
  sum.2 = const 0
  t1 = const 0
  sum.2 = copy t1
L0:

  t3 = i.1 <= t2
  branch t3 ? L1 : L2
L1:
```

最后两条 <code>t8/return</code> 是 <code>main</code> 的隐式返回，因为函数体已经显式返回，它们位于不可达块，CFG 剪枝会去掉。TAC 允许暂时保留不可达指令；这比在降级时做可达性分析简单，而且不影响语义。真正需要干净 CFG 的是 SSA，它在构造前调用 <code>prune&#95;unreachable</code>。

## 13.6 Step 4：SSA、常量传播与死代码 {#sec-compilers.4.13.6}

SSA（static single assignment）要求每个变量名只被赋值一次。minic 的变量名本来带 <code>uid</code>，但一个变量在循环里会被多次赋值，所以仍需要重命名。重命名的结果形如 <code>i.1&#95;3</code>：基础名、版本号、定义序号。合流处用 phi 选择来自不同前驱的值。

构造算法是 Cytron 等人的经典三步：支配树、支配边界、phi 插入与重命名。第 4 章已经讲过定义，这里只强调两个工程细节。第一，**剪枝 phi**。朴素算法对每个变量的每个定义块，在其支配边界插入 phi，不管这个变量在合流点是否活跃。对结构化代码，这会产生大量无用的 phi；更糟的是，如果变量只在一个分支里定义，另一个分支的 phi 操作数就是未定义的。minic 在插入前计算活跃变量（may-liveness），只在该变量属于合流点的 <code>live&#95;in</code> 时插入。

```python
for y_name in sorted(df.get(x, ())):
    if y_name in has_phi:
        continue
    if var not in live_in.get(y_name, set()):
        continue
    y = cfg.block(y_name)
    has_phi.add(y_name)
    phi = Phi("", var, [(p, "") for p in y.preds])
    pos = 1 if y.instrs and isinstance(y.instrs[0], Label) else 0
    y.instrs.insert(pos, phi)
    work.append(y_name)
```

这段代码里的 <code>live&#95;in</code> 检查是关键。没有它，<code>print.mc</code> 中一个分支里的除法临时量会在合流点生成 phi，而另一个分支没有定义，重命名阶段报 <code>use of unrenamed variable t15</code>。这个错误不是「phi 插多了」这么简单：它说明 SSA 的不变量「每个 use 都有支配它的 def」被破坏了。

第二，**重命名按支配树 DFS**。进入一个块时，为每个 def 创建新版本并压栈；处理 use 时取栈顶；离开块时弹出本块创建的版本。phi 的操作数不在自己的块里填，而是在每个前驱块的末尾填：前驱执行完时，<code>current(base)</code> 就是该边上的值。这个「在边上填 phi」的规则直接决定了后面的 phi 消解。

```python
def rename_block(b):
    pushed = []
    for ins in b.instrs:
        if isinstance(ins, Phi):
            new = fresh(ins.base)
            ins.dst = new
            pushed.append(ins.base)
        elif isinstance(ins, Label):
            continue
        else:
            _rename_uses(ins, current)
            for d in defs_of(ins):
                new = fresh(d)
                ins.dst = new
                pushed.append(d)
    for succ_name in b.succs:
        succ = cfg.block(succ_name)
        for ins in succ.instrs:
            if isinstance(ins, Phi):
                for i, (p, s) in enumerate(ins.pairs):
                    if p == b.name:
                        ins.pairs[i] = (p, current(ins.base))
    for child in children[b.name]:
        rename_block(cfg.block(child))
    for var in pushed:
        stacks[var].pop()
```

真实的 SSA 输出如下。命令与 <code>loop.mc</code>：

```bash
python3 projects/minic/minic.py projects/minic/examples/loop.mc --emit=ssa
```

```text
fn main() {
entry:  ; preds = -
  i.1_1 = const 0
  t0_1 = const 1
  i.1_2 = copy t0_1
  sum.2_1 = const 0
  t1_1 = const 0
  sum.2_2 = copy t1_1
L0:  ; preds = entry, L1
  sum.2_3 = phi [entry: sum.2_2], [L1: sum.2_4]
  i.1_3 = phi [entry: i.1_2], [L1: i.1_4]
  t2_1 = const 100
  t3_1 = i.1_3 <= t2_1
  branch t3_1 ? L1 : L2
L1:  ; preds = L0
  t4_1 = sum.2_3 + i.1_3
  sum.2_4 = copy t4_1
  t5_1 = const 1
  t6_1 = i.1_3 + t5_1
  i.1_4 = copy t6_1
  jump L0
L2:  ; preds = L0
  print sum.2_3
  t7_1 = const 0
  return t7_1
}
```

读这段 SSA 的顺序：先看 <code>L0</code> 的两个 phi，它们的操作数分别来自 <code>entry</code> 和 <code>L1</code>，与 <code>preds</code> 一一对应；再看 <code>L1</code> 里的 <code>sum.2&#95;4</code> 与 <code>i.1&#95;4</code>，它们是回边上的新版本；最后看 <code>L2</code> 里的 <code>sum.2&#95;3</code>，它是循环退出时被 <code>print</code> 使用的版本。如果漏掉 phi，<code>L2</code> 会引用 <code>sum.2&#95;2</code>（进入循环前的 0），输出就错了。

SSA 验证器检查四件事：每个名字只定义一次；每个 use 有定义；phi 的操作数与前驱一一对应；跳转目标存在。它不是形式化证明，但能抓住大多数构造 bug。测试脚本对每个非错误用例都跑一遍 <code>verify&#95;ssa</code>，并在优化后再跑一遍。

常量传播在 SSA 上进行。每个名字对应一个格值：<code>UNDEF</code>（还不知道）、<code>CONST(c)</code>、<code>NAC</code>（非常量）。参数和调用的返回值是 <code>NAC</code>；<code>const</code> 指令给 <code>CONST</code>；二元/一元指令在两个操作数都是常量时折叠；phi 在忽略 <code>UNDEF</code> 后，如果所有已知值相同则是常量，否则是 <code>NAC</code>。

| 指令 | 传递函数 | 备注 |
|:--|:--|:--|
| <code>t = const c</code> | <code>CONST(c)</code> | 初始值 |
| <code>t = copy x</code> | <code>V(x)</code> | 直接传递 |
| <code>t = a op b</code> | 两边 CONST 时计算，否则 NAC/UNDEF | 除零保持 NAC，不折叠 |
| <code>t = -a / !a</code> | 操作数 CONST 时计算 | 回绕 |
| <code>t = phi [...]</code> | 合并：相同 CONST 则 CONST，否则 NAC | 忽略 UNDEF |
| <code>t = call f(...)</code> | <code>NAC</code> | 不假设纯函数 |

折叠之后是死代码消除（dead code elimination，DCE）。活跃指令的根是 <code>print</code>、<code>call</code>、<code>return</code>、<code>jump</code>、<code>branch</code> 和标签；每个根的操作数把定义它的指令标为活跃，递归直到不动点。删除的候选是 <code>const</code>、<code>copy</code>、二元、一元和 phi，但 <code>/</code> 与 <code>%</code> 例外：它们可能触发除零，属于可观察行为，永远保留。

优化后的 SSA 如下：

```bash
python3 projects/minic/minic.py projects/minic/examples/loop.mc --emit=ssa --opt
```

```text
; optimized: folded=2 removed=4

fn main() {
entry:  ; preds = -
  i.1_2 = const 1
  sum.2_2 = const 0
L0:  ; preds = entry, L1
  sum.2_3 = phi [entry: sum.2_2], [L1: sum.2_4]
  i.1_3 = phi [entry: i.1_2], [L1: i.1_4]
  t2_1 = const 100
  t3_1 = i.1_3 <= t2_1
  branch t3_1 ? L1 : L2
L1:  ; preds = L0
  t4_1 = sum.2_3 + i.1_3
  sum.2_4 = copy t4_1
  t5_1 = const 1
  t6_1 = i.1_3 + t5_1
  i.1_4 = copy t6_1
  jump L0
L2:  ; preds = L0
  print sum.2_3
  t7_1 = const 0
  return t7_1
}
```

<code>folded=2 removed=4</code> 的含义是：<code>i.1&#95;1/t0&#95;1</code> 与 <code>sum.2&#95;1/t1&#95;1</code> 的复制链被折叠，未被使用的临时量被删除。循环里的 <code>t4/t5/t6</code> 不能被删，因为它们参与下一轮的 phi。DCE 不会跨过 phi 删除活跃值；这是 SSA 上的 DCE 与普通基本块 DCE 的差别。

::: thm 定理 13.6.1 · 构造后的 SSA 满足单一定义 {#thm-compilers.4.13.6.1}
对任意通过 sema 的 minic 函数，<code>build&#95;ssa</code> 的输出满足：每个 SSA 名字在至多一个块中被定义一次；每个 use 都能在支配它的路径上找到定义；每个 phi 的操作数集合等于其所在块的前驱集合。
:::

这条定理的证明思路是归纳：重命名给每个 def 分配唯一版本；DFS 的栈保证 use 只能看到支配它的 def；phi 的操作数在每条入边上用前驱末尾的栈顶填充。实现里的 <code>verify&#95;ssa</code> 是这条定理的可执行近似——它检查结构，不检查支配关系本身，但支配关系由构造过程保证。

::: note phi 消解不是「把 phi 删掉」
phi 不是机器指令，不能直接删。正确做法是在每个入边上插入复制：<code>phi(dst, [P1: a], [P2: b])</code> 在 P1→B 的边上执行 <code>dst = a</code>，在 P2→B 的边上执行 <code>dst = b</code>。如果多条 phi 的复制互相覆盖，还要用临时量做两阶段复制。minic 的 <code>lower.py</code> 对每条边生成 <code>pc&#95;i = src&#95;i; dst&#95;i = pc&#95;i</code>，用新鲜临时量避免顺序问题。
:::

## 13.7 Step 5：x86-64 SysV 代码生成与栈对齐 {#sec-compilers.4.13.7}

后端不做寄存器分配，只做栈槽分配和指令选择。这不是因为寄存器分配不重要，而是因为本章要把 ABI 合同单独暴露出来：每个 SSA 名字占一个 4 字节槽，所有运算用 <code>%eax</code>/<code>%ecx</code> 做临时寄存器，结果写回槽。这样生成的代码冗长，但每条指令的语义和栈帧位置都一目了然，适合用反汇编器核对。

x86-64 SysV 的栈对齐规则只有三句话：<code>call</code> 指令把返回地址压栈，所以 callee 入口的 <code>rsp</code> 是 8 mod 16；callee 用 <code>pushq %rbp</code> 把 <code>rsp</code> 变成 0 mod 16；之后的 <code>subq</code> 必须是 16 的倍数，才能保证再次 <code>call</code> 时仍是 0 mod 16。把这三句话画出来：

<pre class="layout">
caller before call:              rsp % 16 == 0
    ...
    call f                       push return address (8 bytes)
callee entry:                    rsp % 16 == 8
    pushq %rbp                   rsp % 16 == 0
    movq %rsp, %rbp
    subq &#36;80, %rsp               rsp % 16 == 0   (80 = 5 * 16)
    ...
    call printf                  rsp % 16 == 0   (leaf call also aligned)
    ...
    leave                        movq %rbp, %rsp; popq %rbp
    ret                          rsp % 16 == 8 in caller again
</pre>

读图：任何时刻只要准备执行 <code>call</code>，<code>rsp</code> 就必须是 0 mod 16；callee 入口的 8 是 <code>call</code> 压入返回地址造成的，不是错误。prologue 里的 <code>subq</code> 如果不是 16 的倍数，后续每个 <code>call</code> 都会错位 8 字节；printf 内部使用 SSE（Streaming SIMD Extensions）对齐存储时可能崩溃，也可能「看起来正常」，这让它成为典型的偶发 bug。

::: thm 定理 13.7.1 · minic 栈帧对齐不变量 {#thm-compilers.4.13.7.1}
若函数帧大小 <code>F</code> 是 16 的倍数，且函数体内除 prologue 的 <code>pushq %rbp</code> 外没有改变 <code>rsp</code> 的指令，则该函数的所有 <code>call</code> 点都满足 <code>rsp % 16 == 0</code>。
:::

::: proof 证明
入口处 <code>rsp % 16 == 8</code>；<code>pushq %rbp</code> 减 8，得到 0；`subq $F` 且 <code>F % 16 == 0</code>，余数不变；函数体内没有其他修改 <code>rsp</code> 的指令，因此每个 <code>call</code> 前仍是 0。返回时 <code>leave</code> 恢复 <code>rsp</code> 到入口值，<code>ret</code> 弹出返回地址，调用者看到的 <code>rsp</code> 与调用前一致。
:::

实现里的帧大小计算是 <code>((4 &#42; n + 15) // 16) &#42; 16</code>，其中 <code>n</code> 是名字数。即使没有局部变量，帧大小也可能是 0；这时不生成 <code>subq</code>，<code>rsp</code> 仍然是 0，不变量成立。测试脚本用两条独立证据检查：静态正则检查汇编文本里的每个 `subq $N, %rsp`，以及 <code>llvm-objdump</code> 反汇编后的立即数。

指令选择表：

| TAC | x86-64（AT&T） | 说明 |
|:--|:--|:--|
| <code>t = const c</code> | `movl $c, -k(%rbp)` | 32 位立即数 |
| <code>t = copy x</code> | <code>movl -k(%rbp), %eax; movl %eax, -j(%rbp)</code> | 经 eax |
| <code>t = a + b</code> | <code>movl a,%eax; movl b,%ecx; addl %ecx,%eax</code> | 结果写回 |
| <code>t = a / b</code> | <code>cltd; idivl %ecx</code> | 商在 eax |
| <code>t = a % b</code> | <code>cltd; idivl %ecx; movl %edx,%eax</code> | 余数在 edx |
| <code>t = a &lt; b</code> | <code>cmpl %ecx,%eax; setl %al; movzbl %al,%eax</code> | 有符号比较 |
| <code>branch c ? L1 : L2</code> | `cmpl $0,-k(%rbp); je L2; jmp L1` | 先假后真 |
| <code>print t</code> | <code>leaq L&#95;.fmt(%rip),%rdi; movl t,%esi; call printf</code> | 变参需 <code>xorl %eax,%eax</code> |
| <code>return t</code> | <code>movl t,%eax; leave; ret</code> | 返回值在 eax |

注意表中没有 <code>movq</code> 到 <code>%eax</code> 这种写法。32 位目的必须用 <code>movl</code>；<code>movq 8(%rdi), %eax</code> 是非法指令，汇编器会直接拒绝。项目的静态检查还会主动扫描这种模式，防止 agent 在「优化」时把 <code>movl</code> 改成 <code>movq</code>。

生成的汇编（<code>loop.mc</code>，前 28 行）：

```bash
python3 projects/minic/minic.py projects/minic/examples/loop.mc --emit=asm | sed -n '1,28p'
```

```asm
.section __TEXT,__text,regular,pure_instructions
  .p2align 2
  .globl _main
  .p2align 2
_main:
  pushq %rbp
  movq %rsp, %rbp
  subq $80, %rsp
  # frame 80 bytes; rsp % 16 == 0 before calls
.Lmain_entry:
  movl $0, -4(%rbp)
  movl $1, -8(%rbp)
  movl -8(%rbp), %eax
  movl %eax, -12(%rbp)
  movl $0, -16(%rbp)
  movl $0, -20(%rbp)
  movl -20(%rbp), %eax
  movl %eax, -24(%rbp)
  movl -24(%rbp), %eax
  movl %eax, -28(%rbp)
  movl -12(%rbp), %eax
  movl %eax, -32(%rbp)
  movl -28(%rbp), %eax
  movl %eax, -36(%rbp)
  movl -32(%rbp), %eax
  movl %eax, -40(%rbp)
.Lmain_L0:
  movl $100, -44(%rbp)
```

第 8 行的 `subq $80, %rsp` 就是证据链的起点：80 是 16 的倍数。用 LLVM 的汇编器生成目标文件，再反汇编（空白按空格显示）：

```bash
export PATH=/opt/homebrew/opt/llvm@22/bin:$PATH
python3 projects/minic/minic.py projects/minic/examples/loop.mc --emit=asm > /tmp/loop.s
clang -target x86_64-apple-darwin -c /tmp/loop.s -o /tmp/loop.o
llvm-objdump -d /tmp/loop.o | sed -n '1,12p'
```

```text
/tmp/loop.o:    file format mach-o 64-bit x86-64

Disassembly of section __TEXT,__text:

0000000000000000 <_main>:
       0: 55                               pushq    %rbp
       1: 48 89 e5                         movq    %rsp, %rbp
       4: 48 83 ec 50                      subq    $0x50, %rsp
```

<code>0x50</code> 是 80，80 mod 16 = 0。反汇编器看到的是机器码里的立即数，不是汇编文本，因此这条证据独立于生成器。测试脚本对每个非错误用例都做同样的检查：汇编文本里的 <code>subq</code> 与 objdump 里的 <code>subq</code> 都必须是 16 的倍数。

参数传递按 SysV 的整型寄存器顺序：<code>%edi, %esi, %edx, %ecx, %r8d, %r9d</code>。prologue 把参数从寄存器存到栈槽，之后所有参数访问都走内存，避免在函数体内追寄存器。调用时反过来：先把实参从槽加载到对应寄存器，再 <code>xorl %eax, %eax</code>，再 <code>call</code>。清 <code>%eax</code> 是变参调用的要求；对固定参数函数也无害。

```asm
  movl -12(%rbp), %edi
  movl -16(%rbp), %esi
  movl -20(%rbp), %edx
  movl -24(%rbp), %ecx
  movl -28(%rbp), %r8d
  movl -32(%rbp), %r9d
  xorl %eax, %eax
  call _add6
  movl %eax, -36(%rbp)
```

这段调用六个参数的序列来自 <code>six&#95;args.mc</code>。测试用例 <code>six&#95;args.mc</code> 在四种模式下都输出 21，说明寄存器顺序、prologue 的存参、返回值的 <code>%eax</code> 都对齐。超过六个参数不在子集里，parser 之后的 sema 会在参数列表处报错，而不是让后端悄悄丢参数。

Darwin 与 Linux 的差异集中在符号前缀和段名：Darwin 的函数符号是 <code>&#95;main</code>、<code>&#95;printf</code>，代码段是 <code>&#95;&#95;TEXT,&#95;&#95;text</code>，字符串是 <code>&#95;&#95;TEXT,&#95;&#95;cstring</code>；Linux 没有下划线，使用 <code>.text</code> 与 <code>.rodata</code>，并在末尾加 <code>.note.GNU-stack</code>。代码生成用一个 <code>Target</code> 数据类集中管理这些差异，指令序列本身不变。

```bash
python3 projects/minic/minic.py projects/minic/examples/loop.mc --emit=asm --target=linux > /tmp/loop_linux.s
clang -target x86_64-linux-gnu -c /tmp/loop_linux.s -o /tmp/loop_linux.o
sed -n '1,10p' /tmp/loop_linux.s
```

Linux 目标在 macOS 上只能汇编，不能链接执行；测试脚本对每个用例都生成并汇编 Linux 目标，执行则留给 Linux 主机。这条边界必须写清楚：能生成汇编不等于能在本机运行，跨目标验证需要交叉链接器或目标机。

四条执行路径的对比（<code>loop.mc</code>）：

| 路径 | 命令 | 输出 | 退出码 |
|:--|:--|:--|--:|
| 直接 TAC 解释器 | <code>--run</code> | 5050 | 0 |
| 优化后 SSA 解释器 | <code>--run --opt</code> | 5050 | 0 |
| 未优化 x86-64 | <code>--run-compiled</code> | 5050 | 0 |
| 优化后 x86-64 | <code>--run-compiled --opt</code> | 5050 | 0 |

四行都相同，说明至少在这个用例上，优化、phi 消解、指令选择、调用约定没有引入偏差。单个用例不能证明所有程序正确；测试套件用 42 个用例覆盖不同的控制流和边界，仍然只是抽样。本章的结论要带条件：**在这 42 个用例和这些工具版本上**，四条路径一致。

::: note 为什么用 leave 而不是手写 movq/popq
<code>leave</code> 等价于 <code>movq %rbp, %rsp; popq %rbp</code>，语义相同但编码更短。minic 选择 <code>leave</code> 只是为了让 prologue/epilogue 对称；这不影响对齐证明。
:::

## 13.8 Step 6：测试、差分、调试与已知限制 {#sec-compilers.4.13.8}

测试脚本 <code>projects/minic/tests/run&#95;tests.py</code> 不是一个「跑一遍例子」的脚本，而是一个差分框架。它对每个非错误用例执行四种模式，对错误用例检查诊断，对所有非错误用例做两个目标的汇编检查，再跑一组单元测试。

| 检查 | 做什么 | 抓什么 bug |
|:--|:--|:--|
| 四模式对拍 | 解释器/优化解释器/未优化机器码/优化机器码 | 优化不保语义、phi 消解错误、指令选择错误 |
| 期望输出 | 用例注释里的 <code>// expect:</code> | 语义实现错误 |
| 退出码 | <code>// exit: N</code> | <code>main</code> 返回值、隐式返回 |
| 编译错误 | <code>// error: 子串</code> | 诊断缺失或信息退化 |
| 汇编文本 lint | <code>subq</code> 16 对齐、无 <code>movq</code> 到 32 位寄存器 | 栈帧、位宽 |
| objdump | 反汇编后的 <code>subq</code> 立即数 | 同上，独立于文本 |
| 单元测试 | 位置、优先级、phi、SSA 验证、优化、消解 | 各阶段的局部不变量 |

运行：

```bash
cd compilers
bash projects/minic/run_tests.sh
```

当前输出：

```text
cases: 42  modes: 4  asm targets: 28
ALL TESTS PASSED (42 cases, 4 execution modes)
```

<code>asm targets: 28</code> 表示 28 个非错误用例各生成了 darwin 与 linux 两份汇编；错误用例不生成代码。测试脚本在没有 x86-64 运行环境时会自动降级：仍然汇编和反汇编，仍然跑两种解释器，只把 <code>--run-compiled</code> 标记为跳过。降级不是「静默通过」，输出里会有一行 <code>NOTE: compiled execution skipped ...</code>，CI 应该把这行当作环境信息，而不是成功证据。

单元测试里有一条专门针对栈对齐的负向检查：

```python
bad = "f:\\n  pushq %rbp\\n  movq %rsp, %rbp\\n  subq $24, %rsp\\n  call g\\n"
assert check_asm_alignment(bad), "subq $24 not detected"
```

它把一段故意写坏的汇编喂给检查器，要求检查器报错。这是「测试测试」：如果检查器本身退化成永远返回空列表，这条断言会失败。相同的思想也用于 <code>movq ... %eax</code> 和 phi 缺失。

### agent 生成代码出错案例：多减 8 与漏 phi

一个 agent 在实现后端时交出了这样一版代码：prologue 里写 `subq $frame + 8, %rsp`，理由是「多留 8 字节给对齐更安全」；SSA 构造只处理了 <code>if</code> 的合流，<code>while</code> 的回边没有插 phi。它通过了「编译 fib」的手工测试，因为 fib 的递归不依赖循环；但一跑 <code>loop.mc</code> 就露馅。

现象有两层。第一层是输出错误：<code>loop.mc</code> 期望 5050，实际输出停留在进入循环时的 <code>sum</code> 值，不再是 5050。第二层是偶发崩溃：当 <code>print</code> 调用 printf 且栈未对齐时，printf 内部的 SSE 对齐存储可能触发保护错误；是否崩溃取决于 libc 版本和调用路径，因此它不能作为稳定的检测手段。

根因同样有两层。漏 phi 让循环头一直使用 <code>sum.2&#95;2</code>（进入循环前的 0），<code>L2</code> 的 <code>print</code> 读到的不是回边版本；多减 8 让每个 <code>call</code> 点的 <code>rsp</code> 变成 8 mod 16，违反 SysV ABI。两者都不是语法错误，编译器会安静地生成代码。

如何发现：第一步跑四模式对拍，<code>--run</code> 输出 5050，<code>--run-compiled</code> 的输出不再是 5050，差异立刻定位到 SSA/后端；第二步跑 <code>--emit=ssa</code>，看到循环头只有常量定义、没有 phi；第三步跑 SSA 验证器，报 <code>use of undefined SSA name sum.2&#95;3</code>；第四步用 <code>llvm-objdump</code> 看栈帧，发现 `subq $0x58`（88），88 mod 16 = 8。

项目里保留了一个可复现的演示脚本 <code>projects/minic/tests/agent&#95;bug&#95;demo.py</code>。它不修改编译器，只构造两个坏样本：删掉循环头的 phi，以及把第一条 <code>subq</code> 加 8。真实输出（空白按空格显示）：

```bash
python3 projects/minic/tests/agent_bug_demo.py
```

```text
== bug 1: loop header without phi ==
  verify_ssa: use of undefined SSA name i.1_3
  verify_ssa: use of undefined SSA name sum.2_3
  verify_ssa: use of undefined SSA name i.1_3
  detected: True
== bug 2: prologue subtracts 8 too much ==
  patched line: subq $88, %rsp
  asm lint: frame size 88 is not a multiple of 16
  objdump: objdump frame size 0x58 is not 16-aligned
  4: 48 83 ec 58                      subq    $0x58, %rsp
```

修复分三步。第一，phi 插入改成「支配边界 + 活跃变量剪枝」，并在 <code>rename</code> 前后跑验证器；第二，帧大小用 <code>((4&#42;n + 15) // 16) &#42; 16</code>，并在生成后断言 <code>frame % 16 == 0</code>；第三，把这两种坏样本写进测试：一个检查 <code>verify&#95;ssa</code> 非空，一个检查 <code>check&#95;asm&#95;alignment</code> 非空。修复后 <code>run&#95;tests.sh</code> 42 个用例全部通过。

这个案例的教训不是「agent 不可靠」，而是**验收线必须独立于生成者**。如果只看「编译成功」，漏 phi 和多减 8 都能通过；只有对拍、验证器和反汇编三条独立证据同时存在，才能把错误逼出来。

调试时按症状选择工具：

| 症状 | 先看 | 再看 | 常见根因 |
|:--|:--|:--|:--|
| 解释器与机器码不一致 | <code>--emit=ssa</code> | <code>--emit=asm</code> + objdump | phi 消解、比较方向、栈槽冲突 |
| 解释器自己就错 | <code>--emit=ir</code> | TAC 解释器 | 短路降级、除法符号、32 位回绕 |
| 编译错误位置不对 | <code>--emit=tokens</code> | span 构造 | 注释未更新行列、EOF span |
| 汇编器报错 | 汇编文本 | <code>clang -c</code> | 非法 <code>movq</code>、符号前缀、段名 |
| 运行时崩溃 | objdump 栈帧 | <code>subq</code> 对齐 | 帧大小不是 16 的倍数 |
| 优化后结果变错 | <code>--emit=ssa --opt</code> | 优化前后对拍 | 常量传播不保守、DCE 删了陷阱指令 |

如果程序里有 <code>print(1 / 0);</code>，解释器报告函数名和指令下标，而不是抛 Python 异常：

```text
runtime error: division by zero (function main, instruction 3)
```

这个格式让「运行期错误」也可以被测试脚本断言。机器码在同样输入下会收到 <code>SIGFPE</code>，退出码不同；这是语言契约里写明的差异，不是编译器 bug。测试不把除零放进自动对拍，否则两条路径的退出码必然不同。

### 测试的边界
测试通过不等于编译器正确。42 个用例是对语义、ABI 和诊断的抽样；它们能抓住已经写进用例的错误，不能证明所有程序都正确。每一条结论都要带条件：工具版本、目标平台、是否启用 Rosetta。

| 问题 | 现有测试能否发现 | 还需要什么 |
|:--|:--|:--|
| 漏 phi 的循环 | 能，<code>loop&#95;phi.mc</code> 对拍 | 覆盖更多循环形态 |
| 栈帧多减 8 | 能，静态 lint + objdump | 无 |
| 未定义行为 | 不能，minic 已固定语义 | 真实 C 的 UB 检查（第 9 章） |
| 大程序性能 | 不能，只测 42 个小例 | 基准与剖析 |

::: note 测试环境要写进结论
本章的实测条件是 macOS 27.0.1、Apple clang 21.0.0、LLVM 22.1.8，x86-64 代码经 Rosetta 2 执行。换到 Linux 或别的 clang 版本，汇编语法和链接命令可能不同；测试脚本的 Linux 目标只验证汇编，不验证执行。
:::

已知限制如下。它们不是「待办」，而是本章明确不覆盖的边界；每条都给出原因，避免读者误以为「没报错就是支持」。

| 不支持的特性 | 当前行为 | 原因 |
|:--|:--|:--|
| 数组、指针、字符串 | 词法/语法错误 | 需要类型、寻址、内存模型与别名分析 |
| 结构体、联合、枚举 | 保留字报错 | 布局、聚合传参、对齐超出子集 |
| 全局变量 | 语法错误 | 只做栈上局部变量，避免数据段与初始化器 |
| <code>for</code>、<code>do</code>、<code>switch</code>、<code>goto</code> | 保留字报错 | 用 <code>while</code> 足以覆盖 CFG/SSA |
| <code>break</code>、<code>continue</code> | 保留字报错 | 需要循环上下文与跳转目标管理 |
| 浮点、<code>char</code>、<code>short</code>、<code>long</code> | 保留字报错 | 单一 32 位 int 语义 |
| 预处理、<code>#include</code> | 不支持 | 单文件编译单元 |
| 逗号表达式、赋值表达式、<code>++</code>/<code>--</code> | 语法错误 | 赋值只作为语句，降低优先级与副作用复杂度 |
| 复合赋值 <code>+=</code> | 语法错误 | 同上 |
| 函数指针、可变参数、超过 6 个参数 | 语法/语义错误 | 调用约定只覆盖 6 个整型寄存器参数 |
| 递归深度、无限循环 | 解释器步数上限 2000 万 | 防止测试挂死 |

最后一行需要澄清：步数上限是解释器的保护，不是语言语义。机器码没有这个上限，死循环会一直跑。测试用例都保证终止；如果读者写了一个不终止的程序，<code>--run</code> 会报 <code>step limit exceeded</code>，<code>--run-compiled</code> 需要外部超时。

本章实验的完整输出可以用一条命令重现：

```bash
cd compilers
bash experiments/ch13/run.sh
```

它依次打印 SSA、优化后 SSA、四种执行结果、汇编栈帧和 objdump 证据。脚本在第 3 步依赖 x86-64 执行环境；在 Apple Silicon 上需要 Rosetta 2。没有 Rosetta 时，前两步和汇编检查仍然可跑，输出里会明确说明哪一步失败。

测试的 oracle 是手写的期望输出，不是另一个编译器生成的。手写 oracle 的优点是独立，缺点是可能把错误当成期望；缓解办法是每个期望值都能用手算或 Python 一行验证，例如 1 到 100 的和是 5050，<code>fib(10)</code> 是 55。不要把被测编译器自己生成的输出直接回填成期望，那是循环论证。

## 13.10 本章陷阱（8–15 条） {#sec-compilers.4.13.10}

::: errata 本章陷阱
1. **把 <code>--</code> 当注释**：C 没有 <code>--</code> 注释，<code>a--b</code> 是两个减号。minic 的 lexer 只认 <code>//</code> 与 <code>/&#42; &#42;/</code>；如果误把 <code>--</code> 吞掉，<code>1 - -2</code> 会少一个操作数。验证：<code>--emit=tokens</code> 应看到两个 <code>-</code>。
2. **注释未更新行列**：跳过 <code>//</code> 或块注释时忘记处理换行，后续所有诊断偏移。验证：在注释后放一个未声明变量，看 caret 是否仍指向正确列。
3. **Pratt 右操作数用了 <code>bp</code> 而不是 <code>bp+1</code>**：所有二元运算变成右结合，<code>10-3-2</code> 得 9。验证：<code>arith&#95;assoc.mc</code> 的期望值是 5。
4. **块作用域退出未弹栈**：内层 <code>x</code> 泄漏到外层，后续同名声明报重复或解析到已销毁的符号。验证：<code>shadowing.mc</code> 必须先输出 2 再输出 1。
5. **<code>if</code>/<code>while</code> 子语句没有隐式作用域**：<code>if (1) int x = 2;</code> 的 <code>x</code> 泄漏到外面。验证：<code>err&#95;scope.mc</code> 必须在 <code>print(x)</code> 处报未声明。
6. **声明初值先读后写**：<code>int x = x + 1;</code> 在 minic 中读到的是声明处写入的 0；如果 TAC 先读后写，会读到旧槽值。验证：<code>--emit=ir</code> 中声明应先 <code>const 0</code> 再复制初值。
7. **TAC 标签落在错误的基本块**：把标签放在 <code>jump</code> 之后而不是目标块开头，CFG 会多出一条 fallthrough 边或丢掉目标。验证：<code>--emit=cfg</code> 的 preds/succs 是否与源码控制流一致。
8. **只给 <code>if</code> 插 phi、漏掉 <code>while</code> 回边**：循环头使用进入循环时的值，第二次迭代起就不更新。验证：<code>loop&#95;phi.mc</code> 输出 55 和 11；漏 phi 时通常只输出第一次迭代的结果。
9. **不剪枝 phi**：对只在单边定义的临时量插 phi，另一边的操作数未定义，重命名报 <code>use of unrenamed variable</code>。验证：SSA 验证器的 <code>use of undefined SSA name</code>；修复是加 <code>live&#95;in</code> 检查。
10. **phi 消解顺序错误**：在分支的两边都写全部复制，或按 phi 列表顺序直接覆盖源槽，循环交换时会丢值。验证：<code>lower&#95;ssa</code> 的输出应没有 <code>phi</code>，且每条边先写临时量再写目标；<code>--run --opt</code> 与 <code>--run</code> 对拍。
11. **prologue 多减 8**：`subq $frame+8` 让 <code>rsp</code> 在 <code>call</code> 前变成 8 mod 16。验证：<code>check&#95;asm&#95;alignment</code> 与 objdump 都应报帧大小不是 16 的倍数；负向演示见 <code>agent&#95;bug&#95;demo.py</code>。
12. **用 <code>movq</code> 写 <code>%eax</code>**：32 位目的必须 <code>movl</code>；<code>movq 8(%rdi), %eax</code> 是非法指令。验证：<code>clang -c</code> 直接拒绝，静态 lint 也会扫描。
13. **DCE 删掉未使用的除法**：<code>a / b</code> 的结果没人用，但 <code>b</code> 可能为 0，删除会改变「是否发生运行期错误」。验证：优化前后对拍除零路径；实现上把 <code>/</code> 与 <code>%</code> 当根。
14. **Darwin 忘记下划线**：生成 <code>call printf</code> 而不是 <code>call &#95;printf</code>，链接器报未定义符号。验证：<code>--target=darwin</code> 的汇编里函数符号带 <code>&#95;</code>，<code>--target=linux</code> 不带。
15. **用 <code>print</code> 当函数名**：<code>print</code> 是语句关键字，<code>int print(int x)</code> 在词法阶段就被当作关键字，parser 报错。验证：错误信息应指向函数名位置，而不是「expected '('」。
:::

::: method 即时自测 · 13
**Q1** 你的 <code>while</code> 循环头为什么需要 phi？如果只在循环体末尾给变量赋值，不插 phi 会发生什么？请用 <code>loop&#95;phi.mc</code> 的 SSA 输出指出两个版本号。

**Q2** 一个函数的帧大小是 4 个槽，计算出的 <code>subq</code> 立即数应该是多少？如果写成 24，<code>rsp</code> 在 <code>call</code> 前是多少 mod 16？哪个工具能发现它？

**Q3** 为什么常量传播不能把 <code>a / b</code> 在 <code>b</code> 非常量时折叠成 0 或删除？如果 <code>b</code> 是常量 0，应该怎样处理？

**Q4** 四条执行路径中，哪一条不经过 SSA？为什么保留这条路径，而不是让所有模式都走 SSA？

::: sol 答案
**A1** 循环头有两个前驱：进入循环的 <code>entry</code> 和回边 <code>L1</code>。变量在两条路径上的版本不同，必须用 phi 选择。<code>loop.mc</code> 中 <code>sum.2&#95;3 = phi [entry: sum.2&#95;2], [L1: sum.2&#95;4]</code>，<code>i.1&#95;3 = phi [entry: i.1&#95;2], [L1: i.1&#95;4]</code>。不插 phi 时，循环条件与循环体一直读进入循环时的版本，<code>sum</code> 不会累加，输出停在第一次迭代。

**A2** 4 个槽是 16 字节，帧大小 16，立即数是 16。写成 24 时，24 mod 16 = 8，<code>call</code> 前 <code>rsp % 16 == 8</code>，callee 入口变成 0，违反 SysV。静态 lint 检查 <code>subq</code> 立即数，<code>llvm-objdump</code> 检查机器码里的立即数；两者都应报 24 不是 16 的倍数。

**A3** 因为除法可能触发除零，属于可观察行为；<code>b</code> 非常量时不能证明安全，所以不能折叠或删除。若 <code>b</code> 是常量 0，常量传播保持 <code>NAC</code>，DCE 也把除法当根保留，让运行期错误如期发生；不能把它折成 0，否则程序从「报错」变成「正常返回」。

**A4** <code>--run</code>（不带 <code>--opt</code>）直接执行扁平 TAC，不经过 SSA。保留它是为了给优化后的 SSA 路径提供一个独立的语义基准：两条路径共享源码和 TAC 语义，但在 SSA 构造、优化和 phi 消解上分叉，任何一边出错都会在对拍中暴露。
