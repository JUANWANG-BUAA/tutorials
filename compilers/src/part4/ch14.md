第 13 章把一个迷你编译器从词法一路做到 x86-64 汇编，验收靠的是「解释器与编译执行对拍」。那一章的被测对象是你自己写的编译器，错误会以错误答案或崩溃的形式出现。这一章的被测对象换成 agent 生成的代码：它通常语法正确、命名合理、注释自信，示例输入也能跑过。失败往往藏在副作用、资源消耗、测试环境分支和静态解析盲区里。

一个具体的反例。`fixtures/bad/exit_after_print.py` 只有两行：

```python
print("ok")
raise SystemExit(3)
```

如果验证器只比较标准输出，它看到 `ok\n` 就判定通过。退出码 3 被丢掉了。再如 `fixtures/quarantine/side_effect.py` 打印 `ok` 的同时向 `/tmp/guard-ch14-demo.txt` 写入 8 个字节。RLIMIT 不阻止这次写入，临时目录也不是文件系统命名空间。只读 stdout 的验证器会把这两类代码都放过去。

本章交付 `projects/validator/`：一个 Python 3.11+ 标准库实现的三层门禁加证据化裁决器。三层是静态规则、编译门禁、受限行为门禁；第四层「沙箱」只做资源遏制，不宣称隔离。裁决只有三种：accept、reject、quarantine。每条裁决带命令、退出码、哈希与耗时，quarantine 强制进入人工复核。

先在仓库根跑一次实验入口，确认三类裁决都能复现：

```bash
cd compilers
bash experiments/ch14/run.sh
```

真实输出（macOS 27 / Apple clang 21 / Python 3.13.13）：

```text
accept       verdict=accept     exit=0
reject       verdict=reject     exit=1
quarantine   verdict=quarantine exit=2
```

三条路径分别对应：干净代码加匹配测试；C 编译门禁被 `-Werror` 拦下；死循环触发超时。后面的小节会拆开每一条，给出可复制的命令与真实 JSON。

## 14.1 威胁模型：agent 代码的失败模式 {#sec-compilers.4.14.1}

验证器不是「判断代码对不对」的机器。它只能观察有限几种信号：源码结构、编译器诊断、进程的输出与退出状态、资源用量。把这些信号拼成一个可复核的裁决，是工程目标；证明程序语义正确，不在目标内。

::: def 定义 14.1.1 · 代码验证器 {#def-compilers.4.14.1.1}
代码验证器（code validator）是一个把「候选代码 + 语言 + 策略 + 测试夹具」映射到「裁决 + 发现 + 证据」的程序。裁决取值 accept、reject、quarantine；发现（finding）至少含规则 id、严重度、消息、文件与行号；证据（evidence）至少含实际执行的命令、退出码、源码哈希与耗时。验证器不修改候选代码，也不把「测试通过」等同于「语义正确」。
:::

表 14.1 列出本章覆盖的七类失败模式。最后一列是「哪一层看不见」，它比「哪一层能看见」更重要：误判通常来自把某一层的通过当成另一层的证明。

| 失败模式 | 可观察信号 | 能看见的层 | 看不见的层 |
|:--|:--|:--|:--|
| 危险 API（`os.system`、`subprocess`、`ctypes`） | AST Call / C token / Rust 标识符 | 静态 | 行为（若静态高危直接短路，根本不执行） |
| 无限循环 | 超时、`SIGXCPU`、耗时 | 行为 | 静态只能给低危启发式，不能证明终止 |
| 越界写 | 崩溃信号、ASan 报告、输出异常 | 行为（有限） | 静态正则；未插桩的运行可能静默破坏内存 |
| 网络访问 | socket/connect 调用、网络头文件 | 静态 | 行为（默认不阻断网络，连接可能成功） |
| 资源耗尽 | `RLIMIT` 命中、超时、`EFBIG` | 行为 | 静态无法判断实际分配量 |
| 策略绕过（别名、`getattr`、宏） | 解析后的规范名、宏定义 | 静态（部分） | 编译（语法通常合法）；行为（可能没有测试覆盖） |
| 测试造假（环境嗅探、硬编码输出） | CI 变量读取、输出哈希、退出码 | 静态 + 行为 | 语义等价性；它可能只在测试输入上正确 |

agent 代码还有两个分布特征。第一，注释与命名是「说给人听」的，可能包含 `ignore previous instructions` 之类的文本；验证器必须把注释当数据，不能当指令。第二，测试夹具也可能是同一个 agent 写的，oracle（判据）本身可能错。验证器能固定夹具哈希、记录期望输出，但不能证明夹具覆盖了真实需求。

<pre class="layout">
agent 生成的补丁 / 文件
        │
        ▼

读图：四层是并联观测，不是串联证明。静态高危可以在行为门禁之前短路（`execute_below`），避免执行已知危险代码；编译失败会阻止行为门禁；行为门禁失败会追加高危发现。任何一层的通过都不能替代另一层，最后的裁决只由「所有活跃发现的最大严重度」决定。

::: intuition 直觉 · 四个窗口，不是四把锁 {#intuition-compilers.4.14.1.1}
把验证器想成一间有四扇窗的房间：静态窗看见源码结构，编译窗看见类型与警告，行为窗看见一次运行，资源窗看见用量。四扇窗都看不见「这段代码在所有输入上做什么」。窗越多，漏掉的东西越少，但房间没有门——它不是虚拟机，也不是证明助手。
:::

威胁模型明确排除三类对手：被篡改的编译器/工具链、被篡改的验证器自身、内核或硬件的 0day。它也排除「候选代码能读验证器内存」这类同机攻击。若威胁模型包含这些，资源限制与静态规则都不够，需要虚拟机、独立机器或形式化验证；第 12 章讨论过这条边界。

### 信任边界：验证器在借用谁的权限

验证器以当前用户身份运行，这一点决定了威胁模型的形状。候选代码被 `subprocess` 启动后，继承的是验证器进程的 uid、gid、补充组、工作目录与大部分文件系统权限。验证器不是「站在系统外面的裁判」，而是「把自己的权限借给候选代码的中介」。安全工程把这叫 confused deputy：调用者没有权限，但被调用者有权，于是攻击者借被调用者之手行事。

| 资产 | 入口 | 验证器的假设 | 失守后果 |
|:--|:--|:--|:--|
| 工作区文件 | `open`、`os.remove`、编译产物 | 临时目录可写，其余路径只读 | 覆盖源码、删除构建产物 |
| 用户主目录 | 绝对路径、`..`、符号链接 | 运行环境已清理，路径不可逃 | 读取 SSH 密钥、浏览器配置、令牌 |
| 网络 | `socket`、`urllib`、子进程 `curl` | 主机可联网，未做网络隔离 | 数据外传、拉取二次载荷 |
| 进程表 | `fork`、`kill`、`subprocess` | 同 uid 进程可见 | 干扰其他任务、留后台进程 |
| 测试 oracle | 夹具 JSON、期望输出 | 夹具由可信方编写并哈希 | 测试与实现共享错误假设 |
| 人类注意力 | 注释、提交信息、findings 文本 | 人类会独立判断 | 提示注入改变复核结论 |

这张表说明「验证器通过」从来不等于「候选代码安全」：验证器只观察了它被设计来观察的通道。把候选代码放到虚拟机或独立账户里运行，改变的是上表前四行；把夹具交给独立团队写，改变的是第五行；规定「注释不得进入裁决」并做评审培训，改变的是第六行。三者不能互相替代。

### 成本：误报与漏报不是对称的

静态规则每增加一条，误报与漏报都会变化。对 agent 代码来说，漏报的代价通常更高：一段能写文件的代码被 accept 后，可能在其他流水线里反复执行；误报的代价是人工复核时间与开发者挫败感。本章用三档严重度把这两类成本分开：high 直接 reject，medium 进 quarantine，low 只记录。阈值可配，但默认值必须能解释。

严重度不是「危险程度」的绝对度量，而是「证据强度 × 潜在影响」的工程约定。`PY-EVAL` 是 high，因为 `eval` 的输入一旦可控就是任意代码执行；`PY-INFINITE-LOOP` 是 low，因为死循环可能只是服务主循环，行为门禁的超时会兜底。把 low 规则一律升成 high，会让验证器变成噪声源；把 high 规则降成 low，会让 `allow_rules` 变成默认放行。校准严重度需要真实样本，而不是拍脑袋。

### 为什么不让 LLM 直接裁决

一个自然的想法是：把代码和策略交给另一个 LLM，让它输出 accept/reject。这个做法在本章被明确排除在裁决回路之外。理由不是「LLM 不够聪明」，而是三条工程性质不满足：不可复现（同一输入不同采样可能不同结论）、可被提示注入（代码注释、字符串、文件名都是攻击面）、证据不可核（「我认为它安全」不是可审计的命令与退出码）。

LLM 可以在裁决之后做事：把 findings 翻译成人话、给复核者生成摘要、从失败日志里提取线索。它不能替代 `m = max(severity)` 这一步。把 LLM 放在裁决之前，等于把一个非确定性、可注入的组件放进信任边界；把它放在裁决之后，它只是一个阅读辅助。

::: note 威胁模型随部署变化 {#note-compilers.4.14.1.1}
实验室里的验证器可以假设「运行者接受风险」；CI 里的验证器必须假设「候选代码来自不可信贡献者」；生产环境里的验证器必须假设「候选代码可能主动对抗」。同一份规则表在三种部署下的阈值、隔离强度与人工复核比例都不同。本章给出的是 CI 之前的「合并前筛查」模型：候选代码可能不怀好意，但验证器运行在有网络、有用户文件、无内核隔离的普通主机上。这个模型决定了 14.6 的边界必须写得比功能更醒目。
:::

### 验证器不替代代码审查

代码审查看的是意图、接口与维护性；验证器看的是可观察信号。两者不能互相替代。一个 accept 的补丁可能把业务逻辑写错，只是恰好通过了夹具；一个 reject 的补丁可能只是用了 `system` 调一个可信工具，人工复核后应当放行。把验证器当审查的替代品，会让团队停止阅读 diff；把审查当验证器的替代品，会漏掉别名、资源与超时这类机器更容易发现的问题。

本章的定位是「合并前的机械筛查」：它负责把明显危险的、明显跑不起来的、明显不终止的代码挡在人工复核之前，把不确定的放进 quarantine。它不负责判断「这个功能是否应该存在」。这条边界写进 README 的第一屏，比藏在第 14 节更有用。

## 14.2 裁决对象：补丁、语言、策略与证据 {#sec-compilers.4.14.2}

「验证一个补丁」在工程上常被说成「跑一下 CI」。但补丁是 diff，验证器吃的是文件。两者之间有一个必须显式处理的缝：被测的到底是哪个快照。

::: def 定义 14.2.1 · 裁决单元 {#def-compilers.4.14.2.1}
裁决单元（adjudication unit）是一个五元组 `(source, language, policy, tests, gates)`：`source` 是候选文件的字节快照，`language` 决定静态与编译后端，`policy` 给出阈值、允许规则与资源参数，`tests` 是行为门禁的输入/期望输出夹具，`gates` 是本次实际请求的层。裁决单元的标识至少包含源码哈希与策略哈希；测试夹具参与行为门禁时必须记录夹具哈希。
:::

本章的 validate 以文件或目录为单位。一个 git 补丁应先被应用到一个干净工作树，再把「变更后的文件集合」交给验证器；补丁的提交号、基线提交与文件列表由外部系统固定。验证器不解析 unified diff，也不判断「这行改动是否属于本补丁」。这条边界必须写进接入文档，否则「验证通过」会指向一个没有固定快照的移动目标。

策略是一个 JSON 对象。默认策略如下（`projects/validator/policy.json`，字段顺序略有调整）：

```json
{
  "name": "default",
  "reject_at": "high",
  "quarantine_at": "medium",
  "execute_below": "high",
  "require_tests": true,
  "allow_rules": [],
  "severity_overrides": {},
  "max_file_bytes": 262144,
  "sandbox": {
    "timeout_s": 5.0,
    "cpu_s": 2,
    "address_space_mb": 512,
    "file_size_mb": 1,
    "nofile": 64,
    "max_output_bytes": 65536,
    "max_cases": 20
  }
}
```

| 字段 | 作用 | 误用的后果 |
|:--|:--|:--|
| `reject_at` | 严重度达到此值即 reject | 设成 `low` 会把所有提示都变成拒绝 |
| `quarantine_at` | 达到此值即交人工 | 设得比 `reject_at` 高会让 quarantine 不可达 |
| `execute_below` | 静态严重度低于此值才允许执行 | 设成 `medium` 会让中危代码不跑行为门禁 |
| `require_tests` | 请求 `--run` 却无夹具时是否 quarantine | 设成 `false` 会把「没测过」当成通过 |
| `allow_rules` | 抑制指定规则并留痕 | 大范围抑制会隐藏真实风险；抑制项仍进 suppressed |
| `severity_overrides` | 按规则覆盖严重度 | 覆盖后阈值判断随之改变，必须写进策略评审 |
| `sandbox.*` | 超时与 RLIMIT 参数 | 数值不是安全边界；见 14.6 |

::: thm 定理 14.2.1 · 硬门禁单调性 {#thm-compilers.4.14.2.1}
设 `S` 为一次裁决中所有未被策略抑制的发现的严重度集合，`r = reject_at`。若 `max(S) ≥ r`，则无论编译或行为门禁是否通过，裁决都是 reject。
:::

::: proof 证明
裁决函数先计算 `m = max(S)`，再按 `m ≥ reject_at → reject`、否则 `m ≥ quarantine_at → quarantine`、否则 accept 的顺序返回。编译失败与行为失败都会追加高严重度发现，因此只会抬高 `m`，不会降低。任何「其他门禁通过」的分支都在阈值判断之后，无法覆盖 reject。证毕。
:::

这条性质是「不做加权平均」的直接结果。加权平均会让一个高危发现被十个通过项稀释；硬门禁不会。它的代价是误报更贵：一条错误的高危规则会拒绝整批代码。因此规则严重度必须经过校准，且策略要允许对具体规则留痕抑制。

策略可以改变同一份代码的裁决。`fixtures/good/injection_comment.py` 只有一条提示注入注释和一条 `print`；默认策略下它是 accept，因为该规则是 low。换成 `fixtures/policies/strict.json`（`quarantine_at: low`、`reject_at: medium`）后：

```bash
cd projects/validator
python3 guard.py fixtures/good/injection_comment.py \
  --policy fixtures/policies/strict.json --static-only
```

```text
QUARANTINE fixtures/good/injection_comment.py (python)
  static    warn
  compile   skip (static-only)
  behavior  skip (not requested)
  [low   ] PY-PROMPT-INJECTION    fixtures/good/injection_comment.py:1 注释包含提示注入文本；验证器不读取注释作为指令
  human_review: required (quarantine)
```

代码没有变，策略变了，裁决就变了。这就是为什么证据里必须记录策略哈希：只贴一个 verdict 字段，复现者不知道用的是哪套阈值。

证据链的字段与用途：

| 字段 | 例子 | 它能支持什么 | 它不能支持什么 |
|:--|:--|:--|:--|
| `code_sha256` | `9b76b4…c75d1` | 确认被裁决的字节快照 | 证明快照就是待合并的补丁 |
| `policy_sha256` | `14e6f3…850c64` | 复现阈值与允许规则 | 证明策略本身经过评审 |
| `tests_sha256` | `dd768b…0371` | 确认 oracle 未被替换 | 证明 oracle 覆盖了需求 |
| `commands[]` | `compile` / `run` | 复现实际执行的命令与退出码 | 证明命令输出没有被截断 |
| `elapsed_ms` | `65` | 发现异常慢的路径 | 作为性能结论（受机器负载影响） |
| `started_at` | `2026-10-20T07:50:16+00:00` | 关联日志与批次 | 证明执行顺序或因果关系 |

哈希在验证开始时计算，之后不再重算。若候选文件在静态分析与行为执行之间被替换，裁决对应的是两个不同的字节串。单机教学实现不防这种 TOCTOU（time-of-check to time-of-use）；生产接入应把文件复制到只读临时目录，或在运行前后各算一次哈希并比较。

### 只请求一层时，accept 意味着什么

`--static-only`、`--compile`、`--run` 三种请求产生的 accept 不是同一个结论。把「请求了哪些层」写进 `gates`，是为了防止读者把「静态通过」误读成「行为通过」。

| 请求 | accept 能保证 | accept 不能保证 |
|:--|:--|:--|
| `--static-only` | 没有达到 `quarantine_at` 的发现 | 能编译、能运行、行为正确 |
| 默认（静态 + 编译） | 源码结构与编译诊断都通过 | 运行时输出、退出码、资源行为 |
| `--compile --run --tests` | 上述两项 + 夹具下输出/退出码匹配 | 夹具之外的行为、语义正确、无副作用 |

因此裁决 JSON 里的 `gates` 不是装饰字段。复核者看到 accept 时，第一件事应是确认 `gates` 包含 behavior；只包含 static 的 accept 只能作为「进入下一轮」的凭据，不能作为合并凭据。

### 目录模式与裁决格

目录模式对每个匹配文件独立裁决，再取最坏值：任一 reject 则整体 reject；否则任一 quarantine 则整体 quarantine；否则 accept。这个聚合是「格的 join」，不是平均分。`fixtures/bad` 目录的实测摘要：

```text
SUMMARY {'accept': 3, 'reject': 5, 'quarantine': 0} -> reject
```

三个 accept 分别是「静态干净但行为未测」的 `exit_after_print.py`、`missing_import.py`、`wrong.py`。它们没有触发静态规则，所以目录模式在 `--static-only` 下给 accept；一旦加 `--run` 与夹具，它们会分别变成 reject 或 quarantine。这个例子说明目录聚合只反映「本次请求的门禁」，不反映「文件本身的历史」。

### 把补丁钉在快照上

接入 git 时，推荐的处理顺序是：

1. 在干净工作树上应用补丁，记录基线提交与补丁提交号。
2. 生成变更文件列表，只把这些文件交给验证器；不要扫描整个仓库。
3. 对每个文件算 `code_sha256`，由外部系统写进补丁记录；不要直接和 git blob 哈希比较，两者算法与对象头不同。
4. 把验证器版本、策略哈希、夹具哈希、命令与退出码写入 CI artifact。
5. 合并前要求 verdict 为 accept 且 `human_review.required` 为 false；quarantine 必须有复核记录。

第 3 步是补丁与裁决单元之间的桥。没有它，验证器算的哈希只能证明「我读了某个文件」，不能证明「我读的是这个补丁的文件」。

## 14.3 静态规则：AST、token 与误报控制 {#sec-compilers.4.14.3}

静态层要回答的问题是：在不执行代码的前提下，哪些结构值得拦截或降级？Python 用 `ast` 拿到真实的调用树；C 与 Rust 没有标准库 AST，本章用「去注释/去字符串后的 token 扫描 + 编译门禁」兜底。两种做法的证据强度不同，误报模式也不同。

Python 的关键不是匹配 `os.system` 这个字符串，而是把别名还原成规范名。`from os import system as run` 之后，调用点只写 `run(...)`；只匹配文本的规则会漏掉。`guard.py` 先收集 import 绑定，再对 `Attribute` 链做递归解析：

```python
def _dotted(node, aliases, depth=0):
    if node is None or depth > 12:
        return None
    if isinstance(node, ast.Name):
        return aliases.get(node.id, node.id)
    if isinstance(node, ast.Attribute):
        base = _dotted(node.value, aliases, depth + 1)
        return f"{base}.{node.attr}" if base else node.attr
    return None
```

`_python_aliases()` 把 `import os as o` 记成 `o → os`，把 `from os import system as run` 记成 `run → os.system`，星号导入单独记一条低危发现。对 `getattr` 则分两种情况：属性名是字符串常量时继续解析，非常量时只能把不确定性降级为 quarantine。

```text
if isinstance(func, ast.Name) and func.id == "getattr" and len(node.args) >= 2:
    attr = _const_str(node.args[1])
    base = _dotted(node.args[0], aliases)
    if attr is not None and base:
        match_call(f"{base}.{attr}", node.lineno)
    elif attr is None:
        add("PY-DYN-ATTR",
            "getattr() 的属性名不是字符串常量，静态规则无法确定目标", node.lineno)
    continue
```

这段代码验证两件事：`getattr(o, "sys" + "tem")` 的字符串拼接能被 `_const_str` 折叠，规范名仍是 `os.system`；`getattr(o, name)` 里 `name` 来自运行时，静态层拒绝猜。前者是高危 reject，后者是中危 quarantine。两者都不执行代码。

规则与观察能力（节选）：

| 规则 | 严重度 | 观察对象 | 典型漏报 |
|:--|:--|:--|:--|
| `PY-EVAL` | high | `eval`/`exec`/`compile` 调用 | 通过 `__builtins__` 间接取到 |
| `PY-OS-SYSTEM` | high | 规范名 `os.system`/`os.popen` | 把函数对象存进容器后调用 |
| `PY-SUBPROCESS` | high | `subprocess.*` | 用 `os.posix_spawn`（另有规则） |
| `PY-NET` | high | `socket`/`urllib`/`http.client` | 通过第三方扩展或 `ctypes` |
| `PY-FS-WRITE` | medium | `open` 写模式、`write_text`、`os.mkdir` | 通过已有 fd、第三方库或 `os.write` 写 |
| `PY-DYN-ATTR` | medium | `getattr` 非常量属性名 | 通过 `vars()`/`__dict__` 取属性 |
| `PY-TEST-SNIFF` | medium | `os.environ` 的 CI 键 | 通过文件系统或 argv 判断测试环境 |
| `PY-INFINITE-LOOP` | low | `while True` 且当前作用域无 `break` | `while flag`、递归、事件循环 |

别名样例的真实输出：

```bash
python3 guard.py fixtures/bad/agent_alias.py --static-only
```

```text
REJECT     fixtures/bad/agent_alias.py (python)
  static    fail
  compile   skip (static-only)
  behavior  skip (not requested)
  [high  ] PY-OS-SYSTEM           fixtures/bad/agent_alias.py:3 os.system()：os.system() 启动 shell
```

拼接样例同样被还原：

```bash
python3 guard.py fixtures/bad/getattr_concat.py --static-only
```

```text
REJECT     fixtures/bad/getattr_concat.py (python)
  static    fail
  compile   skip (static-only)
  behavior  skip (not requested)
  [high  ] PY-OS-SYSTEM           fixtures/bad/getattr_concat.py:3 os.system()：os.system() 启动 shell
```

误报控制靠两条：只看调用节点，不扫字符串；C 先把注释与字符串字面量抹成空格，再扫标识符。`fixtures/good/strings_only.py` 里有一整句 `"os.system('rm -rf /')"`，静态结论是 accept；`fixtures/c/string_ok.c` 打印 `"system( and popen( are just text"`，同样是 accept：

```bash
python3 guard.py fixtures/c/string_ok.c --static-only
```

```text
ACCEPT     fixtures/c/string_ok.c (c)
  static    pass
  compile   skip (static-only)
  behavior  skip (not requested)
```

C 侧还有几条规则覆盖越界写与网络：`C-UNSAFE-STR`（`strcpy`/`strcat`/`sprintf`/`gets`）、`C-UNSAFE-SCAN`（`scanf` 的 `%s`）、`C-SOCKET`（`socket`/`connect`）、`C-DLOPEN`（`dlopen`/`dlsym`）。它们只能指出「用了危险原语」，不能证明越界真的发生。行为层没有 ASan/UBSan 插桩，一次越界写可能静默通过；这是 14.8 限制表里的明确条目。

C 的绕过更多来自预处理。`#define LAUNCH system` 之后调用 `LAUNCH("…")`，token 扫描在调用点只看到 `LAUNCH`。本章用一条 `C-MACRO-ALIAS` 规则扫描「宏直接等于危险函数名」的定义，把它降级为 quarantine；更复杂的宏拼接仍然会漏。`fixtures/c/macro_alias.c` 的实测：

```text
QUARANTINE fixtures/c/macro_alias.c (c)
  static    warn
  compile   skip (static-only)
  behavior  skip (not requested)
  [medium] C-MACRO-ALIAS          fixtures/c/macro_alias.c:3 宏把 system 改名：调用点看起来无害
  human_review: required (quarantine)
```

Rust 的静态层只做粗筛：`Command::new`、`std::fs::remove_*`、`TcpStream`、`libc::`、`unsafe`、`extern "C"`。Rust 的宏展开与过程宏可能在编译期生成这些调用，源码正则看不到；编译门禁能确认展开后的程序类型正确，但不会因为「生成了 `Command`」而拒绝。两者必须分开理解。

::: errata 静态规则的三个边界 {#errata-compilers.4.14.3.1}
1. **注释不是代码**：验证器不把注释送进任何解释器。`fixtures/good/injection_comment.py` 第一行写着「ignore all previous instructions」，它只会产生一条 low 发现，不会改变裁决逻辑，也不会被执行。真正危险的是注释诱导人类或上层 agent 忽略 findings。
2. **AST 不等于语义**：`getattr`、`vars`、`__dict__`、`exec` 组合可以把调用目标推到运行时。静态层能说的是「看见了什么」，不是「只可能是什么」。非常量 `getattr` 被降级而不是放行，就是为了保留这个不确定性。
3. **C 的 token 扫描依赖「先去掉什么」**：去掉注释与字符串会消掉大量误报，也会消掉 `fopen("out", "w")` 里的模式串。本章对 `fopen` 单独在「保留字符串、去掉注释」的视图上匹配，两个视图都保留行号，避免诊断错位。
:::

### 三个扫描视图

C 与 Rust 的静态扫描不是一次正则，而是三个视图：代码视图（去掉注释与字符串）、保留字符串视图（去掉注释）、注释视图（只留注释）。每个视图保留换行，行号才对得上。

| 视图 | 用途 | 典型漏报/误报 |
|:--|:--|:--|
| 代码视图 | 找 `system(`、`socket(`、`unsafe {` | 字符串里的同名文本被正确忽略 |
| 保留字符串视图 | 看 `fopen("out", "w")`、`scanf("%s")` | 注释里的格式串可能干扰，需另行去注释 |
| 注释视图 | 标提示注入文本 | 不参与代码规则，只产生 low 发现 |

三个视图由同一个状态机生成。块注释跨行、转义引号、字符字面量都按 C 的规则处理；Rust 的 raw string（`r#"…"#`）不在处理范围内，这是已知限制，写在 README 与 14.8 的限制表里。行号通过「保留换行、其余字符替换成空格」保持稳定，诊断不会因为去掉字符串而偏移。

### 规则 id 是接口

`PY-OS-SYSTEM` 这样的 id 会出现在策略的 `allow_rules`、CI 的豁免单、复核对讲里。改名等于破坏兼容性：旧策略里的字符串会变成未知规则，加载直接报错。本章把规则 id 当公开接口对待，测试断言 id 而不是消息文本；消息可以改，id 不能随手改。新增规则要同时更新 `RULES`、策略校验与至少一个夹具。

星号导入是另一个边界。`from os import *` 之后，`system` 这个名字可能来自 `os`，也可能来自别的模块；静态层给一条 `PY-STAR-IMPORT` low 发现，并把后续调用当作未知。它不拒绝，因为星号导入本身合法；它也不放行到「没有不确定性」，因为名字来源确实不可判定。

### 行号、片段与诊断定位

静态发现里的 `line` 与 `snippet` 不是装饰。复核者需要在一百行文件里定位到具体调用，行号错了就会看错位置。Python 的 `ast` 节点自带 `lineno`；C 与 Rust 的扫描通过「保留换行、替换字符」保持行号。`snippet` 取该行去掉首尾空白后的前 160 个字符，不展开多行，避免把无关上下文带进证据。

诊断定位还有一层：编译器输出的文件名是 `candidate.c`，行号对应原文件。验证器从 `:行:列:` 解析行号，解析失败时退回第 1 行并在消息里保留原始诊断。不要把「解析失败」伪装成「第 1 行有问题」；消息里必须能看到原始 stderr，否则复核者会被误导。

## 14.4 编译门禁：语法、警告与链接 {#sec-compilers.4.14.4}

编译门禁是最便宜的一层：不执行候选代码，只让编译器读一遍。它适合拦截语法错误、类型错误、未使用变量、格式串不匹配这类「机器能确定」的问题；它不适合证明运行时会发生什么。三种语言的门禁命令与证明范围并不相同。

| 语言 | 命令 | 能证明 | 不能证明 |
|:--|:--|:--|:--|
| Python | `python3 -I -m py_compile candidate.py` | 源码可解析，能生成字节码 | 导入是否成功、顶层代码是否抛异常 |
| C | `cc -std=c17 -Wall -Wextra -Werror -fsyntax-only candidate.c` | 预处理、解析、类型检查、警告清零 | 链接是否成功、运行时行为 |
| Rust | `rustc --edition 2021 --emit=metadata -o candidate.rmeta candidate.rs` | 名字解析、类型检查、借用检查 | 代码生成、链接、运行时行为 |

`guard.py` 的选择逻辑只有十几行：

```python
if lang == "python":
    tool = sys.executable
    argv = [tool, "-I", "-m", "py_compile", "candidate.py"]
    copy_to = workdir / "candidate.py"
elif lang == "c":
    tool = _compiler_available("cc")
    if tool is None:
        return {"status": "skip", "reason": "cc 不可用", ...}
    argv = [tool, "-std=c17", "-Wall", "-Wextra", "-Werror",
            "-fsyntax-only", "candidate.c"]
    copy_to = workdir / "candidate.c"
else:
    tool = _compiler_available("rustc")
    if tool is None:
        return {"status": "skip", "reason": "rustc 不可用", ...}
    argv = [tool, "--edition", "2021", "--emit=metadata",
            "-o", "candidate.rmeta", "candidate.rs"]
    copy_to = workdir / "candidate.rs"
```

节选里的 `...` 表示省略的字段，不是可运行代码。这段验证的是「命令与语言对应」，不验证候选代码。源文件被复制到临时目录，编译器在临时目录里运行，诊断里的文件名因此是 `candidate.c` 而不是原始路径。行号仍然对应原文件，因为复制不改变内容。

干净的 Python 文件通过编译门禁时，human 输出只有一行状态：

```bash
python3 guard.py fixtures/good/sum.py --compile
```

```text
ACCEPT     fixtures/good/sum.py (python)
  static    pass
  compile   pass
  behavior  skip (not requested)
```

C 的 `-Werror` 把警告变成错误。`fixtures/c/warn_unused.c` 只有一个未使用变量（为排版压成一行；原文件第 2 行是 `int unused = 3;`，诊断行号按原文件）：

```c
int main(void) { int unused = 3; return 0; }
```

编译器诊断是：

```text
candidate.c:2:9: error: unused variable 'unused' [-Werror,-Wunused-variable]
```

验证器把这条诊断转成 `C-SYNTAX` 高危发现，行号从诊断的 `:2:9` 解析出来。完整裁决（`examples/verdict-reject.brief.json`，真实输出，机器可读版比这里多出完整 argv）：

这份 JSON 的证据链很短：静态层 0 条发现，编译层退出码 1，行为层因为没请求而 skip。裁决是 reject，理由只有编译器诊断。人类复核字段是 `required: false`，因为这是硬失败，不需要人来「判断是否危险」；但可以申诉，所以 reason 写的是「可申诉，但不应直接合并」。`-Werror` 也有版本漂移的代价。

编译门禁只能看一个翻译单元。`fixtures/c/link_bad.c` 声明了 `missing_function()` 但没有定义，`-fsyntax-only` 会通过，因为声明足以完成类型检查。行为门禁自己编译可执行文件时才链接：

```bash
python3 guard.py fixtures/c/link_bad.c --run --tests fixtures/tests/link_bad.json
```

```text
REJECT     fixtures/c/link_bad.c (c)
  static    pass
  compile   pass
  behavior  fail (编译失败)
  [high  ] C-SYNTAX               fixtures/c/link_bad.c:1 C 链接/编译失败：Undefined symbols for architecture arm64:
  "_missing_function", referenced from:
      _main in candidate-b709a9.o
ld: symbol(s) not found for architecture arm64
clang: error: linker command failed with exit code 1 (use -v to see invocation)
```

这条输出验证了「语法通过 ≠ 能链接」。行为门禁在运行前先做一次带链接的编译；链接失败会把行为状态标成 fail，并追加一条高危发现。Python 也有类似的缝：`py_compile` 不执行 import，`fixtures/bad/missing_import.py` 能通过编译门禁，但一运行就以退出码 1 失败，行为门禁给出 `RUN-EXIT`。

Rust 的 `--emit=metadata` 会做类型检查与借用检查，但不生成机器码。`fixtures/rust/unsafe_ok.rs` 里有一个 `unsafe` 块，编译门禁通过，静态层给 `RS-UNSAFE` 中危，最终 quarantine。这说明「编译通过」与「可以接受」是两件事：Rust 编译器保证的是类型与借用规则，不保证 `unsafe` 块里的指针解引用正确。

实现时踩过一个环境坑：验证器给候选程序准备的是清理过的环境（`HOME` 指向临时目录），但 rustup 的 `rustc` 是 shim，需要 `HOME` 或 `RUSTUP_HOME` 才能找到 toolchain。直接用 `clean_env` 跑编译会得到「rustup could not choose a version of rustc」并把整个 Rust 门禁误判为编译失败。修复是分开两个环境构造函数：候选程序用 `clean_env`，编译器用 `compiler_env`（保留 `HOME`/`RUSTUP_HOME`/`CARGO_HOME`）。编译器是受信工具，不执行候选代码，这个区分是安全的。

::: note 为什么不用 `-c` 代替 `-fsyntax-only` {#note-compilers.4.14.4.1}
`-c` 会生成目标文件，能多抓一类后端错误，但也更慢、更容易受目标架构影响。本章把「语法/类型」与「链接/运行」拆成两个门禁：前者用 `-fsyntax-only`，后者在行为门禁里做一次带链接的编译。这样诊断的归属清楚：编译门禁失败是「源码不过关」，行为门禁里的链接失败是「构建不过关」。
:::

## 14.5 行为门禁：差分测试与受限执行 {#sec-compilers.4.14.5}

行为门禁要回答一个很窄的问题：在给定的输入与资源约束下，候选程序的输出、退出码与资源行为是否符合夹具？它不回答「程序是否在所有输入上正确」，也不回答「程序有没有副作用」。夹具是一个 JSON 文件，可以包含多个 case：

```json
{"name": "sum", "stdin": "3 4\n", "stdout": "7\n", "exit_code": 0, "timeout_s": 2}
```

| 字段 | 必填 | 含义 |
|:--|:--|:--|
| `name` | 否 | case 名，缺省 `case-N` |
| `argv` | 否 | 追加到候选程序后的参数 |
| `stdin` | 否 | 写入标准输入的文本 |
| `stdout` | 否 | 期望的标准输出字节；缺省时只比较退出码 |
| `exit_code` | 否 | 期望退出码，缺省 0 |
| `timeout_s` | 否 | 覆盖策略的墙钟超时，夹在 0.1–60 秒 |
| `files` | 否 | 运行前写入 case 目录的文件，键必须是相对路径 |

四个状态需要区分：`pass`（退出码与输出都匹配）、`fail-exit`（输出可能匹配但退出码不对）、`fail-output`（退出码对但字节不匹配）、`timeout`/`resource`（被墙钟或 RLIMIT 终止）。把它们压成一个布尔值会丢掉最有用的证据。

一次 case 的执行骨架如下（去掉错误处理）：

```python
argv = base_cmd + case["argv"]
with open(stdout_path, "wb") as out_f, open(stderr_path, "wb") as err_f:
    proc = subprocess.Popen(
        argv, cwd=case_dir, env=clean_env(str(case_dir)),
        stdin=subprocess.PIPE, stdout=out_f, stderr=err_f,
        start_new_session=True, preexec_fn=_set_limits(policy),
    )
    try:
        proc.communicate(input=case["stdin"].encode("utf-8"), timeout=timeout_s)
    except subprocess.TimeoutExpired:
        os.killpg(proc.pid, signal.SIGKILL)
        proc.communicate()
```

这段验证四件事：工作目录是独立的 case 目录；环境是清理过的；超时会杀掉整个进程组；标准输出落到文件而不是内存，`RLIMIT_FSIZE` 才能对输出量生效。`start_new_session=True` 让子进程成为新会话组长，`killpg` 才能覆盖它启动的普通子进程。

干净 Python 程序的 accept 裁决（`examples/verdict-accept.brief.json`，真实输出）：

::: ex 例 14.5.1 · 输出匹配但程序已经失败 {#ex-compilers.4.14.5.1}

:::

测试造假是行为门禁的软肋。一个候选程序可以读取 `CI` 环境变量，在测试环境打印期望值、在真实环境执行别的逻辑；也可以把期望输出硬编码。本章的对策有三条，但都不是证明：

1. 环境清理：只给 `PATH`、`LANG`、`HOME` 等最小变量，不继承 CI 标记；`fixtures/quarantine/env_sniff.py` 在清理后的环境里走 `local` 分支，行为输出匹配，但静态规则仍然报 `PY-TEST-SNIFF` 并 quarantine。
2. 夹具哈希：`tests_sha256` 让复核者确认 oracle 没有被替换；它不能阻止候选程序猜中输出。
3. 静态规则：`PY-TEST-SNIFF` 对 `os.environ` 的 CI 键做中危标记；它不能覆盖文件系统、argv、时间等所有环境信号。

因此「行为门禁通过」只应写成「在夹具 X 下输出与退出码匹配」。把它写成「功能正确」是越界。

## 14.6 沙箱边界：资源限制、文件与网络 {#sec-compilers.4.14.6}

先给结论：本章的「沙箱」只做资源遏制（containment），不做隔离（isolation）。它没有命名空间、没有 seccomp/landlock、没有网络命名空间、没有只读根文件系统。它能防的是「程序吃光 CPU、内存、磁盘或句柄」这一类普通错误；它不能防「程序写到工作目录之外」「程序连上网络」「程序读取同用户的其他文件」。

| 限制 | 设置 | 能拦住 | 拦不住 |
|:--|:--|:--|:--|
| `RLIMIT_CPU` | soft 2s, hard 3s | 纯 CPU 自旋 | `sleep`、阻塞 I/O、等待网络 |
| `RLIMIT_AS` | 请求 512 MB，失败则翻倍 | 大块内存分配（Linux） | macOS 上低于当前虚拟内存时无法设置 |
| `RLIMIT_FSIZE` | 1 MB | 单个文件/重定向输出超过 1 MB | 写很多个小文件；写工作目录之外 |
| `RLIMIT_NOFILE` | 64 | 打开过多句柄 | 打开一个敏感文件 |
| 墙钟超时 | 2–5 s | 死循环、长时间阻塞 | 已脱离进程组的后台进程 |

`RLIMIT_AS` 的行为在 macOS 上很不一样。策略写 512 MB，但 `setrlimit` 返回 `EINVAL`，因为进程当前的虚拟地址占用（包含 dyld 共享缓存）已经超过 512 MB。`_set_limits` 从请求值开始翻倍，直到设置成功，并把真正生效的值写进 `.limits.json`。在这台机器上，512 MB 连续翻倍 10 次，生效值是 `524288` MB（512 GB）。accept JSON 里的 `address_space_mb: 524288` 就是这么来的。它说明「策略里写的数字」与「实际生效的限制」可能不是一回事，证据必须记录后者。

```python
if hasattr(resource, "RLIMIT_AS"):
    value = as_bytes
    effective = None
    for _ in range(12):
        try:
            resource.setrlimit(resource.RLIMIT_AS, (value, value))
            effective = value
            break
        except (ValueError, OSError):
            value *= 2
    if effective is None:
        skipped.append("address_space: 无法设置低于当前虚拟内存的 RLIMIT_AS")
    else:
        applied["address_space_mb"] = effective // (1024 * 1024)
```

这段代码验证「限制真的生效了」，而不是「策略里写了」。`applied` 与 `skipped` 两个字段随 case 一起进 JSON，复核者能看到哪些限制被降级。Linux 上 512 MB 通常一次成功；macOS 上会看到 524288。两个平台都不影响 `RLIMIT_CPU`、`RLIMIT_FSIZE`、`RLIMIT_NOFILE` 的正常设置。

资源限制拦不住绝对路径写入。`fixtures/quarantine/side_effect.py` 打印 `ok`，同时向 `/tmp/guard-ch14-demo.txt` 写 8 个字节。在清理临时文件后运行：

```bash
rm -f /tmp/guard-ch14-demo.txt
python3 guard.py fixtures/quarantine/side_effect.py --run \
  --tests fixtures/tests/side_effect.json
ls -l /tmp/guard-ch14-demo.txt
cat /tmp/guard-ch14-demo.txt
```

真实输出：

```text
QUARANTINE fixtures/quarantine/side_effect.py (python)
  static    warn
  compile   pass
  behavior  pass
  [medium] PY-FS-WRITE            fixtures/quarantine/side_effect.py:2 open(mode='w')：写文件
  human_review: required (quarantine)

-rw-r--r--  1 juanwang  wheel  8 Oct 20 15:52 /tmp/guard-ch14-demo.txt
escaped
```

行为门禁判定 pass：stdout 是 `ok\n`，退出码 0，`RLIMIT` 全部生效。文件确实写到了 `/tmp`，在 case 目录之外。静态层只报了 `PY-FS-WRITE`（中危），没有报 `PY-ABS-PATH`，因为路径来自变量 `path`，不是字符串常量；静态层没有做数据流追踪。裁决仍是 quarantine，但「quarantine」来自写文件这条中危规则，不是来自「发现它逃出目录」。如果把 `PY-FS-WRITE` 加入 `allow_rules`，这份代码会 accept，而 `/tmp` 里的文件仍然存在。这个反例说明：允许规则必须配合人工复核，不能只看裁决颜色。

### v0 的核心代码

把下面案例里的 v0 简化到核心，大致是这十几行：

```python
def check(path, test):
    proc = subprocess.run(
        [sys.executable, path],
        cwd=tempfile.mkdtemp(),
        env={"PATH": "/usr/bin:/bin"},
        capture_output=True,
        text=True,
        timeout=5,
        preexec_fn=set_limits,   # RLIMIT_CPU/AS/FSIZE/NOFILE
    )
    ok = proc.stdout == test["stdout"] and proc.returncode == 0
    return {"sandboxed": ok, "stdout": proc.stdout}
```

它有三个可辩护的假设：临时 cwd 能限制相对路径；`timeout` 能限制总时长；`RLIMIT` 能限制资源。三个假设都不是隔离。`cwd` 只影响相对路径解析，绝对路径不受影响；`timeout` 只限制父进程等待；`RLIMIT` 是每进程资源计数，不是路径或网络策略。v0 还把 `sandboxed` 与 `ok` 绑在同一个布尔值上，语义上把「测试通过」升级成了「被隔离且通过」。

### agent 案例：把 RLIMIT 当安全边界

一个 agent 写了验证器 v0：用 `subprocess.run([...], timeout=5, preexec_fn=set_limits)` 执行候选代码，比较 stdout，把结果字段命名为 `sandboxed: true`。它用这个验证器审了 `side_effect.py`，stdout 匹配，退出码 0，于是 accept。半小时后有人在 `/tmp` 里发现了 `guard-ch14-demo.txt`。

现象：v0 的输出显示「sandboxed and passed」；候选程序却在工作目录之外创建了文件。根因有三层：`RLIMIT` 限制的是进程资源，不是路径空间；`timeout` 只保证父进程在 5 秒后放弃等待，不保证子进程及其后代退出；stdout 不是副作用 oracle，程序可以一边打印正确答案一边写文件。三个假设各自都「看起来合理」，合在一起就是一个错误的隔离声明。

如何发现：本章的 `workspace_created` 只快照 case 目录，看不到 `/tmp`；v0 连这个字段都没有。把 `evidence.commands` 里的 cwd 与 `ls /tmp` 对照，才定位到绝对路径写入。静态层给了一条 `PY-FS-WRITE`，但 v0 没有静态层，也没有记录「行为通过不等于无副作用」。

修复分四步。第一，静态层增加 `PY-FS-WRITE` 与 `PY-ABS-PATH`，后者只覆盖字符串常量路径；变量路径仍会漏，必须承认。第二，行为层用 `start_new_session=True` 建新会话，超时用 `killpg` 杀整个进程组；这能覆盖普通子进程，覆盖不了自己 `setsid` 的后代。第三，运行前后对 case 目录做快照，把新增文件写进 `workspace_created`；这能看见工作目录内的副作用，看不见目录外的。第四，把字段名从 `sandboxed` 改成 `bounded_execution`，并在 `limits` 里写清「不是隔离」。

修复后的验证器仍然不是沙箱。`side_effect.py` 依然能写 `/tmp`；区别是裁决变成 quarantine，证据里有一条中危发现，人工复核能看到 `open(mode='w')`。要真正阻止写入，需要文件系统命名空间、只读挂载、`landlock`/`seccomp` 或虚拟机；这些不在本章实现范围内，第 12 章给出了边界讨论。

::: errata 资源限制的三个误解 {#errata-compilers.4.14.6.1}
1. **「设了 RLIMIT_AS 就不会 OOM」**：在 macOS 上，低于当前虚拟地址占用的 AS 限制根本设不上去；即使设上去，子进程仍可能通过文件映射、共享内存或子进程绕过。证据里要写生效值，不要写策略值。
2. **「timeout 会杀死所有子进程」**：`subprocess.run(timeout=…)` 只杀直接子进程；孙进程若脱离进程组会继续运行。本章用 `start_new_session` + `killpg` 覆盖同组后代，仍不覆盖 `setsid`。
3. **「临时目录就是隔离」**：临时目录只改变 cwd，不改变路径解析。绝对路径、`..`、符号链接都能出去；`RLIMIT_FSIZE` 只限制单文件大小，不限制写到哪里。
:::

### 真正隔离需要什么

| 机制 | 加在哪 | 能多拦住 | 仍拦不住 |
|:--|:--|:--|:--|
| mount namespace + 只读根 | Linux | 写系统路径、改工作区外文件 | 内核漏洞、已挂载的可写卷 |
| network namespace | Linux | 出站连接、DNS | 通过已继承的 fd 通信 |
| `seccomp` 过滤 | Linux | 禁用 `socket`/`execve` 等系统调用 | 允许的系统调用里的逻辑漏洞 |
| `landlock` | Linux 5.13+ | 按路径限制文件访问 | 未覆盖的内核接口 |
| cgroup v2 | Linux | 内存/CPU/IO 总量 | 瞬时峰值、页缓存 |
| 虚拟机/独立主机 | 任意 | 上述全部 + 内核边界 | 硬件漏洞、侧信道 |

这张表不是实现清单，而是「声明边界时的参照系」。本章的实现只用了资源限制与进程组，没有用表里的隔离机制；因此文档里只能写「bounded execution」，不能写「sandbox」。如果部署环境需要真正的隔离，应该把候选代码送进容器/虚拟机，而不是继续往 `guard.py` 里加 `setrlimit`。

### 网络与继承的 fd

行为门禁没有网络命名空间。`fixtures/bad/net.py` 的 `socket.socket()` 会被静态层拦下（high，reject），所以它不会被执行；但如果一段代码通过第三方库或子进程 `curl` 发起连接，静态层可能只给低危或中危，行为层会真的连上去。验证器不检测出站连接，也不记录流量。要补这条，需要在容器里跑并抓包，或用 `seccomp` 禁用 `socket`；两者都超出本章实现。

文件描述符也会继承。默认 `close_fds=True` 会关掉大多数 fd，但 `stdin/stdout/stderr` 仍然连着验证器的文件；候选程序可以向 `stderr` 写大量数据，也可以读 `stdin`（本章给了空输入）。环境已经清理，但 `/proc/self/environ`（Linux）仍可能暴露验证器启动时的环境；macOS 没有 `/proc`，但 `ps` 能看到命令行。这里的结论不是「清理无用」，而是「清理只减少泄漏面，不构成隔离」。

### 超时与资源命中要分开

超时（`RUN-TIMEOUT`）与资源命中（`RUN-RESOURCE`）都是 medium，但含义不同。超时说明程序在墙钟内没有结束；资源命中说明它撞到了某条 `RLIMIT`。`fixtures/quarantine/big_output.py` 写 2 MB 到 stdout，撞到 1 MB 的 `RLIMIT_FSIZE`，进程以 1 退出并在 stderr 留下 `File too large`；验证器把它归为 `resource: fsize`，而不是 timeout。`timeout_loop.py` 则是 `timed_out: true`、`exit_code: -9`、`stdout_sha256` 为空串哈希。两种情况的复核动作不同：前者要判断输出量是否合理，后者要判断循环是否有终止条件。

### 资源限制不是权限

`RLIMIT` 管的是「这个进程最多能用多少资源」，不是「这个进程能访问哪些对象」。它不检查路径、不检查 socket、不检查 `ptrace`、不检查 `ioctl`。一个设置了 `RLIMIT_CPU=2` 的进程仍然可以读 `~/.ssh/id_ed25519`，只要它有权限；一个设置了 `RLIMIT_FSIZE=1MB` 的进程仍然可以把 1 MB 数据发到网络。把资源限制与权限控制混为一谈，是 v0 这类验证器最常见的概念错误。

权限控制需要另一套机制：文件系统权限、mount namespace、`landlock` 路径规则、`seccomp` 系统调用过滤、网络命名空间、SELinux/AppArmor。它们与 `RLIMIT` 正交：可以只用资源限制，也可以只用权限控制，也可以两者都用。本章只用前者，所以只能声称「遏制资源滥用」，不能声称「阻止越权访问」。

### 报告边界的三句话

README 与裁决 JSON 里的 `limits` 应能回答三个问题：这次执行被什么限制？哪些通道没有被限制？结论适用于哪个范围？本章的答案分别是「CPU/文件大小/句柄/墙钟，地址空间在 macOS 上被降级」「文件系统、网络、系统调用、进程后代」「在夹具与策略下的一次筛查，不是安全证明」。三句话必须同时出现；只说第一句会让人误以为有沙箱，只说第三句会让人不知道实际做了什么。

这三句话也适合放在 PR 模板里。评审者看到「bounded execution: CPU 2s, FSIZE 1MB; no filesystem/network isolation; tests X/Y」时，能立即判断这次验证的强度。看到「sandbox passed」时，只能猜测。

## 14.7 裁决协议、证据链与人类复核 {#sec-compilers.4.14.7}

裁决函数很短，短到可以全文背下来：

```text
findings = static_findings + compile_findings + behavior_findings
active   = apply_policy(findings)          # 覆盖严重度、抑制 allow_rules
m        = max(severity(f) for f in active, default=0)
if m >= reject_at:      verdict = "reject"
elif m >= quarantine_at: verdict = "quarantine"
else:                    verdict = "accept"
```

三个退出码对应三种裁决：accept 返回 0，reject 返回 1，quarantine 返回 2。输入错误（策略非法、夹具不存在、扩展名无法判断）也返回 2，但 JSON 里 `verdict` 是 `null`、`error` 有消息；脚本应同时检查退出码与 `verdict`，不要把「工具坏了」当成「代码需要人工复核」。

| 裁决 | 退出码 | 含义 | 人类动作 |
|:--|:--|:--|:--|
| accept | 0 | 在本次请求的门禁与策略下没有达到阈值的发现 | 可按正常流程合并；仍受测试覆盖限制 |
| reject | 1 | 至少一条高危发现，或行为硬失败 | 不合并；修复或申诉 |
| quarantine | 2 | 存在中危发现、超时、资源命中或证据不足 | 必须人工复核后再决定 |

裁决 JSON 的顶层字段：

| 字段 | 内容 | 复核时的用法 |
|:--|:--|:--|
| `target` / `language` | 被裁决文件与语言 | 确认对象 |
| `verdict` | accept/reject/quarantine | 与退出码交叉检查 |
| `gates` | 实际请求的层 | 确认没有把 static-only 当成全量验证 |
| `findings[]` | 规则、严重度、消息、文件、行号、代码片段 | 逐条判断真伪与严重度 |
| `suppressed[]` | 被策略抑制的规则与位置 | 审查策略是否放得太宽 |
| `checks[]` | 每层的状态、退出码、耗时 | 定位失败层 |
| `evidence` | 哈希、命令、退出码、耗时、时间 | 复现与审计 |
| `human_review` | 是否必需、状态、复核人、决定、备注 | 交接给人工 |
| `limits` | 明确不提供的保证 | 防止把裁决读成安全证明 |

quarantine 的真实 JSON（`examples/verdict-quarantine.brief.json`）：


这份 JSON 的关键不是 `verdict` 这个词，而是证据的组合：`RUN-TIMEOUT` 是中危，`PY-INFINITE-LOOP` 是低危，编译通过，行为用例的 `exit_code` 是 `-9`（被 `SIGKILL` 杀死），`timed_out` 为 `true`，`stdout_sha256` 是空串的哈希。`human_review.required` 为 `true`，`status` 为 `pending`，复核人、决定、备注都还是 `null`。这些字段一起说明「程序没有在 1 秒内结束」，而不是「程序有 bug」或「程序有恶意」。

::: method 人工复核的顺序 {#method-compilers.4.14.7.1}
1. 先看 `gates`：是 static-only、compile-only 还是跑了 behavior。没有 behavior 的 accept 只能说明静态与编译通过。
2. 再按严重度看 `findings`：高危先判断是否真调用；中危判断是否在本次补丁的语义内；低危只作背景。
3. 打开 `suppressed`：如果关键规则被 `allow_rules` 抑制，复核策略而不是代码。
4. 对照 `evidence.commands` 的退出码与 `checks` 的状态：确认没有「命令没跑但状态是 pass」的缝。
5. 对 quarantine，把 `human_review.status` 从 `pending` 改成 `approved`/`rejected`，填 `reviewer`、`decision`、`notes`；不要只改 verdict 字段。
6. 最后看 `limits`，确认这次裁决没有被当成安全证明。
:::

证据链有三个真实的缺口。第一是 TOCTOU：哈希在开始时计算，之后文件可能被替换；本章不重算。第二是 oracle 质量：夹具期望输出可能错，测试通过只证明「与夹具一致」。第三是截断：编译器 stderr 只保留末尾 2000 字符，case 的 stdout 只保留 `max_output_bytes` 字节，截断标志会进 JSON，但复核者可能忽略。把这三条写进接入文档，比在 README 里写「已验证」有用。

本项目的裁决协议是「保守 + 可解释」：宁可 quarantine，不轻易 accept；每条拒绝都能指到规则与行号；每条通过都能指到命令与哈希。它不追求自动化率，也不把人工复核当成失败。

## 14.8 Step 7：测试、对抗样例与已知限制 {#sec-compilers.4.14.8}

项目总览把验证器拆成 V1–V5 五个 Stage。V5 的验收不是「能跑一个例子」，而是「回归能重复、对抗样例有结论、限制写清楚」。完整说明见 `projects/validator/README.md`。

本章的测试套件放在 `projects/validator/tests/test_guard.py`，全部通过 CLI 调用，不 import `guard.py` 的内部函数。这样做的好处是测试锁住的是命令行契约：参数、退出码、JSON 字段；坏处是每个测试都要付一次进程启动成本，43 个测试在本机约 3.5 秒。

测试分组与数量：

| 组 | 数量 | 覆盖内容 |
|:--|--:|:--|
| StaticRules | 18 | 别名、`getattr`、字符串误报、C 宏、策略抑制/升级、目录聚合 |
| CompileGate | 7 | Python 编译、C 警告即错误、链接失败、Rust 类型检查/`unsafe` |
| BehaviorGate | 12 | accept、输出/退出码差分、超时、FSIZE、环境嗅探、argv、快照 |
| CliContract | 6 | 三种退出码、缺失夹具、参数冲突、证据字段、扩展名 |

运行入口：

```bash
cd compilers
bash projects/validator/run_tests.sh
```

真实输出末尾（时间随机器变化）：

```text
Ran 43 tests in 3.531s

OK
```

对抗样例不是为了「证明安全」，而是为了给每条规则一个已知的失败模式。表 14.2 是本章实际使用的样例。

| 样例 | 绕过意图 | 捕获层 | 残余风险 |
|:--|:--|:--|:--|
| `bad/agent_alias.py` | `from os import system as run` 隐藏调用 | 静态别名解析，high | 把函数对象放进容器再调用仍会漏 |
| `bad/getattr_concat.py` | 字符串拼接拼出 `system` | 静态常量折叠，high | 运行时拼出的名字无法折叠 |
| `quarantine/dynamic_attr.py` | 变量属性名 | 静态中危 `PY-DYN-ATTR` | 无法知道实际调用 |
| `c/macro_alias.c` | `#define LAUNCH system` | 宏别名规则，medium | 复杂宏拼接、函数式宏 |
| `good/injection_comment.py` | 注释里的 prompt injection | low 标记，不执行 | 上层 agent 可能把注释当指令 |
| `quarantine/env_sniff.py` | 读 `CI` 改变输出 | 静态 `PY-TEST-SNIFF`，medium | 通过文件/argv/时间嗅探 |
| `quarantine/side_effect.py` | 绝对路径写 `/tmp` | 静态 `PY-FS-WRITE`，medium | 变量路径、目录外写入仍会发生 |
| `quarantine/big_output.py` | 输出 2 MB 撑爆输出文件 | `RLIMIT_FSIZE` + `RUN-RESOURCE` | 多个小文件、网络发送 |
| `bad/exit_after_print.py` | 输出正确后非零退出 | `RUN-EXIT`，high | 退出码本身也可能被伪造成期望值 |

明确的已知限制：

| 限制 | 具体表现 | 影响 |
|:--|:--|:--|
| 不是隔离 | 没有 namespace、seccomp、landlock、网络隔离 | 不应运行真正不可信的代码；只能做教学与低风险筛查 |
| RLIMIT_AS 平台差异 | macOS 上 512 MB 请求生效为 524288 MB | 内存耗尽不在 macOS 上被有效限制 |
| 静态规则是模式匹配 | 变量 `getattr`、复杂宏、Rust 过程宏 | 漏报；中危规则只把不确定性变成 quarantine |
| 行为 oracle 有限 | 只覆盖夹具；stdout 超过 `max_output_bytes` 会被截断 | 通过不等于正确；超长输出无法精确比较 |
| 哈希有时序缝 | 运行前后不重算 | 文件被替换时证据不对应同一快照 |
| 编译器依赖 | `cc`/`rustc` 版本、Rust 工具链 shim | 工具缺失时 SKIP 并 quarantine，不冒充通过 |
| 无 sanitizer | 不插桩 ASan/UBSan | 越界写可能静默通过 |
| Rust raw string / Rust 宏 | `c_strip` 只处理普通字符串 | 静态扫描可能错位或漏报 |

::: note 测试全绿说明什么 {#note-compilers.4.14.8.1}
43 个测试全绿说明「当前实现与当前夹具一致」，不说明「规则覆盖完整」。把 `PY-EVAL` 从规则表删掉，`test_eval_rejected` 会立刻变红；这只证明测试能发现一类回归。把 `PY-EVAL` 的严重度从 high 改成 low，测试仍会绿，但裁决会变——这类语义变化需要策略测试或人工评审来兜。测试是回归网，不是覆盖率证明。
:::

### 一条规则怎样进入回归

新增规则不是「写个正则就完事」。本章的流程是：

1. 在 `RULES` 里登记 id、默认严重度、一句话说明；id 一旦发布不改名。
2. 写一个最小夹具，分别覆盖「应命中」与「不应命中」两种输入。
3. 在 `tests/test_guard.py` 加断言：规则 id、行号、退出码、裁决。
4. 用 `--static-only` 跑一次，确认误报控制（字符串/注释不触发）。
5. 若规则会改变执行决策，补一个 `execute_below` 或策略覆盖测试。
6. 更新 README 的规则表与本章的表 14.1；两边不一致视为文档缺陷。

第 3 步的断言要锁 id 与行号，不要锁完整消息。消息是给人读的，会改写；id 与行号是接口。

### 策略覆盖不会被测试自动发现

测试套件全部用默认策略，因此「把 `PY-EVAL` 的严重度覆盖成 low」不会让任何测试变红。跑一次就能看到：

```bash
python3 guard.py fixtures/bad/eval_dynamic.py \
  --policy fixtures/policies/eval_low.json --static-only
```

```text
ACCEPT     fixtures/bad/eval_dynamic.py (python)
  static    warn
  compile   skip (static-only)
  behavior  skip (not requested)
  [low   ] PY-EVAL                fixtures/bad/eval_dynamic.py:2 eval()：eval() 执行任意表达式
```

规则仍然命中，但阈值判断变成了 accept。这是策略的合法能力，也是风险：一份过宽的 `severity_overrides` 可以让高危规则静默失效，而回归测试仍然全绿。对策是把策略本身纳入评审：策略文件改动需要 CODEOWNERS 或独立审批；`allow_rules` 与 `severity_overrides` 的每一条都要有到期时间与理由。本章的实现只记录 `suppressed`，不记录「为什么允许」。

### CI 接入与性能预算

CI 里建议按变更文件调用，而不是扫全仓库：`python3 guard.py $(git diff --name-only)` 这类命令在文件多时会超过参数上限，应该用 `xargs` 或一个文件列表参数（本章未实现 `--files-from`）。单文件的门禁成本大约是「一次 Python 启动 + 一次编译 + 一次运行」，本机 43 个测试约 3.5 秒；全仓库扫描会线性增长，超过几十秒就应该改成增量。

CI artifact 至少保留三样：裁决 JSON、每个 case 的 stdout/stderr 文件、编译器 stderr。只保留 verdict 字段无法复盘；只保留日志不保留哈希，无法确认日志对应哪个快照。artifact 的保留期应覆盖补丁的可回滚窗口。

### Step 7 验收清单

| 项目 | 达标线 | 证据 |
|:--|:--|:--|
| 三类裁决 | run.sh 退出码 0/1/2 | 实验输出 |
| 回归 | `run_tests.sh` 全绿，≥ 25 个测试 | unittest 汇总 |
| 对抗样例 | 别名/拼接/宏/环境嗅探/绝对路径各有结论 | 14.8 表 14.2 |
| 限制 | README 与 JSON `limits` 一致 | 文档 diff |
| 可复现 | 哈希 + 命令 + 退出码 | 裁决 JSON |

### 失败时怎么查

先看 `checks` 哪一层不是 pass，再看该层的 `commands` 退出码，最后看 `findings` 的行号与片段。顺序不要反过来：先读 findings 容易被规则消息带偏，先读 checks 能定位「是静态误报、编译环境问题，还是行为夹具问题」。如果 `checks` 全是 pass 但 verdict 是 quarantine，检查 `suppressed` 与 `human_review.reason`，而不是重复跑。

### 变异测试：确认测试真的会红

回归测试的价值取决于「代码坏掉时它会不会红」。可以手工做一次变异：把 `_python_aliases` 里的 `from os import system as run` 映射注释掉，再跑 `test_import_alias_rejected`，它应当失败；恢复后应当通过。这个动作比看覆盖率数字更能说明测试是否锁住了关键行为。

变异不需要工具链：改一处、跑一个测试、恢复，三步即可。选变异点时优先选「规则解析」「阈值判断」「退出码映射」这三类核心逻辑，不要选日志文案。每次新增规则时做一次，能发现「测试只断言了 verdict，没有断言规则 id」这类空转。

### 测试之外的对拍

行为门禁的夹具是手写的；另一个独立的证据来源是「同一程序在解释器与编译执行下对拍」——第 13 章用过。对验证器自身，可以对拍「CLI 输出」与「直接调用 `evaluate()` 的返回值」：两者应当在字段上一致，除了耗时与时间戳。本章没有实现这个对拍，因为 CLI 是唯一公开接口；如果后续重构内部函数，建议补一个把 CLI JSON 与内部对象比较的测试，防止「打印时改字段」的漂移。

### 误报怎么处理

误报不是「忽略一次」就结束。处理顺序应当是：先确认规则命中的位置确实是代码而不是字符串/注释；再确认调用是否真的可达（死代码、测试辅助、平台分支）；最后判断这条规则的严重度是否适合当前策略。三步都走完，才决定改规则、改策略还是改代码。

1. 复现：用同一文件跑 `--static-only`，确认 `file:line` 与 `snippet` 指向真实调用。
2. 归类：若是字符串/注释误报，修扫描视图；若是可达性误判，考虑加白名单但记录理由。
3. 降级：个别场景可用 `severity_overrides` 降级，不要全局关规则；覆盖项要有到期时间。
4. 回归：为这个误报加一个「不应命中」的夹具，防止下次修规则时再引入。
5. 记录：在 `suppressed` 或策略评审里留下「为什么允许」，否则半年后没人知道。

### 证据保留与清理

每次裁决至少保留裁决 JSON 与测试夹具的哈希；需要复盘时，再用 `code_sha256` 找回源码。临时目录在 `TemporaryDirectory` 退出时删除，stdout/stderr 文件也随之消失，因此裁决 JSON 里的 `stdout_sha256` 与 `stderr` 片段是唯一残留。若需要完整输出，应在 `run_cases` 返回前复制到 artifact 目录；本章没有实现 artifact 存储，这是接入层的工作。

清理本身也有风险：`/tmp` 里的演示文件不会被 `TemporaryDirectory` 清掉。实验脚本应在结束时 `rm -f /tmp/guard-ch14-demo.txt`，CI 也应在 job 结束时清理已知路径。验证器不能假设「临时目录」等于「所有副作用都被回收」。

## 14.10 本章陷阱（8–15 条） {#sec-compilers.4.14.10}

::: errata 本章陷阱 {#errata-compilers.4.14.10.1}
1. **只比较 stdout**：现象是打印正确结果后以非零码退出仍被判 pass。原因是 oracle 少了一半；修复是同时比较 `exit_code`，并保留 `stdout_sha256` 作为独立事实（14.5）。
2. **把 RLIMIT 当安全边界**：现象是「sandboxed」的候选仍能写 `/tmp`、连网络。原因是资源限制不是命名空间；修复是把字段改名为 `bounded_execution`，并在 `limits` 里声明不隔离（14.6）。
3. **以为临时目录等于隔离**：现象是绝对路径、`..`、符号链接都能逃出 cwd。原因是没有挂载命名空间；修复是承认边界，或改用容器/虚拟机（14.6）。
4. **直接扫原始文本**：现象是字符串或注释里的 `system(` 触发误报。原因是没区分代码与数据；修复是先去掉注释/字符串再扫，字符串模式另开视图（14.3）。
5. **只匹配字面 API 名**：现象是 `from os import system as run` 漏报。原因是没有别名解析；修复是建立 import 绑定与规范名，动态 `getattr` 降级（14.3）。
6. **把 `-fsyntax-only` 当链接检查**：现象是声明了未定义函数仍编译通过。原因是语法门禁只看翻译单元；修复是行为门禁前做一次带链接的编译（14.4）。
7. **不锁工具链就用 `-Werror`**：现象是升级 clang 后新警告让旧代码全红。原因是警告集合随版本变化；修复是固定编译器版本并把版本写进证据（14.4）。
8. **超时只杀直接子进程**：现象是候选退出后孙进程还在跑。原因是 `subprocess.run` 只杀直接子进程；修复是 `start_new_session` + `killpg`，并声明 `setsid` 仍可逃（14.6）。
9. **夹具由被测 agent 提供**：现象是测试与实现共享同一个错误假设。原因是 oracle 污染；修复是记录夹具哈希、人工复核、用独立测试集（14.5、14.8）。
10. **忽略输出截断**：现象是 `max_output_bytes` 之外的内容不参与比较，`stdout_truncated` 为 true 却仍判 pass。原因是只比较截断后的字节；修复是把截断当 quarantine 或提高上限并明确证据（14.8）。
11. **把 quarantine 当 accept 或 reject**：现象是脚本只看 exit code 0/1，把 2 当成工具错误或直接合并。原因是三值裁决被压成二值；修复是脚本显式处理 2，并检查 `human_review.required`（14.7）。
12. **证据只有 verdict 字段**：现象是复核者无法复现，不知道跑了哪条命令、哪个策略。原因是没记哈希与命令；修复是 `evidence` 至少含 `code_sha256`、`policy_sha256`、`commands[].exit_code`（14.2、14.7）。
13. **把注释当指令**：现象是上层 agent 读到「ignore previous instructions」后修改结论。原因是把数据送进了决策回路；修复是验证器只标记不执行，评审流程也不让注释进入裁决（14.3）。
14. **把工具缺失当成通过**：现象是 `cc`/`rustc` 不在 PATH 时门禁 skip，脚本却按 exit 0 合并。原因是 skip 被当成 pass；修复是让 BUILD-TOOL-MISSING 进 quarantine，并检查 checks.status（14.4）。
15. **只在默认策略下跑测试**：现象是策略覆盖把 high 降成 low，回归仍全绿。原因是测试不覆盖策略组合；修复是加策略回归，并把 allow_rules/severity_overrides 纳入代码评审（14.8）。

::: method 即时自测 · 14 {#method-compilers.4.14.11.1}
**Q1** 文件里有 `from os import system as run` 和 `run("id")`。静态层给什么规则、什么严重度、什么裁决？如果改成 `getattr(__import__("os"), "sys" + "tem")("id")`，哪条规则先触发？

**Q2** 一个 C 文件声明了 `int missing(void);` 并调用它，`cc -std=c17 -Wall -Wextra -Werror -fsyntax-only` 通过。为什么行为门禁仍然可能 reject？请指出是哪条命令、哪个状态、哪条发现。

**Q3** 在 macOS 上策略写 `address_space_mb: 512`，accept JSON 却出现 `"address_space_mb": 524288`。这个数字是怎么来的？它说明验证器提供了什么、没有提供什么？

**Q4** 为什么静态层出现 high 发现时，行为门禁直接 skip，而不是「先跑一下看看」？这样会不会丢失运行期证据？

::: sol 答案 {#sol-compilers.4.14.11.1}
**A1** 别名解析把 `run` 还原成 `os.system`，规则 `PY-OS-SYSTEM`，严重度 high，裁决 reject。第二种写法里 `__import__("os")` 先触发 `PY-EVAL`（high），即使 `getattr` 的拼接能被折叠，裁决仍是 reject；两条规则不冲突，证据里会同时出现。

**A2** `-fsyntax-only` 只做语法/类型检查，声明足以让它通过；行为门禁在运行前用 `cc -std=c17 -O1 -o candidate candidate.c` 真正链接，链接器报 `Undefined symbols`，行为状态 `fail`，追加 `C-SYNTAX`（high），裁决 reject。关键差别是「编译一个翻译单元」与「链接成可执行文件」。

**A3** macOS 上 `setrlimit(RLIMIT_AS, 512 MB)` 返回 `EINVAL`，因为进程当前虚拟地址占用（含共享缓存）已超过 512 MB。实现从 512 MB 开始翻倍，直到设置成功，本机生效值是 524288 MB；证据记录的是生效值而不是策略值。它说明验证器提供了「可观察的资源限制与其真实值」，没有提供「按策略值强制限额」的保证；在 macOS 上内存耗尽基本不受这条限制约束。

**A4** 默认策略的 `execute_below` 是 `high`：静态严重度达到 high 就不执行。原因有二：已知危险的代码执行一次就可能造成不可逆副作用；high 已经足以 reject，运行期证据不会改变阈值判断。代价是证据里缺少「它实际做了什么」，所以 `checks.behavior.reason` 必须写「静态严重度达到 high，拒绝执行」，复核者能看出这是主动短路而不是门禁故障。若某个高危规则误报率高，正确做法是校准规则或写策略例外，而不是先执行再补证据。
