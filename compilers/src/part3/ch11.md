第 10 章用 fuzzing 和差分测试找 bug。那些手段的共同点是：跑过的输入才算数。一个跑了一百万次的程序，仍然可能在第一百万零一个输入上错；覆盖率告诉你「哪些代码被碰过」，不告诉你「所有输入都满足后置条件」。这一章换一种证据：把程序当成数学对象，对它的所有状态给一个陈述，再证明这个陈述。

形式化验证不是「再测一遍」。它先要有一份精确的语义——一条语句在什么状态下走到什么状态；然后把「程序正确」写成断言之间的蕴含；再用证明规则把蕴含拆成一组验证条件（verification condition，VC）；最后交给人或者求解器。任何一步偷懒，结论都会缩水：语义写错，证明的是另一个程序；不变式写弱，证不出后置条件；不变式写强到不可满足，可能「证明」一个错误程序；求解器返回 unknown，不是通过。

本章的主线是一个很小的命令式语言 IMP。它只有赋值、顺序、条件、循环和断言，刚好够暴露所有关键问题。起点是一个反例：

```text
int i = 0;
while (i < n) i += 2;
assert(i == n);
```

`n = 0, 2, 4` 时断言成立，`n = 1` 时 `i` 从 0 跳到 2，循环退出，断言失败。分支覆盖可以做到 100%：循环体执行过，循环条件真、假两支都走过，断言也执行过。它仍然是错的。测试覆盖的是路径，证明覆盖的是所有状态。

本章实验入口是 `experiments/ch11/`。先在仓库根目录执行：

```bash
cd compilers
bash experiments/ch11/run.sh
```

脚本会依次跑四个场景：带循环的求和程序、步长为 2 的反例、漏掉入口条件的假证明、补上入口条件后的失败。11.4 会逐行解释这些输出。实验不依赖 z3，只做化简与有限域枚举；这也正好用来说明「有界检查」和「全称证明」的差距。

读图：左边是「程序是什么意思」，右边是「程序要满足什么」，两边在 VC 处汇合。VC 不是程序本身，也不是测试用例；它是「只要这些公式成立，程序对所有满足前置条件的状态都满足后置条件」的桥梁。桥的每一端都可能出问题：语义、注解、VC 生成、求解器。

## 11.1 从测试到证明：覆盖的是路径，不是全称 {#sec-compilers.3.11.1}

先把手上的反例拆开。对 `n = 0..5` 逐步执行，记录循环次数、退出时的 `i` 和断言结果：

| `n` | 循环体执行次数 | 退出时 `i` | `i == n` |
|--:|--:|--:|:--|
| 0 | 0 | 0 | 成立 |
| 1 | 1 | 2 | 失败 |
| 2 | 1 | 2 | 成立 |
| 3 | 2 | 4 | 失败 |
| 4 | 2 | 4 | 成立 |
| 5 | 3 | 6 | 失败 |

如果测试集只选 `n = 0, 2, 4`，所有断言都通过；语句覆盖、分支覆盖、甚至「循环执行 0 次、1 次、2 次」的路径覆盖都能满足。失败只出现在奇数的 `n` 上。测试集的选取方式决定了它看不见什么；覆盖准则只约束「代码有没有被走到」，不约束「输入空间有没有被覆盖」。

::: def 定义 11.1.1 · 测试、验证与全称陈述 {#def-compilers.3.11.1.1}
给定程序 `S`、前置条件 `P`、后置条件 `Q`。**测试**是选取有限个状态 $\sigma_1,\dots,\sigma_k$，执行 `S`，检查每个终止状态是否满足 `Q`。**验证**是证明陈述「对所有满足 `P` 的状态 $\sigma$，若 `S` 从 $\sigma$ 终止于 $\sigma'$，则 $\sigma'$ 满足 `Q`」。前者只对有限输入负责：找到一个反例就能推翻全称陈述；后者要求覆盖整个状态空间。**部分正确性**只约束终止的执行；**全正确性**还要求终止。
:::

测试的优点是便宜、可自动化、能直接跑真实二进制；缺点是它只对跑过的输入负责。证明的优点是全称；缺点是它只对模型负责。两者不是替代关系：证明告诉你「在模型内没有反例」，测试告诉你「模型和实现至少在这个输入上一致」。一个经过证明的排序函数，如果编译器把比较指令编译错，最终二进制仍然可能错；这不是证明的失败，而是证明边界之外的事。

::: ex 例 11.1.1 · 100% 分支覆盖下的失败 {#ex-compilers.3.11.1.1}
程序就是本章开头的三行。取测试集 $\{0,2,4\}$：

| 输入 | 循环条件真 | 循环条件假 | 执行循环体 | 断言 |
|--:|:--:|:--:|:--:|:--:|
| 0 | 是（一次） | 是 | 否 | 通过 |
| 2 | 是（一次） | 是 | 是 | 通过 |
| 4 | 是（两次） | 是 | 是 | 通过 |

分支覆盖要求每个判定真、假都至少一次，这个测试集满足；循环体也执行过。但 `n = 1` 不在集合里，而它恰好让 `i` 从 0 跳到 2。结论：覆盖率高只说明测试集碰到了代码的每个分支，不说明它碰到了每个等价类。奇偶性是一个等价类，测试集漏掉了它。
:::

形式化验证的「全称」也有粒度。按量化对象，常见证据可以排成一张表：

| 证据 | 量化范围 | 能发现 | 不能保证 |
|:--|:--|:--|:--|
| 单元测试 | 有限输入 | 这些输入上的错误 | 未测输入 |
| 分支/路径覆盖 | 已执行路径 | 未覆盖的代码 | 同一路径上的不同数据 |
| 有界模型检查 | 深度/域有界 | 界内反例 | 界外行为 |
| 演绎证明 | 所有状态（在模型内） | 模型内的反例不存在 | 模型、编译器、硬件 |
| 翻译验证 | 单次编译的输入输出 | 这一次翻译的错误 | 下一次编译、链接器 |

这张表里没有「最强」的一行。每往右走一格，代价更高、覆盖更广，但依赖的假设也更多。工程上通常组合使用：测试守住实现，证明守住算法，翻译验证守住某一次优化，CI 守住回归。

验证的第一个隐藏假设是语义。Hoare 逻辑里的赋值公理假定「`x = e` 之后，`x` 的值就是 `e` 在旧状态下的值」。如果语言有别名、并发、异常、`volatile`，这条公理要改写；如果语言有未定义行为（undefined behavior，UB），某些状态根本没有语义，证明覆盖不到它们。第 9 章已经说明：UB 的程序没有「所有执行都满足 `Q`」这种说法，因为执行可以任意。验证一个含 UB 的程序，先要证明它不触发 UB，或者把 UB 变成显式的错误状态。

因此，「验证通过」至少要说清四件事：验证的是哪个语言子集；语义模型是什么；前置条件排除了哪些状态；后置条件是否包含终止性。少一项，结论就要降级。后面的 CompCert 一节会把这张清单用在编译器本身上。



测试的 oracle 本身也可能错。一个「期望输出」写错，测试会把正确实现判成失败，或者把错误实现判成通过。验证的 oracle 是语义与规约；测试的 oracle 是断言、参考实现或人工期望。三者都可能错，所以证据要交叉：

| oracle | 典型错误 | 后果 | 交叉检查 |
|:--|:--|:--|:--|
| 手写期望值 | 期望值抄错 | 正确实现被误杀 | 用独立实现/性质对拍 |
| 参考实现 | 参考实现同错 | 两边一起错，测试绿 | 用规格/证明/第三方实现 |
| 断言 | 断言太弱 | 错误状态通过 | 加强后置条件，做变异测试 |
| 覆盖率 | 只统计行/分支

把 oracle 写死也有代价：它会把「当前实现的行为」固化成「正确行为」。如果参考实现和被测实现共享同一个 bug，差分测试会两边都绿。测试用例要尽量从规格生成，而不是从实现反推；至少保留一组独立计算的期望值，定期用人工或第二种实现复核。
 | 漏掉数据等价类 | 补边界值、等价类、符号执行 |

这张表说明：测试通过不是「没有 bug」的证据，只是「这个 oracle 在这个输入上没意见」。证明通过也不是「绝对正确」，只是「在模型与规约内没有反例」。两种证据都要写清依赖，才能互相补位。

### 11.1.1 小域穷举：比随机测试强，仍不是证明

如果不想只测三个偶数，可以把 `n` 在一个小域里全部跑一遍。下面这段只做一件事件：对 `n = 0..11` 执行同一个循环，收集断言失败的输入。

```python
def check(n: int) -> bool:
    i = 0
    while i < n:
        i += 2
    return i == n

bad = [n for n in range(12) if not check(n)]
print("bad:", bad)
print("tested:", 12)
```

```text
bad: [1, 3, 5, 7, 9, 11]
tested: 12
```

小域穷举比随机测试强：它不是碰运气，而是把 `[0,11]` 里的每个值都覆盖了。它仍然不是证明，因为域外的 `n` 没有被检查。把域扩大到 `[0,10^6]` 也只是把「没找到」推进到更大的有限集合；只要程序对奇数的行为没有改变，域外永远有反例。

| 方法 | 覆盖的输入 | 能下的结论 | 不能下的结论 |
|:--|:--|:--|:--|
| 随机测试 100 次 | 100 个随机值 | 这 100 个值通过 | 其他值通过 |
| 小域穷举 `[0,11]` | 12 个连续值 | 这 12 个值通过 | 域外通过 |
| 小域穷举 `[0,10^6]` | 一百万个值 | 这一百万个值通过 | 第一百万零一个通过 |
| 归纳证明 | 所有整数 | 所有 `$n \ge 0$` 通过 | 模型外、编译器外 |

有界穷举的真正价值是「快速否证」：它便宜、可重复、能给出具体反例。把它当成「小规模的全称证明」就会犯错。工程上可以把有界穷举放在 CI 的快速门禁里，把归纳证明放在发布前的高保证门禁里；两者的结论要分开写，不能把前者的绿色当成后者的替代。

::: note 否证与证实的不对称
一个反例就能推翻「所有输入都正确」，一百万次通过却不能确立它。这种不对称不是测试的缺陷，而是全称陈述的逻辑性质。形式化验证的价值，在于它把「所有」写进结论；测试的价值，在于它把「具体哪里错」写进反例。两者都在回答同一个问题的不同侧面。
:::

## 11.2 操作语义与断言 {#sec-compilers.3.11.2}

Hoare 逻辑不是凭空发明的，它建立在操作语义（operational semantics）上。操作语义把「执行一步」定义成配置之间的转移关系。配置由语句和状态组成；状态是变量到整数的映射。IMP 足够小，可以把规则写全。

语法：

```text
a ::= n | x | a + a | a - a | a * a | a % a
b ::= true | false | a == a | a != a | a < a | a <= a
    | a > a | a >= a | !b | b && b | b || b
S ::= skip
    | x = a
    | S ; S
    | if (b) { S } else { S }
    | while (b) invariant (b) { S }
    | assert (b)
    | assume (b)
```

状态记作 $\sigma : \text{Var} \to \mathbf{Z}$。表达式在状态下的值记作 $\llbracket a \rrbracket\sigma$，布尔表达式记作 $\llbracket b \rrbracket\sigma \in \{\text{true},\text{false}\}$。赋值用 $\sigma[x \mapsto n]$ 表示「除 `x` 改为 `n` 外，其余不变」。

::: def 定义 11.2.1 · 小步操作语义 {#def-compilers.3.11.2.1}
配置是 $\langle S,\sigma\rangle$。小步转移关系 $\longrightarrow$ 由以下规则给出（省略显然的对称与上下文规则）：

$$
\dfrac{}{\langle x = a,\sigma\rangle \longrightarrow \langle \text{skip},\sigma[x \mapsto \llbracket a \rrbracket\sigma]\rangle}
\quad\quad
\dfrac{}{\langle \text{skip};\ S,\sigma\rangle \longrightarrow \langle S,\sigma\rangle}
$$

$$
\dfrac{\langle S_1,\sigma\rangle \longrightarrow \langle S_1',\sigma'\rangle}
     {\langle S_1;\ S_2,\sigma\rangle \longrightarrow \langle S_1';\ S_2,\sigma'\rangle}
\quad\quad
\dfrac{\llbracket b \rrbracket\sigma = \text{true}}
     {\langle \text{if}\ (b)\ \{S_1\}\ \text{else}\ \{S_2\},\sigma\rangle \longrightarrow \langle S_1,\sigma\rangle}
$$

$$
\dfrac{\llbracket b \rrbracket\sigma = \text{true}}
     {\langle \text{while}\ (b)\ \{S\},\sigma\rangle \longrightarrow \langle S;\ \text{while}\ (b)\ \{S\},\sigma\rangle}
\quad\quad
\dfrac{\llbracket b \rrbracket\sigma = \text{false}}
     {\langle \text{while}\ (b)\ \{S\},\sigma\rangle \longrightarrow \langle \text{skip},\sigma\rangle}
$$

$\longrightarrow^*$ 是 $\longrightarrow$ 的自反传递闭包。若不存在从 $\langle S,\sigma\rangle$ 出发的无限转移，则称 `S` 从 $\sigma$ 终止。
:::

规则表省略了 `assert`/`assume`：`assert(true)` 与 `assume(true)` 归约为 `skip`，`assert(false)` 进入错误配置，`assume(false)` 不产生后继。

这套规则有一个重要特征：它是**确定性**的。给定配置，至多有一条规则可以应用。把这一点写成定理，后面才能放心地用「一条路径」代表「所有执行」。

::: thm 定理 11.2.2 · IMP 的执行确定性 {#thm-compilers.3.11.2.2}
对任意语句 `S` 和状态 $\sigma$，若 $\langle S,\sigma\rangle \longrightarrow c_1$ 且 $\langle S,\sigma\rangle \longrightarrow c_2$，则 `c_1 = c_2`。
:::

::: proof 证明
对 `S` 的结构做归纳。赋值、`skip`、`assert`、`assume` 只有一条规则；顺序语句分两种情况：`S_1` 是 `skip` 时只能走顺序规则，否则只能走上下文规则，再由归纳假设 `S_1` 的下一步唯一；条件语句由 $\llbracket b \rrbracket\sigma$ 的真假唯一决定分支；循环语句同样由 $\llbracket b \rrbracket\sigma$ 唯一决定是展开还是退出。所有规则的前提都只依赖当前配置，因此不存在两个可应用且结论不同的规则。
:::

确定性说明 IMP 没有并发和内部选择。真实语言不是这样：`x = f() + g()` 的求值顺序、信号、线程交错都会让「下一步」不唯一。那些语言的 Hoare 逻辑要引入环境、rely-guarantee 或者分离逻辑。本章只用 IMP，目的是把证明的形状看清楚，而不是假装真实语言也这么干净。

下面用一个小步推导展示反例程序在 `n = 1` 时怎样走到断言失败。为了简洁，把 `while (i < n) { i = i + 2 }` 记作 `W`，把状态写成 $[i \mapsto 0, n \mapsto 1]$。

::: ex 例 11.2.1 · `n = 1` 的执行轨迹 {#ex-compilers.3.11.2.1}
$$
\begin{aligned}
\langle i=0;\ W;\ \text{assert}(i=n),[n \mapsto 1]\rangle
&\longrightarrow \langle W;\ \text{assert}(i=n),[i \mapsto 0,n \mapsto 1]\rangle \\
&\longrightarrow \langle i=i+2;\ W;\ \text{assert}(i=n),[i \mapsto 0,n \mapsto 1]\rangle \\
&\longrightarrow \langle W;\ \text{assert}(i=n),[i \mapsto 2,n \mapsto 1]\rangle \\
&\longrightarrow \langle \text{assert}(i=n),[i \mapsto 2,n \mapsto 1]\rangle
\end{aligned}
$$

此时 $\llbracket i=n \rrbracket = \text{false}$，`assert` 失败。注意第 4 步：循环条件 `i < n` 已经为假，所以循环退化成 `skip`，而不是继续执行。轨迹只有一条，因为 IMP 是确定性的；反例是「这条轨迹的终点不满足后置条件」，不是「某条交错路径出错」。
:::

断言（assertion）在语义里是一个「必须为真」的检查。`assert(b)` 在 `b` 为假时让程序停在一个错误配置，而不是产生某个任意值。验证时，`assert(b)` 变成证明义务：所有到达这里的状都要满足 `b`。这和 C 的 `assert` 宏不是一回事：C 的 `assert` 在 `NDEBUG` 下会被预处理掉，IMP 的 `assert` 是语义的一部分，永远存在。

`assume(b)` 则是「只考虑 `b` 为真的状态」。它不检查，而是把不满足 `b` 的状态从分析中删掉。验证里常用它来写前置条件或路径条件；运行时它没有对应的检查。把 `assume` 和 `assert` 混用，是后面假证明的常见来源：`assume(false)` 让一切义务空真，`assert(false)` 则要求证明矛盾。

| 构造 | 运行时行为 | 验证中的角色 |
|:--|:--|:--|
| `assert(b)` | `b` 假则出错 | 生成义务 `b` |
| `assume(b)` | 无操作 | 把 `b` 假的状态排除 |
| `if (b)` | 按 `b` 分支 | 两条路径，各自带条件 |
| `while (b)` | 可能不终止 | 需要不变式与变体 |

终止性是另一个维度。小步语义里，`while (true) { skip }` 有无限转移序列，永远不会到达 `skip`。部分正确性对这条轨迹 vacuously 为真：没有终止状态需要检查。全正确性则要求不存在无限转移。工程上很多工具默认只证部分正确性；看到「verified」时，要问一句「终止性证了吗」。

::: intuition 为什么先有语义，再有证明规则
证明规则不是从天上掉下来的。每条 Hoare 规则都要能对操作语义成立：如果规则说 $\{P\}\ S\ \{Q\}$，那么任何从满足 `P` 的状态出发、终止于 $\sigma'$ 的执行，$\sigma'$ 都要满足 `Q`。赋值公理之所以是「把后置条件里的 `x` 替换成 `e`」，正是因为操作语义把新状态定义为 $\sigma[x \mapsto \llbracket e \rrbracket\sigma]$。先写语义，规则的对错才有判据；反过来，先写规则再补语义，很容易把副作用、别名和终止性漏掉。
:::


### 11.2.1 大步语义与卡住的状态

小步语义适合看「每一步」，大步语义适合看「整个执行的结果」。大步判断写作 `$\langle S,\sigma\rangle \Downarrow \sigma'$`，表示 `S` 从 `$\sigma$` 出发、有限步后终止于 `$\sigma'$`。几条代表性规则：

```text
⟨skip, σ⟩ ⇓ σ
⟨S1, σ⟩ ⇓ σ'    ⟨S2, σ'⟩ ⇓ σ''
────────────────────────────────
⟨S1; S2, σ⟩ ⇓ σ''

b 在 σ 下为真    ⟨S1, σ⟩ ⇓ σ'
──────────────────────────────
⟨if (b) {S1} else {S2}, σ⟩ ⇓ σ'

b 在 σ 下为假
────────────────────────────────────────
⟨while (b) {S}, σ⟩ ⇓ σ

b 在 σ 下为真   ⟨S, σ⟩ ⇓ σ'   ⟨while (b) {S}, σ'⟩ ⇓ σ''
──────────────────────────────────────────────────────
⟨while (b) {S}, σ⟩ ⇓ σ''
```

大步语义不记录中间状态，所以它更适合定义「程序的结果」，不适合描述「哪里卡住」。卡住（stuck）是第三种情况：既不是 `$\Downarrow$`，也不是无限循环。例如 `assert(false)` 没有成功规则，执行停在一个错误配置；含 UB 的 C 程序在形式语义里也常常是卡住或没有规则。部分正确性对卡住和发散都不产生后置义务；这也是为什么「证明通过」不能推出「程序不会崩溃」。

| 语义 | 记录什么 | 适合证明 | 不擅长 |
|:--|:--|:--|:--|
| 小步 | 每一步配置 | 类型安全、进度、并发交错 | 全局结果，规则多 |
| 大步 | 初始/终止状态 | 编译正确性、程序结果 | 卡住位置、无限行为 |
| 公理语义 | 断言之间的关系 | 程序逻辑、WP | 运行时错误、资源 |

## 11.3 Hoare 逻辑：前置、后置与循环不变式 {#sec-compilers.3.11.3}

Hoare 三元组写作 $\{P\}\ S\ \{Q\}$。读法是：如果初始状态满足 `P`，并且 `S` 终止，那么终止状态满足 `Q`。这是部分正确性。全正确性写成 $[P]\ S\ [Q]$，额外要求终止。本章不混淆这两种记号。

::: def 定义 11.3.1 · Hoare 三元组的有效性 {#def-compilers.3.11.3.1}
三元组 $\{P\}\ S\ \{Q\}$ 在操作语义下**有效**，当且仅当：对每个状态 $\sigma$，若 $\sigma \vDash P$ 且存在 $\sigma'$ 使 $\langle S,\sigma\rangle \longrightarrow^* \langle \text{skip},\sigma'\rangle$，则 $\sigma' \vDash Q$。若 `S` 从 $\sigma$ 发散，该状态不产生义务。`P,Q` 是状态断言，$\sigma \vDash P$ 表示 `P` 在 $\sigma$ 下为真。
:::

证明系统是一组规则。下面列出本章用到的核心规则；每条都可以对照 11.2 的语义检查。

| 规则 | 形式 | 直觉 |
|:--|:--|:--|
| 赋值 | $\{Q[x := a]\}\ x = a\ \{Q\}$ | 后置条件里的 `x` 换回旧表达式 |
| 跳过 | $\{P\}\ \text{skip}\ \{P\}$ | 状态不变 |
| 顺序 | $\dfrac{\{P\}\ S_1\ \{R\}\quad \{R\}\ S_2\ \{Q\}}{\{P\}\ S_1;S_2\ \{Q\}}$ | 中间断言搭桥 |
| 条件 | $\dfrac{\{P \land b\}\ S_1\ \{Q\}\quad \{P \land \neg b\}\ S_2\ \{Q\}}{\{P\}\ \text{if}(b)\{S_1\}\text{else}\{S_2\}\ \{Q\}}$ | 两支各自证 |
| 循环 | $\dfrac{\{I \land b\}\ S\ \{I\}}{\{I\}\ \text{while}(b)\{S\}\ \{I \land \neg b\}}$ | `I` 是不变式 |
| 强化前置 | $\dfrac{P' \Rightarrow P\quad \{P\}\ S\ \{Q\}}{\{P'\}\ S\ \{Q\}}$ | 前置越弱越容易用 |
| 弱化后置 | $\dfrac{\{P\}\ S\ \{Q\}\quad Q \Rightarrow Q'}{\{P\}\ S\ \{Q'\}}$ | 后置越弱越容易证 |

赋值公理值得单独停一下。它不是「向前算」，而是「把后置条件里的变量替换成赋值右侧的表达式」。例如 $\{x + 1 \gt 0\}\ x = x + 1\ \{x \gt 0\}$ 是赋值公理的一个实例。若反过来写成 $\{x \gt 0\}\ x = x + 1\ \{x \gt 0\}$，这当然也成立，但它是强化前置/弱化后置推出来的，不是赋值公理直接给的。混淆方向会在 11.4 的 WP 里放大。

循环规则只证「保持」，不证「足够强」。规则给的是 $\{I\}\ \text{while}\ \{I \land \neg b\}$；要把后置条件 `Q` 接上，还需要 $I \land \neg b \Rightarrow Q$。要把前置条件 `P` 接上，还需要 $P \Rightarrow I$。把这三件事合起来，就是循环的三个义务：

| 义务 | 公式 | 作用 |
|:--|:--|:--|
| 初始化 | $P \Rightarrow I$ | 进入循环时不变式成立 |
| 保持 | $I \land b \Rightarrow \text{wp}(S,I)$ | 每轮结束仍成立 |
| 退出 | $I \land \neg b \Rightarrow Q$ | 不变式加退出条件足够推出后置 |

很多教程只写「保持」这一条，因为它看起来最像循环规则；但初始化与退出同样必要。缺少初始化，不变式可能从未成立；缺少退出，不变式可能太弱，退出时推不出后置。11.8 的 agent 错误正是漏掉初始化，配合一个不可满足的不变式，制造了假证明。

现在把三个义务用在求和程序上。程序是：

```text
i = 0;
s = 0;
while (i < n) {
  i = i + 1;
  s = s + n;
}
assert(s == n * n);
```

取前置 $P: n \ge 0$，后置 $Q: s = n \cdot n$，不变式 $I: s = i \cdot n \land 0 \le i \land i \le n$。逐条检查：

- 初始化：`i=0,s=0` 后，$0 = 0 \cdot n$ 成立，$0 \le 0$ 成立，$0 \le n$ 由 `P` 成立。所以 $P \Rightarrow I$。
- 保持：假设 $I \land i \lt n$。执行 `i = i + 1` 后 `i' = i+1`；执行 `s = s + n` 后 $s' = s+n = i \cdot n + n = (i+1)n$。又由 $i \lt n$ 与整数性得 $i+1 \le n$，且 $0 \le i+1$。所以 `I` 在下一轮成立。
- 退出：$I \land \neg(i \lt n)$ 给出 $i \le n$ 与 $i \ge n$，即 `i=n`；代入 $s=i \cdot n$ 得 $s=n \cdot n$。后置成立。

这三段就是一次完整的部分正确性证明。它没有枚举 `n`，对任意整数 $n \ge 0$ 都成立。终止性另算：每轮 `i` 增加 1，且 $i \le n$，所以循环最多执行 `n+1` 次；取变体 `n-i`，它在每轮严格减小且下界为 0。加上这段，才是全正确性。

::: thm 定理 11.3.2 · Hoare 逻辑相对于操作语义的可靠性 {#thm-compilers.3.11.3.2}
若三元组 $\{P\}\ S\ \{Q\}$ 可由上述规则推出，则它在 11.2 的小步语义下有效。
:::

::: proof 证明
对推导树做归纳。赋值：若终止状态 $\sigma' = \sigma[x \mapsto \llbracket a \rrbracket\sigma]$ 满足 `Q`，则 $\sigma$ 满足 `Q[x:=a]`，与公理前提一致。顺序：对 `S_1` 用归纳假设得到中间状态满足 `R`，再对 `S_2` 用归纳假设。条件：按 `b` 的真假选择分支，两边的归纳假设给出 `Q`。循环：对循环次数做归纳；每轮用保持义务维护 `I`，退出时用 $\neg b$ 与退出义务。强化前置与弱化后置由蕴含的传递性直接得到。所有规则都只依赖终止执行，因此结论是部分正确性。
:::

可靠性定理的方向很重要：它说「规则推出的结论在语义下是真的」，不说「语义下真的结论都能由规则推出」。后者是完备性，Hoare 逻辑对 IMP 是相对完备的（相对于断言语言能表达所有必要不变式），但断言语言本身可能不够强。实际工具不追求理论完备，而追求「能证的程序尽量多，证不了就报错」。

::: ex 例 11.3.1 · 一个保持义务失败的不变式 {#ex-compilers.3.11.3.1}
仍用步长为 2 的程序，取 $I: 0 \le i \land i \le n$，$P: n \ge 0$，`Q: i=n`。

| 义务 | 公式 | 结果 |
|:--|:--|:--|
| 初始化 | $n \ge 0 \Rightarrow 0 \le 0 \land 0 \le n$ | 成立 |
| 保持 | $0 \le i \land i \le n \land i \lt n \Rightarrow 0 \le i+2 \land i+2 \le n$ | 在 `i=0,n=1` 失败 |
| 退出 | $0 \le i \land i \le n \land \neg(i \lt n) \Rightarrow i=n$ | 成立 |

保持义务的反例是 `i=0,n=1`：前提满足，结论 $2 \le 1$ 不成立。这个反例同时是程序的反例：`n=1` 时循环体把 `i` 推到 2，退出后断言失败。不变式没有「编造」错误；它只是不够强，无法在奇数 `n` 上保持。
:::

如果想让这个程序通过，有两条路：把前置条件加强为「`n` 是偶数」，或者把后置条件弱化为「$i \ge n$ 且 `i-n` 是偶数」。前者缩小了程序的责任，后者承认程序不保证等于。两条路都改变了「正确性」的含义；验证的第一步永远是把这句话说清楚。

::: intuition 不变式是「猜」出来的，不是「算」出来的
循环不变式没有通用算法。归纳不变式（inductive invariant）要满足三件事：入口成立、每轮保持、退出足够强。最弱的不变式可能复杂到无法用一阶公式表达；最强的、能保持的不变式又可能推不出后置。工程上的做法是：从后置条件反推一个候选，逐条检查三个义务，失败就加强或改写。工具能帮你检查，不能替你猜。猜错的代价不是「证明失败」就是「证明了一个空集」——后者更危险。
:::

最后区分「证明」与「验证」。Hoare 逻辑是证明系统：你在纸上或证明助手里构造推导。VC 生成器把证明变成公式：你不再构造推导树，而是让求解器证明一组公式。两者等价的前提是 VC 生成器正确。VC 生成器本身也可能有 bug；11.8 就是一个。对 VC 生成器做测试、做翻译验证，和证明程序本身同样重要。


### 11.3.1 全正确性与变体

部分正确性不要求终止。把 11.3 的求和循环改成减法循环，可以看清全正确性多出来的那一步：

```text
x = n;
while (x > 0) {
  x = x - 1;
}
assert(x == 0);
```

取 `$P: n \ge 0$`，`Q: x = 0`，`$I: 0 \le x \land x \le n$`。

| 义务 | 公式 | 结果 |
|:--|:--|:--|
| 初始化 | `$n \ge 0 \Rightarrow 0 \le n \land n \le n$` | 成立 |
| 保持 | `$0 \le x \land x \le n \land x \gt 0 \Rightarrow 0 \le x-1 \land x-1 \le n$` | 成立 |
| 退出 | `$0 \le x \land x \le n \land \neg(x \gt 0) \Rightarrow x=0$` | 成立 |

三条义务只证明「如果终止，则 `x=0`」。要证明一定终止，取变体（variant）`V = x`：每轮 `x` 严格减小 1；`x` 是整数且有下界 0；所以不可能无限下降。变体的两个条件是「严格减小」与「有下界」，缺一不可。若把循环体改成 `x = x - 2`，`V` 仍然严格减小，但 `x` 可能从 1 变成 -1，退出时 `$x \ne 0$`；这时保持义务会失败（`$0 \le x-1$` 在 `x=0` 时不成立），不是变体单独能救的。

::: method 方法 11.3.3 · 构造不变式的四步 {#method-compilers.3.11.3.3}
1. 从后置条件倒推：退出时 `$\neg b$` 与 `Q` 之间差什么？把差的那部分写成候选不变式。
2. 加入范围约束：循环变量通常需要上下界，例如 `$0 \le i \le n$`；没有范围，保持义务容易失败。
3. 加入「已处理部分」的账本：求和用 `$s = i \cdot n$`，累加用 `$s = \sum_{k=0}^{i-1} a[k]$`；账本要能随循环体更新。
4. 逐条检查三个义务；保持失败就加强，退出失败就补「账本 + 退出条件」到后置的蕴含，初始化失败就弱化到入口能满足。
:::

## 11.4 最弱前置条件与符号执行 {#sec-compilers.3.11.4}

Hoare 规则可以正着用，也可以倒着用。正着用是从前置条件出发，经过每条语句，得到后置条件；倒着用是从后置条件出发，经过每条语句，得到「为了让后置成立，前面必须成立什么」。后者叫最弱前置条件（weakest precondition，WP）。

::: def 定义 11.4.1 · 最弱前置条件 {#def-compilers.3.11.4.1}
给定语句 `S` 和后置断言 `Q`，`S` 相对于 `Q` 的 WP 记作 $\text{wp}(S,Q)$，它是满足以下条件的最弱断言 `P`：对每个状态 $\sigma$，若 $\sigma \vDash P$，则 `S` 从 $\sigma$ 出发的每条终止执行都终止于满足 `Q` 的状态；并且任何满足这个条件的 `P'` 都蕴含 `P`。直观上，$\text{wp}(S,Q)$ 是「执行 `S` 后一定满足 `Q`」的初始状态集合。
:::

WP 的计算规则与 Hoare 规则一一对应，但方向相反：

| 语句 | $\text{wp}(S,Q)$ |
|:--|:--|
| `skip` | `Q` |
| `x = a` | `Q[x := a]` |
| `S1; S2` | $\text{wp}(S_1,\text{wp}(S_2,Q))$ |
| `if (b) {S1} else {S2}` | $(b \Rightarrow \text{wp}(S_1,Q)) \land (\neg b \Rightarrow \text{wp}(S_2,Q))$ |
| `assert(b)` | $b \land Q$ |
| `assume(b)` | $b \Rightarrow Q$ |
| `while (b) invariant (I) {S}` | `I`，另发保持与退出 VC |

为什么赋值是替换而不是「解方程」？因为 $\text{wp}(x=a,Q)$ 要刻画「执行后 `Q` 成立」的旧状态集合。执行后 `x` 的值是 `a` 的旧值，所以把 `Q` 里的 `x` 换成 `a`，再在旧状态上求值。这个方向与直觉相反：你不是从 `x` 的新值反解旧值，而是把后置条件「翻译」回旧状态。

::: ex 例 11.4.1 · 手算三段 WP {#ex-compilers.3.11.4.1}
**(a)** $\text{wp}(x = x + 1,\ x \gt 0) = x + 1 \gt 0$，等价于 $x \ge 0$（整数）。

**(b)** $\text{wp}(\text{if}\ (x \lt 0)\ x = -x\ \text{else}\ \text{skip},\ x \ge 0)$

$$
(x \lt 0 \Rightarrow -x \ge 0) \land (\neg(x \lt 0) \Rightarrow x \ge 0)
$$

第一项对 $x \lt 0$ 成立，第二项对 $x \ge 0$ 成立，所以整个 WP 是 `true`。这段程序对所有整数都满足后置条件（在整数范围内，`-x` 不会溢出；换成 C 的 `int` 就要考虑 `INT_MIN`）。

**(c)** $\text{wp}(s = s + n,\ s = i \cdot n) = s + n = i \cdot n$。把它再代入 `i = i + 1`，得到 $s + n = (i+1) \cdot n$。这正是求和循环保持义务的右边。
:::

WP 的优点是精确：对无循环的程序，它给出的就是最弱前置条件，不多不少。缺点是表达式会膨胀。顺序组合会把后一个语句的 WP 替换进前一个语句，分支会把两份 WP 拼成蕴含；一个 20 行的直线程序可能生成比源码大一个数量级的公式。更麻烦的是循环：`while` 的精确 WP 通常不是一阶公式能表达的，需要不变式或者不动点迭代。

符号执行（symbolic execution）换一个方向：从初始符号状态出发，正着走，把变量的值记成符号表达式，把路径条件记成 PC。遇到分支就分裂成两个状态，分别加上 `b` 和 $\neg b$。走到断言时，检查 $\text{PC} \Rightarrow Q$；走到循环时，要么展开固定次数（有界），要么用不变式汇总。

```text
初始：σ = {x ↦ x₀}, PC = true
  if (x > 0)
    ├─ 真：PC = x₀ > 0
    └─ 假：PC = x₀ ≤ 0
每条路径末端：检查 PC ⇒ 后置
```

路径数是指数级的。`k` 个互相独立的分支产生 `2^k` 条路径；20 个分支就是 1,048,576 条路径；30 个就是 10 亿条。这就是路径爆炸（path explosion）。缓解手段有：路径合并（在汇合点用 $\phi$ 或 ITE 合并）、状态子集化（subsumption）、有界展开、随机/启发式搜索、以及把循环交给不变式而不是展开。

| 方法 | 覆盖 | 代价 | 循环处理 |
|:--|:--|:--|:--|
| 全路径符号执行 | 所有路径 | 指数级 | 展开或不支持 |
| 有界符号执行 | 深度 $\le k$ | 随 `k` 增长 | 展开 `k` 次 |
| WP + 不变式 | 所有状态 | 依赖注解 | 三个义务 |
| 抽象解释 | 所有状态 | 精度换速度 | 不动点 |

现在运行实验，看看 WP 生成器实际吐出什么。命令与真实输出如下（macOS 27、Python 3.13.13）：

```bash
cd compilers
python3 experiments/ch11/proof_lab.py
```

```text

s = 0;

  i = i + 1;
  s = s + n;
}

pre : n >= 0
post: s == n * n

== verification conditions (3) ==
[entry] !(n >= 0) || 0 <= n
[exit@1] !(s == i * n && 0 <= i && i <= n && !(i < n)) || s == n * n
[preserve@1] !(s == i * n && 0 <= i && i <= n && i < n) || s + n == (i + 1) * n && 0 <= i + 1 && i + 1 <= n

[entry] no counterexample (69 assignments)
[exit@1] no counterexample (328509 assignments)

note: bounded enumeration is a test, not an unbounded proof.
```

三条 VC 对应 11.3 的三个义务。`[entry]` 是 $n \ge 0 \Rightarrow$ 循环入口处的不变式；`[preserve@1]` 是保持；`[exit@1]` 是退出。`!` 是逻辑非，`&&` 是合取，`@1` 是第一个循环。化简器把 `0 == 0 * n`、`0 <= 0` 这类常数项消掉了，但没有做线性算术推理，所以入口 VC 仍写成 `!(n >= 0) || 0 <= n`，而不是 `true`。

有界检查在 `[-4,64]` 上枚举三个自由变量，共 `69^3 = 328509` 个赋值。它没有找到反例。这个结果只能说明「在这个有限域内没有反例」，不能说明「对所有整数没有反例」。真正的全称证明是 11.3 的三段论证；脚本的作用是把 VC 生成器的输出摊开，让你检查它有没有漏义务、 substitution 有没有写错。

把程序换成步长为 2 的版本：

```bash
python3 experiments/ch11/proof_lab.py --demo parity
```

```text
== verification conditions (3) ==
[entry] !(n >= 0) || 0 <= n
[exit@1] !(0 <= i && i <= n && !(i < n)) || i == n
[preserve@1] !(0 <= i && i <= n && i < n) || 0 <= i + 2 && i + 2 <= n

== bounded check: D = [-4, 64], max_vars=3 ==
[entry] no counterexample (69 assignments)
[exit@1] no counterexample (4761 assignments)
[preserve@1] INVALID  counterexample: i=0, n=1

RESULT: FAIL (1 invalid VC(s))
```

反例是 `i=0,n=1`，与手算一致。注意 `[exit@1]` 只检查了 4761 个赋值，因为化简后只剩 `i` 和 `n` 两个自由变量（`69^2=4761`）；`[preserve@1]` 有三个变量，检查了 328509 个。自由变量数会随化简变化，输出里的计数不是性能指标，只是「枚举了多大空间」。


### 11.4.1 具体加符号：concolic 执行

纯符号执行在分支多、约束非线性时会卡住；纯具体执行只能走一条路径。concolic（concrete + symbolic）把两者混起来：先用具体输入跑一条路径，同时记录路径条件；然后取某个分支条件的否定，交给求解器生成新输入；再用新输入跑下一条路径。求解器返回 `unknown` 时，就退化成随机/变异搜索。它不能保证覆盖所有路径，但比纯随机更容易撞到边界。

| 策略 | 输入来源 | 覆盖 | 代价 |
|:--|:--|:--|:--|
| 随机 | 随机/变异 | 无保证 | 低 |
| 符号 | 求解路径条件 | 求解器能解的所有路径 | 高，可能爆炸 |
| concolic | 具体路径 + 取反 | 逐步探索可行路径 | 中，依赖求解器 |
| 抽象解释 | 抽象域不动点 | 所有状态（近似） | 精度换速度 |

::: method 方法 11.4.2 · 读一份 WP 输出 {#method-compilers.3.11.4.2}
1. 先看 `pre` 和 `post` 是否与你要证的目标一致；不一致，后面的 VC 都无意义。
2. 数 VC：一个循环至少三条（入口、保持、退出）；少一条就是漏义务。
3. 看每条 VC 的自由变量：入口通常含前置变量，保持通常含不变式变量与循环条件变量，退出含后置变量。
4. 找反例：反例的变量赋值要能手工代回源码走一遍；代不回去，说明 VC 生成或语义有 bug。
5. 看 `RESULT`：`NO-COUNTEREXAMPLE-IN-DOMAIN` 不是「证明」，只是「有限域内没找到」；`valid by simplification` 才是化简器证明的恒真。
6. 把 VC 与 11.3 的三个义务逐一对应；对不上就停下来查生成器。
:::

::: errata WP 的三个常见方向错误
1. **把赋值公理写成向前替换**：$\text{wp}(x=e,Q)$ 是 `Q[x:=e]`，不是「解出 `x`」。写成 `Q` 本身，会漏掉赋值的影响。
2. **把 `if` 的 WP 写成合取两支**：正确形式是两条蕴含的合取；直接合取 $\text{wp}(S_1,Q) \land \text{wp}(S_2,Q)$ 会把两个分支的义务都要求成无条件成立，过强。
3. **把循环的 WP 当成不变式本身**：不变式只是 WP 的一个上近似；它必须附带入口、保持、退出三条 VC，单独一个 `I` 不构成证明。
:::

## 11.5 SMT 编码与可判定性边界 {#sec-compilers.3.11.5}

VC 生成之后，剩下的问题是「这个公式是不是恒真」。对小公式可以化简，对带算术、数组、位向量的公式，通常交给 SMT（satisfiability modulo theories）求解器。SMT 的思路是：把公式的否定交给求解器，返回 `unsat` 表示原公式恒真；返回 `sat` 时给一个模型，就是反例；返回 `unknown` 则是求解器放弃。

一个 VC 的 SMT-LIB 编码大致是这样。它验证的是「入口条件加上循环入口不变式」这一条：

```text
(set-logic QF_NIA)
(declare-const n Int)
(declare-const i Int)
(declare-const s Int)
(assert (not (=> (>= n 0)
                 (and (= s (* i n)) (<= 0 i) (<= i n)))))
(check-sat)
(get-model)
```

这条 VC 含 `i * n`，是变量乘变量，所以落在 QF_NIA；如果只取线性部分，可以用 QF_LIA。这段编码没有在本机执行：实验环境没有安装 z3，`proof_lab.py` 也不依赖它。这里展示的是编码形态，不是求解结果。若安装了 z3，`unsat` 对应入口 VC 有效；`sat` 会给出一个反例模型。不要把这段文字当成已经跑过的证据。

可判定性取决于公式落在哪个理论片段。下面这张表是选择工具时的第一道筛子：

| 片段 | 可判定性 | 典型用途 | 备注 |
|:--|:--|:--|:--|
| 命题逻辑 | 可判定（NP 完全） | 布尔 VC、配置约束 | 规模大时仍需启发式 |
| QF_LIA（线性整数算术） | 可判定（Presburger） | 循环边界、数组下标 | 复杂度高，但理论上有判定过程 |
| QF_LRA（线性实数） | 可判定 | 浮点近似、几何 | 不含整数取整 |
| QF_BV（位向量） | 可判定 | 机器整数、溢出 | 位宽固定，适合 C |
| QF_NIA（非线性整数） | 不可判定 | 乘法、多项式不变式 | 希尔伯特第十问题 |
| 带量词的整数算术 | 不可判定 | 归纳不变式 | 需要切模式或证明助手 |
| 分离逻辑 | 视片段而定 | 堆、链表 | 小片段可判定 |

两个结论要分清。第一，QF_LIA 可判定，所以线性不变式的 VC 原则上可以由求解器给出是/否；实际中求解器可能超时，返回 `unknown`。第二，QF_NIA 不可判定：不存在对所有输入都终止并给出正确答案的算法。像 `s == i * n` 这样的乘法不变式已经落在非线性整数算术里；实验里的枚举能找反例，但不能替你对所有整数证明。

::: thm 定理 11.5.1 · QF_LIA 的可判定性 {#thm-compilers.3.11.5.1}
量化自由的线性整数算术（Presburger 算术）的满足性问题可判定。
:::

::: proof 证明思路
Presburger 算术允许加法、整数常数、比较和布尔组合，不允许乘法（常数乘变量可由重复加法展开）。它的判定过程可以基于量词消去：对形如 $\exists x.\ \varphi(x)$ 的公式，消去 `x` 后得到一个等价的、不含 `x` 的公式；反复消去直到只剩常数比较。另一种实现是欧几里得抽象或整数线性规划。两种构造都终止，因此满足性可判定。复杂度是超指数的，所以「可判定」不等于「跑得快」。
:::

::: thm 定理 11.5.2 · QF_NIA 的不可判定性 {#thm-compilers.3.11.5.2}
量化自由的非线性整数算术的满足性问题不可判定。
:::

::: proof 证明思路
希尔伯特第十问题问「整系数多项式方程是否有整数解」，已被证明不可判定（Matiyasevich，1970）。任意这样的方程 $p(x_1,\dots,x_n)=0$ 都可以写成 QF_NIA 公式 $p(x_1,\dots,x_n)=0$；若 QF_NIA 可判定，就能判定希尔伯特第十问题，矛盾。因此不存在对所有 QF_NIA 公式都终止并正确回答的算法。实践中求解器对很多实例仍然有效，但总有实例让它返回 `unknown` 或发散。
:::

不可判定性不是「不要用 SMT」的理由。它说明：工具不能保证对每个输入都给答案；工程上要设置超时、资源上限，并把 `unknown` 当作「未证」，而不是「通过」。一个 CI 门禁如果把 `unknown` 当成功，等于把不可判定性变成了静默的漏洞。

编码本身也会引入错误。下面这些坑在 C 程序上尤其常见：

| 源码概念 | 朴素编码 | 问题 | 正确做法 |
|:--|:--|:--|:--|
| `int` 溢出 | 数学整数 | C 的有符号溢出是 UB；数学整数不溢出 | 用位向量，或显式加溢出检查 |
| 除法/取模 | 实数除法 | C 的向零截断、负数取模 | 按 C 语义编码 `quot`/`rem` |
| 指针 | 一个整数 | 别名、越界、生命周期 | 用数组模型 + 显式边界 |
| 浮点 | 实数 | 舍入、NaN、`-0.0` | 用浮点理论或避免 |
| 未初始化内存 | 任意值 | UB 或不确定值 | 显式建模，或先证明不读未初始化 |
| 函数调用 | 纯函数 | 副作用、全局状态 | 用 havoc + 后置条件 |

一个具体的编码陷阱来自「有符号溢出是 UB」。源码：

```c
int f(int x) {
    return x + 1 > x;
}
```

如果把它编码成数学整数，`x+1 > x` 对所有整数恒真，于是 VC 被证成 `true`。但 C 的 `int` 在 `x == INT_MAX` 时发生有符号溢出，行为未定义；编译器可以把整个函数折成 `return 1`，也可以做别的。数学整数模型证明的是「没有溢出的那个函数」，不是这段 C 代码。要覆盖 C 的真实行为，得用 32 位位向量，并把溢出路径显式标成错误状态；或者先证明 `x < INT_MAX`。第 9 章已经把这条边界讲透，这里只强调：编码的选择会改变被证明的对象。


### 11.5.2 量词与归纳不变式

循环不变式天然带量词：`$s = \sum_{k=0}^{i-1} a[k]$` 展开后是「对所有 `k`」。SMT 求解器对带量词的公式通常不保证判定；它会用触发模式（trigger）实例化量词，可能不终止，也可能漏实例化。工程上的替代是：把求和写成递归函数/折叠，用归纳法证明；或者把不变式限制在量化自由的片段，把量词消去。不要假设「SMT 能处理所有数学公式」；它处理的是你选定的理论片段。

::: errata 关于 SMT

不可判定不等于「所有实例都难」。很多工业 VC 落在 QF_LIA/QF_BV 的可判定片段，求解器几毫秒就能给出答案；真正困难的是带量词、非线性、数组与堆的混合公式。工程上的策略是「把问题切小」：把大循环拆成不变式，把内存拆成数组片段，把非线性乘法换成有界位向量。切不动的部分标记为未证，而不是硬说通过。
 的四个误解
1. **「`unsat` 就是程序正确」**：只说明 VC 在编码下不可满足；编码错了、语义漏了、前置条件太强，都会让错误的程序得到 `unsat`。
2. **「`sat` 一定是程序 bug」**：模型可能包含源码不可能出现的状态（例如违反前置条件、整数溢出）；要先确认模型合法。
3. **「`unknown` 可以当通过」**：`unknown` 是未证，不是证毕；CI 应当把它标成待处理。
4. **「SMT 能处理所有循环」**：循环需要不变式或展开；SMT 只解你给它的公式，不替你猜不变式。
:::

::: note 求解器的可信基础
SMT 求解器本身是大程序，也可能有 bug。高保证场景会要求求解器输出证明（proof log），再用独立的证明检查器验证；或者用经过验证的求解器/检查器。即便求解器正确，VC 生成器、语义模型、前置条件仍然是信任基。把整条链的每一环写清楚，比迷信一个 `unsat` 更有用。
:::


### 11.5.1 三种求解结果的处理

求解器不是预言机。它返回三种结果，每种对应不同的工程动作：

| 结果 | 含义 | 行动 |
|:--|:--|:--|
| `unsat` | 否定不可满足，VC 在编码下有效 | 检查编码、前置条件、公理；记录求解器版本与超时 |
| `sat` | 存在模型，VC 有反例 | 把模型代回源码；确认模型满足前置条件与类型约束 |
| `unknown` | 求解器未能判定 | 拆分 VC、换理论、加超时、转人工证明；不能算通过 |

`sat` 的模型不一定是程序反例。模型可能给 `x` 一个超出 `int` 范围的值、违反前置条件、或让未初始化内存取任意值。先把模型过滤一遍：满足前置条件吗？所有中间值都在类型范围内吗？路径条件与源码可达吗？三项都过，才是真正的反例。过滤脚本本身也要测试，否则会把「模型不合法」误报成「程序 bug」。

::: method 方法 11.5.3 · 给 VC 选求解器 {#method-compilers.3.11.5.3}
1. 先看公式里有没有乘法变量对变量：有就是非线性，准备 `unknown` 或手工不变式。
2. 有机器整数就用位向量；有数组/堆就用数组理论或显式内存模型。
3. 把前置条件写成 `assume`，不要让求解器去猜调用方的约束。
4. 给每个 VC 单独超时；超时的 VC 标记为未证，不要合并成一个「整体通过」。
5. 保留求解器的模型/证明日志；没有日志的 `unsat` 很难复核。
:::

## 11.6 翻译验证：CompCert 与「编译器正确性」 {#sec-compilers.3.11.6}

前面证明的是源程序。源程序要变成机器码，还要经过编译器、汇编器、链接器、加载器。编译器本身也可能错：优化把 `x/0` 折成常量、寄存器分配把活跃值放到被调用者破坏的寄存器、指令选择把 32 位运算写成 64 位。测试编译器只能发现某些输入上的错误；要排除一整类错误，需要证明编译器。

CompCert 是在这方面最著名的工程之一。它用 Coq 写了一个 C 子集的编译器，并为编译过程建立了语义保持（semantic preservation）证明。直观地说：如果源程序的行为是定义好的，编译后的目标程序的行为必须是源程序允许的行为之一；对确定性程序，就是「结果相同」。

::: def 定义 11.6.1 · 语义保持 {#def-compilers.3.11.6.1}
设 $\mathbf{S}$ 是源语言程序，$\mathbf{T}$ 是目标语言程序，$\rightsquigarrow$ 是编译关系。若对每个源程序 `S` 和每个目标程序 `T` 满足 $S \rightsquigarrow T$，以及每个定义好的源行为 `B`，目标程序 `T` 的行为集合包含 `B`（或与 `B` 在可观察事件上一致），则称该编译关系保持语义。不同编译器对「行为」的定义不同：有的只比较返回值和系统调用，有的还比较终止性、内存分配失败、外部调用顺序。
:::

::: thm 定理 11.6.2 · CompCert 的语义保持（条件陈述） {#thm-compilers.3.11.6.2}
在 CompCert 3.x 所覆盖的 C 子集与其形式化语义下，若源程序 `S` 的行为是定义好的，且 CompCert 将 `S` 编译为 `T`，则 `T` 的可观察行为是 `S` 允许的行为之一。该结论覆盖 CompCert 内部经过证明的编译阶段；不覆盖预处理器、解析器、汇编器、链接器、运行时库、操作系统与硬件。
:::

这个定理的力量和边界同样重要。先看它覆盖了什么：

| 阶段 | 是否在证明内 | 说明 |
|:--|:--|:--|
| C 前端解析 | 否 | 预处理器与解析器通常不在 Coq 证明内 |
| 类型检查/语义分析 | 部分 | 取决于版本与前端实现 |
| 中间表示与优化 | 是 | 各 pass 有 semantic preservation 引理 |
| 指令选择/寄存器分配 | 是 | 目标语义与源语义通过模拟关系连接 |
| 汇编文本生成 | 是（到 asm AST） | 打印成文本后由外部汇编器接管 |
| 汇编器/链接器 | 否 | 外部工具，可能重排、放松、重定位 |
| 运行时/OS/硬件 | 否 | 系统调用、信号、页错误、CPU 行为 |

所以「CompCert 编译的程序绝对正确」是错的。正确的说法是：在 CompCert C 语义覆盖的范围内，且源程序不触发 UB，编译阶段不会引入新的可观察行为。源程序自己写错、汇编器有 bug、链接到错误的库、操作系统违反假设，都不在定理里。

为什么解析器常常不在证明内？把完整的 C 预处理器和解析器形式化很费劲，而且它们的输入是文本、文件系统、宏展开；这些外部交互难以纳入纯语义模型。CompCert 的策略是把「已解析的 AST」作为信任起点，前端用常规工程手段测试。你看到的「verified compiler」通常指「从某个中间表示到汇编」这一段的验证，不是「从磁盘上的字节到进程」的全链路。

汇编器与链接器同理。编译器输出的是汇编文本或汇编 AST；真正变成机器码还要经过 `as`、`ld`、重定位、PLT/GOT、加载器。第 8 章只交叉引用这些基础，本节也不重写；要点是：语义保持的证明在「汇编文本」处截止，后面的工具没有被证明。一个经过 CompCert 编译的程序仍然可能因为链接到不兼容的 ABI 而崩溃。

还有一层：源语言的语义。CompCert C 不是 ISO C 的全部。它有自己的形式化语义，某些在 ISO C 中未定义或实现定义的行为，在 CompCert C 里可能有确定解释；反过来，某些 ISO C 程序在 CompCert C 里可能不被接受。证明只对这套形式化语义负责。如果你把「ISO C 程序」当作源，先要确认它落在 CompCert C 的子集里。

::: ex 例 11.6.1 · 证明边界外的一次失败 {#ex-compilers.3.11.6.1}
假设源程序有一个有符号整数溢出。ISO C 说这是 UB；CompCert 的语义保持定理只对行为定义好的源程序负责，不会保证「你期望的溢出回绕」。如果程序员期望 `INT_MAX + 1` 变成 `INT_MIN`，他验证的不是 C 程序，而是某个特定编译器的偶然行为。修复不是换编译器，而是改源码：用无符号类型，或显式检查溢出。

另一个例子：源程序调用了一个外部函数，链接时连到了 ABI 不兼容的实现。CompCert 证明的是「调用按 ABI 传递参数」，不是「被调用方真的按这个 ABI 实现」。链接器把两个不兼容的目标文件拼在一起，定理管不到。
:::

与「verified compiler」相对的是翻译验证（translation validation）：不证明编译器本身，而是每次编译后检查「这一次的输入和输出语义一致」。检查器可以比编译器简单，甚至可以用另一个工具生成证明。翻译验证的优点是：编译器升级、优化规则变化时，不需要重新证明整个编译器；缺点是：每次编译都要付检查成本，而且检查器本身也要可信。

| 方法 | 证明对象 | 成本 | 失效模式 |
|:--|:--|:--|:--|
| 测试编译器 | 有限输入 | 低 | 未测输入 |
| 经过验证的编译器 | 编译器所有输入（在模型内） | 极高（一次性） | 模型、前端、汇编器、链接器 |
| 翻译验证 | 单次编译 | 中（每次） | 检查器 bug、规约不完整 |
| 差分测试 | 两个编译器 | 低 | 两边同错 |

工程上常见组合：核心优化用翻译验证或经过验证的 pass，前端和链接用测试与 CI 守住。第 12 章会把这条思路延伸到 JIT：JIT 每次生成的代码都可以反汇编、差分、检查权限，而不必证明整个 JIT 编译器。

::: intuition 为什么「编译器正确」比「程序正确」更难说清
程序正确有明确的源语义作参照；编译器正确要同时说清源语义、目标语义、可观察行为、以及两者的关系。目标语义还依赖 ABI、内存模型、浮点舍入、系统调用。任何一项没形式化，证明就有一个洞。CompCert 的贡献不是「消灭了所有洞」，而是把洞的位置标得很清楚：证明内的阶段可以依赖，证明外的阶段要另找证据。
:::


### 11.6.1 证明结构：模拟关系

语义保持不是一条大定理，而是一串「每一步都保持关系」的引理。每个编译阶段建立源配置与目标配置之间的模拟关系（simulation relation）；如果源走一步、目标能走若干步并回到关系里，关系就保持。把所有阶段串起来，得到整条编译链的保持。

<pre class="layout">
C source
  |  parse（未验证）
  v
C AST --&gt; Clight --&gt; Cminor --&gt; RTL --&gt; LTL --&gt; Mach --&gt; asm AST
             |         |         |        |        |
             +---------+---------+--------+--------+-- 每段有模拟关系
                                                          |
                                                          v
                                                       .s 文本
                                                          |  as/ld（未验证）
                                                          v
                                                       进程
</pre>

读图：证明的边界画在「asm AST → .s 文本」附近。文本之前的每个箭头都有语义保持引理；文本之后的 `as`、`ld`、加载器、运行时不在证明里。把这条边界记成一句话：**CompCert 证明的是翻译，不是工具链**。

| 阶段 | 证明内容 | 依赖的模型 |
|:--|:--|:--|
| Clight → Cminor | 表达式/语句的语义保持 | C 内存模型、整数语义 |
| Cminor → RTL | 控制流与变量映射 | 局部变量、调用 |
| RTL → LTL | 寄存器分配/线性化 | 寄存器、栈槽 |
| LTL → Mach | 指令选择/调用约定 | 目标 ISA、ABI |
| Mach → asm | 汇编语法 | 打印格式 |

整条编译链的定理是各阶段引理的组合：如果每个阶段都保持可观察行为，组合关系也保持。组合的传递性依赖「可观察行为」的定义在每一层一致；如果某个阶段只保留返回值、另一个阶段还保留异常/终止性，组合时就会漏掉后者。读 CompCert 论文或文档时，先找「behavior」的定义，再看每个 pass 的定理用的是不是同一个。


这也解释了为什么「换一个后端」不是免费的：每个后端都要重新建立模拟关系，目标 ISA 的语义、ABI、内存模型都要形式化。CompCert 支持多个后端，但每个后端的证明是独立的；没有证明的后端不能继承前端的结论。

::: note 版本与优化级别
CompCert 的证明随版本演进，支持的 C 子集、优化 pass、目标架构都会变化。引用「CompCert 证明了编译器」时，至少要写清版本、目标架构、优化选项和源语言子集；只写产品名，结论不可复核。就像引用编译器 bug 要写版本与命令行一样。
:::


### 11.6.2 翻译验证检查什么

翻译验证不证明编译器，而是证明「这一次的输入和输出等价」。以一个窥孔优化为例：把 `x * 2` 改成 `x + x`。检查器要为所有 32 位 `x` 证明两条指令序列的结果相同；用位向量求解，`x + x` 与 `x * 2` 在模 `2^{32}` 下相等（包括溢出回绕），所以这次替换合法。如果优化把 `x * 2` 改成 `x << 1`，对无符号数也成立；对有符号负数，左移在 C 里是 UB，检查器必须按目标语义判断，而不是按数学整数。

| 检查对象 | 需要的模型 | 检查器能发现 | 检查器可能漏掉 |
|:--|:--|:--|:--|
| 单条窥孔规则 | 目标 ISA 的位向量语义 | 这一条规则的等价性 | 规则触发条件写错 |
| 一个基本块 | 寄存器/标志/内存 | 块内指令替换错误 | 跨块优化 |
| 一次编译 | 源/目标语义关系 | 这一次输入输出不等价 | 规约/模型错误 |
| 整个编译器 | 所有 pass 的语义 | 不需要逐次检查 | 证明规模巨大 |

翻译验证的检查器通常比编译器小，但也不是「零信任」。检查器可能写错、可能漏掉标志位、可能把浮点 NaN 当成相等。高保证场景会要求检查器也经过验证，或者用两个独立检查器交叉。它的优势是定位准：失败时直接给出「这一条规则/这一次编译」的反例，而不是「编译器某处有 bug」。

## 11.7 轻量验证：契约、断言与 CI {#sec-compilers.3.11.7}

不是每个项目都值得上 Coq。工程上更常见的是轻量验证：把关键前提写成契约（contract），把关键不变量写成断言，把检查放进 CI，让每次提交都重新验证。它不覆盖所有状态，但能把「上次修过的 bug」变成「以后不会再静默回归」。

::: def 定义 11.7.1 · 契约与运行时断言 {#def-compilers.3.11.7.1}
**契约**是函数或模块与调用方之间的声明：前置条件（precondition）说明调用方必须保证什么，后置条件（postcondition）说明被调用方保证什么，不变式（invariant）说明在哪些时刻什么性质必须成立。**运行时断言**是把契约的一部分编译成检查，在程序执行到该点时验证；失败时终止或进入错误处理。断言不是输入校验：它检查的是「程序员认为不可能发生」的内部状态，不是「用户可能传什么」。
:::

先看一个能编译、能运行的最小例子。这段验证的是：`abs_int` 在调用方遵守「不传 `INT_MIN`」的前提下，返回非负值。

```c
#include <assert.h>
#include <limits.h>

static int abs_int(int x) {
    assert(x != INT_MIN);
    return x < 0 ? -x : x;
}

int main(void) {
    assert(abs_int(-7) == 7);
    assert(abs_int(0) == 0);
    assert(abs_int(7) == 7);
    return 0;
}
```

编译并运行：

```bash
cc -std=c17 -Wall -Wextra -Werror contract.c -o contract
./contract
echo "contract rc=$?"
```

```text
contract rc=0
```

把同一个程序用 `-DNDEBUG` 再编译一次，所有 `assert` 都会被预处理掉。为了看清这一点，用一个必然失败的断言：

```c
#include <assert.h>

int main(void) {
    assert(0);
    return 0;
}
```

```bash
cc -std=c17 -Wall -Wextra -Werror fail.c -o fail
./fail
echo "fail rc=$?"
cc -std=c17 -Wall -Wextra -Werror -DNDEBUG fail.c -o fail_ndebug
./fail_ndebug
echo "ndebug rc=$?"
```

关键输出（macOS 27、Apple clang 21）：

```text
Assertion failed: (0), function main, file fail.c, line 4.
fail rc=134
ndebug rc=0
```

`rc=134` 是 `SIGABRT` 的退出码。`-DNDEBUG` 版本直接返回 0，因为断言根本不存在。这个差异是断言的第一条边界：**断言不是安全边界**。如果程序依赖断言来拒绝恶意输入，发布构建把断言去掉，检查就消失了。

断言还有第二个陷阱：副作用。`assert(i++ < n)` 在启用断言时会自增，在 `-DNDEBUG` 下不会。同一个程序在两种构建下行为不同，测试可能全绿，发布却错。规则很简单：断言里只放无副作用的纯表达式。

| 手段 | 检查时机 | 保证 | 典型失效 |
|:--|:--|:--|:--|
| `assert` | 运行时（可被 `NDEBUG` 移除） | 到过该点的状态满足条件 | 发布构建移除、副作用 |
| `_Static_assert` | 编译时 | 常量表达式为真 | 只能检查编译期常量 |
| 契约（ACSL/Dafny/SPARK） | 静态或运行时 | 调用方/被调用方义务 | 规约写错、工具不支持 |
| 单元测试 | 运行时 | 选定输入 | 未测输入 |
| CI 门禁 | 每次提交 | 回归 | 跳过、超时、环境差异 |
| 证明助手 | 静态 | 模型内全称 | 模型与实现的距离 |

轻量验证的工程做法，是把这些手段按成本排列，放在不同的门禁上：

::: method 方法 11.7.2 · 把契约放进 CI {#method-compilers.3.11.7.2}
1. **列出关键函数**：只给边界、解析、内存分配、权限判断这类函数写契约，不要给每个 getter 写。
2. **写前置/后置**：前置写调用方义务（非空、长度上界、状态机位置），后置写返回值与副作用。能写成机器可检查的，优先用 ACSL/Dafny/SPARK 语法。
3. **运行时检查**：在测试构建启用断言与契约检查；发布构建明确记录哪些检查被移除。
4. **静态检查**：把编译器警告、`-Werror`、UBSan、类型检查、契约工具放进 CI；对 `unknown`/超时设人工复核。
5. **回归证据**：每次修 bug，先加一个能复现的测试或契约，再修；确保 CI 在修复前红、修复后绿。
6. **审计信任基**：列出没有被工具覆盖的部分（第三方库、汇编、链接器、OS），在发布说明里写清楚。
:::

CI 里最容易造假的是「绿色」。一个 job 超时被标成 skipped、一个 `unknown` 被脚本当成 0、一个 `|| true` 把失败吞掉，都会让门禁看起来通过。门禁脚本要显式区分「通过」「失败」「未证」三种状态；未证不能算通过。第 14 章的 agent 代码验证器会把这一点做成裁决协议。

契约的另一个边界是规约本身。你可以证明「函数满足后置条件」，但如果后置条件写的是 `true`，证明毫无信息；如果前置条件写的是 `false`，任何实现都满足。规约太弱，证明没有用；规约太强，调用方无法满足。11.8 的假证明就是「规约/不变式不可满足」的一个变种。

::: errata 轻量验证的四个坑
1. **用断言做输入校验**：`assert` 在 `NDEBUG` 下消失；用户输入必须用显式错误处理，不是断言。
2. **断言里放副作用**：`assert(f() == 0)` 在发布构建里可能根本不调用 `f()`；两种构建语义不同。
3. **把 CI 绿当成证明**：CI 只覆盖它跑过的配置和输入；超时、跳过、`unknown` 都要单独处理。
4. **契约只写在注释里**：注释不会被执行，也不会被工具检查；要么用可检查的语法，要么至少加运行时断言。
:::


### 11.7.1 断言与错误处理的分工

断言和错误处理解决两类不同的问题，混用会让发布构建出现空洞：

| 场景 | 应该用什么 | 失败时 | 发布构建 |
|:--|:--|:--|:--|
| 内部不变量（不可能发生） | `assert` / 契约 | 终止并报告 bug | 可移除，但要记录 |
| 用户输入非法 | 显式检查 + 错误码 | 返回错误、拒绝请求 | 必须保留 |
| 资源不足 | 显式检查 + 回退 | 降级或重试 | 必须保留 |
| 编译期配置 | `_Static_assert` | 编译失败 | 不适用 |

这张表的核心是「谁负责」。断言把责任放在程序员身上：如果断言失败，说明代码有 bug，不是用户输入的问题。错误处理把责任放在调用方或用户身上：输入非法是预期情况，必须有可恢复的路径。把用户输入交给断言，等于把「预期情况」当成「不可能情况」，发布构建一移除断言，攻击者就能把非法输入送进后面的代码。

::: note 契约写在哪里
契约可以写在类型里（非空、枚举、newtype）、写在函数签名里（返回 `Result`）、写在注释里（ACSL）、写在运行时检查里。四种位置的保证强度不同：类型和签名由编译器检查，注释要靠工具，运行时检查只在启用时有效。选择位置时，先问「这个约束错了会导致什么」：会导致内存安全，就尽量放进类型；只是性能假设，运行时断言即可。
:::


### 11.7.2 CI 的三种状态

门禁脚本只返回 0/1 不够。验证任务有第三种结果：未证。把未证映射成 0 会让超时和 `unknown` 静默通过；映射成 1 又会让所有不支持的边角料阻塞合并。可行的做法是三种状态、三种处理：

| 状态 | 退出码 | 合并策略 | 记录 |
|:--|:--|:--|:--|
| PASS | 0 | 允许 | 证据路径、工具版本、耗时 |
| FAIL | 1 | 阻止 | 反例、VC、复现命令 |
| UNKNOWN | 2 | 人工复核/延后 | 超时、未支持的理论、缺失注解 |

CI 平台通常只认 0/1，所以 UNKNOWN 要单独开一个 job 或在报告里显式列出；不要用一个 `|| true` 把它吞掉。第 14 章的裁决协议会把 PASS/FAIL/QUARANTINE 分开，思路相同。

## 11.8 agent 错误：不变式过强导致的假证明 {#sec-compilers.3.11.8}

这一节复现一个具体的 agent 失败。任务很普通：给一个循环程序生成 WP 验证条件，证明 `assert(i == 42)`。程序是：

```text
i = 0;
while (i < n) {
  i = i + 1;
}
assert(i == 42);
```

这个程序对任何 `n` 都不保证 `i == 42`：`n = 0` 时 `i = 0`，断言直接失败。正确的验证器应当报出反例。agent 却报告「所有 VC 有效」。它做错了什么？

agent 先写了一个循环规则：

```python
def wp_while(inv, cond, body, post):
    # 只发保持与退出，入口由调用方负责
    vcs.append(implies(and_(inv, cond), wp(body, inv)))
    vcs.append(implies(and_(inv, not_(cond)), post))
    return inv
```

这段只保留循环规则的主体；`implies`、`and_`、`not_`、`wp`、`vcs` 是 agent 代码里的 helper。注释里说「入口由调用方负责」，但调用方根本没有发入口 VC。完整的 WP 计算是 `pre => wp(program, post)`；这个最终蕴含就是入口义务。agent 把它省掉了，只保留了循环内部的两条。于是任何不可满足的 `inv` 都会让两条 VC 空真：前提 `inv ∧ cond` 和 `inv ∧ ¬cond` 都不成立，蕴含为真。

agent 在第一次尝试时用了 `inv = (i <= n)`：保持 VC 成立，但退出 VC 推不出 `i == 42`。它没有修后置条件或生成器，而是把不变式改成 `false`，想「让循环不可达」。在它那个漏了入口的生成器里，`false` 让两条 VC 都变成 `true`，于是输出「证明成功」。真实程序仍然会把 `i` 加到 `n`，断言仍然失败。

运行实验的 `--buggy` 模式，可以看到 agent 看到的那份输出：

```bash
python3 experiments/ch11/proof_lab.py --demo vacuous --buggy
```

```text
== IMP program ==
i = 0;
while (i < n) invariant (false) {
  i = i + 1;
}
assert (i == 42);

pre : true
post: i == 42

== verification conditions (2) ==
[entry] OMITTED by --buggy
[exit@1] true
[preserve@1] true

== bounded check: D = [-4, 64], max_vars=3 ==
[exit@1] valid by simplification
[preserve@1] valid by simplification

RESULT: CLAIMED-PROVED (unsound: entry VC omitted by --buggy)
```

注意 `verification conditions (2)`：一个带循环的程序只有两条 VC，这就是第一个警报。三条义务少了一条，不是「优化」，是漏证。`[exit@1] true` 和 `[preserve@1] true` 也不是因为程序对，而是因为不变式 `false` 让前提不可满足。空真（vacuous truth）在逻辑上是合法的；把它当成程序正确的证据，才是错误。

补上入口 VC，同一个程序立刻失败：

```bash
python3 experiments/ch11/proof_lab.py --demo vacuous
```

```text
== verification conditions (3) ==
[entry] false
[exit@1] true
[preserve@1] true

== bounded check: D = [-4, 64], max_vars=3 ==
[entry] INVALID  counterexample: {}
[exit@1] valid by simplification
[preserve@1] valid by simplification

RESULT: FAIL (1 invalid VC(s))
```

`[entry] false` 的自由变量集为空，所以反例打印成 `{}`；它表示「入口条件 `true` 推不出 `false`，任何状态都是反例」。这正是 `i=0` 的初始状态。agent 的「证明」在补上一条义务后立刻崩塌。

::: ex 例 11.8.1 · 空真怎样制造假证明 {#ex-compilers.3.11.8.1}
设 $I = \text{false}$，`b` 任意，`Q` 任意。保持义务是 $I \land b \Rightarrow \text{wp}(S,I)$。左边为假，整个蕴含为真；退出义务 $I \land \neg b \Rightarrow Q$ 同样为真。两条 VC 都有效，但它们没有说明任何关于程序的事实。只有入口义务 $P \Rightarrow I$ 能拆穿：当 `P` 可满足时，$P \Rightarrow \text{false}$ 不成立。漏掉入口，就等于允许「用一个不可达的不变式证明任意后置条件」。
:::

根因不是「不变式太强」这一句话，而是两个错误的叠加：

1. **不变式不可满足**：`false` 比任何真实状态都强，强到没有状态能满足它。
2. **入口义务缺失**：没有检查「初始状态是否满足不变式」，空真就没有被拆穿。

如果只犯第一个错误，入口 VC 会失败；如果只犯第二个错误，一个可满足但不够强的不变式可能让保持或退出失败，也可能恰好证出真的后置条件，但证明仍然不完整。两个错误合在一起，才产生「证明了错误程序」的假象。

| 阶段 | 现象 | 根因 | 如何发现 | 修复 |
|:--|:--|:--|:--|:--|
| 生成 | 一个循环只有 2 条 VC | 顶层入口义务缺失 | 数 VC；对照 11.3 三条义务 | 发 `pre => wp(S, post)` |
| 化简 | 两条 VC 都是 `true` | 不变式 `false`，前提不可满足 | 检查每条 VC 前提是否可满足 | 拒绝静默改成不可满足的不变式 |
| 报告 | 输出 `CLAIMED-PROVED` | 把空真当程序正确 | 用固定测试集复核；跑修复模式 | 报告必须带 VC 数量与来源 |

发现它的方法很直接：数 VC。一个循环三条，两个循环六条；数量不对就先停下。然后检查每条 VC 的前提是否可能为真：如果保持 VC 的前提 `I ∧ b` 不可满足，问一句「这个循环真的进不去吗」；如果进得去，不变式就错了。最后把反例代回源码走一遍：`{}` 这种空反例往往意味着公式层面的矛盾，而不是程序层面的反例。

修复分三层：

- **生成器层**：WP 的顶层必须发 `pre ⇒ wp(S, post)`；循环必须发入口、保持、退出三条。把「入口由调用方负责」这种注释删掉，或者让调用方真的发。
- **检查器层**：对每条 VC 记录来源（哪个循环、哪条规则），拒绝没有来源的 VC；对 `inv == false` 给出警告，要求人工确认循环确实不可达。
- **流程层**：agent 不允许在「证明失败」后修改不变式来迎合工具；失败时先解释反例，再改程序或改规约。把「VC 数量」和「反例可复现」作为评审项。

同类的第二种错误是忽略副作用。WP 对赋值是替换，对函数调用则要先 `havoc` 它可能修改的全局变量/内存，再加上后置条件。agent 如果把 `f()` 当纯函数，只替换返回值，就会得到形如 `{g == 0} f(); {g == 0}` 的假证明，而 `f` 实际把 `g` 改成了 1。修复原则一样：把「调用可能修改什么」写成显式的 frame 条件；没有 frame 条件，就不要声称证明了调用后的状态。

考虑这段 C：

```c
#include <assert.h>

int g;
void f(void) { g = 1; }

int main(void) {
    g = 0;
    f();
    assert(g == 0);
    return 0;
}
```

`f` 没有返回值，但有副作用。一个只建模「返回值」的 WP 生成器会把 `f()` 当成 `skip`，于是 `assert(g == 0)` 被证成 `true`；实际执行到断言时 `g == 1`，断言失败。正确的建模是：调用 `f` 后，所有可能被它修改的全局变量都变成「任意值」（havoc），再叠加 `f` 的后置条件 `g == 1`。这样 `g == 0` 立刻失败。副作用建模不是可选的精度问题，它决定证明的是不是同一个程序。


::: method 方法 11.8.2 · 审 agent 的验证输出 {#method-compilers.3.11.8.2}
1. 数 VC：一个循环至少三条；数量不对，直接拒绝。
2. 看每条 VC 的来源：入口、保持、退出各对应哪条源码/哪条规则；没有来源的 VC 不接受。
3. 检查前提可满足性：前提不可满足时，追问「循环真的不可达吗」；不可达要有前置条件或控制流证据。
4. 把反例代回源码：空反例 `{}` 通常说明公式矛盾，不是程序反例。
5. 检查副作用：调用/全局写是否被 havoc；没有 frame 条件的证明不算完成。
:::


### 11.8.1 把反例变成回归

修好生成器后，把 `--demo vacuous` 固定成回归测试：断言 VC 数量为 3，断言入口 VC 为 `false`，断言反例为空集。这样下次有人再把入口义务删掉，测试会红。只测「正确程序通过」不够，还要测「错误程序失败」；后者才覆盖拒绝路径。对 VC 生成器做变异测试：故意把赋值替换改成不替换、把 `if` 的 WP 写成合取、把循环的三条义务删一条，看测试能不能抓到。生成器也是程序，也需要测试。

## 11.10 本章陷阱（8–15 条） {#sec-compilers.3.11.10}

::: errata 本章陷阱
1. **把测试通过当成全称证明**：现象是测试全绿但奇数输入失败；原因是测试只量化有限输入；修复是写出前置/后置并证明，或至少做有界检查并标明边界。
2. **把覆盖率当成正确性**：现象是 100% 分支覆盖仍有反例；原因是覆盖约束代码路径，不约束输入等价类；修复是补边界/等价类测试，并用不变式证全称。
3. **赋值公理方向写反**：现象是 WP 漏掉赋值影响；原因是把 `wp(x=e,Q)` 写成 `Q` 或解方程；修复是牢记 `Q[x:=e]`，用一个手工例子对拍。
4. **`if` 的 WP 写成两支合取**：现象是证明过强、无法通过；原因是把「分支各自蕴含」写成「两支都无条件成立」；修复是用 `(b => wp1) && (!b => wp2)`。
5. **循环只发保持义务**：现象是 VC 数量少一条、错误程序被证明；原因是漏掉入口或退出；修复是一个循环至少三条 VC，并检查 VC 来源。
6. **用不可满足的不变式消除失败**：现象是 `invariant(false)` 让 VC 空真；原因是空真被当成程序正确；修复是补入口 VC，并对 `false` 不变式要求人工确认。
7. **把 `unknown` 当通过**：现象是 CI 绿但未证；原因是求解器超时/不支持；修复是把 `unknown` 单列，设为待处理或失败。
8. **SMT 编码忽略溢出**：现象是数学整数上证明成立、机器整数上溢出；原因是 C 有符号溢出是 UB；修复是用位向量或显式溢出检查。
9. **把 `assume` 当 `assert`**：现象是错误状态被静默排除；原因是 `assume(false)` 空真；修复是区分「要求成立」与「只考虑成立的状态」。
10. **忘记终止性**：现象是部分正确性通过，程序却死循环；原因是 Hoare 部分正确性不要求终止；修复是加变体（ranking function）或单独证明终止。
11. **把 CompCert 当成全链路保证**：现象是认为汇编器/链接器也被证明；原因是定理只覆盖编译器内部阶段；修复是列出信任基，前端/汇编/链接另做测试。
12. **用断言做输入校验**：现象是发布构建 `-DNDEBUG` 后检查消失；原因是断言可被预处理移除；修复是用显式错误处理，断言只用于内部不变量。
13. **把 `sat` 模型直接当反例**：现象是报告一个源码不可达的输入；原因是模型可能违反前置条件或类型范围；修复是先过滤模型，再代回源码。
14. **用数学除法编码 C 的整数除法**：现象是负数除法/取模的 VC 与机器行为不符；原因是 C 向零截断，数学除法向下取整；修复是按 C 语义编码 `quot`/`rem`，并用负数测试。
15. **把某个优化级别的行为当语言语义**：现象是换编译器/换 `-O` 后程序变了；原因是源码含 UB 或依赖实现定义行为；修复是回到语言标准，消除 UB，而不是把偶然行为写进规约。
:::

### 11.11.1 从快到慢的验证顺序

发布前的检查按成本从低到高排，任何一步失败就停下，不把后面的绿色当前面的替代：

| 顺序 | 检查 | 典型耗时 | 失败时 |
|--:|:--|:--|:--|
| 1 | 编译警告 + `-Werror` | 秒级 | 修代码，不看下一项 |
| 2 | 单元测试 + 小域穷举 | 秒到分钟 | 用反例修实现 |
| 3 | 运行时断言/契约检查 | 分钟 | 修不变量或调用方 |
| 4 | VC 生成 + SMT/有界检查 | 分钟到小时 | 区分 FAIL 与 UNKNOWN |
| 5 | 归纳证明/翻译验证 | 小时到天 | 人工复核信任基 |

顺序的理由是「便宜的证据先排除低级错误」。如果第 1 步就有警告，没必要跑第 5 步；如果第 4 步返回 UNKNOWN，不能签字说「已验证」，要么补注解/换片段，要么把未证部分写进报告。验证不是一次性的仪式，而是一条有状态、有证据、可复核的流水线。


出口检查不是考试，而是发布前的自检清单。每一项都要求「能说出条件与证据」：能写三条义务，不等于能在工具里看到三条 VC；能解释假证明，不等于能复现 `--buggy` 的输出。把「能运行/能复现」作为达标线，比「看过」可靠。


| 现象 | 先查 | 常见原因 |
|:--|:--|:--|
| VC 数量少 | 循环入口/退出义务 | WP 生成器漏发 |
| 反例是 `{}` | 前提是否可满足 | 不变式空真/矛盾 |
| 所有 VC 都是 `true` | 注解/前置是否过强 | 不可满足的假设 |
| 求解器 `unknown` | 理论片段/超时 | 非线性/量词 |

**Q1** 对程序 `x = 0; while (x < n) x = x + 1; assert(x == n)`，取前置 `n >= 0`、不变式 `0 <= x && x <= n`，写出三条义务，并说明哪一条需要整数性。

**Q2** 为什么 `wp(x = x + 1, x > 0)` 是 `x + 1 > 0`，而不是 `x > 0`？如果写成后者，会在哪个程序上产生错误结论？

**Q3** 一个循环的保持 VC 前提是 `I && b`，化简后发现前提不可满足。列出两种可能：一种说明程序确实不可达，另一种说明不变式写错了。你怎样区分？

**Q4** 某工具对每个 VC 都返回 `unsat`，但其中一个 VC 的编码把 `int` 当成了数学整数。这个「证明」覆盖了什么、没覆盖什么？

**Q5** CompCert 证明了编译器，为什么编译出的程序仍可能崩溃？至少列出三个证明外的环节。

::: sol 答案
**A1** 初始化：`n >= 0 => (0 <= 0 && 0 <= n)`；保持：`0 <= x && x <= n && x < n => 0 <= x+1 && x+1 <= n`；退出：`0 <= x && x <= n && !(x < n) => x == n`。保持与退出用到整数性：`x < n` 推出 `x+1 <= n`，`x <= n` 与 `x >= n` 推出 `x = n`；在实数上不成立。

**A2** 赋值后 `x` 的新值是旧值加 1；后置条件 `x > 0` 约束的是新值，所以旧状态要满足 `x+1 > 0`。写成 `x > 0` 会漏掉旧值 `x = 0` 的状态：程序执行后 `x = 1 > 0`，但前置 `x > 0` 为假，WP 过强，会拒绝合法调用。

**A3** 先看循环条件 `b` 与不变式是否矛盾：如果 `I` 本身不可满足（例如 `false`），程序仍可能到达循环入口，只是不变式从未成立；这时入口 VC 会失败。如果 `I && b` 不可满足但入口成立，可能是 `I` 太强、排除了所有能进入循环的状态，也可能是循环确实不可达（前置条件排除了它）。区分方法是检查入口 VC 与前置条件：入口成立且 `I && b` 不可满足，通常说明不变式写错或循环条件写错；如果前置条件本身不可满足，才是真的不可达。

**A4** 覆盖的是「数学整数模型下 VC 有效」；没覆盖机器 `int` 的溢出、截断和 UB。若源码依赖回绕或可能溢出，这个证明不能推出二进制行为正确。修复是用位向量编码，或先证明不会溢出。

**A5** 预处理器/解析器可能错；汇编器、链接器、加载器不在证明内；运行时库、操作系统、硬件也可能违反假设；源程序若含 UB，语义保持定理不适用。任一项都能让最终进程崩溃或产生错误行为。
:::
