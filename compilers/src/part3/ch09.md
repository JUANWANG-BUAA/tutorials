第 8 章把调用约定、栈帧和代码生成拆到了指令级。那些规则默认程序本身是合法的：只要 ABI 对齐、寄存器宽度和内存布局正确，生成代码就应当与源程序同义。这一章换一个方向问：如果源程序根本不合法，编译器还欠你什么？

答案比多数人想的更冷。C 标准只约束「可观察行为」，而可观察行为只对没有未定义行为（undefined behavior，UB）的执行成立。一旦某条执行路径踩到 UB，标准不再规定这次运行的结果，优化器可以假设这条路径不存在，于是它后面的检查、分支、甚至整个函数都可能被改写。你在源码里写 `if (p) *p = 1;` 并不构成一道防线，如果前面已经有一次 `p->field`，编译器完全可以把 `if (p)` 删掉。

先看一个能跑的反例。`experiments/ch09/ub_lab.c` 里有一个 `guarded_load`：先读 `p->value`，再判断 `p != NULL`。在 `-O2` 下，x86-64 的目标码只剩一条 `movl (%rdi), %eax`，比较和分支消失；传 `NULL` 进去直接段错误。同一份源码在 `-O0` 下保留了 `cmpq $0` 和 `je`，但那条读操作仍在检查之前。两种优化级别都救不了这个函数，差别只在于「检查是否还存在」。

这一章的主线是证据链，而不是工具清单。先定义抽象机器与可观察行为（9.1），再区分未定义、未指定、实现定义（9.2），把常见 UB 归类到优化器会利用的假设上（9.3）。然后看 sanitizer 插了什么、漏什么（9.4），静态分析怎样用抽象解释和符号执行逼近不可判定问题（9.5、9.6），最后落到 CI 矩阵与抑制（9.7），并用一个 agent 生成代码的案例把前面的机制串起来（9.8）。

本章实验入口是 `experiments/ch09/run.sh`。它在本机编译并运行 UBSan、ASan、TSan 用例，生成 x86-64 反汇编，再跑一个区间抽象解释器。下文引用的 sanitizer 输出都来自这次运行；地址与 PID 由脚本归一化为 `0xADDR`、`PID`。

## 9.1 UB 是什么：可观察行为与抽象机器 {#sec-compilers.3.9.1}

C 程序不是直接在寄存器上执行的。标准定义了一台抽象机器（abstract machine），程序是对这台机器的指令序列；实现（编译器加运行时）必须让合法程序的可观察行为与抽象机器一致。可观察行为在 C17 5.1.2.3 中列得很窄：文件与交互设备的输入输出、以及 `volatile` 访问的顺序。内存里的中间值、寄存器分配、求值顺序都不在保证范围内。

这条「as-if」规则是优化的全部空间。只要最终的可观察行为不变，编译器可以重排、删除、合并任何计算。`x * 2` 可以变成 `x + x`，循环可以展开，函数可以内联。问题在于：当程序有 UB 时，「可观察行为」这个前提不成立，as-if 规则失去约束对象。

::: def 定义 9.1.1 · 未定义行为 {#def-compilers.3.9.1.1}
C17 3.4.3 把未定义行为定义为：本国际标准没有对其施加任何要求的行为。它可能被翻译期诊断，也可能不被诊断；可能产生任意结果，也可能在翻译期或运行期以任意方式终止。标准明确写了「possible undefined behavior ranges from ignoring the situation completely with unpredictable results, to behaving during translation or program execution in a documented manner characteristic of the environment, to terminating a translation or execution」。

关键在「没有施加任何要求」：不是「结果不确定但仍在某个集合内」，而是连集合都没有。对一次踩到 UB 的执行，实现可以做任何事，包括让时间旅行式的优化成立——假设这条执行不会发生。
:::

把这句话落到优化器上，就得到一条可操作的推理规则。

::: thm 定理 9.1.2 · UB 的路径删除许可 {#thm-compilers.3.9.1.2}
设程序 P 的某条执行路径 e 在抽象机器上触发 UB。若编译器把 e 视为不可达，并从所有路径中删除它，则对 P 的**合法执行**，生成代码的可观察行为不变。

证明要点：as-if 规则只要求「所有合法执行」的可观察行为一致。e 不合法，因此 e 上发生什么不在义务范围内。删除 e 不会改变任何合法执行；反过来，利用 e 不可达推出的事实（例如「e 之前的解引用意味着指针非空」）也只影响 e 或与 e 共享该事实的路径。条件是：编译器对「合法执行」的定义必须与标准一致；如果编译器错误地把合法执行判成 UB，这条许可就被滥用，变成编译器 bug。
:::

定理的措辞很小心：它许可的是「删除 UB 路径」，不是「任意改变合法路径」。现实中的争议几乎都落在第二句的条件上：编译器是否错误地扩大了 UB 的范围。例如把 `-fwrapv` 之外的补码回绕当成可假设不溢出，是标准允许的；把有符号比较 `x + 1 > x` 直接折成 `true`，也是同一假设的推论，因为溢出会使该执行 UB。

::: ex 例 9.1.3 · 一条加法怎样变成常量 {#ex-compilers.3.9.1.3}
函数 `int f(int x) { return x + 1 > x; }` 在 C 抽象机器上对多数 `x` 返回 1，但当 `x == INT_MAX` 时 `x + 1` 溢出，是 UB。编译器因此可以假设 `x != INT_MAX`，于是 `x + 1 > x` 恒真。用 Clang 生成 LLVM IR 能看到 `add nsw`：`nsw` 是 no signed wrap，正是「溢出即 UB」的机器可读形式。

```bash
printf 'int f(int x) { return x + 1 > x; }\n' > /tmp/add.c
clang -std=c17 -O0 -S -emit-llvm -o - /tmp/add.c | sed -n '/define/,/}/p'
```

```text
define i32 @f(i32 noundef %0) #0 {
  %2 = alloca i32, align 4
  store i32 %0, ptr %2, align 4
  %3 = load i32, ptr %2, align 4
  %4 = add nsw i32 %3, 1
  %5 = load i32, ptr %2, align 4
  %6 = icmp sgt i32 %4, %5
  %7 = zext i1 %6 to i32
  ret i32 %7
}
```

`-O0` 仍保留比较，因为前端只负责打标记；到 `-O2`，`InstCombine` 依据 `nsw` 把比较折成常量，本机函数体只剩一条 `ret i32 1`。这段 IR 是 E2 级证据：本机 Clang 22 的实际输出。换编译器或换版本，标记与折叠时机可能不同，但语义依据相同。
:::

这里有一个容易混淆的点：UB 是「执行」的属性，不是「程序」的属性。同一个程序，输入 `1` 时一切正常，输入 `INT_MAX` 时踩 UB。编译器不能因为程序「可能」有 UB 就拒绝编译；它只在能证明某条路径必然 UB 时才删除该路径（或者更常见：在假设「本路径无 UB」的前提下推导事实）。所以「这个函数有 UB」通常应说成「这个函数在哪些输入/路径上有 UB」。

| 概念 | 谁定义 | 典型例子 | 能否依赖 |
|:--|:--|:--|:--|
| 可观察行为 | C17 5.1.2.3 | 文件输出、`volatile` 访问顺序 | 可以 |
| 未定义行为 | C17 3.4.3 | 有符号溢出、越界解引用 | 不可以 |
| 未指定行为 | C17 3.4.4 | 函数实参求值顺序 | 不可移植，但结果仍有定义 |
| 实现定义行为 | C17 3.4.1 | `char` 是否有符号、右移负数 | 实现必须文档化 |

再强调一次边界的形状。编译器不需要诊断 UB，也不需要让 UB 在运行时「表现出一致的结果」。你可以用 `-fsanitize=undefined` 把一部分 UB 变成运行时报告，但那是工具的额外契约，不是语言契约。工具没报，只说明这次执行没有被插桩捕获，不说明程序合法。

<pre class="layout">
C 源程序
   │  前端：语法/类型检查，给运算打假设标记
   │        add nsw / getelementptr inbounds / load !nonnull
   ▼
LLVM IR（仍带 UB 假设）
   ├──────────────► 优化器：常量折叠、删除死分支、提升负载
   │                  依据：本路径不得触发 UB
   ▼
机器码 ──► 运行：合法输入得到可观察行为；UB 输入无契约
   │
   └──────────────► sanitizer 插桩：在运算前加检查
                      命中则报告；未命中不等于合法
</pre>

读图：同一份 IR 有两条消费路径。优化器把 UB 假设当作事实来删代码；sanitizer 则把一部分假设变成运行时检查。两条路径互不替代——优化器删掉的检查，sanitizer 也未必能补回来，因为插桩发生在前端之后、优化之前，后续 pass 仍可能依据 UB 删除整段代码。

### 从假设到变换：三个常见模式

把「UB 路径可删除」落到具体优化，能看到三种反复出现的模式。它们都不需要编译器「知道」程序会崩；只需要证明某条路径上的某个操作一旦发生就违反语言契约。

| 变换 | 源码模式 | 依赖的假设 | 假设不成立时 |
|:--|:--|:--|:--|
| 删除空检查 | 先 `p->x`，后 `if (p)` | 解引用过的指针非空 | 空指针输入直接崩溃 |
| 折叠比较 | `x + 1 > x` | 有符号加法不溢出 | `INT_MAX` 输入结果错误 |
| 提升边界检查 | 循环内 `a[i]`，`i < n` | `i` 不溢出、数组不越界 | 边界输入越界 |
| 删除冗余初始化 | `int x; if (c) x = 1; use(x)` | 未初始化读不发生 | 未初始化值被使用 |
| 识别 `memcpy` 为移动 | 手写逐字节拷贝 | 源和目标不重叠 | 重叠拷贝结果错误 |

第一种模式最容易被误读成「编译器在针对空指针」。实际上编译器只是在做常量传播：`p->x` 生成一个 `load`，`load` 的地址操作数在 LLVM 里可以带 `!nonnull` 元数据；前端从「解引用」这个动作推出非空，后续比较就被折叠。换成 `p[0]`、`*p`、`p->next` 都一样，因为都要求 `p` 指向一个对象。

第三种模式解释了为什么「循环边界检查」在优化后可能消失。若 `i` 是 `int`，`i < n` 且 `n` 是 `int`，编译器可以假设 `i++` 不溢出；当 `n == INT_MAX` 时，循环变量最终会溢出，这条执行本来就是 UB，删除边界检查是合法的。想让循环在 `INT_MAX` 附近也有定义行为，应把索引改成 `size_t`（无符号回绕有定义），或在循环条件里显式防止溢出。

::: note 关于「时间旅行」的准确说法
坊间常说 UB 会「时间旅行到 printf 之前」。更准确的说法是：可观察行为的保证只对合法执行成立；对含 UB 的执行，编译器没有义务保持 `printf` 与 UB 的相对顺序，也没有义务让 `printf` 发生。实际编译器很少主动做跨 I/O 的重排，但你不能用「我加了 printf，所以 UB 之前的输出一定在」来推理。调试 UB 时，日志本身也可能被优化影响。
:::

这也解释了一个工程现象：在 `-O0` 下加 `printf` 能把 bug「修好」，在 `-O2` 下又出现。`printf` 改变了内联、寄存器分配和代码布局，可能让越界写到无害位置，也可能让优化器放弃某个变换。它没有改变 UB 的性质，只是改变了这一次运行的表现。

### 诊断不是义务，证据要自己造

C 标准不要求实现对 UB 给出诊断。编译器可以完全接受一段必然越界的代码，生成一段必然崩溃的目标码，并在文档里保持沉默。`-Wall -Wextra` 打开的是「实现愿意做的检查」，不是「标准要求的检查」。`-Wuninitialized` 依赖数据流，`-Warray-bounds` 依赖常量传播，二者都可能因为优化级别、内联深度或指针别名而时有时无。

这带来一个评审上的陷阱：代码在开了 `-Werror` 的 CI 里通过，只能说明「这组警告没有触发」，不能说明「没有 UB」。要造证据，得主动做三件事：

1. 在 `-O0` 与 `-O2` 各编译一次，比较反汇编中关键检查是否还在。
2. 在 `-O1` 跑 UBSan+ASan，在 `-O2` 再跑一次 ASan；两者都失败才算稳定复现。
3. 对可疑函数写一个最小驱动，用边界值（0、-1、INT_MAX、NULL）各跑一次，并保存报告。

| 证据 | 能证明 | 不能证明 |
|:--|:--|:--|
| `-Werror` 通过 | 这组警告未触发 | 程序无 UB |
| UBSan 报告 | 该次执行踩到被插桩的 UB | 其他输入/路径也安全 |
| ASan 报告 | 该次访问越界/UAF | 未插桩库、对象内越界 |
| `-O2` 反汇编无 `cmp` | 该检查被优化删除 | 删除一定是错的（可能路径确实不可达） |
| 静态分析 no warning | 该工具没找到 | 程序正确 |

把这张表放在 review 模板里，能挡住「CI 绿了所以没问题」这类结论。真正的结论应该写成「在 clang 22、`-O2`、输入 `INT_MAX` 下 UBSan 报告有符号溢出，已复现；修复后用同一命令验证通过」，带上版本、命令、输入和输出。

### UB 的「传染性」

UB 不是只影响出错的那一条指令。只要某条路径上存在 UB，编译器就可以把整条路径视为不可达，路径上位于 UB 之前或之后的检查都可能被删除。这意味着「在出错点之后加防御」通常无效，而「在出错点之前加检查」才可能改变控制流。

更隐蔽的是跨函数传染：内联之后，被调用函数里的 UB 假设会进入调用者的优化上下文。一个 `static inline` 的 `get(p)` 如果先解引用 `p`，调用者里的 `if (p)` 也可能被删。判断一个检查是否有效，不能只看当前函数，还要看它是否在第一次解引用之前、以及内联后是否仍然在前。

### 未定义值与不确定值

C 里还有一类常被忽略的状态：对象有存储但值不确定（indeterminate）。读一个未初始化的 `int` 可能得到任意值，甚至可能是陷阱表示（对某些类型）；对 `unsigned char` 读未初始化值是允许的，但值仍不确定。MSan 抓的是「未初始化值影响了可观察行为」，而不是「读未初始化」本身。把 `malloc` 得到的内存当已初始化使用，是 C 代码里最常见的未初始化 bug；`calloc` 或显式 `memset` 才是正确起点。

### 优化器的证明义务

优化器不需要向用户证明某个变换是对的；它只需要在自己的语义模型里成立。LLVM 的 `nsw`、`nuw`、`inbounds`、`!nonnull` 都是「前端承诺 + 优化器消费」的接口。前端在生成这些标记时，依据的是语言标准；优化器在消费时，不再检查源程序是否真的满足。这个分工让编译很快，也让「前端标错」变成整条链路的 silent bug。

因此，排查 UB 相关问题时，不要只盯着优化 pass。先确认前端为什么打了某个标记：源码里是否有解引用、是否有有符号加法、是否用了 `inbounds` 的 GEP。如果标记本身错了，禁用某个优化只是掩盖症状；如果标记是对的，源码就是 UB，必须改源码。

## 9.2 未定义、未指定与实现定义 {#sec-compilers.3.9.2}

三个词经常被混用，但它们的工程后果完全不同。未定义行为是「没有要求」；未指定行为是「标准给了若干允许结果，实现每次可以选一个，但不必文档化」；实现定义行为是「实现必须选一个并写进文档」。三者都可能让代码不可移植，但只有 UB 允许编译器做任意变换。

::: def 定义 9.2.1 · 三类行为的判别 {#def-compilers.3.9.2.1}
给定一个语言构造，问三个问题：

1. 标准是否规定了所有合法结果？若是，它是**已定义**的。
2. 标准是否允许一组结果、但不要求实现说明选哪个？若是，它是**未指定**的（unspecified）。
3. 标准是否要求实现选一个并在文档中说明？若是，它是**实现定义**的（implementation-defined）。
4. 以上都不是，标准对该构造没有任何要求？它是**未定义**的。

判别顺序不能颠倒。比如「`int` 的宽度」是实现定义的（`sizeof(int)` 可以是 2、4、8），但「`int` 溢出」是未定义的；「函数实参的求值顺序」是未指定的，但「同一标量在两个未序列化点上被修改两次」是未定义的。
:::

先看未指定。C17 6.5p3 规定：运算符的操作数求值顺序、函数调用的实参求值顺序、赋值表达式的左右操作数求值顺序，都是未指定的。下面的程序没有 UB，但 `f()` 与 `g()` 谁先执行不确定：

```c
#include <stdio.h>

static int calls;

static int f(void)
{
    calls++;
    return calls;
}

static int g(void)
{
    calls++;
    return calls * 10;
}

int main(void)
{
    int r = f() + g();
    printf("%d %d\n", r, calls);
    return 0;
}
```

这段代码在合法程序范围内，但结果依赖求值顺序：先 `f` 后 `g` 得 21，先 `g` 后 `f` 得 12（`calls` 的读也参与其中，具体值还依赖读的时机）。如果业务需要确定顺序，应拆成两条语句，而不是靠括号。编译器不会为未指定行为给出诊断，因为它没有违反标准。

再看实现定义。`char` 是否有符号是最常见的例子。C17 6.2.5p15 说 `char`、`signed char`、`unsigned char` 是三种不同的类型，`char` 是否与 `signed char` 同表示由实现定义。下面的程序本身合法：

```c
#include <stdio.h>

int main(void)
{
    char c = (char)255;
    int shifted = -1 >> 1;
    printf("char255=%d shift=%d sizeof_int=%zu\n", c, shifted, sizeof(int));
    return 0;
}
```

在本机（Apple clang 22，arm64 macOS）上，默认 `char` 有符号，输出 `char255=-1 shift=-1 sizeof_int=4`；加上 `-funsigned-char` 后同一行变成 `char255=255 shift=-1 sizeof_int=4`。右移负数是实现定义（算术右移或逻辑右移），本机选算术右移。把这两个值写进跨平台协议，就是把实现细节当成了语言保证。

最后看 UB。C17 6.5p2 规定：如果对一个标量的副作用相对于同一标量上的另一个副作用或值计算是未序列化的，行为未定义。经典错误是：

```text
int i = 1;
i = i++ + 1;   /* UB：i 的读与写在赋值序列中未排序 */
```

很多旧教材说「结果是 3 或 4，取决于编译器」，这是错的。标准没有给结果集合；编译器可以把它折成任意值，也可以直接删掉这段。类似地，`a[i++] = i;` 也是 UB。若需要旧值，应写 `int old = i; i = old + 1;`。

::: ex 例 9.2.2 · 三个程序，三种命运 {#ex-compilers.3.9.2.2}
考虑三行代码：

```text
x = f() + g();          // 未指定：f/g 顺序不定，但程序合法
char c = (char)255;     // 实现定义：结果由实现文档规定
i = i++ + 1;            // 未定义：无任何保证
```

第一行可以在不同编译器上输出不同结果，但你仍可依赖「两个函数都会被调用一次」。第二行可以依赖「实现会一致地选择有符号或无符号」，前提是你读了该实现的文档；C23 起 `char` 的符号性仍由实现定义。第三行连「两个操作数都会被求值」都不能依赖；如果 `f()` 有副作用，优化器可以在它认为无用的路径上删掉调用。

这张对照的价值在于选工具：未指定行为靠「拆语句 + 固定顺序」消除；实现定义行为靠 `static_assert`、`<limits.h>`、构建矩阵覆盖；未定义行为只能靠「不写」加 sanitizer/分析器兜底，不能靠运行时观察。
:::

C23 对有符号整数表示做了补码强制，但没有把有符号溢出变成定义行为；`INT_MAX + 1` 仍是 UB。C++ 的规则更细：C++26 引入「erroneous behavior」用于一部分原本 UB 的场景，但核心的越界、空指针解引用、有符号溢出仍是 UB。不要因为「新标准修了一点」就推断整类行为都变合法。

### 把实现定义变成构建期检查

实现定义行为不是「不可知」，而是「必须查文档 + 在构建期固定」。对本机这几个值，可以直接测出来：

| 表达式 | 本机值 | 标准是否保证 |
|:--|--:|:--|
| `sizeof(int)` | 4 | 不保证，只保证至少 16 位 |
| `sizeof(long)` | 8 | 不保证，LP64 与 LLP64 不同 |
| `sizeof(void *)` | 8 | 不保证 |
| `CHAR_BIT` | 8 | 不保证，但绝大多数平台是 8 |
| `INT_MAX` | 2147483647 | 不保证，取决于 `int` 宽度 |

不要在代码里写 `int` 一定是 32 位。需要固定宽度时用 `<stdint.h>` 的 `int32_t`/`uint32_t`；需要「至少 32 位」时用 `int_least32_t`。需要编译期断言时，C11 的 `_Static_assert` 比 `#if INT_MAX == ...` 更直接：

```c
#include <limits.h>
#include <stdint.h>

_Static_assert(sizeof(int32_t) == 4, "int32_t must be 4 bytes");
_Static_assert(CHAR_BIT == 8, "this code assumes 8-bit bytes");
_Static_assert(INT_MAX >= 2147483647, "int too narrow for protocol");
```

还有一类「看起来像实现定义、其实是 UB」的构造：`INT_MIN / -1`。C17 6.5.5p6 规定，如果商不能用结果类型表示，行为未定义；在 32 位补码上 `INT_MIN / -1` 的数学结果是 `INT_MAX + 1`，不可表示。类似地，`INT_MIN % -1` 也可能触发 UB。不要用「先取绝对值再除」绕开，`abs(INT_MIN)` 本身就是 UB。

把三类行为写成检查清单，评审时能少吵很多架：

1. 这段代码是否依赖某个「实现会怎么选」的值？若是，改成固定宽度类型或加 `_Static_assert`。
2. 这段代码是否依赖两个副作用之间的顺序？若是，拆成两条语句。
3. 这段代码是否可能在某个输入上越界、溢出、解引用空指针或读未初始化值？若是，先修代码，再谈 sanitizer。

C23 把有符号整数强制为补码表示，并调整了部分移位与转换的措辞，但没有把有符号溢出变成定义行为。把代码从 C17 迁到 C23 时，不要假设「补码强制」等于「溢出回绕」；需要回绕就显式用无符号类型。另一个容易忽略的变化是 `NULL` 的定义与 `nullptr` 的引入（C23），它们不改变空指针解引用的 UB 性质。

### 需要顺序时怎么写

不要用「加括号」试图固定求值顺序。C 的括号只改变结合性，不改变求值顺序；`(f() + g())` 仍然是未指定。需要顺序时，拆成两条语句并引入临时变量：

```text
int a = f();
int b = g();
int r = a + b;
```

如果两个调用有副作用且顺序重要，这个改写是唯一可移植的做法。若顺序不重要但结果要可复现，仍然建议拆开，因为不同编译器/优化级别可能选择不同顺序，测试快照会不稳定。

### 指针来源与 `inbounds`

LLVM 的 `getelementptr inbounds` 表示「结果仍在同一对象内（或 one-past）」。如果源码做了 `p + n` 但 `n` 让指针越出对象，前端可能仍然生成 `inbounds`，优化器据此假设不越界，进而删除边界检查。C 的指针算术规则（6.5.6p8）本来就禁止越界，所以这不是优化器擅自加码，而是源码先违约。把指针运算限制在对象内，是让 `inbounds` 成立的前提。

## 9.3 常见 UB 分类：溢出、移位、别名、生命周期 {#sec-compilers.3.9.3}

工程上最有用的分类不是按标准条款，而是按「优化器会从这条 UB 推出什么假设」。下表把常见类别、假设和能抓它的工具放在一起。表中「ASan」指 AddressSanitizer，「UBSan」指 UndefinedBehaviorSanitizer；工具细节在 9.4。

| 类别 | 标准位置（C17） | 优化器可用的假设 | 典型检测 |
|:--|:--|:--|:--|
| 有符号溢出 | 6.5p5 | 加法/乘法不溢出，可做代数化简 | UBSan |
| 非法移位 | 6.5.7p3–p4 | 移位量小于位宽、左移不溢出 | UBSan |
| 数组/指针越界 | 6.5.6p8 | 指针始终指向对象或 one-past | ASan（堆/栈/全局） |
| 严格别名 | 6.5p7 | 不同类型的指针不指向同一对象 | 无直接 sanitizer，靠优化差异/审查 |
| 生命周期结束 | 7.22.3 | 释放后的对象不再被访问 | ASan |
| 未初始化读 | 6.7.9p10 | 未初始化值不参与可观察行为 | MSan |
| 空指针解引用 | 6.5.3.2p4 | 解引用过的指针非空 | UBSan/ASan |
| 除零 | 6.5.5p5 | 除数非零 | UBSan |
| 数据竞争 | 5.1.2.4p25 | 无同步的冲突访问不并存 | TSan |

有符号溢出值得单独拆开。无符号运算在 C 中是模 2 的 N 次方的，定义明确；有符号溢出不是。`x + 1 > x` 的折叠、`x * 2 / 2 == x` 的化简、循环归纳变量 `i < n` 的边界推导，都依赖「不溢出」。如果你确实想要回绕，标准 C 没有可移植写法；GCC/Clang 的 `-fwrapv` 是扩展，代价是放弃这类优化，而且它不能修复已经写错的库代码。

移位有两层。第一层是移位量：`x << 32` 对 32 位 `int` 是 UB，`x << -1` 也是 UB。第二层是左移的值：C17 6.5.7p4 要求左移结果能用结果类型表示，否则 UB；对有符号正数 `2 << 31` 就越界。右移负数是实现定义，不是 UB，但不同目标可能给出算术或逻辑结果。下面的程序在 `-fsanitize=undefined` 下会报左移溢出：

```c
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char **argv)
{
    int x = argc > 1 ? atoi(argv[1]) : 1;
    int s = argc > 2 ? atoi(argv[2]) : 31;
    printf("%d\n", x << s);
    return 0;
}
```

本机在实验目录运行 `./build/ub_ubsan shift 2 31`（由 `run.sh` 生成）在 UBSan 下输出 `left shift of 2 by 31 places cannot be represented in type 'int'`，退出码 134（`-fno-sanitize-recover=all`）。

指针越界的边界常被误解。C17 6.5.6p8 允许指向数组最后一个元素之后一个位置的指针（one-past-the-end），但**不允许解引用**它，也不允许再往前/往后走一步，即使不读内存。`int *end = a + 4;` 合法；`int *bad = a + 5;` 本身就是 UB；`*end` 也是 UB。ASan 对 `a + 4` 的计算通常不报，因为地址算术没有内存访问；`*end` 才会触发报告。这意味着「指针算出来了但没解引用」也可能是 UB，静态分析器对这类代码的告警往往不是误报。

严格别名（strict aliasing）是另一个高频争议点。C17 6.5p7 规定：对象的存储值只能由兼容类型的左值、字符类型左值或 `memcpy` 访问。把 `float` 对象的地址转成 `int *` 再解引用，违反有效类型规则，是 UB。下面的写法是错的：

```c
#include <stdio.h>

int main(void)
{
    float f = 1.0f;
    int *ip = (int *)&f;
    int bits = *ip;          /* UB：通过不兼容类型的左值访问 */
    printf("%d\n", bits);
    return 0;
}
```

正确做法是用 `memcpy`（编译器会把它优化成一条移动指令）或 `unsigned char` 逐字节观察：

```c
#include <stdio.h>
#include <string.h>

int main(void)
{
    float f = 1.0f;
    unsigned int bits;
    memcpy(&bits, &f, sizeof bits);
    printf("%08x\n", bits);
    return 0;
}
```

`memcpy` 版本在本机输出 `3f800000`，且没有别名 UB。不要把「在我的机器上跑出了期望值」当成别名规则不成立；优化器是否利用别名假设取决于上下文，失败往往只在 `-O2` 加内联后出现。

生命周期类 UB 包括：`free` 后继续用指针、`realloc` 后继续用旧指针、返回局部数组地址、在对象生命周期开始前写入。C 的对象生命周期在 7.22.3 中描述；`free` 结束分配对象的生命周期。`experiments/ch09/ub_lab.c` 的 `uaf` 用例在 ASan 下给出 `heap-use-after-free`，并同时打印释放栈和分配栈；没有 ASan 时它可能打印旧值，也可能崩溃，这正是「没有契约」的表现。

最后是数据竞争。C11 5.1.2.4p25 把冲突的、非原子的、无 happens-before 关系的访问定义为 UB。两个线程同时对 `shared_counter++` 就是典型。这里没有「读到旧值也算合法」的说法；TSan 报告的是 `data race`，不是「结果可能不对」。修复要么加锁，要么用原子类型；`volatile` 不是同步。

### 转换、提升与「看起来无害」的溢出

整数转换是 UB 的另一个入口，而且比加法隐蔽。C 的整数提升会把 `char`、`short` 提升到 `int` 再运算；如果两个 `unsigned short` 相乘，结果按 `int` 计算，可能溢出（`int` 装不下），也可能不溢出，取决于宽度。下面的表达式在 16 位 `int` 上是 UB，在 32 位 `int` 上是定义的：

```c
unsigned int mul(unsigned short a, unsigned short b)
{
    return a * b;   /* 先提升为 int，再乘；结果可能超出 int */
}
```

在 32 位 `int` 平台上，`65535 * 65535 = 4294836225` 超过 `INT_MAX`，但两个操作数都是 `int`，所以这是有符号溢出，UB。很多代码以为「无符号乘无符号一定回绕」，忽略了提升。修复是显式转换：`(unsigned int)a * (unsigned int)b`，此时按模 2^32 回绕，定义明确。

有符号到无符号的转换是定义的（模 2^N），无符号到有符号的转换在值不可表示时是实现定义或抛出信号（C17 6.3.1.3p3）。`int x = (int)UINT_MAX;` 在补码平台上通常是 -1，但标准不保证；不要用它做位模式传输，用 `memcpy` 或 `uint32_t`。

`-Wconversion` 能抓一部分隐式窄化，但它不是 UB 检测器：它报的是「可能丢信息」，而 UB 是「行为没有定义」。两者有交集，但不能互相替代。把 `-Wconversion` 打开的项目，往往要处理大量无害的 `int` 到 `size_t` 转换；更实际的做法是把边界上的类型统一，而不是逐行加 cast。

### 别名、restrict 与有效类型

严格别名不是「编译器故意找茬」，而是类型系统给优化器的承诺：不同类型的指针不会指向同一对象，于是编译器可以分别缓存、重排、向量化。C 的 `restrict` 把同类承诺显式化：

```c
void vadd(int n, int *restrict a, int *restrict b, int *restrict c)
{
    for (int i = 0; i < n; i++) {
        c[i] = a[i] + b[i];
    }
}
```

`restrict` 的语义是：在 `a`、`b`、`c` 各自被使用的块内，通过它们访问的对象不与其他 `restrict` 指针访问的对象重叠。调用 `vadd(n, x, y, x)` 让 `a` 与 `c` 指向同一数组，就是违反契约，UB。编译器可以据此把 `a[i]` 提到循环外、把写 `c[i]` 与读 `a[i]` 重排。`restrict` 不会在运行时检查，也没有诊断；它是一份你签给编译器的合同。

`memcpy` 的重叠也是 UB（C17 7.24.2.1）。`memcpy(dst, src, n)` 要求区域不重叠；重叠时用 `memmove`。很多实现会在小拷贝时把 `memcpy` 展开成前后向逐字节循环，重叠时「碰巧」正确，但这不代表合法。换成大拷贝或不同目标，结果就变。

C 的 `union` 类型双关是合法的（C11 6.5.2.3 的脚注明确允许读取与写入不同的成员，结果为实现定义），但 C++ 不允许用 `union` 做类型双关。跨语言头文件里用 `union` 传 `float`/`int` 的写法，在 C 侧可接受，在 C++ 侧应改用 `memcpy`。这只是别名规则的一个分支，不要把它推广成「所有双关都合法」。

| 操作 | 是否定义 | 备注 |
|:--|:--|:--|
| 无符号加法溢出 | 定义（模 2^N） | 可以用来做哈希 |
| 有符号加法溢出 | UB | 用 `__builtin_add_overflow` 显式检查 |
| 左移进入符号位 | UB（若结果不可表示） | 用无符号类型做位运算 |
| 右移负数 | 实现定义 | 不要依赖算术/逻辑 |
| 指向 one-past 的指针 | 定义（不可解引用） | `a + n` 合法，`*(a+n)` 不合法 |
| `free` 后读 | UB | ASan 可抓 |
| `memcpy` 重叠 | UB | 用 `memmove` |
| `restrict` 指针重叠 | UB | 合同违约，无运行时诊断 |

「为什么 `-O2` 才出问题」的答案通常在这里：低优化级别下，编译器按语句逐条生成，别名假设没有机会发挥作用；高优化级别下，内联、循环提升、向量化把假设变成实际重排，错误才显形。把 `-O2` 的失败当成「优化器 bug」之前，先用本章的分类表确认源码是否已经违约。

### `volatile` 不是 UB 的解药

`volatile` 告诉编译器「这个访问有副作用，不要删除或合并」，但它不提供原子性、不建立 happens-before、也不让越界变得合法。用 `volatile` 修饰共享计数器不能消除数据竞争；用 `volatile` 修饰越界指针不能消除越界 UB。它唯一的语义是「按抽象机器的规则执行这个访问」，而访问本身的合法性仍由数组边界、对象生命周期和别名规则决定。

「越界写为什么有时不崩」也值得解释。普通分配器按块管理内存，`malloc(16)` 可能实际给出 24 或 32 字节的可用块；越界 4 字节仍落在块内，于是写成功、读回也成功。ASan 把可用区域精确到 16 字节并在两侧放红区，才让同一行代码稳定报错。不要用「没崩」推断「没越界」，也不要用「换了分配器就崩」推断「代码以前是对的」。

### `realloc` 与指针失效

`realloc` 可能原地扩展，也可能搬到新地址并释放旧块。无论哪种，旧指针在 `realloc` 返回后都不应再被解引用；如果搬了，旧指针指向已释放内存（UAF），如果没搬，旧指针与新指针指向同一对象但生命周期由新块决定。正确写法是先保存返回值到临时变量，成功后再覆盖原指针：

```c
#include <stdlib.h>

int *grow(int *p, size_t n)
{
    int *tmp = realloc(p, n * sizeof *p);
    if (tmp == NULL) {
        return NULL;   /* p 仍然有效，由调用者释放 */
    }
    return tmp;
}
```

直接写 `p = realloc(p, ...)` 在失败时丢掉原指针，造成泄漏；在成功但搬家时，其他别名仍然悬空。ASan 能抓后一种，抓不到泄漏（除非开 LeakSanitizer）。这也是「生命周期 UB」常与资源管理 bug 混在一起的原因。

## 9.4 sanitizer：ASan/UBSan/TSan/MSan 的原理与局限 {#sec-compilers.3.9.4}

sanitizer 是编译器插桩加运行时库的组合。它们把一部分 UB 变成「运行到这里就报告」，代价是代码体积、内存和速度。理解插桩位置，才能理解报告为什么有时缺席。

::: def 定义 9.4.1 · 插桩与影子内存 {#def-compilers.3.9.4.1}
插桩（instrumentation）是在 IR 或机器码中插入额外检查，使程序在接近出错点时主动调用运行时报告函数。影子内存（shadow memory）是为每个被监视的字节维护元数据的独立地址空间；检查就是「读元数据，判断这次访问是否合法」。

ASan 的影子比例是 1:8：每 8 个应用字节对应 1 个影子字节，影子字节编码前 8 个字节中哪些可访问。地址映射近似为 `shadow = (addr >> 3) + offset`，具体 offset 依平台而定。UBSan 不用影子内存，它直接在运算前插入条件分支，条件来自静态类型和操作数范围。
:::

ASan 的堆插桩由分配器拦截器完成：`malloc` 返回的区域两侧加红区（redzone），释放后进入隔离区（quarantine），延迟复用，以便捕获 use-after-free。栈和全局变量也有红区，但栈上的精确越界依赖编译器插入的栈帧描述；`detect_stack_use_after_return` 默认不开，开启后能抓「返回后使用栈」，代价更高。ASan 还能抓 `double-free`、`invalid-free` 和部分 `memcpy` 溢出。

ASan 的漏报边界很清楚：它只检查被插桩的访问。未插桩的库（例如系统自带、没开 ASan 的共享库）内部的越界不会报；对象内部的越界（`struct { char a[4]; int b; }` 里从 `a` 写到 `b`）不跨越红区，不报；自定义分配器（内存池、`mmap` 直接管理）如果没有调用 ASan 的 poisoning 接口，也不报；`malloc_usable_size` 之外的一点点「分配器给的富余」可能被当作合法。最后一类尤其容易骗人：`malloc(4 * sizeof(int))` 在 ASan 下是精确 16 字节区域，但普通分配器可能给 24 或 32 字节，越界写不崩不代表没 UB。

UBSan 的插桩点在运算本身：有符号加减乘、左移、除法、空指针、对齐、虚表指针、`bool` 装载、枚举越界等。它默认「报告后继续」，所以 CI 里必须加 `-fno-sanitize-recover=all`，否则进程退出码仍是 0，流水线会把失败当通过。UBSan 不负责数组越界（那是 ASan 的领域），也不保证捕获所有 UB：`-fsanitize=undefined` 是一组检查的集合，具体列表随 Clang 版本变化；未初始化读、数据竞争、严格别名都不在这个集合里。

TSan 的机制是影子单元加 happens-before 图。它在编译期给每个内存访问插桩，在运行时记录访问的线程、位置和同步边；当两个冲突访问之间没有 happens-before 边时报告。TSan 会拦截 `pthread`、C11 原子和部分系统调用；对自定义同步（自旋锁用普通变量实现）可能误报，对没有被拦截的同步可能漏报。开销通常是 5–15 倍，不能和 ASan 同时链接。

MSan 用影子位标记「未初始化」，沿数据流传播，读到未初始化值且影响分支或输出时报告。它的硬约束是「所有代码都必须插桩」，包括 C++ 标准库；因此它主要在 Linux 上可用，macOS 没有官方支持。本章脚本探测 `-fsanitize=memory`，在本机得到 `unsupported option '-fsanitize=memory' for target 'arm64-apple-darwin...'`，于是明确 SKIP，而不是伪造一份报告。

C 源码 ──► 前端 ──► IR ──► [ASan/UBSan/TSan 插桩 pass] ──► 优化 ──► 目标码
                              │                                  │
                              │ 记录访问宽度/类型/线程            │
                              ▼                                  ▼
                        运行时库 + 影子内存  ◄──────────────  执行

| 工具 | 抓什么 | 不抓什么 | 典型开销 |
|:--|:--|:--|:--|

### TSan 的注解与误报边界

TSan 对「什么是同步」有固定模型：互斥锁、原子操作、线程创建/加入、条件变量。它不认识你自己用 `volatile int flag` 实现的自旋锁，也不认识通过 `mmap` 共享内存加 `futex` 的自定义协议。前者会被报成数据竞争（误报），后者可能被漏报。TSan 提供 `__tsan_acquire`/`__tsan_release` 注解，让自定义同步进入 happens-before 图；标准 C11 代码则应直接用 `atomic_*`，让编译器和 TSan 都理解。

另一个边界是「竞争但没读到坏值」。TSan 报告的是「存在冲突访问且无 happens-before」，不是「这次运行一定读到了撕裂值」。因此 TSan 的报告是可能性的证据，不是错误的充分条件；但在 C 的内存模型里，数据竞争本身就是 UB，所以报告仍然成立。不要用「我跑了一万次都没出错」来反驳 TSan。

### 怎样读一份 sanitizer 报告

ASan 的报告看起来吓人，结构其实固定。以本章的越界读为例：

```text
==PID==ERROR: AddressSanitizer: heap-buffer-overflow on address 0xADDR ...
READ of size 4 at 0xADDR thread T0
    #0 0xADDR in read_at ub_lab.c:37
    #1 0xADDR in main ub_lab.c:128
0xADDR is located 0 bytes after 16-byte region [0xADDR,0xADDR)
allocated by thread T0 here:
    #1 0xADDR in main ub_lab.c:119
SUMMARY: AddressSanitizer: heap-buffer-overflow ub_lab.c:37 in read_at
```

读法分四层。第一层是错误类型与访问宽度：`heap-buffer-overflow` 说明越界发生在堆上，`READ of size 4` 说明读 4 字节。第二层是位置：`0 bytes after 16-byte region` 说明地址正好在 16 字节分配区之后，对应 `int a[4]` 的 `a[4]`。第三层是栈：`#0` 是出错函数，往下是调用者；没有符号时只剩地址。第四层是分配点：它告诉你这块内存是谁申请的，对 UAF 还会给出释放点。

影子字节也值得会看。ASan 用 `00` 表示连续 8 字节都可访问，`01`–`07` 表示前 k 字节可访问，`fa` 表示堆红区，`fd` 表示已释放区域。报告末尾的 Shadow bytes 里，`=>` 指向的字节就是出错地址的影子；看到 `fa` 或 `fd`，基本可以确认越界/释放后使用。不要花时间记全部编码，记住 `00`、`fa`、`fd` 三个就够日常排查。

报告里的地址每次运行都不同，不要把它写进 bug 标题或快照测试。稳定的键是「错误类型 + 源码位置 + 顶层栈帧」，必要时加分配点。把地址归一化后，同一 bug 的多次报告才能聚合。

### 符号化、内联与报告可读性

sanitizer 报告的质量取决于调试信息。`-g` 让栈帧带文件名和行号；`-fno-omit-frame-pointer` 让 ASan 能走帧指针栈；`-O1` 以上会内联，报告里的 `#0` 可能指向被内联的函数，而不是源码里看到的调用点。遇到「行号对不上」，先看是否是内联：用 `-fno-inline` 重编一次，或在报告里找 `inlined by` 标记。

优化还会改变「哪条访问被插桩」。同一个 `a[i]` 在循环展开后可能变成多个访问，在向量化后可能变成一条宽访问；ASan 对宽访问的检查按向量宽度进行，报告的 `READ of size 16` 并不对应源码里的 `int`。读报告时先看访问宽度和源码行，再判断是哪一个逻辑访问。

### 组合与优化级别

`-fsanitize=address,undefined` 可以同时链接 ASan 与 UBSan 运行时，但插桩顺序会影响报告：一次越界可能先触发 ASan 的检查，UBSan 的溢出检查根本没机会执行。排查时不要假设「只开 UBSan 就能看到全部 UB」，也不要假设「ASan 报了就越界是唯一问题」。按类别拆 job，比在一个 job 里堆 sanitizer 更容易定位。

优化级别也会改变插桩密度。`-O0` 保留所有变量和语句，报告栈最完整；`-O2` 内联后栈更短、行号更偏，但更接近发布配置。一个实用的组合是：`-O1 -g` 跑 ASan/UBSan 做定位，`-O2 -g` 跑 ASan 做发布前确认。两者都保留 `-fno-omit-frame-pointer`，否则栈回溯会退化。

## 9.5 静态分析：抽象解释、数据流与符号执行 {#sec-compilers.3.9.5}

静态分析不运行程序，而是在所有可能输入上求一个近似。近似必须回答两个问题：分析结果是否覆盖所有真实行为（soundness），以及是否只包含真实行为（completeness）。对 UB 检测，这两者不可兼得；工程工具通常选一边，再用用户体验补另一边。

抽象解释（abstract interpretation）把这套直觉形式化：选一个抽象域 D，用 concretization 函数 γ 把每个抽象值映射到一组具体状态；每个指令对应一个单调的抽象转换函数；在 CFG 上迭代到不动点。区间域是最常见的例子：变量 x 的抽象值是 [l, u]，γ([l,u]) 是所有落在这个区间的具体值。

::: def 定义 9.5.1 · 分析的可靠性与完备性 {#def-compilers.3.9.5.1}
设分析在程序点 p 输出抽象状态 a_p，真实可达状态集合为 S_p。

- **可靠（sound）**：S_p 包含于 γ(a_p)。分析不遗漏任何真实行为；代价是可能包含不可达状态，于是产生误报。
- **完备（complete）**：γ(a_p) 包含于 S_p。分析不引入多余状态；代价是可能漏掉真实行为，于是产生漏报。
- **既可靠又完备**：γ(a_p) 等于 S_p，即精确分析。对图灵完备语言的可达性问题，一般做不到。

静态分析器报 warning 的依据通常是「γ(a_p) 中存在违反性质的状态」。可靠分析器的 warning 可能是误报（该状态实际不可达），但不会漏报；不完备分析器可能安静地放过真实 bug。工程上大多数工具为了可用性会牺牲一点可靠性（例如超时后放弃、对复杂特性建模不全），所以「没有 warning」永远不能当证明。
:::

数据流分析是抽象解释的一个特例。第 5 章已经给出到达定值、活跃变量、可用表达式的框架；这里只强调与 UB 相关的两个选择。第一，may 分析与 must 分析的合并方向不同：越界检查需要 may（只要可能越界就报），空指针检查也是 may；而「除数一定非零」需要 must（所有路径都非零才安全）。第二，初始状态的选择直接决定误报/漏报：把未初始化变量设为「任意值」是可靠的，设为 0 则会漏报。

区间域的非关系性（non-relational）是误报的主要来源。它分别记录 `x ∈ [0, +∞)` 和 `y ∈ [0, +∞)`，却不知道 `x + y <= 7`。于是下面这段实际安全的代码会被报越界：

```text
x = input; y = input;
if (x < 0) goto END;
if (y < 0) goto END;
if (x + y > 7) goto END;
a[x] = 0;              // x 实际在 [0,7]
```

要证明安全，需要关系域（如多面体域、八边形域）或路径条件，代价是更高复杂度。符号执行（symbolic execution）走另一条路：把输入符号化，沿路径累积约束，用 SMT 求解器判断「是否存在满足约束且触发错误的输入」。它能给出具体反例，但对循环需要上界或不变式，否则路径数爆炸。concolic 执行把具体执行与符号约束结合，用具体值引导探索，是很多现代 fuzzer 的基础。

Clang 生态里有两类工具。`clang-tidy` 基于 AST matcher 做局部模式匹配，适合「禁止某 API」「必须检查返回值」这类规则；Clang Static Analyzer（`clang --analyze`）在 CFG 上做路径敏感分析，能跟踪 `malloc`/`free`、空指针、除零。两者都不是证明：`clang-tidy` 的检查通常不跨翻译单元，Static Analyzer 有路径上限和建模盲区。把它们放进 CI 时，应按「新增告警」而不是「全量清零」设门禁，否则历史代码会把门禁淹没。

为了看清误报与漏报的机制，本章写了一个约 300 行的区间抽象解释器 `experiments/ch09/static_lab.py`。它支持赋值、加减乘模、条件跳转、数组写检查和循环上的 widening。运行结果如下（节选）：

```text
[guarded]  rounds=8
  no warning
  witness: i=3 时 a[3] 在界内：分析器与运行时一致，不报。
  concrete: a[3] -> in bounds

[negative]  rounds=7
  WARNING pc 2: a[i] 可能越界；下标区间 [-inf, 7]，合法区间 [0, 7]
  witness: i=-1 通过上界检查，但 a[-1] 越界：真阳性。
  concrete: a[-1] -> OUT OF BOUNDS

[relational]  rounds=10
  WARNING pc 5: a[x] 可能越界；下标区间 [0, +inf]，合法区间 [0, 7]
  witness: x=3,y=4 满足 x+y<=7，a[3] 安全；区间域丢失相关性，报假阳性。
  concrete: a[3] -> in bounds

[modulo]  rounds=4
  WARNING pc 2: a[j] 可能越界；下标区间 [-7, 7]，合法区间 [0, 7]
  witness: i=-1 时 C 的 -1%8 == -1，a[-1] 越界；--mod=math 会漏报。
  concrete: a[-1] -> OUT OF BOUNDS

[overflow]  rounds=3
  WARNING pc 1: y = (x + 1) 可能使 int 溢出
  witness: INT_MAX+1 是有符号溢出；--semantics=wrap 把 UB 当回绕，漏报。
```

`guarded` 是路径细化起作用的例子：两个 `if` 把 `i` 收窄到 `[0,7]`，检查通过。`negative` 只检查了上界，负下标漏进来，是真阳性。`relational` 的关系信息丢失，是假阳性。`modulo` 的区间 `[-7,7]` 是 C 的截断取模结果；如果分析器按数学取模算成 `[0,7]`，就会漏报（`--mod=math` 的输出正是 `no warning`）。`overflow` 在严格模式下报，在 `--semantics=wrap` 下不报，因为后者把 UB 建模成了硬件回绕。

这段实验的结论不是「区间分析不好」，而是：**分析器的语义必须与语言的 UB 规则对齐**。把 C 的 `%` 当数学取模、把有符号加法当模运算，都会让分析器在真实 UB 面前保持沉默。这类错误在自研分析器里比在成熟工具里更常见，因为成熟工具通常有专门的「语言语义」层。

### 把区间分析写成方程

抽象解释的骨架可以用三行方程写完。对每个程序点 n：

```text
IN[n]  = join { OUT[p] | p 是 n 的前驱 }
OUT[n] = transfer_n(IN[n])
```

`join` 在区间域上是逐变量的最小上界：`[0,3] join [2,7] = [0,7]`，`[0,3] join [1,+inf) = [0,+inf)`。`transfer` 按指令类型定义：

| 指令 | 抽象转换 | 备注 |
|:--|:--|:--|
| `x = const` | `state[x] = [c,c]` | 精确 |
| `x = input` | `state[x] = [-inf,+inf]` | 未知输入 |
| `x = y + k` | 区间端点加 k | 溢出时置顶并报 UB |
| `x = y % 8` | 非负时 `[0,7]`，否则 `[-7,7]` | C 的截断取模 |
| `if (x < k)` | 真边 `x <= k-1`，假边 `x >= k` | 路径细化 |
| `a[x] = 0` | 下标不在 `[0,N-1]` 则报 | 检查点 |

循环会让朴素迭代不终止：`i` 从 0 开始，每轮加 1，区间变成 `[0,0]`、`[0,1]`、`[0,2]`……。区间域的高度是无限的，必须用 widening 把「不断增长的上界」推到 `+inf`。下面的循环在第三次访问后触发 widening：

```text
i = 0
L: if (i >= 8) goto E
   a[i] = 0
   i = i + 1
   goto L
E: halt
```

widening 后 `i` 在 `L` 处变成 `[0,+inf)`，但循环体里的 `if (i >= 8)` 假边又把 `i` 收窄回 `[0,7]`，所以 `a[i]` 仍然安全。这说明精度来自「域 + 路径细化」的组合，而不是单靠 widening。`static_lab.py` 的 `widen_states` 和 `refine` 分别实现这两件事。

符号执行把「状态」换成「路径条件」。对 9.5 开头的 `relational` 程序，走到 `a[x]` 的路径条件是：

```text
x >= 0 且 y >= 0 且 x + y <= 7
```

SMT 求解器可以判断「是否存在 x >= 8 且满足上述条件」；答案是不可满足，因此该路径安全。区间分析给不出这个结论，因为它丢掉了 `x + y <= 7` 这个关系。两条路线的代价不同：符号执行精确但可能路径爆炸，抽象解释总是终止但可能不精确。工程工具常把两者混用：先用抽象解释缩小范围，再对可疑点做符号求解。

### widening 的轨迹与精度

把循环分析的过程打印出来，widening 的代价就很直观。对 `i = 0; while (i < 8) { a[i]; i++; }`，`L` 处的 `i` 区间依次是：

| 轮次 | `L` 处 `i` | 说明 |
|--:|:--|:--|
| 1 | `[0,0]` | 入口 |
| 2 | `[0,1]` | 回边合并 |
| 3 | `[0,2]` | 继续增长 |
| 4 | `[0,+inf)` | 触发 widening |
| 5 | `[0,+inf)` | 不动点 |

如果没有 widening，这个序列永远不收敛；如果 widening 太激进，连 `i >= 0` 都丢掉，循环体里的 `a[i]` 就会报负下标。工程上的折中是「延迟 widening」：先迭代若干轮，等区间稳定增长后再推无穷；或者加一层 narrowing，在 widening 之后用 guard 重新收紧。`static_lab.py` 用「访问次数超过 4 才 widen」的简单策略，对示例足够，但不是通用解。

符号执行的代价可以用路径数说明：一个循环体有两个分支，展开 k 层就有 2^k 条路径；再加函数调用，路径数乘起来。缓解手段是路径合并（把相同后缀的路径合并）、循环摘要（用不变式代替展开）、以及有界探索（只找深度 d 以内的反例）。这也是为什么「符号执行能证明无 bug」通常只在有界或带注解的代码上成立。

### 上下文敏感与摘要

过程间分析比过程内难得多。上下文敏感（context-sensitive）分析会为不同调用点维护不同的抽象状态，精度高但状态数爆炸；上下文不敏感分析把所有调用者合并，容易把不相关的路径混在一起，产生误报。工程折中是「函数摘要」：为每个函数计算一个输入-输出关系（例如「返回非空」「不修改参数」「可能除零」），调用点只消费摘要。摘要的精度决定了跨函数误报的上限。

对 UB 检测，摘要至少要记录「是否可能解引用空指针」「是否可能越界」「是否可能不返回」。这些性质不是简单的类型，不能靠签名推导；它们需要分析函数体，或者由程序员用契约标注。`static_lab.py` 不做过程间分析，所以它对跨函数的例子只能给出「未知」；这不是实现偷懒，而是范围声明。

抽象解释的终止性依赖域的高度。有限域（如 `may/must` 布尔格）天然终止；无限域（区间、多面体）需要 widening 或有限截断。工程实现常用「迭代上限 + widening」的组合：先跑若干净则结束，超过上限就推无穷并标记「结果不精确」。这个标记很重要，它告诉调用者「no warning」的置信度更低。

## 9.6 误报、漏报与可判定性 {#sec-compilers.3.9.6}

误报（false positive）是报了但程序实际安全；漏报（false negative）是程序有 bug 但没报。二者不是对称的：对编译器优化，漏报可能意味着生成错误代码；对安全工具，漏报可能意味着漏洞上线。评估一个分析器，至少要看它在固定基准上的 precision/recall，而不是只看「报了多少」。

::: thm 定理 9.6.1 · UB 检测的不可判定性 {#thm-compilers.3.9.6.1}
不存在一个算法，对任意 C 程序都能在有限时间内判定「该程序是否存在一次触发 UB 的执行」，并且对存在 UB 的程序回答「是」、对不存在的回答「否」。

证明思路：把任意图灵机 M 与输入 w 编码成一个 C 程序 P，使 P 触发 UB 当且仅当 M(w) 停机。若存在上述判定器，就能判定停机问题，矛盾。编码只需一个循环模拟 M，停机后执行一次越界写。C 的实现有资源限制，但作为语言模型足以表达通用计算；对有限状态或受限子集，判定可能可行，这正是「按子集做可判定分析」的空间。
:::

定理的实践含义：任何声称「零漏报且零误报」的 UB 工具，要么只覆盖一个可判定子集，要么在某个地方不终止/不精确。成熟工具通常明确写出边界：ASan 只抓插桩到的访问，CBMC 只对有限展开深度成立，Frama-C 的 WP 插件要求注解和循环不变式。看到「形式化验证」四个字，先问它的假设和覆盖范围。

误报的来源可以按抽象层次列成一张表：

| 来源 | 例子 | 缓解 |
|:--|:--|:--|
| 路径不敏感 | 两个分支合并后丢失条件 | 路径敏感分析、条件分片 |
| 非关系域 | 知道 `x>=0`、`y>=0`，不知道 `x+y<=7` | 多面体域、符号执行 |
| widening 过强 | 循环变量被推到 `+inf` | narrowing、循环不变式 |
| 建模不精确 | 不认识自定义分配器/同步原语 | 模型注解、sanitizer 接口 |
| 别名保守 | 两个指针可能别名，合并状态 | 别名分析、`restrict` |
| 库边界 | 外部函数的行为未知 | 函数摘要、契约 |

漏报的来源同样具体：

| 来源 | 例子 | 缓解 |
|:--|:--|:--|
| 语义建模错误 | 把有符号溢出当回绕 | 对照标准写 transfer 函数 |
| 路径爆炸后放弃 | 深层循环只展开固定次数 | 不变式、有界模型检查 |
| 超时/预算 | CI 只给 60 秒 | 分层分析、增量缓存 |
| 抑制过期 | 旧 bug 的 `NOLINT` 一直留着 | 抑制带 owner 与到期日 |
| sanitizer 盲区 | 未插桩库、对象内越界 | 全量插桩、硬件辅助检查 |
| 输入未覆盖 | fuzz 没走到那条路径 | 覆盖率引导、结构化输入 |

误报的代价常被低估。一个每天报 200 条误报的工具，团队会在两周内学会忽略它；此后真阳性也会被忽略。降低误报的工程手段包括：只在 diff 上报告新增告警、按置信度分级、给出可执行的反例、允许带到期日的抑制。不要用「全量清零」当 KPI，那会诱导开发者写更宽的抑制。

对单个告警的 triage 可以固定成五步：

1. 复现：用报告给的输入/路径在本机跑一遍，确认是运行时 bug 还是分析器建模问题。
2. 缩小：把代码删到最小仍触发，区分「真 UB」与「分析器不理解」。
3. 归类：对照 9.3 的表，确认标准条款；若是实现定义，改文档而不是改代码。
4. 修复：优先改代码结构（检查提前、边界显式、避免别名），而不是加抑制。
5. 回归：把最小复现加入测试或 fuzz 语料，确保修复不会回退。

本章实验正好覆盖了三类结果：`negative` 是真阳性，`relational` 是假阳性，`modulo --mod=math` 与 `overflow --semantics=wrap` 是漏报。把这三类都跑一遍，比只看一个「成功抓到 bug」的 demo 更有教育意义，因为真实项目里三者会同时出现。

### 指标与一次完整的 triage

把「准不准」变成数字，至少需要四个量：真阳性 TP、假阳性 FP、真阴性 TN、假阴性 FN。常用的两个指标是：

```text
precision = TP / (TP + FP)     报出来的里面有多少是真的
recall    = TP / (TP + FN)     真的里面有多少被报出来
```

假设一个分析器在 100 个真实 bug 上报了 80 个，其中 20 个是误报，那么 TP=60、FP=20、FN=40，precision=0.75，recall=0.60。只看「报了 80 个」会高估它；只看 recall 又会忽略误报成本。发布门禁通常更看重 precision，因为误报会训练团队忽略告警；安全审计更看重 recall，因为漏报的代价更高。

把 `static_lab.py` 的五个程序当成一个小基准，可以得到一张具体的表：

| 程序 | 分析器输出 | 真实情况 | 分类 |
|:--|:--|:--|:--|
| `guarded` | no warning | 安全 | 真阴性 |
| `negative` | warning | 越界 | 真阳性 |
| `relational` | warning | 安全 | 假阳性 |
| `modulo`（默认 C 语义） | warning | 越界 | 真阳性 |
| `modulo --mod=math` | no warning | 越界 | 假阴性 |
| `overflow --semantics=wrap` | no warning | UB | 假阴性 |

这张表比任何「我们的分析器很准」都更有说服力，因为它把每个判断和可执行的反例放在一起。写工具文档时，也应该给出这种表：哪些构造能证明、哪些只能报可能、哪些明确不覆盖。

一次完整的 triage 记录可以长这样：

| 字段 | 示例 |
|:--|:--|
| 告警 | `a[x] may be out of bounds; x in [0, +inf)` |
| 复现 | `python3 static_lab.py --program=relational` |
| 真实行为 | `x=3,y=4` 时 `a[3]` 安全 |
| 分类 | 假阳性（非关系域） |
| 处理 | 不改代码；给分析器加关系域或在该点加断言 |
| 回归 | 把该程序加入基准，防止未来把 FP 当 TP 修 |

对假阴性则相反：先确认反例真的触发 UB（用 UBSan/ASan 或人工对照标准），再判断是分析器建模错、路径没覆盖，还是超时放弃。不要因为「工具没报」就关闭一个真实 issue；也不要因为「工具报了」就盲目改代码。triage 的价值在于把两者分开。

### 怎样评估一个分析器

评估分析器最怕「自己出题自己判卷」。一个可信的小基准至少要有三类样本：真阳性（已知 UB，带触发输入）、真阴性（合法，但写法容易触发误报）、以及边界样本（实现定义、未指定、依赖平台）。每类样本都要有可执行入口，而不是只写「应该报」。

第二层是变异测试：拿一组无 UB 的程序，人工注入已知 bug（把 `i < n` 改成 `i <= n`、把 `p->next` 改成 `p->next->next`、把 `free` 后的读加回来），看分析器能抓到多少。变异体给了 ground truth，比「在真实项目里数 warning」可控。代价是变异可能不真实，所以还要用历史 bug 做补充。

第三层是成本：分析时间、内存、误报数、修复误报所需时间。一个 recall 高但每天报 500 条误报的工具，实际价值可能低于 recall 中等但每天报 5 条的工具。把这些数字写进工具选型文档，比比较「支持多少 check」有意义。

最后要记录「不覆盖」清单。`static_lab.py` 明确不覆盖：跨函数、堆、指针别名、并发、浮点。文档里写清楚这些，用户才不会把 no warning 当成证明。工具的可信度来自边界透明，而不是宣称全能。

### 误报与漏报的代价不对称

同一个分析器，在不同场景下的最优工作点不同。面向开发者的 IDE 插件应偏向低误报：一条误报会打断思路，十条误报会让插件被关掉。面向发布的审计应偏向低漏报：漏掉一个越界可能变成 CVE。把两者混成一个「默认配置」，通常两边都不满意。

可以用一个简单的代价模型来选阈值：设单条误报的处理成本为 `c_fp`，单条漏报的损失为 `c_fn`，则期望成本约为 `FP * c_fp + FN * c_fn`。安全审计里 `c_fn` 远大于 `c_fp`，所以接受更多误报；日常开发里反过来。把这个模型写进工具配置文档，比争论「这个 warning 有没有用」更可操作。

可判定子集是工业工具的现实出路。只检查「常量下标的数组访问」是可判定的；只检查「单函数、无循环、无指针别名」的子集也是可判定的。工具文档应写清楚自己覆盖哪个子集，而不是暗示「能检查所有 C」。当用户把一段超出子集的代码交给工具时，正确行为是「不保证」或「跳过」，而不是「没报就等于安全」。

### 可判定子集的取舍

一个只会分析「常量下标 + 单函数 + 无循环」的工具，仍然有价值：它能 100% 覆盖自己声明的子集，误报极低，适合做提交前门禁。它的局限也清晰：遇到指针、循环、跨函数就返回「未知」。把「未知」显式呈现给用户，比假装分析过更诚实。工具的能力边界应该是一等公民，而不是文档角落的一句话。

## 9.7 工程化：CI 矩阵、抑制与证据 {#sec-compilers.3.9.7}

### 矩阵不是越大越好

维度多了，组合会爆炸。选择维度的原则是「每个维度都要能改变结论」，不能改变结论的维度只增加成本。对 UB 检查，通常值得保留这些维度：

| 维度 | 取值 | 为什么保留 |
|:--|:--|:--|
| 编译器 | clang、gcc | UB 假设与诊断不同，双编译器能抓实现依赖 |
| 优化级别 | `-O0`、`-O2` | UB 在低优化「碰巧能跑」，高优化才暴露 |
| sanitizer | ASan、UBSan、TSan | 覆盖不同类别，不能互相替代 |
| 标准 | `-std=c17`、`-std=c23` | 新旧标准对部分构造的归类不同 |
| 目标 | 本机、`-target x86_64-...` | 位宽、字符符号、对齐不同 |

不值得默认展开的维度：所有 `-O1/-O2/-O3/-Os` 的笛卡尔积（选 `-O1` 与 `-O2` 即可）、所有 sanitizer 的两两组合（ASan+TSan 不可链接）、所有架构的完整测试套件（用交叉编译的静态检查替代）。矩阵的目标是「用最少的 job 覆盖最多的失效模式」，不是「把所有 flag 都跑一遍」。

具体到命令，PR 的 L1 可以只有两条：

```bash
clang -std=c17 -Wall -Wextra -Werror -O1 -g \
  -fsanitize=address,undefined -fno-sanitize-recover=all \
  src/*.c -o build/app-asan
./build/app-asan --self-test

clang -std=c17 -Wall -Wextra -Werror -O2 -g \
  -fsanitize=address -fno-omit-frame-pointer \
  src/*.c -o build/app-asan-o2
./build/app-asan-o2 --self-test
```

第二条命令仍然只开 ASan，因为 UBSan 在 `-O2` 下的一部分检查可能被 UB 假设删除；把「优化后的 ASan」与「`-O1` 的 UBSan」分开，能避免一个 job 里的检查互相掩盖。nightly 再加 TSan 与 `-O0` 的 UBSan，release 前跑一次全矩阵并把报告归档。

抑制文件要像代码一样评审。一个 ASan 抑制文件的最小内容如下：

```text
# owner: runtime-team, expires: 2026-06-30
# reason: third-party libfoo 1.2 reads one byte past its own buffer
interceptor_via_fun:foo_parse
```

`interceptor_via_fun` 的粒度是函数级，比 `src:file:line` 宽；优先用后者，只有在调用点不稳定时才用前者。UBSan 的抑制文件按检查名或源码位置匹配，格式随版本变化，升级编译器时要重新验证。所有抑制都要有到期日，到期后 CI 变红，由 owner 决定「修上游 / 换版本 / 续期」。

成本也要测，不要凭感觉。Linux 上可以用 `/usr/bin/time -v` 看 `Maximum resident set size` 与 `Elapsed (wall clock)`；macOS 用 `/usr/bin/time -l`。把同一测试在无 sanitizer、ASan、TSan 下各跑三次，取中位数，才能判断矩阵是否值得。没有测量就扩矩阵，通常只是把 CI 变慢。

把 UB 检查放进 CI，核心矛盾是「覆盖要广」与「反馈要快」。一个包含 6 种编译器 × 4 个优化级别 × 4 种 sanitizer 的矩阵会跑几十个 job，PR 等不起。可行做法是分层：PR 跑快速子集，nightly 跑扩展矩阵，release 前跑一次全量并归档证据。

| 层级 | 触发 | 配置 | 目标 | 预算 |
|:--|:--|:--|:--|:--|
| L0 | 每次 push | `-O0` 编译 + 单测 | 语法/链接/基本行为 | 分钟级 |
| L1 | PR | `-O1` UBSan + ASan，`-fno-sanitize-recover=all` | 快速抓溢出/越界/UAF | 2–3 倍 |
| L2 | nightly | `-O2` ASan、`-O2` UBSan、TSan | 抓优化后才出现的 UB/竞争 | 10–20 倍 |
| L3 | nightly | clang-tidy diff、Static Analyzer | 模式类问题、跨函数路径 | 分钟到小时 |
| L4 | release | 全矩阵 + fuzz smoke + 归档 | 发布证据 | 小时级 |

优化级别必须覆盖 `-O0` 与 `-O2`，因为 UB 的表现依赖优化。`-O0` 下未定义行为往往「按硬件语义」跑出看似合理的结果；`-O2` 下同一段代码可能被删、被折、被重排。只在 `-O0` 跑 sanitizer 会漏掉「优化器利用 UB」这一类；只在 `-O2` 跑又会漏掉「前端插桩在低优化级别才保留」的细节。两者都跑，才有一致的证据链。

`-fno-sanitize-recover=all` 是 CI 的硬要求。UBSan 默认在报告后继续执行，进程退出码可能仍是 0；如果 job 只看退出码，就会把「已经踩到 UB」判成通过。ASan 默认在错误后终止，但 `halt_on_error=0` 会改变行为；不要为了「多收集几条」而在门禁 job 里关掉终止。需要收集全部报告时，另开一个非门禁 job。

抑制（suppression）是必要的恶。没有它，第三方头文件或已知误报会让整个矩阵变红；滥用它，则会把真 bug 永久埋掉。可审计的抑制至少包含四样：精确范围（文件/行/函数）、理由、owner、到期日。C 代码里可以用属性：

```c
__attribute__((no_sanitize("undefined")))
int legacy_hash(int x)
{
    return x * 2654435761u;   /* 依赖无符号回绕，且已审计 */
}
```

注意 `no_sanitize("undefined")` 只关闭 UBSan，不会关闭 ASan；属性要写在最小函数上，不要写在头文件里传染整个翻译单元。ASan 的抑制文件用 `interceptor_via_fun:` 或 `src:file:line` 规则，通过 `ASAN_OPTIONS=suppressions=path` 加载；UBSan 用 `UBSAN_OPTIONS=suppressions=path`，格式是 signature 或 `src:file`。两条规则都要进版本库并经过 review。

`clang-tidy` 的抑制是 `// NOLINT(check-name)` 或 `.clang-tidy` 配置。不要把 `NOLINT` 写成裸标记；至少写出 check 名，方便以后审计。静态分析器的基线可以用 `scan-build` 的 HTML 报告或 SARIF 输出做 diff：只对新增行报告，历史告警进入基线文件，并给基线设置到期清理日。

一个最小但可用的 CI 矩阵如下。它是配置示意，不在本章实验中执行；真正的命令与输出以 `experiments/ch09/run.sh` 为准。

```yaml
name: ub-checks
on: [push, pull_request]
jobs:
  sanitizers:
    strategy:
      fail-fast: false
      matrix:
        opt: ["-O1", "-O2"]
        san: ["address,undefined", "thread"]
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - run: sudo apt-get update && sudo apt-get install -y clang
      - run: |
          clang -std=c17 -Wall -Wextra -Werror \
            -fno-sanitize-recover=all -fsanitize=SANITIZER \
            OPTFLAG -g src/*.c -o app
      - run: ./app --self-test
```

这段 YAML 有两个真实约束：`address,undefined` 可以组合，`thread` 不能与它们同链接；`thread` job 需要把 `opt` 也展开，否则矩阵会重复跑同一个配置。CI 配置也要像代码一样测试——至少在本地用 `act` 或手动命令验证一次，别让矩阵维度写错却没人发现。

证据归档比「绿了」更重要。每次 nightly 至少保存：编译器版本、完整命令行、sanitizer 报告原文（含栈）、失败输入的哈希、以及去重后的问题 ID。报告里的地址每次运行都不同，去重不能按地址；应按「错误类型 + 顶层栈帧 + 源码位置」聚合。第 10 章会讨论 fuzz 场景下的去重键，这里的规则相同：键太粗会合并不同 bug，键太细会让同一个 bug 刷屏。

最后是预算。ASan 约 2 倍、UBSan 约 1.2–2 倍、TSan 约 5–15 倍；如果测试套件本身要 20 分钟，L2 矩阵很容易超过一小时。可行的压缩手段是：只对改动涉及的二进制跑 sanitizer、把长测试放到 nightly、用 `-O1` 而不是 `-O2` 跑 ASan（多数越界不依赖优化级别）、把 TSan 限制在并发相关模块。不要用「跳过 sanitizer」来换速度，除非你明确记录了风险。

### 不稳定的 job 比没有 job 更糟

sanitizer 报告可能受地址布局、线程调度、ASLR 影响。一个「有时红有时绿」的 job 会让团队学会重跑，而不是修复。降低不稳定性的手段：固定输入与 seed（fuzz 用例）、关闭依赖地址的断言、把 TSan 的竞争报告与具体调度解耦、对超时设置明确的预算而不是「跑完为止」。如果某个 job 在 20 次运行中有 1 次假红，应先修 job 或隔离它，不要把它留在门禁里。

上面 YAML 里的 `SANITIZER` 与 `OPTFLAG` 是占位符，真实流水线要在矩阵展开时替换成具体值；不要原样提交，否则命令会以字面量传给 clang 并报错。更稳妥的写法是把两条命令写成两个独立 job，避免在 YAML 字符串里做变量拼接。CI 配置的第一原则是「本地能复现」：把 job 里的命令复制到终端，能跑通再提交。

### 证据的最小格式

一条可复现的 UB 证据至少包含六项：编译器与版本、完整命令行、优化级别、输入或 seed、sanitizer 输出（含错误类型与源码位置）、以及复现脚本路径。缺少任何一项，别人都可能在本地复现失败。把这条格式写进 issue 模板，比事后在聊天记录里翻命令更可靠。

## 9.8 agent 错误：把 UB 当「可移植」并用 sanitizer 兜底 {#sec-compilers.3.9.8}

这一节复盘一个 agent 生成代码的典型失败。任务很简单：写一个函数，返回链表头节点的值；如果头指针为空，返回 -1。agent 的产物如下：

```c
#include <stddef.h>

struct Node {
    int value;
    struct Node *next;
};

int list_head_value(struct Node *head)
{
    int v = head->value;      /* 先解引用 */
    if (head != NULL) {       /* 再检查 */
        return v;
    }
    return -1;
}
```

agent 在说明里写「已加空指针保护」。代码 review 时看起来也有 `if (head != NULL)`，很容易通过。真正的测试在 `-O2` 下：传入 `NULL` 直接段错误，`-1` 永远不会返回。

根因不是「agent 忘了检查」，而是检查的位置错了。`head->value` 已经完成一次解引用；如果 `head` 为空，这次解引用就是 UB。优化器从这次解引用推出「`head != NULL` 在所有后续路径上成立」，于是 `if (head != NULL)` 的条件恒真，分支被删除。这个推理是标准的、跨编译器的，不是某个版本的 bug。

用本章的工具可以这样发现它：

1. **看反汇编**。`clang -target x86_64-apple-darwin -O2 -c` 后 `llvm-objdump -d`，函数体只剩 `movl (%rdi), %eax; retq`，没有 `cmpq $0`。`-O0` 则有比较和分支。
2. **跑 sanitizer**。ASan 传 `NULL` 得到 `SEGV on unknown address 0x000000000000`，栈顶是 `guarded_load` 的 `movl (%rdi)`；UBSan 的 `-fsanitize=null` 会先报 `member access within null pointer`，但随后仍可能崩溃。
3. **静态分析**。Clang Static Analyzer 能在 `head->value` 处报 `Access to field 'value' results in a dereference of a null pointer`；`clang-tidy` 的 `bugprone-null-dereference` 也可能命中，取决于路径。
4. **对照优化级别**。`-O0` 与 `-O2` 的行为差异不是「优化器坏了」，而是 UB 假设在 `-O2` 被真正利用。

下面是本机生成的真实 x86-64 反汇编（节选，`--no-show-raw-insn`）：

```asm
0000000000000000 <_guarded_load>:
       0:      	pushq	%rbp
       1:      	movq	%rsp, %rbp
       4:      	movl	(%rdi), %eax
       6:      	popq	%rbp
       7:      	retq
```

```asm
0000000000000000 <_guarded_load>:
       0:      	pushq	%rbp
       1:      	movq	%rsp, %rbp
       4:      	movq	%rdi, -0x10(%rbp)
       8:      	movq	-0x10(%rbp), %rax
       c:      	movl	(%rax), %eax
       e:      	movl	%eax, -0x14(%rbp)
      11:      	cmpq	$0x0, -0x10(%rbp)
      16:      	je	0x20 <_guarded_load+0x20>
      18:      	movl	-0x14(%rbp), %eax
      1b:      	movl	%eax, -0x4(%rbp)
      1e:      	jmp	0x27 <_guarded_load+0x27>
      20:      	movl	$0xffffffff, -0x4(%rbp) ## imm = 0xFFFFFFFF
      27:      	movl	-0x4(%rbp), %eax
      2a:      	popq	%rbp
      2b:      	retq
```

`-O2` 版本里没有 `cmpq`，`-O0` 版本里有。检查被删掉的证据就在这四行差异里。

修复不是加 `-fno-delete-null-pointer-checks`，也不是「把优化关掉」，而是把检查提到第一次解引用之前：

```c
#include <stddef.h>

struct Node {
    int value;
    struct Node *next;
};

int list_head_value(struct Node *head)
{
    if (head == NULL) {
        return -1;
    }
    return head->value;
}
```

::: ex 例 9.8.1 · 为什么 `if (p)` 救不了 {#ex-compilers.3.9.8.1}
把 `guarded_load` 的 `p->value` 改成 `p->next->value`，情况更糟：`p->next` 已经隐含 `p` 非空，第二次解引用又隐含 `p->next` 非空；后面的 `if (p && p->next)` 会被整段删除。修复必须从「第一次解引用」开始，而不是从「最后一次检查」开始。

这类错误的共同模式是「先使用、后防御」。agent 往往把防御性检查当成一种可以后置的礼节；在 C 里，UB 假设会把后置检查变成死代码，于是防御只存在于源码阅读者的想象中。用 `-O2` 反汇编检查每个「看起来有保护」的函数，比在 `-O0` 下跑一遍更能暴露问题。
:::

### agent 的说明、补丁与回归测试

复盘时最值得保存的是 agent 的「自信说明」。它通常写成：「已添加空指针检查，若 `head` 为空返回 -1。」这句话在源码层面为真：确实有一个 `if`。但在语义层面为假：检查在解引用之后，`head` 为空时函数已经进入 UB，返回值没有定义。

把修复做成最小 diff，便于 review：

```text
-    int v = head->value;
-    if (head != NULL) {
-        return v;
-    }
-    return -1;
+    if (head == NULL) {
+        return -1;
+    }
+    return head->value;
```

回归测试要覆盖「空指针」这条路径，而不是只测非空：

```c
#include <assert.h>
#include <stddef.h>

struct Node {
    int value;
    struct Node *next;
};

int list_head_value(struct Node *head);

int main(void)
{
    struct Node n = {7, NULL};
    assert(list_head_value(&n) == 7);
    assert(list_head_value(NULL) == -1);
    return 0;
}
```

这段测试在修复前会在第二个 `assert` 崩溃（或在 `-O2` 下被优化成不可达），修复后通过。测试本身也可能被 UB 影响：如果被测函数先解引用，编译器可以假设 `NULL` 不会传进来，从而把 `assert(list_head_value(NULL) == -1)` 删掉。所以测试要在 `-O0` 和 `-O2` 都跑，并且用 ASan/UBSan 确认第二条路径真的被执行。

### 接口契约：把检查前移

修复 `list_head_value` 之后，还可以把契约写进类型系统，减少下一次犯错的概率。Clang 支持 `_Nonnull` 注解：把参数声明为 `struct Node * _Nonnull head`，签名就明确表示「调用方必须传非空指针」。

这个签名明确表示「调用方必须传非空指针」。传 `NULL` 时，Clang 在相关可空性检查下可能给出诊断；但它不会在运行时保护你，也不会阻止 `-O2` 依据「`head` 非空」做优化。注解的价值是让契约可见，让 review 和静态分析有依据，而不是替代检查。

对可能为空的接口，另一种设计是返回 `bool` 并通过出参写值：成功返回 `true` 并写 `*out`，失败返回 `false` 且不碰出参。这种接口把「空」变成正常控制流，不需要 UB 假设，也不依赖调用方记得检查。代价是调用点多两行；对 agent 生成的代码，它比「返回 -1 表示空」更稳，因为 -1 可能是合法值，空指针却必须是显式分支。

对 agent 生成代码的 review，可以固定问四个问题：指针的第一次解引用在哪里、空检查在它之前还是之后；数组下标的合法范围是什么、边界检查在不在计算之前；`malloc`/`realloc` 的返回值是否在第一次使用前检查；`free` 之后还有没有别名会被读。这四个问题不需要运行程序就能问，每一个都能用反汇编、sanitizer 或静态分析验证。

把案例收束成一条可执行规则：在 C 中，空指针检查的价值取决于它相对于第一次解引用的位置。任何「先解引用再检查」的代码，无论检查写得多漂亮，都不能阻止优化器删除它；sanitizer 只能在运行时报告这次 UB，不能把检查恢复成有效逻辑。

母本中的 sanitizer 章节以 Rust 的 Miri/ASan 为主，本章把同样的插桩原理落到 C17，并用本机 clang 的真实输出做证据。Rust 的借用检查在编译期排除了一部分 UB，但 `unsafe` 块内的指针操作仍需要 sanitizer 与人工审计；这一点与 C 的边界相同。

这张表还可以补一列「证据类型」：C 语言现代方法给的是标准条款与例子（E1），Rust Reference 给的是语言模型对照（E1），Rustc Dev Guide 给的是 sanitizer 实现（E2/E4），Effective Modern C++ 给的是并发背景（E1）。本书的落点尽量同时给条款与可复现输出，避免只读结论。

还有一条跨语言的对照值得记住：Rust 在安全代码里用借用检查排除了悬垂指针与数据竞争，但 `unsafe` 块内的原始指针解引用仍可能触发 UB；C 没有这层编译期检查，所以更依赖 sanitizer 与人工审计。两者的共同点是：一旦进入 UB 领域，语言标准不再保证运行结果，工具只能提供有限证据。

## 9.10 本章陷阱（8–15 条） {#sec-compilers.3.9.10}

::: errata 本章陷阱
1. **把 `-O0` 的行为当语义**。现象：同一段代码在 `-O0` 输出 42，在 `-O2` 崩溃或输出别的值。原因：`-O0` 只是碰巧按硬件语义执行了 UB，并没有把它变成定义行为。修复：用 UBSan/ASan 在 `-O1`/`-O2` 复现，并以标准条款而不是某次运行结果为准。
2. **以为 sanitizer 没报就是安全**。现象：ASan 全绿，线上仍越界。原因：越界发生在未插桩库、对象内部或自定义分配器里；sanitizer 只检查实际生成的访问。修复：全量插桩、补 poisoning、用 MSan/TSan 覆盖其他类别，并保留「未覆盖」清单。
3. **把未指定行为当 UB**。现象：`f() + g()` 结果随编译器变化，被误判为 UB。原因：求值顺序是未指定，不是未定义；两个调用都会发生。修复：需要顺序就拆语句；不要用「结果不同」反推 UB。
4. **把实现定义行为当可移植**。现象：`char` 在 x86 有符号、在 ARM 无符号，协议解析错位。原因：`char` 的符号性由实现定义。修复：用 `uint8_t`/`int8_t` 明确宽度与符号，构建矩阵覆盖。
5. **在解引用之后加空指针检查**。现象：`if (p)` 在 `-O2` 被删除。原因：`p->field` 已隐含 `p != NULL`，后续检查是死代码。修复：检查必须在第一次解引用之前；用反汇编确认 `cmp` 仍在。
6. **用 `-fno-delete-null-pointer-checks` 当修复**。现象：加了 flag 后检查保住了。原因：这只是让编译器少利用一个假设，其他 UB 假设仍在，且代码依旧不可移植。修复：改代码结构；flag 只能作为临时缓解并记录到期日。
7. **把有符号溢出交给 `-fwrapv`**。现象：本地回绕正常，换编译器/平台后结果不同。原因：`-fwrapv` 是扩展，改变了优化契约，且不保证所有库都这样编译。修复：用无符号类型表达模运算，或在运算前显式检查边界。
8. **认为 ASan 能抓所有数组越界**。现象：`struct { char a[4]; int b; }` 里写 `a[4]` 不报。原因：访问仍在同一分配对象内，没有跨红区。修复：用 `-fsanitize=bounds`、编译器内建 `__builtin_object_size`，或把数组边界显式建模。
9. **在 CI 里让 UBSan 恢复执行**。现象：报告打印了，job 仍然绿。原因：默认 `halt_on_error=0`，退出码为 0。修复：门禁 job 加 `-fno-sanitize-recover=all`，并检查退出码而不是日志关键字。
10. **抑制没有 owner 和到期日**。现象：三年前的 `NOLINT` 还在，真 bug 被永久静音。原因：抑制是代码，却没有生命周期管理。修复：抑制必须带理由、owner、到期日；到期自动变红，由 owner 决定续期或修复。
11. **把静态分析的 warning 当证明**。现象：分析器报「可能越界」，实际路径不可达；或反过来，分析器沉默但程序有 bug。原因：可靠性与完备性不可兼得，工具还有超时和建模盲区。修复：按 9.6 的 triage 五步复现、缩小、归类，再决定修代码还是修模型。
12. **把 `sizeof` 当跨平台常量**。现象：协议结构体在 32 位与 64 位平台上布局不同，解析错位。原因：`long`、指针、`size_t` 的宽度由实现决定。修复：用固定宽度类型、显式填充与 `_Static_assert(sizeof(struct S) == N)` 锁定布局。
13. **只在 `-O0` 跑 ASan**。现象：本地全绿，发布版崩溃。原因：`-O2` 的 UB 假设会删除访问或改变布局，低优化级别没有暴露。修复：L2 增加 `-O2` ASan，并把反汇编中关键检查是否保留纳入评审。
:::

以上 13 条可以归成三类，处理方式不同：

| 类别 | 条目 | 首选动作 |
|:--|:--|:--|
| 语义误判 | 1、3、4、7、12 | 回标准条款，改代码或类型 |
| 位置错误 | 5、6 | 把检查前移，反汇编验证 |
| 证据不足 | 2、8、9、10、11、13 | 补 sanitizer/分析器 job 与复现脚本 |

遇到新问题时先归类，再决定是改代码、改工具配置，还是补证据。不要用「加一个抑制」同时掩盖三类问题。

**Q1** 下面两个函数在 `-O2` 下行为是否可能不同？为什么？

```c
#include <stddef.h>

struct Node {
    int value;
    struct Node *next;
};

int a(struct Node *p) { if (p) return p->value; return -1; }
int b(struct Node *p) { int v = p->value; if (p) return v; return -1; }
```

**Q2** 你的 CI 在 `-O1` 下跑 ASan 全绿，在 `-O2` 下跑普通测试也全绿。能否据此说「没有内存错误」？给出两个反例场景。

**Q3** 区间分析器对 `x = input; if (x < 0) ...; if (x > 7) ...; a[x]` 报不报？如果把两个条件合并成 `if (x < 0 || x > 7)`，分析结果会变吗？为什么？

**Q4** 反汇编显示 `-O2` 下空指针检查被删除，但 ASan 运行时没有报错。这两个证据矛盾吗？应该信哪个？


::: sol 答案
**A1** 可能不同。`a` 的第一次解引用在检查之后，`p == NULL` 时走 `return -1`，是合法路径；编译器不能假设 `p` 非空。`b` 的第一次解引用在检查之前，`p == NULL` 时已经 UB，编译器可以假设 `p != NULL` 并删掉 `if`；`-O2` 下 `b` 可能只剩一条 load。把 `b` 的检查移到解引用之前，两者才等价。

**A2** 不能。反例一：越界发生在没有插桩的第三方库内部，ASan 看不到；反例二：对象内越界（`struct` 的数组字段写到相邻字段），没有跨红区；反例三：`-O2` 把整段 UB 访问删掉，普通测试根本没有执行到那条指令。要覆盖这些，需要全量插桩、`-fsanitize=bounds`、以及在不同优化级别下保留可观察的访问。

**A3** 默认的路径敏感区间分析不报：两个 `if` 分别把 `x` 收窄到 `[0, +inf)` 和 `[-inf, 7]`，交汇处得到 `[0,7]`。合并成 `x < 0 || x > 7` 后，如果分析器只做布尔路径分裂而不做区间补集，可能在「条件为假」的分支上得不到 `[0,7]`，从而报假阳性；好的实现会对析取条件做拆解。结论是：同一程序、同一域，控制流形状会改变精度。

**A4** 不矛盾，它们回答不同问题。反汇编回答「编译器生成了什么」：检查确实被删了。ASan 回答「这次执行有没有发生被插桩的非法访问」：如果测试输入从未传 `NULL`，或者那条路径被优化成不执行，ASan 就不会报。两者都要信，但结论要分开写：「检查已删除（反汇编证据）；本次测试未覆盖空指针输入（ASan 阴性）」。要证明修复有效，补一个传 `NULL` 的测试，并在 `-O2` 下确认返回值是 -1 而不是崩溃。
