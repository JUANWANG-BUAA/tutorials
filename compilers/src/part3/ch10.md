第 9 章讨论的是「程序是否合法」：UB 让编译器的变换失去约束，sanitizer 与静态分析只能提供有限证据。这一章换一个更主动的问题：如果我不知道正确结果，怎样让机器替我找反例？

答案是 oracle（判定器）。fuzzer 本身只负责生成输入、执行、观察；真正决定「这是不是 bug」的是 oracle。没有 oracle 的 fuzzer 只是在随机跑程序，跑得再多也不知道哪次结果错了。编译器领域之所以适合 fuzz，是因为 oracle 可以很便宜：同一段程序用解释器跑一遍、用 `-O0` 编译跑一遍、用 `-O2` 编译跑一遍，三者对可观察结果的判断就是一组差分 oracle。

但 oracle 也会错。一个把「两边都抛异常」判成一致的比较器，会把「优化器把除零错误删掉」这种 bug 判成通过；一个按「异常类型」去重的键，会把两个不同的优化 bug 合成一个。本章的实验 `experiments/ch10/fuzz_lab.py` 故意在优化器里放了两条不安全的化简规则，用固定 seed 跑 4000 次，找到并缩减到 `(x / x)` 与 `(0 / x)`；再用 `--oracle=skip-errors` 和 `--dedup=symptom` 复现两种「把 bug 判没」的错误。所有输出都来自本机实跑。

这一章的主线是「反馈的质量决定发现的质量」：先定义 oracle（10.1），再看覆盖率引导的变异与能量（10.2），然后用差分把「正确性」变成可比较的观察（10.3）。属性测试把「正确性」写成不变量（10.4），缩减与去重把一次失败变成可回归的资产（10.5），结构化输入与持久化决定 fuzz 能不能持续跑（10.6），资源边界决定它会不会把 CI 拖垮（10.7）。最后用 agent 的错误 oracle 案例收束（10.8）。

本章实验入口是 `experiments/ch10/run.sh`。它不依赖网络和第三方包，只用 Python 标准库；固定 seed 保证输出可复现。下文引用的计数、最小化结果与「0 bug」对照都来自这次运行。

## 10.1 oracle 问题：正确性从哪里来 {#sec-compilers.3.10.1}

fuzzing 的定义常被简化为「随机生成输入喂给程序」，这只说对了一半。随机输入只能触发执行，不能判断结果。真正的循环是：生成输入、执行、用 oracle 判定、把「有意义」的输入留在语料里。没有 oracle，崩溃是唯一的信号；而编译器的大多数 bug 不是崩溃，是「编译成功了但结果不对」。

::: def 定义 10.1.1 · 测试 oracle {#def-compilers.3.10.1.1}
测试 oracle（test oracle）是一个判定过程：给定输入 x、程序 P、以及 P 在 x 上的观察 O，回答「O 是否符合 P 的期望」。oracle 可以是：

- **参考实现**：另一个语义等价的解释器/编译器，比较输出。
- **性质**：不依赖具体输出，只检查不变量（如 `opt(opt(p)) == opt(p)`）。
- **规范**：把语言标准或接口契约编码成断言。
- **崩溃/资源**：只检查是否崩溃、超时、内存超限。
- **元差分**：比较同一程序在不同优化级别/目标/版本下的行为。

oracle 的强度与成本不成正比。崩溃 oracle 最便宜，但只能抓「硬失败」；参考实现最强，但参考实现本身可能错；性质 oracle 介于两者之间，需要设计不变量。
:::

编译器 fuzz 的独特之处是「参考实现通常存在」。一个解释器、一个 `-O0` 构建、另一个编译器，都可以作为参考。差分测试（differential testing）就是把「P 与 Q 应该一致」当成 oracle。它的盲点是相关性：如果 P 与 Q 共享同一个前端 bug，两边会一起错，差分通过。第 10.3 会展开这一点。

::: ex 例 10.1.2 · 一个便宜的差分 oracle {#ex-compilers.3.10.1.2}
考虑表达式优化器 `optimize` 与解释器 `eval_ast`。对输入表达式 e 和环境 x，参考结果是 `eval_ast(e, x)`，候选结果是 `eval_ast(optimize(e), x)`。若两者不同，就找到一个 bug。

实验中的具体反例：e = `x / x`，x = 0。参考解释器抛出除零；优化器把 `x / x` 化简成 `1`，候选返回 1。差分 oracle 报不一致。这个 bug 不需要「优化器崩溃」，只需要「两边对同一个输入给出不同观察」。

如果 oracle 写成「两边都抛异常就算一致」，同一个反例会变成「参考抛异常、候选返回值」——仍然不一致；但如果写成「参考抛异常就跳过」，反例就被吞掉。差别只在 oracle 的一行逻辑，结果从 2 个 bug 变成 0 个（10.8 会给出真实输出）。
:::

oracle 的观察对象要选对。对编译器，至少有三类观察：进程退出码、标准输出/文件内容、以及诊断信息。只比较退出码会漏掉「两边都成功但结果不同」；只比较 stdout 会漏掉「错误信息不同但都失败」；只比较诊断文本又会被格式变化干扰。一个实用的组合是：先比较退出码，再比较规范化后的输出，最后对失败情形比较错误类别而不是完整文本。

| oracle | 能抓 | 抓不到 | 成本 |
|:--|:--|:--|:--|
| 崩溃 | 段错误、断言、sanitizer 报告 | 静默错误结果 | 低 |
| 差分（参考实现） | 语义不一致、优化 bug | 两边同错、参考也错 | 中 |
| 属性 | 不变量破坏、幂等性 | 不变量没覆盖的语义 | 中 |
| 规范/注解 | 契约违反 | 规范没写的边界 | 高 |
| 元差分（多配置） | 优化级别/目标差异 | 所有配置共享的 bug | 中 |

「oracle 错」比「fuzzer 弱」更危险，因为前者会给出「零 bug」的假安全感。一个 fuzzer 跑了一周没找到 bug，先问的不是「是不是输入不够多」，而是「oracle 有没有可能把 bug 判成通过」。验证 oracle 的一个办法是「植入已知 bug」：人为把正确实现改错一行，看 fuzzer 能不能在合理时间内找到。如果找不到，先修 oracle 或生成器，而不是加机器。

### oracle 的三类错误

oracle 不是「有或没有」，而是会以三种方式出错：

| 错误 | 表现 | 后果 | 例子 |
|:--|:--|:--|:--|
| 假接受（false accept） | 把错误结果判成通过 | 漏报，最危险 | 参考抛异常时直接 return True |
| 假拒绝（false reject） | 把正确结果判成失败 | 噪声，消耗信任 | 把合法浮点差异当 bug |
| 跳过（skip） | 不比较，也不记录 | 统计失真 | 超时用例直接丢弃 |

假接受最难发现，因为它表现为「0 bug」。防御手段是阳性对照：人为植入一个已知 bug，确认 oracle 能报。假拒绝表现为「大量重复 issue」，防御手段是规范化观察、限制到规范保证的子集。跳过本身不是错，错在不记录；一个诚实的 fuzzer 应报告「执行 N 次、比较 M 次、跳过 K 次」，而不是只报「0 bug」。

### 观察的规范化

差分比较前要先把观察变成稳定形式。进程退出码、stdout、stderr、生成文件内容、以及执行时间，各自需要不同的规范化：

- 退出码：区分「正常退出」「断言失败」「被信号杀死」；不要把信号值当普通退出码。
- stdout：去掉时间戳、临时路径、PID、地址；对浮点保留固定有效位。
- stderr：只比较错误类别与关键 token，不比较完整格式。
- 文件：按内容哈希比较，或按语义解析后比较；不要比较 mtime。
- 时间：只用于性能回归，不进入功能差分。

```python
import re

def normalize(text):
    text = re.sub(r"0x[0-9a-fA-F]+", "0xADDR", text)
    text = re.sub(r"/tmp/[^\s]+", "/tmp/PATH", text)
    text = re.sub(r"\b\d{4}-\d{2}-\d{2}T[^\s]+", "TIMESTAMP", text)
    return text.strip()
```

这段代码验证「规范化能消除环境噪声」：地址、临时路径、时间戳被替换成固定标记。预期结果是同一 bug 在不同运行下得到相同字符串；如果规范化过度（例如把所有数字都替换掉），又会把真实差异抹平。规范化的边界应由「规范是否保证该字段」决定，而不是由「看起来烦不烦」决定。

### oracle 的边界不是「对/错」两态

真实 oracle 往往返回三态：通过、失败、未知。未知不是失败，也不是通过；它是「这次没有足够信息判断」。例如超时、参考实现崩溃、输入超出可移植子集，都应归为未知并单独计数。把未知强行归入通过，会制造假接受；归入失败，会制造假拒绝。三态计数能让团队看到「比较覆盖率」，而不是只看到「零 bug」。

### oracle 的成本模型

oracle 越强，单次判断越贵；fuzz 的吞吐越低。工程上要按「每个 bug 的期望成本」选 oracle，而不是盲目追求最强：

| oracle | 单次成本 | 发现能力 | 适合 |
|:--|:--|:--|:--|
| 崩溃/超时 | 极低 | 硬失败 | 大规模持续 fuzz |
| 幂等/往返 | 低 | 结构性 bug | PR 门禁 |
| 参考解释器 | 中 | 语义 bug | nightly |
| 多编译器差分 | 高 | 实现相关 bug | 发布前 |
| SMT/证明 | 极高 | 全输入 | 关键模块 |

成本不只是 CPU。维护参考实现、处理假阳性、解释报告都要人力。一个「单次 1 毫秒、误报率 30%」的 oracle，实际价值可能低于「单次 10 毫秒、误报率 1%」的 oracle，因为后者不需要人来 triage。先算「每小时能确认多少真 bug」，再决定是否加机器。

### 比较粒度：输出、AST 还是 token

差分比较可以在不同粒度上做：

- **字节级**：比较原始 stdout。简单，但对格式、空格、地址敏感。
- **token 级**：把输出切成 token 再比。能忽略空白，但仍受措辞影响。
- **语义级**：解析输出成 AST/数值再比。最稳，但需要解析器，且解析器本身可能错。
- **性质级**：不比较完整输出，只比较某个投影（如「是否抛异常」「返回值的符号」）。最便宜，但可能漏掉投影之外的差异。

选择粒度时要问「我想抓的 bug 会改变哪一层」。优化器 bug 通常改变数值/AST，用语义级；诊断信息 bug 改变 token，用 token 级；崩溃用退出码级。不要把「字节级不一致」直接当 bug，先看它是否在规范保证的观察范围内。

### oracle 与规范的差距

oracle 编码的是「我们以为的规范」，不是规范本身。两者之间常有三种差距：规范没写的边界（实现自由）、规范写了但没实现（工具 bug）、以及规范写了但测试没覆盖（oracle 盲区）。差分测试最容易掉进第一种：把实现自由当 bug。解决办法不是「读更多规范」，而是「把不确定的构造排除出测试子集」，并在文档里写明排除理由。

对编译器，一个实用的子集是：固定宽度整数、无 UB、无未指定顺序、无浮点、无实现定义构造。子集越小，oracle 越可信；代价是覆盖变窄。工程上可以分层：PR 跑「小可信子集」，nightly 跑「大子集 + 人工 triage」。不要用一个 oracle 同时追求「覆盖全部 C」和「零误报」。

### oracle 的失败预算

oracle 也会失败：参考实现崩溃、输出解析失败、超时。对「oracle 失败」要设预算：单次运行允许多少比例未知、连续多少次未知后暂停、哪些未知可以重试。没有预算，一个坏掉的参考实现会让 fuzzer 把所有输入标成「未知」，看起来跑得很忙，实际没有比较。把未知比例作为监控指标，比看「执行数」更能发现 oracle 退化。

### 把 oracle 写进文档

oracle 的定义应写进测试文档，而不是只存在于代码里。至少要写：比较哪些观察、忽略哪些字段、异常如何编码、未知如何计数、哪些输入被排除。这样 review 的人才能判断「这个 oracle 是否适合当前目标」，而不是只看它「跑通了」。文档与代码不一致时，以文档为准，并补测试锁住行为。

### oracle 也要版本化

oracle 的判定规则会随规范/实现变化。把 oracle 版本写进运行元数据，才能在「三个月后结果不同」时判断是程序变了还是 oracle 变了。对差分 oracle，参考实现的版本同样要记录；升级参考实现后，历史语料应重跑一遍，确认没有把「参考的 bug」当成「候选的 bug」。

### 最后一条：把「没找到」写清楚

fuzz 报告最容易误导人的一句话是「未发现 bug」。应改成「在 N 次执行、M 个输入、K 类 oracle 下未发现新类别；已知未覆盖 X/Y/Z」。把覆盖边界、oracle 边界、资源边界写清楚，「没找到」才是一个有信息量的结论。读者才能判断：是程序稳，还是测试没走到。

## 10.2 覆盖率引导 fuzz：反馈、能量与变异 {#sec-compilers.3.10.2}

盲随机 fuzz 的命中率随输入结构复杂度指数下降。一个 100 字节的输入有 256 的 100 次方种可能，随机撞到一个合法 JS 程序几乎不可能。覆盖率引导（coverage-guided）fuzz 的核心是：把「执行到新代码」当作奖励，优先变异那些能带来新覆盖的输入。它不保证找到 bug，但把搜索引向「程序还没被探索的部分」。

<pre class="layout">
            ┌─────────────────────────────────────────────┐
            │                 corpus（语料）               │
            │   seed1  seed2  ...  seedN（含新覆盖的输入） │
            └───────────────┬─────────────────────────────┘
                            │ 选择（energy / 稀有度）
                            ▼
                    ┌───────────────┐
                    │   mutate      │  位翻转/算术/拼接/字典/结构变异
                    └───────┬───────┘
                            │ 新输入
                            ▼
                    ┌───────────────┐
                    │   execute     │  ← 超时/内存/崩溃边界
                    └───────┬───────┘
                            │ 观察：输出、退出码、覆盖率位图
                            ▼
                    ┌───────────────┐
                    │   feedback    │  新边？新值？新错误？
                    └───────┬───────┘
                            │ 是：加入 corpus；否：丢弃或降权
                            └──────────► 回到 corpus
</pre>

读图：闭环里有三个可能失效的环节。变异不产生合法输入，执行被超时/资源限制打断，反馈把「新」定义得太粗或太细。任何一环坏了，corpus 都会停止增长，fuzzer 进入「跑得很快但什么也没发现」的状态。覆盖率只是反馈的一种；对编译器，错误类别、优化 pass 命中、输出哈希都可以作为反馈。

覆盖率的粒度决定成本。基本块覆盖（block coverage）便宜但粗糙；边覆盖（edge coverage）能区分「同一个块从不同前驱进入」；路径覆盖最精确但数量爆炸。工业 fuzzer 常用边覆盖加命中计数（8 位计数器），再把 `(edge_id, count_bucket)` 哈希成一个特征。LLVM 的 SanitizerCoverage 提供 `trace-pc-guard`、`inline-8bit-counters` 等模式，libFuzzer 用它们维护 corpus。

| 反馈 | 特征 | 优点 | 缺点 |
|:--|:--|:--|:--|
| 基本块 | 是否执行过 | 便宜、稳定 | 丢失路径差异 |
| 边 | 前驱→后继 | 常用折中 | 不区分循环次数 |
| 边+计数桶 | 执行次数分桶 | 能区分浅循环 | 特征膨胀 |
| 值剖面 | 比较操作数的差值 | 帮助绕过 magic 值 | 噪声大、依赖插桩 |
| 优化 pass 命中 | 哪个规则触发 | 贴近编译器 bug | 需要自定义插桩 |

能量（energy）决定「从语料里挑谁、给它多少次变异」。均匀选择会让语料被大量「容易但无用」的输入占据；AFL 系列用「稀有边优先」「执行时间短优先」「新覆盖优先」等策略。一个简单的近似是：给每个 seed 一个权重，权重与「它独有特征的稀有度」成正比，与「它最近被选中的次数」成反比。能量分配不是理论最优问题，而是工程调参；关键是别让 corpus 被同一类输入垄断。

变异算子要与输入结构匹配。字节级算子包括位翻转、字节替换、算术加减、插入/删除、拼接（splice）；结构化算子包括替换子树、复制子树、交换操作数、包裹新运算。 `fuzz_lab.py` 走的是后一类：它把表达式解析成 AST，随机替换节点、复制节点、包裹新运算，再序列化回字符串。这样每次变异都产生合法表达式，解析失败率为 0，fuzzer 的时间不会被语法错误吃掉。

```python
def mutate(node, rng):
    nodes = collect(node)
    choice = rng.random()
    if choice < 0.5:
        target = rng.randrange(len(nodes))
        return replace_node(node, target, rand_expr(2, rng))
    if choice < 0.75:
        target = rng.randrange(len(nodes))
        return replace_node(node, target, rng.choice(nodes))
    if choice < 0.9:
        target = rng.randrange(len(nodes))
        op = rng.choice(["add", "sub", "mul", "div"])
        return replace_node(node, target, (op, copy.deepcopy(nodes[target]), rand_atom(rng)))
    target = rng.randrange(len(nodes))
    return replace_node(node, target, ("num", rng.randrange(-2, 8)))
```

这段代码验证「结构变异能保持语法合法」：所有替换都发生在 AST 节点上，序列化后的字符串必然能被同一个 parser 接受。预期结果是 `parse_failures=0`；本机 4000 次执行确实是 0。换成字节级变异，解析失败率通常远高于 50%，这就是结构化输入的价值（10.6 继续）。

覆盖率高不等于更容易找到 bug。一个程序可能有 90% 的边被覆盖，但触发 bug 需要「特定值组合」而不是「新边」。值剖面（value profile）试图补这一点：记录比较指令两侧的差值，把「接近相等」的输入也当作新特征。它对 `if (x == 0xdeadbeef)` 这类 magic 值有效，但对「两个变量之和等于 7」这种关系无能为力。另一种补充是「定向 fuzz」：把目标函数/分支作为反馈，而不是全程序覆盖。

本机实验的计数如下（固定 seed=20261020，4000 次）：

```text
[iter 4] NEW BEST zero_div: '(0 / x)' x=0 expected=ERR actual=0
[iter 12] NEW BEST div_self: '(x / x)' x=0 expected=ERR actual=1
[iter 1000] corpus=417 features=574 mismatches=79 classes=2
[iter 2000] corpus=551 features=717 mismatches=207 classes=2
[iter 3000] corpus=591 features=757 mismatches=315 classes=2
[iter 4000] corpus=617 features=783 mismatches=414 classes=2
```

读这组数：前 12 次就找到了两类 bug，后面的 3988 次主要在做覆盖探索。语料从 12 个种子增长到 617，特征从初始的一小部分增长到 783；不匹配数从 79 涨到 414，说明同一类 bug 被大量不同输入重复触发。覆盖率增长与 bug 发现并不同步：bug 在很早就出现，覆盖率继续涨只是说明生成器在探索新形状。评估 fuzzer 时要把「首次发现时间」和「总执行数」分开看。

覆盖率引导也有反模式。第一，把「执行过的输入」全塞进 corpus，导致语料膨胀、选择变慢；应做 corpus minimization（10.6）。第二，把「新特征」定义得太细（例如把完整调用栈当特征），导致每个输入都是「新」的，反馈失去区分度。第三，只奖励「新边」而不奖励「新错误」，导致 fuzzer 反复撞同一个崩溃；应把去重后的错误类别也纳入反馈。

### 插桩、forkserver 与持久模式

覆盖率不是免费的。`trace-pc-guard` 在每个基本块插一个回调，运行时把 `guard id` 写进位图；`inline-8bit-counters` 用内联计数器，开销更低但需要定期清零。位图大小通常是 64K 或 1M，哈希冲突会让不同边共享同一个槽；冲突太多时覆盖率会失真，表现为「新输入没有新特征」。

进程启动成本会吃掉 fuzz 的吞吐。每次 `fork+exec` 启动一个编译器，可能花几十毫秒，而执行一次小输入只要几毫秒。forkserver 解决这个问题：父进程先完成初始化，再 `fork` 出子进程执行输入；子进程共享父进程的内存映射，启动成本降到微秒级。持久模式（persistent mode）更进一步：在同一个进程里循环执行多个输入，只在状态需要重置时重启。代价是 target 必须无全局状态泄漏，否则输入之间会互相污染。

| 模式 | 启动成本 | 隔离性 | 适用 |
|:--|:--|:--|:--|
| fork+exec | 高 | 最好 | 任意 target |
| forkserver | 低 | 好 | 大多数 CLI |
| persistent | 最低 | 差（状态泄漏） | 无全局状态的库 |
| in-process | 零 | 无 | 纯函数、可重置 |

本实验没有用真正的覆盖率插桩，而是用「AST 形状特征」当反馈：每个节点的 `(kind, child kinds, depth)` 是一个特征。它的优点是零依赖、可读；缺点是它不是程序覆盖率，不能直接和 AFL/libFuzzer 的数字比较。读实验结果时要把这一点记住：`features=783` 是「见过的 AST 形状数」，不是「执行过的边数」。

### 能量调度：一个可实现的近似

设 seed 集合为 S，每个 seed s 有「稀有特征集合」R(s) 和「最近被选次数」n(s)。一个简单的能量函数是：

```text
energy(s) = (1 + |R(s)|) / (1 + n(s))
```

每次按 energy 归一化后的概率选 seed，选中后给它 k 次变异（k 与 energy 成正比）。稀有特征可以通过「统计每个特征被多少 seed 覆盖」得到：只被一个 seed 覆盖的特征最稀有。这个近似不需要复杂的排队论，却比均匀选择更偏向「独特」的输入。缺点是它会过度偏爱长输入（长输入特征多），需要用长度归一化或设置上限。

能量调度只影响「先试谁」，不改变「能试什么」。如果变异算子根本产生不了 `/`，再多能量也找不到除法 bug。调优顺序应是：先确认变异算子覆盖目标语法，再调能量，最后调反馈粒度。反过来做，通常是在给一个不会生成合法输入的 fuzzer 加速。

覆盖率数字不能跨工具比较。AFL 的「边数」、libFuzzer 的「特征数」、本实验的「AST 形状数」是三种不同的度量；把它们放在一张表里排名没有意义。能比较的是同一工具、同一 target、同一 seed 下的趋势：覆盖率是否在增长、首次发现时间是否变短、每秒执行数是否下降。跨工具只比较「是否找到已知 bug」和「找到用了多久」。

### 语料选择的一个实现

把「稀有特征」落成代码，只需要两个字典：`feature_to_seeds` 和 `seed_to_features`。每次发现新特征，更新两个字典；选择 seed 时，按「它独有的特征数 / 被选次数」加权。这个实现不需要全局排序，每次选择 O(特征数)，对几千个 seed 足够快。真正的 fuzzer 会更复杂（队列、功率调度、确定性重放），但核心思想相同：让「独特」的输入获得更多变异机会。

### seed 的最小集合

seed 不是越多越好。一个 1000 个文件的 seed 目录会让启动变慢、选择变慢，而其中大多数输入共享同一组特征。做法与 corpus minimization 相同：按特征做集合覆盖，保留「每个产生式/每个 pass/每个错误分支至少一个」的最小集合。目标不是「覆盖所有输入」，而是「覆盖所有起点类型」。

### 反馈的归一化

覆盖率位图也要归一化。不同进程的 `guard id` 可能因链接顺序变化，同一份代码重新编译后位图对不上。持久化覆盖率时，应存「特征集合的哈希」或「符号化后的边」，而不是原始位图。否则换一次构建，历史语料就被判为「全新」，corpus 会爆炸。

插桩本身有成本。边覆盖通常带来 10%–30% 的减速，值剖面更高；持久模式能抵消一部分，但不能抵消内存增长。选反馈时先测「每秒执行数」，再决定是否值得加更细的特征；一个让吞吐下降 10 倍、只多覆盖 1% 的特征，通常不划算。

覆盖率引导不是魔法。它把「随机」变成「有偏随机」，但没有改变「需要 oracle 判定」这一事实。一个覆盖率 99% 的 fuzzer 仍然可能对某个错误结果视而不见，因为它的 oracle 只看崩溃。评估 fuzzer 时，先看 oracle，再看覆盖率。

## 10.3 差分测试：编译器、解释器与优化级别 {#sec-compilers.3.10.3}

差分测试把「两个实现应该一致」变成 oracle。编译器领域有几组天然的对比对象：

| 对比 | 能抓 | 主要污染源 |
|:--|:--|:--|
| 解释器 vs 编译器 | 代码生成/优化 bug | 解释器与编译器共享前端 bug |
| `-O0` vs `-O2` | 优化 bug | UB 在两边都「合法」地不同 |
| clang vs gcc | 实现相关 bug、ABI | 未指定/实现定义行为 |
| 本机 vs 交叉目标 | 位宽/端序/对齐 | 目标相关合法差异 |
| 旧版本 vs 新版本 | 回归 | 规范变化、库变化 |

差分 oracle 的黄金规则是「只比较规范保证的观察」。对 C 程序，浮点结果、结构体填充、求值顺序、`char` 符号性都可能是合法差异；把它们纳入比较，会制造大量假阳性。对编译器测试，常见的做法是先把程序限制在一个「可移植子集」：固定宽度整数、无 UB、无未指定顺序、禁用浮点或固定舍入模式。子集越小，差分越可信。

::: ex 例 10.3.1 · 优化器与解释器的差分 {#ex-compilers.3.10.3.1}
实验里的参考实现是 `eval_ast`（直接解释 AST），候选是 `eval_ast(optimize(ast))`。oracle 对每个环境 x 比较返回值；异常统一记作 `ERR` 再比较。这样既比较了正常值，也比较了「是否抛异常」这一观察。

对 `(x / x)` 在 x=0：参考是 `ERR`，候选是 `1`，不一致。对 `(0 / x)` 在 x=0：参考 `ERR`，候选 `0`，不一致。两个 bug 都来自优化器的「代数化简」规则，而不是解释器。若参考实现也用了同一套化简，差分就会通过——这是相关性盲点。
:::

相关性是差分测试最大的敌人。两个实现共享前端、共享库、共享规范理解，就会在同一个地方一起错。缓解手段是「多角化」：用不同团队/不同语言的实现、用解释器而不是另一个编译器、用随机化的参考语义（metamorphic testing）。对编译器，另一个有效手段是「自举差分」：同一编译器在不同优化级别/不同目标上编译同一程序，比较行为；它抓不到前端 bug，但能抓后端与优化 bug。

差分测试还要处理「非确定性」。同一程序多次运行可能因为地址布局、线程调度、时间、随机数而不同。比较前要固定环境：ASLR 关闭、时区/locale 固定、随机种子固定、并发度固定。对编译器本身，输出文件里可能包含时间戳或临时路径；比较前要规范化，或者只比较可执行文件的行为而不是字节。

差分测试与 UB 的关系需要特别小心。若程序有 UB，`-O0` 与 `-O2` 的差异不构成编译器 bug；两边都可以做任何事。第 9 章的规则在这里同样适用：先确保测试程序在契约内，再把差异当 bug。工业编译器 fuzz 常用「UB 筛查」：用 UBSan 跑一遍，若报告 UB 就丢弃该用例，不进入差分比较。这会降低吞吐，但能避免把 UB 噪声当 bug。

本机实验的差分结果（exact oracle，4000 次）：

```text
seed=20261020 iters=4000 oracle=exact
executions=4000 parse_failures=0 corpus=617 features=783 rule_hits=47883
mismatches=414 other_classes=3 unique_after_dedup(source)=2
  div_self: minimized='(x / x)' env x=0 expected=ERR actual=1
  zero_div: minimized='(0 / x)' env x=0 expected=ERR actual=0
```

414 次不匹配只归并成 2 类，说明「同一 bug 会被大量输入重复触发」。如果按每次不匹配建 issue，团队会被 414 条重复报告淹没；如果只按「异常类型」归并，2 类又会变成 1 类（10.5 与 10.8）。去重键的选择直接决定「看到几个 bug」。

### 一条可执行的差分流水线

把差分测试落成流水线，至少要六步。少一步，结果就难以复现或难以解释。

1. **构建**：同一份源码，用不同配置生成可执行文件（解释器、`-O0`、`-O2`、另一编译器）。
2. **筛选**：用 UBSan 或静态检查丢弃 UB/未指定行为的输入，避免把合法差异当 bug。
3. **执行**：固定环境（locale、时区、ASLR、随机种子），记录退出码与输出。
4. **规范化**：按 10.1 的规则替换地址、路径、时间戳。
5. **比较**：先比退出码，再比规范化输出；失败类别不同也算差异。
6. **归并**：按最小化源码或故障类别去重，保留代表与完整命令。

```bash
set -eu
CC=clang
for opt in -O0 -O2; do
  "$CC" -std=c17 -Wall -Wextra -Werror "$opt" -g \
    tests/expr.c -o "build/expr$opt"
done
./build/expr-O0 > build/out-O0.txt 2>&1 || true
./build/expr-O2 > build/out-O2.txt 2>&1 || true
diff -u build/out-O0.txt build/out-O2.txt || echo "differential mismatch"
```

这段脚本验证「同一源码、两个优化级别、比较输出」；把 `tests/expr.c` 换成你的目标源文件即可运行。预期结果是：无差异时 diff 退出 0；有差异时打印 diff 并输出 `differential mismatch`。`|| true` 是故意的：测试程序可能以非零退出，流水线不应该在第一行就中断；真正的判定交给 diff 与后续归并。

### 假阳性从哪里来

差分测试的假阳性几乎都来自「把规范允许的差异当成 bug」。常见四类：

| 来源 | 例子 | 处理 |
|:--|:--|:--|
| UB | 有符号溢出、越界 | UBSan 筛查，丢弃用例 |
| 未指定行为 | 实参求值顺序、`f()+g()` | 限制语法/拆语句，或只比较集合 |
| 实现定义 | `char` 符号、右移负数 | 固定平台/编译选项，或排除该构造 |
| 环境 | 地址、时间、locale、文件顺序 | 规范化、固定环境 |

第四类最容易被忽略：同一程序在两次运行中输出不同，可能只是因为哈希表遍历顺序不同。差分测试要求「确定性」，而确定性本身需要设计：固定哈希种子、避免并发、避免依赖文件系统顺序。把不确定性当成 bug 报，会让团队对差分结果失去信任。

### 变形测试：没有参考实现时怎么办

不是所有语言都有独立解释器。变形测试（metamorphic testing）用「输入之间的关系」代替「输入到输出的绝对映射」。例如：

- 对表达式 e，`eval(e + 0) == eval(e)`。
- 对程序 P，给一个不影响结果的注释/空语句，行为不变。
- 对编译器，`-O0` 与 `-O2` 的可观察行为一致（在无 UB 前提下）。
- 对优化器，`opt(opt(e)) == opt(e)`（幂等）。

变形关系比参考实现弱，但不需要第二套实现。它的风险是「关系本身不成立」：`eval(e + 0) == eval(e)` 在浮点、溢出、异常场景下可能不成立。写变形关系时，要像写规范一样给出前提。

### 差分与回归的结合

差分测试最适合做「回归放大」：修一个 bug 后，把最小反例加入差分语料，每次 CI 都跑一遍 `-O0` 与 `-O2` 的对比。这样修复不会悄悄回退。反过来，差分也可以用来「发现回归」：同一程序在旧版本与新版本上行为不同，且旧版本符合参考实现，就说明新版本退化。

把差分纳入 CI 时，要区分「已知差异」与「新差异」。已知差异可能是规范允许的实现差异，应进入基线并写明理由；新差异才让 job 变红。基线不能无限增长，否则差分退化成「什么都不报」。一个可操作的上限是「基线条目不超过测试数的 5%」，超过就说明差分粒度或测试子集需要调整。

### 跨目标差分

同一份源码在不同目标上编译，行为可能合法地不同：`int` 宽度、字节序、`char` 符号、对齐、浮点格式。跨目标差分只应比较「规范保证与目标无关」的部分，例如「程序是否接受输入」「抽象值是否相同」。地址、结构体大小、诊断文本都不应比较。

一个常见的跨目标 bug 是「代码生成假设了某种对齐」。在 x86-64 上未对齐访问通常可用，在 ARM64 上可能触发异常或性能惩罚；如果编译器把「未对齐指针」当「已对齐」生成向量指令，就会在 ARM64 上崩溃。跨目标差分能抓到这类 bug，但需要目标模拟器或真机，成本高于同机差分。

### 差分的观察文件

除了 stdout，编译器还会生成目标文件、汇编、诊断。差分可以比较这些产物，但要先规范化：目标文件含时间戳/路径，汇编含寄存器分配差异，诊断含列号。对优化器 bug，比较 `-S` 生成的汇编通常比比较可执行文件更敏感；对代码生成 bug，比较反汇编/行为更直接。选择观察文件时，问「这个 bug 会在哪一层留下痕迹」，不要所有层都比较。

### 差分的报告

一份可行动的差分报告应包含：两边的命令行、退出码、规范化前后的输出、差异位置、最小化输入、以及「是否为已知差异」。只贴一段 diff 不够，因为读的人不知道两边是怎么编的。报告还应标注「置信度」：是规范保证的差异，还是可能受 UB/未指定行为影响。置信度低的报告先进入 triage，不直接建 bug。

### 诊断也要差分

编译器 bug 不只在运行结果，也在诊断：该报错的不报、错误位置偏移、警告文案误导。诊断差分比输出差分难，因为文案会变。可行做法是只比较「诊断数量 + 严重级别 + 主位置的行号」，忽略具体措辞；或者用结构化诊断（JSON）比较字段。对 agent 生成的代码，诊断差分能发现「编译通过但语义错」之前的一层问题。

### 差分结果的置信度

给每条差异标置信度：高（规范保证、无 UB、可复现）、中（可能受实现定义影响）、低（依赖未指定行为/环境）。只有高置信度差异直接进 bug tracker；中低先人工 triage。置信度不是拍脑袋，而是由「输入是否在可移植子集」「是否通过 UBSan」「是否在多平台复现」三个事实决定。

### 差分的成本曲线

差分测试的成本随「对比对象数量」线性增长，收益却递减。两个对比（解释器 vs 编译器）通常能抓到大部分语义 bug；再加 `-O0` vs `-O2` 能抓优化 bug；再加另一个编译器能抓实现相关 bug，但也会带来更多假阳性。不要一开始就上四五个对比，先把两个对比的误报压到可接受，再扩展。

## 10.4 属性测试：生成器、收缩与不变量 {#sec-compilers.3.10.4}

属性测试（property-based testing）不写「输入 3 应输出 5」，而写「对所有输入，某个性质成立」。框架负责生成输入、在失败时收缩（shrink）到最小反例。对编译器，最有用的性质往往不是「输出等于某个值」，而是「两个阶段的结果一致」：

| 性质 | 形式 | 抓什么 |
|:--|:--|:--|
| 语义等价 | `eval(opt(p)) == eval(p)` | 优化 bug |
| 幂等 | `opt(opt(p)) == opt(p)` | pass 不稳定、重复应用 |
| 往返 | `parse(print(ast)) == ast` | 解析/打印不一致 |
| 确定性 | 同输入两次编译输出相同 | 非确定性、哈希顺序 |
| 单调 | 增加信息不减少已推导事实 | 分析器精度回归 |

生成器的质量决定属性测试的上限。一个只会生成 `x + 1`、`2 * x` 的生成器，永远碰不到除零、溢出、别名这些边界。好的生成器要控制三件事：语法合法性（只生成可解析的输入）、规模分布（小输入多、大输入少，避免一上来就超时）、边界覆盖（常量 0、正负 1、类型极值、空结构、重复子树）。递归生成器还要限制深度，否则会生成指数级大的树。

收缩器的质量决定「失败是否可读」。一个 200 节点的表达式失败后，如果收缩器只做「删除最后一个字符」，报告仍然不可读；如果做「用子树替换整棵树」「把子树替换成常量」「删除 token 块」，就能缩到 `(x / x)` 这种一行反例。收缩的本质是「在保持失败的前提下，按偏好序尝试更小的候选」；偏好序通常是「节点数少 > 常量小 > 字符少」。

```python
import random
import fuzz_lab as f

rng = random.Random(7)
checked = 0
bad = 0
for _ in range(200):
    node = f.rand_expr(3, rng)
    x = rng.choice(f.ENVS)
    try:
        expected = f.eval_ast(node, x)
    except ZeroDivisionError:
        expected = "ERR"
    try:
        actual = f.eval_ast(f.optimize(node), x)
    except ZeroDivisionError:
        actual = "ERR"
    if expected != actual:
        bad += 1
        if bad <= 3:
            print("counterexample", f.to_src(node), "x=", x,
                  "expected=", expected, "actual=", actual)
    checked += 1
print("checked", checked, "failures", bad)
```

这段代码验证「属性测试能在不理解优化器的前提下找到 bug」：它只检查语义等价，不关心优化器内部规则。本机输出如下：

```text
counterexample (-1 - ((x - x) / (x - x))) x= 1 expected= ERR actual= -2
counterexample (((x / x) * x) * ((0 + 3) - (x - x))) x= 0 expected= ERR actual= 0
counterexample ((0 / 0) - 0) x= -1 expected= ERR actual= 1
checked 200 failures 5
```

200 个随机表达式里 5 个失败，比例不低，因为优化器的两条错误规则很容易被触发。属性测试的价值在于「自动生成反例」；它的局限在于「性质本身可能错」。如果性质写成 `eval(opt(p)) >= 0`，就会把合法的负结果当失败；如果性质写成「两边都抛异常就算过」，就会漏掉真正的 bug。性质是 oracle 的一种，仍然需要审查。

属性测试与 fuzz 的边界很模糊：都用生成器，都用 oracle，都可能收缩。区别在「输入空间是否由语法定义」和「失败判定是否是全局性质」。工程上不必纠结名词；把生成器、oracle、收缩器三件事拆开，各自测试，才是可维护的做法。

### 生成器的规模分布

生成器最容易犯的错是「均匀随机深度」。如果深度在 0–10 均匀选，大多数节点会落在深层，输入规模迅速膨胀，执行时间被大输入吃掉。更好的分布是「小输入多、大输入少」：例如 70% 深度不超过 2，25% 深度 3–4，5% 深度至少 5。这样既能覆盖边界，又不会让平均执行时间失控。

```python
import random

def pick_depth(rng):
    r = rng.random()
    if r < 0.70:
        return rng.randint(0, 2)
    if r < 0.95:
        return rng.randint(3, 4)
    return rng.randint(5, 7)
```

这段代码验证「深度分布可控」：大多数样本是小树，少数是深树。预期结果是平均节点数远小于「均匀 0–7」的分布，同时仍能生成足够深的边界用例。生成器还应对「常量集合」做偏置：0、1、-1、类型极值出现频率应高于普通随机整数，因为边界 bug 更容易被它们触发。

### 收缩的偏好序

收缩不是「越小越好」，而是「按可读性排序」。同一个失败可能有多个最小候选：`(x/x)`、`(0/x)`、`((x)/(x))`。偏好序可以是：

1. AST 节点数少。
2. 嵌套深度浅。
3. 常量绝对值小。
4. 字符数少。
5. 保留原始运算符（不引入新运算符）。

最后一条常被忽略：收缩器如果把 `a / b` 换成 `a * b` 来减小常量，就可能改变 bug 类别。好的收缩器只做「删除/替换为更简单常量」，不引入新的语义构造；如果必须引入，要用失败签名确认类别不变。

### 属性的强度

| 性质 | 强度 | 误报风险 | 适合阶段 |
|:--|:--|:--|:--|
| 不崩溃 | 弱 | 低 | smoke |
| 幂等 | 中 | 低 | 优化 pass |
| 语义等价 | 强 | 中（依赖参考） | 优化器 |
| 往返 | 强 | 低（同实现） | parser/printer |
| 规范断言 | 最强 | 高（规范可能写错） | 关键模块 |

从弱到强排 CI：smoke 用「不崩溃」，PR 用「幂等 + 往返」，nightly 用「语义等价」。不要一上来就用最强性质，否则假阳性会把流水线拖红，团队会关掉它。

### 生成器的可复现性

属性测试的失败必须可复现。生成器要接受显式 seed，并把「第几个样本、生成参数、收缩历史」写进报告。否则开发者拿到一个「`x / x` 失败」的报告，无法知道是哪个 seed 生成的、能否再跑一次。可复现的生成器还应避免依赖 Python 的哈希顺序（`set` 遍历顺序）和全局随机状态；用独立的 `random.Random(seed)`，每次测试重新创建。

### 生成器与收缩器的接口

生成器和收缩器应共享同一个「输入表示」。如果生成器产 AST、收缩器却按字符串删字符，收缩就会频繁产生语法错误，效率极低。正确做法是：生成器产 AST；收缩器在 AST 上工作；序列化只在「报告/持久化」时发生。需要字符级缩减时，先把 AST 打印成文本，再让字符级收缩器处理，最后重新解析验证。

接口还应暴露「大小度量」。收缩器需要知道「哪个候选更小」，而「小」可能是节点数、深度、常量绝对值、字符数的组合。把度量做成可配置的偏好序，而不是硬编码在递归里，能让同一套收缩器服务不同语言。

### 属性测试的 seed 管理

属性测试也应固定 seed，并把失败的 seed 写进回归。与 fuzz 不同的是，属性测试的样本数通常较少（几百到几千），所以「每个 seed 都记录」是可行的。CI 可以每天换一个 seed 跑，周再把所有失败 seed 固化；这样既有随机探索，又有稳定回归。

### 属性的命名

给属性起一个能搜索的名字，例如 `opt_semantics_preserved`、`parse_print_roundtrip`。失败报告里带属性名，团队可以用它查历史 issue、找相关代码。不要把属性写成匿名 lambda；匿名属性在报告里只剩一行断言，无法归类。

属性失败后的收缩，也要保持「属性仍失败」，而不是「程序仍崩溃」。这两者不同：一个违反语义等价的反例，收缩后可能变成一个崩溃，虽然也是失败，但根因变了。把属性谓词作为收缩的 `fail`，而不是「非零退出」，才能保证收缩后的反例仍说明同一个问题。

属性测试的通过率也要看。一个属性如果 90% 的样本都失败，说明它太强或生成器太偏，报告会被噪声淹没；如果 0.01% 失败，说明它可能太弱或生成器没覆盖边界。把失败率当成调参信号：既不要 0，也不要 0.5。

生成器还应支持「定向生成」：给定一个目标分支/函数，生成能走到它的输入。定向生成比盲生成更容易触发深层 bug，但需要程序分析（覆盖率/符号执行）配合。第 11 章会把符号执行展开；本章只需知道「生成器可以有目标」，不必完全随机。

## 10.5 缩减、去重与回归 {#sec-compilers.3.10.5}

找到一个失败输入只是开始。一个 200 节点的表达式、一个 3 KB 的源文件、一个 10 MB 的二进制，直接贴进 issue 没人能读，也很难判断根因。缩减（reduction）的目标是：在保持「同一个失败」的前提下，把输入变得尽可能小、尽可能可读。去重（dedup）的目标是：把大量「同一个 bug 的不同触发」合并成一个问题，同时不把不同 bug 合掉。

::: def 定义 10.5.1 · 最小失败输入 {#def-compilers.3.10.5.1}
给定失败谓词 `fail: Input -> bool`（输入触发目标 bug 返回真），输入 i 是「最小」的，若 `fail(i)` 为真，且不存在更小的 i' 使 `fail(i')` 为真。这里的「更小」需要定义：常见的有字符数、token 数、AST 节点数、以及「可读性偏好」（少量嵌套优先）。

最小性依赖 `fail` 的定义。若 `fail` 只要求「程序崩溃」，缩减可能把「除零」换成「空指针」，bug 类别变了；若 `fail` 要求「同一个错误类别 + 同一个顶层栈帧」，缩减才能保持根因。工程上应把 `fail` 写成「原始失败签名不变」，而不是「只要还失败」。
:::

最常用的缩减算法是 delta debugging（ddmin）。它把输入切成 n 块，尝试删除每一块；若删除后仍然失败，就接受更小的输入并把 n 调小；否则增大 n，直到无法再删。对 token 序列，ddmin 最坏需要 O(n^2) 次执行，常见情况下接近 O(n log n)；对 AST，可以先把「删除子树」「替换子树」作为更高层的算子，再用 token ddmin 收尾。

```python
def ddmin(src, fails):
    toks = tokenize(src)
    n = 2
    while len(toks) >= 2:
        chunk = max(1, (len(toks) + n - 1) // n)
        reduced = False
        for start in range(0, len(toks), chunk):
            cand = "".join(toks[:start] + toks[start + chunk:])
            if cand and fails(cand):
                toks = tokenize(cand)
                n = max(2, n - 1)
                reduced = True
                break
        if not reduced:
            if n >= len(toks):
                break
            n = min(len(toks), n * 2)
    return "".join(toks)
```

这段代码验证 ddmin 的骨架：每次只接受「仍然失败」的更小候选，失败谓词由调用者提供。预期行为是对可删减的输入快速收敛；对「删除任何 token 都会变成语法错误」的输入，它会退化成逐个尝试，最终停在局部最小。ddmin 不保证全局最小，也不保证可读；它保证的是「在尝试过的候选里没有更小的」。

本实验的缩减器比 ddmin 多两步：先反复用「仍然失败的最小子树」替换整棵树，再尝试把每个子树替换成 `x`、`0`、`1`，最后才做 token ddmin。这样能从 `(2 * ((x) - (x / x)))` 直接收缩到 `(x / x)`，而不是逐个删 token。真实结果如下：

```text
div_self: minimized='(x / x)' env x=0 expected=ERR actual=1
zero_div: minimized='(0 / x)' env x=0 expected=ERR actual=0
```

两个最小反例都只有 5 个字符（含括号），一眼能看出根因：一个是「同式相除化简为 1」，一个是「0 除以任何式化简为 0」，都没有检查除数是否可能为 0。缩减的价值不只是「短」，而是把「414 次不匹配」变成两个可读的规则反例。

去重比缩减更容易出错。常见键有：

| 键 | 合并依据 | 风险 |
|:--|:--|:--|
| 完整栈哈希 | 崩溃栈完全相同 | 优化/内联导致同一 bug 栈不同，去重失败 |
| 顶层栈帧 | 出错函数相同 | 同一函数里的不同 bug 被合并 |
| 异常类型 | `ZeroDivisionError` 等 | 不同根因同一症状被合并 |
| 最小化源码 | 缩减后输入相同 | 缩减器不稳定时同一 bug 去重失败 |
| 故障类别 | `div_self` / `zero_div` | 需要人工定义类别，可能过粗 |

实验里两个 bug 的症状完全相同：参考实现都是 `ERR`，候选都返回值。如果按「异常类型」去重，它们会被合成一个；按「最小化源码」去重，才是两个。`--dedup=symptom` 的真实输出是 `unique_after_dedup(symptom)=1`，而默认的 source 键给出 2。这个对比说明：**去重键是 bug 模型的一部分，不是后勤细节**。

```text
seed=20261020 iters=4000 oracle=exact
executions=4000 parse_failures=0 corpus=617 features=783 rule_hits=47883
mismatches=414 other_classes=3 unique_after_dedup(symptom)=1
  div_self: minimized='(x / x)' env x=0 expected=ERR actual=1
  zero_div: minimized='(0 / x)' env x=0 expected=ERR actual=0
```

注意这张表里「unique=1」但下面仍列出两个类：去重计数用的是 symptom 键，列表保留的是内部类别。真实系统里应避免这种不一致：要么按同一键过滤列表，要么在报告里明确「合并后 1 类，包含 2 个根因」。否则读报告的人会以为只有一个 bug。

回归资产至少包含四样：最小输入、触发命令/环境、期望行为、以及「修复前失败、修复后通过」的测试。最小输入要能独立运行，不依赖 fuzz 时的随机语料；触发命令要带 seed、版本、优化级别；期望行为要写「应该抛除零」而不是「输出不为 1」；测试要能在 CI 里以秒级运行。

回归测试本身也要防「假通过」。如果测试只断言「程序不崩溃」，那么把 bug 从「错误结果」改成「另一个错误结果」仍会通过；如果测试只断言「输出等于某个值」，而该值依赖未指定行为，换平台就会红。好的回归测试断言「规范保证的观察」：对本章的优化器 bug，断言「参考与候选在 x=0 时都抛除零」，而不是断言某个具体整数。

### 层级缩减：从 AST 到字符

单一粒度的缩减容易卡住。AST 缩减能快速删掉大子树，但对「同一个 token 重复」无能为力；字符缩减能删掉多余括号，但容易破坏语法。层级缩减（hierarchical delta debugging）把两者结合：先在 AST 上删/换子树，再把结果序列化，最后在 token/字符上做 ddmin。每一层只需要一个「仍然失败」的谓词，层与层之间用序列化/解析衔接。

工业工具走得更远。C-Reduce 对 C 源文件做「删除声明/语句/表达式」「替换标识符」「简化常量」等变换，再用 GCC 的语法检查保证结果仍是合法 C。它能在几小时内把一个几千行的崩溃文件缩到几十行。代价是需要一个「仍然崩溃」的判定，且每步都要编译；对编译器 bug，编译时间就是缩减成本。

缩减的终止条件也要设计。常见做法是「连续 N 轮没有改进就停」或「达到时间上限」。不要追求「绝对最小」：一个 20 行的可读反例，比一个 5 行但依赖未定义行为、难以解释的反例更有价值。缩减的目标是「让人能看懂」，不是「让字符数最小」。

### 去重的评估

去重键没有绝对正确，只有「在这个项目的历史 bug 上表现如何」。可以用一个小标注集评估：取过去 50 个已知根因的 crash，用候选键聚类，算「同一根因被分到同一类」的比例（合并正确率）和「不同根因被分开」的比例（分离正确率）。两个指标都重要：只追求合并会让不同 bug 消失，只追求分离会让同一 bug 刷屏。

| 键 | 合并正确率 | 分离正确率 | 维护成本 |
|:--|:--|:--|:--|
| 栈哈希 | 中 | 高 | 低 |
| 顶层帧 | 高 | 低 | 低 |
| 异常类型 | 高 | 很低 | 低 |
| 最小化源码 | 高 | 高 | 中 |
| 故障类别 | 高 | 中 | 高（要定义类别） |

实验里的两个 bug 是最小反例：`div_self` 与 `zero_div` 的异常类型相同，栈也几乎相同，只有最小化源码不同。用「异常类型」去重会合并，用「最小化源码」去重能分开。真实项目里还要加一层人工复核：自动聚类给出候选，人确认根因，再把确认结果写回标注集，持续校准键。

### 回归测试放在哪里

最小反例放错位置，等于没放。常见三层：

| 层 | 位置 | 运行频率 | 适合 |
|:--|:--|:--|:--|
| 单元测试 | 源码旁 | 每次提交 | 5 行以内的表达式/函数 |
| 集成测试 | tests/ | PR | 需要多文件/多阶段的用例 |
| fuzz 语料 | corpus/regression/ | nightly | 需要随机环境或长输入的用例 |

能用单元测试就不用 fuzz 语料：单元测试快、可读、失败信息直接。只有当最小反例依赖 fuzz 的生成环境（例如需要特定 seed 的随机序列）时，才放进语料。放进去后也要加一个「启动命令 + 期望」，否则语料只是死文件。

### 缩减的时间预算

缩减可能比发现 bug 还慢。每接受一个候选都要重新执行，复杂目标一次几秒，几千次就是几小时。给缩减设时间预算：先做「删大块」的粗缩，几分钟内得到一个可读反例；细缩放到后台，不阻塞 issue 创建。报告里标明「已缩减/未完全缩减」，让读者知道当前反例不是全局最小。

### 缩减后的验证

缩减完成后，必须用原始失败谓词再验证一次，并记录「缩减前/后的失败签名一致」。有时缩减器会接受一个「仍然崩溃但根因不同」的候选；签名比较能发现这一点。签名可以是错误类型 + 顶层帧 + 关键消息，不需要完整栈。验证失败时，回退到上一个候选，而不是发布一个错的反例。

### 去重的假分裂

去重不只会「合并过多」，也会「分裂过多」。同一根因在不同优化级别/不同栈布局下可能产生不同栈哈希，被拆成多个 issue；团队逐个修，最后发现是同一个 bug。缓解办法是同时按「最小化源码」聚类，并在报告里附「相似 issue」链接。人工复核时优先看最小化源码，而不是栈。

### 缩减器的回归

缩减器本身也会退化。有人改了「更小」的偏好序，结果把有意义的反例缩成不可读的片段。给缩减器加回归：输入一个已知失败的长表达式，断言输出仍是同一个失败类别，且节点数不超过阈值。缩减器不是一次性脚本，而是测试基础设施的一部分。

去重键应可解释。一个键如果无法用一句话说明「为什么这两个 crash 是同一个 bug」，就不适合当门禁。最小化源码之所以好用，是因为它直接展示触发条件；栈哈希之所以常用，是因为它便宜且容易解释「同一个崩溃点」。选择键时先问「解释成本」，再问「准确率」。

## 10.6 结构化输入、字典与持久化 {#sec-compilers.3.10.6}

输入结构越强，盲变异的浪费越大。对 JSON、protobuf、ELF、LLVM IR 这类格式，随机改字节通常在第一层解析就失败；fuzzer 的执行预算全花在「报语法错误」上。结构化 fuzz 的思路是：让生成器/变异器理解语法，只产生合法或接近合法的输入。

三种常见做法：

1. **语法生成**：用文法随机推导 AST，再打印成文本。优点是合法率 100%，缺点是需要写生成器、可能重复生成相似结构。
2. **自定义变异**：在 AST/字节码层做替换、插入、删除，再序列化。本章的 `fuzz_lab.py` 属于这一类。
3. **字典辅助的字节变异**：给 fuzzer 一个 token 字典（关键字、操作符、magic 值），让变异更容易拼出合法片段。实现成本最低，但合法率仍有限。

```text
# 表达式语言的字典示例（每行一个 token）
(
)
+
-
*
/
x
0
1
2147483647
```

字典不是语法。它只提高「撞到关键字」的概率，不保证括号配对、操作数齐全。对深度嵌套的格式，字典辅助的字节变异仍会大量产生语法错误；这时应上 grammar fuzzer 或 custom mutator。选择标准是「解析失败率」：如果 fuzz target 的解析失败率超过 80%，先改生成方式，而不是加执行时间。

| 方式 | 合法率 | 实现成本 | 适合 |
|:--|:--|:--|:--|
| 字节变异 | 低 | 最低 | 二进制、无严格语法 |
| 字典辅助 | 中 | 低 | 文本协议、关键字密集 |
| AST 变异 | 高 | 中 | 编译器/解释器 |
| 文法生成 | 最高 | 高 | 深层嵌套语言 |

持久化（persistence）决定 fuzz 能不能跨会话积累。一次 fuzz 运行的语料、崩溃、覆盖位图如果丢了，下一次又从零开始。最小持久化应保存：seed 语料、发现新覆盖的输入、崩溃输入、以及「运行元数据」（版本、命令、seed、时间）。目录结构可以简单到：

```text
corpus/
  seed/
    expr-001.txt
  queue/
    id-000123.txt
  crashes/
    div-self-x0.txt
  meta.json
```

`meta.json` 里记录 `{"seed": 20261020, "iters": 4000, "commit": "...", "oracle": "exact"}`。没有这些元数据，三个月后无法判断「这个 crash 还能不能复现」。语料本身也要版本化：如果语言/优化器变了，旧语料可能不再触发，但仍应保留作为回归样本。

语料最小化（corpus minimization）是持久化的另一面。corpus 越大，选择越慢、存储越贵；但删错输入会丢覆盖。常用做法是「贪心集合覆盖」：按「新特征」排序，依次保留能带来未覆盖特征的输入，直到覆盖集合不再增长。对编译器，还可以按「优化 pass 命中」做覆盖，保留能触发不同 pass 的输入。

持久化还要考虑「可复现」。同一个 seed 在不同 Python 版本、不同字典顺序、不同并发度下可能产生不同序列。本章脚本固定 `random.Random(seed)`、单线程、固定迭代次数，因此输出可复现；真实 fuzzer 还要固定哈希种子、线程数、超时值。把「不可复现」当成一等 bug 修，而不是接受「fuzz 本来就这样」。

### 语料的生命周期

语料不是「一个文件夹」，而是一条流水线：种子 → 队列 → 崩溃 → 回归 → 归档。每一站都有不同的保留策略：

| 阶段 | 内容 | 保留策略 |
|:--|:--|:--|
| seed | 人工挑选的最小合法输入 | 永久，随代码版本化 |
| queue | 触发新覆盖的输入 | 定期做集合覆盖最小化 |
| crash | 触发失败的输入 | 永久，附最小化与元数据 |
| regression | 已修复 bug 的最小反例 | 永久，进 CI |
| archive | 历史运行的全量语料 | 冷存储，按需恢复 |

seed 的质量决定起点。一个好的 seed 集合应覆盖语法的每个产生式、每个优化 pass、每个错误分支；不是「越多越好」，而是「越多样越好」。可以从项目自带的测试用例、文档示例、历史 bug 反例中抽取，再用 corpus minimization 去掉重复覆盖。

### 元数据与复现

每个 crash 至少带一份元数据，否则无法复现。一个最小 JSON 结构如下：

```json
{
  "id": "div-self-x0",
  "seed": 20261020,
  "iters": 4000,
  "oracle": "exact",
  "command": "python3 fuzz_lab.py --seed 20261020 --iters 4000",
  "witness": {"x": 0},
  "expected": "ERR",
  "actual": 1,
  "minimized": "(x / x)",
  "limits": {"timeout_s": 1, "memory_mb": 512}
}
```

字段不是越多越好，但 `seed`、`command`、`expected/actual`、`minimized`、`limits` 缺一不可。`command` 要能直接复制运行；`seed` 保证随机序列可复现；`limits` 解释「为什么本地可能不复现」。如果 target 依赖外部文件，还要记录文件哈希或相对路径。

复现清单可以写成五步：检出对应 commit、安装固定工具链、设置相同环境变量、用 `command` 跑、确认 `expected/actual`。任何一步缺失，复现就会变成「我这里没问题」。把清单放进 issue 模板，比在聊天里反复问有效。

语料归档还要考虑隐私与安全。真实程序的输入可能含用户数据、密钥、路径；入库前要脱敏或只存哈希。崩溃文件可能包含内存转储，不能直接公开。对开源项目，最好只保留最小化后的输入，并把原始大文件放到受控存储。

### 字典的自动提取

手写字典容易漏 token。可以从三个来源自动提取：文法文件里的终结符、源码里的关键字/操作符、以及历史 crash 里出现的高频片段。提取后去重、按长度排序，再人工删掉噪声（例如过长的字符串字面量）。对编译器，字典还应包含类型名、属性名、以及目标相关的 magic 值；这些是字节变异最难撞到的部分。

自动提取的字典要版本化。语言增加关键字、优化器增加 pass 名称时，字典应同步更新；否则 fuzzer 会一直生成旧语法。把字典生成脚本放进仓库，用 CI 检查「字典是否与文法同步」，比手动维护可靠。

### 结构化输入的边界

结构化变异不是万能的。它依赖一个「能解析所有合法输入」的 parser；如果 parser 本身有 bug，生成器会继承同样的盲区。例如 parser 不接受某种合法语法，生成器就永远生成不出该语法，fuzzer 也就测不到。缓解办法是用两个独立 parser 交叉验证，或定期用「原始字节变异」做补充，专门打 parser 的边界。

### 持久化目录的权限

语料目录可能被 fuzz target 读写。如果 target 是恶意的，它可以删除语料、写满磁盘、或通过符号链接逃逸。目录权限应最小化：target 只读挂载语料，输出写到独立临时目录；符号链接在写入前检查；归档目录与运行目录分离。CI 里还要限制 artifact 上传大小，避免一个巨大 crash 文件拖垮流水线。

### seed 的来源与许可

seed 可能来自第三方测试集、用户报告、或开源项目。入库前要确认许可与隐私：用户输入可能含密钥、路径、个人信息；第三方语料可能带不兼容的许可证。一个实践是「只保留最小化后的结构，不保留原始数据」，并在 `meta.json` 里记录来源与许可。对商业项目，seed 还要经过法务/安全 review，不能直接从网上抓。

### 语料的去重与压缩

语料文件多时，存储和传输成本会超过计算成本。可以在归档时做两层压缩：内容级去重（相同哈希只留一份）和结构级去重（相同特征集合只留最小输入）。压缩不能替代 cmin：cmin 保覆盖，压缩只省空间。恢复时先解压再按 meta 的哈希校验，避免损坏的语料污染下一次运行。

### 语料的访问模式

fuzzer 读语料是「随机读」，cmin 是「全量读」，归档是「顺序读」。三种模式对存储的要求不同：随机读适合本地 SSD，全量读适合批量任务，顺序读适合对象存储。不要把归档目录直接挂给 fuzzer 当语料；延迟会让执行速度下降一个数量级。运行语料与归档语料应物理分离。

## 10.7 资源边界与安全 {#sec-compilers.3.10.7}

fuzz target 处理的是不可信输入。一个解析器可能因为递归深度爆栈、因为 `malloc` 失败崩溃、因为正则回溯卡死、因为输出无限增长把磁盘写满。fuzzer 不能假设 target 会友好退出；它必须给每次执行设边界。

| 资源 | 限制手段 | 失败表现 | 处理 |
|:--|:--|:--|:--|
| CPU 时间 | 子进程 timeout / alarm | 挂起 | 记为 hang，单独去重 |
| 内存 | `setrlimit(RLIMIT_AS)` / cgroup | OOM/被 kill | 记为 OOM，限制并发 |
| 栈 | `RLIMIT_STACK` / 递归深度检查 | 段错误 | 与真实栈溢出区分 |
| 输出 | 管道上限 / 临时文件配额 | 写满磁盘 | 截断并标记 |
| 文件描述符 | `RLIMIT_NOFILE` | `EMFILE` | 清理后重试 |
| 子进程 | 进程组 + kill | 僵尸/逃逸 | 超时后杀进程组 |

在 Python 里，最简单的隔离是 `subprocess.run(..., timeout=...)`，把 target 放到子进程；超时后 kill。更严格的做法是 `resource.setrlimit` 限制地址空间和 CPU，再用 `os.setsid` 建进程组，超时杀整组。不要把 target 直接跑在 fuzzer 进程里：一次 `exit()` 或段错误会带走整个 fuzzer。

```python
import subprocess

def run_one(path, timeout=1.0):
    try:
        p = subprocess.run([path], capture_output=True, timeout=timeout)
        return p.returncode, p.stdout
    except subprocess.TimeoutExpired:
        return "TIMEOUT", b""
```

这段代码验证「超时是观察，不是异常」。预期行为是：正常退出返回 `(returncode, stdout)`，超时返回 `("TIMEOUT", b"")`。调用者据此把 hang 当成一类失败，而不是让整个 fuzzer 崩掉。注意 `timeout` 只杀直接子进程；如果 target 又 fork 了子进程，需要进程组或 cgroup 才能清干净。

资源限制也会影响「bug 是否可复现」。一个在 1 秒超时下被记为 hang 的输入，在 10 秒超时下可能正常返回；一个在 1 GB 内存下 OOM 的输入，在 4 GB 下可能成功。报告里必须写清限制值，否则「本地复现不了」会浪费大量时间。CI 的 fuzz job 应把限制写成配置，而不是散落在脚本里。

安全边界不止资源。fuzz target 可能执行任意代码（JIT、插件、反序列化），必须在沙箱里跑；语料文件可能包含路径穿越、压缩炸弹、超大整数。第 12 章会展开沙箱与 JIT 的信任边界；这里记住一条：**fuzzer 的宿主进程不应与 target 共享权限**。用容器、虚拟机或至少独立用户跑 target，限制网络与文件系统写权限。

本章实验为了可读性，没有给 `fuzz_lab.py` 加超时和内存限制；它只在进程内跑纯 Python 表达式，风险可控。这是明确的实验边界，不是生产建议。把同一套逻辑搬到真实编译器上时，必须补上 10.7 的边界，否则一个 hang 就能让 CI job 卡到全局超时。

### hang 不是一种东西

「超时」是一个笼统的观察，背后可能是四种完全不同的机制：

| 类型 | 表现 | 检测 | 处理 |
|:--|:--|:--|:--|
| 慢 | 最终返回，但超过阈值 | 放宽阈值重跑 | 性能问题，不是 hang |
| 死循环 | CPU 100%，永不返回 | 超时 + CPU 时间 | 真 hang，最小化循环条件 |
| 死锁 | 阻塞在锁/条件变量 | 超时 + 栈采样 | 并发 bug，需 TSan/栈 |
| 阻塞 I/O | 等文件/网络/管道 | 超时 + 系统调用跟踪 | 环境问题，隔离 I/O |

把四类都记为「hang」，会让报告无法行动。至少应记录「超时值、CPU 时间、是否可复现、是否依赖输入大小」。如果 10 秒能返回，就把它归为「慢」并单独统计；如果 CPU 时间为 0，优先怀疑阻塞而不是死循环。

### 隔离层级

资源限制只是第一层，隔离是第二层。常见层级从弱到强：

| 层级 | 隔离什么 | 成本 | 适用 |
|:--|:--|:--|:--|
| 进程内 | 无 | 零 | 纯函数、可信输入 |
| 子进程 | 崩溃、全局状态 | 低 | 大多数 CLI |
| 容器 | 文件系统、网络、PID | 中 | 不可信解析器 |
| 虚拟机 | 内核攻击面 | 高 | JIT、内核/驱动 |
| 独立机器 | 硬件/侧信道 | 最高 | 高风险目标 |

第 12 章会展开沙箱谱系。这里只需记住：`setrlimit` 限制不了 `fork` 炸弹、限制不了 `mmap` 之外的共享内存、也限制不了 target 通过 `/proc` 读宿主信息。真正的隔离要靠命名空间/容器/虚拟机，而不是一个 `ulimit`。

### 拒绝服务面

fuzz target 的「输入」可能触发资源耗尽，这类问题本身也是 bug：

- 压缩炸弹：几十 KB 解压成几十 GB。
- 深递归：一个嵌套 10 万层的 JSON 让栈溢出。
- 正则回溯：一个短字符串让匹配时间指数增长。
- 输出放大：一个 `printf` 循环把磁盘写满。
- 文件描述符泄漏：每次解析打开文件不关闭。

对这些目标，超时/内存限制只能「止损」，不能「修复」。修复要在解析器里加深度上限、输出配额、正则超时/DFA 化、RAII 式关闭。fuzz 报告应把「资源耗尽」与「内存安全」分开，否则修 bug 的人会找错方向。

### CI 资源预算

fuzz job 最容易挤占 CI 资源。一个不限时的 job 可能跑满 6 小时，把其他任务排队；一个不限内存的 job 可能触发 OOM killer，影响同机任务。给 fuzz job 设预算，至少包括：

| 预算 | 建议值 | 超限行为 |
|:--|:--|:--|
| 墙钟时间 | 10–30 分钟（PR）/ 数小时（nightly） | 优雅退出，保存语料 |
| 单次执行超时 | 1–5 秒 | 记 hang，继续 |
| 总内存 | 容器限额的 70% | 降并发，不 OOM |
| 语料大小 | 几百 MB | 做 cmin，归档冷存储 |
| 报告数量 | 每类 bug 1 条 | 去重后写入 issue |

「优雅退出」很重要：fuzz 被 kill 时若没保存语料，下一次又从零开始。脚本应捕获 SIGTERM，写完 meta.json 再退出；容器要给它足够的 termination grace period。CI 的缓存策略也应把 corpus 缓存起来，键用「target 哈希 + 字典哈希 + 工具版本」，避免不同配置互相污染。

预算不是越低越好。把单次超时设成 100 毫秒，会把所有正常但稍慢的输入记成 hang；把总时间设成 1 分钟，覆盖率还没起步就结束。先测「空跑」的启动成本，再定预算；fuzz 的有效时间应是「总时间减去启动/收尾」。

### 平台差异

资源限制的行为依赖平台。Linux 的 `RLIMIT_AS` 限制地址空间，macOS 对 `RLIMIT_AS` 的支持不完整；Windows 没有 `fork`，隔离要靠 Job Object。超时的实现也不同：`SIGALRM` 只对单线程有效，多线程 target 要用 `timer_create` 或外部监控。跨平台 fuzz 应把「限制」抽象成接口，而不是在脚本里写死 `ulimit`。

### 验证限制真的生效

设了 `RLIMIT_AS` 不代表 target 不会 OOM。限制可能被 `fork` 的子进程继承但被 `exec` 重置，可能被容器覆盖，也可能因为 overcommit 而不触发。验证方法：写一个故意分配大内存的 target，确认它在限制内被 kill；写一个死循环，确认超时生效；写一个 `fork` 炸弹，确认进程组被杀。没有验证的限制，只是配置文件里的一行字。

| 限制 | 验证用例 | 期望 |
|:--|:--|:--|
| 内存 | 分配 2 倍限额 | 被 kill，不拖垮宿主 |
| CPU | 无限循环 | 超时退出 |
| 进程数 | `fork` 100 次 | 被限制或被杀组 |
| 输出 | 无限打印 | 写满配额后截断 |
| 文件 | 打开大量文件 | `EMFILE`，不崩溃宿主 |

### 沙箱也要测试

沙箱配置错误比没有沙箱更危险，因为它给人虚假的安全感。至少测试三件事：target 能否写工作目录之外的文件、能否建立网络连接、能否读取环境变量中的密钥。用一个故意恶意的 target（尝试 `open("/etc/passwd")`、`connect()`、打印 `environ`）验证沙箱会拒绝。测试结果应进 CI，沙箱配置变更时重跑。

### 资源限制与可复现性的冲突

限制越紧，越容易把「慢」误判为「hang」，把「大内存」误判为「泄漏」。报告里要同时记录限制值与观测值（实际 CPU 时间、峰值 RSS），而不是只写「超时」。复现时先用宽松限制确认行为，再用生产限制验证；两者不一致时，说明限制本身影响了结果，应调整阈值而不是改 bug 结论。

### 资源耗尽的分类

同样是 OOM，可能是「输入要求 10 GB」也可能是「内存泄漏」。前者是输入规模问题，后者是 target bug。fuzzer 应记录峰值 RSS 随输入大小的曲线：线性增长是正常，指数/不释放是泄漏。只看「是否 OOM」会把两类问题混在一起，修复方向完全不同。

## 10.8 agent 错误：错误 oracle 把 bug 判成通过 {#sec-compilers.3.10.8}

这一节复盘 agent 写差分测试时最常见的两个错误：oracle 把「参考实现抛异常」当成「跳过」，以及去重键只按异常类型合并。它们都会让 fuzzer 报告「0 bug」，而代码里明明有 bug。

agent 的任务是「比较解释器与优化器的结果」。它写出的核心逻辑如下：

```python
def same(expr, env):
    try:
        expected = eval_ast(expr, env)
    except ZeroDivisionError:
        return True          # 参考实现报错，认为“环境问题”，跳过
    try:
        actual = eval_ast(optimize(expr), env)
    except ZeroDivisionError:
        return True
    return expected == actual
```

这段代码的意图是「不要让除零异常打断 fuzz」。实际效果是：只要参考实现抛异常，就判为一致，根本不看候选做了什么。于是 `x / x` 在 x=0 时（参考抛异常、优化器返回 1）被判成通过。真实运行 `--oracle=skip-errors` 的输出是：

```text
seed=20261020 iters=4000 oracle=skip-errors
executions=4000 parse_failures=0 corpus=617 features=783 rule_hits=23649
mismatches=0 other_classes=0 unique_after_dedup(source)=0
  no bug found
```

同一份目标、同一个 seed、同样的 4000 次执行，exact oracle 找到 2 类 bug，skip-errors oracle 找到 0 类。差别只在「异常算不算观察」。根因不是 fuzzer 不够强，而是 oracle 把「参考失败」当成了「无需比较」。

修复原则是「失败也是观察」。参考实现抛异常时，候选也必须抛同类异常；两者都抛，才算一致；一方抛一方不抛，就是不一致。异常类型、错误码、甚至错误消息的关键部分都应纳入比较，具体粒度取决于规范。修正后的逻辑：

```python
def same(expr, env):
    def observe(node):
        try:
            return ("value", eval_ast(node, env))
        except ZeroDivisionError:
            return ("error", "division-by-zero")
    return observe(expr) == observe(optimize(expr))
```

这段代码把「值」与「错误」编码成可比较的观察，避免「异常即通过」。它仍然可能漏掉「两边都抛异常但错误类型不同」的 bug；更严格的做法是比较异常类与消息模板。代价是消息格式变化会导致假阳性，需要规范化。

第二个错误是去重键。agent 常写：

```python
def bug_key(exc):
    return type(exc).__name__
```

对本章的两个 bug，参考实现都抛 `ZeroDivisionError`，于是键相同，两个根因被合成一个。真实运行 `--dedup=symptom` 的输出是 `unique_after_dedup(symptom)=1`，而默认按最小化源码去重是 2。去重键太粗，团队会以为只有一个 bug，修完 `div_self` 就关闭 issue，`zero_div` 继续留在代码里。

::: ex 例 10.8.1 · 用「植入 bug」验证 oracle {#ex-compilers.3.10.8.1}
在信任一个 fuzzer 之前，先给它一个已知 bug：把 `optimize` 的 `div(a, a) -> 1` 规则临时打开（或保留），跑固定 seed。如果 oracle 与去重键正确，应在少量执行内报告 `div_self` 类；如果报告 0，说明 oracle/生成器/去重键至少有一处坏了。

这个「阳性对照」比「跑一周没 bug」更有说服力。它证明的是「工具能发现它应该发现的东西」，而不是「程序没有 bug」。对 agent 生成的测试代码，第一步就该跑阳性对照；没有对照的「全绿」不可信。
:::

修复后的 agent 代码还应带三类测试：oracle 单元测试（构造「参考错/候选对」「两边都错但类型不同」的用例）、去重键测试（两个不同根因不能被合并）、以及端到端测试（固定 seed 跑 N 次，断言语料增长且至少发现 2 类）。这三类测试不依赖真实 bug，能在 CI 里稳定运行。

把这一节收束成一条规则：**oracle 的每个「跳过」「忽略」「视为通过」分支，都是一次潜在的漏报**。写 oracle 时，先列出所有提前返回的路径，逐条问「这里是否可能把 bug 判成通过」；如果答案是「可能」，就改成显式比较或至少记录「未比较」的计数。一个诚实的 oracle 会说「这次没比较」，而不是说「这次通过了」。

### 给 oracle 写单元测试

oracle 本身是代码，应该有单元测试。构造四类用例：参考对/候选对（应通过）、参考错/候选对（应失败）、参考对/候选错（应失败）、两边都错但类型不同（应失败）。这四类覆盖了假接受、假拒绝与「都错」的盲区。测试不需要真实 bug，几行断言就够。

```python
def observe_value(fn, expr, env):
    try:
        return ("value", fn(expr, env))
    except ZeroDivisionError:
        return ("error", "div0")

def oracle(expr, env):
    return observe_value(eval_ast, expr, env) == \
           observe_value(lambda e, x: eval_ast(optimize(e), x), expr, env)

assert oracle(("add", ("num", 1), ("num", 2)), 0) is True
assert oracle(("div", ("var",), ("var",)), 0) is False
```

这段代码验证「oracle 能区分值与错误」：正常表达式通过，`x / x` 在 x=0 时不通过。预期结果是两条断言都成立；如果第二条断言失败，说明 oracle 把「参考抛异常」当成了通过。把这类测试与 fuzzer 一起跑，能在 oracle 改动时立刻发现行为变化。

### 阳性对照矩阵

| 对照 | 植入什么 | 期望 | 说明 |
|:--|:--|:--|:--|
| oracle 阳性 | 已知 `div_self` bug | 报 1 类 | 证明 oracle 能看见 |
| oracle 阴性 | 无 bug 的正确优化器 | 报 0 类 | 证明不误报 |
| 去重阳性 | 两个不同根因 | 报 2 类 | 证明键不过粗 |
| 去重阴性 | 同一根因的 10 个输入 | 报 1 类 | 证明键不过细 |
| 生成器阳性 | 只有加法/乘法 | 报 0 类 | 证明生成器覆盖不足 |

这五条对照可以在几分钟内跑完，适合放进 CI 的 smoke。它们不测试「真实 bug 是否存在」，只测试「工具是否按预期工作」。一个 fuzzer 的信任度，取决于它的对照矩阵是否完整，而不是它跑了多少小时。

### agent 的修复流程

发现 oracle 错误后，不要只改一行 `return True`。按四步修：

1. **写失败测试**：构造「参考抛异常、候选返回值」的用例，确认当前 oracle 判通过。
2. **改观察模型**：把值/错误编码成可比对象，双方一致才通过。
3. **加阳性对照**：保留一个已知 bug，确认新 oracle 能报。
4. **加回归**：把该用例放进单元测试，防止下次又写成「异常即通过」。

这四步与修编译器 bug 的流程相同：先复现，再修根因，再加回归。区别是 oracle 的「根因」在测试代码里，不在被测程序里；因此更容易被忽视，也更容易在重构中回退。

### agent 交接清单

把 fuzz 工具交给别人前，交接四样：怎么跑（命令 + seed）、怎么判断（oracle 定义 + 已知盲区）、怎么看结果（去重键 + 报告字段）、怎么扩展（生成器/变异器接口）。缺任何一项，下一个人都会重新踩一遍 oracle 的坑。文档里最好附一个「阳性对照」命令，让对方五分钟内确认工具在工作。

### oracle 的监控指标

上线后要监控 oracle 的健康度：比较率（实际比较的次数 / 执行次数）、未知率、失败率、以及「每千次执行发现的新类别数」。比较率突然下降，说明参考实现或解析器坏了；未知率上升，说明输入超出子集或超时变多。把这些指标画成趋势图，比只看「今天有没有 crash」更早发现问题。

### oracle 漂移

oracle 会随代码重构「悄悄」变化：有人把异常捕获从 `ZeroDivisionError` 改成 `Exception`，有人把「比较输出」改成「比较退出码」。这些改动通常不会让现有测试变红，却会让漏报率上升。把 oracle 的行为用单元测试锁住（10.8 的四类用例），并在 code review 时把 oracle 改动当语义改动看待，而不是普通重构。

agent 生成测试代码时，最容易把「让测试通过」当成目标。它会在参考实现抛异常时 return True，在比较失败时 catch 后 pass，在去重时用最省事的键。这些选择单独看都「合理」，合起来就是一个不会报 bug 的 fuzzer。review 测试代码时，优先看「哪些路径没有比较」，而不是看「断言写得多不多」。

agent 还容易把「参考实现没报错」当成「参考实现正确」。参考实现可能只是没实现该检查，或者把错误吞掉了。给参考实现也跑一遍它自己的单元测试/阳性对照，确认它在该报错时会报错，再拿它当 oracle。参考实现不是神，它只是另一个需要被测试的程序。

## 10.10 本章陷阱（8–15 条） {#sec-compilers.3.10.10}

::: errata 本章陷阱
1. **把「没崩溃」当「没 bug」**。现象：fuzzer 跑了一周，零 crash，发布后结果错误。原因：oracle 只看崩溃，没比较输出。修复：加参考实现或性质 oracle，并对已知 bug 做阳性对照。
2. **把参考实现的异常当「跳过」**。现象：差分 fuzzer 报 0 bug，但优化器明显漏掉除零。原因：oracle 在参考抛异常时提前返回「通过」。修复：把异常编码成观察，双方一致才算通过。
3. **按异常类型去重**。现象：两个不同优化 bug 被合成一个 issue。原因：症状相同不等于根因相同。修复：按最小化源码或故障类别去重，并保留多个代表。
4. **只跑 `-O0`**。现象：优化 bug 抓不到。原因：多数优化在 `-O0` 不启用。修复：至少加 `-O1`/`-O2` 的差分，并处理 UB 噪声。
5. **把 UB 差异当编译器 bug**。现象：`-O0` 与 `-O2` 结果不同，被报成回归。原因：程序本身有 UB，两边都合法。修复：先用 UBSan 筛查，丢弃 UB 用例（第 9 章）。
6. **语料只增不减**。现象：fuzz 越跑越慢，选择阶段占大头。原因：corpus 膨胀，重复输入太多。修复：定期做集合覆盖最小化，按特征去重。
7. **变异不保语法**。现象：99% 的输入在 parser 第一行就失败。原因：字节变异破坏了结构。修复：用 AST/文法变异，或加字典与修复 pass。
8. **超时值随手写**。现象：同一输入有时 hang 有时正常，报告无法复现。原因：超时边界不稳定，未记录限制。修复：固定超时并写进元数据；hang 单独分类。
9. **fuzz target 跑在宿主进程**。现象：一次段错误带走整个 fuzzer；或 target 写满磁盘。原因：没有进程/资源隔离。修复：子进程 + rlimit/cgroup + 只读文件系统。
10. **没有固定 seed/版本**。现象：别人复现不了 crash。原因：随机序列、编译器版本、环境变量未记录。修复：元数据记录 seed、commit、命令、限制值；CI 用固定镜像。
11. **把覆盖率当目标**。现象：覆盖率 95%，bug 数不涨。原因：覆盖率奖励「新边」，不奖励「新语义」。修复：加值剖面、定向目标、错误类别反馈，并看首次发现时间。
12. **把「差分通过」当「语义正确」**。现象：两个实现都不报错，但都漏掉同一个检查。原因：参考与候选共享同一套错误假设（相关性）。修复：加独立参考（解释器/另一编译器），或用性质/规范做第三方 oracle。
13. **缩减后不复验**。现象：最小反例修好后，原 bug 仍在。原因：缩减器换了一个失败类别，只保证「还失败」。修复：用原始失败签名复验；签名不一致就回退。
:::

### 给陷阱做一张排查表

| 症状 | 先查 | 常见根因 |
|:--|:--|:--|
| 0 bug | oracle/生成器/去重 | 异常被当通过、语法生成缺失 |
| 大量重复 issue | 去重键 | 键太细、栈哈希不稳定 |
| 语料不涨 | 反馈/变异 | 特征太粗、变异破坏语法 |
| 越跑越慢 | 语料/资源 | corpus 膨胀、无超时 |
| 结果不可复现 | 元数据 | seed/版本/限制未记录 |

排查顺序应从「0 bug」开始，因为它最容易被误判为「程序没问题」。先跑阳性对照，再谈覆盖率与执行数。

把 13 条按「证据来源」再分一次：1、2、3、4、5、10、13 属于 oracle/环境类，6、7、8 属于 fuzzer 机制类，9、11、12 属于资源与评估类。排查时先定位类别，再动手；否则容易在生成器上调半天，真正的问题却在 oracle。

排查表只能缩小范围，不能替代复现。每一条都要落到「命令 + 输入 + 期望」；没有复现的排查，只是猜测。把排查表打印出来贴在 issue 模板里，比放在文档深处更有效。

### 交付清单

在把 fuzz 结果交给别人之前，逐项打勾：

- 命令可复制，seed/版本/限制齐全。
- 每个 bug 有最小输入与期望/实际。
- 每个 bug 有去重键与「为什么是同一类」的说明。
- 已知未覆盖项写清楚（浮点、并发、跨函数等）。
- 阳性对照通过，oracle 的未知比例可接受。
- 资源限制经过验证，不会拖垮宿主/CI。

六项里缺一项，报告就只能算「线索」，不能算「证据」。

清单之外还有一条软标准：报告要让没参与 fuzz 的人能在十分钟内复现。做不到，就说明元数据或最小化还不够。

这条标准也适用于本书：本章的每个数字都应能通过 `bash experiments/ch10/run.sh` 重新得到，否则就是文档与实验脱节。

### 一次完整的 fuzz 记录

把本章实验当成一次小型审计，记录可以写成下面这样。它不是「跑完了」，而是「每一步都能解释」：

| 阶段 | 事实 | 证据 |
|:--|:--|:--|
| 目标 | 表达式优化器，两条不安全化简规则 | `fuzz_lab.py` 的 `div_self`、`zero_div` |
| 种子 | 12 个表达式，覆盖加减乘除与边界常量 | `SEEDS` 列表 |
| 生成 | AST 变异，4000 次执行，解析失败 0 | `executions=4000 parse_failures=0` |
| 反馈 | 783 个 AST 形状特征，语料 617 | `features=783 corpus=617` |
| 判定 | 参考解释器 vs 优化后解释器，6 个环境 | `ENVS = [0, 1, -1, 2, -2, 3]` |
| 发现 | 414 次不匹配，2 个根因 | `mismatches=414 unique=2` |
| 缩减 | 子树收缩 + 替换 + ddmin | `(x / x)`、`(0 / x)` |
| 对照 | 错误 oracle 报 0，错误去重报 1 | `--oracle=skip-errors`、`--dedup=symptom` |

这张表的价值在于「每个数字都能追到代码/输出」。如果只写「跑了 4000 次找到 2 个 bug」，读者无法判断 4000 是否足够、2 个是否完整、错误 oracle 是否也会得到 2 个。把对照跑一遍，结论才有边界。

一次审计还要记录「没做什么」：没有测浮点、没有测跨函数、没有测并发、没有给 target 加资源限制。这些不是缺陷，而是范围声明；写清楚，后续的人才知道从哪里扩展。最危险的不是「没测」，而是「以为测了」。

### 常见追问

**为什么不用 Hypothesis/libFuzzer？** 本章要展示闭环的每一环，纯标准库实现更容易逐行解释；工业工具在调度、插桩、持久化上更成熟，但 oracle/去重/缩减的问题相同。

**为什么 bug 这么容易找到？** 因为优化器故意留了两条错误规则，且生成器覆盖了除法与重复子树。真实编译器的 bug 更稀疏，需要更长的运行与更好的反馈；但「找到之后怎么缩、怎么去重、怎么防回归」不变。

**4000 次够吗？** 对这两个 bug 足够（前 12 次就出现）；对「证明没有 bug」永远不够。fuzz 的结论只能是「在这组输入/oracle/限制下没找到」，不能是全称否定。

**怎么判断一个 crash 是不是安全漏洞？** 先看是否可被不可信输入触发，再看影响（越界读写/任意代码执行/信息泄露），最后看缓解措施（ASan/沙箱/权限）。本章的优化器 bug 是语义错误，不是内存安全漏洞，但两者都需要最小复现与回归。

**Q1** 一个差分 fuzzer 在 `-O0` 与 `-O2` 下比较程序输出，跑了 10 万次零差异。能否说「优化器没有 bug」？给出两个反例场景。

**Q2** 你的 fuzzer 找到 500 个 crash，按「异常类型」去重后剩 3 个。下一步应该做什么？为什么不能直接修这 3 个？

**Q3** 属性测试生成器只生成 `x + 1` 和 `x * 2`，能发现 `x / x` 的优化 bug 吗？为什么？怎样改生成器？

**Q4** 一个输入在 1 秒超时下被记为 hang，在 10 秒下正常返回。它是 bug 吗？报告里应该怎么写？

**Q5** 有人说「我的 fuzzer 跑了 10 亿次，所以这个优化器没有 bug」。这句话缺了哪些限定？

**Q6** 错误 oracle 与错误去重键，哪个更危险？如果只能先修一个，修哪个？

**Q7** 为什么差分测试在编译器上比在普通业务程序上更容易落地？




::: sol 答案
**A1** 不能。反例一：两个优化级别共享同一个前端 bug，错误在生成 IR 之前就存在，差分两边一起错；反例二：bug 只在某个输入上触发，而生成器从未生成该类输入（例如没有除零、没有大整数）。差分通过只说明「在这组输入上两边一致」，不说明优化器正确。

**A2** 先抽样复现并按「最小化源码/顶层栈帧」重新聚类，确认 3 个类型是否真的对应 3 个根因；再用阳性对照检查去重键是否过粗。不能直接修，是因为「异常类型」可能把不同根因合并（例如本章两个优化 bug 都是 `ZeroDivisionError`），修了一个另一个还在；也可能同一根因因不同栈被拆成多个，导致重复劳动。

**A3** 不能。生成器只产生加法和乘法，永远构造不出 `x / x` 或 `0 / x`，优化器的除法规则不会被触发。改法是：把除法加入生成器、加入重复子树复制、加入 0/1/边界常量，并控制深度；或者用文法生成覆盖全部运算符。

**A4** 取决于目标与限制。如果 1 秒是明确的资源契约，超时就是「在该限制下的失败」，应记为 hang；如果 10 秒能正常完成，说明它是「慢」而不是「死循环」，报告里要写清限制值并单独分类。不能简单说「是 bug」或「不是 bug」；要写明「在 timeout=1s 下 hang，timeout=10s 下返回 X」。

**A5** 至少缺四个：输入分布（是否覆盖除法、溢出、边界常量）、oracle（是否只比较崩溃、是否把异常当跳过）、资源限制（超时/内存是否把慢路径截断）、以及去重（是否把多个 bug 合成一个）。「10 亿次」只说明执行量，不说明搜索空间、判定能力与观察粒度。正确的说法是「在输入分布 D、oracle O、限制 L 下执行 10 亿次，未发现新类别；已知未覆盖 X/Y/Z」。

**A6** 错误 oracle 更危险，因为它把「有 bug」判成「没 bug」，会让整个 fuzz 结论失效；错误去重键只是把多个 bug 合并或拆分，至少 bug 还在报告里。先修 oracle：加阳性对照、把异常纳入观察、记录未知比例。oracle 可信后，再调去重键，否则你连「有几个 bug」都不知道。

**A7** 因为编译器有「同一语义的多个实现/多个配置」：解释器与编译器、`-O0` 与 `-O2`、不同后端与不同目标。业务程序通常只有一个实现，找不到便宜的第二意见；编译器还能把输入限制在无 UB 的可移植子集，减少合法差异。代价是要处理相关性（共享前端）与 UB 噪声。
