第 11 章证明的是源程序：给定语义，所有满足前置条件的执行都满足后置条件。这个结论有一个前提——执行环境按语义办事。真实环境里，代码可能是运行时生成的，内存可能同时可写可执行，子进程可能继承了一个不该给它的文件描述符。证明管不到这些；它们属于执行层的信任边界。

JIT（just-in-time compilation）把编译搬到了运行时。它读取字节码或源文本，生成机器码，写进内存，再跳过去执行。这三步每一步都在扩大攻击面：输入不可信，编译器可能被输入诱导出错，代码内存必须可执行，常量池可能被越界写，代码缓存可能把错误类型的代码复用给下一次调用。解释器不生成代码，AOT 在进程启动前生成代码，它们的边界与 JIT 不同；不能把「JIT 能跑」当成「JIT 安全」。

沙箱常被误解成「限制资源」。`RLIMIT_CPU` 限制的是 CPU 时间，`timeout` 限制的是墙钟时间，`cwd` 只改变相对路径的基准，`env={}` 只改变环境变量；它们都不撤销已经打开的文件描述符，也不阻止子进程用绝对路径写文件。资源限制回答「能用多少」，隔离回答「能碰什么」。本章的实验会把这两件事拆开给你看。

读图：三种执行模型的区别不在「谁更快」，而在「代码从哪里来、什么时候变成可执行」。解释器的代码是固定的；AOT 的代码在进程启动前已经生成，运行时通常不可写；JIT 的代码在运行时生成，因此必须存在一段「先写、后执行」的生命周期。沙箱要管的正是这段生命周期，以及代码能触达的常量池、栈和系统调用。

## 12.1 执行模型：解释、AOT、JIT 与代码缓存 {#sec-compilers.3.12.1}

解释器直接遍历 AST 或字节码。它不需要生成机器码，所以不需要可执行内存；它的攻击面主要是解释器自身的类型判断、边界检查和宿主 API。AOT 编译器在进程启动前把源码变成机器码，代码段加载后通常是只读可执行；运行时没有代码生成，但优化只能基于静态信息，无法针对本次运行的实际类型做特化。

JIT 把编译推迟到运行时。它先解释或快速编译，收集类型/分支 profile；热路径触发优化编译；生成的机器码写进代码缓存；后续调用跳到缓存里的入口。类型假设不成立时，代码通过守卫（guard）跳到慢路径或触发去优化（deoptimization）。这套机制让 JIT 能针对实际输入特化，但也让「代码」变成了运行时数据。

::: def 定义 12.1.1 · 执行模型与代码缓存 {#def-compilers.3.12.1.1}
**解释器**在运行时逐条读取并执行中间表示，不生成新的机器码。**AOT 编译器**在程序启动前把源程序翻译成目标代码，运行时通常不再编译。**JIT 编译器**在程序运行期间把中间表示翻译成机器码，写入代码缓存并跳转执行。**代码缓存**（code cache）是以「输入表示 + 编译假设」为键、以可执行代码为值的映射；键通常包含字节码/源码哈希、参数类型、目标特性、编译选项与 profile 版本。缓存命中复用的是一段已经生成的代码，因此键漏掉任何影响语义的假设，都会把错误的代码复用给新的调用。
:::

三种模型的关键差异可以列成一张表：

| 维度 | 解释器 | AOT | JIT |
|:--|:--|:--|:--|
| 代码生成时机 | 无 | 启动前 | 运行时 |
| 可执行内存 | 不需要 | 加载时映射，通常 RX | 运行时分配，先 W 后 X |
| 启动成本 | 低 | 编译/链接成本前置 | 预热成本，冷启动慢 |
| 峰值性能 | 低 | 高（静态信息） | 高（运行时特化） |
| 主要攻击面 | 解释器、宿主 API | 编译器、加载器、签名 | 输入、编译器、代码内存、缓存 |
| 失效方式 | 解释错误 | 编译错误、ABI 不匹配 | 守卫失败、去优化、缓存污染 |

JIT 的代码缓存不是一个简单的哈希表。它要处理并发编译、缓存淘汰、去优化、栈上替换（on-stack replacement，OSR）、以及「旧代码还在栈上执行时不能释放」。一个典型的键长这样：

```text
key = (bytecode_hash, receiver_type, arg_types, isa_features,
       compile_flags, profile_version, deopt_count)
```

键少一项，就可能把一段为「整数加法」生成的代码复用给「浮点加法」；键多一项，缓存命中率下降，代码缓存膨胀。缓存污染（cache poisoning）不一定是攻击者直接写内存，也可能是「键没有覆盖某个影响语义的假设」，让运行时自己把错误代码放进了错误的槽位。

JIT 的另一个常见误解是「JIT 一定比解释器快」。冷启动时 JIT 要编译，可能比解释器慢；短生命周期进程可能还没预热就退出；去优化会把执行拉回慢路径。性能结论要带 workload、预热时间、代码缓存大小和去优化次数，不能只看峰值。

| 场景 | 更合适的模型 | 理由 |
|:--|:--|:--|
| 一次性脚本、冷启动敏感 | 解释器/AOT | 避免编译预热 |
| 长驻服务、类型稳定 | JIT | 运行时特化收益高 |
| 硬实时、可预测性优先 | AOT | 避免编译抖动 |
| 多租户、不可信输入 | 解释器或 Wasm 验证 + 受限 JIT | 代码生成面太大 |

代码缓存还要和内存管理配合。缓存里的代码持有常量池、内联缓存（inline cache）、栈映射（stack map）等元数据；GC 移动对象时，代码里的立即数不能指向旧地址，必须通过句柄或 relocation 更新。并发 GC 与 JIT 同时运行时，需要读写屏障或 safepoint。这里的 bug 往往不是「代码生成错」，而是「代码与元数据不同步」。

::: intuition 为什么 JIT 的信任边界比 AOT 宽
AOT 的输入在编译时已经确定，编译器可以在受控环境里跑；JIT 的输入在运行时才到，编译器本身也在攻击者的进程里。AOT 的代码段加载后通常只读；JIT 必须在运行时写代码，再把它变成可执行。AOT 的优化基于静态类型；JIT 的优化基于 profile，profile 可以被输入影响。每多一个「运行时决定」，就多一个需要验证的假设。
:::


JIT 的执行循环可以简化成下面这段伪代码。它把「解释」「编译」「缓存」「执行」串在一起，也把每个可能出错的点标了出来：

```text
for each call:
    key = (bytecode_hash, arg_types, flags, profile_version)
    if code_cache.has(key):
        entry = code_cache.get(key)       # 缓存命中：假设仍然成立？
        if guard(entry, args): jump(entry)
        else: deopt(); continue
    if hot_counter exceeds threshold:
        code = compile(bytecode, profile)  # 编译器可能失败/超时
        if code is None: fallback()
        else:
            seal(code); code_cache.put(key, code)  # 键是否完整？
    interpret_one_step()
```

这段伪代码里有四个「假设」：缓存键完整、守卫覆盖所有类型假设、编译器对失败有回滚、封存后不再写。任何一个假设被破坏，JIT 就会执行错误代码或把半成品暴露给下一次调用。

代码缓存的淘汰策略也会影响安全。LRU 只看使用频率，不看代码页的敏感度；一个攻击者可以反复触发编译，把合法代码挤出缓存，再让下一次调用走慢路径或重新编译（编译抖动）。更稳的策略是按租户/按代码来源分区，限制每区的代码页总量与编译次数，并在淘汰时等待 safepoint。

| 策略 | 命中率 | 内存 | 风险 |
|:--|:--|:--|:--|
| 无上限 | 高 | 随输入增长 | 代码缓存膨胀/DoS |
| LRU | 高 | 有界 | 抖动、淘汰热代码 |
| 按租户分区 | 中 | 可配额 | 实现复杂 |
| 按代码来源哈希 | 中 | 可去重 | 哈希冲突/共享代码 |
| 编译预算 + 上限 | 中 | 有界 | 热路径被降级 |

::: method 方法 12.1.2 · 选择执行模型 {#method-compilers.3.12.1.2}
1. 先问输入是否可信：不可信输入优先解释器/Wasm 验证，JIT 只作为受限后端。
2. 再问生命周期：短进程/冷启动敏感选 AOT 或解释器；长驻/类型稳定才考虑 JIT。
3. 问可预测性：硬实时/安全关键避免运行时编译抖动，选 AOT。
4. 问隔离：多租户要按租户隔离代码缓存、限制编译预算；单租户可以共享。
5. 最后才谈峰值性能：没有预热/去优化数据，不比较 JIT 与 AOT。
:::


JIT 的运行时指标也能当安全信号。编译次数/代码页总量突然上升、去优化率异常、守卫失败率接近 100%、缓存命中率骤降，可能不是性能问题，而是输入在诱导编译/去优化。把「编译预算」「代码页上限」「去优化率阈值」做成可观测指标，才能在 DoS 发生前限流，而不是等 OOM。

| 指标 | 正常 | 异常含义 | 动作 |
|:--|:--|:--|:--|
| 编译次数/秒 | 稳定 | 编译炸弹/形状爆炸 | 限流、降级解释器 |
| 代码页总量 | 有界 | 缓存膨胀/泄漏 | 淘汰、按租户配额 |
| 去优化率 | 低 | 守卫假设不稳/攻击 | 阈值告警、回退 |
| 守卫失败率 | 低 | 类型混淆尝试/输入漂移 | 检查验证器/守卫 |
| 缓存命中率 | 高 | 键过细/抖动 | 调整键、分区 |


profile 本身也是不可信输入。攻击者可以通过构造调用序列让某个分支看起来「总是整数」，诱导 JIT 生成省略类型检查的代码；下一次调用再传入对象，触发类型混淆。守卫不能只看「profile 这么说」，还要看「这次调用的实际值」；profile 只用于选择优化，不用于替代检查。把 profile 当事实、把守卫当可选，是 JIT 漏洞的常见模式。


OSR 是 JIT 里最容易被忽略的边界。解释器在循环里跑了很多次，触发编译；JIT 不能等函数返回再切换，否则热循环永远进不了优化代码。OSR 把当前解释器栈帧「翻译」成编译代码的栈帧，然后跳到循环入口。翻译要读对每个局部变量/栈槽的类型与位置；栈映射错了，编译代码会读到错误的局部变量，甚至把对象指针当整数。OSR 的测试要覆盖「在循环第 N 次迭代切换」的多个 N，而不是只测函数入口。

## 12.2 JIT 的信任边界：输入、编译器、代码内存 {#sec-compilers.3.12.2}

JIT 的信任边界不是一条线，而是一组资产与能力的分界。资产包括：输入程序的完整性、生成代码的完整性、常量池、栈映射、寄存器/栈、GC 元数据、宿主进程的文件描述符与系统调用权限。攻击者能控制其中一部分：字节码、常量、类型标签、profile、配置；不能直接控制 CPU 和内核，但可以通过输入诱导编译器生成越界访问。

::: def 定义 12.2.1 · JIT 信任边界 {#def-compilers.3.12.2.1}
JIT 的**信任边界**是「不可信输入」与「必须被保护的资产」之间的分界。边界内的组件被假定正确（或至少被验证）：编译器、运行时、代码内存管理器、GC、宿主 API。边界外的输入被假定恶意：字节码、常量、类型信息、profile、环境配置。安全论证必须说明：输入在跨过边界前经过哪些验证；验证失败时发生什么；验证通过的输入能触达哪些能力。
:::

把边界画出来：

<pre class="layout">
不可信输入
  |  字节码 / 源码 / 常量 / 类型标签 / profile
  v
+-------------------- 验证器 --------------------+
| 结构检查、类型检查、边界检查、栈深度检查        |
+----------------------+-------------------------+
                       | 验证通过的 IR
                       v
+-------------------- JIT 编译器 ----------------+
| 优化、寄存器分配、指令选择、常量池布局          |
+----------------------+-------------------------+
                       | 机器码 + 元数据
                       v
+-------------------- 代码内存 ------------------+
| RW 页（写入） --封存--&gt; RX 页（执行）           |
| 常量池（RW, NX）  栈映射  relocation            |
+----------------------+-------------------------+
                       | 跳转
                       v
                 CPU / 栈 / 系统调用
</pre>

读图：验证器是输入侧的门，代码内存是执行侧的门。两道门之间是编译器；编译器本身也可能有 bug，所以「验证通过」不等于「生成代码正确」。代码内存之后是宿主进程的能力：文件描述符、网络、环境变量。JIT 沙箱如果只验证字节码，不限制系统调用，攻击者仍可以通过生成的代码调用宿主 API。

按资产列威胁：

| 资产 | 攻击者能力 | 边界 | 证据 |
|:--|:--|:--|:--|
| 输入程序 | 任意字节码/常量 | 验证器 | 验证失败必须拒绝，不能「尽力修复」 |
| 生成代码 | 诱导编译器 | 代码生成正确性 | 反汇编、差分、翻译验证 |
| 代码页 | 写内存原语 | W^X / 双重映射 | 页权限、写保护切换 |
| 常量池 | 越界写/类型混淆 | 边界检查、隔离 | 常量池不可执行、只读 |
| 栈/寄存器 | 生成代码越界 | 栈映射、守卫 | 栈深度、canary、CFI |
| 宿主能力 | 生成代码发系统调用 | 进程沙箱/seccomp | 系统调用白名单、fd 关闭 |

JIT 喷射（JIT spraying）是输入侧最典型的攻击：攻击者把希望执行的指令字节藏进常量，编译器把这些常量作为立即数写进代码段；如果代码段可执行且攻击者能跳到常量中间，就能执行非预期的指令序列。防御不是「检查常量是不是指令」——那不可判定——而是 W^X、常量盲化（constant blinding）、随机化、以及不让攻击者控制跳转目标。W^X 切断「写常量」到「执行常量」的直接路径；常量盲化让攻击者无法精确预测字节布局。

类型混淆（type confusion）是另一类：JIT 根据 profile 假设某个值总是整数，省略了类型检查；下一次调用传入堆对象，生成的代码把对象指针当整数做算术，得到越界地址。守卫（guard）就是为此存在的：在假设可能失效的地方插入检查，失败则跳慢路径。守卫太少，类型混淆；守卫太多，性能下降。守卫的完整性是 JIT 验证的核心。

编译器本身也是信任边界内的一环。JIT 编译器可能因为输入规模、嵌套深度、常量折叠而栈溢出、超时、生成错误代码。一个「验证器通过」的程序仍可能让编译器崩溃，这是拒绝服务（DoS），不是代码执行；但如果编译器崩溃后留下部分写入的代码页，下一次复用可能执行半成品。代码缓存要在编译成功后才发布，失败时回滚。

::: ex 例 12.2.1 · 一个漏掉守卫的加法 {#ex-compilers.3.12.2.1}
假设 JIT 为 `a + b` 生成代码，profile 显示 `a`、`b` 都是小整数，于是省略了类型检查，直接生成整数加法。这个优化在「profile 仍然成立」时正确；一旦调用方传入装箱的浮点数，生成的代码把指针当整数相加，得到任意地址。正确的做法是保留一个守卫：检查两个操作数的类型标签，失败则跳到通用加法或去优化。守卫不是性能负担的借口；没有守卫的假设不是优化，是赌运气。
:::

JIT 的输入还包括「环境」：命令行参数、环境变量、文件内容、网络响应。如果 JIT 读取一个配置文件来决定优化选项，配置文件就进入了信任边界。很多漏洞不是出在字节码验证，而是出在「JIT 信任了一个不该信任的配置」。

| 输入 | 是否可信 | 验证点 | 失败处理 |
|:--|:--|:--|:--|
| 字节码 | 否 | 结构、类型、栈深度 | 拒绝，不编译 |
| 常量 | 否 | 类型、范围、池边界 | 拒绝或盲化 |
| profile | 否（可被输入影响） | 守卫、去优化 | 慢路径 |
| 编译选项 | 部分 | 白名单、范围 | 拒绝 |
| 宿主 API | 是（但最小化） | 能力列表 | 返回错误 |


JIT 喷射的防御可以用一个字节序列说明。假设攻击者希望代码段里出现一段特定指令，他把字节藏进一个常量；编译器把常量作为立即数写进 `mov` 指令。若代码段同时可写可执行，攻击者只要让跳转落在立即数的中间，就能从任意偏移开始解码。防御的第一层是 W^X：常量写入的页没有执行权限；第二层是常量盲化：编译器把常量与随机数异或，运行时再还原，攻击者无法预测字节；第三层是随机化：代码页布局/寄存器分配随机，跳转目标不可预测。

| 验证器检查 | 检查什么 | 失败时 |
|:--|:--|:--|
| 结构 | 段长度、版本、函数/局部变量数量 | 拒绝模块 |
| 类型 | 操作数类型、栈高度、分支参数 | 拒绝模块 |
| 边界 | 内存/表索引、全局变量 | 插入 trap 或拒绝 |
| 控制流 | 跳转目标在函数内、循环深度 | 拒绝模块 |
| 资源 | 函数大小、嵌套深度、编译预算 | 拒绝/降级 |

::: method 方法 12.2.2 · 给 JIT 做威胁建模 {#method-compilers.3.12.2.2}
1. 列出输入：字节码、常量、类型标签、profile、配置、环境；标出哪些可由攻击者控制。
2. 列出资产：代码页、常量池、栈映射、fd、网络、宿主 API；标出哪些是秘密/能力。
3. 画边界：验证器、编译器、代码内存、运行时；每个边界写「检查什么/失败怎么办」。
4. 找假设：每个优化都对应一个假设（类型、范围、对齐、无别名）；假设必须有守卫或证明。
5. 写负例：畸形字节码、超大函数、类型混淆、越界常量、缓存键碰撞；每个都要有预期拒绝/降级。
:::


验证器的失败模式要单独测。一个验证器可能「接受非法模块」（soundness 破）或「拒绝合法模块」（completeness 破）；前者是安全问题，后者是可用性问题。测试要同时覆盖：畸形段、类型不匹配、栈溢出、越界分支、超大函数、深层嵌套、重复导出。对每个失败，记录「拒绝原因 + 错误码」，不要只返回一个 `false`；否则线上无法区分「输入恶意」与「验证器 bug」。

| 失败模式 | 后果 | 测试 |
|:--|:--|:--|
| 接受非法模块 | 代码执行/越界 | 变异字节码、模糊测试 |
| 拒绝合法模块 | 兼容性/DoS | 规范样例、边界值 |
| 验证器崩溃 | DoS | 超大/深嵌套输入 |
| 验证超时 | DoS | 编译预算/超时 |
| 错误码不清 | 无法排障 | 断言错误分类 |


验证器的 soundness 与 completeness 要分开写。soundness：验证通过的模块不会越界/类型混淆；completeness：所有合法模块都能通过。前者是安全边界，后者是兼容性。很多引擎为了性能，验证器只做「快速路径」，复杂模块走「慢速验证/解释器」；这时 soundness 仍要成立，只是 completeness 可能下降。测试报告要分别列「非法模块被拒」与「合法模块被接受」，不能只报一个总数。


JIT 编译器本身也有供应链。它可能链接 LLVM/自研后端、依赖汇编器/链接器、读取 CPU 特性；版本升级会改变生成的代码。可复现的 JIT 证据要记录：编译器/运行时版本、后端版本、目标三元组、CPU 特性、优化级别、随机种子（如果有）。没有这些，反汇编出来的代码无法与下一次构建对照，差分测试也失去意义。

## 12.3 W^X、双重映射与代码缓存 {#sec-compilers.3.12.3}

JIT 最直接的需求是「写一段内存，然后执行它」。最朴素的做法是 `mmap(PROT_READ|PROT_WRITE|PROT_EXEC)`，但这让攻击者一旦获得任意写原语，就能直接把数据变成代码。W^X（write XOR execute）要求任何页在任意时刻不能同时可写和可执行：写的时候是 RW，执行的时候是 RX，中间用 `mprotect` 切换。

::: thm 定理 12.3.1 · W^X 的条件保证 {#thm-compilers.3.12.3.1}
假设：(1) 进程的页表中不存在同时具有写权限与执行权限的映射；(2) 攻击者不能调用 `mprotect`/`VirtualProtect` 等等价原语；(3) 代码入口只能指向已经完成权限切换的页。则攻击者仅通过写数据（包括写常量池、写代码缓冲区）不能使写入的字节被 CPU 当作指令执行。
:::

::: proof 证明
CPU 取指时检查页的执行权限；写操作检查页的写权限。若一个页不同时可写可执行，则对它的写在写入时要么被拒绝，要么发生在一个没有执行权限的页上。攻击者要让写入的字节被执行，必须让某个指令指针指向该页，或者把该页变成可执行；前者需要控制跳转目标，后者需要调用权限切换原语。条件 (2)(3) 排除了这两条路径，因此仅靠数据写不能完成「数据变代码」。证明依赖页表与 TLB 的一致性；切换权限后必须刷新 TLB，否则旧权限可能仍被使用。
:::

这个定理是条件性的，条件 (2) 尤其关键：如果攻击者已经能调用 `mprotect`，W^X 只是多了一步，不是不可逾越的墙。沙箱设计要把「谁能调用 mprotect」也纳入威胁模型；JIT 进程通常允许自己的运行时代码调用，所以攻击者一旦劫持运行时，条件 (2) 就破了。

代码内存的生命周期可以画成：

<pre class="layout">
reserve RW --&gt; emit prologue/body/constants --&gt; seal --&gt; mprotect RX
    ^                                                       |
    |                                                       v
    +---- deopt/invalidate: stop threads, wait, unmap &lt;-- execute
</pre>

读图：写和 execute 之间有一次「封存」（seal）。封存不是一次 `mprotect` 就完事：要确保所有写入完成、指令缓存同步、没有其他线程正在执行这段代码、没有栈帧还指向旧入口。去优化/失效时方向相反：先让所有线程离开这段代码（safepoint/stop-the-world），再改权限或 unmap，最后回收元数据。顺序错了，就会出现「代码正在执行时被改写」或「栈上的返回地址指向已释放页」。

平台机制不同，但形状相似：

| 平台 | 写阶段 | 执行阶段 | 备注 |
|:--|:--|:--|:--|
| Linux | `mmap(PROT_READ|PROT_WRITE)` | `mprotect(PROT_READ|PROT_EXEC)` | 可用 `memfd_create` + 双重映射 |
| macOS | `MAP_JIT` + `pthread_jit_write_protect_np` | 同一映射按线程切换 | hardened runtime 要求 entitlement |
| Windows | `VirtualProtect(PAGE_READWRITE)` | `VirtualProtect(PAGE_EXECUTE_READ)` | 改后 `FlushInstructionCache` |
| WebAssembly 引擎 | 线性内存/代码缓冲 | 引擎管理的 RX 页 | 具体实现依赖引擎 |

双重映射（dual mapping）把同一段物理页映射到两个虚拟地址：一个 RW 别名用于写，一个 RX 别名用于执行。写入通过 RW 别名，执行通过 RX 别名；两个别名指向同一物理页，所以不需要 `mprotect` 来回切。它减少了切换开销，也让「写」和「执行」的权限在任意时刻都是分离的。代价是：必须保证两个别名的偏移一致、TLB/指令缓存同步、以及卸载时同时解除两个映射。

macOS 的 `MAP_JIT` 与 `pthread_jit_write_protect_np` 是「按线程」切换写保护：一个线程在写代码时，其他线程仍可执行同一页的已封存部分。这比全局 `mprotect` 细，但也要求运行时严格配对 `enable/disable`，否则写线程可能长期持有写权限。Linux 的 `mprotect` 是进程级的，切换时其他线程会短暂看到新权限；需要 stop-the-world 或每线程代码副本来避免竞争。

常量池是另一个容易忽略的资产。它通常放在 RW、NX 的页里，代码通过固定偏移或句柄访问。攻击者如果能越界写常量池，就能改掉代码读取的常量、函数指针、类型元数据；但常量池不可执行，W^X 阻止它直接变成代码。防御包括：常量池与代码页分离、边界检查、只读化（写一次后 `mprotect` 成 RO）、以及不让代码里的偏移由输入直接决定。

| 区域 | 权限 | 内容 | 攻击者写入后能做什么 |
|:--|:--|:--|:--|
| 代码页 | RX（写时 RW） | 指令、立即数 | 改指令，需先获得写权限 |
| 常量池 | RW/RO, NX | 常量、元数据 | 改数据，不能直接执行 |
| 栈 | RW, NX | 局部变量、返回地址 | 改返回地址，受 CFI/canary 限制 |
| 堆 | RW, NX | 对象、缓存 | 改对象/指针，受类型检查限制 |
| 代码缓存索引 | RW | 键、入口、元数据 | 改映射，导致错误代码复用 |

代码缓存的失效与 W^X 交织在一起。去优化时，旧代码可能还在某个栈帧上执行；不能立刻 unmap。常见做法是：标记旧代码为「待回收」，等所有线程经过 safepoint，确认没有栈帧引用，再 unmap；在此之前，旧代码页保持 RX，不写。新代码写入新页，不覆盖旧页。这样既避免「执行中改写」，也避免「释放后使用」。

::: errata W^X 的四个误区
1. **「W^X 等于不可绕过」**：它只保证页权限分离；攻击者若能调用 `mprotect`、利用内核漏洞、或控制已有代码的跳转，仍可绕过。
2. **「mprotect 后立刻生效」**：TLB 与指令缓存需要同步；多线程下还要确保没有线程正在执行旧权限的页。
3. **「常量池可执行没关系」**：常量池通常不需要执行权限；给它 X 只会扩大攻击面。
4. **「双重映射等于两份内存」**：两个别名指向同一物理页；写一个别名，另一个别名立即可见，但指令缓存仍要刷新。
:::

页权限的转换可以列成一张表。注意「可写」与「可执行」不是二选一，而是四个组合；W^X 禁止的是 `W+X`，不是「曾经 W 过」：

| 当前权限 | 允许的操作 | 典型用途 | 风险 |
|:--|:--|:--|:--|
| RW, NX | 写代码/常量 | 编译、加载 | 不能执行 |
| RX | 取指/读常量 | 执行已封存代码 | 不能写 |
| R, NX | 读常量/元数据 | 只读常量池 | 不能写/执行 |
| RWX | 写 + 执行 | 不应出现 | 数据可直接变代码 |
| 无访问 | 已 unmap | 回收 | 悬垂指针 |

在 ARM64 上，写入指令后还要清理数据缓存并 invalidate 指令缓存，否则 CPU 可能取到旧字节；x86-64 的指令缓存与数据缓存一致性由硬件维护，但多核下仍需要序列化。JIT 运行时通常封装一个 `flush_icache_range`/`sys_icache_invalidate`，把「写完、刷缓存、封存、发布入口」做成一个原子步骤。

::: method 方法 12.3.2 · 审查代码内存生命周期 {#method-compilers.3.12.3.2}
1. 分配：是否用 RW/NX 起步？有没有预留 guard page？
2. 写入：写入长度是否检查？常量池是否在独立页？
3. 封存：是否在发布入口前完成所有写入与缓存刷新？
4. 发布：入口指针是否只指向已封存页？是否有竞态窗口？
5. 失效：是否等待 safepoint/无栈帧引用再 unmap？旧入口是否从缓存移除？
6. 回收：代码页/元数据/常量池是否一起释放？有没有双重释放/泄漏？
:::


双重映射的实现细节决定它是否真的安全。Linux 上常见做法是 `memfd_create` 创建一个匿名文件，用 `ftruncate` 定长，然后 `mmap` 两次：一次 `PROT_READ|PROT_WRITE`，一次 `PROT_READ|PROT_EXEC`。两个映射的偏移必须对齐到页；写通过 RW 别名，执行通过 RX 别名；卸载时两个 `munmap` 都要做。若两次映射的偏移不一致，代码里的相对跳转就会算错；若只解除一个别名，另一个别名仍可访问物理页，造成泄漏。

| 切换方式 | 开销 | 并发风险 | 适用 |
|:--|:--|:--|:--|
| 全局 `mprotect` | 系统调用 + TLB shootdown | 其他线程短暂看到新权限 | 单线程/可停顿 |
| 双重映射 | 一次映射，写不走 mprotect | 需要两个别名同步 | 高吞吐 JIT |
| 按线程 W^X（macOS） | 轻量 | 必须严格配对 | Apple JIT |
| 每线程代码副本 | 内存翻倍 | 副本间一致性 | 低延迟/多核 |

指令缓存是另一个平台差异。ARM64 的 I-cache 与 D-cache 不保证一致，写完代码要 `dc cvau`/`ic ivau` 或调用运行时封装；x86-64 的 I-cache 与 D-cache 一致，但多核仍需序列化指令。JIT 的「封存」步骤要把这些平台操作封装进去，不能只做 `mprotect`。


W^X 还需要 guard page。代码缓冲区末尾留一页 `PROT_NONE`，越界写入会立刻触发 `SIGSEGV`，而不是悄悄改到相邻的常量池/元数据。guard page 不能替代边界检查，但能把「越界写」从静默破坏变成可定位的崩溃。同理，常量池/元数据区之间也可以加 guard page；代价是虚拟地址空间碎片化。

| 保护 | 防什么 | 不防什么 |
|:--|:--|:--|
| W^X | 数据页直接执行 | 控制流劫持到已有代码 |
| guard page | 线性越界写 | 任意地址写/整数溢出绕过 |
| ASLR | 预测地址 | 信息泄漏后绕过 |
| CFI | 非法间接跳转 | 合法目标的错误调用 |
| 常量盲化 | 精确布局喷射 | 逻辑漏洞 |

## 12.4 沙箱谱系：进程、seccomp/landlock、Wasm {#sec-compilers.3.12.4}

沙箱不是某一个系统调用，而是一组「把不可信代码关进更小能力集合」的机制。进程沙箱用地址空间和权限位隔离；seccomp 用系统调用过滤器缩小内核接口；landlock 用可堆叠的访问控制限制文件/网络；Wasm 用验证过的字节码和线性内存把代码关在语言级虚拟机里。它们的信任边界不同，能防的东西也不同。

::: def 定义 12.4.1 · 沙箱的隔离边界 {#def-compilers.3.12.4.1}
**沙箱**是一个执行环境，它把被沙箱化的代码可观察、可修改、可调用的资源限制在一个显式策略内。**隔离边界**是策略执行的最后一层：进程沙箱的边界是内核的地址空间/权限检查；seccomp 的边界是内核的系统调用入口；Wasm 的边界是引擎的验证器与线性内存边界。边界之外的组件（内核、引擎、宿主）一旦被攻破，沙箱的保证就失效。资源限制（CPU、内存、fd 数量）只约束消耗，不改变可访问的资源集合，因此不等同于隔离。
:::

| 类型 | 隔离单位 | 内核攻击面 | 启动成本 | 能防 | 防不住 |
|:--|:--|:--|:--|:--|:--|
| 进程 + uid/gid | 地址空间、凭证 | 完整系统调用 | 低 | 直接内存访问、部分文件权限 | 同内核漏洞、继承 fd、绝对路径 |
| namespace/chroot | 视图 | 完整系统调用 | 低 | 路径/pid/网络视图 | 内核漏洞、特权操作 |
| seccomp-bpf | 系统调用 | 过滤后的系统调用 | 低 | 禁用危险 syscall | 参数指向的内存、逻辑漏洞 |
| landlock | 文件/网络访问 | 文件系统路径 | 低 | 未授权路径/端口 | 已打开 fd、内核漏洞 |
| Wasm | 线性内存/验证字节码 | 引擎 + 宿主导入 | 低到中 | 越界内存、任意 syscall | 引擎 JIT bug、宿主 API 过宽 |
| 虚拟机 | 硬件虚拟化 | 虚拟化层 | 高 | 内核级隔离 | 虚拟化逃逸、侧信道 |

### 12.4.1 进程沙箱：共享内核的边界

进程沙箱是最常见的一层：`fork` 出子进程，设置 uid/gid，`chroot` 或 mount namespace，限制 rlimit，然后 `exec` 不可信程序。它依赖内核的地址空间隔离：子进程不能直接读写父进程内存；依赖凭证检查：子进程的 uid 决定它能打开哪些文件；依赖 namespace：子进程看到的是另一棵挂载树/pid 树。

进程沙箱的弱点也在「共享内核」。所有进程共用同一个内核，内核漏洞可以让子进程逃逸；`/proc`、`ptrace`、共享内存、抽象 socket 可能跨越 namespace；继承的文件描述符是已打开的句柄，权限检查在 `open` 时已经完成，子进程拿到的 fd 不受后续路径权限影响。`chroot` 不是安全边界：root 可以逃逸，且它只改变路径解析的根，不改变已打开的 fd。

### 12.4.2 seccomp 与 landlock：缩小内核接口

seccomp-bpf 在内核系统调用入口挂一个 BPF 过滤器，按 syscall 号与参数值决定 allow/deny/trap/errno。它适合做「白名单」：只允许 `read`、`write`、`exit`、`mmap` 等必要调用，禁用 `execve`、`socket`、`ptrace`。限制也很明确：BPF 只能看寄存器里的参数值，不能解引用用户指针；一个 `write(fd, ptr, len)` 的 `ptr` 指向什么，过滤器看不到。参数检查与内核实际使用之间存在 TOCTOU；多线程程序要用 `SECCOMP_FILTER_FLAG_TSYNC` 把过滤器同步到所有线程，否则未同步的线程仍可发 syscall。

landlock 是另一个方向：不拦 syscall，而是给进程加一组「只能访问这些路径/端口」的规则。它是无特权可用的（unprivileged），可以堆叠，适合给子进程收缩文件系统权限。它管的是「能不能打开/执行某个路径」，不管已打开的 fd；也不替代 seccomp——landlock 不限制 `ptrace`、`ioctl`、`bpf` 等非文件操作。较新的内核还给 landlock 加了 TCP bind/connect 限制，但具体可用性取决于内核版本与 ABI。

macOS 没有 seccomp。它提供的是 App Sandbox（由 Sandbox.kext 执行，靠 entitlement 声明能力）、hardened runtime、以及按 XPC 服务拆分权限。`sandbox-exec` 仍然存在于 macOS 27，但已被标记为弃用；它适合做实验/兼容，不应作为长期安全边界。实验的 D 段用 `sandbox-exec` 拒绝读取一个文件，返回 `Operation not permitted`，这说明策略层确实能拦截；但它不是 Linux seccomp 的等价物，也没有可移植的 ABI。

### 12.4.3 Wasm：语言级沙箱

Wasm 的沙箱建立在「验证 + 线性内存」上。模块在编译前要经过验证器：类型、栈深度、分支目标、内存边界都要合法；验证失败的模块不能编译。运行时，所有内存访问都限制在模块自己的线性内存里，越界会 trap；模块没有原始指针，不能直接解引用宿主地址；它能调用的宿主函数必须显式导入，导入表就是能力表。

这层边界很有效，但不是「绝对安全」。引擎的验证器/JIT 可能有 bug；宿主导入如果给了 `readFile`/`exec`，沙箱里就有文件/进程能力；WASI 的 capability 设计要把预打开目录、环境变量、时钟等逐项授予。Wasm 沙箱防的是「模块越界访问宿主内存/任意 syscall」，不是「模块调用你给它的危险 API」。

下面用 Node 的 WebAssembly 验证器做一个最小实验：构造一个声明了类型段、但段长度超过实际字节的模块。命令与真实输出（Node v24.19.0，macOS 27）：

```bash
node -e 'const bad=new Uint8Array([0,97,115,109,1,0,0,0,1,3,1,96]);
console.log("validate:", WebAssembly.validate(bad));
try { new WebAssembly.Module(bad); } catch (e) {
  console.log(e.constructor.name+": "+e.message);
}'
```

```text
validate: false
CompileError: WebAssembly.Module(): section (code 1, "Type") extends past end of the module (length 3, remaining bytes 2) @+8
```

`validate` 返回 `false`，`new WebAssembly.Module` 抛出 `CompileError`，说明验证器在编译前拒绝了畸形输入。这是 Wasm 沙箱的第一道门：验证失败的模块不会进入 JIT。它不证明引擎没有 bug，也不证明导入表安全；它只证明「这个模块的结构不合法」。

::: ex 例 12.4.1 · 同一个任务，三种边界 {#ex-compilers.3.12.4.1}
任务：运行一段不可信代码，它只能读一个输入文件，不能写文件、不能联网、不能启动进程。

- **进程 + rlimit**：子进程仍能打开任何它有权访问的路径；rlimit 只限制 CPU/内存/fd 数量，不限制「能打开哪个文件」。要限制路径，得再加 landlock/chroot/uid。
- **seccomp 白名单**：只允许 `openat`，禁用写/网络/execve，能缩小 syscall；但 `openat` 仍可打开任意路径，除非用 landlock/路径检查。
- **Wasm + WASI**：只把输入文件预打开为 fd，导入表只给 `fd_read`；模块没有 `open`/`socket`/`exec` 能力。边界在引擎验证器与导入表，不在内核。

三种方案都能「跑起来」，但保证完全不同。说「我们用了沙箱」时，要能回答：边界在哪一层？策略是什么？哪些能力仍然可达？
:::


seccomp 过滤器可以写成一个只有几个分支的 BPF 程序。下面这段是伪代码，不是可直接加载的 BPF 字节码：

```text
if arch != AUDIT_ARCH_X86_64: return KILL
if nr == read:  return ALLOW
if nr == write: return (arg0 == 1) ? ALLOW : ERRNO(EPERM)
if nr == exit_group: return ALLOW
return ERRNO(EPERM)
```

它只允许读、向 stdout 写、退出；其他 syscall 一律返回 `EPERM`。注意 `arg0 == 1` 只检查了 fd 号，没有检查缓冲区指针/长度；如果攻击者能控制 `write` 的指针，过滤器看不见。BPF 的返回值也不止 `ALLOW`/`ERRNO`：还有 `KILL_THREAD`、`KILL_PROCESS`、`TRAP`、`TRACE`、`USER_NOTIF`。`USER_NOTIF` 把 syscall 交给用户态监督进程，能做更复杂的检查，但也引入 TOCTOU 与监督进程被攻破的风险。

| 机制 | 管文件路径 | 管网络 | 管已打开 fd | 管 syscall 参数指向的内存 |
|:--|:--|:--|:--|:--|
| uid/gid | 打开时检查 | 端口/权限 | 否 | 否 |
| chroot | 路径解析根 | 否 | 否 | 否 |
| seccomp | 否（只能看 syscall 号/标量参数） | syscall 级 | 否 | 否 |
| landlock | 是（路径 beneath） | 较新内核支持 TCP | 否 | 否 |
| App Sandbox | 是（entitlement） | 是（entitlement） | 部分 | 否 |
| Wasm | 仅导入能力 | 仅导入能力 | 仅导入能力 | 线性内存边界 |

landlock 的规则是「路径 beneath」：先创建一个 ruleset，声明要处理的访问类型（读文件、写文件、执行、创建、删除、网络端口等），再给某个目录加规则，最后 `restrict_self`。它不需要 root，适合在 `exec` 前给子进程收缩权限。限制是：它只对「未来打开」的路径生效；已经打开的 fd 不受影响；也不拦 `ptrace`、`ioctl`、`bpf` 等非文件操作。

macOS 的 App Sandbox 用 entitlement 声明能力，常见项包括：

| entitlement | 能力 | 风险 |
|:--|:--|:--|
| `com.apple.security.app-sandbox` | 启用沙箱 | 必须与签名/描述文件配合 |
| `com.apple.security.files.user-selected.read-only` | 用户选择的文件只读 | 只覆盖用户选择，不是全盘 |
| `com.apple.security.network.client` | 出站网络 | 可外联 |
| `com.apple.security.cs.allow-jit` | 允许 JIT | 需要 W^X 配合 |
| `com.apple.security.cs.disable-library-validation` | 关闭库校验 | 扩大注入面，慎用 |

Wasm 的能力表就是导入表。下面这段 WAT 只导入 `fd_read`，没有 `open`/`socket`/`exec`；模块能读一个已经预打开的 fd，不能打开新文件：

```text
(module
  (import "wasi_snapshot_preview1" "fd_read"
    (func $fd_read (param i32 i32 i32 i32) (result i32)))
  (memory (export "memory") 1)
  (func (export "_start") (result i32) i32.const 0))
```

这段 WAT 只用于说明导入表，不在本章构建/执行。真正的 WASI 运行时还要配置预打开目录、环境变量、时钟、随机数等能力；导入表越宽，沙箱越薄。

::: method 方法 12.4.2 · 选一层沙箱 {#method-compilers.3.12.4.2}
1. 先明确要防的是「读文件」「联网」「执行子进程」还是「内核提权」；不同目标对应不同层。
2. 不可信 native 代码：进程 + 独立 uid + namespace + seccomp/landlock；不要只靠 chroot。
3. 不可信但可移植的模块：Wasm + 最小导入表；引擎本身要打补丁。
4. macOS：App Sandbox/XPC；不要假设 seccomp 存在；`sandbox-exec` 只做实验。
5. 多层叠加：资源限制（rlimit/cgroup）+ 能力限制（fd/路径/syscall）+ 监控（超时/日志）。
6. 写清「不防什么」：内核 0day、侧信道、宿主 API 的逻辑漏洞。
:::


Wasm 的导入表就是能力表。下面这些导入分别代表不同的能力，授予前要逐项问「模块真的需要吗」：

| 导入 | 能力 | 风险 |
|:--|:--|:--|
| `fd_read` | 读已打开的 fd | 只能读预打开的资源 |
| `path_open` | 按路径打开 | 需要 preopen 目录 + 路径检查 |
| `sock_connect` | 出站连接 | 可外联/扫描 |
| `proc_exit` | 退出 | 低 |
| `clock_time_get` | 读时钟 | 可用于计时侧信道 |
| `random_get` | 随机数 | 低，但可影响可复现性 |

能力越小，沙箱越厚；但能力太小，模块跑不起来。WASI 的 preopen 设计就是折中：宿主只把特定目录暴露为 fd，模块用 `fd_read`/`fd_write` 操作，不能用任意路径。即便如此，路径穿越、符号链接、TOCTOU 仍要由运行时处理。


namespace 改变的是「视图」，不是「内核对象的所有权」。一个进程在 mount namespace 里看不到宿主目录，不代表它不能通过已打开的 fd、`/proc/<pid>/root`、或共享内存访问；network namespace 隔离了网卡/端口，但不隔离 CPU 缓存和内核全局计数器。把 namespace 当完整沙箱，和把 cwd 当牢笼是同一类错误：它们只改变了「名字解析/可见性」，没有改变「已经握在手里的能力」。


namespace 的隔离能力并不整齐：

| 资源 | mount ns | PID ns | net ns | IPC ns | 备注 |
|:--|:--|:--|:--|:--|:--|
| 文件路径 | 是 | 否 | 否 | 否 | 已打开 fd 不受影响 |
| 进程可见性 | 否 | 是 | 否 | 否 | 宿主仍可见部分信息 |
| 网络端口 | 否 | 否 | 是 | 否 | 宿主网络仍可共享 |
| 共享内存 | 否 | 否 | 否 | 是 | SysV/POSIX 语义不同 |
| CPU 缓存 | 否 | 否 | 否 | 否 | 需缓存分区/隔离核 |

## 12.5 资源限制、超时与配额 {#sec-compilers.3.12.5}

资源限制回答「能用多少」，不回答「能碰什么」。`RLIMIT_CPU` 限制 CPU 秒数；`RLIMIT_AS` 限制虚拟地址空间；`RLIMIT_FSIZE` 限制单个文件大小；`RLIMIT_NOFILE` 限制 fd 数量；`RLIMIT_NPROC` 限制同一 uid 的进程数。它们由内核在进程级别记账，子进程继承，但不会跨进程聚合，也不会撤销已打开的资源。

::: thm 定理 12.5.1 · 资源限制不构成隔离 {#thm-compilers.3.12.5.1}
设 `L` 是一组 per-process rlimit，`P` 是一个遵守 `L` 的进程。则 `L` 不限制 `P` 能打开哪些路径、能继承哪些 fd、能向哪些地址发网络请求、能读写哪些共享内存；它只限制 `P` 在 CPU 时间、地址空间、文件大小、fd 数量等维度上的消耗。因此「`P` 受 `L` 约束」不能推出「`P` 只能访问策略允许的资源」。
:::

::: proof 证明
rlimit 的检查点位于资源分配路径：CPU 调度、`mmap`/`brk`、文件扩展、fd 分配、`fork`。路径解析与权限检查由 VFS/uid/gid 决定，rlimit 不参与；已打开的 fd 是 `open` 时权限检查的结果，后续读写不再做路径检查。网络访问由 socket/namespace/防火墙决定，rlimit 不参与。共享内存由 shm 权限决定，rlimit 不参与。因此存在满足 `L` 但访问了策略外资源的进程，命题得证。
:::

实验的 A 段给出了一组真实观测（macOS 27、Python 3.13.13）：

```text
[RLIMIT_CPU=1s] rc=-24 elapsed=1.02s
[RLIMIT_FSIZE=4KiB] rc=1 out='' err_tail='OSError: [Errno 27] File too large'
[RLIMIT_NOFILE=16] rc=1 out='' err_tail="OSError: [Errno 24] Too many open files: '/dev/null'"
[RLIMIT_AS=64MiB] setrlimit rejected: current limit exceeds maximum limit
  current soft=9223372036854775807 hard=9223372036854775807 (RLIM_INFINITY=9223372036854775807)
[ulimit -v 65536] rc=1 err='bash: line 1: ulimit: virtual memory: cannot modify limit: Invalid argument' current='unlimited'
```

前三行说明限制生效：CPU 超时收到 `SIGXCPU`（返回码 -24），文件超过 4 KiB 报 `EFBIG`，fd 超过 16 报 `EMFILE`。后两行说明 macOS 27 的 `RLIMIT_AS` 有限值被拒绝：Python 的 `setrlimit` 抛 `ValueError`，C 探针的 `setrlimit(RLIMIT_AS, ...)` 返回 `-1/EINVAL`；`ulimit -v` 也报 `Invalid argument`，当前仍是 `unlimited`。这不是「脚本写错」，而是 Darwin 对这两个 limit 的实现差异。把 Linux 的「`ulimit -v` 限制内存」直接搬到 macOS，会得到「看起来设置了，实际没生效」的假象。

超时是另一类边界。`subprocess.run(timeout=...)` 在超时后杀掉直接子进程，但不会自动杀它的后代；如果子进程自己 `fork` 或 `Popen` 了孙进程，孙进程会继续运行。实验的 C 段：

```text
[timeout] wall clock hit 0.4s; subprocess.run would kill only the child
[descendant] heartbeat after child kill: 11 -> 23 (grew 12 bytes)
[descendant] killpg(SIGKILL) sent
[descendant] after killpg: 23 -> 23 (grew 0 bytes)
```

子进程被 kill 后，孙进程仍在往 heartbeat 文件写字节（11 → 23）；直到父进程对子进程所在的进程组发 `SIGKILL`，增长才停止（23 → 23）。这段输出的具体字节数会随调度变化，但「kill 子进程 ≠ kill 后代」是稳定的。修复不是「把 timeout 调小」，而是：`start_new_session=True` 建独立进程组，超时后 `killpg`；更好的做法是 cgroup/Job Object 按组记账，进程组里有人逃逸也能被统一回收。

| 控制 | 限制什么 | 不限制什么 | 典型绕过 |
|:--|:--|:--|:--|
| `RLIMIT_CPU` | CPU 秒数 | 墙钟、后代、IO 等待 | `sleep`、多进程 |
| `RLIMIT_AS` | 虚拟地址空间 | RSS 峰值、页缓存、其他进程 | 多进程各自计数 |
| `RLIMIT_FSIZE` | 单文件大小 | 文件总数、inode、磁盘总量 | 多文件、删除重写 |
| `RLIMIT_NOFILE` | fd 数量 | 已打开 fd 的读写 | 继承 fd、fd 传递 |
| `RLIMIT_NPROC` | 同 uid 进程数 | root、其他 uid | 换 uid/绕过 |
| `timeout` | 墙钟 | 后代、内核态阻塞 | 孙进程、D 状态 |
| cgroup v2 | 组记账/限额 | 内核漏洞、侧信道 | 特权逃逸 |

配额（quota）与 rlimit 不同：配额通常按用户/租户/文件系统聚合，能跨进程记账；cgroup v2 按控制组聚合 CPU/内存/PID/IO；API 网关按租户限流。它们更适合多租户，但需要特权配置，而且仍然不改变「能访问哪些资源」——一个内存配额很低的进程仍能读它有权读的所有文件。

::: method 方法 12.5.2 · 给不可信代码加限制的顺序 {#method-compilers.3.12.5.2}
1. **先关能力，再限资源**：关闭不需要的 fd（`close_fds=True`/`CLOEXEC`），丢弃不需要的环境变量，设置只读工作目录。
2. **建独立进程组/会话**：`start_new_session=True`，超时后对组发信号；有 cgroup 就用 cgroup 记账。
3. **设 rlimit**：CPU、FSIZE、NOFILE、NPROC；内存限制在 Linux 用 `RLIMIT_AS`，macOS 不要假设它生效。
4. **设墙钟超时**：超时是最后的兜底，不替代资源限制；超时后要回收后代。
5. **加策略层**：Linux 用 seccomp/landlock，macOS 用 App Sandbox/XPC；Wasm 用导入表/WASI 能力。
6. **做负例测试**：尝试读秘密文件、写工作目录外、继承 fd、启动孙进程；每个都应该失败。
:::


一个相对完整的子进程启动器至少要把「资源」「进程组」「fd」「环境」分开处理：

```python
import os, resource, signal, subprocess, sys

def limits():
    resource.setrlimit(resource.RLIMIT_CPU, (1, 1))
    resource.setrlimit(resource.RLIMIT_FSIZE, (1 << 20, 1 << 20))
    resource.setrlimit(resource.RLIMIT_NOFILE, (32, 32))

env = {"PATH": "/usr/bin:/bin", "LC_ALL": "C"}
p = subprocess.Popen(
    [sys.executable, "-I", "untrusted.py"],
    cwd="/tmp/sandbox",
    env=env,
    close_fds=True,
    start_new_session=True,
    preexec_fn=limits,
)
try:
    p.wait(timeout=5)
except subprocess.TimeoutExpired:
    os.killpg(p.pid, signal.SIGKILL)
    p.wait()
```

这段代码仍然不是完整沙箱：它没有文件系统/系统调用策略，`cwd` 不是牢笼，`preexec_fn` 在多线程父进程里也不安全（Python 文档明确警告）。它做到了「资源有上限、超时杀整组、fd 默认关闭、环境最小」；这些是必要项，不是充分项。

| rlimit | 对应的 cgroup v2 控制 | 差异 |
|:--|:--|:--|
| `RLIMIT_CPU` | `cpu.max` | rlimit 按进程累计 CPU 秒；cgroup 按组限速 |
| `RLIMIT_AS` | `memory.max` | rlimit 限虚拟地址空间；cgroup 限组内存，含页缓存 |
| `RLIMIT_NPROC` | `pids.max` | rlimit 按 uid；cgroup 按组 |
| `RLIMIT_NOFILE` | 无直接对应 | cgroup 不管 fd 数；用 rlimit |
| `RLIMIT_FSIZE` | `io.max`（带宽，不是大小） | 文件大小仍用 rlimit/配额 |

超时的实现也有细节。`subprocess.run(timeout=)` 在超时后先 `kill` 再 `wait`；如果子进程忽略 `SIGTERM`，`kill` 发的是 `SIGKILL`（Python 的实现），但只对直接子进程。要优雅关闭，先发 `SIGTERM`，等一个 grace period，再 `SIGKILL` 整组；grace period 太长会让攻击者多跑几秒，太短会误杀正常清理。

配额适合跨进程聚合：Linux cgroup v2 的 `memory.max`、`cpu.max`、`pids.max`、`io.max` 按控制组记账；文件系统 quota 按用户/项目；API 网关按 token bucket 限流。它们的共同点是「需要一个有特权的管理者」；在无特权容器里，往往只能设 rlimit，不能设 cgroup。选方案时要写清部署前提。

::: errata 资源限制的四个误区
1. **「设了 RLIMIT_AS 就限制了内存」**：macOS 27 拒绝有限值；Linux 上它限制虚拟地址空间，不等同于 RSS；多进程各自计数，聚合可超过单进程上限。
2. **「timeout 会杀整棵进程树」**：它只保证直接子进程被 kill；后代要进程组/cgroup 才能回收。
3. **「RLIMIT_NOFILE 会关闭已有 fd」**：它只限制新分配；已有 fd 仍可读写，继承的 fd 仍是能力。
4. **「rlimit 是安全边界」**：它约束消耗，不约束访问；路径/网络/syscall 需要另一层策略。
:::


`setrlimit` 还有 soft/hard 两个值。soft 是当前生效值，hard 是上限；进程可以把自己的 soft 降到 hard 以下，但不能把 hard 提高（除非有特权）。子进程继承两者。把 hard 设成和 soft 一样，等于「以后不能再放宽」；只设 soft，子进程仍可在 hard 范围内调整。审计时要看两个值，不能只看 soft。

| 维度 | soft | hard | 继承 | 备注 |
|:--|:--|:--|:--|:--|
| 当前生效 | 是 | 否 | 子进程继承 | 可降低 |
| 上限 | 否 | 是 | 子进程继承 | 提权才能升 |
| `RLIMIT_CPU` | 秒 | 秒 | 是 | 超时发 `SIGXCPU` |
| `RLIMIT_NOFILE` | 个数 | 个数 | 是 | 已达 fd 不受影响 |

`RLIMIT_NPROC` 按 uid 计数，root 通常不受限；容器里如果共享 uid，一个租户的 fork 会影响另一个租户。用 cgroup 的 `pids.max` 按组计数更稳。`RLIMIT_CPU` 只算 CPU 时间，不算阻塞/睡眠；一个 `sleep 3600` 的进程不会触发 CPU 限制，但会触发墙钟超时。


超时的语义要按 API 写清楚：

| API/机制 | 计时对象 | 超时后做什么 | 注意 |
|:--|:--|:--|:--|
| `subprocess.run(timeout=)` | 墙钟 | kill 直接子进程，wait | 不杀后代 |
| `Popen.wait(timeout=)` | 墙钟 | 抛异常，不自动 kill | 调用方负责清理 |
| `SIGALRM` | 墙钟 | 递送信号 | 信号处理函数要异步安全 |
| `RLIMIT_CPU` | CPU 秒 | `SIGXCPU`，可升级 `SIGKILL` | 睡眠/阻塞不计 |
| cgroup `cpu.max` | 组 CPU 带宽 | 限流/节流 | 不杀进程 |
| cgroup `pids.max` | 组进程数 | `fork` 失败 | 已存在进程不受影响 |

「超时」不是一种机制，而是一族机制；选错计时对象，就会出现「CPU 限制没触发，因为进程在 sleep」或「墙钟到了，但子进程还在跑」。


`RLIMIT_NPROC` 按真实 uid 计数，root 通常豁免；容器里如果多个租户共享 uid，一个租户的 fork 会影响另一个。把 `RLIMIT_NPROC` 当租户隔离，在共享 uid 的部署里会失效。更稳的是 cgroup 的 `pids.max`（按组）加独立 uid；两者都要，才能同时限制「单进程」与「整组」。

## 12.6 侧信道、共享资源与拒绝服务 {#sec-compilers.3.12.6}

沙箱能阻止「直接读文件」，但阻止不了「通过时间/缓存观察另一个租户」。侧信道（side channel）利用共享硬件资源：CPU 缓存、分支预测器、TLB、内存带宽、页缓存、频率/功耗。JIT 生成的代码与解释器共享同一颗 CPU、同一级缓存；代码缓存、常量池、内联缓存的位置会影响缓存行竞争。一个租户的访问模式可能被另一个租户观测到，即使它们的地址空间完全隔离。

共享资源不止 CPU。`/tmp`、`/dev/shm`、抽象 Unix socket、PID、进程表、文件锁、inotify watch、epoll 实例、熵池、页面缓存、GPU、日志文件都是跨进程共享的。namespace 能把其中一部分隔离（mount、pid、network、ipc），但不是全部；`/proc` 的某些文件、内核全局计数器、硬件性能计数器仍可能泄漏信息。

拒绝服务（DoS）是另一类：沙箱能阻止代码执行，但不能阻止它耗尽资源。算法复杂度攻击（一个输入让排序变成平方级）、内存放大（一个小输入解压成巨大对象）、fork 炸弹、磁盘填满、inode 耗尽、日志洪水、JIT 编译炸弹（大量不同形状的函数触发编译）、去优化抖动（在快慢路径之间反复）、代码缓存膨胀。防御是配额、超时、速率限制、编译预算、缓存上限，而不是「沙箱」两个字。

| 资源 | 共享方式 | 可观察/可利用 | 缓解 |
|:--|:--|:--|:--|
| CPU 缓存 | 同一物理核/缓存层级 | 时间侧信道 | 缓存分区、常量时间、隔离核 |
| 分支预测器 | 同一核 | Spectre 类 | 屏障、IBRS、代码审计 |
| 页缓存 | 同一文件系统 | 文件访问时间/存在性 | 独立文件系统、预取噪声 |
| `/tmp` | 全局目录 | 文件名/内容/符号链接 | 每租户私有目录、`O_NOFOLLOW` |
| `/dev/shm` | 全局 tmpfs | 共享内存读写 | IPC namespace、权限 |
| PID/进程表 | 全局 | 进程存在性/数量 | PID namespace、隐藏 |
| 磁盘/inode | 全局 | 填满 | 配额、只读层 |
| JIT 代码缓存 | 进程内/共享 | 编译抖动、缓存污染 | 编译预算、缓存上限、隔离 |

JIT 特有的 DoS 值得单独列：

- **编译炸弹**：输入生成大量不同类型的函数/循环，触发反复编译；每次编译都分配代码页和元数据。
- **去优化抖动**：守卫反复失败，代码在优化/未优化之间来回切换；CPU 花在编译而不是业务。
- **代码缓存膨胀**：缓存键太多（类型组合爆炸），旧代码不回收，内存持续增长。
- **内联缓存污染**：一个调用点被大量不同类型命中，退化成 megamorphic，性能骤降。

这些问题的共同点是「资源消耗与输入形状相关」，而资源限制只设了上限，没有设「编译预算/缓存预算」。多租户 JIT 要按租户隔离代码缓存、限制编译次数/代码页总量、在去优化率过高时降级到解释器。

::: ex 例 12.6.1 · cwd 不是文件系统边界 {#ex-compilers.3.12.6.1}
实验的 B 段把子进程的 `cwd` 设为 `sandbox/`，子进程却用绝对路径写到了 `outside/escape.txt`：

```text
[cwd] child cwd=sandbox/ wrote outside exists=True
  content='escaped'
```

`cwd` 只影响相对路径的解析起点；绝对路径、`..`、符号链接都可以离开它。要限制写入范围，需要 mount namespace + 只读 bind mount、landlock 规则、或把子进程放进一个只写特定目录的容器。`cwd` 适合做「默认工作目录」，不适合做「牢笼」。
:::

侧信道没有「一键修复」。能做的包括：把秘密相关的时间/地址/分支尽量从代码里去掉（常量时间）；隔离共享缓存（缓存着色、core scheduling）；限制跨租户的并发；对高价值操作使用独立进程/机器；接受「同一物理机上的强隔离需要硬件/虚拟化」这一事实。沙箱文档要写清「不防侧信道」，否则读者会以为隔离等于保密。

侧信道按共享资源分类，比「时间攻击」这个笼统说法更有用：

| 类别 | 共享什么 | 典型观察 | 缓解 |
|:--|:--|:--|:--|
| 缓存 | L1/L2/L3、TLB | 访问时间、缓存行状态 | 缓存分区、常量时间、隔离核 |
| 分支预测 | 预测器/历史 | 分支结果、Spectre 类 | 屏障、IBRS、代码审计 |
| 页缓存 | 文件系统缓存 | 文件是否存在/被访问 | 独立文件系统、预取噪声 |
| 内存去重 | 页合并 | 页面是否共享 | 关闭去重、加密内存 |
| 频率/功耗 | 电源管理 | 负载/指令类型 | 固定频率、噪声 |
| GPU/加速器 | 显存/队列 | 计算时间、缓存 | 分区、独立设备 |
| 网络 | 带宽/队列 | 流量形状 | 填充、限速 |

共享资源清单要按部署环境写，不能只写「/tmp」：

| 资源 | 默认共享范围 | namespace 能隔离吗 | 备注 |
|:--|:--|:--|:--|
| `/tmp` | 主机 | mount namespace（私有 tmpfs） | 符号链接/竞态 |
| `/dev/shm` | 主机 | IPC namespace | 共享内存读写 |
| 抽象 Unix socket | 网络 namespace | 是（Linux） | 名字全局可见 |
| PID/进程表 | 主机 | PID namespace | 仍可观察宿主部分信息 |
| 文件锁 | 文件系统 | 取决于挂载 | 跨容器可冲突 |
| inotify watch | 主机 | 部分 | 可观察路径事件 |
| 熵池 | 内核 | 否 | 早期启动耗尽 |
| 页缓存 | 主机 | 否（按文件） | 访问时间/命中 |

DoS 的分类同样要按「消耗什么」来列：

| 类型 | 例子 | 消耗 | 缓解 |
|:--|:--|:--|:--|
| 算法复杂度 | 哈希碰撞、退化的排序输入 | CPU | 输入上限、算法审计 |
| 内存放大 | 解压炸弹、深度嵌套 | 内存 | 解压上限、流式处理 |
| 进程炸弹 | `fork` 循环 | PID/调度 | `pids.max`、`RLIMIT_NPROC` |
| 磁盘/inode | 小文件洪水、日志 | 磁盘/inode | quota、只读层、轮转 |
| 编译炸弹 | 大量形状触发 JIT | CPU/代码页 | 编译预算、缓存上限 |
| 去优化抖动 | 守卫反复失败 | CPU | 去优化率阈值、降级解释器 |
| 网络 | 慢连接、放大反射 | 连接/带宽 | 超时、限速、SYN cookie |

JIT 的 DoS 有一个特点：攻击者不需要让程序「算得慢」，只需要让「编译得多」。每次编译都分配代码页、常量池、元数据；编译预算不设上限，输入形状就能把内存吃光。防御要在 JIT 层做：限制单租户代码页总量、每单位时间的编译次数、单个函数的 IR 大小/嵌套深度；超过阈值就降级到解释器或拒绝。

侧信道与 DoS 都不在「访问控制」的范畴里。沙箱能说「你不能读这个文件」，但不能说「你读这个文件的时间不会泄漏给邻居」；沙箱能说「你不能超过 1 秒 CPU」，但不能说「你的输入不会让编译器吃光内存」。安全文档要把这两类风险单独列出，别用「已沙箱化」一笔带过。


侧信道是否在威胁模型内，要在文档里明确写。下面这张表可以直接抄进安全说明：

| 问题 | 如果答案是「是」 | 如果答案是「否」 |
|:--|:--|:--|
| 攻击者与受害者共享物理核？ | 需要缓存/分支隔离 | 可接受同机 |
| 攻击者能测量细粒度时间？ | 常量时间/噪声 | 时间不是秘密 |
| 共享文件系统/页缓存？ | 独立挂载/预取噪声 | 可共享 |
| 共享 GPU/加速器？ | 分区/独立设备 | 可共享 |
| 多租户 JIT 共享代码缓存？ | 按租户隔离/配额 | 可共享 |

「不防侧信道」不是耻辱，伪装成「防了」才是。把边界写清楚，用户才能决定是否把秘密放进这个沙箱。


共享资源不能靠「读文档」确认，要靠实验。至少做三组：

1. **路径共享**：两个租户同时往 `/tmp` 写同名文件/符号链接，观察是否能覆盖/读取对方。
2. **IPC 共享**：一个租户创建抽象 socket/共享内存，另一个租户尝试连接/映射；确认 namespace 是否真的隔离。
3. **调度共享**：一个租户跑 CPU 密集任务，另一个租户测延迟/吞吐；观察是否有跨租户的性能干扰。

实验结果要写成「资源 → 是否共享 → 证据 → 缓解」。没有实验的「我们隔离了」只是声明。


侧信道不是沙箱的「bug」，而是威胁模型的一部分。任何共享硬件的隔离（进程、容器、VM）都可能有侧信道；区别在于攻击者需要什么前提（同核、同缓存、能测时间）、能观察到什么、值不值得防。安全说明要写「本沙箱不防跨租户侧信道」，而不是假装隔离等于保密。


侧信道评估要先固定实验条件，否则测出来的差异可能只是噪声：

| 问题 | 为什么重要 | 最低要求 |
|:--|:--|:--|
| 攻击者与受害者同核吗？ | 同核才有缓存/预测器共享 | 记录 CPU 亲和性 |
| 能测多细的时间？ | 纳秒级才能看缓存命中 | 用 `rdtsc`/单调时钟，报告分布 |
| 有噪声源吗？ | 频率/调度会淹没信号 | 多次重复、中位数/置信区间 |
| 共享什么缓存层级？ | L1/L2/L3 影响不同 | 记录 CPU 型号/拓扑 |
| 缓解是否可观测？ | 分区/固定频率改变结果 | 对照实验，不只看单次 |

没有这些条件，「我们测了侧信道，没测到」没有意义。侧信道结论和性能结论一样，要带实验设置。

## 12.7 验证 JIT 输出：反汇编、差分与随机化 {#sec-compilers.3.12.7}

JIT 生成的代码没有源码可读，只有字节和元数据。验证它的第一步不是「看代码像不像」，而是把字节变成可检查的表示：反汇编、控制流图、守卫列表、栈映射、重定位表。然后再用差分/随机化检查语义：同一段输入，JIT 的结果要与解释器/参考实现一致；同一段字节码，在不同优化级别/不同编译次数下要一致。

::: def 定义 12.7.1 · JIT 输出的可复核证据 {#def-compilers.3.12.7.1}
JIT 输出的**可复核证据**是一组能独立重放的记录：代码字节的哈希与长度；反汇编文本与起始地址；编译器版本、目标三元组、CPU 特性；守卫及其失败目标；常量池布局与重定位；代码页的最终权限；缓存键与失效条件。只有「能重放、能对照」的证据才算数；「我看过，应该没问题」不是证据。
:::

先看一个可以反汇编核对的最小例子。C 源码：

```c
unsigned sat_add(unsigned a, unsigned b) {
    unsigned s = a + b;
    return s < a ? ~0u : s;
}
```

它做无符号饱和加法：溢出时返回 `UINT_MAX`，否则返回和。用 x86-64 目标生成汇编（宿主是 arm64，所以这是交叉生成；JIT 也可能为不同目标生成代码）：

```bash
clang -target x86_64-apple-darwin -std=c17 -Wall -Wextra -Werror -O2 \
      -S sat_add.c -o sat_add.s
clang -target x86_64-apple-darwin -c sat_add.s -o sat_add.o
llvm-objdump -d sat_add.o
```

关键汇编行（省略调试/CFI 指令）：

```asm
_sat_add:
	pushq	%rbp
	movq	%rsp, %rbp
	addl	%esi, %edi
	movl	$-1, %eax
	cmovael	%edi, %eax
	popq	%rbp
	retq
```

反汇编（真实输出，macOS 27、LLVM 22.1.8）：

```text
0000000000000000 <_sat_add>:
       0: 55                           	pushq	%rbp
       1: 48 89 e5                     	movq	%rsp, %rbp
       4: 01 f7                        	addl	%esi, %edi
       6: b8 ff ff ff ff               	movl	$0xffffffff, %eax
       b: 0f 43 c7                     	cmovael	%edi, %eax
       e: 5d                           	popq	%rbp
       f: c3                           	retq
```

这段输出要怎样读？`addl` 把 `a+b` 写进 `edi`，并在无符号溢出时置进位标志；`movl $-1, %eax` 把候选返回值设为 `UINT_MAX`；`cmovael` 在进位为 0（无溢出）时把 `edi` 移到 `eax`。JIT 验证器要检查的不是「指令名字对不对」，而是「这段代码的语义是否等于字节码的饱和加法」：溢出分支、返回值、标志使用、调用约定都要覆盖。一个把 `cmovael` 写成 `cmovbl` 的 JIT 会在溢出时返回错误结果；反汇编能发现这个差异，差分测试能发现结果不一致，两者互补。

| 验证手段 | 能发现 | 可能漏掉 | 成本 |
|:--|:--|:--|:--|
| 反汇编对照 | 指令选择、守卫、常量、调用约定 | 语义等价但指令不同、运行时状态 | 低 |
| 差分执行 | 结果/异常不一致 | 两边同错、未覆盖输入 | 中 |
| 随机化/属性测试 | 边界、类型组合 | 稀有路径、侧信道 | 中 |
| 翻译验证 | 单次生成的语义等价 | 规约/检查器错误 | 高 |
| 页权限检查 | RWX、意外可写 | 逻辑漏洞 | 低 |

JIT 验证的检查清单应该包括：

1. **代码页权限**：执行时 RX，写入时 RW，不能有 RWX；常量池 NX。
2. **入口与边界**：入口地址在代码页内，长度与元数据一致；不跳到常量池/栈。
3. **守卫**：每个 profile 假设都有守卫；守卫失败目标在代码页内；守卫不能被输入直接改写。
4. **栈映射**：每个 safepoint 的栈布局与 GC 元数据一致；返回地址/帧指针在范围内。
5. **重定位/常量**：常量池偏移在界内；外部符号通过受控 relocation 解析。
6. **缓存键**：键包含所有影响语义的假设；失效时旧代码不再被命中。
7. **并发**：编译、封存、执行、失效之间没有「执行中改写」或「释放后使用」。

差分测试要注意 oracle。把 JIT 结果与解释器比较，如果解释器也有 bug，两边可能同错；把 JIT 结果与另一个 JIT 比较，两个 JIT 可能共享同一个前端 bug。更稳的做法是：用规格/参考实现生成期望值，用属性测试检查不变量（例如饱和加法的结果一定 `\ge a` 且 `\ge b`），再用反汇编检查代码形状。三者结合，才不容易被「两边同错」骗过。

随机化不是「随便跑」。要控制输入分布：类型标签、边界值（0、1、UINT_MAX）、对齐、长度、嵌套深度；要记录 seed 与失败输入；要能把失败输入缩减到最小。JIT 的随机化还要覆盖「编译次数/优化级别/去优化」这些维度：同一个函数在冷代码、热代码、去优化后的代码上结果必须一致。

::: method 方法 12.7.2 · 审一段 JIT 输出 {#method-compilers.3.12.7.2}
1. 记录编译器版本、目标三元组、CPU 特性、优化级别、缓存键；缺一项就无法复现。
2. dump 代码字节与长度，计算哈希；确认入口在代码页内。
3. 反汇编，标出守卫、调用、返回、常量加载；与字节码逐段对照。
4. 检查页权限：执行段 RX、写段 RW、常量池 NX；确认没有 RWX。
5. 跑差分/属性测试，记录 seed 与失败输入；把失败输入缩减。
6. 检查失效路径：去优化/缓存淘汰后，旧代码是否还可能被跳转；栈上是否还有旧帧。
:::


差分框架的形状很简单：候选实现（JIT 生成的函数）与参考实现（解释器/规格）对同一组输入比较结果。真实 JIT 还要比较异常、副作用、资源消耗；下面用 Python 模拟这个形状：

```python
def sat_add(a: int, b: int) -> int:
    s = (a + b) & 0xFFFFFFFF
    return 0xFFFFFFFF if s < a else s

cases = [(0, 0), (1, 2), (0xFFFFFFFF, 1), (0x80000000, 0x80000000)]
bad = []
for a, b in cases:
    got = sat_add(a, b)
    want = min(a + b, 0xFFFFFFFF)
    if got != want:
        bad.append((a, b, got, want))
print("bad:", bad)
print("cases:", len(cases))
```

```text
bad: []
cases: 4
```

真实 JIT 的差分还要覆盖：`a+b` 溢出、`a/b` 除零、NaN、对象类型、数组越界、异常路径。参考实现要么是解释器，要么是规格生成的期望值；两者都可能错，所以要再加属性检查（例如饱和加法的结果一定不小于任一操作数）。

| 检查 | 证据 | 漏掉什么 |
|:--|:--|:--|
| 结果相等 | 返回值 | 副作用/异常 |
| 异常相等 | trap/错误码 | 错误消息/时序 |
| 副作用相等 | 内存/IO 日志 | 未观察的全局状态 |
| 资源相等 | 编译/执行计数 | 侧信道 |
| 代码形状 | 反汇编/守卫 | 语义等价但不同指令 |


JIT 验证的误报/漏报要提前列出来，避免把「反汇编看起来对」当成证明：

| 现象 | 类型 | 原因 | 处理 |
|:--|:--|:--|:--|
| 反汇编把数据当指令 | 误报 | 代码中嵌入常量/跳转表 | 用符号/边界标注，只反汇编入口区间 |
| 守卫被优化掉 | 漏报 | 编译器认为条件恒真 | 检查 IR/最终代码，加不透明守卫 |
| 栈映射过期 | 漏报 | 编译后修改了帧布局 | 生成时绑定，校验哈希 |
| 差分两边同错 | 漏报 | 参考实现共享 bug | 加规格/属性/第三方实现 |
| 页权限检查通过但仍有 RWX | 漏报 | 检查的是错误区间/别名 | 枚举所有映射，查物理页 |
| 缓存键碰撞 | 漏报 | 键哈希冲突/漏字段 | 用结构化键 + 全字段比较 |


重定位是 JIT 代码与元数据的接缝。代码里的绝对地址（常量池、函数入口、全局变量）在 ASLR/GC 下不能写死；要么用相对寻址，要么在加载时重定位。重定位表本身也是攻击面：攻击者改一个偏移，就能让代码跳到错误地址。验证时要检查重定位项在界内、目标在允许的段、加载后没有被二次修改。


差分测试的输入生成要覆盖「类型 × 边界 × 形状」：类型（int/uint/float/object/null）、边界（0、1、最大值、最小值、NaN）、形状（标量/数组/嵌套对象/大字符串）。随机生成器要能复现：记录 seed、生成器版本、失败输入；失败后先缩减，再修复。只跑「正常输入」的差分，发现不了守卫/溢出/类型混淆。

## 12.8 agent 错误：把 RLIMIT 当安全边界 {#sec-compilers.3.12.8}

这一节复现一个 agent 生成的「沙箱」。任务：运行一段不可信 Python 代码，限制它只能读写临时目录，不能读宿主秘密，最多跑 5 秒，最多用 1 秒 CPU。agent 写了：

```python
import resource, subprocess, sys

def run_untrusted(path: str):
    def limit():
        # 另一版还试过 RLIMIT_AS；macOS 上 setrlimit 直接失败
        resource.setrlimit(resource.RLIMIT_CPU, (1, 1))

    return subprocess.run(
        [sys.executable, path],
        cwd="/tmp/sandbox",
        env={},
        timeout=5,
        preexec_fn=limit,
    )
```

agent 的报告写：「已用 rlimit 限制 CPU，用 timeout 限制墙钟，用 cwd 限制工作目录，用 env={} 清理环境，因此不可信代码不能访问宿主资源。」这段话把「限制消耗」与「限制访问」混为一谈。实验的 B/C 段给出了反例：

```text
[cwd] child cwd=sandbox/ wrote outside exists=True
  content='escaped'
[env cleaned] rc=0 out='LAB_SECRET=<missing>' err_tail=''
[env passed] rc=0 out='LAB_SECRET=ENV_SECRET=alpha' err_tail=''
[fd passed] rc=0 out='fd 3 => TOP_SECRET=swordfish' err_tail=''
[fd closed] rc=1 out='' err_tail='OSError: [Errno 9] Bad file descriptor'
```

逐条看：

- **cwd**：子进程用绝对路径写到了 `outside/escape.txt`。`cwd` 只改变相对路径的起点，不是文件系统边界。
- **env**：`env={}` 确实让 `LAB_SECRET` 消失（`<missing>`），但只要调用方把秘密放进子进程的环境（`env passed`），子进程就能读到。清理环境是「不主动给」，不是「不能拿」。
- **fd**：父进程把打开的 fd 通过 `pass_fds` 传给子进程，子进程读到 `TOP_SECRET=swordfish`；不传时读同一个 fd 号得到 `EBADF`。fd 是能力（capability）：一旦继承，rlimit 不会撤销它。
- **timeout**：12.5 的 C 段已经显示，kill 直接子进程后孙进程还在写 heartbeat；agent 的 `timeout=5` 同样管不到后代。

还有一条更隐蔽：agent 在 macOS 上设置 `RLIMIT_AS` 想限制内存，但 12.5 的 A 段显示 `setrlimit` 直接被拒绝，当前仍是 `unlimited`。agent 的代码没有检查返回值/异常，报告里却写「内存已限制」。这不是「限制太松」，是「限制根本没生效」。

::: ex 例 12.8.1 · 一个 fd 就是一条能力 {#ex-compilers.3.12.8.1}
父进程打开 `secret.txt` 得到 fd 3，启动子进程时把它放进 `pass_fds=(3,)`。子进程执行 `os.read(3, 128)`，读到 `TOP_SECRET=swordfish`。整个过程中：

- 子进程的 uid/gid 没变；
- `cwd` 在 `sandbox/`；
- `RLIMIT_CPU` 仍为 1 秒；
- `env` 里没有秘密。

唯一让读取成功的是继承的 fd。fd 在 `open` 时已经通过了权限检查，之后的 `read` 不再看路径/uid。要阻止它，必须在 `exec` 前关闭 fd（`close_fds=True` 且不传 `pass_fds`），或用 `CLOEXEC` 标记，而不是加大 rlimit。
:::

根因可以拆成四层：

| 层 | agent 的假设 | 实际 | 修复 |
|:--|:--|:--|:--|
| 资源 | rlimit 限制一切 | rlimit 只限制消耗维度 | 用 cgroup/配额 + 策略层 |
| 路径 | cwd 是牢笼 | cwd 只是相对路径基准 | mount namespace/landlock/chroot+uid |
| 环境 | env={} 清空能力 | env 只是环境变量 | 不传秘密；用能力句柄/服务 |
| fd | 子进程只拿到 stdio | fd 可继承/传递 | close_fds、CLOEXEC、fd 白名单 |
| 后代 | timeout 杀整棵树 | 只杀直接子进程 | 进程组/cgroup/Job Object |
| 内存 | RLIMIT_AS 生效 | macOS 拒绝有限值 | 平台检测 + 容器/VM |

**症状**：子进程仍能读秘密、写目录外、继承 fd、留下孙进程；**根因**：把 rlimit/cwd/env/timeout 当成能力边界；**如何发现**：跑实验 B/C 段与负例测试；**修复**：close_fds、路径/系统调用策略、进程组/cgroup、平台检测。

发现这些问题不需要读内核源码，只需要负例测试：让子进程尝试读秘密、写工作目录外、读 fd 3、启动孙进程、分配大内存；每个动作都应该失败。agent 的测试只覆盖了「正常代码能跑」，没有覆盖「恶意代码不能跑」。安全测试的重点是否例，不是正例。

修复后的方案至少要做到：

- **能力最小化**：不把秘密放进环境/命令行；不需要的 fd 全部关闭；用 `O_CLOEXEC`。
- **文件系统边界**：Linux 用 mount namespace + 只读 bind mount + landlock；macOS 用 App Sandbox/XPC，不能只靠 cwd。
- **进程边界**：独立 uid、独立进程组、cgroup/Job Object；超时杀整组。
- **系统调用边界**：Linux seccomp 白名单 + landlock；macOS App Sandbox entitlement；Wasm 用导入表。
- **资源边界**：rlimit + cgroup/配额；macOS 不要假设 `RLIMIT_AS` 生效。
- **验证**：负例测试 + 审计报告，明确写出「不防什么」。

::: method 方法 12.8.2 · 审计一个「子进程沙箱」 {#method-compilers.3.12.8.2}
1. 列出子进程继承的 fd：`/proc/self/fd`（Linux）或 `lsof -p`（macOS）；确认没有秘密/网络/目录句柄。
2. 列出环境变量与命令行：秘密不能出现在 `env`/argv`；敏感配置用 fd 或一次性令牌。
3. 尝试绝对路径/`..`/符号链接写工作目录外；失败才算有文件系统边界。
4. 尝试 `fork`/`setsid` 启动后代；超时后检查是否还有进程存活。
5. 检查每个 `setrlimit` 的返回值；在不支持的平台（如 macOS 的 `RLIMIT_AS`）记录「未生效」，不要写「已限制」。
6. 检查策略层：seccomp/landlock/App Sandbox/Wasm 导入表是否真的启用；没有策略层就只算「资源限制」，不算「沙箱」。
:::


修复后的 runner 至少要能被负例测试验证。负例矩阵：

| 测试 | 期望 | 证据 |
|:--|:--|:--|
| 读宿主秘密 | 失败 | `open` 被 landlock/沙箱拒绝 |
| 写工作目录外 | 失败 | 绝对路径被 mount namespace 限制 |
| 读继承 fd 3 | 失败 | `close_fds`/`CLOEXEC` |
| `fork` 孙进程 | 超时后无存活 | 进程组/cgroup 回收 |
| 分配大内存 | 失败/被杀 | cgroup/VM 限制 |
| 超时 | 整组被杀 | `killpg` + `wait` |
| 读环境秘密 | 看不到 | 不把秘密放进 env |

这些测试要进 CI，且在修复前必须红。只写「已加 sandbox」而没有负例，等于没有验证。

审计命令（Linux/macOS 各一套）：

```bash
# Linux：看子进程继承的 fd
ls -l /proc/$PID/fd
# macOS：看打开的文件/管道
lsof -p $PID
# 看进程组/会话
ps -o pid,ppid,pgid,sess,command -p $PID
```

命令输出因进程而异，本章不贴伪造的样例；关键是检查「有没有 fd 指向秘密/目录/ socket」「pgid 是否独立」。


agent 的报告要按「声明—证据—未覆盖」三栏写，不能只写「已完成」：

| 声明 | 证据 | 未覆盖 |
|:--|:--|:--|
| 资源受限 | `RLIMIT_CPU`/`FSIZE`/`NOFILE` 的返回值与实测输出 | macOS `RLIMIT_AS` 未生效 |
| 文件系统受限 | landlock/mount namespace 配置 + 负例 | 已打开 fd 的读写 |
| 环境清理 | `env` 白名单 + 负例 | 命令行/配置文件泄漏 |
| 后代回收 | 进程组/cgroup + 超时测试 | 双 fork/`setsid` 逃逸 |
| 系统调用受限 | seccomp 过滤器 + 负例 | 参数指向的内存/TOCTOU |

这张表可以直接作为 PR 模板。没有「未覆盖」栏的报告，默认不可信。


agent 的测试盲区通常不是「没写测试」，而是「只写正例」。它测了「正常脚本能跑」「超时能触发」「cwd 里有文件能读」，却没测「读秘密失败」「写目录外失败」「fd 3 读不到」「孙进程被杀」。安全测试要把「应该失败」的用例写成断言；只断言「正常路径成功」，等于只验证了功能，没有验证边界。


平台检测要写进代码，而不是假设。一个最小的检查：

```python
import resource, sys

def set_memory_limit(nbytes: int) -> bool:
    if sys.platform == "darwin":
        return False  # Darwin 27 拒绝 RLIMIT_AS 有限值
    try:
        resource.setrlimit(resource.RLIMIT_AS, (nbytes, nbytes))
        return True
    except (ValueError, OSError):
        return False
```

返回 `False` 时，runner 必须记录「内存限制未生效」，并改用容器/VM/监控；不能静默继续，更不能在报告里写「已限制」。

## 12.10 本章陷阱（8–15 条） {#sec-compilers.3.12.10}

::: errata 本章陷阱
1. **把 rlimit 当隔离**：现象是限制了 CPU/内存却仍能读秘密文件；原因是 rlimit 只约束消耗；修复是加 fd 关闭、路径/系统调用策略。
2. **把 cwd 当牢笼**：现象是子进程用绝对路径写到目录外；原因是 cwd 只影响相对路径；修复是 mount namespace/landlock/只读挂载。
3. **把 env={} 当清空能力**：现象是秘密仍可通过继承 fd/命令行/配置文件拿到；原因是 env 只是环境变量；修复是能力最小化，不传秘密。
4. **忽略继承 fd**：现象是子进程读到父进程打开的文件；原因是 fd 在 open 时已通过权限检查；修复是 close_fds/CLOEXEC。
5. **timeout 只杀直接子进程**：现象是孙进程继续写文件/占 CPU；原因是 timeout 不遍历进程树；修复是进程组/cgroup/Job Object。
6. **在 macOS 假设 RLIMIT_AS 生效**：现象是 setrlimit 被拒绝、内存仍 unlimited；原因是 Darwin 实现差异；修复是检测平台，用容器/VM 或 cgroup（Linux）。
7. **把 JIT 缓存键当无关紧要**：现象是错误类型的代码被复用；原因是键漏了类型/标志/profile 版本；修复是补全键并做过期/失效测试。
8. **给常量池可执行权限**：现象是 W^X 被破坏；原因是图省事用 RWX；修复是代码/常量池分离，常量池 NX。
9. **mprotect 后不刷新指令缓存**：现象是执行到旧字节/半成品；原因是 TLB/I-cache 未同步；修复是按平台刷新并 stop-the-world。
10. **把 seccomp 当路径过滤器**：现象是允许 openat 后仍能打开任意路径；原因是 BPF 不能解引用路径；修复是 seccomp + landlock/路径检查。
11. **把 Wasm 验证当万能沙箱**：现象是模块通过验证却通过导入表读文件；原因是能力在导入表；修复是审计 WASI/宿主导入。
12. **忽略侧信道**：现象是地址空间隔离但仍能观测时间/缓存；原因是共享硬件；修复是常量时间/缓存分区/独立机器，并在文档中声明不防侧信道。
13. **代码缓存无上限**：现象是内存随输入形状增长；原因是编译预算/淘汰策略缺失；修复是限制代码页总量与编译次数。
14. **只测正例**：现象是正常代码能跑，恶意输入也能跑；原因是缺少负例；修复是把读秘密/写目录外/继承 fd/孙进程加入测试。
15. **把「验证通过」当成「引擎无 bug」**：现象是 Wasm/字节码验证通过后仍越界；原因是验证器只保证模块结构，不保证引擎 JIT 正确；修复是引擎补丁、模糊测试、最小权限导入。
:::

| JIT 崩溃在奇怪地址 | 代码页权限/缓存键 | RWX、错误代码复用 |
| 反汇编与源码不符 | 目标/优化级别/符号 | 交叉编译、内联、常量池 |
| 沙箱「通过」但可外联 | 导入表/seccomp | 过宽的宿主 API |

这张表是排障顺序，不是根因清单；每一条都要用实验确认，不能凭症状猜。

发布门禁可以按「证据类型」列，而不是按「工具名」列：

| 门禁 | 通过条件 | 证据 |
|:--|:--|:--|
| 输入验证 | 畸形模块全部拒绝 | 验证器负例集 |
| 代码生成 | 反汇编/守卫/栈映射检查通过 | dump + 期望模式 |
| 差分 | 候选与参考在测试矩阵一致 | seed、失败输入 |
| 权限 | 执行段 RX、常量池 NX、无 RWX | 页权限 dump |
| 缓存 | 键完整、失效后不命中旧代码 | 单元测试/日志 |
| 隔离 | 负例矩阵全部失败 | CI 报告 |
| 资源 | 超时/配额/后代回收 | 压测/故障注入 |

任何一项「未知」都不能算通过；报告里要有 `PASS/FAIL/UNKNOWN` 三态。第 14 章的裁决协议会把这条原则用在 agent 代码上。

::: note 一份 JIT/沙箱的发布报告 {#note-compilers.3.12.11.1}
至少写：目标平台与版本；威胁模型（防谁、不防谁）；JIT 的缓存键与失效条件；代码页权限与 W^X 实现；验证器/导入表/系统调用策略；资源限制及其未生效项（例如 macOS 的 `RLIMIT_AS`）；负例测试结果；已知侧信道/DoS 风险。把「未覆盖」写出来，比把「已加固」写满更有用。
:::


证据优先级：可复现的实验 > 可重放的日志 > 反汇编/页权限 dump > 口头声明。发布报告里，任何一条「已验证」都要能指向一个可重放的命令或日志；指向文档/博客不算证据。


| 证据 | 命令/文件 | 通过标准 |
|:--|:--|:--|
| 代码字节 | dump + hash | 与发布版本一致 |
| 反汇编 | `llvm-objdump -d` | 守卫/常量/调用符合预期 |
| 页权限 | `vmmap`/`/proc/$PID/maps` | 无 RWX，常量池 NX |
| 缓存键 | 日志/单元测试 | 失效后不命中旧代码 |
| 负例 | CI 报告 | 读秘密/写外/孙进程均失败 |

这些证据要与发布版本绑定；缺一项就在报告里标 UNKNOWN。

**Q4** macOS 上 `RLIMIT_AS` 的有限值被拒绝，`ulimit -v` 也失败。一个多租户 runner 应该怎样补上内存限制？至少给出两种方案，并说明代价。

**Q5** seccomp 白名单允许 `openat`，禁止 `write`/`socket`/`execve`。这是否等于把文件访问限制在 `/work`？为什么？

**Q7** 一个 JIT 的代码缓存键包含字节码哈希与参数类型，但不包含 CPU 特性。把同一份缓存从支持 AVX-512 的机器复制到不支持 AVX-512 的机器，会发生什么？怎样在缓存层防住？

::: sol 答案
**A1** 换来了写入后直接执行的便利，省掉了权限切换；失去了「写不能变执行」的边界。只有在攻击者不能写代码页、不能控制跳转、且代码页内容完全由可信编译器生成时，风险才可控；一旦有任意写或跳转劫持，RWX 直接把数据变代码。W^X 的条件保证需要页不同时可写可执行，并且攻击者不能调用 `mprotect`。

**A2** 可能漏掉：目标 CPU 特性/ISA 扩展（同一字节码在支持/不支持 AVX 的机器上生成不同代码）、编译标志/优化级别、profile 版本、去优化计数、常量池布局/重定位模式。漏掉类型会导致把整数代码复用给浮点/对象；漏掉 CPU 特性会在不支持该指令的机器上崩溃；漏掉 profile 版本会复用基于过期假设的代码。

**A3** 可以。路径一：父进程把打开的 fd 通过 `pass_fds` 传进来，子进程直接 `read`；路径二：子进程用绝对路径/`..`/符号链接访问 `cwd` 外的文件（若 uid 权限允许）；路径三：环境虽空，但命令行参数/配置文件/继承的 socket 仍可能带秘密。`cwd`/`env`/rlimit 都不撤销这些能力。

**A4** 方案一：Linux 上用 cgroup v2 的 `memory.max`，按组记账，能跨进程；代价是需要 cgroup 权限/编排。方案二：把不可信代码放进轻量 VM/容器，由 hypervisor/运行时限制内存；代价是启动/运维成本。方案三：macOS 上用 App Sandbox/XPC 把内存密集操作放到受限服务，或接受「只能做 CPU/文件/fd 限制，内存靠监控+杀进程」，并在文档中写明。不能继续假装 `RLIMIT_AS` 生效。

**A5** 不等于。seccomp 只能看 syscall 号与标量参数，不能解引用 `openat` 的路径指针；只要 uid 权限允许，`openat` 仍能打开 `/work` 之外的路径。要限制路径，需要 landlock/mount namespace/chroot+uid 等另一层策略，seccomp 只负责缩小 syscall 面。

**A6** 边界只剩「引擎的线性内存/类型验证」和「宿主导入的实现」；模块可以通过 `path_open` 打开 preopen 目录内的文件，通过 `sock_connect` 外联。缩小能力：删掉不需要的导入，只保留 `fd_read`/`fd_write`；用 preopen 限定目录；对 `sock_connect` 做地址/端口白名单；在宿主侧记录/限流。

**A7** 缓存可能命中一段使用了 AVX-512 指令的代码，在不支持的 CPU 上触发 `SIGILL`（非法指令），或按 CPU 的特性位解释出不同语义。防住的办法：把目标 ISA/CPU 特性/运行时版本纳入键；缓存文件带头部元数据并在加载时校验；不跨机器共享未验证的代码缓存。
