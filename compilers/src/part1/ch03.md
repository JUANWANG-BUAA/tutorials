第 2 章结束时，你手里是一棵带 span 的 AST。节点 `Var("x")` 仍然只是一个字符串，`int x = true` 也只是三个 token 和一个初始化表达式。编译器还没有回答三个问题：这个 `x` 指哪个声明？这个表达式是什么类型？如果错了，错在源码的哪一段？

本章处理这三个问题。作用域决定名字在哪些位置可见，符号表把可见的名字映射到声明，类型检查给表达式一个类型并决定接受还是拒绝。三件事共享同一套基础设施：稳定的标识、精确的 span、可回滚的作用域状态。第 4 章会把这里得到的类型与绑定信息降成 TAC 和 SSA；第 5 章的数据流分析则默认名字已经解析完毕。

先看一个具体失败。一个 agent 为块语句写了 `enter_scope()` 和 `leave_scope()`，但在 `return` 分支提前返回，漏掉了 `leave_scope()`。块结束后，`print(y)` 仍然解析到块内已经销毁的 `y`，于是本该报“未声明”的程序被接受，后续代码生成访问了一个生命周期已经结束的槽位。这个案例在 3.8 展开，复现命令是：

```bash
cd compilers
python3 experiments/ch03/scope_lab.py
python3 experiments/ch03/scope_lab.py --leak-scope
```

正常模式跑五个用例，打印每次进入/离开作用域的栈深度、绑定编号和错误 span；`--leak-scope` 把 `leave()` 的弹栈去掉，复现“名字解析到已退出作用域”的现象。

## 3.1 类型系统的职责：静态/动态、可靠/完备 {#sec-compilers.1.3.1}

类型系统（type system）是一组可判定的规则，用来在程序运行前排除某一类错误。它不证明程序符合你的业务意图，也不证明程序会终止。它只回答：在这个语言的定义下，这个表达式能否得到一个类型，以及这个类型是否允许当前上下文要求的操作。

先固定记法。类型环境 $\Gamma$ 是从变量到类型的有限映射；判断 $\Gamma \vdash e : \tau$ 读作“在 $\Gamma$ 下，表达式 $e$ 具有类型 $\tau$”。一条规则通常写成前提在横线上、结论在横线下的形式。例如加法：

$$
\frac{\Gamma \vdash e_1 : \mathsf{int} \qquad \Gamma \vdash e_2 : \mathsf{int}}
     {\Gamma \vdash e_1 + e_2 : \mathsf{int}}
$$

这条规则只说明“两个 int 相加得到 int”。它不说明溢出时怎么办，也不说明两个操作数的求值顺序；那些属于语言的动态语义（dynamic semantics）和实现定义。把类型规则与运行时语义分开，是后面讨论可靠性的前提。

::: def 定义 3.1.1 · 类型系统与类型判断 {#def-compilers.1.3.1.1}
一个类型系统由三部分组成：类型集合 $T$、判断形式 $\Gamma \vdash e : \tau$、以及一组推导规则。程序通过规则得到类型，称为良类型（well-typed）；得不到类型则被拒绝。类型系统是**静态**的，指检查发生在执行之前，且只依赖程序的文本或编译期可得的信息；**动态**类型指值的类型标签随值一起在运行时流动，操作在运行时检查标签。
:::

“静态类型”不等于“强类型”。C 是静态类型，但允许大量隐式转换和指针强制转换；Python 是动态类型，却很少做隐式数值转换，`1 + "2"` 直接抛 `TypeError`。把这两个轴分开，才能解释为什么 TypeScript 能在编译期报错却仍在运行时出现类型问题。

| 语言 | 检查时机 | 类型强度 | 运行时是否保留类型 | 典型漏洞 |
|:--|:--|:--|:--|:--|
| C17 | 编译期 | 弱，允许隐式转换与指针转换 | 基本不保留 | 越界、悬垂指针、有符号溢出 |
| Rust 2021 | 编译期 | 强，安全子集禁止未检查转换 | 基本不保留，`dyn` 用 vtable | `unsafe` 块、逻辑错误、panic |
| Python 3.12 | 运行期 | 强，操作前检查标签 | 保留 | 属性拼写错误到运行时才暴露 |
| JavaScript | 运行期 | 弱，自动转字符串/数字 | 保留 | `"1" + 1` 得到 `"11"` |
| TypeScript | 编译期，擦除 | 中等，靠标注与结构类型 | 擦除后不保留 | `any`、断言、运行时的外部数据 |

表中的“强度”是工程用语，不是形式定义。形式定义要回到两条性质：可靠（soundness）与完备（completeness）。

::: def 定义 3.1.2 · 可靠与完备 {#def-compilers.1.3.1.2}
设 $P$ 是我们希望排除的运行时错误集合。类型系统对 $P$ 是**可靠**的，若所有良类型程序在运行中都不会触发 $P$；是**完备**的，若所有不会触发 $P$ 的程序都是良类型的。可靠性的典型形式是保持（preservation）与进展（progress）：良类型表达式求值一步后类型不变，且要么是值，要么还能继续求值。完备性要求检查器不误杀合法程序。
:::

可靠性是“没有假阴性”：类型检查通过，就不该出现这一类错误。完备性是“没有假阳性”：程序本身不会出这类错，就不该被拒绝。两者同时成立的类型系统，对图灵完备语言来说通常不存在；这不是实现不够努力，而是可判定性的边界。

::: thm 定理 3.1.1 · 可靠且完备的静态检查器不存在 {#thm-compilers.1.3.1.1}
对图灵完备的语言，若“程序对所有输入都不触发某类运行时错误”是一个非平凡的语义性质，则不存在只依赖程序文本、总能终止、且对该性质既可靠又完备的检查器。
:::

::: proof 证明思路
把停机问题归约到该性质。给定图灵机 $M$ 和输入 $w$，构造程序 $Q_{M,w}$：先模拟 $M(w)$，若模拟终止则触发目标错误，否则不触发。一个既可靠又完备的检查器若能判定 $Q_{M,w}$ 是否触发错误，就能判定 $M(w)$ 是否停机；而停机问题不可判定。因此这样的检查器不存在。这里的“非平凡”排除了“所有程序都触发”或“所有程序都不触发”这类常数性质。
:::

实际语言选择一条可判定的近似，因此必然在某一边让步。ML、Haskell、Rust 的安全子集选择可靠性：拒绝一些其实不会出错的程序（例如需要更复杂证明的索引边界）。C 的类型系统连内存安全都不保证，它把大量检查推给程序员和运行时；它的“可靠性”只覆盖很窄的语法层。TypeScript 选择实用性：结构化类型和 `any` 让大量 JavaScript 代码能渐进迁移，代价是可靠性有洞。

::: ex 例 3.1.1 · 类型检查通过但程序出错 {#ex-compilers.1.3.1.1}
下面这个 C 函数能通过 `cc -std=c17 -Wall -Wextra -Werror` 的类型检查，但调用时触发未定义行为：

```c
int divide(int a, int b) {
    return a / b;
}

int main(void) {
    return divide(1, 0);
}
```

类型规则只要求两个操作数是 `int`，不要求 $b \ne 0$。除零在 C17 中是未定义行为（undefined behavior，UB），不是“类型错误”。Rust 的 `i32 / 0` 同样通过类型检查，但会在运行时 panic；panic 是定义良好的终止，不是 UB。把“类型安全”当成“程序正确”，是本章最常见的误读。
:::

这张表把“保证”与“不保证”分开，读代码 review 时可以直接对照：

| 系统 | 它保证什么 | 它不保证什么 |
|:--|:--|:--|
| C17 类型检查 | 声明与使用在语法上匹配，隐式转换有定义 | 内存安全、算术安全、初始化 |
| Rust 安全子集 | 无数据竞争、无悬垂引用、无类型混淆 | 不 panic、不泄漏、不死锁、逻辑正确 |
| Python 运行时 | 每个操作的类型标签匹配 | 程序在到达该操作前不会因别处出错 |
| TypeScript 擦除后 | 编译期能发现的属性/参数错误 | 运行时外部数据、`any` 路径 |

::: intuition 类型是通行证，不是行为证明
把类型想成机场安检：它检查你带的物品类别是否允许登机，不检查你到达目的地后做什么。可靠=“允许登机的人不会带违禁品”；完备=“没带违禁品的人都能登机”。安检不可能既放过所有好人又拦住所有坏人，因为它只能看行李的外观。
:::

可靠性也有层次。Rust 说“安全代码不会悬垂”，这句话的条件是：`unsafe` 块内部的契约由程序员保证，外部 crate 的 `unsafe` 实现也遵守契约。Java 说“类型安全”，但要排除未检查转换（unchecked cast）、反射和原生代码。C 的类型系统甚至不把指针转换视为错误，所以它的“可靠”只到“表达式类别”这一层。

::: errata 三个常见混淆
1. **“静态类型 = 强类型”**：C 静态但弱；Python 动态但强。两个轴独立。
2. **“类型检查器通过 = 程序没有 UB”**：C 的除零、越界、有符号溢出都能通过类型检查。
3. **“动态类型 = 没有类型”**：运行时标签就是类型；只是检查推迟到操作发生。
:::

类型系统还决定编译器能做什么优化。若语言规定有符号加法溢出是 UB，优化器可以在 `x + 1 > x` 上假设不溢出并把它折成真；若规定二进制补码回绕（wrap），这个变换就不成立。第 9 章会展开 UB 与可观察行为；这里只需记住：类型规则、转换规则和 UB 规则共同定义了优化器可以依赖的契约。

::: note 渐进类型与擦除
TypeScript、Python 的 `typing`、Sorbet 都属于渐进类型（gradual typing）：一部分代码有静态标注，一部分没有，边界处插入运行时检查或直接放弃检查。TypeScript 的选择是**擦除**（erasure）：类型标注不进入 JavaScript 输出，因此运行时无法验证外部 JSON 的形状。Java 的泛型也擦除，但会在需要处插入转换并在失败时抛 `ClassCastException`。擦除让实现简单、二进制兼容，却把一部分可靠性推回给程序员。
:::

到此为止，类型系统的“职责”可以压缩成一句话：用可判定的规则，把某一类运行时错误变成编译期错误，并明确哪些错误不在保证范围内。下一节先把名字解析做对；没有正确的绑定，类型规则连“这个 `x` 是哪个 `x`”都说不清。



### 3.1.1 类型信息在流水线中的位置

类型检查器的输出不应该只是“通过/拒绝”两个布尔值。后续的 IR 生成需要知道每个表达式的宽度、是否有符号、聚合布局、调用约定；诊断需要知道每个节点的类型和绑定；增量编译需要把类型结果缓存成可比较的值。常见做法是给每个表达式分配稳定的 ExprId，再用一张旁表（side table）记录 ExprId 到类型的映射，而不是在每个 AST 节点上挂一个可变的 type 字段。

旁表的好处是可共享、可缓存、可并行：两个查询可以同时读同一份类型表；增量重算只替换受影响的条目；调试时可以打印“表达式 → 类型”的完整映射。坏处是查询时要多一次间接寻址，且必须保证 ExprId 在重解析后稳定。若 AST 节点会被重新创建，ExprId 必须由语法位置或稳定哈希生成，不能简单用内存地址。

| 阶段 | 输入 | 输出 | 类型信息的作用 |
|:--|:--|:--|:--|
| 名称解析 | AST、导入表 | 每个 use 的 BindingId | 区分同名遮蔽，确定声明 |
| 类型检查 | 带 BindingId 的 AST、类型环境 | ExprId → Type、BindingId → Type | 接受/拒绝，插入隐式转换 |
| 降级到 IR | 带类型的 AST | TAC/CFG | 选择指令宽度、符号扩展、内存布局 |
| 优化 | SSA/数据流事实 | 等价 IR | 依赖无 UB、无别名等类型契约 |
| 代码生成 | 目标相关 IR | 机器码/汇编 | 寄存器宽度、调用约定、聚合传递 |

一张带类型标注的树可以长这样（<code>text</code> 仅表示结构，不是某个编译器的真实 dump）：

```text
Add :: int
├── Var x :: int          binding #1, decl @1:5
└── Mul :: int
    ├── Int 2 :: int
    └── Var y :: int      binding #2, decl @1:9
```

读法：根节点的类型由子节点规则推出；每个 <code>Var</code> 都带 BindingId 和声明位置，否则后续无法区分“同名但不同绑定”。如果这里只存名字字符串，第 4 章生成 IR 时又要重新解析一次，且可能得到不同结果。

类型信息也不是越多越好。把完整类型、约束、trait 候选、借用区域全部塞进每个 AST 节点，会让内存和缓存膨胀；常见做法是分层：AST 只存语法和 BindingId，类型检查结果放旁表，约束求解的中间状态在检查结束后丢弃，只保留最终类型和必要的 obligation 结果。Rust 的 THIR、clang 的 <code>QualType</code> 都是这种“按需保留”的工程折中。

还有一个顺序问题：名称解析必须在类型检查之前完成，但某些语言的类型检查会影响名字解析（例如 C++ 的模板依赖名、Rust 的方法解析需要 trait 信息）。这类语言通常分成多轮：先解析非依赖名，实例化时再解析依赖名；或者把名字解析和类型检查交织在一个固定点迭代里。无论哪种，BindingId 的稳定性都是前提，否则缓存会错位。

## 3.2 作用域、绑定、遮蔽与名称解析 {#sec-compilers.1.3.2}

源码里的标识符有两次生命：声明处（binding occurrence）和每个使用处（use occurrence）。名称解析（name resolution）的任务，是把每个使用处关联到唯一的声明，或者报告“找不到/有歧义”。作用域（scope）是这个关联有效的文本区域；遮蔽（shadowing）是内层声明覆盖外层同名声明。

先看一个最小的 C 程序：

```c
#include <stdio.h>

int main(void) {
    int x = 1;
    {
        int x = 2;
        printf("%d\n", x);
    }
    printf("%d\n", x);
    return 0;
}
```

输出是 `2` 和 `1`。两个 `x` 是两个不同的对象，编译器必须给它们不同的标识；如果符号表把名字当键、把类型当值，后一个 `int x = 2` 会覆盖前一个，块结束后再查 `x` 就只剩内层声明。正确做法是每个声明分配一个 BindingId，作用域栈保存“名字到 BindingId”的映射；离开块时弹出这一层，外层的映射自然恢复。

::: def 定义 3.2.1 · 绑定、作用域与可见性 {#def-compilers.1.3.2.1}
**绑定**把名字与一个声明实体（变量、函数、类型、模块）关联。**作用域**是绑定可见的文本区域。**遮蔽**是内层作用域中的同名绑定使外层绑定在该区域内不可见。名称解析从使用点所在的最内层作用域开始，逐层向外查找，取第一个匹配的绑定；若到最外层仍没有，则报未声明。
:::

词法作用域（lexical scope）按程序的文本嵌套决定可见性；动态作用域（dynamic scope）按调用链决定可见性。现代主流语言几乎都用词法作用域，因为它在编译期就能解析，且不依赖调用顺序。动态作用域仍出现在少数地方：Bash 的 `local` 变量是动态作用域，早期 Lisp 的 `special` 变量也是。读旧代码时看到“同名变量被调用者影响”，先确认语言是不是动态作用域。

作用域的起点由语言的声明点（point of declaration）规则精确给出。C17 6.2.1p7 规定，标识符的作用域从声明符完成之后开始。因此下面这个片段（只展示声明点，不单独编译）：

```text
int x = 1;
{
    int x = x;   /* 右边的 x 已经是新声明的 x，不是外层的 1 */
}
```

C 里右边读到的是未初始化的自动变量，行为未定义；这不是“初始化器先看外层”的语法糖。Rust 的规则相反：`let x = x + 1;` 中右边的 `x` 仍是旧绑定，新绑定在整条 `let` 语句之后才生效。C++ 的声明点也在声明符之后、初始化器之前，所以 `int x = x;` 引用自身。三种语言看起来相似，语义却不同；实现类型检查器时必须按各自标准的声明点写，而不能凭“初始化器应该看外层”的直觉。

遮蔽与重复声明是两件事。C 允许内层块重新声明同名变量（遮蔽），但同一作用域重复声明是错误；C++ 在类成员、命名空间和重载场景下有更复杂的规则；Rust 允许同一作用域用 `let` 重复绑定，每次产生新绑定，类型也可以改变：

```rust
fn main() {
    let x = 1;        // x: i32
    let x = "two";    // 新绑定，x: &str；旧的 x 被遮蔽
}
```

Rust 的第二次 `let` 不是赋值，而是新声明；旧绑定仍然存在，只是名字不可达。编译器可以在旧绑定不再被使用时提前结束它的生命周期（drop），但名字解析必须保留“两个不同 BindingId”的事实。把 `let` 当成赋值，会在借用检查、drop 顺序和调试信息上同时出错。

名称解析的朴素实现是沿着环境链查找：

```python
def resolve(env, name):
    scope = env
    while scope is not None:
        if name in scope.bindings:
            return scope.bindings[name]
        scope = scope.parent
    return None
```

这段代码只说明查找方向。真实实现还要处理：声明是否已经生效（顺序敏感的语言）、是否允许前向引用（函数、类型、模块）、是否有多个同名候选（重载、trait 方法、`use` 导入冲突）、以及当前点是否在某个声明的初始化器内部。C 的函数可以在声明前调用（有隐式声明或头文件），局部变量不行；Rust 的项（item）顺序无关，局部 `let` 顺序有关；Python 的局部变量在函数编译期就确定，赋值前使用会得到 `UnboundLocalError`。

下面这张表把常见语言的作用域规则压缩成实现要点：

| 语言 | 块作用域 | 同作用域重声明 | 声明点/前向引用 | 特别之处 |
|:--|:--|:--|:--|:--|
| C17 | 有 | 错误（同作用域） | 声明符之后；函数可前向 | 文件作用域与链接 |
| C++20 | 有 | 多数情况错误，可重载函数 | 声明符之后 | 命名空间、类成员、ADL |
| Rust 2021 | 有 | 允许 `let` 遮蔽 | `let` 语句之后；项顺序无关 | 模式绑定、生命周期 |
| Python 3.12 | 函数/类/模块 | 允许赋值覆盖 | 函数内任意赋值使名字成为局部 | `global`/`nonlocal` |
| JavaScript | `let`/`const` 块级 | 同一块内错误 | `let` 有暂时性死区 | `var` 函数级提升 |

“声明点”还会影响错误信息。考虑 `int x = x;`：如果编译器先在外层作用域查 `x`，它会把初始化器绑到外层变量，程序可能“看起来能跑”；如果按 C 标准先让新声明生效，它应该报告“使用了未初始化的变量”或直接生成读取未初始化槽位的代码。两种实现都能通过语法分析，差别只在名称解析的时机。

::: ex 例 3.2.1 · 走一遍作用域栈 {#ex-compilers.1.3.2.1}
对下面的程序，作用域栈在每一行的状态如下。`#1`、`#2` 是 BindingId，不是源码里的名字。

```text
1  int x = 1;          stack: [program: x -> #1]
2  {
3      int x = 2;      stack: [program: x -> #1, block: x -> #2]
4      print(x);       resolve x -> #2
5  }
6  print(x);           resolve x -> #1
```

第 4 行的 `x` 与第 6 行的 `x` 文本相同，绑定不同。类型检查器在第 4 行用 `#2` 的类型，在第 6 行用 `#1` 的类型；如果两个声明的类型不同（例如外层 `int`、内层 `bool`），同一个表达式在块内外的合法性可能相反。
:::

把 AST 遍历与作用域栈画在同一根时间轴上，可以看到“进入/离开”必须成对：

<pre class="layout">
源码事件          作用域栈（栈顶在右）                 解析结果
program start     [program]                             -
int x = 1         [program: x#1]                        declare #1
{                 [program: x#1] [block]                enter
  int x = 2       [program: x#1] [block: x#2]           declare #2
  print(x)        [program: x#1] [block: x#2]           x -&gt; #2
}                 [program: x#1]                         leave，弹出 #2
print(x)          [program: x#1]                        x -&gt; #1
program end       []                                    leave
</pre>

读图：栈的深度只在中括号数量变化时改变；每次 `leave` 必须弹出与最近一次 `enter` 对应的那一层。图中第 5 行之后 `#2` 已不在栈上，所以第 6 行不可能解析到它。任何“块退出后仍能看见块内名字”的实现，都是在某条路径上漏掉了这次弹出。

名称解析还要区分“找到名字”和“选对实体”。C++ 的 `f(1)` 先做名字查找，得到一个重载集合，再做重载决议；Rust 的 `x.foo()` 先找方法候选，再按接收者类型、自动解引用和 trait 约束筛选；Java 的 `import` 冲突可能在名字查找阶段就报错。这些都属于“解析出候选集合”，不是简单的 `dict[name]`。第 3.4 节会把重载与约束放在类型检查里讲；这里只需要记住：名称解析的输出可以是一个集合，而不是单个 BindingId。

::: errata 作用域不等于生命周期
“变量离开作用域”与“对象被销毁”经常同时发生，但不是同一件事。Rust 的 `let x = ...;` 被遮蔽后，旧绑定仍在栈帧里，直到其作用域结束才 drop；C 的 `static` 局部变量在离开块后仍存活；C++ 的临时对象生命周期由完整表达式决定。符号表只负责名字可见性，销毁/回收由另一套规则（drop、析构、GC）负责。把两者混在一起，会在实现 drop 或调试信息时把“名字不可见”误当成“存储已释放”。
:::

::: note 动态作用域的一个真实例子
Bash 函数里的 `local x` 是动态作用域：被调用函数看到的 `x` 取决于调用链，而不是定义位置。这解释了为什么在 shell 函数里给变量加 `local` 能避免污染调用者。写编译器时如果实现的是 shell 或某些 DSL，别默认套用词法作用域。
:::

名称解析的错误也分层次。未声明（undeclared）是找不到任何绑定；歧义（ambiguous）是找到多个同等优先的绑定；不可见（inaccessible）是找到了但当前上下文无权访问（private、模块边界）；未初始化是找到了绑定但数据流上还没有值。四类错误需要不同的诊断和修复建议。把“未初始化”报成“未声明”，会让用户去检查拼写，浪费一次编译。

下一节把这些规则落到数据结构上：栈式符号表、持久 map、以及“名字 + 位置”的哈希/区间方案。结构选错，正确性 bug 会以“块退出后还能看见名字”的形式出现；结构选对，3.8 的漏弹栈问题在类型上就很难发生。

## 3.3 符号表：栈式、持久 map 与哈希 {#sec-compilers.1.3.3}

名称解析需要一张“名字 → 声明”的表，但表不能只有一层。进入块要新增一层，离开块要恢复上一层；同一个名字在不同层可以指向不同声明；错误信息还要能找回声明的位置。把这三件事都塞进一个全局 `dict`，就会出现 3.8 的泄漏；把作用域实现成不可变结构，则从类型上消除“忘记弹出”的可能。

先固定接口。符号表至少提供四个操作：`enter(span)` 开一个新作用域，`leave()` 关闭当前作用域，`declare(name, type, span)` 在当前作用域新增绑定，`resolve(name, span)` 从内向外查找。再加两个查询：`lookup_at(name, position)` 给 IDE 和增量分析用，`snapshot()` 给调试和测试用。接口里返回的是 BindingId，不是指向栈帧的裸指针；BindingId 在编译单元内稳定，绑定被销毁后仍然可以用于诊断，但不再可解析。

::: def 定义 3.3.1 · 符号表接口 {#def-compilers.1.3.3.1}
符号表是部分函数 $\mathrm{Lookup} : \mathrm{Name} \times \mathrm{Position} \rightharpoonup \mathrm{BindingId}$，满足：若位置 $p$ 处名字 $x$ 可见，则 $\mathrm{Lookup}(x,p)$ 返回在 $p$ 之前最近进入且尚未离开的作用域中声明的 $x$；若不存在，则未定义。符号表还必须支持按作用域批量插入和回滚，且回滚后所有被该作用域声明的名字不再可见。
:::

### 栈式符号表

最直接的实现是“作用域栈 + 每层一个哈希表”：

```python
class SymbolTable:
    def __init__(self):
        self.scopes = [{}]
        self.bindings = []

    def enter(self):
        self.scopes.append({})

    def leave(self):
        self.scopes.pop()

    def declare(self, name, typ, span):
        if name in self.scopes[-1]:
            raise Duplicate(name)
        bid = len(self.bindings)
        self.bindings.append(Binding(bid, name, typ, span))
        self.scopes[-1][name] = bid
        return bid

    def resolve(self, name):
        for scope in reversed(self.scopes):
            if name in scope:
                return scope[name]
        return None
```

查找代价是 $O(d)$ 次哈希查找，$d$ 是当前作用域深度；插入是均摊 $O(1)$。对普通源文件，$d$ 通常小于 20，这个代价可以接受。真正的问题不在复杂度，而在**回滚的完备性**：`leave()` 必须在所有退出路径上执行，包括 `return`、`break`、`continue`、异常和错误恢复。只要有一条路径跳过它，后面所有名字都会多看见一层。

提高鲁棒性的办法有三种。第一，把 `enter/leave` 包进 RAII、`defer` 或 Python 的 `with`，让作用域对象的析构负责弹出；第二，不在遍历中维护可变栈，而是把环境作为参数传下去，进入块时构造子环境，离开时直接丢弃；第三，在每次语句/表达式检查后断言“栈深度等于 AST 预期的深度”，把静默错误变成测试失败。三种可以叠加，成本很低。

### 持久 map

持久 map（persistent map）把“当前环境”表示成不可变值。`enter` 不修改旧环境，而是返回一个带父指针的新环境；`leave` 就是丢弃新环境、继续用旧的。绑定插入返回新 map，旧 map 仍然可用。这样不存在“忘记弹出”的路径：离开作用域只是不再传递新环境，旧环境天然没有被污染。

用父指针链实现时，查找仍是 $O(d)$；用持久平衡树或 HAMT（hash array mapped trie）实现时，插入和查找是 $O(\log n)$，且新旧版本共享大部分节点。每次插入只复制一条路径，内存是 $O(\log n)$ 个节点，而不是整表复制。对增量编译和并行分析，这个性质很重要：旧版本的符号表可以安全地留给另一个线程或另一个查询使用。

```text
持久 map 的一次插入（结构共享）：

        version 0                 version 1
        +-------+                 +-------+
        | root  |                 | root' |
        +---+---+                 +---+---+
            |                         |
        +---+---+                 +---+---+
        |  ...  |                 |  ...  |   <-- 未修改的子树被共享
        +-------+                 +---+---+
                                      |
                                  +---+---+
                                  | x:#7  |   <-- 只复制路径上的节点
                                  +-------+
```

读图：版本 1 只新建根到 `x` 的路径，其他节点与版本 0 共享。丢弃版本 1 不会影响版本 0，因此“回滚”是 $O(1)$ 的指针切换。代价是每次插入分配 $O(\log n)$ 个节点，且哈希/比较的常数比可变哈希表大。

### 哈希与“名字 + 位置”方案

第三类实现不给每个作用域建表，而是维护一张全局哈希表：名字 → 声明列表，列表按源码位置排序；解析时对列表二分，找位置之前最近、且作用域包含该位置的声明。Clang 的 `DeclContext` 查找、部分 IDE 的索引都接近这个思路。它适合“给定文件偏移，查可见声明”的查询，也适合把符号表序列化到索引文件。

| 结构 | enter/leave | declare | resolve | 快照/回滚 | 适合场景 |
|:--|:--|:--|:--|:--|:--|
| 作用域栈 + 哈希 | $O(1)$ / $O(1)$ | 均摊 $O(1)$ | $O(d)$ | 需显式回滚 | 单遍编译器、教学实现 |
| 持久 map（父指针） | $O(1)$ / $O(1)$ | $O(1)$ | $O(d)$ | 天然，$O(1)$ | 递归下降、增量查询 |
| 持久 HAMT/平衡树 | $O(1)$ 生成新根 | $O(\log n)$ | $O(\log n)$ | 天然，结构共享 | 并行前端、IDE |
| 全局哈希 + 位置区间 | 无栈 | $O(1)$ 追加 | $O(\log k)$ | 按版本重建 | 索引、跨文件查找 |

哈希表本身还有两个工程细节。其一是名字驻留（string interning）：源码里成千上万个 `x` 只保留一份字节串，哈希表存 `Symbol(u32)`，比较整数而不是字符串。其二是确定性：如果诊断或代码生成依赖哈希表的遍历顺序，同一份源码在不同进程可能产生不同输出，破坏可复现构建（第 1 章）。需要遍历时按源码位置或 SymbolId 排序，不要依赖 `dict` 的插入顺序。

::: ex 例 3.3.1 · 绑定编号与死绑定 {#ex-compilers.1.3.3.1}
`scope_lab.py` 的嵌套遮蔽用例输出：

```text
[snap] after decl x @1:5 depth=1 scope#1(x:#1:int@1:5)
[snap] after decl x @3:8 depth=2 scope#1(x:#1:int@1:5) | scope#2(x:#2:bool@3:8)
[snap] after block @2:1 depth=1 scope#1(x:#1:int@1:5)
trace:
  declare #1 x:int @1:5
  declare #2 x:bool @3:8
  resolve x -> #2 (bool) @4:9
  leave block @2:1 depth=1
  resolve x -> #1 (int) @6:7
```

快照里 `#1` 和 `#2` 同时存在，离开块后只剩 `#1`。绑定表在最后把两个绑定都标成 `alive=no`（程序结束），但它们的 `decl_span` 仍然可用于诊断。注意“离开作用域”只改变可见性，不删除 BindingId；这正是增量分析和错误恢复需要的稳定性。
:::

::: method 选择符号表结构的顺序
1. 先问是否需要增量/并行：需要，优先持久 map 或带版本号的索引；不需要，栈式哈希足够。
2. 再问回滚是否可能被异常/提前返回打断：会，使用 RAII/上下文管理器，或改成参数传递的持久环境。
3. 最后问诊断是否需要“在某个位置查可见名字”：需要，保留作用域区间或位置索引，别只留一个可变栈。
:::

符号表的生命周期还要和 AST 的所有权对齐。常见做法是 AST 节点由 arena 分配，绑定记录也放在 arena 或单独数组中，节点只存 `BindingId`。不要存 `Binding*`：arena 扩容、增量重解析或跨模块合并都可能让指针失效。BindingId 是整数，复制、比较、序列化都稳定；需要取声明信息时再通过表查回。

::: note 哈希冲突不是正确性问题，确定性才是
哈希冲突由哈希函数和相等比较处理，不影响语义正确性；但哈希遍历顺序会影响诊断顺序、寄存器分配和调试信息。若构建要求可复现，所有“遍历符号表”的地方都要有稳定排序，或者使用有序 map。另一点：不要用指针地址做哈希，地址每次运行都可能不同。
:::

## 3.4 类型检查：判断、推导与合一的边界 {#sec-compilers.1.3.4}

有了绑定，类型检查就可以给每个表达式算类型。最直接的方式是自底向上：变量查符号表，字面量有固定类型，二元运算要求操作数满足规则，`if` 要求条件为 bool、两个分支类型一致。这种方式叫合成（synthesis）：从子表达式得到类型，向上组合。

但有些表达式无法只靠子节点决定类型。`[]` 是空数组，元素类型未知；`None` 在 Python 里可以是任意可选类型；Rust 的 `let v = Vec::new();` 需要从后续使用反推 `Vec<T>` 的 `T`。这时需要检查（checking）：已知期望类型，向下传播。双向类型检查（bidirectional type checking）把两种方向分开：`synth(e)` 返回类型，`check(e, expected)` 验证并传播期望。

::: def 定义 3.4.1 · 合成与检查 {#def-compilers.1.3.4.1}
**合成**判断 $\Gamma \vdash e \Rightarrow \tau$：由表达式自身得到类型 $\tau$。**检查**判断 $\Gamma \vdash e \Leftarrow \tau$：在期望类型 $\tau$ 下验证 $e$。典型的切换点是 `let x = e`：若没有标注，对 $e$ 合成；若有标注，对 $e$ 检查。函数调用、数组字面量、`return` 都常需要期望类型向下传播。
:::

以简单表达式语言为例，规则可以写成：

```text
Γ(x) = τ
-------------  (Var)
Γ ⊢ x ⇒ τ

Γ ⊢ e1 ⇐ int    Γ ⊢ e2 ⇐ int
----------------------------  (Add)
Γ ⊢ e1 + e2 ⇒ int

Γ ⊢ c ⇐ bool    Γ ⊢ e1 ⇐ τ    Γ ⊢ e2 ⇐ τ
------------------------------------------  (If)
Γ ⊢ if c then e1 else e2 ⇒ τ

Γ ⊢ e ⇒ τ1    Γ, x:τ1 ⊢ body ⇐ τ2
----------------------------------  (Let)
Γ ⊢ let x = e in body ⇒ τ2
```

这些规则假设类型完全已知。遇到未知类型，就引入类型变量（type variable）和约束（constraint）。例如 `fn id(x) { x }` 给参数一个变量 $\alpha$，返回类型也是 $\alpha$；调用 `id(1)` 产生约束 $\alpha = \mathsf{int}$，把 $\alpha$ 解成 int。解约束的过程就是合一（unification）。

合一的核心是替换：维护一个从类型变量到类型的映射，遇到两个类型变量就合并，遇到两个构造器（例如 `List`、`Pair`）就递归合一参数，遇到不同构造器就报错。必须做出现检查（occurs check）：若把 $\alpha$ 解成包含 $\alpha$ 的类型（例如 $\alpha = \alpha \to \mathsf{int}$），就会得到无限类型，必须拒绝。

```python
def unify(a, b, subst):
    a = prune(a, subst)
    b = prune(b, subst)
    if a == b:
        return
    if is_var(a):
        if occurs(a, b):
            raise Type_error("infinite type")
        subst[a] = b
        return
    if is_var(b):
        if occurs(b, a):
            raise Type_error("infinite type")
        subst[b] = a
        return
    if a.tag != b.tag or len(a.args) != len(b.args):
        raise Type_error(f"cannot unify {a} with {b}")
    for x, y in zip(a.args, b.args):
        unify(x, y, subst)
```

这段伪代码只处理一阶、无子类型的类型。真实语言会在此之上加三样东西：子类型约束（$\tau_1 \le \tau_2$）、重载/多态约束（从候选集合中选一个）、以及带前提的约束（Rust 的 trait obligation、Haskell 的类型类）。它们不再是单纯合一，而是约束求解（constraint solving）。

| 策略 | 代表语言 | 主要判断 | 边界 |
|:--|:--|:--|:--|
| 纯合成 + 显式标注 | C17 | 声明给出类型，表达式向上合成 | 无局部推导，隐式转换多 |
| 双向检查 | Rust、TypeScript、Scala 3 | synth/check 交替，期望类型向下 | 需要设计切换点，否则错误信息差 |
| Hindley–Milner 合一 | OCaml、Haskell（无扩展） | 生成等式约束，合一求最一般类型 | 子类型、高阶多态会破坏 |
| 约束/逻辑式 | Rust trait solver、Swift | 生成谓词，按规则求解 | 可能歧义、循环、编译时间 |
| 流敏感检查 | TypeScript（部分）、Python 类型检查器 | 结合控制流收窄类型 | 别名与副作用会让收窄失效 |

Hindley–Milner 的可贵之处是“最一般类型”（principal type）：若程序有类型，算法总能找到最一般的那一个，且不需要标注（除了一些多态递归场景）。代价是它依赖一阶合一，遇到子类型、重载或高阶多态就不够用。Rust 的泛型 + trait 约束、C++ 的重载 + 模板、TypeScript 的结构子类型，都在不同位置离开了纯 HM。

::: thm 定理 3.4.1 · HM 推导的边界 {#thm-compilers.1.3.4.1}
在无子类型、无重载、无高阶多态、且允许 let 泛化的核心语言上，Hindley–Milner 算法 W 能判定类型并给出最一般类型；算法终止。若加入任意高阶多态或任意子类型约束，类型判定可能不可判定，或者需要显式标注/受限的形式。
:::

::: proof 证明思路
算法 W 对表达式结构递归，每个 `let` 处对类型变量做泛化，其余约束用合一求解。合一在带出现检查时终止，因为每次替换都减少未绑定变量的“深度”；最一般类型的存在性来自合一的最一般解性质。加入高阶多态后，类型量词可以出现在任意位置，判定问题可编码二阶 unification；加入任意子类型约束后，约束系统可以表达交/并和递归约束，判定性依赖具体限制。
:::

C++ 是另一个极端：名字查找得到重载集合，重载决议按参数类型排序候选，模板参数推导再产生一组候选，SFINAE（substitution failure is not an error）把替换失败变成“候选不可用”。这套机制在编译器内部是约束求解，但表面语法把它藏在了函数调用里。Rust 的 trait 求解类似：每个泛型调用生成 `T: Trait` 的义务，编译器用 impl 和 where 子句证明它；找不到唯一 impl 或出现重叠 impl，就报错。两者都不是“简单查表”。

::: ex 例 3.4.1 · 从约束到替换 {#ex-compilers.1.3.4.1}
考虑：

```text
fn id(x) { x }
let a = id(1);
let b = id(true);
```

第一次调用生成 $\alpha = \mathsf{int}$，第二次生成 $\alpha = \mathsf{bool}$。若 `id` 是单态的，两次约束冲突；若允许 let 泛化，每次调用把 `id` 的 $\alpha$ 实例化成新的变量，两个约束分别求解，程序通过。这个例子说明“多态”不是语法装饰，而是约束生成时是否复制类型变量。Rust 的泛型函数在定义处检查一次、在调用处实例化；C++ 的模板在调用处才完整检查，因此错误可能延迟到实例化点。
:::

类型检查还要决定“错误之后怎么办”。如果 `x` 未声明，给 `x` 一个错误类型（error type）并继续，可以避免每个使用 `x` 的位置都报一次；但错误类型会污染后续推导，必须保证它不与正常类型产生假错误。常见做法是让错误类型与任何类型合一（类似动态类型），但在最终诊断里标记“由前面的错误引起”。Rust 的 `{integer}` 和 `{float}` 是另一种占位类型：字面量先得到推断变量，最后按默认规则落成 `i32`/`f64`；若同一变量同时被推成 int 和 float，才报错。

::: errata 类型推导的三个误区
1. **“有类型推导就不需要标注”**：多态递归、重载、高阶函数常需要标注；Rust 的函数签名必须写参数和返回类型。
2. **“合一能处理子类型”**：合一要求相等，子类型要求偏序；把结构子类型硬塞进合一，会把 `Dog <: Animal` 和 `Cat <: Animal` 错解成 `Dog = Cat`。
3. **“推导失败 = 程序错误”**：可能只是信息不足；错误信息应报告“无法推断”并给出标注建议，而不是断言类型矛盾。
:::

::: note 类型检查与借用检查是两层
Rust 的借用检查（borrow checking）不是类型检查，但它消费类型检查的产物：每个引用的生命周期、每个所有者的移动路径。可以把借用检查看成在 MIR 上求解一组“引用不得悬垂、可变借用不得重叠”的约束。它和第 3.5 节的泛型实例化共享“约束求解”的工程结构，但语义层不同；第 9 章会从 UB 角度再回到借用与别名。
:::

最后给出一个判断实现是否“讲得通”的检查：随便挑一个含内层块和同名变量的程序，手工写出每个使用点的 BindingId 和类型；再让编译器输出它的符号表/类型（或用一个最小解释器验证），两者应一致。若编译器把块外的名字解析到块内，或者把 `int` 和 `bool` 的遮蔽关系弄反，先查作用域栈的弹出，再查声明点和名字驻留；不要先怀疑类型规则。



### 3.4.1 重载决议与 trait 求解的工程差异

C++ 的重载决议是“先收集候选，再筛可行性，再排序”。候选来自名字查找（成员、自由函数、ADL）；可行性看参数个数、默认参数、模板推导、访问权限；排序看转换序列的等级（精确匹配、提升、标准转换、用户定义转换、省略号）。如果两个候选无法比较出更优，报歧义。编译器实现这套规则时，通常把每个候选的转换序列算成一个代价元组，再按字典序比较；模板偏序是另一层规则，不能和普通重载混在一起。

Rust 的 trait 求解更像逻辑程序设计。每个泛型调用生成 obligation，例如 <code>T: Clone</code>；求解器在 impl 表、where 子句、内置 impl 中找匹配，可能产生嵌套 obligation（impl 的 where 子句）。找不到唯一解、或多个 impl 重叠、或递归深度超限，都会报错。它没有 C++ 那种“转换序列排序”，但有“候选唯一性”和“递归终止”的工程约束。

| 维度 | C++ 重载 | Rust trait |
|:--|:--|:--|
| 候选来源 | 名字查找 + ADL | impl 表 + where 子句 |
| 可行性 | 参数个数/类型/模板推导/SFINAE | obligation 是否能被证明 |
| 选择 | 转换序列排序，可能歧义 | 唯一 impl；重叠/歧义报错 |
| 错误时机 | 调用点/实例化点 | 定义点/调用点/单态化前 |
| 工程风险 | 候选爆炸、错误信息长 | 递归求解、coherence |

两者都给编译器带来“候选集合”这一层，而不是简单的 <code>dict[name]</code>。第 3.2 节说名称解析可以返回集合，这里就是它的下游：类型检查必须把集合收缩成一个实体，或者报告无法选择。

## 3.5 泛型与实例化：Rust/C++ 对照（不重讲语法） {#sec-compilers.1.3.5}

泛型（generics）让一段代码对多种类型复用。编译器面前有两条根本不同的路：在编译期为每个具体类型生成一份代码，叫单态化（monomorphization）；或者只生成一份代码，把类型信息擦除或在运行时通过字典/vtable 查表。前者把类型当编译期参数，后者把类型当运行时数据。两条路对符号表、链接、代码体积和错误诊断的影响完全不同。

::: def 定义 3.5.1 · 单态化 {#def-compilers.1.3.5.1}
给定泛型定义 f(x: T) 和一组具体类型 T1, ..., Tn，单态化为每个 Ti 生成一个独立函数，把定义中的 T 替换成 Ti，再分别做类型检查后的优化与代码生成。生成的实例是普通函数，调用点直接调用对应实例；类型参数在运行时不再存在。
:::

Rust 的流程大致是：泛型函数在定义处做一次类型检查，trait 约束（bound）被记录成义务；调用点产生具体的实例化请求；代码生成阶段为每个实际用到的类型组合复制一份 MIR/LLVM IR，做单态化后再优化。`dyn Trait` 是另一条路：对象包含数据指针和 vtable 指针，调用通过 vtable 间接跳转，不复制函数体。`impl Trait` 在返回位置是不透明类型，仍然静态分派；在参数位置是匿名泛型。

C++ 的模板在名字查找和实例化上更晚：模板定义先做第一阶段查找（非依赖名），实例化时再做依赖名查找；模板参数推导、重载决议和 SFINAE 共同决定候选。每个翻译单元可以独立实例化同一组模板，链接器用弱符号/COMDAT 合并重复实例；这带来 ODR（One Definition Rule）问题，也带来“同一个模板在多个 .o 里各生成一份”的代码膨胀。显式实例化（`extern template`）可以把生成集中到一个翻译单元。

先看 Rust 的真实证据。下面的程序对 `i32` 和 `f64` 各调用一次 `twice`，用 `--emit=llvm-ir` 看代码生成结果：

```bash
cat > /tmp/mono.rs <<'EOF'
#[inline(never)]
fn twice<T: Copy + std::ops::Add<Output = T>>(x: T) -> T { x + x }
fn main() {
    let a = twice(3i32);
    let b = twice(2.5f64);
    println!("{a} {b}");
}
EOF
rustc -C opt-level=0 --emit=llvm-ir /tmp/mono.rs -o /tmp/mono.ll
grep -n 'define.*twice' /tmp/mono.ll
```

在 rustc 1.99.0（aarch64-apple-darwin）上，输出包含两行（符号后缀含 crate hash，换路径会变）：

```text
16:define internal double @_RINvCskymt3iPv87r_4mono5twicedEB2_(double %x) unnamed_addr #0 !guid !9 {
25:define internal i32 @_RINvCskymt3iPv87r_4mono5twicelEB2_(i32 %x) unnamed_addr #0 !guid !10 {
```

读法：同一个源码函数 `twice` 变成了两个 LLVM 函数，参数类型分别是 `double` 和 `i32`。注释行还会写出 `; mono::twice::<f64>` 与 `; mono::twice::<i32>`，直接标明实例化参数。这里没有运行时类型参数，也没有 vtable；调用点直接调用对应符号。

C++ 的符号证据更直接。用 `clang++ -std=c++17 -O0 -c` 编译两个实例，再用 `nm` 看符号：

```bash
cat > /tmp/twice.cpp <<'EOF'
template <typename T> T twice(T x) { return x + x; }
int f(int x) { return twice(x); }
double g(double x) { return twice(x); }
EOF
clang++ -std=c++17 -O0 -c /tmp/twice.cpp -o /tmp/twice.o
nm -nm /tmp/twice.o | grep twice
```

本机 clang 22.1.8 的输出：

```text
0000000000000024 (__TEXT,__text) weak external __Z5twiceIiET_S0_
0000000000000064 (__TEXT,__text) weak external __Z5twiceIdET_S0_
```

两个符号分别是 `twice<int>` 和 `twice<double>`，并且是 weak external：不同翻译单元都实例化时，链接器保留一份。Rust 默认不把泛型实例暴露成 weak 符号；它在 crate 内生成，跨 crate 时通过 rlib/元数据按需实例化，具体策略随编译器和链接方式变化。

| 维度 | Rust 单态化 | C++ 模板实例化 | Java 泛型擦除 |
|:--|:--|:--|:--|
| 类型参数何时消失 | 代码生成前，每个实例替换 | 实例化时替换 | 编译期擦除为上界/Object |
| 运行时表示 | 每个实例独立函数 | 每个实例独立函数，weak/COMDAT | 一份字节码，必要时插入 cast |
| 分派方式 | 静态；`dyn` 走 vtable | 静态；虚函数走 vtable | 静态检查，运行时 cast |
| 代码体积 | 随实例数增长 | 随实例数增长 | 基本不增长 |
| 典型错误 | trait bound 不满足、实例化递归 | 模板错误在实例化点、ODR | 运行时 `ClassCastException` |
| 跨编译单元 | 元数据驱动按需生成 | 头文件 + 弱符号合并 | 无实例化概念 |

单态化不是“零成本”的同义词。它把运行时分派成本换成编译期代码复制：十个类型实例就是十份机器码，指令缓存和链接时间都会涨。Rust 的 `-Zshare-generics`（nightly）尝试跨 crate 共享实例；C++ 用 `extern template` 抑制重复实例化；链接器的 ICF（identical code folding）可以合并完全相同的机器码，但它不解决调试信息和编译时间。反过来，擦除把代码体积压到一份，却在需要具体类型的地方插入运行时转换，并把一部分类型错误推迟到运行期。

::: ex 例 3.5.1 · 同一个约束，两种失败时机 {#ex-compilers.1.3.5.1}
Rust 的 `fn twice<T: Copy + Add<Output=T>>(x:T)->T` 在定义处就要求 T 满足约束；调用 `twice(SomeStruct)` 时，若 `SomeStruct` 没有实现 `Add`，错误在调用点/实例化点报告，并列出未满足的 obligation。C++ 的 `template <typename T> T twice(T x) { return x + x; }` 在定义处只做语法检查；`twice(SomeStruct)` 只有在实例化 `operator+` 失败时才报错，错误栈里会出现模板实例化路径。两者都把错误推到了“具体类型已知”的位置，但 Rust 的约束是显式签名的一部分，C++ 的约束常常藏在函数体里，直到实例化才暴露。
:::

::: errata 单态化的三个误解
1. **“单态化没有运行时开销，所以一定更快”**：代码体积、指令缓存、编译时间都是成本；小函数多实例可能变慢。
2. **“C++ 模板和 Rust 泛型只是语法不同”**：名字查找时机、约束检查位置、链接模型都不同，错误信息和 ODR 规则也不同。
3. **“泛型在运行时保留类型参数”**：Rust/C++ 单态化后类型参数消失；Java 擦除后也不保留；只有 C# 等具体化泛型在运行时保留。
:::

Rust 的 trait 求解还有两个工程边界。其一是一致性（coherence）：孤儿规则（orphan rule）要求 impl 要么在定义 trait 的 crate，要么在定义类型的 crate，否则不同 crate 可以写出冲突的 impl，链接时无法决定用哪一个。其二是重叠检查：两个 impl 可能对同一类型都适用时，编译器必须拒绝，除非有 specialization（nightly）。这两条规则让单态化时的“选哪个 impl”在编译期有唯一答案。

C++ 的边界则是两阶段查找和依赖名。模板里出现的 `x.foo()`，若 `x` 的类型依赖模板参数，编译器在定义时不能确定 `foo` 是成员、自由函数还是需要 ADL；它只能在实例化时再查。这也是为什么模板错误常常“看起来在库内部”，实际调用栈却指向用户代码。读这类诊断时，先找最内层的“required from here”，再找真正的类型不匹配。

::: note 借用检查与单态化的顺序
Rust 先在泛型 MIR 上做借用检查，再在 codegen 阶段单态化。因此借用错误只报告一次，不会因为实例化成十个类型而重复十次；反过来，单态化后的 LLVM IR 不再携带生命周期信息，生命周期只影响前端检查，不影响机器码布局（除了一些 drop 顺序）。这也是“生命周期是编译期概念”的具体含义。
:::

::: method 判断一个泛型实现走哪条路
1. 看符号表：调用点是否出现按类型参数展开的多个符号？是，单态化。
2. 看运行时对象：是否有 vtable/字典指针？有，擦除或字典传递。
3. 看错误时机：约束错误在定义/调用点报，还是运行时 cast 失败？前者偏静态，后者偏擦除。
4. 看代码体积：实例数增加时机器码是否线性增长？是，单态化。
:::



### 3.5.1 实例化的三个边界

第一个边界是终止性。单态化在编译期为每个具体类型生成实例；若泛型定义递归地请求更大的类型，实例化可能不终止。例如一个函数对 <code>T</code> 实例化后又请求 <code>Vec&lt;T&gt;</code>，再请求 <code>Vec&lt;Vec&lt;T&gt;&gt;</code>，编译器会不断生成新类型。Rust 用递归上限（recursion limit）截断并报错，C++ 用模板实例化深度限制；这不是“编译器不够聪明”，而是语言允许的递归没有自然终点。工程上要么限制深度，要么要求用户显式标注/拆分层级。

第二个边界是分离编译。Rust 的泛型定义放在 crate 的元数据里，下游 crate 需要实例化时重新做单态化；这要求上游保留足够的 MIR/类型信息，也让“二进制接口稳定”变难。C++ 把模板定义放在头文件里，每个翻译单元自行实例化，链接器再合并 weak 符号；好处是简单，坏处是重复工作和 ODR 违规难以在编译期发现。Java 擦除后不存在实例化，但运行时需要 cast；C# 具体化泛型把实例化推迟到运行时/JIT。三种模型对“库升级后 ABI 是否兼容”的回答完全不同。

第三个边界是代码体积与调试信息。每个实例都是一份函数，调试器要能区分 <code>twice&lt;i32&gt;</code> 与 <code>twice&lt;f64&gt;</code>；符号表、行号表、内联信息都会随实例增长。链接器的 ICF 可以合并相同机器码，但调试信息通常不能简单合并。发布带泛型的库时，实例数量是构建预算的一部分，不是“优化阶段才考虑”的细节。

| 边界 | 触发条件 | 典型症状 | 处理 |
|:--|:--|:--|:--|
| 递归实例化 | 泛型体请求包含自身的更大类型 | 编译时间爆炸/递归上限错误 | 限制深度、显式分层、用 <code>dyn</code> |
| 分离编译 | 跨 crate/翻译单元使用泛型 | 重复实例、ODR、ABI 不稳定 | 元数据、<code>extern template</code>、显式实例化 |
| 代码体积 | 大量不同具体类型 | 二进制膨胀、指令缓存压力 | 共享实例、擦除、抽取非泛型部分 |

判断一个实现是否真的单态化，不要只看语法。看符号表里是否出现按类型展开的多个符号，看运行时是否有 vtable/字典，看错误是在实例化点还是运行时 cast 处出现。三者组合起来，基本能定位它属于哪条路线。

## 3.6 转换、整数提升与 UB 的接口 {#sec-compilers.1.3.6}

C 的类型检查器通过之后，表达式仍然可能因为转换而改变值。整数提升（integer promotion）和常规算术转换（usual arithmetic conversions）是 C17 6.3 的规则，不是“编译器顺手做的优化”。前端必须把它们显式编码进 AST/IR，否则后面的常量折叠、代码生成和 UB 判断都会错。

先把 C 的整数转换等级（conversion rank）排清楚：`_Bool` < `char` < `short` < `int` < `long` < `long long`，对应的无符号类型等级相同。整数提升的规则是：若 `int` 能表示该类型的所有值，提升为 `int`；否则提升为 `unsigned int`。在常见的 32 位 `int`、8 位 `char` 平台上，`char`/`short` 都提升为 `int`；但“总是提升到 int”是错的，16 位平台上 32 位 `unsigned int` 可能无法被 `int` 表示，规则会选 `unsigned int`。

常规算术转换在提升之后进行，顺序大致是：若任一操作数是 `long double`/`double`/`float`，转到该浮点类型；否则对两个整数操作数做整数提升；若同号，转到等级较高者；若一个无符号、一个带符号，且无符号等级不低于带符号，转到无符号类型；若带符号类型能表示无符号类型的所有值，转到带符号类型；否则转到带符号类型对应的无符号类型。C17 6.3.1.8 给出了完整规则。

| 表达式 | 提升/转换后 | 结果 | 原因 |
|:--|:--|:--|:--|
| `char c = -1; c < 0` | `(int)c < 0` | 真（char 有符号时） | char 提升为 int，保留 -1；无符号 char 则另算 |
| `-1 < 1u` | `(unsigned)-1 < 1u` | 假 | int 转 unsigned，-1 变成 UINT_MAX |
| `u + i`（u 为 1u，i 为 -2） | `1u + (unsigned)-2` | 4294967295 | 无符号回绕 |
| `(unsigned char)300` | 300 mod 256 | 44 | 转无符号类型按模 2 的 N 次方 |
| `sizeof('a')` | `sizeof(int)` | 4（C17） | 字符常量类型是 int |
| `sizeof(i + 1)` | `sizeof(int)` | 4 | 提升后仍是 int |

这些规则可以用一个严格编译的 C 程序实测。下面的代码在 macOS 14 / Apple clang 21 上通过 `cc -std=c17 -Wall -Wextra -Werror`：

```c
#include <stdio.h>
#include <limits.h>

int main(void) {
    int i = -2;
    unsigned int u = 1;
    printf("i < u        = %d\n", (unsigned)i < u);
    printf("u + i        = %u\n", u + i);
    printf("sizeof(i+1)  = %zu\n", sizeof(i + 1));
    printf("sizeof('a')  = %zu\n", sizeof('a'));
    printf("(unsigned char)300 = %u\n", (unsigned char)300);
    printf("INT_MAX + 1u = %u\n", (unsigned)INT_MAX + 1u);
    printf("-1 < 1u      = %d\n", (unsigned)-1 < 1u);
    return 0;
}
```

编译并运行：

```bash
cc -std=c17 -Wall -Wextra -Werror /tmp/promo.c -o /tmp/promo
/tmp/promo
```

真实输出：

```text
i < u        = 0
u + i        = 4294967295
sizeof(i+1)  = 4
sizeof('a')  = 4
(unsigned char)300 = 44
INT_MAX + 1u = 2147483648
-1 < 1u      = 0
```

注意第一行：源程序写的是 `i < u`，但为了让严格编译通过，代码显式写成 `(unsigned)i < u`，语义与 C 的常规算术转换一致。若直接写 `i < u`，clang 会在 `-Wsign-compare` 下发警告；在 `-Werror` 下编译失败。这个警告本身不是错误，但它提醒你：比较发生了符号转换，结果可能和数学直觉相反。

::: def 定义 3.6.1 · 转换、提升与 UB {#def-compilers.1.3.6.1}
**整数提升**把等级低于 `int` 的整数类型转成 `int` 或 `unsigned int`。**常规算术转换**在二元运算前把两个操作数转到一个公共类型。**未定义行为**（UB）指标准不规定程序行为的操作；编译器可以假设它不发生，并据此优化。C17 中有符号整数溢出、除零、越界访问、移位位数为负或超过位宽等都属于 UB；无符号整数运算按模 2 的 N 次方回绕，是定义良好的。
:::

转换在编译器内部必须显式表示。前端把 `int + unsigned` 降成“把 int 转成 unsigned，再做无符号加法”；在 LLVM IR 里对应 `zext`/`sext`/`trunc`/`bitcast` 加相应宽度的 `add`。如果前端偷懒，直接生成一个 64 位加法再截断，结果在某些输入上会不同。下面的 x86-64 代码生成结果说明“32 位结果”和“64 位扩展”是两件事：

```c
int add_i(int a, int b) { return a + b; }
unsigned add_u(unsigned a, unsigned b) { return a + b; }
long long widen(int a, unsigned b) { return (long long)a + (long long)b; }
```

```bash
clang -target x86_64-apple-darwin -O2 -S /tmp/widen.c -o /tmp/widen.s
clang -target x86_64-apple-darwin -O2 -c /tmp/widen.c -o /tmp/widen.o
llvm-objdump -d /tmp/widen.o
```

```asm
_add_i:
        leal    (%rdi,%rsi), %eax
        retq
_add_u:
        leal    (%rdi,%rsi), %eax
        retq
_widen:
        movslq  %edi, %rcx
        movl    %esi, %eax
        addq    %rcx, %rax
        retq
```

这里只读代码生成结论，不展开指令集。`add_i` 与 `add_u` 都用 32 位 `leal` 产生结果，说明返回类型宽度决定了截断；`widen` 先用 `movslq` 把有符号 `int` 符号扩展，再用 `movl` 把 `unsigned` 零扩展到 64 位，最后做 64 位加法。ABI 与指令语义的细节在第 8 章和《Linux 系统与内核》1.14–1.16，这里只关心“前端必须把转换意图传给后端”。

有符号溢出的接口最容易被误解。C17 6.5p5 规定，若算术运算的结果不能由类型表示，行为未定义。于是：

```c
#include <limits.h>
#include <stdio.h>
int main(void) {
    int x = INT_MAX;
    printf("%d\n", x + 1);
    return 0;
}
```

用 UBSan 编译运行：

```bash
cc -std=c17 -Wall -Wextra -Werror -fsanitize=undefined -fno-sanitize-recover=all /tmp/ov.c -o /tmp/ov
/tmp/ov
```

本机输出（退出码 134）：

```text
ov.c:5:22: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
SUMMARY: UndefinedBehaviorSanitizer: undefined-behavior ov.c:5:22
```

UBSan 报错不等于“所有 UB 都被抓住”，也不等于“没有报错就没有 UB”；它只是在运行时插桩检查了部分操作。第 9 章会展开 sanitizer 的覆盖边界。这里要记住的是：类型检查器允许 `x + 1`，因为两个操作数都是 `int`；UB 规则在类型规则之外，优化器可以假设 `x + 1` 不溢出，从而把依赖溢出的检查删掉。

::: ex 例 3.6.1 · 逐步算一次混合比较 {#ex-compilers.1.3.6.1}
对 `int i = -2; unsigned u = 1; i < u`：

1. 两个操作数分别已经是 `int` 和 `unsigned int`，不需要提升。
2. 常规算术转换：无符号等级不低于带符号，`int` 转成 `unsigned int`。
3. `-2` 转无符号得到 2 的 32 次方减 2，即 4294967294。
4. 比较 `4294967294 < 1`，结果为假（0）。

若把 `u` 改成 `1ULL`，`int` 会先转成 `unsigned long long`，结果仍是假；若把 `i` 改成 `long long`，在 64 位平台上 `long long` 能表示所有 `unsigned int`，比较会按带符号进行，结果为真。转换结果依赖类型等级和平台位宽，不能只背“有符号转无符号”。
:::

::: errata 整数转换的四个陷阱
1. **“整型提升总是到 int”**：若 `int` 无法表示该类型的全部值，提升到 `unsigned int`；16 位平台上是真实场景。
2. **“无符号减法不会得到负数，所以不会出问题”**：它会回绕成很大的正数，后续除法/取模可能得到意外结果。
3. **“UB 只影响出错的那一行”**：UB 一旦触发，整个执行都没有保证；优化器可以基于“不会发生”重写前后代码。
4. **“显式 cast 就安全”**：`(unsigned char)300` 是定义良好的模运算；`(int)UINT_MAX` 是实现定义或信号，仍可能不是你想要的值。
:::

::: note 编译选项会改变契约
`-fwrapv` 让 GCC/Clang 把有符号溢出当作二进制补码回绕，`-ftrapv` 插入溢出陷阱；它们改变的是编译器对该程序的契约，不是 C 标准。带 `-fwrapv` 编译的库和没带的调用方混用，优化假设可能不一致。跨模块发布时，把这类选项写进构建系统，不要依赖“默认应该一样”。
:::

类型检查与转换的接口可以总结成一条流水线：解析得到表达式类型 → 插入隐式转换节点 → 在 IR 中用显式宽/窄化指令表示 → 优化器只依赖语言规定的 UB/回绕契约。任何一步省略，都会在边界输入上表现为“类型检查通过但结果不对”。下一节讨论错误发生时，编译器怎样把位置、原因和修复建议组织成可用的诊断，以及增量编译怎样避免每次全量重算。


## 3.7 诊断、增量分析与错误恢复 {#sec-compilers.1.3.7}

类型检查器拒绝一个程序时，用户看到的不是“判断失败”，而是一条诊断（diagnostic）。诊断的质量取决于三件事：位置是否精确、原因是否说清、修复建议是否可执行。编译器内部还要决定错误之后是否继续、继续到什么程度，以及下一次编译能否只重算受影响的部分。这三件事共享同一套 span 和稳定 ID 基础设施。

先看一条真实的 clang 诊断。文件 <code>/tmp/dup.c</code> 内容如下；它故意在同一作用域重复声明，不能通过编译，只用来触发诊断：

```text
int main(void) {
    int x = 1;
    int x = 2;
    return x;
}
```

运行：

```bash
clang -std=c17 -fsyntax-only /tmp/dup.c
```

输出：

```text
/tmp/dup.c:3:9: error: redefinition of 'x'
    3 |     int x = 2;
      |         ^
/tmp/dup.c:2:9: note: previous definition is here
    2 |     int x = 1;
      |         ^
1 error generated.
```

这条诊断包含四个可用信息：主位置（3:9，第二个 <code>x</code>）、错误码/类别（redefinition）、次位置（2:9，第一次声明）、以及源码行与 caret。编译器内部不能只存一个字符串；它要存结构化记录，渲染器再根据终端宽度、颜色和语言环境输出。否则 IDE、CI 和 <code>--error-format</code> 无法复用同一份诊断。

::: def 定义 3.7.1 · 诊断记录 {#def-compilers.1.3.7.1}
一条诊断至少包含：严重级别（error/warning/note/help）、稳定的错误码、主 span、若干带标签的次 span、消息、可选的修复建议（fix-it）和关联诊断。span 是文件 ID 加字节区间；渲染时才转换成行:列。错误码用于测试与文档，消息用于人读，二者不能互相替代。
:::

错误恢复（error recovery）决定“报了一个错之后还能不能继续”。语法分析器通常在同步 token（分号、右花括号、关键字）处恢复，构造错误节点继续解析；类型检查器则给失败表达式一个错误类型（error type），让后续推导继续进行但不再产生连锁错误。错误类型与任何类型“兼容”，否则一个未声明变量会让整个函数体炸出几十条假错误。最终渲染时可以只显示第一条根因，其余标记为“由前面的错误引起”。

恢复策略需要边界。若错误类型过于宽松，真正的类型冲突会被吞掉；若过早停止，用户一次只能看到一个错。常见折中是：每个函数/块最多报 20 条错误，超过后进入“静默模式”，只统计数量；对同一位点相同错误码去重；对未声明名字，后续使用不再重复报，除非出现在新的作用域。clang 的 <code>-ferror-limit</code>、Rust 的 <code>--error-format=json</code> 都服务这个目的。

| 阶段 | 典型恢复动作 | 风险 |
|:--|:--|:--|
| 词法 | 跳过非法字符，继续切 token | 把一个字符错误扩散成多个 token 错误 |
| 语法 | 同步到分号/右花括号，插入错误节点 | 错误节点导致 AST 形状异常 |
| 名称解析 | 返回“未声明”占位绑定 | 后续类型检查把占位当真实类型 |
| 类型检查 | 返回错误类型，继续检查兄弟节点 | 吞掉真实冲突，诊断顺序不稳定 |
| 借用检查 | 标记受污染区域，跳过相关约束 | 漏报后续真实的借用错误 |

增量分析（incremental analysis）把“每次全量重跑”改成“只重算受影响的查询”。核心是查询（query）：每个查询有键（例如 <code>typeck(function_id)</code>）、结果和依赖集合。第一次执行时记录它读了哪些输入/其他查询；源文件变化后，把受影响的键标脏，按依赖图重算。若重算结果与旧结果相同，依赖它的查询不必重算，这叫提前截止（early cutoff）。

一个可用的增量前端至少需要：

1. 稳定的实体 ID（函数、类型、绑定），不能随文件重排而变。
2. 精确的依赖记录，包括“读了哪个文件的哪个区间”。
3. 内容哈希或版本号，避免 mtime 相同但内容变化。
4. 诊断缓存，连同 span 一起失效；旧 span 不能指向新文件。
5. 确定性输出，缓存命中与未命中都产生相同顺序的诊断。

| 缓存键 | 依赖 | 失效条件 | 备注 |
|:--|:--|:--|:--|
| <code>parse(file)</code> | 文件内容、语言版本 | 内容哈希变化 | 注释变化也会重解析，但可进一步做 token 级复用 |
| <code>resolve(module)</code> | 导入表、可见声明 | 任一依赖模块的导出签名变化 | 只看签名，不看函数体 |
| <code>typeck(fn)</code> | 函数 AST、签名、trait impl 表 | 函数体或相关 impl 变化 | 签名不变时调用方不重算 |
| <code>borrowck(fn)</code> | MIR、类型、生命周期约束 | MIR 或类型变化 | 泛型函数只检查一次 |
| <code>codegen(instance)</code> | 单态化后的 MIR、目标配置 | 实例集合或优化级别变化 | 代码体积随实例增长 |

增量系统最容易错在“依赖漏记”。若 <code>typeck(fn)</code> 读取了某个全局常量但没有记录依赖，常量改变后它仍用旧结果，表现为“改了代码不生效”。调试方法是对拍：全量编译与增量编译的结果/诊断逐条比较；对每个查询打印它读过的键，检查是否包含所有输入。另一个坑是 span 失效：缓存里存了 <code>(file_id, start, end)</code>，文件被编辑后偏移可能指向别的位置；要么在文件版本变化时使诊断失效，要么把 span 转成“锚点 + 偏移”并做重映射。

::: ex 例 3.7.1 · 一条诊断怎样被消费 {#ex-compilers.1.3.7.1}
<code>scope_lab.py</code> 对 <code>int z = 1; int z = 2;</code> 输出：

```text
error[E_DUP_DECL] @2:5: redeclaration of 'z' in the same scope
  2 | int z = 2;
    |     ^
  note @1:5: previous declaration of 'z' is here
    1 | int z = 1;
      |     ^
```

测试不该断言整段文本，而应断言：错误码是 <code>E_DUP_DECL</code>、主 span 是 2:5、次 span 是 1:5、消息包含名字 <code>z</code>。渲染格式可以随版本变化，结构化字段应稳定。若测试只 grep 一句英文，翻译或改标点就会误报。
:::

::: errata 诊断与增量的四个陷阱
1. **“错误越多越好”**：级联错误会淹没根因；限制数量、去重、标记根因。
2. **“用消息文本做测试断言”**：消息会改；断言错误码和 span。
3. **“缓存只按文件 mtime”**：内容可能在同一秒内变化；用内容哈希。
4. **“缓存诊断不用失效”**：span 指向旧文件，IDE 会跳到错误位置。
:::

::: note Rust 的查询系统
rustc 的查询系统（query system）把编译拆成带键的查询，依赖关系由执行过程自动记录；Salsa 等框架把同样思想带到 IDE。关键设计不是“缓存 map”，而是“依赖图 + 失效传播 + 提前截止”。增量编译的正确性最终仍要靠全量/增量对拍来保证。
:::

::: method 诊断 review 清单
1. 有没有稳定错误码？测试是否只依赖码和 span？
2. 主 span 是否指向用户能修改的最小片段？次 span 是否给出“之前在这里”？
3. 报错后是否继续？是否限制级联？错误类型是否会吞掉真实冲突？
4. 增量缓存是否记录了所有输入？诊断是否随文件版本失效？
5. 同一份源码跑两次，诊断顺序和内容是否完全一致？
:::



### 3.7.1 全量与增量对拍

验证增量编译器，最可靠的办法是把它和全量编译器对拍。对同一批源文件，分别跑“清空缓存的全量编译”和“先冷启动、再修改、再增量编译”，比较三类输出：诊断集合、生成的 IR/目标文件哈希、以及查询日志。诊断要按（错误码，文件，起止偏移）排序后比较，不能按渲染文本比较；目标文件若包含时间戳或路径，要先规范化。

对拍的修改要覆盖不同失效粒度：

| 修改 | 期望失效范围 | 若未失效，说明 |
|:--|:--|:--|
| 改注释/空白 | 最多重解析，不重做类型检查 | 依赖粒度太粗 |
| 改函数体 | 该函数的 typeck/borrowck/codegen | 依赖漏记或键不稳定 |
| 改函数签名 | 该函数及所有调用方的 typeck | 签名未进入依赖 |
| 改 trait impl | 相关泛型实例的 trait 求解 | impl 表未进入依赖 |
| 改目标配置 | 全部 codegen | 配置未进入缓存键 |

查询日志是定位“为什么重算了”的关键。每次查询打印键、是否命中、读了哪些依赖；对比两次编译的日志，就能看出是哪个输入变化导致了大面积失效。若日志显示“只改了注释却重算了整个 crate”，先查文件级依赖是否过粗，再查查询键是否包含整份源码哈希。

span 重映射是另一个高频 bug。增量缓存里存的是旧文件的偏移；文件插入一行后，同一偏移可能指向不同 token。修复方式有两种：缓存诊断时存“锚点（前后 token/行号）+ 相对偏移”，读取时按新文件重映射；或者在文件版本变化时直接丢弃所有相关诊断，宁可重算也不显示错位。前者省时间，后者省复杂度，按产品需求选。

### 3.7.2 机器可读诊断

CI、IDE 和自动修复工具不该解析人类可读的 caret 文本。编译器应提供结构化输出：JSON 诊断（文件、span、severity、code、message、fix-it）或 SARIF。Rust 的 <code>--error-format=json</code>、clang 的 <code>-fdiagnostics-format</code>（不同版本支持不同格式）都是这个方向。结构化的关键是稳定：字段名、错误码、span 语义要版本化；消息文本可以改，消费方不应依赖它。

机器可读输出还要处理多文件、宏展开、生成代码。一个 span 可能指向宏定义或展开后的位置，诊断要能同时给出“展开处”和“定义处”；否则 IDE 跳转只会跳到宏里。设计诊断格式时，把 primary span、related spans、notes、fix-it 分开，不要把所有信息塞进 message 字符串。

## 3.8 agent 错误：块作用域泄漏与同名遮蔽 {#sec-compilers.1.3.8}

这一节复盘一个具体的 agent 失败。任务是“给带块语句的表达式语言写类型检查器，支持变量声明、赋值和 return”。agent 写了递归下降的检查器，用 <code>enter()</code>/<code>leave()</code> 维护作用域栈，代码大致如下：

```python
class Checker:
    def __init__(self):
        self.scopes = [{}]

    def enter(self):
        self.scopes.append({})

    def leave(self):
        self.scopes.pop()

    def check_block(self, block):
        self.enter()
        for stmt in block.body:
            if isinstance(stmt, Return):
                self.check_expr(stmt.value)
                return              # BUG: 提前返回，没有 leave()
            self.check_stmt(stmt)
        self.leave()

    def resolve(self, name):
        for scope in reversed(self.scopes):
            if name in scope:
                return scope[name]
        return None
```

现象不是崩溃，而是“错误地接受”。触发条件是块里有一条提前 <code>return</code> 的路径：

```text
int f() {
  {
    int y = 2;
    return y;
  }
}
int g() {
  print(y);     // 应该报未声明
  return 0;
}
```

<code>check_block</code> 在内层块遇到 <code>return</code> 时直接返回，<code>leave()</code> 没有执行。于是检查 <code>g</code> 的函数体时，作用域栈顶部仍然留着 <code>f</code> 内层块的 <code>y</code>；<code>print(y)</code> 解析成功，类型检查通过。后续代码生成会为这个 <code>y</code> 分配/引用一个已经结束的槽位，或者错误地复用另一个函数的栈偏移。症状取决于后端：可能是“未声明变量被接受”，也可能是运行时读到垃圾值。

根因有两层。表层是“清理代码没有覆盖所有控制流出口”；深层是把作用域的生命周期绑在**可变栈的当前状态**上，而不是绑在 AST 的语法结构上。只要用可变栈，就必须保证每条路径都成对调用；<code>return</code>、<code>break</code>、<code>continue</code>、异常、诊断提前退出都是潜在的漏点。修复不能只补一个 <code>return</code> 分支，而要让“离开”不可能被忘记。

先复现。实验脚本的 <code>--leak-scope</code> 模式故意在 <code>leave()</code> 里不弹栈，输出：

```text
[snap] after decl y @2:7 depth=2 scope#1(-) | scope#2(y:#1:int@2:7)
[snap] after block @1:1 depth=2 scope#1(-) | scope#2(y:#1:int@2:7[dead])
trace:
  enter program @1:1 depth=1
  enter block @1:1 depth=2
  declare #1 y:int @2:7
  resolve y -> #1 (int) @3:9
  BUG leave block @1:1: skipped pop, depth=2
  resolve y -> #1 (DEAD, scope exited)
diagnostics: 0 error(s), 1 warning(s)
warning[W_DEAD_BINDING] @5:7: 'y' resolves to #1 in an exited scope
```

正常模式下同一个程序会报 <code>E_UNDECLARED</code>，主 span 是 5:7。两种输出的差别只在 <code>leave()</code> 是否真的弹出；类型规则、解析器和错误渲染都没有变。这说明 bug 在作用域状态管理，不在类型系统。

怎样更早发现？三个检查按成本从低到高：

1. **深度断言**：每次进入/离开块后，断言 <code>len(scopes) == expected_depth(block)</code>。expected_depth 可以由 AST 的嵌套深度算出，或由进入时记录的 token 深度算出。
2. **绑定来源检查**：解析每个名字时打印它命中的 BindingId 和声明 span；若声明 span 不在当前 AST 子树的祖先链上，说明跨作用域泄漏。
3. **死绑定标记**：离开作用域时把所有绑定标成 <code>alive=False</code>，解析到死绑定时至少发 warning；这不能替代正确弹出，但能把静默错误变成可观测信号。

修复一：用 <code>try/finally</code> 包住块体，保证任何退出路径都弹出。

```python
def check_block(self, block):
    self.enter()
    try:
        for stmt in block.body:
            if isinstance(stmt, Return):
                self.check_expr(stmt.value)
                return
            self.check_stmt(stmt)
    finally:
        self.leave()
```

修复二：不维护可变栈，把环境作为参数传下去。进入块时构造子环境，离开时直接丢弃；<code>return</code> 只是提前返回，不会污染调用者的环境。

```python
def check_block(self, block, env):
    inner = env.child()
    for stmt in block.body:
        if isinstance(stmt, Return):
            self.check_expr(stmt.value, inner)
            return
        self.check_stmt(stmt, inner)
    # 没有 pop：inner 离开函数就不可见
```

修复二更彻底：作用域的正确性由数据流保证，而不是由“记得调用 leave”保证。代价是环境对象更多、查找可能更慢；可以用持久 map 或 arena 降低成本。无论选哪种，测试都要覆盖“提前返回/异常/错误恢复”三条路径，而不只是正常落到底的块。

| 观察 | 表层解释 | 真正根因 | 验证 |
|:--|:--|:--|:--|
| 块外名字被接受 | 符号表还有内层条目 | <code>leave()</code> 在某条路径未执行 | 打印栈深度；<code>--leak-scope</code> 复现 |
| 同名变量解析错 | 内层遮蔽外层 | 绑定 ID 与声明 span 不匹配 | 解析时打印 BindingId + decl_span |
| 错误位置跳到别处 | 诊断用了旧 span | 增量缓存未失效/文件重映射错 | 对比全量与增量诊断 |
| 后端读到垃圾 | 槽位已释放 | 前端把死绑定传给 IR | 在 IR 生成前断言 binding.alive |

::: errata 漏弹栈的三个错误修法
1. **只在 <code>return</code> 分支补 <code>leave()</code>**：<code>break</code>/<code>continue</code>/异常仍会漏；用 <code>finally</code> 或不可变环境。
2. **在 <code>leave()</code> 里清空整个栈**：会把外层作用域一起删掉，后续名字全部未声明；只弹一层。
3. **用“解析失败再回溯”掩盖**：回溯可能让同一个名字先命中内层死绑定，再命中外层；必须从结构上保证死绑定不可见。
:::

::: method 作用域 bug 的定位顺序
1. 用最小程序复现：内层声明 + 提前返回 + 块外同名使用。
2. 打印每次 enter/leave 的深度和 span，找深度不为零的出口。
3. 打印每个 use 的 BindingId 与 decl_span，确认声明在祖先作用域内。
4. 加断言/回归测试，再改结构（finally 或持久环境）。
5. 跑全量测试，确认没有把“合法的遮蔽”误报成泄漏。
:::

这个案例的教训可以推广到所有“遍织式”状态：符号表栈、借用作用域、诊断上下文、代码生成的槽位分配，只要用可变栈，就要为每条退出路径负责。类型系统本身没有错；错在把“语法块的生命周期”实现成了“函数调用栈的生命周期”。

## 3.10 本章陷阱（8–15 条） {#sec-compilers.1.3.10}

::: errata 本章陷阱
1. **现象**：块退出后仍能解析到块内名字。**原因**：<code>leave()</code> 在提前返回/异常路径被跳过。**修复/验证**：用 <code>try/finally</code> 或持久环境；跑 <code>scope_lab.py --leak-scope</code>，并断言每次 enter/leave 后深度正确。
2. **现象**：同一作用域重复声明被当成合法遮蔽。**原因**：只查了“外层有没有”，没查“当前层有没有”。**修复/验证**：<code>declare</code> 先查当前层；测试 <code>int z=1; int z=2;</code> 必须报重复声明。
3. **现象**：<code>int x = x;</code> 初始化器解析到外层变量。**原因**：按“初始化器先求值”的直觉实现，忽略了声明点。**修复/验证**：按语言标准把新声明在声明符之后、初始化器之前加入作用域；C 与 Rust 的规则不同，分别测试。
4. **现象**：把名称解析当成重载决议，<code>f(1)</code> 直接报“找不到 f”。**原因**：解析只返回单个 BindingId，没有返回候选集合。**修复/验证**：解析阶段返回候选集合，类型检查阶段再做重载/约束筛选；测试同名不同参数。
5. **现象**：类型检查通过就认为没有 UB。**原因**：把“类型安全”当成“程序正确”。**修复/验证**：单独实现除零、溢出、越界检查或依赖 sanitizer；用 3.6 的 UBSan 用例验证。
6. **现象**：要求类型系统既可靠又完备，拒绝任何误报。**原因**：忽略了可判定性边界。**修复/验证**：明确保证范围；把“拒绝合法程序”与“接受非法程序”分开测试，记录已知的保守点。
7. **现象**：把静态类型当成强类型，认为 C 不会类型混淆。**原因**：混淆检查时机与检查强度。**修复/验证**：用 C 的指针转换/联合体与 Python 的 <code>TypeError</code> 对照；在文档里分别写“何时检查”和“检查多严”。
8. **现象**：认为有类型推导就不需要标注。**原因**：把 HM 的适用范围当成所有语言。**修复/验证**：测试多态递归、重载、高阶函数；在需要处加标注并检查错误信息是否建议标注。
9. **现象**：合一产生无限类型或栈溢出。**原因**：缺少 occurs check，或对递归类型变量反复展开。**修复/验证**：在绑定类型变量前检查出现；测试 <code>fn f(x) { f(x) }</code> 一类递归约束。
10. **现象**：认为整型提升总是到 <code>int</code>。**原因**：只考虑了 32 位平台。**修复/验证**：按 C17 6.3.1.1 实现“能表示则 int，否则 unsigned int”；用 16 位平台或 <code>unsigned int</code> 宽度不同的目标测试。
11. **现象**：把有符号溢出当成二进制补码回绕。**原因**：把 x86 的实现行为当成 C 的语义。**修复/验证**：用 <code>-fsanitize=undefined</code> 跑 <code>INT_MAX + 1</code>；不要在优化器里假设回绕，除非使用 <code>-fwrapv</code>。
12. **现象**：无符号转有符号后得到意外的负数。**原因**：超出目标类型范围时是实现定义或信号，不是模运算。**修复/验证**：检查转换前后范围；必要时用更宽类型或显式检查。
13. **现象**：诊断测试因改文案而失败。**原因**：断言了完整英文消息。**修复/验证**：断言错误码、主/次 span、关键名字；渲染文本只做快照测试。
14. **现象**：增量编译改了代码却不生效。**原因**：查询漏记依赖，或缓存诊断的 span 未失效。**修复/验证**：全量/增量对拍；打印查询依赖；文件版本变化时使诊断失效。
15. **现象**：认为单态化一定比擦除快。**原因**：只看到运行时分派成本，忽略代码体积和编译时间。**修复/验证**：比较实例数、机器码大小、编译时间；在热路径上再谈性能。
:::



这些陷阱看似分散，其实围绕三条主线。第一条是**状态**：作用域栈、绑定表、缓存版本，任何“进入/离开”或“读/写”不成对，都会让名字或诊断指错对象。第二条是**近似**：类型系统、类型推导、整数转换都是可判定的近似，必须写清保证范围与平台条件，不能用“总是”掩盖边界。第三条是**证据**：错误码、span、真实编译输出、全量/增量对拍，都是把“我觉得对”变成“可以复现”的手段。

| 主线 | 代表陷阱 | 最小验证 |
|:--|:--|:--|
| 状态 | 漏弹栈、重复声明、缓存 span 失效 | 深度断言、<code>--leak-scope</code>、全量对拍 |
| 近似 | 可靠=完备、推导=动态、提升总到 int | 反例程序、平台位宽、UBSan |
| 证据 | 断言文案、单态化零成本、缓存漏依赖 | 错误码+span、符号表、查询日志 |

把这三条主线记住，比背 15 条清单更有用：遇到新问题时，先问它属于状态、近似还是证据，再去找对应的最小实验。

::: method 即时自测 · 3
**Q1** 为什么块作用域退出时一定要弹栈？如果只在函数结束时清空整个栈，会出什么问题？

::: sol 答案
块作用域的名字只在块内可见。如果不弹栈，块外的同名或不同名使用会解析到已经销毁的绑定，类型检查和代码生成都会基于错误的 BindingId；如果函数结束时才清空，函数内多个块的声明会互相污染，遮蔽关系也错。正确做法是进入块压一层、离开块弹一层，或用持久环境让离开自动生效。验证方式是打印每次 enter/leave 后的深度，并测试“内层声明 + 块外同名使用”必须报未声明。
:::

**Q2** 在 32 位 <code>int</code>、<code>unsigned int</code> 的平台上，<code>int i = -2; unsigned u = 1; i < u</code> 的结果是什么？为什么？

::: sol 答案
结果是 0（假）。两个操作数先做整数提升，但 <code>int</code> 和 <code>unsigned int</code> 都已经不低于 <code>int</code>，所以不变；常规算术转换发现无符号等级不低于带符号，把 <code>int</code> 转成 <code>unsigned int</code>。-2 转成 4294967294，和 1 比较为假。若在 64 位平台上把 <code>i</code> 改成 <code>long long</code>，且 <code>long long</code> 能表示所有 <code>unsigned int</code>，则按带符号比较，结果为真。
:::

**Q3** 单态化和类型擦除在符号表与运行时各留下什么痕迹？各举一个可验证的现象。

::: sol 答案
单态化为每个具体类型生成独立函数：Rust 的 <code>--emit=llvm-ir</code> 能看到 <code>twice::&lt;f64&gt;</code> 和 <code>twice::&lt;i32&gt;</code> 两个函数，C++ 的 <code>nm</code> 能看到 <code>twice&lt;int&gt;</code> 与 <code>twice&lt;double&gt;</code> 两个 weak 符号；运行时不保留类型参数。擦除只生成一份代码，类型参数在编译期消失，必要时插入运行时 cast；Java 的 <code>List&lt;String&gt;</code> 与 <code>List&lt;Integer&gt;</code> 共享同一个类，错误可能以 <code>ClassCastException</code> 形式出现。验证时看符号数量、代码体积和运行时异常，而不是只看语法。
:::
