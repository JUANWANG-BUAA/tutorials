## 2.1 词法：正则、DFA、最大匹配与关键字 {#sec-compilers.1.2.1}

词法分析（lexical analysis）的任务是把字符序列切成 token，并给每个 token 一个类别与位置。它不判断「这个表达式是否类型正确」，也不建树；它只回答「从这里开始，最长的合法 token 是什么」。

::: def 定义 2.1.1 · token、词素与模式 {#def-compilers.1.2.1.1}
- **模式**（pattern）：一类 token 的字符集合，通常用正则表达式描述，例如标识符 `[A-Za-z_][A-Za-z0-9_]*`。
- **词素**（lexeme）：源文本中实际匹配到的字符序列，例如 `ifx`。
- **token**：`(kind, text, span)` 三元组，`kind` 是类别（IDENT、INT、IF……），`text` 是词素，`span` 是位置。关键字不是单独的字符类，而是标识符匹配后查表得到的类别。

把三者分开，才能解释「关键字也是标识符」：`if` 与 `ifx` 都匹配标识符模式，查表后前者变成 IF，后者仍是 IDENT。
:::

### 2.1.1 从正则到 DFA

正则表达式可以机械地转成非确定有限自动机（NFA），再子集构造为确定有限自动机（DFA）。把所有 token 的模式合并成一个大正则，构造一个 DFA，让它在字符流上跑到不能跑为止，最后停在一个接受状态，就得到最长匹配。

| 模式 | 类别 | 接受例子 | 边界 |
|:--|:--|:--|:--|
| `[A-Za-z_][A-Za-z0-9_]*` | IDENT/关键字 | `ifx`、`let` | 最长匹配后查关键字表 |
| `[0-9]+` | INT | `42` | 后面跟 `.` 时要看下一位 |
| `[0-9]+\.[0-9]+` | FLOAT | `1.5` | `1..2` 不能匹配成 FLOAT |
| `//[^\n]*` | 行注释 | `// note` | 不产生 token |
| `/*` … `*/`（状态机） | 块注释 | `/* note */` | 未闭合要报错 |

「最长匹配」（maximal munch）的规则是：在所有能从当前位置匹配的模式中，选消费字符最多的那个；若有多个模式匹配同样长度，按优先级（通常关键字优先于标识符，或先匹配标识符再查表）。实现上不需要真的构造 DFA：手写 lexer 用「先看首字符，再看若干位」的分支，就是在模拟 DFA 的状态转移。

::: thm 定理 2.1.1 · 正则语言不能识别嵌套结构 {#thm-compilers.1.2.1.1}
设 L 是正则语言。由泵引理，存在常数 p，使得任意长度不小于 p 的串 s 可以写成 xyz，满足 |xy| ≤ p、|y| ≥ 1，且对所有 i ≥ 0，xy^i z 仍在 L 中。取 L = { a^n b^n | n ≥ 0 }，对足够大的 n，y 只可能由 a 组成；令 i = 2 得到 a^{n+|y|} b^n，不在 L 中。因此 L 不是正则语言。

推论：括号匹配、嵌套注释、缩进块这类需要计数的结构，不能只靠正则/DFA 识别；它们需要下推自动机（parser）或显式的深度计数器。词法阶段可以识别「一个括号」，但不能判断「括号是否配平」。
:::

这条定理解释了为什么编译器要分词法与语法两层：词法处理**线性**的字符模式，语法处理**嵌套**的结构。把嵌套判断硬塞进 lexer，会得到一个既不是 DFA、也不便维护的状态机。

### 2.1.2 最大匹配的边界

最大匹配是必要规则，但不是充分规则。考虑 `1..2`：

- 数字模式 `[0-9]+(\.[0-9]+)?` 在 `1` 后看到 `.`，如果允许「点后零个数字」，会匹配 `1.`；
- 剩下的 `.2` 又可能匹配 `\.[0-9]+`，得到两个浮点数；
- 正确的词法应该把 `..` 当作独立 token（范围运算符），因此数字模式必须在「点后必须跟数字」时才消费点，否则把点留给下一个 token。

本章实验的实测 token 流：

```text
#03 INT       '1'          1:9-1:10
#04 DOTDOT    '..'         1:10-1:12
#05 INT       '2'          1:12-1:13
...
#10 FLOAT     '1.5'        2:9-2:12
...
error[E1003] 3:12 小数点后缺少数字
    let bad = 1.;
               ^
```

这三行分别证明：`1..2` 没有被贪婪地吃成浮点；`1.5` 正常成为 FLOAT；`1.` 在点处报错而不是被当作合法数字。边界规则是「数字里的点只在后一位是数字时才属于数字」，它比「最长匹配」多了一次**向前看**（lookahead）。

同样的边界出现在很多语言里：C 的 `1..2` 不合法，但 `1.0` 合法；Rust 的 `1..2` 是范围，数字点号的规则由语言规范单独规定；JavaScript 的 `1..toString()` 依赖「第一个点是数字的一部分，第二个点是成员访问」。规则不同，但实现手法相同：**先确定 token 的候选边界，再用下一位决定是否扩展**。

### 2.1.3 关键字与标识符

关键字通常不作为单独的正则分支，而是标识符匹配后的查表：

```python
text = ""
while self.peek().isalpha() or self.peek().isdigit() or self.peek() == "_":
    text += self.advance()
self.emit(KEYWORDS.get(text, "IDENT"), text, line, col)
```

这样做有两个好处：关键字表只有一处，增加关键字不需要改 DFA；错误消息可以说「`ifx` 是标识符，`if` 是关键字」，而不是「这里不该出现字母」。坏处是关键字不能再作为普通标识符使用（除非语言允许转义），这是语言设计选择，不是词法实现细节。

| 输入 | 最长匹配 | 查表后 | 说明 |
|:--|:--|:--|:--|
| `if` | IDENT(if) | IF | 关键字优先 |
| `ifx` | IDENT(ifx) | IDENT | 更长匹配阻止关键字 |
| `let1` | IDENT(let1) | IDENT | 数字可以跟在标识符后 |
| `_if` | IDENT(_if) | IDENT | 下划线开头不是关键字 |

### 2.1.4 词法需要语法反馈的地方

纯 DFA 的词法在少数语言里不够用，需要 parser 或上下文提供信息：

- C++ 的 `>>`：在模板参数闭合时应拆成两个 `>`，在移位表达式里是一个 `>>`。词法层无法只靠字符判断。
- Rust 的 `'a`：可能是字符字面量，也可能是生命周期标注；需要看闭合引号与后续 token。
- JavaScript 的 `/`：可能是除号，也可能是正则字面量开头；需要知道前一个 token 是否允许表达式。
- 嵌套块注释：Rust 允许嵌套，C 不允许；词法状态机要显式维护深度。

这些是**工程边界**，不是「正则无用」的证明。多数语言的词法仍是正则的；少数歧义点用「lexer hack」或 parser 驱动的扫描解决。设计时要把这些点列出来，写成测试，而不是假设 DFA 能处理一切。

读图：注释分支在运算符分支之前，所以 `//` 不会被当成两个 `/`；`--` 在 `-` 之前判断，所以它不会被当成两个一元减号；数字分支在消费点之前检查下一位，所以 `1..2` 的点留给 `DOTDOT`。**分支顺序本身就是词法规则的一部分**，不是实现细节。

### 2.1.6 token 之外的元数据

真实 lexer 产出的不只是 `(kind, text, span)`。parser 与工具常常还需要：这个 token 前面是否有换行（用于自动分号插入）、前面是否有空白（用于格式保留）、是否在宏展开中、是否来自 `#include`。把这些放进 token 的 flags 或 trivia 列表，比事后从 span 反推可靠。

| 元数据 | 用途 | 若缺失 |
|:--|:--|:--|
| `newline_before` | 自动分号插入、语句边界 | gofmt 风格语言解析错 |
| leading trivia | 注释/空白的保留与重排 | 格式化工具丢注释 |
| expansion span | 宏/模板诊断跳转 | 错误指向宏调用而非定义 |
| raw text | 字符串转义、数字进制 | 语义阶段要重新扫描 |

代价是 token 变大、缓存不友好。多数编译器只在需要时保留 trivia（例如格式化模式），普通编译路径丢弃它。设计时要问：谁会读这个字段？没有读者的字段不要加。

## 2.2 手写 lexer：位置、注释、数字与错误恢复 {#sec-compilers.1.2.2}

手写 lexer 的核心不是「写一堆 if」，而是维护三个不变量：**每个 token 的 span 正确**、**每个字符恰好被消费一次**、**出错后仍然前进**。破坏任何一个，都会产生难以定位的后续错误。

::: def 定义 2.2.1 · 源位置与 span {#def-compilers.1.2.2.1}
**span** 是源文本中的一个半开区间 `[start, end)`，通常带行列号与字节偏移。行列号从 1 开始，列指向字符边界；`start` 是第一个字符，`end` 是最后一个字符之后的位置。半开区间的好处是：相邻 span 可以直接拼接，空 span 的 `start == end`，长度等于 `end - start`。

一个 token 的 span 必须满足：`source[span.start:span.end] == token.text`（按同一编码与换行规则）。这条性质可以写成测试，2.7 会用到。
:::

### 2.2.1 位置跟踪

位置跟踪最容易出的错不是算法，而是约定不统一：

| 约定 | 常见选择 | 坑 |
|:--|:--|:--|
| 行号起点 | 1 | 与编辑器一致；0 起点会让诊断差一行 |
| 列号起点 | 1 | 制表符算一列还是展开到 8？要写清楚 |
| 偏移单位 | 字节 / Unicode 码点 / UTF-16 码元 | 多字节字符与编辑器列号不一致 |
| 换行 | `\n`、`\r\n`、`\r` | 只处理 `\n` 会把 Windows 文件的行号算错 |
| 半开/闭区间 | 半开 | 闭区间在拼接时容易多算一个字符 |

本章实验用「1 基行列 + 半开区间 + 只把 `\n` 当换行」的简化约定，源文本是 ASCII。真实编译器还要处理 BOM、CRLF、Unicode 标识符与制表符展开；这些都要在规范里写明，不能靠「大家都知道」。

### 2.2.2 注释：丢弃还是保留

注释通常不进入 token 流，但**不能简单丢掉**：

- 格式化工具需要保留注释与空行；
- 文档生成器需要文档注释；
- 诊断可能要把注释作为上下文；
- 重写工具（codemod）要在保留注释的前提下改代码。

常见设计是把注释放进 **trivia** 列表，附在相邻 token 上，或单独存一个按位置索引的数组。parser 不读 trivia，但工具可以读。这样既不污染语法，也不丢失信息。

块注释还要决定是否嵌套。C 的 `/* /* */` 在第一个 `*/` 结束，Rust 允许嵌套。本章实验实现非嵌套，并在遇到未闭合时发出诊断，span 从 `/*` 延伸到文件结尾：

```text
error[E1002] 3:12 块注释未闭合
    let c = 3; /* open
               ^
    help: 补上 '*/'；错误 span 延伸到文件结尾
```

### 2.2.3 数字：最长匹配 + 向前看

数字的词法规则看似简单，实际边界最多：整数/浮点、进制前缀、指数、后缀、分隔符、溢出。本章实验只支持十进制整数与「点后必须有数字」的浮点，代码是：

```python
if c.isdigit() or (self.buggy_float and c == "." and self.peek(1).isdigit()):
    sl, sc = self.line, self.col
    text = ""
    while self.peek().isdigit():
        text += self.advance()
    if self.peek() == ".":
        nxt = self.peek(1)
        if nxt.isdigit():
            text += self.advance()
            while self.peek().isdigit():
                text += self.advance()
    kind = "FLOAT" if "." in text else "INT"
    self.emit(kind, text, sl, sc)
```

关键行是 `if nxt.isdigit()`：只有下一位是数字才消费点。这一行同时解决了 `1..2`、`1.` 与 `1.5` 三种情况。若把它改成「看到点就消费」，`1..2` 会变成 FLOAT(1.) + FLOAT(.2)，2.8 会展示这个错误版本的完整输出。

| 输入 | 结果 | 规则 |
|:--|:--|:--|
| `42` | INT(42) | 连续数字 |
| `1.5` | FLOAT(1.5) | 点后至少一位数字 |
| `1..2` | INT(1) DOTDOT INT(2) | 点后不是数字，点留给 `..` |
| `1.` | INT(1) + E1003 | 点后没有数字，报错并跳过点 |
| `0x10` | INT(0) IDENT(x10) | 本语言不支持十六进制；解析器会报错 |

最后一行说明「词法正确」不等于「程序正确」：`0x10` 被切成两个合法 token，错误要到语法或语义阶段才暴露。词法只负责边界，不负责语言特性是否存在。

### 2.2.4 错误恢复：报告、跳过、继续

lexer 的错误恢复比 parser 简单：遇到无法识别的字符，发诊断、跳过它、继续扫描。但要注意三件事：

1. **不要跳过太多**：跳一个字符通常够；跳过整行会把后续合法 token 也吞掉。
2. **不要制造无限循环**：每个错误分支必须至少 `advance()` 一次。
3. **不要静默**：非法字符必须有诊断；否则 parser 会在缺少 token 的情况下产生级联错误。

| 错误 | 检测点 | 恢复 | 下游影响 |
|:--|:--|:--|:--|
| 非法字符 `\` | 所有分支都不匹配 | 跳过 1 字符 + E1001 | parser 少一个 token，可能级联 |
| 未闭合块注释 | 扫描到 EOF 未见 `*/` | 诊断 + 到 EOF | 后续代码全部被注释掉 |
| 数字后孤立点 | 点后非数字 | 诊断 + 跳过点 | 数字仍可用，表达式可能缺运算符 |
| 非法转义 | 字符串扫描 | 诊断 + 保留字符 | 字符串值可能不符合预期 |

「未闭合块注释」是最危险的一类：它不是少一个 token，而是把文件剩余部分全部吞掉。诊断的 span 必须覆盖从 `/*` 到 EOF，用户才能看出影响范围。本章实验的 span 是 `3:12-5:1`（起点到文件结尾），渲染时只画第一行，但数据里保留了终点。

### 2.2.5 位置与恢复的测试

位置正确性可以用一条性质检验：对每个非 EOF token，按 `span` 从源文本切片，必须等于 `text`。这条性质不需要知道 lexer 的内部状态，能抓住行列算错、半开/闭区间混用、多字节字符偏移等一类错误。

恢复正确性则要断言「诊断之后仍然前进了多少」：例如 `let bad = 1.;` 在报 E1003 后，解析器仍然得到 `Let bad = 1`，后续语句还能继续。只断言「有诊断」不够，还要断言 AST 没有崩、token 位置没有乱。

本节留下两个问题：token 怎样组合成树？优先级与结合性由谁决定？下一节进入语法分析。
### 2.2.6 未闭合注释的影响范围

::: ex 例 2.2.1 · 一个未闭合注释怎样吞掉后续代码 {#ex-compilers.1.2.2.1}
输入：

```text
let c = 3; /* open
more
```

词法结果：前面的 `let a`、`let b`、`let c` 正常，`/*` 之后的 `more` 全部被当作注释，直到 EOF。诊断是 `E1002 3:12 块注释未闭合`，span 从 `3:12` 到 `5:1`。parser 只看到三条完整语句，不会报「more 未定义」，因为 `more` 根本没有成为 token。

这个例子说明：lexer 的错误恢复会改变**后续所有阶段看到的输入**。如果诊断只写「unterminated comment」而不给 span 终点，用户无法判断影响范围；如果 lexer 静默丢弃而不报错，parser 会给出完全无关的「缺少语句」诊断。
:::

### 2.2.7 编码与换行边界

| 边界 | 错误做法 | 后果 | 正确做法 |
|:--|:--|:--|:--|
| UTF-8 BOM | 当作普通字符 | 第一个 token 前多一个非法字符 | 文件开头识别并跳过 BOM |
| CRLF | 只处理 `\n` | `\r` 留在 token 文本里 | 把 `\r\n` 当一个换行，列号重置 |
| 制表符 | 算一列 | 诊断的 caret 与编辑器不对齐 | 规范里定义 tab 宽度，或输出字节偏移 |
| 代理对 | 按 UTF-16 码元算列 | emoji 后的列号错位 | 明确列号单位，测试非 BMP 字符 |
| EOF 无换行 | 忘记补 EOF | parser 越界或死循环 | 总是在末尾补零宽 EOF token |

这些不是「边角料」。一个只在 ASCII + LF 上测试的 lexer，到了 Windows 文件或含 emoji 的注释就会给出错位的诊断。第 2.7 节的 span 回查能抓住一部分，但编码规则本身要写进规范。

## 2.3 语法：CFG、递归下降、Pratt 与优先级 {#sec-compilers.1.2.3}

token 流是线性的，程序结构是嵌套的。语法分析（parsing）的任务是把 token 流变成一棵抽象语法树（AST），并拒绝不符合语法的序列。描述语法的标准工具是上下文无关文法（context-free grammar，CFG）。

::: def 定义 2.3.1 · 上下文无关文法与推导 {#def-compilers.1.2.3.1}
一个 CFG 是四元组 `G = (N, T, P, S)`：`N` 是非终结符集合，`T` 是终结符（token 类别）集合，`P` 是产生式集合 `A ::= α`，`S` 是开始符号。一次**推导**（derivation）从 `S` 开始，反复把某个非终结符替换为某条产生式的右部，直到只剩终结符。所有能这样得到的终结符串构成文法识别的语言。

若一个串存在两棵不同的推导树，文法就是**歧义**的（ambiguous）。歧义不是「实现细节」，它意味着语言规范没有决定程序的含义；2.5 会处理最著名的一个例子。
:::

本章实验的语言子集可以用下面的文法描述（省略语句细节）：

```text
program  ::= stmt* EOF
stmt     ::= 'let' IDENT '=' expr ';'
           | 'if' '(' expr ')' stmt ('else' stmt)?
           | '{' stmt* '}'
           | 'print' expr ';'
           | expr ';'
expr     ::= expr ('..' | '==' | '<' | '>' | '+' | '-' | '*' | '/') expr
           | '-' expr
           | INT | FLOAT | IDENT
           | '(' expr ')'
```

这条文法只回答「哪些 token 串合法」，没有规定优先级：`expr` 的二元产生式本身就是歧义的，`a + b * c` 可以有两棵树。Pratt 的绑定力表负责消歧，文法本身不编码优先级。

最后一条 `expr` 产生式是**左递归**的：右部第一个符号又是 `expr`。递归下降 parser 直接按这条规则写会无限递归。解决办法是把左递归改写成循环：

```text
expr     ::= unary (binop unary)*
unary    ::= '-' unary | primary
primary  ::= INT | FLOAT | IDENT | '(' expr ')'
```

改写后的文法仍然识别同样的语言，但结合性由循环决定：`a - b - c` 解析为 `(a - b) - c`，因为循环从左到右吃操作数。若想要右结合（例如赋值），应改成右递归，或在 Pratt parser 里给右结合运算符不同的绑定力。

### 2.3.1 递归下降

递归下降（recursive descent）为每个非终结符写一个函数。函数消费它能识别的 token，返回 AST 节点；遇到不匹配就报错并恢复。它的优点是代码与文法一一对应，调试直观；缺点是需要手动处理左递归、优先级与错误恢复。

以本章实验的 Pratt parser 为例，表达式函数只做三件事：解析前缀、循环处理中缀、按绑定力决定是否继续：

```python
def parse_expr(self, min_bp: int):
    tok = self.advance()
    if tok.kind == "INT":
        left = IntLit(int(tok.text), tok.span)
    elif tok.kind == "IDENT":
        left = Var(tok.text, tok.span)
    elif tok.kind == "MINUS":
        left = Unary("-", self.parse_expr(9), tok.span)
    elif tok.kind == "LPAREN":
        left = self.parse_expr(0)
        self.expect("RPAREN", "')'")
    else:
        self.pos -= 1
        self.error("E2002", f"期望表达式，但遇到 {self.describe(tok)}", tok)
        return ErrorNode(tok.span)
    while True:
        bp = self.BINDING.get(self.peek().kind)
        if bp is None or bp[0] < min_bp:
            break
        op = self.advance()
        right = self.parse_expr(bp[1])
        left = Binary(op.text, left, right, Span(left.span.line, left.span.col,
                                                 right.span.end_line, right.span.end_col))
    return left
```

这段代码同时实现了优先级与左结合：`BINDING` 给每个运算符一对 `(左绑定力, 右绑定力)`；只有当左绑定力不小于当前最小绑定时才继续吃运算符；右操作数用右绑定力递归，保证同级运算符向左结合。

| 运算符 | 左绑定力 | 右绑定力 | 结合性 | 例子 |
|:--|--:|--:|:--|:--|
| `..` | 1 | 2 | 左 | `1..2..3` 解析为 `(1..2)..3` |
| `== != < <= > >=` | 3 | 4 | 左 | `a < b == c` 解析为 `(a < b) == c` |
| `+ -` | 5 | 6 | 左 | `a - b - c` 解析为 `(a - b) - c` |
| `* /` | 7 | 8 | 左 | `a / b * c` 解析为 `(a / b) * c` |
| 一元 `-` | 9 | — | 前缀 | `-a * b` 解析为 `(-a) * b` |

结合性不是「数学上应该怎样」，而是文法/优先级表的规定。减法左结合是大多数语言的约定；如果改成右结合，`a - b - c` 会变成 `a - (b - c)`，结果不同。测试必须同时断言 AST 形状与求值结果，不能只测后者。

### 2.3.2 结合性的实测

```bash

```

输出中两棵 AST 的差异就是结合性：

```text
Print @1:1-1:16
  expr: Binary '-' @1:7-1:16
    left: Binary '-' @1:7-1:12
      left: Var a @1:7-1:8
      right: Var b @1:11-1:12
    right: Var c @1:15-1:16

Print @2:1-2:17
```

第一棵是 `(a - b) - c`，第二棵是 `a - (b - c)`。括号没有进入 AST，它只改变了树的形状；这正是「AST 是语法结构的表示」的含义。

### 2.3.3 递归下降的边界

递归下降不是万能 parser。它要求文法没有左递归、尽量没有公共前缀；它不能直接处理需要任意前瞻的语法；它在错误恢复上需要手动设计同步点。LL(1) 文法可以用 FIRST/FOLLOW 集合机械地构造预测分析表，但手写 parser 通常不显式算这两个集合，而是用「看下一个 token」的经验规则。

| 问题 | 递归下降的表现 | 处理 |
|:--|:--|:--|
| 直接左递归 | 无限递归 | 改写成循环或右递归 |
| 间接左递归 | 仍然无限递归 | 先展开再消除 |
| 公共前缀 | 需要回溯或前瞻 | 提取左因子，或增加前瞻 |
| 优先级 | 需要多层函数 | 用 Pratt/优先级爬升 |
| 错误恢复 | 容易级联 | 同步集合 + 最大错误数 |

Pratt parser 的本质是「把优先级表放进循环」，它不是另一种文法，而是递归下降在表达式上的高效写法。2.5 会说明：即使 parser 能接受一个串，文法歧义仍可能让 AST 形状不符合用户预期。

本节留下一个问题：AST 应该长什么样，span 放在哪里，工具怎样遍历它？

### 2.3.4 FIRST/FOLLOW 与预测分析

当文法适合 LL(1)（从左到右扫描、最左推导、一个 token 前瞻）时，可以用 FIRST/FOLLOW 集合机械地决定走哪条产生式。FIRST(α) 是从 α 能开头的终结符集合；FOLLOW(A) 是能紧跟在 A 后面的终结符集合。对 `A ::= α | β`，若当前 token 在 FIRST(α) 中选 α，在 FIRST(β) 中选 β；若 α 可空，还要看 FOLLOW(A)。

| 非终结符 | FIRST | FOLLOW |
|:--|:--|:--|
| program | LET, IF, PRINT, IDENT, INT, FLOAT, MINUS, LPAREN, LBRACE | EOF |
| expr | INT, FLOAT, IDENT, MINUS, LPAREN | SEMI, RPAREN, 二元运算符 |
| stmt | LET, IF, PRINT, LBRACE, 表达式起始 | LET, IF, PRINT, RBRACE, ELSE, EOF |

手写递归下降通常不显式计算这些集合，而是把选择写成 `if/elif`。这没错，但要把「当前 token 不在任何候选里」的分支显式处理成诊断，而不是 `else: pass`。后者会让 parser 静默接受非法输入，直到后面才崩。

### 2.3.5 语句层的递归下降

表达式只是语法的一半。语句层的函数通常长这样：先看首 token 分派到 `let`/`if`/`print`/块/表达式语句；每个分支消费自己的关键字与分隔符；最后统一处理分号。语句层的错误恢复比表达式层更重要，因为一个坏语句不该让整个文件无法解析。

分派表（dispatch table）是常见优化：把 token 类别映射到处理函数，避免长 `if/elif` 链。它在语言有很多语句种类时更清晰，也更容易做「这个 token 能否作为语句开头」的诊断。

## 2.4 AST 设计：节点、span、访问者与序列化 {#sec-compilers.1.2.4}

抽象语法树（abstract syntax tree，AST）是编译器的中枢数据结构：前端建它，中端读它，诊断引用它，工具修改它。它的设计决定了后续所有 pass 的易用性。最常见的错误不是「节点不够多」，而是「节点里塞了太多不属于语法的东西」。

### 2.4.1 节点：标签联合还是类层次

一个 AST 节点是「种类 + 该种类的字段」。两种常见表示：

- **标签联合**（tagged union）：一个基类/枚举 + 每种节点的字段；Rust 的 `enum`、Haskell 的 `data`、Python 的 `dataclass` 联合。
- **类层次**：`Expr` 基类，`Binary`、`Call` 继承；访问者用双重分派。

本章实验用冻结的 dataclass，每种节点一个类，字段直接列出：

```python
@dataclass(frozen=True)
class Binary:
    op: str
    left: object
    right: object
    span: Span

@dataclass(frozen=True)
class If:
    cond: object
    then: object
    orelse: object
    span: Span
```

冻结（immutable）的好处是 pass 不能偷偷改树，必须显式重建；坏处是每次变换都要复制路径。可变树写起来快，但容易出现「这个 pass 改了节点，那个 pass 还在用旧引用」的 bug。选择哪一种，取决于你更怕「忘记重建」还是「复制开销」。

| 设计 | 好处 | 代价 | 适用 |
|:--|:--|:--|:--|
| 冻结 dataclass/union | 易推理、可共享、快照稳定 | 变换要重建 | 教学编译器、分析工具 |
| 可变类层次 | 原地修改方便 | 别名与顺序 bug | 早期原型 |
| arena + 索引 | 缓存友好、序列化简单 | 生命周期/索引管理 | 大型编译器 |
| 带父指针 | 向上遍历方便 | 环、序列化、并发 | IDE 重构 |

### 2.4.2 span：每个节点都要有

span 是 AST 节点在源文本中的范围。它有三个用途：诊断指向、IDE 跳转/高亮、source map。没有 span 的 AST 只能报「类型错误」，不能报「第 3 行第 7 列」。

本章实验的每个节点都带 `Span(line, col, end_line, end_col)`。合成节点（例如隐式类型转换、脱糖产生的节点）需要一个**合成 span**：可以指向触发它的源节点，也可以标记为「无源位置」。不要随便填 `0:0`，否则诊断会指向文件开头。

| span 场景 | 建议 | 原因 |
|:--|:--|:--|
| 普通节点 | 起止 token 的并集 | 用户能定位完整表达式 |
| 二元节点 | 从左操作数起点到右操作数终点 | 括号信息已丢失，但范围正确 |
| 合成节点 | 继承触发节点的 span，或标记 synthetic | 避免指向错误位置 |
| 宏展开 | 保留展开位置与定义位置两层 | 诊断要能跳回宏定义 |
| EOF 错误 | 零宽 span 在文件末尾 | 插入修复的锚点 |

### 2.4.3 访问者与 fold

访问者（visitor）把「对每种节点做什么」与「怎样遍历」分开。最轻的版本不是双重分派，而是一个 `children(node)` 函数 + 递归：

```python
def children(node):
    if isinstance(node, If):
        return [("cond", node.cond), ("then", node.then), ("else", node.orelse)]
    if isinstance(node, Binary):
        return [("left", node.left), ("right", node.right)]
    return []

def walk(node, visit):
    visit(node)
    for _, child in children(node):
        if child is not None:
            walk(child, visit)
```

这种写法牺牲了一点类型安全，换来极低的扩展成本：新增节点只需改 `children`，所有遍历自动支持。代价是编译器不能帮你检查「是否漏了某个子节点」；测试要覆盖每个节点的子节点列表。

### 2.4.4 序列化：快照测试的基础

把 AST 序列化成稳定文本，是快照测试与差分测试的基础。要点：

1. 字段顺序固定，不依赖 `dict` 迭代顺序；
2. 不写对象地址、时间、随机 ID；
3. span 可选：语义快照可以去掉 span，诊断快照必须保留；
4. 字符串转义统一，换行/引号不随平台变化。

本章实验的 `dump` 输出是缩进树，每个节点带 span：

```text
Program @1:1-3:1
  Let r @1:1-1:13
    value: Binary '..' @1:9-1:13
      left: IntLit 1 @1:9-1:10
      right: IntLit 2 @1:12-1:13
```

这类输出适合人读，也适合快照。若要给程序读，JSON 更稳：字段名固定、数组顺序固定、span 用四个整数。不要用 `repr(node)` 做快照，它包含内存地址与 Python 版本相关的格式。

### 2.4.5 AST 里不该放什么

- **类型信息**：类型检查的结果应放在 side table（节点 ID → 类型），否则同一棵树在不同 pass 里含义不同。
- **符号表**：绑定结果可以用 ID 引用，不要把整个符号表挂到节点上。
- **父指针**：除非工具需要向上遍历；父指针会形成环，序列化与并发都麻烦。
- **格式化信息**：空格、注释属于 trivia，不属于语法结构。

把这些分开，AST 才能在不同 pass、不同工具、不同版本之间保持稳定。第 3 章会说明 side table 怎样与作用域配合；第 4 章会说明为什么优化不该直接改 AST。

本节留下一个问题：文法有歧义时，AST 会变成什么样？dangling else 为什么是最典型的例子？

### 2.4.6 稳定节点 ID 与 side table

当 AST 需要被多个 pass 引用时，给每个节点一个稳定 ID（在本次编译内唯一）比对象地址可靠。side table 用 ID 做键，存类型、绑定、常量值、源码映射。这样 AST 本身可以保持纯语法，pass 之间通过表共享分析结果。

| 方案 | 键 | 优点 | 风险 |
|:--|:--|:--|:--|
| 对象地址/id() | 内存地址 | 零成本 | 不可序列化、不可复现 |
| 递增整数 | 构造顺序 | 稳定、紧凑 | 并行构造要原子/分片 |
| 路径 | 从根到节点的索引 | 可跨版本 | 路径长、重写后失效 |
| 内容哈希 | 子树文本 | 可去重 | 碰撞与性能 |

ID 的分配顺序也会影响可复现构建：并行解析时，不同线程拿到的 ID 段不同，若最终输出依赖 ID 顺序，产物就会漂移。解决方式是按源位置排序后再分配，或在发射前做一次规范化。

### 2.4.7 AST 重写与 span 维护

重写（rewrite）是 pass 的常见操作：把 `a + 0` 换成 `a`，把 `if (true) S` 换成 `S`。重写后 span 怎么办？

- 保留原节点的 span：诊断仍指向用户写的表达式；
- 用新节点的 span 覆盖：可能指向不存在的源位置；
- 标记为 synthetic 并链回原 span：工具可以区分「用户写的」与「编译器生成的」。

第三种最完整，但实现成本高。教学编译器至少要做到「不要产生非法 span」：合成节点的起止必须来自真实 token，或显式标记为 0 宽。否则 IDE 跳转会随机跳。

## 2.5 歧义、左递归与 dangling else {#sec-compilers.1.2.5}

歧义（ambiguity）是指同一个 token 串存在两棵不同的语法树。它不是「parser 实现得不好」，而是文法没有规定唯一结构。最著名的例子是 dangling else：

```text
if (a) if (b) print 1; else print 2;
```

`else` 属于外层 `if (a)` 还是内层 `if (b)`？两种都符合直觉，结果却不同。

### 2.5.1 两棵推导树

用简化文法：

```text
stmt ::= 'if' '(' expr ')' stmt
       | 'if' '(' expr ')' stmt 'else' stmt
       | 'print' expr ';'
```

对上面的输入，可以推导出：

- 外层 if 的 then 是「内层 if + else」：`else` 属于内层；
- 外层 if 的 then 是「内层 if」，`else` 属于外层。

两棵树都合法，文法因此有歧义。多数语言（C、Java、Rust、Go）选择「`else` 绑定最近的未匹配 `if`」，因为这与递归下降的自然行为一致：内层 `parse_stmt` 在返回前会先吃掉 `else`。

### 2.5.2 实测：else 绑到了谁

```bash
python3 experiments/ch02/lexer_lab.py --case dangling
```

```text
If @1:1-1:36
  cond: Var a @1:5-1:6
  then: If @1:8-1:36
    cond: Var b @1:12-1:13
    then: Print @1:15-1:22
      expr: IntLit 1 @1:21-1:22
    else: Print @1:29-1:36
      expr: IntLit 2 @1:35-1:36
```

输出显示 `else` 挂在内层 `If` 上，内层 `If` 的 span 延伸到 1:36，包含 `else` 分支；外层 `If` 的 then 就是这棵内层树。若想绑定到外层，必须加花括号：

```text
if (a) { if (b) print 1; } else print 2;
```

这时内层 `If` 在 `}` 处结束，`else` 只能属于外层。花括号不是风格问题，它改变了语法结构。

### 2.5.3 用无歧义文法消除 dangling else

除了「约定最近匹配」，还可以改写文法，把「已匹配/未匹配」编码进非终结符：

```text
stmt      ::= matched | unmatched
matched   ::= 'if' '(' expr ')' matched 'else' matched
            | 'print' expr ';'
unmatched ::= 'if' '(' expr ')' stmt
            | 'if' '(' expr ')' matched 'else' unmatched
```

这个文法没有歧义：`unmatched` 的 `then` 分支可以是任意 `stmt`（包括未匹配的 if），但 `else` 分支必须是 `unmatched`，从而强制「else 属于最近的那个未匹配 if」。它比「约定」更形式化，但写递归下降时通常不需要显式实现两套非终结符——自然递归已经产生同样的结构。

::: thm 定理 2.5.1 · 最近匹配的消除 {#thm-compilers.1.2.5.1}
对上述 matched/unmatched 文法，任意合法 token 串都有唯一推导树；且树中每个 `else` 都绑定到它前面最近的、尚未匹配 `else` 的 `if`。

证明思路：对推导树做结构归纳。`matched` 产生的树中所有 `if` 都已匹配；`unmatched` 产生的树中恰有一个未匹配的 `if`，且 `else` 只能通过 `unmatched` 的第二个产生式引入，因此绑定到该未匹配的 if。唯一性由文法无公共前缀且每个产生式首 token 不冲突推出。这里不展开完整形式证明，关键是：**消除歧义靠文法结构，不靠 parser 的偶然行为**。
:::

### 2.5.4 左递归与结合性

左递归是另一类结构问题。直接左递归：

```text
expr ::= expr '+' term | term
```

递归下降会在 `expr` 上无限调用自己。消除左递归：

```text
expr ::= term rest
rest ::= '+' term rest | ε
```

这个改写把「向左生长」变成「向右循环」，但默认产生右结合。若要左结合，应写成循环而不是尾递归：

```text
expr ::= term ('+' term)*
```

然后用循环构造 `Binary(left, right)`，每次把当前树作为左子树。结合性不是文法美化，它直接决定 AST 形状与求值结果。

| 构造 | 风险 | 处理 | 测试 |
|:--|:--|:--|:--|
| 直接左递归 | 无限递归 | 改循环/右递归 | 解析深表达式不栈溢出 |
| 间接左递归 | 仍然无限递归 | 展开后消除 | 覆盖所有非终结符 |
| dangling else | 两棵合法树 | 最近匹配/无歧义文法 | 断言 else 的父节点 |
| 公共前缀 | 需要回溯 | 提取左因子/前瞻 | 最小对 |
| 运算符优先级 | AST 形状错 | Pratt/分层 | 断言括号化输出 |

本节留下一个问题：parser 出错时，怎样给出有用的诊断并继续？期望集合、同步点与修复建议应该怎样组织？
### 2.5.5 歧义能检测吗

对一般 CFG，判定「文法是否歧义」是不可判定的；不存在一个算法对所有文法都给出是/否。工程上不追求通用判定，而是：

1. 对具体文法用工具（yacc/bison 的冲突报告、ANTLR 的警告）检查移进/归约或选择冲突；
2. 对递归下降，检查每个分派点的 FIRST 集合是否相交；
3. 对已发现的歧义，用「两棵 AST 是否不同」的测试锁定解析结果；
4. 在语言规范里写明消歧规则（最近匹配、优先级、结合性）。

::: ex 例 2.5.1 · 两种绑定给出不同输出 {#ex-compilers.1.2.5.1}
取 `a = false`、`b = true`，程序是 `if (a) if (b) print 1; else print 2;`。

- 最近匹配（内层）：外层条件为假，整个语句不执行，**没有输出**。
- 外层匹配：外层条件为假，执行外层 `else`，**输出 2**。

同一段文本、同一组输入，语义不同。这不是「实现差异」，而是文法没有规定唯一结构。测试必须断言 AST 的 `else` 父节点，不能只断言「能解析」。
:::

### 2.5.6 左递归消除的代价

消除左递归不是免费的。它改变了推导形状，可能影响：

- **结合性**：`term ('+' term)*` 的循环默认左结合；若写成右递归就变成右结合；
- **错误位置**：左递归文法的错误可能在对齐 token 处报，改写后可能提前/推迟；
- **语义动作**：在 yacc 里，左递归允许边解析边归约，右递归会堆积栈；手写 parser 不受这条影响，但 AST 构造顺序会变。

因此「消除左递归」要与「保持结合性」「保持诊断位置」一起测试，而不是只看能否解析。

## 2.6 诊断：期望集合、同步点与修复建议 {#sec-compilers.1.2.6}

parser 出错时最容易写成「syntax error」四个字。用户需要知道：在哪儿、期望什么、实际遇到什么、能不能修。把这些信息结构化，诊断才是产品的一部分，而不是调试输出。

::: def 定义 2.6.1 · 一条语法诊断 {#def-compilers.1.2.6.1}
一条语法诊断至少包含：

- **主 span**：出错位置，通常指向「意外的 token」而不是它前面的合法 token；
- **期望集合**（expected set）：当前位置允许出现的 token 类别集合，来自当前非终结符各产生式的 FIRST 集；
- **实际 token**：`kind`、`text` 与 span；
- **消息**：人类可读的一句话，说明期望与实际；
- **修复建议**（可选）：插入/删除/替换一个 token，或跳到同步点。

「期望集合」是可计算的结构，不应该靠手写字符串。递归下降 parser 在分支处已经知道有哪些候选；把这些候选收集起来，就能生成「expected one of ';', ')'」这类诊断。
:::

### 2.6.1 期望集合从哪来

对产生式 `A ::= α1 | α2 | ...`，当 parser 在 `A` 的入口看到 token `t` 时，期望集合是各 `αi` 的 FIRST 集合并集。若某个 `αi` 可以推出空串，还要加入 FOLLOW(A)。手写 parser 通常不显式算集合，而是在 `expect` 调用处传入一个类别；多个候选时传入列表。

本章实验的 `expect` 只接受一个类别，因此消息是「期望 `;`，但遇到 `let`」。更完整的实现会传「语句结束符集合 {`;`, `}`, EOF}」，消息变成「期望 `;` 或 `}`」。期望集合越大，消息越长；工程上要限制展示数量，并优先展示与当前上下文最相关的几个。

| 位置 | 期望集合 | 实际 | 诊断 |
|:--|:--|:--|:--|
| `let` 后 | IDENT | `=` | 期望标识符，但遇到 '=' |
| 表达式后 | `;`、`)`、运算符 | `let` | 期望 ';'，但遇到 'let' |
| `(` 后 | 表达式起始集合 | `;` | 期望表达式，但遇到 ';' |
| 语句开头 | 语句起始集合 | `else` | 无法作为语句开头 |

### 2.6.2 三种恢复策略

| 策略 | 做法 | 优点 | 风险 |
|:--|:--|:--|:--|
| 恐慌模式（panic mode） | 跳到同步 token，丢弃中间 token | 实现简单、保证前进 | 丢失信息，可能级联 |
| 短语级恢复 | 在局部插入/删除一个 token | 保住更多结构 | 修复可能错，产生假 AST |
| 错误产生式 | 文法显式接受常见错误 | 诊断精准 | 文法膨胀，维护成本高 |

本章实验混合使用前两种：缺分号时**插入**一个虚拟分号，不消费下一个 token；缺标识符或操作数时**跳到分号**并丢弃当前语句；遇到无法作为语句开头的 token 时，报告后跳过一个 token。三条规则都必须保证「每次恢复至少消费一个 token」，否则 parser 会死循环。

### 2.6.3 三种错误的实测

```bash
python3 experiments/ch02/lexer_lab.py --case recover
```

输入是：

```text
let x = 1 let y = 2;
let = 3;
let z = 1 + ;
print z;
```

输出保留了三条诊断，并且后续语句仍然被解析：

```text
error[E2001] 1:11 期望 ';'，但遇到 'let'
    let x = 1 let y = 2;
              ^^^
    help: 在此插入 ';'
error[E2001] 2:5 期望 标识符，但遇到 '='
    let = 3;
        ^
    help: 在 'let' 后写变量名
error[E2002] 3:13 期望表达式，但遇到 ';'
    let z = 1 + ;
                ^
    help: 补一个操作数，或删除前面的运算符
```

三条诊断对应三种恢复：

1. **缺分号**：在 `let` 前插入虚拟 `;`，不消费 `let`，所以 `let y` 还能被解析成独立语句。AST 里 `x` 与 `y` 都在。
2. **缺标识符**：`let = 3` 无法构成声明；报告后跳到 `;`，丢弃这一条语句，继续下一条。
3. **缺操作数**：`1 + ;` 的右操作数缺失；报告后跳到 `;`，保留一个 `Error` 节点，避免把分号当成表达式。

实验的 summary 是 `tokens=22 nodes=12 diagnostics=3`。三个诊断、十二个节点说明恢复没有把整棵树丢掉；如果只报第一个错就退出，后两条语句的用户要改三次、编译三次。

### 2.6.4 级联与抑制

错误恢复最大的敌人是级联：一个缺失的右括号会让后面十行都「 unexpected 」。常见抑制手段：

- 在同步点之后重置「已报告」状态，避免同一个缺失 token 反复报；
- 对同一条语句只报第一个错误；
- 设最大错误数（本章是 8），超过就停止并给出总结；
- 对插入的虚拟 token 做标记，后续诊断不再引用它。

抑制不是隐藏错误，而是把「一个根因」与「十个症状」分开。测试要断言诊断数量在一个范围，而不是精确等于某个数；否则恢复策略一改，测试全红。

### 2.6.5 诊断的稳定接口

错误码与主 span 应该稳定，消息文本不应该。一个可测试的诊断对象至少要有：

```json
{
  "code": "E2001",
  "severity": "error",
  "message": "期望 ';'，但遇到 'let'",
  "span": {"line": 1, "col": 11, "end_line": 1, "end_col": 14},
  "hint": "在此插入 ';'"
}
```

CI 断言 `code` 与 `span`，不要断言完整 `message`；文档链接到 `code`；工具用 `--error-format=json` 消费结构化字段。这样改文案不会破坏测试，改语义必须换错误码。

本节留下一个问题：怎样证明这些 lexer/parser 在大量输入下不崩溃、不静默改语义？下一节给出四层测试。

### 2.6.6 修复建议的生成

修复建议不是猜谜。对最常见的三类错误，可以机械地生成候选：

| 错误 | 候选修复 | 置信度 | 风险 |
|:--|:--|:--|:--|
| 缺少分隔符 | 在当前位置插入 `;`/`)`/`}` | 高 | 插入位置可能差一个 token |
| 多余 token | 删除该 token | 中 | 可能是前面缺了 token |
| 拼写错误的关键字 | 替换为编辑距离最近的关键字 | 中 | 标识符可能本就该这样写 |
| 缺少操作数 | 插入占位表达式，或删除前面的运算符 | 低 | 可能掩盖真正的问题 |

生成候选后要用「修复后能否继续解析」过滤：插入一个分号后，parser 能前进至少一个 token，才算有效修复。不要给用户一个「修复后仍然报同样错误」的建议。

### 2.6.7 诊断位置的选择

同一个错误可以有多个合理位置：缺分号可以指向行尾、下一行的开头、或前一个 token 的末尾。选择原则是**让用户最容易改**：

- 缺分隔符：指向「意外 token」的起点，help 说「在此插入」；
- 多余 token：指向该 token 的完整 span；
- 缺少操作数：指向运算符或分号，而不是文件末尾；
- 未闭合结构：指向开头，span 延伸到 EOF。

位置选择是产品决策，不是编译器内部细节。测试要断言 span，而不是只断言消息。

## 2.7 测试：token/AST 快照、属性与模糊入口 {#sec-compilers.1.2.7}

前端测试有一个特殊困难：输出是结构化的，手写断言很快变得又长又脆。解决办法是分层：最小对、快照、属性、模糊。每层抓不同的错误，成本也不同。

| 层 | 输入 | 断言 | 抓什么 | 成本 |
|:--|:--|:--|:--|:--|
| 最小对 | 两三个字符 | token 序列/诊断 | 边界、分支顺序 | 低 |
| 快照 | 一个程序 | 完整 token/AST 文本 | 结构回归 | 中 |
| 属性 | 随机/生成 | span 回查、无异常、前后缀 | 位置、恢复、健壮性 | 中 |
| 模糊 | 随机字节 | 不崩溃、有界时间/错误 | 崩溃、死循环 | 高 |

### 2.7.1 最小对

最小对（minimal pair）是只差一个字符、但应产生不同结果的两个输入。词法边界尤其适合：

| 输入 A | 输入 B | 差异 | 断言 |
|:--|:--|:--|:--|
| `a - -b` | `a--b` | 空格 | 前者 MINUS MINUS，后者 DECR |
| `1..2` | `1.5` | 第二个点/数字 | 前者 INT DOTDOT INT，后者 FLOAT |
| `if` | `ifx` | 后缀 | 前者 IF，后者 IDENT |
| `// c` | `/ / c` | 空格 | 前者注释，后者两个 SLASH |

最小对的价值在于**定位**：失败时你立刻知道是哪个分支顺序或哪个前瞻条件错了。随机测试能发现「有问题」，最小对能告诉你「问题在哪」。

### 2.7.2 快照

快照测试把完整 token 流或 AST 文本存成基线，改动后 diff。要点：

- 快照里不要包含时间、随机 ID、绝对路径；
- span 可以保留，但要固定换行与编码；
- 更新快照要经过 review，不能「一键接受」；
- 一个快照只覆盖一个关注点，不要把十个 case 塞进一个文件。

AST 快照尤其适合捕捉 dangling else、结合性、优先级这类「结构变了但程序还能跑」的错误。只测求值结果不够：`a - b - c` 与 `a - (b - c)` 在某些输入下可能碰巧相等。

### 2.7.3 属性：span 回查与不变量

本章实验的 `spans_ok` 检查每个 token 的文本是否出现在它声明的行列：

```python
def spans_ok(src: str, tokens: list[Token]) -> bool:
    lines = src.split("\n")
    for tok in tokens:
        if tok.kind == "EOF":
            continue
        if tok.span.line != tok.span.end_line:
            return False
        line = lines[tok.span.line - 1]
        if line[tok.span.col - 1:tok.span.end_col - 1] != tok.text:
            return False
    return True
```

这条性质不需要知道 lexer 的内部实现，能抓住半开/闭区间、列号起点、换行处理等一类错误。其他有用属性：

- token 的 span 单调不减（按出现顺序）；
- 相邻 token 不重叠；
- 拼接所有非注释 token 的文本，能覆盖源文本的非空白部分；
- parser 对任意输入都在有限步内返回（错误数上限）。

### 2.7.4 模糊入口

模糊测试不需要第三方库。一个最小入口是：生成随机字符串，喂给 lexer + parser，断言「不抛异常、错误数有界、时间有界」。本章实验的 `--fuzz` 用固定种子生成 0–60 字符的输入：

```bash
python3 experiments/ch02/lexer_lab.py --fuzz 400
```

```text
fuzz: seed=20240602 inputs=400 exceptions=0 with_diagnostics=361 max_tokens=45
```

`exceptions=0` 说明 400 个随机输入没有让 lexer/parser 崩溃；`with_diagnostics=361` 说明大多数输入被诊断拒绝，而不是被静默接受。模糊测试只能证明「这些输入没崩溃」，不能证明「所有输入都正确」；它适合发现健壮性问题，不适合替代语义测试。

### 2.7.5 自检输出

```bash
python3 experiments/ch02/lexer_lab.py --selftest
```

```text
selftest: valid=8/8 invalid=8/8 spans=ok
```

8 个合法程序全部解析且 span 正确；8 个非法程序全部产生至少一条诊断且没有抛异常。这个规模很小，但覆盖了注释、数字、关键字、dangling else、三种恢复。真实项目要把这个列表扩成回归语料库：每修一个 bug，就把最小复现加进去。

本节留下最后一个问题：agent 生成的 lexer 最容易在哪两个边界出错？我们怎样用前面的工具定位？

### 2.7.6 差分测试

差分测试用两个独立实现跑同一批输入，比较 token、AST 或诊断。适用场景：从旧 parser 迁移到新 parser、手写 parser 对拍生成器、两个版本的语言前端。oracle 的独立性是关键：如果两边共享同一个 lexer，词法错误会被同时复制，差分失效。

| 对拍对象 | 比较 | 能发现 | 不能发现 |
|:--|:--|:--|:--|
| 旧/新 lexer | token kind+text+span | 边界回归 | 两边都错的规范误解 |
| 手写/参考 parser | AST 序列化 | 优先级/结合性 | 两边共享的错误文法 |
| 前端/解释器 | 诊断数量+求值 | 恢复策略差异 | 未覆盖的语法 |

差分测试的输出要可复现：固定输入语料、固定序列化、固定随机种子；差异要能缩小到最小输入，否则一个 500 行的文件 diff 没人看。

### 2.7.7 测试成本与维护

| 测试 | 写一次成本 | 每次改动成本 | 适合频率 |
|:--|--:|--:|:--|
| 最小对 | 低 | 低 | 每次提交 |
| 快照 | 中 | 中（要 review diff） | 每次结构改动 |
| 属性 | 中 | 低 | CI |
| 模糊 | 高（要 triage） | 低（自动） | 夜间/发布前 |
| 差分 | 高 | 中 | 迁移/大版本 |

测试不是越多越好。一个断言完整 AST 文本的快照，会在每次加字段时失败；一个只断言 span 的属性，能在重构中保持稳定。选择「断言什么」比「断言多少」更重要。

### 2.7.8 一个最小的回归语料库

回归语料库不需要框架，先要结构。建议按「输入 → 期望产物」组织，每个 case 只回答一个问题：

| 目录/文件 | 内容 | 断言 |
|:--|:--|:--|
| `lexer/pairs.txt` | 两列最小对，逗号分隔 | 两边 token 序列不同 |
| `lexer/spans.txt` | 源文本 + 期望 token 列表 | span 回查通过 |
| `parser/ast/*.txt` | 源文本 + 快照 | AST 文本一致 |
| `parser/errors/*.txt` | 源文本 + 错误码/span | 诊断数量与位置 |
| `fuzz/seeds/` | 合法程序种子 | 解析成功、无诊断 |

每修一个 bug，先把最小复现加进对应目录，再改代码。这样回归测试是「从失败中来」的，而不是凭空写的；它也能防止同一个边界被修好又改坏。

## 2.8 agent 错误：`--` 注释与 `1..2` 的最大匹配 {#sec-compilers.1.2.8}

这一节复盘两个可复现的错误。它们的共同点是：agent 从一个熟悉的语言「借」了一条规则，但没有检查目标语言的 token 边界。

### 2.8.1 案例一：把 `--` 当行注释

任务：实现一个类 C 表达式语言的 lexer。agent 见过 SQL/Lua 的 `--` 注释，于是写了：

```text
if c == "-" and self.peek(1) == "-":
    while self.i < len(self.src) and self.peek() != "\n":
        self.advance()
    continue
```

它把 `--` 到行尾全部丢弃。源文件 `let x = 10--3;` 的实测对比：

```text
== buggy lexer A: '--' treated as a line comment ==
source: let x = 10--3;
correct tokens: LET IDENT ASSIGN INT DECR INT SEMI EOF
buggy   tokens: LET IDENT ASSIGN INT EOF
buggy diagnostics=0 statements=1
buggy AST:
Program @1:1-2:1
  Let x @1:1-1:11
    value: IntLit 10 @1:9-1:11
symptom: '--3;' is gone, 'let x = 10' is accepted without an error
```

症状：没有诊断，AST 合法，`x` 的值从「DECR 表达式（本语言不支持，应报错）」变成 10。若这段代码后面还有依赖 `x` 的逻辑，错误会以「值不对」的形式出现在很远的地方。

根因：注释语法是从别的语言借的，目标语言的 `--` 是 DECR（或两个一元减号，取决于空格）。agent 没有把「注释前缀」与「运算符前缀」列成互斥的最小对，也没有用 token 回查验证「被丢弃的字符是否真的都是注释」。

如何发现：第一，token dump 里 `DECR` 消失了，`EOF` 提前出现；第二，span 回查会发现 `--3;` 没有对应 token；第三，用 `a - -b` 与 `a--b` 做最小对，前者应产生两个 MINUS，后者应产生 DECR 或诊断。

修复：注释只认 `//` 与 `/* */`；`--` 先作为 DECR 发射，由 parser 决定是否合法；在词法测试里为每个运算符/注释前缀写正反例；用「token 覆盖源文本」性质检查没有字符被静默吞掉。

### 2.8.2 案例二：`1..2` 被贪婪浮点吃掉

agent 用正则 `[0-9]+\.[0-9]*` 匹配数字，认为「点后零个数字」也应允许（像 C 的 `1.`）。对 `let r = 1..2;`：

```text
== buggy lexer B: greedy float regex [0-9]+\.[0-9]* ==
source: let r = 1..2;
correct tokens: LET(let) IDENT(r) ASSIGN(=) INT(1) DOTDOT(..) INT(2) SEMI(;) EOF()
buggy   tokens: LET(let) IDENT(r) ASSIGN(=) FLOAT(1.) FLOAT(.2) SEMI(;) EOF()
buggy diagnostics=0 statements=2
buggy AST:
Program @1:1-2:1
  Let r @1:1-1:11
    value: FloatLit 1.0 @1:9-1:11
  ExprStmt @1:11-1:13
    expr: FloatLit 0.2 @1:11-1:13
symptom: '1..2' becomes two adjacent literals; range is lost
```

症状：`1..2` 变成 `1.0` 与 `0.2` 两个字面量，parser 把它们解析成两条语句（第二条是表达式语句），没有诊断。范围表达式消失，程序仍然「合法」。

根因：最长匹配只规定了「尽量长」，没有规定「点属于数字的条件」。agent 把 `1.` 的规则（C 允许）与范围运算符 `..` 的规则混在一起，缺少一位前瞻；同时没有为 `..` 建独立 token，导致第二个点只能被数字模式吃掉。

如何发现：token dump 直接暴露 `FLOAT(1.) FLOAT(.2)`；若只看 AST，会看到两个语句而不是一个范围；用 `1..2`、`1.5`、`1.` 三个最小对，能立刻区分「点后必须有数字」与「点后可以没有数字」。

修复：数字模式在消费点前检查下一位是否为数字；`..` 在数字之前或之后都作为独立 token；为 `1.` 发出明确诊断（或按语言规范允许它，但必须与 `..` 的优先级写清楚）。修复后的 token 流是 `INT(1) DOTDOT INT(2)`。

### 2.8.3 两个案例的共同根因

| 维度 | 案例一 | 案例二 |
|:--|:--|:--|
| 借来的规则 | SQL/Lua 的 `--` 注释 | C 的 `1.` 浮点 |
| 缺失的检查 | 注释前缀与运算符前缀互斥 | 点号归属的前瞻 |
| 症状 | 静默丢 token | 静默换 token 类别 |
| 发现手段 | token dump + span 回查 | token dump + 最小对 |
| 修复 | 注释只认 `//`、`/*` | 点后必须是数字；`..` 独立 |
| 回归 | `a--b` vs `a - -b` | `1..2` vs `1.5` vs `1.` |

两个错误都不是「agent 不会写 if」，而是**没有把语言规范里的 token 边界写成可执行的测试**。修复也不只是改一行：要补最小对、span 回查、随机输入不崩溃，才能防止下一个边界再犯。

### 2.8.4 修复后的最小测试

修复要用测试锁定，而不是只改一行代码。下面三条测试分别锁定 `--`、`1..2` 与 `1.`：

```python
def test_dash_is_decr():
    toks = Lexer("a--b;").tokens
    assert [t.kind for t in toks] == ["IDENT", "DECR", "IDENT", "SEMI", "EOF"]


def test_range_is_not_float():
    toks = Lexer("1..2;").tokens
    assert [t.kind for t in toks] == ["INT", "DOTDOT", "INT", "SEMI", "EOF"]


def test_dot_needs_digit():
    lx = Lexer("1.;")
    assert [t.kind for t in lx.tokens] == ["INT", "SEMI", "EOF"]
    assert lx.diags and lx.diags[0].code == "E1003"
```

这三条都可以在本章实验的 `Lexer` 类上直接跑通（`Lexer` 是纯 Python，无外部依赖）。它们比「跑一遍 demo 看看」强，因为失败时能定位到具体 token；它们比「断言完整 AST」稳，因为不依赖节点字段顺序。

### 2.8.5 注释语法不是通用的

| 语言 | 行注释 | 块注释 | 备注 |
|:--|:--|:--|:--|
| C/C++/Rust/Java/JS | `//` | `/* */` | Rust 块注释可嵌套 |
| SQL | `--` | `/* */` | `--` 到行尾 |
| Lua | `--` | `--[[ ]]` | 长注释有层级 |
| Haskell | `--` | `{- -}` | 可嵌套 |
| Python | `#` | 无 | 三引号是字符串 |
| Shell | `#` | 无 | 除 shebang 外 |

一个 agent 如果只看过 SQL/Lua，就会把 `--` 当注释；如果只看过 C，就会认为 `1.` 合法。**语法规则必须从目标语言的规范来，不能从相似语言类推**。写 lexer 前先把这张表填一遍，能避免一半的边界错误。

### 2.8.6 为什么这类错误难以发现

- 症状不崩溃：token 少了/类别变了，AST 仍然合法；
- 诊断可能指向别处：`--3;` 被吞掉后，错误可能报在下一行；
- 测试只覆盖 happy path：`10 - 3` 用空格写，永远不会触发 `--`；
- 代码审查看逻辑：分支看起来「很合理」，但不符合语言规范。

对策不是「更仔细」，而是把边界变成测试：每个注释前缀、每个运算符前缀、每个数字形态都有一组最小对；每个 token 都做 span 回查；每个修复都加回归。这样错误会在 CI 里暴露，而不是在用户的值里暴露。

### 2.8.7 修复顺序

发现边界错误后，不要直接改 lexer 的一行。按这个顺序：

1. **写规范**：在语言文档里明确注释前缀、数字点号规则、运算符的最长匹配；
2. **写最小对**：为每个规则写正反例，先让它们失败；
3. **改 lexer**：按「注释 → 运算符 → 数字 → 标识符」的顺序检查分支，确保没有前缀被后一个分支抢走；
4. **跑 span 回查**：确认没有字符被静默吞掉，EOF 位置正确；
5. **跑差分/模糊**：确认修复没有破坏其他 token，恢复仍然前进。

这个顺序把「改代码」放在「写测试」之后，避免修好一个边界、弄坏另一个。它也解释了为什么 agent 容易犯错：它通常从第 3 步开始，跳过 1、2、4，于是修复只对当前例子成立。

## 2.10 本章陷阱（8–15 条） {#sec-compilers.1.2.10}

::: errata 本章陷阱
1. **把最长匹配当成唯一规则**：`1..2` 被吃成两个浮点，`a--b` 被当成注释。原因是没有规定「点/减号在什么条件下属于当前 token」。修复：为每个边界写最小对，明确前瞻条件与分支顺序。
2. **注释识别放在运算符之前却不做互斥**：`--` 既可能是 DECR 又可能是注释。原因是分支顺序没有写进规范。修复：先确定语言的注释前缀，再为每个运算符前缀写正反例；token dump 检查没有字符被静默吞掉。
3. **关键字用单独正则分支**：`ifx` 被切成 `if` + `x`。原因是关键字没有走「标识符匹配后查表」。修复：标识符模式统一匹配，再查关键字表；测试 `if`/`ifx`/`_if` 三个边界。
4. **span 用闭区间或 0 基列号**：诊断差一列，拼接 span 多一个字符。原因是没有统一约定。修复：半开区间 + 1 基行列，写 `source[start:end] == text` 的性质测试。
5. **lexer 出错后跳过整行**：把后续合法 token 也吞掉，parser 产生级联错误。原因是恢复粒度太粗。修复：默认只跳一个字符；未闭合注释才跳到 EOF，并让 span 覆盖影响范围。
6. **块注释允许嵌套但实现不计数**：`/* /* */` 提前结束，后续代码被当成代码。原因是照搬 C 的规则却忘了目标语言的选择。修复：在规范里写明是否嵌套；嵌套就维护深度，不嵌套就在文档里声明。
7. **数字溢出在 lexer 里静默截断**：`99999999999999999999` 变成一个错误的 int。原因是把「识别」与「求值」混在一起。修复：lexer 只产出文本/大整数，范围检查放在语义阶段并给 span。
8. **递归下降直接写左递归**：`expr ::= expr '+' term` 导致栈溢出。原因是文法没有改写。修复：改成循环或右递归；用深表达式测试栈深度。
9. **dangling else 靠「实现碰巧这样」**：换一个 parser 或重构后 else 绑定变了。原因是没有把「最近匹配」写成文法/测试。修复：断言 else 的父节点；或用 matched/unmatched 文法显式编码。
10. **错误恢复不保证前进**：parser 在同一个 token 上循环，编译挂起。原因是错误分支没有消费 token。修复：每次恢复至少 `advance()` 一次；设最大错误数与超时测试。
11. **诊断断言完整文案**：改一个词测试全红，团队开始忽略测试。原因是把文案当接口。修复：断言 code/severity/span；文案做包含性检查。
12. **模糊测试只看「不崩溃」**：parser 静默接受非法输入也算通过。原因是 oracle 太弱。修复：同时断言诊断数量、AST 根节点、错误恢复后的 token 位置；对合法语料断言无诊断。
13. **把 lexer 的「跳过非法字符」当成恢复**：跳过一个字符但不报错，parser 会得到缺 token 的流，报出无关错误。原因是把「不崩溃」当成「可诊断」。修复：每个跳过分支都发诊断，span 指向被跳过的字符，并测试后续 token 位置。
14. **用 AST 快照替代语义断言**：快照能证明结构没变，不能证明求值正确。原因是把「结构回归」当成「语义回归」。修复：快照 + 求值对拍 + 关键路径的差分；对优化/重写尤其要两者都测。
15. **忽略 EOF 的零宽 token**：parser 在文件末尾越界或死循环，诊断指向最后一行之后。原因是 lexer 没有补 EOF，或 parser 在 EOF 上回退。修复：总是补 EOF；EOF 上不 `pos -= 1`；用空输入与「以运算符结尾」的输入测试。
:::

**A4** 只写「unexpected token」把「实际遇到什么」与「本应出现什么」都丢了，用户不知道是缺分号、缺括号还是写错关键字。期望集合给出候选（例如 ; 或 }），让修复有方向；同步点决定恢复后从哪里继续，避免一个错误吞掉整个文件。两者一起，诊断才既可读又可恢复。
