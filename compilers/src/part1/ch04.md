第 3 章结束时，AST 上每个名字都有 BindingId，每个表达式都有类型。编译器仍然不能直接优化：AST 保留了语法嵌套，<code>a + b * c</code> 的求值顺序、临时值、控制流都藏在树形结构里；同一个值在不同路径上可能有不同定义，分析器要反复在树上走来走去。优化需要一种更小、更规整、控制流显式的表示。

本章讲中间表示（intermediate representation，IR），重点是三地址码（three-address code，TAC）、控制流图（control-flow graph，CFG）和静态单赋值形式（static single assignment，SSA）。SSA 的核心不是“每个变量只赋值一次”这句口号，而是“每个使用都能静态地指到唯一一个定义”。phi 是合流处的选择，不是运行时函数调用；支配边界决定 phi 应该插在哪里；验证器决定构造器有没有骗你。

先看一个会骗人的例子。一个 agent 为 <code>while</code> 生成了 SSA，给循环条件里的 <code>i</code> 用了循环前的定义，却没有在循环头插 phi。结构验证器可能照样通过，因为循环前的定义确实支配循环头；但程序第二次迭代仍然用第一次的 <code>i</code>，要么死循环，要么结果错误。这个案例在 4.8 展开，实验在：

```bash
cd compilers
bash experiments/ch04/run.sh
```

脚本构造含 if/while 的 CFG，打印支配树、支配边界、phi 位置和 SSA，运行验证器，并用一个缺少 sum phi 的变体演示“结构验证通过但结果为 0”。

## 4.1 为什么需要 IR：树、线性与图 {#sec-compilers.1.4.1}

AST 是语法导向的：它保留括号、语句嵌套、声明顺序，甚至注释。对类型检查和诊断，这很好；对优化，这很糟。优化关心的是“值从哪里来、到哪里去、哪些路径会到达这里”，而不是“源码第几行写了什么”。把 AST 直接当优化 IR，会遇到三个问题：嵌套表达式没有显式的临时值，控制流不显式，分析结果无法低成本地跨 pass 复用。

IR 是源码与目标代码之间的抽象机器。它定义一组指令、一组值和一组控制流规则；前端负责把源码翻译进来，后端负责翻译出去。好的 IR 让分析变得简单：活跃变量只需要看 use/def，常量传播只需要看定值，循环优化只需要看 CFG 的强连通分量。坏的 IR 让每个 pass 都重新解析语法，优化器变成一堆特例。

| 形态 | 代表 | 优点 | 缺点 | 适合 |
|:--|:--|:--|:--|:--|
| 树 IR | AST、表达式树 | 贴近源码，构造简单 | 控制流隐含，临时值不显式 | 前端、解释器、模板 |
| 线性 IR | 字节码、TAC、栈机 | 紧凑、易解释、易序列化 | 控制流用跳转表示，分析需重建 CFG | 解释器、JIT 前端 |
| 图 IR | CFG、SSA、sea-of-nodes | 分析与优化友好，显式 def-use | 构造/销毁成本高，调试不直观 | 优化器、代码生成 |

同一个表达式 <code>x = a * b + c * d</code> 在三种 IR 里的样子不同。树 IR 保留嵌套；TAC 把每个中间结果命名；图 IR 把值和操作变成节点，把依赖变成边。

```text
树：        = (x, + (* (a,b), * (c,d)))

TAC：       t0 = a * b
            t1 = c * d
            t2 = t0 + t1
            x  = t2

图：        a ─┐
              ├─ mul ─ t0 ─┐
            b ─┘            ├─ add ─ t2 ─ x
            c ─┐            │
              ├─ mul ─ t1 ─┘
            d ─┘
```

TAC 的临时量 <code>t0</code>、<code>t1</code> 不是源码变量，而是编译器内部的值。它们让“求值顺序”和“每个中间结果”显式化；优化器可以在不改变语义的前提下重排、删除、合并它们。图 IR 进一步把“谁依赖谁”变成边，调度和指令选择可以在图上做匹配。

::: def 定义 4.1.1 · 中间表示 {#def-compilers.1.4.1.1}
中间表示是编译器内部的一种程序表示，由值、指令、控制流和类型/布局信息组成。它不必与源码语法同构，也不必与目标机器指令同构；它的职责是让前端翻译容易、让分析与优化有稳定的接口、让后端能生成目标代码。一个编译器可以有多层 IR（例如 rustc 的 HIR/THIR/MIR/LLVM IR），每层只暴露下一层需要的抽象。
:::

为什么不在 AST 上做常量传播？可以，但每个 pass 都要处理“表达式嵌套、短路求值、语句边界、作用域”这些语法细节。把 AST 降成 TAC 后，常量传播只关心“这个临时量的定值是不是常量、所有 use 是否都能被替换”；控制流合并只关心“这个块的前驱是谁”。IR 把问题从“语法树重写”变成“图上的数据流方程”，这是第 5 章的基础。

::: ex 例 4.1.1 · 把短路表达式降成 CFG {#ex-compilers.1.4.1.1}
源码 <code>if (a &amp;&amp; b) x = 1; else x = 2;</code> 不能简单降成 <code>t = a &amp;&amp; b</code>，因为 <code>&amp;&amp;</code> 要求 <code>a</code> 为假时不再求值 <code>b</code>。TAC 用两个分支块表达：

```text
    if a goto Lcheck
    goto Lelse
Lcheck:
    if b goto Lthen
    goto Lelse
Lthen:
    x = 1
    goto Lend
Lelse:
    x = 2
    goto Lend
Lend:
```

这个例子说明：IR 的“指令”不仅是算术，还包括控制流；把布尔表达式降成单条指令会丢失短路语义。SSA 之后，<code>x</code> 在 <code>Lend</code> 需要一个 phi，因为两条路径给了不同的值。
:::

::: intuition IR 是给优化器看的“电路图”
源码是给人看的布线图，AST 是带注释的接线图，IR 是去掉外壳后的电路图：每个门有编号，连线显式，开关（分支）显式。优化器在电路图上做等价变换，比在注释和括号里找模式可靠得多。
:::

实际编译器往往同时保留多层 IR。前端需要源码位置和语法结构做诊断；中端需要 CFG/SSA 做优化；后端需要寄存器/指令约束做调度。层与层之间用稳定的接口隔开，任何一层都不应该偷看另一层的私有结构。Rust 的 MIR 负责借用检查和 drop  elaboration，LLVM IR 负责机器无关优化，机器 IR 负责寄存器分配，这是同一原则的不同实现。

```text
<pre class="layout">
源码 ──parse──▶ AST ──typecheck──▶ 带类型的 AST
                                      │
                                      ▼
                                 TAC / CFG
                                      │
                                      ▼
                                    SSA
                                      │
                          ┌───────────┴───────────┐
                          ▼                       ▼
                    优化 pass（第 5–6 章）      验证器（4.5）
                          │
                          ▼
                    机器 IR / 汇编（第 7–8 章）
</pre>
```

读图：每一层只向下游承诺某种不变量。AST 承诺“名字已解析、类型已标注”；CFG 承诺“基本块单入口单出口、边显式”；SSA 承诺“每个 use 指向唯一 def，def 支配 use”。验证器检查的是最后一层承诺，而不是源码语义；这就是为什么 SSA 验证通过仍可能算错（4.8）。

::: note 历史与命名
TAC 这个名字来自“每条指令最多三个地址（两个源、一个目的）”。实际 IR 常有更多操作数（调用、phi、聚合），但“把复杂表达式拆成简单指令”的思想不变。SSA 由 Cytron 等人在 1991 年的论文中系统化，核心算法是支配边界 + 重命名；LLVM、GCC、HotSpot 都实现了它或它的变体。
:::

### 4.1.1 IR 与源码位置

IR 不是调试信息的敌人。每条 IR 指令都应能带一个源码位置（文件、行、列，或指向位置表的索引），优化在移动/合并指令时更新它；否则崩溃栈、profiler 和调试器只能指到“某个临时量”。LLVM 用 <code>!dbg</code> 元数据把指令关联到 DILocation，机器 IR 再降成行号表；GIMPLE 用 location_t；MIR 用 <code>SourceInfo</code>。位置信息不参与大多数优化，但它是诊断和可观测性的基础设施。

| 信息 | 放在哪 | 优化后如何处理 |
|:--|:--|:--|
| 源码 span | 指令/语句的位置字段 | 移动时保留，合并时选主位置 |
| 变量名 | 调试元数据 | 优化可能删除变量；用 DWARF 描述位置 |
| 类型 | IR 类型或旁表 | 降低到机器类型后可能丢失 |
| 内联栈 | 调试元数据 | 内联时串联 caller/callee 位置 |

一个常见错误是“降级后就把 AST 丢了”。优化确实不需要 AST，但诊断、调试、profiling 和增量分析仍可能需要源码位置。折中做法是保留一个位置表，IR 指令只存索引；这样 IR 紧凑，位置信息可按需加载。第 1 章的可复现构建也依赖位置信息的确定性：同一份源码、同一组选项，行号表应该逐字节一致。

### 4.1.2 IR 的所有权与 pass 复用

IR 一旦构造出来，就面临“谁拥有、谁修改、谁失效”的问题。优化 pass 通常有两种风格：就地修改（in-place）和重建（rebuild）。就地修改快，但容易让缓存的 use-def 链、支配树、循环信息失效；重建安全，但分配和复制成本高。工程折中是给 IR 加“版本号/失效标记”：修改值的 pass 负责标记相关分析失效，下一次查询时按需重算。

| 策略 | 优点 | 缺点 | 适用 |
|:--|:--|:--|:--|
| 就地修改 | 快、少分配 | 分析缓存易失效 | 局部 peephole、指令替换 |
| 重建 IR | 不变量清晰 | 内存/复制成本 | 跨函数、大改写 |
| 版本号 + 懒重算 | 折中 | 需要严格标记 | 工业优化流水线 |

SSA 的 use-def 链是典型例子：删除一条指令要同时从所有 use 的 operand 列表里移除；插入 phi 要更新前驱边的参数。只改指令不动 use 列表，验证器可能暂时通过，但下一次优化会读到悬空 use。把“修改 IR”封装成 API，让它在改结构时同步维护 use-def，是比“每个 pass 自己记得”更可靠的做法。

## 4.2 TAC 设计与 CFG 构造 {#sec-compilers.1.4.2}
TAC 的指令集不需要很大，但每条指令的语义要精确。下面是一套够用的最小集合；本书后续的 IR 都按这个形状读写。

| 指令 | 形式 | 语义 | 备注 |
|:--|:--|:--|:--|
| 常量 | <code>t = 42</code> | 定义 t 为常量 | 立即数可内联 |
| 复制 | <code>t = x</code> | 把 x 的值给 t | 后续可合并 |
| 二元 | <code>t = x + y</code> | 算术/位运算 | 操作数可以是常量 |
| 比较 | <code>t = x &lt; y</code> | 产生布尔/0-1 | 分支使用 |
| 跳转 | <code>goto L</code> | 无条件转移 | 基本块终止符 |
| 条件跳转 | <code>if t goto L1 else L2</code> | 按 t 选择 | 两个后继 |
| 调用 | <code>t = call f(x, y)</code> | 调用函数 | 有副作用 |
| 返回 | <code>return t</code> | 函数返回 | 终止符 |
| phi | <code>t = phi(x1, x2)</code> | 按前驱选择 | 只在 SSA 合流处 |

构造 CFG 的第一步是找基本块（basic block）的 leader。规则只有三条：函数的第一条指令是 leader；任何跳转的目标是 leader；任何跳转/返回之后的下一条指令是 leader（如果存在）。从每个 leader 开始，直到下一个 leader 之前，构成一个基本块。块的最后一条指令必须是终止符：跳转、条件跳转或返回；否则 CFG 的边不完整。

::: def 定义 4.2.1 · 控制流图 {#def-compilers.1.4.2.1}
CFG 是一个有向图 $G=(V,E)$：节点 $V$ 是基本块，边 $(b_1,b_2) \in E$ 表示执行可以从 $b_1$ 的终止符到达 $b_2$ 的入口。每个块有唯一入口；入口块没有前驱或只有回边前驱；出口块以 return 结束。前驱/后继关系由终止符决定：<code>goto L</code> 有一条边，<code>if t goto L1 else L2</code> 有两条边，<code>return</code> 没有后继。
:::

把结构化语句降成 CFG 有固定模板。对 <code>if (c) S1 else S2</code>：

```text
    t = eval(c)
    if t goto Lthen else Lelse
Lthen:
    <S1>
    goto Lend
Lelse:
    <S2>
    goto Lend
Lend:
```

对 <code>while (c) S</code>：

```text
    goto Lcond
Lbody:
    <S>
    goto Lcond
Lcond:
    t = eval(c)
    if t goto Lbody else Lend
Lend:
```

这两个模板看起来简单，但边界很多：<code>break</code> 要跳到 <code>Lend</code>，<code>continue</code> 要跳到 <code>Lcond</code>，<code>return</code> 直接终止当前块；嵌套循环要维护一个“跳转目标栈”。短路布尔表达式不能先求值再合并，必须按 4.1 的例子拆成多个块。把这些规则写成递归函数，输入是语句，输出是“当前块 + 后续块”，比在一个大函数里手写标签更不容易错。

下面是一个真实实验输入：<code>i = 0; sum = 0; while (i &lt; 3) { if (i == 1) sum += 10; else sum += 1; i += 1; } return sum;</code> 的 CFG。实验脚本 <code>ssa_lab.py</code> 的输出如下（节选）：

```text
=== CFG (before SSA) ===
B0:
  i = 0
  sum = 0
  goto B1
  preds: -; succs: B1
B1:
  t0 = i < 3
  if t0 goto B2 else B6
  preds: B0, B5; succs: B2, B6
B2:
  t1 = i == 1
  if t1 goto B3 else B4
  preds: B1; succs: B3, B4
B3:
  sum = sum + 10
  goto B5
  preds: B2; succs: B5
B4:
  sum = sum + 1
  goto B5
  preds: B2; succs: B5
B5:
  i = i + 1
  goto B1
  preds: B3, B4; succs: B1
B6:
  return sum
  preds: B1; succs: -
```

同一个 CFG 画成图：

```text
<pre class="layout">
                 ┌──────────────┐
                 │ B0           │
                 │ i=0; sum=0   │
                 └──────┬───────┘
                        │
                        ▼
                 ┌──────────────┐
          ┌─────▶│ B1           │
          │      │ t0 = i &lt; 3   │
          │      │ if t0 ...    │
          │      └───┬──────┬───┘
          │          │true  │false
          │          ▼      ▼
          │   ┌──────────┐ ┌──────────┐
          │   │ B2       │ │ B6       │
          │   │ t1=i==1  │ │ return   │
          │   └──┬────┬──┘ └──────────┘
          │      │    │
          │      ▼    ▼
          │  ┌─────┐ ┌─────┐
          │  │ B3  │ │ B4  │
          │  │ +10 │ │ +1  │
          │  └──┬──┘ └──┬──┘
          │     └───┬───┘
          │         ▼
          │   ┌──────────┐
          └───┤ B5       │
              │ i=i+1    │
              └──────────┘
</pre>
```

读图：B1 是循环头，也是 if 的入口；B5 是 latch（回边来源），它有一条边回到 B1。B1 有两个前驱（B0 和 B5），所以任何在 B0 与 B5 都有定义的变量，都必须在 B1 合流；B5 有两个前驱（B3、B4），所以任何在两条分支都定义的变量，都必须在 B5 合流。这个“多前驱”观察就是支配边界和 phi 插入的入口。

::: ex 例 4.2.1 · 从源码到 CFG 的手算 {#ex-compilers.1.4.2.1}
对上面的程序，手工列出每个块的后继：

- B0：<code>goto B1</code>，后继 {B1}。
- B1：<code>if t0 goto B2 else B6</code>，后继 {B2, B6}。
- B2：<code>if t1 goto B3 else B4</code>，后继 {B3, B4}。
- B3：<code>goto B5</code>，后继 {B5}。
- B4：<code>goto B5</code>，后继 {B5}。
- B5：<code>goto B1</code>，后继 {B1}。
- B6：<code>return</code>，后继为空。

前驱是后继的逆：B1 的前驱 {B0, B5}，B5 的前驱 {B3, B4}，其余同理。注意 B1 的前驱包含 B5，这条边就是回边（back edge）；没有它，B1 只是一个普通分支入口，有了它，B1 成为循环头。
:::

CFG 有两个容易忽略的工程细节。其一是临界边（critical edge）：源块有多个后继、目标块有多个前驱的边。例如 B1→B2 不是临界边（B2 只有一个前驱），B2→B3 也不是；但如果一个块同时有多个后继、目标又有多前驱，后续插入 phi 消解代码时需要拆边。其二是不可规约 CFG（irreducible CFG）：由任意 <code>goto</code> 形成的多入口循环，不能只用结构化模板处理；SSA 构造仍可做，但循环分析需要额外处理。C/C++ 的 <code>goto</code> 和异常展开都可能产生不可规约流。

::: method 构造 CFG 的检查顺序
1. 每条指令是否属于且仅属于一个基本块？
2. 每个块的最后一条指令是否是终止符？中间是否混入了跳转？
3. 每个跳转目标是否存在？条件跳转是否有两个不同后继？
4. 入口块是否没有前驱（或只有回边）？出口块是否以 return 结束？
5. 是否有不可达块？不可达块可以删除，但删除前要确认没有诊断/调试信息引用。
6. 是否有临界边需要拆分？这一步可以推迟到 phi 消解，但要在 IR 里能查出来。
:::

TAC 和 CFG 的设计没有唯一答案。栈机 IR 更紧凑，但分析前要重建栈深度；sea-of-nodes 把依赖做成边，调度自由但构造复杂；LLVM IR 把类型、内存、异常都放进指令，表达力强但语法重。选择取决于你要做的优化和要支持的语言特性。第 4.7 节会对照 LLVM IR、GIMPLE 和 MIR，看看它们各自把哪些信息放进了 IR。


## 4.3 SSA 定义、phi 与支配边界 {#sec-compilers.1.4.3}

SSA 的形式定义只有两句话：每个变量在程序中只被定义一次；每个使用都能静态地指到唯一一个定义。第一句是语法约束，第二句是语义约束。只做第一句不够：如果循环头使用循环前的定义，程序仍然“每个变量只定义一次”，但第二次迭代会拿到旧值。phi 函数就是为合流处补上“按路径选择”的定义。

先看一个菱形：

```text
      B0: x0 = 1
          if c goto B1 else B2
B1: x1 = 2          B2: x2 = 3
          \        /
           \      /
            B3: x3 = phi(x1, x2)
                use x3
```

B3 有两个前驱 B1、B2；<code>x</code> 在两条路径上分别被定义为 x1、x2。若 B3 直接写 <code>use x1</code>，从 B2 来的路径就错了；写 <code>use x2</code>，从 B1 来的路径就错了。phi 用“参数按前驱顺序”表达选择：<code>x3 = phi(x1, x2)</code> 表示“从 B1 来取 x1，从 B2 来取 x2”。phi 的语义是并行的：所有 phi 在同一时刻根据前驱选择值，不能理解成按文本顺序赋值。

::: def 定义 4.3.1 · SSA 与 phi {#def-compilers.1.4.3.1}
SSA 程序满足：(1) 每个变量名在整个函数中只有一个定义点；(2) 对每个非 phi 使用，定义点支配使用点；(3) 对 phi 的第 i 个参数，定义点支配该 phi 所在块的第 i 个前驱（或就在该前驱中）。phi 指令 <code>x = phi(v1, ..., vk)</code> 位于有 k 个前驱的块开头，参数顺序与块的前驱列表一一对应；控制流从第 i 个前驱进入时，x 取 vi。
:::

“定义支配使用”是 SSA 的核心不变量。支配（dominance）的定义是：在所有从入口到节点 n 的路径上，节点 d 都出现，则 d 支配 n，记作 d dom n。d 严格支配 n 指 d dom n 且 d ≠ n。直接支配者（immediate dominator，idom）是离 n 最近的严格支配者；每个节点（除入口）有唯一 idom，所有 idom 边构成支配树。

支配边界（dominance frontier，DF）刻画“合流点”：DF(n) 包含所有这样的节点 y——n 支配 y 的某个前驱，但 n 不严格支配 y。直观上，n 的定义在某个分支上到达了 y 的入口，而 y 还有另一条不经过 n 的路径，所以需要在 y 合并。

::: def 定义 4.3.2 · 支配与支配边界 {#def-compilers.1.4.3.2}
$d$ 支配 $n$：从入口到 $n$ 的每条路径都经过 $d$。严格支配：$d$ 支配 $n$ 且 $d \ne n$。支配边界：$DF(n) = \{ y \mid \exists p \in pred(y),\ n\ 支配\ p\ 且\ n\ 不严格支配\ y \}$。若 $y$ 有多个前驱，且 $n$ 的定值能沿某条前驱到达 $y$，但 $n$ 不支配 $y$ 的全部路径，则 $y \in DF(n)$。
:::

以 4.2 的 CFG 为例，实验脚本算出的支配集和支配树是：

```text
=== dominators ===
dom[B0] = {B0}
dom[B1] = {B0, B1}
dom[B2] = {B0, B1, B2}
dom[B3] = {B0, B1, B2, B3}
dom[B4] = {B0, B1, B2, B4}
dom[B5] = {B0, B1, B2, B5}
dom[B6] = {B0, B1, B6}

dominator tree:
B0
└── B1
    ├── B2
    │   ├── B3
    │   ├── B4
    │   └── B5
    └── B6
```

读法：B1 支配 B2 和 B6，所以从 B1 出发的两条路都在 B1 之后；B2 支配 B3、B4、B5，因为从 B1 进入循环体必须先经过 B2；B5 不支配 B1（B1 在它之前），所以 B5 的定义要想到达 B1，必须经过合流/phi。支配树把“谁一定在谁之前”变成了树形祖先关系，后面重命名就沿这棵树做 DFS。

对应的支配边界是：

```text
=== dominance frontiers ===
DF[B0] = {}
DF[B1] = {B1}
DF[B2] = {B1}
DF[B3] = {B5}
DF[B4] = {B5}
DF[B5] = {B1}
DF[B6] = {}
```

这里有两个反直觉但正确的点。第一，DF[B1] 包含 B1 自己：B5 有一条回边到 B1，B1 支配 B5，但 B1 不严格支配自己，所以 B1 在 DF[B1] 中。第二，DF[B2] 包含 B1：B2 支配 B5，而 B5 是 B1 的前驱；B2 不支配 B1，所以 B1 在 DF[B2] 中。把 DF 想成“从 n 出发的定义可能到达的合流点”，不要想成“n 的后继”。

::: ex 例 4.3.1 · 手算一个菱形 {#ex-compilers.1.4.3.1}
CFG：B0 → B1、B0 → B2，B1 → B3，B2 → B3。入口 B0。

- dom(B0)={B0}，dom(B1)={B0,B1}，dom(B2)={B0,B2}，dom(B3)={B0,B3}。
- idom(B1)=B0，idom(B2)=B0，idom(B3)=B0。
- DF(B1)={B3}（B1 支配 B3 的前驱 B1，但不严格支配 B3）；DF(B2)={B3}；DF(B0)=∅。

若 <code>x</code> 在 B1、B2 都有定义，B3 需要 <code>x3 = phi(x1, x2)</code>。若 <code>x</code> 只在 B0 定义，B0 支配 B3，B3 不需要 phi；这正是“不是每个合流都插 phi，只有多个可达定义才需要”的例子。
:::

phi 的插入规则不是“每个多前驱块都插”，而是“对每个变量，沿着定义点的迭代支配边界插”。如果变量在某个块有定义，且该块支配一个多前驱块，那么该多前驱块可能需要 phi；具体是否插，取决于是否有另一条路径带来不同的定义。经典 Cytron 算法会为每个变量计算定义点的 DF，并在 DF 中的块插入 phi；若插入 phi 的块本身不在原定义点集合中，它也会成为新的“定义点”，继续沿 DF 传播。这个过程叫迭代 DF。

| 变量 | 定义块 | DF(定义块) | phi 位置 |
|:--|:--|:--|:--|
| i | B0, B5 | DF[B0]=∅，DF[B5]={B1} | B1 |
| sum | B0, B3, B4 | DF[B0]=∅，DF[B3]={B5}，DF[B4]={B5}，DF[B5]={B1} | B5、B1 |
| t0 | B1 | DF[B1]={B1} | 不需要（临时量单一定义且只在 B1 用） |
| t1 | B2 | DF[B2]={B1} | 不需要（只在 B2 用） |

表里 t0/t1 是表达式临时量，编译器在降级时已经保证每个临时量只定义一次，不需要再为它们插 phi；真正需要 SSA 重命名的是源码变量 i、sum。这个区分不是语义上的，而是实现上的优化：对临时量做 SSA 构造也可以，但会产生很多无用 phi，后面还要做 pruned SSA 或死代码删除。

::: thm 定理 4.3.1 · phi 参数与前驱的对应 {#thm-compilers.1.4.3.1}
若块 $b$ 有前驱序列 $(p_1, \dots, p_k)$，且 $b$ 开头有 <code>x = phi(v_1, \dots, v_k)</code>，则从 $p_i$ 进入 $b$ 时，$x$ 的值等于 $v_i$ 在边 $p_i \to b$ 上的值。phi 的所有参数在同一时刻读取，参数之间不能有先后依赖。
:::

::: proof 证明思路
对执行路径归纳。到达 $b$ 之前最后一次执行的块必是某个 $p_i$；phi 的语义规则直接取第 i 个参数。由于参数读取是并行的，即使 $v_i$ 是另一个 phi 的结果，也按进入 $b$ 时的值计算，不受同一块内 phi 文本顺序影响。若参数顺序与前驱顺序错位，取到的就是另一条路径的值，语义立即改变。
:::

::: errata phi 不是运行时函数
phi 不是一条机器指令，也没有“调用开销”。它只存在于 SSA IR 中，表示“在这个合流点，按来自哪个前驱选择值”。退出 SSA 时，phi 会被消解成前驱边上的复制；机器码里没有 phi。把 phi 当成“运行时 select”会在寄存器分配和代码生成时多出不必要的指令，也会误解它的并行语义。
:::

既然 phi 只在合流处有意义，下一步就是让构造算法自动找到所有该插的位置，而不是靠人肉看 CFG。4.4 给出经典算法：先算支配树和 DF，再插 phi，最后沿支配树重命名。

### 4.3.1 pruned SSA 与活跃变量

经典算法对每个变量在 DF 上插 phi，即使这个变量在合流点已经死了。对教学 IR 没问题，对真实程序会产生大量无用 phi：一个只在某个分支内使用的临时量，可能在多个合流点都拿到 phi，后面还要靠死代码删除清理。pruned SSA 用活跃变量（liveness）先剪枝：只有当变量在合流点 live-in 时才插 phi；半剪枝（semi-pruned）只对“有 use 的变量”插，不精确到每个块。

| 变体 | 插 phi 条件 | 优点 | 缺点 |
|:--|:--|:--|:--|
| 经典 SSA | 定义点的迭代 DF 闭包 | 实现简单，不依赖 liveness | 产生死 phi |
| 半剪枝 | 变量至少有一个 use | 去掉完全无用的 phi | 仍有局部死 phi |
| pruned | 变量在合流点 live-in | phi 数量少 | 需要先做 liveness（第 5 章） |

对 4.2 的程序，i 和 sum 都是循环携带的活跃变量，必须在 B1 插 phi；t0/t1 是块内临时量，经典算法也可能因为 DF 给它们插 phi，但 pruned 会直接跳过。工业编译器通常先做半剪枝或 pruned，再做 phi 消解；phi 不是越多越好，每个 phi 都是一次复制和一次寄存器分配约束。

### 4.3.2 不可达块与死 phi

不可达块（unreachable block）没有从入口出发的路径。它们可能来自 <code>return</code> 之后的代码、永假分支、或优化删除前驱后的残留。SSA 构造前应先做可达性分析：删除不可达块，或至少标记它们不参与支配/DF 计算。否则不可达块的前驱可能为空，phi 参数填不满；支配集也会因为“没有路径”而出现反直觉的结果。

死 phi 是另一种清理对象：phi 的结果没有任何 use，或者所有操作数都相同。死 phi 可以删除，但删除后可能让另一个 phi 变成死 phi，需要迭代清理。验证器不应把死 phi 当错误；它只检查结构。优化器可以在 SSA 上做死代码删除（DCE），把死 phi 和死指令一起清掉，减少后续复制。

## 4.4 SSA 构造：支配树、前线与重命名 {#sec-compilers.1.4.4}

SSA 构造可以拆成四步：算支配关系；算支配边界；在 DF 上迭代插 phi；沿支配树重命名。四步都不难，难在每个细节都要与 CFG 的前驱顺序、不可达块、临时量、重命名栈对齐。下面给出一套可实现的伪代码，并与实验脚本的输出对照。

第一步，算支配集。最朴素的方法是迭代数据流：

```text
dom[entry] = {entry}
for n != entry: dom[n] = ALL
repeat
    for n in reverse_postorder(CFG) except entry:
        new = {n} ∪ (∩_{p ∈ pred(n)} dom[p])
        if new != dom[n]: dom[n] = new; changed = true
until not changed
```

这个算法对任意 CFG 都收敛，因为 dom 集合只减不增，且格的高度有限。复杂度最坏是 O(n^2) 次集合操作，对教学和小函数足够；工业编译器会用 Cooper–Harvey–Kennedy 的半交算法或 Lengauer–Tarjan 的近线性算法。实验脚本用的是上面的朴素迭代，输出与工业实现一致，只是常数大。

第二步，从 dom 求 idom。对每个非入口节点 n，严格支配者集合是嵌套的；idom 是其中“最大”的那个，即支配集大小最大、包含其他所有严格支配者的节点。实验里用 <code>max(strict, key=lambda d: len(dom[d]))</code>，在集合嵌套的前提下正确；工业实现通常用半交或 DFS 编号，避免反复比较集合。

第三步，算 DF。除了按定义对每个 y 的所有前驱枚举，还可以沿支配树走：

```text
for each join node y (|pred(y)| >= 2):
    for each p in pred(y):
        runner = p
        while runner != idom[y]:
            DF[runner].add(y)
            runner = idom[runner]
```

这个走法从每个前驱出发，沿 idom 向上走到 y 的直接支配者为止，把 y 加到路径上每个节点的 DF。它比“枚举所有支配者”快，因为它只走必要的那条链。对回边 y=B1、p=B5，runner 依次是 B5、B2、B1，于是 B1 被加进 DF[B5]、DF[B2]、DF[B1]；这与 4.3 的输出一致。

第四步，插 phi。对每个需要 SSA 的变量 v：

```text
work = def_sites(v)
while work not empty:
    x = pop(work)
    for y in DF[x]:
        if y not in phi_blocks(v):
            insert phi(v) at start of y
            phi_blocks(v).add(y)
            if y not in def_sites(v):
                work.push(y)
```

关键在最后三行：插入 phi 后，y 也成了一个“定义点”；如果 y 原来不定义 v，就要把 y 放进 work，继续沿 DF 传播。没有这一步，循环头的 phi 可能插了，但由它引出的更外层合流会漏。实验脚本对 sum 的处理是：B3、B4 的 DF 都有 B5，先在 B5 插 phi；B5 不是 sum 的原定义点，入栈；DF[B5]={B1}，在 B1 插 phi；B1 不是原定义点，入栈；DF[B1]={B1}，已在 phi 集合，停止。

第五步，重命名。沿支配树 DFS，为每个变量维护一个定义栈：

```text
rename(block):
    pushed = []
    for phi in block.phis:
        new = fresh(phi.var)
        phi.dst = new
        push(phi.var, new)
        pushed.append(phi.var)
    for inst in block.instructions:
        replace each use u with top(u)
        if inst defines v:
            new = fresh(v)
            inst.dst = new
            push(v, new)
            pushed.append(v)
    for s in successors(block):
        for phi in s.phis:
            i = index of block in preds(s)
            phi.operands[i] = top(phi.var)
    for child in dom_children(block):
        rename(child)
    pop pushed in reverse
```

几个容易错的点。phi 的定义要先于块内指令入栈，因为块内第一条指令就可能使用 phi 结果。phi 的参数要在处理**前驱块的后继**时填写，而不是在访问 phi 所在块时填写；否则前驱还没重命名，拿不到正确的栈顶。支配树 DFS 的子树结束后要弹出本块压入的所有名字，恢复父块的状态；弹出顺序与压入相反，但每个变量独立，顺序不影响正确性，只影响调试输出。

实验脚本对 4.2 的程序生成的 SSA 是：

```text
=== SSA ===
B0:
  i0 = 0
  sum0 = 0
  goto B1
B1:
  i1 = phi(i0, i2)   ; i, preds: B0, B5
  sum1 = phi(sum0, sum4)   ; sum, preds: B0, B5
  t0 = i1 < 3
  if t0 goto B2 else B6
B2:
  t1 = i1 == 1
  if t1 goto B3 else B4
B3:
  sum2 = sum1 + 10
  goto B5
B4:
  sum3 = sum1 + 1
  goto B5
B5:
  sum4 = phi(sum2, sum3)   ; sum, preds: B3, B4
  i2 = i1 + 1
  goto B1
B6:
  return sum1
```

逐行读：B1 的 <code>i1</code> 从 B0 取 i0、从 B5 取 i2；<code>sum1</code> 从 B0 取 sum0、从 B5 取 sum4。B5 的 <code>sum4</code> 从 B3 取 sum2、从 B4 取 sum3。B6 在循环退出时用 sum1，而 sum1 的值来自最后一次 B5 的 sum4。所有 use 都能指到唯一 def，且 def 支配 use；这正是下一节验证器要检查的性质。

::: thm 定理 4.4.1 · 迭代 DF + 支配树重命名的正确性 {#thm-compilers.1.4.4.1}
对可规约或不可规约的 CFG，只要支配关系和 DF 计算正确，迭代 DF 会在每个需要的合流点插入 phi；沿支配树重命名后，每个变量满足 SSA 定义唯一、use 被定义支配、phi 参数与前驱对应。
:::

::: proof 证明思路
定义点的 DF 覆盖了所有“该定义能到达、但定义不支配”的合流点；迭代把 phi 自身产生的新定义继续传播，直到闭包，因此不会漏。重命名沿支配树进行，保证到达某块时栈顶就是支配该块的最近定义；phi 参数在前驱处理时填写，保证参数与边对应。形式化证明可对支配树深度和 CFG 路径长度归纳。
:::

::: errata 三个构造细节
1. **只对源码变量做 SSA**：临时量如果已经单一定义，可以跳过；但若临时量在多块赋值，仍要处理，否则验证器会报重复定义。
2. **phi 参数顺序按块编号排**：必须按 <code>preds(block)</code> 的实际顺序，块编号顺序不一定是前驱顺序；顺序错位是语义 bug，验证器应检查。
3. **不可达块不删就重命名**：不可达块可能没有前驱或前驱不可达，phi 参数填不满；先删不可达块，或在验证器里显式标记。
:::

到这里，SSA 的“构造”部分完成。接下来要回答一个更工程的问题：怎么知道构造器没有错？靠人眼看 SSA 不可靠，尤其是在循环和嵌套分支里；需要一个独立的验证器，把 SSA 的不变量逐条检查。


### 4.4.1 sealed blocks：不预计算 DF 的构造

Cytron 算法是“先建完整 CFG，再算支配树/DF，再插 phi”。另一条路是 Braun 等人的 sealed blocks：在构造 CFG 的同时增量地建 SSA；当一个块的所有前驱都已“封闭”（sealed），才处理它的 phi。对结构化语言，前端可以在生成块的同时知道前驱是否齐全，因此不需要全局 DF；对不可规约流，仍要退回到全局算法或拆分。

| 方法 | 何时插 phi | 是否需要全局 DF | 适合 |
|:--|:--|:--|:--|
| Cytron | CFG 完成后 | 是 | 通用、教学、批处理 |
| sealed blocks | 块的前驱封闭时 | 否（局部） | 结构化前端、增量构造 |
| 支配树 + 重命名 | CFG 完成后 | 是 | 需要最小 phi 的优化器 |

两种方法得到的结果不必逐字相同：phi 的位置和名字可能不同，但只要满足 SSA 不变量、语义等价，就是合法实现。比较实现时，不要用“phi 数量完全一样”当正确性标准；用验证器 + 解释器对拍。

## 4.5 SSA 性质与独立验证器 {#sec-compilers.1.4.5}

SSA 构造器是一个复杂的图算法，最可靠的测试不是“看输出像不像 SSA”，而是写一个独立验证器，把不变量逐条检查。验证器不依赖构造器的内部状态，只读最终的块、指令、phi 和前驱表；它应该能拒绝重复定义、未定义使用、use 不被支配、phi 参数数量不对、phi 参数来自错误的边、phi 出现在入口块等错误。

| 检查 | 规则 | 错误码 |
|:--|:--|:--|
| 定义唯一 | 每个名字（含 phi 目的）只出现一次定义 | E_DUP_DEF |
| 使用有定义 | 每个 use 都能在 def 表中找到 | E_UNDEF |
| 普通 use 被支配 | def 所在块支配 use 所在块；同块时 def 在 use 之前 | E_USE_NOT_DOM / E_USE_ORDER |
| phi 参数数量 | 参数个数等于前驱个数 | E_PHI_ARITY |
| phi 参数对应边 | 第 i 个参数的定义块支配第 i 个前驱 | E_PHI_EDGE |
| phi 位置 | 入口块不能有 phi | E_PHI_ENTRY |
| phi 自引用 | 参数不能直接等于自己的目的 | E_PHI_SELF |

实验脚本的验证器按这个表实现，输出如下：

```text
verify(correct SSA): OK (defs=10, uses=19, phis=3)

verify(duplicate definition): REJECT (defs=10, uses=19, phis=3)
  E_DUP_DEF: 'sum2' defined in B3 and B4
  E_UNDEF: 'sum3' used at phi sum4 edge B4->B5 has no definition

verify(phi arity mismatch): REJECT (defs=10, uses=18, phis=3)
  E_PHI_ARITY: sum1 has 1 operands, block B1 has 2 predecessors

verify(use not dominated): REJECT (defs=10, uses=19, phis=3)
  E_USE_NOT_DOM: 'i2' defined in B5 is used at B1:0 (t0 = i2 < 3) in B1, but B5 does not dominate B1

verify(phi operand from wrong edge): REJECT (defs=10, uses=19, phis=3)
  E_PHI_EDGE: 'sum2' defined in B3 does not dominate predecessor B5 of B1
```

注意验证器对“重复定义”的变体同时报了 E_UNDEF：把 B4 的 sum3 改成 sum2 后，B5 的 phi 仍引用 sum3，而 sum3 已经不存在。这是正常的连锁错误；验证器不需要只报一个根因，但输出应稳定、可定位。

实现上有三个细节。第一，定义表要区分 phi 定义和普通定义：phi 定义在块首，位置记为 -1；普通定义按指令下标记录。第二，同块 use 的顺序检查不能只看“def 块 == use 块”，还要比较下标；否则块内先用后定义会被漏掉。第三，phi 参数检查的不是“定义块支配 phi 所在块”，而是“定义块支配对应的前驱块”。因为参数值是在前驱边结束时取的，不是进入 phi 块之后才产生的。

::: def 定义 4.5.1 · SSA 验证器的契约 {#def-compilers.1.4.5.1}
验证器输入一个 CFG、前驱表、每个块的定义/使用信息，输出一组错误。它必须满足：若验证器返回空错误集，则程序满足 SSA 的结构不变量；若程序违反任一不变量，验证器至少报告一个错误。验证器不负责证明程序与源码语义等价；它只检查 IR 自身的结构性质。
:::

::: thm 定理 4.5.1 · 验证器的可靠性边界 {#thm-compilers.1.4.5.1}
上述检查能保证：每个值只有一个定义，每个 use 都能解析到定义，普通 use 被定义支配，phi 参数与前驱一一对应。它不能保证：IR 与源码语义一致、没有死代码、没有类型错误、没有 UB、循环一定终止。结构验证通过是“SSA 形状正确”的必要条件，不是“程序正确”的充分条件。
:::

::: proof 证明思路
逐条检查直接对应定义 4.3.1 的三个条件：定义唯一对应 (1)，支配检查对应 (2)，phi 参数与前驱对应 (3)。因此空错误集蕴含 SSA 结构不变量。反过来，语义等价需要另一层证明（翻译验证或差分测试），结构不变量不涉及指令含义，所以不能推出语义正确。4.8 的漏 phi 例子就是结构验证通过但语义错误的见证。
:::

::: ex 例 4.5.1 · 一个“看起来对”的错误 SSA {#ex-compilers.1.4.5.1}
把 B1 的 <code>t0 = i1 &lt; 3</code> 改成 <code>t0 = i2 &lt; 3</code>，其中 i2 在 B5 定义、B1 使用。这个 SSA 仍然每个变量只定义一次，但 i2 的定义块 B5 不支配 B1，验证器报 E_USE_NOT_DOM。若只看“每个变量赋值一次”，会误以为它合法；支配检查才是关键。
:::

::: errata 验证器的三个误用
1. **“验证器通过 = 程序正确”**：它只检查结构，不检查语义；漏 phi 可以结构合法但算错。
2. **“验证器报错 = 构造器一定错”**：输入的前驱表/块顺序如果有错，验证器也会报错；先验证 CFG 本身。
3. **“phi 参数检查支配 phi 块”**：应检查支配对应前驱；这两个条件在循环里差别很大。
:::

::: method 给 SSA 构造器加验证的顺序
1. 先验证 CFG：前驱/后继对称、终止符正确、无不可达块。
2. 再验证定义唯一和 use 有定义；这一步能抓大多数重命名 bug。
3. 加支配检查；没有支配树时先用 dom 集合，慢但正确。
4. 加 phi 参数数量与前驱顺序检查；最后加 phi edge 检查。
5. 用变异测试：故意破坏一处，确认验证器能报出对应错误码。
:::

### 4.5.1 用支配树区间做常数时间支配检查

验证器如果对每个 use 都做集合包含，复杂度是 O(uses × |dom|)，大函数上会很慢。支配树有一个标准技巧：对支配树做 DFS，记录每个节点的进入时间 <code>tin</code> 和离开时间 <code>tout</code>；d 支配 u 当且仅当 <code>tin[d] &lt;= tin[u]</code> 且 <code>tout[u] &lt;= tout[d]</code>。这样每次检查是 O(1)，预处理是 O(n)。

| 检查 | 区间条件 | 备注 |
|:--|:--|:--|
| d 支配 u | tin[d] ≤ tin[u] 且 tout[u] ≤ tout[d] | 包含 d=u |
| d 严格支配 u | 上式且 d ≠ u | 用于 DF 定义 |
| 同块顺序 | def 下标 &lt; use 下标 | 间隔只解决跨块 |
| phi 边 | d 支配 pred[i] | 不是支配 phi 块 |

实现时要注意：支配树区间只回答“块级”支配；块内指令顺序要单独比较下标。phi 参数检查的目标是前驱块，不是 phi 所在块；把这两个条件写反，会在循环头漏报 E_PHI_EDGE。

### 4.5.2 验证器的测试策略

验证器本身也要测试。最有效的是变异测试：拿一个正确的 SSA，故意注入一种错误，确认验证器报出对应错误码；再注入一个“结构合法但语义错”的变体（漏 phi），确认验证器不报错——这不是失败，而是契约边界，应该由解释器测试覆盖。

| 变异 | 期望结果 | 说明 |
|:--|:--|:--|
| 同一名字定义两次 | E_DUP_DEF | 定义唯一 |
| phi 少一个参数 | E_PHI_ARITY | 前驱数量 |
| phi 参数换成另一前驱的值 | E_PHI_EDGE | 边对应 |
| 用循环体定义的值做循环头 use | E_USE_NOT_DOM | 支配 |
| 删除循环头 phi，改用 preheader 定义 | OK（结构） | 语义错误，交给解释器 |

把变异测试和属性测试结合：随机生成小 CFG，随机做重命名，跑验证器；再用解释器对拍源程序。验证器保证形状，解释器保证语义，两者都不能省。

### 4.5.3 与真实验证器对照

LLVM 自带 IR 验证器，<code>opt -passes=verify</code> 会检查 SSA 支配、phi 类型/前驱、终止符等。自己写验证器时，可以拿 LLVM 的接受/拒绝行为做对照：把你认为是合法的 SSA 交给 <code>opt -passes=verify</code>，看它是否接受；再注入错误，看它报什么。不要直接复制 LLVM 的错误消息，理解它检查的条件即可。

| 检查 | 自己的验证器 | LLVM verifier |
|:--|:--|:--|
| 定义唯一 | E_DUP_DEF | 有 |
| use 支配 | E_USE_NOT_DOM | 有 |
| phi 前驱对应 | E_PHI_ARITY/E_PHI_EDGE | 有 |
| 类型匹配 | 可选 | 有（LLVM 是强类型 IR） |
| 语义等价 | 不检查 | 不检查 |

LLVM verifier 通过也不代表程序正确；它和 4.5 的验证器一样，只保证 IR 的结构/类型约束。语义正确仍要靠解释器、差分测试或翻译验证。

## 4.6 退出 SSA：phi 消解与并行复制 {#sec-compilers.1.4.6}

机器指令没有 phi。退出 SSA 时，必须把每个 phi 变成前驱边上的复制：若 <code>x = phi(v1, v2)</code> 位于 B，前驱是 B1、B2，则在 B1→B 的边上复制 <code>x = v1</code>，在 B2→B 的边上复制 <code>x = v2</code>。如果边是临界边，先拆边，插入一个新的空块，把复制放在新块里；否则复制可能被放到错误的位置，或者一个前驱的复制影响另一个前驱。

真正的难点是并行语义。一个块可能有多个 phi，它们在同一时刻取值；把多个 phi 直接按文本顺序展开成复制，可能覆盖后面还要用的旧值。两个经典现象：

```text
交换（swap）：a <- b, b <- a
顺序执行 a <- b; b <- a 得到 a=b, b=b，丢了旧的 a。
正确：t <- a; a <- b; b <- t

丢失复制（lost copy）：x <- y, y <- z, z <- x
顺序执行 x <- y; y <- z; z <- x 得到 z = 新 y，不是旧 x。
正确：t <- x; x <- y; y <- z; z <- t
```

“丢失复制”这个名字强调：某个目的在被读取之前就被覆盖，旧值丢了。它和交换本质上是同一个问题：一组复制必须同时完成。解决方法是把并行复制（parallel copy）排成一个顺序序列，必要时引入临时量。

一个简单且正确的调度算法：

```text
pending = 所有 (dst, src)
while pending 非空:
    if 存在 (d, s) 且 d 不是任何 pending 的 src:
        emit d <- s
        remove it
    else:
        pick (d, s)
        emit t <- d          # 保存旧的 d
        把所有 pending 中的 src == d 替换成 t
```

直观解释：如果某个目的 d 不再被其他复制当作源，说明它的旧值已经没人需要，可以安全覆盖；如果所有目的都还在被读，就说明存在环，先保存一个目的到临时量，打破环。对交换，算法会先保存 a，再把 b 的源改成临时量，最后完成；对丢失复制同理。

实验脚本对 B5→B1 的回边输出：

```text
=== parallel copies on the B5->B1 back edge ===
parallel: i1 <- i2, sum1 <- sum4
  i1 <- i2
  sum1 <- sum4
swap example: a <- b, b <- a
  tmp0 <- a
  a <- b
  b <- tmp0
lost-copy example: x <- y, y <- z, z <- x
  tmp0 <- x
  x <- y
  y <- z
  z <- tmp0
```

B5→B1 的两个复制没有冲突：i1 和 sum1 都不是 pending 的源，所以直接顺序执行即可。交换和丢失复制则需要临时量。注意临时量的名字只要唯一即可；寄存器分配阶段可以把它分配到物理寄存器或栈槽，甚至通过 coalescing 消除复制。

::: def 定义 4.6.1 · 并行复制 {#def-compilers.1.4.6.1}
并行复制是一组赋值 $d_i \leftarrow s_i$，所有右值在同一时刻读取，所有左值在同一时刻写入。它的顺序化是一个序列，使得执行完后每个 $d_i$ 的值等于并行语义下 $s_i$ 的旧值。若复制图中有环，必须引入至少一个临时量；无环时可按拓扑序直接展开。
:::

::: thm 定理 4.6.1 · 调度算法的正确性 {#thm-compilers.1.4.6.1}
上述“目的不在源集合中就先发射，否则保存目的到临时量并替换源”的算法终止，且得到的序列与并行复制语义等价。
:::

::: proof 证明思路
不变量：pending 中的复制所读取的源，要么是尚未被覆盖的旧值，要么是保存旧值的临时量。每次发射 (d,s) 时，d 不是任何 pending 的源，因此覆盖 d 不会破坏剩余复制读取的旧值；每次打破环时，t 保存了 d 的旧值，并把所有对 d 的读取改成 t，等价性保持。每次迭代减少 pending 或减少环上的边，算法终止。
:::

::: errata phi 消解的三个坑
1. **在 phi 所在块开头复制**：这会覆盖上一轮循环的值；复制应放在前驱边/拆出的边上。
2. **按 phi 文本顺序直接展开**：多个 phi 是并行的；交换和丢失复制会出错。
3. **忘记拆临界边**：把一个前驱的复制放到共享的后继块，另一个前驱也会执行它；先拆边再插复制。
:::

::: note LLVM 的实现
LLVM 在 <code>PHIElimination</code> 或机器 IR 的 <code>phi-node-elimination</code> 阶段消解 phi，并用并行复制的调度处理交换；寄存器分配器可能把复制合并掉。不同版本的 pass 名称和顺序会变，但“phi 只存在于 SSA、机器码只有复制”这条边界不变。
:::

### 4.6.1 临界边拆分与复制放置

临界边（critical edge）是“源块有多个后继、目标块有多个前驱”的边。若把某个 phi 的复制放在目标块开头，所有前驱都会执行它；若放在源块末尾，源块的其他后继也会执行它。两种位置都不对，除非把边拆开：在源和目标之间插入一个空块，源到空块、空块到目标各一条边，复制放在空块里。

```text
拆分前：B1 --(多后继)--> B2(多前驱)
拆分后：B1 --> Bnew --> B2
        Bnew 里只放 B1->B2 的 phi 复制
```

拆边会增加块和跳转，代码生成阶段可能再合并；但语义上必须这样做，否则复制会作用到错误的路径。LLVM 在 phi 消解前会 split critical edges；如果后端能证明某条边不是临界边，可以省掉拆分。

### 4.6.2 复制合并与寄存器分配

并行复制调度后得到的是一串机器复制。寄存器分配器可以通过 coalescing 把“复制到同一个寄存器”的复制删掉；如果源和目的冲突，就保留复制或插入交换。很多架构有交换指令（x86 的 <code>xchg</code>），但编译器不应依赖它：先保证并行复制语义，再让后端选择指令。

| 阶段 | 输入 | 输出 | 责任 |
|:--|:--|:--|:--|
| phi 消解 | SSA phi | 边上的并行复制 | 语义正确 |
| 复制调度 | 并行复制 | 顺序复制 + 临时量 | 打破环 |
| 寄存器分配 | 顺序复制 | 物理寄存器/栈槽 | 消除或保留复制 |
| 指令选择 | 机器复制 | mov/xchg/load-store | 目标相关 |

复制不是“多余指令”的同义词。它可能是唯一表达“值从一条路径流到另一条路径”的方式；只有在数据流证明两个值可以共享寄存器时，才能删除。

### 4.6.3 消解后的检查

phi 消解后，IR 里不应再有 phi；每条前驱边上的复制数量应等于该边对应的 phi 参数数量；复制调度引入的临时量必须有定义且只在本边使用。可以用一个“消解后验证器”检查：遍历所有边，确认每个 phi 都被替换；遍历所有复制，确认源/目的已定义；再用解释器跑同一组输入，和 SSA 解释器对拍。

这一步能抓住两类 bug：复制放错边（某个前驱多复制/少复制）、并行复制顺序错（交换后值不对）。它们都不会在 SSA 验证器里出现，因为 SSA 本身是合法的；错误发生在退出 SSA 的翻译步骤。

## 4.7 IR 设计权衡：LLVM IR、GCC GIMPLE、Rust MIR {#sec-compilers.1.4.7}

三种真实 IR 代表三种取舍。LLVM IR 是类型化 SSA，phi 显式，基本块显式，内存用 load/store；GIMPLE 是 GCC 的三地址元组，SSA 用 PHI 节点，语句更接近 C；MIR 是 Rust 的中层 IR，有 CFG 但不是 SSA，局部变量可以被多次赋值，显式处理 drop 和借用检查。把它们放在一起看，能理解“IR 的抽象层次”不是一条线，而是一组坐标。

先看 LLVM IR 的循环。源码：

```c
int f(int n, int k) {
    int s = 0;
    int i = 0;
    while (i < n) {
        s += (i * k) ^ s;
        i++;
    }
    return s;
}
```

用 clang 22.1.8、<code>-O1 -fno-vectorize -fno-slp-vectorize -S -emit-llvm</code> 生成（节选）：

```text
define i32 @f(i32 noundef %0, i32 noundef %1) local_unnamed_addr #0 {
  %3 = icmp sgt i32 %0, 0
  br i1 %3, label %4, label %12

4:                                                ; preds = %2, %4
  %5 = phi i32 [ %10, %4 ], [ 0, %2 ]
  %6 = phi i32 [ %9, %4 ], [ 0, %2 ]
  %7 = mul nsw i32 %5, %1
  %8 = xor i32 %7, %6
  %9 = add nsw i32 %8, %6
  %10 = add nuw nsw i32 %5, 1
  %11 = icmp eq i32 %10, %0
  br i1 %11, label %12, label %4, !llvm.loop !10

12:                                               ; preds = %4, %2
  %13 = phi i32 [ 0, %2 ], [ %9, %4 ]
  ret i32 %13
}
```

块 4 是循环头，两个 phi 分别合并 i（%5）和 s（%6）；参数 <code>[ %10, %4 ]</code> 表示从回边来取新 i，<code>[ 0, %2 ]</code> 表示从入口来取 0。<code>nsw</code>/<code>nuw</code> 是“无符号/有符号不溢出”的标记，属于 LLVM 的 UB 契约：优化器可以依赖它们做变换。块 12 的 phi 合并“循环没执行”和“循环退出”的 s。

再看 Rust MIR。源码是一个 <code>while</code> 循环的 <code>sum_to</code>，用 stable 的 <code>rustc --emit=mir</code> 输出（节选）：

```text
fn sum_to(_1: u32) -> u32 {
    let mut _0: u32;
    let mut _2: u32;
    let mut _4: bool;
    let mut _5: u32;
    let mut _8: (u32, bool);
    scope 1 {
        debug s => _2;
        let mut _3: u32;
        scope 2 {
            debug i => _3;
        }
    }

    bb0: {
        _2 = const 0_u32;
        _3 = const 0_u32;
        goto -> bb1;
    }

    bb1: {
        _5 = copy _3;
        _4 = Lt(move _5, copy _1);
        switchInt(move _4) -> [0: bb5, otherwise: bb2];
    }

    bb4: {
        _3 = move (_8.0: u32);
        goto -> bb1;
    }

    bb5: {
        _0 = copy _2;
        return;
    }
}
```

MIR 有基本块、显式 goto/switchInt、局部变量 <code>_1</code>、<code>_2</code>，但 <code>_3</code> 在循环里被反复赋值，所以它不是 SSA。MIR 还带 <code>scope</code>、<code>debug</code>、<code>StorageLive/Dead</code>、<code>drop</code> 等前端语义，适合借用检查和 drop  elaboration，不适合直接做机器无关优化。Rust 在 MIR 之后才把程序交给 LLVM，由 LLVM 构造 SSA。

GCC 的 GIMPLE 是另一种三地址 IR：语句是元组，SSA 用 <code>PHI</code> 节点，优化 pass 在 GIMPLE 上跑，后端再降到 RTL。本机 macOS 的 <code>gcc</code> 是 Apple clang 的别名，没有真正的 GCC，因此本节不伪造 GIMPLE dump；可验证的形态描述是：GIMPLE 的赋值形如 <code>_1 = a + b;</code>，条件跳转形如 <code>if (_1 != 0) goto &lt;L&gt;; else goto &lt;L&gt;;</code>，SSA 阶段插入 <code>PHI</code> 节点，<code>-fdump-tree-ssa</code> 可导出。需要精确输出时，在装有 GCC 14 的 Linux 上运行该命令，而不是凭记忆贴一段。

| 维度 | LLVM IR | GCC GIMPLE | Rust MIR |
|:--|:--|:--|:--|
| 层次 | 中端/后端之间 | 中端 | 前端之后、借用检查层 |
| 是否 SSA | 是（alloca 除外） | SSA 阶段是 | 否，局部可多次赋值 |
| 合流表示 | phi 指令 | PHI 节点 | 无 phi，变量直接赋值 |
| 类型 | 强类型、显式宽度 | 类型化树/元组 | Rust 类型 + 布局 |
| 内存 | load/store、GEP | 内存引用、调用 | 局部/投影、drop |
| 额外语义 | 元数据、异常、调试 | 语句/表达式、内建 | 借用、drop、StorageLive |
| 稳定性 | 文本格式版本化但会变 | dump 格式随版本变 | 明确标注“human consumers only” |

::: def 定义 4.7.1 · IR 的抽象层次 {#def-compilers.1.4.7.1}
IR 的抽象层次由三组选择决定：控制流是结构化还是图；值是否单赋值；语义信息（类型、内存、异常、drop）放在 IR 里还是放在旁表/前端。层次越高，前端信息越多、优化越难；层次越低，机器相关细节越多、可移植性越差。没有“最好的 IR”，只有“对某组 pass 和某类语言最合适的 IR”。
:::

::: ex 例 4.7.1 · 同一个循环，三种表示 {#ex-compilers.1.4.7.1}
LLVM IR 用两个 phi 表达 i/s 的循环携带依赖；MIR 用 <code>_3</code> 的重复赋值和 <code>goto bb1</code> 表达同一件事，借用检查器不需要 phi；GIMPLE 在 SSA 阶段用 PHI 节点，在非 SSA 阶段用普通赋值。三者的控制流图同构，差别在“值是否单赋值”和“额外语义是否在 IR 里”。读 IR 时先问这三个问题，比逐条指令猜更有效。
:::

::: errata MIR 与 SSA 的两个误解
1. **“MIR 是 SSA”**：不是。MIR 的局部变量可以被多次赋值；它在借用检查后才交给 LLVM 构造 SSA。
2. **“LLVM IR 一定是 SSA”**：<code>alloca</code> 出来的内存在 <code>mem2reg</code> 之前通过 load/store 访问，不是 SSA 值；<code>-O0</code> 的 LLVM IR 大量使用 alloca，正是这个原因。
:::

::: note 为什么编译器要这么多 IR
前端需要语法/作用域/类型；中端需要 CFG/SSA 做优化；后端需要寄存器/指令约束。把这些需求塞进一个 IR，会让每个 pass 都处理无关细节。多层 IR 的代价是翻译和保持一致，但收益是每层都能被独立验证和测试。第 13 章的项目会实现一条简化流水线，亲手体会这个取舍。
:::

下一节回到最常见的构造 bug：循环回边漏 phi。它特别危险，因为结构验证器可能通过，只有解释器/差分测试能抓住。


### 4.7.1 GIMPLE 的语句形态与验证方式

GIMPLE 把表达式拆成三地址元组，语句种类包括赋值、条件、跳转、调用、返回、PHI 等。SSA 阶段的 GIMPLE 用 PHI 节点合并值，和非 SSA 阶段的普通赋值不同。GCC 的 dump 选项（如 <code>-fdump-tree-ssa</code>、<code>-fdump-tree-gimple</code>）可以把某个 pass 后的 IR 打到文件；不同 GCC 版本的格式会变，读 dump 时先看版本和 pass 名。

本机没有真正的 GCC（<code>gcc</code> 是 Apple clang 的别名），所以本节不贴 GIMPLE 的“真实输出”。可验证的结论是结构性的：GIMPLE 是三地址、带类型、以语句为单位的 IR；SSA 阶段用 PHI；优化 pass 在 GIMPLE 上跑，后端再降 RTL。需要逐行对照时，在 Linux 上装 GCC 14 并运行 dump 命令；不要把记忆中的片段当成实测输出。

## 4.8 agent 错误：循环回边漏 phi 与最小实验 {#sec-compilers.1.4.8}

这一节复盘一个具体的 agent 失败。任务是“为含 if/while 的 TAC 写 SSA 构造器”。agent 实现了支配树和 DF，也给 if 的合流点插了 phi；测试一个简单菱形时通过。随后它跑循环用例，程序不崩，验证器也通过，但结果不对。

源码（4.2 的实验程序）：

```text
i = 0; sum = 0;
while (i < 3) {
    if (i == 1) sum += 10;
    else        sum += 1;
    i += 1;
}
return sum;
```

正确结果：i=0 加 1，i=1 加 10，i=2 加 1，sum=12。agent 生成的 SSA 是：

```text
B0:
  i0 = 0
  sum0 = 0
  goto B1
B1:
  i1 = phi(i0, i2)
  t0 = i1 < 3
  if t0 goto B2 else B6
B2:
  t1 = i1 == 1
  if t1 goto B3 else B4
B3:
  sum2 = sum0 + 10
  goto B5
B4:
  sum3 = sum0 + 1
  goto B5
B5:
  i2 = i1 + 1
  goto B1
B6:
  return sum0
```

表面上它“有 phi”：B1 有 i 的 phi，B5 是 if 的合流点。问题在 sum：B3、B4 都定义了 sum，但它们都从 sum0 取值，而不是从上一轮的 sum 取值；B1 没有 sum 的 phi，B6 返回 sum0。于是每次迭代都重新计算“0+10”或“0+1”，最后一次迭代的结果被丢弃，返回 0。

更隐蔽的是，这个 SSA 在结构上完全合法：

- 每个变量只定义一次（i0、sum0、i1、t0、t1、sum2、sum3、i2）。
- 每个 use 都被定义支配：sum0 在 B0 定义，支配 B3、B4、B6；i1 在 B1 定义，支配 B2、B5。
- i 的 phi 参数与前驱 B0/B5 对应：i0/i2。
- 没有入口 phi，没有自引用，没有 arity 错误。

所以验证器输出：

```text
=== missing loop phi: structural verifier cannot see the bug ===
verify(missing sum phi (structurally)): OK (defs=8, uses=15, phis=1)
interpret correct SSA:     12 (expected 12)
interpret missing-phi SSA: 0 (expected 12)
```

“验证通过但算错”不是验证器写得差，而是验证器的契约只覆盖结构不变量（4.5）。漏 phi 没有违反“定义唯一”或“use 被支配”，它违反的是“IR 与源码语义等价”，这需要另一层证据。

根因在 phi 插入的传播。sum 的原定义点是 B0、B3、B4。DF[B3]={B5}、DF[B4]={B5}，所以在 B5 插 sum 的 phi；B5 不在原定义点集合，应该入 worklist；DF[B5]={B1}，所以还要在 B1 插 sum 的 phi。agent 的实现只做了第一层：它在 B5 插了 phi，却没有把 B5 当作新的定义点继续传播，于是 B1 漏了。更糟的是，它把 B5 的 phi 删掉/未使用，B3、B4 仍然引用 sum0，导致“看起来有 SSA 结构，实际没有循环携带值”。

怎样更早发现？四个检查按成本排序：

1. **对每个循环头，列出所有在循环体内被赋值、且在循环头或循环外被使用的变量**；这些变量必须在循环头有 phi。这个检查不需要完整语义，只需要 CFG 的循环信息和 def/use。
2. **看 DF 闭包**：对每个变量，从定义点出发迭代 DF，打印所有 phi 位置；与“循环头集合”对比，缺失一目了然。
3. **跑解释器/差分测试**：用一个小 TAC 解释器执行 SSA，和源码解释器对拍；输入 n=3，正确 12，错误 0。第 10 章的差分测试会把这一招系统化。
4. **检查 use-def 链**：若循环体内所有 sum 的 use 都指向 sum0，而源码在循环体内对 sum 赋值，说明循环携带依赖没有被表达。

修复不是“在 B1 手写一个 phi”，而是把 phi 插入的 worklist 传播补全。标准算法在 4.4：插入 phi 后，若 y 不是原定义点，把 y 入栈，继续处理 DF[y]。对 sum，B5 入栈后会发现 DF[B5]={B1}，从而在 B1 插入 <code>sum1 = phi(sum0, sum4)</code>；B3、B4 改用 sum1，B5 插入 <code>sum4 = phi(sum2, sum3)</code>，B6 返回 sum1。修复后的 SSA 就是 4.4 实验输出，解释器得到 12。

| 观察 | 表层解释 | 根因 | 验证 |
|:--|:--|:--|:--|
| 验证器 OK 但结果错 | “SSA 没问题” | 漏循环头 phi，结构仍合法 | 解释器对拍；DF 闭包 |
| 循环只执行一次/死循环 | 条件变量没更新 | 循环头用了循环前定义 | 打印循环头 phi 集合 |
| 结果等于最后一次迭代 | 累加器被覆盖 | sum 的 use 都指向 sum0 | use-def 链 |
| 修了 B1 又错别的 | 只补一个 phi | worklist 未继续传播 | 用迭代 DF 重跑 |

::: ex 例 4.8.1 · 为什么“每个变量只赋值一次”不够 {#ex-compilers.1.4.8.1}
错误 SSA 中 sum0 只定义一次，sum2、sum3 也只定义一次；从“定义唯一”看完全合规。但 sum2 和 sum3 都没有支配 B6，B6 只能用 sum0，所以循环的累加结果永远传不到出口。SSA 的第二个条件“use 被定义支配”也只保证“有值可用”，不保证“这个值来自正确的迭代”。循环携带依赖必须由 phi 表达，验证器只能检查 phi 的形状，不能替你发现“这里应该有一个 phi”。
:::

::: errata 漏 phi 的三个错误直觉
1. **“phi 只插在 if 的合流点”**：循环头也是合流点（前驱是 preheader 和 latch）；DF 会把它算出来。
2. **“插入 phi 后就结束了”**：新 phi 是新的定义点，要沿 DF 继续传播；迭代到闭包。
3. **“验证器过了就不用测”**：结构验证不检查语义；至少加一个解释器/差分测试。
:::

::: method 定位漏 phi 的顺序
1. 打印每个循环头的块号、前驱、phi 列表。
2. 列出循环体内被赋值的变量，减去只在循环内临时使用的变量。
3. 对每个变量，从定义点迭代 DF，打印 phi 闭包；与循环头集合对比。
4. 用解释器跑小输入，和源码结果对拍；若不一致，检查循环头的 use 指向哪个 def。
5. 修 worklist 传播，重跑验证器 + 解释器 + 全量回归。
:::

这个案例的教训是：SSA 构造器的正确性有两层证据。结构层靠验证器，语义层靠解释器/差分测试/翻译验证。只做一层，就会得到“验证器通过但程序算错”的 IR；只做另一层，则可能在更大的程序上遇到难以定位的结构错误。第 5 章的数据流分析和第 10 章的差分测试，会分别补上这两层的工具。

### 4.8.1 修复后的关键行

补全 worklist 后，B1 和 B5 的 sum phi 应该是：

```text
B1:
  i1 = phi(i0, i2)
  sum1 = phi(sum0, sum4)
  ...
B3:
  sum2 = sum1 + 10
B4:
  sum3 = sum1 + 1
B5:
  sum4 = phi(sum2, sum3)
  i2 = i1 + 1
B6:
  return sum1
```

对照错误版本：B3/B4 从 sum0 改成 sum1，B6 从 sum0 改成 sum1，B5 多出 sum4。改完后解释器输出 12；再用 n=0、n=1、n=4 做边界测试，确认循环不执行/执行一次/多次都正确。只修一个用例不够，循环携带变量的 phi 要在所有回边上都成立。

### 4.8.2 循环携带变量的检查清单

定位漏 phi 时，可以按下面的清单逐项检查：

- 找出所有回边（latch → header），标记对应的循环头。
- 列出循环体内被赋值的变量；排除只在循环体内定义、循环外不用的临时量。
- 对每个变量，检查循环头是否有 phi，且 phi 的某个参数来自 latch。
- 检查循环头的 use 是否指向 phi 结果，而不是 preheader 的定义。
- 检查循环出口块使用的是否是 phi 结果（或从 phi 结果派生的值）。
- 用 n=0、n=1、n=3 等边界输入跑解释器，和源码对拍。

这份清单不依赖支配树实现，适合在 code review 或调试时快速定位。它也不能替代标准算法：手写检查容易漏掉嵌套循环/多个 latch；最终还是要让 phi 插入走迭代 DF 闭包。

## 4.10 本章陷阱（8–15 条） {#sec-compilers.1.4.10}

::: errata 本章陷阱
1. **现象**：SSA 验证通过但循环结果错。**原因**：循环头漏 phi，结构仍合法。**修复/验证**：检查循环头 phi 集合；解释器对拍（4.8）。
2. **现象**：phi 参数顺序错，程序在某些输入下取错值。**原因**：按块编号排序而不是按前驱表顺序。**修复/验证**：打印 preds 与 phi 参数；验证器检查 E_PHI_EDGE。
3. **现象**：phi 被当成运行时 select，生成多余指令。**原因**：误解 phi 的语义。**修复/验证**：退出 SSA 时消解为边复制；机器码里不应有 phi。
4. **现象**：在 phi 所在块开头做复制，循环第一轮值被覆盖。**原因**：复制位置错。**修复/验证**：复制放在前驱边或拆出的临界边上。
5. **现象**：多个 phi 直接顺序展开，交换/丢失复制出错。**原因**：忽略并行语义。**修复/验证**：用并行复制调度算法；测试交换用例。
6. **现象**：支配边界算成“后继集合”。**原因**：混淆 DF 与 CFG 边。**修复/验证**：用菱形和回边手算；对照实验输出。
7. **现象**：只对源码变量做 SSA，临时量重复定义。**原因**：临时量在多块被赋值但被忽略。**修复/验证**：统一 def 表；验证器抓 E_DUP_DEF。
8. **现象**：不可达块导致 phi 参数填不满。**原因**：没有删不可达块或标记。**修复/验证**：先做可达性分析；验证器报 E_UNDEF/E_PHI_ARITY。
9. **现象**：验证器只查“每个变量赋值一次”，漏掉支配错误。**原因**：检查项不全。**修复/验证**：补 E_USE_NOT_DOM 与 E_PHI_EDGE；用变异测试。
10. **现象**：把 LLVM 的 <code>alloca</code> 当成 SSA 值。**原因**：没经过 <code>mem2reg</code>。**修复/验证**：看 <code>-O0</code> 与 <code>-O1</code> 的 IR 差异；用 <code>opt -passes=mem2reg</code>。
11. **现象**：认为 MIR 是 SSA。**原因**：看到基本块就以为单赋值。**修复/验证**：找同一个 <code>_3</code> 的多次赋值；查 rustc 文档。
12. **现象**：临界边上的复制被两个前驱共享。**原因**：没有拆边。**修复/验证**：识别“多后继→多前驱”的边；拆出空块。
13. **现象**：CFG 有不可达块/悬空跳转，后续分析崩溃。**原因**：构造时没检查目标。**修复/验证**：建图后做可达性与目标存在性检查。
14. **现象**：把 SSA 当优化本身，认为构造完就更快。**原因**：混淆表示与优化。**修复/验证**：SSA 只是让分析和变换更容易；性能要看具体 pass。
:::

**Q1** 为什么循环头 B1 的支配边界包含 B1 自己？这是不是算法 bug？

::: sol 答案
不是。DF 的定义是：存在 y 的前驱 p，n 支配 p，且 n 不严格支配 y。取 n=B1、y=B1、p=B5：B1 支配 B5（进入循环体必经 B1），但 B1 不严格支配自己（严格支配要求不相等），所以 B1∈DF[B1]。这条性质让“在循环头插入的 phi”本身成为新的定义点，迭代 DF 时会在 B1 再看到自己；算法用“已在 phi 集合”去重，不会无限循环。
:::

**Q2** 一个 SSA 通过了 4.5 的验证器，是否说明它和源码语义一致？举一个反例。

::: sol 答案
不一致。验证器只检查结构不变量：定义唯一、use 被支配、phi 参数与前驱对应。4.8 的漏 sum phi 变体满足这些条件，但循环累加器每次都用 sum0，返回 0 而不是 12。要发现语义错误，需要解释器/差分测试/翻译验证；结构验证通过只是必要条件。
:::

**Q3** phi 消解时，为什么不能把 <code>x = phi(a, b)</code> 直接放在 phi 所在块的开头？

::: sol 答案
phi 的值由“从哪个前驱进入”决定。如果放在块开头，复制会在进入块之后执行，可能覆盖上一轮循环还要用的值；正确位置是前驱边的末尾（或拆出的临界边块）。此外多个 phi 必须并行处理，直接顺序展开会遇到交换/丢失复制，需要临时量调度。
:::
**Q4** 如果验证器对缺 phi 的 SSA 返回 OK，是否应该修改验证器让它报错？

::: sol 答案
不应该把它塞进结构验证器。缺 phi 的程序仍然满足 SSA 的结构定义（定义唯一、use 被支配），结构验证器报告 OK 是符合契约的。要抓这类错误，应该增加语义层的检查：循环头 phi 完整性、解释器对拍、差分测试或翻译验证。把语义检查硬塞进结构验证器，会让它依赖源码/语义信息，失去“独立、只读 IR”的优点。
:::
