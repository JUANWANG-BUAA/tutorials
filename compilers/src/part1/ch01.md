先看一条能跑的命令。本章实验把一个只有赋值与四则运算的程序，依次变成 token、AST（abstract syntax tree，抽象语法树）、栈机字节码，再由解释器执行：

```bash
python3 experiments/ch01/pipeline_tour.py
```

它打印 26 个 token、17 个 AST 节点、21 条字节码指令，最后三行是 `tree eval = 599`、`vm, no pass = 599`、`vm, const_fold = 599`。三个 599 来自三种不同的表示：树遍历、未优化字节码、常量折叠后的字节码。这个等式不是巧合，而是编译器存在的理由；它也是本章所有讨论的基线。

上一章（导论）只说了这本书覆盖什么。这一章要回答一个更基本的问题：**从文本到进程，哪些东西被改写了，改写者要对什么负责**。如果不先建立这条链，后面的词法、类型、SSA、寄存器分配就只是孤立技巧；你会写出「能跑」但说不清哪一步该为错误负责的编译器。

本章的位置是第 1 篇的入口。1.1 给出流水线与每步的失败模式；1.2 把解释、AOT、JIT、transpiler 放进同一个成本框架；1.3 用真实命令走一遍流水线；1.4 讲 pass 管理器；1.5 讲正确性契约；1.6 讲可复现构建；1.7 讲预算；1.8 用一个 agent 生成的 codegen 错误把前面几条串起来。第 2 章进入第一站：词法与语法。

一个具体反例先放在这里。把 `a = 3 * (4 + 5) - 7 / 2;` 编译成字节码时，如果 codegen 先发射右操作数、解释器却按「栈顶是右操作数」弹出，那么减法与除法会静默算反：树遍历得 599，解释器得 -755。词法、语法、栈高度检查全部通过，只有语义错了。1.8 会完整复盘这个案例。

## 1.1 问题：从一行源码到退出码，谁改写了它 {#sec-compilers.1.1.1}

把下面四行存成 `expr.mc`：

```text
a = 3 * (4 + 5) - 7 / 2;
b = a * a - 1;
a + b;
```

实验脚本对它的处理不是「翻译成汇编」这一件事，而是七次表示变换：

| 阶段 | 输入 | 输出 | 谁生产 | 典型失败 | 怎么检查 |
|:--|:--|:--|:--|:--|:--|
| 字符流 | 文件字节 | 字符序列 | 操作系统/驱动 | 编码、BOM、CRLF | `xxd`、`file` |
| 词法 | 字符 | token + span | lexer | 注释/数字边界、非法字符 | token dump、span 回查 |
| 语法 | token | AST | parser | 缺分号、优先级、dangling else | AST 快照、括号化打印 |
| 语义 | AST | 带类型/绑定的 AST 或 HIR | resolver/typechecker | 未定义名、类型不匹配 | 符号表、诊断 |
| 中端 IR | AST/HIR | TAC/CFG/SSA | lowering | 控制流降级错、phi 漏插 | IR 打印、验证器 |
| 后端 | IR | 汇编/机器码 | instruction selection、regalloc | 操作数顺序、栈对齐 | 反汇编、ABI 测试 |
| 运行 | 可执行文件 | 进程、退出码 | loader + OS | 链接错、运行期崩溃 | 退出码、stdout、sanitizer |

这张表最重要的列不是「输出」，而是「典型失败」。每一列都对应一种**只在那个阶段才能便宜地发现**的错误。缺分号在词法阶段看不出来，在语法阶段一行诊断就能定位；操作数顺序错误在语法阶段完全合法，只有差分执行才会暴露。

<pre class="layout">
  源文件 expr.mc
      |
      |  bytes / encoding / BOM
      v
  [ lexer ] --(非法字符)--&gt; 诊断 + 恢复
      |
      |  token(kind, text, span)
      v
  [ parser ] --(期望集合为空)--&gt; 诊断 + 同步点
      |
      |  AST（节点 + span）
      v
  [ resolver / typechecker ] --(未定义名/类型冲突)--&gt; 诊断
      |
      |  带绑定与类型的树
      v
  [ lowering ] --(不可降级的构造)--&gt; 诊断
      |
      |  TAC / CFG / SSA
      v
  [ optimizer ] --(验证器拒绝)--&gt; 编译期失败
      |
      |  等价 IR
      v
  [ instruction selection + regalloc ] --(无可用寄存器/不支持的操作)
      |
      |  汇编文本或目标文件
      v
  [ assembler + linker ] --(未定义符号/重定位)--&gt; 链接错误
      |
      |  可执行文件
      v
  [ loader + OS ] --&gt; 进程 --&gt; 退出码 / stdout / 文件
</pre>

读图：从左到右，每一段箭头都是一次**表示变换**，也都是一次**契约检查点**。错误越靠右，能用来定位的源级信息越少；到了进程阶段，你只剩退出码、输出和 core dump。编译器工程的很大一部分工作，是把尽可能多的检查左移，同时不在左侧做它没有信息做的判断。

::: def 定义 1.1.1 · 编译（compilation）与翻译单元 {#def-compilers.1.1.1.1}
给定源语言 S、目标语言 T 与一个可观察行为契约 C，**编译**是一个把 S 的翻译单元映射为 T 的程序的变换，使得对每个在 C 下有定义的源程序 P，目标程序的可观察行为与 P 在 C 下的规定行为一致。**翻译单元**（translation unit）是一次交给编译器处理的源文本及其包含的声明集合；C 的翻译单元是预处理之后的 `.c` 文件，Rust 的 crate 则是一个编译单元但可分成多个 CGU。

这个定义有三个限定词，缺一不可：目标语言（可以是字节码、另一门源语言或机器码）、契约（哪些行为算「规定」）、有定义（未定义行为不在保证范围内）。「编译器保证程序正确」这句话没有意义，除非先说清契约。
:::

按这个定义，「编译」不必然产出机器码。把 Python 编译成 CPython 字节码是编译，把 TypeScript 编译成 JavaScript 也是编译；把 C 编译成 x86-64 机器码只是最常见的一种目标。反过来，把源文件逐行拼接、不建立任何中间表示的工具，也很难称为编译器。

### 1.1.1 为什么中间表示不是可选项

如果目标只是「把 `a + b` 变成一条加法指令」，确实可以写一个直接发射机器码的递归函数。问题是这个函数要同时承担四件事：识别语法、决定类型与求值顺序、选择指令、分配寄存器。任何一件改变，都会迫使你改同一个函数。

中间表示把这几件事拆开。以本章实验为例，AST 保留源级结构（括号、优先级、变量名），字节码只保留求值顺序（把树后序摊平成一维指令），两者之间由 `compile_program` 这一个函数连接。你可以替换后端而不动 parser，也可以替换 parser 而不动 VM。第 4 章会说明为什么真实的优化需要在 CFG/SSA 上做，而不是在 AST 上做；这里只要记住拆分带来的可测试性：每一段都能单独对拍。

拆分的代价是**表示之间的信息损失**。字节码里没有括号，只有指令顺序；一旦发射顺序错了，AST 的括号信息已经不在，错误只能靠执行结果发现。1.8 的 agent 案例正是这样：parser 正确、栈高度正确、语义错误。

### 1.1.2 三个常见误解

第一个误解是「编译 = 生成汇编」。生成汇编只是后端的一步；前端要拒绝非法程序，中端要保证变换等价，驱动要管理文件、临时文件、诊断与退出码。一个只会打印汇编的程序不是编译器，是一个语法翻译器。

第二个误解是「能跑就是正确」。本章实验的 buggy 模式也能跑完 21 条指令并返回一个整数，只是符号反了。正确性必须相对于一个 oracle：树遍历、参考解释器、另一套工具链，或者形式化规范。没有 oracle（判定基准）的「跑通了」只是没有崩溃。

第三个误解是「优化只影响性能」。在 C/C++ 里，优化可以利用「未定义行为不会发生」的假设，从而改变一个 UB 程序的行为；在 Rust 里，优化可以利用别名与生命周期的保证。1.5 会把这条边界写清楚：优化保持的是**契约内的可观察行为**，不是「你脑子里想的那个程序」。

### 1.1.3 驱动做什么

真实编译器不是一个函数，而是一个**驱动**（driver）：它解析命令行、展开响应文件、决定预处理/编译/汇编/链接哪些阶段、管理临时目录、并行编译多个翻译单元、汇总诊断、设置退出码。`cc` 是驱动，`clang` 也是驱动；`clang -cc1` 才是前端本身。1.3 会用 `clang -ccc-print-phases` 把驱动的阶段划分打印出来。

驱动最容易出的错不是算法，而是**状态**：临时文件没清理、并行输出交错、增量缓存键漏了 flag、失败后继续链接。这些问题不会出现在编译器教科书的语法里，却会决定一个构建系统是否可信。1.6 与 1.7 分别处理其中的确定性与预算问题。

本节留下一个问题：同一条流水线，为什么有时在运行前完成，有时在运行时完成？这就是下一节的四类执行模型。

### 1.1.4 错误成本随阶段右移

同一种错误在不同阶段被发现，修复成本差一个数量级。下面这张表不是精确统计，而是工程经验的排序；它解释为什么编译器要把检查尽量左移。

| 发现阶段 | 例子 | 定位信息 | 修复代价 |
|:--|:--|:--|:--|
| 词法 | 非法字符 `@` | 行列号 | 改一个字符 |
| 语法 | 缺分号 | 期望集合、附近 token | 改一行 |
| 语义 | 未定义变量 | 声明/使用位置 | 改一行或补声明 |
| IR 验证 | 栈下溢、SSA 重复定义 | 指令位置、前驱 | 改生成逻辑 |
| 汇编/链接 | 未定义符号、重定位错 | 符号名、段 | 改接口或构建 |
| 运行 | 操作数顺序反了 | 退出码、输出、core dump | 反推整条链 |

左移的极限是**信息不足**：词法阶段不知道变量是否定义，语法阶段不知道类型是否匹配。把不该它管的检查硬塞进去，会产生误报或更差的诊断。正确做法是让每个阶段只检查它能证明的东西，并把剩余信息传给下一段。

### 1.1.5 翻译单元与全程序

编译器的输入边界不总是「整个程序」。C 以翻译单元为单位分别编译，再由链接器合并；Rust 以 crate 为单位，但可以切成多个 codegen unit；JIT 可能一次只编译一个函数。边界决定了哪些优化能做：没有跨单元信息，内联只能发生在单元内；LTO 把边界推迟到链接期，换来跨单元优化，也换来更大的内存与更长的链接时间。

「全程序优化」不是免费的 correctness 升级。它需要看到所有可能被调用的函数，包括通过函数指针、动态加载、反射调用的那些；漏掉一个，去虚拟化或死代码删除就可能删错。第 6 章会讨论内联与可见性，第 7 章会讨论调用破坏；这里只要记住：**优化范围由可见性决定，不由口号决定**。

## 1.2 四类执行模型：解释、AOT、JIT、transpiler {#sec-compilers.1.1.2}

「解释器慢、编译器快」是一句不可操作的话。可操作的问题是两个：**翻译发生在什么时刻**，以及**翻译的产物被复用了多少次**。按这两个维度，可以把常见系统放进四类：解释器（interpreter）、AOT（ahead-of-time compilation，提前编译）、JIT（just-in-time compilation，即时编译）与 transpiler（源到源翻译器）。这四类之间是连续谱，不是四个抽屉。

| 模型 | 翻译时刻 | 产物 | 启动成本 | 稳态成本 | 诊断时机 | 典型系统 |
|:--|:--|:--|:--|:--|:--|:--|
| 解释器 | 运行时逐条 | 内部字节码或树 | 低（可只解析） | 每条指令一次解码+分派 | 解析期 + 运行到该路径时 | CPython、Ruby MRI、Wasm 解释器 |
| AOT | 运行前 | 目标文件/机器码 | 中（加载、重定位） | 接近硬件上限 | 编译期为主 | C/C++/Rust/Go 的常规构建 |
| JIT | 运行时，按热度 | 代码缓存中的机器码 | 低→升温 | 可接近 AOT | 编译期 + 运行时去优化 | HotSpot、V8、PyPy、LuaJIT |
| transpiler | 运行前 | 另一门源语言 | 取决于后端 | 取决于后端 | 转换期 | tsc、Babel、早期 cfront |

::: def 定义 1.2.1 · 执行模型的判定问题 {#def-compilers.1.1.2.1}
对一个具体系统，问三个问题而不是贴标签：

1. **翻译单元何时确定？** 运行前一次确定是 AOT；每次运行都可能重新确定是解释/JIT；输出仍是源文本是 transpiler。
2. **产物是否跨进程复用？** `.o`、`.pyc`、AOT 镜像会复用；JIT 的代码缓存可能复用也可能在进程退出时丢弃。
3. **失败发生在哪一侧？** 编译期拒绝、加载期拒绝、首次执行该路径时拒绝，是三件不同的事。

只有前两个问题都答完，「它是 JIT 吗」才有意义；第三个问题决定你怎么测试它。
:::

### 1.2.1 解释器：把解码成本摊到每次执行

解释器的核心是一个循环：取指令、解码、分派、修改状态、回到开头。本章实验的 `run_vm` 就是这个形状：`ip` 是程序计数器，`stack` 是操作数栈，`while True` 每轮执行一条 `Instr`。默认程序执行 21 条指令，树遍历访问 17 个 AST 节点；两个数字不能直接比较，因为「一条指令」和「一个节点」的工作量不同，但它们都说明：解释执行的成本与**动态执行的操作数**成正比。

解释器的优势不在峰值速度，而在**可移植性与启动延迟**。字节码是平台无关的，换 CPU 不用重新生成；解析后即可执行，不需要等待整个程序编译完。代价是每条指令都要一次间接分派，且优化只能作用在字节码层面（超级指令、内联缓存、专用化）。

一个常见混淆是「有字节码就是 JIT」。`.pyc` 只是把解析结果缓存到磁盘，执行时仍然逐条解释；没有运行时生成机器码，就不是 JIT。反过来，JIT 也不一定先有字节码：可以直接从 AST 或 IR 生成机器码。

### 1.2.2 AOT：把翻译成本前置

AOT 编译器在程序运行前完成词法、语法、语义、优化、代码生成、汇编与链接。运行时只剩加载器与库初始化。它的稳态成本最低，因为解码与分派都不存在；它的代价是构建时间、目标平台绑定，以及无法利用运行时的类型/值信息。

AOT 的「编译期」也不是一个点：C 的预处理、编译、汇编、链接是四个可分离的步骤，构建系统可以缓存其中间产物。`cc -c` 只做到目标文件，`cc` 还调用链接器。把「编译」当成一步，会让你在排查未定义符号时找错阶段。

AOT 的诊断能力最强：类型错误、未定义名、不可达代码、ABI 不匹配都能在运行前报告。但 AOT 不能保证程序不会在运行时失败：空指针、越界、除零仍然可能发生。诊断覆盖的是**静态可判定的**那一部分契约，不是全部。

### 1.2.3 JIT：把编译当成运行时服务

JIT 在程序运行期间生成机器码。典型结构是分层：第一层快速生成基线代码（或直接解释），同时收集类型与分支剖面；某段代码变热后，优化层生成更快的版本；如果假设被打破（类型变了、类被重定义），就**去优化**（deoptimization）回到解释器或基线版本。

JIT 的难点不是「生成代码」，而是**管理代码的身份**：同一段字节码可能有多个版本的机器码，每个版本附带一组守卫条件（guard）；栈上的值必须在优化代码与解释器之间可转换；代码缓存要可回收；已生成的代码要能被失效。第 12 章会把 JIT 的信任边界与 W^X 单独展开，这里只建立成本直觉。

JIT 的启动成本不是零：它仍然要解析、验证、生成基线代码。它相对 AOT 的优势是**可以利用运行时信息**做更激进的优化（例如把虚调用去虚拟化），劣势是编译时间计入用户等待，且必须为猜测失败准备退路。

::: ex 例 1.2.1 · JIT 的盈亏平衡点 {#ex-compilers.1.1.2.1}
假设某段循环每次执行 10^8 条字节码指令。解释器每条指令平均 8 ns，JIT 生成的代码每条 2 ns，但 JIT 编译这段代码要 40 ms。忽略预热与去优化：

- 解释执行：10^8 × 8 ns = 0.8 s
- JIT 执行：0.04 s + 10^8 × 2 ns = 0.24 s
- 盈亏平衡的执行条数 N 满足 40 ms = N × (8 − 2) ns，即 N ≈ 6.7 × 10^6 条

如果这段代码只执行 10^6 条，JIT 的 40 ms 编译成本收不回来，解释器更快。这个算式的价值不在具体数字，而在提醒你：**JIT 的收益取决于热度分布**，而热度分布取决于输入。基准测试里的热循环不代表真实负载。
:::

### 1.2.4 transpiler：目标仍是源语言

transpiler 把一门源语言转成另一门源语言，例如 TypeScript 到 JavaScript、现代 JavaScript 到旧版 JavaScript。它通常只做语法层面的降级（去掉类型标注、把 `async` 改写成状态机、把新语法改写成旧语法），不负责生成机器码。

因此 transpiler 的「正确性」是**源到源的语义保持**：输出程序在被后端执行时，行为要与输入程序在规定范围内一致。类型标注被擦除后，运行时的检查可能消失；这不是 bug，而是设计选择，但必须在契约里写清楚。tsc 的 `--target` 与 `--lib` 决定的正是这层契约。

transpiler 不能替代后端。输出仍要交给 JavaScript 引擎（解释/JIT）或另一门语言的编译器。把 transpiler 当成「编译器全家桶」会在讨论性能时失去对象：性能由最终执行引擎决定，不由转译器决定。

### 1.2.5 选型：先写约束，再选模型

| 约束 | 更合适的模型 | 原因 | 代价 |
|:--|:--|:--|:--|
| 冷启动 < 100 ms，脚本短 | 解释器/transpiler | 不需要等待编译 | 峰值性能低 |
| 长驻服务、吞吐优先 | AOT 或分层 JIT | 稳态成本低 | 构建/预热成本 |
| 需要运行时类型反馈 | JIT | 可利用实际类型 | 去优化与代码缓存复杂度 |
| 目标平台不可预知 | 解释器/字节码 | 产物平台无关 | 需要运行时 |
| 安全边界要求可审计 | AOT + 验证器 | 代码在运行前固定 | 动态性受限 |

这张表只能用来排除明显不合适的方案，不能替代测量。一个「启动必须 < 100 ms」的约束，可能被 20 ms 的 AOT 加载打破，也可能被 5 ms 的字节码解析满足；只有测量能决定。

本节留下两个问题：一条真实流水线到底长什么样？以及，流水线中的 pass 由谁按什么顺序执行？下一节先用命令把流水线跑一遍。


### 1.2.6 真实系统是混合的

把系统硬塞进四类会失真。HotSpot 同时有解释器、C1（快速编译）与 C2（优化编译）；V8 有 Ignition 解释器、Sparkplug 基线编译器与 TurboFan 优化编译器；LuaJIT 有解释器与 trace 编译器。它们不是「JIT」一个标签，而是**分层策略**：先用便宜的方式跑起来，再对热点投入编译预算。

| 系统 | 低层 | 中层 | 高层 | 升级依据 |
|:--|:--|:--|:--|:--|
| HotSpot | 解释器 | C1 | C2 | 调用计数/回边计数 |
| V8 | Ignition | Sparkplug | TurboFan | 反馈向量与热度 |
| LuaJIT | 解释器 | trace 记录 | trace 编译 | 热循环 |
| CPython | 字节码解释 | 无 | 无（3.13 起有实验性 JIT） | 不适用 |
| GCC/Clang | AOT | LTO | PGO/LTO | 构建选项 |

「CPython 3.13 起有实验性 JIT」是一条有条件的陈述：它取决于构建选项与版本，且默认未必启用。写进文档时要带版本与开关，不要写成「Python 是 JIT」。

混合模型给测试带来一个新问题：**你测的是哪一层？** 同一个函数在解释器、基线、优化层的语义必须一致，但性能与诊断可能不同。基准测试要报告预热次数、是否禁用 JIT、是否固定 tier；否则两个「Python 更快」的结论可能只是 tier 不同。

### 1.2.7 一条链上的多个翻译器

真实工具链常常串起多个翻译器：TypeScript → JavaScript（tsc/Babel）→ 打包器（esbuild/webpack）→ 压缩器（terser）→ 引擎（Ignition/TurboFan）。每一段都有自己的契约与 source map。把整条链称为「编译器」没有错，但定位问题时必须知道是哪一段改写了行为。

| 环节 | 输入 | 输出 | 典型错误 |
|:--|:--|:--|:--|
| 类型擦除 | TS | JS | 运行时假设类型仍在 |
| 语法降级 | 新 JS | 旧 JS | 语义差异（如 `this` 绑定） |
| 打包 | 多模块 | 单文件 | 副作用顺序、重复导入 |
| 压缩 | JS | 更小 JS | 依赖名字、错误的 pure 标注 |
| 引擎 | JS | 机器码 | 去优化、内联假设失败 |

判断一个环节是否「保语义」，要问它的契约覆盖了哪些观察者：类型擦除不保证运行时类型检查，压缩不保证函数名，打包可能改变模块求值顺序。把这些写进契约，测试才知道该断言什么。

### 1.2.8 选型的三个反例

反例一：一个每天只跑一次的批处理脚本，为了「性能」上 JIT，结果 40 ms 的编译成本占了大头。冷启动约束下，解释器或 AOT 更合适。

反例二：一个需要动态加载用户代码的插件系统，为了「简单」全用 AOT，结果每次加载都要调用编译器，启动延迟不可接受。解释器或预编译字节码更合适。

反例三：一个只做语法转换的工具，宣称「编译到原生」，实际输出仍是 JavaScript。用户以为绕过了引擎，性能却没有变化。transpiler 的产物仍要被执行引擎解释或 JIT。

这三个反例的共同点：**先问翻译发生在什么时候、产物被谁执行**，再谈性能。标签不能替代这两个问题。

### 1.3.1 从 AST 到字节码

后端的第一件事不是选寄存器，而是把树**线性化**。本章实验用后序遍历：先左子树，再右子树，最后发射运算符。对应的生成函数只有二十行：

```python
def compile_program(prog: Program, swap_operands: bool = False) -> list[Instr]:
    code: list[Instr] = []

    def gen(node) -> None:
        if isinstance(node, IntLit):
            code.append(Instr("CONST", node.value))
        elif isinstance(node, Var):
            code.append(Instr("LOAD", node.name))
        elif isinstance(node, Unary):
            gen(node.operand)
            code.append(Instr("NEG"))
        elif isinstance(node, Binary):
            if swap_operands:      # 错误版本：先右后左
                gen(node.right)
                gen(node.left)
            else:
                gen(node.left)
                gen(node.right)
            code.append(Instr(BINOP[node.op]))
        elif isinstance(node, Assign):
            gen(node.value)
            code.append(Instr("STORE", node.name))
        elif isinstance(node, ExprStmt):
            gen(node.expr)
            code.append(Instr("PRINT"))

    for stmt in prog.stmts:
        gen(stmt)
    code.append(Instr("HALT"))
    return code
```

这段代码验证的是「线性化规则」：二元运算的两个操作数按左、右顺序入栈，运算符在两者之后发射。它不验证语义；语义由 1.8 的差分测试负责。`swap_operands` 分支是故意留下的错误开关，用来演示顺序契约被破坏时会发生什么。

## 1.4 前端、中端、后端与 pass 管理器 {#sec-compilers.1.1.4}

编译器教科书常把结构画成三段：前端、中端、后端。这个划分是**责任划分**，不是进程划分；同一个进程里可以全都有，也可以拆成多个可执行文件。

| 层 | 输入 | 输出 | 主要责任 | 典型组件 |
|:--|:--|:--|:--|:--|
| 前端 | 源文本 | AST/HIR | 识别程序、报错、建立名字与类型 | lexer、parser、resolver、typechecker |
| 中端 | 前端产物 | 更低的 IR | 与目标无关的变换与分析 | CFG/SSA 构造、常量传播、DCE、内联 |
| 后端 | IR | 汇编/机器码 | 目标相关的选择与分配 | 指令选择、调度、寄存器分配、发射 |

这个划分有反例。GCC 的 GIMPLE 既是中端 IR，也承载一部分前端降级；rustc 的 MIR 在借用检查阶段就已经是「中端」，但它同时服务前端诊断；有些 DSL 编译器根本没有独立中端，AST 直接生成代码。判断一个组件属于哪层，看它**依赖什么信息**：只依赖源语言语义的是前端，只依赖 IR 语义的是中端，依赖寄存器/指令/ABI 的是后端。

### 1.4.1 pass 是什么

一个 **pass** 是对 IR 的一次遍历或一组遍历，读入一个 IR 并产出另一个 IR（可以原地修改），同时声明它保留/破坏了哪些分析结果。pass 的粒度可大可小：常量折叠一个表达式、内联一个调用、整程序死代码删除，都是 pass。

pass 不是「函数」这么简单，它至少带四个属性：

| 属性 | 含义 | 失败后果 |
|:--|:--|:--|
| 语义保持 | 对契约内程序，变换前后可观察行为一致 | 静默错误代码 |
| 终止性 | 在有限步内停止 | 编译挂起 |
| 分析保留 | 哪些缓存分析仍然有效 | 使用过期分析，错误优化 |
| 确定性 | 相同输入产生相同输出 | 不可复现构建 |

「语义保持」不是 pass 自己说了算。工程上的做法是：每个 pass 后跑验证器（IR 结构合法）、关键 pass 后跑差分测试（与未优化解释器对拍），发布前跑整套回归。验证器只能证明结构性质，不能证明语义；1.8 会给出一个验证器通过但语义错误的例子。

### 1.4.2 一个最小 pass 管理器

本章实验的 pass 管理器只有十几行，但包含了三个关键决策：按什么顺序跑、什么时候停、如何记录变化。

```python
def run_passes(prog: Program, passes, log: list):
    for name, fn in passes:
        rounds = 0
        while True:
            rounds += 1
            prog, changed = fn(prog)
            log.append((name, rounds, changed))
            if not changed:
                break
            if rounds >= 8:
                log.append((name, rounds, "budget-exhausted"))
                break
    return prog
```

它按固定顺序执行 pass；每个 pass 反复运行直到一轮没有变化（固定点）；最多 8 轮，防止实现错误导致无限循环。真实 pass 管理器还负责分析缓存、pass 依赖、并行、调试输出（`-print-after-all` 一类）与统计。

实验的常量折叠 pass 只做一件事：如果二元节点的两个子节点都是整数字面量，就把它替换成结果。运行日志是：

```text
== 4. pass manager: const_fold ==
 run const_fold#1: changed=True
 run const_fold#2: changed=False
 instructions: 21 -> 13
```

第一轮改变了 AST（`3 * (4 + 5) - 7 / 2` 折成 `24`，`4 + 5` 折成 `9`），第二轮没有新变化，达到固定点。折叠后的字节码仍然有 `LOAD a; LOAD a; MUL`：

```text
 0000 CONST    24
 0001 STORE    a
 0002 LOAD     a
 0003 LOAD     a
 0004 MUL
 0005 CONST    1
 0006 SUB
 0007 STORE    b
 ...
```

为什么 `b = a * a - 1` 不折成 `575`？因为这个 pass 是**语法局部**的：它不知道 `a` 在运行时一定是 24。要利用这个事实，需要跨语句的常量传播与到达定值分析（第 5 章），或者一个带环境的解释器。pass 的能力边界由它读取的信息决定，而不是由它的名字决定。

### 1.4.3 后端长什么样：从 IR 到机器码

本章实验只走到「字节码 + 解释器」。真实 AOT 编译器还要走指令选择、寄存器分配、汇编、链接。用 `clang` 的驱动把阶段打印出来：

```bash
clang -target x86_64-apple-darwin -ccc-print-phases -c add.c 2>&1
```

```text
            +- 0: input, "add.c", c
         +- 1: preprocessor, {0}, cpp-output
      +- 2: compiler, {1}, ir
   +- 3: backend, {2}, assembler
+- 4: assembler, {3}, object
5: bind-arch, "x86_64", {4}, object
```

这里的 `compiler` 阶段把预处理后的 C 变成 IR，`backend` 把 IR 变成汇编，`assembler` 把汇编变成目标文件，最后 `bind-arch` 把目标文件绑定到具体架构。注意第 2 阶段输出的是 `ir` 而不是直接汇编：LLVM 的中端与后端都在这条 IR 上工作。

对 `int add(int a, int b) { return a + b; }`，先看 LLVM IR：

```bash
clang -target x86_64-apple-darwin -O1 -S -emit-llvm add.c -o -
```

```text
define i32 @add(i32 noundef %0, i32 noundef %1) local_unnamed_addr #0 {
  %3 = add nsw i32 %1, %0
  ret i32 %3
}
```

IR 里只有一条 `add`，操作数顺序甚至被交换了（`%1, %0`），因为整数加法可交换，IR 不承诺源级顺序。到了汇编（省略帧指针的建立/销毁，只保留与指令选择直接相关的两行）：

```bash
clang -target x86_64-apple-darwin -O1 -S add.c -o -
```

```asm
_add:
	leal	(%rdi,%rsi), %eax
	retq
```

一条 IR 加法被模式匹配成一条 `leal`，两个参数寄存器直接相加。这里不展开寄存器与调用约定：那是第 8 章的内容，且寄存器表、栈对齐、ELF/重定位在《Linux 系统与内核》1.14–1.16 已有系统讲解。这里只取一个结论：**IR 到汇编不是逐句翻译，而是模式匹配 + 资源分配**。

```bash
clang -target x86_64-apple-darwin -O1 -S add.c -o add.s
clang -target x86_64-apple-darwin -c add.s -o add.o
llvm-objdump -d add.o
```

```text
0000000000000000 <_add>:
       4: 8d 04 37                     	leal	(%rdi,%rsi), %eax
       8: c3                           	retq
```

反汇编同样省略了帧指针指令。如果手写的汇编与编译器生成的汇编不一致，llvm-objdump 是裁判：它读的是目标文件里的字节，不是你的注释。第 7、8 章会反复用这条证据链。

### 1.4.4 pass 顺序与固定点

同样的 pass 集合，换一个顺序，结果可能不同：

- 先内联再常量传播：被调用者的常量进入调用者，传播能跨函数；
- 先常量传播再内联：调用边界阻断传播，内联后还要再跑一次传播；
- 先 DCE 再内联：被调用者还没被内联就被删了（如果它看起来不可达），机会丢失。

固定点也不是正确性的必要条件。只跑一轮常量折叠仍然保语义，只是少优化一些；固定点是为了让「反复应用直到稳定」的规则有一个明确的停止条件。对于单调且格高度有限的分析，固定点一定在有限步到达；对于任意重写系统，不保证终止，所以工程上必须有轮数上限或工作列表。

::: thm 定理 1.4.1 · pass 组合的语义保持 {#thm-compilers.1.1.4.1}
若 pass `P1, P2, ..., Pn` 各自对契约内程序保持可观察行为，且每个 pass 都在有限步内终止，则它们的任意有限组合 `Pn ∘ ... ∘ P1` 也保持可观察行为。

证明：对 n 归纳。n = 0 时是恒等变换。设 `Q = Pn-1 ∘ ... ∘ P1` 保语义，对任意契约内程序 `p`，`Q(p)` 与 `p` 可观察行为相同；`Pn` 对 `Q(p)` 也保语义，所以 `Pn(Q(p))` 与 `Q(p)` 相同；由传递性，与 `p` 相同。终止性由每个 pass 的终止性与有限组合推出。注意：这个定理不保证组合后的**诊断**不变，也不保证 UB 程序的行为；它只覆盖契约内的可观察行为。
:::

## 1.5 正确性契约：可观察行为、UB、诊断 {#sec-compilers.1.1.5}

「这个程序是对的」在编译器语境里必须补三个限定：对什么输入、在什么契约下、由谁观察。C 标准把可观察行为限制得很窄：对 volatile 对象的访问、写入文件的数据、交互设备的输入输出，以及这些操作的顺序。进程退出码、stderr 的具体字节、运行时间，都不在 C 的语言级可观察行为里；它们属于 POSIX/操作系统或项目自己的契约。

::: def 定义 1.5.1 · 可观察行为契约 {#def-compilers.1.1.5.1}
一个**可观察行为契约**是一个三元组 `(O, D, E)`：`O` 是观察者能看到的事件集合（例如 stdout 字节、退出码、文件内容），`D` 是这些事件在哪些执行下必须有定义，`E` 是等价规则（例如「stdout 字节相同即等价」）。编译器对程序 P 正确，当且仅当对每个 `P` 在 `D` 中的执行，编译后程序的 `O` 事件与 `P` 的规定行为在 `E` 下等价。

换一个 `O`，同一个编译器的正确性结论可能改变。把运行时间纳入 `O`，任何优化都不保正确性；把退出码排除，崩溃也可能「通过」。所以测试之前先写契约，而不是先写断言。
:::

### 1.5.1 四类行为

C 语言（以及大多数系统语言）把行为分成四类。它们的差别不是「编译器管不管」，而是「标准给不给保证」。

| 类别 | 含义 | 例子 | 编译器自由度 | 测试含义 |
|:--|:--|:--|:--|:--|
| 有定义（defined） | 标准规定了结果 | `1 + 2`、有符号且不溢出的加法 | 必须保持 | 可断言精确值 |
| 未指定（unspecified） | 标准给出一组允许结果 | 函数参数的求值顺序 | 任选一种，且不必文档化 | 不能断言某一种 |
| 实现定义（implementation-defined） | 实现必须选一种并文档化 | `char` 是否有符号、右移负数 | 任选但需文档 | 断言前查文档 |
| 未定义（undefined behavior，UB） | 标准不给任何保证 | 有符号溢出、空指针解引用、越界 | 可做任何事 | 不能用来测试「应该发生什么」 |

「未指定」与「未定义」经常被混为一谈。`f() + g()` 的求值顺序未指定，但程序仍然有定义，结果必须是某个合法顺序的结果；有符号溢出是未定义，编译器可以假设它不发生，从而把 `x + 1 > x` 折成真。

### 1.5.2 UB 如何改变代码生成

下面这个函数在数学上对几乎所有 `int` 都返回真，但在 C 里 `x + 1` 可能溢出：

```c
int always(int x) {
    return x + 1 > x;
}
```

在 x86-64 上用 `-O0` 编译，它老老实实做加法、比较、`setg`：

```asm
_always:
	pushq	%rbp
	movq	%rsp, %rbp
	movl	%edi, -4(%rbp)
	movl	-4(%rbp), %eax
	addl	$1, %eax
	cmpl	-4(%rbp), %eax
	setg	%al
	andb	$1, %al
	movzbl	%al, %eax
	popq	%rbp
	retq
```

用 `-O1` 编译，同一份源码变成（同样省略帧指针）：

```asm
_always:
	movl	$1, %eax
	retq
```

编译器并没有「算错」：它假设有符号加法不溢出（这是 C 的 UB 规则给它的许可），于是 `x + 1 > x` 恒真。对 `x = INT_MAX` 的输入，源程序的行为在标准下没有定义，所以编译器不受约束。这个例子说明：**UB 不是「结果不确定」，而是「没有结果可言」**。

同样的许可也解释了为什么优化后的程序可能崩溃、可能删掉安全检查、可能让「显然成立」的断言失败。第 9 章会系统处理 UB 分类与 sanitizer；这里只建立一条工程规则：任何依赖 UB 的测试都不是可靠 oracle。

### 1.5.3 诊断也是契约的一部分

C17 5.1.1.3 要求：如果一个预处理翻译单元包含语法规则或约束的违反，实现必须产生至少一条诊断。注意措辞是「至少一条」，不是「一条准确的」；标准不规定消息文本、不规定恢复方式、不规定是否继续编译。

| 诊断类别 | 标准是否要求 | 文本是否稳定 | 退出码是否非零 | 测试策略 |
|:--|:--|:--|:--|:--|
| 语法/约束违反 | 是（至少一条） | 否 | 通常非零 | 断言「有诊断」与位置，不断言全文 |
| 警告（如未使用变量） | 否 | 否 | 否（除非 `-Werror`） | 项目策略，不是语言契约 |
| 优化备注 | 否 | 否 | 否 | 不作为测试依据 |
| 内部编译器错误 | 不适用 | 否 | 是 | 视为 bug，收集复现 |

`-Werror` 把警告提升为构建失败，这是**项目策略**，不是语言要求。它有用，但不要把它写进「编译器必须拒绝这个程序」的论证里；换一个编译器或版本，警告可能消失。

诊断的另一个维度是**位置**。一条「expected ';'」如果指向文件结尾，而真正缺分号的位置在第 3 行，用户仍然要自己找。第 2 章会把「期望集合 + 同步点 + 修复建议」做成可测试的诊断结构；这里先记住：诊断的质量不是装饰，它决定了错误恢复能否继续。

### 1.5.4 用 sanitizer 观察 UB，而不是证明没有 UB

把 1.5.2 的溢出程序加上 UBSan 运行。源文件 ub.c：

```c
#include <limits.h>
#include <stdio.h>

int main(void) {
    int x = INT_MAX;
    x = x + 1;
    printf("%d\n", x);
    return 0;
}
```

命令：

```bash
cc -std=c17 -Wall -Wextra -Werror -fsanitize=undefined -fno-sanitize-recover=all ub.c -o ub
./ub
```

```text
ub.c:6:11: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
SUMMARY: UndefinedBehaviorSanitizer: undefined-behavior ub.c:6:11
Abort trap: 6
```

退出码是 134（`SIGABRT`），因为加了 `-fno-sanitize-recover=all`；不加它，UBSan 报告后继续执行，退出码可能仍是 0。这条证据只能说明「这次执行的这条路径被检测到了」，不能说明「程序没有 UB」。没被触发的分支、被优化掉的检查、sanitizer 未覆盖的类别，都不会出现在输出里。

### 1.5.5 契约分层

一个真实项目至少有三层契约，测试时要分别写：

| 层 | 规定者 | 例子 | 违反的后果 |
|:--|:--|:--|:--|
| 语言 | 标准 | 有符号溢出是 UB | 编译器可做任意变换 |
| ABI/平台 | 平台 ABI 文档 | 参数寄存器、栈对齐 | 链接后崩溃或数据错位 |
| 项目 | 你的文档/测试 | 退出码 0 表示成功、日志格式 | 用户脚本失败 |

「编译器正确」只覆盖第一层与一部分第二层；第三层要靠项目自己的测试。把三层混在一起，会出现「编译器通过但产品失败」或「测试失败但语言允许」的争论。写清楚是哪一层，争论会少一半。

本节留下两个工程问题：同样的源码，为什么两次构建的二进制不一样？编译一次要花多少时间、内存，增量构建凭什么可信？下一节先处理确定性。

### 1.5.6 一条诊断由什么组成

诊断不是一句字符串，而是一个结构化对象。最小的字段集是：严重级别、稳定错误码、主 span、消息；好一点再加次要标签、注释、修复建议。把这些字段分开，才能让测试断言「位置对不对」而不断言「文案一模一样」。

| 字段 | 作用 | 是否应稳定 |
|:--|:--|:--|
| severity | error/warning/note | 是 |
| code | 机器可读分类（如 E2001） | 是，文档化 |
| primary span | 出错位置 | 是，测试的核心 |
| message | 面向人的描述 | 否，可改 |
| labels | 相关位置（声明、使用） | 尽量稳定 |
| help | 修复建议 | 否，可改 |
| notes | 规则/标准引用 | 否 |

错误码稳定的价值在于：CI 可以断言「这个用例必须产生 E2001」，而不被文案改动打断；文档可以链接到错误码；用户可以用 `--error-format=json` 做工具集成。代价是错误码一旦发布就很难改语义，所以要在项目早期定好分层（词法 E1xxx、语法 E2xxx、类型 E3xxx……）。

### 1.5.7 继续还是停止

编译器发现第一个错误后通常不会立刻退出：它要继续解析，才能一次报告更多问题。但继续也有限度：错误恢复可能产生级联诊断，一个缺失的右括号会让后面十行都「 unexpected 」。工程上的做法是：

1. 设最大错误数（例如 20），超过就停止并报告「too many errors」；
2. 在同步点（分号、右括号、语句关键字）重新对齐；
3. 对由同一个缺失 token 引起的后续诊断做抑制；
4. 保证每次恢复至少消耗一个 token，防止死循环。

这些策略与第 2 章的 parser 直接相关。这里先建立一条契约：**退出码非零表示至少有一个 error**；warning 是否影响退出码由项目决定。不要把「打印了很多诊断」当成「诊断质量高」，也不要把「只报一个错」当成「恢复能力差」。

## 1.6 可复现构建：符号、调试信息与确定性 {#sec-compilers.1.1.6}

同一个源文件、同一台机器、同一个编译器，两次构建的产物一定一样吗？不一定。下面这些输入都会影响输出：编译器版本、完整命令行、环境变量、当前工作目录、源文件的绝对路径、时间、随机种子、并行调度、链接顺序。**可复现构建**（reproducible build）要求这些输入确定时，输出逐字节相同；它比「行为相同」强，也比「同一台机器上能重现」强。

| 输入 | 是否常被忽略 | 影响的产物 | 检测方法 |
|:--|:--|:--|:--|
| 源文件绝对路径 | 是 | 调试信息（DW_AT_name/comp_dir） | 两目录各构建一次，比较 |
| 构建时间/日期宏 | 是 | `__DATE__`、`__TIME__`、版本字符串 | 固定 `SOURCE_DATE_EPOCH` 后比较 |
| 环境变量 | 是 | 头文件搜索路径、宏定义 | `env -i` 下重建 |
| 并行度 | 是 | 符号表顺序、合并顺序 | `-j1` 与 `-j8` 对拍 |
| 哈希表迭代顺序 | 是 | 生成的 ID、寄存器分配 | 换 seed/语言版本 |
| 链接器 build-id | 否 | 可执行文件 | `llvm-readelf -n` |
| PGO 剖面 | 是 | 优化决策 | 固定剖面文件并记录哈希 |

### 1.6.1 一个可复现的实验

本章实验的 `--hash` 模式把 token、AST、字节码序列化成规范文本，再算 sha256。连续跑两次：

```bash
python3 experiments/ch01/pipeline_tour.py --hash
python3 experiments/ch01/pipeline_tour.py --hash
```

```text
sha256(ast+tokens+code)        = f1d31ad6122afb3b820088f5e44c85bfa358b4a35ddee065e528b159b2bc9e3a
sha256(folded_ast+tokens+code) = 994a14a9a312c17dced867cd5ead07348871afa7ac388cc256f1a9ad45b1c15e
instructions: 21 -> 13
```

第二次输出与第一次逐字符相同；`experiments/ch01/run.sh` 会把两次结果写入变量并比较，不同就以非零退出。这里的关键不是 sha256 本身，而是**规范化序列化**：字段顺序固定、不写时间戳、不写绝对路径、不依赖 `dict` 的迭代顺序。任何一条被破坏，哈希就会漂移。

反例：Python 的 `hash()` 默认带进程随机盐（`PYTHONHASHSEED`），同一个字符串在两个进程里可能得到不同整数。用 `hash()` 做缓存键或产物指纹，会把「进程重启」变成「缓存全部失效」。本章实验用 `hashlib.sha256`，并用排序后的字段构造文本，避免这个问题。

### 1.6.2 调试信息会把路径写进产物

准备两个内容相同的源文件，放在不同目录：

```bash
mkdir -p /tmp/rb/a /tmp/rb/b
cp add.c /tmp/rb/a/
cp add.c /tmp/rb/b/
clang -g -O0 -c /tmp/rb/a/add.c -o /tmp/rb/a/add.o
clang -g -O0 -c /tmp/rb/b/add.c -o /tmp/rb/b/add.o
shasum -a 256 /tmp/rb/a/add.o /tmp/rb/b/add.o
```

```text
a7043b6ea49a56c12ae94709397358ff2600206d60114251faaf0f72753752f8  /tmp/rb/a/add.o
d2eee230be7814f00ead7b1ff1d465a5e6dfc82b96b7ff491037ce8e6c2789e5  /tmp/rb/b/add.o
```

源码内容完全一样，哈希不同。用 `llvm-dwarfdump` 看调试信息：

```bash
llvm-dwarfdump --debug-info /tmp/rb/a/add.o | grep -m1 DW_AT_name
```

```text
DW_AT_name ("a/add.c")
```

编译命令里的路径（相对或绝对）被写进了 DWARF。这不是编译器「不干净」，而是调试器需要知道文件在哪。要在不同构建目录之间复现，必须把路径**规范化**：

- GCC/Clang：`-fdebug-prefix-map=OLD=NEW` 改写调试信息中的路径；`-ffile-prefix-map` 同时影响 `__FILE__`。
- 构建系统：在固定的容器路径下构建，或在比较前用 `llvm-dwarfdump` 之外的规范化工具处理。
- 时间宏：设置 `SOURCE_DATE_EPOCH`，并避免在版本字符串里写构建时间。

这些手段各有版本与平台差异；不要假设「加了 flag 就一定可复现」，要用两次构建 + `cmp` 验证。

### 1.6.3 符号与顺序

符号表顺序、局部符号名、mangling 规则也会影响字节比较。C++ 的 mangling 由 ABI 规定，但编译器可以在符号表里加入本地标签；GNU ld/lld 的 `--build-id` 会写入构建标识（macOS 对应 LC_UUID）；并行 LTO 的合并顺序可能改变函数布局。可复现构建通常要求：

1. 固定并行度，或让合并步骤对输入排序；
2. 固定随机种子（`-frandom-seed` 一类）；
3. 固定链接顺序与 build-id 策略；
4. 记录工具链与 flag 的完整哈希，而不是只记版本号。

第 7、8 章会讨论寄存器分配与指令选择；那里同样的输入可能因为哈希表遍历顺序产生不同的寄存器编号，最终机器码不同但语义相同。**语义可复现**不等于**字节可复现**，测试要分开写。

::: note 可复现性的三个等级 {#note-compilers.1.1.6.1}
- **字节可复现**：两次构建的产物逐字节相同。最强，适合供应链校验。
- **行为可复现**：产物不同，但同一测试集输出相同。适合大多数项目。
- **可重现**：同一环境下能重跑出相同结果（包含时间、路径）。最弱，不能用于跨机器校验。

先声明你要哪一级，再选工具。用「行为可复现」的测试去证明「字节可复现」，会漏掉调试信息与符号顺序的差异。
:::

本节留下一个问题：构建不仅要确定，还要在预算内完成。编译时间、内存、增量与并行，应该怎样度量与取舍？

### 1.6.4 把可复现性放进 CI

可复现性不是发布前的手工检查，而是一条可重复的流水线。最小版本只需要五步：

1. 在目录 A 构建一次，记录产物的 sha256；
2. 在目录 B（不同绝对路径、不同顺序）构建一次，记录 sha256；
3. 比较两份哈希；不同就打印第一个差异的偏移；
4. 对差异做归因：路径、时间、并行顺序、随机种子、链接器；
5. 把归因结果变成修复或明确的豁免，写进文档。

| 检测器 | 能发现 | 不能发现 |
|:--|:--|:--|
| `cmp` / sha256 | 任何字节差异 | 差异来自哪里 |
| `llvm-dwarfdump` | 调试信息中的路径/时间 | 代码布局差异 |
| `llvm-readelf -n` | build-id、note 段 | 编译器内部哈希顺序 |
| 两次 `-j1` 对拍 | 并行导致的顺序差异 | 单线程内的哈希顺序 |
| 固定 `SOURCE_DATE_EPOCH` 后对拍 | 时间宏 | 绝对路径 |

注意第 5 步：有些差异是**有意的**，例如 build-id、签名、嵌入的 commit 哈希。可复现构建的目标不是「消灭所有差异」，而是「每个差异都有解释，且不影响需要比较的层级」。如果只做行为可复现，调试信息差异可以豁免；如果做供应链校验，就不能豁免。

一个常见的失败是只比较可执行文件，不比较中间产物。链接器可能把差异掩盖（例如填充、对齐），让你以为目标文件也可复现。要比较哪一级，就在 CI 里固定那一级的产物，并对它做哈希。

还有一类差异来自**编译器的内部数据结构**：哈希表的遍历顺序、并行任务的完成顺序、临时文件名的随机后缀。它们不改变语义，却会改变寄存器编号、函数布局、符号顺序。修复方式不是「让哈希表有序」这一条，而是把所有影响输出的迭代都显式排序，或在最终发射前做一次规范化。只修一个来源，下一次换一个 pass 又会复现。

工具链本身也是输入。两个 clang 版本即使版本号相同，构建配置、默认目标 CPU、内联阈值也可能不同；容器镜像的更新会悄悄改变产物。可复现构建的记录里要包含编译器的完整版本串、目标三元组、以及构建系统自身的版本。只写「clang 17」不够，至少要写「Apple clang 17.0.0 (clang-1700.0.13.3)」这类可追溯的标识。

## 1.7 预算：编译时间、内存、增量与并行 {#sec-compilers.1.1.7}

编译预算不是一个数字，而是一组约束：全量构建的墙钟时间、单文件增量延迟、峰值内存、产物大小、以及这些指标在 CI 机器上的方差。把它们混成一个「编译太慢」的抱怨，无法定位。

先区分**可复现的工作计数**与**墙钟时间**。本章实验能稳定给出：26 个 token、17 个 AST 节点、21 条字节码、折叠后 13 条、300 个随机表达式（281 个有效对拍，19 个因除零跳过）。它们不随机器负载变化，适合做回归阈值。墙钟时间受 CPU、频率、缓存、后台进程影响，必须记录机器、编译器版本、优化级别、重复次数，并取中位数。

| 杠杆 | 主要影响 | 代价/风险 |
|:--|:--|:--|
| 优化级别 `-O2` → `-O3` | 运行时间可能下降 | 编译时间上升，代码膨胀 |
| LTO | 跨翻译单元优化 | 链接时间与内存大幅上升，并行度下降 |
| 调试信息 `-g` | 可调试性 | 产物变大，路径进入产物 |
| 增量/查询缓存 | 单文件延迟 | 缓存键漏项导致陈旧结果 |
| 并行 `-jN` | 全量墙钟 | 内存峰值上升，输出顺序不确定 |
| 预编译头/模块 | 解析时间 | 依赖管理复杂，缓存失效难查 |

### 1.7.1 增量缓存：键必须覆盖所有输入

实验的 `--cache` 模式模拟两个构建系统：一个用内容哈希做键，一个只用文件名做键。三个文件，第一轮全 miss，第二轮全 hit，然后修改 `b.mc`：

```bash
python3 experiments/ch01/pipeline_tour.py --cache
```

```text
== build #1 ==
 #1 a.mc: content-key=MISS name-key=MISS key=e0f2b4c5
 #1 b.mc: content-key=MISS name-key=MISS key=ec3c8e70
 #1 c.mc: content-key=MISS name-key=MISS key=e0eb3050
== build #2 (nothing changed) ==
 #2 a.mc: content-key=HIT  name-key=HIT  key=e0f2b4c5
 #2 b.mc: content-key=HIT  name-key=HIT  key=ec3c8e70
 #2 c.mc: content-key=HIT  name-key=HIT  key=e0eb3050
== build #3 (b.mc edited: 3 * 4 -> 3 * 5) ==
 #3 a.mc: content-key=HIT  name-key=HIT  key=e0f2b4c5
 #3 b.mc: content-key=MISS name-key=HIT  key=1375a28e
 #3 c.mc: content-key=HIT  name-key=HIT  key=e0eb3050
```

内容键在第三轮正确地让 `b.mc` 失效；文件名键仍然命中，复用旧产物。这就是增量构建最危险的错误：**构建成功、测试通过、产物是旧的**。它不会崩溃，只会让「我明明改了」变成玄学。

真实的缓存键还要包含：传递依赖的内容或哈希、编译 flag、目标三元组、编译器版本、环境宏、生成文件的输入、以及影响调试信息的路径。少一项就多一类陈旧结果。判断一个键是否完整，可以问：**把所有可能改变输出的东西都列出来，键覆盖了几项？** 没覆盖的，要么证明它不影响输出，要么加进去。

### 1.7.2 并行与 LTO 的预算冲突

并行编译按翻译单元切分，`-j8` 理论上把墙钟降到八分之一；实际受内存带宽、磁盘、链接阶段限制。LTO 把优化推迟到链接期，能跨单元内联，但把并行的工作合并成少数几个大任务，峰值内存显著上升。ThinLTO 试图在两者之间折中：按模块摘要并行优化，再做轻量合并。

预算决策要写成可验证的假设：「在 8 核 / 32 GB 的 CI 上，全量构建中位数不超过 6 分钟，峰值 RSS 不超过 12 GB」。然后测。没有基线的优化只是换了一种慢法。

### 1.7.6 峰值内存与产物体积

墙钟时间只回答「多久」，不回答「能不能跑完」。峰值内存（RSS）由这些部分构成：源文件与 token、AST/IR 的堆对象、分析缓存、并行任务的工作集、链接器的段缓冲。一个在 16 GB 机器上通过的构建，换到 8 GB 的 Linux CI 上可能被 OOM killer 杀掉，而日志里只有「exit code 137」。

| 来源 | 典型放大倍数 | 观察手段 | 降低手段 |
|:--|:--|:--|:--|
| AST/IR 对象 | 源文件的 10–100 倍（依实现而定） | 堆剖析、`/usr/bin/time -l` | 复用、arena、流式处理 |
| 分析缓存 | 与函数数量线性 | 缓存命中率/条目数 | 限制缓存、按需重算 |
| 并行任务 | 约等于 `-jN` × 单任务 | RSS 时间序列 | 降低并行度、分波次 |
| LTO 合并 | 全程序规模 | 链接器峰值 | ThinLTO、分片 |
| 调试信息 | 产物的 2–10 倍 | 文件大小、DWARF 段 | 拆分调试文件 |

测量内存时，记录**峰值**而不是平均值；平均值会掩盖瞬时高峰。Linux 用 `/usr/bin/time -v` 的 `Maximum resident set size`，macOS 用 `/usr/bin/time -l` 的 `maximum resident set size`（单位不同，读文档）。同时记录并行度与输入规模，否则数字不可比。

::: method 测量编译预算的五步 {#method-compilers.1.1.7.1}
1. **固定输入**：同一 commit、同一工具链、同一 flag、同一目标；记录它们的哈希。
2. **清理缓存**：全量构建前删除目标目录与增量缓存；否则测到的是缓存命中。
3. **预热一次**：文件系统缓存与编译器自身缓存会影响第一次；正式测量从第二次开始。
4. **重复至少 5 次**：记录墙钟、峰值 RSS、产物大小；取中位数与最大值，不只看平均。
5. **同机对比**：换机器、换负载的对比没有意义；把机器规格与后台负载写进报告。

只用「感觉快了」作为结论，无法区分噪声与改进。
:::

### 1.7.3 增量粒度：文件、函数还是查询

增量构建的粒度决定了「改一行要重编多少」。三种常见粒度：

| 粒度 | 失效单位 | 命中率 | 实现复杂度 | 典型系统 |
|:--|:--|:--|:--|:--|
| 文件 | 整个翻译单元 | 低 | 低 | make + `.o` |
| 函数/模块 | 函数或模块摘要 | 中 | 中 | ThinLTO、增量链接 |
| 查询 | 单个编译步骤 | 高 | 高 | rustc 查询系统、Salsa 风格框架 |

文件级增量最容易实现：源文件内容哈希变了就重编整个 `.o`。它的缺点是改一行注释也可能触发整个文件重编，且头文件变化会波及所有包含者。函数级需要稳定的函数标识与跨函数依赖图；查询级把「类型检查这个函数」「求这个常量的值」都建模成带键的查询，命中率最高，但必须跟踪查询之间的依赖，否则会出现「依赖变了但缓存没失效」。

增量正确性依赖两个条件：**键覆盖输入**、**失效传播完整**。前者是 1.7.1 讨论的内容；后者要求依赖图是真实的，而不是手工维护的近似。测试增量系统的一个有效方法是「改一处、全量重建一次」，比较增量产物与全量产物；差异就是失效漏洞。

### 1.7.4 分析缓存与失效

真实编译器不会每次都重算支配树、活跃变量、别名信息。分析结果被缓存，pass 声明自己保留了哪些、破坏了哪些。一个常见的错误是「pass 修改了 CFG，但没有失效支配树缓存」，后续 pass 用到过期的支配关系，做出错误变换。

工程上的防线有三层：调试构建中每个 pass 后重跑分析（慢但安全）；发布构建中依赖 pass 的显式声明（快但要求声明正确）；CI 中用「开启验证器 vs 关闭验证器」对拍输出。第三层最容易被忽略，也最能抓到声明错误。

| 缓存 | 依赖什么 | 哪些 pass 会让它失效 |
|:--|:--|:--|
| 支配树 | CFG 的边 | 增删基本块、改跳转 |
| 活跃变量 | 指令的 def/use | 增删指令、改变量 |
| 常量表 | 到达定值与控制流 | 改赋值、改分支 |
| 内联摘要 | 函数体与调用点 | 改函数体、改可见性 |

分析缓存与增量缓存是同一个问题的两个尺度：一个在单次编译内避免重算，一个在多次编译间避免重做。两者都要求「输入变了，结果必须失效」。区别在于，分析缓存的失效可以由 pass 精确声明，增量缓存的失效必须覆盖文件系统、环境与工具链。

### 1.7.5 预算与正确性的冲突

最便宜的编译是不做检查、不做优化、直接输出。任何预算压力都会诱使开发者删检查、关验证器、跳过测试。这类改动短期有效，长期把错误推迟到运行时，且难以定位。

一个可操作的规则是：**预算优化不能改变契约**。可以缓存、可以并行、可以跳过不影响输出的分析，但不能跳过语义检查，也不能让缓存返回与输入不符的产物。第 14 章的验证器会把「编译门禁」与「行为门禁」分开，正是为了防止「为了快而跳过」。

预算回归应该进 CI：记录工作计数（token 数、指令数、查询数）与墙钟中位数，超过阈值就失败。只测墙钟会在负载波动时抖动；只测计数会漏掉常数因子。两者一起看，才能区分「算法变慢」与「机器变忙」。

本节留下最后一个问题：如果 agent 生成的编译器跳过了语义检查，或者把操作数顺序写反，前七节的工具能不能抓住它？

预算的优先级应该由产品约束决定，而不是由工具默认值决定。一个交互式工具的冷启动预算可能比稳态吞吐更重要；一个离线批处理则相反。把优先级写下来，才能在「开 LTO 还是不开」「并行度调到多少」这类争论里有裁决依据。没有优先级的预算表，只是一堆互相矛盾的数字。

## 1.8 agent 生成编译管线的错误案例与最小实验 {#sec-compilers.1.1.8}

这一节复盘两个真实可复现的错误。它们不是「agent 不会写代码」的泛泛结论，而是两种典型的**契约缺口**：跳过语义检查、以及隐式的栈顺序约定。

### 1.8.1 案例一：没有名字解析就生成代码

任务：给表达式语言加赋值，生成栈机字节码。agent 写完 lexer、parser、codegen 后，直接运行了一个所有变量都已定义的例子，测试通过。它没有实现名字解析，理由是「VM 会在运行时检查」。

用 `b = a * a - 1;`（`a` 从未定义）验证：

```bash
python3 experiments/ch01/pipeline_tour.py --undefined
```

```text
source: b = a * a - 1;
bytecode emitted without a name-resolution pass:
 0000 LOAD     a
 0001 LOAD     a
 0002 MUL
 0003 CONST    1
 0004 SUB
 0005 STORE    b
 0006 HALT
stack verifier: ok (max depth 2)
runtime: ip=0 LOAD: undefined variable 'a'
static check: undefined variable 'a' at 1:5 (before codegen)
```

症状：编译阶段「成功」，字节码看起来完全合法，栈高度验证也通过；错误直到执行到 `LOAD a` 才出现。如果这段代码在某个分支里，而测试没走到那个分支，错误会一直潜伏到生产。

根因：pipeline 的契约里缺了「名字必须先声明后使用」这条检查。codegen 只负责把 `Var` 变成 `LOAD`，它不知道也不应该知道变量是否已定义；这个判断属于 resolver/typechecker。跳过它，等于把静态可判定的错误推迟到运行时。

如何发现：一是构造未定义变量的最小用例；二是看诊断阶段——如果编译器对「变量未定义」永远不报错，那它就没有名字解析；三是把 VM 的运行时错误与编译期检查对拍，前者不应是唯一的防线。

修复：在 codegen 之前插入一个 resolver pass，按语句顺序维护已定义集合，遇到 `Var` 先查集合；查不到就发诊断并阻止 codegen。实验里的 `static check` 行就是最小版本。真实语言还要处理作用域、前向声明、导入与遮蔽（第 3 章）。

| 检查 | 能抓到 | 抓不到 |
|:--|:--|:--|
| 栈高度验证 | 下溢、上溢、HALT 时栈非空 | 变量是否定义、操作数顺序 |
| resolver | 未定义名、重复定义 | 类型不匹配、运行时越界 |
| 类型检查 | 操作数类型不合法 | 值相关的错误、UB |
| 差分执行 | 语义偏差（在覆盖到的输入上） | 未覆盖路径、非确定性 |

### 1.8.2 案例二：操作数顺序与 VM 的隐式约定

任务：同一个 agent 实现二元运算的 codegen。它决定「先求右操作数，再求左操作数」，理由是 C 的求值顺序未指定，先右后左也合法。它写的发射顺序是：

```python
# agent 的版本：先右后左
gen(node.right)
gen(node.left)
code.append(Instr(BINOP[node.op]))
```

VM 的弹栈约定是「栈顶是右操作数」：

```python
b = stack.pop()   # 右
a = stack.pop()   # 左
stack.append(a - b)
```

两边各自都自洽，合起来对减法与除法就是反的。运行 `--buggy`：

```bash
python3 experiments/ch01/pipeline_tour.py --buggy
```

```text
== buggy codegen: right operand emitted first, VM pops left first ==
 stack verifier: ok (max depth 3)
 bytecode for 'a = 3 * (4 + 5) - 7 / 2;':
 0000 CONST    2
 0001 CONST    7
 0002 DIV
 0003 CONST    5
 0004 CONST    4
 0005 ADD
 0006 CONST    3
 0007 MUL
 0008 SUB
 tree=599 vm=-755 agree=False
 executed 21 instructions
 first random mismatch #5: ((3 - c) * 7);
 tree=-28 vm=28
```

症状：加法与乘法看起来正常（可交换），减法和除法符号/商反了；栈高度验证通过，字节码反汇编也「合法」。如果测试只覆盖 `+` 与 `*`，它会一直通过。

根因：codegen 与 VM 之间有一个**未写下来的契约**——操作数在栈上的顺序。agent 把「C 的求值顺序未指定」错误地推广成「栈顺序可以随便」；实际上 VM 的 `pop` 顺序是硬约定，codegen 必须匹配。更深一层：字节码没有把「左/右」编码进指令，顺序完全由发射顺序隐含，这是一个脆弱的接口设计。

如何发现：用非交换运算做最小对拍（`3 - 5` 应为 -2）；用随机表达式做差分（实验的 281 个有效对拍，第一次不匹配出现在 `((3 - c) * 7)`）；打印 VM 栈轨迹，看 `SUB` 前的栈是 `[3, 27]` 还是 `[27, 3]`。三者结合，能把「哪条指令、哪个操作数」定位到具体位置。

::: def 定义 1.8.1 · 栈机操作数契约 {#def-compilers.1.1.8.1}
一个栈机指令集必须规定：每条指令弹出几个值、按什么顺序解释这些值、压回几个值。对二元运算 `op`，若约定「先压左、后压右，`op` 弹出右再弹出左」，则 codegen 必须按 `gen(left); gen(right); op` 发射；VM 必须按 `b = pop(); a = pop(); push(a op b)` 执行。这个约定要写在指令集文档里，并由 codegen 测试与 VM 单元测试共同锁定。

只检查栈高度的验证器不能验证这个契约：顺序错了，高度仍然正确。
:::

修复分三层：

1. **接口层**：把发射顺序收敛到一个 `emit_binary` 函数，左右操作数的求值顺序只在这里决定；VM 的弹栈顺序在同一条注释/文档里写明。
2. **测试层**：每个非交换运算至少一个最小用例；再加随机表达式差分，oracle 用树遍历（不共享 codegen）。
3. **验证层**：静态栈效果检查（高度）+ 运行时栈轨迹（顺序）+ 可选的类型化 IR（把左右操作数变成显式参数，而不是隐式栈位置）。

第三层是长期解法：第 4 章的 SSA 把「哪个值喂给哪个操作」编码成显式 use，指令不再依赖隐式栈顺序；第 7、8 章的后端则用虚拟寄存器与活跃区间管理值。栈机简单，但它的隐式约定正是错误的温床。

::: ex 例 1.8.1 · 为什么栈高度验证器抓不到这个 bug {#ex-compilers.1.1.8.1}
对 `27 - 3`，错误 codegen 发射 `CONST 3; CONST 27; SUB`。验证器逐步计算：深度 0→1→2→1，每步都满足 `SUB` 需要 2 个操作数，最终深度 0，HALT 时栈空。所有结构条件成立。

正确 codegen 发射 `CONST 27; CONST 3; SUB`，深度序列完全相同。**两个程序在栈效果上不可区分**，区别只在值的身份。结构验证器没有「值」的概念，因此不可能发现。要发现它，需要一个能区分值的 oracle：树遍历、参考解释器、或带数据流语义的验证器。
:::

| 防线 | 成本 | 覆盖 | 适用阶段 |
|:--|:--|:--|:--|
| 最小对拍（每个运算符） | 低 | 已知边界 | 提交前 |
| 随机差分 | 中 | 组合错误 | CI |
| 栈轨迹 | 低 | 顺序/生命周期 | 调试 |
| 类型化 IR | 高 | 从接口上消除隐式顺序 | 设计期 |

两个案例的共同点不是「agent 粗心」，而是**契约没有被写成可执行的检查**。人也会犯同样的错；agent 只是把这个过程加速了。把契约写进类型、验证器与测试，才是可复用的修复。

### 1.8.3 修复与回归

修复不是把 `swap_operands` 改成 `False` 就结束。要把隐式契约变成显式、可执行的检查：

```python
def emit_binary(op: str, left, right) -> None:
    """栈契约：先压左，再压右；op 弹出右、再弹出左。"""
    gen(left)
    gen(right)
    code.append(Instr(BINOP[op]))

def run_vm(code, env=None):
    # 与 emit_binary 的注释成对出现；改一边必须改另一边
    b = stack.pop()   # right
    a = stack.pop()   # left
    stack.append(apply(op, a, b))
```

回归清单至少包含：

1. 每个非交换运算（`-`、`/`、比较、移位）各一个最小用例；
2. 一个混合优先级的表达式，确认 AST 形状与求值结果；
3. 300 个以上随机表达式的差分测试，oracle 不共享 codegen；
4. 一个栈轨迹断言：在 `SUB` 前，栈顶是右操作数；
5. 一个未定义变量的用例，确认 resolver 在 codegen 前拒绝；
6. 一个 `-O0/-O1` 对照，确认优化没有改变结果。

## 1.10 本章陷阱（8–15 条） {#sec-compilers.1.1.10}

::: errata 本章陷阱
1. **把「编译」等同于「生成汇编」**：只写一个 AST→文本的翻译器，遇到类型错误、未定义名、ABI 问题全部推给运行时。原因是没有区分前端/中端/后端的责任。修复：先写阶段表，给每段列出输入、输出、失败模式与检查手段，再决定哪段可以省略。
2. **用「能跑」当正确性证据**：示例程序返回了一个整数，就认为 codegen 正确。原因是缺少 oracle。修复：至少准备树遍历或参考解释器，对随机输入做差分；本章的 300 例随机输入（281 个有效对拍）就是最小版本。
3. **把 JIT 当成「解释器加缓存」**：忽略代码生成、守卫、去优化与代码缓存生命周期。原因是只看了启动性能。修复：画出「解释→基线→优化→去优化」的状态图，标出每个状态的进入条件与失败路径；第 12 章会展开信任边界。
4. **认为求值顺序未指定就等于栈顺序任意**：codegen 与 VM 各自自洽，合起来对减法/除法就是反的。原因是把语言层的未指定语义推广到实现层的硬约定。修复：把栈契约写进文档与 `emit_binary`，用非交换运算做最小对拍。
5. **跳过名字解析直接 codegen**：`LOAD` 一个未定义变量，直到运行时才报错。原因是把静态可判定的检查推给 VM。修复：在 codegen 前加 resolver，维护已定义集合；未定义就发诊断并阻止发射。
6. **只验证栈高度，不验证语义**：结构验证器通过，值却错了。原因是验证器只看形状，不看值的身份。修复：结构验证 + 差分执行 + 关键路径的栈轨迹，三者互补，不能互相替代。
7. **把 `-Werror` 当成语言要求**：换一个编译器/版本，警告消失，构建脚本就失败。原因是把项目策略写进了可移植性假设。修复：区分「标准要求诊断」与「项目把警告当错误」，后者要固定工具链并在文档里声明。
8. **用 `hash()` 做缓存键或产物指纹**：进程重启后哈希变化，缓存全部失效或错误命中。原因是 Python 字符串哈希带随机盐。修复：用 `hashlib.sha256` 对规范化字节序列求哈希，字段排序、不含时间与绝对路径。
9. **缓存键只用文件名或 mtime**：内容变了但时间没变（或反之），复用旧产物。原因是键没有覆盖内容与依赖。修复：键包含内容哈希、传递依赖、flag、目标三元组、编译器版本；本章 `--cache` 的 name-key 列就是反例。
10. **把调试信息当成「不影响产物」**：两个目录构建出不同哈希，CI 的字节比较失败。原因是 DWARF 写入了源路径。修复：用 `-fdebug-prefix-map` 或固定构建路径；比较前先确认比较的是哪一级可复现性。
11. **把 sanitizer 没报当成没有 UB**：测试只覆盖了一条路径，或被优化掉的检查没有插桩。原因是把 E4 观察当成 E1 规范。修复：把 sanitizer 结果写成「本次执行检测到/未检测到」，并补静态分析与代码审查；不要写「无 UB」。
12. **在预算压力下关掉验证器或语义检查**：编译变快，错误推迟到运行时。原因是把「预算」当成可以交换正确性的货币。修复：预算优化只能改缓存/并行/分析范围，不能改契约；用第 14 章的门禁把编译期检查与行为检查分开。
13. **把诊断文案当稳定接口**：测试断言完整的错误消息，改一个字就全线失败。原因是混淆了「错误码/位置」与「面向人的文案」。修复：断言 severity、code、主 span；文案只做包含性检查，并给文案改动留出 review 流程。
14. **把 JIT 的预热排除在基准之外**：只测优化层稳态，得出「JIT 比 AOT 快」的结论。原因是忽略了用户真实经历的启动阶段。修复：同时报告冷启动、预热到稳态的时间、稳态吞吐；固定 tier 并说明是否禁用 JIT。
15. **把「未指定」当成「随便」**：参数求值顺序未指定，于是认为任何顺序都可以用来解释栈契约。原因是混淆了语言层允许的多种结果与实现层必须固定的约定。修复：区分「标准允许的实现选择」与「本实现对外承诺的接口」，后者必须写进文档并由测试锁定。
:::

::: method 即时自测 · 1 {#method-compilers.1.1.11.1}
**Q1** 一个系统把 JavaScript 源码转成另一段 JavaScript，再交给浏览器执行。它属于哪类执行模型？如果它缓存了转换结果，缓存键至少应包含什么？

**Q2** 对 `a - b - c`，错误 codegen 先发射右操作数、VM 按「栈顶是右」弹栈。栈高度验证器会通过吗？树遍历与 VM 的结果分别是什么（设 a=10, b=3, c=2）？

**Q3** 同一份 C 源文件在两个目录用 `clang -g -O0 -c` 构建，产物哈希不同。给出两个可能原因与各自的验证命令。

**Q4** 一个 agent 写的编译器把 -- 当注释、把 1..2 当成两个浮点数。它最可能缺了哪两类测试？分别给出一个最小用例。

**Q5** 为什么本章把「栈高度验证通过」与「语义正确」分开说？给出一个两者分离的最小例子。

::: sol 答案
**A1** 属于 transpiler（源到源），最终执行仍由浏览器的解释器/JIT 负责。缓存键至少包含：源文本内容哈希、转换器版本、目标版本/flag、以及影响输出的环境（例如 `--target`、`--lib`、宏定义）。只按文件名缓存会复用陈旧结果。

**A2** 会通过。`a - b - c` 解析为 `(a - b) - c`；错误 codegen 对每个减法先右后左，得到 `c - (b - a)` 这一路的符号反转。代入 10、3、2：树遍历是 `(10-3)-2 = 5`；错误 VM 先算 `2-3=-1`，再算 `-1-10=-11`（具体取决于交换的层级），总之不等于 5。关键结论是栈高度序列完全相同，结构验证无法区分。

**A3** 原因一：DWARF 写入了不同的源路径；验证：`llvm-dwarfdump --debug-info` 看 `DW_AT_name`/`DW_AT_comp_dir`，或两次构建后 `cmp`。原因二：构建时间/日期宏或环境变量不同；验证：固定 `SOURCE_DATE_EPOCH`、清空环境后重建，再比较哈希。其他可能：并行度、PGO 剖面、链接顺序。

**A4** 缺两类测试：一是词法最小对（每个运算符与注释前缀都有正反例），例如 a - -b、a--b、// c、/* c */ 必须产生不同 token 序列；二是最长匹配的边界用例，例如 1..2、1.5、1. 必须分别得到 INT DOTDOT INT、FLOAT、INT 加诊断。再加上 token span 回查（每个 token 的文本必须出现在声明的行列）与随机输入的「不崩溃」模糊测试，才能覆盖注释/数字的状态转移。第 2 章会完整实现这套测试。

**A5** 因为验证器检查的是结构不变量，语义正确性需要值的对应关系。最小例子是 27 - 3：正确字节码是 CONST 27、CONST 3、SUB，错误字节码是 CONST 3、CONST 27、SUB；两者的栈深度序列都是 0→1→2→1→0，HALT 时都为空，验证器全部通过，但只有前者得到 24。要抓住后者，必须用树遍历或参考解释器做差分。
:::
