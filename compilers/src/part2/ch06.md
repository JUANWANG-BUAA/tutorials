第 5 章算出了「哪些定值可能到达」「哪些变量还活着」「哪些表达式在所有路径上可用」。这些事实本身不改变程序，只有被某个变换消费之后才会产生性能收益。第 6 章讲四个最常用的变换：循环不变代码外提、内联、常量折叠/传播、死代码删除，以及把它们组织起来的 pass 顺序。

每个变换都要回答三个问题：前提是什么，变换做了什么，变换后哪些性质仍然成立。前提写不完整，就会出现「测试全过、边界输入出错」的误编译；前提写得过强，优化不触发，性能回退但程序正确。本章的实验把这两侧都跑一遍：安全版本必须与解释器逐例一致，故意写错的版本必须产生可观察差异。

先看一个最小反例。循环 `while (i < n) { s += 100 / d; i++; }` 在 n=0 时一次也不执行，d=0 也不会触发除零。若把 `100 / d` 当成循环不变量提到循环前，n=0 时反而会 trap。这个变换的「不变」条件成立（d 在循环里没变），但「安全」条件不成立（除法可能 trap，且循环体不支配出口）。本章实验 `experiments/ch06/opt_lab.py` 会把这个反例和它的修复一起跑出来：

```bash
cd compilers
python3 experiments/ch06/opt_lab.py
```

```text
=== 汇总 ===
安全优化全部 match；四个故意错误全部按预期 mismatch；顺序差异在固定点后消失
```

## 6.1 支配、自然循环与循环识别 {#sec-compilers.2.6.1}

循环优化的第一步不是变换，而是找到循环。CFG 里没有显式的 `while` 节点，只有跳转边；一个边集合可能构成循环，也可能只是两条路径的交叉。编译器需要一种与语法无关的判定方式：回边（back edge）加上支配关系。

支配（dominance）回答「从入口到某点，是否必须经过另一个点」。若从入口到 $n$ 的每条路径都经过 $d$，称 $d$ 支配 $n$，记 $d \in dom(n)$。每个点支配自己；入口支配所有可达点。直接支配者（immediate dominator，idom）是「除自己外最近的支配者」，把每个点连到它的 idom，得到支配树（dominator tree）。

::: def 定义 6.1.1 · 支配与直接支配者 {#def-compilers.2.6.1.1}
对 CFG 的入口 $e$ 和节点 $n$，$dom(n)$ 是满足「每条从 $e$ 到 $n$ 的路径都经过 $d$」的节点 $d$ 的集合。$dom(e) = \{e\}$；对 $n \neq e$，
$$
dom(n) = \{n\} \cup \bigcap_{p \in pred(n)} dom(p).
$$
$n$ 的直接支配者 $idom(n)$ 是 $dom(n) \setminus \{n\}$ 中不被其他任何支配者支配的唯一节点。若 $h$ 支配 $n$ 且存在边 $n \to h$，称 $n \to h$ 为回边（back edge），$h$ 为循环头（loop header）。
:::

这个定义直接给出迭代算法：初始时入口的 $dom$ 是单元素集，其余是全集合；每轮用前驱的交集更新，直到不变。真实实验对 `licm_safe` 的输出是：

```text
dom[B0] = ['B0']
dom[B1] = ['B0', 'B1']
dom[B2] = ['B0', 'B1', 'B2']
dom[B4] = ['B0', 'B1', 'B4']
回边目标=B1 循环块=['B1', 'B2'] 出口块=['B1']
```

B2 的支配集合包含 B0、B1、B2：从入口到 B2 必须先过 B0 和 B1。B4 不支配 B2，因为 B4 只在循环退出后到达；B2 也不支配 B4。回边是 B2 -> B1，因为 B1 支配 B2 且存在这条边。

::: def 定义 6.1.2 · 自然循环 {#def-compilers.2.6.1.2}
给定回边 $n \to h$，自然循环（natural loop）是满足以下条件的最小节点集合 $L$：$h \in L$，$n \in L$，且对任意 $x \in L \setminus \{h\}$，$x$ 的所有前驱都在 $L$ 中。等价构造：从 $n$ 出发沿前驱反向搜索，遇到 $h$ 停止，收集到的节点加上 $h$ 就是 $L$。$h$ 是循环的唯一入口。
:::

自然循环的定义保证了「唯一入口」：除循环头外，任何节点的前驱都在循环内，因此不能从外面跳进循环中间。这个性质让循环优化可以使用「循环头支配所有循环节点」这一事实。对结构化语言生成的 CFG，所有循环都是自然循环；手写汇编或 `goto` 可能产生不可归约（irreducible）循环，存在多个入口，需要先做节点分裂或放弃某些优化。

<pre class="layout">
CFG（licm_safe）                     支配树                自然循环

   B0 (i=0, k=2)                      B0                  ┌─────────┐
    │                                  │                  │  B1     │
    ▼                                  ├── B1 ◄──回边──┐   │  c=i&lt;n  │
   B1 ◄──────────────┐                 │    │          │   │  br     │
    │  c = i &lt; n     │                 │    ├── B2     │   └────┬────┘
    ├──true──► B2 ───┘                 │    │          │        │
    │           │                      │    └── B4     │   ┌────▼────┐
    │           └──► B1                │                │   │  B2     │
    └──false─► B4                      │                │   │  s+=t   │
                │                      │                │   │  i++    │
                ▼                      │                │   └────┬────┘
              return                   │                │        │
                                       │                └────────┘
</pre>

读图：B1 是循环头，B2 是循环体，B2 -> B1 是回边；支配树里 B1 在 B0 之下、B2 在 B1 之下，说明 B1 支配 B2；右侧循环区域只包含 B1 和 B2，B4 在区域外，是出口的后继。

把迭代过程展开，可以看到支配集合如何从前驱的交集收敛（按 B0、B1、B2、B4 顺序原地更新）：

| 轮次 | dom(B0) | dom(B1) | dom(B2) | dom(B4) |
|--:|:--|:--|:--|:--|
| 0（初值） | {B0} | 全集合 | 全集合 | 全集合 |
| 1 | {B0} | {B0,B1} | {B0,B1,B2} | {B0,B1,B4} |
| 2 | {B0} | {B0,B1} | {B0,B1,B2} | {B0,B1,B4}（不变） |

第 1 轮 B1 的前驱只有 B0，交集是 {B0}，加上自己得到 {B0,B1}；B2 的前驱只有 B1，且 B1 已经在本轮更新过，所以得到 {B0,B1,B2}。B4 的前驱只有 B1，同理得到 {B0,B1,B4}。如果把 B4 排在 B1 之前处理，B4 会先用 B1 的旧值（全集合），多花一轮才收敛；这就是「原地更新」与「每轮用旧值」的区别，不影响最终结果，只影响轮数。算法的伪代码：

```python
def dominators(prog):
    blocks = list(prog["blocks"])
    dom = {b: set(blocks) for b in blocks}
    dom["B0"] = {"B0"}
    changed = True
    while changed:
        changed = False
        for b in blocks:
            if b == "B0":
                continue
            new = set(blocks)
            for p in preds_of(b):
                new &= dom[p]
            new |= {b}
            if new != dom[b]:
                dom[b] = new
                changed = True
    return dom
```

它验证「入口单元素、其余取前驱交集、加上自己」。预期与上表一致；把 `new |= {b}` 删掉，B1 的 dom 会缺少自己，`idom` 计算会出错。这个 bug 在只检查「h 是否在 dom[n]」时可能仍然通过，因为 h 通常不等于 n，只有自支配的断言能抓到。

循环的形态不止一种。下面这张表列出常见 CFG 结构与自然循环识别的关系：

| 结构 | 回边 | 循环块 | 备注 |
|:--|:--|:--|:--|
| while | 体末尾 -> 头 | 头 + 体 | 零次迭代，体不支配出口 |
| do-while | 体末尾 -> 头 | 头 + 体 | 至少一次，体支配出口 |
| for | 增量块 -> 头 | 头 + 体 + 增量 | 增量通常单独成块 |
| 嵌套循环 | 内层回边、外层回边 | 两层区域 | 内层循环是外层区域的子集 |
| break/continue | 多条回边或出口边 | 需合并同一头的多个回边 | 自然循环取并集 |
| 不可归约 | 多个入口 | 不是自然循环 | 需节点分裂或放弃优化 |

预头部的构造步骤可以固定下来：

1. 找到循环头的所有循环外前驱。
2. 若只有一个，且它只有一条边到循环头，直接把它当预头部。
3. 否则新建一个空块 P，把循环头的所有外部前驱改为指向 P，P 无条件跳到循环头。
4. 把循环不变指令移到 P 的终止指令之前。
5. 更新支配树、前驱/后继表和分析缓存。
6. 若 P 只有一个后继且没有其他指令，后续 CFG 化简可以把它合并掉。

不可归约循环在 C 里可以由 `goto` 构造：两个入口跳进同一个循环体，谁也不是支配者。自然循环算法找不到唯一的头，LICM 的「头支配所有节点」前提失效。编译器通常先做节点分裂（node splitting），把不可归约图变成可归约图，或直接跳过该循环的优化。第 4 章的 SSA 构造也假设可归约 CFG；两处的前提是一致的。

识别循环之后，还要构造预头部（preheader）。自然循环的头可能有多个来自循环外的前驱；循环不变代码需要一条「每次进入循环前只执行一次」的位置。预头部是一个新块，只有一条边指向循环头，循环头的所有外部前驱改为指向预头部。实验里的 B0 天然就是预头部，因为它只有一条边到 B1。

::: thm 定理 6.1.1 · 循环头的支配性 {#thm-compilers.2.6.1.1}
对自然循环 $(L, h)$，$h$ 支配 $L$ 中的每个节点；且 $L$ 中除 $h$ 外的每个节点，其所有前驱都在 $L$ 中。
:::

::: proof 证明思路
由自然循环的构造：从回边源 $n$ 沿前驱反向搜索，只有遇到 $h$ 才停止。对任意 $x \in L \setminus \{h\}$，搜索经过 $x$ 时会把 $x$ 的所有前驱加入（除非前驱是 $h$），所以这些前驱都在 $L$ 中。唯一入口加上「所有前驱在循环内」推出 $h$ 支配每个节点：任何从入口到 $x$ 的路径若第一次进入 $L$，只能通过 $h$，否则会从一个循环外前驱直接进入 $x$，与「前驱在循环内」矛盾。
:::

实现上有三个边界。第一，支配集合的迭代与块顺序无关，但用逆后序能更快收敛；实验为了可读性按 B0、B1、B2、B4 的顺序扫。第二，不可达块没有前驱，交集是全集，会让 `dom` 变成全集合；应先把不可达块删掉，或让它们不参与循环识别。第三，多个回边可能指向同一个头（例如 `continue` 和循环体末尾各有一条边），自然循环要把它们对应的节点并起来；实验只处理单回边，真实编译器要遍历所有回边并合并。

嵌套循环的处理顺序会影响 LICM 的效果。内层循环的不变代码可以提到外层循环之外，前提是它在两层里都不变，并且外提不引入新的 trap。常见做法是从内层向外层处理，或先构造循环树（loop nest），再按深度排序。第 6.2 节的条件对每一层都要重新检查，不能因为「在内层不变」就跳过外层的别名检查。

## 6.2 循环不变代码外提：条件与收益 {#sec-compilers.2.6.2}

循环不变代码外提（loop-invariant code motion，LICM）把循环里每次迭代都算、结果却不变的计算移到预头部，只算一次。它是最容易讲、也最容易写错的优化：不变性只回答「值会不会变」，不回答「提前算安不安全」。

先定义不变性。一个指令在循环 $L$ 中不变，当且仅当它的所有操作数要么是常量，要么在循环外定义，要么由另一条已经在循环外（或已证明不变）的指令定义。这个定义是递归的，实现时通常按「已外提集合」迭代：先把只依赖常量和循环外变量的指令标为不变，再逐步扩大。

::: def 定义 6.2.1 · LICM 的安全条件 {#def-compilers.2.6.2.1}
把指令 $i$ 从循环块 $b$ 移到预头部，需要同时满足：

1. **不变性**：$i$ 的所有操作数在循环内没有被重新定义，或已被外提。
2. **单定义**：$i$ 的目标变量在循环内只有这一处定义（非 SSA 时必须检查，SSA 下自动成立）。
3. **可推测（speculatable）或支配所有出口**：$i$ 不会 trap、不会抛异常、没有副作用；或者 $b$ 支配循环的所有出口，从而「循环退出时 $i$ 一定已经执行过」。
4. **内存安全**：若 $i$ 读内存，循环内没有可能别名到该内存的写，且该内存不是 volatile。
5. **收益**：$i$ 在循环内至少会被执行一次，且外提不会把寄存器压力推过阈值。
:::

条件 3 是本章反例的核心。除法可能 trap，load 可能越界，函数调用可能抛异常；它们即使「值不变」，也不能在循环可能零次执行时提前求值。条件 4 处理别名：`a[0]` 在循环里可能不变，但如果循环体写了 `a[i]`，且 i 可能为 0，那么每次迭代的 `a[0]` 都不同。

先看安全版本。实验对 `licm_safe` 只做 LICM，真实输出是：

```text
--- licm_safe 仅做安全 LICM ---
  B0: i = 0
  B0: k = 2
  B0: t = k * 3
  B0: goto B1
  B1: c = i < n
  B1: if c goto B2 else B4
  B2: s = s + t
  B2: i = i + 1
  B2: goto B1
  B4: print s
  B4: ret s
```

`t = k * 3` 从 B2 移到了 B0。它满足全部条件：k 是循环外定义的常量；t 在循环内只有这一处定义；乘法不会 trap；不读内存；循环体每轮都用 t。外提后 B2 少一条乘法，执行 n 次时省下 n-1 次。

再看反例。`licm_trap` 的循环体是 `q = 100 / d; s = s + q; i = i + 1`，n=0 时循环体不执行：

```text
n=0 正确语义=('ok', (0,), 0) 错误外提=('trap:div0', (), None) 差异=True
```

安全版本把 `q = 100 / 0` 留在 B2（常量折叠把 d 换成了 0，但没有折掉除法），n=0 时正常返回 0。不安全版本把它提到 B0，进入循环前就执行除零，trap。这个差异不是「结果不准」，而是「程序从一个正常返回变成崩溃」。

第二个反例是别名。`licm_alias` 的循环体先写 `a[i] = v`，再读 `t = a[0]`。循环执行两次，a[0] 在第一次迭代后被写成 1，所以正确结果 s=2：

```text
正确语义=('ok', (2,), 2) 错误外提=('ok', (0,), 0) 差异=True
```

不安全版本把 `t = a[0]` 提到 B0，读到初始值 0，两次迭代都加 0。这里不变性分析只检查「a 这个变量有没有被重新定义」，而数组元素是通过 store 修改的，不改变变量 a 的定值；只看变量名会误判为不变。条件 4 要求看内存写，而不是看数组变量本身。

::: ex 例 6.2.1 · 为什么「循环体支配出口」能救除法 {#ex-compilers.2.6.2.1}
把上例改成 `do { q = 100 / d; ... } while (...)`，循环体至少执行一次。此时循环体块支配所有出口：任何离开循环的路径都经过它，除法在原始程序里一定会执行。把它提到预头部不会引入新的 trap（原来就会 trap 的输入仍然 trap，原来不 trap 的输入在执行到除法时仍会 trap），所以条件 3 的后半句成立。反过来，`while` 循环的零次迭代路径绕过了循环体，循环体不支配出口，除法就不能外提。区分 `while` 与 `do-while` 的不是语法，而是「循环体是否支配出口」这一图性质。
:::

LICM 的实现可以写成「反复扫描直到没有指令可移」：

```python
def licm(prog, safe=True):
    loops = natural_loops(prog)
    for header, loop in loops:
        pre = find_or_create_preheader(prog, header, loop)
        hoisted = set()
        changed = True
        while changed:
            changed = False
            for b in loop:
                for ins in prog.blocks[b]:
                    if not invariant(ins, loop, hoisted):
                        continue
                    if not single_def(ins, loop):
                        continue
                    if safe and not (speculatable(ins) or dominates_all_exits(b, loop)):
                        continue
                    if safe and reads_memory(ins) and may_alias_store(ins, loop):
                        continue
                    move_to_preheader(prog, pre, ins)
                    hoisted.add(ins.dst)
                    changed = True
```

它验证「不变 + 单定义 + 安全 + 无别名写」四道门。预期：`t = k * 3` 通过四道门被移到 B0；`q = 100 / d` 在 safe 模式下被第三道门挡住；`t = a[0]` 被第四道门挡住。把 `safe` 设成 False，后两条都会通过，产生 6.2 节的两个反例。

按指令类型列一张安全表，评审时逐行对照：

| 指令 | 不变性 | 可推测 | 需要别名检查 | 默认策略 |
|:--|:--|:--|:--|:--|
| 常量赋值 | 是 | 是 | 否 | 可外提 |
| 整数加减乘 | 看操作数 | 是（无溢出 trap 时） | 否 | 可外提 |
| 整数除法 | 看操作数 | 否（除零 trap） | 否 | 仅支配出口时 |
| 比较 | 看操作数 | 是 | 否 | 可外提 |
| 数组 load | 看下标/数组 | 否（越界 trap） | 是 | 仅无别名写且支配出口 |
| 标量 load | 看地址 | 否（空指针/越界） | 是 | 保守 |
| store | 看地址/值 | 否（副作用） | 是 | 不外提 |
| 调用 | 通常否 | 否（异常/副作用） | 是 | 不外提 |
| volatile 访问 | 否 | 否 | 是 | 不外提 |

收益侧也要量化，不能只看「少算了几次」：

| 因素 | 收益变大 | 收益变小/为负 |
|:--|:--|:--|
| 循环 trip count | 大（成百上千） | 1 到 2 次 |
| 指令成本 | 除法、load、调用 | 常量、简单加法 |
| 寄存器压力 | 富余 | 已接近上限 |
| 代码尺寸 | 循环小、icache 有余 | 循环大、icache 紧张 |
| 分支可预测性 | 外提后循环更短 | 外提引入新分支 |

一个常见的误判是「外提一定减少指令数」。外提把指令从循环体移到预头部，循环体少一条，预头部多一条；净指令数是「1 次 vs n 次」，只有 n 大于 1 才赚。若循环可能零次执行，外提甚至多执行一次（对纯指令无害，对可能 trap 的指令有害）。成本模型要把「执行概率」和「trip count」都算进去，不能只看静态指令数。

LICM 与别名分析的交互还有一个细节：循环内的 store 不一定是「写整个数组」。若分析能证明 store 的下标范围与 load 的下标不重叠（例如 `a[i]` 与 `a[0]` 且 i 从 1 开始），load 仍可外提。实验里的分析没有区间信息，只按「同数组即可能别名」保守处理；真实编译器会用范围分析或版本化（loop versioning）来恢复精度。

收益不是自动的。外提一条指令可能让它的结果在整个循环期间占用一个寄存器，增加寄存器压力，导致溢出；也可能把冷路径上的计算提前到热路径。若循环只执行一两次，外提的收益接近零，反而增加代码尺寸。真实编译器会用循环深度、trip count、寄存器压力估值做代价模型，或在 IR 上先做 LICM 再做寄存器分配，让分配器决定溢出。

还有一个容易被忽略的边界：外提不能改变异常的可观察顺序。若循环体里有 `print`、`store` 或可能抛异常的调用，把后面的计算提前到它们之前，会改变异常发生时的输出。条件 3 的「无副作用」不仅指不写内存，还包括不抛异常、不触发 trap、不产生可观察的日志。

最后，LICM 通常不是单独运行的。它依赖支配树、别名分析、常量传播和副作用分析；它产生的新常量又会被常量折叠消费。第 6.6 节会看到，把 LICM 放在常量传播之前还是之后，会影响「哪些指令还被认为有循环不变性」。这也是 pass 顺序问题的一个具体例子。

## 6.3 内联：成本模型、可见性与边界 {#sec-compilers.2.6.3}

内联（inlining）把被调用函数的函数体复制到调用点，消掉调用开销，并让常量参数、死代码、别名信息跨过原来的函数边界。它是最有效的优化之一，也是最容易让代码膨胀的优化。决定「内联哪个调用点」的是一个成本模型（cost model），不是一条固定规则。

成本模型比较三样东西：省下的调用开销、暴露出的新优化机会、增加的代码尺寸。调用开销包括参数传递、返回地址、栈帧建立/销毁、callee-saved 寄存器保存；在热循环里，这些开销可能占一次调用的很大比例。新机会包括：常量参数让分支折叠、参数别名信息让 load/store 重排、函数体小到可以被外层进一步优化。代码尺寸的代价包括指令缓存压力、编译时间、调试信息体积。

::: def 定义 6.3.1 · 内联成本模型 {#def-compilers.2.6.3.1}
对调用点 $c$（调用者 $A$，被调用者 $B$），估算

$$
\mathrm{benefit}(c) = \mathrm{call\_overhead}(c) + \mathrm{exposed\_opt}(c) - \mathrm{size\_cost}(B) - \mathrm{compile\_cost}(B)
$$

当 $\mathrm{benefit}(c) \gt 0$ 且 $B$ 的规模、递归深度、调用点热度满足阈值时内联。阈值不是语言规范的一部分，随编译器版本、优化级别、目标架构变化；同一段代码在 clang 与 gcc 上可能得到不同的内联决定。
:::

影响决策的因素可以列成表：

| 因素 | 倾向内联 | 倾向不内联 |
|:--|:--|:--|
| 函数体大小 | 小（几条指令） | 大（循环、多个分支） |
| 调用点热度 | 热循环、频繁调用 | 冷路径、只调用一次 |
| 参数 | 常量、地址已知 | 未知、可能别名 |
| 返回值 | 被立即使用 | 被忽略 |
| 递归 | 深度 1、有界 | 无界、互递归 |
| 可见性 | 同编译单元、LTO | 跨动态库、虚调用 |
| 代码尺寸 | 有增长预算 | 已接近 icache 容量 |
| 调试 | 发布构建 | 调试构建（-O0 通常不内联） |

可见性（visibility）是硬边界。一个 `static` 函数只在一个编译单元内可见，编译器可以直接内联；一个 `extern` 函数在另一个编译单元里定义，没有链接时优化（link-time optimization，LTO）时看不到函数体，无法内联。`-fvisibility=hidden` 改变符号导出，不改变「能否看到函数体」；`always_inline` 是给编译器的强提示，但跨编译单元仍然需要 LTO 或头文件里的定义。C++ 的虚调用要先做去虚化（devirtualization），否则调用目标不唯一。

被测代码（`inl.c`，用 `cc -std=c17 -Wall -Wextra -Werror` 编译通过）：

```c
static int square(int x) { return x * x; }

int sum_squares(int n) {
    int s = 0;
    for (int i = 0; i < n; i++) s += square(i);
    return s;
}
```

一个真实的内联报告（macOS，Homebrew clang 22.1.8，`-O2`）：

```bash
clang -O2 -Rpass=inline -c inl.c
```

```text
inl.c:4:38: remark: 'square' inlined into 'sum_squares' with (cost=-15030, threshold=337) at callsite sum_squares:2:38; [-Rpass=inline]
```

负的 cost 表示这次内联在模型里是「赚」的；threshold 是当前优化级别允许的阈值。报告只说明编译器做了决定，不说明决定一定正确；要看代码尺寸和实际性能，不能只看 remark。

递归是成本模型的硬边界。自递归函数可以内联一层，把递归调用留在内联后的函数体里；无限展开会让编译不终止。互递归（A 调 B、B 调 A）需要调用图上的环检测；常见做法是给每个调用点一个深度预算，超过就停止。尾部递归可以转成循环，那是另一类变换，不属于内联。

内联前后的 IR 对照可以写成：

```text
调用前：                        内联后（参数已临时化）：
  t0 = next()                     t0 = next()
  t1 = square(t0)                 t1 = t0 * t0
  ...                             ...
```

它验证「实参只求值一次、函数体替换形参」。预期：`next()` 在两边都只出现一次；若内联器把 `t0` 换成 `next()` 的调用表达式，就会出现两次。内联还会把被调用者的局部变量改名，避免与调用者同名变量冲突；这一步做错，会出现「内联后变量被覆盖」的隐蔽 bug。

有三种情况应该拒绝内联，即使成本模型说划算：函数体包含 `alloca` 且生命周期跨越调用边界；函数有可变参数且调用点用 `va_start`；函数包含内联汇编或 `setjmp`。这些结构的语义依赖真实的栈帧，复制到调用者会改变行为。

内联暴露的优化机会可以列成表：

| 机会 | 例子 | 需要的前提 |
|:--|:--|:--|
| 常量参数折叠 | `f(3)` 里的 `x*2` 折成 6 | 参数是常量 |
| 分支消除 | `if (flag)` 且 flag 为常量 | 参数/全局常量 |
| 死代码删除 | 只会走一个分支，另一支变死 | 分支可折 |
| 别名消解 | 调用者与被调用者不重叠的对象 | 内联后可见 |
| 返回值优化 | 返回值直接进入调用者的表达式 | 无异常/无副作用 |
| 尾调用 | 内联后尾位置可直接跳转 | 语言/ABI 支持 |
| 向量化 | 内联后循环体变简单 | 无别名/可向量化 |
| 常量传播 | 内联后临时变量变常量 | 后续有传播 pass |

这张表解释了为什么内联常放在流水线前部：它的收益不只是省一次调用，而是让后面的 pass 看到更多信息。代价是代码尺寸与编译时间；没有预算的内联会把「更多信息」变成「更多代码」。

::: ex 例 6.3.1 · 参数被使用两次时不能直接替换表达式 {#ex-compilers.2.6.3.1}
设 `f(x) = x + x`，调用点是 `f(next())`，`next()` 每次调用返回不同的值并推进状态。若内联时把参数表达式直接替换进函数体，得到 `next() + next()`，`next()` 被求值两次，结果和副作用都变了。正确做法是先把实参求值到一个临时变量 `t = next()`，再把函数体里的 x 替换成 t，得到 `t + t`。TAC 的调用参数已经是临时变量，所以在 TAC 上做内联不会犯这个错；在 AST/高层 IR 上做内联必须显式引入临时变量。这个例子说明「内联」不只是复制文本，还要保持求值次数与顺序。
:::

代码膨胀可以用一个简单模型估算。若函数 A 调用 B 三次，B 内联后又被 C 内联，且每层有 $k$ 个调用点，嵌套 $d$ 层后代码量可能按 $k^d$ 增长。真实编译器用「内联预算」限制总增长：每个调用者有一个尺寸上限，超过就不再内联；LTO 还会限制跨模块的内联总量。没有预算的内联在大型项目上会让二进制膨胀数倍，指令缓存命中率下降，性能反而变差。

成本模型可以用一个具体例子估算。设调用开销 6 个周期（传参、调用、返回、栈帧），被调用者体 20 条指令，调用点在一个执行 1000 次的循环里，内联后代码尺寸增加 20 条：

| 项目 | 不内联 | 内联 | 差值 |
|:--|--:|--:|--:|
| 每次调用开销 | 6 | 0 | -6 |
| 函数体执行 | 20 | 20 | 0 |
| 常量参数带来的折叠 | 0 | -4 | -4 |
| 循环内总周期（1000 次） | 26000 | 16000 | -10000 |
| 代码尺寸（条） | 20 | 40 | +20 |
| 编译时间 | 低 | 略高 | 可忽略 |

在这个例子里，内联明显划算。若循环只执行 2 次，总周期从 52 降到 32，收益变小；若函数体有 200 条指令，代码尺寸增加 200 条，可能把 icache 挤掉，收益为负。成本模型要同时看「执行频率」和「尺寸代价」，不能只看函数体大小。

可见性决定了「能不能内联」，成本模型只决定「值不值得」。三者的关系可以列成表：

| 场景 | 能看到函数体 | 能内联 | 备注 |
|:--|:--|:--|:--|
| `static` 函数，同文件调用 | 是 | 是 | 最常见 |
| `extern` 函数，无 LTO | 否 | 否 | 只能链接后调用 |
| `extern` 函数，有 LTO | 是 | 是 | 需要链接器支持 |
| 头文件里的 `inline` 定义 | 是 | 通常是 | C99 语义依赖编译器 |
| C++ 虚调用 | 目标不唯一 | 去虚化后可以 | 需要类层次分析 |
| 函数指针调用 | 目标不唯一 | 点分析后可以 | 需要指向分析 |

递归与互递归需要单独的预算：

- 自递归：最多内联一层，递归调用保留；否则编译不终止。
- 互递归：在调用图上检测环，环上的调用点只允许有限深度。
- 尾递归：可以转成循环，属于尾调用优化，不是内联。
- 间接递归（函数指针）：调用图不完整，默认不内联。
- 递归 + 常量参数：可能让递归深度在编译期有界，但仍要设上限。

代码膨胀的估算可以用「调用点数量 × 函数体大小」：

| 场景 | 增长因子 | 风险 |
|:--|:--|:--|
| 一个调用点内联一次 | 1x | 低 |
| 10 个调用点内联同一个大函数 | 10x | 高 |
| 嵌套内联（A 内联 B，B 内联 C） | 每层相乘 | 指数级 |
| 递归内联一层 | 2x | 中 |
| LTO 跨模块全内联 | 总代码量 | 编译时间/icache |

真实编译器用「内联预算」限制总增长：每个调用者有尺寸上限，超过就不再内联；LTO 还有全局预算。预算不是语言规范，不同版本可能不同；把性能押在「这个函数一定会被内联」上是不可靠的。

语义边界比成本模型更重要。内联必须保持：实参求值次数与顺序、异常传播路径、`volatile` 访问次数、调试信息的行号映射、尾调用的栈行为（若语言保证尾调用优化）。任何一条被破坏，程序的可观察行为就可能改变。成本模型只决定「值不值得」，语义规则决定「允不允许」。

## 6.4 常量传播、折叠与死代码 {#sec-compilers.2.6.4}

常量传播（constant propagation）把「这个变量在所有路径上都是常量」的事实沿 CFG 传播；常量折叠（constant folding）把常量表达式在编译期算成一个值；死代码删除（dead code elimination，DCE）删掉结果无人使用、且没有副作用的指令。三者经常一起跑：传播暴露折叠机会，折叠产生死代码，DCE 清理。

第 5 章已经给出非 SSA 的数据流形式。SSA 下可以用稀疏传播：每个变量只有一个定义，常量事实沿着 def-use 链走，不需要在每个块上做集合合并。稀疏条件常量传播（sparse conditional constant propagation，SCCP）进一步把「可达性」加入格：分支条件被证明为常量后，不可达的分支不参与合流，$\phi$ 不会因为一条不可行路径变成 NAC。SCCP 比第 5 章的非 SSA 版本更精确，但正确性条件相同：只折「在所有可达路径上都相同」的值。

折叠规则不是「看到常量就算」，每条规则都带前提：

| 表达式 | 可折条件 | 反例/边界 |
|:--|:--|:--|
| `x + 0` → `x` | 整数，x 已定义 | 浮点 `-0.0`、NaN |
| `x * 1` → `x` | 整数，x 已定义 | 浮点舍入、信号 NaN |
| `x * 0` → 0 | 整数，x 已定义、非 volatile、求值不 trap | 浮点 NaN、volatile 读不能被删 |
| `x - x` → 0 | 整数，x 已定义 | 浮点 NaN、-0.0 |
| `x / 1` → `x` | 整数，x 已定义 | 浮点、除数为 0 的浮点异常 |
| `x / 0` | 不折 | 整数除零是 trap 或 UB；折掉会删 trap |
| `1 << 64` | 不折（或按目标语义） | 移位量越界是 UB |
| `INT_MAX + 1` | 不折（或按回绕语义） | C 有符号溢出是 UB；Rust debug panic |

最后两行是「语言语义决定折叠」的典型。C 的有符号溢出是未定义行为，编译器可以假设它不发生，因此可以把 `x + 1 > x` 折成真；但这是建立在「程序没有 UB」的前提上，不是在所有输入上都成立。Rust 的 debug 构建在溢出时 panic，release 构建回绕；折叠必须按当前构建的语义做，不能按宿主语言的整数行为做。

::: def 定义 6.4.1 · 常量折叠的安全条件 {#def-compilers.2.6.4.1}
对表达式 $e$ 和常量操作数，折叠成常量 $c$ 需要：(1) $e$ 的所有操作数在编译期已知；(2) $e$ 的求值在 IR 语义下不会 trap、不会抛异常、不读取 volatile/原子内存；(3) 计算结果在目标类型的值域内，或 IR 明确规定了回绕/饱和语义；(4) 折叠不改变可观察的求值次数（例如不删除可能发生的异常）。四条缺一不可。
:::

DCE 也有前提。删除一条指令需要：(1) 它的结果没有被任何后续指令使用；(2) 它没有副作用（不写内存、不调用未知函数、不 volatile）；(3) 它不会 trap（除零、越界、空指针解引用）。第三条常被忽略：一条结果无人使用的除法仍然可能 trap，删掉它会改变程序行为。实验里的安全 DCE 对除法保留了「除数是非常量或可能为 0」的指令，正是这个原因。

真实实验的输出（`const_dce` 程序）：

```text
--- const_dce 优化后 ---
  B0: print 42
  B0: print 19
  B0: ret 0
const_dce: before=('ok', (42, 19), 0) after=('ok', (42, 19), 0) match=True
```

原始程序里的 `i=7`、`j=12`、`x=i*6`、`y=j+i`、`dead=99` 全部被折叠/删除，只留下两次 `print`。`dead` 没有任何使用者，是典型的死定义；`i`、`j` 在折叠后也不再被需要，DCE 一并删除。

另一个程序验证 DCE 不会删 trap：

```text
--- div_zero 优化后 ---
  B0: q = 100 / 0
  B0: print q
  B0: ret q
div_zero: before=('trap:div0', (), None) after=('trap:div0', (), None) match=True
```

`q` 的结果被 `print` 使用，所以 DCE 不会删它；即使没人使用，除零仍然必须保留，因为删掉会把「trap」变成「正常返回」。安全性检查在这里压倒了「删除无用代码」的直觉。

折叠与 DCE 的代码都不长。实验里的折叠函数对每种运算显式处理边界：

```python
def fold_bin(op, a, b, unsafe=False):
    if a == NAC or b == NAC:
        return NAC
    if a == UNDEF or b == UNDEF:
        return UNDEF
    if op == "+":
        return a + b
    if op == "*":
        return a * b
    if op == "/":
        if b == 0:
            return 0 if unsafe else NAC
        return a // b
    ...
```

它验证「NAC 吸收、UNDEF 传播、除零不折」。预期：`fold_bin('/', 100, 0)` 返回 NAC；`fold_bin('/', 100, 0, unsafe=True)` 返回 0。后者是本章 agent 错误案例的核心：只改一个分支，就把 trap 删掉了。

死代码删除的边界可以用一张表概括：

| 指令 | 结果未使用时能删吗 | 原因 |
|:--|:--|:--|
| `x = 1` | 能 | 无副作用、不 trap |
| `x = a + b` | 能 | 整数加法不 trap（除非语言规定溢出 trap） |
| `x = a / b` | 仅当 b 是已知非零常量 | 除零可能 trap |
| `x = a[i]` | 通常不能 | 越界可能 trap，volatile 读必须保留 |
| `a[i] = x` | 不能 | 写内存有副作用 |
| `print(x)` | 不能 | 可观察输出 |
| `call f()` | 不能，除非 f 是 pure/readnone 且不 trap | 未知副作用 |

这张表也解释了为什么「DCE 很简单」是错觉：删除的合法性依赖副作用分析、trap 语义和别名信息。第 6.5 节会把这些依赖展开。

SCCP 的迭代可以拆成三步：

1. 从入口开始，把可达块加入工作列表；不可达块不参与合并。
2. 对每个块的指令做常量传播；遇到 `br` 条件为常量时，只把选中的后继加入工作列表。
3. 合流点的 $\phi$ 只合并可达前驱的值；若只有一个可达前驱，直接取该值。

第三步是 SCCP 比普通常量传播精确的原因：不可行路径不参与 $\phi$ 的合并，变量不会因为一条永远不会走的分支变成 NAC。

DCE 的实现可以写成「反向扫描 + 活跃集合」：

```python
def dce_block(insns, live_out):
    live = set(live_out)
    keep = []
    for ins in reversed(insns):
        if ins.dst is not None and ins.dst not in live and removable(ins, live):
            continue
        keep.append(ins)
        if ins.dst:
            live.discard(ins.dst)
        live |= uses_of(ins)
    return list(reversed(keep))
```

它验证「从后往前，先看结果是否活跃，再把 use 加回活跃集」。预期：`dead = 99` 被删；`q = 100 / 0` 因 `removable` 返回 False 而保留；`x = 3 * 4` 若 `x` 无人使用则被删。反向扫描的顺序不能反：正向扫描时，后面的 use 还没被看到，会把仍然活跃的定值误删。

折叠/传播/DCE 三者的交互还有一个细节：DCE 删除一个定值后，可能让另一个表达式变成「操作数未定义」，从而让常量传播的状态变差。正确顺序通常是先传播、再折叠、再 DCE；若 DCE 先跑，删掉了后面还要用的定义，传播会看到 UNDEF。固定点驱动会重跑，但中间状态的调试信息会很难读。

| 折叠 | 输入 | 安全结果 |
|:--|:--|:--|
| 加法 | 2 + 3 | 5 |
| 减法 | 0 - 5 | -5（在目标类型范围内） |
| 乘法 | 7 * 6 | 42 |
| 除法 | 100 / 4 | 25 |
| 除法 | 100 / 0 | 不折（trap/UB） |
| 比较 | 3 < 5 | 1 |
| 移位 | 1 << 63 | 依赖目标宽度与符号 |
| 溢出 | INT_MAX + 1 | 不折（C 是 UB） |

::: ex 例 6.4.1 · 折叠 100/0 删掉了什么 {#ex-compilers.2.6.4.1}
原始程序 `d=0; q=100/d; print q` 的可观察行为是「trap，没有输出」。把 `100/0` 折成 0 后，程序变成 `q=0; print 0`，可观察行为是「正常返回，输出 0」。差异不只是一个值：程序从异常终止变成了正常终止，调用者看到的退出码、后续清理、日志都不同。若这段代码在 sanitizer 或 Wasm 的 trap 语义下运行，折叠还违反了 IR 的语义契约。结论：除零折叠不是「精度问题」，是「删除可观察事件」。
:::

常量传播还有一个精度边界：它只跟踪「值」，不跟踪「值之间的关系」。`x=1; y=2` 能折出 `x+y=3`；`x+y=3` 这样的关系事实不在平坦格里。第 5.6 节已经给出不可分配的例子。需要关系推理时，换域（区间、octagon、符号执行），而不是在常量传播里硬加规则。

## 6.5 别名、副作用与优化屏障 {#sec-compilers.2.6.5}

前四节的所有变换都假设「我知道这条指令读写了什么」。这个假设在指针、数组、函数调用和 `volatile` 面前经常不成立。别名分析（alias analysis）回答「两个指针是否可能指向同一对象」，副作用分析回答「这条指令可能改变什么」，两者共同决定优化能不能跨过一条指令。

::: def 定义 6.5.1 · 可能别名 {#def-compilers.2.6.5.1}
两个内存访问 `*p` 与 `*q` 可能别名（may-alias），当且仅当存在一条执行路径使它们指向同一对象。may-alias 是保守判断：不能证明不别名时，就按可能别名处理。若分析能证明在所有路径上都不别名，称 no-alias；若证明一定别名，称 must-alias。优化只能在 no-alias 的前提下重排两个访问；may-alias 必须保持顺序。
:::

别名信息的来源有几种：指针分析（points-to）、类型基别名分析（type-based alias analysis，TBAA）、`restrict` 限定、数组下标范围、逃逸分析。C 的 `restrict` 是程序员给编译器的承诺：在该指针的生存期内，通过它访问的对象不会被其他指针访问。违反 `restrict` 是 UB，编译器可以据此重排；这也是 `restrict` 容易引发误编译的原因——承诺是程序员的责任，不是编译器的证明。

`volatile` 是另一个极端：它要求每次访问都真实发生，不能合并、不能删除、不能重排到其他 volatile 访问的另一侧。看两段 C 代码（同一文件，`clang -O2`，macOS arm64）：

```c
int g;
volatile int vg;

void spin(void) {
    for (int i = 0; i < 1000; i++) g++;
}

void spin_v(void) {
    for (int i = 0; i < 1000; i++) vg++;
}
```

这段代码用 `cc -std=c17 -Wall -Wextra -Werror` 编译通过。生成的汇编（只展示循环部分，指令集细节见第 8 章与《Linux 系统与内核》1.14–1.16）：

```asm
_spin:
    adrp x8, _g`PAGE
    ldr  w9, [x8, _g`PAGEOFF]
    add  w9, w9, #1000
    str  w9, [x8, _g`PAGEOFF]
    ret

_spin_v:
    mov  w8, #1000
    adrp x9, _vg@PAGE
LBB1_1:
    ldr  w10, [x9, _vg`PAGEOFF]
    add  w10, w10, #1
    str  w10, [x9, _vg`PAGEOFF]
    subs w8, w8, #1
    b.ne LBB1_1
    ret
```

非 volatile 的 `g++` 循环被折成一次 `g += 1000`；volatile 的 `vg++` 循环保留 1000 次 load/add/store。这不是「编译器偷懒」，而是 `volatile` 的可观察语义：每一次访问都必须发生。把 `volatile` 去掉，编译器有权合并；把普通变量当成 `volatile`，性能会大幅下降。

函数调用是最常见的优化屏障。没有函数摘要时，编译器必须假设调用可能读任意全局内存、写任意逃逸对象、抛异常、不返回。于是：调用前的 load 不能提到调用后，调用后的 store 不能提到调用前，调用本身不能被 DCE 删除（除非有 `pure`/`const`/`readnone` 属性）。这些属性是承诺：`readnone` 表示不读不写内存，`readonly` 表示只读，`pure` 在不同编译器里含义略有差异，使用前要查该版本的语义。

| 操作 | 可能读 | 可能写 | 能 DCE | 能跨它外提 |
|:--|:--|:--|:--|:--|
| 标量 load | 该变量 | 否 | 能（非 volatile） | 能（无写屏障） |
| 标量 store | 否 | 该变量 | 不能 | 不能跨读 |
| 数组 load | 该数组元素 | 否 | 仅当不越界且非 volatile | 仅当无别名写 |
| 数组 store | 否 | 该数组元素 | 不能 | 不能跨同数组读 |
| `volatile` 访问 | 是 | 是 | 不能 | 不能 |
| 未知调用 | 全局/逃逸对象 | 全局/逃逸对象 | 不能 | 不能 |
| `readnone` 调用 | 否 | 否 | 能（若不 trap） | 能（若不 trap） |

这张表要配合「trap 也是副作用」一起读。一个 `readnone` 函数如果可能除零或空指针解引用，仍然不能随便外提或删除；`readnone` 只说明内存效果，不说明不会 trap。

屏障与可重排性可以逐项列出来：

| 操作 | 可跨它外提 load | 可跨它下移 store | 可删除 | 备注 |
|:--|:--|:--|:--|:--|
| 纯算术 | 是 | 是 | 是 | 不 trap 时 |
| 标量 load | 是（不同变量） | 是（不同变量） | 是 | 非 volatile |
| 标量 store | 否（同变量） | 否（同变量） | 否 | 写有副作用 |
| 数组 load | 仅无别名写 | 仅无别名写 | 仅不越界 | 越界可能 trap |
| 数组 store | 否（可能别名） | 否 | 否 | 写有副作用 |
| volatile 访问 | 否 | 否 | 否 | 每次访问都要发生 |
| 未知调用 | 否 | 否 | 否 | 可能读写全局/抛异常 |
| `readnone` 调用 | 是 | 是 | 是（不 trap） | 只有内存效果为空 |

这张表把「别名」「副作用」「trap」三件事放在一起看。很多误优化不是不知道别名，而是把「不写内存」当成「没有副作用」，忽略了 trap 和异常。

::: ex 例 6.5.1 · volatile 不是同步原语 {#ex-compilers.2.6.5.1}
用 `volatile` 标志位在两个线程间传递「数据已就绪」，在 C/C++ 里是数据竞争（data race），行为未定义。`volatile` 只保证该访问不被优化掉，不保证与其他内存访问的顺序，也不保证原子性。正确做法是 C11 的 `atomic` 或互斥锁；编译器的优化屏障由原子操作的 memory order 提供，而不是由 `volatile` 提供。把 `volatile` 当同步用，在 x86 上可能「碰巧能跑」，在 ARM 上会因重排而失败。
:::

别名信息的来源可以列成一张表：

| 来源 | 精度 | 代价 | 典型用途 |
|:--|:--|:--|:--|
| 变量名相同 | 低 | 无 | 只适合局部标量 |
| 类型基（TBAA） | 中 | 低 | C/C++ 的不同类型指针 |
| 指针分析（points-to） | 中高 | 中 | 堆对象、逃逸分析 |
| `restrict` 限定 | 高（程序员承诺） | 无 | 手写高性能代码 |
| 下标范围 | 高 | 中 | 数组循环、向量化 |
| 版本化（loop versioning） | 高 | 运行时检查 | 别名不确定时 |

一个 points-to 的小例子：

```text
p = &a;        // p 指向 {a}
q = &b;        // q 指向 {b}
if (cond) p = q;
*p = 1;        // p 可能指向 a 或 b，弱更新两者
r = &a;
*r = 2;        // r 只指向 a，强更新 a
```

若不做流敏感分析，`p` 的指向集合是 {a, b}，对 `*p` 的写必须同时杀死 a 和 b 的定值/可用表达式。若 `r = &a` 之后没有再赋值，`*r` 可以强更新 a。精度来自「指针指向集合的大小」，而不是「指针变量有几个」。

优化屏障可以按强度排序：

1. 纯算术：无屏障，可重排、可删除（不 trap 时）。
2. 标量 load/store：只屏障同一变量，可跨不同变量重排。
3. 数组 load/store：屏障可能别名的数组元素。
4. `volatile` 访问：屏障所有 volatile 访问，不能合并/删除。
5. 未知调用：屏障全局内存、逃逸对象、异常边。
6. 原子/锁：屏障由 memory order 决定，不只是编译器，还包括 CPU。

`volatile` 的顺序语义常被误解。C 标准只要求 volatile 访问按抽象机的顺序发生，不要求它与其他非 volatile 访问之间有屏障；CPU 仍可能重排，编译器也可以把非 volatile 访问移到 volatile 访问的另一侧。把 volatile 当「万能屏障」，在单线程 MMIO 上可能够用，在多线程同步上一定不够。

原子操作提供的是另一套保证：`memory_order_relaxed` 只保证原子性，`acquire`/`release` 建立 happens-before，`seq_cst` 再加全局顺序。优化器对原子访问的处理与 volatile 类似（不能删除、不能合并），但语义更强：它参与数据竞争的定义，乱序会被内存模型禁止。第 9 章会把 C11 内存模型展开；本节只记结论：volatile 不是同步，原子才是。

别名与副作用分析的精度直接决定优化能走多远。保守到「任何 store 杀死所有 load」，程序正确但性能差；激进到「只按变量名判断」，就会像 6.2 节的 `a[0]` 反例一样误优化。工程上的折中是：对局部数组、`alloca`、不会逃逸的对象做精确分析；对全局指针、外部调用、`volatile` 做保守处理；把 `restrict` 和 `readonly` 当作程序员提供的额外信息，但在跨模块边界重新验证。

还有一个容易漏掉的屏障是异常。一个可能抛异常的调用不只是内存屏障，还是控制流屏障：它可能从循环中间跳到异常处理器，跳过后面的指令。把指令从调用后提到调用前，异常发生时的状态就变了。异常边、`longjmp`、信号处理都属于这一类；分析必须把它们建模成额外的后继边，否则「支配出口」的判断也会错。

## 6.6 pass 顺序、相位与收敛 {#sec-compilers.2.6.6}

单个优化很少单独运行。一个函数要依次经过内联、常量传播、折叠、DCE、LICM、GVN、寄存器分配等十几个 pass；每个 pass 都读取前一个 pass 的分析结果，又产生新的优化机会。pass 顺序（phase ordering）因此成为一个独立的工程问题：同样的 pass 集合，换个顺序，最终的代码可能不同。

一个 pass 通常声明三件事：它读取哪些分析、它修改什么、它保留哪些分析。分析结果缓存（analysis cache）根据「保留」声明决定是否失效。若一个 pass 修改了 CFG 却声称保留了支配树，后面的 LICM 会读到过期的支配关系，做出错误的「支配出口」判断。这类 bug 不会在 pass 内部崩溃，只会在很远的地方产生错误代码，极难定位。

| 顺序 | 创造的机会 | 破坏的机会 |
|:--|:--|:--|
| 内联 → 常量传播 | 常量参数进入被内联函数体，分支可折 | 无 |
| 常量传播 → 内联 | 调用点变少，但常量参数看不到 | 内联后仍需再传播 |
| LICM → 常量传播 | 外提的指令可折成常量 | 折叠可能让外提变得不必要 |
| 常量传播 → LICM | 常量操作数让更多指令不变 | 外提后常量传播看不到循环体 |
| DCE → 内联 | 无 | 内联产生的死代码要等下一轮 DCE |
| 内联 → DCE | 内联暴露的死代码立即清理 | 无 |
| 分支化简 → DCE | 不可达块里的死代码被删 | DCE 先跑时删不掉不可达块 |

这张表没有「唯一正确顺序」。真实编译器用固定点驱动（fixed-point driver）：按一个顺序跑一轮，如果还有 pass 报告「改变了 IR」，再跑一轮，直到没有变化或达到上限。固定点驱动能消除大部分顺序差异，但增加编译时间，也可能让某些 pass 反复震荡。

实验用一个小程序演示顺序差异。程序 B0 有常量条件 `c=1`，B1 打印 12，B2 打印 99：

```text
顺序 A: fold -> simplify -> dce
  B0: goto B1
  B1: print 12
  B1: goto B3
  B3: ret 0

顺序 B: dce -> fold（不再 simplify）
  B0: c = 1
  B0: if c goto B1 else B2
  B1: x = 12
  B1: print 12
  B1: goto B3
  B2: print 99
  B2: goto B3
  B3: ret 0
A 指令数=1 B 指令数=4 输出一致=True
B 再跑一轮 simplify+dce 后指令数=1，与 A 文本相等=True
```

计数只统计非终止指令（goto/ret 不算），所以 A 的 "1 条" 指唯一一条 `print`。A 在折叠后立即化简 CFG，B2 变成不可达并被删除；B 先跑 DCE，此时 B2 在 CFG 上仍然可达，DCE 不敢删它的 `print`，折叠后也没有再化简，所以 B2 留在代码里。两者的可观察输出相同（B2 不会执行），但代码尺寸不同。B 再跑一轮 simplify+dce，结果与 A 完全相等。这说明：顺序影响中间结果与总工作量，固定点驱动可以把差异收敛掉，但要多花一轮。

收敛（convergence）不是自动的。一个 pass 如果把 `x + 0` 改成 `x`，另一个 pass 如果把 `x` 改回 `x + 0`（例如为了规范化），两个 pass 会互相触发，永不收敛。真实编译器要求每个 pass 的变换是单调的或规范化的：要么总是朝同一个方向简化，要么有明确的优先级，不能形成环。调试构建里可以给 pass 管理器加「最大轮数」并在超限时 dump IR，定位震荡来源。

一条完整流水线通常分成几个相位（phase）：

1. 规范化：把 IR 变成统一形式，便于后续匹配。
2. 过程间：内联、函数特化、去虚化。
3. 过程内：常量传播、折叠、DCE、LICM、GVN。
4. 循环优化：展开、向量化、循环交换。
5. 后端准备：指令选择、寄存器分配、调度。
6. 清理：CFG 化简、死块删除、调试信息修正。

相位之间的顺序比相位内部的顺序更稳定：先过程间再过程内，先循环优化再寄存器分配。把 LICM 放到寄存器分配之后，外提的指令没有寄存器可用，收益会被溢出抵消；把内联放到寄存器分配之后，调用点已经消失，无法再利用参数常量。

::: method 方法 6.6.1 · 设计一条 pass 流水线
1. 先列每个 pass 的输入/输出：读哪些分析、改哪些 IR 结构、保留哪些分析。
2. 把「创造机会」的 pass 放在「消费机会」的 pass 前面：内联在常量传播前，常量传播在折叠/DCE 前，LICM 在寄存器分配前。
3. 把「清理型」pass 放在最后：DCE、CFG 化简、死块删除。
4. 用固定点驱动包住会产生新机会的 pass 组，设最大轮数并在超限时报警。
5. 对每个 pass 记录它修改 IR 的次数；用「本轮是否有变化」决定是否继续，而不是用固定轮数。
6. 用差分执行验证整条流水线，而不是只验证单个 pass。
:::

pass 顺序还影响编译时间。把昂贵的过程间分析放在早期，可能分析了很多随后被内联删掉的代码；把内联放在早期，能让后续分析只处理最终代码。经验规则是「先做能减少代码量的变换（内联小函数、DCE），再做需要精确分析的重排」；但内联也可能增加代码量，所以要用预算控制。

一条最小流水线可以写成显式的 pass 列表，每个 pass 声明它修改什么：

```python
PIPELINE = [
    ("inline",      {"preserves": {"cfg"}}),
    ("constprop",   {"preserves": {"cfg"}}),
    ("fold",        {"preserves": {"cfg"}}),
    ("licm",        {"invalidates": {"domtree", "loopinfo"}}),
    ("dce",         {"preserves": {"cfg"}}),
    ("simplify_cfg",{"invalidates": {"domtree", "loopinfo", "cfg"}}),
]

def run_pipeline(fn):
    while True:
        changed = False
        for name, effects in PIPELINE:
            changed |= PASSES[name](fn)
            if "invalidates" in effects:
                fn.drop_analyses(effects["invalidates"])
        if not changed:
            return fn
```

它验证「固定点驱动 + 分析失效」。预期：内联后常量传播能立刻看到新常量；LICM 之后支配树被丢弃，下一轮重新计算；`simplify_cfg` 改动 CFG 后所有 CFG 相关分析失效。若忘记 `drop_analyses`，下一轮 LICM 会读到过期的支配关系，可能把指令提到不支配出口的位置。

分析失效的规则可以列成表：

| 分析 | 依赖 | 何时失效 |
|:--|:--|:--|
| 支配树 | CFG | 增删块、改边、拆分临界边 |
| 循环信息 | 支配树 + CFG | 支配树失效时 |
| 活跃变量 | CFG + 指令 def/use | 改指令、改边 |
| 别名/points-to | 内存写、对象布局 | 新增指针赋值、内联 |
| 常量传播 | def-use、CFG | 改指令、改边 |
| 内联摘要 | 调用图、函数体 | 函数体变化、可见性变化 |

一个 pass 如果只改指令、不改 CFG，应声明「保留支配树/循环信息」；如果改了 CFG，必须让它们失效。声明错的代价不是崩溃，而是后续 pass 用错误信息做优化，产生难以复现的 miscompile。调试构建可以在每次分析查询时校验版本号，版本不匹配就重算并报警。

震荡（oscillation）有几种常见来源：

- 两个 pass 互相「规范化」同一个表达式，谁也不肯停。
- 一个 pass 把指令移到新块，另一个 pass 把它移回来。
- 常量传播把 `x` 折成常量，DCE 删掉 `x`，下一轮又因为某个 use 重建 `x`。
- 内联与函数提取（outlining）互相抵消。

解决办法不是「多跑几轮」，而是让每个变换有明确的方向：要么单调减少指令数/代码尺寸，要么有优先级和上限。固定点驱动的最大轮数只是安全网，不是正确性保证。

pass 顺序还会影响分析精度。先内联能让别名分析看到更多具体对象，先 DCE 能减少分析的对象数量；两者都把「分析什么」改变了。经验规则是「先做能减少代码量且不改变语义的变换，再做依赖精确分析的重排」，但这条规则也有反例：内联可能增加代码量，却让后续常量传播删掉更多代码。最终还是要用基准和差分测试验证，而不是靠规则推导。

最后，pass 顺序不是语言规范的一部分。同一份 C 代码在 `-O0`、`-O2`、`-O3` 下经过的 pass 集合不同，结果可以不同（只要都保持定义行为）。调试一个「某个优化级别才出现」的 bug 时，先确认是哪个 pass 引入的，再谈顺序；不要假设 `-O2` 只是「多跑了几遍 `-O1`」。

## 6.7 可观察证据：优化报告与差分测试 {#sec-compilers.2.6.7}

优化是否发生、为什么没发生，需要证据。LLVM 提供优化报告（optimization remarks）：`-Rpass` 报告成功的变换，`-Rpass-missed` 报告「本可以但没做」，`-Rpass-analysis` 报告分析结论。`-fsave-optimization-record` 把报告写成 YAML/JSON，便于脚本比较。GCC 有 `-fopt-info` 系列，Rust 有 `-Z` 系列的调试输出（ nightly）。

报告的作用不是「证明优化正确」，而是回答「这个 pass 有没有跑、为什么没跑」。例如内联报告里的 cost 与 threshold 可以解释「为什么这个调用点没内联」：cost 超过阈值，或调用者太大。没有报告时，只能靠反汇编猜，效率低且容易误判。

差分测试（differential testing）是另一类证据：同一程序用两种配置执行，比较可观察行为。常见组合：

| 对比 | 能发现 | 盲区 |
|:--|:--|:--|
| `-O0` vs `-O2` | 优化引入的语义错误 | 两边都错、UB 程序 |
| 解释器 vs 编译产物 | IR 语义与后端不一致 | 解释器未覆盖的指令 |
| clang vs gcc | 单一编译器的系统性错误 | 两边共享的前端错误 |
| 优化前 vs 优化后（同 IR） | 单个变换的错误 | 变换未触及的路径 |
| 多组输入 + 属性 | 输入相关的错误 | 未生成的输入 |

实验用的是第四种：同一份 TAC，优化前与优化后都跑解释器，比较 `(状态, 输出, 返回值)`。安全优化必须全部 `match=True`；故意写错的优化必须 `match=False`。真实汇总：

```text
安全优化全部 match；四个故意错误全部按预期 mismatch；顺序差异在固定点后消失
```

差分测试的前提是「程序有定义行为」。若程序本身有 UB，`-O0` 与 `-O2` 的输出不同不说明编译器有 bug；若程序读未初始化内存，两次运行可能碰巧相同，也可能不同。测试框架要先过滤 UB，或只在定义行为上比较。第 9 章会把 UB 与 sanitizer 展开。

::: ex 例 6.7.1 · 一次误编译的缩小过程 {#ex-compilers.2.6.7.1}
某程序在 `-O2` 下输出错误，`-O0` 正确。第一步，用 `-opt-bisect-limit=N` 二分 pass 序列，找到引入错误的 pass；第二步，用 `-print-after-all` 或 `-print-changed` 对比该 pass 前后的 IR；第三步，把触发错误的函数抽成最小用例，去掉无关代码；第四步，在最小用例上确认是分析错误还是变换错误；第五步，加回归测试，并在修复后跑一遍差分与 fuzz。缩小的目标不是「找到一行代码」，而是「得到一个可以独立解释的 IR 差异」。
:::

优化报告也能用于差分：把两个版本的 remark 文件排序后 diff，能看到「哪个内联决定变了」「哪个循环没被向量化」。这比直接 diff 汇编稳定，因为汇编受寄存器分配、调度等下游 pass 影响，噪声大。

不过，报告本身也可能骗人。一个 pass 报告「已内联」，不代表内联后的代码被保留；后续 pass 可能把它删掉。一个 pass 报告「未内联」，可能是因为成本模型，也可能是因为可见性、递归、异常。读报告时要看完整字段（cost、threshold、reason），不能只看一行。

优化报告的常用开关：

| 开关 | 作用 | 输出量 |
|:--|:--|:--|
| `-Rpass=inline` | 报告成功的内联 | 每个调用点一行 |
| `-Rpass-missed=inline` | 报告没内联的调用点 | 每个调用点一行 |
| `-Rpass-analysis=inline` | 报告分析原因（成本、可见性） | 较多 |
| `-fsave-optimization-record` | 把报告写成 YAML | 文件 |
| `-foptimization-record-file=` | 指定输出文件 | 文件 |
| `-print-after-all` | 每个 pass 后 dump IR | 很大 |
| `-opt-bisect-limit=N` | 只跑前 N 个 pass | 用于二分 |

优化记录的一个片段（结构示意，字段随 LLVM 版本变化）：

```yaml
--- !Passed
Pass:            inline
Name:            Inlined
DebugLoc:        { File: inl.c, Line: 4, Column: 38 }
Function:        sum_squares
Args:
  - String:      'square'
  - String:      ' inlined into '
  - String:      'sum_squares'
  - Cost:        '-15030'
  - Threshold:   '337'
...
```

它验证「报告是可解析的结构，不只是给人看的字符串」。预期：脚本可以按 Pass/Name/Function 过滤，统计每个函数的内联次数；字段名变化时要按版本适配，不能假设永远叫 Cost。

差分测试的骨架可以写成一个独立脚本：

```python
def differential(prog, inputs):
    before = run(prog, inputs)              # 优化前
    after = run(optimize(prog), inputs)     # 优化后
    if before != after:
        return ("MISMATCH", inputs, before, after)
    return ("ok", inputs, before, after)

for inp in boundary_inputs():
    r = differential(prog, inp)
    if r[0] == "MISMATCH":
        print(r)
```

它验证「同一输入、同一可观察行为」。预期：安全优化全部 ok；故意错误的优化在边界输入上 MISMATCH。`boundary_inputs` 至少包含零次循环、空数组、除数为 0、别名写入、参数有副作用五类。

缩小（reduction）的步骤可以固定成五步：

1. 确认失败与优化级别相关：`-O0` 通过、`-O2` 失败。
2. 用 `-opt-bisect-limit` 二分，找到第一个引入失败的 pass。
3. 用 `-print-after-all` 对比该 pass 前后的 IR，定位被改错的指令。
4. 把触发函数抽成最小用例，删掉无关代码，保留失败。
5. 加回归测试，并在修复后重跑差分与 fuzz。

| 证据 | 回答的问题 | 不能回答的问题 |
|:--|:--|:--|
| 优化报告 | pass 是否跑、为什么跑/没跑 | 结果是否正确 |
| 反汇编 | 最终机器码长什么样 | 源码级语义是否保持 |
| 差分执行 | 这组输入上行为是否一致 | 未测输入、UB 程序 |
| 形式化证明 | 所有输入上是否保持语义 | 编译器/硬件是否可信 |
| 基准测试 | 是否更快 | 是否仍然正确 |

读优化报告时，常见的字段与误读：

| 字段/现象 | 含义 | 常见误读 |
|:--|:--|:--|
| `Cost` | 成本模型的估算值 | 当成真实周期数 |
| `Threshold` | 当前优化级别的阈值 | 当成固定标准 |
| `Pass: inline` | 这是内联 pass 的报告 | 以为所有内联都成功 |
| `-Rpass-missed` | 本可以但没做的变换 | 以为一定是 bug |
| `-Rpass-analysis` | 分析结论/拒绝原因 | 当成最终裁决 |
| 报告为空 | pass 没跑或没有匹配 | 以为优化已生效 |
| 同一调用点多次报告 | 多轮 pass 各报一次 | 以为重复内联 |

报告的用途是定位「哪个 pass、在哪个调用点、因为什么」；它不证明结果正确，也不给出性能数字。把报告和基准、反汇编、差分测试结合，才是完整证据。

这张表说明为什么优化验证要多种证据叠加：报告证明「跑了」，反汇编证明「生成了什么」，差分证明「这组输入一致」，基准证明「值得」。任何单一证据都不足以支撑「优化正确」。

测试输入至少覆盖这几类，否则差分测试很容易「全绿但没测到」：

| 输入类别 | 目的 | 本章对应 |
|:--|:--|:--|
| 零次循环 | 检查 LICM 是否引入 trap | licm_trap, n=0 |
| 别名写 | 检查 load 外提 | licm_alias |
| 除数为 0 | 检查折叠与 DCE | div_zero |
| 副作用调用 | 检查 DCE | side_effect |
| 参数求值两次 | 检查内联 | f(next()) |
| 常量分支 | 检查 pass 顺序 | pipeline_order |
| 空/边界数组 | 检查越界与 trap | 扩展练习 |

差分测试的盲区要写在测试报告里，而不是藏在脚注：

- 两边都错：比较相等不代表正确。
- UB 程序：任何结果都「合法」，比较无意义。
- 未覆盖输入：边界以外的路径没测到。
- 非确定性：并发、时间、随机数会让两次运行不同。
- 浮点：NaN 比较、舍入模式、扩展精度可能产生假差异。

把盲区写出来，读者才知道「测试通过」意味着什么。这也是本书对证据分级的要求：E2（可复现命令）只能证明「这个输入上一致」，不能证明「所有输入都正确」。

差分测试的覆盖面靠输入生成。手写几个边界输入（零次循环、空数组、除数为 0、别名）比随机一百个「正常值」更有效。第 10 章会把生成器、属性测试、fuzzing 与收缩组合起来；本节只要求每个变换至少有一个正例、一个边界反例、一个副作用反例。

## 6.8 agent 错误：把除以零折进常量与错误内联 {#sec-compilers.2.6.8}

这一节复盘三类 agent 生成优化代码时的典型错误。它们的共同点是：变换在「正常输入」上完全正确，在边界输入上改变可观察行为；测试如果只覆盖正常值，全部通过。

**错误一：把 `100 / 0` 折成 0。** agent 写常量折叠时，对除法只判断「两个操作数都是常量」，没有判断除数是否为零：

```text
if op == "/" and isinstance(a, int) and isinstance(b, int):
    return a // b          # b == 0 时抛异常，或被 agent 改成返回 0
```

症状是程序不再 trap。实验的真实输出：

```text
--- div_zero 错误折叠 ---
  B0: d = 0
  B0: q = 0
  B0: print 0
  B0: ret q
正确语义=('trap:div0', (), None) 错误折叠=('ok', (0,), 0) 差异=True
```

根因是把「常量」等同于「可折」，忽略了 IR 的 trap 语义。发现手段是差分执行：原始程序 trap，优化后正常返回，差异立刻可见；若测试只比较「程序没崩」，还会以为优化成功。修复是让折叠函数在除数为 0 时返回 NAC（不是常量），并在 DCE 中保留可能 trap 的除法。

**错误二：把 `print` 当死代码删掉。** agent 的 DCE 用「有 dst 且 dst 无使用者」判断死代码，遇到没有 dst 的 `print` 时，把「没有 dst」误当成「没有副作用」：

```text
if ins.dst is None or ins.dst not in live:
    continue        # 错误：print/store 也被删了
```

实验的真实输出：

```text
--- side_effect 错误 DCE ---
  B0: ret 0
正确语义=('ok', (1, 2), 0) 错误 DCE=('ok', (), 0) 差异=True
```

根因是副作用模型缺失。修复是把指令分成「纯」「可能 trap」「有副作用」三类，只有纯指令能按使用者删除；`print`、`store`、`volatile` 读、未知调用都必须保留。

**错误三：内联时直接替换参数表达式。** agent 在 AST 层做内联，把 `f(next())` 的 `next()` 直接代进函数体，而函数体用了两次参数：

```text
f(x) { return x + x; }
call: y = f(next());
错误内联: y = next() + next();     // next 执行两次
正确内联: t = next(); y = t + t;   // next 执行一次
```

症状是副作用次数改变（计数器多一次、随机数不同、IO 重复），或求值顺序改变导致异常提前/延后。根因是把「复制文本」当成「内联」，没有保持实参的求值次数与顺序。修复是先把每个实参求值到临时变量，再替换函数体里的形参；异常边、`volatile`、`alloca` 也要单独处理。

三类错误都可以用同一套「效果分类」修复。先给每条指令标注效果：

```python
PURE = {"const", "copy", "add", "sub", "mul", "cmp"}
TRAPS = {"div", "load"}          # 可能 trap，即使结果未使用
EFFECTS = {"print", "store", "call", "volatile"}

def removable(ins, live):
    if ins.op in EFFECTS:
        return False
    if ins.op in TRAPS:
        return ins.is_provably_safe() and ins.dst not in live
    return ins.dst not in live
```

它验证「纯指令按使用者删、trap 指令额外证明安全、副作用指令永不删」。预期：`dead = 99` 被删；`q = 100 / 0` 保留；`print` 保留。把 `TRAPS` 合并进 `PURE`，就是实验里的错误 DCE。

内联的修复则是「先把实参变成临时变量」：

```python
def inline_call(call, callee):
    temps = []
    for arg in call.args:                 # 每个实参只求值一次
        t = new_temp()
        emit(("assign", t, arg))
        temps.append(t)
    body = substitute(callee.body, dict(zip(callee.params, temps)))
    emit_all(body)
    return callee.ret_var
```

它验证「求值次数与顺序」。预期：`f(next())` 只生成一次 `next()` 调用；函数体里两次使用参数，用的是同一个临时变量。若直接 `substitute` 原始表达式，会生成两次 `next()`。

评审 agent 生成的优化代码，可以按这张清单逐项问：

| # | 检查 | 不合格的表现 |
|--:|:--|:--|
| 1 | 折叠规则是否检查 trap | `100/0` 被折成 0 |
| 2 | DCE 是否区分纯/副作用 | `print`、`store` 被删 |
| 3 | 指令是否有 `is_provably_safe` | 除零/越界被当成纯指令 |
| 4 | 内联是否实参临时化 | `next()` 执行两次 |
| 5 | 内联是否保留异常边 | landing pad 丢失 |
| 6 | LICM 是否检查支配出口 | 零次循环触发 trap |
| 7 | 别名检查是否看内存写 | `a[0]` 跨 `a[i]` 写外提 |
| 8 | 是否有边界输入测试 | 只测正常值 |

这张表与 6.2–6.5 的规则一一对应。评审时不需要重新推导所有优化，只要抽查每条规则的「前提 → 变换 → 证据」是否齐全。

最后，把三类错误放进「可观察事件」框架：除零是 trap 事件，print 是输出事件，参数副作用是调用/写事件。优化的合法性等价于「事件序列不变」。用这个框架检查新写的变换，比记具体 bug 更不容易漏。三类错误的共同检查表：

| 检查 | 错误一 | 错误二 | 错误三 |
|:--|:--|:--|:--|
| 边界输入 | 除数为 0 | 无输出的程序 | 参数有副作用 |
| 差分执行 | trap vs 正常返回 | 输出丢失 | 副作用次数不同 |
| IR 语义 | trap 是可观察事件 | print 是可观察事件 | 求值顺序/次数 |
| 修复位置 | 折叠函数 | 副作用分类 | 实参临时化 |
| 回归测试 | `100/0`、`x/0` | 带 print 的程序 | `f(next())` |

| 可观察事件 | 例子 | 优化能否改变 |
|:--|:--|:--|
| 返回值 | `return x` | 不能 |
| 输出 | `print`、文件写 | 不能（顺序也不能变） |
| trap | 除零、越界、空指针 | 不能新增或删除 |
| 异常 | `throw`、`longjmp` | 不能改变类型/顺序 |
| volatile 访问 | MMIO 读写 | 不能合并/删除 |
| 原子操作 | `atomic` 读写 | 不能违反 memory order |
| 未定义行为 | 有符号溢出、数据竞争 | 允许任意，但不应依赖 |

这张表是「可观察行为」的操作化定义。优化规则只要逐项检查「这个事件会不会被新增、删除、重排」，就能覆盖大多数边界；剩下的难点是「哪些事件在语言层面可观察」，那要查语言标准，不能靠编译器实现猜。

优化规则可以写成一条通用形式：**变换前后的程序，在所有定义行为上具有相同的可观察事件序列**。可观察事件包括返回值、输出、trap、volatile 访问、异常；不包含未被观察的临时值。把这条规则贴在 code review 的检查表上，比记住十个具体 bug 更有效。

agent 生成的优化代码还有一个系统性风险：它倾向于「让测试通过」，而不是「让规则完整」。例如发现 `100/0` 让测试崩溃，就把结果改成 0 让测试不崩；发现 print 让输出比较失败，就把 print 删掉让输出为空。评审时要问「这条规则的前提是什么」，而不是「测试过没过」。本章的三个反例都来自这种「绕过症状」的修改。

母本对「内联」的讨论多集中在 C++ 的 `inline` 关键字与 ODR，对成本模型的细节着墨较少；本章把成本模型与可见性分开讲，是因为它们对应两个不同的问题：值不值得、允不允许。把两者混在一起，容易出现「明明加了 `inline` 却没内联」的误解。

本章的母本对应不追求「一本对一节」，而是按机制拆分：支配/循环、LICM、内联、常量折叠、DCE、pass 顺序分别对应不同母本的章节。这样做的代价是读者需要在多本书之间跳转；收益是每个机制都能找到更详细的原始讨论，而不是被压缩成一段综述。

读母本时建议带着本章的三个问题：这个变换的前提是什么？它在哪里可能失效？作者用什么证据说明它有效？大多数教材对第一个问题讲得清楚，对第二个问题讲得较少，第三个问题往往留作练习。本章的实验与反例就是补第二、第三个问题。

母本之间的侧重点差异也值得注意：编译器教材偏重算法与数据流，C++ 书籍偏重语言规则与可见性，Rust 文档偏重常量求值与 UB。把三者放在一起读，才能同时回答「怎么算」「允不允许」「算错了谁负责」。本章的顺序是先机制、再边界、最后证据，正是按这三个问题组织的。

母本讲优化时通常以「变换能变快」为主线，较少展开「变换在什么条件下不合法」。本章把安全条件放在每个变换的定义里，并用四个可观察反例验证；代价是篇幅更多花在边界上，而不是在算法细节上。

> **下一站**：第 7 章把这些优化后的 IR 交给寄存器分配。你会看到活跃区间如何变成冲突图、图着色如何溢出、调用点如何破坏 caller-saved 寄存器，以及为什么「优化越多，分配越难」。

## 6.10 本章陷阱（8–15 条） {#sec-compilers.2.6.10}

::: errata 本章陷阱
1. **把「循环不变」当成「可以外提」**：现象是零次循环时触发除零或越界；原因是漏了「不 trap」或「支配所有出口」；修复是给每个候选指令标注 speculatable，非 speculatable 的只在支配出口时外提。  
2. **只看变量名判断别名**：现象是 `a[0]` 被提到写 `a[i]` 之前，读到旧值；原因是数组元素写不改变数组变量的定值；修复是看内存写与 may-alias，循环内有同数组 store 就不外提 load。  
3. **把 volatile 当普通变量**：现象是设备轮询循环被折成一次读，或日志被删；原因是 volatile 语义要求每次访问都发生；修复是把 volatile 访问标为副作用屏障，禁止合并/删除/重排。  
4. **DCE 用「有 dst 且无使用者」判断死代码**：现象是 `print`、`store` 被删；原因是没有副作用分类；修复是纯/可能 trap/有副作用三分类，只有纯指令能按使用者删。  
5. **折叠除法不检查除数**：现象是 `100/0` 被折成 0，trap 消失；原因是把常量等同于可折；修复是除数为 0 返回 NAC，DCE 保留可能 trap 的除法。  
6. **折叠有符号溢出**：现象是 C 程序在 `-O2` 下行为改变；原因是借宿主整数做回绕，而 C 的有符号溢出是 UB；修复是按 IR/语言语义折叠，不能假设回绕。  
7. **内联时直接替换参数表达式**：现象是 `f(next())` 里 `next()` 执行两次；原因是没有先求值到临时变量；修复是实参临时化，保持求值次数与顺序。  
8. **内联忽略异常与调试信息**：现象是异常栈/行号错位，或 landing pad 丢失；原因是只复制了正常路径；修复是复制异常边、保留 debug location，必要时拒绝内联。  
9. **无预算的内联**：现象是二进制膨胀、icache 抖动、编译变慢；原因是没有尺寸/深度上限；修复是成本模型 + 内联预算 + 递归深度上限。  
10. **pass 修改 CFG 却声明保留支配树**：现象是后续 LICM 用过期支配关系做错误外提；原因是分析缓存未失效；修复是显式声明 preserved analyses，CFG 改动后强制重算。  
11. **pass 顺序固定死、不做固定点**：现象是内联后的常量没被传播，或 DCE 没清掉新死代码；原因是只跑一轮；修复是用「有变化就再跑」的驱动，并设最大轮数。  
12. **diff 测试比较了 UB 程序**：现象是 `-O0` 与 `-O2` 输出不同就报 bug；原因是程序本身有未定义行为；修复是先过滤 UB，或只在定义行为上比较。  
13. **只看优化报告就认为优化有效**：现象是 remark 说内联了，性能却下降；原因是代码膨胀/寄存器压力；修复是同时看代码尺寸、icache、实际基准，而不是只看 pass 报告。  
14. **把内联当成纯文本替换**：现象是参数有副作用时执行次数改变，或局部变量重名；原因是没有临时化实参、没有变量改名；修复是先求值实参到临时变量，再替换形参，并做 alpha 重命名。  
15. **用固定轮数代替固定点**：现象是某些函数优化不彻底，或换一个输入就多跑一轮；原因是用「跑 3 遍」代替「跑到不变」；修复是用变化标志驱动，设最大轮数作为安全网，超限时 dump IR。
:::

::: method 即时自测 · 6
**Q1** 一个循环体里的 `t = k * 3` 满足不变性，但循环可能零次执行。它一定能外提吗？还需要什么条件？

**Q2** DCE 看到 `q = 100 / d` 的结果无人使用，能否删除？分 d 是常量 0、常量 5、未知变量三种情况讨论。

**Q3** 内联 `f(next())` 时，为什么不能把 `next()` 直接代进函数体？给出一个函数体使用参数两次的例子，并写出正确做法。

**Q4** 实验里顺序 A 得到 1 条指令，顺序 B 得到 4 条，但两者输出一致。这说明 pass 顺序的什么问题？固定点驱动如何消除差异？

::: sol 答案
**A1** 不一定。`k * 3` 是纯算术、不 trap，可以推测执行，所以零次循环外提也安全；若把 `k * 3` 换成 `100 / d`，除法可能 trap，循环体又不支配出口，就不能外提。条件 1（不变）只说明值不变，条件 3（可推测或支配出口）才说明提前执行安全。

**A2** d 是常量 0 时不能删，除法会 trap；d 是常量 5 时可以删，除数非零、不 trap；d 是未知变量时不能删，可能为 0。DCE 的删除条件包含「不 trap」，不只是「无使用者」。

**A3** 因为实参有副作用，直接替换会把它执行多次。例：`f(x) { return x + x; }`，调用 `f(next())`；错误内联得到 `next() + next()`，`next()` 执行两次；正确做法是先 `t = next()`，再 `t + t`，只执行一次。

**A4** 说明顺序会影响中间代码尺寸与总工作量，但固定点驱动最终会收敛到同一结果。A 在折叠后立即化简并删除不可达块；B 先 DCE 时 B2 仍可达，折叠后没再化简，所以多留了不可达代码。B 再跑一轮 simplify+dce 就与 A 相等。
:::
