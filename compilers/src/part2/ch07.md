第 6 章结束时，你手里有一段做过内联、常量传播和循环优化的 TAC。它仍然假设临时变量无限多：`t17 = t3 * t9` 想写多少个就写多少个。后端的第一个现实约束是寄存器只有十几个，第二个约束是指令集只提供有限的寻址与运算形式。把这两个约束同时满足，就是本章的两件事：指令选择决定「用哪条指令覆盖哪棵表达式树」，寄存器分配决定「哪个值住在哪个寄存器或栈槽」。

这两件事不能完全分开。指令选择偏好三操作数或带内存操作数的形式，会改变同时活跃的值的数量；寄存器分配把值放进栈槽，又会迫使指令选择退回到「先 load 再算」。真实的编译器通常在 IR 上先做选择，再分配，再在分配结果上做局部修补；也有的后端先分配再选择。本章按「选择 → 区间 → 着色/线性扫描 → 调用约束 → 调度 → 目标描述 → 验证」的顺序讲，但每一节都会指出顺序反转时的边界。

一个具体的反例。实验程序 `calls` 有 10 个虚拟寄存器、4 个可用寄存器，中间两次调用。假设分配器只看「同时活跃」，不看调用约定，它会把跨调用的 `d` 放进 `%rcx`、把 `t` 放进 `%rax`。被调用函数按 ABI 可以随意改写这两个寄存器；模拟器把破坏后的值继续用于后续加法，参考答案 145，分配后的程序算出 183。这个错误不会被汇编器发现，也不会在「被调用函数恰好保留了 rcx」的测试里出现。

本章实验在 `experiments/ch07/`，入口命令：

```bash
python3 experiments/ch07/regalloc_lab.py --program calls --dump-intervals --dump-code
```

它不依赖编译器，只用 Python 标准库；输出包含活跃区间、冲突图、两种分配结果、溢出槽、已分配指令序列，以及与未分配 IR 解释器的 200 组输入对拍。后面的真实汇编证据用 `clang -target x86_64-apple-darwin` 生成，再用 `llvm-objdump` 核对；执行只作为可选的第二证据，不作为理解前提。

## 7.1 指令选择：树覆盖、模式与成本 {#sec-compilers.2.7.1}

先把「逐条翻译」的直觉打掉。TAC 里 `t1 = a + b` 是一条指令，到了 x86-64 上，它可能变成 `leal (%rdi,%rsi), %eax`，也可能变成 `movl %edi,%eax` 加 `addl %esi,%eax`，还可能因为 `a` 在栈上而变成「load + add」。选择哪一组，取决于上下文、寄存器约束和成本模型。用一个最小 C 文件观察 clang 的实际选择：

```c
int add2(int a, int b) { return a + b; }
int scale(int a, int b, int c) { return (a + b) * c; }
int idx2(int *p) { return p[2]; }
int idxv(int *p, int i) { return p[i] + 1; }
int scaled_idx(int *p, int i) { return p[i] * 3 + 5; }
```

在 macOS arm64 上用交叉目标生成 x86-64 汇编：

```bash
clang -target x86_64-apple-darwin -O1 -S -o - sel.c
```

真实输出（节选，删除 .cfi 与注释）：

```asm
_add2:
    pushq   %rbp
    movq    %rsp, %rbp
    leal    (%rdi,%rsi), %eax
    popq    %rbp
    retq

_scale:
    pushq   %rbp
    movq    %rsp, %rbp
    leal    (%rdi,%rsi), %eax
    imull   %edx, %eax
    popq    %rbp
    retq

_idx2:
    pushq   %rbp
    movq    %rsp, %rbp
    movl    8(%rdi), %eax
    popq    %rbp
    retq

_scaled_idx:
    pushq   %rbp
    movq    %rsp, %rbp
    movslq  %esi, %rax
    movl    (%rdi,%rax,4), %eax
    leal    (%rax,%rax,2), %eax
    addl    $5, %eax
    popq    %rbp
    retq
```

同样四个函数，在 `-O0` 下 `add2` 会先把两个参数存进 `-4(%rbp)` 和 `-8(%rbp)`，再从内存读出来相加，至少四条指令；`-O1` 只用一条 `leal`。这不是「优化开了就更快」的空话，而是选择器把「参数在寄存器里」这个事实和「LEA 可以一次算 base+index」这个模式匹配上了。`-O0` 仍然做了指令选择，只是它的模式优先把每个临时变量落到栈槽，于是选择结果被内存约束主导。

::: def 定义 7.1.1 · 模式、覆盖与指令选择 {#def-compilers.2.7.1.1}
给定一棵以 IR 运算为结点的表达式树，**模式**（pattern）是带有操作数约束的指令模板，例如「`add` 的两个源都在寄存器，结果写寄存器」或「`load` 的地址是 `base + index*4`」。**覆盖**（tiling）是把树的结点划分成若干模式实例，使每个结点恰好属于一个实例。**指令选择**（instruction selection）是在所有合法覆盖中按成本函数取最小代价的那一个。
:::

模式不是「指令助记符」的同义词。`leal (%rdi,%rsi), %eax` 的模式至少包含三条约束：两个源是 64 位寄存器；结果写 32 位寄存器；不读写内存、不修改标志位。最后一条常被忽略：因为 LEA 不改标志位，选择器可以在一条比较和一条条件跳转之间插入它，而不破坏 `cmp` 设置的标志。若换成 `addl`，同样的插入就不合法。

把 `(a + b) * c` 画成树，两种覆盖的差别一眼可见：

<pre class="layout">
        ( * )                  cover A (2 tiles)          cover B (2 tiles)
        /   \                  t1 = a + b                 t1 = a + b   ; LEA
      ( + )  c                 t2 = t1 * c                t2 = t1 * c  ; IMUL
      /   \
     a     b

  tile 1:  reg &lt;- a + b        ADD  r, r     1 uop, 2 operands
  tile 2:  reg &lt;- reg * c      IMUL r, r     1 uop, 2 operands
  cover B: reg &lt;- a + b        LEA  r, [r+r] 1 uop, base+index, no flags
           reg &lt;- reg * c      IMUL r, r
</pre>

读图：加法结点既可以被 `ADD` 覆盖，也可以被 `LEA` 覆盖；两种覆盖的指令条数相同，差别在操作数形式和标志位副作用。若加法结果还要参与寻址，`LEA` 还能把地址计算并进去，覆盖的结点数进一步减少。覆盖的选择不是「哪条指令更短」这么简单，而是「这个子树的根允许什么结果位置」。

树覆盖有两种常见策略。**最大匹配**（maximal munch）从根往下，每次选能匹配的最大模式，匹配后把子树当作已覆盖；它实现简单，但对某些树会先选大模式、后面被迫用更贵的组合。**动态规划**（dynamic programming）自底向上为每个结点算「结果放在寄存器」和「结果作为内存操作数」两种状态的最小成本，再在根上取最小。对树且成本可加时，DP 给出最优覆盖；这条性质在下面的定理里说清楚。

::: thm 定理 7.1.1 · 树上的 DP 覆盖最优性 {#thm-compilers.2.7.1.1}
设表达式树每个结点只有有限个候选模式，每个模式的成本是非负常数，且模式的匹配只依赖以该结点为根的子树形状与操作数约束。自底向上对每个结点保存「结果必须在寄存器」与「结果可以作为内存操作数」两类最小成本，则根结点的最小值等于所有合法覆盖的最小成本。
:::

::: proof
对树高归纳。叶子只有有限个模式，两类状态的最优值可直接枚举。对内结点，任一覆盖在根处选一个模式；该模式的每个操作数子树要么被独立覆盖，要么被吸收进根模式（例如 load 的地址模式吸收 add）。被吸收的子树在父模式里已经确定了结果位置，未被吸收的子树按归纳假设取到各自状态的最优值。把所有候选模式的成本取最小，即得到根的最优值。关键是状态要记录结果位置约束；只记一个「最小成本」会在父模式要求内存操作数时丢失信息。
:::

成本函数长什么样？不同后端的权重不同，但通常包含四类项：指令条数、编码长度、寄存器压力增量、以及是否引入额外的 `mov`。下面是一张定性表，数值只用于比较，不代表某型号的实测周期：

| 模式 | x86-64 形式 | 指令数 | 额外 `mov` | 标志位 | 适用条件 |
|:--|:--|--:|--:|:--|:--|
| 寄存器加 | `addl %esi, %eax` | 1 | 可能 1 | 写 | 结果可在源寄存器上改写 |
| 地址加（LEA） | `leal (%rdi,%rsi), %eax` | 1 | 0 | 不写 | 地址操作数含 base+index，结果另放 |
| 立即数乘 | `imull $3, %eax` | 1 | 0 | 写 | 常数在 32 位立即数范围 |
| LEA 乘常数 | `leal (%rax,%rax,2), %eax` | 1 | 0 | 不写 | 常数是 2/3/5/9 等小倍数 |
| 访存加 | `addl (%rdi), %eax` | 1 | 0 | 写 | 一个源在内存，另一个在寄存器 |
| 地址折叠 | `movl 8(%rdi), %eax` | 1 | 0 | 不写 | 偏移在编码范围 |
| 大常数 | `movabsq $imm, %rax` | 1 | 0 | 不写 | 64 位立即数 |

表里的「额外 `mov`」不是小事。x86 的多数整数运算是两地址形式：目的寄存器同时是第一个源。若 IR 要求 `t2 = t0 + t1` 且 `t0` 在 `t2` 之后仍然活跃，选择器要么把结果放进 `t1` 再交换操作数，要么插入一条 `mov`。寄存器分配阶段可以通过合并（coalescing）消掉一部分，但合并本身可能增加冲突。指令选择和分配之间的这种来回，是后端里最常见的「局部最优不等于全局最优」。

::: ex 例 7.1.1 · 给 `p[i] * 3 + 5` 定价 {#ex-compilers.2.7.1.1}
IR 树是 `add(mul(load(add(p, mul(i, 4))), 3), 5)`。候选覆盖有两种。覆盖 A 把地址算成独立指令：`movslq %esi,%rax`、`leaq (%rdi,%rax,4),%rdx`、`movl (%rdx),%eax`、`imull $3,%eax`、`addl $5,%eax`，共 5 条。覆盖 B 把地址折进 load，并用 LEA 乘 3：`movslq %esi,%rax`、`movl (%rdi,%rax,4),%eax`、`leal (%rax,%rax,2),%eax`、`addl $5,%eax`，共 4 条。clang -O1 的真实输出正是覆盖 B（见上面的 `_scaled_idx`）。差异来自两个模式：x86 的 load 允许 `base + index*scale + disp`，LEA 允许 `base + index*scale`；两者都不改标志位。
:::

::: intuition 为什么 LEA 常被选中
LEA 本质上是「算地址」，但它只做加法和移位，不访问内存。编译器发现某个加法或小常数乘法只是在算一个值，就可以用 LEA 代替 ADD/IMUL：一条指令算 base+index、不写标志、不占内存端口。代价是 LEA 的复杂寻址在某些微架构上有额外延迟，所以「LEA 一定更快」是错的；正确说法是「在目标描述把 LEA 的成本设为与 ADD 同级或更低，且结果需要新寄存器时，DP 会选择 LEA」。
:::

边界有三条。第一，DP 的最优性只对树成立；IR 是 DAG 时，共享子表达式被不同父结点重复覆盖，可能重复求值。若共享子表达式有副作用或陷入异常，重复求值会改变可观察行为；此时要么先做公共子表达式消除，要么在覆盖时记录共享结点并强制只算一次。第二，成本模型依赖微架构和指令编码，`-O2` 与 `-Os` 的权重不同；本书的表格只做定性比较，不能当成性能结论。第三，指令选择不能替代寄存器分配：选择器可以假设结果在寄存器，但能不能真的放下由分配器决定；两者之间的接口通常是一组带虚拟寄存器约束的机器指令，而不是最终的物理寄存器。

最后给一个「选择器看不到」的例子。`_idx2` 的 `movl 8(%rdi), %eax` 既是 load，也是「地址加偏移」的覆盖；它在 `-O1` 下只有一条指令。如果函数后面还要用 `p` 和 `p+2` 的地址做比较，选择器可能反而保留 `leaq 8(%rdi), %rax`，因为地址本身要被复用。这就是为什么同一段 C 在不同上下文里生成的指令数不同：覆盖的输入不只是表达式树，还有使用次数和活跃范围。

::: note 两地址机器的操作数矩阵
把「目的」和「源」的合法组合列成矩阵，比背指令表更有用。以 32 位整数加法为例：

| 目的 \ 源 | 寄存器 | 立即数 | 内存 |
|:--|:--|:--|:--|
| 寄存器 | 合法，读改写 | 合法 | 合法，内存源 |
| 内存 | 合法，读改写内存 | 合法 | **非法**，两个内存操作数 |
| 立即数 | 非法 | 非法 | 非法 |

矩阵右下角的空格是 x86 编码的直接限制：一条指令最多一个内存操作数。选择器若要把 `mem + mem` 的 IR 加法降下来，必须先用一条 `mov` 把其中一个源取到寄存器，再加。这条 `mov` 不是「多余」，而是编码约束的代价；寄存器分配可以通过让一个源已经在寄存器里来消掉它，但选择器不能假设。

矩阵还解释了交换律的用处。`add` 和 `mul` 可交换，选择器可以把「结果寄存器」安排在任意一个源上：若 `a` 已死、`b` 还活，就把结果放进 `a` 的寄存器，避免覆盖 `b`。减法、除法不可交换，目的只能放在被减数/被除数那边，代价更高；这也是为什么 `x - y` 常常比 `x + y` 多一条 `mov`。
:::

两个模式匹配的工程细节。第一，模式通常按「根操作 + 操作数类别」索引，而不是对整棵树做子图同构；否则选择会退化成指数搜索。第二，匹配失败要能回退到合法化，而不是直接报错；合法化把大树拆小，直到每个结点都有模式。第三，模式的成本要包含「是否产生额外 `mov`」，否则选择器会偏好指令数少但复制多的覆盖，把压力推给分配器。

最后区分两个词：**指令选择**（instruction selection）决定「用哪些指令」，**指令发射**（instruction emission）决定「这些指令的汇编文本/编码长什么样」。前者是 IR 到机器指令的映射，后者是机器指令到字节的映射。本书把两者分开讲，因为它们的错误模式不同：选择错误表现为「结果不对但能汇编」，发射错误表现为「汇编器拒绝」或「编码的寄存器/位宽不对」（第 8 章）。

选择结果要同时满足三类约束，缺一不可：

| 约束 | 例子 | 违反后果 |
|:--|:--|:--|
| 编码约束 | 两个操作数不能同时为内存 | 汇编器拒绝 |
| 语义约束 | `sub` 的操作数顺序、`imul` 的有符号性 | 结果错误但能汇编 |
| 压力约束 | 目的寄存器与仍活跃的源重合 | 多一条 `mov`，或覆盖源 |

编码约束由汇编器兜底，语义约束由测试兜底，压力约束只能由分配器和发射器共同保证。把这三类分开，调试时就知道该看哪一层：汇编失败看编码，结果错看语义，指令数异常看压力。

成本模型需要校准。教材里的「LEA 1 uop、IMUL 3 周期」只是数量级；真实目标要用微架构手册或 `llvm-mca` 之类的工具测。校准的方法不是改一个全局常数，而是对每类模式测「吞吐/延迟/编码长度」，把结果写进目标描述，再用一组固定程序回归。没有校准的成本模型，DP 仍然能跑，但它优化的可能是错误的代价。

## 7.2 虚拟寄存器、活跃区间与冲突图 {#sec-compilers.2.7.2}

指令选择之后，IR 里的每个临时变量仍然是一个**虚拟寄存器**（virtual register）。分配器的任务是把它们映射到有限的物理寄存器或栈槽，使任意两个同时活跃的虚拟寄存器不共享同一个物理寄存器。判断「同时活跃」不需要新的数据流分析：第 5 章的活跃变量分析已经给出每个程序点的 live-in/live-out；本节只是把它变成区间和冲突图。

用实验里的 `calls` 程序做例子。它的 TAC 是：

```text
func calls(a, b)
  s = a + b
  d = a - b
  r = call g
  t = s + d
  q = call h
  u = t + q
  v = s + t
  w = u + v
  ret w
```

按指令下标编号，`call g` 在点 2，`call h` 在点 4。实验输出的区间表是真实的：

```text
vreg      def  last  points                         cross-call  deg  cost  score
  a         0     1  0,1                            no           2     2   1.00
  b         0     1  0,1                            no           2     2   1.00
  d         1     3  1,2,3                          yes          2     2   1.00
  q         4     5  4,5                            no           2     2   1.00
  r         2     2  2                              no           2     1   0.50
  s         0     6  0,1,2,3,4,5,6                  yes          7     3   0.43
  t         3     6  3,4,5,6                        yes          3     3   1.00
  u         5     7  5,6,7                          no           3     2   0.67
  v         6     7  6,7                            no           1     2   2.00
  w         7     8  7,8                            no           0     2   2.00
interference edges (12): a-b a-s b-s d-r d-s q-s q-t r-s s-t s-u t-u u-v
```

::: def 定义 7.2.1 · 活跃区间与冲突图 {#def-compilers.2.7.2.1}
对虚拟寄存器 `v`，令 `P(v)` 为所有满足「`v` 在程序点 `i` 之前或之后活跃」或「`v` 在 `i` 被定义/使用」的点集，则 `v` 的**活跃区间**（live interval）常取其凸包 `[min P(v), max P(v)]`。两个虚拟寄存器 `u`、`v` **冲突**（interfere），若存在一个程序点二者同时活跃，或 `u` 在 `v` 的定义点仍然活跃。以虚拟寄存器为结点、冲突为边构成的图叫**冲突图**（interference graph）。给冲突图做 `K` 着色，就是把 `K` 个物理寄存器分配给虚拟寄存器。
:::

::: thm 定理 7.2.1 · 冲突图着色的语义保持 {#thm-compilers.2.7.2.1}
若分配函数 $\rho$ 把每个虚拟寄存器映射到一个物理寄存器或栈槽，且对冲突图中每条边 `(u,v)` 有 $\rho(u) \ne \rho(v)$（栈槽按槽号区分），每条指令的每个使用都读到最后一次定义写入的位置，调用点不破坏跨调用值所在的位置，则对任意输入，分配后程序的返回值与未分配 IR 的指称语义相同。
:::

::: proof
对执行步数归纳。初始时参数被放进各自位置。每条指令执行前，归纳假设给出：所有在该点活跃的虚拟寄存器的当前位置都保存着它们在未分配语义下的值。冲突条件保证不同时活跃的值不共享位置；指令的目的位置若与某个不再活跃的值重合，不会影响后续使用。复制、二元运算、分支分别按语义更新目的位置；调用点由「不破坏跨调用值」的前提保证。执行到返回点时，返回值的位置保存的正是未分配语义的值。
:::

证明里有两个容易被略过的前提。「每条使用读到最后一次定义」在存在栈槽时要求溢出重写（spill rewriting）在定义处写槽、在使用处读槽；只改定义或只改使用都会破坏前提。「调用点不破坏跨调用值」是 `7.4` 的主题；它不属于图着色的组合部分，而是分配器必须额外满足的约束。

区间图长这样（`|` 表示该点活跃，`^` 标出调用点）：

<pre class="layout">
point     0    1    2    3    4    5    6    7    8
          |    |    |    |    |    |    |    |    |
a         |----|
b         |----|
s         |----------------------------------|
d              |---------|
r                        |
t                        |--------------|
q                             |----|
u                                  |---------|
v                                       |----|
w                                            |----|
call                ^              ^
          call g at 2      call h at 4

edges: a-b (both live at 0), s-d (both live at 2),
       d-t (d live at 3 when t is defined), s-t (both live at 3..6),
       q-s (q live at 5 while s still live)
</pre>

读图：区间在时间轴上重叠的两个虚拟寄存器必须分到不同寄存器；`s` 从 0 活到 6，跨过两次调用，因此它的可用寄存器集合比 `a` 小得多。`d` 只在 1 到 3 活跃，却在点 2 跨过一次调用；它的区间很短，但仍然不能放进 caller-saved。区间图不是「变量作用域图」：`d` 的作用域是整个函数体，区间却只有三个点。

区间是怎么造出来的？实验里的步骤可以直接复述：

1. 把 IR 切成基本块并建 CFG；分支目标指向标签，标签本身作为空指令保留，便于统一下标。
2. 在 CFG 上做后向活跃变量分析，得到每个点的 `live_in` 与 `live_out`；这和第 5 章的工作列表算法是同一个方程，只是这里只需要布尔集合。
3. 对每个虚拟寄存器收集「活跃点、定义点、使用点」，取最小和最大下标作为区间端点；区间内部即使有洞也保留，因为线性扫描只认端点。
4. 在每个点把 `live_in` 中的虚拟寄存器两两连边；再对每条指令把定义与 `live_out` 连边。前者捕获「同时活跃」，后者捕获「定义时另一个值还活着」。
5. 对每个调用点，记录 `live_in` 中的虚拟寄存器为「跨调用」，供 `7.4` 限制可用寄存器。

第 4 步的第二种边容易被漏掉。考虑 `d = a - b`，`a` 在 `d` 定义后不再使用，但 `a` 是这条指令的源；如果只按 `live_in` 连边，`d` 和 `a` 不冲突，分配器可以让它们共用 `%rax`。在 3 地址 IR 上这没问题，因为 `d = a - b` 一次读两个源、写目的；但 x86 是两地址，发射时通常先 `mov a, %rax` 再 `sub b, %rax`，这条 `mov` 会把 `a` 的值覆盖掉。实验的发射器最初就踩了这个坑：图着色把 `u` 和 `c` 分到同一个 `%rax`，`u = a - c` 先 `mov a` 覆盖了 `c`，差分测试 200 组全部失败。修复方式不是加边（那会过度保守），而是在发射阶段检测「目的寄存器等于仍在读取的源」，必要时先算到 scratch。这个例子说明：冲突图保证的是「同时活跃不共享」，不保证「两地址发射不踩源」；后者是 lowering 的责任。

::: ex 例 7.2.1 · 手算 `d` 的冲突边 {#ex-compilers.2.7.2.1}
`d` 在点 1 定义，点 3 最后一次使用。点 1 的 live-in 是 `{a,b}`（`s` 刚定义，`d` 尚未定义），点 2 的 live-in 是 `{s,d}`，点 3 的 live-in 是 `{s,d,t}`（`t` 在点 3 定义前，`d` 还要用）。因此 `d` 与 `s` 在点 2、3 同时活跃，与 `t` 在点 3 同时活跃；`d` 与 `a`、`b` 只在点 1 的定义处相邻，不构成冲突。实验的边表里正好有 `d-s`、`d-t`，没有 `d-a`、`d-b`。跨度上 `d` 只有 3 个点，度数却只有 2，因为它的邻居是长区间。
:::

::: note 区间凸包是保守近似
真实程序里，一个虚拟寄存器可能在循环体外定义、循环体内使用、循环体外再用，中间有一段完全不活跃。凸包会把这段空洞算进区间，导致假冲突和不必要的溢出。工程分配器会做**活跃范围分裂**（live range splitting）：在空洞或调用点把区间切开，分别分配，再用 `mov` 拼接。实验为了可读性只用凸包，因此它的溢出数不是最优；结论要写成「在这个近似下」，而不是「图着色必然溢出这么多」。
:::

如果要在自己的编译器里复现这套分析，最小的验证顺序是：先只打印每个点的 live-in/live-out，与手算的两个程序对照；再加区间，检查 `start <= end`、每个使用点都落在区间内；最后加边，检查「同一活跃集合内的任意两点都有边」。这三步都能用断言写死，出错时定位到具体程序点，而不是等到寄存器分配结果不对再回头猜。

还有一个实现选择：区间是按「指令下标」还是按「基本块内偏移」编号。跨基本块的下标需要先做线性化（例如逆后序），此时同一个值的区间可能跨越不连续的下标；实验为了简单，直接用全局指令下标，并把标签也占一个下标。真实后端通常用「程序点编号 + 块内偏移」的两级结构，以便在块边界插入分裂点和栈槽搬运。两种编号对冲突图没有本质影响，但会影响线性扫描的排序和调试输出的可读性。

::: note SSA、phi 与循环携带值
第 4 章的 SSA 用 `phi` 在合流处选择不同前驱的值。退出 SSA 时，`phi` 被消解成前驱边上的 `mov`；这些 `mov` 是分配器必须处理的复制。如果两个 `phi` 操作数被分到不同寄存器，就在对应的前驱边上插 `mov`；如果所有操作数已经在同一寄存器，复制可以删掉。这个「同址约束」是 SSA 分配器（例如基于弦图的寄存器分配）能比通用图着色更快的原因之一，但它不是免费的：复制可能引入新的冲突。

循环携带值会拉长区间。实验的 `loop` 程序里，`i` 在循环体里定义、在回边处再次使用，区间从点 0 延伸到点 9，尽管它在循环体外只初始化一次。分配器不能因为「`i` 在源程序里只声明一次」就认为它短命；回边让它的活跃范围覆盖整个循环。若循环体里还有调用，`i` 还会变成跨调用值，可用颜色进一步减少。

区间凸包在循环里尤其保守。一个值可能在循环前定义、循环内使用、循环后再使用；中间没有洞，凸包是准确的。另一个值可能在循环内定义、循环外使用、下一次迭代再定义；这时区间会跨越整个循环，凸包也基本准确。真正产生洞的是「条件分支里定义、另一条路径不使用」的情况：凸包把两条路径都算进去，冲突图会多出边。工程分配器用活跃范围分裂处理这些洞，实验不处理，因此实验的溢出数偏高。
:::

活跃变量分析的精度直接决定冲突图的质量。may 分析与 must 分析的保守方向不同；本章只需要「某个值在某点是否可能活跃」，因此用 may 的并集，保守但安全。

| 精度选择 | 代价 | 对分配的影响 |
|:--|:--|:--|
| 只按基本块边界 | 快 | 块内冲突被忽略，可能非法 |
| 指令级 live-in/out | 中等 | 本章采用，精确到点 |
| 路径敏感 | 慢 | 减少假冲突，但实现复杂 |
| 带别名/异常边 | 更慢 | 捕获调用与异常对内存的影响 |

异常边常被忘记：一条可能抛异常的指令会让异常处理路径上的值活跃，若 CFG 只连正常边，区间会变短，分配器可能把两个在异常路径上同时活跃的值放在同一寄存器。C++ 的析构、Rust 的 panic、Java 的 finally 都会引入这类边；本章的 TAC 没有异常，故不建模。

不可达块会让活跃分析出现「看起来奇怪」的结果。若一个块没有前驱，它的 `live_in` 是空集，块内使用的变量在入口处没有定义；分配器可能给它一个寄存器，但运行时永远不会到达。验证时可以把不可达块单独标出来，不要用它们的区间去推断整体压力。异常边则相反：异常处理路径上的值可能让区间变长，若 CFG 只连正常边，分配器会低估冲突。本章的 TAC 既没有异常也没有不可达块，但真实前端两者都有；建图前先确认 CFG 的边集完整。

栈槽编号也要一致。实验用「溢出虚拟寄存器排序后的下标」作为槽号，槽 0 在帧底；真实后端通常把槽号与帧偏移分开：槽号是分配器的抽象，帧偏移由 prologue 计算。两者混用会让「槽 0」在不同函数里指向不同地址，调试时很难对照。把「槽号 → 帧偏移」的映射打印出来，是排查溢出错误的第一步。

## 7.3 图着色分配与溢出代价 {#sec-compilers.2.7.3}

把冲突图染成 `K` 色是 NP 完全问题。工程上不求解精确解，而是用 Chaitin 风格的「简化—选择」：反复删除度数小于 `K` 的结点并压栈；删不动时选一个代价最小的结点标记为「可能溢出」，也压栈；然后按栈逆序弹出，为每个结点选一个邻居没用过的颜色。若弹出时找不到颜色，这个结点就是真溢出，给它一个栈槽，重写使用点，再重跑。

::: def 定义 7.3.1 · 着色、溢出与溢出代价 {#def-compilers.2.7.3.1}
**着色**（coloring）是映射 $c: V \to \{1,\ldots,K\}$，使每条边两端颜色不同。**溢出**（spill）是把一个虚拟寄存器放进栈槽，并在每次定义时写槽、每次使用时读槽。**溢出代价**（spill cost）是估计「溢出这个值会让程序变慢多少」的启发式量；常见形式是 $\mathrm{cost}(v) = \sum_{i \in \mathrm{def}(v) \cup \mathrm{use}(v)} 10^{\mathrm{depth}(i)} / \deg(v)$，其中 $\mathrm{depth}(i)$ 是所在循环的嵌套深度。
:::

公式里的 $10^{\mathrm{depth}}$ 是「循环内的使用更贵」的粗糙编码。深度 1 的一次使用记 10，深度 2 记 100；除以度数是为了惩罚「邻居很多、删不掉」的结点——溢出它能让很多邻居继续着色。不同编译器的公式不一样：LLVM 的 greedy allocator 把使用次数、定义次数、循环深度和溢出时的拆分开销分开计；本书只需要你能解释「为什么选这个而不是那个」，不需要背某个公式。

实验程序 `straight` 在 `K=4` 下的真实候选数据：

```text
vreg   def last  deg  cost  score(cost/deg)
b       0    7    11    2    0.18
c       0    8    12    2    0.17
e       0    3     7    1    0.14
a       0    6    10    2    0.20
s       0    4     8    3    0.38
```

度数都大于等于 `K`，简化阶段很快就卡住。分配器按 score 从小到大选潜在溢出：先 `e`，再 `c`，再 `b`。真实的输出是：

```text
[coloring]
  regs : a->%r12  d->%rax  q->%rax  s->%rbx  t->%rcx  u->%rax  v->%rax  w->%rax  x->%rax  y->%rax  z->%rax
  spill: 0->slot0  1->slot1  2->slot2
  spilled=['b', 'c', 'e']  slots=3  potential=['e', 'c', 'b']
  allocated ops=13 (tac=10, spill moves=5)
```

简化栈的选择顺序和最终溢出集合一致，但这不保证「选中的一定溢出」：乐观着色（optimistic coloring）允许潜在溢出结点在弹出时拿到颜色，只有真的拿不到才落槽。实验里三个都真溢出了，因为它们的邻居把 4 个颜色占满。

把简化—选择画成栈：

<pre class="layout">
K = 4, colors = {rax, rcx, rbx, r12}

初始                 简化（度 &lt; 4 的先走）              卡住时按 score 选
a(10) b(11) c(12)     q(0) w(0) v(1) z(1) ...           e(0.14) -&gt; potential
d(5)  e(7)  s(8)      y(2) x(3) u(6) ...                 c(0.17) -&gt; potential
t(8)  u(6)  v(5)      ...                                 b(0.18) -&gt; potential
w(4)  x(3)  y(2)      stack: [q,w,v,z,y,x,u,...]
z(1)  q(0)

选择（逆序弹出）：
  q -&gt; rax, w -&gt; rax, v -&gt; rax, z -&gt; rax, y -&gt; rax,
  x -&gt; rax, u -&gt; rax, t -&gt; rcx, s -&gt; rbx, a -&gt; r12,
  d -&gt; rax
  b, c, e 弹出时 4 色已占满 -&gt; slot0, slot1, slot2

结果：13 条已分配指令（10 条 TAC + 5 次 spill 访存，减去标签等）
</pre>

读图：简化阶段删掉的结点在弹出时一定还有颜色可用吗？不一定——「度小于 K」只保证删除时邻居少，不保证弹出时邻居没占满；真正保证的是「若简化阶段从未卡住，则图一定 K 可着色」。一旦卡住，潜在溢出结点可能拿到颜色，也可能落槽，这就是乐观着色的「乐观」所在。

::: thm 定理 7.3.1 · 无潜在溢出时的成功保证 {#thm-compilers.2.7.3.1}
若简化阶段对每个结点都能找到当前度数小于 `K` 的结点并删除（即从未进入潜在溢出分支），则选择阶段一定能为每个结点分配 `K` 种颜色之一。
:::

::: proof
对删除的逆序归纳。删除最后一个结点时，它在图中没有邻居，弹出时任意颜色可用。假设后续弹出的所有结点都已成功着色；当前结点弹出时，它的邻居都已在图中被删除并已着色，邻居数量小于 `K`，因此 `K` 种颜色中至少有一种未被邻居使用。选择阶段按同一逆序进行，故每个结点都能拿到颜色。
:::

这个定理只覆盖「简化从未卡住」的情况。卡住后仍然可能成功（乐观着色），也可能失败；失败就需要溢出重写，然后重新建图。实验为了展示完整流程，只做一轮简化—选择—溢出，不迭代重跑；因此它的溢出集合是「一轮启发式的结果」，不是最小溢出数。真实分配器会迭代到没有真溢出为止，或者达到编译时间预算后接受当前结果。

溢出重写要做两件事：在每个定义点之后把值写进槽，在每个使用点之前从槽读到临时寄存器。只做一半是最常见的错误：只写不读，使用点读到旧值；只读不写，槽里永远是初始值。实验的发射器把这两种情况都交给同一套 `loc` 映射：溢出虚拟寄存器的 `loc` 是 `("slot", n)`，`mov` 在寄存器与槽之间搬运；二元运算的目的在槽时，先算到 scratch 再写回。已分配指令数从 10 涨到 13，溢出访存共 5 次，其中有些作为内存操作数出现，不额外占一条指令。

溢出代价的边界也要说清楚。第一，代价是启发式，不是运行时测量；一个在热循环里只使用一次的值可能比冷代码里使用十次的值更贵。第二，除以度数会偏向溢出「邻居多」的结点，但邻居多也可能意味着它连接了两个不相关区域，溢出后两边都要重载。第三，溢出会改变指令选择：原本可以折叠进内存操作数的 load 现在变成显式的 `mov`，成本模型若不同步更新，会选择出更差的覆盖。第四，合并（coalescing）能消掉 `mov`，但合并两个不冲突的虚拟寄存器可能让新结点与更多邻居冲突；保守合并只在「合并后每个邻居的度数仍小于 K」时进行。

::: ex 例 7.3.1 · 为什么溢出 `e` 而不是 `s` {#ex-compilers.2.7.3.1}
`e` 的区间是 `[0,3]`，度数 7，代价 1，score 0.14；`s` 的区间是 `[0,4]`，度数 8，代价 3，score 0.38。溢出 `s` 会在点 0 写槽、点 3 和点 4 读槽，且 `s` 连接 `a,b,d,t,u,v` 六个邻居，重写后这些邻居仍要重新着色；溢出 `e` 只在点 3 使用一次，写槽一次、读槽一次，影响的邻居少。score 把「使用少」和「度数高」两个因素都算进去，所以选 `e`。注意这不是证明最优；若 `e` 在深度 2 的循环里，`10^2` 会让 score 变成 1.4，选择就会反过来。
:::

图着色还有一个常被忽略的输入：预着色结点。物理寄存器不是「颜色」，而是有名字、有固定用途的结点；调用指令定义 caller-saved 寄存器，返回指令使用 `%rax`，参数传递使用 `%rdi` 等。工程实现通常把这些固定约束建成预着色结点或禁止颜色集合，再让普通结点避开。实验用「禁止颜色集合」简化了这部分：跨调用的虚拟寄存器不能选 caller-saved；返回值的 `mov` 固定写到 `%rax`。两种建模在语义上等价，差别在冲突图的大小和调试信息的可读性。

溢出重写的一个具体对照：

```text
IR:                 t = a + b          （t 溢出到 slot0，a、b 在寄存器）
重写后:             mov  a, %r10
                    add  b, %r10
                    mov  %r10, slot0

IR:                 u = t * c          （t 从 slot0 读，u 在寄存器）
重写后:             mov  slot0, %r10
                    mov  %r10, %rax
                    imul c, %rax
```

第一段用 scratch `%r10` 算完再写槽；第二段先读槽再搬到目的寄存器。若第二段的目的寄存器恰好是 `%rax`，`mov %r10,%rax` 可以省掉；若 `c` 也在内存，`imul` 不能有两个内存操作数，必须先把 `c` 取到寄存器。这些细节都属于「溢出重写」，不是「分配」本身；分配只给出 `t -> slot0` 的映射，重写才决定指令序列。

**重物质化**（rematerialization）是溢出的替代方案：如果虚拟寄存器的值可以由一条廉价指令重新算出（常量、`lea` 的地址、参数寄存器的副本），就不必写槽，直接在使用点重算。它省掉访存，但可能增加指令数；对常量尤其划算。实验没有实现重物质化，所有溢出都走栈槽；这也是它指令数偏高的原因之一。

预着色结点的一个例子：返回值必须放在 `%rax`。如果某个虚拟寄存器 `r` 在返回点活跃，它不能占用 `%rax`，否则返回值的 `mov` 会覆盖它；反过来，若 `r` 就是返回值，它可以和 `%rax` 合并。分配器把 `%rax` 建模成一个「在返回点被定义」的固定区间，普通区间在返回点避开它。调用点的 caller-saved 也是同一类约束，只是固定区间更多、时间点更密。

溢出重写会改变冲突图：把一个值放进槽后，它的邻居少了一个，原本不可着色的子图可能变得可着色。工程分配器因此迭代「分配 → 溢出 → 重建 → 再分配」，直到没有真溢出或达到预算。

| 迭代策略 | 终止条件 | 风险 |
|:--|:--|:--|
| 一轮 | 固定次数 | 可能留下真溢出，靠后续修补 |
| 到无溢出 | 图为空 | 可能反复溢出同一批值，编译时间失控 |
| 带预算 | 指令数/时间上限 | 需要回退到「接受溢出」的保守版本 |

迭代不保证收敛到最优，也不保证一定终止：如果每次都在同一组值上循环，说明代价模型或冲突图有 bug。工程上给迭代加「每轮溢出的值必须减少」或「最多 N 轮」的硬限制，超过就接受当前结果并记录诊断。

预着色约束不止调用点。返回指令要求结果在 `%rax`；整数除法要求被除数在 `%rax`、除数在另一个寄存器、商在 `%rax`；移位要求计数在 `%cl`。这些「固定位置」在冲突图里表现为预着色结点或禁止颜色集合：

| 指令 | 固定位置 | 分配器要做什么 |
|:--|:--|:--|
| `ret x` | `%rax` | `x` 在返回点不能与 `%rax` 冲突 |
| `idiv r` | `%rax/%rdx` | 被除数/商/余数避开冲突 |
| `shl r, cl` | `%cl` | 计数不能放在别的寄存器 |
| `call f` | 参数寄存器 | 参数搬运前不能覆盖活值 |

实验只建模了返回值和调用点，除法/移位没有出现。真实后端把这些约束写进指令描述，让分配器统一处理；手写分配器若只在调用点做特殊处理，遇到 `idiv` 就会错。

溢出和调用约束会互相放大。一个跨调用值若被溢出，它在每个调用前后都要保证槽里的值不被覆盖；若栈槽被别的值复用，调用后读到的可能是别人的值。分配器要把「溢出槽的活跃范围」也纳入冲突：两个不同时活跃的溢出值可以共用一个槽，但同时活跃的不能。实验为每个溢出值分配独立槽，简单但浪费；真实后端会做槽复用。

## 7.4 线性扫描与调用破坏 {#sec-compilers.2.7.4}

图着色看全局，线性扫描看时间轴。Poletto 与 Sarkar 的线性扫描把区间按起点排序，维护一个「当前活跃」列表；每来一个新区间，先把已经结束的区间从活跃表里删掉并释放寄存器，再给新区间找空闲寄存器；找不到就溢出「结束点最远」的那个区间。它的复杂度是 $O(n \log n)$（排序）加活跃表操作，适合 JIT 和编译时间敏感的场合。

::: def 定义 7.4.1 · 固定区间与调用破坏 {#def-compilers.2.7.4.1}
**固定区间**（fixed interval）是物理寄存器在某个时间段被占用的区间，例如调用指令在调用点占用所有 caller-saved 寄存器。**调用破坏集合**（clobber set）是一条指令执行后内容不再可靠的寄存器集合；x86-64 SysV 的 caller-saved 是 `%rax, %rcx, %rdx, %rsi, %rdi, %r8–%r11`，callee-saved 是 `%rbx, %rbp, %r12–%r15`。一个虚拟寄存器**跨调用**，若它在某个调用点的 live-in 中。
:::

线性扫描的核心循环可以写成这样（伪代码，不是可运行实现）：

```text
sort intervals by start
active = empty ordered by end
for v in intervals:
    for a in active where a.end < v.start: remove a; free a.reg
    allowed = all_colors
    if v crosses_call: allowed -= caller_saved
    free = allowed - {a.reg for a in active}
    if free not empty:
        v.reg = pick(free)
    else:
        victim = argmax_end(active union {v}) among intervals whose reg is in allowed
        if victim == v: spill(v)
        else: spill(victim); v.reg = victim.reg
    active.add(v)
```

两个细节决定正确性。第一，过期条件是 `a.end < v.start`，不是 `<=`：区间是闭区间，端点相同意味着两个值在同一个程序点都活着，不能共享寄存器。第二，抢寄存器时只能抢「对当前区间合法」的寄存器；若当前区间跨调用，而受害者的寄存器是 caller-saved，抢过来仍然会在调用点被破坏。实验的线性扫描最初没有这个检查，结果把一个跨调用值放进了 `%rax`，差分测试立刻失败。

调用点对分配的影响，用实验的 `calls` 最清楚。图着色给出的结果没有溢出：

```text
[coloring]
  regs : a->%rcx  b->%rax  d->%rbx  q->%rax  r->%rax  s->%r12  t->%rbx  u->%rcx  v->%rax  w->%rax
  spilled=-  slots=0
  allocated ops=17 (tac=9, spill moves=0)
```

线性扫描给出一个溢出：

```text
[linear]
  regs : a->%rax  b->%rcx  d->%r12  q->%rax  r->%rax  t->%rbx  u->%rcx  v->%rax  w->%rbx
  spill: 0->slot0
  spilled=['s']  slots=1
  allocated ops=17 (tac=9, spill moves=3)
```

两者指令数恰好相同，但原因不同：图着色把 `s` 放进 `%r12`，把 `d` 放进 `%rbx`，两个 callee-saved 刚好够；线性扫描在点 0 先把 `s` 放进 `%rbx`，到点 3 遇到跨调用的 `t` 时，两个 callee-saved 都被 `s` 和 `d` 占着，只能抢结束点最远的 `s`，把它溢出。线性扫描没有「后悔」机制：它不会回退到点 0 把 `s` 放进 `%r12`，只在当前活跃表里做局部决策。

<pre class="layout">
calls 的时间轴与两种决策

点        0     1     2(call g)  3     4(call h)  5     6     7     8
a         |-----|
b         |-----|
s         |-------------------------------------------------|
d               |-----------|
r                     |
t                           |-----------------------------|
q                                 |-----|

          d=r12 一直在；t=rbx；s 的使用点改为读槽
</pre>

读图：同一个冲突图、同样的 `K=4`，两种算法给出不同溢出集合；差异来自线性扫描的「先到先得」和「不回退」。图着色看到 `d` 在点 3 就死，`t` 可以复用 `%rbx`；线性扫描在点 0 还不知道 `t` 会出现，先把 `s` 放进 `%rbx`，到点 3 只能溢出。这不是线性扫描「错了」，而是它的信息集更小。

线性扫描与图着色的对比：

| 维度 | 图着色 | 线性扫描 |
|:--|:--|:--|
| 时间复杂度 | 建图最坏 $O(n^2)$，简化近似线性 | 排序加活跃表，$O(n \log n)$ |
| 区间空洞 | 冲突图可精确表达 | 凸包近似，空洞导致假冲突 |
| 溢出质量 | 全局信息多，通常更好 | 局部决策，可能多溢出一个 |
| 调用点 | 预着色/禁止颜色 | 固定区间或允许集合 |
| 增量编译 | 图变化后重建代价高 | 插入新区间较自然 |
| 典型用途 | 静态编译器、优化级别高 | JIT、基线编译器、快速迭代 |

调用约定还决定「值放在哪里」。同一段 C，在 `-O2` 下 clang 把跨调用的 `x` 放进 `%ebx`：

```asm
_after:
    pushq   %rbp
    movq    %rsp, %rbp
    pushq   %rbx
    pushq   %rax
    movl    %edi, %ebx
    callq   _g
    addl    %ebx, %eax
    addq    $8, %rsp
    popq    %rbx
    popq    %rbp
    retq
```

`pushq %rbx` 保存 callee-saved，`pushq %rax` 是一条「死」的 push，唯一作用是让 `%rsp` 在调用前回到 0 mod 16（第 8 章会把这个账算清楚）。在 `-O0` 下，同一个函数把 `x` 放在 `-4(%rbp)`，调用后从栈重载。两种都正确，代价不同：callee-saved 寄存器不用每次访存，但要在 prologue/epilogue 保存恢复；栈槽每次使用都要访存。分配器的选择取决于溢出代价和寄存器压力。

::: ex 例 7.4.1 · 跟着线性扫描走一遍 {#ex-compilers.2.7.4.1}
区间按起点排序：`a[0,1]`、`b[0,1]`、`s[0,6]`、`d[1,3]`、`r[2,2]`、`t[3,6]`……。点 0：`a->rax`、`b->rcx`、`s->rbx`（`r12` 还空着）。点 1：`d` 需要 callee-saved，`r12` 空，`d->r12`；`a`、`b` 未过期（end=1，start=1，闭区间）。点 2：`a`、`b` 过期，`r` 用 `rax`；`s`、`d` 仍在活跃表。点 3：`t` 跨调用，只能选 `rbx` 或 `r12`；两者都被占，受害者是结束点更远的 `s`（end=6），抢 `rbx` 给 `t`，`s` 溢出到 slot0。点 6：`s` 的使用改为从 slot0 读，`t` 仍在 `%rbx`。最终 `s` 有 3 次 spill 访存。
:::

边界：线性扫描的「不做活跃范围分裂」是它的弱点，也是它快的原因。工程上的线性扫描变体（例如 LLVM 的 greedy allocator、HotSpot 的 LinearScan）会在调用点、循环边界和高压点分裂区间，再对片段做分配；分裂后仍然可能溢出，但溢出的是短片段，不是整个长区间。另一个边界是浮点/向量寄存器：它们的调用约定、寄存器类别和别名关系（`%xmm0` 的低 128 位与 `%ymm0`）让「一个颜色一个值」的模型不够用，需要寄存器类别和子寄存器约束。本章的 `K` 色模型只覆盖整数虚拟寄存器；浮点和向量在目标描述里作为独立寄存器类处理（`7.6`）。

最后强调一个术语边界：**调用破坏**（caller-saved）不是「调用会破坏所有寄存器」。callee-saved 寄存器在调用前后保持不变，这正是跨调用值可以放在那里的原因；栈槽也不被调用破坏（只要不越界）。分配器要建模的是「哪些位置在调用点仍然可靠」，而不是「调用很危险，所有值都溢出」。

调用点的另一个实现细节是**参数与返回值的固定位置**。IR 里 `r = call g` 的返回值按约定在 `%rax`，但分配器可能把 `r` 分到 `%rbx`；发射器要在调用后插一条 `mov %rax, %rbx`。如果 `r` 恰好分到 `%rax`，这条 mov 可以省掉。同理，调用参数要按 ABI 放到 `%rdi`、`%rsi` 等固定寄存器，这些 mov 发生在调用之前，且不能被调度到调用之后。实验为了聚焦「破坏」，把调用简化成无参调用；参数传递的完整约束放在第 8 章。你在这里只需要记住：固定位置也是预着色约束，不能只看冲突图。

调用破坏不只来自 `call`。分配器要读目标描述里的隐式 clobber 集合：

| 机制 | 破坏的位置 | 分配器要做什么 |
|:--|:--|:--|
| 普通函数调用 | caller-saved 寄存器 | 跨调用值避开这些颜色 |
| 系统调用 | 按 ABI 可能破坏更多寄存器 | 查目标的 syscall clobber 表 |
| 内联汇编 | 汇编模板的 clobber 列表 | 把列表并进调用点约束 |
| `setjmp`/`longjmp` | 栈指针与 callee-saved 的恢复 | 不能在 `setjmp` 之后依赖寄存器值 |
| 信号处理 | 异步改写寄存器/栈 | 编译器通常不建模，靠运行时约定 |

最后一行是边界：C 标准不保证信号处理函数能看到一致的寄存器状态，编译器也不会为异步信号做分配约束；需要异步安全的代码要用 `volatile sig_atomic_t` 和专门的运行时。把这类「编译器不管」的边界写进文档，比假装分配器能处理更诚实。

调用点的位置可用性可以列成表：

| 位置 | 调用前 | 调用后 | 跨调用值能否放 |
|:--|:--|:--|:--|
| caller-saved 寄存器 | 有效 | 被破坏 | 不能 |
| callee-saved 寄存器 | 有效 | 保持 | 能（需 callee 保存） |
| 栈槽 | 有效 | 保持 | 能（地址不被覆盖） |
| red zone | 有效 | 可能被覆盖 | 不能（非叶函数） |

这张表是分配器的输入，不是它自己能推断的。callee-saved 之所以能放，是因为被调用者承诺恢复；栈槽之所以能放，是因为调用不会改写调用者的帧。把「调用会破坏所有寄存器」当规则，会把 callee-saved 也溢出，代码变慢但正确；把「调用不破坏任何寄存器」当规则，就是 7.8 的错误。

线性扫描还有一个「第二次机会」变体：被溢出的区间不立刻落槽，而是放进一个「稍后再试」的桶，等活跃表变化后再尝试分配；HotSpot 的 LinearScan 用这种分桶减少溢出。它仍然不做全局回退，但比「一次决定」多了一点灵活性。实验没有实现分桶，所以它的溢出数比工业线性扫描更高；结论要限定在「本实验的线性扫描」。

调用点约束与寄存器类别要一起看。浮点调用点破坏 `%xmm0–15`（SysV 的 caller-saved 向量寄存器），整数调用点破坏整数 caller-saved；分配器不能把「caller-saved」当成一个不分类的集合。实验只做整数，故只列整数寄存器；真实后端的 clobber 集合要按寄存器类分别写，否则会把浮点值放进被调用者破坏的 `%xmm`。

## 7.5 指令调度与依赖边界 {#sec-compilers.2.7.5}

指令选择决定「用哪些指令」，寄存器分配决定「值放在哪」，调度决定「按什么顺序执行」。三者的目标互相拉扯：调度想把有延迟的指令尽早发射、把独立的指令填进空隙；寄存器分配希望同时活跃的值尽量少；指令选择希望把地址计算折进访存。一个把寄存器压力推到极限的调度，可能让分配器多溢出三个值，最终比不调度还慢。

调度的合法性来自依赖关系。两条指令之间若有**数据依赖**（data dependence），它们的相对顺序不能随便换；没有依赖的指令可以交换，前提是交换不改变可观察行为。依赖分四类：

| 类型 | 含义 | 例子 | 能否交换 |
|:--|:--|:--|:--|
| 真依赖 RAW | 后者读前者写 | `t = a + b` 后 `u = t * c` | 不能 |
| 反依赖 WAR | 后者写前者读 | `u = t * c` 后 `t = d + e` | 不能直接换，改名后可 |
| 输出依赖 WAW | 两者写同一位置 | 两条都写 `%rax` | 不能直接换，改名后可 |
| 内存依赖 | 访存地址可能别名 | `*p = 1` 与 `x = *q` | 不能，除非证明不别名 |
| 控制依赖 | 分支决定是否执行 | `if` 后的两条臂 | 不能跨分支随意移动 |

寄存器分配会制造新的反依赖。分配前 `t` 和 `u` 是不同虚拟寄存器，`u = t * c` 与后面的 `t = d + e` 只通过 `t` 的真依赖相连；分配后两者可能共用 `%eax`，于是第二条写 `%eax` 与第一条读 `%eax` 形成 WAR，调度器不能再把它们随意交换。这就是为什么「分配前调度」和「分配后调度」不是同一件事：分配前调度器看到的是虚拟寄存器，自由度大；分配后看到的是物理寄存器，反依赖变成硬约束。

用两个函数观察 clang 的实际顺序：

```c
int indep(int a, int b, int c, int d) { return a * b + c * d; }
extern int g(int);
int barrier(int a, int b) { int x = a * b; int y = g(a); return x + y; }
```

`clang -target x86_64-apple-darwin -O2 -S` 的关键行：

```asm
_indep:
    imull   %esi, %edi
    imull   %ecx, %edx
    leal    (%rdx,%rdi), %eax

_barrier:
    pushq   %rbx
    pushq   %rax
    movl    %esi, %ebx
    imull   %edi, %ebx
    callq   _g
    addl    %ebx, %eax
```

`indep` 的两条乘法互不依赖，调度器把它们背靠背放在一起，最后用一条 `leal` 合并；如果先算第一条乘、再算加法、再算第二条乘，功能一样，但第二条乘的延迟无法与第一条重叠。`barrier` 更有意思：`x = a * b` 被提到了 `callq _g` 之前，结果放在 `%ebx`（callee-saved）跨过调用。调用并没有阻止所有指令跨越它——它只阻止「依赖调用副作用」的指令。乘法只读寄存器、不访存、不写内存，移到调用前是合法的；把 `y = g(a)` 移到调用前则不可能，因为它就是调用。

<pre class="layout">
indep 的依赖 DAG（节点 = 指令，边 = 必须先执行）

   mul1: edi = edi * esi        mul2: edx = edx * ecx
        \                          /
         \                        /
          +----&gt; add: eax = edi + edx
                         |
                       ret

两个合法调度：
  S1: mul1, mul2, add, ret          （两条乘法相邻，延迟重叠）
  S2: mul1, add?? 不合法：add 依赖 mul2
  S3: mul2, mul1, add, ret          （合法，和 S1 等价）

barrier 的边界：
  mul(a,b) --data--&gt; add &lt;--data-- call g(a)
      |                             ^
      +-- 不依赖调用，可上移 --------+
  但 call 之后的 add 不能上移，因为它读 g 的返回值。
</pre>

读图：调度器只能在依赖 DAG 的拓扑序里选一个顺序；`mul1` 和 `mul2` 的顺序任意，`add` 必须排在两者之后。`barrier` 里乘法可以上移到调用前，因为它与调用没有数据依赖，也不访问调用可能修改的内存；加法不能上移，因为它依赖调用的返回值。

::: thm 定理 7.5.1 · 相邻独立指令交换保持语义 {#thm-compilers.2.7.5.1}
在直线代码中，若相邻两条指令 `A`、`B` 之间没有数据依赖、没有内存别名、没有控制依赖，且 `A` 不会陷入异常或被观察（无 volatile、无 atomic、无除法/页错误等可观察陷阱），则交换 `A` 与 `B` 不改变程序的可观察行为。
:::

::: proof
对交换点前后的状态做归纳。交换前，`A` 在状态 `s` 上执行得到 `s_1`，`B` 在 `s_1` 上执行得到 `s_2`。由于 `B` 不读 `A` 写的位置（无 RAW），`A` 不读 `B` 写的位置（无 WAR），两者不写同一位置（无 WAW），且不访问可能别名的内存，`B` 在 `s` 上的输入与在 `s_1` 上相同，`A` 在 `B` 之后执行时的输入也与原来相同。两条指令都不产生可观察副作用，故最终状态相同。异常与 volatile 会把这个论证打破：交换可能改变「哪条指令先触发异常」或「观察者看到几次访存」，所以前提里必须排除。
:::

这条定理的条件在真实机器上很难全部满足。内存别名需要别名分析（第 9 章会讲它的保守性）；除法、页错误、浮点异常都可能让「先执行哪条」变得可观察；`volatile` 和 `atomic` 明确要求顺序。因此调度器通常只在基本块内、对已知无副作用的算术和 load 做重排，跨调用或跨分支的移动要保守得多。

列表调度（list scheduling）是最常见的实现：把 DAG 的结点按「到出口的最长路径」算优先级，每次从就绪集合里取优先级最高的指令发射；若功能单元或寄存器压力受限，就选下一个。它不保证最优，但线性时间、容易加机器模型。调度器的输出还要经过寄存器分配；如果分配后发现溢出太多，可能回退调度或做局部重排。

::: method 调度器的检查顺序
1. 建 DAG：为每条指令的每个源找最近的定义；内存指令按别名分析结果连边；调用连到所有可能被它读写的内存和所有 caller-saved 寄存器。
2. 标优先级：从出口反向算最长延迟路径；有资源约束时把占用周期也算进去。
3. 选就绪指令：优先高优先级；若会显著增加活跃值数量，降级或跳过。
4. 发射并更新资源表；遇到分支、调用、volatile、atomic、屏障指令时清空跨越它的重排窗口。
5. 分配后复核：若某个物理寄存器出现新的 WAR/WAW 导致调度非法，回退该对指令的交换。
:::

边界一：调度不能改变异常顺序。把可能除零的 `idiv` 提前，会让本来不会执行的异常路径先崩；把 load 提前到可能越界的检查之前，会改变程序行为。边界二：调度不能跨 `volatile` 或 `atomic` 重排访存；C11 的内存序和编译器的 barrier 语义优先于调度的性能目标。边界三：调度器的机器模型是近似的；它不知道 cache miss、分支预测和端口冲突的全部细节，所以「调度后更快」要在目标机器上测，不能从 DAG 推出来。边界四：调度可能增加寄存器压力；分配前的调度器要用活跃值数量做启发式惩罚，否则会把一个本来不溢出的程序调成溢出。

列表调度的一次手工推演（延迟数值只用于说明，不代表 x86 实测）：

| 周期 | 就绪指令 | 选择 | 理由 |
|--:|:--|:--|:--|
| 0 | mul1, mul2 | mul1 | 两条都无依赖，先选编号小的 |
| 1 | mul2 | mul2 | 与 mul1 无依赖，可并行发射 |
| 2 | mul2 未完成 | 空 | 乘法的延迟假设为 3，add 还不能发射 |
| 3 | add（依赖 mul1、mul2） | add | 两个源都就绪 |
| 4 | ret | ret | 只有一条出口 |

真实调度器还要看端口/功能单元数量：两条乘法若争同一个乘法器，就不能同周期发射；若寄存器压力已经很高，调度器可能故意延后 mul2，先把 mul1 的结果用掉，减少同时活跃的临时值。**调度不是越并行越好**，它是在延迟、吞吐和寄存器压力之间取平衡。

一个压力反转的例子：IR 是 `t1 = a*b; t2 = c*d; t3 = t1+t2; t4 = t3*e`。把两条乘法排在一起，`t1` 和 `t2` 同时活跃；先算 `t1`、立刻加 `t3`、再算 `t2`，同时活跃的值少一个，但第二条乘法的延迟无法重叠。分配器若只有 3 个寄存器，前一种调度可能多溢出，后一种反而更快。调度器在分配前做，要用「活跃值数量」做代价惩罚；分配后做，则已经知道溢出位置，可以针对性重排。

边界再补两条。第一，`volatile` 访问、`atomic` 操作、内存屏障、内联汇编的 `"memory"` clobber 都是硬屏障；调度器不能把普通访存跨越它们，也不能把屏障两侧的屏障重排。第二，可能陷入异常的指令（除法、可能缺页的 load、浮点异常）不能随意提前；把 `x / y` 提前到「`y == 0` 的检查」之前，会改变程序的可观察行为。调度器要么证明不会陷入，要么把它们当作有副作用的指令。

调度的边界可以列成一张表，遇到「能不能移」的问题直接查：

| 边界 | 允许 | 不允许 |
|:--|:--|:--|
| 数据依赖 | 无 RAW 的指令交换 | 读后写的指令跨越 |
| 内存 | 证明不别名的 load/store 重排 | 可能别名的访存跨越 |
| 调用 | 纯寄存器计算跨到调用前 | 依赖返回值或内存副作用的指令 |
| 异常 | 不会陷入的算术 | 除法、可能缺页的 load 提前 |
| 观察 | 无 volatile/atomic | 跨 volatile/atomic/屏障重排 |

这张表不是调度算法的全部，但它能解释大多数「为什么编译器不帮我重排」的问题。调度器不是万能的；它只能在语言和 ABI 允许的自由度里做选择。

调度与寄存器压力的取舍可以用一个具体数字说明。假设两条独立乘法各需 3 周期，加法需 1 周期，机器只有一个乘法器：

| 调度 | 乘法重叠 | 同时活跃值 | 完成周期 |
|:--|:--|--:|--:|
| 先乘1、再加、再乘2 | 无 | 2 | 3+1+3=7 |
| 乘1、乘2、加 | 部分 | 3 | 3+3+1=7（乘法器串行） |
| 乘1、乘2、加（双乘法器） | 完全 | 3 | 3+1=4 |

在单乘法器上，两种调度的完成时间一样，但第二种多一个活跃值，可能多溢出；在双乘法器上，第二种才真正省时间。调度器要知道目标的功能单元数量，否则「并行」只是幻觉。目标描述的调度资源就是为这个服务的。

调度器与分配器的顺序没有唯一答案。分配前调度自由度大，但不知道最终寄存器；分配后调度知道物理寄存器，但反依赖变多。常见做法是「分配前做轻量调度，分配后做局部重排」，并在两次之间传递「哪些值跨调用/在循环里」的信息。把顺序当成教条（「必须先调度」或「必须先分配」）会在某一类程序上吃亏。

调度窗口的大小也是设计变量。窗口越大，越可能找到好的重排；但寄存器压力、编译时间和代码体积都会上升。很多后端只在基本块内调度，跨基本块只做有限移动（例如把循环不变量外提，那是另一类优化）。把「窗口」写进目标描述/编译选项，而不是硬编码在调度器里，才能按优化级别调整。

## 7.6 目标描述与可移植后端 {#sec-compilers.2.7.6}

如果指令选择、寄存器分配、调用约定、调度规则都硬编码在 pass 里，每加一个目标就要复制一遍后端。可移植后端的做法是把「目标是什么」抽成数据：**目标描述**（target description）声明寄存器、寄存器类、指令模式、成本、调用约定和调度资源；pass 只写算法，读描述。

一个够用的目标描述至少包含六块：

| 块 | 内容 | 缺了会怎样 |
|:--|:--|:--|
| 寄存器文件 | 名字、位宽、别名关系 | 分配器不知道 `%eax` 是 `%rax` 的低 32 位 |
| 寄存器类 | 整数、浮点、向量、标志、栈指针 | 把浮点值分到整数寄存器 |
| 指令模式 | 操作码、操作数约束、结果位置 | 选择器无法匹配，或匹配出非法形式 |
| 成本 | 指令数、延迟、编码长度、压力增量 | 选择器在等价覆盖里选错 |
| 调用约定 | 参数/返回位置、caller/callee-saved、栈对齐 | 调用点破坏活跃值，或栈错位 |
| 调度资源 | 功能单元、发射宽度、延迟 | 调度器把两条指令排到同一周期 |

用一个最小的 JSON 描述示意这些字段怎么落数据（不是任何真实后端的格式）：

```json
{
  "registers": [
    {"name": "rax", "bits": 64, "class": "gpr"},
    {"name": "eax", "bits": 32, "class": "gpr", "alias": "rax"},
    {"name": "rbx", "bits": 64, "class": "gpr"},
    {"name": "xmm0", "bits": 128, "class": "vec"}
  ],
  "calls": {
    "arg_regs": ["rdi", "rsi", "rdx", "rcx", "r8", "r9"],
    "ret_regs": ["rax", "rdx"],
    "caller_saved": ["rax", "rcx", "rdx", "rsi", "rdi", "r8", "r9", "r10", "r11"],
    "callee_saved": ["rbx", "rbp", "r12", "r13", "r14", "r15"],
    "stack_align": 16
  },
  "patterns": [
    {"ir": "add(reg, reg)", "asm": "leal ({0},{1}), {2}", "cost": 1},
    {"ir": "mul(reg, imm)", "asm": "imull 1, {0}", "cost": 2},
    {"ir": "load(add(reg, imm))", "asm": "movl {1}({0}), {2}", "cost": 1}
  ]
}
```

这份描述里没有一条指令选择算法，但算法需要的约束都在：`alias` 告诉分配器 `%eax` 写会清 `%rax` 的高位；`caller_saved` 告诉分配器调用点禁止哪些颜色；`stack_align` 告诉 prologue 生成器 `%rsp` 的模数；`patterns` 告诉选择器每个 IR 形状对应哪条汇编模板。换一个目标，只换这份数据，pass 不动。

模式描述通常不是纯字符串，而是带类型的树模式。一个更接近真实后端的写法：

```text
(reg (add reg reg))                    -> LEA r, [r+r]
(reg (add reg (mul reg imm)))          -> LEA r, [r+r*imm]
(reg (load (add reg imm)))             -> MOV r, [r+imm]
(reg (load (add reg (mul reg imm))))   -> MOV r, [r+r*imm]
(mem (add reg imm))                    -> folded into consumer
```

左边的 `reg`/`mem` 是结果位置约束，不是值类型；右边的模板带占位符，发射时填入具体的虚拟寄存器。选择器把 IR 树的根与这些模式匹配，匹配成功就生成一条机器指令，并把子树的虚拟寄存器作为操作数。若没有模式匹配，就走**合法化**（legalization）：把 IR 拆成更小的操作，直到能匹配。合法化和选择是两件事：前者保证「每个操作都有目标支持的形式」，后者在多种合法形式里选成本最低的。

目标描述最容易漏的是调用约定。把 caller/callee-saved 写成注释而不是数据，分配器就无从知道调用点该禁止哪些颜色；把栈对齐写成常量 `16` 而不是描述字段，换到 32 字节对齐的目标就要改 pass。更隐蔽的是**寄存器别名**：`%eax` 写零扩展到 `%rax`，`%ax` 只写低 16 位，`%ah` 写第 8–15 位；如果描述里不声明这些关系，分配器会把 `%eax` 和 `%rax` 当成两个独立颜色，生成自相矛盾的分配。

::: note 目标描述与 LLVM 的位置
LLVM 用 TableGen 描述寄存器、指令和调度模型，SelectionDAG/GlobalISel 读这些描述做合法化与选择；Rustc 的代码生成后端把 MIR 降到 LLVM IR，再交给 LLVM 的目标描述。本书不展开 TableGen 语法，只强调一点：**目标描述是数据，不是文档**。数据可以被检查器验证（寄存器类是否覆盖所有指令操作数、模式是否有非法组合），文档不能。Rustc Dev Guide 的「LLVM 后端」和「交叉编译与目标」两节可以对照阅读。
:::

边界：目标描述不是正确性证明。一个模式可以语法正确但语义错误（例如把 `sub` 的操作数顺序写反），选择器照样生成代码；一个成本表可以过时，选择器照样按它选。工程上要给描述配三类测试：汇编器能接受所有生成的指令；模式覆盖率达到阈值；生成代码在模拟器或真机上通过 ABI 测试（第 8 章）。另一个边界是可移植性的代价：高度抽象的描述会丢失目标特有的优化机会，例如 x86 的 `lea` 既能算地址又能算算术，RISC 目标没有对应指令；描述要么提供目标特有的模式，要么接受多一条指令。

目标描述还决定了「谁负责寄存器压力」。如果模式允许内存操作数，选择器可以把一个 load 折进加法，减少一个虚拟寄存器；如果描述里没有这种模式，合法化会先生成 load，再生成 add，压力更大。分配器和选择器之间的接口因此不只是指令列表，还包括「哪些操作数可以是内存」的约束。把这些约束写进描述，pass 才能在不认识具体目标的情况下做出合法决策。

### 一个模式匹配的走查

考虑 IR 树 `load(add(p, mul(i, 4)))`，目标是 x86-64。选择器自底向上看：

1. `mul(i, 4)` 匹配「寄存器乘立即数」模式，也可以匹配「寻址比例因子」模式。前者生成 `imull $4, %eax`，后者不生成独立指令，而是把 `4` 作为内存操作数的 `scale`。
2. `add(p, ...)` 匹配「基址+索引」模式；若上一步选了寻址比例，结果就是一个合法的 `base + index*4` 地址，不再需要 `add`。
3. `load` 匹配「基址+索引+偏移」模式，生成 `movl (%rdi,%rax,4), %eax`。
4. 若第 1 步选了 `imull`，第 2 步要生成 `leaq (%rdi,%rax,4), %rdx`，第 3 步再 `movl (%rdx), %eax`。多一条指令，但 `%rax` 上的乘法结果可以被后续使用；两种覆盖的取舍取决于 `i*4` 是否还有别的使用者。

这张走查说明：模式匹配不是「看根结点叫什么」，而是「看整个子树的形状能否被一个操作数约束吸收」。`mul(i,4)` 被吸收进寻址模式时，它的结果没有独立的寄存器，也就没有独立的活跃区间；这会直接影响 `7.2` 的压力计算。选择器和分配器的接口必须传递「这个子树的根是否已经被吸收」的信息，否则分配器会为一个不存在的值分配寄存器。

合法化的例子：目标只支持 32 位立即数，IR 里出现 `x = y + 0x123456789`。选择器找不到直接模式，合法化把常量拆成 `movabsq $0x123456789, %r10` 加 `addq %r10, %rax`；若目标支持「大常量 + 加法」的合成模式，选择器也可以直接匹配。合法化不改变语义，只改变 IR 的形状；它和选择器通常交替执行，直到每个结点都能匹配。

### 目标描述的验证

| 检查 | 方法 | 典型失败 |
|:--|:--|:--|
| 寄存器类别覆盖 | 遍历所有指令操作数，检查类别是否有对应寄存器 | 浮点指令的操作数被分到整数类 |
| 别名一致 | 对每个子寄存器写后读父寄存器，检查值 | `%eax` 写后 `%rax` 高位未清零 |
| 模式可汇编 | 对每个模式生成一条样例，交给汇编器 | 模板占位符数量不匹配 |
| 成本单调 | 对同一子树枚举覆盖，检查低成本覆盖不被支配 | 成本表把 `lea` 设得比 `imul` 贵 |
| 调用约定 | 用 ABI 测试调用生成的函数 | caller-saved 列表漏了 `%r10` |
| 调度资源 | 用模拟器检查发射宽度/延迟 | 两条除法被排到同一周期 |

这些检查能抓住「描述写错」，抓不住「描述缺项」。缺项的典型信号是：某个 IR 形状在合法化后变成一串 `mov`，而目标明明有对应指令；或者分配器把两个别名寄存器当成独立颜色，生成自相矛盾的代码。发现缺项后，先补描述，再补一个回归测试，不要只在 pass 里加特判。

::: note 描述是接口，不是实现
同一个目标描述可以被不同的选择算法消费：贪心最大匹配、DP、LLVM 的 SelectionDAG 覆盖、GlobalISel 的规则匹配。算法不同，结果可能不同，但合法的指令集合和调用约定必须一致。把「目标是什么」和「怎么选」分开，才能在不改算法的前提下加目标；这也是本书把目标描述放在调度之后、验证之前的原因：它同时约束前面的选择和后面的 ABI。
:::

目标特性的差异也要进描述，而不是散落在 pass 里：

| 特性 | 描述字段 | 影响 |
|:--|:--|:--|
| 子寄存器别名 | `alias` | 写 `%eax` 清 `%rax` 高位 |
| 寻址比例 | `scale` | `index*1/2/4/8` 可折进访存 |
| 大立即数 | `imm_bits` | 超过范围要 `movabs` |
| 对齐要求 | `align` | `movaps` 需要 16 字节对齐 |
| 调用约定 | `calls` | 参数/返回/保存/栈对齐 |
| CPU 特性 | `features` | AVX/SSE 的可用性 |

最后一项常被忽略：同一份 x86-64 代码，在不支持 AVX 的机器上不能执行 AVX 指令；可移植后端要么按基线特性生成，要么做运行时分派（多版本函数）。目标描述若只写「x86-64」而不写特性集，生成的代码可能在老机器上崩。

模式表可以写成「IR 形状 → 目标形式 → 约束」：

| IR 形状 | 目标形式 | 约束 |
|:--|:--|:--|
| `add(reg, reg)` | `lea r, [r+r]` | 结果另放，源不被改写 |
| `add(reg, imm)` | `add $imm, r` | 立即数范围 |
| `mul(reg, 2/4/8)` | 寻址比例 | 只用于地址计算 |
| `load(add(reg, imm))` | `mov r, [r+imm]` | 偏移范围 |
| `load(add(reg, mul(reg, 4)))` | `mov r, [r+r*4]` | 索引寄存器位宽 |
| `call(sym)` | `call sym` + PLT32 | 外部符号 |

这张表可以直接变成选择器的规则；每条规则都要有「不匹配时怎么合法化」的退路，否则遇到没列出的形状就崩。

目标描述要版本化。同一个架构的 ABI 可能随系统版本变化（例如栈对齐、红区、参数寄存器的约定），CPU 特性也会增加（AVX-512、SVE）。把描述写成「目标三元组 + 特性集 + 版本」的组合，而不是一个全局常量；否则升级工具链后，旧描述可能生成不兼容的代码。描述文件进版本控制，改动要配回归测试。

目标描述写完后，选择器还需要一组「模式覆盖测试」：对每个模式生成一个最小 IR 树，断言选择器选中该模式；对每个非法组合，断言合法化能降级。没有这组测试，描述里的模式可能永远不被命中，或者命中后生成非法指令。测试输入可以从描述自动生成，不需要手写所有组合。

## 7.7 验证：解释器、差分与模拟器 {#sec-compilers.2.7.7}

寄存器分配是「保持语义的改写」，所以它天然适合差分测试：同一段 IR，一份不分配、直接用字典存变量，另一份按分配结果生成寄存器/栈槽指令，喂同样的输入，比较返回值。两份实现的语义规范必须一致，否则对拍通过只说明「两个错误一致」。实验把这条路径做成三层：

1. **参考解释器**：直接执行 TAC，虚拟寄存器用 Python 字典保存；调用返回确定值。
2. **分配器**：图着色或线性扫描，输出「虚拟寄存器 → 物理寄存器/栈槽」的映射和重写后的指令序列。
3. **寄存器机模拟器**：只有实验声明的物理寄存器、栈槽和调用破坏规则；遇到两个内存操作数、非法目的位置等会直接断言失败。

<pre class="layout">
        TAC IR
          |
          +--&gt; 参考解释器 --------------------------+
          |     env: vreg -&gt; int                    |
          |                                         v
          +--&gt; 区间/冲突图 --&gt; 分配 --&gt; 重写 --&gt; 寄存器机模拟器
                (7.2)          (7.3/7.4)   (7.4)     regs + slots
                                                    |
                                          compare --+--&gt; match / mismatch
                                          200 组固定 seed 输入
</pre>

读图：两条路径共享同一份 IR 和同一组输入，但执行机制不同。参考解释器不关心寄存器，模拟器只认寄存器与栈槽；两者结果一致，说明「分配 + 重写」在测试集上没有改变语义。它不证明指令选择正确，也不证明真实硬件上的 ABI 正确——那需要第 8 章的汇编级检查。

::: def 定义 7.7.1 · 参考语义、差分测试与模拟器 {#def-compilers.2.7.7.1}
**参考语义**（reference semantics）是独立于被测实现、按语言规范直接定义的执行函数。**差分测试**（differential testing）用同一组输入分别执行两个实现，比较可观察输出。**模拟器**（simulator）在这里指按目标机器的寄存器/栈槽/调用破坏规则执行已分配指令的程序，它不模拟完整指令集，只模拟分配器生成的那一小类操作。
:::

::: method 差分测试的固定流程
1. 固定 seed，打印 seed 与用例数；输入范围写进输出，避免「只测了 0」。
2. 先跑参考解释器，再跑被测实现；不要先跑被测实现再「反推」期望值。
3. 比较返回值；若有副作用，比较内存/输出缓冲区的快照。
4. 失败时打印最小信息：程序名、用例号、输入、期望、实际、涉及的虚拟寄存器与分配位置。
5. 修完后重跑全部用例，并保留一个「已知会失败」的负控制，确认测试确实能抓到错误。
6. 对分配器再加不变量检查：同一个程序点活跃的两个虚拟寄存器不能同位置；跨调用值不能在 caller-saved；每个使用位置都有定义。
:::

实验的真实输出（节选）：

```text
== calls ==
TAC ops=9  vregs=10  max_pressure=4 at point 1
callee-saved live-across-call: ['d', 's', 't']

[coloring]
  spilled=-  slots=0
  allocated ops=17 (tac=9, spill moves=0)
  differential coloring: 200/200 match

[linear]
  spill: 0->slot0
  spilled=['s']  slots=1
  allocated ops=17 (tac=9, spill moves=3)
  differential linear: 200/200 match
```

200 组输入由 `random.Random(20261020)` 生成，范围 `[-40,40]`；循环程序的 `n` 被限制在 `[0,8]`，避免步数爆炸。两次分配、两种算法都通过，说明在这个测试集上「分配 + 溢出重写 + 调用约束」的组合没有语义偏差。注意「通过」的范围：它只覆盖实验内置的 4 个程序，不覆盖所有 IR 形状。

::: thm 定理 7.7.1 · 分配正确性的模拟器充分条件 {#thm-compilers.2.7.7.1}
若（a）每条 IR 指令的重写保持「读所有源、再写目的」的顺序；（b）溢出虚拟寄存器的每次定义都写槽、每次使用都读槽；（c）跨调用值只放在 callee-saved 寄存器或栈槽；（d）模拟器按目标 ABI 的破坏集合执行调用；则对任意终止的输入，模拟器返回值等于参考解释器返回值。
:::

::: proof
对参考解释器的执行步数归纳，维护不变量：在每个程序点，模拟器的每个活跃虚拟寄存器对应的位置保存着参考解释器同名变量的值，且不同活跃虚拟寄存器不共享位置。初始时参数被放进各自位置，空槽不影响。每条指令按（a）读源、算、写目的，参考解释器同步更新；溢出值按（b）在定义时写槽、使用时读槽，模拟器读到最新值。调用点按（c）（d）不破坏活跃值，返回值按约定放进 `%rax` 后再搬到目的位置。分支条件由相同值算出，走同一分支。终止时返回值在 `%rax`，与参考解释器的返回值相同。
:::

证明条件（d）里的「按目标 ABI」是外生假设：模拟器把哪些寄存器标成 caller-saved，必须和真实 ABI 一致；如果模拟器的破坏集合写错，证明不成立，测试也可能放过错误。实验把破坏集合硬编码为 `rax`、`rcx` 和 scratch，和它自己的 `K=4` 分配池一致；换目标时要改这份数据，而不是改证明。

不变量检查比差分更早暴露问题。实验里可以单独打开以下断言：

| 检查 | 断言 |  Failure 说明 |
|:--|:--|:--|
| 区间合法 | 每个虚拟寄存器的 `start <= end`，使用点落在区间内 | 活跃分析或编号错 |
| 冲突边 | 同一 `live_in` 内任意两点有边 | 建图漏边 |
| 着色合法 | 每条边的两端颜色不同 | 选择阶段错 |
| 溢出完整 | 溢出的每个定义有写槽、每个使用有读槽 | 重写只做一半 |
| 调用约束 | 跨调用值的位置不在 caller-saved | 7.8 的错误 |
| 编码合法 | 不生成「两个内存操作数」或非法目的位置 | lowering 错 |

这些断言不依赖「参考答案」是否正确，因此能抓住「参考解释器和被测实现一起错」的一部分情况。它们仍然抓不住「两边对语言语义的理解都错」，例如都把有符号溢出当回绕；这类问题要靠语言规范和第 9 章的 UB 讨论。

边界：第一，差分测试的覆盖率取决于程序生成器；固定 4 个手写程序只能证明这些形状。第二，模拟器不是硬件：它不模拟标志位的全部语义、不对齐异常、不模拟 cache 和乱序，因此它不能替代第 8 章的 ABI 测试。第三，参考解释器可能和被编译程序共享同一个错误假设（例如调用返回值公式），对拍通过不等于语义正确；要尽量让参考实现简单、独立、可审查。第四，随机测试不是证明；第 10 章会把「找到一个 bug」和「证明没有 bug」的区别讲清楚。

测试集要覆盖不同的区间形状，而不只是不同的算术：

| 形状 | 例子 | 主要覆盖 | 抓不到 |
|:--|:--|:--|:--|
| 直线 | `straight` | 高压、溢出、两地址 lowering | 分支合流 |
| 循环 | `loop` | 回边拉长区间、循环深度权重 | 调用破坏 |
| 分支 | `branch` | 合流、不同路径的活跃集 | 长区间溢出 |
| 单调用 | 一个 `call` | caller-saved 禁止 | 多次调用的累积破坏 |
| 多调用 | `calls` | 跨多个调用、callee-saved 竞争 | 参数传递（第 8 章） |
| 深递归/大常量 | 手写 | 栈槽数量、立即数范围 | 寄存器别名 |

失败后先缩小，不要直接改代码。缩小的顺序是：固定 seed，减少输入范围；删掉与失败无关的指令；把循环次数降到 1；把两个调用删到一个；最后得到「最短仍失败」的程序。实验的负控制已经是最小例子：一个函数、两次调用、三个跨调用值。缩小后把程序贴进回归测试，再修分配器；否则修完只验证了「这个大程序过了」，没验证「这个机制对了」。

日志也要为缩小服务。每条失败至少打印：程序名、用例号、输入、参考值、实际值、失败指令下标、涉及的虚拟寄存器、它们的分配位置、该点的 `live_in`。只打印「mismatch」不够；没有位置信息，你无法判断是分配错、重写错、还是模拟器的调用语义错。

```bash
python3 experiments/ch07/regalloc_lab.py --program calls --cases 200 \
    --seed 20261020 --dump-code
```

这条命令把分配后的指令序列打出来，配合参考解释器逐步对照，能直接看到 `d` 和 `t` 在调用后的值跳变。若只想看负控制，加 `--program calls` 并观察输出的最后一段；实验默认会跑负控制，且只有在确实抓到错误时才打印 `negative control OK`。

验证也分层，每层能回答的问题不同：

| 层级 | 工具 | 能说明什么 | 不能说明什么 |
|:--|:--|:--|:--|
| 不变量 | 断言 | 分配结果满足冲突/调用约束 | 语义是否正确 |
| 差分 | 参考解释器 | 测试集上语义一致 | 所有输入、真实硬件 |
| 汇编 | clang/objdump | 生成的指令合法、位宽正确 | ABI 运行时行为 |
| 运行 | 模拟器/真机 | 调用约定、栈对齐的实际效果 | 未覆盖的路径 |

层级越高，越接近真实；层级越低，越容易定位。一个 bug 往往需要两层证据：差分告诉你「结果错」，汇编告诉你「哪条指令错」，不变量告诉你「哪个约束没进模型」。

模拟器与真机的差距不止对齐。模拟器通常不建模 cache、分支预测、乱序执行和端口冲突，也不建模信号/异常; 它能验证「值对不对」，不能验证「性能好不好」或「异常路径对不对」。把模拟器当语义 oracle 是合理的，把它当性能 oracle 是错的。第 8 章的 Rosetta 例子说明：模拟器甚至可能不触发真机会触发的对齐异常。

日志要能复现。实验打印 seed、用例数、K、颜色池、程序名；失败时打印输入、期望、实际、指令下标。真实分配器还应打印「版本/目标/优化级别」，否则同一段日志在不同构建上无法比较。可复现的日志比「我这边是好的」有用得多。

## 7.8 agent 错误：调用后复用已破坏寄存器 {#sec-compilers.2.7.8}

这一节复盘一个 agent 生成分配器的典型失败模式。任务描述是「为 TAC 写一个图着色分配器，支持函数调用」。agent 完成了区间构造、冲突图、简化—选择、溢出重写，单元测试用的是一个没有调用的函数，全部通过。它把 `K` 设为 4，颜色池是 `%rax、%rcx、%rbx、%r12`；它知道 `%rbx、%r12` 是 callee-saved，但没有把「调用点会破坏 `%rax、%rcx`」写进约束。

**症状**。把测试换成带两次调用的 `calls` 后，返回值随输入变化，但和参考解释器对不上；有时差几十，有时看起来「几乎正确」。用 `clang` 生成的真实程序不一定崩，因为被调用函数可能恰好没碰 `%rcx`；agent 的第一版测试里，被调用函数是空的，所以错误潜伏了。

**根因**。分配器把跨调用的 `d` 放进 `%rcx`、把 `t` 放进 `%rax`。被调用函数按 ABI 可以任意改写这两个寄存器；模拟器在调用点把它们改成垃圾值，后续 `t = s + d` 用的是垃圾。冲突图没有「调用点」这个结点，也没有把 `%rax、%rcx` 标成「在调用点被定义」；简化—选择看到的是一张静态图，不知道时间轴上的破坏。

**如何发现**。三个检查按成本从低到高：

1. 打印每个调用点的 `live_in`，再打印这些虚拟寄存器的分配位置；若位置在 caller-saved，直接报错。实验的输出是 `callee-saved live-across-call: ['d', 's', 't']`，而错误分配里 `d->%rcx`、`t->%rax`。
2. 在模拟器里执行「调用破坏」：把 caller-saved 置为可识别的毒值，再继续执行；参考答案 145，错误程序 183，立刻暴露。
3. 看真实编译器的选择：clang `-O2` 把跨调用的 `x` 放进 `%ebx`，并 `pushq %rbx` 保存；`-O0` 则放进 `-4(%rbp)`，调用后重载。两种都在告诉你「跨调用值不能留在 caller-saved」。

真实的负控制输出：

```text
== negative control: allow caller-saved across call ==
  regs : a->%rcx  b->%rax  d->%rcx  q->%rcx  r->%rax  s->%rbx  t->%rax  u->%rcx  v->%rax  w->%rax
  spilled=-  slots=0  potential=-
  cross-call values in caller-saved: ['d', 't']
  case 0: inputs=[18, 0] reference=145 allocated=183
    d: assigned %rcx, live across call, clobbered by the callee
    t: assigned %rax, live across call, clobbered by the callee
  negative control OK: the unconstrained allocator is wrong on this case
```

::: ex 例 7.8.1 · 145 与 183 的差从哪来 {#ex-compilers.2.7.8.1}
输入 `a=18, b=0`。参考解释器：`s=18`、`d=18`、第一次调用 `g` 返回 `(1*37+7) % 97 - 30 = 14`、`t=s+d=36`、第二次调用 `h` 返回 `(2*37+11) % 97 - 30 = 55`、`u=t+q=91`、`v=s+t=54`、`w=u+v=145`。

错误分配把 `s` 放在 `%rbx`（安全），`d` 放在 `%rcx`、`t` 放在 `%rax`（都不安全）。第一次调用把 `%rcx` 改成毒值，`t = s + d` 用了毒值；第二次调用又把 `%rax` 改成毒值，`t` 再次被覆盖；`u`、`v`、`w` 继续传播，最终 183。

把每个中间值打印出来：`s` 始终 18，`d` 和 `t` 在调用后跳变。这一步就能把错误缩到两个虚拟寄存器，而不是停留在「结果不对」。
:::

这些数来自实验的参考解释器，调用计数从 1 开始。真正重要的是「哪些值在调用后跳变」，而不是具体数字；换一组输入，公式不变，跳变的位置也不变。

**修复**。有三个层次：

| 修复 | 做法 | 代价 | 适用 |
|:--|:--|:--|:--|
| 禁止颜色 | 跨调用虚拟寄存器的允许集合去掉 caller-saved | 可能多溢出 | 最小改动，首选 |
| 分裂区间 | 在调用点把区间切开，调用前存、调用后取 | 插入 load/store | 值很长、callee-saved 不够 |
| 换寄存器类 | 把值放进 callee-saved 或栈槽 | 保存/恢复开销 | 全局策略 |

错误的「修复」也要点名。第一，把所有 caller-saved 在 prologue 保存、epilogue 恢复：这只能保护「整个函数体不调用别人」的情况；函数中间调用 `g` 时，`g` 仍会改写这些寄存器，保存的副本在内存里，后续使用必须从内存重载，不能只靠 epilogue 恢复。第二，把 `%rcx` 从 caller-saved 列表里删掉：这会让所有调用者对被调用者的假设失效，是 ABI 违规，不是修复。第三，把所有跨调用值都溢出：正确但可能显著变慢；先试禁止颜色，再看溢出代价。

::: method 调用破坏的排查顺序
1. 列出所有调用点，打印每个点的 `live_in`；这些就是「必须活过调用」的集合。
2. 对每个集合成员查分配位置；位置在 caller-saved 就是 bug，不管测试是否通过。
3. 在模拟器/测试里注入破坏：把 caller-saved 改成不会偶然相等的毒值；不要用 0，因为 0 可能和正确答案巧合。
4. 若必须跨调用，检查是否在调用前保存、调用后恢复；保存的位置本身不能被调用破坏。
5. 最后看真实编译器：clang 选 callee-saved 还是栈槽，能给你成本直觉，但不能替代你的分配器约束。
:::

这个错误之所以常见，是因为它同时满足「局部测试通过」和「代码看起来合理」。分配器的单元测试通常只检查「同一条边不同色」，不检查「调用点的 live-in 是否落在安全颜色」；后者需要把 ABI 的破坏集合作为输入。把破坏集合写成目标描述的数据（`7.6`），并在分配前做一次断言，成本很低，收益很高。

最后一个边界：调用破坏不只发生在 `call`。某些指令会隐式写寄存器（`cpuid`、`rdtsc`、系统调用、内联汇编的 clobber 列表），某些目标把返回地址放在链接寄存器（ARM64 的 `x30`，第 8 章）。分配器不能只识别 `call` 这个助记符，而要读目标描述里的「指令 clobber 集合」；否则换一个目标，同一个 bug 会以另一种形式回来。

把错误分配和正确分配并排看，差异只在两个位置：

```text
正确（图着色，K=4）:
  d -> %rbx        t -> %rbx        s -> %r12
  call g
  t = s + d        ; 读 r12 和 rbx，二者都跨调用安全
  call h
  ...

错误（允许 caller-saved 跨调用）:
  d -> %rcx        t -> %rax        s -> %rbx
  call g           ; %rcx 被破坏，%rax 也被破坏
  t = s + d        ; 读 rbx 和 rcx：rcx 已是毒值
  call h           ; %rax（t）再次被破坏
  ...
```

第二段的 `t = s + d` 在源码层面完全正确，错的是「`d` 住在 `%rcx`」这个前提。定位时不要从加法指令往回猜，直接查 `d` 的分配位置和它是否跨调用；两条信息一交叉，结论就出来了。

测试矩阵应该显式包含「被调用函数故意破坏所有 caller-saved」的情况。可以写一个汇编辅助函数，把 `%rax、%rcx、%rdx、%rsi、%rdi、%r8–%r11` 全部写成可识别的毒值再返回；任何跨调用值留在这些寄存器里，测试都会失败。若只调用一个「什么都不做」的函数，编译器/解释器可能恰好保留寄存器，bug 就潜伏下来。

| 测试 | 被调用函数行为 | 能否抓到本 bug |
|:--|:--|:--|
| 叶子函数，无调用 | 不适用 | 不能 |
| 调用空函数 | 不改寄存器 | 不能（可能偶然通过） |
| 调用返回常量的函数 | 只写 `%rax` | 只能抓到 `%rax` |
| 调用破坏全部 caller-saved 的函数 | 写 `%rax,%rcx,%rdx,%rsi,%rdi,%r8–%r11` | 能 |
| 两次调用，中间使用跨调用值 | 同上 | 能，且能抓到第二次破坏 |

回归测试要断言「分配结果里没有跨调用的 caller-saved 值」，而不只是断言「输出等于期望」。前者是机制级测试，换一个程序仍然有效；后者是结果级测试，可能被巧合通过。实验的负控制就是机制级断言：打印 `cross-call values in caller-saved: ['d', 't']`，再跑输入确认数值错。两者结合，才能既定位又防回归。

最后一个工程细节：把 clobber 集合放进目标描述，而不是写死在分配器里。x86-64 的 caller-saved 与 ARM64 的不同，ARM64 还没有 `%rax` 这种命名；写死会让分配器在换目标时静默出错。目标描述里增加一个 `clobbers` 字段，分配器在建图时读取；测试里再写一个「描述与 ABI 文档一致」的检查，防止描述本身漂移。

把回归测试写成断言，而不是只写「输出等于 145」：

| 断言 | 写法 | 抓什么 |
|:--|:--|:--|
| 跨调用位置 | 对每个调用点，`live_in` 的分配位置不在 caller-saved | 本节的 bug |
| 溢出完整 | 每个溢出的定义有写槽、每个使用有读槽 | 重写只做一半 |
| 两地址合法 | 目的寄存器不等于仍在读取的源 | lowering 覆盖源 |
| 调用后值稳定 | 调用前后打印跨调用值，必须相等 | 破坏/保存恢复错 |
| 颜色合法 | 冲突边两端不同色 | 选择阶段错 |

前两条是机制级，后三条是结果级；机制级断言在程序变化后仍然有效，结果级断言容易被巧合通过。两者都写，测试才有诊断力。

保存/恢复的两种写法：

```asm
; 方案 A：调用前保存，调用后恢复
movq %rcx, -16(%rbp)
callq _g
movq -16(%rbp), %rcx

; 方案 B：跨调用值本来就在 callee-saved
movq %rdi, %rbx
callq _g
addq %rbx, %rax
```

方案 A 对每个调用点插入两条访存，方案 B 在 prologue/epilogue 各一条 push/pop。若值跨多个调用，方案 A 要在每个调用点保存/恢复（或保存一次、每个调用后重载），方案 B 只付一次保存成本。分配器选择哪种，取决于值的活跃范围、调用点数量和 callee-saved 的竞争；不能一律说「溢出到栈最安全」。

## 7.10 本章陷阱（8–15 条） {#sec-compilers.2.7.10}

::: errata 本章陷阱
1. **用变量名而不是程序点判断冲突**。现象：两个不同块里的临时变量同名，分配器把它们当成一个区间；或反过来，同一个值在两条路径上被当成两个值。原因：区间由程序点和活跃变量分析决定，不由源程序的变量名或块结构决定。修复：打印每个点的 `live_in`/`live_out`，用程序点核对，而不是用变量名核对。
2. **只按 `live_in` 连边，漏掉「定义与 `live_out`」的边**。现象：`d = a - b` 的 `d` 与仍活跃的 `a` 同色，发射时先 `mov` 覆盖了源。原因：3 地址语义下一次读两个源，两地址 lowering 会破坏这个假设。修复：建图时补定义—活跃边，或在 lowering 时检测目的寄存器与仍在读取的源重合，必要时用 scratch。
3. **把调用点当成普通指令**。现象：测试在「被调用函数不碰 rcx」时通过，换一个被调用函数就错。原因：caller-saved 寄存器在调用点被破坏，冲突图里没有这个约束。修复：把调用点的 `live_in` 与 caller-saved 集合求交，命中的虚拟寄存器禁止使用这些颜色；见 7.8。
4. **溢出代价只看使用次数，不看循环深度**。现象：热循环里的值被溢出，冷代码里的值留在寄存器。原因：代价函数没有按循环深度加权。修复：用 $10^{\mathrm{depth}}$ 或等价的循环权重，并在输出里打印每个值的 cost 与 depth，便于复查。
5. **溢出重写只改定义、不改使用（或反过来）**。现象：使用点读到旧值，或栈槽永远是初始值。原因：重写不是「把虚拟寄存器换个名字」，而是每个定义写槽、每个使用读槽。修复：在重写器里对每个虚拟寄存器收集全部定义点与使用点，逐点替换；用差分测试验证。
6. **认为「度小于 K」就一定能在弹出时拿到颜色**。现象：简化阶段顺利，选择阶段却溢出。原因：度数是删除时的度数，弹出时邻居可能已经占满颜色；无潜在溢出时才有保证。修复：区分「无潜在溢出」与「乐观着色」，不要用简化成功推断最终成功。
7. **线性扫描的过期条件写成 `<=`**。现象：两个区间在端点相接，被分到同一寄存器，后一个值覆盖前一个。原因：区间是闭区间，端点相同表示同一程序点同时活跃。修复：用 `end < start` 过期，并为端点相同的区间保留冲突。
8. **线性扫描抢寄存器时不检查「对当前区间是否合法」**。现象：跨调用区间抢到一个 caller-saved 寄存器，调用后值被破坏。原因：受害者的寄存器不一定在当前区间的允许集合里。修复：只在 `allowed(v)` 内选受害者，否则溢出当前区间。
9. **把区间凸包当成精确活跃集**。现象：循环体外定义、循环体内使用、循环体外再用的值，区间中间一大段空洞，仍然被算作与别人冲突。原因：凸包是保守近似。修复：做活跃范围分裂，或在报告里明确「这是凸包近似，溢出数不是最优」。
10. **合并（coalescing）不检查邻居度数**。现象：消掉一条 `mov` 后，新结点与更多邻居冲突，反而多溢出两个值。原因：合并改变了冲突图的度。修复：用保守合并（Briggs/George 条件），合并后重算度数，不满足就放弃。
11. **把 DAG 当树做指令选择**。现象：共享子表达式被求值两次，若它有副作用或会陷入异常，程序行为改变。原因：树覆盖不记录共享结点。修复：先做公共子表达式消除，或在覆盖时标记共享结点并强制只算一次；有副作用的结点不要重复覆盖。
12. **调度跨过调用或 `volatile` 移动访存**。现象：性能测试通过，语义测试偶发失败。原因：调用可能读写内存、破坏寄存器；`volatile`/`atomic` 的顺序是可观察行为。修复：把这些指令当屏障，只允许不依赖它们的纯寄存器计算跨越；用第 9 章的 UB 与可观察行为清单复查。
13. **把 `K` 当成「所有寄存器」**。现象：着色成功，发射时却和返回值、参数寄存器或栈指针冲突。原因：物理寄存器有固定用途，不能都当自由颜色。修复：把固定用途建成预着色结点或禁止集合，`K` 只数「真正可自由分配」的寄存器。
14. **认为溢出数越少越好**。现象：为了少溢出两个值，把溢出搬到热循环里。原因：溢出代价是动态的，不是静态计数。修复：按循环深度/执行频率加权，比较「溢出指令数 × 动态执行次数」，而不是只比较槽数。
:::

这份清单的用法是「现象 → 位置 → 约束 → 验证」：先按现象找到出错的值或指令，再打印该点的活跃集合和分配位置，然后检查对应约束（冲突边、调用破坏、两地址、屏障），最后用差分测试或汇编检查确认。不要一上来改分配器；大多数错误在「约束没进模型」，不在「算法写错」。

把 14 条按「建图、分配、溢出、调用、选择、调度」六组归档，比按编号背更有用：建图错会让所有区间看起来都冲突；分配错会让颜色非法；溢出错会让使用点读到旧值；调用错会让值在 call 后跳变；选择错会让指令数异常；调度错会让语义偶发失败。每组配一个可复现的实验或反汇编检查，复习时先跑检查，再看对应的条目。

失败反推的顺序是：先看差分测试的「第一个不匹配」在哪条指令，再看该指令涉及的虚拟寄存器的分配位置，最后看该点的活跃集合与约束。若位置在 caller-saved 且跨调用，是调用约束；若目的寄存器等于仍在读取的源，是 lowering；若使用点读到旧值，是溢出重写；若颜色本身非法，是选择。这个顺序能把「结果不对」缩到一条指令、一个约束，而不是重读整个分配器。

从错误到实验的映射也要练：看到「调用后值不对」想到 `--program calls` 与负控制；看到「溢出太多」想到 `--program straight --dump-intervals`；看到「线性扫描与图着色不同」想到 `--dump-code`；看到「调度/选择」想到 clang 的 `-O1/-O2` 汇编。每个现象都有对应的命令，实验不是只跑一次的数字，而是排查工具。

最后一条：把「不确定」写出来。分配器的启发式、线性扫描的近似、目标成本的数量级，都有适用条件；在笔记里标注这些条件，比写一个看似绝对的结论更有用。

::: sol 答案
**A1** 它跨调用，因此可用颜色只剩 2 个 callee-saved；最少需要 1 个（如果它不与另一个跨调用值同时活跃），但若与另一个跨调用值同时活跃就需要 2 个。两个都被更长区间占着时，选择是：溢出这个值（写槽/读槽），或在调用前把它存到栈、调用后取回（区间分裂），或重新分配更长的区间，把 callee-saved 让给它。不能改用 caller-saved，除非在调用前保存、调用后恢复。

**A2** 不能。指令数只反映代码量，不反映执行频率。还要看：溢出访存落在哪个循环深度、每条溢出指令的动态执行次数、寄存器压力峰值、以及是否引入了额外的 `mov`。两个分配器在同一个测试集上指令数相同，可能一个把溢出放在冷路径、另一个放在热循环。

**A3** 乘法只读寄存器、不访存、不依赖调用的返回值，也不产生可观察副作用，所以它与调用之间没有 RAW/WAR/WAW 或内存依赖；移动它是合法的。`y = g(a)` 本身就是调用，不能移到调用之前；把「调用」移到「调用」之前会改变副作用顺序。若乘法可能陷入异常（整数除法、浮点异常），移动还要受异常顺序约束。

**A4** 不能只凭一个程序下结论。`calls` 的形状是「短区间 + 两个 callee-saved 刚好够」，图着色的全局视野占优；换一个「区间很长、调用很少、寄存器压力低」的程序，线性扫描可能更快且溢出相同。分配器的好坏要按目标程序的分布、编译时间预算和动态执行代价一起评估；本章的对比只说明「信息集不同会导致不同决策」，不是排名。
:::

**A5** `K=3` 时，`calls` 有三个跨调用值 `d,s,t`，而 callee-saved 只有 2 个（若颜色池是 2 caller + 1 callee 或 1+2），必然至少溢出一个。图着色会按代价选一个溢出，线性扫描可能溢出另一个；两者都正确，差别在代价。先改目标描述没有用——寄存器数量是目标事实，不是描述错误；应该先确认 `K` 是否真的只有 3，再决定是接受溢出还是做区间分裂/重物质化。若目标其实有更多寄存器，改描述/颜色池才是对的。

**A6** 两地址指令的目的必须是寄存器，而内存到内存的搬运不合法；当目的在栈槽、源也在栈槽时，需要先搬到 scratch，算完再写回。scratch 是保留寄存器，不计入可分配颜色 `K`；它减少的是「实际可用于虚拟寄存器的物理寄存器数」。若目标寄存器本来就少，保留两个 scratch 会显著降低 `K` 的有效值，这时可以选择只保留一个 scratch、用更多 `mov` 换寄存器，或把部分溢出改成重物质化。

**A7** 不能。200 组输入只覆盖实验内置的 4 个程序形状；它不能证明所有 IR、所有目标、所有 ABI 都正确。还缺：更多程序形状（嵌套循环、异常、可变参数）、静态不变量检查（冲突/调用约束/溢出完整）、汇编级 ABI 测试（第 8 章）、以及形式化证明或更大规模的差分/模糊测试（第 10、11 章）。对拍是必要证据，不是充分证明。

做完这八节，你应该能独立回答三个问题：某个值为什么被放进这个寄存器；某个值为什么被溢出；某个调用点为什么禁止某些颜色。答不上来时，回到对应的区间表、冲突图或已分配指令序列，用数据而不是直觉定位。
