第 7 章把虚拟寄存器变成了物理寄存器，但它对「调用」只做了一个简化模型：调用点会破坏 caller-saved，跨调用值要放 callee-saved 或栈槽。真实机器上的调用还要求栈指针对齐、参数放在约定位置、返回值放在约定寄存器、聚合类型按分类规则传递、callee-saved 在返回前恢复。这些规则合起来叫 **ABI**（application binary interface，应用二进制接口）。ABI 不是建议，是编译器、汇编器、链接器、运行时和操作系统共同遵守的合同。

合同的一侧是调用者，另一侧是被调用者。调用者负责在 `call` 前把 `%rsp` 对齐、把参数放好、把返回值的位置留出来；被调用者负责保存它要用的 callee-saved 寄存器、按约定返回、不破坏调用者的栈。任何一侧少做一步，程序可能在「测试通过」的情况下运行几个月，直到某个库函数用了 `movaps`、某个可变参数函数读了 `%al`、或者某个异常展开走了另一条路径。

一个具体的失败例子。agent 被要求为一个小语言生成 x86-64 代码。它写出的 prologue 是 `pushq %rbp; movq %rsp, %rbp; subq $8, %rsp`，理由是「栈要 16 字节对齐，减 8 更安全」。在它的测试机上，被调用函数都是空的，程序正常返回；换到调用 `printf` 的测试，程序在 libc 的 `movaps` 上崩。它还把 `int` 的 load 写成 `movq 8(%rdi), %eax`，汇编器直接拒绝；它注释说「`add` 的目的不能是内存」，于是把所有 `*p += x` 都拆成 load/add/store。三个错误来自同一个原因：把 ABI 当成「约定俗成的写法」，而不是可检查的合同。

本章实验在 `experiments/ch08/`，入口：

```bash
python3 experiments/ch08/abi_lab.py
```

脚本生成汇编与 C、汇编成 object、用 `llvm-objdump`/`llvm-readelf` 检查，并在 macOS arm64 上通过 Rosetta 的 `arch -x86_64` 真实执行三个小程序：对齐见证、错位见证、`add` 内存形式。它会打印真实的 objdump 片段与退出码；不能执行的环境会明确标注 skipped，而不是伪造输出。

脚本面向 macOS（Mach-O 汇编 + Rosetta 运行）；在 Linux 上它返回 77 并打印手工命令，静态证据可用 `clang -target x86_64-linux-gnu` + `llvm-objdump`，运行证据需要 qemu 或真机。书中的运行输出均来自 macOS arm64 + Rosetta，不冒充 Linux 结果。

## 8.1 ABI 是接口合同：本书的边界 {#sec-compilers.2.8.1}

::: def 定义 8.1.1 · ABI {#def-compilers.2.8.1.1}
**ABI** 是两个已编译模块之间如何互相调用的规范：哪些寄存器传参数、哪些寄存器保存返回值、栈指针在调用点的对齐、聚合类型如何分类、哪些寄存器由 callee 保存、符号如何命名、重定位如何表示。它约束的是机器级接口，不是源语言的类型系统；两个源语言可以共享同一个 ABI（例如 C 和 Rust 的 `extern "C"`），同一个源语言也可以有多个 ABI（例如 x86-64 的 SysV 与 Windows x64）。
:::

本书只写「编译器生成与验证」这一侧。指令语义、寄存器表、ELF 格式、链接与重定位的基础在《Linux 系统与内核》1.14–1.16 与 1.7；本章不重写这些内容。你需要能看懂 `%rdi` 是第一个整数参数、`%xmm0` 是第一个浮点参数、`call` 会把返回地址压栈，但不要求背完整指令表。

把合同拆成编译器必须决定的事：

| 合同项 | 编译器要决定/生成 | 验证手段 |
|:--|:--|:--|
| 参数位置 | 整数前 6 个进 `%rdi…%r9`，浮点前 8 个进 `%xmm0…%xmm7`，其余进栈 | 反汇编看参数搬运 |
| 返回值 | 整数 `%rax`/`%rdx`，浮点 `%xmm0`/`%xmm1`，大聚合用隐藏指针 | 反汇编看 `ret` 前的寄存器 |
| 栈对齐 | `call` 前 `%rsp % 16 == 0`，callee 入口 `8` | 静态走 `%rsp` + 运行时见证 |
| callee-saved | `%rbx,%rbp,%r12–%r15` 保存/恢复 | 反汇编看 push/pop 或栈槽 |
| caller-saved | `%rax,%rcx,%rdx,%rsi,%rdi,%r8–%r11` 可被破坏 | 跨调用值的位置检查 |
| 聚合分类 | ≤16 字节按八字节分类，超过走内存 | 反汇编看 `%rax`/隐藏指针 |
| 可变参数 | `%al` 放向量寄存器个数 | 反汇编看 `movb` 到 `%al` |
| 符号与重定位 | 外部调用发 `R_X86_64_PLT32` | `llvm-readelf -r` |

这张表里没有一条是「风格」。每一条错了，都可能让另一个编译单元（甚至同一个程序里的另一个函数）读到错的值。ABI 的麻烦在于：错误往往不在生成错误的那条指令附近暴露，而在被调用者使用错误前提时暴露。

六条历史错误在本书里的处理位置：

| # | 历史错误 | 正确写法 | 本章位置 |
|--:|:--|:--|:--|
| 1 | 栈对齐多减 8 | `call` 前 0 mod 16；callee 入口 8；`push %rbp` 后 `sub` 是 16 的倍数 | 8.2、8.5、8.7 |
| 2 | `movq 8(%rdi), %eax` | 32 位目的必须 `movl` | 8.6、8.7 |
| 3 | 说 `add` 目的不能是内存 | `add` 可读改写内存；两个操作数不能同时为内存 | 8.6、8.7 |
| 4 | 把 `x30` 当 callee-saved | `x30` 是 link register；callee-saved 按 AAPCS64 是 `x19–x28` | 8.4、8.7 |
| 5 | PLT 懒绑定跳 `_init` | 懒绑定经 PLT0 解析 | 8.1、8.7（交叉引用 Linux 1.7） |
| 6 | 分配器漏 footer | `need = align_up(n + HDR + FTR, ALIGN)`；112B 回归 | 8.1、8.7（交叉引用 Linux 9.9.6） |

后两条不属于代码生成，但它们提醒一件事：编译器输出不是终点。代码生成正确，只是把程序交给链接器和分配器；下一层的合同同样要验证。本书只给验证方法和回归条件，不重写链接器或分配器。

### PLT 懒绑定：编译器只负责发对重定位

在 x86-64 Linux 上调用一个外部函数 `ext`，编译器生成的是 `call ext`，并在目标文件里留下一个重定位：

```text
Relocation section '.rela.text' at offset 0x118 contains 1 entries:
    Offset             Info             Type               Symbol's Value  Symbol's Name + Addend
0000000000000002  0000000400000004 R_X86_64_PLT32         0000000000000000 ext - 4
```

这是 `abi_lab.py` 的真实输出（`clang -target x86_64-linux-gnu -O1 -c plt.c` 后 `llvm-readelf -r plt.o`）。编译器的工作到此为止：它告诉链接器「这里要调用 `ext`，请按 PLT 规则解析」。链接器若决定走 PLT，会生成 `.plt` 与 `.got.plt`：PLT0 是解析器入口，PLT[n] 先跳到 GOT 里的函数地址，未解析时把重定位下标压栈并跳回 PLT0。懒绑定必须跳 PLT0，而不是 `_init`；`_init` 是进程初始化代码，不是动态解析器。

本机是 macOS，没有 ELF 链接器，所以只能验证编译器侧的重定位，不能验证链接器生成的 PLT。在 Linux 上的验证步骤是：

```bash
llvm-readelf -S app | grep -E '\.plt|\.got'
llvm-objdump -d --section=.plt app
```

读 `.plt` 时检查三件事：PLT0 先压 GOT+8（link_map），再跳 GOT+16（解析器）；每个 PLT[n] 的未解析路径最后跳到 PLT0，而不是 `_init`；`.rela.plt` 的下标与 PLT[n] 的压栈立即数一致。这三条都能用 `llvm-objdump` 的注释和 `llvm-readelf -r` 对照，不依赖反汇编器猜符号。本书不重写 PLT 的字节布局；你只需要知道「编译器发 PLT32，链接器决定 PLT，懒绑定回 PLT0」。

::: note 为什么本书坚持「只交叉引用」
链接与加载的完整机制（节区、符号表、GOT、重定位、动态链接器）属于《Linux 系统与内核》1.7。编译器书如果把 PLT 展开讲，会挤掉寄存器分配、ABI 测试等真正属于编译器的问题，也容易把「链接器行为」误写成「编译器生成」。本章的边界是：编译器必须发对重定位，必须知道外部调用可能破坏 caller-saved；PLT 的内部形状由链接器负责，验证方法给出即可。
:::

### 分配器 footer：112B 回归

分配器的 footer 属于《Linux 系统与内核》9.9.6，本章不重写。这里只记与编译器相关的回归条件：一次分配需要同时容纳用户数据、头部和尾部，公式是

`need = align_up(n + HDR + FTR, ALIGN)`

以 `HDR = FTR = 16`、`ALIGN = 16` 的实现为例，请求 `n = 112` 时，漏掉 footer 会算成 `align_up(112 + 16, 16) = 128`，而正确值是 `align_up(112 + 16 + 16, 16) = 144`。128 字节的块里，头部占 16、用户占 112，已经没有 footer 的位置；footer 会写进下一个块的头部。分配器若把 `112` 当作「刚好」，就会在相邻块上踩内存。若常量是 `HDR = FTR = 8`，临界请求会变成 120，而不是 112；关键是公式，不是某一个数字。

编译器为什么会关心分配器？代码生成假设 `malloc` 返回的指针至少 16 字节对齐、不同分配块不重叠、块头不会被用户写坏。footer 漏写会让相邻块的元数据被覆盖，表现为「编译器生成的代码写坏了堆」，但根因在分配器。验证时用 ASan/guard 页或 golden 分配序列，把 `112` 作为回归输入；不要在没有证据时把它归咎于代码生成。

::: errata 三条边界
1. ABI 不是「优化建议」。栈对齐、callee-saved、参数位置少做一步就是未定义行为，不是「可能慢一点」。
2. 汇编器只检查语法与编码，不检查 ABI。`movq` 到 `%eax` 会被拒绝，但「`push %rbp` 后 `sub $8`」能汇编，错的是运行时前提。
3. 本机通过不等于跨平台通过。SysV 与 Windows x64 的寄存器角色不同，AAPCS64 又没有 `%rax`；目标描述和测试都要按目标分别写。
:::

谁检查什么，决定了错误在哪一层暴露：

| 层 | 能检查 | 不能检查 |
|:--|:--|:--|
| 编译器前端/中端 | 类型、参数个数、聚合布局 | 机器寄存器与栈对齐 |
| 汇编器 | 助记符、操作数宽度、编码 | ABI 语义、栈对齐、callee-saved |
| 链接器 | 符号、重定位、PLT/GOT | 运行时栈行为 |
| 运行时/测试 | 实际调用、对齐、返回值 | 未覆盖的路径 |
| 静态检查器 | prologue 的 `%rsp` 账、保存/恢复配对 | 数据相关的未定义行为 |

编译器能保证的是「生成的指令符合它读到的 ABI 描述」；汇编器保证「这些指令能编码」；链接器保证「符号能接上」。三者都不保证「运行时的栈一定对齐」。所以 ABI 测试必须自己走一遍 `%rsp`，不能把责任推给工具链。

PLT 的分工也是同理。编译器在目标文件里留下 `R_X86_64_PLT32`，这是它能做且必须做对的事；链接器决定建不建 PLT、PLT0 放在哪、GOT 槽怎么填。把「PLT 跳 `_init`」写进编译器文档，是把链接器的职责错记到编译器头上；验证时应该用 `llvm-readelf -r` 看重定位，用 `llvm-objdump -d --section=.plt` 看链接器的产物，两个证据分开。

ABI 变体是本章最常见的误用来源。同一段 x86-64 汇编，在 Linux/macOS 上按 SysV 调用，在 Windows 上按 Microsoft x64 调用；后者的前四个整数参数是 `%rcx,%rdx,%r8,%r9`，`%rdi/%rsi` 反而是 callee-saved，还有 32 字节 shadow space。把这些差异写进目标描述，而不是散落在生成器里，才能在换目标时不复制一套代码。ARM64 的 AAPCS64 又是另一套：`x0–x7` 传参，`x8` 是间接结果，`x30` 是 LR。本章的例子分别标注目标，不把 SysV 的结论推广到所有平台。

ABI 违反与语言层 UB 要分开归因。ABI 违反是「两个模块对机器接口的理解不一致」，例如调用者以为 `%rbx` 会被保存、callee 没有保存；语言层 UB 是「源程序本身没有定义」，例如有符号整数溢出。前者可以用反汇编和运行时见证定位，后者要靠规范、sanitizer 和优化对照（第 9 章）。把 ABI 错误当成 UB 会导致「换个编译器就好了」的误判；把 UB 当成 ABI 错误会导致在生成器里加一堆无用的保存/恢复。

目标三元组（`x86_64-unknown-linux-gnu`、`aarch64-apple-darwin` 等）把「架构 + 厂商 + 系统 + ABI」编码在一起；同一条 `x86_64` 可以对应 SysV 或 Windows x64，同一个 `arm64` 可以对应 AAPCS64 或 Apple 的变体。生成器若只按架构选寄存器表，不看系统/ABI，就会在跨平台时错。目标描述里应该同时有 `arch` 与 `abi` 两个维度，而不是一个字符串。

ABI 的很多项可以直接写进目标描述，而不是散落在生成器里：

| 合同项 | 目标描述字段 | 生成器读取后做什么 |
|:--|:--|:--|
| 参数寄存器 | `arg_regs` | 按顺序搬运参数 |
| 返回寄存器 | `ret_regs` | 返回值放到约定位置 |
| caller-saved | `caller_saved` | 调用点禁止跨调用值 |
| callee-saved | `callee_saved` | prologue 保存/epilogue 恢复 |
| 栈对齐 | `stack_align` | 计算 `sub` 与 padding |
| 聚合分类 | `aggregate_rules` | 决定寄存器/内存传递 |

把这些写成数据的好处是：换 ABI 时只改描述，生成器不用改；测试也可以按描述自动生成。坏处是描述本身可能写错，所以需要 8.7 的合规测试。描述与测试是一对：描述声明合同，测试验证生成物满足合同。

ABI 的「最小充分集」可以只记六项：参数位置、返回位置、栈对齐、callee-saved、caller-saved、聚合分类。其余（符号修饰、TLS、异常表）按目标与语言补。把六项做成一张检查表，贴到生成器的输出目录；每次改 prologue/参数搬运，先过表。表不需要很厚，但每一项都要有「怎么验证」。

## 8.2 栈帧与对齐：画清楚 rsp 的每一步 {#sec-compilers.2.8.2}

栈对齐的规则只有一句话：**`call` 指令执行前，`%rsp` 必须是 16 的倍数；`call` 压入 8 字节返回地址后，callee 入口的 `%rsp` 是 8 mod 16**。所有「多减 8」「少减 8」的争论，都可以用这一句话和一张逐步表解决。

<pre class="layout">
调用者的视角（地址向下增长，X 是 16 的倍数）

  caller 的帧
  X+16   [ caller 的局部变量/ outgoing args ]
  X      &lt;-- call 前 %rsp = X，X % 16 = 0
  X-8    [ 返回地址 ]          &lt;-- call 压入
  X-16   [ 旧的 %rbp ]         &lt;-- callee: push %rbp
  X-16-N [ callee 的局部变量 ] &lt;-- callee: sub N, %rsp，N % 16 = 0
  X-16-N &lt;-- callee 调用别人前，%rsp % 16 = 0

  callee 入口：%rsp = X-8，8 mod 16
  push %rbp 后：%rsp = X-16，0 mod 16
  sub N 后：  %rsp = X-16-N，N 是 16 的倍数 -&gt; 仍 0 mod 16
  leave/ret：  pop %rbp -&gt; X-8（8）；ret 弹出返回地址 -&gt; X（0）
</pre>

读图：`call` 自己会改变 `%rsp`，所以「callee 入口是 8」不是矛盾，而是同一次压栈的结果。prologue 里的 `sub` 必须在 `push %rbp` 之后保持 0 mod 16；如果 `sub` 是 8，`call` 前就变成 8，callee 入口变成 0，整条链往后错 8。

把每一步写成表：

| 时刻 | `%rsp` 相对 X | 模 16 | 谁改变 |
|:--|--:|--:|:--|
| caller 准备调用 | X | 0 | caller 的 prologue/局部变量 |
| `call` 压返回地址 | X-8 | 8 | `call` |
| callee `push %rbp` | X-16 | 0 | callee prologue |
| callee `sub $N`（N%16=0） | X-16-N | 0 | callee prologue |
| callee 调用别人前 | X-16-N | 0 | 必须保持 |
| `leave`/`pop %rbp` | X-8 | 8 | epilogue |
| `ret` 弹出返回地址 | X | 0 | `ret` |

「多减 8」错在哪：如果 prologue 是 `push %rbp; sub $8`，`call` 前 `%rsp` 是 8 mod 16，callee 入口是 0。callee 若再 `push %rbp`，它变成 8；再 `sub $16`，还是 8；它调用别人时 `%rsp` 是 8，于是错误沿着调用链传播。某个 callee 可能用 `movaps` 把 `%xmm` 存到它认为 16 字节对齐的栈槽，或者把栈参数按 16 字节对齐读取；这时才会崩。错误不是「多减了 8 字节空间」，而是「破坏了对齐不变量」。

一个重要的反例：**没有 `push %rbp` 的函数，`sub $8` 可能是对的**。callee 入口是 8，若它不 push 帧指针、又要调用别人，`sub $8` 正好把 `%rsp` 变成 0。规则要写成「`push %rbp` 之后，`sub` 是 16 的倍数」；脱离上下文说「sub 8 一定错」是另一种教条。本章的 agent 错误案例正是「push 了 rbp 还 sub 8」。

callee-saved 寄存器的 push 也会改变模 16。每 push 一个 8 字节寄存器，模 16 翻转一次；因此：

| callee 保存的寄存器个数 | push 后模 16 | 调用前需要 |
|--:|--:|:--|
| 0（只 push rbp） | 0 | 不再调整 |
| 1 | 8 | 再 sub 8 或再 push 一个 8 字节 |
| 2 | 0 | 不再调整 |
| 3 | 8 | 再 sub 8 |

clang 在 `_after` 里用的就是「push rbp（0）+ push rbx（8）+ push rax（0）」：第三条 `pushq %rax` 不保存任何活值，只是把模 16 翻回 0。它的真实反汇编是：

```text
_after:
   0: 55                   pushq   %rbp
   4: 53                   pushq   %rbx
   5: 50                   pushq   %rax
   8: e8 00 00 00 00       callq   _g
  13: 5b                   popq    %rbx
  14: 5d                   popq    %rbp
```

`pushq %rax` 看起来多余，但删掉它，`callq _g` 就在 `%rsp` 为 8 时执行，callee 入口变成 0。这个例子说明：对齐不是 prologue 的「一次性减法」，而是整条调用链的不变量；临时 push 一个死寄存器也是合法手段。

栈参数的位置也由这个不变量决定。SysV 规定：第 7 个及以后的整数参数放在栈上，callee 入口时第一个栈参数在 `8(%rsp)`（0 是返回地址），`push %rbp` 后在 `16(%rbp)`。真实 `_seven` 的 `16(%rbp)` 就是这个偏移：

```asm
_seven:
    pushq   %rbp
    movq    %rsp, %rbp
    addq    %rdi, %rsi
    leaq    (%rdx,%rcx), %rax
    addq    %rsi, %rax
    addq    %r8, %rax
    addq    %r9, %rax
    addq    16(%rbp), %rax
    popq    %rbp
    retq
```

如果调用者在 `call` 前没有把 `%rsp` 对齐，callee 用 `%rbp` 相对偏移读栈参数仍然能读到（因为 `%rbp` 跟着实际 `%rsp` 走），但 ABI 要求栈参数区按 16 字节对齐；某些 callee 会用对齐的向量 load 读栈参数，错位就崩。不要因为「我的测试能读到参数」就认为对齐不重要。

ARM64 的对比要单独看。`bl` 把返回地址写进 `x30`，不压栈；因此 `%sp` 在调用点保持 16 字节对齐，callee 入口也是 0 mod 16，不存在 x86 的「入口 8」。AAPCS64 要求公共接口处 `%sp` 16 字节对齐；callee 用 `stp x29, x30, [sp, #-16]!` 一次减 16，仍然保持对齐。这是第 8.4 节 `x30` 讨论的前置事实。

::: ex 例 8.2.1 · 走一遍「三 push + sub」 {#ex-compilers.2.8.2.1}
函数入口 `%rsp = 8`。`push %rbp` → 0；`push %rbx` → 8；`push %r12` → 0；`sub $32` → 0；调用前 0，callee 入口 8。若把 `sub $32` 改成 `sub $24`：24 % 16 = 8，调用前变成 8，callee 入口 0，违反合同。若把两次 callee-saved push 改成三次（再加 `push %r13`）：入口 8 → push rbp 0 → push rbx 8 → push r12 0 → push r13 8，需要再 `sub $8` 或再 push 一个寄存器才能回到 0。三步账算完，任何 prologue 都能检查。
:::

::: note Rosetta 不模拟对齐异常
本机是 macOS arm64，x86-64 代码通过 Rosetta 执行。实验发现：在 Rosetta 下，`movaps` 对未对齐地址并不一定触发 #GP，错位的程序可能正常退出。因此本章不用「崩不崩」作为对齐证据，而用一个见证函数返回 `%rsp & 15`：正确 prologue 返回 8，错误 prologue 返回 0。真实硬件上未对齐的 `movaps` 会触发异常；模拟器可能掩盖 ABI 错误，这也是「模拟器通过不等于硬件通过」的一个实例。
:::

::: method 检查一个 prologue 的顺序
1. 找到函数入口，记 `%rsp ≡ 8`。
2. 逐条跟踪 `push`/`pop`/`sub`/`add` 对 `%rsp` 的影响；`call` 前必须 0。
3. 检查每条 `sub $N, %rsp`：若之前有奇数个 8 字节 push，`N` 应为 8 mod 16；若有偶数个，`N` 应为 0 mod 16。更简单的统一规则是「算到 `call` 前为 0」。
4. 检查 `call` 的目标是否可能回调你的函数；若是，callee 也必须满足同一不变量。
5. 检查所有返回路径的 epilogue 是否与 prologue 对称；异常展开路径也要能恢复 `%rsp`。
:::

栈对齐还有两个容易忽略的细节。第一，outgoing 参数区的对齐：调用者把第 7 个及以后的参数放在 `%rsp` 上，callee 用 `8(%rsp)` 起读；如果调用者只 `sub` 了参数字节数而没有把 `%rsp` 对齐，callee 读参数可能仍然对（偏移固定），但 ABI 要求的 16 字节对齐被破坏，使用对齐向量 load 的 callee 会崩。第二，`%rbp` 相对寻址与 `%rsp` 相对寻址的差别：prologue 之后 `%rbp` 固定，局部变量偏移不随 `sub` 变；`%rsp` 会随每次 `push`/`sub` 变，用 `%rsp` 相对寻址必须实时更新偏移。编译器通常在 prologue 后切到 `%rbp`，或者维护一个「当前 `%rsp` 偏移」的符号量。

大帧还需要栈探测（stack probe）：一次 `sub` 跳过 guard page 会触发栈溢出保护，编译器要逐页触碰。这个细节属于运行时/OS 边界，本章不展开；你只需要知道「`sub` 的字节数」不只是对齐问题，还受栈增长策略约束。

ABI 文档对栈对齐的措辞值得逐字读：SysV 说「`%rsp` 在 `call` 前必须 16 字节对齐」，而不是「`%rsp` 永远是 16 的倍数」。`push`/`pop`/`sub` 都会临时改变它，只要在 `call` 前回到 0 即可。这个区别让「push 一个死寄存器做 padding」合法，也让「`sub $8`」在无帧指针时合法。检查器要算「`call` 前的模」，不能只看某一条 `sub` 的大小。

信号处理与栈对齐还有一条边界：信号可能在任意指令处打断程序，内核交付信号时使用被中断代码的栈；如果代码用了 red zone，内核会跳过 128 字节以保护它。这个约定只对用户态 SysV 成立，内核代码/其他目标不成立。生成信号处理函数或内核代码时，编译器选项（`-mno-red-zone`）比分配器的推断更可靠。

两套 ABI 的栈行为对照：

| 项目 | x86-64 SysV | AAPCS64 |
|:--|:--|:--|
| 调用时压返回地址 | 是（`call` 压栈） | 否（`bl` 写 `x30`） |
| callee 入口 `%rsp`/`%sp` 模 16 | 8 | 0 |
| `call`/`bl` 前模 16 | 0 | 0 |
| 典型 prologue | `push %rbp` + `sub` | `stp x29,x30,[sp,#-16]!` |
| callee-saved | `rbx,rbp,r12–r15` | `x19–x28,x29` |
| red zone | 128 字节 | 无 |

这张表解释了一个常见困惑：为什么 x86 的 callee 入口是 8，而 ARM64 是 0。不是哪个 ABI「更严格」，而是调用指令是否把返回地址放到栈上。把 x86 的「入口 8」套到 ARM64，会多减 8 并破坏 `%sp` 的 16 字节对齐；把 ARM64 的「入口 0」套到 x86，会少减 8 并让 callee 看到错位的栈。

对齐失败的实际模式不止「`movaps` 崩」一种。第一，callee 用 `%rsp` 相对偏移读栈参数，错位后读到相邻字节；第二，可变参数函数用 `movaps` 保存 `%xmm`，地址不对齐；第三，调用者把 `__m128` 按值放到栈上，callee 用对齐 load 读；第四，某些运行时（例如 Objective-C 消息发送、协程切换）要求栈指针对齐到 16 字节。它们的共同前提都是「`call` 前 0 mod 16」，而不是某一条指令的语法。

对齐检查器的实现要点：解析 objdump 时，`push`/`pop` 每次改 8，`sub`/`add` 改立即数，`call` 只检查不改变（对调用者而言，返回后 `%rsp` 恢复）。不要忘了 `leave`：它把 `%rsp` 设为 `%rbp`，再弹 `%rbp`；如果分析器把 `leave` 当普通指令，后面的模 16 会算错。遇到无法静态确定的 `sub %rax`（动态栈），检查器应报「unknown」，不要猜。

对齐的另一个实用检查：在 callee 入口把 `%rsp` 存进一个全局变量，运行后打印。这个「探针」不依赖见证函数的返回值，能看到实际调用链上每一层的模；对多层调用特别有用。探针本身要遵守 ABI（不能改 callee-saved），否则测的是它自己。

## 8.3 参数、返回值、聚合与浮点 {#sec-compilers.2.8.3}

参数传递是 ABI 里最容易被「看起来能跑」掩盖的部分。整数参数少一个、浮点参数放到整数寄存器、结构体按指针传而不是按值传，程序都可能在小测试里跑通，直到另一个编译单元按正确规则读参数。编译器必须按分类规则生成搬运指令，不能凭「这个类型看起来像指针」猜。

x86-64 SysV 与 AAPCS64 的分类规则对照：

| 类别 | x86-64 SysV | AAPCS64 | 编译器要生成什么 |
|:--|:--|:--|:--|
| 整数/指针 | `%rdi, %rsi, %rdx, %rcx, %r8, %r9` | `x0–x7` | 依次搬进参数寄存器 |
| 浮点 | `%xmm0–%xmm7` | `v0–v7` | 按 SSE/NEON 搬 |
| 超出寄存器的参数 | 栈，从 `8(%rsp)` 起 | 栈，按 8/16 字节对齐 | `sub` 出空间并 store |
| 整数返回 | `%rax`（大值 `%rdx`） | `x0`（大值 `x1`） | 返回值放约定寄存器 |
| 浮点返回 | `%xmm0`（大值 `%xmm1`） | `v0`（HFA 最多 4 个） | 放向量寄存器 |
| 小聚合 | ≤16 字节按八字节分类，可能进寄存器 | ≤16 字节按 HFA/整数分类 | 拆成寄存器或栈 |
| 大聚合返回 | 隐藏指针在 `%rdi`，参数后移 | 隐藏指针在 `x8` | 写调用者的缓冲区 |
| 可变参数 | `%al` = 向量寄存器个数 | `x0–x7/v0–v7` + 栈 | 设置 `%al`，保存寄存器区 |

先看整数与栈参数。`long seven(long a,...,long g)` 的第 7 个参数在栈上；clang `-O1` 的真实输出用 `16(%rbp)` 读它：

```asm
_seven:
    pushq   %rbp
    movq    %rsp, %rbp
    addq    %rdi, %rsi
    leaq    (%rdx,%rcx), %rax
    addq    %rsi, %rax
    addq    %r8, %rax
    addq    %r9, %rax
    addq    16(%rbp), %rax
    popq    %rbp
    retq
```

为什么是 `16` 而不是 `8`？callee 入口时返回地址在 `0(%rsp)`，第一个栈参数在 `8(%rsp)`；`push %rbp` 后 `%rsp` 减 8，`%rbp` 指向旧 `%rsp`，于是第一个栈参数在 `16(%rbp)`。如果编译器在 prologue 里又 `sub` 了局部空间，栈参数相对 `%rbp` 的偏移不变（它们在被调用者的帧之上），所以 `16(%rbp)` 是稳定的。用 `%rsp` 相对寻址时偏移会随 `sub` 变化，编译器通常在 prologue 后改用 `%rbp` 或重新计算。

浮点参数走另一组寄存器。`double dsum(double a, double b)` 只用 `addsd %xmm1, %xmm0`。9 个 `double` 的第 9 个在栈上，clang 输出 `addsd 16(%rbp), %xmm0`：

```asm
_many:
    pushq   %rbp
    movq    %rsp, %rbp
    addsd   %xmm1, %xmm0
    addsd   %xmm2, %xmm0
    addsd   %xmm7, %xmm0
    addsd   16(%rbp), %xmm0
    popq    %rbp
    retq
```

注意整数参数与浮点参数各自有 6/8 个寄存器名额，不共享。一个函数 `f(int a, double b, int c, double d)` 的参数是 `%edi, %xmm0, %esi, %xmm1`，不是 `%rdi, %rsi, %rdx, %rcx`。编译器若按「第 n 个参数用第 n 个寄存器」的简化模型生成，会在混合签名上错位。

小聚合按八字节分类。`struct Pair { int x; int y; }` 是 8 字节，可以放进一个整数寄存器返回；clang 把 `%edi` 和 `%esi` 拼进 `%rax`：

```asm
_mkpair:
    pushq   %rbp
    movq    %rsp, %rbp
    shlq    $32, %rsi
    movl    %edi, %eax
    orq     %rsi, %rax
    popq    %rbp
    retq
```

大聚合返回用隐藏指针。`struct Big { long a,b,c; }` 是 24 字节，超过两个八字节，调用者提供一个缓冲区，指针放在 `%rdi`；原来的第一个参数 `x` 因此后移到 `%rsi`。clang 的真实输出：

```asm
_make:
    pushq   %rbp
    movq    %rsp, %rbp
    movq    %rdi, %rax
    movq    %rsi, (%rdi)
    leaq    1(%rsi), %rcx
    movq    %rcx, 8(%rdi)
    addq    $2, %rsi
    movq    %rsi, 16(%rdi)
    popq    %rbp
    retq
```

`movq %rdi, %rax` 把隐藏指针作为返回值（SysV 规定返回 `%rax` 指向缓冲区），`%rsi` 才是 `x`。如果编译器把 `x` 放在 `%rdi`，就会把整数当指针写，运行时崩。这个错误在只看 C 签名时很难发现，必须看 ABI 分类。

可变参数要求 `%al` 放「用了多少个向量寄存器」。`int use_var(void) { return call_var("%f", 1.5); }` 在调用前生成 `movb $1, %al`：

```asm
_use_var:
    pushq   %rbp
    movq    %rsp, %rbp
    movsd   LCPI6_0(%rip), %xmm0
    movb    $1, %al
    popq    %rbp
    jmp     _call_var
```

被调用者 `call_var` 用 `testb %al, %al` 判断是否需要保存向量寄存器区；clang 的 `subq $208, %rsp`（208 是 16 的倍数）为 `va_list` 的寄存器保存区留空间，并用 `movaps` 把 `%xmm0–%xmm7` 存进去。若调用者没设 `%al`，被调用者可能跳过保存，`va_arg` 读到垃圾；若栈没对齐，`movaps` 的地址可能不对。可变参数是对齐与 `%al` 两个约束同时生效的地方。

::: ex 例 8.3.1 · 第 7 个参数到底在哪 {#ex-compilers.2.8.3.1}
调用 `seven(1,2,3,4,5,6,7)`。调用者把 1–6 放进 `%rdi…%r9`，把 7 放在 `call` 前的 `0(%rsp)`。`call` 压返回地址后，callee 入口的 `8(%rsp)` 是 7；`push %rbp` 后，`16(%rbp)` 是 7。callee 若在 prologue 里 `sub $32`，`%rsp` 变了，但 `%rbp` 不变，`16(%rbp)` 仍是 7。若 callee 改用 `32(%rsp)` 读（假设 `sub $32` 后栈参数在 `32(%rsp)`），也能读到，但偏移必须随 `sub` 调整；用 `%rbp` 相对寻址更稳。
:::

::: note ABI 变体
x86-64 至少有 SysV（Linux/macOS）与 Windows x64 两套：Windows 的前 4 个整数参数是 `%rcx,%rdx,%r8,%r9`，`%xmm0–3` 对应前 4 个浮点参数，`%rdi/%rsi` 是 callee-saved，还有 32 字节 shadow space。Rust 的 `extern "sysv64"`/`extern "win64"` 就是在选 ABI。AAPCS64 的 `x8` 是间接结果寄存器，`x16/x17` 是 IP0/IP1 链接器跳板临时寄存器。本书的例子默认 SysV 与 AAPCS64；换目标时，参数表、callee-saved 列表、栈对齐都要按目标描述改，不能复制。
:::

聚合分类的边界比「小于 16 字节进寄存器」复杂。`struct { char c; long x; }` 有填充，大小 16，但分类要看每个八字节的字段类型；`struct { double d; int i; }` 的前 8 字节是 SSE，后 8 字节是 INTEGER，可能分别进 `%xmm0` 和 `%rdi`。`__attribute__((packed))` 的结构体可能未对齐，按值传递时编译器要生成逐字节复制，而不是直接 `movq`。位域、联合体、空结构体、柔性数组都有各自的分类规则；本书不展开，只强调「按大小猜分类」会在混合字段上错。

返回值也分大小。`struct Pair`（8 字节）走 `%rax`；`struct Big`（24 字节）走隐藏指针；`struct HFA { float x,y,z,w; }` 在 AAPCS64 里是 HFA，走 `v0–v3`，在 SysV 里可能走两个 `%xmm` 或内存。编译器必须按目标 ABI 分类，不能把「小结构体」一律当整数。

可变参数的 `va_list` 实现依赖 ABI：SysV 把参数分成「寄存器保存区」和「溢出区」，`va_start` 记录当前偏移；AAPCS64 用 `x0–x7`/`v0–v7` 加栈，`va_list` 是一个结构体。编译器生成可变参数函数时，要在 prologue 里保存所有可能被 `va_arg` 读取的寄存器（或用 `%al` 判断），否则 `va_arg` 读到未保存的寄存器。这个保存区的对齐要求也是栈对齐的一部分：`movaps` 存 `%xmm` 时地址必须 16 字节对齐。

AAPCS64 的 HFA（homogeneous floating-point aggregate）是一个特殊分类：全部成员是相同浮点类型、最多 4 个的聚合，按 `v0–v3` 传递/返回；超过 4 个或成员类型不同，就按普通聚合/内存处理。x86-64 SysV 没有 HFA 这个名字，但小聚合也按八字节分类。生成器若把 HFA 当普通结构体逐字段搬到栈上，功能可能对，性能与 ABI 都不对；若把非 HFA 当 HFA，寄存器数量不够，直接错。

参数搬运的顺序也有讲究。调用者要先把参数放到约定寄存器/栈，再 `call`；如果某个参数的表达式需要调用别的函数，那个调用可能破坏已经放好的参数寄存器。编译器通常先把参数表达式求值到临时位置，最后统一搬运；或者按从右到左的顺序求值，减少冲突。这个顺序不是 ABI 规定，而是编译器实现选择；它影响代码大小和寄存器压力，不影响合同。

## 8.4 callee-saved、x30 与 red zone {#sec-compilers.2.8.4}

callee-saved 的意思是：被调用者如果要用这些寄存器，必须在返回前恢复它们原来的值；调用者可以假设它们在调用前后不变。caller-saved 则相反：调用者若要在调用后继续使用，必须自己保存。两边的责任划分必须一致，否则调用者保存了、被调用者也保存了，浪费；或者都没保存，值丢失。

| 寄存器角色 | x86-64 SysV | AAPCS64 |
|:--|:--|:--|
| 整数参数/返回 | `%rdi…%r9`，`%rax`/`%rdx` | `x0–x7`，`x0/x1` |
| 浮点参数/返回 | `%xmm0–7`，`%xmm0/1` | `v0–v7`，`v0–v3`（HFA） |
| callee-saved | `%rbx, %rbp, %r12–%r15` | `x19–x28`，`x29`（FP） |
| caller-saved | `%rax, %rcx, %rdx, %rsi, %rdi, %r8–%r11` | `x0–x17`（x18 平台相关） |
| 栈指针 | `%rsp` | `%sp` |
| 链接寄存器 | 无（返回地址在栈上） | `x30` |
| 红区 | `%rsp` 下 128 字节 | 无 |

`x30` 是 **link register**（链接寄存器），不是 callee-saved。`bl` 指令把返回地址写进 `x30`；非叶函数在调用别人之前必须把 `x30` 保存到栈上（通常和 `x29` 一起 `stp`），返回前恢复；叶函数不调用别人，`x30` 不会被覆盖，可以不保存。AAPCS64 的 callee-saved 列表是 `x19–x28` 加 `x29`；`x30` 不在其中，因为它由调用指令本身写入，不是「被调用者用了要恢复」的普通寄存器。

clang 为叶函数与非叶函数生成的真实 ARM64 代码：

```asm
_leaf:
    add     w0, w0, #1
    ret

_nonleaf:
    stp     x29, x30, [sp, #-16]!
    mov     x29, sp
    bl      _g
    add     w0, w0, #1
    ldp     x29, x30, [sp], #16
    ret
```

`_leaf` 没有 `stp`，因为它不调用别人；`_nonleaf` 在 `bl` 前保存 `x29/x30`，返回前 `ldp` 恢复。如果 `_nonleaf` 漏了保存，`bl _g` 会把 `x30` 改成「`_g` 返回后回到 `_nonleaf` 的 `bl` 下一条」——这正是它想要的；但 `_nonleaf` 自己的返回地址已经被覆盖，`ret` 会跳回调用者的调用者，形成错误的返回链。

::: def 定义 8.4.1 · callee-saved 与 link register {#def-compilers.2.8.4.1}
**callee-saved** 是一组寄存器，被调用者若修改它们，必须在返回前恢复；调用者可以假设它们在调用前后不变。**link register** 是存放子程序返回地址的寄存器；调用指令写入它，返回指令从它跳转。二者不是同一概念：link register 可能由调用指令隐式改写，因此非叶函数必须显式保存，但它不属于 callee-saved 列表。
:::

::: errata x30 的三种说法
1. 「`x30` 是 callee-saved」——错。AAPCS64 的 callee-saved 是 `x19–x28` 与 `x29`；`x30` 是 LR。
2. 「`x30` 必须保存」——不完整。叶函数不需要；非叶函数必须，因为 `bl` 会覆盖它。
3. 「保存 `x30` 就等于保存返回地址」——在标准调用序列里是，但如果函数用 `ret xN` 切换到别的返回地址，或做尾调用，`x30` 的语义要按代码具体分析。
:::

red zone 是 x86-64 SysV 的一个优化：叶函数可以使用 `%rsp` 以下 128 字节，而不调整 `%rsp`，因为信号处理程序不会覆盖这块区域（内核保证）。这省掉 `sub`/`add`，但只对叶函数安全：非叶函数在调用别人时，callee 会使用 `%rsp` 以下的区域，覆盖 red zone。编译器在非叶函数里若把值放在 red zone，调用后就会丢。内核代码通常用 `-mno-red-zone` 关闭它，因为中断处理不受用户态 red zone 约定保护。

```asm
; 叶函数可以用 red zone（示意）
_leaf_use:
    movq    %rdi, -8(%rsp)
    movq    -8(%rsp), %rax
    ret
```

上例只是示意，不保证 clang 一定这样生成；red zone 的使用取决于优化器和目标选项。能确定的规则是：**非叶函数不能把跨调用的值放在 red zone**，因为 callee 的栈帧会覆盖它。AAPCS64 没有 red zone，ARM64 代码不能照搬这个优化。

callee-saved 的保存方式有两种：push/pop，或在 prologue 里 `mov` 到栈槽、epilogue 里取回。push/pop 更短，但会改变 `%rsp` 的模 16，需要配合 padding；栈槽方式不改变 `%rsp`，但需要计算偏移。clang 在 `_after` 里用 push/pop，在 `_demo`（实验的汇编）里用 `movq %rbx, -8(%rbp)`/`movq -8(%rbp), %rbx`；两种都合法，关键是每条返回路径都恢复。

::: method 判断一个函数要不要保存 x30
1. 函数里有没有 `bl`/`blr` 或其他写 `x30` 的指令？没有 → 叶函数，可不保存。
2. 有 → 在第一次 `bl` 之前保存 `x30`，在所有 `ret` 之前恢复。
3. 检查异常/尾调用路径：`b` 尾调用不写 `x30`，但会把控制权交给另一个函数；`ret` 仍用当前 `x30`，所以保存/恢复的配对不能被尾调用绕过。
4. 用反汇编确认 `stp x29, x30` 与 `ldp x29, x30` 成对出现，且 `bl` 在两者之间。
:::

callee-saved 的保存有成本，选择哪种方式要看帧大小和寄存器压力：

| 方式 | 指令 | 优点 | 缺点 |
|:--|:--|:--|:--|
| push/pop | `push %rbx` … `pop %rbx` | 短、自动更新 `%rsp` | 改变模 16，需要 padding |
| 栈槽 | `mov %rbx,-8(%rbp)` … | 不影响 `%rsp` | 需要偏移，访存两次 |
| 不用 | 改分配到 caller-saved/栈 | 无保存开销 | 跨调用值不能放 caller-saved |
| shrink-wrap | 只在用到时保存 | 省冷路径开销 | 实现复杂，异常路径要覆盖 |

`.cfi` 指令不是 ABI 的一部分，但它描述「栈帧长什么样」，异常展开和调试器依赖它。生成 prologue 时如果只改 `%rsp` 而不更新 CFA 偏移，调试器/展开器会读到错误的返回地址。clang 的汇编里每条 `push` 后都有 `.cfi_def_cfa_offset`/`.cfi_offset`；手写汇编若省略，程序可能仍能跑，但异常/回溯会错。本书不展开 CFI 语法，只提醒：ABI 合规不仅是寄存器值，还包括「可展开的帧描述」。

red zone 在信号处理里还有一条边界：用户态信号处理程序不能使用被中断代码的 red zone，内核在交付信号时会跳过 128 字节。编译器生成叶函数时可以用 red zone；生成信号处理函数（`__attribute__((signal))` 或运行时注册的回调）时不能用，除非运行时保证。这个区别通常由运行时/编译器选项控制，不是分配器能推断的。

`x30` 与异常展开还有一层关系。非叶函数保存 `x29/x30` 时，编译器同时生成 `.cfi_def_cfa`/`.cfi_offset`，告诉展开器「`x30` 存在栈的哪个位置」。如果只写 `stp` 而不更新 CFI，调试器/异常展开器可能按旧规则找返回地址，栈回溯错位。ABI 合规不仅是「运行时寄存器对」，还包括「帧描述对」；后者在正常返回时看不出来，在异常/调试时才暴露。

| 函数类型 | 保存 `x30` | 典型 prologue | 返回 |
|:--|:--|:--|:--|
| 叶函数 | 不需要 | 无栈调整 | `ret` |
| 非叶、无局部 | 需要 | `stp x29,x30,[sp,#-16]!` | `ldp …; ret` |
| 非叶、有局部 | 需要 | `stp` + `sub` | `add` + `ldp` + `ret` |
| 尾调用 | 通常不需要恢复 | `b` 而不是 `bl` | 目标函数 `ret` |

尾调用用 `b` 而不是 `bl`，不写 `x30`，所以不需要保存；但它把返回责任交给目标函数。若生成器把尾调用写成 `bl` 再 `ret`，就会多一次保存/恢复，甚至破坏 `x30` 的链。这个区别在优化后的代码里很常见，读反汇编时要注意 `b` 与 `bl`。

再强调一次 `x30` 的检查方法：反汇编里找 `bl`，往前找最近的 `stp x29, x30`，往后找 `ldp x29, x30`；三者顺序对，才说明保存/恢复覆盖了这次调用。若函数有多条返回路径，每条路径都要有 `ldp`。这个检查不依赖汇编器，必须写成脚本；16 条陷阱里的第 9、10 条都靠它。

red zone 的代码证据不容易从 C 直接构造，因为 clang 是否用 red zone 取决于优化与目标。能确定的是规则：叶函数可以使用 `%rsp` 以下 128 字节；非叶函数在调用前必须假设这块区域会被 callee 覆盖。写生成器时，把「是否叶函数」作为 prologue 的输入，而不是在分配器里猜。若函数后面被内联进一个非叶调用者，red zone 的使用要重新评估——这也是内联会改变栈布局的原因之一。

callee-saved 的保存策略还要考虑异常与协程：

| 场景 | 保存点 | 风险 |
|:--|:--|:--|
| 普通函数 | prologue/epilogue | 多返回路径漏恢复 |
| shrink-wrapped | 使用点前 | 异常路径未覆盖 |
| 协程/纤程 | 切换时保存寄存器集 | 编译器生成的 prologue 不够 |
| 信号处理 | 运行时保存 | red zone/异步安全 |

本章的生成器只覆盖第一行。第二行需要 CFG 分析与 CFI；第三、四行需要运行时配合，不能靠单个函数的 prologue 解决。把边界写清楚，读者才知道什么时候该换工具（例如协程库的上下文切换），而不是继续改代码生成。

callee-saved 的测试要用哨兵：调用前把 `%rbx/%r12–%r15` 写成不同的魔数，调用后逐个比对。只检查「返回值对」不够，因为 callee 可能恰好没用到某个寄存器，测试放过了；哨兵能覆盖「用到了但没恢复」的情况。caller-saved 的测试则相反：调用后不要假设值还在，跨调用值必须从内存/callee-saved 读。

callee-saved 的保存顺序也会影响调试：先保存 `%rbp` 再保存其他寄存器，展开器能按 `%rbp` 链找到调用者；反过来，`%rbp` 还没建立就保存其他寄存器，CFI 需要更复杂的规则。clang 的顺序是 `push %rbp; mov %rsp,%rbp` 后再保存其他 callee-saved，这不是随意，而是为了让 `%rbp` 链稳定。手写 prologue 时照这个顺序，展开/调试会省很多事。

## 8.5 生成 prologue/epilogue 并用 objdump 验证 {#sec-compilers.2.8.5}

prologue 的目标只有三个：建立帧指针（可选）、为局部变量与溢出槽留空间、保存要用的 callee-saved 寄存器；同时保持 `%rsp` 的对齐不变量。epilogue 必须精确地反向执行，并在每条返回路径上恢复 `%rsp` 与 callee-saved。生成器的输入是「局部字节数、溢出槽数、用到的 callee-saved、outgoing 参数空间」，输出是一段汇编；它不应该在 pass 里硬编码 `16` 或 `push %rbp`。

先用一个可运行的规划函数把账算清楚：

```python
def align_up(n, a=16):
    return (n + a - 1) // a * a

def frame_plan(locals_bytes=0, spills=0, callee_saved=(), outgoing=0,
               frame_pointer=True):
    body = locals_bytes + 8 * spills + 8 * len(callee_saved) + outgoing
    if frame_pointer:
        frame = align_up(body, 16)          # push rbp 后 rsp 已 0 mod 16
    else:
        frame = ((body - 8 + 15) // 16) * 16 + 8  # 入口 8，sub 后要 0
    call_site = (8 - (8 if frame_pointer else 0) - frame) % 16
    return frame, call_site

for args in [(24, 2, ("rbx",), 0, True),
             (0, 0, (), 8, False),
             (16, 0, ("rbx", "r12"), 16, True),
             (0, 0, (), 0, False)]:
    print(args, "->", frame_plan(*args))
```

真实输出：

```text
(24, 2, ('rbx',), 0, True) -> (48, 0)
(0, 0, (), 8, False) -> (8, 0)
(16, 0, ('rbx', 'r12'), 16, True) -> (48, 0)
(0, 0, (), 0, False) -> (8, 0)
```

第一行：24 字节局部 + 2 个溢出槽（16）+ 1 个 callee-saved（8）= 48，正好是 16 的倍数，`call` 前 0。第二行：无帧指针、无局部，但有一个 8 字节的 outgoing 参数；入口 8，`sub $8` 后 0；如果错误地按「sub 必须是 16 的倍数」取 16，反而会变成 8。第四行：无帧指针、无 outgoing，仍然 `sub $8`，因为要调用别人；如果这个函数是叶函数（不调用），可以完全不 sub。

帧布局可以画成：

<pre class="layout">
高地址
  [ caller 的栈参数 / outgoing args ]
  [ 返回地址 ]                     &lt;- callee 入口 rsp
  [ 保存的 %rbp ]                  &lt;- push rbp 后 rbp
  [ 保存的 callee-saved 寄存器 ]
  [ 对齐 padding ]
  [ 局部变量 / 溢出槽 ]             &lt;- rsp，16 字节对齐
低地址

偏移约定（rbp 相对）：
  -8(%rbp)   第一个保存的 callee-saved 或局部
  -16(%rbp)  第二个
  -(frame)(%rbp) 帧底；rsp = rbp - frame
</pre>

读图：`%rbp` 指向保存的旧帧指针，`%rsp` 指向帧底；局部变量与溢出槽用负偏移，栈参数用正偏移（`16(%rbp)` 起）。帧大小必须是 16 的倍数（有帧指针时），否则 `%rsp` 在调用点不对齐。padding 不是浪费，它是把「局部变量字节数」凑成对齐的填充。

clang 在 `-O0` 下为带局部数组和两次调用的 `frame` 生成 `subq $0x30, %rsp`（48 字节）：

```text
_frame:
   0: 55                   pushq   %rbp
   1: 48 89 e5             movq    %rsp, %rbp
   4: 48 83 ec 30          subq    $0x30, %rsp
  22: e8 00 00 00 00       callq   0x27 <_frame+0x27>
  2d: e8 00 00 00 00       callq   0x32 <_frame+0x32>
```

48 是 16 的倍数；入口 8 → push rbp 0 → sub 48 仍 0，两次 `callq`（重定位目标是 `_g`）都在 0 上。`-O2` 下同一个函数改成 push 两个 callee-saved：

```text
_frame:
   0: 55                   pushq   %rbp
   4: 41 56                pushq   %r14
   6: 53                   pushq   %rbx
   8: e8 00 00 00 00       callq   _g
```

push rbp（0）→ push r14（8）→ push rbx（0），两个 callee-saved 的偶数次 push 把模 16 翻回 0，不需要额外 padding。若只 push 一个 callee-saved，就需要再 push 一个死寄存器或 `sub $8`；clang 在 `_after` 里选择 `pushq %rax`。

epilogue 必须与 prologue 对称。可以用 `leave`（等价于 `mov %rbp,%rsp; pop %rbp`），也可以显式 `add $frame,%rsp; pop ...`。选择取决于是否还有 callee-saved 要弹：`leave` 只恢复 `%rsp` 和 `%rbp`，不会弹 callee-saved；如果 prologue 在 `%rbp` 之下 push 了 `%rbx`，epilogue 要先 `pop %rbx` 再 `leave`。顺序错了会把 `%rbp` 弹进 `%rbx`，返回地址错位。

验证 prologue/epilogue 的工具就是反汇编加一个 `%rsp` 走查器。实验的 `rsp_walk` 做三件事：解析 `llvm-objdump` 的每条指令；按 `push/pop/sub/add` 更新相对入口的偏移；在每个 `callq` 检查 `(8 + delta) % 16 == 0`。它还会检查每条 `sub $N, %rsp` 的 `N` 是否是 16 的倍数——但这条检查只对「之前有偶数个 push」的函数成立，严格的做法是直接算 `call` 前的模，而不是孤立地看 `sub`。

| prologue 变体 | 适用 | `call` 前模 16 | 风险 |
|:--|:--|--:|:--|
| `push rbp; mov rsp,rbp; sub 16k` | 需要帧指针/调试 | 0 | `sub` 必须 16 的倍数 |
| `push rbp; push rbx; push rax` | 少量 callee-saved | 0 | padding 寄存器不能有活值 |
| 无帧指针，`sub 8` | 叶/小型非叶 | 0 | 只 sub 8 是正确的，不要改成 16 |
| 无帧指针，无 sub | 叶函数、无调用 | 8（不调用） | 一旦加调用就错 |
| 动态 `sub %rax` | VLA/alloca | 运行时决定 | 必须运行时对齐，且恢复 |

::: ex 例 8.5.1 · 读一段 objdump 的栈账 {#ex-compilers.2.8.5.1}
`_frame` 的 `subq $0x30` 是 48；入口 8，`push %rbp` 后 0，`sub` 后 0；两次 `callq _g` 都在 0。`_after` 的 `push %rbp; push %rbx; push %rax`：8 → 0 → 8 → 0；`callq _g` 在 0。`align_bad` 的 `push %rbp; sub $8`：8 → 0 → 8；`callq _witness` 在 8，所以 `_witness` 看到的入口是 0，返回 0。三行账分别对应「正确」「用 padding 修正」「错误」，不需要运行就能判断。
:::

::: method 生成并验证一个 prologue
1. 统计 `locals`、`spills`、`callee_saved`、`outgoing`；按 `frame_plan` 算帧大小。
2. 选择是否用 `%rbp`；若用，先 `push %rbp; mov %rsp,%rbp`，再 `sub` 帧大小。
3. 保存 callee-saved：push/pop 或栈槽；每次 push 都重算模 16。
4. 在每条 `call` 前断言 `%rsp % 16 == 0`；若不对称，加 padding。
5. epilogue 按相反顺序恢复；每条 `ret` 前检查 `%rsp` 回到入口值。
6. 用 `llvm-objdump` 反汇编，跑 `rsp_walk`；再在运行时用见证函数确认 callee 入口模 16。
:::

边界：动态栈分配（`alloca`/VLA）让帧大小在运行时才知道，prologue 不能简单 `sub` 常量；编译器要在运行时把 `%rsp` 对齐，并保存恢复链。Windows x64 还有 32 字节 shadow space 和 `%rsp` 的 16 字节对齐要求，栈探测（stack probe）用于大帧。本书的例子是 SysV/AAPCS64 的固定帧；换目标时，帧布局与对齐规则要按目标描述重新生成，不能照搬 `sub $16`。

objdump 之外还有两类证据。第一，`llvm-readelf --unwind` 或 `llvm-dwarfdump --debug-frame` 可以看 `.eh_frame`/`.debug_frame` 里的 CFA 规则，验证 prologue 的每一步是否被正确描述；第二，`llvm-objdump -d` 只能看指令，不能看「这条 `ret` 是否在异常路径上也被执行」，需要结合 CFG 检查所有返回路径。对于手写汇编，后者尤其重要：一个函数可能有多条 `ret`，每条都要有对称的 epilogue。

| 工具 | 看什么 | 不能看什么 |
|:--|:--|:--|
| `llvm-objdump -d` | 指令、编码、跳转目标 | 异常路径、CFA |
| `llvm-readelf -r` | 重定位类型/符号 | 运行时解析结果 |
| `llvm-readelf --unwind` | `.eh_frame` 的 CFA | 源代码级变量 |
| `rsp_walk`（实验） | `call` 前模 16、`sub` 倍数 | 数据相关对齐 |
| 见证函数 | 运行时 `%rsp & 15` | 哪条指令导致错位 |

把这些工具组合起来，才能从「指令看起来对」走到「合同确实被满足」。

shrink wrapping 是 prologue/epilogue 的一个变体：只在真正需要保存寄存器的路径上保存，而不是函数入口一律保存。它可以减少冷路径开销，但要求每条返回路径都能恢复，且异常展开信息覆盖所有路径。对教学编译器，建议先用「入口统一保存、出口统一恢复」的简单策略；等测试覆盖了多返回路径，再考虑 shrink wrapping。否则很容易出现「一条 early return 忘了恢复」的 bug，而这条路径恰好不在测试里。

一个帧大小的手算例子：局部 24 字节、2 个溢出槽（16）、保存 `%rbx`（8）、outgoing 参数 8 字节，总计 56；有帧指针时 `frame = align_up(56,16) = 64`，`sub $64`。若把 `%rbx` 改成 push/pop，push 已经占了 8 字节，帧里就不再算这 8 字节，但 push 会改变模 16，需要重新配平。两种布局的帧大小可能不同，不能用同一个公式套。

帧大小的常见错误：

| 错误 | 现象 | 修复 |
|:--|:--|:--|
| 只算局部，不算溢出槽 | 溢出写到帧外 | 把 spills × 8 计入 |
| 忘记 outgoing 参数区 | 调用时覆盖局部 | 加 `outgoing` 并向上取整 |
| push 后仍按入口 8 算 | `call` 前模 16 错 | 先算 push 后的模 |
| 对齐 padding 没算 | 帧大小不是 16 的倍数 | padding = `(-body) mod 16` |

帧规划函数要把这些项都作为输入，输出「帧大小 + 每个槽的偏移 + `call` 前模 16」。只输出一个 `sub` 数字不够，后面生成 `mov` 时还需要偏移。

epilogue 的异常路径常被忽略。一个函数可能有多条 `ret`：正常返回、错误分支、异常展开。每条路径都要恢复到入口的 `%rsp` 和 callee-saved；shrink wrapping 更容易漏。检查方法不是只看最后一条 `ret`，而是对 CFG 的每个出口跑同样的栈账。没有 CFG 时，至少把所有 `ret` 前 5 条指令列出来人工核对。

## 8.6 位宽、movl 与内存读改写 {#sec-compilers.2.8.6}

x86-64 的整数寄存器有 8/16/32/64 位视图，指令的操作数宽度由寄存器名和内存操作数的大小共同决定。写 `movq 8(%rdi), %eax` 是把 64 位 load 的目标写成 32 位寄存器：汇编器直接拒绝。真实的错误是：

~~~bash
clang -target x86_64-apple-darwin -c bad_width.s -o bad_width.o
~~~


```text
bad_width.s:4:19: error: invalid operand for instruction
    movq 8(%rdi), %eax
                   ^~~~
```

把 `movq` 改成 `movl` 就合法：

```asm
movl 8(%rdi), %eax      ; 8b 47 08
movq 8(%rdi), %rax      ; 48 8b 47 08
```

`llvm-objdump -d` 的真实输出（节选）：

```text
8: 8b 47 08          movl    0x8(%rdi), %eax
c: 48 8b 47 08       movq    0x8(%rdi), %rax
```

32 位写会零扩展到 64 位：`movl` 写 `%eax` 后，`%rax` 的高 32 位清零。这不是「顺手」，而是 x86-64 的规则。若源是 `int`、目标是 64 位值，用 `movl` 得到零扩展；若源是负数、需要符号扩展，用 `movslq`（`48 63`）或先 `movl` 再 `cltq`。若源是 `unsigned char`，用 `movzbl`；若源是 `signed char`，用 `movsbl`。把「load 一个 int」写成 `movq` 即使能汇编（目标写成 `%rax`），也会读 8 字节，越过 `int` 的边界，属于越界读。

| 源类型 | 指令 | 效果 |
|:--|:--|:--|
| `int`（32 位） | `movl 8(%rdi), %eax` | 读 4 字节，零扩展到 `%rax` |
| `long`/指针 | `movq 8(%rdi), %rax` | 读 8 字节 |
| `signed char` | `movsbl 8(%rdi), %eax` | 读 1 字节，符号扩展 |
| `unsigned char` | `movzbl 8(%rdi), %eax` | 读 1 字节，零扩展 |
| `short` | `movswl` | 读 2 字节，符号扩展 |
| `int` 到 `long` | `movslq %eax, %rax` | 32→64 符号扩展 |

下一个历史错误：**`add` 的目的可以是内存**。x86 的 `add` 是读改写：读目的、加源、写回目的；目的可以是寄存器或内存，源可以是寄存器、立即数或内存，但两个操作数不能同时是内存。真实的汇编与反汇编：

```asm
addl %eax, (%rdi)       ; 01 07，内存目的，读改写
addl $1, (%rdi)         ; 83 07 01，立即数到内存
addq (%rdi), %rax       ; 48 03 07，内存源
```

运行证据：实验的 `ops.s` 在 `-8(%rbp)` 放 35，`%rdi` 指向它，`%eax` 放 7，执行 `addl %eax, (%rdi)`，再把结果放进 `%eax` 返回；通过 `arch -x86_64` 运行，退出码 42。这个 42 不是算出来的巧合，是内存里的 35 被读改写成了 42。

若两个操作数都是内存，汇编器拒绝：

```text
bad_add.s:4:18: error: invalid operand for instruction
    addl (%rdi), (%rsi)
                  ^~~~~
```

编译器遇到 `mem + mem` 的 IR 加法，必须先用 `mov` 把一个源取到寄存器，再 `add`。这不是「`add` 不能写内存」，而是「一条指令最多一个内存操作数」。第 7 章的溢出重写也依赖这条规则：目的在栈槽时，先算到 scratch，再 `mov` 写回；不能直接 `add` 两个栈槽。

| 目的 \ 源 | 寄存器 | 立即数 | 内存 |
|:--|:--|:--|:--|
| 寄存器 | 合法 | 合法 | 合法（内存源） |
| 内存 | 合法（读改写） | 合法 | **非法** |
| 立即数 | 非法 | 非法 | 非法 |

`add` 还会写标志位（CF/OF/SF/ZF/AF/PF）。这有两面：好处是后面可以接 `jc`/`jo`/`jz`；坏处是它不能随意穿过一条依赖标志的指令。`lea` 不写标志，所以编译器常用 `lea` 做「只算值、不改标志」的加法；这也是第 7 章选择 LEA 的原因之一。若代码在 `add` 后不读标志，`add` 与 `lea` 在语义上可互换；若后面紧接条件跳转，替换要小心。

::: ex 例 8.6.1 · 三种 `*p += x` 的生成 {#ex-compilers.2.8.6.1}
`void f(int *p, int x) { *p += x; }` 在 `-O1` 下通常生成 `addl %esi, (%rdi)`：一个内存操作数，读改写，一条指令。若 `x` 在内存、`p` 在寄存器，合法形式是 `movl x(%rip), %eax; addl %eax, (%rdi)`；若 `p` 也在内存，先要把指针读进寄存器，再加。若目标架构没有内存目的形式（例如某些 RISC），就必须 load/add/store 三条。x86 的一条 `addl` 是编码优势，不是 ABI 要求；不要把「x86 能一条」写成「所有目标都该一条」。
:::

::: note 汇编器抓到什么、抓不到什么
`movq` 到 `%eax`、两个内存操作数会被汇编器拒绝；但「用 `movl` 读一个 `long`」不会——它语法合法，语义错（只读低 32 位）。「用 `movq` 读一个 `int`」也不会——它读越界 4 字节。位宽错误分两类：编码错误由汇编器抓，语义错误由类型检查/测试抓。生成器要按源类型选择指令，而不是按「寄存器够不够大」选择。
:::

位宽错误可以分成三类，处理方式不同：

| 错误 | 例子 | 谁抓 | 修复 |
|:--|:--|:--|:--|
| 编码宽度不匹配 | `movq …, %eax` | 汇编器 | 改成 `movl` 或 `%rax` |
| 读越界 | 用 `movq` 读 `int` | 测试/ASan | 按源类型选宽度 |
| 截断/扩展错 | 用 `movl` 读 `long`、用 `movq` 读 `int` | 类型检查/测试 | `movslq`/`movzbl`/`movq` |

第三类最隐蔽，因为汇编器不报错。`long f(int x) { return x; }` 需要把 32 位 `%edi` 符号扩展到 64 位 `%rax`；clang `-O1` 生成 `movslq %edi, %rax`（或 `movl %edi,%eax` 后 `cltq`）。若生成器只写 `movl %edi,%eax` 就返回，返回值高 32 位是 0，负数会变成大正数。反过来，`int g(long x) { return (int)x; }` 只取低 32 位，`movl %edi,%eax` 就够；写 `movq %rdi,%rax` 也不会错，但没有表达「截断」。

指针截断是另一类：在 x86-64 上把指针放进 `%eax` 会丢掉高 32 位，地址变成低 32 位。编译器若把「指针」和「int」都当 32 位处理，在小于 4GB 的地址空间里可能偶然正确，换一个分配器/ASLR 就崩。位宽选择必须由类型和 ABI 决定，不能由「这个值看起来小」决定。

`add` 与 `lea` 的标志差异值得单独记：

| 指令 | 写标志 | 典型用途 |
|:--|:--|:--|
| `add` | CF/OF/SF/ZF/AF/PF | 算术 + 后续条件跳转 |
| `lea` | 不写 | 算地址/算值，保持前面 `cmp` 的标志 |
| `inc`/`dec` | 除 CF 外都写 | 循环计数，保留 CF |
| `sub`/`cmp` | 写 | 比较/减法 |

若生成器在 `cmp` 和 `jne` 之间插入一条 `add` 来做地址计算，会把 `cmp` 的标志覆盖，条件跳转走错。用 `lea` 就不会。反过来，若代码依赖 `add` 设置的 CF 做多精度加法，换成 `lea` 会丢 CF。选择哪条不是风格，而是「标志是否活跃」的语义问题。

位宽检查的自动化方式：对每个 load/store 记录「源类型宽度」和「指令后缀」，两者不一致就报错。汇编器只能抓「`movq` 配 `%eax`」这种编码错误，抓不到「`movq` 读 `int`」这种语义错误。把类型宽度作为生成器的输入，而不是从目标寄存器反推，才能避免第二类错误。

再补一组编码事实（可用 `llvm-objdump` 核对）：`movl 8(%rdi), %eax` 是 `8b 47 08`；`movq 8(%rdi), %rax` 是 `48 8b 47 08`；`addl %eax,(%rdi)` 是 `01 07`；`addl $1,(%rdi)` 是 `83 07 01`；`movslq %esi,%rax` 是 `48 63 c6`。前缀 `48` 表示 64 位操作数，`8b`/`01`/`83` 是操作码，ModRM 字节编码寄存器与寻址。你不需要背编码，但能用 `objdump` 的字节列核对「生成的是不是你以为的那条指令」。

`movl`/`movq` 的选择可以总结成「目的宽度 = 源类型宽度」：

| 源类型 | 目的寄存器 | 指令 | 高位行为 |
|:--|:--|:--|:--|
| `int` | `%eax` | `movl` | 零扩展到 `%rax` |
| `long` | `%rax` | `movq` | 保持 64 位 |
| `int` → `long` | `%rax` | `movslq` | 符号扩展 |
| `unsigned` | `%eax` | `movl` | 零扩展 |
| 指针 | `%rax` | `movq` | 64 位地址 |

「目的宽度 = 源类型宽度」比「目的寄存器越大越好」可靠。若源是 `int` 而你想在 64 位上下文里用，先 `movl`（零扩展）或 `movslq`（符号扩展），不要直接 `movq` 读 8 字节。

`add` 与 `lea` 的选择在代码生成里很常见。若加法结果要写回一个操作数、且后面要读标志，用 `add`；若只是想算一个新值、不想破坏标志，用 `lea`；若地址是 `base+index*scale+disp`，`lea` 还能省掉一条加法。反过来，`lea` 不能用于「读内存再加」，那需要 `add` 的内存源形式。两者不是互相替代，而是不同约束下的选择。

## 8.7 ABI 合规测试与六条历史错误回归 {#sec-compilers.2.8.7}

ABI 测试不能只测「函数返回值对不对」。返回值正确但栈没对齐、callee-saved 没恢复、参数分类错的程序，可能在你换一个 libc 版本或换一个优化级别后崩。合规测试要直接检查合同项，而不是只检查最终数值。

一个够用的测试集：

| 测试 | 做法 | 抓什么 |
|:--|:--|:--|
| 对齐见证 | callee 返回 `%rsp & 15` | 调用点是否 0 mod 16 |
| 哨兵寄存器 | 调用前把 callee-saved 写成魔数，调用后比对 | callee 是否恢复 |
| 位宽扫描 | 对每种源类型生成 load/store，反汇编核对 | `movl`/`movq`/`movsbl` 选择 |
| 内存读改写 | 生成 `*p += x`，运行比对结果 | `add` 目的/源合法性 |
| 参数边界 | 6/7 个整数、8/9 个浮点、大小聚合 | 参数分类与栈偏移 |
| 可变参数 | 浮点可变参数，检查 `%al` | `%al` 与 `movaps` 对齐 |
| 链接检查 | `llvm-readelf -r` 看 PLT32；Linux 上看 `.plt` | 外部调用重定位/PLT |
| 分配器回归 | `112B` 分配与相邻块元数据 | footer 越界 |

六条历史错误的逐条回归：

| # | 历史错误 | 正确做法 | 本机证据 | 通过标准 |
|--:|:--|:--|:--|:--|
| 1 | 栈对齐多减 8 | `call` 前 0 mod 16；callee 入口 8；`push %rbp` 后 `sub` 是 16 的倍数 | `align_ok` 退出 8；`align_bad` 退出 0；clang `subq $0x30` | 见证函数返回 8 |
| 2 | `movq 8(%rdi), %eax` | 32 位目的必须 `movl` | 汇编器报 `invalid operand`；`movl` 编码 `8b 47 08` | `movq` 被拒绝，`movl` 通过 |
| 3 | 说 `add` 目的不能是内存 | `add` 可读改写内存；两个操作数不能同时为内存 | `addl %eax,(%rdi)` 编码 `01 07`，运行结果 42 | 运行得到 42；两内存被拒绝 |
| 4 | 把 `x30` 当 callee-saved | `x30` 是 LR；非叶函数保存，叶函数不必；callee-saved 按 AAPCS64 | `_nonleaf` 的 `stp/ldp x29,x30`；漏保存仍能汇编 | 非叶函数有 `stp/ldp`，静态检查通过 |
| 5 | PLT 懒绑定跳 `_init` | 懒绑定经 PLT0 | `R_X86_64_PLT32` 重定位（本机）；Linux 上 `llvm-objdump -d --section=.plt` | PLT[n] 未解析路径跳 PLT0 |
| 6 | 分配器漏 footer | `need = align_up(n + HDR + FTR, ALIGN)` | 交叉引用 Linux 9.9.6；112B 用例 | 相邻块元数据不被覆盖 |

第 1 条的三个数字要能同时说清：`call` 前 0、callee 入口 8、`push %rbp` 后 0。只记「栈要 16 字节对齐」会在 `push %rbp` 之后多减 8；只记「入口是 8」会在 prologue 里把 `sub` 写成 8 的倍数而不是 16 的倍数。第 2、3 条能被汇编器抓住，适合做 CI 的第一道门；第 1、4、5、6 条汇编器抓不到，必须靠运行时见证、静态走查、链接器检查、分配器回归。

哪些工具抓哪些错误：

| 错误 | 汇编器 | 链接器 | 静态走查 | 运行时测试 |
|:--|:--:|:--:|:--:|:--:|
| 位宽/两个内存操作数 | 抓 | — | — | — |
| 栈对齐 | 不抓 | — | 抓 | 抓 |
| callee-saved 未恢复 | 不抓 | — | 抓 | 抓 |
| `x30` 未保存 | 不抓 | — | 抓 | 抓（返回链错） |
| PLT 误读 | 不抓 | 抓（`.plt`） | — | 抓（首次调用） |
| footer 越界 | 不抓 | — | — | 抓（ASan/元数据） |

这张表解释了为什么「能编译」不等于「ABI 正确」。汇编器只验证编码；链接器只验证符号与重定位；静态走查验证栈与寄存器契约；运行时测试验证实际行为。四层都要有，缺一层就有一类错误漏网。

::: method ABI 合规测试的编写顺序
1. 先写对齐见证：一个只返回 `%rsp & 15` 的 callee，调用者用不同 prologue 调用它；期望 8。
2. 再写哨兵测试：调用前把 `%rbx/%r12–%r15` 写成魔数，调用后比对；任何未恢复都会失败。
3. 用 `llvm-objdump` 扫描所有 `callq` 前的 `%rsp` 模 16；把扫描器接进 CI。
4. 对每个源类型生成 load/store，反汇编核对助记符与宽度；不只比对运行结果。
5. 对每个外部符号检查重定位类型；Linux 上再加 `.plt` 的 PLT0 检查。
6. 最后跑分配器 112B 回归；确认相邻块头部/尾部未被覆盖。
:::

边界：这些测试验证的是「你的生成器在这个目标上的合同」，不是「所有 ABI 变体」。Windows x64 的 shadow space、AAPCS64 的 `x8`、RISC-V 的 `a0–a7` 都要各自的测试。测试也不能证明「没有未定义行为」；它只能证明「在这些输入和这些检查下没有发现违反」。第 9、10 章会把「测试通过」与「语义正确」的差距讲清楚。

把六条回归接进 CI 的命令可以很具体：

```bash
python3 experiments/ch08/abi_lab.py
llvm-objdump -d experiments/ch08/build/demo.o
llvm-readelf -r experiments/ch08/build/plt.o
```

第一行跑对齐、位宽、add、x30、PLT32 的自动检查；第二行看 `_demo` 的 `movl`/`addl`/`subq`；第三行看 `R_X86_64_PLT32`。在 Linux 上再加：

```bash
llvm-readelf -S app | grep -E '\.plt|\.got'
llvm-objdump -d --section=.plt app
```

检查 `.plt` 时，先找 PLT0 的 `jmp *GOT+16`，再找每个 PLT[n] 的未解析路径是否跳到 PLT0 的地址；如果它跳到 `_init`，说明你看错了节区或链接器生成了非懒绑定。把这条检查写成脚本，输入是 `llvm-objdump` 的输出，断言「PLT[n] 的最后一条 `jmp` 目标是 PLT0」。

回归失败时按症状定位：

| 症状 | 先查 | 再查 |
|:--|:--|:--|
| 见证返回 0 而非 8 | prologue 的 `push/sub` | callee 的 `sub` 是否 16 的倍数 |
| 库函数崩在 `movaps` | 调用点 `%rsp` 模 16 | 可变参数 `%al` |
| callee-saved 值变 | 保存/恢复配对 | 是否用了 caller-saved 存跨调用值 |
| 外部调用跳错 | `R_X86_64_PLT32` | Linux 上 `.plt` 的 PLT0 |
| 堆元数据坏 | 112B 分配的 footer | 相邻块头部 |

这张表把「现象」映射到「第一个该看的证据」，避免在错误层浪费时间。ABI 问题的定位顺序通常是「栈 → 寄存器 → 参数 → 链接」，因为栈错会污染后面所有观察。

把回归输入写成表，测试才有覆盖：

| 签名 | 重点 | 期望 |
|:--|:--|:--|
| `long f(long,long,long,long,long,long,long)` | 第 7 个参数在栈 | `16(%rbp)` |
| `double f(double×9)` | 第 9 个浮点在栈 | `16(%rbp)` |
| `struct Pair f(int,int)` | 8 字节聚合进 `%rax` | 无隐藏指针 |
| `struct Big f(long)` | 24 字节聚合用 `%rdi` 隐藏指针 | 参数后移 |
| `int f(const char*, ...)` | `%al` 向量计数 | `movb` 到 `%al` |
| `void f(int*)` | `*p += x` | `addl` 内存目的 |

每条都配一个反汇编断言，而不是只跑数值。数值测试可以因为「恰好没用到高 32 位」通过，反汇编断言不会。

在 CI 里，把 `abi_lab.py` 的退出码当作门禁：24 项检查全过才允许合并。它覆盖了对齐、位宽、内存 add、x30、PLT32；链接器侧的 `.plt` 检查在 Linux job 里单独跑。不要把「编译通过」当作门禁——本章的 agent 错误全部能编译通过，只有一个会被汇编器拒绝。

一次完整的本地检查可以写成：

```bash
python3 experiments/ch08/abi_lab.py
llvm-objdump -d experiments/ch08/build/demo.o | grep -E 'subq|callq|movl|addl'
llvm-readelf -r experiments/ch08/build/plt.o
llvm-objdump -d --disassemble-symbols=_nonleaf experiments/ch08/build/arm.o
```

第一行 24 项检查；第二行看 x86 栈/位宽/add；第三行看 PLT32；第四行看 ARM64 的 `x30` 保存。四条命令覆盖六条历史错误里的 1–5；第 6 条（分配器 footer）在 Linux 9.9.6 的回归里，不在本仓库实验范围。把命令贴进 CI，比写「已检查」可靠。

六条回归的执行顺序建议：先跑汇编级检查（2、3），因为失败信息最直接；再跑运行时对齐/哨兵（1、4），因为需要执行；最后跑链接/分配器（5、6），因为它们依赖外部工具/环境。每条都记录「命令、真实输出、通过标准」；没有真实输出的回归不算回归。CI 里可以把 1–4 做成一个 job，5 单独一个 Linux job，6 放分配器仓库。

测试矩阵还应包含「无调用」「单调用」「多调用」「可变参数」「聚合返回」五种形状。只测无调用函数，栈对齐和 callee-saved 都可能潜伏；只测单调用，跨多个调用的累积破坏测不到；只测整数，浮点寄存器类/`%al` 测不到；只测标量返回，隐藏指针/sret 测不到。形状覆盖比输入数量更重要。

## 8.8 agent 错误：栈对齐、寄存器破坏与 PLT 误读 {#sec-compilers.2.8.8}

这一节的 agent 任务：为一个小语言生成 x86-64 代码，要求支持函数调用、`int` 局部变量、指针写。agent 交出的 prologue 是：

```asm
pushq %rbp
movq %rsp, %rbp
subq $8, %rsp
```

它的解释是「栈要 16 字节对齐，减 8 是为了留空间」。**症状**：所有不调用 libc 的测试通过；一旦调用 `printf`，程序在 libc 内部崩，栈回溯显示 `movaps` 的地址未对齐。换一台机器/换一个 libc 版本，崩溃位置可能不同，甚至可能不崩——这让问题看起来像「环境问题」。这个 libc 崩溃场景是复盘，不是本机复现；本机复现的是同一条栈对齐违反（`align_bad` 退出 0），见下。

**根因**：入口 `%rsp ≡ 8`，`push %rbp` 后 ≡ 0，再 `sub $8` 变成 ≡ 8；`call` 前是 8，callee 入口是 0，违反「callee 入口 8」。libc 的 `printf` 在保存向量寄存器或处理 `va_list` 时使用 16 字节对齐的 `movaps`；入口错 8 会让某些地址不对齐。错误不是「少减了 8 字节空间」，而是「破坏了调用链的不变量」。

**如何发现**：实验的见证函数在 callee 入口返回 `%rsp & 15`。正确 prologue 返回 8；agent 的 prologue 返回 0：

```text
align_ok: exit=8
align_bad: exit=0
ops: exit=42
```

第一行是 `push %rbp; sub $16`，第二行是 `push %rbp; sub $8`。两个程序都能汇编、都能运行，差别只在退出码。用静态走查也能得到同样结论：入口 8 → push 0 → sub 8 → 8，`call` 前不是 0。

**修复**：`sub` 改成 16 的倍数（或删掉这条 `sub`，如果不需要局部空间）：

```asm
pushq %rbp
movq %rsp, %rbp
subq $16, %rsp
addq $16, %rsp
popq %rbp
retq
```

如果函数没有 `push %rbp`，入口 8，`sub $8` 反而是对的；修复要针对实际 prologue，而不是背「sub 8 一定错」。如果 prologue 保存了奇数个 callee-saved 寄存器，还需要再 `sub $8` 或 push 一个 padding 寄存器；clang 在 `_after` 里用 `pushq %rax` 做 padding，见 8.2。

同一个 agent 的输出里还有三处相关错误：

| agent 的说法/写法 | 实际 | 检查 |
|:--|:--|:--|
| `movq 8(%rdi), %eax` 读 `int` | 32 位目的必须 `movl` | 汇编器报 `invalid operand` |
| 「`add` 的目的不能是内存」，所以 `*p += x` 拆成 load/add/store | `add` 可读改写内存；限制是两个操作数不能同时为内存 | `addl %eax,(%rdi)` 运行 42 |
| 注释「PLT 懒绑定跳到 `_init`」 | 懒绑定经 PLT0；`_init` 是初始化代码 | `llvm-readelf -r` 看 PLT32；Linux 上看 `.plt` |

这三个错误和栈对齐错误来自同一种思维：把 ABI 当成「大概的写法」，而不是「可检查的合同」。agent 没有恶意，它只是没有被要求给出「`call` 前模 16」「`movl` 编码」「PLT0 目标」这些可验证的证据。修复流程也应该按合同走：先写见证/断言，再改代码，最后把断言接进 CI。

::: ex 例 8.8.1 · 错位如何沿调用链传播 {#ex-compilers.2.8.8.1}
agent 的 `main`：入口 8 → push rbp 0 → sub 8 → 8 → `call f`，`f` 入口 0。`f` 的 prologue：push rbp → 8 → sub 16 → 8 → `call g`，`g` 入口 0。`g` 若用 `movaps` 存 `%xmm0` 到它认为 16 字节对齐的栈槽，地址可能错 8；若 `g` 再调用 `h`，错位继续传播。每一层都「只错 8」，但每一层都认为自己是按 ABI 写的。见证函数在任意一层返回 `%rsp & 15`，都能看到 0 而不是 8。
:::

::: method 排查「调用后崩在库里」
1. 先在 callee 入口打印/返回 `%rsp & 15`；期望 8。不是 8 就查调用者的 prologue。
2. 用 `llvm-objdump` 走查每个 `callq` 前的 `%rsp`；不要只看有问题的那个函数。
3. 检查 prologue 是否 `push %rbp` 后 `sub` 了 8 的奇数倍；若是，改成 16 的倍数或调整 padding。
4. 检查 callee-saved 的 push 个数；奇数个 push 需要额外 padding。
5. 检查可变参数调用是否设置 `%al`；`%al` 错会让 callee 跳过向量保存。
6. 最后才怀疑 libc/内核；ABI 错误通常在你自己的 prologue 里。
:::

边界：不是所有 `movaps` 崩溃都等于栈错位；也可能是指针本身没对齐、结构体布局错、越界写坏了栈。见证函数只能告诉你 `%rsp` 的模，不能告诉你「哪个指针对齐错」。排查时先把 `%rsp` 排除，再看数据地址；两条线索不要混在一起。

第二个 mini-case 是位宽。agent 生成的 `int` load 是 `movq 8(%rdi), %eax`；它说「`%rax` 是 64 位，读 8 字节更保险」。汇编器拒绝后，它改成 `movq 8(%rdi), %rax`，编译通过了，但读的是 8 字节，而源对象只有 4 字节；在小测试里相邻字节恰好是 0，值看起来对，换一个栈布局就错。正确的修复不是「换成 `%rax`」，而是「读 `int` 用 `movl`」。这个案例说明：汇编器的错误信息只告诉你「操作数不匹配」，不告诉你「源类型是 `int`」；生成器必须自己带类型信息。

第三个 mini-case 是 `add`。agent 在注释里写「`add` 的目的不能是内存」，于是把 `*p += x` 生成成 `movl (%rdi), %eax; addl %esi, %eax; movl %eax, (%rdi)`。功能正确，但多了一条 load 和一条 store；在热循环里这是可测量的差距。它没有测试「一条 `addl %esi,(%rdi)` 是否合法」，也没有读 `llvm-objdump` 的编码。修复后代码变短，且不影响标志语义（两条形式都写标志；若后续不读标志，还可以用 `lea` 进一步优化）。

三个错误（对齐、位宽、add）加 PLT 误读，共同根因是「用记忆中的规则代替证据」。agent 的输出没有一条断言「`call` 前模 16」「源类型宽度」「`add` 的内存形式」「PLT0 目标」；它只写了「应该这样」。修复流程也应该围绕断言：先写见证/反汇编检查，再改生成器，最后把断言接进 CI。这样下一个 agent（或下一个人）改坏时，测试会先说话。

| agent 的输出 | 检查 | 结果 |
|:--|:--|:--|
| `push %rbp; sub $8` | 见证返回 `%rsp & 15` | 0，应为 8 |
| `movq …, %eax` | 汇编器 | 拒绝 |
| `movq …, %rax` 读 `int` | 反汇编 + 源类型 | 读越界 4 字节 |
| 「`add` 不能写内存」 | `addl %eax,(%rdi)` | 合法，运行 42 |
| 「PLT 跳 `_init`」 | `llvm-readelf -r` / `.plt` | 应为 PLT0 |

这张表可以直接当 code review 清单：看到生成器输出，就按行要证据；没有证据的断言，默认不可信。

修复后的 prologue 与对应断言：

```asm
pushq %rbp
movq %rsp, %rbp
subq $16, %rsp
addq $16, %rsp
popq %rbp
retq
```

```text
assert rsp_walk("_main") == [0]        # call 前 0 mod 16
assert witness() == 8                   # callee 入口 8
assert "subq $0x10" in disasm           # 帧大小 16 的倍数
assert "movl 0x8(%rdi), %eax" in disasm # 32 位 load 用 movl
assert "addl %eax, (%rdi)" in disasm    # 内存读改写
```

这些断言比「输出等于 42」更能防回归：它们直接检查合同项，换一个测试程序仍然有效。把断言接到 CI，agent 下一次改 prologue 时会先看到失败，而不是等 libc 崩。

修复顺序建议：先改 prologue 的对齐（影响最大、最容易复现），再改位宽（汇编器会立刻告诉你），再改 `add` 的生成（性能/代码量），最后补 PLT/x30 的注释与检查。每改一项，先跑对应的断言，再跑全量；不要一次改四处，否则失败时不知道哪一处引入的新问题。

修复 agent 输出时按这个顺序：

1. 先跑见证函数，确认 `%rsp` 模 16；不改其他代码。
2. 再跑汇编，修位宽/操作数错误；汇编器会逐条告诉你。
3. 用 `llvm-objdump` 检查 `add` 是否用了内存形式；若没有，改生成器。
4. 检查 callee-saved 的保存/恢复配对；用哨兵测试。
5. 检查 PLT32/`.plt`（Linux）与 `x30`（ARM64）。
6. 最后跑全量差分/ABI 测试，确认没有回归。

每步只改一类问题，失败时才能定位。一次改四处，测试红了也不知道是哪一处引入的。

本章的六条历史错误不是「考试题」，而是六个曾经真实发生过的错误。它们之所以值得单列，是因为每一条都能通过「看起来合理」的代码审查：多减 8 像是保守，`movq` 像是读得更全，`add` 不写内存像是「安全」，`x30` 像是该保存，PLT 跳 `_init` 像是「初始化入口」，footer 像是「分配器细节」。识别它们靠证据，不靠直觉。

## 8.10 本章陷阱（8–15 条） {#sec-compilers.2.8.10}

::: errata 本章陷阱
1. **认为 callee 入口 `%rsp` 是 0 mod 16**。现象：prologue 里 `sub` 了一个 16 的倍数，仍然错位。原因：`call` 压了 8 字节返回地址，入口是 8，不是 0。修复：按 8.2 的表逐步记账，校准到 `call` 前为 0。
2. **认为 `call` 不改变 `%rsp`**。现象：只计算 prologue 的 `sub`，忘了返回地址。原因：`call` 压栈 8 字节，`ret` 弹出。修复：把 `call`/`ret` 也纳入 `%rsp` 走查。
3. **`push %rbp` 之后 `sub $8`「为了对齐」**。现象：callee 入口变成 0，libc 的 `movaps` 崩。原因：push 已经把 `%rsp` 从 8 变成 0，再减 8 反而破坏。修复：`push %rbp` 后 `sub` 用 16 的倍数，或删掉不必要的 `sub`。
4. 认为「`sub $8` 一定错」。现象：把无帧指针函数的正确 `sub $8` 改成 `sub $16`，反而错位。原因：没有 `push %rbp` 时入口是 8，`sub $8` 正好到 0。修复：按实际 prologue 记账，不背结论。
5. **`movq 8(%rdi), %eax`**。现象：汇编器报 `invalid operand`。原因：`movq` 需要 64 位目的寄存器，`%eax` 是 32 位。修复：读 `int` 用 `movl`；读 `long`/指针用 `movq` 到 `%rax`。
6. **认为 `movl` 对所有类型都安全**。现象：读 `long` 只拿到低 32 位，或读 `int` 用 `movq` 越界。原因：位宽由源类型决定，不由「寄存器够不够大」决定。修复：按类型选择 `movl`/`movq`/`movslq`/`movzbl`。
7. **说 `add` 的目的不能是内存**。现象：把所有 `*p += x` 拆成 load/add/store，代码变长。原因：`add` 支持内存目的读改写；限制是两个操作数不能同时为内存。修复：用 `addl %eax,(%rdi)`；两个都内存时先 load 一个。
8. **认为两个内存操作数可以相加**。现象：`addl (%rdi),(%rsi)` 被汇编器拒绝。原因：x86 一条指令最多一个内存操作数。修复：先 `mov` 到寄存器，再 `add`。
9. **把 `x30` 当 callee-saved**。现象：非叶函数不保存 `x30`，`ret` 跳错。原因：`x30` 是 LR，`bl` 会覆盖；AAPCS64 的 callee-saved 是 `x19–x28`/`x29`。修复：非叶函数在 `bl` 前 `stp x29,x30`，返回前 `ldp`。
10. **认为叶函数也要保存 `x30`**。现象：叶函数多一对 `stp/ldp`，性能略降但不算错。原因：叶函数没有 `bl`，`x30` 不被覆盖。修复：按是否含 `bl` 决定，不要一律保存。
11. **说 PLT 懒绑定跳 `_init`**。现象：解释链接过程时把初始化代码当解析器。原因：懒绑定经 PLT0，`_init` 是进程初始化。修复：用 `llvm-objdump -d --section=.plt` 看 PLT[n] 的未解析路径跳 PLT0。
12. **认为汇编器会检查 ABI**。现象：`push %rbp; sub $8` 能汇编，就以为正确。原因：汇编器只检查语法/编码，不检查栈对齐、callee-saved、LR。修复：加静态走查与运行时见证。
13. **在非叶函数里使用 red zone**。现象：调用后局部值被覆盖。原因：callee 的栈帧会使用 `%rsp` 以下区域。修复：只有叶函数能用 red zone；非叶函数先 `sub`。
14. **可变参数调用不设 `%al`**。现象：`va_arg` 读到垃圾或 `movaps` 崩。原因：`%al` 告诉 callee 用了多少向量寄存器；不设会让它跳过保存。修复：调用前按使用的 `%xmm` 个数写 `%al`。
15. **只测返回值，不测合同项**。现象：数值测试全过，换 libc/换机器崩。原因：数值正确不代表栈对齐、callee-saved、参数分类正确。修复：按 8.7 的表加见证、哨兵、反汇编断言，把合同项变成可执行测试。
:::

这份清单里，第 1–4 条是栈账，第 5–8 条是位宽/操作数，第 9–10 条是 `x30`，第 11–12 条是链接与工具边界，第 13–14 条是 red zone 与可变参数。每条都能用本章的实验或 objdump 命令复现；不要只记结论，记「用哪条命令看哪个数」。

复习时不要按 1–15 的顺序背。先按「栈账、位宽、x30、链接、测试」五组分类，每组挑一条实验命令跑一遍，再看对应陷阱。能复现的陷阱才是真陷阱；复现不了的，回到 8.1 的分工表，确认自己是不是把链接器/分配器的责任算到了编译器头上。

不是所有 ABI 错误都能靠测试抓到。测试只覆盖它执行的路径；一个只在异常展开、只在可变参数、只在跨动态库边界发生的错误，可能长期潜伏。这就是为什么本章同时要求静态走查（栈账、保存/恢复配对）和反汇编断言（位宽、内存形式）：它们不依赖输入覆盖。测试负责「实际行为」，静态检查负责「合同形状」，两者不能互相替代。

复习顺序可以是：先跑 `abi_lab.py` 看 24 项检查的输出，再按 8.2 的表手算一遍 `_after` 的栈账，然后用 `llvm-objdump` 核对 `movl`/`addl`，最后读 8.4 的 ARM64 反汇编与 8.1 的 PLT32。每一步都要能指出「哪条指令、哪个偏移、哪个退出码」，而不是「我记得是这样」。

最后区分三种证据的可信度，避免把一种证据当成全部：

| 证据 | 能证明 | 局限 |
|:--|:--|:--|
| 汇编成功 | 指令编码合法 | 不证明 ABI、不证明语义 |
| 反汇编断言 | 生成的指令/偏移符合预期 | 依赖反汇编器，不证明运行时 |
| 运行时见证 | 实际寄存器/栈值符合合同 | 只覆盖执行的路径 |
| 六条回归全过 | 已知历史错误不再复现 | 不证明没有新错误 |

对本章的六条错误，最弱的证据是「能编译」，最强的是「在目标硬件上按合同运行且反汇编断言通过」。本机没有 x86-64 硬件，用 Rosetta 做运行时见证、用 objdump 做静态断言，两者合起来接近「可复现」；不能声称等同于真机。把这个条件写进结论，比写「已验证」更准确。

证据等级不是修辞：同一句结论，用 E1（规范）、E2（本机复现）、E3（推理）、E4（单次观察）标注，读者才知道它能推广多远。

这些陷阱反复出现，是因为它们都「能编译、能跑小测试」。位宽错误里只有编码不匹配会被汇编器抓；栈对齐、callee-saved、x30、PLT、footer 都要专门的证据。学习时不要把「编译通过」当成「ABI 正确」，也不要把「本机跑通」当成「目标硬件正确」。

与 Linux 书的边界再划一次：本章讲「编译器生成什么、如何验证」，不讲「ELF 怎么加载、PLT 怎么改写 GOT、分配器怎么合并空闲块」。遇到这些机制，去 Linux 1.7/9.9.6 读完整版；本章只保留验证入口（PLT32 重定位、footer 公式与 112B 回归）。边界清楚，两本书才不会互相重复。

如果只能记一句话：**ABI 是合同，不是风格**。合同项可以逐条检查，风格不能。栈对齐、位宽、callee-saved、x30、PLT、footer 都有明确的通过/失败标准；把它们写成断言/命令，比记「通常这样写」可靠。

另一个常见误区是把「编译器优化」当成 ABI 的替代。优化可以改变指令选择、调度、内联，但不能改变合同；反过来，ABI 合规也不要求关闭优化。测试要在 `-O0`/`-O2` 下都跑，因为优化会改变栈布局、寄存器分配和内联边界，可能暴露不同的 ABI 错误。

ABI 的很多规则在源码层看不出来，只有反汇编/运行时才暴露。读本章时随手打开终端跑 `abi_lab.py`，对照输出看每一行；只看文字不跑实验，很容易把「16 的倍数」记成「8 的倍数」。

读到这里，你应该能解释「为什么 `sub $8` 有的地方对、有的地方错」而不是背结论；能解释「`movq` 到 `%eax` 为什么被拒绝」而不是背助记符；能解释「`x30` 为什么不是 callee-saved」而不是背列表。三个「为什么」都能用本章的表/反汇编回答，才算过关。

把六条错误的「正确写法」抄成一张小卡：`call` 前 0、`movl`、`add` 可写内存但最多一个内存操作数、`x30` 是 LR、PLT0、`need=align_up(n+HDR+FTR)`。卡上每条都配一个命令；没有命令的条目，说明你还没真正验证过它。

六条错误的回归不是一次性的：每次改 prologue、参数搬运、位宽选择，都可能让其中一条复发。
把 8.7 的表贴进 PR 模板，要求作者填「跑了哪条命令、看到什么输出」。
没有输出的「已检查」不算检查。

## 8.11 本章出口检查 {#sec-compilers.2.8.11}

六条错误的正确写法，按检查顺序排列：
- 栈：`call` 前 0 mod 16，入口 8，`push %rbp` 后 `sub` 为 16 的倍数。
- 位宽：32 位目的用 `movl`，64 位用 `movq`，符号扩展用 `movslq`。
- 内存：`add` 可读改写内存，但两个操作数不能同时为内存。
- ARM64：`x30` 是 LR，非叶函数保存，叶函数不必。
- 链接：PLT 懒绑定经 PLT0，不是 `_init`。
- 分配器：`need = align_up(n + HDR + FTR, ALIGN)`，112B 是回归输入。

证据等级写在结论旁边，读者才知道它能推广多远。
本机验证是 E2，不是 E1；真机/规范才是更强的证据。

**Q1** 函数入口 `%rsp = 8`，prologue 是 `push %rbp; push %rbx; sub $24, %rsp`。`call` 前 `%rsp` 模 16 是多少？如果错，怎么改最小？

**Q2** 为什么 `push %rbp` 之后 `sub $8` 是错的，而某些没有 `push %rbp` 的函数 `sub $8` 又是对的？用一句话说清规则。

**Q3** `movl 8(%rdi), %eax` 与 `movq 8(%rdi), %rax` 都从地址 8(%rdi) 取值，什么时候必须用前者？如果源是 `long` 而用了 `movl`，会发生什么？

**Q4** `x30` 是 link register，不是 callee-saved。为什么非叶函数仍然要保存它？叶函数为什么不保存也能正确返回？

**Q5** 在 Rosetta 下，一个 `sub $8` 错位的程序可能正常退出。能否据此说「这个程序 ABI 正确」？应该用什么证据？

**Q6** 为什么 `addl %eax, (%rdi)` 只有一条指令，而某些 RISC 目标需要三条？这是否意味着 x86 的代码生成「更好」？

**Q7** `movl` 写 `%eax` 会把 `%rax` 高 32 位清零。这是 ABI 规定还是指令集规定？它对返回 `long` 有什么影响？

**Q8** clang 在 `_after` 里用 `pushq %rax` 做对齐 padding，而不是 `subq $8, %rsp`。两者都对吗？为什么它选 push？

**Q9** 如果一段汇编在 Rosetta 下运行正确、在真机上崩，应该先怀疑 ABI 还是 UB？用什么证据区分？

**Q10** 为什么 callee-saved 的测试要用「哨兵寄存器」，而不能只看函数返回值？

**Q11** 如果一个函数既有 `push %rbx` 又有 `sub $8`，`call` 前 `%rsp` 是多少？需要怎么改？

::: sol 答案
**A1** 入口 8 → push rbp 后 0 → push rbx 后 8 → sub 24 后 (8 - 24) mod 16 = 0，所以在 call 前是 0，正确。若把 sub 24 改成 sub 16，(8 - 16) mod 16 = 8，就错；可以保留 sub 24，或在 sub 16 后再 sub 8。关键是按实际 push 个数逐条算，不要套「16 的倍数」。

**A2** 规则是「`call` 前 `%rsp % 16 == 0`」。`push %rbp` 把入口的 8 变成 0，所以之后的 `sub` 要是 16 的倍数；没有 `push %rbp` 时入口还是 8，`sub $8` 正好到 0。离开「当前模 16」谈 `sub` 的大小没有意义。

**A3** 源是 `int`（4 字节）时必须用 `movl`；`movq` 会读 8 字节，越过 `int` 边界，属于越界读，而且目标 `%eax` 与 `movq` 不匹配（汇编器会拒绝 `movq ... , %eax`）。若源是 `long` 而用了 `movl`，只读低 32 位，高 32 位被清零（`movl` 零扩展），得到错误的值；需要 `movq` 读 8 字节，或明确只想要低 32 位。

**A4** 非叶函数执行 `bl` 时，硬件把返回地址写进 `x30`，覆盖函数入口时收到的返回地址；不保存就无法回到自己的调用者。叶函数没有 `bl`，`x30` 保持入口值，`ret` 直接用它返回，所以不必保存。保存 `x30` 是「因为调用指令会覆盖它」，不是「因为它属于 callee-saved 列表」。

**A5** 不能。Rosetta 是模拟器，可能不模拟未对齐 `movaps` 的 #GP，或者库函数的实现恰好没有触发异常；「没崩」不是「合同满足」。证据应该是见证函数返回 `%rsp & 15`（正确为 8）、静态走查每个 `call` 前为 0、以及反汇编确认 `sub`/`push` 的账。真机上的崩溃是更强的证据，但不是唯一证据；模拟器通过反而可能掩盖错误。

**A6** x86 的 `add` 允许内存目的读改写，所以一条指令完成 load/add/store；RISC 的 load/store 架构通常要求先把内存读进寄存器，运算后再写回，因此三条。它不意味着 x86「更好」：RISC 的定长编码、流水线和寄存器压力更可控，x86 的一条 `add` 在微架构上仍要拆成 load/add/store 微操作。代码生成的评价要看目标、动态指令数和实际瓶颈，不能只看汇编行数。

**A7** 这是 x86-64 指令集的规定（32 位写零扩展），不是 SysV ABI 的额外要求；ABI 只是在这个事实上定义「`int` 返回值放 `%eax`」等约定。对返回 `long` 的函数，若只写 `%eax` 就返回，`%rax` 的高 32 位被清零；负数 `int` 转 `long` 时必须显式 `movslq`/`cltq`，否则值会变成大正数。

**A8** 两者都能把 `%rsp` 从 8 调到 0（或从 0 调到 8），都合法。`pushq %rax` 编码 1 字节，`subq $8, %rsp` 编码 4 字节；push 还会写一个「死」寄存器（把 `%rax` 的值存到栈上），但反正马上要调用、`%rax` 是 caller-saved，不影响语义。clang 选 push 是编码大小/调度习惯，不是 ABI 要求；手写汇编用 `sub` 同样正确，只要 epilogue 对称。

**A9** 先怀疑 ABI，因为本章的错误模式就是「模拟器不崩、真机崩」；但不要停在怀疑。区分证据：ABI 问题能在反汇编里找到栈/寄存器/位宽/保存恢复的违反，且见证函数/哨兵测试会失败；UB 问题通常在优化级别变化、sanitizer 或不同输入下表现不同，反汇编本身可能完全合法。先跑 ABI 的四类检查（对齐、callee-saved、位宽、调用约定），全部通过再转到第 9 章的 UB 工具。

**A10** 返回值只反映函数「算得对不对」，不反映它「有没有偷偷改 callee-saved」。一个函数可能返回正确结果，却把 `%rbx` 改成临时值；调用者如果依赖 `%rbx` 跨调用，就会在后续出错。哨兵在调用前把 `%rbx` 写成魔数，调用后比对，能直接发现「未恢复」；返回值测试发现不了，因为返回值可能根本不用 `%rbx`。

**A11** 入口 8；`push %rbx` 后 0；`sub $8` 后 8。`call` 前是 8，错误。最小改法是把 `sub $8` 改成 `sub $16`（保持 0），或删掉 `sub`（若无局部空间），或在 push 前/后加一个 8 字节的 padding 使总调整量为 16 的倍数。改完用 `rsp_walk` 或见证函数确认 `call` 前为 0。

:::

做完这八节，你应该能从一段汇编里读出四件事：`%rsp` 在 `call` 前是否对齐、参数/返回值放在哪、callee-saved 是否成对保存、位宽/内存操作数是否合法。读不出来时，回到对应的表或 objdump 片段，用数据核对；不要用「应该没问题」代替证据。
:::
