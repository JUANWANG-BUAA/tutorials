第 4 章把程序降成了基本块和 CFG，并在 SSA 下把「哪个定义到达哪个使用」写成了显式的 def-use 链。SSA 让链变得清楚，却没有回答另外一类问题：在程序的某个点上，哪些事实对所有可能的执行路径都成立？在循环里，一个变量的值可能来自哪几条赋值？在块边界上，哪些变量还必须留在寄存器里？

这些问题不适合逐条路径回答。一条带循环的 CFG 有无限多条路径，而编译器只有有限的时间。数据流分析（dataflow analysis）换了一个角度：给每个基本块一个事实集合，用局部传递函数描述块内指令如何改变事实，用合并操作把多个前驱的事实合起来，然后迭代到不动点。第 5 章给出这套方法的定义、四个具体分析、算法与正确性边界。

这套框架是后面所有优化的地基。第 6 章的常量折叠、公共子表达式删除、循环不变代码外提都要读取这里算出的 IN/OUT；第 7 章的寄存器分配直接消费活跃变量；第 9 章的静态分析则把「事实集合」换成抽象域，继续用同一套单调迭代。

先看一个具体的坑。下面这张 CFG 里，`p + q` 只在循环体 B2 里计算，出口 B5 又写了同一个表达式：

```text
B0: i = 0; k = 7; h = 3 * 4; goto B1
B1: t0 = i < n; if t0 goto B2 else B5
B2: t1 = p + q; t2 = i == 0; if t2 goto B3 else B4
B3: s = s + t1; x = k * 6; y = h + k; goto B4
B4: i = i + 1; goto B1
B5: z = p + q; return z
```

如果 n 等于 0，执行路径是 B0 -> B1 -> B5，`p + q` 一次也没有算过。B5 不能把 `t1` 当作 `p + q` 的已有值来复用。把可用表达式的入口边界误写成「所有表达式都可用」，分析就会给出相反的结论，后面的公共子表达式删除（common subexpression elimination，CSE）会把 B5 改写成使用一个从未定义的临时变量。本章实验就是围绕这张图和两类初始化错误展开：

```bash
cd compilers
python3 experiments/ch05/dataflow_lab.py
```

脚本会打印四种分析每一轮的 IN/OUT、朴素迭代与工作列表的求值次数，最后给出两个反例。真实运行的结尾是：

```text
=== 固定点自检（正确解） ===
到达定值=True 活跃变量=True 可用表达式=True 常量传播=True
结论：OK（一致、自检通过、两个反例均按预期偏离）
```

## 5.1 格、单调框架与不动点 {#sec-compilers.2.5.1}

数据流分析最先要回答的不是「怎么算」，而是「为什么算得完」。如果只写一个 `while changed` 循环，循环体可能让事实集合越来越大，也可能让它在两个状态之间来回跳。前者在有界格上会停，后者连有界都救不了。终止性需要两个条件：值域有有限高度，传递函数单调。

先看方向。前向分析（forward analysis）沿 CFG 的边从入口向出口传播，后向分析（backward analysis）反过来。两个方向共用同一套格与传递函数，只是「谁合并谁」不同：

<pre class="layout">
前向：                         后向：
  IN[n] = ⊔ OUT[p]               OUT[n] = ⊔ IN[s]
          p∈pred(n)                       s∈succ(n)
  OUT[n] = f_n(IN[n])            IN[n] = f_n(OUT[n])

     ┌─────────┐                    ┌─────────┐
     │  IN[n]  │◄── 合并前驱 ──┐     │ OUT[n]  │◄── 合并后继 ──┐
     └────┬────┘               │     └────┬────┘               │
          │ f_n                │          │ f_n                │
          ▼                    │          ▼                    │
     ┌─────────┐               │     ┌─────────┐               │
     │ OUT[n]  │─── 流向后续 ──┘     │  IN[n]  │─── 流向前面 ──┘
     └─────────┘                    └─────────┘

格的形状（以集合的包含序为例，箭头指向「更大」）：
        ⊤ = 全集
       ╱       ╲
   {a,b}       {a,c}          ← 不可比，合并时取上确界
       ╲       ╱
        {a}
         │
        ⊥ = ∅
</pre>

读图：前向与后向只交换了「前驱/后继」和「IN/OUT」的位置，合并发生在进入传递函数之前；格图说明为什么合并结果必须落在同一个格内，以及为什么两条不可比的路径不能简单取其中一个。

::: def 定义 5.1.1 · 偏序、上确界与格 {#def-compilers.2.5.1.1}
集合 $L$ 上的二元关系 $\sqsubseteq$ 若自反、传递、反对称，则称偏序（partial order）。对 $a, b \in L$，元素 $c$ 是 $\{a,b\}$ 的上界，当 $a \sqsubseteq c$ 且 $b \sqsubseteq c$；最小的上界记作 $a \sqcup b$，称为上确界（join）。若任意两个元素都有上确界，$(L, \sqsubseteq)$ 是并半格。若还有下确界 $a \sqcap b$，则是格（lattice）。本书的数据流格都带最小元 $\bot$ 和最大元 $\top$，且满足有限高度条件：不存在无限严格上升链 $x_0 \sqsubset x_1 \sqsubset \cdots$。
:::

::: def 定义 5.1.2 · 数据流框架 {#def-compilers.2.5.1.2}
一个数据流框架由六部分组成：

1. 方向 $d \in \{\text{前向}, \text{后向}\}$；
2. 有限格 $(L, \sqsubseteq, \sqcup, \bot, \top)$；
3. 每个基本块 $n$ 的传递函数 $f_n : L \to L$；
4. 合并操作 $\sqcup$：前向合并前驱 OUT，后向合并后继 IN；may 分析取并集（上确界），must 分析取交集（下确界）；
5. 边界条件（boundary condition）：入口块的 IN 或出口块的 OUT；
6. 其余块的迭代初值。

方程写成 $\mathrm{IN}[n] = \bigsqcup_{p \in pred(n)} \mathrm{OUT}[p]$、$\mathrm{OUT}[n] = f_n(\mathrm{IN}[n])$。如果传递函数对每个 $n$ 都单调（$x \sqsubseteq y \Rightarrow f_n(x) \sqsubseteq f_n(y)$），则称单调框架（monotone framework）。
:::

四个分析填进这张表，差别只在方向和格：

| 分析 | 方向 | 格元素 | 合并 $\sqcup$ | 边界 | 其余初值 |
|:--|:--|:--|:--|:--|:--|
| 到达定值 | 前向 | 定值集合 | 并集 | $\mathrm{IN}[\text{entry}] = \varnothing$ | $\varnothing$ |
| 活跃变量 | 后向 | 变量集合 | 并集 | $\mathrm{OUT}[\text{exit}] = \varnothing$ | $\varnothing$ |
| 可用表达式 | 前向 | 表达式集合 | 交集 | $\mathrm{IN}[\text{entry}] = \varnothing$ | 全集 $U$ |
| 常量传播 | 前向 | 每个变量一个平坦格值 | 逐变量上确界 | 参数为 NAC，局部为 UNDEF | 全 UNDEF |

本书沿用 `notation.md` 的记法，用 $\sqcup$ 表示分析的合并算子，而不强调它在格论上是上确界还是下确界：may 分析取并集，must 分析取交集。读到 must 分析时，把 $\sqcup$ 理解成「合并」即可，不要套用上确界的直觉。

「其余初值」一列最容易被当成细节跳过，5.8 节会看到，把这一列和「边界」列混在一起，会让分析给出一个满足方程却不符合程序语义的解。

::: thm 定理 5.1.1 · 单调框架的终止性与不动点 {#thm-compilers.2.5.1.1}
设格 $L$ 高度有限（最长严格链长度为 $h$），每个 $f_n$ 单调，且迭代从某个初值 $x_0$ 出发、每轮按固定顺序用方程更新所有块。则迭代在有限轮内到达不动点。若 $x_0 \sqsubseteq \mathrm{MOP}$（前向 may 分析的乐观初值），得到的是最小不动点；若 $x_0 \sqsupseteq \mathrm{MOP}$（must 分析的乐观初值），得到的是最大不动点。
:::

::: proof 证明思路
每轮更新只会把某个块的值沿 $\sqsubseteq$ 向上（或向下）推进一步，不能来回。每个块的值最多经过 $h$ 次严格变化，$N$ 个块合计最多 $N \cdot h$ 次严格变化；每轮至少发生一次变化才会继续，因此轮数不超过 $N \cdot h + 1$。有限性保证没有无限链，单调性保证更新方向一致。最小/最大不动点的结论来自 Knaster–Tarski：单调函数在完备格上的不动点构成完备格，从最小元向上迭代得到最小不动点，从最大元向下迭代得到最大不动点。数据流格有限，完备性自动满足。
:::

实际实现里没人真的数 $N \cdot h$。常见做法是把每个事实编码成位向量（bitvector），一次合并就是几十条机器字上的按位或/与。此时 $h$ 等于事实总数（定值数、变量数或表达式数），终止性仍然成立，但迭代轮数可能达到事实数级别。第 5.5 节的工作列表把「每轮扫全部块」换成「只重算受影响的块」，渐进复杂度降一个 $N$。

::: intuition 为什么 must 分析要从「太大」的初值出发
可用表达式问的是「在所有到达这里的路径上，这个表达式都算过吗」。空集是「什么都没算」的悲观答案，全集是「什么都算过」的乐观答案。如果从空集出发向上加，循环的回边永远无法把「上一轮已经算过」这一事实带回循环头，分析会卡在空集；从全集出发向下删，第一次到达循环头时假设「都算过」，随后回边带来的 kill 会把它修正到真正对所有路径都成立的最大集合。may 分析反过来：空集是乐观的（没有事实），全集是悲观的；所以到达定值从空集出发向上加。
:::

::: note 单调性不是装饰
如果某个传递函数不单调，迭代可能震荡：某一轮把事实加进去，下一轮又因为新事实触发了另一个分支把它删掉。构造一个「若集合大小是偶数则加 $x$，否则删 $x$」的函数，就能让两个块互相触发、永不收敛。写分析时，`transfer` 只应读取输入集合，按固定的 gen/kill 规则产生输出；不要在传递函数里根据迭代轮数或全局状态改变规则。
:::

边界条件值得单独强调。入口块的 IN 不是「所有事实」或「空集」二选一的口味问题，而是程序语义的一部分：函数入口处没有任何表达式被计算过，所以可用表达式的入口 IN 必须是 $\varnothing$；函数参数的值未知，所以常量传播把参数标成 NAC。把入口的边界和迭代初值分开存放，是后面所有正确性检查的前提。

不可达块也要处理。若一个块没有前驱，前向合并是对空集求上确界：并集的身份元是 $\varnothing$，交集的身份元是全集 $U$。如果代码对空前驱列表直接返回 $\varnothing$，可用表达式会在不可达块上算出「没有表达式可用」，随后可能把死代码里的表达式误判为不可用；反过来，若对 must 分析返回 $U$，不可达块会声称一切可用。两种都不影响可达代码，但会让「删除不可达块」这个后续优化看到不同的输入。约定：先删不可达块，或让不可达块的分析结果不参与任何优化决策。

一个小菱形足以区分 may 与 must。B0 执行 `x = 1`，然后分两路：B1 不改变 x，B2 把 x 改成 2，两路在 B3 汇合，B3 读 x。若分析的事实是「x 等于 1」：

- may 分析（并集）：B1 的 OUT 含「x=1」，B2 的 OUT 不含；B3 的 IN 是两者并集，仍含「x=1」。结论是「x 可能等于 1」，不能据此把 B3 的 x 折成 1。
- must 分析（交集）：B1 的 OUT 含「x=1」，B2 的 OUT 不含；交集为空，B3 的 IN 不含「x=1」。结论是「不是所有路径都让 x=1」，同样不能折。

两个结论都不能支持「B3 的 x 一定是 1」，但原因不同：may 给的是「可能」，must 给的是「不是一定」。只有当你需要「可能」时（例如「这个值可能来自哪次赋值」），may 才有用；需要「一定」时，must 的交集才有用。把两者的结果混用，是 5.6 表格最后一列警告的情形。

| 编码 | 合并成本 | 空间 | 适用 |
|:--|:--|:--|:--|
| 位向量 | $O(F/w)$ | $F$ 位 | 事实固定、稠密 |
| 有序列表 | $O(F)$ | $O(F)$ | 事实稀疏、需要遍历 |
| 哈希集合 | 期望 $O(F)$ | 常数较大 | 动态事实、调试实现 |
| 区间 | $O(1)$ 每条 | 与区间数成正比 | 变量活跃区间、寄存器 |

路径枚举为什么不可行，值得用一个数字说明。假设一条路径上有 10 个独立的二元分支，从入口到出口就有 $2^{10} = 1024$ 条路径；20 个分支是 100 万条；带循环的图直接是无限条。数据流分析在每个合流点做一次合并，代价与路径数无关，只与块数、边数和格的高度有关。这是它能在编译器里使用的根本原因：用「在每个点合并」换掉了「枚举每条路径」。

| 结构 | 路径数 | 逐路径分析 | 数据流分析 |
|:--|--:|--:|--:|
| 10 个顺序 if | $2^{10}$ | 1024 次块遍历 | 每块一次，约 20 次 |
| 20 个顺序 if | $2^{20}$ | 约 100 万次 | 约 40 次 |
| 一个 while 循环 | 无限 | 不终止 | 有限轮，受格高度限制 |
| 嵌套循环 | 无限 | 不终止 | 有限轮，块数×高度 |

传递函数不是凭空写的，它由块内指令逐条复合而成。以一个四指令块为例：

```text
B7: a = b + c
    d = a * 2
    b = d - 1
    e = b + c
```

若分析是「哪些表达式可用」，逐条处理得到：

| 指令 | 加入 gen | 被 kill 的表达式 | 处理后 gen |
|:--|:--|:--|:--|
| a = b + c | b+c | 含 a 的表达式（无） | {b+c} |
| d = a * 2 | a*2 | 含 d 的表达式（无） | {b+c, a*2} |
| b = d - 1 | d-1 | b+c、b? 含 b 的都杀 | {a*2, d-1} |
| e = b + c | b+c | 含 e 的表达式（无） | {a*2, d-1, b+c} |

最终 $gen_{B7} = \{a*2, d-1, b+c\}$，$kill_{B7}$ 是所有含 a、b、d、e 的表达式（除了 gen 里的）。这张表也说明为什么顺序重要：第三条指令杀死 b+c，第四条又重新计算它，所以 b+c 在块尾又可用；如果实现先算 kill 再算 gen，就会把第四条的计算漏掉。

格的高度决定了迭代上界。四种分析的 $h$ 大致是：

| 分析 | 事实数 $F$ | 格高度 $h$ | 典型迭代轮数 |
|:--|:--|:--|:--|
| 到达定值 | 定值数 $D$ | $D+1$ | 与循环嵌套深度相关，常为个位数 |
| 活跃变量 | 变量数 $V$ | $V+1$ | 同上 |
| 可用表达式 | 表达式数 $E$ | $E+1$ | 同上 |
| 常量传播 | 变量数 $V$ | 每个变量 3 层 | 与 $V$ 线性相关的最坏界 |

「典型」不是保证。构造一个块链，每块只改变一个事实，轮数可以接近块数；这正是工作列表要解决的问题。

后向分析可以严格地看成「反向图上的前向分析」：把每条边 $u \to v$ 换成 $v \to u$，把 IN 与 OUT 的名字互换，把入口换成出口，后向方程就变成前向方程。这个等价性有两个实用后果。第一，任何前向分析的实现都可以通过反转 CFG 复用，不必写两套；第二，前向分析的性质（单调性、终止性、MOP 关系）自动适用于后向分析，只要把「路径」的方向反过来理解。实验里后向求解器单独实现，是为了让方向错误显式暴露；生产代码通常用同一套框架加一个 `reverse` 标志。

边界条件在两种方向下也要对称理解：前向的边界在入口，后向的边界在出口。把后向分析的边界误放在入口，活跃变量会从函数入口开始向后传播，得到的集合通常偏小；这个错误在小图上可能看不出来，因为入口的活跃集合往往也是空的。

本节只建立了框架。接下来四节分别填表：到达定值回答「哪些赋值可能产生这个值」，活跃变量回答「这个值后面还会不会被读」，可用表达式回答「这个表达式是不是在所有路径上都算过」，常量传播回答「这个变量的值是不是在所有路径上都相同」。

## 5.2 到达定值：方程、直觉与实现 {#sec-compilers.2.5.2}

到达定值（reaching definitions）回答一个具体问题：在程序点 $p$ 读到变量 $x$ 时，有哪些赋值语句可能产生这个值？编译器用它做常量传播、复制传播、未初始化检查，也用它判断某条赋值是否已经「死掉」。

定义把「可能」写成了集合的并。一个定值 $d$ 到达块 $n$ 的入口，当且仅当存在一条从 $d$ 所在块到 $n$ 的路径，且路径上没有对 $d$ 所定义变量的另一次赋值。

::: def 定义 5.2.1 · 到达定值 {#def-compilers.2.5.2.1}
设 $D$ 是程序中所有赋值语句（定值）的集合。对每个基本块 $n$，$\mathrm{IN}[n], \mathrm{OUT}[n] \subseteq D$。对定值 $d$ 所定义的变量 $v$，记 $kill_n$ 为「在块 $n$ 中被重新定义、从而杀死 $d$ 的定值集合」，$gen_n$ 为「块 $n$ 中产生且能到达块尾的定值集合」。前向方程为

$$
\mathrm{IN}[n] = \bigcup_{p \in pred(n)} \mathrm{OUT}[p], \qquad
\mathrm{OUT}[n] = gen_n \cup (\mathrm{IN}[n] \setminus kill_n)
$$

边界 $\mathrm{IN}[\text{entry}] = \varnothing$。合并是并集，因此这是 may 分析：一个定值只要在一条路径上到达，就留在集合里。解是最小不动点。
:::

块级 $gen$ 与 $kill$ 的计算有两个常见写法。第一种按指令顺序扫描：遇到赋值 $d: v = \cdots$，把 $d$ 加入 $gen$，把同变量的旧定值加入 $kill$，并从 $gen$ 中删掉被 $kill$ 的项。第二种先收集块内所有定值，再对每个变量只保留最后一次赋值作为 $gen$，把该变量的其他所有定值放进 $kill$。两种写法等价；第二种更容易向量化。

本实验的 CFG 有 11 条定值。编号按程序顺序：

| 定值 | 块 | 指令 | 变量 |
|:--|:--|:--|:--|
| d1 | B0 | i = 0 | i |
| d2 | B0 | k = 7 | k |
| d3 | B0 | h = 3 * 4 | h |
| d4 | B1 | t0 = i < n | t0 |
| d5 | B2 | t1 = p + q | t1 |
| d6 | B2 | t2 = i == 0 | t2 |
| d7 | B3 | s = s + t1 | s |
| d8 | B3 | x = k * 6 | x |
| d9 | B3 | y = h + k | y |
| d10 | B4 | i = i + 1 | i |
| d11 | B5 | z = p + q | z |

块级 gen/kill 如下。B0 定义 i、k、h，其中 i 在 B4 还有一次定义 d10，所以 d10 被 B0 杀死；对称地，B4 的 d10 杀死 B0 的 d1。其余变量在整张图里只有一次定义，kill 为空。

| 块 | gen | kill |
|:--|:--|:--|
| B0 | {d1, d2, d3} | {d10} |
| B1 | {d4} | ∅ |
| B2 | {d5, d6} | ∅ |
| B3 | {d7, d8, d9} | ∅ |
| B4 | {d10} | {d1} |
| B5 | {d11} | ∅ |

把表代入方程迭代，真实输出（第 3 轮已无变化）的最终解是：

| 块 | IN | OUT |
|:--|:--|:--|
| B0 | ∅ | {d1, d2, d3} |
| B1 | {d1, d2, d3, d4, d5, d6, d7, d8, d9, d10} | 同左 |
| B2 | 同 B1 | 同左 |
| B3 | 同 B1 | 同左 |
| B4 | 同 B1 | {d2, d3, d4, d5, d6, d7, d8, d9, d10} |
| B5 | 同 B1 | {d1, d2, d3, d4, d5, d6, d7, d8, d9, d10, d11} |

::: ex 例 5.2.1 · 为什么 B4 的 OUT 没有 d1 {#ex-compilers.2.5.2.1}
B4 的 IN 同时包含 d1（从 B0 经 B1、B2 传下来）和 d10（从 B3 传下来）。B4 执行 `i = i + 1`，它定义 i，于是 kill 掉所有其他 i 的定值：d1 被删，d10 是本次新产生的定值，保留。因此 $\mathrm{OUT}[B4] = \{d10, d2, d3, d4, \ldots\}$。这正是「强更新」：对确定的变量赋值，杀死该变量的全部旧定值。
:::

读最终表时容易产生一个错觉：B1 的 IN 有 10 条定值，似乎每条都「真的」到达了 B1。实际上 d7、d8、d9 只在循环至少执行一次后才到达；零次循环的路径上它们不产生。may 分析把「可能」全部并起来，所以集合大是正常的，不能据此断定某条定值一定执行过。要回答「是否一定执行过」，需要另一个方向的分析（must，例如「必定已定义」），不能用到达定值代替。

实现上有三个细节。

第一，定值的编号必须稳定。编译单元里重新排序基本块或重跑 pass 都可能改变编号；如果优化决策依赖编号的数值而不是集合关系，缓存和增量编译会失效。把定值 ID 与指令的稳定标识（函数名、块标签、指令序号或源码位置）绑定，别用数组下标直接当语义 ID。

第二，调用与指针会破坏「按变量名 kill」的规则。对一个可能指向任意内存的指针写入，编译器不能只杀死该指针变量本身的定值，还要杀死所有可能被别名（alias）到的变量的定值。保守做法是：遇到未知调用或逃逸指针的写入，杀死所有可从内存读取的变量定值，只保留局部标量。第 6.5 节会把这条规则展开。

第三，参数和全局变量在入口处需要隐式定值。函数参数在入口有一个「外部定义」，全局变量在程序启动时也有初始定值。若不建模，读到参数时会得到空集，未初始化检查会误报。实验里 p、q、n、s 被当作参数，但 CFG 没有为它们建入口定值；因此 B3 读 s 时，到达定值集合里没有 s 的定值。这在本实验里无害（我们只用它演示方程），在真实编译器里必须补上隐式定值，否则「读 s 没有定值」会被误判为未初始化。

下面这段是实验里块级 gen/kill 的核心。它验证「只保留每个变量在块内的最后一次赋值」这一规则：

```python
def reach_gen_kill(blocks, b, defs):
    defined = {var for (bb, var, _) in defs.values() if bb == b}
    kill = {d for d, (bb, var, _) in defs.items() if var in defined and bb != b}
    last = {}
    for d, (bb, var, _) in defs.items():
        if bb == b:
            last[var] = d
    gen = set(last.values())
    kill -= gen
    return gen, kill
```

对 B0，`last` 得到 i->d1、k->d2、h->d3，`kill` 得到 d10；对 B4，`last` 得到 i->d10，`kill` 得到 d1。预期输出与上表一致。注意 `kill -= gen`：同一条定值既在 gen 又在 kill 时，保留在 gen 里，因为它确实在块尾产生了一个新值。

强更新与弱更新是到达定值实现里最容易含糊的地方。对 `x = 1` 这样目标确定的标量赋值，可以强更新：杀死 x 的所有旧定值，只留新定值。对 `*p = 1`，若 p 可能指向 x 也可能指向 y，就不能只杀 x 或只杀 y，必须把所有可能被 p 指向的对象的定值都杀掉；这称为弱更新（weak update）。弱更新之后，被写对象的到达定值集合通常变成「旧定值 + 新定值」的并，而不是被新定值替换。

| 语句 | 影响的对象 | 更新方式 | 对常量传播的后果 |
|:--|:--|:--|:--|
| x = 1 | 标量 x | 强：杀 x 的旧定值 | x 变成常量 1 |
| *p = 1 | p 可能指向的任意对象 | 弱：杀所有可能对象的定值 | 受影响变量变成 NAC |
| a[i] = 1 | 数组 a 的任意元素 | 弱：杀 a 的所有元素定值 | a 的元素变成 NAC |
| call f() | 全局变量、逃逸对象、返回值 | 保守：按 f 的摘要或全部杀死 | 受影响的变量变成 NAC |
| volatile 写 | 该对象，且不能被优化掉 | 强更新但保留可观察顺序 | 不能折常量 |

异常边会改变 gen/kill。看一段带 try/catch 的 TAC：

```text
B0: x = 1
    if p goto B1 else B2
B1: x = 2
    call may_throw()
    goto B3
B2: y = x + 1
    goto B3
B3: return y
```

若 may_throw 抛出，控制流从 B1 直接到异常处理器，不经过 B3；此时 x 的定值 d2 仍然「到达」处理器，但到达定值分析若只按正常边建图，会漏掉这条路径。修复不是改传递函数，而是把异常边加进 CFG 的后继集合。同理，活跃变量在异常边上的使用（处理器读 x）也要建模，否则分配器会在异常展开前覆盖 x。

这张表和 5.6 的「调用/别名边界」是同一件事的两种表述：到达定值的 kill 规则必须和副作用模型一致。若 kill 少了，分析会认为某个旧值还能到达，常量传播会把旧常量继续传下去；若 kill 多了，分析会变得保守，但至少不会错。工程上先求 sound，再谈精度。

到达定值的用途可以列成一张表，每种用途都带自己的前提：

| 用途 | 需要的事实 | 额外前提 | 失败模式 |
|:--|:--|:--|:--|
| 常量传播 | 到达定值集合 | 所有到达定值给同一常量 | 只检查一条定值，漏掉另一条 |
| 复制传播 | 到达定值集合 | 所有到达定值都是同一个 copy | 把不同来源的 copy 混用 |
| 死存储删除 | 该定值不再到达任何使用 | 存储无副作用（非 volatile、非逃逸） | 删掉对 volatile/内存映射的写 |
| 未初始化检查 | 使用点没有到达定值 | 参数/全局有隐式定值 | 误报参数未初始化 |
| 指针分析初始化 | 指针变量的到达定值 | 所有定值指向同一对象 | 漏掉一条路径上的指针赋值 |

第四行值得展开。到达定值集合为空，可能意味着「未初始化」，也可能意味着「这个变量是参数，入口有隐式定值但没建模」。这两者的处理完全不同：前者要报错，后者是正常程序。真实编译器通常先做「必定已定义」（definitely assigned）的 must 分析，再对可能未定义的路径报错；到达定值只用来缩小检查范围。

位向量实现的核心是三条操作：并集、差集、测试。下面这段把块级 gen/kill 应用到 IN 上，得到 OUT：

```python
def transfer_reaching(gen, kill, in_bits):
    # gen、kill、in_bits 都是整数位图；第 d 位表示定值 d
    return gen | (in_bits & ~kill)
```

它验证的是 $OUT = gen \cup (IN \setminus kill)$。预期：`gen=0b0011, kill=0b0100, in=0b0111` 时结果是 `0b0011`（in 的 bit2 被 kill，bit0/1 来自 gen）。位运算的优先级容易写错，`in & ~kill` 必须加括号；在 Python 里 `~kill` 是无限位补码，配合 `&` 使用没问题，但若先把结果截断到固定宽度，顺序会反过来。

SSA 下到达定值的作用会缩小。SSA 已经保证每个变量只有一个定义，使用点直接连到定义，不需要集合推理；但内存（数组、指针、全局变量）通常不做 SSA，仍然需要到达定值或类似的 memory SSA。第 4 章讲过 SSA 构造，这里只强调：不要把「SSA 下的 def-use」和「到达定值」混为一谈，前者是语法链，后者是路径上的 may 集合。

到达定值的复杂度是 $O(N \cdot D)$ 位运算每轮，$D$ 是定值数。一个 10 万条指令的函数有 10 万个定值，位向量是 12.5 KB；每轮扫 1 万个块就是 125 MB 的内存流量，工作列表的必要性在这里变得具体。5.5 节会给出本实验的实测计数：朴素迭代 18 次块求值，工作列表 12 次 pop。

## 5.3 活跃变量：后向分析与寄存器分配接口 {#sec-compilers.2.5.3}

到达定值问「值从哪来」，活跃变量（live variable）问「值往哪去」：在程序点 $p$ 之后，变量 $v$ 的当前值是否还会被读取？如果不会，寄存器可以立刻复用，这条赋值也可能被删除。第 7 章的寄存器分配器把每个块入口/出口的活跃集合当作活跃区间（live interval）的边界；边界算错，分配器会把一个还要用的值覆盖掉。

活跃变量是后向 may 分析。说它 may，是因为「存在一条后续路径读取」就足以让变量活跃；说它后向，是因为信息从使用点向定义点倒流。

::: def 定义 5.3.1 · 活跃变量 {#def-compilers.2.5.3.1}
对基本块 $n$，$use_n$ 是在块内「先被读、后可能被写」的变量集合（upward-exposed uses），$def_n$ 是块内被赋值的变量集合。后向方程为

$$
\mathrm{OUT}[n] = \bigcup_{s \in succ(n)} \mathrm{IN}[s], \qquad
\mathrm{IN}[n] = use_n \cup (\mathrm{OUT}[n] \setminus def_n)
$$

边界 $\mathrm{OUT}[\text{exit}] = \varnothing$。合并是并集，解是最小不动点。变量 $v$ 在点 $p$ 活跃，当且仅当存在一条从 $p$ 到某个使用点的路径，且路径上没有对 $v$ 的重新定义。
:::

$use_n$ 的计算必须按指令顺序扫描，不能简单地把块内所有读操作并起来。看 B5：

```text
B5: z = p + q
    return z
```

块内读集合是 {p, q, z}，但 z 在块内先被定义，读 z 时用的是块内新值，不是入口值。因此 $use_{B5} = \{p, q\}$，$def_{B5} = \{z\}$，$\mathrm{IN}[B5] = \{p, q\}$。若把 z 也算进 use，$\mathrm{IN}[B5]$ 会多出 z，z 的活跃区间会被人为拉长到函数入口，寄存器压力凭空增加。这个错误不会让程序算错，只会让分配器多溢出几个值，因此很难靠功能测试发现。

真实输出中六个块的活跃集合是：

| 块 | IN | OUT |
|:--|:--|:--|
| B0 | {n, p, q, s} | {h, i, k, n, p, q, s} |
| B1 | {h, i, k, n, p, q, s} | {h, i, k, n, p, q, s} |
| B2 | {h, i, k, n, p, q, s} | {h, i, k, n, p, q, s, t1} |
| B3 | {h, i, k, n, p, q, s, t1} | {h, i, k, n, p, q, s} |
| B4 | {h, i, k, n, p, q, s} | {h, i, k, n, p, q, s} |
| B5 | {p, q} | ∅ |

::: ex 例 5.3.1 · 手算 B3 与 B4 {#ex-compilers.2.5.3.1}
B3 的指令是 `s = s + t1`、`x = k * 6`、`y = h + k`。按顺序扫描：读 s、t1 时两者都还没被定义，加入 use；随后 s 被定义；读 k、h 加入 use；x、y 被定义。所以 $use_{B3} = \{s, t1, k, h\}$，$def_{B3} = \{s, x, y\}$。$\mathrm{OUT}[B3] = \mathrm{IN}[B4]$。B4 读 i，随后定义 i；它的 IN 来自 B1，因此 B4 的 IN 至少含 i。代入 $\mathrm{IN}[B3] = use \cup (\mathrm{OUT} \setminus def)$，得到表里的 {h, i, k, n, p, q, s, t1}：x、y 被定义后没有再被读，所以不在 IN 里。
:::

这张表里有两个容易误读的地方。第一，B0 的 IN 只有 {n, p, q, s}，没有 i、k、h：它们在 B0 里先被定义，入口处不需要旧值。第二，n 在 B0 的 IN 里，因为 n 只在 B1 被读，而 B0 到 B1 的路径上 n 没有被重新定义；活跃性沿控制流反向传播，不要求变量在入口已定义。

对寄存器分配的接口，关键是块边界的活跃集合。分配器为每个变量构造活跃区间：从某个定义点开始，到所有后续使用点结束；跨块的区间用 IN/OUT 拼接。这里有两个方向性后果：

- 活跃变量是 may 分析，过近似是安全的：多算一个活跃变量，最多让分配器多保留一个值（多占寄存器或溢出），不会覆盖活值。少算一个活跃变量是危险的：分配器可能把一个仍要被读的值所占的寄存器分给别人。
- 调用点要特别处理。caller-saved 寄存器在调用后不保留，调用指令处活跃的变量必须放到 callee-saved 寄存器或栈上；这部分在第 7、8 章展开，本节只保证活跃集合在调用边界上是保守的。

实现后向分析时，工作列表的依赖方向与前向相反：一个块的 IN 改变后，要重新入队的是它的前驱，而不是后继。这个方向写反，分析通常仍会收敛（因为初始轮询可能碰巧覆盖），但在大图上会漏掉更新，给出偏小的活跃集合。5.5 节的工作列表代码把 `preds` 和 `succs` 作为参数显式传入，就是为了让方向错误在代码审阅时可见。

SSA 下还有一个细节：$\phi$ 函数的操作数在**前驱边上**使用，不在 $\phi$ 所在块内使用。若把 $\phi$ 的操作数当作块内 use，活跃区间会在合流块入口多出一段，可能让两个本可共享寄存器的区间冲突。第 4 章已经给出 $\phi$ 的语义与消解方法，这里只记结论：活跃性分析要在 CFG 的边上处理 $\phi$ 操作数，或者先消解 $\phi$ 再做后向分析。

把每个变量的活跃区间按块列出来，可以直接看出寄存器压力：

| 变量 | 定值块 | 使用块 | 块级活跃区间 | 备注 |
|:--|:--|:--|:--|:--|
| i | B0, B4 | B1, B4 | B0–B4 | 循环变量，跨回边 |
| k | B0 | B3 | B0–B4（经回边） | 循环不变，但活跃 |
| h | B0 | B3 | B0–B4（经回边） | 同上 |
| n | 参数 | B1 | 入口–B1 | 参数，入口活跃 |
| p, q | 参数 | B2, B5 | 入口–B5 | 参数 |
| s | 参数, B3 | B3 | 入口–B3 | 累加器 |
| t1 | B2 | B3 | B2–B3 | 临时值 |
| t0 | B1 | B1 | B1 | 分支条件 |
| t2 | B2 | B2 | B2 | 分支条件 |
| x, y | B3 | 无 | 空 | 死值，DCE 可删 |
| z | B5 | B5（return） | B5 内 | 块内先定义后使用 |

这张表暴露了两个事实。第一，k 和 h 虽然「循环不变」，它们的活跃区间却跨越整个循环；循环不变代码外提可以把计算移出循环，但不能让它们的值在循环期间消失（除非外提后循环体不再使用）。第二，x 和 y 是死值，活跃区间为空；第 6 章的 DCE 会删掉它们，删掉后 B3 的活跃集合不变，因为它们的定值本来就不贡献 use。

块级活跃集合是「保守的块粒度近似」，块内可能有空洞。例如 B3 里 s 在第一条指令被读、随后被写；在「读之前」s 活跃，在「写之后、下一次读之前」不活跃。块级分析只看块入口和出口，会把整块都算成活跃。第 7 章的分配器需要指令级区间，会在块级结果的基础上做线性扫描或活跃区间拆分；块级 IN/OUT 提供边界，块内细节由分配器补。

| 粒度 | 精度 | 代价 | 用在哪 |
|:--|:--|:--|:--|
| 块级 IN/OUT | 块内无空洞，偏大 | 每块一次 | 数据流分析、跨块边界 |
| 指令级 live | 精确到指令间 | 每条指令一次 | 线性扫描、溢出判定 |
| 区间级 live | 合并相邻指令 | 中等 | 图着色、区间分裂 |
| 带洞区间 | 允许区间内空洞 | 高 | 寄存器合并、coalescing |

后向工作列表的代码与前向对称，只列关键部分：

```python
def live_transfer(use, define, out_set):
    return use | (out_set - define)

# 后向：一个块的 IN 变了，重算它的前驱
for p in preds[b]:
    if p not in in_queue:
        queue.append(p)
```

它验证 $IN = use \cup (OUT \setminus def)$。预期：`use={s,t1}, def={s,x,y}, out={i,n,p,q,s}` 时，`IN={s,t1,i,n,p,q}`；s 在 use 里所以保留，x、y 在 def 里且不在 use 里所以不会出现。

参数和全局变量的活跃性要特别处理。参数在入口处活跃，除非函数体从不读它；全局变量在调用点可能被任何未知函数读写，活跃性分析必须把「调用可能读全局」建模成 use。若把调用当成无操作，全局变量的活跃区间会在调用点断开，分配器可能把它的寄存器复用给别的值，而调用返回后代码继续读全局，读到的是被覆盖的寄存器（如果全局被提升到寄存器）或旧内存（如果没提升）。这类错误在有大量全局状态的程序里很常见。

SSA 下的活跃性与非 SSA 有一点不同：$\phi$ 的每个操作数只在前驱边上活跃，而不是在 $\phi$ 所在块内活跃。若用块级 use/def 直接处理 $\phi$，会把所有操作数都算成块内 use，导致合流块的 IN 偏大。第 4 章已经给出 $\phi$ 消解；如果选择保留 SSA 做分配，活跃性要在边上算，或者用「$\phi$ 操作数对应到前驱的 live-out」这条规则修正。

最后，活跃变量的结果依赖「什么算一次使用」。调试输出、日志、volatile 读都算使用；寄存器分配不能因为一个值只被 `printf` 使用就把它当死值。相反，纯计算但结果未被使用的指令可以被 DCE 删除，这正是第 6 章的内容。分析阶段只负责「哪些变量在哪些点还被需要」，不负责决定「这条指令能否删」；后者需要副作用信息。

最后是边界。出口块的 OUT 为空，表示函数返回后没有变量还被需要；但如果函数有多个返回点，每个返回块都是出口。异常边、`longjmp`、内联汇编的 `clobber` 列表都会让「后继」比显式的跳转边更多。漏掉异常边，异常处理路径上的变量会被误判为死，寄存器分配可能在异常展开前覆盖它们。这类边不在本实验的 CFG 里，真实后端必须显式建模。

## 5.4 可用表达式与常量传播 {#sec-compilers.2.5.4}

可用表达式（available expressions）回答：「在程序点 $p$，表达式 $e$ 是否在所有到达 $p$ 的路径上都已经被计算过，且操作数此后没有被改写？」如果是，$e$ 的重复计算可以删除，直接复用上次的结果。这是 CSE 的判定条件，也是循环不变代码外提的前置分析之一。

它与到达定值的区别在合并方向。到达定值是 may：一条路径到达就算；可用表达式是 must：所有路径都到达才算。must 分析的合并不是并集，而是交集。

::: def 定义 5.4.1 · 可用表达式 {#def-compilers.2.5.4.1}
设 $E$ 是程序中出现的表达式集合。对块 $n$，$gen_n$ 是块内计算且到块尾仍未被杀死的表达式集合，$kill_n$ 是块内被重新定义的操作数所影响的表达式集合。前向方程为

$$
\mathrm{IN}[n] = \bigcap_{p \in pred(n)} \mathrm{OUT}[p], \qquad
\mathrm{OUT}[n] = gen_n \cup (\mathrm{IN}[n] \setminus kill_n)
$$

边界 $\mathrm{IN}[\text{entry}] = \varnothing$；其余块的初值是全集 $E$。解是最大不动点。若某块没有前驱，交集的身份元是全集；若某块不可达，应先删除，不要让它的 $E$ 污染后继。
:::

$gen$ 与 $kill$ 的顺序不能反。对块内每条指令，先把它计算的表达式加入 $gen$，再用它定义的变量去删除所有含该变量的表达式（同时从 $gen$ 和输入中都删）。以 `x = x + y` 为例：先加 `x+y`，再因为定义 x 删除 `x+y`，所以该表达式在块尾不可用。如果先 kill 后 gen，就会错误地声称 `x+y` 在赋值之后可用，CSE 会把后面的 `x+y` 替换成一个刚刚被覆盖的旧值。

实验的表达式全集是 {h+k, i+1, i<n, i==0, k*6, p+q, s+t1}。最终解：

| 块 | IN | OUT |
|:--|:--|:--|
| B0 | ∅ | ∅ |
| B1 | ∅ | {i<n} |
| B2 | {i<n} | {i<n, i==0, p+q} |
| B3 | {i<n, i==0, p+q} | {h+k, i<n, i==0, k*6, p+q} |
| B4 | {i<n, i==0, p+q} | {p+q} |
| B5 | {i<n} | {i<n, p+q} |

::: ex 例 5.4.1 · 为什么 B5 不能复用 t1 {#ex-compilers.2.5.4.1}
B5 的 IN 是 {i<n}，不含 p+q。零次循环的路径 B0 -> B1 -> B5 上，B2 从未执行，p+q 没有被计算；可用表达式要求所有路径都算过，所以 p+q 不可用。B5 自己执行 `z = p + q` 后，OUT 才含 p+q，但那是给 B5 的后继用的，不能倒过来证明 B5 入口可用。若在 B5 用 t1 替换 p+q，n 等于 0 时 t1 是未定义值。
:::

正例也要有一个。B2 的 OUT 含 p+q，B3 的 IN 也含 p+q（B2 是 B3 的唯一前驱）；B3 的 `s = s + t1` 已经用了 t1，但假设 B3 还有一条 `w = p + q`，CSE 可以把它替换成 `w = t1`。条件逐条核对：p+q 在 B3 入口可用；B2 的 t1 支配 B3；p、q 在 B2 到 B3 之间没有被改写；中间没有调用。四条都成立，替换安全。若 B3 之前插入了 `p = 0`，p+q 被 kill，IN 不再含它，CSE 必须放弃。

B4 的 OUT 只剩 {p+q} 也值得看：B4 执行 `i = i + 1`，杀死了所有含 i 的表达式（i<n、i==0、i+1），但 p+q 的操作数 p、q 没变，所以留下。到了 B1，IN 是 B0 的 OUT（∅）与 B4 的 OUT（{p+q}）的交集，仍然是 ∅；循环头的第一次迭代没有计算过 p+q，交集正确地把回边带来的「可用」抹掉了。

常量传播（constant propagation）把这套格换成了「每个变量一个值」。值域是一个平坦格：

```text
        NAC（不是常量）
         │
   ... 1  2  3 ...        ← 具体常量，两两不可比
         │
       UNDEF（还没有定义）
```

合并（在 CFG 合流处）取最小上界：UNDEF 与任何值合并得到那个值（无边路径还没有贡献信息）；两个相同的常量合并得到该常量；两个不同的常量合并得到 NAC；NAC 与任何值合并得到 NAC。这个「UNDEF 是单位元」的规则依赖一个前提：每个使用点都有支配它的定义，或者程序已经转成 SSA。若一条路径可能先用后定义，UNDEF 不能被当作「没有信息」轻轻放过，必须由未初始化检查单独报告。

::: def 定义 5.4.2 · 常量传播 {#def-compilers.2.5.4.2}
对每个变量 $v$，其抽象值 $a(v) \in \{\text{UNDEF}\} \cup \mathbb{Z} \cup \{\text{NAC}\}$。块 $n$ 的传递函数按指令顺序更新：赋值 $v = e$ 时，若 $e$ 的所有操作数都是常量，则 $a(v)$ 为计算结果；若任一操作数是 NAC，则为 NAC；若操作数是 UNDEF，则为 UNDEF。除法在除数为 0 时结果为 NAC，不产生常量。合并为逐变量的最小上界。入口处参数取 NAC，局部变量取 UNDEF。解是最小不动点。
:::

合并表如下。行、列分别是两条前驱路径上的值：

| $\sqcup$ | UNDEF | 常量 $c$ | 常量 $d \neq c$ | NAC |
|:--|:--|:--|:--|:--|
| UNDEF | UNDEF | $c$ | $d$ | NAC |
| 常量 $c$ | $c$ | $c$ | NAC | NAC |
| 常量 $d \neq c$ | $d$ | NAC | $d$ | NAC |
| NAC | NAC | NAC | NAC | NAC |

实验的常量传播结果：B0 的 OUT 是 `i=0 k=7 h=12`；B3 的 IN 是 `k=7 h=12 i=NAC`，因为 i 在循环头由 0 和 1 合并成 NAC；B3 的 OUT 是 `x=42 y=19`。这三行是真实输出，不是手算：

```text
  B0 OUT: i=0 k=7 h=12 x=UNDEF y=UNDEF z=UNDEF
  B3 OUT: i=NAC k=7 h=12 x=42 y=19 z=UNDEF
B3 IN 的 k=7 h=12 i=NAC；B3 OUT 的 x=42 y=19
```

注意 i 的结果。循环第一次迭代 i 是 0，第二次是 1，之后还可能更大；合并成 NAC 是正确的，不能因为「第一次一定是 0」就把 i 折成 0。反过来，k 和 h 在循环里从未被改写，所以 7 和 12 穿过回边仍然是常量。常量传播的精度取决于它能否区分「被改写」和「没被改写」，而不是取决于循环执行多少次。

实现合并的核心只有几行：

```python
def cp_join_value(a, b):
    if a == UNDEF:
        return b
    if b == UNDEF:
        return a
    return a if a == b else NAC
```

这段验证「UNDEF 是单位元、不同常量变 NAC」。预期：`cp_join_value(UNDEF, 7) == 7`，`cp_join_value(3, 4) == NAC`，`cp_join_value(NAC, 7) == NAC`。

常量传播有四个边界，写优化时必须逐条检查：

1. 除零。`x = 100 / 0` 在定义了 trap 的 IR 里是一个可观察的异常；折成 0 会删掉 trap。除数是非常量时也不能折。第 6.4 节会给出反例与修复。
2. 整数溢出与目标位宽。C 的有符号溢出是未定义行为，但 Rust 的 debug 构建会 panic，Wasm 的 i32 会回绕。折叠必须在 IR 的语义域里做，不能借宿主语言的 `int` 溢出规则。
3. 浮点。`x + 0.0` 不能随便折成 `x`（-0.0、NaN、舍入模式），除非开了 fast-math 并接受语义变化。本实验只处理整数。
4. 非 SSA 的自支持常量。循环体里定义的 x 可能沿回边把 42 带回循环头，于是循环头的 x 也显示 42，尽管零次迭代路径上 x 未定义。本实验的 x 在 B3 定义后才使用，所以这个 42 是可靠的；换一个先用后定义的例子就不可靠。第 6 章在 SSA 上做常量传播时，$\phi$ 会把「未定义」显式带进来，这类自支持会自然消失。

把每个块的表达式 gen/kill 列出来，可以核对表中的结果：

| 块 | 计算的表达式 | 被定义的变量 | gen | kill |
|:--|:--|:--|:--|:--|
| B0 | 无 | i, k, h | ∅ | {i<n, i==0, i+1, k*6, h+k} |
| B1 | i<n | t0 | {i<n} | ∅ |
| B2 | p+q, i==0 | t1, t2 | {p+q, i==0} | ∅ |
| B3 | s+t1, k*6, h+k | s, x, y | {k*6, h+k} | {s+t1} |
| B4 | i+1 | i | {i+1} | {i<n, i==0, i+1 的旧值} |
| B5 | p+q | z | {p+q} | ∅ |

B3 的 gen 看起来应该是 {s+t1, k*6, h+k}，但 s+t1 在块内被 s 的定值杀死：`s = s + t1` 先计算 s+t1，随后定义 s，所以块尾不再可用。k*6 和 h+k 的操作数是 k、h，B3 没有定义它们，所以保留。B4 的 kill 含 i+1 自己，但 gen 在 kill 之后重新加入，所以 OUT 里仍有 i+1；这正好验证了「gen 优先于 kill」的规则。

CSE 的正确性条件可以写成一条规则：

> 若表达式 $e$ 在点 $p$ 可用，且从上次计算 $e$ 到 $p$ 之间没有对 $e$ 的操作数赋值、没有可能修改内存的调用、没有异常边绕过上次计算，则 $p$ 处的 $e$ 可以替换为上次的结果。

三个「没有」分别对应可用表达式、kill 规则和副作用屏障。缺任何一个，替换都可能读到旧值或跳过 trap。第 6.2 节的 LICM 会把这条规则从「同块/同路径」推广到「循环外」，条件更强。

常量传播的迭代可以写成工作列表形式。与到达定值不同，状态是每个变量一个值，合并是逐变量的上确界：

```python
def cp_step(block, in_state):
    state = dict(in_state)
    for insn in block.insns:
        dst, rhs = split_assign(insn)
        state[dst] = eval_rhs(rhs, state)   # 除零 -> NAC，未知 -> NAC
    return state

def cp_join(a, b):
    return {v: lub(a[v], b[v]) for v in a}  # UNDEF<常量<NAC
```

它验证「块内顺序更新、块间逐变量合并」。预期：入口 `k=7`，B1 的 IN 从 B0 和 B4 合并，B4 不定义 k，所以 B1 的 k 仍是 7；B3 的 `x = k * 6` 折成 42。若把合并写成「取第一个前驱」，B1 可能拿到 B4 的 UNDEF，k 就丢了；这是初始化/合并顺序的常见错误。

块内常量传播的代码也只有几行，关键是每个赋值都覆盖目标变量，读未知变量给 UNDEF：

```python
def cp_transfer(block, state):
    st = dict(state)
    for insn in block["insns"]:
        m = ASSIGN.match(insn)
        if not m:
            continue
        dst, rhs = m.group(1), m.group(2)
        st[dst] = eval_rhs(rhs, st)   # 常量 -> 常量；未知 -> UNDEF；NAC -> NAC
    return st
```

它验证「块内按顺序更新」。预期：B0 之后 `i=0, k=7, h=12`；B3 的传递把 `k*6` 算成 42。若 `eval_rhs` 对 UNDEF 操作数返回常量 0，先用后定义的路径会被折成 0，这是 5.8 提到的另一类错误。

SSA 上的常量传播（SCCP）比这里的非 SSA 版本更精确。SCCP 同时传播「可达性」和「常量性」：如果某个分支条件被证明为常量，不可达的分支不会被并入合流点的 $\phi$，于是 $\phi$ 不会因为一条不可行路径变成 NAC。第 6.4 节会把 SCCP 与折叠、DCE 放在一起讲；本节只需记住：非 SSA 的数据流常量传播会把不可行路径也算进去，精度较低但仍然是 sound 的。

浮点常量传播要额外小心。整数加法满足结合律，浮点不满足；`x + 0.0` 在 x 为 -0.0 时结果可能是 +0.0，不能直接折成 x。NaN 的传播、舍入模式、x87 的扩展精度都会让「编译期算出的值」与「运行时算出的值」不同。除非语言标准或编译选项明确允许（例如 C 的 `-ffast-math`），浮点表达式不要做跨语句的常量折叠；本实验只处理整数，正是为了避开这层复杂性。

可用表达式与常量传播经常一起用：前者判断「这个表达式算过没有」，后者判断「这个表达式的操作数是不是常量」。两者都不能单独证明优化安全，必须再加上「替换后的值在所有路径上与原计算相同」这一条。6.2 节的循环不变代码外提就是这条组合规则的直接应用。

## 5.5 工作列表算法与复杂度 {#sec-compilers.2.5.5}

朴素迭代的伪代码只有四行：

```text
repeat
    changed = false
    for each block n in a fixed order:
        new_in  = merge(OUT[p] for p in preds(n))   // 后向分析换成 succs
        new_out = f_n(new_in)
        if new_in != IN[n] or new_out != OUT[n]:
            IN[n], OUT[n] = new_in, new_out
            changed = true
until not changed
```

它每轮都重算所有块，哪怕只有一个块的事实变了。工作列表（worklist）只把「输入可能变了」的块放进队列：一个块的 OUT 改变后，只有它的后继（前向）或前驱（后向）需要重算。队列里重复的块要去重，否则一个块可能在一次变化后被多次压入。

实验里两种算法的真实计数：

| 分析 | 朴素轮数 | 朴素块求值 | 工作列表 pop | 工作列表更新 |
|:--|--:|--:|--:|--:|
| 到达定值 | 3 | 18 | 12 | 11 |
| 活跃变量 | 3 | 18 | 16 | 12 |
| 可用表达式 | 2 | 12 | 7 | 6 |
| 常量传播 | 4 | 24 | 16 | 14 |

这张表最容易被误读成「工作列表总是更快」。在这张只有 6 个块的小图上，两者差距不大；活跃变量的工作列表甚至 pop 了 16 次，接近朴素的 18 次。原因是工作列表的计数单位是「块被处理一次」，而朴素迭代的计数单位是「块被求值一次」，量纲相同，但工作列表会因为一个块在队列里被重新唤醒而重复处理。它的优势在块数和事实数都大时才显现：朴素迭代每一轮都要碰所有块，工作列表只碰受影响的块。

看到达定值的实际步序（`*` 表示这次 pop 改变了 OUT）：

```text
B0* B1* B2* B5* B3* B4* B1* B2* B5* B3* B4* B1
```

第一轮从 B0 开始，沿 B1、B2、B5 走了一条路径，再处理 B3、B4；B4 的 OUT 改变了，于是 B1 被重新入队。第二轮 B1 的 IN 多了 d10，B1 的 OUT 变了，继续唤醒 B2；B2 的 OUT 又变了，但 B5 的 IN 没有变（B5 只依赖 B1），所以 B5 仍然被 pop 一次、发现没变，又唤醒它的后继（没有）。第三轮 B1 被 pop 时已经没有变化，队列清空。12 次 pop 里有 11 次真更新，1 次空转。

工作列表的核心代码如下。注意 `in_queue` 去重和「只把后继入队」这两点：

```python
def solve_forward_worklist(blocks, entry, transfer, init_out, boundary, join, identity):
    inn = {b: init_out() for b in blocks}
    out = {b: init_out() for b in blocks}
    q = deque([entry])
    inq = {entry}
    pops = 0
    updates = 0
    while q:
        b = q.popleft()
        inq.discard(b)
        pops += 1
        new_in = boundary() if b == entry else reduce_join(join, identity, blocks[b]["preds"], out)
        new_out = transfer(b, new_in)
        if new_in != inn[b] or new_out != out[b]:
            updates += 1
            inn[b], out[b] = new_in, new_out
            for s in blocks[b]["succ"]:
                if s not in inq:
                    q.append(s)
                    inq.add(s)
    return inn, out, pops, updates
```

实验里的前向求解器骨架如下（省略计数与 trace），边界与初值是两个独立参数：

```python
def solve_forward(blocks, order, entry, transfer, init_out, boundary, join, identity):
    inn = {b: init_out() for b in blocks}
    out = {b: init_out() for b in blocks}
    while True:
        changed = False
        for b in order:
            if b == entry:
                new_in = boundary()          # 边界，只有入口特殊
            else:
                new_in = identity()
                for p in blocks[b]["preds"]:
                    new_in = join(new_in, out[p])
            new_out = transfer(b, new_in)    # 块内传递
            if new_in != inn[b] or new_out != out[b]:
                changed = True
            inn[b], out[b] = new_in, new_out
        if not changed:
            return inn, out
```

它验证「入口用边界、其余块用合并、每轮重算到不变」。预期：到达定值 3 轮收敛，可用表达式 2 轮收敛。把 `boundary` 改成 `init_out`，可用表达式的入口就会变成全集；这个单行改动是 5.8 反例的来源。

后向版本只改三处：种子是出口块集合，合并读后继的 IN，更新后把前驱入队。写错任何一处，分析可能仍然收敛，但会漏掉某些块。判断方向是否正确，可以看一个只有两个块的图：前向分析中，B0 的 OUT 改变必须让 B1 重算；后向分析中，B1 的 IN 改变必须让 B0 重算。把这条断言写进单元测试，比读代码可靠。

复杂度要分两层看。设块数 $N$、边数 $E$、格的高度 $h$（最长严格链长度）。朴素迭代最多 $N \cdot h + 1$ 轮，每轮 $N$ 次块求值，合计 $O(N^2 h)$ 次块求值；每次求值还要做一次合并，位向量合并的代价是 $O(F/w)$（$F$ 是事实数，$w$ 是机器字长）。工作列表在最坏情况下每个块的值改变 $h$ 次，每次改变最多唤醒所有后继，合计 $O((N + E)h)$ 次块求值。对稀疏图 $E = O(N)$，两者差一个 $N$；对稠密图差距缩小到常数。空间上工作列表多一个队列和去重位图，$O(N)$。

实际编译器还会调整处理顺序。前向分析按逆后序（reverse postorder，RPO）处理，能让循环头在回边之前先拿到入口的值，通常减少迭代次数；后向分析按后序。这个优化不改变最终不动点，只改变 pop 次数。实验为了展示「每轮 IN/OUT」，朴素迭代固定按 B0 到 B5 的顺序；工作列表的种子只有入口，因此第一次 pop 的顺序取决于后继列表的顺序。顺序不同，计数会不同，但结果必须相同。

三个实现边界：

1. 初始值。工作列表只把入口入队，意味着不可达块永远不会被处理。对只关心可达代码的优化，这是正确的；但如果你要用分析结果删除不可达块，必须先单独做可达性分析，不能指望数据流分析顺带覆盖它们。
2. must 分析的初值。可用表达式把其余块的 OUT 初始化为全集，工作列表第一次处理某个块时，它的 IN 可能还是「所有前驱都是全集」的状态；随着前驱被处理，IN 下降。因为下降是单调的，队列最终会清空。若把初始值写成空集，分析会从「什么都不不可用」开始向上加，得到最小不动点（通常是空集），这不是可用表达式要的最大不动点。
3. 收敛判定。比较整个 IN/OUT 字典/位向量，而不是只比较「大小」或「是否包含某个事实」。两个不同的集合可以大小相同；只比较大小会让分析提前停止。

把 12 次 pop 展开成表，可以看到队列的实际行为：

| pop | 块 | OUT 是否改变 | 这次 pop 后入队 |
|--:|:--|:--|:--|
| 1 | B0 | 是 | B1 |
| 2 | B1 | 是 | B2, B5 |
| 3 | B2 | 是 | B3, B4 |
| 4 | B5 | 是 | 无 |
| 5 | B3 | 是 | B4（已在队列） |
| 6 | B4 | 是 | B1 |
| 7 | B1 | 是 | B2, B5 |
| 8 | B2 | 是 | B3, B4 |
| 9 | B5 | 是 | 无 |
| 10 | B3 | 是 | B4 |
| 11 | B4 | 是 | B1 |
| 12 | B1 | 否 | 无（队列空） |

第 4 次 pop B5 时它确实变了：第一轮 B1 的 OUT 只含 d1..d4，B5 的 IN 从空变成这些，OUT 加了 d11。第二轮 B5 的 IN 又多了 d10，所以第 9 次 pop 也变了。第 12 次 B1 已经稳定，队列清空。这张表说明工作列表的「pop 次数」不是「块数」的倍数，而是「值改变的次数 + 最后一次确认」；在格高度大的分析里，这个数字可能远大于块数。

处理顺序对 pop 次数有直接影响。若按逆后序（RPO）处理，循环头 B1 会先拿到 B0 的入口值，再处理循环体；B4 的回边值到达时，B1 只需要再更新一次。实验的顺序是 B0、B1、B2、B5、B3、B4（B1 的后继列表中 B2 在 B5 前），所以 B5 被提前处理了两次。把后继顺序改成 B5 在前，步序会变，但最终 IN/OUT 不变。编译器可以根据 profile 调整顺序，但不能依赖顺序保证正确性。

复杂度可以用一组具体数字感受。设 $N = 10^4$ 个块、$E = 3 \times 10^4$ 条边、$D = 10^5$ 个定值、$h \approx 200$（循环嵌套导致的链长）。朴素迭代最坏 $N \cdot h = 2 \times 10^6$ 次块求值，每次合并 10 万位的位向量（约 1.6 KB），总内存流量约 3 GB。工作列表最坏 $(N+E)h \approx 8 \times 10^6$ 次——比朴素还多，因为它把「每次边触发」都算进去了。实际程序远低于最坏界：大多数块的值只改变一两次，工作列表的 pop 数接近 $N + E$，而不是 $(N+E)h$。理论界和实测的差距，正是编译器优化里「复杂度分析只能排除最坏情况，不能预测常数」的例子。

队列的实现也有讲究。用一个 `deque` 加一个 `in_queue` 位图，入队/出队 $O(1)$；用优先队列按 RPO 排序，能减少 pop 但增加 $\log N$ 的开销；用两个栈模拟工作列表，可以避免动态内存分配。对位向量分析，合并本身的成本往往超过队列操作，所以先优化位向量宽度（把事实按块分组、只分配可达事实）比优化队列更划算。

::: note 无限格与 widening
本章的格都有限，所以迭代一定停。第 9 章的抽象解释会用到无限格（区间、多面体），这时需要 widening（外推）来强制有限步收敛，再用 narrowing 恢复精度。widening 的结果仍然是 sound 的，但可能比不动点更粗糙；它不是「近似算法」，而是「在无限格上保证终止的算子」。数据流分析是它的有限格特例。
:::

::: note 混沌迭代
工作列表算法属于混沌迭代（chaotic iteration）：只要每轮取一个「还没稳定」的块，并按单调函数更新，最终都会到达同一个不动点。处理顺序只影响速度，不影响结果（在格有限、函数单调的前提下）。这条性质让编译器可以按任意顺序调度分析，也允许把多个分析交错执行；代价是调试时看到的中间状态依赖顺序，不能把某一次 pop 的 IN 当成最终答案。
:::

## 5.6 正确性：保守性、路径敏感与边界 {#sec-compilers.2.5.6}

数据流分析给出的不是程序事实，而是程序事实的近似。把「近似」说清楚，需要先定义它相对什么近似。

对一条具体执行路径 $\pi$，可以沿着路径逐块应用传递函数，得到路径末端的真实事实集合。把所有从入口到块 $n$ 的路径的结果合并起来，就是 meet-over-all-paths（MOP）解：

$$
\mathrm{MOP}[n] = \bigsqcup_{\pi \in Paths(\text{entry}, n)} f_\pi(\text{boundary})
$$

若把方程迭代到不动点得到的解记作 MFP（maximum/minimum fixed point），则在集合包含序下有 $\mathrm{MFP} \sqsupseteq \mathrm{MOP}$（may）或 $\mathrm{MFP} \sqsubseteq \mathrm{MOP}$（must）。也就是说，不动点解可能比「逐路径精确合并」更不精确（may 多算、must 少算），但不会越过安全边界。

::: thm 定理 5.6.1 · 不动点解的可靠性 {#thm-compilers.2.5.6.1}
设框架单调、边界条件与程序语义一致、迭代初值是乐观的（may 取 $\bot$，must 取 $\top$），则对每个块 $n$，MFP 包含（may）或被包含于（must）MOP。若每个 $f_n$ 对合并运算可分配，即 $f_n(\bigsqcup_i x_i) = \bigsqcup_i f_n(x_i)$，则 MFP $=$ MOP。
:::

::: proof 证明思路
May 分析从 $\bot$ 向上迭代，每一步都是对「所有可达路径」的过近似：合并把所有前驱的路径并起来，单调传递函数不会漏掉任何一条路径的转移。因此 MFP 不会漏掉具体事实，它是方程的最小解；额外的事实只可能来自把不可行路径组合在一起。可分配时，块内计算与路径合并可以交换，MOP 本身是方程的不动点，最小解等于 MOP；不可分配时，MFP 可能比 MOP 更粗（在集合序下更大）。Must 分析把「过近似」换成「欠近似」，方向对偶。
:::

可分配性不是自动成立的。到达定值、活跃变量、可用表达式的传递函数都是 gen/kill 形式，对并集/交集可分配；常量传播不是：两条路径分别到达 `(x=1, y=2)` 和 `(x=2, y=1)`，在合流点逐变量合并得到 `x=NAC, y=NAC`，再算 `x+y` 得到 NAC；若先分别计算，两条路径的 `x+y` 都是 3，合并得 3。MOP 是 3，MFP 是 NAC。这解释了为什么常量传播的 MFP 可能严格弱于 MOP，也解释了为什么基于 SSA 的稀疏常量传播（sparse conditional constant propagation，SCCP）能在某些程序上得到更精确的结果。

保守性（conservatism）是另一个维度。may 分析过近似，must 分析欠近似；两者都可能让优化「少做」，但不应让优化「做错」。把这两个方向混在一起，是很多误优化的根源：

| 分析 | 方向 | 过近似意味着 | 欠近似意味着 | 优化端的用法 |
|:--|:--|:--|:--|:--|
| 到达定值 | may | 多算几条可能到达的定值 | 漏掉可能到达的定值 | 欠近似会误删仍可能被使用的赋值 |
| 活跃变量 | may | 多算几个活跃变量 | 漏掉活跃变量 | 欠近似会让分配器覆盖活值 |
| 可用表达式 | must | 少算几个可用表达式 | 多算不可用的表达式 | 过近似（多算）会让 CSE 复用错值 |
| 常量传播 | may（单值） | 少判几个常量 | 多判常量 | 多判会把变量折成错误常量 |

表格最后一列是使用方式，不是分析本身的属性。同一个分析结果，优化端如果把它当成「一定」而不是「可能」，就会把保守性用反。例如到达定值说「d5 可能到达这里」，CSE 不能因为它「可能」就断定 t1 等于 p+q；必须额外证明所有到达的定值都给出同一个值。

路径敏感（path sensitivity）是数据流分析放弃的第一样东西。看这个例子：

```text
if (x != 0) goto L1 else L2
L1: y = 100 / x; goto L3
L2: y = 0; goto L3
L3: return y
```

在 L1 里，路径条件 $x \neq 0$ 保证了除法安全。路径不敏感的数据流分析在 L1 的入口只知道「x 可能是任意值」，不会把分支条件带进事实集合，因此无法证明除数非零。要证明它，需要路径敏感的分析（按条件分裂状态）或区间/关系域（记录 $x \neq 0$）。这就是为什么真实的编译器在除法优化上非常保守：没有关系域，就不能把「分支已经检查过」当成事实。

::: ex 例 5.6.1 · 相关条件让 must 分析失效 {#ex-compilers.2.5.6.1}
考虑 `if (a > 0) { if (b > 0) { ... } }`。路径不敏感的分析在第二个分支只知道 a、b 各自「可能大于 0」，不知道它们同时大于 0；若优化需要 `a + b > 0`，这个结论不能从两个独立的事实推出来。更糟的是，若程序里还有 `a = -b`，相关性会让「a 大于 0」和「b 大于 0」互斥，路径不敏感分析仍会把两个分支都当作可行。结论：数据流事实是逐变量的，不含变量之间的关系；需要关系推理时，换域（第 11 章的符号执行/不变式）而不是硬改数据流。
:::

把「证明义务」按优化列出来，可以看清分析与变换的分工：

| 优化 | 依赖的分析 | 变换前必须证明 | 证明失败时的表现 |
|:--|:--|:--|:--|
| 常量折叠 | 常量传播 | 操作数都是常量，且运算在 IR 语义下不 trap | 除零被折掉、溢出行为改变 |
| 公共子表达式删除 | 可用表达式 + 副作用 | 表达式在所有路径可用，操作数未变，中间无屏障 | 复用旧值 |
| 死代码删除 | 活跃变量 + 副作用 | 结果无使用者，指令无副作用/不 trap | 删除 volatile 读或除零 |
| 循环不变代码外提 | 支配关系 + 别名 + 常量传播 | 操作数不变，外提不引入新 trap，不跨别名写 | 零次循环触发除零、读到旧数组值 |
| 内联 | 调用图 + 成本模型 | 参数求值顺序、异常、可见性、递归边界 | 参数求值两次、异常语义改变 |

这张表把「分析是 sound 的」翻译成了「变换的前提被证明」。sound 的分析只保证事实不被漏掉；变换仍然要检查额外条件（无副作用、不 trap、别名）。很多误优化的复盘最后都落在「分析对了，但变换少了一个前提」，而不是「分析算错了」。

用误报/漏报的术语对照：may 分析的过近似会产生误报（false positive），欠近似会产生漏报（false negative）；must 分析反过来。优化端对误报的容忍度高（少优化），对漏报的容忍度低（可能误优化）。所以 must 分析宁可少报「可用」，也不要多报；may 分析宁可多报「可能到达」，也不要少报。这个不对称性是 5.6 整节的结论。

保守性还有几个必须显式建模的边界：

- 函数调用。未知调用可能读写任意全局内存、修改指针指向的对象、抛出异常、不返回。若分析把调用当成「无操作」，到达定值和可用表达式都会给出过于乐观的结果。安全做法是让调用杀死所有可能受影响的事实，除非有 `pure`/`const`/`readnone` 之类的属性或过程间分析证明。
- 别名。两个指针可能指向同一对象时，对 `*p` 的写入可能改变 `*q` 的定值/可用表达式。没有别名信息，只能按「可能别名」处理，杀死所有可能被写的对象的事实。
- 并发。另一个线程可以在两条指令之间修改共享变量；没有原子/锁的语义，数据流事实在并发程序上不成立。第 9 章的 TSan 与内存模型会展开。
- 异常与控制流。`throw`、`longjmp`、信号处理会从任意点跳出当前 CFG；分析必须把这些边加进后继集合，否则异常路径上的活跃变量和可用表达式都是错的。
- 不可行路径。MOP 本身也把不可行路径算进去（例如 `x != 0` 与 `x == 0` 同时成立的分支组合）。路径可行性一般不可判定，所以「比 MOP 更精确」需要额外的可行性推理，不能靠数据流单独完成。

可分配性失效的例子值得手算一遍。设两条路径分别到达合流点：

```text
路径 A：x = 1; y = 2; goto J
路径 B：x = 2; y = 1; goto J
J: z = x + y
```

在 J 的入口，逐变量合并得到 x=NAC、y=NAC（两条路径的值都不同）。再用传递函数算 `z = x + y`，得到 NAC。若先分别算两条路径，A 给 z=3，B 也给 z=3，再合并得到 3。MOP 是 3，MFP 是 NAC；两者不等，因为合流丢失了「x 和 y 来自同一条路径」这一相关性。常量传播因此不是可分配的，MFP 可能严格弱于 MOP。

这个例子也解释了为什么「路径敏感」不是万能药。要得到 3，分析必须保留 x 与 y 的关系（$x + y = 3$），而不只是两个独立的常量。关系域（如 octagon、polyhedra）可以表达这类约束，但代价高、实现复杂；大多数编译器选择接受 MFP 的精度损失，只在热点路径上做额外推理。

把「分析依赖哪些假设」列成表，评审时逐项对照：

| 假设 | 如果没建模 | 后果 | 补偿手段 |
|:--|:--|:--|:--|
| 调用不读写内存 | 调用后旧常量/可用表达式仍被信任 | 误优化 | pure/const 属性、函数摘要、LTO |
| 指针不别名 | 对 *p 的写不影响 *q | 常量传播传旧值 | 别名分析、保守 kill |
| 无异常边 | 异常路径上的值被当成死的 | 展开时覆盖活值 | 异常 CFG、landing pad |
| 无并发 | 共享变量被当成寄存器 | 数据竞争下错误 | 原子/锁语义、禁止提升共享 |
| volatile 可删 | 设备读写被删除/合并 | 硬件行为改变 | 把 volatile 当副作用屏障 |
| 无 UB | 溢出/越界后的行为被推理 | 优化暴露 UB | 只在定义行为内优化 |

最后一行常被误解。编译器可以把「有 UB 的程序」优化成任意行为，这是 C/C++ 标准允许的；但编译器不能把「没有 UB 的程序」优化成有 UB 的行为。数据流分析如果假设了某个指针非空、某个除法非零，却没有证明，就会把后者变成前者。第 9 章会把这条边界展开；这里只需记住：优化规则的前提必须是「对所有定义行为都成立」，而不是「对测试输入成立」。

正确性条件的写法应该落在优化规则上，而不是停在「分析是保守的」。以 CSE 为例，规则是：若表达式 $e$ 在点 $p$ 可用，且从上次计算 $e$ 到 $p$ 之间没有对 $e$ 的操作数赋值、没有可能修改内存的调用，则可以把 $p$ 处的 $e$ 替换为上次的结果。三个条件缺一不可，分别对应可用表达式、kill 规则和副作用屏障。第 6 章会把每条优化都写成这样的「前提 → 变换 → 保持的性质」。

写正确性条件时，按四个问题检查，能避免大多数「分析对了、变换错了」的情况：

1. 事实是 may 还是 must？优化需要的是「可能」还是「一定」？
2. 优化规则的前提是否覆盖了所有定义行为（不是所有测试输入）？
3. 变换是否引入了新的 trap、异常或可观察副作用？
4. 失败时有没有一条可复现路径或一个可比较的解释器结果？

这四个问题分别对应方向、语义边界、副作用和证据。答不上来，说明规则还没写完整。

本节结束时，你应该能回答两个问题：这个分析是 may 还是 must，它的解相对 MOP 在哪一侧；这个优化用到的是「可能」还是「一定」。如果两个问题的答案不一致，优化就是错的。

## 5.7 验证数据流结果：交叉检查与反例 {#sec-compilers.2.5.7}

分析写完后，怎么知道它算得对？「跑一遍没崩」不算验证。数据流结果有四类可以独立检查的性质，每一类能抓住不同的错误：

1. 方程自检：把最终的 IN/OUT 代回每块的合并与传递函数，检查等式成立。
2. 边界自检：入口/出口的值必须等于语义规定的边界，而不是迭代初值。
3. 独立实现：用朴素迭代和工作列表各算一遍，比较结果；两种实现的错误通常不相关。
4. 路径反例：对可达的块枚举有界路径，检查不动点是否被某条路径推翻；或者构造一条具体输入，让错误结果产生可观察差异。

实验的前三项都打印了真实结果：

```text
=== 固定点自检（正确解） ===
到达定值=True 活跃变量=True 可用表达式=True 常量传播=True

=== 反例 A：可用表达式把入口边界写成全集 U ===
错误解的 IN[B5]={i<n,p+q}，正确解={i<n}
方程自检（含它自己的边界 U）：True；与 MOP 一致：False

=== 反例 B：到达定值把 OUT 初始化成全集 ALL ===
错误解：轮数=2 块求值=12；IN[B5]={d1,d10,d11,d2,d3,d4,d5,d6,d7,d8,d9}（11 条定值）
正确解：轮数=3 块求值=18；IN[B5]={d1,d10,d2,d3,d4,d5,d6,d7,d8,d9}（10 条定值）
错误解是方程的不动点：True；但它是最大不动点，不是最小不动点
```

反例 A 暴露了第 1 项检查的局限：错误解满足它自己的方程，甚至满足「入口 IN 等于它自己设定的边界 U」，所以方程自检通过。只有第 2 项（边界应为 ∅）或第 4 项（路径 B0 -> B1 -> B5 上 p+q 不可用）能发现它。反例 B 更微妙：错误解也是方程的不动点，只是它是最大不动点，而到达定值要最小不动点。方程自检同样通过，只有「与正确初值下的最小解比较」或「用具体输入走一遍」能发现。

::: ex 例 5.7.1 · 一个自洽但不可用的传递函数 {#ex-compilers.2.5.7.1}
把可用表达式的块内规则写成「先 kill 后 gen」。对 `x = x + y`，先删除含 x 的表达式，再把 `x+y` 加进 gen。分析会稳定地声称 `x+y` 在赋值之后可用，因为每次重算都得到同样的错误结果，方程自检完全通过。但只要构造一条路径：B0 计算 `a = x + y`，B1 执行 `x = 1`，B2 再算 `b = x + y`，B2 就会复用 B0 的旧值，而 x 已经变了。这个错误不能靠「再跑一遍分析」发现，只能靠路径反例或差分执行。
:::

路径反例的构造方法：从入口到目标块做深度优先搜索，限制路径不重复块、长度不超过某个上界。对每条路径，从边界开始逐块应用传递函数，得到该路径末端的集合；所有路径结果的合并就是有界 MOP。实验里 B5 只有一条简单路径 B0 -> B1 -> B5，状态是 {i<n}，不含 p+q，直接推翻了错误解。对带环的图，简单路径会漏掉「绕两圈才成立」的事实，所以有界 MOP 只能用来**否证**，不能用来证明。要证明，需要归纳不变式或定理证明。

第四项检查是差分执行。数据流结果最终要驱动一个变换；把变换前后的程序各跑一遍，比较可观察行为，是最接近用户的验证。第 6 章的实验会对常量折叠、DCE、LICM 做这件事；本章可以先做一个最小版本：如果可用表达式声称 p+q 在 B5 可用，就把 B5 的 `z = p + q` 改成 `z = t1`，然后让 n=0 执行，观察 t1 的值。真实编译器里 t1 可能是任意栈上垃圾，测试可能「碰巧通过」；把 t1 初始化为一个哨兵值（例如 0xdead），能让错误稳定复现。

::: method 方法 5.7.1 · 验证一个数据流实现的顺序
1. 给每种分析写一个 3 到 6 个块的手算用例，先确认方程和边界，再看代码。
2. 打印每一轮 IN/OUT，检查第一次迭代是否从正确的边界/初值开始。
3. 用朴素迭代与工作列表对拍；两者结果必须逐块相等。
4. 单独断言边界：可用表达式入口 IN=∅，到达定值入口 IN=∅，活跃变量出口 OUT=∅，常量传播入口参数=NAC。
5. 对至少一个目标块枚举有界路径，检查不动点不被任何路径推翻；保留一条见证路径。
6. 把分析接到一个真实变换上，做「优化前/后解释器对拍」，并至少包含一个零次循环、一个别名、一个除零边界。
:::

| 检查 | 能发现 | 发现不了 |
|:--|:--|:--|
| 方程自检 | 迭代没收敛、合并写错、传递函数与更新不一致 | 边界写错、传递函数本身语义错 |
| 边界断言 | 入口/出口初值混淆 | 块内规则错 |
| 朴素 vs 工作列表 | 队列方向、去重、漏更新 | 两者共享的规则错误 |
| 有界 MOP/见证路径 | 过近似（must）或欠近似（may）的具体反例 | 需要多圈循环才出现的事实 |
| 差分执行 | 变换的真实语义错误 | 未被测试输入覆盖的路径 |

把验证流程放进一次具体的调试会话，更容易记住顺序。假设 CSE 在 n=0 时输出错误，手头只有实验结果：

1. 先跑实验，确认正确解的 `IN[B5]={i<n}`，错误解的 `IN[B5]={i<n,p+q}`。这一步把「感觉不对」变成「差一个 p+q」。
2. 打印入口的 IN。错误解是全集，正确解是 ∅。这一步定位到边界，而不是传递函数。
3. 跑方程自检。错误解通过，说明不能靠它；跑边界断言，失败。
4. 枚举 B5 的路径。只有 B0 -> B1 -> B5 一条简单路径，状态 {i<n}，确认 p+q 不在其中。
5. 用 n=0 做差分执行，把 t1 预填成 0xdead；错误版本输出 0xdead+...，正确版本输出 p+q。
6. 修复后重跑 1 到 5，并加一条回归测试。

这六步的顺序是有意的：先缩小差异，再定位边界，再用独立证据确认，最后用执行验证。反过来先改代码，容易把错误「修」成另一种错误。

验证命令本身也要写进正文，方便复现：

```text
$ bash experiments/ch05/run.sh | tail -2
到达定值=True 活跃变量=True 可用表达式=True 常量传播=True
结论：OK（一致、自检通过、两个反例均按预期偏离）
```

差分执行的骨架可以写得很小：

```python
def check_transform(program, inputs, transform):
    before = run(program, inputs)          # 解释器
    after = run(transform(program), inputs)
    if before != after:
        print("MISMATCH", inputs, before, after)
        return False
    return True
```

它验证「优化前后可观察行为一致」。预期：所有正常输入都打印 True；构造的边界输入（n=0、除数为 0、别名写入）如果打印 MISMATCH，就说明变换有 bug。注意比较的是「可观察行为」（返回值、输出、trap），不是整个内存状态；未被观察的差异可能只是优化掉了死值，不应该判失败。

| 错误 | 方程自检 | 边界断言 | MOP/路径 | 差分执行 |
|:--|:--|:--|:--|:--|
| 入口边界写成全集 | 通过 | 失败 | 失败 | n=0 失败 |
| must 分析用并集 | 通过 | 通过 | 可能失败 | 视优化而定 |
| 块内 use 算错 | 通过 | 通过 | 可能通过 | 通常不失败（只影响分配） |
| gen/kill 顺序反 | 通过 | 通过 | 失败 | CSE 场景失败 |
| 工作列表方向错 | 可能失败 | 通过 | 可能失败 | 大图才失败 |

这张表的用处是分工：不要指望一种检查抓住所有错误。工程上把四类检查都接进 CI，成本不高（实验脚本已经覆盖前两类和 MOP），收益是把「偶发」变成「可复现」。

分析结果要能被别人复核，最好落成可比较的文本。一个最小的见证格式包含：目标块、目标事实、路径、每步的传递结果。实验里 B5 的见证可以写成：

```json
{
  "analysis": "available-expressions",
  "block": "B5",
  "fact": "p+q",
  "available": false,
  "path": ["B0", "B1", "B5"],
  "state_at_end": ["i<n"],
  "reason": "path skips B2, the only block that computes p+q"
}
```

它验证「结论 + 证据」一起保存。只存结论，复现时要重新跑分析；只存路径，读的人不知道路径末端对应哪个事实。把见证放进测试用例，回归时可以直接比较，不需要重新推导。

分析结果本身也应该可序列化：每个块的 IN/OUT 按稳定顺序输出，事实 ID 用语义名（d1 这种编号要附带指令文本），不要依赖哈希顺序。否则同一份程序在不同机器上输出不同，diff 无法用。实验里的 `fmt_set` 对集合排序，正是为了让输出稳定；真实编译器的分析 dump 也应如此。

差分测试也有盲区。若优化前后的程序都读未初始化内存，两次运行可能碰巧给出相同结果；若程序有 UB，编译器的任何变换都「合法」，差分比较没有意义；若输入没覆盖到错误路径，测试通过不代表正确。第 10 章会把差分测试、属性测试和 fuzzing 组合起来，用生成器覆盖边界；本节只要求至少有一个零次循环和一个别名/除零输入。

验证的价值在于「独立」。用同一个函数既算分析又做检查，错误会一起通过；用工作列表检查工作列表没有意义。实验里朴素迭代与工作列表共享 gen/kill 和传递函数，所以它们只能互相检查调度，不能检查规则；规则由手算用例和 MOP 检查。三层证据各自独立，才有意义。

## 5.8 agent 错误：未初始化 IN 集导致的漏报 {#sec-compilers.2.5.8}

这一节复盘一个具体的 agent 失败。任务描述是「给一个小 IR 加公共子表达式删除」。agent 写了通用的数据流求解器，支持前向/后向、may/must 参数化，然后在可用表达式上调用它。代码结构大致如下：

```python
def solve(analysis):
    state = {b: analysis.top() for b in blocks}   # 所有块从全集开始
    for b in blocks:
        state[b] = analysis.boundary()            # 入口也设成全集？
    changed = True
    while changed:
        changed = False
        for b in blocks:
            new_in = analysis.join(state[p] for p in preds[b])
            new_out = analysis.transfer(b, new_in)
            ...
```

问题出在第二行。agent 把「迭代初值」和「程序边界」当成了同一个东西：可用表达式的其余块确实从全集 $U$ 开始迭代，但入口块的 IN 必须是空集。它给入口也设了 `analysis.top()`，于是分析在入口就声称「所有表达式都可用」。

症状不是崩溃，而是生成错误代码。CSE 在 B5 看到 p+q 可用，把 `z = p + q` 换成 `z = t1`。测试用的输入 n 都大于 0，循环至少执行一次，t1 恰好是上一轮算出的 p+q，输出完全正确。上线后遇到 n=0 的输入，t1 是未初始化的栈槽，输出随环境变化；如果开了优化，甚至可能因为读未初始化值触发 UB，表现为「同一份源码在不同机器上结果不同」。

根因有两层。表层是初始化写错：must 分析的入口边界是 $\varnothing$，不是 $\top$。深层是把「分析方向」和「迭代起点」混为一谈：may 分析从 $\bot$ 开始向上迭代，must 分析从 $\top$ 开始向下迭代，但两者的**边界**都由程序语义决定，不能从迭代起点推导。入口没有执行过任何语句，所以可用表达式为空；出口之后没有变量会被读，所以活跃变量为空。这些是语义事实，不是算法偏好。

用本章的工具怎么发现它：

1. 看迭代次数。另跑一个「入口边界=全集」的变体，错误版本 3 轮才停，正确版本 2 轮；错误版本反而多跑一轮，所以「轮数少」既不是正确性证据，也不能用来判断方向。
2. 跑方程自检。错误版本通过，因为它满足自己设定的边界。
3. 打印边界。`IN[B0]` 是全集而不是 ∅，一眼可见；这个断言应该写进求解器的前置条件。
4. 枚举路径。B0 -> B1 -> B5 这条路径上没有任何 p+q 的计算，直接给出反例。
5. 差分执行。n=0 时比较优化前后的输出；这是最接近用户症状的检查。

修复分三步。第一，把边界与初值拆成两个接口：

```python
def solve(analysis):
    # 迭代初值：must 分析从 top 开始，may 分析从 bottom 开始
    state = {b: analysis.init() for b in blocks}
    while changed:
        for b in blocks:
            # 边界只覆盖入口/出口，不参与其他块的初值
            if b == analysis.entry:
                new_in = analysis.boundary()
            else:
                new_in = analysis.join(state[p] for p in preds[b])
            ...
    assert state[analysis.entry] == analysis.boundary()
```

第二，给每种分析写死边界断言：可用表达式入口 ∅、到达定值入口 ∅、活跃变量出口 ∅、常量传播入口参数 NAC。第三，加一个 n=0 的回归测试，并在测试里把临时变量预填成哨兵值，避免「碰巧正确」。

反例 B 展示了同一个错误的另一种后果：到达定值把 OUT 初始化成全集 ALL。它没有让分析崩溃，而是让分析在 2 轮内收敛到「所有定值都到达所有块」的最大不动点——一个 sound 但完全无用的解。后果是常量传播看到每个变量都有多个到达定值，什么都不敢折；CSE 不敢复用；死代码删除不敢删。用户看到的是「优化没生效」，而不是「程序算错」，因此这类错误更容易被忽略。

| 分析 | 方向 | 边界 | 其余块初值 | 不动点 |
|:--|:--|:--|:--|:--|
| 到达定值 | 前向 | IN[entry]=∅ | ∅ | 最小 |
| 活跃变量 | 后向 | OUT[exit]=∅ | ∅ | 最小 |
| 可用表达式 | 前向 | IN[entry]=∅ | $U$ | 最大 |
| 常量传播 | 前向 | 参数 NAC，局部 UNDEF | 全 UNDEF | 最小 |

| 初始化写法 | 症状 | 哪个检查能发现 |
|:--|:--|:--|
| must 的入口也设成 top | 声称入口的表达式都可用，CSE 复用未定义值 | 边界断言、MOP、n=0 差分 |
| must 的其余块设成 bottom | 合流处交集恒为空，优化不触发 | 正例测试、首轮 trace |
| may 的其余块设成 top | 所有定值都到达所有块，常量传播放弃 | 与最小不动点比较、迭代轮数 |
| may 的入口设成非空 | 入口凭空多出事实，未初始化检查漏报 | 边界断言 |
| 后向的出口设成 top | 活跃变量在出口凭空活跃，寄存器压力变大 | 出口边界断言 |
| 边界只在初始化时应用一次 | 块被重新入队后入口值被覆盖 | 迭代中的边界复查 |

第二个失败模式方向相反：agent 记住了「入口是空集」，却把「其余块从全集开始」也改成了空集。代码看起来更「保守」：

```python
state = {b: set() for b in blocks}      # 所有块从空集开始
state[entry] = set()                     # 入口也是空集
# 于是可用表达式永远只在块内 gen，合流处交集成空
```

症状不是算错，而是优化根本不触发。CSE 在 B2 看到 i<n 可用（B1 的 gen 在 B2 的 IN 里），但在 B3 之后、B4 之前，交集把 p+q 抹掉了，后面所有依赖跨块可用性的优化都不动。用户看到的是「编译器没优化」，性能回归但功能正确，因此更难被功能测试发现。

根因是 must 分析的迭代方向：可用表达式要从全集向下删，才能得到最大不动点；从空集向上加，得到的是最小不动点（通常是空集）。这不是「保守一点更安全」的问题——对 must 分析，空集初值不是保守，而是把「所有路径都算过」的条件误读成「没有路径算过」，两者不是同一条边。

发现它的方法：

1. 写一个已知应该触发 CSE 的正例（比如 B2 的 p+q 与 B3 的复用），看优化是否发生。没有正例，就无法区分「没有机会」和「机会被漏掉」。
2. 打印第一次迭代的 OUT。正确版本 B0 的 OUT 为空、B1 的 OUT 为 {i<n}；错误版本 B1 的 OUT 仍为空，因为它的 IN 被交集成了空。
3. 检查迭代轮数与 OUT。把 must 初值改成空集另跑，错误版本 2 轮稳定，正确版本也是 2 轮，轮数没有区分度；但错误版本的 OUT[B1] 只有 {i<n}，跨块的 p+q 永远传不出去。
4. 断言「至少有一个块在迭代中值变大」，否则 must 分析没有真正开始下降。

修复是把初值和边界分开，并给 must 分析显式的 top：

```python
def solve(analysis):
    state = {b: analysis.init() for b in blocks}   # must: top，may: bottom
    for b in blocks:
        if b == analysis.entry:
            state[b] = analysis.boundary()          # must: empty
    ...
    assert analysis.is_must or state[analysis.entry] == analysis.boundary()
```

评审 agent 写的数据流代码时，按这张清单逐项问：

| # | 检查 | 不合格的表现 |
|--:|:--|:--|
| 1 | entry/exit 是否特殊处理 | 入口也参与前驱合并 |
| 2 | must 的初值是否是 top | 可用表达式从空集开始 |
| 3 | may 的初值是否是 bottom | 到达定值从全集开始 |
| 4 | 合并方向是否与分析类型一致 | must 用并集、may 用交集 |
| 5 | 后向分析的队列是否入队前驱 | 活跃变量沿后继传播 |
| 6 | 块内 use 是否按顺序扫描 | z 出现在 B5 的 use 里 |
| 7 | 边界是否有独立断言 | 只有初始化，没有断言 |
| 8 | 是否有正例和反例各一个 | 只有「跑通」的 smoke test |

回归测试可以写成一个函数，把两个失败模式都覆盖：

```python
def test_boundaries():
    inn, out, *_ = available(blocks, entry, order, U)
    assert inn[entry] == set(), "可用表达式入口必须是空集"
    assert out[B1] == {"i<n"}, "B1 应产生 i<n"
    assert "p+q" not in inn[B5], "零次循环路径不能声称 p+q 可用"

def test_reaching_least_fixpoint():
    inn, out, *_ = reaching(blocks, entry, order, defs)
    assert len(inn[B5]) == 10, "最小不动点应只有 10 条定值"
    assert inn[B5] == out[B1], "B5 的 IN 等于 B1 的 OUT"
```

它验证的是边界与最小不动点，不依赖实现细节。预期：正确实现全部通过；把入口改成全集，第一条断言失败；把到达定值初值改成全集，第二条断言失败（会得到 11 条）。

表里「边界」和「初值」两列必须分开实现。一个实用的检查是：让求解器接收 `boundary` 和 `init` 两个独立参数，并在每次迭代开始时重新应用边界，而不是只在初始化时应用一次。这样即使某个块被重新入队，入口的值也不会被前驱的合并覆盖。

最后一条经验：agent 生成的分析代码最容易错的地方不是传递函数，而是**边界与方向的组合**。传递函数通常有明确的公式可抄，边界却常被当成「初始化细节」。评审 agent 代码时，先看它有没有把 entry/exit 特殊处理，再看它从 top 还是 bottom 开始，最后才看 gen/kill。

## 5.10 本章陷阱（8–15 条） {#sec-compilers.2.5.10}

::: errata 本章陷阱
1. **把入口边界和迭代初值写成同一个值**：现象是可用表达式的 IN[entry] 变成全集，CSE 复用未定义的值；原因是没有区分「程序语义规定的边界」与「为了求最大/最小不动点选的起点」；修复是让求解器接收独立的 boundary 与 init，并在每次迭代重新应用边界，同时断言 IN[entry]=∅。  
2. **must 分析用并集合并**：现象是可用表达式在分支合流处越并越多，最终声称几乎一切可用；原因是用 may 的直觉写 must 的分析；修复是把合并改成交集，并把其余块初值改成全集，检查解是最大不动点。  
3. **may 分析用交集合并**：现象是到达定值/活跃变量在分支处只剩公共部分，漏掉只在一条路径上的事实；原因是方向反了；修复是 may 用并集、必须用交集，并用 5.6 的表逐项核对。  
4. **后向分析沿着后继传播**：现象是活跃变量在小图上偶尔正确、在大图上漏变量；原因是工作列表更新后把后继入队，而后向分析应把前驱入队；修复是显式传入 preds/succs，并写一个两块图的单元测试。  
5. **块内 use 把先定义后使用也算进去**：现象是 z 的活跃区间被拉到函数入口，寄存器压力变大；原因是没有按指令顺序扫描；修复是维护 defined 集合，只有未定义的读才加入 use。  
6. **gen/kill 顺序写反**：现象是 `x = x + y` 之后仍声称 `x+y` 可用，CSE 复用旧值；原因是先 kill 后 gen；修复是按指令顺序先 gen 再 kill，并用路径反例验证。  
7. **kill 只按变量名、忽略指针和调用**：现象是对 *p 的写入没有杀死 *q 的定值，常量传播把旧值传下去；原因是没有别名/副作用模型；修复是未知调用与逃逸指针写入杀死所有可能受影响的事实。  
8. **把不动点解当成程序事实**：现象是用「可能到达」的定值做「一定相等」的优化；原因是混淆 may 与 must；修复是优化规则显式写出「所有到达定值给出同一值」这一额外前提。  
9. **不可达块用交集身份元处理不当**：现象是死代码块声称所有表达式可用或都不可用，影响后续删除；原因是空前驱列表的合并返回了错误身份元；修复是先删不可达块，或让不可达块不参与优化决策。  
10. **只比较集合大小判断收敛**：现象是分析提前停止，IN/OUT 还在变；原因是两个不同集合可以大小相同；修复是比较完整位向量/字典，并保留每轮 trace。  
11. **工作列表只从入口播种，却想分析不可达块**：现象是某些块从未被处理，结果停留在初值；原因是工作列表只覆盖可达部分；修复是单独做可达性分析，或在需要时把所有块作为种子。  
12. **常量传播把 UNDEF 当常量、把除零折成 0**：现象是先用后定义的路径被折成一个具体值，或 trap 被删除；原因是平坦格的 UNDEF 语义与 trap 语义没有建模；修复是要求使用点有支配定义（或先 SSA），除零返回 NAC，并在第 6 章用差分执行验证。  
13. **用迭代轮数判断结果对**：现象是错误解 3 轮收敛、正确解 2 轮，轮数差异不能说明谁对；原因是把性能指标当正确性证据；修复是用边界断言、MOP 见证与差分执行，而不是轮数。  
14. **把工作列表当拓扑排序、假设每个块只处理一次**：现象是在有环图上结果停在中间状态，或者队列反复唤醒同一块却仍不收敛；原因是工作列表允许重复处理，收敛靠值的单调变化而不是入度归零；修复是保留 in_queue 去重、用值变化作为唯一终止条件，不要用「每个块处理一次」做剪枝。  
15. **改写 CFG 后复用旧的分析结果**：现象是插入/删除块、拆分临界边之后，活跃变量或可用表达式突然多出或缺少事实；原因是没有失效缓存，或 pass 声明保留了它其实改坏的分析；修复是让每个变换显式声明保留哪些分析，CFG 改动后强制重算，并在调试构建里校验分析结果的版本号。
:::

::: method 即时自测 · 5
**Q1** 到达定值的入口 IN 为什么是空集而不是全集？如果把入口也设成全集，会得到什么不动点，后果是什么？

**Q2** 活跃变量的块内 use 为什么要按指令顺序扫描？用 B5 的 `z = p + q; return z` 说明。

**Q3** 可用表达式在 B5 的 IN 是 {i<n} 而不是 {i<n, p+q}。给出推翻 {i<n, p+q} 的路径，并说明这条路径为什么在分析里必须被考虑。

**Q4** 一个 agent 写的求解器对可用表达式 2 轮收敛，方程自检通过，但 CSE 在 n=0 时算错。列出至少三条能发现它的检查，并说明每条检查分别依赖什么独立信息。

::: sol 答案
**A1** 入口没有执行过任何语句，可用表达式为空是语义事实；全集只是 must 分析为了求最大不动点选的迭代起点。把入口设成全集，会得到一个满足方程的最大不动点，声称入口处所有表达式可用；CSE 会把循环体里才算过的值复用到零次循环的出口，读到未定义值。

**A2** z 在块内先被定义，`return z` 用的是新值，不是入口值。若把 z 算进 use，IN[B5] 会多出 z，z 的活跃区间被拉到函数入口，寄存器压力变大；功能可能仍然正确，所以只能靠活跃集合/分配结果检查发现。

**A3** 路径 B0 -> B1 -> B5。n=0 时循环体 B2 不执行，p+q 从未计算。数据流分析必须考虑所有 CFG 路径，包括零次循环；可用表达式是 must 分析，一条路径不满足就足以否定。B5 的 IN 因此只有 {i<n}。

**A4** 边界断言（IN[entry] 应为 ∅）、有界 MOP/见证路径（B0 -> B1 -> B5 不含 p+q）、差分执行（n=0 时比较优化前后输出，t1 预填哨兵）。三者分别依赖语义边界、路径枚举和真实执行，互相独立；方程自检在这个例子里会通过，不能作为证据。
:::
