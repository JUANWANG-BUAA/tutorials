## A 组 · 概念（1–7）

::: ex A1 · 三件对象各管什么（主线 ①） {#ex-8.A.1}

Future、driver、Waker 各负责什么？为什么「收到一次 wake」不能当作「这次完成了」？

::: sol 解答

Future 描述可恢复计算，携带帧与状态；driver 决定何时再 poll；Waker 只请求执行器「再检查一次」。
通知不携带结果，也不保证这次一定完成；完成与否由 poll 的返回值给出。
这条边界同时限定本章的 `block_on`：它只驱动单个 Future，不含多任务调度与 I/O 注册。
对照[定义 8.1.1](ch08.md#def-8.1.1)与[定义 8.4.1](ch08.md#def-8.4.1)。

:::

:::

::: ex A2 · 构造与执行之间（主线 ①） {#ex-8.A.2}

从调用 `async fn` 到函数体第一行真正执行，中间发生了什么？只测「构造 Future」测到了什么、没测到什么？

::: sol 解答

调用只捕获参数并产生一个实现 Future 的匿名值，业务代码一行都没跑；真正进入函数体要等某个 driver 的一次 poll。
只测构造，测到的是建对象这一步；没测到任务体执行、结果产出与取消清理。
只测第一次 poll，对真正的 I/O 工作通常仍不完整。
对照[定义 8.1.2](ch08.md#def-8.1.2)、[例 8.1.1](ch08.md#ex-8.1.1)。

:::

:::

::: ex A3 · 静态未知与类型擦除（主线 ①） {#ex-8.A.3}

`impl Future<Output = u32>` 与 `Pin<Box<dyn Future<Output = u32> + Send>>`，哪一个可能引入堆分配与间接 poll？什么时候它才真的付出这两项？

::: sol 解答

后者是类型擦除，可能引入堆分配与间接 poll 调用；前者只是编译期名字未知，泛型调用链仍可单态化。
是否真的付出，取决于对象是否逃逸、优化是否去虚化，不能按签名报一个固定纳秒数。
对照[定义 8.1.3](ch08.md#def-8.1.3)。

:::

:::

::: ex A4 · 帧字段与变体字段（主线 ①） {#ex-8.A.4}

`field` 行与 `variant_fields` 有什么区别？在 cancellation_probe 的布局里，`Suspend0` 的 `[_s0, _s1]` 各是什么？`Unresumed` 为什么是空列表？

::: sol 解答

`field` 是帧里真实存放的字段；`variant_fields` 是状态机各变体各自持有哪几个字段。
`_s0` 是 `Guard`，`_s1` 是正在等待的 `std::future::Pending<()>`；两者都要跨过这个挂起点。
`Unresumed` 为空，因为业务体还没执行，没有需要跨挂起保存的活跃局部量。
对照[定义 8.2.1](ch08.md#def-8.2.1)、[例 8.2.1](ch08.md#ex-8.2.1)。

:::

:::

::: ex A5 · 判别值与恢复（主线 ①） {#ex-8.A.5}

poll 入口读判别值之后做了什么？为什么说恢复不是「从头重跑 async 函数」？把编号 3 写进外部判断错在哪？

::: sol 解答

poll 先读判别值，再按状态用 `switchInt` 跳到对应基本块；跨 await 存活的数据已经在帧里，接着跑即可。
所以恢复不需要重新解析源码或重建调用栈。
编号 0/1/2/3 只属于这一版 rustc 1.99.0 的输出，换版本或优化级别都可能重排；要区分状态应走 poll 返回值一类接口，或在本轮产物上重新核对。
对照[定义 8.2.2](ch08.md#def-8.2.2)、[思考 8.2.1](ch08.md#think-8.2.1)。

:::

:::

::: ex A6 · Pin 钉住的是什么（主线 ①） {#ex-8.A.6}

`Pin` 约束的是句柄还是对象？为什么 poll 收的是 `Pin<&mut Self>`？这是否意味着每个 Future 都含自引用、运行时都维护一个「钉住标志」？

::: sol 解答

约束的是被指向对象的地址稳定性承诺，不是外部指针的位模式。
poll 拿到独占的 `Pin<&mut Self>`，是因为某些 Future 在首次 poll 后形成内部自引用，整块 memcpy 会让内部引用失效。
这不表示每个 Future 都含自引用，也不表示运行时有钉住标志；Pin 主要通过类型与安全 API 表达承诺。
对照[定义 8.3.2](ch08.md#def-8.3.2)、[思考 8.3.1](ch08.md#think-8.3.1)。

:::

:::

::: ex A7 · 取消安全是一条接口性质（主线 ①） {#ex-8.A.7}

写出取消安全的定义。为什么「`Drop` 实现正确」既不充分、也不必要地证明业务层取消安全？举一个 `select!` 场景的后果。

::: sol 解答

取消安全：任何一次 `.await` 处被丢弃后，外部可观察状态仍然只有「完全没做」或「完整做完」两种。
`Drop` 只清理本进程字段，管不到已写出的字节、已提交的设备请求与另一进程里的工作，所以不足。
`select!` 里丢掉一个分支时，另一个分支可能已经把请求发出去了；重复执行与取消风险是同一枚硬币的两面。
对照[定义 8.8.1](ch08.md#def-8.8.1)、8.8.1 的三条误解。

:::

## B 组 · 推理（8–14）

::: ex B8 · 三组数字谁减谁（主线 ②） {#ex-8.B.8}

`sync` 0.519、`async-ready` 0.867、`async-self-wake` 7.407，单位都是 ns/element。哪一对相减能说什么？为什么这两个差都不能叫「async 函数调用成本」？

::: sol 解答

三组做同样的整数累加，区别只在有没有真实的调度边界。
`async-ready − sync` 测到的是状态机推进：没有 Pending 边界，但多了通过 driver 的推进。
`async-self-wake − async-ready` 更接近通知协议：每轮多一次真实 Pending，多出改 bool、`wake_by_ref`、置通知位、`unpark`、清位、再 poll 这一串动作。
第一、二组没有相同调度边界，所以不能把差异笼统归为「async 函数调用成本」，也不能宣布固定指令数。
对照 8.6.1、[例 8.6.1](ch08.md#ex-8.6.1)。

:::

:::

::: ex B9 · 这条交错需要乱序吗（主线 ①） {#ex-8.B.9}

消费者检查 ready 为 false、生产者写结果并置 ready、生产者看不到已注册 Waker 而不通知、消费者注册 Waker 并返回 Pending。

1. 触发这次丢通知，是否要求处理器乱序或编译器重排？
2. 把 ready 改成 `AtomicBool` 并在末尾补一条 `fence`，能可靠修复吗？
3. 为什么「在同一临界区内既读谓词又登记 Waker」更稳？

::: hint 提示

问自己：窗口是在一条语句内部，还是在两条语句之间？fence 能缩小一段时间，能不能消除一段交错？

:::

::: sol 解答

1. 不要求。完全合法、顺序一致的线程交错就足以触发，问题在「检查」与「注册」之间的窗口。
2. 不能。谓词写与注册仍是分开的两个事件，窗口照旧；原文明令禁止「补一条 fence 就宣称解决」。
3. 两个事件进了同一临界区后，生产者无法把自己的置位插进「读谓词」与「登记 Waker」之间：要么消费者读到 ready，要么生产者看到已注册的 Waker。
本章 `bench/src/park.rs` 的 `Mutex<Shared>` 测试就是这么安排的，真正的 wake 放到锁外只为缩短临界区。
对照[定义 8.4.2](ch08.md#def-8.4.2)、[例 8.4.1](ch08.md#ex-8.4.1)。

:::

::: ex B10 · 8.326 是什么的尾（主线 ②） {#ex-8.B.10}

`async-self-wake` 的批次 p99 是 8.326。能否读成「最慢的一次 poll 花了 8.326 ns」？它在 21 个数里排第几、每个数代表什么？

::: sol 解答

不能。它是 21 个批均值的最近秩分位数，每个批均值 = 一批 100000 个元素的墙钟除以元素数。
单元素抖动在批内被平均掉了，所以它反映批次之间的波动，不是一次 poll 的尾部。
要谈单次 poll 的尾部，得按 poll/Pending 次数或逐请求计时重新采集，本章没有采。
对照[定义 8.6.1](ch08.md#def-8.6.1)。

:::

::: ex B11 · 4097 与 2 能说什么（主线 ②） {#ex-8.B.11}

布局表给出「跨 await 数组 Future 4097、对齐 1」与「await 前缩短作用域 Future 2、对齐 1」，第三行 257 的对齐栏写着「本基准只输出 size」。

1. 4097 与 2 的差能写成「省了 4095 字节常驻内存」吗？
2. 第三行为什么不填一个对齐数字？
3. 这两行数字能外推到「所有缩帧都省两个数量级」吗？

::: sol 解答

1. 不能。这是跨挂起帧字段之差；大数组仍可能在首次 poll 的临时栈空间出现，缩的是帧，不是所有时刻的总内存。
2. 因为该例输出里只有 size、没有对应 align 记录。按证据纪律，没采集到的量就留空并写明，不替它编一个数；要对齐得用 `align_of_val` 或 `Layout` 重新记录。
3. 不能。尺寸由「恢复时还要用到哪些值」决定，换一段代码就要重新生成布局记录。
对照[例 8.3.1](ch08.md#ex-8.3.1)、[定义 8.3.1](ch08.md#def-8.3.1)。

::: ex B12 · 257 里的那个 1（主线 ②） {#ex-8.B.12}

Ready Future 的尺寸是 257，捕获载荷是 256 字节。多出来的 1 字节是什么？汇编里怎么印证它排在载荷之前？申请这条分配时大小与对齐各是多少？

::: hint 提示

回到 8.7.11 那张目标代码表：读状态与读载荷首字节用的偏移差多少？

:::

::: sol 解答

多出来的 1 字节是状态判别值，与[定义 8.2.2](ch08.md#def-8.2.2)的判别值相符。
汇编印证：`ldrb w8, [x0]` 读对象首字节的状态，`ldrb w8, [x0, #1]` 读载荷首字节，说明此版本数据起于状态之后的偏移 1；Ready 后 `mov w9, #1; strb w9, [x0]` 记录完成。
Box 分支的申请参数是 `w0=257, w1=1`，即 257 字节、对齐 1。
但实际分配器可能用更大的内部 size class，不能把 257 直接称为物理驻留内存增量。
对照 8.7.10、8.7.11。

:::

::: ex B13 · 11.6 能叫 malloc 税吗（主线 ②） {#ex-8.B.13}

`19.817 − 8.241 ≈ 11.6`，单位 ns/Future。有人说「这就是每次 `Box::pin` 的 malloc+free 成本」。指出至少三处过头，并给出可接受的措辞。

::: sol 解答

① 两个均值各自还含 256 字节 payload 准备与一次 Ready poll，相减不保证只剩分配。
② 8.241 与 19.817 绑定当前环境、257 字节载荷、未锁核未控温，11.6 不是常数。
③ 分配是否真的发生，光看均值不够；要回到汇编核对 `__rust_alloc` 与 `__rust_dealloc` 是否成对，若分配被消除，归因就错了。
可接受措辞：「本次测量的 Box 分支比栈上分支多出约 11.6 ns/Future，对应堆申请与释放这一对操作，前提是汇编里该对仍在。」
对照[思考 8.7.1](ch08.md#think-8.7.1)、[定义 8.7.1](ch08.md#def-8.7.1)。

::: ex B14 · 401、59、28、339 各是什么（主线 ②） {#ex-8.B.14}

`sample` 报告顶部折叠栈里 block_on 401、Darwin Parker::unpark 59、sync_sum 28，另有 339 条 dyld 观察。这四个数是什么量？能支持哪一句结论？不能支持哪一句？

::: sol 解答

它们是「某函数出现在折叠栈里的观察次数」，即栈位置计数，不是每条消息的耗时，也不是 CPU 周期或能耗。
能支持的弱结论只有一句：实际执行路径里包含 driver 与 `unpark`。
不能支持：把 401 除以总计数报稳定态 CPU 百分比，或填入 IPC、cache-miss 比例；339 条 dyld 观察说明采样窗口被启动过程污染。
要测稳定态，应先预热、让长运行负载到达明确阶段，再启动采样。
对照[定义 8.6.2](ch08.md#def-8.6.2)、8.6.8。

## C 组 · 实操（15–20）

::: ex C15 · 给这段 async 块写状态机字段（主线 ①） {#ex-8.C.15}

下面是一段示意代码（不是编译产物）。按 8.2 的读法，写出它的 `field` 列表与 `variant_fields` 骨架，并说明 `big` 为什么不在其中。

```rust
async fn mixed(count: Arc<AtomicUsize>) {
    let _guard = Guard(count);
    let big = black_box([7u8; 4096]);
    let first = black_box(big[0]);
    std::future::pending::<()>().await;
    black_box(first);
}
```

::: hint 提示

先标出每个局部量的最后一次使用在 await 之前还是之后，再决定谁进帧。

:::

::: sol 解答

`_guard` 活到挂起点之后，进帧；`first` 在 await 之后才用，也进帧；`big` 的最后一次使用（`big[0]`）在 await 之前，按[定义 8.3.1](ch08.md#def-8.3.1)不进帧，只在首次 poll 的临时栈空间出现；子 Future 同样进帧。

```text
coroutine layout {
    field _s0: Guard;
    field _s1: u8;
    field _s2: std::future::Pending<()>;
    variant_fields = {
        Unresumed: [],
        Returned: [],
        Panicked: [],
        Suspend0: [_s0, _s1, _s2],
    }
}
```

这是骨架，不是编译结果：字段顺序与变体编号属于某一版输出，必须用 8.2.1 的 `rustc --emit=mir` 命令在本机核对。
把 `Suspend0` 的编号当 ABI 违反[定义 8.2.1](ch08.md#def-8.2.1)的用途/编号之分。
参考[定义 8.2.1](ch08.md#def-8.2.1)与本页 A4。

:::

::: ex C16 · 这个 Future 为什么不是 Send（主线 ①） {#ex-8.C.16}

```rust
async fn bad(rc: Rc<String>) -> usize {
    std::future::pending::<()>().await;
    rc.len()
}
```

这个 Future 能不能交给可能跨线程迁移的执行器？给出两种修法，并说明为什么把 `async fn bad` 改成 `async move` 没有用。

::: sol 解答

不能。`rc` 在 await 之后仍被使用，所以它是挂在 `Suspend0` 里的帧字段；`Rc` 不是 `Send`，整个 Future 也就不是 `Send`。
修法一：把参数换成 `Arc<String>`。
修法二：把 `rc` 的活跃区间收在 await 之前（先算 `len`），让它不进帧。
还可以选择根本不跨线程：本章 driver 始终在调用它的线程上 poll，不要求 `Future: Send`，只有通知对象通过 `Arc` 与原子跨线程。
`async move` 只决定按值捕获，不改变值的类型属性，`Rc` 仍是 `Rc`，内部可变状态也不会自动加锁。
对照 8.8.4、8.5.6、[定义 8.3.1](ch08.md#def-8.3.1)。

:::

::: ex C17 · 两个析构读数（主线 ①） {#ex-8.C.17}

`cancellation_probe` 在函数体内构造 `Guard`，再等待永远 Pending 的子 Future。程序输出：

```text
drop before first poll: 0 guards; drop after Pending: 1 guard
```

解释 0 与 1 的差别。如果第二次的读数也是 0，你会先查哪两件事？

::: sol 解答

第一次销毁发生在首次 poll 之前：状态机还停在初始态，`Guard` 从未被构造，自然没有析构可计；但捕获的 `count` 仍作为帧字段被正常销毁。
第二次在 Pending 之后销毁：`Guard` 已作为跨挂起存活的局部对象存在于状态机字段里，drop Future 就会 drop 它，所以是 1。
若第二次也是 0，先查两件事：`Guard` 是否在 poll 内构造却没跨过挂起点（那样它在 poll 返回时已析构）；计数用的 `AtomicUsize` 是否与被测 Future 共享同一份。
对照[例 8.1.1](ch08.md#ex-8.1.1)、[例 8.8.1](ch08.md#ex-8.8.1)。

::: ex C18 · 把驱动器改坏，再改回来（主线 ①） {#ex-8.C.18}

先把本章的循环改成「Pending 就 park」的极简版（只写这一段），再构造一个令牌被吞的交错，最后改回协议版并说明窗口。

::: hint 提示

极简版错在把「有待检查」这件事寄存在 OS 线程的令牌上；回想 `consumed_park_token` 测试是怎么把它吃掉的。

:::

::: sol 解答

极简版：

```rust
loop {
    match future.as_mut().poll(&mut context) {
        Poll::Ready(value) => return value,
        Poll::Pending => thread::park(),
    }
}
```

交错（与 8.5.1 的反例同形）：poll 中先 wake 当前线程；poll 中其它逻辑调用 park，消耗掉 unpark 令牌；poll 返回 Pending；driver 再次 park，此时没有新的 unpark，可能永久等待。
协议版把「有待检查」交给驱动器自己的原子位：

```rust
loop {
    match future.as_mut().poll(&mut context) {
        Poll::Ready(value) => return value,
        Poll::Pending => {
            while !notify.notified.swap(false, Ordering::Acquire) {
                thread::park();
            }
        }
    }
}
```

窗口被盖住的方式：通知先置 `notified` 再 unpark；swap 读到 true 就不 park，直接重 poll；读到 false 才 park，而通知若发生在 swap 之后会补一个令牌，覆盖进入 park 之前的这段窗口。
park 允许伪唤醒，醒来后必须重新检查通知位，不能推断资源已完成。
对照[定义 8.5.1](ch08.md#def-8.5.1)、[例 8.5.1](ch08.md#ex-8.5.1)、8.5.4。

::: ex C19 · 把一个 4096 字节数组移出帧（主线 ②） {#ex-8.C.19}

正文里的 `large_across_await` 让数组跨 await 存活，记录尺寸 4097。把它改写成 `large_before_await` 的形式，先预测尺寸方向，再按 8.3.2 的命令核对，并写一句限定范围的结论。

::: hint 提示

改写只是给数组一个内层作用域，把「要用的那个字节」提前取出来；不要把命令输出之外的数值写进结论。

:::

::: sol 解答

改写（与正文同形）：把 `let bytes = black_box([7u8; 4096]);` 放进内层块，先取出 `first`，块结束即结束数组的局部作用域，再 await。

```rust
async fn large_before_await() -> u8 {
    let first = {
        let bytes = black_box([7u8; 4096]);
        black_box(bytes[0])
    };
    std::future::pending::<()>().await;
    first
}
```

预测：进帧的只剩一个 `u8` 与状态编码，尺寸应从 4097 量级降到个位数量级；正文记录的对照是 4097 与 2。
核对：`cargo run --offline --release --manifest-path bench/Cargo.toml --example future_layout`，必要时再跑 8.2.1 的 `--emit=mir` 看 `Suspend0` 字段。
限定：本机重测的数字记在自己的记录里并附版本；缩的是帧，首次 poll 的临时栈空间仍在，不能说总内存同倍数下降。

## 批改时最常给的三条意见

1. **把批均值当单次延迟**：7.407 写成「一次切换」、8.326 写成「最慢一次 poll」。先改句子里的分母与对象，再改表格。
2. **结论超出证据**：50 次重复说成任意交错都正确、采样计数说成 CPU 占比、11.6 说成 malloc 税、4097 与 2 说成常驻内存下降。每句补上「这组输入、这个版本、本次运行内」。
3. **把编号当 ABI**：拿 `Suspend0`、判别值 3、偏移 1 去写跨版本判断。改成「本轮 rustc 1.99.0 产物如此」，并附上生成它的命令。
