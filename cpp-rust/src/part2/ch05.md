## 5.1 trait 约束首先是一份可检查的接口 {#sec-cpp-rust.2.5.1}

本节回答一个问题：**同一个 trait 为什么既能当编译期的检查契约、又能当运行时的隐藏类型入口，而这两种用途都不规定「多久调用一次」？**

::: preview 先抓住一件事

把两件不同的事分开：**目标在哪一步定下来**（静态还是动态），以及**多久定一次**（每个元素还是一批一次）。`&T`（`T: Kernel`）与 `&dyn Kernel` 都能调用 `batch`，前者在编译期锁定目标，后者要到运行时查元数据；但一次动态进入，不等于循环里每次调用都动态。要否定「这条路径没有间接分派」，在产物里找到一条间接跳转就够了；要肯定「这里没有额外成本」，得同时核对声明约束、单态实例与最终目标码三层。第 1 章把这种分层观察写成了[@def-1.3.1]，本章把它用在类型上。
:::

### 5.1.1 不要从分派方式反推业务模型

同一个 trait 可以服务两个目的。
其一是描述某个具体类型必须提供的操作。
其二是让运行时持有隐藏具体类型的对象。
这两种用途可以共享方法集合。
但它们并不要求使用相同调用粒度。

考虑批量转换整数的业务。
算法需要一个 step，也需要处理完整切片的 batch。
类型可能在编译期确定。
也可能由配置在运行时选择。
无论哪种情况，都不必每处理一个整数就重新选择策略。

本章关注的是优化信息在哪个边界丢失。
不是介绍 trait 语法的入门章节。
也不把泛型简单等同于「没有任何成本」。
泛型会影响编译量、最终体积和优化范围。
对象擦除则会影响某些具体类型事实的可见性。

「分派」这个词在本章只表示一件小事：**一次方法调用怎样落到一段具体代码上**。

::: def 定义 5.1.1 · 分派 dispatch {#def-5.1.1}

**分派**（dispatch）指把一次方法调用对应到一段具体代码。目标在编译期就定死的叫**静态分派**（static dispatch），调用点通常能直接看见目标函数。目标要等程序跑到那里才知道的叫**动态分派**（dynamic dispatch），运行时靠对象自带的元数据找到实现。分派只说「什么时候确定目标」，既不承诺快慢，也不涉及谁拥有这块内存。

:::

::: ex 例 5.1.1 · 三行调用各自把目标定在哪一步 {#ex-5.1.1}

同一个 `Affine`，三种写法：① `generic_batch(&kernel, &input)`，形参是 `&T`（`T: Kernel`）；② `dynamic_batch(erased, &input)`，`erased: &dyn Kernel`；③ `dynamic_items(erased, &input)`，它在循环里逐个元素调 `kernel.step(v)`。按[@def-5.1.1]分别指出静态部分和动态部分。

::: sol 解答

① 具体类型在编译期进入 `T`，目标定死，属于静态分派；本轮它的 `Affine` 实例被内联进调用方（5.4.4 的产物对照表）。② `batch` 的目标由元数据在运行时给出，是动态分派，但只发生**一次**；进入实现以后 `Self` 又回到具体类型，见[@def-5.1.2]。③ 入口与②相同，但 `step` 落在循环里，动态分派的次数变成 16384。三种写法用的是同一套方法集合，所以「用了 trait」这句话本身不含任何粒度信息；正式计时见[@ex-5.5.1]。

:::

:::

### 5.1.2 实验接口：step 与 batch

以下是实验包中实际编译的类型和默认批处理方法。
整数计算全部使用 wrapping 语义。
旋转操作在每个 case 中完全相同。
没有浮点近似，也没有额外的数值精度差异。

```rust
pub trait Kernel {
    fn step(&self, value: u64) -> u64;
    fn batch(&self, input: &[u64]) -> u64 {
        input
            .iter()
            .map(|&v| self.step(v))
            .fold(0, u64::wrapping_add)
    }
}

#[derive(Clone, Copy)]
pub struct Affine {
    pub multiplier: u64,
    pub increment: u64,
}
impl Kernel for Affine {
    #[inline]
    fn step(&self, value: u64) -> u64 {
        value
            .wrapping_mul(self.multiplier)
            .wrapping_add(self.increment)
            .rotate_left(7)
    }
}
```

Affine 保存两个 u64 参数。
输入值先乘 multiplier，再加 increment，最后左旋七位。
batch 将每个结果以 wrapping 加法归约。
类型本身没有堆分配。
trait 对象引用也不必来自 Box。

默认 batch 是一个方法体，而不是「永远动态分派的循环」。
对具体 Affine 实现生成 batch 时，self 的具体类型已知。
其中 step 的调用可以直接解析到 Affine。
外部经 vtable（一张函数指针表，`dyn` 靠它决定运行时调哪个实现）进入这个 batch，不意味着其内部每个 step 仍需查表。
这是后面实验的关键。

::: def 定义 5.1.2 · 调用粒度 call grain {#def-5.1.2}

**调用粒度**指一次分派替多少个元素负责。每个元素一次调用是逐元素粒度；一整批只在开头进入一次是每批粒度。粒度由接口形状决定，不由编译器决定：`step` 和 `batch` 同时存在于同一个 trait 里，选哪个是调用点的责任。5.5 的两个 case 只差这一处，它们的正式结果按[@def-5.5.1]计量。

:::

### 5.1.3 约束检查与实例化不是一回事

泛型函数体先要在声明约束下成立。
不能因为本轮只传入 Affine，就在函数体里调用未声明的任意方法。
trait 约束把这份需求显式化。
实现选择和关联类型归一化提供后续类型事实。
这发生在编译阶段。

单态化（泛型为每种具体类型各生成一份代码）随后针对实际需要的具体参数生成代码。
它不是把任意不合法泛型程序「碰巧实例化成功」。
也不是每次运行都重新生成一个函数。
普通 ahead-of-time Rust 程序不会在这里建立泛型 JIT。
运行时收到的是已经构建好的产物。

::: def 定义 5.1.3 · 单态化 monomorphization {#def-5.1.3}

**单态化**（monomorphization）是编译期的一步：泛型定义先只作为模板存在，编译器再针对**实际用到的具体类型参数**各生成一份代码。一份定义、若干具体实例，程序跑起来时已经没有「正在生成函数」这回事——运行时拿到的产物早已构建完毕。单态化出来的实例仍可能被内联、合并或删除，所以它既不是源码文本替换，也不是保留函数边界的承诺；最终留下多少，要按[@def-5.2.1]在产物里数。

:::

### 5.1.4 类型路径表

| 接口形态 | 调用点掌握的信息 | 循环内部可能掌握的信息 | 主要代价边界 |
|:--|:--|:--|:--|
| &amp;Affine | 具体类型 | 字段和具体方法 | 优化后的业务本身 |
| &amp;T，T: Kernel | 实例化后具体类型 | 视单态实例与内联而定 | 编译量与代码体积 |
| &amp;dyn Kernel | 数据与方法表 | 取决于是否去虚化 | 间接调用与信息隐藏 |
| dyn 的 batch 方法 | 外部类型擦除 | 实现内部 Self 可以具体 | 每批一次分派 |
| enum 策略 | 有限变体集合 | match 分支中可具体化 | 分支与最大变体布局 |

表中的「可能」很重要。
具体类型可见，不表示每个函数都会内联。
动态类型隐藏，也不表示优化器永远无法恢复目标。
应把声明、编译可见性与最终调用形态分别检查。
不能只根据类型签名给每次调用分配固定纳秒税。

::: ex 例 5.1.2 · 把一行调用填进表里 {#ex-5.1.2}

调用点写成 `for v in input { total = total.wrapping_add(kernel.step(*v)) }`，其中 `kernel: &dyn Kernel`。① 它落在表格哪一行？② 能不能据此写「每个元素多花若干纳秒」？③ 要否定「这里没有间接调用」，最小证据是什么？

::: sol 解答

① 落在表格 `&dyn Kernel` 那一行，而且循环里没有任何批方法把元素包住，所以「循环内部可能掌握的信息」也停在擦除契约上。② 不能。本章没有为单条间接跳转单独定价：[@ex-5.5.1] 测到的是接口粒度改变之后的总体代码效果，跳转、跨边界内联与展开一起变。③ 目标码里一条循环内的间接跳转就是充分证据；5.3.3 摘录的 `blr x23` 正是这种证据。反过来要**肯定**「没有」，就得看完整函数体，不能只看签名（[@def-5.4.1]）。

:::

:::

::: think 思考 · 「入口只动态一次，所以 dyn 的成本可以忽略」 {#think-5.1.1}

有人读完 5.1.2 后主张：既然具体实现内部的 `step` 已被直接解析，`dyn` 的代价就只剩入口那一次跳转，任何情况下都能忽略。这个推理绕过了哪个前提？

::: sol 解答

绕过了「批次够大」这个前提。那一次的成本是被**摊薄**出来的：一批 16384 个元素时它几乎看不见——5.6 里 known_dyn 0.156133、opaque_dyn 0.158303，均值只差 0.002170 ns/元素；一批只有几个元素时，同一次进入连同夹具开销就摊不薄，[@def-5.6.2] 的条件不再成立。还有第二层：动态进入同时改变了优化器能跨边界看到多少业务，`dyn_item` 的差值不是一条跳转的价格（[@ex-5.5.1]）。能说的只是「本次批大小下一次进入被摊薄」，不是「dyn 免费」。

:::

:::

### 5.1.5 与所有权分开推理

选择 dyn 不等于选择共享所有权。
`&dyn Kernel`是借用。
`Box<dyn Kernel>`是某种拥有者。
`Arc<dyn Kernel>`还涉及引用计数与线程安全约束。
三者的生命周期成本不能合并成「虚调用成本」。

本章正式实验不在热路径分配 trait 对象。
Affine 与输入在计时前构造。
case 闭包的 Box 也在计时前创建。
夹具自身仍存在一次外层闭包动态调用。
它由大量元素摊薄，并且在各个 case 中共同存在。

::: def 定义 5.1.4 · 类型擦除 type erasure {#def-5.1.4}

**类型擦除**（type erasure）指把具体类型从接口签名中去掉，只留下「某个实现 `Kernel` 的对象」这个事实，外加一份能找到实现的方法元数据。被擦掉的是**编译期可见的类型信息**，不是值本身，也不是它待在哪里：`&dyn Kernel` 完全可以是对栈上 `Affine` 的借用。所以擦除、分派、所有权是三件事，要分别核对——正如[@def-1.1.3] 要求一次实验只回答一个受控的问题。

:::

::: method 判定流程 · 一次调用该算静态还是动态

1. **看签名**：形参是具体类型或 `&T`（`T: Kernel`），目标在编译期，属[@def-5.1.1] 的静态一侧；是 `&dyn` 或 `Box<dyn>`，目标在运行时。
2. **看粒度**：这一次动态进入替多少个元素负责（[@def-5.1.2]）。每批一次和每元素一次是两个量级。
3. **看产物**：签名说静态，也要确认最终代码里这一层有没有被内联、合并或删除（[@def-5.1.3]）；签名说动态，也要确认循环内部是否重新具体化（[@def-5.4.1]）。
4. **看所有权**：`&`、`Box`、`Arc` 的账各归各的，不并成一句「虚调用成本」（[@def-5.1.4]）。

:::

### 5.1.6 小结与常见错误

**小结。**① 分派只回答「目标什么时候定下来」（[@def-5.1.1]）；② 擦掉的是编译期类型信息，不是值也不是位置（[@def-5.1.4]）；③ 单态化按实际用到的类型生成代码，不保证产物里留着独立函数（[@def-5.1.3]）；④ 真正改变量级的是调用粒度——同一批元素，逐元素动态比每批动态慢约 4.1 倍（0.647618 对 0.156428，见[@def-5.1.2] 与[@ex-5.5.1]）；⑤ 声明、编译可见性与最终调用形态要分三层检查。下一节 [5.2 单态项、可达性与真实代码体积](#sec-cpp-rust.2.5.2) 把「实例到底生成多少」变成可数的东西。

::: errata 常见错误清单（5.1 节）

E-a **按关键字给调用定价。**`dyn` 不规定粒度，泛型也不保证内联（[@def-5.1.1]）。

E-b **把动态进入一次当成动态调用每次。**具体 `Self` 在 `batch` 内部是已知的（[@def-5.1.2]）。

E-c **把单态化理解成源码文本替换。**产物里的实例可能被合并或删除（[@def-5.1.3]）。

E-d **认为 `&dyn Kernel` 一定在堆上。**本章两个正式实验借用的是栈上 `Affine`（[@def-5.1.4]）。

E-e **把 `Box`、`Arc` 的成本记进分派账。**所有权与分派要分开计量（5.1.5）。

E-f **拿「方法集合相同」推出「成本相同」。**同一个 trait 可以承载两种调用粒度（[@ex-5.1.1]）。

:::

**第 1 题 · 记忆**　给出「分派」的定义，并写出静态与动态的判据。

::: sol 第 1 题答案
分派是把一次方法调用对应到一段具体代码。判据是确定目标的时机：编译期定死为静态分派，运行时靠元数据查找为动态分派。对应[@def-5.1.1]。
:::

**第 2 题 · 辨析**　`dyn_batch` 与 `dyn_item` 都接收 `&dyn Kernel`。哪一层相同，哪一层不同？

::: sol 第 2 题答案
相同的是外部擦除与方法集合；不同的是调用粒度——前者只在批次入口动态一次，进入后 `Self` 具体；后者把 `step` 放进循环，每元素一次。见[@def-5.1.2] 与 5.4.4 的产物对照表。
:::

**第 3 题 · 应用**　同事断言「`Vec<Box<dyn Kernel>>` 慢是因为有堆分配」。给出你先查的两件事。

::: sol 第 3 题答案
① 粒度：热循环里调的是 `step` 还是 `batch`（[@def-5.1.2]）。② 分配落在计时边界的哪一侧：本章正式夹具把对象构造放在计时外，所以它的数字不能替分配成本说话（[@def-1.1.3]）。两项查完，才轮到「堆」这个解释。
:::

**第 4 题 · 迁移**　把每元素调 `step` 的插件循环改成每批调一次 `batch`，其余不动。按本节骨架说明你要重新核对哪三层。

::: sol 第 4 题答案
① 声明层：策略能否在一批内保持不变，业务语义是否被偷换（[@ex-5.6.2]）。② 可见性层：具体实现内部是否真的把 `step` 解析掉了。③ 产物层：目标码的循环里还有没有间接调用（[@def-5.4.1]）。三层都核过，才谈得上用[@def-1.7.1] 的预算判定这次改动。
:::

## 5.2 单态项、可达性与真实代码体积 {#sec-cpp-rust.2.5.2}

本节回答一个问题：**「泛型让代码变大了多少」这句话要按哪个口径数，才不至于把编译机制写成一个编造的成本？**

::: preview 先抓住一件事

体积是**产物**的属性，不是源码的属性。想肯定「这个实例进了最终代码」，得在符号列表或`__text`里找到它；想否定「多了 N 个类型就多 N 份代码」，本轮 one→many 的 3008 字节差值本身就是一条反例：16 个 const 实例带来的增量既不等于单实例乘 16，也不能换算成任何每元素成本。口径要先说清，就像单位要先说清（[@def-1.1.3] 的估计对象在这里是字节）。
:::

### 5.2.1 单态化不是源码文本替换

一个泛型定义可以被很多具体类型使用。
但最终产物只需要可达的实例。
没有调用且不可达的定义可能不生成机器码。
生成过的实例还可能被内联、合并或删除。
因此「用了十个类型」不等于「最终恰有十个外部函数符号」。

单态项收集还要考虑其他可达对象。
某个 vtable 中被引用的方法可能需要实际代码。
函数指针保存的目标也不能轻易消失。
析构 glue 同样可能形成实例。
仅数源码中的泛型调用表达式是不够的。

::: def 定义 5.2.1 · 可达性 reachability {#def-5.2.1}

**可达性**（reachability）指从程序入口出发，编译与链接过程有办法用到某段代码：它被调用、被取地址，或者出现在一张必须存在的方法表里。可达的实例才需要生成机器码；不可达的定义可以只停在源码和中间表示里。可达集合会随内联、函数合并、链接删除和 LTO 改变，所以「最终留下多少代码」只能在产物上数，不能从源码调用点数出来（对照[@def-5.1.3]）。

:::

::: def 定义 5.2.2 · 单态项收集 monomorphization item collection {#def-5.2.2}

**单态项收集**是编译前端决定「要为哪些具体参数生成代码」的那一步。除了泛型调用点，被 vtable 引用的方法、函数指针保存的目标、析构 glue 都会把实例拉进这个集合。它给出的是**候选集合**，不是最终字节；后端与链接器还会继续改这个集合（[@def-5.2.1]）。

:::

### 5.2.2 实例生成与链接删除

rustc 需要先知道要生成什么。
后端优化又会改变函数边界。
链接器可能继续删除不可达节。
LTO 会增加某些跨模块处理机会。
多个阶段都能改变最终符号数量。

这也是「代码大小」必须指定口径的原因。
rlib 大小不是最终可执行文件的热指令体积。
调试信息占用不等于执行时 I-cache 压力。
Mach-O 的虚拟地址保留区更不应被算成物理代码。
本章只选明确的`__text`节口径做观测。

::: def 定义 5.2.3 · `__text` 口径 code-size measure {#def-5.2.3}

**`__text` 节**是 Mach-O 可执行文件里存放机器指令的那一段。本章用它的字节数作体积口径，因为它比文件总长少掉调试信息、元数据和对齐填充，也更接近真正会被取指的代码。三种口径要分清：rlib 是中间产物，文件长度含所有节，`__PAGEZERO` 只是虚拟地址保留区。口径没写明的「代码大小」不能拿来比较，正如单位没写明的耗时不能比较（[@def-1.5.1] 的名义分母是同一类错误）。

:::

::: ex 例 5.2.1 · 「被十个类型用到，所以至少十份代码」{#ex-5.2.1}

一位库作者声称：我的泛型 API 被 10 个具体类型使用，最终产物里因此**至少**多 10 份独立代码。按[@def-5.2.1] 和[@def-5.2.2] 给出三条具体检查，并说明本轮探针（只为观察产物变成什么样而留下的小程序）为什么非要把函数地址存进一张表。

::: sol 解答

① 内联之后可能根本没有独立符号——本轮 `generic_batch` 的 `Affine` 实例就被内联到调用方（见 5.4.4 的产物对照表）。② 没有被引用且不可达的实例可以整个不生成：`probes/code_size.rs` 正是用 `functions` 表把各实例的地址交给产物，否则 `--cfg=many` 里多出来的实例可能连候选集合都进不了。③ 链接与 LTO 还会继续改：本轮 many 开 ThinLTO 后`__text`是 214768 字节，比普通 many 的 220156 更小，说明份数不是源码决定的。结论只能在符号列表和节大小上核（[@def-5.8.3]）。

:::

:::

### 5.2.3 真实尺寸探针

`probes/code_size.rs`使用 const 参数产生不同计算实例。
每个实例有真实的输入依赖与不同常量。
函数地址存进一个表，使这些目标可达。
运行时逐实例与参考函数比较输出。
然后打印聚合 checksum。

单实例构建只保留 TAG=1。
多实例构建启用`--cfg=many`。
它需要 TAG=1 到 16。
这里不是「十六个 Rust 类型」对比。
它是十六个不同 const 参数的泛型实例。

```rust
use std::hint::black_box;
#[inline(never)]
fn transform<const TAG: u64>(input: &[u64]) -> u64 {
    input.iter().fold(0u64, |sum, &v| {
        sum.wrapping_add(v.wrapping_mul(TAG | 1).rotate_left(TAG as u32 & 63))
    })
}
fn reference(tag: u64, input: &[u64]) -> u64 {
    let mut result = 0u64;
    for &v in input {
        result = result.wrapping_add(v.wrapping_mul(tag | 1).rotate_left(tag as u32 & 63));
    }
    result
}
fn main() {
    let input: Vec<_> = (0u64..4096).map(|v| v.wrapping_mul(173)).collect();
    let functions: &[(u64, fn(&[u64]) -> u64)] = &[
        (1, transform::<1>),
        #[cfg(many)]
        (2, transform::<2>),
        #[cfg(many)]
        (3, transform::<3>),
        #[cfg(many)]
        (4, transform::<4>),
        #[cfg(many)]
        (5, transform::<5>),
        #[cfg(many)]
        (6, transform::<6>),
        #[cfg(many)]
        (7, transform::<7>),
        #[cfg(many)]
        (8, transform::<8>),
        #[cfg(many)]
        (9, transform::<9>),
        #[cfg(many)]
        (10, transform::<10>),
        #[cfg(many)]
        (11, transform::<11>),
        #[cfg(many)]
        (12, transform::<12>),
        #[cfg(many)]
        (13, transform::<13>),
        #[cfg(many)]
        (14, transform::<14>),
        #[cfg(many)]
        (15, transform::<15>),
        #[cfg(many)]
        (16, transform::<16>),
    ];
    let mut checksum = 0u64;
    for _ in 0..32 {
        for &(tag, function) in functions {
            let output = function(black_box(&input));
            assert_eq!(output, reference(tag, &input));
            checksum = checksum.wrapping_add(output);
        }
    }
    println!("instances={} checksum={checksum}", functions.len());
}
```

这个探针不是第三个计时 benchmark。
我们执行它以验证各构建产物的计算。
没有正式报告其运行时间。
它服务的是可达实例与体积观察。
不要把它的 checksum 误写成吞吐指标。

它的输出观察方式与[@def-1.3.1] 的要求一致：逐实例与独立写法的 `reference` 比较，再聚合。没有通过运行时间校验的构建，不能只凭字节数进入体积结论。

### 5.2.4 本轮尺寸结果

| 构建 | 可达计算实例 | Mach-O __text 字节 | 执行校验 |
|:--|--:|--:|:--|
| one，普通 O3 | 1 | 217148 | checksum=92855992320 |
| many，普通 O3 | 16 | 220156 | checksum=95338125850705920 |
| many，ThinLTO | 16 | 214768 | `thin-run.txt`：checksum=95338125850705920，与 many 同值 |
| many，PGO-use | 16 | 220028 | `pgo-use-run.txt`：checksum=95338125850705920，与 many 同值 |

普通 many 比 one 的`__text`多 3008 字节。
这个差值包含实例和相关生成形态的变化。
不是把整个可执行文件体积平均分给十五个函数的语言规则。
标准库与启动代码仍占很大一部分。
也没有测量运行时指令缓存的驻留情况。

ThinLTO 的整个`__text`比普通 many 更小。
这不保证每个单态实例都变小。
它可能改变标准库和调用边界等更广范围。
PGO-use 也已实际构建执行，但本章不为它提供加速百分比。
第6章讨论该流程的训练与验证边界。

::: ex 例 5.2.2 · 3008 字节能不能除以 15 {#ex-5.2.2}

有人从上一张表推出：「16 个实例比 1 个多 3008 字节，所以每新增一个实例约 200 字节，今后加类型就按 200 字节预算。」这条除法在哪里不成立？本节能诚实说出的又是什么？

::: sol 解答

不成立在三处。① 分子不是「15 个新实例的指令」：one 与 many 是两个完整构建，差值里还含相关生成形态的变化（[@def-5.2.1]）。② 分母口径不对：表里的字节是整个`__text`，标准库与启动代码占很大一部分，它不是「业务代码总量」。③ 增量不是线性的：同一份 16 实例代码在 ThinLTO 下`__text`为 214768，比普通 many 的 220156 少 5388，说明构建方式的影响已经和实例数量同量级。能诚实说的是：本轮口径下 many 比 one 大 3008 字节，即约 one 的 1.4%（3008 ÷ 217148）；PGO-use 构建为 220028，介于两者之间。至于这些字节落到哪个负载、执行多少次，本节没有采集。

:::

:::

::: think 思考 · 多了 3008 字节，取指缓存压力一定上升吗 {#think-5.2.1}

代码体积变大，通常会让人直接写「I-cache 压力上升」。这个推理绕过了哪个前提？

::: sol 解答

绕过了「体积证据与运行证据分属两层」这条规则。新增的字节可能全在冷路径上，也可能在真实业务里一次都没被执行；本轮既没有采集 I-cache、ITLB、分支目标缓冲（BTB）的任何硬件事件，也没有统计这些实例的实际执行次数。所以这里只能写「`__text`多 3008 字节」，不能写成「多了 3008 字节导致命中率下降多少」。要把这句话补全，需要[@def-5.8.3] 里另一层的证据。

:::

:::

### 5.2.5 代码膨胀何时值得担心

泛型层层包装时，内层大函数可能被多次实例化。
若不同类型只影响很小的一部分计算，体积收益可能有限。
此时可以把稳定的大内核从泛型外壳分离出来。
外壳负责类型适配。
核心接收切片、数值参数或已归一化的中间表示。

这种重构不一定要引入 dyn。
一个非泛型私有函数也可以共享机器代码。
反过来，一个接受 dyn 的函数也可能被内联后复制到多个调用者。
应查看最终产物。
不要把源码函数数量当成最终代码字节数。

::: method 判定流程 · 怀疑代码膨胀时按四步走

1. **定口径**：先说数什么——`__text` 字节、符号数，还是 rlib 大小（[@def-5.2.3]）。口径没定的比较直接作废。
2. **数产物**：用符号列表和节大小确认哪些实例真的存在，而不是数源码里的泛型调用（[@def-5.2.2]）。
3. **找可共享部分**：把与类型无关的稳定内核挪进非泛型函数；这一步不需要引入 `dyn`（对照[@def-5.1.4]）。
4. **改完重测同口径**：字节数变化要回到同一构建、同一节上比较，并保留校验输出（[@ex-5.2.1]）。

:::

### 5.2.6 不报告未测的硬件结论

代码体积增大可能影响 I-cache、ITLB 或分支目标结构。
但本轮没有收集相关 PMU 事件。
不能写成「多了 3008 字节导致 BTB 命中率下降多少」。
甚至不能保证这些新增代码在某个真实业务负载中都被执行。
体积证据与缓存性能证据是两个层次。

把这一条写成制度：**没有采集的指标一律写「本节没有采集」**。本章的缺失清单是：指令缓存缺失次数、ITLB 缺失、分支目标结构命中率、指令退休数、核心周期，以及这些实例在真实业务里的执行次数。它们既不能从`__text`字节推出来，也不能从[@def-1.5.2] 的批均值换算出来。

### 5.2.7 小结与常见错误

**小结。**① 只有可达的实例才需要生成机器码（[@def-5.2.1]）；② 单态项收集给的是候选集合，后端与链接器还会继续改（[@def-5.2.2]）；③ 体积必须按[@def-5.2.3] 的口径数，本轮 many 相对 one 的`__text`增量是 3008 字节；④ 这个增量不能线性外推到「每个类型多少字节」（[@ex-5.2.2]）；⑤ 静态字节与缓存性能是两个层次，本章没有采集后者。下一节 [5.3 dyn 的数据、元数据与非稳定布局](#sec-cpp-rust.2.5.3) 转向运行时那一侧。

::: errata 常见错误清单（5.2 节）

E-a **用源码里的泛型调用数估最终符号数。**可达性、内联与链接删除都会改形态（[@def-5.2.1]）。

E-b **把文件总长当成指令体积。**rlib、调试信息、`__PAGEZERO` 都不是`__text`（[@def-5.2.3]）。

E-c **把 3008 字节平均分成 15 份。**差值含生成形态变化，且构建方式影响同量级（[@ex-5.2.2]）。

E-d **由体积直接写缓存回归。**没有硬件事件就没有这句的权利（[@think-5.2.1]）。

E-e **为了共享代码强行引入 dyn。**非泛型私有函数也能共享机器代码（5.2.5）。

E-f **把探针的 checksum 当吞吐指标。**它只验证计算正确，没有正式计时（5.2.3）。

:::

::: method 即时自测 · 5.2

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　说出「可达性」的定义，并列出三种把实例拉进集合的方式。

::: sol 第 1 题答案
可达性指编译与链接过程有办法用到某段代码：被调用、被取地址、或出现在必须存在的方法表里。三种方式是 vtable 引用的方法、函数指针保存的目标、析构 glue。对应[@def-5.2.1] 与[@def-5.2.2]。
:::

**第 2 题 · 辨析**　「many 的`__text`比 one 大 3008 字节」和「ThinLTO 让 many 的`__text`小了 5388 字节」，这两句话的证据强度一样吗？

::: sol 第 2 题答案
口径一样（同一口径的节大小），但含义不同：前者含新增实例与相关生成形态，后者是构建方式对整体代码的影响，两者都不能换算成每元素成本，也不能推成缓存变化。两句都只是静态体积陈述，见[@ex-5.2.2] 与[@def-5.2.3]。
:::

**第 3 题 · 应用**　评审里有人说「这个 crate 有 40 个泛型调用，太膨胀了，换 dyn」。给三步反驳动作。

::: sol 第 3 题答案
① 先定口径并取本轮可比的`__text`与符号列表（[@def-5.2.3]）；② 数实际生成的实例，看哪些真的可达（[@def-5.2.2]）；③ 找出与类型无关的稳定内核挪进非泛型函数，再同口径复测（5.2.5）。换 `dyn` 只是把类型事实藏起来，不保证字节变小，而且会引入新的分派问题（[@def-5.4.1]）。
:::

**第 4 题 · 迁移**　把探针从 const 参数改成 16 个不同实现类型，表还能不能照读？

::: sol 第 4 题答案
不能照读。const 参数的 16 份实例与 16 个类型的实例是两套生成形态，`__text` 增量不通用；探针的 `functions` 表、`reference` 校验和聚合 checksum 要重写，否则「执行校验」那一列失去意义（[@ex-5.2.1]）。这是一次新实验，需要新归档，不能在旧表上写新句子（[@def-1.7.3]）。
:::

## 5.3 dyn 的数据、元数据与非稳定布局 {#sec-cpp-rust.2.5.3}

本节回答一个问题：**`&dyn Kernel` 占的那两个机器字里到底装了什么，其中哪些是语言层面的事实、哪些只是本轮产物的观察？**

::: preview 先抓住一件事

先把「值」和「指向值的指针」分开。`Affine` 是两个 `u64`，占 16 字节；`&dyn Kernel` 也占 16 字节，但它装的是数据地址加一份元数据，对象本体仍留在原处。要否定「`dyn` 一定要堆分配」，只需给出一个借用栈上对象的合法程序——本章两个正式实验都是；要肯定「这里每次调用都查表」，得在目标码里找到那条间接跳转，而不是数签名里出现了几次 `dyn`（[@def-5.4.1]）。
:::

### 5.3.1 先区分值与指向值的指针

dyn Kernel 是动态尺寸类型。
实际使用通常通过某种指针或拥有者访问。
借用对象携带实际数据位置和相应元数据。
元数据使运行时可以找到正确的方法实现。
这不要求把具体对象复制进一个统一的大结构体。

本章用图表示逻辑组成。
不通过 transmute 拆解 trait 对象。
不从私有 vtable 地址读取任意槽位。
这些操作对于解释实验没有必要。
安全 Rust 已足以构造、调用与测试对象。

::: def 定义 5.3.1 · 动态尺寸类型 dynamically sized type, DST {#def-5.3.1}

**动态尺寸类型**（dynamically sized type, DST）指编译期算不出大小的类型。`dyn Kernel` 就是：实现它的结构体各不相同，`Affine` 是 16 字节，别的实现可能更大也可能更小。尺寸未知，所以它只能通过指针或拥有者来使用，而这类指针必须比「具体类型的指针」多带一份信息。DST 既不规定对象活在哪里，也不规定谁拥有它——那两件事由 `&`、`Box`、`Arc` 分别决定（[@def-5.1.4]）。

:::

::: def 定义 5.3.2 · vtable 虚方法表 {#def-5.3.2}

**vtable**（虚方法表，virtual table）是一张按 trait 与方法排好的表，槽位里存的是**函数地址**，此外还有大小、对齐、析构这类类型管理信息。动态分派的过程就是：从对象自带的元数据找到这张表，取出对应槽位的地址，再跳过去。本章只把 vtable 当解释模型——表里有几个槽、`step` 排在第几槽、偏移是多少，都是当前编译产物的实现细节，不是跨版本的语言承诺（见[@ex-5.3.2]）。

:::

::: def 定义 5.3.3 · trait 对象（胖指针）trait object {#def-5.3.3}

**trait 对象**指「指向 DST 的指针连同它的元数据」这个组合。`&dyn Kernel`、`Box<dyn Kernel>`、`Arc<dyn Kernel>` 都是 trait 对象，区别只在所有权那一层（[@def-5.1.4]）。它常被叫作**胖指针**，因为比具体类型的引用多带一个字。多出来的这个字在本轮存的是方法元数据，不是长度，也不是引用计数——尺寸相同不代表语义可以互换（见[@ex-5.3.1]）。

:::

### 5.3.2 本机尺寸探针

| 类型 | size | align | 包含什么 | 不包含什么 |
|:--|--:|--:|:--|:--|
| Affine | 16 | 8 | 两个 u64 参数 | vtable 与堆头 |
| &amp;u64 | 8 | 8 | 具体类型的借用指针 | 被借用对象本体 |
| &amp;dyn Operation | 16 | 8 | 数据和元数据 | 对象分配 |
| Box&lt;dyn Operation&gt; | 16 | 8 | 擦除后的拥有指针信息 | 分配器实际块成本 |
| &amp;[u64] | 16 | 8 | 数据与长度 | 元素缓冲 |

切片引用与 trait 对象引用都可能占两个机器字。
但第二个字的语义不同。
切片长度不能当作 vtable 指针。
vtable 指针也不能当作元素数量。
相同尺寸不支持任意类型重解释。

这些是本机探针的实际结果。
不能据此声明 Rust 对任意 DST 都承诺两个字。
也不能把 usize 的本机宽度推广到 32 位目标。
接口跨平台时应使用语言层面的类型契约。
对 FFI 更应另行制定稳定表示。

::: ex 例 5.3.1 · 两个 16 字节能不能互换 {#ex-5.3.1}

上表里 `&dyn Operation` 与 `&[u64]` 都是 size 16、align 8。① 有人据此写 `transmute`，把擦除引用直接当切片引用，声称「反正都是两个字」——指出错在哪一步。② 若目标平台的 `usize` 是 4 字节，这张表能照抄吗？③ 接口要跨平台、跨构建稳定，应该靠什么表达？

::: sol 解答

① 错在第二个字的语义：一个是元素个数，一个是 [@def-5.3.2] 里那份方法元数据。把长度当元数据用，第一次调用就会去一个不存在表的地方取地址。本节所有观察都由安全 Rust 的尺寸探针给出，解释实验不需要 `transmute`（5.3.1 已声明不这么做）。② 不能照抄。16 与 8 都是本机探针的实测结果，`usize` 宽度变化会同时改变两个字段如何打包，对任意 DST 承诺「两个字」也不是语言规则。③ 用语言层面的类型契约表达接口；确实需要独立版本的组件边界，另行设计显式函数表与所有权接口（5.3.5）。

:::

:::

### 5.3.3 实际 vtable 调用证据

本轮`dynamic_items`目标码在循环外加载 step 目标。
循环中执行间接调用。
下面摘录了真实片段，完整符号保存在归档中。

```asm
ldr x23, [x1, #24]
LBB14_2:
ldr x1, [x20], #8
mov x0, x22
blr x23
add x21, x0, x21
subs x19, x19, #1
b.ne LBB14_2
```

24 是本轮这个目标码中的观察偏移。
不把它称为 Rust vtable 的永久第三槽 ABI。
优化器把目标指针加载移出循环，也说明「每次动态调用必定两次加载」的口号太粗糙。
本轮仍保留了每元素一次的间接跳转。
真正代价还包括无法跨调用边界展开的业务。

::: ex 例 5.3.2 · 偏移 24 能写进文档吗 {#ex-5.3.2}

上面那段摘录里，`ldr x23, [x1, #24]` 在循环外取出了 `step` 的地址，循环体里只剩 `blr x23`。① 能不能据此在内部文档写「`Kernel::step` 在 vtable 偏移 24」？② 「每次动态调用都要两次内存加载」这句话被这段产物证明了还是否定了？③ 这段摘录真正支持的结论是什么？

::: sol 解答

① 不能。24 只属于本轮这一份目标码：增删 trait 方法、改变方法声明顺序、换优化级别或换工具链都可能改变它，把它写成永久槽位就是[@def-5.3.4] 意义上的 ABI 承诺，而本章没有做过那种承诺。② 否定了。加载被优化器提到循环外，每个元素只剩一次间接跳转——[@def-5.1.2] 的粒度视角在这里能直接看见。③ 支持的是「本轮 `dynamic_items` 的循环内确实每元素一次间接调用」，与[@ex-5.5.1] 里它更慢的观察相互印证；它不支持「差值全是跳转的价钱」。

:::

:::

::: think 思考 · 给外壳加 `repr(C)`，内部的 `dyn` 就稳定了吗 {#think-5.3.1}

有人提议：把持有 `&dyn Kernel` 的那个结构体标成 `repr(C)`，这样就能把这个 trait 对象的裸指针交给独立编译的动态库，省掉一层显式接口。这个推理绕过了什么？

::: sol 解答

绕过了「`repr(C)` 只约束它直接标注的那个类型的字段布局」。`&dyn Kernel` 第二个字指向的元数据内部长什么样、槽位怎么排、符号叫什么，都不由这个属性决定；对面那个用另一套工具链、另一个版本编译出来的库，没有理由和你看到同一份事实。布局之外还有符号解析、panic 策略与分配器（按需划分和回收内存的那个库）契约（5.3.5）。真要独立版本，应该设计显式函数表和所有权接口，而不是把[@def-5.3.2] 的实现细节当协议消费。

:::

:::

### 5.3.4 对象不自动拥有线程安全

`&dyn Kernel`本身不承诺 Send 或 Sync。
是否可以跨线程传递还需要相应自动 trait 约束。
本章正式实验单线程执行。
没有测 Arc 引用计数、锁或工作队列。
这些开销不能从本表推出。

类型擦除也不把借用变成`'static`。
对象可能引用外部数据。
接口需要让这些数据活得足够久。
默认对象生命周期规则不应被当成「编译器延长底层对象寿命」。
所有权与分派仍需分别审查。

擦除改变的是**类型信息**，不是**寿命**和**线程属性**。这两条与[@def-5.1.4] 是同一件事的两面：签名里的 `dyn` 只说明目标晚点才知道。

### 5.3.5 Rust trait 对象不是插件 ABI

同一工具链构建内部的 dyn 调用可以非常实用。
但把一个 trait 对象裸指针交给独立编译的动态库，是另一类问题。
布局、符号、panic 与分配器契约都需要额外保证。
本章没有设计跨编译器版本的插件 ABI。
也不把`repr(C)`加在某个外壳上就宣布其内部 dyn 稳定。

如果确实需要独立版本组件，通常应设计显式函数表和所有权接口。
这属于 FFI 项目边界，而非本章把 vtable 私有细节变公开。
不要为了节省一次间接调用，先引入无法维护的二进制契约。
语义边界清晰通常比依赖隐式布局更重要。

::: def 定义 5.3.4 · 应用二进制接口 ABI {#def-5.3.4}

**ABI**（application binary interface，应用二进制接口）约定的是**独立编译的两段代码之间**怎么传参、怎么命名符号、谁负责释放内存。同一工具链、同一构建内部的 `dyn` 调用不需要 ABI 承诺，因为两侧看到的是同一份布局事实。跨版本、跨构建交付时，元数据内部结构、槽位顺序和符号都必须另有显式保证。本章的 24 与 32 只是产物观察值，不是协议——第 1 章 1.5.4 把符号别名当成「当时构建的观察」而非语言承诺，是同一个道理（[@def-1.8.1]）。

:::

::: method 判定流程 · 面对一个 dyn 调用先问四件事

1. **本体在哪**：这是对栈上对象、静态数据还是堆上对象的擦除？尺寸表（5.3.2）说明 `&dyn` 不必来自 `Box`。
2. **粒度多大**：擦除后的方法每批进入一次还是每元素一次（[@def-5.1.2]）？
3. **产物长什么样**：循环里有没有间接跳转，跳转前有没有表加载（[@ex-5.3.2]）？
4. **边界跨不跨**：这个指针会不会离开当前构建？跨出去就落入[@def-5.3.4]，本章不给结论。

:::

### 5.3.6 小结与常见错误

**小结。**① DST 只是「编译期算不出大小」，不规定对象住在哪儿（[@def-5.3.1]）；② trait 对象的第二个字是元数据，和切片长度同宽不同义（[@def-5.3.3]、[@ex-5.3.1]）；③ 动态分派的机制是「元数据 → 表 → 取地址 → 跳转」（[@def-5.3.2]），但加载可以被提出循环（[@ex-5.3.2]）；④ 偏移属于产物，不属于协议（[@def-5.3.4]）；⑤ 擦除不改变寿命与线程属性。下一节 [5.4 去虚化取决于信息，不取决于关键字](#sec-cpp-rust.2.5.4) 处理「这些查找为什么有时根本不存在」。

::: errata 常见错误清单（5.3 节）

E-a **认为 `dyn` 就一定在堆上。**`&dyn Kernel` 可以借用栈上 `Affine`（[@def-5.3.1]）。

E-b **把尺寸相同当成语义相同。**16 字节的切片引用与擦除引用不能互换（[@ex-5.3.1]）。

E-c **把本轮偏移写成永久 ABI。**24 与 32 只属于当前产物（[@def-5.3.4]）。

E-d **用 `transmute` 拆 trait 对象解释实验。**安全 Rust 已足够构造与调用（5.3.1）。

E-e **由 `dyn` 推出跨线程要加 `Arc`。**Send/Sync 与分派是两条独立的约束（5.3.4）。

E-f **给外壳加 `repr(C)` 就宣布内部 `dyn` 稳定。**属性不覆盖元数据内部（[@think-5.3.1]）。

:::

**第 1 题 · 记忆**　`&dyn Kernel` 的两个机器字各存什么？它和 `&[u64]` 的差别在哪？

::: sol 第 1 题答案
第一个字指向数据本体（本轮是栈上 `Affine`），第二个字是方法元数据；`&[u64]` 的第二个字是元素个数。尺寸同为 16，语义不可互换。对应[@def-5.3.3] 与[@ex-5.3.1]。
:::

**第 2 题 · 辨析**　「`blr x23` 说明动态调用每元素两次内存加载。」这句话哪一半对、哪一半错？

::: sol 第 2 题答案
「每元素一次间接调用」对；「两次加载」错——`ldr x23, [x1, #24]` 在循环外只执行一次，见[@ex-5.3.2] 的摘录顺序。

::: sol 第 3 题答案
① 设计显式函数表：导出 `extern "C"` 的函数指针数组与不透明的 `*mut c_void` 状态，边界只用 C 级类型（[@def-5.3.4]）。② 明确所有权与释放责任，并固定 panic、分配器契约（5.3.5）。两条都比消费[@def-5.3.2] 的实现细节更可维护。

## 5.4 去虚化取决于信息，不取决于关键字 {#sec-cpp-rust.2.5.4}

本节回答一个问题：**源码里写了 `dyn`，最终机器代码里到底会不会留下间接调用；如果留下，是哪条信息让它留下的？**

::: preview 先抓住一件事

去虚化取决于优化器**能看到什么**，不取决于你写了哪个关键字。同一句 `erased.batch(input)`：对象刚在同一个函数里由 `&Affine` 转出来时，本轮目标码一次表调用都没有；对象来源被 `black_box` 挡住时，本轮保留了一条间接尾跳转。要否定「这里有去虚化」，找一条间接跳转就够了；要肯定「所有 `dyn` 都会被消解」，得给每个调用点分别拿出产物——本章只对三个具体函数这么做。
:::

### 5.4.1 本地构造对象可以保留来源

一个函数先拿到`&Affine`。
在函数内部将它转成`&dyn Kernel`。
随后立即调用 batch。
如果中间没有让来源变得不可知，优化器可以知道目标实现。
源码使用 dyn 不意味着最终一定有间接调用。

实验函数`visible_dynamic`就是这样的场景。
它被标为 inline(never)，保留一个可定位外层符号。
但这个属性没有阻止函数体内部的优化。
内部 erased.batch 仍可直接消解。
应区分「外层不内联」和「内部不优化」。

::: def 定义 5.4.1 · 去虚化 devirtualization {#def-5.4.1}

**去虚化**（devirtualization）指优化器在编译期已经能确定「这个动态调用只会去一个目标」，于是把查表跳转换成直接调用，甚至把目标整个展开进调用者。它的条件不是语法，而是**信息**：目标集合能收敛到一个，并且优化器有权看到这一事实。`inline(never)` 约束的是「本函数要不要被并入调用方」，不约束函数体内部做什么——本轮 `visible_dynamic` 正是外层保留符号、内部照样消解（见[@ex-5.4.1]）。

:::

### 5.4.2 隐藏来源的对照

`dynamic_batch`接受一个已经擦除的引用。
入口将该对象经过 black_box。
被测函数无法只从形参静态认定实现是 Affine。
因此本轮保留了方法表加载与间接尾跳转。
这是一种刻意控制可见性的夹具。

black_box 不模拟所有真实插件系统。
它只是给出一条保守的优化边界。
不能把它的行为称为内存同步屏障。
也不能把它当成防止所有优化的形式证明。
仍需要检查产物。

::: def 定义 5.4.2 · 优化可见性 optimization visibility {#def-5.4.2}

**优化可见性**指在某个编译边界内，优化器**能够看到**的关于程序的事实有哪些：具体类型、字段的常量值、对象的唯一来源、调用目标的完整集合。它不是一根总开关，而是逐条事实、逐次调用的。把函数移到别的 crate、增加一次不透明调用、改变内联策略、开启 LTO，改变的都是这份事实集合，因此去虚化和展开的结果都可能跟着变（对照[@def-5.2.1]：可达性管「要不要生成」，可见性管「能不能化简」）。

:::

::: def 定义 5.4.3 · `black_box` 作为优化边界 {#def-5.4.3}

`std::hint::black_box` 让优化器**对这个值的使用保持悲观**：它把值原样交出去，同时不让编译器假定它仍是某个具体来源。本章用它刻意隐藏对象来源，制造一个「信息确实不可见」的对照组。它不是内存同步屏障，也不是对编译器的强制保证，更不能替代产物核验——第 1 章的[@def-1.1.2] 给了它的完整边界，[@def-1.1.1] 说明为什么「结果被观察到」是另一件事。

:::

### 5.4.3 三个实际函数

```rust
pub fn generic_batch<T: Kernel>(kernel: &T, input: &[u64]) -> u64 {
    kernel.batch(input)
}

#[inline(never)]
pub fn dynamic_items(kernel: &dyn Kernel, input: &[u64]) -> u64 {
    input
        .iter()
        .map(|&v| kernel.step(v))
        .fold(0, u64::wrapping_add)
}

#[inline(never)]
pub fn dynamic_batch(kernel: &dyn Kernel, input: &[u64]) -> u64 {
    kernel.batch(input)
}

#[inline(never)]
pub fn visible_dynamic(kernel: &Affine, input: &[u64]) -> u64 {
    let erased: &dyn Kernel = kernel;
    erased.batch(input)
}
```

这三者使用同一方法集合。
前两个的差异主要在动态边界放在循环里面还是外面。
第三个还改变了调用目标是否能直接恢复。
这些是三个独立概念。
后面的两个 benchmark 分别控制其中一部分。

::: ex 例 5.4.1 · 四个调用点各会不会被消解 {#ex-5.4.1}

就 5.4.3 的四个函数，逐个说明本轮产物里有没有留下动态查找，并写出依据的是哪一条可见事实。

::: sol 解答

`generic_batch`：形参是 `&T`，目标在编译期就定了；本轮它的 `Affine` 实例被直接内联进调用方，产物里没有独立的泛型符号——这是[@def-5.1.3] 的单态化与[@def-5.4.2] 的可见性共同作用的结果。`dynamic_items`：目标只能从元数据取，且调用点写在循环里，于是每元素一次 `blr x23`（摘录在 5.3.3）。`dynamic_batch`：目标同样来自表，但只取一次，随后 `br x4` 是间接尾跳转，业务在具体实现里继续跑完 16384 个元素。`visible_dynamic`：形参是 `&Affine`，`&dyn Kernel` 在函数内部才出现，来源没有被不透明处理，所以内部一次表调用都不剩。注意它的 `inline(never)` 只保证外层符号可定位，并没有妨碍这一步（[@def-5.4.1]）。

:::

### 5.4.4 本轮代码生成对照

| 函数 | 实际保留的调用形态 | 业务循环在哪里 | 能支持的结论 |
|:--|:--|:--|:--|
| dynamic_items | 循环内 blr | 擦除调用方内 | 每元素仍有间接调用 |
| dynamic_batch | 加载目标后 br | 具体 batch 实现内 | 每批一次动态进入 |
| visible_dynamic | 内部无 vtable 调用 | 本函数内展开 | 本地来源使去虚化成立 |
| generic_batch 的 Affine 实例 | lib 单元里没有它的机器码（`compiler_lab-55987aab45b3e67f.s` 里 0 命中，只有 `.mir` 有定义）| 单态化发生在调用方那侧，本归档没留调用方反汇编 | 泛型实例不在 lib 层留独立符号；「到底有没有内联进调用方」本章未采集 |

`dynamic_batch`的真实主体很短。

```asm
ldr x4, [x1, #32]
mov x1, x2
mov x2, x3
br x4
```

这是一段尾调用形式的间接分派。
不是返回之前循环处理每个输入元素。
其目标 batch 实现仍会执行全部工作。
短入口不能被解释成整个业务只有四条指令。
必须继续追踪真实目标。

这张表是[@ex-5.4.1] 的核对结果，也是 5.5 与 5.6 两组计时数字的解释入口：表里那一列「业务循环在哪里」决定了[@def-5.1.2] 的粒度到底落在哪个数量级上。

### 5.4.5 看见 vector.body 不一定看见 SIMD

**SIMD**（single instruction, multiple data，单指令多数据）指一条指令同时处理多个数据元素。判断「有没有用上它」，看的是操作数类型和最终指令，不是中间阶段的名字。

`visible_dynamic`的 LLVM IR 中存在名为 vector.body 的块。
但本轮该块包含多路标量 i64 乘加与旋转。
目标码也主要使用标量寄存器（CPU 内部最快取用的小存储格）展开。
不能仅凭块名断言使用了 SIMD。
第6章会给出确实含向量类型与向量加法的内核。

这个区别很有教学价值。
优化器可能进行交错、展开或标量化。
一个中间阶段的名字不等于最终硬件执行宽度。
要核验操作数类型与本机目标码。
避免把任何「循环被处理了」都称为 SIMD 加速。

::: ex 例 5.4.2 · 一个块名能不能算证据 {#ex-5.4.2}

有人在评审里贴出 IR 片段，指出循环已经进了 `vector.body` 块，据此声称这个内核「向量化了」（即一条 CPU 指令同时处理多个数）。按本节说明这句话缺了哪一步，并写出本节的核对方式。

::: sol 解答

缺的是操作数类型与目标码这一层。IR 里出现叫 `vector.body` 的块只说明优化器按向量化流程处理过这个循环；本轮该块里的乘加与旋转是多路**标量** `i64` 操作，目标码也主要用标量寄存器展开，所以不能写「用了 SIMD」。正确顺序是：先确认 IR 中的操作数类型是不是向量类型，再看本机目标码里有没有对应的向量指令——[@def-1.3.1] 的分层观察在这里同样成立：中间表示与最终产物各支持各的结论，不能互相替代（体积口径的同款错误见[@def-5.2.3]）。

:::

### 5.4.6 去虚化也不是永久属性

移动函数到别的 crate 可能改变可见性。
改变内联策略可能改变常量传播。
增加一次黑盒外部调用可能隐藏来源。
LTO 又可能恢复某些跨模块事实。
这些变化都需要固定版本观察。

因此代码评审不能只要求「使用泛型而不要 dyn」。
应该要求明确热点边界、调用粒度与可达类型集合。
如果一个方法每批只调用一次，内部已充分优化，改写收益可能很小。
若每元素都跨不透明边界，小方法也可能阻断更大的优化机会。
这比给 dyn 统一贴快慢标签更准确。

::: think 思考 · 「这一版没有虚调用，所以以后也不会有」 {#think-5.4.1}

读完 `visible_dynamic` 的产物后，团队把「本模块的 `dyn` 都会被去虚化」写进了性能规约，之后不再复查。这个前提在哪里被绕过？

::: sol 解答

被绕过的是「固定版本观察」这条。去虚化依赖[@def-5.4.2] 的事实集合，而事实集合会随改动漂移：把函数移到别的 crate、加一次 `black_box`、调整内联属性、换工具链，都可能让同一句调用重新变成间接跳转；反过来，LTO 也可能恢复某些跨模块事实。规约里能写的是「本次构建的目标码在循环里没有间接调用，附产物指纹」，而不是给未来版本作担保——这与[@def-1.7.3] 区分探索性与确认性实验是同一条纪律，只是对象从计时换成了代码形态。

:::

:::

::: method 判定流程 · 评审一次擦除调用要不要改

1. **定粒度**：这个方法每批进入一次，还是每元素一次（[@def-5.1.2]）？前者通常已经在具体实现里跑完业务。
2. **查来源**：对象在同一个函数里由具体引用转成，还是从模块外拿进来的（[@def-5.4.2]）？
3. **看产物**：循环体内还有没有间接跳转？表加载在循环内还是循环外（[@ex-5.4.1]）？
4. **估摊薄**：一次进入被多少个元素摊薄，批大小接近业务真实值吗（[@def-5.6.2]）？
5. **才谈改写**：前四步指向「热点上有实际代价」再动手，改完重跑同一套产物核对与计时。

:::

### 5.4.7 小结与常见错误

**小结。**① 去虚化的条件是信息，不是关键字（[@def-5.4.1]）；② `inline(never)` 管外层符号，管不到函数体内部（[@ex-5.4.1]）；③ `black_box` 给出一条保守的优化边界，但不是同步屏障（[@def-5.4.3]）；④ 中间阶段的名字不能当硬件宽度的证据（[@ex-5.4.2]）；⑤ 结论绑定固定版本的产物，改动后要重核（[@think-5.4.1]）。下一节 [5.5 benchmark 一：每元素分派与每批分派](#sec-cpp-rust.2.5.5) 把粒度差异变成一个可核对的数字。

::: errata 常见错误清单（5.4 节）

E-a **按 `dyn` 关键字断言必有间接调用。**本轮 `visible_dynamic` 内部一次都没有（[@def-5.4.1]）。

E-b **把 `inline(never)` 当成「内部也不优化」。**两个约束作用在不同层（[@ex-5.4.1]）。

E-c **把 `black_box` 说成内存同步屏障。**它只是尽力而为的优化提示（[@def-5.4.3]）。

E-d **由 IR 块名宣布 SIMD。**要核对操作数类型与目标码（[@ex-5.4.2]）。

E-e **把四条指令的短入口当成整个业务。**真正的循环在具体 `batch` 实现里（5.4.4）。

E-f **给未来版本担保去虚化。**可见性随构建漂移，要固定版本重测（[@think-5.4.1]）。

:::

::: method 即时自测 · 5.4

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　给出去虚化的定义，并写出它成立需要的两类条件。

::: sol 第 1 题答案
去虚化是优化器在编译期确定动态调用只有一个目标，从而把查表跳转换成直接调用或展开。条件一是目标集合收敛到一个，二是优化器有权看到这条事实。对应[@def-5.4.1] 与[@def-5.4.2]。
:::

**第 2 题 · 辨析**　`visible_dynamic` 和 `dynamic_batch` 都调用了 `erased.batch(input)`。为什么一个内部没有表调用、一个有？

::: sol 第 2 题答案
差别在对象来源是否可见：前者形参是 `&Affine`，擦除发生在函数体内；后者的擦除引用从外面进来，还经过 `black_box`（[@def-5.4.3]），实现身份无法从形参静态认定，于是保留加载与间接尾跳转。见[@ex-5.4.1]。
:::

**第 3 题 · 应用**　线上一次重构后，原本「不该有虚调用」的热点里出现了 `blr`。给出两条最可能的可见性变化。

::: sol 第 3 题答案
① 被调函数或对象构造被移到了另一个 crate，目标集合不再收敛（[@def-5.4.2]）；② 新增了一次不透明处理（`black_box`、外部回调或跨库边界）把来源挡住（对照 5.4.2 的夹具）。两条都要用同一口径重新取目标码来确认，不能只读签名（[@def-5.4.1]）。
:::

**第 4 题 · 迁移**　有人提议「为了消灭虚调用，把 `dynamic_batch` 的形参全改成泛型」。按本节说明这个改动可能的净效果与验证顺序。

::: sol 第 4 题答案
净效果不确定：泛型会把类型事实交给单态化，实例数与`__text`可能上升（[@def-5.2.1]），而每批一次的动态进入本来就被摊薄（[@def-5.6.2]）。验证顺序应是：先确认热点里真有循环内的间接调用（[@ex-5.4.1]），再改，然后同构建同时对比产物与[@def-5.5.1] 的批均值，并检查体积代价。没有这两项就不该声称收益。

## 5.5 benchmark 一：每元素分派与每批分派 {#sec-cpp-rust.2.5.5}

本节回答一个问题：**同样的 16384 个元素、同样的算术语义，只把动态边界从每批挪到每元素，代价会怎么变，这个差值又能说明什么？**

::: preview 先抓住一件事

三个 case 的业务完全相同，唯一被设计改变的是[@def-5.5.2]：`generic` 编译期定目标，`dyn_batch` 每批动态进入一次，`dyn_item` 每元素动态进入一次。本轮结果是 generic 0.158334、dyn_batch 0.156428、dyn_item 0.647618 ns/元素——差距出现在逐元素那一行，量级约 4.1 倍。要肯定「这就是动态分派唯一造成的差别」，需要一个只改变跳转、其余优化完全相同的实验，本轮没有构造它；这张表能支持的是「粒度改变后的总体代码效果」。
:::

### 5.5.1 三个 case 的共同业务

入口是`src/bin/dispatch_grain.rs`。
输入含 16384 个 u64。
参数固定为 multiplier=17，increment=29。
所有 case 执行同一 wrapping 乘加、旋转和归约。
参考结果由入口独立表达式先算出。

第一种 case 用泛型调用 batch。
第二种 case 在循环中对每个元素调用 dyn step。
第三种 case 只动态调用一次 batch。
第三种在具体实现内部仍能解析 step。
所以它并不是把逐元素动态开销除以批大小那么简单。

::: def 定义 5.5.2 · 每元素分派与每批分派 {#def-5.5.2}

**每元素分派**指热循环里每个元素都跨过一次动态调用边界；**每批分派**指一整批只在开头跨过一次，之后的循环在具体实现内部跑。两者是[@def-5.1.2] 的两种取值，也是本实验唯一被设计改变的量。它们不等价，也不能靠「把逐元素的动态开销除以批大小」互相换算——[@def-5.4.1] 说明每批那一次往往能被摊薄，而每元素那一次还会顺带阻断跨边界的展开与归约。

:::

### 5.5.2 完整入口

```rust
use compiler_lab::{
    Affine, Case, Kernel, dynamic_batch, dynamic_items, generic_batch, input_data, measure,
};
use std::hint::black_box;
fn main() {
    let input = input_data(16384);
    let kernel = Affine {
        multiplier: 17,
        increment: 29,
    };
    let expected = input
        .iter()
        .map(|&v| v.wrapping_mul(17).wrapping_add(29).rotate_left(7))
        .fold(0, u64::wrapping_add);
    let erased: &dyn Kernel = black_box(&kernel);
    let mut cases = [
        Case {
            name: "generic",
            run: Box::new(|| generic_batch(black_box(&kernel), black_box(&input))),
            expected,
        },
        Case {
            name: "dyn_item",
            run: Box::new(|| dynamic_items(black_box(erased), black_box(&input))),
            expected,
        },
        Case {
            name: "dyn_batch",
            run: Box::new(|| dynamic_batch(black_box(erased), black_box(&input))),
            expected,
        },
    ];
    measure(&mut cases, input.len());
}
```

Affine 在栈上创建。
erased 只是借用它。
没有为 16384 个输入分别创建 Box。
也没有按元素创建新的 trait 对象。
因此本实验不混入对象分配与追逐异构对象位置的成本。

### 5.5.3 计时责任表

| 阶段 | generic | dyn_item | dyn_batch |
|:--|:--|:--|:--|
| 输入构造 | 不计时 | 不计时 | 不计时 |
| 对象构造 | 不计时 | 不计时 | 不计时 |
| 外层 case 闭包调用 | 计时 | 计时 | 计时 |
| 元素计算 | 计时 | 计时 | 计时 |
| 每元素间接调用 | 本轮无 | 本轮有 | batch 内本轮无 |
| 每批间接进入业务 | 依内联 | 有外层夹具 | 本轮有 |
| checksum 验证 | 批后 | 批后 | 批后 |

不能将 dyn_item 的全部差值归给跳转指令本身。
跨调用边界的内联、展开、归约调度也会变化。
本轮没有构造一个保持所有其他优化完全相同的单条跳转实验。
测到的是接口粒度改变后的总体代码效果。
这种效果正是实际 API 决策常常需要关注的对象。

::: def 定义 5.5.3 · 计时集合 timing set {#def-5.5.3}

**计时集合**指一次批次的耗时里被算进去的阶段。本实验把输入构造、对象构造和 case 闭包的 `Box` 都放在计时之外，只把「外层闭包调用 + 元素计算 + 批后校验」算进去；上一张表的每一行就是在声明某件事属于哪一侧。三个 case 的计时集合一致，差值才可解释——这与[@def-1.1.3] 要求先固定实验契约是同一件事。

:::

### 5.5.4 正式结果

单位为 ns/输入元素。
每个 case 都至少预热 500ms。
随后记录 21 个归一化批时间。

::: def 定义 5.5.1 · 批均值 ns/输入元素 batch mean {#def-5.5.1}

**批均值**是「一批的墙钟耗时 ÷（重复数 × 输入元素数）」，单位是 ns/输入元素。它回答聚合吞吐：处理一个元素平均摊到多少时间。它不回答单个元素、单个请求的延迟。本章的 p50 与 p99 是 21 个批均值上的 nearest-rank 分位数（口径见[@def-1.5.2]），所以它们仍是**批**的分布而不是请求的分布；这个区别在 5.5.6 直接决定能写哪些结论。

:::

| case | mean | N-1 sd | 批 p50 | 批 p99 |
|:--|--:|--:|--:|--:|
| generic | 0.158334 | 0.008248 | 0.156409 | 0.194214 |
| dyn_item | 0.647618 | 0.088345 | 0.694790 | 0.709374 |
| dyn_batch | 0.156428 | 0.004677 | 0.155254 | 0.176579 |

dyn_item 在本轮明显更慢。
这与其循环内间接调用及不可跨调用展开的产物相容。
dyn_batch 与 generic 的本轮均值接近。
不能根据约千分之一纳秒量级的均值差写出「动态分派普遍更快」的标题。
这种差异还处在桌面微基准的小波动范围内。

::: ex 例 5.5.1 · 这三行数字分别支持什么 {#ex-5.5.1}

① `dyn_item` 比 `generic` 慢 0.489284 ns/元素，这笔差值能全部记成「一次间接跳转的价格」吗？② `dyn_batch` 的均值比 `generic` 低 0.001906，能写「动态分派更快」吗？③ `dyn_item` 的均值 0.647618 比它自己的 p50 0.694790 还低，这说明了什么？

::: sol 解答

① 不能。5.5.3 已经声明本轮没有构造「只改跳转、其余优化不变」的实验：跨调用边界的内联、展开与归约调度一起变了，[@def-5.4.1] 那一层的代码形态也不同。能说的是「粒度从每批改成每元素之后，本轮总体批均值高了约 4.1 倍」。② 不能。0.001906 比 `generic` 自己的 N-1 标准差 0.008248 和 `dyn_batch` 的 0.004677 都小，而本轮没有为这三个数计算区间，方向不可判定；按[@def-1.7.2] 只能记成「证据不足」。③ 说明 21 个批均值里有若干明显偏快的批把平均数拉到中位数以下，也说明 `dyn_item` 的运行条件波动比另两个 case 大（0.088345 对 0.008248）。这正是[@def-1.5.2] 要求均值与分位数连着读的原因。

:::

:::

::: think 思考 · 「三个 case 的 checksum 都相同，所以差值必然来自分派」 {#think-5.5.1}

每个 case 的批结果都与入口独立算出的 `expected` 相等。这是否足以把 0.489284 归因给动态分派本身？

::: sol 解答

不足以归因，但它是比较成立的前提。校验相同只确立「三个 case 算的是同一件事」，也就是[@def-1.6.1] 意义上的等价工作比较；它不控制代码形态。粒度改变顺带改变了内联、展开与归约调度（5.5.3），产物对照里 `dynamic_items` 的业务循环在擦除调用方内、`dynamic_batch` 的在具体实现内（5.4.4），这两句都不是「只有跳转不同」。要把差值归给一条跳转，需要新增保持其余优化不变的对照实验——本轮没有做，所以只能在总体效果这一层陈述，并且不报没有计算的显著性（[@def-1.4.2] 的配对在这里也没有做，本轮只报同一 case 的批分布）。

:::

:::

### 5.5.5 这一结果支持的设计

运行时选择策略时，可以先选择批处理对象。
把重复的同类元素留在一次具体 batch 内。
这样保留扩展性，也给实现内部充分优化空间。
它不要求知道所有未来类型。
更不需要手工解析 vtable。

当 batch 较小时，外层分派与夹具开销更难摊薄。
当单个元素计算很重时，逐元素分派比例也可能下降。
这两种方向本轮没有单独扫描。
本章不提供「最小批大小永远是某个常数」的建议。
应该根据真实工作量和延迟预算做粒度选择。

::: ex 例 5.5.2 · 批只有 8 个元素时能不能照抄这张表 {#ex-5.5.2}

某服务的真实批次是 8 个元素。有人打算直接用本表：「按 `dyn_batch` 的 0.156428 ns/元素报价，比 `dyn_item` 便宜 4 倍」。① 这句话哪里越界了？② 要给出可用的数字，实验要怎么改？③ 本轮有没有小批量的数据？

::: sol 解答

① 单位越界。0.156428 是 16384 个元素摊薄之后的批均值（[@def-5.5.1]），一次进入的固定成本在里面只占极小比例；批长度换成 8，同样的固定成本除以 8，两个 case 的比值就不再是 4.1。② 要按[@def-1.1.3] 重建实验：把批长度作为显式因素扫描，保持总工作量与参考语义不变，逐档重新取批均值，并把凑批等待放进系统夹具（5.5.6）。③ 没有。本轮只跑了 16384 一种批长度，小批量的数字**本节没有采集**，所以本章不提供「最小批大小是某个常数」的建议。

:::

:::

::: method 判定流程 · 粒度该放在哪一层

1. **问业务**：一批之内的策略会不会变？会变就不能用每批粒度（对照[@ex-5.6.2]）。
2. **数次数**：热循环里跨边界的调用是每元素还是每批（[@def-5.5.2]）。
3. **看摊薄**：一次进入被多少个元素摊薄，批长度是否接近真实值（[@def-5.6.2]、[@ex-5.5.2]）。
4. **查产物**：确认 `batch` 内部真的把 `step` 解析掉了，别只看签名（[@ex-5.4.1]）。
5. **定预算**：把「每请求最多几次动态边界」写成可验收的约束，用[@def-1.7.1] 的预算而不是本轮表格做判定。

:::

### 5.5.6 吞吐不等于低延迟

大批量可以降低每元素聚合成本。
但等待凑批可能延长单请求响应时间。
一个 batch 还可能长期占住执行线程。
对于交互系统，需要同时设计最大等待与最大批工作量。
本章只测已准备好输入后的计算批次。

因此不能拿本表的 ns/元素直接承诺网络 p99。
表中 p99 是 21 个批均值的 nearest-rank 分位数。
它等于该 case 的最大批均值。
没有采集用户到达、排队或输出延迟。
这些指标需要不同的系统夹具。

这里有一个容易被跳过的等号：**21 个批均值上的 p99 就是最大值**（[@def-1.5.2]）。`dyn_batch` 的 0.176579 是它 21 批里最快到最慢那一端点，不是「99% 请求的体验」；请求级 p99 需要的到达过程、队列与输出观察，本节没有采集。

### 5.5.7 输出验证不是可选项

每次结果都经 black_box 进入批 checksum。
批结束检查与期望值的 wrapping 乘积相等。
测试还覆盖空输入与不整除展开宽度的长度。
即使去虚化很彻底，也不能让整个业务没有可观察结果。
只有速度没有输出观察的 benchmark 容易被删除工作量污染。

这条防线为什么必须在：[@def-1.1.1] 的 `dce_empty` 就是一个全程绿灯、只在解释阶段暴露的假结果——断言通过，工作却没了。擦除与批处理让「结果去哪了」更隐蔽，所以观察边界要写进[@def-5.5.3] 的计时集合里，而不是靠评审记忆。

### 5.5.8 小结与常见错误

**小结。**① 三个 case 只差[@def-5.5.2] 的粒度，业务与参考结果完全相同（[@def-1.6.1]）；② 数字口径是[@def-5.5.1] 的批均值，p50/p99 属于批而不是请求；③ 本轮 `dyn_item` 0.647618 对 `dyn_batch` 0.156428，差值不能全记给跳转（[@ex-5.5.1]）；④ `dyn_batch` 与 `generic` 的 0.001906 之差在本轮属于证据不足；⑤ 换批长度就是换实验，小批量本节没有采集（[@ex-5.5.2]）。下一节 [5.6 benchmark 二：局部已知 dyn 与不透明 dyn](#sec-cpp-rust.2.5.6) 把粒度固定住，只改来源可见性。

::: errata 常见错误清单（5.5 节）

E-a **拿 0.156428 去报任意批长度的成本。**它是 16384 元素摊薄后的批均值（[@def-5.5.1]）。

E-b **把差值全归给一条间接跳转。**内联、展开与归约调度一起变了（[@ex-5.5.1]）。

E-c **由 0.001906 的小数写「动态更快」。**差值小于批间波动，方向未定（[@ex-5.5.1]）。

E-d **把表中 p99 当请求分位数。**它是 21 个批均值的最大点（5.5.6）。

E-e **把对象构造算进批次。**计时集合把构造放在外面，三个 case 才可比（[@def-5.5.3]）。

E-f **只看速度不校验输出。**没有可观察结果的工作可能被整段删除（[@think-5.5.1]）。

:::

## 5.6 benchmark 二：局部已知 dyn 与不透明 dyn {#sec-cpp-rust.2.5.6}

本节回答一个问题：**粒度已经固定在每批之后，来源能不能被优化器看到，还能剩下多少差别？**

::: preview 先抓住一件事

这一组把[@def-5.5.2] 的粒度钉在「每批一次」，只换一个因素：对象的具体来源在被测函数里看不看得见。本轮 `known_dyn` 与 `opaque_dyn` 的均值是 0.156133 与 0.158303 ns/元素，差 0.002170；同一轮归档里的目标码却明确不同——一个内部没有任何表调用，一个保留间接尾跳转。**产物不同、聚合时间接近**，正是本节要教的判断：接近不等于相同，也谈不上谁更快。
:::

### 5.6.1 控制的变量不同

第一个实验比较动态边界的粒度。
第二个实验固定为每批处理。
只改变被测函数是否从具体 Affine 来源构造对象。
known_dyn 进入 visible_dynamic。
opaque_dyn 进入 dynamic_batch。

两者都以引用方式使用同一份参数。
输入长度仍为 16384。
没有加入类型切换、随机策略表或分配。
因此不能把它叫作异构对象混排测试。
它回答的是来源可见性与一次批边界的关系。

::: def 定义 5.6.1 · 来源可见性 source visibility {#def-5.6.1}

**来源可见性**指优化器能不能沿着一次擦除调用往上追到对象的构造处，从而把目标集合收敛到一个实现。它是[@def-5.4.2] 那堆事实里对本节最要紧的一条：`visible_dynamic` 在函数内部把 `&Affine` 转成 `&dyn Kernel`，来源就在眼前；`dynamic_batch` 收到的是已经擦除的引用，而且入口先过了 `black_box`（[@def-5.4.3]）。可见与否是编译期的信息问题，与对象在栈上还是堆上无关（[@def-5.1.4]）。

:::

### 5.6.2 完整入口

```rust
use compiler_lab::{Affine, Case, Kernel, dynamic_batch, input_data, measure, visible_dynamic};
use std::hint::black_box;
fn main() {
    let input = input_data(16384);
    let kernel = Affine {
        multiplier: 17,
        increment: 29,
    };
    let expected = input
        .iter()
        .map(|&v| v.wrapping_mul(17).wrapping_add(29).rotate_left(7))
        .fold(0, u64::wrapping_add);
    let erased: &dyn Kernel = black_box(&kernel);
    let mut cases = [
        Case {
            name: "known_dyn",
            run: Box::new(|| visible_dynamic(black_box(&kernel), black_box(&input))),
            expected,
        },
        Case {
            name: "opaque_dyn",
            run: Box::new(|| dynamic_batch(black_box(erased), black_box(&input))),
            expected,
        },
    ];
    measure(&mut cases, input.len());
}
```

known_dyn 的形参是具体引用。
内部虽然写了 dyn，但来源仍然明确。
opaque_dyn 的对象在外部被 black_box。
被测函数只能按擦除契约处理它。
归档中两种目标码确实不同。

### 5.6.3 正式结果

| case | mean ns/元素 | N-1 sd | 批 p50 | 批 p99 |
|:--|--:|--:|--:|--:|
| known_dyn | 0.156133 | 0.004065 | 0.154657 | 0.167349 |
| opaque_dyn | 0.158303 | 0.004387 | 0.156222 | 0.171070 |

本轮已知来源版本均值略低。
但两者都在一次批处理内完成同样的大量计算。
主要业务循环相似。
一次动态进入被 16384 个元素摊薄。
本章不从这个小差值外推所有服务的收益。

::: def 定义 5.6.2 · 摊薄 amortization {#def-5.6.2}

**摊薄**指把一次与批长度无关的固定成本除以批里的元素数。若一次动态进入的成本是 c，批长 n 个元素，它对每个元素的贡献是 c/n；本轮 n = 16384，所以一次进入在每元素口径里几乎看不见。摊薄成立有两个前提：这笔成本确实与 n 无关，以及[@def-5.5.3] 的计时集合里没有被夹带别的工作。n 变小时贡献按 1/n 上升——这就是 5.5.5 拒绝给出「最小批大小常数」的原因（[@ex-5.5.2]）。

:::

::: ex 例 5.6.1 · 0.002170 这个差值能说什么 {#ex-5.6.1}

两行均值之差是 0.002170 ns/元素。① 能不能写成「去虚化让每个元素快 0.00217 纳秒」？② 能不能写成「动态分派有约 1.4% 的稳定代价」？③ 乘回 16384 得到什么，这个数有什么资格？

::: sol 解答

① 不能。0.002170 小于两个 case 各自的 N-1 标准差（0.004065 与 0.004387），本轮既没有算区间（[@def-1.6.2]）也没做配对（[@def-1.4.2]），方向本身不可判定；按[@def-1.7.2] 属于「证据不足」。② 也不能。「1.4%」把一个点估计当成了比例承诺，而且差值来源不止那一次进入——`known_dyn` 的产物里连表加载都没有，两条路径的内联范围也不同（5.6.4）。③ 0.002170 × 16384 ≈ 36 纳秒，含义是「一次完整遍历 16384 个元素上的均值差」。它只能用来检查量级是否合理：本轮没有单独测量任何一次跳转，所以无权给它定价（[@def-5.6.2] 的 c 在本章是未知的）。

:::

:::

### 5.6.4 代码证据比关键字统计可靠

known_dyn 内部没有保留 vtable 调用。
其目标码直接加载两个参数字段。
随后执行展开的计算循环。
opaque_dyn 保留间接尾跳转。
后续进入具体 batch 实现。

所以「看到 dyn 就有虚调用」在这里是错误的。
反过来，「看到泛型就没有间接调用」也不成立。
泛型参数本身可以是函数指针或包装了 trait 对象的类型。
泛型层能够静态选择包装器，并不意味着包装器内部没有动态行为。
需要追到真正的热点操作。

这两句合起来就是[@def-5.4.1] 的操作性版本：关键字既不是充分条件，也不是必要条件。`T` 可以是 `fn(&[u64]) -> u64` 这样的函数指针类型，也可以是内部装着 `Box<dyn Kernel>` 的包装结构——静态选择的是包装器，动态行为还在包装器里面（[@ex-5.4.1] 的四个函数就是四种不同组合）。

### 5.6.5 不能从接近的耗时推断没有虚调用

如果一批工作足够大，一次动态分派可能被摊薄。
两个 case 很接近，不代表两者目标码相同。
如果编译器恰好合并了函数，目标码相同也不代表语言要求它合并。
性能表与产物表应该互相检查，而不是互相替代。
本轮就是「目标码不同，聚合时间接近」的具体例子。

::: think 思考 · 「时间接近就说明编译器已经帮我们做了」 {#think-5.6.1}

看到 0.156133 与 0.158303 只差千分之几，有人结论：「反正动态分派在这里等于免费，编译器会处理，接口随便写。」这条推理绕过了哪个前提？

::: sol 解答

绕过了「批长 16384」这个前提。接近是[@def-5.6.2] 的摊薄结果，不是分派消失：`opaque_dyn` 的产物里那条间接尾跳转仍然存在，只是被摊到看不见。把批长改成 8，同一个进入的每元素贡献按 1/n 上升（[@ex-5.5.2]）；把每元素一次的 `step` 暴露出来，就是本轮 0.647618 那条慢路径（[@ex-5.5.1]）。所以「接口随便写」不成立——能被摊薄的是这一次进入，不能被摊薄的是接口选择的粒度（[@ex-5.6.2]）。

:::

:::

### 5.6.6 扩展测试要先提出具体问题

若关心很多不同策略混排，应增加策略选择序列。
需要记录序列是否固定、随机或与数据相关。
还要记录对象存储布局与访问顺序。
否则测到的可能主要是缓存位置而不是分派。
本轮没有声称测量这些因素。

若关心很小 batch，应扫描批大小并保持总工作量可比较。
若关心不可预测目标，应保留目标分布。
若关心构建时间，应分开记录单态生成与链接。
每一个问题都需要相应对照。
不能从同一张两行表生成所有结论。

::: method 判定流程 · 把两行表扩成一组可信实验

1. **先写问题**：一句话说明「什么因素变动时，哪个指标怎么变」，并写出预期能推翻它的结果。
2. **再定因素层级**：批长度、策略序列、目标分布、对象布局各是一根独立轴；一根轴一次只动它（[@def-1.1.3]）。
3. **补对照**：混排需要策略序列与存储布局的记录（5.6.6）；小批需要保持总工作量可比的扫描（[@ex-5.5.2]）。
4. **限定结论范围**：本轮没有采集的轴，一律写「本节没有采集」，不借用两行表外推（[@def-1.7.3]）。

:::

### 5.6.7 安全的性能回退案例

把 batch 接口重构成只暴露 step，仍可能完全通过功能测试。
但上层循环变成了每元素动态调用。
这正是第一个实验中实际执行的慢路径。
没有 UB，也没有数据竞争。
回归发生在优化边界，而不是内存安全边界。

修复不一定是全局改成泛型。
恢复 batch 方法就能在本轮保留动态扩展性并消除热点中的逐元素动态边界。
当然，业务如果需要每元素切换实现，这种修复会改变需求。
必须先确认策略是否真的能在一批内保持不变。
API 粒度必须忠于业务，而非只追求表格更漂亮。

::: ex 例 5.6.2 · 这次重构算不算安全变更 {#ex-5.6.2}

一次评审的 diff 只做了一件事：从 trait 里删掉 `batch`，只留下 `step`，调用方改写成显式循环。测试全绿，没有 `unsafe`，没有新增依赖。① 用本节的数字说明这次改动把什么变了。② 什么情况下它是正确的设计决策？③ 恢复 `batch` 需要注意什么？

::: sol 解答

① 每个元素的动态边界从「无」变成「一次」。本轮 16384 个元素上，每批一次是 0.156428 ns/元素，每元素一次是 0.647618（[@ex-5.5.1]）；产物层面循环里多出 `blr x23`（5.3.3），跨边界的展开与归约也一起消失。功能测试看不见它，因为[@def-1.6.1] 的等价性成立——语义完全没变（[@think-5.6.1]）。② 当业务确实需要每元素换策略时，这是忠实表达需求，不该为了表格好看而伪造批不变性。③ 恢复 `batch` 前必须确认策略在一批内不变，否则等于把选择的时机偷偷挪到批边界（[@def-5.5.2]），那是改需求而不是优化。

## 5.7 可擦除接口、有限策略与失败测试 {#sec-cpp-rust.2.5.7}

本节回答一个问题：**哪些接口能装进 trait 对象、哪些装不进去，装不进去时业务上还有哪些替代？**

::: preview 先抓住一件事

trait 对象要能在一张有限的表里给每个方法找到一个槽位。带任意类型参数的方法 `fn apply<T>` 代表潜在无限组实例，槽位排不完，所以编译器在形成 `&dyn Bad` 时报 E0038。这不是风格偏好，而是[@def-5.3.2] 那张表的容量问题。判断顺序应当是：先问「对象调用者需要知道什么」，再决定用 `dyn`、`enum` 还是保留泛型——性能考量排在接口能不能成立之后。
:::

### 5.7.1 dyn 兼容性限制不是任意障碍

trait 对象需要能通过有限元数据调用方法。
一个带任意类型参数的方法代表潜在无限组实例。
它无法简单放进一个固定有限方法表。
返回裸 Self 也需要调用者知道具体大小。
这解释了某些 dyn 兼容性限制的工程动机。

本轮拒绝测试使用泛型方法。
编译器在形成无效对象类型时报告 E0038。
没有通过不安全强转去构造一个假的 vtable。
失败输入只参与编译，不参与执行。

::: def 定义 5.7.1 · dyn 兼容性 dyn compatibility {#def-5.7.1}

一个 trait 是 **dyn 兼容**的（dyn-compatible，旧称「对象安全」），当它可供对象调用的方法都能放进一张有限的方法表：接收者形式受限、方法自身不再引入新的类型参数、返回类型不需要调用者知道隐藏尺寸。`Kernel` 满足这个条件（`step` 与 `batch` 只吃 `Self` 和已知类型），`Bad { fn apply<T>(&self, value: T); }` 不满足——`T` 有无穷多种，槽位就排不完。术语从「对象安全」换成「dyn 兼容性」，约束本身没有变化。

:::

```rust
trait Bad { fn apply<T>(&self, value: T); } fn accept(_: &dyn Bad) {} fn main() {}
```

旧材料常用「对象安全」一词。
新文档也使用「dyn 兼容性」。
术语变化不意味着可以忽略方法具体约束。
给个别方法加`where Self: Sized`可以把它们排除在对象调用外。
但不能让对象调用者凭空知道隐藏返回值的尺寸。

::: ex 例 5.7.1 · E0038 应该修哪一边 {#ex-5.7.1}

上面对 `trait Bad` 的输入让编译器报 E0038。① 错误发生在哪一步——形成对象类型，还是真的调用它？② 给出三种修法，各自改变了什么？

::: sol 解答

① 在**构造对象类型** `&dyn Bad` 的那一刻，不需要任何调用发生。所以这一类失败输入只进编译、不进执行，不会污染任何计时数字（5.7.1）。② 三种：(a) 把 `T` 换成具体类型或换成关联类型，让方法表有限——接口收紧了，调用点失去任意类型输入；(b) 给这个方法加 `where Self: Sized`，`dyn Bad` 就能成形，代价是对象路径少一个方法；(c) 放弃 `dyn`、保留泛型，让调用点继续掌握类型，此时代价转成[@def-5.1.3] 的实例数量，按 5.2 的口径去数。没有第四种「用 `unsafe` 强转造一个假表」的选项：那等于把编译期检查换成未定义行为（[@def-1.1.1] 的观察纪律在这里同样适用）。

:::

:::

### 5.7.2 关联类型可以成为擦除接口的一部分

若处理链只输出一种固定元素类型，可以将关联类型约束具体化。
例如迭代接口擦除为某个固定 Item。
这与「任意泛型方法」不是同一回事。
对象使用方仍知道输出的具体类型。
不必因使用关联类型就自动放弃 dyn。

如果多个实现需要不同输出表示，应先决定业务统一边界。
可以统一为 enum、公共结果结构或显式拥有者。
也可以保留泛型边界，让调用点继续掌握类型。
不要为了让接口能装进 Vec，就把所有结果转成无结构字符串。
类型擦除应有明确目的。

区别在「谁还掌握类型事实」：`<T = 具体类型>` 或关联类型固定之后，对象调用方仍然知道输出是什么，[@def-5.7.1] 的表也仍然有限；而 `fn apply<T>` 是把无穷多种可能压进一张有限表。擦除本身不是目标，别为了让 `Vec` 收下就丢掉结果结构（对照[@def-5.1.4]）。

### 5.7.3 enum 是有限集合的另一种工具

策略集合完全固定时，enum 可以表达所有变体。
match 分支里可获得具体实现。
连续存储可能减少对象分配。
但 enum 的大小受最大变体、对齐与判别表示影响。
不能把它称为一定更小的 trait 对象替代物。

若各变体尺寸悬殊，连续 enum 数组可能浪费空间。
若变体很多，分支与生成代码又可能增大。
若外部实现必须开放扩展，封闭 enum 可能不合适。
本章没有对 enum 混排做正式计时。
不以「通常」替代缺失的测量。

::: def 定义 5.7.2 · 封闭策略集 enum 策略 {#def-5.7.2}

**enum 策略**是把全部可能实现写进一个封闭的枚举：每个变体携带自己那份数据，`match` 的每个分支里类型重新变具体，通常还能[@def-5.4.1] 掉一层查找。它与 `dyn` 的差别不是快慢，而是**扩展方向**：enum 要求一次性知道所有变体，`dyn` 允许后来者（[@def-5.1.4]）。代价也不同——enum 的每个槽要按最大变体与对齐来留空间，而 `&dyn Kernel` 只是两个机器字（5.3.2 的表）。

:::

本章没有对 enum 混排计时，所以这里只给出结构对比，不写「enum 更省」或「分支更贵」：那两组数字**本节没有采集**。要立这条结论，需要新增变体尺寸分布、混排序列与缓存位置的实验（[@ex-5.5.2] 的批长扫描是同类设计）。

### 5.7.4 不要为减少实例牺牲所有类型信息

一个有用的折中是泛型解析、非泛型执行。
外层接受不同来源或配置类型。
转换成统一的运行计划。
热内核只处理紧凑的计划和数据切片。
这样可以减少重复大内核，又保留输入侧类型安全。

另一个折中是开放对象边界加批方法。
第一个 benchmark 实际验证了这种结构的一种小实例。
这不证明所有库都应提供同名 batch。
但它提醒接口设计者，调用粒度比「是否用了 trait」更具体。
性能需求最好写在契约层，而不是依赖调用者猜测。

::: def 定义 5.7.3 · 泛型解析、非泛型执行 {#def-5.7.3}

这个折中把接口拆成两段：**解析段**保留泛型或 `dyn`，负责接受多种来源、多种配置，产出一份统一的运行计划；**执行段**是非泛型函数，只吃紧凑计划和数据切片。它同时缓解两个问题——[@def-5.2.2] 的大内核实例重复（只生成一份执行段机器码），以及[@def-5.5.2] 的逐元素动态边界（热循环里没有分派）。拆分的边界要画在「与类型无关的那部分计算」上，否则只是把泛型换了个名字。

:::

### 5.7.5 当前稳定版与母本年代差异

两句要分开引。Rust 1.70 时点的限制在第 12 条：本地 PDF 第 103 页原文是「在撰写本文时（截至 Rust 1.70 版本），没有办法从 Shape 向上转型到 Draw」，登记在 `sources/reviews/S08.md` 的 S08/COMPILER-S08-008（页范围 97–105，落点 5.1）。第 19 条那条一线在 PDF 第 169 页，写的是「该功能在正式发布前已在 `#![feature(trait_upcasting)]` 开启，预计在 Rust 1.76 版本发布」，登记为已过时的未来版本预测（`sources/reviews/S08.md` 的 S08-U0024，起始页 164），它不提供 1.70 这个时点。
该历史结论不能原封不动用于本轮 Rust1.99.0。
本轮测试实际把`&dyn Child`转成`&dyn Parent`。
随后调用父 trait 方法并校验输出。
测试已通过。

```rust
trait Parent {
    fn value(&self) -> u64;
}
trait Child: Parent {}
impl Parent for u64 {
    fn value(&self) -> u64 {
        *self
    }
}
impl Child for u64 {}
#[test]
fn current_stable_supports_trait_upcast() {
    let value = 19u64;
    let child: &dyn Child = &value;
    let parent: &dyn Parent = child;
    assert_eq!(parent.value(), 19);
}
```

这并不意味着 vtable 布局成为稳定 ABI。
语言支持某种转换，与应用能够自行解析元数据是不同承诺。
也不意味着每种任意 trait 组合都能相互转换。
必须满足真实的超 trait 关系与相应类型规则。
读旧母本时，时间范围本身就是事实的一部分。

::: ex 例 5.7.2 · 这段测试推翻了什么、没推翻什么 {#ex-5.7.2}

上面这段测试在 Rust 1.99.0 上通过，而母本记录的是 Rust 1.70 时点的限制。① 它推翻了哪句话？② 它没有推翻哪三句话？

::: sol 解答

① 它推翻的是「`&dyn Child` 转不成 `&dyn Parent`」这条**当时**的规则，因此母本的历史结论只能带时间范围引用（5.7.5）。② 它没有推翻：语言支持该转换 ≠ 应用可以自行解析元数据（[@def-5.3.4]）；`Child: Parent` 这种真实超 trait 关系成立 ≠ 任意 trait 组合都能互转；本轮通过 ≠ 未来版本与别的构建仍通过（[@think-5.4.1] 的固定版本观察同理）。测试只回答它跑过的那一次。

### 5.7.6 失败与回归应分层记录

编译失败测试验证不合法接口被拒绝。
输出测试验证不同分派路径计算一致。
性能测试验证粒度变化后的总体成本。
尺寸探针验证生成产物中的节大小。
这些证据各自有边界。

不能因为 E0038 测试通过，就宣布 dyn 路径性能正确。
也不能因为两个 checksum 相同，就宣布对象生命周期正确。
若添加 unsafe 擦除层，还需要额外证明初始化、别名、释放与 panic。
本实验完全使用安全 Rust，避免把这些新风险混进分派问题。

::: think 思考 · 「四类测试都绿了，所以 dyn 接口没问题」 {#think-5.7.1}

E0038 拒绝通过、输出一致、批均值已记录、节大小已测量。有人据此在评审里写「dyn 路径验证完毕」。这个说法绕过了什么？

::: sol 解答

绕过了「各自有边界」这条。四类测试分别支持四类声明：[@def-5.7.1] 的成立、[@def-1.6.1] 的等价工作、[@def-5.5.1] 的批均值口径、[@def-5.2.3] 的体积口径。它们拼不成一句「没问题」，因为「没问题」通常还包含生命周期与线程属性——本节恰好没有测 `Send`/`Sync`、`Arc` 与跨线程场景（5.3.4 明确声明）。要写结论，就得按[@def-1.8.1] 指明每条声明背后是哪一层证据。

::: method 判定流程 · dyn、enum、泛型三选一

1. **扩展性**：实现集合是否由外部代码增加？会 → `dyn`（[@def-5.1.4]）；不会 → 下一题。
2. **能否成立**：方法表放得下吗？放不下（任意 `T`、裸 `Self` 返回）→ 改接口或保留泛型（[@def-5.7.1]、[@ex-5.7.1]）。
3. **粒度**：热路径每元素还是每批跨边界？每元素且策略在一批内不变 → 先加批方法（[@def-5.5.2]），再考虑是否要 `dyn`。
4. **体积**：大内核被多份复制？→ 拆出非泛型执行段（[@def-5.7.3]），并用[@def-5.2.3] 的口径复测。
5. **布局**：变体尺寸悬殊、数量多？→ `enum` 的每槽代价要重新算（[@def-5.7.2]），本章没有这组数字。

### 5.7.7 小结与常见错误

**小结。**① dyn 兼容性是方法表容量问题，不是风格问题（[@def-5.7.1]）；② 关联类型固定后仍可擦除，任意 `T` 不行（5.7.2）；③ `enum` 与 `dyn` 的差别在扩展方向与布局代价（[@def-5.7.2]）；④ 大内核可以用[@def-5.7.3] 拆出来，不必整体泛型化；⑤ 母本结论要带时间范围（[@ex-5.7.2]），证据要分层引用（[@think-5.7.1]）。下一节 [5.8 从采样、统计与构建边界解释结果](#sec-cpp-rust.2.5.8) 把前面所有数字的口径统一说清。

::: errata 常见错误清单（5.7 节）

E-a **把 E0038 当编译器的口味。**它是有限方法表的容量约束（[@def-5.7.1]）。

E-b **用 `unsafe` 强转绕过兼容性限制。**换来的是未定义行为，不是合法对象（[@ex-5.7.1]）。

E-c **称 enum 一定比 trait 对象小。**每槽按最大变体留空间（[@def-5.7.2]）。

E-d **为塞进 `Vec` 把结果转成无结构字符串。**擦除要有明确目的（5.7.2）。

E-e **拿 Rust 1.70 的限制当现行规则。**本轮 1.99.0 的转换测试已通过（[@ex-5.7.2]）。

E-f **一类测试通过就宣布整条路径正确。**证据分层各有各的边界（[@think-5.7.1]）。

::: method 即时自测 · 5.7

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　说出 dyn 兼容性对方法的三条要求，并解释 `fn apply<T>` 为什么违反。

::: sol 第 1 题答案
接收者形式受限、方法不引入新的类型参数、返回类型不需要隐藏尺寸。`apply<T>` 的 `T` 有无穷多种，对应无穷多个实例，一张有限表排不完（[@def-5.7.1]）。
:::

**第 2 题 · 辨析**　「关联类型让 trait 不能擦除」与「泛型方法让 trait 不能擦除」，哪句对？

::: sol 第 2 题答案
都不对，但差别关键：关联类型**被固定成某个具体类型**之后方法表仍然有限，可以擦除；泛型方法每次调用都可能要新实例，表放不下（[@def-5.7.1]、5.7.2）。

:::

**第 3 题 · 应用**　一个插件框架要接受外部 crate 提供的实现，评审要求「改成 enum 去掉 dyn」。给出两条反对理由。

::: sol 第 3 题答案
① enum 是封闭集合，外部无法新增变体，这会改变业务的扩展性（[@def-5.7.2]）；② 性能理由要先看粒度与摊薄：每批一次的动态进入本轮已被摊薄（[@def-5.6.2]），去掉 `dyn` 未必有收益，反而可能增加[@def-5.1.3] 的实例数量。
:::

**第 4 题 · 迁移**　把本章的 `Kernel` 换成「解析配置 → 生成运行计划 → 非泛型热内核」，写出你要重做的三类验证。

::: sol 第 4 题答案
① 等价性：热内核与旧路径对同一输入产出相同 checksum（[@def-1.6.1]）；② 产物：新热内核是否真的一份、循环里有无间接调用（[@ex-5.4.1]）；③ 体积与计时：同一口径复测`__text`（[@def-5.2.3]）与批均值（[@def-5.5.1]）。缺任何一类，[@def-5.7.3] 的收益声明都不成立。
:::

:::

## 5.8 从采样、统计与构建边界解释结果 {#sec-cpp-rust.2.5.8}

本节回答一个问题：**本章那两组 ns/元素 与四行字节数是在什么协议下产生的，哪些句子它们支持、哪些不支持？**

::: preview 先抓住一件事

读性能数字之前先读协议：入口有几个、每个 case 存了几批、归一化除数是什么、构建参数怎么设。本章口径是「每个正式 case 保存 21 个批均值」，所以 p50 与 p99 是**批**的分位数，不是请求的分位数（[@def-1.5.2]）；「差约 4.1 倍」也只能在这份输入与这份构建里读。要否定一条结论，只要指出它依赖的观察不在这份归档里——最典型的一类就是硬件事件：本章没有采集。
:::

### 5.8.1 正式采样的结构

实验包共六个独立入口。
本章占其中两个。
同一入口内各 case 轮转顺序。
每个 case 独立预热至少 500ms。
每个正式 case 保存 21 个原始批次。

共享夹具在第4章给出了完整源码。
本章不复制整段夹具填充篇幅。
完整实现保存在`src/lib.rs::measure`。
每次调用返回值进入 wrapping checksum。
批后与参考结果乘重复数比较。

轮转与独立预热的作用是削弱时间位置与实现之间的混淆（[@def-1.4.1]），预热则把冷启动状态挡在正式批次之外（[@def-1.2.3]）。这两件事在[@def-1.1.3] 的合同里必须先写明，否则表里的数字没有可复核的解释。

### 5.8.2 为何不是单请求分布

每个原始观察都包含多次批内核调用。
归一化除数是重复数乘输入元素数。
p50 和 p99 因而是批均值分位数。
它们不是一个元素或一个请求的独立延迟。
nearest-rank p99 在 21 点样本中就是最大点。

mean 采用算术平均。
sd 采用样本标准差，分母 N-1。
没有删除最慢样本。
没有把不同 case 混成一组标准差。
没有报告未计算的置信区间或 p 值。

::: def 定义 5.8.1 · 批均值分位数 batch-mean quantile {#def-5.8.1}

**批均值分位数**的算法是：先对每一批做一次归一化（批耗时 ÷（重复数 × 输入元素数）），得到 21 个 ns/元素 的数，再把它们排序取 nearest-rank 分位点（口径同[@def-1.5.2]）。它描述批与批之间的波动，不描述元素之间、也不描述请求之间。21 个点上的 p99 恰好是最大值，这不是精度损失，而是定义直接导出的结果——5.5.6 那句「不能承诺网络 p99」就是从这里来的。

:::

把没有算过的量写成结论，是这一节最容易犯的错：本章没有区间（[@def-1.6.2] 属于第 1 章那组配对数据）、没有 p 值、没有配对差值（[@def-1.4.2]）。想套用[@def-1.7.2] 的三态判定，得先补上区间估计，那是另一轮实验。

### 5.8.3 独立 macOS sample

正式计时完成后，脚本另起 dispatch_grain。
`sample`以一毫秒间隔采集一秒。
原始报告保存在`stable-02/macos-sample.txt`。
该运行的 CSV 单独保存在`sample-run.csv`。
它不参与正式表格。

采样中可见 dynamic_items 和 Affine::step。
也可见具体 batch 实现以及泛型路径的闭包计算。
这与逐元素间接边界确实执行相容。
但一秒观察会覆盖预热和 case 切换。
不能据此给出稳定态各 case 的精确 CPU 百分比。

::: ex 例 5.8.1 · 这份 sample 报告能支持哪一句 {#ex-5.8.1}

`stable-02/macos-sample.txt` 里出现了 `dynamic_items` 与 `Affine::step` 的栈帧。① 这句话支持什么声明？② 它能不能用来算各 case 的稳定态 CPU 占比？③ 它能不能证明「`dyn_item` 慢在分支预测失败」？

::: sol 解答

① 支持一条弱声明：**逐元素那条边界确实在执行**——栈里同时出现擦除调用方与 `step`，与 5.3.3 的 `blr x23` 循环相容；这属于[@def-1.3.1] 那类「工作真的发生」的核对。② 不能。这一秒覆盖预热与 case 切换，且是另一次运行（它的 CSV 单独放在 `sample-run.csv`，不进正式表）。③ 不能。栈采样给出的是执行位置的时间归因，不是硬件事件；分支预测失败需要 PMU 计数，本轮没有采集（5.8.4）。

:::

:::

### 5.8.4 不从采样反推硬件事件

sample 是栈采样，不是 Linux perf 的 PMU 事件集。
本轮没有收集 I-cache miss。
没有 BTB 命中率。
没有指令退休数量。
没有固定核心频率或核心 cycle。

因此「间接调用慢」在本章的可检验含义是总体批时间更高。
代码证据同时说明调用边界与优化机会变化。
不能进一步声称差值全部来自分支预测失败。
目标在本轮始终是同一个 Affine，可能并不难预测。
即使预测很好，无法内联也可能是主要区别之一。

::: def 定义 5.8.3 · 证据层次 evidence layer {#def-5.8.3}

本章的证据分四层，每层只支持它能支持的那句话：**编译期拒绝**（[@def-5.7.1] 的 E0038）说明接口能否成立；**输出校验**（[@def-1.6.1]）说明算的是不是同一件事；**静态产物**（目标码、符号列表、`__text` 字节，[@def-5.2.3]）说明代码形态与体积；**计时与采样**（[@def-5.5.1]、[@def-5.8.1]）说明聚合成本与执行位置。跨层的句子必须有跨层的证据：从第三层跳到「缓存命中率」「分支预测失败」这类第四层命题，本轮没有采集，因此一律不写。第 1 章的[@def-1.8.1] 给的是同一套分层交付方式。

:::

### 5.8.5 编译设置必须随结论保存

| 项目 | 本轮设置 | 对解释的影响 |
|:--|:--|:--|
| opt-level | 3 | 不使用 debug 代码比较分派 |
| codegen-units | 1 | 减少分区差异 |
| LTO | false | 主表不是 ThinLTO 结果 |
| debug info | 1 | 允许采样定位部分源码 |
| panic | unwind | 保留相应异常清理策略 |
| target-cpu | 未显式设置 | 不外推为所有 CPU 的最优形态 |

::: def 定义 5.8.2 · 构建配置 build configuration {#def-5.8.2}

**构建配置**指会改变最终代码形态的那组编译设置：opt-level、codegen-units、LTO、debug info、panic 策略与 target-cpu。本章主表用的是上表六项的组合。换掉其中任何一项，[@def-5.4.2] 的可见性事实与[@def-5.2.1] 的可达集合都可能变，产物对照和计时因此都要重取。结论必须与配置同存——否则下一轮构建接手的是一个没人知道自己继承了什么条件的数字。

:::

补充尺寸探针单独使用其记录的 rustc 参数。
它没有替换正式主表的二进制。
正式归档保存了六个可执行文件。
源码与产物指纹分别保存。
不要拿后来重编译的 target 文件覆盖原始测量对象。

### 5.8.6 热调用之外还要列出哪些成本

本轮把对象与输入的构造放在计时外。
这使分派粒度成为一个清楚的问题。
实际组件却可能为每个请求创建对象。
也可能不断分配小型 Box，再把它们存进异构容器。
这些工作必须在系统实验中重新纳入。
不能把本章的热批次结果直接当作完整对象生命周期成本。

一种可靠的实验设计是先列出生命周期阶段。
分别记录解析配置、创建策略、执行批次与销毁策略。
如果生产中策略长时间复用，就不应每个元素都重建。
如果生产中策略每条请求都改变，就不应无限摊薄创建成本。
夹具的复用范围应与业务事实一致。
本章的范围是一个进程内复用同一 Affine。

| 阶段 | 本章正式夹具 | 系统级扩展实验需要记录 |
|:--|:--|:--|
| 策略选择 | 在准备阶段完成 | 配置命中与更新频率 |
| 策略对象分配 | 无逐批分配 | 分配器与对象大小分布 |
| 参数生命周期 | 覆盖整个入口 | 是否借用请求或共享配置 |
| 批执行 | 进入正式统计 | 批大小与最大等待 |
| 策略销毁 | 入口结束 | Drop 的实际资源释放 |
| 数据布局 | 连续 u64 切片 | 异构对象位置与指针追逐 |

这里还有一个经常被忽略的区别。
把对象引用存进一个连续 Vec，只保证引用本身连续。
它不保证每个被引用对象在内存中相邻。
若对象分散在很多分配中，访问成本可能来自位置而不是分派。
反过来，连续 enum 存储可能减少指针追逐。
但大变体也可能拉长每个槽的跨度。
本轮没有在这些布局之间计时。
因此不为其附会缓存命中率。

这张阶段表就是[@def-5.5.3] 的展开版：每一行都要写明它落在计时集合的哪一侧。本章把「策略选择」与「对象分配」放在外面，所以它不能回答带分配成本的系统问题；「数据布局」那一行的位置效应，与[@ex-5.5.2] 一样属于**本节没有采集**。

### 5.8.7 代码体积的归因需要分区证据

`__text`是比整个文件长度更清楚的口径。
但它仍然包含启动、标准库、错误路径与业务代码。
要解释一个具体泛型重构，应进一步定位相关符号。
可以保留链接映射或符号列表。
再结合反汇编确认代码边界是否改变。
本轮保存 nm 列表，作为继续核验的入口。

函数被内联后，符号列表可能看不到原来的独立名字。
这不意味着其业务计算没有占用指令空间。
计算可能分散在多个调用者中。
如果几个函数被合并，符号数量又可能高估独立代码份数。
因此计数与字节数需要一起看。
不要使用一次正则匹配结果宣称精确复制倍数。

对真实热点，还要区分冷错误路径与热主体。
冷路径增加总节大小，不一定增加同一时刻的取指工作集。
热主体很小也可能被频繁跳转打散。
这些都是需要运行证据的问题。
本轮没有相应硬件事件，所以只列出下一步观察责任。
静态体积变化不能自动转写成运行时缓存回归。

这一节是[@def-5.8.3] 第三层与第四层之间的那道缝：`nm` 列表和 `__text` 属于静态产物，取指工作集属于运行证据。本轮交付前者，后者明确没有采集（对照[@think-5.2.1]）。

### 5.8.8 两轮桌面记录怎样使用

先行 stable-01 也完整保留了正式批次。
本章主表采用之后的 stable-02。
第二轮脚本还把独立 sample 运行纳入同一目录锁保护。
这样可避免 profiler 的计算负载与其他代理的正式计时重叠。
两轮没有把最快的 case 逐项拼成一张表。
主表所有行都来自同一轮归档。

不同轮之间的绝对均值确有变化。
例如 dyn_item 的第一轮均值为 0.680228ns/元素。
第二轮为 0.647618ns/元素。
第二轮样本标准差也较大。
这些事实要求我们限定桌面环境结论。
它们不允许声称硬件核心类型、频率或热状态已被识别。
本轮没有采集足以完成这种归因的证据。

::: ex 例 5.8.2 · 0.680228 变成 0.647618 说明什么 {#ex-5.8.2}

同一个 case 在两轮归档里的均值差 0.032610 ns/元素（约为第一轮的 4.8%）。① 能写成「第二轮快了近 5%」吗？② 能据此推断核心频率或热状态吗？③ 什么句子是这两份数据支持的？

::: sol 解答

① 不能当结论写。两轮是两次独立运行，不是[@def-1.4.1] 的轮内配对，也没有算差值区间；主表只取 stable-02，两行数字来自不同时间条件（[@def-1.6.1] 的等价工作比较要求在一份协议内）。② 不能。核心类型、频率与热状态本轮没有采集，5.8.4 的缺失清单同样适用于这里。③ 支持的是描述性事实：同一份源码与构建在两台时间不同的桌面运行里，绝对均值会漂移约这个量级，且第二轮批间波动更大（sd 见[@def-1.5.2]）。这正是把本章定位成[@def-1.7.3] 探索性实验的理由。

:::

:::

### 5.8.9 体积与速度的决策矩阵

如果热点逐元素动态调用很频繁，先检查能否批处理。
如果代码膨胀来自大泛型核心，先检查可共享的非泛型部分。
如果类型集合开放，别为了消除 dyn 关闭必要扩展性。
如果体积是硬约束，记录真正相关的节与峰值内存。
如果延迟是硬约束，同时测凑批等待和最大连续工作。

这些决策不应由一个微基准独断。
本轮实验为某些机制提供可复现的小证据。
真实应用仍有分配、数据布局、线程迁移和外部资源。
保持边界清楚，才能知道下一轮该增加哪种测量。
把所有问题归为「trait 太慢」通常只会妨碍定位。

::: think 思考 · 「差 4.1 倍，那就在规范里禁掉热循环里的 dyn」 {#think-5.8.1}

有人读完 5.5 提议把这条写进团队规范：任何循环内都不得出现 `dyn` 方法调用，理由是「本轮慢 4.1 倍」。这个提法绕过了哪两个前提？

::: sol 解答

第一个是**归因前提**：4.1 倍是接口粒度改变后的总体代码效果，不是单条跳转的价格，本轮也没有构造只改跳转的对照（[@ex-5.5.1]）。第二个是**业务前提**：它默认策略在一批内不变，而真正要求逐元素换实现的业务里，强行批处理是改需求（[@ex-5.6.2]）。再加上[@def-5.8.2] 的构建绑定与[@def-5.5.1] 的批长绑定，这条规范会变成「把方法当结论」。可以写的规范是：*热循环中每元素跨擦除边界必须有产物与计时证据*，判定用[@def-1.7.1] 的预算，而不是本章的一个倍数。

:::

:::

::: method 判定流程 · 拿到本章任一个数字先查五件事

1. **口径**：单位是 ns/输入元素还是字节？分母是谁（[@def-5.5.1]、[@def-5.2.3]）？
2. **协议**：哪个入口、几批、是否轮转、有没有预热（5.8.1、[@def-1.4.1]）？
3. **构建**：六项设置与[@def-5.8.2] 是否就是当前环境？不一致就只是参考。
4. **层次**：这句话属于[@def-5.8.3] 的哪一层？跨层就需要另一层的证据。
5. **范围**：批长、线程数、输入分布之外的情形，本章没有采集——照抄即越界（[@ex-5.5.2]）。

:::

### 5.8.10 小结与常见错误

**小结。**① 本章数字的口径是[@def-5.8.1] 的批均值分位数，p99 不是请求分位数；② 结论与[@def-5.8.2] 的构建配置同存；③ 采样只支持「边界确实在执行」，硬件事件本节没有采集（[@ex-5.8.1]）；④ 两轮之间的漂移不构成结论（[@ex-5.8.2]）；⑤ 一切跨层陈述按[@def-5.8.3] 逐层核对，决策按[@def-1.7.1] 的预算而不是本章的倍数。下一节 [5.9 延伸阅读与来源](#sec-cpp-rust.2.5.9) 给出继续读的入口。

::: errata 常见错误清单（5.8 节）

E-a **把批 p99 当请求 p99。**21 个批均值的 p99 就是最大点（[@def-5.8.1]）。

E-b **拿 sample 的栈帧比例算稳定态 CPU 占比。**它覆盖预热与切换，还是另一次运行（[@ex-5.8.1]）。

E-c **从「没有硬件事件」补写分支预测结论。**本轮缺的清单在 5.8.4（[@def-5.8.3]）。

E-d **换构建配置继续引用旧表。**主表不是 ThinLTO 结果（[@def-5.8.2]）。

E-e **把两轮均值差写成优化收益。**没有配对与区间（[@ex-5.8.2]）。

E-f **用本章倍数当团队阈值。**决策要按[@def-1.7.1] 的预算与真实工作量（[@think-5.8.1]）。

:::

::: method 即时自测 · 5.8

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　写出本章正式 case 的采样结构五要素。

::: sol 第 1 题答案
六个独立入口中本章占两个；同一入口内各 case 轮转；每个 case 独立预热至少 500ms；每个正式 case 保存 21 个原始批次；归一化除数是重复数 × 输入元素数。见 5.8.1 与[@def-5.5.1]。
:::

**第 2 题 · 辨析**　「本轮没有算区间，所以三个 case 的差别都不可信。」这句话对吗？

::: sol 第 2 题答案
一半对。它正确限制了 `generic` 与 `dyn_batch` 之间 0.001906 的方向判断（[@ex-5.5.1]）；但 `dyn_item` 高出约 4.1 倍且 sd、分位数一起偏大，属于可陈述的观察（[@def-5.8.1]）。「不可信」把「不能判定方向」扩大成了「数字无效」。
:::

**第 3 题 · 应用**　别人复现你的结论时换了 LTO=true。按本节列出必须重做的三项。

::: sol 第 3 题答案
① 产物对照：重新确认循环内有无间接调用与表加载（[@ex-5.4.1]）；② 体积：同一口径重取`__text`（[@def-5.2.3]）；③ 计时：新构建下重跑协议（5.8.1）。三项都要进新归档，不能在旧表上写新句子（[@def-1.8.2]）。
:::

**第 4 题 · 迁移**　把本章协议搬到一个多线程服务上，哪两条本章结论立刻失效？

::: sol 第 4 题答案
① 「对象构造在计时外、无逐批分配」——真实服务每请求建对象就要重列生命周期表（5.8.6、[@def-5.5.3]）；② 「单线程、同一 `Affine`」——`Send`/`Sync`、`Arc` 计数与线程迁移本轮没有采集（5.3.4），ns/元素 不能搬过去。批长与延迟预算也需按[@ex-5.5.2] 重做。
:::

## 5.9 延伸阅读与来源 {#sec-cpp-rust.2.5.9}

本章的材料来自三类入口，你可以顺着它们继续往下读。

- **《Effective Rust》第 12 条**（母本 S08）：讨论泛型与 trait 对象的权衡。它提醒的一件事和本节直接相关——分派方式是接口决定，不是业务模型决定（[@def-5.1.1]、[@def-5.5.2]）。
- **《Guide to Rustc Development》**（母本 S09）：单态项收集、后端与代码生成单元。读完对[@def-5.2.2] 的「候选集合」和[@def-5.4.2] 的「可见性」会有更具体的图像。（另有一类叫 polymorphization 的收缩思路，本书仓库里没有登记到任何母本原文，故此处不提名也不引用，见结论只按 [@def-5.2.1] 的观察口径说。）
- **当前 Rust 语言 Reference（在线，2026-10-31 抓取入盘）**：[trait 对象](https://doc.rust-lang.org/reference/types/trait-object.html)、[dyn 兼容性](https://doc.rust-lang.org/reference/items/traits.html#dyn-compatibility)与[代码生成属性](https://doc.rust-lang.org/reference/attributes/codegen.html)。这三页正好覆盖[@def-5.3.1]、[@def-5.7.1] 与[@def-5.4.1] 的规范出处。**注意别把它们算成母本 S10**：S10 是旧译参考手册，用「对象安全」一词、没有 dyn 兼容性这一节；本地副本与指纹登记在来源台账的 `REF-trait-object` / `REF-dyn-compatibility` / `REF-codegen-attrs` 三条下。

标准库文档另有两处值得先读：[`std::hint::black_box`](https://doc.rust-lang.org/std/hint/fn.black_box.html)（它只是尽力而为的优化屏障，见[@def-5.4.3]）与 [`std::time::Instant`](https://doc.rust-lang.org/std/time/struct.Instant.html)（墙钟口径见[@def-5.5.1]）。想系统读语言侧的背景，可以看《Rust 程序设计语言》讲 trait 对象与可扩展性的那一章，但它不替代本章的测量协议。

如果想自己动手复核本章的数字，这三处是入口：`bench/compiler-lab/` 里的 `src/bin/dispatch_grain.rs` 与 `src/bin/dispatch_visibility.rs` 是两个正式入口，正式批次分别落在 `dispatch_grain.csv` 与 `dispatch_visibility.csv`；`results/stable-02/codegen/` 存着稳定版 IR 与本机汇编（[@ex-5.4.1] 的依据）；`results/extra-02/` 里的 `*-size.txt` 与 `*-nm.txt` 是[@def-5.2.3] 的字节与符号来源。另一条关联链是校验：不同分派路径使用同一参考语义，尺寸探针逐实例校验后才输出聚合值，PGO 与 ThinLTO 构建的输出也实际比较通过。复现命令在 [5.11](#sec-cpp-rust.2.5.11) 汇总。

母本的时效裁决需要说明一句：S08 关于对象上转型的限制来自 Rust 1.70 时点，本轮 Rust 1.99.0 的转换测试已经通过（[@ex-5.7.2]），所以本章保留它的历史解释、不保留旧限制作为现行结论；S08 的 trait 对象结构图也不是跨版本二进制协议（[@def-5.3.4]）。**每份母本核读到哪一页、哪些范围没有审计、贡献记录在哪个文件**，属于来源台账，写在[附录：来源覆盖](../appendix/coverage.md)，不搬进正文。本章与相邻章节的衔接，见[第 4 章](../part1/ch04.md)的分层表示与编译期责任，以及第 6 章的向量化与 PGO 流程。

## 5.10 常见错误索引 {#sec-cpp-rust.2.5.10}

本章的陷阱不集中堆在章末。每一条都写在它所属小节的「常见错误清单」里，让你在使用它的地方看见它：八份清单共 48 条（E-a … E-f × 5.1–5.8）。这张索引只回答两件事——**各节的清单共同把什么搞错了，出错之后先查什么**。

| 节 | 清单 | 这些错误共同把什么搞错了 | 出错后先查 |
|:--|:--|:--|:--|
| [5.1](#sec-cpp-rust.2.5.1) | E-a … E-f | 把「目标什么时候定」当成「快不快」 | 粒度是每元素还是每批（[@def-5.1.2]） |
| [5.2](#sec-cpp-rust.2.5.2) | E-a … E-f | 把源码形态当成产物形态 | 数的是哪个口径的字节（[@def-5.2.3]） |
| [5.3](#sec-cpp-rust.2.5.3) | E-a … E-f | 把尺寸、位置与协议混成一件事 | 第二个字到底装了什么（[@def-5.3.3]） |
| [5.4](#sec-cpp-rust.2.5.4) | E-a … E-f | 把关键字当成优化结果的因 | 产物里那条跳转还在不在（[@ex-5.4.1]） |
| [5.5](#sec-cpp-rust.2.5.5) | E-a … E-f | 把总体效果当成单条指令的价格 | 差值有没有超过批间波动（[@ex-5.5.1]） |
| [5.6](#sec-cpp-rust.2.5.6) | E-a … E-f | 把「时间接近」读成「机制相同」 | 摊薄的前提还成立吗（[@def-5.6.2]） |
| [5.7](#sec-cpp-rust.2.5.7) | E-a … E-f | 把接口约束当成风格偏好或万能开关 | 方法表放不放得下（[@def-5.7.1]） |
| [5.8](#sec-cpp-rust.2.5.8) | E-a … E-f | 把口径与构建当成可省略的背景 | 这句话属于哪一层证据（[@def-5.8.3]） |

另有四条不属于任何单一小节，只有整章读完才看得见：

1. **把「静态快、动态慢」当成本章结论带走。**两张正式表都不支持它：`dyn_batch` 与 `generic` 差 0.001906、方向未定（[@ex-5.5.1]），`known_dyn` 与 `opaque_dyn` 差 0.002170、同样未定（[@ex-5.6.1]）。真正被支持的是「粒度改变后总体成本不同」。
2. **跨节搬数字。**5.2 的 3008 字节是静态体积，不能写进 5.5 的成本句子；5.5 的 4.1 倍绑定 16384 这个批长，换批长即失效（[@ex-5.5.2]）。每个数字先问它属于[@def-5.8.3] 的哪一层。
3. **只查一层证据就收尾。**只看目标码会漏掉「产物不同、时间接近」这一类（5.6.5）；只看计时表会把接口问题误读成指令问题。性能表与产物表要互相检查，不互相替代（[@ex-5.8.1]）。
4. **用性能收益换掉业务前提。**把每元素的 `step` 改成每批的 `batch`，前提是策略在一批内不变；不成立时这是改需求（[@ex-5.6.2]、[@think-5.8.1]）。API 粒度必须忠于业务，而不是忠于表格。

## 5.11 本章小结与章末件 {#sec-cpp-rust.2.5.11}

::: note 本章小结

- 分派回答「目标什么时候定下来」，粒度回答「多久定一次」；决定成本量级的是后者（[@def-5.1.1]、[@def-5.1.2]）。
- 单态化与可达性决定产物里有几份代码，体积必须按口径数：本轮 many 比 one 的`__text`大 3008 字节（[@def-5.1.3]、[@def-5.2.1]、[@def-5.2.3]）。
- trait 对象是「数据加元数据」，对象仍在原处；本轮的偏移只是产物观察，不是 ABI（[@def-5.3.3]、[@def-5.3.4]）。
- 去虚化取决于信息不取决于关键字：同一份业务循环，`visible_dynamic` 内部没有表调用，`dynamic_batch` 留一条间接尾跳转（[@def-5.4.1]、[@ex-5.4.1]）。
- 每批与每元素相差约 4.1 倍（0.156428 对 0.647618）；两组接近的数字都方向未定，不能写成百分比结论（[@def-5.5.2]、[@ex-5.5.1]、[@ex-5.6.1]）。

**改动本章实验的责任**：换批长要重跑协议并重新摊薄（[@ex-5.5.2]）；换构建配置要重取产物与计时（[@def-5.8.2]）；换拥有者（`Box`、`Arc`）要把分配与计数成本从分派里分出来（[@def-5.1.4]）；改接口粒度前先确认策略能否在一批内保持不变（[@ex-5.6.2]）。

:::

### 本章导航

**学习目标**：学完这一章，你应该能——

- 把擦除、分派与所有权分开说明，并算清一次动态边界替多少元素负责；
- 用可达性与节口径解释「泛型让代码变大」这类说法，指出哪些量本章没有采集；
- 从目标码判断去虚化有没有发生，并说明它随构建配置漂移；
- 把两组批均值读成有口径、有前提、有范围的结论。

**先修**：[第 4 章](../part1/ch04.md)的分层表示与编译期责任；第 1 章的实验契约与批均值（[@def-1.1.3]、[@def-1.5.2]）。
**课时**：讲授 2 学时 + 实验 2 学时。
**实验包**：`bench/compiler-lab/`，只依赖标准库。
**入口**：`src/bin/dispatch_grain.rs` 与 `src/bin/dispatch_visibility.rs`；尺寸探针是 `probes/code_size.rs`。
**数据**：`results/stable-02/`（含 `codegen/`、`macos-sample.txt`）与 `results/extra-02/`，均相对实验包。
**边界**：单线程、一个进程内复用同一 `Affine`、批长 16384、构建配置固定；没有 Linux perf、Miri 或缓存事件测量；没有跨版本插件 ABI 的安全实现；没有核读所有泛型相关 RFC，也没有审计 rustc 完整的 vtable 生成代码——这些审计范围记在[来源台账](../appendix/coverage.md)。nightly 损坏的事实未被隐藏。

### 复现与定位

从`cpp-rust/`执行。
正式脚本要求新归档目录不存在。

```bash
cargo test --offline --locked --manifest-path bench/compiler-lab/Cargo.toml
cargo clippy --offline --locked \
  --manifest-path bench/compiler-lab/Cargo.toml --all-targets -- -D warnings
bash bench/compiler-lab/run.sh bench/compiler-lab/results/my-trait-run
python3 bench/compiler-lab/extra.py bench/compiler-lab/results/my-trait-extra
```

正式脚本还执行 rustfmt 检查。
六个入口顺序运行，不并发计时。
目录锁覆盖两段：六个入口的正式计时，以及其后那次刻意排除在 21 批之外的 profiler 采样运行（脚本会重新取锁，避免采样负载压到别人的计时上）。
编译与功能测试不使用这个锁。
因此不同代理可以编译不同包而不会修改本实验的源文件。

本章交付的边界也一并写明：两个正式入口都有完整源文件，五个正式 case 各保存 21 批，所有输出校验通过，尺寸探针实际运行并逐实例校验；读者应据此提出下一项更贴近业务的实验，而不是只背「静态快、动态慢」。

**出口检查**（合上正文自问）：应能解释 `generic_batch` 为什么不需要 trait 对象、`dynamic_batch` 为什么仍有具体实现、其内部 `step` 为什么有机会直接解析，并区分类型擦除与共享所有权；应能在 `dynamic_items` 的目标码里指出循环内的间接调用、在 `dynamic_batch` 里指出一次间接尾跳转、在 `visible_dynamic` 里确认内部目标已消解，并确认 one 与 many 的`__text`不同而不把`__PAGEZERO`计入指令字节；应能说明为什么 21 批的 p99 不是网络请求的 p99（[@def-5.8.1]），以及关联类型固定后与任意泛型方法有何不同（[@def-5.7.1]）。

真实系统应为热点 API 的粒度设定预算，可以记录每请求最多跨几次动态边界、单态化后相关节多大，但预算必须建立在真实请求与构建配置上（[@def-1.7.1]、[@def-5.8.2]）；后来新增策略类型要重查可达实例，移动 crate 边界要重查优化可见性，加入分配或线程共享要把它们从分派问题里分出去。
