# 第5章 · 综合自测卷

**闭卷，60 分钟，100 分。**不许查正文、不许跑代码、不许看[回忆卡](ch05_recall.md)。允许一张空白草稿纸。做完先按[评分标准](#ch05-exam-score)自己打分，再逐题对照解答。低于 70 分不要往下读第 6 章，回到扣分项对应的小节重读那一段。

时间分配建议：第一部分 15 分钟，第二部分 20 分钟，第三部分 20 分钟，留 5 分钟检查单位与措辞。

## 第一部分 · 概念辨析（每题 5 分，共 30 分）

判断对错并写一句理由。只写「对/错」不得分。

1. 这个循环里用了 trait，所以每次调用都必须查表。
2. 一个泛型 API 被 10 个具体类型使用，产物里至少有 10 份独立代码。
3. `&dyn Operation` 与 `&[u64]` 都是 size 16、align 8，可以用 `transmute` 互转。
4. 源码里写了 `dyn`，目标码里就一定有一条间接跳转。
5. 带类型参数的方法 `fn apply<T>(&self, value: T)` 也能放进 trait 对象，只要调用时把 `T` 写出来。
6. 删掉 `batch` 只留 `step`，功能测试全绿，所以这次改动不影响性能。

## 第三部分 · 设计与表达（共 40 分）

10. （20 分）服务现状是热循环里逐元素调用 `step`，策略由配置选定、在准备阶段完成。你要论证「改成每批一次 `batch` 是否值得」。写出实验设计：
    - 输入家族与冷热状态；
    - 计时边界（哪些阶段在界内、哪些在界外）；
    - 观察方式（怎样保证工作真的发生、结果可比）；
    - 外部条件与 CSV 字段；
    - 统计方法与判定规则（含预算 `B` 怎么写）。
    最后指出：本章哪三个数字不能直接搬进这份设计。

11. （10 分）评审意见原文：「这批平均 0.156428 ns/元素，比上一版快 4.1 倍；p99 是 0.176579，请求延迟可控；体积多了 3008 字节，缓存命中率会下降；测试全绿，可以合并。」指出四处问题，各给一句改写。

12. （10 分）`dynamic_batch` 的入口在归档里是这四行：

    ```asm
    ldr x4, [x1, #32]
    mov x1, x2
    mov x2, x3
    br x4
    ```

    ① 有人说「业务只花四条指令」，错在哪？② 要确认业务成本，还要追什么？③ 写一句符合证据层次的结论。

## 解答与给分说明

**1. 错。** trait 只说明方法集合，不规定多久调用一次。同一个 `Kernel` 里，`step` 是逐元素粒度、`batch` 是每批粒度，选哪个是调用点的责任（[定义 5.1.2](ch05.md#def-5.1.2)）。

**2. 错。** 只有可达实例才需要机器码；内联后可能没有独立符号，不可达的实例可以整个不生成。本章 many 的 16 个 const 实例相对 one 只多了 3008 字节，不能当成 16 份独立代码（[定义 5.2.1](ch05.md#def-5.2.1)、[例 5.2.1](ch05.md#ex-5.2.1)）。

**3. 错。** 两个字的语义不同：一个是元素个数，一个是方法元数据。把长度当元数据用，第一次调用就会去一个不存在表的地方取地址（[例 5.3.1](ch05.md#ex-5.3.1)）。

**4. 错。** `visible_dynamic` 的形参是 `&Affine`，擦除发生在函数体内，本轮内部一次表调用都不剩。去虚化取决于优化器能看到什么（[定义 5.4.1](ch05.md#def-5.4.1)）。

**5. 错。** `T` 有无穷多种实例，一张有限方法表排不完。错误在构造对象类型 `&dyn Bad` 的那一刻就报告 E0038，不需要任何调用发生；调用时写出 `T` 并不能减少实例数（[定义 5.7.1](ch05.md#def-5.7.1)、[例 5.7.1](ch05.md#ex-5.7.1)）。

**6. 错。** 语义确实没变，但逐元素的动态边界从「无」变成「一次」：16384 个元素上，每批一次是 0.156428，每元素一次是 0.647618 ns/元素。回归发生在优化边界（[例 5.6.2](ch05.md#ex-5.6.2)）。

**7.（参考）** ① 相同 checksum 只确立「三个 case 算的是同一件事」，是比较成立的前提；它不控制代码形态，也不证明每个 case 的优化机会相同。

② 错在把总体效果当成单条指令的价格：粒度改变顺带改变了内联、展开与归约调度，`dynamic_items` 的业务循环在擦除调用方内、`dynamic_batch` 的在具体实现内，这两句都不是「只有跳转不同」。给分：第①问 3 分，第②问 5 分；只说「checksum 对」不给分，必须说出「等价工作比较」与「代码形态未受控」。

**8.（参考）** 越界一：0.156428 是 16384 个元素摊薄后的批均值，一次动态进入的固定成本只占极小比例；批长换成别的值，固定成本按 1/n 变化，4.1 的比值不再成立。

越界二：把两个 case 的比值说成「批处理接口」的普遍属性，忽略了本轮只有一种批长与一份构建配置。能写的句子：「在本轮 16384 个元素、这份构建下，`dyn_batch` 的批均值是 0.156428，`dyn_item` 是 0.647618 ns/元素，粒度改变后的总体差异约 4.1 倍。」给分：每处越界 4 分，正确句子 2 分。

**9.（参考）** ① 不能。0.002170 小于两者的 sd（0.004065 与 0.004387），本轮没有区间、没有配对，方向不可判定。

② 0.002170 × 16384 ≈ 36 纳秒，含义是「一次完整遍历 16384 个元素的均值差」；它只能检查量级，不能给单次跳转定价。

③ 失效的是「一次进入被摊薄到看不见」这条：批长为 8 时贡献按 1/n 上升。「接近」也不再成立，但本章没有 8 元素批的数据，不能给出新数字。给分：每问 4 分；第③问必须同时说出「1/n」与「本章没有采集」。

**10.（参考骨架，五件各 4 分）**
- 输入：同一份 16384 个 `u64`，参数固定 multiplier=17、increment=29；对象与输入在计时前构造，声明不覆盖每请求分配。
- 计时界内：外层 case 闭包调用、元素计算、批后 checksum 校验；界外：输入构造、对象构造、`Box` 创建。
- 观察：每个 case 的结果与入口独立算出的 `expected` 相等，空输入与不整除展开宽度的长度也要覆盖。
- 外部条件与字段：opt-level 3、codegen-units 1、LTO false、debug info 1、panic unwind、target-cpu 未显式设置；CSV 至少含 case、round、position、ns/元素、checksum。
- 统计与判定：每个 case 独立预热至少 500ms、保存 21 个批均值，报 mean、N−1 sd、批 p50 与 p99；`B` 在采集前写下，按 `U ≤ B` 接受、`L > B` 拒绝、其余证据不足。
- 不能搬的三个数字：0.156428 只对应 16384 的批长；0.647618 绑定同一份构建与同一台机器；p99 是批的分位数，不是请求延迟。任何一项换了都要重做设计。

**11.（参考，四处各 2.5 分）**
- 「平均 0.156428，比上一版快 4.1 倍」口径缺失且用错对象 → 写「本 case 21 个批均值为 0.156428 ns/输入元素，批长 16384」；4.1 倍是 `dyn_item` 相对 `dyn_batch` 的粒度差，不是新旧版本之差。
- 「p99 是 0.176579，请求延迟可控」→ 它是 21 个批均值的最大点，本章没有采集到达、排队与输出延迟。
- 「体积多 3008 字节，缓存命中率会下降」→ 体积属于静态产物，缓存属于运行证据，本章没有硬件事件。
- 「测试全绿，可以合并」→ 测试只证明语义没变，接口粒度改变可能把热点推上慢路径。

**12.（参考）** ① 这是尾调用形式的间接分派，`br x4` 之后进入具体 `batch` 实现，循环与全部 16384 个元素都在那里，四条指令只是入口。② 继续追踪 `x4` 指向的目标函数，确认业务循环的位置与展开形态。③ 结论句示例：「本轮 `dynamic_batch` 的入口保留一次间接尾跳转，业务在具体 `batch` 实现内完成；这支持『每批一次动态进入』，不支持『整个业务只有四条指令』。」给分：① 4 分，② 3 分，③ 3 分（须含「本轮」「每批一次」「不断言业务只有四条指令」）。
