把线程阻塞调用换成async函数，并不自动减少工作量。
如果函数内部继续调用阻塞I/O，它仍会占住执行poll的线程。
如果没有真正的挂起，await也不必发生任务调度。
如果每处理一个字节都主动唤醒自己，调度协议可能比计算本身更贵。

因此异步性能的分析单位不能只用「协程切换」四个字。
要拆成Future构造、帧存储、一次poll、通知、入队和线程唤醒。
这些阶段可能被内联（把被调函数的身体搬进调用处，省掉一次跳转）消除，也可能因对象逃逸和动态分派而保留下来。
编译器和运行时各负责一部分，不能把全部成本归给Rust语法。

本章只实现一个单Future驱动器。
它没有socket reactor，也不伪装成Tokio替代品。
我们用这个小范围，把最容易被黑箱掩盖的协议展开。
更复杂的多任务运行时需要额外的就绪队列、取消、背压（下游一慢，就把上游也压慢）与回收设计。

一条主线贯穿全章：**先把 async 还原成对象，再看编译器在帧里存了什么，然后守住 poll 与唤醒的协议，最后用两个基准把成本拆到可核对的粒度。** 每一节都回到这条线上。本章出现的每个数字都来自文件里已有的实测产物；凡没有对应记录之处，一律写「本节没有采集」，不补一个假定的数字（对照[@def-1.1.3]：先把观察对象与边界定清楚，再谈成本）。

## 8.1 async函数构造的是对象，不是线程 {#sec-cpp-rust.2.8.1}

本节回答一个问题：**调用一个 `async fn`，我手里拿到的到底是什么？**直觉常把「调用 async 函数」等同于「启动一件事」。这一节把两件事分开——调用产生一个可恢复的对象，真正的计算要等 poll 才推进。这条边界想清楚，后面每一处计时才谈得上对象明确（对照[@def-1.1.3]：先定观察对象，再谈成本）。

::: preview 先抓住一件事

调用 async 函数返回一个「还没开始算」的匿名 Future，它不是线程，也不是已提交的任务。构造、提交、完成是三个不同的时点；本章几乎所有错误估算，都能追溯到把这三者混成一个「async 调用」。
:::

### 8.1.1 调用与执行体的边界

::: def 定义 8.1.2 · 可恢复计算对象 resumable computation {#def-8.1.2}
调用 async 函数会**捕获参数并产生一个实现 Future 的匿名值**；函数体的计算由后续 poll 推进。返回的那一刻，业务代码一行都还没跑；跑起来之后可以停在 await、以后再从原地继续——这才是「可恢复」的确切含义。
:::

按[@def-8.1.2]，这个返回值不需要在调用点创建 OS 线程，也不需要语言内置一个全局调度器。

**拿内核里的真线程对照，差别更清楚。**rCore 教程第八章讲用户态线程时，把「线程」定义成一组必须自己保存的东西：编号、运行状态、程序停在哪一条指令、那批通用寄存器（CPU 里放得下当前执行状态的那几个格子）、以及一截专属于它的栈；切换两个线程时，运行库要把这些逐样搬到另一个线程的上下文里。这套动作在用户态完成，内核全程不知情，于是线程只有等当前线程主动交出处理器时才有机会跑——协作式调度就是这么来的。

`async` 的 Future 做的是同一类保存（状态存在对象里），但两件事的方向相反：**Future 把「保存状态」交给编译器，把「何时切换」交给你的 `poll` 调用点**；用户态线程则把两件事都交给运行库，于是切换点只能由协作点决定。本章后面要量的每一次 `poll` 返回都不换栈、不换页表；但**「不进内核」只对没有唤醒别人的那次返回成立**：self-wake 那一路在 `poll` 内部调 `wake_by_ref`，顺着 `Notify::notify` 落到 `unpark`，那是系统调用（陷入内核代为执行的操作）——`bench/results/profile/async-sample.txt` 里就采到了 `unpark` 帧，8.6.5 也把这部分工作算进结论，不当作零成本。

这个区分影响错误处理与测量。
只测Future构造，没有测到完成异步工作。
只测spawn返回，也没有测到任务结果。
只测第一次poll，对真正的I/O工作通常仍不完整。

先看本章的取消探针（观察取消路径怎样落地的小程序）。
源文件是 `bench/examples/future_layout.rs`。
其中 `cancellation_probe` 在函数体内构造Guard，再等待永远Pending的子Future。

```rust
async fn cancellation_probe(count: Arc<AtomicUsize>) {
    let _guard = Guard(count);
    std::future::pending::<()>().await;
}
```

调用后直接drop该Future，Guard还没被构造。
其中捕获的Arc参数仍需要正常销毁。
「函数体未执行」不等于「Future里什么资源都没有」。

第一次poll进入函数体，Guard才成为一个活跃局部对象。
在Pending之后drop，则必须释放这个Guard。
这是编译器管理暂停状态的具体责任。

::: ex 例 8.1.1 · 三个销毁时点 {#ex-8.1.1}

`cancellation_probe` 里有两样东西：捕获的参数 `count`（一个 `Arc<AtomicUsize>`），和函数体内构造的 `Guard`。给出下列三种情形下「Guard 析构计数器」的值，并说明为什么「还没执行函数体」不等于「帧里什么都没有」：

1. 只调用、从不 poll，直接 drop；
2. poll 一次拿到 Pending 之后 drop；
3. 为什么本例永远走不到「正常返回并收尾析构」。

::: sol 解答

1. Guard 计数为 0：函数体从没进入，`Guard(count)` 这行从没执行；但被捕获的 `count` 仍作为帧字段正常销毁——构造路径就把参数移进了帧（见[@def-8.2.1]）。
2. Guard 计数为 1：首次 poll 进入函数体，`Guard` 成为活跃局部对象、落在挂起态字段里，此时 drop 必须释放它（8.8 节用 `AtomicUsize` 实测到 0 与 1 两种计数）。
3. 唯一后续是 `std::future::pending::<()>().await`，它永远返回 Pending，外层也就永远停在挂起态、不会自己走到 `Ready` 收尾；资源回收只能靠外部 drop 或进程结束。这条是[@def-8.1.1]「通知只提供重新检查机会」的另一面：没有通知，也没有自动完成。

:::

:::

读图：Future 可以住在栈上、`Box` 里或专用的任务分配区，放哪儿不由 `async` 关键字决定。`poll` 由执行层调用，可能就在当前线程，也可能被调度器迁到另一个线程；能否迁移取决于 `Send` 与运行时接口（8.8 节）。最底下两行是这一章最容易被混起来的两件事：**线程是执行者，状态机是被执行者；I/O 驱动报告的是「资源好了」，不是「任务该继续跑了」**。

### 8.1.3 Future 没有自动并行性

两个Future在同一线程上轮流poll，可以形成并发等待。
它们不会因此同时在两个物理核心上计算。
要利用多核执行CPU工作，需要多线程调度或显式并行机制。

同一个Future通常不能被两个线程同时poll。
`poll`需要独占的 `Pin<&mut Self>`。
运行时必须保证任务不会并发获得两个这样的访问权。
不能因为Waker可从多个线程调用，就推导poll也能同时执行。

「并发等待」和「并行执行」是两件事，别用同一个词混过去。这是[@def-8.1.1]把 driver 的职责限定成「何时再 poll」的原因：poll 时机是策略，同时在几个核上跑是另一套机制。

### 8.1.4 函数返回的 impl Future

::: def 定义 8.1.3 · 静态返回与类型擦除 static vs erased Future {#def-8.1.3}
匿名 Future 常通过 `impl Future<Output = T>` 隐藏具体类型；这只是**编译期名字未知**，泛型调用链仍可单态化（泛型为每种具体类型各生成一份代码）为具体类型，不自动等于动态分派。相反，`Pin<Box<dyn Future<Output = T> + Send>>` 才是类型擦除，可能引入堆分配与间接 poll 调用。
:::

按[@def-8.1.3]，是否真正付出堆分配与间接调用，要看对象是否逃逸、优化是否去虚化（把运行时查表跳转折成一次直接调用），不能只按签名做固定纳秒数估计——这与第 1 章「先看工作是否存在，再谈单位」是同一纪律（[@def-1.1.1]）。

原句保留：**不要只按签名做固定纳秒数估计**——这句是本章反复用到的判据。

### 8.1.5 边界表

| 概念 | 负责内容 | 不负责内容 |
|:--|:--|:--|
| async函数 | 构造可恢复计算对象 | 不创建内置线程池 |
| Future::poll | 推进一次状态机 | 不保证这次就完成 |
| Waker | 请求任务再次被检查 | 不携带本次计算结果 |
| executor | 管理就绪任务与poll时机 | 不必亲自完成I/O |
| reactor / I/O驱动 | 追踪I/O就绪或完成 | 不决定语言级局部变量生命周期 |
| OS调度器 | 给线程分配CPU执行机会 | 不直接理解任意Rust Future |

### 8.1.6 思考：把「调用」当成「启动」会漏掉什么

::: think 思考 · 一张只有 async fn 的调用栈能说明什么 {#think-8.1.1}

有人在火焰图里看到 `operation` 这个 async 函数的名字出现，就断定「async 调用创建了一个线程 / 立即开始执行」。用[@def-8.1.2]反驳这个推断，并指出正确读法。

::: sol 解答

名字出现在栈里，只说明「这段代码在某一刻被 poll 推进」，不能说明它是「调用即执行」，更不能说明它独占了一个 OS 线程。按[@def-8.1.2]，调用 async 函数只构造对象；真正让 `operation` 进入栈的，是某个 driver 的一次 poll。要看「谁在跑、跑多久」，得区分[@def-8.1.1]里的三件对象：Future（帧与状态）、driver（poll 时机）、承载它的 OS 线程。三者可以同线程、可迁移、也可一个线程承载多个 Future，名字本身不给这些信息。

:::

### 8.1.7 小结与常见错误

**小结。**① 调用 async 函数得到的是「还没算」的匿名 Future，构造、提交、完成是三个时点（[@def-8.1.2]）；② 「函数体没执行」不等于「帧里没资源」，被捕获参数照常析构（[@ex-8.1.1]）；③ 同一线程轮流 poll 是并发等待，不是多核并行（[@def-8.1.1]）；④ `impl Future` 是静态未知，`Box<dyn Future>` 才是擦除，别只按签名估成本（[@def-8.1.3]）；⑤ 一个 Future 通常不能被两个线程同时 poll。下一节 [8.2 MIR 里保存了什么](#sec-cpp-rust.2.8.2) 打开帧，看编译器到底存了哪些字段。

::: errata 常见错误清单（8.1 节）

E-a **把「调用 async fn」当成「启动线程」。**调用只构造对象（[@def-8.1.2]）。

E-b **只测 Future 构造就当测了异步完成。**构造、提交、完成是三个时点（[@ex-8.1.1]）。

E-c **认为函数体没执行就等于帧里空无一物。**被捕获的参数仍是活跃字段（[@def-8.1.2]）。

E-d **把同线程轮流 poll 说成并行。**并发等待 ≠ 多核执行（[@def-8.1.1]）。

E-e **从 `impl Future` 直接推断动态分派。**静态未知不等于类型擦除（[@def-8.1.3]）。

E-f **凭签名报一个固定纳秒开销。**要看逃逸与去虚化，不看签名字面（[@def-8.1.3]）。

:::

## 8.2 MIR里保存了什么 {#sec-cpp-rust.2.8.2}

本节回答一个问题：**编译器到底把哪些东西留在了挂起帧里？**上一节说 async 返回一个对象（[@def-8.1.2]），这一节把那个对象打开——用稳定工具链生成的 MIR 实际产物，而不是凭空写一个「应该是这样」的枚举来冒充编译结果。

### 8.2.2 实际状态摘要

在 cancellation_probe 的MIR中，可以看到以下布局摘要。
这是实际产物的节选，而非手写一个假定枚举去冒充编译结果。

::: def 定义 8.2.1 · 协程帧与状态变体 coroutine frame & variants {#def-8.2.1}
async 函数降低成一个协程对象：`field` 行是**帧里真实存放的字段**，`variant_fields` 是状态机的各个变体（未恢复 `Unresumed`、已完成 `Returned`、panic 后 `Panicked`、以及每个挂起点 `SuspendN`）。构造路径把被捕获的参数移进帧（这就是[@ex-8.1.1]里 `count` 即使不 poll 也要销毁的原因）；只有跨某个 await 仍存活的局部量，才会成为那个 `SuspendN` 变体的字段。
:::

```text
coroutine layout {
    field _s0: Guard;
    field _s1: std::future::Pending<()>;
    variant_fields = {
        Unresumed(0): [],
        Returned (1): [],
        Panicked (2): [],
        Suspend0 (3): [_s0, _s1],
    }
}
```

Suspend0保存了Guard与正在等待的子Future。
Unresumed、Returned、Panicked标识状态用途。
编号0、1、2、3只描述这个版本的输出。
语言没有保证所有Future都按这些字节编号布局。

::: ex 例 8.2.1 · 从这段 layout 读出三件事 {#ex-8.2.1}

盯着上面的 `variant_fields`：

1. 为什么 `Unresumed`、`Returned`、`Panicked` 三个变体的字段列表都是空 `[]`？
2. `_s0: Guard` 出现在 `Suspend0`，说明 Guard 的存活区间是什么？
3. 能否据此说「Rust 的 Future 一定把状态放在第 3 号分支」？

::: sol 解答

1. 因为这三态没有「需要跨挂起保存的数据」：未恢复时业务体还没跑（Guard 未构造），完成或 panic 后帧里的活跃局部量都已析构，只剩一个判别值（[@def-8.2.1]）。
2. Guard 从「首次 poll 执行到 `Guard(count)`」存活，一直到越过 `pending().await` 的挂起点，所以它必须进 `Suspend0`；这也解释了[@ex-8.1.1]第 2 种情形计数为 1。
3. 不能。编号 0/1/2/3 只属于这一版 rustc 1.99.0 的输出，语言不保证跨版本的字节编号布局；把它当 ABI 违反[@def-8.2.1]的用途/编号之分。

:::

:::

### 8.2.3 构造函数没有执行业务体

同一文件里的构造函数很短。
它把count参数移入coroutine对象，然后返回。
Guard初始化出现在后续poll路径，而不是构造路径。

```text
fn cancellation_probe(count) -> anonymous_future {
    anonymous_future = coroutine { count: move count };
    return anonymous_future;
}
```

这里为了说明读取方式，对局部名字做了简化。
完整原始MIR保留在结果目录中。
不能把简化图中的字段顺序视作内存保证。

构造路径只做「把参数搬进帧」这一件事，与[@def-8.1.2]「调用不跑业务体」严丝合缝：`count: move count` 就是那步搬运，而 `Guard` 不在这里出现。

### 8.2.4 poll 入口检查判别值

::: def 定义 8.2.2 · 判别值 discriminant {#def-8.2.2}
每个协程对象头部有一个**判别值**，记录它当前处在 `Unresumed / Returned / Panicked / SuspendN` 哪一个变体。`poll` 入口先读这个判别值，再用 `switchInt` 跳到对应基本块——恢复不是重新解析源码，而是「读状态、跳过去、接着跑」。
:::

实际MIR读取Future的discriminant。
随后按状态跳转到不同基本块。
首次进入会构造Guard与子Future。
恢复进入会继续poll之前的子Future。

```text
discriminant = discriminant(future)
switchInt(discriminant):
    0 -> 首次执行路径
    1 -> 完成后恢复的错误路径
    2 -> panic后恢复的错误路径
    3 -> Suspend0恢复路径
```

这说明恢复不是「从头重跑async函数」。
需要跨await存活的数据已经在帧里。
不需要重新解析源代码或构建调用栈字符串。

分支代价是「读一个判别值 + 一次跳转」，与第 1 章提醒的一致：接近某个常数不来自签名，而来自实际留在产物里的控制流（[@def-1.1.1]）。

### 8.2.5 Ready 与 Pending 分支

子Future返回Pending时，外层记录挂起状态并返回Pending。
子Future返回Ready时，外层取出结果，继续后面的普通逻辑。
若后面还有await，可能在同一次poll里继续推进到下一个挂起点。

因此，一次poll并不等于跨一个await。
多个已就绪await可以在同一次poll中通过。
真正消耗调度边界的是实际返回Pending的路径。

这条判据马上要在[@def-8.4.1]变成测量口径：**统计调度次数要数真正返回 Pending 的次数，而不是源码里 await 的个数**——按 await 数估算调度开销是本章反复出现的错误（见 8.10）。

### 8.2.6 取消与正常结束的不同出口

正常结束路径销毁活跃局部对象，再设置完成状态。
panic展开路径清理对应活跃对象，再继续展开。
外部drop处于挂起态的Future，也需要按当前状态清理其字段。

这里讨论的是正常Rust析构与unwind路径。
若进程abort或被操作系统直接终止，不能保证执行全部Drop。
不要写「所有资源在任何退出情况下都确定释放」。

三条出口对应[@def-8.2.1]的三个不同变体：完成走 `Returned`、panic 走 `Panicked`、外部 drop 按当前所在变体清理；把三者混为「反正都会 Drop」会掩盖 abort 这条不设保证的出口。

### 8.2.8 思考：能不能记住编号当 ABI

::: think 思考 · 编号 3 会不会有一天代表别的东西 {#think-8.2.1}

某段性能笔记写着「Suspend 状态恒等于判别值 3，所以可以直接在外部按 3 判断是否挂起」。用本节的产物纪律反驳它，并给出安全的读法。

::: sol 解答

不能把编号当契约。[@def-8.2.2]只说「判别值选出当前变体」，编号 0/1/2/3 是这一版 rustc 1.99.0 输出的细节，换版本、换优化级别都可能重排。安全读法是：要区分状态，就调用语言/标准库提供的接口（poll 的返回、`is_completed` 一类），或在**同一版本产物**上重新核对 layout，而不是在外部硬编码一个整数——母本只提供框架、不替代版本化产物（对照[@def-1.1.3] 的外部条件）。

### 8.2.9 小结与常见错误

**小结。**① 帧里只放跨 await 存活的字段，不是所有源码局部量（[@def-8.2.1]）；② 构造路径搬运参数、不跑业务体（[@def-8.1.2]）；③ poll 靠判别值跳转恢复，不是重跑（[@def-8.2.2]）；④ 一次 poll 可穿过多个已就绪 await，调度次数要数真正的 Pending（8.2.5）；⑤ 编号属于当前版本产物，不是 ABI（[@think-8.2.1]）。下一节 [8.3 帧大小、存活分析与 Pin 的边界](#sec-cpp-rust.2.8.3) 把这些字段换算成尺寸。

::: errata 常见错误清单（8.2 节）

E-a **手编一个「假定的枚举」冒充编译结果。**只引用这一版真实生成的产物（[@def-8.2.1]）。

E-b **把帧大小当成所有局部变量之和。**只有跨挂起存活的才进帧（[@def-8.2.1]）。

E-c **把判别值编号当 ABI 或稳定内存布局。**编号只属于当前输出（[@think-8.2.1]）。

E-d **认为恢复 = 从头重跑 async 函数。**恢复是读状态、跳进对应基本块（[@def-8.2.2]）。

E-e **按 await 个数估算调度边界。**要数真正返回 Pending 的次数（8.2.5）。

E-f **声称任何退出都确定跑完 Drop。**abort 与进程终止不设此保证（8.2.6）。

:::

## 8.3 帧大小、存活分析与Pin的边界 {#sec-cpp-rust.2.8.3}

本节回答一个问题：**帧到底有多大，Pin 又到底钉住了什么？**上一节的字段（[@def-8.2.1]）在这里换算成字节：一段代码的 Future 尺寸，取决于「恢复时还要用到哪些值」，而不是「写过哪些局部变量」。

::: preview 先抓住一件事

帧尺寸是「跨挂起存活集合」的大小，不是「所有局部变量之和」。要缩小帧，就把重对象的活跃区间收在 await 之前；但 Pin 是另一件事——它约束被指向对象的地址稳定，跟「放栈上还是堆上」没有必然关系。两个探针只差一个作用域，尺寸差两千倍，就是这个区别最干净的证据。

:::

### 8.3.1 两个只差作用域的探针

::: def 定义 8.3.1 · 跨 await 存活 liveness across await {#def-8.3.1}
一个局部量「跨 await 存活」，指它在某个挂起点**之后仍会被使用**，因此编译器必须把它搬进对应的 `SuspendN` 帧字段（[@def-8.2.1]）。如果它的最后一次使用在 await 之前，它就不需要进帧——即使它很大。
:::

第一种让4096字节数组跨await存活。
第二种在await前取出所需字节，结束数组的局部作用域。
两个Future都先等待一个永不就绪的子Future。
所以没有把I/O差异混进布局问题。

```rust
async fn large_across_await() -> u8 {
    let bytes = black_box([7u8; 4096]);
    std::future::pending::<()>().await;
    black_box(bytes[0])
}

async fn large_before_await() -> u8 {
    let first = {
        let bytes = black_box([7u8; 4096]);
        black_box(bytes[0])
    };
    std::future::pending::<()>().await;
    first
}
```

按[@def-8.3.1]，`large_across_await` 里 `bytes` 在 `await` 之后才被 `bytes[0]` 使用，所以整个 4096 字节数组进帧；`large_before_await` 里 `bytes` 的活跃区间被一个内层作用域收在 `await` 之前，进帧的只剩一个 `u8`（`first`）。

第一种恢复时仍要访问bytes。
第二种只需保存一个u8。
大数组仍可能在首次poll的临时栈空间存在，但无需成为跨挂起状态的字段。
不要把帧缩小直接等同为所有时刻总内存都缩小相同倍数。

### 8.3.3 内存预算要按并发存活量计算

假设系统有K个同时挂起任务。
如果每个任务都保留一个4096字节缓冲区，帧内存规模会接近K乘以该容量。
还应加任务头、队列链接、分配器元数据及对齐浪费。

K不是每秒请求数。
请求到达率和并发存活量之间还取决于服务时间。
用QPS直接乘Future大小可能完全误判内存预算。

这是第 1 章「估计对象」纪律在内存上的翻版：先问「同时存活」是多少，再乘帧大小，而不是拿 QPS 当并发度（[@def-1.1.3]）。

### 8.3.4 Pin 不等于堆分配

::: def 定义 8.3.2 · Pin 钉住的是对象不是句柄 {#def-8.3.2}
`Pin<P>` 约束的是**被指向对象 `T` 的地址稳定性承诺**，不是外部指针本身的位模式（内存里各比特的具体排列）。`Pin<&mut T>` 可指向栈上对象，`Pin<Box<T>>` 把对象放进堆分配；移动 Box 句柄本身通常不移动堆上的 `T`，而移动一个普通 Future 值可能改变其地址。对 `T: Unpin`，Pin 不再限制通常的安全移动；对依赖地址稳定的 `!Unpin` 对象，安全接口不能随意取出可移动的 `T`。
:::

按[@def-8.3.2]，「用不用 Pin」和「放栈上还是堆上」是两个正交的问题，8.7 基准因此分开测。

`Pin<&mut T>` 可以指向栈上对象。
`Pin<Box<T>>` 把被钉住对象放在堆分配里。
移动Box句柄本身通常不会移动堆上的T。
移动一个普通Future值则可能改变其地址。

对于 `T: Unpin`，Pin不再限制通常的安全移动操作。
对于依赖地址稳定性的 `!Unpin` 对象，安全接口不能随意取出可移动的T。
Pin约束的是相应被指向对象，不是所有外部指针位模式。

### 8.3.5 为什么 poll 接收 Pin

某些Future在首次poll后形成内部自引用。
如果后续把整个状态对象memcpy到另一个地址，内部引用可能失效。
`Pin<&mut Self>` 让执行器在poll时遵守地址稳定协议。

这不表示每个Future一定包含自引用。
也不表示编译器必须在运行时维护一个「钉住标志」。
Pin主要通过类型和安全API限制表达承诺。
其包装尺寸与真正分配成本必须分开测——这条在 8.7 用两个存储策略对照。

### 8.3.6 投影也属于 unsafe 边界

从 `Pin<&mut Outer>` 访问内层字段，不能任意生成可移动引用。
对结构化pin字段的投影需要保持原来的地址稳定承诺。
随意调用get_unchecked_mut再mem::replace可能破坏该承诺。

本章驱动器使用标准库 `pin!` 宏。
不手写RawWaker。
也不为了说明Pin就实现一个容易出错的自引用容器。
把unsafe范围压小，有利于把注意力集中到通知协议。

### 8.3.7 思考：Pin 有没有运行时开销

::: think 思考 · 编译器会真的维护一个「钉住标志」吗 {#think-8.3.1}

有人说「`Pin` 是类型体操，运行时一定多存一个布尔标志、每次访问都检查」。用[@def-8.3.2]判断这句话哪里越界。

::: sol 解答

越界在「一定」。[@def-8.3.2] 明说 Pin 主要通过**类型与安全 API** 表达承诺，不保证运行时存在一个「钉住标志」；多数情况下它是零成本抽象，检查发生在编译期的接口约束上。至于包装尺寸与是否引入分配，必须像 8.7 那样分开测——把「Pin 语法」当成固定运行时开销，是把类型层承诺误算成机器层指令，和 8.1 里「凭签名报固定纳秒」同源（[@def-8.1.3]）。

:::

:::

### 8.3.8 小结与常见错误

**小结。**① 帧大小 = 跨挂起存活集合大小，不是局部变量之和（[@def-8.3.1]）；② 缩帧只缩帧，不等于所有时刻总内存（[@ex-8.3.1]）；③ 内存预算按并发存活量 K，不按 QPS（8.3.3）；④ Pin 钉的是对象地址稳定，与栈/堆正交（[@def-8.3.2]）；⑤ 投影是 unsafe 边界，本章靠 `pin!` 把它压小。下一节 [8.4 poll、Waker 与就绪通知](#sec-cpp-rust.2.8.4) 从「对象存了什么」转向「对象怎样被推进」。

::: errata 常见错误清单（8.3 节）

E-a **把帧大小当成所有局部变量之和。**只有跨 await 存活的进帧（[@def-8.3.1]）。

E-b **缩了帧就说总内存按同倍数下降。**首次 poll 的临时栈空间没被消除（[@ex-8.3.1]）。

E-c **用 QPS 直接乘 Future 大小估内存。**并发存活量 K ≠ 请求到达率（8.3.3）。

E-d **认为用了 Pin 就必须堆分配。**`Pin<&mut T>` 可指栈上对象（[@def-8.3.2]）。

E-e **把 Box 句柄可移动当成被钉对象可移动。**两者约束不同（[@def-8.3.2]）。

E-f **断言 Pin 有固定运行时开销。**它主要是类型层承诺，成本要分开测（[@think-8.3.1]）。

:::

## 8.4 poll、Waker与就绪通知 {#sec-cpp-rust.2.8.4}

本节回答一个问题：**poll 与 Waker 之间到底约定了什么？**前面几节把 async 还原成对象、量好帧大小（[@def-8.3.2]）；这一节讲推进它的协议——poll 只能「尽力往前推一下」，Waker 只递一个「以后再来看看」的机会，二者都不保证结果、也不该被当成忙轮询的许可证。

::: preview 先抓住一件事

poll 的返回只有 Ready 与 Pending 两种含义，Pending 必须伴随「将来会有通知」的义务；Waker 通知会被合并，通知次数不等于完成次数，更不等于 I/O 数量。把 wake 计数当进度，是本节要拦住的第一个错误。

:::

### 8.4.1 Future 契约不是忙轮询接口

::: def 定义 8.4.1 · poll 契约与 Pending 语义 {#def-8.4.1}
`poll` 应努力快速返回；资源未就绪时返回 `Pending`，并负责安排「以后能前进时通知」执行器。执行器不应在没有新通知时对所有 Future 紧密轮询。由此得到测量口径：**调度/挂起次数要数真正返回 `Pending` 的次数，而不是源码里 await 的个数**（承接[@def-8.2.2]的「一次 poll 可穿过多个已就绪 await」）。
:::

按[@def-8.4.1]，poll 应努力快速返回。
资源未就绪时返回Pending，并安排以后能前进时通知。
执行器不应在没有新通知时持续对所有Future进行紧密轮询。

Future可以把工作交给其他线程。
此时其他线程可能独立计算，Future只充当结果通道。
「Future本身惰性」不代表外部已启动的工作也一定暂停。

### 8.4.2 一个自唤醒的最小 Future

本章async-poll benchmark使用YieldOnce。
它第一次被poll时发出通知并返回Pending。
第二次被poll时返回Ready。
它不模拟网络延迟，也没有系统I/O。

```rust
struct YieldOnce(bool);

impl Future for YieldOnce {
    type Output = ();

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
        if self.0 {
            Poll::Ready(())
        } else {
            self.0 = true;
            cx.waker().wake_by_ref();
            Poll::Pending
        }
    }
}
```

bool字段可安全通过Pin修改，因为该类型本身是Unpin。
这个例子没有用unsafe解除地址约束。
每个新的YieldOnce值只产生一次Pending。

`self.0 = true;` 之所以安全，正因为 `YieldOnce` 是 `Unpin`（[@def-8.3.2]）：换到一个 `!Unpin` 的自引用 Future 上，同样的写法就不被允许。

### 8.4.3 wake 不意味着完成

Waker的作用是请求执行器再检查任务。
多个wake可能被合并成一次poll。
一次wake之后的poll也可能仍然Pending。
因此不要按通知次数累计已完成I/O数量。

最新一次poll提供的Waker应成为后续通知目标。
任务可能已换到另一个执行环境。
长期保存旧Waker而不更新，可能让通知到达错误位置。

这是[@def-8.4.1]的另一面：通知是「机会」不是「事件计数」。把它当计数去推进度，8.6 的数字就会被读错。

### 8.4.4 唤醒前检查与注册竞态

::: def 定义 8.4.2 · 丢通知（lost wake）与注册竞态 {#def-8.4.2}
结果生产者与 Future 之间要同时处理两个事件：结果已就绪、当前 Waker 已注册。若「检查谓词」和「注册 Waker」分处两个无协议的临界区，就可能落入窗口：消费者检查到未就绪，生产者置就绪却看不到已注册的 Waker 而不通知，消费者随后注册并 Pending——结果已存在，任务却不再被 poll。修复要么用同一把锁保护「检查 + 注册」，要么用经过证明的原子注册协议；仅在最后补一条 fence 不算解决。
:::

结果生产者和Future之间要同时处理两个事件。
一个是结果已准备。
另一个是当前Waker已注册。
二者若分开且无协议，可能出现丢通知。

```text
consumer: 检查ready，发现false
producer: 写结果，设置ready=true
producer: 看不到已注册waker，不通知
consumer: 注册waker
consumer: 返回Pending

结果已存在，但任务没有下一次被poll的机会
```

::: ex 例 8.4.1 · 这条交错需要内存乱序吗 {#ex-8.4.1}

上面的时序里，每一行单独看都合法。判断：

1. 触发这个丢通知，是否要求处理器乱序或编译器重排？
2. 「把 ready 改成 `AtomicBool` 并在末尾加一条 `fence`」能否可靠修复？
3. 为什么「在临界区内既读谓词又登记 Waker」是更稳的写法？

::: sol 解答

1. 不要求。按[@def-8.4.2]，完全合法（顺序一致）的线程交错就足以触发：问题在两条语句之间的窗口，不在重排。
2. 不能可靠修复。单加 fence 不消除「检查—注册」两步之间的窗口，谓词写与注册仍是分开的两个事件，交错照旧发生（这是原文明令禁止的「补一条 fence 就宣称解决」）。
3. 因为把两个事件放进同一临界区后，「读谓词」与「登记 Waker」之间不会再被生产者的置位插进来，要么消费者看到 ready、要么生产者看到已注册的 Waker，窗口被关闭（8.4.5 的 `Mutex<Shared>` 测试就是这么安排的）。

:::

:::

这个失败不要求发生内存乱序。
完全合法的线程交错就足以触发。
修复可以使用同一锁保护谓词与注册，或者使用经过证明的原子注册协议。
不能仅在最后补一条fence就宣称解决。

### 8.4.5 本章的跨线程完成测试

`bench/src/park.rs` 的测试使用 `Mutex<Shared>`。
Shared内含ready和`Option<Waker>`。
消费者在同一把锁内检查谓词并注册Waker。
生产者在同一把锁内设置ready并取走Waker。
实际wake在释放锁后执行。

这么安排不追求「所有地方无锁」。
它为验证driver提供一个容易检查的合法Future。
否则Future和driver一起有bug时，失败原因会难以定位。

这直接落实了[@def-8.4.2]的修复：谓词检查与 Waker 注册共锁，把 8.4.4 的窗口关掉；把真正的 wake 挪到锁外，只为缩短临界区，不改变「两个事件在一个临界区内」这一关键约束。

### 8.4.6 Wake 与 RawWaker

`Wake` 是基于Arc构建Waker的安全接口。
`wake(self: Arc<Self>)` 消费一次持有。
`wake_by_ref(&Arc<Self>)` 不要求调用者交出这次持有。
默认实现可能通过clone再wake完成。

本章显式实现wake_by_ref，直接执行通知。
这避免仅为该默认路径制造额外Arc克隆。
不过创建驱动器本身仍分配一个Arc通知对象。
不应把它描述为整个block_on完全零堆分配。

RawWaker还需自己维护clone、wake、wake_by_ref、drop四个函数与数据指针的所有权协议。
它不是「更底层所以一定更快」的自动选项。
只有清楚需要何种存储布局时才值得扩大unsafe审查范围。

「零堆分配」这种全局断言，和[@def-8.1.3]「别凭签名报固定纳秒」是同一类越界：Arc 通知对象的存在就把「完全零分配」否掉了，能说的是「相对默认路径少一次 clone」。

### 8.4.7 思考：通知能当进度用吗

::: think 思考 · 把 wake 次数当成 I/O 完成数 {#think-8.4.1}

有人为「这条连接完成了多少 I/O」写了一个计数器：每收到一次 wake 就 +1。结合[@def-8.4.1]和 8.4.3，说这个计数在什么前提下会偏大、什么前提下会偏小。

::: sol 解答

偏大：多个 wake 会被合并成一次 poll（8.4.3），一次就绪可能触发多次 wake，逐次 +1 会重复计数。偏小：一次 wake 之后的 poll 仍可能 Pending，真正的完成要等 poll 返回 Ready，而 Ready 不来自 wake 事件本身。结论按[@def-8.4.1]：完成度只能由 poll 的返回值给出，通知只是「再来检查」的机会（对照[@ex-8.4.1] 的窗口——通知甚至可能一个都不到）。

:::

:::

### 8.4.8 小结与常见错误

**小结。**① poll 只有 Ready/Pending，Pending 附带「将来通知」的义务（[@def-8.4.1]）；② wake 会被合并，通知次数 ≠ 完成次数 ≠ I/O 数量（[@think-8.4.1]）；③ 最新一次 poll 的 Waker 才是后续通知目标；④ 「检查—注册」分处两临界区会丢通知，须共锁或原子注册协议（[@def-8.4.2]、[@ex-8.4.1]）；⑤ `Wake` 是安全接口，`RawWaker` 要自己维护四函数所有权协议，不是「更底层就更快」。下一节 [8.5 单 Future 驱动器](#sec-cpp-rust.2.8.5) 用这套协议挡住丢唤醒。

::: errata 常见错误清单（8.4 节）

E-a **无新通知时紧密轮询所有 Future。**违反 poll 契约（[@def-8.4.1]）。

E-b **按 wake 次数累计完成的 I/O。**通知会被合并，也不代表 Ready（[@think-8.4.1]）。

E-c **长期缓存旧 Waker 不更新。**任务迁移后通知会打到错误位置（8.4.3）。

E-d **检查与注册分两步、靠一条 fence 兜底。**窗口没关，交错照旧（[@def-8.4.2]）。

E-e **把 `wake_by_ref` 省 clone 说成零分配。**驱动构造仍产生 Arc 通知对象（8.4.6）。

E-f **认为 RawWaker 更底层就一定更快。**它是协议负担，不是自动优化（8.4.6）。

:::

::: method 即时自测 · 8.4

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　`YieldOnce` 两次 poll 分别返回什么？为什么只产生一次 Pending？

::: sol 第 1 题答案
第一次：置位 `self.0`、`wake_by_ref`、返回 Pending；第二次：`self.0` 为真，返回 Ready。每个新值只在首 poll 走 else 分支一次，故恰一次 Pending（[@def-8.4.1]）。
:::

**第 2 题 · 辨析**　生产者与消费者都顺序一致、无乱序，还会丢通知吗？为什么？

::: sol 第 2 题答案
会。丢通知来自「检查谓词」与「注册 Waker」两步之间的交错窗口，不需要乱序即可触发（[@def-8.4.2]、[@ex-8.4.1]）。
:::

**第 3 题 · 应用**　要给任务完成做进度计数，你只能安全地数什么？

::: sol 第 3 题答案
数 poll 返回 Ready 的次数（或已就绪结果被消费的次数），不能数 wake；wake 只表示「有机会再 poll」（[@def-8.4.1]、[@think-8.4.1]）。
:::

**第 4 题 · 迁移**　一个 runtime 把 Waker 迁移到别的线程执行环境，却沿用了旧 Waker。按本节会出什么问题、怎么修？

::: sol 第 4 题答案
旧 Waker 可能把通知送到过期的执行位置，任务不再被正确 poll。修法是每次 poll 更新「当前 Waker」为最近一次提供的克隆，与注册竞态的「注册最新 Waker」是同一约束（8.4.3、[@def-8.4.2]）。
:::

## 8.5 单Future驱动器：防止丢失唤醒 {#sec-cpp-rust.2.8.5}

本节回答一个问题：**一个只有单个 Future 的驱动器，怎样既不忙轮询、又不把唤醒弄丢？**上一节的丢通知（[@def-8.4.2]）说的是 Future 内部；这一节把它翻到驱动器一侧——Pending 之后既不能死转 CPU 轮询，也不能盲目 park 把自己停死。OS 的 park/unpark 令牌看起来够用，其实不可靠。

::: preview 先抓住一件事

极简实现「Pending 就 thread::park」把正确性押在 unpark 令牌上，而令牌可被同线程别处吞掉。可靠做法是给驱动器一个自己的通知位 `notified`：park 只用来盖住「检查与停放之间」的窗口，真正保存「有通知」这件事的是驱动器自己的原子量。

:::

### 8.5.1 错误的极简循环

::: def 定义 8.5.1 · park/unpark 令牌不是通知的存储 {#def-8.5.1}
`thread::park` 让线程停放，`unpark` 递一个「可醒来一次」的令牌；令牌可在 park 之前存下，因此简单 Future 里「Pending 就 park」通常能跑。但令牌是**每 OS 线程一个、可被同线程其它代码消耗**的资源，它不是「本任务有待检查」这一事实的存储。把它当通知存储，就丢唤醒。
:::

许多入门实现只在Pending后调用thread::park。
如果Waker只调用unpark，在简单Future中通常能工作。
因为unpark令牌可在park之前存下。

但同一OS线程上的其他代码可能消耗这个令牌。
嵌套调用驱动器也可能互相干扰。
标准库Wake文档明确提醒极简示例不等于完整生产实现。

```text
poll中先wake当前线程
poll中其他逻辑调用park，消耗unpark令牌
poll返回Pending
driver再次park

此时没有新的unpark，driver可能永久等待
```

这个例子是对令牌协议的反例，不是建议在poll中阻塞。
即便业务Future原则上不应这么做，驱动器仍需清楚自己的适用边界。
反例与[@def-8.4.1]同源：poll 内不该做长期阻塞，但**驱动器必须假设它可能发生**，并据此设计自己的等待策略。

### 8.5.2 独立通知状态

我们增加一个不依赖OS线程令牌的AtomicBool。

### 8.5.3 对应的 Release/Acquire 边

通知者先写通知状态，再unpark。
driver读到true后重新poll。
更重要的载荷访问仍应由具体Future自己的同步机制保证。
本driver并不替所有Future兜底任意普通内存数据竞争。

通知位可以合并多次wake。
它不是计数信号量。
一次swap清掉true后，这一次poll负责检查是否仍有工作。
这符合Waker通知语义，而不是逐条消费消息语义。

「合并、不是计数」这句和[@think-8.4.1]是同一件事的两种表述：一个布尔位天然会吞掉多次 wake，所以绝不能用它推断完成了几个事件。

### 8.5.4 已实现代码的核心

以下是driver循环的节选。
完整版本在 `bench/src/park.rs`，还包含重入防护与Notify实现。

```rust
loop {
    match future.as_mut().poll(&mut context) {
        Poll::Ready(value) => return value,
        Poll::Pending => {
            while !notify.notified.swap(false, Ordering::Acquire) {
                thread::park();
            }
        }
    }
}
```

park允许伪唤醒。
因此醒来后重新检查通知状态，不直接推断资源已完成。
poll可再次Pending，driver同样继续按协议等待。

::: ex 例 8.5.1 · 令牌被吞之后，为什么 driver 还能前进 {#ex-8.5.1}

`consumed_park_token` 测试故意在 poll 内部把当前线程的 unpark 令牌消耗掉，再返回 Pending。对照[@def-8.5.1]与上面的循环，逐步说明 driver 接下来发生什么，以及为什么它不会永久停死。

::: sol 解答

Pending 后进入 `while !notified.swap(false, Acquire)`：若此前通知已把 `notified` 置 true，swap 返回 true，循环条件为假，**根本不 park**，直接回到再次 poll——这就是「独立通知位」兜住令牌被吞的情形（[@def-8.5.1]）。只有当 `notified` 为 false 时才 park，而此时靠的是「通知若发生在 swap 之后会补 unpark 令牌」这条窗口覆盖（8.5.2 读图）。两条路合起来，令牌丢失不再致命。测试断言「独立 notified 仍让 driver 前进」，就是这条。

:::

:::

### 8.5.5 拒绝嵌套执行

本实现用thread_local的Cell记录是否进入驱动器。
嵌套block_on直接panic，明确拒绝不支持的调用形态。
RAII进入守卫在正常返回和unwind时清除该标记。

这不是异步系统通用错误策略。
它是教学driver对重入行为的明确边界。
生产接口可以选择返回错误或更完整的嵌套模型。
隐式死锁比清楚拒绝更难排查。

这条边界和[@def-8.1.1]一致：本驱动器只承诺「单 Future、当前线程」，嵌套超出承诺范围，panic 是把适用边界写明，而不是掩盖成一次可能的死锁。

### 8.5.6 线程与任务局部存储

thread_local属于OS线程。
一个多线程任务执行器迁移Future时，thread_local值不会随Future迁移。
任务局部状态需要运行时单独实现。

本driver始终在调用它的线程上poll。
它接受Future，不要求Future: Send。
通知对象则通过Arc和原子安全地被其他线程持有。
把这两个对象的Send要求混为一谈，会无端限制单线程工作负载。

「Future 不要求 Send，但通知对象可跨线程」这两句要分开读，否则 8.8 会把它误当成迁移约束（见 8.8 的 Send 小节）。

### 8.5.8 思考：重复 50 次能证明无并发 bug 吗

::: think 思考 · 50 次重复意味着什么、不意味着什么 {#think-8.5.1}

### 8.5.9 小结与常见错误

**小结。**① park/unpark 令牌可被同线程吞掉，不能当通知存储（[@def-8.5.1]）；② 驱动器用自有原子位 `notified` 保存「有待检查」这一事实，park 只盖窗口（[@ex-8.5.1]）；③ 通知位会合并 wake、不是计数信号量（8.5.3）；④ 嵌套 block_on 明确 panic，是把[@def-8.1.1] 的边界写死；⑤ 50 次重复是回归保护不是正确性证明（[@think-8.5.1]）。下一节 [8.6 Benchmark A](#sec-cpp-rust.2.8.6) 把这套协议放进可计时的对照里。

::: errata 常见错误清单（8.5 节）

E-a **只靠 unpark 令牌保存通知。**令牌可被同线程别处消耗（[@def-8.5.1]）。

E-b **park 一次就认定资源已就绪。**伪唤醒常见，醒来必须重查谓词（8.5.4）。

E-c **把 `notified` 布尔位当计数信号量。**它会合并掉多余的 wake（8.5.3）。

E-d **允许嵌套 block_on 还指望隐式串行。**应显式拒绝或给出完整嵌套模型（8.5.5）。

E-e **混淆「Future 不要求 Send」与「通知对象可跨线程」。**两个对象约束不同（8.5.6）。

E-f **拿 50 次重复宣称无并发 bug。**它不是全交错检查（[@think-8.5.1]）。

:::

::: method 即时自测 · 8.5

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　`while !notified.swap(false, Acquire) { thread::park(); }` 为什么先 swap 再 park？

::: sol 第 1 题答案
先把「是否有通知」这一事实从驱动器自己的原子位读出并清零；只有读到 false（确无通知）才 park，从而把 park 限定在「检查与停放」窗口内，避免把令牌当存储（[@def-8.5.1]、[@ex-8.5.1]）。
:::

**第 2 题 · 辨析**　`consumed_park_token` 测试里令牌被吞，为什么不丢唤醒；而极简实现同样情形会永等？

::: sol 第 2 题答案
因为有独立的 `notified=true`：swap 读到 true 就不 park，直接重 poll。极简实现把「待检查」全押在令牌上，令牌被吞后 swap 处无从判断，便永久 park（[@def-8.5.1]）。
:::

**第 3 题 · 应用**　伪唤醒让 driver 从 park 返回，但 `notified` 仍是 false。按协议该做什么？

::: sol 第 3 题答案
重查通知位：仍 false 就再次 park 等待，不得据此推断资源就绪；完成与否只由下一次 poll 的返回值决定（[@def-8.4.1]、8.5.4）。
:::

**第 4 题 · 迁移**　把本驱动器换成多线程执行器，`thread_local` 的重入守卫会怎样失效？

::: sol 第 4 题答案
`thread_local` 属于 OS 线程，不随 Future 迁移；跨线程的任务局部状态需要运行时单独实现（8.5.6）。同理，重入判定也应基于「本执行器/任务」而非「本 OS 线程」。
:::

:::

## 8.6 Benchmark A：Ready路径与真实Pending路径 {#sec-cpp-rust.2.8.6}

本节回答一个问题：**「走 async」到底贵在哪一步？**本节没有把成本归给「async 关键字」，而是造三组做**同样整数累加**的模式：普通同步循环、通过 driver 推进但不主动让出的 async、每轮真正产生一次 Pending 的 async-self-wake。三者之差才是「协议本身」的成本，不是语法成本。

::: preview 先抓住一件事

三组都在做同一份工作，区别只在「有没有真正的调度边界」。self-wake 那组每轮多出来的，是 poll→`wake_by_ref`→置通知位→`unpark`→清位→再 poll 这条协议路径，而不是「函数调用多了 async」。读数前先把「测的是哪条路径」钉死，否则 7.4 会被误读成一次线程切换。

:::

### 8.6.1 对照组定义

`bench/src/bin/async_poll.rs` 比较三个模式。
它们都累加同样的整数序列。
输入在循环内经过black_box，避免直接化成等差数列公式。
每批结束校验总和。

同步模式执行普通函数循环。
async-ready模式通过driver推进一个不主动yield的async循环。
async-self-wake模式每轮先等待一个YieldOnce。

第三种每轮明确产生一次Pending。
第一和第二种没有相同的调度边界。
因此其差异不能简称为「async函数调用成本」。

这里把[@def-8.4.1]的口径落成实验：真正制造调度边界的是 self-wake 组每轮的那次 Pending，另两组没有等价边界，所以「async-ready 减 sync」测到的是状态机推进，「self-wake 减 async-ready」才更接近通知协议。

### 8.6.2 编译与执行

```bash
cargo run --offline --release \
  --manifest-path bench/Cargo.toml \
  --bin async-poll -- 100000 21
```

参数为每批元素数与保留批次数。
每种模式先执行一批不计入输出统计的预热。
测量顺序逐批轮换。
本机环境与第7章相同。

### 8.6.3 方法细节

driver为一次完整任务创建一个通知Arc。
不是每次YieldOnce都分配一个新的任务。
因此benchmark分摊了driver构造的成本。

同步组不调用driver。
async-ready组仍通过async_sum状态机执行。
yielding参数的分支与编译器能做的优化，也可能影响两者差异。
不应拿这两个组的差直接宣布某个抽象有固定指令数。

「一个 Arc / 完整任务」这条分摊很关键：它意味着下面的 ns/element 里不含每轮重新分配任务头的成本，比较对象因此是「通知协议」而不是「分配频率」。

### 8.6.4 原始样本统计

本表单位是 ns/element：一批 100000 个元素的墙钟除以元素数，得到「批均值」，21 批再算 mean/sd/p50/p99。它是**吞吐型聚合成本**，不是单次 poll 或单条指令的延迟；p99 是「批均值的分位数」，不是「一次 poll 的 p99」——批内 100000 个元素的抖动被平均掉了（[@def-1.5.2] 反复区分这两个对象）。

### 8.6.5 解释 Pending 路径中的工作

每次YieldOnce第一次poll修改bool状态。
它调用wake_by_ref。
Notify设置原子通知位并调用unpark。
外层Future返回Pending。
driver清除通知位并再次poll。
第二次poll让子Future完成，外层进入下一轮。

这条路径没有必然进入内核睡眠。
由于通知已经存在，driver通常无需实际park等待。
但调用unpark和通知状态的工作仍然存在。
不能把7.407 ns解释成OS线程切换耗时。

::: ex 例 8.6.1 · 把 7.407 拆成可核对的动作 {#ex-8.6.1}

self-wake 的均值是 7.407 ns/element，sync 是 0.519。有人写「一次异步调度切换要 7.4 ns」。用本节与 8.5 的协议反驳，并说明这 7.4 里到底包含了什么、没包含什么。

::: sol 解答

7.407 是「每元素的批均值」，不是「一次切换的延迟」（[@def-8.6.1]）。它包含的是每轮多出的协议动作：改 bool、`wake_by_ref`、置通知位、`unpark`、外层 Pending、driver swap 清位、再 poll 一次（8.5.4）。由于通知已存在，driver 通常**没有真正 park 进内核**（本条明说），所以不能读成 OS 线程切换耗时；它也没含任务头重复分配（[@def-8.6.1] 前的分摊）。差值 7.407−0.867 更接近「多一次真实 Pending 的协议成本」，仍不是单条指令数——「有固定指令数」这种断言本节明确拒绝。

:::

:::

### 8.6.6 为什么不能据此排名 Tokio

benchmark没有Tokio队列。
没有work stealing。
没有多任务公平性预算。
没有I/O资源注册。
没有定时器轮。
没有取消任务句柄。

因此它只测一个最小driver与具体Future的组合。
若换运行时，需要保持工作量、通知频率与计时边界一致。
不能用不同项目里的两个数字直接做优劣比较。

这和第 1 章的「比较对象要先相同」是同一条纪律（[@def-1.6.1] 的等价工作比较）：工作量、通知频率、计时边界三者对齐，才谈得上比。

### 8.6.7 业务上的含义

若每条消息只做极少计算却频繁自yield，调度工作可能占主导。
可以增加每次poll内的批处理量，减少通知频率。
但一次poll内工作太久，又会拖慢同线程其他任务。

批量化需要同时观察吞吐和公平性。
本benchmark只有一个Future，无法测出其他任务的尾延迟恶化。
系统级结论必须加入竞争任务与到达过程。

### 8.6.8 本机采样剖析

::: def 定义 8.6.2 · 采样栈计数不等于占比 {#def-8.6.2}
macOS `sample` 记录的是「某函数出现在折叠栈里的观察次数」，是**栈位置计数**：它既不是每条消息的耗时，也不是 CPU 周期或能耗；除以总计数得到的比例，在混入启动（dyld）观察、且未达稳定态时，不能当成稳定态 CPU 百分比。
:::

另开较长负载采样，避免把profiler扰动混进前面的计时表。

```bash
bench/target/release/async-poll 10000000 21 \
  > bench/results/profile/async-workload.txt &
pid=$!
sample "$pid" 1 -file bench/results/profile/async-sample.txt
wait "$pid"
```

报告顶部折叠栈中，block_on关联观察计数为401，Darwin Parker::unpark为59，sync_sum为28。
这是栈位置计数，不是每条消息的耗时，更不是CPU周期或能耗。
本次抓取还包含339条dyld启动位置观察，说明采样窗口受启动过程污染。
因此不能直接把401除以总计数，宣称某个稳定态CPU百分比。

该报告能够支持「实际执行路径包含driver与unpark」，不能单独分离一次wake成本。
若要测稳定态，应先预热并使长运行负载到达明确阶段，再启动采样。
它也不提供Linux perf事件，不能填入IPC或cache-miss比例。

按[@def-8.6.2]，这 401/59/28/339 只支持一句弱结论：driver 与 `unpark` 确在执行路径里；它既不给[@def-8.6.1] 的每元素成本，也不给任何百分比归因——339 条 dyld 尤其说明窗口被启动污染。

### 8.6.9 正确性出口

三个模式均校验累加结果。
测试通过只说明固定输入上的工作没有被漏掉。
它不证明任意自定义Future都遵守Waker契约。
错误Future可能永不wake，也可能在poll内部永久阻塞。

这种情况下driver不能凭空保证完成。
超时测试应在独立进程外层设置，避免挂起整个测试运行器。
本章不把该测试driver描述为可运行不可信任务的沙箱。

「测试通过」在这里只排除「工作被删掉」这一类误测（同[@def-1.1.1] 的反面检查），不升级成「任意 Future 都守约」——那是[@def-8.4.1] 契约层面的问题，测试夹具证明不了。

### 8.6.10 思考：换更大的数字能升级结论吗

::: think 思考 · 把单 Future 的均值推广到服务 {#think-8.6.1}

有人拿 self-wake 的 7.407 去除 sync 的 0.519，得「async 比同步慢 14 倍」，并写进选型报告。用本节列出这句话至少踩了哪三个坑。

::: sol 解答

① 分母口径错：7.407 与 0.519 是批均值/元素，不是「一次 async vs 一次同步」的倍数（[@def-8.6.1]）；② 比较对象不同：self-wake 每轮多一次真实 Pending，sync 根本没有该边界，差里混的是协议工作量而非「async 本身」（[@def-1.6.1]）；③ 外推越界：单 Future、无竞争任务、无到达过程，推不出服务尾延迟，也没有采集 IPC/cache-miss（[@def-8.6.2]、8.6.7）。正确写法是把这三层各自限定结论范围，而不是压成一个「慢 14 倍」。

:::

:::

### 8.6.11 小结与常见错误

**小结。**① 三组做同样累加，差异只在有无真实调度边界（[@def-8.4.1]）；② 7.407 是批均值/元素，不是切换延迟，也不能算固定指令数（[@def-8.6.1]、[@ex-8.6.1]）；③ 采样计数只支持「路径含 driver/unpark」，不支持 CPU 占比（[@def-8.6.2]）；④ 没有 Tokio 队列/窃取/公平性，不能排名运行时（8.6.6）；⑤ 测试通过只排除「工作被删」，不证明契约（8.6.9）。下一节 [8.7 Benchmark B](#sec-cpp-rust.2.8.7) 换一类边界：存储策略。

::: errata 常见错误清单（8.6 节）

E-a **把 7.407 说成一次 OS 线程切换。**driver 通常没真正 park（[@ex-8.6.1]）。

E-b **拿两组的差宣布固定指令数。**分支与内联都可能改变差异（8.6.3）。

E-c **把批均值 p99 当单次 poll p99。**分母是批、不是请求（[@def-8.6.1]）。

E-d **用 `sample` 计数除总计数报 CPU 百分比。**含启动污染、非稳定态（[@def-8.6.2]）。

E-e **据本基准排名 Tokio。**工作量与边界不同，不可直接比（8.6.6）。

E-f **测试通过就认为任意 Future 守约。**契约与误测是两回事（8.6.9）。

:::

::: method 即时自测 · 8.6

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　三组模式各自「多做了什么」？为什么不能叫它「async 函数调用成本」？

## 8.7 Benchmark B：栈上pin与Box分配 {#sec-cpp-rust.2.8.7}

本节回答一个问题：**栈上 `pin!` 与 `Box::pin` 的差，是「Pin 抽象」的差还是「存储/分配策略」的差？**上一节 8.6 测的是通知协议；这一节把变量换成「对象放哪」，其余（同样的 Future、同样的 `drive`、同样的 payload 准备）都钉死，才让差值只归给存储策略。

::: preview 先抓住一件事

`Pin` 是类型包装、不是系统调用（[@def-8.3.2]）。本实验故意让对象逃逸（经 `black_box` 传入不可内联的 `drive`），否则编译器可能把两种存储都消掉、量不到东西。测到的差包含 256 字节 payload 准备、Future 初始化、一次 Ready poll 与销毁——所以它既不是「Pin 指令成本」，也不能外推成「所有 `Box::pin` 的固定耗时」。

:::

### 8.7.1 要测的不是 Pin 本身

`Pin`本身是类型包装，不是一个内建系统调用。
栈上pin与Box::pin的主要区别在于存储与分配策略。
如果benchmark让对象完全不逃逸，编译器可能把两者都消掉。

本实验故意把Pin引用经black_box传入不可内联的drive函数。
这样保持存储策略对编译器可见。
测量包含256字节payload准备、Future初始化、一次Ready poll和销毁。
不能把最终差值称作「Pin指令成本」。

### 8.7.2 实验函数

```rust
async fn ready(payload: [u8; 256]) -> u64 {
    black_box(payload[0] as u64)
}

#[inline(never)]
fn drive<F: Future<Output = u64>>(
    future: Pin<&mut F>,
    cx: &mut Context<'_>,
) -> u64 {
    match future.poll(cx) {
        Poll::Ready(value) => value,
        Poll::Pending => panic!("ready future unexpectedly pending"),
    }
}
```

drive用于两种存储方式，Future的具体类型相同。
Waker::noop用于这个保证立即Ready的例子。
不要把noop Waker拿去驱动实际Pending I/O任务——它的「不通知」只在这个恒 Ready 的对象上安全，换成真 Pending 就成了 8.4 里[@def-8.4.2] 的反面。

### 8.7.3 两种存储策略

```rust
let value = if heap {
    let mut future = Box::pin(ready(payload));
    drive(black_box(future.as_mut()), &mut context)
} else {
    let future = pin!(ready(payload));
    drive(black_box(future), &mut context)
};
```

Box在分支结束后释放。
因此计时不是只包含申请而排除销毁。
栈上对象也在相应作用域结束后销毁。
最终结果总和被检查为 `iters * 7`。

两个分支唯一受控的差别就是 `Box::pin` 与 `pin!`，其余同形——按[@def-8.3.2]「Pin 与栈/堆正交」设计对照：被比的是存储策略，不是 Pin 类型本身。

### 8.7.4 首轮漂移不能藏掉

第一次试跑只给每个模式预热一个批次。
记录显示stack从前期约13.35降到后期7.89 ns。
box从约37.60降到18.71 ns。
这种持续漂移不能当作稳定对照。

原始试跑保存在 `future-allocation-drift.txt`。
该日志对应增加500ms预热之前的夹具版本。
它是失败方法的保留证据，不参与最终稳定结果统计。
不把它删掉，然后假装第一次就测到了理想数据。

::: ex 例 8.7.1 · 为什么保留一份「没用上」的漂移日志 {#ex-8.7.1}

首轮 stack 从前三个样本的约 13.3 一路掉到 7.89，box 从约 37.60 掉到 18.71；但两条序列都**不是严格单边**：box 在样本 1 反而涨到 40.22（全表最大值），stack 在样本 3 跳到 17.56。既然最终表用了稳定后的 8.241/19.817，为什么还要留这份旧日志？

::: sol 解答

因为这份日志记录了「为什么需要 500ms 预热」这一决策的证据（对照第 1 章 1.10 的 E-c：「在多张表里挑最快的一张发布」就是选择偏差[@def-1.7.3]）。**高起点加回落**的形态与预热不足一致，但 21 个样本不足以把它和随机噪声干净分开——本轮没有采集逐样本的计数器，所以这里只能说形态吻合，不能说已排除噪声；若只发布漂亮的稳定均值、删掉漂移批次，读者就无法判断 8.241 是不是又一个没预热够的瞬时值。保留它并写明「不参与最终统计」，是把[@def-1.8.2] 的复算/重跑分开：最终表可复算，预热修改有独立留档可核对。

### 8.7.9 工程选择边界

栈上pin适用于词法上能确保对象存储稳定且不逃逸的驱动方式。
任务要存入动态队列，通常需要更长生命周期的存储。
可能是Box，也可能是slab、arena或嵌入式静态任务槽。

不要仅因一次Box微基准有额外成本，就断言生产执行器绝不能堆分配。
一次任务分配可能被成千上万次poll与I/O工作分摊。
真正应检查的是每请求、每任务、每poll各分配多少次。

「每请求 / 每任务 / 每 poll 各分配几次」正是[@def-8.3.1] 帧存活分析的分配版：把「Pin 快不快」的伪问题，换成「分配发生在哪一层、被谁分摊」的真问题。

### 8.7.10 实际汇编里的分配证据

完整产物已经保存到 `bench/results/local/future-allocation.s`。
在batch的Box分支，不只是出现了名叫alloc的字符串。
能够沿控制流看到申请、填充、drive、释放的完整序列。

以下仅把较长的Rust符号缩写为其函数职责。
指令与大小参数来自实际产物。

```asm
mov w0, #257
mov w1, #1
bl  __rust_alloc
cbz x0, allocation_failure

; 此处有多组ldp/stur，把捕获载荷写入新分配
; 状态初始化为未恢复
strb wzr, [x0]

; 黑盒后的地址传给具体Future的drive
bl  drive_ready_future

; 正常返回后释放相同大小与对齐的分配
mov x0, allocated_pointer
mov w1, #257
mov w2, #1
bl  __rust_dealloc
```

缩写的allocated_pointer不是一条可直接汇编的寄存器（CPU 内部最快取用的小存储格）名称。
本段用于阅读调用关系，完整可核对机器文本保存在.s文件中。
不把注释改写后的片段冒充逐字反汇编输出。

申请参数说明该版本请求257字节、对齐1字节。
实际分配器可能使用更大的内部size class。
因此不能把257字节直接称为物理驻留内存增量。

栈分支同样调用具体Future的drive。
它没有对应的每次Future堆申请与释放对。
但仍包含payload物化与寄存器/栈的数据移动。
这与测得8.241 ns不是「绝对零工作」相一致。

### 8.7.11 ABI / 代码生成核对表

下表是 `drive_ready_future` 符号的实际观察，不是稳定Rust ABI承诺。

| 边界/字段 | 本轮目标代码 | 可以解释的含义 |
|:--|:--|:--|
| 具体Future引用 | 以x0指向对象，使用`ldrb w8, [x0]` | 状态先从对象首字节读取 |
| 捕获payload首字节 | `ldrb w8, [x0, #1]` | 此版本数据起于状态后的偏移1 |
| Ready后状态 | `mov w9, #1; strb w9, [x0]` | 记录完成，不是无状态重复调用 |
| 返回u64 | `mov x0, x8`再返回 | 结果经本轮函数返回寄存器传递 |
| Box申请参数 | `w0=257, w1=1`后调用分配入口 | 大小与对齐明确保留在申请路径 |

Context在本例Ready Future中没有业务用途。
优化器可以删去未使用的参数处理，不应期待所有源码形参都留下实际机器指令。
若改为dyn Future或真正Pending资源，调用边界需要重新核对。

「数据起于状态后的偏移 1」与[@def-8.2.2] 的判别值、[@def-8.2.1] 的帧字段布局相互印证：状态字节在前、载荷在后。`ldrb w8, [x0]` 读的就是那个判别值。

### 8.7.12 从探针迁移到真实服务

若服务把多个任务放到异构队列里，可能额外出现dyn Future调用。
本探针的drive仍是具体类型的单态化函数。
它没有测虚表间接分派。

若服务复用任务槽，本探针每轮Box申请也不再代表该服务的分配频率。
要增加新的复用组，首先定义槽位初始化和取消后的清理责任。
不能只把Box移出循环，却允许前一个Future的内部引用逃逸。

若服务保留大缓冲区跨多个await，帧大小也会远大于257字节。
应按真实的跨挂起字段重复生成MIR与布局记录。
这样微基准才成为解释工具，而不是一个脱离任务形态的排行榜。

dyn Future 的间接分派、任务槽复用、跨多个 await 的大缓冲——这三条分别越过了[@def-8.1.3]（静态 vs 擦除）、[@def-8.3.1]（帧存活）与本节的分配假设。迁移前先按真实形态重新生成证据，别把探针数字直接搬进服务结论。

### 8.7.13 思考：11.6 纳秒能叫「malloc 税」吗

::: think 思考 · 把两个均值相减当成分配成本 {#think-8.7.1}

19.817 − 8.241 ≈ 11.6 ns。有人说「这就是每次 `Box::pin` 的 malloc+free 成本」。按[@def-8.7.1] 与本节汇编，指出这句至少哪里过头。

::: sol 解答

过头在三处：① 两个均值各自还含 payload 初始化与一次 Ready poll，相减不保证只剩分配（[@def-8.7.1]）；② 8.241/19.817 是当前环境、257 字节、未锁核未控温的数字，11.6 不是常数（8.7.5）；③ 分配是否真的发生，光看均值不够，还得回到汇编核对——若编译器消除分配，这 11.6 就归错因（8.7.8 的核查清单即为此）。汇编显示 Box 分支确有 `__rust_alloc`/`__rust_dealloc` 成对，才允许把差值「大致」归给分配对，但仍要写成「本次测量的分配路径成本」，不是「malloc 税」。

:::

:::

### 8.7.14 小结与常见错误

**小结。**① Pin 是类型包装、不是系统调用，被测的是存储策略（[@def-8.3.2]）；② 差值只能命名到真实测量操作，不是「Pin 开销」（[@def-8.7.1]）；③ 首轮漂移要保留、预热针对观测到现象（[@ex-8.7.1]）；④ 8.241/19.817 是当前环境与 257 字节的数，不外推（8.7.5）；⑤ 生产别因一次 Box 微基准就禁堆分配，要看每请求/每 poll 分配几次（[@def-8.3.1]）。下一节 [8.8 接口边界](#sec-cpp-rust.2.8.8) 从「怎么测」转向「哪些能力不由语言自动保证」。

::: errata 常见错误清单（8.7 节）

E-a **把 box−stack 的差叫「Pin 指令成本」。**差值只归给存储/分配对（[@def-8.7.1]）。

E-b **删掉漂移批次只留漂亮均值。**违反证据纪律（[@ex-8.7.1]）。

E-c **把 19.817 当所有 `Box::pin` 的固定耗时。**它绑定 257 字节与当前环境（8.7.5）。

E-d **让对象完全不逃逸还自称测了分配。**编译器可能把两种存储都消掉（8.7.1）。

E-e **据一次 Box 微基准断言执行器绝不能堆分配。**分摊与复用没进判断（8.7.9）。

E-f **把探针结论直接搬到 dyn Future/复用槽的服务。**边界变了要重测（8.7.12、[@def-8.1.3]）。

:::

## 8.8 取消、阻塞、多线程与多进程的接口边界 {#sec-cpp-rust.2.8.8}

本节回答一个问题：**一个 Future 被丢弃之后，究竟有多少事情真的停下了？**8.7 讲了驱动器如何推进任务；这一节处理它推不动的部分——已提交给外部世界的工作、阻塞调用、跨线程迁移与跨进程边界。

::: preview 先抓住一件事

**取消首先是生命周期事件，不是控制流事件。**drop 一个挂起的 Future 会清理它当前的 Rust 字段，但不会回滚已经发生的副作用：写进 socket 的字节不会从对端消失，已提交给设备的请求也不会自动撤销。判断一段代码「取消安全不安全」，要看它在哪些阶段可以被丢弃、哪些状态已经提交出去——只看 `Drop` 实现正确，证明不了业务层的取消语义。

:::

### 8.8.1 取消安全是一条接口性质

::: def 定义 8.8.1 · 取消安全 cancel safety {#def-8.8.1}

一个异步操作是**取消安全**的，指它在任何一次 `.await` 处被丢弃后，外部可观察状态仍然属于「要么完全没做，要么完整做完」这两种之一。做不到时就必须写明它允许的中间态，以及调用方在取消后需要做的补偿。

:::

这条定义解释了三件常见误解。第一，「字段析构了」不等于「外部操作回滚了」（[@def-8.8.1]）。第二，`select!` 里丢掉一个分支，剩下的那个分支可能已经把请求发出去了。第三，重复执行的风险与取消风险是同一枚硬币的两面——没做完的那一半，重试时可能被再做一次。

### 8.8.2 一个已经跑过的析构探针

这段程序执行两次构造/销毁路径：一次在首次 poll 之前销毁，一次 poll 到 `Pending` 之后销毁，用 `AtomicUsize` 统计 `Guard` 的析构次数。输出是：

```text
drop before first poll: 0 guards; drop after Pending: 1 guard
```

这是一个可复现的状态检查，不是基准测试——不要把析构次数和运行时间混成同一个指标。它证明的是：本例里编译器按当前挂起状态清理了 `Guard`，也就是状态机把 `Guard` 放进了挂起态路径。它不证明任意 FFI 资源、任意进程终止方式都能这样恢复。

::: ex 例 8.8.1 · 两个读数分别说明了什么 {#ex-8.8.1}

上面的输出里，第一次销毁计数是 0、第二次是 1。为什么第一次不是 1？如果第二次的计数也是 0，你会先查什么？

::: sol 解答

第一次销毁发生在**首次 poll 之前**：状态机还停在初始态，`Guard` 根本没有被构造出来，自然没有析构可计。第二次在 `Pending` 之后销毁，`Guard` 已经作为跨挂起点存活的局部对象存在于状态机字段里，drop Future 就会 drop 它，所以计数为 1。若第二次也是 0，先查两件事：`Guard` 是否在 poll 内构造但没跨过挂起点（那样它在前一次 poll 返回时就已析构），以及计数用的 `AtomicUsize` 是否与被测 Future 共享了同一份（放错位置会读到另一个实例的计数）。

:::

:::

### 8.8.3 阻塞调用放进 async 里，仍然是阻塞

如果 poll 内部调用耗时的文件读取或等待外部进程，承载线程就无法及时 poll 其他任务。`.await` 只描述 Future 协议，不会把任意阻塞函数变成异步 I/O。可选方案有三种：换成真正的非阻塞驱动、把阻塞工作放到专门的线程池、或者干脆放进独立进程。CPU 密集型任务同理，需要限制并发度，避免把所有执行线程长时间占住——选哪一种取决于取消、资源限制与隔离要求（[@def-8.8.1] 的补偿责任在三种方案里差别很大）。

### 8.8.4 跨线程迁移的三个要求

Future 若要被可能跨线程迁移的执行器持有，通常需要 `Send`；跨 `.await` 存活的局部字段决定这个 Future 是不是 `Send`。若其中含 `Rc` 或某些非 `Send` 的 guard，这个 Future 就不能安全迁移。`async move` 只改变捕获所有权的方式：它不把 `Rc` 变成 `Arc`，也不给内部状态自动加锁。

还有一条容易漏的协议：**Future 返回 `Ready` 之后不应再被 poll**。具体实现可以 panic、阻塞或产生其他非预期行为，但 `poll` 是安全方法，合法调用本身不能被实现者用来引入未定义行为。自定义 Future 通常要显式记录完成状态；运行时则要让队列里的过期唤醒与任务完成状态协调——队列里残留一个 `Arc`，不意味着任务还应该继续执行。

### 8.8.5 跨进程不是跨线程的自然推广

`Waker` 里的数据指针与函数表属于当前进程，`Arc` 的引用计数也不提供进程间共享的生命期。把 `Waker` 的原始内存复制到另一个进程再调用其中的函数指针，是无效做法。进程工作池必须定义自己的消息协议：父进程记录请求 ID、子进程身份、提交状态与完成状态；子进程退出时要通知等待中的 Future，而不是让对端永久停在 `Pending`。

::: think 思考 · 超时的 Future 丢掉就够了吗 {#think-8.8.1}

一个工具调用超时后，你把等待它的 Future 丢掉，函数返回「已取消」。这算完成了吗？

::: sol 解答

不算。丢掉 Future 只停止**你这一侧的等待**；子进程可能还在跑，双路管道里没人读的那一路随时会被写满，把子进程阻塞在半路上，而它占着的资源要等到进程退出才释放。所以超时路径至少要补三件事：终止并回收进程（含后代）、排空两路输出、把「已取消」与「已回收」分开报告。第 15 章要按项验收这三件事，这也是本节所述接口边界的具体化。

:::

:::

### 8.8.6 Agent 工具 runtime 需要的额外约束

工具执行可能同时产生 stdout 与 stderr，只读其中一路，另一路满了就会阻塞子进程；超时不能只丢弃等待 Future，还要处理子进程与后代的生命周期；有界队列要在**接收请求之前**执行背压；取消请求要区分「尚未开始」与「已提交执行」；日志截断要记录丢弃的字节数，而不是无声截断后仍报告完整成功。本章的单 Future 驱动器不提供上述任何一项，项目章的验收应逐项覆盖，不能因为 `block_on` 能跑就称为完整 runtime。

### 8.8.7 下一阶段各层要测什么

| 层级 | 需要测的指标 | 容易混淆的量 |
|:--|:--|:--|
| 编译器 | 帧大小、代码体积、内联与分支 | 单凭 `async` 关键字估算开销 |
| 单任务 | poll 次数、实际 `Pending` 次数 | `await` 的源码数量 |
| 调度器 | 每任务入队次数、窃取次数、队列深度 | wake 总次数 |
| OS 线程 | CPU 时间、阻塞、迁移 | Future 对象数量 |
| 多进程工具 | 在途请求、管道积压、回收时间 | 只测 `spawn` 返回 |

这些指标要分别记录，因为一个层级的优化常把成本挪到另一个层级：减少分配可能增大常驻任务槽，增加批处理可能损伤公平性。性能工程要保留这类权衡，而不是只收集最快的那一列。

### 8.8.8 小结与常见错误

**小结。**① 取消是生命周期事件，`Drop` 清理字段不等于回滚外部副作用（[@def-8.8.1]）；② 析构探针证明的是状态机把对象放进了哪条路径，不是性能数据（[@ex-8.8.1]）；③ `.await` 不把阻塞调用变成异步，阻塞要挪走；④ `Send`、完成状态与过期唤醒都是协议的一部分；⑤ 跨进程要自己的消息协议，`Waker` 不能搬过去；⑥ 超时要同时管进程与管道（见本节思考框）。下一节 [8.9 延伸阅读与来源](#sec-cpp-rust.2.8.9) 交代这些结论的出处。

::: errata 常见错误清单（8.8 节）

E-a **把 drop 当成回滚。**已写出的字节、已提交的请求都不会因为 Future 销毁而撤回（[@def-8.8.1]）。

E-b **用析构次数当性能指标。**它是状态路径检查，回答「有没有构造」，不回答「快不快」。

E-c **在 poll 里做阻塞 I/O。**承载线程被占住，其他任务连被 poll 的机会都没有。

E-d **认为 `async move` 解决了线程安全。**它只改捕获方式，`Rc` 仍是 `Rc`。

E-e **对已完成的 Future 继续 poll。**实现侧要显式记完成态，运行时要清理过期唤醒。

E-f **把 `Waker` 复制到另一个进程。**函数表属于原进程，跨进程必须走消息协议。

E-g **超时只丢 Future。**子进程与两路管道没人回收，资源会拖到进程退出。

E-h **在接收请求之后才背压。**队列已经被填满，背压失去了意义。

:::

::: method 即时自测 · 8.8

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　写出取消安全的定义，并说明「`Drop` 正确」为什么不够。

::: sol 第 1 题答案
取消安全指任何一次 `.await` 处被丢弃后，外部可观察状态只有「没做」或「完整做完」两种（[@def-8.8.1]）。`Drop` 只保证本进程内的字段被清理，管不到已发出的网络字节、已提交的设备请求与另一个进程里的工作，所以它既不必要也不充分地证明业务取消安全。
:::

**第 2 题 · 辨析**　「`async move` 把捕获都变成了 `Send`。」这句话错在哪？

::: sol 第 2 题答案
错在两处：`async move` 只决定按值捕获，不改变被捕获值的类型属性；`Rc` 仍是 `Rc`，内部可变状态也不会自动加锁。Future 是否 `Send`，取决于所有跨 `.await` 存活的字段，而不是捕获方式。
:::

**第 3 题 · 应用**　一个任务超时被你丢弃，进程数却持续上涨。按本节你会先查什么？

::: sol 第 3 题答案
先查超时路径有没有终止并回收子进程：丢弃 Future 只停止等待，子进程可能还活着；再查双路管道是否只读了一路，另一路写满后子进程会卡住不退出。两处都补上之后，才谈「已取消」这个状态（[@think-8.8.1]）。
:::

**第 4 题 · 迁移**　你要把本章的单 Future 驱动器换成多线程执行器，列出三项必须先补的协议。

::: sol 第 4 题答案
① `Send` 边界：跨 `.await` 存活的字段都要满足 `Send`；② 完成状态与过期唤醒的协调：任务完成后队列里可能还有唤醒，不能再次 poll；③ 取消与回收的责任划分：阻塞工作要么挪进专用线程池，要么放进独立进程，并写明取消后谁来清理。三项都对应 8.8.3–8.8.5 的内容。
:::

## 8.10 常见错误索引 {#sec-cpp-rust.2.8.10}

这一节是全章的常见错误索引；每一节的 `::: errata 常见错误清单（8.M 节）` 已经就地列出该节的具体错误，这里不再重述。下面十二条跨过了小节边界，只有把构造、驱动与取消放在一起读时才暴露，每条都按误判、机制与修法三件事展开。

1. **以为 async 会自动启动线程。** 只构造 Future 并不会执行其中的函数体，没有 poll 推进它就停在初始状态。把构造、提交与完成三个计时点分开，才能看出等待发生在哪一段。

2. **以为 await 必然切换任务。** 已就绪的子 Future 可以在同一次 poll 里继续推进，调度次数并不等于 await 的个数。统计真正返回 Pending 的次数，才能估准切换成本。

3. **以为 Pin 必然堆分配。** Pin 是类型包装，不是分配器；它约束的是对象地址，并不决定对象放在栈上还是堆上。按生命周期选择 `pin!`、`Box` 或任务池，再分别测量各自的成本。

4. **以为 Future 尺寸等于所有源码局部变量之和。** 帧里只保存跨 await 存活的字段，其余局部量可以在挂起前结束。内存预算要核对 MIR 与 `size_of_val`，不能照抄源码变量表。

5. **仅靠 unpark 令牌保存通知。** 同线程的 park 可能消费掉令牌，真正的通知到达时已无处记录。驱动器要有独立的 `notified` 谓词，并用窗口测试覆盖令牌被吞的交错。

6. **先检查 ready 再独立注册 Waker。** 检查与注册分处两个临界区时，生产者可能正好落在窗口里，结果已到却不再 poll。应把两者放进同一把锁，或采用成熟的原子注册协议。

7. **用 noop Waker 驱动真实 I/O。** noop Waker 没有合法通知目标，返回 Pending 之后任务会永久睡眠。它只适合保证 Ready 的路径或布局探针。

8. **把 drop 当成外部事务回滚。** 取消只结束本地状态机，不会撤回已经发出的消息或已经提交的外部操作。提交与回收要各自定义协议，并在文档里写清哪一步不可逆。

9. **把 Future 的 Send 与 Waker 的 Send 混为一谈。** 两者约束的是不同对象：前者管帧字段能否跨线程移动，后者管通知回调能否跨线程调用。分别检查帧字段与通知对象，别用一个约束去推另一个。

10. **把 Box 分配差值当成 Pin 语法开销。** 差值里还有 payload 初始化、drive 与分配器行为，不能整体记在 Pin 名下。结果要按完整测量操作命名，例如「一次构造加 Ready 销毁」。

11. **删除漂移批次却不说明筛选。** 只留下漂亮均值会隐藏预热不足的事实，读者无法判断最终值是不是又一个没预热够的瞬时值。保留首轮日志，并公开预热修改与重跑结果。

12. **以为 Future 内的阻塞调用会被 await 自动异步化。** poll 被长期占用时，同线程上的其他任务只能等待，await 不会把阻塞变成异步。改用真正的事件驱动，或把阻塞工作交给有界工作池。

## 8.11 本章小结与章末件 {#sec-cpp-rust.2.8.11}

::: note 本章小结

- 调用 async 函数得到的是还没算的 Future，构造、提交、完成是三个时点（[@def-8.1.2]、[@ex-8.1.1]）。
- 帧里只放跨 await 存活的字段，帧大小不是源码局部变量之和（[@def-8.2.1]、[@def-8.3.1]）。
- Pin 钉住的是对象地址，与放在栈上还是堆上无关（[@def-8.3.2]）。
- poll 只有 Ready 与 Pending，Pending 附带将来通知的义务；检查与注册必须共用临界区（[@def-8.4.1]、[@def-8.4.2]）。
- park/unpark 令牌不能当通知存储，驱动器要有自己的 `notified` 位（[@def-8.5.1]、[@ex-8.5.1]）。
- 7.407 是批均值/元素，8.241 与 19.817 只能命名到真实测量操作（[@def-8.6.1]、[@def-8.7.1]）。
- 取消是生命周期事件，Drop 不回滚外部提交，跨进程要另立协议（[@def-8.8.1]、[@ex-8.8.1]）。

:::

::: method 即时自测 {#method-cpp-rust.2.8.1}
一条请求在poll里循环处理100万条记录，没有await到Pending。
这会不会自动让同线程任务每条记录都有运行机会？
不会。
Future协议是协作式推进接口；执行线程仍在当前poll里。
应限制每次poll的工作预算，或把CPU工作交给有界并行工作池。

把YieldOnce的wake_by_ref删除，driver是否仍应忙轮询直到它Ready？
不应。
Future若返回Pending却不安排未来通知，就不能要求事件驱动executor凭空推进。
本driver没有轮询所有任务的兜底计时器。

为什么「栈上pin更快」不能直接变成「禁止Box任务」？
因为任务生命周期、逃逸、动态队列和复用方式不同。
本benchmark测一次构造与Ready销毁，不测长期I/O任务摊销。
接口可实现性与实际分配频率都应进入设计判断。
:::
