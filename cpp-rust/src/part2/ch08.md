把线程阻塞调用换成async函数，并不自动减少工作量。
如果函数内部继续调用阻塞I/O，它仍会占住执行poll的线程。
如果没有真正的挂起，await也不必发生任务调度。
如果每处理一个字节都主动唤醒自己，调度协议可能比计算本身更贵。

因此异步性能的分析单位不能只用“协程切换”四个字。
要拆成Future构造、帧存储、一次poll、通知、入队和线程唤醒。
这些阶段可能被内联消除，也可能因对象逃逸和动态分派而保留下来。
编译器和运行时各负责一部分，不能把全部成本归给Rust语法。

本章只实现一个单Future驱动器。
它没有socket reactor，也不伪装成Tokio替代品。
我们用这个小范围，把最容易被黑箱掩盖的协议展开。
更复杂的多任务运行时需要额外的就绪队列、取消、背压与回收设计。

::: def 定义 8.1 · 驱动边界 {#def-cpp-rust.2.8.1}
Future描述可恢复计算；driver负责何时再次poll；通知只提供重新检查的机会。
本章的block_on仅驱动单个Future，不包含多任务调度与I/O注册。
:::

## 8.1 async函数构造的是对象，不是线程 {#sec-cpp-rust.2.8.1}

### 调用与执行体的边界

调用async函数会捕获参数并产生实现Future的匿名值。
函数体的计算由后续poll推进。
不需要在这个调用点创建OS线程。
也不需要语言内置一个全局调度器。

这个区分影响错误处理与测量。
只测Future构造，没有测到完成异步工作。
只测spawn返回，也没有测到任务结果。
只测第一次poll，对真正的I/O工作通常仍不完整。

先看本章的取消探针。
源文件是 `bench/examples/future_layout.rs`。
其中 `cancellation_probe` 在函数体内构造Guard，再等待永远Pending的子Future。

```rust
async fn cancellation_probe(count: Arc<AtomicUsize>) {
    let _guard = Guard(count);
    std::future::pending::<()>().await;
}
```

调用后直接drop该Future，Guard还没被构造。
其中捕获的Arc参数仍需要正常销毁。
“函数体未执行”不等于“Future里什么资源都没有”。

第一次poll进入函数体，Guard才成为一个活跃局部对象。
在Pending之后drop，则必须释放这个Guard。
这是编译器管理暂停状态的具体责任。

### 四层对象关系

<pre class="layout">
     源码层：async fn operation(args)
                    |
                    v
     编译器层：匿名Future，含状态判别与跨await存活字段
                    |
              Pin&lt;&amp;mut Future&gt;
                    |
                    v
     执行层：driver/executor 调用 poll(context)
                    |
               +----+----+
               |         |
             Ready     Pending
               |         |
          交付结果     等待wake后再检查

     OS线程：承载poll调用，不等于上面的Future对象
     I/O驱动：报告资源就绪，不等于编译器生成的状态机
</pre>

读图：Future可以存在于线程栈、Box或专用任务分配中。
存储策略不是async关键字固定规定的。
poll由执行层调用，可能在当前线程，也可能由任务调度器迁移。
是否迁移还要满足Send与运行时接口要求。

### Future没有自动并行性

两个Future在同一线程上轮流poll，可以形成并发等待。
它们不会因此同时在两个物理核心上计算。
要利用多核执行CPU工作，需要多线程调度或显式并行机制。

同一个Future通常不能被两个线程同时poll。
`poll`需要独占的 `Pin<&mut Self>`。
运行时必须保证任务不会并发获得两个这样的访问权。
不能因为Waker可从多个线程调用，就推导poll也能同时执行。

### 函数返回的impl Future

匿名Future经常通过 `impl Future<Output=T>` 隐藏具体类型。
这不自动意味着动态分派。
泛型调用链可在编译期知道其具体类型并进行单态化。

相反，`Pin<Box<dyn Future<Output=T> + Send>>` 使用类型擦除。
它可能引入堆分配与间接poll调用。
是否保留这些成本，要看对象是否逃逸、优化是否去虚化。
不要只按签名做固定纳秒数估计。

### 边界表

| 概念 | 负责内容 | 不负责内容 |
|:--|:--|:--|
| async函数 | 构造可恢复计算对象 | 不创建内置线程池 |
| Future::poll | 推进一次状态机 | 不保证这次就完成 |
| Waker | 请求任务再次被检查 | 不携带本次计算结果 |
| executor | 管理就绪任务与poll时机 | 不必亲自完成I/O |
| reactor / I/O驱动 | 追踪I/O就绪或完成 | 不决定语言级局部变量生命周期 |
| OS调度器 | 给线程分配CPU执行机会 | 不直接理解任意Rust Future |

## 8.2 MIR里保存了什么 {#sec-cpp-rust.2.8.2}

### 从源码生成可核对产物

下列命令在稳定工具链可运行。
它输出面向人阅读的MIR，不承诺格式跨版本稳定。
不要把每个编号当成ABI。

```bash
cd bench
rustc --edition=2021 --crate-type=bin \
  --emit=mir -C opt-level=0 \
  examples/future_layout.rs \
  -o results/local/future-layout.mir
```

本章保存的文件来自rustc 1.99.0。
其中包含构造函数、poll状态机、Guard析构与多个布局探针。
它与 `-Z dump-mir` 的逐Pass输出不是同一个接口。
不要求为了基础复现先安装nightly。

### 实际状态摘要

在 cancellation_probe 的MIR中，可以看到以下布局摘要。
这是本轮产物的节选，而非手写一个假定枚举去冒充编译结果。

```text
coroutine layout {
    field _s0: Guard;
    field _s1: std::future::Pending<()>;
    variant_fields = {
        Unresumed(0): [],
        Returned (1): [],
        Panicked (2): [],
        Suspend0 (3): [_s0, _s1],
    }
}
```

Suspend0保存了Guard与正在等待的子Future。
Unresumed、Returned、Panicked标识状态用途。
编号0、1、2、3只描述这个版本的输出。
语言没有保证所有Future都按这些字节编号布局。

### 构造函数没有执行业务体

同一文件里的构造函数很短。
它把count参数移入coroutine对象，然后返回。
Guard初始化出现在后续poll路径，而不是构造路径。

```text
fn cancellation_probe(count) -> anonymous_future {
    anonymous_future = coroutine { count: move count };
    return anonymous_future;
}
```

这里为了说明读取方式，对局部名字做了简化。
完整原始MIR保留在结果目录中。
不能把简化图中的字段顺序视作内存保证。

### poll入口检查判别值

实际MIR读取Future的discriminant。
随后按状态跳转到不同基本块。
首次进入会构造Guard与子Future。
恢复进入会继续poll之前的子Future。

```text
discriminant = discriminant(future)
switchInt(discriminant):
    0 -> 首次执行路径
    1 -> 完成后恢复的错误路径
    2 -> panic后恢复的错误路径
    3 -> Suspend0恢复路径
```

这说明恢复不是“从头重跑async函数”。
需要跨await存活的数据已经在帧里。
不需要重新解析源代码或构建调用栈字符串。

### Ready与Pending分支

子Future返回Pending时，外层记录挂起状态并返回Pending。
子Future返回Ready时，外层取出结果，继续后面的普通逻辑。
若后面还有await，可能在同一次poll里继续推进到下一个挂起点。

因此，一次poll并不等于跨一个await。
多个已就绪await可以在同一次poll中通过。
真正消耗调度边界的是实际返回Pending的路径。

### 取消与正常结束的不同出口

正常结束路径销毁活跃局部对象，再设置完成状态。
panic展开路径清理对应活跃对象，再继续展开。
外部drop处于挂起态的Future，也需要按当前状态清理其字段。

这里讨论的是正常Rust析构与unwind路径。
若进程abort或被操作系统直接终止，不能保证执行全部Drop。
不要写“所有资源在任何退出情况下都确定释放”。

### 编译器内部模型的阅读纪律

Guide to Rustc Development 本地PDF319–321页说明了单态化收集与MIR lowering。
PDF277–279页说明MIR上的移动与初始化跟踪。
这些章节可以帮助理解状态字段为何需区分活跃与已移出。

但这份PDF不是本机1.99.0所有内部模块名的保证。
解释本次函数具体降低结果，仍以本轮生成文件为准。
母本提供机制框架，不替代版本化产物。

## 8.3 帧大小、存活分析与Pin的边界 {#sec-cpp-rust.2.8.3}

### 两个只差作用域的探针

第一种让4096字节数组跨await存活。
第二种在await前取出所需字节，结束数组的局部作用域。
两个Future都先等待一个永不就绪的子Future。
所以没有把I/O差异混进布局问题。

```rust
async fn large_across_await() -> u8 {
    let bytes = black_box([7u8; 4096]);
    std::future::pending::<()>().await;
    black_box(bytes[0])
}

async fn large_before_await() -> u8 {
    let first = {
        let bytes = black_box([7u8; 4096]);
        black_box(bytes[0])
    };
    std::future::pending::<()>().await;
    first
}
```

第一种恢复时仍要访问bytes。
第二种只需保存一个u8。
大数组仍可能在首次poll的临时栈空间存在，但无需成为跨挂起状态的字段。
不要把帧缩小直接等同为所有时刻总内存都缩小相同倍数。

### 类型与对象布局实测表

运行：

```bash
cargo run --offline --release \
  --manifest-path bench/Cargo.toml \
  --example future_layout
```

本轮输出的布局如下。

| 对象 | size字节 | align字节 | 解释边界 |
|:--|--:|--:|:--|
| 跨await数组Future | 4097 | 1 | 保存数组与该版本状态编码 |
| await前缩短作用域Future | 2 | 1 | 保存必要字节与状态 |
| 分配基准里的Ready Future | 257 | 本基准只输出size | 256字节捕获载荷加状态 |

前两行的对齐来自 `align_of_val`。
第三行不填一个未经该输出记录的对齐数字。
若需要分析分配器size class，应额外打印Layout并重新记录。

### 内存预算要按并发存活量计算

假设系统有K个同时挂起任务。
如果每个任务都保留一个4096字节缓冲区，帧内存规模会接近K乘以该容量。
还应加任务头、队列链接、分配器元数据及对齐浪费。

这里的K不是每秒请求数。
请求到达率和并发存活量之间还取决于服务时间。
用QPS直接乘Future大小可能完全误判内存预算。

### Pin不等于堆分配

`Pin<&mut T>` 可以指向栈上对象。
`Pin<Box<T>>` 把被钉住对象放在堆分配里。
移动Box句柄本身通常不会移动堆上的T。
移动一个普通Future值则可能改变其地址。

对于 `T: Unpin`，Pin不再限制通常的安全移动操作。
对于依赖地址稳定性的 `!Unpin` 对象，安全接口不能随意取出可移动的T。
Pin约束的是相应被指向对象，不是所有外部指针位模式。

### 为什么poll接收Pin

某些Future在首次poll后形成内部自引用。
如果后续把整个状态对象memcpy到另一个地址，内部引用可能失效。
`Pin<&mut Self>` 让执行器在poll时遵守地址稳定协议。

这不表示每个Future一定包含自引用。
也不表示编译器必须在运行时维护一个“钉住标志”。
Pin主要通过类型和安全API限制表达承诺。
其包装尺寸与真正分配成本必须分开测。

### 投影也属于unsafe边界

从 `Pin<&mut Outer>` 访问内层字段，不能任意生成可移动引用。
对结构化pin字段的投影需要保持原来的地址稳定承诺。
随意调用get_unchecked_mut再mem::replace可能破坏该承诺。

本章驱动器使用标准库 `pin!` 宏。
不手写RawWaker。
也不为了说明Pin就实现一个容易出错的自引用容器。
把unsafe范围压小，有利于把注意力集中到通知协议。

## 8.4 poll、Waker与就绪通知 {#sec-cpp-rust.2.8.4}

### Future契约不是忙轮询接口

poll应努力快速返回。
资源未就绪时返回Pending，并安排以后能前进时通知。
执行器不应在没有新通知时持续对所有Future进行紧密轮询。

Future可以把工作交给其他线程。
此时其他线程可能独立计算，Future只充当结果通道。
“Future本身惰性”不代表外部已启动的工作也一定暂停。

### 一个自唤醒的最小Future

本章async-poll benchmark使用YieldOnce。
它第一次被poll时发出通知并返回Pending。
第二次被poll时返回Ready。
它不模拟网络延迟，也没有系统I/O。

```rust
struct YieldOnce(bool);

impl Future for YieldOnce {
    type Output = ();

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
        if self.0 {
            Poll::Ready(())
        } else {
            self.0 = true;
            cx.waker().wake_by_ref();
            Poll::Pending
        }
    }
}
```

bool字段可安全通过Pin修改，因为该类型本身是Unpin。
这个例子没有用unsafe解除地址约束。
每个新的YieldOnce值只产生一次Pending。

### wake不意味着完成

Waker的作用是请求执行器再检查任务。
多个wake可能被合并成一次poll。
一次wake之后的poll也可能仍然Pending。
因此不要按通知次数累计已完成I/O数量。

最新一次poll提供的Waker应成为后续通知目标。
任务可能已换到另一个执行环境。
长期保存旧Waker而不更新，可能让通知到达错误位置。

### 唤醒前检查与注册竞态

结果生产者和Future之间要同时处理两个事件。
一个是结果已准备。
另一个是当前Waker已注册。
二者若分开且无协议，可能出现丢通知。

```text
consumer: 检查ready，发现false
producer: 写结果，设置ready=true
producer: 看不到已注册waker，不通知
consumer: 注册waker
consumer: 返回Pending

结果已存在，但任务没有下一次被poll的机会
```

这个失败不要求发生内存乱序。
完全合法的线程交错就足以触发。
修复可以使用同一锁保护谓词与注册，或者使用经过证明的原子注册协议。
不能仅在最后补一条fence就宣称解决。

### 本章的跨线程完成测试

`bench/src/park.rs` 的测试使用 `Mutex<Shared>`。
Shared内含ready和`Option<Waker>`。
消费者在同一把锁内检查谓词并注册Waker。
生产者在同一把锁内设置ready并取走Waker。
实际wake在释放锁后执行。

这么安排不追求“所有地方无锁”。
它为验证driver提供一个容易检查的合法Future。
否则Future和driver一起有bug时，失败原因会难以定位。

### Wake与RawWaker

`Wake` 是基于Arc构建Waker的安全接口。
`wake(self: Arc<Self>)` 消费一次持有。
`wake_by_ref(&Arc<Self>)` 不要求调用者交出这次持有。
默认实现可能通过clone再wake完成。

本章显式实现wake_by_ref，直接执行通知。
这避免仅为该默认路径制造额外Arc克隆。
不过创建驱动器本身仍分配一个Arc通知对象。
不应把它描述为整个block_on完全零堆分配。

RawWaker还需自己维护clone、wake、wake_by_ref、drop四个函数与数据指针的所有权协议。
它不是“更底层所以一定更快”的自动选项。
只有清楚需要何种存储布局时才值得扩大unsafe审查范围。

## 8.5 单Future驱动器：防止丢失唤醒 {#sec-cpp-rust.2.8.5}

### 错误的极简循环

许多入门实现只在Pending后调用thread::park。
如果Waker只调用unpark，在简单Future中通常能工作。
因为unpark令牌可在park之前存下。

但同一OS线程上的其他代码可能消耗这个令牌。
嵌套调用驱动器也可能互相干扰。
标准库Wake文档明确提醒极简示例不等于完整生产实现。

```text
poll中先wake当前线程
poll中其他逻辑调用park，消耗unpark令牌
poll返回Pending
driver再次park

此时没有新的unpark，driver可能永久等待
```

这个例子是对令牌协议的反例，不是建议在poll中阻塞。
即便业务Future原则上不应这么做，驱动器仍需清楚自己的适用边界。

### 独立通知状态

我们增加一个不依赖OS线程令牌的AtomicBool。
通知先设置notified，再调用unpark。
返回Pending后，driver反复检查notified，必要时才park。

<pre class="layout">
notifier:                             driver:
  notified.store(true, Release)          poll(future)
  thread.unpark()                       |
                                         +-- Ready -> 返回结果
                                         |
                                         +-- Pending
                                               |
                               notified.swap(false, Acquire)
                                      /                  \
                                  true                    false
                                   |                       |
                              再次poll                   park
                                                           |
                                                    醒来重新检查

OS令牌：只帮助避免检查与停放之间的丢唤醒
notified：保存本driver拥有的待检查通知事实
</pre>

读图：即便poll内部错误地消费了线程的unpark令牌，notified仍保留true。
因此driver会重查Future，而不是再次无条件park。
如果通知发生在swap读false之后，unpark令牌负责覆盖进入park之前的窗口。

### 对应的Release/Acquire边

通知者先写通知状态，再unpark。
driver读到true后重新poll。
更重要的载荷访问仍应由具体Future自己的同步机制保证。
本driver并不替所有Future兜底任意普通内存数据竞争。

通知位可以合并多次wake。
它不是计数信号量。
一次swap清掉true后，本轮poll负责检查是否仍有工作。
这符合Waker通知语义，而不是逐条消费消息语义。

### 已实现代码的核心

以下是driver循环的节选。
完整版本在 `bench/src/park.rs`，还包含重入防护与Notify实现。

```rust
loop {
    match future.as_mut().poll(&mut context) {
        Poll::Ready(value) => return value,
        Poll::Pending => {
            while !notify.notified.swap(false, Ordering::Acquire) {
                thread::park();
            }
        }
    }
}
```

park允许伪唤醒。
因此醒来后重新检查通知状态，不直接推断资源已完成。
poll可再次Pending，driver同样继续按协议等待。

### 拒绝嵌套执行

本实现用thread_local的Cell记录是否进入驱动器。
嵌套block_on直接panic，明确拒绝不支持的调用形态。
RAII进入守卫在正常返回和unwind时清除该标记。

这不是异步系统通用错误策略。
它是教学driver对重入行为的明确边界。
生产接口可以选择返回错误或更完整的嵌套模型。
隐式死锁比清楚拒绝更难排查。

### 线程与任务局部存储

thread_local属于OS线程。
一个多线程任务执行器迁移Future时，thread_local值不会随Future迁移。
任务局部状态需要运行时单独实现。

本driver始终在调用它的线程上poll。
它接受Future，不要求Future: Send。
通知对象则通过Arc和原子安全地被其他线程持有。
把这两个对象的Send要求混为一谈，会无端限制单线程工作负载。

### 本章测试覆盖

| 测试 | 安排的交错 | 断言 |
|:--|:--|:--|
| pre_park_notification | Future先wake再Pending | 下次poll能返回42 |
| consumed_park_token | poll内部消耗令牌 | 独立notified仍让driver前进 |
| nested_call | 外层poll中再次block_on | 明确拒绝，展开后守卫可恢复 |
| cross_thread_completion | 另一线程设置ready | 注册与就绪的两种先后均不丢通知 |

跨线程完成测试重复50次。
它不等于全交错模型检查。
尤其没有证明操作系统公平调度或有界响应时间。
测试的目的，是保证已构造的几个危险窗口不会悄悄退回极简错误实现。

## 8.6 Benchmark A：Ready路径与真实Pending路径 {#sec-cpp-rust.2.8.6}

### 对照组定义

`bench/src/bin/async_poll.rs` 比较三个模式。
它们都累加同样的整数序列。
输入在循环内经过black_box，避免直接化成等差数列公式。
每批结束校验总和。

同步模式执行普通函数循环。
async-ready模式通过driver推进一个不主动yield的async循环。
async-self-wake模式每轮先等待一个YieldOnce。

第三种每轮明确产生一次Pending。
第一和第二种没有相同的调度边界。
因此其差异不能简称为“async函数调用成本”。

### 编译与执行

```bash
cargo run --offline --release \
  --manifest-path bench/Cargo.toml \
  --bin async-poll -- 100000 21
```

参数为每批元素数与保留批次数。
每种模式先执行一批不计入输出统计的预热。
测量顺序逐批轮换。
本机环境与第7章相同。

### 方法细节

driver为一次完整任务创建一个通知Arc。
不是每次YieldOnce都分配一个新的任务。
因此benchmark分摊了driver构造的成本。

同步组不调用driver。
async-ready组仍通过async_sum状态机执行。
yielding参数的分支与编译器能做的优化，也可能影响两者差异。
不应拿这两个组的差直接宣布某个抽象有固定指令数。

### 原始样本统计

| 模式 | mean ns/element | 样本标准差 | 批次p50 | 批次p99 |
|:--|--:|--:|--:|--:|
| sync | 0.519 | 0.074 | 0.487 | 0.635 |
| async-ready | 0.867 | 0.108 | 0.870 | 1.125 |
| async-self-wake | 7.407 | 0.603 | 7.386 | 8.326 |

21个样本保存在 `bench/results/local/async-poll.txt`。
这里的p99是批均值分位数，不是一次poll的p99。
同一个批次处理100000个元素，掩盖了单个元素的抖动。

### 解释Pending路径中的工作

每次YieldOnce第一次poll修改bool状态。
它调用wake_by_ref。
Notify设置原子通知位并调用unpark。
外层Future返回Pending。
driver清除通知位并再次poll。
第二次poll让子Future完成，外层进入下一轮。

这条路径没有必然进入内核睡眠。
由于通知已经存在，driver通常无需实际park等待。
但调用unpark和通知状态的工作仍然存在。
不能把7.407 ns解释成OS线程切换耗时。

### 为什么不能据此排名Tokio

benchmark没有Tokio队列。
没有work stealing。
没有多任务公平性预算。
没有I/O资源注册。
没有定时器轮。
没有取消任务句柄。

因此它只测一个最小driver与具体Future的组合。
若换运行时，需要保持工作量、通知频率与计时边界一致。
不能用不同项目里的两个数字直接做优劣比较。

### 业务上的含义

若每条消息只做极少计算却频繁自yield，调度工作可能占主导。
可以增加每次poll内的批处理量，减少通知频率。
但一次poll内工作太久，又会拖慢同线程其他任务。

批量化需要同时观察吞吐和公平性。
本benchmark只有一个Future，无法测出其他任务的尾延迟恶化。
系统级结论必须加入竞争任务与到达过程。

### 本机采样剖析

另开较长负载采样，避免把profiler扰动混进前面的计时表。

```bash
bench/target/release/async-poll 10000000 21 \
  > bench/results/profile/async-workload.txt &
pid=$!
sample "$pid" 1 -file bench/results/profile/async-sample.txt
wait "$pid"
```

报告顶部折叠栈中，block_on关联观察计数为401，Darwin Parker::unpark为59，sync_sum为28。
这是栈位置计数，不是每条消息的耗时，更不是CPU周期或能耗。
本次抓取还包含339条dyld启动位置观察，说明采样窗口受启动过程污染。
因此不能直接把401除以总计数，宣称某个稳定态CPU百分比。

该报告能够支持“实际执行路径包含driver与unpark”，不能单独分离一次wake成本。
若要测稳定态，应先预热并使长运行负载到达明确阶段，再启动采样。
它也不提供Linux perf事件，不能填入IPC或cache-miss比例。

### 正确性出口

三个模式均校验累加结果。
测试通过只说明固定输入上的工作没有被漏掉。
它不证明任意自定义Future都遵守Waker契约。
错误Future可能永不wake，也可能在poll内部永久阻塞。

这种情况下driver不能凭空保证完成。
超时测试应在独立进程外层设置，避免挂起整个测试运行器。
本章不把该测试driver描述为可运行不可信任务的沙箱。

## 8.7 Benchmark B：栈上pin与Box分配 {#sec-cpp-rust.2.8.7}

### 要测的不是Pin本身

`Pin`本身是类型包装，不是一个内建系统调用。
栈上pin与Box::pin的主要区别在于存储与分配策略。
如果benchmark让对象完全不逃逸，编译器可能把两者都消掉。

本实验故意把Pin引用经black_box传入不可内联的drive函数。
这样保持存储策略对编译器可见。
测量包含256字节payload准备、Future初始化、一次Ready poll和销毁。
不能把最终差值称作“Pin指令成本”。

### 实验函数

```rust
async fn ready(payload: [u8; 256]) -> u64 {
    black_box(payload[0] as u64)
}

#[inline(never)]
fn drive<F: Future<Output = u64>>(
    future: Pin<&mut F>,
    cx: &mut Context<'_>,
) -> u64 {
    match future.poll(cx) {
        Poll::Ready(value) => value,
        Poll::Pending => panic!("ready future unexpectedly pending"),
    }
}
```

drive用于两种存储方式，Future的具体类型相同。
Waker::noop用于这个保证立即Ready的例子。
不要把noop Waker拿去驱动实际Pending I/O任务。

### 两种存储策略

```rust
let value = if heap {
    let mut future = Box::pin(ready(payload));
    drive(black_box(future.as_mut()), &mut context)
} else {
    let future = pin!(ready(payload));
    drive(black_box(future), &mut context)
};
```

Box在分支结束后释放。
因此计时不是只包含申请而排除销毁。
栈上对象也在相应作用域结束后销毁。
最终结果总和被检查为 `iters * 7`。

### 首轮漂移不能藏掉

第一次试跑只给每个模式预热一个批次。
记录显示stack从前期约13.35降到后期7.89 ns。
box从约37.60降到18.71 ns。
这种持续漂移不能当作稳定对照。

原始试跑保存在 `future-allocation-drift.txt`。
该日志对应增加500ms预热之前的夹具版本。
它是失败方法的保留证据，不参与最终稳定结果统计。
不把它删掉，然后假装第一次就测到了理想数据。

### 调整后的预热

最终程序先交替运行两个模式至少500ms。
然后再开始21批正式记录。
这个修复针对观察到的漂移，不保证所有硬件500ms就足够。

对绝对性能门禁，还应自动比较前后窗口、增加独立进程重复。
本章保留的桌面运行仍未锁核、未控制温度。
数值只作当前环境下的工程证据，不作为发布SLA。

### 复现命令

```bash
cargo run --offline --release \
  --manifest-path bench/Cargo.toml \
  --bin future-allocation -- 100000 21
```

源文件为 `bench/src/bin/future_allocation.rs`。
本轮Ready Future尺寸为257字节。
两个模式都做同样的payload准备。
分配器使用本机Rust默认系统分配器，没有替换jemalloc。

### 最终记录

| 模式 | mean ns/Future | 样本标准差 | 批次p50 | 批次p99 |
|:--|--:|--:|--:|--:|
| stack-pin | 8.241 | 0.306 | 8.183 | 8.953 |
| box-pin | 19.817 | 0.465 | 19.682 | 20.969 |

本次Box模式有额外成本。
但8.241不是栈上Pin抽象的固定开销。
19.817也不是所有Box::pin在所有payload尺寸下的耗时。
256字节初始化、优化屏障与非内联drive共同构成了当前操作。

### 汇编核查清单

先找两种路径是否都调用drive。
再找Box路径中分配与释放是否保留。
然后检查payload是否实际被物化。
最后看是否出现错误地把所有元素校验删掉的路径。

```bash
cargo rustc --offline --release \
  --manifest-path bench/Cargo.toml \
  --bin future-allocation -- --emit=asm
```

该命令的完整.s产物保存在target目录。
复核时应把实际产物与工具链版本一起归档。
若分配被消除，就不能再按“每次malloc/free”解释结果。

### 工程选择边界

栈上pin适用于词法上能确保对象存储稳定且不逃逸的驱动方式。
任务要存入动态队列，通常需要更长生命周期的存储。
可能是Box，也可能是slab、arena或嵌入式静态任务槽。

不要仅因一次Box微基准有额外成本，就断言生产执行器绝不能堆分配。
一次任务分配可能被成千上万次poll与I/O工作分摊。
真正应检查的是每请求、每任务、每poll各分配多少次。

### 本轮实际汇编的分配证据

已经把完整产物归档为 `bench/results/local/future-allocation.s`。
在batch的Box分支，不只是出现了名叫alloc的字符串。
能够沿控制流看到申请、填充、drive、释放的完整序列。

以下仅把较长的Rust符号缩写为其函数职责。
指令与大小参数来自本轮实际产物。

```asm
mov w0, #257
mov w1, #1
bl  __rust_alloc
cbz x0, allocation_failure

; 此处有多组ldp/stur，把捕获载荷写入新分配
; 状态初始化为未恢复
strb wzr, [x0]

; 黑盒后的地址传给具体Future的drive
bl  drive_ready_future

; 正常返回后释放相同大小与对齐的分配
mov x0, allocated_pointer
mov w1, #257
mov w2, #1
bl  __rust_dealloc
```

缩写的allocated_pointer不是一条可直接汇编的寄存器名称。
本段用于阅读调用关系，完整可核对机器文本保存在.s文件中。
不把注释改写后的片段冒充逐字反汇编输出。

申请参数说明该版本请求257字节、对齐1字节。
实际分配器可能使用更大的内部size class。
因此不能把257字节直接称为物理驻留内存增量。

栈分支同样调用具体Future的drive。
它没有对应的每次Future堆申请与释放对。
但仍包含payload物化与寄存器/栈的数据移动。
这与测得8.241 ns不是“绝对零工作”相一致。

### ABI / 代码生成核对表

下表是本轮 `drive_ready_future` 符号的实际观察，不是稳定Rust ABI承诺。

| 边界/字段 | 本轮目标代码 | 可以解释的含义 |
|:--|:--|:--|
| 具体Future引用 | 以x0指向对象，使用`ldrb w8, [x0]` | 状态先从对象首字节读取 |
| 捕获payload首字节 | `ldrb w8, [x0, #1]` | 此版本数据起于状态后的偏移1 |
| Ready后状态 | `mov w9, #1; strb w9, [x0]` | 记录完成，不是无状态重复调用 |
| 返回u64 | `mov x0, x8`再返回 | 结果经本轮函数返回寄存器传递 |
| Box申请参数 | `w0=257, w1=1`后调用分配入口 | 大小与对齐明确保留在申请路径 |

Context在本例Ready Future中没有业务用途。
优化器可以删去未使用的参数处理，不应期待所有源码形参都留下实际机器指令。
若改为dyn Future或真正Pending资源，调用边界需要重新核对。

### 从探针迁移到真实服务

若服务把多个任务放到异构队列里，可能额外出现dyn Future调用。
本探针的drive仍是具体类型的单态化函数。
它没有测虚表间接分派。

若服务复用任务槽，本探针每轮Box申请也不再代表该服务的分配频率。
要增加新的复用组，首先定义槽位初始化和取消后的清理责任。
不能只把Box移出循环，却允许前一个Future的内部引用逃逸。

若服务保留大缓冲区跨多个await，帧大小也会远大于257字节。
应按真实的跨挂起字段重复生成MIR与布局记录。
这样微基准才成为解释工具，而不是一个脱离任务形态的排行榜。

## 8.8 取消、阻塞、多线程与多进程的接口边界 {#sec-cpp-rust.2.8.8}

### 取消首先是生命周期事件

drop一个挂起Future会清理其当前活跃的Rust字段。
它不自动回滚已经执行的外部操作。
已写入socket的数据不会因Future销毁而从对端消失。
已提交给设备的请求也不必自动撤销。

因此取消安全是接口性质。
要说明任务在哪些阶段可丢弃、哪些状态已提交、是否有重复执行风险。
只有Drop正确，不足以证明业务取消正确。

### 已运行的析构探针

本轮程序执行两次构造/销毁路径。
第一次在首次poll之前销毁。
第二次poll到Pending后销毁。
用AtomicUsize统计Guard析构次数。

输出为：

```text
drop before first poll: 0 guards; drop after Pending: 1 guard
```

这是可复现的状态检查，不是benchmark。
不把析构次数和运行时间混成同一指标。
它证明本例编译器按当前挂起状态清理Guard。
不证明任意FFI资源或任意进程终止方式都可恢复。

### 阻塞调用放在async内部仍然阻塞

如果poll内部调用耗时文件读取或等待外部进程，承载线程就无法及时poll其他任务。
`.await`只描述Future协议，不会神奇地把任意阻塞函数转成异步I/O。

可选方案包括真正的非阻塞驱动、独立阻塞线程池或独立进程。
CPU密集任务也应限制并发度，避免把所有执行线程长时间占住。
具体选择取决于任务取消、资源限制与隔离要求。

### 多线程迁移的要求

Future若要被可能跨线程迁移的执行器持有，通常需要Send。
跨await存活的局部字段会影响Future的Send属性。
如果其中有Rc或某些非Send guard，Future可能不能安全迁移。

`async move`只改变捕获所有权方式。
它不把Rc变成Arc。
也不把内部非线程安全状态自动加锁。

### 一个任务不能被重复poll到完成以后

Future返回Ready后，调用者不应再poll它。
具体实现可以panic、阻塞或产生其他非预期行为。
不过poll是安全方法，合法调用本身不能被实现者用来引入未定义行为。

对自定义Future，完成状态通常应显式记录。
对运行时，队列里的过期唤醒需要和任务完成状态协调。
队列残留一个Arc并不意味着任务仍应继续执行。

### 跨进程不是跨线程的自然推广

Waker中的数据指针和函数表属于当前进程。
Arc引用计数也没有自动提供进程共享生命期。
不能把Waker原始内存复制到另一个进程，然后调用其中函数指针。

进程工作池应定义独立消息协议。
父进程记录请求ID、子进程身份、提交状态与完成状态。
子进程退出时要通知等待Future，而不是永久保留Pending。

### Agent工具runtime需要的额外约束

工具执行可能同时产生stdout和stderr。
只读其中一路，另一路满管道可能阻塞子进程。
超时不能只丢弃等待Future，还要处理子进程与后代进程生命周期。

有界队列要在接收请求前执行背压。
取消请求要区分尚未开始与已提交执行。
日志截断要记录丢弃字节，而不是无声截断后仍报告完整成功。

本章单Future驱动器不提供上述能力。
项目章的验收应逐项覆盖，而不能因为block_on能跑就称为完整runtime。

### 下一阶段的优化指标

| 层级 | 需要测的指标 | 容易混淆的量 |
|:--|:--|:--|
| 编译器 | 帧大小、代码体积、内联与分支 | 单凭async关键字估算开销 |
| 单任务 | poll次数、实际Pending次数 | await源码数量 |
| 调度器 | 每任务入队次数、窃取次数、队列深度 | wake总次数 |
| OS线程 | CPU时间、阻塞、迁移 | Future对象数量 |
| 多进程工具 | 在途请求、管道积压、回收时间 | 仅测spawn返回 |

这些指标应分别记录。
一个层级的优化也可能把成本挪到另一个层级。
例如减少分配可能增大常驻任务槽；增加批处理可能损伤公平性。
性能工程需要保留这种权衡，而不只收集最快的一列。

## 8.10 本章陷阱 {#sec-cpp-rust.2.8.10}

::: errata 本章陷阱
1. **async自动启动线程**。现象：只构造Future却不执行；原因：没有poll推进；修复：把构造、提交与完成三个计时点分开。
2. **await必然切换任务**。现象：错误估算调度次数；原因：Ready子Future可在同一次poll继续；修复：统计真正Pending的次数。
3. **Pin必然堆分配**。现象：每任务无端Box；原因：混淆包装与存储；修复：按生命周期选择pin!、Box或任务池，分别测量。
4. **Future尺寸等于所有源码局部变量之和**。现象：内存预算严重偏大；原因：忽略跨await活跃集合；修复：核对MIR和size_of_val。
5. **仅靠unpark令牌保存通知**。现象：中间park消耗令牌后永等；原因：driver无独立通知状态；修复：notified谓词循环加窗口测试。
6. **先检查ready再独立注册Waker**。现象：结果已到却不再poll；原因：生产者落在注册窗口；修复：统一保护检查与注册或采用成熟原子注册协议。
7. **noop Waker驱动真实I/O**。现象：Pending后永久睡眠；原因：没有合法通知目标；修复：仅在保证Ready或布局探针中使用noop。
8. **把drop当成外部事务回滚**。现象：取消后工具仍执行或消息已发出；原因：外部提交不由Future析构逆转；修复：定义提交与回收协议。
9. **Future Send与Waker Send混淆**。现象：单线程任务被无端约束或错误跨线程；原因：对象责任不同；修复：分别检查帧字段与通知对象。
10. **Box分配差值等于Pin语法开销**。现象：报告固定倍数；原因：忽略payload、drive和分配器；修复：按完整测量操作命名结果。
11. **删除漂移批次却不说明筛选**。现象：只剩漂亮均值；原因：选择性报告；修复：保留首轮日志，公开预热修改与重跑结果。
12. **Future内阻塞调用会被await自动异步化**。现象：同线程任务停顿；原因：poll被长期占用；修复：改用真正驱动或有界阻塞工作池。
:::

::: method 即时自测 {#method-cpp-rust.2.8.1}
一条请求在poll里循环处理100万条记录，没有await到Pending。
这会不会自动让同线程任务每条记录都有运行机会？
不会。
Future协议是协作式推进接口；执行线程仍在当前poll里。
应限制每次poll的工作预算，或把CPU工作交给有界并行工作池。

把YieldOnce的wake_by_ref删除，driver是否仍应忙轮询直到它Ready？
不应。
Future若返回Pending却不安排未来通知，就不能要求事件驱动executor凭空推进。
本driver没有轮询所有任务的兜底计时器。

为什么“栈上pin更快”不能直接变成“禁止Box任务”？
因为任务生命周期、逃逸、动态队列和复用方式不同。
本benchmark测一次构造与Ready销毁，不测长期I/O任务摊销。
接口可实现性与实际分配频率都应进入设计判断。
:::
