「看懂」只说明答案在眼前时能认出来；写代码、做评审时要的是从空白纸上提取。
这一页把第八章拆成 22 张卡：先读卡面，合上正文自己答，再展开核对。

**用法与节奏**

## 第一组 · 定义卡（说全称与前提）

::: ex 卡 1 · 驱动边界 {#rc-08-1}

卡面：Future、driver、通知各负责什么？通知带不带结果、保证不保证这次就完成？

::: sol 核对

Future 描述可恢复计算；driver 决定「何时再 poll」；通知只提供「重新检查一次」的机会。
通知不携带结果，也不保证这次就完成。
本章的 `block_on` 只驱动单个 Future，不含多任务调度与 I/O 注册。
对照[定义 8.1.1](ch08.md#def-8.1.1)。

:::

:::

::: ex 卡 2 · 静态返回与类型擦除 {#rc-08-2}

卡面：`impl Future` 与 `Pin<Box<dyn Future>>` 各意味着什么？哪一个才可能引入堆分配与间接 poll？

::: sol 核对

`impl Future<Output = T>` 只是编译期「名字未知」，泛型调用链仍可单态化，不等于动态分派。
`Pin<Box<dyn Future<Output = T> + Send>>` 才是类型擦除，可能带来堆分配与间接 poll 调用。
是否真的付出这两项，取决于对象是否逃逸、能否去虚化。
对照[定义 8.1.3](ch08.md#def-8.1.3)。

:::

:::

::: ex 卡 3 · 协程帧与状态变体 {#rc-08-3}

卡面：`field` 与 `variant_fields` 各记什么？`Unresumed`、`Returned`、`Panicked` 为什么常常是空列表？

::: sol 核对

`field` 行是帧里真实存放的字段；`variant_fields` 是状态机各变体：未恢复、已完成、panic 后、以及每个挂起点 `SuspendN`。
前三态没有需要跨挂起保存的数据：业务体还没跑，或活跃局部量都已析构，只剩一个判别值。
只有跨某个 await 仍存活的局部量，才成为该 `SuspendN` 的字段。
对照[定义 8.2.1](ch08.md#def-8.2.1)、[例 8.2.1](ch08.md#ex-8.2.1)。

:::

:::

::: ex 卡 4 · 判别值 {#rc-08-4}

卡面：协程对象头部那个判别值有什么用？恢复一次 poll 时发生了什么？

::: sol 核对

判别值记录当前处在哪个变体：`Unresumed`、`Returned`、`Panicked` 或某个 `SuspendN`。
poll 入口先读它，再用 `switchInt` 跳到对应基本块。
所以恢复是「读状态、跳过去、接着跑」，不是重新解析源码、从头重跑。
编号 0/1/2/3 只描述当前版本产物，不是 ABI。
对照[定义 8.2.2](ch08.md#def-8.2.2)、[思考 8.2.1](ch08.md#think-8.2.1)。

:::

:::

::: ex 卡 5 · 跨 await 存活 {#rc-08-5}

卡面：什么局部量必须进帧？一个很大的数组什么时候可以完全不进帧？

::: sol 核对

判据是「在某个挂起点之后是否还会被使用」。
会，就必须搬进对应的 `SuspendN` 字段；最后一次使用在 await 之前，就不必进帧——即使它很大。
这也是帧尺寸不等于「所有局部变量之和」的原因。
对照[定义 8.3.1](ch08.md#def-8.3.1)。

:::

:::

::: ex 卡 6 · Pin 钉的是对象 {#rc-08-6}

卡面：`Pin` 约束的是什么？`Pin<&mut T>` 能不能指向栈上对象？`T: Unpin` 时它还剩什么限制？

::: sol 核对

约束的是被指向对象 `T` 的地址稳定性承诺，不是外部指针本身的位模式。
`Pin<&mut T>` 可以指向栈上对象；`Pin<Box<T>>` 把对象放进堆分配。
移动 Box 句柄通常不移动堆上的 `T`，移动普通 Future 值则可能改地址。
对 `T: Unpin`，Pin 不再限制通常的安全移动。
对照[定义 8.3.2](ch08.md#def-8.3.2)。

:::

:::

::: ex 卡 7 · 丢通知与注册竞态 {#rc-08-7}

卡面：写出会丢通知的那段交错，并说出两种可靠修法。

::: sol 核对

交错：消费者检查 ready 为 false；生产者写结果、置 ready；生产者看不到已注册 Waker，不通知；消费者注册 Waker 并返回 Pending。
结果已存在，任务却不再有机会被 poll。
修法：用同一把锁保护「检查谓词 + 注册 Waker」，或用经过证明的原子注册协议。
仅在最后补一条 fence 不算解决。
对照[定义 8.4.2](ch08.md#def-8.4.2)、[例 8.4.1](ch08.md#ex-8.4.1)。

:::

:::

::: ex 卡 8 · 取消安全 {#rc-08-8}

卡面：写出取消安全的定义；为什么 `Drop` 实现正确还不够？

::: sol 核对

取消安全指：在任何一次 `.await` 处被丢弃后，外部可观察状态只有「完全没做」或「完整做完」两种。
做不到时，必须写明允许的中间态与调用方要做的补偿。
`Drop` 只清理本进程内的字段，管不到已写进 socket 的字节、已提交给设备的请求，也管不到另一个进程。
对照[定义 8.8.1](ch08.md#def-8.8.1)。

:::

:::

## 第二组 · 结论卡（说清前提与范围）

::: ex 卡 9 · 4097 与 2 {#rc-08-9}

卡面：两个只听一个 await 的 Future，尺寸为什么差这么多？这个差不能说明什么？

::: sol 核对

`large_across_await` 的 4096 字节数组在 await 之后仍被使用，整块进帧，尺寸 4097、对齐 1。
`large_before_await` 把数组收在内层作用域里，进帧的只剩一个 `u8`，尺寸 2。
差的是跨挂起帧字段，不是所有时刻的总内存：首次 poll 的临时栈空间仍可能出现大数组。
对照[例 8.3.1](ch08.md#ex-8.3.1)。

:::

:::

::: ex 卡 10 · 7.407 的口径 {#rc-08-10}

卡面：`async-self-wake` 的 7.407 是什么单位、什么分母？它里面包含哪些动作、不包含什么？

::: sol 核对

单位 ns/element，是一批 100000 个元素的墙钟除以元素数，21 批再算统计量，属于吞吐型聚合成本。
它含每轮多出的协议动作：改 bool、`wake_by_ref`、置通知位、`unpark`、外层 Pending、driver swap 清位、再 poll 一次。
它不含任务头重复分配；由于通知已存在，driver 通常没有真正 park，所以不能读成 OS 线程切换耗时。
对照[定义 8.6.1](ch08.md#def-8.6.1)、[例 8.6.1](ch08.md#ex-8.6.1)。

:::

:::

::: ex 卡 11 · 8.326 是谁的 p99 {#rc-08-11}

卡面：self-wake 的 p99 是 8.326。它是「最慢一次 poll」吗？它相对于什么分布取分位？

::: sol 核对

不是。它是 21 个批均值的最近秩分位数，每批含 100000 个元素，单元素抖动已被平均掉。
所以它是「批均值的分位数」，不是「一次 poll 的 p99」。
对照[定义 8.6.1](ch08.md#def-8.6.1)、8.6.4 的正文说明。

:::

:::

::: ex 卡 12 · 401、59、28、339 {#rc-08-12}

卡面：四个采样计数分别是什么？能支持哪一句结论、不能支持哪一句？

::: sol 核对

它们是 macOS `sample` 报告顶部折叠栈里各栈位置的观察次数：block_on 401、Darwin Parker::unpark 59、sync_sum 28，另有 339 条 dyld 启动位置观察。
这是栈位置计数，不是每条消息的耗时，也不是 CPU 周期或能耗。
能支持的弱结论：实际执行路径里包含 driver 与 `unpark`。
不能支持：把 401 除以总计数去报稳定态 CPU 百分比，或填入 IPC、cache-miss；339 条 dyld 已说明采样窗口被启动污染。
对照[定义 8.6.2](ch08.md#def-8.6.2)。

:::

:::

::: ex 卡 13 · 8.241 与 19.817 {#rc-08-13}

卡面：两个模式各测了哪一组操作？19.817 − 8.241 ≈ 11.6 能命名成什么？

::: sol 核对

两者跑同一组操作：准备 256 字节 payload、初始化 Future、一次 Ready poll、销毁；唯一受控差别是 `Box::pin` 与 `pin!`。
所以差值归给「堆申请/释放这一对」，不是「Pin 抽象的开销」。
汇编里 Box 分支确有成对的 `__rust_alloc` 与 `__rust_dealloc`（`w0=257, w1=1`），栈分支没有这一对。
对照[定义 8.7.1](ch08.md#def-8.7.1)、[思考 8.7.1](ch08.md#think-8.7.1)。

:::

:::

::: ex 卡 14 · 令牌不是通知的存储 {#rc-08-14}

卡面：为什么「Pending 就 `thread::park`」不够？驱动器真正该保存的是什么？

::: sol 核对

`unpark` 令牌是每 OS 线程一个、可被同线程其它代码消耗的资源，它不保存「本任务有待检查」这一事实。
同一线程上的其它代码、或嵌套调用驱动器，都可能先把它用掉；driver 随后无条件 park 就会永久等待。
驱动器应自己维护一个原子位 `notified`：通知先置位再 unpark；Pending 后用 swap 读并清零，读到 false 才 park。
park 只负责盖住「swap 读到 false」与「进入 park」之间的窗口。
对照[定义 8.5.1](ch08.md#def-8.5.1)、[例 8.5.1](ch08.md#ex-8.5.1)。

:::

:::

::: ex 卡 15 · 析构探针的 0 与 1 {#rc-08-15}

卡面：输出是 `drop before first poll: 0 guards; drop after Pending: 1 guard`。两个读数分别证明什么？

::: sol 核对

第一次在首次 poll 之前销毁：状态机还在初始态，`Guard` 从没被构造，所以计数为 0。
第二次在 Pending 之后销毁：`Guard` 已作为跨挂起存活的局部对象落在状态机字段里，drop Future 就会 drop 它，计数为 1。
它证明的是「编译器按当前挂起状态清理了 Guard」，是状态路径检查，不是性能数据。
对照[例 8.8.1](ch08.md#ex-8.8.1)。

:::

:::

::: ex 卡 16 · 50 次重复意味着什么 {#rc-08-16}

卡面：跨线程完成测试重复 50 次都过，等于「任何交错下都不丢唤醒」吗？

::: sol 核对

不等于。50 次只是已构造的几个危险窗口在当前机器、当前调度下各跑通一遍。
它不是全交错模型检查，也没证明 OS 公平调度或有界响应时间。
它给的是回归保护：不会悄悄退回极简错误实现。
对照[思考 8.5.1](ch08.md#think-8.5.1)、8.5.7 的测试表。

:::

::: ex 卡 19 · 结果到了，任务没再 poll {#rc-08-19}
