# 6 LLVM、CTFE 与可验证的优化边界

<div class="chapter-index">

**问题主线**：优化器需要哪些可证明事实，而程序员怎样确认这些事实真的变成了有用代码？

- 从真实 noalias、readonly 与循环 IR 解释优化依据。
- 用安全切片内核观察向量化、尾部与长度拒绝路径。

- 把 Miri 工具运行和编译器内的常量解释明确分开。
- 实际执行 ThinLTO 与 PGO 流程，但不虚构速度提升。

## 6.1 LLVM 得到的不是原样 Rust 源码 {#sec-cpp-rust.2.6.1}

### 后端只优化被保留下来的语义

rustc 在生成 LLVM IR 之前已经完成很多语言层工作。
类型已经明确。
借用检查已经排除了不合法访问。
析构责任已经转成合法控制流。
泛型代码也要在具体实例上生成。

LLVM 不需要重新理解 Rust 的每个 trait 约束。
它看到的是低层类型、控制流、调用、内存操作和属性。
这些属性携带部分前端已知事实。
优化是否合法，依赖这些事实与操作的真实语义。
随意违反引用契约会破坏优化依据。

这不是“LLVM 猜测指针大概不重叠”。
也不是“release 模式允许任意改变结果”。
合法输入的可观察行为仍受语言语义约束。
显式 wrapping 加法允许模运算变换。
普通浮点归约则不能默认套用相同结合律。

### 本章使用的整数域

正式向量内核使用 u64。
所有加法显式 wrapping。
因此溢出行为在 debug 与 release 之间保持一致。
CTFE 表使用 u8 输入域。
结果是一个字节内置一位的精确个数。

没有数值近似。
没有浮点误差容限。
没有多项式拟合或截断级数。
因此本章不会给出无来源的“误差小于某个 epsilon”。
精确性通过穷举字节域和逐元素测试验证。

### 优化事实传播图

读图：优化需要合法性，也需要成本判断。
前端事实足够，不表示后端必须选择向量化。
目标不同、版本不同、循环形态不同，都可能改变决策。
本章的图描述推理步骤，不是固定 pass 名字的执行日志。
实际结论以保留的产物为准。

### 真实 ABI 与代码生成观察

| 观察对象 | 本轮产物形态 | 不能扩大为的结论 |
|:--|:--|:--|
| add_slices 形参 | 两个切片各拆成指针与长度 | 稳定 Rust FFI ABI |
| output 指针 | noalias、align 8 等属性 | 任意 raw pointer 自动不别名 |
| input 指针 | readonly 等属性 | UnsafeCell 中所有共享访问只读 |
| 向量主体 | LLVM 的 2×i64 操作 | 所有 u64 循环都使用相同宽度 |
| runtime_table 返回值 | sret 指向 256 字节结果 | 所有数组都经同一种返回约定 |

本轮目标是 aarch64-apple-darwin。
源码没有手写目标专用 SIMD。
也没有用`target-cpu=native`额外启用本机特性。
目标默认能力仍足以生成后面看到的向量加法。
这不构成其他目标必须出现同样指令的承诺。

### 观察工具的分工

MIR 更适合检查语言控制流和析构责任。
LLVM IR 更适合检查低层属性与优化后的循环。
本机汇编说明指令选择和保留调用。
正式计时说明这个程序在本机桌面环境中的总体效果。
四者不能互相替代。

只找到一条向量指令不证明整个内核向量化。
只看到 IR 里的 vector.body 不证明最后仍有 SIMD。
只看到耗时下降也不能确定是向量化起作用。
本章同时展示目标业务函数、实际指令与同语义对照。
目的是让解释可被反驳。

## 6.2 alias、有效范围与安全接口的优化价值 {#sec-cpp-rust.2.6.2}

### 别名真正危险的是冲突访问

两个只读指针可以指向同一个值。
这本身并不妨碍很多读取优化。
关键问题通常是某个写入是否可能改变另一个读取的来源。
如果允许重叠写入，缓存旧值或移动读取就可能改变行为。
别名分析为这些变换提供依据。

Rust 引用会携带比裸地址更强的访问契约。
但不能把契约粗暴简化成“整个作用域内永远不允许任何别名”。
再借用、活跃范围和内部可变性都需要考虑。
UnsafeCell 尤其改变共享引用下的可变性条件。
本章不试图给出完整形式化别名模型。

### 真实参数属性

add_slices 的 output 形参在本轮 IR 中带 noalias。
input 形参带 readonly，且同样有该版本生成的别名相关信息。
两者的对齐观察为 8。
这是 Rust u64 切片接口降级后的结果。
它不等于承诺传入地址按 16 或 128 字节对齐。

因此后端不能假设每个输入都满足某个手写 SIMD 对齐要求。
本轮向量 load 的 align 仍为 8。
目标指令能够处理相应访问形态。
若手写 intrinsic 要求更强对齐，必须另行保证。
语言类型的最小对齐与缓存行大小是不同概念。

### 内部可变性的反例边界

第4章的 DropProbe 持有 Cell 引用。
通过共享引用更新 Cell 是合法的。
因此不能对该函数套用“共享引用绝不会变化”的无条件推理。
本章加法内核的元素是普通 u64。
没有在元素内部藏可变单元。

这种差异可能影响前端能生成的属性。
也影响优化器是否可以把某次 load 长期保留在寄存器。
若把所有接口都改成地址整数，优化器也不会自动恢复完整契约。
unsafe 不天然更快。
它常常只是让程序员承担了额外证明。

### 不重叠切片如何安全取得

同一个缓冲中的不相交区域可以通过安全分割取得。
例如 split_at_mut 给出两个不重叠可变切片。
不需要先制造两个重叠可变引用，再承诺只访问不同下标。
引用本身的有效性就需要满足契约。
不能把“这轮循环恰巧没撞到”当成普遍证明。

若业务需要重叠源与目的，例如滑动窗口搬移，应选择相应 API。
copy_within 的语义与两个不重叠切片相加不同。
不能为了让 LLVM 更容易向量化，伪造不别名前提。
正确做法是保留真实访问模式，再检查能否分阶段处理。
本章所有正式内核使用不同 Vec 存储源和目的。

### 安全失败而非 UB 演示

本包有一个编译拒绝输入尝试重叠共享与可变借用。
编译器报告 E0502。
该程序没有被执行。
这验证了某种非法调用形式被静态排除。
它不是完整别名模型证明。

本章运行时还保留长度不符的明确失败路径。
输入长度不等时，函数在进入循环前 panic。
这比忽略多余元素更符合本实验的“逐元素配对”契约。
失败由安全断言产生，不是越界访问。
测试确认它确实被拒绝。

### 不应滥用 noalias 解释一切

即使没有强别名信息，编译器也可能生成运行时重叠检查。
满足条件时走向量路径，否则走标量路径。
本轮没有构造这种 raw pointer 对照。
所以不报告“去掉引用会慢多少”。
本文的对照改变的是调用边界，而不是把安全与 UB 放在一起计时。

如果想测别名属性的净影响，需要设计所有路径都合法的输入。
应同时检查运行时检查与循环形态。
不能用重叠`&mut`制造一个看似便宜的非法输入。
未定义行为程序没有可用于性能比较的可靠基线。
安全性证明先于优化归因。

## 6.3 边界检查、迭代器与循环向量化 {#sec-cpp-rust.2.6.3}

### 先决定长度不等时的语义

zip 通常按较短一侧结束。
这对某些业务是正确行为。
但本实验要求输入与输出长度完全一致。
因此内核先 assert_eq 长度。
不要把漏算尾部误当成优化。

断言放在循环外。
成功之后两侧具有同样的迭代上界。
配对迭代避免每次显式下标访问都独立表达边界条件。
编译器仍需要证明访问合法。
它可以把已有类型与循环结构用于证明。

### 完整内核

```rust
#[inline(never)]
pub fn add_slices(output: &mut [u64], input: &[u64]) {
    assert_eq!(output.len(), input.len());
    for (out, &value) in output.iter_mut().zip(input) {
        *out = out.wrapping_add(value);
    }
}

#[inline(never)]
pub fn scalar_add(left: u64, right: u64) -> u64 {
    left.wrapping_add(right)
}

#[inline(never)]
pub fn add_with_calls(output: &mut [u64], input: &[u64]) {
    assert_eq!(output.len(), input.len());
    for (out, &value) in output.iter_mut().zip(input) {
        *out = scalar_add(*out, value);
    }
}
```

两个内核都没有 unsafe。
都执行同样的 wrapping_add。
区别是第二个逐元素调用 inline(never) 的 scalar_add。
这人为保留一个不透明程度更高的调用边界。
它是一个真实可执行的安全性能回退模型。

### 为什么会影响向量化

自动向量化需要看到重复元素操作之间的关系。
若每个元素都进入一个保留函数调用，循环转换会受到限制。
即使被调用函数体本身非常简单，属性与成本模型也可能选择不跨过它。
本轮 scalar_add 调用确实留在循环里。
因此对照不只是源码外观不同。

这不证明所有函数调用都阻止向量化。
可内联的函数往往会先被展开。
某些函数具有专用向量实现或可识别 intrinsic。
某些调用还会被删除、合并或特化。
本章只对本轮实际保留的边界下结论。

### 真实 LLVM 向量主体

下面是 add_slices 目标业务函数中的真实语句摘录。
省略调试元数据和其他基本块。
完整文件保存在`stable-02/codegen/`。

```llvm
%wide.load = load <2 x i64>, ptr %1, align 8
%wide.load10 = load <2 x i64>, ptr %0, align 8
%8 = add <2 x i64> %wide.load10, %wide.load
store <2 x i64> %8, ptr %0, align 8
%index.next = add nuw i64 %index, 8
```

实际主体同时处理四组 2×i64。
一次主体迭代推进八个元素。
这里的向量类型与向量操作都清楚存在。
不同于第5章只有名为 vector.body 的标量展开。
但仍需确认本机最终指令。

### 本机目标码

```asm
ldp q0, q1, [x10, #-32]
ldp q2, q3, [x10], #64
ldp q4, q5, [x9, #-32]
ldp q6, q7, [x9]
add.2d v0, v4, v0
add.2d v1, v5, v1
add.2d v2, v6, v2
add.2d v3, v7, v3
stp q0, q1, [x9, #-32]
stp q2, q3, [x9], #64
subs x11, x11, #8
b.ne LBB6_5
```

这不是汇编语法课程。
应关注的是成组读、成组加、成组写与八元素推进。
同一函数还包含长度断言失败路径。
也包含不足一个向量主体的标量尾部。
不能只摘主体就宣布小输入也走同样路径。

### 尾部测试的重要性

正式长度 16384 恰好能被八整除。
只验证这个长度会漏掉尾部问题。
测试因此遍历 0 到 129 的长度。
包含空切片、短切片和非整块尾部。
同时将输出初始化为 u64::MAX。

这验证 wrapping 语义和尾部结果。
它不靠最终总和单独判断每个位置是否正确。
两个向量化对照逐元素比较。
额外再与`input-1`的 wrapping 参考值比较。
这样比只看总 checksum 更强。

```rust
#[test]
fn vector_tails_and_max_values() {
    for len in 0..130 {
        let input = input_data(len);
        let mut left = vec![u64::MAX; len];
        let mut right = left.clone();
        add_slices(&mut left, &input);
        add_with_calls(&mut right, &input);
        assert_eq!(left, right);
        for (got, v) in left.iter().zip(input) {
            assert_eq!(*got, v.wrapping_sub(1));
        }
    }
}
```

### 长度拒绝回归

```rust
#[test]
#[should_panic(expected = "assertion")]
fn unequal_lengths_are_rejected() {
    add_slices(&mut [0; 2], &[1]);
}
```

测试有意触发定义良好的 panic。
没有越界读取，也没有未初始化输出。
若将断言删除而保留 zip，测试可能不再失败。
那会改变函数契约，并可能漏处理目的尾部。
优化前后应首先保证这种行为没有被意外改写。

## 6.4 benchmark 一：完整数据通路中的调用回退 {#sec-cpp-rust.2.6.4}

### 不只测一条 add

入口为`src/bin/vectorize.rs`。
每次内核运行先把输出清零。
然后对所有元素做加法。
最后读取输出计算 checksum。
这三部分都在批计时内。

清零使每次调用从相同状态开始。
否则重复调用会累积输出，参考结果也要随次数变化。
保留 checksum 读取确保结果被观察。
它也增加了共同的内存通路工作。
所以表格不等于纯向量加法带宽。

### 完整入口

```rust
use compiler_lab::{Case, add_slices, add_with_calls, borrowed_sum, input_data, measure};
use std::hint::black_box;
fn run(f: fn(&mut [u64], &[u64]), input: &[u64], output: &mut [u64]) -> u64 {
    output.fill(0);
    f(black_box(output), black_box(input));
    borrowed_sum(black_box(output))
}
fn main() {
    let input = input_data(16384);
    let mut left = vec![0; input.len()];
    let mut right = left.clone();
    let expected = input.iter().copied().fold(0, u64::wrapping_add);
    let mut cases = [
        Case {
            name: "zip",
            run: Box::new(|| run(add_slices, &input, &mut left)),
            expected,
        },
        Case {
            name: "calls",
            run: Box::new(|| run(add_with_calls, &input, &mut right)),
            expected,
        },
    ];
    measure(&mut cases, input.len());
}
```

两个输出缓冲分别持有。
它们不与输入重叠。
case 创建时没有把正在使用的同一 Vec 借给两份闭包。
编译器检查了这些独占借用关系。
正式执行时 case 顺序轮转。

### 计量表

| 阶段 | zip | calls | 是否共同存在 |
|:--|:--|:--|:--|
| 创建 Vec | 计时外 | 计时外 | 是 |
| output.fill(0) | 计时内 | 计时内 | 是 |
| 配对读取与加法 | 计时内 | 计时内 | 是 |
| scalar_add 保留调用 | 无 | 每元素有 | 否 |
| 输出求和 | 计时内 | 计时内 | 是 |
| 批 checksum 断言 | 时间戳后 | 时间戳后 | 是 |

不能把 calls 与 zip 的差值完全归成函数调用的裸延迟。
循环宽度、寄存器使用、读写交错也不同。
但我们可以准确说：把这个小操作隔在保留调用后面，导致本轮总体成本增加。
这是足够具体、可重现的工程结论。
不需要虚构硬件计数来增强说服力。

### 实测结果

| case | mean ns/元素 | N-1 sd | 批 p50 | 批 p99 |
|:--|--:|--:|--:|--:|
| zip | 0.347104 | 0.016887 | 0.346487 | 0.378854 |
| calls | 0.723644 | 0.059594 | 0.718884 | 0.833090 |

zip 路径在本机这组桌面测量中更快。
目标码同时证明向量主体保留。
calls 的目标码保留逐元素直接调用。
结果与代码生成方向一致。
没有将此差值外推为所有数据长度的固定加速比。

### 缓存与尺寸限制

输入为 16384 个 u64，即 128KiB。
每个输出也同样大小。
多轮重复会形成热数据访问情形。
这不是对大于末级缓存的数据流测试。
也不是从磁盘到输出的端到端吞吐。

本章不计算 DDR 带宽。
因为初始化、求和、缓存写回与硬件缓存层次都影响实际总流量。
只把数组字节数除以总时间，未必等于外部内存流量。
没有采集内存控制器计数。
因此只报告明确定义的 ns/输入元素。

### 可执行的修复方向

真实代码若出现类似回退，应先检查小函数是否可见。
可以让合适的小内核被内联。
也可以提高 API 粒度，让整个切片在具体实现内处理。
不应首先把安全循环改成 unchecked 下标。
本轮安全 zip 已经得到向量化。

若内核很大，强制 always inline 可能反过来增加代码体积。
若需要独立 ABI 或调试边界，也可能必须保留调用。
应把这些约束纳入设计。
“删除所有函数边界”不是本章的建议。
先测真实热点，再决定哪个边界值得改变。

### 归约、循环依赖与不能随意重排的业务

本轮向量加法对不同输出位置分别写入。
第 i 个元素不读取第 i-1 个元素的新结果。
这种独立性有利于成组处理。
如果业务改成前缀和，访问关系就不同。
前缀和需要把此前结果传给后续位置。
不能只把相同的 zip 结构复制过去，就期待同一种向量化。

归约也需要看运算语义。
本章 u64 wrapping 加法可以按模运算重新组合。
但浮点加法通常不满足相同结合律。
改变归约树可能改变舍入路径。
若未来扩展浮点实验，应明确结果要求。
逐位一致、绝对误差和相对误差是不同契约。

本章没有打开 fast-math 类选项。
也没有把整数结论转成浮点允许任意重排。
如果提出近似算法，需要先给出输入定义域。
还要覆盖零、符号变化、极端值与非有限值的处理。
再为同一域报告最大误差或其他清楚的指标。
速度表不能替代这些语义检查。

| 循环形态 | 必须先检查的依赖 | 本章证据范围 |
|:--|:--|:--|
| 独立逐元素加法 | 源目的不冲突、长度一致 | 已运行与逐元素测试 |
| wrapping 求和 | 模运算可组合、尾部完整 | 已用于输出观察 |
| 前缀递推 | 后续读取此前新结果 | 未做正式实验 |
| 浮点归约 | 舍入与允许的重排范围 | 未使用该类内核 |
| 含外部副作用的映射 | 调用顺序和可观察行为 | 不能套用纯加法结论 |

这张表不是要在本章增加未经测量的性能排名。
它说明一个向量化成功案例究竟依赖哪些事实。
实际循环含日志、锁或错误提前返回时，应重新分析。
若某个元素处理可能 panic，也要考虑部分更新的可观察状态。
本轮内核在长度检查成功后只做 wrapping 整数加法。
因此没有中途数值溢出 panic 的路径。

### 对照完整数据通路而不是只看主体

目标码中的向量主体很容易吸引注意。
但真实调用还可能包含短输入分支。
可能有长度检查。
可能有标量尾部。
可能有输出清零与校验读取。
本章正式时间保留这些夹具工作。

如果需要纯内核吞吐，可以另外设计输出复用与观测方法。
但不能从现有时间里主观减去一段没有测量的开销。
尤其不能把 fill 的预估成本从两种结果中分别扣除后宣称净加速。
独立测量之间可能共享缓存、调用和调度效应。
减法不自动产生干净的内核时间。
本章直接报告完整边界，更容易复现和解释。

第一轮 stable-01 的 zip 均值为 0.311992ns/元素。
主表采用第二轮 stable-02 的 0.347104ns/元素。
两轮均保留所有原始点。
没有为了更漂亮的数字选择第一轮 zip、第二轮其他 case。
不同轮的变化提醒读者这里不是隔离实验室。
但两轮都保留了同方向的调用边界回退。
这支持局部机制观察，不支持某个普遍固定倍数。

### 正式统计边界

每个 case 至少预热 500ms。
每个 case 21 个正式批次。
样本是批均值，不是每个元素独立延迟。
标准差采用 N-1。
nearest-rank p99 在此就是最大批值。

本轮没有并行计时其他 benchmark。
脚本使用全项目约定的独占目录锁。
采样 profiler 没有附着到正式向量测试。
桌面噪声仍然存在。
该表不是硬实时或 SLA 证据。

## 6.5 CTFE、普通常量传播与 Miri 的分界 {#sec-cpp-rust.2.6.5}

### const fn 不代表每次调用都在编译期

const fn 表示某个函数满足常量上下文可调用条件。
在 const 或 static 初始化器等常量上下文中使用时，需要编译期求值。
在普通运行时代码中调用，仍可以作为普通函数执行。
优化器也可能把某些常量输入调用折叠。
这与语言要求的 CTFE 不是同一个承诺。

因此`const fn`不是一个性能属性的别名。
它不保证所有运行时调用零开销。
也不保证输入未知时能神奇地提前计算。
常量上下文、输入可知性和优化决策需要分别判断。
本章用 static 初始化明确要求预计算。

### 本章的精确表

输入域是 0 到 255。
每个表项记录该字节有多少个位为一。
结果范围是 0 到 8。
表大小为 256 字节。
没有哈希，没有冲突问题，也没有近似误差。

编译期函数用移位和计数生成所有表项。
static BIT_TABLE 的初始化器调用它。
这要求编译器求得整个表。
运行时查表使用字节转 usize，索引天然落在域内。
所有转换都有清晰范围。

```rust
pub const fn bit_table() -> [u8; 256] {
    let mut table = [0; 256];
    let mut index = 0;
    while index < table.len() {
        let mut bits = index;
        let mut count = 0;
        while bits != 0 {
            count += (bits & 1) as u8;
            bits >>= 1;
        }
        table[index] = count;
        index += 1;
    }
    table
}

pub static BIT_TABLE: [u8; 256] = bit_table();

#[inline(never)]
pub fn runtime_table() -> [u8; 256] {
    // Runtime black_box prevents replacing this experiment with its const result.
    let seed = black_box(0usize);
    let mut table = [0; 256];
    for (index, slot) in table.iter_mut().enumerate() {
        let mut bits = index + seed;
        let mut count = 0;
        while bits != 0 {
            count += (bits & 1) as u8;
            bits >>= 1;
        }
        *slot = count;
    }
    table
}

#[inline(never)]
pub fn lookup_bits(table: &[u8; 256], input: &[u8]) -> u64 {
    input
        .iter()
        .map(|&v| u64::from(table[usize::from(v)]))
        .sum()
}
```

runtime_table 是故意保留的运行时构造对照。
seed 在真实运行中为零。
black_box 阻止编译器把整次实验直接替换为静态答案。
这个屏障是夹具，不是生产优化建议。
如果真实程序输入完全固定，编译器可能自动做得更多。

### CTFE 的错误发生在哪一阶段

常量上下文中的越界不能作为成功常量值进入程序。
本轮 rejected/const_bounds.rs 在编译时报告 E0080。
它不生成可执行版本再等待运行时 panic。
这个区别可以直接验证。
失败输入如下。

```rust
const BAD: u8 = [1u8; 2][3]; fn main() { println!("{BAD}"); }
```

`extra.py`检查了非零退出状态与错误代码。
完整诊断保存在`extra-02/const_bounds.txt`。
本轮没有用 UB 常量来获得所谓快速路径。
也没有把错误常量藏到不使用的分支中宣称验证通过。
错误实际由引用它的 main 触发求值需求。

### 编译器解释器与 cargo miri 不可混称

rustc 的 CTFE 使用 MIR 解释基础设施。
Miri 工具也与 MIR 解释技术密切相关。
但编译成功并不等于对整个程序运行了 Miri。
CTFE 只求值所需的常量上下文。
运行时的大部分行为没有因此被动态检查。

本轮没有执行`cargo miri test`。
nightly 安装也不可用。
因此不能在测试列表中写“Miri 通过”。
只能说静态表已经通过编译器常量求值并进入可执行产物。
运行时测试又逐项验证了表值。

Miri 的通过也不等于完整形式语义证明。
它只检查执行到的路径与所选模型范围。
系统调用、目标差异和模型状态还可能限制覆盖。
这些是一般边界，不是本轮执行结果。
没有执行就不填写一个虚假的绿色状态。

### CTFE 与 build.rs 的目标环境

CTFE 依照编译目标的数据模型解释常量。
例如目标 usize 的宽度由 target 决定。
build.rs 则是运行在 host 上的普通程序。
交叉编译时，host 和 target 可能不同。
这会影响按指针宽度生成表或布局的逻辑。

build.rs 可以访问文件、环境或外部工具。
这很灵活，也引入输入声明与可复现性责任。
需要明确 rerun-if-changed 和相关环境变量。
不能依赖未记录的当前目录、时间或网络响应生成发布数据。
本章没有使用 build.rs。

### 预计算不是免费消失

CTFE 把部分成本从运行期移到构建期。
还可能增加二进制只读数据。
大表也可能增加加载、缓存或重定位压力。
编译时间与内存成本同样需要考虑。
不能将“运行期少计算”概括成所有维度都更快。

本章表只有 256 字节。
这有利于解释和穷举验证。
不代表把任意数值函数变成巨大查表都合适。
特别是近似函数，必须先说明定义域、误差度量和边界处理。
本章没有通过近似偷换计算语义。

## 6.6 benchmark 二：静态表复用与逐批重建 {#sec-cpp-rust.2.6.6}

### 比较的是放置时机

入口是`src/bin/ctfe_table.rs`。
输入正好包含所有 256 个字节值。
两种 case 都查表统计置一位数量并归约。
区别是复用静态表，还是每次先运行时构造同样的表。
因此它是初始化放置的对照。

它不比较查表与硬件 count_ones 的最快实现。
count_ones 只用于计算参考值。
也不证明查表胜过本机 popcount。
若需要回答那个问题，应新增同语义计时 case。
不能把参考实现的存在当成已经测量。

### 完整入口

```rust
use compiler_lab::{BIT_TABLE, Case, lookup_bits, measure, runtime_table};
use std::hint::black_box;
fn main() {
    let input: Vec<u8> = (0u8..=255).collect();
    let expected = input.iter().map(|v| u64::from(v.count_ones())).sum();
    let mut cases = [
        Case {
            name: "static_table",
            run: Box::new(|| lookup_bits(black_box(&BIT_TABLE), black_box(&input))),
            expected,
        },
        Case {
            name: "rebuild_table",
            run: Box::new(|| {
                let table = runtime_table();
                lookup_bits(black_box(&table), black_box(&input))
            }),
            expected,
        },
    ];
    measure(&mut cases, input.len());
}
```

输入构造在计时外。
static 表已经属于可执行产物。
rebuild_table 每次运行都生成一张局部表。
构造和查表都在计时内。
局部表不会逃逸为悬垂引用。

### 穷举验证

```rust
#[test]
fn ctfe_exhaustive_domain() {
    assert_eq!(BIT_TABLE, runtime_table());
    for v in 0u8..=255 {
        assert_eq!(u32::from(BIT_TABLE[usize::from(v)]), v.count_ones());
    }
}
```

测试先比较整张静态表与运行时表。
随后逐项与字节的 count_ones 比较。
这覆盖完整输入域，不只是几个常用值。
输出上界也清晰地不超过八。
不存在浮点比较容忍度的歧义。

穷举域很小，适合做比 checksum 更强的校验。
未来若把表换成更复杂映射，验证应继续保留。
如果改成完美哈希，必须显式检查域内碰撞和域外拒绝。
不能只给生成函数起名为 perfect 就算证明。
本章没有采用哈希方案。

### 类型与布局表

| 对象 | 本机 size | align | 运行期角色 |
|:--|--:|--:|:--|
| [u8;256] | 256 | 1 | 整张精确表 |
| u8 输入 | 1 | 1 | 保证索引在 0..255 |
| u64 归约 | 8 | 8 | 保存一批统计值 |
| &amp;[u64] | 16 | 8 | 向量实验的输入位置与长度 |
| runtime_table 结果 | 256 字节 | 1 | 本轮经返回位置传递 |

数组的 align 为一，不意味着静态项实际地址一定奇数。
链接器可以给它更强的实际放置对齐。
但调用者只能依赖语言与类型承诺的最低要求。
也不能把 static 名称当成硬件 cache residency 保证。
是否命中缓存是运行时观察问题。

### 正式结果

| case | mean ns/字节 | N-1 sd | 批 p50 | 批 p99 |
|:--|--:|--:|--:|--:|
| static_table | 0.169413 | 0.001526 | 0.169365 | 0.172596 |
| rebuild_table | 1.953818 | 0.017490 | 1.949261 | 1.997598 |

逐批重建在本轮明显更昂贵。
这是包含构造与查表的归一化时间。
不是两种查表指令自身的比较。
也不是 CTFE 编译器“执行一次位运算”的速度。
CTFE 的构建成本没有被计入这张运行时表。

### 产物中的构造确实保留

runtime_table 的 IR 保留逐表项循环。
内部还有对 bits 反复右移的计数循环。
返回结果经 256 字节输出位置传递。
本机目标码也保留这些循环与表数据写入。
所以慢路径不是一个已被优化掉的假构造。

static_table 不需要执行相同的构造循环。
但它仍需要读输入、查表与归约。
表必须存在于程序的数据视图中。
本轮没有测进程冷启动时首次加载该页的代价。
热批次不等于冷加载成本。

### 更贴近生产的三种选择

若表完全固定且很小，常量初始化很直接。
若表依赖运行配置，可以在配置加载时构造一次并复用。
若表依赖每条请求，不能把它移到全局而忽略输入差异。
这三种情况有不同语义。
本轮慢路径是故意重复构造固定表的回退案例。

修复不是“把所有函数加 const”。
关键是表值是否真的在请求间相同。
如果配置会更新，还需要版本与生命周期策略。
如果表很大，还需要测缓存和内存预算。
应让初始化位置与数据依赖相匹配。

### 受控外推

对这个 256 字节全域输入，本轮结果稳定支持复用更便宜。
不支持任何更大表的固定倍数收益。
不支持某个实时系统的极端尾延迟。
不支持 CTFE 没有编译资源成本。
没有测量的维度继续保持未测。

## 6.7 内联、CGU 与 LTO：扩大视野也有代价 {#sec-cpp-rust.2.6.7}

### inline 属性是一种提示

Rust 参考手册明确将 inline 描述为优化提示。
编译器本身也会根据启发式选择内联。
没有属性不代表从不内联。
有属性也不应被当作稳定指令边界契约。
实际产物仍需检查。

本轮 scalar_add 使用 inline(never)。
目标码确实保留该调用。
visible_dynamic 也使用 inline(never)。
但其内部的 dyn 来源仍能被消解。
这说明一个函数边界被保留，不意味着函数体内部的优化冻结。

### 内联的主要价值不只是省 call

内联可以暴露常量参数。
可以让范围关系进入同一控制流。
可以删除无用分支。
也可以让循环内的小操作成为向量化候选。
因此某些回归差值远超过一条调用指令的直觉成本。

但内联也可能复制大型函数体。
增加热代码体积与寄存器压力。
改变调试栈形状。
增加构建时间。
不应该把 always inline 当通用优化开关。

### 代码生成单元的权衡

多个 CGU 允许后端并行处理不同模块。
也可能改善修改后的复用。
但部分优化信息会受到分区影响。
CGU=1 能扩大某些局部视野，却可能减少构建并行。
这不是运行时线程数量设置。

本轮正式 profile 固定 CGU=1。
LTO=false。
因此主表不能被标为“开启跨 crate LTO 后的性能”。
补充尺寸实验单独构建 ThinLTO。
它与正式表格必须分开。

### ThinLTO 的实际执行范围

`extra.py`对同一个 code_size 探针生成普通 many 与 thin。
thin 使用`-Clto=thin`。
两者都以 O3 与一个 CGU 构建。
两个可执行文件都实际运行。
所有 16 个实例的输出都与参考函数比较通过。

这给出了真正的功能与产物证据。
没有正式采样两种构建的运行时间。
因此不报告 ThinLTO 加速百分比。
更小的代码节也不必然意味着任何特定负载更快。
构建时间同样没有作受控比较。

### 已观察的节大小

| 构建 | __text 字节 | 对照意义 | 是否有正式速度样本 |
|:--|--:|:--|:--|
| many O3 | 220156 | 基线多实例产物 | 否 |
| many ThinLTO | 214768 | 完整构建优化后产物 | 否 |
| many PGO-use | 220028 | 使用训练 profile 的产物 | 否 |

所有数值来自`size -m`原始输出。
不包括把 __PAGEZERO 的虚拟保留量当作代码。
也不把调试符号文件长度当作 I-cache 工作集。
这一口径足够明确，但仍是静态尺寸观察。
需要运行行为时应另行设计正式测量。

### 跨 crate 的可见性并非全有或全无

泛型函数通常需要把足够信息提供给实例化方。
普通非泛型函数的处理又可能不同。
inline 属性和 LTO 会影响可见性。
构建 profile 还会改变优化预算。
因此“跨 crate 就一定不能内联”同样过度简化。

真实排查可以先比较边界前后的产物。
确认热点小核是否仍是保留调用。
再尝试最小构建选项变化。
如果同时改 LTO、CGU、panic 与 target-cpu，就难以归因。
应一次控制清晰的问题，保留每种构建的输出校验。

### 不要把尺寸收益变成无限内联建议

ThinLTO 本轮缩小的是整个探针产物。
其中可能包括标准库与其他函数的变化。
无法只凭总差值判断某个用户函数该不该 inline。
局部属性改动应有局部证据。
全程序构建选项则要考虑完整构建成本和发布流程。

若编译时间是团队瓶颈，应同时记录构建矩阵。
若部署包体积有限，应记录 strip 前后与相关节。
若延迟是目标，应执行相同负载的正式配对测量。
本轮没有混用这三种目标。
第14章的发布工程可以在此基础上安排更完整矩阵。

## 6.8 PGO：真实训练、可用产物与未证明的收益 {#sec-cpp-rust.2.6.8}

### PGO 给优化器频率线索

profile-guided optimization 收集实际执行分布。
优化器可据此调整内联、布局和其他决策。
它不会使错误算法自动正确。
也不会使训练负载自动代表生产。
训练数据是输入，而不是性能保证。

本章采用 rustc 支持的插桩流程。
不是 Linux perf 采样式 PGO。
也不是把 macOS sample 文本直接交给编译器。
sample 报告与 LLVM profile 数据格式完全不同。
两条证据链需要分别保存。

### 四阶段实际执行

第一步构建带 profile-generate 的程序。
第二步实际执行它，产生 profraw。
第三步用匹配版本 llvm-profdata 合并。
第四步用 profile-use 重编译并执行校验。
本轮四步均已完成。

训练对象是 code_size 的 many 配置。
它依次访问 16 个实例，每轮按固定顺序处理输入。
共重复 32 轮。
这是一个可重复的小训练负载。
它不是生产策略分布。

### 工具版本核对

本机 rustc 使用 LLVM23.1.1。
所用 llvm-profdata 来自同一稳定工具链目录。
其版本输出为`23.1.1-rust-1.99.0-stable`。
未使用 Xcode 中另一个版本的同名程序冒充匹配工具。
完整命令与版本输出位于 extra-02。

profile-generate 与 profile-use 采用相同源文件。
共同参数包括 edition2024、O3、CGU=1 和 cfg=many。
只有 profile 模式和输出路径按阶段变化。
profile 路径使用绝对路径。
这避免工作目录变化使编译器读错数据。

### 可复现驱动代码

完整脚本为`bench/compiler-lab/extra.py`。
它拒绝覆盖已有输出目录。
下面保留实际 PGO 分支的核心。
run 会保存命令、stdout、stderr，并检查成功状态。

```python
sysroot = subprocess.check_output(['rustc', '--print', 'sysroot'], text=True).strip()
profdata = Path(sysroot) / 'lib/rustlib/aarch64-apple-darwin/bin/llvm-profdata'
if profdata.exists():
    run([profdata, '--version'], 'profdata-version.txt')
    data = out / 'pgo-data'
    data.mkdir()
    common = ['rustc', '--edition=2024', '-O', '-Ccodegen-units=1', '--cfg=many', root / 'probes/code_size.rs']
    run([*common, f'-Cprofile-generate={data}', '-o', out / 'pgo-train'], 'pgo-generate.txt')
    run([out / 'pgo-train'], 'pgo-training-run.txt')
    raw = list(data.glob('*.profraw'))
    assert raw
    run([profdata, 'merge', '-o', data / 'merged.profdata', *raw], 'pgo-merge.txt')
    run([*common, f'-Cprofile-use={data / "merged.profdata"}', '-Cllvm-args=-pgo-warn-missing-function',
         '-o', out / 'pgo-use'], 'pgo-use.txt')
    run([out / 'pgo-use'], 'pgo-use-run.txt')
    run(['size', '-m', out / 'pgo-use'], 'pgo-size.txt')
```

这段代码不是要求读者在已有归档里重复覆盖数据。
应为每次尝试选择新目录。
profraw 和 merged.profdata 一起保留。
不要只保存最后二进制，却丢弃训练输入与编译日志。
也不要把旧 profile 默默混入新源码构建。

### 真实警告没有隐藏

profile-use 阶段启用了`-pgo-warn-missing-function`。
本轮出现一个 lang_start 包装函数缺少 profile 的警告。
日志中原样保存。
因此不能声称“所有函数的训练数据都完整匹配”。
程序仍成功构建并完成输出校验。

这种警告需要根据真实项目检查。
可能存在未覆盖函数、源码或选项差异。
不应该直接关掉诊断，只为了得到干净日志。
本轮没有进一步声称解决了该包装函数 profile 缺口。
它作为已知局限保留。

### 结果校验与尺寸

训练程序输出 16 个实例的 checksum。
profile-use 程序输出相同的`95338125850705920`。
每个实例还分别与参考函数比较。
这验证该训练与使用流程没有在本测试域改变结果。
不等于对所有可能输入完成形式证明。

PGO-use 的`__text`为 220028 字节。
普通 many 为 220156 字节。
这个静态差值很小。
没有正式测量速度。
所以本章不写“PGO 提升百分之几”。

### 训练偏差是核心工程风险

只训练热路径会影响冷路径决策。
只训练某一数据长度可能改变内联与分支选择。
输入分布变化后，原 profile 可能不再有利。
因此发布前应同时跑代表性负载与保留验证集。
训练集与评估集最好不要完全重合。

本轮训练和验证共享一个小探针输入。
这是流程验证，不是泛化收益验证。
不能把它包装为生产 PGO 优化完成。
更不能拿插桩程序的耗时与未插桩程序直接比较作为最终收益。
插桩本身会改变执行开销。

### Cargo 工作流还要区分 host

若改成 Cargo 全工程 PGO，应固定 target。
否则 RUSTFLAGS 可能影响 host 构建脚本等工具。
构建脚本的执行分布通常不是目标服务要训练的对象。
要记录 features、依赖版本与所有构建参数。
本章独立探针没有第三方依赖或 build.rs。

匹配 profile 也需要匹配源码和工具链。
更新编译器之后应重新训练和验证。
不要把本机生成的数据当作跨目标通用配置。
profile 是构建输入的一部分。
它应该进入可追溯归档，而不是一个没人知道来历的二进制文件。

## 6.10 常见陷阱 {#sec-cpp-rust.2.6.10}

1. **以为 unsafe 会自动增加优化信息。**
   裸地址往往比安全引用丢失更多可用契约。
   错误引用更可能造成 UB。
   本轮安全切片内核已经向量化。

2. **将共享引用一概视为永不变化的内存。**
   UnsafeCell 和内部可变性需要不同推理。
   第4章 Cell 计数就是合法变化例子。
   应检查真实元素类型与访问契约。

3. **把 align 8 的向量访问说成 16 字节保证。**
   LLVM load 的对齐字段仍然重要。
   缓存行大小与类型对齐无直接等同关系。
   手写更强对齐要求必须另有证明。

4. **删除长度断言后把少算元素当加速。**
   zip 本身按较短序列停止。
   本实验要求长度一致。
   不同语义不能放进同一性能结论。

5. **只测整除向量宽度的长度。**
   正式热长度可能漏掉尾部错误。
   本轮测试包含空输入和 0..129 的尾部。
   逐元素校验不能只用总和替代。

6. **把一次保留调用的差值叫裸 call 延迟。**
   调用边界还影响内联、展开和向量化。
   本轮测的是完整数据通路。
   机制归因需要同时看产物。

7. **给函数加 const 就宣称运行时零成本。**
   普通上下文仍可在运行时调用 const fn。
   本章用 static 初始化明确要求 CTFE。
   预计算也会增加构建和数据存储成本。

8. **编译成功就写 Miri 通过。**
   CTFE 只解释所需常量。
   不会检查整个程序的运行路径。
   本轮没有执行 cargo miri。

9. **把 build.rs 的 usize 当成 target usize。**
   构建脚本运行在 host。
   交叉编译需要显式处理目标数据模型。
   CTFE 与 host 代码生成器不能混称。

10. **从 ThinLTO 节变小推出速度必升。**
    静态尺寸不是运行时间。
    本轮只执行校验并报告 __text。
    正式速度收益仍未测量。

11. **把 sample 文本当作 PGO profile。**
    本轮使用 LLVM 插桩产生 profraw。
    macOS 栈采样不是该输入格式。
    两条工具链要分别记录。

12. **隐藏 missing-profile 警告。**
    警告提示训练覆盖或匹配可能有缺口。
    本轮原样保留 lang_start 警告。
    没有声称所有函数训练完整。

13. **训练一次就认为对所有生产输入泛化。**
    本轮只验证流程与小探针计算。
    没有独立保留负载的性能评估。
    发布优化需要更完整的分布证据。
