<div class="chapter-index">

**问题主线**：优化器需要哪些可证明事实，而程序员怎样确认这些事实真的变成了有用代码？

## 6.1 LLVM 得到的不是原样 Rust 源码 {#sec-cpp-rust.2.6.1}

本节回答一个问题：**优化器凭什么认为这段循环可以改成向量指令，读者又该在哪一层确认它真的改了？**6.3 会给出一条被向量化的内核和它的本机指令；这一节先把「凭据是什么、在哪一层看」这两件事定下来，后面每节的判断都回到这张地图上。

::: preview 先抓住一件事

**LLVM 看到的不是 Rust 源码，而是 rustc 做完语言层工作之后留下的低层事实：类型、控制流、调用、内存操作和参数属性。**一条优化结论能不能成立，取决于这些事实在哪一层被保留、结论在哪一层被核对。肯定它要同时给出合法性依据、成本依据和产物证据；否定它只需要指出「这句话所属的那一层根本没有被看」。
:::

### 6.1.1 rustc 交给后端的到底是什么

rustc 在生成 LLVM IR 之前已经完成很多语言层工作。类型已经明确。借用检查已经排除了不合法访问。析构责任已经转成合法控制流。泛型代码也要在具体实例上生成。

LLVM 不需要重新理解 Rust 的每个 trait 约束。它看到的是低层类型、控制流、调用、内存操作和属性。这些属性携带部分前端已知事实。优化是否合法，依赖这些事实与操作的真实语义。随意违反引用契约会破坏优化依据（[@def-1.6.1] 对「同一件事」的要求在这里同样成立）。

这不是「LLVM 猜测指针大概不重叠」。也不是「release 模式允许任意改变结果」。合法输入的可观察行为仍受语言语义约束。显式 wrapping 加法允许模运算变换。普通浮点归约则不能默认套用相同结合律。

::: def 定义 6.1.1 · 优化依据 {#def-6.1.1}

**优化依据**指后端可以据以改写代码的那些可证明事实，而不是它对常见情形的猜测。Rust 里的事实分两类：语言语义直接给出的（[@def-6.1.2] 的溢出行为、引用所携带的访问契约），以及降级后被写进 LLVM 参数属性与循环结构的（6.2 的 noalias、readonly，6.3 的可见循环体）。事实齐了只说明改写**合法**；要不要改写还取决于成本判断，见 [@def-6.1.3]。

:::

::: def 定义 6.1.2 · 定义良好的溢出与模运算变换 {#def-6.1.2}

**wrapping 加法**是 Rust 里显式写出「溢出就模 2 的幂」的整数加法，`u64` 上即模 2⁶⁴。它在 debug 与 release 中结果相同，所以编译器可以自由重组求和顺序，对应 [@def-6.1.1] 里「语义允许」那一栏。对照组是普通 `+`：debug 下 panic、release 下行为不同，以及浮点加法：改变结合顺序就可能改变舍入路径。

:::

### 6.1.2 本章使用的整数域

正式向量内核使用 `u64`。所有加法显式 wrapping，因此溢出行为在 debug 与 release 之间保持一致。CTFE 表使用 `u8` 输入域，结果是一个字节内置一位的精确个数。

没有数值近似。没有浮点误差容限。没有多项式拟合或截断级数。因此本章不会给出无来源的「误差小于某个 epsilon」。精确性通过穷举字节域和逐元素测试验证——这一点让本章的性能结论可以用「同样的输入、同样的输出」来钉死，正如 [@def-1.6.1] 要求的等价工作比较。

读图：优化需要合法性，也需要成本判断。前端事实足够，不表示后端必须选择向量化。目标不同、版本不同、循环形态不同，都可能改变决策。本章的图描述推理步骤，不是固定 pass 名字的执行日志。实际结论以保留的产物为准。

::: def 定义 6.1.3 · 合法性判断与成本判断 {#def-6.1.3}

上图把后端的决策拆成两道门。**合法性判断**问「这样改写会不会改变合法输入的可观察行为」，靠 [@def-6.1.1] 的事实回答；**成本判断**问「这样改写值不值」，靠目标向量能力、调用边界和循环规模回答。两者都可能否决一次向量化：前者说「不许」，后者说「不划算」。因此「源码写法可以向量化」这种说法永远只是必要条件。

:::

::: ex 例 6.1.1 · 两条产物证据各能撑到哪句话 {#ex-6.1.1}

6.3 会给出同一份 IR 与本机指令：IR 中出现 `add <2 x i64>` 这样的向量加法，本机汇编中出现 `add.2d` 和成组的 `ldp`/`stp`，一次主体迭代推进八个元素。

1. 只看 IR 里那一行向量加法，能写「本机用了 SIMD」吗？
2. IR 与汇编两条一起，能写「这个内核在任何机器上都向量化」吗？
3. 再补一条「zip 的批均值比 calls 低」，能写「加速来自向量化」吗？

::: sol 解答

1. 不能。只看到 IR 里的 vector.body 不证明最后仍有 SIMD——第 5 章就出现过只有名为 vector.body 的标量展开。要看本机目标码才算 [@def-6.1.4] 的第一层闭合。
2. 不能。本轮目标是 aarch64-apple-darwin，源码没有手写目标专用 SIMD，也没有用 `target-cpu=native` 额外启用本机特性；目标默认能力仍足以生成看到的向量加法，但这不构成其他目标必须出现同样指令的承诺。
3. 不能直接写。耗时下降也可能是别的成本变化，本章用「同语义对照 + 产物检查」两件事一起支撑归因：calls 保留逐元素调用、zip 不保留（6.3、6.4），方向与代码生成一致。即便如此，[@ex-1.6.1] 的教训仍然适用——不外推成固定倍数。

### 6.1.4 真实 ABI 与代码生成观察

::: def 定义 6.1.4 · 产物层级 {#def-6.1.4}

同一份源码会留下四层可核对的产物：**MIR**（语言层控制流与析构责任）、**LLVM IR**（低层类型、属性与循环）、**本机汇编**（指令选择与保留的调用）、**运行计时**（这个程序在本机桌面环境中的总体效果）。每层只支持它能支持的那句话，跨层引用必须显式说明证据来自哪一层；这与 [@def-1.8.1] 把证据拆成文件级链条是同一件事。

:::

本轮的表就是这样逐层写的：

| 观察对象 | 本轮产物形态 | 不能扩大为的结论 |
|:--|:--|:--|
| add_slices 形参 | 两个切片各拆成指针与长度 | 稳定 Rust FFI ABI |
| output 指针 | noalias、align 8 等属性 | 任意 raw pointer 自动不别名 |
| input 指针 | readonly 等属性 | UnsafeCell 中所有共享访问只读 |
| 向量主体 | LLVM 的 2×i64 操作 | 所有 u64 循环都使用相同宽度 |
| runtime_table 返回值 | sret 指向 256 字节结果 | 所有数组都经同一种返回约定 |

本轮目标是 aarch64-apple-darwin。源码没有手写目标专用 SIMD。也没有用 `target-cpu=native` 额外启用本机特性。目标默认能力仍足以生成后面看到的向量加法。这不构成其他目标必须出现同样指令的承诺。

::: method 判定流程 · 一条优化结论要凑齐哪几层

1. **先问合法性依据在哪**：是语言语义（[@def-6.1.2]）、引用契约（6.2），还是循环结构（6.3）？说不出依据，就不该出现这句结论。
2. **再问成本依据**：目标能力、调用边界、循环规模中哪一项被本轮产物支持？对照 [@def-6.1.3] 的第二道门。
3. **然后逐层看产物**：按 [@def-6.1.4]，IR 一句、本机汇编一句、计时一句，每句只写自己那一层能证明的。
4. **最后写边界**：目标、版本、是否 `target-cpu=native`、输入长度范围，缺一件就把结论降级成「本轮观察到」。

:::

### 6.1.5 观察工具的分工

MIR 更适合检查语言控制流和析构责任。LLVM IR 更适合检查低层属性与优化后的循环。本机汇编说明指令选择和保留调用。正式计时说明这个程序在本机桌面环境中的总体效果。四者不能互相替代。

只找到一条向量指令不证明整个内核向量化。只看到 IR 里的 vector.body 不证明最后仍有 SIMD。只看到耗时下降也不能确定是向量化起作用。本章同时展示目标业务函数、实际指令与同语义对照。目的是让解释可被反驳。

::: think 思考 · 「有 vector.body 这个名字」能不能算证据 {#think-6.1.1}

有人主张：IR 里出现 `vector.body` 这个块名，说明自动向量化已经跑起来了，因此不必再看汇编。这个前提哪里容易被绕过？

::: sol 解答

绕过它不需要改代码，只需要后端换一次决策：块名是 LLVM 生成中间结构时的命名，保留它不等于保留 SIMD——第 5 章观察到的只有名为 vector.body 的标量展开。所以名字属于 [@def-6.1.4] 的「哪一层」问题，而结论想要的是「本机指令」。正确的动作是回到目标码找成组加载、成组加、成组写（6.3 给的那段），并确认同一函数还包含标量尾部与长度断言失败路径，避免只摘主体。这也提醒我们别把 pass 名字当成执行日志，正如上图的说明。

### 6.1.6 小结与常见错误

**小结。**① 后端只优化被保留下来的语义，事实由 rustc 降级时写入（[@def-6.1.1]）；② 本章把精确性建立 [@def-6.1.2] 的 wrapping 整数域上，所以「同样输入同样输出」可以穷举验证；③ 合法性与成本是两道门，都过才有向量化（[@def-6.1.3]）；④ 结论要按 [@def-6.1.4] 逐层写，名字与形态都不算跨层证据。下一节 [6.2 alias、有效范围与安全接口的优化价值](#sec-cpp-rust.2.6.2) 处理这张传播图里最容易被误用的一栏：别名事实。

::: errata 常见错误清单（6.1 节）

## 6.2 alias、有效范围与安全接口的优化价值 {#sec-cpp-rust.2.6.2}

本节回答一个问题：**「这两个指针不重叠」这句话，在 Rust 里到底是谁保证的，又该怎么在不撒谎的前提下把它交给优化器？**

::: preview 先抓住一件事

**别名真正危险的地方不是「两个名字指向同一块内存」，而是「一个写入可能改变另一个读取的来源」。**两个只读指针共享同一个值不妨碍很多读取优化；一旦允许重叠写入，缓存旧值或移动读取就可能改变行为。判断顺序因此是：先确认访问契约成立，再谈优化收益——契约不成立时连可靠的性能基线都没有（[@def-6.1.1] 的合法性门槛在这里最具体）。
:::

### 6.2.1 冲突访问才是问题

两个只读指针可以指向同一个值。这本身并不妨碍很多读取优化。关键问题通常是某个写入是否可能改变另一个读取的来源。如果允许重叠写入，缓存旧值或移动读取就可能改变行为。别名分析为这些变换提供依据。

Rust 引用会携带比裸地址更强的访问契约。但不能把契约粗暴简化成「整个作用域内永远不允许任何别名」。再借用、活跃范围和内部可变性都需要考虑。UnsafeCell 尤其改变共享引用下的可变性条件。本章不试图给出完整形式化别名模型。

::: def 定义 6.2.1 · 别名与冲突访问 {#def-6.2.1}

**别名**指两个或更多名字可以指到同一块内存。**冲突访问**指其中一个名字写入、另一个名字的读取结果会因此改变的情形。优化器需要知道的是「有没有冲突访问」，而不是「有没有别名」：纯读共享是安全的，写读共享才限制重排。[@def-6.2.2] 的属性就是把这个判断写成机器可读的形式。

:::

::: def 定义 6.2.2 · noalias 与 readonly 参数属性 {#def-6.2.2}

**参数属性**是 LLVM 在函数签名上携带的事实标记。本轮 IR 里 `add_slices` 的 output 形参带 **noalias**（经这个指针的写入不会与同批其他带标记的指针冲突），input 形参带 **readonly**（只读该内存，不写）。两者都还带对齐观察 8。它们是 [@def-6.1.1] 里「降级后被写进 IR 的事实」那一类：由 Rust 的独占借用与共享借用契约推导而来，而不是程序员口头承诺。

:::

### 6.2.2 真实参数属性

`add_slices` 的 output 形参在本轮 IR 中带 noalias。input 形参带 readonly，且同样有该版本生成的别名相关信息。两者的对齐观察为 8。这是 Rust `u64` 切片接口降级后的结果。它不等于承诺传入地址按 16 或 128 字节对齐。

因此后端不能假设每个输入都满足某个手写 SIMD 对齐要求。本轮向量 load 的 align 仍为 8。目标指令能够处理相应访问形态。若手写 intrinsic 要求更强对齐，必须另行保证。语言类型的最小对齐与缓存行大小是不同概念（6.6 的布局表给出 `[u8; 256]` 的对照：align 为 1）。

::: ex 例 6.2.1 · 三个属性各支持哪句结论 {#ex-6.2.1}

本轮产物给出：output 带 noalias、input 带 readonly、两者对齐为 8。现有三句话，判断哪句成立：

1. 「output 与 input 指向的区间不重叠，所以循环里读 `input[i]` 可以提到写入 `output[i]` 之前。」
2. 「input 是 readonly，所以整个函数期间它的内容绝不会被任何代码改变。」
3. 「align 为 8，所以这条向量 load 满足要求 16 字节对齐的 intrinsic。」

::: sol 解答

1. 成立。noalias 提供依据（[@def-6.2.2]），配合 6.3 的可见循环体才走到向量化。
2. 不完全成立。readonly 说的是「经由这个指针不写」，函数仍然可能通过别的别名写入；元素里藏可变单元时更会如此（[@def-6.2.3]）。要写成「本轮 IR 对该参数标记为 readonly」，不能写成绝对不变。
3. 不成立。align 8 是类型最小对齐降级来的观察值，更强对齐必须另行保证；把 align 8 说成 16 字节保证是本章的已知陷阱之一（6.10 索引）。

:::

:::

### 6.2.3 内部可变性的反例边界

第 4 章的 DropProbe 持有 Cell 引用。通过共享引用更新 Cell 是合法的。因此不能对该函数套用「共享引用绝不会变化」的无条件推理。本章加法内核的元素是普通 `u64`。没有在元素内部藏可变单元。

::: def 定义 6.2.3 · 内部可变性 {#def-6.2.3}

**内部可变性**（interior mutability）指通过共享引用 `&T` 仍能修改内容的机制，标准实现是 `UnsafeCell` 与包着它的 `Cell`。它不违反借用规则，因为可变性被藏在类型契约里。对优化器意味着：「共享引用指向的数据全程不变」这条推理必须先看元素类型，不能只看引用形式——这就是 [@def-6.2.1] 里「冲突访问」判断为什么不能靠引用数量草草得出。

:::

这种差异可能影响前端能生成的属性。也影响优化器是否可以把某次 load 长期保留在寄存器（CPU 内部最快取用的小存储格）。若把所有接口都改成地址整数，优化器也不会自动恢复完整契约。unsafe 不天然更快。它常常只是让程序员承担了额外证明。

### 6.2.4 不重叠切片如何安全取得

同一个缓冲中的不相交区域可以通过安全分割取得。例如 `split_at_mut` 给出两个不重叠可变切片。不需要先制造两个重叠可变引用，再承诺只访问不同下标。引用本身的有效性就需要满足契约。不能把「这轮循环恰巧没撞到」当成普遍证明。

若业务需要重叠源与目的，例如滑动窗口搬移，应选择相应 API。`copy_within` 的语义与两个不重叠切片相加不同。不能为了让 LLVM 更容易向量化，伪造不别名前提。正确做法是保留真实访问模式，再检查能否分阶段处理。本章所有正式内核使用不同 Vec 存储源和目的——这让 [@def-6.2.1] 的「无冲突访问」由构造方式给出，而不是由口头保证给出。

### 6.2.5 安全失败而非 UB 演示

本包有一个编译拒绝输入尝试重叠共享与可变借用。编译器报告 E0502。该程序没有被执行。这验证了某种非法调用形式被静态排除。它不是完整别名模型证明。

本章运行时还保留长度不符的明确失败路径。输入长度不等时，函数在进入循环前 panic。这比忽略多余元素更符合本实验的「逐元素配对」契约。失败由安全断言产生，不是越界访问。测试确认它确实被拒绝（见 [@def-6.3.1] 与 6.3 的长度拒绝回归）。

::: think 思考 · 编译期拒绝算不算别名模型的证据 {#think-6.2.1}

既然 E0502 拦下了重叠借用，能不能写「本包的别名契约已由编译器证明，因此 noalias 永远可信」？

::: sol 解答

不能，有两个跳跃。第一，E0502 只证明「这一种非法调用形式被静态排除」，某个具体程序没被拒不等于不存在合法但别名丰富的写法（再借用、内部可变性都属后者，[@def-6.2.3]）。第二，安全代码里的 noalias 来自借用契约；一旦接口被改成地址整数或包进 `unsafe`，契约由程序员承担，编译器不会自动恢复它——「unsafe 不天然更快」说的就是这件事。正确的写法是把结论限定在「本轮函数、本轮 IR 的观察」，正如 [@ex-6.2.1] 第 2 问的处理。

:::

:::

### 6.2.6 不应滥用 noalias 解释一切

即使没有强别名信息，编译器也可能生成运行时重叠检查。满足条件时走向量路径，否则走标量路径。本轮没有构造这种 raw pointer 对照。所以不报告「去掉引用会慢多少」。本文的对照改变的是调用边界，而不是把安全与 UB 放在一起计时。

如果想测别名属性的净影响，需要设计所有路径都合法的输入。应同时检查运行时检查与循环形态。不能用重叠 `&mut` 制造一个看似便宜的非法输入。未定义行为程序没有可用于性能比较的可靠基线。安全性证明先于优化归因。

::: method 判定流程 · 这条性能差异能不能归因给别名信息

1. **问合法性**：参与比较的每个 case 是否都在语言契约内？出现 UB 或编译被拒的写法直接出局（[@think-6.2.1]）。
2. **问对照变量**：本轮真正改变的是别名信息，还是调用边界、循环形态、内存分配？6.4 明确改变的是后者。
3. **问产物**：IR 与目标码里是否出现预期的差异（重叠检查的有无、循环宽度变化）？按 [@def-6.1.4] 逐层核对。
4. **缺证据就写未测**：本轮没有构造 raw pointer 对照，所以「去掉引用会慢多少」在本章是「没有采集」，不给数字也不给趋势。

:::

### 6.2.7 小结与常见错误

**小结。**① 要防的是冲突访问而不是别名本身（[@def-6.2.1]）；② noalias、readonly 与对齐观察是降级到 IR 的事实，各有自己的边界（[@def-6.2.2]、[@ex-6.2.1]）；③ 内部可变性会推翻「共享引用绝不变」的推理（[@def-6.2.3]）；④ 不重叠应由 `split_at_mut` 这类安全构造给出，失败应由断言给出；⑤ 没有对照就不写归因（本节的判定流程）。下一节 [6.3 边界检查、迭代器与循环向量化](#sec-cpp-rust.2.6.3) 看这些事实怎样汇成一条真的向量主体。

::: errata 常见错误清单（6.2 节）

E-a **以为 unsafe 会自动增加优化信息。**裸地址往往比安全引用丢失更多可用契约，本轮安全切片内核已经向量化（[@def-6.2.2]）。

E-b **把共享引用一概视为永不变化的内存。**`UnsafeCell` 与内部可变性需要不同推理，第 4 章的 Cell 计数就是合法变化的例子（[@def-6.2.3]）。

E-c **把 align 8 说成 16 字节保证。**类型最小对齐、实际放置、缓存行是三个不同概念（[@ex-6.2.1]）。

E-d **为了向量化伪造不别名前提。**重叠源与目的应选 `copy_within` 一类语义相符的 API（6.2.4）。

E-e **拿「这轮循环恰巧没撞到」当普遍证明。**引用本身的有效性就要满足契约（[@def-6.2.1]）。

E-f **用重叠 `&mut` 造一个看似便宜的非法输入做基线。**UB 程序没有可靠的性能比较基线（[@think-6.2.1]）。

E-g **把编译拒绝写成「别名模型已证」。**E0502 只排除这一种非法调用形式（本节的思考框）。

## 6.3 边界检查、迭代器与循环向量化 {#sec-cpp-rust.2.6.3}

本节回答一个问题：**同样一段「把两个切片逐元素相加」的 Rust 代码，什么条件下后端真的敢把它变成成组指令，又是什么条件把它挡在门外？**

::: preview 先抓住一件事

**向量化要同时凑齐三件事：长度关系可证明、跨迭代没有冲突访问、循环体里的操作看得见。**本章用安全写法一次凑齐：循环外 `assert_eq` 长度、源与目的用不同 Vec（[@def-6.2.1] 的无冲突由构造给出）、循环体内只做 wrapping 加法（[@def-6.1.2] 的语义允许）。对照内核只做一件事——把元素操作隔进一个 `inline(never)` 的调用——于是第三件被破坏。判断哪个条件掉了，比记住「迭代器比索引快」这类口号有用得多。
:::

### 6.3.1 先决定长度不等时的语义

zip 通常按较短一侧结束。这对某些业务是正确行为。但本实验要求输入与输出长度完全一致。因此内核先 `assert_eq` 长度。不要把漏算尾部误当成优化。

断言放在循环外。成功之后两侧具有同样的迭代上界。配对迭代避免每次显式下标访问都独立表达边界条件。编译器仍需要证明访问合法。它可以把已有类型与循环结构用于证明。

::: def 定义 6.3.1 · 长度一致契约 {#def-6.3.1}

**长度一致契约**指函数在进入循环之前先断言两侧切片等长，不等就 panic 失败。它与「按较短一侧静默截断」是两种语义：前者多余元素会让程序拒绝执行，后者会少算。[@def-1.6.1] 要求比较的双方算的是同一件事，所以契约必须在计时之前定下来；删掉断言、只留 zip 得到的不是「更快的同一个函数」，而是另一个函数。

:::

### 6.3.2 完整内核

```rust
#[inline(never)]
pub fn add_slices(output: &mut [u64], input: &[u64]) {
    assert_eq!(output.len(), input.len());
    for (out, &value) in output.iter_mut().zip(input) {
        *out = out.wrapping_add(value);
    }
}

#[inline(never)]
pub fn scalar_add(left: u64, right: u64) -> u64 {
    left.wrapping_add(right)
}

#[inline(never)]
pub fn add_with_calls(output: &mut [u64], input: &[u64]) {
    assert_eq!(output.len(), input.len());
    for (out, &value) in output.iter_mut().zip(input) {
        *out = scalar_add(*out, value);
    }
}
```

两个内核都没有 unsafe。都执行同样的 wrapping_add。区别是第二个逐元素调用 `inline(never)` 的 `scalar_add`。这人为保留一个不透明程度更高的调用边界。它是一个真实可执行的安全性能回退模型。

### 6.3.3 为什么会影响向量化

自动向量化需要看到重复元素操作之间的关系。若每个元素都进入一个保留函数调用，循环转换会受到限制。即使被调用函数体本身非常简单，属性与成本模型也可能选择不跨过它。本轮 `scalar_add` 调用确实留在循环里。因此对照不只是源码外观不同。

这不证明所有函数调用都阻止向量化。可内联的函数往往会先被展开。某些函数具有专用向量实现或可识别 intrinsic。某些调用还会被删除、合并或特化。本章只对本轮实际保留的边界下结论。

::: def 定义 6.3.2 · 保留调用边界 {#def-6.3.2}

**保留调用边界**指编译产物里确实存在一次 `call`，被调函数的体没有并进调用方。它由 [@def-6.1.4] 的「本机汇编」一层判定，而不是由源码上有没有写 `#[inline(never)]` 判定——属性只是提示（6.7）。边界一旦保留，循环里每个元素都要穿过它，向量化看到的就不再是一个可直接复制的元素操作，[@def-6.1.3] 的成本判断也随之一变。

:::

### 6.3.4 真实 LLVM 向量主体

下面是 `add_slices` 目标业务函数中的真实语句摘录。省略调试元数据和其他基本块。完整文件保存在 `stable-02/codegen/`。

```llvm
%wide.load = load <2 x i64>, ptr %1, align 8
%wide.load10 = load <2 x i64>, ptr %0, align 8
%8 = add <2 x i64> %wide.load10, %wide.load
store <2 x i64> %8, ptr %0, align 8
%index.next = add nuw i64 %index, 8
```

实际主体同时处理四组 2×i64。一次主体迭代推进八个元素。向量类型与向量操作都清楚存在。不同于第 5 章只有名为 vector.body 的标量展开。但仍需确认本机最终指令。

::: def 定义 6.3.3 · 向量主体与标量尾部 {#def-6.3.3}

**向量主体**（vectorized main loop）是循环里按向量宽度成组处理的那段：本轮一次推进八个元素。**标量尾部**（scalar tail）是长度不足一个主体时逐个处理的剩余部分，本轮测试覆盖到 0..129 的所有长度（6.3.6）。两者属于同一个函数的不同分支，所以「主体向量化」从不等于「所有输入都走 SIMD」——长度 7 的输入就走不到主体。

:::

### 6.3.5 本机目标码

```asm
ldp q0, q1, [x10, #-32]
ldp q2, q3, [x10], #64
ldp q4, q5, [x9, #-32]
ldp q6, q7, [x9]
add.2d v0, v4, v0
add.2d v1, v5, v1
add.2d v2, v6, v2
add.2d v3, v7, v3
stp q0, q1, [x9, #-32]
stp q2, q3, [x9], #64
subs x11, x11, #8
b.ne LBB6_5
```

这不是汇编语法课程。应关注的是成组读、成组加、成组写与八元素推进。同一函数还包含长度断言失败路径。也包含不足一个向量主体的标量尾部。不能只摘主体就宣布小输入也走同样路径。

::: ex 例 6.3.1 · 三处产物证据能否拼成一句结论 {#ex-6.3.1}

现在手上有三条证据：① IR 中 `%8 = add <2 x i64>`；② 本机汇编中四条 `add.2d` 与 `subs x11, x11, #8`；③ 6.4 的表里 zip 的批均值低于 calls。请写一句能被反驳的结论，并列出它依赖的三件事。

::: sol 解答

结论可以写成：「本轮 aarch64-apple-darwin 构建中，`add_slices` 的循环主体以每次八个元素的成组加载、相加、写回执行，而 `add_with_calls` 的产物保留逐元素调用。」它依赖三件事：合法性能被证明（[@def-6.3.1] 的长度断言 + [@def-6.2.2] 的 noalias/readonly）、循环体可见（[@def-6.3.2] 的对照没有被保留调用破坏）、以及 [@def-6.1.4] 的逐层核对——IR 一句、汇编一句，缺任何一层都要降级。反驳它的方式也很具体：拿出不同目标或不同版本的产物、或拿出该函数实际走标量尾部的长度，结论就不适用；③ 只能说明总体成本方向，不能单独证明「加速来自向量化」（[@ex-6.1.1]）。

:::

### 6.3.6 尾部测试的重要性

正式长度 16384 恰好能被八整除。只验证这个长度会漏掉尾部问题。测试因此遍历 0 到 129 的长度。包含空切片、短切片和非整块尾部。同时将输出初始化为 `u64::MAX`。

这验证 wrapping 语义和尾部结果。它不靠最终总和单独判断每个位置是否正确。两个向量化对照逐元素比较。额外再与 `input-1` 的 wrapping 参考值比较。这样比只看总 checksum 更强。

```rust
#[test]
fn vector_tails_and_max_values() {
    for len in 0..130 {
        let input = input_data(len);
        let mut left = vec![u64::MAX; len];
        let mut right = left.clone();
        add_slices(&mut left, &input);
        add_with_calls(&mut right, &input);
        assert_eq!(left, right);
        for (got, v) in left.iter().zip(input) {
            assert_eq!(*got, v.wrapping_sub(1));
        }
    }
}
```

### 6.3.7 长度拒绝回归

```rust
#[test]
#[should_panic(expected = "assertion")]
fn unequal_lengths_are_rejected() {
    add_slices(&mut [0; 2], &[1]);
}
```

测试有意触发定义良好的 panic。没有越界读取，也没有未初始化输出。若将断言删除而保留 zip，测试可能不再失败。那会改变函数契约，并可能漏处理目的尾部。优化前后应首先保证这种行为没有被意外改写。

::: think 思考 · 「测试全绿」是不是向量化的证据 {#think-6.3.1}

0..129 的长度全部通过、逐元素与参考值一致。有人据此主张「功能正确说明向量化路径也被验证过」。这个前提能被怎样绕过？

::: sol 解答

绕过方式是：全部走标量路径，测试同样全绿。正确性测试证明的是「语义与尾部都对」，[@def-6.3.3] 的两条路径有没有真的生成、走没走，属于产物层问题，要在 IR 与目标码里看（[@def-6.1.4]）。反过来也成立：看到主体里有 `add.2d`，不能推出小输入也用了它。两条证据链各有各的用处，测试的作用是让人可以放心地只挑一个分支去读汇编，而不是替汇编说话（对照 [@ex-1.5.1] 里「断言通过」与「工作发生」的分工）。

:::

::: method 判定流程 · 这个循环能不能向量化

1. **定语义**：长度不等是拒绝还是截断？写进契约并留回归测试（[@def-6.3.1]）。
2. **查冲突**：源与目的会不会重叠？本章用不同 Vec，让 [@def-6.2.1] 的判断不用靠推理。
3. **看上界**：循环长度关系在循环外证明过一次吗（断言后的等长）？
4. **看可见性**：元素操作有没有被保留调用挡住（[@def-6.3.2]、6.7 的属性只是提示）。
5. **逐层验证**：IR 里的向量类型 → 目标码里的成组指令 → 覆盖尾部的测试 → 最后才读计时表。

:::

### 6.3.8 小结与常见错误

**小结。**① 语义先定：长度一致契约让「少算尾部」不被误当优化（[@def-6.3.1]）；② 合法与成本两道门都要过（[@def-6.1.3]），本轮靠 noalias/readonly 加可见循环体；③ 产物证据分主体与尾部，「向量化」不覆盖所有长度（[@def-6.3.3]）；④ 测试证明语义，汇编证明指令，两者不能互换（[@think-6.3.1]）。下一节 [6.4 benchmark 一：完整数据通路中的调用回退](#sec-cpp-rust.2.6.4) 把这两个内核放进正式计时，看完整边界下的差值。

::: errata 常见错误清单（6.3 节）

E-a **删除长度断言后把少算元素当加速。**zip 本身按较短序列停止，不同语义不能进同一性能结论（[@def-6.3.1]）。

E-b **只测整除向量宽度的长度。**16384 能被八整除，正式热长度会漏掉尾部错误（[@def-6.3.3]）。

E-c **用总 checksum 代替逐元素校验。**位置错误可能在总和里互相抵消（6.3.6）。

E-d **把「调用一定挡向量化」写成通用规律。**可内联函数会先展开，某些调用被删除、合并或特化（[@def-6.3.2]）。

E-e **只摘向量主体就说小输入同样快。**同一函数还有失败路径与标量尾部（[@ex-6.3.1]）。

E-f **以为源码写了 `inline(never)` 就等于产物里有 call。**属性是提示，要在目标码里确认（6.7）。

E-g **把测试通过当成向量化证据。**功能与产物是两条证据链（[@think-6.3.1]）。

:::

## 6.4 benchmark 一：完整数据通路中的调用回退 {#sec-cpp-rust.2.6.4}

本节回答一个问题：**「保留一次函数调用」让程序慢了多少，这个差值究竟测的是什么、能说到哪一步？**6.3 已经在产物层看到两个内核的不同；这一节把它们放进正式计时，并逐条说清计时边界。

::: preview 先抓住一件事

**这张表测的是完整数据通路：清零、加法、校验读取三部分都在批计时内，所以它不等于纯向量加法带宽。**要肯定「调用边界造成了回退」，需要同一计时集合、同一语义、同一夹具下的两个 case，加上产物里确实保留的调用；要否定「这就是裸 call 的延迟」，只需要指出循环宽度、寄存器使用和读写交错也同时不同。两个方向都能站住。
:::

### 6.4.1 不只测一条 add

入口为 `src/bin/vectorize.rs`。每次内核运行先把输出清零。然后对所有元素做加法。最后读取输出计算 checksum。这三部分都在批计时内。

清零使每次调用从相同状态开始。否则重复调用会累积输出，参考结果也要随次数变化。保留 checksum 读取确保结果被观察（[@def-1.3.1] 要求「结果进入观察集合」）。它也增加了共同的内存通路工作。所以表格不等于纯向量加法带宽。

::: def 定义 6.4.1 · 完整数据通路 {#def-6.4.1}

**完整数据通路**指计时区间覆盖的那条真实执行链：`output.fill(0)` → 配对读取与加法 → 输出求和。它相对「只测内核」多包含初始化与观察工作，相对端到端吞吐又少了 Vec 创建。写 ns/元素时必须同时说清这个集合（[@def-1.2.3]），否则同一个数字可以被解释成两种东西。

:::

### 6.4.2 完整入口

```rust
use compiler_lab::{Case, add_slices, add_with_calls, borrowed_sum, input_data, measure};
use std::hint::black_box;
fn run(f: fn(&mut [u64], &[u64]), input: &[u64], output: &mut [u64]) -> u64 {
    output.fill(0);
    f(black_box(output), black_box(input));
    borrowed_sum(black_box(output))
}
fn main() {
    let input = input_data(16384);
    let mut left = vec![0; input.len()];
    let mut right = left.clone();
    let expected = input.iter().copied().fold(0, u64::wrapping_add);
    let mut cases = [
        Case {
            name: "zip",
            run: Box::new(|| run(add_slices, &input, &mut left)),
            expected,
        },
        Case {
            name: "calls",
            run: Box::new(|| run(add_with_calls, &input, &mut right)),
            expected,
        },
    ];
    measure(&mut cases, input.len());
}
```

两个输出缓冲分别持有。它们不与输入重叠。case 创建时没有把正在使用的同一 Vec 借给两份闭包。编译器检查了这些独占借用关系。正式执行时 case 顺序轮转（轮转与配对的理由见 [@def-1.4.1]）。

::: def 定义 6.4.2 · 期望值与参考计算 {#def-6.4.2}

**期望值**指由被测实现之外的途径独立算出的结果，本例为 `input.iter().copied().fold(0, u64::wrapping_add)`。两个 case 共用同一个 `expected`，因此「输出一致」是 [@def-1.6.1] 意义上的同一件事；如果让期望值来自其中一个 case，断言就只会验证错误目标（[@ex-1.5.1]）。

:::

### 6.4.3 计量表

| 阶段 | zip | calls | 是否共同存在 |
|:--|:--|:--|:--|
| 创建 Vec | 计时外 | 计时外 | 是 |
| output.fill(0) | 计时内 | 计时内 | 是 |
| 配对读取与加法 | 计时内 | 计时内 | 是 |
| scalar_add 保留调用 | 无 | 每元素有 | 否 |
| 输出求和 | 计时内 | 计时内 | 是 |
| 批 checksum 断言 | 时间戳后 | 时间戳后 | 是 |

不能把 `calls` 与 `zip` 的差值完全归成函数调用的裸延迟。循环宽度、寄存器使用、读写交错也不同。但我们可以准确说：把这个小操作隔在保留调用后面，导致本轮总体成本增加。这是足够具体、可重现的工程结论。不需要虚构硬件计数来增强说服力。

### 6.4.4 实测结果

| case | mean ns/元素 | N-1 sd | 批 p50 | 批 p99 |
|:--|--:|--:|--:|--:|
| zip | 0.347104 | 0.016887 | 0.346487 | 0.378854 |
| calls | 0.723644 | 0.059594 | 0.718884 | 0.833090 |

zip 路径在本机这组桌面测量中更快。目标码同时证明向量主体保留。`calls` 的目标码保留逐元素直接调用。结果与代码生成方向一致。没有将此差值外推为所有数据长度的固定加速比。

::: ex 例 6.4.1 · 从这张表里能读出哪三句、不能读出哪三句 {#ex-6.4.1}

用 [@def-1.5.2] 的口径读上表：每格单位都是 ns/元素，样本是 21 个批均值。

1. 差值「calls − zip」的均值是多少？它是配对差值还是两组均值之差？
2. 「zip 每元素多花 0.347 ns，就是一次 u64 加法的成本」——能写吗？
3. 「p99 0.378854 是尾延迟」——能写吗？

::: sol 解答

1. 按本表两列直接相减得 0.723644 − 0.347104 = 0.376540 ns/元素，这是**两组均值之差**。要得到配对差值及其区间，必须按轮相减（[@def-1.4.2]）；本轮归档没有把这一对差值的区间作为结论给出，所以这里只用它说明量级，不写「显著」。
2. 不能。它是 [@def-6.4.1] 的完整通路批均值，包含 `output.fill(0)`、向量主体、标量路径与 checksum 读取，不是单条指令延迟（同 [@ex-1.5.1] 第 1 问）。
3. 不能。p99 是 21 个批值的 nearest-rank 分位数，而 21 个数上 `ceil(21 × 0.99) = 21`，所以它就是最大批值（[@def-1.5.2]）；请求级尾延迟需要逐请求观测，本章没有采集。

:::

### 6.4.5 缓存与尺寸限制

输入为 16384 个 `u64`，即 128KiB。每个输出也同样大小。多轮重复会形成热数据访问情形。这不是对大于末级缓存的数据流测试。也不是从磁盘到输出的端到端吞吐。

本章不计算 DDR 带宽。因为初始化、求和、缓存写回与硬件缓存层次都影响实际总流量。只把数组字节数除以总时间，未必等于外部内存流量。没有采集内存控制器计数。因此只报告明确定义的 ns/输入元素。同样地，IPC、cache miss、周期数与能耗本轮都没有采集，本节不给出这些数字，也不给出它们的变化趋势。

### 6.4.6 可执行的修复方向

真实代码若出现类似回退，应先检查小函数是否可见。可以让合适的小内核被内联。也可以提高 API 粒度，让整个切片在具体实现内处理。不应首先把安全循环改成 unchecked 下标。本轮安全 zip 已经得到向量化。

若内核很大，强制 `always inline` 可能反过来增加代码体积。若需要独立 ABI 或调试边界，也可能必须保留调用。应把这些约束纳入设计。「删除所有函数边界」不是本章的建议。先测真实热点，再决定哪个边界值得改变。

::: method 判定流程 · 看到类似回退时按顺序做

1. **确认差值可信**：先看是不是同一计时集合、同一期望值下的比较（[@def-6.4.1]、[@def-6.4.2]），再看波动（[@def-1.5.2]）。
2. **回产物层定位**：找出被保留的调用边界（[@def-6.3.2]、[@def-6.1.4]），别停在「源码看起来差不多」。
3. **选最小改动**：优先让小内核可见或提高 API 粒度，而不是先动 unchecked 访问——后者把 [@def-6.2.1] 的证明责任从编译器转到你。
4. **改完重测并重生成产物**：换边界就是新实验，需要新归档（[@def-1.8.1]），不能在旧表上写新句子。
5. **保留非性能约束**：独立 ABI、调试栈形状、构建时间都可能是保留调用的正当理由（6.7）。

:::

### 6.4.7 归约、循环依赖与不能随意重排的业务

本轮向量加法对不同输出位置分别写入。第 i 个元素不读取第 i−1 个元素的新结果。这种独立性有利于成组处理。如果业务改成前缀和，访问关系就不同。前缀和需要把此前结果传给后续位置。不能只把相同的 zip 结构复制过去，就期待同一种向量化。

归约也需要看运算语义。本章 `u64` wrapping 加法可以按模运算重新组合（[@def-6.1.2]）。但浮点加法通常不满足相同结合律。改变归约树可能改变舍入路径。若未来扩展浮点实验，应明确结果要求。逐位一致、绝对误差和相对误差是不同契约。

本章没有打开 fast-math 类选项。也没有把整数结论转成浮点允许任意重排。如果提出近似算法，需要先给出输入定义域。还要覆盖零、符号变化、极端值与非有限值的处理。再为同一域报告最大误差或其他清楚的指标。速度表不能替代这些语义检查。

| 循环形态 | 必须先检查的依赖 | 本章证据范围 |
|:--|:--|:--|
| 独立逐元素加法 | 源目的不冲突、长度一致 | 已运行与逐元素测试 |
| wrapping 求和 | 模运算可组合、尾部完整 | 已用于输出观察 |
| 前缀递推 | 后续读取此前新结果 | 未做正式实验 |
| 浮点归约 | 舍入与允许的重排范围 | 未使用该类内核 |
| 含外部副作用的映射 | 调用顺序和可观察行为 | 不能套用纯加法结论 |

这张表不是要在本章增加未经测量的性能排名。它说明一个向量化成功案例究竟依赖哪些事实。实际循环含日志、锁或错误提前返回时，应重新分析。若某个元素处理可能 panic，也要考虑部分更新的可观察状态。本轮内核在长度检查成功后只做 wrapping 整数加法。因此没有中途数值溢出 panic 的路径。

### 6.4.8 对照完整数据通路而不是只看主体

目标码中的向量主体很容易吸引注意。但真实调用还可能包含短输入分支。可能有长度检查。可能有标量尾部。可能有输出清零与校验读取。本章正式时间保留这些夹具工作（[@def-6.3.3]）。

如果需要纯内核吞吐，可以另外设计输出复用与观测方法。但不能从现有时间里主观减去一段没有测量的开销。尤其不能把 fill 的预估成本从两种结果中分别扣除后宣称净加速。独立测量之间可能共享缓存、调用和调度效应。减法不自动产生干净的内核时间。本章直接报告完整边界，更容易复现和解释。

第一轮 `stable-01` 的 zip 均值为 0.311992 ns/元素。主表采用第二轮 `stable-02` 的 0.347104 ns/元素。两轮均保留所有原始点。没有为了更漂亮的数字选择第一轮 zip、第二轮其他 case。不同轮的变化提醒读者这里不是隔离实验室。但两轮都保留了同方向的调用边界回退。这支持局部机制观察，不支持某个普遍固定倍数。

::: think 思考 · 能不能把 fill 的成本减掉，只报「内核时间」 {#think-6.4.1}

`output.fill(0)` 对两个 case 都一样，看起来像一笔可以从两边同时扣除的公共开销。为什么本章不这么算？

::: sol 解答

因为减法的被减数必须是被测对象的组成部分。这里只有一份完整通路的计时（[@def-6.4.1]），fill 从未被单独计时，所谓「预估成本」是主观估计；把它从两个数里各减一次，得到的差值不再对应任何一次真实运行。更麻烦的是两项工作会互相影响：fill 刚写过输出，加法紧接着读同一批缓存行，两个 case 的共享效应不一样，减法不自动产生干净的内核时间。真要纯内核吞吐，唯一办法是重新设计夹具并另开一轮归档（[@def-1.8.1]），而不是在旧表上做算术。

每个 case 至少预热 500ms。每个 case 21 个正式批次。样本是批均值，不是每个元素独立延迟（[@def-1.2.2]）。标准差采用 N−1。nearest-rank p99 在此就是最大批值（[@def-1.5.2]）。

### 6.4.10 小结与常见错误

**小结。**① 计时集合是完整数据通路，单位必须带着它一起读（[@def-6.4.1]、[@ex-6.4.1]）；② 两个 case 只差一个保留调用边界，期望值同源独立（[@def-6.4.2]、[@def-6.3.2]）；③ 差值支持「本轮总体成本增加」，不支持「裸 call 延迟」也不支持固定倍数；④ 内存带宽、IPC、尾延迟等维度本章没有采集（6.4.5）；⑤ 修复按流程走，先产物后边界（6.4.6）。下一节 [6.5 CTFE、普通常量传播与 Miri 的分界](#sec-cpp-rust.2.6.5) 把「成本在哪个阶段发生」这个问题换到编译期。

::: errata 常见错误清单（6.4 节）

E-a **把一次保留调用的差值叫裸 call 延迟。**调用边界还影响内联、展开和向量化（[@def-6.3.2]、[@ex-6.4.1]）。

E-e **主观减去没测过的开销。**减法不产生干净内核时间（[@think-6.4.1]）。

## 6.5 CTFE、普通常量传播与 Miri 的分界 {#sec-cpp-rust.2.6.5}

本节回答一个问题：**「这段计算发生在编译期」到底是什么意思，它和「编译器顺手折叠了」「我跑过 Miri」分别是三件事中的哪一件？**

::: preview 先抓住一件事

**三句话很容易被混成一句：`const fn` 可以在常量上下文求值、优化器可能折叠常量输入的调用、`cargo miri test` 检查过执行路径。**它们的主体、覆盖面和失败方式都不同。本章把 `static BIT_TABLE` 的初始化器交给编译期求值，这是语言要求的 CTFE；`runtime_table` 用 `black_box` 挡住折叠，是故意留下的运行时对照；Miri 本轮根本没有执行，所以测试列表里没有它。判定的抓手是「哪个组件在哪一阶段执行了这段代码」，而不是「有没有出现 const 这个词」。
:::

### 6.5.1 const fn 不代表每次调用都在编译期

const fn 表示某个函数满足常量上下文可调用条件。在 const 或 static 初始化器等常量上下文中使用时，需要编译期求值。在普通运行时代码中调用，仍可以作为普通函数执行。优化器也可能把某些常量输入调用折叠。这与语言要求的 CTFE 不是同一个承诺。

因此 `const fn` 不是一个性能属性的别名。它不保证所有运行时调用零开销。也不保证输入未知时能神奇地提前计算。常量上下文、输入可知性和优化决策需要分别判断。本章用 static 初始化明确要求预计算。

::: def 定义 6.5.1 · CTFE（编译期求值） {#def-6.5.1}

**CTFE**（compile-time function evaluation，编译期函数求值）指常量上下文——`const` 项、`static` 初始化器、数组长度、泛型常量参数等——要求编译器在构建期间把表达式算成一个值。语言在这里给出的是**必须完成**：算不出来就编译失败，例如 6.5.4 的 E0080。`const fn` 只是「有资格参与这种求值」的函数声明，它本身不规定每次调用都发生在编译期。

:::

### 6.5.2 普通常量传播

::: def 定义 6.5.2 · 普通常量传播 {#def-6.5.2}

**常量传播**是优化器在运行时代码里把已知常量沿数据流推进、并顺带算掉部分表达式的变换。它是[@def-6.1.3] 意义上的**成本决策**：可做可不做、做多少取决于版本与上下文，所以不能作为承诺引用。与 [@def-6.5.1] 的区别：CTFE 是语义要求、失败即编译错误；常量传播是优化机会、不做也没错。`runtime_table` 里的 `black_box` 用来阻止后者冒充前者。

:::

### 6.5.3 本章的精确表

输入域是 0 到 255。每个表项记录该字节有多少个位为一。结果范围是 0 到 8。表大小为 256 字节。没有哈希，没有冲突问题，也没有近似误差。

编译期函数用移位和计数生成所有表项。`static BIT_TABLE` 的初始化器调用它。这要求编译器求得整个表。运行时查表使用字节转 `usize`，索引天然落在域内。所有转换都有清晰范围。

```rust
pub const fn bit_table() -> [u8; 256] {
    let mut table = [0; 256];
    let mut index = 0;
    while index < table.len() {
        let mut bits = index;
        let mut count = 0;
        while bits != 0 {
            count += (bits & 1) as u8;
            bits >>= 1;
        }
        table[index] = count;
        index += 1;
    }
    table
}

pub static BIT_TABLE: [u8; 256] = bit_table();

#[inline(never)]
pub fn runtime_table() -> [u8; 256] {
    // Runtime black_box prevents replacing this experiment with its const result.
    let seed = black_box(0usize);
    let mut table = [0; 256];
    for (index, slot) in table.iter_mut().enumerate() {
        let mut bits = index + seed;
        let mut count = 0;
        while bits != 0 {
            count += (bits & 1) as u8;
            bits >>= 1;
        }
        *slot = count;
    }
    table
}

#[inline(never)]
pub fn lookup_bits(table: &[u8; 256], input: &[u8]) -> u64 {
    input
        .iter()
        .map(|&v| u64::from(table[usize::from(v)]))
        .sum()
}
```

`runtime_table` 是故意保留的运行时构造对照。seed 在真实运行中为零。`black_box` 阻止编译器把整次实验直接替换为静态答案。这个屏障是夹具，不是生产优化建议——它与第 1 章的观察屏障同属一类工具（[@def-1.3.1]）。如果真实程序输入完全固定，编译器可能自动做得更多。

### 6.5.4 CTFE 的错误发生在哪一阶段

常量上下文中的越界不能作为成功常量值进入程序。本轮 `rejected/const_bounds.rs` 在编译时报告 E0080。它不生成可执行版本再等待运行时 panic。这个区别可以直接验证。失败输入如下。

```rust
const BAD: u8 = [1u8; 2][3]; fn main() { println!("{BAD}"); }
```

`extra.py` 检查了非零退出状态与错误代码。完整诊断保存在 `extra-02/const_bounds.txt`。本轮没有用 UB 常量来获得所谓快速路径。也没有把错误常量藏到不使用的分支中宣称验证通过。错误实际由引用它的 main 触发求值需求。

::: def 定义 6.5.3 · 常量求值失败（E0080） {#def-6.5.3}

**E0080** 是编译器在求值常量表达式时遇到非法操作所报告的错误码，例如上面那个越界下标。它的发生阶段是构建期：程序没有可执行版本，也就没有「运行时 panic」这回事。这与 [@def-6.5.1] 的「必须完成」是同一枚硬币的两面，也和 6.3 的长度断言形成对照——后者是定义良好的运行时 panic（[@def-6.3.1]）。

:::

### 6.5.5 编译器解释器与 cargo miri 不可混称

rustc 的 CTFE 使用 MIR 解释基础设施。Miri 工具也与 MIR 解释技术密切相关。但编译成功并不等于对整个程序运行了 Miri。CTFE 只求值所需的常量上下文。运行时的大部分行为没有因此被动态检查。

本轮没有执行 `cargo miri test`。nightly 安装也不可用。因此不能在测试列表中写「Miri 通过」。只能说静态表已经通过编译器常量求值并进入可执行产物。运行时测试又逐项验证了表值（6.6 的穷举验证）。

Miri 的通过也不等于完整形式语义证明。它只检查执行到的路径与所选模型范围。系统调用（程序请操作系统替它办事的那次请求）、目标差异和模型状态还可能限制覆盖。这些是一般边界，不是本轮执行结果。没有执行就不填写一个虚假的绿色状态。

::: def 定义 6.5.4 · Miri 工具 {#def-6.5.4}

**Miri** 指 `cargo miri test` 这类**工具运行**：它把（通常未经优化的）程序交给 Rust 的 MIR 解释器执行，报告越界、悬垂、数据竞争等未定义行为。它和 [@def-6.5.1] 共享解释技术，但覆盖对象完全不同：前者检查你真正跑到的运行时路径，后者只求值常量上下文。两者都受路径覆盖限制（[@def-1.5.2] 意义上的「样本能说到哪」）。

:::

::: ex 例 6.5.1 · 三句陈述分别属于哪个组件 {#ex-6.5.1}

判断下面三句话各自成立与否，并说明依据来自哪一层：

1. 「`static BIT_TABLE` 的值是编译期算出来的。」
2. 「`runtime_table()` 在真实运行中每次调用都执行构造循环。」
3. 「本包通过了 Miri 检查，所以没有未定义行为。」

::: sol 解答

1. 成立。`static` 初始化器属于常量上下文，[@def-6.5.1] 要求编译器求得整个表；表已进入可执行产物，6.6 的产物检查确认 `runtime_table` 的构造循环是**另一个**函数。
2. 成立，但有边界。它是 [@def-6.5.2] 意义上的运行时执行：`black_box` 挡住了常量折叠，产物里保留逐表项循环与计数循环（6.6）。这不等于生产代码也必须这样写——屏障是夹具。

### 6.5.6 CTFE 与 build.rs 的目标环境

CTFE 依照编译目标的数据模型解释常量。例如目标 `usize` 的宽度由 target 决定。`build.rs` 则是运行在 host 上的普通程序。交叉编译时，host 和 target 可能不同。这会影响按指针宽度生成表或布局的逻辑。

`build.rs` 可以访问文件、环境或外部工具。这很灵活，也引入输入声明与可复现性责任。需要明确 `rerun-if-changed` 和相关环境变量。不能依赖未记录的当前目录、时间或网络响应生成发布数据。本章没有使用 `build.rs`。

::: method 判定流程 · 「这段代码在哪个阶段跑」

1. **看上下文**：`const`/`static` 初始化器、数组长度 → 常量求值，必须成功（[@def-6.5.1]、[@def-6.5.3]）。
2. **看调用点**：普通运行时代码调用 `const fn` → 运行时执行，最多可能被 [@def-6.5.2] 顺手折叠；要确认就看产物。
3. **看执行主体**：`build.rs` 跑在 host，不遵守 target 数据模型；CTFE 遵守 target。
4. **看检查工具**：只有实际运行 `cargo miri test` 才能声称 Miri 结果（[@think-6.5.1]）。
5. **不确定就分层写**：像 [@def-6.1.4] 那样，把「编译期事实」「运行时事实」「工具结论」分栏陈述。

:::

### 6.5.7 预计算不是免费消失

CTFE 把部分成本从运行期移到构建期。还可能增加二进制只读数据。大表也可能增加加载、缓存或重定位压力。编译时间与内存成本同样需要考虑。不能将「运行期少计算」概括成所有维度都更快。

本章表只有 256 字节。这有利于解释和穷举验证。不代表把任意数值函数变成巨大查表都合适。特别是近似函数，必须先说明定义域、误差度量和边界处理。本章没有通过近似偷换计算语义。构建期耗时、二进制各节尺寸增量、冷启动加载代价这三个维度**本节**都没有采集具体数字，6.6 的运行时表也不含 CTFE 的构建成本。别把它当成整章没有：6.7.6 给了 many O3、many ThinLTO、many PGO-use 三个产物的 `__text` 字节数（归档 `results/extra-02/{many,thin,pgo}-size.txt`；同目录另有 `one-size.txt`，217148 字节，本章表没用它），6.8 还报了 PGO 前后 128 字节的尺寸差。

构建耗时这一维度本章没有可用数字：仓里只有 cargo 的 `Finished … in 0.00s` 增量空构建行（`results/stable-01|stable-02/codegen-build.txt`），它不是单次 rustc 构建耗时。冷启动加载代价则全书都没测。

### 6.5.8 小结与常见错误

**小结。**① `const fn` 只是资格声明，真正要求编译期求值的是常量上下文（[@def-6.5.1]）；② 优化器的常量传播是成本决策，不能当承诺引用（[@def-6.5.2]）；③ 常量算不出来是构建失败，不是运行时 panic（[@def-6.5.3]）；④ Miri 是另一件工具、另一份覆盖面，本轮未执行（[@def-6.5.4]）；⑤ 预计算把成本移到构建期与数据体积，且 build.rs 属于 host（6.5.6、6.5.7）。下一节 [6.6 benchmark 二：静态表复用与逐批重建](#sec-cpp-rust.2.6.6) 把「放置时机」变成一张可复现的计时表。

::: errata 常见错误清单（6.5 节）

E-a **给函数加 const 就宣称运行时零成本。**普通上下文仍可在运行时调用 `const fn`（[@def-6.5.1]）。

E-b **把优化器的折叠当成 CTFE。**前者是机会、后者是要求，边界条件不同（[@def-6.5.2]）。

E-c **以为常量越界会「运行时才炸」。**本轮它编译期就报 E0080，没有可执行版本（[@def-6.5.3]）。

E-d **编译成功就写 Miri 通过。**CTFE 只求值所需常量，不检查运行路径（[@def-6.5.4]、[@ex-6.5.1]）。

E-e **把 build.rs 的 `usize` 当成 target `usize`。**构建脚本运行在 host，交叉编译要显式处理目标数据模型（6.5.6）。

E-f **把「运行期少算」说成所有维度都更快。**构建时间、只读数据体积、加载压力都是同一变更的代价（6.5.7）。

E-g **拿 `black_box` 当生产优化建议。**它是让对照成立的屏障（[@def-1.3.1]）。

:::

## 6.6 benchmark 二：静态表复用与逐批重建 {#sec-cpp-rust.2.6.6}

本节回答一个问题：**把同一张表放在编译期、放在全局、还是每次重建，代价差多少，而这个差值又能说明什么、不能说明什么？**

::: preview 先抓住一件事

**这张表比的是初始化的放置时机，不是查表与硬件 popcount 谁快。**`static_table` 的表已经在产物里，`rebuild_table` 每批都要先构造再用；两者的差值里包含构造成本，所以它既不是两种查表指令的比较，也不是 CTFE 编译器执行一次位运算的速度。肯定这条结论要给出：同一 `expected`、同一 `measure` 边界、产物里确实保留的构造循环；否定它只需要指出问题问的根本不是这件事。
:::

### 6.6.1 比较的是放置时机

入口是 `src/bin/ctfe_table.rs`。输入正好包含所有 256 个字节值。两种 case 都查表统计置一位数量并归约。区别是复用静态表，还是每次先运行时构造同样的表。因此它是初始化放置的对照。

它不比较查表与硬件 count_ones 的最快实现。count_ones 只用于计算参考值。也不证明查表胜过本机 popcount。若需要回答那个问题，应新增同语义计时 case。不能把参考实现的存在当成已经测量（[@def-1.6.1] 的「同一件事」在这里同样管用）。

::: def 定义 6.6.1 · 放置时机 {#def-6.6.1}

**放置时机**指同一份数据的构造工作发生在哪个阶段：常量求值期（[@def-6.5.1]，构建时一次）、进程启动后一次性初始化并复用、或每次使用前重建。本章的两个 case 分别落在第一和第三种。归一化时间因此测的是「构造 + 使用」的合成本，列名必须写清楚，否则读者会读成纯使用成本——这与 [@def-6.4.1] 的完整通路是同一类口径问题。

:::

### 6.6.2 完整入口

```rust
use compiler_lab::{BIT_TABLE, Case, lookup_bits, measure, runtime_table};
use std::hint::black_box;
fn main() {
    let input: Vec<u8> = (0u8..=255).collect();
    let expected = input.iter().map(|v| u64::from(v.count_ones())).sum();
    let mut cases = [
        Case {
            name: "static_table",
            run: Box::new(|| lookup_bits(black_box(&BIT_TABLE), black_box(&input))),
            expected,
        },
        Case {
            name: "rebuild_table",
            run: Box::new(|| {
                let table = runtime_table();
                lookup_bits(black_box(&table), black_box(&input))
            }),
            expected,
        },
    ];
    measure(&mut cases, input.len());
}
```

输入构造在计时外。static 表已经属于可执行产物。`rebuild_table` 每次运行都生成一张局部表。构造和查表都在计时内。局部表不会逃逸为悬垂引用。

### 6.6.3 穷举验证

```rust
#[test]
fn ctfe_exhaustive_domain() {
    assert_eq!(BIT_TABLE, runtime_table());
    for v in 0u8..=255 {
        assert_eq!(u32::from(BIT_TABLE[usize::from(v)]), v.count_ones());
    }
}
```

测试先比较整张静态表与运行时表。随后逐项与字节的 count_ones 比较。这覆盖完整输入域，不只是几个常用值。输出上界也清晰地不超过八。不存在浮点比较容忍度的歧义（对照 6.4.7 的浮点契约）。

穷举域很小，适合做比 checksum 更强的校验。未来若把表换成更复杂映射，验证应继续保留。如果改成完美哈希，必须显式检查域内碰撞和域外拒绝。不能只给生成函数起名为 perfect 就算证明。本章没有采用哈希方案。

::: def 定义 6.6.2 · 穷举验证 {#def-6.6.2}

**穷举验证**指把输入的整个定义域逐一算一遍并与参考实现比较，而不是抽样几个常用值。本章的定义域是 0..=255，共 256 个输入，可以全部覆盖；比较的参考值是 `count_ones`，结果范围 0 到 8，没有近似误差。它比单一 checksum 强，因为位置错误不会在求和里相互抵消（同 6.3.6 的逐元素校验）。

:::

### 6.6.4 类型与布局表

| 对象 | 本机 size | align | 运行期角色 |
|:--|--:|--:|:--|
| [u8;256] | 256 | 1 | 整张精确表 |
| u8 输入 | 1 | 1 | 保证索引在 0..255 |
| u64 归约 | 8 | 8 | 保存一批统计值 |
| &amp;[u64] | 16 | 8 | 向量实验的输入位置与长度 |
| runtime_table 结果 | 256 字节 | 1 | 本轮经返回位置传递 |

表中 `u8 输入`（1/1）与 `u64 归约`（8/8）两行是按 Rust 数据模型推导的类型属性，不是从 `layout.csv` 量出的观测——该归档只登记 `[u8;256]`、`&[u64]`、`Vec<u64>` 等复合类型，没有裸 `u8` 与 `u64` 行；`[u8;256]` 256/1、`&[u64]` 16/8 与 `runtime_table` 的 `sret([256 x i8]) align 1` 才分别落在归档与 IR 上。

数组的 align 为一，不意味着静态项实际地址一定奇数。链接器可以给它更强的实际放置对齐。但调用者只能依赖语言与类型承诺的最低要求。也不能把 static 名称当成硬件 cache residency 保证。是否命中缓存是运行时观察问题。

::: def 定义 6.6.3 · 最小对齐与实际放置 {#def-6.6.3}

**最小对齐**（type alignment）是类型对地址的最低要求，`[u8; 256]` 是 1；**实际放置对齐**是链接器最终给某个静态项选定的地址属性，可能更强。两者都不是缓存行大小，也不是「一定常驻缓存」的保证。这与 6.2.2 的 `align 8` 是同一个区分：属性值来自类型降级，不等于 16 或 128 字节的承诺（[@ex-6.2.1]）。

:::

### 6.6.6 产物中的构造确实保留

`runtime_table` 的 IR 保留逐表项循环。内部还有对 bits 反复右移的计数循环。返回结果经 256 字节输出位置传递。本机目标码也保留这些循环与表数据写入。所以慢路径不是一个已被优化掉的假构造。

`static_table` 不需要执行相同的构造循环。但它仍需要读输入、查表与归约。表必须存在于程序的数据视图中。本轮没有测进程冷启动时首次加载该页的代价。热批次不等于冷加载成本。

::: think 思考 · 「慢的那一侧会不会已经被优化掉」 {#think-6.6.1}

性能对照最常见的失效方式是慢侧其实没在做事——或者被删成空循环，或者被折叠成静态答案。本节用了哪些手段排除这种失效？还能怎么绕过？

::: sol 解答

手段有三条：`seed` 经 `black_box` 处理，阻止整次实验被替换为常量结果（[@def-6.5.2]）；IR 与本机目标码里都确认构造循环和表写入仍在（[@def-6.1.4]）；`expected` 由独立参考计算给出并被逐批校验（[@def-6.4.2]、[@def-1.3.1]）。仍可绕过的地方是「冷加载」这一维：本轮没有测进程首次加载该页的代价，所以若把结论用于对启动时间敏感的场合，那部分是空缺，不是已通过。这与 [@def-1.8.1] 的「证据链覆盖到哪，结论就写到哪」一致。

:::

### 6.6.7 更贴近生产的三种选择

若表完全固定且很小，常量初始化很直接。若表依赖运行配置，可以在配置加载时构造一次并复用。若表依赖每条请求，不能把它移到全局而忽略输入差异。这三种情况有不同语义。本轮慢路径是故意重复构造固定表的回退案例。

修复不是「把所有函数加 const」。关键是表值是否真的在请求间相同。如果配置会更新，还需要版本与生命周期策略。如果表很大，还需要测缓存和内存预算。应让初始化位置与数据依赖相匹配。

::: method 判定流程 · 这张表该放在哪

1. **先问数据依赖**：值在请求间是否恒定？恒定才谈常量初始化（[@def-6.5.1]）；依赖配置就放配置加载时；依赖请求就保留在请求路径。
2. **再问体积**：小表（本章 256 字节）适合直接放产物；大表要算只读数据、加载与重定位成本（6.5.7）。
3. **然后看正确性能否穷举**：定义域小就用 [@def-6.6.2] 把整域跑一遍；不能穷举就要另设误差契约。
4. **最后测放置差值的完整通路**：按 [@def-6.4.1] 的口径把构造与使用一起计入，不要主观拆账（[@think-6.4.1]）。

:::

### 6.6.8 受控外推

对这个 256 字节全域输入，本轮结果稳定支持复用更便宜。不支持任何更大表的固定倍数收益。不支持某个实时系统的极端尾延迟。不支持 CTFE 没有编译资源成本。没有测量的维度继续保持未测。

## 6.7 内联、CGU 与 LTO：扩大视野也有代价 {#sec-cpp-rust.2.6.7}

本节回答一个问题：**编译器「看得见多少代码」是由哪些开关决定的，改变它们之后本章实际拿到了什么证据、哪些没拿到？**

::: preview 先抓住一件事

**内联、代码生成单元（CGU）与链接期优化（LTO）改变的是优化器的可见范围，可见范围本身既不是收益也不是成本。**属性的确切含义是提示：写了 `inline(never)` 要回到产物里确认调用真的保留（6.3），写了 `inline` 也不保证一定内联（[@def-6.7.1]）。本节能给的正面证据是功能与静态尺寸——三个构建的 `__text` 字节数和 16 个实例的输出校验；速度百分比一个都没有，因为对应样本没有采集。
:::

### 6.7.1 inline 属性是一种提示

Rust 参考手册明确将 inline 描述为优化提示。编译器本身也会根据启发式选择内联。没有属性不代表从不内联。有属性也不应被当作稳定指令边界契约。实际产物仍需检查。

本轮 `scalar_add` 使用 `inline(never)`。目标码确实保留该调用。`visible_dynamic` 也使用 `inline(never)`。但其内部的 dyn 来源仍能被消解。这说明一个函数边界被保留，不意味着函数体内部的优化冻结。

::: def 定义 6.7.1 · 优化提示（hint） {#def-6.7.1}

**优化提示**指写给编译器参考、但不构成接口承诺的标注。`#[inline]`、`#[inline(never)]`、`#[cold]` 都属于这一类：它们影响决策权重，最终产物由启发式与成本模型共同决定。判断方式只有一个——按 [@def-6.1.4] 看产物，而不是看源码写了什么。与之相对的是语言语义给出的保证（如 [@def-6.1.2] 的溢出行为），那种才能当承诺引用。

:::

::: def 定义 6.7.2 · 边界保留与体内优化 {#def-6.7.2}

**边界保留**指调用点在产物里仍然存在；**体内优化**指被调函数自身代码仍会被正常优化。两者互相独立：本轮 `visible_dynamic` 的调用边界被 `inline(never)` 保留，但它内部的 dyn 来源仍能被消解。所以「这个函数没被内联」推不出「这个函数体是原样编译的」。

:::

### 6.7.3 内联的主要价值不只是省 call

内联可以暴露常量参数。可以让范围关系进入同一控制流。可以删除无用分支。也可以让循环内的小操作成为向量化候选。因此某些回归差值远超过一条调用指令的直觉成本——6.4 里 `zip` 与 `calls` 的差值就是这种结构性收益的缺失，而不是 `call` 指令本身的账（[@def-6.3.2]、[@ex-6.4.1]）。

但内联也可能复制大型函数体。增加热代码体积与寄存器压力。改变调试栈形状。增加构建时间。不应该把 `always inline` 当通用优化开关。

### 6.7.4 代码生成单元的权衡

::: def 定义 6.7.3 · 代码生成单元（CGU） {#def-6.7.3}

**代码生成单元**（codegen unit）是 rustc 把程序切分给后端并行处理的单位。多个 CGU 允许后端并行处理不同模块，也可能改善修改后的复用；但部分优化信息会受到分区影响。`codegen-units=1` 能扩大某些局部视野，却可能减少构建并行。它是编译配置，**不是运行时线程数量设置**——这两件事混淆后，很容易把「构建变慢」误读成「程序里的并行变少」。

:::

本轮正式 profile 固定 `CGU=1`。`LTO=false`。因此主表不能被标为「开启跨 crate LTO 后的性能」。补充尺寸实验单独构建 ThinLTO。它与正式表格必须分开。

### 6.7.5 ThinLTO 的实际执行范围

`extra.py` 对同一个 `code_size` 探针（只为观察产物变成什么样而留下的小程序）生成普通 many 与 thin。thin 使用 `-Clto=thin`。两者都以 O3 与一个 CGU 构建。两个可执行文件都实际运行。所有 16 个实例的输出都与参考函数比较通过。

这给出了真正的功能与产物证据。没有正式采样两种构建的运行时间。因此不报告 ThinLTO 加速百分比。更小的代码节也不必然意味着任何特定负载更快。构建时间同样没有作受控比较。

### 6.7.6 已观察的节大小

::: def 定义 6.7.4 · `__text` 节大小 {#def-6.7.4}

**`__text`** 是 Mach-O 可执行文件里存放机器指令的节；本机用 `size -m` 读取。本节报的是它的字节数，属于**静态尺寸观察**：不含被 `__PAGEZERO` 虚拟保留的量，也不把调试符号文件长度当作 I-cache 工作集。它能说明「产物变小了」，不能单独说明「某个负载变快了」。

:::

| 构建 | __text 字节 | 对照意义 | 是否有正式速度样本 |
|:--|--:|:--|:--|
| many O3 | 220156 | 基线多实例产物 | 否 |
| many ThinLTO | 214768 | 完整构建优化后产物 | 否 |
| many PGO-use | 220028 | 使用训练 profile 的产物 | 否 |

所有数值来自 `size -m` 原始输出。不包括把 `__PAGEZERO` 的虚拟保留量当作代码。也不把调试符号文件长度当作 I-cache 工作集。这一口径足够明确，但仍是静态尺寸观察。需要运行行为时应另行设计正式测量。

::: ex 例 6.7.1 · 这张表能支撑的最强句子 {#ex-6.7.1}

由上表相减可得：普通 O3 与 ThinLTO 的 `__text` 差 220156 − 214768 = 5388 字节；与 PGO-use 差 220156 − 220028 = 128 字节。请写出这张表支持的最强结论，并列出两句它不支持的。

::: sol 解答

### 6.7.7 跨 crate 的可见性并非全有或全无

泛型函数通常需要把足够信息提供给实例化方。普通非泛型函数的处理又可能不同。inline 属性和 LTO 会影响可见性。构建 profile 还会改变优化预算。因此「跨 crate 就一定不能内联」同样过度简化。

真实排查可以先比较边界前后的产物。确认热点小核是否仍是保留调用。再尝试最小构建选项变化。如果同时改 LTO、CGU、panic 与 target-cpu，就难以归因。应一次控制清晰的问题，保留每种构建的输出校验。

::: think 思考 · 只改一个开关，为什么还可能有多个原因 {#think-6.7.1}

假设你把 `codegen-units` 从 16 改成 1，代码确实变小、某个 case 也确实变快。能写「这是 CGU 带来的收益」吗？

::: sol 解答

方向上可以，但要限定三点。第一，CGU 变小扩大的是优化可见范围，收益经由内联、向量化等具体机制实现，机制层证据要按 [@def-6.1.4] 去产物里找，否则只知道开关不知道原因。第二，构建并行度同时下降，构建时间成本本节没有采集，不能写成「没有代价」。第三，「变快」需要一次配对、同契约的计时（[@def-1.4.2]），并且像本节的表那样明确标注有没有正式速度样本；只有静态尺寸时，只能说尺寸。

:::

:::

### 6.7.8 不要把尺寸收益变成无限内联建议

ThinLTO 本轮缩小的是整个探针产物。其中可能包括标准库与其他函数的变化。无法只凭总差值判断某个用户函数该不该 inline。局部属性改动应有局部证据。全程序构建选项则要考虑完整构建成本和发布流程。

若编译时间是团队瓶颈，应同时记录构建矩阵。若部署包体积有限，应记录 strip 前后与相关节。若延迟是目标，应执行相同负载的正式配对测量。本轮没有混用这三种目标。第 14 章的发布工程可以在此基础上安排更完整矩阵。

::: method 判定流程 · 要动构建选项，先分清你在解哪个问题

1. **定目标**：尺寸、构建时间、还是运行延迟？三者的证据形式不同（6.7.8），别用一张表回答三个问题。
2. **定可见范围**：正式 profile 的 CGU 与 LTO 设置是什么？本轮是 `CGU=1`、`LTO=false`，主表不能标成 LTO 后的性能（[@def-6.7.3]）。
3. **一次只改一项**：LTO、CGU、panic 策略、`target-cpu` 同时改动就无法归因（[@think-6.7.1]）。
4. **每次构建都跑输出校验**：本轮两个构建各校验 16 个实例，功能不过关时尺寸数字没有意义（对照 [@def-1.6.1]）。
5. **缺的维度写未采集**：速度、构建时间若没测，就在结论里明说「没有正式样本」，不拿静态尺寸替代。

:::

### 6.7.9 小结与常见错误

**小结。**① inline 是提示，边界与体内优化要分别到产物里看（[@def-6.7.1]、[@def-6.7.2]）；② 内联的价值主要是暴露事实与结构，不是省一条 `call`（6.7.3，配合 [@ex-6.4.1]）；③ CGU 是编译并行单位，不是运行时线程数（[@def-6.7.3]）；④ 本节只有功能与静态尺寸两类证据，速度一律未采集（[@def-6.7.4]、[@ex-6.7.1]）；⑤ 尺寸、构建时间、延迟是三种目标，各要各的证据（6.7.8）。下一节 [6.8 PGO](#sec-cpp-rust.2.6.8) 把「输入给优化器的信息」换成真实执行分布。

::: errata 常见错误清单（6.7 节）

E-g **用总尺寸差判断某个用户函数该不该内联。**局部属性改动应有局部证据（6.7.8）。

## 6.8 PGO：真实训练、可用产物与未证明的收益 {#sec-cpp-rust.2.6.8}

本节回答一个问题：**PGO 的四步流程怎样在本机真实跑通，跑通之后能声称什么、哪些没拿到？**

::: preview 先抓住一件事

**profile 是构建输入，不是性能保证。**本轮四步全部实际执行：插桩构建 → 真跑一次产生 profraw → 用匹配版本的 llvm-profdata 合并 → 用 profile 重编译并执行校验，训练程序与使用程序的输出校验值相同。能据此说的是「流程可复现、产物可用、结果没变」；不能说的是「PGO 提升了百分之几」——两种构建的正式运行时间从未采集，训练负载也只是一个小探针。缺哪一样，那句话就不写。
:::

### 6.8.1 PGO 给优化器频率线索

profile-guided optimization（PGO，按性能分析数据指导的优化）收集实际执行分布。优化器可据此调整内联、布局和其他决策。它不会使错误算法自动正确。也不会使训练负载自动代表生产。训练数据是输入，而不是性能保证。

本章采用 rustc 支持的插桩流程。不是 Linux perf 采样式 PGO。也不是把 macOS sample 文本直接交给编译器。sample 报告与 LLVM profile 数据格式完全不同。两条证据链需要分别保存（对照 [@def-1.8.1] 的文件级链条）。

::: def 定义 6.8.1 · 插桩式 PGO 与采样式 PGO {#def-6.8.1}

**插桩式 PGO**在编译时往程序里插入计数代码，程序真跑一遍就写出执行计数文件（本轮走这条，产物是 `.profraw`）。**采样式 PGO**依赖外部性能监控设施定期抓取栈与事件（Linux perf 一类），不必重编译就有数据，但覆盖与精度取决于采样设计。macOS `sample` 的文本报告属于后一类工具的输出，格式与 LLVM profile 完全不同，不能直接交给 `-Cprofile-use`。插桩的固有代价是训练程序本身被改慢——6.8.6 会用到这一点。

:::

### 6.8.2 四阶段实际执行

第一步构建带 `profile-generate` 的程序。第二步实际执行它，产生 profraw。第三步用匹配版本 llvm-profdata 合并。第四步用 `profile-use` 重编译并执行校验。本轮四步均已完成。

训练对象是 `code_size` 的 many 配置。它依次访问 16 个实例，每轮按固定顺序处理输入。共重复 32 轮。这是一个可重复的小训练负载。它不是生产策略分布。

::: def 定义 6.8.2 · profraw 与 merged.profdata {#def-6.8.2}

**`.profraw`** 是插桩程序每次运行写出的原始计数文件，多次运行可能留下多个；**`merged.profdata`** 是用 `llvm-profdata merge` 把它们合成的一份 profile，供 `-Cprofile-use` 读取。两者都要留在归档里：只保存最后的二进制，就等于丢掉 [@def-6.8.1] 流程的输入，结论无法复核（对照 [@def-1.8.1]）。

:::

### 6.8.3 工具版本核对

本机 rustc 使用 LLVM23.1.1。所用 llvm-profdata 来自同一稳定工具链目录。其版本输出为 `23.1.1-rust-1.99.0-stable`。未使用 Xcode 中另一个版本的同名程序冒充匹配工具。完整命令与版本输出位于 extra-02。

`profile-generate` 与 `profile-use` 采用相同源文件。共同参数包括 edition2024、O3、CGU=1 和 cfg=many。按阶段变化的有三项：profile 模式、输出路径，以及 use 阶段多带的 `-Cllvm-args=-pgo-warn-missing-function`（`extra.py:54-55`，两份命令逐字对 `pgo-generate.txt:1` 与 `pgo-use.txt:1`）。profile 路径使用绝对路径。这避免工作目录变化使编译器读错数据。

::: ex 例 6.8.1 · 哪些文件能证明四步真的走完 {#ex-6.8.1}

假设你只拿到 `pgo-use` 这个二进制和它打印的一行 checksum。这够不够证明 PGO 流程完成？不够的话还缺哪些东西？

::: sol 解答

不够。一行输出只能证明「这个二进制跑过，并打印了 95338125850705920」。按 [@def-6.8.2] 与归档约定，至少要补齐四类：`pgo-generate.txt`（插桩构建的命令与结果）、`pgo-training-run.txt`（训练确实执行过）、`extra-02/pgo-data/` 里的 `.profraw` 与 `merged.profdata`（profile 的来源）、`pgo-merge.txt` 与 `pgo-use.txt`（合并与使用阶段的命令、版本，以及那条缺 profile 的警告）。再叠一份 `profdata-version.txt` 证明用的是匹配工具（6.8.3）。缺任何一件，「四步已完成」这句话就得降级——判据与 [@def-1.8.1] 相同：交出去的是证据链，不是一个文件。

:::

:::

### 6.8.4 可复现驱动代码

完整脚本为 `bench/compiler-lab/extra.py`。它拒绝覆盖已有输出目录。下面保留实际 PGO 分支的主要代码。`run` 会保存命令、stdout、stderr，并检查成功状态。

```python
sysroot = subprocess.check_output(['rustc', '--print', 'sysroot'], text=True).strip()
profdata = Path(sysroot) / 'lib/rustlib/aarch64-apple-darwin/bin/llvm-profdata'
if profdata.exists():
    run([profdata, '--version'], 'profdata-version.txt')
    data = out / 'pgo-data'
    data.mkdir()
    common = ['rustc', '--edition=2024', '-O', '-Ccodegen-units=1', '--cfg=many', root / 'probes/code_size.rs']
    run([*common, f'-Cprofile-generate={data}', '-o', out / 'pgo-train'], 'pgo-generate.txt')
    run([out / 'pgo-train'], 'pgo-training-run.txt')
    raw = list(data.glob('*.profraw'))
    assert raw
    run([profdata, 'merge', '-o', data / 'merged.profdata', *raw], 'pgo-merge.txt')
    run([*common, f'-Cprofile-use={data / "merged.profdata"}', '-Cllvm-args=-pgo-warn-missing-function',
         '-o', out / 'pgo-use'], 'pgo-use.txt')
    run([out / 'pgo-use'], 'pgo-use-run.txt')
    run(['size', '-m', out / 'pgo-use'], 'pgo-size.txt')
```

这段代码不是要求读者在已有归档里重复覆盖数据。应为每次尝试选择新目录。profraw 和 merged.profdata 一起保留。不要只保存最后二进制，却丢弃训练输入与编译日志。也不要把旧 profile 默默混入新源码构建（这条与 [@def-1.8.1] 的「指纹要对应」是同一要求）。

::: def 定义 6.8.3 · `-pgo-warn-missing-function` {#def-6.8.3}

这是通过 `-Cllvm-args=` 传给 LLVM 的一条诊断开关，作用是：使用 profile 重编译时，若某个函数在 profile 里没有对应记录就发出警告。本轮它确实报出一个 `lang_start` 包装函数缺少 profile 的警告，日志原样保存在 `extra-02/pgo-use.txt`。警告的含义是「训练覆盖或匹配有缺口」，不是编译失败——程序仍成功构建并完成输出校验。

:::

### 6.8.5 真实警告没有隐藏

`profile-use` 阶段启用了 `-pgo-warn-missing-function`。本轮出现一个 `lang_start` 包装函数缺少 profile 的警告。日志中原样保存。因此不能声称「所有函数的训练数据都完整匹配」。程序仍成功构建并完成输出校验。

**同一份归档里还有第二条更要紧的警告，先前只写 `lang_start` 是不完整的**：`pgo-training-run.txt` 第 3 到 12 行连着十次 `LLVM Profile Warning: Unable to track new values: Running out of static counters`。它出现在**训练阶段**，含义是计数器池不够用、新遇到的值没有被记下来，也就是这份 `.profraw` 本身就漏记了一部分分支与调用频次。后果要说白：本轮 PGO 的输入是一份**已知不完整**的 profile，由它得到的尺寸与行为差异只能代表「这份被截断的语料下的结果」。提示里给了修法（`-mllvm -vp-counters-per-site=<n>` 加大每个站点的计数器），但**本轮没有做第二次带该参数的运行**，所以这条缺口留着，不当它不存在。

这种警告需要根据真实项目检查。可能存在未覆盖函数、源码或选项差异。不应该直接关掉诊断，只为了得到干净日志。本轮没有进一步声称解决了该包装函数 profile 缺口。它作为已知局限保留。

### 6.8.6 结果校验与尺寸

训练程序输出 16 个实例的 checksum。`profile-use` 程序输出相同的 `95338125850705920`。每个实例还分别与参考函数比较。这验证该训练与使用流程没有在本测试域改变结果。不等于对所有可能输入完成形式证明。

PGO-use 的 `__text` 为 220028 字节。普通 many 为 220156 字节。这个静态差值很小。没有正式测量速度。所以本章不写「PGO 提升百分之几」。口径与限制同 6.7.6 的 [@def-6.7.4]：这是两个静态节大小的比较，不含运行时间，也不含构建时间；插桩训练程序自身的开销同样没有单独计时，属「本节没有采集」。

### 6.8.7 训练偏差是核心工程风险

只训练热路径会影响冷路径决策。只训练某一数据长度可能改变内联与分支选择。输入分布变化后，原 profile 可能不再有利。因此发布前应同时跑代表性负载与保留验证集。训练集与评估集最好不要完全重合。

本轮训练和验证共享一个小探针输入。这是流程验证，不是泛化收益验证。不能把它包装为生产 PGO 优化完成。更不能拿插桩程序的耗时与未插桩程序直接比较作为最终收益。插桩本身会改变执行开销（[@def-6.8.1]）。

::: think 思考 · 训练与校验同值，能不能推出「PGO 是安全的」 {#think-6.8.1}

`profile-use` 输出的 checksum 与训练程序一致，16 个实例逐个与参考函数比较也都通过。由此写「PGO 不改变程序行为，所以可以放心上生产」，漏了哪一步？

::: sol 解答

漏了两步。第一，校验通过只覆盖这个探针的这个输入域，它是正确性证据、不是性能证据，也不是形式证明（[@def-1.6.1] 式的「同一件事」范围要写清）。第二，「安全上生产」还需要行为之外的东西：训练分布是否代表生产负载（6.8.7）、profile 缺口是否影响关键函数（[@def-6.8.3]）、以及同负载的正式配对计时——本轮没有测，所以这一格是空缺而不是绿灯。补一句：把插桩程序的耗时拿来当收益基线也是错的，插桩本身改变了执行开销。

:::

:::

### 6.8.8 Cargo 工作流还要区分 host

若改成 Cargo 全工程 PGO，应固定 target。否则 `RUSTFLAGS` 可能影响 host 构建脚本等工具。构建脚本的执行分布通常不是目标服务要训练的对象。要记录 features、依赖版本与所有构建参数。本章独立探针没有第三方依赖或 `build.rs`（host 与 target 的分别见 6.5.6）。

匹配 profile 也需要匹配源码和工具链。更新编译器之后应重新训练和验证。不要把本机生成的数据当作跨目标通用配置。profile 是构建输入的一部分。它应该进入可追溯归档，而不是一个没人知道来历的二进制文件。

::: method 判定流程 · 一次 PGO 变更能不能算「做过验证」

1. **查工具匹配**：llvm-profdata 版本输出与 rustc 的 LLVM 版本一致，且来自同一工具链目录（6.8.3）。
2. **查阶段完整**：`*.profraw`、`merged.profdata`、四个阶段的命令与日志都在归档里（[@ex-6.8.1]）。
3. **查诊断**：missing-function 之类警告是否原样保留、是否解释过（[@def-6.8.3]）。
4. **查语义**：训练与使用两侧的输出是否与同一参考值比较通过（[@def-6.4.2]）。
5. **查收益声明**：有没有与目标负载一致的正式配对计时？没有就只写流程与尺寸，不写百分比（[@think-6.8.1]）。

:::

### 6.8.9 小结与常见错误

**小结。**① profile 是构建输入而非保证（[@def-6.8.1]）；② 四步都真跑过，证据按 [@def-6.8.2] 分层归档；③ 警告原样保留，缺口是已知局限（[@def-6.8.3]）；④ 尺寸差 128 字节属于静态观察，速度一律未采集（6.8.6、[@def-6.7.4]）；⑤ 训练分布决定结论范围，host 与 target 要分开（6.8.7、6.8.8）。下一节 [6.9 延伸阅读与来源](#sec-cpp-rust.2.6.9) 给出继续读的入口。

::: errata 常见错误清单（6.8 节）

E-a **把 `sample` 文本当作 PGO profile。**本轮用 LLVM 插桩产生 profraw，两条工具链要分别记录（[@def-6.8.1]）。

E-b **只保存最终二进制。**`.profraw` 与 `merged.profdata` 一起保留，否则输入丢失（[@ex-6.8.1]）。

E-c **隐藏 missing-profile 警告。**警告提示训练覆盖或匹配有缺口，本轮原样保留 `lang_start` 与训练阶段的十次 `Running out of static counters`（[@def-6.8.3]）。

E-d **从节大小差 128 字节推「PGO 收益」。**静态尺寸不是运行时间，本章没有速度样本（6.8.6）。

E-e **训练一次就认为对所有生产输入泛化。**本轮只验证流程与小探针计算，没有独立保留负载的评估（6.8.7）。

E-f **拿插桩程序耗时与未插桩程序比较当收益。**插桩本身改变执行开销（[@think-6.8.1]）。

E-g **用 Xcode 的同名 llvm-profdata 冒充匹配工具。**版本输出必须核对，且来自同一工具链目录（6.8.3）。

:::

## 6.9 延伸阅读与来源 {#sec-cpp-rust.2.6.9}

这一章的材料来自三类入口，你可以顺着它们继续往下读。

- **《Effective Rust》（母本 S08）第 15 条「理解借用检查器」**（PDF 126–130，台账行 `S08/COMPILER-S08-016`）：本章取的是该条后半段——借用规则让编译器能对数据的别名作更好的决策，换来更好的优化。它和本章 [@def-6.2.1] 是同一个议题——优化器要的是「没有冲突访问」这一可证明事实，不是「大概不重叠」。第 9 条（用迭代器转换代替显式循环）也相关：迭代器写法是否消去检查、能否向量化，都必须看当前生成产物，原书开篇不提供性能保证（[@def-6.1.4]）。
- **《Guide to Rustc Development》（母本 S09）**：MIR 优化与常量解释、Lowering 到代码生成 IR 与后端。读完对 [@def-6.1.1] 的「前端事实怎样降级」和 [@def-6.5.1] 的求值阶段会有具体图像。该卷把解释器基础设施与 Miri 的叙述放在一起，本章特意把两者拆开：编译器求值常量不等于对整个程序跑过 Miri（[@def-6.5.4]）。
- **Rust 参考手册（母本 S10）**：[代码生成属性](https://doc.rust-lang.org/reference/attributes/codegen.html)（`inline` 一类提示的规范口径，见 [@def-6.7.1]）与常量求值、常量上下文部分（[@def-6.5.1]、[@def-6.5.3]）。这里要加一条时效说明：S10 关于常量函数限制的描述来自较早版本，不能照搬「浮点在 const fn 中不可运算」这类历史表述当作当前限制；本章实验只依赖实际编译通过的整数操作，也没有据此声称新版全部 const 能力已被系统审阅。

在线补充材料两处，本章确实核读过正文：Nomicon 的 [Aliasing](https://doc.rust-lang.org/nomicon/aliasing.html) 一章用于解释合法性，不提供本机性能数值；rustc book 的 [Profile Guided Optimization](https://doc.rust-lang.org/rustc/profile-guided-optimization.html) 给出 6.8.2 那四阶段的官方流程，照着做即可。标准库文档另有三处值得一读：[`std::hint::black_box`](https://doc.rust-lang.org/std/hint/fn.black_box.html)（尽力而为的优化边界，不是同步屏障，见 [@def-6.5.2]）、[`std::cell::Cell`](https://doc.rust-lang.org/std/cell/struct.Cell.html)（内部可变性的合法例子，[@def-6.2.3]）、[`u8::count_ones`](https://doc.rust-lang.org/std/primitive.u8.html)（本章参考值的来源，[@def-6.6.2]）。构建选项的口径见 [Cargo profiles 与 codegen-units/LTO 设置](https://doc.rust-lang.org/cargo/reference/profiles.html)，对应 [@def-6.7.3]。

想自己动手复核本章数字，入口是这些：`bench/compiler-lab/` 是实验包；两个正式入口 `src/bin/vectorize.rs` 与 `src/bin/ctfe_table.rs`，正式批次分别存在 `vectorize.csv` 与 `ctfe_table.csv`；`stable-02/codegen/` 存稳定版 MIR、LLVM IR 与本机汇编（[@ex-6.3.1] 的依据）；`extra-02/` 有常量拒绝诊断 `const_bounds.txt`、PGO 各阶段日志与 `pgo-data/` 里的训练与合并数据（[@ex-6.8.1]）。复现命令汇总在 [6.11](#sec-cpp-rust.2.6.11)。

以下维度本章没有采集，读任何跨机器比较时都要先确认它们是否成立：没有 Linux perf 或硬件 PMU，所以没有 IPC、cache miss、周期数一类的数字；没有手写 SIMD 与 `target_feature` 派发实验；没有执行 Miri 工具；没有正式的 LTO 或 PGO 速度矩阵；没有近似数值函数的精度评估，因为本章没有使用近似。不同机器不应被要求复现相同纳秒数（[@def-1.8.1]）。

## 6.10 常见错误索引 {#sec-cpp-rust.2.6.10}

这一节是全章的常见错误索引，不是又一份逐节清单：每一节末尾的 `::: errata 常见错误清单（6.M 节）` 已经就地列出该节的具体错误，这里不再重述。下面十三条是只有把整章连起来读才看得见的误判模式，它们把同一种错误从产物、计时与构建三处串起来，也标出了回到哪一节去补证明。

1. **以为 unsafe 会自动增加优化信息。** 裸地址往往比安全引用丢失更多可用契约，因为别名与有效范围的事实正是在类型转换处断掉的。错误引用更可能造成 UB：契约缺失不会让代码变快，只会让编译器少一条可以依赖的前提。本章的安全切片内核已经向量化，恰好说明优化来自事实而不是来自 unsafe。

2. **将共享引用一概视为永不变化的内存。** `UnsafeCell` 与内部可变性让「共享引用指向的值恒定」这句话失效，需要另换一套推理。第 4 章的 `Cell` 计数就是合法的变化例子，不能拿它当反例扔回去。判断时应检查真实元素类型与访问契约，而不是只看参数写成了 `&T`。

3. **把 align 8 的向量访问说成 16 字节保证。** LLVM load 的对齐字段记录的是这条指令实际承诺的对齐，写 8 就只保证 8 字节。缓存行大小与类型对齐也没有直接等同关系，两者不是同一个尺子。若手写更强的对齐要求，必须另有证明，否则就是把未验证的前提写进了结论。

4. **删除长度断言后把少算元素当加速。** `zip` 本身按较短序列停止，少算的尾部不会报错，计时反而变漂亮。本实验要求长度一致，断言失败是契约违例而不是性能事件。不同语义的两段代码不能放进同一张性能表比较。

5. **只测整除向量宽度的长度。** 正式热长度往往带尾部，只测 8 的倍数会漏掉标量尾部与长度检查的错误。本轮测试包含空输入和 0..129 的尾部长度，让尾部路径也有观察。逐元素校验不能只用总和替代，否则元素重排也能通过总和校验。

6. **把一次保留调用的差值叫裸 call 延迟。** 调用边界还会影响内联、展开与向量化，差值里同时混着好几件事。本节测的是完整数据通路，不是一条指令的价格。要把机制归因到调用本身，必须同时看产物，确认保留下来的是哪条边界。

7. **给函数加 const 就宣称运行时零成本。** 普通上下文仍可在运行时调用 `const fn`，关键字不改变调用点的代码生成。本章用 `static` 初始化明确要求 CTFE，才让求值真的发生在编译期。预计算还会增加构建时间与数据体积，这两笔成本也要算进结论。

8. **编译成功就写 Miri 通过。** CTFE 只解释被要求求值的常量，不会检查整个程序的运行路径。本章没有执行 `cargo miri`，也没有拿 CTFE 的成功冒充它的结果。把「常量算出来了」写成「Miri 通过」，是两种工具、两种覆盖面的混淆。

9. **把 build.rs 的 usize 当成 target usize。** 构建脚本运行在 host 上，交叉编译时目标的数据模型可能不同。CTFE 与 host 侧的代码生成器也不能混称。涉及目标宽度时要在目标侧测试里确认，而不是相信构建脚本里的 `size_of`。

10. **从 ThinLTO 节变小推出速度必升。** 静态尺寸不是运行时间，节变小只说明代码布局变了。本章只执行校验并报告 `__text` 的大小。正式速度收益仍未测量，任何加速说法都要等到计时表出现。

11. **把 sample 文本当作 PGO profile。** 本章用 LLVM 插桩产生 profraw，再合并成 profdata 供构建使用。macOS 栈采样不是这种输入格式，两者不能互相替代。采样与插桩这两条工具链要分别记录，否则会把「采到了栈」当成「有了 profile」。

12. **隐藏 missing-profile 警告。** 警告提示训练覆盖或匹配可能有缺口，删掉它等于删掉证据。本章原样保留了 `lang_start` 的警告与训练阶段十次 `Running out of static counters`（后者说明这份 profile 漏记了值，见 6.8.5）。因此本章没有声称所有函数都训练完整，这个缺口是可以被看见的。

13. **训练一次就认为对所有生产输入泛化。** 本章只验证流程与小探针计算，样本不代表真实负载的分布。没有独立保留负载的性能评估，profile 只是把一次运行的偏见固化进产物。发布优化需要更完整的分布证据，否则收益只属于那次训练。

## 6.11 本章小结与章末件 {#sec-cpp-rust.2.6.11}

::: note 本章小结

- 后端只优化被保留下来的语义，别名、有效范围与对齐都是降级时写入的事实（[@def-6.1.1]、[@def-6.2.1]）。
- 合法性与成本是两道门，长度一致契约先过关，才轮得到向量化（[@def-6.1.3]、[@def-6.3.1]）。
- 「向量化」只覆盖向量主体，标量尾部与长度失败路径仍留在同一函数里（[@def-6.3.3]、[@ex-6.3.1]）。
- 完整数据通路的计时单位带着 fill 与 checksum，差值只能写成总体成本增加（[@def-6.4.1]、[@ex-6.4.1]）。
- `const fn` 只是资格，真正要求编译期求值的是常量上下文；Miri 是另一件工具、另一份覆盖面（[@def-6.5.1]、[@def-6.5.4]）。
- 内联、CGU 与 LTO 改变的是视野，本章对它们只有功能与静态尺寸证据（[@def-6.7.2]、[@def-6.7.4]）。
- profile 是构建输入而非保证，训练分布决定结论能走多远（[@def-6.8.1]、[@ex-6.8.1]）。

:::

### 出口检查

**复现命令。** 从 `cpp-rust/` 执行，并选择全新的归档目录：

```bash
cargo fmt --manifest-path bench/compiler-lab/Cargo.toml --check
cargo clippy --offline --locked \
  --manifest-path bench/compiler-lab/Cargo.toml --all-targets -- -D warnings
cargo test --offline --locked --manifest-path bench/compiler-lab/Cargo.toml
bash bench/compiler-lab/run.sh bench/compiler-lab/results/my-llvm-run
python3 bench/compiler-lab/extra.py bench/compiler-lab/results/my-pgo-run
```

正式脚本会运行六个入口，不是在后台并行运行一组 benchmark。PGO 驱动不做正式计时，它验证训练产物、合并工具与使用阶段的可执行性；找不到匹配工具时，脚本会明确记录未执行，而不是静默跳过。

**语义检查。** 你应能解释本章为什么使用 `wrapping_add`，说明长度不等时的预期失败，并指出本章没有浮点近似。字节查表索引始终落在 0..255，穷举 256 个值足以覆盖这个输入域，这两句要能自己证明。你还要能区分安全切片与任意 raw pointer 的契约，说明 `Cell` 为什么不能套用普通共享只读直觉。

继续追问：Miri 工具与 CTFE 的覆盖范围有何不同，`build.rs` 为什么按 host 执行，以及静态表为什么也有体积与加载成本。这三问分别对应工具边界、构建边界与数据边界。

**产物检查。** 在 `add_slices` 中找到真正的向量 load、add 和 store，并在本机汇编中找到对应的成组操作。同一函数里应同时存在标量尾部与长度失败路径。在 `add_with_calls` 中确认 `scalar_add` 被保留，在 `runtime_table` 中确认构造循环没有消失。

**测量解释。** 你要能回答五件事：为什么 `vectorize` 的 ns/元素包含 fill 和 checksum，为什么不能由这张表直接计算外部内存带宽，为什么 CTFE 表格比较的是初始化位置而不是 popcount 最优实现，为什么 21 批 p99 不是元素延迟或请求尾延迟，以及为什么 LTO 与 PGO 只能报告功能和静态尺寸。

**PGO 检查。** 应能找到 profraw 与 merged.profdata，指出 `llvm-profdata` 的实际版本，并核对 generate 与 use 的共同参数。missing-profile 的原始警告应仍在归档里，训练负载的分布为何不代表生产也要能讲清。

**完成与限制。** 两个正式入口共四个 case，每个 case 均有 21 个原始观察，全部输出校验通过；边界、尾部和常量拒绝测试实际执行，ThinLTO 与 PGO-use 产物也实际运行并验证过。本章没有声称普遍最快的实现，没有给出未经执行的 nightly 转储，也没有伪造 Linux perf、Miri 或硬件计数结果。完成的标准是语义、产物与数值相互对应，而不是每个开关都得到一个漂亮加速比。
