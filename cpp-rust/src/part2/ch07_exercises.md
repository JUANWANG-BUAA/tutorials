## A 组 · 概念（1–7）

::: ex A1 · 数据竞争的三个条件（主线 ①） {#ex-7.A.1}

「冲突访问」成立需要哪两个条件？在此之上再加哪一条才构成数据竞争？为什么「偶尔读到旧值」不是它的同义词？

::: sol 解答

冲突访问：两个访问的内存区域重叠，且至少一个是写入。数据竞争再加两条：冲突双方至少一个不是原子操作；两者之间没有 happens-before 排序。三条同时成立才是数据竞争。它是 UB（未定义行为，标准不再对结果作任何承诺），不是可以靠重试或加打印观察的温和错误——实验样本是否复现，与它成不成立无关。对照[定义 7.1.1](ch07.md#def-7.1.1)。

:::

:::

::: ex A2 · 三层证明各管什么（主线 ①） {#ex-7.A.2}

同步证明的三层分别证明什么？「两个库存字段都是原子，读取结果一定一致」错在第几层？反过来，用普通 `u64` 在两线程间轮询失了哪几层？

::: sol 解答

第一层是对象的合法生命周期：载荷存在、已初始化、未被提前销毁。第二层是访问互斥与可见性：谁能写、谁能读、哪条边建立同步。第三层是业务不变量：多个字段是否必须一起改变。库存快照不一致缺的是第三层的线性化点，不是原子性失效；普通 `u64` 轮询则第一、二层同时失守。原子类型只提供第二层的构件。对照[定义 7.1.2](ch07.md#def-7.1.3)。

:::

:::

::: ex A3 · 同步边的「观察到」前提（主线 ①） {#ex-7.A.3}

一个 Release store 与一个 Acquire load 要满足什么条件才构成 synchronizes-with？「两个线程一边摆一个」「反正是后来的时间点」为什么都不够？

::: sol 解答

当且仅当该 Acquire load 观察到了（reads-from，值来源关系）这个 Release store 写入的值。边成立后，Release 之前的所有写入对 Acquire 之后的读取可见。条件缺一不可：只有「一边一个」的形态，观察关系可能根本没发生；「后来的时间点」也不是关系本身，晚发生的 load 可能读到别的写入。对着[定义 7.2.2](ch07.md#def-7.2.2)与[例 7.2.1](ch07.md#ex-7.2.1)核对：读到 `false` 那一轮没有观察到发布，`x` 不受这条链保护。

:::

:::

::: ex A4 · RMW 的两半（主线 ①） {#ex-7.A.4}

`fetch_add` 的读侧与写侧分别由哪种 Ordering 约束？用 `Release` 递增去「发布」载荷，漏掉的保护是什么？

::: sol 解答

读侧指旧值被谁看到、能否获取对端发布；写侧指新值发布什么、对方 Acquire 后才能读到。Acquire 只管读侧，Release 只管写侧，AcqRel 两者都要。用 `Release` 递增时，递增自身的旧值读取没有获取语义，读到的前一状态不受保护；反过来 Acquire 也不发布写侧。对照[定义 7.2.3](ch07.md#def-7.2.3)。

:::

:::

::: ex A5 · Send 与 Sync 的两问（主线 ①） {#ex-7.A.5}

`Send` 与 `Sync` 各自管什么转移？按正文类型表，`Cell<u64>`、`Rc<u64>`、`UnsafeCell<T>` 各满足哪一侧？为什么 `Arc<RefCell<T>>` 不是多线程内部可变性的通用替代品？

::: sol 解答

`Send` 管值的所有权转移，`Sync` 管共享引用 `&T` 的转移，强度恰好是「多线程同时只读是安全的」。`Cell<u64>` 可 Send、不可 Sync；`Rc<u64>` 两者都不满足（引用计数非原子）；`UnsafeCell<T>` 是否 Send 取决于 `T`，且不自动具备 Sync。`Arc` 只包装所有权与计数，不会把任意 `T` 变成线程安全对象，共享引用那一侧仍按 `T` 判定。对照[定义 7.3.1](ch07.md#def-7.3.1)与 7.3.1 的类型表。

:::

:::

::: ex A6 · 八条义务（主线 ④） {#ex-7.A.6}

手写 `unsafe impl<T: Send> Sync for Slot<T>` 时，作者对所有调用方承诺哪八条？为什么编译器此后不再替你核对？

::: sol 解答

① 端点唯一，不存在两个并发生产者；② 不存在两个并发消费者；③ 消费者只在 full 状态读取已初始化的 `T`；④ 生产者只在 empty 状态写入；⑤ 两个方向均有 Release/Acquire 交接；⑥ `T` 作为值跨线程转移，因而要求 Send；⑦ 载荷不被多线程同时按共享引用访问，不要求 `T: Sync`；⑧ Slot 销毁时排除了所有存活端点。`unsafe impl` 绕过自动推导后，编译器停止核对，义务全部转给作者；任一条被后续修改破坏，整段实现失效。对照[定义 7.3.4](ch07.md#def-7.3.4)。

:::

:::

::: ex A7 · 聚合吞吐倒数（主线 ②） {#ex-7.A.7}

表中「ns/聚合操作」的分子与分母各是什么？为什么 0.070 不能读成「一条指令 0.07 纳秒」？21 个批均值的 p99 又是哪一个数？

::: sol 解答

它等于批次墙钟时间除以（线程数 × 每线程操作数），回答「系统整体每完成一次逻辑操作摊到多少时间」，是吞吐的倒数。分母合并了并行完成的操作，所以多线程下它可以小于单核一条指令的周期，不能当单次原子访问的延迟。21 个批均值的 nearest-rank p99 就是其中最大值，不是请求级尾延迟。对照[定义 7.5.2](ch07.md#def-7.5.2)。

:::

:::

## B 组 · 推理（8–15）

::: ex B8 · 哪两行才算单变量（主线 ③） {#ex-7.B.8}

四线程表里 Shared Relaxed 5.980、Shared SeqCst 5.952、Adjacent 5.253、Padded 0.418、Batched 0.070（单位 ns/聚合操作）。指出哪些两行构成单变量对照，哪些不构成，并说明每组差在哪。

::: sol 解答

单变量的只有两组：Shared 与 Shared-SeqCst 只差内存序；Adjacent 与 Padded 只差布局（是否按 128 字节行对齐隔离）。Shared 与 Padded 同时差布局与共享性，严格说不是单变量，其差值只支持「争用来自写入位置」的机制假设。Shared 与 Batched 同时差全局 RMW 次数与可观测语义，所以 0.070 不能写成「快 85 倍」的免费结论。对照[定义 7.5.1](ch07.md#def-7.5.1)与[例 7.5.1](ch07.md#ex-7.5.1)。

:::

:::

::: ex B9 · 同一条 movq 能推出什么（主线 ①） {#ex-7.B.9}

x86-64 上三种 load 都生成 `movq`，本机 Apple AArch64 分别是 `ldr`、`ldapr`、`ldar`。三句话哪些被这张表直接支持：①「x86-64 上 Acquire load 不需要专门指令」；②「三种 load 的源码语义可以互换」；③「换 rustc 版本后 `ldapr` 一定还在」？

::: sol 解答

只有①的弱化版：该版本编译器在探针里为三种 load 都选出 `movq`，与强序平台无需额外指令的解释相容。②不能——汇编相同推不出源码同步语义相同，周围操作的合法变换约束仍不同；③不能——表是固定 rustc 1.99.0 / LLVM 23.1.1 的产物观察，不是语言承诺。补充线索：同一平台的 `ldadd` 与 `ldaddal` 就说明变体差异确实存在。对照[例 7.4.1](ch07.md#ex-7.4.1)与[定义 7.4.1](ch07.md#def-7.4.1)。

:::

:::

::: ex B10 · 3070 比 112 缺哪四个限定（主线 ④） {#ex-7.B.10}

单槽忙等 112.239、`sync_channel(1)` 3070.823（单位 ns/message，21 批 × 5000 条）。把比值写「快约 27 倍」缺了哪些限定？合格的句子应该长什么样？

::: sol 解答

缺四项。① 条件：两端持续满载、消息间隔为零；到达稀疏时忙等方在空转烧核。② 对象：112.239 覆盖一整条 Release/Acquire 双向交接加逐条校验，不只是「一次传递」。③ 接口：`sync_channel` 有断开检测与阻塞语义，单槽没有。④ 尾延迟：批次 p99 127.900 与 3608.550 都是 21 个批均值的最大者，不是单条消息 p99。合格句：「在本夹具的饱和负载下，单槽忙等的批均耗时约为阻塞通道的 1/27；换到达率或换接口需求，数字不迁移。」对照[例 7.6.1](ch07.md#ex-7.6.1)。

:::

::: ex B11 · 把 false 方向的 Store 改成 Relaxed（主线 ①） {#ex-7.B.11}

有人主张：`full.store(false, Release)` 改成 Relaxed 没有影响，因为生产者下一轮写入前总会 load 到 `false`。这条论证漏了哪一环？为什么测试仍可能全过？

::: hint 提示

他证明了「生产者知道槽位空了」，但证明的是谁的什么对谁可见？

:::

::: sol 解答

他只论证了「生产者知道槽位空了」，没有论证「消费者读完对生产者可见」。Relaxed store 不释放之前的 `assume_init_read`，生产者的 Acquire load 观察不到发布边，`R happens-before N` 断链，下一代写入可能落在上一轮读取完成之前——这是[定义 7.1.1](ch07.md#def-7.1.1)意义上的数据竞争。有限压力测试在宽松调度下大概率全过，所以「没测出来」不能代替证明。对照[思考 7.2.1](ch07.md#think-7.2.1)。

:::

:::

::: ex B12 · 单线程下 Padded 为什么没有变快（主线 ③） {#ex-7.B.12}

单线程表里 Padded 1.697、Shared 1.703，均值差在 0.5% 以内。有人据此说「隔离没有收益」。他读错了什么？

::: sol 解答

读错了对照组的目的。单线程没有并发写入者，本来就没有要消除的跨线程伪共享，这张表的作用是证明夹具本身不引入收益，为四线程表里 0.418 对 5.980 的落差提供基线。数值接近正是这个对照该得的结果，两者也不必精确相等——地址、分支路径和运行顺序仍有区别。对照[思考 7.5.1](ch07.md#think-7.5.1)。

:::

:::

::: ex B13 · 826 次等待观察说明什么（主线 ②） {#ex-7.B.13}

`sample` 报告里主线程有 826 次观察落在等待路径，折叠统计中工作线程闭包关联栈 3281、`__psynch_cvwait` 847。能否据此写「锁占 CPU 的大头」？正确的读法是什么？

::: sol 解答

不能。这些是栈观察计数，不是硬件事件计数：单位是「被采样到的次数」，不是时间占比，也不是缓存失效数。主线程的职责就是等工作线程完成，它在 barrier 或条件等待中被采样很正常。正确读法是先按线程角色分组，确认工作线程正在跑哪段循环；要机制数字得在目标机按 7.7.5 的事件清单采集。对照[定义 7.7.1](ch07.md#def-7.7.1)与 7.7.4。

:::

:::

::: ex B14 · publication 反例证明了什么（主线 ①） {#ex-7.B.14}

示例输出 `ready=true payload=0: wrong program order, not a hardware-reordering test`。这句输出能否支持「Acquire/Release 不可靠」？示例真正演示的是哪一层的失守？

::: hint 提示

消费者到底有没有观察到那次 Release store？`payload.store(42, Relaxed)` 排在 Release 的哪一侧？

:::

::: sol 解答

不能。示例里 synchronizes-with 边其实成立了——消费者确实观察到了那次 Release store，所以「边不可靠」的指控不成立。问题在于该携带的载荷还没写：`payload.store(42, Relaxed)` 排在 Release 之后，不在发布范围内，边建立时它还不存在。按三层证明这是发布时机（第一、二层的拼接）错误，修复只需把 payload 准备挪到 Release 之前，不需要更换同步原语。把输出读成「硬件乱序」，等于把程序顺序 bug 判给 CPU。对照[例 7.7.1](ch07.md#ex-7.7.1)。

:::

:::

::: ex B15 · 把线程实验改成 fork 先撞上什么（主线 ④） {#ex-7.B.15}

团队想把本章实验搬到多进程共享内存：`std::thread` 换成 `fork`，`Arc` 换成裸偏移。按 `Send + Sync` 的定义与 7.8.3 的八项清单，最先失效的是哪条假设？随后还要补什么？

::: hint 提示

两个进程的虚拟基址一定相同吗？同一数值地址一定指向同一物理页吗？

:::

::: sol 解答

最先失效的是「地址空间同一」：两个进程的虚拟基址可以不同，同一数值地址不保证指向同一物理页，`Arc` 的计数写进映射也只在各自页里各数各的。`Send + Sync` 不含任何跨进程保证。随后要补 7.8.3 的八项：映射归属、偏移还是绝对指针、原子宽度与对齐、同步机制是否支持进程间共享、异常退出恢复、残留 full 的代际判定、版本布局协商、非法消息拒绝。多线程进程 fork 后继承的锁与分配器状态还可能让进程内证明整体作废。对照[思考 7.8.1](ch07.md#think-7.8.1)。

:::

## C 组 · 实操（16–20）

实验包在 `bench/`。这组题要求真的动手：跑出批次、保存产物、把结论写成可复核的句子。不要覆盖仓库保存的 `local` 结果。

::: ex C16 · 跑出四线程表并交代分母（主线 ②） {#ex-7.C.16}

按 7.5.2 的命令构建并运行共享计数实验（1 线程与 4 线程各一次，每线程 500000 次、保留 21 个样本）。提交一张表，并在表下写清 N、I、分母与计时区间。

::: hint 提示

计时从哪个屏障返回开始，到哪个屏障结束？线程 join 在不在计时区间里？

:::

::: sol 参考路径

命令是 `cargo build --offline --release --manifest-path bench/Cargo.toml`，再跑 `bench/target/release/atomic-contention 1 500000 21` 与 `... 4 500000 21`。表下必须交代：N 是线程数，I 是每线程操作数，分母是 N × I（四线程每批 2000000 次逻辑递增），单位是 ns/聚合操作；计时覆盖 start barrier、全部循环与 done barrier，线程创建与 join 不在主计时区间。你的绝对值不必与书中相同（本机为 Apple M5 Pro、18 逻辑 CPU、128 字节缓存行、未设亲和性），但必须能解释差异来自哪里。对照 7.5.4 与 7.5.5。

:::

:::

::: ex C17 · 保存并核对原子指令（主线 ①） {#ex-7.C.17}

用 7.4.2 与 7.4.3 的三条命令生成产物，在保存的汇编里找出 `movq`、`ldapr`、`ldadd`，并写一句这条证据能支持、一句不能支持的判断。

::: sol 参考路径

本机命令：`rustc --edition=2021 --crate-type=lib -C opt-level=3 --emit=asm,llvm-ir bench/probes/atomics.rs --out-dir bench/results/local`；交叉命令把 `--target` 换成 `x86_64-unknown-linux-gnu` 与 `aarch64-linux-android`，分别输出到 `bench/results/x86_64-linux` 与 `bench/results/aarch64-android`。能支持：「这个 rustc 版本、这个 target 上，Acquire load 生成了 `ldapr`」。不能支持：「源码只要写 Acquire 就一定更快/更慢」，或把交叉产物叫目标机运行数据。四条核对：版本（`rustc -Vv`）、来源（本机还是交叉）、跨度（指令形态还是运行期成本）、方向（解释源码还是倒推语义）。对照 7.4.2–7.4.3 与 7.4 的判定流程。

:::

::: ex C18 · 复现 publication 反例并修好它（主线 ①） {#ex-7.C.18}

运行 `bench/examples/publication.rs`，记录输出；然后只改一处，让 `payload` 在 Release 之前就绪，重跑并解释为什么这个修复不需要更换同步原语。

::: hint 提示

先看生产者那段伪代码的语句顺序：哪一条写在 Release 后面？

:::

::: sol 参考路径

命令：`cargo run --offline --release --manifest-path bench/Cargo.toml --example publication`。本轮输出是 `ready=true payload=0: wrong program order, not a hardware-reordering test`。原因是 `payload.store(42, Relaxed)` 排在 `ready.store(true, Release)` 之后，Release 不发布尚未执行的未来写入。把载荷准备挪到 Release 之前即可；若载荷换成非原子的普通类型，还要检查是否有相应互斥与生命周期保证，不能把它改成普通引用数据竞争再叫「合法结果」。对照 7.7.2 与[例 7.7.1](ch07.md#ex-7.7.1)。

:::

::: ex C19 · 用非 Copy 载荷抓重复析构（主线 ①） {#ex-7.C.19}

用 `String` 在两线程间传 2000 条消息，再用一个记录析构次数的 `Tracked` 对象分别验证「已接收」与「未接收」两条路径。写出你要断言的不变量，并说明这套测试不能覆盖什么。

::: sol 参考路径

不变量：已接收消息由接收者拥有，不在 Slot 中再次析构；未接收消息在 Slot 销毁时恰好析构一次；空读不读取未初始化值；满写把未发送的 value 原样还给调用者。只断言总和正确不够，必须分别数两种路径的析构次数——仅用 `u64` 测试会掩盖重复析构问题。不能覆盖：强制每一种硬件执行次序、线程异常退出后的进度。跨线程 `String` 测试能暴露明显的重复、乱序或丢失。对照 7.6.5 与 7.8.7 的测试矩阵。

:::

:::

::: ex C20 · 把「锁瓶颈」改写成合格的句子（主线 ④） {#ex-7.C.20}

同事根据一份 profiler 报告写：「主线程 826 次落在等待路径，可见原子算法已被 Mutex 串行化，锁是瓶颈。」用三段式改写这句话：保留观察、去掉越界、补上下一步采集计划。

::: sol 解答

示例：「本次 `sample` 每毫秒抓取线程栈，主线程有 826 次观察落在等待路径；这是栈观察计数，不是时间占比或缓存失效数，主线程在 barrier 等待中本就应被采样。要判断争用来源，需在目标机按事件清单逐模式采集 cycles 与 cache-misses，并写清事件名、计数区间与平台。」三段分别是：可核对的观察、证据类型的边界、补证据的动作。对照[定义 7.7.1](ch07.md#def-7.7.1)、7.7.4 与 7.7.5。

## 批改最常给的三条意见

1. **单位与对象错位**：把 0.418 与 0.070 说成一次原子访问的延迟，把批次 p99 说成单条消息的尾延迟。先改句子，再改表格——它们是吞吐倒数与批均值分布。
2. **结论超出证据**：把约 27 倍写成「标准库算法慢 27 倍」，把 826 次观察换算成锁的 CPU 占比，把汇编相同写成「三种序等价」。给每个结论补上「在这台机器、这个 target、这组负载、这个接口」。
3. **证明缺方向**：只证 `true` 方向的发布边，不证 `false` 方向的复用边；或者只写「字段是原子的」就宣布义务清单成立。用[定义 7.3.4](ch07.md#def-7.3.4) 的八条与[定义 7.2.2](ch07.md#def-7.2.2) 的观察关系逐条对到代码。
