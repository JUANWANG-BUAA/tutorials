# 阅读指南

这本书是给已经会写 Rust、但还没有一套稳定性能方法的工程师看的。它不替代语言教程，也不假装所有机器都长成作者这台 Mac。下面说明怎么读、怎么跑、怎么理解书里的数字。

## 这本书假设你已经会什么

- Rust 的基本语法、所有权、借用、`trait`、`Result` 和 `cargo`；
- 操作系统的基本概念：线程、进程、虚拟内存、系统调用；
- 一点统计常识：均值、标准差、分位数、置信区间。

如果其中一项还很陌生，先补那一项。如果你对「延迟、吞吐、尾延迟、资源占用」这些性能指标还没有把握，先读[导论](introduction.md)；它用几个真实场景把这些词分开。第 1 章会用到 DCE、`black_box` 和 bootstrap；第 7 章会用到 happens-before；第 9 章会用到 Tokio 的任务状态字。前置知识不到位，读起来会很痛苦，而且不是你的问题。

## 三种读法

不知道从哪开始的，先做两件事：花 15 分钟做[入学诊断自测](entry-test.md)，再用[全书知识地图](preface-map.md)确认十七章的依赖顺序；诊断里露出来的缺口，去[先修工具箱](prerequisite.md)取对应那一格。

**只学过 Rust 基础语法、没学过计算机底层**：直接走[第 0 章 · 零基础起步](onboarding.md)里的 12 周慢速路线。它把每章「在讲什么」用一句不带术语的话说清，并标出第一遍可以跳过的小节；看不懂的硬件词，去那里六个词的最小解释。

### 通读：先走一遍主干

按 `1 → 2 → 3 → 4 → 7 → 8 → 9 → 13 → 14 → 15/16 → 17` 读，最后停在第 17 章做大项目。这条路径覆盖「测量—对象—所有权—编译器—并发—异步—执行器—profiling—门禁—项目」，先把性能工程的主干走通。第 5、6、10、11、12 章可以第二遍再读，它们分别深入泛型、LLVM、进程、无锁和 SIMD。这条链的顺序就是[四步主线](mainline.md#mainline-spine)的顺序：先能怀疑数字，再看对象与编译器，再进并发，最后用门禁把结论守住。

### 查阅：只想知道一个词或一个命令

直接看[符号表](preface-notation.md)、[术语表](appendix/glossary.md)和[速查卡](appendix/cheatsheet.md)；要找「这类题的固定流程」，去[解题工具箱](toolbox.md)，要动手设计一次测量，先照[实验设计骨架](lab-workshop.md)填五行草稿。术语表按主题分组，每条给出一句话定义和正文入口；速查卡把内存序选择、布局属性、测量检查、profiling 命令、FFI 清单压成表。

## 动手之前

### 工具链

书里的数字固定使用 rustc 1.99.0、LLVM 23.1.1 和 Tokio 1.54.0。你不必装同一个版本；先装 stable，能编译就先跑起来。版本不同会导致三个东西变化：LLVM 的优化、标准库的实现、Tokio 的内部状态字。遇到结果对不上，先记录你的 `rustc -Vv`，再对比书里的环境。

### 仓库结构

所有路径都相对于仓库的 `cpp-rust/` 目录：

```text
cpp-rust/
├── src/                 # 书稿
├── bench/               # 6 个实验包
│   ├── foundations-lab/ # 第 1–3 章
│   ├── compiler-lab/    # 第 4–6 章
│   ├── runtime-lab/     # 第 9–10 章
│   ├── systems-lab/     # 第 11–12 章
│   └── evidence-lab/    # 第 13–14 章
├── projects/            # 第 15–17 章
└── sources/             # 来源台账和原始记录
```

### 跑一个实验

以第 1 章为例，从 `cpp-rust/` 目录执行：

```bash
cargo test --offline --locked --manifest-path bench/foundations-lab/Cargo.toml
bash bench/foundations-lab/run.sh results/my-new-run
```

`run.sh` 会先构建，再取得共享测量锁，然后按「预热—正式批次—CSV」的流程跑。最后一个参数是新目录名，目录必须尚不存在；脚本不会覆盖旧结果。

### 没有网络怎么办

实验包只依赖标准库或已经锁定的 `Cargo.lock`。`--offline --locked` 会在本地缓存缺失时直接失败，而不是悄悄换一个版本。这比「能跑但版本不对」更容易排查。

## 数字怎么读

### 先看单位

书里常见的单位有三种：

- `ns/元素`：批均值除以处理的元素数；
- `ns/调用`：批均值除以调用次数；
- `ns/批次`：一个批次的墙钟时间，不再归一化。

同一个数字，分母不同，含义完全不同。看到 `0.06 ns`，先问它是每个元素、每次调用，还是每个批次。

### 批均值不是请求延迟

批均值回答「在固定输入和固定批次下，平均每个单位要多久」。它不回答「单个请求的 p99 是多少」。要回答后者，必须保存请求级观测，记录到达、开始服务和完成时间；批次总时长会把长尾平均掉。

### p50 和 p99

p50 是中位数，p99 是第 99 百分位。书里的 p50/p99 如果标了「批」，指的是 21 个批均值的分位数，不是请求的分位数。N=21 时，nearest-rank 的 p99 就是最大值，分辨率很粗；不要把 21 个批次的 p99 当成生产 SLA。

### 标准差和置信区间

书里的标准差使用 N−1 分母。bootstrap 区间是对原始批次做有放回重采样得到的，它描述「当前运行内」的不确定性，不包含编译器版本、机器差异和跨时段漂移。区间跨零，只能说当前证据不足以确定方向，不能说两者严格等速。

### 「本机」和「机制」

书里的数字分两类：

- **本机观测**：在作者这台 Apple M5 Pro、macOS、rustc 1.99.0 上测到的值。换机器、换版本，数值会变。
- **机制结论**：比如「Release 之前的写入对 Acquire 之后的读取可见」「`black_box` 不提供同步语义」。这类结论不依赖具体机器，但仍然依赖你正确使用同步原语。

正文会尽量标明哪些是数字、哪些是机制。你引用时也请保留这个区分。

### 看到「太快」的数字，先查 DCE

如果一个结果比理论下限还快，优先检查三件事：工作真的执行了吗？输出被观察了吗？分母是不是名义元素？第 1 章的 `dce_empty` 就是一个真实的反例：输入已经过 `black_box`，求和仍然被删掉，因为结果没人用。

## 你的机器不一样怎么办

### Linux / x86

书里的实验主要在一台 ARM64 Mac 上跑。Linux/x86 的缓存行、原子指令、调度器和 `perf` 都不同。你可以重新跑同样的实验包，但不要直接把书里的纳秒数搬到你的机器上。跨平台比较应该看方向和量级，而不是小数末位。

### 没有 `perf` 或 `sample`

第 13 章同时讨论 macOS 的 `sample` 和 Linux 的 `perf`。如果你的平台只有其中一个，就读对应的小节；不要用 `sample` 的栈计数去推算 cache miss，也不要用 `perf` 的 PMU 数据去替代调用栈归因。

### Tokio 版本不同

第 9 章分析 Tokio 1.54.0 的任务状态字。Tokio 的内部状态机不是稳定 ABI，版本一变，字段和转换就可能变。读这一章时，先确认你的 `Cargo.lock` 里的 Tokio 版本；版本不同，应该把这一章当「怎么读源码」的示例，而不是逐位对照表。

### 结果对不上

先按这个顺序排查：工具链版本、目标三元组、`RUSTFLAGS`、release 配置、CPU 频率/后台负载、输入规模和批次大小。把六项都记录下来，再讨论差异。只写「我这边跑不出来」，无法定位。

## 符号与约定

全书记号集中在[符号表](preface-notation.md)：`T`、`K`、`N`、批均值、配对差值 `d`、区间 `[L, U]`、预算 `B`，以及项目章的 `Q`、`C`、`R`，每条都给了读法、首次出现的小节和最容易被混成的东西。这里只留两条单位约定：**`ns/元素` 是批均值除以元素数，`ns/调用` 是批均值除以调用次数**，两者都是摊薄口径，不是单次请求延迟；正文每张表都会写明分母是什么。

## 常见问题

**为什么不讲 Rust 基础语法？**  
因为这本书的定位是进阶手册，不是语言教程。基础语法请读[《Rust 程序设计语言》中文版](https://rustwiki.org/zh-CN/book/)。书里只在性能相关的地方解释语言机制，比如 move 的机器码、`Pin` 的内存约束、`Drop` 的展开路径。

**为什么所有数字都来自一台 Mac？**  
因为作者只在这台机器上采集了完整证据。书里没有把别的平台的「典型值」补进来，也没有用交叉生成的汇编冒充目标机运行。你可以把实验包搬到自己的机器上重跑，方法不变。

**为什么有些代码不能直接编译？**  
正文里的代码块有三种：`rust` 是可以编译的完整入口或片段；`text` 是伪代码或格式示意；`asm` 是编译器实际生成的汇编。遇到 `text` 块，不要直接复制进 `main.rs`；遇到 `asm` 块，先确认它对应哪个源文件和目标。

**为什么没有 Linux `perf` 的 cache miss 数字？**  
因为作者没有在 Linux 上采集这些事件。书里只报告采集到的指标；没有采集的 IPC、cache miss、能耗和频率不会出现在结论里。第 13 章会说明哪些工具能回答哪些问题，以及它们的边界。

**我可以直接引用书里的加速比吗？**  
可以引用，但要带上条件：哪台机器、哪个版本、哪种输入、哪个单位。只写「某某优化快了 7.7 倍」，会把一个局部实验变成一句广告。书里的每个数字都对应实验包里的原始 CSV；引用时最好把路径一起给出。
