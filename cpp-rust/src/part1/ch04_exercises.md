# 第四章 · 习题集

共 19 题，分三组。**A 组概念**检验你能否说出名词指的是什么；**B 组推理**检验你能否从数据或 MIR 片段推出结论；**C 组实操**要求你真的跑命令、在产物里找证据、写结论。全部题目附解答，难题另附提示层。

用法约定：先写下自己的答案，再展开核对。看解答时只看第一行就停住，问自己「接下来那一步是不是我要走的」，再往下读。实验包在 `bench/compiler-lab/`，正式归档在 `bench/compiler-lab/results/stable-02/`，补充归档在 `results/extra-02/`。

### 按主线四步分组

| 步 | 这一章练这一步的题 | 这一步在本章的具体形态 |

## A 组 · 概念（1–8）

::: ex A1 · 三层各管什么（主线 ①） {#ex-4.A.1}

「分层证据」的三层分别是什么？各写一句「它只支持什么判断」。为什么「语言要求移动」和「机器上多了一次 memcpy」不能互相顶替？

::: sol 解答

语言允许的行为：只规定义务——谁可用、谁负责释放，不规定机器动作。固定版本编译器采用的表示：记录这一版用什么结构表达该程序（HIR、THIR、MIR）。固定目标机器执行的程序：记录这次构建真正留下了哪些调用与内存操作（LLVM IR、汇编、实际运行的代码）。前一层约束后一层，但不唯一决定后一层，所以第三层看不到搬运，否定的只是物理搬运；第一层的责任转移与第二层的 `move` 仍然成立。对照[定义 4.1.1](ch04.md#def-4.1.1) 与[例 4.1.1](ch04.md#ex-4.1.1)。

:::

:::

::: ex A2 · 依赖图与时间日志（主线 ④） {#ex-4.A.2}

表示关系图允许哪两件事同时成立？「图里有一个箭头」能推出什么、不能推出什么？本章有没有采集过时间日志？

::: sol 解答

它表达「哪个表示需要哪个前置事实」：允许两个函数体停在不同阶段，也允许一份产物在被需要时才第一次构造（某个常量被需求时可能首次触发其 MIR 构造）。一个箭头只说明这项计算需要那个前置事实，推不出整个 crate 已完成前一阶段。本章没有采集按时间排好、可逐条复现的执行记录。对照[定义 4.1.2](ch04.md#def-4.1.2)。

:::

:::

::: ex A3 · 本机观察（主线 ④） {#ex-4.A.3}

什么算一条「本机观察」？它的适用范围由什么划定？把本章记录的工具链事实复述一遍，并说明它凭什么不是承诺。

::: sol 解答

只在这台机器、这个版本、这套选项下成立的事实；适用范围由第 1 章的外部条件集合划定——换工具链提交、换目标三元组、换构建选项都算换了一个观察对象。本轮稳定版是 Rust 1.99.0，提交 `b940084d7eb6a299eb4bfeb8e34901bc051e7ac4`，LLVM 23.1.1，宿主与执行目标均为 `aarch64-apple-darwin`，机器 Apple M5 Pro、系统 macOS 27.0.1，系统报告的 cache line 为 128 字节；没有设置 `target-cpu=native`，没有绑核，没有锁频，也没有隔离桌面后台负载。原始输出保存在 `environment.txt`，所以这些数只能作为观察，不能当服务等级协议。对照[定义 4.1.3](ch04.md#def-4.1.3)、[4.1.5](ch04.md#sec-cpp-rust.1.4.1)。

:::

::: ex A4 · THIR 为什么省不掉（主线 ①） {#ex-4.A.4}

THIR 显式化哪四类动作？body 指什么范围？为什么不能把它想成 HIR 全树的常驻副本？

::: sol 解答

自动引用、自动解引用、方法调用与重载运算符选到的具体目标、销毁作用域。body 指「需要求值的代码」：函数体与 `const` 初始化器；结构体声明本身不是 body。它按需构造、及时释放，这本身属于编译器内存成本设计，与依赖图的「被需要时才构造」是同一件事的两面。对照[定义 4.2.3](ch04.md#def-4.2.3)。

:::

:::

::: ex A5 · Place、投影与 move path（主线 ①） {#ex-4.A.5}

`a.0`、`*p`、`v[3]` 和整个 local 是什么关系？move path 的父子规则怎么说？哪两个方向是错的：移出父路径、只移出一个子字段？

::: sol 解答

Place 是可访问位置，后面这些是带投影的 Place；初始化和借用按 Place 记账，不按变量名。move path 为「可被跟踪移动的位置」建索引，`a.b.c` 由父路径 `a.b` 派生：移出父路径会影响所有后代的初始化状态；只移出一个子字段不应取消无关兄弟字段的责任。另有限制——不能从普通共享引用后面移出拥有所有权的 `String`，也不能把任意数组下标位置当作安全的空洞。对照[定义 4.3.2](ch04.md#def-4.3.2)、[定义 4.3.3](ch04.md#def-4.3.3)。

:::

:::

::: ex A6 · 两个集合管两件不同的事（主线 ①） {#ex-4.A.6}

「必定初始化」与「可能未初始化」各自在合流点上怎么合？各决定哪件事？为什么这套记法不构成 rustc 的内部 API？

::: sol 解答

必定初始化要求到达该点的所有前驱都成立，一条缺失就够推翻它，因此它决定能否无条件读取。可能未初始化只要一条到达路径成立就成立，因此它决定析构责任是否需要保留——这就是条件析构的来源。它是本章阅读产物的记法，不是 rustc 内部类型的名字，也不构成跨版本 API。对照[定义 4.3.4](ch04.md#def-4.3.4)。

:::

:::

::: ex A7 · 构建期的三个家（主线 ②） {#ex-4.A.7}

查询的四件套是什么？会话内记忆化、增量编译、Cargo 最新状态判断三者的命中条件各是什么？为什么三条都不能当「查询引擎很快」的证据？

::: sol 解答

四件套是名字（问哪类事实）、键（问哪个定义）、结果（被算出来的东西）、provider（计算它的代码）。会话内记忆化在同一次编译进程内有效，进程结束就消失；增量编译要先把之前记录的输入与依赖判为仍有效才复用，磁盘上有目录不等于可命中；Cargo 判定整个单元最新时连 rustc 都不启动，那种 no-op 构建时间根本测不到编译器内部。本轮没有采集增量编译的定量加速表。对照[定义 4.7.1](ch04.md#def-4.7.1)、[定义 4.7.3](ch04.md#def-4.7.3)、[例 4.7.1](ch04.md#ex-4.7.1)。

:::

:::

::: ex A8 · 三种证据各自回答什么（主线 ①） {#ex-4.A.8}

「产物核验」要求在产物里确认哪些操作、核验对象是什么？静态产物与采样各回答哪个问题？它们是不是批计时？

::: sol 解答

产物核验要在编译器实际生成的文件里，按目标业务函数逐项确认分配调用、复制调用、释放调用、归约指令是否留存；核验对象是归档中的完整符号与其周边控制流，不是网页上的相似片段。静态产物（LLVM IR、汇编）说明一次给定构建留下了什么工作；采样（macOS `sample`）说明另一次运行在哪些调用栈上被采到。两者都不是批计时意义上的时间测量，也互不替代。对照[定义 4.5.2](ch04.md#def-4.5.2)、[定义 4.8.2](ch04.md#def-4.8.2)。

:::

## B 组 · 推理（9–14）

::: ex B9 · 三个返回同一个数字的签名（主线 ①） {#ex-4.B.9}

`&Vec<u64>`、消费 `Vec<u64>`、函数内 `to_vec()` 后求长度——三种写法返回同一个整数。有人说「返回值一致，所以实现相同」。请按三层分别推出每种写法改变了什么，并指出只比较最终整数为什么是不充分的语义检查。

::: sol 解答

① 调用者保留所有权，函数只观察；表示层接收者前有一次自动借用；机器层读一次长度字段。② 所有权责任转给函数，调用者之后不可再用这个名字；表示层出现一次移动；机器层没有理由逐元素复制缓冲。③ 调用者数据仍有效，函数另得一份副本；表示层多一次分配与复制的责任；机器层真的可能留下分配调用与复制操作。期望值相同不代表工作是同一件事。对照[例 4.2.2](ch04.md#ex-4.2.2)、[例 4.1.1](ch04.md#ex-4.1.1)。

:::

:::

::: ex B10 · 合流点上记哪一个（主线 ①） {#ex-4.B.10}

本轮实际编译的输入 `fn main() { let value: u64; if std::hint::black_box(true) { value = 7; } println!("{value}"); }` 被拒绝。有人主张：`black_box(true)` 的值就是 `true`，路径唯一，编译器应当放行。请推出合流点上 `value` 属于哪个集合，并说明拒绝为什么仍然正确。

::: hint 提示

被检查的是「这一次执行走了哪条边」，还是「这个程序允许哪些控制流」？

:::

::: sol 解答

有一条允许的路径（条件为假）没有给 `value` 赋值，所以它不属于「必定初始化」，属于「可能未初始化」；无条件读取要求前者，因此被拒绝，诊断码是 E0381。`black_box` 让条件在优化器眼里不透明，但更重要的是检查对象是该程序允许的控制流，不是某一次执行恰好走了哪条边——这与「优化器能看见删除」用的是同一套静态推理，只是方向相反。对照[例 4.3.2](ch04.md#ex-4.3.2)、[4.3.5](ch04.md#sec-cpp-rust.1.4.3)。

:::

:::

::: ex B11 · 从 `bb6` 读出责任（主线 ①） {#ex-4.B.11}

正式归档那份 `conditional_drop` 的 MIR 里，`bb6 (cleanup)` 写的是 `switchInt(copy _8) -> [0: bb4, otherwise: bb5]`，`bb4` 是 `resume`，`bb5` 是 `drop(_3)`。请推出：① 这条检查防的是什么事故？② `_8` 在哪个基本块被置为 false，之前发生了什么？③ 能否据此断言发布版机器码永久保留一个布尔槽？

::: sol 解答

① 防的是「已经移走的值被第二次销毁」：`bb1` 的非零分支先 `_8 = const false`，再 `_5 = move _3` 与 `drop(_5)`，此后展开进入 `bb6` 时读到 0 就直接 `resume`，不再 `drop(_3)`。② 置 false 发生在 `bb1`。③ 不能。MIR 属于第二层，记录责任如何被判定；已知状态无需动态 flag，始终共同变化的路径可共享状态，后续优化还可能消除或改写它——要谈第三层得看 LLVM IR 与汇编的实际留存。对照[例 4.4.3](ch04.md#ex-4.4.3)、[例 4.4.2](ch04.md#ex-4.4.2)。

:::

:::

::: ex B12 · 0.143648 与 3.43（主线 ②） {#ex-4.B.12}

[4.5 节](ch04.md#sec-cpp-rust.1.4.5)的表给出 borrow 均值 0.059091、sd 0.001233、批 p50 0.058640、批 p99 0.063338，clone 均值 0.202739、sd 0.006949、批 p50 0.201627、批 p99 0.225702，单位 ns/输入元素。有人写：「借用检查为每次调用省下 0.143648 ns/元素，比值 3.43 说明拥有者设计普遍比借用设计慢 3.43 倍。」列出全部错误并给一个站得住的表述。

::: sol 解答

三处。① 归因错：borrowck 是编译期分析，不在进程运行时循环中执行，真正不同的是程序请求的工作。② 口径错：0.143648 是两个批均值相减，本轮没有计算配对区间，只能说方向与量级；两个 sd 说明批次间有波动。③ 外推错：比值只在 16384 个 `u64`、本机这一版产物、这套夹具下成立，换尺寸后分配固定开销的占比会变，而且两个分支做的不是同一件事。站得住的表述：在本机、本输入长度、本构建配置下，克隆分支的批均值比借用分支高约 0.14 ns/元素，方向与产物中保留的分配、复制与释放一致。对照[例 4.5.2](ch04.md#ex-4.5.2)、[4.5.6](ch04.md#sec-cpp-rust.1.4.5)。

:::

:::

::: ex B13 · 0.216 与两倍的 sd（主线 ③） {#ex-4.B.13}

[4.6 节](ch04.md#sec-cpp-rust.1.4.6)的表给出 implicit 均值 2.372296、sd 0.098044、批 p50 2.354229、批 p99 2.757235，option 均值 2.587951、sd 0.246970、批 p50 2.669365、批 p99 2.980856，单位 ns/逻辑调用。判断三件事：① 能否写「Option 每次调用多花 0.216 ns」？② 「波动更大」这条信息能用来做什么？③ 要得到区间本轮还缺什么？

::: hint 提示

先问 0.216 是怎么算出来的：同一轮里的差值，还是两列各自平均之后再相减？

:::

::: sol 解答

① 不能。0.216 是两个批均值相减，不是同一轮内的配对差值，也没有区间支撑；只能说本轮 Option 写法平均更高。② sd 更大说明 21 批之间更不稳定，它削弱方向的可靠性，但本身不是机制证据——它提示这条差异的置信度低于 4.5 节那条。③ 缺按轮配对后的差值样本与重采样计算；归档保留了每个 case 的 21 个原始批次行，但第 1 章的区间算法本轮没有执行，所以不报区间。对照[例 4.6.3](ch04.md#ex-4.6.3)、[定义 4.8.1](ch04.md#def-4.8.1)。

:::

:::

::: ex B14 · 8192 与 count=2（主线 ①） {#ex-4.B.14}

`drop_paths` 两个 case 的 `expected` 都是 8192；展开测试 `panic_unwinds_initialized_guards` 最后断言 `assert_eq!(count.get(), 2)`。推理两件事：① 若某次运行两个 case 都返回 4096，两张计时表还能读吗？② 这条断言检查的是哪两件事，它没有证明什么？

::: sol 解答

① 不能。4096 说明有一条路径上的守卫没被销毁，析构责任被漏记；此时两张表比较的是两个做了不同工作的程序，数字再漂亮也不能读成「状态表达的成本」。8192 = 4096 × 2 来自规格（每次逻辑调用构造两个守卫、各加一次计数），与走哪条分支无关，所以它是「资源总量没变」的证明。② 断言检查的是：`pair.0` 已移走、展开时不能第二次销毁它；`pair.1` 仍要负责。它没有在 `Drop` 内再次 panic，因此不证明所有析构函数都可失败恢复。对照[例 4.6.1](ch04.md#ex-4.6.1)、[4.6.6](ch04.md#sec-cpp-rust.1.4.6)。

:::

## C 组 · 实操（15–19）

这组题要求真的动手：跑正文给出的命令、在归档产物里找出某条证据、把结论写成可复核的句子。正文只给了 `--emit=mir`、`--emit=llvm-ir`、`--emit=asm` 三个观察入口和 [4.8.6](ch04.md#sec-cpp-rust.1.4.8) 那五条复现命令，所以取产物就从那里开始。

::: ex C15 · 在 `.mir` 里核对条件析构（主线 ①） {#ex-4.C.15}

执行 `bash bench/compiler-lab/run.sh bench/compiler-lab/results/my-stable-run`（新目录必须不存在，脚本不覆盖既有归档）。打开新归档 `codegen/` 里那份 `.mir`——正式归档对应的文件是 `compiler_lab-55987aab45b3e67f.mir`——核对四件事并写下你看到的原文：`debug first` 对应哪个 local、`_8 = const false` 出现在哪个基本块、`bb6 (cleanup)` 的两条分支目标、`bb3 (cleanup)` 末尾那条边。

::: hint 提示

先按 `debug` 行对上源码名字，再找所有 `drop(...)` 与 `StorageDead(...)`；编号只对本轮文件有效，别背它。

:::

::: sol 参考路径

对应[4.4.5](ch04.md#sec-cpp-rust.1.4.4)的原文：`debug first => _3`（`_4` 是 `second`）；`_8 = const false` 在 `bb1`，同块里随后是 `_5 = move _3` 与 `drop(_5) -> [return: bb7, unwind: bb3]`；`bb6 (cleanup)` 为 `switchInt(copy _8) -> [0: bb4, otherwise: bb5]`，`bb4` 是 `resume`、`bb5` 是 `drop(_3)`；`bb3 (cleanup)` 末尾是 `unwind terminate(cleanup)`。按[定义 4.4.3](ch04.md#def-4.4.3)说清哪些是正常边、哪些是展开边。若你换版本后编号变了，结论范围要跟着改。

:::

:::

::: ex C16 · 在同目录找分配与复制（主线 ①） {#ex-4.C.16}

同一个 `codegen/` 目录里另有 `.ll` 与 `.s`。按[定义 4.5.2](ch04.md#def-4.5.2) 核对 `cloned_sum` 是否保留三类操作，并到 `.s` 里找复制的真实调用。然后回答：你搜到的向量加法属于哪个符号？为什么「搜到几条 add」不等于核验完成？

::: sol 参考路径

正文给出的核对结果是：`cloned_sum` 的 LLVM IR 保留 allocator 调用，随后有 `llvm.memcpy`，计算之后保留 deallocator 调用；本机目标码中可见 `_memcpy` 的真实调用。`borrowed_sum` 里出现向量加法归约，它没有按源码 iterator 层级逐层函数调用。要确认指令属于目标业务函数的完整范围与周边控制流，因为一份 `.s` 里同时有标准库其它例程的指令；看到的向量化也只是本机这一版的产物，不构成该接口跨版本的承诺。对照[4.5.5](ch04.md#sec-cpp-rust.1.4.5)、[思考 4.5.1](ch04.md#think-4.5.1)。

::: ex C17 · O0 与 O3 的差异说到哪一步（主线 ④） {#ex-4.C.17}

`results/extra-02/` 下保留 `stages-o0.mir` 与 `stages-o3.mir`，同目录还有两种优化等级的 LLVM IR 与汇编。对照两份 `.mir`，写出本轮证据允许的表述；再说明这两个探针为什么没有进性能表。

::: hint 提示

两份文件都是「最终」表示，中间没有逐 pass 转储——这决定了你的句子能走多远。

::: sol 参考路径

允许的写法是：「在 opt-level 3 的最终 MIR 里看不到该节点，在 opt-level 0 的最终 MIR 里还能看到；本轮未确定它是哪个转换删的。」不能从最终差异逆向编造一次没有记录的 pass 执行顺序。这两个入口实际运行了 `count=2` 的断言，是分析探针而不是正式计时入口，所以正文没有把 opt-level 0 的运行时间放进性能表。对照[4.7.6](ch04.md#sec-cpp-rust.1.4.7)、[例 4.7.2](ch04.md#ex-4.7.2)。

::: ex C18 · 拒绝输入与失败记录（主线 ④） {#ex-4.C.18}

::: ex C19 · 复现一遍并核对夹具契约（主线 ④） {#ex-4.C.19}

按 [4.8.6](ch04.md#sec-cpp-rust.1.4.8) 的五条命令从 `cpp-rust/` 依次跑一遍：格式检查、clippy、测试、正式脚本、补充脚本。核对 `src/lib.rs` 里那份共用的 `measure`：预热时长、批次目标时长、正式批数、每批校验位置、CSV 头部的七个字段名。最后用一句带限定条件的话交付「clone 分支更贵」这个结论，并说明改过被测内核后旧归档还能不能引用。

::: sol 参考路径

四个数字：每个 case 至少单独预热 500ms；按预热速度选择约 10ms 的批次重复数；正式采样每 case 21 批；校验在每批计时结束后比较聚合 checksum 与「期望值 × 重复数」，预热阶段就已逐次断言返回值。CSV 头部为 `case,round,repeats,units,elapsed_ns,ns_per_unit,checksum`。六条命令共用这一份 `measure`，但各表的 units 不同（元素数、逻辑调用数），所以六张表不能直接横向排名。结论句示例：「在本机 Rust 1.99.0、`aarch64-apple-darwin`、固定一个 CGU 且 `lto=false` 的 release 构建、16384 个 `u64` 的热输入下，clone 分支的批均值 0.202739 ns/元素高于借用分支的 0.059091，方向与产物中保留的分配、复制与释放一致；本结论不覆盖其他输入长度、跨线程共享与请求级尾延迟。」改过内核或夹具后，旧归档只对应旧二进制，结论要重新采集。对照[定义 4.8.1](ch04.md#def-4.8.1)、[4.8.1](ch04.md#sec-cpp-rust.1.4.8)。

## 批改最常给的三条意见

1. **层与层互相顶替**：拿汇编里没有复制否认移动责任，或从 MIR 的 local 个数推栈槽数量。先写清这个判断属于哪一层，再决定读哪份产物（[定义 4.1.1](ch04.md#def-4.1.1)）。
2. **结论超出产物**：把批均值差写成单调用成本、把「本轮观察到」写成「应当禁用 `Option`」。每条结论补上采集条件，并说明缺哪一类证据。
3. **不写证据缺口**：不提 nightly 不可用、没有逐 pass 转储、没有 self-profile、没有 PMU、没有跨尺寸分布。缺什么就写缺什么，比拿文档样例改个文件名更容易复核（[定义 4.1.3](ch04.md#def-4.1.3)）。
