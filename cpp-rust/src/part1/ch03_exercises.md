# 第三章 · 习题集

共 21 题，分三组。**A 组概念**检验你能否说出名词指的是什么、适用于哪一段；**B 组推理**检验你能否从表里的数字或一段代码推出结论；**C 组实操**要求你真的写代码、读代码、把证明写成可核对的条目。全部题目附解答，难题另附提示层。

用法约定：先写下自己的答案，再展开核对。看解答时只看第一行就停住，问自己「接下来那一步是不是我要走的」，再往下读。直接通读解答，得到的只是「看懂了」，不是「会做了」。

本章所有数字都来自正文的 native-01 归档与代码。凡是「假想约定」的预算都照正文标明，不是采集量。

## A 组 · 概念（1–8）

::: ex A1 · 移动要求什么，不要求什么（主线 ①） {#ex-3.A.1}

给出「所有者」与「移动」的定义，并说出正文从这个定义引出的三条推论各自禁止哪种说法。

::: sol 解答

所有者承担一个值的合法使用与最终清理责任；移动把这份责任转移给新位置，旧绑定随即失效，它本身不要求为每一步执行某段固定机器指令。推论一：不能从源码里数 `move` 推导内存带宽，被消除的搬运不产生任何指令。推论二：「移动通常便宜」解释不了所有类型，大数组的按值传递在某些调用边界仍可能实际搬运。另外，重复的拥有者才是 double free 的来源，而定义只允许一份责任。对照[定义 3.1.1](ch03.md#def-3.1.1)。
:::

:::

::: ex A2 · 三种都叫「复制」的操作（主线 ②） {#ex-3.A.2}

`Copy`、`Vec` 的 `clone`、`Arc` 的 `clone` 三者的成本对象分别是什么？为什么 `Copy` 不能与 `Drop` 同时要求？

::: sol 解答

`Copy` 是隐式复制的类型属性，成本在按位复制该值本身：值被使用一次后原绑定仍可用，它不调用用户定义的深克隆逻辑。`Vec` 的 clone 成本在载荷——分配、元素复制、随后一次释放。`Arc` 的 clone 成本在共享计数，与载荷大小无关，但带来计数的实际语义。`Copy` 要求相应字段满足约束且不能同时要求 `Drop`：隐式复制会产生重复的拥有者，而重复拥有者正是重复析构的来源。对照[定义 3.1.2](ch03.md#def-3.1.2)。
:::

:::

::: ex A3 · 「所有权免费」漏了什么（主线 ①） {#ex-3.A.3}

「编译期借用检查不在每次普通引用访问时维护运行时借用表」能不能写成「Rust 所有权没有成本」？举出正文里四类真实成本。

::: sol 解答

不能，那句话只说明检查发生在编译期。四类成本：`Drop` 会执行真实清理；`Rc` 与 `Arc` 维护计数；`RefCell` 在运行时维护借用状态；`Mutex` 需要同步协议。这些都是所选抽象的实际语义工作——编译器删掉的必须是没人做的工作，这里每一步都有人做。把它们概括成「Rust 所有权免费」会误导性能分析。对照[3.1.3](ch03.md#sec-cpp-rust.1.3.1)。
:::

:::

::: ex A4 · 时间轴上的借用（主线 ①） {#ex-3.A.4}

排他访问与共同读取按什么维度描述？重借用为什么会让「一条路径」的合法窗口变成两段？

::: sol 解答

按时间区间描述，不按指针变量的个数描述：排他访问是某段时间内只有这一条路径被允许写入这块存储，共同读取是多条路径可以同时读但都不写。重借用从已有引用派生出一段更短生命周期的引用，派生借用有效期间要遵守它的约束，于是同一地址在时间轴上被划成「原路径可用 / 派生路径可用 / 原路径恢复」若干阶段。指针的数值地址可能不变，允许的访问阶段却可能已受新借用限制，所以证明要写访问时间，不只写地址范围。对照[定义 3.2.1](ch03.md#def-3.2.1)、[定义 3.2.3](ch03.md#def-3.2.3)。
:::

:::

::: ex A5 · 三个不同的事实（主线 ②） {#ex-3.A.5}

容量、长度、「已经有合法的 `T`」三件事分别由谁决定？为什么「先全清零、之后再填」不能作为通用初始化方案？

::: sol 解答

容量由分配器决定（已经买下的存储元素数），长度由容器的承认决定（当前被承认存在合法 `T` 的元素数），合法值由类型 `T` 自身的取值规则决定。清零方案不通用，因为任意零字节未必构成合法 `T`：零不一定是合法引用，零不一定是合法 `NonZero` 值。本章的 `zero_fill` 只用于 `u64`，因为对 `u64` 而言零是有效值。对照[定义 3.3.1](ch03.md#def-3.3.1)、[例 3.3.2](ch03.md#ex-3.3.2)。
:::

:::

::: ex A6 · `MaybeUninit` 的角色（主线 ①） {#ex-3.A.6}

它表达什么、不使什么合法、不替你做什么？本章为什么没有用它？

::: sol 解答

它表达「一段保证合法、但不保证里面有 `T` 的存储」。它允许表示尚未初始化的存储，但不自动使内部 `T` 合法——只有完整写入有效 `T` 之后，才能按其契约取得 `T`。它也不会替你自动销毁已初始化的 `T`，复杂容器要另外记录初始化进度与清理责任。本章组件用 `Vec` 的长度就维护住了前缀，不需要它，所以没有为性能加入手工初始化代码。对照[定义 3.3.3](ch03.md#def-3.3.3)。
:::

:::

::: ex A7 · 部分移动与 `mem::take`（主线 ①） {#ex-3.A.7}

两者各自让旧位置处于什么状态？为什么「实现 `Drop` 的结构」不能照抄元组例子随意拆字段？

::: sol 解答

部分移动只把一个聚合值中的某个字段移走，旧位置的其余字段仍是合法值并仍有析构责任。`mem::take` 把旧值移出并在原位置放入 `Default` 值，使旧位置立刻回到合法状态（对 `Vec` 就是空 `Vec`）。对实现 `Drop` 的结构，直接移出字段有额外限制，因为析构函数通常需要看到完整有效的 `self`。另外 `Default` 状态在类型层面合法，不代表业务上允许为空——安全合法性与领域事务一致性仍要分开审查。对照[定义 3.4.3](ch03.md#def-3.4.3)。
:::

:::

::: ex A8 · 地址与来源（主线 ①） {#ex-3.A.8}

两者分别是什么？`addr`、`with_addr`、`map_addr` 各做什么、都不证明什么？

::: sol 解答

地址是指针的数值位置；来源是围绕这个数值的语义约束，表达允许访问的空间、时间和可变性范围。`addr` 提取地址部分，`with_addr` 保留原指针的来源并改变地址，`map_addr` 对地址做变换同时保留来源。三者都不自动证明新地址可解引用：边界、对齐、有效值与别名仍需逐项检查；新地址超出原分配时，保留来源也不会创造新的访问权限。对照[定义 3.7.2](ch03.md#def-3.7.2)、[3.7.3](ch03.md#sec-cpp-rust.1.3.7)。
:::

## B 组 · 推理（9–15）

::: ex B9 · 8 字节能解释 0.1 ns 吗（主线 ②） {#ex-3.B.9}

borrow 实验里 `&[u64]` 的描述符是 16 字节、`Vec` 的描述符是 24 字节。有人写：「借用版每次少搬 8 字节，所以省下 0.100168563 ns/元素。」这条推理链断在哪几步？

::: sol 解答

断在三处。① 描述符尺寸与载荷成本无关：`cloned` 多做的是一次独立元素存储的分配、524288 字节的复制和一次释放，元素区约是描述符的两万倍（524288 ÷ 24 ≈ 21845）。② 单位口径是「一次工作核调用摊到每个输入元素」，不是一次 `borrow` 语法操作的耗时，把 0.1 ns 拆给「搬句柄」这个动作本身就错读了分母。③ 本轮没有对分配、复制、释放逐项计时，也没有采集真实内存流量，所以连「省下 8 字节搬运」这种成分说法都没有证据。对照[例 3.1.1](ch03.md#ex-3.1.1)、[定义 3.5.1](ch03.md#def-3.5.1)、[3.5.6](ch03.md#sec-cpp-rust.1.3.5)。
:::

:::

::: ex B10 · 证据表的第四行（主线 ①） {#ex-3.B.10}

别名证据表里「入口断言 / 长度相等检查」这一行，可以下的结论与不可扩大为分别是什么？断言失败时的行为是什么？

::: sol 解答

可以下：不匹配长度会安全 panic。不可扩大为：任意输入都无分支。也就是说，长度相等这条前提在运行时被真实检查，检查失败就走 panic 路径；它不承诺调用总是无分支地进行。对照[例 3.2.2](ch03.md#ex-3.2.2) 上方的证据表与[定义 3.2.2](ch03.md#def-3.2.2)。
:::

::: ex B11 · 把注入点挪到下标 5（主线 ①） {#ex-3.B.11}

正文的两条回归是「下标 3 返回 `Err`，计数 3」和「下标 4 触发 panic，计数 4」，n 都是 8。现在把注入点改成「下标 5 返回 `Err`」，写出四个数：容量、退出时长度、已丢弃元素数，并说明下标 6 与 7 有没有被读取或析构。

::: hint 提示

前缀长度等于「成功构造并被 `push` 进去的个数」，注入下标之前每一次调用都成功。余量位置从来没有 `T`。
:::

::: sol 解答

容量 8（`with_capacity(8)` 一次买下）；退出时长度 5——下标 0 到 4 五次成功，每次 `push` 一个；已丢弃元素数 5，由局部 `Vec` 在早退离开作用域时清理；下标 5 返回 `Err` 后循环不再继续，下标 6、7 从未进入长度，也就从未被 `Drop` 或读取触及。这与正文的 3 和 4 是同一条规则的不同注入点：计数等于注入下标。对照[例 3.3.1](ch03.md#ex-3.3.1)、[例 3.4.2](ch03.md#ex-3.4.2)。
:::

::: ex B12 · 三行日志（主线 ①） {#ex-3.B.12}

用正文的计数对象思路构造两组：一组是三个局部变量，id 依次声明为 1、2、3；另一组是一个三元组的三个字段，id 依次声明为 1、2、3，整个元组被销毁。写出两串日志，说明各自依据哪条规则、能不能互换。

::: hint 提示

先判断这次退出销毁的容器是「块作用域」还是「字段集合」，再选规则。

:::

::: sol 解答

局部变量那组是 `[3, 2, 1]`：同一块作用域退出时按相反声明顺序析构，最后声明的 id 3 先走。字段那组是 `[1, 2, 3]`：结构体（含元组）字段按声明顺序析构。两条规则不可互换。正文在同一次测试里分别记录 `[2, 1]` 与 `[3, 4]`，正是为了防止把局部逆序误记成字段逆序。临时值另受具体表达式与 edition 规则影响，不在这两串里。对照[定义 3.4.2](ch03.md#def-3.4.2)、[例 3.4.1](ch03.md#ex-3.4.1)。

::: ex B13 · 两张表能不能排进同一列（主线 ②） {#ex-3.B.13}

3.5 的配对均值是 +0.100168563，3.6 的是 −0.952518123，两者区间都不跨零。有人把两行放进同一张「所有权写法快慢排名」表，按差值大小排序。这个操作错在哪两处？

::: sol 解答

第一处：差值来源不同。前者来自多做了一整份资源工作（分配、复制、释放），后者来自两个合法结构交给优化器的循环形状不同；它们与第 1、2 章的表一样，脱离各自的边界就不能横向比较。第二处：单位口径不同。前者是 ns/输入元素，后者是 ns/最终元素、包含构造、初始化、消费与销毁，两个分母不是同一个量。排序把它们当成同类数字，就已经把两本不同的账并成一列。对照[3.10 跨节错误第 1 条](ch03.md#sec-cpp-rust.1.3.10)、[定义 3.5.1](ch03.md#def-3.5.1)、[3.6.4](ch03.md#sec-cpp-rust.1.3.6)。
:::

::: ex B14 · sd 大是不是就更不稳定（主线 ③） {#ex-3.B.14}

3.6 里 `push` 的 N−1 标准差 0.019135814 大于 `zero_fill` 的 0.005930436。能否写「`push` 的波动更大」？两者各自的批 p99（1.194040060 与 0.218312025）是什么数？

::: sol 解答

绝对标准差不宜直接横比：两个 case 的均值相差约 5.73 倍（1.153849851 与 0.201331729），波动会随均值同量级缩放。比较稳定性要改用相对量并说明归一化方式——按本节数字各除以自己的均值，分别约为 1.7% 与 3.0%，相对波动反而是 `zero_fill` 略大，所以「绝对 sd 大就更不稳定」这句在这里连方向都是反的。两个 p99 都不是请求级分位数：21 个批均值上 `ceil(21 × 0.99) = 21`，这一列取的就是最大值，只描述批次之间的波动范围。对照 3.6.4 的表与[例 3.5.1](ch03.md#ex-3.5.1) 第 2 问。
:::

::: ex B15 · 一次扩容毁掉哪几行（主线 ①） {#ex-3.B.15}

把 `Vec` 的 `as_ptr()` 结果存进结构体字段，随后向原 `Vec` 再做一次 `push`（可能触发扩容），之后解引用字段里那个地址。按十维证明表指出被破坏的行，并说明「对齐」这一行为什么比创建引用时更弱。

::: sol 解答

被破坏的行至少三行。**时间**——存储可能随扩容或析构失效，地址相等不延长生命周期。**空间**——新元素的访问范围属于另一次分配，旧地址不在新分配的来源范围内。**初始化**——若原 `Vec` 扩容，前缀位置整体改变，旧地址指向的内容不再由原长度保证。对齐这一行变弱，是因为「切片由分配保证 align 8」是一次性的事实，保存成裸指针之后无法再证明此刻的绝对地址仍满足要求。这个场景最少要补的两条仍是「时间」与「别名」。对照[例 3.7.1](ch03.md#ex-3.7.1)、[思考 3.7.1](ch03.md#think-3.7.1)。
:::

## C 组 · 实操（16–21）

实验包在 `bench/foundations-lab/`。这组题是写代码与读代码：先写出会被拦下的版本、把证明写成条目，再按[出口检查](ch03.md#sec-cpp-rust.1.3.11)给出的命令验证。没有要求你重跑 benchmark，也没有要求你报新的实测值。

::: ex C16 · 写一段被借用检查拒绝的代码（主线 ①） {#ex-3.C.16}

写一段最短的 Rust，让它在编译期被借用检查拒绝（不是运行时 panic，也不是 `unsafe`），写明是哪条规则拦住了它，并给出两种安全修复。

::: hint 提示

让一个共享引用还活着的时候，对同一个容器做一次要写入的操作。扩容只是让后果更容易看懂，不是拒绝的理由。
:::

::: sol 参考路径

一种会编译失败的最小写法：

```rust
let mut v: Vec<u64> = vec![1, 2, 3];
let first: &u64 = &v[0];
v.push(4);
println!("{}", first);
```

拦住它的是[定义 3.2.1](ch03.md#def-3.2.1) 的排他一侧：`first` 代表的共享读取仍然有效时，`push` 需要这条路径之外的写入许可，同一阶段两种访问权限不能并存。两条常见修复。① 改变访问阶段：先把需要的值取出来（`let x = *first;`），或让 `first` 的作用域在 `push` 之前结束，之后重新索引。② 改变访问范围：需要同时读写同一存储时先分区，例如 `let (head, tail) = v.split_at_mut(1);`——正文的 `copy_add` 测试走的就是这条路（[例 3.2.1](ch03.md#ex-3.2.1)）。如果你的写法改完仍报错，先检查那个引用是不是真的已经不再被使用。
:::

:::

::: ex C17 · 给一段 unsafe 补出不变量清单（主线 ①） {#ex-3.C.17}

下面这个变式把 `copy_add` 的两个切片换成两个裸指针与一个长度。请写出它的 Safety 段落（把原来由类型保证的东西写成显式前提），再按证明表逐行给出依据或缺口，并说明哪几行在这个场景可以标「不适用」、依据是什么。

```rust
/// # Safety
/// （这里由你填写）
pub unsafe fn copy_add_raw(dst: *mut u64, src: *const u64, n: usize) {
    for i in 0..n {
        unsafe { *dst.add(i) = (*src.add(i)).wrapping_add(1) };
    }
}
```

::: sol 参考路径

Safety 段落至少五条：① 两段范围各覆盖 `[ptr, ptr + n)` 且分别属于各自的分配；② 两个指针非空且对齐到 8；③ 两段范围在 0 到 `n − 1` 上互不重叠——`split_at_mut` 那种分区可以，重叠就违反[定义 3.2.1](ch03.md#def-3.2.1) 的排他前提；④ 两个范围内每个位置在本函数执行期间都已初始化，且没有其他可变路径；⑤ 调用期间 `n` 不变，指针背后的存储不被移动、扩容或析构。
证明表十行的填法：所有权——原 `Vec` 仍是拥有者，指针不拥有任何东西；空间——范围由调用方给出的 `n` 界定，要写明 `n` 的来源；时间——要证明调用期间存储仍存活；对齐——`u64` 要求 align 8，只能写成前提；初始化——范围内每个位置已写入合法 `u64`（[定义 3.3.1](ch03.md#def-3.3.1)）；别名——两段不重叠且期间无其它可变借用；同步——**可标「不适用」，依据是「本函数不跨线程发布这块存储」**，不能只留空白；销毁——原 `Vec` 析构负责全部元素，届时指针成为悬垂值；panic——**可标「不适用」，依据是循环只做整数读写、不构造带 `Drop` 的值**；泄漏——要按[定义 3.7.1](ch03.md#def-3.7.1) 论证客户端 `mem::forget` 之后仍不导致内存不安全。空白不等于通过。参照[例 3.7.1](ch03.md#ex-3.7.1) 与 3.7 即时自测第 3 题的写法。
:::

::: ex C19 · 一个 layout 探针与它的限度（主线 ②） {#ex-3.C.19}

写一段打印 `Vec` 的 `u64` 元素形式、切片引用、以及一个「拥有字节区的结构体」的描述符尺寸与对齐的探针。写出本章探针给出的三个数，再用一句话说明这张表不能用来解释什么。

::: sol 参考路径

探针形态（正文说 layout 探针就是一段打印 `size_of` 与 `align_of` 的辅助程序）：

```rust
use std::mem::{align_of, size_of};

struct ByteRegion {
    ptr: *mut u8,
    len: usize,
    cap: usize,
    pad: usize,
}

fn main() {
    println!("Vec {} {}", size_of::<Vec<u64>>(), align_of::<Vec<u64>>());
    println!("Slice {} {}", size_of::<&[u64]>(), align_of::<&[u64]>());
    println!("Region {} {}", size_of::<ByteRegion>(), align_of::<ByteRegion>());
}
```

本章给出的三个数是：`Vec` 的 `u64` 元素形式 24 字节、`&[u64]` 16 字节、`ByteRegion` 32 字节（见 3.1.2 的本机类型与责任图）。这张表不能用来解释一次 clone 或一次借用改造的耗时：clone 的真实工作在载荷上（524288 字节的独立元素存储），描述符只有它的约两万分之一（[例 3.1.1](ch03.md#ex-3.1.1)）；表也不承诺 `Vec` 的字段顺序，不把切片引用尺寸称为数据总大小。你写的 `ByteRegion` 只是为了复现「指针加两个 `usize` 再加填充」这个量级，字段命名不必与正文一致。

::: ex C20 · 读 `zero_fill`：它凭什么合法（主线 ①） {#ex-3.C.20}

正文的两个初始化候选里，`init_zero` 先构造 n 个零再覆盖。回答三件事：① 它为什么没有越容量与长度那条界；② 把它的第一行换成「先建空 `Vec`、抬高长度到 n、再逐项写」会破坏什么；③ 若再加一个只改一个合法结构的候选（例如数据来源本就是迭代器时的 `collect`），必须与现有两个 case 保持一致的是哪几件事？

::: hint 提示

第①问只答「长度一次到位」还不够，要说清每个位置上有什么。第③问的判据是可比性，不是速度。

:::

::: sol 解答

① `vec![0u64; n]` 一步把长度置为 n，且 n 个位置全部是合法的零 `u64`：对 `u64` 而言零是有效值，所以「长度以内都有合法 `T`」成立，读取与 `Drop` 都只按长度触及已初始化元素（[定义 3.3.1](ch03.md#def-3.3.1)、[定义 3.6.1](ch03.md#def-3.6.1)）。② 提前抬高长度会让长度越过实际写入：此后任何合法 API（迭代、切片、`black_box` 消费）都能读到还没写入的位置，未初始化读取对 `Copy` 类型也不是「随机但无害」；更根本的是长度不再等价于已初始化前缀，[定义 3.3.2](ch03.md#def-3.3.2) 的不变量被破坏，之后每一步维护长度的代码都不再能信任长度（[思考 3.3.1](ch03.md#think-3.3.1)）。③ 必须一致的是：n、值序列、消费者与分母，并且只改一个合法结构——同时换布局或换算法就没法归因。采集还要沿用 21 批、配对交替、独立归档，不覆盖 native-01（[3.6.8 的判定流程](ch03.md#sec-cpp-rust.1.3.6)）。
:::

::: ex C21 · 三句话的评审意见（主线 ④） {#ex-3.C.21}

某库文档写了三句话：(a)「本类型只暴露 `Pin` 包住 `Box` 的自己，所以内部自引用由 `Pin` 保证有效」；(b)「我们跑过 ASan，所以指针来源与并发都安全了」；(c)「资源收尾都放在 `Drop` 里，业务不会漏」。逐句给评审意见，并按 3.8.6 的拒绝条件指出哪些足以拦下这个改动。

::: sol 参考路径

(a) 不成立：`Pin` 只覆盖「此后不再按普通方式移动」这一条轴，不覆盖「内部指向在最终位置建立」，也不排除该类型自己实现 `Unpin` 使 `Pin` 不施加同等约束，或某个可变访问方法把被 pin 的字段移出、替换（[定义 3.8.1](ch03.md#def-3.8.1)、[定义 3.8.2](ch03.md#def-3.8.2)、[思考 3.8.1](ch03.md#think-3.8.1)、[例 3.8.1](ch03.md#ex-3.8.1)）。(b) 越界：工具各有模型边界，跑过 sanitizer 只支持其模型内的结论；跨进程映射的合法性来自映射与协议设计，`Send`/`Sync` 与 sanitizer 都不证明对象格式与来源连续性——本包本轮只跑了普通测试、clippy、代码生成与 macOS `sample`（3.7.7、[定义 3.7.2](ch03.md#def-3.7.2)）。(c) 混淆两层：`Drop` 无法返回结果，被忽略的刷新错误就是丢失的业务确认，应改出 `finish`/`close` 显式接口；若许可代表的资源实际由后台工作占用，调用方取消还会过早释放预算（3.4.6、3.8.4）。
足以拦下这个改动的拒绝条件有三条对应：安全方法能造出悬垂引用（对应 a）、把整数地址当唯一有效性证据（对应 b）、只有 happy path 测试（对应 c 的反例）。任一命中就退回安全结构或补证明；「unsafe 行数少于多少」不是通过理由（[3.8.6](ch03.md#sec-cpp-rust.1.3.8)）。
:::

## 批改最常给的三条意见

1. **跨维度借证据**：用「指针来自 `Vec`」推时间有效，用变量名不同推不重叠，用 `Send` 或 sanitizer 推来源与并发协议。每处都要退回它所在的那一行重写。
2. **单位与口径错位**：把 ns/输入元素或 ns/最终元素说成一次语法操作的耗时，把批 p99 说成请求 p99。先改句子，再改表格。
3. **把机制解释写成成分归因**：声称「差值全由容量检查造成」「分配、复制、释放各占几成」。正文没有逐项计时，就只写产物可见的结构差异，并补一句「成分占比未采集」。
