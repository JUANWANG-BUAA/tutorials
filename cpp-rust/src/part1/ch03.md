## 3.1 所有权转移不是自动深拷贝 {#sec-cpp-rust.1.3.1}

### 所有权描述的是责任

一个值的所有者承担其合法使用与最终清理责任。
移动把责任转移给新的位置。
它不要求为每个移动执行某段固定机器指令。
编译器可能通过寄存器传递、栈槽复用或返回位置优化消除物理搬运。
因此不能从源码里数move推导内存带宽。
也不能把“移动通常便宜”解释为所有类型移动都零字节复制。
大数组的按值传递在某些调用边界仍可能涉及实际数据搬运。

对于Vec，移动通常只涉及拥有者描述符的转移。
元素存储保持在原分配中。
旧绑定不再拥有清理责任。
新绑定负责最终销毁。
这是避免double free的语义基础。
不是让两个拥有者同时相信自己拥有同一分配。

### 复制也有不同层次

Copy允许隐式复制类型的值。
它不调用用户定义的深克隆逻辑。
实现Copy要求相应字段满足约束，并且不能同时要求Drop。
Clone则是显式可调用的操作。
它的成本与语义由具体实现决定。
Vec&lt;u64&gt;的clone会复制元素到独立拥有存储。
Arc的clone通常增加共享计数，不深拷贝载荷。
二者都叫clone，但资源行为不同。

### 本机类型与所有权表

| 类型/操作 | 本机描述符尺寸 | 是否拥有元素 | 本章关注的成本 |
|:--|--:|:--|:--|
| u64切片引用 | 16字节 | 否 | 访问现有存储 |
| Vec&lt;u64&gt; | 24字节 | 是 | 分配、元素、销毁 |
| borrowed输入 | 切片引用 | 否 | 求和与调用屏障 |
| cloned临时对象 | Vec描述符及新元素区 | 是 | 分配、复制、求和、释放 |
| ByteRegion | 32字节 | 拥有字节区 | reset与短暂借用 |

描述符尺寸来自本机layout探针。
表格不承诺Vec字段顺序。
也不把切片引用尺寸称为数据总大小。
borrow实验的输入元素区有524288字节。
每次cloned工作核还需要一份独立元素存储。
这项差异属于被比较的工作，不应隐藏。

### 移动与借用的责任图

<pre class="layout">
拥有Vec A ──move──&gt; 拥有Vec B ──drop──&gt; 元素销毁与存储释放
   旧A失效              |
                        +──borrow──&gt; &[u64]
                                       |
                                       +──只读使用，不承担释放

拥有Vec B ──clone──&gt; 独立Vec C
     |                    |
     +──各自生命周期──────+──各自释放一次
</pre>

读图：move箭头转移责任，不表示复制整个堆分配。
borrow箭头不产生第二个释放者。
clone箭头在本图中特指Vec&lt;u64&gt;的独立数据复制。
不能把同一图直接套到Arc或Rc。

### “零成本所有权”需要准确理解

编译期借用检查不在每次普通引用访问时维护一个运行时借用表。
这不代表所有权相关操作都没有成本。
Drop会执行真实清理。
Rc与Arc维护计数。
RefCell在运行时维护借用状态。
Mutex需要同步协议。
这些都是所选择抽象的实际语义工作。
将它们概括为“Rust所有权免费”会误导性能分析。

### 借用不总是最佳接口

借用可以避免复制，但会约束数据生命周期。
如果结果必须独立保存，拥有副本可能更简单。
如果要跨线程或异步任务长期持有数据，也需要合适所有权。
不能为了避免一次clone让整个系统绑上复杂生命周期。
S08在复制与可用性的讨论中强调了这种取舍。
本章的benchmark只回答一个同步只读求和问题。
它不能替业务决定所有接口都应返回借用。

### 身份与内容

移动一个Vec句柄，不改变元素分配的身份。
但移动一个内联对象可能改变对象地址。
若对象内部保存指向自身字段的指针，地址变化就可能破坏关系。
这种结构不能只凭“move不复制堆数据”得到安全性。
必须区分句柄地址、载荷地址与内部引用目标。
本章最后会讨论自引用与Pin边界。

### 先画生命周期，再做优化

每份存储应能指出创建者、访问者和释放者。
每条借用应能指出其有效区间。
每次clone应能说明为什么需要独立或共享所有权。
每个Drop应能说明资源何时真正结束。
若这些问题无法回答，优化往往只是在把责任藏起来。
一份明确的所有权图通常比添加unsafe更能降低成本。

## 3.2 借用如何成为优化依据 {#sec-cpp-rust.1.3.2}

### 排他访问不是“一个地址只能有一个指针值”

程序可以保存多个裸指针值。
安全借用关心的是哪些访问在何时被允许。
可变引用建立排他访问约束。
共享引用允许共同读取，但一般不允许直接修改其覆盖内容。
UnsafeCell提供内部可变性相关的例外基础。
它不会自动提供线程同步。
也不会自动允许任意别名写入。

不能把借用规则简化成数指针数量。
派生引用、重借用与分区访问都可能合法。
它们依靠更细的范围与使用阶段。
优化器也可能依据这些约束重排和合并访问。
如果unsafe代码破坏约束，结果不能按“源代码写入顺序”预测。

### 一个真实的别名敏感核

包中的copy_add接受可变目标与共享源切片。
先检查长度相等。
再逐元素读取源、加1并写目标。
完整实现使用安全迭代器。

```rust
#[inline(never)]
pub fn copy_add(dst: &mut [u64], src: &[u64]) {
    assert_eq!(dst.len(), src.len());
    for (dst, src) in dst.iter_mut().zip(src) {
        *dst = src.wrapping_add(1);
    }
}
```

调用方通过split_at_mut提供不相交区域。
不需要自己构造两个裸切片。
测试用同一个数组的两个半区验证行为。

```rust
let mut input = [10, 20, 0, 0];
let (src, dst) = input.split_at_mut(2);
copy_add(dst, src);
assert_eq!(input, [10, 20, 11, 21]);
```

这个例子说明“来自同一个原数组”并不等于非法别名。
关键是访问范围已经安全分离。
反过来，两个不同变量名也不自动证明范围不重叠。

### 本轮LLVM参数属性

实际IR中copy_add的目标指针带noalias与writeonly。
源指针带noalias与readonly。
两者带nonnull、align8等属性。
这反映了当前后端如何利用函数边界的信息。
代码中随后出现向量加载、向量加与向量存储。
不是所有权本身在CPU中执行了检查。
而是前端约束帮助后端选择合法转换。

| 证据层次 | 本轮观察 | 可以下的结论 | 不可扩大为 |
|:--|:--|:--|:--|
| Rust接口 | dst可变、src共享 | 合法调用受借用约束 | 任意裸指针都不重叠 |
| LLVM参数 | noalias、readonly/writeonly | 后端利用访问性质 | 完整语言别名模型 |
| 向量循环 | 批量load/add/store | 当前核获得批量化 | 所有借用核都向量化 |
| 入口断言 | 长度相等检查 | 不匹配长度安全panic | 任意输入都无分支 |
| 分区测试 | split_at_mut | 同分配可合法分区 | 相邻分配可合成切片 |

### 语言模型与后端模型不能混成一句话

本地S10较旧译文用LLVM noalias概括别名。
当前标准库指针文档仍明确指出精确别名规则尚未完全确定。
本章因此分开记录二者。
实际IR属性是一项版本化代码生成观测。
它不是我们自行定义Rust全部形式语义的许可。
Miri采用的研究与检查模型也不能直接等同于最终语言定义。
本轮没有运行Miri。
不发布“已经通过Miri验证”的声明。

### 重借用的访问阶段

从一个可变引用派生较短的引用后，应在派生借用有效时遵守其约束。
不能一边使用派生引用，一边经独立旧路径写入同一位置。
unsafe代码常见错误是把旧裸指针保存起来，误以为它永远有效。
指针的数值地址可能不变。
其允许的访问阶段却可能已受新借用限制。
因此安全证明必须描述访问时间，不只描述地址范围。

### Interior mutability不是后门

Cell适合特定所有权与替换模式。
RefCell把部分借用检查推迟到运行时。
Mutex把跨线程互斥与同步接入接口。
这些工具有不同的约束与失败模式。
它们都不是“关闭借用规则”的开关。
UnsafeCell只允许在特定层面存在内部可变性。
共享跨线程访问仍需要合法同步。

### 一个真正安全的借用失败

测试先持有RefCell的可变借用。
再调用try_borrow，应得到错误。
释放第一份借用后，共享借用成功。
这没有数据竞争，也没有UB。
它显示运行时借用机制如何把冲突变成可观察失败。

```rust
let cell = std::cell::RefCell::new(7);
let first = cell.borrow_mut();
assert!(cell.try_borrow().is_err());
drop(first);
assert_eq!(*cell.borrow(), 7);
```

如果改用borrow而不是try_borrow，冲突通常表现为panic。
选择哪种API取决于失败是否属于正常控制流。
不能为了避免错误返回而手工解引用内部裸指针。
那只会移除保护，而不是解决别名冲突。

## 3.3 初始化是一条状态边界 {#sec-cpp-rust.1.3.3}

### 有存储不代表有T

分配器提供一段存储。
类型化读取要求那里存在合法的T。
初始化建立这个条件。
Vec::with_capacity取得容量，但初始长度为0。
它没有提前构造capacity个T。
安全push写入新值，然后把相应位置纳入长度。
这一顺序保证析构只触及已初始化元素。

把容量当长度会破坏不变量。
尤其是包含引用、Box、String或枚举的T。
任意零字节也未必构成合法T。
零不一定是合法引用。
零不一定是合法NonZero值。
因此“先全清零，之后再填”不能作为通用类型初始化方案。
本章zero_fill只用于u64，零是有效值。

### 已初始化前缀

Vec可以用逻辑长度表达初始化进度。
在长度以内，所有元素合法存在。
在长度以外，只能按容量存储处理。
对泛型构建器，这个前缀非常有用。
每成功构造一个元素，就push一次。
遇到Err时，局部Vec自动销毁已有元素。
若构造器panic并展开，清理路径也处理已初始化前缀。

<pre class="layout">
capacity n
+----+----+----+----+----+----+----+----+
| T0 | T1 | T2 |        尚无T的容量余量       |
+----+----+----+----+----+----+----+----+
               ^
             len = 3

make(3)失败：只drop T0、T1、T2，不能读取余量
make(3)成功：写入T3，然后逻辑长度推进到4
</pre>

读图：余量不是“值为零的T”。
它只是一段尚未属于有效元素集合的存储。
Drop依赖长度追踪责任。
手工跳过这条边界，就必须自己承担完整证明。

### 安全构建器

本包try_build用Vec维护初始化状态。
它不需要MaybeUninit或手工drop计数。
这是在加入unsafe前应先尝试的结构。

```rust
pub fn try_build<T, E>(
    n: usize,
    mut make: impl FnMut(usize) -> Result<T, E>,
) -> Result<Vec<T>, E> {
    let mut out = Vec::with_capacity(n);
    for i in 0..n {
        out.push(make(i)?);
    }
    Ok(out)
}
```

如果make(i)返回Err，问号触发早退。
此前的out仍由当前函数拥有。
它在离开时被销毁。
若全部成功，out移动到Ok中。
清理责任转移给返回值所有者。
没有第二次销毁同一个Vec。

### 初始化中的panic

构造某个元素可能在返回前panic。
这时该元素的内部局部对象由其自身展开路径处理。
已经push进out的前缀由out处理。
尚未开始构造的元素没有Drop责任。
这种分层依赖每个组件维护自己的初始化不变量。
不需要中央计数器猜测“可能创建过多少对象”。

若使用panic=abort，进程直接终止，不执行普通展开清理。
本轮测试采用默认可展开测试配置。
没有把catch_unwind的结果推广到abort构建。
外部强制终止进程也不提供Rust析构保证。
资源协议不能仅靠“Drop总会运行”的口号。

### MaybeUninit的正确角色

MaybeUninit允许表示尚未初始化的存储。
它不自动使内部T合法。
只有完整写入有效T后，才能按其契约取得T。
它也不会替你自动销毁已初始化的T。
复杂容器需要另外记录初始化进度与清理责任。
因此它是表达存储状态的工具，不是跳过证明的工具。
本章组件不需要它，故没有为性能加入手工初始化代码。

### 提前set_len的问题

如果先把Vec长度设为n，再逐项写入，panic可能使析构访问未初始化尾部。
如果T有Drop，后果尤其直接。
即使T是整数，读取未初始化值也不是合法“随机数”。
这种写法不能拿来与安全push比较速度。
benchmark不应执行UB来获得好看的下界。
本章只比较两种合法u64初始化方式。
性能差异将在后面用实际产物解释。

### 构建失败与容量失败不同

try_build的E来自元素工厂。
Vec::with_capacity的分配失败并没有被转换成E。
它可能走标准库的分配失败处理路径。
因此本组件并非完全可恢复OOM接口。
若业务要求可恢复容量错误，应考虑try_reserve等受检接口并设计错误类型。
不能因返回Result就宣称所有失败都已可恢复。
错误类型的覆盖范围必须明确。

### 初始化顺序影响可优化性

push不断维护长度，保持每一步都可安全清理。
已初始化整片切片的覆盖写入可以表达另一种循环。
编译器可能对后者更容易做批量展开。
这不表示安全性本身必然慢。
它表示不同安全接口提供了不同的循环结构。
优化工作应先改变合法结构，再评估是否真的需要unsafe。

## 3.4 Drop、部分移动与错误展开 {#sec-cpp-rust.1.3.4}

### Drop责任跟随初始化状态

已初始化的值离开相应销毁作用域时，通常执行清理。
移动后的旧位置不再拥有同一值。
部分移动后，剩余已初始化字段仍有清理责任。
编译器通过数据流分析确定哪些位置需要drop。
某些控制流需要运行时状态来区分。
另一些状态在编译期就可消除。

这就是drop flag讨论的背景。
它不意味着每个Rust对象都隐藏着一个固定布尔字段。
标志可能只出现在控制流中。
也可能被优化完全删除。
不能把它加入size_of表作为每对象固定开销。

### 字段顺序与局部变量顺序

结构体字段通常按声明顺序销毁。
块中局部变量一般按相反声明顺序销毁。
这两条规则不能互换。
临时值还受到具体表达式与edition规则影响。
本地S10 PDF包含较旧的临时作用域描述。
本章不把旧版本尾表达式规则直接套到edition2024。
性能相关锁守卫应使用明确作用域或显式drop表达边界。
不要依赖读者容易误判的复杂临时生命周期。

### 一个可计数的清理对象

测试使用Rc&lt;Cell&lt;usize&gt;&gt;记录Drop次数。
它是单线程测试工具。
没有使用非同步计数跨线程观察。
每个Tracked销毁时增加一次计数。
工厂返回Err时，已构造数量应等于Drop数量。

```rust
struct Tracked(std::rc::Rc<std::cell::Cell<usize>>);

impl Drop for Tracked {
    fn drop(&mut self) {
        self.0.set(self.0.get() + 1);
    }
}
```

这个Drop没有分配、I/O或故意panic。
测试目标因此聚焦于生命周期。
若Drop本身panic，展开协议会更复杂。
尤其是正在展开时再次panic，可能导致终止。
本章不靠双panic实验推断清理完整性。

### Err路径回归

```rust
let count = std::rc::Rc::new(std::cell::Cell::new(0));
let result = try_build(8, |i| {
    if i == 3 {
        Err("injected")
    } else {
        Ok(Tracked(std::rc::Rc::clone(&count)))
    }
});
assert!(result.is_err());
assert_eq!(count.get(), 3);
```

构建索引0、1、2成功。
索引3返回Err，没有产生Tracked。
结果应清理三个已初始化元素。
测试在安全Rust里真实执行这条失败路径。
没有把泄漏或未初始化访问伪造成“预期异常”。

### panic路径回归

另一个测试在索引4触发断言panic。
catch_unwind只用于测试观察。
测试明确包裹AssertUnwindSafe。
原因是计数器状态通过内部可变性在展开前后被观察。
这不是宣称任意业务对象都满足异常安全。
本测试的受控不变量只有前缀清理与计数。

```rust
let count = std::rc::Rc::new(std::cell::Cell::new(0));
let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
    let _: Result<Vec<_>, ()> = try_build(8, |i| {
        assert!(i != 4, "injected panic");
        Ok(Tracked(std::rc::Rc::clone(&count)))
    });
}));
assert!(result.is_err());
assert_eq!(count.get(), 4);
```

### 实际MIR清理边

归档MIR包含try_build泛型函数的实际控制流。
调用make的展开边通向cleanup。
cleanup先drop局部Vec，再drop工厂闭包。
成功路径把Vec移动进返回Result。
Err路径清理局部Vec后返回。

可见的代表性片段如下。
局部编号只属于本次生成。

```text
bb6 (cleanup): {
    drop(_3) -> [return: bb7, unwind terminate(cleanup)];
}
bb7 (cleanup): {
    drop(_2) -> [return: bb8, unwind terminate(cleanup)];
}
bb8 (cleanup): {
    resume;
}
```

这里_3是out，_2是工厂闭包。
完整MIR还包含正常返回与Result判别。
片段不证明所有泛型T的Drop都不会panic。
它证明本函数有对应清理责任的中间表示路径。

### Drop不保证业务完成

文件句柄被关闭，不等于业务数据已按持久化要求落盘。
锁守卫释放，不等于事务提交成功。
缓冲对象销毁，也不自动传回所有刷新错误。
需要显式报告错误的收尾，应设计finish或close接口。
Drop适合不返回错误的兜底清理。
不能把关键业务确认藏进无法返回结果的析构。

### 泄漏与内存安全

Rust允许某些资源泄漏而不立即构成UB。
mem::forget可以放弃析构责任。
进程退出也未必逐个运行所有Drop。
因此unsafe接口必须在安全客户端可能泄漏值时仍不导致内存不安全。
不能把“调用方最后肯定会Drop”当成唯一内存安全前提。
这与资源是否合理使用是两个层面的问题。

### 成功路径也要验证责任转移

失败清理正确，不代表成功返回没有提前Drop。
补充集成测试`tests/contracts_more.rs`覆盖成功返回后的拥有者。
构造五个Counted后，计数仍应为零。
把Vec再次移动到新绑定，也不应触发元素Drop。
最后销毁新绑定，计数才变成五。

```rust
let count = Rc::new(Cell::new(0));
let values = try_build::<_, ()>(5, |_| {
    Ok(Counted(Rc::clone(&count)))
}).expect("all elements constructed");
assert_eq!(count.get(), 0);
let moved = values;
assert_eq!(count.get(), 0);
drop(moved);
assert_eq!(count.get(), 5);
```

这个测试不是测移动需要几条机器指令。
它验证语义责任没有被复制或提前消耗。
Counted与前面的Tracked采用相同计数方式。
它们属于测试对象，不参与正式计时。
新增测试没有修改native-01绑定的内核源码。
补充测试日志单独放在validation-01。

### 部分移动不必手写析构状态

另一个测试从二元组中移动第一个资源。
销毁第一个资源后计数为一。
再销毁仍留在原位置的第二个资源，计数为二。
编译器知道各个位置的初始化状态。
程序不需要自行放置布尔标志。

```rust
let count = Rc::new(Cell::new(0));
let pair = (
    Counted(Rc::clone(&count)),
    Counted(Rc::clone(&count)),
);
let first = pair.0;
drop(first);
assert_eq!(count.get(), 1);
drop(pair.1);
assert_eq!(count.get(), 2);
```

这里pair本身没有自定义Drop。
对于实现Drop的结构，直接移出字段有额外限制。
原因是析构函数通常需要看到完整有效self。
不能从元组例子推导任意带析构结构都可随意拆走字段。
设计需要分离资源时，可以使用Option字段的take等安全模式。
这样旧位置仍保持一个合法状态。

### 用mem::take保持旧位置合法

mem::take把旧值移出，并放入Default值。
对Vec而言，旧位置成为合法空Vec。
这与裸指针read后忘记使旧位置失效不同。
补充测试在销毁旧空容器时确认资源尚未清理。
真正资源由移出的容器负责。

```rust
let count = Rc::new(Cell::new(0));
let mut original = vec![Counted(Rc::clone(&count))];
let moved = std::mem::take(&mut original);
assert!(original.is_empty());
drop(original);
assert_eq!(count.get(), 0);
drop(moved);
assert_eq!(count.get(), 1);
```

这种模式适合从可变self中转移拥有集合。
它让调用者在失败或返回后仍能安全销毁原对象。
但Default状态是否满足业务不变量，需要组件自行决定。
空Vec在类型层面合法，不代表业务上一定允许为空。
因此安全合法性与领域事务一致性仍要分开审查。

### 销毁顺序的实际日志

集成测试还定义Logged对象记录销毁id。
两个局部对象的日志为[2,1]。
一个元组的两个字段日志为[3,4]。
两者在同一次测试中分别验证。
这防止把局部逆序误记成字段逆序。
记录使用单线程Rc与RefCell。
没有在Drop中跨线程打印或读取非同步计数。
日志只用于功能验证，不用于性能采样。

测试可以验证某条具体控制流的结果。
它不能穷举所有panic和所有泛型T。
因此MIR核读与不变量说明仍然必要。
本章把测试、静态产物与接口契约并列保留。
任何一项都不能单独替代另外两项。

## 3.5 benchmark一：借用与显式克隆的真实工作差异 {#sec-cpp-rust.1.3.5}

### 待比较的问题

同一份65536个u64，求一个模加法和。
borrowed直接读取现有切片。
cloned先建立独立Vec，再求和，最后释放。
两者输出相同。
但资源工作并不相同。
本实验要量化“不需要独立拥有数据时，额外克隆路径的代价”。
不是证明所有clone都应该删除。

### 完整入口

以下是`src/bin/borrow.rs`完整代码。
每批执行256次工作核。
公共夹具逐次校验返回值。

```rust
use foundations_lab::{Case, N, borrowed, cloned, data, run};
use std::hint::black_box;

fn main() {
    let input = data(N);
    let expected = input.iter().fold(0u64, |a, &b| a.wrapping_add(b));
    let mut cases = [
        Case {
            name: "borrowed",
            work: Box::new(|| borrowed(black_box(&input))),
            expected,
        },
        Case {
            name: "cloned",
            work: Box::new(|| cloned(black_box(&input))),
            expected,
        },
    ];
    run(&mut cases, 256, N);
}
```

实际工作核如下。
独立Vec不会逃出cloned。
因此它的析构发生在工作核返回前。
该分配、复制和释放都计入时间。

```rust
#[inline(never)]
pub fn borrowed(input: &[u64]) -> u64 {
    sum_iter(std::hint::black_box(input))
}

#[inline(never)]
pub fn cloned(input: &[u64]) -> u64 {
    let owned = input.to_vec();
    sum_iter(std::hint::black_box(&owned))
}
```

### 本轮结果

来源为`results/native-01/borrow.csv`。
单位是ns/输入元素。
不是一次borrow语法操作的耗时。

| case | mean | N-1 sd | 批p50 | 批p99 |
|:--|--:|--:|--:|--:|
| borrowed | 0.058851898 | 0.000404976 | 0.058824778 | 0.059892774 |
| cloned | 0.159020461 | 0.002093374 | 0.158538461 | 0.166441023 |

cloned减borrowed的配对均值为0.100168563。
bootstrap区间为[0.099374896, 0.101163745]。
本轮支持额外拥有副本路径更贵。
差值包含分配、复制、释放和缓存状态变化。
不能单独命名为“借用检查节省了0.1ns”。
借用检查并没有在被测循环中逐元素执行。

### 代码生成支持

cloned的实际IR保留分配调用。
随后有llvm.memcpy。
之后调用求和核并释放存储。
borrowed则转入相同求和核。
因此两条路径的真实工作差异与接口设计一致。
不是编译器把clone完全删除后偶然测出不同噪声。

### profiler核对

独立`sample-borrow.txt`看到borrowed进入sum_soa。
也看到cloned及其求和、分配器相关路径。
一部分复制工作可能以内联或库函数形态出现。
不能仅凭采样符号名缺失就断言没有复制。
应结合实际IR中的memcpy与调用点。
采样不进入正式21批统计。
本章不把它换算成稳态百分比。

### 安全性能回退

假设接口只需同步读取输入。
为了绕开生命周期困惑，调用方先to_vec再传给求和函数。
这在安全Rust中完全合法。
它却引入不必要的独立拥有存储。
本实验真实重现了这条回退路径。
修复是把接口改为借用切片，而不是写裸指针。

如果结果需要在输入销毁后继续使用，前提就变了。
此时独立副本可能是正确设计。
不能照搬本表删除clone造成生命周期错误。
应把异步持有、共享计数或拥有转移纳入新实验。

### 测试覆盖与未覆盖

等价性测试覆盖多个长度。
它验证borrowed与cloned返回相同值。
没有测多线程共享输入。
没有测Arc计数。
没有测复制与其他工作并行重叠。
因此本章不能给出Arc与借用的通用成本排序。

### 如何把结果应用到业务

先定位clone发生的粒度。
一次启动时clone大配置，与每请求clone大正文意义不同。
再判断副本的生命周期是否确实独立。
然后检查能否转移所有权而不是复制。
最后测完整调用链与内存峰值。
只在clone确实位于热路径且不需要独立副本时，借用改造才有明确价值。

## 3.6 benchmark二：push并不自动胜过置零再填充 {#sec-cpp-rust.1.3.6}

### 一个应被数据否定的直觉

常见直觉是with_capacity加push没有提前清零，所以必然更快。
这个推理只数了源码表面的写入。
它忽略循环控制、长度维护与优化器能证明的范围。
也忽略分配器与后端可能采用不同实现路径。
本章不把这种直觉当结论。
使用两种合法初始化方式实际比较。

### 两种安全实现

push先取得容量，再逐项追加合法u64。
zero先构造n个合法零u64，再覆盖每个元素。
两者最终都产生相同长度与值序列。
二者都把完整结果切片交给black_box。
随后用相同求和核消费。
整个Vec创建与销毁都计入时间。

```rust
#[inline(never)]
pub fn init_push(n: usize) -> u64 {
    let mut out = Vec::with_capacity(n);
    for i in 0..n {
        out.push((i as u64).wrapping_mul(17));
    }
    sum_iter(std::hint::black_box(&out))
}

#[inline(never)]
pub fn init_zero(n: usize) -> u64 {
    let mut out = vec![0u64; n];
    for (i, value) in out.iter_mut().enumerate() {
        *value = (i as u64).wrapping_mul(17);
    }
    sum_iter(std::hint::black_box(&out))
}
```

### 完整入口

`src/bin/initialization.rs`独立编译。
每批重复64次。
N仍为65536。
输入n经过black_box。
避免把固定长度完全烘焙进所有调用上下文。

```rust
use foundations_lab::{Case, N, init_push, init_zero, run};
use std::hint::black_box;

fn main() {
    let expected = (0..N).fold(0u64, |a, i| {
        a.wrapping_add((i as u64).wrapping_mul(17))
    });
    let mut cases = [
        Case {
            name: "push",
            work: Box::new(|| init_push(black_box(N))),
            expected,
        },
        Case {
            name: "zero_fill",
            work: Box::new(|| init_zero(black_box(N))),
            expected,
        },
    ];
    run(&mut cases, 64, N);
}
```

### 实测结果

来源为`results/native-01/initialization.csv`。
单位是ns/最终元素。
包括构造、初始化、消费与销毁。

| case | mean | N-1 sd | 批p50 | 批p99 |
|:--|--:|--:|--:|--:|
| push | 1.153849851 | 0.019135814 | 1.152266979 | 1.194040060 |
| zero_fill | 0.201331729 | 0.005930436 | 0.201612711 | 0.218312025 |

zero_fill减push的配对均值为-0.952518123。
bootstrap区间为[-0.959926571, -0.945401044]。
当前结果明确不支持“push必然更快”的直觉。
我们保留它，而不是改参数直到出现预期排序。

### 实际代码生成

push循环中仍可见容量比较。
容量不足的grow_one路径也保留。
正常每次push还更新逻辑长度。
虽然预先申请n容量，当前代码生成没有消除全部相关路径。
这是一项当前编译器观测。
不是Vec::push永远无法优化的语言定理。

zero_fill中保留alloc_zeroed调用。
覆盖循环可见成对展开写入。
本轮汇编中有stp存储序列。
不要把它不加区分地称为所有操作都SIMD化。
成对标量存储与向量存储不是同一回事。
这里能确定的是覆盖循环采用了不同的展开结构。

### 不能过度归因

本轮没有逐成分计时分配、清零、覆盖与求和。
也没有采集真实内存流量。
因此不能精确分配每项贡献。
保留的容量路径与展开写入支持一种机制解释。
它不证明差值全部由某一个分支造成。
若要确认，应设计只改变一个合法结构的后续实验。

### 为什么不加入未初始化unsafe版本

因为本章目标是先识别安全结构之间的优化空间。
引入MaybeUninit或手工set_len会增加初始化与panic证明。
如果安全版本已足够快，这份复杂度可能不值得。
只有在正确匹配业务且安全候选不足时，才有理由评估unsafe。
即使评估，也必须先完成完整清理与有效值证明。
不能把UB版本作为“理论最快”参照。

### 泛型场景不能直接套用结果

u64的零初始化合法。
引用、NonZero或复杂资源类型未必如此。
泛型T也可能有昂贵Drop。
本章try_build因此采用安全push维护前缀。
性能测试和正确性组件选择了不同优先级。
这并不矛盾。
一个用于解释数值核，一个用于维护泛型失败清理。

### 更贴近业务的下一步

若数据来源本来就是迭代器，可以增加collect候选。
若有可复用缓冲，可以测clear后重新填充。
若最终消费者允许流式处理，可以不保存全部元素。
每种方案改变的资源生命周期不同。
应分别报告，而不是寻找一个通用“初始化最快写法”。
本轮只完成当前两种实现的真实比较。

## 3.7 unsafe、来源与有效引用的证明清单 {#sec-cpp-rust.1.3.7}

### unsafe转移责任，不取消责任

unsafe允许执行某些编译器无法自动证明安全的操作。
它不允许UB。
安全封装还必须保证任意符合公开接口的安全客户端不会触发UB。
只证明示例调用合法不够。
公开方法组合、panic、提前返回与泄漏都需要考虑。
因此unsafe边界通常要比一行解引用大得多。

### 地址不是完整指针

当前std::ptr文档把地址与provenance分开讨论。
地址说明数值位置。
来源表达允许访问的空间、时间和可变性范围。
一块存储释放后，即使另一分配复用了同一地址，也不能凭旧地址访问新对象。
地址相等不能延长生命周期。
地址连续也不能合并两次独立分配。

provenance是语义约束。
不意味着每个普通指针都在运行时携带一个额外堆对象。
它使编译器与检查工具能够表达访问是否合法。
不要用“机器寄存器只有地址位”否定语言抽象机要求。
优化本来就依赖语言级前提。

### Strict Provenance API

addr提取地址部分。
with_addr保留原指针的来源并改变地址。
map_addr用于对地址做变换同时保留来源。
这些API不自动证明新地址可解引用。
仍需检查边界、对齐、有效值与别名。
如果新地址超出原分配，保留来源也不会创造新访问权限。

普通指针转整数再转回的语义属于更复杂的exposed provenance讨论。
当前文档明确承认其语义不如Strict Provenance清晰。
本章不把所有整数往返一概称为立即UB。
也不把它当成可忽略来源的万能捷径。
优先保留真实来源指针，避免不必要的重建歧义。

### 创建引用是立即承担义务

把裸指针写成引用时，需要非空、对齐、可解引用、有效值与合法别名。
不能说“先创建引用，之后不会真正读取”。
义务在形成引用时已经相关。
未使用的引用也不是豁免。
零尺寸访问与零长度切片还有各自的具体API要求。
不能把允许某种零字节裸操作的例外推广到任意引用构造。

### 证明表

| 维度 | 需要回答的问题 | 常见错误替代 |
|:--|:--|:--|
| 所有权 | 谁负责最终释放，是否仅一次 | 地址现在还在 |
| 空间 | 整个访问范围属于哪次分配 | 两个地址看起来连续 |
| 时间 | 分配与对象是否仍存活 | 以前曾经有效 |
| 对齐 | 绝对地址满足什么align | 相对偏移是8的倍数 |
| 初始化 | 是否已有合法T | 已分配了足够字节 |
| 别名 | 哪些路径在此阶段可访问 | 变量名不一样 |
| 同步 | 并发冲突通过什么协议排除 | 指针是Send |
| 销毁 | 已初始化元素怎样清理 | 最后大概会drop |
| panic | 半构建与展开如何恢复不变量 | 正常路径测试过 |
| 泄漏 | 客户端forget后是否仍内存安全 | 用户不会这样做 |

### UnsafeCell的边界

UnsafeCell允许共享引用之下的特定内部可变性。
它不使数据竞争合法。
它不允许随意产生多个互相冲突的可变引用。
它也可能影响外围类型的布局优化。
因此把一个T包进UnsafeCell不能被视为纯粹“无表示影响”的动作。
本章没有为它写通用niche推断。

### 指针算术与访问要分开

某些wrapping指针运算可以暂时得到范围外地址。
这不代表该地址可以读写。
受in-bounds约束的运算还有更严格前提。
具体API的Safety段必须逐项阅读。
不能根据函数名里有wrapping就推断最终解引用安全。
回到原范围也不能修复已经发生的非法访问。

### provenance与共享内存协议

跨进程映射常使用偏移而不是持久保存本进程裸地址。
即使两个进程都能看到相同字节，Rust对象生命周期也不是自动共享。
锁、初始化与版本协议需要另外设计。
Send与Sync描述线程相关约束，不证明跨进程对象格式。
本章不实现共享内存容器。
这里只指出来源与访问权需要与实际映射方式协调。

### 工具能证明什么

Miri可以发现其支持模型下的多种非法访问。
它不能替代所有外部代码、硬件与并发协议证明。
ASan、TSan和Loom也各有覆盖范围。
没有执行这些工具时，不能在交付里列为通过。
本轮只有普通测试、clippy、代码生成与macOS sample。
我们保留明确限制，不用工具名为unsafe背书。

### 为什么本包保持全安全

当前六个实验不需要unsafe才能回答问题。
ByteRegion利用切片与可变self表达重用限制。
try_build利用Vec表达初始化前缀。
copy_add利用split_at_mut提供不相交输入。
这些结构把证明交给成熟安全接口。
底层标准库内部可能使用unsafe，但本包没有新增unsafe边界。
这比为了展示“底层能力”而写一个未经证明的分配器更合适。

## 3.8 自引用、Pin与资源协议的组合边界 {#sec-cpp-rust.1.3.8}

### 地址稳定性是独立维度

所有权转移不保证对象地址稳定。
借用约束不自动给一个对象永久固定地址。
当内部指针指向自身字段时，需要额外机制。
Pin表达某些值在被pin后不再按普通方式移动的约束。
它不是普遍禁止移动一切句柄。
移动Pin包装的指针句柄与移动被指向值要分开。

### Box与自引用

Box使载荷位于独立分配中。
移动Box句柄通常不移动载荷。
但仅有Box并不禁止通过合法接口移出或替换内部值。
若要依赖永久地址关系，还需要Pin及相应类型约束。
构造自引用也要在最终位置建立内部指向。
不能先在栈上创建内部指针，再搬到Box后假定它自动修复。

### Unpin的意义

对Unpin类型，Pin并不施加同样的不可移动约束。
需要地址敏感不变量的类型通常不能随意实现Unpin。
使用PhantomPinned只是阻止自动获得某些性质的一环。
它不自动证明内部指针有效。
构造、投影、销毁与安全公开方法仍要维护不变量。
本章没有实现自引用unsafe类型。
因此不把几行Pin样例当成完成证明。

### Pin不是线程亲和性

对象地址不变，不意味着由同一线程操作。
可跨线程移动的拥有句柄仍可能让不同线程访问被pin对象。
线程局部资源需要自己的Send边界。
异步任务在不同worker之间恢复也可能保持被pin存储地址不变。
Future章节将继续区分poll状态与执行线程。
这里不把Pin说成调度器锁核工具。

### 析构与自引用

地址敏感对象需要在销毁期间保持约定。
Drop实现不能先破坏仍将被使用的内部关系。
若提供投影方法，还要确保投影不会移出被pin字段。
安全API只露出Pin并不自动保证内部投影sound。
每个unchecked投影都必须说明字段移动与销毁边界。
本章选择不提供此类接口，避免无必要扩大证明面积。

### 资源许可与真正工作生命周期

所有权系统只知道对象跟谁走。
它不知道一个业务许可本来要代表哪种资源。
若许可跟随调用方，但实际工作在后台继续运行，调用方取消会过早释放预算。
这可以在完全安全Rust里发生。
因此业务资源所有权必须与真正占用者绑定。
不是只要“有Drop”就自然正确。
并发与runtime章节会用许可迁移测试这一点。

### 错误恢复中的基本保证

一个操作失败后，组件至少应保持内存安全和可销毁。
更强的事务保证要求状态完全不变。
try_build返回Err时销毁已建前缀，不返回半成品。
ByteRegion失败时保持游标不变。
这两种保证不同。
必须在接口文档里分别写清。
不能统一叫“异常安全”而省略状态语义。

### 初始化、发布与并发

线程间发布一个对象之前，需要先建立完整合法状态。
发布协议还需要相应同步关系。
初始化完成不等于其他线程一定可见。
Release/Acquire等同步不能修复发布前已经产生的无效引用。
对象合法性与并发可见性是不同证明。
本章只做单线程初始化实验。
不从其结果推导原子发布协议。

### 性能重构的顺序

先减少不必要的拥有副本。
再匹配访问集合与布局。
再选择更易优化的安全循环。
随后核对生成代码和真实测量。
只有仍存在重要瓶颈时，才考虑扩大unsafe边界。
这一顺序不是禁止unsafe。
它是让每一份额外证明都有可衡量的必要性。

### 代码审查中的拒绝条件

如果安全方法能制造悬垂引用，应拒绝。
如果panic能使长度覆盖未初始化尾部，应拒绝。
如果reset依赖用户口头承诺不保留借用，应要求更强接口。
如果整数地址被当作唯一有效性证据，应补来源证明。
如果性能结论来自UB版本，应丢弃该结论。
如果只有happy path测试，应增加真实失败路径。
这些条件比“unsafe行数少于多少”更有意义。

### 何时可以停止继续微调

当安全实现满足业务预算，额外复杂度未必值得。
本轮zero_fill已经展示安全结构间有较大优化空间。
borrowed也避免了不需要的副本。
此时优先维护测试、文档与真实调用链。
不要因为一本底层书就必须在每章写unsafe。
理解边界并知道何时不跨越，本身就是专业能力。

## 3.10 常见陷阱 {#sec-cpp-rust.1.3.10}

1. **把move理解为必定复制整个堆对象。**
   Vec移动转移描述符与责任，元素分配可保持不动。
   物理搬运必须查看具体调用边界。

2. **把clone统一看成深拷贝。**
   Vec与Arc的clone有不同资源语义。
   成本分析必须写出具体类型。

3. **为减少clone强迫所有接口返回借用。**
   独立生命周期可能确实需要拥有数据。
   不应以复杂性和错误生命期换微基准收益。

4. **把noalias属性当成完整Rust形式语义。**
   它是本轮LLVM产物的一部分。
   当前语言别名模型仍有未完全确定的边界。

5. **用变量名不同证明指针不重叠。**
   名字不决定地址范围。
   使用安全分区或完整范围证明。

6. **把capacity当成已初始化长度。**
   余量中还不一定有合法T。
   析构只能处理真正已初始化元素。

7. **提前set_len再逐项填充。**
   panic可能使清理读取未初始化尾部。
   先用安全前缀结构，必要时再证明手工状态机。

8. **认为零字节适合初始化任意T。**
   引用和NonZero等类型排除零表示。
   本章zero_fill只用于合法的u64。

9. **把drop flag算成每对象固定字节。**
   它可能是控制流状态并被优化掉。
   不应擅自加到size_of结果上。

10. **把catch_unwind等同于所有失败可恢复。**
    abort、分配失败处理与外部终止有不同边界。
    测试只覆盖指定的展开路径。

11. **地址相同就沿用旧指针。**
    存储复用不会延长旧来源的有效时间。
    地址不是完整访问权限。

12. **创建非法引用但保证不用。**
    引用形成本身就有有效性义务。
    不使用不能豁免非空、对齐和有效值要求。

13. **用UnsafeCell替代同步。**
    内部可变性不是数据竞争许可。
    跨线程仍需正确发布与互斥协议。

14. **把Pin解释为线程固定。**
    地址稳定性与执行线程是不同维度。
    Send与调度边界需要另行处理。

15. **只数写入次数预测初始化速度。**
    本轮push保留容量路径，zero_fill有展开写入。
    源码直觉必须接受真实产物与实测反证。
