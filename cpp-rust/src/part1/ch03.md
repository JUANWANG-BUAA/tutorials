所有权常被讲成「一段代码能不能编译」的语言规则。这一章换一个角度：把所有权看成**责任的账本**——谁创建存储、谁有权在什么时间访问、谁负责销毁、失败时剩下什么。优化依据、初始化边界和 unsafe 的证明义务，都是这本账的不同页。本章的两个 benchmark 不是附属练习，它们是账本的计量部分：借用与克隆相差多少、`push` 与置零填充相差多少，都用归档里的真实数字回答。

一条主线：**先问谁负责，再问能访问什么、有没有合法的值，最后才问要不要把证明担到自己身上。**每一节都回到这条线上。

## 3.1 所有权转移不是自动深拷贝 {#sec-cpp-rust.1.3.1}

本节回答一个问题：**源码里写下一个 move，机器上究竟发生了多少字节？**「移动很便宜」和「移动就是复制指针」是两个流传很广的说法，它们都不精确：前者掩盖了大数组的按值传递，后者把编译期的责任归属误当成运行时的一次赋值。本节把责任、字节和清理义务分开，再给一张接口选择表。

::: preview 先抓住一件事

所有权是编译期的**责任归属**，不是一段固定的指令序列。肯定「这次移动不搬运数据」，要同时说清类型、调用边界和是否内联（优化器把被调函数的代码直接搬进调用点）；否定「所有移动都是零字节复制」，只需一条例外：大数组的按值传递在某些调用边界仍要实际搬运数据。判断顺序永远是：先问谁负责释放，再问搬了多少字节。
:::

### 3.1.1 所有者、移动与清理责任

::: def 定义 3.1.1 · 所有者与移动 owner / move {#def-3.1.1}

一个值的**所有者**（owner）承担它的合法使用与最终清理责任。**移动**（move）把这份责任转移给新位置，旧绑定随即失效。移动本身并不要求为每一步执行某段固定机器指令：编译器可能通过寄存器（CPU 内部最快取用的小存储格）传递、栈槽复用或返回位置优化消除物理搬运。

:::

[@def-3.1.1] 有三条推论。第一，不能从源码里数 `move` 来推导内存带宽——被消除的搬运不产生任何指令。第二，「移动通常便宜」解释不了所有类型：大数组的按值传递在某些调用边界仍可能涉及实际数据搬运。第三，重复的拥有者才是 double free（同一块存储被释放两次）的来源，而[@def-3.1.1] 只允许一份责任。

对 `Vec`，移动通常只涉及拥有者描述符（descriptor，句柄里那几个字：指针、长度、容量）的转移，元素存储保持在原分配中。旧绑定不再拥有清理责任，新绑定负责最终销毁——这是避免 double free 的语义基础，而不是让两个拥有者同时相信自己拥有同一分配。

::: def 定义 3.1.2 · Copy 与 Clone {#def-3.1.2}

**Copy** 是允许隐式复制的类型属性：值被使用一次后原绑定仍可用，它不调用用户定义的深克隆逻辑；实现 `Copy` 要求相应字段满足约束，并且不能同时要求 `Drop`。**Clone** 是显式可调用的操作，它的成本与语义由具体实现决定。

:::

`Vec<u64>` 的 `clone` 会复制元素到独立拥有存储；`Arc` 的 `clone` 通常增加共享计数，不深拷贝载荷。二者都叫 clone，但资源行为不同：前者复制载荷，后者复制责任的一份引用（[@def-3.1.2]）。

::: ex 例 3.1.1 · 一次 clone 的账要算在哪 {#ex-3.1.1}

本章 borrow 实验的输入元素区有 524288 字节，即 65536 个 `u64`。本机 layout 探针（打印类型尺寸与字段偏移的小程序）给出的描述符尺寸是：`Vec<u64>` 24 字节、`&[u64]` 16 字节、`ByteRegion` 32 字节。`cloned` 工作核每次还需要一份独立的元素存储。

1. 这次复制的成本主要由描述符还是由载荷决定？
2. 能不能写「描述符只有 24 字节，所以 clone 可以忽略」？
3. `Arc::clone` 走同一条推理吗？

::: sol 解答

1. 载荷。独立元素存储与输入的 524288 字节同量级，描述符只有它的约两万分之一（524288 ÷ 24 ≈ 21845）。
2. 不能。clone 的真实工作是分配、元素复制、随后的一次释放，它们都计进 3.5 节 `cloned` 的 0.159020461 ns/元素，而 `borrowed` 的 0.058851898 里没有这部分（数值判定在 3.5 做，本节只确定「该算谁」）。
3. 不走。`Arc::clone` 改的是计数，成本与载荷大小无关，但带来共享计数的实际语义（[@def-3.1.2]）。

:::

:::

### 3.1.3 「零成本所有权」需要准确理解

编译期借用检查不在每次普通引用访问时维护一个运行时借用表——这一点常被写成「所有权免费」。它只说明**检查发生在编译期**，不说明所有权相关操作都没有成本：`Drop` 会执行真实清理；`Rc` 与 `Arc` 维护计数；`RefCell` 在运行时维护借用状态；`Mutex` 需要同步协议。这些都是所选择抽象的实际语义工作（对照[@def-1.1.1]：编译器删掉的必须是没人做的工作，这里每一步都有人做）。把它们概括成「Rust 所有权免费」会误导性能分析。

::: think 思考 · 一个函数把 `Vec` 按值收进去，是不是多了一次复制 {#think-3.1.1}

调用方写完 `consume(v)` 就不能再用 `v`。有人据此认为「按值传参比传引用慢，因为要复制整个数组」。这句话漏了什么？

::: sol 解答

漏了两层。第一，移动的是描述符，元素存储留在原分配中，按值传递本身不要求复制载荷（[@def-3.1.1]）。第二，代价不在复制而在**责任转移**：调用方此后不能再使用该 `Vec`，如果它还要用，就得先 `clone`——那才是载荷级复制（[@def-3.1.2]）。真正要测的是接口是否迫使调用方保留两份数据，而不是数源码里有几个 move。大数组在某些调用边界的实际搬运属于另一件事，要看具体产物，本节没有为它采集数据。

:::

:::

### 3.1.4 借用不总是最佳接口

借用可以避免复制，但会约束数据生命周期。如果结果必须独立保存，拥有副本可能更简单；如果要跨线程或异步任务长期持有数据，也需要合适的所有权。不能为了避免一次 clone 让整个系统绑上复杂生命周期。S08（Effective Rust）在复制与可用性的讨论中强调了这种取舍。本章的 benchmark 只回答一个同步只读求和问题，它不能替业务决定所有接口都应返回借用（[@ex-3.1.1]）。

::: method 判定流程 · 这段接口该拥有还是该借用

**① 谁能先释放**：调用方若可能在被调用方之后销毁输入，借用就不成立，需要副本或转移。

**② 结果是否长期存活**：结果要活过输入，返回借用会把生命周期传染给整条调用链（[@def-3.1.1]）。

**③ 是否跨线程**：跨任务长期持有要么转移所有权，要么用共享计数，两者成本对象不同（[@def-3.1.2]）。

**④ 副本在不在热路径**：启动时 clone 一次大配置与每请求 clone 大正文不是一个量级，先定位粒度再决定改造（3.5 的实测差值就是按「一次调用」的粒度给出的）。

**⑤ 改造后能否验证**：接口改成借用后必须仍能编译并给出相同输出，否则只是把复杂度藏起来（对照[@def-1.3.1] 的逐次观察要求）。

:::

### 3.1.5 身份与内容：三种地址

移动一个 `Vec` 句柄，不改变元素分配的身份；但移动一个内联对象可能改变对象地址。若对象内部保存指向自身字段的指针，地址变化就可能破坏这种关系。这类结构不能只凭「move 不复制堆数据」（[@def-3.1.1]）得到安全性。要区分三个对象：**句柄地址**（结构体本身在哪）、**载荷地址**（堆上的元素区在哪）、**内部引用目标**（字段里那个指针指向谁）。本章 3.8 节讨论自引用与 `Pin` 边界。

### 3.1.6 先画生命周期，再做优化

每份存储应能指出创建者、访问者和释放者；每条借用应能指出其有效区间；每次 clone 应能说明为什么需要独立或共享所有权；每个 `Drop` 应能说明资源何时真正结束。若这些问题无法回答，优化往往只是在把责任藏起来。一份明确的所有权图通常比添加 unsafe 更能降低成本（对照 3.7 节的证明清单）。

### 3.1.7 小结与常见错误

**小结。**① 移动转移的是责任，物理搬运由编译器在具体调用边界决定（[@def-3.1.1]）；② Copy、Clone 与共享计数是三种不同操作，成本对象不同（[@def-3.1.2]）；③ 描述符尺寸与载荷大小是两个量，别拿 24 字节解释 524288 字节的账（[@ex-3.1.1]）；④ 借用省下载荷，代价是生命周期约束；⑤ 句柄地址、载荷地址与内部引用目标要分开谈。下一节 [3.2 借用如何成为优化依据](#sec-cpp-rust.1.3.2) 把「谁在什么时候能访问」写成后端能用的信息。

::: errata 常见错误清单（3.1 节）

## 3.2 借用如何成为优化依据 {#sec-cpp-rust.1.3.2}

本节回答一个问题：**「这条路径此刻独占写入」这个编译期事实，在后端换来了什么？**3.1 说移动只转移责任（[@def-3.1.1]）；这一节看借用怎样把访问信息交给优化器，并用一个真实核 `copy_add` 的本轮 IR 属性说明这类证据能写到哪一步。

::: preview 先抓住一件事

借用规则数的是**访问权限**，不是指针数量。肯定「这两个切片不重叠」，要看它们是否来自同一个安全分区；否定它，只需一次真正重叠的写入。优化器依据这些约束重排和合并访问；unsafe 代码一旦破坏约束，结果就不能按「源代码写入顺序」预测。
:::

### 3.2.1 排他访问不是「一个地址只能有一个指针值」

程序可以保存多个裸指针（raw pointer，不带借用约束的指针）值。安全借用关心的是哪些访问在何时被允许。

::: def 定义 3.2.1 · 排他访问与共同读取 exclusive access / shared read {#def-3.2.1}

**排他访问**指在某段时间区间内，只有这一条路径被允许写入这块存储。**共同读取**指多条路径可以同时读，但都不写。两者都按时间描述，不按指针变量的个数描述。

:::

可变引用建立[@def-3.2.1] 的排他一侧；共享引用建立共同读取一侧。`UnsafeCell` 提供内部可变性（interior mutability，在共享引用之下仍可改写字段的能力）相关的例外基础，它不会自动提供线程同步，也不会自动允许任意别名写入。不能把借用规则简化成数指针数量：派生引用、重借用与分区访问都可能合法，它们依靠更细的范围与使用阶段（[@def-3.2.3]）。优化器也可能依据这些约束重排和合并访问；如果 unsafe 代码破坏约束，结果不能按「源代码写入顺序」预测。

### 3.2.2 一个真实的别名敏感核

包中的 `copy_add` 接受可变目标与共享源切片，先检查长度相等，再逐元素读取源、加 1 并写目标。完整实现使用安全迭代器。

```rust
#[inline(never)]
pub fn copy_add(dst: &mut [u64], src: &[u64]) {
    assert_eq!(dst.len(), src.len());
    for (dst, src) in dst.iter_mut().zip(src) {
        *dst = src.wrapping_add(1);
    }
}
```

调用方通过 `split_at_mut` 提供不相交区域，不需要自己构造两个裸切片。测试用同一个数组的两个半区验证行为。

::: ex 例 3.2.1 · 同一个数组的两个半区算不算非法别名 {#ex-3.2.1}

请写出下面测试执行后 `input` 的内容，并判断「两个切片来自同一个原数组」是否构成非法别名。

```rust
let mut input = [10, 20, 0, 0];
let (src, dst) = input.split_at_mut(2);
copy_add(dst, src);
assert_eq!(input, [10, 20, 11, 21]);
```

::: sol 解答

`src` 是 `[10, 20]`，`dst` 是写入区。逐元素读源、加 1、写目标：`0→11`、`0→21`，`input` 变成 `[10, 20, 11, 21]`，断言成立。这不构成非法别名：`split_at_mut` 把一段可变存储分成两个不相交区间，读侧与写侧的**地址范围**已经不重叠，[@def-3.2.1] 的排他条件仍然满足。反过来，两个不同的变量名也不自动证明范围不重叠——名字不决定地址。这个例子说明「来自同一个原数组」并不等于非法别名，关键是访问范围已经安全分离。

:::

:::

### 3.2.3 本轮 LLVM 参数属性

::: def 定义 3.2.2 · LLVM 参数属性与 noalias {#def-3.2.2}

**参数属性**（parameter attribute）是编译器写在函数签名上的附加事实，用来告诉优化器某个参数允许怎样被访问。`noalias` 表示该指针指向的存储在本函数的有效范围内不被其它参数别名写入；`readonly` / `writeonly` 表示只读与只写；`nonnull`、`align 8` 表示非空与对齐要求。

:::

实际 IR 中 `copy_add` 的目标指针带 `noalias` 与 `writeonly`，源指针带 `noalias` 与 `readonly`，两者带 `nonnull`、align 8 等属性。这反映了当前后端如何利用函数边界的信息。代码中随后出现向量加载、向量加与向量存储。要点是：**不是所有权本身在 CPU 中执行了检查**，而是前端约束帮助后端选择了合法转换（[@def-3.2.2]）。

| 证据层次 | 本轮观察 | 可以下的结论 | 不可扩大为 |
|:--|:--|:--|:--|
| Rust 接口 | dst 可变、src 共享 | 合法调用受借用约束 | 任意裸指针都不重叠 |
| LLVM 参数 | noalias、readonly/writeonly | 后端利用访问性质 | 完整语言别名模型 |
| 向量循环 | 批量 load/add/store | 当前核获得批量化 | 所有借用核都向量化 |
| 入口断言 | 长度相等检查 | 不匹配长度安全 panic | 任意输入都无分支 |
| 分区测试 | split_at_mut | 同分配可合法分区 | 相邻分配可合成切片 |

::: ex 例 3.2.2 · 这条 IR 属性支持哪一句结论 {#ex-3.2.2}

有人根据上表写下三句话：①「Rust 保证所有指针互不别名」；②「本次构建中 `copy_add` 的读写互不重叠，因此后端可以安全批量化」；③「只要参数带 `noalias`，任何机器码都会向量化」（这里说的向量化，就是一条 CPU 指令同时处理多个数）。逐句判定。

::: sol 解答

①错。语言层面的别名规则约束的是合法借用关系，不是「所有指针」——裸指针与 `UnsafeCell` 都在[@def-3.2.1] 的例外面里。②对，这是本轮代码生成观察能支持的强度：它说的是这一次构建里发生的事（[@def-3.2.2]）。③错。属性给出优化许可，不保证后端采用；换优化级别或换版本都可能不同，表格第三行正是这个边界。这条边界与[@def-1.7.3] 的精神一致：一次构建的观测只支持一次构建的结论。

:::

### 3.2.4 语言模型与后端模型不能混成一句话

本地 S10（Rust 参考手册）PDF 第 344 页「未定义的行为」一节写的是：`&mut T` 和 `&T` 遵循 LLVM 的「作用域无别名(noalias)模型(scoped noalias model)」，除非 `&T` 内部包含 `UnsafeCell<U>`。同一页的警告段原话是「下面的列表并非详尽无遗地罗列了 Rust 中的未定义行为。而且对于在非安全代码中什么是明确不允许的，目前 Rust 还没有正式的语义模型」。

在线的 Rustonomicon 别名一节（`compiler-web-aliasing`，2026-11-01 重新抓取，SHA-256 与登记值逐位一致）说得更直白：它声明自己用最宽泛的别名定义讨论问题，Rust 自己的定义「大概会更受限制，要把变更(mutation)与活跃性(liveness)算进去」，而完整的别名模型还必须计入函数调用、裸指针与 `UnsafeCell`。当前标准库指针文档也仍指出精确别名规则尚未完全确定（`FOUNDATIONS-PTR`）。

本章因此把两者分开记录：实际 IR 属性是一项**版本化代码生成观测**，它不是我们自行定义 Rust 全部形式语义的许可。Miri（Rust 官方的解释器式 UB 检查工具）采用的研究与检查模型也不能直接等同于最终语言定义。本轮没有运行 Miri，因此不发布「已经通过 Miri 验证」的声明（对照 3.7 的工具边界）。

### 3.2.5 重借用的访问阶段

::: def 定义 3.2.3 · 重借用与访问阶段 reborrow / access phase {#def-3.2.3}

**重借用**是从已有引用派生出一段更短生命周期的引用。**访问阶段**指一块存储在时间轴上被划出的「谁能访问」的区间；同一个地址在不同阶段可以有不同的合法访问者。

:::

从一个可变引用派生较短的引用后，应在派生借用有效时遵守其约束：不能一边使用派生引用，一边经独立旧路径写入同一位置。unsafe 代码常见错误是把旧裸指针保存起来，误以为它永远有效。指针的数值地址可能不变，其允许的访问阶段却可能已受新借用限制（[@def-3.2.3]）。因此安全证明必须描述访问时间，不只描述地址范围——这正是 3.7 证明表里「时间」那一行的来历。

### 3.2.6 Interior mutability 不是后门

`Cell` 适合特定所有权与替换模式；`RefCell` 把部分借用检查推迟到运行时；`Mutex` 把跨线程互斥与同步接入接口。这些工具有不同的约束与失败模式，它们都不是「关闭借用规则」的开关。`UnsafeCell` 只允许在特定层面存在内部可变性；共享跨线程访问仍需要合法同步（[@def-3.2.1]）。

::: ex 例 3.2.3 · 一次真正安全的借用失败 {#ex-3.2.3}

下面这段测试出自本包的 `dynamic_borrow_conflict_is_safe_failure`。请说明 `try_borrow` 返回错误时是否发生了 UB，以及把它换成 `borrow` 之后失败形态怎么变。

```rust
let cell = std::cell::RefCell::new(7);
let first = cell.borrow_mut();
assert!(cell.try_borrow().is_err());
drop(first);
assert_eq!(*cell.borrow(), 7);
```

::: sol 解答

没有 UB。测试先持有 `RefCell` 的可变借用，再请求共享借用，两条路径在同一阶段想访问同一存储，冲突违反[@def-3.2.1] 的排他前提，所以运行时借用机制把它变成可观察失败（返回 `Err`）。`drop(first)` 结束第一个访问阶段后，共享借用成功，值仍是 7。如果改用 `borrow` 而不是 `try_borrow`，冲突通常表现为 panic（运行时中止）。选哪个 API 取决于失败是否属于正常控制流；不能为了避免错误返回而手工解引用内部裸指针，那只会移除保护，而不是解决别名冲突（见[@think-3.2.1]）。

:::

::: think 思考 · 手工解引用内部指针来绕过 `try_borrow` 的错误 {#think-3.2.1}

`try_borrow` 返回错误让这段代码没法继续。有人提议：从 `RefCell` 里拿到裸地址，直接读写，跳过运行时检查。问题出在哪？

::: sol 解答

它移除了保护，而不是解决了别名冲突。冲突的原因是两条路径在同一阶段都想访问同一存储（[@def-3.2.3]）；手工解引用并没有让这个事实消失，只是让编译器不再有机会知道它。后果分两类：逻辑上可能读到半成品；内存安全上，若同时存在被允许的可变访问，就破坏了[@def-3.2.1] 的排他前提，后续优化重排不再有可预测的行为。正确做法是调整访问阶段（先 `drop` 第一份借用），或者改变数据结构让两份访问本就分区（如 `split_at_mut`，见[@ex-3.2.1]）。

::: method 判定流程 · 这两个访问到底冲不冲突

**① 列范围**：写出每次访问覆盖的地址区间，而不是变量名（[@ex-3.2.1]）。

**② 列阶段**：标出每个借用的起止位置；重借用会把一条路径的合法窗口切成两段（[@def-3.2.3]）。

**③ 看写侧**：同一阶段有两个写入者，或一个写入者与一个读取者重叠，就冲突（[@def-3.2.1]）。

**④ 找合法分离手段**：`split_at_mut`、`iter_mut` 分区、先 `drop` 再借用，都是把阶段或范围分开的安全做法（[@ex-3.2.3]）。

**⑤ 只在剩下无法分离时**才考虑 `UnsafeCell`，并且要自己补上 3.7 的别名与同步两行义务。

### 3.2.7 小结与常见错误

**小结。**① 借用约束描述的是时间与权限，不是指针计数（[@def-3.2.1]）；② 合法分区（`split_at_mut`）与非法别名是两件事（[@ex-3.2.1]）；③ 后端属性是版本化观测，支持「本次构建利用了访问性质」，不支持语言级承诺（[@def-3.2.2]、[@ex-3.2.2]）；④ 证明要写访问时间，不只写地址范围（[@def-3.2.3]）；⑤ `Cell`/`RefCell`/`UnsafeCell` 各有边界，都不是关闭规则的开关（[@ex-3.2.3]）。下一节 [3.3 初始化是一条状态边界](#sec-cpp-rust.1.3.3) 把「访问权限」换成「有没有合法的值」。

::: errata 常见错误清单（3.2 节）

E-a **用变量名不同证明指针不重叠。**名字不决定地址范围（[@ex-3.2.1]）；先查是否来自同一安全分区。

E-b **把 `noalias` 当成完整 Rust 形式语义。**它是本轮 LLVM 产物的一部分（[@def-3.2.2]）；先查文档对别名模型的保留。

E-c **把同一分配的两半当非法别名。**分区后地址范围已不重叠（[@ex-3.2.1]）；先查重叠区间而不是变量个数。

E-d **保存旧裸指针并假定它永远有效。**数值地址不变，访问阶段可能已变（[@def-3.2.3]）；先查此刻谁持有借用。

E-e **用 `UnsafeCell` 代替同步。**内部可变性不是数据竞争许可（[@def-3.2.1]）；先查跨线程发布协议。

E-f **为跳过 `try_borrow` 错误手工解引用内部指针。**这是移除保护，不是解决冲突（[@think-3.2.1]）。

E-g **写「已通过 Miri 验证」。**本轮没有运行 Miri（3.2.4）；先查工具执行记录。

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　[@def-3.2.1] 的排他访问与共同读取分别是什么？它们按什么维度描述？

::: sol 第 1 题答案
排他访问：某区间内只有一条路径被允许写入；共同读取：多条路径可同时读但都不写。两者按时间区间描述，不按指针个数描述。对应[@def-3.2.1]。
:::

**第 2 题 · 辨析**　本轮 IR 里 `dst` 带 `noalias writeonly`、`src` 带 `noalias readonly`。这能支持「所有借用核都会向量化」吗？

::: sol 第 2 题答案
不能。它只支持「当前核在本轮构建中获得批量化」；属性给的是许可，不保证后端选择，证据表的第三行明确写了不可扩大为「所有借用核都向量化」（[@ex-3.2.2]）。
:::

**第 3 题 · 应用**　你要写一个函数读 `&mut [u64]` 的前一半、写后一半。给出安全实现的第一行，并说明它为什么合法。

::: sol 第 3 题答案

**第 4 题 · 迁移**　线上代码把一个 `&mut T` 转成裸指针存进全局表，稍后再解引用。按本节你会先问哪两个问题？

## 3.3 初始化是一条状态边界 {#sec-cpp-rust.1.3.3}

本节回答一个问题：**分配器（负责向系统要内存、再把内存还给系统的那层代码）给了 n 个元素的存储空间，离「这里放着 n 个合法的 T」还差什么？**3.2 处理的是「谁能在此刻访问」；这一节处理的是「此处是否已经有一个值」。差的那一步就是初始化边界，它同时决定了 `Drop` 能碰哪些位置（3.4）和优化器能改写哪些循环（3.6）。

::: preview 先抓住一件事

容量、长度和「已经有合法的 T」是三个不同的事实。**肯定**「这段存储可以安全读取」，要同时满足：位置在长度以内、该位置已被写入合法值、类型 `T` 的合法值条件成立；**否定**它只需一条：`with_capacity` 之后长度是 0。凡是从「分配了多少字节」直接推出「能读多少个 T」的写法，都跨过了这条边界。
:::

### 3.3.1 有存储不代表有 T

::: def 定义 3.3.1 · 容量与长度 capacity / len {#def-3.3.1}

**容量**（capacity）是分配器已经买下的存储元素数；**长度**（len）是当前被承认「此处存在合法 `T`」的元素数。`Vec::with_capacity(n)` 取得容量 `n`，但初始长度为 0——它没有提前构造 n 个 `T`。安全 `push` 先写入新值，再把相应位置纳入长度，这个顺序保证析构只触及已初始化元素。

:::

按[@def-3.3.1]，把容量当长度会破坏不变量，尤其是 `T` 包含引用、`Box`、`String` 或枚举的时候。任意零字节也未必构成合法 `T`：零不一定是合法引用，零不一定是合法 `NonZero` 值。因此「先全清零，之后再填」不能作为通用类型初始化方案；本章的 `zero_fill` 只用于 `u64`，因为对 `u64` 而言零是有效值（[@def-3.1.1] 谈的是责任归属，这里谈的是值合法性，两者不能互换）。

### 3.3.2 已初始化前缀

::: def 定义 3.3.2 · 已初始化前缀 initialized prefix {#def-3.3.2}

**已初始化前缀**指容器里从下标 0 到 `len − 1` 的那一段：长度以内，所有元素合法存在；长度以外，只能按容量存储处理，其中还没有 `T`。对泛型构建器，这个前缀非常有用：每成功构造一个元素就 `push` 一次，遇到 `Err` 时局部 `Vec` 自动销毁已有元素；构造器 panic 并展开时，清理路径同样处理已初始化前缀。

### 3.3.3 安全构建器用 Vec 维护状态

本包 `try_build` 用 `Vec` 维护初始化状态。它不需要 `MaybeUninit` 或手工 drop 计数——这是在加入 unsafe 前应先尝试的结构。

```rust
pub fn try_build<T, E>(
    n: usize,
    mut make: impl FnMut(usize) -> Result<T, E>,
) -> Result<Vec<T>, E> {
    let mut out = Vec::with_capacity(n);
    for i in 0..n {
        out.push(make(i)?);
    }
    Ok(out)
}
```

如果 `make(i)` 返回 `Err`，问号触发早退。此前的 `out` 仍由当前函数拥有，它在离开时被销毁。若全部成功，`out` 移动到 `Ok` 中，清理责任转移给返回值所有者——这正是[@def-3.1.1] 的责任转移，没有第二次销毁同一个 `Vec`。

::: ex 例 3.3.1 · 第三次成功之后失败，谁清理什么 {#ex-3.3.1}

调用 `try_build(5, make)`，其中 `make` 对下标 0、1、2 返回 `Ok`，对下标 3 返回 `Err("injected")`，下标 4 从未被调用。请写出退出时刻的四个数：容量、逻辑长度、已被丢弃的元素数、返回给调用方的 `Vec` 长度；并说明「余量里那两个位置」是否被读取过。

::: sol 解答

容量 5（`with_capacity(5)` 一次买下）；退出时逻辑长度 3——三次成功各 `push` 一个，按[@def-3.3.2] 这 3 个位置有合法 `T`；已被丢弃的元素数 3（局部 `Vec` 离开作用域时清理前缀）；返回值是 `Err`，没有 `Vec`，调用方拿不到半成品。余量下标 3、4 从未进入长度，也就从未被 `Drop` 或读取触及。整条路径不需要中央计数器去猜「大概创建过几个对象」，长度本身就是证明（对照 3.4 用计数对象把这条路径跑成测试）。

:::

:::

### 3.3.4 初始化中的 panic

构造某个元素可能在返回前 panic。这时该元素的内部局部对象由其自身展开路径处理；已经 `push` 进 `out` 的前缀由 `out` 处理；尚未开始构造的元素没有 `Drop` 责任。这种分层依赖每个组件维护自己的初始化不变量（[@def-3.3.2]），不需要中央计数器猜测「可能创建过多少对象」。

若使用 `panic = "abort"`，进程直接终止，不执行普通展开清理。本轮测试采用默认可展开测试配置，没有把 `catch_unwind` 的结果推广到 abort 构建。外部强制终止进程也不提供 Rust 析构保证。资源协议不能仅靠「Drop 总会运行」的口号——这句话在三份退出路径（正常返回、展开、abort）上分别要重述一遍（3.4 的[@def-3.4.1]）。

### 3.3.5 MaybeUninit 的正确角色

::: def 定义 3.3.3 · MaybeUninit {#def-3.3.3}

**`MaybeUninit<T>`** 是「一段保证合法、但不保证里面有 `T` 的存储」的类型包装。它允许表示尚未初始化的存储，但不自动使内部 `T` 合法；只有完整写入有效 `T` 后，才能按其契约取得 `T`。它也不会替你自动销毁已初始化的 `T`：复杂容器需要另外记录初始化进度与清理责任。

:::

按[@def-3.3.3]，`MaybeUninit` 是表达存储状态的工具，不是跳过证明的工具。本章组件不需要它，故没有为性能加入手工初始化代码。

::: ex 例 3.3.2 · 零能不能当初始化 {#ex-3.3.2}

三种 `T`：`u64`、`&u64`、`NonZeroU64`。`vec![0u64; n]` 的「先置零再覆盖」思路，哪些能直接套用，哪些不能？

::: sol 解答

`u64` 能：零是有效值，且它没有 `Drop` 责任。`&u64` 不能：零不是合法引用，被覆盖之前若发生 panic 或被读取，引用构造的有效性义务就已经被破坏——这与[@def-3.2.1] 的排他条件是两回事（3.7 证明表的「初始化」与「有效值」两行）。`NonZeroU64` 不能：它的合法值集合明确排除零，所以 `vec![0; n]` 这种表达在这两个类型上根本构造不出来。结论：清零只在「零是该类型的合法值」这个前提下才是初始化方案，这个前提要逐类型检查，不能由泛型 `T` 继承。

:::

:::

### 3.3.6 提前 set_len 与容量失败是两件事

如果先把 `Vec` 长度设为 n，再逐项写入，panic 可能使析构访问未初始化尾部；如果 `T` 有 `Drop`，后果尤其直接。即使 `T` 是整数，读取未初始化值也不是合法「随机数」。这种写法不能拿来与安全 `push` 比较速度；benchmark 不应执行 UB 来获得好看的下界。本章只比较两种合法 `u64` 初始化方式（3.6），性能差异用实际产物解释。

另一条容易混淆的边界：`try_build` 的 `E` 来自元素工厂，而 `Vec::with_capacity` 的分配失败并没有被转换成 `E`，它可能走标准库的分配失败处理路径。因此本组件并非完全可恢复 OOM 接口。若业务要求可恢复容量错误，应考虑 `try_reserve` 等受检接口并设计错误类型。不能因返回 `Result` 就宣称所有失败都已可恢复——错误类型的覆盖范围必须明确。

::: think 思考 · 「T 是 u64，所以先 set_len 再填也无所谓」 {#think-3.3.1}

有人论证：本节的清零反例只对「`T` 有 `Drop`」成立；`u64` 没有析构函数，所以先 `set_len(n)` 再逐项写入既不会 double free，也不会读到脏内存，可以放心用。这个前提哪里被绕过了？

::: sol 解答

绕过了「读取」这一步由谁发起。长度一旦被设成 n，容器上任何合法 API（迭代、切片、`black_box` 消费）都可以立即读到还没写入的位置；对 `u64` 这类 `Copy` 类型（[@def-3.1.2]），编译器有权把未初始化读取当作可优化的未定义值处理，而不是「随机但无害」。即使这一版恰好没人读，[@def-3.3.2] 的不变量也已经被破坏：此后每一步维护长度的代码都不再能信任长度。此外这条路径一旦成立，就必须在每个 `panic` 边界上重新证明「长度以内都已初始化」，而 `push` 结构把这个证明交给标准库。省下的写入次数属于机制假设，实测支持的是另一件事（3.6 保留了反直觉结果）。

:::

:::

### 3.3.7 初始化顺序影响可优化性

`push` 不断维护长度，保持每一步都可安全清理；已初始化整片切片的覆盖写入可以表达另一种循环。编译器可能对后者更容易做批量展开。这不表示安全性本身必然慢，它表示不同安全接口提供了不同的循环结构。优化工作应先改变合法结构，再评估是否真的需要 unsafe（3.6 的两个候选都合法）。

::: method 判定流程 · 选哪种初始化结构

**① 定合法值集合**：`T` 的零是否有效？有 `Drop` 吗？（[@ex-3.3.2]）

**② 定失败路径**：中途 `Err` 或 panic 时，谁清理已建前缀？答案是「`Vec` 的长度」就安全（[@def-3.3.2]）。

**③ 先试安全结构**：`push` 前缀 → `vec![0; n]` 覆盖 → `collect`，按①②筛掉不合法的。

**④ 用产物核对**：保留容量检查路径还是消除它，看生成的循环，不看源码直觉（3.6 的实际代码生成）。

**⑤ 只有④显示真实瓶颈、且安全候选都不够时**，才用[@def-3.3.3] 表达未初始化存储，并补上「长度以内的每个位置都已写入合法 `T`」的逐路径证明。

:::

### 3.3.8 小结与常见错误

**小结。**① 容量与长度是两个事实，`with_capacity` 只买到存储（[@def-3.3.1]）；② 已初始化前缀是 `Drop` 与 panic 清理的责任边界（[@def-3.3.2]、[@ex-3.3.1]）；③ 零初始化只在零是合法值时成立，`u64` 可以、引用与 `NonZero` 不行（[@ex-3.3.2]）；④ 提前 `set_len` 破坏不变量，不能拿来当性能候选（[@think-3.3.1]）；⑤ 工厂错误与分配错误是两类错误，返回 `Result` 不等于全部可恢复。下一节 [3.4 Drop、部分移动与错误展开](#sec-cpp-rust.1.3.4) 把这条前缀跑成可观察的计数测试。

::: errata 常见错误清单（3.3 节）

E-a **把 capacity 当成已初始化长度。**[@def-3.3.1]；先查 `len` 的实际值与来源。

E-b **提前 `set_len` 再逐项填充。**panic 会使清理读取未初始化尾部（[@think-3.3.1]）；先查失败路径上谁维护长度。

E-c **认为零字节适合初始化任意 T。**引用与 `NonZero` 排除零表示（[@ex-3.3.2]）；先查该类型的合法值集合。

E-d **把 `MaybeUninit` 当成「跳过证明」的开关。**[@def-3.3.3] 只表达存储状态；先查初始化进度记录在哪。

E-e **以为返回 `Result` 就覆盖所有失败。**分配失败没有转换成 `E`（3.3.6）；先查 `try_reserve` 一类受检接口。

E-f **用 `catch_unwind` 的结果推广到 abort 构建。**abort 不执行展开清理（3.3.4）；先查 `panic` 策略。

E-g **拿 UB 版本当下界参照。**benchmark 不应执行未定义行为（[@think-3.3.1]）；先确认两个候选都合法。

:::

::: method 即时自测 · 3.3

**第 2 题 · 辨析**　「`T` 没有 `Drop`，所以先 `set_len` 再填是安全的。」这句话漏了什么？

## 3.4 Drop、部分移动与错误展开 {#sec-cpp-rust.1.3.4}

本节回答一个问题：**当构造中途失败时，谁负责清理已经建好的那一段？**3.3 定义了已初始化前缀（[@def-3.3.2]）；这一节把那条边界跑成可观察的计数测试，再用归档 MIR 核对清理边确实存在，最后说明「有 `Drop`」为什么不等于「业务已完成」。

::: preview 先抓住一件事

销毁责任跟着初始化状态走，不跟着变量名走。**肯定**「这条失败路径清理干净」，要能指出前缀长度、每个位置的拥有者、以及展开与 abort 两种退出方式的差别；**否定**它只需一个反例：提前 `set_len` 之后 panic，析构就会读到[@def-3.3.1] 里那段「还没有 `T`」的余量。本节的测试就是把反例逐个排除。
:::

### 3.4.1 销毁责任跟随初始化状态

::: def 定义 3.4.1 · 销毁责任与 drop flag drop responsibility / drop flag {#def-3.4.1}

已初始化的值离开相应销毁作用域时，通常执行清理。移动后的旧位置不再拥有同一值（[@def-3.1.1]）；部分移动后，剩余已初始化字段仍有清理责任。编译器通过数据流分析确定哪些位置需要 drop：某些控制流需要运行时状态（俗称 **drop flag**，一个记录「这里是否还需要析构」的隐式标记）来区分，另一些状态在编译期就可消除。

:::

[@def-3.4.1] 不意味着每个 Rust 对象都隐藏着一个固定布尔字段。标志可能只出现在控制流中，也可能被优化完全删除；不能把它加进 `size_of` 表作为每对象固定开销——这与[@def-1.5.1] 的教训同构：把「名义上的开销」当成「实测的分母」，两边都是命名错误。三条退出路径要分别重述：正常返回把责任移给调用方，展开清理已建前缀，`panic = "abort"` 则不执行普通展开清理（3.3.4）。

### 3.4.2 字段顺序与局部变量顺序

::: def 定义 3.4.2 · 销毁顺序 drop order {#def-3.4.2}

**销毁顺序**指同一次退出里多个析构的先后：结构体字段通常按声明顺序销毁；块中局部变量一般按相反声明顺序销毁。这两条规则不能互换。临时值还受到具体表达式与 edition 规则影响。

:::

本地 S10 PDF 包含较旧的临时作用域描述，本章不把旧版本尾表达式规则直接套到 edition2024。性能相关的锁守卫应使用明确作用域或显式 `drop` 表达边界，不要依赖读者容易误判的复杂临时生命周期。

::: ex 例 3.4.1 · 两份日志为什么互为反序 {#ex-3.4.1}

集成测试用 `Logged` 对象在析构时把 `id` 推进一个 `Rc<RefCell<Vec<u8>>>`，观察到两串日志：两个局部对象那一组是 `[2, 1]`；一个元组的两个字段那一组是 `[3, 4]`。请判断这两串是否矛盾，并说明各自依据哪条规则。

::: sol 解答

不矛盾，它们是两个不同的销毁容器。局部变量 `_first_local`（id 1）与 `_second_local`（id 2）在同一块作用域退出，按[@def-3.4.2] 的**逆声明顺序**，后声明的 id 2 先析构，得到 `[2, 1]`。元组那一组是先 clear 日志、再 `drop(fields)`：两个字段按**声明顺序**析构，先 id 3 后 id 4，得到 `[3, 4]`。两者在同一次测试中分别验证，正是为了防止把局部逆序误记成字段逆序。记录用单线程 `Rc` 与 `RefCell`（借用冲突的语义见[@ex-3.2.3]），没有在 `Drop` 中跨线程打印或读取非同步计数；日志只用于功能验证，不用于性能采样。

:::

### 3.4.3 一个可计数的清理对象

测试使用 `Rc<Cell<usize>>` 记录 Drop 次数。它是单线程测试工具，没有使用非同步计数跨线程观察。每个 `Tracked` 销毁时增加一次计数；工厂返回 `Err` 时，已构造数量应等于 Drop 数量。

```rust
struct Tracked(std::rc::Rc<std::cell::Cell<usize>>);

impl Drop for Tracked {
    fn drop(&mut self) {
        self.0.set(self.0.get() + 1);
    }
}
```

这个 `Drop` 没有分配、I/O 或故意 panic，测试目标因此聚焦于生命周期。若 `Drop` 本身 panic，展开协议会更复杂：尤其是正在展开时再次 panic，可能导致终止。本章不靠双 panic 实验推断清理完整性。

### 3.4.4 Err 路径与 panic 路径的回归

```rust
let count = std::rc::Rc::new(std::cell::Cell::new(0));
let result = try_build(8, |i| {
    if i == 3 {
        Err("injected")
    } else {
        Ok(Tracked(std::rc::Rc::clone(&count)))
    }
});
assert!(result.is_err());
assert_eq!(count.get(), 3);
```

另一个测试在索引 4 触发断言 panic。`catch_unwind` 只用于测试观察；测试明确包裹 `AssertUnwindSafe`，原因是计数器状态通过内部可变性在展开前后被观察（内部可变性的边界见[@def-3.2.1]）。这不是宣称任意业务对象都满足异常安全——本测试的受控不变量只有前缀清理与计数。

```rust
let count = std::rc::Rc::new(std::cell::Cell::new(0));
let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
    let _: Result<Vec<_>, ()> = try_build(8, |i| {
        assert!(i != 4, "injected panic");
        Ok(Tracked(std::rc::Rc::clone(&count)))
    });
}));
assert!(result.is_err());
assert_eq!(count.get(), 4);
```

::: ex 例 3.4.2 · 两个计数为什么一个是 3 一个是 4 {#ex-3.4.2}

上面两段测试的 n 都是 8，注入点分别是「下标 3 返回 `Err`」和「下标 4 触发 panic」，实测计数分别是 3 与 4。请解释这两个数，并说明若把 `Tracked` 换成一个读取余量的类型会怎样。

::: sol 解答

`Err` 那组：下标 0、1、2 构造成功并 `push`，前缀长度 3（[@def-3.3.2]）；下标 3 返回 `Err`，`?` 早退，`out` 在离开时销毁这 3 个元素，`Tracked::drop` 各加一次，计数 3；下标 4 到 7 从未构造，没有责任。panic 那组同理，只是注入点变成「下标 4 的断言」——前 4 个（0–3）已进入前缀，所以计数 4。两组都没有读取容量余量：8 个位置的存储里有 3（或 4）个 `T`。如果类型改为在析构时读取未初始化尾部，就同时违反[@def-3.3.1] 与[@def-3.4.1]，测试也就失去意义。

:::

:::

### 3.4.5 实际 MIR 清理边

归档 MIR 包含 `try_build` 泛型函数的实际控制流。调用 `make` 的展开边通向 cleanup；cleanup 先 drop 局部 `Vec`，再 drop 工厂闭包；成功路径把 `Vec` 移动进返回 `Result`；`Err` 路径清理局部 `Vec` 后返回。可见的代表性片段如下，局部编号只属于本次生成。

```text
bb6 (cleanup): {
    drop(_3) -> [return: bb7, unwind terminate(cleanup)];
}
bb7 (cleanup): {
    drop(_2) -> [return: bb8, unwind terminate(cleanup)];
}
bb8 (cleanup): {
    resume;
}
```

这里 `_3` 是 `out`，`_2` 是工厂闭包。完整 MIR 还包含正常返回与 `Result` 判别。这个片段不证明所有泛型 `T` 的 `Drop` 都不会 panic；它证明本函数有对应清理责任的中间表示路径。[@ex-3.4.2] 给出行为证据，MIR 给出结构证据，二者说的是同一件事的不同层——与[@def-1.7.3] 分探索与确认同一精神：静态核对与动态测试都不能单独替代对方。

### 3.4.6 Drop 不保证业务完成

文件句柄被关闭，不等于业务数据已按持久化要求落盘。锁守卫释放，不等于事务提交成功。缓冲对象销毁，也不自动传回所有刷新错误。需要显式报告错误的收尾，应设计 `finish` 或 `close` 接口。`Drop` 适合不返回错误的兜底清理；不能把关键业务确认藏进无法返回结果的析构。

### 3.4.7 泄漏仍是内存安全的一部分

Rust 允许某些资源泄漏而不立即构成 UB。`mem::forget` 可以放弃析构责任；进程退出也未必逐个运行所有 `Drop`。因此 unsafe 接口必须在安全客户端可能泄漏值时仍不导致内存不安全——不能把「调用方最后肯定会 Drop」当成唯一内存安全前提。这与资源是否合理使用是两个层面的问题（这条义务在 3.7 证明表里单列一行「泄漏」）。

::: think 思考 · 「测试里计数正确，所以清理协议已经证明完毕」 {#think-3.4.1}

本节两个测试的计数分别是 3 和 4，`tests/contracts_more.rs` 的成功路径计数是 0→0→5，部分移动是 1→2。有人据此写下结论：「`try_build` 的清理责任已被完整证明。」这句话把什么当成了什么？

::: sol 解答

把「若干条具体控制流的结果」当成了「所有泛型实例与所有退出路径的证明」。测试可以验证某条具体控制流，但它不能穷举所有 panic 时机和所有 `T`：`T` 的 `Drop` 里可能再分配、可能 panic、可能通过 `Rc` 循环把责任留在堆上（3.4.7）。另外 `panic = "abort"` 构建根本没有展开路径可测（[@def-3.4.1]）。所以本章把测试、静态产物（[@ex-3.4.2] 对应的 MIR 边）与接口契约并列保留，任何一项都不能单独替代另外两项。

### 3.4.8 成功路径、部分移动与 mem::take

失败清理正确，不代表成功返回没有提前 Drop。补充集成测试 `tests/contracts_more.rs` 覆盖成功返回后的拥有者：构造五个 `Counted` 后计数仍应为零；把 `Vec` 再次移动到新绑定也不应触发元素 Drop；最后销毁新绑定，计数才变成五。

```rust
let count = Rc::new(Cell::new(0));
let values = try_build::<_, ()>(5, |_| {
    Ok(Counted(Rc::clone(&count)))
}).expect("all elements constructed");
assert_eq!(count.get(), 0);
let moved = values;
assert_eq!(count.get(), 0);
drop(moved);
assert_eq!(count.get(), 5);
```

这个测试不是测移动需要几条机器指令（[@def-3.1.1] 已经说明那不由源码决定），它验证语义责任没有被复制或提前消耗。`Counted` 与前面的 `Tracked` 采用相同计数方式，它们属于测试对象，不参与正式计时；新增测试没有修改 native-01 绑定的内核源码，补充测试日志单独放在 validation-01。

::: def 定义 3.4.3 · 部分移动与 mem::take partial move / mem::take {#def-3.4.3}

**部分移动**指只把一个聚合值中的某个字段移走，旧位置的其余字段仍是合法值并仍有析构责任。**`mem::take`** 把旧值移出并在原位置放入 `Default` 值，使旧位置立刻回到合法状态（对 `Vec` 就是空 `Vec`）。

:::

按[@def-3.4.3]，另一个测试从二元组中移动第一个资源：销毁第一个资源后计数为一，再销毁仍留在原位置的第二个资源，计数为二。编译器知道各个位置的初始化状态，程序不需要自行放置布尔标志（对照[@def-3.4.1] 的 drop flag 讨论）。

```rust
let count = Rc::new(Cell::new(0));
let pair = (
    Counted(Rc::clone(&count)),
    Counted(Rc::clone(&count)),
);
let first = pair.0;
drop(first);
assert_eq!(count.get(), 1);
drop(pair.1);
assert_eq!(count.get(), 2);
```

这里 `pair` 本身没有自定义 `Drop`。对于实现 `Drop` 的结构，直接移出字段有额外限制，原因是析构函数通常需要看到完整有效的 `self`；不能从元组例子推导「任意带析构结构都可随意拆走字段」。设计需要分离资源时，可以使用 `Option` 字段的 `take` 等安全模式，这样旧位置仍保持一个合法状态。

```rust
let count = Rc::new(Cell::new(0));
let mut original = vec![Counted(Rc::clone(&count))];
let moved = std::mem::take(&mut original);
assert!(original.is_empty());
drop(original);
assert_eq!(count.get(), 0);
drop(moved);
assert_eq!(count.get(), 1);
```

这种模式适合从可变 `self` 中转移拥有集合：它让调用者在失败或返回后仍能安全销毁原对象。但 `Default` 状态是否满足业务不变量，需要组件自行决定——空 `Vec` 在类型层面合法（[@def-3.3.1]），不代表业务上一定允许为空。因此安全合法性与领域事务一致性仍要分开审查。

::: method 判定流程 · 审查一份清理责任

**① 写出前缀**：这次退出时 `len` 是多少，哪些位置有合法 `T`？（[@def-3.3.2]、[@ex-3.4.1]）

**② 写出容器**：每个位置由谁负责销毁——局部变量、字段、返回值，还是 `mem::forget` 的例外（3.4.7）？

**③ 写出退出方式**：正常返回、展开、abort 三条都要各自说一遍（[@def-3.4.1]）。

**④ 看顺序**：字段声明顺序与局部逆声明顺序不能混用（[@def-3.4.2]）。

**⑤ 补静态核对**：展开边是否通向 cleanup，看归档 MIR（3.4.5），不只看测试通过。

**⑥ 分清事务**：需要报告错误的收尾走 `finish`/`close`，不要塞进 `Drop`（3.4.6）。

:::

### 3.4.9 小结与常见错误

**小结。**① 销毁责任由初始化状态决定，drop flag 是编译策略不是固定字段（[@def-3.4.1]）；② 字段按声明顺序、局部变量按逆序，两条规则不可互换（[@def-3.4.2]、[@ex-3.4.1]）；③ `Err` 与 panic 两条路径的前缀计数分别是 3 和 4（[@ex-3.4.2]）；④ 部分移动与 `mem::take` 让旧位置保持合法（[@def-3.4.3]）；⑤ 测试、MIR 与契约三者并列，谁也不能单独代表「已证明」（[@think-3.4.1]）。下一节 [3.5 benchmark一](#sec-cpp-rust.1.3.5) 把所有权差异换成实测数字。

::: errata 常见错误清单（3.4 节）

E-b **把局部逆序当成字段逆序。**两条规则分属不同容器（[@ex-3.4.1]）；先查是局部变量还是字段。

## 3.5 benchmark一：借用与显式克隆的真实工作差异 {#sec-cpp-rust.1.3.5}

本节回答一个问题：**多出来的那 0.1 ns/元素，究竟买下了什么？**第 1 章 1.5 节看的是「工作被删掉」的假结果；这一节看两个都在正常工作的实现——读现有切片与先复制再读——怎样在同一个输出下留下不同的资源账，并且这份差值能归因到哪一步。

::: preview 先抓住一件事

两个实现返回值相同，不等于它们做的是同一份工作。**肯定**「这条路径更贵是因为多了一份独立副本」，要能指出分配、复制、释放各自发生在哪个函数边界，并看到产物里真的存在这些调用；**否定**「这 0.1 ns 是借用检查的开销」只需一条事实：借用检查在编译期完成，被测循环里一个元素也没有检查过。
:::

### 3.5.1 待比较的问题与单位口径

同一份 65536 个 `u64`，求一个模加法和。`borrowed` 直接读取现有切片；`cloned` 先建立独立 `Vec`，再求和，最后释放。两者输出相同，但资源工作并不相同。本实验要量化「不需要独立拥有数据时，额外克隆路径的代价」，不是证明所有 clone 都应该删除（[@def-3.1.1]、[@ex-3.1.1]）。

::: def 定义 3.5.1 · 额外拥有副本路径与单位口径 {#def-3.5.1}

**额外拥有副本路径**指在被计时的工作核内部完成「分配一份独立存储 → 复制元素 → 使用 → 释放」的这一串资源动作，它的析构发生在函数返回之前，所以全部计入时间。**单位口径**指 `ns/输入元素`：批次墙钟时间除以「迭代次数 × 元素数」，它是一次工作核调用的平均元素成本，不是一次 `borrow` 语法操作的耗时——借用语法本身没有运行时开销（[@def-1.5.1] 的名义分母教训在这里同样适用：分母是元素数，不代表每个动作都真的执行过）。

:::

按[@def-3.5.1]，本节的统计口径沿用第 1 章[@def-1.5.2]：21 个批均值，均值、以 N−1 为分母的标准差、nearest-rank 的批 p50 与 p99。

### 3.5.2 完整入口

以下是 `src/bin/borrow.rs` 完整代码。每批执行 256 次工作核，公共夹具逐次校验返回值（[@def-1.3.1]）。

```rust
use foundations_lab::{Case, N, borrowed, cloned, data, run};
use std::hint::black_box;

fn main() {
    let input = data(N);
    let expected = input.iter().fold(0u64, |a, &b| a.wrapping_add(b));
    let mut cases = [
        Case {
            name: "borrowed",
            work: Box::new(|| borrowed(black_box(&input))),
            expected,
        },
        Case {
            name: "cloned",
            work: Box::new(|| cloned(black_box(&input))),
            expected,
        },
    ];
    run(&mut cases, 256, N);
}
```

实际工作核如下。独立 `Vec` 不会逃出 `cloned`，因此它的析构发生在工作核返回前；该分配、复制和释放都计入时间。

```rust
#[inline(never)]
pub fn borrowed(input: &[u64]) -> u64 {
    sum_iter(std::hint::black_box(input))
}

#[inline(never)]
pub fn cloned(input: &[u64]) -> u64 {
    let owned = input.to_vec();
    sum_iter(std::hint::black_box(&owned))
}
```

| borrowed | 0.058851898 | 0.000404976 | 0.058824778 | 0.059892774 |
| cloned | 0.159020461 | 0.002093374 | 0.158538461 | 0.166441023 |

`cloned` 减 `borrowed` 的配对均值为 0.100168563（[@def-1.4.2]）。bootstrap 区间为 [0.099374896, 0.101163745]（[@def-1.6.2]）。本轮支持额外拥有副本路径更贵；差值包含分配、复制、释放和缓存状态变化。不能单独命名为「借用检查节省了 0.1 ns」——借用检查并没有在被测循环中逐元素执行。

### 3.5.4 代码生成与 profiler 支持

`cloned` 的实际 IR 保留分配调用，随后有 `llvm.memcpy`，之后调用求和核并释放存储；`borrowed` 则转入相同求和核。因此两条路径的真实工作差异与接口设计一致，不是编译器把 clone 完全删除后偶然测出不同噪声（对照[@def-1.1.1] 的反例：那里才是「被删空」）。

独立 `sample-borrow.txt` 看到 `borrowed` 进入 `sum_soa`，也看到 `cloned` 及其求和、分配器相关路径。

**这里有个陷阱值得当场说清**：源码里 `borrowed` 调的是 `sum_iter`（`src/lib.rs:127`），可采样栈与库汇编的调用点（`codegen/*.s` 第 800、844、1043、1296 行都是 `bl …sum_soa`）都指向 `sum_soa`——`sum_iter` 与 `sum_soa` 的函数体逐字相同，链接期只留了一份，符号名因此会「张冠李戴」；机制是推断（本轮没有跑 `nm`/`dyld_info` 去核地址），可观察事实是确定的：**采样符号名不等于源码调用边**。一部分复制工作可能以内联或库函数形态出现，不能仅凭采样符号名缺失就断言没有复制——应结合实际 IR 中的 memcpy 与调用点。采样不进入正式 21 批统计，本章不把它换算成稳态百分比（[@def-1.7.3]：探索性证据不冒充确认性结论）。

::: think 思考 · 「输出相同，所以差值就是写法成本」 {#think-3.5.1}

等价性测试覆盖多个长度，它验证 `borrowed` 与 `cloned` 返回相同值。有人据此写下：「两者做的是同一份工作，只是写法不同，所以 0.100168563 是『克隆这种写法』的成本。」这个前提绕过了什么？

::: sol 解答

绕过了[@def-1.6.1] 的资源口径维度。相同输出只保证算术语义相同，不保证被执行的机器动作相同：`cloned` 多做一次分配、一次 524288 字节的复制和一次释放（[@def-3.5.1]）。所以这个差值应当读成「额外拥有副本路径的代价」，而不是「某种语法的价格」——换成 `Arc`、换成分块复制、换成不需要求和的消费者，差值就不再是同一个数。把它写成「写法成本」还会掩盖另一个可能：如果应用本来就需要独立副本，这条路径就是必要工作，不是可以「改造掉」的开销。

:::

:::

### 3.5.5 安全性能回退与改造判断

假设接口只需同步读取输入，为了绕开生命周期困惑，调用方先 `to_vec` 再传给求和函数。这在安全 Rust 中完全合法，它却引入不必要的独立拥有存储——本实验真实重现了这条回退路径。修复是把接口改为借用切片，而不是写裸指针（3.7 说明后者要补齐多少义务）。

如果结果需要在输入销毁后继续使用，前提就变了：此时独立副本可能是正确设计（3.1.4 判定流程的第②条）。不能照搬本表删除 clone 造成生命周期错误，应把异步持有、共享计数或拥有转移纳入新实验。

::: method 判定流程 · 这次 clone 该不该改

**① 定位粒度**：这次复制每秒被执行几次？启动时一次与每请求一次差三个数量级（[@ex-3.5.2]）。

**② 查生命周期**：结果是否要活过输入（3.1.4）。要活过就别改，改成借用只是把复杂度搬进调用链。

**③ 找转移的可能**：能不能把已有 `Vec` 直接交出去（[@def-3.1.1]），或用 `mem::take` 让旧位置合法（[@def-3.4.3]），而不是复制一份再丢掉原份。

**④ 看产物**：确认改动真的去掉了分配与 memcpy，而不只是换了写法（3.5.4）。

**⑤ 用同口径复测**：保持 21 批、配对顺序与分母不变，再按[@def-1.7.2] 判三态；换分母就是新实验（[@def-1.5.1]）。

:::

### 3.5.6 测试覆盖、未覆盖与应用方式

等价性测试覆盖多个长度，验证 `borrowed` 与 `cloned` 返回相同值。没有测多线程共享输入，没有测 `Arc` 计数，没有测复制与其他工作并行重叠，也没有对分配、复制、释放逐项计时——**本节没有采集**这些量，因此本章不能给出 `Arc` 与借用的通用成本排序（[@def-1.7.3]）。

如何把结果应用到业务：先定位 clone 发生的粒度；再判断副本的生命周期是否确实独立；然后检查能否转移所有权而不是复制；最后测完整调用链与内存峰值。只在 clone 确实位于热路径且不需要独立副本时，借用改造才有明确价值。

### 3.5.7 小结与常见错误

**小结。**① 单位是 ns/输入元素，描述的是工作核调用，不是语法操作（[@def-3.5.1]）；② 配对均值 0.100168563、区间 [0.099374896, 0.101163745] 不跨零，方向可判（[@def-1.6.2]、[@ex-3.5.2]）；③ 差值属于额外副本路径，不能命名为借用检查（[@think-3.5.1]）；④ IR 与采样只提供机制支持，成分占比没有采集（3.5.4）；⑤ 改造价值取决于粒度与生命周期，不取决于本表的比值（[@ex-3.5.2]）。下一节 [3.6 benchmark二](#sec-cpp-rust.1.3.6) 用另一组数据否证一个流行直觉。

## 3.6 benchmark二：push并不自动胜过置零再填充 {#sec-cpp-rust.1.3.6}

本节回答一个问题：**一个只数了源码写入次数的直觉，被实测推翻时应该保留什么结论？**3.5 的量级差来自「多做了一份工作」；这一节的量级差来自「两种都合法的结构，编译器拿到的循环形状不同」，而方向恰好和常见直觉相反。

::: preview 先抓住一件事

「`with_capacity` 加 `push` 没有提前清零，所以必然更快」这个推理只数了源码表面的写入次数。**肯定**它，要假设循环控制、长度维护与优化器可证明的范围都不起作用；**否定**它只需一组数据：本轮 `zero_fill` 的均值只有 `push` 的约 1/5.7，配对差值区间整体在零的同一侧。保留反直觉结果，比把它调成符合直觉更有价值。
:::

### 3.6.1 一个应被数据否定的直觉

常见直觉是 `with_capacity` 加 `push` 没有提前清零，所以必然更快。这个推理只数了源码表面的写入，它忽略循环控制、长度维护与优化器能证明的范围，也忽略分配器与后端可能采用不同实现路径（[@def-3.3.1] 已经说明容量与长度是两个事实，但没说哪个结构更好优化）。本章不把这种直觉当结论，而是用两种合法初始化方式实际比较。

::: def 定义 3.6.1 · 两种合法初始化：push 与 zero_fill {#def-3.6.1}

**push 结构**指 `Vec::with_capacity(n)` 后逐项 `push`：每一步长度都被维护，因此[@def-3.3.2] 的前缀始终成立。**zero_fill 结构**指 `vec![0u64; n]` 先构造 n 个合法零 `u64`（长度一次到位、全部位置都有合法值），再用覆盖循环逐位置写入最终值。两者最终产生相同长度与值序列，且都不越[@def-3.3.1] 的边界；差别在于编译器看到的循环形状不同。

:::

按[@def-3.6.1]，「先清零」在这里不是违规操作，因为 `u64` 的零是有效值——这个前提只对 `u64` 成立（[@ex-3.3.2]），泛型场景另说（3.6.7）。

### 3.6.2 两种安全实现

二者都把完整结果切片交给 `black_box`，随后用相同求和核消费；整个 `Vec` 创建与销毁都计入时间（口径与[@def-3.5.1] 同构）。

```rust
#[inline(never)]
pub fn init_push(n: usize) -> u64 {
    let mut out = Vec::with_capacity(n);
    for i in 0..n {
        out.push((i as u64).wrapping_mul(17));
    }
    sum_iter(std::hint::black_box(&out))
}

#[inline(never)]
pub fn init_zero(n: usize) -> u64 {
    let mut out = vec![0u64; n];
    for (i, value) in out.iter_mut().enumerate() {
        *value = (i as u64).wrapping_mul(17);
    }
    sum_iter(std::hint::black_box(&out))
}
```

### 3.6.3 完整入口

`src/bin/initialization.rs` 独立编译。每批重复 64 次，N 仍为 65536。输入 n 经过 `black_box`，避免把固定长度完全烘焙进所有调用上下文（[@def-1.3.1]）。

```rust

```

| push | 1.153849851 | 0.019135814 | 1.152266979 | 1.194040060 |
| zero_fill | 0.201331729 | 0.005930436 | 0.201612711 | 0.218312025 |

`zero_fill` 减 `push` 的配对均值为 −0.952518123（[@def-1.4.2]）。bootstrap 区间为 [−0.959926571, −0.945401044]（[@def-1.6.2]）。当前结果明确不支持「push 必然更快」的直觉。我们保留它，而不是改参数直到出现预期排序（[@def-1.7.3]）。

::: ex 例 3.6.1 · 直觉、数据与结论三者优先级 {#ex-3.6.1}

1. 本轮 `push` 均值是 `zero_fill` 的几倍？
2. 区间 [−0.959926571, −0.945401044] 跨零吗？能判方向吗？
3. 把配对均值换算成「一次 `init_push` 调用比 `init_zero` 多花多少时间」。
4. 能不能据此写「初始化应该永远用 `vec![0; n]`」？

::: sol 解答

1. 1.153849851 ÷ 0.201331729 ≈ 5.73 倍。
2. 不跨零：上下界都是负数，本轮证据支持 `zero_fill` 更快（[@def-1.6.2] 的区间只覆盖本次运行的抽样波动）。
3. 0.952518123 ns/元素 × 65536 元素 ≈ 62,424 ns，即一次调用约多花 62.4 微秒；按[@def-3.6.1]，两个 case 的 n 相同，所以这个换算在两种结构之间是对齐的。一批 64 次调用约 4.0 毫秒（62,424 × 64 ≈ 4.0 × 10⁶ ns）。
4. 不能。这个结论只在「`T` = `u64`、零合法、消费者要求完整切片、本机本轮构建」这四个条件上成立；`T` 换成有 `Drop` 或非零排除的类型，`vec![0; n]` 根本构造不出来（[@ex-3.3.2]）。

:::

:::

::: ex 例 3.6.2 · 这条结论离「可发布判定」还差什么 {#ex-3.6.2}

设业务在评审前写下 B = 0.5 ns/最终元素（**假想约定**，仅为演示 [@def-1.7.2] 的形状，不是本章采集量）。按本节差值 −0.952518123 与区间 [−0.959926571, −0.945401044] 判定「改用 `zero_fill` 是否可发布」，并列出这条判定还没覆盖的两类风险。

::: sol 解答

把回归量定义为「新结构 − 旧结构」，则 L = −0.959926571、U = −0.945401044，`U ≤ B` 成立且远在预算之内 → 接受（[@def-1.7.2]）。两类未覆盖的风险：其一，区间只覆盖本次运行，不含编译器版本与机器差异（[@def-1.6.2]），换构建要重测；其二，判定只覆盖时间，内存代价没有逐项采集（3.6.6），而 `vec![0; n]` 与 `with_capacity` 的分配行为并不相同——时间、内存、正确性是并列约束，不能互相覆盖（[@def-1.7.1]）。

### 3.6.5 实际代码生成

`push` 循环中仍可见容量比较；容量不足的 `grow_one` 路径也保留；正常每次 `push` 还更新逻辑长度。虽然预先申请了 n 容量，当前代码生成没有消除全部相关路径。这是一项当前编译器观测，不是 `Vec::push` 永远无法优化的语言定理（对照[@def-3.2.2]：属性与产物都是版本化观测）。

`zero_fill` 中保留 `alloc_zeroed` 调用；覆盖循环可见成对展开写入；本轮汇编中有 `stp` 存储序列。不要把它不加区分地称为「所有操作都 SIMD 化」——成对标量存储与向量存储不是同一回事（这是本节没有采集的区分依据之一：没有事件计数，只能描述结构与汇编可见的形式）。这里能确定的是：覆盖循环采用了不同的展开结构。

::: def 定义 3.6.2 · 成分归因与机制解释 {#def-3.6.2}

**机制解释**指用产物里可见的结构差异（保留的容量路径、`alloc_zeroed`、成对展开写入）说明「差值与哪一种循环形状相容」。**成分归因**指把差值拆成「清零占多少、覆盖占多少、分配占多少」。[@def-3.6.2] 的区分标准是证据：前者有静态产物支持，后者需要逐项计时或流量采集。

:::

### 3.6.6 不能过度归因

本轮没有逐成分计时分配、清零、覆盖与求和，也没有采集真实内存流量，因此不能精确分配每项贡献——**本节没有采集这些量**。保留的容量路径与展开写入支持一种机制解释（[@def-3.6.2]），它不证明差值全部由某一个分支造成。若要确认，应设计只改变一个合法结构的后续实验（[@def-1.7.3] 的确认性一侧），而不是在同一批数据上换统计量。

### 3.6.7 为什么不加入未初始化 unsafe 版本

因为本章目标是先识别安全结构之间的优化空间。引入 `MaybeUninit`（[@def-3.3.3]）或手工 `set_len` 会增加初始化与 panic 证明（[@think-3.3.1]）。如果安全版本已足够快，这份复杂度可能不值得。只有在正确匹配业务且安全候选不足时，才有理由评估 unsafe；即使评估，也必须先完成完整清理与有效值证明（3.7 的证明表）。不能把 UB 版本作为「理论最快」参照（[@think-3.5.1] 同样禁止把不同资源工作混成一个「写法成本」）。

::: think 思考 · 「补一个 unsafe 版本才知道安全代码的距离」 {#think-3.6.1}

有人提议：再加一个「`MaybeUninit` + 手工 `set_len` + 逐项写入」的第三 case，这样才能说清 push 慢的 62.4 微秒里有多少是安全性的税。这个提议的前提哪里站不住？

::: sol 解答

前提站不住在两点。第一，如果第三 case 在长度抬高后允许任何一次读取未初始化位置，它就是[@think-3.3.1] 禁止的写法，benchmark 不应执行 UB 来获得好看的下界；要合法就必须逐路径补证明，而那已经不是「一行改动」。第二，本轮证据已经说明安全性不是这里的瓶颈：`zero_fill` 同样是安全代码（长度一次到位、每个位置都有合法值），却比 `push` 快约 5.7 倍，所以「安全 vs 快」这个轴解释不了差值——要改的是循环结构，不是安全性（[@def-3.6.1]）。真要拆分，就得设计只改变一个合法结构的对照实验，而不是引入不合法的那个。

:::

:::

### 3.6.8 泛型边界与更贴近业务的下一步

`u64` 的零初始化合法，引用、`NonZero` 或复杂资源类型未必如此（[@ex-3.3.2]）；泛型 `T` 也可能有昂贵 `Drop`（[@def-3.4.1]）。本章 `try_build` 因此采用安全 `push` 维护前缀（[@def-3.3.2]）。性能测试和正确性组件选择了不同优先级，这并不矛盾：一个用于解释数值核，一个用于维护泛型失败清理。

更贴近业务的下一步：若数据来源本来就是迭代器，可以增加 `collect` 候选；若有可复用缓冲，可以测 `clear` 后重新填充；若最终消费者允许流式处理，可以不保存全部元素。每种方案改变的资源生命周期不同（[@def-3.1.1]），应分别报告，而不是寻找一个通用「初始化最快写法」。本轮只完成当前两种合法实现的真实比较。

::: method 判定流程 · 要不要加一个初始化候选

**① 合法性检查**：候选是否满足[@def-3.3.1]——长度以内的每个位置都有合法 `T`？不合法直接出局（[@think-3.6.1]）。

**② 语义对齐**：n、值序列、消费者与分母是否与现有两个 case 一致（[@def-1.6.1]）？

**③ 单因素**：是否只改一个合法结构？同时换布局或换算法就分不清归因（[@def-3.6.2]）。

**④ 同协议采集**：21 批、配对交替、独立归档，不覆盖 native-01（[@def-1.4.2]）。

**⑤ 报告边界**：写清新候选改变的资源生命周期与未采集的成分占比（3.6.6）。

:::

### 3.6.9 小结与常见错误

**小结。**① 两种结构都合法，差别在编译器拿到的循环形状（[@def-3.6.1]）；② 本轮 `zero_fill` 快约 5.73 倍，差值区间不跨零，方向可判但仅覆盖本次运行（[@ex-3.6.1]、[@ex-3.6.2]）；③ 静态产物支持机制解释，不支持成分归因，后者没有采集（[@def-3.6.2]）；④ 不能用 UB 版本当参照（[@think-3.6.1]）；⑤ 结论不迁移到泛型 `T`（[@ex-3.3.2]）。下一节 [3.7 unsafe、来源与有效引用的证明清单](#sec-cpp-rust.1.3.7) 处理「什么时候才值得把证明担到自己身上」。

::: errata 常见错误清单（3.6 节）

E-a **只数写入次数预测初始化速度。**循环控制与展开结构同样入账（[@ex-3.6.1]）；先查产物里的容量路径。

E-b **把「push 慢」写成「安全性慢」。**同为安全代码的 `zero_fill` 快得多（[@think-3.6.1]）；先区分结构与安全性。

E-e **把 u64 结论推广到任意 T。**零对引用与 `NonZero` 不合法（[@ex-3.3.2]）；先查类型合法值集合。

E-f **加一个 unsafe 版本当下界。**benchmark 不应执行 UB（[@think-3.6.1]）；先证明合法性。

E-g **改参数直到出现预期排序。**这是选择偏差（[@def-1.7.3]）；先固定协议再采集。

## 3.7 unsafe、来源与有效引用的证明清单 {#sec-cpp-rust.1.3.7}

本节回答一个问题：**把责任从标准库转到自己身上，究竟要补齐哪几项互相独立的义务？**3.3 与 3.4 展示了安全结构怎样替我们维护初始化前缀与清理责任；一旦改用裸指针，这些替我们说话的东西全部消失，剩下的是一张必须逐项填写的证明表。

::: preview 先抓住一件事

`unsafe` 转移责任，不取消责任。**肯定**「这个封装是 sound」，要为任意符合公开接口的安全客户端论证全部义务——包括 panic、提前返回与泄漏；**否定**它只需构造出一个能让安全客户端触发 UB 的方法组合，一行示例调用合法并不能证明。地址、来源、有效值、别名、同步是五个互相独立的维度，任何一项被另一项「顺带推出」都是漏证。
:::

### 3.7.1 unsafe 转移责任，不取消责任

::: def 定义 3.7.1 · unsafe 边界与安全封装 {#def-3.7.1}

**unsafe** 允许执行某些编译器无法自动证明安全的操作，它不允许 UB（未定义行为，undefined behavior）。**安全封装**的额外义务是：任意符合公开接口的安全客户端都不会触发 UB。只证明示例调用合法不够——公开方法组合、panic、提前返回与泄漏都要考虑。

:::

按[@def-3.7.1]，unsafe 边界通常要比一行解引用大得多：它包含所有能让这块存储进入非法状态的公开方法。泄漏也要算进来——`mem::forget` 之后旧位置仍可能被内部结构引用（3.4.7），所以不能把「调用方最后肯定会 `Drop`」当成内存安全前提（[@def-3.4.1]）。

### 3.7.2 地址不是完整指针

::: def 定义 3.7.2 · 地址与来源 address / provenance {#def-3.7.2}

**地址**是指针的数值位置。**来源**（provenance）是围绕这个数值的语义约束：它表达允许访问的空间、时间和可变性范围。当前 `std::ptr` 文档把两者分开讨论。一块存储释放后，即使另一分配复用了同一地址，也不能凭旧地址访问新对象；地址相等不能延长生命周期，地址连续也不能合并两次独立分配（时间维度与[@def-3.2.3] 的访问阶段同源）。

:::

[@def-3.7.2] 是语义约束，不意味着每个普通指针都在运行时携带一个额外堆对象。它使编译器与检查工具能够表达访问是否合法。不要用「机器寄存器只有地址位」否定语言抽象机要求——优化本来就依赖语言级前提（这正是[@def-3.2.2] 里参数属性能够存在的原因）。

### 3.7.3 Strict Provenance API

`addr` 提取地址部分；`with_addr` 保留原指针的来源并改变地址；`map_addr` 用于对地址做变换同时保留来源。这些 API 不自动证明新地址可解引用，仍需检查边界、对齐、有效值与别名。如果新地址超出原分配，保留来源也不会创造新访问权限（[@def-3.7.2]）。

普通指针转整数再转回的语义属于更复杂的 exposed provenance 讨论。当前文档明确承认其语义不如 Strict Provenance 清晰。本章不把所有整数往返一概称为立即 UB，也不把它当成可忽略来源的万能捷径；优先保留真实来源指针，避免不必要的重建歧义。

::: ex 例 3.7.1 · 给一行解引用填满证明表 {#ex-3.7.1}

场景：某函数把一个 `Vec<u64>` 的 `as_ptr()` 结果存进结构体字段，随后在另一处对该地址解引用（元素数仍记为 65536，输入区 524288 字节，与本节讨论的 borrow 数据同量级）。请按[@def-3.7.1] 逐项填写证明表，并指出最少需要补哪两条才谈得上合法。

::: sol 解答

逐行填写（「本轮证据」指本章文件里已有的材料）：

- **所有权**：`Vec` 仍是拥有者（[@def-3.1.1]），字段里的地址不拥有任何东西——缺口：谁负责最终释放没有写进类型。
- **空间**：范围应覆盖从 `ptr` 起 65536 个 `u64`，属同一次分配——缺口：没记录范围长度的来源。
- **时间**：取决于解引用发生在 `Vec` 被 drop 之前还是之后——地址相等不延长生命周期（[@def-3.7.2]）。
- **对齐**：`u64` 要求 align 8，切片本身由分配保证——缺口：保存成裸地址后无法再证明绝对地址对齐。
- **初始化**：长度以内的元素都已写入合法 `u64`（[@def-3.3.1]）——缺口：若原 `Vec` 扩容，前缀位置整体改变。
- **别名**：需论证期间是否另有可变路径（[@def-3.2.1]）。
- **同步**：单线程场景，无并发冲突；跨线程则需另给协议。
- **销毁**：`Vec` 析构负责全部元素——缺口：字段里的旧地址届时成为悬垂值。
- **panic**：本例无构造过程，但半构建路径要按 3.4 单独论证（[@def-3.4.1]）。
- **泄漏**：客户端 `mem::forget` 后地址仍在但没有拥有者——这是[@def-3.7.1] 明列的义务。

最少要补的两条是「时间」和「别名」：前者要求证明解引用时存储仍存活（扩容、`mem::take`、移动都会改变事实，[@def-3.4.3]），后者要求证明这一段时间内没有别的路径写入同一存储（[@def-3.2.1]）。其余各项在这个具体场景里可以标注「不适用」，但必须逐行写明为什么不适用——空白不等于通过。

:::

:::

### 3.7.4 创建引用是立即承担义务

把裸指针写成引用时，要同时满足非空、对齐、可解引用、指向已初始化的有效值、不违反别名规则这几项义务；[@ex-3.7.1] 的证明表把其中几项分成了独立行（空间、时间、对齐、初始化、别名、同步），逐行核对用它，不要用本句的合并写法回查。不能说「先创建引用，之后不会真正读取」——义务在形成引用时已经相关，未使用的引用也不是豁免。零尺寸访问与零长度切片还有各自的具体 API 要求，不能把允许某种零字节裸操作的例外推广到任意引用构造。

::: think 思考 · 「这个指针来自 Vec，所以肯定安全」 {#think-3.7.1}

有人这样论证合法性：地址来自本包的 `data(N)`，也就是来自一个 `Vec<u64>`，`Vec` 的存储是刚分配的、对齐良好的，所以任何时刻解引用它都成立。这个推理跳过了什么？

::: sol 解答

跳过了三件事。第一，「来自 `Vec`」是一次性事实，不是持续状态：`Vec` 会被移动、扩容、`mem::take` 走内容或析构（[@def-3.1.1]、[@def-3.4.3]、[@def-3.4.1]），地址相等不能延长来源的有效时间（[@def-3.7.2]）。第二，`Vec` 的存储只保证「长度以内是合法 `T`」，容量余量里没有 `T`（[@def-3.3.1]），所以可解引用范围要单独论证。第三，合法性还取决于此刻谁在访问：同一块存储上若有别的可变路径，就破坏[@def-3.2.1] 的排他前提。这三条分别落在「时间」「初始化/空间」「别名」三行，任何一行都不能由「来自 Vec」推出——这正是 3.11 出口检查要求逐行填写、不接受一句带过的原因。

:::

:::

### 3.7.6 UnsafeCell 的边界与指针算术

`UnsafeCell` 允许共享引用之下的特定内部可变性。它不使数据竞争合法，也不允许随意产生多个互相冲突的可变引用（[@def-3.2.1]）；它还可能影响外围类型的布局优化（比如用不到的有效位模式（内存里各比特的具体排列）被拿出来当 niche（类型编码里剩下来、轮不到合法值的空位）用），因此把一个 `T` 包进 `UnsafeCell` 不能被视为纯粹「无表示影响」的动作。本章没有为它写通用 niche 推断——**本节没有采集**任何布局对比数据。

指针算术要与访问分开讨论。某些 wrapping 指针运算可以暂时得到范围外地址，这不代表该地址可以读写；受 in-bounds 约束的运算还有更严格前提。具体 API 的 Safety 段必须逐项阅读，不能根据函数名里有 `wrapping` 就推断最终解引用安全。回到原范围也不能修复已经发生的非法访问。

### 3.7.7 跨进程共享与工具边界

跨进程映射常使用偏移而不是持久保存本进程裸地址。即使两个进程都能看到相同字节，Rust 对象生命周期也不是自动共享：锁、初始化与版本协议需要另外设计。`Send` 与 `Sync` 描述线程相关约束，不证明跨进程对象格式（对照证明表「同步」行的错误替代）。本章不实现共享内存容器，这里只指出来源与访问权需要与实际映射方式协调（[@def-3.7.2]）。

工具能证明什么，也有边界。Miri 可以发现其支持模型下的多种非法访问，但不能替代所有外部代码、硬件与并发协议证明；ASan、TSan 和 Loom 也各有覆盖范围。没有执行这些工具时，不能在交付里列为通过。本轮只有普通测试、clippy、代码生成与 macOS `sample`（3.5.4 的采样就属于这一类）——我们保留明确限制，不用工具名为 unsafe 背书。

### 3.7.8 为什么本包保持全安全

当前六个实验不需要 unsafe 就能回答问题。`ByteRegion` 利用切片与可变 `self` 表达重用限制；`try_build` 利用 `Vec` 表达初始化前缀（[@def-3.3.2]）；`copy_add` 利用 `split_at_mut` 提供不相交输入（[@ex-3.2.1]）。这些结构把证明交给成熟安全接口。底层标准库内部可能使用 unsafe，但本包没有新增 unsafe 边界。这比为了展示「底层能力」而写一个未经证明的分配器更合适（[@def-3.7.1]）。

::: method 判定流程 · 一段裸指针代码能不能进主干

**① 先试安全等价物**：`split_at_mut`（[@ex-3.2.1]）、`Vec` 前缀（[@def-3.3.2]）、`mem::take`（[@def-3.4.3]）能不能表达同一约束？能就不用补证明。

**③ 摊开客户端组合**：任何公开方法序列、panic、提前返回、`mem::forget` 都不能造出 UB（[@def-3.7.1]、[@think-3.7.1]）。

**④ 声明工具边界**：没跑 Miri/TSan/Loom 就不写「已验证」（3.7.7）。

**⑤ 检查性能理由**：只有当安全候选确实不足、且瓶颈已由实测支持时才扩边界，不能用 UB 版本当下界（[@think-3.6.1]）。

**⑥ 留拒绝条件**：能造出悬垂引用、能让长度覆盖未初始化尾部、把整数地址当唯一证据的，一律拒绝（3.8 的拒绝条件）。

:::

### 3.7.9 小结与常见错误

**小结。**① unsafe 把证明责任转给作者，不取消任何义务（[@def-3.7.1]）；② 地址与来源是两个对象，复用同一地址不等于延长有效时间（[@def-3.7.2]）；③ Strict Provenance API 只保留来源，不证明新地址可解引用；④ 引用在形成时就承担义务（[@ex-3.7.1]）；⑤ 证明表的十行互相独立，跨行借用证据等于漏证（[@think-3.7.1]）。下一节 [3.8 自引用、Pin 与资源协议的组合边界](#sec-cpp-rust.1.3.8) 处理「地址稳定性」这条独立维度。

## 3.8 自引用、Pin与资源协议的组合边界 {#sec-cpp-rust.1.3.8}

本节回答一个问题：**地址稳定、线程归属和业务许可这三件事，为什么不能由同一个机制负责？**3.7 的清单里「时间」与「别名」是两行；这一节看第三条独立轴——对象地址会不会变——以及它和所有权、并发、事务各自管住哪一段。本章没有实现自引用 unsafe 类型，因此本节没有运行数据可采集，只给出边界与判定条件。

::: preview 先抓住一件事

`Pin` 管「这个值此后不再按普通方式移动」，`Send`/`Sync` 管「谁能把它交给另一个线程」，`Drop` 管「谁负责收尾」。三者互不蕴含。**肯定**「一处内部自引用安全」，要同时证明最终位置已确定、投影方法不会移出被 pin 字段、析构期间约定仍成立；**否定**只需找出一个能让安全客户端把值移走或替换掉的公开方法。
:::

### 3.8.1 地址稳定性是独立维度

::: def 定义 3.8.1 · 地址稳定与 Pin address stability / Pin {#def-3.8.1}

**地址稳定**指「在被依赖的这段时间里，这个值的地址不会变」。所有权转移不保证地址稳定（[@def-3.1.1] 说的是堆载荷身份，移动内联对象仍会换地址，见 3.1.5）；借用约束也不自动给一个对象永久固定地址。**`Pin<P>`** 表达「被指向的值在 pin 之后不再按普通方式移动」这一约束，它不是普遍禁止移动一切句柄：移动 `Pin` 包装的指针句柄，与移动被指向的值，要分开谈。

:::

`Box` 使载荷位于独立分配中，移动 `Box` 句柄通常不移动载荷。但仅有 `Box` 并不禁止通过合法接口移出或替换内部值（[@def-3.4.3] 的 `mem::take` 就是一个合法替换）；若要依赖永久地址关系，还需要 `Pin` 及相应类型约束。构造自引用也要在最终位置建立内部指向——不能先在栈上创建内部指针，再搬到 `Box` 后假定它自动修复。

::: ex 例 3.8.1 · 这个 Box 够不够保证地址稳定 {#ex-3.8.1}

一个结构体有两个字段 `a: u64` 与 `p: *const u64`，`p` 指向同一结构体里的 `a`。有人把它 `Box::new` 起来，认为「`Box` 的载荷在堆上，地址不会再变，所以 `p` 永远有效」。请按 3.1.5 的三种地址与[@def-3.8.1] 判定这句话，并列出两条仍然缺失的证明。

::: sol 解答

判定不成立。`Box` 保证的是「移动句柄不动载荷」这一条，它没有排除三种其它变化：构造顺序（先在别处建好内部指针再搬进 `Box`，指向的就是旧位置）、合法替换（把载荷整体移出或 `mem::take`，载荷地址变了而 `p` 还留着旧值）、以及析构期间（[@def-3.4.1]：收尾时 `p` 与 `a` 的先后顺序要单独论证）。两条缺失证明：① 内部指向必须在最终位置建立，之后不再移动该值（这正是[@def-3.8.1] 要求 `Pin` 的理由）；② 公开方法不能给安全客户端任何「把值移走或替换掉」的途径（[@def-3.7.1] 的客户端组合义务）。缺任一条，光有 `Box` 就是把一句话当成一份证明。

:::

:::

### 3.8.2 Unpin 的意义

::: def 定义 3.8.2 · Unpin 与 PhantomPinned {#def-3.8.2}

对 **`Unpin`** 类型，`Pin` 并不施加同样的不可移动约束——大多数类型自动实现它。需要地址敏感不变量的类型通常不能随意实现 `Unpin`；**`PhantomPinned`** 是一个只用来阻止自动获得 `Unpin` 的零大小标记。

:::

按[@def-3.8.2]，使用 `PhantomPinned` 只是阻止自动获得某些性质的一环，它不自动证明内部指针有效：构造、投影、销毁与安全公开方法仍要维护不变量。本章没有实现自引用 unsafe 类型，因此不把几行 `Pin` 样例当成完成证明（[@def-3.7.1]）。

### 3.8.3 Pin 不是线程亲和性，也不是投影许可

对象地址不变，不意味着由同一线程操作。可跨线程移动的拥有句柄仍可能让不同线程访问被 pin 对象；线程局部资源需要自己的 `Send` 边界（对照 3.7.7：`Send`/`Sync` 不证明跨进程格式）。异步任务在不同 worker 之间恢复也可能保持被 pin 存储地址不变——这一段属于 Future 章节，**本节没有采集**任何调度或跨线程观测，因此不把 `Pin` 说成调度器锁核工具。

析构与自引用也要单独论证：地址敏感对象需要在销毁期间保持约定，`Drop` 实现不能先破坏仍将被使用的内部关系；若提供投影方法，还要确保投影不会移出被 pin 字段。安全 API 只露出 `Pin` 并不自动保证内部投影 sound，每个 unchecked 投影都必须说明字段移动与销毁边界——本章选择不提供此类接口，避免无必要扩大证明面积（[@def-3.7.1]）。

::: think 思考 · 「已经用 Pin 包住 Box 里的值，所以内部指针一定有效」 {#think-3.8.1}

一个库对外只暴露 `Pin<Box<Self>>`，作者据此在文档里写「内部自引用由 `Pin` 保证有效」。这个前提能被怎样绕过？

::: sol 解答

至少两条途径。第一，`Pin` 约束的是「不再移动这个值」，不覆盖「值内容从未被合法构造」：如果构造时先在临时位置建好内部指针再放进 `Box`，pin 住的是一个从一开始就指错的地址（[@ex-3.8.1]）。第二，若类型还实现了 `Unpin`，`Pin` 就不施加同样的约束（[@def-3.8.2]）；若它还提供了任何能移出或替换字段的安全方法，地址关系同样会被合法破坏（[@def-3.4.3]）。所以有效性要按[@def-3.7.1] 逐条客户端组合证明，`Pin` 只是其中「不再移动」这一条的名字。

:::

:::

### 3.8.4 资源许可与真正工作的生命周期

所有权系统只知道对象跟谁走，不知道一个业务许可本来要代表哪种资源。若许可跟随调用方，但实际工作在后台继续运行，调用方取消会过早释放预算——这可以在完全安全的 Rust 里发生，与[@def-3.7.1] 的 UB 无关，是事务语义问题。因此业务资源所有权必须与真正占用者绑定，不是只要「有 `Drop`」就自然正确（3.4.6）。并发与 runtime 章节会用许可迁移测试这一点。

### 3.8.5 错误恢复中的两种基本保证

一个操作失败后，组件至少应保持内存安全和可销毁；更强的事务保证要求状态完全不变。本包里两个例子给出两种不同的保证：`try_build` 返回 `Err` 时销毁已建前缀、不返回半成品（[@ex-3.3.1]）；`ByteRegion` 的 `take` 失败时保持游标不变，随后仍可成功申请原有空间。这两种保证不同，必须在接口文档里分别写清，不能统一叫「异常安全」而省略状态语义。

::: method 判定流程 · 地址敏感对象的接受条件

**① 最终位置先定**：内部指向必须在值不再移动的位置建立，之后才 `Pin`（[@ex-3.8.1]）。

**② 确认没有被 `Unpin` 绕过**：需要地址不变量的类型不要随手实现 `Unpin`，标记 `PhantomPinned` 只是起点（[@def-3.8.2]）。

**③ 逐个公开方法问**：有没有哪个方法能把被 pin 的字段移出、替换或 `mem::take`（[@def-3.4.3]、[@think-3.8.1]）？

**④ 析构顺序单独论证**：`Drop` 不能先破坏仍将被使用的内部关系（3.8.3、[@def-3.4.2]）。

**⑤ 线程与事务另开一栏**：`Pin` 不回答「谁在执行」，也不回答「许可该何时释放」（3.8.4）。

**⑥ 有一条不满足就回到安全结构**：缩小接口或去掉自引用，通常比补证明便宜（3.7.8）。

:::

### 3.8.6 初始化、发布与性能重构顺序

线程间发布一个对象之前，需要先建立完整合法状态；发布协议还需要相应同步关系。初始化完成不等于其他线程一定可见；Release/Acquire 等同步不能修复发布前已经产生的无效引用（[@def-3.3.1] 管「有没有合法 `T`」，同步管「看不见」，两者是不同证明）。本章只做单线程初始化实验，不从其结果推导原子发布协议。

性能重构的顺序：先减少不必要的拥有副本（3.5）；再匹配访问集合与布局；再选择更易优化的安全循环（3.6）；随后核对生成代码和真实测量。只有仍存在重要瓶颈时，才考虑扩大 unsafe 边界（[@def-3.7.1]）。这一顺序不是禁止 unsafe，它是让每一份额外证明都有可衡量的必要性。

代码审查中的拒绝条件：如果安全方法能制造悬垂引用，应拒绝；如果 panic 能使长度覆盖未初始化尾部，应拒绝（[@think-3.3.1]）；如果 `reset` 依赖用户口头承诺不保留借用，应要求更强接口；如果整数地址被当作唯一有效性证据，应补来源证明（[@def-3.7.2]）；如果性能结论来自 UB 版本，应丢弃该结论（[@think-3.6.1]）；如果只有 happy path 测试，应增加真实失败路径（[@ex-3.4.2]）。这些条件比「unsafe 行数少于多少」更有意义。

何时可以停止继续微调：当安全实现满足业务预算，额外复杂度未必值得。本轮 `zero_fill` 已经展示安全结构间有较大优化空间，`borrowed` 也避免了不需要的副本；此时优先维护测试、文档与真实调用链。不要因为一本底层书就必须在每章写 unsafe——理解边界并知道何时不跨越，本身就是专业能力。

### 3.8.7 小结与常见错误

**小结。**① 地址稳定性是与责任归属（[@def-3.1.1]）、访问阶段（[@def-3.2.3]）并列的独立轴（[@def-3.8.1]）；② `Box` 只保证「移动句柄不动载荷」，不保证内部指向有效（[@ex-3.8.1]）；③ `Unpin`/`PhantomPinned` 只是性质门槛，不是证明（[@def-3.8.2]）；④ `Pin` 与线程归属、业务许可无关（3.8.3、3.8.4）；⑤ 失败保证要区分「可销毁」与「状态不变」两种强度（3.8.5）。下一节 [3.9 延伸阅读与来源](#sec-cpp-rust.1.3.9) 给出本章结论对应的读物入口。

::: errata 常见错误清单（3.8 节）

E-a **把 `Pin` 解释为线程固定。**地址稳定性与执行线程是不同维度（3.8.3）；先查 `Send` 边界与调度事实。

E-b **以为 `Box` 自动修复内部指针。**内部指向必须在最终位置建立（[@ex-3.8.1]）；先查构造顺序。

E-c **给地址敏感类型随手实现 `Unpin`。**`Unpin` 会让 `Pin` 不再施加同等约束（[@def-3.8.2]）；先查 `PhantomPinned`。

E-d **露出 `Pin` 就宣布投影 sound。**每个 unchecked 投影要说明移动与销毁边界（[@think-3.8.1]）；先列公开方法的移出途径。

E-e **以为有 `Drop` 就代表业务许可正确释放。**所有权不知道许可代表什么资源（3.8.4）；先查真正占用者是谁。

E-f **把「初始化完成」当成「其他线程可见」。**发布需要额外同步关系（3.8.6）；先查同步与合法状态是两件事。

E-g **统一用「异常安全」描述两种保证。**可销毁与状态不变强度不同（3.8.5）；先查接口文档写了哪一种。

:::

::: method 即时自测 · 3.8

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　[@def-3.8.1] 里 `Pin` 约束什么、不约束什么？

::: sol 第 1 题答案
约束「被指向的值在 pin 之后不再按普通方式移动」；不约束 `Pin` 句柄本身的移动，也不保证内部指向曾被合法构造，更不规定执行线程。对应[@def-3.8.1]。
:::

**第 2 题 · 辨析**　「`Pin<Box<T>>` 加 `Drop`，所以资源协议一定正确。」指出两处独立缺口。

::: sol 第 2 题答案
其一，`Drop` 只保证收尾动作发生，不保证业务事务完成或错误被上报（3.4.6）；其二，若许可代表的资源实际由后台工作占用，调用方取消会过早释放（3.8.4）。两者都与地址稳定性无关，需要各自论证。
:::

**第 3 题 · 应用**　你要评审一个自引用状态机，只暴露 `Pin<Box<Self>>` 和一个 `get_mut`。按[@def-3.8.2] 与[@think-3.8.1]，先查哪两件事？

::: sol 第 3 题答案
① 类型是否 `Unpin`（若是，`Pin` 形同虚设）；② `get_mut` 是否允许把被 pin 的字段移出或替换（等价于 `mem::take`，[@def-3.4.3]）。任一条不过，接口就不能对外宣称地址不变量成立。
:::

**第 4 题 · 迁移**　一个异步任务被 pin 后在不同 worker 上恢复执行。按 3.8.3，你能否据此说「这个对象始终由同一线程操作」？

::: sol 第 4 题答案
不能。地址不变与执行线程是两条轴：worker 迁移可以保持被 pin 存储地址不变，而线程局部资源仍需自己的 `Send` 边界；本章没有采集调度观测，这类判断要交给 runtime 层的证据（3.8.3）。
:::

**所有权解释**：指出 `borrowed` 输入的拥有者；指出 `cloned` 临时 `Vec` 何时析构；说明两者输出相等为何仍有不同资源工作；说明复制是否必要取决于哪项生命周期需求；说明 move 与 `Pin` 分别约束什么（[@def-3.1.1]、[@def-3.8.1]）；说明 `RefCell` 失败为何没有 UB（[@ex-3.2.3]）。

**初始化解释**：画出 `try_build` 在第三次成功后的前缀（[@ex-3.3.1]）；指出下一次 `Err` 由谁销毁已有元素；指出下一次 panic 的 MIR cleanup 边（3.4.5）；说明 `panic = "abort"` 为何不能复用同样结论（[@def-3.4.1]）；说明 `u64` 零初始化为何不推广到引用类型（[@ex-3.3.2]）；说明 `push` 慢于 `zero_fill` 为何不自动要求 unsafe 改写（[@think-3.6.1]）。

**unsafe 审查练习**：对任意一个裸指针解引用，逐项填写证明表（[@ex-3.7.1]）；不能只填「来自 `Vec`，所以安全」（[@think-3.7.1]）；必须说明 `Vec` 是否仍活着、是否扩容、范围是否完整、借用是否冲突，还要说明是否已经初始化以及是否可能被其他线程修改。若某项证据缺失，应保留阻塞问题，不要用一次成功运行替代语言级访问证明。

**已有回归与证据**：十项 Rust 测试包含 `Err` 前缀清理、panic 前缀清理与动态借用失败，还包含安全分区更新、容量失败事务性与多表示求和等价（[@ex-3.4.2]）；compile-fail 文档测试维护 `reset` 借用边界；本章两个入口各有两 case，每 case 21 条正式原始批次；归档包含本机 MIR、LLVM IR、汇编与独立 borrow 采样；性能表均可从原始 CSV 重算；没有执行 UB，没有虚构硬件计数。独立审计与跨时段确认仍由后续集成安排。

### 本章导航

**学习目标**：学完这一章，你应该能：

- 把一次 move、clone 或 `Arc::clone` 拆成责任转移与资源工作量两件事；
- 用访问范围与访问阶段判断两个借用是否冲突，并说明 IR 参数属性支持到哪一步；
- 用已初始化前缀解释 `with_capacity`、`vec![0; n]`、提前 `set_len` 三者的差异与后果；
- 为 `Err`、panic 与部分移动写出「谁清理哪些元素」，并用测试与 MIR 双向核对；
- 读懂 3.5、3.6 两张实测表：说清单位、区间含义与不能归因的部分；
- 对一行裸指针解引用逐项填写十维证明表，并指出哪些义务不能互相替代。

**先修**：[第 1 章](ch01.md)的证据协议（批次、配对、区间、三态判定）与[第 2 章](ch02.md)的布局边界。
**课时**：讲授 2 学时 + 实验 2 学时。
**实验包**：`bench/foundations-lab/`，只依赖标准库。
**入口**：`src/bin/borrow.rs` 与 `src/bin/initialization.rs`；回归在 `src/lib.rs` 的单元测试与 `tests/contracts_more.rs`。
**数据**：`bench/foundations-lab/results/native-01/`（补充测试日志在 `validation-01/`）。
**边界**：全部实验是单线程、同步、桌面机上的 `u64` 求和与构建；没有采集跨机器、跨版本与内存流量数据，没有运行 Miri/TSan/Loom，没有实现自引用 unsafe 类型，也不验证生产环境的服务等级协议（SLA）。

**章末件**：五页配套材料已经就位——总结给「带走了什么」，回忆卡管「能不能提取」，习题集管「会不会做」，自测卷管「限时能不能验收」，自检表管「哪一条还没达标」。
