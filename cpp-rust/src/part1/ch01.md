## 1.1 先看一个不可信的数字 {#sec-cpp-rust.1.1.1}

本节回答一个问题：**为什么一个看起来正常的计时程序，会测出一段根本没有执行的代码？**讨论从 `0.000016 ns/元素` 这个反常数字出发，先看清「结果没人用」怎样骗过断言，再给出一套判断数字能不能用的检查顺序。

::: preview 先抓住一件事

性能数字的可信度，不取决于它写了多少位小数，而取决于**被测的工作是否真的发生、结果是否真的被使用**。肯定一个结果「能用」，要同时说清输入、计时边界、观察方式和外部条件；否定它，只要找到一条被破坏的规则——比如一个没人读取的返回值。
:::

### 1.1.1 一个比加法还快的求和

先约定三个词。`u64` 是 64 位无符号整数，取值到 2^64−1；`ns` 是纳秒，十亿分之一秒；`ns/元素` 表示「平均每个元素花了多少纳秒」。

看一段求和代码：

```rust
let sum: u64 = data.iter().copied().fold(0, u64::wrapping_add);
```

`wrapping_add` 是「溢出就从头绕回」的加法：结果超过 2^64−1 时回到 0 继续数，不会 panic（panic 指程序遇到无法继续的错误时中止执行）。

有人对 65536 个 `u64` 计时，得到 0.000016 ns/元素。同一批实验里真正做求和的那版是 0.058630038 ns/元素，比值 3645.71 倍（0.058630038 ÷ 0.000016082，本章后面按数量级写作「3600 倍」）；至于「一次普通整数加法要零点几纳秒」，那是量级常识，本书没有测过整数加法基线。硬件没有突破物理极限，问题出在「结果没人用」。

::: def 定义 1.1.1 · 死代码消除 dead code elimination, DCE {#def-1.1.1}

如果一段纯计算的**结果没有任何可观察效果**——不被打印、不被写进内存、不参与任何判断——编译器就有权删掉整段计算。这个优化叫**死代码消除**（dead code elimination, DCE）。

:::

[@def-1.1.1] 不是编译器的失误，而是它的义务：没人用的计算，删掉就省时间。危险在于，微基准常常顺手删掉的正是「使用结果」那一步，于是你测到的是空函数。把刚才的实现编译出来，函数体只剩两行汇编（汇编是编译器生成的机器指令文本）：

```asm
mov x0, #0
ret
```

`mov x0, #0` 把 0 放进返回寄存器（CPU 用来传返回值的一小块存储），`ret` 返回。数组一个元素都没被读取。

::: ex 例 1.1.1 · 断言为什么没拦住它 {#ex-1.1.1}

实验夹具（fixture：为了测量而包住被测函数的那圈代码——读表、存结果、比对）在计时结束后检查「每次调用的返回值都等于期望值」。`discarded` 分支的期望值写成 0，返回值也是 0，断言成功；但 21 个批次的耗时里，数组求和一次都没有发生。断言为什么没有发现问题？

::: sol 解答

因为断言检查的是**声明的契约**，不是**你想测的工作**。`discarded` 的期望值被声明为 0，编译器返回 0，两者一致，断言忠实地验证了一个错误目标。要让断言有意义，期望值必须来自独立的参考计算，而不是与被测实现共享同一个被简化掉的常量。

:::

:::

这个例子给出本节第一个可复用的判断：**先问「结果被谁用了」，再问「数字是多少」。**

### 1.1.2 让结果可观察：输入屏障与结果屏障

::: def 定义 1.1.2 · 优化屏障与 `black_box` {#def-1.1.2}

**优化屏障**（optimization barrier）是人为设置的信息边界，用来阻止编译器跨越这条边界做推断。标准库的 `std::hint::black_box` 是最常用的一种：它是身份函数（输入什么就返回什么），同时告诉优化器「这个值的用途我看不清，别乱猜」。

:::

[@def-1.1.2] 只影响优化器能看到的信息。它不是锁或原子操作那样的同步工具，也不提供安全保证。屏障有两个位置，回答两个不同的问题：

| 屏障位置 | 阻止什么 | 单独使用时的失效方式 |
|:--|:--|:--|
| 输入边界 | 编译器利用已知的输入值（常量折叠、按值特化） | 结果没人用，整段计算照删 |
| 结果边界 | 编译器删除未被观察的结果 | 表达式内部先折成常量，屏障挡在外面 |

```rust
black_box(5 * 10)
```

不能保证真的做了乘法：乘法可能在进入屏障之前就被折成 50。位置要按真实应用的信息边界来放，不是越多越好。

::: think 思考 · 打印耗时算不算「使用结果」 {#think-1.1.1}

```rust
let sum: u64 = data.iter().copied().fold(0, u64::wrapping_add);
let elapsed = start.elapsed();
println!("{} ns", elapsed.as_nanos());
```

这段代码里，`sum` 是活的吗？

::: sol 解答

**不是。**`sum` 没有进入任何输出、比较或存储；打印耗时只用到 `elapsed`，不构成对 `sum` 的观察。编译器可以连同整条求和一起删掉。要让 `sum` 变活，必须把它写进被检查、被打印或被屏障挡住的位置。

:::

:::

### 1.1.3 一个数字要可信，先回答四个问题

拿到 0.000016 ns/元素，先别问「怎么更快」。先问四件事。

::: def 定义 1.1.3 · 实验契约 {#def-1.1.3}

一次性能实验的**契约**，是下面四组问题的答案合起来：**输入集合**（数据怎么生成、多长、是否复用同一块内存）、**计时集合**（哪一段代码被两个时间戳夹住）、**观察集合**（哪些输出会被读取、比较或保存）、**外部条件集合**（编译器、目标平台、优化级别、系统负载、机器状态）。

:::

[@def-1.1.3] 的四组答案，这一章的做法是：

| 集合 | 要回答的问题 | 这一章的做法 |
|:--|:--|:--|
| 输入集合 | 数据怎么生成、长度多少、是否复用内存 | 65536 个 `u64`，固定公式生成，每次一样，只读 |
| 计时集合 | 哪一段被两个时间戳夹住 | 只包围求和循环；输入生成、结果检查在计时之外 |
| 观察集合 | 哪些输出会被读取或保存 | 每次调用的结果写进输出数组，批后逐项比对 |
| 外部条件集合 | 编译器、平台、优化级别、负载 | rustc 1.99.0、`aarch64-apple-darwin`、release、同一台 Mac |

只看一个纳秒数，等于把这份契约藏起来：别人无法判断你测的是元素、调用还是批次，也无法判断结果有没有被编译器删掉。

::: method 检查顺序 · 这个性能数字能用吗

**否定**（命中任意一条就要警惕）：① 结果没被观察，可能整段被删；② 分母与实际工作量不符，数字没有物理意义；③ 计时边界把输入生成或终端 I/O 包了进来；④ 没有记录编译参数与机器状态，无法复核。
**肯定**：四组问题都有明确答案，而且答案能和代码、原始数据一一对上。

:::

### 1.1.4 最小计时程序缺了哪一块

::: ex 例 1.1.2 · 找出契约里的缺口 {#ex-1.1.2}

```rust
use std::time::Instant;

fn main() {
    let data: Vec<u64> = (0..65_536).collect();
    let start = Instant::now();
    let sum: u64 = data.iter().copied().fold(0, u64::wrapping_add);
    let elapsed = start.elapsed();
    println!("{:.6} ns/element, sum={sum}", elapsed.as_nanos() as f64 / data.len() as f64);
}
```

按 [@def-1.1.3] 检查：这段程序回答了哪几问，还缺哪几问？

::: sol 解答

**已回答**：输入集合（65536 个 `u64`）和计时集合（`Instant::now()` 到 `elapsed()`）；`sum` 出现在打印里，结果也算被观察了一次；分母明确是元素数。

**还缺**：① 没有重复，一次采样无法区分噪声；② 没有预热，首次调用的缺页（第一次访问某页内存时由操作系统装入）和代码装载都算进了耗时；③ 没有检查结果是否正确，求和算错也照样打印；④ 没有记录编译器版本、优化级别和系统状态，别人无法复核；⑤ `Instant` 的分辨率未知，纳秒级的单次差值可能整块被量化掉。

这五条缺口就是 1.2、1.3、1.4 要逐个补上的内容。

:::

:::

### 1.1.5 先确定「算的是同一件事」

比较两个实现之前，要先说清它们算的是不是同一个东西。拿求和举例：整数 `1 + 2 + 3` 和 `3 + 2 + 1` 都等于 6，换顺序不影响结果；但浮点数不一定，`0.1 + 0.2 + 0.3` 与 `0.3 + 0.2 + 0.1` 的末位可能不同，因为浮点加法不满足结合律。

这一章的求和定义在 `u64` 的**模加法**上：结果超过 2^64 就绕回。模加法满足结合律，所以换遍历顺序不改变最终结果，「两种写法是否等价」这件事可以被严格检查。

::: ex 例 1.1.3 · 换顺序会不会改变结论 {#ex-1.1.3}

`sum_index` 用 `while` 顺序累加，`sum_iter` 用迭代器累加，两者都用 `wrapping_add`。它们算的是同一个函数吗？如果改成 `f64` 求和，这个判断还成立吗？

::: sol 解答

**`u64` 情形成立。**两者都是对同一批元素做模加法；模加法满足结合律与交换律，遍历顺序不改变结果，因此可以谈「语义等价下的成本比较」。

**`f64` 情形不成立。**浮点加法不满足结合律，换顺序可能改变舍入路径。这时要么先固定一个误差界（比如「相对误差不超过 1e-12」）再比较，要么承认测的是两个不同的函数，不能只比耗时。

:::

:::

浮点归约（把一串数折成一个结果的最后那步）不能照搬 `u64` 的结论：算法比较必须把「用什么算术、允许多大误差」也写进契约，否则你测的可能是两个不同的函数。

### 1.1.6 把问题写成可以被否定的形式

如果事先相信「迭代器一定比索引慢」，你很容易只挑支持这个结论的批次。好的实验问题应该能被结果否定：

- 可否定的问法：「在当前编译参数下，两种遍历的批均值是否可区分？」
- 不可否定的问法：「测出迭代器零成本的证据。」

这一章的实际结果是：在这台机器、这组参数下，两者不可区分。这仍然有价值，因为它告诉你，在这个场景里继续为两种写法争论的收益很小。

### 1.1.7 微基准要接到一个工程决策上

微基准只有接到一个工程决策上才有意义。如果业务每个请求只处理两个元素，这一章的大数组结果不适用；如果业务必须在多个线程之间交接数据，单线程求和缺少同步路径；如果业务主要等待网络，这段求和再快也无足轻重。

读完一个微基准，先问三个问题：这段工作占完整请求多少比例？它是否决定整体完成时间？局部加速能不能转化成整体改善？吞吐瓶颈和延迟瓶颈也可能不同：某段代码 CPU 占用高，不代表它决定尾延迟；某个锁 CPU 占用低，却可能让大量线程排队。第 13 章会继续分离「运行」和「等待」。

### 1.1.8 小结与常见错误

**小结。**① 结果没有可观察效果就会被删，这是 DCE（[@def-1.1.1]），微基准最容易踩到；② 屏障分输入与结果两处，位置由应用的信息边界决定（[@def-1.1.2]）；③ 一个数字要可信，先回答输入、计时、观察、外部条件这四组问题，合起来就是实验契约（[@def-1.1.3]）。三件事串成一条链：先看结果有没有被用，再看单位对不对，最后看环境全不全。[1.2 观测开销、批量与时钟边界](#sec-cpp-rust.1.1.2) 沿这条链讨论「计时边界该画在哪里、批次要多大」。

::: errata 常见错误清单（1.1 节）

E-a **把打印耗时当成使用结果。**`sum` 没进输出、比较或存储，计算照样被删（见本节的思考框）。

E-b **只加输入屏障就以为安全。**输入不透明修不了「输出没人要」；[@def-1.1.1] 的删除照样发生。

E-f **不写外部条件就发布数字。**换编译器、换优化级别结论会变，读者无法复核（[@def-1.1.3]）。

## 1.2 观测开销、批量与时钟边界 {#sec-cpp-rust.1.1.2}

本节回答一个问题：**计时边界该画在哪里，一个批次里要重复多少次？**1.1 解决了「结果必须被观察」；这一节把「一次测量」拆成时钟、批次、夹具和预热四件事，并说清这样设计换来什么、代价是什么。

::: preview 先抓住一件事

一次测量的时间由三部分构成：**工作**（你要比较的计算）、**夹具**（为了测它而付出的额外代价）、**干扰**（你控制不了的机器状态）。这一节的目标不是把噪声测没，而是把噪声压到能说明白的范围，并且把剩下的部分写进结论。
:::

### 1.2.1 为什么不逐元素打时间戳

最直观的做法，是在循环体里为每个元素读一次时钟。这个做法通常会毁掉你要测的东西。

读时钟不是免费操作。它会打断原本可以向量化的循环（把多条同类运算合成一条批量指令），增加存储和分支，还可能因为调用路径、缓存状态和调度而变化。你无法用一个固定的「时钟开销」把它减掉，因为开销本身不是常数。

::: def 定义 1.2.1 · 墙钟时间与分辨率 {#def-1.2.1}

**墙钟时间**（wall-clock time）就是挂钟走过的时间：从开始到结束，手表上读到的差值。它与 CPU 周期数不同，中间包含被抢占、休眠和频率变化。**分辨率**（resolution）是这块时钟能分辨的最小间隔；比分辨率还短的差值会被量化，读数只能是 0 或者一个固定步长。

:::

这一章只在一个批次前后读时钟，批内包含多次完整的工作核调用（「工作核」指被测的那段计算，「批次」见[@def-1.2.2]）。这样把时钟调用摊薄到更多工作上，代价是丢失单次调用的分布信息。所以批次 p99 不能拿去回答请求 p99：p99 表示 99% 的观测不超过这个值，而批次和请求是两个不同的观测单位。这个限制必须和结果一起发布。

### 1.2.2 批次模型：一次测量到底在测什么

::: def 定义 1.2.2 · case、批次与批均值 {#def-1.2.2}

一个 **case** 是「某个被测实现的一次完整流程」：先预热，再采集若干批次。一个**批次**（batch）是「把同一个工作核连续调用 K 次，只在前后各读一次时钟」。若该批的墙钟间隔为 T、每次处理 N 个元素，则

**批均值 = T / (K × N)**，单位记作 ns/元素。

一个 case 采集 21 个批次；这 21 个数值的分布，才是这一节的观测对象。

:::

按[@def-1.2.2]，可以把 T 概念性地拆成三部分：工作、夹具和干扰。夹具包括动态闭包分派、输出存储和 `black_box`；干扰包括系统抢占、后台负载和频率变化。这个分解帮助你设计实验，不代表你已经把每一项都测出来了——三项也不彼此独立，工作本身就会改变缓存和热状态。

::: ex 例 1.2.1 · 用空循环扣掉夹具，行不行 {#ex-1.2.1}

有人提议：先跑一个不做任何工作的空批次，记下耗时 T₀，再用 T − T₀ 当作「纯工作」的成本。这个扣减法在什么时候失效？

::: sol 解答

只要删掉实际工作，优化器和处理器看到的就不是同一条路径：空循环可能被整体折叠，闭包的分派目标可能改变，分支预测也进入另一种状态。于是 T₀ 与「带着真实工作的夹具」并不相等，减法会把一个错误的常数扣进结果。更可靠的做法是让两套实现的夹具完全相同、足够小，然后明确声明它仍然被计入。

:::

:::

### 1.2.3 计时边界：哪些阶段进，哪些阶段出

[@def-1.2.2] 只说了「批内做什么」，还没说「边界画在哪」。这一节的答案写成一张清单：

| 阶段 | 是否计时 | 为什么 |
|:--|:--|:--|
| 输入 `Vec` 创建 | 否 | 控制求和输入，不混入分配 |
| 参考值计算 | 否 | 不与被测核竞争时间 |
| 闭包调用 | 是 | 这是夹具实际的分派成本 |
| 工作核读取 | 是 | 真正要比较的工作 |
| 输出 `black_box` | 是 | 防止批次不可观察（[@def-1.1.2]） |
| 输出数组写入 | 是 | 保存每次返回值 |
| 结果断言 | 否 | 验证失败时拒绝该批 |
| CSV 格式化 | 否 | 不把终端 I/O 算进工作核 |
| 下一轮顺序选择 | 否 | 不是求和算法的一部分 |

这张表本身就是实验契约的一部分。换一个项目，边界可以不同，但必须写清楚，否则读者无法判断你的数字里装了什么。

::: method 判定流程 · 这一段该不该进计时

**进计时**：这段工作正是你要比较的对象，或者是为了保证结果可观察而必须付的代价。
**不进计时**：准备输入、计算参考值、写文件、打印、选择下一轮顺序——它们属于计时之外的仪式。
**两种都要写进契约**：进与不进都要在正文给出边界清单，让读者能够自己重画这条线。

:::

### 1.2.4 `Instant` 能回答什么，不能回答什么

`Instant` 适合这一章的墙钟间隔。它不提供核心执行周期数，分辨率和实现依赖目标平台。即使底层使用了某种硬件计数器，直接把它称为 CPU cycle 也会混淆计数频率、计数器语义和核心实际运行频率；跨核心迁移和系统暂停也需要按平台说明处理。

这一章没有直接读取 TSC 或 CNTVCT（x86 与 ARM 的两种硬件计数器），因此不发布任何 cycle/元素结果。[@def-1.2.1] 的分辨率限制在这里同样生效：批次越短，时钟和循环入口成本占比越大。`dce` 的删除分支就是一个极端，它只剩极少工作，按 65536 个元素归一化没有物理意义。

::: think 思考 · 打印了九位小数，就有九位精度吗 {#think-1.2.1}

实测表里会出现 `0.058630038 ns/元素` 这样的数。最后几位可信吗？

::: sol 解答

不可信。这个数字是 `T / (K × N)` 的除法结果：T 受分辨率限制，K × N 是固定整数，多出来的位数只是除不尽的尾巴。有效位数由测量协议决定，不由打印格式决定。想提高可信位数，只能增加独立样本、改进夹具，而不是把 `format!` 的精度调大。

:::

:::

### 1.2.5 批大小、缓存状态与预热

K 太小，时间戳和系统量化明显；K 太大，单个批次可能跨越明显的热漂移，一次错误输入也会污染更多工作。这一章为每个入口固定 K，不同入口的 K 不同，而且它不是工作量的单调函数：`allocation` 每次迭代做一次 64 字节堆分配，是本章单次迭代最重的入口，K 却是全章最小的 16（`allocation.rs:36`，它的 `units` 也只有 4096，不是共享常量 $N$）；`initialization` 64（`initialization.rs:17`）、`locality` 128（`locality.rs:22`）、`borrow` 与 `dce` 各 256（`borrow.rs:18`、`dce.rs:18`）、`paired` 512（`paired.rs:18`）。

后四个同样是对 $N=65536$ 的 `u64` 求和，K 却差到四倍。这说明 K 来自各入口自己的批次成本预算与单位定义，不能反过来写成「工作越多 K 越大」。跨入口比较时只能比较各自定义清楚的单位，不能把不同入口当成同一个实验的随机重复。

批大小也决定缓存状态。连续重复同一数组会强调热数据路径，不代表每次都从冷内存读取。要研究冷缓存，应该另设输入轮换协议，而不是在测量前访问一个大数组就宣称清空了缓存。

::: def 定义 1.2.3 · 预热与热漂移 {#def-1.2.3}

**预热**（warm-up）指正式计时之前先运行一段时间，让代码装载、缺页和分支预测进入稳定状态。**热漂移**（drift）指频率、温度和后台负载随时间变化，使前后批次不再可比。预热处理前者，处理不了后者；后者要靠 1.4 的配对与顺序诊断。

:::

每个 case 至少预热 500 ms。按[@def-1.2.3]，这个数字的作用要说清楚：它让首次调用、代码装载和一部分页面访问不完全落入正式批次，但没有证明温度、频率和系统负载已经稳定。两个 case 依次预热，会形成不同的时间位置，所以正式轮次采用交替顺序，减弱位置与实现的绑定。预热中的耗时不进入统计，但预热中的结果仍然检查正确性，否则你可能在预热阶段跑了一条与正式测量不同的错误路径。

这一章没有自动增长 K 直到达到某个时长。这样归档里的逻辑工作量容易复核。如果将来加入自适应校准，应该保存校准结果和最终 K；不同 case 自动选到不同 K，也需要解释批次状态差异。发布归一化数值时，也要一起给出批次规模。

### 1.2.6 桌面系统上的隔离能做到哪一步

正式脚本通过**目录锁**（同一时刻只允许一个测量进程创建的那个目录）串行化参与协议的 benchmark。锁不控制浏览器、窗口服务和操作系统后台工作。开始正式计时前，脚本会查询 `cargo` 与 `rustc` 进程；这次的 `build-processes.txt` 为空，只表示该时刻没有匹配到构建进程，不表示整个测量期间没有干扰。

实验没有锁核（把线程固定在某个 CPU 上）、锁频（把频率钉住），也没有禁止调度迁移。所有推断都限定在当前桌面运行条件下。把边界说清楚，比假装严谨更有用：如果你要的是生产环境的结论，应该在生产等价的环境里重做，而不是把桌面数字外推。

### 1.2.7 小结与常见错误

**小结。**① 逐元素读时钟会毁掉被测路径，所以只在批次前后各读一次（[@def-1.2.1]）；② 一次观测的单位是批均值 `T / (K × N)`，一个 case 有 21 个这样的数（[@def-1.2.2]）；③ 计时边界要写成清单，它和四组问题一样属于实验契约；④ 预热处理装载与缺页，处理不了热漂移（[@def-1.2.3]）。顺着这条链往下走：[1.3 优化屏障与可观察结果](#sec-cpp-rust.1.1.3) 把[@def-1.1.2]的屏障放到具体位置上，回答「结果要怎样才能一直可观察」。

::: errata 常见错误清单（1.2 节）

E-a **逐元素读时钟。**测到的是「计时 + 工作」的混合，向量化也会被打断（[@def-1.2.1]）。

E-b **用空循环扣夹具。**工作被删掉之后路径就变了，减法扣的是错误的常数（[@ex-1.2.1]）。

E-c **把批次 p99 当请求 p99。**21 个批均值的最大值，只说明批次之间的波动。

E-d **只看位数不看分辨率。**位数由协议决定，不由打印格式决定（见本节的思考框）。

E-e **用一次大数组访问冒充冷缓存。**没有输入轮换协议，就没有「冷」这个前提。

E-f **只写「预热过」，不写时长与检查。**预热没有可解释的时长和正确性检查时，你可能测了一条错误路径（[@def-1.2.3]）。

:::

**第 1 题 · 记忆**　写出批均值的公式，说明每个符号的含义，并说出一个 case 有几个这样的数。

::: sol 第 1 题答案

批均值 = `T / (K × N)`：T 是一个批次的墙钟间隔，K 是批内调用次数，N 是每次调用处理的元素数；一个 case 采集 21 个批次，所以有 21 个批均值。对应[@def-1.2.2]。若把 K 与 N 说反，请回到那条定义重读：一个批次是「连续调用 K 次、只读两次时钟」。
:::

**第 2 题 · 辨析**　「我把输入生成放在计时之外，所以我这个数不含夹具开销。」这句话错在哪？

::: sol 第 2 题答案

错在后半句。输入生成确实在边界之外，但闭包调用、输出数组写入和 `black_box` 在边界之内，它们就是夹具，仍然被计入。正确的说法是「两套实现的夹具相同且足够小，并且仍然计入」，依据是本节的计时边界清单。
:::

**第 3 题 · 应用**　你要比较两种 JSON 解析器的耗时，输入是一个 50 MB 文件。K 取 1 还是取 10？说明理由，以及你还要额外记录什么。

::: sol 第 3 题答案

K=1 更贴近「用户等多久」，但单次读数会被缺页、分配器（向系统申请内存的那层代码）扩容和后台负载主导，波动很大；K=10 能摊薄时钟与入口成本，却会把同一个文件的后续解析变成热数据实验，与首次解析不是一回事。可行做法是两种都测：K=1 回答延迟，K=10 回答稳定吞吐，并在结论里分别标注单位（ns/次 与 ns/字节）。还要记录文件是否已经进过页缓存、解析结果有没有被观察（[@def-1.1.3]）。
:::

**第 4 题 · 迁移**　预热 500 ms 之后，机器仍可能发生哪些变化？协议里怎么体现？

::: sol 第 4 题答案

频率随温度回降、后台任务抢占、别的进程竞争内存带宽、调度器把线程迁到另一类核心。这些不是「装载」问题，预热管不了（[@def-1.2.3]）。协议里的体现方式是：同轮交替顺序、记录 `round` 与 `position`、输出前后段均值做漂移诊断，并把结论限定为「当前运行内」（见 1.4）。
:::

:::

## 1.3 优化屏障与可观察结果 {#sec-cpp-rust.1.1.3}

本节回答一个问题：**屏障到底放在哪一层，才能让「每一次调用」都真的被观察到？**1.1 给了 DCE（[@def-1.1.1]）和优化屏障（[@def-1.1.2]）的定义，1.2 定了计时边界（[@def-1.2.2]）；这一节把它们落到具体夹具上，检查观察集合是不是真的成立。

::: preview 先抓住一件事

可观察性是**逐次调用**建立的，不是「程序最后有个 println」建立的。夹具里只要有一次调用的结果没留下痕迹，编译器就有权把那一次——甚至整批——简化掉；你事后读到的平均值，就不再对应 K 次真实工作。
:::

### 1.3.1 这个夹具里装了哪几道屏障

1.1 的表格讲的是「屏障能挡什么」；这里把它对号入座，列出本章夹具实际用到的四道，以及每道的代价。

| 位置 | 写法 | 挡住什么 | 你付出的代价 |
|:--|:--|:--|:--|
| 输入边界 | `black_box(&input)` | 编译器利用已知的长度和元素值 | 一次不可折叠的取址与内存屏障语义 |
| 每次调用结果 | `*output = black_box(work())` | K 次调用的返回值被合并或删掉 | 每次调用一次存储，计入计时 |
| 批后验证 | 逐项比对 `outputs` 与 `expected` | 实现算错却「看起来很快」 | 在计时之外，但要额外存一份参考值 |
| 函数边界 | `#[inline(never)]` | 跨边界常量传播与整体消除 | 保留调用开销，可能低估内联后的收益 |

表里的「内联」指优化器把被调函数的代码直接搬进调用点（inline），省掉调用开销，也让两边的代码混在一起；`#[inline(never)]` 要求它别这么做。

前三道服务于[@def-1.1.3]的观察集合，第四道是实验设计选择，下一节讨论它的偏差。

### 1.3.2 观察一个描述符，不等于观察它指向的数据

| 对象 | 本机尺寸 | 内容 | 对观测的影响 |
|:--|--:|:--|:--|
| `u64` 输出 | 8 字节 | 模加法结果 | 每次调用都可检查 |
| `u64` 切片引用 | 16 字节 | 数据位置与长度 | 屏障隐藏描述符，不复制数组 |
| `Vec<u64>` | 24 字节 | 所有权描述符 | 尺寸不包含元素存储 |
| case 工作闭包 | 动态 trait 对象 | 捕获环境与调用入口 | 增加共同分派成本 |
| 输出数组 | K 个 `u64` | 每次调用的结果 | 避免只观察最后一次调用 |

切片引用的 16 字节来自本机探针（打印类型尺寸与字段偏移的小程序），不能当成跨所有平台的稳定接口；`Vec` 的字段顺序这里也没有承诺。后续章节会把类型布局与 FFI 布局分开。这里要记住的只有一句：**把描述符交给 `black_box`，不等于读取它指向的全部数据。**

::: def 定义 1.3.1 · 观察集合与验证覆盖 {#def-1.3.1}

一个批次的**观察集合**，是这批调用留下的可检查痕迹。若夹具为 K 次调用准备 K 个输出槽、停表后逐个比对，则每次调用都被观察；若只保存最后一次返回值，前 K−1 次的结果对编译器就是可丢弃的，[@def-1.1.1] 会照删。

:::

::: ex 例 1.3.1 · 只检查最后一次返回会怎样 {#ex-1.3.1}

有人把夹具改成：批内循环调用工作核但不写数组，循环结束后只把最后一次返回值送进 `black_box`。这样做还测得到 K 次工作的成本吗？

::: sol 解答

测不到完整成本。前 K−1 次的返回值既没被存下也没被比较，编译器可以让它们共用一次计算，甚至整体折叠成一次执行；只有最后一次被保证发生。于是「K 次调用的批均值」实际上变成了「约一次调用的成本除以 K」，恰好造出一个比[@def-1.2.2]预期小得多的数字。这就是为什么夹具要为每次调用准备一个槽位，并在停表后逐个比对。

:::

:::

### 1.3.3 `inline(never)` 是选择，不是「更真实」

这一章的工作核使用 `#[inline(never)]`，好处是能在独立符号里核对工作是否保留，代价是保留了应用中可能被内联消除的调用边界。于是结果不是该算法在所有调用环境下的下界。

如果真实业务依靠跨调用的常量传播，当前夹具会抑制一部分机会。正确的下一步是增加匹配真实调用链的实验，而不是假定「不内联更接近真实」。

### 1.3.4 验证的强度要与声明匹配

[@def-1.3.1] 要求逐次观察，但逐次比对本身也不是功能证明。checksum 只能检出一部分实现错误，不同的错误输出可能撞出同一个摘要；求和核逐次比较完整 `u64` 结果，仍要配合覆盖空输入、短输入和非整块尾部的测试。

改成浮点核时，「比较结果」这件事要先有定义：误差界是多少、在哪个量级上比较。这些应在测量之前定下，而不是看到数字之后再放宽。

::: think 思考 · 应用真的只用结果的一个字段 {#think-1.3.1}

假设线上代码只用到求和结果的最低位（例如判断奇偶），夹具却坚持保留完整的 `u64` 并把它送进 `black_box`。这样测出来的是不是真实成本？

::: sol 解答

偏贵。真实应用里，编译器知道「只有最低位会被使用」，高位计算可以被整体删除；夹具强行保留完整结果，测的是一个并不存在的约束。反过来，如果线上确实要用完整值，夹具保留它就是对的。结论：**屏障的位置应当复刻应用的信息边界**——目标是阻止与真实用途不一致的优化，而不是把「阻止优化」当成目的。若工作本身就会产生副作用（写文件、发请求），输出屏障往往是多余的。

:::

:::

### 1.3.5 小结与常见错误

**小结。**① 夹具里的四道屏障各有位置与代价，前三道服务观察集合（[@def-1.3.1]）；② 观察描述符不等于观察数据；③ 只保留最后一次调用会让批均值失去意义（[@ex-1.3.1]）；④ `#[inline(never)]` 与「完整结果」都是实验选择，要让它们与真实用途一致。下一节 [1.4 配对、顺序与时间漂移](#sec-cpp-rust.1.1.4) 处理另一类误差来源：机器状态随时间变化。

::: errata 常见错误清单（1.3 节）

E-a **只在最后 `black_box` 一次。**前面 K−1 次调用没有痕迹，可被合并或折叠（[@ex-1.3.1]）。

E-b **把屏障数量当成可信度。**加得越多，越可能测到一个不存在的约束（见本节的思考框）。

E-c **用描述符的屏障冒充数据的屏障。**切片引用的长度被藏住，元素仍可不被读取（[@def-1.1.2]）。

E-d **假定 `inline(never)` 更真实。**它保留调用边界，也抑制跨边界传播（1.3.3）。

E-e **把 checksum 通过当功能证明。**摘要相同不等于实现正确，边界输入要另测（1.3.4）。

E-f **测量之后再定误差界。**浮点核的容差必须在看到数字之前写进契约（1.3.4）。

:::

::: method 即时自测 · 1.3

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　本章夹具的四道屏障分别放在哪里，各挡住什么？

::: sol 第 1 题答案
输入边界 `black_box(&input)` 挡住对已知输入的特化；每次调用的 `*output = black_box(...)` 挡住返回值被合并；批后逐项比对挡住实现算错；`#[inline(never)]` 挡住跨调用折叠。代价分别是屏障语义、一次存储、额外的参考值、保留调用开销。对应 1.3.1 的表。
:::

**第 2 题 · 辨析**　「我已经 `black_box(&data)` 了，所以整个数组一定被读过。」这句话对吗？

::: sol 第 2 题答案
不对。被藏住的是切片的**描述符**（长度与地址），数组内容是否被读取取决于结果有没有人用。`dce_empty` 正是输入过了屏障、`fold` 仍被删掉的例子（[@def-1.1.1]）。
:::

**第 3 题 · 应用**　你怀疑自己的夹具「只观察了最后一次调用」。写出两条能证实这一点的证据。

::: sol 第 3 题答案
① 静态证据：看生成代码里循环是否折叠成一次计算（汇编或 LLVM IR 里只有一份累加）。② 数值证据：把 K 翻倍再测，如果批均值几乎不变而不是保持在同一量级，说明多出来的调用没有真正发生。两者都指向[@def-1.3.1]未被满足。
:::

**第 4 题 · 迁移**　线上代码只要结果的奇偶性，你的夹具保留完整 `u64`。这个测法偏高还是偏低，怎么改？

::: sol 第 4 题答案
偏高：真实应用里高位计算可被删除，夹具强行保留，测到了一个不存在的约束。做法是让夹具复刻应用的输出形状——只把最低位送进 `black_box`，并另测「需要完整值」的场景，两者分开报告（见本节的思考框）。
:::

:::

## 1.4 配对、顺序与时间漂移 {#sec-cpp-rust.1.1.4}

本节回答一个问题：**怎么把「实现之间的差异」和「机器随时间的变化」分开？**[@def-1.2.3] 已经说明预热挡不住热漂移；这一节给出对抗它的采样设计：一轮里同时测两个实现，并把顺序记下来。

::: preview 先抓住一件事

同一台机器上，越靠后跑的批次越可能受温度和后台负载影响。因此比较两个实现时，最危险的做法不是样本太少，而是**让每个实现固定待在时间轴的一段上**——那时你分不清测到的是实现差异，还是机器状态的变化。配对与交替顺序解决的就是这一件事。
:::

### 1.4.1 独立分组会把时间当成实现

先跑完 A 的 21 批，再跑完 B 的 21 批，流程很简单。但如果机器逐渐变热，B 总是处于后半段，实现差异就与时间位置混在一起。即使两组各自看起来都很稳定，也可能存在组间偏差。把样本数量加倍不一定消除这种偏差；更多相同偏差的重复，只会让错误结论看起来更精确。

::: def 定义 1.4.1 · 轮、位置与配对 {#def-1.4.1}

一轮（round）指「把参与比较的每个实现各测一个批次」的完整过程；位置（position）记录某个批次在这轮里排第几。若一轮内 A、B 各测一次，就得到一个**配对**（pair）。配对的意义在于两个批次几乎处在同一时间位置，共享了大部分机器条件。

:::

按[@def-1.4.1]，这一章的安排是：第 0 轮顺序为 A、B，第 1 轮为 B、A，之后继续交替；每条记录同时保存 `round` 与 `position`，这样既能恢复配对关系，也能检查顺序效应——也就是「先跑的那个是否总是更快」。

### 1.4.2 配对差值：先相减，再平均

::: def 定义 1.4.2 · 配对差值 {#def-1.4.2}

令同一轮中 A、B 的批均值分别为 a、b，定义该轮的**配对差值** `d = b - a`。d 为负表示第二个实现的单位成本较低。统计时先对每一轮算出 d，再对这 21 个 d 求均值和标准差。

:::

先算差值再平均，保留了两者的共同时间条件；如果先把两组的数排好序再相减，或者删掉 A 的慢批却留着同轮的 B，对应关系就被破坏了。

::: method 判定流程 · 差值怎么算才不会自我欺骗

**要做**：按原始 `round` 配对；缺轮就整对删除（两侧一起删）；报告差值均值、差值标准差和区间。
**不能做**：先排序再相减；只删一侧的慢批；把两组的均值各自算好再相减当作配对结果——数量上看一样，波动估计完全不同。
**要说明**：配对只削弱系统性偏差，不消除抢占与缓存的相互影响；它不是因果识别的万能工具。

:::

### 1.4.3 原始记录最少要有哪些字段

```text
kind,round,position,case,ns_per_unit,checksum
raw,0,0,indexed,...,...
raw,0,1,iterator,...,...
raw,1,0,iterator,...,...
raw,1,1,indexed,...,...
```

这里省略数字只用于说明格式，正式 CSV 保留全部实际数字。章节里的性能表由正式 CSV 生成，格式示意只用于说明字段，正式结论要回到原始记录。

::: ex 例 1.4.1 · 少了 position 会失去什么 {#ex-1.4.1}

一份 CSV 记了 `case`、`ns_per_unit`，但没记 `round` 和 `position`。哪些结论就此无法复核？

::: sol 解答

三件事查不了。① 配对：没有轮次编号，就无法把同一轮的 A、B 配成一对，只能退回两组独立均值的比较，共同时间条件的信息全丢。② 顺序效应：没有位置，就看不出「先跑的那个是不是总更快」。③ 整对删除：某轮缺一个实现时，无法把对应的那一侧一起删掉，只能单方面删点，破坏[@def-1.4.2]要求的对应关系。

:::

:::

### 1.4.4 漂移诊断：先看时间结构，再谈归因

分析脚本同时输出每个 case 前 7 轮与后 7 轮的平均值。这是粗略的时间位置诊断，没有建立频率或温度的物理模型；前后差异可能来自热漂移，也可能来自普通噪声。诊断的作用是提醒你检查时间结构，不是自动给每一个异常归因。

这次 `paired` 的 indexed 前 7 轮为 0.058683 ns/元素，后 7 轮为 0.058575 ns/元素；iterator 对应为 0.058684 与 0.058643。这些只是同一次运行内的局部摘要，不能据此宣称系统没有漂移。要判定长期稳定性，应在不同时段独立重跑，并保留每次运行的环境与顺序。

::: think 思考 · 前后段只差 0.0001，能算「没有漂移」吗 {#think-1.4.1}

上面四个数的前后差分别约为 0.000108 与 0.000041 ns/元素，而批均值的样本标准差在 0.0005 量级。能据此写「本次运行无漂移」吗？

::: sol 解答

不能。第一，这个差值远小于批间波动，本来就在噪声范围内，检测不出漂移不等于证明没有漂移；第二，前 7 与后 7 只覆盖「同一次运行内的时间位置」，管不到跨时段的温度循环、别的机器、别的后台负载（[@def-1.2.3]）。诚实的写法是把这四个数作为摘要公开，并说明它只支持「本次运行内未见明显时间结构」这一条弱结论。

:::

:::

### 1.4.5 21 是奇数：把设计缺陷写出来

21 是奇数，因此 A 先运行 11 次，B 先运行 10 次。这不是完全平衡的交叉设计。「平衡」指每个实现出现在每个位置上的次数相同。这一章选择 21，是为了保留统一的小样本协议；代价是顺序次数有一轮差异。这个差异没有被隐藏。如果顺序效应很强，应该使用偶数轮或分块随机化的新实验；结果出来后再挑轮次删掉，会破坏平衡。

### 1.4.6 计时随机化与分析随机化是两件事

交替顺序容易复核，但可能与周期性后台任务偶然相关。随机顺序能减少固定周期绑定，但随机化也应保存种子或完整顺序，否则不能重建一次异常发生的位置。

这一章的正式计时使用确定性交替，bootstrap 重采样使用固定种子 13013。前者决定「机器条件如何分配给实现」，后者决定「如何评估统计量的不确定性」，两者层次不同：报告时要分开写，不能把分析种子说成计时随机化。

### 1.4.7 为什么不并行跑两种实现

并行可以让两种实现处于相近的墙钟时间，但它们会互相竞争 CPU、缓存和内存带宽。此时[@def-1.1.3]里的估计对象已经变成「彼此干扰下的执行」。如果业务确实需要共同运行，这可能是有意义的系统实验；对于这一章的单核工作核比较，它只会引入额外变量。因此正式脚本逐个运行入口，入口内部逐个运行 case，采样也不附着到正式测量进程。

### 1.4.8 绝对差值与比值

绝对差值适合表达每元素多付出的成本，比值适合表达相对变化。但基线接近零时，比值会非常不稳定。

::: ex 例 1.4.2 · 3600 倍加速从哪来 {#ex-1.4.2}

`dce` 的 observed 均值 0.058630038、discarded 均值 0.000016082。有人写下「实测比删掉的版本慢 3600 倍，说明优化器带来 3600 倍加速」。这个说法错在哪？

::: sol 解答

错在把两个不同语义的量做除法。discarded 没有读取数组（[@def-1.1.1]），它的分母仍是 65536 个名义元素；observed 做的是一次真实求和。两者的比只反映「被删掉的工作」与「没被删掉的工作」之差，不是任何一种算法的加速。基线接近零时比值发散，[@def-1.1.3] 因此要求先固定估计对象。真实等价实现之间可以算比值或对数比值，但平均方式要写明——平均比值通常不等于两组均值的比值，更不能在多种统计定义里挑最大加速比。

:::

:::

这一章的主结论使用配对绝对差值；比值只作辅助表达。

### 1.4.9 小结与常见错误

**小结。**① 一轮 = 每个实现各测一批，位置记先后（[@def-1.4.1]）；② 先算配对差值再平均，缺轮整对删（[@def-1.4.2]）；③ `round` 与 `position` 缺失会让配对与顺序效应无法复核（[@ex-1.4.1]）；④ 前后段均值只能给出弱结论，计时随机化与分析种子分层次；⑤ 比值在近零基线上会造出荒谬倍数（[@ex-1.4.2]）。有了这套设计，下一节可以先看一个「假结果」被完整记录下来的样子：[1.5 实验一：DCE 与错误归一化](#sec-cpp-rust.1.1.5)。

::: errata 常见错误清单（1.4 节）

E-a **先跑完 A 再跑完 B。**实现与时间位置混杂，加倍样本只会让错误结论更精确（[@def-1.4.1]）。

E-b **排序后配对。**对应关系被破坏，差值不再是同轮差值（1.4.2 的流程框）。

E-c **只删一侧的慢批。**配对分布被单侧删点改变，必须整对删除。

E-d **没测出漂移就宣称无漂移。**差值小于批间波动时，检测不到不等于不存在（见本节的思考框）。

E-e **不报告 21 是奇数。**顺序次数不平衡是设计代价，写出来比假装平衡更可信。

E-f **把分析种子当计时随机化。**两者回答不同层次的问题（1.4.6）。

E-g **用近零基线算比值。**得到巨大倍数，语义上却是两件事（[@ex-1.4.2]）。

:::

**第 1 题 · 记忆**　说出「轮」「位置」「配对」各指什么，并写出配对差值的定义。

::: sol 第 1 题答案
一轮是每个参与比较的实现各测一个批次的过程；位置是该批次在这轮里的先后次序；配对是同一轮里两个实现的一对批次。配对差值 `d = b - a`，先按轮算 d，再对 21 个 d 做统计。对应[@def-1.4.1] 与[@def-1.4.2]。
:::

**第 2 题 · 辨析**　「我做了 42 批，比 21 批更可信。」这句话在什么设计下才成立？

::: sol 第 2 题答案
只有当新增的 21 批仍然与另一实现同轮配对（或至少两个实现都等量增加且顺序交替）时才成立。如果是把 A 从 21 批加到 42 批而 B 仍是 21 批，两组的时间覆盖不同，样本更多只是让组间偏差更「精确」，不是更可信。
:::

## 1.5 实验一：DCE 与错误归一化 {#sec-cpp-rust.1.1.5}

本节回答一个问题：**一个被优化器删空的实验，完整记录下来的样子是什么？**1.1 用两行汇编说明工作会被删掉；这一节把同一个错误放进正式协议里——21 个批次、原始 CSV、代码生成证据和回归测试，看它怎样一路通过所有检查，最后只在解释阶段被抓住。

::: preview 先抓住一件事

这个实验的失败方式是**静默**的：构建成功、测试通过、断言满足、数字漂亮。识别它不靠更贵的计时器，而靠两个动作——把结果送进观察集合（[@def-1.3.1]），以及核对分母是否代表真实工作量。
:::

### 1.5.1 实验设置：两个 case，一套夹具

下面是 `src/bin/dce.rs` 的完整入口。公共夹具和工作核位于同包的 `src/lib.rs`；包没有第三方依赖，`Cargo.lock` 已经生成并保留。

```rust
use foundations_lab::{Case, N, data, dce_empty, run, sum_iter};
use std::hint::black_box;

fn main() {
    let input = data(N);
    let expected = input.iter().fold(0u64, |a, &b| a.wrapping_add(b));
    let mut cases = [
        Case {
            name: "discarded",
            work: Box::new(|| dce_empty(black_box(&input))),
            expected: 0,
        },
        Case {
            name: "observed",
            work: Box::new(|| sum_iter(black_box(&input))),
            expected,
        },
    ];
    run(&mut cases, 256, N);
}
```

这个入口有意保留两种不同的输出契约：`discarded` 的 `expected` 是 0，不冒充求和值；`observed` 的 `expected` 来自独立的参考计算。于是你能看到失效夹具为什么仍然「正确通过断言」。

::: def 定义 1.5.1 · 名义元素 {#def-1.5.1}

**名义元素**指「用来做分母的元素个数」，而不是「实际被访问的元素个数」。当数组求和被 DCE 删掉（[@def-1.1.1]）后，代码一次也没有读这 65536 个 `u64`，但归一化仍然除以 65536——这就是名义分母。

:::

按[@def-1.5.1]，本实验两个 case 里只有 `observed` 的元素数是真实的；`discarded` 的数字是有意保留的反例，用来演示单位被误用。它不参与「谁更快」的排名。

### 1.5.2 两个工作核

```rust
#[inline(never)]
pub fn dce_empty(input: &[u64]) -> u64 {
    let _ = input.iter().copied().fold(0u64, u64::wrapping_add);
    0
}

#[inline(never)]
pub fn sum_iter(input: &[u64]) -> u64 {
    input.iter().copied().fold(0u64, u64::wrapping_add)
}
```

两个函数只差一行：`dce_empty` 算完就把结果丢掉，然后返回 0。输入经过 `black_box` 后，长度和内容不再能被调用方简单固定，但 `fold` 的结果仍然没人要，所以整个循环被删。这是「输入不透明修不了输出无用」最干净的证据（对照 1.1 里那两行汇编）。

### 1.5.3 描述统计：这张表在说什么

::: def 定义 1.5.2 · 均值、标准差与 nearest-rank 分位数 {#def-1.5.2}

一个 case 有 21 个批均值（[@def-1.2.2]）。**均值**是它们的算术平均；**标准差 sd** 用 N−1 作分母，是「批与批之间波动」的估计；**分位数 p50/p99** 用 nearest-rank 定义：把 21 个数排序后取第 `ceil(21 × 0.50)`、第 `ceil(21 × 0.99)` 个。

:::

来源是 `results/native-01/dce.csv`，按[@def-1.5.2]统计，单位都是 ns/名义元素。

| case | mean | sd | 批 p50 | 批 p99 |
|:--|--:|--:|--:|--:|
| discarded | 0.000016082 | 0.000001491 | 0.000014901 | 0.000019848 |
| observed | 0.058630038 | 0.000235237 | 0.058561563 | 0.059458137 |

第一行不是求和性能，它反映的是剩余调用与夹具成本被巨大名义分母稀释的结果。第二行才执行了声明的数组求和，但它也不能读成「一次 `u64` 加法的延迟」：它是多条向量加载、累加链和归约共同形成的聚合成本。

::: ex 例 1.5.1 · 读懂这张表 {#ex-1.5.1}

observed 的均值是 0.058630038 ns/元素，标准差是 0.000235237，21 批的 p99 是 0.059458137。

1. 这个均值能不能解释为「一次 `u64` 加法需要 0.0586 ns」？
2. discarded 的 0.000016082 为什么不能拿去和 observed 比？
3. 如果只报告均值，会漏掉什么？

::: sol 解答

1. 不能。它是批次墙钟时间除以元素数的批均值（[@def-1.2.2]），包含向量加载、累加链、归约和夹具成本，不是单条指令的延迟。
2. 因为 discarded 的循环被 DCE 删掉了（[@def-1.1.1]），分母仍是 65536 个名义元素（[@def-1.5.1]）。它测的是「空路径被大分母稀释」，不是求和；两者不是同一语义工作。
3. 会漏掉批次之间的波动和尾部分布。sd 0.000235237 说明 21 批之间有波动；p99 0.059458137 是这批样本的最大值（因为 `ceil(21 × 0.99) = 21`），不是生产请求的 p99。

:::

### 1.5.4 代码生成核对：四个层次各说一句话

导论里那条流水线（cargo → rustc → MIR → LLVM IR → 机器码）在这里全部用上。同一个判断，要在每一层单独核对：

| 层次 | 实际证据 | 支持的判断 | 不支持的判断 |
|:--|:--|:--|:--|
| MIR | `dce_empty` 仍可见迭代语义 | 前端确实接收了源码工作 | 后端一定执行这些操作 |
| LLVM IR | `dce_empty` 返回常量 0 | 优化后求和已删除 | 所有编译器都在同阶段删除 |
| 本机汇编 | `mov` 与 `ret` | 函数不读取数组 | 调用点全部零成本 |
| `sum_iter` | 指向 `sum_soa` 的符号别名 | 相同实现被合并 | Rust ABI 永久固定 |
| sample | 独立 locality/borrow 运行 | 工作核可以出现在运行栈 | 正式批次有相同采样比例 |

ABI（应用二进制接口）这一列要说清楚：别名是当前构建产物的观察结果，不是语言承诺。归档包含实际的 `.mir`、`.ll`、`.s` 完整文件，不是从网页抄来的相似汇编；本机 `dce_empty` 的有效主体就是 `mov x0, #0` 与 `ret` 两行，调试行号和调用帧信息（CFI）省略。这里只用它证明「没有遍历数组」，不扩写成汇编教程：函数调用、链接和调用方屏障仍要看完整产物。

### 1.5.5 修复方式与回归测试

失效版本是实验语义错误，不是内存安全错误。修复方法是把真实结果返回，在调用边界观察，并用参考值检查结果，不只读一个常量哨兵。如果应用本来只需要判断结果是否为零，就按该应用的输出重建夹具，不必为了 benchmark 强行保留完全无用的中间量。

可执行回归测试 `tests::sums_and_representations_agree` 比较不同输入长度：0、1、7、65、65536。短长度覆盖向量化尾部之外的路径；它们都要求索引与迭代器得到相同的模加法结果。这个测试不把 `discarded` 当成合法求和实现——它的作用是维护语义分界。

::: think 思考 · 加一条「结果不能是常量」的检查行不行 {#think-1.5.1}

有人提议：在 `run` 里加一句 `assert!(outputs.iter().any(|&v| v != 0))`，这样 `dce_empty` 就会被抓住。这个检查能不能推广成通用防线？

::: sol 解答

不能。它只是针对这一个反例的巧合检查：合法的求和结果本来就可能为 0（例如空输入或恰好抵消的模加法），加了这条会误伤正确实现；而把 `fold` 换成一个非零常量的实现照样能绕过它。通用的防线只有两条：期望值来自独立参考计算（本节入口里的 `expected`），以及[@def-1.3.1]要求逐次观察输出。检查得越强，越要保证它对正确的实现也成立。

:::

:::

### 1.5.6 数据生成器为什么不是随机数发生器

生成器采用「索引乘 17 再异或常量」的方式，提供确定且不全相同的输入。它不声称代表生产数据分布。对无分支整数求和来说，元素值分布不决定循环访问次数；换成条件过滤、压缩或哈希表，分布就可能成为主要变量——那时必须新增输入家族，不能继续沿用「求和不敏感」的判断（[@def-1.1.3] 的输入集合）。

### 1.5.7 小结与常见错误

**小结。**① 一个被删空的实验可以全程「绿灯」，只在解释阶段暴露；② 分母必须是真实工作量，否则得到名义数字（[@def-1.5.1]）；③ 描述统计要连着样本数一起读，21 个数上的 p99 就是最大值（[@def-1.5.2]）；④ 判断保留还是删除，要按 MIR / LLVM IR / 汇编 / 别名 / 采样逐层核对，每层只支持它能支持的那句话。下一节 [1.6 实验二](#sec-cpp-rust.1.1.6) 用同一套夹具比较两个都真的在工作的实现。

::: errata 常见错误清单（1.5 节）

E-a **拿名义分母的数字去排名。**[@def-1.5.1] 的 discarded 比 observed 快 3600 倍，只是删除的证明。

E-b **把批均值当单条指令延迟。**聚合成本与因果延迟是两个对象（[@def-1.5.2]）。

E-c **只报均值。**sd 与分位数说明波动；21 个数的 p99 恰好是最大值。

E-d **用「结果不能为 0」当通用防线。**它会误伤正确实现，也挡不住返回非零常量的实现（见本节的思考框）。

E-e **让期望值与被测实现同源。**断言于是只能验证错误目标（[@ex-1.5.1]）。

E-f **把符号别名当 ABI 承诺。**别名是当前构建的观察，不是接口保证（1.5.4）。

:::

**第 1 题 · 记忆**　两个工作核只差一行代码，为什么性能差四个数量级？

::: sol 第 1 题答案
`dce_empty` 丢掉 `fold` 的结果并返回 0，编译器据此删除整段循环（[@def-1.1.1]）；`sum_iter` 返回结果并被逐次观察，循环真的执行。分母都是 65536，所以差异全在「有没有工作」上，不是快慢。
:::

**第 2 题 · 辨析**　`discarded` 的 sd 是 0.000001491，比 observed 的 0.000235237 小得多。这能说明空路径「更稳定」吗？

::: sol 第 2 题答案
不能。两者测的对象不同：前者是计时与调用开销的残差，后者是真实内存带宽与向量化路径的波动。对象不同时，sd 的大小关系没有可解释的含义（[@def-1.5.2]）。
:::

**第 3 题 · 应用**　你跑出的数字是 0.00002 ns/元素，怀疑被删了。给出最小的一步验证。

::: sol 第 3 题答案
看目标汇编里那个函数：若只剩装载常量与 `ret`（像本节的 `mov x0, #0`），就是被删了；或把返回值送进 `black_box` 并打印，再看数字是否跳到合理量级。这比换计时器或加批次更快定位。
:::

**第 4 题 · 迁移**　把同一个夹具用于「统计数组里大于 50 的元素个数」。数据生成本节还能不管分布吗？

::: sol 第 4 题答案
不能。比较操作引入分支，元素分布决定分支走向与是否可向量化，输入家族就成了主要变量之一。要按 1.5.6 的方式新增至少两组分布（例如均匀与极端集中），并在契约里写清（[@def-1.1.3]）。
:::

:::

## 1.6 实验二：索引与迭代器的配对观察 {#sec-cpp-rust.1.1.6}

本节回答一个问题：**两个都在正常工作的实现，差异小到什么程度就该停手？**1.5 看的是被删空的假结果；这一节看一个诚实的实验怎样得出「当前证据分不出方向」，并且说清这个区间是怎么来的、能支持什么结论。

::: preview 先抓住一件事

「没测出差异」有两种完全不同的含义：两者确实几乎等价，或者实验的检测能力不足。区分它们靠的不是更多小数位，而是把差值的波动和实验本身的分辨能力一起报出来——这就是配对差值加区间的作用。
:::

### 1.6.1 两个实现，一份参考结果

::: def 定义 1.6.1 · 等价工作比较 {#def-1.6.1}

两个实现构成**等价工作比较**，当且仅当：输入相同、算术语义相同（本例为 `u64` 模加法，见 1.1.5）、输出对调用方可观察，并且用同一份独立计算的参考值校验。只有满足这些条件，比较耗时才叫「同样的工作，不同的写法」。

:::

`src/bin/paired.rs` 与第一个入口独立编译，共享夹具，但不共享正式原始批次。按[@def-1.6.1]，两种实现都必须返回同一参考结果：

```rust
use foundations_lab::{Case, N, data, run, sum_index, sum_iter};
use std::hint::black_box;

fn main() {
    let input = data(N);
    let expected = input.iter().fold(0u64, |a, &b| a.wrapping_add(b));
    let mut cases = [
        Case {
            name: "indexed",
            work: Box::new(|| sum_index(black_box(&input))),
            expected,
        },
        Case {
            name: "iterator",
            work: Box::new(|| sum_iter(black_box(&input))),
            expected,
        },
    ];
    run(&mut cases, 512, N);
}
```

索引核使用 `while`，循环条件与输入长度之间提供了边界证明机会，它没有使用 unchecked 访问。迭代器核使用 `copied` 与 `fold`。两者都用模加法，不借助未定义行为（UB）给优化器不真实的前提。

```rust
#[inline(never)]
pub fn sum_index(input: &[u64]) -> u64 {
    let mut sum = 0u64;
    let mut i = 0;
    while i < input.len() {
        sum = sum.wrapping_add(input[i]);
        i += 1;
    }
    sum
}
```

### 1.6.2 共同夹具的计时核心

完整的 `run` 函数还包括预热、轮转顺序与 CSV 输出。关键计时部分如下：

```rust
let start = Instant::now();
for output in &mut outputs {
    *output = black_box((case.work)());
}
let elapsed = start.elapsed();
assert!(outputs.iter().all(|&v| v == case.expected));
let ns = elapsed.as_secs_f64() * 1e9 / (iterations * units) as f64;
```

输出检查在 `elapsed` 之后，`black_box` 在 `elapsed` 之前。改变这两个位置，就改变了[@def-1.1.3] 里的计时集合与观察集合。阅读别人的夹具时要逐项确认位置，不能只看调用了什么函数（[@def-1.3.1] 要求逐次观察）。

### 1.6.3 实测：均值接近，区间跨零

来源是 `results/native-01/paired.csv`，单位是 ns/元素，统计口径按[@def-1.5.2]。

| case | mean | sd | 批 p50 | 批 p99 |
|:--|--:|--:|--:|--:|
| indexed | 0.058694076 | 0.000458518 | 0.058524311 | 0.060221791 |
| iterator | 0.058768701 | 0.000541829 | 0.058590114 | 0.060894847 |

iterator 减 indexed 的配对均值（[@def-1.4.2]）为 0.000074625 ns/元素，配对差值样本标准差为 0.000484383。固定种子 bootstrap 区间为 [−0.000128553, 0.000269819]，跨零。

::: ex 例 1.6.1 · 区间跨零该怎么解释 {#ex-1.6.1}

上面这组数据的区间跨零。再看一组假想数据：同一轮 A=0.0600、B=0.0601，下一轮机器整体变慢成 A=0.0700、B=0.0701。

1. 为什么配对差值比「先跑完 A 再跑完 B」更稳？
2. 这组假想数据能证明 B 永远比 A 慢 0.0001 吗？
3. 真实数据的区间跨零，可以写「两者等速」吗？

::: sol 解答

1. 同一轮的 A、B 共享了大部分时间条件，整体变慢在差值里被抵消；独立分组会把「机器变慢」误当成实现差异（[@def-1.4.1]）。
2. 不能。它只说明这两轮的差值相同；还需要更多轮次、区间和不同环境。配对减少偏差，不消除所有偏差。
3. 不能。跨零只说明当前证据不足以确定方向；「等速」是更强的断言，需要匹配目标容差的独立重复才谈得上。

:::

:::

### 1.6.4 区间是怎么算出来的

::: def 定义 1.6.2 · bootstrap 置信区间 {#def-1.6.2}

对 21 个配对差值做**有放回重采样**：每次抽 21 个差值算一个均值，重复 10000 次，得到「均值」这个统计量的经验分布；取该分布排序后的 2.5% 与 97.5% nearest-rank 点，就是 95% **bootstrap 置信区间**。随机种子固定为 13013，算法保存在 `analyze.py::paired_interval`。

:::

[@def-1.6.2] 有两处前提要摊开说。第一，它把 21 个差值当成可交换的重复；如果差值有明显的时间相关性（1.4.4 的漂移就是这种相关性），这个假设不成立，区间会偏窄。第二，它只覆盖「本次运行内的抽样波动」，不包含编译器版本、机器差异和跨时段变化。因此它是当前运行的不确定性摘要，不是所有环境下 95% 的性能保证。

### 1.6.5 为什么不能只比较两个标准差

两组各自的 sd 不能替代配对差值的 sd。同一轮可能共同经历更慢的系统条件，这种共同变化在差值中会部分抵消；也可能存在相反方向的缓存影响。必须根据原来的配对计算。

::: think 思考 · 「两条误差条重叠」能不能判等价 {#think-1.6.1}

indexed 的区间大约是均值 ± sd，iterator 也类似，两条形带明显重叠。可以直接写「两者等价」吗？

::: sol 解答

不能，理由有两层。第一，「误差条重叠」不是统计检验，两条带重叠与差值区间是否含零是不同计算；这里该看的是配对差值区间（[@def-1.6.2]）。第二，即使区间不含零，也只能说「本次运行内可区分方向」，说不上等价——等价需要预先给出容差，也就是 1.7 要处理的回归预算。本章不报没有计算的 p 值，也不在结果出来后换统计量寻找显著性。

:::

:::

### 1.6.6 代码生成能补什么，不能补什么

本机的 `sum_iter` 与 `sum_soa` 是 LLVM 别名，`indexed` 保持独立符号；两者都保留了实际的加载与归约。相近的性能与生成的批量处理路径相容——但相容不等于完整归因。没有采集指令退休数或性能监控单元（PMU）事件，因此这里不报告「每元素恰好执行几条指令」。静态证据的作用是排除「根本没执行」这类误测（对照 1.5.4），不是替代计时。

### 1.6.7 不确定不代表不能行动

::: method 判定流程 · 分不出方向时怎么办

**只是选可维护写法**：直接保留迭代器版本，理由写「可读性与已有正确性约束」，不要编造「更快」。
**预算很紧**：增加匹配真实输入的独立重跑，或测完整调用链，看内联之后是否仍然相近。
**差异远小于容忍带**：停止争论小数末位，把时间花在别的层（先看 13 章定位热点）。
**要下「等价」结论**：先固定容差 B，再按[@def-1.6.2]的区间判断，规则在看到数字之前定好。

:::

### 1.6.8 小结与常见错误

**小结。**① 只有满足[@def-1.6.1] 的比较才谈得上「同样工作的两种写法」；② 差值区间按[@def-1.6.2] 计算，它只覆盖本次运行的抽样波动；③ 跨零意味着方向未知，不意味着等速；④ 误差条重叠不是检验，等价需要容差；⑤ 静态代码证据能排除「没执行」，不能替代计时。下一节 [1.7 置信区间、回归预算与三态门禁](#sec-cpp-rust.1.1.7) 把「什么时候该停手」写成可执行的判定。

::: errata 常见错误清单（1.6 节）

E-a **拿两组的 sd 直接合成差值的 sd。**必须按配对计算（1.6.5）。

E-b **跨零就写「等速」。**跨零只表示方向未定（[@ex-1.6.1]）。

E-c **把 bootstrap 区间当跨机器保证。**它不含版本与机器差异（[@def-1.6.2]）。

E-d **用误差条重叠代替检验。**两者是不同的量（见本节的思考框）。

E-e **改了夹具位置还说同一回事。**`black_box` 与断言的先后属于计时集合与观察集合（[@def-1.1.3]）。

E-f **从别名推断「每元素几条指令」。**没采的事件不进结论（1.6.6）。

:::

::: method 即时自测 · 1.6

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　说出 bootstrap 区间的四步算法，并指出它的两处前提。

::: sol 第 1 题答案
对 21 个配对差值有放回抽 21 个、算均值、重复 10000 次、取排序后的 2.5% 与 97.5% 点。前提是差值可交换（无明显时间相关）且只覆盖本次运行的抽样波动，不含编译器版本与机器差异。对应[@def-1.6.2]。
:::

**第 2 题 · 辨析**　「indexed 的均值更小，所以索引写法更快。」这句话漏了什么？

::: sol 第 2 题答案
漏了不确定性。均值差 0.000074625 的区间跨零，方向本身没定；而且 21 批的差值只覆盖这一次运行的时间条件。正确表述是「本次实验中索引均值略低，但方向不可判定」（[@ex-1.6.1]）。
:::

**第 3 题 · 应用**　你要用同样的协议比较两个序列化器，输出差异在 1% 量级且区间跨零。给出两个能真正推进决策的动作。

::: sol 第 3 题答案
① 先定容差 B（例如「慢于 3% 才需要处理」），再按区间判定，这样跨零可以直接归为「在容差内可接受」（1.6.7）。② 提高检测能力：在真实输入分布上做独立重跑，或测完整调用链，看内联后差距是否放大。换更多小数位或同一批数据反复算统计量都不算动作。
:::

**第 4 题 · 迁移**　把夹具里 `assert!` 挪到 `elapsed` 之前，结论会怎么变？

::: sol 第 4 题答案
断言进入计时区间，测到的变成「工作 + 校验」的混合成本；两种实现都加同一份开销时，差值方向未必变，但绝对值被抬高，且比较的对象已不是[@def-1.6.1]声明的工作。位置变化必须同时更新契约（[@def-1.1.3]）与表格标题里的单位说明。
:::

## 1.7 置信区间、回归预算与三态门禁 {#sec-cpp-rust.1.1.7}

本节回答一个问题：**差异要多小才算「不算差异」，这个标准该由谁定？**1.6 得到一个跨零的区间；这一节把它变成可执行的判定：先定预算，再看区间落在预算哪一侧，最后按三态处理。

::: preview 先抓住一件事

统计问题（差值是多少、有多不确定）和工程问题（多大差异才值得处理）必须分开回答。**预算由业务定，区间由实验定**；把两者混成一个「超过 5% 就退回」的口号，等于把决策权交给了一个没有依据的常数。
:::

### 1.7.1 统计显著与工程重要是两件事

统计上可分，和工程上重要，是两件事。数据量很大时，极小的差异也可能稳定可分，但维护复杂度和安全边界可能远比它重要。相反，小样本未能区分，不表示不存在重要回归。性能门禁需要同时表达效应大小和不确定性；只看一个均值阈值，容易在噪声附近反复抖动。

::: def 定义 1.7.1 · 回归预算 B {#def-1.7.1}

**回归预算** B 是「本次变更允许的最大性能回退」，用与统计量相同的单位表达（绝对 ns/元素，或明确定义的相对量）。它必须来自业务需求或资源成本：一次请求的延迟余量、一个容器的 CPU 配额、一份 SLA 承诺。[@def-1.7.1] 要在使用[@def-1.6.2]的区间做判定之前写下，看到数字之后再定等于没有定。

:::

先设定预算，再采集数据。这一章不替你发明一个通用的「5% 就是回归」：不同服务对 CPU、内存和尾延迟有不同约束，同一组件也可能有多个同时成立的预算。

### 1.7.2 三态判定

::: def 定义 1.7.2 · 三态门禁 {#def-1.7.2}

设回归量为「候选 − 基线」的配对差值（[@def-1.4.2]），其区间为 [L, U]，预算为 B：

- **U ≤ B → 接受**（当前证据未越预算）；
- **L > B → 拒绝**（当前证据支持超预算）；
- **其余 → 证据不足**：既不能证明没超，也不能证明已超。

:::

| 区间与预算关系 | 结论 | 合理动作 |
|:--|:--|:--|
| U ≤ B | 当前证据未越预算 | 记录协议后接受 |
| L > B | 当前证据支持超预算 | 阻止发布并分析 |
| L ≤ B，且 U 更大 | 证据不足 | 独立重跑或扩大匹配输入 |
| 正确性失败 | 不进入性能判断 | 先修功能与契约 |
| 夹具被优化删除 | 估计对象失效 | 重建观察边界（[@def-1.3.1]） |

读图：三条横条是同一种东西，都是配对差值的 95% 区间。判定的依据看区间整体在预算线的哪一侧，不看均值小不小：完全在左侧才叫「当前证据未越预算」，完全在右侧才叫「当前证据支持超预算」，跨过去就是第三种结论，动作是补证据，不是二选一。③ 的均值 0.0004 其实比 ① 的均值 0.0003 更差，但两者给的是完全不同的句子。[@def-1.7.2] 因此要三态，不能压成两态。

[@def-1.7.2] 里的「接受」不是永久保证，它只适用于固定的输入家族、环境和构建。生产上线仍然可能需要金丝雀发布（先放一小部分流量观察）和资源监控。

::: ex 例 1.7.1 · 这个变更能不能发布 {#ex-1.7.1}

预算 B = 0.0005 ns/元素（业务约定：每元素多花 0.0005 纳秒以内可接受）。三组候选的配对差值区间分别是：① [0.0002, 0.0004]；② [0.0006, 0.0011]；③ [−0.0001, 0.0009]。给出各自的判定与下一步。

::: sol 解答

① U = 0.0004 ≤ B → **接受**，记录协议（输入、构建、环境）后发布。② L = 0.0006 > B → **拒绝**，阻止发布并分析原因（可能是分派粒度或分配次数）。③ L ≤ B，且 U 更大 → **证据不足**：不能放行说「没问题」，也不能退回说「已证明变慢」；要么独立重跑加大样本，要么承认这个差异在工程上不重要并改用更大的 B（但 B 的修改要在看到数字之前提出）。

:::

:::

### 1.7.3 多重比较的代价

::: def 定义 1.7.3 · 探索性实验与确认性实验 {#def-1.7.3}

**探索性实验**用来发现机制，可以自由改输入、换指标、看各种切片；**确认性实验**用来出结论，协议、输入家族、统计量和判定规则在采集前固定，并独立重跑。[@def-1.7.3] 分开的原因很简单：在同一批数据上反复调整再报告「最好的一次」，等于把偶然极值当成稳定收益。

:::

同时测试许多输入、参数和实现，偶然极值会变多。从几十张表里挑最快的一张会高估收益；根据结果不断调整输入、再用同一批数据下结论，也是选择偏差。这一章是带有教学目标的桌面实验，属于[@def-1.7.3] 的探索性一侧，没有宣称完成跨时段的确认性发布验证。

### 1.7.4 别让 CI 噪声变成组织噪声

共享 CI 机器常同时运行构建、测试和安全扫描。如果没有串行化协议，微基准结果会随排队位置变化。把每次微小变动都标红，会让维护者忽略真正的回归。

合理的门禁应该区分快速正确性测试和较慢的正式测量：正确性失败立即阻塞；性能证据不足可以触发专门的复测队列。复测要有事先约定的停止规则和汇总方式——反复重跑直到撞上一次绿灯，等于把[@def-1.7.2] 的三态压成「重跑直到好看」。

### 1.7.5 变更不只是源码变更

工具链升级可能改变向量化和分配器调用，目标 CPU 参数可能改变指令选择，LTO 和代码生成单元也会改变优化可见范围。因此基线和候选必须记录构建配置。如果配置本身就是变更对象，应该把它明确写入实验因素。如果同时换编译器和算法，差异就无法归因；把配置变更单独列为实验因素。

### 1.7.6 内存和正确性预算不能被速度覆盖

一个更快的实现可能分配更多内存，也可能降低精度或扩大 panic 面。这种取舍必须显式列出。这一章的求和实验使用相同输入和算术语义；第 2 章的布局实验改变总数据布局；第 3 章的复制实验改变所有权和资源工作量。跨章表格不能脱离这些边界直接横向排名。

::: think 思考 · 快 8%、内存多 40%，发不发 {#think-1.7.1}

一个改动让批均值下降 8%，但峰值内存从 240 MB 涨到 336 MB。你的[@def-1.7.1] 只写了「每元素耗时」。哪里出了问题？

::: sol 解答

预算漏项。只定义了时间预算，就等于默认内存无代价，而这两个资源常常互相兑换（更大的缓冲、更少的重算、更长的复用链）。正确做法是把 B 写成一组约束：时间预算 + 内存预算 + 正确性要求，任何一条被突破都算失败；如果只能选一个，就把取舍和受影响的工作负载写进结论，而不是只报「快 8%」。

:::

:::

### 1.7.7 异常值怎么处理

这次实验保留全部 21 个正式批次，没有按「看起来像后台干扰」删除慢批。如果确实有外部事件证据，应该记录事件和受影响批次，可以另做包含与排除的敏感性分析，但不能只发布有利的一种。从观测值大本身推定「它必定无效」是循环论证；尤其在尾延迟研究中，慢值可能正是研究对象。

### 1.7.8 重跑要生成新归档

脚本拒绝覆盖已有输出目录，这是为了避免新结果悄悄替换旧证据。重跑时应该使用新目录名，然后对运行间差异另行分析。不要把不同运行中各自最快的批次拼成一份新样本，这样的样本不对应任何真实实验过程。

### 1.7.9 可执行的绝对预算判定

包里的 `gate.py` 把[@def-1.7.2] 实现为纯函数。它不读取计时器，也不修改原始 CSV；输入区间和预算必须采用同一绝对单位。函数拒绝非有限数和倒置区间，避免 `NaN` 悄悄让比较全部返回 false。门禁代码本身也有四组单元测试。

下面按盘上 `bench/foundations-lab/gate.py` 逐字列出，包含它依赖的 `unittest` 导入与文件末尾的四组单元测试：

```python
#!/usr/bin/env python3
"""An absolute-budget gate, deliberately separate from data collection."""
import math
import unittest


def decide(interval, budget):
    """Interval is candidate-minus-baseline in the same absolute unit as budget."""
    low, high = interval
    if not all(math.isfinite(value) for value in (low, high, budget)):
        raise ValueError('non-finite gate input')
    if low > high:
        raise ValueError('reversed interval')
    if high <= budget:
        return 'accept'
    if low > budget:
        return 'reject'
    return 'inconclusive'


class GateTests(unittest.TestCase):
    def test_accept(self):
        self.assertEqual(decide((-2, -1), 0), 'accept')
        self.assertEqual(decide((0, 1), 1), 'accept')

    def test_reject(self):
        self.assertEqual(decide((2, 3), 1), 'reject')

    def test_inconclusive(self):
        self.assertEqual(decide((0, 2), 1), 'inconclusive')
        self.assertEqual(decide((1, 2), 1), 'inconclusive')

    def test_invalid(self):
        for interval, budget in [((2, 1), 0), ((0, math.inf), 0),
                                 ((math.nan, 1), 0), ((0, 1), math.nan)]:
            with self.assertRaises(ValueError):
                decide(interval, budget)


if __name__ == '__main__':
    unittest.main()
```

边界相等时的选择也是协议。这个函数把 `high == budget` 视为可接受；`low == budget` 但 `high` 更大时，仍然是证据不足。这样「所有可能都超出预算」和「可能超出」就分开了。测试专门覆盖这两个边界。团队可以选择别的保守规则，但规则必须在看到候选数字之前固定，不能为当前变更临时改变等号含义。

执行方法：

```bash
python3 bench/foundations-lab/gate.py
```

它测试接受、拒绝、证据不足和非法输入，不替读者提供通用预算数值。工程预算仍应由工作负载和资源目标决定。把一段正确的比较代码接到错误单位上，仍然会得到错误决策，因此接口名和日志里都应该保留量纲。

### 1.7.10 相对预算不能直接塞进绝对区间

如果预算是百分比，不能与 ns/元素差值直接比较。需要把统计量也改成相应的相对量，可以使用每轮比值，或另建明确的归一化模型。基线接近零时，相对量会失去稳定解释；基线本身的不确定性也不应被忽略。用基线的一个点估计缩放整个绝对区间，只是一种近似；如果采用，应该在报告中说明。这一章的 gate 只接收绝对量，避免混淆两套规则。

### 1.7.11 串行依赖与停止规则

连续批次可能共享热状态和系统负载。如果差值具有时间相关性，逐点 bootstrap 可能低估不确定性（见 1.6.4 的第一个前提）。分块重采样是候选改进，但块长度也需要依据，不能仅为缩小区间而选择块长。另一种办法是在不同时段重启进程采集独立运行，把「运行」作为更高层抽样单位。这会使一次运行内的 21 批不再被误当成 21 台独立机器；运行间差异往往比批内差异更接近发布风险。这次实验没有实施这项层级确认实验，因此区间明确限定为运行内摘要。

停止规则也影响判断。如果每测几批就检查一次区间，直到出现满意方向再停止，结论会偏；看到候选慢就继续加样本，看到快就立即结束，也不公平。固定轮数是这一章采用的简单约束。正式发布如果采用顺序分析，应该使用相应的方法和预注册边界（边界在看到数据之前就登记好，不许中途改），不能把固定样本区间当成可以任意窥看的顺序检验。

### 1.7.12 小结与常见错误

**小结。**① 预算 B 是工程约束，必须在采集之前写下（[@def-1.7.1]）；② 判定按区间与 B 的关系给三态，「证据不足」是第三种合法结论（[@def-1.7.2]）；③ 探索性与确认性实验要分开，否则挑出来的是极值（[@def-1.7.3]）；④ 门禁规则（等号归哪边、复测怎么停）要预先固定；⑤ 时间、内存、正确性是并列约束，不能互相覆盖。下一节 [1.8 可追溯证据与复现](#sec-cpp-rust.1.1.8) 处理「别人怎么复核这三态」。

::: errata 常见错误清单（1.7 节）

E-a **看到数字再定预算。**等于允许结论挑选阈值（[@def-1.7.1]）。

E-b **把证据不足判成通过或失败。**三态缺一个就会系统性偏袒某一边（[@def-1.7.2]）。

E-c **在多张表里挑最快的一张发布。**这是选择偏差（[@def-1.7.3]）。

E-d **CI 反复重跑到绿灯。**绕过了停止规则，等价于改协议（1.7.4）。

E-e **同时换编译器和算法。**差异无法归因（1.7.5）。

E-f **只报时间收益不报内存代价。**取舍被隐藏（见本节的思考框）。

E-g **删掉「看着像干扰」的慢批。**没有事件证据时，这是在删研究对象（1.7.7）。

E-h **拼接不同运行的最快批次。**这样得到的样本不对应任何真实过程（1.7.8）。

:::

::: method 即时自测 · 1.7

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　三态判定的三条规则是什么？「证据不足」的下一步动作有哪些？

::: sol 第 1 题答案
`U ≤ B` 接受；`L > B` 拒绝；其余证据不足。证据不足的下一步：独立重跑、扩大匹配真实输入的样本、或者预先改用更大的 B（不能事后改）；如果是正确性或夹具问题，先修功能与契约。对应[@def-1.7.2]。
:::

**第 2 题 · 辨析**　「样本量够大就能证明两者等价。」对吗？

::: sol 第 2 题答案
不对。大样本能可靠地区分微小差异，但「等价」要事先给容差，而且本节的 B 不是那个容差：[@def-1.7.1] 把 B 定成「允许的最大性能回退」，`gate.py` 也只做单侧判定（区间上界 `high ≤ B` 就 accept），变快的那一侧不受约束。要说「业务容差内等价」，得另写一个双侧容差 ±T，并交代 T 与 B 不是一个数——把 `±B` 当等价判据，等于偷偷把单侧预算放宽成双侧。没有事先写下的 T，统计结论只能说到「差异很小」为止。
:::

**第 3 题 · 应用**　CI 上同一份代码三次跑出 accept、reject、inconclusive。你怎么处理？

::: sol 第 3 题答案
先查测量条件是否相同（构建配置、后台负载、串行化锁），把运行当成抽样单位而不是重复样本（1.7.11）；然后按预注册的停止规则汇总，例如「独立三次取多数并公布三个区间」，而不是重跑直到 accept。规则要事先写，不能看到这三次结果之后再定。
:::

**第 4 题 · 迁移**　你要给一个数据库组件设预算，负载是「p99 读延迟 ≤ 10 ms」。[@def-1.7.1] 该怎么写？

::: sol 第 4 题答案
不能写成微基准的 ns/元素。要写成：请求级 p99 在指定并发与数据集下的绝对上界（10 ms），外加允许的相对回退（例如基线 p99 +2%）；统计量随之换成请求级分位数区间——这需要 1.8 里「尾分位数需要不同采集设计」的那套观测方式，而不是本章的批均值。
:::

:::

## 1.8 可追溯证据与复现 {#sec-cpp-rust.1.1.8}

本节回答一个问题：**怎样让别人（和三个月后的你）复核这一章得到的每个数字？**前七节讲的是「一个数字怎样才算可信」，这一节把可信变成可交接：一份归档、一条命令、一句限定范围的结论，以及失败时的分层报告。

::: preview 先抓住一件事

证据的价值在于**能被独立重做**。归档绑定的是对象，不是正确性；结论绑定的是条件，不是保证。复核有两个互不冒充的目标——**结果复算**（同一份 CSV 应得到同一份摘要）和**实验重跑**（新环境会生成新观测）。拿前者的通过去宣称后者，是这一节最常犯的错误。
:::

### 1.8.1 环境是契约的一部分

这次实验的主机在 `native-01/environment.txt` 里只留了 `hw.model: Mac17,9`；同一台机器的芯片名（Apple M5 Pro，18 核）记在同机其它实验的 `environment.txt`（`brand_string`，如 `bench/compiler-lab/results/stable-02/`、`bench/systems-lab/results/run-01/`），缓存行（核之间搬运数据的最小单位）128 字节也来自那些文件。这不是所有 ARM 或所有 Apple 机器的通用常量。实验没有把线程固定在某一类核心上。内存为 25769803776 字节（约 24 GiB），操作系统为 macOS 27.0.1，build 26A434。

编译器为 rustc 1.99.0，提交 `b940084d7eb6a299eb4bfeb8e34901bc051e7ac4`，后端为 LLVM 23.1.1，目标为 `aarch64-apple-darwin`。`RUSTFLAGS` 为 `-C target-cpu=native`；release 使用 `opt-level=3`、`codegen-units=1`、`lto=false`、`debug=1`。这些设置共同限定了代码生成观察，属于[@def-1.1.3]第四组问题（外部条件）的答案。

### 1.8.2 文件级证据链

::: def 定义 1.8.1 · 证据链 evidence chain {#def-1.8.1}

一次可复核的测量，交付的不该只是一张结果表。**证据链**指从「哪个环境、哪份代码」到「哪些原始观测、哪份统计摘要、哪段生成代码」的完整对应关系：每一层都能被单独打开检查，上下两层能互相印证。
:::

| 文件 | 内容 | 可以复核的问题 |
|:--|:--|:--|
| `environment.txt` | 工具链、系统、硬件查询 | 数字属于哪种环境 |
| `source-sha256.txt` | 源文件与脚本指纹 | 运行对应哪一版代码 |
| `build.txt` | 构建输出 | 是否真实编译 |
| `dce.csv` / `paired.csv` | 原始批次 | 是否每个 case 21 条 |
| `statistics.json` | 明确的统计输出 | 表格是否可重算 |
| `codegen/*.mir` | 实际 MIR | 哪些语义进入中间表示 |
| `codegen/*.ll` | 优化后 LLVM IR | 删除、别名、批量化路径 |
| `codegen/*.s` | 本机汇编 | 实际目标机器代码形态 |
| `sample-*.txt` | 独立 macOS 采样 | 运行栈是否包含相应工作核 |

源码指纹不是功能正确性的证明，它只证明归档绑定的是哪个对象。修改夹具后要生成新指纹和新归档；旧汇编只对应旧二进制。

上表按主链口径列九类交付物；`native-01/` 完整归档另含七类：`sample-command.txt`、`timeline.txt`、`lock-owner.txt`、`build-processes.txt`（本次为空）、`layout.txt`、`statistics-stdout.txt`，以及 `profile-locality.csv-excluded` 与 `profile-borrow.csv-excluded`（合一类）。前六类依次记采样命令与进程号、六个二进制启动时刻、取锁进程、构建残留进程、类型布局与 `analyze.py` 标准输出，支撑 1.8.3 的锁与计时边界；最后一类与 `sample-command.txt` 是 1.8.5「采样另起进程、混了预热与正式阶段」的直接证据，按 `run.sh:45-53` 不并入正式统计。只按上表点收，这七类就会留在包里没人核对。

### 1.8.3 复现命令与共享测量锁

从 `cpp-rust/` 目录执行：

```bash
cargo fmt --check --manifest-path bench/foundations-lab/Cargo.toml
cargo test --offline --locked --manifest-path bench/foundations-lab/Cargo.toml
cargo clippy --offline --locked --manifest-path bench/foundations-lab/Cargo.toml --all-targets -- -D warnings
bash bench/foundations-lab/run.sh results/my-new-run
```

最后一个参数相对于实验包目录，目录必须尚不存在。脚本先构建，再取得共享测量锁；编译不在正式计时边界内。测量锁路径是 `bench/.work/measure.lock`：`run.sh` 先 `cd` 进实验包，锁再取当前目录的上一层（`run.sh:32`）。早先用 `$0/..` 的写法有 bug——`$0` 常常是相对路径，`cd` 过一次就解不出来，从仓库根照本书命令调用会在取锁那行退出。锁用 `mkdir` 取得、`EXIT` trap 释放；等满 600 秒拿不到就报错退出，不会无声转圈。不要用手工删除别人的锁来加快等待。

### 1.8.4 两种复现目标

::: def 定义 1.8.2 · 结果复算与实验重跑 {#def-1.8.2}

**结果复算**：给定同一份 CSV，统计脚本应得到相同摘要。它验证的是解析、公式、排序与舍入。**实验重跑**：重新启动二进制，生成新的原始批次，它会受到新环境与时间条件影响。两者都重要，但不能互相冒充：复算通过不证明新机器也会得到同样的纳秒数；重跑接近也不能修复一个错误的统计公式。
:::

实验包把原始 CSV 与 `statistics.json` 同时保留，支持第一种检查；`run.sh` 生成新目录，支持第二种检查。

`source-sha256` 绑定的是当时的计时内核和采集脚本。后续新增的纯门禁测试不参与原来的正式计时，因此不能反过来声称它已包含在 `native-01` 源清单里；补充验证放在 `results/validation-01/`，正式 CSV 仍保留原来的源指纹。改动被测内核必须重新采集；仅新增不参与内核的测试，不会改写旧原始观测。

### 1.8.5 静态证据、采样与计时各回答什么

MIR 适合观察 Rust 层面的控制流和清理义务；优化后 IR 适合观察删除、参数属性与循环转换；汇编适合确认当前目标最终保留的操作。三者各自回答不同问题，生产性能仍要靠实际计时。静态代码还需要与实际执行路径相连，实际计时也需要静态检查来排除误测。两类证据互相约束，而不是互相替代。

macOS 的 `sample` 在另一个进程运行中采集。locality 采样看到了 `sum_aos` 与 `sum_soa`；borrow 采样看到了 `borrowed`、`cloned` 以及求和路径，还可见系统分配器相关栈。这支持「相应工作确实在运行」的有限核对，不提供 cache miss、IPC（每周期指令数）或能耗。采样覆盖了预热与正式循环的混合阶段，因此这一章不把采样占比当成稳定态 CPU 百分比。

### 1.8.6 尾分位数需要另一套采集设计

如果目标是请求 p99，必须保存**请求级观测**，并定义请求到达、开始服务和完成的时间。只保存批次总时长会把内部长短请求平均掉；即使某批因个别慢请求变长，也无法恢复逐请求分布——批次平均稳定，不代表请求长尾稳定。[@def-1.5.2] 的 nearest-rank 也需要样本数支撑：21 个值的最大值不足以定位总体高分位，增加打印精度不解决这个问题。

队列等待还可能发生在工作核入口之前。计时若从开始执行才算，会漏掉准入和排队；若负载发生器等上一个请求完成才发下一个，到达过程本身被改变，这种闭环负载会隐藏系统过载时的积压。

分位数还要说明是否包括失败与超时：只对成功请求计算会排除最慢的路径，而超时值是删失观察（只知道「超过截止值」，不知道真实耗时），不是精确耗时。因此吞吐实验和响应时间实验需要不同夹具，把列名改成 latency 不等于做了请求级测量。这一章的求和核没有到达过程、排队和超时，刻意不提供任何生产请求分位数。

### 1.8.7 量纲与数量级自检

先确认原始时长是秒、微秒还是纳秒；再确认 `K` 与 `N` 是否都进入分母；检查整数乘法是否可能溢出。当前固定的 `K` 与 `N` 远小于 `usize` 范围，但泛化为外部参数时仍应受检。检查工作核是否真的处理了 `N` 个元素：对提前终止的算法，名义输入长度未必等于已处理数量。检查吞吐倒数能否被误读为延迟：对多线程聚合，尤其不能把亚纳秒单位解释为单核调用速度。最后用实际批次时长反向乘回 `K × N`；无法回到原始量级时，就应该暂停解释表格。

量纲检查不是用经验数字替代实测，它的作用是发现单位、工作量或删除路径错误。发现异常快时，优先检查 DCE 与常量折叠；发现异常慢时，检查计时边界、调试构建与后台干扰。两种情况都不应先改数据迎合直觉。

::: ex 例 1.8.1 · 这份复现失败属于哪一层 {#ex-1.8.1}

三则报告：① 换一台机器，`cargo test` 就没过；② 跑通了，但 checksum 与归档不符；③ 跑通且校验通过，批均值 0.11 ns/元素，比本章的 0.0586 大近一倍。各属于哪一层失败？第一行动作分别是什么？

::: sol 解答

① **构建失败**：工具链、目标或依赖环境不同。这一层单独记为构建失败，性能字段留空，先对齐 [@def-1.1.3] 的外部条件。② **功能失败**：候选不满足契约，先修功能——短耗时没有意义（[@ex-1.5.1] 的教训：期望值不能与被测实现同源）。③ **解释失配**：程序正常执行，但新机器的代码生成或布局不同。这不一定是错误，而是结论适用范围变了，应该改写结论句而不是追问「为什么没上一章的数」。
:::

:::

### 1.8.8 发布结论的最小句式

一个合格的结论应该同时包含对象、条件、指标和限制。例如：

> 在这次固定的热数组与 native 构建下，两种求和核的批均值接近，配对差值区间跨零。

这个句子没有承诺语言级等速，也没有把桌面结果提升为服务等级协议（SLA），但它仍然足以指导当前代码的可读性取舍。精确地缩小结论范围，比给一个巨大加速比更专业。

::: think 思考 · 「复算一致，可以发布了吗」 {#think-1.8.1}

你把归档里的 `dce.csv` 重跑一遍 `analyze.py`，摘要与 `statistics.json` 完全一致。能不能据此写「本实验已复核，结论成立」？

::: sol 解答

只能写「统计实现已复核」。**结果复算**验证的是公式、解析与舍入（[@def-1.8.2]），它对「工作是否真的执行」「这台机器之外的条件」一个字都没说。要支撑发布决策，还缺三件：代码证据确认工作未被删除（[@def-1.1.1] 的反面检查）、预先写下的预算与三态判定（[@def-1.7.2]）、以及目标环境自己的观测。复算通过是必要条件，不是充分条件。
:::

:::

### 1.8.9 复现失败要分层报告

::: method 判定流程 · 五层失败各查各的

① **构建失败**——工具链、目标或依赖不同；单独记为构建失败，性能字段留空。<br>
② **功能失败**——checksum 或断言不过；先修功能，短耗时没有意义。<br>
③ **采集失败**——原始记录缺轮次；分析脚本对 `round` 集合做严格检查，不会默默把缺失批次当成有效小样本。<br>
④ **解释失配**——程序正常执行，但新机器的代码生成或布局不同；这是结论范围变化，不一定是错误（[@ex-1.8.1]）。<br>
⑤ **统计不确定**——区间跨预算；继续改进证据，而不是二选一（[@def-1.7.2]）。
:::

把这五层都写成「benchmark 失败」，会妨碍定位：五层的修法完全不同，混在一起就只能整章重跑。

### 1.8.10 小结与常见错误

**小结。**① 交付的是证据链而不是一张表（[@def-1.8.1]）；② 复算与重跑是两个目标，不能互相冒充（[@def-1.8.2]）；③ 静态证据、采样、计时各答一个问题，缺哪一层就少说一句话；④ 请求级尾延迟要另一套采集设计，不是把批均值换个列名；⑤ 结论句必须带对象、条件、指标、限制，失败要分五层报告。下一节 [1.9 延伸阅读与来源](#sec-cpp-rust.1.1.9) 交代这些方法的出处。

::: errata 常见错误清单（1.8 节）

E-a **把环境写成一行 CPU 名称。**缓存行、核数、rustc 提交、`RUSTFLAGS` 共同限定结论范围（1.8.1）。

E-b **用复算通过宣称实验成立。**它只验证统计实现，不含代码证据与环境（[@def-1.8.2]）。

E-c **改完夹具继续沿用旧指纹。**旧汇编只对应旧二进制，旧结论不再适用（1.8.2）。

E-d **手工删掉别人的测量锁。**锁是为了串行化计时，绕过它等于制造新的干扰源（1.8.3）。

E-e **把 `sample` 栈的占比当 CPU 使用率。**采样混了预热与正式阶段，也不给 cache miss、IPC 或能耗（1.8.5）。

E-f **把列名改成 latency 就当做了请求级测量。**没有请求级观测，就没有请求分位数（1.8.6）。

E-g **五层失败统一写成 benchmark 失败。**定位不到该动哪一层（[@ex-1.8.1]）。

:::

**第 1 题 · 记忆**　证据链的九个文件各自能复核什么问题？至少说出四个。

::: sol 第 1 题答案

::: sol 第 2 题答案
不对。[@def-1.8.2] 的实验重跑会受新环境与时间条件影响，差异属于第④层（解释失配）或第⑤层（统计不确定）；只有功能失败（第②层）才意味着实现不满足契约。先分层，再谈对错。

## 1.11 本章小结与章末件 {#sec-cpp-rust.1.1.11}

::: note 本章小结

- 一个耗时数字必须带着实验契约：输入、计时边界、观察方式、外部条件，缺一条就不是同一个量（[@def-1.1.3]）。
- 先确认工作真的执行，再比较单位。DCE 与常量折叠是微基准里最常见的假结果（[@def-1.1.1]、[@def-1.3.1]）。
- 批均值回答吞吐，不回答单次请求延迟。p99 只有在存在逐请求分布时才是请求的分位数（[@def-1.2.2]、[@def-1.5.2]）。
- 配对、交替顺序、原始 CSV 是对抗时间漂移的最低配置；缺 `round` 与 `position`，配对与顺序效应都无法复核（[@def-1.4.1]、[@ex-1.4.1]）。
- 回归门禁要有「接受、拒绝、证据不足」三态，预算在采集之前写下，内存与正确性是并列约束（[@def-1.7.1]、[@def-1.7.2]）。

**改动实验时的责任**：改了 `N` 要重算参考值；改了 `K` 要重新解释夹具占比；改了优化参数要重新生成代码证据；改了输出语义要重新判断两种实现是否等价；改了统计规则要保留旧规则并说明差异。不允许把旧归档和新说明拼成一份看起来完整的证据。

:::

- 把「我想测什么」写成一份别人可以复核的实验契约；
- 用死代码消除（DCE）和 `black_box` 的例子，判断一段微基准是否真的在执行工作；
- 设计配对批次，读懂批均值、p50/p99（第 50/99 百分位）、标准差和 bootstrap（自助重采样）区间；
- 为一次性能回归建立「接受、拒绝、证据不足」三档判定。

完整的目标编号与检验方式见[自检表](ch01_checklist.md)。

**先修**：导论的「性能的六个常用指标」；Rust 的 `Vec`、迭代器、闭包；均值与标准差的定义。
**课时**：讲授 2 学时 + 实验 2 学时。
**实验包**：`bench/foundations-lab/`，只依赖标准库。
**入口**：`src/bin/dce.rs` 与 `src/bin/paired.rs`。
**数据**：`bench/foundations-lab/results/native-01/`。
**边界**：这一章讲桌面微基准的方法，不验证生产环境的服务等级协议（SLA），也不教时钟指令。
