# 4 从所有权事实到机器码：rustc 的分层证据

<div class="chapter-index">

**问题主线**：同一段 Rust，为什么在源码、MIR 与最终指令中呈现出不同的所有权形状？

- 用 HIR、THIR 与 MIR 区分语义消解、数据流检查和后端优化。
- 用初始化集合解释条件移动，而不是把 move 想成运行时清零。
- 用真正生成的 MIR 检查析构责任与 cleanup 边。
- 用两个已执行 benchmark 区分复制成本与析构状态成本。
- 把查询缓存、增量缓存、代码生成单元放回构建期，而非运行期。

**边界**：本章不实现编译器，不把 rustc 内部数据结构称为稳定接口。

## 4.1 编译阶段不是八台独立机器 {#sec-cpp-rust.1.4.1}

本节回答一个问题：**同一个所有权动作，为什么在源码、MIR 与最终指令中呈现出不同的形状，而结论该去哪一层找？**

::: preview 先抓住一件事

分层证据的价值不在背出阶段名字，而在**问题与表示的对应关系**。要肯定一个结论，你得在正确的那一层拿出这一层的产物；要否定「某个源码动作必然在机器上产生某段搬运」，只需要在最终产物里找不到它。本节先把「哪一层能说什么」定下来。
:::

### 4.1.1 性能排查经常从一个错误的问题开始

性能排查经常从一个错误的问题开始。
「这行 Rust 编译成几条指令」并不能覆盖所有权检查。
有些源码动作只形成静态约束。
有些动作产生可见的分配和复制。
还有些动作先形成控制流，再被后端删除。
必须先知道问题属于哪一种。

### 4.1.2 三层证据：语言、编译器表示、目标机器

::: def 定义 4.1.1 · 分层证据 layered evidence {#def-4.1.1}

**分层证据**指把一次判断拆到三层上分别核对。第一层是**语言允许的行为**，即规范层面的义务；第二层是**固定版本编译器采用的表示**，即 HIR、THIR、MIR 这些中间表示；第三层是**固定目标机器执行的程序**，即 LLVM IR、汇编与实际运行的代码。前一层约束后一层，但不唯一决定后一层。
:::

按[@def-4.1.1]，本章每个结论都要写明它属于哪一层。
「语言要求移动」和「机器上多了一次 memcpy」是两个判断，不能互相顶替。
第 1 章用[@def-1.1.3]把外部条件固定下来，本层证据链要沿用同一份约束。

例如，移动一个 Vec 会转移缓冲区的销毁责任。
语言不要求把缓冲区逐元素复制。
也不要求把原来的三个机器字写成零。
如果移动前后的两个名字从不同时使用，物理存储甚至可以复用。
这不等于移动语义被取消。
它意味着静态语义与物理数据搬运不是同一个计量对象。

::: ex 例 4.1.1 · move 到底有没有搬运数据 {#ex-4.1.1}

`Vec<u64>` 的句柄由指针、长度、容量三部分组成，本实验包报告的句柄尺寸是 24 字节（见 [4.6 节](#sec-cpp-rust.1.4.6)的尺寸表）。把一个 `Vec` 赋给另一个名字之后，分别按[@def-4.1.1]的三层回答：语言层要求什么、表示层记录什么、机器层可能留下什么。

::: sol 解答

① 语言层：原名字失去有效性，销毁责任转到新名字。这一层只规定「谁能用、谁负责释放」。
② 表示层：MIR 里出现一次 `move`，它改写的是初始化状态与责任归属，不规定任何一次内存写入（见 4.3 节）。
③ 机器层：可能只是把 24 字节的句柄拷进寄存器（CPU 内部最快取用的小存储格）或栈槽；当移动前后的名字从不同时活跃时，连这份句柄拷贝都可能消失。

不能因为第③层没看到搬运，就说第①层的移动语义被取消；也不能因为第②层写着 `move`，就断言第③层多了一次 128KiB 复制。

:::

:::

这个例子给出一个可复用的判断顺序：**先问责任，再问状态，最后问搬运**。顺序反了，就会拿一张汇编表去否定一条语言规则，或者反过来用一条语言规则去虚构一次复制。

### 4.1.4 各层保留的事实

下面这张表是本节的工具。第三列写「这一层仍然能告诉你什么」，第四列写「不要从这一层直接推出什么」。

| 表示 | 主要服务对象 | 仍然有价值的信息 | 不该直接推断的东西 |
|:--|:--|:--|:--|
| AST | 解析、宏展开、语法诊断 | 源语法结构与位置 | 最终循环形态 |
| HIR | 名称与类型相关分析 | 定义身份、脱糖表达式 | 每个表达式的最终机器位置 |
| THIR | 类型明确的函数体处理 | 调整、调用、销毁作用域 | 全 crate 的持久对象布局 |
| MIR | 借用检查、初始化、优化 | Place、move、分支、unwind | 每个 local 都占独立栈槽 |
| LLVM IR | 中低层优化 | 别名属性、控制流、内存操作 | 稳定 Rust ABI |
| 目标汇编 | 目标机实现 | 真正留下的调用和分支 | 源程序唯一合法实现 |

HIR 不是「带注释的机器码」。
MIR 也不是「先排好寄存器的汇编」。
把各层看成[@def-4.1.1]里不同问题的索引，会比背阶段名字更有用。
例如怀疑重复分配，最终产物中的 allocator 调用很直接。
怀疑条件移动后为何仍执行析构，MIR 的控制流更直接。
怀疑宏生成了多少定义，HIR 或展开后的源码更合适。

::: method 判定流程 · 一个怀疑该问哪一层

① **怀疑某段源码工作其实没执行**——先看 LLVM IR 与目标汇编里对应的调用和内存操作是否还在；这与第 1 章用[@def-1.1.1]排除假结果是同一个动作。<br>
② **怀疑所有权责任与析构时机**——看 MIR 的 `move`、`drop` 与 cleanup 边，不看汇编。<br>
③ **怀疑隐式调整**（自动借用、自动解引用、运算符重载选到了谁）——看类型检查之后的表示，MIR 只能看到调整的结果（4.2 节）。<br>
④ **怀疑宏生成了多少定义**——看展开结果与 HIR，最终符号表只作旁证。<br>
⑤ **怀疑一个耗时数字属于哪套条件**——回到[@def-1.1.3]的外部条件集合，也就是构建配置与环境记录，而不是回到汇编。

先选层，再取产物。层选错的核验做得再细，也只是在回答另一个问题。
:::

### 4.1.5 本轮工具链事实

::: def 定义 4.1.3 · 本机观察 local observation {#def-4.1.3}

**本机观察**是只在这台机器、这个版本、这套选项下成立的事实。它的适用范围由[@def-1.1.3]的外部条件集合划定：换工具链提交、换目标三元组、换构建选项，都算换了一个观察对象。本机观察可以如实报告，但不能升格成承诺。
:::

本轮执行的稳定版是 Rust 1.99.0。
提交为 `b940084d7eb6a299eb4bfeb8e34901bc051e7ac4`。
LLVM 版本为 23.1.1。
宿主与执行目标均为 `aarch64-apple-darwin`。
机器为 Apple M5 Pro，系统为 macOS 27.0.1。
系统报告的 cache line 为 128 字节。
这不是对所有 ARM64 或所有 Apple 芯片的普遍承诺。

`environment.txt`保存了原始命令输出。
本章没有设置`target-cpu=native`。
没有锁定工作线程到某个核心。
没有锁频，也没有隔离桌面后台负载。
以下纳秒数只能作为[@def-4.1.3]意义上的本机观察。
不能把它们当作服务等级协议。

::: think 思考 · 能不能写「ARM64 的缓存行是 128 字节」 {#think-4.1.1}

本节记录系统报告的缓存行（cache line，CPU 与内存之间整块搬运数据的单位）为 128 字节。有人据此在评审意见里写下「ARM64 的缓存行是 128 字节，所以按 128 对齐一定最优」。这句话越界在哪里？

::: sol 解答

越界在两处。第一，这个数字来自一台 Apple M5 Pro、macOS 27.0.1 上 `environment.txt` 的一条查询输出，属于[@def-4.1.3]的本机观察；「这台机器系统报告的值」和「该指令集所有实现的常数」不是同一个命题。第二，即使缓存行（CPU 和内存之间整块搬运数据的单位）确实相同，「按它对齐就更快」还需要分布与测量支持，而本章没有采集对齐档位之间的对比。正确写法是把机器、系统与查询产物一起留在句子旁边。

:::

:::

### 4.1.6 小结与常见错误

**小结。**① 一个性能问题要先归入三层之一，每层只支持它能支持的那句话（[@def-4.1.1]）；② move 改的是责任与状态，机器上是否有搬运要另外在产物里找（[@ex-4.1.1]）；③ 表示关系图是依赖图，不是时序日志（[@def-4.1.2]）；④ 判定从「该问哪一层」开始，而不是从「读哪一份文件」开始（4.1.4 的流程框）；⑤ 工具链与机器数字都属于本机观察，不能升格成承诺（[@def-4.1.3]）。下一节 [4.2 HIR、THIR 与不可省略的类型调整](#sec-cpp-rust.1.4.2) 补上「类型检查之后」那一层为什么省不掉。

::: errata 常见错误清单（4.1 节）

E-a **从最终汇编里看不到搬运，就去否认语言层的移动责任。**先确认问题属于哪一层（[@def-4.1.1]），再决定读哪份产物。

E-b **看到 MIR 写着 `move` 就写「多复制了一次缓冲」。**先查 LLVM IR 与汇编里是否有实际的内存操作（[@ex-4.1.1]）。

E-c **从表示关系图的一个箭头推出整个 crate 已完成前一阶段。**它是依赖图，不是时序日志（[@def-4.1.2]）。

E-d **把本机 cache line、机器型号写成架构常数。**它们是本机观察（[@def-4.1.3]）。

## 4.2 HIR、THIR 与不可省略的类型调整 {#sec-cpp-rust.1.4.2}

本节回答一个问题：**为什么「类型检查之后、MIR 之前」这一层省不掉，以及拿到它在本机的转储需要什么工具？**

::: preview 先抓住一件事

源码里没写出来的动作，才是所有权成本最容易藏身的地方。要肯定「这里发生了一次隐式调整」，得看带类型的中间表示；要否定「源码没写就一定不存在」，只要指出后续分析必须知道它是谁。这两层的转储只有 nightly 的 `-Zunpretty` 给得出，所以取到转储本身也是工具链问题，本节按补采时间分段记录。
:::

### 4.2.1 HIR 的关键变化是身份与依赖

::: def 定义 4.2.1 · HIR high-level intermediate representation {#def-4.2.1}

**HIR**（高层中间表示）是解析与脱糖之后、以「项」为单位的编译器表示。项（item）指有身份的定义：模块、函数、结构体、trait 等。它保留定义的结构，把源码里的 `for` 之类的写法换成更少的核心构造。
:::

源码中的一个模块可以嵌套很多项。
按[@def-4.2.1]，HIR 允许通过项的身份访问这些内容。
读取父模块不必无条件读取每个函数体。
这个组织方式有助于记录更细的查询依赖（查询见 4.7 节）。
它不只是为了把 for 改写成 loop。

::: def 定义 4.2.2 · 项的身份与一次使用 item identity vs use site {#def-4.2.2}

**身份**指「这是哪一个定义」，**一次使用**指「哪一处源码引用了它」。同一个函数定义可以有无数个调用位置，每个位置有自己的源码范围；位置不是多份定义。类型也一样：两处写着一样的文字，可能是两个语法位置上的同一个类型。
:::

应区分[@def-4.2.2]里的定义身份与一次使用的位置。
一个函数定义可以有很多调用位置。
每个位置拥有自己的源码范围。
这些位置不应被当作多份函数定义。
同样，两个相同文字的类型节点并不意味着同一个语法节点。
类型检查之后，它们可能指向同一个内部类型表示。

::: ex 例 4.2.1 · 两处相同写法的类型节点是同一个吗 {#ex-4.2.1}

同一个模块里写了两处 `Vec<u64>`：一处在函数签名上，一处在函数体里。请分别按语法层、[@def-4.2.1]和类型检查之后回答「这是不是一个东西」。

::: sol 解答

语法层：两个独立的类型写法，各自有自己的源码位置，文本替换、诊断定位都要按位置区分。HIR 层：它们是两处使用位置，不是两份 `Vec` 定义；`Vec` 的定义身份只有一份。类型检查之后：两处都可能指向同一个内部类型表示，因此按[@def-4.2.2]判断「同一个类型」要看身份而不是看文字。这个区分决定了「改一处签名会影响几处」这类问题的答案。

:::

:::

本地母本使用了一些较早的 crate 路径和节点名字。
例如母本保留了 NodeId 的历史说明。
本章复用的是「稳定身份有助于增量依赖」的机制。
不会要求读者在 1.99.0 上照抄旧内部路径。
内部字段发生变化不等于语言行为发生变化。

### 4.2.2 THIR 把隐式步骤显式化

函数调用前可能发生自动解引用。
方法接收者可能发生自动借用。
重载运算符会选择一个具体 trait 方法。
这些动作在源码中不一定各占一个符号。
但后续分析必须知道它们究竟是什么。

::: def 定义 4.2.3 · THIR typed high-level IR 与 body {#def-4.2.3}

**THIR**（带类型的高层中间表示）位于类型检查之后，节点已经带有类型。它的作用是把源码里隐式的步骤写明白：自动引用、自动解引用、方法选择、销毁作用域都成为显式节点。**body**（函数体）是它承载的范围：函数体与 `const` 初始化器这类「需要求值的代码」；结构体声明本身不是 body。
:::

按[@def-4.2.3]，THIR 层做的事可以列成四条。
方法调用和重载运算符会表现为普通调用。
自动引用和解引用会显式出现。
销毁作用域也被明确记录。
这让从高级表达式到控制流的降级拥有足够信息。

THIR 主要表示 body。
函数体和 const 初始化器都属于这种范围。
结构体声明本身不是一个可执行 body。
不能把 THIR 想成 HIR 全树的永远驻留副本。
按需构造与及时释放也属于编译器内存成本设计。
这份「按需」与 4.1 节[@def-4.1.2]的依赖图是同一件事的两面。

### 4.2.3 同一个表达式可以有不同访问责任

```rust
fn length(input: &Vec<u64>) -> usize {
    input.len()
}
```

这个教学片段不作为 benchmark。
它故意保留 Vec 引用以便说明方法接收者。
真实接口通常应接受切片，以降低容器耦合。
这里的重点是`input.len()`不是一个未解释的点号。
编译器需要确定实际调用、接收者调整与返回类型。

::: ex 例 4.2.2 · 三个返回同一个数字的签名 {#ex-4.2.2}

把上面的函数改成三种写法：① 保持 `&Vec<u64>`；② 改成消费 `Vec<u64>`；③ 改成在函数内 `input.to_vec()` 之后再求长度。三种都返回相同的长度。请按[@def-4.1.1]的三层，分别写出每种写法改变了什么。

::: sol 解答

① 语言层：调用者保留所有权，函数只是观察；表示层：接收者前有一次自动借用，这就是[@def-4.2.3]要显式写出来的调整；机器层：读一次长度字段。
② 语言层：所有权责任转移给函数，调用者之后不可再用这个名字；表示层：出现一次移动；机器层：没有理由逐元素复制缓冲（对照[@ex-4.1.1]）。
③ 语言层：调用者的数据仍然有效，函数另外得到一份副本；表示层：多一次分配与复制的责任；机器层：真的可能留下分配调用与复制操作——4.5 节就是用这一层来核验它的。

结论：三种接口返回同一个整数，但对调用者的可用状态与机器工作量完全不同。只比较最终返回整数是不充分的语义检查，正如[@ex-1.5.1]展示的那样，期望值相同不代表工作是同一件事。

### 4.2.5 该在什么时候查看哪一层

| 排查问题 | 优先观察 | 随后核验 |
|:--|:--|:--|
| 宏是否重复生成函数 | 展开结果、HIR | 最终符号是否仍保留 |
| 方法实际选择哪一个实现 | 类型检查、THIR | MIR 调用目标 |
| 哪个字段被移动 | MIR Place 与 move | 编译失败测试 |
| 销毁是否受分支控制 | MIR drop 与 cleanup | 实际 Drop 计数 |
| 是否真正复制缓冲 | LLVM 内存操作 | 目标码与计时 |
| 某个 local 是否真的落栈 | 目标码、调试位置 | 不以 MIR 名字计栈大小 |

分层观察不是要求每次读完整套产物。
应该从能反驳当前假设的最小证据开始。
如果一个复制调用清楚地留在目标码里，先测其范围。
没有必要先构建一份自定义 rustc。
只有观察确实卡在内部语义阶段时，才值得增加工具复杂度。

① 先按 4.1.4 的流程框选定层。<br>
② 用现有稳定版能拿到的产物（`--emit=mir`、`--emit=llvm-ir`、`--emit=asm`）做一次最小反驳；够反驳就停手。<br>

④ 仍拿不到，就写成[@def-4.1.3]意义下的证据缺口，改用文档解释，不伪造产物（见本节的思考框）。

## 4.3 MIR：初始化不是内存是否为零 {#sec-cpp-rust.1.4.3}

本节回答一个问题：**MIR 说某个位置「未初始化」，它说的是内存里的位，还是另一件事实？**

::: preview 先抓住一件事

「未初始化」是一个数据流事实，不是一个内存内容事实。肯定「这个位置此刻可以读」，要证明所有到达路径都已把它初始化；否定它，只需要找出一条没有赋值、或者把它移走的前驱路径。硬件层面的旧位模式（内存里各比特的具体排列）仍然存在，既不会让它重新合法，也不会让读取变成可检测的运行时错误。
:::

### 4.3.1 local、Place 与投影：比变量名更精确

::: def 定义 4.3.1 · MIR local {#def-4.3.1}

**local** 是 MIR 函数体里的存储槽编号，写成 `_0`、`_1` 这样的形式。`_0` 通常是返回位置；参数、源码局部量与临时值都可以成为 local。这些编号只是阅读固定产物的工具，不是稳定符号。
:::

按[@def-4.3.1]，MIR 的 local 用`_0`、`_1`等编号表示。
参数、源码局部量与临时值都可以成为 local。
这些编号不是稳定符号，也不是每个都必须独立存在于运行时。
一个 local 可能被标量替换、被消除或与其他 local 复用同一份存储。
因此「有几个 local」推不出「栈上有多少个槽」。

::: def 定义 4.3.2 · Place 与投影 place/projection {#def-4.3.2}

**Place** 是一个可访问位置，**投影**（projection）是附加在它后面的访问步骤：字段名、解引用、下标等。整个 local 是一个 Place，`a.0`、`*p`、`v[3]` 是另外三个 Place。初始化和借用都按 Place 记账，而不是按变量名记账。
:::

按[@def-4.3.2]，Place 可以是一个 local 整体。
也可以通过字段、解引用等投影访问子位置。
初始化分析不能只给每个变量一个永久状态。
结构体部分移动需要区分字段。

### 4.3.2 部分移动：为什么「变量还活着」不够细

例如一个没有自定义 Drop 的二元组持有两个 Vec。
移出第一个字段之后，第二个字段仍可使用。
整个二元组不再适合被当成完整初始化值读取。
剩余字段仍需要在退出时销毁。
这需要比「变量还活着」更细的状态。

::: ex 例 4.3.1 · 移出一个字段之后还剩什么 {#ex-4.3.1}

一个 `(Vec<u64>, Vec<u64>)` 没有自定义 `Drop`。执行 `let left = pair.0;` 之后，请说明三个问题：整体 `pair` 还能不能被完整读取？`pair.1` 还能不能用？退出时谁负责销毁？

::: sol 解答

整体 `pair` 不再是一个完整初始化的值，因此按整体读取会被拒绝（这是 4.3.4 的合流规则要处理的情形）。`pair.1` 从未被移动，仍然可用，可以单独借用或单独移出。退出时的责任被拆开：`pair.1` 由编译器生成的收尾代码销毁，原 `pair.0` 位置的所有权已经转给 `left`，由 `left` 负责（对照[@ex-4.1.1]的责任转移）。这正是[@def-4.3.2]要按 Place 而不是按变量名记账的原因。

:::

:::

### 4.3.3 move path：给可跟踪的移动位置建索引

::: def 定义 4.3.3 · move path {#def-4.3.3}

**move path**（移动路径）是为「可以被跟踪移动的位置」建立的索引。它有父子关系：`a.b.c` 由它的父路径 `a.b` 派生。移出父路径会影响所有后代的初始化状态；只移出一个子字段，不应取消无关兄弟字段的责任。
:::

按[@def-4.3.3]，move path 可以形成父子关系。
`a.b.c`与其父路径`a.b`存在包含关系。
移出父路径会影响后代初始化状态。
只移出一个子字段不应取消无关兄弟字段的责任。

不是每个 Place 都允许被独立移动。
不能从普通共享引用后面移出拥有所有权的 String。
不能任意把一个数组下标位置当作安全的空洞。
这些限制影响分析必须跟踪的路径集合。
本章没有把母本的每个内部索引名字当成版本不变 API。

### 4.3.4 前向数据流中的两个集合

借用检查器需要知道一个点上哪些位置肯定可以读取。
控制流合流时，不能只看最近一条源码赋值。
如果一个前驱没有初始化该位置，后续无条件读取就可能失败。
如果一个前驱移动了该位置，原位置也不再可读。
这里的「未初始化」是语义状态。

::: def 定义 4.3.4 · 必定初始化与可能未初始化 must-init / maybe-uninit {#def-4.3.4}

本章用两个集合来读这份前向分析（沿控制流边从函数入口往后传播）：**必定初始化**指该位置在到达这个点的所有路径上都已完成初始化；**可能未初始化**指至少一条到达路径没有初始化它，或者某条路径把它移走了。读取要求前者，析构责任要求区分后者与「此处必然已初始化」。这是本章阅读产物的记法，不是 rustc 内部类型的名字，也不构成跨版本 API。
:::

按[@def-4.3.4]，两个集合的合流规则不同。
「必定初始化」在合流点要求所有前驱都成立，因此一条缺失就够推翻它。
「可能未初始化」只要有一条路径成立就会成立，因此它决定析构责任是否需要保留。
这就是 4.4 节里条件析构的来源。

它不等于该地址上的所有位都是未定义的硬件信号。
也不等于编译器必须向该地址写某个哨兵。
旧位模式仍然存在，不会使读取重新合法。
把地址重新解释成引用也不能恢复被移动的所有权。
不要通过 unsafe 把静态错误「修成」双重释放。

::: ex 例 4.3.2 · 合流点上到底该记哪一个 {#ex-4.3.2}

```rust
fn main() { let value: u64; if std::hint::black_box(true) { value = 7; } println!("{value}"); }
```

这是本轮实际编译的第二个拒绝输入（见 4.3.5）。在 `println!` 之前的合流点上，按[@def-4.3.4]判断 `value` 属于哪个集合，并说明编译器为什么不能凭「这次条件为真」放行。

::: sol 解答

有一条路径（条件为假）没有给 `value` 赋值，所以它不属于「必定初始化」集合；它属于「可能未初始化」。无条件读取要求前者，因此被拒绝，诊断代码是 E0381。`black_box` 让条件在优化器眼里不透明，更重要的是：被检查的是该程序**允许的控制流**，不是某一次执行恰好走了哪条边——这与[@def-1.1.1]里「优化器能看见删除」的判定用的是同一套静态推理，只是方向相反。

:::

:::

### 4.3.5 两个真正被拒绝的失败样例

`probes/rejected/use_after_move.rs`是本轮实际编译的输入。
它没有运行任何未定义行为。
编译器在产生可执行程序之前拒绝它。

```rust
fn main() { let data = vec![1u8]; drop(data); println!("{}", data.len()); }
```

诊断代码是 E0382。
不是运行时检测到 Vec 被写成零。
也不是分配器（按需划分和回收内存的那个库）发现重复释放后补救。
错误来自移动之后的再次使用。
`extra.py`检查了非零退出状态与诊断代码。

第二个输入测试条件初始化，代码已在[@ex-4.3.2]给出。
编译器不能凭 black_box 返回值的实际常量路径接受所有路径。
被检查的是该程序允许的控制流。

诊断代码是 E0381。
这不是内存不足，也不是零初始化失败。
有一个可能到达打印位置的路径没有赋值。
正确修复应赋予所有路径明确含义。
不应使用未初始化整数来压低计时。

::: ex 例 4.3.3 · 诊断码告诉你拒绝发生在哪一层 {#ex-4.3.3}

有人主张：「E0382 说明运行时能发现 Vec 已经被用坏了，所以可以放心用 raw pointer 绕过它。」请分别用 E0382 与 E0381 这两个诊断码，指出这个主张错在哪一层。

::: sol 解答

两个码都由编译期产生：E0382 是移动之后再次使用（`extra.py` 只检查非零退出状态与诊断代码，从未运行这段程序），E0381 是存在未赋值路径的读取。它们属于[@def-4.1.1]的第二层，不是第三层的运行时事件。既然运行时没有检查，绕过静态拒绝之后不会有任何机制「发现」问题——旧位模式仍在（4.3.4），双重释放会真的发生。因此「运行时能补救」这个前提本身不成立。

:::

### 4.3.6 storage、初始化、借用是三个维度

::: def 定义 4.3.5 · StorageLive 与 StorageDead {#def-4.3.5}

**StorageLive** 是一个 MIR 语句，宣告某个 local 的存储生命周期开始；**StorageDead** 宣告它结束。两者管的是「这块存储在不在这个范围内存在」，不管「里面是不是一个合法完整的值」，也不等于一次用户可见的 `Drop` 调用。
:::

按[@def-4.3.5]，StorageLive 不保证一个完整值已经写入。
StorageDead 也不等价于一次用户 Drop 调用。
二者与[@def-4.3.4]的初始化状态、4.4 节的析构责任相关，却不能互相替代。

借用的有效范围又是另一个维度。
最后一次使用引用之后，借用可以不再阻挡后续操作。
但拥有者的析构时点不因此自动提前到最后一次读取。
一个持锁守卫即使最后一次解引用已经过去，仍可能持锁到作用域末尾。
不要把 NLL 误解成自动缩短所有资源生命周期。

::: think 思考 · 把地址重新解释成引用，能不能把值读回来 {#think-4.3.1}

位置 `data` 已被移出。有人提议：`let p = &raw const data;` 拿到地址后构造一个引用再读。既然[@def-4.3.4]的两个集合只是编译期的记账，而旧位模式仍然存在，这条路「只是绕过检查而已」，代价是什么？

::: sol 解答

代价不是「多一次检查」，而是把语言层已经取消的责任重新接上。所有权仍在新的所有者手里，它退出时照样销毁这块存储；再从旧位置读甚至再构造一次销毁，就同时存在两个负责释放同一块缓冲的位置。编译期的记账是唯一的防线，运行时不会补救（见[@ex-4.3.3]）。静态错误被 unsafe 「修成」的通常是双重释放或悬垂读，不是可恢复的状态。

:::

:::

### 4.3.7 阅读时的最小记录表

| 控制流点 | 存储存在 | 值初始化 | 仍有借用 | 仍有销毁责任 |
|:--|:--|:--|:--|:--|
| 声明后赋值前 | 可能是 | 否 | 否 | 否 |
| 成功构造后 | 是 | 是 | 依程序而定 | 依类型而定 |
| 所有权移出后 | 可能是 | 原位置否 | 必须满足移动限制 | 转交给新所有者 |
| 仅剩一个字段 | 是 | 部分 | 依字段而定 | 仅剩余字段 |
| 作用域退出后 | 否 | 不再可访问 | 不可存活 | 已执行或已转交 |

这张表是一种分析工具。
它不意味着 rustc 为每个 local 保存四个运行时布尔量。
大多数事实在编译期就已确定。
只有静态无法消解而又需要运行时区分的状态才可能进入代码。
下一节具体观察这种状态。

### 4.3.8 小结与常见错误

**小结。**① 记账单位是 Place 而不是变量名（[@def-4.3.2]）；② 部分移动要求字段级状态（[@ex-4.3.1]）；③ 读取要求「必定初始化」，析构责任要看「可能未初始化」（[@def-4.3.4]、[@ex-4.3.2]）；④ 未初始化是语义状态，不是内存位模式，也没有运行时补救（[@ex-4.3.3]）；⑤ 存储范围、初始化、借用是三个维度，不能互相顶替（[@def-4.3.5]）。下一节 [4.4 borrowck 与 Drop elaboration 的责任分界](#sec-cpp-rust.1.4.4) 处理「静态定不下来」时机器上留下什么。

::: errata 常见错误清单（4.3 节）

E-a **按变量名判断能不能读。**要看 Place 与投影（[@def-4.3.2]、[@ex-4.3.1]）。

E-b **把「未初始化」读成「这块内存的位是垃圾」。**它是[@def-4.3.4]意义上的语义状态，旧位仍在也不合法（[@ex-4.3.3]）。

E-c **按 MIR local 个数估算栈槽数量。**local 可以被消除、替换或复用（[@def-4.3.1]）。

E-d **凭 black_box 的实际取值放行所有路径。**被检查的是允许的控制流（[@ex-4.3.2]）。

E-e **拿 StorageDead 统计资源释放次数。**存储范围与销毁义务不同维度（[@def-4.3.5]）。

E-f **用 raw pointer 把移走的位置读回来「补一下」。**两个所有者同时对一块存储负责（见本节的思考框）。

E-g **以为运行时会拒绝移动后使用。**拒绝发生在产生可执行程序之前（[@ex-4.3.3]）。

E-h **认为 NLL 会自动提前释放锁。**借用结束不等于守卫立刻销毁，资源边界要用显式块或 `drop` 写出来（4.3.6）。

:::

## 4.4 borrowck 与 Drop elaboration 的责任分界 {#sec-cpp-rust.1.4.4}

本节回答一个问题：**析构责任什么时候能被静态定死，什么时候必须在运行期留一个判断？**

::: preview 先抓住一件事

两件事都在 MIR 上完成，但分工不同：borrowck 判断「此刻谁能访问这个位置」，Drop elaboration 判断「这个位置退出时到底要不要销毁」。判断越确定，机器上留下的东西越少——四类情形里只有真正定不下来的那两类才可能需要运行期状态。要否定「这里一定有动态 flag」，只要给出一个状态在编译期已知的例子。
:::

### 4.4.1 借用检查不是插入引用计数

::: def 定义 4.4.1 · borrowck {#def-4.4.1}

**borrowck**（借用检查）是 MIR 上的一组分析：它把访问位置、时段与允许的再借用连成区域约束，再检查具体读写、移动与借用是否冲突。它是编译期的证明过程，不在程序运行时执行，也不会为普通引用插入引用计数更新。
:::

按[@def-4.4.1]，borrowck 在 MIR 上分析访问与区域约束。
它跟踪移动、初始化和活跃借用（初始化状态的含义见[@def-4.3.4]）。
它不会为每个普通引用插入一个引用计数更新。
普通引用也没有运行时「借用表」随调用传播。
RefCell 的动态检查是另一套库机制。

分析需要考虑控制流中引用的使用点。
区域约束把必要的有效范围连起来。
随后检查具体读写、移动与借用是否冲突。
只记住「一个可变或者多个共享」还不够做复杂代码审查。
必须把被访问位置、时段与允许的再借用一起考虑。

### 4.4.2 别名冲突在这里被拒绝

```rust
fn main() { let mut data = 7u64; let reader = &data; let writer = &mut data; *writer = 9; println!("{reader}"); }
```

本轮编译器报告 E0502。
共享借用仍要在打印处使用。
在此期间取得冲突的可变借用是不允许的。
没有运行「优化前」和「优化后」的 UB 程序来比较结果。
后端可以利用这些静态排除的输入，而不必检查每次调用。

::: ex 例 4.4.1 · 这段拒绝为什么对后端有用 {#ex-4.4.1}

上面这个输入（`alias_conflict.rs`，本轮实际编译）报告 E0502。请说明：① 拒绝发生在哪一层；② 「后端可以利用这些静态排除的输入」在[@def-4.1.1]的第三层换来什么；③ 为什么没有跑「优化前后」的两份 UB 程序。

::: sol 解答

① 编译期，产生可执行程序之前，与[@ex-4.3.3]同层次。② 换来的是省略运行时检查的许可：既然不存在「共享引用与可变借用同时活跃」的合法输入，后端就不必为保护它插入计数或检查，这与第 1 章[@def-1.1.1]「没有可观察效果就不必生成代码」是同一种推理。③ 因为程序根本不合法：一旦执行未定义行为，任何「优化前后」对比都不再说明语言行为，只说明这一次运行的运气，所以本实验包只检查非零退出状态与诊断代码。

:::

:::

UnsafeCell 会改变共享访问下的可变性条件。
Cell 的合法写入不能被简单套用为普通共享引用不可变。
本章 DropProbe 正是通过 Cell 做单线程可观测计数。
这让析构行为保留下来。
也意味着不能把该内核当成纯无别名整数函数——这一点在 4.8.2 讨论校验强度时还会回来。

### 4.4.3 Drop elaboration 把责任具体化为合法控制流

初始 MIR 中的 drop 位置表示可能需要执行销毁的地方。
这时目标可能已被移动。
直接无条件调用其析构会出错。
Drop elaboration 将销毁责任具体化为合法控制流。
它不是[@def-4.4.1]的替代品。

::: def 定义 4.4.2 · 析构责任的四类情形 Static / Dead / Conditional / Open {#def-4.4.2}

在某个点上问「这个位置此刻是不是还要销毁」，答案落进四类之一：**Static** 表示目标在此处总是初始化；**Dead** 表示目标在此处总是未初始化；**Conditional** 表示整体有或整体无，取决于路径；**Open** 表示可能只剩部分字段（见[@ex-4.3.1]）。
:::

按[@def-4.4.2]，需要区分四类情形。
Static 与 Dead 在编译期就能定论。
Conditional 取决于到达路径。
Open 只承诺「剩余部分仍需负责」。

| 类别 | 必须保留的行为 | 典型实现后果 |
|:--|:--|:--|
| Static | 执行目标的销毁 | 可直接保留 drop |
| Dead | 不执行目标销毁 | 可移除 drop |
| Conditional | 按状态决定是否销毁 | 可能需要 flag 或等价分支 |
| Open | 只销毁已初始化部分 | 分解为字段级责任 |

「每个变量一个 drop flag」只是一个容易理解的上界模型。
它不是最终生成代码的要求。
已知状态无需动态 flag。
多个始终共同变化的路径也可能共享状态。
后续优化还可能消除或改写这些状态。

::: ex 例 4.4.2 · 哪些情形不需要运行期 flag {#ex-4.4.2}

`conditional_drop` 的第二个守卫 `second` 在函数末尾总是销毁；`first` 在 `flag` 为 true 的分支里被显式移走再 drop。请按[@def-4.4.2]分别给这两个位置在每个出口点上的类别，并说明哪个可能需要动态状态。

::: sol 解答

`second`：所有路径都从构造点走到退出点且没有移动它，属于 Static，可直接保留一条 drop，不需要 flag。
`first`：在显式 `drop(first)` 之后的路径上已经移走（Dead），在没走那条分支的路径上仍在（Static）——合流点上就是 Conditional。本轮产物用一次状态记录来表达这件事（4.4.5 会指出它在 MIR 里长什么样），但「用 flag」只是[@def-4.4.2]的实现后果之一，不是要求：状态已知或被合并时，最终代码里可以没有独立布尔槽。

:::

### 4.4.4 与用户 Drop 方法的关系

有用户 Drop 实现的类型，不能随意移出它的字段。
否则 Drop 方法看到的 self 可能缺失字段。
没有用户 Drop 的聚合类型则可以有部分移动。
其剩余字段仍由编译器生成的 glue 负责。
这两种情况不能混为一谈。

Drop glue（编译器为一个类型生成的收尾销毁代码）可能先调用用户 Drop 方法。
随后再递归销毁字段。
用户不能直接调用`value.drop()`来消费对象。
`std::mem::drop(value)`通过接收所有权触发正常销毁。
它与`drop(&value)`不具有相同的资源效果。

::: think 思考 · `drop(&value)` 为什么不算「提前释放」 {#think-4.4.1}

想让一个守卫在作用域结束前放开资源，有人写下 `drop(&value);`，理由是「把引用交给 drop，等于告诉编译器它不再被使用了」。这条推理错在哪一步？

::: sol 解答

错在把「最后一次使用」当成「移交所有权」。`std::mem::drop` 的签名接收参数本身，调用它就是把值移走，销毁责任随之在这一点完成；`&value` 只是借出一个观察位置，原所有者仍在，值要到自己的作用域退出才销毁。[@def-4.3.4]与[@def-4.3.5]给出的记账不会因一次借用而改变，4.3.6 里持锁守卫的例子说的正是同一件事：借用结束不等于资源已释放。

:::

### 4.4.5 本轮实际的条件析构 MIR

::: def 定义 4.4.3 · cleanup 块与展开边 cleanup / unwind {#def-4.4.3}

MIR 里标着 `(cleanup)` 的基本块是**展开路径**上的收尾块：前面的操作 panic 时，控制流沿 unwind 边进入它，由它销毁此刻仍然负责的位置，再把异常继续往外传（`resume`）。与之相对的是 `return`、`goto` 这样的**正常边**。写上 `unwind terminate(cleanup)` 的边表示「这里再 panic 就只能终止」。
:::

以下是`conditional_drop`的完整函数 MIR。
它来自 stable release 产物，不是手写伪 MIR。
归档文件为 `bench/compiler-lab/results/stable-02/codegen/compiler_lab-55987aab45b3e67f.mir`。
编号只对本轮文件有效。

```text
fn conditional_drop(_1: bool, _2: &Cell<u64>) -> () {
    debug flag => _1;
    debug count => _2;
    let mut _0: ();
    let _3: DropProbe<'_>;
    let mut _5: DropProbe<'_>;
    let _6: &DropProbe<'_>;
    let mut _7: &DropProbe<'_>;
    let mut _8: bool;
    scope 1 {
        debug first => _3;
        let _4: DropProbe<'_>;
        scope 2 {
            debug second => _4;
            scope 3 (inlined std::mem::drop::<DropProbe<'_>>) {
            }
            scope 4 (inlined std::hint::black_box::<&DropProbe<'_>>) {
            }
        }
    }

    bb0: {
        StorageLive(_3);
        _8 = const true;
        _3 = DropProbe::<'_>(copy _2);
        StorageLive(_4);
        _4 = DropProbe::<'_>(copy _2);
        switchInt(copy _1) -> [0: bb8, otherwise: bb1];
    }

    bb1: {
        StorageLive(_5);
        _8 = const false;
        _5 = move _3;
        drop(_5) -> [return: bb7, unwind: bb3];
    }

    bb2: {
        StorageDead(_3);
        return;
    }

    bb3 (cleanup): {
        drop(_4) -> [return: bb6, unwind terminate(cleanup)];
    }

    bb4 (cleanup): {
        resume;
    }

    bb5 (cleanup): {
        drop(_3) -> [return: bb4, unwind terminate(cleanup)];
    }

    bb6 (cleanup): {
        switchInt(copy _8) -> [0: bb4, otherwise: bb5];
    }

    bb7: {
        StorageDead(_5);
        StorageLive(_6);
        StorageLive(_7);
        _7 = &_4;
        _6 = std::intrinsics::black_box::<&DropProbe<'_>>(move _7) -> [return: bb9, unwind unreachable];
    }

    bb8: {
        StorageLive(_6);
        StorageLive(_7);
        _7 = &_4;
        _6 = std::intrinsics::black_box::<&DropProbe<'_>>(move _7) -> [return: bb11, unwind unreachable];
    }

    bb9: {
        StorageDead(_7);
        StorageDead(_6);
        drop(_4) -> [return: bb10, unwind: bb6];
    }

    bb10: {
        StorageDead(_4);
        goto -> bb2;
    }

    bb11: {
        StorageDead(_7);
        StorageDead(_6);
        drop(_4) -> [return: bb12, unwind: bb6];
    }

    bb12: {
        StorageDead(_4);
        drop(_3) -> [return: bb2, unwind continue];
    }
}
```

这段产物里有几个位置值得逐条对上[@def-4.4.2]的四类情形。
`_8`记录第一份守卫的责任是否仍存在。
进入显式 drop 路径前将它置为 false。
cleanup 路径检查这个状态，避免再次销毁已经移走的值。
正常路径也被拆成不同分支。
不能只搜索一个`switchInt`就断言机器上永久保留一个布尔槽。

::: ex 例 4.4.3 · 从这段 MIR 里读出责任 {#ex-4.4.3}

只根据本节产物回答四件事：① `debug first` 对应哪个 local？② 责任标记在哪个基本块被置为 false？③ 展开路径为什么不重复销毁已经移走的值？④ 正常分支与 cleanup 分支的区别在哪里？

::: sol 解答

① `_3`（`debug first => _3` 在 scope 1 里；`_4` 是 `second`）。② `bb1`：`switchInt(copy _1)` 走到非零分支后，先 `_8 = const false`，再 `_5 = move _3` 与 `drop(_5)`——移动与显式销毁都发生在这一段。③ `bb6 (cleanup)` 用 `switchInt(copy _8)` 判断：为 0 就直接 `bb4` 的 `resume`，不为 0 才进 `bb5` 的 `drop(_3)`，因此已经移走的情况不会被第二次销毁。④ 正常边是 `bb9`/`bb11` 里的 `drop(_4)` 加 `unwind: bb6`，最后经 `bb10` 或 `bb12` 走到 `bb2` 的 `return`；cleanup 块只处理展开，`bb3` 销毁 `_4` 后 `unwind terminate(cleanup)`。按[@def-4.4.3]，`return`/`goto` 属于正常边，`cleanup`/`resume` 属于展开边。
这些编号只对本轮文件有效，换版本可能重排；要带走的是读法，不是编号。

### 4.4.6 unwind 与 abort

本轮 profile 使用`panic=unwind`。
因此 MIR 中可以看到[@def-4.4.3]描述的 cleanup 和 resume。
这对资源安全很重要。
普通路径与展开路径都需要保持初始化责任一致。
不能只审查没有 panic 的路径。

`panic=abort`会改变部分清理控制流。
它不意味着所有正常返回时的 Drop 都被取消。
也不意味着进程终止时会可靠释放所有外部业务资源。
本轮没有把 abort 与 unwind 计时混在同一张表。
修改 panic 策略时应重新生成产物，而非只改注释。

### 4.4.7 小结与常见错误

**小结。**① borrowck 是编译期证明，不产生运行时记账（[@def-4.4.1]、[@ex-4.4.1]）；② Drop elaboration 把「要不要销毁」落成四类可判定的情形（[@def-4.4.2]）；③ 只有状态定不下来的位置才可能需要运行期判断，flag 是上界模型（[@ex-4.4.2]）；④ 正常边与展开边要一起审查，本轮产物里两者都存在（[@def-4.4.3]、[@ex-4.4.3]）；⑤ `drop(value)` 移交所有权，`drop(&value)` 不移交（见本节的思考框）。下一节 [4.5 benchmark 一：为通过检查而 clone 的实际代价](#sec-cpp-rust.1.4.5) 用计时与产物核对「多出来的工作」。

::: errata 常见错误清单（4.4 节）

E-a **以为借用检查会插入引用计数。**普通引用没有运行时计数，也没有借用表（[@def-4.4.1]）。

E-b **只记「一个可变或多个共享」就下结论。**要连着位置、时段与再借用一起看（4.4.1）。

E-c **把 Cell 的计数内核当纯无别名整数函数。**它靠 Cell 观察副作用，别名条件不同（4.4.2）。

E-d **按「每个变量一个 drop flag」统计运行时开销。**那是[@def-4.4.2]的上界模型，已知状态不需要它（[@ex-4.4.2]）。

E-e **在有用户 `Drop` 的类型上随意移出字段。**析构方法看到的 self 可能缺字段（4.4.4）。

E-f **用 `drop(&value)` 提前释放资源。**移交的是借用不是所有权（见本节的思考框）。

E-g **只审查没有 panic 的路径。**展开边同样要保持责任一致（[@def-4.4.3]）。

E-h **改 `panic=abort` 只改注释不改产物。**清理控制流随构建配置变化（4.4.6）。

## 4.5 benchmark 一：为通过检查而 clone 的实际代价 {#sec-cpp-rust.1.4.5}

本节回答一个问题：**为了绕开借用检查而加的那次 clone，在这台机器上到底买回了多少额外工作？**

::: preview 先抓住一件事

这个实验的价值不在「快了多少倍」，而在**回退是可以完全正确的**：两个分支返回一模一样的值，断言全绿，测试全过，代价却留在分配与复制里。判断它成立要两条证据同时给出——批计时表说明成本，产物核验说明这份成本真的留在代码里。缺任何一条，「clone 更贵」都只是一句猜测。
:::

### 4.5.1 这个实验测什么，以及故意不测什么

入口是`src/bin/move_cost.rs`。
名称强调所有权修复引入的成本。
但本实验没有直接测一次 Vec move 的独立纳秒数。
它比较「借用已有数据求和」与「先复制出拥有者再求和」。
不要把表格写成 Rust move 指令的成本。

输入含 16384 个 u64。
两种 case 对同一输入做模 2 的 64 次方求和。
克隆分支包含新缓冲分配、复制、求和和释放。
借用分支只需要读已有缓冲并求和。
两者返回完全一致的值。

::: def 定义 4.5.1 · 安全但更慢的回归 safe-but-slower regression {#def-4.5.1}

**安全但更慢的回归**指：改动让程序满足借用检查、保持内存安全、输出也完全正确，只是请求了更多工作。它与「错误但很快」正好相反，是所有性能回退里最容易被放过的一种，因为没有任何一条诊断会报它。
:::

这是一种[@def-4.5.1]的真实形态。
为了避开借用设计，调用方可能增加不必要的 to_vec。
程序仍然内存安全。
业务结果也可能毫无变化。
但额外工作不会因为代码「很 Rust」就自动消失。

### 4.5.2 完整入口与两个工作核

```rust
use compiler_lab::{Case, borrowed_sum, cloned_sum, input_data, measure};
use std::hint::black_box;
fn main() {
    let input = input_data(16384);
    let expected = input.iter().copied().fold(0, u64::wrapping_add);
    let mut cases = [
        Case {
            name: "borrow",
            run: Box::new(|| borrowed_sum(black_box(&input))),
            expected,
        },
        Case {
            name: "clone",
            run: Box::new(|| cloned_sum(black_box(&input))),
            expected,
        },
    ];
    measure(&mut cases, input.len());
}
```

完整业务函数如下。
black_box 放在拥有者上，避免把本实验变成可删除复制的纯函数。
这也明确限制了实验外推。
真实代码若能证明副本无用，优化器可能删除更多工作（对照[@def-1.1.1]）。

```rust
#[inline(never)]
pub fn borrowed_sum(input: &[u64]) -> u64 {
    input.iter().copied().fold(0, u64::wrapping_add)
}

#[inline(never)]
pub fn cloned_sum(input: &[u64]) -> u64 {
    let owned = black_box(input.to_vec());
    borrowed_sum(&owned)
}
```

`expected` 由入口独立算出，两个 case 共用同一份参考值。
这正是[@ex-1.1.1]要求的「期望值不与被测实现同源」。
`black_box` 的位置放在 `input.to_vec()` 的结果上，让副本的用途对优化器不透明。

### 4.5.3 计时边界

| 操作 | borrow | clone | 是否在批计时内 |
|:--|:--|:--|:--|
| 创建原始输入 | 一次 | 共享同一份 | 否 |
| 从切片读取 | 是 | 是 | 是 |
| 新缓冲分配 | 否 | 是 | 是 |
| 复制 128KiB 数据 | 否 | 是 | 是 |
| 求和 | 是 | 是 | 是 |
| 副本释放 | 否 | 是 | 是 |
| 每轮聚合校验 | 同一公式 | 同一公式 | 时间戳之后 |

原始缓冲区由入口持有到实验结束。
不存在悬垂切片。
两个 case 没有并行执行。
每次调用的返回值都会进入批 checksum。
分配、复制与释放没有移到计时外偷换任务。

::: ex 例 4.5.1 · 分母是什么，成本就是什么 {#ex-4.5.1}

`measure(&mut cases, input.len())` 传入的 units 是 16384。请说明：① 表格里的 ns/输入元素这个单位，分母是谁给的；② clone 分支多出来的三件事（分配、复制、释放）有没有被这个分母摊薄；③ 为什么「创建原始输入」不计入。

::: sol 解答

① 分母是批内重复次数乘以 units，即[@def-1.2.2]意义上的批均值再除以元素数（4.8.1 给出 `measure` 的完整实现）。② 有：三件事都发生在每次逻辑调用内，于是被 16384 摊薄，所以 clone 那行才只有零点二几纳秒而不是几微秒——这是聚合吞吐倒数，不是单次分配的成本。③ 原始输入在正式批次之前创建、被两个 case 共享，画在计时边界之外，属于夹具条件而不是被测工作；按[@def-1.1.3]，它必须在契约里写明，否则两边读者会以为输入也在计时。

:::

### 4.5.4 结果

单位为 ns/输入元素。
每一个正式原始点都是整批墙钟时间的归一化值。
不是单个整数加法延迟（口径见[@def-1.2.2]与 4.8.3）。

| case | mean | N-1 sd | 批 p50 | 批 p99 |
|:--|--:|--:|--:|--:|
| borrow | 0.059091 | 0.001233 | 0.058640 | 0.063338 |
| clone | 0.202739 | 0.006949 | 0.201627 | 0.225702 |

本轮 clone 分支的聚合成本更高。
这个方向符合保留分配与 memcpy 的代码证据。
但差值不是「每个 borrowck 检查节省的时间」。
[@def-4.4.1]不在进程运行时循环中执行。
真正不同的是程序请求的工作。

::: ex 例 4.5.2 · 0.143648 这个差值能说什么 {#ex-4.5.2}

按表相减：0.202739 − 0.059091 = 0.143648 ns/输入元素；两者比值约 3.43。有人把它写成「借用检查为每次调用省下 0.143648 ns/元素」。请指出两处错误，并给出一个能站住的表述。

::: sol 解答

第一处错误是把成本归给 borrowck：它是编译期分析（[@def-4.4.1]），进程运行时不在循环里。第二处错误是把批均值差当成可外推的常数：两个 sd（0.001233 与 0.006949）说明批次间有波动，本轮没有计算配对区间，所以只能说方向与量级（[@def-1.4.2]的配对做法本轮没有用于这张表）。站得住的表述是：在本机、本输入长度、本构建配置下，克隆分支的批均值比借用分支高约 0.14 ns/元素，方向与产物中保留的分配、复制与释放一致（4.5.5）。

### 4.5.5 产物核验

::: def 定义 4.5.2 · 产物核验 artifact verification {#def-4.5.2}

**产物核验**指在编译器实际生成的文件里，按目标业务函数逐项确认预期的操作是否留存：分配调用、复制调用、释放调用、归约指令。核验对象是归档中的完整符号与其周边控制流，不是网页上的相似片段，也不是别处碰巧看到的指令。
:::

按[@def-4.5.2]，`cloned_sum`的 LLVM IR 保留 allocator 调用。
随后有`llvm.memcpy`。
计算之后保留 deallocator 调用。
本机目标码中可见`_memcpy`的真实调用。
这反驳了「整个克隆已被折叠」的假设。

`borrowed_sum`出现向量加法归约。
它并没有按源码 iterator 层级逐层函数调用。
这说明所有权借用与迭代器表达式并不必然引入逐元素动态开销。
但向量化（一条 CPU 指令同时处理多个数）也不是该接口跨所有版本的承诺。
需要保存完整产物，而不只摘一条 add。

::: think 思考 · 在产物里搜到向量指令，算核验完成吗 {#think-4.5.1}

一位读者按上面的说明复核，打开归档的 `.s` 文件搜索向量加法，看到好几条，于是写下「已核验借用求和的向量化」。他漏了什么？

::: sol 解答

漏了「确认观察的是目标业务函数」。一份 `.s` 里同时有标准库其它例程的指令，搜到一条 add 不等于它属于 `borrowed_sum`；要看该符号的完整范围与周边控制流，再决定它支持哪一句判断。这正是[@def-4.5.2]的边界。第二处漏洞是结论范围：本轮看到的向量化是本机这一版的产物（[@def-4.1.3]），不能写成该接口跨版本的承诺——就像[@ex-4.1.1]里不能从机器层的缺席反推语言层。

:::

:::

### 4.5.6 修复方式与语义核验

如果调用者只需要观察数据，应考虑传入切片。
如果调用者需要独占修改，应重新安排可变借用边界。
如果确实需要两个独立拥有者，复制也许就是正确业务。
不能为了消除 clone，把两个需要独立变化的缓冲强行共享。
性能优化首先要保持所需语义。

对短缓冲，分配固定开销可能占更高比例。
对很大的缓冲，内存层级和分配器行为又会变化。
**本轮没有采集这些分布**：没有测其它输入长度，也没有测跨线程共享或 NUMA。
所以本表只回答本章指定的 128KiB 热输入问题。

### 4.5.7 小结与常见错误

**小结。**① 本实验测的是「借用已有数据」与「先复制出拥有者」，不是一次 move 的纳秒数（[@def-4.5.1]）；② 分母与计时边界共同决定表格含义（[@ex-4.5.1]）；③ 差值不能归给 borrowck，它属于编译期（[@ex-4.5.2]、[@def-4.4.1]）；④ 方向要靠产物核验支撑，而不是靠结果一致（[@def-4.5.2]）；⑤ 修复要保持所需语义，必需的副本不能为性能删掉。下一节 [4.6 benchmark 二：隐式析构状态与 Option 状态](#sec-cpp-rust.1.4.6) 换成另一类回退：状态表达方式改变控制流。

::: errata 常见错误清单（4.5 节）

E-a **把这张表写成「Rust move 指令的成本」。**本实验没有测一次 Vec move 的独立纳秒数（4.5.1）。

E-b **用「结果一致」证明没有回退。**[@def-4.5.1]的形态恰好全部通过断言。

E-c **把批均值读成单条加法延迟。**分母摊薄了分配与复制（[@ex-4.5.1]、[@def-1.2.2]）。

E-d **把差值写成 borrowck 的运行时开销。**它不在运行时循环中执行（[@ex-4.5.2]）。

E-e **在符号表里搜到一条向量指令就宣布核验完成。**要确认它属于目标业务函数（见本节的思考框）。

E-f **拿 128KiB 的结论去排其它尺寸。**本轮没有采集别的分布（4.5.6）。

E-g **为消除 clone 而共享两个需要独立变化的缓冲。**语义先于成本（4.5.6）。

## 4.6 benchmark 二：隐式析构状态与 Option 状态 {#sec-cpp-rust.1.4.6}

本节回答一个问题：**把「可能还有资源」写进业务值（`Option`），对象尺寸没变，机器上的判断变了吗？**

::: preview 先抓住一件事

尺寸相同不等于代码相同。这个实验把同一份析构责任写成两种表达——直接条件移动，和用 `Option` 加 `take`——两边计数都必须是 8192，于是唯一变化的是状态表达方式与它带来的控制流形状。判断这类差异要三条证据并排看：类型尺寸表、批计时表、优化后产物里的合流形态。本节的克制之处恰恰是：三条证据只支持「相容」，不支持归因。
:::

### 4.6.1 相同责任的两种写法

::: def 定义 4.6.1 · 析构状态 destructor state {#def-4.6.1}

**析构状态**指「此刻这个位置上还要不要执行销毁」。4.4 节里它由编译器在[@def-4.4.2]的四类情形之间判定；本节的两种写法把它放在两个不同地方：第一种放在编译器推导的路径状态里，第二种显式写进业务值 `Option` 的「空或非空」。资源总量相同，状态的家不一样。
:::

入口是`src/bin/drop_paths.rs`。
每次逻辑调用创建两个 DropProbe。
flag 为 true 时提前销毁第一个。
flag 为 false 时在末尾销毁第一个。
第二个守卫总是在末尾销毁。

第一种写法直接条件移动到 drop。
第二种写法使用 Option 和 take。
后者把[@def-4.6.1]里的「可能还有资源」显式放进业务值。
两种写法最终都必须让计数增加两次。
这使我们可以比较状态表达，而不改变资源总量。

### 4.6.2 完整内核与完整入口

```rust
pub struct DropProbe<'a>(pub &'a Cell<u64>);
impl Drop for DropProbe<'_> {
    fn drop(&mut self) {
        self.0.set(self.0.get().wrapping_add(1));
    }
}

#[inline(never)]
pub fn conditional_drop(flag: bool, count: &Cell<u64>) {
    let first = DropProbe(count);
    let second = DropProbe(count);
    if flag {
        drop(first);
    }
    black_box(&second);
}

#[inline(never)]
pub fn option_drop(flag: bool, count: &Cell<u64>) {
    let mut first = Some(DropProbe(count));
    let second = DropProbe(count);
    if flag {
        drop(first.take());
    }
    black_box(&second);
}
```

Cell 只在单线程中访问。
没有数据竞争，也不需要原子计数。
但 Cell 的写入是真正被观察到的副作用。
black_box 保留第二份守卫相关的可观察边界。
本实验不代表一个没有副作用的空析构（对照 4.4.2 里对 Cell 的提醒）。

```rust
use compiler_lab::{Case, conditional_drop, measure, option_drop};
use std::{cell::Cell, hint::black_box};
fn run(f: fn(bool, &Cell<u64>)) -> u64 {
    let count = Cell::new(0);
    for i in 0..4096 {
        f(black_box(i % 2 == 0), &count);
    }
    count.get()
}
fn main() {
    let mut cases = [
        Case {
            name: "implicit",
            run: Box::new(|| run(conditional_drop)),
            expected: 8192,
        },
        Case {
            name: "option",
            run: Box::new(|| run(option_drop)),
            expected: 8192,
        },
    ];
    measure(&mut cases, 4096);
}
```

每个 run 包含 4096 次逻辑调用。
flag 在两种路径间交替。
返回的总计数必须是 8192。
把函数指针作为参数也属于夹具设计。
不要据此把结果解释成唯一一种业务调用形态。

::: ex 例 4.6.1 · 8192 是怎么被检查的 {#ex-4.6.1}

`expected` 写成常量 8192，而不是从被测实现算出来。请按[@def-1.1.3]与[@ex-1.5.1]说明：这个期望值为什么独立可得，以及如果两个 case 都返回 4096，计时表还有意义吗。

::: sol 解答

8192 来自规格而非实现：每次逻辑调用构造两个守卫、每个守卫的 `drop` 恰好加一次计数，4096 × 2 = 8192，与走哪条分支无关（`measure` 在每批结束后比较聚合 checksum，见 4.8.1）。这就是[@ex-1.1.1]要求的「与实现同源之外另有一个来源」。若两个 case 都返回 4096，说明有一条路径上的守卫没被销毁——[@def-4.6.1]的责任被漏记了，此时两张计时表比较的是两个做了不同工作的程序，数字再漂亮也不能读成「状态表达的成本」。

:::

:::

### 4.6.3 类型大小不能替代控制流比较

本机探针（只为观察产物变成什么样而留下的小程序）得到如下结果。
尺寸单位均为字节。

| 类型 | size | align | 含义 |
|:--|--:|--:|:--|
| DropProbe | 8 | 8 | 一份 Cell 引用 |
| Option&lt;DropProbe&gt; | 8 | 8 | 本轮复用非空引用 niche |
| Vec&lt;u64&gt; | 24 | 8 | 句柄，不含缓冲 |
| &amp;[u64] | 16 | 8 | 数据与长度 |
| Option&lt;&amp;u64&gt; | 8 | 8 | 不表示任意 Option 都同尺寸 |

::: def 定义 4.6.2 · niche 填充 niche optimization {#def-4.6.2}

**niche**（空隙）是一个类型本来就不可能用到的位模式。`&Cell<u64>` 这样的共享引用永远不为空地址，于是「空」这个模式就空了出来；`Option<&T>` 可以拿它表示 `None`，不必再加一个判别字段。这种把枚举标签塞进空隙的做法叫 **niche 填充**，表里 `Option&lt;DropProbe&gt;` 的 8 字节就是这么来的。
:::

按[@def-4.6.2]，Option 没有增加本轮守卫的对象尺寸。
这不意味着它没有额外状态判断。
状态可以编码在指针可用位模式里。
访问该状态仍可能形成分支。
对象大小相等也不意味着代码生成相同。

::: ex 例 4.6.2 · 同尺寸的两种写法，尺寸表回答了什么 {#ex-4.6.2}

`DropProbe` 与 `Option<DropProbe>` 都是 8 字节、对齐 8。请分别说明：这张表能否定哪一类解释，以及它为什么不能用来判定「两种写法一样快」。

::: sol 解答

它能否定的解释是「Option 多分配了一个堆盒子」——尺寸没变，而且 4.6.5 的产物里也没有额外的分配。它不能判定「一样快」，因为[@def-4.6.1]说的是状态住在哪儿：显式 `Option` 让合流点带上「空或非空」的值，后续要检查它才能决定是否销毁，这是控制流事实，尺寸表里看不到（对照[@def-4.1.1]的层分工）。最后一行的限定也要一起读：`Option<&u64>` 同尺寸不推广成「任意 Option 都同尺寸」。

:::

### 4.6.5 对照目标码解释

implicit 的正常路径已按 flag 分开。
Option 路径在中间合流时保留「空或非空」的指针状态。
随后检查是否仍需销毁 first。
这与优化后 IR 中的 phi 和 null 比较相对应。
它不是额外分配了一个堆盒子（[@ex-4.6.2]）。

本章不按分支条数直接计算纳秒。
不同分支形态的预测、流水与缓存效果需要单独测量。
本轮没有 PMU，也没有分支预测命中率。
因此只能说代码形态与总体观察相容。
不能说已经确定其中某一条指令占了差值的全部。

::: think 思考 · 「既然多一次 null 比较，那就该换回隐式写法」 {#think-4.6.1}

有人根据 4.6.5 的形状与 4.6.4 的均值差，提议把仓库里所有 `Option` 守卫改回「直接条件移动」的写法。按[@def-1.7.1]与[@def-1.7.3]的思路，这个提议缺了哪几件东西？

::: sol 解答

缺三件。第一，没有预算：0.216 ns/逻辑调用相对什么算重要？[@def-1.7.1]要求 B 在看到数字之前由业务约束写下，本轮没有这样的 B。第二，这是探索性观察：单内核、单尺寸、本机这一版产物（[@def-4.1.3]），[@def-1.7.3]要求确认性结论另做独立重跑。第三，它改的是可读性与接口形状，会把[@def-4.6.1]的状态显式地收回编译器推导，而「资源总量不变、只换表达」正是本实验成立的前提——一旦业务语义依赖 `take` 后的空值，两种写法就不再等价，计时表比较的对象也变了。

:::

### 4.6.6 实际安全失败回归

`panic_unwinds_initialized_guards`测试先构造一对守卫。
显式销毁其中一个字段后触发受控 panic。
catch_unwind 在测试边界观察展开完成。
最后要求两个守卫合计只销毁两次。
该测试本轮通过。

```rust
#[test]
fn panic_unwinds_initialized_guards() {
    let count = Cell::new(0);
    let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
        let pair = (DropProbe(&count), DropProbe(&count));
        drop(pair.0);
        panic!("intentional safe regression");
    }));
    assert!(result.is_err());
    assert_eq!(count.get(), 2);
}
```

这条测试检查的正是[@ex-4.3.1]的部分移动加上[@def-4.4.3]的展开路径：`pair.0` 已移走，展开时不能第二次销毁它，`pair.1` 仍要负责。

测试没有在 Drop 内再次 panic。
它也没有证明所有析构函数都可失败恢复。
它验证的是一个部分移动加展开的具体责任交接。
因为没有执行 UB，所以失败时的解释仍建立在语言定义行为上。
不要用双重释放来制造所谓「更明显」的析构样例。

### 4.6.7 小结与常见错误

**小结。**① 两种写法资源总量相同，变的只是[@def-4.6.1]里状态的家；② 期望值 8192 来自规格，不来自实现（[@ex-4.6.1]）；③ niche 填充让尺寸不变，但状态判断仍在控制流里（[@def-4.6.2]、[@ex-4.6.2]）；④ 本轮均值差没有配对区间（[@ex-4.6.3]）；⑤ 产物形态与观察相容不等于机制归因完成，缺 PMU 就不谈分支命中率；⑥ 展开路径的责任交接靠安全测试证明，不靠制造 UB。下一节 [4.7 查询缓存、增量缓存与代码生成单元](#sec-cpp-rust.1.4.7) 把镜头从运行期移回构建期。

::: errata 常见错误清单（4.6 节）

E-a **按对象尺寸相同推断代码相同。**状态判断与析构责任不在尺寸里（[@ex-4.6.2]）。

E-b **把 niche 同尺寸推广成「Option 永远不花钱」。**表最后一行已经限定（[@def-4.6.2]）。

E-f **为了「更明显」制造双重释放样例。**安全回归靠展开测试完成（4.6.6）。

## 4.7 查询缓存、增量缓存与代码生成单元 {#sec-cpp-rust.1.4.7}

本节回答一个问题：**哪些成本属于构建期，它们要怎样才能不被写进运行期的那张表？**

::: preview 先抓住一件事

编译器内部的「缓存」有三个不同的家：一次编译会话内的记忆化、跨构建的增量缓存、以及 Cargo 对整个构建单元的最新状态判断。三者的命中条件、失效条件和计时对象都不同。肯定「这项计算被复用了」要说清是哪一层复用；否定它只要一条线索——磁盘上有目录不代表会命中。本节同时划出观察上限：本轮没有 self-profile 数据，任何「某个查询花了多久」的说法都没有证据。
:::

### 4.7.1 查询是构建期的需求接口

::: def 定义 4.7.1 · 查询 query（编译器意义） {#def-4.7.1}

可以把一个**查询**理解为「名字、键、结果、provider」四件套：名字说明问的是哪类事实，键说明问的是哪个定义，结果是被算出来的东西，provider 是计算它的代码。例如针对某个函数询问它的类型。它按需触发，用完可在同一编译会话里被记住。
:::

按[@def-4.7.1]，provider 需要别的事实时再调用其他查询。
同一编译会话可以记忆已经得到的结果。
这避免重复执行同一计算。

查询不是应用运行时的 HashMap 查询。
它不意味着你的每次泛型调用都会查编译器缓存。
它也不是一个网络数据库服务。
开发指南的数据库比喻用于解释依赖计算。
不要把这个比喻带到性能热路径中（对照[@def-4.1.1]的层分工）。

### 4.7.2 纯输入与依赖图

::: def 定义 4.7.2 · 记忆化与依赖图 memoization / dependency graph {#def-4.7.2}

**记忆化**指把一次查询的结果连同它的输入一起存住，下次同键直接返回。**依赖图**是「谁用到谁」的关系集合：一次查询调用可以触发一串前置查询，两个调用又可以共享某个子查询结果。要让结果可复用，provider 读到的每一项事实都必须登记为输入——源码、选项与上游元数据都算。
:::

按[@def-4.7.2]，可复用的查询结果需要有可追踪输入。
如果 provider 偷读没有登记的外部可变状态，缓存就可能失真。
源码、选项与上游元数据都可能成为相关输入。
正确性依赖这些事实被纳入依赖关系。
这也是构建脚本需要声明输入变化的重要背景。

一次查询调用可以触发一串前置查询。
两个调用又可以共享某个子查询结果。
概念上形成一个依赖图，而非每次重跑整条流水线。
环依赖则需要报告诊断。
不能用「反正会缓存」解释无限递归。

### 4.7.3 两种缓存不可混称

::: def 定义 4.7.3 · 会话内记忆化与增量编译 memoization vs incremental compilation {#def-4.7.3}

**会话内记忆化**只在同一次编译进程里有效，进程结束就消失。**增量编译**试图跨构建复用：它要把之前记录的输入与依赖和当前状态做有效性判断，命中才复用。两者常被一起写成「编译器的缓存」，但计时对象完全不同。
:::

按[@def-4.7.3]，会话内记忆化发生在同一次编译进程内。
增量编译还尝试在不同构建之间复用有效计算结果。
后者需要判断之前的输入和依赖是否仍有效。
磁盘上存在目录并不意味着每一项都可命中。
切换工具链或重要编译选项可能使旧缓存失效。

Cargo 的「不需要重新运行 rustc」又是另一个层次。
如果整个构建单元被判为最新，甚至不会进入本次 rustc 会话。
把这种 no-op 构建时间当作查询引擎耗时会严重误导。
**本章没有采集增量编译的定量加速表**：没有执行过的构建矩阵不补造秒数。

::: ex 例 4.7.1 · 这三条观察分别属于哪个家 {#ex-4.7.1}

三条观察：① 第二次执行 `cargo build` 时 rustc 一次都没启动；② 修改了一个函数体，重编只重做了部分工作；③ `target/` 目录存在，但换了一个工具链之后仍然全量重编。请分别归入[@def-4.7.3]的哪一层，并指出每条能不能拿来当「查询引擎很快」的证据。

::: sol 解答

① 属于 Cargo 的最新状态判断：整个单元被判为最新，连 rustc 会话都没进入，因此它测不到编译器内部任何东西。② 属于增量编译：跨构建复用了部分有效计算，但它能不能归给某个查询，要看 self-profile——本轮没有采集（4.7.6）。③ 属于增量缓存的失效条件：换工具链使旧记录的输入不再有效，正好证明「目录存在不等于命中」。三条都不能写成「查询引擎耗时」，只有第三条能支撑一句否定式的提醒：看到目录在，不能假定复用了。

:::

:::

### 4.7.4 Steal：所有权也存在于编译器内部

::: def 定义 4.7.4 · Steal {#def-4.7.4}

**Steal** 是编译器内部一类「可被转移所有权的中间结果」。后续阶段要原地改写它时，把它整个搬走，而不必克隆整份 MIR。代价是：需要读取旧阶段的分析必须在转移完成之前做完，否则读到的已是改写后的东西。
:::

按[@def-4.7.4]，母本解释的正是这类可转移所有权的中间结果。
它避免为下一组转换克隆整份 MIR。
需要读取旧阶段的分析必须在转移之前完成。
这是有约束的内部性能设计。
它不是用户可调用的稳定 MIR 缓存 API。

这个例子很适合作为工程类比。
一个结果既要便宜共享，又要被后续原地改写时，需要阶段协议。
只把数据放进 Arc 不会自动解决所有权冲突。
但不应据此在业务代码中模拟 rustc 的内部类型。
优先使用适合自身生命周期的简单接口。

::: think 思考 · 「包一层 Arc，共享与改写就都解决了」 {#think-4.7.1}

有人读完 4.7.4 说：我们的业务代码里也有一份要被多个阶段读写的中间结果，用 `Arc<Mutex<T>>` 包起来就能既共享又原地改写，不需要阶段协议。这个类比在哪一步失效？

::: sol 解答

失效在「谁在什么时候读到什么」。[@def-4.7.4]的约束不是防止数据竞争，而是保证**旧阶段的读取发生在新阶段改写之前**；`Arc` 与 `Mutex` 管的是同一份数据能否被安全访问，管不了「先读旧含义、后写新含义」这个顺序。加了锁之后，改写照样可能发生在读取之前，于是旧阶段拿到的是改写后的结果——错误更隐蔽，因为一切看起来都是安全的。

rustc 选 steal 这种转移所有权的写法，正是因为它要的是阶段协议而不是并发保护。业务代码里对应的做法通常是按阶段传值、或者显式区分两个版本的数据，而不是给共享加锁——这也是本节反对「在业务代码里模拟编译器内部类型」的原因。

:::

:::

### 4.7.5 代码生成单元改变什么

::: def 定义 4.7.5 · 代码生成单元 codegen unit, CGU {#def-4.7.5}

**代码生成单元**是单态项收集之后交给后端（LLVM）的分区单位。一个 crate 可以切成多个 CGU 并行编译；切法决定哪些函数在同一个优化视野里，因此也影响能做的跨函数优化。LTO（链接期优化）会再改变一次跨模块的可见范围。
:::

按[@def-4.7.5]，单态项收集后需要分区给后端。
多个代码生成单元有利于并行构建与部分复用。
它也可能影响某些优化看到的范围。
LTO 会再改变部分跨模块优化机会。
因此 CGU 与 LTO 必须同时记录（[@def-1.1.3]的外部条件集合）。

| 构建机制 | 主要影响 | 不直接保证 |
|:--|:--|:--|
| Cargo 最新状态判断 | 是否重新执行构建步骤 | 热路径更快 |
| 查询记忆化 | 会话内重复计算 | 所有结果永久持久化 |
| 增量编译 | 修改后可复用的构建工作 | 每次构建都更小 |
| 多 CGU | 后端分区与并行机会 | 运行时线程并行 |
| ThinLTO | 跨模块分析与导入 | 所有函数必定内联 |

本轮 release 固定一个 CGU。
LTO 为 false。
debug 信息等级为 1。
没有把 debug profile 和 release profile 混在统计里。
这些约束使对照可解释，但不是通用最优构建配置。
它们与 4.1.5 的工具链事实一起，构成[@def-4.1.3]意义上的本机观察范围。

### 4.7.6 稳定版 MIR 的观察上限

稳定版的 emit 输出是一份可读表示。
它不携带所有中间阶段的完整历史。
本轮 opt-level 0 与 3 的 stages 产物可以比较最终表示。
但不能因此把两份文件的差异精确归给某一个 pass。
同一次编译中可能有多个转换共同改变控制流。

`extra-02/stages-o0.mir`与`stages-o3.mir`保留了这个对照。
同目录还保存两种优化等级的 LLVM IR 和汇编。
对应程序都实际运行了 count=2 的断言。
它们是分析探针，不是正式计时入口。
因此本章没有把 opt-level 0 的运行时间放进性能表。

| 想回答的问题 | 本轮是否有证据 | 合法表述 |
|:--|:--|:--|
| 最终 MIR 是否有条件析构 | 有 | 固定输出可见对应控制流 |
| O0 与 O3 产物是否相同 | 有两组文件 | 可以比较整体差异 |
| 哪个 pass 首次删除某个节点 | 无逐 pass dump | 本轮未确定 |
| borrowck 每个查询花多久 | 无 self-profile | 本轮未测 |
| THIR 节点实际长什么样 | 无可用 nightly | 使用文档解释而非本机转储 |

第三、四、五行是本节的证据缺口声明：**逐 pass 的 before/after 转储与 self-profile 计时都属于「本节没有采集」**，前者缺可用 nightly（4.2.4），后者缺专门运行。

::: ex 例 4.7.2 · 两份 MIR 的差异能归给某个 pass 吗 {#ex-4.7.2}

`stages-o0.mir` 与 `stages-o3.mir` 是同一份探针程序在两个优化等级下的最终 MIR。有人对比两份文件后写下「MIR 优化 pass X 在这里删掉了那条 drop」。请按上表的第三行判定这句话，并给出本轮证据允许的替代写法。

::: sol 解答

这句话超出了证据。两份文件都是**最终**表示，中间没有逐 pass 转储，所以「谁先删的」无法定位——同一次编译里可能有多个转换共同改变控制流，[@def-4.1.2]的依赖图本来就不是一条可回溯的时间轴。更要紧的是，这句话的方向本身就错了：数一下归档里的 `drop` 语句，`stages-o0.mir` 有 4 条（第 73、86、94、98 行），`stages-o3.mir` 有 6 条（第 90、99、107、132、143、148 行），O3 的最终 MIR 里**不是更少而是更多**；O3 还多出 20 处 `StorageDead`（O0 为 0）。允许的写法是：「O0 的最终 MIR 里有 4 条 `drop` 语句，O3 的最终 MIR 里有 6 条，另有 20 处 `StorageDead`；本轮没有逐 pass 转储，无法指认是哪些转换改的。」这与[@ex-1.8.1]的分层思路一致：先说清观察属于哪一层，再谈能支持什么结论。

:::

:::

分析编译器回归时，这些边界尤其重要。
若某版本最终代码变化，首先保存最小输入与两份完整产物。
随后再在可用工具链上增加阶段日志。
不能从最终差异逆向编造一次没有记录的 pass 执行顺序。
也不能把没有符号解释成源程序里的责任不存在。
优化可能只是把责任合并进其他控制流（对照[@def-4.1.1]：某一层里看不到，不等于另一层里不存在）。

### 4.7.7 构建回归的可操作检查

先区分冷构建、no-op 构建和修改后构建。
再区分类型检查、单态项生成、LLVM 与链接。
应保留实际命令、缓存状态和修改补丁。
只记录一次总秒数，很难给出责任归因。
本章的运行时实验不替代构建期 profiling。

::: method 判定流程 · 一次「编译变慢」报告的最小记录

① 先分类：冷构建、no-op 构建、还是修改后构建？三者的命中条件不同（[@def-4.7.3]），混在一起就谈不上比较。<br>
② 再分层：类型检查、单态项生成、LLVM 后端、链接各占多少？只记一个总秒数无法归因。<br>
③ 记下实际命令、工具链提交、`RUSTFLAGS`、CGU 与 LTO 设置（[@def-4.7.5]），也就是[@def-1.1.3]的外部条件集合。<br>
④ 保留缓存目录状态与本次修改的补丁，让「命中/未命中」可被复核（[@ex-4.7.1]）。<br>
⑤ 需要逐查询成本时，改用可用且固定的 nightly 并单独保存 self-profile；本轮拿不出这类数据，所以本节不给任何秒数。
:::

若下一轮要测查询成本，应使用可用且固定的 nightly。
应该单独保存 self-profile 数据与对应工具版本。
不能把本轮损坏 nightly 的名字当作可复现版本号。
编译失败记录是能力边界证据，不是编译器性能证据。

### 4.7.8 小结与常见错误

**小结。**① 查询是构建期的需求接口，与运行时无关（[@def-4.7.1]）；② 复用要连着登记的输入才成立（[@def-4.7.2]）；③ 记忆化、增量编译、Cargo 最新判断是三个家，别混称（[@def-4.7.3]、[@ex-4.7.1]）；④ Steal 说明编译器内部也要阶段协议，但它是内部设计不是可用 API（[@def-4.7.4]）；⑤ CGU 与 LTO 必须与代码产物一起记录（[@def-4.7.5]）；⑥ 观察上限要如实写：本轮没有逐 pass 转储与 self-profile（[@ex-4.7.2]）。下一节 [4.8 证据链、测量夹具与回归定位](#sec-cpp-rust.1.4.8) 回到运行期，把这一章的夹具讲完。

::: errata 常见错误清单（4.7 节）

E-a **把编译器的查询当成运行时 HashMap。**它发生在编译程序时（[@def-4.7.1]）。

## 4.8 证据链、测量夹具与回归定位 {#sec-cpp-rust.1.4.8}

本节回答一个问题：**本章那些数字要能被别人复核，夹具必须满足哪些条件，出现回退时又按什么顺序找？**

::: preview 先抓住一件事

一个可复核的数字交付的从来不只是一个数：完整的夹具源码、原始批次、校验规则、隔离记录，以及「哪一层证据回答哪一个问题」的分工。这六个入口共用一份 `measure`，所以任何一处边界移动都会同时影响六张表。判断回退的顺序也由此定下：先证明业务一致，再核对工作是否留存，然后才谈速度差异与机制解释。
:::

### 4.8.1 共享夹具的完整核心

六个入口共用同一个 measure 函数。
每个 case 至少单独预热 500ms。
预热阶段校验每次返回值。
随后根据预热速度选择约 10ms 的批次重复数。
正式采样每个 case 21 批。

```rust
pub struct Case<'a> {
    pub name: &'a str,
    pub run: Box<dyn FnMut() -> u64 + 'a>,
    pub expected: u64,
}

/// Reports batch means, not a distribution of individual request latencies.
pub fn measure(cases: &mut [Case<'_>], units: usize) {
    assert!(units > 0);
    let mut repeats = Vec::new();
    for case in cases.iter_mut() {
        let start = Instant::now();
        let mut n = 0;
        while start.elapsed() < Duration::from_millis(500) {
            assert_eq!(black_box((case.run)()), case.expected);
            n += 1;
        }
        let ns = start.elapsed().as_secs_f64() * 1e9 / n as f64;
        repeats.push((10_000_000.0 / ns).ceil().max(1.0) as usize);
    }
    println!("case,round,repeats,units,elapsed_ns,ns_per_unit,checksum");
    let mut samples = vec![Vec::new(); cases.len()];
    for round in 0..21 {
        for offset in 0..cases.len() {
            let index = (round + offset) % cases.len();
            let case = &mut cases[index];
            let n = repeats[index];
            let start = Instant::now();
            let mut checksum = 0u64;
            for _ in 0..n {
                checksum = checksum.wrapping_add(black_box((case.run)()));
            }
            let elapsed = start.elapsed().as_nanos();
            assert_eq!(checksum, case.expected.wrapping_mul(n as u64));
            let value = elapsed as f64 / (n * units) as f64;
            samples[index].push(value);
            println!(
                "{},{round},{n},{units},{elapsed},{value:.9},{checksum}",
                case.name
            );
        }
    }
    for (case, values) in cases.iter().zip(samples.iter_mut()) {
        let mean = values.iter().sum::<f64>() / values.len() as f64;
        let sd = (values.iter().map(|v| (v - mean).powi(2)).sum::<f64>()
            / (values.len() - 1) as f64)
            .sqrt();
        values.sort_by(f64::total_cmp);
        println!(
            "summary,{},{mean:.9},{sd:.9},{:.9},{:.9}",
            case.name, values[10], values[20]
        );
    }
}
```

正式轮次轮转 case 起点。
但这不是随机化试验，也不是全局热状态隔离。
预热逐 case 执行，仍可能有顺序效应。
所有表格都保留原始批次，而不是只保留最快值。
输出中的 repeats 是实际批重复数。

::: def 定义 4.8.1 · 原始点与批均值 {#def-4.8.1}

**原始点**是 `measure` 打印的一行 CSV：一个 case、一个 round、一次批次的墙钟时长除以「批重复数 × units」。**批均值**是 21 个原始点的算术平均（[@def-1.2.2]）。两者都是聚合量，不是任何一次单独请求的耗时。
:::

按[@def-4.8.1]，本章每张表里的 mean、N-1 sd、批 p50、批 p99 都是从这 21 个原始点算出来的。
`value` 的分母是 `n * units`，其中 `n` 是这一批实际执行的重复数。
表里的 ns/元素或 ns/逻辑调用因此是吞吐倒数，含义随 units 变化。

### 4.8.2 校验的强度与边界

每次内核运行返回一个 u64。
批内做 wrapping 聚合。
批结束之后与期望值乘重复数比较。
这是可观察工作量检查（对照[@def-1.3.1]）。
它不能排除所有 checksum 碰撞。

因此还配套逐元素和边界长度测试。
求和测试包含空输入与非整块尾部。
析构测试分别覆盖 flag 的两个值。
展开测试覆盖部分移动后的销毁（[@ex-4.3.1]、[@def-4.4.3]）。
校验不是只在 main 的最后打印一个常数。

::: ex 例 4.8.1 · checksum 挡住的是什么，挡不住什么 {#ex-4.8.1}

夹具在每批结束后比较 `checksum` 与 `case.expected.wrapping_mul(n)`。请说明：① 这条检查为什么能排除[@def-1.1.1]所说的那类假结果；② 它挡不住什么；③ 为什么还要另外的边界长度测试。

::: sol 解答

① 因为每次调用的返回值都被读进聚合量，「结果没人用」这一条不再成立，循环不能被整段删掉——第 1 章的 `discarded` 那类假结果在这里会算出错误的 checksum（[@ex-1.5.1]）。② 它挡不住碰撞：wrapping 加法下不同的逐次返回值序列可能聚合成同一个和，所以「checksum 对」只说明总聚合一致，不证明每次实现做的是同一件事；这正是[@def-1.1.3]要求把观察集合单独写出来的原因。③ 空输入与非整块尾部走的是不同的分支路径，聚合值相同也不代表路径被覆盖过；边界测试补的是覆盖，不是强度——所以 4.5.5 仍要用[@def-4.5.2]在产物里核对工作是否留存。

:::

:::

### 4.8.3 分位数含义

样本 mean 是 21 个批均值的算术平均。
sd 的分母是 N-1。
p50 使用 nearest-rank（[@def-1.5.2]）。
21 个样本的 nearest-rank p99 等于最大样本。
这不是逐请求 p99：批次样本里没有留下逐请求分布。
要请求级分位数就得换一套采集设计，那属于[@def-1.8.2]意义上的实验重跑，不是在旧表上改列名。

::: ex 例 4.8.2 · 表里的 p99 为什么就是最大值 {#ex-4.8.2}

`measure` 排序后取 `values[10]` 当 p50、`values[20]` 当 p99。请验证这两个下标与[@def-1.5.2]的 nearest-rank 定义一致，并解释「borrow 的批 p99 是 0.063338」能不能写成「单次调用的 99 分位延迟」。

::: sol 解答

`ceil(21 × 0.50) = 11`，从 1 计数即下标 10，对应 p50；`ceil(21 × 0.99) = 21`，即下标 20，也就是这批样本的最大值——两个下标与定义一致。
不能写成单次调用延迟：每个样本本身是一整批（`n` 次调用）的归一化墙钟时间（[@def-4.8.1]），批内个别慢调用已经被摊平，逐调用分布没有被保存。要请求级分位数，必须改成逐请求观测的采集设计，而不是在同一批上换个列名——换过列名的数字仍然真实，但它回答的不是这个问题。

:::

:::

小于一纳秒的 ns/元素也不意味着一条依赖指令只耗时这么短。
批内多个元素可能重叠执行。
向量操作可以同时处理多个元素（4.5.5 的归约就是这种形状）。
批时间还被大量元素摊薄。
应该把它理解为聚合吞吐倒数（对照[@ex-4.5.1]）。

### 4.8.4 运行隔离记录

`run.sh`通过 mkdir 获取独占测量目录锁。
正式六个进程顺序执行。
退出 trap 会释放锁。
每个入口运行前检查 cargo 和 rustc 进程。
本轮这些检查没有发现活动构建进程。

这只能说明被检查时刻没有观察到这些构建。
它不证明桌面系统没有其他竞争。
也不提供固定频率、固定核心或温度控制。
脚本明确保留这些限制。
不能把目录锁称为操作系统级 benchmark 隔离。

::: think 思考 · 「锁目录 + 顺序执行，所以结果是干净稳态」 {#think-4.8.1}

一位读者看到 `run.sh` 用 `mkdir` 取锁、六个进程顺序执行、每个入口前还检查了构建进程，于是写下「本章数据已做操作系统级隔离，可以当作稳态基线」。这条推理被绕开的前提是什么？

::: sol 解答

被绕开的前提是「锁住了谁」。目录锁只串行化本脚本自己的测量进程，防止两次运行互相干扰；它既不固定频率、不绑定核心、不控温，也不阻止桌面其它程序在同一时刻抢占。检查 cargo/rustc 进程只说明**被检查那一刻**没有活动构建，不是一整段时间的保证。真正需要的是[@def-1.1.3]外部条件集合里的完整记录：本章如实写出这些限制（4.1.5），并要求跨机器复现时按[@def-1.8.2]的实验重跑重新采集，而不是沿用这张表当稳态基线。
:::

:::

### 4.8.5 汇编与采样各自回答什么

::: def 定义 4.8.2 · 静态产物与采样 static artifact vs sampling {#def-4.8.2}

**静态产物**（LLVM IR、汇编）说明一次给定构建留下了什么工作，是对代码的检查。**采样**（macOS `sample`）说明另一次运行在哪些调用栈上被采到，是对进程的观察。两者都不是[@def-1.2.2]意义上的批计时，也互不替代。
:::

按[@def-4.8.2]，汇编说明给定构建留下了什么工作。
macOS sample 说明另一次运行在哪些栈上被采到。
两者不是同一种时间测量。
sample 运行没有进入 21 批正式统计。
本轮采样附着到 dispatch_grain。

因此第 4 章内核没有单独的采样占比。
本章复用该文件只是交代整个实验包的观测能力。
不把 trait 内核的采样热点冒称为 clone 内核热点。
也不报告没有采集的 cache miss、IPC 或核心 cycle（4.6.5 同此）。

### 4.8.6 复现命令与归档边界

从`cpp-rust/`执行以下命令。
新目录必须不存在。
脚本不会覆盖既有归档。

```bash
cargo fmt --manifest-path bench/compiler-lab/Cargo.toml --check
cargo clippy --offline --locked \
  --manifest-path bench/compiler-lab/Cargo.toml --all-targets -- -D warnings
cargo test --offline --locked --manifest-path bench/compiler-lab/Cargo.toml

```

第一组测试验证安全契约。
第二组正式脚本创建六个独立可执行文件的批次记录。
第三组脚本验证编译拒绝与补充产物。
它不执行被拒绝输入。
PGO 工具缺失时会明确记录未执行。

这套命令支撑两种不同的复现目标（[@def-1.8.2]）：重算摘要要在同一份 CSV 上做，重跑实验要新建目录。改过夹具或内核之后，旧归档只对应旧二进制，结论要按[@def-4.1.3]重新采集。

### 4.8.7 找回归时的证据顺序

先证明两种程序执行所需业务一致。
再检查分配、调用与复制是否真的保留。
然后看正式批次是否支持速度差异。
最后提出需要进一步隔离的机制解释。
这个顺序有助于避免从一张耗时表倒推出不存在的硬件事件。

例如 clone 回退可以先定位到显式副本。
它不需要假设 borrowck 变慢（[@def-4.4.1]）。
Option 回退则需要承认状态表达与分支形态都变化。
它不能归因成多了八字节对象，因为本机尺寸并未增加（[@ex-4.6.2]）。
这两种回归说明「先看正确层次」的实际价值。

::: ex 例 4.8.3 · 按顺序走一遍 clone 回退 {#ex-4.8.3}

有人在评审里写：「clone 分支比借用分支慢 3.43 倍，说明借用检查让运行期变慢，应该去掉 `to_vec` 改回切片签名。」请按本节顺序逐条核对，指出他跳过了哪几步。

::: sol 解答

第一步业务一致：两个 case 都返回同一份独立算出的 `expected`，一致（4.5.2）。第二步产物核对：`cloned_sum` 里确实保留 allocator 调用、`llvm.memcpy` 与 deallocator，本机目标码里有 `_memcpy`（4.5.5）——所以差异的来源是显式副本，不是检查器。第三步批次支持方向：0.202739 对 0.059091，21 个原始点（[@def-4.8.1]）。他跳过的正是第二步：把成本归给借用检查（[@def-4.4.1]），而 borrowck 不在运行时执行（[@ex-4.5.2]）。至于「去掉 `to_vec`」，那是另一个语义问题：调用者若只需观察就传切片，若需要两个独立拥有者则副本是业务本身（4.5.6）。

:::

:::

::: method 判定流程 · 回归定位的四步顺序

① **业务一致吗**——期望值是否独立算出、逐次被观察（[@ex-4.6.1]、[@def-1.3.1]）。不一致就先别谈速度（[@def-1.6.1]）。<br>
② **工作留存吗**——按[@def-4.5.2]在目标业务函数的产物里找分配、复制、调用、归约；找不到就别说它发生了。<br>
③ **批次支持吗**——看 21 个原始点与 sd（[@ex-4.8.2]），本轮没算区间就不要写区间（[@ex-4.6.3]）。<br>
④ **机制能解释吗**——只有前三步都成立，才提需要进一步隔离的假设；缺 PMU 就不写 cache miss、IPC 或分支命中率（4.6.5、4.8.5）。
:::

### 4.8.8 小结与常见错误

**小结。**① 六个入口共用一份夹具，所以计时边界、校验位置、隔离程度都属于契约的一部分（[@def-4.8.1]、[@def-1.1.3]）；② checksum 排除「结果没人用」，不排除碰撞，覆盖要靠边界测试（[@ex-4.8.1]）；③ p99 在这套设计里就是 21 个批样本的最大值，不是请求分位数（[@ex-4.8.2]）；④ 静态产物、采样、计时各答一个问题（[@def-4.8.2]）；⑤ 定位回归按四步顺序走，别从耗时表倒推硬件事件（[@ex-4.8.3]）。章末的 [4.9 延伸阅读与来源](#sec-cpp-rust.1.4.9) 给出这些方法的出处。

::: errata 常见错误清单（4.8 节）

E-a **把 `ns/元素` 读成单条指令延迟。**它是批均值摊到元素上的吞吐倒数（[@def-4.8.1]、[@ex-4.8.2]）。

E-b **把批 p99 写成请求 p99。**21 个批样本里的 p99 就是最大值（[@ex-4.8.2]）。

E-c **以为 checksum 通过就证明每次实现同工作。**碰撞没有被排除，覆盖要靠边界测试（[@ex-4.8.1]）。

E-d **把目录锁称作操作系统级隔离。**它只串行化本脚本的测量进程（见本节的思考框）。

E-e **拿 `dispatch_grain` 的采样当作 clone 内核的热点。**采样附着对象与结论范围要一致（4.8.5）。

E-f **在旧归档上写新说明。**改过内核就要重新采集（[@def-1.8.2]、[@def-4.1.3]）。

E-g **从速度差异直接跳到机制解释。**顺序是业务、产物、批次、机制（[@ex-4.8.3]）。

:::

::: method 即时自测 · 4.8

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　说出夹具的四个数字：预热时长、批次目标时长、正式批数、每批校验位置。

::: sol 第 1 题答案
每个 case 至少单独预热 500ms；按预热速度选择约 10ms 的批次重复数；正式采样每 case 21 批；校验在每批计时结束后比较聚合 checksum 与「期望值 × 重复数」，而预热阶段就已逐次断言返回值。对应[@def-4.8.1]与 4.8.2。
:::

**第 2 题 · 辨析**　「同一份 `measure` 被六个入口共用，所以六张表可以直接横向排名。」为什么不行？

::: sol 第 2 题答案
共用夹具只保证「测量方式相同」，不保证「比较对象相同」。各表的 units 不同（元素数、逻辑调用数），[@def-4.8.1]的分母因此不同；两个入口的语义工作也可能不同，不满足[@def-1.6.1]的等价条件。第 1 章[@def-1.1.3]的契约在这里同样适用：跨表比较要先对齐输入、计时与观察集合。
:::

**第 3 题 · 应用**　复现者报告「跑通了，但 checksum 与归档不符」。按 4.8.6 与四步顺序，你第一步做什么？

::: sol 第 3 题答案
这是功能失败，不是性能差异（[@ex-1.8.1]的第②层）。第一步核对源码指纹与构建条件是否同一版本（[@def-4.1.3]、[@def-1.8.2]），先修功能与契约，再谈任何耗时；此时把差异写成「新版更快/更慢」都没有意义。
:::

**第 4 题 · 迁移**　你要在 CI 上长期跑这套夹具，但 CI 机器同时跑构建、测试与安全扫描。按[@def-4.8.2]与本节，改哪三处最能减少误报？

::: sol 第 4 题答案
① 保留并扩展独占测量锁的语义：把正式测量与并发任务串行化，并记录被检查时刻的进程状态（4.8.4），同时如实写明锁不覆盖其它竞争（4.8.4 的思考框）；② 把「运行」当成抽样单位，不同时段独立重跑，而不是在同一批上多加次数（[@def-1.8.2]）；③ 门禁只吃正确性失败与[@def-4.8.1]口径下的区间结论，别把每个小数位波动标红（第 1 章 1.7.4 的同一教训）。采样类文件不进正式统计（[@def-4.8.2]），CI 上也一样。
:::

:::

## 4.9 延伸阅读与来源 {#sec-cpp-rust.1.4.9}

### 4.9.1 四条值得继续读的入口

- **Guide to Rustc Development（rustc 开发指南）**：查询与记忆化、HIR 与 MIR 的构建与阶段依赖、move path 与初始化分析、MIR 优化与常量求值、单态项与后端分区。它是本章 4.2、4.3、4.4、4.7 的机制来源。母本里的 HAIR 是较早的历史称呼，本章按当前指南的 THIR 纠正它的上下文（[@def-4.2.3]）。

1. **只读一层就下结论。**两个 benchmark 的差别都长在「第二层说责任、第三层说搬运」的接缝上。只看汇编会漏掉[@def-4.5.1]那种全部绿灯的回退；只看 MIR 会误报栈槽数量（[@def-4.3.1]）。先按[@def-4.1.1]选层，再取产物。

3. **换了语义还沿用旧数字。**三个返回同一长度的签名（[@ex-4.2.2]）、把 `Option` 改回条件移动（[@ex-4.6.3]）、把 `&[u64]` 改成消费 `Vec`（4.5 即时自测第 4 题）都改变了比较对象。[@def-1.6.1]的等价条件一旦不成立，耗时表就没有可解释的差值。
4. **把构建条件写成脚注。**CGU、LTO、panic 策略、`RUSTFLAGS`、工具链提交共同决定产物形状（[@def-4.7.5]、[@def-4.1.3]）。改动其中任何一项，都属于[@def-1.8.2]意义上的实验重跑，而不是在旧结论旁边补一句话。

## 4.11 本章小结与章末件 {#sec-cpp-rust.1.4.11}

::: note 本章小结

- 同一个所有权动作在三层的形状不同：责任、状态、搬运各归不同层管，跨层引用必须先说清出处（[@def-4.1.1]、[@ex-4.1.1]）。
- 类型检查之后的隐式调整省不掉：自动引用、方法选择、销毁作用域要在 THIR 里写明白；这两层的本机转储来自 2026-11-01 补采的 nightly 产物（[@def-4.2.3]、4.2.4）。
- 「未初始化」是数据流事实而不是位模式：读取要求「必定初始化」，析构责任要看「可能未初始化」（[@def-4.3.4]、[@ex-4.3.3]）。
- 析构责任落进四类情形，只有静态定不下来的才可能需要运行期判断；正常边与展开边必须一起审查（[@def-4.4.2]、[@def-4.4.3]）。
- 两类回退各测一次：完全正确的 clone（[@def-4.5.1]）与尺寸不变而控制流改变的 Option（[@ex-4.6.2]）；构建期的查询与缓存不属于运行期成本（[@def-4.7.3]）。

**改动实验时的责任**：改输入长度要重算参考值（[@ex-4.6.1]）；改计时边界要重新解释单位（[@def-4.8.1]）；改 panic 策略、CGU 或 LTO 要重新生成产物（[@def-4.7.5]、4.4.6）；改被测内核要新建归档重跑，而不是在旧结论旁边补一句话（[@def-1.8.2]）。

**本轮能力边界**：八项运行时契约测试通过，五项编译拒绝输入返回预期错误代码，六个正式入口均已运行并校验输出，每个 case 保留 21 个正式原始点。这些事实不等于任意输入、任意版本都已被验证。没有执行 Miri、Loom、TSan 或 Linux perf；没有可用 nightly 的阶段内部转储；没有借此宣布 rustc 本身已经审计。独立技术审阅仍由后续整合安排。读者应把本章的分层方法用于缩小证据，而不是扩大没有执行过的结论。

:::
