# 2 对象：布局、热字段与可证明的存储复用

<div class="chapter-index">

**问题主线**：一个对象占多少字节、访问哪些字节、谁承担存储成本，如何共同决定Rust数据通路的性能？

- 区分语言保证、标准库保证与当前编译器观测。
- 用实际偏移、niche（类型编码里剩下来、轮不到合法值的空位）和代码生成解释布局，而非依赖想象图。
- 对照AoS与热列投影，限定缓存与向量化（一条 CPU 指令同时处理多个数）归因。
- 用纯安全字节区域复用存储，不包装未经证明的通用分配器（按需划分和回收内存的那个库）。
- 明确容量失败、旧数据、reset借用边界与绝对地址对齐责任。

## 2.1 类型布局：保证、观测与外部格式 {#sec-cpp-rust.1.2.1}

本节回答一个问题：**为什么「这个对象占多少字节」不是一个能独立回答的问题？**size 要配上 align 和字段偏移才说得完，而这三者各自属于哪一层承诺，决定了这句话能走多远。

::: preview 先抓住一件事

一条布局结论的可信度，取决于它**属于哪一层保证**：语言约束、标准库保证，还是本机一次观测。要肯定它，得同时说清量的是 size、align 还是偏移，用的是哪种 `repr`、哪个目标、哪次构建；要否定「声明顺序就是文件格式」，只需要一条规则——默认 `repr` 不承诺字段安排。填充字节属于「未承诺」那一类，它不是留给你的隐藏存储。
:::

### 2.1.1 三个量，一个步长

::: def 定义 2.1.1 · 布局三元组 size / align / offset {#def-2.1.1}

**size** 是一个该类型的值占多少字节，包含字段本身与必要填充；它同时决定同类型数组里相邻元素的**步长（stride）**。**align** 是合法存放位置的地址约束，例如 align 为 8 表示起始地址必须是 8 的倍数。**字段偏移（offset）** 是某个字段相对对象起点的距离。三者合起来才叫「布局」。
:::

按[@def-2.1.1]，只报告 size 会遗漏重要边界：size 相同的两个类型可能有不同 align；字段集合相同的两个类型，也可能因为表示方式不同而有不同偏移。数组步长、单次访问触及的字节、对象之间的空隙，都由这三个量共同决定，不是由「字段个数」决定。

完整探针（专门打印类型尺寸、对齐与字段偏移的小程序）是 `examples/layout.rs`。它调用 `size_of`、`align_of` 与 `offset_of`，没有读取填充字节，也没有通过 `transmute` 猜测对象表示。结果来自本轮 native 构建。

| 类型 | size | align | 本轮含义 |
|:--|--:|--:|:--|
| COrder | 24 | 8 | repr(C)声明顺序与填充 |
| RustOrder | 16 | 8 | 当前默认布局重排 |
| Record | 64 | 8 | 一个热u64与七个冷u64 |
| Option&lt;NonZeroU64&gt; | 8 | 8 | 标准库保证范围内的niche |
| Option&lt;u64&gt; | 16 | 8 | 本机观察，不类推所有枚举 |
| Option&lt;Handle&gt; | 8 | 8 | 透明包装的相应保证 |
| u64切片引用 | 16 | 8 | 本机宽引用观察 |
| Vec&lt;u64&gt; | 24 | 8 | 描述符，不含堆元素 |
| ByteRegion | 32 | 8 | Vec描述符加游标 |

表里最后两行属于本章的引用类型与存储组件，`ByteRegion` 的两个字段到 2.6 节再解释；这张表在本节的作用是给后面所有小节提供同一份「本轮观测」基线。

### 2.1.2 句柄与它承载的数据是两笔账

::: def 定义 2.1.2 · 描述符与元素区 {#def-2.1.2}

**描述符（descriptor）** 是那个你可以直接拿在手里的对象，例如 `Vec` 本身；**元素区**是描述符指向的、真正承载数据的存储。`Vec` 描述符可以只有 24 字节，背后的元素区却有 524288 字节。移动一个 `Vec` 只移动描述符，不复制元素区；一个引用本身的 size 也不包含它所引用数据的大小。
:::

性能分析必须把「句柄」与「承载的数据」分开统计（[@def-2.1.2]）。否则很容易把每对象的真实内存成本低估一个数量级——这是[@def-1.1.3]里「估计对象」这一项在内存维度上的对应错误。

::: ex 例 2.1.1 · 一只装满 `u64` 的 `Vec` 到底占多少内存 {#ex-2.1.1}

上表给出 `Vec<u64>` 的描述符 size 是 24 字节。本章 locality 实验的数组有 65536 个 `u64`。这只 `Vec` 占多少内存？只报告「24 字节」漏掉了什么？

::: sol 解答

描述符 24 字节；元素区是 65536 × 8 = 524288 字节。两者相加 524312 字节，描述符只占其中约两万分之一（524288 ÷ 24 ≈ 21845）。

漏掉的是「谁在为扫描付钱」这个问题：2.3 节算地址跨度时必须用 524288 这个数，而不是 24。描述符大小恒定，工作集大小随元素数增长；把两者混成一个「对象大小」，后面的缓存推理就全建在错的分母上。
:::

:::

### 2.1.3 声明顺序不是契约：COrder 与 RustOrder

默认 `repr` 允许编译器选择任何满足约束的字段安排。因此不能把一次编译看到的字段顺序写进持久化文件，不能从 Rust 字段声明顺序推导网络偏移，也不能靠裸字节转储建立稳定协议。编译器版本、目标与类型参数都可能影响布局。

本章没有启动布局随机化来生成结果。但「默认布局没有承诺不变」这一条不依赖是否启用随机化。

```rust
#[repr(C)]
struct COrder {
    tag: u8,
    value: u64,
    short: u16,
}

struct RustOrder {
    tag: u8,
    value: u64,
    short: u16,
}
```

两个类型有相同的声明字段。前者带 `repr(C)`，后者使用默认表示，实测偏移不同：

| 类型 | size | 偏移（tag, value, short） |
|:--|--:|:--|
| COrder | 24 | 0、8、16 |
| RustOrder | 16 | 10、0、8 |

COrder 尾部还需填充到整体 align 的倍数；RustOrder 在本轮选择了更紧凑的内部安排。「更小」不是默认表示永远优于 `repr(C)` 的证明，它只是当前类型与目标上的实际结果（层级判断见[@def-2.1.3]）。

::: ex 例 2.1.2 · 把填充字节数出来 {#ex-2.1.2}

只用表里的 size 与偏移，算出 COrder 和 RustOrder 各有几个填充字节。这两个数能拿来当「可用空间」吗？

::: sol 解答

COrder 的三个字段共 1 + 8 + 2 = 11 字节，size 是 24，所以填充 24 − 11 = 13 字节，分成两段：偏移 1–8 的 7 字节和偏移 18–24 的 6 字节。RustOrder 同为 11 字节字段，size 16，填充 5 字节。

不能当可用空间。填充字节不是额外用户存储：编译器可能在移动或赋值时不保留它们，它们也可能处于未初始化状态（这是[@def-2.1.1]里没有承诺的那一部分）。任何「顺便借用这几字节」的做法，都把结论建立在没有承诺的表示上。
:::

### 2.1.4 这句话属于哪一层

::: def 定义 2.1.3 · 保证层级：语言约束 / 标准库保证 / 本机观测 {#def-2.1.3}

同一句「它是 16 字节」在不同层级的强度完全不同。**语言约束**由 `repr` 等语法直接规定；**标准库保证**是文档在明确条件下承诺的性质（见 2.2 节 `Option` 的表示条目）；**本机观测**只是当前构建产物上量到的数字，换目标、换编译器版本或换类型参数都可能变。写结论时要说它属于哪一层。
:::

| 结论 | 层级（[@def-2.1.3]） | 换环境后要不要重测 |
|:--|:--|:--|
| `repr(C)` 按声明顺序排列字段 | 语言约束（本目标的对齐规则仍适用） | 需要，但方向稳定 |
| `Option<NonZeroU64>` 与载荷同 size | 标准库保证（条件见 2.2） | 文档范围内不需要 |
| `RustOrder` 是 16 字节 | 本机观测 | 必须重测 |
| `&[u64]` 是 16 字节 | 本机观测 | 必须重测 |

::: method 判定流程 · 一句布局结论的落层检查

① **找出量的是哪一个**——size、align、偏移还是步长（[@def-2.1.1]），四者不能互相代换。<br>
② **找出它的来源**——`repr` 语法？标准库文档的哪一段条件？还是一次 `size_of` 打印？<br>
③ **找出它的适用范围**——本轮构建、当前目标，还是文档承诺的整个类型集合。<br>
④ **写结论时把范围一起写**：一句「本轮观察到」胜过十句「Rust 一定会」。
:::

### 2.1.5 repr(C) 不是序列化，填充不是隐藏存储

`repr(C)` 约束的是本目标上的布局算法。它不自动统一大小端，不自动统一不同目标的整型对齐，也不保证内部 Rust 字段本身成为 C 兼容类型；外层 `repr(C)` 不会递归改变内层默认 `repr`。包含 `String`、`Vec` 或引用的结构仍然需要所有权与生命周期协议，把它直接写成文件只会保存一批无意义的地址。

稳定外部格式应使用显式字段编码：字节序、长度、版本与校验逐项定义。对象布局优化和线格式可以采用不同结构，读入时允许做一次批量转换——是否值得转换，要把转换成本与后续访问次数一起测量。本章 locality 实验不计转换成本，因此它只回答「重复访问阶段」的问题（范围见 2.4 节）。

字段语义相等也不等于表示字节相等：即使两个对象所有字段都相等，填充也未必相同（[@ex-2.1.2]）。因此不能把整个对象当字节数组做稳定哈希，不能用 `memcmp` 替代字段语义比较。性能优化不应建立在未承诺的填充值上。

::: think 思考 · 用整行原始字节做缓存键行不行 {#think-2.1.1}

某查询层想加速判重：把每个 `COrder` 的 24 个原始字节当作键，`HashMap<[u8; 24], _>` 直接查。字段全相等的两条记录，键一定相等吗？

::: sol 解答

不一定，有两层漏项。第一，[@ex-2.1.2] 算出 COrder 有 13 个填充字节，语言没有承诺它们的值：一条记录由字面量构造、另一条由反序列化再移动得到，字段可以全等而填充不同。第二，键里带着填充等于把「未承诺的表示」当成契约，编译器版本一变就可能整批未命中。

正确做法是按字段构造键，或用显式编码把字段序列化之后再哈希。这条判断和「用什么哈希函数」无关，先查的是键里有没有填充。
:::

:::

### 2.1.6 小结与常见错误

**小结。**① 布局是三元组，size 决定步长但说不出 align 与偏移（[@def-2.1.1]）；② 描述符与元素区要分开记账，否则工作集算错（[@def-2.1.2]、[@ex-2.1.1]）；③ 默认 `repr` 不承诺顺序，`repr(C)` 也只是布局算法而不是序列化协议（2.1.5）；④ 任何一句布局话都要落层：语言约束、标准库保证还是本机观测（[@def-2.1.3]）；⑤ 填充是未承诺区域，不能借用、不能比较、不能哈希（[@ex-2.1.2]）。下一节 [2.2 niche、透明包装与有效值集合](#sec-cpp-rust.1.2.2) 处理「为什么标签省得下」。

::: errata 常见错误清单（2.1 节）

## 2.2 niche、透明包装与有效值集合 {#sec-cpp-rust.1.2.2}

本节回答一个问题：**同样装一个 64 位整数，`Option<NonZeroU64>` 是 8 字节而 `Option<u64>` 是 16 字节——多出来的 8 字节是谁付的？**答案不在压缩算法里，在「这个类型有哪些位模式（这串二进制位的某种具体取值）根本不合法」里。

::: preview 先抓住一件事

能不能省掉那个标签，取决于**载荷的有效值集合是否小于全部位模式**——所谓 niche（空位），就是这些「轮不到合法值」的位模式（[@def-2.2.1]）。肯定它要给出被排除的表示，还要说清这条保证来自标准库文档还是本机观察（[@def-2.1.3]）；否定「所有 `Option` 都省标签」只需一个反例：普通 `u64` 每种位模式都是合法数值，再装 `None` 就得多一份状态。
:::

### 2.2.1 有效值集合与 niche

::: def 定义 2.2.1 · 有效值集合与 niche {#def-2.2.1}

一个类型的**有效值集合（valid values）**是它的表示中合法的那些位模式；**niche** 是被排除在外、不能作为正常载荷的那些表示。`NonZeroU64` 排除了数值 0，引用排除了空、未对齐与无效指向。枚举可以把 `None` 编码进这个被排除的位模式，从而不需要额外标签。
:::

这不是压缩算法在运行时扫描数据，而是编译器在表示层利用类型的有效值集合（[@def-2.2.1]）。普通 `u64` 的所有位模式都表示数值，若再增加 `None` 就需要表达更多逻辑状态，于是本轮 `Option<u64>` 的尺寸是 16。

不能由此断言「所有载荷 size 相同的 `Option` 都是 16」：表示策略取决于具体类型及其保证范围（层级见[@def-2.1.3]）。

::: ex 例 2.2.1 · 三行 `Option` 的对照 {#ex-2.2.1}

2.1 的探针表里 `Option<NonZeroU64>` 是 8、`Option<u64>` 是 16、`Option<Handle>` 是 8，其中 `Handle` 是 `NonZeroU64` 的透明包装。解释这三行，并指出哪一行的数字仍然只是本机打印出来的观测值。

::: sol 解答

`NonZeroU64` 天生排除 0，`None` 就借用这个不合法的位模式，所以不需要额外标签，`Option<NonZeroU64>` 与载荷同 size——这是标准库文档在明确条件下承诺的那一类（2.2.2）。`Handle` 是不带 `pub` 的单字段元组结构 `struct Handle(NonZeroU64)`，用 `#[repr(transparent)]` 标注；该 `repr` 的形式条件是「恰好一个非零尺寸字段」，与字段或结构是否公开无关（规则见参考手册 Type layout，2.9.1）。透明包装把 `NonZeroU64` 的 niche 传下去，所以 `Option<Handle>` 也是 8。`Option<u64>` 的载荷没有任何被排除的位模式，标签无处可藏，只能另开 8 字节。

第三行虽然有布局规则支撑，但表里那一列仍然是本轮 `size_of` 打印出来的观测值：换目标时它的 size 与 align 都要重新量一遍（[@def-2.1.3]）。
:::

:::

### 2.2.2 标准库保证比经验规律更重要

本轮另外核读了 `std::option` 的 Representation 段。它列出某些 `T` 的 `Option<T>` 具有与 `T` 相同的 size、align 和函数调用 ABI（应用二进制接口），包括满足相应条件的引用、`NonZero`、`NonNull` 和函数指针等；其中 `Box` 条目限定为相应的 Global 形式与 `Sized` 条件。透明包装也有明确条件。这些条件不能在转述时省略——省略之后，一条有前提的保证就退化成了经验规律（[@def-2.1.3]）。

本章只使用 `NonZeroU64` 及其透明包装，没有依赖任意自定义枚举的内部标签位置。也没有把 `None` 转成 `NonZeroU64`：那样产生的是无效值，而不是一个可以暂时不用的零（[@def-2.2.1]）。有效值限制从类型被构造出来时就要满足，不等到第一次解引用才检查。

### 2.2.3 一个适合句柄的类型边界

```rust
use std::num::NonZeroU64;

#[repr(transparent)]
struct Handle(NonZeroU64);

fn handle(raw: u64) -> Option<Handle> {
    NonZeroU64::new(raw).map(Handle)
}
```

::: def 定义 2.2.2 · 安全构造边界 safe construction site {#def-2.2.2}

**安全构造边界**指把「这个值必须满足什么」写进类型，然后只通过返回 `Option` 或 `Result` 的构造函数产生它。这样约束从对象被造出来的那一刻起就成立，而不是等到第一次解引用时才检查；调用方拿到类型，就等于拿到前提。
:::

按[@def-2.2.2]，这段代码里零输入得到 `None`，非零输入得到有效 `Handle`，没有 unsafe 构造器。调用方不需要知道 `Option` 如何利用 niche（[@def-2.2.1]），它只使用公开类型的安全行为。内部表示节省可以被编译器利用，正确性仍建立在构造器维护的有效值上。

::: ex 例 2.2.2 · 入口拦下 0，后面还要判零吗 {#ex-2.2.2}

外部传入 `raw: u64`，其中 0 表示「无效句柄」。写出经过[@def-2.2.2] 之后的下游代码形状，并说明这种设计除了正确性之外还给了优化器什么。

::: sol 解答

下游拿到的是 `Handle`，不再需要 `if raw == 0`：`let h = handle(raw).ok_or(Error::BadHandle)?;` 之后，所有函数签名里的 `Handle` 都自带「非零」这个前提。

给优化器的东西是「无效值不可表示」这条信息，它可能据此删掉重复的零检查——但这是代码生成层面的观察，要确认某处检查真的被删，仍要看该调用上下文的产物（2.2.5 的教训：没有证明就不能假定已删）。业务上如果 0 本身是合法值，就不能为了凑 niche 把它抹掉。
:::

:::

### 2.2.4 不能滥用的推论

透明包装不等于所有嵌套枚举都保证表示不变；`Option` 的保证也不会自动扩展为任意 `Result`。标准库文档只在特定条件下讨论相应优化，不能从一次 `size_of` 结果发明通用泛型定理（[@def-2.1.3]）。即使两个类型 size 相同，也不表示可以任意 `transmute`：对齐、有效值、所有权与析构责任都可能不同。

`Option<&T>` 节省标签，不代表引用可以为空。`None` 属于 `Option` 的表示；`Some` 内部的引用仍必须有效（[@def-2.2.1]）。把 `None` 按引用类型读取就是跨越了有效值边界——所谓「底层都是指针」不能消除这项义务。

::: def 定义 2.2.3 · 宽引用与元数据 {#def-2.2.3}

**宽引用（fat pointer）** 是携带额外**元数据（metadata）**的引用：切片引用同时带元素地址与长度，trait 对象引用带与动态类型相应的元数据。探针表里的 16 字节是 `&[u64]` 这个**描述符**（[@def-2.1.2]），不含 65536 个 `u64` 本体。
:::

对数组与切片还要分清两个类型：`[T]` 是动态尺寸的元素区域，`&[T]` 是引用描述符（[@def-2.2.3]）。用描述符大小估算热数据工作集会严重失真，这与[@ex-2.1.1] 是同一条错误。这些本机尺寸可以通过探针观察，但不能把内部元数据布局当成稳定的 C 结构；尤其不要把任意 `usize` 伪造成 trait 对象元数据——尺寸碰巧匹配不是有效性证明。

### 2.2.5 niche 省的是空间，不一定省判断

省掉独立标签可能降低对象尺寸，从而改善数组密度与缓存使用（这条线索接到 2.3 节）。但它不自动省去逻辑上的 `None` 判断：机器代码仍可能测试零值或其他模式。判断是否被消除，需要看调用上下文；如果上游已经证明一定是 `Some`，编译器可能删除判断，若没有证明，优化器不能凭愿望跳过它（对照[@ex-2.2.2]）。

::: think 思考 · 「既然表示一样，就直接把外部 0 塞进 `Handle`」 {#think-2.2.1}

有人嫌 `handle(raw)` 多一次分支：`Option<Handle>` 是 8 字节、`Handle` 也是 8 字节，于是写 `unsafe { std::mem::transmute::<u64, Handle>(raw) }`，理由是「反正 `None` 也就是一个 0」。这条捷径错在哪一步？

::: sol 解答

错在把「位模式相同」当成「有效值相同」。`Handle` 的内部是 `NonZeroU64`，0 根本不在它的有效值集合里（[@def-2.2.1]）；`None` 是 `Option` 的合法表示，不是 `Handle` 的合法值。这样构造出来的不是「暂时不用的零」，而是从诞生那一刻就违反约束的对象（[@def-2.2.2]），后续任何使用都是未定义行为，而且优化器有权假设它非零。

省掉那次分支的正确做法是保留构造、把判断挪到批次入口，让成本被摊薄，而不是绕过类型。
:::

:::

### 2.2.6 本节没有采集的部分，以及语义类型本身的价值

**本节没有采集 `Option` 访问的时间数据。**本章没有为 `Option` 访问单独做时序测量，因此不报告 niche 带来的纳秒加速；这里只发布真实 size 与 align 探针（2.1 的表）。把布局收益转成业务收益还需要访问模式实验（见 2.3 节热字段分析）。

另外，语义类型本身也有价值：`NonZero` 的构造边界可以把无效句柄拦在入口，类型有效值因此更窄，调用方无需到处重复检查零（[@def-2.2.2]）。这种设计同时帮助正确性与优化。但不能为了追求 niche 把有意义的零状态丢掉；如果零本来是业务合法值，应使用合适类型表达，性能表示不能反过来篡改业务定义域。

### 2.2.7 小结与常见错误

**小结。**① niche 来自载荷的有效值集合，不是运行时压缩（[@def-2.2.1]）；② 标准库文档给的是有条件的保证，条件不可省略（[@def-2.1.3]、2.2.2）；③ 用安全构造边界把无效值拦在入口（[@def-2.2.2]、[@ex-2.2.2]）；④ size 相同不等于可以 `transmute`，宽引用的 16 字节只是描述符（[@def-2.2.3]）；⑤ niche 省空间不必然省判断，本节没有采集时间（2.2.6）。下一节 [2.3 缓存、TLB 与热字段密度](#sec-cpp-rust.1.2.3) 把「小」换成「访问得到什么」。

::: errata 常见错误清单（2.2 节）

E-a **把一次 `Option` 观察推广成通用规律。**保证有类型与条件（[@def-2.1.3]）。先查文档条目原文。

E-b **认为 `None` 可以按其内部引用读取。**有效值边界必须保持（[@def-2.2.1]）。

E-c **用 `transmute` 绕过构造器。**产生的是无效值，不是「暂时不用的零」（[@think-2.2.1]）。

E-d **转述时省略 `Box` 条目的 Global 与 `Sized` 前提。**丢条件就等于换命题（2.2.2）。

E-e **以为省掉标签就省掉了分支。**判断是否被删要看调用上下文的产物（2.2.5）。

E-f **拿 `&[T]` 的 16 字节估算工作集。**描述符与元素区是两笔账（[@def-2.2.3]、[@def-2.1.2]）。

**第 1 题 · 记忆**　给出 niche 的定义，并说出探针表里哪三行分别对应「有 niche」「无 niche」「随包装传递」。

::: sol 第 1 题答案
niche 是载荷类型中不能作为正常表示的位模式（[@def-2.2.1]）。`Option<NonZeroU64>`（8 字节）有；`Option<u64>`（16 字节）没有；`Option<Handle>`（8 字节）通过透明包装传递。

**第 2 题 · 辨析**　「`Option<NonZeroU64>` 和 `NonZeroU64` 一样大，所以 `Option` 一定没有开销。」哪里过头了？

::: sol 第 2 题答案
空间上确实没有额外标签，但逻辑判断不一定被消除（2.2.5）；而且结论只在文档列出的类型与条件下成立（[@def-2.1.3]）。时间开销本节没有采集，所以不能说「没有开销」。
:::

**第 3 题 · 应用**　外部 API 给你一个 `u64` 句柄，0 保留给「无」。写出符合[@def-2.2.2] 的入口，并说明失败怎么表达。

::: sol 第 3 题答案
`fn handle(raw: u64) -> Option<Handle>`，用 `NonZeroU64::new(raw).map(Handle)`（2.2.3）。失败用 `Option` 或 `Result` 返回给调用方决定；不要在类型内部塞 0，也不要 `transmute`（[@think-2.2.1]）。
:::

**第 4 题 · 迁移**　同事说「我们的枚举也只有一个非零指针变体，所以 `Option<MyEnum>` 一定省标签」。你要查哪两件事？

::: sol 第 4 题答案
① 文档是否把这一类类型列入保证范围，还是只是本机碰巧（[@def-2.1.3]）；② 该类型自身的有效值集合是否真的留出了可用作 `None` 的位模式（[@def-2.2.1]）。两者都不满足时，只能记录为一次观测，不能写进接口承诺。
:::

## 2.3 缓存、TLB 与热字段密度 {#sec-cpp-rust.1.2.3}

本节回答一个问题：**步长从 64 字节缩到 8 字节，这笔账能算到哪一步——能换算成「少了 8 倍 cache miss」吗？**先分清哪些是布局事实（可以直接算），哪些是需要另外采集的机器事件。

::: preview 先抓住一件事

地址跨度是**可算的布局事实**，搬运字节数、miss 次数和 TLB 事件都是**需要单独采集的观测量**（[@def-2.3.2]）。要肯定一条「这是缓存收益」，你得拿出对应事件或层级容量的证据；否定它只需要指出：本实验重复扫描同一份热数组，而且一次性能计数事件都没有采集。
:::

### 2.3.1 逻辑读取量与实际搬运量

CPU 执行一个字段读取，不意味着内存系统只搬运该字段的字节。缓存通常以更大的粒度处理相邻数据，预取（硬件提前把相邻数据也取进来）、缓存层次与共享状态都会影响实际流量。本机 `sysctl` 报告的缓存行（cacheline）为 128 字节；这不是所有架构的统一值，本章不使用「缓存行一定 64 字节」的假设。

::: def 定义 2.3.1 · 地址跨度与逻辑有效负载 {#def-2.3.1}

一次扫描的**地址跨度（address span）**是它触及的首末地址之间的距离，由元素数乘以步长（[@def-2.1.1]）决定。**逻辑有效负载**是真正被使用的字节数，由被读字段的大小决定。`Record` 的步长是 64 字节、热字段只有 8 字节，所以同样元素数下跨度是有效负载的 8 倍——这是布局事实。至于这 8 倍里有多少真的从内存搬进来，取决于缓存层次，不是布局能单独回答的。
:::

`Record` 尺寸为 64 字节，其中只有第一个 `u64` 参与求和：热字段逻辑有效负载为 8 字节，其余 56 字节在该工作核中不使用。数组步长仍为 64 字节，因此同样元素数下 AoS 覆盖的地址跨度较大；热列投影只需要连续的 `u64`，它的跨度与有效负载相等。

::: ex 例 2.3.1 · 把跨度算清楚，然后停手 {#ex-2.3.1}

65536 个逻辑元素。按[@def-2.3.1] 分别算出 AoS 与热列的地址跨度、两者的比值、双方真正使用的字节，以及热字段密度。然后回答：能不能据此说「AoS 多带了 7 倍内存流量」？

::: sol 解答

AoS：$65536 \times 64 = 4194304$ 字节，两个因子分别来自 `bench/foundations-lab/src/lib.rs:5` 的 `N = 65_536` 与 `results/native-01/layout.txt` 里 `Record` 的 size 64，这是由布局算出来的，归档 CSV 本身没有这一列。热列：65536 × 8 = 524288 字节。比值 8，是布局事实。双方真正使用的字节相同，都是 8 × 65536 = 524288 字节；AoS 只是把它们摊在 4 MiB 的地址上。热字段密度 = 8 ÷ 64 = 12.5%。

不能。「多带 7 倍流量」把跨度当成了搬运字节：cacheline 是 128 字节，理想对齐下每行可容两个 `Record`，但 `Vec` 只保证 `Record` 所需的 8 字节对齐，不保证分配起点恰好是 128 的倍数，跨行边界数量因此不确定；更重要的是本章重复使用同一份热数组，不少访问可能命中某层缓存。所以只能说跨度差 8 倍——把跨度改名成「外部内存总读取字节」就跨过了证据边界（[@def-2.3.2]）。
:::

:::

### 2.3.2 哪些量能报，哪些不能报

::: def 定义 2.3.2 · 布局事实、机制证据与性能结果 {#def-2.3.2}

一次布局研究里有三类量。**布局事实**：size、偏移、步长、跨度，可以算出来。**机制证据**：cache miss、TLB 事件、指令退休数，要靠性能监控单元（PMU）之类的事件采集。**性能结果**：批均值耗时，是墙钟计时得到的（口径见[@def-1.2.2]）。2.3 节里本章只有第一类和第三类，因此结论只能写成「两者相关」，不能写成「第三类由第二类唯一造成」。
:::

可以计算覆盖的地址跨度，不能把跨度直接改名为外部内存总读取字节。本轮 AoS 元素区为 4194304 字节、热列为 524288 字节，这个 8 倍跨度差异是布局事实；最终 0.519 对 0.059 的耗时差异则是实测（表见 2.5 节）。两者相关，但不构成唯一因果证明。

| 想说的话 | 需要的证据 | 本节状态 |
|:--|:--|:--|
| AoS 地址跨度是热列的 8 倍 | 布局事实（[@ex-2.3.1]） | 已给出，可直接算 |
| 热列单位耗时低于 AoS | 计时（2.5 节表） | 已采集 |
| 差距中有多少来自 miss | 未采集 | 只能写「本节没有采集」 |
| TLB 参与了多少 | 未采集 | 只能作为机制列出 |
| 是否存在伪共享 | 未采集（单线程读） | 不下结论 |
| 换算成 DRAM 带宽 | 需要搬运字节模型 | 不发布 |

::: method 判定流程 · 能不能把一次布局差距说成「缓存收益」

① **先报布局事实**：步长、跨度、密度（[@def-2.3.1]、[@ex-2.3.1]），这部分不需要任何测量设备。<br>
② **再查有没有第二类证据**：本节没有采集 cache miss、TLB 事件或任何 PMU 计数（[@def-2.3.2]），所以不能给 miss 次数，也不能报带宽。<br>
③ **检查分母是否唯一**：同一时间还伴随向量化与归约形态变化，见 2.4 的代码生成表——多因并存时不要用单一机制命名全部差距。<br>
④ **写结论句式**：「跨度差 8 倍与耗时差 8.74 倍方向一致」，把机制留在候选解释里，等下一次采集再升级。
:::

### 2.3.3 TLB 与页面：只作为机制列出

更大的地址跨度可能涉及更多页面。TLB（转换后备缓冲器）负责缓存地址转换相关信息，页面大小、TLB 层次与替换行为依赖平台。**本章没有采集 TLB 事件**，也没有用平台 API 建立大页实验，因此这里只把 TLB 作为需要考虑的机制，不能把本轮 AoS 较慢全部归因于 TLB。

机制这一侧不是空白，可以先把「谁会影响 TLB 命中率」说清楚。rCore 教程在讲 RISC-V SV39 三级页表时给出了一条完整因果链：地址转换以页为单位，虚拟页号被分成三级索引，逐级查页表节点才能拿到物理页号；**大页**之所以有用，是因为它一方面省掉大量页表项的读写、另一方面减少页表树的节点数，更关键的是**让一条 TLB 表项覆盖更大的地址范围**，从而减轻 TLB 压力、提高命中率，最终体现在访存指令的执行速度与整体 IPC 上；代价是内核必须支持三种不同大小的连续物理区域分配（`chapter4/3sv39-implementation-1.html`）。

这条链对本节的用处是**限定措辞**，不是给出结论：跨度更大的扫描之所以可能更慢，候选机制至少包括「命中的页面数更多 → 页表遍历更深 → TLB 条目更紧张」。但要把任何一环变成数字，都需要本章没有采集的那一类证据（PMU 的 TLB 事件、或平台 API 的大页对照）。所以本节仍然只写「方向一致」，把大页留给下一次采集当假设去检验。

如果要检验 TLB 假设，需要控制每页访问模式，还应控制工作集、步长、预取和总有效工作量。随机跳转与顺序扫描的实验契约不同（[@def-1.1.3]），不应混在一张「缓存速度表」中。没有采集的事件不能由墙钟时间倒算出来。

::: think 思考 · 4 MiB 缩到 512 KiB，就能说「全进 L1」吗 {#think-2.3.1}

热列工作集 524288 字节（约 512 KiB），比 AoS 的 4194304 字节小得多。有人据此写「热列完全落在 L1/L2 里，所以快 8 倍」。这条推理缺了哪两个数？

::: sol 解答

缺两个本节没有的数：① 本机的各级缓存**容量**——归档里只有 `sysctl` 报告的缓存行大小 128 字节，没有采集 L1/L2 容量与相联度；② 实际命中情况——没有采集任何 miss 事件（[@def-2.3.2]）。512 KiB 会不会超出某一层、重复扫描下哪一层驻留，都只是推测。

能说的只到这里：跨度更小，与更友好的缓存驻留**相容**。要把它写成「全进 L2」，需要按[@def-1.1.3] 另做一份带事件采集的实验。
:::

:::

### 2.3.4 访问模式决定布局价值

只读一个字段时，热列投影通常有更高密度（[@def-2.3.1]）；若每次都要读取全部字段，AoS 可能更方便；如果对象之间存在复杂依赖，列式拆分还可能增加索引协调；若多个线程分别写不同列，布局还会影响共享争用。因此布局选择取决于具体访问集合与数据生命期的匹配。

连续扫描容易形成可预测地址序列，硬件可能重叠多个读取并提前取数；随机索引会限制这种机会。同样的对象尺寸，在两种模式下成本可能完全不同。**本章 locality 只做顺序扫描**，不外推到哈希表、树或图遍历——这些结构还需要单独控制指针追逐和依赖链。

读密集工作与写密集工作有不同的系统代价：写入可能涉及所有权转移和缓存一致性协议；不同线程改写同一缓存行的不同对象也可能互相干扰，这通常称为伪共享（false sharing）。避免伪共享不能只看类型字段是否不同，还要看实际地址与目标缓存行大小。**本章是单线程读实验，没有测量伪共享**，并发章节会用专门协议研究共享写入。

### 2.3.5 工作集的生命周期与一致性协议

一次构造、多次扫描，适合把转换成本摊薄；一次构造、只扫描一次，则必须把构造成本算入同一个分母（[@ex-1.5.1] 的分母教训在这里同样适用）。热列更新也需要维持与原对象的一致性：若数据经常修改，投影可能产生同步负担；如果投影过期而仍被使用，结果可能语义错误。

因此布局优化首先需要一份一致性协议。没有这份协议的加速不应进入业务候选。这条约束在 2.4 节的实验范围里会再出现一次：本实验压根没有测量转换与更新（[@def-2.4.1]）。

### 2.3.6 算力与带宽不能只看单位推断

很小的 ns/元素可以来自向量化、缓存命中与多条累加链，它不是测出内存带宽的直接证据（口径见[@def-1.2.2]）。若要报告带宽，必须定义搬运字节的模型：读取有效字段字节与触及地址跨度是两种不同分母（[@def-2.3.1]），外部内存流量还可能与两者都不同。本章坚持使用 ns/逻辑元素，没有发布未经计数验证的 DRAM 带宽。

### 2.3.7 小结与常见错误

**小结。**① 跨度、密度是布局事实，可以直接算（[@def-2.3.1]、[@ex-2.3.1]）；② 搬运字节与 miss 数是第二类证据，本节没有采集（[@def-2.3.2]）；③ TLB、伪共享在本书只作为机制列出，各有未采集的原因（2.3.3、2.3.4）；④ 布局价值取决于访问集合与生命期，顺序扫描不外推随机访问（2.3.4）；⑤ 带宽要先有搬运模型才谈得上，一致性协议要先于加速结论（2.3.5、2.3.6）。下一节 [2.4 AoS、SoA 与编译器的访问证明](#sec-cpp-rust.1.2.4) 说明同一时间差距里还有第三种因素：代码形态。

::: errata 常见错误清单（2.3 节）

E-a **把地址跨度当外部流量。**跨度可算，搬运字节要看层次（[@ex-2.3.1]）。

E-b **用「元素数 ÷ 每行元素数」宣称 miss 数。**重复扫描、起点又不保证 128 字节对齐，两个前提都不成立（[@def-2.3.2]）。

E-c **写死 cacheline = 64 字节。**本机查询为 128，且它不是跨架构常量（2.3.1）。先查目标机器的报告值再写。

E-d **把 AoS 较慢归因于 TLB。**没有采集 TLB 事件（2.3.3、[@think-2.3.1]）。

E-e **用单线程读实验谈伪共享。**写与共享争用没有被测量（2.3.4）。

E-f **把 ns/元素的倒数报成带宽。**分母模型没定义（2.3.6）。

:::

## 2.4 AoS、SoA与编译器的访问证明 {#sec-cpp-rust.1.2.4}

本节回答一个问题：**这段代码生成证据到底证明了什么——是「SoA 更快」，还是「两种写法让编译器走了不同的路」？**同一份逻辑工作里，数据跨度和执行形态会一起变，归因必须逐条对应产物。

::: preview 先抓住一件事

机制归因要一条对一条：AoS 的本机产物是标量加载加 64 字节步长，SoA 的产物是连续向量加载加多条累加链（2.4.3 的表）。两者与「跨度更小」这件事**相容，但不构成唯一因果**（[@def-2.3.2]）。要肯定「这就是收益来源」，需要第二类证据；要否定「SoA 永远更快」，只要指出本实验的 SoA 其实只是热列投影（[@def-2.4.1]）。
:::

### 2.4.1 本章 SoA 的准确范围

::: def 定义 2.4.1 · 热列投影 hot-column projection {#def-2.4.1}

实验中的 `soa` 只保存热字段那一列，没有保存七组冷字段列，因此准确名称是**完整 SoA（Structure of Arrays，数组结构）中的热列投影**。AoS（Array of Structs，结构数组）与热列两个表示都在计时前创建、在同一进程中同时存在，计时只是选择扫描哪一个。所以本实验既没有测量「把现有 AoS 转换成完整 SoA」的成本，也没有比较两种完整数据模型的总内存峰值。
:::

这个限制不削弱扫描问题本身的答案，它限制的是另一个判断：能否直接宣布生产数据结构应整体替换。要做那项决定，还要测构建、更新、删除与索引维护（[@def-2.3.2] 的第二类证据同样缺位，一致性要求见 2.3.5）。本章把这些后续问题单独列出来，不混进结果表。

### 2.4.2 两个实际数据通路

```rust
#[repr(C)]
#[derive(Clone, Copy)]
pub struct Record {
    pub hot: u64,
    pub cold: [u64; 7],
}

#[inline(never)]
pub fn sum_aos(input: &[Record]) -> u64 {
    input.iter().fold(0u64, |sum, row| {
        sum.wrapping_add(row.hot)
    })
}

#[inline(never)]
pub fn sum_soa(input: &[u64]) -> u64 {
    input.iter().copied().fold(0u64, u64::wrapping_add)
}
```

`Record` 使用 `repr(C)` 是为了让热字段位置易于复核（偏移与 size 见 2.1 的探针表），不是因为此实验需要调用 C。冷字段初始化为 11，保持对象全部合法初始化；被测核只读取 `hot`，没有从未初始化的冷字段构造虚假的低成本对象。

### 2.4.3 本机代码生成：差异不止一个来源

AoS 主体保留每 64 字节一个 `u64` 的读取，循环一次展开多个这样的读取；SoA 主体使用连续向量加载与多条向量累加链。这表明性能差异不只有数据跨度因素（[@def-2.3.1]），编译器选择的执行形态也不同。因此本章不把全部差距命名为「缓存惩罚」。

| 入口/边界 | 实际产物 | 能支持的机制判断 |
|:--|:--|:--|
| sum_aos | 标量加载，64字节步长 | 热字段读取稀疏 |
| sum_soa | q寄存器成对加载与向量加 | 连续列形成批量归约 |
| sum_iter | LLVM符号别名到sum_soa | 相同核被合并 |
| 切片参数 | LLVM readonly与noalias属性 | 当前后端使用了引用约束 |
| Record ABI | 仅通过切片访问 | 不建立跨语言按值传递保证 |

本节的 `noalias` 是当前生成代码的属性，不是本章对所有 Rust 别名规则的完整形式定义，尤其不能用它为不合法的重叠引用背书；合法输入的证明仍来自 Rust 借用与接口契约。符号别名与指令选择都属于本机观测这一层（[@def-2.1.3]），对照[@def-1.8.1] 的证据链读法。

SoA 的关键循环中可见以下加载与累加（省略循环控制与尾部处理）：

```asm
ldp q4, q5, [x8, #-32]
ldp q6, q7, [x8], #64
add.2d v0, v4, v0
add.2d v1, v5, v1
add.2d v2, v6, v2
add.2d v3, v7, v3
```

AoS 可见不同步长：

```asm
ldur x15, [x13, #-128]
ldur x16, [x13, #-64]
ldr x17, [x13]
ldr x15, [x13, #64]
add x13, x13, #256
```

::: ex 例 2.4.1 · 从六行汇编里数出「每个元素前进多少字节」 {#ex-2.4.1}

只用上面两段片段：SoA 一轮处理多少个逻辑元素、基址前进多少字节？AoS 呢？两者之比是多少，与[@ex-2.3.1] 的跨度比一致吗？

::: sol 解答

SoA：`ldp q4, q5, [x8, #-32]` 取回 2 个 16 字节寄存器（CPU 内部最快取用的小存储格），`ldp q6, q7, [x8], #64` 再取 2 个并把基址推进 64，合计一轮消费 64 连续字节 = 8 个 `u64`；四条 `add.2d` 正好累加 4 × 2 = 8 条 64 位通道。每元素前进 8 字节。

AoS：四条标量装载（`ldur`／`ldr`，每次 8 字节）位于 −128、−64、0、+64，即四个相隔 64 字节的热字段，`add x13, x13, #256` 推进 256 字节。每元素前进 64 字节。

比值 64 ÷ 8 = 8，与[@ex-2.3.1] 算出的地址跨度比一致。但要看清两件事同时变了：AoS 每元素一次标量加载，SoA 一轮 8 元素批量加载并向量累加——执行形态也换了。这是「不能把差距只命名为缓存惩罚」的直接证据。片段只用于定位差异：完整符号才包含入口、尾部与返回，不能由六行片段计算完整调用周期，也不应把当前指令选择推广为所有 aarch64 后端行为。
:::

:::

### 2.4.4 改成读取全部字段会怎样

那将是另一项实验。应让两种表示读取同样的逻辑字段：SoA 需要相应的多个列，输出校验也要覆盖全部字段。不能用当前只读 `hot` 的结果预言它一定更快。同样，若只访问少量随机对象，AoS 的局部聚合可能更合适（访问模式的讨论见 2.3.4）。布局没有脱离访问集合的绝对优胜者。

::: think 思考 · 把「热列快 8 倍」写成重构决议 {#think-2.4.1}

技术评审上有人贴出 2.5 节的结果表，结论是「本服务的数据层应整体改为列式存储」。按本节的定义，这份提案漏了哪些前提？

::: sol 解答

至少四条。① 实验对象是热列投影，不是完整 SoA（[@def-2.4.1]），七组冷字段的列、索引与更新成本都没建模；② 两个表示在计时前都已存在，构建与转换成本不在区间内（2.4.1）；③ 访问集合是顺序扫描单一字段，业务里的全字段处理与随机查询是另外的实验（2.4.4、[@def-1.1.3]）；④ 一致性协议还没有设计，投影过期会给出错误结果（2.3.5）。

正确的写法是把这条结果当作**候选场景**的证据：反复顺序读取少数字段；其余留给后续实验逐条补测。
:::

:::

### 2.4.5 小结与常见错误

**小结。**① 本章的 SoA 是热列投影，转换与峰值内存不在测量范围内（[@def-2.4.1]）；② 代码生成表里的每一行只支持它自己那句话（2.4.3）；③ 汇编片段数出来的是步长与执行形态两件事同时变化（[@ex-2.4.1]）；④ 全字段读取与随机访问是另外的实验契约（[@def-1.1.3]）；⑤ `noalias`、符号别名都是当前产物的属性，不是承诺（[@def-2.1.3]）。下一节 [2.5 benchmark 一：热列扫描的实测边界](#sec-cpp-rust.1.2.5) 把这里攒下的三类证据放到同一张结果表上。

::: errata 常见错误清单（2.4 节）

E-a **把热列投影叫「SoA 实验」。**冷列、索引与转换都不在其中（[@def-2.4.1]）。

E-b **用生成代码证明缓存是原因。**代码形态也变了，且没有事件采集（[@ex-2.4.1]、[@def-2.3.2]）。

E-c **拿 `noalias` 当别名规则的完整定义。**它是后端属性，不是接口证明（2.4.3）。

E-d **由六行片段推算调用周期。**片段省略了控制与尾部（[@ex-2.4.1]）。先查归档里的完整 `.s` 符号。

E-e **用只读 `hot` 的结果预测全字段场景。**访问集合不同，实验契约也就不同（[@def-1.1.3]）。

E-f **把本机指令选择当成 aarch64 通用行为。**落层判断出错（[@def-2.1.3]）。

:::

## 2.5 benchmark一：热列扫描的实测边界 {#sec-cpp-rust.1.2.5}

本节回答一个问题：**0.519 对 0.059 这条实测差距，能撑到哪一句话？**前面三节攒下布局事实与代码形态证据，这一节把它们和计时放在一起，并划出这条结论走不出多远的边界。

::: preview 先抓住一件事

一个可用的 benchmark 结论必须同时带着四件事：**被测对象、计时边界、单位、样本协议**（[@def-1.1.3]）。本节的边界写得很具体——两种表示在计时外创建（[@def-2.5.1]）、单位是 ns/逻辑元素、每 case 21 个批均值。要肯定「热列更便宜」，这四件都要对上；要否定「所以业务应改成列式」，只需要一条被破坏的规则：转换与更新成本根本不在这条边界里（[@def-2.4.1]）。
:::

### 2.5.1 完整入口与夹具参数

以下是 `src/bin/locality.rs` 的完整代码。公共核与夹具位于 `src/lib.rs`。输入的两个表示在计时外创建，校验值只依赖热字段。

```rust
use foundations_lab::{Case, N, Record, data, run, sum_aos, sum_soa};
use std::hint::black_box;

fn main() {
    let hot = data(N);
    let aos: Vec<_> = hot.iter().map(|&hot| Record {
        hot,
        cold: [11; 7],
    }).collect();
    let expected = hot.iter().fold(0u64, |a, &b| a.wrapping_add(b));
    let mut cases = [
        Case {
            name: "aos",
            work: Box::new(|| sum_aos(black_box(&aos))),
            expected,
        },
        Case {
            name: "soa",
            work: Box::new(|| sum_soa(black_box(&hot))),
            expected,
        },
    ];
    run(&mut cases, 128, N);
}
```

::: def 定义 2.5.1 · 计时外构造 out-of-timing setup {#def-2.5.1}

**计时外构造**指被扫描的数据在正式计时区间开始之前就全部建好：这里 `hot` 与 `aos` 两个表示都由 `main` 在进入 `run` 之前创建，夹具只选择扫描哪一个。好处是两次扫描面对同一份工作集；代价是构建与转换成本被移出边界（对照 2.4 的[@def-2.4.1]），所以本节的数字只属于「重复访问阶段」。
:::

按[@def-2.5.1]，每次调用处理 65536 个逻辑元素，每批重复 128 次；每 case 预热至少 500 ms，正式 21 轮中轮转先后位置（协议见[@def-1.4.1]）。夹具保存每次调用的输出，批后逐个比较参考值（[@def-1.3.1]）；打印与统计不在正式计时区间。

### 2.5.2 本轮结果

来源为 `results/native-01/locality.csv`，单位为 ns/逻辑元素，统计口径按[@def-1.5.2]。

| case | mean | N-1 sd | 批p50 | 批p99 |
|:--|--:|--:|--:|--:|
| aos | 0.519143207 | 0.005283686 | 0.519196153 | 0.529403567 |
| soa热列 | 0.059380878 | 0.000798904 | 0.059301615 | 0.060682416 |

热列减 AoS 的配对均值为 −0.459762329（算法见[@def-1.4.2]）。固定种子 bootstrap 区间为 [−0.461856757, −0.457715438]（[@def-1.6.2]）。区间只描述当前运行内的重采样结果，不覆盖跨机器和跨工具链变化。批 p99 仍是 21 个批均值中的最大值，不是一次对象访问的尾延迟（[@def-1.5.2]）。

::: ex 例 2.5.1 · 把单位换算回真实时长，检查量级 {#ex-2.5.1}

一批 = 128 次调用 × 65536 个元素。用表里的均值算出 aos 与 soa 各一批多长、整个正式阶段 21 批多长、以及差值区间有多宽。这类换算有什么用处？

::: sol 解答

每批元素数 128 × 65536 = 8388608。aos 一批 ≈ 8388608 × 0.519143207 ns ≈ 4 354 889 ns，即约 4.35 ms；soa 一批 ≈ 8388608 × 0.059380878 ≈ 498 123 ns，即约 0.50 ms。21 批合计分别约 91.5 ms 与 10.5 ms。差值 −0.459762329 ns/元素换回每批约 −3.857 ms，与两者相减一致；区间宽度 0.004141319 ns/元素，约 |均值| 的 0.9%。

用处有三个。第一，量级自检：如果换算出来是「一批 0.004 ms」，说明单位或分母写错了（对照 1.8.7 的量纲检查思路）。第二，它暴露批均值的真实含义——0.519 是 4.35 ms 摊到 838 万个元素上的结果，不是任何一次访问的耗时。第三，它能防止把 sd 读成「亚纳秒级的稳定」：aos 的 sd 0.005283686 摊到每批就是约 44 μs 的批间波动。
:::

:::

### 2.5.3 这条数字支持什么，不支持什么

可以保留的结论有三项，它们互相一致：在固定热数组顺序扫描下，热列单位成本较低（计时）；AoS 的读取跨度更大（布局事实，[@ex-2.3.1]）；本机 SoA 生成了连续向量归约路径（代码形态，2.4.3）。这三项支持把「只读少数字段」作为布局重构的候选场景，但还没有测出完整业务转换收益（[@def-2.4.1]）。

不能保留的结论同样要写下来：不能宣称所有 AoS 一定比 SoA 慢；不能宣称本轮精确测到了 L1、L2 或 TLB miss 差异（[@def-2.3.2]）；不能宣称扫描结果可以直接预测随机查询（2.3.4）；不能宣称冷数据永远不应保存在对象中；也不能把热列数组的 524288 字节当成整个业务状态大小——完整业务状态还需要其他字段与索引（[@def-2.1.2]）。

::: ex 例 2.5.2 · 把三态门禁套在这条差距上 {#ex-2.5.2}

热列减 AoS 的配对差值是 −0.459762329，区间 [−0.461856757, −0.457715438]，整体远离零。按[@def-1.7.2] 判定这个变更能不能发布。

::: sol 解答

判不了。[@def-1.7.2] 的三态需要三个输入：配对差值区间、回归方向、以及**在采集之前写下的预算 B**。这里前两个有：回归量取「候选（热列）− 基线（AoS）」为负，即变快，区间不跨零，方向在本轮运行内可定。第三个没有：**本章没有为 locality 实验定义业务预算 B**，因为 65536 个元素的顺序扫描不对应任何一条真实的请求预算（[@def-1.7.1]）。

所以合格的句子止于「在本次固定的热数组与 native 构建下，热列的批均值低于 AoS，配对差值区间不跨零」；一旦要写「可以发布」或「应重构」，就必须先在自己的服务上预先写下 B，并补上转换与一致性成本（2.3.5、[@def-2.4.1]）。

:::

:::

::: method 判定流程 · 把一个布局差距写成能用的结论

① **报对象与边界**：扫的是哪个数组、构造是否在计时外（[@def-2.5.1]）、单位是什么（[@def-1.2.2]）。<br>
② **报三类证据各自的位置**：布局事实（[@def-2.3.1]）、代码形态（2.4.3）、计时结果（2.5.2），谁也不替代谁。<br>
③ **报不确定性的覆盖范围**：区间只含本次运行的抽样波动（[@def-1.6.2]），不含跨机器与跨版本。<br>
④ **补上缺的那一类才算决策**：要发布就预先写预算 B（[@def-1.7.1]）；要推广到别的访问模式就重做契约（[@def-1.1.3]）。
:::

### 2.5.4 一个安全性能回退案例与它的回归测试

::: def 定义 2.5.2 · 安全性能回退 safe performance regression {#def-2.5.2}

**安全性能回退**指代码完全符合语言规则、没有任何未定义行为，却因为它所选择的**数据表示**而使某条通路退化。与 DCE 那类「工作根本没执行」的错误不同（[@def-1.1.1]），本例每一个字节都被合法读写，只是被摊在了更大的地址跨度上（[@def-2.3.1]）。
:::

按[@def-2.5.2]，把热字段与大量冷字段绑在一起不会违反 Rust 内存安全，它却可能使热扫描退化。本实验用安全 Rust 实际重现了这个问题：不存在故意越界或数据竞争。回归的对象是当前访问通路，不是类型定义本身的道德好坏（访问集合见 2.3.4）。修复候选是热列投影（[@def-2.4.1]）、热冷拆分或改变访问批量，每一种修复都需要重新检查一致性成本（2.3.5）。

`sums_and_representations_agree` 对多个长度建立两种表示，每种表示都从相同的 `hot` 值生成，它要求 `sum_aos` 与 `sum_soa` 相等，还覆盖非向量整块长度。这避免把尾部遗漏误当作性能收益——与[@ex-1.5.1] 的教训同源：期望值必须独立于被测实现，两种实现必须处理同一份工作。若以后修改 `Record` 字段，测试应继续保持逻辑输入一致；不能通过缩短某一分支实际处理的数据量获得漂亮数字（[@def-1.3.1]）。

### 2.5.5 采样报告能支持哪一句话

独立 `sample-locality.txt` 中同时出现 `sum_aos` 与 `sum_soa`：它们在预热阶段分别占用约固定墙钟时间，所以采样数量接近不表示两种实现单次成本接近。预热策略本来就按时间而非调用数运行，这是采样协议与计时协议必须一起解释的例子（对照[@def-1.8.1] 的证据链读法）。本章不把该报告换算成每元素 CPU 周期——那需要没有采集的事件计数（[@def-2.3.2]）。

::: think 思考 · 「两个符号采样次数接近，所以单次成本接近」 {#think-2.5.1}

有人拿 `sample-locality.txt` 里 `sum_aos` 与 `sum_soa` 的采样计数几乎一样，写成「热列并没有真的更快，采样是中立证据」。这个推理绕过了哪个前提？

::: sol 解答

绕过了「采样覆盖的是哪段时间」这个前提。预热按固定墙钟时间运行，两个 case 各自在被采样的时间里都在反复执行自己的工作核；AoS 一轮 4.35 ms、热列一轮 0.50 ms（[@ex-2.5.1]），同样时长里 AoS 完成的调用次数更少，但采样统计的是「这个符号在跑」的次数而不是每次的字节数。所以采样接近既不支持「成本接近」，也不支持「热列没更快」；它能支持的只有「两个工作核确实都在运行」这一句（[@def-1.3.1]）。

要看差距仍然只能看计时表（2.5.2）；要区分机制就得补事件采集，本节没有做。

### 2.5.6 怎样继续做确认实验

## 2.6 分配成本、容量与安全字节区域 {#sec-cpp-rust.1.2.6}

本节回答一个问题：**不写一个 `unsafe`，区域复用要先把哪几件事放进接口？**答案是三件：容量失败的事务性语义、`reset` 的借用约束、以及「复用不等于擦除」这条诚实声明。

::: preview 先抓住一件事

一个安全复用组件的能力边界，写在它的**签名**里而不是注释里。`take(&mut self, len: usize) -> Option<&mut [u8]>` 这一个签名同时给出三件事：返回 `Option` 表示容量不足是可恢复的正常结果；借用整个 `self` 为可变，表示同一时刻只能有一个存活切片；生命周期绑定 `self`，表示旧切片没结束就调不了 `reset`（[@def-2.6.2]）。要肯定「这个组件安全」，逐项核对这三条即可；要否定「它相当于通用 arena」，只需要指出它不构造任意 `T`、也不提供任意对齐请求。
:::

### 2.6.1 分配器不是一个固定延迟函数

一次 `Vec` 创建可能经过不同大小类与缓存路径；系统分配器可能复用已释放块；较大请求可能走不同的后端；页面首次触及也可能在初始化阶段才体现；线程局部缓存、跨线程释放与碎片都会影响成本。因此「`malloc` 固定需要多少纳秒」不是通用事实，本章只比较具体生命周期。

::: def 定义 2.6.1 · 生命周期复用 lifecycle reuse {#def-2.6.1}

**生命周期复用**指用一次长期存在的存储，替代许多次「申请—使用—归还」。这里一条路径反复创建 64 字节 `Vec`、填充、观察、销毁；另一条路径复用预先初始化的字节区域。两者不只是分配器算法不同：它们改变了**分配频率**与**存储生命期**这两个被研究的量（[@def-1.1.3]）。所以比较前必须声明区域的初次构造不进入每批计时（[@def-2.5.1] 同一条边界规则）。
:::

按[@def-2.6.1]，这条差别必须写在性能表旁边，否则读者会把「换了生命期」误读成「分配器更快」。

### 2.6.2 本章组件不是通用 arena

::: def 定义 2.6.2 · 有限安全组件 bounded safe component {#def-2.6.2}

**有限安全组件**指故意把能力范围缩到能完整证明的那一块，并在接口上写清楚它不提供什么。本章的 `ByteRegion` 存储一个已初始化 `Vec<u8>`，`take` 只返回该 `Vec` 内部的可变字节切片：它不构造任意 `T`、不提供任意 align 请求、不实现 `GlobalAlloc`，也不允许调用方同时保留多个 `take` 结果后继续分配——因为 `take` 借用整个 `self` 为可变，前一个切片的有效使用会阻止下一次 `take`。
:::

| 通用 arena 通常需要 | 本章 `ByteRegion` |
|:--|:--|
| 构造任意 `T` 并返回 `&mut T` | 只给 `&mut [u8]`，无类型化放置 |
| 按请求处理对齐 | 只继承 `u8` 的分配对齐（见 2.8） |
| 多个对象长期共存 | 同一时刻只有一个存活切片 |
| 自定义 `GlobalAlloc` 路由 | 不实现，也不包装 |
| 逐项析构已放置的 `T` | 字节没有 `Drop`，`reset` 只动游标 |

这种限制使证明简单：它适合逐个填充并消费短暂字节块的通路，不适合需要长期保存多个对象引用的图结构（对应[@def-2.6.2] 的第三条禁令）。如果业务需要后者，应选择更强的已有容器或补全专门证明；不要把一个安全而有限的组件宣传成通用分配器替代品（这条与 2.8 的决策表相连）。

### 2.6.3 完整组件：一次事务性的游标推进

```rust
pub struct ByteRegion {
    storage: Vec<u8>,
    used: usize,
}

impl ByteRegion {
    pub fn new(capacity: usize) -> Self {
        Self {
            storage: vec![0; capacity],
            used: 0,
        }
    }

    pub fn take(&mut self, len: usize) -> Option<&mut [u8]> {
        let end = self.used.checked_add(len)?;
        let result = self.storage.get_mut(self.used..end)?;
        self.used = end;
        Some(result)
    }

    pub fn reset(&mut self) {
        self.used = 0;
    }
}
```

这里没有 `unsafe` 块。越界由 `get_mut` 拒绝，整数溢出由 `checked_add` 拒绝，而失败都发生在更新游标之前——因此容量失败不消耗剩余空间，这是一项明确的事务性行为（对照[@def-2.2.2]：约束由构造点维持，而不是靠调用方自觉）。`ByteRegion` 自身的 size 是 32 字节、align 是 8（2.1 探针表），它是「描述符 + 元素区」两笔账的典型（[@def-2.1.2]）。

::: ex 例 2.6.1 · 手推一个 8 字节区域 {#ex-2.6.1}

按[@def-2.6.2] 的接口，从 `ByteRegion::new(8)` 开始依次执行：`take(6)` 并把返回切片 `fill(7)`；`take(3)`；`take(usize::MAX)`；`take(2)`；`reset()`；`take(6)`。写出每步之后 `used` 的值、返回内容是 `None` 还是切片、以及切片内容。

::: sol 解答

`used = 0`。`take(6)`：`checked_add` 得 6，`get_mut(0..6)` 成功，`used = 6`，切片写成 7。`take(3)`：`checked_add` 得 9（没有溢出），但 `get_mut(6..9)` 越出长度 8，返回 `None`，且 `used` 仍是 6——游标在失败路径上没有被赋值。`take(usize::MAX)`：`checked_add` 溢出，返回 `None`，连 `get_mut` 都不会执行，`used` 仍 6。`take(2)`：`end = 8`，成功，返回偏移 6、7 两字节，内容是 `[0; 2]`（这两位从没被写过），`used = 8`。`reset()`：`used = 0`，`storage` 一个字节都没动。`take(6)`：成功，内容是 `[7; 6]`——上一次填进去的旧字节又被看见了（2.6.5）。

这五步说明两件事：失败不消耗剩余空间，所以重试和小请求仍然可用；复用会暴露旧内容，所以「新取的切片必定为零」这种假设不成立。归档里的容量失败测试断言了这两条（见 2.7 的安全失败用例）。
:::

:::

### 2.6.4 生命周期如何限制 reset

返回切片的生命周期绑定到可变 `self` 借用。若切片后续仍被使用，调用 `reset` 需要的第二个可变借用不能成立。这让「`reset` 期间不存在仍将被使用的旧借用」由接口表达，而不是在注释里请求调用方自觉遵守（[@def-2.2.2]）。包中的 compile-fail 文档测试验证这个拒绝案例：它在编译阶段失败，不执行任何危险运行。

```rust,compile_fail
let mut region = ByteRegion::new(64);
let slice = region.take(4).expect("capacity");
region.reset();
slice[0] = 3;
```

::: def 定义 2.6.3 · 词法作用域与有效借用区间 {#def-2.6.3}

**词法作用域**是变量在源码里可见的范围；**有效借用区间**是这个借用真正被后续使用撑起的时间段。现代借用分析关注后者：切片变量已经不再使用，借用就可以结束，此时 `reset` 合法进行（第 3 章会把这两件事进一步分开）。
:::

::: ex 例 2.6.2 · 这三个调用序列哪些能编译 {#ex-2.6.2}

按[@def-2.6.3] 判断：① `let s = region.take(4).unwrap(); region.reset(); s[0] = 3;`；② `let s = region.take(4).unwrap(); s[0] = 3; region.reset();`，此后再没有用到 `s`；③ `region.take(4).unwrap()[0] = 3; region.reset();`。哪个会失败？为什么 ② 和 ③ 能通过？

::: sol 解答

只有 ① 失败：`s[0] = 3` 是 `s` 的一次后续使用，它落在 `region.reset()` 之后，两个可变借用（`s` 与 `reset` 需要的 `&mut region`）重叠，借用检查器拒绝——上面那段 compile-fail 就是这个形状。

② 里 `s` 的最后一次使用在 `reset` 之前，借用区间已经结束，`reset` 拿到的新可变借用不与任何存活借用冲突；`s` 这个名字还在词法作用域里，但没有后续使用，所以不阻塞（见[@def-2.6.3] 的区分）。③ 更短：临时切片的唯一一次使用就在那条语句内完成，借用随语句结束。

要注意这条通过不等于「语义上安全」：②和③能编译，是因为程序确实不再访问旧切片；如果后续重新取用同一区域，读到的仍是上一次留下的字节（2.6.5）。借用检查保证的是不会用到失效引用，不保证旧内容符合你的预期。
:::

:::

### 2.6.5 reset 不等于擦除

`reset` 只把 `used` 设为 0，旧字节仍保留在 `storage` 中，下一次 `take` 可以观察这些旧字节——[@ex-2.6.1] 的最后一步就是这个行为，测试也明确验证它。这适合已知会覆盖全部有效内容的内部缓冲；不适合把「新取到切片必定为零」当成安全需求的调用者，也不能用于未经设计的敏感数据清理承诺。

若需要清零，应显式增加清理策略，并把清理成本计入相应生命周期（[@def-2.6.1]）。不能一边依赖「复用不清零」的速度，一边声称等价于每次新建零缓冲。本章 benchmark 会在读取前 `fill(7)`，因此它不依赖旧内容为零。

::: think 思考 · 「同一个区域循环使用，等于每块都是新缓冲」 {#think-2.6.1}

有人把上面的接口改成常驻区域：每批只 `reset` 一次，逐块 `take`、写入有效字段、交给下游。他写下「行为等价于每次新建 `Vec`，只是省了分配」。这条等价声明在哪一步被破坏？

::: sol 解答

在「未写入的字节」那一步。新建 `vec![0u8; 64]` 保证 64 字节全零；从复用区域 `take(64)` 拿到的是上一轮的残留内容。只有当写入覆盖了切片的每一个字节，两者才在**被读到的位置**上等价——一旦写入是部分覆盖（例如只写前 40 字节而下游读 64），旧数据就被当成新数据消费了。

还有第二条更隐蔽的差别：资源释放时机。`fresh_vec` 每块归还存储，区域整批保留存储（2.7 会把这条写进契约）。所以「等价」要同时验证内容覆盖范围与释放语义，缺任何一条都只能写成「在本实验的读取集合上不可区分」（对照[@def-1.6.1] 的等价工作比较）。
:::

:::

### 2.6.6 全局分配器自己要花哪三笔

2.6.1 说「`malloc` 没有固定延迟」，但要判断换分配器值不值，得先知道每次分配**必然**要付什么。rCore 教程在实现内核堆时把 `GlobalAlloc` 这个接缝摊开讲：`alloc` 与 `dealloc` 各收一个 `Layout`（`size` 加 `align`，`align` 必须是 2 的幂，返回地址必须是它的倍数），堆本身是一块位于 `.bss` 的零初始化字节数组，而实现 `LockedHeap` 时被 `Mutex<T>` 包着——**对它的任何操作都要先拿锁**。把这三件事摊开，就是三笔成本。

::: def 定义 2.6.4 · 全局分配器的三笔成本 global allocator overhead {#def-2.6.4}

走 `GlobalAlloc` 的堆分配要付的成本，按随什么增长可分成三笔：**① 参数与协议**：每次调用都要带 `Layout`，对齐是请求的一部分而不是平台常数（C 的 `malloc` 不必传对齐，因为按平台上限对齐一次就够；Rust 把这件事变成每次分配的显式需求）。**② 同步**：全局分配器是全进程共享的一个对象，多线程下每次 `alloc`/`dealloc` 都要过一把锁，锁的争用随线程数与分配频率增长，与你的数据结构无关。

前两笔都是随分配次数成正比的固定开销，少分配对两者的削减同向，不存在「只有某一笔能绕开」的分别。**③ 元数据与碎片**——按块记账的分配器要记录每块的归属与大小才能释放，小对象长期混用会留下装不下下次请求的空洞；这一笔随存活块数与生命期相关，且以「按块记账」为前提，本章 `ByteRegion` 只用一个游标、不带每块元数据，就不付这一笔。
:::

这条定义给出一个可检验的推论：**如果一段代码的收益主要来自「少调用分配器」，那么它的收益有一部分其实来自少拿锁**，在多线程下会被放大，在单线程下几乎不存在。所以「换成区域分配后快了 2.93 倍」这类结论（2.7.3 的真数：`fresh_vec` 均值 8.248312814 ÷ `byte_region` 均值 2.813854399），必须同时报告线程数与是否共享堆，否则读者无法判断这个数字在他的服务里还成不成立（[@def-1.4.1] 的同一条边界规则）。

本章 2.7 的对照是单线程的，它只能告诉你两臂的总差值；这 2.93 倍里 ①③ 各占多少、生命期占多少，要逐事件采集才分得开，这类采集**没有做过**，多线程下的锁争用对照同样**没有采集**。

### 2.6.7 小结与常见错误

**小结。**① 分配成本属于具体生命周期，比较前要先声明分配频率与存储生命期都变了（[@def-2.6.1]）；② 能力边界写进签名：只给字节切片、同一时刻一个借用、`Option` 表达容量失败（[@def-2.6.2]）；③ 游标推进是事务性的，失败不消耗剩余空间（[@ex-2.6.1]）；④ `reset` 的合法性由借用区间决定，不是由变量名决定（[@def-2.6.3]、[@ex-2.6.2]）；⑤ 复用会暴露旧字节，清理要显式设计并计入成本（[@think-2.6.1]）。下一节 [2.7 benchmark 二：小缓冲生命周期与区域复用](#sec-cpp-rust.1.2.7) 给这套接口上计时。

::: errata 常见错误清单（2.6 节）

E-a **把 `ByteRegion` 当通用 arena。**它不构造 `T`、不处理对齐、不支持多借用（[@def-2.6.2]）。

E-b **假设 `take` 得到的切片是零。**`reset` 不清内容，旧字节会被看见（[@ex-2.6.1]）。

E-c **在容量失败分支里先推进游标。**那会把剩余空间一起吃掉；必须 `checked_add` 与 `get_mut` 都成功后才提交（[@ex-2.6.1]）。

E-d **靠注释要求调用方「用完再 reset」。**约束必须由借用关系表达（[@ex-2.6.2]、[@def-2.2.2]）。

E-e **认为变量还在作用域里就不能 reset。**决定权在有效借用区间（[@def-2.6.3]）。

E-f **一边复用一边声称「等价于每次新建零缓冲」。**覆盖范围与释放时机都要验（[@think-2.6.1]）。

:::

::: method 即时自测 · 2.6

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　`take` 的签名里哪三处分别承载了哪条约束？

::: sol 第 1 题答案
`&mut self`：同一时刻只有一个存活借用；返回 `Option<&mut [u8]>`：容量不足是可恢复结果，且只给字节切片不给 `T`；返回引用的生命周期绑定 `self`：旧借用不结束就调不了 `reset`。对应[@def-2.6.2]。
:::

**第 2 题 · 辨析**　「`take` 用 `get_mut` 而不是索引，所以这个组件是 unsafe 的简化版。」对吗？

::: sol 第 2 题答案
不对，方向正好相反。`get_mut` 返回 `Option`，越界是可检查的失败，因此不需要 `unsafe`；索引 `self.storage[a..b]` 会在越界时 panic。选 `get_mut` 是为了把失败变成可恢复的 `None`，配合 `checked_add` 构成事务性游标（[@ex-2.6.1]、[@def-2.6.2]）。
:::

**第 3 题 · 应用**　容量 8 的区域，依次 `take(5)`、`take(4)`、`take(3)`。写出每步结果与最终 `used`。

::: sol 第 3 题答案
`take(5)` 成功（`used` 0→5）；`take(4)`：`checked_add` 得 9，`get_mut(5..9)` 越界，返回 `None`，`used` 仍 5；`take(3)`：`end = 8`，成功，`used = 8`。总量仍是 8 字节可用空间，失败没有消耗它（[@ex-2.6.1]）。
:::

**第 4 题 · 迁移**　业务要求「每个请求的敏感字节在归还后立即不可读」。本节接口能直接满足吗？说出缺的那一件与代价。

::: sol 第 4 题答案
不能直接满足：`reset` 只动游标，不清内容（2.6.5）。缺的那件是显式清理策略——在归还或 `reset` 前对已用范围做清零（以及语言层面不被优化消除的处理），代价是把这部分写入计入生命周期，收益相应缩小（[@think-2.6.1]）。若还要「多块同时存活」，本节接口就不匹配了，应改用拥有缓冲或分块池（2.7 的适用形态讨论）。
:::

## 2.7 benchmark二：小缓冲生命周期与区域复用 {#sec-cpp-rust.1.2.7}

本节回答一个问题：**8.25 对 2.81 里，有多少其实是被计量的对象换了？**两个 case 的返回值相同，资源释放时机却不同；先把单位与契约钉死，才知道这条差距归谁。

::: preview 先抓住一件事

比较两种存储策略前，先确认它们做的是**同一份逻辑工作**（[@def-1.6.1]）：这里两边都填 7、都只把首字节计入校验、都返回 28672。差别在资源语义上——`fresh_vec` 每块归还存储，`byte_region` 整批持有 262144 字节。要肯定「复用更快」，得同时接受「分配频率与生命期都变了」这个前提（[@def-2.6.1]）；要否定「2.81 是分配器耗时」，只需看单位：它是 ns/逻辑块操作，不是纯分配调用延迟。
:::

### 2.7.1 工作契约：一次逻辑块操作是什么

::: def 定义 2.7.1 · 逻辑块操作 {#def-2.7.1}

本实验的计量单位是**一次逻辑块操作**：取一段 64 字节、用 7 填满、把首字节加进校验、再把整段切片交给 `black_box` 观察。一次工作核做 4096 次这样的操作，一批调用工作核 16 次，所以单位是 ns/逻辑块操作——它包含取存储、写入、观察三项，不是纯分配调用延迟。
:::

按[@def-2.7.1]，两边共用的规则是：每块先填充 7，再把首字节加入校验；整个切片经 `black_box` 观察，避免只保留单字节初始化（观察集合的取法见[@def-1.3.1]）。`fresh_vec` 每块创建并销毁独立 `Vec`；`byte_region` 每次工作核 `reset` 一次，并依次取出短暂切片。

### 2.7.2 完整入口

完整代码位于 `src/bin/allocation.rs`，这里保留全部业务路径与参数；统计与预热使用同包公共夹具（[@def-2.5.1] 的计时外规则同样适用）。

```rust
use foundations_lab::{ByteRegion, Case, run};
use std::hint::black_box;

const COUNT: usize = 4096;
const LEN: usize = 64;

fn main() {
    let mut region = ByteRegion::new(COUNT * LEN);
    let mut cases = [
        Case {
            name: "fresh_vec",
            expected: (COUNT * 7) as u64,
            work: Box::new(|| {
                let mut sum = 0;
                for _ in 0..COUNT {
                    let mut bytes = vec![0u8; black_box(LEN)];
                    bytes.fill(7);
                    sum += u64::from(black_box(&bytes)[0]);
                }
                sum
            }),
        },
        Case {
            name: "byte_region",
            expected: (COUNT * 7) as u64,
            work: Box::new(|| {
                region.reset();
                let mut sum = 0;
                for _ in 0..COUNT {
                    let bytes = region.take(black_box(LEN))
                        .expect("fixed capacity");
                    bytes.fill(7);
                    sum += u64::from(black_box(bytes)[0]);
                }
                sum
            }),
        },
    ];
    run(&mut cases, 16, COUNT);
}
```

`expected` 为 28672，即 `COUNT × 7`：每块只有首字节进入校验（[@def-2.7.1]）。正式夹具逐次验证返回值（[@def-1.3.1]）。容量 `COUNT × LEN` = 262144 字节恰好覆盖一次工作核，每次工作核开始前 `reset`；失败不是被测常态路径，容量失败另外由测试验证（2.7.6）。

::: ex 例 2.7.1 · 校验值与每批时长都要自己算一遍 {#ex-2.7.1}

① 只用 `COUNT`、`LEN` 与「每块填 7、只加首字节」这条契约，算出 `expected`。② 一批有多少次逻辑块操作？用 2.7.3 的均值算出两边各一批多长、每批差多少。③ 如果 `byte_region` 改成只在最后一次才 `fill`，`expected` 会怎样？

::: sol 解答

① 4096 × 7 = 28672，与代码里的 `(COUNT * 7) as u64` 一致，两个 case 共用同一个参考值（[@def-1.6.1]）。② 每批 = 16 × 4096 = 65536 次逻辑块操作。fresh_vec 一批 ≈ 65536 × 8.248312814 ns ≈ 540 561 ns，约 0.54 ms；byte_region 一批 ≈ 65536 × 2.813854399 ≈ 184 409 ns，约 0.18 ms；每批差 ≈ 356 153 ns，与配对均值 −5.434458415 × 65536 = −356 153 ns 相符——差值换算能对上，说明单位和分母没有写错（对照[@ex-2.5.1]）。③ `sum` 只剩最后一次那块的 7，与 28672 不符，夹具会在批后立刻报失败。

这条自查的作用是：任何一次「看起来更快」的改动，只要让校验值偏离独立参考值，就说明少干了活，谈不上加速（[@def-1.3.1]）。
:::

:::

|:--|--:|--:|--:|--:|
| fresh_vec | 8.248312814 | 0.173203503 | 8.246734619 | 8.638381958 |
| byte_region | 2.813854399 | 0.027682164 | 2.817779541 | 2.855300903 |

区域减 fresh_vec 的配对均值为 −5.434458415，bootstrap 区间为 [−5.514596121, −5.358680362]（[@def-1.4.2]、[@def-1.6.2]）。这支持当前短暂块通路中的复用收益；不支持把 2.81 称为任意对象分配耗时，也不支持宣称自制区域优于所有系统分配器（[@def-2.1.3]）。

::: def 定义 2.7.2 · 接口语义收益与算法收益 {#def-2.7.2}

**接口语义收益**来自被研究对象本身变了：区域不为每块调用全局分配与释放、它提前持有一整段已初始化存储、它也不在 `reset` 时擦除旧数据（2.6.5）。这三条都不是「同一个算法跑得更快」，而是接口换掉了分配频率与生命期（[@def-2.6.1]）。**算法收益**则是同一接口的实现改进。两者的报告方式不同：前者必须写出换掉了什么、还剩什么成本在边界外。
:::

按[@def-2.7.2]，`fresh_vec` 的零初始化可能被后续覆盖与优化改变，实际后端行为不能仅从宏表面推断（对照[@def-1.1.1] 的删除判断方法）；本章不声称逐字节测出了哪部分初始化被消除。

### 2.7.4 哪些成本被移出边界

区域最初的 `Vec` 创建在计时外，区域最终的 `Vec` 销毁也在计时外（[@def-2.5.1]）。如果请求只用一次区域，必须把这些成本加回来；如果区域长期占用而使用率很低，还可能增加常驻内存。当前区域容量为 262144 字节，即 `COUNT × LEN` = 4096 × 64；这是整个工作核的预留存储，不是每块新分配大小（[@def-2.1.2] 的两笔账在这里同样成立）。比较时应同时报告生命周期与内存预留（[@def-1.7.1] 的并列约束）。

::: think 思考 · 「表里没报内存，所以可以当它不存在」 {#think-2.7.1}

有人只看 2.81 与 8.25 这两个数就下结论：每块省下 5.43 ns，所以每条连接都配一个区域。这条推理绕过了哪个前提？

::: sol 解答

绕过了「时间收益与空间成本是并列约束」这条前提（[@def-1.7.1]）。区域把 262144 字节整批持有；若每条连接各留一个，连接数会把这笔预留放大同样的倍数，而结果表里根本没有内存这一列——**本节没有采集多连接工作负载下的常驻内存与峰值**，所以这条差距只覆盖了时间轴（对照 2.8 的内存峰值讨论）。

第二层漏项是命中率：预留按 4096 块设计，实际请求的块数分布没有测过，容量失败路径也就没有统计概率（2.7.6、2.8 的容量治理）。正确写法是把 2.81 ns 与 262144 字节预留一起交出去，让预算方判断，而不是只报好看的那一列。
:::

:::

### 2.7.5 该组件适用的实际工作形态

同步批处理中逐块编码并立即交付，是一种可能形态：每个切片消费完成后再取下一块（[@def-2.6.2] 的第三条限制正好对应这种用法）。若接收方异步持有数据，当前接口就不匹配；不能把借用强行延长成 `static` 来绕过它（[@def-2.6.3]）。应该改为转移拥有缓冲、使用分块池或采用有界共享所有权，这些方案有不同的内存和同步成本，应单独测量，而不是偷偷把当前区域改成裸指针接口（对齐与来源责任见 2.8）。

### 2.7.6 安全失败用例：它覆盖了什么

测试先从 8 字节区域取 6 字节并填 7，接着请求 3 字节应返回 `None`，再请求 `usize::MAX` 也应返回 `None`，最后请求 2 字节应成功；这证明两种失败没有改变游标。`reset` 后再次取 6 字节，读到此前的 7，这同时验证「不擦除」的真实契约（[@ex-2.6.1] 逐步推过这条序列）。

```rust
let mut region = ByteRegion::new(8);
region.take(6).expect("fits").fill(7);
assert!(region.take(3).is_none());
assert!(region.take(usize::MAX).is_none());
assert_eq!(region.take(2).expect("failure preserved cursor"), [0; 2]);
region.reset();
assert_eq!(region.take(6).expect("reusable"), [7; 6]);
```

容量失败是正常可恢复结果；benchmark 里的 `expect` 只验证固定夹具配置（`COUNT × LEN` 恰好等于一次工作核的需求），生产接口可直接处理 `None` 并实施回退策略。不能把固定输入下不会失败的假设推广到外部请求（[@def-1.1.3] 的输入集合）。

::: ex 例 2.7.2 · 这段测试能支持哪一句结论 {#ex-2.7.2}

上面的断言序列加上 2.7.1 的契约，能支持「区域路径在生产中不会失败」吗？把这段测试实际覆盖的断言逐条列出来，再列出它没有覆盖的两件事。

::: sol 解答

能支持的句子止于接口契约：① 越过剩余空间的 `take` 返回 `None`（`6+3 > 8`）；② 加法溢出也返回 `None`（`usize::MAX`）；③ 两种失败都不动游标（随后 `take(2)` 成功且内容是 `[0; 2]`）；④ `reset` 不清内容（再次 `take(6)` 得到 `[7; 6]`）。这四条与[@ex-2.6.1] 的逐步推算完全一致，都是确定性断言，不涉及概率。

没有覆盖的两件事：一是**失败发生的频率**——生产请求的块数分布没有采集，所以无法说「实际上不会失败」，只能说「失败时接口给出 `None`」；二是**失败之后的回退策略成本**（拒绝、分块、拥有缓冲、慢路径各有尾延迟与内存代价，见 2.8 的容量治理，本节没有测量）。把确定性测试当成生产概率证明，是把两类证据混成一类（[@def-2.3.2] 的三分法在这里同样适用）。
:::

:::

### 2.7.7 小结与常见错误

**小结。**① 两边做同一份逻辑工作、同一个参考值 28672，所以可以比（[@def-1.6.1]、[@ex-2.7.1]）；② 单位是 ns/逻辑块操作，含取存储、写入与观察，不是纯分配延迟（[@def-2.7.1]）；③ 收益来自接口语义变化，不是同一个算法跑得更快（[@def-2.7.2]）；④ 区域的构造、销毁与 262144 字节预留在计时外，必须与耗时一起报告（[@think-2.7.1]）；⑤ 确定性测试只证明失败给出 `None` 且游标不动，不证明失败概率（[@ex-2.7.2]）。下一节 [2.8 对齐、分配器边界与布局重构决策](#sec-cpp-rust.1.2.8) 回答「要把它推广到任意 `T`，还缺哪几份证明」。

::: errata 常见错误清单（2.7 节）

## 2.8 对齐、分配器边界与布局重构决策 {#sec-cpp-rust.1.2.8}

本节回答一个问题：**要把这块字节交给任意 `T`，还缺哪几份证明？**本节把「算得出偏移」与「有权把这段地址当成对象」分开，并把本章没有实现的能力明确留在清单上。

::: preview 先抓住一件事

类型化放置需要**两份互不替代的证明**：布局证明（放在哪里合适）与来源证明（是否有权这样访问）。肯定一条放置是合法的，八项要素都要在（2.8.2）；否定一句「我把游标向上取整了就对齐了」只需要一个反例——基地址本身不满足目标 align 时，整齐的偏移仍会得到错误地址（[@def-2.8.1]）。本章刻意只实现字节切片区域，所以下面这份清单是设计清单，不是已交付的实现。
:::

### 2.8.1 为什么不从字节区域直接返回任意 T

`Vec<u8>` 只要求 `u8` 对齐；即使某次系统分配碰巧高度对齐，也不是接口保证（[@def-2.1.3] 的层级区分在这里决定成败）。把区域的**相对游标**向上取整，不等于**绝对地址**对齐：如果基地址未对齐，整齐的偏移仍会得到错误地址。通用 arena 必须基于绝对地址计算可用位置，还要处理加法溢出、容量、初始化与销毁（[@def-2.6.2] 的「不提供任意 align 请求」就是为了回避这一整段责任）。

::: def 定义 2.8.1 · 相对偏移对齐与绝对地址对齐 {#def-2.8.1}

设区域基地址为 `base`、当前游标为 `used`，待放置地址是 `base + used`。**相对偏移对齐**只让 `used` 成为目标 align 的倍数；**绝对地址对齐**要求 `base + used`（再计入 padding 后）本身是 align 的倍数，且整个对象完整落在同一次分配内。只有后者满足 `&mut T` 的要求（[@def-2.1.1] 的 align 定义说的是「合法存放位置的地址约束」，量的就是绝对地址）。
:::

计算顺序也属于证明的一部分：应先检查加法是否溢出，然后按目标 align 求上取整位置，最后确认对象完整落在分配内。这个过程不能靠无检查位运算拼成「高性能代码」——语言的布局约束不会因 benchmark 需要速度而放宽。

### 2.8.2 绝对地址对齐的证明要素

第一，align 必须来自合法 `Layout` 或等价的受检参数。第二，`base` 与 `used` 相加不能溢出。第三，向上取整不能越出地址空间。第四，padding 与 size 相加不能溢出。第五，新范围必须完全属于原分配。第六，返回引用前必须已构造有效 `T`（有效值的概念见[@def-2.2.1]）。第七，后续 `reset` 不能发生在仍需使用的借用期间（[@def-2.6.3]）。第八，所有需要 `Drop` 的对象必须有明确回收路径。

这些要素合起来是设计清单，不是本章已经实现的通用 arena。本章刻意只实现字节切片区域，因此不需要伪装为完整的类型化分配器——有限组件的诚实边界优于未经证明的通用接口（[@def-2.6.2]）。

::: ex 例 2.8.1 · 手推一次「看起来对齐」的放置 {#ex-2.8.1}

假设（这是算术演示，不是实测）某区域基地址 `base = 0x1004` 且只保证 4 字节对齐，游标 `used = 3`，现在要放置一个 `u64`（align 8，size 8）。按[@def-2.8.1] 分别用「相对游标上取整」和「绝对地址上取整」算出候选地址，判断各自是否合法。

::: sol 解答

候选起点 `base + used = 0x1007`。相对做法把 `used` 上取整到 8，得偏移 8，地址 `0x1004 + 8 = 0x100c`；`0x100c ÷ 8 = 513.5`，余 4，**未对齐**，用它构造 `&mut u64` 就是无效引用。绝对做法把待放置地址上取整：`0x1007 → 0x1008`，`0x1008 ÷ 8 = 513` 整除，对齐成立，但要继续走完清单——本次消耗 `padding = 0x1008 − 0x1007 = 1` 字节，`padding + size = 9` 字节，最后确认 `0x1008 + 8` 不超过分配末尾（第五项）。

相对做法为什么会错？因为它默认了 `base` 已是 align 的倍数，而这个前提属于分配器给 `u8` 向量的承诺之外（本节第一段）。两条结论都归结为：**先证明基地址，再算偏移**，顺序反了就得出一张漂亮的错误偏移表（对照 2.8.8 的 Layout 输出，那个 8 是「相对满足整体 align 的基地址」的偏移）。
:::

:::

### 2.8.3 ZST、空请求，以及分配与初始化的拆分

零尺寸类型（ZST，size 为 0 的类型）可能没有实际字节载荷，但引用仍有非空、对齐等要求；不能用 null 构造一个「反正不访问」的引用（有效值与引用约束见[@def-2.2.1]）。类型化容器还需要处理逻辑元素数量与析构次数——即使每个元素 size 为 0，`Drop` 也可能有可观察效果。本章 `ByteRegion` 只接受字节长度，`take(0)` 的行为由安全切片接口维护（[@def-2.6.2]），不把它类推为任意 ZST 的对象工厂。

分配与初始化也是两件事。分配得到的是存储，不自动意味着存在有效对象；`Vec` 的容量与长度正是这种区分的一个安全封装——长度范围内必须存在合法 `T`，容量余量可以还没有 `T`（2.1 的字段图末尾那一段画的就是这条边界）。第 3 章会讨论为什么 `set_len` 越过初始化边界会出错；本章不为速度调用 `set_len`，所有字节都由 `vec![0; capacity]` 合法初始化（含义见[@def-2.6.1]）。

### 2.8.4 packed 并非免费压缩，缓存对齐也不是类型对齐

`packed` 降低对齐可能减少填充，但字段可能位于不满足其自然对齐要求的位置（自然对齐由[@def-2.1.1] 的 align 给出），形成普通引用就可能违反要求。不能先创建未对齐引用，再声称「稍后只做拷贝」。若必须处理紧凑外部格式，应使用字节解析或合适的未对齐访问接口，还要判断目标上未对齐访问的实际成本。**本章没有运行 packed 性能实验**，因此不给它填入「典型惩罚」数字（这是 2.3 那套三类证据纪律的再一次应用，见[@def-2.3.2]）。

::: def 定义 2.8.2 · 类型对齐与缓存对齐 {#def-2.8.2}

**类型对齐**是语言层面对存放地址的约束；**缓存对齐**是为了让对象落在预期缓存行边界上而人为提高的 align 要求，例如 `repr(align(128))`。后者可以提高某类型的对齐要求，但也可能扩大数组步长与内存占用；缓存行大小本身是目标观测（本机 `sysctl` 报告 128 字节，2.3.1），不是 Rust 类型系统自动理解的业务语义。
:::

::: ex 例 2.8.2 · 给 `Record` 加 `repr(align(128))` 会发生什么 {#ex-2.8.2}

本轮 `Record` 的 size 是 64、align 是 8（2.1 探针表）。若改成 `#[repr(align(128))]`，按 size 必须是 align 倍数的规则，它的 size 至少变成多少？65536 个元素的数组步长总量变成多少，与 2.5 的热列和 AoS 三个数放在一起怎么读？

::: sol 解答

align 变成 128 后，size 必须上取整到 128 的倍数，而字段本身只占 64 字节，所以 size 至少为 128——每个对象多出 64 字节纯填充。数组总跨度从 65536 × 64 = 4194304 字节变成 65536 × 128 = 8388608 字节，正好翻倍；热列（524288 字节）不受影响，因为它压根不含冷字段（[@def-2.4.1]）。

读法：这条改动对单线程顺序读 `hot` 的通路只有坏处——地址跨度更大、密度更低（热字段密度从 8 ÷ 64 = 12.5% 降到 8 ÷ 128 = 6.25%，2.3.1 的算法）。它可能在「多线程分别写不同对象」时减少同一行争用，但**本章没有测量伪共享**（2.3.4 明确记为未采集），所以这里不能声称它更快。结论只能写成：提高对齐有时减少共享，有时浪费容量；不能因为本机 cacheline 为 128，就把所有结构都填充到 128。
:::

:::

### 2.8.5 从实验到设计的决策表

| 业务约束 | 候选布局/存储 | 必须新增的验证 |
|:--|:--|:--|
| 反复顺序读取少数字段 | 热列或热冷拆分 | 转换与一致性维护 |
| 单对象全字段处理 | AoS | 随机索引与对象密度 |
| 短暂同步字节块 | ByteRegion式复用 | 覆盖旧内容与容量回退 |
| 异步持有多个块 | 拥有缓冲或有界池 | 回收、取消和上界 |
| 任意类型长期借用 | 已验证的类型化容器 | 对齐、Drop、别名与reset |
| 跨语言外部布局 | 明确repr及C ABI协议 | 双边布局与所有权测试 |

::: method 判定流程 · 一次布局或存储改动的取舍顺序

① **先固定访问集合与生命期**：读几个字段、扫描几次、数据活多久（2.3.4、2.3.5），这一层决定候选是什么。<br>
② **再查保证层级**：候选依赖的是语言约束、标准库保证还是一次本机观测（[@def-2.1.3]）；依赖后者就要打算换环境重测。<br>
③ **补齐缺的那一类证据**：机制归因要事件采集，收益要带转换与更新成本（[@def-2.3.2]、[@def-2.4.1]）。<br>
④ **最后写下没有实现的能力**：对齐、`Drop`、别名、来源——清单在 2.8.2，缺一项就不要伪装成通用组件（[@def-2.6.2]）。
:::

::: think 思考 · 「`Layout` 算出了 8，所以地址安全」 {#think-2.8.1}

某人读完 2.8.8 的示例后写道：`extend` 给出 `value_offset = 8`，于是从 `Vec<u8>` 的 `as_ptr()` 加 8 处取一个 `u64` 完全合法。这条推理跳过了哪几步？

::: sol 解答

跳过了三步。第一，`base` 的对齐没有证明：`Vec<u8>` 只承诺 `u8` 对齐，[@ex-2.8.1] 算的就是这种情形下整齐的偏移仍可能给出未对齐地址。第二，加法与范围要受检：`base + 8` 是否溢出、`8 + size` 是否越出分配（2.8.2 的第二、三、四、五项）。第三，也是完全不同的一类：那个位置**还没有构造出有效的 `u64`**，而指针来源必须属于同一次分配（2.8.7 的 provenance）。

`Layout` 给的是「相对一个满足整体 align 的基地址的偏移」，它是布局证明的一半，不是访问权限证明。把两半合成一半，就把[@def-2.1.1] 的 align 读成了「偏移表里的数字」。
:::

:::

### 2.8.6 不要让内存峰值消失在平均值里

复用池可能让每次操作更快，也可能长期保留峰值容量；若每条连接都保留一个大区域，连接数会放大内存成本（[@think-2.7.1] 是同一条错误）。因此系统预算应包括常驻、峰值与突发分配三类量（[@def-1.7.1] 的并列约束）。**本章没有多连接工作负载**，262144 字节区域只是实验配置，不是每请求或每线程的通用推荐值。

### 2.8.7 对齐证明与指针来源是两类证明

即使整数地址满足模对齐，也不代表它拥有访问权限：指针必须源自适当分配，并在该分配生命周期内；邻接的两次分配也不能因为地址连续就合并成一个切片。这部分将在第 3 章展开。布局计算解决「放在哪里合适」（[@def-2.8.1]），来源与借用解决「是否有权把它当成对象访问」——两类证明缺一不可（[@think-2.8.1] 数出的正是被合并成一句话的那两步）。

### 2.8.8 用受检 Layout 规划组合存储

新增的 `examples/storage_plan.rs` 演示布局计算而非分配：它把一个 `u8` 布局与一个 `u64` 布局组合，`extend` 返回组合布局及第二个成员的偏移，`pad_to_align` 把整体尺寸补到对齐倍数。这比手写无检查的上取整表达式更适合维护溢出边界（2.8.2 清单的第一、三、四项就落在这些返回类型里）。程序没有构造裸指针，也没有分配对象。

```rust
use std::alloc::Layout;

fn main() -> Result<(), std::alloc::LayoutError> {
    let tag = Layout::new::<u8>();
    let value = Layout::new::<u64>();
    let (combined, value_offset) = tag.extend(value)?;
    let padded = combined.pad_to_align();
    println!(
        "value_offset={value_offset} size={} align={}",
        padded.size(),
        padded.align()
    );
    assert_eq!(value_offset, 8);
    assert_eq!(padded.size(), 16);
    assert_eq!(padded.align(), 8);
    assert!(Layout::array::<u64>(usize::MAX).is_err());
    let zst = Layout::array::<()>(100)?;
    assert_eq!(zst.size(), 0);
    assert_eq!(zst.align(), 1);
    println!(
        "overflow=rejected zst_size={} zst_align={}",
        zst.size(),
        zst.align()
    );
    Ok(())
}
```

该程序在本机实际编译和执行，结果位于 `results/validation-01/storage-plan.txt`：组合后的偏移为 8，尺寸 16，对齐 8；超大 `u64` 数组请求被拒绝；100 个单元值的布局 size 为 0、align 为 1。这些是布局规划结果，不是实际内存消耗测量（[@def-2.3.2] 的分类里，它们属于第一类）。

::: ex 例 2.8.3 · 从 `Layout` 的输出读出四件事 {#ex-2.8.3}

`value_offset = 8`、`padded.size() = 16`、`padded.align() = 8`、`Layout::array::<u64>(usize::MAX)` 返回 `Err`、`Layout::array::<()>(100)` 的 size 是 0。逐条说明它各自对应 2.8.2 清单里的哪一项（或 2.1 的哪条规则），并说明这份输出**不能**支持哪一句结论。

::: sol 解答

`value_offset = 8`：`u8`（size 1、align 1）之后要放 align 8 的成员，偏移必须上取整到 8，与[@def-2.1.1] 的 align 定义一致；COrder 的 `value` 偏移同样是 8（2.1.3 的表），两处互相印证。`size = 16`、`align = 8`：`pad_to_align` 把 8 + 8 = 16 补到 align 的倍数（16 已是），对应清单第四项「padding 与 size 相加」。`array::<u64>(usize::MAX)` 报 `Err`：清单第二、三项（加法与上取整溢出）由返回类型而不是位运算承担。`Layout::array::<()>(100)` 的 size 0、align 1：对应 2.8.3 说的 ZST——100 个逻辑元素不占字节，但容器仍要按 100 次计数处理析构（若类型有 `Drop`）。

不能支持的结论：「所以从 `Vec<u8>` 的第 8 个字节起放 `u64` 是安全的」。这个 8 是**相对**偏移，前提是整个分配满足组合 Layout 的 align 8（[@ex-2.8.1]、[@think-2.8.1]）；也不能读成「程序占用了 16 字节内存」——它一个对象都没分配。
:::

:::

Layout 规划仍有范围边界：它给出的是相对于一个满足整体 align 的基地址的偏移。若底层只有 `u8` 对齐保证，不能直接套用该偏移返回 `u64` 引用；必须让实际分配满足组合 `Layout`，或者在现有分配中计算绝对地址并证明所有范围约束（2.8.2 清单）。本章只演示前半份规划，不实现后半份 unsafe 放置——把两份证明分开，为的是防止「算出了 8，所以地址安全」这个错误（[@think-2.8.1]）。

组合布局常用于「头部 + 尾部载荷」：头部可能记录长度、状态与回收信息，尾部可能是动态大小元素区。这种结构要同时规划头部、元素步长与总长度；字段布局正确并不表示尾部元素已经初始化，头部记录的长度也必须与实际初始化状态一致——若头部提前发布了完整长度，其他访问者可能读取未构造元素（这条边界在 2.1 字段图的「容量余量」处已经画过，第 3 章专门讨论）。因此布局规划应与初始化状态机一起审查。

把头部与载荷放在一次分配中可能减少分配次数，但也会绑定两者生命周期。如果头部很热而载荷很冷，共置可能扩大热访问跨度（[@def-2.3.1]）；如果头部跨线程共享，布局还可能引入缓存行争用（2.3.4 记为未采集）。一次分配不是天然优于两次分配，要看分配频率、访问模式和回收路径。**本章不为这种未实现结构发布加速数字**。

### 2.8.9 区域复用的容量治理，与「生命周期等价」这件事

固定区域的容量来自上界假设。外部输入若超过该上界，接口应返回失败而非截断数据（[@def-2.6.2] 的 `Option` 即为此而设）；可选策略包括拒绝、分块、申请拥有缓冲或转入慢路径，每种策略会改变尾延迟和内存峰值。应将失败频率与慢路径成本单独记录，不能只测永远命中池的路径，然后声称池解决了所有分配问题。**本轮只测固定容量内的正常路径**；容量错误由确定性测试覆盖（[@ex-2.7.2]），没有统计其生产概率。

若按历史峰值自动扩容，区域可能永远保留一次异常大请求的内存；若每次收缩，又可能恢复分配抖动。合理策略需要容量分级、归还时机或显式上限；选择策略前应测请求大小分布和并发持有数量——这两项本章都没有采集。不应把微基准中的 262144 字节复制为线上默认参数（2.8.6）。

性能对比前还有一件更基础的事：两种通路的**资源释放时机**是否等价。`fresh_vec` 在每块操作后释放存储，区域在整个批处理期间保留存储；如果业务语义要求每块立即归还全局内存，区域不满足同一需求；如果业务只要求块内容在消费后不再可访问，区域可能满足（[@think-2.6.1]）。因此输出字节相同不一定意味着完整资源语义等价（[@def-1.6.1]）——本章把这项差别明确放在契约里，而不是藏在实现细节中。

### 2.8.10 析构型对象把游标变成资源状态机

::: def 定义 2.8.3 · 资源状态机 resource state machine {#def-2.8.3}

一个复用组件的**资源状态机**至少包含：槽位处于「未初始化 / 已构造 / 已销毁」哪一态、由谁负责推进、失败时回到哪一态。字节的这三种状态是同一件事，所以 `ByteRegion` 的 `reset` 只需要维护游标；一旦存放拥有资源的 `T`，每个槽位都要逐项跟踪。
:::

按[@def-2.8.3]，若区域存放任意拥有资源的 `T`，`reset` 就需要逐项销毁：跳过销毁可能泄漏句柄、计数或其他资源；错误销毁未初始化槽可能直接触发 UB；若 `Drop` 会 panic，还要规定中途失败后的状态。所以把 `u8` 换成泛型 `T` 不是一个局部泛化，它改变了整个资源状态机（[@def-2.6.2] 的第三条限制就是为了不把状态机带进来）。

返回多个存活引用的 arena 还需要更强的别名策略：只要继续分配不移动已有元素，部分地址稳定性问题可能简化，但可变引用之间仍不能重叠；`reset` 需要证明所有借用结束（[@def-2.6.3]），跨线程共享还需要同步与 `Send`/`Sync` 分析。这些都不是一个游标自增表达式能承担的。本章通过有限安全接口明确拒绝这些未完成能力。

### 2.8.11 小结与常见错误

**小结。**① 相对偏移对齐不等于绝对地址对齐，先证明基地址（[@def-2.8.1]、[@ex-2.8.1]）；② 八项要素是设计清单，本章只交付字节区域（[@def-2.6.2]）；③ 布局证明与来源证明是两类，缺一不可（2.8.7、[@think-2.8.1]）；④ 类型对齐与缓存对齐不同，提高 align 会扩大步长（[@def-2.8.2]、[@ex-2.8.2]）；⑤ 泛型化会把游标变成资源状态机（[@def-2.8.3]）。下一节 [2.9 延伸阅读与来源](#sec-cpp-rust.1.2.9) 交代这些结论的出处。

::: errata 常见错误清单（2.8 节）

E-a **只对相对游标取整就宣称对齐。**基地址可能不满足目标对齐（[@ex-2.8.1]）。

E-b **把 `Layout` 输出的偏移当访问权限。**来源与借用是另一份证明（2.8.7、[@ex-2.8.3]）。

E-c **因为本机 cacheline 是 128 就把所有结构填到 128。**步长与常驻都会涨（[@ex-2.8.2]）。

E-d **先建未对齐引用再声称「只拷贝」。**形成引用即已违反要求（2.8.4）。

E-e **把 `u8` 换成 `T` 当局部泛化。**`Drop`、初始化态与失败状态全变了（[@def-2.8.3]）。

E-f **拿微基准的 262144 字节做线上默认值。**请求分布与并发持有数没有测（2.8.9）。

:::

::: method 即时自测 · 2.8

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　按两分法，八项要素哪几项属「布局证明」、哪几项属「来源证明」？

::: sol 第 1 题答案
布局证明：一（align 来源合法）、二（`base+used` 不溢出）、三（上取整不越出地址空间）、四（padding+size 不溢出）、五（新范围属于原分配）。来源证明：六（返回引用前 `T` 已构造有效）、七（借用结束后才可 `reset`）、八（需 `Drop` 的对象有回收路径）。对应 2.8.2 与[@def-2.8.3]。
:::

**第 2 题 · 辨析**　「`Layout::new::<u64>()` 的 align 是 8，所以任何一次 `Vec<u8>` 分配里第 8 个字节都能放 `u64`。」错在哪？

::: sol 第 2 题答案
把语言约束与本机观测接反了：`Layout` 给的是类型对自身起点的**要求**，而 `Vec<u8>` 只承诺 `u8` 级对齐；第 8 个字节处的绝对地址取决于 `base`（[@def-2.8.1]、[@ex-2.8.1]）。要成立必须让实际分配满足组合 `Layout`，或证明绝对地址（2.8.8）。
:::

**第 3 题 · 应用**　把 `Record` 改成 `repr(align(128))`，65536 个元素要多占多少字节？这条改动对哪类通路可能有利、为什么本章不给数字？

::: sol 第 3 题答案
每对象从 64 涨到至少 128 字节，数组多占 65536 × 64 = 4194304 字节（[@ex-2.8.2]）。可能对「多线程分别写不同对象」的争用有利，但本章是单线程读、没有测量伪共享（2.3.4），所以只能列为待测假设（[@def-2.3.2]）。
:::

**第 4 题 · 迁移**　评审里有人说「一次分配头部+载荷比两次分配快」。按本节，你要他先回答哪三个问题？

::: sol 第 4 题答案
① 访问集合：头部热而载荷冷时共置会扩大跨度（[@def-2.3.1]、2.8.8）；② 生命周期与回收：一次分配绑定两者，释放路径怎么设计（2.8.9、[@def-2.8.3]）；③ 分配频率：省下的那一次分配相对总工作量占比多少（[@def-1.1.3]）。三个都答完才谈得上测，而**本章没有为这种结构采集任何数字**。
:::

:::

### 2.9.2 哪些来自母本，哪些来自本机实验

AoS 与热列的性能对比、`ByteRegion` 组件、以及本机 cacheline 的 128 字节查询，都来自本章自己的实验与系统查询，母本没有提供这些。`ByteRegion` 不是母本中某个通用分配器实现的翻写，它的安全边界是本章自己设定的（[@def-2.6.2]）。N−1 标准差、配对 bootstrap 与归档协议沿用第 1 章的实验方法（[@def-1.4.2]、[@def-1.6.2]），不宣称这些细节来自某一份母本。

### 2.9.3 本章没有覆盖的部分

1. **把本机观测当契约带走。**布局尺寸、cacheline 的 128 字节、生成的向量序列、两个 benchmark 的均值，全都属于[@def-2.1.3] 的最后一层；换目标、换编译器版本或换类型参数，它们一起失效（[@ex-2.4.1]）。
2. **把「方向一致」写成「唯一因果」。**跨度、执行形态与耗时三者同时变化，而第二类证据（事件计数）本章一次都没采集（[@def-2.3.2]、[@ex-2.4.1]）；这类错误在 2.3、2.4、2.5 三节里各出现一次，句式却一模一样。
3. **只报收益，不报被换掉的东西。**热列换来的是一致性协议（2.3.5），区域换来的是释放时机与常驻内存（[@think-2.7.1]）；两者的性能数字都没有把这些写进分母。跨章横向排名因此不成立（[@def-1.6.1]）。
4. **把有限组件当成通用方案的跳板。**`ByteRegion` 拒掉的那几项（任意 `T`、任意对齐、多个存活借用、逐项析构）对应 2.8.2 清单没有打勾的那几行（[@def-2.6.2]、[@def-2.8.3]）；从「它省了分配」滑向「所以它是 arena」，是本章最容易被绕过的一步（[@think-2.8.1]）。

## 2.11 本章小结与章末件 {#sec-cpp-rust.1.2.11}

::: note 本章小结

- 布局是三元组：size 决定步长、align 约束存放地址、偏移说明内部位置；任何一句尺寸结论都要先落到语言约束、标准库保证或本机观测这三层之一（[@def-2.1.1]、[@def-2.1.3]）。
- niche 来自载荷的有效值集合，不是运行时压缩；省标签省的是空间，不必然省判断，把无效值拦在构造点比事后检查更可靠（[@def-2.2.1]、[@def-2.2.2]）。
- 地址跨度可以算，搬运字节、cache miss、TLB 事件与带宽都要另外采集；本章只有布局事实与计时结果两类证据（[@def-2.3.1]、[@def-2.3.2]）。
- 本章的 SoA 是热列投影：两个表示在计时前同时存在，转换、更新与峰值内存都不在测量内，所以「0.519 对 0.059」只支持候选场景（[@def-2.4.1]、[@def-2.5.1]）。
- 存储复用的能力边界写在签名里：容量失败返回 `None` 且不动游标、同一时刻只有一个存活借用、`reset` 不清内容；要推广到任意 `T`，还缺绝对地址、来源与析构三份证明（[@def-2.6.2]、[@def-2.8.1]、[@def-2.8.3]）。

:::

### 本章速查

| 问题 | 一句话答案 | 详细位置 |
|:--|:--|:--|
| 只报 size 够不够？ | 不够，align 与偏移一起才构成布局 | [@def-2.1.1] |
| `Vec` 的 24 字节是这条数组的成本吗？ | 那是描述符，元素区另有 524288 字节 | [@def-2.1.2]、[@ex-2.1.1] |
| `Option` 什么时候不带标签？ | 载荷的有效值集合排除了某些位模式时 | [@def-2.2.1] |
| 跨度差 8 倍等于流量差 8 倍吗？ | 不等于，搬运字节要另外采集 | [@def-2.3.1]、[@ex-2.3.1] |
| 本实验的 SoA 是什么？ | 只有热字段列的投影，冷列与转换都没测 | [@def-2.4.1] |
| 0.519 ns/元素是访问延迟吗？ | 是 4.35 ms 摊到 838 万个元素上的批均值 | [@ex-2.5.1]、[@def-1.2.2] |
| `take` 失败了游标动了吗？ | 没有，`checked_add` 与 `get_mut` 都成功才提交 | [@ex-2.6.1] |
| `reset` 等于清零吗？ | 只把 `used` 归零，旧字节仍然可见 | 2.6.5、[@think-2.6.1] |
| 2.81 ns/块 是 malloc 耗时吗？ | 是逻辑块操作成本，含取存储、写入与观察 | [@def-2.7.1] |
| 相对游标上取整算对齐吗？ | 不算，要证明的是 `base + used` 这个绝对地址 | [@def-2.8.1]、[@ex-2.8.1] |
| `Layout` 算出偏移 8 就能放 `u64` 吗？ | 还要基地址满足 align、范围受检、对象已构造 | [@ex-2.8.3]、[@think-2.8.1] |

```bash

```

最后一条运行所有六个入口。不要让手工计时绕过共享锁；输出目录必须新建，避免覆盖原归档（复现协议见[@def-1.8.2]）。不同机器可以得到不同布局与耗时，首先核对语义、尺寸、单位与工作规模。

**布局阅读任务**：用 `offset_of` 核对 COrder 三个字段，再核对 RustOrder，不假定顺序相同；说明 COrder 为何需要尾部填充、`Record` 的 align 为何不是它的 size；说明 `Vec` 描述符与元素区如何分别计入内存预算（[@def-2.1.2]）；指出 `Option<NonZeroU64>` 的保证来自哪里（2.2.2），以及任意 `Option` 尺寸推断为什么不能只靠这一例子（[@def-2.1.3]）。

**实验解释任务**：说明 locality 的 SoA 为何准确说是热列投影（[@def-2.4.1]）、两个表示是否同时存在于进程（[@def-2.5.1]）、转换成本是否计入；说明采样数量接近为何不等于单次成本接近（[@think-2.5.1]）；说明 allocation 的 ns 单位为何不是纯 malloc 延迟（[@def-2.7.1]）、区域预留内存与逐块 `Vec` 生命周期的差别（[@def-2.7.2]）、`reset` 后旧数据为什么仍然合法可见（2.6.5）。

**安全边界任务**：尝试在仍将使用切片时 `reset`，观察编译失败（[@ex-2.6.2]）；不要通过裸指针或延长生命周期绕过这个失败（[@def-2.6.3]）；解释失败如何维护区域复用的有效借用边界，检查容量失败测试是否保持游标（[@ex-2.7.2]）；说明任意类型 arena 还缺少哪些对齐与 `Drop` 义务（2.8.2、[@def-2.8.3]），以及整数地址对齐为何不等于指针拥有访问权限（2.8.7）。

### 当前证据与限制

本章两个入口各有两种 case，每 case 21 个原始批次；共同夹具每 case 至少 500 ms 预热（[@def-1.2.3]）。归档保存源码 SHA、环境、MIR、LLVM IR 与本机汇编，locality 另有独立的 macOS `sample` 证据——它们能核对的是「工作确实发生」，不是机制归因（[@def-1.8.1]、[@def-2.3.2]）。测试没有执行 UB，没有实现未证明的自定义全局分配器，也没有承诺本机结果代表生产 SLA（[@def-2.6.2]）。本章属于探索性一侧，尚需独立技术审计与业务匹配的确认实验（[@def-1.7.3]）。

### 本章导航

**学习目标**：学完这一章，你应该能：

- 报出一个类型的 size、align 与字段偏移，并说出这条结论属于哪一层保证；
