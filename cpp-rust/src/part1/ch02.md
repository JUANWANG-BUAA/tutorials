# 2 对象：布局、热字段与可证明的存储复用

<div class="chapter-index">

**问题主线**：一个对象占多少字节、访问哪些字节、谁承担存储成本，如何共同决定Rust数据通路的性能？

- 区分语言保证、标准库保证与当前编译器观测。
- 用实际偏移、niche和代码生成解释布局，而非依赖想象图。
- 对照AoS与热列投影，限定缓存与向量化归因。
- 用纯安全字节区域复用存储，不包装未经证明的通用分配器。
- 明确容量失败、旧数据、reset借用边界与绝对地址对齐责任。

**实验包**：`bench/foundations-lab/`。

**两个入口**：`src/bin/locality.rs`与`src/bin/allocation.rs`。

**归档**：`bench/foundations-lab/results/native-01/`。

**前置**：[第1章](ch01.md)的计时边界与批均值解释。

## 2.1 类型布局：保证、观测与外部格式 {#sec-cpp-rust.1.2.1}

### 对象尺寸不是有用数据大小

size包含字段与必要填充。
它同时决定同类型数组中相邻元素的步长。
align决定合法存放位置的地址约束。
字段偏移说明对象内部的相对位置。
这三个量共同构成最基本的布局信息。
只报告size会遗漏重要边界。
例如相同size的两个类型可能有不同align。
相同字段集合也可能因为表示方式不同而有不同偏移。

对象的存储位置与逻辑所有权也是两回事。
Vec描述符可以很小，背后元素区却很大。
移动Vec不等于复制元素区。
一个引用本身的尺寸也不包含其所引用数据。
性能分析必须把“句柄”与“承载的数据”分开统计。
否则容易把每对象真实内存成本低估一个数量级。

### Rust默认表示不是声明顺序契约

默认repr允许编译器选择满足约束的字段安排。
不能把一次编译看到的字段顺序写进持久化文件。
不能从Rust字段声明顺序推导网络偏移。
也不能通过裸字节转储建立稳定协议。
编译器版本、目标与类型参数都可能影响布局。
本章不启动布局随机化来生成结果。
但默认布局没有承诺不变，这一点不依赖是否启用随机化。

### 本机探针

完整探针是`examples/layout.rs`。
它调用size_of、align_of与offset_of。
没有读取填充字节。
也没有通过transmute猜测对象表示。
结果来自本轮native构建。

| 类型 | size | align | 本轮含义 |
|:--|--:|--:|:--|
| COrder | 24 | 8 | repr(C)声明顺序与填充 |
| RustOrder | 16 | 8 | 当前默认布局重排 |
| Record | 64 | 8 | 一个热u64与七个冷u64 |
| Option&lt;NonZeroU64&gt; | 8 | 8 | 标准库保证范围内的niche |
| Option&lt;u64&gt; | 16 | 8 | 本机观察，不类推所有枚举 |
| Option&lt;Handle&gt; | 8 | 8 | 透明包装的相应保证 |
| u64切片引用 | 16 | 8 | 本机宽引用观察 |
| Vec&lt;u64&gt; | 24 | 8 | 描述符，不含堆元素 |
| ByteRegion | 32 | 8 | Vec描述符加游标 |

COrder与RustOrder有相同声明字段。
前者带repr(C)，后者使用默认表示。
它们的实际偏移不同。

```rust
#[repr(C)]
struct COrder {
    tag: u8,
    value: u64,
    short: u16,
}

struct RustOrder {
    tag: u8,
    value: u64,
    short: u16,
}
```

COrder偏移依次为0、8、16。
RustOrder偏移依次为10、0、8。
前者尾部还需填充到整体align的倍数。
后者在本轮选择了更紧凑的内部安排。
“更小”不是默认表示永远比repr(C)优越的证明。
它只是当前类型与目标上的实际结果。

### 字段图

<pre class="layout">
COrder, size 24, align 8
0       1              8              16    18          24
| tag   | padding      | value        |short| padding   |

RustOrder, size 16, align 8，本轮观察
0                      8       10  11                  16
| value                | short |tag| padding             |

[私有表示]     [T][T][T] ... [已初始化长度] ... [容量余量]
</pre>

读图：横向位置表示字节偏移，不表示执行先后。
默认布局图只适用于本轮产物。
Vec图描述逻辑状态，不承诺描述符内部字段顺序。
容量余量不能直接当成已初始化T来读取。
后续章节将专门讨论初始化边界。

### repr(C)也不是完整序列化方案

repr(C)约束本目标上的布局算法。
它不自动统一大小端。
它不自动统一不同目标的整型对齐。
它不保证内部Rust字段本身成为C兼容类型。
外层repr(C)不会递归改变内层默认repr。
包含String、Vec或引用的结构仍需要所有权与生命周期协议。
把它直接写成文件也会保存无意义地址。

稳定外部格式应使用显式字段编码。
字节序、长度、版本与校验应逐项定义。
对象布局优化与线格式设计可以采用不同结构。
读入时允许做一次批量转换。
是否值得转换，要把转换成本与后续访问次数一起测量。
本章locality实验不计转换成本。
因此它只回答重复访问阶段的问题。

### 填充不是可以随意利用的隐藏字段

填充字节不是额外用户存储。
编译器可能在移动或赋值时不保留它们。
它们也可能处于未初始化状态。
不能把整个对象当成字节数组做稳定哈希。
不能用memcmp替代字段语义相等。
即使两个对象所有字段相等，填充也未必相同。
性能优化不应建立在未承诺的填充值上。

## 2.2 niche、透明包装与有效值集合 {#sec-cpp-rust.1.2.2}

### niche来自表示空间中的不可用状态

一个类型可能不是每种位模式都有效。
NonZeroU64排除了数值零。
引用也有非空、对齐与有效指向等约束。
枚举可以利用这些不可作为正常载荷的表示。
这样某些Option无需额外存储独立标签。
这不是压缩算法在运行时扫描数据。
而是编译器在表示层利用类型有效值集合。

普通u64的所有位模式都可表示数值。
若再增加None，就需要表达更多逻辑状态。
本轮Option&lt;u64&gt;尺寸为16。
不能由此断言所有载荷大小相同的Option都为16。
表示策略取决于具体类型及保证范围。

### 标准库保证比经验规律更重要

本轮另外核读了std::option的Representation。
它列出某些T的Option具有与T相同的size、align和函数调用ABI。
包括满足相应条件的引用、NonZero、NonNull和函数指针等。
其中Box条目限定为相应Global形式及Sized条件。
透明包装也有明确条件。
这些条件不能在转述时省略。

本章只使用NonZeroU64及其透明包装。
没有依赖任意自定义枚举的内部标签位置。
没有将None转成NonZeroU64。
那样会产生无效值，而不是得到一个可以暂时不用的零。
有效值限制从类型被构造出来时就需要满足。
不等到第一次解引用才检查。

### 一个适合句柄的类型边界

```rust
use std::num::NonZeroU64;

#[repr(transparent)]
struct Handle(NonZeroU64);

fn handle(raw: u64) -> Option<Handle> {
    NonZeroU64::new(raw).map(Handle)
}
```

这里零输入得到None。
非零输入得到有效Handle。
没有unsafe构造器。
调用方不需要知道Option如何利用niche。
它只使用公开类型的安全行为。
内部表示节省可以被编译器利用。
正确性仍建立在构造器维护的有效值上。

### 不能滥用的推论

透明包装不等于所有嵌套枚举都保证不变。
Option保证也不自动扩展为任意Result。
标准库文档只在特定条件下讨论相应优化。
不能从一次size_of结果发明通用泛型定理。
即使两个类型size相同，也不表示可以任意transmute。
对齐、有效值、所有权与析构责任都可能不同。

Option&lt;&amp;T&gt;节省标签，不代表引用可以为空。
None属于Option的表示。
Some内部的引用仍必须有效。
把None按引用类型读取就是跨越了有效值边界。
所谓“底层都是指针”不能消除这项义务。

### 宽指针与元数据

切片引用不仅携带元素地址，还需要长度。
trait对象引用需要与动态类型相应的元数据。
它们的本机尺寸可以通过探针观察。
但不能把内部元数据布局当成稳定C结构。
尤其不要把任意usize伪造成trait对象元数据。
尺寸碰巧匹配不是有效性证明。

对于数组与切片还要分清两个类型。
`[T]`是动态尺寸的元素区域。
`&[T]`是引用描述符。
本章表中的16字节是后者。
它不包含65536个u64本体。
用描述符大小估算热数据工作集会严重失真。

### niche与分支成本

省掉独立标签可能降低对象尺寸。
这可能改善数组密度与缓存使用。
但不自动省去逻辑上的None判断。
机器代码仍可能测试零值或其他模式。
判断是否被消除，需要看调用上下文。
如果上游已经证明一定Some，编译器可能删除判断。
若没有证明，优化器不能凭愿望跳过它。

本章没有为Option访问单独做时序测量。
因此不报告niche带来的纳秒加速。
这里只发布真实size与align探针。
把布局收益转成业务收益还需访问模式实验。
这一点与下一节热字段分析相连。

### 语义类型本身也有价值

NonZero构造边界可以把无效句柄拦在入口。
类型有效值因此更窄。
调用方无需到处重复检查零。
这种设计同时帮助正确性与优化。
但不能为了追求niche把有意义的零状态丢掉。
如果零本来是业务合法值，应使用合适类型表达。
性能表示不能反过来篡改业务定义域。

## 2.3 缓存、TLB与热字段密度 {#sec-cpp-rust.1.2.3}

### 逻辑读取量与实际搬运量

CPU执行一个字段读取，不意味着内存系统只搬运该字段字节。
缓存通常以更大的粒度处理相邻数据。
预取、缓存层次与共享状态都会影响实际流量。
本机sysctl报告cacheline为128字节。
这不是所有架构的统一值。
本章不使用“缓存行一定64字节”的假设。

Record尺寸为64字节。
其中只有第一个u64参与求和。
热字段逻辑有效负载为8字节。
其余56字节在该工作核中不使用。
数组步长仍为64字节。
因此同样元素数下，AoS覆盖的地址跨度较大。
热列投影只需要连续的u64。

### 不能仅凭算术宣称cache miss数量

128字节行在对齐理想时可以容纳两个Record。
但Vec只保证Record所需的8字节对齐。
它不保证分配起点恰好是128字节倍数。
跨行边界与预取也会影响实际访问。
更重要的是，本章重复使用热数组。
不少访问可能命中某层缓存。
因此不能用元素数除以每行元素数，宣称测到了多少miss。

可以计算覆盖的地址跨度。
不能把跨度直接改名为外部内存总读取字节。
本轮AoS元素区为4194304字节。
热列为524288字节。
这个8倍跨度差异是布局事实。
最终0.519对0.059的耗时差异则是实测。
两者相关，但不构成唯一因果证明。

### TLB与页面

更大的地址跨度可能涉及更多页面。
TLB负责缓存地址转换相关信息。
页面大小、TLB层次与替换行为依赖平台。
本章没有采集TLB事件。
也没有用平台API建立大页实验。
因此只把TLB作为需要考虑的机制。
不能把本轮AoS较慢全部归因于TLB。

如果要检验TLB假设，需要控制每页访问模式。
还应控制工作集、步长、预取和总有效工作量。
随机跳转与顺序扫描的实验契约不同。
它们不应混在一张“缓存速度表”中。
没有采集的事件不能由墙钟时间倒算出来。

### 访问模式决定布局价值

只读一个字段时，热列投影通常有更高密度。
若每次都要读取全部字段，AoS可能更方便。
如果对象之间存在复杂依赖，列式拆分还可能增加索引协调。
若多个线程分别写不同列，布局还会影响共享争用。
因此布局选择不是“面向对象与数据导向”的口号竞争。
它是具体访问集合与数据生命期的匹配。

### 顺序与随机的区别

连续扫描容易形成可预测地址序列。
硬件可能重叠多个读取并提前取数。
随机索引会限制这种机会。
同样的对象尺寸，在两种模式下成本可能完全不同。
本章locality只做顺序扫描。
不外推到哈希表、树或图遍历。
这些结构还需要单独控制指针追逐和依赖链。

### 读写集合与共享

读密集工作与写密集工作有不同的系统代价。
写入可能涉及所有权转移和缓存一致性协议。
不同线程改写同一缓存行的不同对象也可能互相干扰。
这通常称为伪共享。
避免伪共享不能只看类型字段是否不同。
还要看实际地址与目标缓存行大小。
本章是单线程读实验，没有测量伪共享。
并发章节会用专门协议研究共享写入。

### 工作集的生命周期

一次构造，多次扫描，适合把转换成本摊薄。
一次构造，只扫描一次，则必须把构造成本算入。
热列更新也需要维持与原对象的一致性。
若数据经常修改，投影可能产生同步负担。
如果投影过期而仍被使用，结果可能语义错误。
布局优化首先需要一份一致性协议。
没有这份协议的加速不应进入业务候选。

### 算力与带宽不能只看单位推断

很小的ns/元素可以来自向量化、缓存命中与多条累加链。
它不是测出内存带宽的直接证据。
若要报告带宽，必须定义搬运字节的模型。
读取有效字段字节与触及地址跨度是两种不同分母。
外部内存流量还可能不同。
本章坚持使用ns/逻辑元素。
没有发布未经计数验证的DRAM带宽。

## 2.4 AoS、SoA与编译器的访问证明 {#sec-cpp-rust.1.2.4}

### 本章SoA的准确范围

实验中的soa是热字段列。
它没有保存七组冷字段列。
因此更准确地说，它是完整SoA中的热列投影。
AoS和热列都在计时前创建。
两者在同一进程中同时存在。
计时仅选择要扫描的表示。
没有测量把现有AoS转换成完整SoA的成本。
也没有比较两种完整数据模型的总内存峰值。

这个限制不削弱扫描问题的答案。
它限制的是能否直接宣布生产数据结构应整体替换。
要做那项决定，还要测构建、更新、删除与索引维护。
本章把这些后续问题单独列出来。

### 两个实际数据通路

```rust
#[repr(C)]
#[derive(Clone, Copy)]
pub struct Record {
    pub hot: u64,
    pub cold: [u64; 7],
}

#[inline(never)]
pub fn sum_aos(input: &[Record]) -> u64 {
    input.iter().fold(0u64, |sum, row| {
        sum.wrapping_add(row.hot)
    })
}

#[inline(never)]
pub fn sum_soa(input: &[u64]) -> u64 {
    input.iter().copied().fold(0u64, u64::wrapping_add)
}
```

Record使用repr(C)是为了让热字段位置易于复核。
不是因为此实验需要调用C。
冷字段初始化为11，保持对象全部合法初始化。
被测核只读取hot。
没有从未初始化冷字段构造虚假的低成本对象。

### 访问图

<pre class="layout">
AoS:
[hot0 cold0........][hot1 cold1........][hot2 cold2........]
  |                    |                    |
  +------读取----------+------读取----------+

热列投影:
[hot0][hot1][hot2][hot3][hot4][hot5][hot6][hot7]
  +---------------连续加载与归约----------------+

转换/更新协议：本实验不计时，真实应用必须另测
</pre>

读图：竖线是逻辑读取的位置。
AoS的冷字节仍占地址跨度。
热列图不是声称对象的其他信息已经不存在。
它只显示当前工作核需要的列。

### 本机代码生成

AoS主体保留每64字节一个u64的读取。
循环一次展开多个这样的读取。
SoA主体使用连续向量加载与多条向量累加链。
这表明性能差异不只有数据跨度因素。
编译器选择的执行形态也不同。
因此本章不把全部差距命名为“缓存惩罚”。

| 入口/边界 | 实际产物 | 能支持的机制判断 |
|:--|:--|:--|
| sum_aos | 标量加载，64字节步长 | 热字段读取稀疏 |
| sum_soa | q寄存器成对加载与向量加 | 连续列形成批量归约 |
| sum_iter | LLVM符号别名到sum_soa | 相同核被合并 |
| 切片参数 | LLVM readonly与noalias属性 | 当前后端使用了引用约束 |
| Record ABI | 仅通过切片访问 | 不建立跨语言按值传递保证 |

这里的noalias是当前生成代码属性。
不是本章对所有Rust别名规则的完整形式定义。
尤其不能用它为不合法的重叠引用背书。
合法输入的证明仍来自Rust借用与接口契约。

### 本机汇编片段

SoA的关键循环中可见以下加载与累加。
省略循环控制与尾部处理。

```asm
ldp q4, q5, [x8, #-32]
ldp q6, q7, [x8], #64
add.2d v0, v4, v0
add.2d v1, v5, v1
add.2d v2, v6, v2
add.2d v3, v7, v3
```

AoS可见不同步长。

```asm
ldur x15, [x13, #-128]
ldur x16, [x13, #-64]
ldr x17, [x13]
ldr x15, [x13, #64]
add x13, x13, #256
```

这些片段只用于定位差异。
完整符号才包含入口、尾部与返回。
不能由六行片段计算完整调用周期。
也不应把当前指令选择推广为所有aarch64后端行为。

### 改成读取全部字段会怎样

那将是另一项实验。
应让两种表示都读取同样逻辑字段。
SoA需要相应的多个列。
输出校验也要覆盖全部字段。
不能用当前只读hot的结果预言它一定更快。
同样，若只访问少量随机对象，AoS局部聚合可能更合适。
布局没有脱离访问集合的绝对优胜者。

## 2.5 benchmark一：热列扫描的实测边界 {#sec-cpp-rust.1.2.5}

### 完整入口

以下是`src/bin/locality.rs`的完整代码。
公共核与夹具位于`src/lib.rs`。
输入的两个表示在计时外创建。
校验值只依赖热字段。

```rust
use foundations_lab::{Case, N, Record, data, run, sum_aos, sum_soa};
use std::hint::black_box;

fn main() {
    let hot = data(N);
    let aos: Vec<_> = hot.iter().map(|&hot| Record {
        hot,
        cold: [11; 7],
    }).collect();
    let expected = hot.iter().fold(0u64, |a, &b| a.wrapping_add(b));
    let mut cases = [
        Case {
            name: "aos",
            work: Box::new(|| sum_aos(black_box(&aos))),
            expected,
        },
        Case {
            name: "soa",
            work: Box::new(|| sum_soa(black_box(&hot))),
            expected,
        },
    ];
    run(&mut cases, 128, N);
}
```

每次调用处理65536个逻辑元素。
每批重复128次。
每case预热至少500ms。
正式21轮中轮转先后位置。
夹具保存每次调用的输出。
批后逐个比较参考值。
打印与统计不在正式计时区间。

|:--|--:|--:|--:|--:|

### 可以保留的结论

在固定热数组顺序扫描下，热列单位成本较低。
AoS的读取跨度更大。
本机SoA生成了连续向量归约路径。
这三项证据互相一致。
它们支持把“只读少数字段”作为布局重构的候选场景。
但还没有测出完整业务转换收益。

### 不能保留的结论

不能宣称所有AoS一定比SoA慢。
不能宣称本轮精确测到了L1、L2或TLB miss差异。
不能宣称扫描结果可以直接预测随机查询。
不能宣称冷数据永远不应保存在对象中。
也不能把热列数组的524288字节当成整个业务状态大小。
完整业务状态还需要其他字段与索引。

### 安全性能回退案例

把热字段与大量冷字段绑在一起，不会违反Rust内存安全。
它却可能使热扫描退化。
本实验用安全Rust实际重现了这个问题。
不存在故意越界或数据竞争。
回归的对象是当前访问通路，不是类型定义本身的道德好坏。
修复候选是热列投影、热冷拆分或改变访问批量。
每一种修复都需要重新检查一致性成本。

### 语义回归测试

`sums_and_representations_agree`对多个长度建立两种表示。
每种表示都从相同hot值生成。
它要求sum_aos与sum_soa相等。
还覆盖非向量整块长度。
这避免把尾部遗漏误当作性能收益。
若以后修改Record字段，测试应继续保持逻辑输入一致。
不能通过缩短某一分支实际处理的数据量获得漂亮数字。

### profiler支持的范围

独立`sample-locality.txt`中同时出现sum_aos与sum_soa。
它们在预热阶段分别占用约固定墙钟时间。
所以采样数量接近不表示两种实现单次成本接近。
预热策略本来就按时间而非调用数运行。
这是采样协议与计时协议必须一起解释的例子。
本章不把该报告换算成每元素CPU周期。

### 怎样继续做确认实验

首先加入完整字段读取版本。
其次加入构建与转换成本。
再次加入代表性随机访问。
最后加入更新与删除的一致性维护。
每一项都应独立命名输入、计时边界与输出校验。
不能把不同问题混在一个总“layout benchmark”数字里。
本轮只完成热字段扫描这一项。

## 2.6 分配成本、容量与安全字节区域 {#sec-cpp-rust.1.2.6}

### 分配器不是一个固定延迟函数

一次Vec创建可能经过不同大小类与缓存路径。
系统分配器可能复用已释放块。
较大请求可能走不同的后端。
页面首次触及也可能在初始化阶段才体现。
线程局部缓存、跨线程释放与碎片都会影响成本。
因此“malloc固定需要多少纳秒”不是通用事实。
本章只比较具体生命周期。

一条路径反复创建64字节Vec、填充、观察、销毁。
另一条路径复用预先初始化的字节区域。
两者不只是分配器算法不同。
它们改变了分配频率与存储生命周期。
区域的初次构造不进入每批计时。
这一点必须写在性能表旁边。

### 本章组件不是通用arena

ByteRegion存储一个已初始化Vec&lt;u8&gt;。
take只返回该Vec内部的可变字节切片。
它不构造任意T。
不提供任意align请求。
不实现GlobalAlloc。
也不允许调用方同时保留多个take结果后继续分配。
因为take借用整个self为可变。
前一个切片的有效使用会阻止下一次take。

这种限制使证明简单。
它适合逐个填充并消费短暂字节块的通路。
不适合需要长期保存多个对象引用的图结构。
如果业务需要后者，应选择更强的已有容器或补全专门证明。
不要把一个安全而有限的组件宣传成通用分配器替代品。

### 完整组件

```rust
pub struct ByteRegion {
    storage: Vec<u8>,
    used: usize,
}

impl ByteRegion {
    pub fn new(capacity: usize) -> Self {
        Self {
            storage: vec![0; capacity],
            used: 0,
        }
    }

    pub fn take(&mut self, len: usize) -> Option<&mut [u8]> {
        let end = self.used.checked_add(len)?;
        let result = self.storage.get_mut(self.used..end)?;
        self.used = end;
        Some(result)
    }

    pub fn reset(&mut self) {
        self.used = 0;
    }
}
```

这里没有unsafe块。
越界由get_mut拒绝。
整数溢出由checked_add拒绝。
失败发生在更新游标之前。
因此容量失败不消耗剩余空间。
这是一项明确的事务性行为。

### 生命周期如何限制reset

返回切片的生命周期绑定到可变self借用。
若切片后续仍被使用，调用reset需要的第二个可变借用不能成立。
这使“reset期间不存在仍将被使用的旧借用”由接口表达。
不是注释中请求调用方自觉遵守。
包中compile-fail文档测试验证这个拒绝案例。
它在编译阶段失败，不执行任何危险运行。

```rust,compile_fail
let mut region = ByteRegion::new(64);
let slice = region.take(4).expect("capacity");
region.reset();
slice[0] = 3;
```

这不是说切片变量必须在词法上消失。
现代借用分析关注后续使用。
若切片已经不再使用，借用可以结束。
此时reset可以合法进行。
第3章将把词法作用域与有效借用区间进一步分开。

### reset不等于擦除

reset只把used设为0。
旧字节仍保留在storage中。
下一次take可以观察这些旧字节。
测试明确验证这一行为。
这适合已知会覆盖全部有效内容的内部缓冲。
不适合把“新取到切片必定为零”当成安全需求的调用者。
也不能用于未经设计的敏感数据清理承诺。

若需要清零，应显式增加清理策略。
清理成本应计入相应生命周期。
不能一边依赖“复用不清零”的速度，一边声称等价于每次新建零缓冲。
本章benchmark会在读取前fill(7)。
因此它不依赖旧内容为零。

## 2.7 benchmark二：小缓冲生命周期与区域复用 {#sec-cpp-rust.1.2.7}

### 工作契约

每次工作核进行4096个逻辑块操作。
每块长度64字节。
每块先填充7，再把首字节加入校验。
整个切片经black_box观察，避免只保留单字节初始化。
fresh_vec每块创建并销毁独立Vec。
byte_region每次工作核reset一次，并依次取出短暂切片。
每批调用工作核16次。
单位为ns/逻辑块操作。
不是纯分配调用延迟。

### 完整入口

完整代码位于`src/bin/allocation.rs`。
这里保留全部业务路径与参数。
统计与预热使用同包公共夹具。

```rust
use foundations_lab::{ByteRegion, Case, run};
use std::hint::black_box;

const COUNT: usize = 4096;
const LEN: usize = 64;

fn main() {
    let mut region = ByteRegion::new(COUNT * LEN);
    let mut cases = [
        Case {
            name: "fresh_vec",
            expected: (COUNT * 7) as u64,
            work: Box::new(|| {
                let mut sum = 0;
                for _ in 0..COUNT {
                    let mut bytes = vec![0u8; black_box(LEN)];
                    bytes.fill(7);
                    sum += u64::from(black_box(&bytes)[0]);
                }
                sum
            }),
        },
        Case {
            name: "byte_region",
            expected: (COUNT * 7) as u64,
            work: Box::new(|| {
                region.reset();
                let mut sum = 0;
                for _ in 0..COUNT {
                    let bytes = region.take(black_box(LEN))
                        .expect("fixed capacity");
                    bytes.fill(7);
                    sum += u64::from(black_box(bytes)[0]);
                }
                sum
            }),
        },
    ];
    run(&mut cases, 16, COUNT);
}
```

expected为28672。
正式夹具逐次验证返回值。
容量COUNT×LEN恰好覆盖一次工作核。
每次工作核开始前reset。
失败不是被测常态路径。
容量失败另外由测试验证。

### 本轮结果

来源为`results/native-01/allocation.csv`。
每case有21个原始批均值。
单位是ns/64字节块生命周期操作。

| case | mean | N-1 sd | 批p50 | 批p99 |
|:--|--:|--:|--:|--:|
| fresh_vec | 8.248312814 | 0.173203503 | 8.246734619 | 8.638381958 |
| byte_region | 2.813854399 | 0.027682164 | 2.817779541 | 2.855300903 |

区域减fresh_vec的配对均值为-5.434458415。
bootstrap区间为[-5.514596121, -5.358680362]。
这支持当前短暂块通路中的复用收益。
不支持把2.81称为任意对象分配耗时。
也不支持宣称自制区域优于所有系统分配器。

### 哪些工作被省去了

区域不为每块调用全局分配与释放。
它提前持有一整段已初始化存储。
它也不在reset时擦除旧数据。
这些都是接口语义变化带来的收益来源。
fresh_vec的零初始化可能被后续覆盖与优化改变。
实际后端行为不能仅从宏表面推断。
本章不声称逐字节测出了哪部分初始化被消除。

### 哪些成本被移出边界

区域最初的Vec创建在计时外。
区域最终的Vec销毁也在计时外。
如果请求只用一次区域，必须把这些成本加回来。
如果区域长期占用而使用率很低，还可能增加常驻内存。
当前区域容量为262144字节。
这是整个工作核的预留存储，不是每块新分配大小。
比较时应同时报告生命周期与内存预留。

### 该组件适用的实际工作形态

同步批处理中逐块编码并立即交付，是一种可能形态。
每个切片消费完成后再取下一块。
若接收方异步持有数据，当前接口就不匹配。
不能把借用强行延长成static来绕过它。
应该改为转移拥有缓冲、使用分块池或采用有界共享所有权。
这些方案有不同的内存和同步成本。
应单独测量，而不是偷偷把当前区域改成裸指针接口。

### 安全失败用例

测试先从8字节区域取6字节并填7。
接着请求3字节，应返回None。
再请求usize::MAX，也应返回None。
最后请求2字节，应成功。
这证明两种失败没有改变游标。
reset后再次取6字节，读到此前的7。
这同时验证“不擦除”的真实契约。

```rust
let mut region = ByteRegion::new(8);
region.take(6).expect("fits").fill(7);
assert!(region.take(3).is_none());
assert!(region.take(usize::MAX).is_none());
assert_eq!(region.take(2).expect("cursor preserved"), [0; 2]);
region.reset();
assert_eq!(region.take(6).expect("reusable"), [7; 6]);
```

容量失败是正常可恢复结果。
benchmark里的expect只验证固定夹具配置。
生产接口可直接处理None并实施回退策略。
不能把固定输入下不会失败的假设推广到外部请求。

## 2.8 对齐、分配器边界与布局重构决策 {#sec-cpp-rust.1.2.8}

### 为什么不从字节区域直接返回任意T

Vec&lt;u8&gt;只要求u8对齐。
即使某次系统分配碰巧高度对齐，也不是接口保证。
把区域相对游标向上取整，不等于绝对地址对齐。
如果基地址未对齐，整齐的偏移仍会得到错误地址。
通用arena必须基于绝对地址计算可用位置。
还要处理加法溢出、容量、初始化与销毁。

设基地址为base，当前游标为used。
待放置地址是base+used。
应先检查加法是否溢出。
然后按目标align求上取整位置。
最后确认对象完整落在分配内。
这个过程不能靠无检查位运算拼成“高性能代码”。
语言的布局约束不会因benchmark需要速度而放宽。

### 绝对地址对齐的证明要素

第一，align必须来自合法Layout或等价受检参数。
第二，base与used相加不能溢出。
第三，向上取整不能越出地址空间。
第四，padding与size相加不能溢出。
第五，新范围必须完全属于原分配。
第六，返回引用前必须已构造有效T。
第七，后续reset不能发生在仍需使用的借用期间。
第八，所有需要Drop的对象必须有明确回收路径。

这些要素是设计清单，不是本章已经实现的通用arena。
本章刻意只实现字节切片区域。
因此不需要伪装为完整的类型化分配器。
有限组件的诚实边界优于未经证明的通用接口。

### ZST与空请求

零尺寸类型可能没有实际字节载荷。
但引用仍有非空、对齐等要求。
不能用null构造一个“反正不访问”的引用。
类型化容器还需要处理逻辑元素数量与析构次数。
即使每个元素size为0，Drop也可能有可观察效果。
本章ByteRegion只接受字节长度。
take(0)的行为由安全切片接口维护。
不把它类推为任意ZST对象工厂。

### 分配与初始化的拆分

分配得到的是存储，不自动意味着存在有效对象。
Vec容量与长度正是这种区分的一个安全封装。
长度范围内必须存在合法T。
容量余量可以还没有T。
第3章会讨论为什么set_len越过初始化边界会出错。
本章不为速度调用set_len。
所有字节都由vec![0; capacity]合法初始化。

### packed并非免费压缩

降低对齐可能减少填充。
但字段可能位于不满足其自然对齐要求的位置。
形成普通引用就可能违反要求。
不能先创建未对齐引用，再声称稍后只做拷贝。
若必须处理紧凑外部格式，应使用字节解析或合适的未对齐访问接口。
还要判断目标上未对齐访问的实际成本。
本章没有运行packed性能实验。
因此不给它填入“典型惩罚”数字。

### 缓存对齐与类型对齐不同

repr(align(128))可以提高某类型的对齐要求。
它也可能扩大数组步长与内存占用。
缓存行大小是目标观测，不是Rust类型系统自动理解的业务语义。
提高对齐有时减少共享，有时浪费容量。
不能因为本机cacheline为128，就把所有结构都填充到128。
读密集紧凑对象可能因此变慢。
并发写对象才可能需要另一种权衡。

### 从实验到设计的决策表

| 业务约束 | 候选布局/存储 | 必须新增的验证 |
|:--|:--|:--|
| 反复顺序读取少数字段 | 热列或热冷拆分 | 转换与一致性维护 |
| 单对象全字段处理 | AoS | 随机索引与对象密度 |
| 短暂同步字节块 | ByteRegion式复用 | 覆盖旧内容与容量回退 |
| 异步持有多个块 | 拥有缓冲或有界池 | 回收、取消和上界 |
| 任意类型长期借用 | 已验证的类型化容器 | 对齐、Drop、别名与reset |
| 跨语言外部布局 | 明确repr及C ABI协议 | 双边布局与所有权测试 |

### 不要让内存峰值消失在平均值里

复用池可能让每次操作更快。
它也可能长期保留峰值容量。
若每条连接都保留一个大区域，连接数会放大内存成本。
因此系统预算应包括常驻、峰值与突发分配。
本章没有多连接工作负载。
262144字节区域只是实验配置。
不是每请求或每线程的通用推荐值。

### 对齐证明与provenance

即使整数地址满足模对齐，也不代表它拥有访问权限。
指针必须源自适当分配，并在该分配生命周期内。
邻接的两次分配也不能因为地址连续就合并成一个切片。
这部分将在第3章展开。
布局计算解决“放在哪里合适”。
来源与借用解决“是否有权把它当成对象访问”。
两类证明缺一不可。

### 用受检Layout规划组合存储

新增的`examples/storage_plan.rs`演示布局计算而非分配。
它把一个u8布局与一个u64布局组合。
extend返回组合布局及第二个成员的偏移。
pad_to_align把整体尺寸补到对齐倍数。
这比手写无检查的上取整表达式更适合维护溢出边界。
程序没有构造裸指针，也没有分配对象。

```rust
use std::alloc::Layout;

fn main() -> Result<(), std::alloc::LayoutError> {
    let tag = Layout::new::<u8>();
    let value = Layout::new::<u64>();
    let (combined, value_offset) = tag.extend(value)?;
    let padded = combined.pad_to_align();
    println!(
        "value_offset={value_offset} size={} align={}",
        padded.size(),
        padded.align()
    );
    assert_eq!(value_offset, 8);
    assert_eq!(padded.size(), 16);
    assert_eq!(padded.align(), 8);
    assert!(Layout::array::<u64>(usize::MAX).is_err());
    let zst = Layout::array::<()>(100)?;
    assert_eq!(zst.size(), 0);
    assert_eq!(zst.align(), 1);
    println!(
        "overflow=rejected zst_size={} zst_align={}",
        zst.size(),
        zst.align()
    );
    Ok(())
}
```

该程序在本机实际编译和执行。
结果位于`results/validation-01/storage-plan.txt`。
组合后的偏移为8，尺寸16，对齐8。
超大u64数组请求被拒绝。
100个单元值的布局size为0、align为1。
这些是布局规划结果，不是实际内存消耗测量。

Layout规划仍有范围边界。
它给出的是相对于一个满足整体align的基地址的偏移。
若底层只有u8对齐保证，不能直接套用该偏移返回u64引用。
必须让实际分配满足组合Layout。
或者在现有分配中计算绝对地址并证明所有范围约束。
本章只演示前半份规划，不实现后半份unsafe放置。
把两份证明分开，可以防止“算出了8，所以地址安全”的错误。

### 组合布局与字段可见性

手工组合存储常用于头部加尾部载荷。
头部可能记录长度、状态与回收信息。
尾部可能是动态大小元素区。
这种结构需要同时规划头部、元素步长与总长度。
字段布局正确并不表示尾部元素已经初始化。
头部中记录的长度也必须与实际初始化状态一致。
若头部提前发布了完整长度，其他访问者可能读取未构造元素。
因此布局规划应与初始化状态机一起审查。

把头部与载荷放在一次分配中可能减少分配次数。
但它也会绑定两者生命周期。
如果头部很热而载荷很冷，共置可能扩大热访问跨度。
如果头部跨线程共享，布局还可能引入缓存行争用。
一次分配不是天然优于两次分配。
需要看分配频率、访问模式和回收路径。
本章不为这种未实现结构发布加速数字。

### 区域复用与容量治理

固定区域的容量来自上界假设。
外部输入若超过该上界，接口应返回失败而非截断数据。
可选策略包括拒绝、分块、申请拥有缓冲或转入慢路径。
每种策略会改变尾延迟和内存峰值。
应将失败频率与慢路径成本单独记录。
不能只测永远命中池的路径，然后声称池解决了所有分配问题。
本轮只测固定容量内的正常路径。
容量错误由确定性测试覆盖，没有统计其生产概率。

若按历史峰值自动扩容，区域可能永远保留一次异常大请求的内存。
若每次收缩，又可能恢复分配抖动。
合理策略需要容量分级、归还时机或显式上限。
选择策略前，应测请求大小分布和并发持有数量。
不应把微基准中的262144字节复制为线上默认参数。

### 析构型对象与区域reset

字节没有用户自定义Drop。
这使ByteRegion的reset只需要维护游标。
若区域存放任意拥有资源的T，reset就需要逐项销毁。
若跳过销毁，可能泄漏句柄、计数或其他资源。
若错误销毁未初始化槽，可能直接触发UB。
若Drop会panic，还要规定中途失败后的状态。
所以把u8换成泛型T不是一个局部泛化。
它改变了整个资源状态机。

返回多个存活引用的arena还需要更强的别名策略。
只要继续分配不移动已有元素，部分地址稳定性问题可能简化。
但可变引用之间仍不能重叠。
reset需要证明所有借用结束。
跨线程共享还需要同步与Send/Sync分析。
这些都不是一个游标自增表达式能承担的。
本章通过有限安全接口明确拒绝这些未完成能力。

### 对比实验的生命周期等价性

fresh_vec在每块操作后释放存储。
区域在整个批处理期间保留存储。
如果业务语义要求每块立即归还全局内存，区域不满足同一需求。
如果业务只要求块内容在消费后不再可访问，区域可能满足。
因此性能对比前，应先比较资源释放时机的要求。
输出字节相同不一定意味着完整资源语义等价。
本章把这项差别明确放在契约中，而不是藏在实现细节里。

## 2.10 常见陷阱 {#sec-cpp-rust.1.2.10}

1. **把默认repr字段顺序写进外部格式。**
   本轮RustOrder的实际顺序就不同于声明顺序。
   使用显式编码或受控布局协议。

2. **只看size而忽略align与offset。**
   相同尺寸不能证明相同访问要求。
   三者都应进入布局证据。

3. **把Option的niche经验推广到所有T。**
   标准库保证有明确类型与条件。
   未列出的类型只可记录当前观察。

4. **认为None可以按其内部引用读取。**
   Option的合法None不构成合法引用。
   有效值边界必须保持。

5. **认为缓存行永远是64字节。**
   本机查询为128字节。
   目标数据应查询并记录，不能写成普遍规律。

6. **把AoS与热列差距全称为cache miss。**
   生成代码也有标量与向量路径差异。
   本轮没有采集PMU事件。

7. **用热扫描结果推荐所有业务改成SoA。**
   构建、更新、随机查询与全字段读取没有计入。
   必须补齐真实访问集合。

8. **把ByteRegion当成通用arena。**
   它只提供短暂字节切片。
   不构造任意类型，也不支持长期多借用。

9. **只对相对游标取整就宣称对齐。**
   基地址可能不满足目标对齐。
   类型化放置需要绝对地址证明。

10. **把reset当成清零。**
    本组件只重置游标。
    旧字节可见，安全需求必须另设清理协议。

11. **容量失败仍更新游标。**
    这会破坏后续可用空间与重试语义。
    checked_add与get_mut成功后才提交游标。

12. **用对象原始字节做稳定哈希。**
    填充可能不稳定或未初始化。
    字段语义相等不等于整个表示字节相等。

13. **看见更高对齐就认为一定更快。**
    更高对齐可能增加步长与常驻内存。
    缓存局部性与共享写入必须分别测量。

不同机器可以得到不同布局与耗时。
首先核对语义、尺寸、单位与工作规模。

### 布局阅读任务

用offset_of核对COrder三个字段。
再核对RustOrder，不假定顺序相同。
说明COrder为何需要尾部填充。
说明Record的align为何不是其size。
说明Vec描述符与元素区如何分别计入内存预算。
指出Option&lt;NonZeroU64&gt;的保证来自哪里。
指出任意Option尺寸推断为什么不能只靠这一例子。

### 实验解释任务

说明locality的SoA为何准确说是热列投影。
说明两个表示是否同时存在于进程。
说明转换成本是否计入。
说明采样数量接近为何不等于单次成本接近。
说明allocation的ns单位为何不是纯malloc延迟。
说明区域预留内存与逐块Vec生命周期的差别。
说明reset后旧数据为什么仍然合法可见。

### 安全边界任务

尝试在仍将使用切片时reset，观察编译失败。
不要通过裸指针或延长生命周期绕过这个失败。
解释失败如何维护区域复用的有效借用边界。
检查容量失败测试是否保持游标。
解释任意类型arena还缺少哪些对齐与Drop义务。
说明整数地址对齐为何不等于指针拥有访问权限。

本章两个入口各有两种case，每case21个原始批次。
共同夹具每case至少500ms预热。
归档保存源码SHA、环境、MIR、IR与本机汇编。
locality另有独立macOS sample证据。
测试没有执行UB。
没有实现未证明的自定义全局分配器。
没有承诺本机结果代表生产SLA。
尚需独立技术审计与业务匹配的确认实验。
