## A 组 · 概念（1–7）

::: ex A1 · 两个观测对象（主线 ①） {#ex-13.A.1}

同事说「CPU 占用不高，但接口很慢，所以瓶颈在等待」。这句话里的 CPU 占用与「慢」各是什么观测对象？要确认等待，还需要哪一类观测，为什么 CPU flamegraph（火焰图）不能代替它？

::: sol 解答

CPU 占用是运行样本一侧的指标，慢是批次或请求的墙钟；两者不是同一个统计量。CPU 低但响应慢，需要的是等待阶段、排队与资源就绪时间，也就是执行分解里的「主动等待／外部等待／就绪未运行」。只采运行栈的 CPU 图拿不到线程不运行时的区间，所以它几乎必然给出误导。对照[定义 13.1.1](ch13.md#def-13.1.1)、[定义 13.1.2](ch13.md#def-13.1.2)。
:::

:::

::: ex A2 · 一个 duration 字段能支持哪一层（主线 ①） {#ex-13.A.2}

服务在响应体里加了 `{"duration_ms": 128}`。它能支持五层证据里的哪一层？不能支持哪几层？要补齐至少要在哪些位置记时间戳？

::: sol 解答

只支持第一层业务现象：批次墙钟有了数值，可以和输入规模、正确性一起读。第二层执行分解支持不了，128 ms 里运行、就绪未运行、主动等待、外部等待各占多少，一个字段恢复不出来。第三层的两条采集路径也不成立：既没有栈观察，也没有阶段时间戳，只有起点与终点的差。

补齐至少要在「进入系统」「真正开始」「资源就绪」「完成并可观察」四处记录，并带一个能跨线程识别同一请求的相关标识。对照[思考 13.1.1](ch13.md#think-13.1.1)。
:::

:::

::: ex A3 · 描述还是假设（主线 ③） {#ex-13.A.3}

两条陈述：A「profile 里 `parse` 最宽，所以它是批次完成时间的根因」；B「`parse` 每次调用被观察到很多次，把 `parse` 换成不解析直接取缓存后批次墙钟不变，说明它的宽度不进入用户等待」。哪一条是描述、哪一条是可反驳假设？要否定 B 需要什么证据？

::: sol 解答

A 是描述：它把「被观察到很多次」直接写成「是根因」，中间没有可检查的预测，也无法被任何结果否定。B 是假设：它给出机制（缓存路径不需要解析）、预测（替换后批次墙钟不变）和检验对象（批次墙钟）。

要否定 B，最直接的证据是保持输入与业务输出不变，替换 `parse` 后批次墙钟显著下降；或者发现替换后 `parse` 的工作被搬到了别处，说明观测对象已被换掉。对照[定义 13.1.3](ch13.md#def-13.1.3)、[例 13.1.1](ch13.md#ex-13.1.1)。
:::

:::

::: ex A4 · 1698、1082 与 616（主线 ②） {#ex-13.A.4}

本轮 CPU 采样根计数 1698，`mix` 叶子 1082，`compute` 自身叶子 616。有人报「共 3396 个工作样本，`mix` 占 32%」。错在哪一步？`mix` 的正确分母是什么？这个分母能不能读成 CPU 时间？

::: sol 解答

错在把不同层级的表示相加。1698 是根的观察总数，1082 与 616 是它的两个叶子划分，1082＋616＝1698；再加一次根，就是把每条观察数了两遍。

正确写法是 `mix` 占主线程观察的 1082／1698，`compute` 自身占 616／1698，两者互斥、和为 100%。1698 是主线程根观察数，不是 CPU 时间、周期数或业务工作量。对照[例 13.2.1](ch13.md#ex-13.2.1)。
:::

:::

::: ex A5 · 三个 0 不是同一件事（主线 ②） {#ex-13.A.5}

一次 `perf stat` 的三行都显示 0：`cache-misses`（事件受支持，工作集很小）、某个厂商原始事件编码（当前内核不认得）、`instructions`（同时请求的事件多于槽位，整段没被调度）。三行能合并写成「本轮 miss 与指令数为零」吗？各应怎么记？

::: sol 解答

不能合并。第一行是数据值，可以进结论，但要连同工作集规模一起写；第二行是能力信息，应记为「不支持」，并保留工具错误输出原文；第三行是采集状态，应记为「未运行」，同时记录 `time_enabled`／`time_running`，说明这条线没被观测覆盖。

合并会带来三层破坏：读者把「无法测量」读成「测得为零」；以这些数为分母的 IPC（每周期执行指令数）、miss 率会算出无意义的值；日后重跑时第 2、3 行的状态可能变化，新旧表对不上。对照[定义 13.3.3](ch13.md#def-13.3.3)、[例 13.3.1](ch13.md#ex-13.3.1)。
:::

:::

::: ex A6 · 两份折叠数据的四问（主线 ②） {#ex-13.A.6}

本轮折叠表：CPU 运行根 1698、2 条叶子路径，`mix` 1082、`compute` 616；waiting 运行根 1648、5 条叶子路径，`__semwait_signal` 1443、`mix` 181。回答四件事：为什么叶子路径数不同？1443／1648 与 1082／1698 能相减吗？各归一化到 100% 会丢什么？权重能写成 CPU 时间占比吗？

::: sol 解答

① 叶子路径数是被观察到的互斥叶子个数，不是采集器参数；CPU 运行的观察集中在 `compute` 与 `mix` 两个叶子，waiting 运行分布在睡眠栈、`mix`、`compute` 等 5 条路径上。

② 不能相减。它们属于两份不同运行中的不同分支：一个是 CPU 夹具，一个是加了主动等待的夹具，两个分母来自两次独立进程启动。

③ 丢失总量差异：1698 与 1648 这两个根观察数不再可见，读者会把「份额增加」读成「绝对成本增加」。

④ 不能。权重是线程栈快照的观察条数；本轮没有采集核心周期或运行时长，`__semwait_signal` 恰恰是睡眠路径。对照[例 13.4.1](ch13.md#ex-13.4.1)。
:::

:::

::: ex A7 · 同 checksum 夹具与三种模式（主线 ③） {#ex-13.A.7}

13.5 的 CPU 分支与 wait 分支、13.6 的 none／batch／each 三模式，为什么都算同 checksum 诊断夹具？它们各自只改变了哪一个因素？batch 相比 each 放弃了什么？

::: sol 解答

两组都共享完全相同的业务工作核与输出，checksum 必须相等；差异只能来自被研究的那个因素。13.5 只改变「一段主动等待」：CPU 分支执行 1000000 次递推，wait 分支执行同样递推后再申请 40 ms 线程睡眠。13.6 只改变观测方式：none 不记录逐项观测，batch 在批末提交总步数，each 对每步读时钟、构造事件并提交原子计数。

batch 保留总数 200000，但丢失逐项分布；它不能回答「每个异常请求卡在哪一步」。对照[定义 13.5.1](ch13.md#def-13.5.1)、[定义 13.6.1](ch13.md#def-13.6.1)。
:::

## B 组 · 推理（8–15）

::: ex B8 · 32.832639 是什么（主线 ②） {#ex-13.B.8}

13.6 表中 none 均值 2.472857、each 均值 32.832639，单位 ns/聚合 step，每批 200000 步，checksum 相同。有人写：「一次打点约 32.8 纳秒；把 32.832639 减 2.472857 得 30.359782，这就是打点的净成本。」两句话各错在哪？

::: hint 提示

先看分子是一步还是一整批；再问这个减法需要什么假设。

:::

::: sol 解答

第一句错在把聚合值当单次事件延迟。32.832639 是整批墙钟除以 200000 步的合成值，含时钟、事件屏障、计数与循环形状变化，既不是单次事件延迟，也没有分位数。

第二句错在假设可加性。插桩改变寄存器压力（同时要保活的临时值太多）、内联（函数体被直接放进调用者）与循环优化机会，还改变运行时长与调度机会；要拆出「净成本」需要额外的可加性假设，对极轻量循环尤其危险。本章只报告两套真实程序的总体差异。对照[例 13.6.1](ch13.md#ex-13.6.1)、[定义 13.6.2](ch13.md#def-13.6.2)。
:::

:::

::: ex B9 · 0.002817 是收益还是噪声（主线 ③） {#ex-13.B.9}

none 的均值 2.472857、sd 0.094581；batch 的均值 2.470040、sd 0.079995。两者只差 0.002817，约 0.11%。有人据此写「batch 优化了业务核」。这个结论能成立吗？给出你的判据。

::: sol 解答

不能。0.002817 ns/step 约合 0.11%，小于两列任一批次标准差（0.094581 与 0.079995）；这点差异落在批次波动之内，不能当收益。判据是差异与批间波动、样本数的关系，而不是「小数点后还有数」。batch 的价值在保住总数、放弃逐项分布，不在加速业务核。对照[例 13.6.1](ch13.md#ex-13.6.1)、[定义 13.6.1](ch13.md#def-13.6.1)。
:::

:::

::: ex B10 · 1698 与 2000 的缺口（主线 ②） {#ex-13.B.10}

本轮 sample 使用 1 ms 请求间隔、2 秒窗口。按「2 秒除以 1 毫秒」应有 2000 条根观察；报告里 CPU 运行 1698、waiting 运行 1648。有人写「采样器漏掉了一部分样本，漏多少可以按比例算」。这个比例能算吗？这个缺口能支持什么结论？

::: hint 提示

2000 是实际发生的采样次数，还是按参数推算的理想值？进程启动与退出落在窗口哪里？

:::

::: sol 解答

不能这样算。2000 是按请求参数推算的理想值，不是实际发生的采样次数；请求间隔不是精确时钟，工具可能限流、合并或拒绝记录，进程启动与退出也吃掉窗口两端。本轮没有采集丢样计数与每条请求的实际时刻，缺口不能按比例归因。

能说的只有：报告根计数低于请求间隔推算的理想值，因此不能把间隔当成精确采样时钟，也不能用根计数直接换算时间占比。对照[例 13.7.1](ch13.md#ex-13.7.1)、[定义 13.7.1](ch13.md#def-13.7.1)。
:::

:::

::: ex B11 · 13.3 倍能不能当采样器开销（主线 ③） {#ex-13.B.11}

同事说「日志让 Rust 慢 13.3 倍，所以 `sample` 的开销也能按这个倍率估」。这两件事为什么不能互推？要测采样器开销，应设计哪两次运行、记录哪三类时间？

::: sol 解答

13.3 倍来自应用内逐项插桩：each 与 none 都跑同一段 200000 步递推，前者每步读时钟、构造事件并经屏障观察。`sample` 是外部进程周期性读栈；一个由应用自己读时钟，一个由外部进程读栈，观察对象与扰动来源都不同。

要测采样器开销，应做同等输入、同一二进制的附着／未附着两次运行，两者交替，保留足够原始观察，并区分采集器 CPU、被测进程 CPU 与总墙钟。本轮没有做这种 21 次配对实验，本节没有采集。对照[定义 13.7.2](ch13.md#def-13.7.2)。
:::

:::

::: ex B12 · 34.306250 是哪一条（主线 ②） {#ex-13.B.12}

13.6 的 each 列：均值 32.832639、N−1 标准差 0.608977、批均值 p50 32.762500、p99 34.306250。p99 对应排序后的第几条？能不能写「99% 的打点步都在 34.31 纳秒以内」？六位小数是不是六位有效精度？

::: sol 解答

p99 是第 21 条。`ceil(0.99 × 21) = 21`，所以 p99 就是最大值 34.306250。

不能写「99% 的打点步」：它是 21 条批均值上的分位数，描述批次之间的波动，不是逐 step 延迟；本轮也没有 200000 个 `Event` 的分布可查。

六位小数不是六位有效精度。小数位为复算保留，统计量本身含批次与桌面环境的波动。对照[定义 13.7.3](ch13.md#def-13.7.3)、[例 13.7.2](ch13.md#ex-13.7.2)。
:::

:::

::: ex B13 · 汇编摘录能证明什么（主线 ①） {#ex-13.B.13}

本轮 `mix` 的完整函数体逐字列在[13.8.2 的逐字摘录](#repro-13.8.2)，摘出时只删调试元数据。就其中可见的 `madd`，有人写「有 `madd`，说明这批时间的瓶颈是乘加吞吐」。这句话越过了哪条界线？完整函数体能证明什么？要谈成本分摊还缺什么？

::: hint 提示

符号存在与成本分摊是两个概念；函数体能说明操作没被删除，不能说明时间花在哪里。

:::

::: sol 解答

越过了「符号存在」与「成本分摊」的界线。完整函数体只证明屏障、旋转与乘加没有被整段删除，`madd` 只证明乘加存在，不证明整批时间由乘加吞吐决定。循环有数据依赖，也有函数调用，`black_box` 还引入可见存取；这些都没有被单独测量。要谈成本分摊，需要计时或事件证据，并按同一区间、同一分母拆解。对照[定义 13.8.2](ch13.md#def-13.8.2)。
:::

:::

::: ex B14 · 35% 涨到 58%（主线 ③） {#ex-13.B.14}

团队删掉 A 阶段的工作后重跑，flamegraph 上 B 函数从 35% 涨到 58%，于是写「B 变慢了，是新的瓶颈」。给出三种都能解释这组数字的情况，并说出你需要的最小补充数据。

::: sol 解答

三种情况：① 整体变快，B 的绝对权重不变，只因为分母缩小而占比上升；② 整体变快但 B 真的略微变慢，涨幅小于表面读法；③ 整体变慢，B 的绝对权重上升更多。归一化图对这三者给出形状相似的结果。

最小补充数据是两张图的总权重与总运行量（原始观察条数与批次墙钟），并按同一互斥分类给出绝对量。有了总量，才能把「占比 35% → 58%」换成「观察数 x → y，同期批次墙钟 m → n」。对照[例 13.4.2](ch13.md#ex-13.4.2)。
:::

:::

::: ex B15 · 模拟 miss 下降等于本机变快吗（主线 ④） {#ex-13.B.15}

有人在别的机器上用 Cachegrind 看到模拟 cache miss 下降，就写「本机 PMU（硬件性能计数器）的 miss 也会下降，墙钟必然变快」。列出至少三条不能这样推的理由，并说明本轮有哪些 Cachegrind 证据。

::: sol 解答

① 模拟 miss 不是硬件 PMU 的 miss；Cachegrind 累计的是动态执行追踪得到的模拟计数，指令定义也可能不同于 retired instructions（硬件实际退休的指令数）。

② 缓存与分支模拟是基础模型，不完整反映现代处理器；它没有自动模拟内核活动、其他进程竞争、真实虚实地址映射、全部 TLB（地址翻译缓存）与推测执行效果、原生线程调度交错、完整预取（提前把数据取进缓存）与分支预测。

③ 文档说明这些模拟默认关闭，实际使用必须核对安装版本；布局、共享库、路径变化都会改变模拟结果。

本轮没有执行 Cachegrind，本机也没有生成任何 `cachegrind.out` 证据；书中没有用模拟数据补齐性能表。对照[定义 13.7.5](ch13.md#def-13.7.5)、[13.7 采样扰动、统计与 Cachegrind 边界](ch13.md#sec-cpp-rust.4.13.7)。
:::

## C 组 · 实操（16–20）

这组题要求真的动手：复跑实验包、核对原始文件、把结论写成可复核的句子。实验包在 `bench/evidence-lab/`，实测目录是 `results/run-01/`。

::: ex C16 · 数一遍 cpu-wait 原始行（主线 ④） {#ex-13.C.16}

从 `cpp-rust/` 按 13.11 的命令构建并运行 `measure.sh` 到一个不存在的新目录。打开 `cpu-wait.txt`，回答：每 case 多少批、总共多少条原始批次、所有业务 checksum 是否一致、表里的 cpu 与 wait 均值能否复算。写下你检查了哪四项。

::: sol 参考路径

四项：① 每个 case 恰好 21 批，文件共 42 条原始批次；② 所有业务 checksum 都等于 14437947664662268765；③ 用 N−1 重算每组标准差；④ 用 nearest-rank 重算 p50／p99。

::: sol 参考路径

N=21。p50 的秩是 `ceil(0.5 × 21) = 11`，p99 的秩是 `ceil(0.99 × 21) = 21`。排序后第 21 条就是最大值，所以 p99 等于 34.306250；p50 取第 11 条，应等于 32.762500。

这不是精度声明：p99 只是 21 条批均值之间的最大值，不是 200000 个逐 step 事件的分布。对照[定义 13.7.3](ch13.md#def-13.7.3)、[例 13.7.2](ch13.md#ex-13.7.2)。

## 批改最常给的三条意见

1. **把观察数当时间。** 1698、1082、1648、1443 都是观察条数，不是纳秒；`1082／1698` 只能写成观察份额，不能写成 CPU 时间占比。先改句子，再改表格。
2. **把聚合值当单次事件。** 32.832639 是 ns/聚合 step，分子是一整批 200000 步的墙钟；30.359782 不是可加项。凡出现「一次打点多少纳秒」，一律退回重写。
3. **缺证据却给结论。** 附着开销、Cachegrind、PMU、IPC、cache miss、分项耗时本轮都没有采集；正确写法是「本节没有采集」，而不是填零、填比例或拿插桩倍率顶替。
