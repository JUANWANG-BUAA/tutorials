# 16 项目二：Rust 高性能组件与最小 C ABI

<div class="chapter-index">

**问题主线**：把一个 Rust 数据核交给真实 C 调用者后，如何同时保留批处理机会、明确释放责任，并给失败留下可验证的出口？

- 从安全 Rust 算法出发，而不是先设计一套裸指针类库。
- 用版本化元数据和整数错误码限定外部可见表示。

- 用 Rust 测试与实际 C11 调用共同验证布局、错误清理和线程协议。
- 用两组已执行 benchmark 区分调用粒度、复制与消费位置。

## 16.1 先确定组件能力与跨边界成本 {#sec-cpp-rust.4.16.1}

### Rust 是实现主体

项目实现一个不可变整数数据组件。
输入和输出元素都是 `u64`。
核心映射对每个元素独立执行右移、异或、模乘和模加。
数据生成、批量变换、checksum、分配、注册表和线程同步都在 Rust 中。
C 只提供真实外部调用者、命令行驱动和测量入口。

这个核刻意保持简单。
它让跨边界粒度和所有权路径成为可观察变量。
它不是密码学散列，也没有抗碰撞或保密性承诺。
不要把本章的 wrapping 映射用于认证令牌或内容签名。

完整实现的安全入口如下：

```rust
#[inline]
pub fn mix(value: u64) -> u64 {
    (value ^ (value >> 29))
        .wrapping_mul(0x9e37_79b9_7f4a_7c15)
        .wrapping_add(0x243f_6a88_85a3_08d3)
}

pub fn transform(input: &[u64], output: &mut [u64]) -> Result<(), i32> {
    if input.len() != output.len() {
        return Err(ECAPACITY);
    }
    for (source, dest) in input.iter().zip(output) {
        *dest = mix(*source);
    }
    Ok(())
}

pub fn checksum(values: &[u64]) -> u64 {
    values.iter().fold(0, |sum, x| sum.wrapping_add(*x))
}
```

Rust 调用者不必经过 FFI 注册表。
它可以直接传递切片，复用编译器对借用的检查。
外部入口只是这个算法周围的一层协议适配。
先把算法写成安全函数，能减少必须同时推理的未知量。

### 三种数据路径

第一条路径是同步借入。
C 提供输入和输出存储，Rust 在本次调用期间访问它们。
函数返回后不保留任何 C 数据指针。
适合调用者已经有缓冲区的批量计算。

第二条路径是复制导入。
`rb_create_copy` 把 C 输入复制到 Rust 的不可变存储。
成功返回后，原 C 输入可以修改或释放。
后续查询通过句柄识别新对象。

第三条路径是 Rust 生产结果。
`rb_generate` 根据 seed 与长度生成一批值。
它把句柄和释放责任交给 C，而不交出数据裸指针。
C 可以要求元数据和归约结果，也可以显式复制出整个数组。

| 路径 | 调用期间的数据所有者 | 返回后的所有者 | 是否保留 C 指针 |
|:--|:--|:--|:--|
| 同步批量变换 | C | C | 否 |
| create_copy 导入 | C 原件、Rust 新副本 | 两者各自管理自己的分配 | 否 |
| generate 结果 | Rust | Rust 存储，C 承担句柄释放责任 | 否 |
| copy 导出 | Rust 原件、C 输出 | 两者各自管理自己的分配 | 否 |

这里的“所有权转移”是协议责任的转移。
它不等于把一个 `malloc` 指针塞进 `Vec`。
Rust 分配仍由 Rust 析构。
C 分配仍由 C 释放。

### 架构图

<pre class="layout">
 C11 CLI / test / benchmark
    | rb_transform(input, output, len)
    |------------------------------&gt; numeric guards --&gt; Rust slice kernel
    |
    | rb_generate(seed, len, &amp;handle)
    |------------------------------&gt; Vec --&gt; Arc&lt;[u64]&gt;
    |                                           |
    |                              Mutex&lt;Registry&gt;
    |                                 slot + generation
    |                                           |
    | rb_info / rb_copy -------------------------+
    |                 clone Arc under lock --&gt; work outside lock
    |
    | rb_release(handle) --&gt; remove slot owner --&gt; drop outside lock
</pre>

读图：上面的同步路径不经过句柄管理。
下面的拥有路径通过注册表保留 Rust 分配。
图中 `Vec → Arc` 不代表零成本转换；本轮产物实际存在复制。
`release` 移除槽内所有者后，已经取得快照的读取仍可能存活。

### 需求不是“函数能被 C 找到”

导出符号只是集成的第一步。
完整需求还包括版本、尺寸、长度单位和错误语义。
更关键的是失败之后谁还拥有资源。
如果接口失败时顺便消费句柄，调用者就必须知道这一点。
本项目明确选择：普通查询和复制失败不消费句柄。

每次成功创建只产生一个释放责任。
复制句柄数值不会复制这个责任。
并发释放时只能有一个成功者。
其余调用得到旧身份错误，而不是再次析构同一块存储。

### 不纳入这一版的能力

组件不执行外部回调，也不接收函数指针。
它没有让外部异常回到 Rust 的需求。
它没有提供可变裸数据视图。
因此不必同时设计回调重入、借出视图撤销和原地修改协议。
这些是有意削减的接口面，不是把难题藏到未实现函数后面。

## 16.2 版本化布局与整数错误协议 {#sec-cpp-rust.4.16.2}

### 只让必要的表示成为 ABI

外部可见类型只有固定宽度整数、指针和一份元数据结构。
不把 `Vec`、`Arc`、`Result` 或 Rust 枚举布局暴露给 C。
注册表内部怎么换容器，不应影响 C 的头文件。
同样，C 调用者不需要知道引用计数头的字节偏移。

元数据的 Rust 定义是：

```rust
#[repr(C)]
#[derive(Clone, Copy, Debug, Default, PartialEq, Eq)]
pub struct InfoV1 {
    pub abi_version: u32,
    pub struct_size: u32,
    pub len: u64,
    pub checksum: u64,
}
```

`repr(C)` 给出本机目标下的 C 结构布局规则。
它不是序列化格式，也不自动解决大小端转换。
结构里若放入 Rust 专有类型，外层标记也不能替它发明 C 表示。
本项目因此只使用对应的固定宽度整数。

### 两侧都检查布局

本轮目标是 `aarch64-apple-darwin`。
Rust 测试使用 `size_of`、`align_of` 与 `offset_of!`。
C 头文件使用 C11 静态断言。
二者各自经过实际编译，不是只在正文里写一个期望表。

| 对象或字段 | 本机尺寸 | 本机对齐 | 字段偏移 |
|:--|--:|--:|--:|
| rb_handle / u64 | 8 | 8 | 不适用 |
| InfoV1 / rb_info_v1 | 24 | 8 | 不适用 |
| abi_version / u32 | 4 | 4 | 0 |
| struct_size / u32 | 4 | 4 | 4 |
| len / u64 | 8 | 8 | 8 |
| checksum / u64 | 8 | 8 | 16 |

表格描述的是这份发行物的目标约束。
头文件还断言指针大小为8。
32位目标不会悄悄套用这张表，而会在构建阶段拒绝。
没有执行过的目标不写成“天然兼容”。

C 侧对应断言包含：

```c
_Static_assert(sizeof(rb_info_v1) == 24, "v1 size");
_Static_assert(_Alignof(rb_info_v1) == 8, "v1 alignment");
_Static_assert(offsetof(rb_info_v1, abi_version) == 0, "version offset");
_Static_assert(offsetof(rb_info_v1, struct_size) == 4, "size offset");
_Static_assert(offsetof(rb_info_v1, len) == 8, "length offset");
_Static_assert(offsetof(rb_info_v1, checksum) == 16, "checksum offset");
```

### 版本和容量由调用参数先行声明

`rb_info` 接收版本和输出结构字节数。
只有版本为1且尺寸恰好为24时才写结构。
它不先读取一份可能未初始化的输出结构来猜调用者版本。
输出结构里的两个头字段用于结果自描述，而不是输入协商。

这个选择不支持“旧调用者自动忽略新尾字段”。
以后扩展时应增加新版本或新入口。
保持 v1 的定义不变，比把字段插到结构中间更容易审查。
如果要支持前缀兼容，应重新定义明确的最小尺寸与写入上界。
不能仅把等号改成大于等于就声称已完成兼容设计。

### 错误码是一份稳定词表

外部函数返回 `i32`，C 声明对应 `int32_t`。
成功为0，普通错误保持非零整数。
没有借出的错误字符串，也没有线程局部最后错误缓冲。
因此不存在“下一次调用把上一条错误文本覆盖”的隐式寿命。

| 数值 | 名称 | 典型触发 | 资源后果 |
|--:|:--|:--|:--|
| 0 | OK | 操作成功 | 按具体操作提交结果 |
| 1 | EINVAL | null、对齐、重叠、版本或尺寸错误 | 不消费原句柄 |
| 2 | ERANGE | 长度上限、转换或地址算术溢出 | 不创建结果 |
| 3 | ESTALE | 无效槽、旧代、重复释放 | 不再释放资源 |
| 4 | ECAPACITY | C 输出容量小于对象长度 | 数据和 written 不写 |
| 5 | EPANIC | 捕获到 Rust unwind panic | 不承诺进程已全面恢复 |
| 6 | EPOISON | 注册表锁被毒化 | 拒绝继续解释注册表状态 |
| 7 | ERESOURCE | 可报告的预留失败或槽上限 | 局部临时资源由 Rust 回收 |

一个输入同时违反多条规则时，不保证每版都返回同一种优先错误。
例如坏版本与旧句柄并存，本版先检查版本。
调用者应只依赖文档允许的错误集合，不解析内部检查顺序。
若业务需要精确诊断，应增加专门诊断能力，而不是猜分支。

### 输出提交点

创建入口先构造数据，再登记句柄，最后写输出句柄。
普通参数错误时不覆盖调用者原有值。
查询先完成快照和 checksum，再写完整元数据。
复制先验证容量，最后才复制并写入 written。

这些承诺是普通受控错误路径的行为。
它们不是面对任意硬件故障的事务系统。
panic 被捕获也不自动提供业务回滚。
本项目核函数没有在写出一半后主动 panic 的分支。
将来添加可失败变换时，必须重新讨论部分输出。

### 长度单位不能含糊

所有数据长度和容量都以 `u64` 元素计数。
只有 `rb_info` 的 bytes 参数以字节计数。
两种单位在名称、文档和检查里分开。
内部再用受检查转换得到 `usize`。
单对象上限为 `2^24` 个元素，而不是 `2^24` 字节。
这个上限是项目资源策略，不是 Rust 切片的语言上限。

## 16.3 指针守卫与不能替调用者证明的条件 {#sec-cpp-rust.4.16.3}

### 先检查数值，再形成引用

FFI 入口收到的是裸指针。
Rust 的类型系统不会跨语言证明它们来自有效分配。
因此检查必须发生在 `from_raw_parts` 之前。
一旦先形成非法引用，再检查 null，就已经太迟。

项目把共同的数值检查放在 `range` 中。
它返回半开地址区间，用于检测参数重叠。
这里的地址整数仅用于拒绝显然错误的输入。
程序不会把算过的整数地址重新制造为可解引用指针。

```rust
fn range<T>(ptr: *const T, len: usize) -> Result<(usize, usize), i32> {
    if len == 0 {
        return Ok((0, 0));
    }
    if ptr.is_null() || !(ptr as usize).is_multiple_of(align_of::<T>()) {
        return Err(EINVAL);
    }
    let bytes = len.checked_mul(size_of::<T>()).ok_or(ERANGE)?;
    if bytes > isize::MAX as usize {
        return Err(ERANGE);
    }
    let start = ptr as usize;
    Ok((start, start.checked_add(bytes).ok_or(ERANGE)?))
}
```

本项目使用它的类型都不是零尺寸类型。
数据元素是 `u64`，元数据是固定结构。
不能把这个小工具脱离上下文，当成任意泛型内存验证库。
它从未查询操作系统映射表，也无法发现悬垂分配。

### 空数据不构造空指针切片

C 常用 null 表示空数组。
Rust 的切片引用即使长度为0，也有非空和对齐要求。
所以 `rb_transform` 在长度为0时直接成功返回。
它不会把 null 交给 `from_raw_parts`。
复制导入和复制导出也分别跳过零长度数据访问。

元数据输出不是空数组。
输出句柄、written 和 InfoV1 始终要求一个完整可写对象。
不能用“这次没有数据”解释为什么输出句柄指针可以是 null。
测试覆盖了空对象的完整创建、复制和释放链。

### 重叠拒绝先于借用

`rb_transform` 不支持原地变换。
它要求输入区域与输出区域分离。
如果两个地址区间相交，就返回 EINVAL。
只有数值检查和重叠检查都通过，才形成只读输入和独占输出切片。

```rust
fn separate(a: (usize, usize), b: (usize, usize)) -> Result<(), i32> {
    if a.0 < b.1 && b.0 < a.1 {
        Err(EINVAL)
    } else {
        Ok(())
    }
}
```

输出数据与 written 也必须分离。
否则最后写一个长度就可能覆盖刚复制出的数据。
复制导入时，输入与输出句柄同样做区间检查。
这些检查覆盖本次调用可见的参数关系。
它们不能找出其他线程偷偷持有的别名。

### 真正的 unsafe 证明分两半

| 条件 | 入口能检查什么 | 调用者仍须保证什么 |
|:--|:--|:--|
| 非空 | 非零区域指针不为 null | 指向实际存活分配 |
| 对齐 | 地址满足类型对齐数值 | 对象表示和目标类型匹配 |
| 长度 | 上限、乘法、转换和地址加法 | 分配真实容量足够 |
| 单分配 | 不能可靠检查 | 整段不能拼接多个相邻分配 |
| 初始化 | u64 位模式均有效 | 每个输入元素已初始化 |
| 别名 | 本次参数区间是否重叠 | 外部无冲突访问和数据竞争 |
| 寿命 | 不保存外部指针 | 返回前分配不能失效 |
| 可写性 | 不能可靠检查 | 输出不是只读页或失效对象 |

注意“所有 u64 位模式有效”不代表未初始化字节可以读。
位模式有效性和初始化状态是两件事。
同样，地址不溢出也不代表区间属于同一个分配。
操作系统可访问页不等于 Rust 对象寿命仍有效。

### 安全的负面测试怎么写

C 测试传入真实数组的相同首地址作为输入和输出。
入口在形成引用前识别重叠并返回错误。
它不执行那次重叠变换。
这验证的是守卫，而不是执行一个未定义行为版本看看会不会崩溃。

对齐拒绝测试放在 Rust 契约测试中。
测试从真实字节数组得到一个未对齐裸指针。
创建这种 Rust 裸指针本身不读取内存。
入口检查对齐后返回，不形成 `u64` 引用。
测试没有在 C 中进行可能违反对齐要求的指针类型转换。

坏长度测试使用超上限值。
实现先检查长度，再检查和访问数据。
这样可以安全验证 `u64::MAX` 被拒绝。
不能把 null 配一个可接受的非零长度后，绕过检查强行读取。
更不能真的读释放后的 C 缓冲来测试 catch_unwind。

### 不假装这是沙箱

如果调用者给一个对齐但悬垂的地址，接口无法保证返回错误。
如果另一个线程在调用期间释放输入，Rust 无法事后补救。
如果调用者对同一输出并发写入，注册表互斥锁也不会保护那块 C 内存。
错误码只覆盖被检查和受支持的错误。
对任意恶意地址提供内存隔离，需要进程等更强边界。

## 16.4 代号句柄、释放线性化与并发快照 {#sec-cpp-rust.4.16.4}

### 不把地址当身份

直接把分配地址强转成整数，不能可靠识别旧对象。
旧地址可能被后来的分配复用。
调用者手里仍有同样数值，却指向一个不同生命期。
本项目让外部身份与数据地址分离。

句柄高32位是 generation。
低32位是槽下标加一。
低位为0保留为无效身份。
本项目最多4096槽，实际下标远小于32位上限。
这不是把4096写进 ABI 位宽，而是当前资源边界。

| 组成 | 位数 | 有效性规则 | 作用 |
|:--|--:|:--|:--|
| generation | 32 | 与槽当前代号相等 | 拒绝旧生命期 |
| index + 1 | 32 | 非零且槽存在 | 定位内部槽 |
| data 存在性 | 内部状态 | 槽必须仍持有 Arc | 拒绝已经释放的当前代 |

### 空槽复用

第一次使用一个槽时，代号为1。
释放时取走数据，但保留代号。
再次使用该槽时，把代号递增后再登记新数据。
因此新对象的句柄不同于旧对象。

复用核心来自完整实现：

```rust
if let Some((index, slot)) = self
    .slots
    .iter_mut()
    .enumerate()
    .find(|(_, slot)| slot.data.is_none() && slot.generation < u32::MAX)
{
    slot.generation += 1;
    slot.data = Some(data);
    return Ok((u64::from(slot.generation) << 32) | (index as u64 + 1));
}
```

### 不回绕比“几乎不会发生”更明确

代号达到 `u32::MAX` 的槽不再复用。
它会退休，而不是回到1。
这样不会在该库实例的生命期内重新产生同一个槽代组合。
测试直接构造一个已到最大代号的空槽，验证插入改用新槽。

这是一种可证明的身份策略。
代价是极端长期运行下可用槽会逐渐减少。
达到槽上限时返回 ERESOURCE。
如果系统需要可无限复用的身份，不能只把位宽加大后省略寿命证明。
还应定义调用者最长持有期限和实例重启协议。

### 查找必须同时检查三件事

查找先拒绝低32位为0。
然后检查下标是否存在。
最后比较代号，并确认该槽仍有数据。
仅仅“下标没越界”不足以证明句柄有效。
仅仅“代号相等”也不能证明当前对象尚未释放。

这些步骤在同一个注册表锁内完成。
不能先在锁外检查代号，再等一会儿获取数据。
中间若发生释放和复用，就会把旧身份检查与新数据拼在一起。
本项目不把检查结果缓存成一个长期裸槽指针。

### 读取拿快照，计算不持全局锁

内部对象是不可变的 `Arc<[u64]>`。
查询和复制在持锁期间克隆 Arc。
之后释放锁，在快照上执行 checksum 或复制。
这使大数组计算不必独占整个注册表。

不可变数据减少了协议面。
读取者不会在释放锁后争夺可变借用。
Arc 负责存活，Mutex 负责身份映射。
两个机制解决不同问题，不能用“用了 Arc”省略注册表同步。

### release 的线性化点

释放在锁内从槽中取走 Arc。
这一动作让之后的查找返回 ESTALE。
锁外再 drop 取出的所有者。
大分配的最终析构不会故意放在全局锁内。

并发两次释放的结果因此明确。
先取走对象的一方成功。
后一方即使代号相同，也因为 data 已空而失败。
不会出现两份都认为自己是最后所有者的裸指针析构。

### release 返回不等于所有读者结束

如果读取先拿到快照，再发生释放，读取可以正常完成。
如果释放先移除槽，再开始读取，读取返回 ESTALE。
这两种结果都符合协议。
release 并不是“等待全部读取结束”的 join 操作。

内部单元测试保留一个快照，然后释放注册表所有者。
它随后仍能安全读取快照的 checksum。
这个确定性测试证明了存活机制。
另一个并发测试允许读者得到 OK 或 ESTALE，检验真实竞态的合法结果集合。

### 身份不是权限，也不是可持久化主键

知道一个句柄数值的人可能调用释放。
代号设计防的是误用旧生命期，不是恶意猜测。
外部授权必须另行设计。
把句柄写进文件，换一个进程或另一个加载实例后也没有意义。
静态库若被分别链接进不同模块，甚至可能有不同注册表实例。

## 16.5 panic 防线、失败清理与真实双向测试 {#sec-cpp-rust.4.16.5}

### 普通错误不使用 panic 表达

坏版本、容量不足和旧句柄都属于普通错误。
它们直接通过 `Result` 走到整数码。
`catch_unwind` 不是正常分支选择器。
只靠 panic 把每个越界都变成错误码，会把业务错误与程序缺陷混在一起。

边界帮助处理意外 unwind。
所有可能失败的 C 导出操作都在边界内部执行。
测试专用入口也走同一条边界。
不使用 `extern "C-unwind"` 让 Rust 展开穿过 C 栈。

```rust
fn boundary(f: impl FnOnce() -> Result<(), i32>) -> i32 {
    match catch_unwind(AssertUnwindSafe(f)) {
        Ok(Ok(())) => OK,
        Ok(Err(code)) => code,
        Err(payload) => {
            std::mem::forget(payload);
            EPANIC
        }
    }
}
```

### 为什么遗忘 panic payload

捕获结果里的 payload 可能具有会 panic 的析构器。
若在外部入口返回之前直接 drop 它，可能再次触发展开。
本项目选择在异常路径遗忘 payload。
这避免把一个用户自定义 payload 的析构再次带到边界外。

代价必须公开。
每次捕获可能泄漏该 payload 所占的资源。
这不是“所有 panic 都可无限恢复”的实现。
如果持续出现 EPANIC，服务应告警、停止接收相关工作并安排进程恢复。
不能把故障泄漏当成正常吞吐路径。

### AssertUnwindSafe 不提供回滚

这个包装允许闭包通过 unwind 安全性边界。
它不检查业务状态是否恢复。
本项目用局部 RAII 管理尚未提交的数据，并对被毒化锁采取拒绝策略。
将来若加入多步可变状态，必须重新审查提交顺序。

分配失败也要分层。
`try_reserve_exact` 能报告部分预留失败。
但 `Arc::from` 等分配路径仍可能走不可恢复的分配错误处理。
catch_unwind 不捕获 abort。
本章不承诺内存耗尽时一定返回 ERESOURCE。

### poison 的处理不是强行解锁继续

如果持有注册表锁时 panic，锁可能被毒化。
后续操作把锁错误映射成 EPOISON。
不使用 `into_inner` 自动相信内部状态。
这是保守停止，不是完整在线修复。

测试只毒化局部 Mutex，避免污染所有测试共享的全局实例。
随后检查 poison 状态和错误映射。
它证明策略存在，不证明任意内部 panic 后都能继续服务。
C 的故意 panic 入口在取得注册表锁之前触发。
因此 C 测试后续调用正常，不应被解释成对全局 poison 恢复的验证。

### C 调用者的清理规则

CLI 创建成功后，不论查询成功与否，都调用 release。
查询失败不消费句柄，这使清理规则简单。
释放结果也会检查，而不是被无条件忽略。
只有创建成功后才拥有要释放的句柄。

实际 CLI 的关键顺序是：

```c
rb_handle handle = 0;
int32_t code = rb_generate(args[0], args[1], &handle);
if (code != RB_OK) {
    fprintf(stderr, "generate error=%" PRId32 "\n", code);
    return 1;
}
rb_info_v1 info = {0};
code = rb_info(handle, RB_ABI_VERSION, sizeof(info), &info);
int32_t release = rb_release(handle);
if (code != RB_OK || release != RB_OK) {
    fprintf(stderr, "info error=%" PRId32 " release=%" PRId32 "\n", code, release);
    return 1;
}
```

完整文件还检查十进制参数、负号、尾部字符和范围。
不要只截取创建成功的 happy path 当作应用示例。
异常资源寿命往往由失败分支决定。

### 安全失败回归：容量不足不写输出

Rust 与 C 都执行了这一回归。
先创建一个长度大于输出容量的对象。
把输出数组和 written 初始化为可识别哨兵。
调用 rb_copy，检查 ECAPACITY，并确认两个输出都没变。
最后释放原句柄。

这不是假设的公司事故。
它是项目内可运行的真实失败路径。
测试防止以后有人把容量检查移到复制之后。
没有越界访问参与测试，也不需要依赖“越界可能会崩溃”。

### 测试分工与实际数量

| 测试层 | 实际覆盖 | 本轮执行 |
|:--|:--|:--|
| Rust 内部4项 | 代号退休、槽上限复用、快照存活、panic及局部poison | 通过 |
| Rust 导出契约6项 | 布局、核对照、容量/版本、空对象、释放争用、读者竞态 | 通过 |
| C11 契约可执行文件 | 独立参考核、布局断言、错误清理、pthread读取、panic探针 | 通过 |
| CTest CLI3项 | 正常调用、过大长度、非法数字 | 通过 |

CTest 总计4项，其中一项是完整 C11 契约程序。
不能把 C 程序里的每条 assert 都称为一个独立测试进程。
Rust 的12线程释放测试要求恰好一个 OK、11个 ESTALE。
这检验当前实现的可观察竞争结果，不是所有线程交错的形式证明。

## 16.6 原生构建与实际代码生成核验 {#sec-cpp-rust.4.16.6}

### Cargo 与 CMake 各自管理清楚的部分

Cargo 构建 Rust 库。
CMake 构建 C11 外部调用者，并把 Rust 静态库作为真实链接输入。
这里没有用 CMake 重新列举 Rust 模块，也没有用一个空命令假装集成成功。
`add_custom_command` 实际执行 offline、locked、release Cargo 构建。

项目输出 rlib、staticlib 和 cdylib。
本轮 CMake 只验证静态库集成。
生成 cdylib 不等于完成动态库的装载路径、安装和卸载测试。
本章不把未执行的部署方式写成通过。

### 可直接执行的命令

在仓库的 `cpp-rust/projects/ffi-bridge/` 中运行：

```bash
cargo fmt --check
cargo clippy --offline --locked --all-targets --features test-hooks -- -D warnings
cargo test --offline --locked --features test-hooks
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DRB_TEST_HOOKS=ON
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
./build/bridge_demo 42 8192
```

测试专用 feature 导出 `rb_test_panic`。
发布构建应使用另一个新目录并设置 `RB_TEST_HOOKS=OFF`。
Rust 单独构建时不启用该 feature 即不导出探针。
不要把故意触发 panic 的接口当成正式业务能力。

CMake 给三个 C 可执行文件都加 `-UNDEBUG`。
这是为了让 Release 模式里的校验 assert 真正执行。
如果 `-DNDEBUG` 把 checksum 相等断言删除，就失去了部分夹具验证。
Rust API 返回码检查在 benchmark 中也用显式分支保留。

### 编译条件保存到证据中

本轮 Rust 是1.99.0，LLVM 是23.1.1。
目标为 `aarch64-apple-darwin`。
C 编译器是 Apple clang21.0.0。
CMake 是4.4.4。
Rust release 使用 opt-level3、单 codegen unit、关闭 LTO、panic unwind。
没有跨语言 LTO，也没有手工指定 target-cpu=native。

宿主型号查询为 Mac17,9，实验机为 Apple M5 Pro。
系统报告18个逻辑 CPU，cacheline 查询为128字节。
这些数值只描述当前宿主。
本项目没有靠写死64字节对齐来声称消除了伪共享。
更没有测出缓存未命中率或内存带宽上限。

### 保存的代码生成层次

脚本另行执行 `cargo rustc`，保存 MIR、LLVM IR 与本机汇编。
还用 clang 保存 C benchmark 的汇编。
这些产物来自与正式构建相同的优化配置和 feature。
它们不是目标机外的交叉生成结果。

| 边界 | 实际证据 | 可支持的结论 |
|:--|:--|:--|
| C 到 rb_mix | c-benchmark.s 中存在对 `_rb_mix` 的调用 | 逐元素跨边界没有整体消失 |
| C 到 rb_transform | 同文件中存在独立批量调用 | 批量路径真正进入 Rust |
| rb_mix | ffi_bridge.s 中含检查、madd、存储和返回 | 安全守卫与计算均保留 |
| rb_transform | 长度/重叠守卫后四元素展开 | 批量能摊薄守卫与调用 |
| Rust 切片核 | LLVM IR 的别名 scope 与 noalias 信息 | 引用契约参与优化 |
| rb_copy | memcpy 路径与独立 sample 的 memmove 栈 | 完整导出实际复制了数据 |
| rb_generate | 分配及 Vec 到 Arc 的复制路径 | 拥有句柄不等于全流程零拷贝 |
| 注册表同步 | 汇编含 mutex 调用与 ldapr | 同步未被当成普通无锁读删掉 |

### 小函数的边界防线未必留下异常表

`rb_mix` 的源码也经过 boundary。
本轮优化器能证明其正常路径没有需要 unwind 的操作。
因此实际小函数很紧凑。
不能按源码中 catch_unwind 的次数直接推算异常运行时成本。

另一方面，存在分配和锁的入口保留了相应失败与清理路径。
测试探针确实触发 unwind 并回到 C 错误码。
“某个叶函数没有异常表”和“整个库没有 panic 防线”不是一回事。
代码生成检查必须定位到具体入口。

### 看见 vector.body 不能立即宣布 SIMD

LLVM IR 的批量循环块叫 `vector.body`。
但这一版块内主要是展开后的标量 i64 运算。
最终本机汇编也呈现多个标量 madd。
因此本章称它为四元素展开，不把标签名称当成 SIMD 证据。

实际循环中的一段如下：

```asm
ldp x14, x15, [x11, #-16]
ldp x16, x17, [x11], #32
eor x14, x14, x14, lsr #29
eor x15, x15, x15, lsr #29
eor x16, x16, x16, lsr #29
eor x17, x17, x17, lsr #29
madd x14, x14, x8, x9
madd x15, x15, x8, x9
madd x16, x16, x8, x9
stp x14, x15, [x12, #-16]
madd x14, x17, x8, x9
stp x16, x14, [x12], #32
```

这段只说明固定版本的核心循环形态。
它不是汇编或调用约定入门。
也不从指令条数直接换算 CPU 周期。
完整产物还包含前置检查、尾部循环和错误返回。

## 16.7 benchmark 一：逐元素调用与批量 FFI {#sec-cpp-rust.4.16.7}

### 要回答的有限问题

对同一批8192个输入，逐元素进入 Rust 与一次批量进入 Rust，有什么差别？
每批重复64轮，总计524288个词。
两条路径使用相同 Rust 映射和相同 C 输出 checksum 循环。
它们不创建注册表句柄，也不分配拥有对象。
因此第一组主要观察边界粒度及批量优化机会。

逐元素分支每个词调用一次 rb_mix。
批量分支每轮调用一次 rb_transform。
后者仍然检查参数、长度、对齐和重叠。
它不是为了跑分快速跳过安全守卫的秘密入口。

### 完整可执行源与核心分支

完整 benchmark 在 `c/benchmark.c`。
没有依赖未给出的随机数生成器或测量库。
统计脚本在 `tools/summarize.py`。
以下摘录来自计时函数中的分支：

```c
if (which == 0) {
    for (unsigned i = 0; i != WORDS; ++i)
        check(rb_mix(input[i], &output[i]));
} else if (which == 1) {
    check(rb_transform(input, output, WORDS));
}
```

两者随后都在 C 中遍历完整 output。
这个 checksum 工作进入计时。
计时结束后，结果与独立 C 参考计算比较。
因此“相同数学结果”的检查不依赖刚才那个 Rust 输出自己证明自己。

参考输入是确定的整数序列。
测试还比较零、最大 u64 等边界值。
这不是面对随机业务数据的统计抽样。
输入可预测有利于复现，却限制了向复杂真实负载外推。

### 计时边界

| 阶段 | 是否计入每个正式批次 | 原因 |
|:--|:--|:--|
| 初始化输入 | 否 | 不重复制造固定数据 |
| 独立参考 checksum | 否 | 不把参考核重复计算计入被测耗时 |
| 每轮 FFI 调用 | 是 | 被比较的核心边界 |
| 输入读取和输出写入 | 是 | 算法真实工作 |
| C checksum 遍历 | 是 | 两路径共同消费完整输出 |
| 校验 expected | 否 | 时间戳后检查 |
| CSV 格式化与打印 | 否 | 不把终端输出当算法成本 |
| 程序启动与退出 | 否 | 不测冷启动 |

每个 case 独立预热至少500ms。
不是四个 case 共享一次500ms后就各自算预热充分。
正式采样每case21批。
每轮轮转起始case，避免固定顺序与时间漂移完全重合。
预热循环也检查结果，不会把错误计算当成预热。

### 原始观察与统计定义

CSV 保存 case、观察号、批耗时、词数与 checksum。
统计先把批耗时除以524288，得到 ns/word。
平均值与 N-1 样本标准差都基于21个批均值。
分位数使用 nearest-rank。
21个值的 p99 在这里就是最大批均值。

这不是21个请求的端到端延迟。
也不是每次 rb_mix 的独立计时。
批量值小于1ns/word，不意味着系统时钟能以亚纳秒分辨率测量一次调用。
本轮原始 elapsed_ns 还呈现1000ns步长的量化现象。
单位是纳秒，不等于实际时钟分辨率就是1ns。

### 本轮实测

来源为归档的 `raw.csv` 和 `summary.json`。
以下数值保留六位小数，完整精度在 JSON 中。

| case | n | mean ns/word | N-1 sd | 批p50 | 批p99 |
|:--|--:|--:|--:|--:|--:|
| per_element | 21 | 0.978652 | 0.021629 | 0.986099 | 1.005173 |
| batch | 21 | 0.211897 | 0.004042 | 0.211716 | 0.217438 |

两者 checksum 都是 `999f7c01d1040000`。
样本方差分别约为0.000467809与0.000016336，单位是 `(ns/word)^2`。
没有报告未做的显著性检验或 p-value。
这些桌面批次不能直接转成线上回归门限。

### 能支持什么解释

固定工作量下，批量路径的聚合成本更低。
它减少了外部调用次数，且把检查摊到更多元素上。
代码生成还显示展开的循环和一次准备的常量。
这些机制共同解释观察方向。

不能把两个平均值之差简单命名为“一次 C ABI 调用成本”。
两条路径的优化范围也不同。
逐元素要反复返回错误码，批量可以在一个循环里调度多个独立运算。
如果启用跨语言 LTO，差异可能再次变化。
本轮没有执行那组配置。

### 性能回退也是安全问题之外的真实故障

若客户端把批处理接口改回每元素调用，所有内存访问仍可合法。
但这份夹具会显示明显的吞吐回退。
因此它是安全 Rust 与合法 C 都可能引入的性能回归。
本章没有通过执行 UB 制造一个“错误版本更快”的故事。

## 16.8 benchmark 二：复制导出与拥有句柄内归约 {#sec-cpp-rust.4.16.8}

### 不同问题，不能沿用第一组归因

第二组比较结果消费位置。
两条路径都让 Rust 生成同样的8192词对象。
每批仍重复64轮，每轮都创建并释放一个句柄。
区别是把完整结果复制回 C 后求和，还是在 Rust 内部归约后只返回元数据。

copy_out 执行 generate、copy、release，然后在 C 中求和。
owned_handle 执行 generate、info、release，在 info 内完成同一模加归约。
两者的最终 checksum 一致。
但后者没有把完整数组交给 C 任意后续使用。
如果业务确实需要每个词，就不能拿归约结果替代数组而声称等价。

### 真实拥有路径

完整实现中的拥有分支为：

```c
rb_handle handle = 0;
check(rb_generate(UINT64_C(97) + rep, WORDS, &handle));
if (which == 2) {
    uint64_t written = 0;
    check(rb_copy(handle, output, WORDS, &written));
    if (written != WORDS) abort();
} else {
    rb_info_v1 info;
    check(rb_info(handle, RB_ABI_VERSION, sizeof(info), &info));
    if (info.len != WORDS) abort();
    sum += info.checksum;
}
check(rb_release(handle));
```

copy_out 分支随后执行公共 C 求和循环。
owned_handle 不重复遍历 C output。
这一点由 `which != 3` 条件明确区分。
没有忘记观察拥有路径的结果，也没有漏掉 release。

### 所有权转移到底省了什么

C 接收的是负责消费和释放的句柄。
Rust 数据始终由 Rust 分配器管理。
owned_handle 省掉的是一次完整 Rust 到 C 输出复制。
它没有接管 C 分配，也没有从 C 借出一个长期裸数据视图。

这可以称为“结果留在组件内”的接口优化。
不宜笼统称为“零拷贝”。
本轮 `Arc::from(Vec)` 在内部构造中实际发生复制。
两条路径都承担这个共同成本。
将来若要进一步优化，应先测量直接构造引用计数存储的收益和初始化证明。

### 本轮实测

| case | n | mean ns/word | N-1 sd | 批p50 | 批p99 |
|:--|--:|--:|--:|--:|--:|
| copy_out | 21 | 0.641505 | 0.028644 | 0.642776 | 0.684738 |
| owned_handle | 21 | 0.358854 | 0.013968 | 0.356674 | 0.400543 |

两者 checksum 都是 `f9e695131a980000`。
样本方差分别约为0.000820485与0.000195100，单位仍是 `(ns/word)^2`。
这组时间包括分配、生成、注册表、读取或复制、释放和求和。
不是单独 memcpy 的吞吐，也不是单独 Arc 原子引用计数成本。

### 与第一组不能直接排名算法优劣

第一组复用外部分配的输入输出。
第二组每轮都创建 Rust 拥有对象。
它们有不同的资源生命期和被计入工作。
不能因为 batch 数值最低，就宣布“句柄接口设计失败”。
它们服务不同调用需求。
如果数据已经在 C 内，批量借入很合适。
如果数据由 Rust 生产且只需要摘要，留在 Rust 内归约更自然。
若 C 必须长期读取每个元素，则需要复制或另一个经过严格寿命设计的视图接口。

### 另一次执行采样，不污染正式计时

脚本在84条正式观察之后另起一个进程。
该进程预热后轮转执行四个case。
macOS sample 以1ms间隔请求采样2秒。
完整报告保存在 `macos-sample.txt`，不并入 raw.csv。

报告能看到 rb_mix、rb_transform、rb_generate、rb_copy 和 rb_info。
还可看到 rb_copy 下的 `_platform_memmove`。
这与完整导出发生内存复制一致。
rb_generate 下也出现内存复制和分配器路径。
它提醒我们不要把“没有复制回 C”写成“没有任何复制”。

采样轮转的四个case不是等墙钟占比的生产负载。
因此不把栈样本数换成每种 API 的稳定 CPU 占比。
也不报告 sample 没采集的 IPC、cache miss、频率或能耗。
macOS 栈采样不能冒充 Linux perf 的硬件计数器实验。

## 16.10 常见陷阱 {#sec-cpp-rust.4.16.10}

1. **把非空检查当成指针有效性证明。**
   对齐且非空的地址仍可能悬垂、只读或越出分配。
   有效分配和完整调用寿命必须由调用者保证。

2. **先构造切片，后检查长度或重叠。**
   非法引用的形成本身就可能违反契约。
   本项目在所有数值守卫之后才进入 unsafe 转换。

3. **把两个地址连续的分配拼成一个切片。**
   单分配约束不由地址连续性推出。
   range 的加法检查没有证明分配来源。

4. **把长度单位混成字节。**
   数据参数计数的是 u64 元素，元数据 bytes 才是字节。
   测试和头文件都必须沿用同一单位。

5. **给外层结构加 repr(C)，就传出 Vec。**
   表示标记不会把内部 Rust 容器变成稳定 C 对象。
   项目只传固定宽度元数据与不透明整数身份。

6. **用 C 的 free 释放 Rust 结果。**
   本项目根本不导出可供释放的数据地址。
   句柄只能由 rb_release 消费，不能转成分配指针。

7. **复制句柄数值后释放两次。**
   数值副本不是第二个所有者。
   第二次释放应返回 ESTALE，调用者不应据此继续读旧对象。

8. **代号达到最大值后回到1。**
   这会在极端寿命下重新生成旧身份。
   当前实现退休该槽，测试覆盖这一分支。

9. **以为 release 返回说明所有读取结束。**
   先拿到 Arc 快照的读取仍可完成。
   卸载库和回收外部执行环境需要更高层的在途调用协调。

10. **以为 Mutex 保护了所有 C 输出。**
    它只保护注册表身份映射。
    外部共享输出上的并发读写仍是调用者的数据竞争责任。

11. **认为 catch_unwind 能捕获 UB、abort 和外部异常。**
    它只负责受支持的 Rust unwind。
    内存耗尽和进程信号也不因此获得错误码恢复语义。

12. **捕获 payload 后无条件析构它。**
    payload 的析构可能再次 panic。
    本项目在异常路径有意遗忘它，并公开可能泄漏的限制。

13. **AssertUnwindSafe 等于事务回滚。**
    它是调用方对 unwind 安全性的声明，不是修复器。
    注册表被 poison 后仍会拒绝服务，而非强行恢复。

14. **Release 模式让 assert 消失却继续称校验通过。**
    本项目 C 构建显式使用 -UNDEBUG。
    benchmark 还用显式分支核验错误码和最终 checksum。

15. **把批均值 p99 当成请求尾延迟。**
    这里每个样本是524288词的批量墙钟成本。
    21个批次的最大值不能替代线上请求延迟分布。

16. **把 owned_handle 称为全链路零拷贝。**
    它避免复制回 C，但 Vec 到 Arc 的内部复制仍存在。
    sample 与汇编都提醒我们限定结论范围。

17. **只凭 vector.body 标签宣传 SIMD。**
    当前转换核实际是四元素展开的标量运算。
    应同时查看 IR 操作和最终本机汇编。

18. **用槽数量上限替代总内存预算。**
    单对象上限和4096槽仍允许很高的理论总占用。
    生产准入需要单独限制聚合字节，不能靠分配失败治理负载。
