## 16.1 先确定组件能力与跨边界成本 {#sec-cpp-rust.4.16.1}

本节回答一个问题：**把一个 Rust 数据核交给真实 C 调用者之前，要先确定哪些能力、哪些数据路径？**第 1 章说明测量可以静默出错；这一节说明接口设计同样可以——符号能链接、签名能编译，而「返回之后这块内存归谁」没有人写下来。

::: preview 先抓住一件事

**跨边界的第一份设计不是函数签名，而是「本次调用返回之后，数据归谁」。**本章后面 16.3 的数值检查、16.4 的代号句柄、16.5 的 panic 边界这几道守卫，都只为守住一句承诺：Rust 分配仍由 Rust 析构，C 分配仍由 C 释放。判断一个接口能不能发布，就先查这一句在每条路径上是否写成了白纸黑字；肯定它要逐条路径核对，否定它只需要一条被破坏的归属。
:::

### 16.1.1 Rust 是实现主体

项目实现一个不可变整数数据组件，输入和输出元素都是 `u64`。核心映射对每个元素独立执行右移、异或、模乘和模加。数据生成、批量变换、checksum、分配、注册表和线程同步都在 Rust 中；C 只提供真实外部调用者、命令行驱动和测量入口。

这个核刻意保持简单：它让跨边界粒度和所有权路径成为可观察变量。它不是密码学散列，也没有抗碰撞或保密性承诺，不要把本章的 wrapping 映射用于认证令牌或内容签名。

完整实现的安全入口如下：

```rust
#[inline]
pub fn mix(value: u64) -> u64 {
    (value ^ (value >> 29))
        .wrapping_mul(0x9e37_79b9_7f4a_7c15)
        .wrapping_add(0x243f_6a88_85a3_08d3)
}

pub fn transform(input: &[u64], output: &mut [u64]) -> Result<(), i32> {
    if input.len() != output.len() {
        return Err(ECAPACITY);
    }
    for (source, dest) in input.iter().zip(output) {
        *dest = mix(*source);
    }
    Ok(())
}

pub fn checksum(values: &[u64]) -> u64 {
    values.iter().fold(0, |sum, x| sum.wrapping_add(*x))
}
```

Rust 调用者不必经过 FFI 注册表：它直接传递切片，复用编译器对借用的检查（[@def-3.2.1]）。外部入口只是这个算法周围的一层协议适配。先把算法写成安全函数，能减少必须同时推理的未知量。

::: def 定义 16.1.1 · 安全核与协议适配层 safe kernel / protocol adapter {#def-16.1.1}

**安全核**指不触碰裸指针、只用切片和 `Result` 表达工作的那部分实现，本节就是 `mix`、`transform`、`checksum` 三个函数。**协议适配层**指 `extern "C"` 入口：它做数值检查、形成引用、把 `Result` 换成整数码，除此之外不重新实现算法。分层的验收标准只有一条——出问题时能不能只推理一层。
:::

按[@def-16.1.1]，本章的阅读顺序是固定的：先读安全核是否成立，再读适配层有没有把核的前提（长度相等、区间不重叠）检查到位。反过来先读 `unsafe` 块，你会同时面对算法语义和指针语义两个未知量。

### 16.1.2 三种数据路径

第一条路径是同步借入。C 提供输入和输出存储，Rust 在本次调用期间访问它们，函数返回后不保留任何 C 数据指针；它适合调用者已经有缓冲区的批量计算。

第二条路径是复制导入。`rb_create_copy` 把 C 输入复制到 Rust 的不可变存储，成功返回后原 C 输入可以修改或释放，后续查询通过句柄识别新对象。

第三条路径是 Rust 生产结果。`rb_generate` 根据 seed 与长度生成一批值，把句柄和释放责任交给 C，而不交出数据裸指针；C 可以要求元数据和归约结果，也可以显式复制出整个数组。

| 路径 | 调用期间的数据所有者 | 返回后的所有者 | 是否保留 C 指针 |
|:--|:--|:--|:--|
| 同步批量变换 | C | C | 否 |
| create_copy 导入 | C 原件、Rust 新副本 | 两者各自管理自己的分配 | 否 |
| generate 结果 | Rust | Rust 存储，C 承担句柄释放责任 | 否 |
| copy 导出 | Rust 原件、C 输出 | 两者各自管理自己的分配 | 否 |

「所有权转移」是协议责任的转移，它不等于把一个 `malloc` 指针塞进 `Vec`：Rust 分配仍由 Rust 析构，C 分配仍由 C 释放。

::: def 定义 16.1.2 · 所有权路径 ownership path {#def-16.1.2}

**所有权路径**是一次调用里「谁分配、谁读写、谁释放」的完整责任链，由三个问句回答：调用期间谁是数据所有者？返回后谁是？Rust 是否保留了指向 C 分配的指针？三条问句答不全，16.3 的守卫就不知道该检查到哪一步为止。
:::

::: method 判定流程 · 一次跨边界调用该走哪条路径

**数据已经在 C 里，只在本次调用中被使用**：同步借入，不建句柄，也就没有失效问题。<br>
**数据在 C 里，但调用返回之后还要反复查询**：复制导入，用一次复制换独立寿命。<br>
**数据由 Rust 生产，C 只需要摘要**：拥有句柄加 `rb_info`，不做导出复制（16.8 的 `owned_handle` 量化了这次节省）。<br>
**C 要长期逐元素读 Rust 数据**：用 `rb_copy` 复制进 C 自己的分配；可变视图这一版有意不提供，不要临场发明。
:::

### 16.1.4 需求不是「函数能被 C 找到」

导出符号只是集成的第一步。完整需求还包括版本、尺寸、长度单位和错误语义；更关键的是失败之后谁还拥有资源。如果接口失败时顺便消费句柄，调用者就必须知道这一点——本项目明确选择：普通查询和复制失败不消费句柄。

每次成功创建只产生一个释放责任。复制句柄数值不会复制这个责任。并发释放时只能有一个成功者，其余调用得到旧身份错误，而不是再次析构同一块存储。

::: ex 例 16.1.1 · 三个需求，各写一遍调用序列 {#ex-16.1.1}

三个 C 侧需求：① 输入和输出缓冲区已经 `malloc` 好，只想让 Rust 帮忙批量变换；② C 有一块初始化好的数据，用完就 `free`，但之后还要反复查询它的摘要；③ 数据完全由 Rust 生成，C 只要 checksum，不需要每个元素。按[@def-16.1.2]写出各自的调用序列，并回答「返回后谁是数据所有者」。

::: sol 解答

① 同步借入：`rb_transform(in, out, n)` 一次调用。返回后两块内存仍全部归 C，`free` 由调用者做；Rust 一个指针也不留，所以这条路径没有句柄，也就没有 16.4 的失效问题。
② 复制导入：`rb_create_copy(in, n, &h)` → 之后 `free(in)` 合法，因为 Rust 持有的是自己的副本 → `rb_info(h, 1, 24, &info)` 反复查询 → 恰好一次 `rb_release(h)`。原件归 C、副本归 Rust，释放责任只有一个，挂在句柄上。
③ Rust 生产：`rb_generate(seed, n, &h)` → `rb_info(h, 1, 24, &info)` 直接拿到 checksum → `rb_release(h)`。完整数组从未离开 Rust，这条路径省掉的正是 16.8 量化过的那次导出复制。
三条路径的共同点：任何一条里 `free` 一个 Rust 交出来的指针都不合法，因为接口从未交出一个数据指针。
:::

:::

### 16.1.5 不纳入这一版的能力

组件不执行外部回调，也不接收函数指针；它没有让外部异常回到 Rust 的需求；它没有提供可变裸数据视图。因此不必同时设计回调重入、借出视图撤销和原地修改协议。这些是有意削减的接口面，不是把难题藏到未实现函数后面。

::: think 思考 · 让 Rust 接管一块 malloc 内存，省下了什么 {#think-16.1.1}

有人提议加一个 `rb_adopt(p, n)`：把 C 的 `malloc` 指针直接交给 `Vec`，返回句柄，这样连复制导入那一次拷贝也省了。按[@def-16.1.2]，这个接口改掉了哪一句承诺？

::: sol 解答

它把「Rust 分配由 Rust 析构」换成了「Rust 负责释放 C 的分配」，而这就是被藏在未实现函数后面的那种难题：分配器（负责申请和归还堆内存的那层代码）不匹配时，`Vec` 的析构会拿 Rust 的释放例程去处理 C 的分配，属于未定义行为；要让它合法，还得再约定对齐、扩容语义和「哪个线程分配、哪个线程释放」。省下一次复制，换来一整套新的调用者义务。更便宜的替代在 16.8：把结果留在组件内，而不是把所有权交给对方。
:::

:::

### 16.1.6 小结与常见错误

**小结。**① 先写安全核，再包协议适配层，审查时才能一层一层推（[@def-16.1.1]）；② 每条路径都要能用[@def-16.1.2]的三个问句回答，缺一句「返回后归谁」，后面的守卫就不知道要守到哪里；③ 本章的「所有权转移」只指释放责任，不指分配器交换（[@ex-16.1.1]）；④ 有意削减的能力要明写，未实现不等于已经支持。下一节 [16.2 版本化布局与整数错误协议](#sec-cpp-rust.4.16.2) 把外部可见的表示缩小到两侧都能锁定的范围。

::: errata 常见错误清单（16.1 节）

E-a **把导出符号当成接口需求。**版本、尺寸、长度单位、错误语义、失败后的归属都还没定。先查头文件里有没有写「返回之后谁拥有」。

E-b **用 `free` 处理 Rust 交出来的东西。**本章从不交出数据地址，句柄只能由 `rb_release` 消费一次（[@ex-16.1.1]）。

E-c **交换分配器还自称转移了所有权。**Rust 的析构不会去调用 C 的 `free`（[@def-16.1.2]，见本节思考）。

E-d **先设计 `extern "C"` 签名，再补算法。**同时推理指针层和算法层，出错率最高；按[@def-16.1.1]的顺序反过来。

E-e **忘了「失败不消费句柄」这条承诺。**调用者的清理代码就得按分支写，16.5 的 CLI 规则会立刻变复杂。

E-f **把削减掉的能力说成「以后再加」。**回调与可变视图一旦进来，16.3 和 16.5 的整套守卫都要重写；要先说清它们为什么不属于这一版。

:::

## 16.2 版本化布局与整数错误协议 {#sec-cpp-rust.4.16.2}

本节回答一个问题：**哪些表示可以跨过边界被别人依赖，依赖之后怎么锁定？**16.1 定下责任，这一节定下形状：一旦某个布局出现在头文件里，改它就是破坏别人的程序。

::: preview 先抓住一件事

**能被外部读写的形状就是 ABI，凡是进 ABI 的东西必须两侧各锁一次。**本节的判断标准很具体：Rust 侧有 `size_of`、`align_of`、`offset_of!` 断言，C 侧有 C11 静态断言，两边都要真的编译过。只在一侧写期望表、或者只写在正文里，都算不上锁定。
:::

### 16.2.1 只让必要的表示成为 ABI

外部可见类型只有固定宽度整数、指针和一份元数据结构。不把 `Vec`、`Arc`、`Result` 或 Rust 枚举布局暴露给 C：注册表内部怎么换容器，不应影响 C 的头文件；同样，C 调用者也不需要知道引用计数头的字节偏移。

元数据的 Rust 定义是：

```rust
#[repr(C)]
#[derive(Clone, Copy, Debug, Default, PartialEq, Eq)]
pub struct InfoV1 {
    pub abi_version: u32,
    pub struct_size: u32,
    pub len: u64,
    pub checksum: u64,
}
```

`repr(C)` 给出本机目标下的 C 结构布局规则（[@def-2.1.1] 的三元组在这里被固定下来）。它不是序列化格式，也不自动解决大小端转换；结构里若放入 Rust 专有类型，外层标记也不能替它发明 C 表示。本项目因此只使用对应的固定宽度整数。

::: def 定义 16.2.1 · ABI 面 ABI surface {#def-16.2.1}

**ABI 面**指跨语言双方都能依赖的表示集合：导出符号的名字与调用约定、参数与返回值的类型、结构体的尺寸与字段偏移，以及每个字段的单位和含义。判断一个类型该不该进 ABI 面的问题是：「对方改了它，我要不要重新编译？」答案是需要，就锁死它；答案是不需要，就别让它出现在头文件里。
:::

### 16.2.2 两侧都检查布局

本轮目标是 `aarch64-apple-darwin`。Rust 测试使用 `size_of`、`align_of` 与 `offset_of!`，C 头文件使用 C11 静态断言；二者各自经过实际编译，不是只在正文里写一个期望表。

| 对象或字段 | 本机尺寸 | 本机对齐 | 字段偏移 |
|:--|--:|--:|--:|
| rb_handle / u64 | 8 | 8 | 不适用 |
| InfoV1 / rb_info_v1 | 24 | 8 | 不适用 |
| abi_version / u32 | 4 | 4 | 0 |
| struct_size / u32 | 4 | 4 | 4 |
| len / u64 | 8 | 8 | 8 |
| checksum / u64 | 8 | 8 | 16 |

表格描述的是这份发行物的目标约束。头文件还断言指针大小为 8；32 位目标不会悄悄套用这张表，而会在构建阶段拒绝。没有执行过的目标不写成「天然兼容」。

C 侧对应断言包含：

```c
_Static_assert(sizeof(rb_info_v1) == 24, "v1 size");
_Static_assert(_Alignof(rb_info_v1) == 8, "v1 alignment");
_Static_assert(offsetof(rb_info_v1, abi_version) == 0, "version offset");
_Static_assert(offsetof(rb_info_v1, struct_size) == 4, "size offset");
_Static_assert(offsetof(rb_info_v1, len) == 8, "length offset");
_Static_assert(offsetof(rb_info_v1, checksum) == 16, "checksum offset");
```

这六行与 Rust 侧 `tests/contracts.rs::layout_matches_c_v1` 的六个断言一一对应：尺寸 24、对齐 8、偏移 0/4/8/16。它们各自经过实际编译，任何一侧改动都会在构建期失败，而不是等到运行期读出错乱的字段。

### 16.2.3 版本和尺寸由调用参数先行声明

`rb_info` 接收版本和输出结构字节数，只有版本为 1 且尺寸恰好为 24 时才写结构。它不先读取一份可能未初始化的输出结构来猜调用者版本；输出结构里的两个头字段用于结果自描述，而不是输入协商。

这个选择不支持「旧调用者自动忽略新尾字段」。以后扩展时应增加新版本或新入口；保持 v1 的定义不变，比把字段插到结构中间更容易审查。如果要支持前缀兼容，应重新定义明确的最小尺寸与写入上界，不能仅把等号改成大于等于就声称已完成兼容设计。

::: def 定义 16.2.2 · 自描述输出与输入协商 {#def-16.2.2}

**自描述输出**指结构里的 `abi_version` 和 `struct_size` 两个头字段，它们描述的是本次写出的东西是什么版本、多大，供调用者事后核对。**输入协商**指调用者在写入之前通过参数声明自己期望的版本与尺寸。两者容易混淆：前者是结果的一部分，后者是守卫的输入。本项目的顺序是先按[@def-16.2.2]的输入协商拒绝不匹配，再考虑写不写输出。
:::

::: method 判定流程 · 要不要给 ABI 结构加一个字段

**新字段只服务内部实现**：不加，注册表换容器不该动头文件（[@def-16.2.1]）。<br>
**新字段是给调用者的新能力**：定义 v2 结构和新入口，v1 的定义保持不变。<br>
**想省一个入口、让 v1 调用者忽略尾字段**：那是前缀兼容，必须先写清最小尺寸和写入上界，本项目没有实现，就不要在文档里暗示它可用。<br>
**已经发布 v1**：把字段插到结构中间 = 破坏所有旧调用者的偏移，只能新增版本。
:::

### 16.2.4 错误码是一份稳定词表

外部函数返回 `i32`，C 声明对应 `int32_t`：成功为 0，普通错误保持非零整数。没有借出的错误字符串，也没有线程局部最后错误缓冲，因此不存在「下一次调用把上一条错误文本覆盖」的隐式寿命。

| 数值 | 名称 | 典型触发 | 资源后果 |
|--:|:--|:--|:--|
| 0 | OK | 操作成功 | 按具体操作提交结果 |
| 1 | EINVAL | null、对齐、重叠、版本或尺寸错误 | 不消费原句柄 |
| 2 | ERANGE | 长度上限、转换或地址算术溢出 | 不创建结果 |
| 3 | ESTALE | 无效槽、旧代、重复释放 | 不再释放资源 |
| 4 | ECAPACITY | C 输出容量小于对象长度 | 数据和 written 不写 |
| 5 | EPANIC | 捕获到 Rust unwind panic | 不承诺进程已全面恢复 |
| 6 | EPOISON | 注册表锁被毒化 | 拒绝继续解释注册表状态 |
| 7 | ERESOURCE | 可报告的预留失败或槽上限 | 局部临时资源由 Rust 回收 |

一个输入同时违反多条规则时，不保证每版都返回同一种优先错误。例如坏版本与旧句柄并存，本版先检查版本。调用者应只依赖文档允许的错误集合，不解析内部检查顺序；若业务需要精确诊断，应增加专门诊断能力，而不是猜分支。

::: def 定义 16.2.3 · 稳定错误词表 stable error vocabulary {#def-16.2.3}

**稳定错误词表**指一份发布后不再改变含义的整数集合：每个数值对应一种可判定的资源后果（是否消费句柄、是否写输出）。它的「稳定」只承诺两件事——同一数值不会因为一次改版而换意思，也不会因为某次实现调整而凭空多出一个新值。它不承诺检查顺序，也不承诺同一输入在多条规则同时被违反时返回哪一种（本节上文）。
:::

::: ex 例 16.2.1 · 一次调用违反两条规则，谁接住 {#ex-16.2.1}

同一组误用在两侧都跑过，但夹具参数不同：Rust 侧（`tests/contracts.rs` 的 `cleanup_capacity_stale_and_version`）建的是**长度 3** 的对象（checksum 60），C 侧（`c/tests.c`）建的是**长度 4** 的。下面四步各标了自己那一侧：① `rb_info(h, 2, 24, &info)`（两侧都有）；② `rb_info(h, 1, sizeof(info) - 1, &info)`，尺寸 23（C 侧独有）；③ `rb_copy(h, short_out, 2, &written)`，输出只有 2 格、`written` 预置哨兵（C 侧哨兵是 71/72 与 777，Rust 侧是 999 与 888）；④ 释放之后再 `rb_info(h, 1, 24, &info)`（Rust 侧）。给出每次返回码、输出是否被改动，以及接住它的那道守卫。

::: sol 解答

① 返回 `EINVAL`（1）。被破坏的是[@def-16.2.2]的输入协商：版本必须是 1。接住它的是 `rb_info` 函数体的第一条判断，它在 `range(out, 1)` 和句柄查找之前，所以 `info` 一个字节都没写，仍是调用者的原值。
② 同样返回 `EINVAL`，原因是尺寸必须恰好等于 24；传 23 不会被当成「前缀兼容」而少写一格（见本节判定流程）。

③ 返回 `ECAPACITY`（4）。被破坏的是「容量必须覆盖完整对象」，接住它的是 `rb_copy` 里 `capacity < data.len()` 那次判断——它在 `copy_nonoverlapping` 之前，也 `written.write` 之前，所以 `short_out` 两格和 `written` 的 777 都保持原值（Rust 契约测试用的是 999/888 哨兵，结论一样）。
④ 返回 `ESTALE`（3）。此时消费的是[@def-16.4.1]的身份不变量：槽里已经没有所有者。注意 ①③④ 都没有消费句柄——只有 ④ 之前那次 `rb_release` 消费了它，所以 ①②③ 之后仍可正常调用。
:::

:::

### 16.2.5 输出提交点

创建入口先构造数据，再登记句柄，最后写输出句柄；普通参数错误时不覆盖调用者原有值。查询先完成快照和 checksum，再写完整元数据。复制先验证容量，最后才复制并写入 written。

这些承诺是普通受控错误路径的行为，不是面对任意硬件故障的事务系统：panic 被捕获也不自动提供业务回滚，本项目核函数没有在写出一半后主动 panic 的分支。将来添加可失败变换时，必须重新讨论部分输出。

### 16.2.6 长度单位不能含糊

所有数据长度和容量都以 `u64` 元素计数，只有 `rb_info` 的 bytes 参数以字节计数。两种单位在名称、文档和检查里分开，内部再用受检查转换得到 `usize`。单对象上限为 `2^24` 个元素，而不是 `2^24` 字节；这个上限是项目资源策略，不是 Rust 切片的语言上限（[@def-2.3.1] 的地址跨度与有效负载之别在这里就是判据）。

::: think 思考 · 把上限从「元素」改成「字节」会怎样 {#think-16.2.1}

有人觉得以字节计更直观：`RB_MAX_BYTES = 2^24`，检查 `len * 8 <= 上限`。按本节，这个改动破坏了[@def-16.2.3]的哪一条？

::: sol 解答

破坏的是「同一数值的含义发布后不再改变」。`ERANGE` 现在意味着「元素数越界」，改成字节后同样的返回码对应另一个阈值，旧调用者传入的 2^24 个元素本来合法、现在会被拒。要改就得升版本、给新入口，并且新旧两套上限不能由同一个返回码承担两种解释；单位属于 ABI 面（[@def-16.2.1]），不是实现细节。
:::

:::

### 16.2.7 小结与常见错误

**小结。**① 进 ABI 面的表示必须两侧各锁一次，且都要真的编译过（[@def-16.2.1]）；② 版本与尺寸是输入协商，结构头字段只是自描述，别把两者混成一句「向后兼容」（[@def-16.2.2]）；③ 错误词表稳定的是数值含义与资源后果，不是检查顺序（[@def-16.2.3]）；④ 每条误用都能指出被破坏的不变量和接住它的守卫（[@ex-16.2.1]）。下一节 [16.3 指针守卫](#sec-cpp-rust.4.16.3) 处理这些判断之前必须先过的一关：裸指针。

::: errata 常见错误清单（16.2 节）

E-a **只在一侧写布局期望。**Rust 断言改了、头文件没改，要到运行时字段错乱才暴露。先查两侧断言是否都进过编译。

E-b **给已发布结构插字段。**旧调用者的偏移全部失效，只能新增版本（[@def-16.2.1]）。

E-c **把等号改成大于等于就叫兼容。**前缀兼容需要另外定义最小尺寸与写入上界（本节判定流程）。

E-d **猜实现的检查顺序。**坏版本与旧句柄并存时返回的是 `EINVAL` 而不是 `ESTALE`，这属于未承诺的细节（[@ex-16.2.1]）。

E-e **加一个线程局部最后错误。**它制造「下一次调用覆盖上一条文本」的隐式寿命，正好是整数词表想避免的（[@def-16.2.3]）。

E-f **把长度单位写成「大概都是字节」。**`2^24` 是元素数，字节口径要另算且会改变返回码含义（见本节思考）。

:::

## 16.3 指针守卫与不能替调用者证明的条件 {#sec-cpp-rust.4.16.3}

本节回答一个问题：**裸指针进 `unsafe` 之前能查清多少，剩下的缺口归谁？**16.2 锁定了表示，这一节要说明检查的能力上限——它只能拒绝显然错误的输入，证明不了分配真实存在。

::: preview 先抓住一件事

**检查的顺序就是检查的一部分。**同一个 null 判断，放在 `from_raw_parts` 之前是守卫，放在之后就是拿非法引用去触发未定义行为。本节所有判断都围绕这一句：先数值、后引用；能查的写进代码，查不动的写进头文件里的调用者义务（[@def-3.7.1]）。
:::

### 16.3.1 先检查数值，再形成引用

FFI 入口收到的是裸指针，而 Rust 的类型系统不会跨语言证明它们来自有效分配，因此检查必须发生在 `from_raw_parts` 之前：一旦先形成非法引用再检查 null，就已经太迟。

项目把共同的数值检查放在 `range` 中。它返回半开地址区间，用于检测参数重叠；其中的地址整数仅用于拒绝显然错误的输入，程序不会把算过的整数地址重新制造为可解引用指针（[@def-3.7.2] 的地址与来源之别在此是硬约束：区间算术不重建来源）。

```rust
fn range<T>(ptr: *const T, len: usize) -> Result<(usize, usize), i32> {
    if len == 0 {
        return Ok((0, 0));
    }
    if ptr.is_null() || !(ptr as usize).is_multiple_of(align_of::<T>()) {
        return Err(EINVAL);
    }
    let bytes = len.checked_mul(size_of::<T>()).ok_or(ERANGE)?;
    if bytes > isize::MAX as usize {
        return Err(ERANGE);
    }
    let start = ptr as usize;
    Ok((start, start.checked_add(bytes).ok_or(ERANGE)?))
}
```

本项目使用它的类型都不是零尺寸类型：数据元素是 `u64`，元数据是固定结构。不能把这个小工具脱离上下文当成任意泛型内存验证库——它从未查询操作系统映射表，也无法发现悬垂分配。

::: def 定义 16.3.1 · 数值守卫 numeric guard {#def-16.3.1}

**数值守卫**指只看整数就能完成的检查：是否为零长、指针是否非空、地址是否满足对齐、`len * size_of` 是否溢出、总字节是否超过 `isize::MAX`、两个半开区间是否相交。它的产物只是一对地址整数和一个返回码。与之相对的是**语义前提**：这段地址是否属于一个存活分配、内容是否已初始化、有没有别的线程同时在写——这些都不是数值能算出来的（[@ex-16.3.1] 逐个给出反例）。
:::

### 16.3.2 空数据不构造空指针切片

C 常用 null 表示空数组，而 Rust 的切片引用即使长度为 0 也有非空和对齐要求。所以 `rb_transform` 在长度为 0 时直接成功返回，不会把 null 交给 `from_raw_parts`；复制导入和复制导出也分别跳过零长度数据访问。

元数据输出不是空数组。输出句柄、written 和 `InfoV1` 始终要求一个完整可写对象，不能用「这次没有数据」解释为什么输出句柄指针可以是 null。测试覆盖了空对象的完整创建、复制和释放链：`rb_create_copy(null, 0, &h)` 成功、`rb_copy(h, null, 0, &n)` 返回 OK 且把 n 写成 0。

### 16.3.3 重叠拒绝先于借用

`rb_transform` 不支持原地变换：它要求输入区域与输出区域分离，如果两个地址区间相交就返回 `EINVAL`。只有数值检查和重叠检查都通过，才形成只读输入和独占输出切片。

```rust
fn separate(a: (usize, usize), b: (usize, usize)) -> Result<(), i32> {
    if a.0 < b.1 && b.0 < a.1 {
        Err(EINVAL)
    } else {
        Ok(())
    }
}
```

输出数据与 written 也必须分离，否则最后写一个长度就可能覆盖刚复制出的数据；复制导入时，输入与输出句柄同样做区间检查。这些检查覆盖本次调用可见的参数关系，它们不能找出其他线程偷偷持有的别名（[@def-3.2.1]）。

::: ex 例 16.3.1 · 三次误用，各被哪一关接住 {#ex-16.3.1}

①②在 C 侧真实执行过（`projects/ffi-bridge/c/tests.c:31-34`），输入数组 `input` 与输出数组 `output` 都是活对象：① `rb_transform(input, input, 4)`，把同一个首地址同时当输入和输出；② `rb_transform(NULL, output, 1)`，null 配一个非零长度。③ 未对齐那条只在 Rust 侧执行（`tests/contracts.rs:36-42`：从 24 字节数组里取一个未对齐地址再 `rb_transform(misaligned, …, 1)`），因为 C 里构造未对齐指针本身是 UB，把它写成「C 测试执行过」就是无中生有；16.3.5 已经按这个口径区分过两侧。逐一说明被破坏的前提、`range`/`separate` 的判断顺序、返回码，以及「有没有可能它其实已经读了内存」。

::: sol 解答

① 被破坏的是[@def-3.2.1]的排他访问：同一块存储既做只读借用又做独占借用。`checked_len(4)` 通过后，`separate(range(input,4), range(input,4))` 得到 `a.0 < b.1 && b.0 < a.1` 成立，返回 `EINVAL`。两次 `range` 只算了整数，`from_raw_parts` 从未被调用，所以不存在「读到一半」的状态。
② 被破坏的是非空。`range(output, 1)` 里 `len != 0`，于是检查 `ptr.is_null()`——注意被检查的是 null 那一侧，返回 `EINVAL`。若顺序颠倒、先构造切片，就是拿 null 形成引用，程序已经错了。

③ 被破坏的是对齐。测试从真实字节数组得到一个未对齐裸指针（构造裸指针本身不读内存），入口在 `range` 里用 `is_multiple_of(align_of::<u64>())` 拒绝，返回 `EINVAL`，没有形成 `u64` 引用，也没有在 C 里做可能违反对齐要求的指针类型转换。
三条的共同点：守卫全部在形成引用之前；每一条都能在没有任何未定义行为发生的前提下被验证。
:::

:::

### 16.3.4 真正的 unsafe 证明分两半

| 条件 | 入口能检查什么 | 调用者仍须保证什么 |
|:--|:--|:--|
| 非空 | 非零区域指针不为 null | 指向实际存活分配 |
| 对齐 | 地址满足类型对齐数值 | 对象表示和目标类型匹配 |
| 长度 | 上限、乘法、转换和地址加法 | 分配真实容量足够 |
| 单分配 | 不能可靠检查 | 整段不能拼接多个相邻分配 |
| 初始化 | u64 位模式均有效 | 每个输入元素已初始化 |
| 别名 | 本次参数区间是否重叠 | 外部无冲突访问和数据竞争 |
| 寿命 | 不保存外部指针 | 返回前分配不能失效 |
| 可写性 | 不能可靠检查 | 输出不是只读页或失效对象 |

注意「所有 u64 位模式（内存里各比特的具体排列）有效」不代表未初始化字节可以读：位模式有效性和初始化状态是两件事（[@def-2.2.1]、[@def-3.3.2]）。同样，地址不溢出也不代表区间属于同一个分配；操作系统可访问页不等于 Rust 对象寿命仍有效。

::: def 定义 16.3.2 · 调用者义务 caller obligation {#def-16.3.2}

**调用者义务**指入口在函数体内无法证明、必须由对方用文档承担的前提，本项目的头文件把它们写成五条：整段区间属于一个有效分配；对象表示与目标类型匹配；分配真实容量足够且返回前不失效；本次调用的各参数区域两两不相交；没有别的线程并发访问同一输出。义务写在文档里而不是代码里，不代表它更弱——它一旦被破坏，返回码不会来救你（[@ex-16.3.1] 只覆盖能被代码接住的那几种）。
:::

### 16.3.5 安全的负面测试怎么写

C 测试传入真实数组的相同首地址作为输入和输出；入口在形成引用前识别重叠并返回错误，它不执行那次重叠变换。这验证的是守卫，而不是执行一个未定义行为版本看看会不会崩溃。

对齐拒绝测试放在 Rust 契约测试中：测试从真实字节数组得到一个未对齐裸指针——创建这种 Rust 裸指针本身不读取内存——入口检查对齐后返回，不形成 `u64` 引用。测试没有在 C 中进行可能违反对齐要求的指针类型转换。

坏长度测试使用超上限值：实现先检查长度，再检查和访问数据，这样可以安全验证 `u64::MAX` 被拒绝。不能把 null 配一个可接受的非零长度后绕过检查强行读取，更不能真的读释放后的 C 缓冲来测试 `catch_unwind`；至于故意触发 panic 的探针（测试里故意安排的一次触发），它只能在取得注册表锁之前发作，理由见 16.5。

::: method 判定流程 · 一个指针参数进 unsafe 之前要过哪几关

① **零长先放行**：`len == 0` 直接返回空区间，null 在这里合法（仅数据区域）。<br>
② **非空与对齐**：`ptr.is_null()`、`地址 % align_of == 0`，违反给 `EINVAL`。<br>
③ **算术不溢出**：`len.checked_mul(size_of)`、结果不超过 `isize::MAX`、`start + bytes` 不绕回，违反给 `ERANGE`。<br>
④ **两两区间不相交**：对每对参数调用 `separate`，相交给 `EINVAL`。<br>
⑤ **此后才允许** `from_raw_parts`，且作用域不越过本次调用。<br>
⑥ **剩下两关代码查不动**：是否同一分配、是否存活且无并发访问 —— 进[@def-16.3.2]，写进头文件。
:::

### 16.3.6 不假装这是沙箱

如果调用者给一个对齐但悬垂的地址，接口无法保证返回错误；如果另一个线程在调用期间释放输入，Rust 无法事后补救；如果调用者对同一输出并发写入，注册表互斥锁也不会保护那块 C 内存。错误码只覆盖被检查和受支持的错误，对任意恶意地址提供内存隔离需要进程等更强边界（[@def-2.6.2] 的有限安全组件与此是同一个取舍）。

::: think 思考 · 查一下操作系统映射表，是不是就安全了 {#think-16.3.1}

有人提议：在 `range` 里加一次 `mach_vm_region`/`mincore` 之类的查询，确认地址确实映射着，这样悬垂指针也能被拒。这个改动能覆盖[@def-16.3.2]的几条义务？

::: sol 解答

一条也覆盖不全。第一，查询与被查内存之间有竞态：这一刻映射着，下一刻可以被 `free`，检查并没有建立寿命（TOCTOU）。第二，「映射着」不等于「属于同一个分配」，更不等于它属于调用者声称的那个对象——分配器早就把地址复用了。第三，它把每个入口的常数开销抬高，而这恰恰是 16.7 要测的边界成本。真要隔离恶意输入，边界应该设在进程之间，不是设在一次函数调用的入口。
:::

:::

### 16.3.7 小结与常见错误

**小结。**① 顺序本身就是守卫的一部分，先数值后引用（[@def-16.3.1]）；② 零长数据可以让 null 过，元数据输出永远不行；③ 每一次拒绝都要能在没有未定义行为的前提下被测试（[@ex-16.3.1]）；④ 代码查不动的前提要写成[@def-16.3.2]，而不是假装「加个检查就好」；⑤ 本组件是有限安全边界，不是沙箱。下一节 [16.4 代号句柄](#sec-cpp-rust.4.16.4) 处理唯一还需要跨调用存活的东西：身份。

::: errata 常见错误清单（16.3 节）

E-a **先构造切片再检查。**引用一旦形成就已经违约，后面返回错误码也补救不了。先查 `from_raw_parts` 的调用点在所有检查之后。

E-b **把非空检查当成指针有效性证明。**对齐且非空仍可悬垂、只读或越出分配（[@def-16.3.2]）。

E-c **用两个相邻分配拼一段区间。**加法查不出来源，连续性推不出「同一分配」（[@def-3.7.2]）。

E-d **「u64 什么位模式都合法，所以未初始化也能读」。**合法值集合与初始化状态是两个问题（[@def-2.2.1]）。

E-e **靠「越界大概会崩」来测试负面分支。**要执行UB才能验证的检查不算验证（[@ex-16.3.1]）。

E-f **以为注册表锁保护了 C 的输出缓冲。**它只保护身份映射，外部共享输出的数据竞争仍是调用者的责任。

## 16.4 代号句柄、释放线性化与并发快照 {#sec-cpp-rust.4.16.4}

本节回答一个问题：**一个整数怎么同时充当身份、所有权凭证和并发检查点？**16.3 的守卫只活在一次调用里；句柄要跨调用，于是必须回答「旧身份怎么办、谁负责释放、正在读的怎么办」。

::: preview 先抓住一件事

**地址不能当身份，因为分配器会复用地址。**本节把身份与地址拆开：句柄高 32 位是代号（generation），低 32 位是槽下标加一。判废一个句柄要同时过三关——低位非零、槽存在、代号相等且槽里还有数据，少任何一关都会把旧身份和新数据拼在一起。
:::

### 16.4.1 不把地址当身份

直接把分配地址强转成整数，不能可靠识别旧对象：旧地址可能被后来的分配复用，调用者手里仍有同样数值，却指向一个不同生命期。本项目让外部身份与数据地址分离。

句柄高 32 位是 generation，低 32 位是槽下标加一，低位为 0 保留为无效身份。本项目最多 4096 槽，实际下标远小于 32 位上限；这不是把 4096 写进 ABI 位宽，而是当前资源边界。

::: def 定义 16.4.1 · 代号句柄 generation handle {#def-16.4.1}

**代号句柄**是一个 `u64`：高 32 位是该槽当前的代号，低 32 位是槽下标加一，低位为 0 表示无效身份。它承担三条不变量——同一槽的代号在一次库实例生命周期内单调不减（16.4.3）、槽必须存在、槽必须仍持有所有者。三条同时成立才算有效身份，所以句柄既不是地址，也不是权限凭证（16.4.8）。
:::

| 组成 | 位数 | 有效性规则 | 作用 |
|:--|--:|:--|:--|
| generation | 32 | 与槽当前代号相等 | 拒绝旧生命期 |
| index + 1 | 32 | 非零且槽存在 | 定位内部槽 |
| data 存在性 | 内部状态 | 槽必须仍持有 Arc | 拒绝已经释放的当前代 |

### 16.4.2 空槽复用

第一次使用一个槽时，代号为 1。释放时取走数据，但保留代号；再次使用该槽时，把代号递增后再登记新数据。因此新对象的句柄不同于旧对象。

复用核心来自完整实现：

```rust
if let Some((index, slot)) = self
    .slots
    .iter_mut()
    .enumerate()
    .find(|(_, slot)| slot.data.is_none() && slot.generation < u32::MAX)
{
    slot.generation += 1;
    slot.data = Some(data);
    return Ok((u64::from(slot.generation) << 32) | (index as u64 + 1));
}
```

### 16.4.3 不回绕比「几乎不会发生」更明确

代号达到 `u32::MAX` 的槽不再复用，它会退休，而不是回到 1。这样不会在该库实例的生命期内重新产生同一个槽代组合。测试直接构造一个已到最大代号的空槽，验证插入改用新槽。

这是一种可证明的身份策略。代价是极端长期运行下可用槽会逐渐减少，达到槽上限时返回 `ERESOURCE`。如果系统需要可无限复用的身份，不能只把位宽加大后省略寿命证明，还应定义调用者最长持有期限和实例重启协议。

::: ex 例 16.4.1 · 一个句柄的三次生命 {#ex-16.4.1}

空注册表上依次执行（下标从 0 计，按[@def-16.4.1]的编码规则算出数值）：① `insert` 得到句柄 `h1`；② `release(h1)`；③ 再 `insert` 得到 `h2`；④ 用 `h1` 调 `snapshot`；⑤ 另起线程同时用 `h2` 调 12 次 `release`。给出每个句柄的数值、每步的代号比较结果和返回码。

::: sol 解答

① 槽 0 首次启用，代号 1，`h1 = (1 << 32) | 1 = 4294967297`（十六进制 `0x1_0000_0001`）。
② `release` 在锁内 `take()` 走 Arc，返回 OK。此后槽 0 的代号仍是 1，但 data 为空。
③ 复用槽 0：代号加一变成 2，`h2 = (2 << 32) | 1 = 8589934593`。`h2 != h1`，尽管它们指向同一个槽、甚至可能指向复用后的同一块地址。
④ `h1` 的低位 1 定位到槽 0，代号字段是 1，而槽当前代号是 2，第二关就失败，返回 `ESTALE`；即便调用者还留着旧数值，它也进不到数据。
⑤ 12 个线程同时释放 `h2`：恰好一个拿到 OK，其余 11 个看到 data 已空得到 `ESTALE`（契约测试逐个数过）。不会出现两份都自认为是最后所有者的析构。
:::

:::

### 16.4.4 查找必须同时检查三件事

查找先拒绝低 32 位为 0，然后检查下标是否存在，最后比较代号并确认该槽仍有数据。仅仅「下标没越界」不足以证明句柄有效，仅仅「代号相等」也不能证明当前对象尚未释放。

这些步骤在同一个注册表锁内完成。不能先在锁外检查代号，再等一会儿获取数据——中间若发生释放和复用，就会把旧身份检查与新数据拼在一起。本项目不把检查结果缓存成一个长期裸槽指针。

### 16.4.5 读取拿快照，计算不持全局锁

内部对象是不可变的 `Arc<[u64]>`。查询和复制在持锁期间克隆 Arc，之后释放锁，在快照上执行 checksum 或复制——这使大数组计算不必独占整个注册表。

不可变数据减少了协议面：读取者不会在释放锁后争夺可变借用。Arc 负责存活，Mutex 负责身份映射，两个机制解决不同问题，不能用「用了 Arc」省略注册表同步（[@def-16.3.2] 的并发义务仍属于调用者自己那份输出缓冲）。

::: def 定义 16.4.2 · 快照 snapshot {#def-16.4.2}

**快照**是在注册表锁内克隆出来的一个 `Arc<[u64]>`：它拥有对自己那份不可变数据的引用计数，因此它的有效期与槽无关。槽被释放、代号被递增，都不会让已经到手的快照失效——这是 16.4.7 里「release 之后仍能读完」的全部依据。
:::

### 16.4.6 release 的线性化点

释放在锁内从槽中取走 Arc，这一动作让之后的查找返回 `ESTALE`；锁外再 drop 取出的所有者，大分配的最终析构不会故意放在全局锁内。

并发两次释放的结果因此明确：先取走对象的一方成功，后一方即使代号相同，也因为 data 已空而失败。不会出现两份都认为自己是最后所有者的裸指针析构。

::: def 定义 16.4.3 · 线性化点 linearization point {#def-16.4.3}

**线性化点**（linearization point，并发操作在外界看来「生效」的那一瞬间）指一个操作「在语义上真正发生」的时刻，其余耗时都在它前后。`rb_release` 的线性化点是锁内的 `take()`：从这一刻起新查找必然 `ESTALE`，而锁外的 `drop` 只是清理成本。把这两步分清，才能说清[@def-16.4.2]的读者为什么既可能读完也可能被拒，两种都合法。
:::

### 16.4.7 release 返回不等于所有读者结束

如果读取先拿到快照，再发生释放，读取可以正常完成；如果释放先移除槽，再开始读取，读取返回 `ESTALE`。这两种结果都符合协议——`release` 并不是「等待全部读取结束」的 join 操作。

内部单元测试保留一个快照，然后释放注册表所有者，它随后仍能安全读取快照的 checksum；这个确定性测试证明了存活机制。另一个并发测试允许读者得到 OK 或 `ESTALE`，检验真实竞态的合法结果集合。

### 16.4.8 身份不是权限，也不是可持久化主键

知道一个句柄数值的人可能调用释放，所以代号设计防的是误用旧生命期，不是恶意猜测，外部授权必须另行设计。把句柄写进文件，换一个进程或另一个加载实例后也没有意义；静态库若被分别链接进不同模块，甚至可能有不同注册表实例（[@def-16.4.1] 的单调性只在单个实例内成立）。

::: think 思考 · 把代号从 32 位扩到 64 位，槽就永远不会退休 {#think-16.4.1}

槽位 32 + 代号 32 已经用满一个 `u64`。有人提议改用 `u128` 句柄，或干脆让代号回绕，理由是 `2^32` 次复用「几乎不可能发生」。按本节的判据，这个说法漏了哪一步？

::: sol 解答

漏的是「可证明」与「概率低」的区别。回绕意味着存在一条真实的执行序列，能让旧句柄重新指向一个新对象——那时调用者手里的数值完全合法，守卫全部通过，拿到的是别人的数据；而退休策略把这条序列从设计里删掉了，代价可以算出来（极端长期运行下槽变少、到上限返回 `ERESOURCE`）。换成 128 位句柄还会破坏[@def-16.2.1]：`rb_handle` 的宽度是 ABI 面的一部分。要真正解决，得给句柄加「最长持有期限」和实例重启协议，而不是把位宽变大后继续靠「几乎不会」。
:::

:::

::: method 判定流程 · 拿到 ESTALE 之后先查什么

① **先看低位**：为 0 说明拿的是初值或默认值，根本没有创建成功。<br>
② **再看是不是第二次释放**：一次创建只有一个释放责任，重复释放必然 `ESTALE`（[@ex-16.4.1]）。<br>
③ **再查句柄来源**：来自另一个进程、另一份库实例或文件，本来就不属于这张注册表（16.4.8）。<br>
④ **若句柄确实有效过**：检查是不是并发释放，另一方已经取走所有者（[@def-16.4.3]）。<br>
⑤ **不要在 `ESTALE` 之后继续读**：这个返回码不携带「还能不能再试」的信息，重试要重新创建。
:::

### 16.4.9 小结与常见错误

**小结。**① 身份与地址分离，代号句柄的三关缺一不可（[@def-16.4.1]）；② 代号退休而不是回绕，这才叫可证明（[@ex-16.4.1]、[@think-16.4.1]）；③ 读取用快照，计算不持全局锁（[@def-16.4.2]）；④ `release` 的语义发生在锁内 `take()`，锁外 `drop` 只是成本（[@def-16.4.3]）；⑤ release 返回不等于读者结束，句柄也不是权限。下一节 [16.5 panic 防线](#sec-cpp-rust.4.16.5) 处理最后一种失败：代码内部炸了。

::: errata 常见错误清单（16.4 节）

E-a **把地址当身份。**分配器会复用地址，旧数值可以指向新生命期。先查身份里有没有代号这一维（[@def-16.4.1]）。

E-b **让代号回绕或只加大位宽。**「几乎不会发生」不是证明；退休才是当前可审查的策略（见本节思考）。

E-c **锁外查代号、锁内取数据。**两步之间发生释放与复用，就把旧身份和新数据拼在了一起（16.4.4）。

E-d **以为 Arc 取代了注册表锁。**Arc 管存活，Mutex 管身份映射，两件事（[@def-16.4.2]）。

E-e **把 release 当成 join。**它不等读者；先拿到快照的读者照样能完成（[@def-16.4.3]）。

E-f **把句柄数值当权限，或写进文件跨进程用。**它只在当前加载实例内有意义，知道数值的人就能释放（16.4.8）。

:::

::: method 即时自测 · 16.4

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　一个句柄要过哪三关才算有效？这些检查在哪里完成？

::: sol 第 1 题答案
低位非零且槽存在、代号与槽当前值相等、槽仍持有所有者。三关在同一次注册表锁内完成（[@def-16.4.1]）。
:::

**第 2 题 · 辨析**　「`rb_release` 返回 OK 之后，任何线程都不可能再读到那块数据。」对在哪、错在哪？

::: sol 第 2 题答案
对在：新查找必然 `ESTALE`。错在「任何线程」：先克隆出快照的读者仍能把 checksum 算完（[@def-16.4.2]、[@def-16.4.3]）。
:::

**第 3 题 · 应用**　某个槽的代号已经是 `u32::MAX` 且为空。现在插入新对象，会发生什么？注册表随后少了几格？

::: sol 第 3 题答案
`find` 的 `slot.generation < u32::MAX` 条件让它被跳过，插入改用新槽；若已达 4096 槽上限则返回 `ERESOURCE`。该槽从此退休，可用槽少一格——这就是不回绕策略的代价（[@ex-16.4.1]）。
:::

**第 4 题 · 迁移**　要支持「句柄在 10 分钟后自动失效」的新需求。按本节，该加什么，而不是改什么？

::: sol 第 4 题答案
该加的是授权与寿命层：为句柄记录创建时刻与最长持有时限，超时就走一次与 `release` 相同的取走所有者路径，让[@def-16.4.3]的线性化点保持唯一。不该改的是代号编码本身（那会动 ABI 面），也不该指望「位宽更大」顺带解决权限问题（16.4.8）。
:::

## 16.5 panic 防线、失败清理与真实双向测试 {#sec-cpp-rust.4.16.5}

本节回答一个问题：**一个不许把 unwind 交回 C 的入口，怎么把内部炸掉变成整数码，又怎么证明失败后的清理真的跑过？**16.4 处理句柄失效，这一节处理最后一种失败：代码自己 panic。防线能做的只是换一个出口，不能假装状态没有坏。

::: preview 先抓住一件事

**边界只承诺把展开换成 `EPANIC`，不承诺业务回滚。**判断一条失败路径是否被验证，看它有没有在真实 C 调用下跑过，并且检查过输出是否原样未动。只让 Rust 单测通过，证明不了 C 侧拿到的清理规则成立。

:::

### 16.5.1 普通错误不使用 panic 表达

坏版本、容量不足和旧句柄都属于普通错误。它们直接通过 `Result` 走到整数码（[@def-16.2.3]）。`catch_unwind` 不是正常分支选择器。只靠 panic 把每个越界都变成错误码，会把业务错误与程序缺陷混在一起。

边界只处理意外 unwind，也就是 panic 触发的栈展开。所有可能失败的 C 导出操作都在边界内部执行，测试专用入口也走同一条边界；不使用 `extern "C-unwind"` 让 Rust 展开穿过 C 栈。

```rust
fn boundary(f: impl FnOnce() -> Result<(), i32>) -> i32 {
    match catch_unwind(AssertUnwindSafe(f)) {
        Ok(Ok(())) => OK,
        Ok(Err(code)) => code,
        Err(payload) => {
            std::mem::forget(payload);
            EPANIC
        }
    }
}
```

::: def 定义 16.5.1 · panic 边界 panic boundary {#def-16.5.1}

**panic 边界**指每个 `extern "C"` 入口里那层 `catch_unwind` 包装。闭包正常完成给 `OK`，闭包返回 `Result` 的错误就给对应整数码，捕获到展开则遗忘载荷并给 `EPANIC`。三条出口里有两条是普通错误，它的职责只是不让任何展开越过 C 栈。

:::

按[@def-16.5.1]，`boundary` 的签名把「失败必须是整数码」写成了类型要求：入口作者不必记得在每个分支返回错误，闭包根本无法用其他方式失败。

### 16.5.2 为什么遗忘 panic payload

捕获结果里的 payload 可能具有会 panic 的析构器。若在外部入口返回之前直接 drop 它，可能再次触发展开。本项目因此选择在异常路径遗忘 payload。

::: def 定义 16.5.2 · 载荷遗忘 payload forget {#def-16.5.2}

**载荷遗忘**指捕获 panic 之后不析构载荷，直接放弃它（`std::mem::forget`）。换来的是确定性：异常路径上只剩「返回 `EPANIC`」这一件事，不会有第二次展开。代价是每次捕获都可能泄漏该载荷占用的资源，所以它不是「所有 panic 都能无限恢复」的实现。

:::

代价必须公开。如果持续出现 `EPANIC`，服务应告警、停止接收相关工作并安排进程恢复。不能把故障泄漏当成正常吞吐路径。

### 16.5.3 AssertUnwindSafe 不提供回滚

这个包装允许闭包通过 unwind 安全性边界，它不检查业务状态是否恢复。本项目用局部 RAII 管理尚未提交的数据，并对被毒化的锁采取拒绝策略——锁被毒化，指持锁线程 panic 之后留下的标记（16.5.4）。将来若加入多步可变状态，必须重新审查提交顺序。

分配失败也要分层。`try_reserve_exact` 能报告部分预留失败，但 `Arc::from` 等分配路径仍可能走不可恢复的分配错误处理；`catch_unwind` 不捕获 abort。本章因此不承诺内存耗尽时一定返回 `ERESOURCE`，那个码只覆盖可报告的预留失败（[@def-16.2.3]）。

### 16.5.4 poison 的处理不是强行解锁继续

如果持有注册表锁时 panic，锁可能被毒化。后续操作把锁错误映射成 `EPOISON`，不使用 `into_inner` 自动相信内部状态。这是保守停止，不是完整在线修复。

::: def 定义 16.5.3 · 毒化拒绝 poisoned refusal {#def-16.5.3}

**毒化拒绝**指锁一旦被毒化就不再提供正常服务，把后续调用统一变成 `EPOISON`，直到进程按运维流程重启。它与「解锁继续」的区别不在性能，而在是否承认内部状态可能只改了一半。

:::

测试只毒化局部 Mutex，避免污染所有测试共享的全局实例。随后检查 poison 状态和错误映射，它证明策略存在，不证明任意内部 panic 后都能继续服务。C 的故意 panic 入口在取得注册表锁之前触发，因此 C 测试后续调用正常；这件事不能被解释成全局 poison 已经恢复。

### 16.5.5 C 调用者的清理规则

CLI 创建成功后，不论查询成功与否，都调用 release。查询失败不消费句柄（[@ex-16.2.1]），释放则只在锁内取走所有者（[@def-16.4.3]），两条规则合起来使清理简单。释放结果也会检查，而不是被无条件忽略。只有创建成功后才拥有要释放的句柄。

实际 CLI 的关键顺序是：

```c
rb_handle handle = 0;
int32_t code = rb_generate(args[0], args[1], &handle);
if (code != RB_OK) {
    fprintf(stderr, "generate error=%" PRId32 "\n", code);
    return 1;
}
rb_info_v1 info = {0};
code = rb_info(handle, RB_ABI_VERSION, sizeof(info), &info);
int32_t release = rb_release(handle);
if (code != RB_OK || release != RB_OK) {
    fprintf(stderr, "info error=%" PRId32 " release=%" PRId32 "\n", code, release);
    return 1;
}
```

完整文件还检查十进制参数、负号、尾部字符和范围。不要只截取创建成功的 happy path 当作应用示例。异常资源寿命往往由失败分支决定。

### 16.5.6 安全失败回归：容量不足不写输出

Rust 与 C 都执行了这一回归。先创建一个长度大于输出容量的对象，把输出数组和 written 初始化为可识别哨兵，调用 rb_copy，检查 `ECAPACITY`，并确认两个输出都没变。最后释放原句柄。

这是项目内可运行的真实失败路径。测试防止以后有人把容量检查移到复制之后。没有越界访问参与测试，也不需要依赖「越界可能会崩溃」。

::: ex 例 16.5.1 · 一次 panic 与一次容量失败，分别被哪一层接住 {#ex-16.5.1}

两个都在项目内真实执行过的 C 侧序列。① 调用测试探针 `rb_test_panic()`，它在取得注册表锁之前故意 panic。② `c/tests.c` 里那组夹具：长度 4 的对象、只有 2 格的输出缓冲（预置 71/72）、`written` 预置 777，调用 `rb_copy`。给出返回码、输出是否被写、句柄是否被消费，以及「假如没有这道防线，C 侧会看到什么」。

::: sol 解答

① 展开发生在 `boundary` 的闭包里，`catch_unwind` 接住，载荷被遗忘，返回 `EPANIC`（5）。被破坏的是「内部缺陷不得越过 C 栈」，接住它的是[@def-16.5.1]那层包装。因为 panic 在取锁之前发生，注册表没有毒化，后续调用照常成功；这恰好说明「C 测试通过了」不能反推[@def-16.5.3]已被验证。若没有边界，Rust 展开进入 C 帧就是未定义行为。
② 返回 `ECAPACITY`（4）。两格输出与 777 都保持原值，句柄不被消费，随后 `rb_release` 返回 OK。被破坏的是「容量必须覆盖完整对象」，接住它的是 `rb_copy` 里 `capacity < data.len()` 那次判断，它排在复制和写 `written` 之前（[@ex-16.2.1] ③）。
两条的共同点：都能在没有未定义行为的前提下被测试，且失败分支的 release 也执行并检查了返回值。

:::

| Rust 导出契约6项 | 布局、核对照、容量/版本、空对象、释放争用、读者竞态 | 通过 |
| C11 契约可执行文件 | 独立参考核、布局断言、错误清理、pthread读取、panic探针 | 通过 |
| CTest CLI3项 | 正常调用、过大长度、非法数字 | 通过 |

CTest 总计4项，其中一项是完整 C11 契约程序。不能把 C 程序里的每条 assert 都称为一个独立测试进程。Rust 的12线程释放测试要求恰好一个 OK、11个 ESTALE，这检验当前实现的可观察竞争结果，不是所有线程交错的形式证明。

::: def 定义 16.5.4 · 双向契约测试 bidirectional contract test {#def-16.5.4}

**双向契约测试**指同一份契约由两侧各执行一次：Rust 侧证明内部不变量（代号退休、槽上限复用、快照存活、panic 及局部 poison），C11 侧证明跨语言可观察行为（布局、错误清理、pthread 读取、panic 探针）。任何一侧缺席，都只能说明「在我这边成立」。

:::

::: think 思考 · 直接用 drop 处理载荷不是更省 {#think-16.5.1}

有人提出：把 `Err(payload)` 分支改成 `drop(payload)`，泄漏就没有了。按本节，这个「改进」丢掉了哪一条保证？

::: sol 解答

丢掉的是「异常路径不会再抛第二次」。载荷的类型由 panic 发起方决定，它的析构器自己也可能 panic；第二次展开发生在已经展开的栈上时通常直接 abort，C 侧连 `EPANIC` 都拿不到。泄漏是写在文档里的代价（[@def-16.5.2]），double panic 则把「返回错误码」变成「进程消失」，两者不能互换。要少泄漏只能约束载荷类型或限制 panic 来源。

:::

:::

::: method 判定流程 · 拿到 EPANIC 或 EPOISON 之后先查什么

① **先看码**：`EPANIC` 是捕获到展开，`EPOISON` 是锁已毒化，两者的恢复动作不同（[@def-16.5.3]）。<br>
② **`EPANIC` 再分位置**：panic 发生在取锁之前，注册表仍可用；发生在持锁期间，才按毒化处理（[@ex-16.5.1]）。<br>
③ **查业务状态**：边界不提供回滚，已提交的部分要由调用者自己核对（16.5.3）。<br>
④ **`EPOISON` 不解锁继续**：不要 `into_inner`，按运维流程重启并保留现场。<br>
⑤ **计数与告警**：持续出现就停止接收相关工作，不能把泄漏当吞吐（[@def-16.5.2]）。

:::

### 16.5.8 小结与常见错误

**小结。**① 边界只换出口，三条出口里两条是普通错误（[@def-16.5.1]）；② 载荷有意遗忘，用可解释的泄漏换确定性（[@def-16.5.2]）；③ `AssertUnwindSafe` 是声明不是回滚，锁被毒化就拒绝服务（[@def-16.5.3]）；④ 清理规则由「失败不消费句柄」决定，release 也要检查结果；⑤ 契约要在 Rust 与真实 C 两侧各跑一次（[@def-16.5.4]），C 侧事后调用正常也不能反推 poison 已恢复。下一节 [16.6 原生构建](#sec-cpp-rust.4.16.6) 用构建与代码生成证明这层边界确实存在。

::: errata 常见错误清单（16.5 节）

E-a **把 panic 当成错误码生成器。**坏版本、容量不足本该走 `Result`，混进来会把业务错误和程序缺陷搅在一起。先查每个入口是不是先返回 `Result`（[@def-16.5.1]）。

E-b **捕获后立刻 drop 载荷。**析构器再 panic 就是第二次展开，通常直接 abort（见本节思考）。

E-c **把 `AssertUnwindSafe` 当事务回滚。**它只是调用方的声明，提交顺序仍要自己审查（16.5.3）。

E-d **毒化后 `into_inner` 解锁继续。**内部状态可能只改了一半；当前选择是统一 `EPOISON`（[@def-16.5.3]）。

E-e **用「C 测试后续调用正常」证明 poison 已恢复。**探针在取锁之前发作，两件事没有关系（[@ex-16.5.1]）。

E-f **只测 happy path 的释放。**失败分支才决定资源寿命；容量不足那条要检查输出哨兵未变、句柄仍可释放（16.5.6）。

## 16.6 原生构建与实际代码生成核验 {#sec-cpp-rust.4.16.6}

本节回答一个问题：**构建成功、测试通过之后，还要看到什么，才敢说这层 C 边界真的存在？**16.5 证明了失败路径被接住，这一节证明它没有被构建系统、优化器或断言开关悄悄改掉。

::: preview 先抓住一件事

**编译通过只证明两边能链接，不证明守卫还在。**要支持「边界存在」这句话，得在保存下来的代码生成里定位到具体入口，并说清每份证据只能支持哪一层。把标签名当成结论——比如看见 `vector.body` 就宣布 SIMD——是这一节最容易犯的错。

:::

### 16.6.1 Cargo 与 CMake 各自管理清楚的部分

Cargo 构建 Rust 库。CMake 构建 C11 外部调用者，并把 Rust 静态库作为真实链接输入。这里没有用 CMake 重新列举 Rust 模块，也没有用一个空命令假装集成成功。`add_custom_command` 实际执行 offline、locked、release Cargo 构建。

项目输出 rlib、staticlib 和 cdylib。本轮 CMake 只验证静态库集成。生成 cdylib 不等于完成动态库的装载路径、安装和卸载测试。本章不把未执行的部署方式写成通过。

::: def 定义 16.6.1 · 原生构建 native build {#def-16.6.1}

**原生构建**指两侧各用原生的构建系统：Cargo 编 Rust，CMake 编 C，并由 CMake 把 Rust 静态库当作真实链接输入。判据只有一条——把 Rust 目标从这个构建里拿掉，C 的可执行文件应当链接失败。做不到这一点的「集成」，只是把两份构建并排跑了一遍。

:::

按[@def-16.6.1]，CMake 里那条 `add_custom_command` 属于构建事实，不是说明文字。它一旦被换成 `echo`，C 侧测试测的就不再是被测库。

### 16.6.2 可直接执行的命令

在仓库的 `cpp-rust/projects/ffi-bridge/` 中运行：

```bash
cargo fmt --check
cargo clippy --offline --locked --all-targets --features test-hooks -- -D warnings
cargo test --offline --locked --features test-hooks
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DRB_TEST_HOOKS=ON
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
./build/bridge_demo 42 8192
```

测试专用 feature 导出 `rb_test_panic`。发布构建应使用另一个新目录并设置 `RB_TEST_HOOKS=OFF`。Rust 单独构建时不启用该 feature 即不导出探针。不要把故意触发 panic 的接口当成正式业务能力。

CMake 给三个 C 可执行文件都加 `-UNDEBUG`。这是为了让 Release 模式里的校验 assert 真正执行。如果 `-DNDEBUG` 把 checksum 相等断言删除，就失去了部分夹具验证。Rust API 返回码检查在 benchmark 中也用显式分支保留。

### 16.6.3 编译条件保存到证据中

本轮 Rust 是1.99.0，LLVM 是23.1.1。目标为 `aarch64-apple-darwin`。C 编译器是 Apple clang21.0.0。CMake 是4.4.4。Rust release 使用 opt-level3、单 codegen unit、关闭 LTO、panic unwind。没有跨语言 LTO，也没有手工指定 target-cpu=native。

宿主型号查询为 Mac17,9，实验机为 Apple M5 Pro。系统报告18个逻辑 CPU，缓存行（cacheline，CPU 和内存之间整块搬运数据的单位）查询为128字节。这些数值只描述当前宿主。本项目没有靠写死64字节对齐来声称消除了伪共享（不同核的数据挤在同一段缓存里，被彼此的写入拖慢），更没有测出缓存未命中率或内存带宽上限。

### 16.6.4 保存的代码生成层次

脚本另行执行 `cargo rustc`，保存 MIR、LLVM IR 与本机汇编。还用 clang 保存 C benchmark 的汇编。这些产物来自与正式构建相同的优化配置和 feature，不是目标机外的交叉生成结果。

| 边界 | 实际证据 | 可支持的结论 |
|:--|:--|:--|
| C 到 rb_mix | c-benchmark.s 中存在对 `_rb_mix` 的调用 | 逐元素跨边界没有整体消失 |
| C 到 rb_transform | 同文件中存在独立批量调用 | 批量路径真正进入 Rust |
| rb_mix | ffi_bridge.s 中含检查、madd、存储和返回 | 安全守卫与计算均保留 |
| rb_transform | 长度/重叠守卫后四元素展开 | 批量能摊薄守卫与调用 |
| Rust 切片核 | LLVM IR 的别名 scope 与 noalias 信息 | 引用契约参与优化 |
| rb_copy | memcpy 路径与独立 sample 的 memmove 栈 | 完整导出实际复制了数据 |
| rb_generate | 分配及 Vec 到 Arc 的复制路径 | 拥有句柄不等于全流程零拷贝 |
| 注册表同步 | 汇编含 mutex 调用与 ldapr | 同步未被当成普通无锁读删掉 |

::: def 定义 16.6.2 · 代码生成层次 codegen layers {#def-16.6.2}

**代码生成层次**指 MIR、LLVM IR、本机汇编这三份可保存的中间产物，加上运行时的采样栈。每一层只回答它自己那一类问题：MIR 说明前端保存了什么语义，LLVM IR 说明优化后还剩什么结构，汇编说明本机最终发出哪些指令，采样说明运行时确实走到哪个函数。跨层推断——用 IR 的块名证明汇编里有向量指令——不算证据。

:::

按[@def-16.6.2]，上面那张表每一行都写成「实际证据 + 可支持的结论」两列，而不是一句「已核实」。

### 16.6.5 小函数的边界防线未必留下异常表

`rb_mix` 的源码也经过 boundary。本轮优化器能证明其正常路径没有需要 unwind 的操作，因此实际小函数很紧凑。不能按源码中 `catch_unwind` 的次数直接推算异常运行时成本。

它对输出指针做的检查属于[@def-16.3.1]的数值守卫；守卫、madd、存储和返回一起出现在 `ffi_bridge.s` 里，说明这一版没有把检查删掉。

::: def 定义 16.6.3 · 异常表 unwind table {#def-16.6.3}

**异常表**指编译器为可能发生展开的调用点生成的元数据，展开器靠它找到每一帧的清理代码。一个函数如果在正常路径上既没有可失败的调用、也没有需要析构的局部值，就可能不生成表项。因此「这个函数没有异常表」只说明它自己不会展开，不说明整个库没有 panic 防线。

:::

另一方面，存在分配和锁的入口保留了相应失败与清理路径。测试探针确实触发 unwind 并回到 C 错误码。「某个叶函数没有异常表」和「整个库没有 panic 防线」不是一回事，代码生成检查必须定位到具体入口（[@def-16.6.2]）。

### 16.6.6 看见 vector.body 不能立即宣布 SIMD

LLVM IR 的批量循环块叫 `vector.body`。但这一版块内主要是展开后的标量 i64 运算，最终本机汇编也呈现多个标量 madd。因此本章称它为四元素展开，不把标签名称当成 SIMD 证据。

实际循环中的一段如下：

```asm
ldp x14, x15, [x11, #-16]
ldp x16, x17, [x11], #32
eor x14, x14, x14, lsr #29
eor x15, x15, x15, lsr #29
eor x16, x16, x16, lsr #29
eor x17, x17, x17, lsr #29
madd x14, x14, x8, x9
madd x15, x15, x8, x9
madd x16, x16, x8, x9
stp x14, x15, [x12, #-16]
madd x14, x17, x8, x9
stp x16, x14, [x12], #32
```

这段只说明固定版本的核心循环形态。它不是汇编或调用约定入门，也不从指令条数直接换算 CPU 周期。完整产物还包含前置检查、尾部循环和错误返回。

::: ex 例 16.6.1 · 三条结论，各需要哪一份证据 {#ex-16.6.1}

有人从这轮产物里提出三条结论：① C 对 `rb_mix` 的逐元素调用被整体消除了；② `rb_mix` 的守卫被优化掉了，只剩计算；③ 批量核已经是 SIMD。按[@def-16.6.2]，逐条给出反证或限定。

::: sol 解答

① 反证在 `c-benchmark.s`：其中存在对 `_rb_mix` 的调用，说明逐元素跨边界没有整体消失。用到的证据是 C 侧汇编，不是 Rust 侧。
② 反证在 `ffi_bridge.s`：`rb_mix` 里含检查、madd、存储和返回，说明安全守卫与计算都保留。它只说明这个入口的汇编形态，不说明每个入口都如此。
③ 只能限定。`vector.body` 是 IR 的块名，块内是展开后的标量 i64 运算，最终汇编也是多个标量 madd；结论应写成「四元素展开」。要主张 SIMD，还得在汇编里看到对应的向量指令。
三句话的共同错误，是把上一层的信息搬到下一层当结论。[@def-16.6.2]要求分层核对，挡的就是这一步。

:::

:::

::: think 思考 · 源码里每个入口都有 catch_unwind，异常表一定在 {#think-16.6.1}

有人据此推算：库里有 N 个入口，异常表就该有 N 份，异常运行时成本也按 N 份算。这个推算漏了哪一步？

::: sol 解答

漏了「优化器可以证明这个入口的正常路径根本不会展开」这一步。`rb_mix` 的源码同样经过 boundary，但本轮产物里它很紧凑，没有留下需要展开的表项（[@def-16.6.3]）。反过来也不能推广成「所有入口都没有异常表」：带分配和锁的入口保留了失败与清理路径，测试探针也确实展开并回到 `EPANIC`。成本要按入口逐个看代码生成，不能按源码里的包装次数乘出来。

:::

::: method 判定流程 · 发布前 FFI 交付检查

① **干净目录复现**：`cargo fmt --check`、clippy（`-D warnings`）、`cargo test`、CMake 配置与构建、`ctest` 全部从空目录跑一遍，离线且 `--locked`。<br>
② **链接是真的**：C 可执行文件确实链接 Rust 静态库；删掉 Rust 目标应当链接失败（[@def-16.6.1]）。<br>
③ **两侧布局都编译过**：Rust 断言与头文件 `_Static_assert` 同时存在（[@def-16.2.1]）。<br>
④ **断言没被 Release 删掉**：三个 C 目标带 `-UNDEBUG`，benchmark 用显式分支校验返回码与 checksum。<br>
⑤ **探针不进发布物**：换新构建目录并设 `RB_TEST_HOOKS=OFF`，确认 `rb_test_panic` 不导出。<br>
⑥ **代码生成对得上入口**：保存 MIR / LLVM IR / 汇编，按[@def-16.6.2]逐层核对守卫、调用与同步路径。<br>
⑦ **条件写进证据**：工具链、目标三元组、优化配置、宿主与 cacheline 都归档，否则数字无法被复核。

:::

### 16.6.7 小结与常见错误

**小结。**① 原生构建的判据是「删掉 Rust 目标，C 就链接失败」（[@def-16.6.1]）；② Release 下的断言要靠 `-UNDEBUG` 保住，否则校验静默消失；③ 编译条件与宿主一起归档，数字才有边界；④ 代码生成必须分层核对，每层只说一层的话（[@def-16.6.2]）；⑤ 叶函数没有异常表不等于库没有防线（[@def-16.6.3]）；⑥ `vector.body` 不是 SIMD 证据。下一节 [16.7 逐元素调用与批量 FFI](#sec-cpp-rust.4.16.7) 开始用这套构建测第一组数字。

::: errata 常见错误清单（16.6 节）

E-a **用空命令假装 CMake 集成。**C 侧测试于是没测到 Rust 库。先查 Rust 目标是否真是链接输入（[@def-16.6.1]）。

E-b **Release 下断言被 `-DNDEBUG` 删掉，还称验证通过。**三个 C 目标都要 `-UNDEBUG`。

E-c **把 cdylib 产物当成动态装载已验证。**装载、安装、卸载都没跑过，本章只验证静态库。

E-d **按 `catch_unwind` 出现次数估算异常成本。**优化器可能不给叶函数留表项（[@def-16.6.3]）。

E-e **看见 `vector.body` 就写 SIMD。**块里是标量 i64 运算，汇编也是标量 madd（[@ex-16.6.1]）。

E-f **不记录工具链与优化配置。**换一次 rustc 或 codegen unit，汇编和数字都可能变，结论无法复核。

:::

## 16.7 benchmark 一：逐元素调用与批量 FFI {#sec-cpp-rust.4.16.7}

本节回答一个问题：**同一份映射，逐元素跨边界和整批跨边界，差别来自哪里，这份夹具又能回答到哪一步？**16.6 给了可复核的构建，这一节开始用它测第一组数字；要回答的只有「调用粒度」一件事。

::: preview 先抓住一件事

**这组实验只变一个量：每批进几次边界。**两条路径共用同一个 Rust 映射和同一份 C 侧 checksum 循环，也都不创建句柄。两个均值之差是聚合成本差，不能命名为「一次 C ABI 调用成本」。

:::

### 16.7.1 要回答的有限问题

对同一批8192个输入，逐元素进入 Rust 与一次批量进入 Rust，有什么差别？每批重复64轮，总计524288个词。两条路径使用相同 Rust 映射和相同 C 输出 checksum 循环，它们不创建注册表句柄，也不分配拥有对象。因此第一组主要观察边界粒度及批量优化机会，走的是[@def-16.1.2]里的同步借入路径。

逐元素分支每个词调用一次 rb_mix。批量分支每轮调用一次 rb_transform。后者仍然检查参数、长度、对齐和重叠（[@def-16.3.1]），它不是为了跑分快速跳过安全守卫的秘密入口。

### 16.7.2 完整可执行源与核心分支

完整 benchmark 在 `c/benchmark.c`。没有依赖未给出的随机数生成器或测量库。统计脚本在 `tools/summarize.py`。以下摘录来自计时函数中的分支：

```c
if (which == 0) {
    for (unsigned i = 0; i != WORDS; ++i)
        check(rb_mix(input[i], &output[i]));
} else if (which == 1) {
    check(rb_transform(input, output, WORDS));
}
```

两者随后都在 C 中遍历完整 output，这个 checksum 工作进入计时。计时结束后，结果与独立 C 参考计算比较。因此「相同数学结果」的检查不依赖刚才那个 Rust 输出自己证明自己。

参考输入是确定的整数序列。测试还比较零、最大 u64 等边界值。这不是面对随机业务数据的统计抽样。输入可预测有利于复现，却限制了向复杂真实负载外推。

### 16.7.3 计时边界

| 阶段 | 是否计入每个正式批次 | 原因 |
|:--|:--|:--|
| 初始化输入 | 否 | 不重复制造固定数据 |
| 独立参考 checksum | 否 | 不把参考核重复计算计入被测耗时 |
| 每轮 FFI 调用 | 是 | 被比较的核心边界 |
| 输入读取和输出写入 | 是 | 算法真实工作 |
| C checksum 遍历 | 是 | 两路径共同消费完整输出 |
| 校验 expected | 否 | 时间戳后检查 |
| CSV 格式化与打印 | 否 | 不把终端输出当算法成本 |
| 程序启动与退出 | 否 | 不测冷启动 |

每个 case 独立预热至少500ms，不是四个 case 共享一次500ms后就各自算预热充分。正式采样每case21批。每轮轮转起始case，避免固定顺序与时间漂移完全重合。预热循环也检查结果，不会把错误计算当成预热。

::: def 定义 16.7.1 · 计时边界 timing boundary {#def-16.7.1}

**计时边界**是一份事先写下的清单：哪些阶段进入被测区间、哪些留在外面，以及为什么。它决定了两个数字能不能相减——边界不同的两张表，差值没有含义。本节那张表就是这份协议：C 侧 checksum 遍历在界内，独立参考计算与打印在界外。

:::

::: def 定义 16.7.2 · 每词成本 cost per word {#def-16.7.2}

**每词成本**是一批的墙钟时间除以该批词数（这里固定 524288），单位 ns/word。它是聚合量，包含循环、守卫、边界调用摊销和 C 侧遍历。它不是单次 `rb_mix` 的延迟，数值小于 1 也不代表时钟能测到亚纳秒。

:::

### 16.7.4 原始观察与统计定义

CSV 保存 case、观察号、批耗时、词数与 checksum。统计先把批耗时除以524288，得到 ns/word。平均值与 N-1 样本标准差都基于21个批均值。分位数使用 nearest-rank，21个值的 p99 在这里就是最大批均值。

这不是21个请求的端到端延迟，也不是每次 rb_mix 的独立计时。批量值小于1ns/word，不意味着系统时钟能以亚纳秒分辨率测量一次调用。本轮原始 elapsed_ns 还呈现1000ns步长的量化现象，单位是纳秒，不等于实际时钟分辨率就是1ns。

### 16.7.5 本轮实测

来源为归档的 `raw.csv` 和 `summary.json`。以下数值保留六位小数，完整精度在 JSON 中。

| case | n | mean ns/word | N-1 sd | 批p50 | 批p99 |
|:--|--:|--:|--:|--:|--:|
| per_element | 21 | 0.978652 | 0.021629 | 0.986099 | 1.005173 |
| batch | 21 | 0.211897 | 0.004042 | 0.211716 | 0.217438 |

两者 checksum 都是 `999f7c01d1040000`。样本方差分别约为0.000467809与0.000016336，单位是 `(ns/word)^2`。没有报告未做的显著性检验或 p-value。这些桌面批次不能直接转成线上回归门限。

### 16.7.6 能支持什么解释

固定工作量下，批量路径的聚合成本更低。它减少了外部调用次数，且把检查摊到更多元素上。代码生成还显示展开的循环和一次准备的常量。这些机制共同解释观察方向。

不能把两个平均值之差简单命名为「一次 C ABI 调用成本」。两条路径的优化范围也不同：逐元素要反复返回错误码，批量可以在一个循环里调度多个独立运算。如果启用跨语言 LTO，差异可能再次变化，本轮没有执行那组配置。

::: ex 例 16.7.1 · 这张表能支持哪三句话 {#ex-16.7.1}

按[@def-16.7.2]读本节两行：per_element 均值 0.978652、N-1 sd 0.021629；batch 均值 0.211897、sd 0.004042；两者 n 都是 21，批 p99 分别为 1.005173 与 0.217438。判断三句话：①「一次跨边界调用成本 0.766755 ns」；②「批量比逐元素快约 4.6 倍」；③「batch 的 p99 是 0.217438 ns，所以线上尾延迟很低」。

::: sol 解答

① 不成立。0.978652 − 0.211897 = 0.766755，这是每词聚合成本之差，不是单次调用成本。差值里同时含调用次数、每词错误码分支和守卫摊销的变化，两条路径的优化范围也不同。
② 在固定工作量、固定构建下成立，但要写成「本夹具的聚合成本约为逐元素的 1/4.6」；它不能推广成对任何调用者的加速比，因为逐元素调用者往往攒不出批。
③ 不成立。p99 用 nearest-rank，21 个值取第 ceil(21 × 0.99) = 21 个，就是最大批均值；它是 524288 个词一次批量的成本，不是请求级尾延迟。原始 elapsed_ns 还有 1000ns 步长，1ns 级的差别不可分辨。

:::

:::

::: think 思考 · 批量路径更快，是因为它跳过了守卫 {#think-16.7.1}

有人这样解释这组结果：`rb_transform` 一次处理 8192 个元素，肯定没做逐元素那些检查。按本节，这个解释错在哪，正确的机制是什么？

::: sol 解答

错在事实层面：批量入口仍然检查参数、长度、对齐和重叠（[@def-16.3.1]），守卫一个都没少。正确的机制是摊销——同一次检查覆盖 8192 个词，而逐元素路径每词都要过一遍入口并返回错误码；批量循环还能让编译器展开并调度多个独立运算。收益来自「每词分摊的守卫与调用次数」，不是「守卫被取消」。

:::

:::

### 16.7.7 性能回退也是安全问题之外的真实故障

若客户端把批处理接口改回每元素调用，所有内存访问仍可合法。但这份夹具会显示明显的吞吐回退。因此它是安全 Rust 与合法 C 都可能引入的性能回归。本章没有通过执行 UB 制造一个「错误版本更快」的故事。

::: method 判定流程 · 什么时候把逐元素调用改成批量

① **调用者能否攒批**：手上有多个值再调用；每次只算得出一个值，批量路径就用不上。<br>
② **数据是否已在 C 侧且本次用完即弃**：是，走同步借入，不建句柄（[@def-16.1.2]）。<br>
③ **失败语义能否整批承担**：`rb_transform` 一次失败即整批无结果，逐元素则可能部分成功。<br>
④ **容量与重叠能否一次声明**：输出缓冲要一次给足，输入输出不能相交（[@ex-16.3.1]）。<br>
⑤ **改完用同一份 checksum 复核**：先与独立 C 参考比较，再重跑本夹具看方向。

:::

### 16.7.8 小结与常见错误

**小结。**① 这组只变调用粒度，8192 词 × 64 轮 = 524288 词；② 计时边界先写清，checksum 在界内、参考计算在界外（[@def-16.7.1]）；③ ns/word 是聚合量，21 个值的 p99 就是最大值（[@def-16.7.2]）；④ 批量更快来自单次检查摊到更多元素与更少的返回码分支；⑤ 差值不能命名成单次调用成本，也不能跨配置外推。下一节 [16.8 复制导出与拥有句柄内归约](#sec-cpp-rust.4.16.8) 换一个问题：结果由谁消费。

::: errata 常见错误清单（16.7 节）

E-a **把 ns/word 当单次 rb_mix 延迟。**它包含循环、守卫与 C 侧遍历（[@def-16.7.2]）。

E-b **把两个均值之差叫一次 C ABI 调用成本。**两条路径的优化范围不同（[@ex-16.7.1]）。

E-c **把批 p99 当线上尾延迟。**21 个值的 p99 是最大值，单位还是 524288 词一批。

E-d **用亚纳秒分辨率解释差值。**原始 elapsed_ns 有 1000ns 步长，1ns 以下的差别读不出来。

E-e **以为批量入口跳过了守卫。**长度、对齐、重叠照查（见本节思考）。

E-f **拿未执行的跨语言 LTO 配置推断差异方向。**本轮没有跑那组配置。

## 16.8 benchmark 二：复制导出与拥有句柄内归约 {#sec-cpp-rust.4.16.8}

本节回答一个问题：**结果由 Rust 生产、C 只要一个摘要时，把数组导出和在组件内归约，差的是什么，又共同付了什么？**16.7 比较调用粒度，这一节比较结果的消费位置；两条路径都经过句柄，所以差别不在「有没有所有权」。

::: preview 先抓住一件事

**这组比的是结果在哪里被消费，不是句柄比裸指针快。**两条路径每轮都创建并释放一个句柄，也都在 `Arc::from(Vec)` 里复制一次；owned_handle 省掉的只是「完整数组复制回 C 再遍历求和」。

:::

### 16.8.1 不同问题，不能沿用第一组归因

第二组比较结果消费位置。两条路径都让 Rust 生成同样的8192词对象。每批仍重复64轮，每轮都创建并释放一个句柄。区别是把完整结果复制回 C 后求和，还是在 Rust 内部归约后只返回元数据。

copy_out 执行 generate、copy、release，然后在 C 中求和。owned_handle 执行 generate、info、release，在 info 内完成同一模加归约。两者的最终 checksum 一致，但后者没有把完整数组交给 C 任意后续使用。如果业务确实需要每个词，就不能拿归约结果替代数组而声称等价。

::: def 定义 16.8.1 · 复制导出 copy-out {#def-16.8.1}

**复制导出**指 `rb_copy` 把 Rust 存储里的完整数组复制进 C 提供的缓冲，再由 C 自己消费。复制之后两份分配互相独立：C 可以对数组做任意后续处理，也要自己管好那块缓冲。

:::

::: def 定义 16.8.2 · 拥有句柄内归约 owned-handle reduction {#def-16.8.2}

**拥有句柄内归约**指 C 只拿到句柄和元数据，归约（本例为模加 checksum）在 `rb_info` 内部完成，完整数组从未离开组件。它交付摘要，不交付数据；一旦业务要逐元素读取，这个接口就不够用。

:::

### 16.8.2 真实拥有路径

完整实现中的拥有分支为：

```c
rb_handle handle = 0;
check(rb_generate(UINT64_C(97) + rep, WORDS, &handle));
if (which == 2) {
    uint64_t written = 0;
    check(rb_copy(handle, output, WORDS, &written));
    if (written != WORDS) abort();
} else {
    rb_info_v1 info;
    check(rb_info(handle, RB_ABI_VERSION, sizeof(info), &info));
    if (info.len != WORDS) abort();
    sum += info.checksum;
}
check(rb_release(handle));
```

copy_out 分支随后执行公共 C 求和循环。owned_handle 不重复遍历 C output，这一点由 `which != 3` 条件明确区分。没有忘记观察拥有路径的结果，也没有漏掉 release。

### 16.8.3 所有权转移到底省了什么

C 接收的是负责消费和释放的句柄，Rust 数据始终由 Rust 分配器管理。owned_handle 省掉的是一次完整 Rust 到 C 输出复制，以及随后那次 C 侧遍历。它没有接管 C 分配，也没有从 C 借出一个长期裸数据视图。

这可以称为「结果留在组件内」的接口优化，不宜笼统称为「零拷贝」（意思是一次数据复制都不发生）。本轮 `Arc::from(Vec)` 在内部构造中实际发生复制，两条路径都承担这个共同成本。将来若要进一步优化，应先测量直接构造引用计数存储的收益和初始化证明。按[@def-16.1.2]的三个问句，这两条路径的答案完全相同，差别只在结果交给谁消费。

### 16.8.4 本轮实测

| case | n | mean ns/word | N-1 sd | 批p50 | 批p99 |
|:--|--:|--:|--:|--:|--:|
| copy_out | 21 | 0.641505 | 0.028644 | 0.642776 | 0.684738 |
| owned_handle | 21 | 0.358854 | 0.013968 | 0.356674 | 0.400543 |

两者 checksum 都是 `f9e695131a980000`。样本方差分别约为0.000820485与0.000195100，单位仍是 `(ns/word)^2`。这组时间包括分配、生成、注册表、读取或复制、释放和求和。不是单独 memcpy 的吞吐，也不是单独 Arc 原子引用计数成本。

### 16.8.5 与第一组不能直接排名算法优劣

第一组复用外部分配的输入输出，第二组每轮都创建 Rust 拥有对象。它们有不同的资源生命期和被计入工作。不能因为 batch 数值最低，就宣布「句柄接口设计失败」，它们服务不同调用需求。

如果数据已经在 C 内，批量借入很合适。如果数据由 Rust 生产且只需要摘要，留在 Rust 内归约更自然。若 C 必须长期读取每个元素，则需要复制或另一个经过严格寿命设计的视图接口。

::: ex 例 16.8.1 · 0.282651 这个差该怎么说 {#ex-16.8.1}

copy_out 均值 0.641505、owned_handle 均值 0.358854，两者 n 都是 21，checksum 都是 `f9e695131a980000`。有人据此写：「省下的 0.282651 ns/word 就是一次 memcpy 的成本。」按本节，这句话哪几处要改？

::: sol 解答

三处。第一，差值里不止复制：copy_out 还要在 C 侧遍历完整 output 求和，owned_handle 在 `rb_info` 内完成同一归约，两条路径的消费位置整个不同（[@def-16.8.1]、[@def-16.8.2]）。
第二，0.282651 是每词聚合差，不是一次 memcpy 的耗时；本轮没有单独测 memcpy 吞吐，也没有单独测 Arc 原子引用计数成本。
第三，两条路径都付了生成、分配、注册表、`Arc::from(Vec)` 内部复制与释放，这些共同成本同时计在两边；差值只能说明「导出并遍历」这一段的量级。

:::

:::

::: think 思考 · checksum 相同，所以两条路径可以互换 {#think-16.8.1}

两条路径最终 checksum 都是 `f9e695131a980000`。有人据此说：那就用 owned_handle 替代 copy_out，反正结果一样。这个推理的隐含前提是什么？

::: sol 解答

隐含前提是「调用者只需要摘要」。checksum 是模 2^64 加法归约，不同的数组完全可能得到同一个值，它不证明数据相等；更需要问的是调用者拿结果做什么。若业务要逐元素读取，owned_handle 从未交付数组（[@def-16.8.2]），替换就是能力缺失而不是优化。checksum 相等在这组夹具里只用于确认两条路径算的是同一份映射。

:::

:::

::: method 判定流程 · 结果导出还是留在组件内

① **C 要逐元素读吗**：要，走 `rb_copy` 导出到 C 自己的缓冲（[@def-16.8.1]）。<br>
② **只要摘要吗**：只要 checksum 之类，走 `rb_info`，让归约留在组件内（[@def-16.8.2]）。<br>
③ **需要长期读又不想复制**：当前版本没有可变视图，也不要临场发明；先复制，另立设计（[@def-16.1.2]）。<br>
④ **能否接受每轮一个句柄**：拥有路径每轮创建并释放，调用者必须恰好 `rb_release` 一次（[@def-16.4.3]）。<br>
⑤ **报告时写清消费位置**：加速比对应的是「少导出一次」，不是「没有复制」。

:::

### 16.8.6 另一次执行采样，不污染正式计时

脚本在84条正式观察之后另起一个进程。该进程预热后轮转执行四个case。macOS sample 以1ms间隔请求采样2秒。完整报告保存在 `macos-sample.txt`，不并入 raw.csv。

报告能看到 rb_mix、rb_transform、rb_generate、rb_copy 和 rb_info。还可看到 rb_copy 下的 `_platform_memmove`，这与完整导出发生内存复制一致。rb_generate 下也出现内存复制和分配器路径。它提醒我们不要把「没有复制回 C」写成「没有任何复制」。

采样轮转的四个case不是等墙钟占比的生产负载。因此不把栈样本数换成每种 API 的稳定 CPU 占比。也不报告 sample 没采集的 IPC、cache miss、频率或能耗。macOS 栈采样不能冒充 Linux perf 的硬件计数器实验。

### 16.8.7 计时互斥与干扰记录

正式测量前，脚本通过 mkdir 获取章节间共享目录锁，退出时用 trap 删除锁目录。它不与另一个遵守协议的 benchmark 并行计时。构建和测试在锁外执行，以免长期占着测量窗口。

进程快照保存在 interference.txt。其中可见其他代理包含 Cargo 或 clang 的脚本命令痕迹。快照没有显示正在执行的 rustc 子进程，但一次快照不能排除随后发生的活动。本章据此明确保留干扰限制，不声称机器完全空闲。

没有固定核心、固定频率或控制桌面后台任务，也没有把低标准差当成「已隔离环境」的证明。正式值只在当前机器、当前源码和当前构建条件下成立。归档目录名是运行标识；宿主采集时钟写在 environment.txt，不从目录名推断日期。

### 16.8.8 小结与常见错误

**小结。**① 这组比的是结果消费位置，两条路径都经过句柄；② 复制导出交付数组，拥有句柄内归约只交付摘要（[@def-16.8.1]、[@def-16.8.2]）；③ 差值 0.282651 ns/word 是聚合差，不能叫 memcpy 吞吐（[@ex-16.8.1]）；④ 两条路径共同承担 `Arc::from(Vec)` 的内部复制，所以不是零拷贝；⑤ 与第一组不能直接排名，资源寿命与被计入工作不同。下一节 [16.9 母本对应与来源核读](#sec-cpp-rust.4.16.9) 交代这些结论的来源与边界。

::: errata 常见错误清单（16.8 节）

E-a **把 owned_handle 称为全链路零拷贝。**`Arc::from(Vec)` 仍复制，采样里也能看到 `_platform_memmove`（16.8.6）。

E-b **把 0.282651 差值叫 memcpy 吞吐。**差值还含 C 侧遍历与归约位置的变化，本轮没有单独测 memcpy（[@ex-16.8.1]）。

E-c **拿本组与第一组直接排名。**资源寿命与被计入工作不同，batch 数值最低不代表句柄设计失败（16.8.5）。

E-d **用 checksum 相等证明数组相等。**模加会碰撞，它只确认两条路径算的是同一份映射（见本节思考）。

E-e **忘记 release，或把它放在失败分支之外。**拥有路径每轮都创建句柄，泄漏会累积（[@def-16.4.3]）。

E-f **把 macOS 采样栈的样本数换成 CPU 占比或 IPC。**这些量本轮没有采集。

::: method 即时自测 · 16.8

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　copy_out 与 owned_handle 各自的调用序列是什么？两者 checksum 是否相同？

::: sol 第 1 题答案
copy_out 是 generate → copy → release，再在 C 中求和；owned_handle 是 generate → info → release，归约在 info 内完成。两者 checksum 都是 `f9e695131a980000`（[@def-16.8.1]、[@def-16.8.2]）。
:::

**第 2 题 · 辨析**　「owned_handle 均值 0.358854，比 copy_out 的 0.641505 少 44%，所以句柄接口总是更好。」对在哪、错在哪？

::: sol 第 2 题答案
只在这个夹具、这个「只要摘要」的需求下成立。它没有交付数组，业务要逐元素读时不能用；两条路径也承担共同的分配与 `Arc::from(Vec)` 复制。约 1/1.79 是聚合差，不是通用加速比（[@ex-16.8.1]）。
:::

**第 3 题 · 应用**　调用者先 `rb_generate`，再 `rb_copy` 到自己的 8192 格缓冲，然后要读这 8192 个值。句柄什么时候释放？

::: sol 第 3 题答案
复制成功之后就可以释放；C 缓冲是独立分配，`rb_release` 只消费句柄（[@def-16.4.3]）。若要顺带查 checksum，应在释放前调用 `rb_info`，因为释放之后再查只能得到 `ESTALE`（[@def-16.4.1]）。
:::

**第 4 题 · 迁移**　把归约从模加 checksum 换成「取最大值」，owned_handle 的结论还成立吗？

::: sol 第 4 题答案
结构上成立：归约仍在组件内完成、只交摘要。但本节没有采集最大值归约的数据，0.358854 不能沿用；`rb_info` 的 v1 布局也只有 checksum 字段（[@def-16.2.1]），要换归约就得升版本或新增入口。
:::

## 16.10 常见错误索引 {#sec-cpp-rust.4.16.10}

这是本章的跨节错误索引：每一节末尾都有自己的「::: errata 常见错误清单（16.M 节）」，按你阅读的顺序给出局部清单。下面这一份只收那些要读完整个章才浮出来的错误，它们在单节内部看不出问题，放进「导出、调用、释放」的整条链才露馅。

**把非空检查当成指针有效性证明。** 对齐且非空的地址仍可能悬垂、只读或越出分配。有效分配与完整调用寿命必须由调用者保证（[@def-16.3.2]）。

**先构造切片，后检查长度或重叠。** 非法引用一旦形成就已经违约，后面的检查救不回来。本项目在所有数值守卫之后才进入 unsafe 转换（[@def-16.3.1]）。

**把两个地址连续的分配拼成一个切片。** 单分配约束不由地址连续性推出，range 的加法检查也没有证明分配来源（[@ex-16.3.1]）。

**把长度单位混成字节。** 数据参数计的是 u64 元素，元数据 bytes 才是字节。测试与头文件必须沿用同一单位（[@def-16.2.2]）。

**给外层结构加 repr(C)，就传出 Vec。** 表示标记不会把内部 Rust 容器变成稳定的 C 对象；本项目只传固定宽度元数据与不透明整数身份（[@def-16.2.1]）。

**用 C 的 free 释放 Rust 结果。** 本项目根本不导出可释放的数据地址，句柄只能由 `rb_release` 消费，不能转成分配指针（[@def-16.1.2]）。

**复制句柄数值后释放两次。** 数值副本不是第二个所有者，第二次释放应返回 ESTALE，调用者也不应据此继续读旧对象（[@ex-16.4.1]）。

**代号达到最大值后回到 1。** 这会在极端寿命下重新生成旧身份，当前实现退休该槽，测试覆盖了这一分支（[@def-16.4.1]）。

**以为 release 返回说明所有读取结束。** 先拿到 Arc 快照的读取仍可完成；卸载库与回收外部执行环境需要更高层的在途调用协调（[@def-16.4.2]）。

**以为 Mutex 保护了所有 C 输出。** 它只保护注册表的身份映射，外部共享输出上的并发读写仍是调用者的数据竞争责任。

**认为 catch_unwind 能捕获 UB、abort 和外部异常。** 它只负责受支持的 Rust unwind，内存耗尽与进程信号也不会因此获得错误码恢复语义（[@def-16.5.1]）。

**捕获 payload 后无条件析构它。** payload 的析构可能再次 panic；本项目在异常路径有意遗忘它，并公开可能泄漏的限制（[@def-16.5.2]）。

**把 AssertUnwindSafe 当成事务回滚。** 它是调用方对 unwind 安全性的声明，不是修复器；注册表被 poison 后仍会拒绝服务，而不是强行恢复（[@def-16.5.3]）。

**Release 模式让 assert 消失却继续称校验通过。** 本项目的 C 构建显式使用 `-UNDEBUG`，benchmark 还用显式分支核验错误码与最终 checksum（[@def-16.6.1]）。

**把批均值 p99 当成请求尾延迟。** 这里每个样本是 524288 词的批量墙钟成本，21 个批次的最大值替代不了线上请求延迟分布（[@def-16.7.2]）。

**把 owned_handle 称为全链路零拷贝。** 它避免复制回 C，但 Vec 到 Arc 的内部复制仍然存在；sample 与汇编都提醒我们限定结论范围（[@def-16.8.2]）。

**只凭 vector.body 标签宣传 SIMD。** 当前转换核实际是四元素展开的标量运算，应同时查看 IR 操作与最终本机汇编（[@def-16.6.2]）。

**用槽数量上限替代总内存预算。** 单对象上限与 4096 槽仍允许很高的理论总占用，生产准入需要单独限制聚合字节，不能靠分配失败治理负载。

## 16.11 本章小结与章末件 {#sec-cpp-rust.4.16.11}

::: note 本章小结

- 安全核与协议适配层分开，FFI 边界上只让可审计的少量代码碰 unsafe（[@def-16.1.1]、[@ex-16.1.1]）。

机制上，你应能指出 release 在哪一步使句柄失效，解释一个快照为什么仍可在 release 之后安全读完，解释 generation 退休如何避免身份回绕，区分句柄释放责任与底层分配器所有权，并说明 null 检查为什么无法验证任意地址。四个性能值分别包含什么也要说清：第一组没有拥有对象分配，第二组有；copy_out 能给 C 完整数组，owned_handle 在本夹具中只交付摘要。跨边界成本与业务计算位置必须一起描述，否则一个看似漂亮的加速比很容易对应错误的问题。

交付范围到这里为止：安全 Rust 核、最小 C ABI、C11 CLI、CMake 链接、两侧测试与两组实测都已完成；Miri、TSan、Loom 与 Linux perf 没有运行，Windows、32 位、动态装载卸载与多库实例互通也没有验证，更没有把不合法指针解引用当作负面测试来执行。注册表线性扫描空槽，聚合内存预算也不属于本项目的能力，这限制了它直接作为高并发无限对象服务使用的可能；若要部署，先补业务级总内存准入、授权与卸载协调，再做独立性能与故障验证，这些限制不影响现有接口在已声明边界内的可执行性。
