共 21 题，分三组。**A 组概念**检验你能否说出协议里每个名词指的是什么；**B 组推理**检验你能否从表、代码与测试矩阵推出结论；**C 组实操**是设计与验收任务：推出上界、指定清理路径、写出可执行的验收测试。全部题目附解答，四道题另附提示层。

## A 组 · 概念（1–8）

::: ex A1 · 有界执行器的三件事与两不做（主线 ④） {#ex-15.A.1}

「有界执行器」要求哪三件事？它明确不做的两件事是什么？为什么这两组不能混着说？

::: sol 解答

三件：管理员预先命名的工具集、类型化参数预算、每份已接受工作在退出前报告资源状态（reaped、EOF 与清理错误）。不做：文件/网络/内核配额隔离，后代进程清理。混着说的后果是把「能执行命名工具」偷换成「能安全执行任意程序」——后者需要独立 OS 机制与测试，不会因为用 Rust 写就自动出现（[定义 15.1.1](ch15.md#def-15.1.1)、[定义 15.1.4](ch15.md#def-15.1.4)）。

:::

:::

::: ex A2 · 两种注册入口（主线 ④） {#ex-15.A.2}

`Registry::helper` 与 `Registry::fixed` 各自固定了什么？请求方还能改什么？为什么没有第三种「传命令字符串」的入口？

::: sol 解答

两者都固定可执行文件绝对路径与 argv，请求方都不能替换。`helper` 只接受 Echo、Logs、Sleep、Fail 四种受限行为；`fixed` 只接受 `Input::Fixed`，argv 完全来自启动配置。未注册名字一律 `UnknownTool`。第三种入口不存在，因为命令字符串会把类型化预算退回自由文本，并破坏不经过 shell 的字节边界（[定义 15.1.2](ch15.md#def-15.1.2)）。

:::

:::

::: ex A3 · 参数预算的七条边界（主线 ④） {#ex-15.A.3}

写出参数预算的七条边界，并说明超限之后发生什么。为什么「截断后继续执行」不可接受？

::: sol 解答

Echo 4096 字节且拒绝内部 NUL；Logs 每路 16MiB；Sleep 60000 毫秒；Fail 只接受非零 `u8`；timeout 大于零且不超过 60 秒；argv 最多 32 项、每项最多 4096 字节；注册名限 ASCII 字母、数字与连字符。超限返回 `InvalidInput`。截断会让执行内容与请求不一致，等于换了一份工作却报告成功（[定义 15.1.3](ch15.md#def-15.1.3)、[例 15.1.2](ch15.md#ex-15.1.2)）。

:::

:::

::: ex A4 · 范围声明（主线 ④） {#ex-15.A.4}

范围声明规定的环境、目录、stdin 与标准流各是什么？它同时否定了哪种「兼容」做法？

::: sol 解答

空环境（`env_clear`）、工作目录 `/`、stdin 接 null、stdout 与 stderr 各一条独立管道。它避免不经意继承凭据与配置，也意味着依赖 `HOME`、`PATH` 或项目 cwd 的命令不能照搬；否定的做法是「为了兼容重新继承整个环境，然后仍声称接口没变」。Windows 语义本轮未运行（[定义 15.1.4](ch15.md#def-15.1.4)）。

:::

:::

::: ex A5 · 三个上界各挡什么（主线 ②） {#ex-15.A.5}

`Q`、`C`、`R` 默认各是多少？各挡哪一类失控？缺任意一个会留下什么无界集合？

::: sol 解答

`Q=16` 挡上游积压，`C=4` 挡无限 spawn（也是直接子进程数上界），`R=8192` 挡日志留存；总许可 `Q+C=20` 还覆盖「提交中」的临时持有。只有 Q 没有 C，消费方会无限 spawn；只有 C 没有 Q，上游积压无限；只有信号量却先 spawn 再等，会留下无限等待任务（[定义 15.2.1](ch15.md#def-15.2.1)）。

:::

:::

::: ex A6 · 三种观察（主线 ①） {#ex-15.A.6}

取消意图、阶段快照、最终结果各由什么通道承载？各自能说明什么、不能替代什么？

::: sol 解答

取消意图走 Ticket 持有的 watch 发送端，可被 `send_replace` 覆盖合并，读到 `true` 只说明请求已登记；阶段快照走另一个 watch 的 Stage（Queued、Running(pid)、Reaped、Finished），只说明读取时的最后状态；最终结果走 oneshot 的 `ToolResult`。三者不能互相替代：快照不是事件日志，也不是回收凭证（[定义 15.3.1](ch15.md#def-15.3.1)）。

:::

:::

::: ex A7 · 六个完整性字段（主线 ①） {#ex-15.A.7}

`prefix.len`、`total`、`checksum`、`eof`、`error`、`reaped` 各能支持什么解释？各不能支持什么解释？

::: sol 解答

`prefix.len` 是当前保留前缀长度，不能说明工具只输出了这些字节；`total` 是父进程实际读到的累计字节，不是所有后代的总输出；`checksum` 是全部已读字节的 FNV-1a，不是密码学认证；`eof` 是这一路 read 确实返回 0，不代表另一条流完成；`error` 是读取或排空期限错误，不推出子进程必定非零退出；`reaped` 是直接 Child 的 wait 成功，不代表整个进程树退出（[15.4 字段表](ch15.md#sec-cpp-rust.4.15.4)）。

:::

:::

::: ex A8 · 三类证据各管一段（主线 ④） {#ex-15.A.8}

母本 S11、Tokio 1.54.0 的固定版本文档、本项目自有源码与编译产物，各支持哪一类论断？举一个把它们互相冒充的例子。

::: sol 解答

S11 的 390–394 页提供所有权交接、关闭与多生产者概念；Tokio 1.54.0 的指定行提供 `start_kill`、`kill`、`wait` 与 cancel-safe 等行为契约；自有源码、测试与编译产物提供本机实际执行证据。互相冒充的例子：拿一段 `.s` 或 MIR 证明「进程树会被正确回收」——编译产物只说明生成了哪些指令，不证明操作系统层的回收（[15.9 节](ch15.md#sec-cpp-rust.4.15.9)）。

:::

:::

## B 组 · 推理（9–16）

::: ex B9 · 第 17 次提交为什么立刻 Full（主线 ②） {#ex-15.B.9}

`Q=16`、`C=4`。runtime 刚启动、dispatcher 还没被调度，调用方连续 `try_submit`。第 17 次提交拿到了总许可吗？它会成功吗？结论要写成哪两句？

::: sol 解答

许可拿得到（总数 `Q+C=20`，此前只用 16），但 `try_send` 会返回 `Full`，因为通道容量只有 16 且没有消费者。局部 Job 销毁时许可随析构归还，不需要手工减计数。两句结论：`Q+C` 是总体持有上界，不是初始同步提交成功数下界；需要等待的接口要另设有限期限，本项目选择直接拒绝（[例 15.2.2](ch15.md#ex-15.2.2)）。

:::

:::

::: ex B10 · 8 个双路工具的准入账（主线 ②） {#ex-15.B.10}

8 个「双路各写 262144 字节」的 `Logs` 工具同时到达。按 `Q=16`、`C=4`、`R=8192` 推出：总许可、通道里最多几个 Job、同时最多几个直接子进程、用户态日志保留上界、每项实际读取多少字节，以及哪些数字不在这个预算里。

::: sol 解答

总许可 20，8 项都在预算内，8 次 `try_submit` 都能拿到许可；运行槽上界 `C=4`，其余 4 项留在队列里，队列此刻 4 项、不超过 `Q=16`。保留前缀 `8 × 2 × 8192 = 131072` 字节有效长度；每项实际读取 `2 × 262144 = 524288` 字节，超出前缀的部分只进 total 与 checksum。不在预算里的：Vec 容量与分配器（向系统申请堆内存的组件）元数据、路径与 argv、watch 与 oneshot、任务头、两个各 8192 字节的读缓冲、内核管道缓冲（[例 15.2.1](ch15.md#ex-15.2.1)）。

:::

:::

::: ex B11 · 用 layout 表算一批工具的内存（主线 ②） {#ex-15.B.11}

沿用 `Q=16`、`C=4`、`R=8192`，一批 8 个 `Logs` 工具。只用 15.5.1 的表能写出哪几项？哪些必须写「未采集」？为什么不能把 `224 × 8` 当常驻内存？

::: sol 解答

可加三项：8 个 `ToolResult` 句柄 `8 × 224 = 1792` 字节；8 个 `Ticket` `8 × 32 = 256` 字节；两路保留前缀 `8 × 2 × 8192 = 131072` 字节（前缀长度上界，不是 Vec 容量）。这组可加项合计 133120 字节，即 130 KiB；按 1000 进制除出来的是 133 kB，两个读数只差在单位，写成「133 KiB」就是把 kB 的数冠上 KiB 的名。必须写未采集：两份 Log 的 Vec 容量与分配器元数据、Job 与 watch/oneshot 共享状态、两个 8192 字节读缓冲、跨 await 存活的工作 Future。224 字节只是句柄，不含前缀堆分配，更不能拿来推算 RSS（[例 15.5.1](ch15.md#ex-15.5.1)）。

:::

:::

::: ex B12 · 复算拒绝路径的 p99 与整批时间（主线 ②） {#ex-15.B.12}

admission-full 表：21 批，mean 3.662、sd 0.064、p50 3.653、p99 3.886，单位 ns/拒绝。请回答：p99 为什么正好等于最大值？整批 100000 次拒绝大约花多少时间？把 3.662 写成「过载响应延迟 3.7 ns」错在哪？

::: sol 解答

nearest-rank 取第 `ceil(21 × 0.99) = 21` 个，所以 p99 就是最大批均值 3.886。整批约 `3.662 ns × 100000 ≈ 366200 ns = 366.2 µs`，这是批聚合量。写成「过载响应延迟」错在对象：本节测的是单生产者循环里被拒绝的尝试，不含成功提交的 watch/oneshot/Job、不含子进程、也不含调用方重试；正确写法是「热态饱和下，单线程连续 100000 次拒绝的批均值为 3.662 ns/拒绝尝试，21 批的 p99 为 3.886」（[例 15.6.1](ch15.md#ex-15.6.1)）。

:::

:::

::: ex B13 · 前缀保留到底慢不慢（主线 ③） {#ex-15.B.13}

C1/R0 的批均值 2.871944、中位数 2.535537；C1/R4096 的批均值 3.505500、中位数 2.285484，sd 2.472717，p99 9.227984，单位 ms/工具。能不能写「保留 4096 字节前缀使这批工具变慢」？正确表述是什么？

::: hint 提示

先看中位数与 sd 的方向，再问这两轮是不是同环境、随机化配对的净增量实验。

:::

::: sol 解答

不能。均值升高的同时中位数反而更低，sd 达到 2.472717、最大批均值 9.227984，说明高噪声长尾在拉动均值；第一轮修复版 run-03 中两者均值接近、R4096 还略低，两轮不是随机化配对实验，不能据此报显著性。完整生命周期还含进程启动、两路各 256KiB 校验、调度与 wait，无法从这些批次识别稳定的前缀复制惩罚。正确表述：「本轮桌面环境下，C1/R4096 的批均值高于 C1/R0，但中位数更低且长尾明显，数据不支持稳定结论；要研究纯复制增量需另设聚焦实验」（[15.7](ch15.md#sec-cpp-rust.4.15.7)）。

:::

:::

::: ex B14 · C4 的改善属于谁（主线 ③） {#ex-15.B.14}

同为 R4096，C1 的批均值 3.505500、C4 为 1.046813，单位 ms/工具。能写「C 从 1 提到 4 带来四倍加速定律」吗？能写「单个工具耗时 1 ms」吗？能支持的最强结论是什么？

::: sol 解答

都不能。`1.046813 ms/工具` 是 8 个工具重叠执行后的批聚合值，单个工具的完整响应可能更长；C4 的改善只属于这份日志负载，结果没有分离进程启动、内核复制、用户校验与调度各自贡献，也不是对任意 CPU 工具都成立的四倍定律。最强结论是：在这份 8 工具、两路各 262144 字节的负载与本轮构建下，C4 的批聚合 ms/工具低于 C1，与「多工具可重叠」的机制一致；生产配置仍应按实际资源成本决定（[15.7](ch15.md#sec-cpp-rust.4.15.7)）。

:::

::: ex B15 · 两种保留长度的 checksum 为什么相同（主线 ②） {#ex-15.B.15}

一批 8 个工具、每路 262144 字节。R=0 与 R=4096 下，一批总读取字节、前缀保留上界、checksum 覆盖范围各是多少？为什么两者聚合 checksum 相同？`7596343361303360080` 是哪个范围的值？

::: sol 解答

总读取都是 `8 × 2 × 262144 = 4194304` 字节。R=0 时前缀 0 字节；R=4096 时保留 `8 × 2 × 4096 = 65536` 字节，每路前缀长度 `min(4096, 262144) = 4096`。checksum 覆盖父进程读到的全部 4194304 字节，与保留多少无关，所以两种配置算出相同聚合值。`7596343361303360080` 是单批（8 工具 × 2 路）的聚合 checksum，三个配置的 63 批逐行都等于它；跨 63 批再求和会得到另一个数（17401029919372894640），归档里没有这个数（[例 15.7.1](ch15.md#ex-15.7.1)）。

:::

:::

::: ex B16 · 360 项测试能写到哪一级（主线 ④） {#ex-15.B.16}

debug/release 各 10 轮、共 360 项测试执行全部通过，另有每 profile 5 轮八独立 Runtime、共 800 条结果。能不能写「并发正确性已被验证」？应该怎么写？

::: sol 解答

不能。测试验证的是一组写明的契约（满载 `Full`、超时 reaped、shutdown 后 `Closed` 等），不是所有交错；本轮没有 Loom、Miri、TSan，也没有独立技术审计。正确表述是「这些契约在 360 次执行中被重复观察到，800 条压力结果各自核验了字段」。另外 200 毫秒是串行排空负对照的测试观察预算，不是被报告的 benchmark 延迟（[定义 15.8.3](ch15.md#def-15.8.3)、[15.8](ch15.md#sec-cpp-rust.4.15.8)）。

:::

## C 组 · 实操（17–21）

这一组不要求跑出新的性能数字，要求你写出可被他人复核的设计与验收条件。所有配置都沿用 `Config::default()`：`Q=16`、`C=4`、`R=8192`、`drain_grace=1s`。

::: ex C17 · 从 12 个工具的突发推出准入上界（主线 ②） {#ex-15.C.17}

一批 12 个 `Logs` 工具同时到达，每个向两路各写 131072 字节。请推出：总许可是否够用、同时最多几个直接子进程、通道里最多几个 Job、用户态前缀保留上界、一批总读取字节；再列出三项不在预算里、必须写「未采集」的存储，并写出这批结束时你要求的字段断言。

::: hint 提示

先算 `Q+C` 能容下几项，再算运行槽与队列的差；前缀只乘保留长度 R，不要乘实际读取字节。

:::

::: sol 参考路径

总许可 `Q+C=20 ≥ 12`，12 次 `try_submit` 都能取得许可。运行槽 `C=4`，同时最多 4 个直接子进程；其余 `12 − 4 = 8` 项留在队列里，不超过 `Q=16`。前缀保留上界 `12 × 2 × 8192 = 196608` 字节有效长度；每项实际读取 `2 × 131072 = 262144` 字节，一批共 `12 × 262144 = 3145728` 字节。不在预算里：Vec 容量与分配器元数据、Job 与 watch/oneshot 共享状态、两个 8192 字节读缓冲、跨 await 存活的工作 Future、内核管道缓冲。验收断言：12 个 `ToolResult` 全部到手；每个 `reaped=true`、两路 `eof=true`、无清理错误；每个 `total=131072`，每个 `prefix.len=min(8192,131072)=8192`；`shutdown` 的 join 计数为 12（[定义 15.2.1](ch15.md#def-15.2.1)、[定义 15.7.1](ch15.md#def-15.7.1)）。

:::

:::

::: ex C18 · 200 毫秒超时走哪条清理路径（主线 ①） {#ex-15.C.18}

一个 `Logs{bytes: 262144}` 工具已经在 Running，timeout 为 200 毫秒。到期后发出 kill，wait 随后成功，但工具留下一个后代仍持有 stderr 写端。请写出最终 `ToolResult` 的每个字段、许可归还时机，以及验收测试要断言什么、不要求库做什么。

::: hint 提示

四个字段分开写：Outcome、reaped、两路 eof、error；`total` 不许补到 262144。

:::

::: sol 参考路径

路径：timeout 只触发停止意图，`start_kill` 发信号；工作继续 select wait 与两路读取；wait 成功 → `reaped=true`，进入 Draining；stdout 读完 → `eof=true`；stderr 写端仍被后代持有，继续等到 `drain_grace=1s` 到期，关闭该读端并记录排空 error。最终结果：`TimedOut`、`reaped=true`、stdout `eof=true`、stderr `eof=false` 且 error 非空；`total` 只累计父进程真正读到的字节，不会补到 262144。许可仍由 Job 持有，直到结果交付、任务被 join 后随析构归还。验收断言：started 先看到 Running(pid)；最终 Outcome 与四个字段如上；shutdown join 计数包含它。不要求库：杀后代、宣称进程树已回收、把排空错误改写成 EOF（[例 15.4.1](ch15.md#ex-15.4.1)、[定义 15.4.4](ch15.md#def-15.4.4)）。

:::

::: ex C19 · 为取消写一条验收测试（主线 ①） {#ex-15.C.19}

为「运行中取消」与「排队中取消」各写一条验收测试：建立什么阶段关系、断言哪些字段、怎样证明许可没有提前释放、为什么不能用固定 sleep 等待启动。

::: sol 参考路径

运行中取消：提交 `Sleep(60000)`（timeout 1 秒即可）；等 `Ticket::started` 读到 `Running(pid)`，再 `cancel`；`wait` 得到 `Cancelled`、`reaped=true`、两路 `eof=true`；`shutdown` 的 join 计数包含这一项。排队中取消：先用长任务占满运行槽（必要时配 `Q=1`、`C=1`），再提交第二个并取消；dispatcher 取到它时先查取消位与 deadline，直接返回结构化结局，`pid` 保持 `None`。许可没有提前释放的证据来自所有权阅读与 join：许可在 Job 的 `_admission` 里，随工作 Future 析构；测试至少断言 shutdown 计数与后续工作仍能完成。不能用固定 sleep：短 echo 可能只让观察者看到 Finished，固定等待是在猜「应该启动了」，`started` 才是真实阶段关系；`started` 返回 None 也不证明从未 spawn，最终要看 `ToolResult.pid`（[15.3](ch15.md#sec-cpp-rust.4.15.3)、[15.8 测试矩阵](ch15.md#sec-cpp-rust.4.15.8)）。

:::

::: ex C20 · shutdown 的接受与拒绝边界（主线 ①） {#ex-15.C.20}

调用方保留一个 Client 克隆，队列里已有一个排队 Job，另有一个 Ticket 已被 drop。此时 await `shutdown`。请写出验收断言：排队 Job 是否被丢弃、shutdown 后新提交返回什么、已 drop 的 Ticket 结果还能否取出、join 计数至少是几。

::: sol 参考路径

断言一：排队 Job 不被丢弃，dispatcher 继续 recv 直到 None，按 C 推进并最终 join。断言二：shutdown 之后新提交返回 `Closed`，但 Client 克隆仍可存活。断言三：已 drop 的 Ticket 没有接收者，结果不可取；工作仍完成清理并计入 join。断言四：join 计数至少包含排队 Job 与被 drop Ticket 对应的工作两项，即至少 2；若它们尚未结束，shutdown 等待而不是返回 0。还要断言「已进入 oneshot 的结果仍可取」与「`shutdown` 很快返回」不是同一件事：完成的标志是 dispatcher 已 join 所有工作，而不是停止信号已发出（[例 15.8.1](ch15.md#ex-15.8.1)、[定义 15.8.1](ch15.md#def-15.8.1)）。

:::

::: ex C21 · 出口检查与归档复核（主线 ④） {#ex-15.C.21}

写一份出口验收清单：从干净构建到 CLI 要跑哪些命令？`sleep 5000 100` 的预期结局与退出码是什么？重新采集归档时，输出目录、锁与旧 run 各有什么约束？

::: sol 参考路径

命令序列：`cargo fmt --check`；`cargo clippy --offline --locked --all-targets -- -D warnings`；`cargo test --offline --locked`；`cargo build --offline --locked --bins`；`cargo run --offline --locked --example library -- "$PWD/target/debug/tool-helper"`；再跑 `echo` 与 `sleep 5000 100`。最后一条应返回 `TimedOut`、`reaped=true`、退出码 1——这是业务结局，不是崩溃，不能改成 0。归档：`bash scripts/measure.sh evidence/my-runtime-run` 的输出目录必须尚不存在，脚本不覆盖 run-01 至 run-04，失败归档不自动删除；正式计时用目录锁串行化，锁存在时等待持有者正常退出，不能直接 rm 锁目录；采样使用另一个独立进程；换机器先复现正确性与计量边界，再讨论数值差异（[15.11](ch15.md#sec-cpp-rust.4.15.11)）。

## 批改时最常给的三条意见

1. **把「已请求」写成「已清理」**：缺 wait 成功、两路各有结论、任务 join 中任一项，结论就只能停在「已请求停止」。先改句子，再补测试。
2. **单位与对象错位**：把 ns/拒绝尝试写成请求延迟，把 ms/工具写成单工具耗时。先写对象名（拒绝尝试、批聚合），再写数字。
3. **上界只算一半**：只写 `Q` 或只写 `C`，漏掉提交中的 `Q+C` 与表外内存。按[定义 15.2.1](ch15.md#def-15.2.1) 的五类资源逐行补，缺的写「未采集」，不要填推测值。
