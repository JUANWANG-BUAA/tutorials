# 第十五章 · 闭卷回忆卡

「看懂」只说明答案在眼前时能识别；评审和故障定位要的是从空白纸上提取。这一页把第十五章拆成 24 张卡，先读卡面自己答，再展开核对。

**用法与节奏**

| 时点 | 做什么 | 判定 |
|:--|:--|:--|
| 学完当天 | 第一组「定义卡」8 张 | 关键词写全才算 ✓ |
| 第 1 天 | 第二组「结论卡」8 张 | 能说清前提才算 ✓ |
| 第 3 天 | 第三组「第一行卡」8 张 | 写出第一步才算 ✓ |
| 第 7 天 | 只重做标成 △ 与 × 的卡 | 全对即可进入第十六章 |

每张卡给自己一个记号：✓ 一次说对；△ 说对一半或要提示；× 想不起来。只重做 △ 与 ×，不要把整叠反复过一遍——那是在读，不是在提取。

## 第一组 · 定义卡（说全称与前提）

::: ex 卡 1 · 有界执行器 {#rc-15-1}

卡面：有界执行器要求哪三件事？本项目明确不做的两件事是什么？

::: sol 核对

三件：管理员预先命名的工具集、类型化参数预算、每份已接受工作在退出前报告资源状态（reaped、EOF 与清理错误）。不做：文件/网络/内核配额隔离，以及后代进程清理。三件事缺一不可，两件不做要逐字写进范围声明（[定义 15.1.1](ch15.md#def-15.1.1)、[定义 15.1.4](ch15.md#def-15.1.4)）。
:::

:::

::: ex 卡 2 · 两种注册入口 {#rc-15-2}

卡面：`helper` 与 `fixed` 各固定了什么？请求方还能改什么？

::: sol 核对

两者都固定可执行文件绝对路径与 argv，请求方都不能替换。`helper` 接受 Echo、Logs、Sleep、Fail 四种受限行为；`fixed` 只接受 `Input::Fixed`。未注册名字一律 `UnknownTool`，不存在命令字符串入口（[定义 15.1.2](ch15.md#def-15.1.2)）。
:::

:::

::: ex 卡 3 · 参数预算 {#rc-15-3}

卡面：默写参数预算的七条边界，并说出超限的结局。

::: sol 核对

Echo 最多 4096 字节且拒绝内部 NUL；Logs 每路最多 16MiB；Sleep 最多 60000 毫秒；Fail 只接受非零 `u8`；timeout 大于零且不超过 60 秒；固定 argv 最多 32 项、每项最多 4096 字节；注册名只接受有限长度的 ASCII 字母、数字与连字符。超限返回 `InvalidInput`，不是截断后继续执行（[定义 15.1.3](ch15.md#def-15.1.3)）。
:::

:::

::: ex 卡 4 · 范围声明 {#rc-15-4}

卡面：子进程的环境、目录与标准流各是什么？这条声明同时否定了什么做法？

::: sol 核对

空环境（`env_clear`）、工作目录固定为 `/`、stdin 接 null、stdout 与 stderr 各一条独立管道。它避免不经意继承凭据，也否定了「为了兼容性重新继承整个环境，然后仍声称接口没变」；依赖 `HOME`、`PATH` 或项目 cwd 的命令不能照搬（[定义 15.1.4](ch15.md#def-15.1.4)）。
:::

:::

::: ex 卡 5 · 三层上界 Q、C、R {#rc-15-5}

卡面：三个字母各是多少、各挡哪一类失控？总许可为什么是 `Q+C`？

::: sol 核对

默认 `Q=16`、`C=4`、`R=8192`。Q 挡上游积压，C 挡无限 spawn（也是直接子进程数上界），R 挡日志留存；总许可 `Q+C=20`，同时覆盖「排队中」与「已接受但正在提交」两类持有（[定义 15.2.1](ch15.md#def-15.2.1)）。
:::

:::

::: ex 卡 6 · 许可寿命 {#rc-15-6}

卡面：许可从哪一刻开始、到哪一刻结束？它绑定的是什么？

::: sol 核对

从 `try_submit` 取得开始，到持有它的 Job 字段 `_admission` 随工作 Future 析构为止。它绑定「还有一份真实工作没收拾完」，不是「调用方还愿意等」；调用方超时、丢弃 Ticket 或断开连接都不会缩短这段寿命（[定义 15.3.2](ch15.md#def-15.3.2)）。
:::

:::

::: ex 卡 7 · 回收观察点 {#rc-15-7}

卡面：`reaped=true` 的定义是什么？它覆盖谁、不覆盖谁？

::: sol 核对

父进程确实观察到直接 Child 的 wait 返回成功。它只覆盖本进程亲手 spawn 的那一个子进程，不覆盖后代，也不等于两路日志已读完；wait 出错时结果是 `WaitFailed` 且 `reaped=false`（[定义 15.4.2](ch15.md#def-15.4.2)）。
:::

:::

::: ex 卡 8 · 排空宽限 {#rc-15-8}

卡面：`drain_grace` 的默认值、它所限定的对象，以及到期后允许与不允许的动作。

::: sol 核对

默认 1 秒，限定进入 Draining 后继续等待两路 EOF 的时间。到期后关闭尚未完成的读端、记录排空错误，已经读到的 prefix、total 与 checksum 全部保留；不允许填 `eof=true` 伪造 EOF，也不杀后代（[定义 15.4.4](ch15.md#def-15.4.4)）。
:::

:::

## 第二组 · 结论卡（说清前提与范围）

::: ex 卡 9 · 拒绝路径为什么短 {#rc-15-9}

卡面：`try_submit` 的实际检查顺序是什么？饱和时停在哪一步？

::: sol 核对

检查关闭状态 → 检查 timeout → 尝试总许可 → 解析注册项 → 构造消息 → `try_send`。饱和时停在第三步，不创建 watch、oneshot 与 Job，所以成本显著低于成功路径。错误优先级不永远是「先 UnknownTool 再 Full」，鉴权应由更外层独立完成（[定义 15.2.2](ch15.md#def-15.2.2)）。
:::

:::

::: ex 卡 10 · `Q+C` 是哪种保证 {#rc-15-10}

卡面：拿到了总许可，`try_send` 还会失败吗？`Q+C` 能保证初始突发全部收下吗？

::: sol 核对

会。多个提交者与 dispatcher 交错时，`try_send` 仍可能返回 `Full` 或 `Closed`；局部 Job 销毁时许可随析构归还。初始 dispatcher 未调度时通道只能先收 Q 项，第 17 次提交拿得到许可也可能 `Full`。`Q+C` 是总体持有上界，不是初始同步提交成功数下界（[例 15.2.2](ch15.md#ex-15.2.2)）。
:::

:::

::: ex 卡 11 · 三种观察各管什么 {#rc-15-11}

卡面：取消意图、阶段快照、最终结果各由什么承载？各不能替代什么？

::: sol 核对

取消意图是 Ticket 通过 watch 写下的布尔位，可用 `send_replace` 覆盖合并，读到 `true` 只说明请求已登记；阶段快照是另一个 watch 的 Stage（Queued、Running(pid)、Reaped、Finished），只说明读取时的最后状态；最终结果走 oneshot 的 `ToolResult`。三者不能互相替代，`started` 返回 None 也不证明从未 spawn（[定义 15.3.1](ch15.md#def-15.3.1)）。
:::

:::

::: ex 卡 12 · wait 成功为何不够 {#rc-15-12}

卡面：子进程已退出，为什么还要排空？串行读两路会怎样？

::: sol 核对

「子进程退出」与「写端全部关闭」不是同一事件：后代可能继承写端，CLOEXEC 竞争还可能让无关进程持有额外写端。串行先读 stdout 到 EOF 再读 stderr，双路大输出时双方互锁。可宣称回收要 wait 成功 + 两路各有结论 + join（[定义 15.4.1](ch15.md#def-15.4.1)）。
:::

:::

::: ex 卡 13 · 前缀与校验 {#rc-15-13}

卡面：`Log::record` 先做什么、后做什么？`R=0` 时哪些成本仍在？

::: sol 核对

先更新全部已读字节的 checksum 与 total，再计算还能保留多少前缀。`R=0` 时前缀为空，但读取、计数与 FNV-1a 逐字节校验照旧，读取也不能停——达到 R 后继续读并丢弃后缀，否则工具会被反压卡住（[定义 15.4.3](ch15.md#def-15.4.3)）。
:::

:::

::: ex 卡 14 · 布局不是 ABI {#rc-15-14}

卡面：224 字节的 `ToolResult` 包含什么、不包含什么？`sret` 能当 C 接口吗？

::: sol 核对

包含两份 Log 的结构体（Vec 句柄、计数、checksum 与错误状态），不含前缀堆分配与 Vec 容量。size/align 是 rustc 1.99.0、aarch64-apple-darwin 这次构建的观测；32 字节 `sret` 是本轮降低 Result 的实现细节，不是 C ABI。跨进程只承诺 argv 与管道字节（[定义 15.5.1](ch15.md#def-15.5.1)、[定义 15.5.2](ch15.md#def-15.5.2)）。
:::

:::

::: ex 卡 15 · 两个 benchmark 的单位 {#rc-15-15}

卡面：`ns/拒绝尝试` 与 `ms/工具` 各由什么除以什么？各自回答什么问题？

::: sol 核对

前者是整批 100000 次 `try_submit` 的墙钟纳秒除以操作数，回答热态饱和下一次被拒绝的提交摊到多少纳秒；后者是 8 个工具从首次 `try_submit` 到全部 `ToolResult` 到手的批墙钟除以工具数，回答这份负载的聚合完成速度。两者都不是请求延迟；C4 重叠执行使聚合倒数可小于单工具完整响应时间（[定义 15.6.2](ch15.md#def-15.6.2)、[定义 15.7.2](ch15.md#def-15.7.2)）。
:::

:::

::: ex 卡 16 · 关闭协议与兜底 {#rc-15-16}

卡面：shutdown 的四步是什么？Drop 为什么不能替代它？

::: sol 核对

停止接收 → 处理已接受 Job → join 全部工作任务 → 返回 join 计数与失败信息。它是异步的，必须显式 await；关闭接收端不丢弃已缓冲 Job，shutdown 后新提交返回 `Closed`。Drop 只发停止请求、不同步等待，程序立刻销毁外层 runtime 时不能承诺清理 Future 仍有机会运行（[定义 15.8.1](ch15.md#def-15.8.1)、[定义 15.8.2](ch15.md#def-15.8.2)）。
:::

:::

## 第三组 · 第一行卡（只写第一步）

这一组练的是「一离开答案就不知道第一行写什么」那个毛病。每题只写第一行动作，不展开。

::: ex 卡 17 · 要挂一个新工具 {#rc-15-17}

卡面：管理员要接入一个依赖仓库目录与配置文件的只读检查程序。第一行写什么？

::: sol 核对

第一行：把这个工具的动态字段写下来，逐个对照 helper 与 fixed，确认三条路都不直接成立，再谈新增适配器。适配器要把目录与配置表达成有限字段、在预算内校验，并把需要哪些环境与目录写进契约（[例 15.1.1](ch15.md#ex-15.1.1)）。
:::

:::

::: ex 卡 18 · 100 KiB 的 Echo {#rc-15-18}

卡面：调用方提交 100 KiB 文本要求回显。第一行写什么？

::: sol 核对

第一行：返回 `InvalidInput`，既不能截断到 4096，也不能取消预算按内容排队。随后补一句分工：预算只限已进入队列的消息大小，接收网络请求的上层仍要先验证长度再读正文（[例 15.1.2](ch15.md#ex-15.1.2)）。
:::

:::

::: ex 卡 19 · 第 17 次提交立刻 Full {#rc-15-19}

卡面：runtime 刚启动，`Q=16`、`C=4`，第 17 次 `try_submit` 返回 `Full`。第一行写什么？

::: sol 核对

第一行：把问题拆成两问——许可拿到了吗（`Q+C=20` 还有余量），通道有消费者吗（dispatcher 未调度，容量 16 已满）。结论写成「`Q+C` 是持有上界，不是初始同步提交成功数下界」（[例 15.2.2](ch15.md#ex-15.2.2)）。
:::

:::

::: ex 卡 20 · cancel 之后问「清理完了吗」 {#rc-15-20}

卡面：调用方已 `cancel`，问这项工作是否已清理。第一行写什么？

::: sol 核对

第一行：按六步查——取消意图是否登记、Child 是否存在过、停止请求是否发出、wait 是否成功、两路是否各有结论、任务是否被 join。缺任何一步，只能写「已请求停止」，不能写「已清理」（[15.3 节](ch15.md#sec-cpp-rust.4.15.3)）。
:::

:::

::: ex 卡 21 · 工具退出了，stderr 没有 EOF {#rc-15-21}

卡面：直接 Child 已 wait 成功，stderr 仍读不到 EOF。第一行写什么？

::: sol 核对

第一行：查写端——可能是后代继承了 stderr，也可能是 CLOEXEC 竞争让无关进程多持了一个 PIPE。等到 `drain_grace=1s` 到期记排空错误，`eof=false`，不伪造 EOF，也不杀后代（[定义 15.4.4](ch15.md#def-15.4.4)）。
:::

:::

::: ex 卡 22 · 拿 224 字节算常驻内存 {#rc-15-22}

卡面：同事用 `224 × 8` 报「这批请求的常驻内存就是这些」。第一行写什么？

::: sol 核对

第一行：先分表内句柄与表外存储——8 个 `ToolResult` 1792 字节、8 个 `Ticket` 256 字节、两路前缀 131072 字节可以相加；Vec 容量与分配器元数据（分配器是向系统申请堆内存的组件）、Job 与 watch/oneshot、两个 8192 字节读缓冲、跨 await 存活的工作 Future 本轮未采集，只能写「未采集」（[例 15.5.1](ch15.md#ex-15.5.1)）。
:::

:::

::: ex 卡 23 · 有人引用 3.662 ns/拒绝 {#rc-15-23}

卡面：汇报里出现「3.662 ns/拒绝」。第一行写什么？

::: sol 核对

第一行：查三条——满载是否被证明（两个 Job 占满 `Q+C`、每次提交都 `Full`）、单位是否写成 ns/拒绝尝试、路径是否只到许可失败。三条缺一，这个数只能内部参考（[定义 15.6.1](ch15.md#def-15.6.1)、[定义 15.6.2](ch15.md#def-15.6.2)）。
:::

:::

::: ex 卡 24 · 有人报「单个工具 1 ms」 {#rc-15-24}

卡面：有人把 1.046813 ms/工具写成「一个工具约 1 毫秒」。第一行写什么？

::: sol 核对

第一行：查它是不是 C4 的批聚合——8 个工具重叠执行、计时终点是全部结果到手、批后校验在计时外但 checksum 在计时内。它不是单工具完整响应，也不是请求 p99（[定义 15.7.2](ch15.md#def-15.7.2)）。
:::

:::
