# 17 综合大项目：tidekv——把四步主线一次走完

<div class="chapter-index">

**这一章换一个问法**：前面十六章每章只解决一环，这一章要求你在同一个代码仓库里把四环同时守住。项目是一台最小的本地键值引擎 `tidekv`——写请求进日志和内存表，读请求跨内存表和不可变段文件查找，压缩交给子进程，旧段由 epoch（一个全局逻辑时钟，用来判断哪些旧数据所有读者都放手了）回收。

它足够小，一个人两周内能写完；也足够深，布局、所有权、泛型、并发、异步、进程、回收、SIMD、归因与门禁，每一章都能在这里找到一个具体的咬合点。

**代码位置**：`projects/tidekv/`（与第 15 章的 `projects/agent-runtime/`、第 16 章的 `projects/ffi-bridge/` 并列，但只有零个外部依赖，只用标准库）。

**本章怎么读**：17.1 立项，17.2–17.7 六块机制，17.8 实验与门禁。第一遍只读 17.1、17.2、17.8；第二遍按顺序全读。

</div>

读图：**三条泳道不是三层架构，是三笔账。**第一行的账是「副作用到底在哪一步真的落盘」，它决定计时边界画在哪里；第二行的账是「字节搬到哪里」，它决定读一个键要碰多少数据；第三行的账是「旧数据什么时候能放手」，它决定零拷贝（不复制字节，直接交出指向原缓冲的引用）省下的复制会不会换成内存增长。任何一处想改设计，先看清自己动的是哪一笔账。

## 17.1 立项：先把边界、输入家族与不做什么写死 {#sec-cpp-rust.4.17.1}

**本节回答一个问题**：一个还没写一行代码的项目，能确定些什么？

::: preview 先抓住一件事

**立项阶段唯一值得产出的东西是「边界」，不是「进度」。**性能项目最常见的失败不是写不完，而是写完之后没人说得清这条结论适用于什么负载、什么机器、什么版本——于是它既不能被接受，也不能被拒绝，只能被忽略。

`tidekv` 在动手之前先写下四件事：操作集合、输入家族、不变量、不覆盖范围。前三件规定你要证明什么，第四件规定你不许声称什么。

:::

### 17.1.1 项目契约

::: def 定义 17.1.1 · 项目契约 project contract {#def-17.1.1}

一个性能项目的**契约**是四元组 $(O, F, I, X)$：$O$ 是操作集合（本项目的 `put`、`delete`、`get`、`scan_prefix`、`flush`、`compact_two`、`sync`）；$F$ 是输入家族（键长分布、值长分布、读写比、键空间大小）；$I$ 是必须始终成立的不变量；$X$ 是本结论明确不覆盖的范围。契约写在采集之前，采集之后不许修改 $F$ 与 $X$。
:::

这份契约的四个槽位分别对应主线的一步：$O$ 与 $I$ 保证 ①「活真的干了」，$F$ 保证 ②「这个数是什么」有一个固定的分母，$X$ 是 ④「守得住」的护栏。

::: def 定义 17.1.2 · 不变量 invariant {#def-17.1.2}

**不变量**是任何合法操作序列之后都必须成立、能被一个测试一次性证伪的命题。本项目有六条：已 `sync` 的写在**进程重启**后仍在（不是「掉电后仍在」——默认配置下预写日志只刷到内核，不做 `fsync`，见 17.8.2）；`get` 的结果与独立参考实现逐键相等（夹具里的 REF 是 `HashMap` 上的操作重放，与基线 A 的 `RwLock<BTreeMap>` 不是同一段代码）；删除对后续读不可见；段文件字节一旦写下不再修改；同一批键在压缩前后集合相同；被读者持有的快照在 epoch 推进到「所有活跃读者都越过退休纪元」之前不释放（不是引用计数归零，见 17.5）。

六条里有五条各有测试，**「段文件字节一旦写下不再修改」这条没有**（`segment_format.rs` 只测外部改动会被 CRC 拒掉）。
:::

一条不变量要配一个能触发它的测试。写不出测试的「不变量」只是愿望（[@def-17.1.2]）。

### 17.1.2 里程碑与出口条件

::: def 定义 17.1.3 · 出口条件 exit condition {#def-17.1.3}

每个里程碑的**出口条件**是「一组可执行的判据 + 判据的输出落盘位置」。`cargo test` 通过不是出口条件，「六条不变量各有至少一个测试，且原始输出保存在 `results/run-01/`」才是。
:::

| 里程碑 | 内容 | 出口条件 | 主要回看章 |
|:--|:--|:--|:--|
| M1 | 日志、内存表、段文件与恢复 | CRC 截断与损坏测试通过；重启后逐键等于参考值 | 2、3 |
| M2 | 只读路径与布隆过滤 | 无漏报测试；假阳率有实测计数 | 2、12 |
| M3 | 快照并发与 epoch 回收 | 读者持快照期间旧段不释放 | 7、11 |
| M4 | 有界准入（按请求取消未实现，见 17.6.2） | 饱和时返回明确错误而非排队到耗尽；另有 `CAP=64` 与 `CAP=4` 的实测对照 | 8、9 |
| M5 | 压缩子进程（重放幂等未实现，见 17.7.1 的定义 17.7.2） | 两路管道均排空；退出码非零时带出错误文本 | 10 |
| M6 | 代码生成证据 | MIR、LLVM IR、asm 落盘，热路径的判定有 grep 结果 | 4、6、13 |
| M7 | 配对基准与三态门禁 | CSV、`statistics.json`、`environment.txt` 齐全；**两格缺档**：源码指纹、主轮 `gate.json` 的预算出处（见 17.8.3 与 17.9） | 1、14 |

::: ex 例 17.1.1 · 给一份没有边界的立项挑缺项 {#ex-17.1.1}

一位同学交来的立项只有一句话：「做一个 Rust 写的 KV 引擎，比 `std` 的 `BTreeMap` 加锁快。」请指出它缺什么，并写出补齐后的四元组。

::: sol 解答

一句话里能挑出四处缺口。

① **操作集合没定。** 「KV 引擎」包含什么？只有点读写，还是含前缀扫描、范围删除、批量压缩？扫描路径和点读路径的瓶颈完全不同，把两者混在一个「快」里，等于没说话。

② **输入家族没定。** 键长、值长、读写比、键空间大小四项一个都没给。值长 8 字节与值长 4 KiB 时，段文件的收益机制不是同一个（[@def-1.2.2]）。

③ **基线没定。** 「`BTreeMap` 加锁」是进程内的一把 `RwLock`，还是别的库？两者在同机同输入下不保证算术语义相同，就不满足等价工作比较（[@def-1.6.1]）。

④ **不覆盖范围没定。** 不写这一条，结论会被读者自动外推到他们的生产负载上。

补齐后的四元组：$O$ = `put`/`delete`/`get`/`scan_prefix`/`flush`/`compact_two`；$F$ = 机制轮（17.4 的 `tide-mech`）取键 16 字节（8 序号 + 8 随机）、值 64 字节、每批 4096 个不同键，**只有写与删、没有读**（codec 臂只调 `encode_all`/`encode_all_dyn`；compaction 臂键为 `k{i:08}` 共 9 字节、20% 是删除）；主轮（17.8 的 `tide-bench`）是另一族：键长 14/15/17、值长 80–300 字节、键空间不超过两万个键；$I$ = 上面六条不变量；$X$ = 不覆盖值长超一页的记录、多进程共享同一份数据、非本机缓存层次下的尾延迟。

:::
:::

::: think 思考 · 边界是限制还是内容

把 $X$ 写长会让人觉得在给自己找退路。反过来想：如果不写 $X$，读者会把结论外推到哪里？外推一旦出事，损失的是结论的可信度，不是措辞的漂亮程度。判断一条结论有没有价值，看的正是它敢不敢把不适用的地方列出来（[@def-1.7.2]）。

:::

::: method 判定流程 · 立项评审五问

1. 操作集合是什么？有没有把「点读」和「扫描」混报成同一个数？
2. 输入家族的四项（键长、值长、读写比、键空间）写全了吗？
3. 每条不变量有没有对应的、能触发失败的测试？
4. 基线在输入、算术语义、可观察输出三个意义上都等价吗？
5. 不覆盖范围写了吗？读者最可能把它外推到哪里？

五问里有一问答不上，就先别开始写代码。

:::

### 17.1.3 明确不做什么

一个项目章最容易给人的错觉是「列了七节就要做七件事」。下面这六条是 `tidekv` **主动放弃**的范围。它们不是「以后再说」，是写进契约第 $X$ 格的边界（[@def-17.1.1]）：如果哪天做了其中一件，那是一份新结论，得重新走一遍四步主线。

| 不做什么 | 为什么不做 | 真要做，去看哪一章 |
|:--|:--|:--|
| 不做分层与 leveled 合并策略 | 一旦分层，写放大与读放大互相牵扯，基准的输入家族要整个重定 | 第 9 章（调度与配额）之外，本书没有覆盖 LSM 分层 |
| 不做多进程共享同一份段文件 | 需要外部锁服务或租约，跨进程一致性不是本项目的边界 | [10 章](../part3/ch10.md) 讲进程边界，但不给分布式锁 |
| 不用 `mmap` 代替一次读取 | 映射会把页缓存与缺页行为混进读路径，测到的就不再是「一次搬运多少字节」 | [12 章](../part3/ch12.md) 的零拷贝与 [2 章](../part1/ch02.md) 的搬运量 |
| 不做常驻压缩 worker 池 | 压缩在本项目是一次性任务；常驻池会引入排队与背压，那是另一套契约 | [10 章](../part3/ch10.md) 的持久 worker |
| 不做事务与隔离级别 | 只保证「一次读用一份不可变快照」，不保证跨多次读的可重复读 | 本书不涉及数据库事务语义 |
| 不接跨机器与跨版本比较 | 换机器换编译器，结论的适用范围要重写；本项目只在一台机器上采数 | [14 章](../part4/ch14.md) 的构建身份 |

**怎么判断一条「不做」写得对不对**：看它有没有对应的**失败场景**。上表第二行之所以成立，是因为「两个进程同时改同一份段列表」这件事在本项目里没有任何机制能挡住；如果硬做，读者会在 17.5 的快照之外看到一份不属于任何快照的修改——那时 ① 与 ④ 同时失守。

### 17.1.4 小结与常见错误

**小结。**①项目契约是四元组 $(O,F,I,X)$，写在采集之前（[@def-17.1.1]）。②不变量必须能被测试一次性证伪（[@def-17.1.2]）。③里程碑的出口条件是判据加落盘位置，不是「跑通了」（[@def-17.1.3]）。

::: errata 常见错误清单（17.1 节）

E-a **把「功能做完了」当成立项完成。**立项交付的是边界，功能只是其中一格。

E-b **一条不变量配零个测试。**写不出触发它的测试，说明它不是不变量，是愿望（[@def-17.1.2]）。

E-c **输入家族只写「随机数据」。**随机分布有无数种，不同分布下段文件的收益机制不同。

E-d **不覆盖范围留空，等被质疑时再补。**事后补的范围等于为这次结果临时改判定口径（[@def-1.7.2]）。

E-f **里程碑只有代码项，没有证据项。**没有 M7 的项目做不出可发布结论。

:::

## 17.2 记录与段文件布局：字节先算清楚 {#sec-cpp-rust.4.17.2}

**本节回答一个问题**：一条记录在磁盘上到底占多少字节，省字节的位置在哪里？

::: preview 先抓住一件事

**先算字节，再谈速度。**第 2 章给过布局的账（[@def-2.1.1] 是 size/align/offset；2.3.1 把八倍差距归到布局），但那一章**明说没有采 PMU**，所以「字段顺序影响缓存行（本机 `sysctl` 报告一条 128 字节）覆盖」在本书里是布局推断，不是实测结论。磁盘格式又不一样：磁盘格式不一样：段文件的字节一旦写下就不再改，它的布局决定的是**一次读要搬多少**，而不是**一个缓存行覆盖几个字段**。

`tidekv` 的段文件因此分成三区：数据区每条先放一个 17 字节条目头再放键与值，索引区把「键长、条目偏移」用固定宽度的小端整数单独摆放，页脚放魔数、版本号、条目数、两区偏移与整段校验和。

:::

### 17.2.1 三种布局放在同一张桌子上

::: def 定义 17.2.1 · 段文件三区间 segment layout {#def-17.2.1}

**数据区**按 key 字典序依次写入每条记录：先 17 字节的**条目头**（键长 4、值长 4、操作标记 1、序号 8），紧接着是键字节与值字节，中间不放别的元信息。**索引区**是一条等宽数组，第 $i$ 项只有两项：键长（4 字节）与这条记录在数据区的起始偏移（8 字节），共 12 字节——键长在这里复制了一份，为的是二分不必先读条目头。**页脚**放魔数 `TIDE1`、版本号、条目数、索引区起始偏移、布隆区起始偏移与长度、整段 CRC32，共 34 字节。
:::

索引区为什么与数据区分开：二分每步从索引项拿到（键长，偏移），再去数据区取那段**键**字节比较，**值字节全程不碰**。交错摆放时，为了比一个键就得把整条记录连 64 字节值一起读进来。这与第 2 章 AoS 与 SoA 的差别是同一件事，只是分母从「一条缓存行」换成了「一次文件读取」。

::: def 定义 17.2.2 · 墓碑与 niche {#def-17.2.2}

删除操作在内存表里写成「值为空」的条目。**墓碑**（tombstone）就是这条记录：它必须活到压缩，否则旧段里的值会重新被读到。本项目用一个 `Option` 承载它？不是——内存表里的墓碑是显式变体 `EntryKind::Delete`（`src/memtable.rs`），全仓没有 `NonZero` 类型。`Option<NonZeroU32>` 那类利用编译器为判别式留出的空闲比特位表达「没有值」的技巧叫 niche（[@def-2.2.1]，定义在第 2 章），这里只用来说明「省字节」确实可能，不能当本项目的实现读。

::: ex 例 17.2.1 · 算一条记录在段文件里占多少字节 {#ex-17.2.1}

这里用 17.4 机制轮那族参数：键长固定 16 字节、值长固定 64 字节。请算出：① 一条记录在数据区占多少字节；② 在索引区占多少；③ 一个装满 $2^{16}$ 条记录的段文件总字节数（不计布隆区与页脚）；④ 若把索引里重复的那份键长去掉、只留偏移，总数变成多少，省下的是什么、多出来的又是什么。

::: sol 解答

① 数据区每条 = 17 字节条目头 + 键 + 值 = $17 + 16 + 64 = 97$ 字节。

② 索引区每条 12 字节：键长 4 + 条目偏移 8（见 [@def-17.2.1]）。

③ 数据区 $97 \times 65536 = 6{,}356{,}992$ 字节；索引区 $12 \times 65536 = 786{,}432$ 字节；两区合计 $7{,}143{,}424$，加 34 字节页脚是 $7{,}143{,}458$（不计布隆区）。这是纸面算例：默认 64 KiB 的内存表阈值下，真实段远装不到 $2^{16}$ 条。

④ 若把索引里重复的那份键长去掉，只留偏移：索引每条 8 字节，省 $4 \times 65536 = 262{,}144$ 字节。代价是二分每步都要先读 17 字节条目头才知道键长——一次点读约 $\log_2 65536 = 16$ 步，等于拿 16 次额外访问换 256 KiB 磁盘。

结论反直觉：**索引瘦身更省磁盘字节，重复键长更省读取。**点读命中率不是 100% 时，把键长留在索引里在「一次读搬多少」上占优。段文件字节数是**静态可算**的，不属于需要采集的性能量；任何「省了 20% 空间」的说法要给算式或实测，不能靠印象（[@def-2.3.2]）。

:::
:::

::: ex 例 17.2.2 · 把布隆区的字节账和假阳率对上 {#ex-17.2.2}

段文件的布隆区用 8 bit 指纹（[@def-17.2.1]）。请回答三问：① 一个**不存在**于本段的键，被指纹判断成「可能在」的概率上界是多少，前提是什么；② 要把这个上界压到千分之一以下，指纹至少要几位；③ 这道题算出来的数，能不能当作本章的性能结论写进发布说明？

::: sol 解答

① 先给一个**会被实测推翻的答案**：一次探测里，非成员键的某个槽撞上同值指纹即误判，若 8 bit 指纹均匀分布，**单个槽**的误判上界是 $2^{-8} = 1/256 \approx 0.39\%$。但本项目每键 8 字节 = 64 bit，一个桶是 `BUCKET = 16` 字节，一次探测要**比较 16 个槽**（`src/bloom.rs`），并集上界是 $16 \times 2^{-8} = 1/16 = 6.25\%$。**把单槽上界当成整体假阳率，是这类算式最常见的越界。**

② 要求整体假阳率不超过千分之一，按 16 槽并集就是 $16 \times 2^{-f} \le 1/1000$，得 $f \ge \lceil \log_2 16000 \rceil = 14$。照 ① 里那个单槽答案只要 10 bit——**上界少算 4 bit，参数就跟着错**，代价是每键常驻从 64 bit（8 槽 × 8）涨到 112 bit，多 48 bit。本项目仍取 8 bit：0.76% 的误判只多付一次数据区比对，不付正确性代价。

③ **不能。**①②是**算式**，回答的是「设计上最坏能错多少」；发布说明要的是「这台机器上这批输入实际错了多少次」，那是一次计数，属于 M2 的出口条件（[@def-17.1.3]）。把算式当实测，正是第 1 章反复警告的那类越界：静态可推的量不需要采集，需要采集的量不能靠推（[@def-1.5.1]）。

**实测（`tests/bloom_contract.rs` 的未捕获输出，2026-10-30 归档在 `results/bloom-contract-2026-10-30.txt`）**：那条测试只断言「假阳率小于 5%」，下面是它打印的三行数。每键 8 字节、共 400,000 槽的过滤器，对 200,000 个从未插入的键探测，误判 1,525 次，经验假阳率 **0.762%（约 1/131）**——比单槽上界 1/256（0.39%）差约 1.95 倍，又落在修正后的两条线之间（单槽 1/256 与 16 槽并集 1/16 = 6.25%）。段级另一组 8,000 键、50,000 次不存在的探测，**0 次漏进来**；引擎侧 2,000 次「读不存在的键」有 1,989 次被当场挡掉（99.45%）。**漏报为零**在两组测试里都是硬断言：布隆说「不在」就一定不在，说「在」才需要去数据区核对（[@def-17.2.1]）。

:::

:::

::: think 思考 · 索引区为什么要定宽

定宽让第 $i$ 项的地址是 `base + 12 × i`，一次乘法就够，二分因此才成立。索引一旦变长（键长随键变化、偏移要变长编码），定宽寻址就没了，二分退化成顺序扫描——布隆的价值因此被削弱。这是「布局决定可达的算法」的一个具体例子（[@def-2.1.2]）。

:::

::: method 判定流程 · 磁盘格式的四步自查

1. 一格元信息占几字节，能不能用 niche 或位模式（用比特的形状而不是比特的值来表达信息）省掉？
2. 元信息与数据分开摆放，未命中路径少搬多少字节？
3. 一次读需要的定位是除法可得的，还是需要顺序扫描？
4. 校验和覆盖哪些字节？漏掉的字节就是损坏时读不出来的那部分。

:::

### 17.2.2 索引放在哪里：与 easy-fs 的一次对照

同一个「先查索引再取数据」的问题，文件系统的答案不一样：rCore 的 easy-fs 把索引**塞进磁盘数据块里**——`DiskInode` 28 个直接项满了走一级间接（一个 512 B 块装 512/4 = 128 个 `u32` 指针），再不够上二级间接。这里要分清「本层新增」与「累计上限」：直接项 14 KiB、一级间接再加 64 KiB，母本按累计 78 KiB 划线，超过才用二级间接，二级再加约 8 MiB。代价就藏在「索引块也是数据块」里：读间接索引要先多读一次索引块，那笔读和数据读一样要过块设备。

`tidekv` 反过来——索引集中在段末、定宽、一次读进内存，换来二分只读键不读值，付的是常驻内存。两条路各对各的场景：文件系统面对任意大小的文件，索引必须能长在磁盘上；本项目段的键数已知、索引区大小可算，所以能整区驻留。

这个对照给出可迁移的判据：**问「索引要装进多大内存」，如果答案不可控，索引就得能留在磁盘上分层**；如果可控，集中定宽摆放几乎总是更好，因为它把定位从「多次 I/O」换成「一次乘法加二分」。17.2.1 那道题里索引瘦身省 4 字节、却要多读一次条目头，是同一个道理的另一面。

### 17.2.3 小结与常见错误

**小结。**①段文件三区（数据、索引、页脚）的分工是「少搬字节」而不是「少占字节」（[@def-17.2.1]、[@ex-17.2.1]）。②墓碑必须活到压缩，判别位可用 niche 表达（[@def-17.2.2]）。③静态字节可以算，不需要采集；一旦写成百分比收益，就必须交代算式或实测。

::: errata 常见错误清单（17.2 节）

E-a **用「结构体字段顺序」的道理去改磁盘格式。**前者受缓存行覆盖支配，后者受单次读取字节支配（[@def-2.3.1]）。

E-b **为了省几个字节把索引改成变长，就宣称布局更好。**省下 4 字节/条，换来二分每一步都先回数据区读条目头。

E-b2 **索引变长却仍然写「支持二分」。**变长索引不能定址（[@def-17.2.1]）。

E-c **段文件写完就更新头部。**头一改，正在读的快照看到的就不是同一份文件了。

E-d **以为校验和覆盖了整个文件。**`crc32(&data[..f])` 覆盖数据区、索引区与布隆区，**页脚那 34 字节不在其中**；魔数、版本、条目数与两个偏移全靠 `open` 里的范围核对兜着，核对漏了就变成切片越界（对应第 3 章的边界检查）。

E-e **把删除记录直接抹掉。**旧段里的同键值会复活（[@def-17.2.2]）。

:::

::: method 即时自测 · 17.2

1. **记忆**：段文件三区各放什么？索引区每条为什么定宽？
2. **辨析**：「分区摆放总字节更大但读得更快」这两句里，哪一句需要实测支撑？
3. **应用**：键长改为 1–64 字节可变，索引区怎么改才仍然可二分？
4. **迁移**：给一份日志文件设计同样的三区划分，写出你的取舍。

::: sol 第 1 题答案

## 17.3 零拷贝读路径与 unsafe 担保 {#sec-cpp-rust.4.17.3}

**本节回答一个问题**：读路径想一次复制都不做，要担保什么、付出什么？

::: preview 先抓住一件事

第 12 章讲的**零拷贝**（copy-free，省掉「先把值复制到一个新缓冲再交给调用方」那一次复制）把这种返回方式叫切片视图（[@def-12.4.1]），把附带的代价叫生命周期级联（[@def-12.4.2]）。在本项目里形状很具体：段文件一次读进一块 `Vec<u8>`，`get` 直接返回指向它的切片。返回 `Vec<u8>` 每次都要分配和复制；返回切片则要借用与缓冲的寿命对上——对不上的那段只有 `unsafe` 能写，也只有把担保写进注释才算数。

:::

### 17.3.1 谁拥有那块缓冲

::: def 定义 17.3.1 · 段句柄 segment handle {#def-17.3.1}

`Segment` 结构持有的就是六样东西：`info`（段号、路径、条目数、字节数、键数）、整段字节 `data: Vec<u8>`、`index_off`、`bloom_off`、`bloom_len`，和解好码的 `bloom`。`open` 把文件一次 `read_to_end` 读进 `data` 之后**就把 `File` 丢了**——没有常驻文件描述符，也没有 `Arc<SegmentData>` 这种中间层。**句柄**指这个可复制的访问凭证：多个读者各持一份 `Arc<Segment>`，共用里面同一块 `data` 缓冲；段一旦写完就不再修改，析构随最后一个 `Arc` 释放。
:::

::: def 定义 17.3.2 · 读路径的安全不变量 safety invariant {#def-17.3.2}

要在 `get` 里返回 `&[u8]` 而不复制，必须同时成立三条：① 目标字节落在 `data` 那块缓冲的范围内，且范围由索引区给出而不是由调用方给出；② 该缓冲在返回切片的生命周期内不被修改、不被释放；③ 段文件不可变，即写入完成后没有任何路径能改变已映射的字节。三条里任何一条只能靠「大家都知道不会这么做」来保证，就是没有保证。
:::

三条各自对应一个具体的实现约束：① 由边界检查与页脚核对保证（条目偏移是 `u64` 的 8 字节，`open` 时核对四条范围关系（两个偏移不得越过页脚、布隆区必须紧贴页脚、`index_off + entries × 12 == bloom_off`），页脚之前还有长度、魔数、版本与 CRC 四道前置检查）；② 由 `Arc` 的引用计数与 17.5 的 epoch 回收共同保证；③ 由「段文件写完即只读」的流程保证——需要修改时新建一个段，而不是改旧的。

::: ex 例 17.3.1 · 把一段 SAFETY 注释写完整 {#ex-17.3.1}

下面是某人写的读路径，请补出 `// SAFETY:` 注释必须交代的内容，并指出哪个版本不能过评审：

```rust
fn value_at(data: &[u8], off: usize, len: usize) -> &[u8] {
    // SAFETY: ???
    unsafe { core::slice::from_raw_parts(data.as_ptr().add(off), len) }
}
```

::: sol 解答

先问一句：这个函数**需要** `unsafe` 吗？`data.get(off..off + len)` 就能返回 `Option<&[u8]>`，一次边界检查、无复制、无 `unsafe`。用 `from_raw_parts` 把边界检查省掉，省下的是一次比较，付出的是把越界读变成未定义行为。

若确实要用（例如为了躲开 `usize` 溢出这一条，改用 `checked_add` 后再判），注释至少要写清四件事：① `off + len` 已在调用方经 `checked_add` 核对且不超过 `data.len()`；② `data` 指向的缓冲在本切片存活期间不会被移动或释放（它由 `Arc<Segment>` 持有，引用计数非零）；③ 对齐与元素类型：这里是 `u8`，无对齐要求；④ 为什么这不会造成别名写冲突（该缓冲构造后只读）。

通不过评审的写法是「这里不会越界，因为格式保证偏移正确」——格式正确不是编译期或运行期的检查，段文件被截断或损坏时它立刻不成立（[@def-17.3.2]）。本章自己的判据在这里同样适用：能算出来的前提，就别只写在注释里（[@def-2.3.2]）。

:::
:::

::: think 思考 · 复制省掉了，钱付给谁

`get` 返回切片之后，调用方拿到的借用会把那块 `data` 缓冲的寿命钉住：只要切片还活着，那块缓冲就不能释放。这在 17.5 里会变成一个真实问题——读者迟迟不放手游标，旧段的回收就被推迟。零拷贝省掉的复制，换成了「回收延迟」这笔账——这正是第 12 章说生命周期会级联传播（[@def-12.4.2]）时给的现实版本。判断哪种划算要看值长与读延迟的分布，而不是看「零拷贝」这三个字。

:::

::: method 判定流程 · 能不能用 unsafe 省一次复制

1. 有没有安全写法能达到同样效果（返回切片、`get`、`split_at`）？有就用安全的。
2. 省下的到底是什么操作？数出来：一次分配？一次 memcpy？一次边界比较？
3. 破坏契约的后果是什么级别？越界读、别名写、双重释放都属于未定义行为，不能拿「实测没事」当证据。
4. 前提能不能用检查或类型固定下来？能固定的写进代码，剩下才写进注释。
5. 这个前提错了会怎样？给出一个能触发它的测试。

五个问题有一个答不上，这段 `unsafe` 就还不该合进主干。

:::

::: def 定义 17.3.3 · 只读缓冲的别名规则 aliasing rule {#def-17.3.3}

段缓冲在构造完成之后没有任何写路径，因此允许存在多个共享的只读引用（这就是返回切片的前提）。**一旦出现哪怕一处写入，多个引用立刻构成别名写冲突**，未定义行为不需要等到越界才发生。本项目因此把「不可变」做成流程约束：修改意味着新建一个段，而不是原地更新（[@def-17.3.2]）。
:::

### 17.3.2 「同一份数据两份缓冲」是同一类病

easy-fs 讲块缓存层时警告过：每个使用者各留一块缓冲区，某个块被改后另一份副本不会跟着变，后到的读看到的是**旧内容**；母本在「块缓存」一节给的判断是：块缓冲区里改过的内容如果对后续同一个块的读不可见，这事后果重且难查（`2fs-implementation` 篇）；「为什么难查」是本书补的——功能测试常只走单条路径，看不出问题在缓存一致性上。

它的解法是把缓冲区收归一处统一管理：每次要读写某个块，先问全局管理器这个块是不是已经在内存里、并且始终落在同一块固定缓冲上，这样同一段时间内对同一个块的多次访问才是同一份数据。

换成我们的语言：`tidekv` 的读路径返回切片，靠的是**同一件事的另一半**——不只「同一份数据只有一个缓冲区」，还要「缓冲区构造后没有写路径」（[@def-17.3.2]）。文件系统需要管理器是因为它**允许写**；我们只读，所以能用共享引用替代一层全局查表。一旦有人给段缓冲加了原地更新（比如就地写布隆位），这条替代立刻失效——正是 17.3.3 那条别名规则要挡的事。

判据可以带走：**只要「同一份数据可能存在两份可写副本」，就必须有一个地方回答「谁才是权威副本」**；没有这样的地方，正确性就取决于线程调度顺序，而那正是最难复现的一类缺陷。

### 17.3.3 小结与常见错误

**小结。**①零拷贝省下的是复制，代价是把缓冲寿命钉在借用上（[@def-17.3.1]）。②前提是缓冲真的没有写路径，一处写入就让多个引用构成别名冲突（[@def-17.3.3]）。③三条安全不变量缺一即未定义行为，且必须逐条对应实现约束（[@def-17.3.2]）。④`SAFETY` 注释要写「前提 + 谁保证 + 前提失效会怎样」，不能写「大家都不会这么做」（[@ex-17.3.1]）。

::: errata 常见错误清单（17.3 节）

E-a **为了躲一次边界检查上 `unsafe`。**边界检查不是复制，省它没有数量级收益（[@ex-17.3.1]）。

E-b **注释只写「调用者保证偏移合法」。**没写谁检查、怎么检查，等于没担保。

E-c **返回切片却忘记借用会把旧段钉住。**于是回收迟迟不能推进（对应 17.5）。

E-d **让段文件可原地更新。**「不可变」这条不变量一破，读者可能看到两次不同的字节。

E-e **用 `#[allow(clippy::undocumented_unsafe_blocks)]` 消警告。**把评审要看的句子藏起来，比不写更糟。

:::

::: method 即时自测 · 17.3

1. **记忆**：三条安全不变量分别是什么？各由谁保证？
2. **辨析**：返回 `&[u8]` 与返回 `Vec<u8>`，各自把开销付在哪里？
3. **应用**：把 `value_at` 改成安全版本，写出签名与错误类型。
4. **迁移**：你的项目里哪一处 `unsafe` 的担保其实可以由类型系统承担？

::: sol 第 1 题答案

①偏移与长度由索引区给出并做边界核对（构造时校验 + `get`）；②缓冲在借用存活期间不释放（`Arc` 引用计数与 epoch 回收）；③段字节写定后不改（新建段而非改旧段）。

::: sol 第 2 题答案

返回切片不复制但把缓冲寿命钉在借用上，回收被推迟；返回 `Vec` 每次分配加一次复制，借用关系干净，读者放手即放手。值小而读者多时前者好，值大而读者停留久时后者好。

::: sol 第 3 题答案

::: sol 第 4 题答案

常见的一处是「手工维护的长度必须等于切片长度」——换成 `&[u8]` 本身或定长数组引用即可由类型保证；另一处是「指针非空」——换成 `NonNull` 或 `Option<&T>`。

## 17.4 编解码：泛型还是 dyn，先问快在哪一层 {#sec-cpp-rust.4.17.4}

**本节回答一个问题**：段文件的编码与比较逻辑，用单态化（monomorphization，泛型为每种具体类型各生成一份代码）还是用 `dyn`（dyn dispatch，运行时查 vtable（那张函数指针表）决定调哪个实现）？

::: preview 先抓住一件事

第 5 章把这件事的一般答案讲清了：分派（[@def-5.1.1]）与单态化（[@def-5.1.3]）不是同层的东西，两者比的不是一句「谁快」，而是四个不同的层——分发开销、内联深度（把被调函数的身体搬进调用处，省掉一次跳转）、代码体积、指令缓存命中。**本项目把选择做成一个可以被追问的实验**：同一个热循环，一份走泛型单态化（`<C: Codec>` 的调用点），一份走 `&dyn Codec` 装箱对象，比较之前先定口径。

:::

### 17.4.1 把三种写法摆在同一个口径下

::: def 定义 17.4.1 · 编解码缝 codec seam {#def-17.4.1}

`trait Codec` 只有两个方法：`encode(&self, rec, out)` 把记录追加进输出缓冲、`cmp_key(&self, a, b) -> Ordering` 比较两个键。**这条缝目前只被分发基准 `tide-mech` 与 `tests/codec_contract.rs` 用到**：段文件写入在 `segment.rs` 里内联写字段，没经过 `Codec`，也没有 `decode`。所以本节讲的是「若读写都走这条缝，泛型与 `dyn` 的代价差在哪一层」，让缝接管全部读写是**还没做的事**。三种候选写法：① 具体类型直接实现，调用点用泛型参数（编译期定死，每处各生成一份）；② `Box<dyn Codec>`，一次间接加一张 vtable；③ 函数指针字段，`fn(...)` 类型仍可被内联但调用点不特化。
:::

::: def 定义 17.4.2 · 分发口径 dispatch measurement {#def-17.4.2}

比较分发代价时必须写清算的是哪一层：**每次调用的墙钟差**（要减掉共同开销）、**生成代码的字节数**（用编译产物量）、还是**热循环里的指令数**（用采样或计数）。三种口径给出的结论可以互相矛盾，所以「`dyn` 比泛型慢多少」这句话在没有口径时没有真值。
:::

::: ex 例 17.4.1 · 这个比较缺哪一样才算等价工作 {#ex-17.4.1}

有人这样比：泛型版在 `benches/codec.rs` 里跑，`dyn` 版在单元测试里跑一段固定 1000 条记录，得出「`dyn` 慢 34%」。请按第 1 章的等价工作定义（[@def-1.6.1]）挑出缺口。

::: sol 解答

四个缺口，任何一个都能让「34%」失效。

① **计时边界不同**：benchmark 夹具通常带预热与多次迭代，单元测试里的一次 1000 条包含首次访问的缺页与代码装载。两个数不是同一个量（[@def-1.2.2]）。

② **分母没说清**：34% 是每条记录的均值差，还是总时长差？如果两版处理的记录数不同，比值没有意义。

③ **没有同轮交替**：不同进程、不同时刻跑，机器热状态与页缓存状态都进了差值（[@def-1.4.1]）。

④ **没验输出可观察**：两版必须写出逐字节相同的段文件；如果编码结果本身不同，比的就不是「同一件工作的两种写法」，而是两件工作。

补齐的顺序是先定契约再采数：同一份输入、逐字节相同的输出、同轮交替、写清单位与分母。差值与区间怎么写，见 17.8。这个比较的实测在 17.4.2：按上面的协议跑完一轮，结论是「方向不可判定，但区间的最坏端在预算内」（[@def-1.7.3]）。

:::
:::

::: think 思考 · 什么时候该主动选 dyn

不是所有场景都该单态化。段文件种类会增多（定长、变长、压缩块），如果每次加一种都要重编译整个 crate 并且产物体积线性增长，那 `dyn` 换来的是构建时间与二进制体积。第 5 章的判据在这里落地成一句：**热路径固定且类型集合封闭，用泛型；类型集合随版本增长，用 `dyn` 并把它留在非热路径。**

:::

::: method 判定流程 · 选分发方式的三步

1. 这段代码每毫秒被执行几次？低于三次的，分发方式不影响结论。
2. 类型集合会随版本增长吗？会增长的，先把构建成本算进来再谈运行成本。
3. 要下结论时，先写口径（[@def-17.4.2]）：测每次调用、代码体积还是指令数？三选一并说明为什么另两个不算。

:::

::: def 定义 17.4.3 · 三条代价的计量单位 measurement units {#def-17.4.3}

选定分发方式要付三种账，**它们的单位互不相同，不能合并成一个「快慢」**：每次调用的墙钟差（ns/次，要减掉共同开销并给区间）、生成代码的体积（`.text` 段字节，静态可量，不需要计时）、热循环里的指令数（需要采样或计数权限，本机没有采集就写未采集）。写结论时先写单位，再写数字，最后写这条数字**不回答**什么。
:::

### 17.4.2 实测：这条缝到底贵多少

**本节回答一个问题**：在段文件这种「一条记录几十字节、一次写几千条」的形状上，`dyn` 与单态化的差别能不能被测出来？

实验在 `projects/tidekv` 里：新增 `src/codec.rs`（一个 `Codec` trait 与它的定长实现）与 `src/bin/tide-mech.rs`（基准）。两臂做同一件事——把 4096 条记录（键 16 字节、值 64 字节，与 17.1 的键值尺寸一致（读写比那一栏对它不适用——机制轮没有读阶段））编码进一个缓冲：A 臂走 `encode_all::<FixedCodec>`，编译期为 `FixedCodec` 生成一份代码；B 臂走 `encode_all_dyn(&dyn Codec)`。缓冲在计时之外分配，分配成本不混进被测量的那一步。

**先证明两臂做的是同一件工作。**两臂的输出缓冲必须逐字节相同，否则比的就是两件工作。基准在计时之前做这次比对，不一致就直接报错、不出数。本轮归档里记着：`bytes=364544, crc32=2b67ab81`，两臂一致。

**再看工作确实发生了。**在真实汇编里找分发方式（`results/run-02/codegen/codec-codegen.txt`）：单态化实例 `FixedCodec::encode` 的函数体有 104 行指令、**0 次间接调用**；`encode_all_dyn` 的函数体只有 24 行指令，里面有 **1 次 `blr x22`**——从 vtable 取函数指针再间接调用。两条路线的差别，在代码层就是这一次间接调用；这正是 17.4.1 那句「先问快在哪一层」的答案。

**然后才计时。**协议形状与主轮一致（21 轮 × 每轮 30 批、每臂预热不少于 500 ms），但种子与批量是这一轮自己的：种子 20261029、每批 4096 条记录（主轮是 20261028 与逐 case 分母），批内交替顺序按轮随机化；单位是 ns/记录（一次 op = 编码一条记录）；差值定义为 diff = B(`dyn`) − A(单态化)。

| 口径 | A 单态化 | B `dyn` | 配对差值 | 95% 区间 |
|:--|--:|--:|--:|:--|
| 每条记录的编码耗时（ns/记录） | 3.965 | 4.036 | +0.071 | [−0.054, +0.208] |

区间跨零，所以**方向不可判定**：这一轮的数据分不清 `dyn` 更慢还是更快。差值只有 +0.071 ns/记录，而样本标准差是 0.318 ns/记录——差本身比噪声还小，这正是 [@def-17.4.2] 说的口径问题：只报一个均值加一个百分比，等于把噪声讲成结论。

**判定用的是区间的最坏端，不是均值。**预算是 1 ns/记录，这是一条设计规则而不是测量结果：`dyn` 每条记录多花的代价一旦超过 1 ns，就说明热路径上多了一次不可预测的间接跳转，应当按 17.4 的规则把类型集合固定下来、把 `dyn` 移出热路径。区间上界 +0.208 ns/记录远低于它，因此本轮判**接受**。

**这条结论不覆盖三件事**，写在这里比事后被人外推好：① 记录更长时，编码本身的成本上升，分发那一点的相对占比会下降，本轮的数字不能外推；② 类型集合继续增长时，泛型路径要为每个实例生成一份代码，体积与指令缓存的账本轮**没有采集**；③ 指令数口径本轮**没有采集**，只有墙钟与代码生成两口径（[@def-17.4.3]）。

**结论句（按 1.8 的最小句式）**：

> 在这台机器（Apple M5 Pro、rustc 1.99.1、release 无 LTO、1 个 codegen unit）、键 16 字节 / 值 64 字节、每批 4096 条记录的输入家族下，`dyn` 相对单态化的每条记录额外编码成本**方向不可判定**（95% 区间 [−0.054, +0.208] ns/记录，跨零）；区间的最坏端低于 1 ns/记录 的预算，本轮判定为**接受**。本结论不覆盖更长记录、类型集合增长后的代码体积，也不覆盖指令数口径。

### 17.4.3 小结与常见错误

**小结。**①编解码缝有三种候选写法，差别在四个层上（[@def-17.4.1]）。②「快多少」必须先指定口径（[@def-17.4.2]）。③输入不同、计时边界不同、未同轮、输出未验，任一项都能让百分比作废（[@ex-17.4.1]）。④本项目的实测结论是「方向不可判定、但最坏端在预算内」（17.4.2），**不是**「`dyn` 与泛型一样快」——前者有区间，后者是另一句话。

::: errata 常见错误清单（17.4 节）

E-a **拿不同夹具的数字算百分比。**一边是预热后的循环，一边是首次执行（[@def-1.2.3]）。

E-b **说「`dyn` 慢 34%」而不说慢在哪一层。**口径缺失时这句话没有真值（[@def-17.4.2]）。

E-c **只比运行时间，忽略构建时间与产物体积。**对随版本增长的类型集合，那才是主要代价。

E-d **用不同输入比两版。**先证明输出逐字节相同，再谈快慢（[@def-1.6.1]）。

E-e **把 vtable 开销外推到所有调用点。**内联之后分发可能整体消失；没有看汇编就没有结论。

:::

## 17.5 快照、原子与 epoch 回收 {#sec-cpp-rust.4.17.5}

**本节回答一个问题**：读者拿着旧快照、写者换掉段列表时，旧段什么时候才允许释放？

::: preview 先抓住一件事

第 11 章讲过：无锁结构的难点不在「改得对」，在「旧数据什么时候能回收」。本项目恰好落在这一格——读请求要一次拿到「当前段集合」的一致视图，而写者每隔一阵就追加或合并段。若读者每次读都锁住列表，就退化成一把读写锁；若不锁，就必须回答：正在被读的那个列表节点，还能不能安全释放？

### 17.5.1 快照发布

::: def 定义 17.5.1 · 快照 snapshot {#def-17.5.1}

某一刻段集合的**不可变**视图：装进 `Heap<SegmentList>` 的一个 `Box<SegmentList>`（`SegmentList` 就是 `segments` 与 `frozen` 两个 `Vec`，没有额外的生成号字段）。写者构造好新的 `SegmentList` 后调 `heap.store(...)`，它内部是 `head.swap(Box::into_raw(next), SeqCst)`；读者 `pin()` 先记纪元再 `head.load(SeqCst)`。写者永不原地修改已发布的 `SegmentList`。
:::

::: def 定义 17.5.2 · 内存序的选择 memory order {#def-17.5.2}

对本项目的两处操作：换快照那一步要保证「新段文件的字节写在前、指针换在后」对其他线程可见——代码里 head 与 PINS 用的都是 `SeqCst`（`src/epoch.rs`），计数器则全是 `Relaxed`（`src/stats.rs`）：前者是先保正确、代价没有量化（见 17.5.2 的 E-c），后者是因为计数不参与任何可见性判断。
:::

::: ex 例 17.5.1 · 把段换掉之后立刻释放旧段 {#ex-17.5.1}

写者这样做：`let old = SWAP.swap(new, AcqRel); drop(old);`。请问会出什么事，怎么修？

::: sol 解答

还握着旧快照里那些段引用的线程，一旦 `drop` 就把它们变成悬垂引用——这是未定义行为，而且在低负载下几乎测不出来，跑到并发读多了才偶发崩溃。这正是第 11 章说的「难点在回收」。

修法有两层。**简单一层**：快照装进 `Arc`，`swap` 后旧值仍被读者的引用计数保护；不需要 epoch，代价是每次读快照付一对引用计数原子增减，热读路径上还会互相踢出伪共享（同缓存行互相作废）。**加一层**：换成 epoch——**本项目走这层**（`store` 收 `Box<SegmentList>`，不是 `Arc`）：读者 `pin()`/`release()`，写者挂旧快照进退休表，等所有 epoch 越过退休时刻再释放；另有测试可驱动 `advance()`，让「旧段不释放」不变量能由确定性测试验证（[@def-17.1.2]）。

选哪一层要看数据：若那对原子增减在配对实验里进不了差值，`Arc` 层就够，不必为了「无锁」加复杂度。这处的实测本节没有采集。

:::
:::

::: think 思考 · 「回收延迟」是不是问题

epoch 回收让旧段多活一阵，活多久取决于最慢的读者什么时候 `release()`。返回指向段字节的切片（17.3）会把引用钉到调用方用完；切片逃进长生命周期结构时，退休表就一直涨。这是设计里真实的一笔账：**零拷贝省下的复制，用退休表的增长偿还**。判据不是「有没有」，而是「退休表长度是否收敛」——它是一个可观测计数。

:::

::: method 判定流程 · 共享结构能不能安全释放

1. 有没有任何路径能让一个引用跨过释放点？有就不能直接 `drop`。
2. 保护用什么？引用计数、epoch（[@def-11.4.3]）、hazard pointer（用一组「我正在看这个」的公告槽阻止回收，[@def-11.4.2]）还是 RCU（读端几乎零成本，写端等宽限期）？
3. 保护加在读路径上的成本是多少？要不要用一个可数的指标把它测出来？
4. 延迟释放会不会无界增长？给出一个观测它的计数。
5. 这条安全性有没有一个确定性测试（能被 `advance()` 之类驱动）？只有压测就不算验证。

:::

### 17.5.2 小结与常见错误

**小结。**①快照不可变，发布用 `SeqCst` 换指针（降到 Release/Acquire 没有实测依据，[@def-17.5.1]、[@def-17.5.2]）。②回收保护可以是 `Arc` 或 epoch，选哪个由读路径成本决定（[@ex-17.5.1]）。③延迟释放必须有可观测计数，否则无法判断它会不会无界。

::: errata 常见错误清单（17.5 节）

E-a **换完快照就 `drop` 旧值。**跨释放点的引用是未定义行为（[@def-17.5.2]）。

E-b **原地修改已发布的快照。**读者可能看到改到一半的数组。

E-c **所有原子都用 `SeqCst`，却说不清为什么。**本项目确实这么写着（`epoch.rs` 的 head 与 PINS 用 `SeqCst`，只有 `Heap::drop` 取 head 用了 `Acquire`；`src/stats.rs` 的纯计数器是 `Relaxed`，但 `submitted`（`engine.rs:148`）与 `closed`（`engine.rs:151`）用 `AcqRel`/`Acquire`/`Release`——它们是同步边，不是纯计数）——这是**先保正确、代价没有量化**的现状：换 `Release/Acquire` 能不能测出差别，本轮没有采集，所以这条既是别人的错误清单，也是本项目挂在墙上的待办。

E-d **用 `Relaxed` 发布快照。**没有同步边，新段内容的写可能与指针的换序（[@def-17.5.2]）。

E-e **只有概率压测、没有确定性测试。**低概率崩溃不能靠「跑了十分钟没出事」排除。

E-f **退休表长度不监控。**回收延迟一旦无界，表现为内存缓慢上涨而不是崩溃。

:::

::: method 即时自测 · 17.5

1. **记忆**：本项目里哪两处用 `SeqCst`，哪两处用 Relaxed？为什么？
2. **辨析**：`Arc` 保护与 epoch 保护，各把成本付在哪条路径上？
3. **应用**：写出「读者持快照期间旧段不释放」这条测试的驱动步骤。
4. **迁移**：你的服务里有没有一个「看起来只是计数」却实际用作同步边的原子变量？

::: sol 第 1 题答案

快照发布（`head.swap` 与 `head.load` 都是 `SeqCst`，见 `src/epoch.rs`）；纯统计计数用 Relaxed，因为它不保护任何伴随数据。降到 Release/Acquire 能不能省，本轮没有采集。

:::

::: sol 第 2 题答案

`Arc` 把成本放在每次读（引用计数原子增减，且有缓存行争用）；epoch 把成本放在进出临界区与回收推进上，读端便宜但旧数据延迟释放。

:::

::: sol 第 3 题答案

① 线程 A `pin()` 并取快照 S；② 写者追加/合并新快照 S2 并把 S 挂进退休表；③ 断言 S 的段尚未释放（可用一个「已释放段」计数）；④ A 完成读并 `release()`；⑤ 测试线程显式 `advance()` 一次（读者已 `release()`，这一轮就该回收）；⑥ 断言释放计数 +1。

:::

::: sol 第 4 题答案

典型是一个「就绪标志」或「序号」：其他线程读到它之后会接着读一批数据。这类变量一旦承担发布角色，就必须配 Acquire/Release，Relaxed 会让数据可见顺序失守。

:::

## 17.6 有界准入与取消：背压挡在门口而不是排在队里 {#sec-cpp-rust.4.17.6}

**本节回答一个问题**：入口该不该拒？拒了之后调用方拿到的是什么？

::: preview 先抓住一件事

第 9 章的**背压**（下游处理不过来时把压力挡回入口）在本项目有**两道**有界闸门：写请求进单写线程前的准入（本节主角），以及 pin 槽位上限 `MAX_SLOTS = 512`（`src/epoch.rs`）。后者要读准：槽号只分配不回收，它封的是**一个进程里先后 pin 过的线程总数**，不是同时在读的线程数。超额时 `pin()` 返回 `None`，而 `None` 的三种去向都不记「槽位耗尽」这笔账：`get`/`get_with_seq`/`scan_prefix` 映射成 `TideError::Shutdown`（语义错，引擎没关），`Stats.get` 在 `pin()` 之前就加、超额的读照样计一格，`segments()` 与 `frozen_tables()` 回空集合与 0。本节只测前一道闸：上限一到就明确报错，重试、丢弃还是抛给用户由调用方定。

这一步的价值在结论层面：一旦允许无界排队，「写入吞吐」就失去含义——你测的是引擎的处理能力，还是进程的内存深度？

:::

### 17.6.1 准入的三态

::: def 定义 17.6.1 · 有界准入 bounded admission {#def-17.6.1}

写请求提交时先看引擎是否已关：已关直接 `TideError::Shutdown`。没关再看队列，若长度已达容量上限 `CAP`，立即返回 `AdmissionRejected`，**不阻塞、不入队、不重试**；队列未满则入队并返回受理。`CAP` 是实验契约的一部分，改它等于换实验。

本项目的「许可」就是队列里的一个槽位：`submit` 只看队列长度，没有另设的信号量计数器。归还点也**不是**「操作真正完成」那一刻——写线程每轮 `take_batch` 一次性取走至多 256 条（`let n = q.len().min(256); q.drain(..n)`），这批命令的槽位在这一刻就空出来了，而它们要到后面 `apply_write` 才被追加进预写日志。

于是任何瞬间「已受理但还没进日志」的请求可以超出 `CAP` 至多 256 条：未处理写请求的真实上界是 `CAP + 256`，不是 `CAP`。这是「以队列长度为唯一闸门」的固有形状——要把上限钉在 `CAP`，归还点就得落在写进日志之后，代价是逐条扣还。
:::

::: def 定义 17.6.2 · 取消与完成的分界 cancellation {#def-17.6.2}

一个请求被取消只意味着「提交方不再等它」，不意味着「它没有发生」。**本项目实际有什么**：`Tide::put` 是 fire-and-forget——拿到序号就返回，引擎没有按请求取消的 API，受理之后调用方拿不回它。

**已受理却没进日志，有三条路径，都不在常规关闭的主线上。**第一条藏在竞态里：`close()` 把 `Shutdown` 排在**队尾**，写线程按 FIFO 一批批取（一批至多 256 条），排在它前面的写**总会先落进日志**——常规关闭不丢写。被丢的只有另一个线程在「`Shutdown` 已入队、`closed` 未置真」这个窗口里 `submit` 成功的写：`shutdown()` 清队列那一行是 `Cmd::Write(_) | Cmd::Shutdown => {}`，既不写日志也不回报，而调用方早拿到序号了，无从知道自己被丢。

**第二条**更粗糙：写线程碰到致命错误就置两个标志 `return`，既不排空队列也不给队列里的 `Flush`/`Sync`/`Compact` 回 `Err(Shutdown)`，而那三个 API 正拿着 `recv()` 等回复——会挂住还是会报错，本轮**没有观察过**。**第三条**最安静：写线程 panic 时 `close()` 只写 `let _ = h.join()`（`engine.rs:431-434`），错误被吞掉，既不落盘也不报错，调用方照样拿到 `Ok`。

所以「尚未开始的请求归还许可、已在执行的跑完再上报已完成但被放弃」这两类计数，是**调用方要自己维护的账**，不是引擎已经替你做掉的事。把它写进定义，是因为少了这两格，任何「已处理数」都会算错。

这三条路径本轮**都没有测试覆盖**：`tests/admission.rs` 的三条测的是满即拒、控制命令同样有界、被拒不扰动序号；`tests/` 里没有「在关闭窗口里并发提交」或「写线程失败之后再 `sync()`」的用例。要拿它们做结论，得先补测试。
:::

::: ex 例 17.6.1 · 饱和时到底谁慢 {#ex-17.6.1}

压力测试里把 `CAP` 从 64 降到 4，观察到「端到端延迟下降，吞吐也下降」。这算不算优化成功？

::: sol 解答

两个方向都成立，所以不能只报其中一个数。吞吐下降是看得见的代价：一部分请求被拒了，它们不再贡献完成的次数——分母变了（[@def-1.2.2]）。延迟下降也是真的：排队的人少了，被受理的请求自然快。

要判断这笔交易划不划算，缺三样东西。① **拒绝率**：`AdmissionRejected` 占总请求的比例，它决定「延迟下降」是不是只发生在幸存者身上。② **口径统一**：吞吐与延迟必须来自同一批请求、同一段时间窗，不能一个数取自被拒前、一个取自被拒后。③ **业务侧的预算**：拒绝多少算不可接受（[@def-1.7.1]）。这三样齐了才能写成结论句；缺 ③ 的话，「延迟更低」是一句可以被业务当场驳回的话。

如果只测了「吞吐降 8%、p99 降 30%」却没报拒绝率，这份报告属于把取舍藏起来（1.7 节的判据）。例中的百分比是题面假设；`CAP=64` 与 `CAP=4` 的真实对照在 17.6.2，那份数据给出的答案与这里的直觉不完全一样。

:::
:::

::: think 思考 · 异步前端要不要自己做

`tidekv` 的核心不用任何异步运行时，但**写线程不是靠 `recv()` 收活的**：它在条件变量上等队列非空，一次 `drain` 至多 256 条，再逐条处理（[@def-17.6.1]）。

`recv()` 有两类角色（源码里是 5 个调用点）：调用方等引擎的回复是一类，写线程处理压缩任务时在自己的线程里等子进程输出是另一类（17.7 的 `spawn_compactor`）。要演示第 8、9 章的机制，可以另加一个极小的执行器：任务表 + `Waker` 唤醒 + 每轮公平扫描，前端把请求交给它，再走同一道准入。这样能直接观察到第 8 章那条：**取消一个任务不等于什么都没发生**——Future 走到哪个 `.await` 点，就已经把多少资源扣住了（[@def-17.6.2]）。两条路径（直写线程、经执行器）在同一输入家族下的差值属于 17.8 的实验，没有采集前不许写进结论。

:::

::: method 判定流程 · 入口该不该设上限

1. 下游有没有真实的处理速率上限？没有上限的说法说明还没读懂系统。
2. 队列无界时，最坏情况占多少内存？这个数能算出来吗？
3. 拒了之后调用方有没有可执行的下一步（重试/降级/上抛）？没有就等于是把错误码当装饰。
4. 拒绝率是不是一个被报告的指标？只报吞吐与延迟就是藏账。
5. 许可在哪一刻归还？整批取走时归还，上限就只约束「还在排的」，不约束「在途的」（[@def-17.6.1]）。本项目的答案是后者，所以内存上界按 `CAP + 256` 算。

:::

::: def 定义 17.6.3 · 三个必须分开的计数 three counters {#def-17.6.3}

一次写请求在本项目里会落进三个互斥的计数之一：**受理**（拿到许可）、**完成**（写进日志并推进序列）、**被拒**（`AdmissionRejected`）。引擎的计数器只拼得出两格：`Stats.put` 数提交尝试，`Stats.admission_reject` 只数满员那一种拒绝——`engine.rs:235` 的关闭拒绝计了 put 却不计 reject，所以两者之差只在没触发过关闭时才等于受理数；**「完成」没有对应计数器**（`Stats` 里没有 applied/written，落定与否只能问 `await_seq` 的内部水位）。第四格「已受理但提交方已放弃」同样不报，要调用方自己记（[@def-17.6.2]）。

任何吞吐数字都要说明分母是哪一格：「尝试数 ÷ 总时长」与「受理数 ÷ 总时长」在饱和时是两个数（[@def-1.2.2]），17.6.2 就是拿这两个分母各算一遍同一把墙钟；「完成」那一格没有计数器，当不了分母。
:::

### 17.6.2 实测：门口调小，改变的是谁被拒

**本节回答一个问题**：把 `admission_capacity` 从 64 调到 4，同一阵突发进来，到底哪一笔账变了？

夹具是 `tide-admit`（`projects/tidekv/src/bin/tide-admit.rs`）。每批把 240 条值长 64 KiB 的 `put` 用单线程连发到底，然后 `sync` 等已受理的全部落定，墙钟只记这一段。两臂吃**同一份由种子决定的操作序列**，代码路径只差 `admission_capacity`——这是单变量对照，不是两个引擎。`memtable_flush_bytes=262144`、`durable=false`，种子 20261030，21 轮 × 每轮 20 批，每臂预热不少于 300 ms，每轮内 A/B 先后由掷硬币决定。

① 这一步先立住：**每臂的最终状态必须等于「把本臂真正受理的那些操作在 `BTreeMap` 里回放」的结果**，且 `受理 + 被拒 = 尝试` 必须与引擎计数器对上；对不上就直接失败，不出数。本轮归档：A 臂受理 130、被拒 110，状态摘要 `eb67d1b3ba7cfa53`；B 臂受理 8、被拒 232，摘要 `ad8e6885296eed0f`，两臂都记 MATCH。**注意这是计时前每臂各跑一次的单批样本**，A 臂那一批的拒绝率 0.458 不等于下表的 0.6858（后者是 420 批的均值，单批受理范围 64–131，130 落在上沿）。1,680 行原始记录（840 个真实批次，每批因两条口径各写一行）全部由 `verify_admit_csv.py` 从 `wall_ns` 与各自分母重算过一遍（`results/run-03/recompute.txt`）。

| 口径 | A（CAP=64） | B（CAP=4） | 配对差值 B−A | 95% 区间 |
|:--|--:|--:|--:|:--|
| 每批受理数（占 240 条） | 75.40（范围 64–131） | 8.07（范围 4–11） | — | — |
| 拒绝率 | 0.6858 | 0.9664 | +0.2805 | — |
| 每批墙钟 | 185.86 ms | 19.90 ms | −165.96 ms | — |
| ns / 尝试 | 774,433.8 | 82,915.5 | **−691,518.3**（sd 是 21 个配对轮均值的样本标准差，不是逐批的） | [−741,468.5, −652,422.3] |
| ns / 受理 | 2,456,036.2 | 2,470,043.5 | **+14,007.4**（同上口径） | [−105,221.5, +132,036.5] |

读法要倒过来看。**每尝试成本降了 9.3 倍**，这个数是真的，可它几乎什么都不是：B 臂每批只做了 8.07 次写，A 臂做了 75.40 次——分母里那约 232 个被拒的请求（240 − 8.07）根本没进引擎。**换到受理分母上，两臂落到同一个量级，本轮分不出谁更贵**：2.456 ms 与 2.470 ms 每受理操作，差值 +14 µs，95% 区间跨零（约 −105 µs 到 +132 µs）。按项目规则 `U ≤ B` 接受、`L > B` 拒绝、其余证据不足，预算 B = 5,000 ns/操作，这一格判**证据不足**：本轮不能宣称浅门口让被受理的写变贵或变便宜。

机制链落在段落盘上。每批 `flush` 次数 A 均值 18.49、B 均值 1.98；每次刷盘多少时间要**先说除法口径**：聚合口径（Σ墙钟 ÷ Σ次数）得 A 10,050.6 / B 10,045.5 µs，差 0.05%；逐批比值再平均得 A 10,013.9 / B 10,054.3 µs，方向反过来、差 0.40%。本节用前者——B 臂每批只约 2 次，逐批除法方差极大。



每次刷盘平均摊到几条记录？阈值 256 KiB、记录值长 64 KiB，看着该是恰好 4 条，实算是 **4.08 条**（两臂各自的批均值相除：75.3976 ÷ 18.4929 与 8.0738 ÷ 1.9810；不是逐批相除再平均，两种口径在 18 与 2 这样的小分母上会分岔）。离开 4 条有两个原因：**键重复覆盖**让 memtable 字节不增长；**批末不足阈值的余量从不落段**（夹具批末只 `sync`）。用 4.08 除 10.05 ms 得 2.46 ms，与每受理那一格的两个数同一量级；按 4 条整算是 2.51 ms，差 2%。

也就是说：**「每受理成本」两臂分不出差别，与「它由 `memtable_flush_bytes` 决定、跟门口那道上限无关」这个解释相符**——但这条解释没有独立佐证，只是没被推翻。要说清性质：`Stats.flush` 只数次数不带时长，「每次刷盘 10.05 ms」是墙钟 ÷ 次数的**归算量**，不是独立佐证；分段耗时**没有采集**。

要紧的是口径本身会翻方向：表里的每受理 2,456,036.2 / 2,470,043.5 是**逐批比值再平均**，改用 Σ墙钟 ÷ Σ受理数得 2,465,119.0 / 2,464,724.3，于是 B−A 从 +14,007 ns 变成 −395 ns。同一个「每受理成本」，两种算法方向相反——这才是判「证据不足」的真正理由。上限改变的只有谁被挡在门外——拒绝率从 0.686 抬到 0.966。（表里那格 +0.2805 是按 840 批逐条重算的，不是拿两列已舍入的数相减——那样会得到 0.2806。）

预算 5,000 ns/操作 不是从结果里挑出来的：一条 64 KiB 记录的 WAL 追加量级是 65536 B ÷ 1 GB/s ≈ 65.5 µs，其中 1 GB/s 是按顺序写设备取的**量级假设，本机没测过**，换设备要重算。5 µs 不到它的 8%，也约为实测每受理成本（2,456 与 2,470 µs）的 0.2%——低于这个量的差值不足以改变「CAP 该设多大」。同一预算换到尝试口径判定是**接受**，但它只说明「浅门口没让每次提交尝试变贵」，不等于浅门口更好——两臂干的活不同（17.8.2 把两条判定并排，就是防止读成同一句话）。

**两条没测的，别混进结论。**其一，端到端每请求延迟：本夹具只在批末设**一个排空点**（`sync` 重试到成功为止，重试有意计进墙钟），观察不到每条请求各自的完成时刻，所以 17.6.1 例面里「p99 降 30%」那类话本轮**没有采集**，要测它得逐请求记提交与完成两个时间戳。其二，按请求取消：引擎根本没有这条 API（[@def-17.6.2]）；而「已受理却没进日志」那三条路径（竞态窗口、致命错误提前 `return`、写线程 panic 被 `close()` 吞掉）都没有测试覆盖。

**结论句（按 1.8 的最小句式）**：

> 在这台机器、每批 240 条 64 KiB 值连发、`memtable_flush_bytes=262144`、`durable=false` 的突发夹具下，把准入上限从 64 调到 4 使拒绝率从 0.686 升到 0.966；每尝试成本从 774 µs 降到 83 µs，但同一墙钟换成每受理口径后两臂相同（2.456 ms 与 2.470 ms，差值 +14 µs，95% 区间跨零），判**证据不足**。本结论不覆盖每请求端到端延迟，也不覆盖按请求取消。

### 17.6.3 小结与常见错误

**小结。**①准入只有一条路：满即拒，不阻塞不入队（[@def-17.6.1]）。②引擎没有按请求取消：常规 `close()` 并不丢排队中的写，只有竞态窗口里的提交、致命错误提前 `return`、写线程 panic 这三条会（[@def-17.6.2]）。所以「已受理」与「已进日志」是两格账，取消语义要调用方自己记。③吞吐与延迟同时变化时，必须报拒绝率并交代分母（[@ex-17.6.1]）——17.6.2 里同一把墙钟换个分母，就给出 9.3 倍与 0.6% 两种完全不同的说法。

::: errata 常见错误清单（17.6 节）

E-a **用无界队列做「高吞吐」实验。**测到的是内存深度，不是处理能力。

E-b **把被拒请求从分母里抹掉。**「处理过的请求平均延迟」与「请求平均延迟」是两个量（[@def-1.2.2]）。

E-c **取消即认为没发生。**已完成但被放弃的操作若参与副作用，会做出两遍。

E-d **把 `CAP` 当成在途请求的内存上界。**整批 `drain` 时槽位已归还、日志未写，真正压制不住的那一段是至多 256 条在途（[@def-17.6.1]）。按 `CAP` 报上界就是低估，饱和时才看出来。

E-e **只报延迟改善。**与只报吞吐改善是同一种毛病。

:::

## 17.7 压缩子进程：管道会满，重试会做两遍 {#sec-cpp-rust.4.17.7}

**本节回答一个问题**：把压缩放进子进程，会多出哪些坑？

::: preview 先抓住一件事

第 10 章讲过进程边界的三件麻烦：**管道会满**、**输出要两路同时排空**、**失败后重试可能把同一件事做两遍**。本项目把段合并（两个旧段 → 一个新段）交给子进程，理由不是「更快」，而是合并的内存峰值不该算进主进程的资源边界——这是一次真实的取舍，不是一次优化。

:::

### 17.7.1 双路排空与退出码

::: def 定义 17.7.1 · 双路排空 dual drain {#def-17.7.1}

子进程的 stdout 与 stderr 必须**同时**被读走。只等 `wait` 之后再读，子进程可能在写满其中一路管道后阻塞。容量这个数字要分开说：`src/ipc.rs` 的注释按 **64 KB** 推理（注释原文就是这么写的单位），但注释只给了数字，没说是哪个系统的默认值；正文也不把它当某个系统的默认值来引。**本机 macOS 的实际管道容量本轮没有采集**，所以 64 KiB 只能当推理前提，不能当测到的数。第 10 章给的也只是「输出量远大于可用缓冲」的停滞重现测试，同样不给常数，父进程在等它退出，它在等父进程读——这就是第 10 章说的背压等待回路（[@def-10.5.1]）。

本项目的做法：stdin、stdout、stderr **三路各起一个独立线程**（`src/ipc.rs` 的 `spawn_compactor`）——stdin 线程写完并关闭，两个输出线程各自 `read_to_string` 到 EOF 后把内容经 channel 送回；真正「同时排空」的是那两路输出，父线程先 join stdin 线程，再收两个输出线程的结果并 join 它们，最后才 `child.wait()`。注意父线程 `recv()` 的是线程的结果，不是管道的字节，所以「同时」这件事是那两个线程在做，`wait` 只是最后一步。
:::

::: def 定义 17.7.2 · 幂等与重放 idempotence {#def-17.7.2}

同一个任务重放两次，结果应当与重放一次相同。要满足这条缺不了两件事：输出先写临时名、`fsync` 后原子重命名；以及**任务标识由输入段的生成号集合决定，而不是提交时刻**——同名段已存在就视为已完成，不再写第二份。

**本项目的现状是：临时名这条路走通了，存在性检查和由输入决定的任务标识都没有，必须说清楚。**`write_segment` 确实是「临时名 → `sync_all` → `rename`」，但重命名之前没有任何存在性检查，而 POSIX `rename` 遇到同名文件是**静默覆盖**，不会报错；输出段名取当前段列表里的最大号加一（`do_compact` 里的 `max().unwrap_or(0) + 1`），也不是输入段生成号的函数。`Stats` 的计数器里没有「重放收敛」这一格。

所以按上面两条衡量，本项目**没有识别重放的机制**：段名由当前最大号加一，发布前也不检查目标。重放同一批输入的后果——多一个重复段、多一个内容重叠的段，还是被 `rename` 悄悄覆盖——取决于它发生在活进程里还是重启之后；这条路径**没有测试覆盖，也没观察过**。收口改动很小：段名由输入段号集合导出，重命名前先看目标在不在，并把「跳过」单独计数。
:::

::: ex 例 17.7.1 · 压缩失败后直接重试 {#ex-17.7.1}

父进程发现子进程退出码非零，于是立刻重发同一个合并任务。请分析可能出现什么问题。

::: sol 解答

三种情况要分开看。①子进程还没开始写就失败：重试无害。②子进程写了半个临时文件后失败：如果重试用同一个临时名，会覆盖残留，正常；如果每次用不同的随机名，残留会累积成磁盘垃圾——这类垃圾不影响正确性，但会一直吃空间。

③子进程已经写完并最终重命名成功，但父进程没读到结果（比如管道里丢消息或自身崩溃后重启）：此时「合并」其实已经发生。若重试时不做存在性检查，会再生成一个相同内容的段，段列表里出现重复；后续读要跨两个相同段查找，语义仍正确但空间翻倍。**幂等的关键就在 ③**：靠输入段生成号集合定任务标识，并在写之前检查同名段是否已存在（[@def-17.7.2]）。

本项目两件都没做，父进程无从判断这批输入是否已经合过。`tests/compaction.rs` 的四条测的是不足两段时返回 `None`、合并后语义正确、随机操作下的等价性、重启后新段仍在，**没有覆盖「同一批输入合并两次」**，因此这条路径的实际后果本轮没有观察过。

还有一个容易漏的：退出码非零时必须把 stderr 的内容带进错误里。只报「压缩失败」的日志，三个月后没人知道那次失败是哪一路管道满了——本项目的 `CompactorError` 就是把 stderr 原文一并带出（`src/ipc.rs`），带多少要受第 10 章那条有限保留约束（[@def-10.5.2]）；失败之后要不要接受「已经做了一半」的结果，判法见第 10 章对超时三件事的分离（[@def-10.7.1]）。

:::
:::

::: think 思考 · 进程边界换来了什么

放进子进程之后，合并那份峰值内存**不再算在主进程的账上**——这是记账边界变了，不是「内存变少了」：两臂的峰值 RSS 本轮**没有采集**，「低了多少」说不出来。

代价倒是三笔实账：进程创建的时间、数据要靠文件系统而不是内存共享、失败路径要重做一遍错误处理。第 10 章没有替我们下过结论，这是本项目自己的账：**跨进程不是免费的隔离，是一次用复杂度换资源边界的交易**。这笔交易在本项目里划不划算，取决于合并的峰值内存是否真的会挤掉读者——要回答它得按 17.8 的协议补一轮**两臂峰值 RSS** 的采集，本轮没有。

:::

::: method 判定流程 · 子进程任务的四条底线

1. 两路输出一条都不许留到 `wait` 之后（[@def-17.7.1]）。
2. 失败信息带上 stderr 内容与任务标识。
3. 输出走「临时名 → 同步 → 原子重命名」，重试前先看目标在不在（[@def-17.7.2]）。本项目只有前半条成立，后半条是待补的缺口。
4. 描述符别漏：每起一个子进程就核对打开的 fd 数量是否回到基线。

:::

::: def 定义 17.7.3 · 原子发布 atomic publish {#def-17.7.3}

新段进入快照之前要走完三步：写临时名 → `fsync` 临时名 → 原子重命名到最终名。**只有走完第三步的文件才允许出现在任何快照里。**

第三步不会因为「目标已存在」而失败：POSIX `rename` 遇到同名目标照样成功，把旧文件换掉。所以「这个任务其实已经做过」这件事不能靠重命名的返回值发现，只能在重命名之前自己查一次目标；查到已存在不是错误，而是幂等收敛的信号，要单独计数（[@def-17.7.2]）。本项目缺的正是这次查询。
:::

### 17.7.2 实测：子进程这条路的额外代价

**本节回答一个问题**：把合并放进子进程，除了换来内存峰值的隔离，还多付了多少墙钟？

协议与 17.4.2 同源：同一对输入段（各 4096 条记录，新段含 20% 墓碑），A 臂在进程内做「读段 → 归并 → 写段」，B 臂把同样的三步交给 `tide-compactor` 子进程，走 17.7.1 那套 ipc 协议。**等价工作由输出文件逐字节相同来保证**：两臂写出的段文件必须一模一样，不一致就不出数。本轮归档记着：`bytes=401770, entries=4096, crc32=7241b72e`。

计时口径：一次 op = 一次两段合并，单位 ns/次；种子 20261029，21 轮 × 每轮 30 批，每臂预热不少于 500 ms；差值定义为 diff = B(子进程) − A(进程内)。**两臂都不走引擎的 `compact_two()`**：夹具直接调 `ipc::spawn_compactor`（A 臂在进程内做同样三步），所以这里量到的是「合并这三步」的代价，不含 `Cmd::Compact` 排队与父线程 `recv()` 那段往返；夹具还传 `drop_tombstones=false`，而引擎的 `do_compact` 固定传 `true`。这两处差异决定了下面那个数不能当成「引擎里一次 `compact_two()` 的开销」。

| 口径 | A 进程内 | B 子进程 | 配对差值 | 95% 区间 |
|:--|--:|--:|--:|:--|
| 一次两段合并（ns/次） | 7,696,326（7.70 ms） | 9,171,896（9.17 ms） | +1,475,570 | [+1,366,636, +1,586,757] |

区间完全在零以上，方向清楚：**子进程这条路每次合并多付约 1.48 ms**（95% 区间 1.37–1.59 ms），比值 1.19。这笔钱按代码形状推断大概花在进程创建、三路管道的往返与父子调度上——**构成没有采集**，本夹具每批只有一个 `value_ns_per_op`，没有分项计数器也没有分段计时；两臂各写一个文件（A 写 `merged-inproc.tide`，B 的子进程写 `merged-subproc.tide`），被证明的是**两者内容逐字节相同**；写段的 `sync_all` 两边都有，所以那部分共同成本被抵消，剩下的是隔离本身的价钱。



预算 B = 10 ms/次要单独交代，因为它不是从测量里长出来的。要分清哪一部分有同期出处、哪一部分是事后重述。

**数值**有同期物证：`gate-compaction.json` 与采集同时落盘，里面就写着 `budget_B=10000000.0`。但「这条预算在采集前就被这样理解」没有物证——`run.sh` 已改过，改前只剩归档里那句 `budget_note`。**含义**也没有：那份归档的 `budget_note` 给的是另一条依据。今天这条解释——「多付的部分不该超过一次进程内合并的量级，向上取整成 10 ms」——是 2026-10-30 重写时给出的重述，不能当成采集时就存在的理由。能当场核对的只有那句稳健性论证：区间上界 1.59 ms 小于 A 臂自己的 7.70 ms。

**这条契约的出处不是代码。**本项目的合并没有后台调度器：`do_compact` 的唯一调用点是写线程处理 `Cmd::Compact` 那个分支，对外只有显式的 `Tide::compact_two()`，整个仓库里没有一个压缩定时器。归档里 `gate-compaction.json` 的 `budget_note` 曾写成「后台每 100 ms 触发一次，所以单次合并最多占十分之一」，那句话在这份代码里没有对应实现；归档文件保持原样，更正记录在同目录的 `CORRECTION.md`，以正文为准。

判定对 B 取多少并不敏感。门禁比的是**区间上界**与预算（规则 `U ≤ B`），上界 1.59 ms 既低于这里的 10 ms，也低于更严的那条线——一次进程内合并自身的 7.70 ms。把契约收到后者仍然判**接受**，所以这条「接受」不是靠放宽预算拿到的。

**这条结论只对当前形状有效。**每段 4096 条记录时一次合并要 7.70 ms；段更多、每段更大时这个数会涨。子进程那 1.48 ms 里有多少是固定开销（进程创建）、多少随数据量变化，本轮**没有采集**——要做单变量对照，得把输入段大小改一档、其余不动，再跑一轮——那是新的一轮实验，不是现有归档能重算出来的。

**结论句（按 1.8 的最小句式）**：

> 在这台机器、每段 4096 条记录、新段含 20% 墓碑的输入下，走子进程合并比进程内合并每次多付 1.48 ms（95% 区间 [1.37, 1.59] ms），在 10 ms/次 的预算内，判定为**接受**。本结论不覆盖更大规模的段，也不区分「固定开销」与「随数据量增长的部分」。

### 17.7.3 小结与常见错误

**小结。**①两路管道必须同时排空，否则是结构性死锁（[@def-17.7.1]）。②重试的安全前提是幂等：任务标识要来自输入而不是时刻——本项目的标识来自「当前最大号加一」，所以这条前提还没满足（[@def-17.7.2]）。③跨进程换的是资源边界，付的是复杂度与失败路径。

::: errata 常见错误清单（17.7 节）

E-a **`wait` 之后才读 stdout。**子进程写满管道即阻塞（[@def-17.7.1]）。

E-b **只排空 stdout，不管 stderr。**错误输出多时同样死锁，且死在报错的路上。

E-c **用「现在」而不是「输入」给任务命名。**同一批输入两次提交会生成两个内容重叠的段（[@def-17.7.2]）。本项目的输出段名是当前最大号加一，正是这一条的实例。

E-d **直接往最终文件名写。**中途失败会留下半个「合法」段，而校验和可能照样自洽——CRC 只证明文件内部一致，不证明它是这次想要的内容。

E-e **失败日志只写「失败」。**没有 stderr 内容、没有任务标识，无法复核。

:::

::: method 即时自测 · 17.7

1. **记忆**：双路排空为什么要「同时」？
2. **辨析**：原子重命名解决了什么，没解决什么？
3. **应用**：写出「子进程已成功但父进程没收到」这条路径的检测方法。
4. **迁移**：你现有的任务队列里，哪一类任务的重试其实不幂等？

::: sol 第 1 题答案

任一路不被读走都会让子进程在那一路写满时阻塞，父进程若在 `wait`，两边互等成死锁。

:::

::: sol 第 2 题答案

解决了「半个文件被当成合法段」；没解决「重复段」。残留的 `.tmp` 也不会自己堆积——本项目的临时名由最终名派生，重试是覆盖同一份，要堆积得改用随机临时名；而仓库里没有清理 `.tmp` 的代码，所以准确说法是「留下一个永不回收的固定残留」。

:::

::: sol 第 3 题答案

启动时按输入段生成号集合推导目标段名并检查是否存在；存在则直接把它接进快照，并把这次标记为「重放收敛」计数——计数非零就是这条路径真实发生过的证据。

:::

::: sol 第 4 题答案

凡是「先扣款再发货」或「写入外部系统」的任务，重试都可能做两遍；解决方式是带幂等键的去重，而不是重试次数退避。

:::

## 17.8 实验、三态门禁与证据包 {#sec-cpp-rust.4.17.8}

**本节回答一个问题**：从原始 CSV 到「可发布的一句话」，中间缺哪几步？

::: preview 先抓住一件事

前七节都在造一个能跑的东西；这一节决定它能不能成为一个结论。做法完全沿用第 1 章：基线与候选同一份输入、算术语义相同、输出可观察、有独立参考值；同轮交替；差值配对；bootstrap 区间；三态判定；证据落盘。**这一节没有新工具，只有纪律**——最容易在「功能刚做完、很想宣称成功」那一刻被丢掉的部分。

:::

### 17.8.1 实验契约

::: def 定义 17.8.1 · 基线与候选 baseline and candidate {#def-17.8.1}

基线 A 是进程内一把 `RwLock` 保护的有序表，直接读写；候选 B 是 `tidekv` 引擎。等价性由三个条件保证：同一份输入序列（同键值样本、同顺序）、同一套算术语义、结果可逐键比对并与一份独立参考值（第三段朴素实现算出）对照。口径要说准：`put` 是 fire-and-forget，B 臂只在每 300 次操作与批末 `sync`，所以三方对齐证明的是**批末静止点之后**的最终状态，不是逐操作的写后读可见（那需要 `await_seq`）。
:::

::: def 定义 17.8.2 · 批生命周期实验 batch-lifecycle run {#def-17.8.2}

候选 B 的一批不是一个纯内存操作：一批写入包含日志追加、内存表插入，并可能触发一次段落盘。计时边界必须把这一批里发生的所有副作用都算进去，**不许在计时器内 `if` 掉 flush**——第 1 章 1.2 节那条纪律在这里最容易违反，因为「跳过 flush」能让数字好看很多。
:::

::: ex 例 17.8.1 · 把差值写成结论 {#ex-17.8.1}

现在你有 21 轮配对数据、`analyze.py` 输出的差值均值与 95% bootstrap 区间，以及事先写下的预算 $B$。请给出三态判定的完整结论句该怎么写。

::: sol 解答

先跑判定，不解释：区间下界 $L > B$ 拒绝，上界 $U \le B$ 接受，其余证据不足（[@def-1.7.2]）。

第 14 章的门禁也用三种退出状态表达结论，但**它的第三种是「证据不可比」，不是「证据不足」**（[@def-14.5.3]）——本章搬进自己仓库的是「三态要落盘成机器可读的判定」这条做法，不是它的编码表。但要说实话：本项目的 `gate.py` 只把三态写进 `gate.json`，退出码恒为 0（脚本末尾 `return 0`）——它是**给人读的账**，不会自动挡住合入，要阻断得由调用方读 `counts`。

三句话对应三种下一步

结论句的骨架，与[主干线上那个缩小版](../mainline.md#mainline-spine)完全一致：机器与构建 + 输入家族 + 两个量各是多少、单位与分母 + 差值与区间 + 方向判定 + 不覆盖范围。六个槽位少任何一个，评审都会追问到那里。

这一句里最难写的是最后一槽。`tidekv` 明确不覆盖：值长接近页大小的记录、多个进程共享同一份段文件的场景、键长超过格式常量的输入、以及任何非本机的缓存层次与尾延迟。把这些写出来不是谦虚，是让别人能判断这条结论在他的负载上适不适用。

:::

::: def 定义 17.8.3 · 证据包目录 evidence pack {#def-17.8.3}

一个目录，别人只凭它就能复算出同样的表。该有的格子是这些：`environment.txt` 与源码指纹合起来是第 14 章说的构建身份（[@def-14.1.1]）——机器、系统、工具链版本、缓存行与核数，外加被编译代码的哈希清单；原始 CSV（逐轮逐 case 的批均值与逐批原始值，列名 `round`、`arm_order`、`arm`、`value_ns_per_op`）；分析脚本；摘要 JSON（差值、区间、种子）；门禁脚本与预算出处；`codegen/`（MIR、LLVM IR、asm 与 grep 结果）；测试输出原样；以及 README 里一段「怎么复跑」。目录结构沿用[1.8](../part1/ch01.md#sec-cpp-rust.1.1.8)。这一格主轮缺一半：`gate.py` 只写 `budget_B`，另两轮才有 `budget_note`（17.9）。

命名有个差异要指出：第 1 章那一列叫 `position`（取值 0/1，[@def-1.4.1]），本项目同一含义叫 `arm_order`（`A_then_B`/`B_then_A`）——照 1.8 的清单去 grep `position` 会一无所获。

**本项目三轮里实际有什么、缺什么，要按现档说。**run-01 有 `environment.txt`、`bench.csv`、`statistics.json`、`gate.json`、`bench-verification.txt`、`test-summary.txt`、`run-log.txt`、`codegen/`；run-02 有 `environment.txt`、`codec.csv`、`compaction.csv`、两份 `statistics-*.json`、两份 `gate-*.json`、`mech-verification.txt`、`codegen/`，外加一份事后写的 `CORRECTION.md`（非采集产物，见 17.7.2）；run-03 有 `environment.txt`、`admit.csv`、`statistics.json`、两份 `gate-*.json`、`recompute.txt`、`admit-verification.txt`。脚本都在 `projects/tidekv/`，由 `run.sh` 串起来：测量二进制自己写 `*-verification.txt`（等价性不成立就不出数），主轮走 `analyze.py` + `gate.py`，另两轮走 `analyze_mech.py` + `gate_mech.py`，准入轮另有 `verify_admit_csv.py` 独立复算。

**缺的是源码指纹。**三份 `environment.txt` 只钉住机器与工具链，没钉住代码本身：归档里没有 `source-sha256.txt` 这一类文件。后果很具体——别人照这个目录复跑，只要他的 `src/` 与产出这三轮的那份不一致，原始 CSV 里的数就换了含义，而他没法从包里发现自己换过。补法是每轮结束时对 `src/**/*.rs` 与 `Cargo.toml` 逐文件算一次 SHA-256，但已归档三轮没有这一步，**本节没有采集**。

::: method 判定流程 · 从代码到结论

1. 契约：$O,F,I,X$ 写在采集之前（[@def-17.1.1]）。
2. 正确性：六条不变量里五条各有测试、一条缺（[@def-17.1.2]），且原始输出落盘。
3. 等价工作：同输入、同语义、可观察、独立参考值（[@def-1.6.1] 那条判据在本项目即 [@def-17.8.1]）。
4. 采集：预热、同轮交替、随机化位置、缺轮整对删。
5. 分析：配对差值 + bootstrap 区间，单位与分母写在表头。
6. 判定：与预算 $B$ 比，三态；「证据不足」要带下一步动作。
7. 归档：证据包目录齐全，别人能复跑。

七步里任何一步「先欠着，之后再补」，最后大概率不会补。

### 17.8.2 实测结果：门禁把自己判成「拒绝」

下面这张表是 `projects/tidekv/results/run-01/` 里的真实数据，采集于 2026-10-29，本机 Apple M5 Pro、`rustc` 1.99.1、`hw.cachelinesize` 128、24 GiB、macOS 27.2（build 26B123）、`arm64`。协议：种子 `20261028`，21 轮 × 每轮 30 批，每批重放**该 case 的完整操作序列**并在批末同步，每臂预热不少于 500 ms，B 侧每 300 次操作落一次段；区间是对配对差值均值做 20,000 次有放回重采样得到的 95% 百分位 bootstrap 区间（分析种子 `20289699`）。差值约定 **diff = B(tidekv) − A(基线)**，单位 `ns/op`，**正数表示 tidekv 更慢**。

**分母不是一个数，是四个。**CSV 的 `ops` 列逐行记着每批的操作数：`put_wide` 是 900，另外三个 case 在 900 个随机操作之前还要整段重放 setup 写——`get_hot` 2,000 条、`get_absent` 1,000 条、`scan_12` 4,096 条，所以每批分别是 **2,900 / 1,900 / 4,996** 次，这些写同样落在计时边界内、同样进 `ns/op` 的分母。CSV 头部那行 `ops_per_batch=900` 指的是随机段长度，与逐行 `ops` 列不同源，读表要以后者为准（`bench-verification.txt` 逐 case 印了这四个值）。

| case | A 基线 | B tidekv | 配对差值 | 95% 区间 | 判定（B = 1000） |
|:--|--:|--:|--:|:--|:--|
| `put_wide`（70% 写 300 B / 10% 删 / 20% 读，2 万键） | 63.144 | 40539.7 | **+40476.5** | [40105.6, 40819.8] | 拒绝 |
| `get_hot`（90% 点读 2 千热键 / 10% 写） | 75.654 | 33823.8 | **+33748.1** | [33561.9, 33929.4] | 拒绝 |
| `get_absent`（100% 读从未写过的键，逼布隆拒绝） | 61.785 | 24471.5 | **+24409.7** | [24219.8, 24594.7] | 拒绝 |
| `scan_12`（80% 读 / 20% 前缀扫，16 个前缀 4 千键） | 114.695 | 32195.3 | **+32080.6** | [31950.9, 32206.1] | 拒绝 |

重采样单位是配对后的 21 个轮均值差，不是原始批行；复现与逐位对账见[本章练习](ch17_exercises.md#repro-17.8)。

四个 case 的判定计数是接受 0、拒绝 4、证据不足 0。**大项目交出来的第一份结论，被自己的门禁全部拒绝了。**这件事比看起来更有教育意义，所以本节把它完整写下来。

**先确认数字没算错。**本节没有直接相信分析脚本：从 `bench.csv` 的 5,040 行原始值出发，先验证每行 `BATCH_MEAN` 等于该（轮，臂）30 个批次的均值（最大偏离 6e-07），再独立复算两臂均值、21 个配对差值的均值与样本标准差（N−1），与 `statistics.json` 逐项一致。等价性由 `bench-verification.txt` 记录：四个 case 的 A、B 与独立参考实现 REF 三方状态摘要逐位相同（`get_hot` 同为 `79802841a06e79bb`）。

**再确认这个差值在说什么。**基线 A 是进程内一把读写锁保护的有序表，**不落盘**；B 在计时边界内还要做预写日志追加、CRC 计算，以及每 300 次操作一次「把 memtable 交给 `write_segment` 编码建索引、写完立刻 `Segment::open` 读回并 CRC 校验、再 `wal.rotate_keeping` 重写日志尾部」（**没有排序**：内存表是 `BTreeMap` 迭代序，`write_segment` 只校验升序）。按 17.8.1 的判据，A 与 B **不是同一件工作的两种写法**：B 多做了整整一层持久化。于是这张表的正确读法是：

> 在本机的这个输入家族与批生命周期下，**持久化路径每操作多付 24.4–40.5 μs**；四个 case 里 `put_wide` 最贵（40.5 μs/op），`get_absent` 最便宜（24.4 μs/op）。这个跨度**不能**读成「谁写得多谁贵」——四个 case 的分母与值长各不相同，理由见下一段。

而**不是**「tidekv 比 `BTreeMap` 慢 642 倍」。比值 642 这个数本身没错（40539.7 ÷ 63.144），错在把它当成同一种工作的比较结果来引用——这正是 1.6 节那条判据（[@def-1.6.1]）在项目里的现实版本。

**差值的排序不能只按「谁写得多」来读**——真实分母里掺着不等量的 setup 写，按 `ops` 列算出的每批写占比排序与付费顺序不一致；完整对照见[本章练习](ch17_exercises.md#repro-17.8)。

所以这四个数只支撑一句：「四个负载家族上都要多付 24–40 μs/op」。要把「写占比越高越贵」写成结论，得先做一条单变量对照——固定值长与写占比，只改 `flush_every`——本轮**没有采集**；要补的是固定值长与写占比、只改 `flush_every` 的那一轮。

**「拒绝」这一态必须带下一步。**三条，按代价从小到大：

1. **改命题，不改代码**：把结论句写成「持久化开销 24.4–40.5 μs/op（区间如上）」，预算相应改成「每操作持久化开销不超过 X μs」，X 由业务的崩溃点目标（能接受丢多少秒的写）推出来，而不是沿用主轮那个 1000 ns/op——它的出处在归档里没有落盘（见 [@def-17.8.3]）。
2. **改实验，不改代码**：把段落盘移出计时边界，同时**另报一条命题**说明计时边界里不含持久化——这恰好是 17.8.4 的 E-a 那条错误，除非结论句里明说「本数字不含落盘」，否则就是让数字变漂亮的那一刻把契约破了（[@def-17.8.2]）。
3. **改实现**：如果业务确实要求每操作 1 μs 以内的写路径，那就要动结构（键值分离、批量提交日志、把 CRC 挪到后台线程），并重新走一遍四步主线。

**再补一条崩溃点语义。**代码里两处落盘的强度**不一样**：段文件写完调 `sync_all()`（`src/segment.rs`），真等内核把数据交给设备；预写日志默认只 `flush()`，把缓冲交给内核就返回，**不做** `fsync`（`src/wal.rs`，`durable` 默认为假）。所以：

- 那 24.4–40.5 μs 里，按代码布局**推断**是每 300 次操作一次的段落盘（含 `sync_all`）占大头，WAL 每操作那笔只到内核页缓存。这是推断，不是观测：CSV 每批只有一个 `value_ns_per_op`，夹具不做分段计时，**这一层本轮没有采集**。
- 因此 17.1.2 第一条不变量的准确说法是「进程重启后仍在」。**掉电语义没有被覆盖**：进程崩溃时数据已在内核里，照样能恢复；整机掉电时最后一段未 `fsync` 的 WAL 会丢。要覆盖它，得把 `durable` 打开重测一轮，并另写一条「掉电后仍在」的测试——**本节没有采集**。
- 这不是咬文嚼字：把「重启后仍在」写成「掉电后仍在」，等于把只保证进程级恢复的结论卖给需要机器级恢复的场景，是 17.8.4 的 E-f（不覆盖范围留空）最典型的形态。内核侧为什么有这种层次（页缓存、脏标记与回写、延迟分配），见 17.9 的 rCore 与 easy-fs 一条。

**再补两轮「机制内部」的对照。**主轮（`results/run-01/`）比 tidekv 与进程内基线，回答「持久化每操作多付多少」；`results/run-02/` 比机制内部的两种写法（17.4.2 编解码、17.7.2 压缩路径）；`results/run-03/` 只改 `admission_capacity` 一个参数（17.6.2）。三轮的门禁判定如下：

| 轮次 | case | A | B | 配对差值 | 95% 区间 | 预算 B | 判定 |
|:--|:--|--:|--:|--:|:--|--:|:--|
| run-02 | `codec_dyn` | 3.965 ns/记录 | 4.036 ns/记录 | +0.071 | [−0.054, +0.208] | 1 ns/记录 | 接受 |
| run-02 | `compact_subproc` | 7,696,326 ns/次 | 9,171,896 ns/次 | +1,475,570 | [+1,366,636, +1,586,757] | 10 ms/次 | 接受 |
| run-03 | `ns_per_attempted` | 774,433.8 ns/尝试 | 82,915.5 ns/尝试 | −691,518.3 | [−741,468.5, −652,422.3] | 5 µs/尝试 | 接受 |
| run-03 | `ns_per_accepted` | 2,456,036.2 ns/受理 | 2,470,043.5 ns/受理 | +14,007.4 | [−105,221.5, +132,036.5] | 5 µs/受理 | **证据不足** |

四条判定是三种不同的话：**「差异无法与噪声区分」**（run-02 编解码、run-03 受理口径）、**「差异确实存在、但远在预算之内」**（run-02 压缩），以及 run-03 尝试口径那句——它只说「浅门口没让每次尝试变贵」，方向是 B 更便宜，而那份便宜来自两边干的活不一样（每批受理 75.40 条对 8.07 条）。把它们写成同一句「都没问题」，就是又破坏一次 17.8.1 的口径。

三轮的臂顺序都是每轮抛硬币、不是配额制，所以位次效应三轮都能查；**随机化不等于平衡**（[@def-1.4.1]）这条已写进项目 README 的待办，主轮 84 条记录里先跑 B／先跑 A 是 52／32 条，其余分配见下表。

准入轮顺手量到一个**位次效应**：按「本臂这一轮先行还是后行」分组，A 臂先行 814,057 ns/尝试、后行 730,849（先行慢 11.4%），B 臂先行 80,885、后行 84,761（后行慢 4.8%）——**方向相反**，没有「谁先跑谁吃亏」那么整齐。

该看的是配对差值自己。按 `diff = A − B` 分顺序类：A 先跑的 11 轮平均 729,296，B 先跑的 10 轮平均 649,963，**类间间距 79,332 ns/尝试**。所以「配对把位次差抵掉了」不成立：同一轮里必有一臂先跑，位次差原样进了那一轮的差值；压小它的是每轮掷硬币且两类轮数接近。按实际分配复算，21 轮平均 691,518，均衡分配下 689,629，偏移 +1,889 ns，只占区间半宽（44,523 ns）的 4.2%。

同一算法把三轮八个 case 全跑了一遍（`python3 order_effect.py`，落盘 `results/order-effect-2026-10-30.txt`，属跨轮派生分析，不进任何单轮证据包）：

| 轮次 · case | A先/B先 轮数 | 类间间距 (ns) | 不均衡偏移 (ns) | 区间半宽 (ns) | 偏移/半宽 |
|:--|:--|--:|--:|--:|--:|
| run-01 `get_absent` | 8/13 | +448.3 | −53.4 | 187.4 | 0.285 |
| run-01 `get_hot` | 8/13 | +55.0 | −6.5 | 183.8 | 0.036 |
| run-01 `put_wide` | 8/13 | −347.8 | +41.4 | 357.1 | 0.116 |
| run-01 `scan_12` | 8/13 | +53.0 | −6.3 | 127.6 | 0.049 |
| run-02 `codec_dyn` | 11/10 | −0.0 | −0.0 | 0.1 | 0.001 |

读法有三条。位次效应三轮都在——run-02 压缩轮的类间间距将近 10 万 ns/次，谈不上「被噪声盖住」。八条判定没因此翻向，靠的是轮数接近均衡：偏移占半宽最大 28.5%（`get_absent`）、次大 11.6%（`put_wide`），其余六条 ≤6.4%。但这是「刚好没出事」，不是设计使然：要真拿掉位次得区组化随机（两类轮数强制相等）或每轮内再对调一次子批。

### 17.8.3 复跑失败时，先判它属于哪一层

大项目最常见的结局不是「结论被推翻」，而是「别人跑不出来」。跑不出来有五种完全不同的原因，混写成一句「项目跑不通」，就只能整章重跑（第 1 章的五层定位在这里逐条落地，[@ex-1.8.1]）。

| 层 | 在 `tidekv` 上的具体症状 | 先查哪个文件 | 该怎么记 |
|:--|:--|:--|:--|
| ① 构建失败 | `cargo build --release` 报目标特性不支持；或换了 `rustc` 版本后 `codegen/` 里的 grep 结果形状变了 | `environment.txt`；源码指纹缺档（[@def-17.8.3]） | 单独记为构建失败，性能字段留空，不许填「很慢」 |
| ② 功能失败 | CRC 恢复测试拒了不该拒的记录；或 `get` 的结果与独立参考值逐键不等 | `tests/` 的原始输出 | 先修功能。功能不对时，任何短耗时都没有意义 |
| ③ 采集失败 | `bench.csv` 里某一轮少了一行，或 `round` 集合不连续 | `bench.csv` + `analyze.py` 对轮次的严格检查 | 缺轮整对删；不许把缺失批次当成有效小样本 |
| ④ 解释失配 | 换一台机器，段文件字节数与测试结果都一样，但差值方向反转 | `codegen/` 的 grep 结果与 `environment.txt` 对照 | 这是**结论范围变化**，不一定是错误：重写不覆盖范围那一格 |
| ⑤ 统计不确定 | 区间跨预算 $B$，判成「证据不足」 | `statistics.json` 与 `gate.py` 的输出 | 独立时段重跑或扩大输入家族，不许在两个数里二选一（[@def-1.7.2]） |

五层的修法互不相通：①要改构建参数，②要改代码，③要改采集，④要改结论边界，⑤要改证据量。**报告里写「复跑失败」而不写层号，等于把定位工作推给读者。**

### 17.8.4 小结与常见错误

**小结。**①基线与候选必须满足等价工作的四个条件（[@def-17.8.1]）。②计时边界要含批内全部副作用，尤其不许跳过 flush（[@def-17.8.2]）。③三态判定的每一态都自带下一步（[@ex-17.8.1]）。④证据包是结论的一部分（[@def-17.8.3]）。⑤复跑失败先判层号：构建、功能、采集、解释、统计五层各查各的文件，各有一种修法。

::: errata 常见错误清单（17.8 节）

E-a **计时器里 `if` 掉 flush。**数字变漂亮的那一刻，实验契约已经破了（[@def-17.8.2]）。

E-b **基线用别的库却不验输出等价。**两件工作的快慢差不是写法差（[@def-17.8.1]）。

E-c **先跑再定预算。**事后定的 $B$ 等于没定（[@def-1.7.1]）。

E-d **只交一张汇总表。**没有原始 CSV，别人算不出你的差值。

E-e **换种子直到区间不跨零。**这是把偶然极值当稳定收益（[@def-1.7.3]）。

E-f **不写不覆盖范围。**结论会被读者外推到你的负载之外，然后回来找你。

:::

::: method 即时自测 · 17.8

## 17.9 延伸阅读与来源 {#sec-cpp-rust.4.17.9}

本章的**判定方法**全部来自书内（第 1 章是母版，配对、区间与三态门禁的完整推导都在那里）；**结构选择与机制解释**不是——「日志 + 不可变段 + 合并」有几十年的前作，索引放在哪里、写完到哪一层、通知落在哪里这些问题都有人在我们先答过。下面按「用在哪一节」分组，每条写明借什么、不借什么。

**存储结构（17.2、17.7）**

- Patrick O'Neil, Edward Cheng, Dieter Gawlick, Elizabeth O'Neil. *The Log-Structured Merge-Tree (LSM-Tree)*. Acta Informatica 33(4):351–385, 1996. —— 本项目「内存表刷成不可变段 + 后台合并」的原始形态。**我们只借它的写路径顺序化与读路径多源合并两点**，不分层、不做 leveled 策略，因此全书没有一处声称写放大系数（那需要另一组实验契约，见 17.1.3 的「不做什么」）。
- Lanyue Lu, Thanumalayan Sankaranarayana Pillai, Andrea C. Arpaci-Dusseau, Remzi H. Arpaci-Dusseau. *WiscKey: Separating Keys from Values in SSD-conscious Storage*. FAST 2016. —— 键值分离的动机。它在 17.8.2 的下一步动作第 3 条里出现：如果要把写路径的每操作开销压下来，第一条可做的结构改动就是把值挪到独立的值日志，代价是范围读要额外一次随机读与一套垃圾回收。**本章没有实现它**，所以也不引用它的任何数字。

**近似成员查询（17.2）**

- Burton H. Bloom. *Space/time trade-offs in hash coding with allowable errors*. Communications of the ACM 13(7):422–426, 1970. —— 布隆过滤器的原始论文，也是「无漏报」这条硬契约的出处。
- Bin Fan, David G. Andersen, Michael Kaminsky, Michael Mitzenmacher. *Cuckoo Filter: Practically Better Than Bloom*. CoNEXT 2014, 75–88. —— 如果将来要支持删除段里的单个键，这条路线比布隆直接。本项目段文件不可变，所以没有这个需求。
- 例 17.2.2 里那条「单槽上界不等于整体假阳率」的修正是**算术给出的**：一次探测扫 16 个槽，并集上界该从 1/256 移到 1/16 那条线上。实测（0.762%，约 1/131，见 `results/bloom-contract-2026-10-30.txt`）只用来确认修正方向没有跑偏；写这一节时先给的是 1/256，跑完测试才发现它与单槽上界差约 1.95 倍，不是一个数量级。**这条修正在原始文献里是显然的**（多哈希方案的假阳率本就要按 k 次比较算），读者不必重走我们的错路。

**内存回收（17.5）**

- Maged M. Michael. *Safe Memory Reclamation for Dynamic Lock-Free Objects Using Atomic Reads and Writes*. PODC 2004（hazard pointer 的正式出处；同一作者的 *Hazard Pointers: Safe Memory Reclamation for Lock-Free Objects*, TPDS 2004 给了工程版）。
- Tim Fraser. *Practical Lock-Freedom*. 博士论文，剑桥大学，2004 —— epoch 回收的最早完整描述。
- Jeehoon Kang, Jaehwang Jung. *A Marriage of Pointer- and Epoch-Based Reclamation*. PLDI 2020, 314–328 —— 两类方案混合的近作，读 17.5 的「该用哪一层」时值得先看它的分类。
- Rust 侧的工程实现是 `crossbeam-epoch`（`Guard`/`pin`/retire 的语义与本项目 `epoch.rs` 同源）；设计说明见 Aaron Turon, *Lock-freedom without garbage collection*, 2015。另可参考一条谱系综述：[Concurrent Immediate Reference Counting, PACMPL 8(PLDI), 2024](https://dl.acm.org/doi/10.1145/3656383) 的相关工作段落，一张表比较 HP / EBR / RCU / 引用计数。
- 17.5 思考框里那条「退休表可能无界增长」不是臆测：批式回收在什么情况下反而有害，可见 *Are Your Epochs Too Epic? Batch Free Can Be Harmful*（arXiv:2401.11347）。**本项目只把退休表长度做成一个可观测计数，没有采集它随时间的曲线。**

**内核侧机制（17.8.2 的崩溃点语义）**

- rCore-Tutorial-Book-v3（清华大学《操作系统》Rust 实现课程，中文，RISC-V / Sv39）。这一组列四份页面，其中**与 17.8.2 崩溃点段直接有关的只有第四份**（easy-fs 的 `BlockCache`：512 字节缓冲 + `modified` 脏标记 + 全局管理器合并块操作）；前三份支撑的是任务切换、时钟与分页那几条对照，别把它们当成掉电语义的出处。本章其余 rCore 页面在下面两组里逐条列出，读取状态都记在台账 `sources/web.json`。

  四份页面：`chapter3/2task-switching.html`（任务切换只保存「仍有用且会被覆盖」的资源：`ra`、`s0~s11`、`sp`，由手写汇编 `__switch` 完成）、`chapter3/4time-sharing-system.html`（时钟中断与时间片：通过 SBI 的 `set_timer` 设定 `mtimecmp`，每秒 100 tick）、`chapter4/3sv39-implementation-1.html`（三级页表逐级索引、`satp` 的 MODE/ASID/PPN 字段、大页为何能减轻 TLB（地址翻译缓存）压力并提升 IPC）、`chapter6/2fs-implementation.html`（easy-fs 的五层结构与 `BlockCache`：512 字节缓冲 + `modified` 脏标记 + 全局管理器合并块操作；并提醒扇区与块是两个概念）。

  落点在 2.3.3、9.2.3、12.8.5 与本章 17.8.2。**借的是层次划分**：`write` 到内核页缓存、`fsync` 到设备、文件系统内部还有一层块缓存与元数据写回，三层各自的成本与崩溃语义不能混为一谈。指纹与核读范围登记在 `sources/web.json` 与来源台账。
- ext4 的**延迟分配**（allocate-on-flush）：buffer write 只把数据放进页缓存并打脏标记，磁盘块要等到回写或 `fsync` 时才分配。这条解释了为什么「写一次的开销」不是一个常数，而取决于它撞上回写点的时机。主轮的夹具把落盘固定在每 300 次操作一次（`--flush-every`，同时把 `memtable_flush_bytes` 设成 `usize::MAX` 关掉按字节触发），就是为了把这个时机变成可控的批边界；**引擎本身的策略是按字节触发**（默认 64 KiB），准入轮用的又是第三种口径（256 KiB、按字节）——这三者不要混成一个。

**文件系统与索引结构（17.2、17.3）**

- rCore-Tutorial-Book-v3 第六章「简易文件系统 easy-fs」（`chapter6/2fs-implementation.html`，指纹见来源台账）——五层架构、`DiskInode` 的 28 个直接索引项与两级间接索引（容量可静态算：14 KiB、64 KiB、8 MiB）、`BlockCache` 的 `modified` 脏标记，以及那句关于**统一缓冲区**的警告：各拿一份缓冲会导致同一块的修改对后续读不可见。17.2.2 与 17.3.2 的对照以它为依据，借的是问题不是实现。
- rCore-Tutorial-Book-v3 第六章「文件系统接口」（`chapter6/1fs-interface.html`）——该页把目录内容定义成一组**目录项**（文件名 → Inode 号的映射），并指出路径解析只能一个目录一个目录地往下查，天然是串行的；它的注解进一步说：极高并发场景可以弱化目录权限、把目录树压平、把磁盘布局改成类键值存储。这正是 17.2 把「集中定宽索引区」当成 tidekv 主动选择的理由——不是文件系统的错，而是并发写路径上少一次串行解析。**借的是取舍，不是实现。**

**有界、取消与原子发布（17.6、17.7）**

- rCore-Tutorial-Book-v3 第七章「管道」（`chapter7/2pipe.html`）——管道被实现成一个固定容量的字节环，状态显式分成满、空与正常三种；环里用弱引用记录「写端是否还有人」，因此**只有所有端都关闭之后**缓冲区才随引用计数归零而回收。对照 17.6.1 的有界准入与 17.7.1 的双路排空：容量是必须写下来的设计量，回收的触发点是最后一个引用而不是「我以为没人用了」。它那个环的容量是个教学内核的取值，本章一个都没有搬进实验结论。
- rCore-Tutorial-Book-v3 第七章「信号」（`chapter7/4signal.html`）——内核把这个检查放在 trap 处理完之后、交回用户态之前的最后一个路口，处理函数跑完还要再调一次专门的返回调用，执行现场才恢复得回去。对照 [@def-17.6.2] 的取消与完成分界：取消需要一个安全点，内核给的是「返回用户态」这一个点；本项目压根没有按请求取消的 API，能算「点」的只有入队前后的队列状态与 `close()` 那个竞态窗口。
- rCore-Tutorial-Book-v3 第九章「virtio 设备与虚拟队列」（`chapter9/2device-driver-2.html`）——驱动把请求填进共享环并 `kick` 通知设备，设备完成后置完成状态；设备状态域把失败分成两个等级（驱动无力驱动、需要重置）。对照 [@def-17.7.3] 的原子发布：提交与完成分离、失败要分级上报，这两条在教学内核里也是显式状态机，而不是「publish 一下就完事」。

**台账边界。**网页与代码证据的落盘副本登记在 `sources/web.json`（每条有 URL、字节数与 sha256）与 `sources/sections.json`（16 份纸本母本的逐条映射）。

只有已抓取并算过哈希的来源进得了台账；LLVM 那条是 2026-10-30 的**在线核读**，没有落盘副本，也就不在台账里——按「读过、可回访」的强度引用，别当归档证据。同理，本节的论文条目（LSM-Tree、WiscKey、布隆 1970、Cuckoo Filter、两条 concurrent hash map、Mytkowicz、Kalibera & Jones 等）是按**标准引文**给出的：能回访，但没有落盘副本、没逐条核读原文，也就不在台账里——别当成「本书核读过的证据」。

**三组实测的落盘位置**

- 功能测试的原始打印（例 17.2.2 那三个数）：`projects/tidekv/results/bloom-contract-2026-10-30.txt`——命令、工具链版本与未捕获 stdout 都在；不是计时轮，没有区间。
- 主轮（17.8.2）：`projects/tidekv/results/run-01/`。逐文件清单见 [@def-17.8.3]，这里只记独有的一条缺口：`gate.json` 里有 `budget_B`，**没有预算出处说明**。
- 机制对照轮（17.4.2、17.7.2）：`projects/tidekv/results/run-02/`。两份 `gate-*.json` 都带 `budget_note`，其中压缩那份的旧依据已被同目录 `CORRECTION.md` 否证；等价性证据是 `mech-verification.txt`（两臂输出逐字节相同）与 `codegen/codec-codegen.txt`（汇编层 `bl`/`blr` 计数）。
- 准入对照轮（17.6.2）：`projects/tidekv/results/run-03/`。`admit.csv` 是 1,680 行原始记录（= 840 个批次 × 两条口径），每行都带 `wall_ns`、受理数、flush 次数、落盘字节，正文每个比值都能从这几列重算；`admit-verification.txt` 记状态回放与计数器两关，`recompute.txt` 是独立重算，两个分母各一份 `gate-*.json`。
- 三轮一条命令复跑：`projects/tidekv/run.sh`。协议与种子写在每轮统计 JSON 的 `protocol` 字段；还有一条输入家族要交代：准入轮把值长取到 **64 KiB**，而 17.1 的契约 $X$ 明写「不覆盖值长接近页大小的记录」（本机 arm64 页 16 KiB）。那一轮是**刻意站在主契约之外**——不把记录撑大，一次刷盘就不会在墙钟里显形。所以那两条判定只在该值长下成立，不能搬回主轮 64 B 值长的家族。

预算出处写在 run-02、run-03 那四份 `gate-*.json` 的 `budget_note` 里，**主轮的 `gate.json` 没有这个键**——它由 `gate.py` 生成，只落 `budget_B`，那条 1000 ns/op 写在 `run.sh` 的 `BUDGET` 默认值上，它的适用边界正是 17.8.2「改命题」那一条在处理的事。跨轮的位次复算另有一份派生产物 `results/order-effect-2026-10-30.txt`，不属于任何单轮证据包。

- 复跑这里要如实补一句：`run.sh` 目前给三轮统一传 `SEED`（默认 20261028）与 `WARM_MS`（默认 500），而归档里 run-02 是 20261029/500、run-03 是 20261030/300——**一条命令重跑不会自动回到那批参数**，要精确复现任一轮得显式传 `SEED=` 与 `WARM_MS=`，各轮的值写在 CSV 头部与 `protocol` 字段里。**README 不抄测量结果**（差值、区间、判定只在这些文件里）；它抄的是协议量——每批分母、轮数分配这类——因为那些不看 CSV 就没法读表。

**测量方法（17.8）**

- Trevor Mytkowicz, Amer Diwan, Matthias Hauswirth, Peter F. Sweeney. *Producing Wrong Data Without Doing Anything Obviously Wrong!* ASPLOS 2009 —— 测量偏倚如何系统性地改变结论方向。17.8.2 那个「先跑 B 52 轮、先跑 A 32 轮」的失衡记录，动机就是这篇。
- Tomas Kalibera, Richard E. Jones. *Rigorous Benchmarking in Reasonable Time*. ISMM 2013 —— 用 bootstrap 给出相对变化的置信区间，本项目 `analyze.py` 的做法与它同族（我们对配对差值均值做 20,000 次有放回重采样）。
- Andy Georges, Dries Buytaert, Lieven Eeckhout. *Statistically Rigorous Java Performance Evaluation*. OOPSLA 2007 —— 预热与重复轮次的统计作用，对应 17.8 协议里「每臂预热不少于 500 ms」。
- LLVM 官方文档 [Benchmarking tips](https://llvm.org/docs/Benchmarking.html) —— 一份很短的实践清单。2026-10-30 在线核读，原文那句是 “low noise is required, but not sufficient. It does not exclude measurement bias.”（低噪声是必要的但不充分，它不排除测量偏倚）。**它没有讲随机化跑序**；能对上的是 17.8.2 位次效应那条读法：区间再窄也不代表没有偏，随机化只是把偏转成方差，剩下的偏要靠轮数配平去消。

**没有跟的地方**：不实现分层与 leveled 合并、不做键值分离、不做事务与隔离级别、不用 `mmap`、不做常驻 worker 池。这些取舍在 17.1.3 已逐条给出理由；引用上面的文献只是为了让读者知道**每条边界另一侧站着谁**。

来源与审计台账统一维护在 [`src/appendix/coverage.md`](../appendix/coverage.md)。

## 17.11 本章小结与章末件 {#sec-cpp-rust.4.17.11}

::: note 本章小结

这一章把十六章的内容收进一个仓库：布局（17.2）、所有权与 `unsafe`（17.3）、分发与口径（17.4）、并发与回收（17.5）、准入与取消（17.6）、进程边界（17.7）、实验与门禁（17.8）。真正贯穿的不是这七块机制，而是那条主线：**先证明活真的干了，再证明这个数是什么，再证明差异不是噪声，最后证明结论守得住、别人复核得了。**

项目的价值也不在那个引擎能跑多快，而在你能不能对一段自己写的代码，交出一份能被追问的证据。这一份，就是这本书的毕业作品。

:::
