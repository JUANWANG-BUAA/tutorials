## 14.1 构建身份不是一个版本号 {#sec-cpp-rust.4.14.1}

### 为什么同一提交仍可能不是同一个程序

源码提交只描述仓库内的一部分输入。
条件编译、工具链、依赖解析和外部工具会共同决定产物。
同一提交启用不同feature，可以编出不同业务路径。
同一Cargo.lock换目标平台，也可能选择不同依赖与系统库。

性能比较的第一步是记录程序身份。
身份不是为了让日志更长。
它决定比较是否具有同一问题的含义。

例如，默认版本不记录逐字节审计，候选版本记录。
两者输出都正确，但执行工作不同。
门禁应能发现成本差异，同时说明功能差异。
不能只把候选版本标成“编译器退化”。

### 身份分层

<pre class="layout">
源文件 + 清单 + 锁文件
          |
          v
包选择 + feature闭包 + target + profile
          |
          v
rustc/Cargo + 标准库 + 链接器 + SDK + 构建脚本输入
          |
          v
对象、IR、调试信息、链接产物
          |
          v
最终二进制指纹 + 运行输入 + 环境 + 原始观察
          |
          v
正确性门禁 / 性能门禁 / 独立重跑 / 发布裁决
</pre>

读图：每一层都增加新的输入或派生物。
锁住上层的一部分，不意味着下层自动确定。
最后的发布裁决仍需要正确性、可比较性和失败处理。

### 至少记录的构建字段

| 层 | 本轮记录 | 不足以单独证明的东西 |
|:--|:--|:--|
| 源码 | Rust、脚本、清单、锁文件SHA256 | 正确性与可信来源 |
| 编译器 | rustc -Vv完整输出 | 链接器与SDK完全相同 |
| Cargo | cargo -V、实际命令 | feature闭包完全一致 |
| 配置 | profile、CGU、LTO、incremental | 所有环境覆盖都已消失 |
| 目标 | aarch64-apple-darwin | CPU固定频率与核绑定 |
| 产物 | 二进制大小和SHA256 | 位级可复现构建 |
| 执行 | 输入长度、checksum与21条观察 | 生产请求分布 |

### 工具链锁定的范围

工程通常可以在包内使用rust-toolchain.toml固定工具链。
还应记录实际执行的rustc版本，而不只相信配置文件存在。
离线环境可能缺少所指定工具链。
自动下载行为也会改变构建可用性与时间边界。

本轮没有新增工具链覆盖文件。
使用现有已安装的stable工具链，并记录其完整版本。
这避免修改共享环境，也避免假称锁定了未安装组件。

已观察版本为：

```text
rustc 1.99.0 (b940084d7 2026-09-28)
commit-hash: b940084d7eb6a299eb4bfeb8e34901bc051e7ac4
host: aarch64-apple-darwin
LLVM version: 23.1.1
cargo 1.99.0 (5f94df478 2026-08-27)
```

这不是未来版本兼容承诺。
升级后应重新检查编译选项、代码生成与统计基线。

### locked、offline与frozen的不同责任

`--locked`要求沿用锁文件，不允许悄悄更新解析。
`--offline`限制Cargo使用本地可用资源。
两者都不把构建脚本变成沙箱。
一个build.rs仍可能读取外部文件或运行任意工具。

`--frozen`组合锁文件与离线约束。
它同样不是网络隔离、供应链审计或位级确定性的同义词。
本轮采用显式`--offline --locked`，便于读者看到两份责任。

### 正确性先于性能可比较性

输出错误的候选程序即使更快，也不能通过性能发布。
checksum只是一种有限观察，不是完整语义证明。
还需要边界输入、错误输入和契约测试。

本实验的简单求和有直接参考实现。
空输入和非整块长度也经过测试。
这比只看一个大输入的成功退出更可靠。

## 14.2 Feature图：相加的能力与隐藏的工作 {#sec-cpp-rust.4.14.2}

### feature是编译输入，不是运行配置文件

feature通常通过条件编译启用代码或可选依赖。
它会改变实际编译出的路径。
运行时环境变量不能自动关闭已经编译进去的所有行为。

因此，性能报告应写明确切feature集合。
“release构建”并不足够。
同一release profile可搭配完全不同的feature闭包。

### Cargo通常统一同一依赖的feature请求

一个依赖被多条路径引用时，相关请求通常取并集。
某条边写default-features=false，不会撤销其他边启用的默认feature。

下面是概念图，不是本轮零依赖实验的实际依赖图。

```text
service -> parser(default-features=false)
service -> plugin -> parser(default feature enabled)

parser的相关构建单元仍可能获得default能力。
```

需要沿反向路径追踪“谁启用了它”。
只检查顶层清单中的一行，往往看不出完整结果。

### feature应尽量保持相加

启用能力通常不应删除已存在的公共接口。
互斥feature要求所有依赖使用者协同，容易失控。

如果确实不能同时启用，应在编译时显式拒绝。
但要先考虑拆包或运行时策略选择。
不要把feature当成只能由顶层唯一控制的全局枚举。

### resolver也参与构建单元划分

resolver2改进了某些不应统一的情况。
例如构建依赖与普通依赖、未构建目标的平台依赖、特定开发依赖。
这种分离有时意味着同一包需要构建多份。

resolver3还涉及Rust版本感知的解析行为。
它不是“所有依赖永远只编译一次”的开关。
本轮独立workspace显式使用resolver3。
由于无第三方依赖，本轮没有测复杂resolver的性能。

### 实际检查命令

```bash
cargo tree --offline --locked \
  --manifest-path bench/evidence-lab/Cargo.toml -e features --features checked
cargo metadata --offline --locked \
  --manifest-path bench/evidence-lab/Cargo.toml --format-version 1
```

输出保存为`feature-tree.txt`与`metadata.json`。
实际树只有本包，没有假造额外依赖来显得复杂。
metadata记录包目标与清单结构。
本轮文件路径属于本机，不能把它当跨机器稳定标识。

### 大工程中的追踪方式

对真实有依赖工程，可以增加以下检查。
这些命令形状不是本轮运行结果。

```bash
# foo应替换为实际工程中的包名；这里不声称本实验存在该包。
cargo tree -e features -i foo
cargo tree --duplicates
cargo tree -f '{p} {f}'
```

重复版本与同版本不同构建单元是不同问题。
后者可能来自host/target、feature或profile差异。
不要只用锁文件中的包条目数量估计编译次数。

### 本实验的feature契约

`checked`不是安全开关。
默认版本与checked版本都只使用安全Rust。
它是一个有意添加逐字节可观察审计工作的实验开关。

| 配置 | 输入类型 | 返回值 | 额外工作 |
|:--|:--|:--|:--|
| default | &amp;[u8] | u64求和 | 无逐字节Event |
| checked | &amp;[u8] | 相同u64求和 | 每字节构造Event并black_box |

不能根据名字认为默认版本跳过了必要内存安全检查。
也不能把checked结果解释成Cargo本身的运行开销。
Cargo只是选择了不同代码。

### 测试组合不能只用all-features

all-features会测试一个并集配置。
它不覆盖“没有任何可选feature”的路径。
对互斥feature，甚至可能不是合法配置。

本轮分别执行默认与all-features测试。
本包只有一个可选feature，所以两种配置覆盖了这两条路径。
真实多feature工程需要风险驱动的组合矩阵。
不要假装一次全开测试穷尽指数级组合。

### 文档也需要配置身份

cargo doc默认展示某个feature集合下可达的API。
文档页存在，不意味着最小配置也有该API。
示例应注明需要的feature或独立编译条件。

本轮实际执行了带-D warnings的all-features文档构建。
库里的求和示例也作为doctest执行。
这只验证本包示例，不表示所有文档平台均通过。

## 14.3 可复现构建：先划清承诺级别 {#sec-cpp-rust.4.14.3}

### 三种经常混用的“可复现”

第一种是流程可重跑。
读者能从源码与命令重新生成可运行程序。
第二种是性能实验可比较。
输入、配置和环境足以让两次结果具有共同解释。
第三种是位级产物相同。
同样输入在规定条件下产生完全相同字节。

前两种不自动推出第三种。
同样字节也不自动证明运行环境相同。
发布文档应明确自己承诺哪一级。

### 锁文件锁住的不是世界

Cargo.lock记录解析出的包身份与版本等信息。
它没有把系统SDK、链接器、环境变量和构建脚本外部读取全部封存。
路径依赖的内容仍由工作目录决定。
本地工具链也可能被替换。

一个有外部C库的Rust包还需要外部库身份。
这里不需要为零依赖实验虚构CMake工程。
若涉及FFI，应另行固定编译器、头文件、链接选项和ABI测试。

### 构建脚本是额外输入边界

build.rs可以读取时间、环境、目录、生成器和外部命令输出。
正确的rerun-if-changed声明影响Cargo何时重跑它。
声明不完整可能导致陈旧产物。
声明过宽可能导致不必要重建。

这两类问题都可能污染性能比较。
一个版本实际没有更新，不代表它“构建非常快”。
一个版本每次都重新生成全部代码，也不代表rustc突然变慢。

本实验没有build.rs和proc macro。
这样可把构建实验范围缩小到本包编译与链接。
代价是不能直接外推大型生成式工程。

### 路径、调试信息和链接元数据

绝对路径可能进入调试信息或对象记录。
不同输出目录也可能改变链接相关元数据。
平台签名与可执行格式还会增加自己的字段。

因此，比较二进制SHA256时，应把它当身份检查。
哈希不同只证明字节不同。
不立即证明业务代码不同，更不证明运行性能一定不同。

### 本轮真实反例

构建矩阵为每个配置创建21个不同目标目录。
同一配置的产物文件大小一致。
但是21个SHA256都不同。

| profile | 文件大小/字节 | fresh构建数 | 不同SHA256数 |
|:--|--:|--:|--:|
| release | 518448 | 21 | 21 |
| one | 512640 | 21 | 21 |
| thin | 502672 | 21 | 21 |

这是实际记录，不是关于所有Rust产物的普遍定理。
本轮没有对全部差异字段作二进制归因。
不能武断断言“全是时间戳”或“全是路径”。

可以确定的是：
本轮设置没有产生跨这21个目标目录的字节相同产物。
所以章节不会写“Cargo.lock保证确定性构建”。

### 无操作重建的另一种身份检查

每个fresh构建后，脚本在同一目标目录执行同一命令。
没有修改源码或标志。
此时Cargo主要检查是否已有最新产物。

原始记录同时保存fresh与noop的产物SHA256。
应检查同一对记录是否一致。
这能发现意外重建或产物被外部修改。
但它仍不是跨环境位级可复现验证。

### remap与SOURCE_DATE_EPOCH不是魔法

路径重映射可以减少某些绝对路径泄漏。
SOURCE_DATE_EPOCH可以作为支持它的工具的约定输入。
二者都只覆盖愿意遵守相应机制的组件。

外部生成器或签名工具可能有自己的行为。
应先识别差异，再逐项消除。
不要看到一个环境变量名字，就宣布整个流水线确定。

本轮没有用这些选项“修饰”哈希结果。
保留失败的确定性假设，正是可复现研究的一部分。

### 缓存键至少包含什么

缓存键应区分目标、工具链、锁文件、feature和关键编译标志。
构建脚本外部输入也需要适当纳入。
过窄缓存键可能复用错误产物。
过宽缓存键则失去复用价值。

性能测量归档不应直接使用可被覆盖的CI缓存目录。
缓存服务为了命中率可以驱逐或替换内容。
证据归档则需要不覆盖、可定位和可核验。

## 14.4 Benchmark一：CGU、LTO与精确缓存边界 {#sec-cpp-rust.4.14.4}

### 为什么测构建也需要实验协议

“构建用了两秒”没有说明重做了什么。
可能是下载依赖、解析、编译本包，也可能只是检查已有文件。
OS页缓存和预装标准库通常仍然存在。

本轮不使用“完全冷构建”这个名称。
准确名称是“新包目标目录构建”。
每次给Cargo一个不存在的target目录。
但源码、工具链、标准库和操作系统缓存已经存在。

### 三种实际profile

以下是完整`Cargo.toml`。
它不是上层共享bench清单的修改。
独立workspace避免影响其他实验包。

```toml
[package]
name = "evidence-lab"
version = "0.1.0"
edition = "2024"
publish = false

[workspace]
resolver = "3"

[features]
default = []
checked = []

[profile.release]
debug = 1
incremental = false
codegen-units = 16
lto = false

[profile.one]
inherits = "release"
codegen-units = 1

[profile.thin]
inherits = "release"
codegen-units = 1
lto = "thin"
```

release保留有限调试信息。
one只改CGU数量。
thin在one基础上显式启用跨crate ThinLTO。
本轮没有测试fat LTO。

### false与off不能混写

Cargo Profiles文档指出，lto=false可对本地crate的CGU做thin local LTO。
CGU=1或opt-level=0时不执行这类本地LTO。
lto="off"才表示关闭LTO。

因此表中release不能命名为“绝无LTO”。
one也不仅是把同一优化任务平均分成一份。
CGU划分会影响代码组织与优化机会。

### 计时边界

| 项目 | 本轮设置 | 是否进入墙钟 |
|:--|:--|:--|
| Cargo启动、检查、编译与链接 | 每次subprocess运行 | 是 |
| 目标目录 | 每profile每轮新建 | fresh路径不存在 |
| 标准库与rustc | 预先安装 | 不重新构建 |
| 下载 | offline，且无第三方依赖 | 无下载工作 |
| 编译并发 | -j1 | 不与其他case并行 |
| 增量 | CARGO_INCREMENTAL=0 | 关闭 |
| 详细日志 | -vv写本地文件 | 是，所有case一致 |
| 大小与SHA256读取 | 命令结束后 | 否 |
| correctness运行 | 每profile第0轮产物 | 否 |

-j1限制Cargo调度的作业数量。
它不能被解释成编译器内部所有线程都只有一个。
CGU与链接阶段仍可能有自己的执行策略。

### 第四个独立benchmark的完整驱动

完整文件为`tools/build_matrix.py`。
以下源码只调整排版与说明性注释，执行逻辑与本轮运行文件一致。

```python
#!/usr/bin/env python3
"""Fresh package-target and no-op builds, never cold OS caches."""
import hashlib
import json
import math
import os
from pathlib import Path
import statistics
import subprocess
import sys
import time

LAB = Path(__file__).resolve().parents[1]


def summary(values):
    ordered = sorted(values)
    return {"n": len(values), "mean": statistics.mean(values),
            "sd": statistics.stdev(values),
            "p50": ordered[math.ceil(.5 * len(values)) - 1],
            "p99": ordered[math.ceil(.99 * len(values)) - 1]}


def main():
    out = Path(sys.argv[1]).resolve()
    root = out / "builds"
    root.mkdir()
    observations = []
    env = os.environ.copy()
    for name in ("RUSTFLAGS", "CARGO_ENCODED_RUSTFLAGS",
                 "RUSTC_WRAPPER", "RUSTC_WORKSPACE_WRAPPER"):
        env.pop(name, None)
    env["CARGO_INCREMENTAL"] = "0"
    profiles = ["release", "one", "thin"]
    subprocess.run(["rustc", "-Vv"], check=True,
                   stdout=subprocess.DEVNULL)
    with (out / "build-raw.jsonl").open("x") as raw:
        for round_id in range(21):
            for offset in range(3):
                profile = profiles[(round_id + offset) % 3]
                target = root / f"{profile}-{round_id:02}"
                command = ["cargo", "build", "--offline", "--locked",
                           "--manifest-path", str(LAB / "Cargo.toml"),
                           "--profile", profile, "--bin", "feature_work",
                           "--target-dir", str(target), "-j", "1", "-vv"]
                for boundary in ["fresh-package-target", "noop"]:
                    log = out / f"build-{profile}-{round_id:02}-{boundary}.txt"
                    with log.open("x") as stream:
                        start = time.perf_counter_ns()
                        subprocess.run(command, check=True, env=env,
                                       stdout=stream, stderr=stream)
                        elapsed_ms = (time.perf_counter_ns() - start) / 1e6
                    binary = target / profile / "feature_work"
                    content = binary.read_bytes()
                    row = {"case": f"{profile}/{boundary}", "round": round_id,
                           "wall_ms": elapsed_ms, "binary_bytes": len(content),
                           "binary_sha256": hashlib.sha256(content).hexdigest(),
                           "command": command}
                    raw.write(json.dumps(row) + "\n")
                    raw.flush()
                    observations.append(row)
                if round_id == 0:
                    result = subprocess.run(["size", "-m", str(binary)],
                                            check=True, capture_output=True,
                                            text=True)
                    (out / f"size-{profile}.txt").write_text(result.stdout)
                    result = subprocess.run([str(binary)], check=True,
                                            capture_output=True, text=True)
                    (out / f"verify-{profile}.txt").write_text(result.stdout)
    cases = sorted({row["case"] for row in observations})
    result = {case: summary([row["wall_ms"] for row in observations
                            if row["case"] == case]) for case in cases}
    (out / "build-summary.json").write_text(json.dumps(result, indent=2) + "\n")
    print(json.dumps(result, indent=2))


if __name__ == "__main__":
    main()
```

正文只调整了排版和模块docstring，不改执行逻辑。
计时脚本`tools/measure.sh`在外层取得独占目录锁。
不要绕过外层锁并行执行多个build_matrix。

### 实际构建墙钟

## 14.5 Benchmark二：feature回退与会拒绝的门禁 {#sec-cpp-rust.4.14.5}

### 为什么需要一个真实失败候选

只让正确基线通过，无法证明门禁能挡住回退。
需要一个实际可运行、输出正确却更昂贵的候选。
本轮checked feature正承担这份责任。

它没有引入UB。
它没有通过故意错误结果取巧。
它只是增加逐字节观察，形成安全的性能回退案例。

### 完整求和实现

```rust
pub fn sum_bytes(bytes: &[u8]) -> u64 {
    bytes
        .iter()
        .map(|&byte| {
            #[cfg(feature = "checked")]
            std::hint::black_box(evidence_lab::Event {
                id: u64::from(byte),
                elapsed_ns: 0,
            });
            u64::from(byte)
        })
        .sum()
}
```

上段是库外调用形式的同义完整函数。
实际库内使用本模块的Event与black_box导入。
唯一被编译与测量的实现保存在`src/lib.rs`。

Event的elapsed_ns在此固定为零。
本实验不读逐字节时钟。
因此它与第13章Each模式测的是不同观测组合。
不能把两张表的差值当成时钟独立成本。

### 可执行入口完整源码

```rust
use evidence_lab::{report, sum_bytes, warm};
use std::hint::black_box;
use std::time::Instant;

fn main() {
    let bytes: Vec<u8> = (0..=255).cycle().take(1_048_576).collect();
    let expected = bytes.iter().fold(0_u64, |sum, byte| sum + u64::from(*byte));
    let case = if cfg!(feature = "checked") {
        "checked"
    } else {
        "default"
    };
    warm(|| {
        assert_eq!(sum_bytes(black_box(&bytes)), expected);
    });
    let mut samples = Vec::new();
    println!(
        "unit=ns_per_byte;case={case};bytes={};checksum={expected}",
        bytes.len()
    );
    for round in 0..21 {
        let start = Instant::now();
        let value = sum_bytes(black_box(&bytes));
        let ns = start.elapsed().as_secs_f64() * 1e9 / bytes.len() as f64;
        assert_eq!(value, expected);
        samples.push(ns);
        println!("raw,{case},round={round},value={ns:.6},checksum={value}");
    }
    report(case, &samples);
    println!(
        "layout,Vec_u8,size={},align={}",
        std::mem::size_of::<Vec<u8>>(),
        std::mem::align_of::<Vec<u8>>()
    );
    println!(
        "layout,slice_u8,size={},align={}",
        std::mem::size_of::<&[u8]>(),
        std::mem::align_of::<&[u8]>()
    );
}
```

### 类型与布局观察

| 类型 | 本轮size | 本轮align | 计时关系 |
|:--|--:|--:|:--|
| Vec&lt;u8&gt; | 24 | 8 | 输入在计时前分配 |
| &amp;[u8] | 16 | 8 | 每批传入借用视图 |
| Event | 16 | 8 | checked路径逐字节临时构造 |

Vec本体不是1MiB输入的全部内存。
它拥有的缓冲长度为1048576字节。
两版本读取同样长度和内容。

### 本轮运行结果

来源为`feature-default.txt`与`feature-checked.txt`。
单位ns/聚合byte。
每个进程预热至少500ms，然后21批。

| 配置 | mean | N-1 sd | 批均值p50 | 批均值p99 |
|:--|--:|--:|--:|--:|
| default | 0.042857 | 0.002920 | 0.041763 | 0.052094 |
| checked | 0.225888 | 0.005934 | 0.222644 | 0.245054 |

两者checksum均为133693440。
小于1ns/byte是大块聚合吞吐倒数，不是一次函数调用延迟。
本轮先运行default进程，再运行checked进程。
未做跨二进制逐轮配对，因此仍有顺序漂移限制。

### 真实代码生成支持的解释

两种feature的MIR、LLVM IR与`.s`均实际保留。
默认产物中可见向量加载、表重排与宽化累加路径。
checked产物中可见逐字节加载和Event栈存储屏障。

| 边界 | 默认配置 | checked配置 |
|:--|:--|:--|
| 求和主循环 | 实际存在向量化路径 | 实际为逐字节循环 |
| Event | 没有逐字节Event观察 | stp保存字段，空内联汇编屏障 |
| 输出 | u64求和返回 | 相同u64求和返回 |
| ABI承诺 | 仅本轮Rust产物 | 不是稳定FFI布局 |

这支持“feature改变了优化后工作形状”。
没有测PMU向量指令数或缓存事件。
不能根据汇编存在就报告硬件吞吐达到理论峰值。

### 描述性预算门禁

`tools/gate.py`检查原始21轮、单位与checksum。
再比较候选均值与基线均值。
预算默认20%，这是教学夹具的明确策略，不是统计显著性检验。

```text
通过条件：candidate_mean / baseline_mean <= 1 + budget
```

本轮checked被拒绝，进程退出码为1。
记录在`gate-rejection.json`。
缺失样本或格式/校验不一致则退出码为2。
不完整证据不会被当作零耗时通过。

### 门禁的核心契约

```python
def compare(baseline, candidate, budget):
    if budget < 0:
        raise ValueError("budget must be nonnegative")
    if (baseline["unit"] != candidate["unit"]
            or baseline["checksum"] != candidate["checksum"]):
        raise ValueError("unit or correctness evidence differs")
    ratio = candidate["mean"] / baseline["mean"]
    return {"ratio": ratio, "budget": budget,
            "pass": ratio <= 1 + budget,
            "scope": "local workload only; no statistical significance or SLA claim"}
```

完整解析、CLI与错误路径在真实源文件中提供。
没有用正文伪代码冒充已测试工具。

### 实际失败测试

Python测试验证三个不同拒绝理由。
真实checked结果超过预算时必须拒绝。
只给20轮候选时必须拒绝。
checksum不同，即使候选更快也必须拒绝比较。

这些测试没有把纳秒数硬编码进Rust单元测试。
它们用实际归档验证本轮门禁行为。
换一轮归档时，应明确更换测试输入，而不是悄悄覆盖旧结果。

## 14.6 PGO：训练数据也是构建输入 {#sec-cpp-rust.4.14.6}

### 本轮状态

本轮阅读了rustc的PGO官方说明。
没有生成profraw或profdata。
没有运行带profile-use的程序。
没有报告PGO加速或退化数字。

下面讨论可执行流程的责任划分。
它不是本轮已经完成的实验。
PGO也不是本章两项实测benchmark之一。

### 四个阶段必须分开

1. 生成带采集插桩的程序。
2. 用训练输入运行该程序。
3. 用匹配的llvm-profdata合并数据。
4. 用合并数据重新编译并验证最终程序。

训练版墙钟不是最终优化版墙钟。
插桩自身会改变执行成本。
最终性能仍需要未插桩的对照运行。

### 训练集合决定优化偏好

PGO可以影响内联、布局和其他优化决策。
训练分布偏向某类输入，会给编译器相应的路径信息。

如果训练只覆盖成功短请求，失败路径可能缺少代表性。
如果上线流量变化，训练所得布局也可能不再合适。
因此PGO不是“让所有输入都更快”的保证。

### 训练与验证输入分离

训练集用于生成优化依据。
留出集用于检查对未参与训练输入的效果。
正确性测试还应覆盖错误与边界情况。

训练集过拟合在性能工程中同样有害。
只展示训练输入上的最好均值，会高估实际收益。
应保留每类输入的指标和总体权重。

### feature、target和编译选项要一致

训练与使用阶段应尽量保持相同源码与关键标志。
只有profile-generate与profile-use按流程替换。
如果同时改feature、目标CPU和业务逻辑，就难以解释数据匹配。

官方说明建议使用绝对路径。
Cargo可能在不同工作目录调用rustc。
相对profdata路径会导致查找失败或使用错误数据。

### build脚本不应该混进训练语料

把RUSTFLAGS应用到所有host构建工具，可能产生额外采集文件。
官方Cargo流程使用显式--target来隔离host构建脚本的相关标志作用。

这不是说--target提供了沙箱。
它只是构建域区分的一部分。
仍应核对实际编译命令和数据文件来源。

### 有条件的流程示例

以下是供具备匹配llvm-profdata环境的读者使用的流程设计。
目录要求新建，避免混入旧训练数据。
本轮没有执行这些命令。

```bash
# 从cpp-rust/执行；LLVM_PROFDATA必须指向匹配工具链的真实工具。
set -euo pipefail
: "${LLVM_PROFDATA:?set the matching llvm-profdata executable path}"
ROOT="$PWD/bench/evidence-lab"
TRAIN="$ROOT/results/my-pgo-training"
mkdir "$TRAIN"
mkdir "$TRAIN/raw"
TARGET=aarch64-apple-darwin
RUSTFLAGS="-Cprofile-generate=$TRAIN/raw" \
  cargo build --offline --locked --release --target "$TARGET" \
  --manifest-path "$ROOT/Cargo.toml" --bin feature_work \
  --target-dir "$TRAIN/generate"
"$TRAIN/generate/$TARGET/release/feature_work"
"$LLVM_PROFDATA" merge -o "$TRAIN/merged.profdata" "$TRAIN/raw"
RUSTFLAGS="-Cprofile-use=$TRAIN/merged.profdata -Cllvm-args=-pgo-warn-missing-function" \
  cargo build --offline --locked --release --target "$TARGET" \
  --manifest-path "$ROOT/Cargo.toml" --bin feature_work \
  --target-dir "$TRAIN/use"
"$TRAIN/use/$TARGET/release/feature_work"
```

这个固定1MiB求和程序训练分布很窄。
即使流程成功，也不能代表网络服务或数据库负载。
示例没有伪造留出集，更没有用同一输入冒充独立泛化评估。

### missing-function警告与数据陈旧

编译器可能找不到某函数对应的训练数据。
默认不一定给出足够醒目的警告。
官方说明建议启用相关missing-function警告。

警告缺席也不是训练充分的证明。
某个存在数据的函数仍可能只见过一种输入。
需要结合训练覆盖和业务分布检查。

### PGO产物的归档

至少保留训练程序指纹、输入清单、运行参数和原始profraw。
合并工具版本、合并命令与profdata指纹也要保留。
最终程序和未PGO基线应有各自身份。

不要只缓存一个名为latest.profdata的可变文件。
它会让发布无法回答“这次用了哪一轮训练”。
性能回退时也很难区分源码变化与训练变化。

### 是否值得用PGO

要综合最终运行收益、构建成本、训练成本和维护风险。
低频运行的小工具可能难以摊薄复杂流程。
长期运行的大程序也需要留出与回退策略。

本轮没有收益数据，所以不做启用建议。
本章给出的是证据要求，而不是默认开启所有优化的清单。

## 14.7 CI：先验证证据，再比较数字 {#sec-cpp-rust.4.14.7}

### CI成功不等于性能成立

普通共享runner会受其他工作影响。
虚拟化、动态频率、缓存命中和镜像更新都可能改变结果。

CI很适合执行功能测试和静态检查。
正式性能门禁则需要更严格的执行域与基线策略。
不能把一次共享runner的微小均值变化当作发布事故。

### 分层门禁

第一层检查工程能否构建、格式化和通过测试。
第二层检查证据是否完整、单位是否一致、输入是否相同。
第三层比较性能预算。
第四层在需要时安排独立重跑与人工裁决。

前一层失败，后一层不应伪造成功。
尤其不能在benchmark崩溃后使用空列表均值零。

### 证据有效性与性能失败不同

| 状态 | 本轮工具行为 | 发布解释 |
|:--|:--|:--|
| 21轮齐全且预算内 | gate退出0 | 仅本地描述性比较通过 |
| 有效但超预算 | gate退出1 | 候选成本超策略阈值 |
| 样本缺失或单位/校验错误 | gate退出2 | 证据不可比较 |
| 构建或测试失败 | 命令非零停止 | 不进入性能比较 |

把这些状态压成“红灯”会丢掉修复方向。
保留机器可读结果与错误原因更有用。

### 本轮小门禁没有检查的字段

gate.py只检查样本结构、单位、checksum与均值预算。
它没有自动比较CPU型号、工具链或输入指纹。
没有自动保证候选与基线来自同一采样协议。

因此它是教学夹具，不是完整生产发布服务。
正式集成应在调用它之前验证证据manifest。
环境不一致应阻塞或转入明确的人工评估。
不能因为脚本有fail-closed分支就声称所有证据都已验证。

### 性能预算应与风险匹配

20%在这里用于让显著的构造回退可观察。
它不是建议所有工程允许20%退化。

业务可用预算可能包含：

- 吞吐下降上限。
- 内存峰值上限。
- 真实请求尾延迟预算。
- 构建与发布窗口。
- 二进制大小或冷启动限制。

这些指标不能由一张ns/byte表替代。
多个预算之间也可能冲突。
需要明确谁有权作取舍。

### 避免自动重跑直到变绿

只保留最好一次结果会形成选择偏差。
“红了就再跑，绿了就停”不是可靠门禁。

预先规定重跑次数与合并方式。
保留所有轮次，并说明触发重跑的原因。
若基础设施故障明确，应将故障证据与排除记录一起保存。
不要静默覆盖旧输出目录。

### 配对与独立重跑

同一轮交替基线与候选有助于降低漂移影响。
另一天或另一执行者独立重跑有助于发现流程依赖。
二者解决不同问题。

本轮构建profile进行了轮转。
feature二进制尚未做跨进程配对轮转。
本轮也没有第二个独立执行者。
这些限制不会因为测试全绿而消失。

### 置信区间与p值的边界

本轮只给描述性均值、N-1标准差和分位数。
没有计算置信区间或p值。
也没有把21次视为严格独立同分布的生产样本。

将来加入统计检验，应先说明模型、依赖性和多重比较策略。
显著性不能替代实际预算。
极小但稳定的变化，未必有业务意义。
巨大但高噪声的变化，也值得排查。

### CI缓存与证据归档分离

缓存可以加速编译。
正式build benchmark则必须注明是否命中缓存。
如果比较的是fresh目标目录，不应悄悄恢复一份target缓存。

证据目录使用新名字并拒绝覆盖。
原始文件应该能在CI作业过期后继续定位。
缓存淘汰策略不应决定审计证据是否存在。

## 14.8 从实验包到发布责任链 {#sec-cpp-rust.4.14.8}

### 本实验包的测试责任

Rust测试覆盖输出等价、空输入与非整块输入。
样本验证测试覆盖缺失、NaN和零值。
分位数测试确认21条nearest-rank p99为最大值。

Python测试覆盖实际feature回退拒绝和错误证据拒绝。
文档示例通过doctest。
这些都是具体而有限的契约测试。

它们不覆盖Cargo实现全部状态。
也不覆盖操作系统所有调度交错。
本章没有把测试数量当成覆盖完整性的替身。

### 实际命令清单

本轮离线执行成功。

命令结果不能表述为独立技术审计。

### 构建产物与采样产物的关联

第13章sample使用正式默认构建的cpu_wait。
本章保留其二进制指纹，并归档可执行文件副本。
生成代码采集在所有正式计时后进行。

因此汇编采集不会与运行计时争用编译资源。
同时也要承认它是另一次同源构建。
它不是从sample进程内存直接反汇编得到的快照。

### 原生汇编不是链接后全部视图

cargo rustc --emit=asm得到各代码生成单元的汇编。
链接器仍可能进行布局、去除与其他处理。

要研究链接后确切地址，应保留最终二进制并使用匹配工具检查。
不能拿编译单元顺序推断最后的I-cache布局。
本轮只用汇编确认路径形状，不报告I-cache或BTB命中率。

### 数据清单应该可机器核验

一个正式证据manifest应包含：

1. 唯一run id与创建时间。
2. 源码、清单与锁文件指纹。
3. 工具链、目标、profile与feature闭包。
4. 输入数据身份与计时单位。
5. 每case期望观察数与实际观察数。
6. 原始文件、统计文件与生成命令。
7. 采样运行是否进入正式统计。
8. 已知干扰、能力缺失与未执行项。

本轮这些信息分布在环境、原始行、SHA文件与说明中。
尚未做跨所有文件的签名manifest发布服务。
不应把分散记录包装成已经具备供应链认证。

### 发布时保留基线，不追随最近一次偶然结果

基线应是经过认可的特定产物与协议。
每次通过后自动把当前最好值设成基线，会改变比较含义。

基线更新应有明确原因。
例如工具链升级、硬件更换或业务输入变化。
更新时保留旧基线与迁移比较。
不要让历史回归在一次配置切换后失去可追溯性。

### 回退策略属于性能工程

候选通过微基准不保证服务整体更好。
部署还需要可回退产物与运行时观测。

回退目标应包含配置与训练数据身份。
PGO程序只回退源码、不回退profile数据，可能不是原来的程序。
feature集合变化也要纳入回退计划。

本实验不执行部署。
所以本章只定义责任，不声称已经验证发布回滚。

### 为什么不展开CMake

本章实验没有外部ABI工程。
加入无关CMake模板不会增强Cargo证据链。

真正的FFI项目应保留最小外部工程及双向测试。
它的编译器、目标和链接选项要进入同一身份清单。
CMake在这里是外部构建支持，不是另一条语言教学主线。

### 环境干扰声明

正式测量前后未见cargo/rustc/clang构建进程名。
但这只是两次快照，不是全程排他CPU保证。
目录锁只协调参与相同协议的测量者。

桌面服务、文件缓存、调度和热状态仍可能变化。
本轮没有锁核或锁频。
构建与运行结果都应限定在这个环境。

## 14.10 常见陷阱 {#sec-cpp-rust.4.14.10}

1. **只写release，不写feature与目标。**
   profile只描述部分编译设置。
   feature可以改变业务工作。
   比较前必须恢复完整身份。

2. **认为Cargo.lock锁住编译器与SDK。**
   锁文件不包含全部外部输入。
   系统库、链接器和构建脚本需要另外记录。
   本轮只承诺流程可重跑。

3. **把offline当成构建沙箱。**
   Cargo离线不等于build.rs无网络能力。
   构建脚本仍可读取外部状态。
   安全隔离需要专门机制。

4. **某条边关闭默认feature后就停止追踪。**
   其他路径仍可能启用它。
   应看统一后的图和反向路径。
   不根据顶层一行做运行归因。

5. **all-features通过就认为所有组合通过。**
   全开只是一个配置。
   最小配置与互斥条件需要独立检查。
   本包只有一个feature才简化为两种路径。

6. **把lto=false写成完全关闭LTO。**
   Cargo可能做thin local LTO。
   off与false不是同义词。
   profile表应沿用准确名称。

7. **更多CGU必然缩短编译。**
   小包的固定成本可能更重要。
   本轮one实际比release更快。
   不为了符合口号改写结果。

8. **把新target称为完全冷缓存。**
   标准库、工具链和OS缓存仍在。
   缓存边界必须精确命名。
   不删除全局缓存制造未经协调的负载。

9. **noop快就认为重新编译也快。**
   noop主要检查已有产物。
   它与fresh和增量修改是不同case。
   本轮分别保存21条。

10. **把Mach-O虚拟段总和当下载体积。**
    __PAGEZERO不是同等磁盘占用。
    文件字节与__text分别报告。
    不把4GiB零填充写成实际二进制大小。

11. **哈希不同就断言机器码性能不同。**
    元数据也能导致差异。
    本轮没有完整归因所有差异字段。
    哈希首先是身份，不是性能指标。

12. **用训练版计时宣称PGO收益。**
    插桩版是收集数据的程序。
    最终profile-use产物必须独立比较。
    留出集也不能省略。

13. **门禁失败就自动重跑到通过。**
    这会引入选择偏差。
    应预先规定重跑策略并保留全部结果。
    原始目录不得覆盖。

14. **证据缺失当作零耗时。**
    缺失样本应是错误状态。
    本轮门禁会拒绝20轮候选。
    正确性不一致也不能进入速度比赛。

15. **把本地阈值检验说成统计显著。**
    gate只做描述性预算比较。
    本轮没有p值或置信区间。
    通过也不是生产SLA。
