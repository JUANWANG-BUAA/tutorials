## 14.1 构建身份不是一个版本号 {#sec-cpp-rust.4.14.1}

本节回答一个问题：**「同一个提交」到底锁住了什么，又漏掉了什么？**1.8 要求结论绑定条件（[@def-1.8.1]）；这一节把「条件」落到构建上：源码提交、依赖解析、feature 闭包、工具链与最终二进制是四层不同的身份，每一层都能单独改变产物。身份记不全，后面的门禁数字比较的可能就不是同一个程序。

::: preview 先抓住一件事

`Cargo.lock` 记录的是**一次依赖解析的结果**，离**构建输入的全集**还差好几层。同一提交、同一锁文件，仍然可能编出执行了不同工作的程序：feature 决定哪些代码路径被编译进去，目标平台决定选哪些依赖与系统库，构建脚本读到的外部状态根本不进锁文件。[@def-14.1.1] 的意义，是把「我以为两边相同」换成「我逐层记下哪些相同、哪些没记」。
:::

### 14.1.1 源码提交只是输入的开头

源码提交只描述仓库内的一部分输入。条件编译、工具链、依赖解析和外部工具会共同决定产物。同一提交启用不同 feature，可以编出不同业务路径；同一 `Cargo.lock` 换目标平台，也可能选择不同依赖与系统库。

所以性能比较的第一步是记录程序身份，计时排在它后面。记下身份的用意在于让比较真的有「同一个问题」的含义，这正是第 1 章[@def-1.1.3]实验契约里「外部条件」那一组的构建侧版本。

本章 14.5 会真跑到这个情形：默认版本不记录逐字节审计，候选版本记录，两者输出都正确，但执行的工作不同（见[@ex-14.1.1]）。门禁应能发现成本差异，同时说明功能差异，不能只把候选版本标成「编译器退化」。

::: def 定义 14.1.1 · 构建身份 build identity {#def-14.1.1}

**构建身份**指「共同决定这一次产物的一整组输入及其派生物」：源文件、清单与锁文件；包选择、feature 闭包、目标平台与 profile；rustc/Cargo 版本、标准库、链接器、SDK 与构建脚本的外部输入；对象、IR、调试信息与链接产物；最终二进制指纹、运行输入、环境与原始观察。**记全**的标准是事后能指认到具体文件或具体命令输出，而不是「我们一直用 stable」。
:::

按[@def-14.1.1]，身份是分层的，一行版本号装不下它。下一小节把层画出来。

读图：自上而下是「输入 → 选择 → 工具 → 中间产物 → 最终产物与观察 → 裁决」。前三层大多能写进 CI 配置，后三层只有工具链和运行时自己知道。右侧五句红字标出五个真实断点：feature 闭包（[@def-14.2.1]）、工具链与 SDK、构建脚本的外部读取（[@def-14.3.2]）、链接元数据导致的字节差异（[@ex-14.3.1]）、以及数字只在本次环境成立（[@def-1.8.2]）。最底下那条绿框是发布裁决：它只消费上面五层留下的证据，不会自己发明证据——这和[@def-1.7.2]「证据不足就不放行」是同一条纪律。

### 14.1.3 至少记录的构建字段

[@def-14.1.1] 落到操作上，就是一张「层 / 记了什么 / 还证明不了什么」的对照表。第三列和[@def-1.8.1]里「每个文件能复核什么问题」是同一个思路：证据只支持它能支持的那句话。

| 层 | 本轮记录 | 不足以单独证明的东西 |
|:--|:--|:--|
| 源码 | Rust、脚本、清单、锁文件SHA256 | 正确性与可信来源 |
| 编译器 | rustc -Vv完整输出 | 链接器与SDK完全相同 |
| Cargo | cargo -V、实际命令 | feature闭包完全一致 |
| 配置 | profile、CGU、LTO、incremental | 所有环境覆盖都已消失 |
| 目标 | aarch64-apple-darwin | CPU固定频率与核绑定 |
| 产物 | 二进制大小和SHA256 | 位级可复现构建 |
| 执行 | 输入长度、checksum与21条观察 | 生产请求分布 |

::: def 定义 14.1.2 · 产物指纹 artifact fingerprint {#def-14.1.2}

**产物指纹**指对最终二进制求的哈希（本轮用 SHA256）加上文件大小。它是**身份检查**：回答「这是不是同一个对象」。它不回答「业务代码是否不同」「运行是否更慢」——路径、调试信息、链接顺序和时间戳都能改变字节而不改变语义（[@def-14.3.1]）。
:::

[@def-14.1.2] 只用于「相同 / 不同」两种判断。按它，哈希相同可以支撑「两次构建拿到同一份产物」；哈希不同只支撑「字节不同」，后面的推论都要另找证据。

### 14.1.4 工具链锁定的范围

工程通常可以在包内使用 `rust-toolchain.toml` 固定工具链。还应记录实际执行的 rustc 版本，而不只相信配置文件存在：离线环境可能缺少所指定工具链，自动下载行为也会改变构建可用性与时间边界。

本轮没有新增工具链覆盖文件，使用现有已安装的 stable 工具链，并记录其完整版本。这样共享环境保持原样，也没有假称锁定了未安装的组件。已观察版本为：

```text
rustc 1.99.0 (b940084d7 2026-09-28)
commit-hash: b940084d7eb6a299eb4bfeb8e34901bc051e7ac4
host: aarch64-apple-darwin
LLVM version: 23.1.1
cargo 1.99.0 (5f94df478 2026-08-27)
```

这不是未来版本兼容承诺。升级后应重新检查编译选项、代码生成与统计基线——工具链升级本身就是[@def-1.7.3]意义上的新实验条件，不能沿用旧基线的均值。

### 14.1.5 `--locked`、`--offline` 与 `--frozen` 的不同责任

::: def 定义 14.1.3 · 三个旗标的责任 flag scope {#def-14.1.3}

`--locked` 要求沿用锁文件，不允许悄悄更新解析；`--offline` 限制 Cargo 只用本地可用资源；`--frozen` 把前两者组合起来。三者都**不是**沙箱：一个 `build.rs` 仍可能读取外部文件或运行任意工具，也都不承诺网络隔离、供应链审计或位级确定性。
:::

按[@def-14.1.3]，本轮采用显式 `--offline --locked`，好处是读者能同时看到两份责任各自由哪个旗标承担，而不是被一个 `--frozen` 糊成一个词。

::: ex 例 14.1.1 「输出都正确」为什么仍不能进同一张性能表 {#ex-14.1.1}

默认配置与 `checked` 配置（14.2 给出契约）都只用安全 Rust，返回同一个 `u64` 求和值，本轮 checksum 都是 133693440。请用[@def-14.1.1]判断：它们是不是同一个被测程序？该记在哪一层？

::: sol 解答

不是同一个程序，但差别不在第一层。源码、清单、锁文件完全相同（① 相同）；差别出现在[@def-14.1.1]的第二层——feature 闭包不同，于是条件编译把逐字节 `Event` 观察编译进去了（③ 的代码生成也随之不同）。checksum 相同只说明**输出语义**相同，不说明**执行的工作**相同；这正是第 1 章[@def-1.3.1]要区分观察集合的原因。结论：可以把它们比，但必须先声明这是「feature 造成的工作差异」，不能报成编译器退化（14.5 节用门禁把这句话写成了机器可读的形式）。
:::

:::

### 14.1.6 正确性先于性能可比较性

输出错误的候选程序即使更快，也不能通过性能发布。checksum 只是一种有限观察，不是完整语义证明；还需要边界输入、错误输入和契约测试。本实验的简单求和有直接参考实现，空输入和非整块长度也经过测试（14.8 节的测试责任清单），这比只看一个大输入的成功退出更可靠。这条顺序和[@def-1.7.2]表里「正确性失败 → 不进入性能判断」完全一致。

::: think 思考 · 只记 `rustc -Vv` 和 `cargo -V` 够不够 {#think-14.1.1}

某团队把构建身份简化成两行版本号，理由是「我们的包没有第三方依赖」。按[@def-14.1.1]，这个推理漏了什么？

::: sol 解答

漏了「没有依赖不等于没有输入」。零第三方依赖仍然有 feature 闭包、profile 与显式 `RUSTFLAGS`、目标三元组、SDK 与链接器版本，以及构建脚本（如果有）读到的外部状态。版本两行只覆盖第三层的一部分。本轮 `checked` 反例（[@ex-14.1.1]）恰好证明：源码与依赖一字未动，仅 feature 不同就能改变执行的工作。至少还要记的是[@def-14.1.3]那三个旗标实际用了哪几个、以及[@def-14.1.2]的产物指纹。
:::

:::

::: method 判定流程 · 两份产物什么时候能放进同一张比较表

**第一步**核对第一层：源码、清单、锁文件指纹是否逐项相同（[@def-14.1.2] 的哈希在这里才是决定性的）。<br>
**第二步**核对第二层：feature 闭包、profile、target 是否相同；不同就改写成「这是配置差异」，不许写「编译器差异」。<br>
**第三步**核对第三层：rustc/Cargo 完整版本、链接器与 SDK、`RUSTFLAGS` 与 wrapper 是否清空（[@def-1.1.3]的外部条件）。<br>
**第四步**核对观察：单位、输入长度、checksum 与批次定义一致吗；不一致先修契约再比数字（[@def-1.3.1]）。<br>
**任何一步不确定**：按[@def-1.7.2]第三态处理——记为证据不足，补记录或独立重跑，「大概一样」这类判断进不了这张表。
:::

### 14.1.7 小结与常见错误

**小结。**① 构建身份是分层的输入全集，不是一行版本号（[@def-14.1.1]）；② 产物指纹只做身份检查，哈希不同推不出性能不同（[@def-14.1.2]）；③ `--locked`、`--offline`、`--frozen` 各有责任，都不是沙箱（[@def-14.1.3]）；④ 输出正确不等于工作相同，比较前要说清差异属于哪一层（[@ex-14.1.1]）；⑤ 正确性先于可比较性，与[@def-1.7.2]同一顺序。下一节[14.2 Feature 图](#sec-cpp-rust.4.14.2)处理其中最容易变的一层：feature 闭包。

::: errata 常见错误清单（14.1 节）

E-a **把「同一提交」当成「同一程序」。**feature、目标与工具链都在提交之外（[@def-14.1.1]）。

E-b **只写 `cargo -V`，不记实际命令与 `RUSTFLAGS`。**旗标与覆盖都是输入（[@def-14.1.3]）。

E-c **相信 `rust-toolchain.toml` 存在就等于锁定了工具链。**要记实际执行的 rustc 输出（14.1.4）。

E-d **哈希不同就宣布机器码变慢。**指纹只证明字节不同（[@def-14.1.2]）。

E-e **两边 checksum 相同就认为测的是同一份工作。**观察集合仍然不同（[@ex-14.1.1]）。

E-f **用 `--frozen` 一词代替三份记录。**组合旗标不告诉你每项责任由谁承担（[@def-14.1.3]）。

## 14.2 Feature图：相加的能力与隐藏的工作 {#sec-cpp-rust.4.14.2}

本节回答一个问题：**feature 到底改变了什么，为什么「release 构建」这句话不够用？**14.1 把身份分成六层（[@def-14.1.1]），本节专门处理最容易被忽略的第二层：feature 闭包。它是编译输入，不是运行时的开关；而在真实依赖图里，「谁启用了什么」通常不写在顶层清单上。

::: preview 先抓住一件事

feature 改变的是**被编译进去的工作**，不是日志详细程度。本章的 `checked` 就是一个反例：默认配置与 `checked` 配置返回完全相同的求和值，`checked` 却为每个字节多构造一个被观察的值（[@ex-14.1.1]）。于是「同一份 release 二进制」这个说法必须升级成「同一份 release 二进制 + 同一个 feature 闭包」。
:::

### 14.2.1 feature 是编译输入，不是运行配置文件

::: def 定义 14.2.1 · feature 闭包 feature closure {#def-14.2.1}

**feature 闭包**指「从本次构建的包出发，沿依赖边一路传递下来、最终实际生效的全部 feature 集合」。它由你显式请求的 feature、各依赖边的 `default-features` 设置，以及 Cargo 对同一依赖的**统一**规则共同决定，不等于清单里写了哪几行。
:::

feature 通常通过条件编译启用代码或可选依赖，因此它会改变实际编译出的路径。运行时环境变量不能自动关闭已经编译进去的所有行为——这一点和[@def-1.3.1]的观察集合直接相关：条件编译决定的是「哪段代码参与执行」，屏障决定的只是「执行结果是否被看见」。

所以性能报告应写明确切 feature 集合。「release 构建」并不足够：同一 release profile 可搭配完全不同的 feature 闭包（[@def-14.2.1]）。

### 14.2.2 Cargo 通常统一同一依赖的 feature 请求

一个依赖被多条路径引用时，相关请求通常取并集。某条边写 `default-features = false`，不会撤销其他边启用的默认 feature。

下面是一张概念图，用来看结构；本轮那份零依赖实验的实际依赖图比它简单。

```text
service -> parser(default-features=false)
service -> plugin -> parser(default feature enabled)

parser的相关构建单元仍可能获得default能力。
```

需要沿反向路径追踪「谁启用了它」。只检查顶层清单中的一行，往往看不出完整结果。

::: ex 例 14.2.1 那一行 default-features=false 生效了吗 {#ex-14.2.1}

读上面那张概念图：`service` 直接依赖 `parser` 并写了 `default-features = false`，同时 `service` 依赖 `plugin`，而 `plugin` 依赖 `parser` 且使用默认 feature。问：① 最终 `parser` 有没有拿到默认 feature？② 这个结果由哪个量决定（对照[@def-14.2.1]）？③ 只看 `service/Cargo.toml` 能判断吗？

::: sol 解答

① 通常会拿到：同一依赖的相关请求被统一为并集，`plugin` 那条边启用的默认 feature 仍会落到 `parser` 的构建单元上。② 决定它的是 feature **闭包**——即整个图上与该依赖相关的边的并集，而不是单条边上的一个属性（[@def-14.2.1]）。③ 不能。顶层清单只看得到自己那一行，看不到反向路径；要看 `cargo tree -e features -i parser` 这类沿入边展开的输出（14.2.5）。结论式的说法是：`default-features = false` 是**这条边的请求**，不是**全局的关闭**。
:::

:::

### 14.2.3 feature 应尽量保持相加

启用能力通常保持相加：已存在的公共接口继续可用。互斥 feature 要求所有依赖使用者协同，容易失控：任何一条边把另一个 feature 打开，闭包（[@def-14.2.1]）就落到一个没人测试过的组合上。

如果确实不能同时启用，应在编译时显式拒绝——让错误配置在构建期失败，而不是在性能表上表现为一个说不清的均值。但要先考虑拆包或运行时策略选择。不要把 feature 当成只能由顶层唯一控制的全局枚举。

### 14.2.4 resolver 也参与构建单元划分

::: def 定义 14.2.2 · 构建单元 build unit {#def-14.2.2}

**构建单元**指「同一个包在一种编译条件组合下的一份实际构建」。同一个包名出现一次，不代表它只被编译一次：host 与 target、不同 feature 闭包、不同 profile、不同目标平台都可能各自生成一份。锁文件里的**包条目数**和实际**编译次数**是两个量。
:::

resolver 2 改进了某些不应统一的情况：构建依赖与普通依赖、未构建目标的平台依赖、特定开发依赖。这种分离有时意味着同一包需要构建多份（[@def-14.2.2]）。resolver 3 还涉及 Rust 版本感知的解析行为。它不是「所有依赖永远只编译一次」的开关。

本轮独立 workspace 显式使用 resolver 3。由于无第三方依赖，本轮没有测复杂 resolver 的性能；这一句是范围声明，本节没有对应的构建时间数据。

### 14.2.5 实际检查命令

```bash
cargo tree --offline --locked \
  --manifest-path bench/evidence-lab/Cargo.toml -e features --features checked
cargo metadata --offline --locked \
  --manifest-path bench/evidence-lab/Cargo.toml --format-version 1
```

输出保存为 `feature-tree.txt` 与 `metadata.json`。实际树只有本包，没有假造额外依赖来显得复杂。`metadata` 记录包目标与清单结构。本轮文件路径属于本机，不能把它当跨机器稳定标识。

### 14.2.6 大工程中的追踪方式

对真实有依赖工程，可以增加以下检查。这些命令形状不是本轮运行结果。

```bash
# foo应替换为实际工程中的包名；这里不声称本实验存在该包。
cargo tree -e features -i foo
cargo tree --duplicates
cargo tree -f '{p} {f}'
```

重复版本与同版本不同构建单元是不同问题。后者可能来自 host/target、feature 或 profile 差异（[@def-14.2.2]）。不要只用锁文件中的包条目数量估计编译次数。

### 14.2.7 本实验的 feature 契约

::: def 定义 14.2.3 · 观察型 feature audit feature {#def-14.2.3}

**观察型 feature**指「只为实验而增加可观察工作、不改变返回值语义的 feature」。本轮的 `checked` 就属于这一类：它不是安全开关，默认版本与 `checked` 版本都只使用安全 Rust；`checked` 有意为每个字节构造一个 `Event` 并送进屏障（对照[@def-1.1.2]的 `black_box`）。它的价值是提供一个**安全且输出等价**的性能回退候选（14.5 节的对照实验）。
:::

| 配置 | 输入类型 | 返回值 | 额外工作 |
|:--|:--|:--|:--|
| default | &amp;[u8] | u64求和 | 无逐字节Event |
| checked | &amp;[u8] | 相同u64求和 | 每字节构造Event并black_box |

按[@def-14.2.3]，不能根据名字认为默认版本跳过了必要内存安全检查，也不能把 `checked` 结果解释成 Cargo 本身的运行开销——Cargo 只是选择了不同代码。这句话是[@def-14.1.1]的直接应用：差异属于第二层（feature 闭包），不属于工具链层。

### 14.2.8 测试组合不能只用 all-features

`all-features` 会测试一个并集配置。它不覆盖「没有任何可选 feature」的路径；对互斥 feature，甚至可能不是合法配置（14.2.3）。

本轮分别执行默认与 all-features 测试。本包只有一个可选 feature，所以两种配置恰好覆盖这两条路径。真实多 feature 工程需要风险驱动的组合矩阵：矩阵的规模按「哪些边会彼此放大」来定，而不是按 2 的幂来定。不要假装一次全开测试穷尽指数级组合。

### 14.2.9 文档也需要配置身份

`cargo doc` 默认展示某个 feature 集合下可达的 API。文档页存在，不意味着最小配置也有该 API——这是[@def-14.2.1]在文档层的表现。示例应注明需要的 feature 或独立编译条件。

本轮实际执行了带 `-D warnings` 的 all-features 文档构建；库里的求和示例也作为 doctest 执行。这只验证本包示例，不表示所有文档平台均通过（对照 14.8 节的测试责任清单）。

::: think 思考 · 把实验开关做成 feature 有什么副作用 {#think-14.2.1}

`checked` 用 feature 实现，好处是「默认关闭、按需打开」。按[@def-14.2.1]和[@def-14.2.2]，一旦这个 feature 被下游包引用，可能出现什么问题？

::: sol 解答

三个方向。① **统一**：下游任何一条边请求了它，同一依赖的构建单元就可能全部带上审计工作（[@def-14.2.1]），性能表里出现「没人打算启用」的成本。② **多份构建**：host/target 或不同闭包让同一包编译两次以上（[@def-14.2.2]），构建时间解释变复杂。③ **测试缺口**：CI 只跑 `--all-features`，就再没人测「不带审计」的默认路径（14.2.8）。可行的缓解是把它留在私有实验包里、不对外发布（本轮 `publish = false`），并在门禁里把 feature 闭包当成身份字段（[@def-14.1.3]）。
:::

:::

::: method 判定流程 · 报告里该写哪一句 feature 说明

**只有一个可选 feature**：写「默认」与「显式启用 X」两行，附实际命令（14.2.5 的 `cargo tree` 输出可作证据）。<br>
**多 feature、无互斥**：按风险挑组合，至少覆盖「全关」「生产实际用的那一组」「全开」，并声明其余未测。<br>
**存在互斥**：编译期显式拒绝非法组合（14.2.3），报告里说明拒绝点在哪。<br>
**结论跨配置**：先核对两边 feature 闭包一致（[@def-14.1.1]）；不一致就改写成「配置差异」，不许写「编译器差异」。<br>
**说不清闭包**：按证据不足处理（[@def-1.7.2]），先补 `cargo tree -e features` 与 `cargo metadata` 记录，再谈数字。
:::

### 14.2.10 小结与常见错误

**小结。**① feature 是编译输入，改变被编译进去的工作，不是运行配置（[@def-14.2.1]）；② 生效的是闭包，不是某一行清单（[@ex-14.2.1]）；③ `default-features = false` 只约束自己那条边；④ 同一包可能有多份构建单元（[@def-14.2.2]）；⑤ 本轮 `checked` 是观察型 feature，输出等价、工作不等价（[@def-14.2.3]）。下一节[14.3 可复现构建](#sec-cpp-rust.4.14.3)把「身份记全了」推进到「能承诺什么」。

::: errata 常见错误清单（14.2 节）

E-a **把 feature 当成运行时开关。**它决定哪些代码被编译；想用环境变量「关掉」已编译进去的行为，是在解释错对象（[@def-14.2.1]）。

E-b **顶层写了一行关闭就停止追踪。**并集在别的边上完成（[@ex-14.2.1]）。

E-c **认为同一包名只编译一次。**host/target、feature、profile 各自成一份（[@def-14.2.2]）。

E-d **用 `--all-features` 通过代替组合矩阵。**最小配置根本没测（14.2.8）。

E-e **把 `checked` 当成「加了安全检查」。**两配置都在安全 Rust 内，多的是审计工作（[@def-14.2.3]）。

E-f **用文档页存在证明 API 可达。**文档也有 feature 闭包（14.2.9）。

:::

## 14.3 可复现构建：先划清承诺级别 {#sec-cpp-rust.4.14.3}

本节回答一个问题：**「可复现」这三个字，本章的构建实验能承诺到哪一级？**14.1 记录了身份层（[@def-14.1.1]），14.2 说清了 feature 闭包（[@def-14.2.1]）；本节把「可复现」拆成三级承诺，并用本轮真实产物证明：最弱的一级成立，最强的一级**没有**成立——这不是失败，而是承诺范围的诚实表达。

::: preview 先抓住一件事

三种「可复现」互相推不出来：**流程可重跑**、**性能实验可比较**、**位级产物相同**。前两种不自动推出第三种；反过来，字节相同也不自动证明运行环境相同。发布文档必须写清自己承诺哪一级，否则一句「构建可复现」会在读者脑子里升级成最强那一档——这与[@def-1.8.2]反复强调的「复算与重跑不能互相冒充」是同一类越界。
:::

### 14.3.1 三种经常混用的「可复现」

::: def 定义 14.3.1 · 可复现的三级承诺 reproducibility levels {#def-14.3.1}

**第一级 流程可重跑**：读者能从源码与命令重新生成可运行程序。**第二级 性能实验可比较**：输入、配置与环境足以让两次结果具有共同解释，也就是[@def-1.1.3]那份契约成立。**第三级 位级产物相同**：同样输入在规定条件下产生完全相同字节。三级递进方向是「越往后越强、越难满足」，而且前两级的成立对第三级没有任何蕴含关系。
:::

按[@def-14.3.1]，本章只在第一级和第二级上给证据：14.11 的入口能让读者重建实验，14.4 与 14.5 的比较都固定了身份字段。第三级不成立，反例在 14.3.5。

### 14.3.2 锁文件锁住的不是世界

`Cargo.lock` 记录解析出的包身份与版本等信息。它没有把系统 SDK、链接器、环境变量和构建脚本外部读取全部封存。路径依赖的内容仍由工作目录决定；本地工具链也可能被替换。

一个有外部 C 库的 Rust 包还需要外部库身份。这里不需要为零依赖实验虚构 CMake 工程。若涉及 FFI，应另行固定编译器、头文件、链接选项和 ABI 测试——那句「另行」的意思是：它们要进同一张身份表（[@def-14.1.1]），而不是另一份没人核对的说明。

### 14.3.3 构建脚本是额外输入边界

::: def 定义 14.3.2 · 构建脚本的外部输入 build-script inputs {#def-14.3.2}

`build.rs` 可以读取时间、环境变量、目录内容、外部生成器和命令输出。这些读取**不进入锁文件**，也不被 `--locked`/`--offline` 约束（[@def-14.1.3]），因此是构建身份里最容易被漏掉的一层。`rerun-if-changed` 声明决定 Cargo 何时重跑它：声明不完整可能导致陈旧产物，声明过宽导致不必要重建。
:::

按[@def-14.3.2]，这两类问题都会直接污染性能比较。一个版本实际没有更新，不代表它「构建非常快」；一个版本每次都重新生成全部代码，也不代表 rustc 突然变慢。这两种误读在 14.4 的计时边界表里都会被当成独立因素处理。

本实验没有 `build.rs` 和 proc macro。这样可把构建实验范围缩小到本包编译与链接；代价是不能直接外推大型生成式工程。

### 14.3.4 路径、调试信息和链接元数据

绝对路径可能进入调试信息或对象记录；不同输出目录也可能改变链接相关元数据；平台签名与可执行格式还会增加自己的字段。

因此，比较二进制 SHA256 时应把它当身份检查（[@def-14.1.2]）：哈希不同只证明字节不同，不立即证明业务代码不同，更不证明运行性能一定不同。

### 14.3.5 本轮真实反例：三级承诺在哪一级断裂

构建矩阵为每个配置创建 21 个不同目标目录。同一配置的产物**文件大小一致**，但是 21 个 SHA256 **都不同**。

| profile | 文件大小/字节 | fresh构建数 | 不同SHA256数 |
|:--|--:|--:|--:|
| release | 518448 | 21 | 21 |
| one | 512640 | 21 | 21 |
| thin | 502672 | 21 | 21 |

这是实际记录（来源 `build-raw.jsonl` 与 `binary-sha256.txt`），不是关于所有 Rust 产物的普遍定理。本轮没有对全部差异字段作二进制归因，所以不能武断断言「全是时间戳」或「全是路径」。

::: ex 例 14.3.1 同一 profile 的 21 份产物：哪一级承诺被证伪了 {#ex-14.3.1}

上表里 `release` 一行：21 次构建产物大小同为 518448 字节，SHA256 有 21 个不同值。请按[@def-14.3.1]判断三件事：① 这证伪了哪一级承诺？② 它对另外两级是肯定还是沉默？③ 能不能据此写「性能也可能因此不同」？

::: sol 解答

① 证伪第三级：本轮设置没有产生跨这 21 个目标目录的字节相同产物，所以本章不会写「Cargo.lock 保证确定性构建」。② 对第一级沉默偏正面——21 次都能构建成功并产出同样大小的可执行文件，`verify-*.txt` 里的 checksum 也一致；对第二级不表态，因为可比较性靠的是[@def-1.1.3]那份契约（单位、输入、批次、计时边界），与字节是否相同无关。③ 不能。按[@def-14.1.2]，哈希不同只证明字节不同；第 0 轮各 profile 单独测过的那一份产物里，`__text` 按 release/one/thin 分别是 242940/241916/236656 字节（14.4.8 的表），三个 profile 本就不同；跨 21 个目标目录是否字节相同，本节没有测过——`size -m` 只在第 0 轮跑过一次，其余 20 个目录只有文件字节与哈希。

能说的只有：21 次都构建成功、同 profile 的文件字节一致而哈希互异，差异大概落在调试信息与链接元数据这类字段上，具体是哪个字段本节没有采集归因。
:::

:::

[@ex-14.3.1] 是本节最重要的一段：它示范了「实验失败也要保留」。用 `--remap-path-prefix` 或 `SOURCE_DATE_EPOCH` 把哈希修饰成一致，只是让第三级**看起来**成立。

### 14.3.6 无操作重建的另一种身份检查

每个 fresh 构建后，脚本在同一目标目录执行同一命令，没有修改源码或标志。此时 Cargo 主要检查是否已有最新产物——这就是 14.4[@def-14.4.2]定义的 noop 边界。

原始记录同时保存 fresh 与 noop 的产物 SHA256。应检查同一对记录是否一致：这能发现意外重建或产物被外部修改（[@def-14.3.2]那类陈旧产物就在这里暴露）。但它仍不是跨环境位级可复现验证（[@def-14.3.1]第三级）。

### 14.3.7 remap 与 SOURCE_DATE_EPOCH 不是魔法

路径重映射可以减少某些绝对路径泄漏；`SOURCE_DATE_EPOCH` 可以作为支持它的工具的约定输入。二者都只覆盖**愿意遵守相应机制**的组件。

外部生成器或签名工具可能有自己的行为。应先识别差异，再逐项消除。不要看到一个环境变量名字，就宣布整个流水线确定。

本轮没有用这些选项「修饰」哈希结果。保留失败的确定性假设，正是可复现研究的一部分——它与[@def-1.7.2]把「证据不足」写成第三种结论是同一个态度：不为了好看而改判定对象。

### 14.3.8 缓存键至少包含什么

::: def 定义 14.3.3 · 缓存键 cache key {#def-14.3.3}

**缓存键**指「命中即复用产物」所依据的那组字段。它至少要区分目标平台、工具链版本、锁文件、feature 闭包（[@def-14.2.1]）与关键编译标志；构建脚本的外部输入（[@def-14.3.2]）也要适当纳入。过窄的键可能复用错误产物，过宽的键失去复用价值。
:::

按[@def-14.3.3]，性能测量归档不应直接使用可被覆盖的 CI 缓存目录：缓存服务为了命中率可以驱逐或替换内容，而证据归档需要不覆盖、可定位和可核验（这与 14.7 的缓存/归档分离是同一条规则）。

::: think 思考 · 「构建可复现」写进 README 之前 {#think-14.3.1}

你要在 README 里写一行「本项目的构建是可复现的」。按[@def-14.3.1]，这句话在什么条件下可以写？写的时候还缺什么？

::: sol 解答

只有当你能指认第三级成立时才能这样写，而且要写出范围：哪台机器、哪个工具链、哪些外部输入被封存。本轮的证据只支持第一级和第二级——[@ex-14.3.1] 直接证伪了第三级。诚实的句式是：「给定同一工具链与同一锁文件，本目录的命令可重跑并得到 checksum 一致的产物；跨目录的字节相同未成立，原因未归因」。把这句交给读者，比一句「可复现」更有用，也符合[@def-1.8.1]「结论要带着它依赖的那一层」。
:::

**说不清差异来源**：本节那种「21 个不同 SHA」保留原样，写成未归因，不修饰。

### 14.3.9 小结与常见错误

**小结。**① 可复现分三级，前两级的成立对第三级没有蕴含（[@def-14.3.1]）；② 锁文件不封存 SDK、链接器与构建脚本的外部读取（[@def-14.3.2]）；③ 产物指纹是身份检查，字节不同推不出性能不同（[@def-14.1.2]、[@ex-14.3.1]）；④ noop 与 fresh 成对核对能发现意外重建（[@def-14.4.2]）；⑤ 缓存键要覆盖 feature 闭包与关键标志，证据归档不能住在可覆盖的缓存目录里（[@def-14.3.3]）。下一节[14.4 Benchmark 一](#sec-cpp-rust.4.14.4)把本节的名词变成计时边界。

::: errata 常见错误清单（14.3 节）

E-a **用「能重新构建」暗示「产物字节相同」。**两级之间没有蕴含（[@def-14.3.1]）。

## 14.4 Benchmark一：CGU、LTO与精确缓存边界 {#sec-cpp-rust.4.14.4}

本节回答一个问题：**测「构建要多久」时，怎样让这个数字有唯一含义？**第 1 章把「一个耗时数字要带哪些条件」写成了实验契约（[@def-1.1.3]）。构建计时面对同样的陷阱：一句「构建用了两秒」完全不说明重做了什么。本节先定义两种缓存边界，再给出三个 profile 的实际墙钟与体积。

::: preview 先抓住一件事

同一份代码、同一条 `cargo build`，在「全新目标目录」「已有产物的无操作重建」「改一个文件的增量重建」三种边界下是三个不同的量，量级差可以到二十倍（本节实测：新包目标目录 338–1996 ms，无操作构建约 18 ms）。所以先命名边界，再谈数字。另一个容易混的是配置语义：`lto = false` 不等于 `lto = "off"`（[@def-14.4.3]）。
:::

### 14.4.1 为什么测构建也需要实验协议

「构建用了两秒」没有说明重做了什么。可能是下载依赖、解析、编译本包，也可能只是检查已有文件；OS 页缓存（系统把最近读过的文件内容留在内存里）和预装标准库通常仍然存在。

::: def 定义 14.4.1 · 新包目标目录构建 fresh package-target build {#def-14.4.1}

**新包目标目录构建**指：每次给 Cargo 一个**不存在**的 `--target-dir`，于是本包的编译与链接工作必须重做；但源码、工具链、标准库和操作系统缓存**都已经存在**。本轮不使用「完全冷构建」这个名称——真正的冷缓存意味着工具链与系统缓存也一并消失，本轮没有制造那种条件。
:::

按[@def-14.4.1]，本节所有 fresh 数字都只支持「本包工作重做一遍需要多久」，不支持「从零开始的机器需要多久」。这个命名纪律和第 1 章「估计对象」（[@def-1.1.3]）是同一件事。

### 14.4.2 第二种边界：无操作构建

::: def 定义 14.4.2 · 无操作构建 noop build {#def-14.4.2}

**无操作构建**指：在**同一个**目标目录、**同一条**命令、源码与标志都没有改动的前提下再跑一次。此时 Cargo 主要做的是检查是否已有最新产物。它测的是「判断要不要重建」的成本，不是重建成本本身；也不等于修改一个源文件后的增量构建——本轮没有测第三种。
:::

按[@def-14.4.2]，14.3.6 的成对身份检查正是靠这两种边界配合：fresh 留下产物，noop 复查「有没有被意外重建」（[@def-14.3.2]）。

### 14.4.3 三种实际 profile

以下是完整 `Cargo.toml`。它不是上层共享 bench 清单的修改；独立 workspace 避免影响其他实验包。

```toml
[package]
name = "evidence-lab"
version = "0.1.0"
edition = "2024"
publish = false

[workspace]
resolver = "3"

[features]
default = []
checked = []

[profile.release]
debug = 1
incremental = false
codegen-units = 16
lto = false

[profile.one]
inherits = "release"
codegen-units = 1

[profile.thin]
inherits = "release"
codegen-units = 1
lto = "thin"
```

release 保留有限调试信息；one 只改 CGU 数量；thin 在 one 基础上显式启用跨 crate ThinLTO。本轮没有测试 fat LTO。

::: def 定义 14.4.3 · 代码生成单元与 LTO 档位 CGU and LTO settings {#def-14.4.3}

**代码生成单元（codegen unit，CGU）**是编译器把 crate 内部切开并行处理的粒度：单元多，单件工作小、可并行，但跨单元的优化视野变窄；单元为 1，视野最大，串行压力也最大。**LTO 档位**分三种写法：`lto = false` 允许对本地 crate 的 CGU 做 thin local LTO（Cargo Profiles 文档；`codegen-units = 1` 或 `opt-level = 0` 时不执行这类本地 LTO），`lto = "thin"` 显式启用跨 crate ThinLTO，`lto = "off"` 才是关闭。`false` 与 `"off"` 不是同义词。
:::

按[@def-14.4.3]，上表里的 `release` 不能命名为「绝无 LTO」；`one` 也不仅是把同一优化任务平均分成一份——CGU 划分会影响代码组织与优化机会。这句话决定了 14.4.6 的读表方式。

### 14.4.4 计时边界

::: def 定义 14.4.4 · 构建墙钟的计时边界 build wall-clock boundary {#def-14.4.4}

本轮的墙钟 = 一次完整 `cargo build` 子进程从启动到退出的时间。进入它的有：Cargo 启动与检查、本包编译、链接、`-vv` 详细日志写入；不进入的有：标准库与 rustc 的构建（预先安装）、下载（`--offline` 且无第三方依赖）、产物大小与 SHA256 的读取（命令结束后）、correctness 运行（每 profile 第 0 轮单独执行）。对照第 1 章[@def-1.2.1]的「哪些区间算进耗时」，这是同一个问题在构建侧的版本。
:::

| 项目 | 本轮设置 | 是否进入墙钟 |
|:--|:--|:--|
| Cargo启动、检查、编译与链接 | 每次subprocess运行 | 是 |
| 目标目录 | 每profile每轮新建 | fresh路径不存在 |
| 标准库与rustc | 预先安装 | 不重新构建 |
| 下载 | offline，且无第三方依赖 | 无下载工作 |
| 编译并发 | -j1 | 不与其他case并行 |
| 增量 | CARGO_INCREMENTAL=0 | 关闭 |
| 详细日志 | -vv写本地文件 | 是，所有case一致 |
| 大小与SHA256读取 | 命令结束后 | 否 |
| correctness运行 | 每profile第0轮产物 | 否 |

`-j1` 限制 Cargo 调度的作业数量。它不能被解释成编译器内部所有线程都只有一个：CGU 与链接阶段仍可能有自己的执行策略（[@def-14.4.3]）。这也是[@def-14.4.1]必须精确命名的原因之一——「单并发」这条约束只覆盖调度层。

### 14.4.5 第四项 benchmark 的完整驱动

完整文件为 `tools/build_matrix.py`。

```python
#!/usr/bin/env python3
"""Fresh package-target and no-op builds, never cold OS caches."""
import hashlib
import json
import math
import os
from pathlib import Path
import statistics
import subprocess
import sys
import time

LAB = Path(__file__).resolve().parents[1]


def summary(values):
    ordered = sorted(values)
    return {"n": len(values), "mean": statistics.mean(values),
            "sd": statistics.stdev(values),
            "p50": ordered[math.ceil(.5 * len(values)) - 1],
            "p99": ordered[math.ceil(.99 * len(values)) - 1]}


def main():
    out = Path(sys.argv[1]).resolve()
    root = out / "builds"
    root.mkdir()
    observations = []
    env = os.environ.copy()
    for name in ("RUSTFLAGS", "CARGO_ENCODED_RUSTFLAGS",
                 "RUSTC_WRAPPER", "RUSTC_WORKSPACE_WRAPPER"):
        env.pop(name, None)
    env["CARGO_INCREMENTAL"] = "0"
    profiles = ["release", "one", "thin"]
    subprocess.run(["rustc", "-Vv"], check=True,
                   stdout=subprocess.DEVNULL)
    with (out / "build-raw.jsonl").open("x") as raw:
        for round_id in range(21):
            for offset in range(3):
                profile = profiles[(round_id + offset) % 3]
                target = root / f"{profile}-{round_id:02}"
                command = ["cargo", "build", "--offline", "--locked",
                           "--manifest-path", str(LAB / "Cargo.toml"),
                           "--profile", profile, "--bin", "feature_work",
                           "--target-dir", str(target), "-j", "1", "-vv"]
                for boundary in ["fresh-package-target", "noop"]:
                    log = out / f"build-{profile}-{round_id:02}-{boundary}.txt"
                    with log.open("x") as stream:
                        start = time.perf_counter_ns()
                        subprocess.run(command, check=True, env=env,
                                       stdout=stream, stderr=stream)
                        elapsed_ms = (time.perf_counter_ns() - start) / 1e6
                    binary = target / profile / "feature_work"
                    content = binary.read_bytes()
                    row = {"case": f"{profile}/{boundary}", "round": round_id,
                           "wall_ms": elapsed_ms, "binary_bytes": len(content),
                           "binary_sha256": hashlib.sha256(content).hexdigest(),
                           "command": command}
                    raw.write(json.dumps(row) + "\n")
                    raw.flush()
                    observations.append(row)
                if round_id == 0:
                    result = subprocess.run(["size", "-m", str(binary)],
                                            check=True, capture_output=True,
                                            text=True)
                    (out / f"size-{profile}.txt").write_text(result.stdout)
                    result = subprocess.run([str(binary)], check=True,
                                            capture_output=True, text=True)
                    (out / f"verify-{profile}.txt").write_text(result.stdout)
    cases = sorted({row["case"] for row in observations})
    result = {case: summary([row["wall_ms"] for row in observations
                            if row["case"] == case]) for case in cases}
    (out / "build-summary.json").write_text(json.dumps(result, indent=2) + "\n")
    print(json.dumps(result, indent=2))


if __name__ == "__main__":
    main()
```

| profile / 边界 | mean | sd | p50 | p99 |
|:--|--:|--:|--:|--:|
| release / 新包目标目录 | 439.733 | 68.274 | 416.813 | 646.793 |
| one / 新包目标目录 | 338.194 | 10.053 | 334.800 | 360.113 |
| thin / 新包目标目录 | 1995.882 | 68.582 | 1972.251 | 2216.728 |

::: ex 例 14.4.1 「one 比 release 快 101 ms」能写成结论吗 {#ex-14.4.1}

看[@def-14.4.4]口径下的两个 fresh 均值：release 439.733（sd 68.274）、one 338.194（sd 10.053）。请回答：① 这个差是配对差值吗？② 设计里有没有可用的配对单位？③ 按[@def-1.7.2]，现在该写哪一句话？

① 不是。表里给的是两个 case 各自的批均值与各自的 sd，属于第 1 章[@def-1.4.1]提醒过的「独立分组」读法，时间条件的一部分会被误算进实现差异。② 有：驱动脚本每一轮都构建三个 profile，起点顺序按轮旋转，所以「同一轮」就是天然的配对单位——这是[@def-14.4.5]的设计后果。③ 只能说「本轮这一批 21 轮里，one 的均值低 101.5 ms」——这个差是较大那个 sd（68.274）的 1.5 倍、较小那个（10.053）的 10 倍，两个读数都不构成可放行的方向证据。

要写成可放行的结论，需要按轮算配对差值与区间，再和事先写下的预算 B 比对（[@def-1.7.1]、[@def-1.7.2]）。**本轮没有计算配对区间**，因此这里给的是描述性比较，第三种状态按证据不足处理。

### 14.4.7 两种边界之间：20 倍的量级差

同一列 noop 的均值都在 18 ms 附近（18.194–18.713），而 fresh 是 338–1996 ms。按[@def-14.4.1]与[@def-14.4.2]，这两个数回答的是两个问题：一次真实重建，和一次「检查要不要重建」。noop 之间的差异极小，也不说明「profile 对构建速度没影响」。

::: def 定义 14.4.5 · 轮转与配对单位 rotation and pairing unit {#def-14.4.5}

驱动脚本每一轮 `round_id` 内依次构建三个 profile，起点用 `(round_id + offset) % 3` 轮换。于是**同一轮包含全部三个 case**，轮就是[@def-1.4.1]意义上的配对单位；轮换的作用是防止「总排最后的那个 profile 永远赶上机器最热的时候」。**包含配对单位不等于做了配对分析**：本轮只按 case 汇总了批均值与分位数。
:::

按[@def-14.4.5]，本节数据是「有配对结构、但只做了非配对汇总」的典型样本。这也是[@def-1.8.2]所说的能力缺失：归档里有能算配对的字段（`round`），但统计摘要没算。

### 14.4.8 实际体积

`size -m` 与文件字节数回答不同问题（对照[@def-14.1.2]）。Mach-O 的 `__PAGEZERO` 是虚拟保留区，不是同样大小的磁盘文件；不能把其 4 GiB 零填充段加到文件下载体积。

| profile | 文件字节 | __text字节 | 解释 |
|:--|--:|--:|:--|
| release | 518448 | 242940 | 固定配置的实际链接产物 |
| one | 512640 | 241916 | 本轮略小 |
| thin | 502672 | 236656 | 本轮更小但构建更久 |

代码段更小不自动意味着运行更快。本轮矩阵主要测构建与体积；`verify-*.txt` 三份各有 21 行、单位与输入都相同，形状和正式观测一样，但它们来自第 0 轮那一次额外运行——同一份产物反复跑同一输入，没有跨轮配对与随机化顺序，所以只用作 checksum 与可运行性验证，不能当 21 轮配对运行比较（[@def-1.2.2]）。这就是它们不进 273 的判据。

::: ex 例 14.4.2 用 1.5 秒构建换 3% 的代码段：这笔交易怎么写 {#ex-14.4.2}

`thin` 相对 `release`：新包目标目录均值 1995.882 ms 对 439.733 ms，`__text` 236656 字节对 242940 字节。有人说「ThinLTO 让产物更小，所以应该默认开」。请按[@def-1.7.1]与[@def-14.3.1]把这句话改写成一个负责任的结论。

::: sol 解答

先承认这是**两个预算之间的兑换**，不是一个方向的改进：构建墙钟本轮约为 4.5 倍（1995.882 ÷ 439.733），代码段约小 2.6%（236656 对 242940）。要下判断，缺三件：① 事先写下的构建时间预算 B 与体积预算（[@def-1.7.1]），二者都该来自 CI 时长与分发成本，而不是看完数字再定；② 运行性能证据——本节只测了构建与体积，**运行侧本节没有采集**；③ 结论范围（[@def-14.3.1]）：这是 `publish = false` 的单包小二进制，依赖多、构建图深时 CGU/LTO 的行为不能外推。合格的句子是：「本轮小包桌面环境下，thin 在构建时间上明显更贵、代码段略小；是否值得取决于两者的预算，运行差异未测」。
:::

### 14.4.9 预热的准确说法

运行基准都预热至少 500 ms。构建实验没有用「500 ms 空转」假装预热完整链接器；它明确依赖已安装工具链与自然变暖的文件系统缓存——这正是[@def-14.4.1]不叫冷缓存的理由。

profile 顺序按轮转改变起点（[@def-14.4.5]），仍不能完全消除时间漂移（[@def-1.4.1]）。结论限定为本轮小包和桌面系统。

::: think 思考 · 缓存键里少写 profile 会怎样 {#think-14.4.1}

某 CI 用「分支 + 提交」当构建缓存键。按[@def-14.3.3]和[@def-14.4.2]，这会带来什么后果？

::: sol 解答

同一提交的不同 profile（甚至不同 feature 闭包，[@def-14.2.1]）会命中同一份缓存目录，于是「fresh」边界被悄悄破坏：本该重做的编译被复用，测出来的是接近[@def-14.4.2]的 noop 成本，却被记成重建成本。更糟的是这种错误在数字上表现为「构建突然变快」，很容易被当成工具链改进。修法就是把目标、工具链、锁文件、feature 与关键标志全部纳入缓存键（[@def-14.3.3]），并在归档里写明本次是否命中缓存（14.7）。
:::

### 14.4.10 小结与常见错误

**小结。**① 构建计时必须先命名缓存边界（[@def-14.4.1]、[@def-14.4.2]）；② `lto = false` 不等于 `lto = "off"`，CGU 划分改变优化视野（[@def-14.4.3]）；③ 墙钟包含什么要逐项列（[@def-14.4.4]）；④ 轮内包含三个 case 只提供了配对单位，配对分析本轮没做（[@def-14.4.5]、[@ex-14.4.1]）；⑤ 文件字节、`__text` 与 `__PAGEZERO` 是三种不同的量（[@ex-14.4.2]）。下一节[14.5 Benchmark 二](#sec-cpp-rust.4.14.5)用 feature 构造一个真实回退，并让门禁拒绝它。

::: errata 常见错误清单（14.4 节）

E-a **把新目标目录叫「冷缓存」。**工具链、标准库与 OS 缓存都在（[@def-14.4.1]）。

E-b **用 noop 的 18 ms 评价 CI 构建速度。**它只证明 Cargo 检查了已有产物（[@def-14.4.2]）。

E-c **把 `lto = false` 写成「关闭 LTO」。**false 仍可做 thin local LTO（[@def-14.4.3]）。

E-d **认定 CGU 越多构建越快。**本轮 one 实测比 release 快（[@ex-14.4.1]）。

E-e **拿两个独立均值判方向。**同一轮的配对单位没有被使用（[@def-14.4.5]）。

E-f **把 `__PAGEZERO` 算进下载体积。**虚拟保留不是磁盘占用（[@ex-14.4.2]）。

E-g **用第 0 轮一次运行冒充 21 轮运行比较。**`verify-*.txt` 那 63 行是同一产物的重复可运行性校验，没有跨轮配对（14.4.8）。

## 14.5 Benchmark二：feature回退与会拒绝的门禁 {#sec-cpp-rust.4.14.5}

本节回答一个问题：**门禁要拿出什么，才能证明自己真的会拒绝一个候选？**14.4 量的是构建；本节量运行，并且故意让一个候选失败。只有让「输出正确、没有 UB、只是更贵」的候选真的被拦下，门禁才不是一句口号。

::: preview 先抓住一件事

门禁的可信度不来自「基线能通过」，而来自**一个真实会失败的候选加一组分得开的退出状态**。本轮用 `checked` 这个观察型 feature（[@def-14.2.3]）造出回退：两版 checksum 都是 133693440，`checked` 只多做了逐字节观察，批均值却从 0.042857 涨到 0.225888 ns/字节；门禁按 20% 的预算拒绝它，退出码 1。**「拒绝」与「证据不可比」是两件事**（退出码 1 与 2），把它们压成一个红灯，就分不清该修性能还是该修采集。
:::

### 14.5.1 为什么需要一个真实失败候选

只让正确基线通过，无法证明门禁能挡住回退。需要一个实际可运行、输出正确却更昂贵的候选。本轮 `checked` feature 正承担这份责任。

它没有引入 UB，也没有通过故意错误结果取巧；它只是增加逐字节观察，形成安全的性能回退案例。这条要求与第 1 章[@def-1.7.2]的三态门禁同源：如果门禁只会说「通过」，它其实只有两态，「拒绝」和「证据不足」都被折叠掉了。

::: def 定义 14.5.1 · 构造回退 constructed regression {#def-14.5.1}

**构造回退**指「为验证门禁而人为加入的、语义正确且行为安全的性能退化」。它要同时满足三条：输出与基线等价、不引入未定义行为、成本差异来自可解释的额外工作。[@def-14.2.3]的 `checked` 就是本章的构造回退——每个字节多构造一个 `Event` 并送进屏障，返回值不变。
:::

按[@def-14.5.1]，判断门禁好不好，看它对**这个已知会失败的候选**给出什么，而不是看它对基线给出什么。

### 14.5.2 完整求和实现：多出来的是观测，不是算法

```rust
pub fn sum_bytes(bytes: &[u8]) -> u64 {
    bytes
        .iter()
        .map(|&byte| {
            #[cfg(feature = "checked")]
            std::hint::black_box(evidence_lab::Event {
                id: u64::from(byte),
                elapsed_ns: 0,
            });
            u64::from(byte)
        })
        .sum()
}
```

上段是库外调用形式的同义完整函数。实际库内使用本模块的 `Event` 与 `black_box` 导入，唯一被编译与测量的实现保存在 `src/lib.rs`。

`Event` 的 `elapsed_ns` 在此固定为零，本实验不读逐字节时钟。因此它与第 13 章 Each 模式测的是不同观测组合，不能把两张表的差值当成时钟独立成本。

::: def 定义 14.5.2 · 逐字节观察 per-byte observation {#def-14.5.2}

**逐字节观察**指「每处理一个元素就构造一个可被优化器看见的值并送进屏障」。它保证循环体不会被整体删除，也让向量化（一条指令同时处理多个元素）无法把多次迭代合并：被观察的中间值必须逐个存在。对照第 1 章[@def-1.3.1]的观察集合，它是把「观察」从整次调用下沉到每个元素。
:::

按[@def-14.5.2]，`checked` 增加的不是算法步骤，而是「每个字节都得留下痕迹」这条数据依赖。这正是它作为回退候选合格的原因：语义没变，工作形状变了。

### 14.5.3 可执行入口与布局

```rust
use evidence_lab::{report, sum_bytes, warm};
use std::hint::black_box;
use std::time::Instant;

fn main() {
    let bytes: Vec<u8> = (0..=255).cycle().take(1_048_576).collect();
    let expected = bytes.iter().fold(0_u64, |sum, byte| sum + u64::from(*byte));
    let case = if cfg!(feature = "checked") {
        "checked"
    } else {
        "default"
    };
    warm(|| {
        assert_eq!(sum_bytes(black_box(&bytes)), expected);
    });
    let mut samples = Vec::new();
    println!(
        "unit=ns_per_byte;case={case};bytes={};checksum={expected}",
        bytes.len()
    );
    for round in 0..21 {
        let start = Instant::now();
        let value = sum_bytes(black_box(&bytes));
        let ns = start.elapsed().as_secs_f64() * 1e9 / bytes.len() as f64;
        assert_eq!(value, expected);
        samples.push(ns);
        println!("raw,{case},round={round},value={ns:.6},checksum={value}");
    }
    report(case, &samples);
    println!(
        "layout,Vec_u8,size={},align={}",
        std::mem::size_of::<Vec<u8>>(),
        std::mem::align_of::<Vec<u8>>()
    );
    println!(
        "layout,slice_u8,size={},align={}",
        std::mem::size_of::<&[u8]>(),
        std::mem::align_of::<&[u8]>()
    );
}
```

输入是 1_048_576 字节；`expected` 由独立参考 fold 算出，预热至少 500 ms 后才进入 21 批（[@def-1.2.2] 的批定义）。

| 类型 | 本轮size | 本轮align | 计时关系 |
|:--|--:|--:|:--|
| Vec&lt;u8&gt; | 24 | 8 | 输入在计时前分配 |
| &amp;[u8] | 16 | 8 | 每批传入借用视图 |
| Event | 16 | 8 | checked路径逐字节临时构造 |

`Vec` 本体不是 1 MiB 输入的全部内存：它拥有的缓冲长度为 1048576 字节，两版本读取同样长度和内容。布局数值在这里只说明「容器本身不是成本主体」，不是 ABI 承诺——按[@def-14.1.2]，它是本轮产物的观察，不是接口保证。

### 14.5.4 本轮运行结果：一个比值能说清的事

来源为 `feature-default.txt` 与 `feature-checked.txt`，单位 ns/聚合 byte；每个进程预热至少 500 ms，然后 21 批。

| 配置 | mean | N-1 sd | 批均值p50 | 批均值p99 |
|:--|--:|--:|--:|--:|
| default | 0.042857 | 0.002920 | 0.041763 | 0.052094 |
| checked | 0.225888 | 0.005934 | 0.222644 | 0.245054 |

两者 checksum 均为 133693440。小于 1 ns/byte 是**大块聚合吞吐的倒数**，不是一次函数调用延迟：它把 1 MiB 的一次遍历摊到每个字节上。

本轮先运行 default 进程，再运行 checked 进程，未做跨二进制逐轮配对，因此仍有顺序漂移限制（[@def-1.4.1]）。[@def-14.4.5]说的配对单位其实存在，入口每轮都打印了 `round`，但归档摘要没有按轮配对——这正是下一道例题要小心的地方。

::: ex 例 14.5.1 · 这个候选按 20% 预算是过还是不过 {#ex-14.5.1}

用上表两个批均值：default 0.042857、checked 0.225888 ns/byte；门禁的通过条件是 `candidate_mean / baseline_mean <= 1 + budget`，预算 20%。问：① 比值是多少？② 门禁判什么、退出码是几？③ 这个「拒绝」是不是统计显著性的结论？

::: sol 解答

① 0.225888 ÷ 0.042857 ≈ 5.27。② 5.27 远大于 1.20，超预算 → 拒绝，退出码 1，结果写入 `gate-rejection.json`。③ 不是。这是**描述性预算判定**：20% 是本教学夹具写定的策略阈值，不是显著性水平；预算按[@def-1.7.1]应来自业务约定，而不是从数据里读出来。要升级成[@def-1.7.2]的三态结论，还需要按轮计算配对差值的区间，本轮没有算。
:::

:::

### 14.5.5 代码生成证据支持到哪一句

两种 feature 的 MIR、LLVM IR 与 `.s` 均实际保留。默认产物中可见向量加载、表重排与宽化累加路径；`checked` 产物中可见逐字节加载和 `Event` 栈存储屏障。

| 边界 | 默认配置 | checked配置 |
|:--|:--|:--|
| 求和主循环 | 实际存在向量化路径 | 实际为逐字节循环 |
| Event | 没有逐字节Event观察 | stp保存字段，空内联汇编屏障 |
| 输出 | u64求和返回 | 相同u64求和返回 |
| ABI承诺 | 仅本轮Rust产物 | 不是稳定FFI布局 |

这支持「feature 改变了优化后工作形状」。没有测 PMU 向量指令数或缓存事件，不能根据汇编存在就报告硬件吞吐达到理论峰值。最后一行的意思与[@def-14.1.2]相同：ABI 一栏只是本轮 Rust 产物的观察，不是稳定 FFI 布局。

### 14.5.6 门禁的核心契约：三种退出状态

`tools/gate.py` 检查原始 21 轮、单位与 checksum，再比较候选均值与基线均值。预算默认 20%，这是教学夹具的明确策略，不是统计显著性检验。

```text
通过条件：candidate_mean / baseline_mean <= 1 + budget
```

```python
def compare(baseline, candidate, budget):
    if budget < 0:
        raise ValueError("budget must be nonnegative")
    if (baseline["unit"] != candidate["unit"]
            or baseline["checksum"] != candidate["checksum"]):
        raise ValueError("unit or correctness evidence differs")
    ratio = candidate["mean"] / baseline["mean"]
    return {"ratio": ratio, "budget": budget,
            "pass": ratio <= 1 + budget,
            "scope": "local workload only; no statistical significance or SLA claim"}
```

完整解析、CLI 与错误路径在真实源文件中提供；没有用正文伪代码冒充已测试工具。本轮 checked 被拒绝，进程退出码为 1，记录在 `gate-rejection.json`；缺失样本或格式/校验不一致则退出码为 2。

::: def 定义 14.5.3 · 门禁的三种退出状态 gate exit states {#def-14.5.3}

本轮门禁用退出码表达三种互不冒充的结论：**0 = 通过**（21 轮齐全、单位与 checksum 一致、比值在预算内）；**1 = 拒绝**（证据有效，但候选超出预算）；**2 = 证据不可比**（样本缺失，或格式、单位、校验不一致）。第三种不是[@def-1.7.2]的「证据不足」：那里是区间跨过预算、证据不够强；这里是**证据本身不成立**，连比较的对象都不齐。
:::

按[@def-14.5.3]，不完整证据不会被当作零耗时通过。这也和第 1 章[@def-1.7.2]的顺序一致：先确认证据有效，再谈接受、拒绝还是补证据。

### 14.5.7 实际失败测试

Python 测试验证三个不同拒绝理由：真实 checked 结果超过预算时必须拒绝；只给 20 轮候选时必须拒绝；checksum 不同时，即使候选更快也必须拒绝比较。

这些测试没有把纳秒数硬编码进 Rust 单元测试，而是用实际归档验证本轮门禁行为。换一轮归档时，应明确更换测试输入，而不是悄悄覆盖旧结果——和[@def-14.3.3]的缓存键一样，新运行必须留下新目录。

::: think 思考 · 候选更快但 checksum 不同，能不能放行 {#think-14.5.1}

某候选批均值明显低于基线，但 checksum 与基线不一致（只差 1）。按[@def-14.5.3]和[@def-1.7.2]，这个结果该怎么处理？

::: sol 解答

先按证据不成立处理，退出码 2，不进入性能判断。checksum 不同说明两版**输出的语义已经不同**，此时的「更快」是在做另一件事；按[@def-14.1.1]，它们甚至不是同一个被测程序。[@def-1.7.2]表里「正确性失败 → 不进入性能判断」正是这一条。正确动作是回到功能与契约，而不是把差 1 的值当成噪声解释掉。
:::

:::

::: method 判定流程 · 一个候选该判哪一态

**第一步**核证据完整性：21 轮是否齐全，单位与 checksum 是否一致（[@def-14.5.3]）。缺一项就退出码 2，先修采集。<br>
**第二步**核身份：feature 闭包、profile、输入长度、工具链是否与基线相同（[@def-14.1.1]）；不同就改写成「配置差异」。<br>
**第三步**算比值：`candidate_mean / baseline_mean` 与 `1 + budget` 比较。<br>
**第四步**给结论：不超预算退出 0，超预算退出 1；两者都只是本输入、本环境下的描述性结论。<br>
**第五步**要发布裁决时，按轮计算配对差值区间，再和事先写下的预算 B 比（[@def-1.7.1]、[@def-1.7.2]）；本轮没有算区间。<br>
**范围**：单包、1 MiB 单一输入、桌面 macOS，不外推到生产负载（[@def-1.8.2]）。
:::

### 14.5.8 小结与常见错误

**小结。**① 门禁要由真实会失败的候选证明（[@def-14.5.1]）；② 构造回退只改工作形状，不改输出（[@def-14.5.2]）；③ 小于 1 ns/byte 是聚合吞吐倒数，不是函数延迟；④ 三种退出状态要分开，证据不可比不是性能失败（[@def-14.5.3]）；⑤ 20% 是教学阈值，不是显著性结论（[@def-1.7.1]）。下一节[14.6 PGO](#sec-cpp-rust.4.14.6)把训练数据也写进构建输入。

::: errata 常见错误清单（14.5 节）

E-a **用「基线通过」证明门禁有效。**没有失败候选，门禁只有两态（[@def-14.5.1]）。

E-b **把 `checked` 读成「更安全的版本」或「编译器退化」。**它只是多做了观测（[@def-14.2.3]）。

E-c **把 ns/byte 当成一次函数调用的延迟。**它是 1 MiB 遍历摊到每字节的聚合倒数。

E-d **checksum 相同就认为工作相同。**两版观察集合不同（[@def-14.5.2]）。

E-e **缺样本时用空列表或零均值放行。**这会把不完整证据伪装成通过（[@def-14.5.3]）。

E-f **把 20% 预算读成统计显著性。**阈值是策略，不是检验结论（[@def-1.7.1]）。

E-g **汇编里有向量化就声称达到理论峰值。**没有 PMU 计数，这句话没有证据（14.5.5）。

:::

::: method 即时自测 · 14.5

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　门禁的三个退出码各代表什么？为什么不能只有一个「失败」？

::: sol 第 1 题答案
0 = 通过（21 轮齐全、单位与校验一致、比值在预算内）；1 = 拒绝（证据有效但超预算）；2 = 证据不可比（缺样本或单位/校验不一致）（[@def-14.5.3]）。三态分开才能决定修性能还是修采集；压成一个红灯就丢了修复方向。
:::

**第 2 题 · 辨析**　「`checked` 版本更慢，说明编译器对带审计的代码优化更差。」这句话错在哪？

::: sol 第 2 题答案
错在把「工作不同」说成「优化能力不同」。两版 feature 闭包不同，`checked` 每字节构造 `Event` 并送进屏障（[@def-14.5.2]），这是[@def-14.1.1]第二层的差异，不是工具链层。代码生成也印证了这一点：默认版有向量化路径，`checked` 是逐字节循环（14.5.5）。
:::

**第 3 题 · 应用**　归档里只有 20 轮候选数据，均值看着在预算内。你能做什么？

::: sol 第 3 题答案
不能放行。按[@def-14.5.3]这是退出码 2：样本不齐，证据不可比，门禁的 21 轮要求写在检查里。正确动作是补齐缺失轮次后重新归档，而不是用 20 轮算出的均值替代（对照[@def-1.7.2]，证据不足不能判成通过）。
:::

**第 4 题 · 迁移**　把这套「构造回退加三退出码」搬到 C++ 服务的构建门禁，最小需要哪几件？

::: sol 第 4 题答案
三件：一个语义等价但确定更贵的构造回退（例如多一次确定性校验或日志观测）；一组分得开的退出码（通过 / 超预算 / 证据不可比）；以及身份字段（编译选项、依赖版本、输入指纹，[@def-14.1.1]）。没有第一件，门禁无法自证会不会拒绝；没有第三件，两次数字可能不是同一个程序。

## 14.6 PGO：训练数据也是构建输入 {#sec-cpp-rust.4.14.6}

本节回答一个问题：**PGO 把什么东西变成了构建输入，哪一步没记就等于没做？**14.5 用 feature 造出一个回退；本节讨论另一种构建输入：运行过的输入本身。PGO 不改源码，却改变优化器看到的世界，所以它的证据要求比普通构建更严。

::: preview 先抓住一件事

PGO 的产物不是「更快的二进制」，而是**一份可指认的训练语料加一次用它重编译的构建**。插桩、训练、合并、重编译验证四个阶段任何一步没记录，最终产物就无法回答「它见过哪些输入」。本节只核读了 rustc 的官方说明，**没有生成 profraw/profdata，也没有运行 profile-use 程序；本节没有任何 PGO 收益数字，训练与验证的耗时本节没有采集**。全书真跑过这四步的是第 6 章 6.8，产物与工具版本在 `bench/compiler-lab/results/extra-02/`。
:::

### 14.6.1 本轮状态：只有流程、没有数字

**本节（14.6）没有做 PGO 实验**：这一节没有生成 profraw 或 profdata，没有运行带 `profile-use` 的程序，没有报告 PGO 加速或退化数字。要分清「本节没做」和「全书没做」：真正把插桩→训练→合并→重编译四步跑通并归档的是第 6 章 6.8，产物就在 `bench/compiler-lab/results/extra-02/pgo-data/`（`.profraw` 与 `merged.profdata`），工具版本核对见 6.8.3。本节只讨论这条流程的责任划分，不复述第 6 章的数字，也不据它给 PGO 报一个收益。

下面讨论可执行流程的责任划分。它不是本轮已经完成的实验，PGO 也不是本章两项实测 benchmark 之一：构建侧是[@def-14.4.1]的 fresh 与 noop，运行侧是 14.5 的 feature 回退。

::: def 定义 14.6.1 · 采样引导优化 profile-guided optimization {#def-14.6.1}

**采样引导优化（PGO）**指「先用带插桩的程序在训练输入上跑一遍，收集分支与调用频次，再用这份数据重新编译」的流程。它把**运行时的输入分布**变成编译期输入——这是[@def-14.1.1]之外新增的一层：不是配置项，而是一份数据文件。它的身份由「哪份数据、哪次合并、哪次重编译」共同决定。
:::

按[@def-14.6.1]，PGO 的构建身份不只要记 feature 与工具链，还要记训练语料本身。

### 14.6.2 四个阶段必须分开

1. 生成带采集插桩的程序。
2. 用训练输入运行该程序。
3. 用匹配的 `llvm-profdata` 合并数据。
4. 用合并数据重新编译并验证最终程序。

训练版墙钟不是最终优化版墙钟，插桩自身会改变执行成本；最终性能仍需要未插桩的对照运行。

::: def 定义 14.6.2 · 插桩版与最终版 instrumented and final build {#def-14.6.2}

**插桩版**是打开 `-Cprofile-generate` 的构建，任务是产出数据，不代表性能；**最终版**是打开 `-Cprofile-use` 的构建，它的耗时才可能与基线比。两者是不同产物，身份不同（[@def-14.1.1]），墙钟不能混用。
:::

按[@def-14.6.2]，把插桩版的耗时写进发布报告，等于把测量工具当成被测对象。四个阶段也对应四份证据：训练程序的指纹、训练输入的清单、合并工具与命令、最终程序与基线的各自身份。

### 14.6.3 训练集合决定优化偏好

PGO 可以影响内联（把函数体搬进调用点那一处）、布局和其他优化决策。训练分布偏向某类输入，会给编译器相应的路径信息。

如果训练只覆盖成功短请求，失败路径可能缺少代表性。如果上线流量变化，训练所得布局也可能不再合适。因此 PGO 不是「让所有输入都更快」的保证。

::: def 定义 14.6.3 · 训练语料 training corpus {#def-14.6.3}

**训练语料**指「实际喂给插桩版程序的输入与参数，连同运行顺序」。它决定优化器看到哪些分支热、哪些冷。语料不等于程序支持的全部输入，也不等于生产流量；[@def-14.6.1]的收益上限由它决定。
:::

按[@def-14.6.3]，报告 PGO 结果要先交代语料长什么样，再说数字；只说「开了 PGO」等于没说。

### 14.6.4 训练与验证输入分离

训练集用于生成优化依据；留出集用于检查对未参与训练输入的效果；正确性测试还应覆盖错误与边界情况。

训练集过拟合在性能工程中同样有害。只展示训练输入上的最好均值，会高估实际收益。应保留每类输入的指标和总体权重。

::: def 定义 14.6.4 · 留出集 holdout set {#def-14.6.4}

**留出集**指「训练时不给插桩程序看、只在最终版上评估的输入」。它的作用与第 1 章[@def-1.7.3]的确认性实验相同：用没参与调参的数据出结论，否则测到的只是「它记住了训练集」。
:::

按[@def-14.6.4]，同一个 1 MiB 输入既训练又验证，等于没有验证；下面的示例流程没有伪造留出集，更没有用同一输入冒充独立泛化评估。

### 14.6.5 feature、target 和编译选项要一致

训练与使用阶段应尽量保持相同源码与关键标志，只有 profile-generate 与 profile-use 按流程替换。如果同时改 feature、目标 CPU 和业务逻辑，就难以解释数据匹配——这正是[@def-14.1.1]第二、三层的差异被混进同一个数字。

官方说明建议使用绝对路径：Cargo 可能在不同工作目录调用 rustc，相对 profdata 路径会导致查找失败或使用错误数据。

把 `RUSTFLAGS` 应用到所有 host 构建工具，可能产生额外采集文件。官方 Cargo 流程使用显式 `--target` 来隔离 host 构建脚本的相关标志作用。这不是说 `--target` 提供了沙箱，它只是构建域区分的一部分；仍应核对实际编译命令和数据文件来源（对照[@def-14.1.3]：旗标各有责任，都不承诺隔离）。

### 14.6.6 有条件的流程示例

以下是供具备匹配 `llvm-profdata` 环境的读者使用的流程设计。目录要求新建，避免混入旧训练数据。本轮没有执行这些命令，也没有对应的耗时与体积数据。

```bash
# 从cpp-rust/执行；LLVM_PROFDATA必须指向匹配工具链的真实工具。
set -euo pipefail
: "${LLVM_PROFDATA:?set the matching llvm-profdata executable path}"
ROOT="$PWD/bench/evidence-lab"
TRAIN="$ROOT/results/my-pgo-training"
mkdir "$TRAIN"
mkdir "$TRAIN/raw"
TARGET=aarch64-apple-darwin
RUSTFLAGS="-Cprofile-generate=$TRAIN/raw" \
  cargo build --offline --locked --release --target "$TARGET" \
  --manifest-path "$ROOT/Cargo.toml" --bin feature_work \
  --target-dir "$TRAIN/generate"
"$TRAIN/generate/$TARGET/release/feature_work"
"$LLVM_PROFDATA" merge -o "$TRAIN/merged.profdata" "$TRAIN/raw"
RUSTFLAGS="-Cprofile-use=$TRAIN/merged.profdata -Cllvm-args=-pgo-warn-missing-function" \
  cargo build --offline --locked --release --target "$TARGET" \
  --manifest-path "$ROOT/Cargo.toml" --bin feature_work \
  --target-dir "$TRAIN/use"
"$TRAIN/use/$TARGET/release/feature_work"
```

这个固定 1 MiB 求和程序训练分布很窄。即使流程成功，也不能代表网络服务或数据库负载。示例没有伪造留出集，更没有用同一输入冒充独立泛化评估。

### 14.6.7 missing-function 警告与数据陈旧

编译器可能找不到某函数对应的训练数据，默认不一定给出足够醒目的警告；官方说明建议启用相关 missing-function 警告。

警告缺席也不是训练充分的证明：某个存在数据的函数仍可能只见过一种输入。需要结合训练覆盖和业务分布检查。

### 14.6.8 PGO 产物的归档

至少保留训练程序指纹、输入清单、运行参数和原始 profraw；合并工具版本、合并命令与 profdata 指纹也要保留；最终程序和未 PGO 基线应有各自身份。

不要只缓存一个名为 `latest.profdata` 的可变文件。它会让发布无法回答「这次用了哪一轮训练」；性能回退时也很难区分源码变化与训练变化。

::: ex 例 14.6.1 · 只留一个 profdata 的归档能回答什么 {#ex-14.6.1}

某工程的 `results/pgo/` 里只有 `merged.profdata` 和最终二进制，没有训练输入清单，也没有生成训练程序时的命令。请按[@def-14.6.1]与[@def-14.6.2]回答：① 能证明最终版用过训练数据吗？② 出现回退时，能区分源码变化与训练变化吗？③ 这份归档缺的第一件东西是什么？

::: sol 解答

① 只能证明旁边放着一份 profdata，不能证明最终二进制是**用这份数据**编出来的——缺 profile-use 命令与最终程序指纹之间的对应（[@def-14.6.2]）。② 不能。回退可能来自源码、工具链、feature 闭包或训练语料，缺少训练输入清单时无法归因（[@def-14.6.3]）。③ 训练输入清单与生成训练程序时的完整命令，其次是与它配对的运行参数。补不齐就按证据不足处理（[@def-1.7.2]），不要用「我们开过 PGO」当结论。
:::

:::

::: think 思考 · 训练和评估用同一份输入行不行 {#think-14.6.1}

有人主张：反正只有一个 1 MiB 求和程序，训练和最终评估都用同一份输入最省事，还能保证「数据一定匹配」。按[@def-14.6.4]，这有什么问题？

::: sol 解答

数据确实匹配，但结论随之失效：训练集同时充当留出集，测到的是「对这组输入的记忆效果」，不是对新输入的泛化（[@def-14.6.4]）。这与第 1 章[@def-1.7.3]把探索性实验的极值当成确认性结论是同一类错误。最低要求是切分出一组没参与训练的输入，并在报告里写明切分方式与权重；若数据太少无法切分，就明确写「本轮不能评估泛化」，而不是用一个数字代替。
:::

:::

::: method 判定流程 · 这次 PGO 产物能不能归档

**第一步**训练程序指纹：插桩版二进制的指纹与构建命令（[@def-14.6.2]）。<br>
**第二步**训练语料：输入清单、参数、运行顺序（[@def-14.6.3]）。<br>
**第三步**原始数据：profraw 文件集合与各自来源。<br>
**第四步**合并：`llvm-profdata` 版本、合并命令、profdata 指纹。<br>
**第五步**重编译：profile-use 命令、最终二进制指纹、与基线各自的身份（[@def-14.1.1]）。<br>
**第六步**验证：留出集上的结果、错误与边界输入（[@def-14.6.4]）。<br>
**任何一步缺失**：记为不可比较，按[@def-1.7.2]的第三态处理；不要用「流程跑通了」代替证据。
:::

### 14.6.9 是否值得用 PGO

要综合最终运行收益、构建成本、训练成本和维护风险。低频运行的小工具可能难以摊薄复杂流程；长期运行的大程序也需要留出与回退策略。

本轮没有收益数据，所以不做启用建议。本章给出的是证据要求，而不是默认开启所有优化的清单。训练与验证的耗时、最终版与基线的差异，本节都没有采集。

### 14.6.10 小结与常见错误

**小结。**① PGO 把运行分布变成构建输入，身份多了一份数据（[@def-14.6.1]）；② 插桩版与最终版是两份产物，墙钟不能混用（[@def-14.6.2]）；③ 收益上限由训练语料决定（[@def-14.6.3]）；④ 训练与验证必须分开，否则结论只是记忆效果（[@def-14.6.4]）；⑤ 本轮没有 PGO 数字，凡涉及收益一律写「未采集」。下一节[14.7 CI](#sec-cpp-rust.4.14.7)讨论这些证据在 CI 里按什么顺序验证。

::: errata 常见错误清单（14.6 节）

E-a **拿插桩版的耗时当最终性能。**插桩本身改变执行成本（[@def-14.6.2]）。

E-b **只留一个 `latest.profdata`。**可变文件名让发布说不清用了哪轮训练（14.6.8）。

E-c **训练与评估用同一份输入。**测到的是记忆而不是泛化（[@def-14.6.4]）。

E-d **训练时改了 feature 或目标 CPU。**数据与产物的对应关系无法解释（[@def-14.1.1]）。

E-e **用相对路径指定 profdata。**Cargo 的工作目录不保证一致（14.6.5）。

E-f **把 missing-function 警告缺席当成训练充分。**有数据的函数也可能只见一种输入（14.6.7）。

E-g **因为「流程跑通了」就宣布 PGO 有收益。**本节没有任何收益数字（14.6.9）。

:::

## 14.7 CI：先验证证据，再比较数字 {#sec-cpp-rust.4.14.7}

本节回答一个问题：**CI 报绿，能说明性能成立吗；一个性能门禁该按什么顺序验证？**14.5 造出了会失败的候选，14.6 把训练数据纳入输入；本节讨论这些证据在共享 runner 上按什么顺序被检查，以及哪一步没做时该说「证据不足」而不是「通过」。

::: preview 先抓住一件事

共享 runner 上的绿灯只证明「命令跑完了」，不证明「数字可比」。顺序是固定的：**先验证证据（轮数、单位、校验、身份），再比较数字（预算），最后才是需要时的人工裁决**。把三层压成一个红灯，修复方向就丢了。本轮的 `gate.py` 只覆盖其中一小段，它自己的说明也是这么写的。
:::

### 14.7.1 CI 成功不等于性能成立

普通共享 runner 会受其他工作影响：虚拟化、动态频率、缓存命中和镜像更新都可能改变结果。

CI 很适合执行功能测试和静态检查；正式性能门禁则需要更严格的执行域与基线策略。不能把一次共享 runner 的微小均值变化当作发布事故。这与第 1 章[@def-1.4.1]对时间漂移的提醒是同一件事：同一台机器不同时段的差异，未必是代码差异。

### 14.7.2 分层门禁

第一层检查工程能否构建、格式化和通过测试。第二层检查证据是否完整、单位是否一致、输入是否相同。第三层比较性能预算。第四层在需要时安排独立重跑与人工裁决。

前一层失败，后一层不应伪造成功，尤其不能在 benchmark 崩溃后使用空列表均值零。

::: def 定义 14.7.1 · 分层门禁 layered gate {#def-14.7.1}

**分层门禁**指「把构建、证据、预算、裁决拆成四层、逐层放行」的检查结构。它的关键不是层数，而是**顺序**：第一层失败时第二层没有输入，第二层失败时第三层没有可比对象。任何一层「用默认值补上」，都会把失败伪装成通过——这与[@def-14.5.3]「不完整证据不会被当作零耗时通过」是同一条纪律。
:::

按[@def-14.7.1]，分层不是多写几个脚本，而是让每次红灯都指向唯一一层。

| 层 | 检查什么 | 失败时的输出 |
|:--|:--|:--|
| 第一层 | 构建、格式化、测试 | 命令非零退出 |
| 第二层 | 轮数、单位、checksum、身份 | 证据不可比（退出码 2） |
| 第三层 | 候选与基线的预算比值 | 拒绝（退出码 1） |
| 第四层 | 独立重跑与人工裁决 | 带原因的人工结论 |

### 14.7.3 证据有效性与性能失败不同

| 状态 | 本轮工具行为 | 发布解释 |
|:--|:--|:--|
| 21轮齐全且预算内 | gate退出0 | 仅本地描述性比较通过 |
| 有效但超预算 | gate退出1 | 候选成本超策略阈值 |
| 样本缺失或单位/校验错误 | gate退出2 | 证据不可比较 |
| 构建或测试失败 | 命令非零停止 | 不进入性能比较 |

把这些状态压成「红灯」会丢掉修复方向；保留机器可读结果与错误原因更有用。

::: def 定义 14.7.2 · 证据不可比 incomparable evidence {#def-14.7.2}

**证据不可比**指「两份观测在对象、单位或完整性上就对不上，比较本身不成立」：轮数不齐、单位不同、checksum 不同、身份字段不一致。它比[@def-1.7.2]的「证据不足」更早一步：证据不足是数据齐了但区间跨过预算，不可比是数据还没资格进比较。
:::

按[@def-14.7.2]，看到退出码 2 时不要讨论快慢，先修采集与身份记录。

### 14.7.4 本轮小门禁没有检查的字段

`gate.py` 只检查样本结构、单位、checksum 与均值预算。它没有自动比较 CPU 型号、工具链或输入指纹，也没有自动保证候选与基线来自同一采样协议。

因此它是教学夹具，不是完整生产发布服务。正式集成应在调用它之前验证证据清单（14.8），环境不一致应阻塞或转入明确的人工评估。不能因为脚本有 fail-closed 分支就声称所有证据都已验证——fail-closed 只覆盖它检查过的那几项。

::: ex 例 14.7.1 · 三条 CI 结果各该修哪一层 {#ex-14.7.1}

同一条流水线报出三种结果：① 候选归档 21 轮齐全、checksum 都是 133693440，比值 5.27；② 候选归档只有 20 轮，其余正常；③ 候选程序在一台 runner 上均值低于基线，在另一台上高于基线，两台的 `rustc -Vv` 不同。按[@def-14.7.1]与[@def-14.7.2]，各自第一动作是什么？

::: sol 解答

① 第三层：证据有效但超预算，退出码 1，先看候选多做了什么工作（本例是 `checked` 的逐字节观察），不是重跑。② 第二层：退出码 2，先补齐第 21 轮；此时均值没有意义。③ 先查身份再谈数字：工具链不同意味着[@def-14.1.1]第三层不同，两台机器上的数字不是同一程序的两次观测，应记为不可比，而不是「第二台机器更慢」。
:::

:::

### 14.7.5 性能预算应与风险匹配

20% 在这里用于让显著的构造回退可观察，它不是建议所有工程允许 20% 退化。

业务可用预算可能包含：

- 吞吐下降上限。
- 内存峰值上限。
- 真实请求尾延迟预算。
- 构建与发布窗口。
- 二进制大小或冷启动限制。

这些指标不能由一张 ns/byte 表替代。多个预算之间也可能冲突，需要明确谁有权作取舍。按[@def-1.7.1]，预算要在采集之前写下，并且可以是一组并列约束；只写时间预算，等于默认内存与正确性没有代价。

### 14.7.6 避免自动重跑直到变绿

只保留最好一次结果会形成选择偏差。「红了就再跑，绿了就停」不是可靠门禁。

预先规定重跑次数与合并方式：保留所有轮次，并说明触发重跑的原因。若基础设施故障明确，应将故障证据与排除记录一起保存。不要静默覆盖旧输出目录。

这条规则与第 1 章[@def-1.7.3]对探索性与确认性实验的区分一致：在同一批数据上反复调整再报告最好的一次，等于把偶然极值当成稳定收益。

::: think 思考 · 三次里两次红一次绿，取绿的那次发布 {#think-14.7.1}

一个性能门禁连跑三次：accept、reject、accept。团队决定采用最近一次 accept 的结果发布，理由是「大部分时候是通过的」。按第 1 章[@def-1.7.3]与本节的停止规则，这个推理错在哪？

::: sol 解答

错在把重复运行当成独立抽样，并按结果挑样本。三次结果不同说明测量条件不稳定（[@def-1.4.1]）或证据本身不可比；取绿的一次等于事后改变判定规则（[@def-1.7.3]）。正确做法是采集前写下重跑次数与合并方式，把三次结果全部保留并按规则汇总，例如取多数并公布三个结果；如果差异来自环境，应先修执行域，而不是选票。
:::

:::

### 14.7.7 配对与独立重跑

同一轮交替基线与候选有助于降低漂移影响；另一天或另一执行者独立重跑有助于发现流程依赖。二者解决不同问题。

本轮构建 profile 进行了轮转（[@def-14.4.5]），feature 二进制尚未做跨进程配对轮转，本轮也没有第二个独立执行者。这些限制不会因为测试全绿而消失。

::: def 定义 14.7.3 · 独立重跑 independent rerun {#def-14.7.3}

**独立重跑**指「由另一个执行者、在另一段时间或另一台机器上，按同一协议重新采集」。它验证的是流程可复现与条件依赖，而不是第 1 章 1.8 节所说的结果复算（同一份 CSV 重算摘要）。[@def-14.7.3]的价值恰在于它可能失败：同一人同一机关掉缓存再跑，测不出流程对环境的依赖。
:::

按[@def-14.7.3]，本轮只有「同一执行者、同一台机器上的轮转」，没有真正意义上的独立重跑。

### 14.7.8 置信区间与 p 值的边界

本轮只给描述性均值、N−1 标准差和分位数，没有计算置信区间或 p 值，也没有把 21 次视为严格独立同分布的生产样本。

将来加入统计检验，应先说明模型、依赖性和多重比较策略。显著性不能替代实际预算（[@def-1.7.1]）：极小但稳定的变化未必有业务意义，巨大但高噪声的变化也值得排查。

### 14.7.9 CI 缓存与证据归档分离

缓存可以加速编译；正式 build benchmark 则必须注明是否命中缓存。如果比较的是 fresh 目标目录（[@def-14.4.1]），不应悄悄恢复一份 target 缓存。

证据目录使用新名字并拒绝覆盖；原始文件应该能在 CI 作业过期后继续定位。缓存淘汰策略不应决定审计证据是否存在。

### 14.7.10 小结与常见错误

**小结。**① CI 绿灯只证明命令跑完，不证明数字可比；② 门禁分四层，顺序不能颠倒（[@def-14.7.1]）；③ 证据不可比要早于预算比较处理（[@def-14.7.2]）；④ 预算是业务约束，不是统计结论（[@def-1.7.1]）；⑤ 重跑与独立重跑解决不同问题，都不能用来「跑到变绿」（[@def-14.7.3]）。下一节[14.8 从实验包到发布责任链](#sec-cpp-rust.4.14.8)把这一套落成可交付的实验包。

::: errata 常见错误清单（14.7 节）

E-a **把共享 runner 的一次波动当发布事故。**虚拟化与频率都在变（14.7.1）。

E-b **前一层失败时用默认值补齐。**空列表均值零会把崩溃伪装成通过（[@def-14.7.1]）。

E-c **在单位或校验不一致时比较快慢。**这时是证据不可比，不是性能问题（[@def-14.7.2]）。

E-d **把 20% 当成通用允许退化。**它是本夹具为了让回退可见而选的阈值（[@def-1.7.1]）。

E-e **自动重跑到绿为止。**等于事后改写判定规则（[@def-1.7.3]）。

E-f **用同机同人的重跑冒充独立重跑。**它测不出流程对环境的依赖（[@def-14.7.3]）。

E-g **让缓存淘汰策略决定证据是否留存。**缓存与归档是两件事（14.7.9）。

:::

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　四层门禁各检查什么？为什么顺序不能颠倒？

::: sol 第 1 题答案
构建与测试 → 证据完整性与单位、输入 → 预算比值 → 独立重跑与人工裁决（[@def-14.7.1]）。前一层失败时后一层没有合法输入；颠倒顺序会让「不可比的数字」先进入预算比较。
:::

**第 2 题 · 辨析**　「gate 退出码 2 说明候选太慢，应该优化。」这句话错在哪？

::: sol 第 2 题答案

:::

**第 3 题 · 应用**　你接手一条 CI，它每天跑一次性能任务，红了就重跑，直到绿。先改哪三处？

:::

**第 4 题 · 迁移**　把这套顺序搬到一组跨平台（macOS / Linux）的构建矩阵上，最容易被误判成哪一层？

::: sol 第 4 题答案

:::

## 14.8 从实验包到发布责任链 {#sec-cpp-rust.4.14.8}

本节回答一个问题：**实验包要交出哪些东西，发布这一步才有据可依？**14.7 说的是门禁顺序；本节把实验包本身当作交付物，逐项说清它承担什么、不承担什么。

::: preview 先抓住一件事

责任链有五环：可重跑的命令、有限但明确的测试契约、产物与采样的对应、机器可核验的清单、基线与回退策略。**本章不执行部署**，所以只定义责任，不声称验证过发布或回滚。任何一环被写成「已覆盖全部情况」，都是把有限契约夸大成保证。
:::

### 14.8.1 本实验包的测试责任

Rust 测试覆盖输出等价、空输入与非整块输入。样本验证测试覆盖缺失、NaN 和零值。分位数测试确认 21 条 nearest-rank p99 为最大值（[@def-1.5.2]）。

Python 测试覆盖实际 feature 回退拒绝和错误证据拒绝。文档示例通过 doctest。这些都是具体而有限的契约测试。

它们不覆盖 Cargo 实现全部状态，也不覆盖操作系统所有调度交错。本章没有把测试数量当成覆盖完整性的替身。

::: def 定义 14.8.1 · 契约测试 contract test {#def-14.8.1}

**契约测试**指「只针对明文写下的少数性质做断言」的测试：输出等价、边界输入、错误拒绝。它证明的是「这几条性质在本轮产物上成立」，不是「系统在所有情况下正确」。[@def-1.7.2]表里「正确性失败 → 不进入性能判断」靠的就是这一层。
:::

按[@def-14.8.1]，测试的价值在于把契约写死，而不在于条数；条数多但都在测同一个性质，等于没有覆盖。

### 14.8.2 实际命令清单

```bash
cargo fmt --manifest-path bench/evidence-lab/Cargo.toml --check
cargo clippy --offline --locked --manifest-path bench/evidence-lab/Cargo.toml \
  --all-targets --all-features -- -D warnings
cargo test --offline --locked --manifest-path bench/evidence-lab/Cargo.toml
cargo test --offline --locked --manifest-path bench/evidence-lab/Cargo.toml \
  --all-features
RUSTDOCFLAGS='-D warnings' cargo doc --offline --locked \
  --manifest-path bench/evidence-lab/Cargo.toml --no-deps --all-features
python3 -m unittest discover -s bench/evidence-lab/tools -p 'test_*.py'
```

本轮离线执行成功。默认与 checked 各有 5 项 Rust 单元测试、1 项 doctest；Python 门禁有 3 项测试。命令结果不能表述为独立技术审计。

### 14.8.3 构建产物与采样产物的关联

第 13 章 `sample` 使用正式默认构建的 `cpu_wait`。本章保留其二进制指纹，并归档可执行文件副本。生成代码采集在所有正式计时后进行。

因此汇编采集不会与运行计时争用编译资源；同时也要承认它是另一次同源构建，不是从 `sample` 进程内存直接反汇编得到的快照。按[@def-14.1.2]，指纹只证明「归档里的这份可执行文件是哪一份」，不证明采样与计时发生在同一个进程里。

### 14.8.4 原生汇编不是链接后全部视图

`cargo rustc --emit=asm` 得到各代码生成单元的汇编，链接器仍可能进行布局、去除与其他处理。

要研究链接后确切地址，应保留最终二进制并使用匹配工具检查。不能拿编译单元顺序推断最后的 I-cache 布局。本轮只用汇编确认路径形状，不报告 I-cache 或 BTB 命中率。

### 14.8.5 数据清单应该可机器核验

::: def 定义 14.8.2 · 证据清单 evidence manifest {#def-14.8.2}

**证据清单**指「用一份机器可读的文件，把一次运行的对象、输入、观察与限制逐项登记」的清单。它的判据不是写得全，而是**每一项都能被另一个程序核对**：指纹能重算、观察数能计数、命令能重跑。它把[@def-14.1.1]的分层身份压成一个可校验的入口。
:::

一个正式证据清单应包含：

1. 唯一run id与创建时间。
2. 源码、清单与锁文件指纹。
3. 工具链、目标、profile与feature闭包。
4. 输入数据身份与计时单位。
5. 每case期望观察数与实际观察数。
6. 原始文件、统计文件与生成命令。
7. 采样运行是否进入正式统计。
8. 已知干扰、能力缺失与未执行项。

本轮这些信息分布在环境、原始行、SHA 文件与说明中，尚未做跨所有文件的签名清单发布服务。不应把分散记录包装成已经具备供应链认证。

### 14.8.6 发布时保留基线，不追随最近一次偶然结果

::: def 定义 14.8.3 · 基线 baseline {#def-14.8.3}

**基线**指「经过认可的特定产物与协议」，不是「上一次跑出来的最好值」。它至少绑定产物指纹、构建身份与采集协议（[@def-14.1.1]）。比较的永远是「候选相对这一份基线」，而不是候选相对任意一次历史运行。
:::

基线应是经过认可的特定产物与协议。每次通过后自动把当前最好值设成基线，会改变比较含义。

基线更新应有明确原因，例如工具链升级、硬件更换或业务输入变化。更新时保留旧基线与迁移比较，不要让历史回归在一次配置切换后失去可追溯性——这与[@def-1.7.3]把工具链升级视为新实验条件是同一判断。

### 14.8.7 回退策略属于性能工程

候选通过微基准不保证服务整体更好，部署还需要可回退产物与运行时观测。

回退目标应包含配置与训练数据身份。PGO 程序只回退源码、不回退 profile 数据，可能不是原来的程序（[@def-14.6.1]）；feature 集合变化也要纳入回退计划（[@def-14.2.1]）。

本实验不执行部署，所以本章只定义责任，不声称已经验证发布回滚。

### 14.8.8 为什么不展开 CMake 与环境干扰声明

本章实验没有外部 ABI 工程。加入无关 CMake 模板不会增强 Cargo 证据链。真正的 FFI 项目应保留最小外部工程及双向测试，它的编译器、目标和链接选项要进入同一身份清单（[@def-14.1.1]）。CMake 在这里是外部构建支持，不是另一条语言教学主线。

`processes-before.txt` 与 `processes-after.txt` 都是 0 字节（`measure.sh:29` 与 `:52` 用 `ps -axo pid,comm | grep -E '(cargo|rustc|clang|ld$)'` 抓，没匹配就留空文件），但这只是两次快照，不是全程排他 CPU 保证。目录锁只协调参与相同协议的测量者；桌面服务、文件缓存、调度和热状态仍可能变化。本轮没有锁核或锁频，构建与运行结果都应限定在这个环境。

::: ex 例 14.8.1 · 这份证据清单能放行吗 {#ex-14.8.1}

某次提交的清单只有四行：run id 与创建时间、源码与锁文件指纹、工具链与 profile 与 feature 闭包、原始文件与生成命令。请按[@def-14.8.2]回答：① 缺了哪几项？② 缺项时，14.5 的门禁还能可靠地给出 0 或 1 吗？③ 第一动作是什么？

::: sol 解答

① 缺第 4、5、7、8 项：输入数据身份与计时单位、每 case 期望与实际观察数、采样是否进入正式统计、已知干扰与未执行项。② 不能可靠给出：门禁只比较均值与 checksum，若不知道单位与输入身份，比值可能来自两组不同输入，按[@def-14.7.2]属于证据不可比。③ 先补清单，而不是先跑门禁；补不齐就按[@def-1.7.2]的第三态记为证据不足，不许放行。

### 14.8.9 小结与常见错误

**小结。**① 测试是有限契约，条数不等于覆盖（[@def-14.8.1]）；② 命令清单要能原样重跑，结果不等于独立审计；③ 采样与计时是同源但不同的两次执行；④ 证据清单要能被机器核对（[@def-14.8.2]）；⑤ 基线是被认可的产物与协议（[@def-14.8.3]）；⑥ 回退必须带上配置与训练数据。下一节[14.9 母本对应与实际核读](#sec-cpp-rust.4.14.9)交代这些方法的出处。

::: errata 常见错误清单（14.8 节）

E-a **用测试条数证明覆盖完整。**它们只覆盖写下的那几条性质（[@def-14.8.1]）。

E-b **把代码生成单元的汇编当链接后视图。**布局由链接器决定（14.8.4）。

E-c **把分散记录包装成已认证清单。**清单的判据是可被程序核对（[@def-14.8.2]）。

E-d **每次通过就把最好值设为基线。**比较含义被悄悄改变（[@def-14.8.3]）。

E-e **回退只回源码，不回配置与训练数据。**PGO 产物可能不是原来的程序（[@def-14.6.1]）。

E-f **把两次进程快照当全程隔离。**目录锁只协调同一协议的参与者（14.8.8）。

E-g **用「命令全绿」宣称独立审计。**没有第二个执行者与签名清单（[@def-14.7.3]）。

:::

### 版本差异裁决

本地母本介绍的是旧版本 Cargo 的示例与输出，当前工具链的选项语义以实际执行和当前规范为准；例如 LTO 的 false 与 off 差别需要回到 Profiles 规范确认。rustdoc 旧材料里的不稳定 lint 不能不加核对直接启用，本章只执行当前工具链接受的文档检查。

每一份母本的实际页码、文件指纹与覆盖状态记录在[附录：来源覆盖](../appendix/coverage.md)，正文只保留上面这些入口。

## 14.10 常见错误索引 {#sec-cpp-rust.4.14.10}

这是本章的跨节错误索引：每一节末尾都有自己的「::: errata 常见错误清单（14.M 节）」，按你阅读的顺序给出局部清单。下面这一份只收那些要读完整个章才浮出来的错误，它们在单节内部看不出问题，放进「构建、测量、门禁」的整条链才露馅。

**只写 release，不写 feature 与目标。** profile 只描述一部分编译设置，feature 还能改变业务工作。比较两份产物之前，必须先把构建身份补全（[@def-14.1.1]）。

**认为 Cargo.lock 锁住了编译器与 SDK。** 锁文件不包含全部外部输入，系统库、链接器和构建脚本都需要另外记录。所谓可复现只承诺到写清的那一级（[@def-14.3.1]）。

**把 offline 当成构建沙箱。** Cargo 离线不等于 build.rs 没有网络能力，构建脚本仍可读取外部状态。要隔离得用专门机制，而不是一个 `--offline` 参数（[@def-14.3.2]）。

**在某条边关掉默认 feature 后就停止追踪。** 其他依赖路径仍可能把它打开，要按统一后的 feature 闭包看，并检查反向路径。只根据顶层一行做运行归因，几乎一定错（[@def-14.2.1]）。

**all-features 通过就认为所有组合通过。** 全开只是一个配置，最小配置与互斥条件要独立检查。本章的包只有一个 feature，才可以把路径简化为两种（[@ex-14.2.1]）。

**把 lto=false 写成完全关闭 LTO。** Cargo 可能仍做 thin local LTO，off 与 false 不是同义词。profile 表里应沿用准确名称，别在结论里换词（[@def-14.4.3]）。

**认为更多 CGU 必然缩短编译。** 小包的固定成本可能更重要，本章的 one 配置实际比 release 更快。不要为了符合口号去改写已经测到的结果（[@ex-14.4.1]）。

**把新 target 称为完全冷缓存。** 标准库、工具链与操作系统缓存仍在，缓存边界必须精确命名。也不要为了制造冷启动而删全局缓存，那会干扰同机其他负载（[@def-14.4.1]）。

**noop 快就认为重新编译也快。** noop 主要检查已有产物，与 fresh、增量修改是三种不同的 case。本章只保存了前两种 case 各 21 条（`build-raw.jsonl` 的 case 取值就是 {release, one, thin} × {fresh-package-target, noop} 六组）；**改一个源文件的增量重建没有测**，14.4.2 也是这么写的，别把它读成已有 21 条观察。

**把 Mach-O 虚拟段总和当下载体积。** `__PAGEZERO` 不是同等磁盘占用，文件字节与 `__text` 要分开报。把 4GiB 的零填充写成实际二进制大小，读者会得到完全错误的印象。

**哈希不同就断言机器码性能不同。** 元数据也能导致差异，本章没有完整归因所有差异字段。哈希首先是身份，不是性能指标（[@def-14.1.2]）。

**用训练版计时宣称 PGO 收益。** 插桩版是收集数据的程序，最终 profile-use 产物必须独立比较，留出集也不能省（[@def-14.6.2]）。

**门禁失败就自动重跑到通过。** 这会引入选择偏差，重跑策略要事先规定并保留全部结果。原始目录不得覆盖，否则拒绝记录就消失了（[@def-14.5.3]）。

**把证据缺失当作零耗时。** 缺失样本应是错误状态，本章门禁会拒绝只有 20 轮的候选。正确性不一致的结果也不能进入速度比较（[@def-14.7.2]）。

**把本地阈值检验说成统计显著。** 门禁只做描述性的预算比较，本章没有 p 值或置信区间，通过也不是生产 SLA。措辞要跟着方法走，不能借统计术语抬高结论（[@def-14.7.1]）。

## 14.11 本章小结与章末件 {#sec-cpp-rust.4.14.11}

::: note 本章小结

- 构建身份由 profile、feature、目标与工具链一起决定，缺一项就不是同一份产物（[@def-14.1.1]、[@ex-14.1.1]）。
- feature 要看闭包与反向路径，关掉一条边不代表它没被别处打开（[@def-14.2.1]、[@ex-14.2.1]）。
- 可复现分三级，锁文件盖不住编译器、SDK 与构建脚本（[@def-14.3.1]、[@ex-14.3.1]）。
- fresh、noop 与增量是三种 case，CGU 与 LTO 要按档位说（[@def-14.4.2]、[@ex-14.4.1]）。
- 门禁要在看到数字之前定预算，并保留拒绝记录（[@def-14.5.3]、[@ex-14.5.1]）。
- PGO 的训练语料是构建输入，插桩版数据不能当收益证据（[@def-14.6.2]、[@ex-14.6.1]）。
- 证据清单要能说明可比性，缺失与不可比都该拒绝（[@def-14.8.2]、[@ex-14.8.1]）。

:::

### 出口检查

先执行 14.8 节的格式、Clippy、测试与文档命令，再从 `cpp-rust/` 构建两种 feature 运行程序，输出目录要选一个不存在的。外层脚本依次运行第 13 章的两个 benchmark、feature benchmark 与 build matrix，之后另行采集 sample 并生成代码证据。

```bash
cargo build --offline --locked --release \
  --manifest-path bench/evidence-lab/Cargo.toml --bins
cargo build --offline --locked --release --features checked \
  --manifest-path bench/evidence-lab/Cargo.toml --bin feature_work \
  --target-dir bench/evidence-lab/target-checked
mkdir -p bench/evidence-lab/results
bash bench/evidence-lab/tools/measure.sh bench/evidence-lab/results/my-new-run
```

验证真实拒绝时，用归档里的两份 feature 结果跑门禁，并给 0.2 的预算：

```bash
python3 bench/evidence-lab/tools/gate.py \
  bench/evidence-lab/results/run-01/feature-default.txt \
  bench/evidence-lab/results/run-01/feature-checked.txt --budget 0.2
```

归档对应预期退出码 1，这是候选超预算的拒绝，不是工具运行失败；不要用 `|| true` 把它变成发布通过；`test_gate.py` 把拒绝路径钉住了——一条 `assertFalse(result["pass"])`，两条 `assertRaisesRegex`（分别匹配 `21 distinct` 与 `correctness`）。

正式原始集合的规模可以直接数出来：CPU 与 waiting 各 21 条共 42 条，instrumentation 三模式各 21 条共 63 条，feature 两配置各 21 条共 42 条，三 profile 乘两缓存边界各 21 条共 126 条，合计 273 条。第 0 轮构建产物另行运行得到的 verify 文件（三份各 21 行 `raw,`，同单位 `ns_per_byte`、同输入 1048576 字节、同校验和 133693440）也是观测形状的文本，但要按盘上的真实判据排除，不能自创一条：`build_matrix.py:57-62` 在 `round_id == 0` 时顺带运行刚构建的二进制，注释写明 Correctness execution is outside measured build intervals，`README.md` 登记的口径是「来自构建第 0 轮产物的额外可运行性校验，不进入主集合」。

反过来说，「没有跨轮配对设计」不能当判据——14.7.7 自己承认 feature 两份也是顺序各跑 21 轮、没做跨进程配对轮转，它们却计入 273。两份 sample 同理：它们是第 13 章的采样观察，不属于本章计时主集合。

你应能独立回答十个问题：哪些输入进入 Cargo.lock、哪些没有；为什么本章没有使用「完全冷构建」这个名称；为什么 one 可能比 16 CGU 构建更快；`lto=false` 与 `lto="off"` 有什么区别；二进制哈希不同为什么推不出机器码变慢；为什么 checked 不是内存安全开关；为什么 default 与 checked 的 ns/byte 不是单次调用延迟；门禁为什么拒绝缺失一轮的候选；训练数据的身份为什么必须随 PGO 产物保留；普通 CI 全绿为什么不足以证明性能发布。

本章交付的是一条可检查的责任链：从源码和配置，到实际产物，再到测量、拒绝与发布裁决。把它带进项目时，还需要项目自己的业务协议、失败路径、资源边界与端到端测试。
