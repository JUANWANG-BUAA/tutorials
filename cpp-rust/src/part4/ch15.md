## 15.1 从工具名称到可执行资源边界 {#sec-cpp-rust.4.15.1}

本节回答一个问题：**一个工具名字要变成可执行的资源边界，中间缺了哪几层定义？**本节先把「谁能调用什么、调用时允许带多少内容」写成可以核对的契约（[@def-15.1.1]），把「执行工具」和「执行任意不可信程序」分开；15.2 再接手谈上界，15.3 谈取消与许可寿命。

::: preview 先抓住一件事

「可以执行命名工具」和「可以安全执行任意不可信程序」是两个命题。前者靠管理员预先命名的注册表（[@def-15.1.2]）、类型化的参数预算（[@def-15.1.3]）与不经过 shell 的字节边界成立；后者还需要文件、网络与内核配额层的隔离，而这些不会因为改用 Rust 写就自动出现。第 1 章那条纪律在这里同样成立：条件没写全的一个数字，不是同一个量（[@def-1.1.3]）。
:::

### 15.1.1 先定义真正交付的工具范围

本项目不是一个只有`spawn`示例的章节附件。
它同时提供库、CLI、真实子进程helper、集成测试和可重跑测量脚本。
调用方可以实际执行命名工具，并取得结构化结果。
但「可以执行工具」不等于「可以安全执行任意不可信程序」。

这里的管理员、请求方和操作系统承担不同责任。
管理员选择可信可执行文件并决定哪些名字可以暴露。
请求方只能选择已有名字和被适配器允许的类型化参数。
操作系统提供进程、管道和终止机制。
本库负责有界接收、运行槽、超时传播、直接子进程wait和有限日志保留。
文件权限、网络权限、内核资源配额没有因使用Rust而自动出现。

::: def 定义 15.1.1 · 有界执行器 bounded executor {#def-15.1.1}

**有界执行器**指只在声明范围内接收请求、并保证每份已接受工作都有明确回收观察点的运行时。三件缺一不可：入口是管理员预先命名的工具集（[@def-15.1.2]）、请求参数受类型化预算约束（[@def-15.1.3]）、每个被接受的工作在退出前把资源状态报告出来（reaped、EOF 与清理错误，见 15.4 节）。它不提供文件权限、网络权限或内核配额隔离，也不负责清理进程树——这条边界在[@def-15.1.4]里逐字写明。

:::

### 15.1.2 两种注册方式对应两种能力

`Registry::helper`注册随项目构建的`tool-helper`。
它支持原样echo、双路定量日志、有限sleep和指定非零退出。
这四种行为既可供CLI调用，也构成稳定、可重复的测试工具。
`Registry::fixed`注册管理员预先固定的可执行文件和argv。
请求使用`Input::Fixed`，不能替换其中任何参数。
这适合暴露一个固定lint或只读检查程序。
需要动态目录、文件名或配置的新工具，应新增适配器及验证规则。

| 注册入口 | 管理员固定的信息 | 请求可提供的信息 | 本轮用途 |
|:--|:--|:--|:--|
| helper | 绝对可执行文件路径、命名映射 | Echo、Logs、Sleep、Fail中的受限值 | CLI、真实进程测试、benchmark |
| fixed | 绝对路径、完整argv | 只能提供Fixed变体 | 固定工具集成、失败路径测试 |
| 未注册名字 | 无对应能力 | 任何Input均无执行目标 | UnknownTool拒绝 |
| 动态shell | 本项目不提供此入口 | 不接受命令字符串 | 不存在shell插值路径 |

注册时先canonicalize路径。
运行请求时使用已经保存的绝对路径，不搜索请求方的PATH。
CLI固定寻找与主程序同目录的`tool-helper`。
漏装helper会明确失败，不会悄悄执行另一个同名程序。
路径固定不能阻止管理员后来替换该路径上的文件。
所以canonicalize不是可执行文件内容认证。
本轮缺失可执行文件测试恰好利用了这种注册后变化。
它验证错误传播，不是针对路径替换攻击的完整防护。

::: def 定义 15.1.2 · 注册入口与请求能力 {#def-15.1.2}

**注册入口**指管理员把「一个可执行文件绝对路径 + 一种名字到参数的映射」交给库的动作；本项目只有两种：`Registry::helper`（受限的四种行为：Echo、Logs、Sleep、Fail）与 `Registry::fixed`（完整 argv 固定，请求只能提供 `Input::Fixed`）。**请求能力**指请求方在该入口下还能改什么——两种入口都不能改可执行文件，都不能改 argv，都拒绝未注册名字。不存在「传一个命令字符串」的第三种入口。

:::

::: ex 例 15.1.1 · 一个新工具该走哪条注册路径 {#ex-15.1.1}

管理员要暴露一个只读检查程序：它必须知道被检查的仓库目录，还要读一份自己的配置文件。请按本节的三种入口判断能不能直接挂上来，并写出拒绝或放行的理由。

::: sol 解答

三条路都不直接成立。`fixed` 要求 argv 在启动时全部固定，「被检查的目录」正是请求要变的部分，硬塞进去只能预先写死一个目录，等于换了个名字注册（[@def-15.1.2]）；helper 只认识四种受限行为，没有检查语义；动态 shell 入口本项目根本不提供，把目录名拼进一个命令字符串是把[@def-15.1.3]的类型化预算退回成自由文本，同时破坏了不经过 shell 的字节边界（15.1.4）。

正确做法是新增一个适配器：把目录与配置表达成有限字段，在[@def-15.1.3]的预算内校验，再决定它需要哪些环境与工作目录（[@def-15.1.4]）。适配器的验收条件写进[@def-15.1.1]的第三件事：结果里必须能看出直接子进程是否已被 wait、两路日志是否读完（15.4 节）。

:::

:::

### 15.1.3 参数预算是执行契约，不是序列化细节

`Input`将可接受请求压缩成有限的业务集合。
Echo最多4096字节，并拒绝内部NUL。
Logs每路最多16MiB。
Sleep最多60000毫秒。
Fail只接受非零的u8退出码。
超时预算必须大于零且不超过60秒。
固定argv最多32项，每项最多4096字节。
注册名字只接受有限长度的ASCII字母、数字与连字符。
这些边界使排队消息大小可以被分析。
它们不限制调用者在构造Input之前已经分配的对象。
接收网络请求的上层仍应先验证长度，再读取大正文。

::: def 定义 15.1.3 · 参数预算 input budget {#def-15.1.3}

**参数预算**指每个 `Input` 变体在构造阶段就被允许的最大内容：Echo 最多 4096 字节且拒绝内部 NUL，Logs 每路最多 16MiB，Sleep 最多 60000 毫秒，Fail 只接受非零 `u8`，timeout 大于零且不超过 60 秒，固定 argv 最多 32 项、每项最多 4096 字节，注册名只接受有限长度的 ASCII 字母、数字与连字符。超出预算是 `InvalidInput` 拒绝，不是截断后继续执行。

:::

::: ex 例 15.1.2 · 十万字节的 Echo 应该发生什么 {#ex-15.1.2}

调用方希望一次提交 100 KiB 文本给工具回显。给出三种可能的设计，并说明本项目选哪一种、为什么。

::: sol 解答

① 截断到 4096 再执行：结果看起来「成功」，实际工作内容和请求不一致，[@def-15.1.1]的第一件事被破坏；② 取消预算、按内容大小排队：单条排队消息就能吃掉任意内存，15.2 的 `Q` 个槽立刻失去意义；③ 直接返回 `InvalidInput`：请求方拿到明确拒绝，可以改走分块或另设工具。本项目选 ③。选完还要诚实地说清预算管到哪：它限制的是已进入队列的消息大小，不限制调用方在构造 `Input` 之前已经分配的对象——所以接收网络请求的上层仍要先验证长度再读正文，这条分工不属于[@def-15.1.1]交付的范围。

:::

:::

### 15.1.4 不经过shell的字节边界

库使用`Command::new(path).args(argv)`。
它没有调用`sh -c`，也没有构造带引号的整条命令行。
Echo里的分号、管道符和美元符号只是参数内容。
`echo_is_literal_even_with_shell_metacharacters`用真实helper验证这一点。
测试不需要通过创建危险文件来证明没有插值。
它直接比较完整stdout字节与输入字节。
对于固定工具，argv完全来自可信启动配置。

::: think 思考 · 元字符测试通过，能写成「这个库不会被注入」吗 {#think-15.1.1}

`echo_is_literal_even_with_shell_metacharacters` 比较了完整 stdout 字节与输入字节，分号、管道符和美元符号都原样回显。据此能不能在文档里写「本项目不存在命令注入」？

::: sol 解答

不能那样推广。这条测试证明的是一个**具体入口性质**：`Command::new(path).args(argv)` 这一条路径不经过 `sh -c`，参数内容不会被重新解释（[@def-15.1.2]）。它是有限结论，不是全局结论：管理员若主动注册一个解释器并让它执行危险脚本，本库没有沙箱机制阻止（[@def-15.1.4]）。第 1 章给过同型的教训——一个检查只在它覆盖的对象上成立（[@def-1.3.1]）；把入口性质写成系统性质，是最常见的一类越界。

:::

:::

### 15.1.5 环境、目录与标准输入也属于API

子进程使用空环境和`/`作为工作目录。
stdin配置为null，工具不会一直等调用方没有提供的输入。
stdout和stderr使用独立管道。
环境清空避免不经意继承上层凭据与配置。
但它也意味着依赖HOME、PATH或项目cwd的普通命令不能直接照搬。
本项目没有隐藏这些差异。
适配一个真实工具时，必须显式决定需要哪些环境与目录权限。
不能为了兼容性重新继承整个环境，然后仍声称接口没有变化。
Windows系统目录和进程语义没有在本轮运行。
本章的可运行范围是所记录的macOS桌面环境。

::: def 定义 15.1.4 · 范围声明 scope declaration {#def-15.1.4}

**范围声明**指把「不做什么」和「做什么」一起写进接口契约：子进程使用空环境（`env_clear`）、工作目录固定为 `/`、stdin 接 null、stdout 与 stderr 各用一条独立管道；不承诺文件、网络、内核配额隔离，不承诺清理后代进程，Windows 语义本轮未运行。空环境避免不经意继承凭据，同时意味着依赖 `HOME`、`PATH` 或项目 cwd 的普通命令不能照搬——这一条差异必须显式说明，而不是重新继承整个环境后仍声称接口没变。

:::

### 15.1.6 为什么这是runtime而不是一个block_on

外层由Tokio多线程runtime提供任务调度、进程I/O和计时器driver。
内部有一个长期dispatcher和多个受限工作任务。
工作之间可以交错推进，并且统一join收集。
本项目没有复制单Future驱动器，也没有手写未经验证的RawWaker。
工具并发数与Tokio worker数是两个配置维度。
两个worker可以治理四个等待I/O的直接子进程。
四个工具槽也不代表预留四个独占CPU。
理解这层区别，才能在后面的测量中正确解释聚合吞吐。

::: def 定义 15.1.5 · 直接子进程与两层并发 {#def-15.1.5}

**直接子进程**指本进程用 spawn 亲手创建的那一个子进程，只有它的 pid 能被本项目 wait；它的后代是「孙级及以下」，本项目既不追踪也不回收（对照 15.4 节）。**两层并发**指工具并发数 `C`（同时被允许推进的工作任务数）与 Tokio worker 数（执行这些任务的线程数）是两个独立配置：两个 worker 可以治理四个等待 I/O 的直接子进程，四个工具槽也不代表预留四个独占 CPU。15.7 节的例题解释聚合吞吐时必须把这两层分开。

:::

### 15.1.7 可运行CLI入口

从`cpp-rust/projects/agent-runtime/`执行：

```bash
cargo build --offline --locked --bins
./target/debug/agent-runtime echo 'literal ; $HOME | $(not-a-command)'
./target/debug/agent-runtime logs 65536
./target/debug/agent-runtime sleep 5000 100
./target/debug/agent-runtime cancel 5000 100
./target/debug/agent-runtime fail 17
```

成功返回退出码0。
NonZero、TimedOut、Cancelled返回1，是业务结局而不是程序崩溃。
输入或观察协议错误返回2。
日志前缀通过Debug转义输出，不把控制字节直接解释成终端命令。
库中的Log仍保存原始字节，不做有损UTF-8转换。
CLI展示层的字符串显示不能反过来充当二进制日志协议。

::: method 判定流程 · 一个请求能不能被这个 runtime 执行

① **名字在注册表里吗**：不在就 `UnknownTool`，参数不再解析（[@def-15.1.2]）。<br>
② **参数在预算里吗**：超限、含 NUL、退出码为零都拒绝，不截断（[@def-15.1.3]）。<br>
③ **timeout 合法吗**：零或超过 60 秒是 `InvalidInput`（见 15.3 节）。<br>
④ **还有总许可吗**：`Q+C` 用尽返回 `Full`（[@def-15.2.1]）。<br>
⑤ **执行语义在声明范围内吗**：需要动态参数、环境变量、目录权限或后代清理时，回到[@def-15.1.4]，这不是把一个字符串塞进 argv 能解决的。<br>
五步都过，才进入 15.3 的状态机。

:::

### 15.1.8 小结与常见错误

**小结。**① 本项目交付的是[@def-15.1.1]意义上的有界执行器，不是任意程序沙箱（[@def-15.1.4]）；② 只有两种注册入口，请求能改什么被[@def-15.1.2]钉死，不存在命令字符串入口；③ 参数预算是执行契约而不是序列化细节（[@def-15.1.3]），它使排队消息大小可分析，是 15.2 上界证明的前提；④ 「不经过 shell」是一条具体入口性质，不能推广成系统性质（[@think-15.1.1]）；⑤ 工具并发与 worker 数是两层配置（[@def-15.1.5]），后面的吞吐解释都依赖这个区分。下一节 [15.2 在 spawn 之前建立有界准入](#sec-cpp-rust.4.15.2) 把这些边界变成可核对的上界。

::: errata 常见错误清单（15.1 节）

E-a **以为 canonicalize 和空环境就是沙箱。**它们固定入口并减少继承状态，但不限制文件、网络或后代，管理员仍能注册危险工具（[@def-15.1.4]）。

E-b **用「没有 shell 插值」推断「不可能被注入」。**前者是入口性质，后者需要隔离机制（[@think-15.1.1]）。

E-c **把所有动态参数塞进一个字符串来「快速支持一切」。**同时丢掉[@def-15.1.2]的类型化能力和不经过 shell 的字节边界（[@ex-15.1.1]）。

E-d **截断超限输入继续执行。**结果与请求不是同一份工作，应返回 `InvalidInput`（[@ex-15.1.2]）。

E-e **为了兼容性重新继承整个环境**，然后仍声称接口没有变化（[@def-15.1.4]）。

E-f **把四个工具槽读成四个独占 CPU。**`C` 与 worker 数是两个维度（[@def-15.1.5]）。

:::

::: method 即时自测 · 15.1

先合上正文作答，再展开核对。

::: sol 第 1 题答案

## 15.2 在spawn之前建立有界准入 {#sec-cpp-rust.4.15.2}

本节回答一个问题：**要挡住过载，上界必须建在哪几个地方，又为什么不能只建一个？**15.1 定下了「接不接受」（[@def-15.1.3]）；本节接手「接受之后谁持有资源」，把队列容量、运行槽与总许可分开证明，并在[@ex-15.2.1]里从一份具体工作负载把上界推出来。

::: preview 先抓住一件事

三个上界回答三个不同问题：只有 `Q` 挡不住无限 spawn，只有 `C` 挡不住上游积压，「先 spawn 再等信号量」会留下一堆永远等待的任务。真正可证明的口径是：**在创建工作任务之前拒绝**，并且许可确实随工作持有而不是随调用方持有。
:::

### 15.2.1 三个不同的上界

::: def 定义 15.2.1 · 三层上界 Q、C、R {#def-15.2.1}

**Q**（队列容量）是有界 mpsc 里可以同时存放的未处理 Job 数；**C**（工作任务上限）是 dispatcher 的 JoinSet 在同一时刻最多持有的工作任务数，也是直接子进程数上界；**R**（每路日志保留长度）是每个 Job 的两路日志各自保留的前缀字节上限。总准入许可数取 `Q+C`，覆盖「排队中」与「已接受但正在提交」两类持有。三个数各挡一类失控：Q 挡上游积压，C 挡无限 spawn，R 挡日志留存；缺任何一个都会留下无界集合（见[@ex-15.2.1]）。

:::

设Q为队列容量，C为工作任务上限，R为每路日志保留长度。
项目使用有界mpsc存放尚未交给工作任务的Job。
dispatcher只有在JoinSet长度小于C时才接收下一项。
每个Job还持有一个总准入许可。
总准入许可数设为Q+C。
许可先取得，再构造通道和排队消息。
`try_submit`同步完成；它不会创建等待发送的任务。

| 资源集合 | 约束机制 | 对应上界 | 不包括什么 |
|:--|:--|--:|:--|
| 通道中排队Job | mpsc容量 | Q | 运行任务、调用者对象 |
| 已spawn但尚未join的工作 | JoinSet接收守卫 | C | dispatcher自身 |
| 提交过程中及已接受的工作 | OwnedSemaphorePermit | Q+C | 已返回且由用户长期保存的结果 |
| 每个工作保留的日志内容 | 两个Log前缀 | 2R字节长度 | Vec容量、任务元数据、内核管道 |
| 单次管道读取缓冲 | 两个固定数组 | 各8192字节 | 编译器Future整体布局 |

这些界分别回答不同问题。
只有Q而没有C，会让消费方无限spawn。
只有C而没有Q，会让上游积压无限请求。
只有信号量但先spawn等待许可，会留下无限等待任务。
本实现同时约束入口、队列与运行集合。
许可预算也覆盖多个调用线程同时进入try_submit的临时阶段。
但Client本身可以无限克隆，这不是本库限制的对象。

::: ex 例 15.2.1 · 从一份工作负载推出准入上界 {#ex-15.2.1}

`Config::default()` 给出 `Q=16`、`C=4`、`R=8192`、`drain_grace=1s`。现在一批 8 个「双路各写 262144 字节」的工具同时到达（就是 15.7 节例题的负载）。请推出：总许可数、此刻通道里最多几个 Job、同时最多几个直接子进程在跑、这一批的用户态日志保留内容上界，以及哪些数字不在这个预算里。

::: sol 解答

总许可 `Q+C=20`，8 项请求都在预算内，因此 8 次 `try_submit` 都能拿到许可。运行槽上界是 `C=4`：dispatcher 只在 JoinSet 长度小于 4 时才 recv，所以同时最多 4 个直接子进程（[@def-15.1.5]），其余 4 项留在队列里，队列此刻持有 4 个 Job，仍不超过 `Q=16`。日志保留长度按每路 `R` 计：8 项 × 2 路 × 8192 = 131072 字节**有效前缀长度**上界；而每项实际读取的是 524288 字节，超出前缀的部分只进 total 与 checksum，不再存储（3.4.3 的保留规则）。

不在这一预算里的：Vec 容量与分配器（负责申请和归还堆内存的那层代码）元数据、路径与 argv、watch 与 oneshot 的共享状态、任务头、两个各 8192 字节的读取缓冲，以及内核管道自己的缓冲（见 15.2 节）。还有一个易错点：8 项都提交成功这件事，并不能由「总许可还有余量」保证——初始突发见[@ex-15.2.2]。

:::

:::

::: def 定义 15.2.2 · 拒绝路径 fast-fail path {#def-15.2.2}

**拒绝路径**指 `try_submit` 在取得总许可失败（或更早）时返回错误的那段代码：检查关闭状态 → 检查 timeout → 尝试总许可 → 解析注册项 → 构造消息 → `try_send`。饱和时路径停在第三步，不创建 watch、oneshot 与 Job。它的成本因此显著低于成功路径，15.6 单独测它并明确单位（15.6 节）；反过来，「先 spawn 一个任务再去等有界队列」不是拒绝路径，那是把无界集合换成了无限等待任务。

:::

### 15.2.2 准入顺序决定失败路径的成本

实际顺序是检查关闭状态、检查timeout、尝试总许可、解析注册项、创建消息、try_send。
因此满载时可以在创建watch和oneshot之前返回。
这也是第15.6节拒绝benchmark测得很短路径的原因。
它不是成功提交路径的完整成本。
解析名字和校验参数也可能在总许可不足时被跳过。
所以错误优先级不是「永远先UnknownTool再Full」。
本项目的饱和测试明确期待Full。
鉴权应由更外层独立完成，不能依赖错误优先级判断工具是否存在。

### 15.2.3 容量不是未来成功的预约

try_acquire_owned成功后，try_send仍可能遇到Full或Closed。
例如多个提交者与dispatcher存在交错。
总许可和通道容量并不是同一个计数器。
失败时局部Job被销毁，owned permit随之归还。
不需要手工在每个错误分支加一个减计数操作。
但这不是「RAII自动理解所有业务资源」的证明。
正确性依赖许可确实被放进代表真实工作的Job里。
若许可只存于调用方栈上，返回Ticket时就会过早释放。

::: think 思考 · 把许可挂在 Ticket 上，调用方一走就自动归还，不是更省事吗 {#think-15.2.1}

`OwnedSemaphorePermit` 是 owned 句柄，放进 `Ticket` 就会随 Ticket 一起析构。这样「没人等了就归还预算」看起来完全自动化，为什么本项目坚持把它放进 Job（`_admission` 字段）？

::: sol 解答

因为许可表示的对象不是「调用方还愿意等」，而是「还有一份真实工作没收拾完」（15.3 节）。调用方超时并丢弃 Ticket 时，直接子进程可能正处在 kill 与 wait 之间；此时归还许可等于凭空放大真实并发，让[@def-15.2.1]的 `C` 失去意义。RAII 只对「谁持有就负责什么」这个前提下成立：把它放到错误的持有者上，自动化得越干净，错得越安静。这也是第 1 章「观察集合」的同一条纪律——归还时机必须是你真正观察到的事件，不是最方便的那个析构点（[@def-1.3.1]）。

:::

:::

### 15.2.4 入口不能承诺初始突发一定接满Q+C

runtime刚启动时，dispatcher可能尚未得到调度。
这时通道最多先接受Q项。
即使总许可还有余量，第Q+1次try_send也可能立即Full。
Q+C是总体持有上界；「初始同步提交一定接满 Q+C」这句话要另立契约才成立。
需要等待的提交接口可以另外设计有限等待期限。
本项目选择直接拒绝，使上游可以快速返回过载。
调用方若用无限自旋重试补位，就等于在库外挂出一个没人记账的无界等待队列；重试策略要自带上界。
正常做法是限制重试次数、退避和请求整体期限。
这些策略没有被伪装成库已经提供的功能。

::: ex 例 15.2.2 · 第 Q+1 次提交为什么可能立刻 Full {#ex-15.2.2}

runtime 刚启动，dispatcher 还没被调度到。调用方连续调用 `try_submit`，`Q=16`、`C=4`。第 17 次提交拿到许可了吗？它会不会成功？

::: sol 解答

许可拿得到（总数 `Q+C=20`，此前只用了 16），但 `try_send` 会返回 `Full`，因为通道容量只有 16 且没有消费者被调度。于是局部 Job 被销毁，许可随析构归还——不需要手工减计数，也不需要额外的错误分支（15.2.3）。结论要写成两句：`Q+C` 是**总体持有上界**，不是**初始同步提交成功数下界**；需要等待的接口要另外设计有限等待期限，本项目选择直接拒绝，让上游快速拿到过载信号。调用方若用无限自旋重试来「补出」等待队列，等于把无界集合搬到库外（15.6 节）。

:::

### 上界证明要覆盖提交中的对象

令P为已经取得许可但尚未完成try_send的调用数。
令W为已接受且未结束的工作数。
许可不被复制，所以P+W不超过Q+C。
每个运行Future仅由dispatcher在空闲槽下spawn。
JoinSet中的完成但未join项仍占槽，因此其长度不超过C。
通道本身最多持有Q项。
这些关系在成功、拒绝、取消与正常关闭路径都成立。
它们不需要假设任务完成顺序等于提交顺序。
它们也不承诺每项获得相同服务时间。

### 内存预算必须写清长度和容量

Log的prefix长度始终不超过R。
Vec分配器可能保留比长度更大的容量。
所以「2R字节」只描述两路有效内容长度；进程 RSS 的精确公式要按实际分配另算。
路径、argv、oneshot、watch、任务头与分配器元数据还占内存。
默认helper请求长度有限，固定argv也有启动时边界。
固定可执行文件的绝对路径长度由本地文件系统配置决定。
内核管道容量不由Rust的Vec决定。
资源预算表必须区分用户态可控内容和操作系统内部缓冲。

### 与母本通道模型的关系

本轮核读S11物理页390–394。
其中通道发送转移值的所有权，克隆发送端允许多个生产者。
本项目沿用的是所有权交接与关闭后收集的思想。
它没有把标准库阻塞recv直接放进Tokio任务。
Tokio有界mpsc的异步调度性质来自固定版本实现，不来自母本示例。
母本中的「发送后不能继续使用原值」能排除一类内存错误。
本项目还必须额外证明容量、运行槽与清理责任。
所有权语言机制垫在协议底下，资源政策仍要显式写出来。

::: errata 常见错误清单（15.2 节）

E-a **只设 Q 就以为挡住了过载。**没有 C，消费方照样可以无限 spawn；三个数各挡一类失控，缺一个就留一个无界集合（[@def-15.2.1]）。

E-b **先 spawn 任务再去等有界队列。**那不是拒绝路径，只是把无界集合换成一堆永远等待的任务（[@def-15.2.2]）。

E-c **把 Q+C 当成初始突发一定接满的数。**dispatcher 未被调度时通道只能先收 Q 项，第 Q+1 次 `try_send` 立即 `Full`；Q+C 是总体持有上界，不是成功数下界（[@ex-15.2.2]）。

E-d **把许可挂在调用方的 Ticket 上。**归还条件就成了「没人等了」，而直接子进程可能正在 kill 与 wait 之间，等于凭空放大并发（[@think-15.2.1]）。

E-e **把「2R 字节」当内存占用。**prefix 长度不超 R，但 Vec 容量、路径与 argv、任务头、分配器元数据和内核管道都不在这笔账里。

E-f **用无限自旋重试补出等待队列。**库外就多出一个没人记账的无界集合；重试要自带次数上界、退避与请求整体期限（15.2.4）。

**第 1 题 · 记忆**　Q、C、R 各是什么、各挡哪一类失控？总许可为什么取 `Q+C`，只取 `Q` 或只取 `C` 各漏了什么？

::: sol 第 1 题答案

## 15.3 取消请求、状态观察与许可寿命 {#sec-cpp-rust.4.15.3}

本节回答一个问题：**调用方发出取消并离开之后，库凭什么说这项工作还在被负责？**15.2 把许可放进了 Job（[@def-15.2.1]）；这一节沿同一条所有权链，看取消怎样进入状态机、哪些观察点能证明回收，以及为什么「没有人在等结果」不等于「工作可以丢掉」。

::: preview 先抓住一件事

取消是**意图**，不是**完成**。`Ticket::cancel` 只写一个 watch 位；回收结论来自三处证据：wait 成功、两路 EOF、任务 join。判定口径是：只要还能指出「谁持有许可、谁还没被 join」，就不能说工作已结束；反过来，也不能拿阶段快照的最后一帧替代最终结果。
:::

### 15.3.1 两个通道表达两种方向

每个 Job 有一个 watch 接收端观察取消意图，Ticket 持有相应发送端。<br>
工作结果经 oneshot 从工作任务流向 Ticket；另一个 watch 提供当前 Stage，便于观察子进程已经 spawn。<br>
取消、阶段与最终结果是三个不同用途：「收到了取消消息」说的是意图登记，「已经完成清理」要等回收证据；Stage 的最后值只给出一帧快照，完整事件日志要另行记录。<br>
watch 允许合并中间状态；真正的回收结论来自最终 ToolResult 和任务 join。

::: def 定义 15.3.1 · 取消意图与阶段观察 cancel intent and stage watch {#def-15.3.1}

**取消意图**是 Ticket 通过 watch 写下的一个布尔位，表示「请求停止」，它可被 `send_replace` 覆盖、可在多个中间值之间合并，因此读到一个 `true` 只说明请求已登记。**阶段观察**是另一个 watch 给出的 Stage 快照（Queued、Running(pid)、Reaped、Finished 等），它只说明本次读取时看到的最后状态，不是事件日志，也不构成回收凭证。两者都不能替代最终 `ToolResult`。

:::

### 15.3.2 状态机中的责任不对称

| 状态 | 仍由谁持有许可 | 可以创建Child吗 | 调用方可以观察什么 |
|:--|:--|:--|:--|
| 提交中 | 提交局部变量/Job | 不可以 | 同步接受或拒绝 |
| Queued | 通道中的Job | 不可以 | Ticket存在、可请求取消 |
| Running(pid) | 工作Future | 已有直接子进程 | started的当前状态 |
| 停止请求已登记 | 同一工作Future | 不再新建 | 还不能宣称已回收 |
| wait成功 | 同一工作Future | 不再新建 | Stage可能为Reaped |
| 排空/排空超时 | 同一工作Future | 不再新建 | 结果尚未交付 |
| Finished | 工作即将结束 | 不可以 | oneshot最终结果 |
| 已join | 工作已经退出 | 不可以 | shutdown聚合观察 |

取消只是从 Running 进入停止路径的触发条件之一；超时也是同类触发条件，自然退出则可以直接让 wait 分支获得结果。<br>
三个事件可能同时就绪，select 选择哪个分支不构成跨线程的绝对时间顺序证明。<br>
所以结局应解释为「本执行器观察到的状态转换」；若业务需要严格的「截止前已完成即算成功」规则，还要定义更强的线性化点（并发操作在外界看来「生效」的那一个瞬间），本项目没有偷偷承诺这条规则。

::: def 定义 15.3.2 · 许可寿命 permit lifetime {#def-15.3.2}

**许可寿命**指一个 `OwnedSemaphorePermit` 从 `try_submit` 取得开始，到持有它的 Job 字段（`_admission`）随工作 Future 析构为止的区间。它绑定的是「还有一份真实工作没收拾完」，不是「调用方还愿意等」；调用方超时、丢弃 Ticket 或关闭连接，都不会缩短这段寿命。

:::

### 15.3.3 Ticket 的 Drop 不 abort 工作任务

实现的关键语义可以缩成下面几行，完整上下文在 `src/lib.rs`。

```rust
impl Ticket {
    pub fn cancel(&self) {
        self.cancel.send_replace(true);
    }

    pub async fn wait(mut self) -> Result<ToolResult, oneshot::error::RecvError> {
        (&mut self.result).await
    }
}

impl Drop for Ticket {
    fn drop(&mut self) {
        self.cancel.send_replace(true);
    }
}
```

如果调用方丢弃 Ticket，工作仍存在于 dispatcher 的 JoinSet 中，取消位会驱动它进入 kill、wait 与排空路径。<br>
不再有结果接收者时，oneshot 发送失败属于正常放弃观察，Job 仍要完成自己的资源处理。<br>
因此「没有人在等响应」不等于「工作可以无条件被丢弃」。<br>
如果库把 JoinHandle 直接交给用户，用户可能 abort 整个清理 Future；本项目故意不暴露这种能力，让取消方式保持为业务协议，而不是任意析构工作状态。

### 15.3.4 owned permit 为什么放在 Job 里

许可表示尚未结束的真实工作占用（[@def-15.3.2]），不表示「调用方还愿意等」。<br>
调用方超时并丢弃 Ticket 后，直接子进程仍可能处于终止途中，许可必须继续占用，直到 wait 和排空已被处理。<br>
Job 的 `_admission` 字段把许可带入工作 Future，工作发送最终结果后才到达字段析构阶段。<br>
这意味着响应观察与许可归还之间可能有极短的调度间隙，上层不应期待 wait 返回后紧接着的一次提交必定成功；但系统不会因为调用方离开而提前放大真实并发。

### 15.3.5 运行槽与总许可是两层机制

本实现没有为每个工作再取得第二个运行信号量：JoinSet 长度就是运行槽的所有权集合。<br>
只要工作还没有被 join 收走，dispatcher 就不会把它的槽交给新 Job；这比「启动后立即从 active 集合删除」更保守，完成但尚未 join 的任务仍计入 C（两层并发的定义见[@def-15.1.5]）。<br>
这种保守性减少了短时超额 spawn 的机会，代价是 dispatcher 必须及时收集完成项。<br>
本轮没有单独测量这种保守收集造成的调度开销。

### 15.3.6 排队取消与 timeout 的边界

排队 Job 尚未拥有直接子进程：当 dispatcher 取得下一项时，先检查取消位与绝对 deadline，已取消或过期的 Job 直接返回结构化结局，pid 保持 None。<br>
因此取消不一定立刻让队列槽空出来，一个排在长任务后面的取消项，可能要等运行槽可用才被处理。<br>
这是项目明确选择的简单队列语义：不为每个排队项再创建一个 timer 任务，也不承诺 deadline 到达就立即给调用方返回结果。

deadline 从成功提交路径中的 accepted 时间点计算，排队时间包含在这份预算内。<br>
一旦工作开始时已经过期，就不会再 spawn 一个过期工具；运行期间观察到 deadline 后发出 kill 请求，随后仍必须等待操作系统确认直接子进程退出。<br>
如果 wait 长期不返回，安全的库不能编造 reaped=true 来满足超时响应，所以请求 timeout 不是 cleanup 的硬实时上界。<br>
本项目优先保持清理责任可观察，而不是在清理未完成时假称一切结束。

### 15.3.7 started 提供什么证据

`Ticket::started` 等待 Stage 不再是 Queued；若当前值为 Running，就返回其 pid。<br>
长 sleep 测试据此确认已经实际 spawn，再发送取消，这优于固定 sleep 一段时间后猜测「应该启动了」。<br>
对很短的 echo，调用方可能只看到 Finished；这种返回 None 不证明工具从未 spawn，只说明当前 watch 快照没有可返回的 Running 状态（[@def-15.3.1]）。<br>
要判断最终是否创建过 Child，应读取 ToolResult.pid；阶段观察只说明读取时刻的形状，最终结论仍要靠持久证据。

::: ex 例 15.3.1 · 丢弃 Ticket 之后，许可什么时候归还 {#ex-15.3.1}

调用方提交一个 `Sleep(60000)` 工具，timeout 为 1 秒，拿到 Ticket 后立刻 drop，既不调用 `cancel` 也不等待结果。请判断：工作会立即停止吗？许可何时归还？这次提交会出现在 shutdown 的 join 计数里吗？

::: sol 解答

Drop 会立即执行 `send_replace(true)`，所以取消意图马上登记（[@def-15.3.1]）；但工作仍在 dispatcher 的 JoinSet 里。已 spawn 时它走 kill、wait 与双路排空（15.4 节）；尚未被取到时，dispatcher 取到后直接返回结构化结局，pid 保持 None（15.3.6）。两条路径下许可都由 Job 的 `_admission` 持有，只有工作 Future 走完才析构，所以 drop 之后许可仍被占用（[@def-15.3.2]）——这正是「没人等结果不等于可以丢弃工作」的机制。oneshot 没有接收者，发送失败按正常放弃观察处理，不产生泄漏。最终 shutdown 的 join 数量仍包含这一项，因为 dispatcher 从不因调用方离开而跳过 join。结论要写成三句：drop 即登记取消；许可随工作结束归还；join 计数不因 Ticket 消失而减少。

:::

::: think 思考 · Stage 快照显示 Running，就能证明子进程还活着吗 {#think-15.3.1}

`started` 返回了 pid，说明 Stage 曾经是 Running。能不能据此断言「此刻子进程一定还在运行」？

::: sol 解答

不能。watch 允许合并中间状态，读到 Running 只说明读取时刻观察到的最后阶段是 Running；进程可能已经退出而阶段尚未推进，也可能已进入停止请求（15.3.2 的状态机）。要证明「已回收」，需要最终 ToolResult 里的 reaped 与 pid；要证明「此刻活着」，只能在操作系统层观察该 pid。阶段快照的作用是减少猜测——例如测试用它替代固定 sleep——而不是充当最终证据（[@def-15.3.1]）。

:::

::: method 判定流程 · 从一次取消到「可宣称回收」

① **取消意图登记了吗**：`cancel` 或 Ticket 的 Drop 已写入 watch 位（[@def-15.3.1]）。<br>
② **Child 存在过吗**：`started` 读到 Running(pid)，或最终 `ToolResult.pid` 非 None（[@def-15.3.1]）。<br>
③ **停止请求发出去了吗**：已 spawn 的工作由停止路径调用 `start_kill`，但发信号不等于回收（15.4 节）；未 spawn 的排队项则直接以结构化结局结束。<br>
④ **wait 确认了吗**：reaped 为 true；wait 出错则记 `WaitFailed`，不能写成已回收。<br>
⑤ **两路排空了吗**：stdout 与 stderr 都 EOF，或 drain_grace 到期并记录排空错误（15.4 节）。<br>
⑥ **任务 join 了吗**：shutdown 计数包含它，许可才随 Job 析构归还（[@def-15.3.2]）。<br>
六步缺任何一步，结论就停在「已请求停止」；「已清理」这句要等六步齐了才写。

:::

### 15.3.8 小结与常见错误

**小结。**① 取消意图与阶段观察是两种 watch 语义，都不能替代最终结果（[@def-15.3.1]）；② 许可寿命绑定真实工作而不是调用方耐心（[@def-15.3.2]）；③ Ticket 的 Drop 只登记取消，不 abort 清理；④ 排队取消与 timeout 都只约束继续执行意图，不承诺硬实时回收；⑤ 回收要沿 kill、wait、EOF、join 逐步观察。下一节 [15.4 直接子进程 wait 与双路日志排空](#sec-cpp-rust.4.15.4) 展开第 ④⑤ 步。

::: errata 常见错误清单（15.3 节）

E-a **把「收到取消」写成「已清理」。**先查 wait 是否成功、两路是否 EOF（[@def-15.3.1]）。

E-b **用 Stage 快照当最终证据。**先查 `ToolResult.pid` 与 reaped，快照会被合并（15.3.7）。

E-c **以为丢弃 Ticket 会归还许可。**许可在 Job 里，随工作结束才析构（[@def-15.3.2]）。

E-d **把 timeout 当成清理硬上界。**先查 wait 是否返回；库不能伪造 reaped。

E-e **直接向用户暴露 JoinHandle。**用户可以 abort 清理 Future，破坏取消协议（15.3.3）。

E-f **认为排队取消会立刻腾出队列槽。**先查 dispatcher 是否已取到该项（15.3.6）。

:::

## 15.4 直接子进程wait与双路日志排空 {#sec-cpp-rust.4.15.4}

本节回答一个问题：**子进程已经 wait 成功，这项工作还差哪几个观察点才算清理完成？**15.3 把回收拆成 wait、EOF、join 三个观察点；这一节解释为什么 EOF 必须和 wait 同权，以及排空期限、保留长度和 CLOEXEC 各自改变了哪条前进条件。

::: preview 先抓住一件事

wait 与 EOF 是**两个事件**：子进程退出不保证管道写端全部关闭，读完 stdout 再去读 stderr 也能把双方锁死。可宣称回收的条件是「wait 成功 + 两路各有结论（EOF 或记录的排空错误）+ 任务 join」；`drain_grace` 到期只允许记录错误，绝不允许伪造 EOF。
:::

### 15.4.1 管道没有无限缓冲的义务

helper 的 logs 模式交替向 stdout 和 stderr 写 8192 字节块，总输出可以远大于系统管道容量。<br>
如果父进程先把 stdout 读到 EOF，再读取 stderr，子进程可能卡在 stderr 写入；此时子进程不会退出，stdout 也就不会出现 EOF。<br>
父进程等待 stdout EOF，子进程等待 stderr 空间——这是一条完全可以用安全 Rust 写出的等待环，不需要数据竞争，也不需要非法指针。<br>
「语言内存安全」与「系统协议能前进」是不同的证明。

::: def 定义 15.4.1 · 双路排空 dual-stream drain {#def-15.4.1}

**双路排空**指在子进程退出前后持续同时推进 stdout 与 stderr 两条读取，直到每一路都得到结论：读到 EOF，或读取出错，或排空宽限到期被关闭。两个「结论」是分开记录的，不允许用一路的 EOF 推断另一路，也不允许用 wait 成功替代任何一路。

:::

### 15.4.2 一份工作 Future 同时推进五类事件

运行阶段 select 的候选项包括 child.wait、取消、deadline、stdout 读取和 stderr 读取。<br>
任一路读取完成就更新相应 Log，再回到选择循环；read 使用固定缓冲，不以整份输出大小分配 Vec，已 EOF 或已报读取错误的分支被停用，因此一个持续就绪的 EOF 分支不会占据空转循环。<br>
wait 成功后退出运行阶段，但不立即丢弃管道：子进程退出与「管道全部数据被读取」是两个事件，各有各的观察点（[@def-15.4.1]）。

```text
Running
  ├─ stdout有字节：计数、校验、有限保留，继续
  ├─ stderr有字节：计数、校验、有限保留，继续
  ├─ 取消或deadline：start_kill，继续wait和读取
  └─ wait成功：记录reaped与状态，进入排空阶段

Draining
  ├─ 两路都EOF：完成
  ├─ 读取错误：记录对应错误，不伪造EOF
  └─ drain_grace到达：关闭未完成读端，记录排空错误
```

运行阶段没有另行 spawn 两个日志任务，这使直接子进程、两个读端与日志状态都由同一工作 Future 独占持有。<br>
普通取消不会遗留独立 reader 任务等待 EOF，也无需让多个任务共享一个带锁的 Log。<br>
这种设计适合本项目有限的工具并发和日志处理量；它不表示所有高吞吐日志系统都应使用单 Future 治理——若校验或解析很重，仍可能需要独立、受限的处理域。

### 15.4.3 select 中的读取消安全

当 stdout 分支 Pending 而 stderr 先完成时，stdout 那次 read Future 会被丢弃。<br>
使用的 read 操作不会像多步骤协议那样偷偷消费一半业务帧却丢失偏移；每次成功读取后立即把字节记入 Log。<br>
本项目处理的是原始字节流，不把一次 read 误当成一条消息。<br>
如果改成 read_exact 或多段解码，必须重新审核取消安全性——不能因为 await 仍在同一个函数里，就假定所有 I/O 组合都可任意取消。<br>
固定版本 Tokio 的 wait 也明确具有 cancel-safe 契约，因此每次选择别的分支后继续 wait 不会丢掉原 Child。

### 15.4.4 start_kill 不是回收凭证

本轮核读 Tokio 1.54.0 进程模块的 start_kill、kill 与 wait 说明。<br>
在 Unix 上 start_kill 相当于发出 SIGKILL，但不等待效果；成功发出信号之后，仍可能需要 wait 释放僵尸资源。<br>
库在停止请求后继续 select child.wait；wait 返回成功才将 reaped 设为 true。<br>
信号退出时 exit_code 可以为 None，这不意味着进程仍在运行；项目保存业务 Outcome 和 exit_code 两个维度，而不把它们压进同一个整数。

::: def 定义 15.4.2 · 回收观察点 reaped {#def-15.4.2}

**回收观察点**指父进程确实观察到直接 Child 的 wait 返回成功的那一刻，项目中记为 `reaped=true`。它只覆盖本进程亲手 spawn 的那一个子进程（[@def-15.1.5]），不覆盖它的后代，也不等于两路日志已经读完（[@def-15.4.1]）；wait 出错时结果是 `WaitFailed` 且 `reaped=false`。

:::

### 15.4.5 为什么不只调用 kill_on_drop

项目设置 kill_on_drop(true) 作为异常析构兜底，但正常路径不会依赖 Child 析构来完成回收。<br>
Tokio 文档说明后台回收是 best effort，对它什么时候完成没有任何承诺；显式 wait 是本项目「观察到清理」的核心证据。<br>
当 wait 发生错误，结果标成 WaitFailed 且 reaped=false，清理错误字符串也会保留。<br>
这条罕见系统错误路径没有被伪装成已经成功释放所有资源；本轮未通过故障注入制造内核 wait 失败。

### 15.4.6 有限保留与持续排空是两个动作

`Log::record` 首先更新全部已读字节的 checksum 和 total，然后才计算还能保留多少前缀字节。<br>
当 prefix 已达 R，后续数据仍参与读取、计数与校验；R=0 意味着不保留内容，不意味着停止读管道。<br>
这正是防止「日志已满后工具突然卡住」的关键：如果达到 R 就关闭读端，工具可能看到 BrokenPipe 或信号退出；如果达到 R 就不再读取，工具可能一直等待管道空间。<br>
两者都改变了工具语义，「单纯减少日志内存」这个说法盖不住它们。

::: def 定义 15.4.3 · 保留前缀与全量校验 retained prefix and full checksum {#def-15.4.3}

**保留前缀**是每路日志实际存下来的前 R 个字节，长度不超过 R；**全量校验**是对父进程读到的全部字节计算的 FNV-1a 递推，与保留多少无关。R=0 时前缀为空，但 total 与 checksum 仍覆盖全部输出；因此「R=0」不等于「没有日志处理成本」（15.5 节的汇编给出证据）。

:::

### 15.4.7 完整性字段的精确定义

| 字段 | 可以支持的解释 | 不能支持的解释 |
|:--|:--|:--|
| prefix.len | 当前保留的前缀长度 | 工具只输出了这些字节 |
| total | 父进程实际读到的累计字节数 | 工具在所有后代上产生的总输出 |
| checksum | 全部已读字节的FNV-1a | 密码学认证或防恶意篡改 |
| eof | 这一路read确实返回0 | 另一条流也完成 |
| error | 读取或排空期限错误 | 子进程必定非零退出 |
| reaped | 直接Child的wait成功 | 整个进程树都已退出 |

读取错误和业务退出码相互独立；Success 但日志未 EOF，仍可能是不完整结果。<br>
CLI 因此联合检查 Outcome、reaped、EOF 和 cleanup_error；库调用者也应根据自己的业务需要制定成功条件。<br>
只检查 outcome==Success 会丢失日志完整性信息。

### 15.4.8 后代持有管道时的诚实边界

直接子进程可能创建后代并让后代继承 stdout 或 stderr；直接子进程 wait 成功，不保证这些写端已经关闭。<br>
排空阶段设置 drain_grace，用于限制继续等 EOF 的时间；到期时保留已经收集的 prefix、total 和 checksum，并记录 error。<br>
本库不会因此杀后代，也不会声称后代已被回收。<br>
本轮没有实现或测试进程组终止、daemon 追踪或权限隔离；需要此类能力，应在受支持 OS 上增加进程组或作业对象协议与专门测试。<br>
把 kill 一个 pid 描述成「清理整个工具树」，会抹掉最重要的资源边界。

::: def 定义 15.4.4 · 排空宽限 drain_grace {#def-15.4.4}

**排空宽限**是进入 Draining 后允许继续等待两路 EOF 的最长时间，默认 1 秒。它是一份观察预算，清理保证要另立：到期后关闭尚未完成的读端、记录排空错误，已经读到的 prefix、total 与 checksum 全部保留，后代进程不受影响（[@def-15.4.1] 的「各有结论」由此完成）。

:::

### 15.4.9 另一条 EOF 故障：无关 spawn 继承了额外写端

后代有意继承 stdout 不是唯一的写端来源。<br>
项目初稿使用 `Command.stdout(Stdio::piped()).stderr(Stdio::piped())`，这个安全 API 没有承诺本机实现的管道创建与 CLOEXEC 标记是单一原子动作。<br>
Rust 1.99.0 的 macOS 实现先调用 pipe，再对两个描述符分别设置 FD_CLOEXEC；若无关线程在中间窗口调用 posix_spawn，就可以复制尚未标记的描述符。<br>
本机被核读的 spawn flags 没有 POSIX_SPAWN_CLOEXEC_DEFAULT 兜底。<br>
后来父进程再补标记，另一个进程的 FD 表早已复制完成，改不回去了。<br>

这不是 Rust 内存数据竞争，但它破坏了进程间资源隔离与 EOF 进展条件。<br>
本项目的命名工具可以并发启动，因此确实暴露于这条已证实的机制；不能用「罕见」或「再跑几次都过了」来取消修复义务。

```text
工具工作A                         无关spawn B
pipe返回：read/write尚无CLOEXEC
                                 posix_spawn复制额外FD
                                 B再启动短寿命后代
fcntl设置父进程原FD的CLOEXEC
A的直接Child结束并wait成功
读端继续等待EOF                   后代仍持有A的额外写端
```

这与工具后代正常持有 fd1/fd2 是不同情况：B 的标准流可以全部指向 null，仍然意外持有编号大于 2 的 PIPE，所以只查看工具 pid 是否消失不能识别这个原因。<br>
需要同时记录暂停位置、继承者 PID 与真实内核 FD 表。<br>
既有专门定位结果在 `bench/results/runtime-fixed/`：其中同一交错有 8 个旧实现失败与 8 个原子修复通过。<br>
这里复用其已证实机制，不宣称重新独立审计了整个标准库；原先缺失 PID/FD 的那一次历史 preview 失败仍不能唯一归因。

### 15.4.10 项目自己的原子捕获模块

`src/process_macos.rs` 在项目包内实现捕获，不依赖实验室包。<br>
它动态查找系统 pipe2，以 O_CLOEXEC 创建两对管道；当前 SDK 把 pipe2 标为 macOS 27.0 起可用，本机 27.0.1 实际执行。<br>
旧 macOS 查不到符号时返回 Unsupported，项目将该错误传播成 SpawnFailed 及 cleanup_error，不启动工具。<br>
没有退回 pipe 后补 fcntl 的有竞争路径，没有靠全局 spawn 锁或增大 drain_grace 让测试通过——一个库内部的锁也不能约束进程内所有无关调用者。<br>
非 macOS 仍保留原标准库/Tokio 路径，但本轮未验证其行为。

| 对象/阶段 | 唯一所有者 | 转移与失败处理 |
|:--|:--|:--|
| pipe2成功返回的两个FD | 两个OwnedFd | 仅成功后构造，作用域退出自动close |
| stdout/stderr读端 | 标准Child流，再转Tokio流 | 注册非阻塞I/O失败则释放已取得对象 |
| spawn前写端 | Command中的显式Stdio | 不是临时piped配置，必须主动替换释放 |
| spawn后父进程写端 | 同一个Command | 无论成功失败，立即替换成null |
| 真正Child的fd1/fd2 | 操作系统子进程FD表 | 正常输出与后代标准流继承继续有效 |

关键流程如下；完整编译过的上下文在项目模块中。

```rust
let (out_read, out_write) = pipe_cloexec()?;
let (err_read, err_write) = pipe_cloexec()?;
let out = ChildStdout::from_std(std::process::ChildStdout::from(out_read))?;
let err = ChildStderr::from_std(std::process::ChildStderr::from(err_read))?;
command.stdout(out_write).stderr(err_write);
let result = command.spawn();
command.stdout(std::process::Stdio::null())
    .stderr(std::process::Stdio::null());
Ok((result?, out, err))
```

替换写端必须发生在 `result?` 之前，否则 spawn 失败的早返回也可能让 Command 继续拥有写端。<br>
成功时如果等 Command 析构才释放，复用 Command 的调用方会一直等不到 EOF。<br>
新增单元测试刻意保持 Command 存活，连续捕获两次 printf 并等待两流 EOF；同一测试也连续执行两次缺失可执行文件的失败路径。<br>
标准 FD1/2 的 dup2 继承仍由 Command 执行；本修复不把所有描述符继承一概关闭，更不伪造读端 EOF。

### 15.4.11 unsafe 的窄边界与销毁前提

动态符号名是静态 NUL 结尾字节串，查找域为 RTLD_DEFAULT；函数指针必须具有 Apple pipe2 的准确 C 签名。<br>
libSystem 在本进程存活期保持加载，OnceLock 只缓存这个可调用地址或缺失状态——这不是接受请求方任意函数地址或卸载动态库的插件接口。<br>

pipe2 的输出数组可写两个 c_int，只有返回成功才把两个新 FD 封装为 OwnedFd；封装前没有把裸 FD 交给其他 Rust 对象，之后也不重复 from_raw_fd，每个 FD 始终只有一个负责 close 的 Rust owner。<br>
成功路径的整数封装不分配；后续任一转换错误都靠已建立的 owner 清理。<br>
若未来加入可 panic 的回调或插件卸载，必须重审上述前提，不能沿用此证明。<br>
测试里的 fcntl 只读取活 FD 的 F_GETFD 标志，不修改创建语义；这里的实施者契约核对不是独立 unsafe 审计签核。

### 15.4.12 用同一个 dyld 窗口验证本项目

`diagnostics/pipe_gate.c` 来自已有证明夹具并保留其交错方式；它在真实 pipe 或 pipe2 完成后、返回调用方之前暂停一次，不修改数据，不改 FD 标志，也不替代内核 read 行为。<br>
`examples/descriptor_race.rs` 先初始化 runtime，再 arm gate；另一条原生线程等 ready，然后启动标准流均为 null 的无关 helper。<br>
helper 生成两秒 hold 后代后退出，后代把自身 PID 写到文件；lsof 按这个精确 PID 采集 FD 表，之后才 release 原创建线程。<br>
测试直接断言继承者仍活着、没有编号大于 2 的 PIPE——不是「没采到进程，所以没看到泄漏」的空成功。

| 项目交错 | debug | release | gate与内核观察 |
|:--|:--|:--|:--|
| logs/stdout | 通过 | 通过 | pipe2、双端flags=1、无额外PIPE |
| logs/stderr | 通过 | 通过 | pipe2、双端flags=1、无额外PIPE |
| timeout/stdout | 通过 | 通过 | pipe2、双端flags=1、无额外PIPE |
| timeout/stderr | 通过 | 通过 | pipe2、双端flags=1、无额外PIPE |

最终完整记录在 `evidence/capture-fix-final-validation-02/` 的双 profile race 目录。<br>
logs 每路实际写 2MiB，检查总字节、前缀内容、全量 checksum 与 EOF；timeout 沿用原项目测试的 200ms 期限，并要求直接 Child 已 reap 及两流 EOF。<br>
捕获默认排空 grace 仍是一秒，没有为了继承者的两秒存活而扩充。<br>
另一个契约测试故意让真正工具后代继承 fd1/fd2：它使用专门的 30ms 测试 grace，预期两路非 EOF 并记排空错误。<br>
该反例验证修复没有通过关闭正常输出继承来偷换语义；夹具后代按固定期限自行退出，不冒充项目已实现进程树回收。

::: ex 例 15.4.1 · 给一次 200ms 超时，排哪条清理路径 {#ex-15.4.1}

配置沿用 `Config::default()`：`Q=16`、`C=4`、`R=8192`、`drain_grace=1s`。一个 `Logs{bytes: 262144}` 工具已经在 Running，timeout 为 200ms。到期后发出 kill，wait 随后成功，但该工具留下一个后代仍持有 stderr 写端。请写出最终 ToolResult 的字段与许可归还时机。

::: sol 解答

timeout 只触发停止意图：`start_kill` 发信号，工作继续 select wait 与两路读取（15.3.6）。wait 成功 → `reaped=true`，进入 Draining（[@def-15.4.1]）。stdout 若已读完则 `eof=true`；stderr 的写端仍被后代持有，于是继续等，直到 `drain_grace=1s` 到期，关闭该读端并记录排空 error（[@def-15.4.4]）。最终结果是 `TimedOut`、`reaped=true`、一路 `eof=true`、另一路 `eof=false` 且 error 非空；`total` 只累计父进程真正读到的字节，不会补到 262144；库不杀后代，也不宣称进程树已回收（15.4.8）。许可仍由 Job 持有，直到结果交付、任务被 join 后随析构归还（[@def-15.3.2]）。这正是 15.8 的 timeout 与排空反例测试分别覆盖的两段。

:::

::: think 思考 · wait 成功就返回结果，不排空行不行 {#think-15.4.1}

子进程都退出了，剩下的管道数据总会被内核丢掉，为什么还要花时间排空？

::: sol 解答

因为「子进程退出」与「写端全部关闭」不是同一事件：后代可能继承写端（15.4.8），CLOEXEC 竞争还可能让无关进程持有额外写端（15.4.9）。不排空就返回，会让 total 与 checksum 只覆盖一部分输出，Success 却带着不完整日志；而先读 stdout 到 EOF 再读 stderr 的串行策略，在双路大输出时直接把双方锁死（[@def-15.4.1]）。排空不是礼貌，它是让结果字段有意义的前进条件。

:::

:::

::: method 判定流程 · 从停止请求到「可宣称回收」

① **停止请求发出**：kill 只是信号，回收要等 reaped（15.4.4）。<br>
② **wait 成功**：`reaped=true`；出错则 `WaitFailed`，到此为止不能写已回收（[@def-15.4.2]）。<br>
③ **两路推进**：stdout 与 stderr 各自读、各自记 total 与 checksum，不互相推断（[@def-15.4.1]）。<br>
④ **每路得到结论**：EOF、读取错误、或 `drain_grace` 到期记排空错误（[@def-15.4.4]）。<br>
⑤ **联合判定**：Outcome、reaped、两路 EOF、cleanup_error 一起看，缺一项就是「不完整结果」（15.4.7）。<br>
⑥ **join 与归还**：任务被 join，许可随 Job 析构归还（[@def-15.3.2]）。<br>

:::

### 15.4.14 小结与常见错误

**小结。**① 双路必须同时推进，串行读到 EOF 会形成等待环（[@def-15.4.1]）；② wait 成功只是回收观察点，不是日志完整（[@def-15.4.2]）；③ R 只限制保留前缀，全量读取与校验照旧（[@def-15.4.3]）；④ drain_grace 到期记录错误而不伪造 EOF（[@def-15.4.4]）；⑤ CLOEXEC 竞争让「无关进程」也能持有写端，只有原子捕获能关掉这个窗口。下一节 [15.5 类型布局、ABI 与真实代码生成](#sec-cpp-rust.4.15.5) 检查这些结构在代码生成里长什么样。

::: errata 常见错误清单（15.4 节）

E-a **先读完 stdout 再读 stderr。**双路大输出时会互锁，先查是否同时 select 两路（[@def-15.4.1]）。

E-b **wait 成功就返回。**先查两路 EOF 与 error，Success 可能带不完整日志（[@def-15.4.2]）。

E-c **R=0 就关闭读端。**工具会看到 BrokenPipe 或卡在写入（[@def-15.4.3]）。

E-d **用 drain_grace 伪造 EOF。**到期应记排空错误，不能填 eof=true（[@def-15.4.4]）。

E-e **用增大 grace 或全局锁掩盖 CLOEXEC 竞争。**先查管道创建是否原子（15.4.9）。

E-f **把 kill 一个 pid 说成清理整个进程树。**先查后代是否继承 fd1/fd2（15.4.8）。

:::

::: method 即时自测 · 15.4

先合上正文作答，再展开核对。

::: sol 第 1 题答案
wait 成功（reaped）、两路各有结论（EOF 或排空错误）、任务被 join（[@def-15.4.2]、[@def-15.4.1]、[@def-15.3.2]）。

## 15.5 类型布局、ABI与真实代码生成 {#sec-cpp-rust.4.15.5}

本节回答一个问题：**一张 size/align 表与几段反汇编，能证明多少资源成本，又不能证明什么？**15.4 说清了回收要观察哪些字段；这一节把那些字段落到具体类型与代码生成上，并划清「进程内布局」与「跨进程协议」的界线。

::: preview 先抓住一件事

size 表量到的是**句柄**，不是请求的常驻内存：堆、共享状态与匿名 Future 都不在表里。同理，MIR、LLVM IR、汇编与 sample 各只支持一句话——**布局会随构建变化，ABI 不跨进程，指令名换算不出纳秒**。
:::

### 15.5.1 先量到具体类型，再讨论成本

`examples/layout.rs` 在本机输出以下尺寸，原始表保存在 run-04 的 `layout.csv`；工具链为 rustc 1.99.0，目标 aarch64-apple-darwin。<br>
这些是固定构建的观测，不是 Rust 稳定 ABI。

| 类型 | size，字节 | align，字节 | 解释 |
|:--|--:|--:|:--|
| Input | 24 | 8 | 变体载荷布局，不含String堆数据 |
| Config | 40 | 8 | 队列、并发、保留长度与排空期限 |
| Log | 72 | 8 | Vec句柄、计数、checksum及错误状态 |
| ToolResult | 224 | 8 | 包含两份Log，不含前缀堆分配 |
| Client | 24 | 8 | 共享句柄，不是注册表和队列全部存储 |
| Ticket | 32 | 8 | 结果、取消和阶段观察句柄 |
| Outcome | 1 | 1 | 当前枚举表示 |
| SubmitError | 1 | 1 | 当前枚举表示 |
| Stage | 8 | 4 | 包含pid的状态载荷 |
| OwnedSemaphorePermit | 16 | 8 | 许可句柄，不是信号量整体 |

一个 32 字节 Ticket 并不意味着每个请求只需 32 字节：请求还关联 Job、watch 共享状态、oneshot 和工作 Future。<br>
两个 8192 字节数组跨 await 存活，也会影响工作 Future 的存储；本轮没有打印该匿名 Future 的精确 size，因此不在表中填一个推测数字。<br>
Log 中的 Vec 长度受 R 限制，但容量与分配器开销另计。<br>
对内存预算做审查时，要逐个列出拥有堆存储的字段，不能只把几个公开句柄的 size 相加。

::: def 定义 15.5.1 · 类型布局 size 与 align {#def-15.5.1}

**类型布局**是某个具体构建（编译器版本、目标三元组、优化选项）下，一个类型占多少字节（size）以及按几字节对齐（align）。它是观测值而不是语言承诺：同一类型换构建可能变化；表里的 224 字节 ToolResult 包含两份 Log 句柄，却不含两份前缀的堆分配。拿布局做预算，必须同时列出「表内句柄」与「表外堆、共享状态、Future」。

:::

### 15.5.2 为什么保留 MIR 而不只看源码

归档同时保存库与 benchmark 的 `.mir`、`.ll` 和 `.s`。<br>
MIR 中的 try_submit 包含 OwnedSemaphorePermit 局部变量与多个错误清理路径，这有助于核对许可没有被简单遗忘在成功路径之外。<br>
record 的 MIR 保留字节迭代、wrapping_mul、saturating_add 与前缀扩展操作。<br>
它不是直接展示机器最终执行周期数的报告，MIR 也不会替你证明外部子进程会响应 kill；它回答的是编译后的 Rust 控制流和销毁结构问题。

### 15.5.3 LLVM IR 暴露的是优化后的边界

record 的 LLVM 签名可见 self 与只读字节切片参数属性；try_submit 的返回值在本轮 IR 中使用 32 字节 sret 存储。<br>
这属于本轮编译器降低 Result 的方式，它不允许外部 C 程序照这个未稳定签名直接调用 Rust 方法。<br>
本项目没有 FFI 导出入口，也不需要伪造一个 C ABI：跨进程传递的内容是 argv 和管道字节，不是 ToolResult 的内存镜像。<br>
因此 Rust 内部布局变化不会自动变成 helper 协议破坏。

| 边界 | 本轮实际证据 | 合理结论 | 不应推导 |
|:--|:--|:--|:--|
| Client::try_submit | MIR局部变量与LLVM sret | 接受/拒绝有不同分配和清理路径 | Rust返回ABI永远固定 |
| Log::record | LLVM逐字节xor/mul循环 | 全量checksum未被删去 | 日志排空只花一次memcpy |
| prefix扩展 | LLVM memcpy和reserve分支 | 保留会有复制及可能分配 | Vec容量恰好等于R |
| 两路read_log | 原生对record的真实调用 | 两路读取都进入完整性处理 | 已证明所有I/O交错 |
| 通道与任务同步 | 原生可见ldapr、casal等 | 本目标保留了同步操作 | 所有ARM目标使用同一指令 |
| Child执行 | sample中的spawn/wait路径 | 实际经过本机进程机制 | 其他OS必定采用相同实现 |
| 原子捕获 | pipe_cloexec的IR间接调用，flag=16777216 | 本轮传入macOS的O_CLOEXEC | 该整数可跨OS照抄 |

run-04 的 `native/agent_runtime.ll` 中，pipe_cloexec 先读 OnceLock，再检查函数地址。<br>
找到函数时向可写数组发起 C 签名间接调用，并在成功后构造 FD owner。<br>
对应 `.s` 在本轮 LBB147_2 中可见 `mov w1, #16777216` 与 `blr x8`，这说明运行中的动态调用没有被替换成旧 pipe/fcntl 捕获代码。<br>
它本身不证明系统调用（程序转交给内核去做的那次操作）内部原子性，原子契约和实际 gate 标志观察仍需共同支持。<br>
完整模块的 MIR 也保留了 OwnedFd、流转换与 Command 替换的正常/错误清理路径。

::: def 定义 15.5.2 · 进程内 ABI 与跨进程协议 {#def-15.5.2}

**进程内 ABI** 是同一构建里函数调用、返回与结构布局的约定，例如本轮 Result 用 32 字节 sret 返回；它随编译器与目标变化，不是稳定接口。**跨进程协议**是本项目真正承诺的东西：argv 的字段、管道里的字节，以及 ToolResult 的各字段含义。改变前者不影响 helper，改变后者才需要迁移（15.4.7 的字段表就是协议的一部分）。

:::

### 15.5.4 checksum 并不是免费观察

本轮 record 的原生循环中可见逐字节加载、xor 和乘法。<br>
下面只摘取循环核心，不展示全部调试位置指示；完整函数仍应从归档符号边界读取。

```asm
LBB123_4:
    ldrb w13, [x12], #1
    eor  x9, x9, x13
    mul  x9, x9, x10
    subs x11, x11, #1
    b.ne LBB123_4
```

checksum 递推有数据依赖，因此 benchmark 不是「只测内核管道拷贝速度」。<br>
即使 R=0，全部字节仍要通过这条计算路径；sample 也实际观察到 Log::record 栈。<br>
这解释了为什么不能把 R=0 当成零日志处理成本（[@def-15.4.3]）。<br>
若产品不需要全量 checksum，可以删掉它再重新测量；但删掉后要承认工作负载与完整性观察方式已经变化。

### 15.5.5 前缀复制的优化证据

LLVM IR 中可见饱和减法计算剩余保留长度，再取它与本次 read 字节数的最小值，最后只对这部分调用 memcpy 或扩展路径。<br>
已达到 R 时，复制长度为零，但 checksum 循环仍执行。<br>
这条结构与源代码的资源意图一致：不能根据 memcpy 存在就说所有字节都被保存在内存中，也不能根据复制长度为零就说 reader 不再触碰输入。<br>
代码生成证据需要和业务字段定义一起解释。

### 15.5.6 硬件事实不写成架构常识

本机查询得到 Apple M5 Pro、128 字节 cache line；当前目标汇编中出现 ldapr，而不是一律只有 ldar。<br>
本章不把 64 字节缓存行（缓存与内存之间搬运数据的最小单位）或某条原子指令写成通用常量。<br>
没有采集 cache miss、IPC、频率或能耗，所以不会从这些指令名称换算出同步操作的纳秒成本。<br>
执行器调度、分配和系统调用也在端到端路径中；一段短汇编只能解释局部机制，不能替代系统测量。

::: ex 例 15.5.1 · 用 layout 表给一批 8 个工具算内存账 {#ex-15.5.1}

沿用 `Q=16`、`C=4`、`R=8192`，一批 8 个 `Logs` 工具，每路实际输出 262144 字节。只用 15.5.1 的表，能写出哪几项内存上界？哪些必须写「未采集」？

::: sol 解答

表内可加的三项：8 个 ToolResult 句柄 8×224 = 1792 字节；8 个 Ticket 8×32 = 256 字节；两路保留前缀 8×2×8192 = 131072 字节（这是前缀长度上界，不是 Vec 容量）。<br>
表外必须另列：两份 Log 的 Vec 容量与分配器元数据、Job 与 watch/oneshot 共享状态、两个 8192 字节读缓冲、以及跨 await 存活的工作 Future——本轮没有打印匿名 Future 的 size，本节没有采集，只能写「未采集」（[@def-15.5.1]）。<br>
所以正确的结论是「句柄 + 前缀 133120 字节 = 130 KiB（按 1000 进制读才是 133 kB），其余未采集」，不能把 224×8 当成这批请求的常驻内存，也不能拿它去推算 RSS。<br>
这正是[@ex-15.2.1]里「131072 字节是有效前缀长度上界」的同一口径。

:::

:::

::: think 思考 · 看到 sret 就能让 C 程序调用吗 {#think-15.5.1}

LLVM IR 显示 try_submit 用 32 字节 sret 返回，签名稳定地出现在归档里。能不能据此导出一个 C 接口？

::: sol 解答

不能。sret 是本轮编译器降低 Result 的实现细节，不是可依赖的调用约定；Rust 没有为这个方法承诺 C ABI，字段顺序和 niche 优化都可能变（[@def-15.5.2]）。本项目根本不导出 FFI，跨进程只传 argv 与管道字节。要把能力给外部，应该设计显式协议并对字节做版本化，而不是把某个构建的 IR 签名当接口。

:::

:::

::: method 判定流程 · 从一张表或一段汇编能写到哪一级结论

① **先问对象**：这是句柄、堆内容，还是跨进程字节（[@def-15.5.1]）。<br>
② **再问构建**：编译器、目标、优化选项是否与结论绑定的那次一致。<br>
③ **再问语言层次**：MIR 只能说控制流与销毁，LLVM IR 只能说优化后结构，汇编只能说本目标指令（15.5.3 的表）。<br>
④ **再问测量**：没有计时或硬件计数器，就不能写 IPC、cache miss 或纳秒成本。<br>
⑤ **最后写边界**：每句结论后面补「不支持什么」，缺这一句就算越界。

:::

### 15.5.7 小结与常见错误

**小结。**① size/align 是构建观测，不是稳定 ABI（[@def-15.5.1]）；② 句柄表不能当 RSS 公式，堆与 Future 要另列；③ sret 等降低细节不构成跨语言接口（[@def-15.5.2]）；④ checksum 在 R=0 时仍逐字节执行；⑤ 没有硬件计数器就不写 IPC 与 cache miss。下一节 [15.6 benchmark 一：饱和准入的拒绝路径](#sec-cpp-rust.4.15.6) 把测量单位钉在「拒绝尝试」上。

::: errata 常见错误清单（15.5 节）

E-a **把 size 表当常驻内存。**先查堆、共享状态与匿名 Future 是否列出（[@def-15.5.1]）。

E-b **把 sret 当 C ABI。**先查有没有 FFI 导出承诺（[@def-15.5.2]）。

E-c **看到 memcpy 就说所有字节都被保留。**先查复制长度是否被 R 截断（15.5.5）。

E-d **用 R=0 宣称零日志成本。**先查 checksum 循环是否仍执行（15.5.4）。

E-e **从 ldapr 推算同步开销。**先查有没有采集周期与硬件计数器（15.5.6）。

E-f **把一次构建的布局写成语言保证。**先查工具链与目标三元组（15.5.1）。

:::

::: method 即时自测 · 15.5

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　ToolResult 的 224 字节包含什么、不包含什么？

::: sol 第 1 题答案
包含两份 Log 的结构体（Vec 句柄、计数、checksum、错误状态），不包含前缀堆分配与 Vec 容量（[@def-15.5.1]）。

::: sol 第 2 题答案

:::

**第 3 题 · 应用**　给出 R=8192、8 个工具的两路前缀上界，并说明它不是 RSS。

::: sol 第 3 题答案

**第 4 题 · 迁移**　若把 ToolResult 加一个字段，哪些结论需要重跑？

::: sol 第 4 题答案
size 表、涉及 ToolResult 的代码生成摘录与内存账都要重测；跨进程协议是否变化取决于字段是否进入 argv/管道字节，而不是 Rust 布局（[@def-15.5.2]）。

## 15.6 benchmark一：饱和准入的拒绝路径 {#sec-cpp-rust.4.15.6}

本节回答一个问题：**一个 3.662 ns/拒绝 的数字，究竟测到了什么，又不能外推到哪里？**15.2 说饱和时失败停在第三步（[@def-15.2.2]）；这一节先证明系统真的满载，再给这段短路径一个诚实的单位。

::: preview 先抓住一件事

拒绝路径的 benchmark 有两个前置条件：**先证明系统处于满载**（不是「提交很多次所以应该满了」），以及**单位写成 ns/拒绝尝试**而不是请求延迟。满足这两条，几纳秒的结果才成立；不满足，它只是一个漂亮的空数字。快速拒绝也不等于系统不会过载——重试策略在库外。
:::

### 15.6.1 先证明系统真的处于满载

入口是 `src/bin/runtime-bench.rs` 的 admission 模式，配置 Q=1、C=1。<br>
先提交一个 60000 毫秒 sleep，并等待 started 观察到 Running；再提交一个排队 sleep。<br>
这两个 Job 占满 Q+C 个总许可，正式循环中的每次提交都应返回 Full。<br>
测试不是靠「我已经提交很多次，所以应该满了」的猜测：基准结束后取消两个 Ticket，并观察活动子进程 reaped，排队项必须返回 pid=None。<br>
最后 shutdown 并 join，不能把睡眠留给下一项实验。

::: def 定义 15.6.1 · 饱和拒绝路径 saturated reject path {#def-15.6.1}

**饱和拒绝路径**指总许可已被占满时，`try_submit` 在取得许可这一步失败并返回 `Full` 的那段代码。它不创建 watch、oneshot 与 Job，也不进入注册表解析和消息通道分配（[@def-15.2.2]）；本节的 benchmark 只有在「两个 Job 确实占满 Q+C、每次提交都返回 Full」被验证之后，才允许宣称测到了它。

:::

### 15.6.2 一批包含哪些工作

每批执行 100000 次 try_submit，输入为一个空 String 的 Echo 变体，避免在调用前人为分配大正文。<br>
timeout 固定为一秒，但拒绝请求不会进入计时器队列；结果经过 black_box，并累计 Full 计数。<br>
每批结束验证拒绝数恰好为 100000；时间戳之后再打印 CSV，避免把终端格式化计入每批。<br>
这份观察覆盖的是热态饱和快速失败路径，它没有覆盖成功创建 watch、oneshot 和 Job 的成本。

### 15.6.3 计时核心

下面片段与完整源文件中的 rejected_batch 一致；统计和真实子进程生命周期仍在完整文件中。

```rust
fn rejected_batch(client: &agent_runtime::Client) -> (u128, usize) {
    let begin = Instant::now();
    let mut rejected = 0;
    for _ in 0..REJECTS {
        let result = client.try_submit(
            "demo",
            Input::Echo(String::new()),
            Duration::from_secs(1),
        );
        if matches!(black_box(result), Err(SubmitError::Full)) {
            rejected += 1;
        }
    }
    (begin.elapsed().as_nanos(), rejected)
}
```

REJECTS 在完整文件中固定为 100000；循环前后一次时间戳，避免对每次短拒绝都读取时钟。<br>
输出单位为 batch_ns 除以 REJECTS，它是批聚合后的 ns/rejected-attempt，不是一个网络请求从到达到返回的延迟，也不是有争用、多生产者同时提交的极限吞吐。<br>
本轮只有一个正式拒绝循环。

::: def 定义 15.6.2 · 批聚合单位 ns/拒绝尝试 {#def-15.6.2}

**ns/拒绝尝试**是一次批计时（整批 100000 次 `try_submit` 的墙钟纳秒）除以批内操作数得到的比值。它回答「在这台机器、这份循环里，平均一次被拒绝的提交摊到多少纳秒」，不回答单次请求延迟、尾部抖动或多生产者吞吐；报告里必须带着「拒绝尝试」这个对象名，否则读者会把它误读成响应时间。

:::

### 15.6.4 预热、统计和原始记录

admission 模式预热至少 500 毫秒，每次预热批也验证完整拒绝数；随后保存 21 个原始批次。<br>
原始文件是 `run-04/admission.csv`，每行保留 case、index、batch_ns、operations 与 checksum——这里的 checksum 就是 100000 次拒绝的计数，不是日志 FNV。<br>
统计脚本检查索引完整为 0 至 20；标准差使用 N−1 分母，p50 和 p99 使用 nearest-rank。<br>
对于 21 个批均值，p99 等于最大批均值。

| case | 样本数 | mean，ns/拒绝 | sd，ns/拒绝 | 批p50 | 批p99 |
|:--|--:|--:|--:|--:|--:|
| admission-full | 21 | 3.662 | 0.064 | 3.653 | 3.886 |

数值来自 run-04 的 statistics.csv。<br>
三位小数不表示跨机器可复现到皮秒；实际时钟记录的是整批耗时，再除以十万次操作。<br>

### 15.6.5 这么短的路径为什么可能成立

饱和时总许可取得失败，调用在注册表解析和消息通道分配之前返回（[@def-15.6.1]）。<br>
空 String 没有负载字节的堆分配，benchmark 并不包含新建一个子进程，所以它与毫秒级工具生命周期不是同一种计量对象。<br>
读到几纳秒结果时，应先检查到底执行了什么；本项目保留了实际 MIR 与原生代码，且结果计数被读取。<br>
但这个值仍不是整个 agent 系统的过载响应耗时。

### 15.6.6 拒绝很快不等于系统不会过载

调用方仍可能无限重试；外层连接、请求正文和已完成结果也可能无限堆积。<br>
如果上游把 Full 捕获后立即 spawn 一个稍后重试的任务，有界性就被移到了库外：本项目可以保证自己没有创建这类等待任务，它不能保证所有调用方都遵守相同预算。<br>
系统级审查要把入口协议和调用者策略一起画出来。<br>
越短的失败路径越容易被高频重试放大成 CPU 负载；快速拒绝应该配合有限重试和明确过载反馈。

### 15.6.7 测量环境与干扰

脚本取得共享目录锁后串行运行两个正式入口。锁路径由脚本位置向上算：`measure.sh:4` 把 `root` 定为项目上三层，锁即 `$root/.work/cpp-rust-agents/measure.lock`，落在本书仓库的**上一层**。<br>

取锁方式是 `while ! mkdir "$lock" 2>/dev/null; do sleep 1; done`（`:45`），**没有等待上限**：拿不到就一直忙等，不超时报错，也不恢复陈旧锁；只有正常退出时 EXIT trap 会 `rmdir` 释放（`:46`）。

上一次运行若被 SIGKILL 打断而 trap 没执行，锁目录会永久残留，之后重采就静默挂死——本节没遇到，这条失败路径的真实表现没有采集。怀疑有陈旧锁时先确认持有者是否还在跑，再手工删那个空目录；绝不用 `rm -rf` 他人的锁抢跑。<br>
构建、clippy 和测试发生在锁外；开始前保存了构建进程快照。<br>
快照未观察到其他 cargo/rustc 构建进程，文件因此为空。<br>
这只说明观察瞬间没有匹配项，不证明整个测量期间没有后台工作；没有据此宣称整台机器独占或没有桌面系统噪声。<br>
这些结果只属于这次有噪声桌面环境。

::: ex 例 15.6.1 · 从 21 批复算 p99 与单位 {#ex-15.6.1}

表里给出 21 个批均值：mean 3.662、sd 0.064、p50 3.653、p99 3.886，单位 ns/拒绝。请回答三件事：p99 为什么正好等于最大值？整批 100000 次拒绝大约花多少时间？把 3.662 写成「过载响应延迟 3.7 ns」错在哪？

::: sol 解答

nearest-rank 对 21 个样本取第 `ceil(21×0.99)=21` 个，所以 p99 就是最大批均值 3.886（15.6.4）。<br>
整批时间约为 `3.662 ns × 100000 ≈ 366200 ns = 366.2 µs`，这是批聚合量，不是单次延迟。<br>
「过载响应延迟」是请求对象，而本节测的是单生产者循环里被拒绝的尝试（[@def-15.6.2]）；它不含成功提交的 watch/oneshot/Job 成本，不含子进程，也不含调用方重试（15.6.5、15.6.6）。<br>
正确写法是「热态饱和下，单线程连续 100000 次拒绝的批均值为 3.662 ns/拒绝尝试，21 批的 p99 为 3.886」。

:::

:::

::: think 思考 · 取倒数就是系统的拒绝吞吐上限吗 {#think-15.6.1}

3.662 ns/拒绝，取倒数约为每秒 2.7 亿次拒绝。能不能把这个数写成「本 runtime 的过载保护吞吐」？

::: sol 解答

不能。倒数的分母是「单线程、无争用、已被证明满载」的循环（15.6.1），它没有多生产者并发提交，也没有把调用方重试、网络与上层排队算进去。更重要的是，拒绝路径快只说明失败得早，不说明系统能吸收多少过载请求（15.6.6）。吞吐是入口协议与调用者策略共同决定的系统量，不是某个微基准批均值的倒数。

:::

:::

::: method 判定流程 · 这个拒绝数字能不能对外引用

① **满载被证明了吗**：两个 Job 占满 Q+C，每次提交都 Full，结束时可取消并 reaped（[@def-15.6.1]）。<br>
② **单位写对了吗**：ns/拒绝尝试，还是被误写成请求延迟（[@def-15.6.2]）。<br>

④ **样本与统计完整吗**：21 批、索引 0–20、N−1 标准差、nearest-rank 分位数（15.6.4）。<br>
⑤ **环境写了吗**：桌面噪声、共享锁、构建快照为空不等于机器独占。<br>
⑥ **重试策略交代了吗**：调用方无限重试会把有界性搬到库外（15.6.6）。<br>
六条缺一条，数字只能内部参考。

:::

### 15.6.8 小结与常见错误

**小结。**① 先证明满载，再计时（[@def-15.6.1]）；② 单位是 ns/拒绝尝试（[@def-15.6.2]）；③ 21 批的 p99 就是最大批均值，不能当请求 p99；④ 几纳秒成立是因为路径短且被代码生成证据支持，不是因为系统整体快；⑤ 快速拒绝必须配合有限重试，否则过载被搬到库外。下一节 [15.7 benchmark 二：工具、日志与回收的批生命周期](#sec-cpp-rust.4.15.7) 换成毫秒级的真实工具。

::: errata 常见错误清单（15.6 节）

E-a **没验证满载就开始计时。**先查两个 Job 是否占满 Q+C 且每次 Full（[@def-15.6.1]）。

E-b **把 ns/拒绝尝试写成请求延迟。**先查单位与对象名（[@def-15.6.2]）。

E-c **把 21 批的 p99 当请求 p99。**先查样本单位是批均值（15.6.4）。

E-d **用批均值倒数宣称系统吞吐。**先查是否多生产者、是否含重试（[@think-15.6.1]）。

E-e **拿几纳秒证明系统整体快。**先查路径是否只到许可失败（15.6.5）。

E-f **忽略调用方的无限重试。**先查 Full 之后上游做了什么（15.6.6）。

:::

## 15.7 benchmark二：工具、日志与回收的批生命周期 {#sec-cpp-rust.4.15.7}

本节回答一个问题：**一批工具从提交到「结果、日志、回收都确认」的成本，由哪几段组成？**15.6 测的是拒绝路径；这一节把时钟移到真实子进程，并让结束条件同时覆盖 wait、双路 EOF 与校验。

::: preview 先抓住一件事

lifecycle 的计时终点不是 spawn 返回，也不是第一条日志到达，而是**8 个 ToolResult 全部到手**；校验发生在计时之后，但读数据时的 checksum 仍在计时之内。C4 改善的是这份工作负载的**聚合** ms/工具，不是单请求延迟；高噪声长尾批次必须保留，不能裁剪。
:::

### 15.7.1 工作负载要包含真实结束条件

lifecycle 模式每批提交 8 个真实 helper；每个 helper 向 stdout 写 262144 字节 O，向 stderr 写 262144 字节 E，一批总计读取 4194304 字节。<br>
工具返回后，父进程必须取得结果并确认 wait 成功，两路都必须 EOF 且无读取错误。<br>
因此不是只计 spawn 返回，也不是只计第一条日志到达。<br>
benchmark 在同一个外层 Tokio runtime 中执行所有批次，外层配置为两个 worker；每个 case 的项目 Runtime 在正式计时前创建，最后显式 shutdown。

::: def 定义 15.7.1 · 批生命周期 batch lifecycle {#def-15.7.1}

**批生命周期**指一次计时覆盖的完整区间：从 8 次 `try_submit` 开始，到 8 个 `ToolResult` 全部到手为止，其中每个结果都必须满足 reaped、两路 EOF、无清理错误（15.4.7）。它不包含批后的字段核对，但包含工作任务在读数据时计算 checksum 的开销；因此「批后校验在外」不等于「完整性处理全部不计时」。

:::

### 15.7.2 三个配置分开回答两个问题

| case | C | 每路R | 用途 |
|:--|--:|--:|:--|
| logs-c1-r0 | 1 | 0 | 不保留内容但仍完整排空与校验 |
| logs-c1-r4096 | 1 | 4096 | 对照有限前缀保留 |
| logs-c4-r4096 | 4 | 4096 | 在相同R下提高工具并发 |

Q 在三个配置中都为 16，每批 8 项可以先进入有界队列。<br>
不能拿 C1/R0 与 C4/R4096 直接证明「某一个参数」的效果；正文沿用 run-02 建立的 C1/R4096 中间对照，但数值全部重测于 run-04。<br>
run-01 只有两个日志配置，仍保留为历史探索归档，没有用覆盖旧文件的方式隐藏实验设计的演进。<br>
三种配置都读取和校验相同数量的字节；保留长度只改变前缀存储，不改变工具生成内容。

### 15.7.3 计时与校验的分界

计时开始后依次完成 try_submit，收集 8 个 Ticket，再等待所有结果；等全部 ToolResult 到手之后结束时间戳。<br>
结果 Vec 的构建也在计时内。<br>
之后才核对 Outcome、reaped、总字节数、前缀长度和 checksum。<br>
这使校验本身不直接进入报告的批耗时，但工作任务在读数据时计算 checksum 的成本仍在计时内。<br>
不能把「批后校验在外」误写成「完整性处理全部不计时」——两者处于不同执行位置。

```rust
async fn lifecycle_batch(runtime: &Runtime) -> (u128, Vec<ToolResult>) {
    let client = runtime.client();
    let start = Instant::now();
    let tickets: Vec<_> = (0..TOOLS)
        .map(|_| {
            client.try_submit(
                "demo",
                Input::Logs { bytes: BYTES },
                Duration::from_secs(5),
            ).expect("bounded admission")
        })
        .collect();
    let mut results = Vec::with_capacity(TOOLS);
    for ticket in tickets {
        results.push(ticket.wait().await.expect("result"));
    }
    (start.elapsed().as_nanos(), results)
}
```

TOOLS=8、BYTES=262144 定义在完整源文件中。<br>
按提交顺序等待 Ticket，不代表工具串行执行：所有 Ticket 已提交，dispatcher 可以并发推进它们。<br>
等待顺序只影响调用方取出已完成结果的顺序；时间终点仍是这一批全部结果可见，它不提供各请求独立的完成时间序列。

::: def 定义 15.7.2 · 批墙钟与聚合吞吐 batch wall clock {#def-15.7.2}

**批墙钟**是从第一次 `try_submit` 到最后一个 `ToolResult` 可见的整段纳秒数；**聚合吞吐**是「批内工具数 ÷ 批墙钟」。因为 C4 时多个工具重叠执行，聚合倒数可以小于单个工具的完整响应时间；它描述的是这一批的完成速度，不是任一请求的延迟。

:::

### 15.7.4 校验要覆盖被丢弃的后缀

预期 checksum 在计时外按 O 和 E 的完整字节数量计算；每个 Log.total 都必须等于 262144，前缀长度必须为 min(R，262144)，两个 checksum 必须分别符合预期。<br>
聚合 checksum 使用 wrapping_add，因此不依赖工具完成顺序。<br>
聚合发生在**批内**：`validate()` 只把这一批 8 个工具、每工具两路的 `log.checksum` 逐个 `wrapping_add`（`runtime-bench.rs:120-133`），跨批没有任何累加器。<br>所以 run-04 的 63 行 `lifecycle.csv` 里 checksum 列都等于同一个值 7596343361303360080——三个配置各 21 行都是它，因为每批写入的字节完全相同。<br>
Python 统计脚本重新按同样递推独立计算预期值；它不是只检查「每行都一样」，也检查这个值确实对应完整输出。<br>
FNV 存在碰撞可能，测试还独立核验总字节数与结果数量（[@def-15.4.3]）。

::: def 定义 15.7.3 · 聚合 checksum aggregate checksum {#def-15.7.3}

**聚合 checksum** 是把一批内各工具、各路的 FNV-1a 结果用 `wrapping_add` 逐项相加得到的值。加法可交换，所以它不依赖工具完成顺序；但它只证明「全部字节参与过校验」，不单独证明顺序或完整性，必须与总字节数、结果数量一起读（15.7.4）。

:::

### 15.7.5 正式统计

每个配置单独预热至少 500 毫秒；每轮轮转三个配置的起点，减弱固定顺序与时间漂移的绑定。<br>
每配置 21 批，共 63 条 lifecycle 原始观察；再加 admission 的 21 条，run-04 共有 84 条正式原始样本。<br>

| C1 / R0 | 2.871944 | 1.268896 | 2.535537 | 7.845750 |
| C1 / R4096 | 3.505500 | 2.472717 | 2.285484 | 9.227984 |
| C4 / R4096 | 1.046813 | 0.621628 | 0.811443 | 3.373109 |

标准差是 21 个批均值的样本标准差；p99 是这些批均值的 nearest-rank 分位数。<br>
它不等于 8 乘 21 个请求的响应时间 p99。<br>
C4 配置中多个工具重叠执行，所以聚合倒数可以小于一个工具的完整响应时间（[@def-15.7.2]）。<br>
若要请求延迟，需要分别记录提交与完成时刻，并保留每个请求观察；本轮没有这样采集，因此不补一个「推算请求 p99」。

### 15.7.6 桌面长尾不能充当保留增量的精确估计

C1/R4096 的本轮均值高于 C1/R0，但中位数反而更低。<br>
R4096 的样本标准差达到 2.472717 ms/工具，最大批均值 9.227984 ms/工具。<br>
应保留这些长批次，而不是裁掉不利样本来恢复理想排序。<br>
第一轮修复版 run-03 中两者均值接近，R4096 还略低；两轮不是随机化配对的净增量实验，不据此报告显著性或复制收益。<br>

完整生命周期中还有进程启动、两路各 256KiB 校验、调度和 wait；本轮不能从这些高噪声批次识别稳定的前缀复制惩罚。<br>
若要研究纯复制增量，应另设更聚焦且独立重跑的实验。<br>
旧 run-02 与新 run-04 也不是同环境配对，不把差值全归因于原子捕获修复；修复的必要性来自确定性继承失败，不是从这些时间表推断出来的。

### 15.7.7 提高 C 改善的是这份工作负载的聚合成本

在相同 R4096 下，C4 的本轮聚合 ms/工具低于 C1；这与多工具进程、日志 I/O 和校验可以重叠的机制一致。<br>
但结果没有分离进程启动、内核复制、用户校验与调度各自贡献，它不是对任意 CPU 工具都成立的四倍加速定律。<br>
四个外部 CPU 密集工具可能争夺与 runtime 相同的核心资源；本轮没有施加系统内存或进程数压力，也没有测 SLA。<br>
生产配置仍应结合工具实际资源成本，而不是照抄 C=4。

::: ex 例 15.7.1 · 一批 8 个工具算字节账与前缀保留 {#ex-15.7.1}

一批 8 个 helper，每个两路各写 262144 字节。分别取 R=0 与 R=4096，写出：一批总读取字节、前缀保留上界、checksum 覆盖范围，并说明为什么两者聚合 checksum 相同。

::: sol 解答

总读取都是 `8 × 2 × 262144 = 4194304` 字节（15.7.1）。<br>
R=0 时前缀保留 0 字节；R=4096 时保留 `8 × 2 × 4096 = 65536` 字节，即每路前缀长度 min(4096，262144)=4096。<br>
checksum 覆盖的是父进程读到的全部 4194304 字节，与保留多少无关（[@def-15.4.3]）。<br>
所以同一批数据在两种配置下算出的 checksum 相同；7596343361303360080 是**单批**（8 工具 × 2 路）的聚合 checksum，三个配置各自的 21 批都算出这一个值，run-04 的 63 行逐行相同（[@def-15.7.3]）。它不是把 63 批再加一遍的跨样本合计——那样会得到 17401029919372894640，归档里没有这个数。<br>
这也解释了 R=0 不能当「零日志成本」：读取、计数与逐字节校验照旧，只是不存前缀。

:::

:::

::: think 思考 · 按提交顺序等待 Ticket，是不是串行执行 {#think-15.7.1}

`lifecycle_batch` 在循环里逐个 `ticket.wait().await`。这是否意味着 8 个工具一个接一个运行？

::: sol 解答

不是。8 次 `try_submit` 在等待之前全部完成，dispatcher 已经在并发推进它们；等待顺序只决定调用方先取哪个结果，不决定工具何时执行（15.7.3、[@def-15.7.2]）。如果某个先提交的工具更慢，后面的结果会先完成但被留在 oneshot 里等前面——这也说明批墙钟不等于各请求延迟之和。

:::

:::

::: method 判定流程 · 一次 lifecycle 批结果能不能写成请求延迟

① **计时起点**是不是第一次 try_submit，终点是不是全部结果到手（[@def-15.7.1]）。<br>
② **结束条件**是否包含 reaped、两路 EOF、无清理错误（15.4.7）。<br>
③ **校验位置**：字段核对在计时外，但 checksum 计算在计时内。<br>
④ **单位**：ms/工具是批聚合，不是请求 p99（[@def-15.7.2]）。<br>
⑤ **配置**：R 与 C 同时变化时不能归因到单个参数（15.7.2）。<br>
⑥ **样本**：21 批全保留，长尾不裁剪，跨轮不配对就不报显著性。<br>
六条都过，才能写「这份负载的聚合成本」；否则只能写「本轮观察」。

:::

### 15.7.8 小结与常见错误

**小结。**① 批生命周期的终点是全部结果可见，且每个结果都 reaped、EOF（[@def-15.7.1]）；② 校验在计时外，checksum 在计时内；③ 聚合 ms/工具不是请求延迟（[@def-15.7.2]）；④ 聚合 checksum 可交换但需与字节数同读（[@def-15.7.3]）；⑤ C4 的改善只属于这份负载，长尾批次不裁剪。下一节 [15.8 测试、正常关闭与采样证据](#sec-cpp-rust.4.15.8) 看支撑这些结论的测试矩阵。

::: errata 常见错误清单（15.7 节）

E-a **只计 spawn 返回。**先查是否等到全部结果与两路 EOF（[@def-15.7.1]）。

E-b **把 ms/工具当请求 p99。**先查单位与 C4 的重叠执行（[@def-15.7.2]）。

E-c **裁剪长尾批次恢复排序。**先查是否保留全部 21 批（15.7.6）。

E-d **把 R 与 C 同时变化归因到单个参数。**先查三个配置的分工（15.7.2）。

E-e **用聚合 checksum 单独证明完整性。**先查总字节数与结果数量（[@def-15.7.3]）。

E-f **把 C4 当成通用四倍加速。**先查负载是否 CPU 密集、是否测过 SLA（15.7.7）。

:::

## 15.8 测试、正常关闭与采样证据 {#sec-cpp-rust.4.15.8}

本节回答一个问题：**360 次测试全部通过之后，哪些结论仍然不能写？**15.7 给出了批成本；这一节说明支撑它的关闭协议、测试矩阵与采样证据各自能证明到哪一步。

::: preview 先抓住一件事

shutdown 是**异步协议**而不是析构副作用：关闭接收端不丢弃已接受的 Job，Drop 也不能代替显式 await。测试通过只说明**具体回归契约被执行**，不是形式验证；sample 与正式计时必须分开，没有硬件计数器就不写 IPC 或 cache miss。
:::

### 15.8.1 正常 shutdown 是一个异步协议

Runtime 持有停止发送端和 dispatcher JoinHandle。<br>
shutdown 先发出停止接收请求；dispatcher 调用接收端 close，使已有 Client 克隆无法继续提交。<br>
已经进入队列的 Job 仍会被处理，工作槽继续按照 C 限制推进。<br>
排空队列之后，dispatcher 还要 join 所有工作任务，最后返回 Shutdown，包含 join 数量和任务失败信息。<br>
它不会因为第一个工具业务失败就遗忘其余任务。

::: def 定义 15.8.1 · 关闭协议 shutdown protocol {#def-15.8.1}

**关闭协议**是「停止接收新请求 → 处理完已接受 Job → join 全部工作任务 → 返回 join 计数与失败信息」这一串有序步骤。它是异步的：调用方必须显式 await；关闭完成的标志是 dispatcher 已 join 所有工作，而不是停止信号已发出。已接受的 Job 不因关闭而被丢弃（15.8.2）。

:::

### 15.8.2 关闭接收端不等于丢弃缓冲

有界通道关闭后，已进入缓冲的消息仍属于接受承诺；直接丢弃接收端会让这些 Job 没有最终结果。<br>
本实现继续 recv 直到返回 None——这是通道生命周期与业务生命周期连接的地方。<br>
Client 克隆可以继续存活，关闭不依赖所有用户主动 drop 发送端。<br>
测试在保留 Client 克隆时调用 shutdown，随后验证提交返回 Closed。<br>
调用方在 shutdown 之后仍可取出已经发送到 oneshot 中的结果：结果可用性与发送端句柄存活不是同一条件。

### 15.8.3 为什么 Drop 不能代替 shutdown

Rust 的 Drop 不是可以任意 await 的析构入口。<br>
本项目 Drop 只发送停止请求，不同步等待 dispatcher，也不 abort dispatcher，避免主动丢弃清理责任。<br>
如果外层 Tokio runtime 继续存在，dispatcher 可以继续完成工作；但程序立刻销毁整个外层 runtime 时，不能承诺清理 Future 仍有机会运行。<br>
所以正常使用必须显式 await shutdown：CLI 和可运行库例子都在外层 runtime 退出前 join，库例子还在准入错误路径上执行 shutdown。<br>
这比在 README 里只写一句「退出会自动清理」更诚实。

::: def 定义 15.8.2 · 析构兜底与显式关闭 drop fallback vs explicit shutdown {#def-15.8.2}

**析构兜底**是 Drop 里「尽力发出停止请求」的那部分，它不同步等待，也不保证清理 Future 有机会运行；**显式关闭**是调用方 await `shutdown()`，拿到 join 计数与失败信息。前者只防止完全忘记关闭，后者才是可观察的完成证据（[@def-15.8.1]）；把两者混为一谈，等于把「尽力而为」写成「保证完成」。

:::

### 15.8.4 测试矩阵

最终每轮运行 2 项单元测试与 16 项集成测试；其中 contracts.rs 有 14 项，regressions.rs 仍有原来的 2 项。<br>
新增单元覆盖原子 FD 标志及 Command 复用/失败，新增契约覆盖有意标准流继承。<br>
它们运行真实 helper 或系统 printf，而不是只返回预设结果的 mock。<br>
最终验证目录为 `evidence/capture-fix-final-validation-02/`。<br>

debug/release 各 10 轮默认并行 cargo test，共 360 项测试执行全部通过；没有使用 test-threads=1，原有测试断言均保留。<br>
每个 profile 另有 5 轮八独立 Runtime 压力，每轮 80 条完整 ToolResult。<br>
单套合计 800 条结果：640 条 logs、80 条 timeout、80 条 cancel，均独立核验预期 Outcome。<br>
每条 logs 核对双路字节、checksum 与前缀；所有条目都要求 reaped、EOF 及无清理错误。<br>

CLI 的成功、非零、超时、取消和 usage 退出码仍由原回归逐轮启动真实二进制验证；库调用例也在两个 profile 实际执行。<br>
此前同源码进程实现的另一套完整重复记录仍保留，但不拿次数替代确定性 gate 证明。

| 场景 | 建立阶段关系的方法 | 观察点 |
|:--|:--|:--|
| 双路大输出 | helper实际写两路各2MiB | 全量total/checksum、有限prefix、EOF、reaped |
| 字面参数 | 输入包含shell元字符 | stdout精确字节比较 |
| 队列满载 | 先等Running，再填唯一队列槽 | 第三次提交Full |

| 运行超时 | started确认真实Child已spawn | TimedOut且reaped、两路EOF |
| 排队期限 | 短deadline排在受控长任务后 | 未spawn即TimedOut |
| 非零退出 | helper显式返回23 | NonZero、exit_code=23、join无失败 |
| 正常shutdown | 保留Client和所有Ticket | 接受项全部join、后续Closed |
| 丢弃Ticket | 先观察pid再drop | shutdown完成且短窗口ps不再列出直接Child |
| 固定工具 | 固定argv与覆盖尝试 | 不能替换参数，原值实际输出 |

部分测试同时覆盖多个性质，所以表行数不是测试数量统计。<br>
输入预算测试还覆盖超大 Echo、NUL、日志超限、sleep 超限、零失败码与非法 timeout；注册测试覆盖重复名字、非法名字与不存在路径。<br>
这些都是安全失败，不通过执行 UB 获得「预期错误」。<br>
本轮没有 Loom 穷举全部交错，也没有 Miri、TSan 或独立技术审计结果。<br>

::: def 定义 15.8.3 · 契约测试 contract test {#def-15.8.3}

**契约测试**是用真实 helper 或系统调用建立阶段关系、再断言可观察字段的测试（如先等 Running 再填队列槽），它验证的是一条写明的回归契约。它不同于 mock 测试，也不同于形式验证：单条契约通过不覆盖所有调度交错，不能外推成「并发正确性已证明」（15.8.4）。

:::

### 15.8.5 一个真实安全的性能回退对照

`sequential_drain_regresses_then_explicitly_recovers` 故意采用错误排空策略：它启动真实 logs helper，持有 stderr 读端但不读取，然后只对 stdout 执行 read_to_end。<br>
测试为这个错误操作设置 200 毫秒观察窗口，预期不能在窗口内完成。<br>
随后显式 child.kill().await，并再次 wait 观察已结束状态，最后释放管道对象。<br>
没有留下一个无限阻塞 reader 任务，也没有让错误子进程留到测试之外。

```rust
let outcome = tokio::time::timeout(
    Duration::from_millis(200),
    stdout.read_to_end(&mut output),
).await;
assert!(outcome.is_err());
child.kill().await.expect("kill and reap negative control");
let status = child.wait().await.expect("observed reaped child");
assert!(!status.success());
drop(stderr);
```

200 毫秒是测试观察预算，不是被报告的 benchmark 延迟。<br>
该测试证明这份真实双路负载下，串行排空不能正常完成；正确实现用两路各 2MiB 的正向测试验证完整结束。<br>
正向与负向对照共同排除了「输出太小，错误策略也碰巧完成」的解释。<br>
它没有证明所有工具都必定产生这种死锁：完全不写 stderr 的工具可能不会触发这条等待环，故障条件应随案例一起保留。

### 15.8.6 许可寿命测试的证据与局限

运行槽测试先等第一个 sleep 出现 Running，再提交一个排队 echo，并取消第一个任务。<br>
第一个结果必须 reaped，第二个最终成功——这验证正常取消不会抛弃后续工作。<br>
更强的「不提前释放」论证仍要结合 dispatcher 的 JoinSet 守卫和 Job 所有权阅读。<br>
单个成功交错不证明所有调度交错；本章没有用测试名称替代源代码不变量。<br>
若未来把日志移到独立任务，需要同步更新这份证明和测试（[@def-15.3.2]）。

### 15.8.7 sample 与正式计时分开

测量脚本在 84 条正式样本结束后，另启动 profile 模式。<br>
该模式运行八秒左右的工具生命周期循环；macOS 的 `sample` 以一毫秒间隔采集三秒。<br>
报告保存在 `run-04/macos-sample.txt`，profile-run.txt 记录该次工具计数。<br>
采样进程不参与 statistics.csv；不能把附着采样时的耗时和未附着正式批次混合。

### 15.8.8 实际看到的栈及能说的结论

报告中可见 Tokio worker、read_log、Log::record、kevent、posix_spawn 和 wait 相关路径。<br>
这与真实进程、两路 I/O 与全量校验的实现边界相符。<br>
Log::record 被采到，提示完整性处理不是免费操作；kevent 被采到，并不能说明每次都长时间睡眠——它也可能服务 readiness 检查与唤醒。<br>
spawn 与 wait 栈说明实际经过本机系统接口，不代表其他平台实现相同。<br>
sample 只采父进程，不覆盖所有 helper 的 CPU 栈，因此这里不把父进程样本百分比当成系统总 CPU 占比。<br>
没有硬件计数器，就不报告 IPC 或 cache miss。

::: ex 例 15.8.1 · 一次 shutdown 的接受与拒绝边界 {#ex-15.8.1}

调用方保留一个 Client 克隆，队列里已有一个排队 Job，另有一个 Ticket 已被 drop。此时调用 shutdown 并 await。请判断：排队的 Job 会被丢弃吗？shutdown 之后新的提交返回什么？已经被 drop 的 Ticket 对应的结果还能取吗？join 计数至少是几？

::: sol 解答

排队 Job 不会被丢弃：dispatcher 继续 recv 直到 None，并按 C 推进它，最终 join（[@def-15.8.1]）。<br>
shutdown 之后新的提交返回 Closed，因为接收端已 close，但 Client 克隆仍可存活（15.8.2）。<br>
被 drop 的 Ticket 没有接收者，结果不可取，但工作仍完成清理并计入 join——这正是 15.3.3 的取消语义。<br>
join 计数至少包含排队 Job 与已被 drop Ticket 的那一项；若它们还没结束，shutdown 会等它们结束，而不是返回一个漂亮的 0。<br>
「关闭很快返回」与「所有工作已回收」是两件事，必须看 join 计数与失败信息。

:::

:::

::: think 思考 · 360 次通过能不能写成「并发正确性已被验证」 {#think-15.8.1}

debug/release 各 10 轮、共 360 项测试全部通过，另有 800 条压力结果。这能不能支撑「并发实现正确」这句话？

::: sol 解答

不能。测试验证的是一组写明的契约（满载 Full、超时 reaped、shutdown 后 Closed 等），不是所有交错；本轮没有 Loom、Miri 或 TSan，也没有独立审计（15.8.4）。正确的表述是「这些契约在 360 次执行中被重复观察到，压力样本各自核验了字段」；「所有调度交错下正确」需要形式化或穷举工具，属于另一类证据（[@def-15.8.3]）。

:::

:::

::: method 判定流程 · 从一条测试通过能写到哪一级结论

① **测试对象**：是真实 helper/二进制，还是 mock（[@def-15.8.3]）。<br>
② **契约内容**：它建立什么阶段关系、断言哪些字段（15.8.4 的表）。<br>
③ **重复方式**：轮数、profile、是否并行，是否每次都核验字段。<br>
④ **工具边界**：没有 Loom/Miri/TSan 就不能写「所有交错已验证」。<br>
⑤ **环境**：sample 与正式计时是否分开，是否有硬件计数器。<br>
⑥ **表述**：只能写「某契约在哪些执行中被观察到」，不写「实现已被证明」。

:::

### 15.8.9 小结与常见错误

**小结。**① shutdown 是有序异步协议，关闭接收端不丢弃已接受 Job（[@def-15.8.1]）；② Drop 只是兜底，不能替代显式 await（[@def-15.8.2]）；③ 测试矩阵验证具体契约，不是形式验证（[@def-15.8.3]）；④ 负向对照与正向测试共同排除「碰巧完成」；⑤ sample 与正式计时分开，没有计数器就不写 IPC。至此 [15.9 母本对应与来源核读](#sec-cpp-rust.4.15.9) 转入来源与边界。

::: errata 常见错误清单（15.8 节）

E-a **把 Drop 当 shutdown。**先查是否显式 await 并核对 join 计数（[@def-15.8.2]）。

E-b **关闭时丢弃缓冲。**已接受 Job 必须有最终结果（[@def-15.8.1]）。

E-c **用 360 次通过宣称形式验证。**先查是否使用 Loom/Miri/TSan（[@def-15.8.3]）。

E-d **把 200ms 负向窗口当 benchmark 延迟。**它只是测试观察预算（15.8.5）。

E-e **把 sample 耗时混入正式批次。**先查 statistics.csv 是否只含正式样本（15.8.7）。

E-f **用父进程样本百分比当系统 CPU 占比。**先查 sample 是否覆盖 helper（15.8.8）。

:::

::: method 即时自测 · 15.8

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　shutdown 协议的四步是什么？

::: sol 第 1 题答案
停止接收 → 处理已接受 Job → join 全部工作 → 返回 join 计数与失败信息（[@def-15.8.1]）。
:::

**第 2 题 · 辨析**　Drop 与 shutdown 各保证什么？

::: sol 第 2 题答案
Drop 只发停止请求、不同步等待；shutdown 才等待 join 并报告结果。程序立刻销毁外层 runtime 时，Drop 不能承诺清理 Future 运行（[@def-15.8.2]）。
:::

**第 3 题 · 应用**　保留 Client 克隆调用 shutdown 后，提交和已发送结果各是什么状态？

::: sol 第 3 题答案
新提交返回 Closed；已进入 oneshot 的结果仍可取；排队 Job 继续处理并 join（15.8.2）。
:::

**第 4 题 · 迁移**　若给项目加 Loom 测试，它能替代 360 次集成测试吗？

::: sol 第 4 题答案
不能。Loom 穷举的是模型内交错，不能覆盖真实子进程、管道与 CLOEXEC 竞争；两类证据互补，表述仍要限定范围（[@def-15.8.3]）。
:::

## 15.10 常见错误索引 {#sec-cpp-rust.4.15.10}

这是本章的跨节错误索引：每一节末尾都有自己的「::: errata 常见错误清单（15.M 节）」，按你阅读的顺序给出局部清单。下面这一份只收那些要读完整个章才浮出来的错误，它们在单节内部看不出问题，放进「准入、执行、回收」的整条链才露馅。

**先 spawn，再在任务里等待有界队列。** 队列只有 Q 个槽，等待入队的任务仍然可以无限增长。本项目改为同步 `try_submit`，在工作任务出现之前就拒绝；上层重试也必须受限，否则只是把队列挪了个位置（[@def-15.2.1]）。

**把 Q+C 写成每次初始突发都能成功接受的数量。** dispatcher 尚未运行时，通道可能先在 Q 处拒绝。Q+C 是所有权持有上界，不是接收进展的保证，是否等待容量必须由接口明确表达（[@def-15.2.1]）。

**让 Ticket 拥有实际工作许可。** 调用方放弃响应时，子进程可能仍在退出途中（[@ex-15.3.1]）。许可应随 Job 留在实际工作里，直到 wait 与排空结束，预算不能由「谁还愿意等」决定（[@def-15.3.2]）。

**把 cancel 返回当成进程已经消失。** cancel 只更新 watch 里的意图，要等 wait 结果的 reaped 与 shutdown 的 join 观察。非阻塞的请求接口不应假装提供同步清理保证（[@def-15.3.1]）。

**把请求 timeout 当作硬响应期限。** 运行超时之后仍要操作系统完成 kill 与 wait，本库不会在 wait 未成功时伪造回收结果。排队过期也可能要等运行槽可用才被观察到（[@def-15.4.2]）。

**先读完 stdout，再读 stderr。** 双路写入超过管道容量时会形成等待环，安全 Rust 同样能出现这种协议死锁（[@def-15.4.1]）。本项目保留了可恢复的真实负对照，回归测试会把它跑出来。

**日志达到保留上限后停止读取。** 工具仍会向管道写入，停读会把子进程反压住。有限保留要求继续读并丢弃后缀，而不是停止消费；即使 R=0 也仍承担 I/O 与 checksum 成本（[@def-15.4.3]）。

**把 Child 的 wait 成功等同于两路 EOF。** 内核管道里可能仍有未读数据，后代也可能持有写端（[@def-15.4.2]）。必须有独立的排空阶段与不完整日志标记，reaped 只涉及直接 Child。

**把 kill_on_drop 写成严格及时回收机制。** 它是异常析构的兜底，不是正常观察点；Tokio 文档里的后台回收是 best effort。显式 wait 失败必须保留为失败，不能改写成「已清理」（[@def-15.8.2]）。

**只检查 `Outcome::Success`。** 工具成功退出与日志完整是两个维度，还应查看 reaped、eof、error 与 cleanup_error。结果结构分层就是为了避免一个布尔值吞掉整份证据（[@def-15.4.2]）。

**把 Stage watch 当成不可丢失的事件队列。** 快工具可能让观察者只看到 Finished，started 返回 None 不等于从未 spawn（[@def-15.3.1]）。最终 pid 与结果才是持久观察。

**把快速 Full 当成完整准入性能。** 饱和路径跳过了注册表解析与通道分配，几纳秒的批均值不能预测成功工具请求的成本（[@def-15.6.2]）。它同样不代表网络端到端的过载响应延迟。

**把批 ns/tool 的 p99 称作请求 p99。** 每条观察已经平均了 8 个工具的批完成时间，并发重叠使这个数更接近吞吐倒数（[@def-15.7.2]）。没有逐请求时间戳，就不应补出请求尾分布。

**只按两次均值的排序解释前缀复制收益。** 结果处在真实桌面噪声与进程启动成本之中，排序可能翻转（[@ex-15.7.1]）。保留当前数据、限制结论即可；要识别微小的复制增量，应另设实验。

**以为 canonicalize 与空环境就是沙箱（15.1 E-a）。** 注册表做到的是入口受限，不是行为受限；后者要独立的 OS 机制与专门的测试（[@def-15.1.4]）。

**靠 `Runtime::Drop` 完成正常关闭。** Drop 只发停止请求，不能原地 await 所有工作；必须在外层 Tokio runtime 仍活着时调用 shutdown（[@def-15.8.1]）。外层 runtime 被强行销毁不属于已证明的清理路径。

**假定安全 API 创建的所有捕获 FD 都原子 CLOEXEC。** 本机 Rust 1.99 的 macOS pipe/fcntl 窗口已经由真实的额外 PIPE 证明，修复只保护项目自己的捕获管道，不能许诺修好了所有 `Command` 调用。

**显式传 `Stdio` 后忘记释放 Command 持有的写端。** 父进程自身也会阻止 EOF，复用 Command 尤其容易暴露这个问题。必须在检查 spawn 结果之前替换双路写端，成功与失败都要清理。

## 15.11 本章小结与章末件 {#sec-cpp-rust.4.15.11}

::: note 本章小结

- 有界执行器把准入、运行与日志保留拆成 Q、C、R 三层上界，缺任何一层都会留下无界集合（[@def-15.2.1]、[@ex-15.2.1]）。
- 拒绝要发生在工作任务出现之前，快速 Full 只说明饱和路径便宜（[@def-15.2.2]、[@ex-15.2.2]）。
- 许可要随实际工作活到 wait 与排空结束，调用方超时不算完成（[@def-15.3.2]、[@ex-15.3.1]）。
- 双路排空必须并发进行，wait 成功不等于两路 EOF（[@def-15.4.1]、[@ex-15.4.1]）。
- 日志保留有上限，但读取不能停，否则反压会卡住子进程（[@def-15.4.3]、[@ex-15.7.1]）。
- 批均值回答吞吐，ns/tool 的 p99 不是请求的 p99（[@def-15.7.2]、[@ex-15.6.1]）。
- 正常关闭要显式 shutdown 并 join，Drop 只是异常兜底（[@def-15.8.1]、[@ex-15.8.1]）。

:::

正式计时前先保存构建、clippy、测试与代码生成结果；正式计时用目录锁串行化，采样是另一个独立进程。脚本对已存在的锁是无上限忙等（`measure.sh:45`），不超时也不清陈旧锁：被 SIGKILL 打断过一次，就得人工确认持有者已死再删那个空目录，不要为了抢跑 rm 他人的锁。开始前的进程快照只证明那个时刻的观察，不证明之后没有后台任务；另一台机器应首先复现正确性与计量边界，再讨论数值差异。

归档应能回答十个问题：environment.txt 给出哪一版 rustc、LLVM、OS 与目标；source-sha256.txt 是否与源文件、Cargo.lock 和测量脚本匹配；admission.csv 是否有 21 个不同索引且每批 100000 次拒绝；lifecycle.csv 是否有三个 case、每个 21 批、每批 8 个工具；Python 独立计算的 checksum 是否与 Rust 一致；statistics.csv 是否明确区分拒绝尝试与工具批均值；native 目录是否同时存在 MIR、LLVM IR 与本机 `.s`；sample 是否来自单独进程而不是正式批次附着采样；build-process-snapshot.txt 是否记录了可见的并发验证工作；shutdown 是否 join 了所有已接受工作，而不是只丢弃 runtime。

阅读实现时，你应能指出 `try_submit` 里总许可取得早于 watch 与 oneshot 创建，能说明 `try_send` 失败时由谁归还许可，能指出 dispatcher 在哪个条件下停止 recv 并发出 spawn。还要能解释完成但未 join 的项为什么仍占运行槽，找出排队 Job 在 spawn 之前检查 deadline 的位置，追踪 cancel 之后 start_kill、wait、drain 与结果发送的顺序。日志读取错误、工具非零退出与任务 JoinError 要能分开；后代继承管道为什么会突破「wait 后必 EOF」也要说清。若只能回答「Rust 有所有权，所以资源安全」，项目理解还没有完成。

本项目交付的是可运行 CLI 与库：两项单元测试、16 项集成测试、rustfmt、离线 locked clippy 与双 profile 重复执行都已完成。正文采用 run-04 的 84 条正式原始观察，另保留 run-01 的 63 条与 run-02、run-03 各 84 条；两种 profile 共 8 个项目 gate 交错，验证了无关进程没有额外捕获 PIPE，正常标准流继承仍如实触发测试 grace，不伪造 EOF。这些结果支持可信命名工具、直接 Child 与声明配置范围内的结论，但旧 macOS 实机、进程组终止、后代清理、跨平台行为与权限沙箱都没有测试，Miri、Loom、TSan、Linux perf 与 io_uring 也没有运行。
