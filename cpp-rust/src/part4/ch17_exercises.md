# 第17章 · 习题集

共 21 题，分三组（A 组 1–7、B 组 8–14、C 组 15–21）。**A 组概念**检验你能否说出每个名词指什么；**B 组推理**给一段设计或报告，要求挑错、算账、下判定；**C 组实操**要求你写契约、改签名、列测试步骤、组装证据包。每题题号后标注它主要考主线四步（① 工作真的发生 / ② 这个数是什么 / ③ 差异不是噪声 / ④ 守得住、可复核）中的哪一步——这是本书第一次这样标注，用它把项目和主线对上。

用法约定：先写下自己的答案，再展开核对。看解答只看第一行就停住，问自己下一步是不是你要走的。17.4、17.6、17.7 已各有一轮实测（机制对照轮在 `results/run-02/`，准入对照轮在 `results/run-03/`），本集考协议与挑错，不要求你复现那些数字，但要能说出它们的单位、区间、预算与不覆盖范围；仍未采集的是每请求端到端延迟与按请求取消的两类计数。C 组涉及的代码在 `projects/tidekv/`：`src/segment.rs`、`src/ipc.rs`、`src/bloom.rs` 等模块，用到回收接口时再给全路径。

## A 组 · 概念（1–7）

::: ex A1 · 四元组对回主线（主线 ①②④） {#ex-17.A.1}

项目契约的四个槽位 $O$、$F$、$I$、$X$，分别对应主线四步里的哪一步？为什么 $F$ 和 $X$ 采集后不许改？

::: sol 解答

$O$ 与 $I$ 保证 ①「活真的干了」：操作集合定义了要证明谁，不变量给了证伪路径。$F$ 保证 ②「这个数是什么」有一个固定的分母。$X$ 是 ④「守得住」的护栏，限定结论不外推。采集后改 $F$ 等于换了实验还沿用旧数字；改 $X$ 等于看见结果之后临时划定结论能站到哪里——两者都让结论失去被追问的资格。对照[定义 17.1.1](ch17.md#def-17.1.1)。

:::

:::

::: ex A2 · 不变量还是愿望（主线 ①） {#ex-17.A.2}

「已 `sync` 的写在重启后仍在」和「写入吞吐不低于每秒 X 万条」，哪条配当不变量？说出判据。

::: sol 解答

前者。判据是「能否用测试一次性证伪」：重启后逐键比对就能触发失败，是二元命题。后者是量级判断，要成立必须先有口径、区间和预算，把它写成不变量是把统计命题伪装成二元命题。每条不变量还得配一个能触发它的测试，配不出来的只是愿望。对照[定义 17.1.2](ch17.md#def-17.1.2)。

:::

:::

::: ex A3 · 两笔字节账（主线 ②） {#ex-17.A.3}

「分区摆放总字节更大」与「分区摆放读得更快」，哪句静态可算、哪句需要实测？后者要成立需要交代什么？

::: sol 解答

第一句是静态算术：[例 17.2.1](ch17.md#ex-17.2.1) 的 97、12、$7{,}143{,}424$ 都是算出来的。第二句是性能量，需要固定输入家族、点读命中率、同机配对测量才能成立；命中率 100% 时它甚至可能反向。凡把第二句写成百分比收益，必须给算式或实测，不给就当作印象。对照 [17.2](ch17.md#sec-cpp-rust.4.17.2)。

:::

:::

::: ex A4 · 三条不变量对实现（主线 ①） {#ex-17.A.4}

读路径返回切片的三条安全不变量，各落在哪个具体机制上？哪一条是「新建段而不是改旧段」在服务？

::: sol 解答

①范围由索引区给出并核对——构造时校验与越界返回空；②缓冲在借用存活期不释放——`Arc` 引用计数加 epoch（记读者代际的计数器）回收；③段字节写定后不改——就是「新建段」这条流程在服务。三条缺一，切片读到的就可能是已释放或被改写的字节，属未定义行为。对照[定义 17.3.2](ch17.md#def-17.3.2)。

:::

:::

::: ex A5 · 口径三选一（主线 ②） {#ex-17.A.5}

比较泛型与 dyn 的代价，允许报哪三种口径？为什么「dyn 慢多少」在没有口径时没有真值？

::: sol 解答

每次调用的墙钟差（要减掉共同开销）、生成代码的字节数、热循环里的指令数。三者量的是不同的层——分发开销、内联（编译器把被调函数体搬进调用点）、代码体积、指令缓存命中——完全可能一个升一个降。先指定口径并说明另两个为什么不算，比较才有真值；本项目的实测结论是「方向不可判定、区间最坏端低于预算」，不是「`dyn` 与泛型一样快」。对照[定义 17.4.2](ch17.md#def-17.4.2)。

:::

:::

::: ex A6 · 内存序的分工（主线 ④） {#ex-17.A.6}

本项目的原子操作分成哪两种强度、各自用在哪里？选弱强度的依据为什么不是「它快」？

::: sol 解答

现状是两种强度：换快照那一步用 `SeqCst`（`epoch.rs` 里 head 的 `swap`/`load` 与 PINS 的 `store`），纯计数用 `Relaxed`（`stats.rs`）。要保住的是「段字节写在前、指针换在后」这条顺序。选 `Relaxed` 的依据是「这个量没有需要同步边保护的伴随数据」；把它快当依据，遇到某个计数实际充当就绪标志时就会用错——可见顺序失守不是概率问题。对照[定义 17.5.2](ch17.md#def-17.5.2)。

:::

:::

::: ex A7 · 两类计数（主线 ①） {#ex-17.A.7}

「已完成但提交方已放弃」为什么不并进「已处理」？并进之后哪两个指标同时失真？

::: sol 解答

取消只意味着提交方不再等它，不意味着它没发生：这类请求消耗了资源、可能已产生外部副作用，并进去等于重复执行的风险被藏起来。失真的是吞吐（分母混入了没人等的完成）与拒绝率（被拒、被弃、被完成三种数互相污染），所以三类各记各的计数。对照[定义 17.6.2](ch17.md#def-17.6.2)。

:::

:::

## B 组 · 推理（8–14）

::: ex B8 · 换一组键值长再算一遍（主线 ②） {#ex-17.B.8}

键长固定 32 字节、值长固定 128 字节，段文件仍装 $2^{16}$ 条记录。算出：① 数据区每条字节数；② 数据区总字节；③ 索引区总字节；④ 合计（不计布隆区与页脚）。再回答：这组数字需要实测吗？

::: hint 提示

别只算键与值：数据区每条前面还有 17 字节条目头；索引项宽度也不随键值长变化，恒为 12 字节。

:::

::: sol 解答

① $17+32+128=177$ 字节。② $177 \times 65{,}536 = 11{,}599{,}872$ 字节。③ 索引区 $12 \times 65{,}536 = 786{,}432$ 字节。④ 合计 $12{,}386{,}304$ 字节（约 11.8 MiB）。不需要实测：这是格式规定的静态算术，与[例 17.2.1](ch17.md#ex-17.2.1) 同一算法。要留意的是别把这类算式写成「性能提升百分之几」——那是另一笔账。

:::

:::

::: ex B9 · 设计说明挑四错（主线 ②④） {#ex-17.B.9}

一份段格式说明写了四句：「索引按变长摆放以省空间，仍支持二分」「删除即从旧段抹掉记录」「校验和只覆盖数据区」「段写完后可原地更新头部」。逐句说明各破坏了什么。

::: sol 解答

①变长索引不能定址，第 $i$ 项位置不再是「基址加宽度乘 $i$」，二分退化成顺序扫描。②抹掉删除记录，旧段同键值会复活——墓碑必须活到压缩。③索引区被截断时读出的偏移越界，校验和必须覆盖索引区。④头部一改，正在读的快照看到的就不是同一份文件，「写定即不可变」这条不变量破了。四句分别对应 [17.2 常见错误清单](ch17.md#sec-cpp-rust.4.17.2) 的 E-b2、E-e、E-d、E-c。

:::

:::

::: ex B10 · 这段 SAFETY 为什么过不了评审（主线 ①） {#ex-17.B.10}

某读路径注释只写了一句：「这里不会越界，因为我们的格式保证偏移正确。」按 17.3 的标准说出它缺的要素，并解释「格式保证」为什么不算担保。

::: sol 解答

注释至少要写：前提（偏移与长度经溢出检查且不超过缓冲长）、谁保证、在哪一层检查（构造时核对加每次访问的边界检查）、对齐与元素类型、为什么没有别名写冲突、前提失效会怎样。「格式保证」不是编译期或运行期的检查：段文件一旦被截断或损坏，格式立刻不成立，越界读就发生。能算出来的前提写进代码，别只写在注释里。对照[例 17.3.1](ch17.md#ex-17.3.1)。

:::

::: ex B11 · 「`dyn` 慢 34%」的缺口（主线 ③） {#ex-17.B.11}

复述 [例 17.4.1](ch17.md#ex-17.4.1) 的场景：泛型版在基准夹具里跑，dyn 版在单元测试里跑一段固定记录数。列出四个缺口，并按正文给出补齐顺序。

::: sol 解答

缺口：①计时边界不同（预热与多次迭代对一次执行含首次装载）；②分母没说清（每条均值还是总时长）；③没有同轮交替，机器热状态进了差值；④没验两版输出逐字节相同。补齐顺序：同一份输入、逐字节相同的输出、同轮交替、写清单位与分母，先定契约再采数。正文没有为这个比较采集实测——修好协议跑出来的才算数，不许引用「34%」。

:::

:::

::: ex B12 · 饱和报告缺什么（主线 ③④） {#ex-17.B.12}

一份压力测试报告写：「`CAP` 从 64 降到 4 后端到端延迟下降、吞吐也下降，判定优化成功。」（题面的百分比是假设：17.6.2 实测了拒绝率与两个分母下的墙钟成本，端到端每请求延迟没有采集。）要让这句话配得上一个结论，还缺哪三样？各回答主线哪一步？

::: hint 提示

先问「延迟降的是谁的延迟」，再问「吞吐降掉的那部分去哪了」，最后问「降多少算不可接受」。

:::

::: sol 解答

①拒绝率：被拒请求占比，决定「延迟下降」是不是只发生在幸存者身上（①）。②口径统一：吞吐、延迟、拒绝率来自同一批请求、同一段时间窗，不能一个取自被拒前一个取自被拒后（②③）。③业务预算 $B$：拒绝多少算不可接受，缺了它「延迟更低」可以被业务当场驳回（④）。三样齐了才写结论句；在这之前任何方向判断都算把取舍藏起来。对照[例 17.6.1](ch17.md#ex-17.6.1)。

:::

:::

::: ex B13 · 重试做两遍（主线 ④） {#ex-17.B.13}

压缩子进程三种失败情形：没开始写就失败、写了半个临时文件就失败、已写完并重命名成功但父进程没收到结果。哪种情形会让重试生成重复段？给出检测「这条路径真实发生过」的办法。

::: sol 解答

第三种。段其实已存在，重试若不检查同名段就会再生成一个同内容段：语义仍对，空间翻倍。检测办法：由输入段生成号集合推导目标段名，存在则接进快照并记一次「重放收敛」计数——计数非零就是这条路径发生过的证据。**注意这是待补的修法，不是现状**：本项目段名取当前最大号加一、`rename` 前不检查（[定义 17.7.2](ch17.md#def-17.7.2)）。前两种里，固定临时名可覆盖残留，随机名会让垃圾累积。对照[例 17.7.1](ch17.md#ex-17.7.1)。

:::

:::

::: ex B14 · 三种区间位置（主线 ③④） {#ex-17.B.14}

设配对差值的 95% 区间为 $[L, U]$，预算为 $B$。分别就 (a) $U \le B$、(b) $L > B$、(c) 区间跨过 $B$ 三种位置写出判定与下一步动作。(b) 里「回到机制」在本项目通常指回到哪两处？

::: sol 解答

(a) 接受：合入，把 $B$ 与判据留在门禁配置里。(b) 拒绝：回到具体机制重做，本项目通常是 17.2 的搬运量或 17.7 的进程边界，别只写「没达标」。 (c) 证据不足：独立时段重跑或扩大输入家族，不许换种子跑到绿灯为止；「证据不足」和「拒绝」的下一步动作必须不同。对照[例 17.8.1](ch17.md#ex-17.8.1)、[定义 1.7.2](../part1/ch01.md#def-1.7.2)。

:::

::: ex C16 · 把越界风险改没（主线 ①） {#ex-17.C.16}

把 17.3 的 `value_at` 改成安全版本：写出签名（返回类型是切片引用或空值），说明偏移加法用什么防溢出、越界与溢出的返回值最后进了哪个计数。再用一句话回答：省掉的到底是什么，付出的是什么？

::: hint 提示

::: ex C17 · 写一条确定性测试（主线 ①④） {#ex-17.C.17}

「读者持快照期间旧段不释放」不许靠压测。按 `projects/tidekv/src/epoch.rs` 的 `pin`、`release`、`advance`、`retired_len` 接口，写出这条测试的六步驱动，新建文件放在 `tests/` 下。

::: ex C19 · 组装证据包（主线 ④） {#ex-17.C.19}

`projects/tidekv/results/run-01/` 将存放本次实验的全部证据。列出目录里应有的八项以上内容；任选四项，各写一句「它回答评审的哪一问」；最后写「怎么复跑」一句的范围。

::: hint 提示

按「别人只凭这个目录就能复算出同样的表」来验收：缺哪件，哪一步就得回来问我。

::: ex C20 · 读这张表（主线 ②③④） {#ex-17.C.20}

[17.8.2 的实测表](ch17.md#sec-cpp-rust.4.17.8) 里 `put_wide` 的配对差值是 +40476.5 ns/op，95% 区间 [40105.6, 40819.8]，基线 A 是 63.144 ns/op。请回答：① 为什么这个区间说明差异不是噪声，却仍然不能写成「tidekv 慢 642 倍」？② 把这条结论按六槽位重写一遍。③ 三态判定给了「拒绝」，你的下一步动作写什么？

::: sol 解答

① 区间不跨零、宽度只有 714 ns（约为差值的 1.8%），21 轮配对、同轮交替、预热 500 ms 都做到了，所以 ③ 这一步是过关的。但 642 这个比值把 A 与 B 当成了同一件工作的两种写法：A 不落盘，B 在计时边界内做日志追加、CRC 与每 300 次操作一次段落盘。按 ② 的判据，分母相同、语义相同、可观察输出相同才算同一件工作，这里语义相同而**副作用不同**，所以比值只能读成「持久化路径每操作多付约 40.5 μs」。

② 六槽位：本机（Apple M5 Pro、rustc 1.99.1、`hw.cachelinesize` 128、macOS 27.2）与固定输入家族（写 300 B 值、2 万键、70% 写 / 10% 删 / 20% 读，每 300 次操作落一次盘）下，批均值为 A=63.144、B=40539.7 ns/op；配对差值 +40476.5，95% bootstrap 区间 [40105.6, 40819.8]，方向确定为 B 更慢；预算 1000 ns/op 时判为拒绝；本结论不覆盖不含落盘的比较、不含大值记录、不覆盖其它机器与编译器版本。

③ 「拒绝」的下一步要具体：先改命题（把预算换成「每操作持久化开销」并由崩溃点目标推出 X），或改实现（键值分离、批量提交日志）。只写「继续优化」不算下一步。

::: ex C21 · 算式与实测差了十倍（主线 ①②） {#ex-17.C.21}

例 17.2.2 里单槽上界是 1/256，而 `tests/bloom_contract.rs` 实测经验假阳率是 1,525/200,000 ≈ 1/131。① 这个落差从哪里来？② 如果只按 1/256 去选指纹宽度，会做出什么错误决定？③ 为什么「漏报为零」这条断言不能靠这个比例推出来，必须单独测？

::: sol 解答

① 每键 8 字节 = 64 bit，但一个桶是 `BUCKET = 16` 字节，一次探测比较的是 **16 个** 8 bit 指纹槽；整体误判是这 16 次比较的并集，上界约 $16/256 = 6.25\%$。实测 0.762% 落在 1/256 与 16/256 之间，说明单槽上界从来不是整体假阳率。

② 会以为 10 bit 就能压到千分之一，实际上按 16 槽并集要 $\lceil \log_2 16000 \rceil = 14$ bit；反过来也可能因为误信 3.1% 而把宽度加到用不着的位数。两种都是拿错口径的算式指导参数选择。

③ 布隆的契约是「说不在就一定不在」，这是**方向性**命题，与误判率的**大小**无关：0.762% 只描述「说在」里有多少是假的，推不出「说不在」里有没有真的。所以无漏报必须由测试逐键核对（本项目 `no_false_negatives_direct` 插入 20,000 个键后逐键 `contains` 断言），而不是由比例算出来。

## 批改时最常给的三条意见

1. **把静态算术写成实测收益**：字节数算得出，「快百分之几」算不出。每个百分比后面必须跟算式或同窗实测，否则删掉这个百分比。
2. **结论句缺槽位**：机器与构建、输入家族、单位分母、差值区间、方向判定、不覆盖范围，六格缺一格就退回重写；没采集的格子留空注明，不许用印象数字顶替。
3. **用「跑过没崩」代替验证**：回收窗口、幂等路径、不变量都必须有能被驱动的确定性测试；压测只能提供嫌疑，不能提供结论。

## 17.8 的复现口径 {#repro-17.8}

正文的 17.8.2 表只给数，这里给两条能对账的口径。

**一、四个 95% 区间怎么逐位复现。**重采样单位是**配对后的 21 个轮均值差**，不是原始批行；算法在 `projects/tidekv/analyze.py:76-86`（percentile bootstrap、20 000 次、种子 `seed ^ 0xB007`）。复现就是重放同一条命令：

```console
$ python3 analyze.py results/run-01/bench.csv /tmp/replay.json
```

第二个参数别省：`analyze.py` 缺省会往证据包里写 `statistics.json`，白跑一次就把归档覆盖了。
四个区间会逐位回到表里的数；run-02 的 `compaction.csv` 同样复现 `1366635.811111`。若跳过 `paired()`、自己拿 raw 行重采样，尾端会差到千分之几——那是另一种口径，不是数据错了。

**二、写占比排序为什么和付费顺序不一致。**四个 case 的差值从大到小是 `put_wide` +40,476.5 > `get_hot` +33,748.1 > `scan_12` +32,080.6 > `get_absent` +24,409.7。按 case 标签上的读写比（70-30 / 90-10 / 纯读 / 80-20）看，确实像「写得多的更贵」；但标签只描述**随机段**，真实分母里还掺着不等量的 setup 写。
按 `ops` 列与生成器（`src/bin/tide-bench.rs`）算出来的每批写占比是 `scan_12` 82%、`put_wide` 81.1%（730/900；标称 80——730 不在归档里，`bench-verification.txt` 只记 `ops=900`，它是按 `seed=20261028` 重放生成器复算的实现值）、`get_hot` 72%、`get_absent` 53%，排序变成 `scan_12` > `put_wide` > `get_hot` > `get_absent`，与付费顺序**不一致**；值长也各不相同（80 / 300 / 120 / 120 B）。正文接着那句「这四个数只支撑 24–40 μs/op」就是这段对照的结论。
