## 13.1 先定义问题，再选择采集器 {#sec-cpp-rust.4.13.1}

### 热不是慢的同义词

用户看到的慢通常是从提交到完成的墙钟时间。
CPU采样通常更接近“进程运行期间出现了哪些执行栈”。
线程栈快照还可能看到正在睡眠的线程。
事件采样则回答“某类事件发生时，记录到了哪些位置”。
这些问题相关，却不是同一个统计量。

一个请求可能大部分时间在排队。
它真正运行时的全部CPU样本却都落在一个很短的解析函数里。
解析函数在CPU图上很宽，不意味着删除它就能消除排队时间。
反过来，一个锁竞争严重的线程也可能在CPU图上几乎消失。
它没有获得CPU，自然不会积累同样多的运行样本。

因此，排查的第一步不是执行最长的一条采样命令。
第一步是写出希望解释的现象。

| 现象 | 首先需要的观测 | 不能直接代替它的东西 |
|:--|:--|:--|
| 一个批次完成慢 | 批次墙钟与输入规模 | 单个函数样本百分比 |
| CPU占用高 | 运行栈、线程与活动区间 | 只看请求平均耗时 |
| CPU低但响应慢 | 等待阶段、排队与资源就绪时间 | 只看CPU flamegraph |
| 同样工作突然多用CPU | 工作量、代码版本、事件或指令证据 | 只比较两张归一化图 |
| 加观测后吞吐掉落 | 有/无观测的受控实验 | 认为观测成本恒为零 |
| 某行cache miss多 | 正确事件定义、可用PMU、采样位置误差 | 仅凭源码中出现指针 |

### 证据层次

<pre class="layout">
业务现象：批次完成时间、输入、正确性
                 |
                 v
执行分解：运行 / 就绪未运行 / 主动等待 / 外部等待
                 |
          +------+------+
          |             |
          v             v
栈采样与符号        阶段时间与相关标识
          |             |
          +------+------+
                 v
候选机制：更多工作、失去向量化、竞争、排队、外部资源
                 |
                 v
受控修改 + 独立重跑 + 保留反例
</pre>

读图：上层现象给下层采集器提出问题。
下层工具不能自动把所有样本转换成业务责任。
最后一条边要求重新运行，而不是只给最宽的框改颜色。

### 一个可反驳的假设应包含预测

“这个函数很热”只是描述。
“每个元素读两次时钟使循环失去原来的轻量执行路径”才接近机制假设。
它应产生可检查的预测。

例如：

1. 保持业务输入与输出相同。
2. 删除逐元素时钟，业务结果不变。
3. 批量统计保留总数，但不保留逐元素时长分布。
4. 优化后产物仍有业务计算，没有被死代码删除。
5. 未附着采样器的正式计时表现出成本差异。

若这些预测不成立，就应修改假设。
不能因为图看起来符合直觉而忽略校验失败。

### 不把层级责任压成一个“耗时”字段

至少区分下列时间戳：

- 输入进入系统。
- 准入许可获得。
- 工作真正开始。
- 外部资源准备好。
- 执行线程恢复。
- 结果完成并可观察。

同一条请求链中的不同阶段可能由不同线程推进。
栈采样没有请求id时，不能可靠恢复这种跨线程因果链。
Rust的所有权转移有助于实现正确协议。
它并不自动为profiler生成业务关联。

### 本章采用两份彼此分离的证据

第一份是未附着profiler的21批计时。
它用于比较受控工作负载的总体成本。
第二份是另行启动进程后采集的栈快照。
它用于识别主要执行位置或等待位置。

两份证据使用同版工作负载源码。
它们不是同一次执行，也不应逐条配对。
采样运行不进入计时统计。
本章也不从二者相减计算“采样器开销”。

## 13.2 样本、符号与归因分母 {#sec-cpp-rust.4.13.2}

### 一条样本究竟记录了什么

一个采样记录可能包含时间、线程、指令地址和调用链。
具体字段由工具、事件类型、权限和配置决定。
没有采到的字段不能从图形外观补出来。

指令地址需要映射到实际加载的映像。
映像需要对应正确的构建版本。
源代码行号又依赖调试信息与优化后的地址范围。
这条链任一处错配，都可能得到非常漂亮的错误报告。

Rust代码尤其要留意：

- 泛型会产生多个具体实例。
- 内联可能把函数体放进调用者。
- 一个源码函数可能对应多个代码区域。
- 一个机器码位置可能携带内联调用链信息。
- 同一函数名可能来自不同crate版本或feature配置。
- 符号名很长不等于它执行了更多工作。

### inclusive与self不是两份独立开销

父栈的inclusive计数包括经过它的子栈。
叶子的self计数表示观察停留在该叶子的位置。
把所有层的inclusive计数相加，会重复统计同一条观察。

本轮CPU采样主线程根计数为1698。
`compute`下的`mix`叶子计数为1082。
另有616条叶子落在`compute`本身。
二者相加等于1698。

不能再把根1698也加进去，报告3396个“工作样本”。
根与叶子是同一观察的不同层级表示。

### 符号可读性不等于语义稳定

本轮`sample`保留了Rust修饰符号。
正文为了说明使用短名`compute`与`mix`。
原始报告里的完整符号和地址没有被改写。

若将来使用demangler，应保存转换命令与工具版本。
只保存demangle后的文字，可能丢掉区分crate实例的信息。
更不能把转换后的名字视为可链接的稳定Rust ABI。

### 类型与布局表

这些值来自本轮可运行程序的布局输出。
它们不是序列化格式，也不是跨编译器的结构体ABI保证。

| 对象 | 本轮size | 本轮align | 观察责任 |
|:--|--:|--:|:--|
| Event | 16字节 | 8字节 | 一个id与一个耗时值 |
| Vec&lt;u8&gt; | 24字节 | 8字节 | 拥有实验输入缓冲，不包括堆数据 |
| &amp;[u8] | 16字节 | 8字节 | 借用输入视图，不拥有数据 |

`Event`是两个u64字段的普通Rust结构体。
本实验不对它进行跨进程共享或FFI传递。
若需要持久化事件，应显式定义字节序、字段与版本。
不能直接把内存字节写盘，宣称获得了稳定日志协议。

### 生命周期比字段数更重要

本实验每次构造的Event经`black_box`观察后立即结束生命周期。
没有把二十万个Event存入Vec。
因此它不测事件队列增长或磁盘写入。
也不测日志格式化和后台flush。

这种选择是为了控制变量。
它保留时钟和观察屏障的成本。
它排除了持久化链路。
读者若加入真实日志系统，必须重新测量。

### ABI与代码生成表

| 边界 | 本轮产物中的观察 | 结论边界 |
|:--|:--|:--|
| mix输入到返回值 | 标量递推、输入屏障、实际函数体 | 没有测纯乘法吞吐 |
| compute到mix | 保留实际调用与循环 | noinline属于夹具成本 |
| observed的Each路径 | 时钟与事件观察保留 | 不等于任意日志库的成本 |
| 普通Rust Event | 本地布局探针为16/8 | 没有承诺C ABI |
| 采样指令地址到源码 | debug=1及固定映像 | 不保证每个内联位置都完整恢复 |

### 不能从符号缺席推出调用不存在

函数可能完全内联。
尾调用可能改变栈的形状。
采样区间可能从未覆盖短暂初始化。
工具还可能无法展开某段栈。

所以“图里没有函数F”至少有四种解释。
先查产物和采集范围，再判断F是否真的不运行。
对短生命周期进程尤其如此。

### 最低归档要求

每份采样报告都应能找到：

1. 对应的可执行映像或其可核验指纹。
2. 对应源码指纹。
3. 构建profile与feature集合。
4. 目标三元组和编译器版本。
5. 采样命令、区间与间隔。
6. 原始报告而不只是截图。

缺少这些信息，图只能作临时线索。
不能作长期回归基线。

## 13.3 perf与PMU：先读事件契约 {#sec-cpp-rust.4.13.3}

### 平台裁决

本节讨论Linux工具的机制与迁移检查清单。
本轮没有在Linux上执行任何命令。
以下命令是有明确适用前提的复现设计，不是本机执行记录。

```bash
# 仅用于具备权限与相应事件支持的Linux主机；本轮未执行。
perf stat -e cycles,instructions -- ./workload
perf record -F 99 --call-graph dwarf -- ./workload
perf report --stdio
```

`perf stat`的计数与`perf record`的抽样需要分别解释。
前者汇总某段范围内的事件计数。
后者在触发条件满足时记录位置与可能的调用链。
同样的事件名称也不能抹平CPU型号和内核支持差异。

### cycles不等于墙钟计时器tick

核心运行周期、参考周期与系统计时器是不同概念。
频率变化会影响它们之间的关系。
等待状态也会影响事件是否增长。

本章的Instant读数只用于墙钟间隔。
没有把它转换成核心cycles。
也没有用处理器宣传频率乘纳秒生成“测得周期数”。
这种乘法至多是带强假设的估计。
它不是PMU观测。

### IPC首先是同一范围内的比值

指令数除以周期数常被称为IPC。
但分子分母应覆盖同一任务、区间和权限范围。
若一个包含内核态，另一个仅用户态，解释会失真。
若两者在不同阶段轮流运行，直接相除也可能误导。

IPC高不等于业务快。
程序可能执行了大量无用但易并行的指令。
IPC低也不自动意味着需要手工向量化。
依赖链、访存、分支和调度都可能相关。

### 硬件计数器槽位是有限资源

同时请求过多事件，可能触发复用。
`perf_event_open`提供time_enabled与time_running来描述这种情况。
计数器只在部分时间实际运行时，可据此缩放估计总数。

概念上的缩放为：

```text
估计总数 = 实际计数 × time_enabled / time_running
```

这不是凭空恢复遗漏阶段的真实事件序列。
它依赖被观测区间有足够代表性。
若工作负载分阶段突变，轮转到某事件的时段可能偏向某一阶段。
复用比例低时，漂亮的小数位并不会提高可信度。

### event group不是让硬件拥有无限槽位

事件组可帮助协调相关事件的调度与读取。
它不能突破实际硬件资源限制。
无法同时调度时，应检查失败、未支持或未计数状态。
不要把这些状态当成零事件。

零是一个数据值。
“不支持”是能力信息。
“未运行”是采集状态。
三者应该在数据结构里区分。

### skid限制了源码级归因

事件发生到记录指令位置之间可能存在偏移。
手册把这类偏移称为skid。
`precise_ip`表达对偏移的要求，但硬件支持有边界。

因此，某条加载后面的算术行出现事件样本，不一定由算术引发miss。
也不能看到某行很宽，就给那一行加prefetch。
应先确认事件支持、精确级别和生成代码。

### 事件名字不保证微架构含义一致

所谓cache miss可能指不同层级、不同访问类别或不同状态。
原始事件编码更依赖型号。
通用别名也需要查当前主机的实际映射与文档。

跨机器报告时至少保留：

- CPU型号与微码/系统信息中实际可得的部分。
- 事件完整名称与修饰符。
- 用户态/内核态过滤范围。
- 线程、进程或CPU范围。
- time_enabled/time_running或工具给出的运行比例。
- 丢失记录、权限限制和错误输出。

本章没有这些硬件采集记录。
因此性能表中没有任何“miss率”或“IPC”列。

### 事件数如何进入优化决策

假设减少分配后墙钟下降，同时分配调用样本下降。
这构成一致的线索。
若还观察到指令数下降，机制解释会更完整。
但不应反向宣称一切加速都来自指令数。

需要比较业务工作量和输出。
需要排除缓存边界、调度与输入变化。
PMU给出额外观测维度，不给出自动因果证明。

## 13.4 Flamegraph、off-CPU与异步链路 {#sec-cpp-rust.4.13.4}

### flamegraph是一种聚合视图

把调用栈与权重折叠后，可以画成横向宽度图。
父框覆盖经过该调用路径的权重。
子框展示其中更深一层的分布。
同名函数出现在不同父路径下，通常仍是不同框。

经典flamegraph横轴不是时间轴。
相邻框不表示它们先后执行。
颜色通常也不是温度计。
没有图例时，不应把红色解释成更慢或更高温。

### 权重必须写在图旁

权重可以是CPU样本数。
也可以是线程快照数、分配字节数或阻塞纳秒数。
同样的画法，可以表达完全不同的对象。

标题应包含权重和范围。
例如“主线程栈快照，独立采样运行，1ms请求间隔”。
不能只写“性能火焰图”，让读者默认是CPU时间。

### 本轮真实折叠数据

`tools/collapse_sample.py`把本轮sample树的inclusive计数转换为叶子exclusive权重。
转换器只支持本轮报告形状。
它不声称能解析所有版本的Apple报告。
原始sample文本始终是权威证据。

| 独立运行 | 根观察数 | 叶子路径数 | 主要叶子 |
|:--|--:|--:|:--|
| CPU | 1698 | 2 | mix1082、compute616 |
| waiting | 1648 | 5 | __semwait_signal1443、mix181 |

折叠文件是`cpu.folded`与`wait.folded`。
它们可作为后续绘图输入。
本轮没有运行Linux的stackcollapse-perf，也没有把文件改名为perf.data。

### 归一化会隐藏总量差异

两张各自归一化到100%的图，总宽总是一样。
一个版本即使整体更快，图中的某个函数比例仍可能变大。
例如其他部分减少后，剩下部分自然占更高比例。

比较前应同时展示总运行量与总权重。
差分图也要说明是否做了归一化。
否则读者会把“份额增加”误解成“绝对成本增加”。

### CPU图不能自动补出等待区间

只在CPU运行时采样，得不到完整off-CPU分布。
off-CPU分析需要知道线程何时停止运行、何时重新运行。
常见系统工具可用调度事件与栈信息重建部分区间。
但其权限、丢失记录和关联规则必须记录。

本轮的sample是线程栈快照。
等待线程可以反复显示同一睡眠栈。
这与按调度事件精确累计的off-CPU时长不同。

本章可以据此说“采样期间经常看到睡眠路径”。
不能据此说“线程总计阻塞了精确的某个纳秒数”。

### 主动等待与被迫等待也不同

`thread::sleep`是实验主动要求等待。
它不代表磁盘、网络、锁或CPU资源竞争。
出现nanosleep不能证明服务瓶颈是操作系统调度器。

真实请求中，应区分：

- 主动退避或定时等待。
- 等待输入到达。
- 等待容量或准入。
- 等待锁或条件变量。
- 已就绪但尚未获得CPU。
- 资源就绪但异步任务尚未恢复。

这些状态可能最终都表现为“请求没有完成”。
优化手段却完全不同。

### 异步任务栈不是业务因果栈

Future挂起后，原来的同步调用栈可能已经返回。
稍后在另一个worker恢复时，采到的是当时的poll链。
创建请求的入口可能根本不在栈上。

所以只看线程栈难以知道某个等待属于哪个请求。
需要span、任务id或消息关联。
关联数据也应限制大小与生命周期。
不能为了补足因果关系，永久保留每个请求的全部上下文。

### 丢失关联比丢失美观更严重

同一个任务id复用时，必须区分不同生命周期。
跨线程传递事件时，不能假设采集顺序就是因果顺序。
不同线程写日志的到达顺序可能交换。

本实验没有实现分布式追踪系统。
Event里的id只是本批操作编号。
它不跨批唯一，也不适合直接当全局trace id。

### 正确的图后行动

看到宽框之后，至少提出两个竞争性解释。
例如“执行更多次”与“每次执行更慢”。
分别需要调用次数和单次/批次工作量才能区分。
单纯展开更深一层，有时只会得到更详细的相关性。

下一步应设计能否定其中一个解释的实验。
本章的逐项观测实验就是这种受控修改。

## 13.5 Benchmark一：计算与等待的两份画像 {#sec-cpp-rust.4.13.5}

### 问题与固定工作量

入口是`src/bin/cpu_wait.rs`。
每批执行1000000次整数递推。
CPU分支只执行递推。
wait分支执行同样递推，再申请40ms线程睡眠。

两分支的checksum必须相等。
因此这是“计算相同、额外等待不同”的诊断夹具。
不是两个业务等价实现的优化比赛。
也不是用于测量单个nanosleep调用固定开销的程序。

### 业务核的完整实现

完整文件见`src/lib.rs`。
以下是该实验真正调用的两个完整函数。
无符号溢出使用wrapping语义，没有执行UB。

```rust
#[inline(never)]
pub fn mix(value: u64) -> u64 {
    std::hint::black_box(value)
        .rotate_left(9)
        .wrapping_mul(0x9e37_79b9_7f4a_7c15)
        .wrapping_add(17)
}

pub fn compute(count: u64) -> u64 {
    let mut value = 7;
    for _ in 0..count {
        value = mix(value);
    }
    value
}
```

noinline让调用路径容易核验。
它也使函数调用成本进入工作负载。
black_box限制编译器把整个结果预先折叠。
它不是硬件内存屏障。

### 可执行入口完整源码

```rust
use evidence_lab::{compute, report, warm};
use std::hint::black_box;
use std::time::{Duration, Instant};

const STEPS: u64 = 1_000_000;

fn run(wait: bool) -> u64 {
    let value = compute(STEPS);
    if wait {
        std::thread::sleep(Duration::from_millis(40));
    }
    black_box(value)
}

fn main() {
    let args: Vec<_> = std::env::args().collect();
    if args.get(1).is_some_and(|s| s == "--profile") {
        let wait = args.get(2).is_some_and(|s| s == "wait");
        let start = Instant::now();
        let mut checksum = 0;
        while start.elapsed() < Duration::from_secs(5) {
            checksum ^= run(wait);
        }
        println!("profile,wait={wait},checksum={checksum}");
        return;
    }
    let expected = compute(STEPS);
    warm(|| {
        assert_eq!(run(false), expected);
    });
    warm(|| {
        assert_eq!(run(true), expected);
    });
    let mut all = [Vec::new(), Vec::new()];
    println!("unit=batch_ms;steps={STEPS};requested_sleep_ms=40;checksum={expected}");
    for round in 0..21 {
        for offset in 0..2 {
            let index = (round + offset) % 2;
            let start = Instant::now();
            let value = run(index == 1);
            let ms = start.elapsed().as_secs_f64() * 1000.0;
            assert_eq!(value, expected);
            all[index].push(ms);
            println!(
                "raw,{},round={round},value={ms:.6},checksum={value}",
                ["cpu", "wait"][index]
            );
        }
    }
    for (case, samples) in ["cpu", "wait"].iter().zip(all.iter()) {
        report(case, samples);
    }
}
```

公共函数report与warm在同一实验包中完整提供。
本章统计定义在下一节展开。
以上入口没有依赖隐藏的外部服务或数据文件。

### 正式计时边界

| 操作 | 计入批次墙钟 | 理由 |
|:--|:--|:--|
| 创建进程与解析参数 | 否 | 不测冷启动 |
| 参考checksum | 否 | 校验基准不是业务工作 |
| 1000000次递推 | 是 | 两分支共有工作 |
| wait分支申请睡眠 | 是 | 被诊断差异 |
| checksum比较 | 否 | 在结束时间戳后执行 |
| 打印原始行 | 否 | 不将终端输出计入本批 |

计时外的打印仍可能影响下一批调度与缓存。
“不计入本批”不等于对整个进程无扰动。
本轮没有把stdout重定向到慢网络文件系统。
原始输出写入本地证据目录。

### 本轮实测

来源为`cpu-wait.txt`。
单位是ms/完整批次。
每case预热至少500ms，正式21批，轮转顺序。

| case | mean | N-1 sd | 批p50 | 批p99 |
|:--|--:|--:|--:|--:|
| cpu | 2.506964 | 0.082729 | 2.477333 | 2.782084 |
| wait | 46.442020 | 1.459728 | 47.026833 | 47.800375 |

共同checksum为14437947664662268765。
40ms是申请睡眠下限语义的一部分，不是精确唤醒承诺。
wait均值大于cpu加40ms，不应被解释成算法多算了四毫秒。
这里还包括计时器、调度和桌面环境影响。

### 另行采样的实际命令

脚本在正式计时结束后启动五秒循环。
启动后等待约0.3秒，再请求两秒采样。
间隔参数为1毫秒。

```bash
# measure.sh中执行的形状，PID由实际后台进程产生。
./target/release/cpu_wait --profile cpu > profile-cpu-run.txt &
PID=$!
sleep 0.3
sample "$PID" 2 1 -file sample-cpu.txt
wait "$PID"
```

waiting运行只把参数cpu改成wait。
两次采样没有并行启动。
进程中的采样循环不包含正式21批输出逻辑。
因此报告没有被每批统计打印所主导。

### 观察到的栈

CPU运行中，根1698条观察都在compute路径上。
其中1082条叶子落在mix，616条落在compute。
waiting运行中，1648条根观察里有1446条经过sleep。
其中1443条的主要叶子是`__semwait_signal`。

这支持“两个夹具的主要栈形状不同”。
它不支持把1446/1648直接替换成正式计时的等待比例。
采样与计时是不同运行。
请求间隔也不是精确固定的硬实时采样时钟。

### 不强求理想比例

从正式均值直觉估算，等待分支应大部分时间睡眠。
实际sample中的compute份额与该粗略估算并不精确相同。
本章保留这个差别。

没有记录每次采样的完整调度上下文。
不能判断差别来自间隔偏差、系统状态还是其他采集影响。
不能用调整报告计数的方法让它匹配预期。

## 13.6 Benchmark二：逐项打点与批量聚合 {#sec-cpp-rust.4.13.6}

### 安全Rust中的性能回退

入口是`src/bin/instrumentation.rs`。
每批执行200000步相同递推。
三种模式只改变观测方式。
所有模式必须得到相同业务checksum。

none不记录逐项观测。
batch在批末提交总步数。
each对每步读时钟、构造事件并提交原子计数。

这是人为构造且实际执行的安全性能回退。
不是某家公司事故叙述。
也没有执行数据竞争或悬空访问来获得“更快基线”。

### 每种模式保留什么

| 模式 | 总数 | 每步耗时 | 事件持久化 | 业务checksum |
|:--|:--|:--|:--|:--|
| none | 不记录 | 不记录 | 无 | 保留 |
| batch | 保留 | 丢失 | 无 | 保留 |
| each | 保留 | 构造并经屏障观察 | 无 | 保留 |

batch并不提供与each同样的诊断信息。
它的低成本不是免费保留全部分布。
如果业务要求逐请求异常定位，就需要另选采样或聚合策略。

### 完整观测核心

```rust
use std::hint::black_box;
use std::sync::atomic::{AtomicU64, Ordering};
use std::time::Instant;

#[derive(Clone, Copy, Debug)]
pub struct Event {
    pub id: u64,
    pub elapsed_ns: u64,
}

#[derive(Clone, Copy, Debug)]
pub enum Mode {
    None,
    Batch,
    Each,
}

pub fn observed(count: u64, mode: Mode) -> (u64, u64) {
    let counter = AtomicU64::new(0);
    let mut value = 7;
    for id in 0..count {
        let clock = matches!(mode, Mode::Each).then(Instant::now);
        value = evidence_lab::mix(value);
        if let Some(clock) = clock {
            black_box(Event {
                id,
                elapsed_ns: clock.elapsed().as_nanos() as u64,
            });
            counter.fetch_add(1, Ordering::Relaxed);
        }
    }
    if matches!(mode, Mode::Batch) {
        counter.fetch_add(count, Ordering::Relaxed);
    }
    (value, counter.load(Ordering::Relaxed))
}
```

上段为可独立使用的同义核心，调用库的mix。
实际库内写作`value = mix(value)`，避免自引用crate名。
完整编译测试的唯一源文件是`src/lib.rs`。
没有因为正文摘录而维护第二份实验实现。

### 原子计数的范围限制

counter是本次函数调用内部的局部原子对象。
没有其他线程并发访问它。
因此本实验不测共享缓存线竞争。

Relaxed只说明不借助它发布其他内存。
它不是取消计数原子性的声明。
但优化器也可能利用局部对象的上下文改变代码形状。
不应把整段耗时命名为“单次共享原子加法耗时”。

### 可执行入口完整源码

```rust
use evidence_lab::{Mode, compute, observed, report, warm};
use std::hint::black_box;
use std::time::Instant;

const STEPS: u64 = 200_000;
fn main() {
    let modes = [Mode::None, Mode::Batch, Mode::Each];
    let names = ["none", "batch", "each"];
    let expected = compute(STEPS);
    warm(|| {
        for mode in modes {
            black_box(observed(STEPS, mode));
        }
    });
    let mut all = [Vec::new(), Vec::new(), Vec::new()];
    println!("unit=ns_per_step;steps={STEPS};checksum={expected}");
    for round in 0..21 {
        for offset in 0..3 {
            let index = (round + offset) % 3;
            let start = Instant::now();
            let (value, count) = observed(STEPS, modes[index]);
            let ns = start.elapsed().as_secs_f64() * 1e9 / STEPS as f64;
            assert_eq!(value, expected);
            assert_eq!(count, if index == 0 { 0 } else { STEPS });
            all[index].push(ns);
            println!(
                "raw,{},round={round},value={ns:.6},checksum={value},count={count}",
                names[index]
            );
        }
    }
    for (case, samples) in names.iter().zip(all.iter()) {
        report(case, samples);
    }
    println!(
        "layout,Event,size={},align={}",
        std::mem::size_of::<evidence_lab::Event>(),
        std::mem::align_of::<evidence_lab::Event>()
    );
}
```

### 本轮实测

来源是`instrumentation.txt`。
单位为ns/聚合step，分母固定200000。
这些不是逐step延迟的分位数。

| 模式 | mean | N-1 sd | 批均值p50 | 批均值p99 |
|:--|--:|--:|--:|--:|
| none | 2.472857 | 0.094581 | 2.448330 | 2.798125 |
| batch | 2.470040 | 0.079995 | 2.448545 | 2.685205 |
| each | 32.832639 | 0.608977 | 32.762500 | 34.306250 |

业务checksum为188478885453998054。
batch与each的记录总数都为200000。
none的记录总数为零。

none与batch均值非常接近。
本章不据那一点差异宣称batch“优化了业务核”。
each成本明显更高，支持逐项观测污染轻量工作负载的判断。
差异包含时钟、屏障、事件与计数路径的组合。
本轮没有逐项拆解这些成分。

### 为什么不能事后减一个常数

插入观测会改变寄存器压力、内联和循环优化机会。
它还可能改变运行持续时间与调度机会。
因此“观测版减去空时钟循环”不一定恢复无观测版。

这种减法需要额外的可加性假设。
对极轻量循环尤其危险。
本章只报告两套真实程序的总体差异。

### 实际回归测试

`observation_does_not_change_business_result`校验三模式输出。
`batch_counter_loses_distribution_not_count`校验批量计数总数。
这些测试不依赖固定纳秒阈值。

功能测试应在慢机器上也能通过。
性能预算则需要单独的环境和证据策略。
把桌面均值硬编码进单元测试，会制造脆弱测试。

## 13.7 采样扰动、统计与Cachegrind边界 {#sec-cpp-rust.4.13.7}

### 采样频率不是越高越好

更高频率可能获得更多位置观察。
同时也会增加中断、展开、数据写入与分析成本。
某些工具可能主动限流或丢失记录。

样本数增加，不保证偏差下降。
若采样与周期性工作锁步，重复观察仍可能偏向同一阶段。
选择99Hz而不是100Hz是一种减少锁步风险的常见策略。
它不是对所有周期都有效的数学保证。

本轮sample使用请求间隔1ms。
报告根计数小于“2秒除以1ms”的理想算式。
这正提醒我们不能把请求间隔当成精确时钟。

### 检查扰动需要独立对照

要测外部采样器开销，应设计同等输入的附着/未附着运行。
两者应交替，并保留足够原始观察。
还要区分采集器CPU、被测进程CPU与总墙钟。

本轮没有做这种附着开销的21次配对实验。
逐项观测实验测的是应用内插桩。
不能把它的倍率写成sample或perf的开销倍率。

### 预热与顺序

warm函数使用Instant累计，至少持续500ms。
CPU与waiting各自预热。
instrumentation则在同一预热循环中遍历三模式。

正式轮次轮转case起点。
轮转减少配置与单向时间漂移完全重合的风险。
它不等于随机化，也不能消除温度或系统服务影响。

### 本轮统计定义

均值是21条原始观察的算术平均。
标准差分母为N-1。
p50与p99使用nearest-rank。

```text
mean = sum(x_i) / N
sd   = sqrt(sum((x_i - mean)^2) / (N - 1))
rank = ceil(probability × N)
quantile = sorted_values[rank - 1]
```

N=21时，p99就是最大观察。
不应把六位小数理解成六位有效精度。
原始输出保留小数便于复算，并非宣称仪器精度。

### 两种实验单位不能混用

cpu_wait每条值是一整个批次的ms。
instrumentation每条值是批次墙钟除以step数。
后者反映聚合吞吐倒数。

它不是在each内部采集的那二十万个Event的分布。
那些Event只经black_box观察，并未写入统计容器。
若需要真实逐项分位数，必须另做存储与扰动设计。

### Cachegrind擅长回答什么

Cachegrind在支持的平台上通过动态执行追踪累计指令等事件。
相对墙钟噪声，固定程序与输入的指令计数通常更稳定。
它适合检查“相同工作是否多走了很多机器指令”。

稳定不代表与原生机器完全相同。
模拟环境中的指令定义也可能不同于硬件retired instructions定义。
手册特别说明了x86 REP指令计数差异。

### 缓存模拟不是现代CPU的数字孪生

官方手册明确把缓存与分支模拟称为基础模型。
它不完整反映现代处理器。
当前文档还说明这些模拟默认关闭。
实际使用必须核对安装版本，不能套用旧博客默认值。

它没有自动模拟：

- 内核活动对缓存的全部影响。
- 其他进程的缓存竞争。
- 真实虚拟到物理地址映射。
- 所有TLB与推测执行导致的效果。
- 原生线程调度交错。
- 目标机器完整预取与分支预测机制。

因此，模拟miss下降不等于本机PMU miss必然下降。
模拟指令下降也不等于墙钟必然下降。
应把它作为补充观测，而非替代原生计时。

### 布局扰动同样会影响模拟结果

可执行大小、共享库、地址布局和路径变化都可能改变结果。
固定输入只是可复现条件之一。
不要因为工具强调稳定，就省略构建与环境指纹。

本轮没有执行Cachegrind。
本机也没有生成任何cachegrind.out证据。
书中没有用模拟数据补齐性能表。

### 桌面环境限制

正式测量持有共享目录锁。
采集前后进程名快照未发现cargo、rustc或clang构建进程。
这只是两个时点的观察，不是连续监控证明。

没有隔离桌面服务。
没有锁定CPU亲和性、频率或热状态。
所以表格只用于这个桌面环境中的工作负载诊断。
它们不是生产SLA，也不是硬实时上界。

## 13.8 从代码生成到证据包 {#sec-cpp-rust.4.13.8}

### 保留三个不同阶段

本轮实际保存了库的MIR、LLVM IR和原生AArch64汇编。
它们位于`codegen/`。
生成命令保存在`codegen-command.txt`。

MIR用于核对Rust中间表示里的控制流和调用。
LLVM IR用于核对更低层优化后的数据流。
原生汇编用于核对目标机器实际生成的函数体。
三者都不是“已经执行过全部路径”的证明。

### 生成命令

```bash
cargo rustc --offline --locked --release \
  --manifest-path bench/evidence-lab/Cargo.toml \
  --lib --target-dir NEW_CODEGEN_TARGET \
  -- --emit=mir,llvm-ir,asm
```

该命令在正式计时后执行。
代码生成采集不与benchmark并行。
本轮是本机目标，没有把交叉汇编当运行结果。

### mix实际保留的代码

从实际`.s`去掉调试行与常量构造细节后，可观察到：

```asm
str x0, [sp, #8]
ldr x8, [sp, #8]
ror x8, x8, #55
madd x0, x8, x9, x10
ret
```

这里x9来自前面的常量构造，x10设为17。
完整符号还包括栈调整与调试位置。
本书不把这五行当汇编课程。
它们只用于核对屏障、旋转与乘加没有被整段删除。

### 产物分析也要防止过度归因

看到madd，不表示整批墙钟只由乘加吞吐决定。
循环有数据依赖，也有函数调用。
black_box还引入可见存取。

看到原子指令，也不表示观测版的全部额外时间来自原子。
时钟和优化形状同样参与。
一个符号只能证明某个操作存在，不能分摊总成本。

### 原始目录的职责

| 文件或目录 | 内容 | 不承担的责任 |
|:--|:--|:--|
| environment.txt | 实际系统、工具链、profile | 完整环境隔离证明 |
| source-sha256.txt | 计时前源码与脚本指纹 | 第三方独立审计 |
| measured-source/ | 与计时前指纹匹配的源码快照 | 后处理工具已经在计时中运行 |
| binary-sha256.txt | 正式运行可执行文件指纹 | 位级可复现构建保证 |
| cpu-wait.txt | 42条原始批次 | 逐请求延迟分布 |
| instrumentation.txt | 63条原始批均值 | 持久化日志成本 |
| sample-cpu.txt / sample-wait.txt | 原生采样报告 | Linux perf事件 |
| cpu.folded / wait.folded | 叶子权重聚合 | 精确调度时间线 |
| codegen/ | 实际MIR/IR/汇编 | 所有优化版本的稳定承诺 |

### 原始文件优先于最终表

表格可以重新格式化。
原始观察不能为了获得理想结论而重排数值或删除慢批。
本轮保留全部21条，包括CPU批次的较大值。

若未来判定某批受到已知外部故障，应保留原值与排除理由。
再报告包含与排除两套结果。
不要静默把“异常值处理”变成结论修饰器。

### 指纹与证据的可追溯关系

源码指纹回答“本轮运行的是哪份输入”。
二进制指纹回答“采样与运行关联哪个产物”。
环境记录回答“这些结果在哪个平台产生”。
run-01之后为采集脚本补充了自动后处理与归档步骤。
其计时版本保存在measured-source中，与计时前SHA256逐项核对。
新增门禁和校验工具另有postprocessing-source-sha256记录。

三者共同提供定位能力。
任意一个都不能单独证明构建可信。
尤其不能把SHA256值本身当作正确性认证。

### 归因结论的模板

一个谨慎结论可以写成：

> 在本轮输入、编译器与桌面环境中，Each模式的聚合step成本高于None。
> 校验输出相同，主要业务递推保留。
> 修改同时引入时钟、事件屏障与计数路径，因此没有将差异拆成独立组件成本。

这比“日志让Rust慢十三倍”更有用。
后者丢掉工作负载、观测内容和测量范围。
前者给下一轮实验留下明确入口。

### 什么情况应该停止下结论

以下情况至少需要暂停比较：

- checksum不相同。
- 单位发生变化。
- 采样报告对应了旧二进制。
- 只剩截图，原始数据丢失。
- 编译profile或feature未知。
- 样本缺失却仍输出尾分位数。
- 工具报告丢失或不支持事件，但表格照填零。

暂停不是实验失败。
继续输出看似精确的数字才会破坏证据链。

## 13.10 常见陷阱 {#sec-cpp-rust.4.13.10}

1. **把线程栈快照称为CPU周期分布。**
   本轮sample能看到睡眠栈。
   权重是观察数，不是核心周期。
   先写分母再解释宽度。

2. **把inclusive计数全部相加。**
   一条观察会经过多个父层。
   应在exclusive叶子或互斥分类上求和。
   本轮折叠结果总数仍是1698和1648。

3. **认为最宽函数就是用户延迟根因。**
   请求可能主要在排队。
   CPU图只能描述被采到的执行。
   需要阶段时间与业务关联。

4. **把flamegraph横轴当时间轴。**
   聚合后相邻框不代表先后。
   需要时间顺序时应选择时间线视图。
   图题还必须标明权重。

5. **把batch聚合说成无损替代。**
   总数保留，逐项分布丢失。
   不能用低成本总数回答每个异常请求的问题。
   选择由诊断目标决定。

6. **测完插桩版再减一个固定时钟成本。**
   插桩可能改变向量化、内联与寄存器压力。
   可加性并不天然成立。
   受控无插桩对照更直接。

7. **把局部原子实验外推为共享争用。**
   本章counter没有并发访问者。
   没有测缓存线迁移或扩展性。
   Relaxed也不是争用消失的保证。

8. **把PMU不支持当成事件数为零。**
   能力缺失与测量结果不同。
   应保存错误与未运行状态。
   不允许在结果表填伪造的零。

9. **忽略事件复用后直接计算IPC。**
   分子分母可能未同时覆盖同一阶段。
   需要检查运行比例与事件组。
   缩放仍是估计。

10. **把事件归到记录位置那一行。**
    skid和内联会影响位置解释。
    先查事件支持与实际代码。
    不根据一条热行盲目加prefetch。

11. **把模拟缓存参数当真实微架构。**
    Cachegrind模型有明确缺项。
    原生PMU与墙钟需要另测。
    本轮没有Cachegrind结果。

12. **采样与正式计时同时跑却不记录。**
    观测本身改变执行环境。
    本章两者分开。
    另行采样不能直接估计附着开销。

13. **只保存SVG或截图。**
    图像不能恢复丢失的样本与映像对应。
    原始报告、二进制指纹和命令必须保留。
    聚合结果只是派生产物。

14. **把21条批均值p99称为服务p99。**
    nearest-rank下它只是最大批均值。
    没有逐请求到达过程。
    也没有极端尾部的足够样本支持。

## 13.11 出口检查 {#sec-cpp-rust.4.13.11}

### 从实验包复现

从`cpp-rust/`执行以下命令。
先构建，再采集；不要把编译耗时混进运行基准。

```bash
cargo fmt --manifest-path bench/evidence-lab/Cargo.toml --check
cargo clippy --offline --locked --manifest-path bench/evidence-lab/Cargo.toml \
  --all-targets --all-features -- -D warnings
cargo test --offline --locked --manifest-path bench/evidence-lab/Cargo.toml
cargo test --offline --locked --manifest-path bench/evidence-lab/Cargo.toml \
  --all-features
cargo build --offline --locked --release \
  --manifest-path bench/evidence-lab/Cargo.toml --bins

  --manifest-path bench/evidence-lab/Cargo.toml --bin feature_work \
  --target-dir bench/evidence-lab/target-checked

```

输出目录必须不存在，父目录需先存在。
脚本用mkdir取得共享测量锁，EXIT时释放。
它拒绝覆盖既有归档。
四项实验依次运行，不并行计时。

### 读原始证据

应能够手动完成以下核对：

1. 从cpu-wait原始行数出每case21批。
2. 检查所有业务checksum一致。
3. 用N-1重算标准差。
4. 用nearest-rank重算p50/p99。
5. 从sample根与叶子核对折叠权重。
6. 从`.s`找到mix实际函数体。
7. 从source-sha256定位计时前源文件。
8. 确认sample不是正式计时进程。

### 机制问答

应能解释：

- 为什么waiting图很宽不意味着CPU执行了四十毫秒睡眠指令？
- 为什么CPU采样与线程快照不能用同一标题？
- 为什么none与batch非常接近时不该宣称后者加速？
- 为什么局部原子计数不能预测多线程共享计数？
- 为什么逐项事件未存储就不能输出其真实分位数？
- 为什么反汇编证明计算存在，却不证明耗时都来自该计算？
- 为什么PMU复用缩放不能恢复被错过阶段？
- 为什么Cachegrind指令稳定不等于原生墙钟稳定？

### 可接受的本章结论

本轮两个实验验证了有限而明确的问题。
相同递推加主动等待，会产生不同墙钟与栈形状。
逐项观测会显著增加这个轻量递推夹具的聚合成本。

没有证明通用日志框架的固定开销。
没有证明Linux硬件事件归因。
没有证明生产服务尾延迟上界。
