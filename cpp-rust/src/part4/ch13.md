## 13.1 先定义问题，再选择采集器 {#sec-cpp-rust.4.13.1}

本节回答一个问题：**程序变慢时，第一个动作该落在哪一层？**「热」和「慢」经常被当成同一件事，它们却来自不同的统计量：墙钟、进程运行时间、硬件事件数、线程栈观察数，各有各的分母。本节先把现象与观测对象对齐，再给出证据层次、一份可反驳假设应有的形状，最后交代本章用哪两份彼此分离的证据。

::: preview 先抓住一件事

先确定分母，再选采集器。**肯定**一个归因，要能说清这个数字统计的是什么对象、在哪个区间上；**否定**一张热图的因果力，只要举出一个反例：一个请求大部分时间花在排队，而它真正运行时的全部 CPU 样本恰好落在一个很短的解析函数里——解析函数在图上很宽，删掉它却消不掉排队时间。
:::

### 13.1.1 热不是慢的同义词

用户看到的慢，通常是从提交到完成的墙钟时间；CPU 采样更接近「进程运行期间出现了哪些执行栈」；线程栈快照还可能看到正在睡眠的线程；事件采样回答的则是「某类事件发生时记录到了哪些位置」。这四句话互相相关，分母却各不相同，要互相替换得先做换算并补上对应的采集。

一个请求可能大部分时间在排队，它真正运行时的全部 CPU 样本却都落在一个很短的解析函数里。解析函数在 CPU 图上很宽，不意味着删掉它就能消除排队时间。反过来，一个锁竞争严重的线程也可能在 CPU 图上几乎消失——它没有获得 CPU，自然不会积累同样多的运行样本。所以排查的第一步是把希望解释的现象写下来，采样命令排在它后面。

::: def 定义 13.1.1 · 观测对象与分母 {#def-13.1.1}

一个性能数字的**观测对象**，是它真正统计的东西：一次批次的墙钟间隔、一段进程运行时间、一类硬件事件的计数，还是一批栈观察的条数。**分母**，是归一化时所用的计数集合：批内元素数、每次调用的字节数、还是总观察数。两者合起来决定一个百分比能和哪个百分比比较。分母不同的两张图，即使各自都写满 100%，说的也不是同一件事（对照第 1 章[@def-1.5.1] 的名义分母教训与[@def-1.1.3] 的实验契约）。

:::

按[@def-13.1.1] 把常见现象与「首先需要的观测」对齐，得到下面这张表；第三列写明谁在什么条件下才顶替得了谁，它是本节唯一需要背下来的东西。

| 现象 | 首先需要的观测 | 不能直接代替它的东西 |
|:--|:--|:--|
| 一个批次完成慢 | 批次墙钟与输入规模 | 单个函数样本百分比 |
| CPU占用高 | 运行栈、线程与活动区间 | 只看请求平均耗时 |
| CPU低但响应慢 | 等待阶段、排队与资源就绪时间 | 只看CPU flamegraph |
| 同样工作突然多用CPU | 工作量、代码版本、事件或指令证据 | 只比较两张归一化图 |
| 加观测后吞吐掉落 | 有/无观测的受控实验 | 认为观测成本恒为零 |
| 某行cache miss多 | 正确事件定义、可用PMU、采样位置误差 | 仅凭源码中出现指针 |

表中每一行第三列都在说同一件事：换一种观测对象，就要换一套采集器与一套分母，旧图的解释也就跟着失效。13.5 与 13.6 的两个实验分别落在第一行与第五行，13.4 会把「只看 CPU flamegraph」这条展开。

### 13.1.2 证据层次：每一层只回答自己那一层的问题

::: def 定义 13.1.2 · 证据层次 {#def-13.1.2}

**证据层次**指把一次性能排查拆成的五层：**业务现象**（批次完成时间、输入、正确性）、**执行分解**（运行 / 就绪未运行 / 主动等待 / 外部等待）、**观测**（栈采样与符号，或阶段时间与相关标识）、**候选机制**（更多工作、失去向量化（一条指令同时处理多项数据）、竞争、排队、外部资源），以及最后的**受控修改与独立重跑**。每层只支持它能支持的那句话：上层给下层提出问题，下层不会自动把样本转换成业务责任。

:::

### 13.1.3 一个可反驳的假设应包含预测

::: def 定义 13.1.3 · 可反驳的归因假设 {#def-13.1.3}

**可反驳的归因假设**是一条同时写出机制与预测的陈述：它说明「为什么这样会变慢」，并给出至少一个可以在现有证据之外检查、且有可能不成立的结论。「这个函数很热」只是描述，无法被任何结果否定；「每个元素读两次时钟使循环失去原来的轻量执行路径」才是机制假设，它承诺了删除时钟后业务结果不变、批量统计保留总数等可检查事项。

:::

「这个函数很热」只是描述。[@def-13.1.3] 要的是一句能被反例推翻的话，例如「每个元素读两次时钟使循环失去原来的轻量执行路径」。它应产生可检查的预测：

1. 保持业务输入与输出相同。
2. 删除逐元素时钟，业务结果不变。
3. 批量统计保留总数，但不保留逐元素时长分布。
4. 优化后产物仍有业务计算，没有被死代码删除（[@def-1.1.1]）。
5. 未附着采样器的正式计时表现出成本差异。

若这些预测落空，就该修改假设。图看起来符合直觉，顶替不了校验失败。[@def-1.7.3] 要求把探索性实验与确认性实验分开：在同一张图上反复调整到「看起来对」，得到的只是被挑选过的解释。

::: ex 例 13.1.1 · 把「这个函数很热」改写成可反驳的假设 {#ex-13.1.1}

某次评审会上给出两条陈述：

- A：「profile 里 `parse` 最宽，所以它是我们批次完成时间的根因。」
- B：「`parse` 每次调用被观察到很多次，把 `parse` 换成不解析直接取缓存后批次墙钟不变，说明它的宽度不进入用户等待。」

按[@def-13.1.3] 判断哪一条是描述、哪一条是假设；再说要否定 B 需要哪一条证据。

::: sol 解答

A 是描述：它把「被观察到很多次」直接写成「是根因」，中间没有可检查的预测，也无法被任何结果否定；本章反复要拦这种推理（对照[@def-13.1.2] 从第四层到第五层的要求）。B 是假设，它给出了机制（缓存路径不需要解析）、预测（替换后批次墙钟不变）和检验对象（批次墙钟，[@def-13.1.1]）。

要否定 B，最直接的证据是：保持输入与业务输出不变，替换 `parse` 后批次墙钟显著下降——那说明宽度确实进了等待；或者发现替换后 `parse` 的工作被搬到了别处（产物里仍存在等量调用），说明「不进入用户等待」这句话的观测对象已被换掉。两种都不成立时，B 才在自己的范围内站住。

:::

:::

### 13.1.4 不要把层级责任压成一个「耗时」字段

同一条请求链中的不同阶段可能由不同线程推进。至少应区分下列时间戳：

- 输入进入系统。
- 准入许可获得。
- 工作真正开始。
- 外部资源准备好。
- 执行线程恢复。
- 结果完成并可观察。

把它们压成一个「耗时」字段，就永久失去了「运行／等待／排队」的区分能力——[@def-13.1.2] 第二层执行分解需要的正是这六个位置。栈采样缺少请求 id 时，这种跨线程因果链就恢复不可靠（13.4 会给出异步任务栈的具体形状）。Rust 的所有权转移有助于实现正确的协议：谁拥有缓冲、谁负责完成后释放，这些在类型上就能写清。但它并不自动为 profiler 生成业务关联——编译器知道的责任，采集器看不见。

::: think 思考 · 只加一个 duration 字段会怎样 {#think-13.1.1}

一个服务在响应体里加了 `{"duration_ms": 128}`，并用它统计「慢请求都卡在哪个阶段」。这个字段能支持[@def-13.1.2] 的哪一层，不能支持哪几层？

::: sol 解答

它能支持第一层业务现象：批次墙钟有了数值，可以和输入规模、正确性一起读（第 1 章[@def-1.2.1] 的墙钟定义）。第二层执行分解支持不了——128 ms 里运行、就绪未运行、主动等待、外部等待各占多少，一个字段无从恢复。第三层两条采集路径同样不成立：既没有栈观察，也没有阶段时间戳，只有起点与终点的差。

要补齐，需要在六个时间戳位置分别记录（至少「进入系统」「真正开始」「资源就绪」「完成并可观察」四处），并带一个能跨线程识别同一请求的相关标识；标识的大小与生命周期还要受约束，见 13.4.6。
:::

:::

### 13.1.5 本章采用两份彼此分离的证据

第一份是未附着 profiler 的 21 批计时，用于比较受控工作负载的总体成本；第二份是另行启动进程后采集的栈快照，用于识别主要执行位置或等待位置。两份证据使用同版工作负载源码，但它们是两次独立执行，逐条配对没有依据；采样运行不进入计时统计。本章也不从二者相减计算「采样器开销」，13.7 已把它归入「本轮没有采集」。

这一点值得单独强调，因为它是本章最容易犯的偷换：把一次采样的栈份额，当作另一次计时的时间构成。13.5.7 的观察表里，waiting 运行的 1446／1648 与正式 21 批的均值就分属两份证据，二者之间可以谈的关系只有「形状是否相容」，不能谈「比例是否相等」。

::: method 判定流程 · 这个现象该先看哪一层

**批次完成慢** → 先看[@def-13.1.1] 意义上的批次墙钟与输入规模，再决定是否需要栈；单函数样本百分比不能直接代替它。
**CPU 占用高** → 需要运行栈、线程与活动区间；只看请求平均耗时区分不了「谁在跑」。
**CPU 低但响应慢** → 需要阶段时间与等待分类；CPU flamegraph 在这里几乎必然给出误导（[@def-13.1.2]）。
**怀疑观测本身有害** → 需要同版源码的有／无观测受控实验（13.6 的形状），一张图回答不了。
**任何一层缺证据** → 写「本节没有采集」，不从上层的数字外推（[@def-1.7.3]）。

:::

### 13.1.6 小结与常见错误

**小结。**① 热与慢是两个观测对象，先写分母再谈解释（[@def-13.1.1]）；② 排查按证据层次走，每层只支持自己那句话，最后一层要求重跑而不是改颜色（[@def-13.1.2]、[图 13-1](#c13-fig-layers-caption)）；③ 「这个函数很热」是描述，机制假设必须附带可否定它的预测（[@def-13.1.3]、[@ex-13.1.1]）；④ 六类时间戳不能压成一个耗时字段，所有权也不替你生成业务关联（[@think-13.1.1]）；⑤ 本章的计时与采样是两份彼此分离的证据，不逐条配对、不相减。顺着这条线往下，[13.2 样本、符号与归因分母](#sec-cpp-rust.4.13.2) 处理证据层次之下最小的单位：一条样本究竟记录了什么。

::: errata 常见错误清单（13.1 节）

E-a **把最宽的函数当成用户延迟根因。**排队时间根本不进 CPU 图（[@def-13.1.1]）；先查现象属于哪一层。

E-b **用单函数样本百分比解释批次完成慢。**分母是观察数不是墙钟（[@ex-13.1.1]）；先对齐观测对象。

E-c **把「这个函数很热」当成假设。**它没有任何可否定的预测（[@def-13.1.3]）；先补一句「若机制是 X，那么 Y 应当成立」。

E-d **把六类责任压成一个耗时字段。**起点与终点的差恢复不出运行／等待／排队（[@think-13.1.1]）；先查时间戳位置。

E-e **认为 Rust 的所有权会自动给出请求关联。**类型层的责任不是采集器的业务关联（13.1.4）；先查有没有跨线程标识。

E-f **拿采样计数与计时均值逐条配对或相减。**两者来自不同运行（13.1.5）；本章的答案是「不是同一次执行」。

E-g **只比较两张归一化图就断言「同样工作多用 CPU」。**归一化抹掉总量（13.4.4）；先查总运行量与总权重。

:::

## 13.2 样本、符号与归因分母 {#sec-cpp-rust.4.13.2}

本节回答一个问题：**一张栈图里最小的可核查单位是什么，哪些计数天生不能相加？**[@def-13.1.2] 把「栈采样」列为第三层的一条路径，这一节要把它拆开：一条样本记录了哪些字段、这些字段怎样映射回源码、inclusive 与 self 计数是什么关系、以及一份报告最少要带上什么才谈得上长期复用。

::: preview 先抓住一件事

一条样本是一个**位置观察**，不是一段时间。**肯定**「这 1082 条说明工作主要落在 `mix`」，要能说清它是叶子 exclusive 计数、根计数是 1698、二者相加不等于「工作样本」总数；**否定**「图里没有函数 F，所以 F 没运行」，只需列出内联（把函数体搬进调用点）、尾调用、采样区间未覆盖、栈展开失败这四种同样能解释缺席的原因。
:::

### 13.2.1 一条样本究竟记录了什么

::: def 定义 13.2.1 · 一条采样记录 {#def-13.2.1}

一个**采样记录**（sample）是采集器在某个时刻留下的一条位置观察，通常包含时间、线程、指令地址与调用链中的若干帧。具体有哪些字段，由工具、事件类型、权限和配置决定；**没有采到的字段不能从图形外观补出来**。地址要映射到实际加载的映像，映像要对应正确的构建版本，源码行号又依赖调试信息与优化后的地址范围——这条链上任一处错配，都能产出一份非常漂亮的错误报告。

:::

按[@def-13.2.1]，一条样本要能被解释，前提是它背后那三样东西同时可得：加载的映像、对应的构建、以及把地址翻译成行号所需的调试信息。缺任何一样，图上那些帧名就只是文字，不是证据（[@def-13.2.4] 把这一条写成归档要求）。

Rust 代码还要额外留意六件事，它们都来自语言本身的编译方式而不是工具缺陷：泛型会产生多个具体实例；内联可能把函数体放进调用者；一个源码函数可能对应多个代码区域；一个机器码位置可能携带内联调用链信息；同一函数名可能来自不同 crate 版本或 feature 配置；符号名很长不等于它执行了更多工作。

### 13.2.2 inclusive 与 self 不是两份独立开销

::: def 定义 13.2.2 · inclusive 计数与 self 计数 {#def-13.2.2}

**inclusive 计数**是「经过这个栈帧的观察条数」，它包含所有经过该帧的子栈；**self 计数**（也叫 exclusive 或叶子计数）是「观察恰好停留在这个位置的条数」。父帧的 inclusive 已经吃掉了子帧的观察，因此把所有层的 inclusive 相加会重复统计同一条观察；同理，把根帧的计数与叶子的计数再加一遍，就是把同一批观察数了两次。

:::

本轮 CPU 采样主线程根计数为 1698。`compute` 下的 `mix` 叶子计数为 1082，另有 616 条叶子落在 `compute` 本身，二者相加正好等于 1698。这组实测数字是[@def-13.2.2] 最干净的示例：叶子之和等于根，因为每条观察都恰好落在一个叶子上。

::: ex 例 13.2.1 · 三个数相加，错在哪一步 {#ex-13.2.1}

有人统计本轮报告：「根 1698，`mix` 叶子 1082，`compute` 自身叶子 616，所以一共 1698 + 1082 + 616 = 3396 个工作样本，`mix` 的实际份额应该按 1082／3396 ≈ 32% 报。」请指出错误，并给出 1082 的正确分母写法。

::: sol 解答

错误在把不同层级的表示相加。1698 是根的观察总数，1082 与 616 是它的两个叶子划分，`1082 + 616 = 1698`（本节的实测），再加一次根就是把每条观察数了两遍。正确的写法是：`mix` 占主线程观察的 1082／1698，`compute` 自身占 616／1698，两者互斥、和为 100%。

1698 是「主线程根观察数」，CPU 时间、周期数与业务工作量各有各的分母（[@def-13.1.1]）。所以这句话写成「在独立采样运行的这批线程栈快照里，`mix` 是 1082 条观察的叶子」就够了；「`mix` 消耗了 64% 的 CPU 时间」要等核心周期采下来才有依据——本轮没有采集核心周期，也不存在可用的时间换算（13.3.2）。

:::

:::

::: method 判定流程 · 这个计数能不能相加

**能相加**：同一父帧下互斥的叶子（exclusive）分类；同一次运行、同一互斥划分下的分类计数。
**不能相加**：不同层级的 inclusive（父已含子，[@def-13.2.2]）；根计数与它自己的叶子划分；两份不同运行的观察数——那属于两份证据（13.1.5）。
**要检查**：加完之后与根对照。若总数大于根，几乎一定是层级重复；若小于根，先查是否有未展开的帧或被丢弃的观察，不要默默把它当损失。

:::

### 13.2.3 符号可读性不等于语义稳定

本轮 `sample` 保留了 Rust 修饰符号（mangled symbol：把模块、泛型实例与版本编进名字的那套编码）。正文为了说明使用短名 `compute` 与 `mix`，原始报告里的完整符号和地址没有被改写。

若将来使用 demangler（把修饰名还原成可读名字的工具），应保存转换命令与工具版本。只保存 demangle 后的文字，可能丢掉区分 crate 实例的信息；更不能把转换后的名字视为可链接的稳定 Rust ABI——第 1 章[@def-1.5.1] 已经给过一次同类教训（符号别名是当前构建的观察，不是接口承诺），这里适用于同一逻辑。

### 13.2.4 类型与布局表：观测到什么，承诺了什么

这些值来自本轮可运行程序的布局输出。它们不是序列化格式，也不是跨编译器的结构体 ABI 保证。

| 对象 | 本轮size | 本轮align | 观察责任 |
|:--|--:|--:|:--|
| `Event` | 16字节 | 8字节 | 一个id与一个耗时值 |
| `Vec<u8>` | 24字节 | 8字节 | 拥有实验输入缓冲，不包括堆数据 |
| `&[u8]` | 16字节 | 8字节 | 借用输入视图，不拥有数据 |

`Event` 是两个 `u64` 字段的普通 Rust 结构体。本实验不对它进行跨进程共享或 FFI 传递。若需要持久化事件，应显式定义字节序、字段与版本；不能直接把内存字节写盘，宣称获得了稳定日志协议。

::: def 定义 13.2.3 · 布局观测与协议承诺 {#def-13.2.3}

**布局观测**是「本次构建里 `size_of` 与 `align_of` 的返回值」，它只对当前目标三元组、当前编译器版本与当前 feature 集合负责。**协议承诺**是「任何读者、任何版本都能按同一套字节解释这些数据」。从前者到后者需要额外的工作：显式字节序、字段宽度与对齐规则、版本号、以及跨语言边界的调用约定。本轮的 16／8 只是布局观测，不构成协议承诺（对照第 1 章[@def-1.1.3] 的外部条件集合）。

:::

::: ex 例 13.2.2 · 能不能把 Event 直接写盘 {#ex-13.2.2}

`Event` 本轮布局是 16 字节、对齐 8，两个 `u64` 字段。有人提议「既然这么整齐，直接把结构体内存 `write` 到日志文件，省一次序列化」。按[@def-13.2.3] 说出这句话混淆了什么，以及要把它变成合法设计还缺哪几件。

::: sol 解答

混淆的是布局观测与协议承诺。16／8 只说明本机本次构建里 `size_of` 与 `align_of` 的返回值（[@def-13.2.3]），它对字节序、字段顺序、跨版本稳定性一个字都没说；`u64` 的内存表示依赖目标平台，两个 `u64` 的排列也不由语言承诺固定。

要变成合法设计，至少要补四件：显式字节序（例如小端）、显式字段宽度与顺序、一个版本号字段或头版本、以及一份把布局与解释规则写死的读写测试。补完之后，这就是一个新的协议实验，需要重新采集成本数据——本节的计时夹具没有测持久化链路（13.2.5），也没有测日志格式化与后台 flush，**本节没有采集**这些数字。

:::

:::

### 13.2.5 生命周期比字段数更重要

本实验每次构造的 `Event` 经 `black_box` 观察后立即结束生命周期，没有把二十万个 `Event` 存入 `Vec`。因此它不测事件队列增长或磁盘写入，也不测日志格式化和后台 flush。

这种选择是为了控制变量：它保留时钟和观察屏障的成本，它排除了持久化链路。读者若加入真实日志系统，必须重新测量——[@def-1.1.3] 的输入集合与观察集合都变了，旧的均值不再对应新的估计对象。

| 边界 | 本轮产物中的观察 | 结论边界 |
|:--|:--|:--|
| mix输入到返回值 | 标量递推、输入屏障、实际函数体 | 没有测纯乘法吞吐 |
| compute到mix | 保留实际调用与循环 | noinline属于夹具成本 |
| observed的Each路径 | 时钟与事件观察保留 | 不等于任意日志库的成本 |
| 普通Rust Event | 本地布局探针为16/8 | 没有承诺C ABI |
| 采样指令地址到源码 | debug=1及固定映像 | 不保证每个内联位置都完整恢复 |

这张表的第三列是它的全部价值。「保留实际调用与循环」只支持「本轮产物里这条调用没有被折叠掉」，不支持任何关于真实内联后收益的说法——`#[inline(never)]` 是夹具的选择，第 1 章 1.3.3 已经交代过它的代价（[@def-1.1.2] 的屏障只影响优化器可见的信息，不改变语义）。同理，「时钟与事件观察保留」只说明本轮这条路径里那些动作真的存在，不能外推成任意日志框架的成本；「本地布局探针（为了不删掉某段代码而故意留下的一次读取）为 16/8」是一次 `size_of` 调用，不是一次 ABI 承诺（[@def-13.2.3]）。

最后一行还要提醒：`debug=1` 与固定映像让地址翻译有条件成立，但「每个内联位置都完整恢复」没有被验证过，13.2.6 说的就是那类缺席。

### 13.2.6 不能从符号缺席推出调用不存在

函数可能完全内联。尾调用可能改变栈的形状。采样区间可能从未覆盖短暂初始化。工具还可能无法展开某段栈。所以「图里没有函数 F」至少有四种解释，先查产物和采集范围，再判断 F 是否真的不运行；对短生命周期进程尤其如此（[@def-13.2.1] 的地址翻译链在这里反向使用）。

::: think 思考 · 图里没有 `alloc`，就能说没分配吗 {#think-13.2.1}

本轮 `compute` 与 `mix` 的源码里没有分配，但在别人的报告里，一个明显会分配 `Vec` 的实现却没有出现任何分配器（负责申请和归还堆内存的那层代码）符号。列出至少三种与「没有分配」无关的解释，并给出最小一步核验动作。

::: sol 解答

三种解释：① 分配发生在被内联的路径里，展开器只留下了调用者帧；② 分配走了批量接口或线程本地缓存，落在另一个符号（甚至库内部函数名）上；③ 采样区间太短，从未覆盖到那一次分配——短生命周期进程最容易这样（13.2.6）。

最小一步核验是回到产物：在 `.s` 或 LLVM IR 里找这条路径上是否存在分配调用（13.8.1 的三层核对），再确认采样窗口覆盖的阶段。产物里有调用而图里没有符号，说明是采集与展开问题；产物里确实没有调用，才有资格谈「没有分配」。

:::

### 13.2.7 最低归档要求

::: def 定义 13.2.4 · 采样报告的最低归档要求 {#def-13.2.4}

一份可以长期使用的采样报告，必须能同时定位到六样东西：① 对应的可执行映像或其可核验指纹；② 对应源码指纹；③ 构建 profile 与 feature 集合；④ 目标三元组和编译器版本；⑤ 采样命令、区间与间隔；⑥ 原始报告而不只是截图。缺任何一项，图只能作临时线索，不能作长期回归基线（第 1 章[@def-1.8.1] 的证据链在此的具体化）。

:::

六项里最容易被省掉的是第五项。「间隔 1ms、请求 2 秒」这类参数决定分母能怎么读：本轮 sample 的报告根计数就小于「2 秒除以 1ms」的理想算式（13.7.1 会展开这条），没有命令与区间，读者只能靠猜。第二项与第一项一起决定[@def-13.2.1] 的翻译链能不能重建；没有它们，一年后这张图连「当时跑的是哪份代码」都回答不了。

::: method 判定流程 · 这张图能不能当基线

**能当基线**：[@def-13.2.4] 六项齐全，原始报告可打开，权重定义写在图旁（13.4.2），同一构建能重跑（[@def-1.8.2] 的实验重跑）。
**只能当线索**：只有截图或只有 demangle 后的文字；没有映像与源码指纹；不知道采样区间；分母换了对象却没换图题。
**要立刻停手**：报告对应的是旧二进制（源码指纹变了）；工具报告了丢失或不支持，而表格里照填一个数（[@def-13.2.3]）。

### 13.2.8 小结与常见错误

**小结。**① 一条样本是位置观察，字段由工具与配置决定，没采到的不能从外观补（[@def-13.2.1]）；② 根与叶子是同一观察的两层表示，inclusive 不能跨层相加，本轮 1082 加 616 正好等于根 1698（[@def-13.2.2]、[@ex-13.2.1]）；③ 修饰名可读不代表语义稳定，demangle 后的文字不是 ABI（13.2.3）；④ 布局观测与协议承诺是两件事，16／8 不授权你把内存写盘（[@def-13.2.3]、[@ex-13.2.2]）；⑤ 符号缺席有至少四种解释，先查产物再谈不存在（[@think-13.2.1]）；⑥ 六项归档要求决定这张图是基线还是线索（[@def-13.2.4]）。下一节 [13.3 perf 与 PMU：先读事件契约](#sec-cpp-rust.4.13.3) 把「分母」换成硬件事件，那里缺的东西比这里更多。

E-a **把各层 inclusive 相加。**父已含子，同一观察被数两遍（[@def-13.2.2]）；先与根对照总数。

## 13.3 perf与PMU：先读事件契约 {#sec-cpp-rust.4.13.3}

本节回答一个问题：**硬件事件给出的数字，要满足哪些前提才允许进入结论？**[@def-13.1.1] 已经说过分母决定一个数能不能比；这一层更严：事件的定义、可用性、精确度和范围全都参与。本节讨论 Linux 工具的机制与迁移检查清单，它不承担本机的执行证据。

::: preview 先抓住一件事

事件名字不是机制说明。**肯定**一个 PMU 数字可以用，要能同时说出事件完整名称与修饰符、用户态／内核态过滤、线程或 CPU 范围、`time_enabled` 与 `time_running` 或运行比例、以及丢失与不支持的记录；**否定**「IPC 低所以要手工向量化」只需一句，理由放在 13.3.3。
:::

### 13.3.1 平台裁决：这一节里没有本机执行记录

::: def 定义 13.3.1 · 事件契约 {#def-13.3.1}

一个 PMU 事件的**契约**由五件事共同决定：**事件完整名称与修饰符**（别名在不同主机上可能映射到不同原始编码）、**计数范围**（用户态／内核态过滤，以及线程、进程或 CPU 范围）、**可用槽位**（同时请求的事件数受硬件限制，超出会触发复用）、**精确度**（事件发生位置与记录位置之间的偏移，即 13.3.5 的 skid）、**采集状态**（丢失记录、不支持、未运行）。[@def-13.3.1] 的意思是：脱离这五项的一段输出，没有唯一解释。

:::

本节讨论 Linux 工具的机制与迁移检查清单。**本轮没有在 Linux 上执行任何命令**，以下命令是有明确适用前提的复现设计，不是本机执行记录。

```bash
# 仅用于具备权限与相应事件支持的Linux主机；本轮未执行。
perf stat -e cycles,instructions -- ./workload
perf record -F 99 --call-graph dwarf -- ./workload
perf report --stdio
```

`perf stat` 的计数与 `perf record` 的抽样需要分别解释：前者汇总某段范围内的事件计数，后者在触发条件满足时记录位置与可能的调用链。同样的事件名称也不能抹平 CPU 型号和内核支持差异（[@def-13.3.1]）。这两句合起来是一条使用纪律：**先说清这段输出属于哪个统计量，再谈它像什么机制**——与第 1 章[@def-1.1.3] 要求先固定估计对象是同一件事。

### 13.3.2 cycles 不等于墙钟计时器 tick

核心运行周期、参考周期与系统计时器是三个不同概念。频率变化会影响它们之间的关系，等待状态也会影响事件是否增长。

本章的 `Instant` 读数只用于墙钟间隔（第 1 章[@def-1.2.1]）。我们没有把它转换成核心 cycles，也没有用处理器宣传频率乘纳秒生成「测得周期数」。这种乘法至多是带强假设的估计：它假设线程在整个区间连续运行、频率恒为宣传值、且计时器与计数器同源，三项在本轮都没有证据。它不是 PMU 观测。因此 13.5 与 13.6 的表里没有任何 cycle 列——**本节没有采集**核心周期。

### 13.3.3 IPC 首先是同一范围内的比值

指令数除以周期数常被称为 IPC（每周期执行指令数）。但分子分母应覆盖同一任务、同一区间、同一权限范围：若一个包含内核态、另一个仅用户态，解释会失真；若两者在不同阶段轮流运行（13.3.4 的复用就会造成这种轮流），直接相除也可能误导。

IPC 高不等于业务快。程序可能执行了大量无用但易并行的指令。IPC 低也不自动意味着需要手工向量化——依赖链、访存、分支和调度都可能相关。这句话与第 1 章[@ex-1.4.2] 是同一个结构：两个量相除得到的比值，不因为它们都叫「每单位」就获得因果含义。

### 13.3.4 硬件计数器槽位是有限资源

同时请求过多事件，可能触发复用。`perf_event_open` 提供 `time_enabled` 与 `time_running` 来描述这种情况：计数器只在部分时间实际运行时，可据此缩放估计总数。概念上的缩放为：

```text
估计总数 = 实际计数 × time_enabled / time_running
```

::: def 定义 13.3.2 · 计数器复用与缩放估计 {#def-13.3.2}

**复用**（multiplexing）指事件多于可用硬件槽位时，采集器让不同事件在不同时段轮流占据槽位。`time_enabled` 是该计数器被使能的时间，`time_running` 是它真正在跑的时间，两者之比给出一个缩放因子。**缩放估计**把「只在部分时间运行」的计数外推到全区间，它依赖被观测区间具有足够代表性：若工作负载分阶段突变，轮到某事件的时段恰好偏向某一阶段，缩放就会系统性地偏离真值。

:::

按[@def-13.3.2]，缩放不是凭空恢复遗漏阶段的真实事件序列。若工作负载分阶段突变，轮转到某事件的时段可能偏向某一阶段；复用比例低时，漂亮的小数位并不会提高可信度。这跟[@def-1.6.2] 的 bootstrap 前提是同构的：把「部分时间的观察」当成「整体可交换的重复」，就必须把这条前提写进结论。

### 13.3.5 事件组不是让硬件拥有无限槽位

事件组可帮助协调相关事件的调度与读取，但它不能突破实际硬件资源限制。无法同时调度时，应检查失败、未支持或未计数状态，不要把这些状态当成零事件。

::: def 定义 13.3.3 · 零、不支持、未运行是三种状态 {#def-13.3.3}

**零是一个数据值**（事件在采集期间确实没有发生）；**「不支持」是能力信息**（该平台或该权限下无法计数此事件）；**「未运行」是采集状态**（事件被请求但没获得槽位，或进程未覆盖到相关区间）。三者在数据结构里必须区分：把它们压成同一个 0，下游任何求和、比值与门禁都会在错误对象上计算（对照第 1 章[@def-1.5.1]：分母与对象错位时，数字越精确越危险）。

:::

::: ex 例 13.3.1 · 三个都显示 0，含义相同吗 {#ex-13.3.1}

某次 `perf stat` 的三行输出都显示 0：第 1 行 `cache-misses`（事件受支持，但工作集确实很小）、第 2 行某个厂商原始事件编码（当前内核不认得这个名字）、第 3 行 `instructions`（同时请求的事件多于槽位，它整段都没被调度）。三行能合并写成「本轮 miss 与指令数为零」吗？分别应该怎么记？

::: sol 解答

不能合并。第 1 行的 0 是数据值，可以进结论，但要连同工作集规模一起写；第 2 行是能力信息，应记为「不支持」，并保留工具的错误输出原文，它既不是零也不是「没有 miss」；第 3 行是采集状态，应记为「未运行」，并同时记录 `time_enabled`／`time_running`，说明这条线根本没被观测覆盖（[@def-13.3.3]）。

合并写法的破坏力有三层：读者会把「无法测量」读成「测得为零」；任何以这些数为分母的比值（IPC、miss 率）会算出无意义的值；日后重跑时，第 2、3 行的状态可能变化，新旧表就对不上（[@def-13.2.4] 的归档要求正是为这类漂移准备的）。本章的处理方式更保守：既然没有硬件采集记录，性能表里就一列 miss 率或 IPC 都不加（13.3.7）。

:::

:::

### 13.3.6 skid 限制了源码级归因

::: def 定义 13.3.4 · skid 与精确级别 {#def-13.3.4}

**skid** 指事件实际发生的位置与采集器记录到的指令位置之间的偏移；乱序执行、流水线深度与中断处理都会造成它。`precise_ip` 表达对偏移的要求（越大越精确），但硬件支持有边界，某些事件根本没有精确形式。[@def-13.3.4] 的后果是：**事件样本落在哪一行，不能直接读成那一行引发了该事件。**

:::

因此，某条加载后面的算术行出现事件样本，不一定由算术引发 miss。也不能看到某行很宽，就给那一行加 prefetch。应先确认事件支持、精确级别和生成代码（13.8 的三层产物核对在此可用）。

::: ex 例 13.3.2 · 那行「很宽」的加载要不要加 prefetch {#ex-13.3.2}

一份 Linux 报告里，某次链表遍历的 `L2 miss` 样本大多记在循环体中「取下一个指针」之后的算术行上。有人提议：「就在这行加 prefetch，能省一半 miss。」按[@def-13.3.4] 与[@def-13.3.1]，列出这句话依赖但尚未确认的前提，并给出两个更该先做的动作。

::: sol 解答

未确认的前提至少有四条：① `L2 miss` 在本机的完整事件名与修饰符，以及它到底指哪一层、哪类访问（13.3.7）；② 该事件是否支持所需的 `precise_ip` 级别——不支持时，记录位置本身就带偏移（[@def-13.3.4]）；③ 用户态／内核态过滤与线程范围，与样本是否来自被测线程；④ 该行在生成代码里对应的实际指令序列，因为内联会让一个源码行覆盖多个地址区间（[@def-13.2.1]）。

两个更该先做的动作：先看产物，确认这行源码对应的是指针加载还是别的操作（13.8.1）；再看事件可用性与精确级别的实测，确认「记在哪一行」这件事有多少可信度。两个动作都可能直接推翻原提议——链表依赖链本身就是下一轮加载无法提前完成的常见原因，而这一点不需要 miss 计数也能从产物读出来。**本节没有采集**任何 PMU 数据，这个例子只用于说明推理形状。

:::

:::

### 13.3.7 事件名字不保证微架构含义一致

所谓 cache miss 可能指不同层级、不同访问类别或不同状态。原始事件编码更依赖型号；通用别名也需要查当前主机的实际映射与文档。跨机器报告时至少保留：

- CPU 型号与微码／系统信息中实际可得的部分。
- 事件完整名称与修饰符。
- 用户态／内核态过滤范围。
- 线程、进程或 CPU 范围。
- `time_enabled`／`time_running` 或工具给出的运行比例。
- 丢失记录、权限限制和错误输出。

这六条与[@def-13.3.1] 是同一张契约的两种写法：前者按「一个事件」列，后者按「一份报告」列。本章没有这些硬件采集记录，因此 13.5 与 13.6 的性能表中没有任何「miss 率」或「IPC」列——不是忘了加，而是没有观测对象可以填进去（第 1 章[@def-1.7.3] 的纪律：探索性材料不冒充确认性结论）。

### 13.3.8 事件数如何进入优化决策

假设减少分配后墙钟下降，同时分配调用样本下降，这构成一致的线索。若还观察到指令数下降，机制解释会更完整。但不应反向宣称「一切加速都来自指令数」。

需要比较业务工作量和输出，需要排除缓存边界、调度与输入变化。PMU 给出额外观测维度，不给出自动因果证明——这句是[@def-13.1.3] 的可反驳要求在硬件事件层的重述：多个指标同时变化只支持「相容」，支持「因为」要靠受控修改与独立重跑（[@def-13.1.2] 的第五层）。

::: think 思考 · 三个指标同向变化，能写成因果吗 {#think-13.3.1}

某次改动后：墙钟下降、`cache-misses` 下降、分配调用样本下降。有人写下「加速来自 miss 减少」。按[@def-13.3.1] 与[@def-13.1.3]，指出这条陈述缺了什么，并设计一个能否定它的实验。

::: sol 解答

缺的是把三个同向变化区分开的干预。三个数各自属于不同分母与不同契约（[@def-13.1.1]、[@def-13.3.1]）：墙钟里含调度与等待，miss 计数含层级定义与复用状态，样本数含采样区间与展开质量。同向变化只与「miss 减少导致变快」相容，也与「少分配本身少了工作」「输入局部性变了」「这段时间机器没那么热」相容（第 1 章[@def-1.2.3] 的热漂移）。

能否定它的实验：保持分配次数与代码形状不变，只改变数据局部性（例如交换存储布局或打乱访问顺序，第 2 章那一类受控布局改动），观察墙钟与 miss 是否仍按同一关系移动；或者反过来固定局部性、只减少分配。若 miss 变了而墙钟不动，「加速来自 miss 减少」当场被否定。这一项是待验证项——本轮没有执行。
:::

:::

### 13.3.9 小结与常见错误

**小结。**① 一个 PMU 数字由事件契约五项共同决定，脱离它们没有唯一解释（[@def-13.3.1]）；② cycles 不是墙钟 tick，`Instant` 读数不能乘频率换算成周期（13.3.2）；③ IPC 首先是同范围比值，高不等于业务快（13.3.3）；④ 槽位有限，复用后的缩放是估计，阶段突变时尤其危险（[@def-13.3.2]）；⑤ 零、不支持、未运行是三种状态，压成一个 0 会污染所有下游比值（[@def-13.3.3]、[@ex-13.3.1]）；⑥ skid 与事件命名限制源码级归因（[@def-13.3.4]、[@ex-13.3.2]）。本节全部内容是迁移检查清单：**本节没有采集任何硬件事件**。下一节 [13.4 Flamegraph、off-CPU 与异步链路](#sec-cpp-rust.4.13.4) 回到本轮真正采到的东西——两份栈快照折叠出的权重。

::: errata 常见错误清单（13.3 节）

E-a **把复现设计当执行记录。**本轮没在 Linux 上跑过任何命令（13.3.1）；先声明平台裁决。

E-b **用宣传频率把纳秒换算成周期。**假设了连续运行与恒定频率（13.3.2）；先分清三种周期。

E-c **拿 IPC 高低直接排优化动作。**分子分母范围不一致就失真（13.3.3）；先对齐区间与权限。

E-d **忽略复用比例，把缩放值当实测。**阶段突变时缩放偏向某阶段（[@def-13.3.2]）；先记录运行比例。

E-e **把不支持或未运行填成零。**三种状态语义不同（[@def-13.3.3]、[@ex-13.3.1]）；先保存工具错误输出。

E-f **按样本记录那一行加 prefetch。**skid 与内联都会移动记录位置（[@def-13.3.4]、[@ex-13.3.2]）；先看产物与精确级别。

E-g **三个指标同向就写因果。**同向只支持相容（[@think-13.3.1]）；先设计能否定它的干预。

## 13.4 Flamegraph、off-CPU与异步链路 {#sec-cpp-rust.4.13.4}

本节回答一个问题：**一张宽度图能替「等待」说到哪一步？**13.2 界定了单条样本的层级与可加性，13.3 说明了事件契约；这一节处理把这些样本聚合成图之后新增的失真——权重、归一化、off-CPU 缺口与异步任务栈的因果断裂。

::: preview 先抓住一件事

flamegraph 是聚合视图，不是时间轴。**肯定**一句图上结论，要写出权重对象与范围，例如「主线程栈快照，独立采样运行，1ms 请求间隔」；**否定**「这块宽框就是用户等待的根因」，只需一句：CPU 图里没有等待区间，异步任务栈里没有创建请求的入口帧。
:::

### 13.4.1 flamegraph 是一种聚合视图

::: def 定义 13.4.1 · 折叠图的宽度与横轴 {#def-13.4.1}

把调用栈与权重折叠后画成横向宽度图，就是经典 **flamegraph**：父框覆盖经过该调用路径的权重，子框展示其中更深一层的分布；同名函数出现在不同父路径下，通常仍是不同框。**横轴不是时间轴**——相邻框不表示它们先后执行；**颜色通常也不是温度计**——没有图例时，不应把红色解释成更慢或更高温。

:::

按[@def-13.4.1]，一张图本身只承诺两件事：某个路径的权重份额，以及路径之间的层级关系。它不承诺顺序、不承诺时长，也不承诺热度。[@def-13.2.2] 的层级可加性在这里以另一种形式出现：父框宽度已经包含子框，横向「逐层求和」在图上看起来自然，语义上却是重复统计。

### 13.4.2 权重必须写在图旁

权重可以是 CPU 样本数，也可以是线程快照数、分配字节数或阻塞纳秒数。同样的画法，可以表达完全不同的对象。[@def-13.1.1] 说的就是「换观测对象要换图题」。

标题应包含权重和范围，例如「主线程栈快照，独立采样运行， 1ms 请求间隔」。不能只写「性能火焰图」，让读者默认它是 CPU 时间。本章的两份折叠文件都按这条规则命名权重：叶子 exclusive 观察数（13.4.3）。

### 13.4.3 本轮真实折叠数据

`tools/collapse_sample.py` 把本轮 sample 树的 inclusive 计数转换为叶子 exclusive 权重。转换器只支持本轮报告形状，它不声称能解析所有版本的 Apple 报告；原始 sample 文本始终是权威证据。

| 独立运行 | 根观察数 | 叶子路径数 | 主要叶子 |
|:--|--:|--:|:--|
| CPU | 1698 | 2 | mix 1082、compute 616 |
| waiting | 1648 | 5 | `__semwait_signal` 1443、mix 181 |

折叠文件是 `cpu.folded` 与 `wait.folded`，它们可作为后续绘图输入。本轮没有运行 Linux 的 stackcollapse-perf，也没有把文件改名为 `perf.data`。

::: ex 例 13.4.1 · 读这两行折叠数据 {#ex-13.4.1}

按上表回答四件事：

1. CPU 行为什么只有 2 个叶子路径，waiting 行却有 5 个？
2. 1443／1648 与 1082／1698 这两个份额能直接相减吗？
3. 把这两行画成两张各归一化到 100% 的图，丢失了什么？
4. 这两行的权重能不能写成「CPU 时间占比」？

::: sol 解答

1. 叶子路径数是被观察到的互斥叶子个数，不是采集器参数。CPU 运行的所有观察集中在 `compute` 与 `mix` 两个叶子（1082 + 616 = 1698，正好等于根，见[@def-13.2.2]）；waiting 运行里睡眠栈、`mix`、`compute` 等分布在 5 条叶子路径上，总数仍应与 1648 一致。
2. 不能直接相减——它们属于两份不同运行中的不同分支：一个是 CPU 夹具，一个是加了一段主动等待的夹具（13.5）。两个分母来自两次独立进程启动，不存在同一次执行里的对应关系（[@def-13.1.1] 的观测对象）。
3. 丢失总量差异：1698 与 1648 这两个根观察数不再可见，读者会把「份额增加」读成「绝对成本增加」（13.4.4）。
4. 不能。权重是线程栈快照的观察条数，本轮没有采集核心周期或运行时长；`__semwait_signal` 恰恰是睡眠路径，把它写成「CPU 时间」会得出「睡眠消耗了 CPU」这种荒谬结论（[@def-13.4.1]）。

:::

:::

### 13.4.4 归一化会隐藏总量差异

两张各自归一化到 100% 的图，总宽总是一样。一个版本即使整体更快，图中某个函数的比例仍可能变大——例如其他部分减少后，剩下部分自然占更高比例。

比较前应同时展示总运行量与总权重；差分图也要说明是否做了归一化。否则读者会把「份额增加」误解成「绝对成本增加」。这条与第 1 章[@ex-1.4.2] 同源：比例类统计量一旦脱离总量与基线，就会造出看似精确的倍数。

::: ex 例 13.4.2 · 「优化后这个函数占比涨了」 {#ex-13.4.2}

某团队把 A 阶段的工作删掉后重跑，flamegraph 上 B 函数从 35% 涨到 58%，于是写「B 变慢了，是新的瓶颈」。按 13.4.4 与[@def-13.4.1]，给出三种都能解释这组数字的情况，并说出你需要的最小补充数据。

::: sol 解答

三种情况：① 整体变快，B 的绝对权重不变，只因为分母缩小而占比上升；② 整体变快但 B 真的略微变慢（寄存器分配（编译器决定哪些值留在 CPU 最快的那一小批格子里）或缓存状态变化），涨幅小于表面读法；③ 整体变慢，B 的绝对权重上升更多。归一化图对这三者给出形状相似的结果，这就是[@def-13.4.1] 的限制。

最小补充数据是**两张图的总权重与总运行量**（原始观察条数与批次墙钟），并按同一互斥分类给出绝对量（[@def-13.2.2]）。有了总量，才能把「占比 35% → 58%」换成「观察数 x → y，同期批次墙钟 m → n」。本轮的 1698 与 1648 就是这一类总量信息，缺的是与它配对的墙钟（那属于另一份证据，见 13.5.6）。

:::

:::

### 13.4.5 CPU 图不能自动补出等待区间

::: def 定义 13.4.2 · off-CPU 分析与线程栈快照 {#def-13.4.2}

**off-CPU 分析**要回答「线程何时停止运行、何时重新运行」，通常需要调度事件与栈信息配合，重建部分运行区间。**线程栈快照**（本轮 macOS `sample` 的形状）只是在若干时刻记录线程当时位于哪条栈上：等待线程可以反复显示同一睡眠栈。两者都描述等待，统计量却不同——前者是区间累计时长，后者是观察条数。

:::

只在 CPU 运行时采样，得不到完整 off-CPU 分布。常见系统工具可用调度事件与栈信息重建部分区间，但其权限、丢失记录和关联规则必须记录（[@def-13.3.1] 的采集状态在这里同样适用）。

按[@def-13.4.2]，本章可以据此说「采样期间经常看到睡眠路径」，不能据此说「线程总计阻塞了精确的某个纳秒数」。13.4.3 的 `__semwait_signal` 1443 条属于前一种说法；后一种需要调度事件时间线，本轮没有采集。

### 13.4.6 异步任务栈不是业务因果栈

Future 挂起后，原来的同步调用栈可能已经返回。稍后在另一个 worker 恢复时，采到的是当时的 poll 链；创建请求的入口可能根本不在栈上。所以只看线程栈难以知道某个等待属于哪个请求——需要 span、任务 id 或消息关联。

关联数据本身也要限制大小与生命周期：不能为了补足因果关系，永久保留每个请求的全部上下文。这句话与[@def-1.3.1] 的观察集合是一对张力——观察越完整，夹具越贵；关联标识的设计目标，是在能定位责任的前提下取最小集合（13.6.4 的逐项事件形状就是这种取舍的极端例证）。

### 13.4.7 主动等待与被迫等待是六种不同状态

`thread::sleep` 是实验主动要求的等待。它不代表磁盘、网络、锁或 CPU 资源竞争；出现 nanosleep 不能证明服务瓶颈是操作系统调度器。真实请求中，[@def-13.1.2] 第二层的执行分解至少应区分六种状态：

- 主动退避或定时等待。
- 等待输入到达。
- 等待容量或准入。
- 等待锁或条件变量。
- 已就绪但尚未获得 CPU。
- 资源就绪但异步任务尚未恢复。

这些状态可能最终都表现为「请求没有完成」，优化手段却完全不同：第一种要改协议，第二种要改上游，第三种要改容量，第四种要改临界区，第五种要改调度与并发度，第六种要执行器与 poll 预算。把它们混成一个「等待」，等于把六种修法压成一个随机猜测（[@think-13.1.1]）。

### 13.4.8 丢失关联比丢失美观更严重

::: def 定义 13.4.3 · 业务关联标识 {#def-13.4.3}

**业务关联标识**是让一条观察能被归回某个请求的最小信息（请求 id、span、任务 id 或消息序号）。它有三条设计约束：跨线程可识别（同一请求由不同线程推进时仍能拼回）、生命周期可区分（同一个 id 被复用时必须能分辨是哪一次）、规模有界（不能为补因果而永久保留全部上下文）。采集顺序不等于因果顺序：不同线程写日志的到达顺序可能交换。

:::

同一个任务 id 复用时，必须区分不同生命周期；跨线程传递事件时，不能假设采集顺序就是因果顺序（[@def-13.4.3]）。本实验没有实现分布式追踪系统：`Event` 里的 `id` 只是本批操作编号，它不跨批唯一，也不适合直接当全局 trace id（[@def-13.2.3] 的布局观测同样提醒：一次 `size_of` 不构成协议）。

### 13.4.9 正确的图后行动

看到宽框之后，至少提出两个竞争性解释，例如「执行更多次」与「每次执行更慢」。前者需要调用次数，后者需要单次或批次工作量才能区分；单纯展开更深一层，有时只会得到更详细的相关性（[@def-13.1.2] 的第三层不能自动跳到第四层）。

下一步应设计能否定其中一个解释的实验。本章的逐项观测实验就是这种受控修改（13.6）：它保持业务输入与输出相同，只改变观测方式，因此「更多次／更慢」这两种解释在设计阶段就被排除了一个维度（[@def-13.1.3]）。

::: think 思考 · 「展开更深一层」为什么常常白做 {#think-13.4.1}

一张图里 `handle` 框很宽，你把它展开成 `handle → decode → parse → tokenize`，四层的 inclusive 宽度完全相同。这次展开新增了什么信息？

::: sol 解答

只新增了一条否定：这条链上四层之间没有可归因的分支差异（同宽意味着观察都经过全部四层，[@def-13.2.2]）。真正能区分责任的，是那些叶子宽度不同的地方——也就是[@def-13.4.1] 说的子框分布；如果展开后各层同宽，结论只是「热点在这条链的末端」，与展开前的信息量几乎相同。

要继续前进，得换问题而不是换图：把「在哪里被观察到」拆成「被执行了多少次」与「每次多少工作」，分别需要调用次数与单次工作量（13.4.9）。这两样都不在栈图里，需要另一条采集路径——阶段时间与相关标识（[@def-13.1.2] 第三层的右盒、[@def-13.4.3]）。
:::

:::

::: method 判定流程 · 看到宽框之后的三步

**① 写权重与范围**：这是观察条数还是时长？哪条线程、哪个区间、什么间隔（[@def-13.4.1]、13.4.2）。
**② 造两个竞争解释**：更多次／每次更慢，或运行／等待（[@def-13.4.2]），并写出各自需要的数据。
**③ 设计能否定其一的实验**：保持业务输入与输出相同，只改一个维度（[@def-13.1.3]）；缺数据就写「本轮没有采集」，不要靠展开更深一层蒙过去（[@think-13.4.1]）。

:::

### 13.4.10 小结与常见错误

**小结。**① 图的横轴不是时间、颜色不是温度计，宽度只承诺权重份额与层级（[@def-13.4.1]）；② 权重必须写在图旁，同样的画法能表达不同对象（13.4.2）；③ 本轮折叠数据是 1698／2 与 1648／5 两行，两份不同运行的份额不能相减（[@ex-13.4.1]）；④ 归一化会隐藏总量差异，比较前要给出总权重与总运行量（[@ex-13.4.2]）；⑤ 栈快照不等于 off-CPU 时长，「经常看到睡眠路径」与「精确阻塞了多少纳秒」是两句话（[@def-13.4.2]）；⑥ 异步任务栈缺创建入口，补因果要关联标识且它有三条约束（[@def-13.4.3]、13.4.6）。下一节 [13.5 Benchmark 一：计算与等待的两份画像](#sec-cpp-rust.4.13.5) 把这套读法用在真实数据上。

::: errata 常见错误清单（13.4 节）

E-a **把横轴当时间轴。**相邻框不表示先后（[@def-13.4.1]）；需要顺序时改用时间线视图。

## 13.5 Benchmark一：计算与等待的两份画像 {#sec-cpp-rust.4.13.5}

本节回答一个问题：**同样的计算再加一段主动等待，计时表和栈表各会长什么样，两张表能互相换算吗？**这是本章第一份真实实验。它把[@def-13.1.2] 的第三层两条路径（阶段计时、栈快照）在同一版源码上各跑一遍，然后用 13.1 到 13.4 建立的读法逐个检验结论。

::: preview 先抓住一件事

这是一个「计算相同、额外等待不同」的诊断夹具，不是优化比赛。**肯定**它的用途，要能说清 checksum 相同、计时单位是整批 ms、采样来自另一次进程启动；**否定**一种常见误用只要一句：40 ms 是 `thread::sleep` 的申请下限语义，不是精确唤醒承诺，wait 均值大于 cpu 加 40 ms 也不意味着算法多算了四毫秒。
:::

### 13.5.1 问题与固定工作量

入口是 `src/bin/cpu_wait.rs`。每批执行 1000000 次整数递推；CPU 分支只执行递推，wait 分支执行同样递推，再申请 40 ms 线程睡眠。两分支的 checksum 必须相等，因此这是「计算相同、额外等待不同」的诊断夹具：不是两个业务等价实现的优化比赛，也不是用于测量单个 nanosleep 调用固定开销的程序（这条限制在 13.5.8 会反过来约束能说什么结论）。

::: def 定义 13.5.1 · 同 checksum 诊断夹具 {#def-13.5.1}

**同 checksum 诊断夹具**指：参与比较的分支共享完全相同的业务工作核与输出（校验和必须相等），只在被研究的那一个因素上不同——本节是「一段主动等待」。它的作用是把[@def-1.6.1] 的「等价工作比较」收窄成单因素实验：既然计算量与输出被固定，观测到的差异就只能来自那个因素、夹具扰动或随机波动，不能来自「多做了一件事」。

:::

按[@def-13.5.1]，本节可以谈「加了等待之后批次墙钟怎么变、栈形状怎么变」，不能谈「等待本身值多少纳秒」——后者需要另一种夹具（对单次 `sleep` 调用直接计时，本包没有实现）。

### 13.5.2 业务核的完整实现

完整文件见 `src/lib.rs`。以下是该实验真正调用的两个完整函数。无符号溢出使用 wrapping 语义，没有执行 UB。

```rust
#[inline(never)]
pub fn mix(value: u64) -> u64 {
    std::hint::black_box(value)
        .rotate_left(9)
        .wrapping_mul(0x9e37_79b9_7f4a_7c15)
        .wrapping_add(17)
}

pub fn compute(count: u64) -> u64 {
    let mut value = 7;
    for _ in 0..count {
        value = mix(value);
    }
    value
}
```

`noinline` 让调用路径容易核验，它也使函数调用成本进入工作负载；`black_box` 限制编译器把整个结果预先折叠，它不是硬件内存屏障（[@def-1.1.2]）。这两句是[@def-13.5.1] 里「夹具」那部分的成本来源：本节比较的两条分支共享同一份成本，差值里因此不含它。

### 13.5.3 可执行入口完整源码

```rust
use evidence_lab::{compute, report, warm};
use std::hint::black_box;
use std::time::{Duration, Instant};

const STEPS: u64 = 1_000_000;

fn run(wait: bool) -> u64 {
    let value = compute(STEPS);
    if wait {
        std::thread::sleep(Duration::from_millis(40));
    }
    black_box(value)
}

fn main() {
    let args: Vec<_> = std::env::args().collect();
    if args.get(1).is_some_and(|s| s == "--profile") {
        let wait = args.get(2).is_some_and(|s| s == "wait");
        let start = Instant::now();
        let mut checksum = 0;
        while start.elapsed() < Duration::from_secs(5) {
            checksum ^= run(wait);
        }
        println!("profile,wait={wait},checksum={checksum}");
        return;
    }
    let expected = compute(STEPS);
    warm(|| {
        assert_eq!(run(false), expected);
    });
    warm(|| {
        assert_eq!(run(true), expected);
    });
    let mut all = [Vec::new(), Vec::new()];
    println!("unit=batch_ms;steps={STEPS};requested_sleep_ms=40;checksum={expected}");
    for round in 0..21 {
        for offset in 0..2 {
            let index = (round + offset) % 2;
            let start = Instant::now();
            let value = run(index == 1);
            let ms = start.elapsed().as_secs_f64() * 1000.0;
            assert_eq!(value, expected);
            all[index].push(ms);
            println!(
                "raw,{},round={round},value={ms:.6},checksum={value}",
                ["cpu", "wait"][index]
            );
        }
    }
    for (case, samples) in ["cpu", "wait"].iter().zip(all.iter()) {
        report(case, samples);
    }
}
```

公共函数 `report` 与 `warm` 在同一实验包中完整提供。计时与统计口径按第 1 章[@def-1.2.2] 的批次模型：一条观察是一整个批次，21 批，轮转顺序（`for offset in 0..2` 让两条分支轮流先跑，对应[@def-1.4.1] 的位置记录思想）。以上入口没有依赖隐藏的外部服务或数据文件。

### 13.5.4 正式计时边界

| 操作 | 计入批次墙钟 | 理由 |
|:--|:--|:--|
| 创建进程与解析参数 | 否 | 不测冷启动 |
| 参考checksum | 否 | 校验基准不是业务工作 |
| 1000000次递推 | 是 | 两分支共有工作 |
| wait分支申请睡眠 | 是 | 被诊断差异 |
| checksum比较 | 否 | 在结束时间戳后执行 |
| 打印原始行 | 否 | 不将终端输出计入本批 |

计时外的打印仍可能影响下一批调度与缓存。「不计入本批」不等于对整个进程无扰动——这句是[@def-1.1.3] 观察集合与计时集合的分界提醒。本轮没有把 stdout 重定向到慢网络文件系统，原始输出写入本地证据目录。

### 13.5.7 观察到的栈

CPU运行中，根1698条观察都在compute路径上。
其中1082条叶子落在mix，616条落在compute。

它不支持把1446/1648直接替换成正式计时的等待比例。

### 13.5.8 不强求理想比例

从正式均值直觉估算，等待分支应大部分时间睡眠。
实际sample中的compute份额与该粗略估算并不精确相同。

没有记录每次采样的完整调度上下文。
不能判断差别来自间隔偏差、系统状态还是其他采集影响。
不能用调整报告计数的方法让它匹配预期。

::: think 思考 · 21 批轮转顺序，能不能改成先跑完 CPU 再跑 wait {#think-13.5.1}

## 13.6 Benchmark二：逐项打点与批量聚合 {#sec-cpp-rust.4.13.6}

本节回答一个问题：**把观测从「每批一次」改成「每步一次」，代价有多大，这笔代价能不能事后减掉？**13.5 比的是「算」与「等」；这一节固定同一段递推，只换观测方式，看三份墙钟各自能支持哪句话。

::: preview 先抓住一件事

观测粒度会改变被测程序本身。**each 把聚合 step 均值从 2.472857 推到 32.832639 ns/step，按表内两均值相除约 13.3 倍；batch 只保住总数、丢掉分布**。因此「把观测成本减掉就还原无观测版」不成立：插桩改变寄存器（CPU 内部最快的那一小批存储格子）压力、内联与循环形状，差值不是可加项。
:::

### 13.6.1 三种模式，同一份业务

入口是 `src/bin/instrumentation.rs`。每批执行 200000 步相同递推，三种模式只改变观测方式，所有模式必须得到相同的业务 checksum。none 不记录逐项观测；batch 在批末提交总步数；each 对每步读时钟、构造事件并提交原子计数。

这是人为构造、实际执行的安全 Rust 性能回退，不是某家公司的事故叙述。它也没有靠数据竞争或悬空访问去换一个「更快的基线」。

::: def 定义 13.6.1 · 逐项打点与批量聚合 per-step instrumentation / batch aggregation {#def-13.6.1}

**逐项打点**（per-step instrumentation）指每次循环迭代都读一次时钟、构造一个事件并经屏障（[@def-1.1.2]）观察；**批量聚合**（batch aggregation）指只在批次结束时提交一次总数。两者共用同一段业务递推，只在观测粒度上不同，因此构成[@def-13.5.1] 意义上的同 checksum 诊断夹具：输出一致，差异只能来自观测方式。
:::

| 模式 | 总数 | 每步耗时 | 事件持久化 | 业务checksum |
|:--|:--|:--|:--|:--|
| none | 不记录 | 不记录 | 无 | 保留 |
| batch | 保留 | 丢失 | 无 | 保留 |
| each | 保留 | 构造并经屏障观察 | 无 | 保留 |

batch 并不提供与 each 同样的诊断信息。它低成本的前提是放弃逐项分布；业务若要求按请求定位异常，就要另选采样或聚合策略，并把选择写进[@def-13.2.3] 的归档说明。

### 13.6.2 观测核心

```rust
use std::hint::black_box;
use std::sync::atomic::{AtomicU64, Ordering};
use std::time::Instant;

#[derive(Clone, Copy, Debug)]
pub struct Event {
    pub id: u64,
    pub elapsed_ns: u64,
}

#[derive(Clone, Copy, Debug)]
pub enum Mode {
    None,
    Batch,
    Each,
}

pub fn observed(count: u64, mode: Mode) -> (u64, u64) {
    let counter = AtomicU64::new(0);
    let mut value = 7;
    for id in 0..count {
        let clock = matches!(mode, Mode::Each).then(Instant::now);
        value = evidence_lab::mix(value);
        if let Some(clock) = clock {
            black_box(Event {
                id,
                elapsed_ns: clock.elapsed().as_nanos() as u64,
            });
            counter.fetch_add(1, Ordering::Relaxed);
        }
    }
    if matches!(mode, Mode::Batch) {
        counter.fetch_add(count, Ordering::Relaxed);
    }
    (value, counter.load(Ordering::Relaxed))
}
```

上段为可独立使用的同义核心，调用库的 `mix`。实际库内写作 `value = mix(value)`，避免自引用 crate 名。完整编译测试的唯一源文件是 `src/lib.rs`；正文摘录不维护第二份实验实现。

::: def 定义 13.6.2 · 聚合 step 单位 aggregate step unit {#def-13.6.2}

本节表格的单位是 **ns/聚合 step**：一批 200000 步的总墙钟除以 200000。它是[@def-1.2.2] 批次墙钟的一种归一化，回答「平均每步摊到多少时间」；它不是单步延迟的分位数，也不是一次事件的独立测量。
:::

按[@def-13.6.2]，2.47 与 32.83 描述的都是「一整批除以步数」的聚合成本。读到六位小数时，先记住分子是一批的总时间。

::: def 定义 13.6.3 · 局部原子计数 local atomic counter {#def-13.6.3}

**局部原子计数**指原子对象定义在本次函数调用内部、没有其他线程能访问它。它只说明计数本身是原子操作，不测共享缓存线的竞争。`Ordering::Relaxed` 只声明不借助这个计数发布其他内存，并不取消计数的原子性；反过来，优化器也可能利用「对象是局部的」这一上下文改变代码形状。
:::

所以不能把整段耗时命名为「单次共享原子加法耗时」。本节没有任何跨线程共享计数的观测。

### 13.6.3 可执行入口与计时边界

```rust
use evidence_lab::{Mode, compute, observed, report, warm};
use std::hint::black_box;
use std::time::Instant;

const STEPS: u64 = 200_000;
fn main() {
    let modes = [Mode::None, Mode::Batch, Mode::Each];
    let names = ["none", "batch", "each"];
    let expected = compute(STEPS);
    warm(|| {
        for mode in modes {
            black_box(observed(STEPS, mode));
        }
    });
    let mut all = [Vec::new(), Vec::new(), Vec::new()];
    println!("unit=ns_per_step;steps={STEPS};checksum={expected}");
    for round in 0..21 {
        for offset in 0..3 {
            let index = (round + offset) % 3;
            let start = Instant::now();
            let (value, count) = observed(STEPS, modes[index]);
            let ns = start.elapsed().as_secs_f64() * 1e9 / STEPS as f64;
            assert_eq!(value, expected);
            assert_eq!(count, if index == 0 { 0 } else { STEPS });
            all[index].push(ns);
            println!(
                "raw,{},round={round},value={ns:.6},checksum={value},count={count}",
                names[index]
            );
        }
    }
    for (case, samples) in names.iter().zip(all.iter()) {
        report(case, samples);
    }
    println!(
        "layout,Event,size={},align={}",
        std::mem::size_of::<evidence_lab::Event>(),
        std::mem::align_of::<evidence_lab::Event>()
    );
}
```

入口先算参考 checksum，再用 `warm` 预热三条路径；正式 21 轮，按 `(round + offset) % 3` 轮转起点，使每个模式在各位置都出现过。每轮断言 checksum 与计数：none 为 0，batch 与 each 为 200000。`report` 按本章统一的 21 条口径输出均值、N-1 标准差与批均值 p50/p99（[@def-13.7.3]）。

### 13.6.4 逐项事件的形状

each 每步构造一个 `Event { id, elapsed_ns }`，交给 `black_box` 之后立刻丢弃，没有容器保存这 200000 个事件。13.2 的布局表把 `Event` 记为 16 字节、对齐 8 字节（[@def-13.2.3]），那是本轮的布局观察，不是协议承诺。

这也是 13.4 所说「关联数据取最小集合」的极端一端：观测存在，保留为零。若需要真实的逐项分位数，必须另做存储与扰动设计，并承担相应的写盘成本；本节没有做这件事。

### 13.6.5 本轮实测

来源是 `instrumentation.txt`。单位为 ns/聚合 step，分母固定 200000；这些不是逐 step 延迟的分位数。

|:--|--:|--:|--:|--:|
| none | 2.472857 | 0.094581 | 2.448330 | 2.798125 |
| batch | 2.470040 | 0.079995 | 2.448545 | 2.685205 |
| each | 32.832639 | 0.608977 | 32.762500 | 34.306250 |

2. 不能。插桩自身改变了代码形状，这条减法需要额外的可加性假设——13.6.6 整节讲的就是这件事。本章只报告两套真实程序的总体差异。

::: think 思考 · 每步一个事件，差值就等于一次打点的成本吗 {#think-13.6.1}

each 每步恰好构造一个 `Event`，表格单位又是「每步」，于是有人写：30.359782 就是一次打点的成本。这个推理看起来单位已经对齐，它漏了哪一步？

::: sol 解答

### 13.6.6 为什么不能事后减一个常数

插入观测会改变寄存器压力、内联和循环优化机会，还可能改变运行持续时间与调度机会。因此「观测版减去空时钟循环」不一定恢复无观测版。

这种减法需要额外的可加性假设，对极轻量循环尤其危险。本章只报告两套真实程序的总体差异，不报告推算出来的「净打点成本」。

### 13.6.7 实际回归测试

`observation_does_not_change_business_result` 校验三模式输出，`batch_counter_loses_distribution_not_count` 校验批量计数总数。两个测试都不依赖固定纳秒阈值。

功能测试应当能在慢机器上通过；性能预算需要单独的环境和证据策略。把桌面均值硬编码进单元测试，会制造脆弱测试。

::: method 判定流程 · 观测粒度怎么选

**只要总量或吞吐**：选 batch。成本接近 none，但放弃逐项分布。
**要按请求定位异常**：选 each，或按 13.2 的记录设计另做采样；两条路都要把额外成本写进结论。
**要真实分布**：先设计存储与导出路径——本节 200000 个事件一个都没落盘。
**有人提议「先测 each 再减掉常数」**：停止。插桩改变代码形状，减法不成立（13.6.6）。
**要写进 CI**：只放正确性断言，纳秒阈值交给独立的性能门禁（[@def-1.7.2]）。

:::

### 13.6.8 小结与常见错误

**小结。**① 三种模式共用同一 checksum，差异只来自观测粒度（[@def-13.6.1]）；② 表里的单位是 ns/聚合 step（[@def-13.6.2]）；③ 局部原子计数不测共享竞争（[@def-13.6.3]）；④ 21 批实测中 each 约为 none 的 13.3 倍，但差值不能拆成单项成本（[@ex-13.6.1]）；⑤ batch 保总数、丢分布，粒度选择是业务问题。

::: errata 常见错误清单（13.6 节）

E-a **把 32.832639 当单次打点延迟。**它是每聚合 step 的成本，分子是一整批墙钟（[@def-13.6.2]）。

E-b **用 each 减 none 拆出「打点净成本」。**插桩改变代码形状，减法需要可加性假设（13.6.6）。

E-c **由 0.002817 的差宣称 batch 优化业务核。**差异小于批次波动，不能当收益（[@ex-13.6.1]）。

E-d **以为 batch 保留了逐项分布。**它只留总数，分布已丢（[@def-13.6.1]）。

E-e **把本节耗时写成共享原子加法成本。**计数对象是函数局部的，没有竞争（[@def-13.6.3]）。

E-f **在单元测试里写纳秒阈值。**功能测试要在慢机器上也能通过（13.6.7）。

:::

**第 1 题 · 记忆**　none、batch、each 三种模式各保留什么？记录总数分别是多少？

::: sol 第 1 题答案

**第 2 题 · 辨析**　「each 慢 13.3 倍，所以一次打点值 30.36 纳秒。」这句话错在哪？

::: sol 第 4 题答案

## 13.7 采样扰动、统计与Cachegrind边界 {#sec-cpp-rust.4.13.7}

本节回答一个问题：**采样频率越高、样本越多，结论就更可信吗；模拟器给出的稳定数字能替原生计时作证吗？**13.6 量的是应用自己插进去的观测；这一节量外部采集器与离线模拟各自能说与不能说。

::: preview 先抓住一件事

采样不是免费的放大镜。**频率越高，中断、展开与写出越多，还可能和周期性工作锁步；样本数增加不保证偏差下降。**本轮 1ms 请求间隔采到的根观察是 1698 与 1648，都低于 2 秒除以 1 毫秒的 2000；这只说明请求间隔不是精确时钟，不能换算丢样比例。Cachegrind 本轮没有执行（本节没有采集），模拟 miss 与原生 PMU 之间没有可搬运的等价关系。
:::

### 13.7.1 采样频率、锁步与理想根数

更高频率可能获得更多位置观察，同时也会增加中断、展开、数据写入与分析成本；某些工具可能主动限流或丢失记录。

样本数增加，不保证偏差下降。若采样与周期性工作锁步，重复观察仍可能偏向同一阶段。选择 99Hz 而不是 100Hz，是一种降低锁步风险的常见策略；它不是对所有周期都有效的数学保证。

::: def 定义 13.7.1 · 采样锁步 lock-step sampling {#def-13.7.1}

**采样锁步**指采样时刻与程序里某段周期性工作保持近似固定的相位关系，于是每次采样都更容易落在同一阶段。这时增加样本只是在重复观察同一段代码，偏差不会随样本数下降。错开频率（如 99Hz 对 100Hz）让相位缓慢漂移，是常见的规避手段，但不是数学保证。
:::

本轮 sample 的根观察数都小于「窗口 ÷ 请求间隔」这个算式给出的理想值——它提醒我们不能把请求间隔当成精确时钟（[@def-13.2.1]）。下面的例题就用这个缺口示范怎么把话写得住。

::: ex 例 13.7.1 · 2000 与 1698 的缺口能写成丢样吗 {#ex-13.7.1}

2 秒窗口、1 毫秒请求间隔，按算式应有 2000 条根观察；本轮 CPU 运行报告 1698 条，waiting 运行 1648 条。

1. 2000 是怎么算出来的？
2. 1698 与 1648 都小于 2000，能否说采集器漏掉了这个缺口对应的样本？
3. 这个缺口能支持什么结论？

::: sol 解答

1. 2 秒除以 1 毫秒等于 2000。这是按请求参数推算的理想值，不是实际发生的采样次数。
2. 不能。请求间隔是请求值，不是精确时钟；工具可能限流、合并或拒绝记录，进程启动与退出也吃掉窗口两端。本轮没有采集丢样计数与每条请求的实际时刻，比例不能这样归因。
3. 只能说报告根计数低于请求间隔推算的理想值，因此不能把间隔当成精确采样时钟（[@def-13.7.1]），也不能用根计数直接换算时间占比（[@def-13.1.1]）。

:::

:::

::: think 思考 · 把间隔改成 0.5ms、样本翻倍，结论就更可信吗 {#think-13.7.1}

有人把请求间隔从 1ms 改成 0.5ms，看到样本数翻倍，就认为报告更可信。这个推理漏掉了什么？

::: sol 解答

漏掉了偏差项。样本翻倍只压缩随机波动，不改变锁步偏差（[@def-13.7.1]）；0.5ms 可能与某段周期性工作对得更紧，反而让每次观察都落在同一阶段。频率提高还会增加中断、展开与写出成本，工具限流的概率也上升。要判断扰动有没有变，必须做附着/未附着的独立对照，而本节没有采集这项对照（[@def-13.7.2]）。

:::

:::

### 13.7.2 扰动与预热都要独立对照

要测外部采样器开销，应设计同等输入的附着/未附着运行：两者交替，保留足够原始观察，还要区分采集器 CPU、被测进程 CPU 与总墙钟。本轮没有做这种附着开销的 21 次配对实验，本节没有采集。

逐项观测实验（13.6）测的是应用内插桩，不能把它的 13.3 倍写成 sample 或 perf 的开销倍率。一个由应用自己读时钟，一个由外部进程读栈，观察对象与扰动来源都不同。

预热方面，`warm` 用 `Instant` 累计，至少持续 500ms；CPU 与 waiting 各自预热，instrumentation 则在同一个预热循环里遍历三模式。正式轮次轮转 case 起点，减少配置与单向时间漂移完全重合的风险；轮转不等于随机化，也不能消除温度或系统服务影响（[@def-1.4.1]）。

::: def 定义 13.7.2 · 附着开销对照 attached / detached control {#def-13.7.2}

**附着开销对照**指同一输入、同一二进制的两次运行：一次挂着采样器，一次不挂，交替执行并各自保留原始观察。只有这种对照才能把「采样器的代价」与「运行间漂移」分开；用插桩实验的倍率代替它，是把两种扰动源混成一个数。
:::

### 13.7.3 统计口径：21 条与 nearest-rank

::: def 定义 13.7.3 · 21 条观察的统计口径 {#def-13.7.3}

本节每个 case 有 21 条原始观察。**均值**是算术平均；**标准差**用 N-1 作分母；**p50/p99** 用 nearest-rank：排序后取第 `ceil(概率 × N)` 个。N=21 时 p99 的秩是 `ceil(20.79) = 21`，也就是最大值。
:::

```text
mean = sum(x_i) / N
sd   = sqrt(sum((x_i - mean)^2) / (N - 1))
rank = ceil(probability × N)
quantile = sorted_values[rank - 1]
```

[@def-13.7.3] 有一条直接后果：21 条样本上的 p99 就是最大观察，不是生产尾延迟。六位小数也不等于六位有效精度；保留小数便于复算，并非宣称仪器精度。

::: ex 例 13.7.2 · 21 条样本上的 p99 是哪一条 {#ex-13.7.2}

13.6 的 each 列：均值 32.832639、N-1 标准差 0.608977、批均值 p50 32.762500、p99 34.306250。

1. p99 对应排序后的第几条？
2. 能不能写「99% 的打点步都在 34.31 纳秒以内」？
3. 六位小数是不是六位有效精度？

::: sol 解答

1. 第 21 条。`ceil(0.99 × 21) = 21`，所以 p99 就是最大值 34.306250（[@def-13.7.3]）。
2. 不能。它是 21 条批均值上的分位数，描述批次之间的波动，不是逐 step 延迟；本轮也没有 200000 个 `Event` 的分布可查（[@def-13.7.4]）。
3. 不是。小数位为复算保留，统计量本身含批次与桌面环境的波动（13.7.7）。

:::

:::

### 13.7.4 两种实验单位不能混用

::: def 定义 13.7.4 · 聚合吞吐倒数 inverse aggregate throughput {#def-13.7.4}

一批 200000 步的总墙钟除以步数，得到的是**聚合吞吐的倒数**：它回答「平均每步摊到多少时间」，不回答「某一步等了多久」。前者的分母是步数，后者的分母是逐次事件；两者不能画在同一张图上比较。
:::

cpu_wait 的每条值是一整个批次的 ms；instrumentation 的每条值是批次墙钟除以 step 数。后者反映聚合吞吐倒数，不是在 each 内部采集的那 20 万个 `Event` 的分布。那些 `Event` 只经 `black_box` 观察，并未写入统计容器；要真实逐项分位数，得按 13.6.4 另做存储与扰动设计。

### 13.7.5 Cachegrind 擅长什么

::: def 定义 13.7.5 · 动态指令计数模拟 dynamic instruction-count simulation {#def-13.7.5}

Cachegrind 在支持的平台上通过动态执行追踪累计指令等事件，得到的是**模拟出来的指令计数**，不是硬件 PMU 的 retired instructions。固定程序与固定输入下，指令计数通常比墙钟稳定，因此它适合回答「相同工作是不是多走了很多机器指令」。
:::

稳定不代表与原生机器完全相同。模拟环境中的指令定义也可能不同于硬件的 retired instructions 定义，手册特别说明了 x86 REP 指令的计数差异（[@def-13.7.5]）。本轮没有执行 Cachegrind，本机也没有生成任何 `cachegrind.out` 证据；书中没有用模拟数据补齐性能表（本节没有采集）。

### 13.7.6 缓存模拟不是现代 CPU 的数字孪生

官方手册明确把缓存与分支模拟称为基础模型，它不完整反映现代处理器；当前文档还说明这些模拟默认关闭，实际使用必须核对安装版本，不能套用旧博客的默认值。

它没有自动模拟：内核活动对缓存的全部影响；其他进程的缓存竞争；真实虚拟到物理地址映射；所有 TLB 与推测执行导致的效果；原生线程调度交错；目标机器完整的预取（CPU 提前把后面要用的数据搬到近处的存储里）与分支预测机制。

因此，模拟 miss 下降不等于本机 PMU miss 必然下降；模拟指令下降也不等于墙钟必然下降。它应作为补充观测，而非替代原生计时。

### 13.7.7 布局扰动与桌面边界

可执行大小、共享库、地址布局和路径变化都可能改变模拟结果。固定输入只是可复现条件之一；不要因为工具强调稳定，就省略构建与环境指纹（[@def-13.2.4]）。

正式测量持有共享目录锁；采集前后各做一次进程名快照，未发现 cargo、rustc 或 clang 构建进程。这只是两个时点的观察，不是连续监控证明。没有隔离桌面服务，也没有锁定 CPU 亲和性、频率或热状态。所以表格只用于这个桌面环境中的工作负载诊断，不是生产 SLA，也不是硬实时上界。

::: method 判定流程 · 这条采样结论能不能写进报告

**先看单位与分母**：观察数、时间还是事件？写不清就先退回（[@def-13.1.1]）。
**再核对根计数**：与请求间隔推算的理想值差多少，有没有丢样记录；差额不能自行解释成丢失（[@ex-13.7.1]）。
**再看是不是同一次运行**：采样与计时若分属两次启动，就不能逐条配对（13.7.4）。
**再看扰动对照**：附着/未附着做过没有；没做就写「本节没有采集」，不拿插桩倍率顶替（[@def-13.7.2]）。
**再看模拟器**：Cachegrind 的 miss 与指令数只能按模拟口径陈述，不能改写成 PMU 事件（[@def-13.7.5]）。
**最后看环境边界**：亲和性、频率、热状态与桌面服务有没有锁定；没锁定就限定结论范围（13.7.7）。

:::

### 13.7.8 小结与常见错误

**小结。**① 采样频率与样本数都不是可信度的充分条件，锁步会让增加样本失效（[@def-13.7.1]）；② 采样器开销只能靠附着/未附着对照，本节没有采集（[@def-13.7.2]）；③ 21 条样本上的 p99 就是最大值（[@def-13.7.3]）；④ 批次 ms 与 ns/step 是两种单位，不能混画（[@def-13.7.4]）；⑤ Cachegrind 给的是模拟计数，本轮没有执行（[@def-13.7.5]）。

::: errata 常见错误清单（13.7 节）

E-a **认为采样频率越高越准。**中断与写出成本上升，锁步会让样本重复同一阶段（[@def-13.7.1]）。

E-b **把 1698 小于 2000 写成丢样比例。**请求间隔不是精确时钟，本节没有采集丢样计数（[@ex-13.7.1]）。

E-c **拿 13.3 倍当 sample 或 perf 的开销。**那是应用内插桩，附着对照没做（[@def-13.7.2]）。

E-d **在 21 条样本上引用 p99 当生产尾延迟。**N=21 时 p99 就是最大值（[@def-13.7.3]）。

E-e **把批次 ms 与 ns/step 画进同一张图。**两者分母不同（[@def-13.7.4]）。

E-f **用模拟 miss 下降推断本机 PMU miss 下降。**模拟模型不完整，且本轮没有执行 Cachegrind（[@def-13.7.5]）。

E-g **把桌面数字写成 SLA 或硬实时上界。**没有锁频、隔离与连续监控（13.7.7）。

## 13.8 从代码生成到证据包 {#sec-cpp-rust.4.13.8}

本节回答一个问题：**一句「这里更慢」要附带哪些证据，才能既敢下结论、又随时能被别人推翻？**13.6 与 13.7 分别交代了观测成本与采样边界；这一节把它们收进一个可交接的证据包，最后写成一句限定范围的结论。

::: preview 先抓住一件事

证据包把**对象、条件、原始观察、代码生成**四件绑在一起。**肯定**一条归因，要能读到 checksum、单位、构建与环境；**否定**它只需一处缺口：checksum 不同、二进制对不上、或只剩一张截图。代码生成只能证明某个操作存在，不能分摊总成本。
:::

### 13.8.1 三个代码生成阶段各证明什么

本轮实际保存了库的 MIR、LLVM IR 和原生 AArch64 汇编，位于 `codegen/`；命令本身在测量脚本里（`measured-source/tools/measure.sh:55`），`codegen-command.txt` 存的是那次 `cargo rustc` 的构建输出（只有 Compiling/Finished 两行），文件名容易读错，别把它当命令清单。同理 `sample-*-command.txt` 装的是采样器的进度文本。MIR 用于核对 Rust 中间表示里的控制流和调用，LLVM IR 用于核对更低层优化后的数据流，原生汇编用于核对目标机器实际生成的函数体。

::: def 定义 13.8.1 · 代码生成证据 codegen evidence {#def-13.8.1}

**代码生成证据**指同一次构建产出的三层中间与最终产物：MIR、LLVM IR、本机汇编。它回答「编译器把这段源码变成了什么」，每一层只支持一句话；它不回答「这些路径有没有真的执行过」，也不回答「各条指令各占多少时间」。
:::

```bash
cargo rustc --offline --locked --release \
  --manifest-path bench/evidence-lab/Cargo.toml \
  --lib --target-dir NEW_CODEGEN_TARGET \
  -- --emit=mir,llvm-ir,asm
```

该命令在正式计时后执行，代码生成采集不与 benchmark 并行。本轮是本机目标，没有把交叉汇编当运行结果（[@def-13.8.1]）。

### 13.8.2 mix 实际保留的代码

`mix` 的完整函数体按产物逐字列在[本章练习](ch13_exercises.md#repro-13.8.2)，摘出时只删 `.loc`/`.cfi_*`/`Ltmp` 等调试元数据，指令一行未改。它们只用于核对屏障、旋转与乘加没有被整段删除。

::: def 定义 13.8.2 · 符号存在与成本分摊 symbol existence / cost attribution {#def-13.8.2}

**符号存在**指产物里能读到某条指令或某个调用；**成本分摊**指把整批墙钟按比例分给这些操作。前者是静态观察，后者需要计时或事件证据。看到 `madd` 只证明乘加没有被删掉，不证明整批时间由乘加吞吐决定；看到原子指令，也不证明观测版的全部额外时间来自原子。
:::

按[@def-13.8.2]，一个符号只能证明某个操作存在。循环有数据依赖，也有函数调用，`black_box` 还引入可见存取；这些都没有被单独测量。

### 13.8.3 原始目录的职责

::: def 定义 13.8.3 · 证据包 evidence bundle {#def-13.8.3}

**证据包**指一次运行结束后可以整包交出去的材料：环境记录、源码与二进制指纹、与指纹匹配的源码快照、全部原始观察、采样报告、折叠结果与代码生成产物。它的用途是让另一个人从原始文件复算表格，而不是相信表格本身。
:::

| 文件或目录 | 内容 | 不承担的责任 |
|:--|:--|:--|
| environment.txt | 实际系统、工具链、profile | 完整环境隔离证明 |
| source-sha256.txt | 计时前源码与脚本指纹 | 第三方独立审计 |
| measured-source/ | 与计时前指纹匹配的源码快照 | 后处理工具已经在计时中运行 |
| binary-sha256.txt | 正式运行可执行文件指纹 | 位级可复现构建保证 |
| cpu-wait.txt | 42条原始批次 | 逐请求延迟分布 |
| instrumentation.txt | 63条原始批均值 | 持久化日志成本 |
| sample-cpu.txt / sample-wait.txt | 原生采样报告 | Linux perf事件 |
| cpu.folded / wait.folded | 叶子权重聚合 | 精确调度时间线 |
| codegen/ | 实际MIR/IR/汇编 | 所有优化版本的稳定承诺 |

这张表和[@def-13.2.4] 的六项归档要求是同一套纪律：每个文件只支持它能支持的那句话，第三列写的就是它说不了的话。

### 13.8.4 原始文件优先于最终表

表格可以重新格式化，原始观察不能为了获得理想结论而重排数值或删除慢批。本轮保留全部 21 条，包括 CPU 批次的较大值。

若未来判定某批受到已知外部故障，应保留原值与排除理由，再报告包含与排除两套结果。不要静默把「异常值处理」变成结论修饰器。

### 13.8.5 指纹与证据的可追溯关系

::: def 定义 13.8.4 · 指纹链 fingerprint chain {#def-13.8.4}

**指纹链**指源码指纹、二进制指纹与环境记录三者的组合：源码指纹回答「本轮运行的是哪份输入」，二进制指纹回答「采样与运行关联哪个产物」，环境记录回答「这些结果在哪个平台产生」。三者共同提供定位能力，任意一个都不能单独证明构建可信。
:::

run-01 之后为采集脚本补充了自动后处理与归档步骤，其计时版本保存在 `measured-source` 中，与计时前 SHA256 逐项核对；新增的门禁与校验工具另有 `postprocessing-source-sha256` 记录。

按[@def-13.8.4]，核对通过只说明「对象对上了」，不说明「构建正确」。尤其不能把 SHA256 值本身当作正确性认证。

::: think 思考 · 指纹都记了，为什么还不能说构建可信 {#think-13.8.1}

有人把 `source-sha256.txt`、`binary-sha256.txt` 和 `environment.txt` 都放进了报告，于是写下「本轮构建可信」。这个推理漏了哪一步？

::: sol 解答

漏了「指纹只做对象绑定」这一步。哈希相同只说明两次比较的是同一串字节，不说明这串字节来自可信工具链、没有被篡改，也不说明它执行了正确的工作。要谈可信，还需要来源与权限控制、独立审计，以及[@def-13.8.3] 证据包里的原始观察与代码生成相互对照；本轮只做了本地记录，没有第三方审计。

:::

:::

### 13.8.6 归因结论的模板

一个谨慎结论可以写成：

> 在本轮输入、编译器与桌面环境中，Each 模式的聚合 step 成本高于 None。
> 校验输出相同，主要业务递推保留。
> 修改同时引入时钟、事件屏障与计数路径，因此没有将差异拆成独立组件成本。

这比「日志让 Rust 慢十三倍」更有用：后者丢掉工作负载、观测内容和测量范围，前者给下一轮实验留下明确入口。

::: ex 例 13.8.1 · 把「日志让 Rust 慢十三倍」改写成可交回的结论 {#ex-13.8.1}

手上只有 13.6 的表：none 2.472857、each 32.832639 ns/step，21 批，每批 200000 步，checksum 均为 188478885453998054；平台 Apple M5 Pro、aarch64-apple-darwin、rustc 1.99.0。

1. 写出三句式结论。
2. 「十三倍」的分母是什么？
3. 这条结论不能支持哪两个断言？

::: sol 解答

1. 在本轮输入、编译器与桌面环境中，Each 模式的聚合 step 成本由 2.472857 升到 32.832639 ns/step，约 13.3 倍；三模式 checksum 同为 188478885453998054；修改同时引入时钟、事件屏障与计数路径，没有拆成独立组件成本。
2. 分母是每批 200000 步的聚合 step，只覆盖这一段递推循环；不是生产请求，也不是单次日志调用的延迟（[@def-13.6.2]）。
3. 不能说「日志子系统在任何服务上都慢 13 倍」，也不能说「13.3 倍里时钟占多少」。功耗、IPC 与 cache miss 本轮没有采集。

:::

:::

### 13.8.7 什么情况应该停止下结论

以下情况至少需要暂停比较：checksum 不相同；单位发生变化；采样报告对应了旧二进制；只剩截图、原始数据丢失；编译 profile 或 feature 未知；样本缺失却仍输出尾分位数；工具报告丢失或不支持事件，但表格照填零。

暂停不是实验失败；继续输出看似精确的数字才会破坏证据链。

::: method 判定流程 · 这句话能不能发出去

**第一关：正确性**。checksum 或期望值不一致，先修功能，不进入性能讨论（[@def-13.5.1]）。
**第二关：单位**。批次 ms、ns/step、观察数三者混用，先统一分母（[@def-13.7.4]）。
**第三关：对象**。采样报告对应的二进制与本次计时是否同一个指纹；不是就重采（[@def-13.8.4]）。
**第四关：原始数据**。只剩截图或最终表，结论降级为线索（[@def-13.8.3]）。
**第五关：构建**。profile 与 feature 未知，任何跨运行比较都不成立。
**第六关：完整性**。样本缺失或事件不支持时，不许输出尾分位数，也不许把表格填零。
六关全过，才按 13.8.6 的模板写一句带条件的结论；任何一关不过，就写「证据不足」。

:::

### 13.8.8 小结与常见错误

**小结。**① 三层代码生成各只证明一句话，不等于执行过全部路径（[@def-13.8.1]）；② 符号存在不等于成本分摊（[@def-13.8.2]）；③ 证据包让原始文件可复算，而不是让人相信最终表（[@def-13.8.3]）；④ 指纹链只提供定位，SHA256 不是正确性认证（[@def-13.8.4]）；⑤ 结论要带条件与缺口，六关有一关不过就停。

::: errata 常见错误清单（13.8 节）

E-a **看到 madd 就断定整批受乘加吞吐限制。**符号只证明操作存在（[@def-13.8.2]）。

E-b **把 MIR/IR/汇编当「执行过全部路径」的证明。**它们只描述生成了什么（[@def-13.8.1]）。

E-c **只留最终表、删掉 21 条原始观察。**表格失去复算入口（[@def-13.8.3]）。

E-d **把 SHA256 当正确性认证。**指纹只绑定对象，不做审计（[@def-13.8.4]）。

E-e **checksum 相同就认定二进制相同。**输出一致不约束构建产物（13.8.5）。

E-f **用「日志让 Rust 慢十三倍」代替结论。**缺工作负载、观测范围与单位（[@ex-13.8.1]）。

E-g **工具不支持某事件，表格照填零。**零、不支持与未运行是三种状态（13.8.7）。

:::

::: method 即时自测 · 13.8

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　MIR、LLVM IR、原生汇编各支持哪一句话？

::: sol 第 1 题答案
MIR 支持「前端接收了什么控制流与调用」，LLVM IR 支持「优化后数据流变成什么样」，原生汇编支持「目标机器实际生成什么函数体」。三者都不支持「这些路径执行过」（[@def-13.8.1]）。
:::

**第 2 题 · 辨析**　「三模式 checksum 相同，所以两次运行的可执行文件相同。」对吗？

::: sol 第 2 题答案
不对。checksum 只约束业务输出，不约束构建产物；不同构建、不同优化或不同工具链都可能算出同一个 checksum。要谈产物相同，得看 `binary-sha256.txt` 与 `environment.txt`（[@def-13.8.4]）。
:::

**第 3 题 · 应用**　交出一份最小证据包，列六项。

::: sol 第 3 题答案
① 环境记录；② 源码指纹与匹配的源码快照；③ 二进制指纹；④ 全部原始观察（本轮 cpu-wait 42 条、instrumentation 63 条）；⑤ 采样报告与折叠结果；⑥ 代码生成产物与命令。对应[@def-13.8.3]，缺一项就少一句结论。
:::

**第 4 题 · 迁移**　把 13.8.6 的模板用于一次数据库慢查询归因，哪些字段要换？

::: sol 第 4 题答案
「聚合 step 成本」换成查询级延迟或其分位数，「三模式 checksum」换成结果集校验，「构建与环境」换成数据库版本、参数、数据量与并发。可加性限制不变：改动同时引入索引与连接策略时，不能把差异拆成单项成本（[@def-13.8.2]）；没有采集的等待事件也不能写成结论。
:::

:::

## 13.10 常见错误索引 {#sec-cpp-rust.4.13.10}

这是本章的跨节错误索引：每一节末尾都有自己的「::: errata 常见错误清单（13.M 节）」，按你阅读的顺序给出局部清单。下面这一份只收那些要读完整个章才浮出来的错误，它们在单节内部看不出问题，放进「采集、归因、出结论」的整条链才露馅。

**把线程栈快照称为 CPU 周期分布。** 本章的 sample 能看到睡眠栈，权重是观察数，不是核心周期。先写清分母，再解释框有多宽（[@def-13.4.2]）。

**把 inclusive 计数全部相加。** 一条观察会经过多个父层，逐层相加等于重复计数（[@def-13.2.2]）。要在 self 计数或互斥分类上求和，本章折叠结果的总数仍是 1698 与 1648。

**认为最宽的函数就是用户延迟根因。** 请求可能大部分时间在排队，CPU 图只能描述被采到的执行。要落到根因，还需要阶段时间与业务关联（[@def-13.4.3]）。

**把 flamegraph 横轴当时间轴。** 聚合后相邻的框不代表先后，需要顺序时应改用时间线视图（[@def-13.4.1]）。图题还必须标明权重，否则读者会默认它是耗时。

**把 batch 聚合说成无损替代。** 总数保留，逐项分布丢失，低成本总数回答不了每个异常请求的问题（[@def-13.6.1]）。选哪种记录方式由诊断目标决定，不存在普遍更优的一种。

**测完插桩版再减一个固定时钟成本。** 插桩可能改变向量化、内联与寄存器压力，可加性并不天然成立（[@def-13.7.2]）。受控的无插桩对照更直接。

**把局部原子实验外推为共享争用。** 本章的 counter 没有并发访问者，也没有测缓存线迁移或扩展性（[@def-13.6.3]）。`Relaxed` 也不保证争用消失。

**把 PMU 不支持当成事件数为零。** 能力缺失与测量结果是两种状态，应保存错误与未运行状态（[@def-13.3.3]）。结果表里不允许填伪造的零。

**忽略事件复用后直接计算 IPC。** 分子分母可能没有同时覆盖同一阶段，需要检查运行比例与事件组（[@def-13.3.2]）。缩放之后仍然是估计，不是原始计数。

**把事件归到记录位置那一行。** skid 与内联都会影响位置解释，要先查事件支持与实际代码（[@def-13.3.4]）。不要根据一条热行就盲目加 prefetch。

**把模拟缓存参数当真实微架构。** Cachegrind 的模型有明确缺项，原生 PMU 与墙钟要另测（[@def-13.7.5]）。本章没有 Cachegrind 结果，更没有据此推断真实缓存的行为。

**采样与正式计时同时跑却不记录。** 观测本身会改变执行环境，本章把两者分开。另行采样不能直接估计附着开销，要单独做对照（[@def-13.7.1]）。

**只保存 SVG 或截图。** 图像恢复不出丢失的样本与映像对应，原始报告、二进制指纹和命令必须一起保留（[@def-13.8.4]）。聚合结果只是派生产物。

**把 21 条批均值的 p99 称为服务 p99。** 在 nearest-rank 下它只是最大的一条批均值，既没有逐请求到达过程，也没有支撑极端尾部的样本量（[@def-13.7.3]）。要谈服务 p99，得先有逐请求观测。

## 13.11 本章小结与章末件 {#sec-cpp-rust.4.13.11}

::: note 本章小结

- 先定观测对象与分母，再选采集器；「这个函数很热」不是可反驳的假设（[@def-13.1.1]、[@ex-13.1.1]）。
- 一条采样记录有 inclusive 与 self 两个账，宽度与价格是两件事（[@def-13.2.1]、[@def-13.2.2]）。
- 事件的零、不支持、未运行是三种状态，不能统一写成 0（[@def-13.3.3]、[@ex-13.3.1]）。
- 折叠图横轴不是时间，图题必须写清权重与分母（[@def-13.4.1]、[@ex-13.4.1]）。
- 逐项打点换来分布，批量聚合换来低成本，两者不能互相冒充（[@def-13.6.1]、[@ex-13.6.1]）。
- 采样与计时分开跑，附着开销要配对对照才能谈（[@def-13.7.1]、[@def-13.7.2]）。
- 结论要带证据包：原始报告、指纹与命令，缺一件就无法复核（[@def-13.8.3]、[@ex-13.8.1]）。

:::

### 出口检查

从 `cpp-rust/` 执行下列命令：先构建，再采集，不要把编译耗时混进运行基准。输出目录必须不存在，父目录需先存在；脚本用 mkdir 取得共享测量锁，EXIT 时释放，并拒绝覆盖既有归档。

```bash
cargo fmt --manifest-path bench/evidence-lab/Cargo.toml --check
cargo clippy --offline --locked --manifest-path bench/evidence-lab/Cargo.toml \
  --all-targets --all-features -- -D warnings
cargo test --offline --locked --manifest-path bench/evidence-lab/Cargo.toml
cargo test --offline --locked --manifest-path bench/evidence-lab/Cargo.toml \
  --all-features
cargo build --offline --locked --release \
  --manifest-path bench/evidence-lab/Cargo.toml --bins
cargo build --offline --locked --release --features checked \
  --manifest-path bench/evidence-lab/Cargo.toml --bin feature_work \
  --target-dir bench/evidence-lab/target-checked
bash bench/evidence-lab/tools/measure.sh bench/evidence-lab/results/my-new-run
```

四项实验依次运行，不并行计时。读原始证据时，你应能手动完成八项核对：从 cpu-wait 原始行数出每个 case 的 21 批；检查所有业务 checksum 一致；用 N−1 重算标准差；用 nearest-rank 重算 p50/p99；从 sample 根与叶子核对折叠权重；从 `.s` 找到 mix 的实际函数体；从 source-sha256 定位计时前的源文件；确认 sample 不是正式计时进程。

机制问答要求你解释八个「为什么」：waiting 图很宽为什么不等于 CPU 执行了四十毫秒的睡眠指令；CPU 采样与线程快照为什么不能用同一标题；none 与 batch 非常接近时为什么不宣称后者加速；局部原子计数为什么不能预测多线程共享计数；逐项事件未存储为什么不能输出真实分位数；反汇编证明计算存在，为什么不证明耗时都来自该计算；PMU 复用缩放为什么不能恢复被错过的阶段；Cachegrind 指令稳定为什么不等于原生墙钟稳定。

本章两个实验验证的是有限而明确的问题：相同递推加主动等待，会产生不同的墙钟与栈形状；逐项观测会显著增加这个轻量递推夹具的聚合成本。它们没有证明通用日志框架的固定开销，没有证明 Linux 硬件事件归因，也没有证明生产服务的尾延迟上界。
