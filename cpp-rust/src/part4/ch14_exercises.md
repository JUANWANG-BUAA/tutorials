# 第14章 · 习题集

共 20 题，分三组。**A 组概念**检验你能否把名词说准；**B 组推理**检验你能否从表格与命令推出结论；**C 组实操**要求你真的跑命令、写判定。全部题目附解答，难题另附提示层。

用法约定：先写下自己的答案，再展开核对。看解答时只看第一行就停住，问自己「接下来那一步是不是我要走的」，再往下读。直接通读解答，得到的只是「看懂了」，不是「会做了」。

本页出现的每一个数都抄自正文并给出锚点。凡是正文说「未采集」的指标，本页不出现在任何答案里；判定练习中的区间都明确标为假设值。

## A 组 · 概念（1–7）

::: ex A1 · 六层身份与两个最常漏的断点（主线 ④） {#ex-14.A.1}

构建身份分成哪六层？本章说最容易漏掉的是哪两处？「我们的包没有第三方依赖，所以记两行版本号就够」这句话漏了什么？

::: sol 解答

六层：源文件加清单加锁文件；包选择加 feature 闭包加 target 加 profile；工具链与标准库与链接器与 SDK 与构建脚本输入；对象、IR、调试信息与链接产物；二进制指纹加运行输入加环境与原始观察；门禁与发布裁决。最常漏的是 feature 闭包与 `build.rs` 的外部读取。零依赖仍有 feature 闭包、profile 与显式 `RUSTFLAGS`、目标三元组、SDK 与链接器版本，所以两行版本号只覆盖第三层的一部分。对照[定义 14.1.1](ch14.md#def-14.1.1)、[思考 14.1.1](ch14.md#think-14.1.1)。
:::

:::

::: ex A2 · 指纹能支撑哪两句话（主线 ④） {#ex-14.A.2}

产物指纹由哪两项组成？哈希相同、哈希不同各能支撑哪一句？「21 份产物大小同为 518448 字节，所以它们是一回事」错在哪一步？

::: sol 解答

由 SHA256 与文件大小组成，是身份检查。哈希相同支撑「两次构建拿到同一份产物」；哈希不同只支撑「字节不同」。大小一致只说明段布局总量相同，不是身份判据——本轮 release 一行 21 份产物大小同为 518448 字节，SHA256 却有 21 个不同值。语义证据要看 checksum 与代码生成，不是看哈希。对照[定义 14.1.2](ch14.md#def-14.1.2)、[例 14.3.1](ch14.md#ex-14.3.1)。
:::

:::

::: ex A3 · 三个旗标各管什么（主线 ④） {#ex-14.A.3}

`--locked`、`--offline`、`--frozen` 的责任分别是什么？为什么「加了 `--frozen` 就有了沙箱」是错的？本轮为什么把 `--offline` 与 `--locked` 分开写？

::: sol 解答

`--locked` 沿用锁文件、不许悄悄更新解析；`--offline` 只允许本地可用资源；`--frozen` 是两者组合。三者都不是沙箱：`build.rs` 仍可能读外部文件或运行任意工具，也不承诺网络隔离、供应链审计与位级确定性。分开写是为了让读者看到两份责任各由哪个旗标承担，而不是被一个组合词糊成一句。对照[定义 14.1.3](ch14.md#def-14.1.3)、[14.1.5](ch14.md#sec-cpp-rust.4.14.1)。
:::

:::

::: ex A4 · 那一行 `default-features = false` 生效了吗（主线 ①） {#ex-14.A.4}

概念图里 `service` 直接依赖 `parser` 并写 `default-features = false`，同时经 `plugin` 依赖 `parser` 且用默认 feature。① `parser` 最终有没有默认能力？② 由哪个量决定？③ 只看 `service/Cargo.toml` 能判断吗？

::: sol 解答

① 通常会拿到：同一依赖的相关请求取并集，`plugin` 那条边启用的默认 feature 仍会落到 `parser` 的构建单元上。② 由 feature 闭包决定，即整个图上与该依赖相关边的并集，不是单条边上的一个属性。③ 不能，顶层清单只看得到自己那一行；要沿入边展开，例如 `cargo tree -e features -i parser`。结论：`default-features = false` 是这条边的请求，不是全局关闭。对照[定义 14.2.1](ch14.md#def-14.2.1)、[例 14.2.1](ch14.md#ex-14.2.1)。
:::

:::

::: ex A5 · 包条目数不等于编译次数（主线 ②） {#ex-14.A.5}

构建单元的定义是什么？为什么同一个包名可能编译多次？resolver 2 与 3 各处理了什么？本轮为什么没有 resolver 的构建时间数据？

::: sol 解答

构建单元是同一包在一种编译条件组合下的一份实际构建；host 与 target、不同 feature 闭包、不同 profile、不同目标平台都可能各生成一份，所以锁文件里的包条目数与实际编译次数是两个量。resolver 2 分离了构建依赖与普通依赖、未构建目标的平台依赖、特定开发依赖；resolver 3 还涉及 Rust 版本感知的解析。它不是「永远只编译一次」的开关。本轮独立 workspace 显式用 resolver 3，但零第三方依赖，所以没有测复杂 resolver 的性能，这一句是范围声明。对照[定义 14.2.2](ch14.md#def-14.2.2)、[14.2.4](ch14.md#sec-cpp-rust.4.14.2)。
:::

:::

::: ex A6 · 三级「可复现」（主线 ④） {#ex-14.A.6}

三级承诺各是什么？前两级成立能不能推出第三级？本轮成立到哪一级，凭什么说不成立第三级？

::: sol 解答

第一级流程可重跑，第二级性能实验可比较，第三级位级产物相同。前两级的成立对第三级没有任何蕴含。本轮只给前两级证据：14.11 的入口能重建实验，14.4 与 14.5 比较前都固定了身份字段。第三级被证伪——构建矩阵为每个配置建 21 个目标目录，同一配置产物大小一致但 21 个 SHA256 都不同；本轮没有对差异字段作二进制归因。对照[定义 14.3.1](ch14.md#def-14.3.1)、[例 14.3.1](ch14.md#ex-14.3.1)。
:::

:::

::: ex A7 · 三种边界各有名字（主线 ②） {#ex-14.A.7}

fresh、noop 与「改一个文件后的增量重建」各测什么？为什么 fresh 不能叫「完全冷构建」？为什么 noop 的十几毫秒不能拿去评价 CI 构建速度？

::: sol 解答

fresh 每次给一个不存在的 `--target-dir`，本包编译与链接必须重做；noop 在同一目标目录、同一命令、源码与标志不变时再跑，测「判断要不要重建」的成本；增量重建测改一个文件后的重建，本轮没有测第三种。不能叫冷构建，因为工具链、标准库与 OS 页缓存（操作系统缓存文件内容的那块内存）都还在，真正的冷缓存要连这些一起消失。noop 只证明 Cargo 检查了已有产物，不代表重建成本，其均值在 18 ms 附近，而 fresh 是 338–1996 ms。对照[定义 14.4.1](ch14.md#def-14.4.1)、[定义 14.4.2](ch14.md#def-14.4.2)。
:::

## B 组 · 推理（8–15）

::: ex B8 · 21 个不同 SHA256 该怎么写（主线 ④） {#ex-14.B.8}

release 一行：21 次构建、大小同为 518448 字节、21 个不同 SHA256。① 证伪了哪一级承诺？② 对第一级和第二级是肯定还是沉默？③ 能不能据此写「性能也可能因此不同」？

::: sol 解答

① 第三级位级产物相同。② 对第一级偏正面：21 次都构建成功、产物大小相同、`verify-*.txt` 的 checksum 一致；对第二级沉默——可比较性靠实验契约（单位、输入、批次、计时边界），与字节是否相同无关。③ 不能。指纹只证明字节不同；本轮大小完全一致，`__text` 段也是同一份，差异落在调试信息与链接元数据这类字段上，具体是哪个字段本节没有采集归因。对照[例 14.3.1](ch14.md#ex-14.3.1)、[定义 14.1.2](ch14.md#def-14.1.2)。
:::

:::

::: ex B9 · 101 ms 的差能不能写成结论（主线 ③） {#ex-14.B.9}

release 的 fresh 均值 439.733（sd 68.274），one 是 338.194（sd 10.053）。有人写「one 比 release 快 101 ms，可以直接下结论」。请指出这个读法缺了哪一步，并给出正文允许的那句话。

::: sol 解答

缺的是配对。表里是两个 case 各自的批均值与各自 sd，属于独立分组读法，会把一部分共同时间条件算进实现差异。设计里其实有配对单位：驱动脚本每轮构建三个 profile、起点按轮旋转，同一轮就是天然配对单位。但本轮只按 case 汇总，没有算配对差值与区间，所以正文只允许描述性说法——「本轮这 21 轮里 one 的均值更低，方向在 4.4 倍于 sd 的量级上」；要放行须按轮算差值与区间，再与事先写下的预算比。对照[例 14.4.1](ch14.md#ex-14.4.1)、[定义 14.4.5](ch14.md#def-14.4.5)。
:::

:::

::: ex B10 · 4.5 倍墙钟换 2.6% 代码段（主线 ④） {#ex-14.B.10}

thin 的 fresh 均值 1995.882 ms 对 release 439.733 ms；`__text` 236656 对 242940 字节。有人写「ThinLTO 让产物更小，所以应默认开」。按预算与承诺级别把它改写成一句负责的结论。

::: sol 解答

先承认这是两个预算之间的兑换：构建墙钟约 4.5 倍，代码段约小 2.6%。要下判断缺三件：事先写下的构建时间预算与体积预算；运行性能证据（本节只测构建与体积，运行侧没有采集）；范围声明（`publish = false` 的单包小二进制，依赖多、构建图深时不能外推）。合格句子：「本轮小包桌面环境下，thin 在构建时间上明显更贵、代码段略小；是否值得取决于两者的预算，运行差异未测。」对照[例 14.4.2](ch14.md#ex-14.4.2)、[定义 14.3.1](ch14.md#def-14.3.1)。
:::

::: ex B11 · 5.27 与 20% 预算（主线 ④） {#ex-14.B.11}

default 批均值 0.042857、checked 0.225888 ns/byte，checksum 同为 133693440，预算 20%。① 比值是多少？② 门禁判什么、退出码几？③ 这个拒绝是不是统计显著性的结论？

::: hint 提示

门禁的条件写在正文里：`candidate_mean / baseline_mean <= 1 + budget`。20% 进这个式子时变成 1.20，不是 0.20。

:::

::: sol 解答

① 0.225888 ÷ 0.042857 ≈ 5.27。② 远大于 1.20，超预算 → 拒绝，退出码 1，结果写入 `gate-rejection.json`。③ 不是。这是描述性预算判定：20% 是本教学夹具写定的策略阈值，不是显著性水平，本轮也没有算 p 值或置信区间。要升级成三态结论，还需按轮算配对差值的区间，本轮没有算。对照[例 14.5.1](ch14.md#ex-14.5.1)、[定义 14.5.3](ch14.md#def-14.5.3)。
:::

:::

::: ex B12 · 只有 20 轮候选（主线 ④） {#ex-14.B.12}

归档里候选只有 20 轮，其余正常，均值看着在预算内。门禁会给出什么？下一步该做什么？为什么不能把 20 轮均值当成结论？

::: sol 解答

退出码 2：证据不可比，不是超预算。样本不齐时连「候选是否更慢」都还没回答。下一步是补齐缺失轮次后重新归档，用新目录，不覆盖旧结果；不能用 20 轮均值替代，也不能用空列表或零均值补上——那会把不完整证据伪装成通过。对照[定义 14.5.3](ch14.md#def-14.5.3)、[定义 14.7.2](ch14.md#def-14.7.2)。
:::

::: ex B13 · 三态门禁：四个区间怎么判（主线 ③） {#ex-14.B.13}

把 14.5 的单点比值升级成区间判定时，预算仍是 20%，即 `B = 1.20`，判定规则是 `U ≤ B` 接受、`L > B` 拒绝、其余证据不足。下面是四组**假设**的比值区间（练习设定，不是本轮实测——正文明确说本轮没有计算配对区间）：

- (a) `[1.02, 1.17]`
- (b) `[1.24, 1.41]`
- (c) `[0.96, 1.26]`
- (d) `[1.08, 1.20]`

逐组给出判定与下一步动作。第 (d) 组要额外说明：等号归哪一边由谁决定？

::: hint 提示

只看两个端点与 1.20 的位置关系，不要重算区间。跨过 1.20 就是第三态，不是「大概差不多」。

:::

::: sol 解答

(a) `U = 1.17 ≤ 1.20` → 接受，记协议后发布，并在说明里保留区间与样本数。(b) `L = 1.24 > 1.20` → 拒绝，但先看候选多做了什么工作，而不是重跑等它变绿。(c) `L ≤ 1.20` 且 `U > 1.20` → 证据不足，补轮次、补独立重跑，或先确认身份字段是否对齐；不能写成「基本等价」。(d) `U = 1.20`，按门禁写的 `ratio <= 1 + budget` 判接受。等号归属本身是协议的一部分，必须在看到候选数字之前固定；团队可以选更保守的规则，但那要事先写明。对照[定义 14.5.3](ch14.md#def-14.5.3)、[例 14.5.1](ch14.md#ex-14.5.1)。
:::

::: ex B14 · 只留一个 profdata 的归档（主线 ①） {#ex-14.B.14}

某工程 `results/pgo/` 里只有 `merged.profdata` 与最终二进制。① 能证明最终版用过训练数据吗？② 出现回退时能区分源码变化与训练变化吗？③ 最先该补哪一件？

::: sol 解答

① 只能证明旁边放着一份 profdata，不能证明最终二进制是用这份数据编出来的——缺 profile-use 命令与最终程序指纹之间的对应。② 不能；回退可能来自源码、工具链、feature 闭包或训练语料，缺训练输入清单时无法归因。③ 训练输入清单与生成训练程序时的完整命令，其次是与它配对的运行参数。补不齐就按证据不足处理，不要用「我们开过 PGO」当结论。对照[例 14.6.1](ch14.md#ex-14.6.1)、[定义 14.6.1](ch14.md#def-14.6.1)。
:::

::: ex B15 · 三条 CI 结果各修哪一层（主线 ④） {#ex-14.B.15}

① 候选 21 轮齐全、checksum 都是 133693440、比值 5.27；② 候选只有 20 轮；③ 两台 runner 上结论相反，`rustc -Vv` 不同。按四层门禁，各自的第一动作是什么？

::: sol 解答

① 第三层：证据有效但超预算，退出码 1，先看候选多做了什么工作（本例是 `checked` 的逐字节观察），不是重跑。② 第二层：退出码 2，先补第 21 轮，此时均值没有意义。③ 先查身份再谈数字：工具链不同意味着第三层不同，两台机器上的数字不是同一程序的两次观测，记为不可比，而不是「第二台更慢」。对照[例 14.7.1](ch14.md#ex-14.7.1)、[定义 14.7.1](ch14.md#def-14.7.1)。

## C 组 · 实操（16–20）

::: ex C16 · 把 feature 闭包落成文件（主线 ④） {#ex-14.C.16}

用 14.2.5 的两条命令生成 `feature-tree.txt` 与 `metadata.json`。写出你实际敲的命令，说明两条输出各回答什么问题，并解释为什么本轮树里只有本包。

::: sol 参考路径

```bash
cargo tree --offline --locked \
  --manifest-path bench/evidence-lab/Cargo.toml -e features --features checked
cargo metadata --offline --locked \
  --manifest-path bench/evidence-lab/Cargo.toml --format-version 1
```

`cargo tree -e features` 沿依赖边展示 feature 的传递，回答「这个 feature 闭包里到底有什么」；`cargo metadata` 记录包目标与清单结构，回答「解析出了哪些单元」。本轮是零第三方依赖的独立 workspace，树里只有本包；正文明确没有假造额外依赖来显得复杂。另注意 `metadata` 里的路径属于本机，不能当跨机器稳定标识。对照[14.2.5](ch14.md#sec-cpp-rust.4.14.2)、[定义 14.2.1](ch14.md#def-14.2.1)。

::: ex C17 · 复验一次真实拒绝（主线 ④） {#ex-14.C.17}

跑 14.11 的 `gate.py` 命令复验拒绝。记下输出与退出码，然后回答：为什么不能加一条兜底让命令永远返回 0？这份归档能不能用来证明生产性能？

::: hint 提示

先 `echo $?` 看退出码，再读 `gate-rejection.json`。正文说这个归档对应预期退出码 1，并且不能用兜底命令把它变成通过。

:::

::: sol 参考路径

```bash
python3 bench/evidence-lab/tools/gate.py \
  bench/evidence-lab/results/run-01/feature-default.txt \
  bench/evidence-lab/results/run-01/feature-checked.txt --budget 0.2
echo $?
```

预期退出码 1：有效候选超预算的拒绝，不是工具运行失败。用兜底命令吞掉它，等于把「拒绝」和「工具出错」合成一态，门禁就再也证明不了自己会拒绝。这份归档只支持「单包、1 MiB 单一输入、桌面 macOS 下的描述性比较」，不支撑生产 SLA，也不是统计显著性结论。对照[14.11](ch14.md#sec-cpp-rust.4.14.11)、[定义 14.5.3](ch14.md#def-14.5.3)。

::: ex C18 · 先预测，再对表（主线 ③） {#ex-14.C.18}

只看 `Cargo.toml` 的三个 profile（release 用 16 个 CGU、`lto = false`；one 用 1 个 CGU；thin 在 one 基础上 `lto = "thin"`），预测 fresh 墙钟从快到慢的顺序，再用 14.4.6 的表核对。预测错了要指出错在哪个直觉。

::: hint 提示

正文专门提醒过「更多 CGU 必然编译更快」这句口号。小包还要算划分、优化与链接的固定成本。

:::

::: sol 参考路径

按「CGU 越多越快」的直觉会预测 release 最快。实际顺序是 one（338.194）快于 release（439.733），thin 最慢（1995.882）；noop 三者都在 18 ms 附近、差异极小，但这不能反过来推出 profile 对构建速度没有影响。错在把并行粒度当成唯一因素：小包里划分、优化与链接的固定成本可能压过并行收益，而跨 crate ThinLTO 要额外付全局优化代价。必须保留这个结果，不能为了符合口号改写数据。对照[例 14.4.1](ch14.md#ex-14.4.1)、[定义 14.4.3](ch14.md#def-14.4.3)。
:::

::: ex C19 · 把区间写成两句可发布的话（主线 ④） {#ex-14.C.19}

预算 `B = 1.20`（即 20%）。两组候选的比值区间是**假设值**（练习设定，正文说本轮没有计算配对区间）：甲 `[1.03, 1.12]`，乙 `[0.98, 1.24]`。为每组写出判定、下一步动作，以及一句带范围的结论。

::: sol 参考路径

甲：`U = 1.12 ≤ 1.20` → 接受。动作是记录协议（输入、构建身份、种子）后发布，并在说明里保留区间与样本数。结论示例：「在这台机器、rustc 1.99.0 的离线锁定 release 构建与 1 MiB 输入下，候选相对基线的比值区间为 [1.03, 1.12]，未超出 20% 预算；本结论不覆盖其他输入、其他工具链与请求级尾延迟。」乙：`L = 0.98 ≤ 1.20` 而 `U = 1.24 > 1.20` → 证据不足。动作是补轮次或独立重跑，并核对 feature 闭包、profile、输入长度与工具链是否与基线一致；不得写成「基本等价」，也不得把区间截到 1.20 以内。对照[定义 14.5.3](ch14.md#def-14.5.3)、[定义 14.7.2](ch14.md#def-14.7.2)。

## 批改时最常给的三条意见

1. **把描述性比值当统计结论。** 5.27 是教学夹具的策略判定，不是显著性；写「证明候选慢 5.27 倍」要扣分，改成「在 20% 预算下被拒绝，退出码 1」。
2. **边界没命名就报数。** 18 ms 是 noop、338–1996 ms 是 fresh，写混了整段分析作废；哈希不同写成变慢同理，指纹只回答「是不是同一个对象」。
3. **把三种状态压成一种。** 退出码 1 与 2 的下一步动作相反：一个修性能，一个修采集。区间跨过预算写成「基本等价」，同样是压状态。
