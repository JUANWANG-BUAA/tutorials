# 第十六章 · 习题集

共 20 题，分三组。**A 组概念**检验你能否把「谁负责」说清楚；**B 组推理**给一条具体误用，要求指出被破坏的不变量与接住它的守卫；**C 组实操**要求你写清单、跑构建、设计迁移方案。全部题目附解答，难题另附提示层。

这一章是项目章，题面里的调用序列都来自 `projects/ffi-bridge/`：`src/lib.rs`、`tests/contracts.rs`、`include/bridge.h`、`c/demo.c`、`c/tests.c`、`c/benchmark.c`。做法约定：先写下自己的答案，再展开核对；看解答时只看第一行就停住。

## A 组 · 概念（1–7）

::: ex A1 · 四个入口的责任表（主线 ④） {#ex-16.A.1}

把 `rb_transform`、`rb_create_copy`、`rb_generate`、`rb_copy` 四个入口填进一张四行表：谁分配数据、返回后谁读写、谁释放、失败后谁清理。填完回答：哪几个入口会产生释放责任？

::: sol 解答

`rb_transform`：C 分配输入与输出，本次调用期间 Rust 读写，返回后仍归 C，Rust 一个指针也不留；失败时按 `EINVAL` 或 `ERANGE` 不写任何输出，C 照常管自己的缓冲。
`rb_create_copy`：C 交原件，Rust 复制出自己的副本；两者各自管理自己的分配，句柄承担且只承担一份释放责任。
`rb_generate`：Rust 分配并持有，C 拿到句柄与元数据，释放责任挂在句柄上。
`rb_copy`：Rust 原件、C 输出，两份分配各自管理。
只有 `rb_create_copy` 与 `rb_generate` 这两条拥有路径产生释放责任，且每次成功创建恰好一个；`rb_transform` 与 `rb_copy` 不产生句柄。对照[定义 16.1.2](ch16.md#def-16.1.2) 与 [16.1.2 三种数据路径](ch16.md#sec-cpp-rust.4.16.1)。

:::

::: ex A2 · 如果把错误码换成错误字符串（主线 ④） {#ex-16.A.2}

有调用者要求「返回字符串错误消息，好直接打日志」。按本章标准，两侧各由谁分配、谁释放、指针能活多久？本章为什么保留整数词表？

::: sol 解答

先要回答三件事，缺一件接口就不能发布。
第一，谁分配：Rust 分配则 C 不能 `free`，必须给出一个 `rb_free_error` 之类的消费者；C 提供缓冲则要声明容量与写入上界，容量不足时得有一个像 `ECAPACITY` 那样的码。第二，谁释放、什么时候：若指针有效到「下一次调用」为止，读取顺序就成了新契约，正好是线程局部缓冲被批评的那条隐式寿命。第三，编码与跨模块可见性：字符串编码、所有权、线程局部可见性都要进头文件，ABI 面因此扩大。
本章选择只返回 `i32`（C 声明 `int32_t`），把每个数值绑定一种可判定的资源后果：是否消费句柄、是否写输出。没有借出的错误字符串，也就没有「下一次调用覆盖上一条文本」的问题。对照[定义 16.2.3](ch16.md#def-16.2.3) 与 [16.2.4 错误码是一份稳定词表](ch16.md#sec-cpp-rust.4.16.2)。

:::

::: ex A3 · 哪些东西能进头文件（主线 ④） {#ex-16.A.3}

下列五项，哪些可以出现在 `include/bridge.h` 里：`Vec`、`Arc<[u64]>`、`Result` 的错误类型、`rb_handle`、`rb_info_v1`？各给一句理由。

::: sol 解答

可以的是 `rb_handle`（就是 `u64`，宽度 8）与 `rb_info_v1`（固定宽度整数的 `repr(C)` 结构，本机 24 字节、对齐 8）。
不可以的是 `Vec`、`Arc<[u64]>` 与 Rust 的 `Result`：它们的布局属于 Rust，注册表内部换容器不该影响 C 的头文件；外层加 `repr(C)` 也不能替内部 Rust 容器发明 C 表示。
判据是[定义 16.2.1](ch16.md#def-16.2.1) 那一句——对方改了它我要不要重新编译。需要，就锁死并两侧断言；不需要，就别让它出现在头文件里。

:::

::: ex A4 · 词表稳定的是什么（主线 ④） {#ex-16.A.4}

「稳定错误词表」承诺哪两件事？为什么调用者不能解析实现的检查顺序？举一个本版里顺序确实没有承诺的例子。

::: sol 解答

承诺两件：同一数值不会因为一次改版而换意思；也不会因为某次实现调整而凭空多出一个新值。
不承诺检查顺序，因为顺序是实现细节：一个输入同时违反多条规则时，返回哪一个并不保证每版相同。
例子是坏版本与旧句柄并存：本版先检查版本，返回 `EINVAL` 而不是 `ESTALE`（见[例 16.2.1](ch16.md#ex-16.2.1) 的 ① 与 ④）。调用者只应依赖文档允许的错误集合；要精确诊断，应增加专门诊断能力。对照[定义 16.2.3](ch16.md#def-16.2.3)。

:::

::: ex A5 · 守卫与义务的分界线（主线 ①） {#ex-16.A.5}

把下面八个前提分成两栏：入口能查 / 只能写进头文件。非空、对齐、长度上限、整段属于同一分配、元素已初始化、与本次其他参数无重叠、返回前分配不失效、输出不是只读页。

::: sol 解答

入口能查：非空、对齐、长度上限（含乘法与 `start + bytes` 不绕回）、本次参数区间两两不相交。
只能写进头文件：整段属于同一分配、元素已初始化、返回前分配不失效、输出不是只读页或失效对象。
另外两条属于同一栏的判断也要说清：「所有 `u64` 位模式（任意取值）都有效」不等于未初始化字节可以读；地址不溢出也不代表区间来自一个分配。
这些合起来就是[定义 16.3.2](ch16.md#def-16.3.2) 的五条义务，正文 16.3.4 那张表把八行逐条对到了「入口能检查什么 / 调用者仍须保证什么」。

:::

::: ex A6 · 身份不是权限（主线 ①） {#ex-16.A.6}

为什么知道一个句柄数值的人就能释放它？代号设计防的是什么、不防什么？把句柄写进文件跨进程用，会得到什么结果？

::: sol 解答

句柄只是一个 `u64`，`rb_release` 不校验「你是不是创建者」，所以拿到数值的人就能消费它。
代号防的是误用旧生命期：槽复用时代号加一，旧数值过不了第二关；它不防恶意猜测，外部授权必须另行设计。
把句柄写进文件、换一个进程或另一个加载实例后没有意义；静态库若被分别链接进不同模块，甚至可能有不同的注册表实例——单调性只在单个实例内成立。对照[定义 16.4.1](ch16.md#def-16.4.1) 与 [16.4.8 身份不是权限](ch16.md#sec-cpp-rust.4.16.4)。

:::

::: ex A7 · 三条出口与两种锁后果（主线 ①） {#ex-16.A.7}

`boundary` 为什么要把「失败必须是整数码」写成类型要求？`EPANIC` 与 `EPOISON` 的恢复动作为什么不同？

::: sol 解答

`boundary` 收一个返回 `Result<(), i32>` 的闭包：闭包正常完成给 `OK`，闭包返回错误给对应整数码，捕获到展开给 `EPANIC`。入口作者不必在每个分支记得返回错误，闭包根本无法用别的方式失败。
`EPANIC` 只说明捕获到了展开：panic 发生在取锁之前，注册表仍可用；发生在持锁期间，锁才可能被毒化。
`EPOISON` 说明锁已被毒化，内部状态可能只改了一半，所以统一拒绝服务直到按运维流程重启，不用 `into_inner` 强行解锁。两者恢复动作不同，因为一个是「这次调用炸了」，另一个是「这份状态不能再信」。对照[定义 16.5.1](ch16.md#def-16.5.1)、[定义 16.5.3](ch16.md#def-16.5.3)。

:::

## B 组 · 推理（8–15）

每组都按同一格式作答：**被破坏的不变量 → 接住它的守卫在函数体哪一步 → 返回码 → 输出或句柄有没有被改动**。

::: ex B8 · 同一个首地址既当输入又当输出（主线 ①） {#ex-16.B.8}

C 契约测试里的 `input` 与 `output` 都是真实存在的活对象。现在调用 `rb_transform(input, input, 4)`，把同一个首地址同时当输入和输出。返回什么？程序有没有可能已经读到一半？

::: sol 解答

被破坏的是排他访问：同一块存储既做只读借用又做独占借用。
顺序是 `checked_len(4)` 通过 → `separate(range(input, 4), range(input, 4))` 得到 `a.0 < b.1 && b.0 < a.1` 成立 → 返回 `EINVAL`。
两次 `range` 只算了整数，`from_raw_parts` 从未被调用，所以不存在「读到一半」的状态。
这也解释了负面测试怎么写：用真实数组的相同首地址验证守卫，而不是执行一个未定义行为版本看它崩不崩（[例 16.3.1](ch16.md#ex-16.3.1)）。

:::

:::

::: ex B9 · 版本与尺寸各差一格（主线 ①） {#ex-16.B.9}

长度 3 的对象上依次调用 `rb_info(h, 2, sizeof(info), &info)` 与 `rb_info(h, 1, sizeof(info) - 1, &info)`。两次各返回什么？`info` 有没有被写？第二个调用为什么不能被当成「前缀兼容」？

::: hint 提示

先问 `rb_info` 函数体的第一条判断是什么，它排在句柄查找和 `range(out, 1)` 之前还是之后。

:::

::: sol 解答

两次都返回 `EINVAL`（1），`info` 一个字节都没写，仍是调用者的原值。
被破坏的是输入协商：版本必须是 1，尺寸必须恰好等于 24。
传 23 不会被当成前缀兼容而少写一格：本版不支持「旧调用者自动忽略新尾字段」，要支持前缀兼容得先定义最小尺寸与写入上界，那是新设计而不是把一个等号改成大于等于。对照[定义 16.2.2](ch16.md#def-16.2.2)、[例 16.2.1](ch16.md#ex-16.2.1)。

:::

:::

::: ex B10 · 容量只有一半（主线 ①） {#ex-16.B.10}

长度 3 的对象，`short_out` 只有 2 格，`written` 预置为 777，调用 `rb_copy(h, short_out, 2, &written)`。返回什么？两个输出变了吗？句柄还能用吗？

::: hint 提示

`rb_copy` 里先验证容量，还是先 `copy_nonoverlapping` 再写 `written`？

:::

::: sol 解答

返回 `ECAPACITY`（4）。
`short_out` 两格与 `written` 的 777 都保持原值：容量判断排在 `copy_nonoverlapping` 之前，也排在 `written.write` 之前。
句柄没有被消费，随后仍可正常查询或复制，最后 `rb_release` 返回 `OK`。
被破坏的是「容量必须覆盖完整对象」。Rust 契约测试里用的是 999/888 哨兵，结论一样（[例 16.2.1](ch16.md#ex-16.2.1) ③、[例 16.5.1](ch16.md#ex-16.5.1) ②）。

:::

::: ex B11 · 释放之后再查一次（主线 ①） {#ex-16.B.11}

在 B9 的两次误用之后再 `rb_release(h)`，然后调用 `rb_info(h, 1, 24, &info)`。返回什么？前面那两次 `EINVAL` 有没有让这次释放变复杂？

::: sol 解答

返回 `ESTALE`（3）：槽里已经没有所有者，这一关在代号比较之后的同一把锁内完成。
前面两次 `EINVAL` 没有消费句柄，所以那次 `rb_release` 才是唯一一次成功释放，返回 `OK`。
换句话说，四次误用里只有 `rb_release` 动了所有权，其余三次只被拒绝。
清理规则因此可以写得很直：创建成功才算拥有，查询失败照常释放并检查返回值（[例 16.2.1](ch16.md#ex-16.2.1)、[16.5.5](ch16.md#sec-cpp-rust.4.16.5)）。

:::

::: ex B12 · 十二个线程抢着释放（主线 ①） {#ex-16.B.12}

`h2` 有效，另起 12 个线程同时调用 `rb_release(h2)`。给出结果分布，并说明若把「检查槽里还有没有数据」挪到锁外会出什么问题。

::: sol 解答

恰好一个线程拿到 `OK`，其余 11 个看到 data 已空，各得 `ESTALE`。
锁内 `take()` 是唯一的线性化点（操作在语义上真正发生的那一瞬）：取走所有者发生在这一刻，锁外 `drop` 只是清理成本。
若把检查挪到锁外，两个线程可能同时看到「还有数据」，于是两块都自认为是最后所有者、各自析构一次同一个分配——正是代号句柄要消除的那种双重析构。
判断和取走必须在同一把锁内完成，也不能把检查结果缓存成一个长期裸槽指针（[定义 16.4.3](ch16.md#def-16.4.3)、[例 16.4.1](ch16.md#ex-16.4.1) ⑤）。

:::

::: ex B13 · null 与未对齐各被哪一关接住（主线 ①） {#ex-16.B.13}

三条调用：`rb_transform(NULL, output, 1)`、`rb_transform(NULL, NULL, 0)`、把 24 字节数组里一个未对齐地址传给 `rb_transform(misaligned, output, 1)`。各自的返回码与被触发的判断是什么？

::: hint 提示

`range` 的第一条分支是 `len == 0`，它在 null 与对齐检查之前。

:::

::: sol 解答

第一条返回 `EINVAL`：`range(output, 1)` 里 `len != 0`，于是检查 null 那一侧，被破坏的是非空。
第二条返回 `OK`：零长数据先放行，null 在这里合法，而且 `from_raw_parts` 不会被调用——C 的 null 不会被塞进空切片。
第三条返回 `EINVAL`：入口在 `range` 里用 `is_multiple_of(align_of::<u64>())` 拒绝，没有形成 `u64` 引用，也没有在 C 里做可能违反对齐要求的指针类型转换。
三者的共同点是守卫全部在形成引用之前（[例 16.3.1](ch16.md#ex-16.3.1)、[16.3.2](ch16.md#sec-cpp-rust.4.16.3)）。
注意第二条只对数据区域成立：输出句柄、`written` 与 `InfoV1` 永远是完整可写对象，不接受 null。

:::

::: ex B14 · 探针（故意 panic 的测试入口）跑过之后还能调用，能证明什么（主线 ④） {#ex-16.B.14}

C 测试调用 `rb_test_panic()` 拿到 `EPANIC`，随后同一进程里的查询照常成功。有人据此写「poison 恢复路径已验证」。这句话对在哪、错在哪？

::: sol 解答

对在：这一次 panic 确实没有留下毒化锁，后续调用正常。
错在：探针在取得注册表锁之前故意 panic，从未毒化注册表；全局 poison 只有局部 Mutex 的确定性测试覆盖，服务级恢复没有被验证。
两件事没有因果关系，把「C 侧后续调用正常」解释成「全局 poison 已恢复」是高估覆盖。
当前的毒化策略是保守停止：映射成 `EPOISON` 并拒绝继续解释注册表状态（[定义 16.5.3](ch16.md#def-16.5.3)、[例 16.5.1](ch16.md#ex-16.5.1)）。

:::

::: ex B15 · 两个差值各量了什么（主线 ②） {#ex-16.B.15}

两句发布说明：①「一次跨边界调用成本 0.766755 ns」；②「省下的 0.282651 ns/word 就是一次 memcpy 的成本」。各错在哪？各给一句正确表述。

::: hint 提示

先问两条路径分别计入了哪些工作；再看这两个数是「每词聚合差」还是「单次操作的耗时」。

:::

::: sol 解答

① 错在命名。0.978652 − 0.211897 = 0.766755 是每词聚合成本之差，差值里同时含调用次数、每词错误码分支与守卫摊销的变化，两条路径的优化范围也不同。正确表述：「在固定工作量、固定构建下，本夹具的批量聚合成本约为逐元素的 1/4.6。」
② 错在三处：差值里不止复制，copy_out 还要在 C 侧遍历完整 output 求和，owned_handle 在 `rb_info` 内完成同一归约；0.282651 是每词聚合差，不是一次 memcpy 的耗时；两条路径都付了生成、分配、注册表、`Arc::from(Vec)` 内部复制与释放。正确表述：「差值只能说明『导出并遍历』这一段的量级，本轮没有单独测 memcpy 吞吐。」（[例 16.7.1](ch16.md#ex-16.7.1)、[例 16.8.1](ch16.md#ex-16.8.1)）

:::

## C 组 · 实操（16–20）

::: ex C16 · 写一张发布前 FFI 检查清单（主线 ④） {#ex-16.C.16}

为 `projects/ffi-bridge/` 写一张七条的上线前检查清单。每条要有：检查什么、用什么命令或文件判定、不合格时说明什么。不能只写「已检查」。

::: sol 参考路径

① 干净目录复现：离线且 `--locked` 跑 `cargo fmt --check`、clippy（`-D warnings`）、`cargo test`、CMake 配置与构建、`ctest`。
② 链接是真的：C 可执行文件确实链接 Rust 静态库；把 Rust 目标从构建里拿掉，C 应当链接失败。
③ 两侧布局都编译过：Rust 的 `size_of`/`align_of`/`offset_of!` 断言与头文件 `_Static_assert` 同时存在，数值是 24、对齐 8、偏移 0/4/8/16。
④ 断言没被 Release 删掉：三个 C 目标带 `-UNDEBUG`，benchmark 用显式分支校验返回码与 checksum。
⑤ 探针不进发布物：换新构建目录并设 `RB_TEST_HOOKS=OFF`，确认 `rb_test_panic` 不导出。
⑥ 代码生成对得上入口：保存 MIR / LLVM IR / 汇编，按层核对守卫、调用与同步路径。
⑦ 条件写进证据：工具链、目标三元组、优化配置、宿主与 cacheline 都归档。
以上七条就是 [16.6 发布前 FFI 交付检查](ch16.md#sec-cpp-rust.4.16.6) 那张判定流程；第 ② 条的依据是[定义 16.6.1](ch16.md#def-16.6.1)。

::: ex C17 · 从空目录把这条链跑一遍（主线 ④） {#ex-16.C.17}

写出构建与测试的完整命令序列。再回答：发布构建与测试构建差在哪两处？为什么三个 C 目标都要 `-UNDEBUG`？

::: sol 参考路径

在 `projects/ffi-bridge/` 里按顺序执行：

```bash
cargo fmt --check
cargo clippy --offline --locked --all-targets --features test-hooks -- -D warnings
cargo test --offline --locked --features test-hooks
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DRB_TEST_HOOKS=ON
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
./build/bridge_demo 42 8192
```

发布构建的两处差别：换一个新的构建目录，并设置 `RB_TEST_HOOKS=OFF`，使 `rb_test_panic` 不导出。Rust 单独构建时不启用该 feature 即不导出探针。
`-UNDEBUG` 的作用是让 Release 模式里的校验 assert 真正执行；若 `-DNDEBUG` 把 checksum 相等断言删掉，就失去了部分夹具验证（[16.6.2](ch16.md#sec-cpp-rust.4.16.6)）。
清单之外还有一条动作值得单独写：故意把 Rust 目标从 CMake 里去掉一次，确认 C 侧链接失败，否则「集成成功」只是两份构建并排跑过。

::: ex C18 · 空对象的完整链（主线 ①） {#ex-16.C.18}

依次执行 `rb_create_copy(NULL, 0, &h)`、`rb_copy(h, NULL, 0, &n)`、`rb_release(h)`，写出每步返回码与 `n` 的值。再说明：既然零长数据可以传 null，为什么 `&h` 与 `&n` 不能是 null？

::: hint 提示

数据区域与元数据输出在文档里是两条分开的规则，先数清这条链里有几个「完整可写对象」。

:::

::: sol 解答

三步都成功：`rb_create_copy(NULL, 0, &h)` 返回 `OK` 并写出一个有效句柄；`rb_copy(h, NULL, 0, &n)` 返回 `OK` 并把 `n` 写成 0；`rb_release(h)` 返回 `OK`。
元数据输出不是空数组：输出句柄、`written` 和 `InfoV1` 始终要求一个完整可写对象，不能用「这次没有数据」解释为什么输出句柄指针可以是 null。
两处规则在文档里分开写，才不会被「既然数据那里可以」类推过去。空对象的完整创建、复制和释放链在测试里有覆盖（[16.3.2 空数据不构造空指针切片](ch16.md#sec-cpp-rust.4.16.3)）。

::: ex C19 · 把归约从模加换成取最大值（主线 ②） {#ex-16.C.19}

调用者说「checksum 对我没用，我要每个对象的最大元素」。按本章的接口，这个需求要动哪里？16.8 的 0.358854 还能不能引用？

::: hint 提示

先查 `InfoV1` 里有几个字段，再决定是改结构还是加版本；然后问本轮实测采过哪种归约。

:::

::: sol 参考路径

先看 ABI：`InfoV1` 的四个字段是 `abi_version`、`struct_size`、`len`、`checksum`，没有位置放最大值。改字段属于破坏已发布结构的偏移，只能定义 v2 结构或新入口，v1 的定义与「尺寸恰好 24」的检查保持不变。
再谈测量：本轮只采集了模加 checksum 这一种归约，0.358854 描述的是「generate → info → release、归约在 info 内」这一条路径的聚合成本；换成取最大值没有被测过，不能沿用。
结构性的结论仍然成立：归约留在组件内、只交摘要、完整数组不离开组件——这正是[定义 16.8.2](ch16.md#def-16.8.2) 的接口形态。报告时要写清消费位置，而不是报一个「新归约更快」。

:::

## 批改时最常给的三条意见

1. **把聚合差写成单次成本。** 0.766755 与 0.282651 都是每词聚合差，分母是 524288 个词，不是一次调用或一次 memcpy。先改句子，再改表。
2. **责任句只写了一半。** 只说「Rust 分配」不写「谁释放」、只说「返回句柄」不写「失败后谁清理」，等于没写。用[定义 16.1.2](ch16.md#def-16.1.2) 的三问逐条补齐。
3. **检查排在引用之后。** 先 `from_raw_parts` 再判 null、先复制再查容量，都属于把守卫写成了事后说明；另外「越界大概会崩」不构成负面测试。对照[例 16.3.1](ch16.md#ex-16.3.1) 与[例 16.5.1](ch16.md#ex-16.5.1)。
