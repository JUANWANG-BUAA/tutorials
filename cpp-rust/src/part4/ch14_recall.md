# 第14章 · 闭卷回忆卡

「看懂」只说明答案在眼前时能识别；评审和发布要的是从空白纸上提取。这一页把第十四章拆成 23 张卡，每张卡先写卡面问题，合上正文自己答，再展开核对。

**用法与节奏**

| 时点 | 做什么 | 判定 |
|:--|:--|:--|
| 学完当天 | 第一组「定义卡」9 张 | 关键词写全才算 ✓ |
| 第 1 天 | 第二组「结论卡」8 张 | 能说出数字的出处与限制才算 ✓ |
| 第 3 天 | 第三组「第一行卡」6 张 | 写出第一步动作才算 ✓ |
| 第 7 天 | 只重做标成 △ 和 × 的卡 | 全对即可进入第十五章 |

每张卡给自己一个记号：✓ 一次说对；△ 说对一半或要提示；× 想不起来。只重做 △ 和 ×，不要把整叠卡反复过一遍——那是在读，不是在提取。凡是卡面要求报数字的，答完必须补一句「这个数只在哪个边界下成立」。

## 第一组 · 定义卡（说全称与前提）

::: ex 卡 1 · 构建身份 {#rc-14-1}

卡面：构建身份指什么？说出它的六个层次，以及「记全」的判据。

::: sol 核对

指共同决定这一次产物的一整组输入及其派生物。六层是：源文件加清单加锁文件；包选择加 feature 闭包加 target 加 profile；rustc 与 Cargo 加标准库加链接器加 SDK 加构建脚本输入；对象、IR、调试信息与链接产物；二进制指纹加运行输入加环境与原始观察；门禁与发布裁决。记全的判据是事后能指认到具体文件或具体命令输出，不是「我们一直用 stable」。对照[定义 14.1.1](ch14.md#def-14.1.1)。
:::

:::

::: ex 卡 2 · 产物指纹 {#rc-14-2}

卡面：产物指纹由哪两项组成？它能支撑哪两种判断，不能支撑什么？

::: sol 核对

最终二进制的哈希（本轮用 SHA256）加文件大小。它回答「这是不是同一个对象」：哈希相同可支撑「两次构建拿到同一份产物」，哈希不同只支撑「字节不同」。它不回答业务代码是否不同、更不回答运行是否更慢——路径、调试信息、链接顺序与时间戳都能改字节。对照[定义 14.1.2](ch14.md#def-14.1.2)。
:::

:::

::: ex 卡 3 · 三个旗标 {#rc-14-3}

卡面：`--locked`、`--offline`、`--frozen` 各承担什么责任？它们共同不承诺什么？

::: sol 核对

`--locked` 要求沿用锁文件、不许悄悄更新解析；`--offline` 只许用本地可用资源；`--frozen` 把前两者组合起来。三者都不是沙箱：`build.rs` 仍可能读外部文件或运行任意工具，也不承诺网络隔离、供应链审计或位级确定性。本轮显式采用 `--offline --locked`。对照[定义 14.1.3](ch14.md#def-14.1.3)。
:::

:::

::: ex 卡 4 · feature 闭包 {#rc-14-4}

卡面：feature 闭包由哪三样决定？它为什么不是清单里的那几行？

::: sol 核对

由显式请求的 feature、各依赖边的 `default-features` 设置、Cargo 对同一依赖的统一规则共同决定。生效的是沿依赖边传递后的并集，不是顶层写的那一行；某条边写 `default-features = false` 也不会撤销别条边启用的默认能力。要沿反向路径追踪，见 `cargo tree -e features -i` 类输出。对照[定义 14.2.1](ch14.md#def-14.2.1)、[例 14.2.1](ch14.md#ex-14.2.1)。
:::

:::

::: ex 卡 5 · 构建单元与观察型 feature {#rc-14-5}

卡面：同一包名为什么可能被编译多次？观察型 feature 的定义是什么、本轮哪个 feature 属于它？

::: sol 核对

构建单元是同一个包在一种编译条件组合下的一份实际构建；host 与 target、不同 feature 闭包、不同 profile、不同目标平台都可能各生成一份，所以锁文件的包条目数与编译次数是两个量。观察型 feature 只为实验增加可观察工作、不改变返回值语义；本轮的 `checked` 就是这一类，两版都只用安全 Rust，checksum 都是 133693440。对照[定义 14.2.2](ch14.md#def-14.2.2)、[定义 14.2.3](ch14.md#def-14.2.3)。
:::

:::

::: ex 卡 6 · 可复现三级 {#rc-14-6}

卡面：三级「可复现」各是什么？本轮成立到哪一级，谁把最强的那级证伪了？

::: sol 核对

第一级流程可重跑，第二级性能实验可比较，第三级位级产物相同。前两级成立对第三级没有任何蕴含。本轮只给前两级证据；每个配置 21 个目标目录、产物大小一致但 21 个 SHA256 全不同，第三级因此不成立。锁文件也不封存 SDK、链接器与 `build.rs` 的外部读取。对照[定义 14.3.1](ch14.md#def-14.3.1)、[定义 14.3.2](ch14.md#def-14.3.2)、[例 14.3.1](ch14.md#ex-14.3.1)。
:::

:::

::: ex 卡 7 · 缓存键 {#rc-14-7}

卡面：缓存键至少要区分哪几样？键过窄与过宽各有什么后果？

::: sol 核对

至少要区分目标平台、工具链版本、锁文件、feature 闭包与关键编译标志，构建脚本的外部输入也要适当纳入。键过窄会复用错误产物（例如同一提交的不同 profile 命中同一目录，fresh 被悄悄换成 noop）；键过宽则失去复用价值。性能证据归档不能住在可被驱逐的 CI 缓存里。对照[定义 14.3.3](ch14.md#def-14.3.3)。
:::

:::

::: ex 卡 8 · 两种缓存边界与计时边界 {#rc-14-8}

卡面：fresh 与 noop 各测什么？一次完整 `cargo build` 的墙钟里，哪些进、哪些不进？

::: sol 核对

新包目标目录构建（fresh）每次给一个不存在的 `--target-dir`，本包编译与链接必须重做，但源码、工具链、标准库与 OS 缓存都在，所以不能叫完全冷构建。无操作构建（noop）在同一目标目录、同一命令、源码与标志不变的前提下再跑，测的是「判断要不要重建」的成本，也不等于改一个文件后的增量构建。墙钟进：Cargo 启动与检查、本包编译、链接、`-vv` 日志；不进：标准库与 rustc 构建、下载、大小与 SHA256 读取、correctness 运行。对照[定义 14.4.1](ch14.md#def-14.4.1)、[定义 14.4.2](ch14.md#def-14.4.2)、[定义 14.4.4](ch14.md#def-14.4.4)。
:::

:::

::: ex 卡 9 · CGU 与 LTO 档位 {#rc-14-9}

卡面：CGU 是什么？`lto = false`、`"thin"`、`"off"` 三种写法各是什么语义？哪两种最容易混？

::: sol 核对

CGU 是编译器把 crate 切开并行处理的粒度：单元多则单件小、可并行，但跨单元优化视野变窄；单元为 1 视野最大、串行压力也最大。`false` 允许对本地 crate 的 CGU 做 thin local LTO（`codegen-units = 1` 或 `opt-level = 0` 时不执行），`"thin"` 显式启用跨 crate ThinLTO，`"off"` 才是关闭。`false` 与 `"off"` 不是同义词。对照[定义 14.4.3](ch14.md#def-14.4.3)。
:::

:::

## 第二组 · 结论卡（说清数字的出处与限制）

::: ex 卡 10 · 21 个不同 SHA256 说明了什么 {#rc-14-10}

卡面：release 一行 21 份产物同为 518448 字节、21 个不同 SHA256。这证伪了哪一级？对另外两级说了什么？

::: sol 核对

证伪第三级：本轮没有跨这 21 个目标目录产生字节相同的产物。对第一级偏正面——21 次都构建成功、大小相同、`verify-*.txt` 的 checksum 一致；对第二级不表态，可比较性靠实验契约，与字节是否相同无关。本轮没有对差异字段作二进制归因，所以不能断言「全是时间戳」或「全是路径」。对照[例 14.3.1](ch14.md#ex-14.3.1)。
:::

:::

::: ex 卡 11 · 两种边界的量级 {#rc-14-11}

卡面：fresh 与 noop 的均值各在什么范围？one 相对 release 快还是慢，这推翻了哪句口号？

::: sol 核对

fresh 是 338–1996 ms（release 439.733、one 338.194、thin 1995.882），noop 三个 profile 都在 18 ms 附近（18.194–18.713），按均值算 one 约 18 倍、release 约 24 倍、thin 约 110 倍。本轮 one 比 release 更快完成新包目标目录构建，推翻了「更多 CGU 必然编译更快」；小包中划分、优化与链接的固定成本可能压过并行收益，本轮未分离这些阶段，给不出百分比分摊。对照[定义 14.4.1](ch14.md#def-14.4.1)、[例 14.4.1](ch14.md#ex-14.4.1)。
:::

:::

::: ex 卡 12 · thin 的兑换 {#rc-14-12}

卡面：thin 相对 release 多花多少构建时间、换来多少代码段？为什么不能直接写「应默认开」？

::: sol 核对

新包目标目录均值 1995.882 ms 对 439.733 ms，约 4.5 倍；`__text` 236656 字节对 242940 字节，约小 2.6%。这是两个预算之间的兑换，不是单向改进：缺事先写下的构建时间预算与体积预算，缺运行性能证据（本节没采集），也缺范围声明（`publish = false` 的单包小二进制）。对照[例 14.4.2](ch14.md#ex-14.4.2)。
:::

:::

::: ex 卡 13 · 会失败的候选 {#rc-14-13}

卡面：构造回退要满足哪三条？`checked` 相对 default 的批均值是多少，比值几倍，门禁判什么？

::: sol 核对

三条：输出与基线等价、不引入未定义行为、成本差异来自可解释的额外工作。default 批均值 0.042857、checked 0.225888 ns/byte，比值约 5.27，预算是 20%，远超 1.20，门禁拒绝、退出码 1，记入 `gate-rejection.json`。这是描述性预算判定，不是显著性结论。对照[定义 14.5.1](ch14.md#def-14.5.1)、[例 14.5.1](ch14.md#ex-14.5.1)。
:::

:::

::: ex 卡 14 · 三种退出状态 {#rc-14-14}

卡面：退出码 0、1、2 各表示什么？为什么不能压成一个红灯？

::: sol 核对

0 = 通过（21 轮齐全、单位与 checksum 一致、比值在预算内）；1 = 拒绝（证据有效但超预算）；2 = 证据不可比（样本缺失，或格式、单位、校验不一致）。压成一个红灯就分不清该修性能还是修采集。退出码 2 比第 1 章的「证据不足」更早一步：那里是数据齐了但区间跨过预算，这里是证据本身不成立。对照[定义 14.5.3](ch14.md#def-14.5.3)、[定义 14.7.2](ch14.md#def-14.7.2)。
:::

:::

::: ex 卡 15 · PGO 的四个阶段 {#rc-14-15}

卡面：四个阶段是什么？哪两份产物的墙钟不能混用，为什么？

::: sol 核对

生成带插桩的程序、用训练输入运行、用匹配的 `llvm-profdata` 合并、用合并数据重编译并验证。插桩版（`-Cprofile-generate`）的任务是产出数据，不代表性能；最终版（`-Cprofile-use`）的耗时才可能与基线比。插桩本身改变执行成本，把插桩版耗时写进报告等于把测量工具当成被测对象。对照[定义 14.6.2](ch14.md#def-14.6.2)。
:::

:::

::: ex 卡 16 · 语料与留出集 {#rc-14-16}

卡面：训练语料决定什么？训练与评估用同一份输入，结论变成了什么？

::: sol 核对

训练语料是喂给插桩版的输入与参数连同运行顺序，它决定优化器看到哪些分支热、哪些冷，也决定收益上限。训练集同时充当留出集时，测到的是对这组输入的记忆效果，不是泛化；这与把探索性极值当成确认性结论是同一类错误。数据太少无法切分时就写「本轮不能评估泛化」。对照[定义 14.6.3](ch14.md#def-14.6.3)、[定义 14.6.4](ch14.md#def-14.6.4)。
:::

:::

::: ex 卡 17 · 四层门禁 {#rc-14-17}

卡面：四层各检查什么？为什么顺序不能颠倒？独立重跑验证的是哪件事？

::: sol 核对

构建、格式化与测试 → 轮数、单位、checksum、身份 → 预算比值 → 独立重跑与人工裁决。前一层失败时后一层没有合法输入；任何一层用默认值补上，都会把失败伪装成通过。独立重跑由另一个执行者、在另一段时间或另一台机器上按同一协议采集，验证流程可复现与条件依赖，不验证同一份 CSV 的重算。对照[定义 14.7.1](ch14.md#def-14.7.1)、[定义 14.7.3](ch14.md#def-14.7.3)。
:::

:::

::: ex 卡 18 · 基线与契约测试 {#rc-14-18}

卡面：基线是什么、不是什么？契约测试证明到什么范围？

::: sol 核对

基线是经过认可的特定产物与协议，至少绑定产物指纹、构建身份与采集协议；它不是上一次跑出来的最好值，每次通过就自动改基线会改变比较含义。契约测试只针对明文写下的少数性质断言：输出等价、边界输入、错误拒绝；它证明这几条性质在本轮产物上成立，不证明系统在所有情况下正确，测试条数也不等于覆盖。对照[定义 14.8.1](ch14.md#def-14.8.1)、[定义 14.8.3](ch14.md#def-14.8.3)。
:::

:::

## 第三组 · 第一行卡（只写第一步）

这一组练的是「一离开答案就不知道第一行写什么」那个毛病。每题只写第一行动作，不计算。

::: ex 卡 19 · 同一提交、数字却变了 {#rc-14-19}

卡面：CI 报昨天 340 ms、今天 460 ms，提交与锁文件没变。第一行写什么？

::: sol 核对

第一行：按六层逐项核对第二、三层——feature 闭包与 profile（含 CGU/LTO/incremental），rustc 与 Cargo 完整版本、LLVM 版本、`RUSTFLAGS` 与 wrapper 是否被覆盖；再问缓存边界是全新目标目录还是复用 target。三项对齐之前不谈数字。对照[定义 14.1.1](ch14.md#def-14.1.1)、[定义 14.1.3](ch14.md#def-14.1.3)。
:::

:::

::: ex 卡 20 · 构建只用 18 ms {#rc-14-20}

卡面：有人拿 18 ms 说「CI 构建很快」。第一行写什么？

::: sol 核对

第一行：先给这个数字贴边界标签——它是 noop，只证明 Cargo 检查了已有产物，不是重建成本。要评价构建速度得看 fresh（338–1996 ms），并写明是否命中缓存。对照[定义 14.4.2](ch14.md#def-14.4.2)、[定义 14.4.1](ch14.md#def-14.4.1)。
:::

:::

::: ex 卡 21 · 两个均值差 101 ms {#rc-14-21}

卡面：release 439.733、one 338.194，有人写「one 快 101 ms」。第一行写什么？

::: sol 核对

第一行：问这两个数是不是配对差值。本轮每轮都构建三个 profile、起点按轮旋转，轮就是现成的配对单位；但归档摘要只做了按 case 的均值与分位数。所以先按 `round` 算逐轮差值，再和事先写下的预算比，而不是拿两个独立均值判方向。对照[例 14.4.1](ch14.md#ex-14.4.1)、[定义 14.4.5](ch14.md#def-14.4.5)。
:::

:::

::: ex 卡 22 · 门禁退出码 2 {#rc-14-22}

卡面：门禁返回 2，同事说「候选太慢，去优化」。第一行写什么？

::: sol 核对

第一行：先分清状态——2 是证据不可比（缺轮次，或单位、checksum 不一致），1 才是超预算。退出码 2 连「候选是否更慢」都还没回答，先补齐采集与身份记录。对照[定义 14.5.3](ch14.md#def-14.5.3)、[定义 14.7.2](ch14.md#def-14.7.2)。
:::

:::

::: ex 卡 23 · 同事说开了 PGO 快了不少 {#rc-14-23}

卡面：第一行写什么？

::: sol 核对

第一行：要训练语料与插桩版指纹、最终版与基线的各自身份（profdata 指纹与 profile-use 命令）、以及留出集上的结果与预算。缺任何一件，结论只能停在不可比较；「流程跑通了」不是收益证据。对照[定义 14.6.3](ch14.md#def-14.6.3)、[定义 14.6.4](ch14.md#def-14.6.4)。
:::

:::
