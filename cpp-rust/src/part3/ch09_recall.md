# 第9章 · 闭卷回忆卡

「看懂」只说明答案在眼前时能识别；评审和执行器排障需要的是从空白纸上提取。这一页把第9章拆成 26 张卡，每张先写卡面问题，合上正文自己答，再展开核对。

**用法与节奏**

| 时点 | 做什么 | 判定 |
|:--|:--|:--|
| 学完当天 | 第一组「定义卡」全部 8 张 | 关键词写全才算 ✓ |
| 第 1 天 | 第二组「结论卡」全部 10 张 | 能说清口径与前提才算 ✓ |
| 第 3 天 | 第三组「第一行卡」全部 8 张 | 写出第一步才算 ✓ |
| 第 7 天 | 只重做标成 △ 和 × 的卡 | 全对即可进入第十章 |

每张卡给自己一个记号：✓ 一次说对；△ 说对一半或要提示；× 想不起来。只重做 △ 和 ×，不要把整叠卡反复过一遍——那是在读，不是在提取。

## 第一组 · 定义卡（说全称与前提）

::: ex 卡 1 · 任务状态字 {#rc-09-1}

卡面：状态字至少把哪几类条件打包在一起？它的关键性质是什么，为什么不是「字段多」？

::: sol 核对

打包的是运行权、是否完成、是否已被通知、是否被请求取消、有没有人等待结果，以及引用计数。关键性质是**任何一次状态判断和状态改变都发生在同一次原子操作里**，不存在「先读到没在跑，再单独写下我开始跑」这种可被插队的两步。对照[定义 9.1.1](ch09.md#def-9.1.1)。

:::

:::

::: ex 卡 2 · 运行权与通知责任 {#rc-09-2}

卡面：这两条账各保证什么？它们能不能同时存在？合并成一位会丢什么？

::: sol 核对

运行权保证 Future 不会被两个线程同时 poll，任意时刻至多属于一个 worker，靠一次原子抢位取得。通知责任保证有效 wake 之后有人重新检查这个 Future，是一笔「欠一次 poll」的账，可以挂在队列项上，也可以挂在正在运行的 worker 上。两者可以同时存在（正在跑的任务被叫醒），合并就丢掉一次 poll。对照[定义 9.1.2](ch09.md#def-9.1.2)。

:::

:::

::: ex 卡 3 · 任务单元 {#rc-09-3}

卡面：任务单元包含哪几部分？为什么「一个分配不等于一个语义对象」？

::: sol 核对

包含状态字、Future 本体、输出区域、等待者的 `Waker`，以及把它们黏在一起的引用计数。队列项可以只是任务单元的一个引用，窃取迁移的是引用而不是 Future 的字节；「最后一个引用释放」与「Future 已被 poll 完」是两件事。对照[定义 9.1.3](ch09.md#def-9.1.3)。

:::

:::

::: ex 卡 4 · 丢失唤醒 {#rc-09-4}

卡面：写出丢失唤醒的判定标准；一笔通知账只能挂在哪里？

::: sol 核对

一次有效的 wake 已经发生，却没有被任何后续 poll 兑现，任务永久停在没人再看的状态。判定标准不是「有没有排过队」，而是「有没有人欠着一次 poll 且这笔账不会消失」：账要么挂在队列项上，要么挂在持有运行权的 worker 上，两边都不挂就是丢失唤醒。对照[定义 9.2.1](ch09.md#def-9.2.1)。

:::

:::

::: ex 卡 5 · 通知的同步义务 {#rc-09-5}

卡面：一次 wake 承担哪两件事？合并通知能省掉哪一件的哪一部分？

::: sol 核对

进展义务（保证未来有人再 poll）与可见性义务（保证 wake 之前发布的资源状态能被那次 poll 观察到）。合并能省掉进展义务里「再次入队、再加一个引用」的动作，不能省可见性义务——把两者混为一谈，就会在「不必排队」的掩护下删掉 Release 语义。对照[定义 9.2.2](ch09.md#def-9.2.2)。

:::

:::

::: ex 卡 6 · 就绪队列与窃取 {#rc-09-6}

卡面：就绪队列里装的是什么？work stealing 搬的是什么、改变的是什么？

::: sol 核对

就绪队列是持有「欠一次 poll」那些任务引用的容器，可以是全局一条、每 worker 各一条，或两者混合。窃取搬的是**任务引用**，不是 Future 的字节；它改变的是「谁来兑现这笔账」，进而改变后续访问该存储的 CPU。对照[定义 9.3.1](ch09.md#def-9.3.1)。

:::

:::

::: ex 卡 7 · 观察延迟与阻塞污染 {#rc-09-7}

卡面：观察延迟的起点与终点在哪一刻？阻塞 poll 污染需要共享状态或写错同步吗？

::: sol 核对

起点是通知真正发出的位置，终点是等待者被再次 poll 并恢复执行。污染指某个任务在自己的 poll 里执行阻塞调用，使执行线程无法回到执行器，从而推迟其他已就绪任务；它不需要共享状态，也不需要写错同步，被推迟的任务可以与阻塞任务毫无关系。对照[定义 9.6.1](ch09.md#def-9.6.1)、[定义 9.6.2](ch09.md#def-9.6.2)。

:::

:::

::: ex 卡 8 · 三个资源边界词 {#rc-09-8}

卡面：分别用一句话说清背压（让上游等一等或直接失败）、准入控制、许可寿命；判断有没有背压该问什么？

::: sol 核对

背压是下游处理不过来时让上游「产生」等一等或直接失败的机制，约束产生速度与在途数量，不只是某段缓冲区的大小。准入控制是在做昂贵工作**之前**先取得名额，事后的拒绝退不回已花的资源。许可寿命是凭证从取得到归还覆盖的时间段，必须罩住真实占用期，否则上界只是名义上的。判断背压要问「无处安放的请求最终会停在哪里」。对照[定义 9.7.1](ch09.md#def-9.7.1)、[定义 9.7.2](ch09.md#def-9.7.2)、[定义 9.7.3](ch09.md#def-9.7.3)。

:::

:::

## 第二组 · 结论卡（说清口径与前提）

::: ex 卡 9 · 2.602 与 0.750 能写什么 {#rc-09-9}

卡面：同一负载下单线程与 4-worker 的聚合 ns/step 是 2.602 与 0.750。能写哪一句、不能写哪两句？

::: sol 核对

能写：「在这个负载、这台机器、这次运行里，4-worker 的聚合 ns/step 更低，约为单线程的三分之一」。不能写「每次调用快了 3 倍」——聚合口径的倒数本来就允许小于一次调用的耗时；也不能写「窃取让并行度提高三倍」——本轮没有采集 steal 次数与成功率，窃取是推测而非观察。对照[定义 9.5.1](ch09.md#def-9.5.1)、[例 9.5.1](ch09.md#ex-9.5.1)。

:::

:::

::: ex 卡 10 · 13.633 µs 不是睡眠变快 {#rc-09-10}

卡面：两个分支都睡 20 ms，为什么 offload 的观察延迟只有 13.633 µs？inline 多出的约 3.658 ms 能拆开归因吗？

::: sol 核对

睡眠一步也没变短；变的是观察者要不要等它。offload 把睡眠挪到阻塞池，执行器线程得以立刻推进观察者，于是观察延迟从毫秒级掉到微秒级。3.658 ms 不能拆：20 ms 是申请值不是保证值，计时器粒度与桌面调度都可能加时间，本轮没有分段打点。对照[例 9.6.1](ch09.md#ex-9.6.1)。

:::

:::

::: ex 卡 11 · 21 个观察的 p99 {#rc-09-11}

卡面：inline 的观察 p99 是 25.060 ms，这个数在说什么、不在说什么？

::: sol 核对

21 个观察上 `ceil(21 × 0.99) = 21`，p99 就是最大值 25.060 ms。它说明这份样本里最慢的一次观察是多少，是样本身份的说明，不是对生产尾延迟的承诺；offload 的 p99 是 18.541 µs。报告尾部需要匹配尾部概率的样本设计。对照 [9.6.3](ch09.md#sec-cpp-rust.3.9.6)。

:::

:::

::: ex 卡 12 · 64 个槽挡不住无限 spawn {#rc-09-12}

卡面：每个请求先 `spawn`，再在任务里 `send` 到 `channel(64)`。内存上界由什么决定？

::: sol 核对

由「已创建任务数 × 每个任务持有的量」加「通道里已有的 64 条消息」决定，与 64 无关。三步核对：谁在等待（所有还没成功发送的任务）、等待者持有什么（请求正文、连接引用、上下文）、边界覆盖哪一段（只覆盖已进入缓冲的消息）。要被 64 约束住，得把准入移到 `spawn` 之前。对照[例 9.7.1](ch09.md#ex-9.7.1)。

:::

:::

::: ex 卡 13 · 许可随调用方释放会超卖 {#rc-09-13}

卡面：复述那条「安全 Rust 里完全合法却超过设定并发」的序列，并给出修复。

::: sol 核对

异步任务取得 permit → 提交 `spawn_blocking` → 异步任务超时并被丢弃 → permit 随异步任务释放 → 阻塞闭包仍然运行 → 新请求取得刚释放的 permit → 实际阻塞并发超过设定值。修复：把 owned permit 移进闭包，调用方被取消时许可仍由正在运行的工作持有，闭包结束才归还。对照[定义 9.7.3](ch09.md#def-9.7.3)。

:::

:::

::: ex 卡 14 · 加 worker 不等于修复 {#rc-09-14}

卡面：「把 current-thread 换成 4 个 worker 就修好了阻塞 poll。」这句话对在哪、错在哪？

::: sol 核对

对的部分：可被占满的线程数从 1 变成 4。错在把扩容当成修复：阻塞任务的个数随并发增长，四个同时阻塞的任务照样能把四个 worker 全占住，污染只是从「必然」变成「看负载」。修复是把有限阻塞工作移到合适的执行域，并控制那个域的并发、队列与取消策略。对照[思考 9.6.1](ch09.md#think-9.6.1)。

:::

:::

::: ex 卡 15 · 公平性不是轮流 {#rc-09-15}

卡面：公平性承诺什么？依赖哪两个前提？它的常见失效形式叫什么？

::: sol 核对

承诺的是「在一定前提下，一个已经被唤醒的任务不会永远等不到 poll」，即关于等待上界的一类保证。前提是在途任务总数有上界、单次 poll 返回所需时间也有上界；它不承诺均匀轮流，也不给用户可配置的硬实时常数。失效形式是饥饿：某些就绪任务因策略偏向另一类任务而长期得不到执行。对照[定义 9.3.2](ch09.md#def-9.3.2)、[定义 9.8.1](ch09.md#def-9.8.1)。

:::

:::

::: ex 卡 16 · 只记总耗时看不出五类慢法 {#rc-09-16}

卡面：哪五类慢法在「到达→完成」的总耗时里长得一模一样？切开后各落在哪一段？

::: sol 核对

准入饱和、排队过长、阻塞 poll、外部资源慢、资源已就绪但任务恢复慢。分段后：准入饱和落在 arrival 到 admission_granted，排队落在 enqueued 到 execution_started，外部资源慢落在 arrival 到 resource_ready；阻塞 poll 落在 resource_ready 到 task_resumed（[例 9.8.1](ch09.md#ex-9.8.1) 第 ③ 行就是这么判的），「资源已就绪但任务恢复慢」说的也是这一段。只记首尾两点，几个总数可能相当接近，判定就退化成猜。对照[定义 9.8.3](ch09.md#def-9.8.3)、[例 9.8.1](ch09.md#ex-9.8.1)。

:::

:::

::: ex 卡 25 · 唤醒丢失的教科书版本 {#rc-09-25}

卡面：条件变量的 `signal` 为什么会丢？信号量为什么不会？这条判据搬到执行器上怎么写？

::: sol 核对

`signal` 时若没有线程在该条件变量的阻塞队列里，这次通知不起作用也**不会被记录**，先 `signal` 后 `wait` 就永远等下去；信号量把通知记进计数，`up` 先发生也不会丢（rCore 教程第八章「条件变量机制」）。搬到执行器：**问「通知落在哪里」，不要问「谁先谁后」**——落在计数或状态位（我们的 NOTIFIED）里就安全，只落在等待队列的调度动作上就可能丢（[9.2](../part3/ch09.md#sec-cpp-rust.3.9.2)、[@def-9.2.1]）。
:::

:::

::: ex 卡 26 · 被唤醒的任务立刻拿到线程吗 {#rc-09-26}

卡面：管程语义里 Hoare 与 Hansen 的区别，对应到执行器是哪一个问题？

::: sol 核对

Hoare 语义把锁直接转交给被唤醒者、唤醒者进紧急等待队列；Hansen 语义要等唤醒者退出管程。对应到本章：被 `wake` 的任务是立刻抢回线程，还是排到下一轮 poll。9.8 的公平性用的是后者——「谁先执行」是被选定的语义，不是实现巧合。
:::

:::

## 第三组 · 第一行卡（只写第一步）

这一组练的是「一离开答案不知道第一行写什么」那个毛病。每题只写第一行动作，不展开。

::: ex 卡 17 · 线上说「任务好像不跑」 {#rc-09-17}

卡面：第一行写什么？

::: sol 核对

第一行：查状态字里它被唤醒过吗、有没有丢失唤醒；再查同一条执行线程是否被阻塞 poll 占住；最后查那次 poll 到底返回了没有。以上都排除，才怀疑队列形状与公平性参数。对照 [9.8 判定流程](ch09.md#sec-cpp-rust.3.9.8)。

:::

:::

::: ex 卡 18 · 恢复延迟变长 {#rc-09-18}

卡面：第一行写什么？

::: sol 核对

第一行：核时间戳是不是在通知真正发出处创建的。在 `recv` 之后才开始计时，被阻塞的那一段已经被漏掉，量到的是「收到之后又花了多久」。对照[定义 9.6.1](ch09.md#def-9.6.1)。

:::

:::

::: ex 卡 19 · 报告写「聚合成本降到三分之一」 {#rc-09-19}

卡面：第一行写什么？

::: sol 核对

第一行：把口径与负载写全——ns/step、128 任务 × 8192 步、同一台机器同一次运行。然后才允许写「该负载下该配置的聚合成本更低」；单次调用延迟与窃取归因都不在这句话里。对照[例 9.5.1](ch09.md#ex-9.5.1)。

:::

:::

::: ex 卡 20 · 汇编里有 casal，要算同步占比 {#rc-09-20}

卡面：第一行写什么？

::: sol 核对

第一行：问这段 `casal` 动态执行了多少次、单次成本是多少。静态存在不等于动态次数，本轮也没有采集这两项，所以只能写「产物里保留了原子状态操作，其单次成本与总占比本轮没有采集」。对照[思考 9.4.1](ch09.md#think-9.4.1)。

:::

:::

::: ex 卡 21 · 要给一条资源链画上界 {#rc-09-21}

卡面：第一行写什么？

::: sol 核对

第一行：列资源行——通道缓冲、活跃请求、阻塞工作、子进程、结果历史，一行一种。然后每行填三格：谁持有、持有多久、上限在哪里；空格通常出现在最早上 `spawn` 或最早读正文的位置。对照 [9.7 判定流程](ch09.md#sec-cpp-rust.3.9.7)。

:::

:::

::: ex 卡 22 · 要写一个取消回归 {#rc-09-22}

卡面：第一行写什么？

::: sol 核对

第一行：先建立阶段关系——让任务发出一个「已进入」的信号，收到之后再 `abort`。否则测试会混进「还没开始 poll 就被取消」的情形，断言仍然成立但检验的对象已经不确定。对照[例 9.2.3](ch09.md#ex-9.2.3)、[9.2.5](ch09.md#sec-cpp-rust.3.9.2)。

:::

:::

::: ex 卡 23 · 要写退出 {#rc-09-23}

卡面：第一行写什么？

::: sol 核对

第一行：停止接受新工作、关闭提交入口。之后才是决定排空还是取消在途任务、逐个观察 `JoinHandle` / `JoinSet`、对阻塞工作发停止信号、等待外部资源回收，最后关闭执行域。对照[定义 9.8.4](ch09.md#def-9.8.4)。

:::

:::

::: ex 卡 24 · 要从 C 侧调异步提交接口 {#rc-09-24}

卡面：第一行写什么？

::: sol 核对

第一行：设计显式的 C ABI 与不透明句柄，写清所有权与释放责任。内部函数表不是可调用 ABI，本机 `size_of` 也不能当跨边界布局；panic 不能跨边界展开。对照 [9.4.3](ch09.md#sec-cpp-rust.3.9.4)。

:::
