## 11.1 互斥锁与无锁并发的真实分水岭 {#sec-cpp-rust.3.11.1}

本节回答一个问题：**有锁与无锁的分水岭画在哪里？**不是代码里有没有 `lock()`，也不是有没有 `while` 自旋，而是进度保证：某个线程被挂起时，系统整体还能不能前进。

::: preview 先抓住一件事

判断一个并发实现是不是「无锁」，只用一个场景：让正在持锁或正在重试的线程被操作系统无限期挂起。再看其余线程能否在有限步内完成操作。自旋锁在这个场景下直接失败——它连最弱的 Obstruction-Free 都不满足（[@def-11.1.2]）。
:::

### 11.1.1 互斥锁的悲观保护与代价构成

在多线程并发系统设计中，`std::sync::Mutex<T>` 代表一种经典的悲观互斥范式。它的哲学很直观：内部数据结构多么复杂都不重要，想读或改受保护的数据，必须先获取锁。拿到锁的线程因此获得排他性的访问权限。

在语义上，互斥锁把所有潜在并发的访问强制串行化，保证对共享状态的独占读写。这份绝对安全不是免费的。我们可以把它的开销解构为三个离散层次。第一层的核心现象值得先给一句定义：

::: def 定义 11.1.1 · 缓存行弹跳 Cacheline Bouncing {#def-11.1.1}

**缓存行弹跳**用一句大白话说：多个核心轮流争抢同一个缓存行的「写权限」。一个核心要写入，硬件必须先把它在其他核心 L1/L2 里的副本作废；下一个核心写入时又反过来作废前者。数据一个字节没多，所有权却像在核心之间来回弹跳，每一弹都是跨核总线流量。
:::

1. **原子状态争用与总线锁机制**：在用户态快速路径中，获取互斥锁通常依赖一条原子读-改-写指令（如 `CAS` 或带有 Release-Acquire 语义的原子交换）。数十个核心并发尝试执行这一指令时，硬件缓存一致性协议（如 MESI、MOESI 或 Directory-based 协议）被迫在各核心私有 L1/L2 缓存之间频繁传递该缓存行的所有权。这就是[@def-11.1.1]所说的缓存行弹跳。弹跳搬运的不是数据，而是写权限。每一弹都是一次跨核总线流量，于是流水线被强行排空，指令吞吐量迅速下降。

2. **内核态上下文切换（Context Switch）的断崖式开销**：现代操作系统的互斥锁绝非纯自旋。CPU 核心在长临界区里无谓空转，互斥锁自旋若干周期后就必然落入慢速路径。挂起当前线程要用操作系统底层原语（在 Linux 上对应 `futex(FUTEX_WAIT)`，在 macOS Darwin 上对应 `__psynch_mutexwait`）。线程挂起意味着当前核心先要保存全部用户态通用寄存器与浮点向量寄存器（CPU 里直接存取数据的那几个槽位），再陷入内核调度器。换人时还要寻找下一个就绪任务、加载新上下文。虚拟内存页表映射与 TLB（缓存「虚拟地址换物理地址」结果的那张对照表）状态也要重新建立。

   这里付的不是一条指令的价钱，而是一整次换人的价钱：单次上下文切换的物理耗时通常在 1,000 至 5,000 纳秒之间。当临界区本身仅需 10 纳秒执行时，这种等待挂起开销高出了临界区本身两到三个数量级。

3. **优先级反转与锁护送（Lock Convoy）**：如果持有互斥锁的线程被操作系统调度器由于时钟中断强行剥夺 CPU，所有排队等待该锁的其他线程将全部陷入停顿。停顿的起点不在锁，而在持锁者被换下。等待队列中哪怕包含极高优先级的实时任务，它也只能无助地等待低优先级线程重新获得调度并释放锁。更常见的是排队本身。多个优先级相近的线程在同一把锁上排队，由于唤醒与重获取锁的时间差，整个系统的吞吐量被迫降级至最慢线程的步调。

### 11.1.2 自适应互斥锁与自旋预算陷阱

为了缓解直接陷入内核的极端开销，现代高性能库（如 `parking_lot::Mutex`）通常采用自适应混合策略（Adaptive Mutex）：先在用户态以受控次数自旋（Spinning）。自旋超过预算阈值仍未获得锁，才真正发起 `futex` 系统调用（用户程序停下来请内核代做一步操作）休眠。自适应改变的是陷入内核的时点，不是把这一步取消。

```rust
// 自适应互斥锁的典型用户态抽象模型
pub struct AdaptiveMutex {
    state: std::sync::atomic::AtomicU32,
}

const UNLOCKED: u32 = 0;
const LOCKED: u32 = 1;
const PARKED: u32 = 2;

impl AdaptiveMutex {
    pub fn lock(&self) {
        // 1. 极速路径：无争用时单次原子 CAS 成功即走
        if self.state.compare_exchange(
            UNLOCKED, LOCKED, std::sync::atomic::Ordering::Acquire, std::sync::atomic::Ordering::Relaxed
        ).is_ok() {
            return;
        }

        // 2. 自适应自旋阶段：在多核硬件上允许适度循环探测
        let mut spin_count = 0;
        while spin_count < 100 {
            if self.state.load(std::sync::atomic::Ordering::Relaxed) == UNLOCKED 
                && self.state.compare_exchange_weak(
                    UNLOCKED, LOCKED, std::sync::atomic::Ordering::Acquire, std::sync::atomic::Ordering::Relaxed
                ).is_ok() {
                return;
            }
            std::hint::spin_loop(); // 下发 PAUSE / YIELD 降低能耗
            spin_count += 1;
        }

        // 3. 慢速路径：标记存在排队者并陷入操作系统内核
        while self.state.swap(PARKED, std::sync::atomic::Ordering::AcqRel) != UNLOCKED {
            // 系统调用：例如 sys_futex_wait(...)
            unsafe { self.sys_wait(); }
        }
    }

    unsafe fn sys_wait(&self) {
        // 操作系统相关挂起实现
    }
}
```

自适应策略在许多场景下表现极佳，但它把收益押在了「自旋预算」这个参数上。预算定小了，等于没有自适应；定大了，会引入两类对微架构特征敏感的浪费：

- **超线程/同步多线程（SMT）资源掠夺**：在支持超线程的 CPU 架构上，同一物理核心上的两个硬件线程共享执行单元。一个线程无节制的空转自旋会直接掠夺同物理核心兄弟线程的运算资源。省下的等待时间不是凭空消失，它可能以兄弟线程变慢的形式加倍付出去。
- **锁争用放大效应**：当并发线程数远超物理 CPU 核心数时，自旋几乎 100% 浪费时钟周期。因为持锁线程必须等待其他自旋线程被操作系统调度切出后，才有机会重新获得时间片完成临界区释放。

### 11.1.3 什么是「无锁」（Lock-Free）：三级进度阶梯

工业界常把「代码中没有写 `lock()` 的并发算法」通俗地称为「无锁」。这个说法经不起推敲。在严谨的系统工程与并发理论中，非阻塞算法（Non-blocking Algorithms）有着精确的形式化分类与进度保证（Progress Guarantees）分级：

::: def 定义 11.1.2 · 非阻塞进度保证三级阶梯 Non-blocking Progress {#def-11.1.2}

1. **无阻碍（Obstruction-Free）**：在任意给定的时刻，如果挂起或暂停系统中其他所有活跃线程，孤立运行的单个线程能够在自身有限步（Finite Steps）内完成其操作。这是非阻塞算法中最弱的形式。它不保证多线程并发时的系统进展，可能在两个线程相互干扰时产生无限活锁（Livelock）。

2. **无锁（Lock-Free）**：判定看系统全局，而不是盯单个线程。在系统全局范围内，无论线程调度如何交错，也无论某些线程是否被操作系统永久挂起、抢占或杀死，**必定至少有一个线程能够在有限步内完成操作并取得全局系统进展（Global Progress）**。在无锁系统中，单个线程可能遭遇饥饿，但整个系统永远不会陷入死锁或全局冻结。

3. **无等待（Wait-Free）**：**系统中的每一个活跃线程都必定能在自身有限步内完成操作并返回**，没有任何线程会被无限期推迟或饿死。这要求算法不仅消除了全局阻塞，还必须通过按轮协助（Helping Scheme）或状态分摊机制消除个体线程的饥饿风险。
:::

依据[@def-11.1.2]，很多常见的所谓「纯原子自旋锁」（SpinLock）具有如下实现：

```rust
// 伪代码示例：这绝非无锁算法！
pub struct SpinLock(std::sync::atomic::AtomicBool);

impl SpinLock {
    pub fn lock(&self) {
        while self.0.compare_exchange_weak(
            false,
            true,
            std::sync::atomic::Ordering::Acquire,
            std::sync::atomic::Ordering::Relaxed,
        ).is_err() {
            std::hint::spin_loop();
        }
    }

    pub fn unlock(&self) {
        self.0.store(false, std::sync::atomic::Ordering::Release);
    }
}
```

现在做那个唯一要紧的测试。线程 A 成功获取了该自旋锁，随后操作系统由于时间片耗尽将线程 A 挂起。在线程 A 重新被调度前，**没有任何其他线程能够取得系统进展**。这个场景不是刁难实现，它就是调度器每天在做的事。因此，自旋锁在数学上连 Obstruction-Free 都不满足，更绝非 Lock-Free。把「代码里有没有自旋 CAS」当成判据，得到的不是无锁，而是一个换了写法的悲观锁——盲区在于没做上面那个挂起测试。

::: think 思考 · 自适应锁也有自旋循环，为何不算违例？ {#think-11.1.1}

11.1.2 的 `AdaptiveMutex` 同样包含有界自旋。既然[@def-11.1.2]判自旋锁不合格，两段循环的区别到底在哪里？

::: sol 解答

差别不在「转了多少圈」，而在「转圈的人离开后，别人能不能继续」。`AdaptiveMutex` 的自旋只是把进入内核前的等待变短，临界区本身仍是排他持有——持锁者一挂起，系统照样停摆，进度等级不变。有界性只限制浪费的上限，不产生进展承诺。真正能跨过非阻塞门槛的，是「提交点收敛为单次原子 CAS、失败即让路重试」的结构（见[@def-11.1.3]）。两类自旋的对照耗时，本节没有采集。
:::

:::

### 11.1.4 硬件原子操作与推测重试的微架构本质

无锁数据结构的核心在于**推测执行（Speculative Execution）与原子提交（Atomic Commit）**。在无锁算法中，线程并不强求获得对整个数据结构的排他控制权，而是遵循以下步骤协同运作：

```text
[ 读取共享状态快照 ] ──► [ 局部计算目标新状态 ] ──► [ 单次原子 CAS 尝试提交 ]
                                                            │
                                  ┌─────────────────────────┴────────────────────────┐
                                  ▼ 成功                                             ▼ 失败 (被他人抢先)
                           [ 线性化点达成，退出 ]                             [ 丢弃推测结果，重读重试 ]
```

1. **快照读取**：线程在不阻碍他人的前提下，以轻量级原子载入（Load Acquire 或 Relaxed）读取当前共享状态的一个一致性观察点。

2. **私有推测**：这步工作落在线程私有的寄存器或栈帧里。基于刚刚读取的快照，计算数据结构的下一个合法拓扑（例如分配新节点、计算新指针）。
3. **单点裁决**：调用硬件提供的不可分割原子指令，尝试把新状态提交到全局可见内存。这类指令在 AArch64 上对应 `casal` 或基于 `ldaxr`/`stlxr` 的排他加载写回循环，在 x86_64 上对应带有 `lock` 前缀的 `cmpxchg`。
4. **失败回退**：若在此期间没有任何并发线程抢先写入，CAS 成功，操作瞬间完成并确立全局序；若其他线程抢先完成了写入，当前线程的 CAS 必然失败。此时线程不阻塞，也不是在等别人让路：它简单丢弃推测数据，重新载入最新状态并开启下一轮推测。

给这套循环一个名字：

::: def 定义 11.1.3 · 乐观重试 Speculative Retry {#def-11.1.3}

**乐观重试**指「读快照 → 私有推测 → 单点 CAS 提交 → 失败就重读再来」这套循环。它不阻塞任何人，代价是把冲突的处理推迟到提交失败之后。重试是无锁结构的常态，不是算法出错的信号；它换来的是什么，11.6 用实测数据回答。
:::

在微架构层面，多核处理器的缓存一致性协议（Cache Coherency Protocol）对这一过程起着决定性作用。在典型的 MESI 协议中，一个核心想要执行写入操作，必须先通过总线广播 `Read Invalidate` 请求。这条广播把所有其他核心私有 L1/L2 缓存里的那份副本标记为 Invalid，同时把它自身的缓存状态跃迁为 Modified。这里被作废的是别人手里的副本，不是那份数据本身。

当多个核心同时针对同一个指针执行 CAS 指令时，总线仲裁器（Bus Arbiter）会裁决某一个核心的请求优先到达。胜出的核心完成原子修改；落后的核心由于其本地缓存行被硬件强行失效，下一次载入将强制重新发起总线读取。原子提交的排他性与可见性，于是在硬件层面自然成立。

下表系统梳理了悲观互斥锁与无锁结构在微架构行为与工程特性上的根本差异：

| 维度 | 悲观互斥锁 (`Mutex<T>`) | 乐观无锁结构 (Lock-Free) |
|:--|:--|:--|
| **控制粒度** | 粗粒度：整个临界区时间段排他拥有 | 极细粒度：仅在单一原子指令生效瞬间仲裁 |
| **单核抢占影响** | 严重：持锁线程被抢占将直接阻断后续所有并发等待者 | 极小：任意线程停顿绝不阻断其他线程完成操作 |
| **硬件缓存压力** | 集中在锁字本身，频繁发生缓存行所有权无效化与弹跳 | 分散于数据节点与头尾原子指针，依争用拓扑而定 |
| **异常安全边界** | 复杂：持锁过程中若发生 panic，将引发锁中毒（Poisoning） | 优异：原生无锁中毒概念，未提交状态直接废弃 |
| **异步与中断兼容**| 严禁在不可阻塞的硬中断或异步 `poll` 中持互斥锁 | 若满足 Wait-Free，可安全在信号/硬中断上下文中执行 |
| **内存释放责任** | 简单自然：对象生命周期与锁范围 RAII 强绑定 | 极其严苛：必须引入专门的安全内存回收机制（SMR） |

::: ex 例 11.1.1 · 三行代码定级别 {#ex-11.1.1}

下面的并发写法各自落在[@def-11.1.2]的哪一级？哪些根本不够格叫非阻塞算法？

1. `Mutex<u32>` 保护的计数器，持锁者做 1 毫秒的工作；
2. Treiber 栈式的 CAS 重试循环：load → 计算 next → compare_exchange，失败就重读；
3. 无等待队列的协助扫描：每个线程进场先替登记在册的待办操作推进一格状态机。

::: sol 解答

1. 不够格。它是悲观互斥：持锁者挂起时全系统等待，连 Obstruction-Free 的定义场景都过不去——机制与 11.1.3 的自旋锁相同，只是慢速路径从用户态换进了内核。
2. Lock-Free。任意线程被杀，其余线程的单次 CAS 仍可在有限步成功提交；单个线程可能反复重试而饥饿，但全局始终有进展（[@def-11.1.3]）。
3. Wait-Free。协助机制正是为把「全局有进展」升级为「个体各自有限步」而设。每个操作在被登记的确定轮次内会被他方代为推进，无人能被无限推迟（[@def-11.1.2] 第 3 级）。
:::

### 11.1.5 小结与常见错误

**小结。**① 有锁与无锁的分水岭是进度保证，不是代码形态（[@def-11.1.2]）。② 互斥锁的代价分三层：原子争用与缓存行弹跳（[@def-11.1.1]）、上下文切换断崖、优先级反转与锁护送。③ 自适应锁的自旋预算是微架构敏感参数，SMT 与超订场景下会放大浪费。④ 无锁的硬件本质是乐观重试——快照、推测、单点 CAS、失败让路（[@def-11.1.3]）。⑤ 自旋锁不是无锁，它在数学上连 Obstruction-Free 都不满足。下一节 [11.2 线性化点](#sec-cpp-rust.3.11.2) 回答：CAS 提交的那一瞬间，凭什么能定义正确性。

::: errata 常见错误清单（11.1 节）

E-a **把「没有 lock() 调用」当成无锁证明。**判定只看挂起测试（[@def-11.1.2]），不看代码里有没有关键字。

E-b **把自旋锁写进「无锁数据结构」清单。**持锁线程被抢占即全局停顿，三级阶梯一级都不满足（11.1.3）。

E-c **无视 SMT 兄弟线程定自旋预算。**同一物理核心的执行单元是共享的，无界自旋抢的是自家线程的周期。

E-d **把缓存行弹跳当成「锁不公平」。**它是硬件所有权迁移（[@def-11.1.1]），换调度策略消不掉，只能改数据布局——11.5 展开。

E-e **认为 CAS 失败说明算法写错了。**失败重试是无锁的常态（[@def-11.1.3]）；11.6 的实测显示，它换来的正是方差放大。

E-f **拿单次不加锁的耗时断言「无锁一定快」。**上下文切换只在高争用慢路径出现，低争用的互斥锁可能全程走用户态快速路径（[@ex-11.1.1]）。

## 11.2 线性化点、顺序保证与进度保证分级 {#sec-cpp-rust.3.11.2}

本节回答一个问题：**CAS 提交的那一行指令，凭什么能定义「正确」？**11.1 给了进度分级，但那只是「不卡死」的承诺。这一节给出正确性的承诺：线性化。审计它时唯一要紧的动作也只有一个——指出线性化点在哪一条原子指令上。

::: preview 先抓住一件事

审计任何无锁算法，先问一个问题：能否把每一次成功调用收缩到调用与返回之间的**某一个瞬间**？剩下的条件是，所有这些瞬间按时间排列后恰好构成一个合法的串行历史。指不出那一条原子指令，算法十有八九有数据竞争。
:::

### 11.2.1 线性化（Linearizability）的形式化意义

在单线程串行程序中，正确性的判定是平凡的：执行顺序严格遵循源码编写顺序（在保留 As-if 语义的前提下），写后即读。然而在高度并发的多核无锁系统中，成百上千个线程同时发起 `push()`、`pop()` 或查找操作。每个操作内部包含数十条汇编指令，它们在物理时间轴上重叠交错。此时「按源码顺序理解」不再可用，交错本身成了要被定义的对象，不是可以留给实现细节的东西。

我们如何向使用者证明，一个在多核上交错运行的并发队列，其行为与一个数学上完美的、按顺序依次调用的队列完全等价？

Maurice Herlihy 与 Jeannette Wing 于 1990 年形式化提出了**线性化（Linearizability）**理论。

::: def 定义 11.2.1 · 线性化点 Linearization Point {#def-11.2.1}

一个并发对象是可线性化的，当且仅当它产生的每一个并发执行历史（History）都满足三条：
1. **瞬时生效点**：对每一次方法调用，都可以在其调用发起（Invocation）到方法返回（Response）之间的绝对物理时间轴上，明确指定一个单一且不可分割的瞬间点，即**线性化点**。这个瞬间不是代码块，而是一条原子指令。
2. **逻辑等价性**：把所有操作按其线性化点在时间轴上的先后串行排列。这样构成的串行操作序列，必须完全符合该数据结构在单线程串行规约（Sequential Specification）下的标准语义。
3. **因果顺序保持**：如果操作 $Op_1$ 的返回时间在物理上早于操作 $Op_2$ 的发起时间，则在等价的串行历史中，$Op_1$ 必须严格排在 $Op_2$ 之前。
:::

线性化是并发系统中最强的一致性模型。它不仅具备局部可组合性（Composability，即两个各自可线性化的对象组合成的新系统依然可线性化），而且赋予了并发系统对真实物理时间的严格因果依附。相比之下，顺序一致性（Sequential Consistency）仅要求存在某种合法的全局交错顺序，而不强制要求该顺序与操作在物理时钟上的先后关系绝对吻合。

### 11.2.2 线性化、顺序一致性与可串行化的深层边界

为了在系统架构层面彻底理清这些概念，我们把并发理论中的三大一致性模型放在同一条时间轴上对比：

```text
物理时间轴 ────────────────────────────────────────────────────────►
线程 1: [--- Inv(push A) ------- Resp(push A) ---]
                                     │
                                     │ 物理因果：A 在 B 发起前已完成返回！
                                     ▼
线程 2:                                  [--- Inv(pop) --- Resp: 必须是 A! ---]

如果某个系统允许 线程 2 的 pop 返回空或返回更晚发起的元素，则它直接违反了线性化！
```

- **线性化（Linearizability）**：针对**单个对象/数据结构**的高强一致性，操作具有实时的先后约束（Real-time Order Constraint）。若 $Resp(Op_A) \lt Inv(Op_B)$，则 $Op_A$ 必须在等价序列中早于 $Op_B$。
- **顺序一致性（Sequential Consistency, SC）**：针对**多处理器内存系统**。它保证所有线程观察到的全局内存访问顺序是一致的，且每个线程内部的访问顺序与其程序序（Program Order）相符。它**不强制要求该全局序与绝对外部物理时间完全锁定**。
- **可串行化（Serializability）**：针对**数据库多事务调度**。它仅保证一组事务的并发执行结果与某种串行执行结果相同，但事务的生效时间点可以被重排，不具备物理时间的实时因果要求。

三者的关系是一级一级放宽的：可线性化必是顺序一致的实现，反之不成立；顺序一致也不自动给出实时约束。写并发代码时不要拿「反正是顺序一致的内存」当挡箭牌——[@def-11.2.1] 第 3 条要求的是墙上时钟意义上的先后。

### 11.2.3 寻找并发算法中的线性化点

在编写与审计任何无锁算法时，工程师必须能够精准标定每一条成功与失败路径的线性化点所在指令。指不出这个指令位置，所谓「已证明正确」就没有意义。

以经典的 Michael-Scott 无锁队列（入队出队分离的单向链表队列）为例，其线性化点定义如下：

```text
线程 1 执行 push(X):
[ 1. 分配 Node(X) ] ──► [ 2. 循环读取 tail ] ──► [ 3. CAS tail.next: null -> X ] ──► [ 4. CAS tail -> X ]
                                                                 ▲
                                                          【入队线性化点】
                                                    此时数据正式成为队列一部分！

线程 2 执行 pop():
[ 1. 读取 head ] ──► [ 2. 读取 head.next ] ──► [ 3. CAS head -> head.next ] ──► [ 4. 读出数据并返回 ]
                                                                ▲
                                                         【出队线性化点】
                                                   此时该节点正式移出共享视野！
```

- **成功入队的线性化点**：CAS 把旧尾节点的 `next` 从 `null` 改写为新节点指针 `X` 的那一条指令；随后更新全局 `tail` 的那条**不是**线性化点。`next` 一改成功，其他线程就能遍历看到新节点，并可协同推进 `tail`。
- **成功出队（Dequeue）的线性化点**：发生在**通过原子 CAS 成功将全局 `head` 指针从当前哨兵节点前移至下一个有效节点**的那一条硬件指令上。该指令生效的瞬间，原头节点的出队所有权被该线程独占确立。无论后续如何拷贝节点数据，都不影响全局拓扑已经转移的事实。
- **空队列检测的线性化点**：发生在出队线程原子读取 `head.next` 并判定其为 `null` 的那一瞬间。

::: ex 例 11.2.1 · 这个返回合法吗 {#ex-11.2.1}

队列初始为空。线程 1 的 `push(A)` 在物理时刻 $t_1$ 完成返回；线程 2 在 $t_2 > t_1$ 才发起 `pop()`。按[@def-11.2.1]，`pop()` 返回空是否合法？若线程 1 的 `push(A)` 尚未返回（仍在 $t_1$ 与 $t_2$ 之间交错运行），答案会变吗？

::: sol 解答

第一种情况不合法。$Resp(push) \lt Inv(pop)$，由[@def-11.2.1] 第 3 条（因果顺序保持），任何等价串行历史必须把 `push(A)` 排在 `pop()` 之前，此时 `pop()` 只能返回 A。第二种情况合法。两个操作时间区间重叠，`pop()` 的线性化点可以落在 `push(A)` 的线性化点之前，返回空是某种合法交错的结果。边界就在「是否已经物理返回」——这正是实时约束与普通可串行化的分界。
:::

:::

如果一个算法的逻辑判定依赖于跨越两次独立的非原子内存读取（例如先读取一个变量 A，再读取另一个变量 B，并假设它们反映了同一时刻的状态），它依赖的就不是一个内存单元。这两个单元之间的一段空隙，才是它真正依赖的东西。这段空隙里没有任何原子动作把状态钉住，该算法便无法收缩为一个瞬时点，从而不可线性化。

::: think 思考 · 「差不多是原子的」为什么不行 {#think-11.2.1}

有人辩护：两次读取之间只有几纳秒，实际系统里几乎不会恰好插进并发写。这个论证为什么过不了[@def-11.2.1]？

::: sol 解答

因为定义要求的是「每一个执行历史」都满足三条，而不是「绝大多数历史」满足。调度、中断、缓存延迟都能把几纳秒拉成几毫秒，一个可构造的反例历史就足以否定线性化。正确性论证不能建立在「交错碰不上」的概率直觉上；要把判定收敛到一条不可分割的原子指令上，例如把 A、B 打包成一次 128 位双字 CAS 所覆盖的对象（11.3 展开）。
:::

:::

### 11.2.4 非局部线性化点（Non-local Linearization Points）

在更为高阶的无锁算法中，线性化点的判定往往会更加精妙。例如：

- 在某些无等待队列中，线程 A 的入队操作可能并不是由线程 A 自身完成的，而是由并发运行的线程 B 在执行协助（Helping）时通过一条 CAS 指令顺带提交的。此时，操作 A 的线性化点发生在**另一条线程的指令执行时刻**。这不违反[@def-11.2.1]：定义只要求瞬间点落在该操作的调用—返回区间内，不要求由发起者本人执行。
- 在某些消除栈（Elimination Backoff Stack）设计中，如果一个 `push(X)` 与一个并发的 `pop()` 在无锁通道（Elimination Array）中发生碰撞，两者直接完成数据交换并同时返回。此时两个操作的线性化点收缩在同一次原子交换成功的瞬间。

### 11.2.5 协助机制（Helping Scheme）与无等待演进

要从无锁（Lock-Free）进一步跃迁到无等待（Wait-Free），算法必须彻底消除某个不幸线程因持续竞争失败而无限循环的可能。解决这一难题的通用范式是**协助机制（Helping Mechanism）**：

- 当一个线程发现自己的操作因竞争而反复失败时，它可以将自己的操作描述符（Operation Descriptor）登记到一个全局可见的待处理数组（Announce Array）中。
- 任何其他线程在尝试执行自己的快速路径之前，或者在观察到系统中存在未决的登记项时，都有义务分摊计算能力，**协助完成登记在案的他方操作**，并通过 CAS 推进其状态。
- 当发起者重新被调度时，它可能惊喜地发现自己的入队或出队请求已经被其他高优先级或抢先运行的核心代为完成，直接读取结果即可返回。

这种机制在理论上确保了每个线程的操作都在确定性的有界步数内返回。但有界不是免费：它的工程代价非常巨大，协助机制引入了额外的全局扫描、双重描述符分配以及更为复杂的内存回收挑战。此外，类似**扁平组合（Flat Combining）**的技术通过在无锁快速路径与全局排队代执行之间动态切换，构成了工业级自适应并发容器的重要分支。

| 保证级别 | 核心实现机制 | 优点 | 极端场景缺陷 | 典型应用领域 |
|:--|:--|:--|:--|:--|
| **Obstruction-free** | 推测写回、冲突时主动让步撤销 | 算法精简、无争用时吞吐极高 | 持续争用时将诱发无限活锁（Livelock） | 乐观软件事务内存（STM） |
| **Lock-free** | 单点 CAS 驱动、重试回退策略 | **全局永不死锁**，代码可控，工业标准 | 单个线程可能遭遇调度饥饿，尾延迟有抖动 | Crossbeam 容器、Tokio 核心调度队列 |
| **Wait-free** | 协助队列（Helping）、状态数组登记 | **强确定性步数上限**，杜绝任何饥饿 | 常数开销极大，吞吐往往远低于 Lock-free | 航空航天硬实时控制、高频交易核心引擎 |

::: method 判定流程 · 线性化点审计四步

① **列路径**：把 API 的每条成功/失败返回路径写全，包括「队列空」「CAS 失败重试」这些不显眼的出口。<br>
② **指指令**：对每条路径，指出唯一一条让结果不可撤销的原子指令——「别人从这一刻起一定能看见」的那条。指不出，转 ④。<br>
③ **排历史**：把所有路径的瞬时点按物理时间排成串行序列，对照单线程规约逐个检查（[@def-11.2.1] 第 2 条）。<br>
④ **补原子性**：若判定依赖跨越两次独立读取（11.2.3 末段），要么合并为一个原子单元（双字 CAS、带标记指针），要么明确宣告不可线性化。
:::

### 11.2.6 小结与常见错误

**小结。**① 线性化把每次调用收缩为一个瞬时点，并要求串行等价与物理因果（[@def-11.2.1]）。② 它是三者中最强的：顺序一致性不保证实时约束，可串行化连全局交错的时间锚都不要。③ 审计的动作只有一个——指出那条原子指令（Michael-Scott 队列的入队点在 `tail.next` 的 CAS 上，不是 `tail` 的 CAS）。④ 线性化点可以发生在别人线程的指令上，协助与消除设计都靠这一点成立。⑤ 判定跨越两次非原子读取的算法不可线性化，要用双字原子或宣告边界。下一节 [11.3 ABA 难题](#sec-cpp-rust.3.11.3) 处理线性化点之后的第一个危机：指针值相等不等于内存状态相同。

::: errata 常见错误清单（11.2 节）

E-a **把「顺序一致」当成「线性化」。**前者允许全局序偏离物理时钟，[@def-11.2.1] 第 3 条不允许。

E-b **把辅助 CAS 当线性化点。**Michael-Scott 入队点在 `tail.next` 改写成功那一条；`tail` 的更新只是帮助性推进（11.2.3）。

E-c **让正确性依赖「两次读取之间没人写」。**跨两个非原子读的判定无法收缩为瞬时点（[@think-11.2.1]）。

E-d **拿「测试没抓到交错」当线性化证明。**定义量化的是每一个历史，不是采样到的历史（[@ex-11.2.1]）。

E-e **认为协助机制帮了别人的线程更慢。**协助改变的是「谁的指令承载线性化点」，不改变操作本身的串行语义（11.2.4）。

E-f **把 Wait-Free 当成 Lock-Free 的加强版性能升级。**它买的是步数上限，付的是常数开销；表格末列写得清楚（11.2.5）。

:::

::: method 即时自测 · 11.2

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　写出[@def-11.2.1]的三条要求，各用一句话。

::: sol 第 1 题答案
瞬时生效点：每次调用可指定调用—返回之间的一个不可分割瞬间。逻辑等价：按瞬间点排序后的串行序列符合单线程规约。因果保持：物理上先返回的操作在串行历史中必须在前。
:::

**第 2 题 · 辨析**　「顺序一致性」和「线性化」差在哪一步？

::: sol 第 2 题答案
差在实时锚。两者都要求存在一个全局一致的串行序；线性化额外要求这个序与墙上时钟的调用/返回先后吻合（11.2.2）。SC 允许把「更晚发起」的操作排到前面，线性化不允许。
:::

**第 3 题 · 应用**　同事的代码在 `push` 里先 `load(head)`、再 `load(len)`、最后依据 `len == 0` 判断是否走快速路径。指出审计结论。

::: sol 第 3 题答案
判定跨越两次独立非原子读取，不能收缩为单一瞬时点：`head` 与 `len` 可能来自两个不同时刻的状态，构造一个中间写历史即可破坏串行等价（[@think-11.2.1]）。要么把两者合并进一个原子字（双字 CAS），要么这个快速路径不可线性化，不能宣称队列整体可线性化（11.2.6 审计四步的第 ④ 步）。

要有，但载体不同。计时的契约是估计对象与计时边界：哪一行开始、哪一行结束、每个批次代表什么。这条契约等价于把「这段数字在说什么」收缩到可指认的区间（呼应第 1 章 1.2 节的批次模型与计时边界讨论）。并发里指不出原子指令的算法不能谈正确；基准里指不出计时边界的数字不能谈性能，两者都是「先定义瞬时/边界，再谈结论」。

## 11.3 经典的ABA难题与其内存安全根因 {#sec-cpp-rust.3.11.3}

本节回答一个问题：**指针数值相等，为什么不等于内存状态相同？**11.2 把正确性锚定在一条 CAS 指令上；这一节说明这条指令的比对本身可以被骗过去——这就是 ABA 难题，以及必须把它区分成哪两类。

::: preview 先抓住一件事

CAS 只回答「这一个内存单元现在的位模式（内存里那串二进制值）还和我读到时一样吗」，不回答「期间这块内存有没有被释放又换了新内容」。凡是把「指针值没变」当成「结构没变」的算法，都站在 ABA 的悬崖边上（[@def-11.3.1]）。
:::

### 11.3.1 逻辑值相同与物理状态异化的冲突

在探讨无锁指针操作时，**ABA 难题（ABA Problem）**是每个并发系统工程师都必须跨越的险滩。这一现象最早在 IBM 370 架构的 CAS 指令演进中被发现。

::: def 定义 11.3.1 · ABA 问题 {#def-11.3.1}

**ABA 问题**指：硬件 CAS 指令只检查目标内存单元当前的物理位模式（Bit Pattern）是否与预期值相等。它不能感知该内存单元在此期间是否经历过复杂的生命周期演进与语义重构。值「从 A 变成 B 又变回 A」后，CAS 会把它当成「从来没变过」而放行。
:::

考虑如下一个未经安全保护的经典无锁栈（Treiber Stack）出栈实现片段：

```rust
// 警告：此段代码包含致命的 ABA 漏洞，仅作技术原理解剖与反面教学使用！
pub struct NaiveStack<T> {
    head: std::sync::atomic::AtomicPtr<Node<T>>,
}

struct Node<T> {
    data: T,
    next: *mut Node<T>,
}

impl<T> NaiveStack<T> {
    pub unsafe fn pop_broken(&self) -> Option<T> {
        let mut curr = self.head.load(std::sync::atomic::Ordering::Acquire);
        loop {
            if curr.is_null() {
                return None;
            }
            // 步骤 1：读取当前头节点的 next 指针
            let next_ptr = (*curr).next;

            // ───【致命的时间窗口】：线程若在此处被时钟中断抢占！ ───

            // 步骤 2：CAS 尝试将 head 从 curr 更新为 next_ptr
            match self.head.compare_exchange_weak(
                curr,
                next_ptr,
                std::sync::atomic::Ordering::Release,
                std::sync::atomic::Ordering::Acquire,
            ) {
                Ok(_) => {
                    // 出栈成功，释放节点内存并返回数据
                    let boxed = Box::from_raw(curr);
                    return Some(boxed.data);
                }
                Err(actual) => curr = actual,
            }
        }
    }
}
```

漏洞就藏在「步骤 1」与「步骤 2」之间：`next_ptr` 是基于旧快照推断的裸指针，CAS 校验的却只有 `curr` 一个值。

### 11.3.3 硬件双字 CAS（128 位）在 x86_64 与 AArch64 的微架构行为差异

在硬件实现层面，128 位原子指令在主流架构上的微代码与总线行为存在显著区别：

```asm
; x86_64 架构: lock cmpxchg16b m128
; 期望值位于 rdx:rax，新值位于 rcx:rbx
mov rax, [old_ptr]
mov rdx, [old_tag]
mov rbx, [new_ptr]
mov rcx, [new_tag]
lock cmpxchg16b [rdi]    ; 比较 [rdi] 是否等于 rdx:rax，若相等则写入 rcx:rbx

; AArch64 架构: casal x0, x1, [x2]
; 期望值与新值均要求必须使用连续的偶数-奇数寄存器对 (x0, x1) 与 (x2, x3)
casal x0, x1, [x4]       ; 尝试原子替换 [x4] 处的 128 位数据
```

- **x86_64 的 `lock cmpxchg16b`**：该指令是复杂的 CISC 微代码操作，固定要求 `rdx:rax` 存放旧值、`rcx:rbx` 存放新值。如果操作的目标内存跨越了 64 字节缓存行边界（Split-lock），处理器将被迫在总线上发起全系统锁定（Bus Lock），冻结内存总线长达上千个周期。因此，使用 128 位原子指令必须无条件确保目标地址严格 16 字节对齐。
- **AArch64 的 `casal`（ARMv8.1 LSE）**：128 位变体要求操作数是连续的偶奇寄存器对（x0 与 x1）。在没有 LSE 的 ARMv8.0 核心上，编译器必须回退成 `ldaxp`/`stlxp` 排他循环；高竞争下监视器被反复清除，惩罚显著。

### 11.3.4 逻辑 ABA 与内存破坏 ABA 的严密区分

在并发算法设计中，必须严格区分两类性质迥异的 ABA：

- **逻辑层面的 ABA（Semantic ABA）**：某个整数计数器或业务状态字从值 A 变为 B，随后又变回 A。在纯整数状态机中，如果算法本身只关心当前值是否为 A，或者通过单调递增时钟进行约束，那么逻辑维度的数值重叠并不必然导致系统崩溃。`bench/systems-lab/tests/contracts.rs` 里的 `safe_logic_aba_is_not_a_data_race`（115–126 行，实测通过，归档在 `run-01/test.txt`）将这一点钉成一个断言：

```rust
// contracts.rs:115-126，逐字摘自仓库里的真实测试
#[test]
fn safe_logic_aba_is_not_a_data_race() {
    let head = AtomicUsize::new(1);
    let observed = head.load(Ordering::SeqCst);
    head.store(2, Ordering::SeqCst);
    head.store(1, Ordering::SeqCst);
    // A successful CAS cannot prove that the intervening history was empty.
    assert_eq!(
        head.compare_exchange(observed, 3, Ordering::SeqCst, Ordering::SeqCst),
        Ok(1)
    );
}
```

探针刻意留在单线程：1 写成 2、再写回 1，中间确实发生过不同的值，而 CAS 仍返回 `Ok(1)`。所以「CAS 成功」只证明**此刻**的值等于期望值，证明不了两次访问之间没有别的写入。纯数值状态机里这种「看不见的中间历史」通常只是业务抖动；一旦期望值是指针，它就是下一段那种事故。

- **内存生命周期层面的 ABA（Destructive Memory ABA）**：如同上述 Treiber Stack，一个代表物理内存地址的指针经历了「分配 $\rightarrow$ 释放 $\rightarrow$ 重新分配」。过期的拓扑推断因此被错误赋权，直接引发非法内存访问（UAF）与数据结构撕裂。这是必须从根源上歼灭的灾难。

::: def 定义 11.3.2 · 破坏性内存 ABA {#def-11.3.2}

**破坏性内存 ABA**指 CAS 的预期值是裸内存地址、且该地址可能被分配器（向系统要内存、再把内存还回去的那层代码）释放后再次发放给新对象的情形。判断一个 CAS 是否中招，只看两问：① 比对单元是不是指针（而非纯数值）？② 该指针指向的内存是否可能在快照与提交之间被 free 再 malloc？两问皆是，就必须上 SMR 或双字标记（[@def-11.3.1]）。
:::

### 11.3.5 解决 ABA 问题的工程技术路线

为了消除破坏性 ABA，工业界探索出了两大主要方案：

1. **版本计数器与双字原子（Tagged Pointers / Double-Word CAS）**：指针旁边附一个单调递增的版本号（Tag）。64 位体系上通常用 128 位宽的原子比较交换指令（AArch64 的 LSE 扩展用 128 位配对比较交换 `casp`/`caspl`/`caspal`，`casa`/`casal` 是同一族的单字带序形式，x86_64 侧对应的是 `lock cmpxchg16b`），将 `(pointer: u64, tag: u64)` 作为原子单元一次性比对。即使物理地址重新分配为 `0x1000`，其 Tag 也必然递增（例如从 1 变为 3），从而迫使 CAS 失败。

以下给出一个在支持 128 位原子指令的架构上的安全 Tagged Pointer 核心抽象实现：

```rust
// 利用 AtomicU128 实现的 128 位标记指针
#[repr(align(16))]
pub struct TaggedPointer<T> {
    storage: std::sync::atomic::AtomicU128,
    _marker: std::marker::PhantomData<T>,
}

impl<T> TaggedPointer<T> {
    pub fn new(ptr: *mut T, tag: u64) -> Self {
        let val = ((tag as u128) << 64) | (ptr as usize as u128);
        Self {
            storage: std::sync::atomic::AtomicU128::new(val),
            _marker: std::marker::PhantomData,
        }
    }

    pub fn load(&self, order: std::sync::atomic::Ordering) -> (*mut T, u64) {
        let val = self.storage.load(order);
        let ptr = (val as usize) as *mut T;
        let tag = (val >> 64) as u64;
        (ptr, tag)
    }

    pub fn compare_exchange_weak(
        &self,
        current: (*mut T, u64),
        new: (*mut T, u64),
        success: std::sync::atomic::Ordering,
        failure: std::sync::atomic::Ordering,
    ) -> Result<(*mut T, u64), (*mut T, u64)> {
        let curr_val = ((current.1 as u128) << 64) | (current.0 as usize as u128);
        let new_val = ((new.1 as u128) << 64) | (new.0 as usize as u128);
        match self.storage.compare_exchange_weak(curr_val, new_val, success, failure) {
            Ok(v) => Ok(((v as usize) as *mut T, (v >> 64) as u64)),
            Err(v) => Err(((v as usize) as *mut T, (v >> 64) as u64)),
        }
    }
}
```

局限也要记住。128 位原子指令在部分架构上开销可观；对齐不是风格问题，必须 16 字节，否则部分 ARM 核心直接 SIGBUS。另一种省钱做法是偷借 64 位指针的高 16 位存 Tag（靠 48 位虚拟地址空间），但启用 ARMv8.3+ PAC 或 Top-Byte Ignore 的宿主（如 macOS Darwin）会让被改的指针解引用时触发硬件异常，跨平台性同时没了。

2. **安全内存回收机制（Safe Memory Reclamation, SMR）**：这是从物理因果上彻底杜绝 ABA 的前提条件。它要求：**只要系统中仍有任何一个活跃线程可能持有指向节点 A 的悬垂观测，该节点 A 的物理内存就绝对禁止被释放回操作系统分配器**。既然内存无法释放，分配器就绝无可能将地址 `0x1000` 分配给新对象，ABA 的因果链条在源头被物理切断。SMR 的两大流派——Hazard Pointer 与 EBR——在下一节展开。

::: ex 例 11.3.1 · 标记指针能骗过吗 {#ex-11.3.1}

回到[@def-11.3.1]的场景：`0x1000` 被 A′ 复用。改用 TaggedPointer 后，线程 1 的 CAS(expected = (0x1000, tag=1)) 还会成功吗？如果 Tag 不是 64 位而是偷借在指针高 16 位的计数器呢？

::: sol 解答

第一问不会。每次释放再分配都伴随 Tag 递增，A′ 的 Tag 已是 3。双字比对 (pointer, tag) 中至少一半不相等，CAS 失败，线程 1 重读最新状态（[@def-11.3.2] 的两问检验里第 ② 问仍成立，但检测手段升级了）。第二问有洞：16 位 Tag 只有 65536 个取值，高吞吐栈每轮分配-释放都推 Tag，绕满一圈后 (0x1000, tag) 可能再次整体重合——ABA 原样复发。纯指针自增或短位宽 Tag 而不处理环绕溢出，等于没解决（E-c 见本节清单；16 位 Tag 绕回所需的吞吐门槛，本节没有采集）。
:::

:::

::: think 思考 · 双字原子是不是万能的 {#think-11.3.1}

有了 128 位原子比对，是否可以宣布 ABA 已死、不再需要 SMR？

::: sol 解答

不能只靠它。Tag 只证明「这个字没被别的 CAS 改过」，不证明「指针指向的内存还活着」。若线程 1 快照里 `next_ptr = 0x2000` 且 Tag 恰好还没被消费（例如节点 B 已 free、但地址未被复用），CAS 依旧可能把 head 写成悬垂地址——除非 Tag 递增与「禁止物理释放」绑定。这正是路线 2 存在的理由：Tag 防检测，SMR 防事故，两者互补（下节）。
:::

### 11.3.6 小结与常见错误

**小结。**① ABA 的根源是 CAS 只认位模式、不认生命周期（[@def-11.3.1]）。② 图 11-1 展示完整事故链：快照、挂起、弹出、地址复用、比对放行、悬垂覆写，五步缺一不可。③ 两类 ABA 是两回事：逻辑 ABA 可用单线程探针[@ex-11.3.1]钉出「CAS 看不见中间历史」这件事，破坏性内存 ABA 必须歼灭（[@def-11.3.2]）。④ 两条工程路线各自堵一半：双字标记指针防「检测盲区」，SMR 断「复用源头」。⑤ 标记指针自身还有三个坑——16 字节对齐、架构开销、Tag 位宽环绕与 PAC/TBI 冲突。下一节 [11.4 内存回收技术对照](#sec-cpp-rust.3.11.4) 展开 SMR。

::: errata 常见错误清单（11.3 节）

E-a **以为 CAS 能天然防范 ABA。**单字 CAS 只比对数值相等，不能识别「释放后重新赋予同一地址」的语义异化（[@def-11.3.1]）。

E-b **把「指针值没变」当成「结构没变」。**图 11-1 里 0x1000 全程没变，变的是整个拓扑。

E-c **用短位宽 Tag 且不处理环绕溢出。**16 位偷借位宽在高吞吐下回绕，ABA 原样复发（[@ex-11.3.1]）。

E-d **在启用 PAC/TBI 的系统上偷借指针高位。**硬件解引用异常，跨平台直接崩（11.3.5 局限段）。

E-e **让双字原子目标跨 64 字节边界。**x86_64 触发 Split-lock 全总线锁定；16 字节对齐不是风格问题（11.3.3）。

E-f **指望 Tag 单独救活悬垂指针。**Tag 防检测、SMR 防事故，少一环都不闭合（[@think-11.3.1]）。

::: sol 第 2 题答案

## 11.4 内存回收技术对照：Hazard Pointer与Epoch-based {#sec-cpp-rust.3.11.4}

本节回答一个问题：**节点被逻辑摘除之后，什么时候才允许物理释放？**11.3 把 SMR 列为解决 ABA 的路线 2；这一节打开 SMR 本身——两大流派各自保护什么、花在哪、边界在哪。

::: preview 先抓住一件事

所有安全内存回收机制只在回答同一个问题：「还有没有人可能看着这个节点？」HP 的答案精确到每个指针——读者逐个登记。EBR 的答案精确到每个时间代际——读者整批豁免。两者保护的不是同一个粒度，成本自然落在不同的地方，精度与成本的取舍从这里就分岔了。
:::

### 11.4.1 Rust 所有权与并发销毁的根本冲突

在带自动垃圾回收的托管运行时（如 Java HotSpot、Go runtime）中，无锁数据结构的实现较为轻松，因为所有节点对象的存续性由后台三色标记或分代 GC 统一托管。只要有任何变量引用节点，GC 就不会回收它。

但在以「零运行时抽象」和确定性析构为基石的 Rust 中，所有权系统在并发无锁场景下面临着深刻挑战：

- 当一个线程从链表或无锁结构中移出一个节点时，它获得了该节点逻辑上的所有权。
- 按照 Rust 的惯例，调用 `drop()` 或移出作用域应当立即归还堆内存。
- 但此时，可能有若干个并发读者线程刚刚读取了该节点的裸指针，正准备解引用其内部字段！
- 如果写者立即物理销毁该对象，读者将当场陷入未定义行为（Undefined Behavior, UB）与内存崩塌。

这里的关键缺口是：Rust 的借用检查器看得见的引用才谈生命周期，而穿过 `AtomicPtr` 的裸指针观测它在静态层面看不见。因此，Rust 无锁系统必须在用户态实现精密的**安全内存回收机制（SMR）**。

::: def 定义 11.4.1 · 安全内存回收 SMR {#def-11.4.1}

**安全内存回收机制（Safe Memory Reclamation）**是一类用户态协议，它承诺：**只要仍有任何活跃线程可能持有指向节点的悬垂观测，该节点的物理内存就禁止归还分配器**。它补的是所有权系统管不到的那段生命周期：静态借用检查之外、由并发读取产生的「隐性引用」。HP 与 EBR 是它的两个主流实现（[@def-11.3.2] 路线 2 的具体化）。
:::

### 11.4.2 冒险指针（Hazard Pointer, HP）的工作原理

Hazard Pointer 由 Maged Michael 于 2004 年提出，其核心逻辑是**读者向全局公布危险保护名单**：

```text
[ 读者线程 ]                                               [ 写者线程 (移除节点) ]
     │                                                           │
     ├─ 1. 读取指针 P                                            ├─ 1. 逻辑移出节点 X (地址 P)
     ├─ 2. 将 P 写入线程私有的 Hazard Slot                       ├─ 2. 将 X 挂入本地待退休链表 (Retire List)
     ├─ 3. 内存屏障 (SeqCst / Store-Load)                        │
     ├─ 4. 再次验证节点 P 是否仍有效                            │ (当退休链表累积满阈值)
     │     (若已被移除则清空 Slot 重试)                          ├─ 3. 扫描全局所有线程的 Hazard Slots
     ├─ 5. 安全访问 (*P).data ──────────────┐                   │
     │                                      │ 对比               ├─ 4. 比对：P 是否在任何人的名单中？
     └─ 6. 访问结束，清空 Hazard Slot       └──────────────────► │     - 是: 保留，等待下一轮
                                                                 └───── - 否: 安全执行 free(P)！
```

::: def 定义 11.4.2 · Hazard Pointer {#def-11.4.2}

**Hazard Pointer（冒险指针）**用一句大白话说：读者解引用一个指针之前，先把这个地址登记到「人人可查的黑名单」上。写者要释放节点前，必须确认这个地址不在任何人的黑名单上。登记这个动作叫 protect，销账叫 clear。
:::

按[@def-11.4.2]，协议要点是：

- **显式保护**：读者在解引用之前，必须通过原子写与强内存屏障，将裸指针地址登记在全局可见的 Hazard Slot 中。
- **延迟销毁**：写者把逻辑移除的节点推入本地待退休列表；列表累积到 $2 \times H$（$H$ 为插槽总数）时批量扫描所有 Hazard Slot，只物理释放没出现在任何插槽里的节点。
- **理论优势**：滞留上限确定（与线程数、插槽数成正比），不会不可控暴涨；代价落在读路径每次解引用上，不在退休批次上。
- **工程痛点**：读操作极度昂贵。读者每遍历一个新节点，都必须执行一次全局发布的写屏障，严重压制现代 CPU 的乱序执行与多核读扩展能力。HP 的读路径实测开销，本章没有采集；本书基准只覆盖 EBR（11.7）。

一个典型的轻量级 Hazard Slot 数据结构定义如下：

```rust
pub struct HazardSlot {
    hazard_ptr: std::sync::atomic::AtomicPtr<()>,
    active: std::sync::atomic::AtomicBool,
}

impl HazardSlot {
    pub fn protect<T>(&self, ptr: *mut T) {
        self.hazard_ptr.store(ptr as *mut (), std::sync::atomic::Ordering::Release);
        // 在强顺序或弱顺序架构上，必须配合内存屏障以确保所有写者立即可见
        std::sync::atomic::fence(std::sync::atomic::Ordering::SeqCst);
    }

    pub fn clear(&self) {
        self.hazard_ptr.store(std::ptr::null_mut(), std::sync::atomic::Ordering::Release);
    }
}
```

### 11.4.3 Hazard Pointer 读者写者的硬件级内存屏障交互

为了彻底理解 Hazard Pointer 的高昂开销，我们来深入审视读者与写者在微架构层面的强同步协议：

```rust
// Hazard Pointer 核心交互协议模型
pub struct HazardPointerCore {
    // 全局 Hazard Slots 数组，每槽对应一个读者正在保护的裸指针
    slots: Vec<std::sync::atomic::AtomicPtr<()>>,
}

impl HazardPointerCore {
    // 读者端保护协议
    pub unsafe fn protect<T>(&self, slot_idx: usize, target: *const T) -> bool {
        // 步骤 1：将目标裸指针发布到全局槽位
        self.slots[slot_idx].store(target as *mut (), std::sync::atomic::Ordering::Release);

        // 步骤 2：强制全系统内存屏障！
        // 在 x86_64 上对应 MFENCE 或带 lock 前缀的指令；
        // 在 AArch64 上对应 dmb ish！
        std::sync::atomic::fence(std::sync::atomic::Ordering::SeqCst);

        // 步骤 3：双重校验（Double Checking）
        // 读者必须核实：在发布该危险指针的期间，写者是否已经将该节点从共享结构中脱钩？
        // 若脱钩则说明当前保护可能已经过晚，必须立即清空槽位并宣告失败重试！
        true
    }

    // 读者端释放协议
    pub fn unprotect(&self, slot_idx: usize) {
        self.slots[slot_idx].store(std::ptr::null_mut(), std::sync::atomic::Ordering::Release);
    }
}
```

注意步骤 2 中的 `SeqCst` 内存屏障：现代超标量处理器具备极强的 Store Buffer（写缓冲区）乱序优化能力。在读者将指针写入私有 Hazard Slot 的瞬间，该写操作可能仅停留在当前 CPU 核心的本地 Store Buffer 中，尚未真正冲刷至一致性缓存。如果此时没有强行下发 `SeqCst` 全局屏障（在 AArch64 下为 `dmb ish`，在 x86 下为 `mfence`），并发写者在执行扫描时就无法从全局总线上读到该 Slot 的最新值。写者读到的不是登记之后的状态，就会误以为没有任何读者引用该节点，从而酿成提前释放的 UAF 灾难。

正是这每一次访问节点都不可避免的强屏障，注定了 Hazard Pointer 在高性能多核读密集型负载中无法匹敌 EBR。

::: think 思考 · 把屏障挪到 protect 之后再补，行不行 {#think-11.4.1}

有人提议：先 store 槽位，直接开始访问，等这一轮遍历结束再统一补屏障。这样读路径不就便宜了？

::: sol 解答

不行，顺序反了。屏障保护的不是读者的访问，而是写者的**扫描时机**。写者扫槽位时，若读者的登记还压在 Store Buffer 里，写者看到的槽位是空的，于是合法地 free 掉读者正要用的节点。协议要求「发布必须先于写者的可见性判定」，所以屏障必须夹在 store 与双重校验之间（11.4.3 步骤 2→3）。事后补屏障保护的是一场已经发生的事故。
:::

:::

### 11.4.4 基于纪元的内存回收（Epoch-Based Reclamation, EBR）

EBR（由 Keir Fraser 提出，并在 `crossbeam-epoch` 中被工业级成熟实现）将保护粒度从「针对单个指针」提升为「针对全局时间代际」：

::: def 定义 11.4.3 · Epoch-Based Reclamation {#def-11.4.3}

**基于纪元的内存回收（EBR）**用一句大白话说：给系统装一个只往前走的「年代钟」。读者进门（`pin()`）时在门票上盖当前年代，出门时撕票。写者退休节点时，按退休瞬间的年代把节点装进对应垃圾袋。只有当所有在场读者的门票都不早于「上一代」，两代之前的垃圾袋才允许倒空。代价是：一张被攥着不放的旧门票，会冻住整条回收流水线（11.7 实测）。
:::

EBR 的四根支柱：

1. **全局代际时钟（Global Epoch）**：系统维护一个单调递增的原子全局纪元计数器 `Global Epoch`，在逻辑上通常模 3 循环（0, 1, 2）。

2. **参与者局部代际登记（Local Epoch & Active Pinning）**：每个工作线程拥有一个绑定的局部状态。当线程需要访问数据结构时，调用 `pin()` 创建一个 RAII 守卫 `Guard`：将该线程的活跃标志置为 `Active`；将当前最新的 `Global Epoch` 载入并同步到自己的 `Local Epoch`。**至关重要的一点**：在此之后，读者可以连续解引用任意数量、任意拓扑的内部指针，**读路径没有任何内存屏障与跨核写入开销**！

3. **退役与垃圾袋（Retirement Bags）**：当节点被逻辑脱钩后，写者不直接销毁它，而是调用 `guard.defer(move || drop(item))` 把析构逻辑封成闭包投进垃圾袋。离开拓扑不是消失，消失要等代际钟走到位。

4. **静止状态判定与代际推进**：某线程尝试刷新垃圾时，逐个检查所有 `Active` 线程。若**每个活跃线程的局部纪元都等于全局纪元**，就没有人还在访问两代前（`Global Epoch - 2`）退役的对象，全局代际自增，那一代的退役对象一次性安全释放。

与[@def-11.4.2]逐项对照：HP 保护「这一个指针」、读者每次解引用都要付费；EBR 保护「这一段时间」、读者只在进出时各付一次费。天下没有免费的代际豁免——EBR 把成本推迟给了最慢的那个线程（[@def-11.4.3] 末句）。

### 11.4.5 深入 crossbeam-epoch 的垃圾袋（Bag）与代际推进机制

在 `crossbeam_epoch` 的内部结构中，延迟释放的对象并非零散地存放在全局链表中，而是以极其精密的**分级垃圾袋（Bags）**进行组织：

```text
线程局部 (Local，internal.rs:289-310)：
  ├── bag: UnsafeCell<Bag> ──► 每线程只有一个袋子，deferreds: [Deferred; 64] + len
  ├── guard_count / handle_count ──► 当前有几层 pin
  └── pin_count ──► 累计 pin 次数，偶尔用它顺手踢一次全局清理
                             │
                             ▼ (袋子满 64 项，或 flush / 代际推进时封口)
全局 (Global，internal.rs:156-165)：
  ├── locals: List<Local> ──► 侵入式链表；推进代际时要逐个看参与者是否已静止
  ├── queue: Queue<SealedBag> ──► 单条队列，元素是 (epoch, Bag) 的封口袋
  └── epoch: CachePadded<AtomicEpoch> ──► 全局代际，三值轮转
```

1. **缓存本地化**：每个工作线程将退役对象的析构指针（`Deferred` 结构体，本质上包含一个函数指针与对象地址）直接追加到本线程私有的那**一个** `Bag` 中——袋子里不放代际号，代际号在封口时由 `SealedBag { epoch, bag }` 盖上（`internal.rs:138-139`），所以「哪一代的垃圾」是袋子的标签，不是袋子的数量。

2. **批量流转**：当 `Bag` 填满（默认 64 项）时，线程将该 `Bag` 作为一个整体原子移动到全局 `Global` 对应的代际队列中。这样避免的是每个对象都单独去碰一次全局锁或原子指针。

3. **协作式垃圾清理**：下一次进入 `pin()` 或显式 `flush()` 时，若全局纪元成功推进，工作线程顺手从已证明过期的两代前全局队列弹出一个完整 `Bag`，物理释放就在本地做。清理分摊在每个线程头上，没有集中的回收线程，因此也不会有它的 Stop-The-World 全局停顿——这是「谁污染，谁治理」。

### 11.4.6 为什么 EBR 只需要 3 个纪元代际（0, 1, 2）？

让我们给出这一经典代际划分的严格数学因果证明：

::: proof EBR 三纪元充分必要性证明

设全局纪元当前为 $e$。
1. 任何在纪元 $e$ 内被移出共享拓扑（Retired）的对象 $O_e$，只能被处于纪元 $e$ 或此前已进入且尚未退出的局部活跃线程所观察到；
2. 在此之后新进入临界区的线程，其 `pin()` 读取到的全局纪元必然 $\ge e$；
3. 当且仅当系统中**所有活跃线程的局部纪元均达到或超过 $e+1$** 时，我们可以确信：系统中没有任何线程依然存活着进入纪元早于 $e$ 的引用；
4. 此时，对象 $O_e$ 处于「静止安全期」（Quiescent Phase），可以被安全回收；
5. 因此，在任意时刻，全局处于存活视野中的对象最多横跨当前纪元 $e$ 与前一个纪元 $e-1$。属于纪元 $e-2$（即模 3 意义下的两代之前）的对象必定可以安全释放。
6. 结论：三状态轮转时钟 $\{0, 1, 2\}$ 足以无冲突地区分「当前活跃」、「宽限期等待」与「确定安全可释放」三种状态。
:::

### 11.4.7 HP 与 EBR 的总对照

下表系统比对 Hazard Pointer 与 Epoch-Based Reclamation 的技术特征：

| 评价维度 | Hazard Pointer (HP) | Epoch-Based Reclamation (EBR) |
|:--|:--|:--|
| **读者路径开销** | 极高（每次解引用均伴随写屏障与双重校验） | **极低**（进入/退出保护区仅需修改私有代际字） |
| **内存滞留上限** | 严格有界：$O(Threads \times Slots)$ | 无界风险：若有单线程停滞在 `Guard` 内，垃圾将无限积压 |
| **拓扑结构适应性** | 差：难以处理环形引用、长路径跨步与复杂图 | 极佳：任意复杂指针网状结构在代际内天然受保 |
| **Rust 生态成熟度** | 较低（缺乏成熟普适的开源实现） | **极高**（`crossbeam-epoch` 为底层事实标准） |
| **典型适用场景** | 内存极度受限、线程可能无预警长休眠的系统 | 高吞吐网络代理、内存数据库、高性能读多写少缓存 |

::: ex 例 11.4.1 · 按工作负载选 SMR {#ex-11.4.1}

三个场景，各选 HP 还是 EBR？给出[@def-11.4.2]与[@def-11.4.3]表中的哪一格支撑你的选择。

1. 嵌入式网关，4 个线程，RAM 极小，允许某线程偶发休眠几十秒；
2. 读多写少的内存缓存，32 线程，纳秒级读路径预算；
3. 图结构索引，单次查找平均穿越 40 个节点。

::: sol 解答

1. HP。滞留上限 $O(Threads \times Slots)$ 严格有界，「线程可能无预警长休眠」正是 HP 那行的典型场景；EBR 会让休眠线程的 Guard 冻住回收（11.7 实测的 1 MB 积压形态）。
2. EBR。HP 每次解引用一发写屏障（[@def-11.4.2] 工程痛点格），32 线程读密集下多核扩展直接被压制；EBR 读路径只在 pin/unpin 付费。
3. EBR。HP「难以处理长路径跨步」（适应性行），40 跳就是 40 次保护登记；EBR 一次 pin 罩住整段遍历。反过来，若场景 2 同时要求「绝不允许任何内存积压」，三项证据里滞留上限会否决 EBR。选择从来是多目标折中（本例只做定性选择，两种机制的对照实测数字，本节没有采集）。
:::

:::

### 11.4.8 小结与常见错误

**小结。**① SMR 补的是静态借用检查看不见的「裸指针观测」生命周期（[@def-11.4.1]）。② HP 精确到指针、读路径每跳一发全局屏障（[@def-11.4.2]），EBR 精确到代际、读路径零屏障（[@def-11.4.3]）。③ 屏障必须夹在「登记」与「写者可见」之间，事后补等于没补（[@think-11.4.1]）。④ 三纪元轮转的充分性由静止状态判定给出（11.4.6 证明框）。⑤ HP 滞留有界、EBR 滞留取决于最慢读者，选型按[@ex-11.4.1]的格子走。下一节 [11.5 类型系统、对齐与代码生成](#sec-cpp-rust.3.11.5) 先处理更底层的地基：这些原子变量在缓存行上怎么摆。

::: errata 常见错误清单（11.4 节）

E-a **把 protect 的屏障当可选优化。**登记滞留在 Store Buffer 里，写者扫描就会漏看并提前 free（[@think-11.4.1]）。

E-b **以为 EBR 的读路径也有每跳成本。**pin 之后连续解引用零屏障零跨核写（[@def-11.4.3]）；同样也不要忘了反向的坑——pin/unpin 的成本没有消失，只是搬到了边界。

E-c **在 EBR 中忽略调用 `flush()` 或主动退出。**不定期刷新局部垃圾袋，已满足回收条件的内存长期滞留本地缓存，还不还给操作系统。

E-d **误把 `crossbeam_epoch::unprotected()` 用于并发写入。**它完全跳过代际追踪，只适用于初始化阶段或已确立外部独占借用的特殊单线程场景。

E-f **只数读者数量、不看门票年代。**代际推进的判据是「所有活跃线程局部纪元都追平全局」（11.4.4 支柱 4），一个旧门票线程就足以否决，哪怕其他一千个线程都已追平。

E-g **把 EBR 垃圾袋当成集中式 GC 线程。**crossbeam 靠「谁污染谁治理」的协作分摊释放，不存在 Stop-The-World 回收线程（11.4.5）。

:::

::: method 即时自测 · 11.4

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　HP 与 EBR 各自把保护粒度落在什么对象上？

::: sol 第 1 题答案
HP 落在「单个指针」：读者逐个地址登记进 Hazard Slot（[@def-11.4.2]）；EBR 落在「时间代际」：读者以 pin 时的纪元盖门票，同代际内一切访问统一受保（[@def-11.4.3]）。
:::

**第 2 题 · 辨析**　「EBR 读路径零屏障，所以 EBR 全面优于 HP。」这句话错在哪一格？

::: sol 第 2 题答案
错在拿单格比全场。EBR 的滞留上限无界：一个停在 Guard 里的线程能冻住全局回收；HP 的滞留严格 $O(Threads \times Slots)$（对照表）。长休眠、内存受限的系统恰恰要选「读路径贵但兜得住」的 HP（[@ex-11.4.1] 第 1 场景）。
:::

**第 3 题 · 应用**　Code review 看到 `let guard = collector.register().pin();` 写在循环外层、`drop(guard)` 在函数末尾，中间遍历 200 个节点。评估并给改法。

::: sol 第 3 题答案
功能上合法——EBR 一次 pin 罩整段遍历正是它的长处（11.4.4 支柱 2）。风险在持有期：这段期间全局回收对该线程的纪元让路，若函数还会做 I/O 或等待，就滑向 11.7 的停顿参与者事故。改法：把 pin 收窄到纯指针遍历段，遍历后立即 drop/flush，耗时操作移出保护区（E-c、E-f 的实务形态）。
:::

**第 4 题 · 迁移**　GC 的三色标记与写屏障、EBR 的代际与门票，解决的其实是同一类问题。用一句话说出共同结构，并指出 Rust 为什么不能直接抄 GC 的答案。

::: sol 第 4 题答案
共同结构是「先冻结观测关系，再推迟销毁」：GC 用可达性判定「还有没有人引用」，EBR/HP 用代际或槽位判定「还有没有人可能看着」。Rust 抄不了 GC，因为它没有可以暂停全世界、扫描全部根引用的运行时。确定性析构与零运行时抽象给出的是同一件事的另一面。存续信息必须由程序自己在协议里显式交出来。不能指望某个后台机制替你判断（[@def-11.4.1]，11.4.1 的四个要点）。
:::

:::

## 11.5 类型系统、对齐与代码生成边界 {#sec-cpp-rust.3.11.5}

本节回答一个问题：**同一个无锁算法，摆错一个字段的位置，为什么硬件就把它变成了另一门生意？**11.1 的[@def-11.1.1]说缓存行是争用的最小单位；这一节看类型系统怎样把「谁和谁共享一条缓存行」变成可以声明的不变量，并核对编译器真正下发了什么。

::: preview 先抓住一件事

原子变量的地址与对齐，不是内存布局的审美问题，而是并发协议的物理参数。本书实测机上 `hw.cachelinesize` 是 **128 字节**：把 64 字节当天下通行的缓存行、硬编码填充，在 Apple Silicon 上照样落在同一条缓存行里（[@def-11.5.1]）。
:::

### 11.5.1 缓存行伪共享的类型级免疫

在无锁数据结构中，多个线程频繁通过原子 RMW 指令修改状态变量（如队列的头部与尾部指针）。如果这两个原本逻辑独立的原子变量在物理上落在同一个 CPU 缓存行（Cacheline）内，将引发微架构级的**伪共享（False Sharing，不同变量落在同一条缓存行上互相踢）**灾难。两个核心上的私有 L1 缓存行将不断被对方的原子写置为 Invalid 状态，导致原子指令耗时激增数十倍。伪共享的对照耗时本实验没有单独采集，本节给出的实测证据是类型尺寸与对齐边界。

::: def 定义 11.5.1 · 伪共享 False Sharing {#def-11.5.1}

**伪共享**用一句大白话说：两个线程逻辑上碰的不是同一个变量，物理上却挤在同一条缓存行里，于是硬件把它们当成同一个人在争。每次一方写入，另一方的副本就作废，[@def-11.1.1]的弹跳就此发生。数据没错，布局错了。
:::

在 Rust 中，我们通过类型系统的对齐属性进行显式隔离。下表给出了我们在 `systems-lab` 实验中探针探测出的真实类型尺寸与对齐边界：

| 内部类型 | 大小（`size_of`，字节） | 对齐（`align_of`，字节） | 架构设计考量 |
|:--|--:|--:|:--|
| `crossbeam_queue::ArrayQueue<u64>` | 384 | 128 | 针对 Apple M5 Pro / 现代硬件 128 字节缓存行填充，彻底隔离头尾索引与缓冲区 |
| `crossbeam_epoch::Guard` | 8 | 8 | 内部仅包含线程本地代际句柄的轻量引用，适合在栈上高频传递 |
| `crossbeam_epoch::Collector` | 8 | 8 | 指向内部全局代际状态池的 `Arc` 封装指针 |
| `std::sync::Arc<[u8]>` | 16 | 8 | 胖指针结构：包含裸数据地址（8B）与切片长度（8B） |
| `&[u8]` (切片借用) | 16 | 8 | 胖指针结构：地址（8B）+ 长度（8B），在寄存器对中传递 |
| `Vec<u8>` (动态向量) | 24 | 8 | 三字结构：堆指针（8B）+ 容量（8B）+ 长度（8B） |
| `AtomicPtr<u64>` | 8 | 8 | 机器字宽原生原子指针，直接映射底层单字 CAS |

宿主系统（Apple M5 Pro）报告 `hw.cachelinesize` 为 **128 字节**，`ArrayQueue` 的头尾索引就按这个粒度隔开（实测对齐 128）。照搬「缓存行都是 64 字节」硬编码 64 字节填充，在 M 系列上仍会落入[@def-11.5.1]的陷阱。

### 11.5.2 深入 ArrayQueue 的世代轮次（Lap）状态机

以 `crossbeam_queue::ArrayQueue` 为例。它要在固定容量的环形缓冲区上实现多生产多消费（MPMC），并未采用简单的单一原子游标，而是为每一个槽位（Slot）分配了一个专属的代际序号（`AtomicUsize`，称为 `lap` 或 `stamp`）：

::: def 定义 11.5.2 · 槽位世代号 Sequence / Lap {#def-11.5.2}

**槽位世代号**指把「这个槽位轮到谁、处于第几圈」编码进一个随复用单调递增的原子计数值。`ArrayQueue` 里它不是索引而是全局位置：低位是索引、高位是圈数（`one_lap` 取大于容量的最小 2 的幂，`array_queue.rs:131`）。写者要 `stamp == tail` 才获准写入，写完置 `tail + 1`；读者要 `stamp == head + 1` 才获准读出，读走置 `head + one_lap`，即同一索引下一圈的写入授权值。一句大白话：每个格子自带一张「本轮状态条」，过期指令的状态条对不上号，天然被拒收。
:::

```text
位置编码:  index = pos & (one_lap - 1)   lap = pos & !(one_lap - 1)
每个槽位:  (stamp: AtomicUsize, value: UnsafeCell<MaybeUninit<T>>)
初始状态:  head = tail = 0；第 i 个槽位 stamp = i（array_queue.rs:113-124）

对于生产者 push(X)，目标位置 tail：
1. 读该槽位 stamp，只有 stamp == tail 才继续（:173）
2. 先把 tail 用 CAS 推进到 new_tail，成功才获得本槽的写授权
3. 写入数据后 stamp.store(tail + 1, Release)（:186）——读者要的就是这个值
   若 stamp + one_lap == tail + 1（:194），说明上一轮的还没被读走，队列已满

对于消费者 pop()，源位置 head：
1. 读该槽位 stamp，只有 stamp == head + 1 才继续（:351）
2. 先把 head 用 CAS 推进，成功才获得本槽的读授权
3. 读出数据后 stamp.store(head + one_lap, Release)（:372-373）
   若 stamp == head（:381），说明这一格还没有新数据，队列已空
```

对照[@def-11.3.1]，通过将「第几轮回环」直接编码进槽位的原子 stamp 中，`ArrayQueue` 巧妙地实现了两大工程突破：

- **天然免疫 ABA**：即便槽位索引相同，每次复用其代际号都单调递增，彻底杜绝了过期指令读写新轮次槽位的风险。它正是[@def-11.3.2]两问检验的第 ② 问被状态条挡住的实例——槽位可以复用，stamp 从不回头。
- **读写各自与自己的 stamp 同步**：生产者认 `tail`、消费者认 `head + 1`，没有全局粗粒度争用。

在编译生成的汇编产物 `systems_lab-*.s` 中，我们可以直接审视 Rust 编译器针对原子操作和循环展开所下发的真实机器指令：

下面按产物第 10368–10391 行逐字摘出函数体，只删掉 `.loc`/`.cfi_*` 与 `Ltmp` 标签这类调试元数据，指令一行未改：

```asm
__RNvCs4WO1Pb37diX_11systems_lab11scalar_step:
    sub    sp, sp, #16
    str    w0, [sp, #12]          ; black_box 把参数落盘，禁止优化掉
    add    x8, sp, #12            ; 取该槽位地址（black_box 需要指针）
    ; InlineAsm Start
    ; InlineAsm End
    ldr    w8, [sp, #12]
    add    w8, w8, w8, lsl #1     ; w8 = w8 + (w8 << 1)，即乘 3
    add    w0, w8, #7             ; w0 = w8 * 3 + 7
    add    sp, sp, #16
    ret
```

`mul` 一次都没有出现：乘 3 被换成单周期移位加法 `add w8, w8, w8, lsl #1`，随后加 7。`black_box` 的两行（`str` 与 `add x8, sp, #12`）也在，说明它确实迫使值走了一次内存。纯算术已经被优化到接近极致，剩下的瓶颈不在算术，而在原子状态更新、内存屏障与缓存一致性协议之上。

再看原子提交与读取：Apple M 系列上 Acquire 载入是 `ldapr`，Release 存储是 `stlr`。强顺序 RMW 则生成为不可分割的 `casal` 指令（同一份产物里 `casal` 3 次、裸形式 `casp` 0 次：本产物的配对 CAS 带 acquire-release 后缀）。「Acquire/Release 不会被升级成全序屏障」要按产物计数理解：这份 `.s` 有 60 条 `dmb`，54 条是只挡访存方向的 `dmb ishld`，6 条全屏障 `dmb ish` 落在 `retire` 2、`epoch_batch` 1、`drain` 1、`Queue::push`/`pop` 各 1，都能在源码的显式 SeqCst 栅栏里找到出处（`array_queue.rs:194`、`internal.rs:185`），不是编译器代劳。

::: ex 例 11.5.1 · 这条结构体会弹跳吗 {#ex-11.5.1}

```rust
struct Counters {
    head: std::sync::atomic::AtomicUsize,
    tail: std::sync::atomic::AtomicUsize,
    buf: [u64; 64],
}
```

生产者高频写 `tail`，消费者高频读 `buf` 并写 `head`。在本书实测机上按[@def-11.5.1]判定：有没有伪共享？只把 `head`/`tail` 用 64 字节填充隔开，够不够？

::: sol 解答

有。`head` 与 `tail` 各 8 字节且相邻，必然同落一条缓存行，两个核心的原子写互为 Invalid 源。用 64 字节填充不够：实测机缓存行是 128 字节，隔了 64 仍可能同线（这正是 11.5.1 末段警告的硬编码陷阱）。合规做法是按探测值对齐：`#[repr(align(128))]` 让每个高频原子字段独占一条缓存行，`ArrayQueue` 的 384/128 探针行就是这么来的。至于「不弹跳版」快多少，本实验没有采集该结构的对照批次，只给布局判定。
:::

:::

::: think 思考 · 把 128 写进常量对不对 {#think-11.5.1}

既然实测机是 128 字节，为什么不干脆全仓库写死 `const LINE: usize = 128;`，还要探针干什么？

::: sol 解答

写死 128 与写死 64 犯的是同一个错误，只是方向相反：缓存行大小是宿主属性，不是语言常数。代码要迁到 64 字节行的 x86、乃至未来更大的行上时，硬编码要么浪费内存、要么重新制造[@def-11.5.1]。正确姿势是运行时探测（`hw.cachelinesize`）或以最大合理值对齐并留注释，把「对齐按机器、不按传闻」写成不变量。11.1 的表早就警告过：无锁的硬件压力「依争用拓扑而定」，布局声明就是拓扑的一部分。
:::

### 11.5.4 小结与常见错误

**小结。**① 原子变量的物理落位是并发协议参数：同一条缓存行上的两个逻辑独立变量，会被硬件当成同一个争用对象（[@def-11.5.1]）。② 缓存行大小按宿主探测——本书实测机为 128 字节，64 字节硬编码在 Apple Silicon 上不成立（[@think-11.5.1]）。③ `ArrayQueue` 用槽位世代号同时解决「过期指令」与「读写解耦」，是[@def-11.3.2]两问检验的正面样本（[@def-11.5.2]）。④ 代码生成核对显示：纯算术已被 LLVM 压到移位加法，瓶颈只剩原子、屏障与一致性。⑤ 类型尺寸表要用探针维护，不能靠记忆。下一节 [11.6 有界无锁队列对决互斥锁队列](#sec-cpp-rust.3.11.6) 用 21 批实测回答「无锁更快」这句口号的两面性。

::: errata 常见错误清单（11.5 节）

E-a **在 128 字节缓存行架构上硬编码 64 字节对齐。**64 字节填充跨不过物理缓存行，原子变量间依然发生严重伪共享（[@def-11.5.1]、[@ex-11.5.1]）。

E-b **把缓存行大小当语言常数。**它是 `hw.cachelinesize` 探测值，跨机型不能移植（[@think-11.5.1]）。

E-c **只给 `head` 对齐、忘给 `tail`。**半对齐全对齐全无：只要两个高频原子字段有同线的可能，弹跳就可能发生。

E-d **拿类型尺寸表凭记忆核对新结构。**表中每一格都来自探针实测；改动字段后旧表立即失效，要重新生成。

E-e **以为 stamp 只是防 ABA 的注释。**它是提交判定的一部分：写者要 `stamp == tail`、读者要 `stamp == head + 1`，对不上就不获准（[@def-11.5.2]）。

E-f **盯着汇编找「无锁慢在哪」。**算术分支已被优化到极致，汇编核对的正确用途是确认原子指令选型（`ldapr`/`stlr`/`casal`），瓶颈归因交给计时与一致性层（11.5.3）。

:::

**第 2 题 · 辨析**　`ArrayQueue` 的 stamp 与 11.3 的 Tagged Pointer 都在「防过期」，机制区别是什么？

::: sol 第 2 题答案
Tagged Pointer 防的是**指针 CAS 误提交**：地址相同、Tag 不同即拒绝，保护单字比对（[@def-11.3.1]）。stamp 防的是**槽位轮次误读写**：把轮次编进每格状态条，读写授权按值匹配，保护的是访问权限而非指针（[@def-11.5.2]）。前者防 ABA 事故，后者让 ABA 无从成立，还顺带解耦读写。

::: sol 第 3 题答案

### 11.6.1 实验设计与测量边界

入口文件：`bench/systems-lab/src/bin/queue.rs`。

在很多技术讨论中，人们脱离并发度、队列长度与争用模型，抽象地声称「无锁队列碾压互斥锁」。「碾压」不是可以测量的量，脱离这三项，这句话就无从判真假。本实验旨在构造一个严格受控的双生产、双消费并发交错场景，进行端到端的吞吐与抖动量化比较。

实验配置与测试协议：

- **并发环境**：在 `std::thread::scope` 内拉起 2 个生产者线程与 2 个消费者线程。
- **任务总量**：每个生产者生产 32768 项，总计处理 65536 项数据。
- **同步起点**：4 个工作线程用 `std::sync::Barrier` 同起点激活，避免启动先后造成假性单线程吞吐。
- **正确性检验**：消费者用全局原子索引领取份额，全部消费出来的 `u64` 回主线程做多重集排序检验（[@def-11.6.1]）：不比对总和，而断言 `0..65536` 每个整数不多不少恰好一次、队列最终完全清空；漏数或重数立即 panic。
- **两种被测结构**：
  1. `Mutex<VecDeque<u64>>`：标准库互斥锁悲观保护的循环缓冲区，带有相同的 1024 元素容量限制，队列满时退让，队列空时自旋尝试。
  2. `ArrayQueue<u64>`：Crossbeam 提供的基于 128 字节对齐填充的高性能有界环形无锁 MPMC 队列（对齐依据见 11.5 探针表）。

::: def 定义 11.6.1 · 多重集校验 {#def-11.6.1}

**多重集校验**指把「消费到的全部元素」排序后与参考序列逐位比对：长度相等、且第 $i$ 个元素恰为 $i$。它比「比对总和」强得多——总和对「漏掉 3、重放两次 3 以外的组合」完全不敏感。并发实验里，这是把「吞吐数字」与「正确性」绑在同一份产物上的最便宜手段。
:::

### 11.6.2 核心源码与验证范式

被测的队列抽象封装与多线程校验核心如下：

```rust
// bench/systems-lab/src/lib.rs 中的关键评测骨干
pub fn queue_batch(ring: bool, each: usize) -> u64 {
    let q = Queue::new(ring, 1024);
    let ready = Barrier::new(4);
    let total = each * 2;
    let next = AtomicUsize::new(0);
    
    let results = std::thread::scope(|scope| {
        // 启动两个生产者
        for producer in 0..2 {
            let q = &q;
            let ready = &ready;
            scope.spawn(move || {
                ready.wait();
                for index in 0..each {
                    let mut value = (producer * each + index) as u64;
                    while let Err(v) = q.push(value) {
                        value = v;
                        std::hint::spin_loop();
                    }
                }
            });
        }
        
        // 启动两个消费者
        let mut consumers = Vec::new();
        for _ in 0..2 {
            let q = &q;
            let ready = &ready;
            let next = &next;
            consumers.push(scope.spawn(move || {
                ready.wait();
                let mut received = Vec::with_capacity(each);
                loop {
                    let ticket = next.fetch_add(1, Ordering::Relaxed);
                    if ticket >= total {
                        break;
                    }
                    loop {
                        if let Some(v) = q.pop() {
                            received.push(v);
                            break;
                        }
                        std::hint::spin_loop();
                    }
                }
                received
            }));
        }
        
        consumers
            .into_iter()
            .flat_map(|h| h.join().expect("consumer panic"))
            .collect::<Vec<_>>()
    });
    
    // 严格的多重集比对：绝不依赖简单的散列加和！
    let mut sorted = results;
    sorted.sort_unstable();
    assert_eq!(sorted.len(), total);
    assert!(sorted.iter().enumerate().all(|(i, &v)| v == i as u64));
    assert_eq!(q.pop(), None);
    sorted.iter().sum()
}
```

消费者取票用的 `fetch_add` 索引导流是刻意为之。两个消费者不是「谁先到谁多拿」，而是按票领份额，消费进度本身也构成一份可复核的账。

### 11.6.4 结果的深度工程洞察

::: intuition 无锁并不自动代表低抖动

实测数据揭示了一个反直觉的性能规律：

1. **吞吐量维度**：在 4 线程中高竞争下，无锁 `ArrayQueue` 凭借消除内核态切换与 128 字节缓存行解耦，均值耗时从 72.86ns 下降至 40.65ns，加速比达到 **1.79x**。
2. **确定性维度**：互斥锁的样本标准差仅为 2.68，而无锁队列的标准差高达 8.02。最快单批次跑进 25.6ns，最慢一批漂到 53.2ns。机制上应是原子 CAS 重试碰撞与总线仲裁，**但本轮没有采集重试计数，这句只是推断**。无锁结构的乐观重试在遭遇多核强争用时会让个体尝试次数剧烈波动。在有硬实时（Hard Real-Time）确定性约束的场景中，互斥锁或基于 Wait-Free 算法的设计反而具有更高的可预测性。
:::

::: ex 例 11.6.1 · 三个句子各错在哪 {#ex-11.6.1}

同事从这份表里摘了三句话发进技术群，逐句用本节数据判定：

1. 「无锁 p99 是 53.2ns，比互斥锁的 p50 72.6ns 还低，全面碾压。」
2. 「均值 40.6 对 72.9，换无锁后我们的尾延迟一定更好。」
3. 「第 5 批跑出 25.6ns，说明队列能稳定跑到 25ns。」

::: sol 解答

1. 跨分位数比大小：p99 与 p50 不是同一个统计量（[@def-1.5.2]）。同列对同列，无锁 p50 40.68 对互斥 p50 72.59 才是加速比的正确读法。
2. 均值口径是批均值（[@def-1.2.2]），回答的是吞吐；这里没有任何逐请求观测，说不了请求级尾延迟。能说的是批次间抖动：无锁标准差 8.02，是互斥锁 2.68 的近三倍，「尾更稳」的方向恰恰相反。
3. 25.6ns 是 21 批里最快的一批（Round 5，交错极度协调、无碰撞重试），单点最优值不能当稳态；均值仍是 40.65。三句话共同的病根：把聚合数字拆出来单卖（[@def-11.6.1] 绑定的正确性账本则完好——数据一个没丢，这倒可以放心引用）。
:::

::: method 判定流程 · 选锁还是选无锁

① **先问约束类型**：场景有没有硬实时/尾延迟契约？有——[@def-11.1.2] 的 Wait-Free 或干脆互斥锁，不要默认无锁（本表 2.68 对 8.02 的抖动差就是价码）。<br>
② **再问争用度**：核心数远大于线程数、碰撞罕见时，无锁优势最大（Round 5/6 型批次）；线程超订时先想 11.1.2 的自旋预算陷阱。<br>
③ **查释放责任**：结构会增删节点吗？会就必须连同 SMR 一起预算（11.4/11.7），「无锁」从不是单个组件的属性。<br>
④ **用同一协议复测**：21 批、交替顺序、多重集校验（[@def-11.6.1]）三件齐，才许说「实测」。
:::

::: think 思考 · 把领票换成「pop 到空就收工」，哪一份账先坏 {#think-11.6.1}

11.6.2 的消费者先 `fetch_add` 领票、领满才走，队列空时自旋。有人嫌它绕：直接 `pop` 拿到 `None` 就退出，代码短一半。按本节的校验口径，这个改法先破坏什么？

::: sol 解答

先坏的是终止条件的可信度。「队列为空」有两种成因：生产者暂时落后，与生产者已经收工；一次 `None` 区分不了二者。提前退出会让 `sorted.len()` 小于 total，[@def-11.6.1] 的逐位断言当场 panic；若改成一直自旋，又可能在真正收工之后停不下来。取票把终止条件绑回「总量已知」这件事上，两个消费者各领到多少票还留下一份可复核的进度账。至于省下的那次原子加值不值，本节没有单独采集，不能拿它当改法收益的依据。

### 11.6.5 小结与常见错误

**小结。**① 同一台 M5 Pro、同一份 21 批协议下，`ArrayQueue` 均值 40.65ns/item、加速比 1.79x，证据链完整（[@def-11.6.1]）。② 代价写在同一行：标准差 2.68 放大到 8.02，乐观重试（[@def-11.1.3]）在强争用批次里制造 53ns 级慢批。③ 批均值不回答尾延迟（[@def-1.2.2]），跨分位数比较不成立（[@ex-11.6.1]）。④ 硬实时场景里「方差小」本身就是性能指标。⑤ 正确性与计时绑在同一产物上，快才有意义。下一节 [11.7 停顿参与者的回收代价](#sec-cpp-rust.3.11.7) 把镜头从耗时切向内存。

::: errata 常见错误清单（11.6 节）

E-a **认为无锁队列的延迟一定全面优于互斥锁。**重试回退让标准差从 2.68 走到 8.02；慢批 53.2ns 目前只有机制推断，没有实测归因（[@ex-11.6.1]）。

E-c **拿最快批次当稳态。**Round 5 的 25.6ns 是一次幸运交错。

E-d **把批均值说成请求级延迟。**本实验没有逐请求观测，只有 65536 项/批的摊薄值（[@def-1.2.2]）。

E-e **只比总和当校验。**漏一补一总和不变；本节用的是多重集逐位断言（[@def-11.6.1]）。

E-f **忽略被测对象的对称性。**两种队列同为 1024 容量、同一起跑 Barrier；换任一条件，1.79x 就不能再引用。

## 11.7 benchmark二：静止状态延迟与停顿参与者的回收代价 {#sec-cpp-rust.3.11.7}

本节回答一个问题：**一个「什么都不干」的线程，能把 EBR 的内存账搞坏到什么程度？**11.4 的[@def-11.4.3]说代价推迟给最慢的读者；这一节把「最慢」做成实验：一个人攥住 Guard 不放，看全系统的 `dropped` 计数器怎么停表。

::: preview 先抓住一件事

实测：单线程停滞期间连续退休 4096 个 256 字节对象，`dropped` 恒为 0，滞留堆内存涨到 1,048,576 字节；`drop(guard)` 的一瞬间 4096 个对象集中销毁（[@def-11.7.1]）。回收速度的上限，由全场最慢的那个 Guard 决定。
:::

### 11.7.1 停顿参与者（Stalled Thread）的致命威胁

EBR 的优雅在于读者近乎零成本的代际注册。它最大的阿喀琉斯之踵是：**整个系统的垃圾物理回收速度受制于系统中最慢的那个停顿线程**。

::: def 定义 11.7.1 · 静止状态与停顿参与者 {#def-11.7.1}

**静止状态（Quiescent State）**指某个线程的一次 `pin()`/`unpin()` 周期已经闭合、旧代际观测已确定失效的时刻。所有活跃线程都越过静止点，全局纪元才能推进。**停顿参与者**是反面角色：进入保护区后长时间不闭合 Guard 的线程。它没有在做任何并发坏事，只是「不出去」，就把所有人的回收闸门顶住了（[@def-11.4.3] 支柱 4 的失效率形态）。它拖住的不是某一个对象，而是整条回收流水线。
:::

如果一个线程通过 `guard = collector.register().pin()` 建立了保护，随后在持有该 `Guard` 的期间进行了一次耗时极长的网络 I/O、磁盘读写或陷入了死循环，会发生什么？

- 该线程的局部纪元永远停留在旧的代际。
- 全局纪元无法跨越推进。
- 其他所有工作线程即便高频地将数以万计的对象标记脱钩（Retired），这些对象也全部只能被积压在各个线程的内存垃圾袋中。**一个字节都无法被真正释放回操作系统**。
- 最终直接引发内存枯竭（OOM）。

### 11.7.2 实验设计与内存滞留测量

入口文件：`bench/systems-lab/src/bin/epoch.rs`。我们在实验中构造了具有严格生命周期计数器的析构探针 `Retired`：

- 每个探针对象在堆上申请 256 字节载荷，并在其 `Drop` 实现中原子累加一个全局析构计数器 `dropped`。
- **Case 1 (short_pin)**：工作线程在短生命周期的 Guard 保护下注销一整批 **8192** 个对象（`epoch.rs` 的 `COUNT`，也就是 `epoch.txt` 里的 `units=8192`），批末再 drain 一次。
- **Case 2 (stalled_pin)**：探针全程单线程——同一个 `holder` 先 `pin()` 出一个长期不释放的 Guard 充当「停滞的读者」，再注销同样 8192 个对象；「停滞线程」是这个 Guard 模拟的，不是第二个线程（`epoch.rs:7-10`）；工作线程随后以相同方式注销同样 8192 个对象——两批的析构总量相同，不同的只是这些对象在批内能不能被回收。

1024 → 4096 那段递增不属于计时批，是另做的滞留观测：每步多注销 1024 个，读 `dropped` 与 `payload_bytes`。

```rust
// bench/systems-lab/src/lib.rs 中的关键回收度量探针
pub struct Retired {
    payload: Box<[u8; 256]>,
    dropped: Arc<AtomicUsize>,
}

impl Drop for Retired {
    fn drop(&mut self) {
        black_box(self.payload[0]);
        self.dropped.fetch_add(1, Ordering::Relaxed);
    }
}

pub fn epoch_batch(stalled: bool, count: usize) -> u64 {
    let collector = Collector::new();
    let holder = collector.register();
    let worker = collector.register();
    let dropped = Arc::new(AtomicUsize::new(0));
    
    // 如果模拟停顿，holder 线程将 Guard 长期悬挂在栈上！
    let guard = stalled.then(|| holder.pin());
    
    retire(&worker, &dropped, count);
    let retained = count - dropped.load(Ordering::Relaxed);
    if stalled {
        // 核心断言：停顿期间，被注销的对象必须 100% 滞留！
        assert_eq!(retained, count);
    }
    drop(guard);
    
    // 解开停顿保护后，等待系统安全将积压对象全数回收
    drain(&worker, &dropped, count);
    assert_eq!(dropped.load(Ordering::Relaxed), count);
    count as u64
}
```

断言本身就是实验假设的可执行陈述：`stalled` 为真时 `retained == count` 必须成立，一个对象都不许被释放。

::: think 思考 · 再多两个停滞线程，1 MB 积压会变成 3 MB 吗 {#think-11.7.1}

本节只有 `holder` 一个线程攥着 Guard。有人担心三个线程同时停滞会把滞留内存乘三。对照[@def-11.7.1]的推进判据，看这个担心对不对。

::: sol 解答

方向不对。纪元推进要等「所有活跃线程都闭合过 Guard」，一个不放行和三个不放行顶住的是同一道闸门。积压由退休速率乘以闸门闭合前的时长决定，与停滞线程的个数不成倍数关系。随人数变化的不是积压上限，而是风险结构：闭合要等最慢的那一个，参与者越多，最慢者越晚到，[@def-11.4.3]的代价推迟越难预估，`after_unpin` 那次集中释放的爆发也越大。三个停滞线程的实际曲线本节没有采集，不能替它填数字。

:::

### 11.7.4 小结与常见错误

**小结。**① EBR 的回收速度等于最慢 Guard 的速度，这是[@def-11.4.3]承诺过的代价在实测中的形状（[@def-11.7.1]）。② 停滞期间 4096 个对象 100% 滞留、1 MB 分毫不差、`dropped` 恒为 0——协议按设计失效，不是偶发事故（[@ex-11.7.1]）。③ unpin 后 4096 个对象在一次代际推进里集中释放，是日志事实；尖刺幅度本轮未采。④ 36.9% 的均值劣化是总账，逐阶段归因本节没有采集。⑤ 停顿参与者的判据是「静止状态是否闭合」，与其在做什么无关。下一节 [11.8 RCU 机制](#sec-cpp-rust.3.11.8) 把同一原理放到内核与异步运行时里检查边界。

::: errata 常见错误清单（11.7 节）

E-a **把 Guard 持有时长不当容量指标。**1 MB 积压只是 4 批；持续退休的产线里积压与持有时间成正比（[@def-11.7.1]）。

E-b **只盯均值 36.9%，忽略爆发式释放。**`after_unpin` 的集中销毁同样是要预算的事件（[@ex-11.7.1] 第 3 问）。

E-c **用「线程没在做坏事」排除停顿嫌疑。**停滞参与者的定义就是不闭合 Guard；无辜不等于无害。

E-d **把 retention 日志读成 RSS。**`payload_bytes` 只计探针载荷，垃圾袋簿记与分配器元数据不在内（[@ex-11.7.1] 第 1 问）。

E-e **以为高频 `retire` 会倒逼纪元推进。**判据在 11.4.4 支柱 4：退休再多也只加深袋子。

E-f **拿两场景总耗时差拆机制归因。**逐阶段成本未采集，36.9% 只能说「更慢」，不能说「慢在哪一步」。

:::

## 11.8 RCU机制与用户态异步的协同与边界 {#sec-cpp-rust.3.11.8}

本节回答一个问题：**内核 RCU 那句「等所有读者都看完再释放」，搬进用户态异步任务时要补哪几张票？**11.7 已经把「最慢的 Guard」兑成 1 MB 滞留账；这一节回到契约本身，逐条核对 RCU 的便宜是从谁身上预支的。

::: preview 先抓住一件事

RCU 的宽限期之所以短，是因为读者被承诺「不睡、不搬、不缺席」；一个 `.await` 同时撕掉这三张承诺。**判断一段读侧代码能不能用代际保护，不看它加没加锁，只看 `Guard` 的驻留期里有没有让出点。**失效形态不是编译错误，而是 11.7 实测的回收冻结（[@def-11.7.1]）。
:::

### 11.8.1 内核 RCU 的三条前提

Linux 内核中的 RCU（Read-Copy-Update）是 SMR（安全内存回收，[@def-11.4.1]）在操作系统层面的实现。我们核读了 MIT 6.828/6.S081 的 RCU 核心讲义（母本落盘在 `sources/archive/systems/mit-rcu.txt`，来源台账里登记为 `systems-mit-rcu`，抓取自 `pdos.csail.mit.edu/6.828/2024/lec/l-rcu.txt`），把它的契约压成三条：

- 经典 RCU 假设内核不会在读侧临界区里调度走。`rcu_read_lock()` 只做一个标记，并不加互斥锁。**括号里那句「可抢占内核里同时关抢占、记深度」不来自这份 MIT 讲义**（讲义内 `preempt`/`ksoftirqd`/`idle` 零命中），它是 Linux 侧的通行说法，本轮没有核读 Linux 源码，因此只当背景，不计入已核实。
- 读者在访问受保护数据时，绝不允许主动休眠或让出 CPU。这条假设不是实现细节，而是宽限期能推进的前提。
- 写者修改数据时先通过指针赋值发布新版本。旧节点要等**系统中所有 CPU 核心都至少经历一次上下文切换（Context Switch）**，度过一个宽限期之后，才经回调 `kfree` 回收。

第三条是 SMR 的通例；前两条是 RCU 特有的预支：读侧几乎零成本，账单记在「宽限期不会太长」这个假设上。

::: def 定义 11.8.1 · 宽限期 Grace Period {#def-11.8.1}

**宽限期**指从写者发布新版本，到旧版本被允许释放之间的那段等待。判据不是「过了多少毫秒」，而是「每个可能的观测者都至少越过一次静止状态（[@def-11.7.1]）」。内核里数 CPU 的上下文切换，用户态 EBR 里数线程 `pin()`/`unpin()` 周期的闭合。宽限期是计数事件，不是计时器。

:::

::: def 定义 11.8.2 · 读侧临界区 Read-side Critical Section {#def-11.8.2}

**读侧临界区**指从 `rcu_read_lock()` 到 `rcu_read_unlock()` 之间的那段代码。经典 RCU 的全部便宜都建立在一个前提上：这段区间里读者不睡眠、不让出、不阻塞。读者一旦睡过去，它就变成 11.7 的停顿参与者——人不在场，票还攥着，宽限期照样被顶住（[@def-11.8.1]）。

:::

读者不睡，宽限期才短。RCU 用读侧的自由度，换写侧的等待时间。

### 11.8.2 五格对照：内核 RCU 与用户态 EBR

下表系统比对 Linux 内核 RCU 与用户态 EBR 的运作机制：

| 机制属性 | Linux 内核 RCU | 用户态 Crossbeam-Epoch (EBR) |
|:--|:--|:--|
| **读者进入标志** | `rcu_read_lock()`（讲义只说「做一个标记」；关抢占与深度计数属 Linux 实现细节，母本未证） | `collector.pin()` (设置本地活跃位与代际) |
| **静止状态定义** | CPU 执行上下文切换、进入 idle 或系统调用返回 | 线程显式调用 `flush()` 或离开 `Guard` 作用域 |
| **宽限期等待原语** | `synchronize_rcu()` / `call_rcu()` 回调 | `guard.defer(f)` / 轮询代际状态自动推进 |
| **抢占容忍度** | 经典 RCU 严禁在读侧睡眠（`PREEMPT_RCU` 是 Linux 自身的演进，登记的 MIT 讲义没有这个词，此处算背景不算核读结论） | 用户态线程随时可能被 OS 剥夺，必须依赖主动刷新 |
| **回收触发点** | 内核里由软中断一类机制批处理释放（`ksoftirqd` 未见于母本，属背景） | 工作线程在 `pin()` 或分配时的协作分摊回收 |

读表的方法：前三行是同一套流程的三个环节——进门盖章、出门撕票、等所有人撕完票再倒垃圾。分水岭在第四行：内核可以要求读者不许睡，用户态线程做不到，它随时可能被操作系统剥夺 CPU。于是 EBR 不能假设读者「在场」，只能要求它主动刷新（[@def-11.4.3]）。第五行的回收触发点也随之从内核软中断，挪到工作线程的协作分摊（11.4.5 的垃圾袋流转）。

### 11.8.3 用户态异步：驻留期交给了执行器

许多 Rust 工程师试图在 Tokio 异步任务里模仿内核 RCU，写出下面这种形式的代码：

```rust
// 严重的设计缺陷模型：切勿在异步环境这样编写
async fn bad_async_rcu_reader(collector: &Collector) {
    let guard = collector.register().pin();
    // 异步网络请求，此点可能产生不可预期的等待！
    let response = fetch_remote_data().await; 
    process(guard, response);
}
```

::: def 定义 11.8.3 · 守卫驻留期 Guard Residency {#def-11.8.3}

**守卫驻留期**指从 `pin()` 成功拿到 `Guard`，到它被 `drop` 之间的整段时间。EBR 推进代际要求所有活跃驻留期闭合（[@def-11.7.1]）；同步代码里这段长度由函数体写死，异步代码里它由调度器和下游 I/O 决定。

:::

上面那个读侧函数，把驻留期交给了 `fetch_remote_data()` 的对端。后果有两类，都是确定的：

1. **持有期不可控**：下游 I/O 一旦阻塞，任务被执行器长久卸下，全局代际回收被封冻，直到对端回包。驻留期的长度不再由这段代码说了算。11.7 已经用 4096 个对象、1,048,576 字节的滞留把这种形态演过一遍。
2. **跨线程迁移破坏局部性**：多线程运行时可能在唤醒后把任务窃取到另一个工作线程，而 `Guard` 内部可能绑定了初始注册线程的 thread-local 上下文。代际计数因此产生竞态，甚至触发断言崩溃。

正确的工程范式一句话：**在纯同步、无挂起、有界的闭包里读指针，克隆不可变快照（如 `Arc<T>`）后立刻退出 Guard，再进入异步悬挂。**保护的是读取的那一瞬间，不是你打算用它的那几秒。

::: ex 例 11.8.1 · 慢 I/O 面前，这段读侧代码的账怎么算 {#ex-11.8.1}

把上面的 `bad_async_rcu_reader` 放进 4 线程运行时，`fetch_remote_data()` 因为对端重传卡住 30 秒。回答三问：

1. 这 30 秒里，`Guard` 的驻留期覆盖了什么？
2. 同进程里别的线程一直在 `retire`，这 30 秒的 `dropped` 会怎样？能报出数字吗？
3. 改成什么写法，驻留期才重新有界？

::: sol 解答

1. 覆盖了取数、等对端、回包与 `process` 的全过程。驻留期长度由网络对端决定，函数体已经管不住它（[@def-11.8.3]）。
2. 按 11.7 的实测形态，只要这张票不撕，别的线程退休多少都释放不了：`stalled_pin` 场景 4 批、4096 个 256 字节对象时 `dropped` 恒为 0，`payload_bytes` 停在 1,048,576。async 版本的滞留量本节没有采集，只能给形态，不能给数字。
3. 快照交接：在 Guard 里把 `process` 需要的字段克隆成 `Arc<T>` 或值，`drop(guard)` 之后再 `.await`；恢复后若还要读共享结构，重新 `pin()` 拿一张当前代际的新票。

:::

:::

::: think 思考 · 「await 前后各查一次版本号，不就能跨了吗」 {#think-11.8.1}

有人说：只要在 `await` 前记下节点版本、`await` 后比对一次，版本没变就继续用，`Guard` 跨挂起点也无妨。这个方案漏掉了哪个前提？

::: sol 解答

漏掉的是「保护在什么时候结束」。EBR 保证的是 Guard 存活期间对象不被释放，不是对象值不会变。Guard 一结束，旧节点可能已被释放，地址再被分配器复用（[@def-11.3.2] 的物理形态），你比对版本号时读到的可能已经是新对象的内存。版本字段本身就在那块可能已释放的内存里。版本号只能说明逻辑值恰好相同，替代不了驻留期；跨挂起点的正确做法始终是缩小驻留期，而不是加检查。

:::

:::

::: method 判定流程 · 守卫能不能跨过这个挂起点

① **画驻留期**：从 `pin()` 到 `Guard` 析构，把路径上每个 `.await`、阻塞读写、锁等待、`yield_now` 标出来。<br>
② **找挂起点**：只要有一个落在驻留期内，判「不可跨」，先做快照交接（[@def-11.8.3]）。<br>
③ **量上界**：纯同步也要有界——循环拉取、指数退避重试、无界遍历都会把驻留期拉长，按 11.7 的滞留形态做容量预算。<br>
④ **长保护换机制**：整段流式处理要么改成 `Arc` 快照加版本重试，要么用 HP 的逐指针保护（11.4.7 对照表「内存滞留上限」一行）。别让 EBR 替你的不确定性背书：它替不了。<br>
⑤ **留证据**：在测试构建里导出 retired 与 dropped 的曲线，驻留期与回收的对应关系才看得见（11.7 的 retention 日志就是模板）。
:::

### 11.8.4 小结与常见错误

**小结。**① 宽限期是「每个观测者都越过静止状态」的计数，不是计时器（[@def-11.8.1]）。② 经典 RCU 的便宜向读侧预支：临界区里不睡、不搬、不缺席（[@def-11.8.2]）。③ 用户态 async 的 `.await` 一次撕掉三张承诺，守卫驻留期从此由执行器和 I/O 决定（[@def-11.8.3]）。④ 失效形态是回收冻结，11.7 用 1 MB 滞留实测过，async 版本本节没有采集。⑤ 正确姿势是快照交接：Guard 里读、拷、退，挂起前放手。下一节 [11.9 母本对应与来源核读](#sec-cpp-rust.3.11.9) 把本节引用的讲义集中登记。

::: errata 常见错误清单（11.8 节）

E-a **跨 `.await` 持有 Guard。**驻留期由对端 I/O 决定，回收整段冻住（[@def-11.8.3]；11.7 的 0 dropped 形态）。

E-b **把「读者不加锁」当成「读者无代价」。**经典 RCU 的代价是读侧不许睡（[@def-11.8.2]）。

E-c **用 `rcu_read_lock` 的心智写 async 读侧。**用户态线程随时被剥夺，EBR 只能靠主动刷新（11.8.2 表第四行）。

E-d **clone 出裸指针就以为延长了保护。**保护随 Guard 结束，指针立刻可能被释放复用（[@def-11.8.2]）。

E-e **把 Guard 交给别的线程收尾。**任务唤醒可能落到另一个 worker，绑定的线程局部状态对不上，断言或计数竞态随之出现（11.8.3）。

E-f **用版本号比对替代驻留期。**释放与地址复用可能已经发生，比的是新对象的内存（[@def-11.3.2]）。

:::

## 11.10 常见错误索引 {#sec-cpp-rust.3.11.10}

这是本章的跨节错误索引：每一节末尾都有自己的「::: errata 常见错误清单（11.M 节）」，按你阅读的顺序给出局部清单。下面这一份只收那些要读完整个章才浮出来的错误，它们在单节内部看不出问题，放进整章的并发链条才露馅。

**把自旋锁当成无锁结构。** 自旋锁在语义上仍是悲观互斥，持锁线程被抢占会让所有等待者一起停摆，一级进度保证都不满足（[@def-11.1.2]）。判断时要看全局进展由谁保证，而不是看代码里有没有原子指令。

**以为 CAS 天然能防 ABA（11.3 E-a）。** 只要比对单元是指针、目标内存可能 free 再 malloc，就必须上 SMR 或双字标记（[@def-11.3.2]）。

**在 128 字节缓存行的机器上硬编码 64 字节对齐。** 在 Apple Silicon 这类芯片上，64 字节对齐跨不过物理缓存行，相邻原子变量仍会互相拖拽。对齐参数要按目标机的缓存行宽度取，不能照搬 x86 的习惯（[@def-11.5.1]）。

**跨越 `.await` 持有 Epoch Guard。** 让出点会把守卫驻留期交给调度器和下游 I/O，长度不再由函数体决定（[@def-11.8.3]）。一张迟迟不撕的票会冻住整条回收流水线，11.7 的 `stalled_pin` 场景已经把这种形态量化过。

**认为无锁队列的延迟全面优于互斥锁。** 无锁结构的重试回退会让高竞争下的标准差明显走高，尾延迟反而恶化。比较时至少要说清是均值还是分位数，跨统计量比大小是这类误读的常见来源（[@ex-11.6.1]）。

**用纯指针自增解决 ABA 却不处理环绕。** 标签位宽有限，高吞吐下 Tag 会快速回绕，ABA 重新出现。要么把标签加宽到双字原子，要么用 SMR 把地址复用挡在回收之后（[@def-11.3.2]）。

**在 EBR 中忘记 `flush()` 或主动退出（11.4 E-c）。** 回收是协作式的：读者不推进代际，写者那边的 `defer` 就只是记账（[@def-11.4.3]）。

**把 `crossbeam_epoch::unprotected()` 用于并发写入（11.4 E-d）。** 把它当捷径，等于把 SMR 的承诺整个撤掉（[@def-11.4.1]）。

**假定 Wait-Free 的吞吐必然高于 Lock-Free。** 为了给每个线程步数上界，Wait-Free 通常要加辅助队列与状态同步，常规吞吐常数反而更大（[@def-11.1.2]）。进度保证与吞吐是两个维度，不能互相代替。

**在析构回调里做可能死锁的加锁操作。** EBR 延迟执行的 Drop 回调发生在未知线程与未知的代际推进时刻，在析构里加锁很容易形成反向的加锁顺序。回调里只做释放，不要再去抢共享结构的锁。

**忽略分配器对地址复用的敏感性。** 高性能分配器倾向立刻复用刚释放的热块，没有 SMR 保护的裸指针 CAS 撞上 ABA 的概率因此很高（[@def-11.3.2]）。这也解释了为什么「本机没复现」不能当成「不会发生」。

**把测试通过当成无锁算法正确的证明。** 数据竞争与 ABA 依赖极罕见的交错，单元测试替代不了线性化论证与模型检验（[@def-11.2.1]）。跑一万次全绿，证明的也只是这一万次没撞上，不是别的交错都不存在。常规做法是先用 Loom 之类的工具枚举小规模交错，再在真实负载上测性能。

## 11.11 本章小结与章末件 {#sec-cpp-rust.3.11.11}

::: note 本章小结

- 进度保证分三级：无阻碍、无锁、无等待，自旋锁一级都不占（[@def-11.1.2]、[@ex-11.1.1]）。
- 线性化点把每次调用钉在时间轴的一个瞬间，是判断并发对象语义的基准（[@def-11.2.1]、[@ex-11.2.1]）。
- ABA 的根因是地址被复用，不是 CAS 指令本身；裸指针 CAS 必须配 SMR 或双字标记（[@def-11.3.1]、[@def-11.3.2]）。
- HP 保护单个指针，读者每次解引用都要付费；EBR 保护一段时间，代价推给最慢的在场者（[@def-11.4.2]、[@def-11.4.3]）。
- 无锁队列的均值可以更低而标准差更大，批均值不回答请求级尾延迟（[@def-11.6.1]、[@ex-11.6.1]）。
- 停滞的 Guard 会冻住整条回收流水线，滞留量可以用析构计数器直接读出来（[@def-11.7.1]、[@ex-11.7.1]）。
- 宽限期是计数事件而不是计时器，异步读侧要克隆快照后立刻退出 Guard（[@def-11.8.1]、[@ex-11.8.1]）。

:::

### 出口检查

从 `cpp-rust/bench/systems-lab` 执行下面三条命令，核验标准差与分位数输出；换机器复跑时先对齐编译选项与线程数，再比较数字。

```bash
cargo test --offline --locked
target/release/queue
target/release/epoch
```

差异归因要能回答两个问题。第一，4 线程实测中 `ArrayQueue` 的平均耗时降到 40.65ns，标准差为什么反而比互斥锁放大了近 3 倍（[@ex-11.6.1]）。第二，`epoch` 探针里单线程停顿 Guard 存活时，累计 4096 个注销对象的 `dropped` 计数器为什么在解开 Guard 之前一直是 0（[@ex-11.7.1]）。

汇编层面，你应能在生成文件里指出 `scalar_step` 如何用 `add w8, w8, w8, lsl #1` 消掉硬件乘法。

最后检查自己能否把范围说清：本章实现的是 Lock-Free 有界环形队列与 EBR 回收的量化，既没有宣称实现全功能 Wait-Free 链表队列，也没有宣称给 Linux 内核的 RCU 打了就地补丁。
