## A 组 · 概念（1–7）

::: ex A1 · 三个词与一个字（主线 ①） {#ex-9.A.1}

用一句话分别解释 poll、驱动、执行器；再写出任务状态字的关键性质，并说明它为什么不是「字段多」。

::: sol 解答

poll 是执行器拿着一个 `Waker` 去问一次 Future「你现在能往前推进吗」，返回值只有 `Pending` 与 `Ready` 两种。驱动是反复 poll 同一个 Future 直到返回 `Ready` 并把输出交出去的过程，第 8 章的 `block_on` 就是最小驱动器。执行器是同时驱动许多 Future 的那个循环，连同它的队列、唤醒源与任务存储。

状态字的关键性质是**判断与改变发生在同一次原子操作里**，不存在「先读到没在跑，再单独写下我开始跑」这种可被插队的两步。对照[定义 9.1.1](ch09.md#def-9.1.1)、[9.1.1](ch09.md#sec-cpp-rust.3.9.1)。

:::

:::

::: ex A2 · 两条账为什么不能合并（主线 ①） {#ex-9.A.2}

运行权与通知责任各自保证什么？举出两者同时存在的一个时刻，并说明合并成一位会丢掉什么。

::: sol 解答

运行权保证 Future 不会被两个线程同时 poll，任意时刻至多属于一个 worker。通知责任保证有效 wake 之后未来有人重新检查这个 Future，是一笔「欠一次 poll」的账。两者可以同时存在：任务的 poll 正在跑，此时资源线程又调用了 `wake_by_ref()`，运行者仍持有运行权，同时账上多了一次待兑现的通知。若把两者压成同一个锁位，这次 wake 会被当成「已经在跑所以不必记」，poll 返回 `Pending` 后没有人再排它，于是丢掉一次 poll。对照[定义 9.1.2](ch09.md#def-9.1.2)。

:::

:::

::: ex A3 · 一个分配里的三个对象（主线 ①） {#ex-9.A.3}

任务单元里至少有三个语义对象，分别是什么？为什么「拿到了队列项」不等于「拿到了三个对象的访问权」？

::: sol 解答

三个对象是：被 poll 的 Future 存储（只有持有运行权的那次调用能以可变引用接触它）、对执行器可见的通知对象（代表那笔还没兑现的账）、等待结果的 `JoinHandle` 状态（决定输出什么时候被读走、观察者什么时候被叫醒）。它们可以协同布局在一个分配里，但各有自己的初始化、访问与销毁阶段；队列项只是任务单元的一个引用，窃取迁移的也是引用而不是 Future 的字节。对照[定义 9.1.3](ch09.md#def-9.1.3)、[9.1.6](ch09.md#sec-cpp-rust.3.9.1)。

:::

:::

::: ex A4 · 丢失唤醒的判定（主线 ①） {#ex-9.A.4}

一次 wake 已经发生、任务却再没被 poll。判定它是不是丢失唤醒，要看「有没有排过队」吗？正确的判据是什么？

::: sol 解答

不看排队。判据是「有没有人欠着一次 poll 且这笔账不会消失」：账要么挂在队列项上，要么挂在持有运行权的 worker 上，两边都不挂就是丢失唤醒。典型成因是 poll 返回之后直接把状态设成 idle，不检查并发登记的通知；那次 wake 恰好落在「通知已被清除」与「poll 已返回」之间，账就没人认领。这类缺陷不崩溃、不报错，只是永远不前进。对照[定义 9.2.1](ch09.md#def-9.2.1)。

:::

:::

::: ex A5 · 合并通知省什么（主线 ①） {#ex-9.A.5}

已被通知的任务再收到 wake 时走合并分支。它省掉了哪一步？为什么不能顺手把这次原子写降级为 relaxed？

::: sol 解答

省掉的是进展义务里「再次入队、再加一个引用」的动作。可见性义务还在：发起 wake 的线程此前可能已经把缓冲区写完，这个写要有一条能被后续 poll 观察到的边。降级为 relaxed 之前必须写出「哪一次 Acquire 读与哪一次 Release 写构成同步边」；若资源自身的协议提供了这条边，并且执行器不再承担可见性义务，才可以讨论。含糊不行。对照[定义 9.2.2](ch09.md#def-9.2.2)、[例 9.2.2](ch09.md#ex-9.2.2)、[思考 9.2.1](ch09.md#think-9.2.1)。

:::

::: ex A6 · 公平性是什么（主线 ①） {#ex-9.A.6}

写出公平性的定义、它依赖的两个前提、它与「轮流执行」的区别，以及它最常见的失效形式。

::: sol 解答

公平性是一类关于等待上界的承诺：在一定前提下，一个已经被唤醒的任务不会永远等不到 poll。两个前提是在途任务总数有上界、单次 poll 返回所需时间有上界。它不承诺均匀轮流，也不给用户可配置的硬实时常数；最常见的失效形式是饥饿——某些就绪任务因为策略偏向另一类任务而长期得不到执行。LIFO 槽（后入先出的暂存位）正是「局部性优化必须受公平性机制约束」的例子。对照[定义 9.3.2](ch09.md#def-9.3.2)、[定义 9.8.1](ch09.md#def-9.8.1)。

:::

::: ex A7 · 三个资源边界词（主线 ②） {#ex-9.A.7}

分别用一句话说清背压（让上游等一等或直接失败）、准入控制、许可寿命。为什么「有界通道容量 64」不能直接当成背压已经做了？

::: sol 解答

背压是下游处理不过来时，让上游「产生」等一等或直接失败的机制，约束产生速度与在途数量。准入控制是在做昂贵工作**之前**先取得名额，拿不到就等待或拒绝。许可寿命是凭证从取得到归还覆盖的时间段，必须罩住真实占用期。有界通道只锁住一段缓冲：`send` 等待容量，控制的是通道内部排队数量，不控制「已经创建、正在等 send」的任务数，每个任务还持有请求正文、连接引用与上下文。对照[定义 9.7.1](ch09.md#def-9.7.1)、[定义 9.7.2](ch09.md#def-9.7.2)、[定义 9.7.3](ch09.md#def-9.7.3)。

:::

## B 组 · 推理（8–14）

::: ex B8 · 四种观察状态各欠谁（主线 ①） {#ex-9.B.8}

版本内的状态转换可概括为四行：complete 不重新执行；already notified 合并并保持同步关系；running 设置 notified；idle 且未通知则设置 notified 并增加相应引用。逐行说明「是否产生新的提交责任」，并指出第三行与第四行的实质差别。

::: sol 解答

第一、二行是「否」，第三行是「由当前运行者负责」，第四行是「是」。这一列的含义是**这次 RMW（读-改-写）是否把一个还没兑现的账交给了明确的负责人**：「否」表示账早就在那儿，或者任务已经结束、账不再有对象，不是表示这次 wake 什么都不必做。第三行没有新增队列项，也没有新增引用，但把兑现人写成了当前运行者；第四行必须由队列项携带这笔账，所以要增加相应引用。对照 [9.2.1](ch09.md#sec-cpp-rust.3.9.2)、[例 9.2.1](ch09.md#ex-9.2.1)。

:::

:::

::: ex B9 · 报告写「窃取把并行度提高三倍」（主线 ④） {#ex-9.B.9}

同事在报告里写：「开启多线程后聚合 ns/step 从 2.602 降到 0.750，说明窃取把有效并行度提高到约三倍。」请指出这句话至少四处缺证据，并给出你能接受的改写。

::: hint 提示

先问：这个数除以的是 step 还是调用？「窃取」这一步本轮有没有打点？差值里还混着哪些成分？

:::

::: sol 解答

① 没有窃取打点：本轮没有采集 steal 次数与成功率，「窃取把任务搬过去」是推测而非观察。② 归因集合太宽：0.750 与 2.602 之间隔着业务并行、driver 路径、join 通知等至少五个成分，差值不属于任何单一成分。③ 单位误读：ns/step 是墙钟除以总 step 数，四个 worker 并行完成不同任务时，这个倒数本来就可以小于单线程一次调用的耗时，不能当成「一次调用只花 0.75 ns」。

④ 工作负载绑定：这是固定 128 任务 × 8192 步的纯 CPU 夹具，没有 I/O 与并发到达过程。可接受的改写是「在该工作负载、这台机器、这次运行里，4-worker 配置的聚合 ns/step 更低，约为单线程的三分之一」。对照[思考 9.3.1](ch09.md#think-9.3.1)、[例 9.5.1](ch09.md#ex-9.5.1)。

:::

::: ex B10 · offload 分支没有证明什么（主线 ①） {#ex-9.B.10}

有人总结 9.6：「`spawn_blocking` 让 20 ms 睡眠缩短到 13.633 µs，而且阻塞池是零成本的。」按 [9.6.4](ch09.md#sec-cpp-rust.3.9.6) 指出这句话的两处错误，并写出 offload 分支真正做到的那一件事。

::: sol 解答

两处错误。① 睡眠没有变短：两分支睡的同样是 20 ms，offload 只是把睡眠挪到阻塞池，执行器线程不必等它，观察延迟因此从 23.658 ms 量级落到 13.633 µs 量级。② 阻塞池不是零成本：若阻塞工作大量积压，队列延迟、线程数与内存仍会出问题；把 CPU 工作全丢进阻塞池也不保证吞吐提升。它真正做到的只有一件：异步执行线程不再被这一次 sleep 占住。对照[例 9.6.1](ch09.md#ex-9.6.1)、[9.6.4](ch09.md#sec-cpp-rust.3.9.6)。

:::

:::

::: ex B11 · 8 字节句柄与十万任务（主线 ②） {#ex-9.B.11}

容量规划写：「`JoinHandle` 只有 8 字节，所以十万个在途任务的控制开销不到 1 MB。」指出三处漏洞，并给出一个本章内做得到的更诚实估计方式。

::: hint 提示

句柄背后还有什么？分配器（向系统申请内存的组件）与对齐会做什么？不保存句柄时任务会停吗？

:::

::: sol 解答

① 混淆描述符与被指对象：句柄是观察者侧的句柄，任务单元（状态字 + Future + 输出 + 队列引用）才是被持有的存储。② 忽略分配器与对齐：真实占用要按分配粒度向上取整，本轮没有采集任务单元的总分配量，连「大约」都不能给。③ 句柄还可能被提前丢弃：`spawn` 后不保存 `JoinHandle`，观察者那侧的账就没了，任务继续在跑，8 字节从来不是任务成本的代理量。更诚实的方式是固定并发数、在途任务数与输出分别核验，把观察点放在能观察的地方，而不是从类型尺寸外推容量。对照[例 9.4.1](ch09.md#ex-9.4.1)、[9.4.2](ch09.md#sec-cpp-rust.3.9.4)。

:::

:::

::: ex B12 · 汇编里有 casal（主线 ①） {#ex-9.B.12}

目标汇编里出现 `casal`。有人据此写「本实验的同步开销约占 15%」。这个句子的证据强度如何？正确的写法是什么？

::: sol 解答

证据不支持。① 静态存在不等于动态次数：一段 `casal` 可能每次 poll 一次，也可能每次状态转换若干次，没有打点就不知道执行了多少回，本轮没有采集。② 指令可见不等于成本可分：`casal` 的耗时依赖缓存行（CPU 缓存的最小搬运单位）归属与争用，而正式批次只报告聚合 ns/step，没有单独成分。③ 采样补不上这个洞：`scheduling-sample.txt` 覆盖预热与两个 runtime 轮转的混合阶段，不能折算成稳定态百分比。正确写法：「产物里保留了原子状态操作，其单次成本与总占比本轮没有采集」。对照[思考 9.4.1](ch09.md#think-9.4.1)、[9.4.3](ch09.md#sec-cpp-rust.3.9.4)。

:::

::: ex B13 · 容量 64 与容量 16（主线 ②） {#ex-9.B.13}

服务对每个请求先 `spawn`，任务内部再 `send` 到 `channel(64)`。请写出内存上界的表达式；再判断「把容量调到 16 就能防 OOM」这句话。

::: sol 解答

上界由「已创建任务数 × 每个任务持有的量」加「通道里已有的 64 条消息」决定，与 64 无关。三步核对：谁在等待（所有还没成功发送的任务，不是 64 个消费者）、等待者持有什么（请求正文、连接引用、上下文）、边界覆盖哪一段（只覆盖已进入缓冲的消息）。

调小到 16 不能给出上界：容量只数已在缓冲里的消息，等 send 的任务与请求正文都不在计数内，等待只会更早发生、等待者更多。要补三样：准入前移到 `spawn` 与正文读取之前、每个任务在拿到名额前不持有正文、一条把名额与真实工作绑在一起的寿命规则。对照[例 9.7.1](ch09.md#ex-9.7.1)、[思考 9.7.1](ch09.md#think-9.7.1)。

:::

::: ex B14 · 21 个观察能支撑什么（主线 ②） {#ex-9.B.14}

inline 分支的观察延迟：均值 23.658 ms、样本 sd 1.302 ms、p50 23.604 ms、p99 25.060 ms，样本数 21。把这四个数写进容量规划时，哪些能用、哪些不能用？p99 为什么等于最大值？

::: sol 解答

能用的只有「这份 21 点样本的描述」：均值与中位数说明这批观察的中心，sd 说明样本内波动，p99 是这份样本的最大值。不能用的：把它当生产请求的尾延迟承诺、把 sd 当总体标准差、把均值当某一次调用的预期。nearest-rank 取排序后第 `ceil(21 × 0.99) = 21` 个值，所以 p99 就是最大值 25.060 ms；样本数必须与分位数一起报，否则读者会把「21 个数里的最大」当成生产尾部。对照 [9.6.3](ch09.md#sec-cpp-rust.3.9.6)、[例 9.6.1](ch09.md#ex-9.6.1)。

:::

## C 组 · 实操（15–19）

实验包在 `bench/runtime-lab/`，Tokio 固定为 1.54.0。当前证据目录是 `bench/results/runtime-fixed/measurements-final/`。这组题要求真的动手：跑命令、加观测点、写回归。

::: ex C15 · 三条命令的最小复验（主线 ④） {#ex-9.C.15}

从 `cpp-rust/` 复跑实验，记录你核对过的五项：任务数、每任务步数、预热、单位、编译设置。

::: sol 参考路径

三条命令依次是：

```bash
cargo test --offline --locked --manifest-path bench/runtime-lab/Cargo.toml
cargo clippy --offline --locked --manifest-path bench/runtime-lab/Cargo.toml --all-targets -- -D warnings
bash tools/run_runtime_benchmarks.sh bench/results/my-runtime-run
```

输出目录要选不存在的新目录，脚本拒绝覆盖已有 `environment.txt` 的归档。核对：每批 128 个任务、每任务 8192 个 step（共 1048576 步）、预热至少 500 ms、单位 ns/step 与 ns/op、Tokio 固定 1.54.0。在另一台机器上运行不应期待复现相同纳秒数。对照 [9.11 出口检查](ch09.md#sec-cpp-rust.3.9.11)、[9.5.1](ch09.md#sec-cpp-rust.3.9.5)。

::: ex C16 · 给一条请求加阶段点（主线 ②） {#ex-9.C.16}

选一条你熟悉的请求链，按 9.8.4 的七个名字布置阶段时间戳。说明只保留首尾两点时，哪几类慢法会混在一起；再给出一次「resource_ready 到 task_resumed 偏大」的判读。

::: sol 解答

七个点：arrival、admission_granted、enqueued、execution_started、resource_ready、task_resumed、response_finished。每段要写清用哪个时钟、怎么采样、靠哪个相关 id 串起来，等待预算与执行预算分开记。只留首尾，准入饱和、排队过长、阻塞 poll、外部资源慢、资源已就绪但恢复慢会给出相近的总耗时。`resource_ready` 到 `task_resumed` 偏大且其他段正常，判读为阻塞 poll：资源早已就绪，任务却被占住的执行线程拖着；本例的量级可与 9.6 的 25.060 ms 对照。对照[定义 9.8.3](ch09.md#def-9.8.3)、[例 9.8.1](ch09.md#ex-9.8.1)。

::: ex C17 · 许可必须活到闭包结束（主线 ①） {#ex-9.C.17}

用安全 Rust 写一个回归：证明 `spawn_blocking` 闭包运行期间，它持有的 permit 不会被调用方释放。

::: sol 解答

步骤：先让闭包发出 `started` 信号；收到后对闭包的 `JoinHandle` 调用 abort；闭包此时仍在等一个同步停止信号，这时再取唯一那个 permit 必须失败；发出停止信号、等闭包结束，再取 permit 必须成功。关键是 permit 以 owned 形式移进闭包，寿命随闭包结束而不是随调用方 Future。不要用固定 sleep 去猜「闭包应该已经启动」，`started` 消息建立的是明确的阶段关系。对照 [9.7.3](ch09.md#sec-cpp-rust.3.9.7)、[9.7.4](ch09.md#sec-cpp-rust.3.9.7)。

:::

::: ex C18 · 把 quantum 从 1024 改到 16（主线 ③） {#ex-9.C.18}

把让出粒度从每 1024 步改成每 16 步，重新跑 21 批。先写下三条可核对的预测，再说明这次改动**不能**回答什么问题。

::: hint 提示

每任务的 yield 次数变成几倍？分母变了吗？读数里混着哪两部分？

:::

::: sol 参考路径

预测应写成三条：① 聚合 ns/step 上升——每任务的 yield 次数变成 64 倍，而业务步数不变；② 上升里同时混着「yield 与重新调度的成本」与「缓存与队列状态被打断的代价」，无法在不额外采集的情况下拆开；③ 口径仍是「一批墙钟 ÷ 1048576 步」，所以读数的变化不能解释成「一次 yield 花多少纳秒」。这次改动不能回答 yield 的单价：要拆需要只改任务数，或单独测空任务链，那是另一个实验设计，且要重写实验契约。对照[定义 9.5.1](ch09.md#def-9.5.1)、[思考 9.5.1](ch09.md#think-9.5.1)。

:::

::: ex C19 · 先等进入再 abort（主线 ①） {#ex-9.C.19}

写一个取消回归：任务持有 Drop 守卫，`abort` 后要能观察到 `JoinError` 是 cancelled，并且 Drop 真的执行过。说明为什么必须先建立一个「已进入」信号。

::: hint 提示

spawn 之后立刻 abort，任务可能停在哪个阶段？断言还成立吗，它检验的对象还是同一件事吗？

:::

::: sol 解答

骨架：让一个 Drop 守卫在析构时经 oneshot 通知外部观察者；任务先发出「已进入」信号，测试收到后再调用 `abort`；随后检查 `JoinError` 是 cancelled，并等待 Drop 信号。先等进入，是为了让两种情形分开：任务在开始 poll 之前被取消（Future 根本没进入），与已经进入后再被取消。缺了这一步，JoinError 断言仍然成立，但检验的对象已经不确定。这个回归只证明合作式挂起点上的一个具体生命周期场景，不证明所有 Future 都能及时取消。对照 [9.2.5](ch09.md#sec-cpp-rust.3.9.2)、[例 9.2.3](ch09.md#ex-9.2.3)。

:::

## 批改时最常给的三条意见

1. **口径与单位错位**：把 ns/step 说成一次 step 或一次 poll 的延迟，把观察延迟说成吞吐。先改句子，再改表格。
2. **结论超出证据**：没有 steal 打点却写「窃取提高并行度」，拿 21 点 p99 承诺生产尾部，或用「加 worker」当修复。每句结论都要补上负载、版本、机器与样本数。
3. **边界缺项**：准入放在分配之后、许可寿命短于真实占用、取消测试不建立阶段关系。用[定义 9.7.2](ch09.md#def-9.7.2)、[定义 9.7.3](ch09.md#def-9.7.3)、[例 9.2.3](ch09.md#ex-9.2.3) 逐条补齐。
