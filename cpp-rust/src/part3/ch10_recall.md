# 第十章 · 闭卷回忆卡

「看懂」只说明答案在眼前时能识别；评审和故障定位要的是从空白纸上提取。这一页把第十章拆成 24 张卡，先读卡面自己答，再展开核对。

**用法与节奏**

| 时点 | 做什么 | 判定 |
|:--|:--|:--|
| 学完当天 | 第一组「定义卡」10 张 | 关键词写全才算 ✓ |
| 第 1 天 | 第二组「结论卡」8 张 | 能说清前提才算 ✓ |
| 第 3 天 | 第三组「第一行卡」6 张 | 写出第一步才算 ✓ |
| 第 7 天 | 只重做标成 △ 与 × 的卡 | 全对即可进入第十一章 |

每张卡给自己一个记号：✓ 一次说对；△ 说对一半或要提示；× 想不起来。只重做 △ 与 ×，不要把整叠反复过一遍——那是在读，不是在提取。

## 第一组 · 定义卡（说全称与前提）

::: ex 卡 1 · 直接子进程与两层边界 {#rc-10-1}

卡面：直接子进程指哪一层？隔离边界与治理边界各回答什么问题？

::: sol 核对

直接子进程是父进程可请求操作系统终止、并对其执行 wait 回收的那一层；孙进程不在内，它可能在直接子进程退出后继续运行并持有继承来的写端。隔离边界答「默认不共享什么」——地址空间、栈、终止对象；治理边界答「其余由谁负责」——协议、配额、权限、后代。边界表前三行是隔离边界，第四行才进入治理边界。对照[定义 10.1.1](ch10.md#def-10.1.1)、[定义 10.1.2](ch10.md#def-10.1.2)。
:::

:::

::: ex 卡 2 · 多线程 fork 的锁状态 {#rc-10-2}

卡面：fork 之后子进程继承了什么、丢掉了什么？为什么类型系统管不了？

::: sol 核对

只保留调用线程，却继承其他线程留下的内存锁状态。若某个分配器内部锁在 fork 瞬间由非调用线程持有，子进程里再没有人能释放它——锁位被物理带过去，持有者却不在。库可以在背后创建线程，调用点没有显式 `thread::spawn` 推不出「整个进程单线程」。所以本章只用 Command 启动独立可执行文件。对照[定义 10.1.3](ch10.md#def-10.1.3)。
:::

:::

::: ex 卡 3 · EOF 的两个条件 {#rc-10-3}

卡面：什么时候读者才能观察到 EOF？两条寿命各以什么为终点？

::: sol 核对

相应管道的**所有写端关闭，且已缓冲数据读完**。进程寿命以 wait 返回为终点；端点寿命以最后一个写端关闭为终点。仍有写端被另一个进程持有时，直接子进程退出也未必带来 EOF。对照[定义 10.2.1](ch10.md#def-10.2.1)。
:::

:::

::: ex 卡 4 · 线格式与内存布局 {#rc-10-4}

卡面：本机原生 `Frame` 的 size 与 align 是多少？24 字节表各偏移写什么？多出的 8 字节买什么？

::: sol 核对

原生 `Frame` size=16、align=8，没有版本字段，填充字节语义未定义。线格式固定 24 字节：0–2 version（little-endian，必须为 1）、2–4 flags（当前必须全 0）、4–8 frame length（little-endian，必须为 24）、8–16 request_id、16–24 value。多出的 8 字节买的是版本、标志与帧长——内存布局给不了的三样。对照[定义 10.3.1](ch10.md#def-10.3.1)。
:::

:::

::: ex 卡 5 · 三种读结局 {#rc-10-5}

卡面：短读、干净 EOF、截断各是什么？`read_frame` 分别返回什么？

::: sol 核对

短读：一次 read 返回字节数少于请求数，管道字节流的正常形态，继续读即可。干净 EOF：帧边界上一个字节都没读到、read 返回 0，`read_frame` 返回 `Ok(None)`。截断：帧首字节已到手后中途 EOF，剩余 23 字节由 `read_exact` 报 `UnexpectedEof`。三者是三个不同的协议事件，合并就丢诊断。对照[定义 10.3.2](ch10.md#def-10.3.2)。
:::

:::

::: ex 卡 6 · 计时边界与已就绪 {#rc-10-6}

卡面：两个 case 各把什么计入计时？worker 从哪一刻算「已就绪」？

::: sol 核对

spawn case 计完整业务生命周期：创建、8 字节 ready 握手、16 次请求响应、逐条校验、stdin 关闭与 wait。persistent case 只计稳态串行往返，创建、握手与批末关闭都在计时外。已就绪＝worker 先输出固定 8 字节 `RPCv0001` 并 flush，父进程 read_exact 核对完成。对照[定义 10.4.1](ch10.md#def-10.4.1)、[定义 10.4.2](ch10.md#def-10.4.2)。
:::

:::

::: ex 卡 7 · 背压停滞 {#rc-10-7}

卡面：背压停滞由哪三个条件同时成立构成？换动作能解开吗？

::: sol 核对

管道缓冲已满、写方在等空间、读方在等别的事件（例如子进程退出）。任何一方换动作都能解开回路，但「先 wait 后读」让双方都在等对方先动。它与 stdin 方向的互等是同构问题，只是换到了 stdout；stderr 也会独立地满、独立地卡。对照[定义 10.5.1](ch10.md#def-10.5.1)。
:::

:::

::: ex 卡 8 · 有限保留的四个字段 {#rc-10-8}

卡面：Capture 的四个字段各记录什么？哪三个「不是」不能忘？

::: sol 核对

prefix（保存的前 cap 字节，长度不超过 cap）、total（实际排空总字节，checked_add 防溢出）、eof（是否读到 0，不能由 child 退出推断）、reader_errors（读取失败或 grace 超时，调用方必须检查）。三个「不是」：cap 不是进程 RSS 上限，不是「达到 cap 自动杀进程」的开关，四个字段也不是退出状态的替代品。对照[定义 10.5.2](ch10.md#def-10.5.2)。
:::

:::

::: ex 卡 9 · 超时三件事与两个时钟 {#rc-10-9}

卡面：一个超时至少牵动哪三件事？deadline 与 grace 各管什么对象？

::: sol 核对

三件事：不再接受该请求的正常结果（调用方预算）；使外部工作停止或受控收尾（外部进程）；回收直接子进程与本地 I/O 任务（内核与本地资源）。deadline 管直接子进程的 wait 阶段，grace 管输出端点集合的排空阶段。grace 到期后 abort 读取任务并观察取消，Capture 保留部分内容、`eof=false`、reader_errors 记下到期原因。对照[定义 10.7.1](ch10.md#def-10.7.1)、[定义 10.7.2](ch10.md#def-10.7.2)。
:::

:::

::: ex 卡 10 · CLOEXEC 创建窗口 {#rc-10-10}

卡面：标准库在 macOS 上如何设置 CLOEXEC？窗口里发生了什么？修复用哪一步替代？

::: sol 核对

`pipe(fds)` 之后分两步为 read 端、write 端设 `FD_CLOEXEC`。在 pipe 返回、fcntl 设置标志之前存在创建窗口：若无关线程在窗口内执行 posix_spawn，未打标的双 FD 会被复制进子进程，该子进程再派生后代，捕获管道的额外写端就可能长期存活。修复以动态探测的 `pipe2(O_CLOEXEC)` 原子创建，每个 FD 立即进入唯一 `OwnedFd` 所有者。对照[定义 10.7.3](ch10.md#def-10.7.3)。
:::

:::

## 第二组 · 结论卡（说清前提与范围）

::: ex 卡 11 · 1.219 ms 与 5.484 µs 能怎么写 {#rc-10-11}

卡面：这两个数各是什么估计对象？222 倍在什么条件下才可以写？

::: sol 核对

spawn case 的批均值 1219110.006 ns/request 是完整生命周期（含握手、往返、校验、关闭、wait）；persistent 的 5484.128 是 16 次请求墙钟均值的批均值，即稳态串行往返。222 倍只在「本机、macOS ARM64、固定 release、极小整数业务、单 worker 严格一请求一响应」下可写，它只是两个均值之比，不引入统计保证。对照[例 10.4.1](ch10.md#ex-10.4.1)。
:::

:::

::: ex 卡 12 · 30ms 重现了什么 {#rc-10-12}

卡面：停滞测试怎么构造？30ms 是容量证明吗？

::: sol 核对

helper 向 stdout 写 2MiB、随后向 stderr 写 2MiB；父进程先读 stdout 一个字节确认已进入输出阶段，然后停止读取、只等退出。30ms 期限内 wait 未完成，测试随后 kill 并 wait 直接子进程。30ms 只是观察窗口，不是管道容量或调度保证。对照 10.5.2。
:::

:::

::: ex 卡 13 · wait 返回不等于流结束 {#rc-10-13}

卡面：退出码 0 且 stdout 读到 EOF，能不能说「输出完整、退出成功」？

::: sol 核对

两个观察各答各的问题。wait 返回只说明直接子进程已被等待；EOF 只说明这条输出流无更多字节，都不说明退出状态，也不说明另一条流。`exit_code` 为 `None` 在 Unix 上可能对应信号终止。对照[例 10.2.1](ch10.md#ex-10.2.1)。
:::

:::

::: ex 卡 14 · kill 之后为什么还要 wait {#rc-10-14}

卡面：kill 与回收是同一个动作吗？`timed_out` 证明了什么？

::: sol 核对

不是。kill 只是提交终止请求，wait 才取回退出状态并释放系统记录；Unix 上未被等待的已退出子进程可能成为 zombie。标准库 `Child` 没有自动等待的 Drop。`timed_out` 只表示父进程的期限路径被触发，不表示操作系统证明该进程被某个信号杀死。对照 10.7.3、10.7.4。
:::

:::

::: ex 卡 15 · 0.514 与 0.515 能推出什么 {#rc-10-15}

卡面：两行数据的单位是什么？为什么不能写「固定前缀快 0.2%」？

::: sol 核对

单位是 ns/聚合输出字节：批墙钟时间除以 4194304 个聚合输出字节，是聚合吞吐的倒数，不是单字节延迟。0.001 的均值差小于两组 sd（0.031 与 0.027），方向不稳健；本轮没有构造配对差值区间，也没有显著性与 p 值。数据支持的稳妥结论只有：固定前缀正确完成同样排空工作，保留内容大幅减少。对照[定义 10.6.1](ch10.md#def-10.6.1)、[例 10.6.1](ch10.md#ex-10.6.1)。
:::

:::

::: ex 卡 16 · sample 栈能说什么 {#rc-10-16}

卡面：四行栈各对应哪个阶段？为什么不能做成 CPU 占比饼图？

::: sol 核对

`posix_spawnp`／`__posix_spawn` 对应启动 worker，`Session::start` 下的 read 对应等 ready 握手，`__wait4` 对应回收直接子进程，请求路径的 read 对应等响应字节。阻塞等待栈被采样不等于消耗 CPU；报告混有预热与多 case 阶段、只观察父进程一侧、且属历史版本，不能用来拆当前表格的纳秒。对照[思考 10.6.1](ch10.md#think-10.6.1)。
:::

:::

::: ex 卡 17 · 单 worker 数据不能乘 worker 数 {#rc-10-17}

卡面：把 5.484 µs 除以 8 得到 0.69 µs/请求，缺了哪几层？

::: sol 核对

缺四层：persistent case 没有并发在途请求，协议连多路关联都还没实现；CPU 核心数、管道缓冲、父进程分发与排队没有建模；各 worker 的冷热状态与父进程争用会引入非线性；没有跑过扩展实验。要外推得先补多 worker 实现与实验。对照[思考 10.4.1](ch10.md#think-10.4.1)。
:::

:::

::: ex 卡 18 · 池化多出来的是责任 {#rc-10-18}

卡面：池有哪几个状态？用什么三元组标识一次执行？失败重试能保证什么？

::: sol 核对

starting（握手前不接业务）、ready（接受有限请求）、busy（请求 id 与 worker 代际绑定）、draining（不接新工作并决定在途策略）、failed（标记受影响请求的不确定性）、restarting（递增代际并重新握手）。三元组是 `(session, generation, request id)`。进程隔离不提供 exactly-once，重试可能重复副作用。对照[定义 10.8.1](ch10.md#def-10.8.1)、[思考 10.8.1](ch10.md#think-10.8.1)。
:::

:::

## 第三组 · 第一行卡（只写第一步）

这一组练「一离开答案就不知道第一行写什么」。每题只写第一行动作。

::: ex 卡 19 · 子进程疑似卡住 {#rc-10-19}

卡面：wait 半天不返回，第一行写什么？

::: sol 核对

第一行：先查三条——两条流是否各有并发读任务、读任务是否在 cap 之后提前退出、wait 是否已返回但 EOF 未到（后者是继承写端，归 10.7）。按这个顺序排除，再谈总量策略。对照 10.5 的判定流程。
:::

:::

::: ex 卡 20 · 只关心前 128 字节 {#rc-10-20}

卡面：要写采集器了，第一行写什么？

::: sol 核对

第一行：写下「排空不等于保留」——全部字节照读，计数用 checked_add；只有 prefix 受 cap 约束，keep 为 0 也继续读。cap 不是 RSS 上限，也不是杀进程开关。对照[定义 10.5.2](ch10.md#def-10.5.2)。
:::

:::

::: ex 卡 21 · 对端在帧中途消失 {#rc-10-21}

卡面：读到首字节后流断了，第一行写什么？

::: sol 核对

第一行：把它判成截断而不是 EOF——`read_exact` 报 `UnexpectedEof`，记录「这一帧不完整」，并按[例 10.2.1](ch10.md#ex-10.2.1) 的观察表保留「该请求副作用是否发生未知」。
:::

:::

::: ex 卡 22 · 评审一份超时处理 {#rc-10-22}

卡面：有人交来「timeout 包住 wait，kill_on_drop 已开」，第一行写什么？

::: sol 核对

第一行：先列三件事打勾——结果预算、外部进程、wait 与本地读取任务；再看 `timed_out` 与 `exit_code` 是否被混成一句，grace 有没有独立时钟。对照[定义 10.7.1](ch10.md#def-10.7.1)。
:::

:::

::: ex 卡 23 · 选 spawn 还是池 {#rc-10-23}

卡面：部署方案还没定，第一行写什么？

::: sol 核对

第一行：先写隔离要求、工作量、故障模型三件事，再读计时边界表。每次以秒计的工作，1 ms 启动差不是主要矛盾；高频小工作、稳态为主才轮到复用。对照 10.4.7 的判定流程。
:::

:::

::: ex 卡 24 · 要上多 worker 池 {#rc-10-24}

卡面：老板说「先开 8 个 worker」，第一行写什么？

::: sol 核对

第一行：先写三件缺一不可的东西——用 `(session, generation, request id)` 绑定执行、每一段队列的容量与满后动作、失败时「确定没做」还是「不确定」。写不出来就先别上池。对照[定义 10.8.1](ch10.md#def-10.8.1)。
:::

:::
