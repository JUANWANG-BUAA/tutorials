## 12.1 现代处理器的向量通道与数据并行本质 {#sec-cpp-rust.3.12.1}

本节回答一个问题：**同一条加法指令，凭什么一次算出 4 个甚至 16 个结果？**答案不在算法层，而在硅片上数据通路的宽度。这一节先定位标量处理器的瓶颈在哪里，再给出 SIMD 的结构模型，为 12.2 的编译判定和 12.6 的实测对照打底。

::: preview 先抓住一件事

向量指令换来的并行度只覆盖「运算」这一段。发射槽位、寄存器写端口（寄存器是 CPU 里直接存取数据的那几个槽位）、内存带宽这三堵墙仍在原地。向量单元算得越快，瓶颈越容易从「算不过来」变成「等数据」。本章报出的加速比，都要在这个前提下读。
:::

### 12.1.1 标量处理器的指令级瓶颈与吞吐墙

在经典的冯·诺依曼架构与单指令单数据（SISD）标量计算模型中，算术逻辑单元（ALU）每次只能接收一个或两个标量操作数，输出单个计算结果。例如，在 64 位 AArch64 架构上，执行一条普通的 32 位加法指令：

```asm
add w0, w1, w2    ; 计算 w0 = w1 + w2，单周期消耗一个发射槽
```

现代微架构有时钟频率，也有超标量多发射流水线。Apple Silicon M 系列核心的发射宽度本书没有取证（母本表里没有这一项），本节也不拿它当结论用。即便如此，指令的译码、重命名、重排序缓冲区（ROB）分配与引退（Retire）依然受物理发射槽的硬性约束。发射宽度说的是每周期能推进多少条指令，不是每周期能算完多少数据。处理数以千万计的音视频采样、图像矩阵、网络数据包校验和或高频量化特征时，指令译码与循环控制分支的开销会迅速饱和发射前端，引发所谓的「指令吞吐墙」。

::: def 定义 12.1.1 · 指令吞吐墙 issue throughput wall {#def-12.1.1}

**指令吞吐墙**指这样一种状态：算术单元本身还有空闲，但每周期能译码、发射、引退的指令数已经到达硬件上限。撞墙之后，继续堆算力没有收益；唯一的出路是让一条指令携带更多数据。SIMD 的全部动机就是这一句（[@def-12.1.1]）。

:::

标量执行还受第二层资源限制：寄存器写端口（Writeback Ports）与旁路网络（Bypass Network）的物理布线。每个时钟周期能完成写回的标量寄存器数量是有限的。用标量循环展开提升吞吐，确实消掉了部分分支跳转；但庞大的标量微操作仍要争夺整数重命名槽位与调度站（Reservation Stations），乱序执行窗口会迅速耗尽。

第三层限制是内存访问延迟。算术指令延迟通常在 1 至 4 个时钟周期，主存访问却要数百个周期。大批量遍历内存时，标量加载无法在总线上形成密集的突发读取（Burst Read），硬件预取器（Hardware Prefetcher）也难建立高带宽流模式，计算流水线因此频繁停在等待内存返回数据上。流水线停在等待上，多发几条指令并不能把这段等待填掉；这一层的账要按每周期搬进的字节数来算。

### 12.1.2 SIMD 向量并行体系的微架构结构

单指令多数据（SIMD, Single Instruction Multiple Data）在硅片上开辟超宽数据通路，把同一个运算同时应用到一组紧密排列的独立操作数上。这些独立槽位叫**车道（lane）**：

```text
标量加法 (SISD):
  Cycle 1: A[0] + B[0] -> C[0]
  Cycle 2: A[1] + B[1] -> C[1]
  Cycle 3: A[2] + B[2] -> C[2]
  Cycle 4: A[3] + B[3] -> C[3]

SIMD 向量加法 (128-bit NEON / SSE):
  Cycle 1: [ A[3] | A[2] | A[1] | A[0] ] + [ B[3] | B[2] | B[1] | B[0] ] ──► [ C[3] | C[2] | C[1] | C[0] ]
           └────────────────────────── 4 个 32 位整数单周期并行完成 ──────────────────────────┘
```

::: def 定义 12.1.2 · SIMD 车道与向量位宽 lane / vector width {#def-12.1.2}

**车道**是向量寄存器里互相独立的一个数据槽位；**车道数 = 向量位宽 ÷ 元素位宽**。一个 128 位 NEON 寄存器按 `v0.4s` 看是 4 个 32 位车道，按 `v0.16b` 看是 16 个 8 位车道——同一块硅片，不同视图（[@def-12.1.2]）。

:::

现代处理器的向量体系结构包含庞大的专用寄存器堆与算术流水线：
- **ARM64 NEON / SVE**：配备 32 个 128 位宽度的向量寄存器（$V_0 \sim V_{31}$）。每个寄存器既可以被当作 16 个 8 位整数（`v0.16b`），也可以视作 8 个 16 位整数（`v0.8h`）、4 个 32 位整数/浮点数（`v0.4s`），或 2 个 64 位整数/双精度浮点数（`v0.2d`）。在 ARMv9 的 SVE/SVE2 架构中，向量位宽更进一步扩展为硬件可伸缩的 128 至 2048 位；
- **x86 AVX2 / AVX-512**：从传统的 128 位 XMM 扩展至 256 位 YMM 与 512 位 ZMM 寄存器，支持在单个时钟周期内并发执行 16 个 32 位单精度浮点或 8 个 64 位双精度浮点乘加运算（FMA）。

SIMD 绝非免费的午餐，其底层伴随着物理权衡：
1. **能耗与发热**：执行 256 位或 512 位超宽向量指令会产生极高的瞬时电流消耗。许多 x86 处理器在激活 AVX-512 指令时会自动降低核心基础频率（AVX Frequency Offset），甚至导致邻近同芯片核心被联动降频；
2. **内存带宽饱和（Memory Bus Saturation）**：当计算单元能够以每周期数十字节的吞吐处理数据时，瓶颈瞬间转移到 L1/L2 缓存带宽乃至系统主存通道。数据无法以对齐且连续的方式流式载入时，向量单元会长时间停在等待内存加载的状态。这时候再宽的通道也是在等，不是在算。

用上面的架构阶梯表回答三个问题：

1. 一条 512 位的 AVX-512 整型加法，最多同时处理多少个 `u32`？
2. 同样宽度换成 `u64` 加法，车道数是多少？
3. 为什么本章实验（12.6 节）在 Apple M5 Pro 上按 4 车道规划主循环与尾部？

::: sol 解答

1. 512 ÷ 32 = 16 个 `u32`，对应架构阶梯表的 AVX-512 行（[@def-12.1.2]）。
2. 512 ÷ 64 = 8 个 `u64`。车道数永远是位宽除以元素位宽，与寄存器叫 ZMM 还是 YMM 无关。
3. M5 Pro 是 ARM64 NEON，向量寄存器 128 位，`u32` 车道数为 4。所以 12.3 的手写内核每次步进 4 个元素；实验把长度取成 65539，正是为了让尾部按 `mod 4 = 3` 强制走进清理分支（见 12.6.1 的协议设计）。

::: think 思考 · SIMD 是免费的吗 {#think-12.1.1}

既然一条指令顶四条，为什么不把所有循环都向量化到极限位宽？

::: sol 解答

因为并行度不是白拿的。256/512 位指令瞬时电流高，部分 x86 会因此降频，甚至联动邻近核心；数据供不上时，超宽向量单元就停在等内存上（[@def-12.1.1] 说的是发射墙，SIMD 缓解它，却可能把瓶颈推到内存带宽墙）。向量化前先问一句：每周期要搬的字节数，当前缓存层级给得起吗？

### 12.1.4 小结与常见错误

**小结。**① 标量执行撞的是三堵墙：发射槽、写端口、内存延迟，指令吞吐墙的定义见 [@def-12.1.1]；② SIMD 用一条指令驱动多条车道，车道数等于位宽除以元素宽度（[@def-12.1.2]）；③ 并行度只覆盖运算段，能耗与带宽是它的账单；④ 图 12-1 下半部预告了本章的另一条主线：零拷贝切片把「数据在哪」与「数据归谁管」拆成寄存器对里的指针加长度。下一节 [12.2 自动向量化的触发条件](#sec-cpp-rust.3.12.2) 回答：编译器什么条件下才肯替你把循环写成这样。

::: errata 常见错误清单（12.1 节）

E-a **把加速比当成常数。**加速比不是常数：位宽翻倍不等于吞吐翻倍，数据供给跟不上时，加宽只会加深停顿（[@def-12.1.2]）。

E-b **估算收益时漏掉降频代价。**部分 x86 上激活 512 位宽向量指令会触发 AVX Frequency Offset，同核心的标量线程被连带拖慢。

E-c **拿标量循环展开硬扛发射墙。**展开消了分支，但微操作仍要抢同一批重命名槽与 ROB（[@def-12.1.1]）。

E-d **以为 NEON 寄存器只有一种类型。**同一个 128 位寄存器按 `v0.16b`、`v0.8h`、`v0.4s`、`v0.2d` 是不同车道划分，视图错配就读错了数据（[@def-12.1.2]）。

E-e **把硬件预取当成保证。**预取器只对连续、可识别的流模式友好；跨步访问落在它的模式之外，这时候指望它补齐带宽并不会兑现。

E-f **拿标量延迟比推 SIMD 收益。**算术指令 1–4 拍、主存数百拍，比值会误导；要按每周期字节数重新算账（[@def-12.1.1]）。

:::

## 12.2 自动向量化的触发条件、障碍与LLVM诊断 {#sec-cpp-rust.3.12.2}

本节回答一个问题：**同样是一个逐元素循环，为什么编译器有时向量化、有时不？**向量化不是编译器的偏好，而是一个证明行为：它必须先证明改写不改变语义，才敢把标量循环重写成 SIMD。这一节给出它要证明什么、通常卡在哪、以及怎样让它自己报告。

::: preview 先抓住一件事

「没向量化」不是玄学，也不是编译器在跟你赌气。每一类障碍都对应编译器证不出某个性质的具体位置：别名、跨迭代依赖、不可预测的边界、非连续访问。读完 [@def-12.2.1]，你应该能在写代码时预先替编译器把这些证明做完。
:::

### 12.2.1 两条向量化通道：循环向量化器与 SLP

在 Rust 开发中，开发者并不总是需要直接调用危险且依赖特定平台的底层硬件内联函数（Intrinsics）。LLVM 优化流水线包含了两个高度精密的向量化通道：多数逐元素循环可以先交给它们，手写并不是第一选择。
1. **循环向量化器（Loop Vectorizer）**：分析连续迭代的 `for` 循环或迭代器链条，将步长为 1 的标量循环体展开并重写为以向量步长（如一次步进 4 或 8 个元素）执行的 SIMD 批处理块，并在首尾附带处理未对齐头尾的标量清理块（Peeling & Epilogue Loops）；
2. **SLP 向量化器（Superword-Level Parallelism Vectorizer）**：在基础块（Basic Block）内部寻找独立且同构的标量运算（例如连续对结构体四个字段赋值），将其合并打包为单条向量指令执行。

::: def 定义 12.2.1 · 自动向量化 auto-vectorization {#def-12.2.1}

**自动向量化**指编译器在不修改源码语义的前提下，把标量操作改写为向量操作。它的本质是一次等价性证明：改写前后每个元素的结果必须一致（[@def-12.2.1]）。证明失败就退回标量，这不是能力问题，而是正确性优先。在理想条件下，编写自然、地道的安全 Rust 迭代器代码即可获得接近手写汇编的性能——12.6 的实测把这句话量化了。

:::

### 12.2.2 阻碍自动向量化的四大障碍

实际工程中，大量看似简单的循环仍被编译器退回纯标量执行。深入分析 LLVM 中间表示，可以提炼出阻止自动向量化的四大核心障碍：

1. **指针别名模糊性（Pointer Aliasing）**：
   C/C++ 语言深受指针别名之苦。如果输入数组与输出数组可能在物理内存中重叠（例如 `dst = src + 1`），把循环向量化就会破坏写后读的正确性。在 Rust 中，借用规则让 `&T` 与 `&mut T` 永不共存，编译器可以直接向 LLVM 标注 `noalias` 参数。这是 Rust 的天然优势：Rust 代码的自动向量化成功率普遍高于未经 `restrict` 标注的 C 代码。这份优势来自借用规则，不是来自某个编译开关；它也不需要你写一行 unsafe。
2. **循环内部的数据依赖（Loop-Carried Dependencies）**：
   如果第 $i$ 次迭代的计算依赖第 $i-1$ 次迭代的输出结果（例如经典递推 $x_i = (x_{i-1} \times 3) + 7$），迭代之间就存在强制的时序先后锁，不能并行发射计算。
3. **未知的循环迭代边界与步长**：
   如果循环上界无法在进入循环前被静态或动态确定，或者循环体内含不可预测的 `break`、提前返回、可能触发 panic 的边界检查，循环向量化器将被迫放弃。原因是向量执行无法在宽指令的中间车道上优雅退出。
4. **非连续或带有跨步的内存访问（Non-contiguous Strided Access）**：
   向量加载指令（如 `vld1q`）最擅长从连续地址载入数据。频繁访问结构体数组（AoS）中的离散字段，或以大跨步遍历内存时，编译器必须使用极昂贵的离散收集（Gather）与分散写回（Scatter）指令，向量化的综合收益反而低于标量流水线。这时候就不能指望向量化提速，该改的是数据布局。

::: def 定义 12.2.2 · 循环携带依赖 loop-carried dependency {#def-12.2.2}

**循环携带依赖**指后一次迭代要等前一次迭代的结果才能开始。递推 $x_i = (x_{i-1} \times 3) + 7$ 是典型：它是迭代之间的串行链，SIMD 车道之间没有可独立分配的同构工作（[@def-12.2.2]）。本章 benchmark 刻意选了**不含**携带依赖的逐元素映射——`output[i] = input[i] × 3 + 7`，见 12.6.1 的协议设计。

:::

### 12.2.3 自动向量化的代码结构范式

为最大限度激发 LLVM 向量化器的能力，编写数据流密集型代码时应遵循如下规范：

```rust
// 推荐的无分支、边界前置确认的向量化友好范式
pub fn transform_optimized(input: &[u32], output: &mut [u32]) {
    // 关键步骤 1：在循环之前断言等长！消除循环内部每一次迭代的边界检查 panic 分支
    assert_eq!(input.len(), output.len());

    // 关键步骤 2：利用 zip 与无分支 wrapping 操作进行直观迭代
    for (x, y) in input.iter().zip(output.iter_mut()) {
        // 使用 wrapping_* 消除溢出检查分支，确保指令流完全线性
        *y = x.wrapping_mul(3).wrapping_add(7);
    }
}
```

通过这一范式，LLVM 可以静态证明数组访问不会越界，从而安全地在机器码层面剥离全部边界检查分支，下发连续无跳转的向量流水线。断言前置买到的就是这份证明：有了它，循环体里的边界检查才不是每次迭代都要重付的成本。

::: ex 例 12.2.1 · 前置断言买到了什么 {#ex-12.2.1}

`transform_optimized` 在循环之前 `assert_eq!(input.len(), output.len())`。

1. 这条断言让向量化器证明了什么？
2. 如果删掉断言、只靠 `zip` 的截断语义，功能上还正确吗？性能判断该怎么下？

::: sol 解答

1. 等长断言加 `zip`，让编译器能静态推出两侧访问共享同一边界，循环体内每次迭代的边界检查与 panic 分支才能被整体剥离（[@def-12.2.1]、[@def-12.2.2] 第 3 类障碍的反面）。`wrapping_*` 再消掉溢出检查，指令流才完全线性。
2. 功能仍正确——`zip` 按较短一侧截断。但「慢不慢」不能靠猜：要按 12.2.5 打开 remark 看向量化器是否放弃，再按 12.5 用汇编核对。缺了断言的版本更可能保留逐次检查，综合收益低于标量路径。

:::

:::

### 12.2.4 浮点向量化与 fast-math 的结合律鸿沟

在整型向量运算中，加法与乘法遵循严格的模算术（Modular Arithmetic），结合律天然成立：$(a + b) + c \equiv a + (b + c) \pmod{2^{32}}$。因此编译器可以放心重排整型向量操作。

浮点向量计算（`f32` 或 `f64`）中，情况发生根本变化。根据 IEEE 754 浮点标准，有限精度舍入误差使浮点加法**在数学上不具备结合律**：
$$(A + B) + C \neq A + (B + C)$$

编译器若把一个长循环累加 `sum += array[i]` 向量化为 4 车道并行累加、最后再求和，计算顺序就从串行的 $((a_0 + a_1) + a_2) \dots$ 变为 $(a_0 + a_4 + \dots) + (a_1 + a_5 + \dots) \dots$。浮点最低几个有效位（ULP, Unit in the Last Place）会产生微小偏离。因此在严格遵循 IEEE 754 的默认安全模式下，LLVM 不会对浮点连续累加循环做自动向量化。这不是编译器偷懒，是它在替你守住精度。

::: def 定义 12.2.3 · 浮点非结合律与 fast-math 授权 {#def-12.2.3}

**浮点非结合律**指舍入误差让括号顺序影响结果。**fast-math** 是用户对编译器的显式授权：允许为并行度重排浮点运算，接受 ULP 级偏离。授权入口有两个——`-C fp-contract=fast`（允许生成硬件级融合乘加 FMA）与未稳定的 `core::intrinsics::fadd_fast`（显式标明允许代数重排）（[@def-12.2.3]）。没有授权，编译器保守；给了授权，数值确定性就得由你自己负责。

:::

要在允许精度微差的科学计算与神经网络推理中解锁向量化，必须显式授权编译器放宽结合律限制：
- 在 `rustc` 中传递 `-C fp-contract=fast` 允许生成硬件级融合乘加（FMA）；
- 或者在非安全数学模式下利用标准库未稳定的 `core::intrinsics::fadd_fast` 显式标明允许代数重排。

浮点确定性与向量化算力之间的权衡必须显式做出，不能被默认值悄悄替你决定。

### 12.2.5 编译器向量化诊断（LLVM Optimization Remarks）

调优密集计算内核时，不应盲目猜测编译器是否执行了向量化，而应让 LLVM 自己报告决策。可用的开关只有一个：

```bash
RUSTFLAGS="-C remark=loop-vectorize" cargo build --release
# 想连源码位置一起看，再加 -C debuginfo=1（否则 rustc 只警告「requires -C debuginfo=n」）
```

`-C pass-remarks-analysis=` 与 `-C pass-remarks-missed=` 是 clang 的 `-Rpass-*` 家族名字，rustc 不认，照抄会直接 `error: unknown codegen option`。

更要用本机事实提醒一句：在本书的机器上（rustc 1.99.1，AArch64），`-C remark=loop-vectorize`、`-C remark=vectorizer`、甚至 `-C remark=all` 都没有打印出任何一条向量化 remark，只有 `-C remark=all` 会输出大量 inline remark。也就是说 remark 这条证据链在本机不可用，向量化成功与否只能靠下游两层判：优化后的 LLVM IR 里有没有 `<4 x i32>` 这类向量类型和 vector shuffle，目标汇编里有没有 `ldur q0` 这种 128 位宽寄存器的访存——正是 12.5 的做法（本书 `run-01/codegen/` 里 `.ll` 与 `.s` 都可核对）。LLVM 那句 `loop not vectorized: could not prove that the loop-carried dependencies allow vectorization` 是向量器常见的诊断措辞，本书没有采到它，不能当作可复现的输出引用。

::: think 思考 · remark 说「向量化成功」就能收工吗 {#think-12.2.1}

优化 remark 是向量化器自己的决策记录。它说 `loop vectorized (width: 4)`，是否等价于最终机器码里一定有 4 车道宽指令？

::: sol 解答

不等价。remark 只报告**该 pass 当时**的判断；后续流水线仍可能改写、拆回或替换这段代码。拿它当机器码清单，层就搞错了——remark 不是机器码。判断「最终落地」要沿证据链再走一层：看优化后 IR 与目标汇编，即 12.5 的做法（[@def-1.8.1]）。remark 是线索，汇编才是凭证。

:::

:::

### 12.2.6 小结与常见错误

**小结。**① 向量化是等价性证明，不是优化偏好（[@def-12.2.1]）；② 四类障碍各自对应一个证不出性质的位置：别名、携带依赖（[@def-12.2.2]）、边界不可预测、跨步访问；③ 替编译器做证明的写法是「断言前置 + 无分支迭代」，收益见 [@ex-12.2.1]；④ 浮点重排需要用户显式授权（[@def-12.2.3]）；⑤ 判断向量化与否要开 remark，再用 12.5 的汇编核对（[@def-1.8.1]）。下一节 [12.3 显式 SIMD](#sec-cpp-rust.3.12.3) 处理编译器证明不了的场景。

::: errata 常见错误清单（12.2 节）

E-a **把没向量化归咎于「编译器不行」。**先按四类障碍逐一定位，remark 会指出具体缺哪个证明（[@def-12.2.1]）。

E-b **循环里留着逐次边界检查或 panic 分支。**一个隐藏分支就能让向量化器整体放弃；断言要前置（[@ex-12.2.1]）。

E-c **在含携带依赖的递推上强求向量化。**车道之间没有可独立分配的工作（[@def-12.2.2]）；这类算法要换分解思路，不是换编译器。

E-d **默认允许 fast-math「反正偏差不大」。**ULP 偏离会随累加长度放大；授权必须对应明确的数值需求（[@def-12.2.3]）。

E-e **凭直觉改写循环再比快慢。**不先开 remark 确认，可能两个版本都是标量，差异全在噪声里（[@def-1.8.1]）。

E-f **把 C 的 `restrict` 经验照搬给 Rust。**Rust 的 `noalias` 来自借用规则而非注解；反过来删掉借用边界（如裸指针跨切片传递）会同时丢掉这个向量化红利。

## 12.3 显式SIMD与目标特性：NEON与AVX-512的移植安全 {#sec-cpp-rust.3.12.3}

本节回答一个问题：**编译器证明不了的场景怎么办，手写 SIMD 又怎样保证不弄崩老机器？**12.2 划清了自动向量化的边界。这一节教两件事：在边界内继续信任编译器；在边界外用 `core::arch` 显式下指令，并用运行时探测把风险锁在单个函数里。

::: preview 先抓住一件事

手写向量化真正的危险不是写得慢，而是把只属于某代 CPU 的指令编进所有机器都会执行的二进制。Rust 的答案是把「用了什么指令集」变成函数级属性：`#[target_feature]` 圈定危险范围，`is_*_feature_detected!` 提供调用前的运行时凭证（[@def-12.3.2]）。
:::

### 12.3.1 仍需显式手写向量化的三类场景

自动向量化已相当强大——12.6 的实测里它与手写 NEON 处于同一量级。但这份「同一量级」只覆盖逐元素映射那一类结构，别的形状不能这么外推。如下场景中，手动编写显式 SIMD 依然是高性能系统工程师的必修课：
- **复杂洗牌与置换（Shuffle & Permutation）**：音视频编码中的离散余弦变换（DCT）、密码学中的 AES 列混合（MixColumns）或网络字节序与主机字节序的高速反转，编译器极难自动推导出最优的向量置换指令组合；
- **特定硬件指令加速**：许多硬件指令（如 SHA256 专用硬件扩展、CRC32 硬件校验和、点积乘加 `vdotq`）没有通用的高级语言抽象可映射，源码里也就写不出它们，不能指望自动向量化替你调出来；
- **饱和算术与截断**：数字信号处理中的饱和加减（Saturating Arithmetic），在标量层面需要繁琐的条件比对，而在向量层面仅需单条 `vqadd` 指令。

### 12.3.2 显式 SIMD 内联函数跨平台对照

::: def 定义 12.3.1 · 内联函数 intrinsic {#def-12.3.1}

**内联函数（intrinsic）**是编译器提供的一层薄封装：函数体基本对应一条具体的硬件指令（如 `vld1q_u32` 对应一次向量加载），存放在 `core::arch` 的平台模块里。调用它通常意味着 `unsafe` 与平台前提——边界、对齐、非重叠都要由调用方自己证明（[@def-12.3.1]）。

:::

下表给出在 ARM64 NEON 与 x86_64 AVX2 架构下，最核心向量操作的 API 映射关系：

| 语义操作 | ARM64 NEON (`core::arch::aarch64`) | x86_64 AVX2 (`core::arch::x86_64`) | 微架构说明 |
|:--|:--|:--|:--|
| **128位非对齐加载** | `vld1q_u32(ptr)` | `_mm_loadu_si128(ptr)` | 从连续内存载入 4 个 32 位整型 |
| **256位非对齐加载** | 需借助 SVE 或两次 NEON | `_mm256_loadu_si256(ptr)` | 单指令载入 8 个 32 位整型 |
| **标量广播** | `vdupq_n_u32(val)` | `_mm256_set1_epi32(val)` | 将单一标量复制填充到向量所有车道 |
| **向量并行乘法** | `vmulq_u32(a, b)` | `_mm256_mullo_epi32(a, b)` | 车道间独立相乘，保留低 32 位 |
| **向量并行加法** | `vaddq_u32(a, b)` | `_mm256_add_epi32(a, b)` | 车道间独立相加 |
| **融合乘加 (FMA)** | `vmlaq_u32(acc, a, b)` | `_mm256_fmadd_ps(...)` (浮点) | 单周期完成乘累加，精度与吞吐双优 |
| **连续内存存储** | `vst1q_u32(ptr, val)` | `_mm256_storeu_si256(ptr, val)` | 将向量计算结果全量写回内存 |

### 12.3.3 安全的硬件特性动态探测（Target Feature Detection）

直接在全局编译配置中启用最高级别的向量指令（如 `RUSTFLAGS="-C target-feature=+avx512f"`）有灾难性的兼容性风险：编译出的二进制在哪怕落后一两代的旧服务器上运行，也会当场触发 `SIGILL`（非法指令异常）崩溃。

Rust 在标准库与 `core::arch` 中建立了严格的硬件特性安全隔离体系：

```rust
// 动态检测与显式内联函数调用的安全封装范式
#[cfg(target_arch = "aarch64")]
#[target_feature(enable = "neon")]
unsafe fn neon_transform_core(input: &[u32], output: &mut [u32]) {
    use std::arch::aarch64::*;
    
    let mut i = 0;
    // 1. 初始化常量向量广播
    let multiplier = vdupq_n_u32(3);
    let addend = vdupq_n_u32(7);
    
    // 2. 向量主循环：每次并发处理 4 个 32 位整数 (128 位宽)
    while input.len() - i >= 4 {
        // SAFETY: 索引边界经过严格检查；切片保证了非重叠与有效对齐
        unsafe {
            // 连续向量加载: ldr q
            let x = vld1q_u32(input.as_ptr().add(i));
            // 源码层是两条：先 vmulq_u32 再 vaddq_u32；能否融成一条 mla.4s 要看后端
            let y = vaddq_u32(vmulq_u32(x, multiplier), addend);
            // 连续向量存储: str q
            vst1q_u32(output.as_mut_ptr().add(i), y);
        }
        i += 4;
    }
    
    // 3. 尾部清理标量循环：处理不足 4 个元素的残余尾部
    for j in i..input.len() {
        output[j] = input[j].wrapping_mul(3).wrapping_add(7);
    }
}

pub fn safe_neon_transform(input: &[u32], output: &mut [u32]) {
    assert_eq!(input.len(), output.len());
    
    #[cfg(target_arch = "aarch64")]
    {
        // 利用标准库宏在运行时动态探测当前 CPU 是否支持 NEON 指令集
        if std::arch::is_aarch64_feature_detected!("neon") {
            // SAFETY: 已在运行时确凿验证了硬件特性的存在
            return unsafe { neon_transform_core(input, output) };
        }
    }
    
    // 回退路径：在不支持的硬件上优雅降级为安全标量处理
    fallback_transform(input, output);
}
```

::: def 定义 12.3.2 · target_feature 的 Unsafe 边界契约 {#def-12.3.2}

标记了 `#[target_feature(enable = "...")]` 的函数在 Rust 中**强制必须是 `unsafe fn`**。原因在硬件：宿主处理器的控制单元若没有该向量运算流水线，调用会触发非法指令陷入，内核随即杀死进程。调用者必须在调用前通过 `is_x86_feature_detected!` 或 `is_aarch64_feature_detected!` 建立运行时凭证（[@def-12.3.2]）。凭证、圈定、回退三步缺一步，就不算安全的向量化封装。

:::

### 12.3.4 跨平台双引擎内核：x86 AVX2 与 ARM NEON

跨平台工业级系统通常需要同时支持 x86_64 与 AArch64。通过条件编译与内联函数抽象，可以构建统一的向量加速引擎。这里统一的是入口，不是每条指令的编码：

```rust
// 跨架构双引擎向量加速内核
pub fn dual_engine_vector_transform(input: &[u32], output: &mut [u32]) {
    assert_eq!(input.len(), output.len());

    #[cfg(target_arch = "x86_64")]
    {
        if is_x86_feature_detected!("avx2") {
            // SAFETY: 运行时已检测到 AVX2 支持，切片长度已在前置断言等长
            return unsafe { avx2_transform_impl(input, output) };
        }
    }

    #[cfg(target_arch = "aarch64")]
    {
        if std::arch::is_aarch64_feature_detected!("neon") {
            // SAFETY: 运行时已检测到 NEON 支持，切片长度已在前置断言等长
            return unsafe { neon_transform_core(input, output) };
        }
    }

    // 针对既非 AVX2 亦非 NEON 的平台，优雅降级为自动向量化标量
    auto_transform(input, output);
}

#[cfg(target_arch = "x86_64")]
#[target_feature(enable = "avx2")]
unsafe fn avx2_transform_impl(input: &[u32], output: &mut [u32]) {
    use std::arch::x86_64::*;

    let mut i = 0;
    // 256 位寄存器单次容纳 8 个 32 位整型 (8 车道并行)
    let mult = _mm256_set1_epi32(3);
    let add = _mm256_set1_epi32(7);

    while input.len() - i >= 8 {
        // SAFETY: i..i+8 在有效切片范围内，未对齐载入保证内存安全
        unsafe {
            let x = _mm256_loadu_si256(input.as_ptr().add(i) as *const __m256i);
            let y = _mm256_add_epi32(_mm256_mullo_epi32(x, mult), add);
            _mm256_storeu_si256(output.as_mut_ptr().add(i) as *mut __m256i, y);
        }
        i += 8;
    }

    // 处理不足 8 个元素的尾部残余
    for j in i..input.len() {
        output[j] = input[j].wrapping_mul(3).wrapping_add(7);
    }
}
```

注意 x86 AVX2 每次步进 8 个元素（256 位），ARM NEON 每次步进 4 个元素（128 位）。在配备 AVX-512 的高端机器上，甚至可以通过硬件掩码寄存器（Mask Registers, $k_0 \sim k_7$）直接下发掩码存储指令 `_mm512_mask_storeu_epi32`：尾部不足 16 个元素的残余数据不需要标量分支清理，分支预测失败的潜在惩罚随之消除。

::: ex 例 12.3.1 · 谁负责尾巴 {#ex-12.3.1}

AVX2 内核按 8 步进、NEON 内核按 4 步进，两者都写了尾部标量清理循环；上文说 AVX-512 的掩码存储可以不留清理分支。

1. 处理 65539 个元素时，两个内核的主循环各留下几个尾部元素？
2. 掩码寄存器为什么能省掉尾部分支？
3. 忘写尾部清理循环，会出什么类型的错？

::: sol 解答

1. $65539 = 8 \times 8192 + 3 = 4 \times 16384 + 3$，两个内核都剩 3 个尾部元素（车道数按 [@def-12.1.2] 的公式算）。
2. 车道彼此独立（[@def-12.1.2]），掩码寄存器给每条车道一个「写不写」开关，一次掩码存储可以只写前 3 条车道，尾部不再是特殊路径。
3. 两类都可能：主循环照步长跑会越界读写内存；主循环提前停则尾部元素保持旧值，输出错误。12.6 的实验长度取 65539，就是为了让每条实现都必须走进这条路径并被校验和抓住。

:::

:::

::: think 思考 · 全局打开 +neon 行不行 {#think-12.3.1}

有人提议：反正目标是 Apple Silicon，直接 `RUSTFLAGS="-C target-feature=+neon"` 全局启用，省掉探测包装。这个论证哪里不完整？

::: sol 解答

结论也许侥幸成立，方法不成立。AArch64 基线确实普遍带 NEON，但这靠的是「我知道这块芯片」的外部知识，代码自己没有携带凭证；同样的写法换成 `+avx512f` 就会在旧 CPU 上当场 `SIGILL`（[@def-12.3.2]）。函数级 `target_feature` 加运行时探测的价值在于：危险范围被圈死在单个函数内，任何机器、任何特性组合下入口都有回退路径，编译器还能据此在不同 TU 里安全内联。全局开关把这些信息从类型系统里抹掉了。

### 12.3.5 小结与常见错误

**小结。**① 显式 SIMD 留给洗牌置换、专用硬件指令、饱和算术这三类编译器证不了的场景（12.3.1）；② 内联函数是带前提的薄封装，前提要自己证明（[@def-12.3.1]）；③ `#[target_feature]` 强制 `unsafe fn`，调用前必须有运行时探测凭证与回退路径（[@def-12.3.2]）；④ 尾部清理的正确性按车道数算账，AVX-512 掩码只是把这条路径合并进主指令（[@ex-12.3.1]）；⑤ 全局特性开关抹掉凭证与回退，不是简化（[@def-12.3.2]）。下一节 [12.4 零拷贝切片视图](#sec-cpp-rust.3.12.4) 把镜头从寄存器转向内存通路。

::: errata 常见错误清单（12.3 节）

E-a **未探测就调用带 `#[target_feature]` 的函数。**旧处理器上直接 `SIGILL`，凭证必须在使用点建立（[@def-12.3.2]）。

E-b **忘写尾部清理循环。**越界读写或输出错误二选一（[@ex-12.3.1]）；长度不是车道数整数倍时这条路径必然存在。

E-c **把显式 SIMD 滥用于简单逐元素映射。**12.6 实测它相对自动向量化没有额外收益，却平添移植与 `unsafe` 面。

E-d **把内联函数当安全函数。**`vld1q_u32` 不检查边界、不保证对齐，安全前提由调用方承担（[@def-12.3.1]）。

E-e **拿 AVX-512 掩码论证「宽就是好」。**掩码省的是尾部分支；降频与带宽代价仍在 12.1.2 的账单里。

E-f **跨平台规划时照搬别家车道数。**AVX2 步进 8、NEON 步进 4，混用会让一个平台的尾部逻辑在另一个平台上失效（[@def-12.1.2]）。

入口函数里先 `is_x86_feature_detected!("avx2")`：真则调用 `#[target_feature(enable = "avx2")]` 的 unsafe 内核（SAFETY 注释写明边界与非重叠凭证），假则走自动向量化标量回退（[@def-12.3.2]）。全局 `target-feature` 开关只改变代码生成，它不能替你做运行时探测，靠它赌用户机器就会在旧机器上崩。

## 12.4 零拷贝切片视图与生命周期约束 {#sec-cpp-rust.3.12.4}

本节回答一个问题：**怎样解析一个 100 字节的协议帧，而不产生一次堆分配？**图 12-1 的下半部已经预告了答案的形状：把「数据在哪」与「数据归谁管」拆成一个指针加一个长度。这一节给出它的类型表示、生命周期约束，以及它替 C 挡掉的两类经典事故。

::: preview 先抓住一件事

零拷贝不是「少拷一点」，而是让业务对象从头到尾不拥有字节。代价是所有权问题的形态变了：拷贝版出错是运行时泄漏或越界，借用版出错被编译器在类型层拒绝——生命周期参数 `'a` 就是拒绝的载体（[@def-12.4.2]）。
:::

### 12.4.1 传统网络/数据流解析中的拷贝深渊

在传统的系统服务实现中，处理连续到达的 TCP 字节流、RPC 分帧（Frame）或文件数据时，普遍存在如下低效模式：

```text
[ 网络缓冲区 (Socket Buffer) ]
             │
             ▼ memcpy (内核向用户态拷贝)
[ 用户态环形缓冲区 (Read Buffer) ]
             │
             ▼ malloc + memcpy (为每个逻辑包分配独立 String/Vec)
[ 业务对象 Packet { payload: Vec<u8> } ]
             │
             ▼ 业务解析与最终销毁 (free)
```

在这种模式下，一个 100 字节的协议帧可能经历 3 次独立的内存拷贝与 2 次全局堆分配器（`malloc`/`free`）调用。在万兆（10GbE）乃至百G（100GbE，即 100 Gbit/s）网络吞吐下，绝大部分 CPU 时钟周期被空耗在向内存总线搬运数据和堆内存碎片整理上。这些周期不是花在业务逻辑上，而是花在搬运上——业务代码一行没多，账却先付了。

### 12.4.2 切片引用（Slice View）的代数学结构

Rust 的切片引用（`&'a [u8]`）是天然的高性能**零拷贝（Zero-Copy）核心抽象**。在物理 ABI 上，切片借用仅仅是一个包含两个机器字宽度的胖指针（Fat Pointer）：

```rust
// 逻辑上的切片结构表示
#[repr(C)]
pub struct RawSliceView {
    pub ptr: *const u8, // 指向底层连续内存缓冲区的起始物理地址 (8 字节)
    pub len: usize,     // 视图的连续字节长度 (8 字节)
}
```

::: def 定义 12.4.1 · 切片视图与胖指针 slice view / fat pointer {#def-12.4.1}

**切片视图**是对一段连续内存的带长度引用；**胖指针**指它在 ABI 上的形态：一个指针字加一个长度字，共 16 字节。创建、切分或传递视图只动这两个字，不动底层数据（[@def-12.4.1]）。原文说传递耗时「不到 1 纳秒」是寄存器对搬运的量级论断，本节没有对该操作单独计时。

:::

业务层拿到视图后，遍历、校验、解码全在宿主缓冲区的原地址上进行。12.7 的实测对照（`owned_copy` 对比 `borrowed_view`）量化的就是这一句的价值。省掉的是复制，付出去的是生命周期，这两笔账不能只记一边。

### 12.4.3 零拷贝分帧解析器的生命周期设计

在 `bench/systems-lab/src/lib.rs` 中，我们设计了一个高效的二进制分帧解析系统。每个帧的格式为：`[ 4 字节小端长度头 ][ N 字节连续载荷 ]`。

```rust
#[derive(Debug, PartialEq, Eq)]
pub enum ParseError {
    Truncated,
    TooLarge,
    Trailing,
}

/// 核心零拷贝解析器：返回的切片视图生命周期严格绑定至底层原始输入缓冲区 'a
pub fn next_frame(bytes: &[u8], limit: usize) -> Result<(&[u8], &[u8]), ParseError> {
    // 1. 安全读取 4 字节头部：边界检查由 get() 静态兜底，绝无越界风险
    let header = bytes.get(..4).ok_or(ParseError::Truncated)?;
    let length = u32::from_le_bytes(header.try_into().expect("four bytes")) as usize;
    
    // 2. 契约防御：拒绝超大异常帧，防范恶意长度
    if length > limit {
        return Err(ParseError::TooLarge);
    }
    
    let rest = &bytes[4..];
    // 3. 截取载荷切片视图：直接借用 rest 中的连续内存，不产生任何堆分配！
    let payload = rest.get(..length).ok_or(ParseError::Truncated)?;
    
    // 返回 (当前帧载荷, 剩余未消费字节)
    Ok((payload, &rest[length..]))
}
```

生命周期参数省略（Lifetime Elision）在此处起到了编译期铁律的保护作用：`next_frame` 返回的两个切片 `(&[u8], &[u8])`，其生命周期与入参 `bytes: &'a [u8]` 严格同源。这意味着：
- 业务逻辑可以在不复制数据的情况下直接对 `payload` 执行遍历、校验、反序列化；
- 编译器静态阻止任何试图在底层 `bytes` 缓冲区被销毁或重写之后继续使用 `payload` 的非法代码；
- 彻底根除了 C 语言中使用裸指针解析数据流时极其普遍的**释放后使用（Use-After-Free）**与**缓冲区溢出（Buffer Overflow）**隐患。

::: ex 例 12.4.1 · limit 防线拒绝的是谁 {#ex-12.4.1}

`next_frame` 在读取长度头后有 `if length > limit { return Err(ParseError::TooLarge) }`。

1. 恶意头部声明 `length = 0xFFFF_FFF0` 时，`rest.get(..length)` 本身会越界或分配吗？
2. 既然 `get` 已经安全，这条 `limit` 防线防的是谁？
3. 拷贝版解析器（`to_vec`）在同一恶意头部下会怎样？

::: sol 解答

1. 不会。`get` 越界返回 `None`，走 `Truncated` 分支；视图截取只动指针和长度，不触碰数据（[@def-12.4.1]）。
2. 防的是**下游消费者**。若不拒绝，载荷声明会原样传给按长度行事的外层逻辑——重传缓冲、按帧预分配、协议状态机都信这个数字。`TooLarge` 把「声明的长度」变成契约的一部分，而不是运行时事故的伏笔。
3. 拷贝版会为声称的 4 GB 载荷真的去申请内存：单次恶意帧就能放大成 OOM 或长暂停。这正是拥有型与借用型在**攻击面**上的差别，12.7 只测了它们的耗时与分配次数，攻击面没有量化采集。

:::

### 12.4.4 嵌套零拷贝协议栈的生命周期级联传播

在真实的分布式网络通信中，协议通常由多层报头嵌套而成（例如以太网帧头 $\rightarrow$ IP 报头 $\rightarrow$ TCP 报头 $\rightarrow$ 业务 Payload）。Rust 的生命周期系统允许我们构建级联零拷贝结构体，保证整条协议栈完全不发生单字节拷贝：

```rust
// 零拷贝分层协议包抽象
pub struct PacketHeader<'a> {
    pub magic: u16,
    pub session_id: u32,
    pub raw_header: &'a [u8],
}

pub struct PacketView<'a> {
    pub header: PacketHeader<'a>,
    pub payload: &'a [u8],
}

impl<'a> PacketView<'a> {
    pub fn parse(raw: &'a [u8]) -> Result<Self, &'static str> {
        if raw.len() < 8 {
            return Err("packet truncated");
        }
        let magic = u16::from_be_bytes(raw[0..2].try_into().unwrap());
        let session_id = u32::from_be_bytes(raw[2..6].try_into().unwrap());
        let payload_len = u16::from_be_bytes(raw[6..8].try_into().unwrap()) as usize;
        
        let rest = &raw[8..];
        if rest.len() < payload_len {
            return Err("payload truncated");
        }

        Ok(PacketView {
            header: PacketHeader {
                magic,
                session_id,
                raw_header: &raw[0..8],
            },
            payload: &rest[..payload_len],
        })
    }
}
```

无论下游业务层如何检索与传递 `PacketView` 的字段，所有生命周期引用 `'a` 都如影随形。调用者无法在释放底层网络接收缓冲区后悬空访问 `payload`。编译器的借用检查器在此处充当了永久在线、零运行时开销的「协议安全卫士」。这条防线不是在运行时才拉起来的：不合规矩的代码根本编译不出来。

::: def 定义 12.4.2 · 生命周期级联传播 cascading lifetime {#def-12.4.2}

当一个借用切片的字段被继续放进新结构体时，参数生命周期 `'a` 沿字段一层层传播，形成**级联**：`PacketHeader<'a>` 嵌进 `PacketView<'a>`，二者共享同一份「宿主缓冲区存活期」上限（[@def-12.4.2]）。级联的后果是约束的传递：只要 `'a` 结束，链条上每一个视图都同时失效——这正是编译器拒绝 use-after-free 的机制，而不是运行时的运气。

:::

### 12.4.5 现代零拷贝序列化框架的架构对比

在现代高性能网络与存储系统中，如何避免中间拷贝是协议设计的核心分水岭。下表系统对比了四种主流数据序列化/传输机制在零拷贝支持与安全约束上的表现：

| 方案 / 库 | 解析耗时模型 | 内存布局与内存分配 | 安全生命周期绑定 | 典型适用场景 |
|:--|:--|:--|:--|:--|
| **Serde (JSON / Bincode)** | $O(N)$ 反序列化 | 产生大量中间堆分配 (`String`, `Vec`) | 解耦（拥有型所有权，独立存活） | 通用 Web API、配置加载、控制面通信 |
| **Cap'n Proto** | $O(1)$ 寻址 | 预先按对齐布局的 Arena 内存池 | 通过借用切片与指针偏移严格受限 | 微服务低延迟 RPC、IPC 共享内存 |
| **FlatBuffers** | $O(1)$ 寻址 | 内部基于 vtable 偏移，向前兼容 | 依赖只读 `&[u8]` 视图，无堆分配 | 游戏网络同步、移动端轻量缓存 |
| **rkyv** (Rust 专属) | **严格 $O(1)$** | **直接将 Rust 内存对象映射在磁盘/网络字节上** | 基于 Rust 借用规则与对齐验证强校验 | 高性能数据库存储引擎、本地高性能 IPC |

在基于 `rkyv` 或本章所设计的二进制分帧模型中，数据在网络传输或磁盘落盘时的结构与其在 CPU 缓存中的结构完全重合，从而彻底达成了「加载即解析、寻址即读取」的理论极致。这份重合靠的是预先排好的布局，不是运行时的运气。

### 零拷贝与非对齐访问的深渊

在从字节切片反序列化多字节结构（如 `u32` 或复杂结构体）时，许多开发者习惯性地进行指针强转：

```rust
// 危险的未定义行为！切勿模仿！
pub unsafe fn read_u32_bad(slice: &[u8]) -> u32 {
    *(slice.as_ptr() as *const u32)
}
```

在 x86 架构上，硬件通常容忍未对齐的加载（代价是轻微的性能损失）；但在许多 ARM 或 RISC-V 核心上，未对齐的指针解引用会直接引发硬件异常（Hardware Fault）并导致操作系统向进程发送 `SIGBUS`。
安全零拷贝处理非对齐内存的规范方案是：使用 `std::ptr::read_unaligned` 或采用小端转换函数：

```rust
pub fn read_u32_safe(slice: &[u8]) -> u32 {
    let bytes: [u8; 4] = slice[..4].try_into().expect("slice too short");
    u32::from_le_bytes(bytes) // LLVM 会将其在支持的硬件上直接折叠为单条非对齐加载指令！
}
```

::: think 思考 · 把视图换成偏移量，能不能更省 {#think-12.4.1}

`PacketView<'a>` 里每个借用字段都是 16 字节的胖指针。有人提议改存「相对宿主缓冲区起点的偏移量」，说结构体更小、还能随手放进队列。按[@def-12.4.1]与[@def-12.4.2]检查这笔交易。

::: sol 解答

省下的只是一个指针字。偏移加长度仍是两个数，下游每个函数都得额外带上宿主切片才能还原，还原之后拿到的还是同一个胖指针，字节一分没少。赔上的却是类型保护：`'a` 从字段上消失，「宿主销毁后不许再用」这条[@def-12.4.2]的级联约束退化成注释与调用纪律，越界从编译期挪到运行时。12.4.5 表里 Cap'n Proto 与 rkyv 走的是反方向——把宿主做成显式的只读缓冲池，视图继续借用它，而不是让业务自己记偏移。
:::

::: errata 常见错误清单（12.4 节）

E-a **把零拷贝当成一个开关。**它要求业务对象从头到尾不拥有字节；中途一次 `to_vec()` 就把搬运的账付回去（preview、[@def-12.4.1]）。

## 12.5 类型尺寸、布局与汇编展开特征 {#sec-cpp-rust.3.12.5}

本节回答一个问题：**一个类型占多少字节、对齐到几，能不能推出它在寄存器里怎么传、在循环里怎么展开？**前半句能，后半句不能。尺寸与对齐是语言层的承诺，汇编是某一次构建的观察。这一节把探针表（用一段只为观察布局而写的小程序量出来的表）、手写内核的汇编和 IR 摆在一起，划清各自能证明的那句话。

::: preview 先抓住一件事

同一句「这个类型很轻」可能在说三件事：占的字节少、传参不落栈、循环里被展开成向量。**三件事各有各的证据，不能互相顶替。**判一句话成立不成立，先问它依据的是布局表、编译产物，还是计时。本节只走到前两层，第三层留给 12.6。
:::

### 12.5.1 尺寸与对齐是两个不同的数

::: def 定义 12.5.1 · 尺寸与对齐 size / alignment {#def-12.5.1}

**尺寸**是一个值在内存里占的字节数，含内部填充；**对齐**是它的起始地址必须满足的倍数。数组按元素尺寸连续排列，所以 `[u32; 4]` 的尺寸是 16、对齐是 4——对齐跟元素走，不跟总尺寸走。

:::

`bench/systems-lab/src/bin/layout.rs` 用一个 `show::<T>` 逐行打印 `size` 与 `align`。`results/run-01/layout.txt` 这份原始输出一共七行，其中与数据通路有关的是：

| 类型 | 尺寸（字节） | 对齐（字节） | 证据 |
|:--|--:|--:|:--|
| `&[u8]` | 16 | 8 | `layout.txt`，探针行 |
| `Vec<u8>` | 24 | 8 | `layout.txt`，探针行 |
| `Arc<[u8]>` | 16 | 8 | `layout.txt`，探针行 |
| `&mut [u32]` | 16 | 8 | 归档未采集，按布局规则写出 |
| `[u32; 4]` | 16 | 4 | 归档未采集，按布局规则写出 |

后两行不在 `layout.txt` 里，本节没有采集它们的探针输出。数值来自 Rust 的布局规则，可以用同一个 `show::<T>` 复核；它们是规则推出来的，不是探针打出来的，这两行的身份要写清。

尺寸解释的是「怎么传」，不是「跑多快」。`&[u8]` 是 16 字节，正好两个机器字：一个放指针，一个放长度（[@def-12.4.1]）。`Vec<u8>` 是 24 字节，多出来的 `cap` 是扩容要用的第三个字。

按 AArch64 的调用约定，两个通用寄存器装得下 16 字节；24 字节装不下，通常会改走内存。这是传参形状的推断，本节没有测传参开销。

`[u32; 4]` 的 16 字节可以一次装进 128 位向量寄存器，这正是 12.1 里 4 个车道的形状（[@def-12.1.2]）。但「可以装进去」不等于「一定装进去」：装不装要看上下文和寄存器压力，只有编译产物能回答。尺寸表回答不了这一问，它不是那一层的证据。

### 12.5.2 手写内核在汇编里展开成什么

在 `results/run-01/codegen/systems_lab-*.s` 这份汇编产物里，`neon_inner` 的循环主体是这 8 行：

```asm
LBB49_3:
    ldr    q1, [x10], #16    ; 读 16 字节到 q1，x10 后移 16
    movi.4s v2, #7          ; v2 = [7, 7, 7, 7]
    mla.4s  v2, v1, v0      ; v2 = v1 * v0 + v2，4 车道各算各的
    str    q2, [x11], #16   ; q2 写回，x11 后移 16
    sub    x9, x9, #4
    add    x8, x1, x9
    cmp    x8, #3
    b.hi   LBB49_3
```

`v0` 在循环外用 `movi.4s v0, #3` 建好。真正搬数据的只有 3 条：`ldr`、`mla`、`str`。`movi.4s v2` 每轮重建一次加数，`sub`/`add`/`cmp`/`b.hi` 四分管计数与跳转。剩下这 5 条不是在算数据，而是在准备常量和管循环。

::: def 定义 12.5.2 · 后变址寻址与乘加融合 post-index / multiply-accumulate {#def-12.5.2}

**后变址寻址**把「按当前基址访问」与「访问后基址自增」压进一条指令：`ldr q1, [x10], #16` 读完 16 字节，顺手把 `x10` 加 16。**乘加融合**把 `a * b + c` 做成一条 `mla`，乘积不单独落一个寄存器。

:::

这三条数据指令合起来，才有一轮 4 个元素的代价：一次非对齐装载、一次 4 车道乘加、一次存储。IR 里的 `align 1` 不是笔误：`vld1q_u32` 不要求 16 字节对齐，所以标注只保证 1 字节。这也解释了 12.4 末尾为什么非对齐读取要靠 `read_unaligned` 一类接口。

把这段循环说成「只消耗 3 条汇编指令」并不准确。3 条是数据指令；把常量与控制算进去是 8 条。说成 3 条，会让人误以为循环开销为零。

### 12.5.3 同一份 IR 里的 4 车道与标量尾巴

`.ll` 是同一批产物里的另一份，`neon_inner` 的循环基本块是 4 车道形状：

```llvm
bb2.i:
  %_3.i.sroa.0.0.copyload.i = load <4 x i32>, ptr %_0.i6.i, align 1
  %_15.i = mul <4 x i32> %_3.i.sroa.0.0.copyload.i, splat (i32 3)
  %y.i = add <4 x i32> %_15.i, splat (i32 7)
  store <4 x i32> %y.i, ptr %_0.i.i, align 1
  %0 = add i64 %i.sroa.0.016.i, 4
  %_6.i = icmp ugt i64 %_7.i, 3
  br i1 %_6.i, label %bb2.i, label %bb7.i
```

`<4 x i32>` 就是 4 个 32 位车道，`splat (i32 3)` 是把标量 3 铺满 4 个车道。索引每次加 4，剩下不足 4 个时跳出。

跳出之后并不在 IR 里展开标量循环，而是 `tail call @auto_transform`。手写内核的尾巴交给自动版本，所以「手写 NEON」并不是每个元素都手写。

同一份 `.ll` 里的 `auto_transform` 是另一幅样子：`load i32`、`mul i32`、`add i32`、`store i32`，一条车道也没有。对应的 `.s` 也是标量四指令循环。这与 12.6 的实测不矛盾，但也不能互相作证。

这批 `.ll`/`.s` 由 `cargo rustc --lib --emit=mir,llvm-ir,asm` 产生。最终二进制还经过 thin LTO，`environment.txt` 记的是完整一行 `profile=release; thin LTO; codegen-units=1; debug=1`。当时没有保留最终二进制的反汇编，所以「auto 也被展开成 4 车道」这句话，本节没有代码生成证据。

这正好是一条方法：**产物只对生成它的那次构建负责。**要用手写内核的汇编解释 12.6 的计时，得先确认两者来自同一份二进制；做不到，就只能把结论停在「这份产物这样展开」。

### 12.5.4 判定流程：一句话该用哪层证据

::: method 判定流程 · 布局、代码生成、性能各问一次

① **问尺寸**：多大、对齐几？查 `size_of`/`align_of` 或 `layout.txt`；表里没有的行，写「未采集」，不要补。<br>
② **问传参**：由尺寸加调用约定推；两个机器字装得下就按寄存器传，装不下就准备走内存。<br>
③ **问指令形状**：只认编译产物，并写明构建参数与阶段；rlib 的产物不等于最终二进制，它不能替最终二进制说话。<br>
④ **问快慢**：只认同配置计时；产物再整齐也不能替代一次测量。<br>
⑤ **三层对不上**：先怀疑构建不一致。挑一个顺眼的当结论，那份结论就不再是证据链上的结论了。

:::

::: ex 例 12.5.1 · 数一数这段循环的车道与尾巴 {#ex-12.5.1}

12.5.2 的循环用 `q` 寄存器，`N = 65539`，尾部交给 `auto_transform`。

1. 每一轮处理几个元素、几条数据指令？
2. 主循环执行多少轮、尾部剩几个元素？
3. 若把 `q` 换成 `d` 寄存器、`4s` 换成 `2s`，尾部会变成几个？

::: sol 解答

1. `q` 是 128 位，按 `4s` 看是 4 个 32 位车道，所以每轮 4 个元素。数据指令 3 条：`ldr`、`mla`、`str`（[@def-12.5.2]）。
2. `65539 = 4 × 16384 + 3`，主循环 16384 轮，尾部 3 个元素。尾部走 `auto_transform`，不在汇编的主循环里。
3. 每条指令只剩 2 个车道，主循环变成 32769 轮，尾部 1 个元素。步进与尾部长度都要跟着车道数改（[@def-12.1.2]）。

:::

:::

::: think 思考 · 对齐是 4，就能把任意字节切片读成 u32 数组吗 {#think-12.5.1}

`align_of::<[u32; 4]>() = 4`，所以有人把 `&[u8]` 的前 16 字节直接 `transmute` 成 `[u32; 4]`，理由是「类型只要求 4 字节对齐」。这个前提哪里被换掉了？

::: sol 解答

换掉的是「类型属性」与「这个地址的属性」。对齐 4 说的是：一个合法的 `[u32; 4]` 值，地址一定是 4 的倍数。它不保证你手上这段 `&[u8]` 的起始地址满足 4 的倍数——切片可以从协议帧的第 3 个字节开始。

地址不满足就是未定义行为，不是「慢一点」。规范做法是 `read_unaligned` 或 `from_le_bytes`，先按字节取再组装（12.4 末段）。即使地址对齐，长度与生命周期还要另外证明。

:::

:::

### 12.5.5 小结与常见错误

**小结。**① 尺寸与对齐是语言承诺，`layout.txt` 只探了七行，另外两行本节没有采集（[@def-12.5.1]）；② 16 字节的切片是两个机器字，24 字节的 `Vec` 多一个 `cap`；③ 手写内核对这份产物展开成每轮 4 个车道、3 条数据指令，常量与控制另算（[@def-12.5.2]）；④ IR 与汇编只对生成它的那次构建负责，最终二进制的反汇编没有归档；⑤「有 `mla`」推不出「更快」，那是 12.6 的计时问题。

::: errata 常见错误清单（12.5 节）

E-a **拿 `size_of` 当性能指标。**16 字节只说明传参宽度，不说明循环快慢（[@def-12.5.1]）。

E-b **把 `[u32; 4]` 的对齐写成 16。**对齐跟元素走，是 4；对齐 4 也不保证任意切片地址可用（本节思考框）。

E-c **把「3 条数据指令」说成「循环体 3 条指令」。**常量与控制还有 5 条，漏掉会把循环开销算成零（12.5.2）。

E-d **用 rlib 的 `.s` 解释最终二进制的速度。**链接期优化不在归档里，先查构建阶段（12.5.3）。

E-e **看到 `mla` 就宣布更快。**指令形状只说明做了什么，不说明吞吐（[@def-12.5.2]）。

E-f **把未采集的两行写成探针结果。**`layout.txt` 只有七行，缺的行要标「未采集」（12.5.1）。

:::

::: method 即时自测 · 12.5

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　`[u32; 4]` 的尺寸与对齐各是多少？为什么对齐不是 16？

::: sol 第 1 题答案
尺寸 16 字节，对齐 4 字节。对齐由元素 `u32` 决定，数组不提高对齐要求；总尺寸是 4 × 4，对齐仍是 4（[@def-12.5.1]）。

**第 2 题 · 辨析**　`Vec<u8>` 24 字节、`&[u8]` 16 字节，能说前者「传参更贵」吗？

::: sol 第 4 题答案
查 `size_of`、`align_of` 与 `offset_of`，写成可复核的断言。拿某次汇编反推字段偏移，就不算布局契约——汇编只说明这份产物的访问方式，布局契约要由语言规则与探针共同支撑（[@def-12.5.1]）。
:::

## 12.6 benchmark一：标量循环与自动/手写NEON向量化实测 {#sec-cpp-rust.3.12.6}

本节回答一个问题：**同一段「乘 3 加 7」，去掉逐元素函数调用、交给自动向量化、再手写 NEON，各自能省下多少时间？**`run-01` 这批记录给出的答案是：第一步省下约 7.7 倍，第二步几乎不再省。这一节把 21 批原始记录、汇总统计和三种写法的边界摆出来，说明这句话能说到哪一步。

::: preview 先抓住一件事

这批数据里，**提升几乎全部来自「每个元素不再走一次函数调用」**，而不是「手写」本身。标量调用平均每个元素 0.535004 纳秒，自动向量化 0.069184 纳秒，手写 NEON 0.069965 纳秒。后两者只差 0.000781 纳秒。记录里没有给出这个差值的区间，所以只能说均值略低，不能说是谁稳定更快。
:::

### 12.6.1 实验设置：一个质数长度、三种写法

入口是 `bench/systems-lab/src/bin/simd.rs`。数组长度 `N = 65539`，每批重复 16 次，合计 1,048,624 个元素。`65539 = 4 × 16384 + 3`，是质数且不被 4 整除，两种向量化实现都必须处理尾部。每批结束断言 `output == expected`，并返回 64 位校验和 `140746630219670`。

手写向量汇编常被说成性能银弹。这组实验就是来量它的：在无别名、无跳转的连续数组上，手写内联函数相对自然写法还能拿到多少。银弹这句话不是测出来的，它来自「手写就更懂硬件」这一直觉；实验要回答的是能拿到多少，不是谁更体面。

::: def 定义 12.6.1 · 元素归一化耗时 ns/元素 {#def-12.6.1}

把一批的墙钟纳秒数除以这一批的元素数，得到**每元素耗时**。它让不同批大小的数字可以并排，也把装载、算术、存储、循环控制揉进同一个数。它是一个聚合量，不是一个元素的延迟。

:::

| 模式 | 写法 | 关键机制 | 尾部 |
|:--|:--|:--|:--|
| `scalar_call` | 逐元素调用 `#[inline(never)] scalar_step` | 每次一次 `bl`、一次栈帧 | 逐元素，无主循环 |
| `auto` | `zip` 加 `wrapping_mul`/`wrapping_add` | 交给 LLVM 自动向量化（[@def-12.2.1]） | 编译器生成 |
| `neon` | `vld1q_u32`/`vmulq_u32`/`vaddq_u32`/`vst1q_u32` | 4 车道内联函数（[@def-12.3.1]） | 手写 4 车道主循环，余数转 `auto` |

`scalar_call` 的存在不是为了赢，而是给另外两种一个「调用边界还在」的参照。它的每个元素都要经过一次调用约定：参数搬运、栈帧、返回。`auto` 与 `neon` 都把这一步消掉了，所以第一层差距在 7 倍量级，不在 1% 量级。

### 12.6.2 驱动器：21 批、交替顺序、每批 1,048,624 个元素

下面是 `simd.rs` 的入口，也就是 `source-sha256.txt` 记下哈希的那一版：

```rust
use std::hint::black_box;
type TransformFn = fn(&[u32], &mut [u32]);

fn main() {
    const N: usize = 65539;
    const REPEAT: usize = 16;
    let input = systems_lab::make_input(N);
    let expected = input
        .iter()
        .map(|x| x.wrapping_mul(3).wrapping_add(7))
        .collect::<Vec<_>>();
    let mut output = vec![0; N];
    let functions: [TransformFn; 3] = [
        systems_lab::scalar_transform,
        systems_lab::auto_transform,
        systems_lab::neon_transform,
    ];
    systems_lab::measure(&["scalar_call", "auto", "neon"], N * REPEAT, |case| {
        for _ in 0..REPEAT {
            functions[case](black_box(&input), black_box(&mut output));
            black_box(&output);
        }
        assert_eq!(output, expected);
        output.iter().map(|&v| u64::from(v)).sum()
    });
}
```

`measure` 先预热到 500 ms，三种配置轮流跑。原始记录的第一行是 `warmup_ns=500298291 rounds=698 units=1048624`：预热了 698 轮，实际约 500.3 ms。预热结束后进入测量，跑 21 轮，每轮从不同的模式开始，顺序按 `(round + offset) % 3` 轮转，避免某个实现总占同一时隙。时隙一旦固定，差值里就混进时段效应，算出来的就不是实现之间的差了。

::: def 定义 12.6.2 · 批与批均值 batch / batch mean {#def-12.6.2}

一次 `run(case)` 的墙钟时间是一**批**；把一个实现 21 批的每元素耗时取算术平均，得到**批均值**。批是抽样单位，代表一段时间内的整批工作，不是一次请求。批均值回答「这 21 批平均怎样」，不回答「最慢的一次怎样」。

:::

::: def 定义 12.6.3 · 样本标准差与 nearest-rank 分位数 {#def-12.6.3}

**样本标准差**用 `N − 1` 作分母，衡量批与批的波动。**nearest-rank 分位数**把 21 个数排序后取第 `ceil(21 × p)` 个：p50 是第 11 个，p99 是第 21 个，也就是最大值。21 个样本上的 p99 没有尾部含义，它只是最大值。

:::

::: def 定义 12.6.4 · 加速比 speedup {#def-12.6.4}

同一单位下，基准实现的批均值除以候选实现的批均值。它是倍数，不是百分比：7.73 倍与「快 673%」是同一件事的两种说法。分母换了，倍数就不能横向比。

:::

### 12.6.3 实测：三行汇总，一张 21 批的底账

来源是 `bench/systems-lab/results/run-01/simd.txt` 的 summary 行，单位 ns/元素，`n=21`。

| 模式 | 批均值 | 样本标准差 | 批 p50 | 批 p99 | 相对标量 |
|:--|--:|--:|--:|--:|:--|
| `scalar_call` | 0.535004 | 0.012816 | 0.537967 | 0.560973 | 1.00 倍 |
| `auto` | 0.069184 | 0.003189 | 0.069456 | 0.078119 | 7.73 倍 |
| `neon` | 0.069965 | 0.003086 | 0.070251 | 0.075973 | 7.65 倍 |

标准差相对均值：`scalar_call` 约 2.4%，`auto` 约 4.6%，`neon` 约 4.4%。三种实现的轮间波动都在几个百分点，这一点后面判差值时要用到。

原始记录里还留着 21 条 `raw` 行。取每行的 ns 除以 `units=1048624`，就是这一轮的 ns/元素。抽四轮看形状：

| 轮次 | `scalar_call` | `auto` | `neon` |
|:--:|--:|--:|--:|
| 0 | 0.538205 | 0.070846 | 0.071959 |
| 3 | 0.520921 | 0.065204 | 0.064847 |
| 15 | 0.560973 | 0.078119 | 0.067429 |
| 19 | 0.512299 | 0.069456 | 0.065840 |

这四轮里 `neon` 赢三轮（第 3、15、19 轮），只有第 0 轮 `auto` 略快；第 15 轮同时是 `auto` 全 21 轮中最慢的一次（0.078119）。抽查轮次偏向哪一头都不奇怪，逐轮值不是结论，它们只是 21 个样本里的四个。

p50 与 p99 更不是「中间那一轮」。`scalar_call` 的 p50 来自第 7 轮，`auto` 的来自第 19 轮，`neon` 的来自第 6 轮；三个 p99 分别来自第 15、15、13 轮。把它们当成某一轮的读数，是最常见的误读。

::: ex 例 12.6.1 · 把三行汇总算成三句话 {#ex-12.6.1}

用上面的汇总行回答：

1. `auto` 相对 `scalar_call` 的加速比是多少？
2. `auto` 比 `neon` 的均值低多少？
3. 能不能说 `auto` 的尾部更差？

::: sol 解答

1. `0.535004 ÷ 0.069184 = 7.733`，即 7.73 倍；`neon` 是 `0.535004 ÷ 0.069965 = 7.647`，即 7.65 倍（[@def-12.6.4]）。
2. `0.069965 − 0.069184 = 0.000781` ns/元素，相对 `neon` 是 `0.000781 ÷ 0.069965 = 1.1%`。这个差没有配对的区间，只能写成「均值低 1.1%」（[@def-12.6.2]）。
3. 不能。`auto` 的 p99 0.078119 是 21 个样本的最大值，来自第 15 轮；`neon` 的最大值来自第 13 轮。单轮极值受当轮系统状态影响，轮间标准差已有 4% 量级。要谈尾部，得换一套采集设计，本节没有采集（[@def-12.6.3]）。

:::

### 12.6.4 这批数字能支持哪句话

显式 SIMD 仍有它的位置：洗牌置换、专用硬件指令、跨车道复杂归约，这些是自动向量化证不了的地方（[@def-12.3.1]）。简单的逐元素映射不在其中。这条定位是结构判断，不是本节的计时结论。

::: method 判定流程 · 从一张批均值表能说到哪一步

① **对单位**：是不是 ns/元素？分母是名义元素还是实际访问的元素？这里三种实现都读了全部 1,048,624 个元素，分母可用。<br>
② **看波动**：把标准差除以均值。本节三个值在 2.4%–4.6%，小于这个量级的差不该排座次。<br>
③ **算差值**：给出绝对差与相对差，并注明有没有区间。没有区间，就不做「谁更快」的判断。<br>
④ **看尾部**：p99 在 21 个样本上就是最大值，只能描述某一轮，不能外推成生产 p99。<br>
⑤ **说归因**：本节只有「去掉调用」与「手写」两组对比，没有 IPC、cache miss、周期数，拆不开更细的机制（本节没有采集）。

:::

::: think 思考 · 均值低 1.1%，能不能写「自动向量化更强」 {#think-12.6.1}

`auto` 的批均值 0.069184，比 `neon` 的 0.069965 低 1.1%，21 批的顺序还是轮转的。把这句话写成「自动向量化优于手写 NEON」，缺了哪一步？

::: sol 解答

缺的是「这个差能不能从轮间波动里分出来」。两者标准差是 0.003189 与 0.003086，约 4.4%–4.6%，比 1.1% 的均值差还大；这批记录没有做配对差值，也没有区间。

按第 1 章的三态判定，这属于「证据不足」，不是「自动更强」。能写的是：在这台机器、这个构建、这组输入上，两者没有分出方向。要分方向，得用配对设计重采，本节没有采集。

:::

### 12.6.5 小结与常见错误

**小结。**① 一批是 1,048,624 个元素，21 批轮转执行，单位是 ns/元素（[@def-12.6.1]）；② 标量调用 0.535004，自动 0.069184，手写 0.069965，前一步 7.73 倍、后一步 7.65 倍（[@def-12.6.4]）；③ 自动与手写只差 0.000781 ns/元素，约 1.1%，没有区间就不分方向；④ p50/p99 是排序后的第 11/21 个样本，不是某一轮（[@def-12.6.3]）；⑤ 本节没有 IPC、cache miss 与最终二进制反汇编，归因只能停在「去掉调用」这一层。

::: errata 常见错误清单（12.6 节）

E-a **把 7.73 倍说成「向量化带来 7.73 倍」。**标量调用还背着 `bl` 与栈帧；调用开销与向量化收益没有拆开（本节没有采集周期数）。

E-b **把 1.1% 写成「自动向量化更强」。**没有配对区间，轮间标准差已有 4% 量级（[@def-12.6.2]）。

E-c **把 p50/p99 当成某一轮的值。**它们是排序后的样本，来自不同轮次；p99 就是 21 个里的最大值（[@def-12.6.3]）。

E-d **用 21 个样本的 p99 外推生产尾延迟。**样本量与采集设计都不支持这句话（12.6.3）。

E-e **拿 rlib 的 `.ll`/`.s` 解释这批计时。**最终二进制经过 thin LTO，反汇编没有归档（12.5.3）。

E-f **忽略 65539 的余数。**16384 轮向量后还有 3 个元素，尾部走标量；写错这一段，校验和立刻变（12.6.1）。

## 12.7 benchmark二：拥有型复制流与借用型分帧解析 {#sec-cpp-rust.3.12.7}

本节回答一个问题：**同一份字节，「复制一份」和「借来看一眼」，为什么能差 3.6 倍？**12.4 给出了切片视图的类型表示（[@def-12.4.1]），却没有给价格。这一节把 `to_vec()` 与借用视图放进同一套夹具、同一份输入，用 21 批逐批记录的测量量出两条路径的距离。

::: preview 先抓住一件事

这里测的不是内存带宽，而是**每帧一次堆分配加一次拷贝**的账单。消费逻辑按 64 字节步进采样（[@def-12.7.2]），把纯读取压小，让分配浮上来。3.60 倍只对「4096 个 1024 字节帧、单线程、稀疏消费」这一组成立，换帧长或换消费方式都要重测。条件换了还照用，那个倍数就不是你这组负载的结论。
:::

### 12.7.1 实验设置：一份缓冲，两条解析路径

入口文件是 `bench/systems-lab/src/bin/views.rs`。它模拟高吞吐代理收到一批连续二进制帧时的解包过程。

夹具由 `encode_frames(4096, 1024)` 生成：每帧是「4 字节小端长度头 + 1024 字节载荷」，共 4096 帧。

合计 4096 × 1028 = 4 210 688 字节，即 4.02 MiB（按 1000 进制是 4.21 MB）。整块缓冲只分配一次，两条路径复用同一份字节。

| 被测模式 | 载荷怎么拿到 | 生命周期 | 每批分配次数 |
|:--|:--|:--|--:|
| `owned_copy` | `payload.to_vec()` 复制到新堆内存 | 不绑定输入缓冲区 | 4096 |
| `borrowed_view` | 直接返回 `&'a [u8]` 切片视图 | 绑定输入缓冲区 | 0 |

`owned_copy` 不是假想敌。它对应一种真实用法：把载荷交给生命周期比接收缓冲区更长的独立业务容器。

::: def 定义 12.7.1 · 拥有型复制流 owned copy stream {#def-12.7.1}

**拥有型复制流**指解析器每取出一帧，就把载荷复制进一块新的堆内存，此后由新对象负责释放。`payload.to_vec()` 是它的最小形态。它买到的只有独立存活期：切片视图靠级联把「缓冲区还活着」这个前提一路传给下游（[@def-12.4.2]）；拥有型对象则把这个前提换成一次分配。

:::

### 12.7.2 两条路径只差一次 `to_vec()`

两个分支共用 12.4.3 的 `next_frame`。差别只在载荷取到之后的下一步。

```rust
// bench/systems-lab/src/lib.rs
pub fn view_batch(bytes: &[u8], count: usize, copy: bool) -> u64 {
    let mut rest = bytes;
    let mut sum = 0;
    for _ in 0..count {
        let (payload, tail) = next_frame(rest, 4096).expect("valid generated frame");
        sum += if copy {
            let owned = black_box(payload.to_vec());
            consume_frame(black_box(&owned))
        } else {
            consume_frame(black_box(payload))
        };
        rest = tail;
    }
    assert!(rest.is_empty(), "unexpected trailing data");
    sum
}
```

`black_box` 在这里出现两次，各有分工：一处挡住载荷被优化掉，一处挡住拷贝被优化掉。缺了任何一处，被测对象就换成了别的东西，量出来的也就不是原来那两条路径。

`consume_frame` 标了 `#[inline(never)]`，内部按 `step_by(64)` 累加校验和。这就是下文的稀疏消费。

::: def 定义 12.7.2 · 稀疏消费 sparse consumption {#def-12.7.2}

**稀疏消费**指只取载荷的一部分字节算校验和。本实验每 64 字节读 1 字节，1024 字节的帧只碰 16 个字节。它不为省时间，而是把「读多少字节」从被测变量里摘出去，让分配与拷贝成为主项（[@def-12.7.2]）。代价是这个数字回答不了完整校验和的吞吐。

:::

驱动只做三件事：先用借用版算一遍基准，再让两种模式各跑 21 批，每批之后断言校验和一致。

```rust
// bench/systems-lab/src/bin/views.rs
use std::hint::black_box;

fn main() {
    const COUNT: usize = 4096;
    let bytes = systems_lab::encode_frames(COUNT, 1024);
    let expected = systems_lab::view_batch(&bytes, COUNT, false);
    systems_lab::measure(&["owned_copy", "borrowed_view"], COUNT, |case| {
        let sum = systems_lab::view_batch(black_box(&bytes), COUNT, case == 0);
        assert_eq!(sum, expected);
        sum
    });
}
```

`measure` 先交替预热 500 ms，再按 `(round + offset) % 2` 轮换两种模式的执行顺序。轮换让时间漂移落在两种模式上，而不是只压在一种上。

`view_batch` 末尾的 `assert!(rest.is_empty())` 保证 4096 帧正好走完。夹具是确定性的：同样的输入，任何一轮的校验和都必须相等。校验和对不上，说明被测对象已经换了，这一批数字就不能要。

### 12.7.3 一次 `to_vec()` 在分配器里做了什么

`to_vec()` 申请的是 1024 字节。这个尺寸在分配器里走一条固定路径，四步：

1. **定尺寸类**：按申请长度算出大小类别，再到线程私有缓存里找可用块；
2. **初始化簿记**：写块头元数据，多线程下还要维护脏页计数；
3. **搬字节**：调 `memcpy`，把 1024 字节从源缓冲搬到新块；
4. **即时释放**：`owned` 出作用域时执行 `free`，块被插回空闲链表；连续释放还可能触发缓存清洗或退页。

一批 4096 帧，就是 4096 次分配与 4096 次释放。借用版在同一批里严格为 0 次。这个 0 不是采样精度造成的巧合，它是借用类型的性质：视图只填寄存器里的一对指针与长度。这个差值是本节的主线。

::: ex 例 12.7.1 · 30.64 与 8.51 之间那 22 纳秒花在哪 {#ex-12.7.1}

两个批均值相差 30.635765 − 8.510533 = 22.125232 ns/帧。请回答：

1. 这 22.1 ns 能不能全部记在 `memcpy` 头上？
2. 帧长从 1024 字节缩到 16 字节，差值会变成多少？
3. 把 `consume_frame` 换成完整校验和，差值还是这么大吗？
4. 这个差值能不能用来推内存带宽？

::: sol 解答

1. 不能。它含分配、簿记、拷贝、释放四段。本节没有把四段拆开采集，只能把它读作「一次拥有化路径减一次借用路径」的整包差价（[@def-12.7.1]），不能分配给其中任何一段。
2. 本节没有采集 16 字节帧。能推断的只有方向：`memcpy` 那一段跟着字节数缩小，分配那一段基本不变；比例没有测，不写数字。
3. 会变小。消费端读得越多，两条路径的共同项越大，差值占均值的比例就下降。这一组同样没有采集（见 12.7.5）。
4. 不能。带宽要按每帧搬运字节数与耗时算，而这里的差值里混着分配器成本（[@def-12.7.2]）。

:::

:::

### 12.7.5 这个倍数在哪里失效

三件事都会改倍数，而这批记录只覆盖一组配置。

- **帧更小**：每帧固定开销的占比上升，倍数会变。本节没有采集。
- **帧更大**：`memcpy` 的占比上升，倍数会变。本节没有采集。
- **消费更密**：两条路径的共同项变大，差值占均值的比例下降。本节没有采集。

多线程下分配器还要处理争用，`owned_copy` 的代价会被放大。本节是单线程，没有采集，这组倍数也就不能拿来谈多线程。

12.4.1 提过拥有型与借用型在攻击面上的差别：一个恶意长度头能让 `to_vec()` 真的去申请声称的内存。本节只测了耗时与分配次数，攻击面没有量化采集。

::: method 判定流程 · 载荷该复制还是该借

1. 这块载荷会被放进生命周期比输入缓冲区更长的结构吗？会，走拥有化；不会，走切片视图（[@def-12.4.1]）。
2. 拥有化时，分配发生在每帧还是每批？每帧，就先把分配账单算出来。
3. 借用时，消费端每次读多少字节？读得越少，本节的倍数越好看，越不能直接搬用。
4. 帧长与并发度与本节一致吗？不一致就重测：条件换了还照抄 3.60，那个数字说的就不是你这组负载。
5. 有没有不可信的长度头？有就先补 `limit` 防线（12.4.3），它不属于性能判断。

:::

::: think 思考 · 校验和相等，能证明两条路径读的是同一份数据吗 {#think-12.7.1}

驱动在每批之后断言 `sum` 与 `expected` 相等，两种模式复用同一块 `bytes`。有人把它当成「两条路径等价」的证据。按[@def-12.7.2]数一数这个数字覆盖了哪些字节。

::: sol 解答

覆盖得很窄：`consume_frame` 每 64 字节读 1 字节，1024 字节的帧只有 16 个字节进过校验和。这条断言挡得住夹具损坏（配合 `view_batch` 末尾的 `assert!(rest.is_empty())`，4096 帧必须正好走完）和整个被测对象被优化掉；挡不住没被触碰的字节——若两条路径在其余偏移上读到的不是同一份内容，表里的校验和仍然相等。要主张「同一份数据」，得逐帧比对整段字节；本节的夹具没有采这一项，它承诺的只是「两条路径读到同样的 16 个字节」。
:::

:::

### 12.7.6 小结与常见错误

**小结。**① 两条路径只差一次 `to_vec()`，差出的是一整套分配与释放（[@def-12.7.1]）；② 稀疏消费把读取压小，让分配成为主项，同时限定了数字的适用范围（[@def-12.7.2]）；③ 21 批均值 30.635765 对 8.510533，比值 3.60，逐批在 3.31 到 3.72 之间没有反转（[@def-12.7.3]）；④ 换帧长、换消费密度、换并发度都要重测。下一节 [12.8 异步 I/O 与 io_uring 的所有权演变](#sec-cpp-rust.3.12.8) 把同一个问题推到内核边界：缓冲区借出去之后，谁保证它没被释放。

::: errata 常见错误清单（12.7 节）

E-a **把 3.60 倍当成 `to_vec()` 的通用价格。** 先查帧长与消费方式，本节的消费者每帧只读 16 字节（[@def-12.7.2]）。

E-b **拿 30.635765 当「复制 1024 字节的耗时」。** 它含分配、簿记、释放与夹具；先查本节有没有把四段拆开（没有）。

E-d **把 21 个数的 p99 当生产 p99。** `ceil(21 × 0.99) = 21`，它就是最大值（[@def-12.7.3]）。

E-e **删掉 `black_box` 再比。** 拷贝与消费都可能被优化掉；先查代码生成，再谈倍数。

E-f **在稀疏消费的夹具上谈带宽。** 每帧只读 16 字节，回答不了完整校验和的吞吐（[@ex-12.7.1]）。

## 12.8 异步I/O与Linux io_uring的所有权演变 {#sec-cpp-rust.3.12.8}

本节回答一个问题：**一个在 C 里顺手到不用想的接口，为什么到了 Rust 里必须先改签名？**因为通知模型变了：`epoll` 只说「可以读了」，`io_uring` 直接接管你的缓冲区指针。交接时点从「读的那一刻」提前到「提交的那一刻」，取消的安全性就跟着变了。

::: preview 先抓住一件事

判据只有一条：**指针交给内核之后，用户态还能不能提前释放这块内存**。就绪型能，因为内核只在 `read()` 期间碰它；完成型不能，因为提交之后内核随时会用它。Rust 的解法不是加锁，而是把所有权随请求移入、随完成移出（[@def-12.8.4]）。本节讲机制，没有采集 io_uring 的任何延迟或吞吐数字。
:::

### 12.8.1 就绪通知与完成通知

`epoll` 自 Linux 2.6 进入主线，Reactor 模式主导服务端网络编程近二十年。它有三处结构性开销。

1. 就绪与 I/O 分离：`epoll_wait` 只说某个描述符可读，真正的 `read()` 要另发一次系统调用。系统调用就是用户程序请内核代做一步操作。于是每个事件至少两次用户态与内核态往返。
2. 缓冲区拷贝：`read(fd, buf, len)` 要把数据从网卡或页缓存（内核替文件与设备保管的那份内存副本）复制到用户态。这份副本由内核保管，用户态要拿到字节就得再搬一次。搬运落在用户态，端到端零拷贝就做不到。
3. 普通文件永远「就绪」：磁盘文件在 Linux 下被视为随时可读，文件 I/O 无法在 `epoll` 里等。把文件读硬塞进 `epoll` 也不能让它变成异步，异步框架只好把它扔进线程池，例如 Tokio 的 `spawn_blocking`。

::: def 定义 12.8.1 · 就绪通知与完成通知 readiness / completion notification {#def-12.8.1}

**就绪通知**指内核只报告「这个描述符现在可以读写了」，数据搬运仍由用户发起；**完成通知**指用户先提交一个带缓冲区的请求，内核搬完再报告「做完了」。前者把搬运留在 `read()` 里，后者把搬运接进内核（[@def-12.8.1]）。模型一变，缓冲区的归属期就从一次调用拉长到一次提交。

:::

### 12.8.2 两个共享环：SQ 与 CQ

`io_uring` 由 Jens Axboe 设计。它的核心是一对位于共享内存映射中的无锁环形队列。

```text
       [ 用户空间 (User Space) ]                       [ 内核空间 (Kernel Space) ]
                   │                                               │
                   ▼                                               ▼
         ┌───────────────────────────────────────────────────────────────────┐
         │             共享内存映射区 (mmap: IORING_OFF_SQ_RING)            │
         │  提交队列 (Submission Queue, SQ): 用户写入 SQE，推进 tail 指针    │
         └───────────────────────────────────────────────────────────────────┘
                                           │
                                           ▼ (无锁轮询内核线程或单次 io_uring_enter)
         ┌───────────────────────────────────────────────────────────────────┐
         │             共享内存映射区 (mmap: IORING_OFF_CQ_RING)            │
         │  完成队列 (Completion Queue, CQ): 内核写入 CQE，推进 tail 指针    │
         └───────────────────────────────────────────────────────────────────┘
                   ▲                                               ▲
                   │                                               │
         [ 用户读取 CQE 确认完成 ]                      [ 硬件/网络中断驱动处理 ]
```

两个环各管一个方向。用户把 SQE 写进 SQ 并原子递增 tail；内核完成硬件操作后把 CQE 推进 CQ，用户直接读。

::: def 定义 12.8.2 · 提交队列与完成队列 submission / completion queue {#def-12.8.2}

**提交队列（SQ）**放用户写的请求描述符（SQE）；**完成队列（CQ）**放内核写的结果（CQE）。两个环都通过 `mmap` 映射进用户地址空间，两侧只读写 tail 与环掩码，所以「把请求交给内核」这一步本身不用再搬一次数据（[@def-12.8.2]）。

:::

环里装的东西很少，SQE 与 CQE 的字段就是全部契约：

```c
// 提交队列条目 (SQE, 64 字节对齐)
struct io_uring_sqe {
    __u8   opcode;         // 操作码：IORING_OP_READV, IORING_OP_WRITE, IORING_OP_SEND ...
    __u8   flags;          // 标志：IOSQE_FIXED_FILE, IOSQE_ASYNC ...
    __u16  ioprio;         // I/O 优先级
    __s32  fd;             // 目标文件描述符
    union {
        __u64  off;        // 文件偏移量
        __u64  addr2;
    };
    union {
        __u64  addr;       // 用户态缓冲区指针 (传递给内核 DMA)
        __u64  splice_off_in;
    };
    __u32  len;            // 缓冲区字节长度
    ...
    __u64  user_data;      // 用户态标识符 (通常编码为 Future 或 Waker 的裸指针)
};

// 完成队列条目 (CQE, 16 字节)
struct io_uring_cqe {
    __u64  user_data;      // 原样回传 SQE 中指定的标识符
    __s32  res;            // 操作结果：>= 0 表示读写字节数，< 0 表示 -errno
    __u32  flags;          // 完成标志位
};
```

推进 tail 只占一行：

```c
// 伪代码：在用户空间无锁推进 SQ
unsigned tail = *sq_ring.tail;
unsigned index = tail & *sq_ring.ring_mask;
sqes[index] = new_sqe;
__atomic_store_n(sq_ring.tail, tail + 1, __ATOMIC_RELEASE);
```

`ring_mask` 把自增的 tail 折回环内下标。`__ATOMIC_RELEASE` 保证 SQE 先写完、tail 后可见；少了这道序，内核可能读到半条请求。这不是快一点慢一点的效率问题，是请求内容是否完整可见的正确性问题。

`user_data` 是上述结构里最关键的一格。提交时写什么，完成时原样拿回来，正好用来认领「这是谁的请求」。多数运行时把它编码成 Future 或 Waker 的地址。

### 12.8.3 固定缓冲区与零系统调用

要让内核直接写你的内存，前提是这块内存不挪窝。前提一旦不成立，内核写的就不是你以为的那块内存。

::: def 定义 12.8.3 · 固定缓冲区 registered buffer {#def-12.8.3}

应用通过 `io_uring_register` 把一块内存提前交给内核。内核钉住这些页并记住物理地址，网卡可以按 DMA 直接写入，内核态与用户态之间的搬运就省掉了（[@def-12.8.3]）。代价同样明确：注销之前，这块内存不能移动，也不能提前释放。

:::

开启 `IORING_SETUP_SQPOLL` 后，内核会为该环起一个专属线程，形如 `iou-sqp-<pid>`。它在绑定的核心上忙轮询 SQ。

用户写完 SQE 并更新 tail，内核线程就能看到请求，提交不再需要 `io_uring_enter`。这就是「零系统调用」的全部含义。

空闲超时由 `sq_thread_idle` 控制，常见取值 1000 毫秒。超时后线程休眠省电；再提交就要显式唤醒：`io_uring_enter(fd, 0, 0, IORING_ENTER_SQ_WAKEUP, NULL)`。省掉的那次调用不是消失了，它只是推迟到下一次提交。

于是高吞吐时吃到红利，突发低频时退化成一次唤醒调用。这份红利不是常在的，它跟着请求密度走。低延迟服务还会把该线程绑到隔离核心（`sq_thread_cpu`），并给实时优先级（`SCHED_FIFO`）。代价是一个常驻忙轮询线程。

这些机制实际省下多少 CPU、多少延迟，本节没有采集。

### 12.8.4 借用型 AsyncRead 在完成型接口下失效

`tokio::io::AsyncRead` 的签名采用短期借用：

```rust
fn poll_read(self: Pin<&mut Self>, cx: &mut Context<'_>, buf: &mut ReadBuf<'_>) -> Poll<io::Result<()>>;
```

`buf` 的有效期只覆盖这次 `poll_read`。在 `epoll` 模型下这没问题：内核只在 `read()` 里碰它，Future 被 `tokio::select!` 取消时，借用随栈帧一起结束。

`io_uring` 下同一段代码不成立。缓冲区指针在提交 SQE 的那一刻就交给了内核。这里的毛病不是 Rust 语法太讲究，而是交接时点被提前了。

::: ex 例 12.8.1 · 取消之后谁还在写这块内存 {#ex-12.8.1}

一个读请求已经提交进 SQ，内核正在等网卡。此时 `tokio::select!` 的超时分支先完成，持有 `buf` 的 Future 被 `drop`。按借用型签名，`buf` 立刻回收。请回答：

1. 内核此刻知道这个 Future 已经被销毁吗？
2. `buf` 所在的内存被另一个对象复用之后，DMA 还会往哪里写？
3. 把 `buf` 换成 `Vec` 装字节、按值传进请求，问题就消失了吗？

::: sol 解答

1. 不知道。SQE 里只有地址、长度与 `user_data`，没有任何字段能撤回已经下发的硬件操作（[@def-12.8.2]）。
2. 仍然写原地址。网卡按提交时拿到的地址写入，落到别人的对象上。这是 DMA 版的释放后使用：编译器看不见，运行时也不报错（[@def-12.8.1]）。
3. 消失的只是「提前释放」这一种。所有权移进请求后，`drop` 只销毁请求对象，缓冲区被送进泄漏池，等对应 CQE 返回才真正释放（[@def-12.8.4]）。这不是免费的安全：泄漏池必须在完成路径上被收割，否则就变成内存泄漏。

:::

:::

### 12.8.5 拥有型缓冲区：签名怎么改

现代生态（`monoio`、`glommio` 等）把异步 I/O 的签名整个换掉了，动作有三个。

- **交出所有权**：不再传 `&mut [u8]`，而是把 `Vec` 或专门的堆内存凭据按值传进去；
- **完成时归还**：返回值从长度变成一个元组，长度和缓冲区一起交回；
- **防止提前释放**：缓冲区对象内部持有引用计数或泄漏守卫，在对应 CQE 归来前不把内存还给分配器。

::: def 定义 12.8.4 · 拥有型 I/O 缓冲区 owned I/O buffer {#def-12.8.4}

**拥有型 I/O 缓冲区**指所有权在提交时移入 I/O 操作、在完成时随结果移出的缓冲区。等待期间发起方手上没有它，也就无法提前释放（[@def-12.8.4]）。它与 [@def-12.7.1] 的拥有型复制流方向相反：那边复制是为了脱离生命周期，这边移交是为了让内核能安全地一直用。

:::

抽象只有两个 trait 与一个方法：

```rust
// 基于完成型异步 I/O 的抽象核心范式
pub trait IoBuf: 'static {
    fn stable_ptr(&self) -> *const u8;
    fn bytes_total(&self) -> usize;
}

pub trait IoBufMut: 'static {
    fn stable_mut_ptr(&mut self) -> *mut u8;
    fn bytes_capacity(&self) -> usize;
}

// 异步接口签名：所有权移入，完成时元组归还
pub trait AsyncUringRead {
    async fn read_owned<B: IoBufMut>(&self, buf: B) -> (std::io::Result<usize>, B);
}
```

`read_owned` 把契约写死在签名里：`buf` 按值传入，返回元组再把所有权还回来。等待期间用户拿不到它，编译期就守住了「不许释放」。

一个最小实现把 `Drop` 也接上：

```rust
// 保证在 DMA 传输期间内存绝对稳定的拥有型 Buffer 抽象
pub unsafe trait StableBuf: 'static {
    fn as_ptr(&self) -> *const u8;
    fn len(&self) -> usize;
}

pub unsafe trait StableBufMut: 'static {
    fn as_mut_ptr(&mut self) -> *mut u8;
    fn capacity(&self) -> usize;
}

// 严禁将借用引用放入该 Future！必须强制移交所有权
pub struct UringReadFuture<B: StableBufMut> {
    buffer: Option<B>,
    ticket: u64,
}

impl<B: StableBufMut> std::future::Future for UringReadFuture<B> {
    type Output = (std::io::Result<usize>, B);

    fn poll(mut self: std::pin::Pin<&mut Self>, cx: &mut std::task::Context<'_>) -> std::task::Poll<Self::Output> {
        // 1. 检查共享完成队列 (CQ) 中是否存在匹配 ticket 的 CQE
        if let Some(res) = check_cqe_completion(self.ticket) {
            let buf = self.buffer.take().expect("buffer must be present on completion");
            let result = if res >= 0 {
                Ok(res as usize)
            } else {
                Err(std::io::Error::from_raw_os_error(-res))
            };
            return std::task::Poll::Ready((result, buf));
        }

        // 2. 注册当前任务的 Waker，等待内核硬件中断或轮询唤醒
        register_uring_waker(self.ticket, cx.waker().clone());
        std::task::Poll::Pending
    }
}

impl<B: StableBufMut> Drop for UringReadFuture<B> {
    fn drop(&mut self) {
        if let Some(buf) = self.buffer.take() {
            // 【核心防线】：如果 Future 在内核完成前被强行 drop！
            // 绝不能直接释放该 buffer！必须将其泄漏至全局泄漏池，
            // 直到对应的内核 CQE 最终返回后再物理释放，彻底杜绝 UAF DMA 覆写！
            leak_until_cqe(self.ticket, Box::new(buf));
        }
    }
}

// 辅助占位函数：模拟全局 CQE 检查与泄漏池管理
fn check_cqe_completion(_ticket: u64) -> Option<i32> { None }
fn register_uring_waker(_ticket: u64, _waker: std::task::Waker) {}
fn leak_until_cqe(_ticket: u64, _leaked: Box<dyn std::any::Any>) {}
```

`poll` 只做两件事：查到匹配的 CQE 就把缓冲区交还，查不到就注册 Waker。真正兜底的是 `Drop`：Future 被提前销毁时，缓冲区不能就地释放。

::: think 思考 · 把缓冲区漏掉算不算修复 {#think-12.8.1}

`Drop` 里调 `leak_until_cqe` 之后，悬空写确实没有了。这算内存安全的修复，还是把问题改了个名字？

::: sol 解答

算半个。它保住了「内核写的那块内存仍属于这次请求」，代价是释放推迟到 CQE 返回之后。若 CQE 永远不返回，例如环坏了、fd 关了、进程要退出，这块内存就真漏了。所以正式实现不让业务代码自己写这个 `Drop`：泄漏池、CQE 收割与超时都是运行时的职责（[@def-12.8.4]）。类型系统负责「不许提前释放」，运行时负责「最终一定释放」，两件事缺一不可。

:::

:::

### 12.8.6 平台引擎横向对照

四个平台的差别集中在两列：谁发起搬运，以及缓冲区要活多久。

| 操作系统机制 | 交互架构模型 | 是否支持用户态提交零系统调用 | 内存缓冲区生命周期约束 | 磁盘异步 I/O 原生支持 |
|:--|:--|:--|:--|:--|
| **Linux `epoll`** | Reactor (就绪通知) | 否（每次事件需至少 2 次系统调用） | 短期借用 `&mut [u8]` 即可，取消安全 | 差（需降级至线程池模拟） |
| **Linux `io_uring`** | Proactor (完成通知) | **是**（`IORING_SETUP_SQPOLL` 共享环） | **严格拥有型**（DMA 期间所有权交托内核） | **极佳**（原生支持直接异步磁盘 I/O） |
| **macOS `kqueue`** | Reactor (就绪通知) | 否（依赖 `kevent` 系统调用往返） | 短期借用即可，生命周期易于绑定 | 差（对磁盘无真正异步完成环） |
| **Windows `IOCP`** | Proactor (完成端口) | 否（需 `WSARecv` / `GetQueuedCompletionStatus`）| 必须保证 `OVERLAPPED` 缓冲区持续存活 | 良好（原生统一网络与文件完成端口） |

macOS 上不存在原生共享内存环。Darwin 给的是 `kqueue`，一个就绪型接口。在这台机器上找完成型环是找不到的，架构也不能建立在这个假设上。

所以 Tokio 在 macOS 上用 `mio` 包一层 `kqueue`，在 Linux 上才引入基于完成型缓冲区的 `io_uring` 驱动。把 Linux 内核特性当成全平台架构，是移植阶段最常见的错误。

两列的关系也可以反过来读：凡是「缓冲区必须持续存活」的格子，都要求接口把所有权写进签名；凡是「短期借用即可」的格子，借用型签名就能正常工作。

::: method 判定流程 · 这个 I/O 接口能不能安全取消

1. 提交之后，内核还持有用户缓冲区指针吗？持有，就不能靠借用，只能走拥有型（[@def-12.8.1]）。
2. 取消路径上，谁能阻止这块内存被复用？只有持有所有权的对象。
3. 完成之后谁收割 CQE、谁归还缓冲区？没有收割者就会漏（[@def-12.8.4]）。
4. 目标平台有完成型环吗？没有就退回就绪型加线程池；硬套 `io_uring` 等于把这里不能用的机制当成已有能力。
5. 有没有实测支持「零系统调用」的收益？本节没有采集。机制讲得再顺，也不能替一个没采集的数字。

:::

### 12.8.7 一次「写」的开销在哪个时刻才真正发生

**本节回答一个问题**：同样一句 `write`，为什么有时测出几十纳秒、有时测出几十微秒？

::: preview 先抓住一件事

**「写完了」在这条链上有三个不同时刻**：数据离开用户态缓冲、数据进入内核的页缓存、设备确认收到。三者的成本差三个数量级，而大多数测量把计时边界画在第一或第二个时刻，却按第三个时刻去解释结果。要谈 I/O 性能，先说清你在说哪一个时刻。

:::

::: def 定义 12.8.5 · 写回与崩溃点 writeback and durability point {#def-12.8.5}

**写回**（延迟写，write-back）指写请求只更新内核里的页缓存（内核替文件与设备保管的那份内存副本）并把该页标成脏，真正的设备写入推迟到后台回写或显式同步时发生。与之相对的是**直写**（write-through），每笔写都等到设备确认。

**崩溃点**就是这条链上最后一个「掉电之后仍然成立」的时刻：在 Linux 侧，它由 `fsync`/`fdatasync`（把该文件的脏页与必要元数据推到设备）或挂载与设备的更弱保证决定；在文件系统内部还有一层自己的块缓存，脏块要等淘汰或显式回写才下去（rCore 的 easy-fs 把这一层写成最小可运行版本：`BlockCache` 内含 `BLOCK_SZ = 512` 字节的缓冲、块号、设备引用与 `modified` 脏标记，外面有一个全局块缓存管理器，尽量把块操作合并、只在必要时机发起真正的磁盘读写；它还特别提醒**扇区与块是两个概念**——扇区通常 512 字节，ext4 的块默认 4096 字节，easy-fs 里两者恰好都取 512 才不再区分）。
:::

::: def 定义 12.8.6 · 绕过页缓存 bypassing the page cache {#def-12.8.6}

三条常见路径各有代价：**`O_DIRECT`** 让 I/O 直接对用户态缓冲与设备生效，绕开页缓存，代价是必须满足对齐要求（地址、长度、偏移通常按逻辑块对齐），且没有缓存就没有「第二次读命中」这种便宜；**`posix_fadvise`/`drop_caches`** 只改变缓存策略或测试条件，不改变崩溃点；**`msync`/`fsync`** 不减少搬运，只是把已经欠下的写回提前结清。测出「加了 `fsync` 之后慢了很多」不是发现，而是承认之前测的不是同一件事。
:::

::: ex 例 12.8.2 · 三种计时边界各测到什么 {#ex-12.8.2}

同一段代码循环写固定大小的记录，三种配置：① 只 `write`；② 每笔 `write` 后 `fsync`；③ 每 N 笔才 `fsync` 一次。请说明各自测到的是什么，以及为什么 ③ 的每笔均值不能简单当成 ① 与 ② 的中点。

::: sol 解答

① 测的是「把字节交给内核」：一次系统调用加一次内存拷贝，量级接近一次 memcpy，**不含设备写入**。② 测的是「一次完整的持久化」：包含设备确认与文件系统内部的元数据写回，通常比 ① 贵两个数量级以上（这里给的是机制与量级关系，**本书没有在本机采集这组对照**）。③ 的每笔均值是「① 的成本 + 每 N 笔一次 ② 的成本摊薄」，它不是 ①② 的中点，而是**锯齿形**：第 N 笔那一次特别贵，其余很便宜。用批均值报告 ③ 时必须同时说明 N 和分布——一个漂亮的平均值可能藏着一半请求都在等同步（[@def-1.2.2]）。

工程含义：如果你的负载是「批量写 + 偶发同步」，那么 ③ 才是被测对象，而它的尾延迟由同步点决定，与平均吞吐无关（[@def-1.5.2]）。

:::
:::

::: think 思考 · 你的计时边界里有几次「等」

把一次写拆成可指认的几步：系统调用陷入内核、把数据拷进页缓存、文件系统分配块与更新元数据、脏页回写、设备确认。前两步每笔都付，后三步的时机由内核与设备决定。所以「写变慢了」至少有三种原因：拷贝变多（数据量变了）、元数据操作变多（文件系统要改的东西变了）、回写被推迟到关键路径上（时机变了）。**这三种的修法完全不同**，而批均值一个数就把它们搅在一起。

:::

::: method 判定流程 · 报告任何写性能之前

1. 写明崩溃点：这笔写测到「交给内核」为止，还是「设备确认」为止？用了 `fsync`/`O_DIRECT` 吗？
2. 写明同步频率与摊薄方式：每笔一次、每 N 笔一次，还是交给后台回写？
3. 对齐与缓存命中要单独说：`O_DIRECT` 的对齐失败会退化成什么路径？
4. 尾延迟与均值分开报：同步点造成的长尾不能被均值掩盖。
5. 没有采就不写：换一台机器、换一个文件系统（APFS、ext4、F2FS 的回写策略不同），量级关系可能保持，绝对值一定变。

:::

### 12.8.8 小结与常见错误

**小结。**① 就绪型只借一次调用，完成型借到提交结束（[@def-12.8.1]）；② SQ 与 CQ 让请求和结果都走共享环，`user_data` 负责把 CQE 认回请求（[@def-12.8.2]）；③ 固定缓冲区省掉内核与用户态之间的搬运，代价是这块内存不能动（[@def-12.8.3]）；④ 借用型 `AsyncRead` 在完成型下不健全，解法是拥有型缓冲区（[@def-12.8.4]）；⑤ 平台没有完成型环时，退回就绪型加线程池。

::: errata 常见错误清单（12.8 节）

E-a **把 `AsyncRead` 直接接到 `io_uring` 上。** 借用只覆盖一次 `poll`，完成型会把它拉长到一次提交；先查取消路径上谁持有缓冲区（[@def-12.8.1]）。

E-b **以为 `Drop` 一定发生在最后一个使用者之后。** 内核不是 Rust 的使用者，它不看析构函数；先查有没有泄漏守卫（[@def-12.8.4]）。

E-c **把 `user_data` 当可选调试字段。** 它是 CQE 认回请求的唯一凭据；先查多请求并发时怎么解码（[@def-12.8.2]）。

E-d **在 macOS 上找 `io_uring`。** Darwin 只有 `kqueue`，完成型环不存在；先查目标平台，再谈架构。

E-e **把 SQPOLL 当默认配置。** 它常驻一个忙轮询线程，空闲时靠 `sq_thread_idle` 休眠；先查 CPU 预算。

E-f **拿「零系统调用」当吞吐结论。** 本节没有采集提交延迟或吞吐；先查有没有实测数字。

:::

::: method 即时自测 · 12.8

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　就绪通知与完成通知的区别，一句话说清。

::: sol 第 1 题答案
就绪通知只报告「可以读写了」，搬运由用户调 `read()` 发起；完成通知由用户先提交带缓冲区的请求，内核搬完再报告（[@def-12.8.1]）。
:::

**第 2 题 · 辨析**　「把缓冲区改成按值传进去，就一定安全了吗？」

::: sol 第 2 题答案
不一定。按值传只挡住「提前释放」这一种；若 `Drop` 里没有泄漏守卫，Future 被取消时缓冲区照样被释放，DMA 仍会写脏内存。安全依赖「所有权移入 + 完成时移出 + 泄漏池收割」三件事同时成立（[@def-12.8.4]）。
:::

**第 3 题 · 应用**　一个 4 KB 读请求要跑在 macOS 上，还想沿用拥有型缓冲区的接口，怎么做？

::: sol 第 3 题答案
保留接口形状，底层换成 `kqueue`：缓冲区借用即可，但把它包装成同样的「移入—归还」签名，让上层的取消语义与平台无关。代价是多一次搬运，收益要自己测，本节没有采集这类跨平台数据（[@def-12.8.1]）。
:::

**第 4 题 · 迁移**　删掉 `UringReadFuture` 的 `Drop`，哪一类 bug 会回来？

::: sol 第 4 题答案
DMA 版的释放后使用。Future 被取消后缓冲区立即回收，内核仍按旧地址写入，破坏别的对象。编译器看不到这条路径，因为它发生在内核而不是 Rust 代码里（[@ex-12.8.1]）。
:::

:::

## 12.10 常见错误索引 {#sec-cpp-rust.3.12.10}

这是本章的跨节错误索引：每一节末尾都有自己的「::: errata 常见错误清单（12.M 节）」，按你阅读的顺序给出局部清单。下面这一份只收那些要读完整个章才浮出来的错误，它们在单节内部看不出问题，放进「源码到指令、再到所有权」的整条链才露馅。

**以为手写 SIMD 一定能超越编译器自动向量化。** 现代 LLVM 循环向量化器在无别名的连续数组上具备很强的展开与调度能力，本章实测里自动向量化与手写 NEON 处于同一性能量级（[@ex-12.6.1]）。先测再写。intrinsics 不是成熟度的象征，它只在编译器证不出的那一刻才轮到上场。

**在未做运行时探测时调用带 `#[target_feature]` 的函数。** 直接调用会在不支持该特性的旧处理器上触发 `SIGILL` 非法指令崩溃（[@def-12.3.2]）。声明特性只改变代码生成，不改变调用方的责任。

**在循环内部保留潜在的边界检查或 panic 分支。** 没有前置的等长断言，循环体里就会生成隐藏分支，向量化器因此拒绝介入（[@def-12.2.2]）。断言要写成编译器看得懂的形式，而不是一句注释。

**把传统的 `&mut [u8]` 借用缓冲区直接交给 `io_uring`。** 如果 Future 提前取消被丢弃，内核的 DMA 可能在内存释放之后继续写入，形成 UAF 覆写（[@ex-12.8.1]）。提交缓冲区的所有权必须撑到完成通知回来。

**误把浮点向量乘加当成满足结合律。** 浮点加法在数学上不满足结合律，未获 `fast-math` 一类授权时，编译器为保证 IEEE 754 精度会拒绝重排（[@def-12.2.3]）。授权是一次精度取舍的签字，不是性能开关。

**忽视数组尾部残余元素的清理。** 长度不能被向量位宽整除时，必须显式写标量清理循环（[@ex-12.3.1]）。少了这一段，尾巴不是少算就是越界。

**以为零拷贝切片可以脱离底层缓冲区存活。** `&'a [u8]` 严格受底层分配的生命周期约束，跨线程或脱离作用域传借用视图都会被借用检查器拒绝（[@def-12.4.1]）。零拷贝省的是复制，付的是生命周期。

**在密集计算里频繁做跨步访问。** 离散非连续访问会迫使向量单元走 gather/scatter 一类的低效路径，抵消 SIMD 的算力红利。数据布局要先按连续访问设计，再谈向量宽度。顺序反了，向量宽度就不能替布局补课。

**滥用 AVX-512 招来核心联动降频。** 部分 Intel 架构上，512 位宽的密集计算会让 CPU 自动下调频率，拖慢同核甚至邻近核心的标量线程。宽度是手段，整机能效才是结论。

**在零拷贝反序列化里忽略内存对齐。** 把未验证的 `&[u8]` 直接强转成 `&[T]`，在 ARM64 这类对齐敏感的架构上会触发硬件对齐异常或未定义行为（[@def-12.5.1]）。转换前先检查地址与长度。

**以为 `io_uring` 在任何场景都显著超越 `epoll`。** 连接数少、小包高频且已经吃满单核时，环形队列的同步常数不一定比成熟优化的 `epoll` 更有优势。选型要按负载形态测，不按宣传材料选。拿宣传材料做判断，选中的就不是你的负载。

**把「没有系统调用」等同于「没有内核开销」。** SQPOLL 的内核轮询线程同样占着一个物理核心，评估整机能效时必须把它算进去。省掉的是调用，不是 CPU 时间（[@def-12.8.2]）。

::: note 本章小结

- 向量通道每周期能发射的指令数有限，宽度只是墙的一部分（[@def-12.1.1]、[@ex-12.1.1]）。
- 自动向量化要求无循环携带依赖、且边界能被证明，一句前置断言往往决定它能否介入（[@def-12.2.2]、[@ex-12.2.1]）。
- fast-math 是精度授权，不是性能开关，重排浮点要你明确签字（[@def-12.2.3]）。
- `target_feature` 只改变代码生成，调用方仍要负责运行时探测（[@def-12.3.2]、[@ex-12.3.1]）。
- 借用视图把复制换成生命周期约束，缓冲区不能先于视图离开（[@def-12.4.1]、[@ex-12.4.1]）。
- ns/元素是批均值口径，加速比只是它的另一种写法（[@def-12.6.1]、[@def-12.6.4]）。
- io_uring 的缓冲区所有权要覆盖到完成通知，取消不等于内核停止写（[@def-12.8.4]、[@ex-12.8.1]）。

:::

### 出口检查

从 `cpp-rust/bench/systems-lab` 执行下面三条命令，核验标准差与分位数输出；换机器复跑时先对齐编译选项与目标特性，再比较数字。编译选项没对齐，两组数字就不是同一个量。

```bash
cargo test --offline --locked
target/release/simd
target/release/views
```

差异归因要能回答两个问题。第一，LLVM 自动向量化（0.069184ns）相对标量调用拿到 7.73 倍加速，为什么与手写 NEON（0.069965ns）的耗时几乎一样（[@ex-12.6.1]）。第二，`views` 的分帧解析里，借用型切片视图相对拥有型深拷贝实现的 72.2% 耗时下降从哪里来（[@ex-12.7.1]）。

汇编层面，你应能在生成文件里指出 `neon_transform` 如何用 `ldr q1, [x10], #16` 与 `mla.4s v2, v1, v0` 完成向量展开。

最后检查自己能否把范围说清：本章做的是 ARM64 向量化吞吐对比与借用切片零拷贝度量，`io_uring` 的所有权分析属于前沿架构讨论，本章没有在本机 macOS 上伪造 Linux 内核测试。
