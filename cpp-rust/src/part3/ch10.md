<div class="chapter-index">

## 10.1 进程边界究竟隔离什么 {#sec-cpp-rust.3.10.1}

本节回答一个问题：**把工作搬到另一个进程，到底买到了什么、没买到什么？**第9章说明已经开始执行、不配合取消的代码无法靠abort强行终止；直觉的下一步是「另开一个进程，不配合就杀掉」。这一节把「可以杀掉」拆清楚——它只是治理协议的一项，不是全部。谈进程成本之前先定对象，这是[@def-1.1.3]对每个测量提出的要求。

::: preview 先抓住一件事

进程买到的是独立虚拟地址空间和一个可直接终止的对象，买不到正确的协议、资源配额、权限限制与后代清理。本章后面几乎所有误用，都能追溯到把「隔离边界」当成「治理边界」来说。
:::

### 10.1.1 从阻塞池走到进程

第9章说明，已经开始执行的spawn_blocking闭包不能依靠abort强行终止。
如果业务必须结束不合作的第三方程序，独立进程提供了另一种控制边界。
父进程可以请求操作系统终止直接子进程。

::: def 定义 10.1.1 · 直接子进程与终止对象 direct child {#def-10.1.1}

**直接子进程**是父进程可以请求操作系统终止、并对其执行wait回收的那一层进程。本章helper治理的唯一对象就是它。孙进程不是直接子进程：它可能在直接子进程退出之后继续运行，还可能继续持有继承来的管道写端（[@def-10.2.1]）。进程边界的「可以杀掉」只覆盖直接子进程这一层。

:::

但「可以杀掉」只是治理协议的一部分。
还需要处理退出状态、输出残留、输入关闭、后代进程和资源配额。
这些责任不会因为使用Rust自动消失。

### 10.1.2 四种经常混淆的边界

线程共享同一进程虚拟地址空间。
进程通常具有独立的虚拟地址空间。
进程仍可以显式共享映射、文件、套接字和其他内核对象。
因此「进程之间绝不共享任何资源」也是错误的。

| 边界 | 解决的问题 | 本身不保证 |
|:--|:--|:--|
| Future任务 | 用户态进度与取消组织 | 强制中止同步函数 |
| 操作系统线程 | 独立栈与内核调度 | 地址空间隔离 |
| 独立进程 | 虚拟地址空间与直接终止对象 | 权限/网络/文件系统沙箱 |
| 受治理的进程树或容器 | 后代、配额、权限等策略 | 任意平台自动等价的安全性 |

::: def 定义 10.1.2 · 隔离边界与治理边界 {#def-10.1.2}

**隔离边界**回答「默认不共享什么」——地址空间、栈、终止对象；**治理边界**回答「其余部分由谁负责」——协议、配额、权限、后代。上表的前三行是隔离边界，第四行才进入治理边界。按[@def-10.1.1]，杀掉能力属于前三行；权限与文件系统策略属于第四行，两列之间没有自动蕴含关系。

:::

本章实现的是受信任helper的直接子进程管理。
没有接收任意互联网脚本并安全执行的能力。
也没有提供进程树的强制清除。
后续项目若面对不可信工具，必须增加真正的隔离策略。

### 10.1.3 Command不是shell字符串

实验使用明确的可执行文件路径与逐个参数。
没有通过`sh -c`拼接请求字段。

这消除了shell重新解释元字符这一层风险。
但不等于任意参数都对目标程序安全。
目标程序仍可能把参数理解为文件路径、选项或危险操作。

实际工具适配器还要规定：

- 可执行文件允许列表。
- 参数数量与长度。
- 工作目录与环境变量。
- 输入大小与编码。
- 输出上限与敏感信息处理。
- 权限、网络、文件访问策略。

这些策略与IPC吞吐测量不应混为一谈。
本轮helper只有固定的几个实验模式。

::: ex 例 10.1.1 · 这份设计评审缺了哪几句话 {#ex-10.1.1}

一份提案写着：「不可信插件放入独立子进程，用 `sh -c` 拼接请求字段执行命令行，五秒超时后 kill——这就是安全隔离。」指出这句话里至少三处混淆，并各补一条本节要求分开陈述的事实。

::: sol 解答

1. 「独立进程＝安全隔离」把[@def-10.1.2]的两列压成一列：地址空间分离不限制文件、网络、权限或后代，表格第三行的「本身不保证」列里就写着第四行的策略内容。
2. 「用 `sh -c` 拼接」把请求字段重新挂回shell元字符解释之下，放弃了10.1.3「明确路径＋逐个参数」的防线；即使改用Command，允许列表、参数数量与长度、工作目录与环境变量、输入输出上限这套策略也要一次补齐。
3. 「超时后kill＝完事」只走到[@def-10.1.1]的直接子进程层：kill之后还要wait回收、排空stdout/stderr，继承写端还可能让EOF迟到，那是10.2与10.7的协议。三处缺任何一处，「隔离」就退化为「不管」。

:::

:::

### 10.1.4 为什么不在Tokio运行后直接fork继续Rust代码

Stanford CS110L 的课程材料讨论过多线程 fork 的锁状态问题。但 `sources/web.json` 里这条断言只登记了课程主页（`stanford` 条目状态为 `fetched-not-reviewed`），盘上没有该讲义具体页的母本；10.9 点名的 `slides/lecture-10-2022.pdf` 也只留了 URL 与指纹、没有本地 PDF。故本节关于该课程的说法只作方向性转述，未逐字核对。

::: def 定义 10.1.3 · 多线程fork的锁状态继承 {#def-10.1.3}

fork后的子进程**只保留调用线程，却继承其他线程留下的内存锁状态**。如果某个分配器（向系统要内存、再把内存还回去的那层代码）内部锁在fork瞬间由非调用线程持有，子进程里就再没有人能释放它——锁位是物理带过去的，持有者却没有。这不是Rust借用检查器能够从类型层面消除的外部状态问题：库可以在背后创建线程，调用点没有显式`thread::spawn`，也不能推断整个进程是单线程。

:::

本轮Tokio1.54.0文档还明确限制fork后重用runtime。
其进程、信号等模块使用无法任意重置的进程全局状态。
即使在子进程里重新构造一个Runtime，也不能据此消除该限制。

因此实验通过Command启动独立可执行文件。
不手写多线程fork后继续运行分配、锁或runtime代码的危险路径。
Command底层选择什么平台启动机制，属于平台实现细节。
本章不把它固定叫作一次fork系统调用（用户程序停下来请内核代做一步操作）。

::: note 课程建议与性能结论分开

Stanford材料说明为什么应优先使用更高层的进程启动抽象。
它没有提供本机Rust进程创建的纳秒数。
本章的启动成本来自实际执行，不从课程叙述推算。

:::

::: think 思考 · 「我们只fork一次，问题不会那么巧出现」 {#think-10.1.1}

有人承认[@def-10.1.3]存在，但认为自己的调用点附近只有单线程，中锁的概率可以忽略。这个论证漏了什么？

::: sol 解答

漏了「调用点附近」不等于「进程里」。分配器、日志、TLS运行时都可能在背后留有线程与锁；你能检查的只有源码可见的部分，锁状态却在整个进程地址空间里。而且fork的危险路径不会以崩溃形式立刻暴露——子进程只是卡住，最容易被当成「偶发调度问题」。论证成立的前提是「证明本进程单线程」，这在有第三方库的进程里给不出来；拿不到这个证明，就换Command启动独立可执行文件这条受支持的路径。

:::

:::

### 10.1.5 小结与常见错误

**小结。**① 进程买到独立地址空间与一个可直接终止的对象，协议、配额、权限与后代都要另外买（[@def-10.1.1]）；② 隔离边界与治理边界要按列分开读，不存在自动蕴含（[@def-10.1.2]、[@ex-10.1.1]）；③ 多线程fork后的锁状态与进程全局状态不在类型系统管辖内，所以本章只走Command启动独立可执行文件的路径（[@def-10.1.3]）；④ 课程建议提供方向，不提供本机纳秒数（note框）。下一节 [10.2 文件描述符、所有权与EOF](#sec-cpp-rust.3.10.2) 把「子进程退出」这一个事件拆成进程寿命与端点寿命两条线。

::: errata 常见错误清单（10.1 节）

E-a **把独立进程当安全沙箱。**地址空间分离不限制文件、网络、权限与后代（[@def-10.1.2]）。

E-b **由「进程隔离」推出「绝不共享任何资源」。**映射、文件、套接字都可以显式共享（10.1.2）。

E-c **把命令拼接当便利。**`sh -c` 重新打开元字符解释层；即便逐个参数，策略清单仍一项不能少（[@ex-10.1.1]）。

E-d **多线程fork后继续调用任意库。**分配器锁与进程全局状态在子进程里不可恢复（[@def-10.1.3]）。

E-e **以为子进程重建Runtime就解除了Tokio限制。**限制在进程全局状态，不在Runtime对象（10.1.4）。

E-f **把课程建议写成性能结论。**Stanford材料没有本机Rust进程创建的纳秒数（note框）。

:::

## 10.2 文件描述符、所有权与EOF {#sec-cpp-rust.3.10.2}

本节回答一个问题：**直接子进程已经退出，为什么读端还可能等不到EOF？**直觉把「进程结束了」当成「流结束了」；这一节把它拆成两条寿命——进程寿命与端点寿命。10.5的排空停滞、10.6的EOF核对、10.7的继承写端回归，全部建立在这条分界上。

::: preview 先抓住一件事

EOF能不能被观察到，取决于「这条管道的写端集合是否已经清空、缓冲是否读完」，不取决于某一个进程是否还活着。一个不写一个字节的后代，只靠「持有」就能拖延EOF。
:::

### 10.2.1 管道有内核缓冲，也有端点寿命

父进程持有ChildStdin，向子进程输入写数据。
父进程持有ChildStdout/ChildStderr，读取子进程输出。
子进程及其后代可能继承这些描述符的另一端。

::: def 定义 10.2.1 · EOF 观察条件 {#def-10.2.1}

EOF不是一个由「子进程退出」直接设置的业务布尔值。当相应管道**所有写端关闭，且已经缓冲的数据读完**，读者才能观察EOF。仍有写端被另一个进程持有时，直接子进程退出也未必带来EOF。这个定义把「子进程结束」拆成两条寿命：进程寿命以wait返回为终点；管道端点寿命以最后一个写端关闭为终点，两者由[@def-10.1.1]治理的对象并不重合。

:::

### 10.2.2 Rust所有权能帮到哪里

Child的stdin/stdout/stderr通常放在Option中。
`take()`把一个端点转交给对应的输入或排空任务。
父对象不再拥有该端点。
这有助于避免一段代码读管道，另一段代码又偷偷竞争读取。

但所有权移动不会关闭已复制到其他进程的描述符。
Drop本地对象也不会自动让远端所有继承者退出。
安全Rust可以精确管理本地句柄，不能替操作系统协议做全局推理。
按[@def-10.2.1]，Drop与`take()`只作用于父进程这一侧的「本地端点」；远端写端集合是否清空，不由本地借用检查决定。

### 10.2.3 stdin关闭是协议事件

持久worker按帧循环读输入。
父进程发送完请求后关闭自己的stdin写端。
worker在帧边界观察EOF，然后正常退出。

如果父进程只调用wait，却仍保存stdin写端，worker可能继续等下一帧。
父子双方就会互等。
实验Session::finish先关闭输入，再等待退出。

```rust
fn finish(mut self) -> std::io::Result<()> {
    drop(self.input.take());
    if self.child.wait()?.success() {
        Ok(())
    } else {
        Err(std::io::Error::other("worker exit failed"))
    }
}
```

完整定义在`src/bin/process_rpc.rs`。
这段代码适用于本章已知有限的helper协议。
它没有通用的不可信worker硬期限。
若helper无法按EOF退出，应使用有治理的异步子进程管理路径。

::: think 思考 · 顺序反过来写会怎样 {#think-10.2.1}

把`finish`改成先`self.child.wait()?`、后`drop(self.input.take())`，编译照样通过。对这个按帧循环的持久worker，运行时会发生什么？

::: sol 解答

父进程在wait上等worker退出；worker在stdin帧边界上等下一帧或EOF，而EOF要等「所有写端关闭」（[@def-10.2.1]）——写端之一正握在父进程手里。双方各等对方先动，形成互等，wait永远不返回。这个死锁不是内存安全问题，borrow checker不报错、编译期抓不到；它由协议双方的等待关系构成，只能像`Session::finish`那样把「先关输入、再等退出」写成固定顺序。10.5的先wait后读停滞是同一类等待回路在输出方向上的版本。

:::

:::

### 10.2.4 stdout不是日志与协议的共享垃圾桶

RPC worker把stdout专用于二进制握手和响应帧。
诊断应走stderr。
父进程必须明确是否继承、排空或禁止stderr。

向stdout多打印一行「worker started」，会破坏二进制帧边界。
这是协议错误，不是性能抖动。
把解析失败重试几次也不能恢复一个没有重同步规则的流。
帧边界被破坏之后，读到的每个「半个响应」都落入下一节[@ex-10.3.1]要逐条分类的截断情形——语义错了，重测多少次都不会变对，这与[@def-1.1.3]对测量对象的要求是同一件事。

### 10.2.5 端点关闭与错误传播

| 事件 | 应观察的事实 | 不能直接认定 |
|:--|:--|:--|
| 父进程关闭stdin | worker可能看到EOF | worker已处理完所有副作用 |
| stdout观察EOF | 此输出流无更多字节 | 退出状态一定为0 |
| wait返回状态 | 直接子进程已被等待 | stdout/stderr已读到EOF |
| 写入报BrokenPipe | 对端读端已不可用 | 请求一定未被执行 |
| 读到半个响应 | 帧不完整 | 整个请求完全没有副作用 |
| 任务被取消 | 本地Future被丢弃 | 外部进程自动停止 |

::: ex 例 10.2.1 · 三个观察各自能推到哪 {#ex-10.2.1}

对照上表判断三个场景（前两种本章有归档观察，第三种本章没有复现，只按协议表推断）：

1. wait返回退出码0，但stdout在读，EOF迟迟不来。
2. stdout已读到EOF，随后exit_code却是None。
3. 向stdin写请求时报BrokenPipe。

每个场景写出「应观察的事实」和「不能直接认定」的内容。

::: sol 解答

1. 观察到的事实只是「直接子进程已被等待」（[@def-10.1.1]）；EOF要等所有写端关闭（[@def-10.2.1]），后代的继承写端还开着——10.7的inherit回归复现的是这个形态。不能认定「输出已完整」。
2. EOF只说明「此输出流无更多字节」，不说明退出状态；exit_code为None在Unix上可能对应信号终止。两个观察各答各的问题，不能互推。
3. 事实是「对端读端已不可用」；不能认定「请求一定未被执行」——半个请求也可能已经送达并被处理了一部分。把BrokenPipe直接映射成「安全重试」，可能制造重复副作用，重试契约放在 10.8 节单独处理。

:::

:::

协议设计必须保留这些「不知道」。
把不确定失败映射成「安全重试」可能制造重复副作用。

### 10.2.6 小结与常见错误

**小结。**① EOF的条件是「所有写端关闭＋缓冲读完」，不是「某个进程退出」（[@def-10.2.1]）；② 所有权与Drop只管本地端点，管不到远端副本（10.2.2）；③ 关闭stdin是协议事件，顺序写反就构造出互等（[@think-10.2.1] 的场景）；④ stdout混日志是协议错误，不是性能抖动（10.2.4）；⑤ 六行观察表的三列结构——事实、可推出、不可推出——是后续所有排空与回收协议的最小语言（[@ex-10.2.1]）。下一节 [10.3 显式线协议、布局与短读短写](#sec-cpp-rust.3.10.3) 处理另一个方向的误会：把Rust内存布局当序列化格式。

::: errata 常见错误清单（10.2 节）

E-a **把EOF当成子进程退出自动设置的布尔值。**EOF由写端集合与缓冲读完共同决定（[@def-10.2.1]）。

E-b **读到stdout EOF就认定退出码为0。**两列观察分属不同问题（[@ex-10.2.1]）。

E-c **认为「不写字节的后代」无害。**只靠持有写端就能拖延所有读者的EOF（图10-1）。

E-d **只调wait不关stdin写端。**父子各等对方，形成互等（10.2.3）。

E-e **把日志与协议帧都写进stdout。**一行「worker started」就破坏帧边界（10.2.4）。

E-f **把BrokenPipe或半响应当成「没发生、可安全重试」。**未知失败必须保留「不知道」（[@ex-10.2.1]）。

:::

::: method 即时自测 · 10.2

**第 1 题 · 记忆**　[@def-10.2.1] 里，EOF的两个条件是什么？各由谁控制？

::: sol 第 1 题答案
所有写端关闭（由每一个持有写端的进程控制，包括后代）＋已缓冲数据读完（由读者推进）。父进程自己Drop只覆盖本地一份写端，这是10.2.2「所有权管不到远端」的原因。
:::

**第 2 题 · 辨析**　「wait(direct child) 返回了，所以这条管道的端点都处理完了。」错在哪？

::: sol 第 2 题答案
wait返回只说明直接子进程被回收（[@def-10.1.1]）；写端可能被后代继续持有，读端也可能还有缓冲数据未读。图10-1下排三个事件不对齐，说的就是进程寿命与端点寿命是两条线（[@def-10.2.1]）。
:::

**第 3 题 · 应用**　写一个持久worker的退出协议：父进程发完所有请求，希望worker正常收尾。给出必要顺序。

::: sol 第 3 题答案

## 10.3 显式线协议、布局与短读短写 {#sec-cpp-rust.3.10.3}

本节回答一个问题：**为什么线协议必须按字节定义，而不能「把结构体发过去」？**两个进程不共享Rust的类型系统——布局、填充、端序、版本都要跨界重新谈定。本实验的业务载荷只有两个`u64`，线协议却固定24字节；这一节说明多出来的字节买了什么。

::: preview 先抓住一件事

`repr(C)`转储送过去的不只是字段，还有填充、本机端序和「永远没有版本号」的默认语义。把线格式写成显式字节表之后，编码器只剩字节级操作，解码顺序本身就成了信任边界的第一道防线。
:::

### 10.3.1 原生结构体不是线格式

实验的业务值只有两个u64：request_id与value。
本机原生Frame实际size=16、align=8。
但线协议固定为24字节。
多出来的字节是版本、标志与帧长。

| 字节偏移 | 长度 | 字段 | 编码/约束 |
|--:|--:|:--|:--|
| 0 | 2 | version | little-endian，必须为1 |
| 2 | 2 | flags | 当前必须全部为0 |
| 4 | 4 | frame length | little-endian，必须为24 |
| 8 | 8 | request_id | little-endian u64 |
| 16 | 8 | value | little-endian u64 |

::: def 定义 10.3.1 · 线格式与内存布局 wire format {#def-10.3.1}

**内存布局**是编译器在当前进程内对结构体的安排：本机原生`Frame` size=16、align=8，没有版本字段，填充字节语义未定义。**线格式**是跨进程的显式契约：每个字节区间的字段、编码与约束逐项写死（上表）。两者的字段集合、顺序、宽度互相独立；这24字节协议多花的8字节，买到的是内存布局给不了的三样东西：版本、标志与帧长。

:::

这个协议没有使用repr(C)转储。
没有把结构体填充、地址、usize宽度或未初始化字节发给另一进程。
也没有依赖父子进程编译器版本完全一致才能解释字段。

### 10.3.2 编码器的完整核心

源文件：`src/wire.rs`。

```rust
pub fn encode(self) -> [u8; FRAME_LEN] {
    let mut bytes = [0u8; FRAME_LEN];
    bytes[0..2].copy_from_slice(&1u16.to_le_bytes());
    bytes[4..8].copy_from_slice(&(FRAME_LEN as u32).to_le_bytes());
    bytes[8..16].copy_from_slice(&self.request_id.to_le_bytes());
    bytes[16..24].copy_from_slice(&self.value.to_le_bytes());
    bytes
}
```

整个数组先初始化为零，所以flags也明确为零。
所有转换都是字节级操作。
不需要对齐转换，也不需要unsafe读取结构体内存。

### 10.3.3 解码顺序就是信任边界

接收到固定长度数组之后，先核对version、flags和length。
再解释id与value。
未知版本不「尽量兼容」地继续处理。

本轮测试逐一破坏三个头部位置，要求返回InvalidData。
另一个测试验证id的little-endian字节顺序。
这比仅在同一主机上encode再decode更强一点。
因为两个函数可能恰好以同样错误方式解释本机端序。
这个强度差别与第1章[@def-1.6.1]的要求同源：校验参照必须独立于被测实现，而不是同一对函数的自我循环。

### 10.3.4 EOF与截断必须区分

read可以返回比请求长度少的字节。
一次read没有读满，不等于对端违反协议。
管道提供的是字节流，不是24字节消息队列。

::: def 定义 10.3.2 · 短读、截断与干净EOF {#def-10.3.2}

**短读**：一次read返回的字节数少于请求数——管道字节流的正常形态，继续读即可，不构成协议违规。**干净EOF**：在帧边界上（一个字节都没有读到）read返回0——对端已按协议结束。**截断**：帧首字节已经拿到，之后中途EOF——必须报`UnexpectedEof`，不能假装正常关闭（[@def-10.2.1]的EOF条件在这里表现为「半帧残留」）。三种结果对应三个不同的协议事件，合并任何两个都会丢失诊断信息。

:::

本轮`read_frame`先尝试读取首字节：

- 一个字节都没有，且返回0：帧边界上的干净EOF。
- 已有首字节：后续必须read_exact剩下23字节。
- 中途EOF：UnexpectedEof，不是假装正常关闭。

```rust
pub fn read_frame(reader: &mut impl std::io::Read)
    -> std::io::Result<Option<Frame>>
{
    let mut bytes = [0; FRAME_LEN];
    loop {
        match reader.read(&mut bytes[..1]) {
            Ok(0) => return Ok(None),
            Ok(_) => break,
            Err(e) if e.kind() == std::io::ErrorKind::Interrupted => continue,
            Err(e) => return Err(e),
        }
    }
    reader.read_exact(&mut bytes[1..])?;
    Frame::decode(bytes).map(Some)
}
```

空流与单字节截断分别有可执行测试。
该函数针对同步字节流。
不能把它放进current-thread异步poll里等待不可信的慢输入。
本实验中它运行在独立helper或同步RPC测量进程。

::: ex 例 10.3.1 · 三次读取各判成什么事件 {#ex-10.3.1}

按[@def-10.3.2]把下面三个观察分类为短读、截断或干净EOF，并给出`read_frame`的返回值：

1. 第一次`read`只返回了7字节。
2. 读满24字节后`decode`发现version字段是2。
3. `read`先返回1字节，下一次返回0。

::: sol 解答

1. 短读。字节流本来就允许少于请求的返回量；继续读满或让`read_exact`推进即可，不构成协议违规。
2. 既不是短读也不是EOF，是头部校验失败：version必须为1（10.3.1表），`decode`返回InvalidData。未知版本不「尽量兼容」地继续处理（10.3.3）。
3. 截断。帧首字节已到手，剩下23字节中途EOF，`read_exact`给出`UnexpectedEof`；这与空流上的干净EOF（首字节就返回0、得到`Ok(None)`）是两个事件，合并上报会丢掉「对端在帧中间消失」这条关键信息（[@ex-10.2.1]的「读到半个响应」行）。

:::

:::

### 10.3.5 write_all与flush也要讲准确

write_all负责在可恢复短写时继续写完指定字节。
它不表示远端已经读到或处理完。
flush的作用取决于writer层是否有用户态缓冲。
本实验保留flush以使协议意图明确。

若把writer换成BufWriter，flush遗漏可能让请求停留在用户缓冲中。
如果直接写裸管道句柄，flush也不是跨进程确认消息。
真正完成确认来自读取并校验响应帧。

### 10.3.6 ABI/代码生成核验

| 项目 | 本轮证据 | 边界 |
|:--|:--|:--|
| Frame原生size/align | type-layout.txt：16/8 | 固定目标观测，不是线格式 |
| Frame线格式 | encode/decode与字节顺序测试 | 24字节，字段偏移显式 |
| Rust函数ABI | runtime-lab.s/.ll的实际导出函数 | 不作为外部C ABI承诺 |
| 子进程接口 | 可执行文件参数与字节流 | 不是共享Rust引用 |
| 错误表达 | io::Error与Report字段 | 不跨进程传Rust错误对象布局 |

如果未来要跨语言worker，可以保持这份线格式并重写另一端编码器。
但协议还需要兼容性测试和错误码设计。
本轮没有因此把第二个FFI项目标为完成。

::: think 思考 · 给协议加一个「心跳帧」该怎么起步 {#think-10.3.1}

设想worker长时间空闲后，父进程想发一个特殊帧探活。最小改动是不是「把value填0当作心跳」？

::: sol 解答

不是。value=0是业务合法值，被解释成心跳就改变了对既有帧的语义——这是把[@def-10.3.1]的「字段语义独立」又混回去了。显式契约的起步方式是：flags里预留位全0是当前版本的硬性约束，所以启用flag需要版本升级（version从1变2），旧解码器遇到未知版本必须按10.3.3拒绝而不是猜测。配合10.3.1的帧长字段，扩展才能被逐字节验证。本轮没有实现心跳帧，这里只给出协议演进必须遵守的顺序。

:::

:::

### 10.3.7 小结与常见错误

**小结。**① 线格式是与内存布局解耦的显式字节契约，多花的8字节买的是版本、标志与帧长（[@def-10.3.1]）；② 先核头再解释载荷，未知版本直接拒绝，解码顺序就是信任边界（10.3.3）；③ 短读是常态，帧首之后的EOF必须报截断，干净EOF与半帧残留是两个事件（[@def-10.3.2]、[@ex-10.3.1]）；④ write_all与flush都不构成跨进程确认，完成确认只来自读回并校验响应帧（10.3.5）；⑤ 静态代码产物只核对「检查确实存在」，不替协议做承诺（10.3.6）。下一节 [10.4 benchmark一：每次启动与持久worker](#sec-cpp-rust.3.10.4) 把这份协议放进两种部署策略里计时。

::: errata 常见错误清单（10.3 节）

E-a **把结构体转储当线协议。**填充、地址、usize宽度与未初始化字节都会跟着过去（[@def-10.3.1]）。

E-b **一次read不满就报协议错误。**字节流允许短读（[@def-10.3.2]）。

E-c **把中途EOF并进干净EOF。**半帧残留与帧边界关闭是两个事件（[@ex-10.3.1]）。

E-d **对未知版本「尽量兼容」。**猜测解析比拒绝更难事后定位（10.3.3）。

E-e **把write_all或flush当成对端确认。**确认只来自响应帧（10.3.5）。

E-f **只用同机encode-decode往返做验证。**同一对函数可能同错，需逐字节破坏测试（10.3.3）。

:::

## 10.4 benchmark一：每次启动与持久worker {#sec-cpp-rust.3.10.4}

本节回答一个问题：**1.219 ms 与 5.484 µs 之间的差，量的是什么？**它是两种部署策略各自完整生命周期的差，不是「一次系统调用的成本」。比较之前先把计时边界钉死——这是[@def-1.1.3]在本章的落地。

::: preview 先抓住一件事

两个case的计时边界故意不同：spawn case计入创建与回收，persistent case只计稳态往返。脱离边界表读这两个均值，任何一句话都可能过度概括。
:::

### 10.4.1 比较的是部署策略

入口：`src/bin/process_rpc.rs`。
每个请求发送一个24字节Frame。
worker把value做wrapping_mul(3)，保留request_id并响应。
父进程逐条检查id和结果。

两个case：

- spawn：每个请求新建worker、握手、请求、响应、关闭输入、wait。
- persistent：每批先启动一个worker并完成握手，在计时内串行完成16次往返。

这是每请求启动与复用已就绪进程的策略比较。
两者计时边界故意不同。
不能把差值全部叫作「一个系统调用的成本」。

::: def 定义 10.4.1 · 计时边界与策略比较 {#def-10.4.1}

两个case测量的对象不同：spawn case是**完整业务生命周期**（创建、握手、请求响应、关闭、回收全部计入）；persistent case是**稳态串行往返**（创建与握手移出计时之外）。按[@def-1.1.3]，它们是两个估计对象；两者的差回答「每请求启动 vs 复用已就绪worker」的策略问题，拆不出「单个系统调用多少纳秒」——本轮也没有把worker的启动延迟拆成动态链接、页错误和用户初始化比例（10.4.5）。

:::

### 10.4.2 握手为什么必须在持久case计时之前

新进程spawn返回，不表示用户代码已经完成初始化。
若直接开始计时第一次请求，持久case的第一条往返仍会包含冷启动。

::: def 定义 10.4.2 · 已就绪worker {#def-10.4.2}

worker启动后先输出固定8字节`RPCv0001`并flush，父进程read_exact并核对握手；只有核对完成，这个worker才算**已就绪**——已经进入按帧循环的协议状态。persistent case从就绪之后才开始计时，被复用的对象因此定义清楚（[@def-10.4.1]）。

:::

按[@def-10.4.2]，握手移出的是一个明确的协议事件「对端已进入帧循环」，不是一段随机代码。这与10.3.4把EOF定义为帧边界事件是同一种纪律。

### 10.4.3 完整生命周期与防遗留

::: def 定义 10.4.3 · 一次进程创建到底做了几件事 process creation anatomy {#def-10.4.3}

rCore 教程把 Unix 风格的三个系统调用摊开实现过一遍，可以拿来当这张表的骨架：`fork` 复制当前进程、给子进程一个新 PID，此后它的资源由父进程负责收尾（在 rCore 里，那份收尾的活儿落在一个专职的初始进程身上）；`exec` **清空当前地址空间**并按名字加载一个 ELF 的代码段与数据段，返回用户态后才开始执行新程序；

`waitpid` 之所以必须存在，是因为进程 `exit` 之后资源**不能立即全部回收**——它那份内核栈此刻正被用来处理这次退出，回收掉就可能让系统调用无法正常返回。进程控制块因此要携带 PID 句柄、内核栈、任务状态与调度信息。
:::

把 10.4 的 1.219 ms 与 5.484 µs 摆在这张骨架上读，两件事就清楚了。**spawn case 每次付的是上面整条链**：新建地址空间、加载 ELF、分配内核栈页帧、首次调度、最后还要等 `waitpid` 把资源收干净；**persistent case 只付一次管道往返**，链上的每一步都发生在计时边界之外。所以这两个数之差叫「每请求启动 vs 复用已就绪进程」的策略差，不能叫「一次系统调用的成本」——一次 `fork` 或一次 `write` 单独值多少，本节没有采集。另外注意 `exec` 会清空地址空间：这意味着**换程序的成本不能靠复用旧进程摊掉**，只能靠复用已经 `exec` 完的进程，这是持久 worker 的定义所在。

实现上，Session取得ChildStdin和ChildStdout。
握手失败时，启动函数尝试kill并wait。
正常finish关闭stdin，然后wait。
Drop在尚未退出时也尝试kill并wait。

这个同步Drop只适用于本实验有限helper。
不能在通用异步服务的关键poll中无条件进行可能阻塞的wait。
本轮没有把它封装为通用异步进程池库。
finish的顺序——先关stdin再wait——由10.2.3的互等分析直接决定（[@ex-10.2.1]的观察表同样适用于这里）。

### 10.4.4 每批工作与时间边界

| 阶段 | spawn case | persistent case |
|:--|:--|:--|
| 创建worker | 每请求计入 | 每批在计时外 |
| 8字节ready握手 | 每请求计入 | 每批在计时外 |
| 16次请求响应 | 计入 | 计入 |
| 响应id/结果校验 | 计入 | 计入 |
| stdin关闭与wait | 每请求计入 | 每批在计时外 |
| 父进程编译 | 不计入 | 不计入 |
| worker文件读取热状态 | 未强制冷缓存 | 未强制冷缓存 |

spawn case包含完整业务生命周期。
persistent case包含稳态串行往返。
这份表必须随结果一起阅读。

### 10.4.5 样本方法

修订后每case先执行至少500ms预热。
每批16次请求。
正式每case21批，轮转先后顺序。
每个样本是16次请求的墙钟均值。

轮转先后顺序对付的是时间位置效应（[@def-1.4.1]），500ms预热对付的是热漂移（[@def-1.2.3]）；「每个样本是16次请求的均值」意味着表里的分位数是批分位数，不是逐请求观测（[@def-1.5.2]）。

已保存本机环境与固定release配置。
没有固定亲和性，没有清空文件系统缓存。
没有把worker的启动延迟拆成动态链接、页错误和用户初始化比例。

### 10.4.6 本轮结果

来源：`runtime-fixed/measurements-final/process-rpc.txt`。
单位为ns/request，表中批分位数不是逐请求尾延迟。

| 策略 | mean | sd | 批p50 | 批p99 |
|:--|--:|--:|--:|--:|
| 每请求spawn | 1219110.006 | 77376.429 | 1208367.188 | 1531747.438 |
| 单worker复用 | 5484.128 | 532.400 | 5372.375 | 7346.375 |

本轮新进程生命周期均值约1.219ms，请求复用往返约5.484µs。
这里「冷」只表示新进程生命周期，不表示磁盘/页缓存（内核留在内存里的那份文件数据，读过一次就命中）已冷却。
不能把这个结果解释成每次新进程都必须从物理磁盘读完整文件。

::: ex 例 10.4.1 · 三句结论哪句被数据支持 {#ex-10.4.1}

候选句子：① 「Rust进程创建需要1.219 ms」；② 「一次请求-响应IPC的成本是5.484 µs」；③ 「对本机这个极小整数业务，每请求启动的完整生命周期批均值约为单worker稳态往返的222倍」。哪些能写？

::: sol 解答

①不能：1219110 ns里含握手、请求响应、校验、关闭与wait（[@def-10.4.1]），没有单独拆出创建成本——本节没有采集该项分解。②措辞要收窄：5484.128是16次请求墙钟均值的批均值（[@def-1.2.2]），不是单请求延迟；「稳态串行往返的批均成本」才是准确说法。③可以写，但必须带上条件：本机、macOS ARM64、固定release构建、极小整数业务、单worker严格一次请求一次响应（[@def-1.1.3]的四组问题一次答全）。222只是两个均值的比，不引入任何新的统计保证。

:::

### 10.4.7 有限结论与判定

对这个极小的整数业务，新进程生命周期显著大于稳态串行IPC往返。
复用可以摊薄初始化和退出成本。
实际业务若每次执行数秒，节省1ms可能不是主要问题。

复用也会引入新的成本：

- worker状态可能跨请求保留。
- 单个worker故障会影响其在途请求。
- 协议需要关联请求与响应。
- 生命周期延长后，内存增长和资源泄漏更容易积累。
- 更新、回收与健康检查需要显式设计。

因此不能直接给出「永远用进程池」的结论。
先确定隔离要求、工作量和故障模型。

::: method 判定流程 · 每请求spawn还是持久worker

**先定三件事**：隔离要求、工作量、故障模型；再读[@def-10.4.1]的边界表。<br>
**每次执行以秒计的业务工作**：1 ms差值不是主要矛盾，per-spawn的干净状态与独立故障域往往更值。<br>
**高频小工作、稳态为主**：持久worker摊薄初始化与退出（本节两行数据支持的唯一方向性结论）。<br>
**选复用时**：上面五条复用成本（状态保留、故障波及在途、请求关联、内存增长、更新回收健康检查）必须逐条给出设计，缺一条就是在复制10.8要治理的问题。<br>
**要下跨环境结论**：这是探索性桌面实验（[@def-1.7.3]），换环境须按新环境的边界重跑。

:::

### 10.4.8 不是多worker并行池benchmark

这里持久case只有一个worker，且严格一次请求一次响应。
没有多个在途请求，也没有负载均衡。
它可以视为复用策略最小退化实验。

本章后面讨论多worker池的责任，不假装已经测出其扩展性。
若把本结果直接乘以worker数得到总吞吐，会忽略CPU、管道、父进程分发与排队。
需要另外实现并运行扩展实验。

::: think 思考 · 5.484 µs × 8 个worker等于总吞吐吗 {#think-10.4.1}

有人想用本轮数据预估8-worker池：5.484 µs ÷ 8 ≈ 0.69 µs/请求。用本节与10.4.8指出这个推算缺了什么。

::: sol 解答

缺了四层：① 本轮persistent case没有并发在途请求，协议连「多路关联」都还没实现（10.3的帧有request_id，但串行往返里没人用它配过乱序响应）；② CPU核心数、管道缓冲、父进程分发与排队都没有建模；③ worker各自的冷/热状态与共享父进程的争用会引入非线性，稳态串行数据无法外推；④ 没有跑过扩展实验，任何总吞吐数字只是算术练习，不是「测量结果」。正确动作是按10.4.8补一个多worker实现与实验，而不是换算现有数字。

:::

:::

### 10.4.9 小结与常见错误

**小结。**① 两个case是两个估计对象，差值是策略差不是 syscall 成本（[@def-10.4.1]）；② 计时从[@def-10.4.2]定义的「已就绪」之后开始，握手是协议事件不是代码片段；③ 表格数字是批均值口径，1.219 ms含完整生命周期（[@def-1.2.2]、[@ex-10.4.1]）；④ 复用摊薄成本，但带来状态、故障、关联、内存与运维五类新责任（[@def-10.4.1]之后的清单）；⑤ 本轮没有测多worker扩展性（[@think-10.4.1]）。下一节 [10.5 输出背压、排空与有限保留](#sec-cpp-rust.3.10.5) 转向输出方向：先wait后读怎样把10.2.3的互等放大成整章最贵的停滞。

::: errata 常见错误清单（10.4 节）

E-a **把两case差值叫「一个系统调用的成本」。**计时边界本来就不同（[@def-10.4.1]）。

E-b **spawn返回即开始计时。**把冷启动混进稳态往返（[@def-10.4.2]）。

E-c **把批p99读成逐请求尾延迟。**样本是16次请求的均值（10.4.5，[@def-1.5.2]）。

E-d **把「新进程生命周期」叫「冷缓存」。**文件读取热状态未强制冷却（10.4.4表末行）。

E-e **拿单worker数据乘worker数外推吞吐。**分发、排队与争用未建模（[@think-10.4.1]）。

## 10.5 输出背压、排空与有限保留 {#sec-cpp-rust.3.10.5}

本节回答一个问题：**只关心开头128字节的输出，为什么还要把4MiB全部读完？**管道缓冲有限，「不读」本身就是一种会反作用到写方的力量。这一节给出停滞的形成条件、排空组件的四个状态字段，以及「排空」与「保留」的分界。

::: preview 先抓住一件事

保存上限约束的是「留多少」，不是「读多少」。达到cap之后停止读取，等于亲手制造10.5.1的等待回路——本轮确实在测试里重现过它。
:::

### 10.5.1 先wait后读为什么会卡住

管道缓冲有限。
如果子进程不断写stdout，缓冲满后写入会等待读者。
父进程若正在wait子进程退出，而不读stdout，就形成循环等待。

```text
parent: wait(child exit)
child:  write(stdout) waits for buffer space
buffer: full
reader: parent, but parent waits instead of reading
```

::: def 定义 10.5.1 · 背压等待回路 backpressure stall {#def-10.5.1}

**背压停滞**由三个条件同时成立构成：管道缓冲已满、写方在等空间、读方在等别的事件（例如子进程退出）。任何一方换动作都能解开回路，但父进程「先wait后读」的写法让双方都在等对方先动——它与[@ex-10.2.1]的互等是同构问题，只是方向从stdin换到了stdout。

:::

stderr也可能独立发生同样问题。
只排空stdout，然后等退出，仍可能被写满的stderr卡住。

### 10.5.2 本轮实际重现停滞

测试：`wait_before_drain_is_a_reproduced_stall`。
helper向stdout写2MiB，随后向stderr写2MiB。
父进程先读取stdout一个字节，确认helper已经进入输出阶段。
之后停止读取，只等待其退出。

30ms期限内wait未完成。
测试随后kill并wait直接子进程，避免制造永久挂起。
这不是通过运行UB来观察异常。
它是安全Rust与有限内核缓冲形成的资源等待回路。

30ms只是测试观察窗口，不是管道容量或调度保证。
完整输出量远大于本机实际可用管道缓冲。
若换平台，应重新确认实验参数与观察事实。

### 10.5.3 有限保留的状态

源文件：`src/process.rs`。
每个输出流维护：

| 字段 | 含义 | 上界/限制 |
|:--|:--|:--|
| prefix | 保存的前cap字节 | length不超过cap |
| total | 实际排空总字节数 | checked_add，防止计数溢出 |
| eof | 是否读到0 | 不能由child退出推断 |
| reader_errors | 读取失败或grace超时 | 调用方必须检查 |

::: def 定义 10.5.2 · 有限保留 bounded capture {#def-10.5.2}

**有限保留**指「排空全部字节、只保存固定前缀」的采集策略：读取不因cap到来而停止，`total`继续用checked_add计数；`prefix`的长度不超过cap；`eof`与`reader_errors`独立记录观察结论。注意三个「不是」：cap不是进程RSS上限（Vec容量、读块、任务头和内核缓冲都有额外开销），不是「达到cap自动杀进程」的开关，四个字段也不是退出状态的替代品（[@ex-10.2.1]的表在这里逐行适用）。

:::

组件限制单流cap不超过16MiB。
这是实验API的输入策略，不是操作系统硬限制。
cap限制保留数据长度，不是整个进程RSS上限。
Vec容量、读块、任务头和内核缓冲都有额外开销。

### 10.5.4 排空循环

每次异步read使用8192字节临时块。
读取完成后，短暂加锁更新Capture。
锁在下一次异步读取之前释放。
下段为旧源码快照中的保留算法；现版用poll_fn另记poll、Pending、EOF与Drop时刻，保留逻辑相同。

```rust
let n = reader.read(&mut chunk).await?;
let mut s = state_lock(&state)?;
if n == 0 {
    s.eof = true;
    return Ok(());
}
s.total = s.total.checked_add(n as u64)
    .ok_or_else(|| std::io::Error::other("byte count overflow"))?;
let keep = n.min(cap.saturating_sub(s.prefix.len()));
s.prefix.extend_from_slice(&chunk[..keep]);
```

这个锁不跨await。
两个流分别有自己的Capture，不共享一个大日志锁。
单次更新成本与最多8192字节的复制相关。
若cap已经耗尽，keep为0，仍继续读取与计数。
「keep为0仍继续读」正是[@def-10.5.2]与[@def-10.5.1]的分界点：保留可以停，排空不能停。

### 10.5.5 内存控制不能只看一个Vec

两个流各自有一个保留前缀。
总保留长度上界是2×cap。
但这是内容长度上界，不是精确的分配器字节上界。

本轮在排空任务结束后使用mem::take移交Capture。
没有为了返回报告再clone整个前缀。
这个细节减少结束时重复持有日志内容的机会。
但没有采集RSS峰值，节省多少MiB RSS这一问，本节没有采集。

::: think 思考 · 达到cap之后，能不能停止读取 {#think-10.5.1}

保存上限达到之后，报告里该留的内容都齐了。此时停掉读任务可以省下带宽——看起来是无风险的优化。指出问题。

::: sol 解答

输出上限不能靠停止读取实现。停读之后，子进程写满缓冲就被堵住（[@def-10.5.1]），它到不了退出点，父进程的wait也就永远返回——10.5.2重现的停滞就是这条路径。必须正确区分「还要继续排空」和「还要继续保存」：本轮组件持续读取所有字节，只保留每流固定前缀（[@def-10.5.2]）。想真正少读，唯一诚实的杠杆是换终止策略（超过某个总量后终止工具），而不是装看不见；该策略本轮没有实现（10.6.5）。

:::

:::

### 10.5.6 二进制输出与UTF-8

Capture保存字节，不假设每次读取正好落在UTF-8边界。
cap也可能截在一个多字节字符中间。
显示层若直接String::from_utf8，可能收到错误。

工具日志可以选择有损显示，但原始字节与截断标志应保留。
协议stdout则不应任意进行有损转换。
如果要按行展示，还要防止一条永远没有换行的超长行。

### 10.5.7 字节总数比截断文本更有诊断价值

只保存128字节前缀可能隐藏后面大量重复错误。
同时保留total，可以告诉读者实际排空了多少数据。
若eof为false，total也只是已读数量，不是对端实际输出总量。

::: ex 例 10.5.1 · 这两行报告各该怎么写 {#ex-10.5.1}

排空结束时的Capture状态分两类，别混着读。**来自 `pipe_drain` 归档的真值**：stdout流 `total=2097152, eof=true`，以及 `cap=128`（与归档逐项对得上：前缀 128、每批 2 097 152 字节，两流共用这个上限）。**为练边界构造的夹具**：stderr流 `total=900000, eof=false, reader_errors=["grace expired"]`，这三个值本轮归档里都没有，只按同一形状假想，cap 同样取 128。把诊断报告的两句结论写准确。

::: sol 解答

stdout：观察到EOF，可以写「该流排空了2097152字节且读完」（[@def-10.2.1]的条件成立）。stderr：grace到期、读到0之前没有EOF，只能写「至少已排空900000字节，尾部未知」——把total写成「子进程只输出了900000字节」就是把已读量冒充总量（[@def-10.5.2]的eof字段存在的意义）。两行都必须同时带prefix长度与reader_errors；「不知道」要在报告语义里保留（对照[@ex-10.2.1]：wait返回也不能替这两个流做EOF声明）。

:::

:::

不要把「total=1000且eof=false」写成「子进程只输出了1000字节」。
未知尾部必须在报告语义里保留。

::: method 判定流程 · 子进程输出疑似卡住，按什么顺序查

① **两个流都有人读吗**——stdout、stderr各自并发排空，缺一侧就中[@def-10.5.1]的回路。<br>
② **读任务是否在cap之后提前退出**——「保存够了」不等于「可以停读」（[@think-10.5.1]）。<br>
③ **wait返回了但EOF还没到吗**——那是端点寿命问题（后代继承写端，[@def-10.2.1]），归10.7处理，不是排空bug。<br>
④ **都排除了再看总量策略**——超大输出要靠「终止+继续回收」，不是靠停读或加大cap（10.6.5）。
:::

### 10.5.8 小结与常见错误

**小结。**① 背压停滞是「缓冲满＋写方等空间＋读方等别的」三元循环，先wait后读是最常见写法（[@def-10.5.1]）；② 有限保留把「排空」与「保存」分开：读完全部字节、只存前缀、total用checked_add、eof与reader_errors独立成字段（[@def-10.5.2]）；③ 本轮用测试重现了停滞，30ms只是观察窗口不是容量证明（10.5.2）；④ cap不是RSS上限，也不是自动杀进程开关（[@def-10.5.2]）；⑤ eof=false时的total只能写成「已读下界」（[@ex-10.5.1]）。下一节 [10.6 benchmark二：保存全部与固定前缀](#sec-cpp-rust.3.10.6) 用数据检验这套策略的代价。

::: errata 常见错误清单（10.5 节）

E-a **先wait后读大输出。**三元循环立刻成立（[@def-10.5.1]）。

E-b **只排空stdout。**stderr独立地满、独立地卡（10.5.1）。

E-c **达到cap就停止读取。**省下的带宽换来永久停滞（[@think-10.5.1]）。

E-d **把cap当进程内存上限或杀进程开关。**它只约束prefix长度（[@def-10.5.2]）。

E-e **eof未到时把total报成总量。**截断计数冒充完整输出（[@ex-10.5.1]）。

E-f **假定读块落在UTF-8边界。**cap可以截在多字节字符中间（10.5.6）。

:::

## 10.6 benchmark二：保存全部与固定前缀 {#sec-cpp-rust.3.10.6}

本节回答一个问题：**「少保存」到底省下了什么？**两个策略都把4MiB完整排空，唯一区别是保留多少。结果表几乎重合——这恰恰是需要把结论写准确的地方：省下的不是带宽，是保留内容与相应的资源风险。

::: preview 先抓住一件事

ns/输出字节是聚合吞吐的倒数，不是任何单字节的延迟。两个case的均值差在本轮波动之下；数据支持的说法是「固定前缀完成了同样的排空工作，保留内容大幅减少」，不是「固定前缀更快」。
:::

### 10.6.1 计量对象

入口：`src/bin/pipe_drain.rs`。
helper向stdout写2MiB，向stderr写2MiB。
每批合计4194304字节。
两个case都完整排空两个流。

- prefix128：每流只保留128字节。
- retain-all：每流上限设为2MiB，恰好保存这个已知工作量的全部输出。

retain-all不是一个对任意输出无限增长的生产实现。
它是为固定4MiB工作量设计的对照。
不要把这个实验改写成「无限Vec一定如此快/慢」。

::: def 定义 10.6.1 · 聚合吞吐倒数 ns/输出字节 {#def-10.6.1}

报告单位为ns/输出字节，即批墙钟时间除以4194304个聚合输出字节。这是一种聚合吞吐倒数（[@def-1.2.2]的批均值换了分母），它不是一个字节从写入到用户看到的独立延迟；两个流在同一轮中可以交叠推进。
:::

### 10.6.2 实验包含的阶段

每批计时由run_child内部记录。
包括spawn、输出传输、读取、wait、读任务结束和报告形成前的大部分工作。
不包括父进程编译。
也不单独分解用户态复制与内核复制。

### 10.6.3 校验不能只看进程退出码

每批都检查：

1. 未发生直接子进程超时。
2. exit_code为Some(0)。
3. reader_errors为空。
4. stdout和stderr都观察到EOF。
5. 两流total都等于2097152。
6. prefix长度分别等于当前cap。
7. 修订版另外校验保存的每个字节都等于helper实际输出的x，校验在计时边界外。

如果只检查退出码，可能漏掉输出尚未排空的情况。
如果只检查保存长度，可能把停止读取导致的截断当成正确完成。
这六项观察连接了执行、传输和保留三个层面——第4、5项是[@def-10.2.1]与[@def-10.5.2]落到测试里的化身。

### 10.6.4 本轮结果

单位为ns/聚合输出字节。

| 保留策略 | mean | sd | 批p50 | 批p99 |
|:--|--:|--:|--:|--:|
| 每流前128字节 | 0.514 | 0.031 | 0.507 | 0.583 |
| 每流全部2MiB | 0.515 | 0.027 | 0.507 | 0.583 |

::: ex 例 10.6.1 · 「快0.2%」能进结论吗 {#ex-10.6.1}

prefix128均值0.514，retain-all均值0.515，sd分别为0.031与0.027。有人想写「固定前缀快约0.2%」。按第1章的统计纪律（[@def-1.5.2]、[@def-1.6.2]）评估这句话，再给出本轮数据真正支持的版本。

不能写。0.001的差值小于两组各自的标准差（[@def-1.5.2]），方向都不稳健；本轮没有对21批构造配对差值区间，也没有显著性检验、没有报告p值——按[@def-1.6.2]的标准，连「区间」这个对象都没建立，更谈不上按[@def-1.7.2]判接受或拒绝。数据支持的稳妥结论只有：固定前缀正确完成同样排空工作（10.6.3的逐项校验通过），且保留内容大幅减少。它不支持宣称固定前缀在所有环境下保证某个百分比加速。

### 10.6.5 吞吐接近也不代表资源风险相同

4MiB是有限输出。
如果真实工具输出4GiB，保存全部的策略会继续累积内容。
固定前缀可以保持保留长度上界，但仍要持续承担读取带宽与CPU开销。

因此还需要总输出量策略。
例如超过某个total后终止工具，同时继续执行回收协议。
本轮没有实现这个额外策略。
不能把cap参数误读成「达到cap自动杀进程」。
这条分界与[@def-10.5.2]的两个「不是」是同一件事：保留上限管内容长度，终止策略管进程生死，两者都要存在且互相引用（10.7给出带期限的回收顺序）。

### 10.6.6 为什么没给出零拷贝结论

helper在用户态构造输出。
管道读入用户块，prefix再复制到Vec。
本实验不是共享内存，也不是splice/sendfile路径。

低ns/byte可能主要受大块传输、缓存和并发排空影响。
没有采集内存带宽计数或复制次数的动态跟踪，「每字节拷贝几次」这类断言，本节没有采集的数据支撑。
因此不把它称为零拷贝（省掉「先复制一份再交出去」那次复制）或每字节只拷贝一次。

### 10.6.7 profiler证据的边界

本轮保存了组件LLVM IR与本机汇编。
它们能核对编码、检查与状态操作实际存在。
但进程启动和管道等待主要跨越操作系统接口。
仅看Rust函数指令数，无法推导整个benchmark耗时。

此前另行采集了macOS父进程报告`process-rpc-sample.txt`，对应历史版本与当时预热设置。
采样与正式吞吐测量分开运行，原始文件保存在`runtime-final/`。
父进程栈中实际出现：

| 观察到的栈 | 对应阶段 | 不应误读为 |
|:--|:--|:--|
| posix_spawnp / __posix_spawn | 启动worker | Rust代码固定执行一次fork |
| Session::start下的read | 等待ready握手 | 父进程正在忙算协议数据 |
| __wait4 | 回收直接子进程 | 已经排空所有后代写端 |
| 请求路径的read | 等待响应字节 | 该栈消耗最多CPU算力 |

采样包含阻塞等待栈。
栈被多次观察到，不代表它在这些时刻一直消耗CPU。
短程序还会经历多个case与预热阶段，不给出稳定态CPU百分比。
该报告只观察父进程，不是所有worker的系统级聚合追踪。
它能验证本轮确实跨过启动、握手等待和回收边界。
不能用它精确拆解当前表格的各阶段纳秒数。

可在macOS上另行运行复验：

```bash

pid=$!
sleep 0.1

wait "$pid"
```

这条命令不覆盖归档计时数据。
其他平台应使用对应工具，不能把没有执行的工具报告补成结果。

本轮没有Linux perf、strace或PMU报告。
也没有子进程每个阶段的独立CPU采样。
因此本章不报告页错误数、context-switch数、系统CPU百分比或IPC。
若需要定位启动与传输的具体占比，应补充平台对应的系统追踪实验——这些量在归档里不存在，本节没有采集，任何补数都是编造（对照[@ex-1.8.1]的分层：没有的观察不能写进结论）。

### 10.6.8 小结与常见错误

**小结。**① ns/输出字节是聚合吞吐倒数，不回答单字节延迟（[@def-10.6.1]）；② 七项校验把「执行、传输、保留」三层绑在一起，只看退出码会漏掉未排空（10.6.3）；③ 本轮均值差在sd之下且无区间，稳妥结论只到「同样排空、少保存」（[@ex-10.6.1]）；④ cap不是终止策略，4GiB场景还需要总输出量策略加回收协议（[@def-10.5.2]）；⑤ 采样与静态产物只能验证「跨过了哪些边界」，拆不出百分比（[@think-10.6.1]）。下一节 [10.7 超时、kill、wait与排空grace](#sec-cpp-rust.3.10.7) 把终止、回收与排空拼成一条带期限的完整顺序。

::: errata 常见错误清单（10.6 节）

E-a **把ns/byte读成单字节延迟。**它是批墙钟除以聚合字节（[@def-10.6.1]）。

E-b **只查退出码。**未排空、截断、grace超时全都看不见（10.6.3）。

E-c **拿0.001的均值差宣布加速比。**差值在sd之下且无区间（[@ex-10.6.1]）。

E-d **把cap当自动杀进程开关。**终止策略是另一件没实现的事（10.6.5）。

E-e **由低ns/byte推出零拷贝。**复制次数没有采集（10.6.6）。

E-f **把`sample`栈占比画成CPU饼图。**阻塞样本、混阶段、单侧视角三重失真（[@think-10.6.1]）。

## 10.7 超时、kill、wait与排空grace {#sec-cpp-rust.3.10.7}

本节回答一个问题：**「超时了」三个字，要拆成几个可观察的事件才算说完整？**10.2把退出与EOF拆成两条寿命，10.5给出排空状态，本节把它们串成一条带期限的终止—回收—收尾顺序，并交代本轮回修的一个真实竞争缺陷。

::: preview 先抓住一件事

timeout、kill、wait、grace、abort各管一个时钟和一个对象；「把Future放进timeout」只完成了三件事中的一件半。本协议的顺序是显式的，每一段都有可观察的成功标志。
:::

### 10.7.1 一个超时至少涉及三件事

- 不再接受该请求的正常结果。
- 使外部工作停止或进入受控收尾。
- 回收直接子进程与本地I/O任务。

::: def 定义 10.7.1 · 超时的三件事分离 {#def-10.7.1}

**三件事**分别对应三个对象：调用方的结果预算（不再接受正常结果）、外部进程的执行（停止或受控收尾）、内核与本地资源（直接子进程的wait回收＋本地读取任务的取消）。把执行Future放进timeout只完成第一件事的一部分；默认丢弃Child句柄，并不意味着子进程终止；即使启用kill_on_drop，也不能用它代替可观察的wait成功。
:::

按[@def-10.7.1]逐项打勾，才能判断一份「超时处理实现」缺了哪几项。后面每一小节补一项。

### 10.7.2 本轮run_child的顺序

```text
配置stdin=null、stdout/stderr=piped、kill_on_drop
 -> spawn
 -> 取出两个输出端点
 -> 启动两个排空任务
 -> timeout(deadline, child.wait())
      正常完成：保留退出状态
      超时：start_kill，然后wait
 -> 对两个排空任务并发等待drain_grace
      正常EOF：保存完整状态
      grace到期：abort读取任务，并观察取消
 -> 移交Capture，返回Report
```

成功返回报告时，直接子进程已经完成wait。
这里成功返回不等于业务退出码为0。
退出码7也会作为一份正常Report返回。
spawn失败则是io::Error，二者不能混为一谈。

### 10.7.3 为什么kill之后还要wait

kill请求与资源回收不是同一个动作。
子进程终止之后，父进程还需要取得退出状态并释放相应系统记录。
Unix上未被等待的已退出子进程可能成为zombie。

标准库Child没有自动等待的Drop实现。
Tokio会在某些路径做尽力回收，但文档不提供严格及时性保证。
对严格清理要求，应显式await wait。
这是[@def-10.1.1]「终止对象」与「回收对象」必须是同一个观察路径的原因：kill只是提交请求，wait才取回状态。

### 10.7.4 超时与自然退出的竞争

子进程可能正好在期限边缘自然退出。
start_kill请求失败或成为无实际效果的请求，并不一定表示wait也失败。
本轮代码仍以wait取得的最终状态为准。

timed_out表示父进程的期限路径被触发。
它不是「操作系统已证明该进程恰好被某个信号杀死」。
exit_code为None在Unix上也可能对应信号终止。
若要报告具体signal，需要另外使用平台相关状态接口。
本轮没有把None伪装成退出码0。

### 10.7.5 drain_grace解决另一个时钟

直接子进程退出后，可能还有后代持有输出写端。
无限等EOF会把有限直接进程期限重新变成无限等待。
所以排空阶段有自己的grace。

::: def 定义 10.7.2 · drain_grace与诚实的部分结果 {#def-10.7.2}

**drain_grace**是排空阶段的独立期限：grace到期后，读取任务被abort并等待其取消；此时Capture可能有部分内容，但`eof=false`，`reader_errors`保留grace到期原因。这是[@def-10.5.2]状态机的出口之一：一种诚实的部分结果——它不声称后代已终止，只保证本轮调用不再无限等这两个输出任务。
:::

grace与10.7.2的deadline是两个时钟：deadline管直接子进程（[@def-10.1.1]的对象），grace管输出端点集合（[@def-10.2.1]的条件）。用一个时钟管两件事，就是「无限等EOF把有限期限变无限」的错误来源。

### 10.7.6 本轮继承写端回归

helper的inherit模式启动一个寿命固定为2秒的后代。
该后代继承stdout/stderr。
直接helper立即exit(0)。

测试观察到：

- wait取得直接子进程退出码0。
- 两条流在短grace内没有EOF。
- 报告保留两条grace超时说明。

测试随后留出2100ms收尾窗口，让固定寿命helper有机会自然结束。
这不是对后代退出事件的严格观察，更不是进程树清理实现。
它反而证明了当前直接子进程治理的明确缺口。

::: ex 例 10.7.1 · 这份报告能写哪句、不能写哪句 {#ex-10.7.1}

inherit回归的报告字段：`timed_out=false`，exit_code为Some(0)，两条流`eof=false`、reader_errors各含一条grace到期。给出允许的观察句与被禁止的推断各两条。

::: sol 解答

允许：①「直接子进程已被wait回收，退出码0」（[@def-10.1.1]路径完成）；②「两个输出流在grace内未观察到EOF，保留部分排空状态」（[@def-10.7.2]的诚实部分结果）。禁止：①「后代进程已终止」——2100ms窗口只是给固定寿命helper机会，不是对后代退出事件的严格观察，更不是进程树清理；②「输出不完整是排空bug」——EOF条件在写端集合而未清空（[@def-10.2.1]），读取任务没有失职。这个案例的价值恰好在把[@ex-10.2.1]表第三行从理论变成实测。

:::

:::

### 10.7.7 确定性补充案例：CLOEXEC创建窗口

初次并行测试只留下两个EOF断言失败。
当时没有child PID、FD列表或read poll时刻，所以不能唯一回溯那一次事故。
后续没有删除失败日志，也没有增大1秒grace或用串行测试掩盖问题。

本轮核读本机安装的Rust1.99.0实现，发现macOS路径采用：

```text
pipe(fds)
  -> 为read端设置FD_CLOEXEC
  -> 为write端设置FD_CLOEXEC
```

::: def 定义 10.7.3 · CLOEXEC创建窗口竞争 {#def-10.7.3}

标准库在macOS路径分两步给管道端点设置close-on-exec标志：`pipe(fds)`返回之后、`fcntl`设置标志之前，存在一个**创建窗口**。若无关线程在窗口内执行posix_spawn，未打标的双FD会被复制进子进程；该子进程再派生后代，捕获管道的额外写端就可能长期存活。症状与10.7.6相同：目标已退出、数据已读完、EOF迟到；但成因不同：这是无关私有FD泄漏，不是工具主动延续输出端点寿命（后者经fd1/fd2正常继承）。两种情况不能通过一律伪造EOF来合并处理。
:::

这不是原子创建。
在pipe返回、fcntl设置标志之前，无关线程的posix_spawn可能复制这些FD。
如果这个无关进程又启动后代，捕获管道的额外写端可能继续存活。
该后代既不是被捕获工具，也没有通过工具的stdout主动继承这一写端。

### 10.7.8 实际交错与内核证据

诊断用dyld interpose在真实pipe创建完成后暂停一次。
不修改FD标志，不注入假输出，不把读缓冲改成EOF。
另一原生线程在这个窗口启动标准流全为null的无关helper，并让其后代短暂存活。
记录lsof后，再放行原来的创建操作。

| 实现/交错 | debug | release | 独立观察 |
|:--|:--|:--|:--|
| 原版，stdout或stderr窗口，flood或timeout | 4组失败 | 4组失败 | gate见pipe和flags=0；后代有额外PIPE |
| 原子CLOEXEC版，同一交错 | 4组通过 | 4组通过 | gate见pipe2和flags=1；无额外PIPE |

旧flood组已完整读出每流2097152字节，但**每组恰好有一路 `eof: true`、另一路还没到**（`baseline-debug/flood-pipe1` 是 stdout 未到、stderr 已到，`flood-pipe2` 正好相反）——读到这里别把它当成「四路都没结束」。
这直接支持「额外写端寿命」而不是「忘了继续读」的诊断。
原版与修复版源码、gate记录、lsof、Report和退出码均保留。
首次interposer本身的递归错误也保留，但不作为runtime缺陷证据。

### 10.7.9 修复边界与所有权

本机macOS27提供pipe2；修复以动态探测的pipe2(O_CLOEXEC)原子创建捕获管道。
每个成功返回的FD立即进入唯一OwnedFd所有者。
读端转入Tokio，写端显式转给Command。

```rust
command.stdout(out_write).stderr(err_write);
let result = command.spawn();
command
    .stdout(std::process::Stdio::null())
    .stderr(std::process::Stdio::null());
```

显式Stdio句柄与Stdio::piped的创建路径不同。
Command可以保留显式句柄，所以spawn成功或失败后都要释放父侧写端。
否则即使CLOEXEC正确，父进程自己的写端也会妨碍EOF——这句是[@def-10.2.1]在修复代码里的直接复读。
完整实现与unsafe义务在`bench/runtime-lab/src/process_macos.rs`，不是复制四行就得到通用封装。

旧macOS没有pipe2时明确返回Unsupported，不静默退回已知竞争路径。
这里也没有用一个全局spawn锁声称能约束所有库和外部调用者。
该修复保护run_child创建的捕获管道，不能让所有标准库Command自动变安全。
同步RPC小夹具仍只用于受信任有限worker，不是这个治理API的替代品。

### 10.7.11 本地读取任务也要防detach

丢弃JoinHandle通常不会自动取消任务。
若run_child在等待阶段被调用方取消，读取任务不能无声变成脱离管理的后台任务。
本轮用ReaderTask包装句柄，Drop请求abort。

```rust
struct ReaderTask {
    handle: tokio::task::JoinHandle<std::io::Result<()>>,
}
impl Drop for ReaderTask {
    fn drop(&mut self) {
        self.handle.abort();
    }
}
```

正常finish_reader路径还会等待完成或观察取消。
外层Future被直接丢弃时，Drop只能请求取消，不能在Drop里异步等待。
所以该取消路径不提供「返回Report时已reap」的同等级保证。
它根本没有返回Report。

::: think 思考 · 超时分支一把丢弃管理Future，算回收吗 {#think-10.7.1}

调用方在超时后直接drop整个run_child的Future：kill_on_drop开着，ReaderTask的Drop也会abort。有人写「超时路径已自动清理资源」。对照[@def-10.7.1]三件事逐项检查。

::: sol 解答

三件事只完成了一半：第二件的「请求」发出（kill_on_drop提交终止意图）、第三件的本地任务收到abort请求——但没有任何一件被**观察**成功。丢弃JoinHandle不会自动取消任务，Drop只能请求取消、不能在Drop里异步等待；直接子进程是否已被wait回收完全未验证（zombie风险仍在，10.7.3），更谈不上后代写端。这条路径连Report都不返回，「已回收」三个字没有观察载体。正确做法：调用方若要求严格回收，应让清理协议本身继续被驱动，不要在超时分支一把丢弃整个管理Future，然后宣布资源已回收。

:::

:::

### 期限不是硬实时总时长

本轮deadline用于wait阶段的期限判断。
spawn本身发生在该timeout构造之前。
kill后的wait和输出grace还会增加收尾时间。
async计时器本身也需要runtime获得执行机会。

因此不能把参数30ms写成「函数最多运行30ms」。
若业务需要端到端期限，应把启动、运行、终止与收尾分别预算。
若需要强隔离的硬配额，还需操作系统层面的治理能力。

::: errata 常见错误清单（10.7 节）

E-a **kill之后不wait就宣布回收完成。**start_kill只提交请求，wait才取回退出状态并释放内核记录；Unix上未被等待的已退出子进程可能成为zombie（10.7.3）。

E-b **拿kill_on_drop代替显式wait。**标准库Child没有自动等待的Drop实现，Tokio只在某些路径尽力回收，文档不提供严格及时性保证（[@def-10.7.1]）。

E-c **把成功返回Report读成业务成功。**退出码7同样作为正常Report返回，spawn失败才是io::Error，两者不能混为一谈（10.7.2）。

E-d **用一个deadline管两个时钟。**grace管的是输出端点集合；少了它，后代仍持有写端时等EOF会把有限期限变回无限等待（[@def-10.7.2]）。

E-e **把timed_out写成「进程被某个信号杀死」。**它只说明父进程的期限路径被触发；exit_code为None在Unix上也可能对应信号终止，报具体signal要另用平台相关状态接口（10.7.4）。

E-f **两类EOF迟到当成同一个bug修。**CLOEXEC创建窗口泄漏的是无关私有FD，主动继承延续的是工具的写端；一律伪造EOF会把两种成因抹平（[@def-10.7.3]）。

:::

## 10.8 进程池、共享内存与故障语义 {#sec-cpp-rust.3.10.8}

本节回答一个问题：**从「一个 worker」扩到「一个池」，多出来的失败模式由谁负责？**10.7 把单 worker 的协议跑通了；池化之后，分发、关联、健康检查与重启都变成了新的责任，而且共享内存与崩溃会把「谁欠谁一个答复」这件事变得模糊。

::: preview 先抓住一件事

池化增加的不是吞吐，而是**责任**：每个在途请求都要有人能说出它现在归属于哪个 worker 代际、失败时是确定没做还是不确定、以及不确定时谁来兜底。**进程隔离提供的是故障边界，不是事务语义**——它挡得住一次崩溃扩散，挡不住一次副作用被执行两遍。

:::

### 10.8.1 池有状态，状态各有责任

单 worker 实验只有一个在途请求，池则必须维护分发、关联、健康与重启四件事。把池当成一组「可用的进程」会漏掉状态迁移：

| 池状态/事件 | 必须维护的责任 | 常见错误 |
|:--|:--|:--|
| starting | 握手完成前不可接业务 | `spawn` 返回就标 ready |
| ready | 可以接受有限请求 | 无界积压到 worker 输入 |
| busy | 请求 id 与 worker 代际绑定 | 只按数组下标认结果 |
| draining | 不再接新工作，决定在途策略 | 更新时直接丢句柄 |
| failed | 标记受影响请求的不确定性 | 所有失败自动重试 |
| restarting | 递增 worker generation 并重新握手 | 旧响应污染新请求 |

如果同一个 worker 允许多路并发，协议必须承载请求 id；若响应允许乱序，父进程还需要一张请求表，而请求表本身也要有容量上限与超时清理策略。这几件事合起来才是「池」，否则只是把单 worker 复制了几份。

### 10.8.2 准入必须在进入池之前

池里有 4 个进程，不表示系统只保留 4 个请求：每个 worker 可能各有输入队列，父进程可能还有等待分发的队列，每条请求又可能带着大正文。第 9 章「把容量画在每一段队列上」的原则在这里继续适用（见 9.7 节）：要说明每一段队列的容量、谁持有内存、满了之后是阻塞还是拒绝。**一个总并发数字描述不了这些资源**。

### 10.8.3 generation 不是可有可无的日志字段

::: def 定义 10.8.1 · worker 代际 generation {#def-10.8.1}

**worker 代际**是每次 worker 重启时递增的标识。它解决的是「同一个 pid 可能对应不同进程实例」这个问题：操作系统会复用 pid，请求 id 也可能在新会话中重复，只有 `(session, generation, request id)` 三元组才能稳定标识一次执行。

:::

有了它，晚到的旧代输出才能被识别并拒绝。本轮的单 worker 同步协议没有这种晚到多路响应场景，所以没有实现拒绝逻辑——但风险说明不能因为没实现就省略：池化之后，一个来自上一代 worker 的响应如果被当成新请求的结果，错误会以「数据莫名其妙错了」的形式出现。

### 10.8.4 失败之后，重试不是纯调度决定

父进程写完请求后，worker 可能已经提交了外部副作用，而响应在到达前连接断了。此刻父进程并不知道业务有没有执行成功：重试可能重复扣费、写文件或发送消息；不重试可能丢掉本来可以恢复的工作。**进程隔离本身不提供 exactly-once 副作用**，要得到它只能靠业务幂等键、事务或外部确认协议。

::: think 思考 · 「失败了就重试一次」错在哪 {#think-10.8.1}

协议里写着「写入失败后重试一次」。对一个扣费操作，这个规则在什么情况下会造成两次扣费？

::: sol 解答

当第一次请求已经到达 worker、worker 已经把扣费提交出去，而失败发生在**响应回程**时。父进程看到的是「写失败」，于是重试，第二次又执行成功——用户被扣两次。要修它，要么让请求携带幂等键，由服务端去重；要么把「提交」与「确认」拆成两步，让父进程能查询上一次的结果。只改超时或重试次数都绕不开这个窗口。

:::

:::

### 10.8.5 共享内存：省下复制，换来五条证明义务

管道传送大数据时，显式共享映射可能减少一部分复制。但共享内存不是「把 `&Vec` 发给子进程」：不同进程的虚拟地址可以不同，地址值在另一进程里通常没有意义。共享结构应该用偏移、长度与版本化描述传递，消费端在访问前至少检查五件事：

- 偏移与长度的加法是否溢出；
- 范围是否落在当前映射内；
- 对齐是否满足目标类型要求；
- 数据是否已经初始化并被发布；
- 发布者是否还能在消费者使用期间覆盖或取消映射。

本轮没有实现共享映射访问器，因此没有未验证的 unsafe 代码可供复制；这里列出的是后续实现必须满足的证明义务，而不是已经完成的验证。

### 10.8.6 发布、复用与崩溃是三个问题

第 7 章单槽的两条同步链在这里仍然有启发作用：`producer: write payload -> publish ready`，`consumer: observe ready -> read payload -> publish reusable`。跨进程还要额外说明：同步原语是否支持进程共享、两次映射是否一致、对象是否正确初始化。不能因为 Rust 原子在同进程多线程里有效，就略过目标平台的进程共享契约。

崩溃又引入第三个问题：持有共享状态的进程可以在任意业务阶段消失。普通锁的持有者消失，其他进程可能永久等待；这时需要故障检测、代际、恢复日志，或者平台提供的相应机制。这三件事——发布、复用、崩溃——要分开讨论，合在一起说就会漏掉其中一个。

### 10.8.7 Linux 机制不能伪装成本机验证

Linux 共享 futex 需要正确区分进程私有与共享用法，PRIVATE 语义的等待策略不能直接用于跨进程共享地址；pthread 的进程共享与 robust mutex 也有平台、属性与恢复协议上的要求。本机没有执行这些实验，所以本书不提供「已经验证」的 Linux 共享内存吞吐表，也不用 macOS 管道的结果去证明 Linux futex 的成本。

### 10.8.8 还没做的资源治理

本轮没有实现：Linux cgroup / namespace / seccomp 治理、Windows Job Object 进程树控制、macOS 任意工具的强沙箱、通用进程组终止与后代回收、共享内存崩溃恢复、多 worker 池的扩展性压测。这些是明确的后续工程项，不是被基准测试间接证明已经存在的能力。本章完成的是两个可复现实验，以及直接子进程管理边界的具体分析。

### 10.8.9 小结与常见错误

**小结。**① 池的每个状态都有对应责任，`spawn` 返回不等于 ready；② 准入要在进入池之前完成，容量要画在每一段队列上；③ 用 `(session, generation, request id)` 标识执行实例，并拒绝旧代输出（[@def-10.8.1]）；④ 失败后重试涉及副作用语义，进程隔离不等于 exactly-once（[@think-10.8.1]）；⑤ 共享内存省下复制，换来五条访问前检查；⑥ 发布、复用、崩溃要分开讨论；⑦ 平台机制与沙箱不在本章验证范围内。下一节 [10.9 延伸阅读与来源](#sec-cpp-rust.3.10.9) 交代这些结论的出处。

::: errata 常见错误清单（10.8 节）

E-a **`spawn` 返回就当 ready。**握手未完成时接业务，第一个请求会打在还没准备好的进程上。

E-b **只按数组下标认结果。**worker 重启后下标仍指向「位置」，不指向「实例」；请求 id 必须与代际绑定。

E-c **把总并发当资源上界。**每段队列都持有内存，一个数字描述不了三段队列（10.8.2）。

E-d **静默重放失败的请求。**回程失败时副作用可能已经发生，重试会制造重复扣费（[@think-10.8.1]）。

E-e **把 `&Vec` 当作跨进程共享。**地址在另一进程没有意义，必须传偏移、长度与版本。

E-f **用同进程原子经验推断跨进程语义。**进程共享要求平台级契约，本章没有验证。

E-g **用 macOS 管道结果证明 Linux 成本。**平台机制不同，结论不能平移。

:::

### 内核侧的机制出处

- **同一教程第七章「命令行参数与标准 I/O 重定向」**：`chapter7/3cmdargs-and-redirection.html`。这一页把「重定向」做成了纯粹的内核外操作：shell 在启动应用之前先打开目标文件，再用一条复制描述符的系统调用把应用描述符表里的 0/1/2 三个槽位换掉，应用自始至终只认「我往 1 号描述符写」，它并不知道那后面连着串口还是文件。

  本章 10.2 与 10.5 的两条判断都从这条来：**描述符是位置而不是身份**（同一个编号在不同进程、不同时刻可以指着不同的东西），而「把输出换到别处」这件事本身不需要应用配合，只需要替换表里的那一格。这条设计也解释了为什么排空必须两路：被替换掉的 1 号与 2 号是两个独立的槽位，替掉其中一个不影响另一个。
- **同一教程第二章「实现特权级的切换」**：`chapter2/4trap-handling.html`。这一页给出用户态进入内核的那道门由硬件做掉的四件事：把原来的特权级记进状态寄存器（CPU 里那几块专门放状态与模式的格子）、把出错那条指令的地址存进返回地址寄存器、把原因与附加信息分别存进两个寄存器、最后跳到入口地址并切到内核特权级；返回时一条专用指令按记录的特权级与地址跳回去。它还点出一个工程约束：**用户态与内核态共用同一套通用寄存器**，所以内核在动手之前必须先把应用的寄存器存到某处，处理完再恢复。

  本章 10.7 讨论超时与 `kill` 时，「打断只能发生在安全点上」这句话有硬件层的对应——能被打断的位置，恰恰是 CPU 已经把控制权交出去的那个时刻。
- **同一教程第七章「基于文件的标准输入/输出」「管道」「信号」**：`chapter7/1file-descriptor.html`、`chapter7/2pipe.html`、`chapter7/4signal.html`。三页分别补上本章三条判断的机制底账。

  其一，进程创建时默认打开 0/1/2 三个描述符，之后**内核总把新文件分配到描述符表里最小的空闲位置**——这解释了为什么 `fd` 不能当身份用，也解释了关闭再打开会让同一个编号指向另一个对象（10.8 的代际问题，[@def-10.8.1]）。

  其二，管道被实现成一个固定容量的字节环，满与空是两个显式状态，写端用弱引用记录「还有没有人可能写」，只有所有端都关闭后缓冲区才随引用计数归零回收——这是 10.5 的背压回路（[@def-10.5.1]）与 10.7 的双路排空在机制层的样子。

  其三，信号分同步与异步两类，内核把这个检查放在 trap 处理完之后、交回用户态之前的最后一个路口，处理函数跑完还要再调一次专门的返回调用，才能把原来的执行现场恢复出来——「取消只能发生在安全点上」有一个内核版原型，对应 10.7 的超时三件事分离（[@def-10.7.1]）。

  三页的常量（环容量、tick 频率）是那个教学内核的设计取值，**本章一个都没有搬进实验结论**。

## 10.10 常见错误索引 {#sec-cpp-rust.3.10.10}

这一节是全章的常见错误索引；每一节的 `::: errata 常见错误清单（10.M 节）` 已经就地列出该节的具体错误，这里不再重述。下面十二条是整章连起来才看得见的跨节误判，每条都按误判、机制与修法展开。

1. **把独立进程称为安全沙箱。** 地址空间分离不限制文件、网络、权限或后代进程。本实验只管理受信任的 helper，沙箱结论需要另外的权限与配额证据。

2. **在多线程 runtime 后 fork，再继续调用任意 Rust 库。** 子进程可能继承无法释放的锁和进程全局状态。优先使用受支持的独立可执行文件启动路径，把 fork 留给受控的最小代码段。

3. **把 repr(C) 结构体直接当线协议。** 对齐、填充、端序、版本和指针都需要明确。本轮原生 Frame 是 16 字节，协议仍是 24 字节，两者不能互相推导。

4. **一次 read 不满就认定协议坏了。** 字节流允许短读，一次 read 返回少于请求长度是常态。但帧首之后的 EOF 必须报告截断，不能与干净 EOF 合并。

5. **把 stdout 同时用于协议与任意日志。** 一条打印就可能破坏帧边界。协议、诊断和用户输出要分开通道，否则解析器会把日志当成载荷。

6. **先 wait，再读取大输出。** 子进程可能被满管道堵住，永远到不了退出。stdout 和 stderr 都应并发排空，再等待直接子进程。

7. **达到保存上限后停止读。** 这会重新制造背压停滞，写方等不到空间。保存上限与读取/终止策略必须分开：读完全部字节，只保留前缀。

8. **认为 wait 完成就一定读到 EOF。** 后代可能仍持有写端，EOF 会迟到。排空有独立的 grace 与部分结果状态，不能无限等所有后代。

9. **只发 kill，不执行 wait。** 终止请求不等于回收完成，僵尸仍然存在。必须观察直接子进程的最终等待结果。

10. **把 timeout 参数当函数硬总时长。** spawn、调度延迟、kill 后等待与排空还占时间。要明确每段预算及其保证级别，而不是把参数当作端到端上限。

11. **工作进程重启后复用旧 id 而没有 generation。** pid 和局部 request id 可能重复。晚到结果需要与当前执行实例匹配，否则会把上一次的输出记到这一次。

12. **把未知执行结果自动重试。** 响应丢失不代表副作用没有发生。幂等与事务是业务协议，不是进程池自动提供的性质。

## 10.11 本章小结与章末件 {#sec-cpp-rust.3.10.11}

::: note 本章小结

- 进程买到独立地址空间与一个可直接终止的对象，协议、配额、权限与后代都要另外买（[@def-10.1.1]、[@def-10.1.2]）。
- EOF 的条件是所有写端关闭加缓冲读完，不是某个进程退出（[@def-10.2.1]、[@ex-10.2.1]）。
- 线格式与内存布局解耦，短读是常态，帧首之后的 EOF 必须报截断（[@def-10.3.1]、[@def-10.3.2]）。
- 每次启动与持久 worker 是两个估计对象，1.219 ms 是完整生命周期的批均值（[@def-10.4.1]、[@def-10.4.2]）。
- 先 wait 后读会把互等放大成背压停滞，有限保留要读完全部字节、只存前缀（[@def-10.5.1]、[@def-10.5.2]）。
- ns/输出字节是聚合吞吐倒数，均值差落在标准差之下时只能写「同样排空、少保存」（[@def-10.6.1]、[@ex-10.6.1]）。
- 超时、终止、回收与排空是四段独立预算，重启后要用代际匹配执行实例（[@def-10.7.1]、[@def-10.8.1]）。

:::
