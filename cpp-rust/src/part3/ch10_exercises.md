## A 组 · 概念（1–7）

::: ex A1 · 能杀谁，不能杀谁（主线 ①） {#ex-10.A.1}

「父进程可以杀掉直接子进程」这句话里的「直接」限制了哪些对象？孙进程为什么可能比直接子进程活得更久，它又为什么会影响父进程读到 EOF？

::: sol 解答

限制在「父进程可请求操作系统终止、并对其执行 wait 回收」的那一层。孙进程不是直接子进程，直接子进程退出后它可能继续运行，并继续持有继承来的管道写端；写端没关，EOF 就不到（[定义 10.1.1](ch10.md#def-10.1.1)、[定义 10.2.1](ch10.md#def-10.2.1)）。所以「可以杀掉」只覆盖一层，后代治理要另设策略。
:::

:::

::: ex A2 · 四行边界表怎么读（主线 ④） {#ex-10.A.2}

边界表有四行：Future 任务、操作系统线程、独立进程、受治理的进程树或容器。哪几行属于隔离边界、哪一行才进入治理边界？「容器比进程更安全」这句话的肯定部分与限定部分各是什么？

::: sol 解答

前三行是隔离边界，第四行才进入治理边界（[定义 10.1.2](ch10.md#def-10.1.2)）。肯定：容器确实带来后代、配额、权限的策略面。限定：最后一列写明「任意平台自动等价的安全性」不在保证之内——策略是否生效取决于运行时、内核与配置。另外「进程之间绝不共享任何资源」也是错的：映射、文件、套接字都能显式共享。
:::

:::

::: ex A3 · 为什么不用 sh -c（主线 ④） {#ex-10.A.3}

实验用明确的可执行文件路径与逐个参数启动 helper。这消除了哪一层风险？即使改成逐个参数，10.1.3 列出的策略清单还剩下哪几项？

::: sol 解答

消除的是 shell 重新解释元字符这一层。剩下六项仍要一次补齐：可执行文件允许列表、参数数量与长度、工作目录与环境变量、输入大小与编码、输出上限与敏感信息处理、权限与网络与文件访问策略（[例 10.1.1](ch10.md#ex-10.1.1)）。逐个参数不等于任意参数都安全，目标程序仍可能把参数理解为路径、选项或危险操作。
:::

:::

::: ex A4 · 审一份写错的线协议表（主线 ②） {#ex-10.A.4}

有人交来这样一张 24 字节表：version 写「1 或 2 都接受」；flags 写「任意位，含义由业务决定」；frame length 写「等于原生 size，16」；request_id 写「本机端序」。按 10.3.1 与 10.3.3 指出四处错误，并写出接收端对每种情况应有的行为。

::: sol 解答

① version 必须为 1，未知版本不「尽量兼容」地继续处理，应返回 `InvalidData`。② flags 当前必须全部为 0；要启用某位必须升版本，因为旧解码器只认 flags 全 0。③ frame length 必须为 24，不是原生 size 16；16 是内存布局，不是线格式。④ request_id 必须是小端 u64，不能依赖本机端序。接收端顺序固定：先核 version、flags、length，再解释 id 与 value，解码顺序本身就是信任边界（[定义 10.3.1](ch10.md#def-10.3.1)）。
:::

:::

::: ex A5 · read_frame 的三条出口（主线 ①） {#ex-10.A.5}

`read_frame` 为什么先读 1 个字节、再 `read_exact` 剩下 23 字节，而不是一次 `read_exact` 24 字节？写出这个函数的三种正常出口与两类错误出口。

::: sol 解答

先读 1 字节是为了区分「帧边界上的干净 EOF」与「帧中途截断」：一次 `read_exact` 24 字节在流空时会直接报错，把「对端按协议结束」也变成失败。三种正常出口：首字节 read 返回 0 → `Ok(None)`；首字节到手、剩余 23 字节读满、`decode` 通过 → `Ok(Some(Frame))`；read 返回 `Interrupted` → 继续循环。错误出口：首字节之后中途 EOF → `UnexpectedEof`；头部校验失败 → `InvalidData`（[定义 10.3.2](ch10.md#def-10.3.2)）。
:::

:::

::: ex A6 · 背压停滞的三个条件（主线 ①） {#ex-10.A.6}

背压停滞需要哪三个条件同时成立？为什么「只排空 stdout，然后等退出」仍然可能被卡住？解开回路的最小改动是什么？

::: sol 解答

条件：管道缓冲已满、写方在等空间、读方在等别的事件（例如子进程退出）。只排空 stdout 时，stderr 仍会独立地写满、独立地卡住写方（[定义 10.5.1](ch10.md#def-10.5.1)）。最小改动：让 stdout 与 stderr 各自有并发读任务，读者不等退出；任何一方换动作都能解开回路，但只有读方持续读才不依赖运气。
:::

:::

::: ex A7 · 超时三件事分别归谁（主线 ①） {#ex-10.A.7}

把「不再接受正常结果」「外部工作停止或受控收尾」「回收直接子进程与本地 I/O 任务」三件事各配一个对象、一个可观察的成功标志，并说明为什么把 Future 放进 timeout 只完成了一部分。

::: sol 解答

结果预算归调用方：成功标志是返回值的语义已定（超时或结果）。外部进程归 helper：成功标志是 wait 取回状态。内核与本地资源归父进程：成功标志是 `child.wait()` 返回、读取任务被等待或观察到取消（[定义 10.7.1](ch10.md#def-10.7.1)）。`timeout` 只作用在 Future 上，默认丢弃 `Child` 句柄不意味着子进程终止；即使开 `kill_on_drop`，也不能代替可观察的 wait 成功。
:::

## B 组 · 推理（8–15）

::: ex B8 · 两个业务该不该上进程池（主线 ④） {#ex-10.B.8}

两个候选业务：(a) 每次执行以秒计的视频转码；(b) 高频小工作、稳态为主的哈希查询。用 10.4.7 的判定流程各给方向，并写出你还必须追问的两项信息。

::: sol 解答

(a) 每次执行数秒时，节省 1 ms 可能不是主要问题，per-spawn 的干净状态与独立故障域更值；还免去复用带来的状态保留、故障波及在途、请求关联、内存增长、更新回收五条责任。(b) 高频小工作、稳态为主，才轮到持久 worker 摊薄初始化与退出。判定流程要先定三件事：隔离要求、工作量、故障模型；工作量已给，所以还要追问隔离要求（是否要每次干净状态）与故障模型（一个 worker 挂掉愿意连累多少在途请求）。
:::

:::

::: ex B9 · 「少保存」到底省了什么（主线 ②） {#ex-10.B.9}

prefix128 与 retain-all 的吞吐几乎一样。那「只保留 128 字节前缀」省下的到底是什么？把结论写成能进设计文档的两句，并指出 4GiB 输出场景下还缺哪一项策略。

::: sol 解答

省下的是保留内容与相应的资源风险，不是带宽：两个 case 都把 4MiB 完整排空，读取与复制照做（[定义 10.6.1](ch10.md#def-10.6.1)）。可写的两句：① 固定前缀正确完成了同样的排空工作，逐项校验通过；② 保留长度有上界，报告体积与内容风险不随输出增长。缺的是总输出量策略：超过某个 total 后终止工具，同时继续执行回收协议；本轮没有实现这项策略（10.6.5）。
:::

:::

::: ex B10 · 两种 EOF 迟到怎么分（主线 ①） {#ex-10.B.10}

两次事故的症状相同：直接子进程已退出、每流 2097152 字节都读到了、就是没有 EOF。一次是 inherit 模式（helper 启动一个寿命固定为 2 秒的后代并继承 stdout/stderr）；一次是 CLOEXEC 创建窗口里被无关进程复制走了捕获 FD。用哪些观察区分这两者？为什么不能一律伪造 EOF 了事？

::: hint 提示

看写端是从哪条路径进去的：工具的 fd1/fd2，还是一个与工具无关的私有 FD。gate 记录里 pipe 创建方式与 flags 值、lsof 里有没有额外 PIPE，各能说明什么？

:::

::: sol 解答

看三处。① 写端来源：inherit 是工具主动经 fd1/fd2 正常继承，CLOEXEC 泄漏是无关私有 FD 被复制。② gate 记录：原版见 `pipe` 和 flags=0，原子版见 `pipe2` 和 flags=1。③ lsof：原版后代有额外 PIPE、原子版无额外 PIPE（10.7.8 的表）。两种成因不同：前者是输出端点寿命被主动延长，后者是无关 FD 泄漏；一律伪造 EOF 会把「对端在帧中间消失」「后代仍在写」这些真实信息一起抹掉，诊断从此不可用。
:::

:::

::: ex B11 · 顺序反过来写会怎样（主线 ①） {#ex-10.B.11}

把 `Session::finish` 改成先 `self.child.wait()?`、后 `drop(self.input.take())`，编译通过。对这个按帧循环的持久 worker，运行时会发生什么？为什么编译器不报错？

::: sol 解答

父进程在 wait 上等 worker 退出；worker 在 stdin 帧边界等下一帧或 EOF，而 EOF 要等所有写端关闭，其中一个写端正握在父进程手里。双方各等对方先动，wait 永远不返回。这不是内存安全问题，borrow checker 只检查本地所有权，检查不到两个进程之间的等待关系；只能把「先关输入、再等退出」写成固定顺序。
:::

:::

::: ex B12 · cap 满了能不能停读（主线 ①） {#ex-10.B.12}

采集器已经存满 128 字节前缀，此时停掉读任务能省带宽，看起来无风险。指出它的后果，并说明想真正少读时唯一诚实的杠杆是什么。

::: sol 解答

停读之后，子进程写满管道缓冲就被堵住，到不了退出点，父进程的 wait 也永远不返回——这就是 10.5.2 重现的停滞（[思考 10.5.1](ch10.md#think-10.5.1)）。必须区分「还要继续排空」与「还要继续保存」：继续读全部字节，只保留固定前缀。想真正少读，唯一诚实的杠杆是换终止策略：超过某个总量后终止工具，同时继续回收；该策略本轮没有实现。
:::

:::

::: ex B13 · 8 个 worker 能线性扩展吗（主线 ②） {#ex-10.B.13}

有人拿 5.484 µs 除以 8 得到 0.69 µs/请求，准备写进容量规划。列出这个推算缺的至少三层，并说明要补什么实验才能回答扩展性问题。

::: hint 提示

先问：本轮 persistent case 里同时有几个在途请求？协议里 request_id 被用来配过乱序响应吗？父进程分发这一段有没有排队？

:::

::: sol 解答

缺：① 没有并发在途请求，串行往返里没人用 request_id 配过乱序响应；② CPU 核心数、管道缓冲、父进程分发与排队都没有建模；③ worker 冷热状态与共享父进程争用会引入非线性，稳态串行数据无法外推。要补一个多 worker 实现：每 worker 输入队列、多路在途与乱序响应关联、父进程分发的排队计时点、每段队列的准入容量，并重新定边界表（[思考 10.4.1](ch10.md#think-10.4.1)）。
:::

:::

::: ex B14 · 重试为什么扣了两次（主线 ①） {#ex-10.B.14}

协议写「写入失败后重试一次」。对一个扣费操作，什么情况下会扣两次？只调大超时或减少重试次数能修好吗？给出两种结构性修法。

::: sol 解答

第一次请求已经到达 worker、扣费已提交，失败发生在响应回程；父进程看到「写失败」于是重试，第二次又成功，用户被扣两次（[思考 10.8.1](ch10.md#think-10.8.1)）。调超时或重试次数都绕不开这个窗口。两种修法：请求携带幂等键由服务端去重；把「提交」与「确认」拆成两步，让父进程能查询上一次结果。
:::

:::

::: ex B15 · macOS 的管道数字能证明 Linux 吗（主线 ④） {#ex-10.B.15}

同事写：「本章测得 5.484 µs，可作为 Linux 上进程间共享 futex 的成本参考。」按 10.8.7 与 10.9 的来源纪律，这句话错在哪两层？给出允许的说法。

::: hint 提示

一层是机制不同，一层是证据来源不同。本章有没有 Linux perf、strace 或 PMU 报告？

:::

::: sol 解答

第一层：平台机制不同，本章没有执行 Linux 共享 futex、cgroup 或 namespace 实验，macOS 管道结果不能平移成 Linux 成本（10.8.7）。第二层：5.484 µs 是 macOS ARM64 上单 worker 串行往返的批均值，属本轮实验的有限结论，不是任何「共享内存成本」的测量。允许的说法：本章的 5.484 µs 只覆盖本机 macOS ARM64、管道传输、单 worker 一请求一响应；Linux 侧需要另做实验并按新边界报告。
:::

## C 组 · 实操（16–20）

实验包与第 9 章共用 `bench/runtime-lab/`。这一组要求真的写、真的跑、真的把观察写成可复核的句子。

::: ex C16 · 设计一条带请求 id 与代际的线协议（主线 ②） {#ex-10.C.16}

10.3.1 的 24 字节帧有 request_id，却没有 worker 代际。现在要为多 worker 池扩一版协议，要求：能关联乱序响应；能拒绝上一代 worker 的晚到响应；旧解码器遇到新帧必须明确拒绝而不是猜。请给出：完整字节表（偏移、长度、字段、约束）、解码顺序、父进程请求表的最小设计（键、容量、超时清理）、三条破坏性测试向量。

::: hint 提示

当前版本把 flags 预留位定死为全 0，所以加字段不能偷偷借 flags 位——那要先升版本。代际是每次重启递增的 u64，放在哪个偏移最省事？

:::

::: sol 参考路径

版本升到 2，帧长 32 字节。字节表：0–2 version，little-endian，必须为 2；2–4 flags，必须全 0；4–8 frame length，little-endian，必须为 32；8–16 request_id；16–24 value；24–32 generation，little-endian u64。解码顺序仍是先核头再解载荷：version → flags → length → request_id → generation → value；version 不为 2 一律 `InvalidData`，不做「尽量兼容」。请求表键为 `(session, generation, request id)`，容量设上限，超时项按期限清理；响应的代际与本代不匹配就丢弃并记一条诊断，不当作当前请求结果（[定义 10.8.1](ch10.md#def-10.8.1)）。至少三条向量：① version=1 的旧帧必须拒；② length=31 必须拒；③ generation 高字节非零的帧验证小端解析；再加一条「上一代响应」验证拒收。注意本轮没有实现多路关联，这是设计题，不是已交付实现。
:::

:::

::: ex C17 · 双路管道只读一路会发生什么（主线 ①） {#ex-10.C.17}

你的采集器对 helper 只起了 stdout 的读任务；stderr 端点 `take()` 出来之后既不读也不关，随后 `await wait`。helper 会先向 stdout 写 2MiB、再向 stderr 写 2MiB。请预测现象、写出能在 30ms 内判定停滞的实验步骤、解释「等 wait 返回后再读 stderr」为什么救不了，并给出修法与要观察的字段。

::: hint 提示

先画三条线：helper 的写入点、缓冲的占用、父进程的等待点。stderr 那条线的读者是谁？如果读者在 wait 之后才出现，wait 之前谁在推进它？

:::

::: sol 参考路径

预测：stdout 2MiB 能读完，stderr 逐渐填满内核缓冲；helper 阻塞在 stderr 的 write 上，到不了退出点；父进程等 wait，双方互等，形成与 10.5.1 同构的回路。步骤：起 helper，先读 stdout 一个字节确认已进入输出阶段，然后停止读 stderr、只等 wait；设 30ms 观察窗口，超时未完成即判定停滞，随后 kill 并 wait 直接子进程，避免永久挂起。30ms 只是观察窗口，不是管道容量。等 wait 返回后再读救不了：wait 永远不返回，读代码根本执行不到。修法：stdout 与 stderr 各自起并发排空任务，cap 满了继续读；观察四个字段 total、prefix、eof、reader_errors，外加退出状态与 `timed_out`（[定义 10.5.1](ch10.md#def-10.5.1)、[定义 10.5.2](ch10.md#def-10.5.2)）。
:::

::: ex C18 · 按出口检查复验，并保护归档（主线 ④） {#ex-10.C.18}

::: ex C19 · 给 4GiB 输出写采集配置（主线 ④） {#ex-10.C.19}

线上工具偶发输出 4GiB 日志。按 10.5、10.6 写一份采集配置：cap 取多少、total 怎么计、超量怎么办、报告怎么措辞。并指出这份配置里哪一项本轮实验没有实现，不能假装已有。

::: sol 参考路径

cap 取小前缀（128 字节量级），prefix 长度受 cap 约束；total 用 checked_add 持续计数，即使 keep 为 0 也继续读；超过阈值后终止工具，并继续走 10.7 的回收协议——这一项本轮没有实现，不能写成「已支持」。报告措辞：`eof=true` 时可写「该流排空 N 字节且读完」；`eof=false` 时只能写「至少已排空 N 字节，尾部未知」，同时带 prefix 长度与 reader_errors。cap 不是 RSS 上限，也不是杀进程开关（[定义 10.5.2](ch10.md#def-10.5.2)、[例 10.5.1](ch10.md#ex-10.5.1)）。

::: ex C20 · 三份期望 Report（主线 ①） {#ex-10.C.20}

为三种 helper 写出你期望的 Report 字段与一句允许的结论：① 读到 EOF 后正常退出；② inherit 模式，启动 2 秒后代并立即 exit(0)；③ 不按 EOF 退出、必须靠 deadline 终止。字段至少覆盖 `timed_out`、`exit_code`、两流 `eof`、`reader_errors`。

::: sol 参考路径

① `timed_out=false`，`exit_code=Some(0)`，两流 `eof=true`，`reader_errors` 为空；可写「直接子进程已回收，两流读完」。② `timed_out=false`，`exit_code=Some(0)`，两流 `eof=false`，`reader_errors` 各含一条 grace 到期；可写「直接子进程已回收，两流在 grace 内未观察到 EOF，保留部分排空状态」，不能写「后代已终止」。③ `timed_out=true`，退出码由 wait 返回、不能预先假定为 0，若为 `None` 也不等于 0；两流 `eof` 视输出是否在 grace 内读完而定，grace 到期则记 reader_errors。三份报告的差别必须逐字段写出，不能用「退出码 0」代替 EOF 声明（[例 10.7.1](ch10.md#ex-10.7.1)、[定义 10.7.2](ch10.md#def-10.7.2)）。

## 批改最常给的三条意见

1. **把「能 kill」当成治理完成。** 缺 wait、缺排空、缺后代清理。先照 10.7.2 的顺序补齐，再改结论句。
2. **口径错位。** 1.219 ms 写成进程创建成本、批 p99 写成请求尾延迟、ns/输出字节写成单字节延迟。先改单位与对象，再看数字。
3. **结论超出证据。** 0.001 的均值差写成 0.2% 加速、`eof=false` 的 total 写成总量、一次 30ms 观察写成管道容量。补 sd、补「至少已排空」、补「本机本实验」。
