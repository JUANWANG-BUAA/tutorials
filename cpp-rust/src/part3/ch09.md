## 9.1 从一个通知位到任务状态机 {#sec-cpp-rust.3.9.1}

本节回答一个问题：**一个只会说「再叫醒一次」的通知位，怎样长成能同时照顾几百个任务的状态字？**第 8 章那个单 Future 驱动器只需要一个布尔位；把它的代码复制一百份再开一百条线程，得到的是并发，不是执行器。多出来的难点不在通知本身，而在「谁有资格动这个 Future，以及谁替它保管存活责任」。

::: preview 先抓住一件事

**从队列里取出一个任务，不等于获得 poll 它的授权。**这两件事在状态字里是两个独立的责任：一个管「谁正在跑」，一个管「谁的唤醒还没被兑现」。把它们当成同一个锁位，是本节要拆开的第一个错误，也是 9.2 至 9.8 全部讨论的地基。
:::

### 9.1.1 两个词先钉死：poll 与驱动

**poll** 是执行器拿着一个 `Waker` 去问一次 Future：「你现在能往前推进吗，还是继续等」。它是一次普通的函数调用，不是线程，也不保证返回时任务有了进展——返回值只有 `Pending`（还得等）和 `Ready`（做完了）两种。**驱动**（drive）指执行器反复 poll 同一个 Future，直到它返回 `Ready` 并把输出交出去的那一整个过程；第 8 章的 `block_on` 就是一个最小的驱动器（[@def-8.1.1]）。**执行器**（executor）则是同时驱动许多 Future 的那个循环连同它的队列、唤醒源和任务存储。

有了这两个词，就能说清「复制一百个 `block_on`」为什么不算执行器：那条路把并发上限交给线程数、把栈空间交给每条线程的栈、把切换时机整个交给操作系统。用户态多任务要的是相反的东西——任务之间切换不经过内核，跨 await 的状态由 Future 自己承载，切换时机由程序决定。代价是：切换时机不再是白拿的，得由状态字、队列和一套通知协议自己挣出来。

### 9.1.2 多任务要额外回答的六个问题

第 8 章的驱动器只需要维护一个 Future，它的通知位表示「再 poll 一次可能有用」。同时维护几百个 Future 时，用户要额外回答一组问题，每个问题最后都会落到状态字的某一位上。

1. 哪些 Future 需要再次 poll？
2. 哪个 worker 获得 poll 的独占权？
3. Future 正在运行时到来的 wake，由谁负责入队？
4. Future 完成后到来的旧 wake，如何避免访问已释放存储？
5. `JoinHandle` 与队列引用分别维持什么生命周期？
6. 取消什么时候才能真的执行析构？

这些不是「把 `Vec` 换成无锁队列」就能自动获得的性质。队列正确性与任务生命周期正确性是两份证明：队列中的元素必须携带足以维持任务存活的所有权，而弹出任务也不代表立即获得合法的可变访问。[@ex-9.1.1] 会把这条分界压到一个具体的交错上。

### 9.1.4 状态位不是五个独立布尔量

一个初学者最容易写出的「执行器」是：给每个任务一个 `is_running` 布尔、一个 `is_notified` 布尔、一个 `is_completed` 布尔，各自用原子类型存着。这个形状看似清晰，实际上让每一位都能被单独读写，于是任何两位之间的竞态都要靠额外代码去堵。Tokio 的做法相反——把这些条件压进**一个**机器字，用一次读-改-写（RMW）原子操作同时读出全部条件、算出新条件、写回，并在写回失败的瞬间知道「状态在我看的那一刻之后变了」。

::: def 定义 9.1.1 · 任务状态字 task state word {#def-9.1.1}

**任务状态字**是一个把「运行权、是否完成、是否已被通知、是否被请求取消、有没有人等待结果，以及引用计数」打包在一起的原子整数。它的关键性质不是「字段多」，而是**任何一次状态判断和状态改变都发生在同一次原子操作里**：不存在「我先读到没在跑，再单独写下我开始跑」这种中间可以被插队的两步。

:::

该版本的任务状态字同时记录：

| 成分 | 含义 | 需要共同维持的不变量 |
|:--|:--|:--|
| RUNNING | 某个线程取得运行权 | 同时不能有第二个poll所有者 |
| COMPLETE | 任务已经完成 | 不再重新执行Future |
| NOTIFIED | 已有通知责任 | 重复wake不能无限复制队列项 |
| CANCELLED | 取消请求已经登记 | 请求本身不是抢占 |
| JOIN_INTEREST / JOIN_WAKER | 结果观察者及其通知 | 输出与等待者寿命配合 |
| 引用计数部分 | 任务存储所有权 | 最后引用释放后才能回收 |

不能把其中任何一位脱离引用计数谈正确性。例如「已经通知」可能对应一个队列引用：消费该通知时，运行者接管其生命周期责任；如果运行失败，也必须正确消费或转交该引用。少还一次，任务存储永远回收不了；多还一次，正在被别人 poll 的存储可能被提前释放——两头都不是「加个锁」能补回来的。

::: def 定义 9.1.2 · 运行权与通知责任 run permission, notification duty {#def-9.1.2}

**运行权**保证 Future 不会被两个线程同时 poll：它在任意时刻至多属于一个 worker，取得它是一次原子抢位的结果。**通知责任**保证发生有效 wake 之后，未来有人重新检查这个 Future：它是一笔「欠一次 poll」的账，可以挂在队列项上，也可以挂在正在运行的那个 worker 身上。二者可以同时存在（正在跑的任务被叫醒），但不能被当成同一个锁位。

:::

::: ex 例 9.1.1 · 弹出队列项之后，谁有权 poll {#ex-9.1.1}

某个任务在队列里，状态字显示 `NOTIFIED` 但没有 `RUNNING`。worker A 把它从队列弹出，正准备 poll；此刻 worker B 因为窃取也拿到了同一任务的另一个队列引用，同样准备 poll。按[@def-9.1.1]与[@def-9.1.2]说明：「弹出」这个动作给出了哪些信息、哪些必须由状态字给出；如果 A、B 各自先读状态再抢位会怎样。

::: sol 解答

「弹出」只给出**候选**信息：这个任务曾经被通知、值得再看一次。它不给出独占权，也不给出「通知已被兑现」的确认。独占 poll 必须由状态字上的一次 RMW 给出——谁把那一位从「未运行」翻转成 `RUNNING` 成功，谁才有资格进入；另一方看到翻转失败，就只能改走别的分支（重排、放弃或合并通知）。若 A、B 各自先读后写，两次读都可能读到「未运行」，两次写都写成「运行」，结果就是同一个 Future 被两个可变引用同时 poll。这是内存不安全，不是性能退化，也正是[@def-9.1.1]要求「判断与改变在同一步里完成」的原因。

:::

:::

### 9.1.6 从原子修改序到生命周期

Tokio 的源码注释明确把状态转换放在 RMW 操作上，这给出的是**状态字内部**的修改顺序（[@def-7.2.1]）。但仅有修改顺序并不能解释全部内存安全：修改顺序只说明「这一位的值按什么次序变化」，它不告诉你 Future 的字节归谁、输出什么时候可以被读、存储什么时候可以被释放。按[@def-7.1.3]的分层，这里缺的是把 Future 存储、输出存储和引用释放接到具体转换上的那一层证明。

本章只追踪相关责任，不给出「一个 AcqRel 就证明执行器正确」的口号。读者应能指出至少三个不同对象，它们可以在一个分配里协同布局，逻辑上却各有自己的初始化、访问与销毁阶段。

- 被 poll 的 Future 存储：只有持有运行权的那次调用能以可变引用接触它（[@def-8.1.2]）。
- 对执行器可见的通知对象：它代表[@def-9.1.2]里那笔还没兑现的账。
- 等待结果的 `JoinHandle` 状态：它决定输出什么时候被读走、观察者什么时候被叫醒。

::: def 定义 9.1.3 · 任务单元 task cell {#def-9.1.3}

**任务单元**指执行器为一个任务准备的那一份存储整体：状态字、Future 本体、输出区域、等待者的 `Waker`，以及把这几部分黏在一起的那份引用计数。本节的要点是——**一个分配不等于一个语义对象**。队列项可以只是任务单元的一个引用，窃取迁移的是引用而不是 Future 的字节，而「最后一个引用释放」与「Future 已被 poll 完」是两件事，必须各自由状态字的转换来保证。

:::

这三个对象混在一起，最容易出的错就是把「拿到了队列项」当成「拿到了三个对象的访问权」。[@ex-9.1.1]已经拆过第一层，剩下的两层（输出何时可读、存储何时可释放）分别在 9.2 的取消与 9.4 的 `JoinHandle` 尺寸讨论里落地。

::: think 思考 · 用一把互斥锁保护整个状态字行不行 {#think-9.1.1}

既然[@def-9.1.1]的价值在于「判断与改变在同一步里完成」，那么更直白的做法是：给任务单元配一把锁，每次读写状态都先加锁。语义上似乎更保守，为什么实现里不这样设计？

::: sol 解答

语义上确实能保住独占，代价在另外三处。第一，wake 的调用方是任意的——可能是 I/O driver 线程、别的 worker，甚至是不能阻塞的上下文；把「登记一笔账」变成一次可能等待的锁竞争，等于让唤醒路径背上调度风险。第二，锁只保护状态字，仍然不回答「Future 的字节现在能不能写」「最后一个引用是谁放的」，[@def-9.1.3]的三个对象还得各自再加锁，加锁次序稍有不慎就与窃取协议互相死锁。第三，性能形态变了：poll 前后各一次进锁出锁，正是 9.5 里那些会被 quantum 放大或摊薄的成本。

RMW 不是为了炫技，是因为这里需要的恰好是「一次比较并交换」而不是「一段临界区」。判断类接口时同理：先问要保护的是**一个字的值**还是**一段过程**，再选原子或锁（对照[@def-7.1.1]）。

:::

:::

### 9.1.7 小结与常见错误

**小结。**① poll 是一次函数调用，驱动是反复 poll 到 Ready 的整个过程（[@def-8.1.1]）；② 从队列弹出任务只给出候选，独占 poll 必须由状态字的一次 RMW 给出（[@def-9.1.1]、[@ex-9.1.1]）；③ 运行权与通知责任是两条独立的账，可以同时存在，不能压成一个锁位（[@def-9.1.2]）；④ 一个任务单元里至少有三个语义对象，修改顺序不等于生命周期证明（[@def-9.1.3]、[@def-7.1.3]）；⑤ 一切结论绑定 Tokio 1.54.0 的指定源码段，不是稳定 ABI。下一节 [9.2 并发 wake、重复入队与取消边界](#sec-cpp-rust.3.9.2) 把这两条账放到具体交错里检验。

::: errata 常见错误清单（9.1 节）

E-a **把队列弹出当成 poll 授权。**弹出给的是候选，独占权只能来自状态字（[@ex-9.1.1]）。

E-b **先读状态再单独写状态。**两步之间可以被插队，两个 worker 会同时进入同一个 Future（[@def-9.1.1]）。

E-c **把运行权与通知责任合并成一位。**正在跑的任务被叫醒时两者同时存在，合并就丢掉一次 poll（[@def-9.1.2]）。

E-d **脱离引用计数谈某一位的正确性。**「已通知」可能挂着一个队列引用，消费它要接管生命周期（[@def-9.1.3]）。

E-e **用「用了 CAS」代替机制说明。**说不清 CAS 作用在哪一位、前提是什么、引用归谁，就还没理解（[@def-7.1.3]）。

E-f **把版本内实现当成公共 ABI 复用。**本章只核读 1.54.0 的指定范围（9.1.3）。

:::

::: method 即时自测 · 9.1

**第 1 题 · 记忆**　用一句话分别解释 poll、驱动、执行器，并说出任务状态字的关键性质。

## 9.2 并发 wake、重复入队与取消边界 {#sec-cpp-rust.3.9.2}

本节回答一个问题：**把 9.1 那两条账放到真实的线程交错里，哪一步做错会丢进展、哪一步做错会丢内存安全？**上一节给的是静态规则；这一节给的是时序——worker 与资源线程同时在动同一个任务时，协议必须同时对两边给出答案。

::: preview 先抓住一件事

**「合并通知」省掉的是再次入队，省不掉的是同步义务。**重复 wake 不必产生第二个队列项，但发起 wake 的那条线程在此之前可能还发布过资源状态；如果因为「不用排队」就顺手删掉全部同步效果，被省掉的就不只是队列操作，还有[@def-7.2.2]那条边。
:::

### 9.2.1 一个具体交错：poll 正在进行时来的 wake

考虑资源线程与 worker 的交错，左边是执行器所在的线程，右边是提供 I/O 完成通知的线程。

```text
worker                         resource thread
取得RUNNING
清除当前通知
poll(resource)
                               资源完成
                               wake_by_ref()
poll返回Pending
检查NOTIFIED
将任务重新安排
```

这个交错里有两处相反的诱惑。**若 worker 在 poll 之后直接把状态设为 idle**，而不检查并发通知，就会丢掉进展：那次 wake 发生的时刻正好落在「通知已被清除」与「poll 已返回」之间，登记下来的账没人认领，Future 从此没人再 poll——这类缺陷叫**丢失唤醒**（lost wake-up），它不崩溃、不报错，只是永远不前进。**若资源线程不管任务是否运行都立即执行 poll**，就会同时存在两个可变引用，那是内存不安全。正确协议必须在状态转换里区分这两种情形：[@def-9.1.2]的运行权负责第二件事，通知责任负责第一件事。

::: def 定义 9.2.1 · 丢失唤醒 lost wake-up {#def-9.2.1}

**丢失唤醒**指一次有效的 wake 已经发生，却没有被任何后续 poll 兑现，任务因此永久停在没人再看的状态。它的判定标准不是「有没有排过队」，而是「有没有人欠着一次 poll 且这笔账不会消失」：账要么挂在队列项上，要么挂在持有运行权的 worker 上，两边都不挂就是丢失唤醒。

:::

Tokio 1.54.0 的 `transition_to_notified_by_ref` 可概括为：

| 观察状态 | 动作 | 是否产生新的提交责任 |
|:--|:--|:--|
| complete | 不重新执行 | 否 |
| already notified | 合并通知并保持同步关系 | 否 |
| running | 设置 notified | 由当前运行者负责 |
| idle 且未通知 | 设置 notified 并增加相应引用 | 是 |

这是源码逻辑摘要，不是可替换的伪实现。实际代码还处理引用计数与失败重试，不能照着四行表格写一个裸指针队列并宣布正确。表格里最容易被误读的是「是否产生新的提交责任」这一列：它的含义是**这次 RMW 是否把一个还没有兑现的账交给了某个明确的责任人**——「否」表示账早就在那儿（或者任务已经结束，账不再有对象），不是表示这次 wake 什么都不必做。

::: ex 例 9.2.1 · 四种观察状态各自欠谁 {#ex-9.2.1}

就着上面那张表回答：① `complete` 分支为什么不重新执行 Future，却不允许把这次 wake 当成访问存储的许可；② `running` 分支里设了 notified 却「由当前运行者负责」，这个责任转移发生在哪一步；③ 第三行和第四行的差别是什么？

::: sol 解答

① `complete` 只保证不再重新执行 Future；旧 wake 的到来者可能还握着 `Waker`，它能不能读输出、能不能触发观察者，取决于 `JoinHandle` 那侧的账（9.1.6 的第三个对象），跟「要不要重跑」无关。所以「不重跑」和「可以安全释放」是两次不同的判断。② 责任转移发生在 worker 退出 poll 时的那次 RMW：它读到 notified 已经被登记，于是按[@def-9.1.2]把账转成一次重新安排，而不是先把状态清成 idle。③ 差别在**谁来兑现**：running 时账交给正在跑的那个人（不新增队列项，也不新增引用），idle 且未通知时账必须由队列项携带，所以要增加相应引用——这正是[@def-9.1.3]里「一个分配不等于一个语义对象」的具体体现。

:::

:::

### 9.2.2 「合并」不意味着没有内存序义务

已经被通知的任务再收到一次 wake，可能不必再次入队。但发起 wake 的线程此前也可能发布了资源状态——它先把缓冲区写完，再调用 `wake_by_ref()`。不再入队，不代表可以删除所有同步效果：写缓冲区这件事仍然需要一条能被后来者看到的边。

被核读版本的源码在 already-notified 分支中特别说明了这个问题：它仍需要与后续运行转换配合的 Release 效果。这正是第 7 章的知识进入执行器内部的具体位置。

错误的推理是：

> 反正任务已经排队，再来的 wake 什么都不用做。

正确的问题是：

> 哪个后续操作会观察到这次 wake 之前的资源更新？

两个问法差别很大。第一个问的是**队列项**，第二个问的是**可见性**。[@def-7.2.2]要求 Release 一侧的写与 Acquire 一侧的读连成一条同步边，这条边的载体可以是队列项，也可以是别的——但边必须存在，而且要说清由谁来提供。有时资源自身的同步协议也会提供边；这不允许执行器随意削弱它承诺的通知协议。多个协议组合时，要逐个说明各自承担的同步责任，而不是笼统写一句「都会同步好的」。

::: def 定义 9.2.2 · 通知的同步义务 notification obligation {#def-9.2.2}

一次 wake 承担两件事：**进展义务**（保证未来有人再 poll 这个 Future）与**可见性义务**（保证 wake 之前发布的资源状态，能被那次 poll 观察到）。合并通知可以省掉第一项里「再一次入队」的动作，但省不掉第二项；把两者混为一谈，就会在「不必排队」的掩护下删掉 Release 语义。

:::

::: ex 例 9.2.2 · 少写一次入队，能不能少写一次同步 {#ex-9.2.2}

资源线程把 `body` 写进共享缓冲区后调用 `wake()`；此时任务已经处于 `NOTIFIED`，走的是合并分支。假设实现者在合并分支里省掉带 Release 的那次原子状态写，只做一次 relaxed 读取就返回。请按[@def-9.2.2]判断谁会看到什么，并给出修复方向。

::: sol 解答

进展义务没有被破坏——账早就挂着，将来一定有人 poll。坏在可见性义务：worker 侧那次读取拿不到与本次资源发布相配的 Acquire 关系，`body` 的写入可能在它看来还没发生，于是 poll 读到旧字节。这类缺陷在 x86 上常常沉默，在弱序架构上偶尔复现，正是[@def-7.1.1]里「数据竞争不一定表现为崩溃」的执行器版本。修复方向有两个：合并分支仍然发布带 Release 的状态写，或者证明资源自身的同步协议已经提供这条边并在注释里点名——两者都行，含糊不行。

:::

:::

### 9.2.3 Pending 不是睡眠指令

`Pending` 只是这一次 poll 没有产出最终结果，它不携带任何「现在要去睡觉」的含义。Future 可以因为 I/O、锁、通道、计时器或主动让出而 `Pending`，这些原因对应完全不同的唤醒来源，也对应执行器完全不同的下一步。

执行器收到 `Pending` 之后可能有三种走法：立即改 poll 队列里的另一个任务；发现所有任务都在等外部事件，于是进入 driver 等待（driver 指负责向内核询问「哪些 fd 已经可读可写」的那个组件）；或者发现此前已经登记了通知，于是马上重新安排同一个任务。三条路径的内核参与度完全不同——第一条一次系统调用（用户程序停下来请内核代做一步操作）都不必有。

因此一次 `Pending` 不能直接换算成一次内核上下文切换（两者各付什么，见[@def-9.2.3]）。同样，一次 wake 不能直接换算成一次线程唤醒：很多 wake 只影响已有运行线程的本地工作集合，线程本来就在跑，只是多了一项可做的活。9.5 的 benchmark 之所以把 `yield_now` 的频率单独列为实验因素，就是因为「让出」落在这三条路径的哪一条、附带多少次 driver 检查，直接决定成本（[@def-1.1.3]的计时集合问题在这里同样成立）。

::: def 定义 9.2.3 · 内核任务切换与 poll 返回的差别 context switch versus poll return {#def-9.2.3}

一次**内核任务切换**至少要付：把当前执行位置的一组寄存器（CPU 内部最快的那一小批格子，程序的状态大半住在这里）存进该任务的控制块、换到另一个任务的栈上、恢复那一组寄存器，还要可能换页表基址（RISC-V 的 `satp`、x86-64 的 `%cr3`）；换了页表之后，TLB（地址翻译缓存，缓存「虚拟地址→物理地址」结果的硬件小表）里属于旧地址空间的条目要么作废、要么按代际保留。

rCore 教程把这一层写到可运行的粒度：它给保存项定的规矩有两条，得同时成立才算数：这份状态切回来之后还得用得上，而且切出去这段时间里它有被别的代码写脏的可能；只有两条都满足，才值得为它付一次保存与恢复。

实现里存的是 `s0~s11` 这 12 个被调用者保存寄存器（callee-saved，被调函数负责保住原值的那批格子），再加返回地址 `ra` 与内核栈指针 `sp`（任务自己那截栈的栈顶），一共 14 项——`ra` 按 RISC-V 调用约定属 caller-saved，不在这 12 个之内，母本原文也只说恢复 `ra`、`s0~s11` 与 `sp`，容器 `TaskContext` 嵌在任务控制块里，切换由一段手写汇编 `__switch` 完成——它表面上是个普通函数调用，中间却藏着控制流的改道（`chapter3/2task-switching.html`）。

抢占则由硬件时钟中断驱动：内核通过 SBI 的 `set_timer` 设定下一次 `mtimecmp`，每秒 tick 数取 100，也就是每 10 ms 一次可能抢占（`chapter3/4time-sharing-system.html`）。一次 **poll 返回**完全不同：它在同一个线程、同一个地址空间里从被调函数返回，把任务的状态字段留在内存里，调用者接着跑下一个任务——付的是一次函数返回加几次状态位读写，不换栈、不换页表、不进内核。

把两边摆在一起，差别是**结构性的**：内核侧那一串动作一项都不能少，poll 返回只是同一线程上的一次函数返回。这也是为什么「一个线程上跑上千个任务」在 `async` 侧是常态，在内核侧的线程模型里却要先问栈空间够不够（每个任务一条内核栈）。**本书没有在本机采集这两类切换的成本对照**，本节只给机制与量级关系。

两者差着数量级，这才是「`async` 的切换便宜」这句话的机制来源。它也解释了另一件事：**poll 里长时间不返回，会把同一个线程上的所有任务一起拖住**——省下的那笔切换费，是用「不能长占线程」这条纪律换来的（9.5 的阻塞 poll 实验测的就是这条）。
:::

::: method 判定流程 · 一次 Pending 之后该看哪三个位置

**看状态字**：这次 poll 期间有没有新登记的 NOTIFIED——有，就是马上重排，不该睡。<br>
**看队列**：本 worker 与全局队列里还有没有别的可 poll 任务——有，就换任务，不进 driver。<br>
**看 driver**：只有全部任务都在等外部事件时才进入等待；等待必须有超时或新的通知能把它叫醒，否则就是[@def-9.2.1]的丢失唤醒。<br>
三步的顺序不能颠倒：先查自己的账，再查别人的账，最后才让出线程。

:::

### 9.2.4 取消是状态请求，不是指令边界抢占

对运行中的异步任务调用 `abort`，执行器做的事只有一件：在状态字里登记取消意图。**取消请求**（cancellation request）是一次登记，不是一次抢占——正在执行的 poll 不会被 Rust 语言机制强行切成两半，它必须先返回执行器控制，取消才有机会被看到。

这一点需要和「挂起点」连起来读。Future 的取消只能在它把控制权交回执行器的那一刻生效，也就是某个 await 边界或 poll 返回处；如果 poll 里执行不返回的 CPU 循环，取消无法在任意指令处介入；如果 poll 里阻塞在本地系统调用上，执行器也不能靠设置一个位就把调用撤回。这与线程的操作系统抢占是不同层面的问题：内核能拿走整条线程，但拿不走「这一次 poll 的一半」。9.8 会把这条边界写成公平性的前提。

::: note abort 与销毁不能画等号

`abort()` 返回只能说明取消请求已发出。需要等待 `JoinHandle` 完成，才能观察该任务是否已结束并执行了相应析构。已经开始执行的 `spawn_blocking` 闭包还具有更强的不可中止限制（9.7 会给出实测）。

:::

### 9.2.5 本轮取消回归测试

完整代码在 `tests/contracts.rs::abort_observed_and_drop_executed`。测试先等待任务进入，再请求取消；Drop 守卫经 oneshot 通知外部观察者。

```rust
struct Signal(Option<tokio::sync::oneshot::Sender<()>>);
impl Drop for Signal {
    fn drop(&mut self) {
        if let Some(tx) = self.0.take() {
            let _ = tx.send(());
        }
    }
}
```

随后检查 `JoinError` 是 cancelled，并等待 Drop 信号。这比「调用 abort 后立即读一个非同步计数器」更明确：后者读到什么取决于观察者的运气，前者把「已结束并析构」变成了一个能被程序看到的消息。

测试没有证明所有 Future 都可及时取消。它验证的是合作式挂起点上的一个具体生命周期场景——这与[@def-1.7.3]的探索性/确认性区分一致：一个通过的回归测试能证明「这条路径被走过」，不能证明「这类性质普遍成立」。

::: ex 例 9.2.3 · 为什么先等进入再 abort {#ex-9.2.3}

本节的测试刻意先等任务发出「已进入」的信号，再调用 `abort`。如果删掉这一步、spawn 之后立刻 abort，测试结果会变成什么？

::: sol 解答

结果会退化成两种情形的混合：任务可能在开始 poll 之前就被取消（Future 根本没进入，析构的是尚未构造的状态），也可能已经进入后再被取消（走[@def-9.2.2]那条挂起路径）。两种情形下 Drop 的时机与次数都可能不同，于是「JoinError 是 cancelled」这条断言仍然成立，但它检验的对象已经不确定。先建立明确的阶段关系，才谈得上观察该阶段的析构——同一个理由在 9.7 的 `blocking_permit_is_held_inside_closure` 里被再用一次，那里用它区分「闭包还没启动就被 abort」与「闭包已经在跑」。

:::

:::

### 9.2.6 任务 panic 与业务错误也要分层

任务返回 `Result<T, E>` 时，`JoinHandle` 本身仍可能失败。前者是业务完成结果，后者可能表示 panic 或取消。把两层 `Result` 压成一个字符串，会丢失调度层证据：你分不清「业务返回了 Err」和「任务被panic干掉、根本没有返回值」。

本轮 `joinset_observes_panic_and_completes_other_task` 同时创建一个故意 panic 的任务和一个正常返回的任务。测试持续 join，分别计数正常完成与 panic。它没有因为一个任务失败就忘记收集其余任务。实际服务可以选择失败即取消其他任务，但仍需完成回收——回收不是一种可选的礼貌，而是[@def-9.1.3]里引用责任的必然要求：不 join 干净的在途任务，它们持有的许可、缓冲与连接不会凭空归还（9.7 展开）。

::: think 思考 · 合并通知时能不能顺手删掉 Release {#think-9.2.1}

有人提议：既然 already-notified 分支不产生新的提交责任，就把这次的原子写降级为 relaxed，省一次开销。请按[@def-9.2.2]给出你需要的证据，并说明「省下来的」到底是什么。

::: sol 解答

需要的证据是：明确写出「哪一次 Acquire 读与哪一次 Release 写构成[@def-7.2.2]那条边」。如果这条边由资源自身的协议（例如通道内部的锁或原子发布）提供，并且执行器不再承担可见性义务，降级可以讨论；如果执行器是唯一把「资源已写」与「将来看资源」连起来的那环，降级就删掉了可见性义务，只留下进展义务。省下来的成本也说不清：本章没有对状态字的单次原子写打点（9.3.6 会重述这条限制），一次 relaxed 与一次 release 的差值没有本地实测支撑，属于用未采集的量换已知的正确性。

:::

:::

### 9.2.7 小结与常见错误

**小结。**① poll 期间的 wake 只能登记，兑现由退出 poll 的运行者负责，否则得到[@def-9.2.1]的丢失唤醒；② 合并通知省的是再次入队，不省可见性义务（[@def-9.2.2]、[@ex-9.2.2]）；③ `Pending` 与睡眠无关，一次 Pending 之后按「自己的账 → 别人的账 → driver」三步决定（9.2.3 的判定流程）；④ 取消是登记不是抢占，`abort()` 返回不等于析构已执行；⑤ 业务 `Result` 与 `JoinHandle` 的失败是两层证据，压成字符串就丢了调度层信息。下一节 [9.3 队列、就绪队列与 work stealing](#sec-cpp-rust.3.9.3) 从「一个任务的账」转向「几百个任务的分布」。

::: errata 常见错误清单（9.2 节）

E-a **poll 返回后直接设 idle。**不检查并发登记的通知，就造出丢失唤醒（[@def-9.2.1]）。

E-b **照四行表格写裸指针队列。**表格省略了引用计数与失败重试，不是伪实现（9.2.1）。

E-c **合并分支删掉 Release。**不排队不等于不同步，可见性义务还在（[@ex-9.2.2]）。

E-d **把一次 Pending 换算成一次内核切换。**它可能只是换了个任务继续 poll（9.2.3）。

E-e **认为 abort 返回等于任务已结束。**要等 `JoinHandle` 观察到取消与析构（9.2.4 的注盒）。

E-f **spawn 之后立刻 abort 就算取消测试。**阶段关系没建立，检验的对象不确定（[@ex-9.2.3]）。

E-g **把 panic 与业务 Err 压成同一条字符串。**两层证据合成一层，调度层信息消失（9.2.6）。

:::

::: method 即时自测 · 9.2

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　一次 wake 承担的两件事分别是什么？合并通知能省掉哪一件的哪部分？

::: sol 第 1 题答案
进展义务（未来有人再 poll）与可见性义务（wake 之前发布的资源状态能被那次 poll 看到）。合并能省掉进展义务里「再一次入队、再加一个引用」的动作，不能省可见性义务。对应[@def-9.2.2]。
:::

**第 2 题 · 辨析**　「任务被取消了，所以它的 Future 已经停止运行并且析构完了。」说出这句话漏掉的三步。

::: sol 第 2 题答案
① 取消只是状态字里的登记，正在执行的 poll 要先返回；② 返回之后执行器才观察到 CANCELLED 并停止重排；③ 析构与「已结束」要靠 `JoinHandle` 的结果（`JoinError` 是 cancelled）与外部观察信号来确认，`abort()` 的返回值本身不给这个保证（9.2.4、[@ex-9.2.3]）。
:::

**第 3 题 · 应用**　线上偶发「I/O 完成后再也没有进展」，但没有任何崩溃。给出两个最优先的检查点。

::: sol 第 3 题答案
① 丢失唤醒：检查 poll 返回 `Pending` 后有没有重新检查 NOTIFIED 那一步，以及 running 分支登记的通知由谁兑现（[@def-9.2.1]）；② driver 进入条件：是不是在所有任务都还欠着账时就进入了等待（9.2.3 的三步顺序）。这两类缺陷都不崩溃，只能靠恢复延迟与遥测暴露，正是 9.6 那类实验要量化的对象。
:::

**第 4 题 · 迁移**　把「取消是登记不是抢占」迁移到你自己写的一个协程库：给出两条必须写进接口的承诺，以及一条不许写的承诺。

::: sol 第 4 题答案
要写：① 取消在下一个挂起点/ poll 返回时生效，实现者保证不会在 poll 中途被切；② 取消完成的观察方式是句柄结果（含是否已析构），不是一次 `abort()` 调用。不许写：「取消即时生效、调用返回即资源已释放」——除非你确实提供了线程级的抢占边界，而那已经不是用户态 Future 协议能承诺的东西（9.8 的 CPU 循环讨论）。

## 9.3 就绪队列、LIFO 槽与 work stealing {#sec-cpp-rust.3.9.3}

本节回答一个问题：**同一个任务状态字，配上不同的队列形状，为什么会跑出差别巨大的性能，而 Future 的语义一句话都没变？**9.1 与 9.2 管的是单个任务的两条账；从这一节起，对象变成「几百个任务的等待怎样分布」。

::: preview 先抓住一件事

队列是**调度策略**，不是 Future 语义的一部分。换执行器不改 poll 契约，但会显著改变任务的实际等待分布、缓存局部性与通知开销——所以「用了 LIFO 所以更快」这类句子必须落到具体版本的具体参数上，而参数表不是调参建议大全。
:::

### 9.3.1 队列层次与硬件局部性

先把词钉死：执行器里那份「已经具备被 poll 条件、正等着轮到」的任务集合叫**就绪队列**（ready queue）。它和 9.2 里的通知责任是两层东西——通知责任说明某个任务欠一次 poll，就绪队列说明这笔欠账此刻由哪个 worker 负责兑现。

单一全局队列容易说明顺序，却让所有 worker 争夺同一入口：每次唤醒与每次弹出都要碰同一个缓存行（CPU 和内存之间整块搬运数据的单位），这正是第 7 章里共享计数器的形状。每 worker 各自的局部队列可以减少这种争用，代价是负载不均与跨 worker 迁移需要额外协议。本轮版本的运行时文档描述了五种结构：

- 多线程 runtime 的一条全局队列。
- 每 worker 各自的局部队列。
- 局部队列溢出时向全局队列转移部分任务。
- 本地无活可做时，从其他 worker 窃取部分任务。
- 特定唤醒路径使用的 LIFO 槽优化。

**LIFO 槽**是每个 worker 额外保留的一小块「后入先出」的位置：刚被唤醒的任务如果有机会马上被同一个 worker 再跑一次，就塞进这里，而不是排到队列尾部。

::: def 定义 9.3.1 · 就绪队列与窃取 ready queue, work stealing {#def-9.3.1}

**就绪队列**是持有「欠一次 poll」那些任务引用的容器，可以是全局一条、每 worker 各一条，或两者混合。**work stealing**（任务窃取）指空闲 worker 从别的 worker 的队列里取走一部分任务来兑现，而不是等它们自己走到全局队列。窃取搬运的是**任务引用**，不是 Future 的字节（[@def-9.1.3]）；它改变的是「谁来兑现这笔账」，进而改变后续访问该存储的 CPU。

:::

这些结构是调度策略，不是任务 Future 的语义组成。换一个执行器，Future 的 poll 契约不应改变；但任务的实际等待分布、局部性与通知开销可能显著变化。这句话是本章后面所有 benchmark 解释的边界条件：9.5 测到的是「配置的总体效果」，不是某一条队列结构的单独价格。

### 9.3.2 当前版本的参数不是语言常量

| 机制 | Tokio1.54.0文档中的观察 | 不应推导出的结论 |
|:--|:--|:--|
| 多线程局部队列 | 最多256任务，溢出转移部分到全局 | 所有版本永远固定256 |
| 空闲worker窃取 | 转移另一局部队列中的一部分任务 | 每次窃取一个必然更公平 |
| current-thread全局检查 | 文档默认31次本地选择后检查 | 每个任务31次内一定运行 |
| I/O/计时器检查 | 文档描述61次调度间隔等触发条件 | 定时器误差固定61纳秒 |
| multi-thread全局检查 | 默认可动态估计检查间隔 | 默认始终等于某个固定次数 |
| LIFO槽 | 连续使用受约束，且不能被其他worker窃取 | 唤醒的任务必定下一条执行 |

不要把参数表当成调参建议大全。要先检查当前运行版本与工作负载：这张表的每一格都属于[@def-1.8.1]意义上「绑定某个产物」的观察，版本一变就要重采。很多「调快 runtime」的配置，只是把延迟从一类任务转给另一类任务——31 与 61 这类数字之所以容易被误用，是因为它们看起来像承诺，实际上是某个检查循环的计数阈值。表里最容易被读错的是最后一列的句式：每一句「不应推导出的结论」都是有人真写过的注释。

### 9.3.3 为什么 LIFO 可能有利，以及它必须被约束

任务 A 把数据交给任务 B，然后自己等待 B 的结果。若 B 尽快在同一 worker 运行，数据可能仍在本地缓存中，这也可能减少全局排队与跨核通知。这就是 LIFO 槽存在的理由：**让刚产生依赖的任务趁热跑完**，省掉一次跨核的缓存行搬运。

但长期只追着刚唤醒的任务跑，会饿死其他已就绪任务。所以要在这里钉住一个后面反复用到的词。

::: def 定义 9.3.2 · 公平性 fairness {#def-9.3.2}

**公平性**不是「轮流执行」，而是一类关于等待的上界承诺：在一定前提下，一个已经被唤醒的任务不会永远等不到 poll。它的常见失效形式是**饥饿**（starvation）——某些就绪任务因为调度策略偏向另一类任务而长期得不到执行。[@def-9.3.2]的上界依赖什么前提，是 9.8 的主题；本节只需要记住一句：**局部性优化必须受公平性机制约束**，本轮版本的文档明确讨论了 LIFO 连续使用限制与预算。

:::

**这条承诺有两条实现路径，读别人的公平性声明时先分清是哪一条。**操作系统那边把这件事讲得更直白（rCore Tutorial v3 第五章第 4 节「调度」，登记为 `rcore-sched`，`chapter5/4scheduling.html`）：一条靠**抽签**——按权重给每个待调度对象发若干张票，每次调度抽一张，权重大的中票概率高。它的好处是调度器几乎不必记历史，新来者只要拿到票就能参与；代价是**短时间窗内的比例不准**，要把窗口拉长才收敛到权重比。

另一条靠**记账**——给每个对象一个与其权重成反比的步长，每次挑累计行程最小的那个执行，于是**每个调度周期都能把比例做准**；代价是新来者的初始账目要参考全局情况，否则它会长时间占着执行机会不放。

落到本书的判断上就是一句话：**「这个 runtime 是公平的」不是一个可以照抄的形容词**。要问三件事——它承诺的是哪一条（概率还是配额）、窗口多长（比例在多长时间内才成立）、新来者按什么规则入队。三件问不出来，公平性就只能当宣传语，不能当结论的前提；9.8 会把它的成立条件正式写成有限性前提（[@def-9.8.1]）。

不要把这些实现细节误写成：

> Tokio 就是严格深度优先调度。

也不要反向宣称 FIFO 队列就意味着整个 runtime 严格 FIFO。执行器有多个入口与多个 worker，队列局部顺序不等于全局完成顺序：一个 worker 的局部队列加上它的 LIFO 槽，再加上别的 worker 的窃取、全局队列的溢出转移，合起来的完成顺序不是任何单条队列的形状。想要「顺序」这句话，得像[@def-1.6.1]那样先说清比较的对象是什么。

::: ex 例 9.3.1 · 一个「快起来」的改动为什么让某类请求变慢 {#ex-9.3.1}

某个服务把唤醒路径改成优先使用 LIFO 槽，压测显示聚合吞吐上升，但一类低频后台请求的等待时间从几十毫秒涨到几秒。按本节解释发生了什么，并说明这属于[@def-1.7.2]的哪种情况——如果根本没设预算呢？

::: sol 解答

这是[@def-9.3.2]的饥饿：高频请求不断被唤醒、不断占用 LIFO 槽，后台请求在队列尾部等待的机会成本被持续推迟；吞吐上升与尾延迟恶化来自**同一个**改动，不是两件事。至于「属于哪种情况」——没设预算就还没有「情况」可言：[@def-1.7.1]要求 B 在看到数字之前写下，而这里连「后台请求最多等多久」都没定义，所以只能报告两个分布，不能给出接受或拒绝。正确动作是先补预算（对后台请求的等待上界），再按三态判定；「调快 runtime」的配置经常就是这样把延迟从一类任务转给另一类任务的。

:::

:::

### 9.3.4 stealing 迁移的是调度责任

stealing 不意味着复制整个 Future 业务数据。队列元素可以只是任务所有权或通知的轻量表示，任务实际存储的位置可以保持不变。但是后续访问该存储的 CPU 可能变化——这影响缓存局部性、NUMA 放置和线程局部数据。**本机没有 NUMA 测量，不能用本轮结果给出跨插槽建议**（这是[@def-1.8.1]的绑定关系：没有采到的环境维度就不进结论）。

某个 Future 在两个 poll 之间换 worker 运行，并不违背 `Pin`。`Pin` 约束的是被 pin 对象的**地址移动**，它不保证执行该对象代码的 CPU 或线程固定（第 8 章 8.3 讨论过这条边界）。这也是线程亲和性不能由 `Pin` 推出的原因：想「黏在某条线程上」需要另一份契约，例如 9.3.5 的局部任务机制，而不是给 `Pin` 加冕它没有做的承诺。

### 9.3.5 !Send 任务与局部执行

`tokio::spawn` 对 Future 与输出有 `Send` 约束。即使你配置 current-thread runtime，这个公共 API 约束也不会自动消失。不能凭「这里只有一个 worker」解释为什么 `Rc` 捕获一定可 spawn：约束写在类型签名上，检查发生在编译期，而 runtime 的配置是运行期的事——两者不是同一个开关。

要运行 `!Send` 任务，应使用适当的局部任务机制，例如被实际驱动的 `LocalSet`。它解决的是不能跨线程转移的任务存储约束；它仍不保证任务不会互相阻塞。一个 `!Send` 任务执行无限循环，同样可以卡住整个局部执行环境——9.6 会给出一个可测量的同型故障，只是那里的阻塞来自系统调用。

### 9.3.6 对性能归因的约束

观察 multi4 快于 current，并不能立刻断言是 stealing 成功。这个差异里还可能包含真正并行的业务计算、不同的 driver 检查路径、不同的 join 通知路径、任务创建与完成的重叠、主线程与 worker 间的同步。

本轮**没有给队列每次窃取打点**，**也没有采集 steal 成功率或每次 steal 的周期数**。所以实验只报告配置总体效果，不报告这些没有采集的量。这不是谦虚，是[@def-1.7.3]的确认性纪律：报出没有测过的数字，比少报一个数字严重得多。

::: think 思考 · 「窃取让并行度翻倍」这句话缺什么 {#think-9.3.1}

### 9.3.7 小结与常见错误

**小结。**① 就绪队列兑现的是通知责任，队列形状属于调度策略，不属于 Future 语义（[@def-9.3.1]）；② 局部队列换的是争用，代价是负载不均与迁移协议；③ LIFO 有利在缓存，危险在饥饿，所以公平性是关于等待上界的承诺而不是「轮流」（[@def-9.3.2]、[@ex-9.3.1]）；④ stealing 搬的是引用不是字节，`Pin` 不保证线程亲和（9.3.4）；⑤ `Send` 约束在编译期签名上，不因 runtime 配置消失（9.3.5）；⑥ 没有打点的成分不进结论（9.3.6）。下一节 [9.4 类型、ABI 与代码生成边界](#sec-cpp-rust.3.9.4) 把「一个任务在内存里长什么样」量化成可核对的尺寸与符号。

::: errata 常见错误清单（9.3 节）

E-a **把参数表当调参建议大全。**256、31、61 绑定当前文档与当前版本（9.3.2）。

E-b **写「Tokio 是严格深度优先」。**LIFO 槽只是局部优化，且有连续使用限制（9.3.3）。

E-f **以为 current-thread 下 spawn 自动接受 `!Send`。**公共 API 的约束在编译期检查（9.3.5）。

## 9.4 类型、ABI 与代码生成边界 {#sec-cpp-rust.3.9.4}

本节回答一个问题：**一个任务在内存里到底占多少、编译器为它留下了什么，以及这些观察最多能撑起哪一句结论？**前面三节讲责任与策略，这一节把它们落到字节与符号上——因为只有落到产物，才能判断「runtime 变慢」发生在哪一层。

::: preview 先抓住一件事

**句柄的尺寸不是任务的尺寸。**8 字节的 `JoinHandle` 与 8 字节的 `Sender` 都是描述符；它们背后各有任务存储、队列引用、输出区域与分配器（向系统要内存、再把内存还回去的那层代码）开销。尺寸探针（只为观察一个事实而写的最小测试程序）能证否「任务只需 8 字节」，不能给出每任务的真实成本。
:::

### 9.4.1 公共类型约束和内部擦除

泛型 spawn 入口可以在编译时检查 Future 类型，调度队列却不能为每一个业务 Future 维护一种独立队列类型：几百种 async 块要进同一条就绪队列（[@def-9.3.1]），执行器内部就必须有一种统一的任务表示。

统一表示不一定等于 `Box<dyn Future>`。实现可以把通用头、具体 Future、结果区域与专用函数表组合在同一块存储里，内部调度入口通过擦除后的任务指针调用具体类型对应的操作。这与第 5 章那条区分一致：被擦掉的是编译期可见的类型信息，不是值本身，也不是它待在哪里（[@def-5.1.4]）。

这也与「Rust 所有异步调用都是静态分派」不矛盾。业务 Future 内部的很多调用可以单态化与内联（[@def-5.1.3]）；执行器调度边界仍可能有间接调用。讨论时必须指出自己在讨论哪一层——「动态」和「静态」在[@def-5.1.1]里是按调用点判定的，不是按整个程序判定的。

| 层次 | 约束/表示 | 性能与安全问题 |
|:--|:--|:--|
| 业务Future | 具体编译器生成类型 | 跨await字段与状态大小 |
| spawn入口 | Future和Output的Send、'static等边界 | 能否被runtime持有和跨线程转移 |
| 任务头 | 版本内通用状态与生命周期信息 | 原子更新、对齐与共享争用 |
| 原始调度入口 | 类型擦除后分发poll/完成操作 | 间接调用与运行权 |
| JoinHandle | 观察结果的句柄 | 不拥有独占执行线程 |
| LocalSet任务 | 允许!Send但局部驱动 | 线程限制不等于吞吐保证 |

这张表读法是「每行一个对象，每行一个问题」：第三列的性能问题只属于第二列那个表示。把它压成一句「异步有动态分派开销」，就把[@def-5.1.2]的调用粒度问题（一次擦除替多少个任务负责）整个丢掉了。

### 9.4.2 本机类型尺寸探针

完整程序在 `examples/type_layout.rs`，输出保存在 `type-layout.txt`。这四个数字是编译期 `size_of` 的本机观察，绑定当前构建产物（[@def-1.8.1]）。

| 类型/对象 | size | align | 说明 |
|:--|--:|--:|:--|
| yield_now返回的Future | 16 | 8 | 固定版本和功能集下的实际对象 |
| JoinHandle&lt;u64&gt; | 8 | 8 | 句柄大小，不是任务总分配量 |
| mpsc::Sender&lt;u64&gt; | 8 | 8 | 发送端大小，不是整个通道大小 |
| 实验Frame | 16 | 8 | 线协议仍使用显式24字节编码 |

不能把 8 字节的 `JoinHandle` 解释成每任务只需要 8 字节：背后还有任务存储、队列引用、Future、输出区域和分配器开销，也就是[@def-9.1.3]那一整块任务单元。同理，小的 `Sender` 可以指向很大的共享通道状态——9.7 会看到这条性质直接变成背压问题。最后一个数字提醒一件事：线协议故意仍使用显式 24 字节编码，也就是说「本机 Rust 对象尺寸」和「跨边界协议尺寸」是两个量，不能互相替换。

::: ex 例 9.4.1 · 从 8 字节句柄推到每任务 8 字节 {#ex-9.4.1}

一份容量规划写：「`JoinHandle` 只有 8 字节，所以十万个在途任务的控制开销不到 1 MB。」请按本节指出这句话的三处漏洞，并给出一个能在本章内做的更诚实的估计方式。

::: sol 解答

① 混淆描述符与被指对象：句柄是观察者侧的句柄，任务单元（状态字 + Future + 输出 + 队列引用）才是被持有的存储，[@def-9.1.3]的三个对象不因为句柄小而消失。② 忽略分配器与对齐：真实占用要按分配粒度向上取整，本轮没有采集任务单元的总分配量，所以连「大约」都不能给。③ 句柄还可能被提前丢弃：`spawn` 后不保存 `JoinHandle`，观察者那侧的账就没了，但任务继续在跑——8 字节从来不是「任务成本」的代理量（[@ex-9.3.1]同型错误：用一个可观察数字代理一个没测的量）。

更诚实的方式是本章已经在用的：固定并发数、在途任务数与输出分别核验，把观察点放在能观察的地方（[@def-1.3.1]），而不是从类型尺寸外推容量。

### 9.4.3 ABI 与代码生成核对表

| 边界 | 本章核验方式 | 可以下的结论 |
|:--|:--|:--|
| step(u64)到u64 | `scheduling.s`中的实际符号 | 输入/返回经本轮寄存器约定，计算保留 |
| 具体Future的poll路径 | 保留的raw poll实例及业务闭包符号 | 两种scheduler路径均有具体实例 |
| 任务运行权 | 生成代码调用transition_to_running | 不是拿到队列元素就无条件poll |
| 状态RMW | 目标汇编可见casal等指令 | 确实保留原子状态操作，不能据此计算总同步开销 |
| 任务结果 | JoinSet逐个收集 | 完成观察包含通知与校验工作 |

这里没有承诺稳定的 Rust 函数 ABI（[@def-5.3.4]），也没有把内部函数表格式当成可供 C 直接调用的接口。若要 FFI，必须另外设计明确的 C ABI 与所有权契约——这与第 5 章把「偏移 24 能不能写进文档」判为不成立（[@ex-5.3.2]）是同一条纪律。「保留的 raw poll 实例」这一行还有一层含义：擦除发生在调度边界，而 Future 的具体实现仍被单独生成，所以「异步就是动态分派」与「异步全是静态分派」两句都错。

### 9.4.4 业务计算没有被整段折叠

`scheduling.rs::step` 使用 `inline(never)` 与标准库 `black_box`。保存的汇编中可见对 step 的实际调用；step 内部保留输入屏障、乘加与返回。核心片段如下，省略了调试位置指示：

```asm
sub    sp, sp, #16
str    x0, [sp, #8]
add    x8, sp, #8           ; black_box 要的是地址
; InlineAsm Start
; InlineAsm End
ldr    x8, [sp, #8]
mov    x9, #32557           ; 下面三条 movk 把同一常量拼满 64 位
movk   x9, #19605, lsl #16
movk   x9, #62509, lsl #32
movk   x9, #22609, lsl #48
mov    x10, #1
madd   x0, x8, x9, x10
add    sp, sp, #16
ret
```

`bench/results/runtime-fixed/measurements-final/scheduling.s:18352-18379` 里 `step` 就这些指令，摘出时只删了 `.loc`/`.cfi_*` 与 `Ltmp` 标签——runtime-lab 的产物目录没有 `run-01` 这种编号，别按那个名字去找。

x9 的常量由前面的 mov/movk 序列构造。完整符号而不是这五行才是代码生成证据——第 1 章反复讲过这件事：静态证据用来排除「根本没执行」（[@def-1.3.1]），不是用来替代计时。`black_box` 不是硬件内存屏障，也不能代替对完整优化后产物的检查（[@def-1.1.2]）。

### 9.4.5 noinline 的代价也属于夹具

每个逻辑 step 包含一次有意保留的函数调用。这让工作量容易验证，也意味着结果不是纯整数乘法吞吐。把这些 ns/step 拿去预测向量化（让一条指令同时算多个数据）数值核会误导：向量化数值核通常希望内联和批量加载。本实验要保留的是很多小型业务步与调度之间的竞争，也就是 9.5 真正想量化的那个对象。

::: think 思考 · 汇编里有 casal，能不能算同步开销占比 {#think-9.4.1}

看到目标汇编里存在 `casal`（原子加载-存储对），有人写成「本实验的同步开销约占 15%」。请按[@def-1.5.2]和本节判断这个句子的证据强度。

::: sol 解答

证据不支持。① 静态存在不等于动态次数：一段 `casal` 可能对应每次 poll 一次、也可能对应每次状态转换若干次，没有打点就不知道执行了多少回（本轮没有采集，见 9.4.6 的结论边界）。② 指令可见不等于成本可分：`casal` 的耗时依赖缓存行归属与争用，而正式批次只报告聚合 ns/step，没有单独成分（[@def-1.2.2]）。③ 采样不能补这个洞：`scheduling-sample.txt` 覆盖预热与两个 runtime 轮转的混合阶段，不能折算成稳定态百分比（9.5.7）。正确的句子只能写「产物里保留了原子状态操作，其单次成本与总占比本轮没有采集」——这跟[@ex-1.4.2]里「用比值编造加速来源」是同一种错误。

:::

### 9.4.6 小结与常见错误

**小结。**① 统一的任务表示不等于 `Box<dyn Future>`，擦除发生在调度边界而具体实例仍被生成（[@def-5.1.4]）；② 描述符尺寸不是对象成本，句柄、发送端都不能代理任务单元（[@def-9.1.3]、[@ex-9.4.1]）；③ 版本内偏移与函数表格式不是可依赖的 ABI，跨界要另设契约；④ 汇编与符号是「工作没被折叠」的证据，不是成本分解的证据（[@def-1.3.1]）；⑤ `inline(never)` 的代价属于夹具声明的一部分，换了夹具就换了被测量的东西（[@def-1.1.3]）。下一节 [9.5 benchmark 一：让出粒度与 worker 数](#sec-cpp-rust.3.9.5) 用这套夹具正式开跑。

::: errata 常见错误清单（9.4 节）

E-a **用句柄尺寸估任务成本。**8 字节 `JoinHandle` 背后是一整块任务单元（[@ex-9.4.1]）。

E-b **把本机对象尺寸当线协议尺寸。**实验 Frame 与线协议 24 字节编码是两回事（9.4.2）。

E-c **把内部函数表当可调用 ABI。**要 FFI 就另行设计 C ABI 与所有权（9.4.3）。

E-d **宣称异步一律静态（或一律动态）分派。**要按调用点分层判断（[@def-5.1.1]）。

E-e **从 `casal` 的存在算同步占比。**静态存在不等于动态次数与成本（见本节的思考框）。

E-f **拿 noinline 的结果预测向量化数值核。**夹具保留了调用边界，不是纯乘法吞吐（9.4.5）。

:::

::: method 即时自测 · 9.4

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　表里六个层次各对应什么对象？说出「任务头」与「原始调度入口」的分工。

::: sol 第 1 题答案

::: sol 第 2 题答案

:::

**第 3 题 · 应用**　你要证明「业务递推没被优化器折叠掉」，按本章给出两条独立证据。

::: sol 第 3 题答案

:::

::: sol 第 4 题答案
不能省：① 显式的 C ABI 边界（`extern "C"` 的函数与不透明句柄，而不是暴露内部函数表）；② 所有权与释放责任（谁创建任务句柄、谁负责调用配套的释放函数，取消与析构的次序对应 9.2.4 那条「登记不等于结束」）；③ 跨边界数据布局（按显式协议编码，不按本机 `size_of` 推，见[@ex-9.4.1]）。此外还要说清 panic 不能跨边界展开。
:::

## 9.5 benchmark一：让出粒度与worker数 {#sec-cpp-rust.3.9.5}

本节回答一个问题：**在同一个执行器里把「主动让出」的粒度改小或改大，聚合吞吐会怎么变？**9.1–9.4 讲的是调度器的结构与语义；从这一节开始动手：只改两件事——运行时是 current-thread 还是 4-worker，以及每 16 步还是每 1024 步 `yield_now()` 一次。

::: preview 先抓住一件事

这是一个**系统级微基准**，不是调度器内核的计时器测试：任务创建、唤醒、业务递推和 join 都在计时界内。因此它报出的数是「整批工作摊到每个逻辑步上的墙钟时间」——这个数到底不是什么，9.5.1 用一整段钉死。读它的前提，是先接受这张阶段表对边界的划分。

:::

### 9.5.1 计量单位：墙钟时间除以聚合步数

::: def 定义 9.5.1 · 聚合步数口径 ns/step {#def-9.5.1}

每批创建 128 个任务、每任务执行 8192 个逻辑 step，一批共 1048576 个 step。把这一批的墙钟时间除以这个总数，得到的**聚合步数口径**（ns/step）回答的是「整批工作的平均每步成本」。它不是单次 poll 的成本，不是一次 `yield_now` 的延迟，也不是某个任务从到达到完成的响应时间。

:::

口径决定结论能说什么。用[@def-9.5.1]的读数比较两种 quantum 时，你比较的是「同样 1048576 步、不同让出频率」下的整批成本；换成单任务延迟或 p99，这个数字一个都不能用。

### 9.5.2 哪些阶段在计时界内

| 阶段 | 是否进入每批计时 | 理由 |
|:--|:--|:--|
| 创建两种 runtime | 否 | 避免混入 runtime 线程启动的比较 |
| 预计算校验结果 | 否 | 不把串行参考实现重复算进测量 |
| 每批创建 128 个任务 | 是 | 这是被测多任务生命周期的一部分 |
| 每个 step | 是 | 主要业务工作 |
| yield 与重新调度 | 是 | 核心被测差异 |
| JoinSet 收集所有完成 | 是 | 批完成必须可观察 |
| 批后比较最终 checksum | 否 | 时间戳之后执行 |
| 析构整个 runtime | 否 | 不测 runtime 的冷退出 |

不要把这张表偷换成「只测调度器本体」：任务创建、通知、业务与 join 都在界内，所以结论的适用范围就是「一次完整的批生命周期」。反过来说，runtime 的启动与关闭不在界内，任何关于「进程启动成本」的说法都不能从这里推出来。

### 9.5.3 任务核心与观察点

完整源文件还包含统计、校验与 case 顺序轮转；下面这段保持与业务核心一致：

```rust
for id in 0..TASKS {
    tasks.spawn(async move {
        let mut value = id;
        for chunk in 0..STEPS / quantum {
            for _ in 0..quantum {
                value = step(value);
            }
            std::hint::black_box(chunk);
            tokio::task::yield_now().await;
        }
        (id, value)
    });
}
```

两种 quantum 都整除 8192，没有遗漏尾部 step。checksum 按任务 id 旋转后异或，因此与完成顺序无关；参考 checksum 在计时之外预先算好（第 1 章的[@def-1.1.3] 要求的正是这种「观察点在界外、被观察工作在界内」的安排）。

这种校验识别不了所有错误——checksum 会碰撞——但它明显优于不观察任何输出；任务数还会被独立核验为 128。改造夹具时，这几个观察点要一起保留，否则「批跑完了」这句话就失去证据。

### 9.5.4 预热、轮转与不并行

先至少预热 500 ms，预热中交替运行四个 case；正式测量每个 case 21 批，每轮轮转 case 起点，避免某个配置总是与时间漂移的后半段重合。没有把四个 benchmark 进程并行启动，也没有把 profiler 附着到正式计时的进程上——前者会把「相互争抢」写进结果，后者会把观测成本写进结果。

::: ex 例 9.5.1 · 2.602 与 0.750 能说明什么 {#ex-9.5.1}

本章的实测里，同一负载（128 任务 × 8192 步）下，单线程与 4-worker 的聚合 ns/step 分别是 2.602 与 0.750。可以据此写「4 个 worker 让聚合成本降到约三分之一」吗？还能写什么、不能写什么？

::: sol 解答

可以写「在这个负载、这台机器、这次运行里，4-worker 的聚合 ns/step 更低，是单线程的 0.29（0.750 ÷ 2.602）」，前提是把口径说全：@def-9.5.1 的聚合口径、固定 128 任务 × 8192 步、同一台机器同一次运行。**不能**写「每次调用快了 3 倍」——聚合口径的倒数本来就允许小于一次调用的耗时，因为四个 worker 在并行推进不同任务。也不能写「窃取让并行度提高三倍」：本轮没有采集 steal 次数与成功率，「窃取」是推测而非观察（9.3.6）。更不能外推到带 I/O 或并发到达的负载。

:::

:::

::: think 思考 · 为什么不能把这张表读成「调度器开销」 {#think-9.5.1}

既然四种组合只改动了 runtime 与 quantum，为什么读数不能解释成「调度器的每次 yield 要花多少纳秒」？

::: sol 解答

因为分母是 1048576 个逻辑 step，不是 yield 次数（[@def-9.5.1]）。quantum 从 1024 缩到 16 时，每任务的 yield 次数变成 64 倍，但业务步数不变；读数上升里混着「yield 与重新调度的成本」「缓存与队列状态被打断的代价」两部分，无法在不额外采集的情况下拆开。要拆，需要单独改变任务数或单独测量空任务链——那是另一个实验设计。

:::

:::

### 9.5.5 小结与常见错误

**小结。**① 本节的口径是聚合步数（[@def-9.5.1]），只回答整批吞吐；② 阶段表划定了边界，创建与 join 在界内、启动与校验在界外；③ checksum 与任务数是必须保留的观察点；④ 预热 500 ms、每 case 21 批、轮转起点是防漂移的最低配置；⑤ 那两行读数只能在同负载内比较（[@ex-9.5.1]）；⑥ 读数不等于 yield 的单价（[@think-9.5.1]）。下一节 [9.6 benchmark二：阻塞 poll 污染观察延迟](#sec-cpp-rust.3.9.6) 把这个设计推到一个更容易被误读的负载上。

::: errata 常见错误清单（9.5 节）

E-a **把 ns/step 读成单次 poll 耗时。**分母是逻辑步数，不是 poll 次数（[@def-9.5.1]）。

E-b **只测调度器本体。**任务创建、通知与 join 都在界内，删掉它们测的是另一个系统。

E-c **让四个 case 并行跑。**相互争抢会被写进结果，比较变成「谁更能抢」。

E-d **不轮转 case 顺序。**配置与时间漂移完全重合，差异无法归因。

E-e **省掉 checksum。**批跑完了却没人验证结果，等于把错误实现算进性能。

E-f **把两行读数外推到其他任务数。**任务数与 worker 数的比例一变，结论就可能翻转（[@ex-9.5.1]）。

:::

## 9.6 benchmark二：阻塞poll污染观察延迟 {#sec-cpp-rust.3.9.6}

本节回答一个问题：**一次不碰任何共享数据、也没写错一行同步的阻塞调用，怎样把另一个毫不相干的任务拖慢二十多毫秒？**9.5 比的是整批吞吐；这一节把观察点收窄到一段：从「通知真正发出」到「等待者恢复执行」。

::: preview 先抓住一件事

这个故障**不是数据竞争，而是执行权被占住**：任务在 poll 里睡 20 ms，当前线程就没回到执行器，已经就绪的观察者拿不到下一次 poll。识别它要看通知恢复延迟，不看吞吐——在这种负载上吞吐几乎不动。

:::

### 9.6.1 实验设置：一个时间戳，两条分支

实验入口是 `src/bin/blocking_poll.rs`，只使用 current-thread runtime。被测任务先经 oneshot 发出一个 `Instant`，再执行 20 ms 本地睡眠；观察任务等待这个 oneshot，用发送方给出的时刻算出自己晚了多久。两条分支的睡眠工作都真的执行，区别只在占哪条线程：

| 分支 | 写法 | 睡眠占用 | 执行器线程是否被释放 |
|:--|:--|:--|:--|
| inline | 异步任务里直接 `thread::sleep` | 正在跑 poll 的线程 | 否 |
| offload | 发送与睡眠一起放进 `spawn_blocking` | 阻塞池线程 | 是 |

两条分支都没有执行 UB，也没有用原始指针绕过 Rust 的同步约束。它们都通过类型检查、都能跑完，差别只在「谁在执行器线程上待了 20 ms」。

::: def 定义 9.6.1 · 观察延迟 observation delay {#def-9.6.1}

**观察延迟**指从「通知真正发出」到「等待者被再次 poll 并恢复执行」的墙钟时长。它只覆盖这一段，既不含被测任务余下的工作，也不是整批吞吐。本节表里的每一个原始观察，都是这样一个样本。

:::

按[@def-9.6.1]，这里报的是延迟而不是吞吐，所以这些读数与 9.5 的 ns/step 不能互相换算（[@def-9.5.1]）。

### 9.6.2 时间戳为什么必须放在发送方

如果观察者在 `recv` 返回后才开始计时，被阻塞的那段时间已经被漏掉，它量到的是「收到之后又花了多久」。所以时间戳要在通知真正发出的位置创建，并随 oneshot 消息一起传过去：

```rust
let sent = rx.await.expect("sender alive");
let delay = sent.elapsed().as_secs_f64() * 1e9;
task.await.expect("async worker panicked");
```

最后仍然 join 被测任务，这样 offload 分支不会把没睡完的睡眠留到下一批。代价是报告的 delay 不含等待剩余睡眠完成的时间——这正是[@def-9.6.1] 的边界：它是观察延迟，不是该任务的完整执行时间。

::: def 定义 9.6.2 · 阻塞 poll 污染 blocking poll contamination {#def-9.6.2}

**阻塞 poll 污染**指某个任务在自己的 poll 里执行阻塞调用，使执行线程无法回到执行器，从而推迟其他已就绪任务被 poll 的现象。它不需要共享状态，也不需要写错同步；被推迟的任务与阻塞任务之间可以毫无关系。

:::

current-thread 夹具让[@def-9.6.2] 必然发生，而不靠运气。inline 任务在 send 之后立刻进入本地 sleep，当前线程没有回到执行器；接收任务虽然逻辑上可运行，却没有机会继续执行；等 sleep 结束、发送任务的 poll 返回，执行器才可能推进观察者。多线程 runtime 里也可能发生同样的污染，但那要看任务实际被放到哪个 worker、还有哪些负载，本章没有把当前实验直接当成多线程的全局停顿。

### 9.6.3 结果与单位

来源是 `runtime-fixed/measurements-final/blocking-poll.txt`。修订后每 case 至少预热 500 ms，正式观察 21 次，case 顺序交替；原始文件以 ns/op 输出，下表换算成更易读的单位。

| 实现 | 平均观察延迟 | 样本 sd | 观察 p50 | 观察 p99 |
|:--|--:|--:|--:|--:|
| inline | 23.658 ms | 1.302 ms | 23.604 ms | 25.060 ms |
| offload | 13.633 µs | 3.494 µs | 14.125 µs | 18.541 µs |

两个均值量的都是[@def-9.6.1]，不是 9.5 的批均值。21 个观察仍远不足以稳定估计生产请求的极端尾分布，表里的 p99 只是这个 21 点样本的 nearest-rank 分位数（[@def-1.5.2]）。另外，20 ms 是申请睡眠时间，不是保证值：桌面系统的调度与计时器都可能加延迟，读数比 20 ms 大不构成任何语言或 runtime 违反承诺。

::: ex 例 9.6.1 · 23.658 ms 与 13.633 µs 之间能写什么 {#ex-9.6.1}

同一台机器、同一次运行里，inline 的平均观察延迟是 23.658 ms，offload 是 13.633 µs。三个问句：① 能不能写「`spawn_blocking` 把 20 ms 睡眠缩短成 13.6 µs」？② inline 比申请的 20 ms 多出约 3.658 ms，这 3.658 ms 是什么？③ inline 的 p99 25.060 ms 能当生产尾延迟吗？

::: sol 解答

① 不能。两分支睡的同样是 20 ms，睡眠一步也没变短；变的是观察者要不要等它。offload 把睡眠挪到阻塞池，执行器线程得以立刻推进观察者，于是[@def-9.6.1] 从毫秒级掉到微秒级。② 不能拆。20 ms 是申请值不是保证值，计时器粒度与桌面调度都可能加时间；本轮没有分段打点，只能写「比申请值大约多 3.658 ms」，不能把这笔差额归给其中某一项。③ 不能。21 个观察上 `ceil(21 × 0.99) = 21`，p99 就是最大值（[@def-1.5.2]），它是这份样本身份的说明，不是对生产尾延迟的承诺。

:::

:::

::: think 思考 · 「多开几个 worker 就没事了」 {#think-9.6.1}

既然污染的是「当前线程」，把 current-thread 换成 4 个 worker，是不是就修好了？

::: sol 解答

只是把可被占满的线程数从 1 改成 4。阻塞任务的个数随并发增长：四个同时阻塞的任务照样能把四个 worker 全占住，[@def-9.6.2] 只是从「必然」变成「看负载」。配置扩容不等于移除了错误的执行边界；修复是把有限阻塞工作移到合适的执行域，并控制那个域的并发、队列与取消策略——9.7 讨论的背压就是这个修复的一半。

:::

:::

### 9.6.4 这个实验没有证明什么

它没有证明 `spawn_blocking` 能让睡眠本身更快完成，没有证明阻塞池线程零成本，也没有证明把所有 CPU 工作都丢进阻塞池会提升吞吐。offload 分支只做到一件事：异步执行线程不再被这一次 sleep 占住。若阻塞工作大量积压，队列延迟、线程数与内存仍会出问题；若业务必须硬中止不可合作的第三方代码，还需要额外的进程边界。

回到判定：本例的回归不是「被测任务慢了 20 ms」，业务本来就要求睡眠。真正的回归是一个无关的观察任务，在消息已经可用之后仍被拖住。

::: method 判定流程 · 一次恢复延迟变长，先查四步

① **核起点**：时间戳是在通知发出处创建的吗？在 `recv` 之后才开始计时，就漏掉了被阻塞的那一段（[@def-9.6.1]）。<br>
② **看量级**：差值是否与某个已知阻塞调用同量级？本例 inline 的 23.658 ms 与 20 ms 睡眠贴得很近。<br>
③ **定执行域**：阻塞调用写在异步任务里，还是写在 `spawn_blocking` 闭包里？<br>
④ **找被占住的线程**：current-thread 下就是执行器本身；多线程下要问任务被放到了哪个 worker。<br>
⑤ **换表述**：结论写成「通知恢复延迟」与「poll 污染」，不写成「吞吐下降」或「runtime 变慢」。

:::

### 9.6.5 小结与常见错误

**小结。**① 本节量的是通知恢复延迟（[@def-9.6.1]），与 9.5 的批均吞吐不是同一个对象；② 时间戳必须在发送方创建，否则漏掉被阻塞段；③ 污染的本质是执行权被占住，不是数据竞争（[@def-9.6.2]）；④ 两分支的差别是执行域，不是睡眠时长（[@ex-9.6.1]）；⑤ 加 worker 只是增加可被占满的线程数（[@think-9.6.1]）。下一节 [9.7 背压、许可寿命与资源上界](#sec-cpp-rust.3.9.7) 处理同一类问题的另一半：谁被允许进来，许可能活多久。

::: errata 常见错误清单（9.6 节）

E-a **把计时起点放在 `recv` 返回之后。**[@def-9.6.1] 的起点必须在通知真正发出处，否则被阻塞的那段已被漏掉。

E-b **把 offload 的 13.633 µs 读成「睡眠变快了」。**睡眠仍是 20 ms，换的只是执行域（[@ex-9.6.1]）。

E-c **把 23.658 ms 减去 20 ms 的差额归因给某一项。**本轮没有分段打点，差额不能拆。

E-d **用 inline 的 p99 25.060 ms 承诺生产尾延迟。**21 个观察的 p99 就是最大值（[@def-1.5.2]）。

E-e **用「加 worker」当修复。**四个并发阻塞任务同样能占满四个 worker（[@think-9.6.1]）。

E-f **把 current-thread 的结论写成多线程全局停顿。**本章没有把当前实验当成多线程的全停（9.6.4）。

:::

**第 1 题 · 记忆**　观察延迟的起点与终点分别在哪一刻？它不含哪一段时间？

::: sol 第 1 题答案

::: sol 第 2 题答案

## 9.7 背压、许可寿命与资源上界 {#sec-cpp-rust.3.9.7}

本节回答一个问题：**一个容量只有 64 的有界通道，为什么挡不住进程被成千上万个「还没轮到发送」的请求撑爆？**9.6 说明阻塞会占住执行域；这一节说清另一半——谁被允许进入、许可能活多久、每条资源的边界画在哪里。

::: preview 先抓住一件事

背压不是一条队列，而是**一组准入点加一张寿命表**：边界必须画在昂贵分配之前，许可必须与真正消耗资源的那段工作同寿。只画一条「并发数 = 64」不能替代完整资源图。

:::

### 9.7.1 有界通道只锁住一段缓冲

Tokio 的 mpsc 有界通道可以让 `send` 等待容量，它控制的是通道内部的排队数量。它不控制「已经创建、正在等 send」的任务数量：若对每个请求先 `spawn`，再在任务里等一次有界 send，任务数照样可以无限增长，每个还持有请求正文、连接引用与上下文。队列只有 64 个槽，进程仍可能因为等待发送者而耗尽内存。

::: def 定义 9.7.1 · 背压 backpressure {#def-9.7.1}

**背压**指下游处理不过来时，让上游的「产生」等一等或直接失败的机制。它约束的是产生速度与在途数量，而不只是某一段缓冲区的大小。判断有没有背压，要问「无处安放的请求最终会停在哪里」，而不是「队列容量是多少」。

:::

| 资源 | 常见边界 | 容易遗漏的额外存储 |
|:--|:--|:--|
| 通道缓冲 | channel(capacity) | 等待 send 的任务和消息 |
| 活跃请求 | admission semaphore | 已接收但尚未取得许可的请求体 |
| 阻塞工作 | 闭包内持有的 permit | 提交队列和调用方的临时对象 |
| 子进程 | 进程池/并发许可 | stdout、stderr、输入及后代进程 |
| 结果历史 | 固定容量结果队列 | JoinHandle 和未消费输出 |

按[@def-9.7.1]，这张表每一行都是一条独立的上界。不同边界管的是不同队列，某一行的数字再小，也不会替另一行兜底——上界只对它自己覆盖的那个集合成立。

::: ex 例 9.7.1 · 64 个槽挡不住无限 spawn {#ex-9.7.1}

某服务的写法是：每个请求先 `tokio::spawn` 一个任务，任务内部再 `send` 到一个 `channel(64)` 的通道。有人据此写「并发已被限制在 64」。进程的内存上界到底由什么决定？

::: sol 解答

由「已创建任务数 × 每个任务持有的量」加「通道里已有的 64 条消息」决定，与 64 无关。按三步核对：① **谁在等待**——不是 64 个消费者，而是所有还没成功发送的任务；② **等待者持有什么**——请求正文、连接引用、上下文；③ **边界覆盖哪一段**——只覆盖「已进入缓冲的消息」这一段。要被 64 约束住，得把准入移到 `spawn` 之前，让任务在拿到名额前不持有正文（[@def-9.7.2]）。

:::

:::

### 9.7.2 把准入放在昂贵分配之前

::: def 定义 9.7.2 · 准入控制 admission control {#def-9.7.2}

**准入控制**指在做昂贵工作之前先取得一个名额，拿不到就等待或拒绝。关键在「之前」：名额必须在内存被分配、连接被占住之前拿到；事后拒绝不能把已经花掉的资源退回去。

:::

一个实用的顺序：

```text
小头部读取
  -> 检查声明长度与身份
  -> 取得系统准入预算
  -> 在预算内读取正文
  -> 投递到有界执行队列
  -> 完成/失败/取消
  -> 释放对应预算
```

这不是唯一正确的顺序，但两个错误方向能一眼看出：若把「读取无限大正文」放在最前面，后面的信号量不会追溯性地减少已分配内存；若取得许可之后又无限等待上游输入，慢客户端就会长期占着名额。所以读入期限、长度检查与准入期限要一起设计（[@def-9.7.2]）。

**这条顺序在教科书里也有原型。**rCore 教程第八章的信号量机制把「先取得名额，再干活」写成了两种原语：一个是取用资源（P 操作），一个是归还资源（V 操作）；资源数量用一个整数计数表示，计数到零后来的线程只能排队等。

那里还有一条细节值得抄进判据：**归还是直接把名额交给一个已经在等的线程**，所以被唤醒的那一方醒来时不必重新确认名额是否还有效——名额的寿命在移交那一刻就定了（[@def-9.7.3]）。这解释了为什么本章坚持「许可必须与工作同寿」：许可一旦被交出去，原持有者就再也不能用它去代表自己那份资源占用。

同一页也把「唤醒丢失」的成因写得很直白：如果唤醒动作发生在等待动作之前，那次唤醒无处可去；信号量的解法是让计数本身记住这次多余的唤醒，于是后来的等待者不会永远挂着。对照 [@def-9.2.1]：丢失唤醒不是「通知发丢了」，而是**通知与等待的先后顺序没有约定**。

### 9.7.3 许可寿命：它必须覆盖真正的工作

::: def 定义 9.7.3 · 许可与许可寿命 permit, permit lifetime {#def-9.7.3}

**许可**（permit）是一个代表有限资源名额的持有凭证，名额在它被 drop 时归还。**许可寿命**指它从取得到归还所覆盖的那段时间。资源上界只在寿命覆盖了真实占用期时才成立；寿命短于占用期，那个上界就只是名义上的。

:::

下面这个序列在安全 Rust 里完全合法，却会让实际并发超过设定值：

```text
异步任务取得permit
提交spawn_blocking
异步任务超时并被丢弃
permit随异步任务释放
阻塞闭包仍然运行
新请求取得刚释放的permit
实际阻塞并发超过设定值
```

所有权系统只保证对象按规则销毁，它不知道你希望[@def-9.7.3] 对齐的是「调用方还活着」，还是「阻塞工作还在跑」。若许可代表阻塞资源占用，就把 owned permit 移进闭包：调用方被取消时，许可仍由正在运行的工作持有，闭包结束才归还。

::: think 思考 · 把容量从 64 调到 16 就能防 OOM 吗 {#think-9.7.1}

有人提出：容量小一点，堆积自然就少了。这个调整能给出内存上界吗？

::: sol 解答

不能。容量只数「已经在缓冲里的消息」，等 send 的任务不在这个计数之内，请求正文也不在——正文在任务手里。调小容量只会让等待更早、等待者更多，[@def-9.7.1] 想要的那条界线依然缺着。要给上界，得同时补三样：准入点前移到 `spawn` 与正文读取之前（[@def-9.7.2]）、每个任务在拿到名额前不持有正文、以及一条把名额与真实工作绑在一起的寿命规则（[@def-9.7.3]）。

:::

:::

### 9.7.4 两条可执行回归

第一条 `bounded_channel_and_close_preserve_messages` 把容量压到 1，验证容量满时拒绝、腾出槽位后可复用、关闭后仍能排空已进入缓冲的消息：

```rust
let (tx, mut rx) = tokio::sync::mpsc::channel(1);
tx.try_send(10).expect("first slot");
assert!(matches!(
    tx.try_send(20),
    Err(tokio::sync::mpsc::error::TrySendError::Full(20))
));
assert_eq!(rx.recv().await, Some(10));
tx.send(20).await.expect("space reused");
drop(tx);
assert_eq!(rx.recv().await, Some(20));
assert_eq!(rx.recv().await, None);
```

它没有测量通道吞吐，也没有报告队列内存峰值。把这个测试当成百万请求压测的证据是不成立的（[@def-9.7.1]）。

第二条 `blocking_permit_is_held_inside_closure` 检验[@def-9.7.3]：先等闭包发出 started 信号，再对它的 `JoinHandle` 调用 abort；闭包此时仍在等一个同步停止信号，这时再取唯一那个 permit 必须失败。随后发出停止信号、等闭包结束，再取 permit 必须成功。测试刻意不用固定 sleep 去猜「闭包应该已经启动了」——started 消息建立了明确的阶段关系，避免把「还没启动就被 abort」和「已经在跑」混为一谈；同一个理由在 9.2 的取消测试里已经用过。

### 9.7.5 有限阻塞该放进哪个执行域

| 工作特征 | 更合适的执行域 | 必须另外说明 |
|:--|:--|:--|
| 短暂有限的同步 I/O | 有界 spawn_blocking 使用 | 队列、最大并发和超时后处理 |
| 长期同步循环 | 专用线程及停止协议 | join、唤醒与退出期限 |
| 大量 CPU 核 | 受限 CPU 池，例如专门的数据并行执行域 | 并行度、NUMA 和任务粒度 |
| 不可合作且需强制中止的工具 | 独立进程 | 进程树、输出、权限和回收 |
| 真正异步 I/O | runtime 资源 driver | readiness、取消与缓冲 |

`spawn_blocking` 不是「CPU 工作自动最优」的按钮。默认阻塞线程上限可能很大；缺少额外准入时，CPU 任务可能制造过量的线程竞争，那时瓶颈就从队列变成了线程数与内存。

::: method 判定流程 · 给一条资源链画上界

① **列资源行**：缓冲、活跃请求、阻塞工作、子进程、结果历史，一行一种（9.7.1 的表）。<br>
② **每行填三格**：谁持有、持有多久、上限在哪里（[@def-9.7.3]）。<br>
③ **找空格**：没有上限的那一行，通常在最早上 `spawn` 或最早读正文的位置。<br>
④ **前移准入**：把取名额的动作放到昂贵分配之前（[@def-9.7.2]）。<br>
⑤ **绑定寿命**：许可随真正的工作移动，进入闭包或随进程池槽位生存。<br>
⑥ **用回归固定行为**：像 9.7.4 那样断言拒绝、复用与排空，而不是用压测替代边界。

:::

### 9.7.6 小结与常见错误

**小结。**① 背压约束的是在途数量，不是某段缓冲区（[@def-9.7.1]）；② 先 spawn 再等 send，等于把内存上界交给了任务创建速度（[@ex-9.7.1]）；③ 准入必须在昂贵分配之前取（[@def-9.7.2]）；④ 许可寿命要覆盖真实占用期，阻塞工作要把许可移进闭包（[@def-9.7.3]）；⑤ 已经开始的阻塞闭包不能靠 abort 终止，要发停止信号并观察 JoinHandle（9.7.4）。下一节 [9.8 公平性、观测与退出协议](#sec-cpp-rust.3.9.8) 把准入、观测与退出收进同一个协议。

::: errata 常见错误清单（9.7 节）

E-a **把有界通道当背压。**它只约束一段缓冲，等待发送者不在计数内（[@def-9.7.1]）。

E-b **先 spawn 再在任务里等 send。**等待者自己就是未受约束的存储（[@ex-9.7.1]）。

E-c **先读完整正文再取许可。**信号量不会追溯性地减少已分配内存（[@def-9.7.2]）。

E-d **许可随调用方释放。**超时丢弃异步任务后闭包仍在跑，并发会超过设定值（[@def-9.7.3]）。

E-e **用 abort 中止已开始的阻塞闭包。**它不终止闭包，要发停止信号并等 JoinHandle。

E-f **把容量为 1 的通道测试当压测证据。**它只验证拒绝、复用与关闭后排队（9.7.4）。

:::

::: method 即时自测 · 9.7

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　用一句话分别说清背压、准入控制、许可寿命。

::: sol 第 1 题答案
背压是让上游等待或失败的机制，约束在途数量（[@def-9.7.1]）；准入控制是在昂贵工作之前先取名额（[@def-9.7.2]）；许可寿命是凭证从取得到归还覆盖的时间段，必须罩住真实占用期（[@def-9.7.3]）。
:::

**第 2 题 · 辨析**　`bounded_channel_and_close_preserve_messages` 能证明队列内存有上界吗？

::: sol 第 2 题答案
不能。它只断言三件事：容量满时 `try_send` 返回 `Full`、腾出槽位后能复用、关闭后仍能排空。它没有测量吞吐，也没有记录内存峰值；内存上界取决于谁在持有请求正文，而这件事发生在通道之外（[@def-9.7.1]）。
:::

**第 3 题 · 应用**　给一条 HTTP 请求链加背压，取名额的那一行该放在哪里？

::: sol 第 3 题答案
放在「读小头部并检查声明长度」之后、「按声明长度分配并读取正文」之前，也就是[@def-9.7.2] 给出的第三行。这样拿不到名额时还没有分配正文；同时要给读入与等名额各设一个期限，否则慢客户端会长期占位。
:::

**第 4 题 · 迁移**　把「许可移进闭包」搬到子进程池，还要注意什么？

::: sol 第 4 题答案
子进程占的不止一个槽：还有 stdout、stderr、输入管道与后代进程（9.7.1 的表）。所以除了把许可与进程生命周期绑定，还要在回收时等待管道关闭与进程退出，并给强制中止留出进程边界；只数「并发进程数」等于把四份资源当成一份（[@def-9.7.3]）。
:::

:::

## 9.8 公平性、观测与退出协议 {#sec-cpp-rust.3.9.8}

本节回答一个问题：**runtime 承诺「被唤醒的任务终会被调度」，这句话在什么前提下成立，又该用什么证据检查它真的发生了？**9.6 与 9.7 分别处理「线程被占住」与「资源没有上界」；这一节把前提、观测与收尾写成一份可以核对的协议。

::: preview 先抓住一件事

公平性是**有前提的等待上界**，不是轮流执行。前提之一是每次 poll 都会返回；内核能抢走整条线程，却抢不走一次 poll 的一半（[@def-9.8.1]）。所以「任务不跑」要先查前提有没有被破坏，而不是先换调度策略。

:::

### 9.8.1 公平性依赖两个有限性前提

本轮版本的 runtime 文档把公平性建立在两个有限性前提上：同时存在的任务总数有上界，每次 poll 返回所需的时间也有上界。在此前提下，runtime 给出「被唤醒的任务最终在有限延迟内得到调度」的保证。

::: def 定义 9.8.1 · 公平性前提 finiteness premises {#def-9.8.1}

**公平性前提**是公平性保证所依赖的两个条件：在途任务数有上界、单次 poll 的时长有上界。前提成立时，被唤醒的任务会在有限延迟内得到调度；这个延迟不是用户可配置的硬实时常数，文档也不承诺任务均匀轮流执行（对照[@def-9.3.2]）。

:::

按[@def-9.8.1]，「我用了 `yield_now`，为什么 B 没有马上运行」不一定是 bug。yield 不是强制切换到指定另一个任务的命令；某些组合 Future 还会让你观察不到预期的外层让出。这时要回到完整的 poll 调用树看，而不是数 `await` 关键字。

::: think 思考 · yield 之后 B 应该马上跑，没跑就是 bug 吗 {#think-9.8.1}

一个任务在循环里每轮 `yield_now().await`，另一个任务 B 早已就绪。有人说：既然让出了，B 就该立刻被 poll。

::: sol 解答

这句话漏掉了一个前提：yield 的作用是把运行权交还执行器，它不指定下一个拿到运行权的是谁（[@def-9.1.2]）。执行器可以立刻再推进同一个任务，也可以选到第三个任务；组合 Future 内部让出时，外层甚至可能根本没有返回 `Pending`。要判断「B 被饿住」，得看 B 的唤醒是否被兑现（[@def-9.1.1]）、以及这段时间里 poll 树实际走了哪一层，而不是看代码里有几个 yield。

:::

:::

### 9.8.2 协作预算管不到纯 CPU 循环

::: def 定义 9.8.2 · 协作预算 cooperative budget {#def-9.8.2}

**协作预算**是 runtime 在它自己掌控的资源操作上做的一项检查：某个任务连续占用了多久，超过阈值就主动让出一次。检查点由 runtime 布置在它能看到的操作里，不覆盖用户代码里的任意循环。协作的前提是「会返回」；不返回的 poll 没有让出的机会。

:::

编译器不会自动在任意 Rust 算术循环里插入 Tokio 调度点。用户的纯 CPU 循环若从不返回，[@def-9.8.2] 就无法从外部安全地抢占那次 poll。本章夹具里的显式 yield 是实验设计的一部分，不能从中推出「Tokio 自动每 16 步抢占」。

操作系统仍然可以抢占运行该 poll 的线程，但那只是把 CPU 交给另一个操作系统线程。同一 current-thread 执行器中的另一个 Future 不会因此自动被 poll——被驱动的是执行器，不是内核。

### 9.8.3 xv6 的 swtch 不是 Future 的 poll

核读的 MIT 6.S081 2020 Lecture 11 是 Thread switching：它解释 xv6 的定时器抢占、寄存器（CPU 内部最快的那一小批存储格子，比缓存还快）与栈的保存，以及 RUNNABLE/RUNNING 的转换。这些内容有助于识别「执行上下文」与「状态责任」的归属。

| 层面 | 谁能拿回控制权 | 粒度 | 状态由谁改 |
|:--|:--|:--|:--|
| xv6 内核 | 定时器中断，强制 | 整条线程 | 内核的进程状态 |
| 用户态 Future | 任务自己返回 `Pending` | 一次 poll | 执行器与状态字 |

但 xv6 的 `swtch` 不是 Future 的 poll。内核可以借助定时器中断强制拿回线程控制；Tokio 不能在任意业务指令处获得同样的 Future 级抢占能力。不区分这两层，就会错误地认为「增加 runtime 队列公平性」足以修复无限 CPU 循环——它甚至可能根本没有再次获得选择队列的机会。

### 9.8.4 观测阶段时间，而不是只有总耗时

::: def 定义 9.8.3 · 阶段时间 stage latency {#def-9.8.3}

**阶段时间**是把一次请求的生命期切成若干有名字的区间，逐段记录各自的时长，而不是只记首尾两点。每段要写清用哪个时钟、怎么采样、靠哪个相关 id 串起来；等待预算与执行预算也要分开记。

:::

服务可以把请求生命期拆成：

```text
arrival
 -> admission_granted
 -> enqueued
 -> execution_started
 -> resource_ready
 -> task_resumed
 -> response_finished
```

只记录 arrival 到 response_finished，五类慢法在里面长得一模一样：准入饱和、排队过长、阻塞 poll、外部资源慢、资源已经就绪但任务恢复慢。按[@def-9.8.3] 切开之后，每一类落在不同的段上；第 9.6 节专门分离最后一种。这比看到吞吐下降就直接加 worker 更能定位问题。

::: ex 例 9.8.1 · 四个读数各指向哪一种慢法 {#ex-9.8.1}

下表是四个请求的阶段读数，每行只有一个差值明显偏大。请按[@def-9.8.3] 判断各属于哪种慢法，并说明只记录总耗时会发生什么。

| 案例 | 偏大的区间 | 其他区间 | 判断 |
|:--|:--|:--|:--|
| ① | arrival 到 admission_granted | 正常 | ？ |
| ② | enqueued 到 execution_started | 正常 | ？ |
| ③ | resource_ready 到 task_resumed | 正常，量级与 9.6 的 25.060 ms 接近 | ？ |
| ④ | arrival 到 resource_ready | 正常 | ？ |

::: sol 解答

① 准入饱和：名额在门口就被卡住，还没进入队列。② 排队过长：已经入队，等的是「轮到执行」。③ 阻塞 poll：资源早已就绪，任务却被占住的执行线程拖着，正是[@def-9.6.2] 的形态。④ 外部资源慢：等待发生在资源返回之前，与执行器无关。若只记总耗时，四行的总数可能相当接近，判定就退化成猜——这就是[@def-9.8.3] 要分段的原因。

:::

:::

::: method 判定流程 · 「这个任务好像不跑」先查三层

① **唤醒是否兑现**：状态字里它被唤醒过吗？有没有丢失唤醒（[@def-9.1.1]、[@def-9.2.1]）？<br>
② **线程被谁占住**：同一条执行线程上是否有阻塞 poll（9.6 的[@def-9.6.2]）？<br>
③ **那次 poll 返回了吗**：无限 CPU 循环里，协作预算没有检查点可用（[@def-9.8.2]）。<br>
④ **别把 OS 抢占当 poll**：内核换线程不产生新的 poll 机会（9.8.3）。<br>
⑤ **最后才怀疑策略**：以上都排除，再谈队列形状与公平性参数。

:::

### 9.8.5 退出不等于丢弃 Runtime

::: def 定义 9.8.4 · 退出协议 shutdown protocol {#def-9.8.4}

**退出协议**是一串有顺序的收尾动作：先停止接受新工作，再逐个观察在途工作的结局，最后才关闭执行域。它的判据是「每一份资源都能说出谁回收了」，而不是「主函数返回了」。

:::

一个可解释的退出协议至少包含七步：

1. 停止接受新工作。
2. 关闭提交入口。
3. 决定排空还是取消在途异步任务。
4. 逐个观察 `JoinHandle` / `JoinSet` 结果。
5. 对阻塞工作发出业务停止信号。
6. 等待必要的外部资源回收。
7. 最后关闭执行域。

Runtime 的 `Drop` 可能等待已经开始、且无法 abort 的阻塞工作——9.7.4 的 `blocking_permit_is_held_inside_closure` 正是这条限制的证据。`shutdown_timeout` 可以停止继续等待，但不等于中止这些闭包。所以「主函数返回了」不能当作「所有工作已安全停止」的证据（[@def-9.8.4]）。

### 9.8.6 本章刻意没有实现的部分

没有手写无锁 work-stealing deque；没有把一份未经验证的 `RawWaker` 示例包装成完整执行器；没有测量网络负载下的全链路 p99；也没有用 macOS 采样假称 Linux perf 硬件计数。本章只采集了聚合 ns/step 与观察延迟两类读数，steal 次数、cache miss、IPC 都没有采集。

这些限制不妨碍本章复现两个具体问题，也不允许把本实验包直接当作项目一交付。项目一仍需调度策略、真实工具适配、取消传播与资源治理的完整集成。

### 9.8.7 小结与常见错误

**小结。**① 公平性是两个有限性前提下的等待上界，不是轮流执行（[@def-9.8.1]）；② 协作预算只在「会返回」的 poll 上有检查点（[@def-9.8.2]）；③ 内核抢占线程不等于 Future 被 poll（9.8.3）；④ 观测要切阶段，否则五类慢法混成一个总耗时（[@def-9.8.3]、[@ex-9.8.1]）；⑤ 退出要逐步观察，别把「主函数返回」当结论（[@def-9.8.4]）。9.6 到 9.8 合起来，才把「任务被唤醒却迟迟不跑」拆成可测的三种原因。

::: errata 常见错误清单（9.8 节）

E-a **把公平性读成轮流执行。**它只是等待上界，还依赖两个前提（[@def-9.8.1]、[@def-9.3.2]）。

E-b **以为 `yield_now` 会切到指定任务。**它只把运行权交还执行器（[@think-9.8.1]）。

E-c **认为 Tokio 会自动每 16 步抢占。**16 是夹具里的显式 quantum，不是 runtime 承诺（[@def-9.8.2]）。

E-d **认为 OS 抢占能让同一执行器里的另一个 Future 跑起来。**内核只换线程，不产生 poll 机会（9.8.3）。

E-e **只记录到达与完成时刻。**五类慢法在总耗时里长得一样（[@ex-9.8.1]）。

E-f **把「主函数返回」当全部工作已停止。**`Drop` 可能还在等无法中止的阻塞闭包（[@def-9.8.4]）。

:::

::: method 即时自测 · 9.8

先合上正文作答，再展开核对。

**第 1 题 · 记忆**　公平性保证的两个前提是什么？它不承诺什么？

::: sol 第 1 题答案
前提是在途任务数有上界、单次 poll 时长有上界（[@def-9.8.1]）。它不承诺轮流执行，也不给出用户可配置的硬实时期限；「被唤醒」与「已运行」之间只有一个有限延迟的保证。
:::

**第 2 题 · 辨析**　一个任务里写了 `yield_now().await`，它就不会独占线程了。对吗？

::: sol 第 2 题答案
只对一半。yield 把运行权交还执行器，但执行器可以再选回同一个任务，也不保证选中你期待的那一个（[@think-9.8.1]）。而且要让预算机制生效，poll 必须返回；写在 yield 之前的无限循环根本走不到这一行（[@def-9.8.2]）。
:::

**第 3 题 · 应用**　线上报「任务变慢」，你只有 arrival 与 response_finished 两个时间戳。下一步做什么？

::: sol 第 3 题答案
补阶段时间（[@def-9.8.3]）：至少加 admission_granted、enqueued、execution_started、resource_ready、task_resumed 五个点，并记下时钟与相关 id。这样五类慢法各落在自己的区间；像[@ex-9.8.1] 那样，一个偏大的区间就能把怀疑范围缩到一处。
:::

**第 4 题 · 迁移**　把本章的退出协议搬到「带子进程的工具调用服务」，要新增哪两步？

::: sol 第 4 题答案
在业务停止信号之后补「等待进程树退出」与「回收 stdout、stderr 与输入管道」两步，并把它们纳入 JoinHandle 的观察（[@def-9.8.4]）。只关闭执行域不够：子进程与管道是执行器之外的资源，9.7.1 的表已经把「后代进程与输出」列为容易遗漏的额外存储。
:::

:::

## 9.10 常见错误索引 {#sec-cpp-rust.3.9.10}

这是本章的跨节错误索引：每一节末尾都有自己的「::: errata 常见错误清单（9.M 节）」，按你阅读的顺序给出局部清单。下面这一份只收那些要读完整个章才浮出来的错误，它们在单节内部看不出问题，放进整章的执行链才露馅。

**把队列弹出等同于 poll 授权。** 队列引用与 RUNNING 独占权是两笔不同的责任，拿到前者不自动取得后者。弹出之后仍要处理任务已经运行、已经完成和已经取消这三种情况，否则重入时会把同一次 wake 兑现两遍（[@ex-9.1.1]）。

**认为合并 wake 就可以忽略同步。** 省去再次入队，省的是队列操作，不是内存可见性义务。你需要指出哪条 Acquire/Release 链让 worker 看见资源更新，否则「少写一次同步」只是把竞争窗口挪到了别处（[@def-9.2.2]）。

**把每次 Pending 都算成一次内核切换。** 执行器可能只切换用户态任务，也可能马上重新安排同一个 Future。把 Pending 的计数直接写成线程切换次数，会让上下文切换的结论整体虚高。

**把 Pin 当成线程亲和性。** 地址不移动，不意味着下一次 poll 仍在同一 worker 上运行。线程局部资源需要单独约定，不能靠给 `Pin` 追加它没有做出的承诺（[@def-9.1.2]）。

**以为 current-thread 下 `tokio::spawn` 自动接受 `!Send`。** `Send` 边界写在公共 API 的类型签名上，不会因为 runtime 配置而消失。要跑 `!Send` 任务，得使用受驱动的局部任务机制，并自己检查它的生命周期。

**把 `yield_now` 当成指定任务切换。** 它不承诺严格轮流，也不提供用户可选的硬实时期限。判断「B 被饿住」要看完整的 poll 树和具体执行器版本，而不是数代码里有几个 `yield`（[@think-9.8.1]）。

**只比较 ns/step，不测无关任务的恢复延迟。** 吞吐改善可能以更长连续占用为代价，两个读数回答的不是同一个问题。本章的两个 benchmark 就是为这两种问法分别设计的（[@def-9.5.1]、[@def-9.6.1]）。

**认为增加 worker 等于修复阻塞 poll。** 加线程只是暂时增加可被占满的线程数，阻塞调用仍然留在原处。阻塞工作要放进合适的执行域，并给它单独的边界（[@def-9.6.2]）。

**认为有界通道可以限制无限 spawn。** 等待发送的 Future 自己也持有内存，通道容量只管已经进入缓冲的那一段。准入必须覆盖真正的在途工作集合，而不是某一个队列的长度（[@def-9.7.2]、[@ex-9.7.1]）。

**超时后释放阻塞工作的许可。** 调用方退出时闭包可能仍在运行，许可却已经归还。许可应由实际工作持有到完成，否则名义并发会超过设定值（[@def-9.7.3]）。

**把 abort 当成已完成析构。** 要观察 `JoinHandle` 的结果，已经开始的 `spawn_blocking` 还不能依靠 abort 终止。把取消请求当成回收完成，退出协议就少了一步（[@ex-9.2.3]）。

**把采样中的 kevent 或 dyld 全部解释成业务 CPU 开销。** 前者可能是零时长检查，后者是启动污染。看到这类样本先问它落在阶段时间的哪一段，不要直接记进业务成本（[@def-9.8.3]）。

## 9.11 本章小结与章末件 {#sec-cpp-rust.3.9.11}

::: note 本章小结

- 状态字把「已入队、已通知、已取消」压进一个原子字，每次转换都要说清旧值与新值（[@def-9.1.1]）。
- 拿到队列引用不等于拿到运行权，运行、完成、取消三种状态各有归属（[@def-9.1.2]、[@ex-9.1.1]）。
- 合并 wake 省的是入队，不是可见性，Acquire/Release 链要指向具体资源（[@def-9.2.2]、[@ex-9.2.2]）。
- ns/step 是聚合口径，回答吞吐，不回答单次调用延迟（[@def-9.5.1]、[@ex-9.5.1]）。
- 阻塞 poll 会把整个 worker 拖住，offload 只改变等待发生在哪（[@def-9.6.2]、[@ex-9.6.1]）。
- 有界通道不等于有界任务，许可寿命要覆盖真实占用期（[@def-9.7.3]、[@ex-9.7.1]）。
- 退出要先停准入、再排空、最后关执行域，顺序反了就会丢工作（[@def-9.8.4]、[@ex-9.8.1]）。

:::
