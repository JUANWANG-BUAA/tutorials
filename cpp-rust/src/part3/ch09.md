## 9.1 从一个通知位到任务状态机 {#sec-cpp-rust.3.9.1}

### 为什么不能直接给每个Future复制一个block_on

第8章驱动器只需要维护一个Future。
它的通知位表示“再poll一次可能有用”。
复制一百份该驱动器并开一百条线程，可以获得并发。
但这没有解决用户态多任务调度。
它把并发上限、栈空间和调度开销交给了操作系统线程。

多任务执行器需要回答另外一组问题。

1. 哪些Future需要再次poll？
2. 哪个worker获得poll的独占权？
3. Future正在运行时到来的wake，由谁负责入队？
4. Future完成后到来的旧wake，如何避免访问已释放存储？
5. JoinHandle与队列引用分别维持什么生命周期？
6. 取消什么时候才能真的执行析构？

这些不是“把Vec换成无锁队列”就能自动获得的性质。
队列正确性与任务生命周期正确性是两份证明。
队列中的元素必须携带足以维持任务存活的所有权。
弹出任务也不代表立即获得合法的可变访问。

### 固定版本的观察范围

本轮核读Tokio1.54.0的以下源文件指定范围：

- `src/runtime/mod.rs`的Detailed runtime behavior。
- `src/runtime/task/state.rs`的状态定义与运行/通知/取消转换。
- `src/runtime/scheduler/current_thread/mod.rs`的park_yield路径。
- `src/task/blocking.rs`的阻塞任务与取消说明。

源码路径和SHA-256记入`sources/runtime-code.json`。
这是版本内实现分析，不是稳定公共ABI。
也不是把Tokio全部unsafe代码审计了一遍。

### 状态位不是五个独立布尔量

该版本的任务状态字同时记录：

| 成分 | 含义 | 需要共同维持的不变量 |
|:--|:--|:--|
| RUNNING | 某个线程取得运行权 | 同时不能有第二个poll所有者 |
| COMPLETE | 任务已经完成 | 不再重新执行Future |
| NOTIFIED | 已有通知责任 | 重复wake不能无限复制队列项 |
| CANCELLED | 取消请求已经登记 | 请求本身不是抢占 |
| JOIN_INTEREST / JOIN_WAKER | 结果观察者及其通知 | 输出与等待者寿命配合 |
| 引用计数部分 | 任务存储所有权 | 最后引用释放后才能回收 |

不能把其中任何一位脱离引用计数谈正确性。
例如“已经通知”可能对应一个队列引用。
消费该通知时，运行者接管其生命周期责任。
如果运行失败，也必须正确消费或转交该引用。

:::def 运行权与通知责任

**运行权**保证Future不会被两个线程同时poll。
**通知责任**保证发生有效wake后，未来有人重新检查这个Future。
二者可以同时存在，但不能被当成同一个锁位。

:::

### 概念状态图

<pre class="layout">
                         wake
       idle / not queued ------&gt; notified / queued
              ^                         |
              |                         | acquire RUNNING
              |                         v
              |                    running / polling
              |                       /       \
              |          Pending     /         \ Ready
              |                     v           v
              +----- not notified / idle       complete
                              ^
                              |
         running期间wake：登记NOTIFIED，由运行者在退出poll时决定重排
</pre>

读图：箭头表示逻辑责任交接，不表示每条边都对应一次队列操作。
正在运行的任务收到wake时，可以先只登记通知。
如果立即另插一个可被第二个worker执行的裸指针，就会破坏独占poll。
完成后的旧Waker也不意味着Future可以重新开始。

### 从原子修改序到生命周期

Tokio的源码注释明确把状态转换放在RMW操作上。
这提供状态字上的明确修改顺序。
但仅有修改顺序并不能解释全部内存安全。
仍要把Future存储、输出存储和引用释放接到具体转换上。

本章只追踪相关责任，不给出“一个AcqRel就证明执行器正确”的口号。
读者应能指出至少三个不同对象：

- 被poll的Future存储。
- 对执行器可见的通知对象。
- 等待结果的JoinHandle状态。

它们可以在一个分配中协同布局。
逻辑上仍有不同的初始化、访问与销毁阶段。

## 9.2 并发wake、重复入队与取消边界 {#sec-cpp-rust.3.9.2}

### 正在运行时发生wake

考虑资源线程与worker的交错。

```text
worker                         resource thread
取得RUNNING
清除当前通知
poll(resource)
                               资源完成
                               wake_by_ref()
poll返回Pending
检查NOTIFIED
将任务重新安排
```

若worker在poll之后直接把状态设为idle，而不检查并发通知，可能丢失进展。
若资源线程不管任务是否运行都立即执行poll，可能产生并发可变访问。
正确协议需要在状态转换中区分这两种情形。

Tokio1.54.0的`transition_to_notified_by_ref`可概括为：

| 观察状态 | 动作 | 是否产生新的提交责任 |
|:--|:--|:--|
| complete | 不重新执行 | 否 |
| already notified | 合并通知并保持同步关系 | 否 |
| running | 设置notified | 由当前运行者负责 |
| idle且未通知 | 设置notified并增加相应引用 | 是 |

这是源码逻辑摘要，不是可替换的伪实现。
实际代码还处理引用计数与失败重试。
不能照着四行表格写一个裸指针队列并宣布正确。

### “合并”不意味着没有内存序义务

已经被通知的任务再收到一次wake，可能不必再次入队。
但发起wake的线程此前也可能发布了资源状态。
不再入队，不代表可以删除所有同步效果。

被核读版本的源码在already-notified分支中特别说明了这个问题。
它仍需要与后续运行转换配合的Release效果。
这是第7章知识进入执行器内部的具体位置。

错误的推理是：

> 反正任务已经排队，再来的wake什么都不用做。

正确的问题是：

> 哪个后续操作会观察到这次wake之前的资源更新？

有时资源自身的同步协议也会提供边。
这不允许执行器随意削弱它承诺的通知协议。
多个协议组合时，要说明各自承担的同步责任。

### Pending不是睡眠指令

Pending只是在这次poll中没有产出最终结果。
Future可以因为I/O、锁、通道、计时器或主动让出而Pending。
这些原因对应不同的唤醒来源。

执行器可能立即改poll另一个任务。
也可能发现所有任务都在等外部事件，进入driver等待。
还可能收到此前已经登记的通知，马上重新安排同一任务。

因此一次Pending不能直接换算成一次内核上下文切换。
同样，一次wake不能直接换算成一次线程唤醒。
很多wake只影响已有运行线程的本地工作集合。

### 取消是状态请求，不是指令边界抢占

对运行中的异步任务调用abort，执行器先登记取消意图。
正在执行的poll不会被Rust语言机制强行切成两半。
它必须先返回执行器控制。

如果poll里执行不返回的CPU循环，取消也无法在任意指令处介入。
如果poll里阻塞在本地系统调用上，执行器也不能靠设置一个位就把调用撤回。
这与线程的操作系统抢占是不同层面的问题。

:::errata abort与销毁不能画等号

`abort()`返回只能说明取消请求已发出。
需要等待JoinHandle完成，才能观察该任务是否已结束并执行了相应析构。
已经开始执行的spawn_blocking闭包还具有更强的不可中止限制。

:::

### 本轮取消回归测试

完整代码在`tests/contracts.rs::abort_observed_and_drop_executed`。
测试先等待任务进入，再请求取消。
Drop守卫经oneshot通知外部观察者。

```rust
struct Signal(Option<tokio::sync::oneshot::Sender<()>>);
impl Drop for Signal {
    fn drop(&mut self) {
        if let Some(tx) = self.0.take() {
            let _ = tx.send(());
        }
    }
}
```

随后检查JoinError是cancelled，并等待Drop信号。
这比“调用abort后立即读一个非同步计数器”更明确。
测试没有证明所有Future都可及时取消。
它验证的是合作式挂起点上的一个具体生命周期场景。

### 任务panic与业务错误也要分层

任务返回`Result<T,E>`，JoinHandle本身仍可能失败。
前者是业务完成结果。
后者可能表示panic或取消。
把两层Result压成一个字符串，会丢失调度层证据。

本轮`joinset_observes_panic_and_completes_other_task`同时创建：

- 一个故意panic的任务。
- 一个正常返回的任务。

测试持续join，分别计数正常完成与panic。
它没有因为一个任务失败就忘记收集其余任务。
实际服务可以选择失败即取消其他任务，但仍需完成回收。

## 9.3 队列、LIFO槽与work stealing {#sec-cpp-rust.3.9.3}

### 队列层次与硬件局部性

单一全局队列容易说明顺序，却让所有worker争夺同一入口。
每worker局部队列可以减少这种争用。
代价是负载不均与跨worker迁移需要额外协议。

本轮版本的运行时文档描述了：

- 多线程runtime的一条全局队列。
- 每worker各自的局部队列。
- 局部队列溢出时向全局队列转移部分任务。
- 本地无活可做时，从其他worker窃取部分任务。
- 特定唤醒路径使用的LIFO槽优化。

这些结构是调度策略，不是任务Future的语义组成。
换一个执行器，Future的poll契约不应改变。
但任务的实际等待分布、局部性与通知开销可能显著变化。

### 当前版本的参数不是语言常量

| 机制 | Tokio1.54.0文档中的观察 | 不应推导出的结论 |
|:--|:--|:--|
| 多线程局部队列 | 最多256任务，溢出转移部分到全局 | 所有版本永远固定256 |
| 空闲worker窃取 | 转移另一局部队列中的一部分任务 | 每次窃取一个必然更公平 |
| current-thread全局检查 | 文档默认31次本地选择后检查 | 每个任务31次内一定运行 |
| I/O/计时器检查 | 文档描述61次调度间隔等触发条件 | 定时器误差固定61纳秒 |
| multi-thread全局检查 | 默认可动态估计检查间隔 | 默认始终等于某个固定次数 |
| LIFO槽 | 连续使用受约束，且不能被其他worker窃取 | 唤醒的任务必定下一条执行 |

不要把参数表当成调参建议大全。
要先检查当前运行版本与工作负载。
很多“调快runtime”的配置，只是把延迟从一类任务转给另一类任务。

### 为什么LIFO可能有利

任务A把数据交给任务B，然后自己等待B的结果。
若B尽快在同一worker运行，数据可能仍在本地缓存中。
这也可能减少全局排队与跨核通知。

但长期只追着刚唤醒的任务跑，会饿死其他已就绪任务。
所以局部性优化必须受公平性机制约束。
本轮版本的文档明确讨论了LIFO连续使用限制与预算。

不要把这些实现细节误写成：

> Tokio就是严格深度优先调度。

也不要反向宣称FIFO队列就意味着整个runtime严格FIFO。
执行器有多个入口与多个worker。
队列局部顺序不等于全局完成顺序。

### stealing迁移的是调度责任

stealing不意味着复制整个Future业务数据。
队列元素可以只是任务所有权或通知的轻量表示。
任务实际存储的位置可以保持不变。

但是后续访问该存储的CPU可能变化。
这影响缓存局部性、NUMA放置和线程局部数据。
本机没有NUMA测量，不能用本轮结果给出跨插槽建议。

某个Future在两个poll之间换worker运行，并不违背Pin。
Pin约束的是被pin对象的地址移动。
它不保证执行该对象代码的CPU或线程固定。
这也是线程亲和性不能由Pin推出的原因。

### !Send任务与局部执行

`tokio::spawn`对Future与输出有Send约束。
即使你配置current-thread runtime，这个公共API约束也不会自动消失。
不能凭“这里只有一个worker”解释为什么Rc捕获一定可spawn。

要运行!Send任务，应使用适当的局部任务机制，例如被实际驱动的LocalSet。
它解决的是不能跨线程转移的任务存储约束。
它仍不保证任务不会互相阻塞。
一个!Send任务执行无限循环，同样可以卡住整个局部执行环境。

### 对性能归因的约束

观察multi4快于current，并不能立刻断言是stealing成功。
还可能包含：

- 真正并行的业务计算。
- 不同driver检查路径。
- 不同join通知路径。
- 任务创建与完成的重叠。
- 主线程与worker间的同步。

本轮没有给队列每次窃取打点。
所以实验只报告配置总体效果。
它不报告没有采集的steal成功率或每次steal周期数。

## 9.4 类型、ABI与代码生成边界 {#sec-cpp-rust.3.9.4}

### 公共类型约束和内部擦除

泛型spawn入口可以在编译时检查Future类型。
调度队列却不能为每一个业务Future维护一种独立队列类型。
执行器内部需要某种统一的任务表示。

统一表示不一定等于`Box<dyn Future>`。
实现可以把通用头、具体Future、结果区域与专用函数表组合。
内部调度入口通过擦除后的任务指针调用具体类型对应的操作。

这与“Rust所有异步调用都是静态分派”不矛盾。
业务Future内部的很多调用可以单态化与内联。
执行器调度边界仍可能有间接调用。
必须指出自己在讨论哪一层。

| 层次 | 约束/表示 | 性能与安全问题 |
|:--|:--|:--|
| 业务Future | 具体编译器生成类型 | 跨await字段与状态大小 |
| spawn入口 | Future和Output的Send、'static等边界 | 能否被runtime持有和跨线程转移 |
| 任务头 | 版本内通用状态与生命周期信息 | 原子更新、对齐与共享争用 |
| 原始调度入口 | 类型擦除后分发poll/完成操作 | 间接调用与运行权 |
| JoinHandle | 观察结果的句柄 | 不拥有独占执行线程 |
| LocalSet任务 | 允许!Send但局部驱动 | 线程限制不等于吞吐保证 |

### 本机类型尺寸探针

完整程序在`examples/type_layout.rs`。
输出保存在`type-layout.txt`。

| 类型/对象 | size | align | 说明 |
|:--|--:|--:|:--|
| yield_now返回的Future | 16 | 8 | 固定版本和功能集下的实际对象 |
| JoinHandle&lt;u64&gt; | 8 | 8 | 句柄大小，不是任务总分配量 |
| mpsc::Sender&lt;u64&gt; | 8 | 8 | 发送端大小，不是整个通道大小 |
| 实验Frame | 16 | 8 | 线协议仍使用显式24字节编码 |

不能把8字节JoinHandle解释成每任务只需要8字节。
背后还有任务存储、队列引用、Future、输出、分配器开销等。
同理，小Sender可以指向很大的共享通道状态。

### ABI/代码生成表

| 边界 | 本章核验方式 | 可以下的结论 |
|:--|:--|:--|
| step(u64)到u64 | `scheduling.s`中的实际符号 | 输入/返回经本轮寄存器约定，计算保留 |
| 具体Future的poll路径 | 保留的raw poll实例及业务闭包符号 | 两种scheduler路径均有具体实例 |
| 任务运行权 | 生成代码调用transition_to_running | 不是拿到队列元素就无条件poll |
| 状态RMW | 目标汇编可见casal等指令 | 确实保留原子状态操作，不能据此计算总同步开销 |
| 任务结果 | JoinSet逐个收集 | 完成观察包含通知与校验工作 |

这里没有承诺稳定的Rust函数ABI。
也没有把内部函数表格式当成可供C直接调用的接口。
若要FFI，必须另外设计明确的C ABI与所有权契约。

### 业务计算没有被整段折叠

`scheduling.rs::step`使用inline(never)与标准库black_box。
保存的汇编中可见对step的实际调用。
step内部保留输入屏障、乘加与返回。
核心片段如下，省略了调试位置指示：

```asm
str x0, [sp, #8]
ldr x8, [sp, #8]
mov x10, #1
madd x0, x8, x9, x10
ret
```

x9的常量由前面的mov/movk序列构造。
完整符号而不是这五行才是代码生成证据。
black_box不是硬件内存屏障。
它也不能代替对完整优化后产物的检查。

### noinline的代价也属于夹具

每个逻辑step包含一次有意保留的函数调用。
这让工作量容易验证。
也意味着结果不是纯整数乘法吞吐。

把这些ns/step拿去预测向量化数值核会误导。
向量化数值核通常希望内联和批量加载。
本实验要保留的是很多小型业务步与调度之间的竞争。

## 9.5 benchmark一：让出粒度与worker数 {#sec-cpp-rust.3.9.5}

### 问题与计量单位

实验入口：`src/bin/scheduling.rs`。
每批创建128个任务。
每任务执行8192个逻辑step。
每批总计1048576个step。

只改变两件事：

1. current-thread或4-worker runtime。
2. 每16步或每1024步执行一次yield_now。

每次yield发生在一块计算之后。
因此同一任务的8192步业务递推保持一致。
任务间的执行交错不同，但最终每任务结果应相同。

报告单位是墙钟时间除以聚合step数。
它不是每次poll耗时。
不是一次yield的独立延迟。
也不是一个任务从到达到完成的响应时间。

### 创建与回收是否计入

| 阶段 | 是否进入每批计时 | 理由 |
|:--|:--|:--|
| 创建两种runtime | 否 | 避免混入runtime线程启动比较 |
| 预计算校验结果 | 否 | 不把串行参考重复算进测量 |
| 每批创建128任务 | 是 | 这是被测多任务生命周期的一部分 |
| 每个step | 是 | 主要业务工作 |
| yield与重新调度 | 是 | 核心被测差异 |
| JoinSet收集所有完成 | 是 | 批完成必须可观察 |
| 批后比较最终checksum | 否 | 时间戳之后执行 |
| 析构整个runtime | 否 | 不测runtime冷退出 |

不要把本表偷换成“只测调度器本体”。
任务创建、通知、业务和join都在表内。
这是一种有明确边界的系统级微基准。

### 任务核心

完整源文件中还包含统计、校验与case顺序轮转。
以下片段保持与其业务核心一致：

```rust
for id in 0..TASKS {
    tasks.spawn(async move {
        let mut value = id;
        for chunk in 0..STEPS / quantum {
            for _ in 0..quantum {
                value = step(value);
            }
            std::hint::black_box(chunk);
            tokio::task::yield_now().await;
        }
        (id, value)
    });
}
```

两种quantum都整除8192。
没有遗漏尾部step。
checksum按任务id对结果做旋转并异或，因此与完成顺序无关。
参考checksum在计时之外预先计算。

这种校验不能识别所有可能的错误，因为checksum有碰撞可能。
但它明显优于不观察任何输出。
任务数还会独立核验为128。
若改造夹具，应保留这些观察点。

### 预热与顺序

先至少预热500ms。
预热中交替运行四个case。
正式测量每case21批。
每轮轮转case起点，避免配置与时间漂移完全重合。

没有把四个benchmark进程并行启动。
没有把profiler附着到正式计时进程。
本机仍是桌面系统，没有锁核、锁频或隔离热状态。

### 本轮结果

来源：`runtime-fixed/measurements-final/scheduling.txt`。
全部数值为ns/聚合step，标准差采用N-1。

| runtime / quantum | mean | sd | 批p50 | 批p99 |
|:--|--:|--:|--:|--:|
| current / 16 | 16.360 | 0.365 | 16.426 | 16.916 |
| current / 1024 | 2.602 | 0.049 | 2.604 | 2.684 |
| multi4 / 16 | 2.033 | 0.111 | 2.036 | 2.291 |
| multi4 / 1024 | 0.750 | 0.015 | 0.749 | 0.783 |

21个批均值的nearest-rank p99就是该case最大批均值。
不要把16.916ns解释成任务尾延迟。
小于1ns的聚合倒数也不表示单核调用step仅花不到1ns。
四个worker可能并行完成不同任务。

### 可以支持的结论

在这个固定工作负载和本机环境下：

- 更细的显式yield显著增加聚合成本。
- 4-worker配置相对current-thread获得更低的聚合ns/step。
- 改变quantum影响的不只是计算块长度，还影响调度与driver路径频率。

不能支持的结论包括：

- 所有服务都应把yield间隔设为1024。
- 多线程runtime对所有I/O服务必然更快。
- 本轮已测出work stealing的单次成本。
- 更低ns/step一定带来更低单请求p99。

### 为什么吞吐与公平性可以冲突

quantum更大，通常意味着在一次返回执行器前做更多业务。
这样可以摊薄调度开销。
但如果一个业务step的时间上界也随输入变大，其他任务可能等得更久。

8192次小整数递推不是不可控解压、正则回溯或外部库调用。
不能用这个小核证明真实业务poll时间始终有界。
在实际服务里，应另外测最大poll持续时间与事件循环延迟。

### profiler核对与限制

另行运行的`scheduling-sample.txt`保存在`runtime-fixed/measurements-final/`。
它使用同一版scheduling业务源码，不参加正式21批统计。
采样同时看到current-thread路径、multi-thread worker、step与wake相关符号。

其中也出现current-thread的park_yield到driver再到kevent路径。
核对固定版本源码可知park_yield使用零时长driver检查。
出现kevent不意味着这里每次都长时间睡眠。
非阻塞检查也可以经过同一系统接口。

这解释了为什么不能把current-q16的额外成本全归给一次原子操作。
它可能包含更频繁的driver检查与通知处理。
但本轮没有逐次打点，不能计算这些成分各占多少纳秒。

采样还包含dyld启动与预热阶段。
两个runtime在同一进程中轮转，空闲worker也被采到。
所以不把该报告转成稳定态CPU百分比或四核利用率。

## 9.6 benchmark二：阻塞poll污染观察延迟 {#sec-cpp-rust.3.9.6}

### 一个没有数据竞争的性能故障

实验入口：`src/bin/blocking_poll.rs`。
只使用current-thread runtime。
被测任务先经oneshot发出一个Instant，再执行20ms本地睡眠。
观察任务等待该oneshot，并记录从发送到真正恢复执行的时间。

两种实现：

- inline：直接在异步任务中调用thread::sleep。
- offload：把发送与sleep一起放进spawn_blocking闭包。

两者的睡眠工作都实际执行。
区别是占用异步执行线程，还是占用阻塞池线程。
没有执行UB，也没有用原始指针绕过Rust同步。

### 为什么时间戳放在发送方

如果观察者在recv返回后才开始计时，会错过被阻塞的那段时间。
因此时间戳必须在通知真正发出的位置创建。
时间戳随oneshot消息一起传递。

```rust
let sent = rx.await.expect("sender alive");
let delay = sent.elapsed().as_secs_f64() * 1e9;
task.await.expect("async worker panicked");
```

最后仍join被测任务。
这样offload分支不会把未完成的睡眠留到下一批。
但报告的delay不包含等待其余睡眠完成的时间。
这是观察延迟，不是该任务完整执行时间。

### 错误分支为何确定污染同一线程

inline任务在send之后立刻进入本地sleep。
当前线程没有回到执行器。
接收任务虽然逻辑上可运行，却没有机会继续执行。
等sleep结束、发送任务的poll返回，执行器才可能推进观察者。

因此这个故障不依赖碰巧把两个任务放到同一worker。
夹具选择current-thread，使调度边界清楚。
多线程runtime中也可能发生污染，但需要考虑任务实际放置和其他负载。
本章没有把当前实验直接当成多线程全局停顿。

### 结果与单位

来源：`runtime-fixed/measurements-final/blocking-poll.txt`。
修订后每case至少预热500ms，正式观察21次，case顺序交替。
原始文件以ns/op输出，表格转成更易读单位。

| 实现 | 平均观察延迟 | 样本sd | 观察p50 | 观察p99 |
|:--|--:|--:|--:|--:|
| inline | 23.658ms | 1.302ms | 23.604ms | 25.060ms |
| offload | 13.633µs | 3.494µs | 14.125µs | 18.541µs |

这里每个原始观察是一次通知的恢复延迟。
它不同于第一个benchmark的批均值。
不过21个观察仍远不足以稳定估计生产请求的极端尾分布。
表中的p99仅为这个小样本的nearest-rank分位数。

20ms是申请睡眠时间，不是保证实际睡眠恰好20ms。
桌面系统调度和计时器可能增加延迟。
结果比20ms大不构成语言或runtime违反承诺。

### 这个实验没有证明什么

它没有证明spawn_blocking能让睡眠本身更快完成。
没有证明阻塞池线程零成本。
没有证明将所有CPU工作都丢到阻塞池会提升吞吐。

offload分支只使异步执行线程不再被该sleep占住。
如果阻塞工作大量积压，队列延迟、线程数和内存仍会出问题。
若业务必须硬中止不可合作的第三方代码，需要额外进程边界。

:::method 回归判断先看被污染对象

本例的回归不是“被测任务慢了20ms”。
业务本来就要求睡眠。
真正的回归是一个无关观察任务在消息已可用后仍被拖住。
排查异步系统应测这种事件循环或通知恢复延迟，而不只看吞吐。

:::

### 调试时不要用更多worker掩盖问题

从一个worker改成四个，可能减轻单个错误sleep的影响。
但四个并发阻塞任务又可以占满四个worker。
配置扩容不等于移除了错误的执行边界。

正确修复需要把有限阻塞工作移到合适执行域。
同时控制该域的并发、队列和取消策略。
接下来讨论的背压就是这个修复的一半。

## 9.7 背压、许可寿命与资源上界 {#sec-cpp-rust.3.9.7}

### bounded channel只限制一段缓冲

Tokio mpsc的有界通道可以使send等待容量。
这控制通道内部排队数量。
它不自动控制已经创建、正在等send的任务数量。

若对每个请求先spawn，然后在任务内部等待有界send，仍可能创建无限任务。
这些任务可能各自持有请求正文、连接引用和上下文。
队列只有64个槽，进程仍然可以因为等待发送者而耗尽内存。

| 资源 | 常见边界 | 容易遗漏的额外存储 |
|:--|:--|:--|
| 通道缓冲 | channel(capacity) | 等待send的任务和消息 |
| 活跃请求 | admission semaphore | 已接收但尚未取得许可的请求体 |
| 阻塞工作 | 闭包内持有的permit | 提交队列和调用方的临时对象 |
| 子进程 | 进程池/并发许可 | stdout、stderr、输入及后代进程 |
| 结果历史 | 固定容量结果队列 | JoinHandle和未消费输出 |

不同边界控制不同队列。
只画一条“并发数=64”不能替代完整资源图。

### 把准入放在大对象分配之前

一个实用的顺序是：

```text
小头部读取
  -> 检查声明长度与身份
  -> 取得系统准入预算
  -> 在预算内读取正文
  -> 投递到有界执行队列
  -> 完成/失败/取消
  -> 释放对应预算
```

这不是唯一正确顺序。
但如果读取无限大正文在最前面，后面的信号量不会追溯性地减少已分配内存。
如果取得许可之后还无限等待上游输入，又会被慢客户端长期占位。
因此读入期限、长度和准入期限应共同设计。

### 本轮可执行背压测试

`bounded_channel_and_close_preserve_messages`验证容量为一的边界：

```rust
let (tx, mut rx) = tokio::sync::mpsc::channel(1);
tx.try_send(10).expect("first slot");
assert!(matches!(
    tx.try_send(20),
    Err(tokio::sync::mpsc::error::TrySendError::Full(20))
));
assert_eq!(rx.recv().await, Some(10));
tx.send(20).await.expect("space reused");
drop(tx);
assert_eq!(rx.recv().await, Some(20));
assert_eq!(rx.recv().await, None);
```

这里只验证容量拒绝、复用与关闭后排空。
没有测量通道吞吐，也没有报告队列内存峰值。
将这个测试当成百万请求压测证据是不成立的。

### 许可必须跟随真正的工作

一个常见但隐蔽的错误：

```text
异步任务取得permit
提交spawn_blocking
异步任务超时并被丢弃
permit随异步任务释放
阻塞闭包仍然运行
新请求取得刚释放的permit
实际阻塞并发超过设定值
```

这个错误完全可以发生在安全Rust中。
所有权系统保证对象按规则销毁。
它不知道你本来希望permit对应“调用方活着”还是“阻塞工作还在执行”。

若许可代表阻塞资源占用，应把owned permit移入闭包。
调用方取消时，许可仍由正在运行的工作持有。
闭包结束，许可才归还。

### 已开始的阻塞任务不能依赖abort终止

本轮`blocking_permit_is_held_inside_closure`先等待闭包发出started信号。
然后对其JoinHandle调用abort。
闭包仍在等待一个同步停止信号。

此时再尝试取得唯一permit，必须失败。
随后发送停止信号，等待闭包完成。
最后再次取得permit，必须成功。

测试刻意不用固定sleep猜测“闭包应该已经启动了”。
started消息建立明确的阶段关系。
这避免把尚未启动就被abort的情况和已经运行的情况混淆。

### 有限阻塞、长期线程与CPU池

| 工作特征 | 更合适的执行域 | 必须另外说明 |
|:--|:--|:--|
| 短暂有限的同步I/O | 有界spawn_blocking使用 | 队列、最大并发和超时后处理 |
| 长期同步循环 | 专用线程及停止协议 | join、唤醒与退出期限 |
| 大量CPU核 | 受限CPU池，例如专门的数据并行执行域 | 并行度、NUMA和任务粒度 |
| 不可合作且需强制中止的工具 | 独立进程 | 进程树、输出、权限和回收 |
| 真正异步I/O | runtime资源driver | readiness、取消与缓冲 |

spawn_blocking不是通用“CPU工作自动最优”按钮。
默认阻塞线程上限可能很大。
缺乏额外准入时，CPU任务可能制造过量线程竞争。

## 9.8 公平性、观测与退出协议 {#sec-cpp-rust.3.9.8}

### 公平性保证有前提

本轮版本的runtime文档把公平性表述建立在两个有限性前提上：

- 同时存在的任务总数有一个上界。
- 每次poll返回所需时间有一个上界。

在此前提下，runtime给出被唤醒任务最终在有限延迟内得到调度的保证。
这个有限延迟不是用户直接配置的硬实时常数。
文档也不承诺任务均匀轮流执行。

所以“我用了yield_now，为什么B没有马上运行”不一定是bug。
yield不是强制切换到指定另一个任务的命令。
甚至某些组合Future可能使你观察不到预期的外层让出。
这里应回到完整poll调用树，而不是只数await关键字。

### CPU循环与协作预算

runtime可以在它掌控的资源操作中检查协作预算。
但编译器不会自动在任意Rust算术循环中插入Tokio调度点。
用户的纯CPU循环若从不返回，预算机制无法从外部安全地抢占该poll。

本章显式yield是夹具的一部分。
不能从中推导“Tokio自动每16步抢占”。
操作系统仍可以抢占运行该poll的线程。
这只能把CPU交给其他操作系统线程。
同一current-thread执行器中的另一个Future不会因此自动被poll。

### MIT与用户态async的边界

核读的MIT6.S0812020 Lecture11是Thread switching。
它解释xv6定时器抢占、寄存器/栈保存和RUNNABLE/RUNNING转换。
这些内容有助于识别执行上下文与状态责任。

但xv6的swtch不是Future的poll。
内核可以借助定时器中断强制拿回线程控制。
Tokio不能在任意业务指令处获得相同的Future级抢占能力。

不区分这两层，就会错误地认为增加runtime队列公平性足以修复无限CPU循环。
它甚至可能根本没有再次获得选择队列的机会。

### 建议观测的是阶段时间，不是只有总耗时

服务可以把请求生命期拆成：

```text
arrival
 -> admission_granted
 -> enqueued
 -> execution_started
 -> resource_ready
 -> task_resumed
 -> response_finished
```

每段都应明确时钟、采样与相关id。
等待预算与执行预算也应分别记录。

只记录arrival到finished，难以区分：

- 准入饱和。
- 排队过长。
- 阻塞poll。
- 外部资源慢。
- 资源已经就绪但任务恢复慢。

第9.6节专门分离最后一种延迟。
这比看到吞吐下降后直接加worker更能定位问题。

### 退出不等于丢弃Runtime

一个可解释的退出协议至少包含：

1. 停止接受新工作。
2. 关闭提交入口。
3. 决定排空还是取消在途异步任务。
4. 逐个观察JoinHandle/JoinSet结果。
5. 对阻塞工作发出业务停止信号。
6. 等待必要的外部资源回收。
7. 最后关闭执行域。

Runtime的Drop可能等待已经开始且无法abort的阻塞工作。
shutdown_timeout可以停止继续等待，但不等于中止这些闭包。
不能把“主函数返回了”当作“所有工作已安全停止”的证据。

### 本章刻意没有实现的部分

没有手写无锁work-stealing deque。
没有把一份未经验证的RawWaker示例包装成完整执行器。
没有测量网络负载下的全链路p99。
没有用macOS采样假称Linux perf硬件计数。

这些限制不妨碍本章复现两个具体问题。
也不允许把本实验包直接当作项目一交付。
项目一仍需调度策略、真实工具适配、取消传播和资源治理的完整集成。

## 9.10 常见陷阱 {#sec-cpp-rust.3.9.10}

1. **把队列弹出等同于poll授权。**
   队列引用与RUNNING独占权是不同责任。
   仍要处理已经运行、已完成和已取消等情况。

2. **认为合并wake就可以忽略同步。**
   省去再次入队不等于省去内存可见性义务。
   要说明哪条Acquire/Release链观察资源更新。

3. **把每次Pending都算成一次内核切换。**
   runtime可能只切换用户态任务。
   也可能马上重新安排同一Future。

4. **把Pin当成线程亲和性。**
   地址不移动不意味着后续poll在同一worker运行。
   线程局部资源需要单独的契约。

5. **以为current-thread下tokio::spawn自动接受!Send。**
   公共API的Send边界不会因配置而消失。
   使用受驱动的局部任务机制，并检查其生命周期。

6. **把yield_now当成指定任务切换。**
   它不承诺严格轮流，也不提供用户选择的硬实时期限。
   观察完整poll树与执行器版本。

7. **只比较ns/step，不测无关任务的恢复延迟。**
   吞吐改善可能以更长连续占用为代价。
   本章两个benchmark解决不同问题。

8. **认为增加worker等于修复阻塞poll。**
   只是暂时增加可被占满的线程数。
   阻塞工作仍需合适的执行域与边界。

9. **认为有界通道可以限制无限spawn。**
   等待发送的Future也持有内存。
   准入必须覆盖真正的在途工作集合。

10. **超时后释放阻塞工作的许可。**
    调用方退出时闭包可能继续运行。
    许可应由实际工作持有到完成。

11. **把abort当成已完成析构。**
    需要观察JoinHandle结果。
    已开始的spawn_blocking还不能依靠abort终止。

12. **把采样中的kevent或dyld全部解释成业务CPU开销。**
    前者可能是零时长检查，后者是启动污染。
    本轮不输出稳定态CPU百分比与PMU计数。

## 9.11 出口检查 {#sec-cpp-rust.3.9.11}

### 复现实验

从`cpp-rust/`执行：

```bash
cargo test --offline --locked --manifest-path bench/runtime-lab/Cargo.toml
cargo clippy --offline --locked --manifest-path bench/runtime-lab/Cargo.toml --all-targets -- -D warnings
bash tools/run_runtime_benchmarks.sh bench/results/my-runtime-run
```

选择不存在的新输出目录。
脚本拒绝覆盖已有environment.txt的归档目录。
在另一台机器上运行，不应期待复现相同纳秒数。
首先核对任务数、业务步数、预热、单位和编译设置。

### 读代码检查

应能在`state.rs`指定范围中找出：

- 在运行转换中清除当前通知的位置。
- running期间wake只登记责任的位置。
- 返回idle时发现新通知的位置。
- complete后不再重新提交的位置。
- 取消请求等待当前poll返回的注释。

若只能复述“用了CAS，所以线程安全”，尚未完成机制理解。
CAS的作用对象、状态前提和引用责任必须具体。

### 解释测量差异

应能回答：

1. 为什么multi4的聚合ns/step可以小于单线程调用一次step的延迟？
2. 为什么quantum增加不一定改善服务请求尾延迟？
3. 为什么current-q16的额外成本不能只归给原子加法？
4. 为什么第9.6节offload并没有缩短20ms睡眠？
5. 为什么21次观察不足以承诺生产p99？
6. 为什么闭包started信号比sleep猜测更适合取消测试？
7. 为什么通道关闭后仍要排空已经进入缓冲的消息？
8. 为什么permit要与实际工作同寿命？
