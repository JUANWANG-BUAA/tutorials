这不是一章要你背完的教材，而是一个**随用随查的抽屉柜**。每一格给三样东西：一句话结论、一个最小例子、本书哪里会用到它。读到某处卡住时，按章末「先修」提示回到这里取那一格就够了。

## 抽屉一 · 所有权、移动与借用（主线 ①：谁真的释放了这块内存）

**一句话结论。** Rust 的每个值在任一时刻只有一个所有者；`move` 是改名字而不是复制内存，`&` 是暂时借出读取权，借用检查会拦住「所有者已经不在，却还拿着指向它的引用」。

最小例子：

```rust
fn take(v: Vec<u64>) -> usize { v.len() }   // 接收所有权

fn main() {
    let a = vec![1u64; 8];
    let n = take(a);                          // a 被移动进来
    // println!("{}", a.len());               // 编译错误：a 已被移动
    let b = vec![1u64; 8];
    let m = take(b.clone());                  // clone 才是真的复制
    println!("{n} {m}");
}
```

| 概念 | 一句话 | 本书用在 |
|:--|:--|:--|
| 移动（move） | 转移所有权，原绑定进入 moved-out 状态 | [第 3 章](part1/ch03.md)、[第 16 章](part4/ch16.md) 的 FFI 交接 |
| 借用（`&T` / `&mut T`） | 只读取 / 只修改，不改变所有权 | [1.6](part1/ch01.md#sec-cpp-rust.1.1.6) 的 borrowed 与 cloned 对照 |
| 生命周期 | 引用的有效范围，编译器据此拒绝悬垂 | [第 3 章](part1/ch03.md)、[8 章](part2/ch08.md) 的自引用状态机 |
| `Copy` / `Clone` | 复制成本由类型决定：`u64` 复制 8 字节，`Vec` 复制整块缓冲区 | [2 章](part1/ch02.md) 的热字段讨论 |
| `Drop` | 离开作用域时的清理义务；自定义 `Drop` 会禁止部分移动 | [3 章](part1/ch03.md)、[10 章](part3/ch10.md) 的异常回收 |
| `unsafe` 边界 | 编译器把若干不变量交给你保证 | [3 章](part1/ch03.md)、[11 章](part3/ch11.md) |

**自查题。** 把 `fn f(v: &Vec<u64>)` 改成 `fn f(v: &[u64])`，函数的性能特征会变吗？调用点呢？
（要点：性能上不该变——两者都是读借用，指针与长度一样；变化在**类型层面**，`&[u64]` 不强求数据来自 `Vec`，因此接受切片、数组、`Vec` 都能编译。见 [3 章](part1/ch03.md) 与 [1.6 例 1.6.1](part1/ch01.md#ex-1.6.1) 的比较口径。）

## 抽屉二 · 操作系统与硬件在做什么（主线 ②：一次搬运到底搬多少）

**一句话结论。** 你的代码在三层东西上跑：CPU 的执行与缓存层次、操作系统的调度与内存管理、编译器的代码生成。性能问题常常不在这三层中的任何「你以为的那一层」。

| 概念 | 一句话 | 本书用在 |
|:--|:--|:--|
| 缓存层次 | 越靠近 CPU 越快也越小；一次访问命中哪一层决定成本量级 | [2.3](part1/ch02.md#sec-cpp-rust.1.2.3)、[12 章](part3/ch12.md) |
| 缓存行 | 主存与缓存之间一次搬运的最小单位（常见 64 字节；本机 `sysctl` 记录 128 字节） | [1.8](part1/ch01.md#sec-cpp-rust.1.1.8)、[2 章](part1/ch02.md) |
| 虚拟内存与缺页 | 地址是虚拟的，第一次触碰可能触发页面装入，成本远高于一次普通访存 | [1.2 预热](part1/ch01.md#def-1.2.3)、[10 章](part3/ch10.md) |
| 进程与线程 | 进程隔离地址空间，线程共享地址空间但各自有栈 | [10 章](part3/ch10.md)、[9 章](part3/ch09.md) |
| 抢占 | 操作系统可以在任意指令边界换下你的线程 | [1.4 时间漂移](part1/ch01.md#sec-cpp-rust.1.1.4)、[11 章](part3/ch11.md) |
| 系统调用 | 进出内核有固定开销，且可能是阻塞点 | [10 章](part3/ch10.md)、[12 章](part3/ch12.md) |
| 频率与热管理 | 持续负载下核心频率会回降，前后测出的同一代码可能不同 | [1.4](part1/ch01.md#sec-cpp-rust.1.1.4)、[1.8](part1/ch01.md#sec-cpp-rust.1.1.8) |

**关于数量级的诚实说法。** 教科书常给「L1 ≈ 4 周期、主存 ≈ 100 ns」这样的表。这本书不采用固定周期数：本机没有采集硬件计数器，跨机器的差异也远大于表格之间的差异。你只需要带走一个结论——**命中与不命中差一到两个数量级**，因此「这段代码访问了哪些字节」通常是第一个要问的问题。

**自查题。** 一个函数在同一进程里第二次跑比第一次快很多，至少给出两种原因，并说出用什么手段区分它们。
（要点：① 一次性装载——代码与数据首次触碰触发缺页、分支预测与缓存尚未建立；② 时间条件变化——频率回降、后台负载、页缓存状态。区分办法是预热后再测并保留逐批观测，看差异是否随「第几次」消失还是随「时间位置」变化。见 [1.2](part1/ch01.md#sec-cpp-rust.1.1.2) 与 [1.4](part1/ch01.md#sec-cpp-rust.1.1.4)。）

## 抽屉三 · 统计与抽样（主线 ③：差异是不是噪声）

**一句话结论。** 一个测量数字描述的是**总体**，你手上只有**样本**；所有报告出来的数都要带着「怎么算的、几个数、在什么条件下」。

| 概念 | 一句话 | 本书用在 |
|:--|:--|:--|
| 均值 | 加起来除以个数；对长尾分布不代表「典型值」 | [1.5](part1/ch01.md#sec-cpp-rust.1.1.5) |
| 样本标准差（N−1） | 描述批与批之间的波动；分母用 N−1 才不低估 | [定义 1.5.2](part1/ch01.md#def-1.5.2) |
| 分位数 p50/p99 | nearest-rank：排序后取第 `ceil(Np)` 个；样本少时高分位没有分辨率 | [定义 1.5.2](part1/ch01.md#def-1.5.2)、[1.8 尾分位数](part1/ch01.md#sec-cpp-rust.1.1.8) |
| 配对差值 | 同轮相减再平均，让共同条件抵消 | [定义 1.4.2](part1/ch01.md#def-1.4.2) |
| 置信区间 | 统计量可能的范围，不是「结论正确的概率」 | [定义 1.6.2](part1/ch01.md#def-1.6.2) |
| bootstrap 区间 | 对差值有放回重采样算出来的经验分布分位点 | [定义 1.6.2](part1/ch01.md#def-1.6.2) |
| 独立重复 | 不同时段重启进程各测一轮，覆盖环境差异 | [1.7](part1/ch01.md#sec-cpp-rust.1.1.7)、[1.8](part1/ch01.md#sec-cpp-rust.1.1.8) |
| 选择偏差 | 在同一批数据上试多种口径后挑最好看的报 | [定义 1.7.3](part1/ch01.md#def-1.7.3) |

最容易混的两件事：

1. **抽样波动 vs 环境差异。** 区间（[定义 1.6.2](part1/ch01.md#def-1.6.2)）覆盖前者，独立重跑才涉及后者。把一次运行的 21 批当成「21 台机器」是这本书反复纠正的错误。
2. **精度 vs 准确。** 多打几位小数只改精度；系统偏差（基线没执行、分母用错、顺序没交替）不会因为位数变多而消失。

**自查题。** 21 个批均值的 p99 恰好等于最大值。这是计算错误吗？它说明样本有什么问题？
（不是错误：`ceil(21 × 0.99) = 21`。它说明这份数据对 99% 分位**没有分辨率**——只有一个数在支撑它。要谈生产尾延迟，得采集请求级观测并匹配目标尾部概率的样本量。见 [1.5](part1/ch01.md#sec-cpp-rust.1.1.5) 与 [1.8](part1/ch01.md#sec-cpp-rust.1.1.8)。）

## 抽屉四 · 编译器、构建与命令行（主线 ④：结论要能被复核）

**一句话结论。** 你写的 Rust 和你测到的机器码之间隔着两级下降和一轮优化；不了解这一层，性能结论会归因到错误的对象上。

| 概念 | 一句话 | 本书用在 |
|:--|:--|:--|
| `cargo` 与 profile | `dev` 与 `release` 的优化级别不同，测出来的不是同一种代码 | [14 章](part4/ch14.md) |
| `opt-level` / `codegen-units` / `lto` | 分别控制优化强度、并行编译单元（会削弱跨单元优化）、链接时优化 | [4 章](part1/ch04.md)、[6 章](part2/ch06.md) |
| `target-cpu` | 允许使用本机指令集，改变指令选择；换目标机结果不一定复现 | [1.8 环境](part1/ch01.md#sec-cpp-rust.1.1.8) |
| MIR / THIR / LLVM IR / asm | Rust 层中间表示 → 下降到 LLVM 前 → LLVM 优化后 → 本机代码 | [4 章](part1/ch04.md)、[6 章](part2/ch06.md) |
| 符号与 demangle | profiler 栈里的 `_ZN...` 需要还原成可读名字 | [13 章](part4/ch13.md) |
| `strace`/`dtrace`/`sample`/`Instruments` | 观测手段各自的视野与代价；采样不是硬件事件计数 | [1.8](part1/ch01.md#sec-cpp-rust.1.1.8)、[13 章](part4/ch13.md) |
| `Cargo.lock` 与 `--offline --locked` | 固定依赖版本，保证「同一份代码」这一前提成立 | [14 章](part4/ch14.md) |

需要能读懂的程度：会写 `cargo build --release`、知道 `RUSTFLAGS` 环境变量会影响代码生成、能在汇编里认出「循环体是否还在」。**不要求**会写 LLVM pass 或读完整 MIR dump——第 4 章就是为了让不会读的人也能用起来。

**自查题。** `cargo bench`、`cargo build --release` 后跑二进制、`cargo run --release` 三种方式，哪种最可能测到与生产不同的代码？
（`cargo run --release` 与直接跑 release 二进制通常同一种代码，差别在进程启动成本；`cargo bench` 走基准测试框架，可能带额外夹具，也可能在 `benches/` 里用不同的 profile。真正要防的是「忘了 `--release`」——`dev` 构建下这本书的所有结论都不成立。见 [1.2 计时边界](part1/ch01.md#sec-cpp-rust.1.1.2) 与 [14 章](part4/ch14.md)。）

## 抽屉五 · 在自己机器上把程序跑起来（主线入口：先让工作真的发生）

**一句话结论。** 这本书的所有实验都只用 `cargo` 和标准库；会四条命令就能开始，不需要额外装测量工具。

```bash
# 1) 装 Rust（若还没装）：按官网提示装 rustup 后
rustc --version          # 确认编译器可用
cargo new first-try      # 新建一个项目
cd first-try
cargo run --release      # 运行；--release 打开优化，性能数字必须用它
cargo test               # 跑测试
```

| 命令 | 作用 | 本书哪里用 |
|:--|:--|:--|
| `cargo run --release` | 用优化后的构建运行 | 第 1 章起所有测量 |
| `cargo build --release` | 只编译，不运行 | 第 4 章看产物 |
| `cargo test` | 跑单元测试与集成测试 | 第 3、16、17 章的契约测试 |
| `cargo rustc -- --emit=mir` | 让编译器输出中间表示 | [第 4 章](part1/ch04.md) |

**几个新手最容易踩的坑**：① 忘了 `--release`，测到的是调试构建，慢几十倍且结论不成立；② 在 IDE 的「运行」按钮里跑，实际用的构建类型与你以为的不同——用终端命令确认；③ 把 `println!` 放进计时区间，测到的是终端 I/O 的速度；④ 只跑一次就下结论，见第 1 章「为什么单次计时不算测量」。

**自查题。** 同一段代码 `cargo run` 与 `cargo run --release` 差很多，哪个才是这本书讨论的对象？
（`--release`。调试构建保留了溢出检查、未优化内联与大量断言，它的耗时不能用来比较算法；但它仍适合验证正确性。见[第 1 章 1.2](part1/ch01.md#sec-cpp-rust.1.1.2) 与[第 14 章](part4/ch14.md)。）
