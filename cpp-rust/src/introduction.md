# 导论：Rust 程序在哪里跑，性能到底指什么

你写了一个 Rust 程序，用户说「有点慢」。这句话可能指五件完全不同的事：

- 一次请求等了 200 毫秒；
- 一秒只能处理 50 个请求；
- 99% 的请求在 50 毫秒内，但 1% 超过 2 秒；
- 内存一直涨，最后被系统杀掉；
- 编译一次要 10 分钟，改一行代码要等半天。

这五件事对应不同的指标，也需要不同的测量方法。如果你一上来就盯着「某个函数快了 0.02 纳秒」，很可能优化了一个和用户体验无关的角落。这一篇导论先把地图铺开：Rust 常用在哪些地方、性能有哪些指标、一个请求经过哪些层、代码怎么变成机器码，以及这本书打算怎么带你走。

这一章是背景，不是主线。全书的主线在[主干线与终极目标](mainline.md)：**先证明活真的干了 → 再证明这个数是什么 → 再证明差异不是噪声 → 最后证明结论守得住**。读完下面六个指标，就去看那一页，知道每个指标挂在主线的哪一步。


## Rust 常用在哪些地方

Rust 不是只用来「写得更安全」的语言。它已经被用在很多对性能和可靠性都敏感的地方：

| 场景 | 常见项目 | 最在意的指标 |
|:--|:--|:--|
| 命令行工具 | ripgrep、fd、bat | 启动时间、单次运行延迟、二进制大小 |
| 网络服务 | Axum、Actix Web、Hyper | 吞吐、p99 延迟、内存占用 |
| 数据库与存储 | TiKV、Databend、sled | 读写延迟、尾延迟、IO 放大 |
| 数据与流处理 | Polars、Arroyo | 吞吐、内存带宽、CPU 利用率 |
| 嵌入式与实时 | Embassy | 中断延迟、内存上限、确定性 |
| WebAssembly | wasm-bindgen、Yew、Leptos | 包体积、启动时间、浏览器内帧率 |
| 操作系统与虚拟化 | Redox、Firecracker | 系统调用开销、隔离、启动时间 |
| 区块链与密码学 | Solana、arkworks | 签名/验证吞吐、常数时间 |
| AI 基础设施 | Candle、tokenizers | 张量吞吐、内存占用、GPU/CPU 协同 |

同一个「快」，在 CLI 里可能指「启动只要 5 毫秒」，在数据库里可能指「p99 读延迟低于 10 毫秒」，在嵌入式里可能指「中断响应不超过 50 微秒」。**先确定你的场景，再谈指标**，否则数字没有意义。

## 性能的六个常用指标

### 延迟（latency）

延迟是一次操作从开始到结束的时间。用户说「点了按钮要等两秒」，说的就是延迟。

延迟可以按不同层次测量：一次函数调用、一次系统调用、一次网络往返、一次完整请求。层次不同，数字不能直接比较。一个函数 50 纳秒，不代表用户请求只多 50 纳秒；中间还有排队、序列化、网络和磁盘。

### 吞吐（throughput）

吞吐是单位时间完成多少次操作。比如「每秒处理 10,000 个请求」「每秒写入 200 MB」。

延迟和吞吐不是一回事。一个系统可以单次延迟很低，但吞吐上不去（比如每次只处理一个请求）；也可以吞吐很高，但个别请求延迟很长（比如批量合并）。

### 尾延迟（tail latency）

只看平均值会骗人。假设 100 个请求里 99 个用 10 毫秒，1 个用 2 秒，平均约 30 毫秒，看起来还能接受；但那个 2 秒的请求会让用户直接关掉页面。

所以生产系统通常看分位数：

- p50：一半请求不超过这个值；
- p95：95% 的请求不超过这个值；
- p99：99% 的请求不超过这个值；
- p999：99.9% 的请求不超过这个值。

分位数越高，越能暴露长尾问题；也越难测量，因为你需要足够多的样本，并且要保留请求级观测。

### 资源占用

资源包括内存、CPU、磁盘 IO、网络带宽、文件描述符和能耗。

一个优化可能让程序更快，但内存翻倍；也可能让单次请求更快，但 CPU 占用更高。这些取舍必须一起看，不能只报告「快了 2 倍」。

### 编译时间与二进制大小

Rust 的编译时间经常是开发体验的瓶颈。泛型单态化、链接时优化（LTO）、大量 `cargo` 依赖都会让编译变慢。二进制大小也会影响启动时间和部署成本。

这两个指标不直接决定运行时性能，但它们决定了你能不能快速迭代。

### 正确性与稳定性

这不是性能指标，但它是性能工作的前提。一个更快的实现如果会 panic、会数据竞争、会在高负载下死锁，那它没有资格参与比较。书里所有性能结论都默认正确性已经通过测试；正确性失败时，先修功能，再谈速度。

## 一个请求经过哪些层

假设你有一个 Rust 写的 HTTP 服务。一次请求大致经过：

```text
客户端
  │  网络、TLS、DNS
  ▼
反向代理 / 负载均衡
  │
  ▼
HTTP 解析 → 运行时调度器 → 业务 handler
                              │
                              ├─ 锁 / 队列 / 通道
                              ├─ 内存分配器
                              ├─ 系统调用（read/write/epoll/io_uring）
                              └─ 数据库 / 磁盘 / 下游服务
  │
  ▼
序列化 → 网络 → 客户端
```

任何一层都可能成为瓶颈：

- 网络往返可能是 1 毫秒，也可能是 100 毫秒；
- TLS 握手可能占掉大半时间；
- 运行时调度器可能让任务排队；
- 锁竞争可能让线程等待；
- 内存分配可能触发缺页或 GC（如果你用了带 GC 的库）；
- 系统调用可能被阻塞；
- 数据库可能慢查询；
- 序列化可能复制大量数据。

**你测哪一层，就只能回答哪一层的问题。** 在 handler 里测一个求和函数，不能解释用户为什么等了两秒；反过来，端到端压测也不能告诉你慢在哪个函数。性能工程的工作，就是在不同层次之间建立证据链。

## Rust 代码怎么变成机器码

你写的是 `.rs` 文件，机器执行的是指令。中间大致经过：

```text
Cargo.toml / Cargo.lock
        │  cargo 解析依赖、选择 feature
        ▼
     rustc 前端
        │  词法/语法分析 → HIR → THIR
        ▼
       MIR
        │  借用检查、初始化分析、Drop 展开
        ▼
   单态化 / 代码生成
        │  为每个具体类型生成一份代码
        ▼
     LLVM IR
        │  内联、别名分析、向量化、常量折叠
        ▼
   目标机器码
        │  链接器
        ▼
      可执行文件
```

这条流水线上的每一站都会影响性能：

- **MIR** 决定借用检查、初始化状态和析构路径；
- **单态化** 决定泛型代码复制多少份；
- **LLVM IR** 决定别名、内联、向量化和常量折叠；
- **目标机器码** 决定实际指令、寄存器分配和缓存行为；
- **链接与 LTO** 决定跨模块能看到多少信息；
- **目标 CPU 参数** 决定用哪些指令集。

同一段 Rust 源码，换一个 `opt-level`、换一个 `target-cpu`、换一个 `codegen-units`，生成的机器码可能完全不同。书里反复看 MIR、LLVM IR 和汇编，就是为了把「源码为什么快/慢」落到这些层上，而不是停在感觉。

## 性能工程的基本循环

性能工作不是「改一改，感觉快了」。它是一个循环：

1. **定义问题**：哪个场景、哪个指标、哪个输入规模？是延迟、吞吐、尾延迟，还是内存？
2. **建立基线**：用可复现的协议测当前版本；保存原始数据、环境、编译参数。
3. **提出假设**：慢在分配、锁、系统调用、缓存、分支、序列化，还是算法复杂度？
4. **只改一个变量**：一次改太多，无法归因。
5. **复测并比较**：用同一套协议、同一套统计方法；看区间，不只看均值。
6. **加回归门禁**：把「不能变慢」写成自动检查，防止下次改回去。

这本书的每一章，基本都按这个循环组织：先定义问题，再给实验，再看代码生成或测量数据，最后讨论边界和回归。

## 微基准和真实负载

**微基准**（microbenchmark）测一个很小的操作，比如「求和 65,536 个 `u64` 需要多少纳秒/元素」。它的优点是变量少、容易复现、能看清机制；缺点是离用户远，容易被编译器优化掉，也不能代表真实请求。

**宏基准**（macrobenchmark）测端到端行为，比如「1000 并发下 p99 请求延迟」。它更接近用户体验，但噪声大、变量多，出了问题也不容易定位。

正确的做法是两者配合：先用微基准理解机制，再用宏基准确认真实收益。只做微基准，容易优化一个没人用的函数；只做宏基准，容易不知道自己在改什么。

## 这本书怎么读

这本书不教 Rust 语法。变量、函数、`match`、模块、生命周期的基础，请先读[《Rust 程序设计语言》中文版](https://rustwiki.org/zh-CN/book/)。这本书假设你能读懂 Rust 代码，但不假设你已经懂性能工程。

如果你对性能还很陌生，按这个顺序读：

1. 这一篇导论，建立「延迟/吞吐/尾延迟/资源」的地图；
2. 第 1 章，学会让一个性能数字可信；
3. 第 2、3 章，理解对象布局和所有权在机器层面的含义；
4. 第 7、8、9 章，进入并发、异步和执行器；
5. 第 13、14 章，学会用 profiling 和门禁把结论守住。

如果你已经会 Rust、也做过性能优化，可以直接从[阅读指南](guide.md)的「按问题查」表进入。术语不熟时，查[术语表](appendix/glossary.md)；要快速回忆命令和检查项，查[速查卡](appendix/cheatsheet.md)。

## 这些指标最后要汇成一条线

上面那些词——延迟、吞吐、尾延迟、资源——不是四个各管一摊的知识点，它们最终服务同一条判断链：**先证明工作真的发生了，再证明这个数的口径是什么，再证明差异不是噪声，最后证明这个结论守得住、别人复核得了。**这四步是全书的主干，[主干线与终极目标](mainline.md)把它们和十七章一一对上；[第 1 章](part1/ch01.md)是它的母版，[第 17 章](part4/ch17.md)要求你在自己的项目上走完一次。

导论只负责把第一个词说清楚：一个请求从客户端走到磁盘，路上有多少层、每层用什么量来描述。它不给你方法——方法从下一章开始。

## 一个约定

书里会出现很多数字。每个数字都对应一个实验包、一份原始数据和一组编译参数。你不需要相信数字本身，但你应该能顺着书里的路径，在自己的机器上把它重新测出来。**读完这本书，你要能自己把数字测出来；结论只是副产品。**
