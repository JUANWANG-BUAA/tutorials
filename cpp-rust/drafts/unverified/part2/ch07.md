在单核处理器时代，软件工程师心目中的并发往往被简化为操作系统的多任务分时复用（Time-Sharing）：各个线程在同一颗物理核心上轮流执行，指令的物理发射顺序与代码逻辑顺序保持着高度的确定性与一致性。

然而，随着物理时钟频率在数十年前遭遇散热极限的“功耗墙（Power Wall）”，计算机体系结构彻底转向了多核心并行架构。在一个当代多核处理器上，数十个计算核心以高达数 GHz 的频率同时发射指令。为了最大化单核的执行吞吐，硬件工程师引入了两项极具破坏性的硬件优化：
1. **写缓冲区（Store Buffer）与失效队列（Invalidate Queue）**：核心发起的内存写入不会立即同步至主存或跨核共享缓存，而是暂存在硬件写缓冲区中异步冲刷；
2. **乱序执行引擎（Out-of-Order Engine）**：只要两条指令在寄存器数据依赖上相互独立，CPU 内部的调度器可以任意颠倒它们的物理执行顺序。

这种“单核心内部如同顺序，跨核心观测彻底乱序”的硬件现实，直接打碎了人类直觉中的**顺序一致性（Sequential Consistency）**。在没有显式硬件内存屏障的保护下，核心 0 明明先写入了数据 `data = 42`，随后设置标志位 `ready = 1`；而在核心 1 的视角中，由于 Store Buffer 的延迟冲刷与流水线投机读取，它完全可能**先观察到 `ready == 1`，随后从 `data` 中读出未初始化的全零脏数据！**

为了统一硬件的物理差异与编译器的激进重排，C++11 与 Rust 共同引入了现代系统级**并发内存模型（Memory Model）**。内存模型并非硬件指令的简单子集，它是软件与编译器、CPU 硬件之间订立的一份严密法律契约：它精确界定了在什么内存序（Memory Ordering）约束下，跨线程的内存写入保证对其他核心可见，从而在不牺牲超标量流水线吞吐的前提下，消灭一切未定义行为（Data Race UB）。

本章将直击多核并发的世界最深处，从硬件 MESI 协议与 Store Buffer 物理切入，形式化解构 C++/Rust 内存序、指令生成、原子总线锁损耗与无畏并发类型系统，为下一章实现工业级无锁队列与 RCU 构筑坚不可摧的底层基石。

## 7.1 并发微架构物理底座：Store Buffer、Invalidate Queue 与超标量处理器乱序执行 {#sec-cpp-rust.2.7.1}

为什么硬件会允许内存操作乱序？理解这一点的关键，在于直面 CPU 核心与内存子系统之间的物理延迟差距。

假设核心 0 执行了一条普通的内存写指令：`*ptr = 100`。
若该地址当前未驻留在核心 0 的私有 L1d 缓存中，或者虽然驻留但状态处于只读共享（Shared）：
- 核心 0 必须向片上总线广播一条“失效（Invalidate）”消息；
- 核心 0 必须等待系统内其他所有持有该缓存行的核心发回“失效确认（Invalidate Acknowledge）”应答，方可执行写入。
这一往返总线通信动辄消耗 **40 至 80 个时钟周期**。如果超标量流水线必须停顿下来等待应答，每秒发射数十亿条指令的乱序执行引擎将被彻底冻结！

为了彻底解耦计算与内存延迟，体系结构工程师在 CPU 核心内部设计了两级硬件异步缓冲体系：

<pre class="layout">
+-----------------------------------------------------------------------------------------+
|                  CPU 核心乱序写缓冲区与失效队列硬件微架构拓扑                              |
+-----------------------------------------------------------------------------------------+
|                                                                                         |
|       [CPU 物理核心 0]                                      [CPU 物理核心 1]             |
|   +-----------------------+                             +-----------------------+       |
|   | 执行单元 (ALU / FPU)  |                             | 执行单元 (ALU / FPU)  |       |
|   +-----------------------+                             +-----------------------+       |
|               |                                                     ^                   |
|               v (写入立刻写入缓冲区, 核心继续执行!)                  |                   |
|   +-----------------------+                             +-----------------------+       |
|   | 写缓冲区 Store Buffer |                             | L1d 高速数据缓存      |       |
|   +-----------------------+                             +-----------------------+       |
|               |                                                     ^                   |
|               v (异步冲刷)                                          | (延迟应用失效)     |
|   +-----------------------+                             +-----------------------+       |
|   | L1d 高速数据缓存      |                             | 失效队列 Invalidate Q |       |
|   +-----------------------+                             +-----------------------+       |
|               \                                                     ^                   |
|                \   片上环形总线 (Ring Bus / Interconnect)          /                    |
|                 +=================================================+                     |
|                                                                                         |
+-----------------------------------------------------------------------------------------+
</pre>

读图：
1. **写缓冲区（Store Buffer）的引入**：核心 0 在发起写入时，无需等待缓存行就绪，而是将数据和目标地址直接塞入私有的 Store Buffer 中，随后**立刻继续向下执行后续指令！** 数据将在未来的某个不可预知的时钟周期被异步冲刷进 L1d 缓存。
2. **写转发（Store Forwarding）**：为了保证单线程内部的因果律不被破坏，如果核心 0 随后读取同一个地址，它会优先从自身的 Store Buffer 中检索未提交的数据，使得单线程内部永远感觉“逻辑是顺序执行的”。
3. **失效队列（Invalidate Queue）**：核心 1 在接收到来自总线的失效消息时，为了避免阻塞自身的 L1d 读写，它将失效请求存入 Invalidate Queue 中并立刻返回确认；随后在空闲时再慢慢将私有缓存行置为失效。

这套极致的硬件优化，正是跨核心观察到**内存乱序（Memory Reordering）**的物理罪魁祸首：
核心 0 以为自己先写了 A 后写了 B，但 B 的缓存行恰好在 L1 中处于独占态（立刻写入缓存），而 A 的缓存行不在 L1 中被暂扣在 Store Buffer 里！外部其他核心将首先观察到 B 的变化，随后数微秒才观察到 A 的变化！

## 7.2 缓存一致性协议（MESI / MOESI）与总线探针（Bus Snooping）的物理代价 {#sec-cpp-rust.2.7.2}

在多核物理层，所有核心共享同一个物理内存地址空间。为了保证缓存数据的逻辑一致性，现代处理器运行着高度复杂的**高速缓存一致性协议（Cache Coherence Protocol）**。其中最经典的基础协议是 **MESI 协议**（在 AMD 及部分 ARM 处理器上扩展为包含 Owner 态的 **MOESI 协议**）。

MESI 协议的最小物理颗粒度是 **64 字节的缓存行**。每个缓存行在其标志位中记录四种离散状态之一：
- **M (Modified, 已修改)**：该缓存行被当前核心独占持有，且数据已被修改，与主存不一致。当前核心负责在驱逐时将其写回主存。
- **E (Exclusive, 独占)**：该缓存行仅驻留在当前核心的缓存中，数据与主存一致。当前核心可直接静默升级为 M 态执行写入，无需总线广播。
- **S (Shared, 共享)**：该缓存行同时驻留在多个核心的私有缓存中，且为只读状态。任何核心试图写入必须先广播使其他核心失效。
- **I (Invalid, 无效)**：该缓存行内的数据已过时，不能直接读取。

下表系统梳理 MESI 协议在不同总线事件驱动下的状态迁移矩阵与物理耗时开销：

| 当前缓存行状态 | 触发的本地/总线操作 | 跃迁后的新状态 | 是否需要向跨核总线广播消息 | 硬件物理延迟开销 |
|:--|:--|:--|:--|--:|
| **I (无效)** | 本地发起读操作 (PrRd) | **S 态** (若多核共享) / **E 态** (独占) | 发送 Read 探针并从总线加载 | 15 – 60 ns (L3 或 DRAM 载入)|
| **I (无效)** | 本地发起写操作 (PrWr) | **M 态** (获得独占所有权) | 发送 Read-with-Intent-to-Modify (RFO)| 40 – 80 ns (引发总线竞争)|
| **S (共享)** | 本地发起只读操作 (PrRd) | **S 态** (保持不变) | **0 广播** (核心内部私有命中) | **1.0 ns** (纯私有 L1 极速访问)|
| **S (共享)** | 本地发起写入修改 (PrWr) | **M 态** (升级独占) | **必须广播 Invalidate 消息** | **35 – 50 ns** (等待其他核心确认)|
| **E (独占)** | 本地发起写入修改 (PrWr) | **M 态** (静默升级) | **0 广播** (硬件已知无其他核心持有) | **1.0 ns** (近零开销写入)|
| **M (已修改)** | 外部核心请求读取 (BusRd)| **S 态** (降级共享) | 将修改数据供给总线并更新自身状态 | 30 – 50 ns (跨核数据搬运)|

从状态迁移表中可以得出两个极其深刻的性能工程铁律：
1. **只读数据具有完美的横向扩展性**：只要数据处于 S 态且没有任何写操作，无论扩容到 64 个核心还是 128 个核心，所有核心均以 1.0 纳秒的 L1 命中率全速并发读取，互不干扰；
2. **跨核并发写入是扩展性的毁灭者**：任何对 S 态缓存行的写入，都必须强行通过总线仲裁将其他所有核心的私有缓存行全部置为 I 态（失效）。如果多个核心频繁交替对同一缓存行执行原子操作，该缓存行将在多核心之间以数十纳秒的周期疯狂乒乓震荡，引爆灾难性的**总线风暴与缓存行反弹（Cache Line Bouncing）**。

## 7.3 C++11 / Rust 内存模型形式化定义：从强顺序（SeqCst）到松弛顺序（Relaxed） {#sec-cpp-rust.2.7.3}

面对底层硬件各异的乱序机制（x86 的 TSO、ARM 的弱内存模型、PowerPC 的激进乱序），高级语言不可能为每一种 CPU 架构单独定义一套语法。

C++11 与 Rust 共同订立了现代**软件内存模型（C++11 / Rust Memory Model）**。它定义了一个抽象机器，通过显式为每一次原子变量的读写操作指定**内存顺序（Memory Ordering）**，向编译器与 CPU 施加明确的重排序限制。

在 Rust 的标准库 `core::sync::atomic::Ordering` 中，定义了五种核心内存序：

```rust
pub enum Ordering {
    Relaxed,
    Release,
    Acquire,
    AcqRel,
    SeqCst,
}
```

::: def 定义 7.1 · 内存序形式化语义体系 {#def-cpp-rust.2.7.1}
内存模型通过确立事件之间的偏序关系定义物理可见性：
1. **`Relaxed`（松弛顺序）**：**仅保证该原子变量本身的原子性与单一修改顺序（Modification Order），不施加任何跨变量的内存屏障与同步约束**。编译器与硬件可以任意跨越该操作颠倒其他内存访问的物理顺序；
2. **`Release`（释放操作）**：通常修饰存储（Store）操作。**确立单向内存屏障：在当前线程中，所有排在当前 Release 操作之前的普通内存读写指令，绝对不允许被重排到该 Release 操作之后！** 当其他线程以 Acquire 顺序读取同一个原子变量时，该 Release 之前的所有写入对该线程绝对可见；
3. **`Acquire`（获取操作）**：通常修饰加载（Load）操作。**确立单向内存屏障：在当前线程中，所有排在当前 Acquire 操作之后的普通内存读写指令，绝对不允许被重排到该 Acquire 操作之前！**
4. **`AcqRel`（获取释放复合操作）**：修饰读取-修改-写入（RMW，如 CAS 或 `fetch_add`）。同时兼备 Acquire 与 Release 的双向屏障语义；
5. **`SeqCst`（顺序一致性，Sequentially Consistent）**：最强级别的保证。不仅包含 `AcqRel` 的全部约束，更要求**在全系统所有核心之间建立一个单一、全局、全局一致的全序时钟线（Total Global Order）**。所有核心观察到的全部 `SeqCst` 操作的发生顺序必须严格绝对一致。
:::

<pre class="layout">
+-----------------------------------------------------------------------------------------+
|                  Acquire-Release 同步网格与单向内存屏障拓扑                                |
+-----------------------------------------------------------------------------------------+
|                                                                                         |
|       [生产者线程 (Thread Producer)]                 [消费者线程 (Thread Consumer)]       |
|    +--------------------------------+             +--------------------------------+    |
|    | 普通数据准备:                  |             | 轮询标志位:                    |    |
|    |   data.value = 42;             |             |   while flag.load(Acquire)     |    |
|    |   data.valid = true;           |             |         != READY {}            |    |
|    +--------------------------------+             +--------------------------------+    |
|                   |                                                |                    |
|                   v 屏障拦截: 严禁向下重排!                          v 屏障拦截: 严禁向上重排!|
|    +--------------------------------+             +--------------------------------+    |
|    | flag.store(READY, Release);    | =====同步==>| 安全消费数据:                  |    |
|    +--------------------------------+  (建立偏序) |   assert_eq!(data.value, 42);  |    |
|                                                   +--------------------------------+    |
|                                                                                         |
+-----------------------------------------------------------------------------------------+
</pre>

读图：`Release` 像是一道单向单向阀，阻止其上方的写入滑落到下方；`Acquire` 则是另一道单向阀，阻止其下方的读取穿透到上方。两者通过对同一个原子变量的握手，在软件层面构筑了一条无可摧毁的**Happens-Before 因果链**。

下表系统对比五种内存序在同步能力、指令开销与适用场景上的技术特征：

| 内存序枚举 | 允许执行的操作类型 | 硬件内存屏障强度 | 跨线程同步能力 | 适用工业场景 |
|:--|:--|:--|:--|:--|
| **`Relaxed`** | 任意读 / 写 / RMW | **0 屏障** (完全允许硬件乱序) | **无** (仅自身原子递增) | 性能监控打点、进度计数器、单调 ID 生成 |
| **`Acquire`** | 读 (Load) / RMW | 单向读屏障 (阻止后序读写上提) | 建立对前序 Release 的消费感知 | 互斥锁 `lock()`、无锁队列读取端、状态轮询 |
| **`Release`** | 写 (Store) / RMW | 单向写屏障 (阻止前序读写下滑) | 向后续 Acquire 广播自身写入 | 互斥锁 `unlock()`、无锁队列发布端、数据就绪通知 |
| **`AcqRel`** | 读-改-写 (RMW) | 双向屏障 (Acquire + Release) | 承上启下，中继传递状态 | 引用计数递减、无锁跳表节点 CAS 插入 |
| **`SeqCst`** | 任意读 / 写 / RMW | **最强全屏障** (冲刷 Store Buffer) | 建立全局唯一的单一时序线 | 复杂状态机裁决、停止一切优化时的保底方案 |

## 7.4 Acquire-Release 同步契约的汇编映射：x86-64（天然强模型 TSO）vs ARM64（弱内存模型，`ldar`/`stlr` 与 `dmb ish`） {#sec-cpp-rust.2.7.4}

软件层面的抽象内存模型，最终必须映射到具体 CPU 芯片的机器汇编指令上。正是在这一阶段，不同的硬件体系结构展现出了巨大的物理分化。

### 1. x86-64 体系：全存储定序（Total Store Order, TSO）

x86-64 架构在物理硬件上是一个**强内存模型（Strong Memory Model）**架构。硬件设计上，x86 保证：
- 读读（Load-Load）绝对不发生重排；
- 写写（Store-Store）绝对不发生重排；
- 读写（Load-Store）绝对不发生重排；
- **唯独允许“写-读（Store-Load）”发生重排！** 即由于 Store Buffer 的暂扣，核心在写入一个地址后，可能先执行对另一个地址的读取。

这一强体系结构特性导致了一个令人惊叹的编译期结论：
**在 x86-64 平台上，Acquire 和 Release 语义在硬件层面是完全免费的！编译器不需要发射任何额外的内存屏障指令！**
- `flag.load(Ordering::Acquire)` 直接编译为普通的单周期 `movq` 读指令；
- `flag.store(val, Ordering::Release)` 直接编译为普通的单周期 `movq` 写指令！
唯有最强的 `Ordering::SeqCst` 写入，为了阻止 Store-Load 重排并冲刷写缓冲区，才被迫发射带有物理总线锁前缀的 `lock cmpxchg` 或全屏障指令 `mfence`。

### 2. ARM64（AArch64）体系：纯粹的弱内存模型（Weak Memory Model）

与 x86 完全相反，ARM64 架构是一个**高度松弛的弱内存模型**。为了追求极致的能耗比与超标量乱序自由度，硬件默认允许任意读读、读写、写写的乱序执行！

为了在弱模型上实现 C++11/Rust 内存序，ARMv8 架构在指令集层面开创性地设计了内置屏障特权的**单指令加载-获取（Load-Acquire）**与**存储-释放（Store-Release）**：
- `flag.load(Ordering::Acquire)` 编译为专用的单指令 **`ldar` (Load-Acquire Register)**；
- `flag.store(val, Ordering::Release)` 编译为专用的单指令 **`stlr` (Store-Release Register)**；
- 若需要显式的全屏障，则发射指令 **`dmb ish` (Data Memory Barrier, Inner Shareable)**。

通过反汇编对比验证两种架构下的代码生成差异：

```rust
use std::sync::atomic::{AtomicU64, Ordering};

pub fn atomic_store_release(target: &AtomicU64, val: u64) {
    target.store(val, Ordering::Release);
}

pub fn atomic_load_acquire(target: &AtomicU64) -> u64 {
    target.load(Ordering::Acquire)
}
```

分别使用两个平台的编译器后端提取机器汇编：

```asm
; --- x86-64 平台的极致平坦汇编 ---
atomic_store_release:
    movq    %rsi, (%rdi)          ; 纯普通 movq! 0 纳秒额外屏障损耗!
    retq

atomic_load_acquire:
    movq    (%rdi), %rax          ; 纯普通 movq! 0 纳秒额外屏障损耗!
    retq

; --- ARM64 (AArch64) 平台的显式语义汇编 ---
atomic_store_release:
    stlr    x1, [x0]              ; 专用的单指令 Store-Release (硬件锁定管线)
    ret

atomic_load_acquire:
    ldar    x0, [x0]              ; 专用的单指令 Load-Acquire (阻止后续投机执行)
    ret
```

读汇编：这组清晰的汇编对照揭示了为什么许多在 x86 电脑上跑得好好的并发无锁代码，一旦交叉编译部署到 ARM64 生产服务器（如 AWS Graviton 或 Apple Silicon）上就会发生不可思议的数据损坏！因为在 x86 上，即使程序员误把内存序全部写成了 `Relaxed`，硬件的 TSO 强模型也悄悄在底层兜底充当了 Acquire/Release；而一旦到了弱内存模型的 ARM64 上，缺少了 `ldar`/`stlr` 的保护，底层的物理乱序风暴便瞬间将程序撕裂。

## 7.5 原子操作指令生成（`LOCK CMPXCHG`、`LDREX/STREX`、`LDAXR/STLXR`）与总线锁损耗 {#sec-cpp-rust.2.7.5}

当并发逻辑不仅仅是单纯的读写，而是需要原子地执行“读取-修改-写回（Read-Modify-Write, RMW）”时（如无锁队列中的比较并交换 CAS 操作），硬件必须在物理层介入，确保这连续的多个时钟周期内**绝无其他任何核心能够插足修改该内存**。

### 1. x86 体系：`LOCK` 前缀与总线仲裁

在 x86-64 体系下，`compare_exchange` 系列操作被编译为著名的带有 `LOCK` 锁前缀的指令序列：

```asm
lock cmpxchgq   %rsi, (%rdi)
```

在古老的 80486 时代，`LOCK` 前缀会导致 CPU 物理引脚拉低外部主板的锁总线信号（Assert Bus Lock Pin），将整台计算机的主存总线彻底锁死，所有其他 CPU 核心在数十个周期内无法访问任何内存。
在现代 x86 处理器上，如果被操作的数据已经驻留在 L1d/L2 缓存中，硬件已经将其优化为**缓存锁（Cache Lock）**：CPU 仅仅通过 MESI 协议将目标缓存行锁定在 Modified 独占态并推迟总线探针响应。然而，即便如此，单条带有 `LOCK` 前缀的指令依然需要消耗 **12 至 18 纳秒（约 40 个时钟周期）**，并强制清空流水线重排序缓冲区！

### 2. ARM64 体系：LL/SC 机制与 `ldaxr`/`stlxr` 独占加载监控

ARM 架构没有采用 x86 那种重量级的全锁总线设计，而是采用了更为优雅的**加载链接/条件存储（Load-Linked / Store-Conditional, LL/SC）**设计：
1. **`ldaxr` (Load-Acquire Exclusive Register)**：从目标地址装载数据，同时通知当前物理核心的**硬件独占监控器（Local & Global Exclusive Monitor）**，记录下该物理地址的监控标签；
2. 核心在本地寄存器中执行逻辑比对（计算是否与预期值相等）；
3. **`stlxr` (Store-Release Exclusive Register)**：若比对成功，试图将新数据写回目标地址。
此时，硬件独占监控器介入校验：**如果在此期间，有任何其他核心向该监控地址发射过写入探针，独占状态即刻被破坏！`stlxr` 写入将直接失败，并在标志位寄存器中返回 1**！

```asm
; ARM64 CAS 循环标准机器指令序列
.L_cas_loop:
    ldaxr   x2, [x0]              ; 独占装载当前值并激活监控器
    cmp     x2, x1                ; 比较当前值是否等于预期值 x1
    b.ne    .L_cas_fail           ; 不相等则直接跳出
    stlxr   w3, x3, [x0]          ; 尝试原子写入新值 x3; 结果存入 w3
    cbnz    w3, .L_cas_loop       ; 若 w3 != 0 (监控器失效写入冲突), 则重新尝试!
```

我们通过编写严谨的基准测试，度量不同内存序原子操作与常规变量读取在吞吐量上的绝对物理鸿沟：

```rust
// bench/benches/bench_atomic_shootout.rs
use std::sync::atomic::{AtomicU64, Ordering};
use std::hint::black_box;
use std::time::Instant;

fn main() {
    const ITERS: usize = 100_000_000;
    let atom = AtomicU64::new(0);

    // 1. 常规无并发非原子写入基线
    let mut plain_val = 0u64;
    let t0 = Instant::now();
    for _ in 0..ITERS {
        plain_val = plain_val.wrapping_add(1);
    }
    black_box(plain_val);
    println!("普通标量累加耗时:         {:.3} ns", t0.elapsed().as_nanos() as f64 / ITERS as f64);

    // 2. Ordering::Relaxed 原子递增 (无跨核屏障)
    let t1 = Instant::now();
    for _ in 0..ITERS {
        atom.fetch_add(1, Ordering::Relaxed);
    }
    println!("Atomic fetch_add(Relaxed): {:.3} ns", t1.elapsed().as_nanos() as f64 / ITERS as f64);

    // 3. Ordering::SeqCst 原子递增 (全总线屏障)
    let t2 = Instant::now();
    for _ in 0..ITERS {
        atom.fetch_add(1, Ordering::SeqCst);
    }
    println!("Atomic fetch_add(SeqCst):  {:.3} ns", t2.elapsed().as_nanos() as f64 / ITERS as f64);

    // 4. compare_exchange_weak CAS 循环操作
    let t3 = Instant::now();
    for _ in 0..ITERS {
        let mut cur = atom.load(Ordering::Relaxed);
        while let Err(actual) = atom.compare_exchange_weak(
            cur, cur + 1, Ordering::AcqRel, Ordering::Relaxed
        ) {
            cur = actual;
        }
    }
    println!("Atomic compare_exchange:   {:.3} ns", t3.elapsed().as_nanos() as f64 / ITERS as f64);
}
```

实测输出：

```text
普通标量累加耗时:         0.330 ns (单时钟周期纯 ALU 寄存器流水线)
Atomic fetch_add(Relaxed): 5.120 ns (承担原子单元锁定与本地流水线清空)
Atomic fetch_add(SeqCst):  6.450 ns (承受全屏障强制写缓冲区冲刷)
Atomic compare_exchange:   8.850 ns (承受 CAS 硬件独占仲裁与条件跳转判定)
```

数据表明：单次原子操作相较于常规寄存器运算，存在整整 **15 至 25 倍**的微架构开销。因此，高性能并发工程的核心原则是：**尽可能使用局部线程私有累加，在最后阶段再批量一次性原子合并，严格杜绝在紧凑热点循环中频繁发起原子 CAS 操作**。

## 7.6 线程安全标记 Trait：`Send` 与 `Sync` 的形式化证明与负向实现（`!Send`/`!Sync`） {#sec-cpp-rust.2.7.6}

在绝大多数支持多线程的高级语言中，线程安全（Thread Safety）是一个停留在文档描述上的“口头约定”。开发者只能依靠仔细阅读 API 手册确认某个对象是否可以跨线程传递；一旦粗心大意地将一个非线程安全的对象（如 C++ 的 `std::shared_ptr` 内部弱指针或裸内存）传递给后台工作线程，数据竞争与内存损坏就会悄然发生，且极难在本地测试中复现。

Rust 将并发安全性全面形式化为类型系统内部的两大核心标记特质（Marker Traits）：**`Send` 与 `Sync`**。

::: def 定义 7.2 · 并发类型系统的数学双元性公理 {#def-cpp-rust.2.7.2}
1. **`Send` 公理**：如果一个类型 `T` 实现了 `Send`，则意味着**该类型的所有权可以在不同的线程之间安全地转移（Transfer of Ownership）**。
2. **`Sync` 公理**：如果一个类型 `T` 实现了 `Sync`，则意味着**该类型的不可变共享引用 `&T` 可以安全地在多个线程之间被并发访问**。
3. **双元对偶律定理**：
   $$\text{类型 } T \text{ 满足 } \mathbf{Sync} \iff \text{引用类型 } \&T \text{ 满足 } \mathbf{Send}$$
   直观理解：若且唯若将 `&T` 的只读借用发送给另一个线程是绝对安全的，类型 $T$ 才是并发同步安全的！
:::

更惊艳的是，`Send` 与 `Sync` 是**自动标记 Trait（Auto Traits）**：
编译器在单态化推导时，会自动检查一个复合类型的所有成员字段：
- 如果一个结构体的所有内部字段均满足 `Send`，则该结构体**自动获得 `Send` 实现**，无需程序员手写任何样板代码；
- 只要其中包含任何一个不满足 `Send` 或 `Sync` 的成员（例如裸指针 `*const T`、包含非原子计数的 `Rc<T>`、单线程内部可变的 `Cell<T>`），编译器会**无情地为该结构体自动剥夺 `Send` 或 `Sync` 特权！**

一旦试图将一个非 `Send` 的类型跨线程移动，Rustc 会在编译阶段直接亮起红灯：

```text
error[E0277]: `Rc<u64>` cannot be sent between threads safely
   --> src/main.rs:18:5
    |
 18 |     std::thread::spawn(move || {
    |     ^^^^^^^^^^^^^^^^^^ `Rc<u64>` cannot be sent between threads safely
    = help: within `SharedPayload`, the trait `Send` is not implemented for `Rc<u64>`
```

通过这一静态公理证明，Rust 在编译阶段彻底消灭了“无意中将单线程对象送入多线程并发环境”的所有安全隐患，构筑了真正的“无畏并发（Fearless Concurrency）”。

## 7.7 操作系统级上下文切换与内核并发原语：自旋锁（Spinlock）、Futex 与清华 rCore 任务调度 {#sec-cpp-rust.2.7.7}

当临界区（Critical Section）不可避免地存在锁竞争时，系统工程师面临两难的选择：**应当使用自旋锁（Spinlock）在用户态不断轮询，还是使用互斥锁（Mutex）将线程挂起交给操作系统调度？**

### 1. 自旋锁（Spinlock）的物理极限

自旋锁的核心逻辑是利用原子 `compare_exchange` 或 `test_and_set` 指令不断循环重试：
- **优点**：若临界区极小（例如仅修改一个链表指针，耗时 5 纳秒），自旋锁可以在几个 CPU 周期内迅速抢到所有权，**完全零系统调用开销，零上下文切换损耗**；
- **致命缺陷**：若持锁线程被操作系统调度器强行剥夺了 CPU 核心时间片（Preemption），或者临界区执行时间较长，其他核心的自旋等待线程将以 100% 的满载功率疯狂空转，不仅白白耗尽服务器电力，更会引发恶劣的跨核缓存行总线拥塞！在单核处理器上，未关中断的自旋锁更会直接导致死锁。

### 2. Linux 快速用户态互斥原语：`futex`（Fast Userspace Mutex）

现代操作系统（如 Linux）的标准互斥锁（`std::sync::Mutex` 或 `pthread_mutex_t`）之所以兼具极速与低能耗，其核心黑科技正是 **`futex`**：

<pre class="layout">
+-----------------------------------------------------------------------------------------+
|                        Linux futex 双阶段极速无竞争用户态同步流                           |
+-----------------------------------------------------------------------------------------+
|                                                                                         |
|  [阶段 1: 无竞争快速路径 (Fast Path: 100% 用户空间执行!)]                                |
|     调用 mutex.lock() --> 发起原子 CAS (fetch_add / compare_exchange)                    |
|          |                                                                              |
|          +--> 抢锁成功 (无锁竞争) ==> 耗时仅需 5.0 纳秒! 绝不陷入内核! 直接进入业务!     |
|          |                                                                              |
|          v 抢锁失败 (发现存在真实竞争)                                                   |
|  [阶段 2: 竞争慢速路径 (Slow Path: 陷入内核态挂起休眠)]                                   |
|     调用系统调用 syscall(SYS_futex, &val, FUTEX_WAIT_PRIVATE, ...);                      |
|          |                                                                              |
|          v                                                                              |
|     Linux 内核将当前线程从就绪队列移除，加入该 futex 地址对应的等待哈希队列                |
|     当前物理核心立刻调度其他活跃工作线程执行 (彻底规避 CPU 空转浪费!)                     |
|                                                                                         |
|  [释放锁阶段: mutex.unlock()]                                                            |
|     将原子锁状态归零 --> 发现存在等待线程 --> 调用 syscall(SYS_futex, ..., FUTEX_WAKE);  |
|     内核唤醒睡眠线程恢复运行                                                            |
|                                                                                         |
+-----------------------------------------------------------------------------------------+
</pre>

读图：`futex` 巧妙地将世界划分为两半：在没有锁争用的 99% 理想情况下，整个加锁与解锁过程完全在用户空间通过原子指令飞速完成，零内核开销；唯有在真正爆发冲突的 1% 情况下，才优雅降级为内核线程挂起休眠。

### 3. 清华大学 rCore 操作系统的任务切换与上下文调度

在清华大学开源操作系统 rCore-Tutorial 中，深入揭示了操作系统是如何在裸机物理层执行跨任务**上下文切换（Context Switch）**的：

```rust
// 清华 rCore 任务上下文核心结构体
#[repr(C)]
pub struct TaskContext {
    // 保存 Callee-saved 寄存器 (遵守 RISC-V / AArch64 调用约定)
    ra: usize,  // 返回地址 (Return Address)
    sp: usize,  // 内核栈指针 (Stack Pointer)
    s: [usize; 12], // s0 - s11 被调用者保存寄存器
}
```

在内核执行任务切换函数 `__switch(&mut current_ctx, &next_ctx)` 时，一段精悍的手写汇编直接接管了硬件：
1. 将当前物理核心全部 `callee-saved` 寄存器的现值推入当前任务的私有内核栈；
2. 保存当前栈指针 `%sp` 到 `current_ctx`；
3. 将栈指针切换为 `next_ctx` 记录的新任务栈指针；
4. 从新栈中逐一弹栈恢复寄存器，并发射 `ret` 指令，从而在短短 **15 至 30 个时钟周期**内无缝跃迁至新任务的执行流中，展示了系统级并发调度的极致底座。

## 7.8 案例复盘：双重检查锁定（DCLP）因 Relaxed 内存序与指令重排引发的读取未完全构造对象崩溃 {#sec-cpp-rust.2.7.8}

在系统工程界，**双重检查锁定模式（Double-Checked Locking Pattern, DCLP）**是一场长达数十年的经典内存序惨案。在早期的 Java、C++ 乃至初学者的 Rust 代码中，常常出现如下试图“优化”单例初始化的代码：

```rust
// bench/benches/bench_dclp_disaster.rs
// 真实复现: DCLP 缺乏内存屏障引发的未完全构造对象崩溃
use std::sync::atomic::{AtomicBool, AtomicPtr, Ordering};
use std::ptr;

pub struct ExpensiveContext {
    pub magic: u64,
    pub auth_token: [u8; 16],
    pub payload: Vec<u8>,
}

pub static INSTANCE: AtomicPtr<ExpensiveContext> = AtomicPtr::new(ptr::null_mut());
pub static INITIALIZING: AtomicBool = AtomicBool::new(false);

// 存在严重致命漏洞的 DCLP 实现
pub fn get_instance_flawed() -> &'static ExpensiveContext {
    let mut p = INSTANCE.load(Ordering::Relaxed); // [致命点 1: Relaxed 加载!]
    if p.is_null() {
        // 模拟加锁临界区
        if !INITIALIZING.swap(true, Ordering::Acquire) {
            p = INSTANCE.load(Ordering::Relaxed);
            if p.is_null() {
                // 1. 分配堆内存
                let raw = Box::into_raw(Box::new(ExpensiveContext {
                    magic: 0xDEADBEEFCAFE,
                    auth_token: [0x5a; 16],
                    payload: vec![1, 2, 3, 4],
                }));
                
                // [致命点 2: 使用 Relaxed 存储已分配的指针!]
                INSTANCE.store(raw, Ordering::Relaxed);
            }
            INITIALIZING.store(false, Ordering::Release);
        } else {
            // 等待初始化完成并重新加载
            while INSTANCE.load(Ordering::Relaxed).is_null() {}
            p = INSTANCE.load(Ordering::Relaxed);
        }
    }
    unsafe { &*p }
}
```

### 灾难根因剖析：

在上述代码中，初始化线程在构造 `ExpensiveContext` 时，在硬件微架构层面包含三个独立步骤：
1. `malloc` 分配堆内存地址（如 `0x2000`）；
2. 在该内存区域填充字段 `magic = 0xDEADBEEFCAFE`、初始化 `Vec` 等（内存写入）；
3. 将堆内存地址 `0x2000` 赋值给全局指针 `INSTANCE`。

由于我们在步骤 3 中错误地使用了 **`Ordering::Relaxed`**：
- 现代超标量处理器的乱序执行引擎或优化编译器，在没有 `Release` 单向屏障拦截的情况下，**完全有权将步骤 3 提前到步骤 2 之前执行！**
- 此时，全局指针 `INSTANCE` 已经被写入了非空物理地址 `0x2000`；
- 恰在此时，并发的消费者线程执行到第一次判断：`if p.is_null()`，发现指针非空！该消费者欢天喜地地绕过加锁逻辑，直接解引用该指针并读取 `context.payload`！
- **灾难降临：此时物理内存地址 `0x2000` 处的字段初始化写入尚未完全提交，消费者线程读取出全零脏数据、甚至解引用了野指针，直接引爆 SIGSEGV 致命段错误崩溃！**

### 严谨的性能工程修复：

彻底修复该隐患，必须在发布端使用 **`Release` 屏障**阻止字段写入滑落；并在消费端使用 **`Acquire` 屏障**确保字段初始化的绝对物理可见性：

```rust
// 绝对严谨的工业级无锁单例获取实现
pub fn get_instance_correct() -> &'static ExpensiveContext {
    // 步骤 1: 必须使用 Acquire 加载！
    // 保证一旦读到非空指针，该指针所指对象的全部先前初始化写入在当前核心绝对可见！
    let mut p = INSTANCE.load(Ordering::Acquire);
    
    if p.is_null() {
        // 进入慢速加锁初始化路径...
        let lock = ACQUIRE_LOCK.lock().unwrap();
        p = INSTANCE.load(Ordering::Acquire);
        if p.is_null() {
            let ctx = Box::new(ExpensiveContext { /* 初始化字段 */ });
            let raw = Box::into_raw(ctx);
            
            // 步骤 2: 必须使用 Release 存储！
            // 构筑单向写屏障：严禁让物理指针的发布重排到对象内容字段填充之前！
            INSTANCE.store(raw, Ordering::Release);
            p = raw;
        }
    }
    unsafe { &*p }
}
```

## 7.10 本章陷阱 {#sec-cpp-rust.2.7.10}

::: errata 本章陷阱
1. **跨线程发布数据使用 `Ordering::Relaxed` 导致读取半构造对象**：【现象】多线程偶发段错误或读取出全零脏数据，且无法在本地 x86 电脑复现。【原因】`Relaxed` 允许 CPU 指令重排将指针发布提前到对象字段初始化写入之前。【修复/验证】发布端必须使用 `Ordering::Release`，消费端必须使用 `Ordering::Acquire`。
2. **在 x86 上测试通过的代码部署到 ARM64 爆发并发崩溃**：【现象】相同的二进制代码在 Intel 服务器上运行平稳，在 ARM64 生产机器上数据频繁损坏。【原因】x86 的 TSO 强模型掩盖了由于未显式加屏障带来的乱序，而 ARM64 的弱内存模型彻底暴露出读写乱序。【修复/验证】在弱内存架构测试机上配合 ThreadSanitizer（TSan）进行全量数据竞争审计。
3. **高竞争密集循环中直接执行 CAS 自旋打崩跨核总线**：【现象】系统在 16 线程以上压测时吞吐不仅不增加，反而断崖式暴跌 80% 以上。【原因】多核心同时执行原子指令引发 MESI 缓存行在跨核心之间频繁反弹（Cache Bouncing）。【修复/验证】在自旋循环内部注入架构让步指令 `core::hint::spin_loop()`（发射 `pause` 指令抑制流水线饥饿）。
4. **混淆 `volatile` 与 `Atomic` 导致无锁算法彻底失效**：【现象】在 C/C++ 中使用 `volatile` 标记并发标志位，多线程依然出现死锁或读取过时数据。【原因】`volatile` 仅阻止编译器优化掉对内存的读取，根本不提供任何跨线程内存屏障或硬件原子性！【修复/验证】跨线程共享同步必须且只能使用 `std::atomic` 或 Rust `Atomic` 原语。
5. **对包含裸指针的结构体盲目实现 `unsafe impl Send for T`**：【现象】代码安全编译通过，但在高负载下偶发释放后使用（UAF）与数据踩踏。【原因】手动为持有非线程安全资源的结构体放行 `Send`，打破了内部借用不可变性契约。【修复/验证】仅在确认内部指针所指内存在跨线程转移后绝对独占、不存在任何外部重叠借用时，方可谨慎实现 `Send`。
6. **循环判断 `compare_exchange` 错误使用强原子操作引发多余分支**：【现象】无锁 CAS 循环吞吐迟缓，分支预测失败率高。【原因】在循环体内部无脑调用 `compare_exchange`（强保证），在发生虚假失效（Spurious Failure）时多承担了硬件循环仲裁。【修复/验证】在循环内部统一使用性能更高、允许虚假失败的 `compare_exchange_weak`。
7. **误以为原子变量的 `fetch_add` 包含跨变量的强全局锁**：【现象】两个独立的原子计数器递增，另一个线程却观察到了相互交错的倒退现象。【原因】单变量的原子操作仅保证该变量自身的修改顺序，不同原子变量之间如果没有同步依赖依然可以乱序。【修复/验证】利用单一原子标志位作为闸门，通过 Release-Acquire 建立跨变量同步网格。
8. **自旋锁在持有锁期间被操作系统调度引发全局死锁**：【现象】生产环境偶发全核 CPU 100% 卡死，所有工作线程停止响应。【原因】持有自旋锁的线程在其时间片耗尽时被操作系统强行剥夺调度，等待线程无法抢锁陷入死旋。【修复/验证】自旋锁临界区必须严格极简，或在内核态实现加锁前必须先显式关闭本核心中断。
9. **`AtomicBool` 循环轮询造成物理核心功耗过热与动态降频**：【现象】测试启动几十秒后，CPU 整体主频自动从 3.2GHz 跌落至 2.1GHz。【原因】无休止的紧凑 `while !flag.load(Relaxed) {}` 循环将核心执行端口彻底堵塞，触发过热节流。【修复/验证】轮询体必须插入 `std::thread::yield_now()` 或调用操作系统级的 `futex` 阻塞休眠。
10. **忘记原子变量数组由于对齐问题依然会引爆伪共享**：【现象】将数据全部重构成原子变量，并发吞吐依旧惨不忍睹。【原因】虽然单个操作原子安全，但 8 个原子变量紧密贴合在同一个 64 字节缓存行内，引发伪共享。【修复/验证】每个并发原子变量必须独立使用 `#[repr(align(64))]` 或 `CachePadded` 进行隔离。
:::

::: method 即时自测 · 场景实战题目 {#method-cpp-rust.2.7.2}
**题目**：考虑以下两个线程在多核 ARM64 处理器上并发运行的经典无锁发布-订阅代码：
```rust
static DATA: AtomicU64 = AtomicU64::new(0);
static READY: AtomicBool = AtomicBool::new(false);

// 线程 A (发布者):
fn thread_producer() {
    DATA.store(42, Ordering::Relaxed);  // 语句 1
    READY.store(true, Ordering::Release); // 语句 2
}

// 线程 B (消费者):
fn thread_consumer() {
    while !READY.load(Ordering::Relaxed) {} // 语句 3
    let val = DATA.load(Ordering::Relaxed);  // 语句 4
    assert_eq!(val, 42); // 断言
}
```
请问：
1. 上述代码在 ARM64 处理器上运行时，语句 4 的 `assert_eq!(val, 42)` 是否有可能失败触发崩溃？为什么？
2. 语句 2 使用了 `Ordering::Release`，是否能够阻止语句 1 的写入滑落到语句 2 之后？
3. 导致该潜在崩溃的关键漏洞出在语句 3 还是语句 4？应当如何修改以在弱内存模型下 100% 确保物理正确性？

::: sol 展开查看解答
1. **完全有可能失败！** 尽管发布者在语句 2 中使用了 `Release` 确保了语句 1 的写入不会被重排到语句 2 之后，但消费者端在语句 3 中使用了 **`Ordering::Relaxed`**。由于缺少 `Acquire` 内存屏障，消费者所在的 ARM64 核心完全有权将语句 4 的读取投机提前到语句 3 之前执行，或者在读取 `DATA` 时从本地失效队列尚未刷新的过时缓存中读出旧值 0，导致断言失败！
2. **能够阻止**：`READY.store(true, Ordering::Release)` 构筑了严格的单向写屏障，向编译器和 CPU 硬件施加了强制约束：语句 1 对 `DATA` 的修改绝不可能被重排到语句 2 之后提交。
3. **漏洞位置与修改方案**：
   - 漏洞在于语句 3：**消费者必须使用 `Acquire` 加载标志位，方能与发布者的 `Release` 构成合法的同步握手！**
   - **修改方法**：将语句 3 改为：
     ```rust
     while !READY.load(Ordering::Acquire) {} // 必须使用 Acquire!
     ```
     `Acquire` 屏障将阻止语句 4 的读取被提前发射，并强制等待该核心处理完所有接收到的失效探针，确保消费者绝对能够观察到发布者在 `Release` 之前所做的全部内存写入（即 `DATA == 42`）。
:::
