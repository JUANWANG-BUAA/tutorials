在工业自动化、轨道交通、汽车电子与医疗仪器中，软件运行的物理世界充满不可预测的残酷扰动：
外部继电器切断产生的高压电磁脉冲（EFT/Surge）可能击穿晶体管状态，引发程序计数器（PC）飞入未映射内存；
时钟晶振引脚受到轻微机械振动，可能突发数个微秒的时钟失锁（Clock Loss）；
传感器短路或总线死锁，可能导致关键控制任务陷入无限等待。

在消费级设备中，软件崩溃的表现往往是弹窗或重启；
而在控制冲压机床、汽车电子刹车（Brake-by-Wire）或无人机旋翼的硬实时边缘嵌入式系统中，**任何一次失去控制的停顿或失控飞车，都可能在数毫秒内演变为机毁人亡的灾难性物理事故**。

本章系统建立工业级嵌入式系统的**功能安全与故障容错防御纵深**。
从 ISO 26262 / IEC 61508 核心时间模型切入，剖析独立看门狗与窗口看门狗的微架构差异；
彻底推翻“在 SysTick 中断中简单喂狗”的伪安全做法，构建多任务窗口心跳监管状态机；
深入 ARM Cortex-M 的 CFSR/HFSR/BFAR 故障寄存器与异常栈帧解码，掌握无需 JTAG 仿真器即可由固件自救式提取崩溃现场的工程方法；
并延伸至 RISC-V 的 `mcause`/`mtval` 与 x86 的 `#PF`/`#GP`/`#DF` 纯净双重错误栈。

实验分为两个严格隔离的层级。
第一层为主机 C11 仿真模型，在 ASan/UBSan 监控下量化验证多任务代际 Token 窗口监管、提前喂狗违约拦截、非易失 RAM 崩溃快照校验与 FTTI 时间预算。
第二层为 QEMU Cortex-M3 与 RV32IM 裸机固件，实际执行硬件看门狗密钥解锁与计数、故意触发未定义指令以运行 HardFault 解码器（精准提取被打断的 PC 与状态寄存器），并由变异测试拦截异常逻辑。
本轮实验没有连接物理高压脉冲发生器或外部硬件故障注入测试台，所有时间预算与寄存器状态均明确标示为数学模型或目标仿真。

## 10.1 功能安全度量与故障时间模型：从 SIL/ASIL 到 FTTI 预算 {#sec-edge.3.10.1}

### 功能安全的核心哲学：从“不犯错”到“有错必控”

在汽车功能安全标准 **ISO 26262**（涵盖 ASIL-A 至最高等级 ASIL-D）以及工业控制通用标准 **IEC 61508**（涵盖 SIL-1 至 SIL-4）中，嵌入式系统工程师面临的首要认知转变是：
**任何复杂的软硬件系统都不可能做到 100% 物理无故障**。
半导体宇宙射线诱发的单粒子翻转（SEU, Single Event Upset）、PCB 焊点老化热疲劳、代码在极端边界条件下的潜伏并发缺陷，迟早会在系统生命周期内的某个时刻爆发。

因此，功能安全的核心目标并非寄希望于系统永远不发生故障，而是建立严密的**故障防御包线**：
确保系统在硬件元器件损坏或软件异常时，能够以极高的确定性及时检出故障，并在物理灾害发生之前，安全将设备引导至预先定义的**安全状态（Safe State）**。

### 故障容错时间间隔（FTTI）与时间预算分解

在功能安全时间模型中，最关键的核心物理指标是**故障容错时间间隔（Fault Tolerant Time Interval, FTTI）**。
FTTI 是物理受控对象（如电机、液压阀、转向齿条）自身所固有的物理属性，由机械动力学与热力学决定，完全独立于控制器主频：
例如，在汽车电子节气门（Electronic Throttle Control）控制中，若电机控制失去闭环导致阀门意外全开，发动机将在 $50\,\text{ms}$ 内发生严重动力突发激增。
因此，该执行机构的 FTTI 上限严格为 **$50\,\text{ms}$**！

系统从发生微观单点故障到彻底进入安全状态，必须经历四个紧密衔接的物理时间阶段：

<pre class="layout" id="fig-edge-3-10-safety-flow">
物理故障发生时刻 (t_fault)
    │
    ├─ 1. 故障表现阶段 (Fault Reaction Phase)
    │     硬件产生单粒子翻转或死锁，控制量开始漂移
    ▼
监测机制捕获时刻 (t_detect) ──────► 经历故障检出时间 T_detect
    │                                (如窗口看门狗超时、差分采样校验失败)
    ├─ 2. 故障诊断与仲裁阶段
    │     CPU 判定故障等级，记录崩溃快照
    ▼
执行应急动作时刻 (t_react) ───────► 经历响应确认时间 T_react
    │                                (如封锁 PWM 逆变桥、切断继电器供电)
    ├─ 3. 执行机构物理跃迁阶段
    │     电机反电动势泄放、电感电流消逝、弹簧物理复位
    ▼
系统安全状态达成 (t_safe) ────────► 达成安全状态 (Safe State)

全生命周期安全不等式：T_detect + T_react + T_transition &le; FTTI
</pre>

读图：故障发生后，经过 $T_{detect}$ 被硬件看门狗或内部自检机制捕获；
随后通过异常服务例程在 $T_{react}$ 内执行紧急阻断动作（如硬件封锁 PWM 驱动信号）；
执行机构在 $T_{transition}$ 内完成物理能量泄放，最终系统在 $t_{safe}$ 达成安全状态。

::: def 故障容错时间预算不等式（FTTI Budget Theorem） {#def-edge.3.10.1.1}
对于任意给定的安全关键功能，其软硬件处理流水线必须在数学上严格满足：
$$T_{total\_reaction} = T_{detect} + T_{react} + T_{transition} \le \text{FTTI} - M_{margin}$$
其中：
- $T_{detect}$ 为看门狗窗口上限或自检周期；
- $T_{react}$ 为中断响应时间、现场转储与控制器决策时间；
- $T_{transition}$ 为执行器从失控状态切换至安全停机状态的物理机械/电气时间；
- $M_{margin} \ge 0$ 为工程安全裕量（通常保留 20% ~ 30%）。
:::

若看门狗的超时周期被随意设置为 $100\,\text{ms}$，而受控执行器的 FTTI 仅有 $50\,\text{ms}$，即使看门狗最终成功复位了单片机，在复位发生前系统早已经跨过了安全红线，引发不可逆的物理设备损毁！


### IEC 61508 / ISO 26262 硬件度量指标体系

在功能安全工程中，系统的安全完整性等级（SIL 1~4 / ASIL A~D）并非主观评估，而是由严格的概率论与统计学硬件度量指标所支撑：
- **安全失效分数（Safe Failure Fraction, SFF）**：
  在系统所有可能的元器件失效模式中，属于“安全失效”（即失效后系统自动偏向安全状态）以及“虽然危险但能被诊断机制实时检测出”的比例：
  $$\text{SFF} = \frac{\sum \lambda_S + \sum \lambda_{DD}}{\sum \lambda_S + \sum \lambda_D}$$
  其中 $\lambda_S$ 为安全失效失效率，$\lambda_D$ 为危险失效失效率，$\lambda_{DD}$ 为可被诊断机制检测出的危险失效（Dangerous Detected）。
  为了达到最高等级的 SIL 3 或 ASIL D，系统的 SFF 通常必须严格 $\ge 99\%$！
- **诊断覆盖率（Diagnostic Coverage, DC）**：
  诊断机制检出的危险失效占全部危险失效的百分比：
  $$\text{DC} = \frac{\sum \lambda_{DD}}{\sum \lambda_D} \times 100\%$$
- **每小时危险失效概率（PFH, Probability of Dangerous Failure per Hour）**：
  在连续运行模式下，系统每小时发生不可控危险失效的数学期望：
  - SIL 2 / ASIL B：$10^{-7} \le \text{PFH} \lt 10^{-6}$ / 小时；
  - SIL 3 / ASIL D：$10^{-8} \le \text{PFH} \lt 10^{-7}$ / 小时（相当于每连续运行 1000 年以上允许出现不可检出的单次危险失效）。

这些冰冷而严密的数字，直接倒逼系统程序员必须在固件每一层部署主动防御：
从寄存器内存镜像自检（RAM Pattern March-C Test）、只读存储区定期 CRC 巡检，到每一个核心线程的窗口看门狗心跳监管。

## 10.2 硬件看门狗微架构：独立看门狗 vs 窗口看门狗与反失控机制 {#sec-edge.3.10.2}

### 传统独立看门狗（IWDG）的重大安全盲区

最基础的硬件看门狗被称为**独立看门狗（Independent Watchdog, IWDG）**：
- 结构：包含一个由芯片内部低频专用阻容振荡器（如 32 kHz LSI/IOSC）独立供电驱动的 12 位或 32 位递减计数器；
- 工作流：软件定期向特定的喂狗寄存器（Key Register）写入固定密钥（如 `0xAAAA`），硬件自动将计数器重装载为预设的最大初值；若软件由于卡死或死锁在计数器减至 0 之前未喂狗，硬件直接拉低芯片的内部复位引脚，触发全系统冷重启。

**独立看门狗的致命缺陷：无法防御“提前过快喂狗”与“失控死循环”！**
设想以下工业实际事故场景：
某工程师编写的任务由于指针越界触发了逻辑死循环，任务被困在一段死循环体内；
然而，该死循环内部恰好包含一行调用底层驱动的 `iwdg_feed()` 语句！
或者，某段失控的代码由于 PC 指针跑飞，意外跳转至某个高频运行的无害中断服务程序中，中断内部无脑执行着喂狗指令。
**后果是灾难性的**：
虽然核心业务逻辑已经彻底停止运转，逆变器由于缺失控制输出即将过流烧毁，但独立看门狗依然在被源源不断地按时刷新，**看门狗被彻底欺骗，硬件永远不会产生复位！**

### 窗口看门狗（WWDG）的双向时序防御机制

为了彻底终结上述失控死循环骗狗的漏洞，汽车与高端工控微控制器标配了**窗口看门狗（Window Watchdog, WWDG）**。

窗口看门狗在时间轴上划定了严密的**合法喂狗有效窗口区间 $[T_{early}, T_{late}]$**：

```text
+----------------------------------------------------------------------------------------------------+
|                         窗口看门狗 (Window Watchdog) 双向合法时间窗口                               |
+----------------------------------------------------------------------------------------------------+
| 上次喂狗时刻 (0 us)                                                                                |
|    |                                                                                               |
|    |==== 非法禁止区域 [0, T_early) ====>|======== 合法喂狗时间窗口 [T_early, T_late] =======>| 严重超时   |
|    |                                    |                                             |           |
|    |--- 若在此区域提前喂狗:             |--- 唯一允许喂狗的合法时间区间:              |--- 计数减至0|
|    |    硬件判定代码失控死循环!         |    刷新计数器，系统正常运行                 |    系统复位|
|    |    立即无条件产生硬件复位!         |                                             |           |
+----+------------------------------------+---------------------------------------------+-----------> 时间
     0                                  T_early                                       T_late
```

窗口看门狗构筑了双向刚性约束：
1. **防止太慢（Too Late）**：若任务陷入无限阻塞、死锁或被低优先级饥饿，时间越过 $T_{late}$（计数器下溢），硬件产生复位；
2. **防止太快（Too Early）**：若任务由于跑飞在异常死循环中疯狂刷新看门狗，只要喂狗时刻早于 $T_{early}$（当前计数值大于窗口寄存器 `WIN_VAL`），**硬件判定程序处于不可信失控状态，立即在喂狗指令执行的瞬间，瞬间主动触发芯片物理复位！**

### 硬件寄存器密钥加锁防篡改机制

以 TI Stellaris LM3S6965 的硬件看门狗控制器（基址 `0x4000_0000`）为例，该外设在物理层设计了精密的**防跑飞篡改安全锁（Lock Register）**：

在芯片受到强烈高压静电或电磁干扰（EMI）时，CPU 内部的通用寄存器或指令译码器可能发生随机突变，导致非预期的指令向任意外设地址盲写数据。
为了杜绝失控的野指针意外关闭或改写看门狗配置，LM3S 看门狗在物理上强制引入了 **`WDTLOCK` (Offset `0xC00`) 密钥寄存器**：
- 寄存器在复位后**处于物理锁定状态**，对 `WDTLOAD`（重载值）、`WDTCTL`（控制位）等所有寄存器的写操作直接被硬件总线忽略！
- 软件若需要修改看门狗初值或使能复位功能，必须向 `WDTLOCK` 显式写入特定的 32 位魔法安全密钥：
  `0x1ACCE551`（ASCII 记忆语义为 "I ACCESS"）！
- 一旦写入正确的解锁密钥，寄存器写保护解除，软件方可写入配置；
- 配置完成后，软件必须立即向 `WDTLOCK` 写入非密钥数值（通常写 0），**重新强制锁上看门狗大门**！

在 `firmware/ch10/arm/main.c` 中，我们给出了标准的安全加解锁配置序列：

```c
/* 安全解锁并装载硬件看门狗 */
#define WDT_BASE       0x40000000UL
#define WDT_LOAD       (*(volatile uint32_t *)(WDT_BASE + 0x000))
#define WDT_CTL        (*(volatile uint32_t *)(WDT_BASE + 0x008))
#define WDT_ICR        (*(volatile uint32_t *)(WDT_BASE + 0x00C))
#define WDT_LOCK       (*(volatile uint32_t *)(WDT_BASE + 0xC00))
#define WDT_UNLOCK_KEY 0x1ACCE551UL

void safe_wdt_configure(uint32_t load_value) {
    /* 1. 显式写入安全密钥解锁总线写权限 */
    WDT_LOCK = WDT_UNLOCK_KEY;

    /* 2. 装填 32 位超时计数值 */
    WDT_LOAD = load_value;

    /* 3. 使能中断生成与二次超时复位使能 */
    WDT_CTL = 0x03; /* Bit 0: INTIEN, Bit 1: RESEN */

    /* 4. 立即重新上锁，防御后续野指针篡改 */
    WDT_LOCK = 0x00;
}
```

在本章配套的变异测试 `run_mutations.sh` 中，我们注入了“故意将解锁密钥改错为 `0x12345678`”的破坏性变异。
在 QEMU Cortex-M3 上运行时，硬件由于未收到合法密钥，内部寄存器配置完全不生效，固件自检立即捕获异常并以退出码 1 终止，严密证明了硬件密钥保护的不可逾越性。


### 窗口看门狗下溢与早期预警中断（EWI）机制

以广泛应用于工业与汽车微控制器的标准**窗口看门狗（WWDG）硬件定时器**为例：
WWDG 内部通常包含一个 7 位的自由递减计数器 `CNT[6:0]`，其工作在专用 APB 分频时钟下：
- 计数器的最高有效位（Bit 6）为**运行标志位**。当计数器从 `0x7F` 持续递减到 `0x40` 期间，Bit 6 始终为 1；
- 一旦计数器减至 `0x3F`，Bit 6 瞬时变为 0，硬件状态机判定发生下溢（Underflow），**立即拉低内部复位引脚触发全系统复位**！
- 软件配置的窗口寄存器 `WIN[6:0]` 设定了允许喂狗的时间上限（数值上界）：
  只有当当前计数值 $CNT \le WIN$ 且 $CNT \ge 0x40$ 时，软件向控制寄存器写入新计数值才被判定为合法刷新；
  若软件在 $CNT \gt WIN$ 时提前喂狗，硬件立即触发复位！

```text
+----------------------------------------------------------------------------------------------------+
|                         WWDG 7 位递减计数器时序与早期预警中断 (EWI)                                |
+----------------------------------------------------------------------------------------------------+
| 0x7F (最大初值)                                                                                    |
|   |                                                                                                |
|   |=== 非法禁止喂狗区 (若在此区间喂狗: 立即复位!) ===>|                                            |
|   |                                                |                                               |
|   |                                                v WIN[6:0] (配置窗口阈值)                       |
|   |                                                |                                               |
|   |================ 合法刷新窗口区 ===============>|                                               |
|   |  (允许软件写入新初值 0x7F 重装载)              |                                               |
|   |                                                v 0x40 (早期预警中断触发点 EWI)                  |
|   |                                                |                                               |
|   |                                                |---> 触发 EWI 中断! 抓取崩溃现场, 保存快照!     |
|   |                                                v 0x3F (Bit 6 变为 0: 硬件复位系统!)             |
+---+------------------------------------------------+----------------------------------------------->
```

*救命的早期预警中断（Early Warning Interrupt, EWI）*：
在高级 WWDG 微架构中，提供了一个极其精妙的硬件中断：当计数器精确递减至 `0x40` 的瞬间，如果软件依然没有喂狗，硬件不会立即产生复位，而是首先拉起 **EWI 中断**！
从 `0x40` 递减到 `0x3F`，为系统留下了整整一个计数周期（通常为数十微秒至数毫秒）。
在这转瞬即逝的最后窗口内，EWI 中断服务程序可以：
1. 紧急封锁电机逆变器的所有高端与低端 PWM 开关管，进入安全的电气浮空状态；
2. 将当前崩溃任务的 ID 与异常状态原子写入非易失 RAM；
3. 随后任由计数器减至 `0x3F` 触发物理硬件复位重启。

## 10.3 多任务心跳监管与代际 Token 机制：杜绝在 ISR 中盲目喂狗 {#sec-edge.3.10.3}

### 为什么在中断中喂狗是致命伪安全

在实际嵌入式工程项目中，**最普遍、最具危害性的错误设计，就是将看门狗喂狗操作直接挂载在 SysTick 或定时器中断中**：

```c
/* 致命伪安全反模式：在硬件滴答中断中盲目喂狗 */
void SysTick_Handler(void) {
    wdt_feed_hardware(); /* 极其危险！千万不要这么做！ */
    os_tick_step();
}
```

*为什么这是致命的系统漏洞？*
因为在绝大多数微控制器中，**中断系统的运行机制完全脱离于操作系统任务调度器**！
假设系统中负责采集电机的关键控制任务陷入了死锁、优先级反转或无限死循环，整个 RTOS 的业务线程已经彻底瘫痪；
但是，硬件 SysTick 定时器依然在独立计数，依然在每隔 1 毫秒无休无止地触发 `SysTick_Handler`！
结果，看门狗在中断里被按时、机械、忠实地持续喂饱，**看门狗形同虚设，整个控制系统陷入植物人状态，物理事故瞬间发生！**

::: def 真实健康状态代际监管契约 {#def-edge.3.10.3.1}
硬件看门狗的物理喂狗权限，必须严格收拢并下放至**多任务健康监管中心（Multitask Watchdog Supervisor）**。
全系统中每一个关键业务任务，必须在自身的完整业务闭环末端，向监管中心汇报自身独有的心跳代际 Token。
监管中心在每个调度周期对全系统的任务矩阵进行严格的健康状态机裁决：
**只有当全系统中所有受控任务均在各自允许的合法时间窗口内完成了检查点汇报，监管中心才被授权向底层硬件看门狗执行一次物理喂狗！**
任一任务发生迟到、早到或死锁，看门狗必须被故意饿死，以触发系统的确定性自愈复位。
:::

### 多任务窗口监管状态机实现

在 `experiments/ch10/fault_recovery.c` 中，我们实现了支持多任务、具备早晚窗口拦截与代际递增防重放机制的集中式看门狗监管中心：

```c
typedef struct {
    uint32_t task_id;
    uint32_t min_interval_us;  /* 窗口下限：早于此时刻喂狗视为死循环失控 */
    uint32_t max_interval_us;  /* 窗口上限：晚于此时刻喂狗视为卡死饥饿 */
    uint32_t last_kick_us;
    uint32_t token;            /* 严格单调递增的健康代际凭证 */
    bool     active;
} WatchdogTaskEntry;

typedef struct {
    WatchdogTaskEntry tasks[MAX_WATCHDOG_TASKS];
    uint32_t num_tasks;
    uint32_t supervisor_now_us;
    uint32_t hardware_wdt_feed_count;
    FaultReason last_fault;
    uint32_t faulting_task_id;
} WatchdogSupervisor;
```

任务在自身执行完毕后，调用 `wdt_task_checkin` 汇报心跳。
算法首先拦截过快喂狗与 Token 重放：

```c
bool wdt_task_checkin(WatchdogSupervisor *ws, uint32_t task_id, uint32_t token, uint32_t now_us) {
    WatchdogTaskEntry *entry = find_task_entry(ws, task_id);
    if (!entry) return false;

    if (entry->token > 0) {
        uint32_t elapsed = now_us - entry->last_kick_us;
        
        /* 1. 早期违约拦截：任务执行太快，可能处于错误短路或失控空转 */
        if (elapsed < entry->min_interval_us) {
            ws->last_fault = FAULT_WDT_EARLY_KICK;
            ws->faulting_task_id = task_id;
            return false;
        }

        /* 2. Token 单调递增校验：杜绝使用静态陈旧凭证重复欺骗 */
        if (token <= entry->token) {
            ws->last_fault = FAULT_CORRUPT_STATE;
            ws->faulting_task_id = task_id;
            return false;
        }
    }

    entry->last_kick_us = now_us;
    entry->token = token;
    return true;
}
```

监管中心作为低优先级的独立看门狗服务任务，或者由专用定时器定期唤醒调用 `wdt_supervisor_poll`：

```c
bool wdt_supervisor_poll(WatchdogSupervisor *ws, uint32_t now_us) {
    /* 逐一扫描全系统所有受监控任务的截止期 */
    for (unsigned i = 0; i < ws->num_tasks; ++i) {
        if (!ws->tasks[i].active) continue;
        uint32_t elapsed = now_us - ws->tasks[i].last_kick_us;
        
        /* 任务超时卡死：未能按时签到！ */
        if (ws->tasks[i].token > 0 && elapsed > ws->tasks[i].max_interval_us) {
            ws->last_fault = FAULT_WDT_TIMEOUT;
            ws->faulting_task_id = ws->tasks[i].task_id;
            
            /* 绝不喂狗！立即退出，允许底层硬件看门狗计数归零触发复位！ */
            return false;
        }
    }

    /* 全系统 100% 任务健康，方可执行物理喂狗动作 */
    ws->hardware_wdt_feed_count++;
    hw_feed_physical_watchdog();
    return true;
}
```

在主机测试（`test_host.c`）中，我们仿真了 500 ms 连续多任务运行（包含 10 ms 控制任务与 50 ms 采样任务），验证了 100 次持续喂狗无一误报；
同时在自检中分别注入了“提前 2 ms 异常喂狗”与“延后 10 ms 饥饿卡死”，监管中心分别以 100% 的确定性精确捕获到了责任任务 ID 与违约类别，彻底消除了盲目喂狗的安全隐患。

## 10.4 ARM Cortex-M 异常捕获实战：HardFault 堆栈帧解码与 CFSR/HFSR 诊断 {#sec-edge.3.10.4}

当防御失败、硬件故障依然不可避免地爆发时，最高优先级任务是**捕获崩溃现场的完整微架构快照**，定位到底由哪一行机器指令引发了致命异常。

在 ARM Cortex-M（M3/M4/M7）体系中，所有严重的未处理总线错误、内存非法访问与非法指令，最终全部汇聚并升级为**硬件致命硬故障（HardFault，异常向量号 3）**。

### 硬件自动压栈帧的微架构双轨结构

正如第三章与第四章所建立的体系结构基础，当发生异常陷入时，CPU 硬件在第 0 周期开始自动将当前寄存器压入**当前活动的堆栈**中：
- 若崩溃发生在主内核或裸机无 OS 环境中，使用的是**主堆栈指针（MSP）**；
- 若崩溃发生在 RTOS 的多任务执行体中，使用的是任务独立的**进程堆栈指针（PSP）**。

因此，进入 `HardFault_Handler` 的第一件事，必须是通过检查连接寄存器 `LR`（此时为 `EXC_RETURN` 伪标记）的 **Bit 2**，判断发生崩溃时系统正在使用哪个堆栈指针！

```armasm
/* 严密的 HardFault 纯汇编分发入口 */
.global hardfault_asm_entry
.type hardfault_asm_entry, %function
.thumb_func
hardfault_asm_entry:
    /* 测试 EXC_RETURN 的 Bit 2 (0b0100)
     * Bit 2 == 0: 异常前使用 MSP (主栈)
     * Bit 2 == 1: 异常前使用 PSP (任务进程栈) */
    tst     lr, #4
    ite     eq
    mrseq   r0, msp             /* 将 MSP 指针存入 R0，作为 C 函数的第一个入参 */
    mrsne   r0, psp             /* 将 PSP 指针存入 R0，作为 C 函数的第一个入参 */
    mov     r1, lr              /* 将 EXC_RETURN 存入 R1，作为第二个入参 */
    b       hardfault_c_decoder /* 跳转至 C 语言高级解码器 */
```

### 堆栈帧内存排布与寄存器解码

传递给 C 函数的指针 `stacked_sp` 精准指向崩溃瞬间在 RAM 中建立的 8 字节（32 字节）基础异常栈帧：

| 栈帧相对偏移 | 物理对应寄存器 | 故障诊断核心价值与分析方法 |
|:--|:--|:--|
| `stacked_sp[0]` | **R0** | 发生故障指令时入参 1 或当前运算结果 |
| `stacked_sp[1]` | **R1** | 发生故障指令时入参 2 |
| `stacked_sp[2]` | **R2** | 发生故障指令时入参 3 |
| `stacked_sp[3]` | **R3** | 发生故障指令时入参 4 |
| `stacked_sp[4]` | **R12** | 内部调用临时寄存器（IP） |
| `stacked_sp[5]` | **LR (Link Register)** | **崩溃函数的调用者返回地址**：指示哪个上级函数调用了崩溃代码 |
| `stacked_sp[6]` | **PC (Program Counter)** | **触发物理故障的精确机器指令物理地址**！将其放入反汇编即可直达代码行！ |
| `stacked_sp[7]` | **xPSR** | 故障发生时的状态标志位（包含 Thumb 标志与条件码） |

### 故障根因全开：CFSR 与 HFSR 状态寄存器组

光知道崩溃发生在哪个 PC 地址还不够，我们必须知道为什么崩溃。
ARM 核心在系统控制块中提供了**可配置故障状态寄存器（`SCB->CFSR`，基地址 `0xE000_ED28`）**，将其细分为三个独立子域：

```text
+----------------------------------------------------------------------------------------------------+
|                         ARM Cortex-M SCB->CFSR 可配置故障状态寄存器位域                             |
+----------------------------------------------------------------------------------------------------+
| [31:16] UFSR (UsageFault)      | [15:8] BFSR (BusFault)          | [7:0] MMFSR (MemManage)         |
| - DIVBYZERO   (Bit 25: 除以0)  | - BFARVALID   (Bit 15: 地址有效)| - MMARVALID  (Bit 7: 地址有效)  |
| - UNALIGNED   (Bit 24: 非对齐) | - STKERR      (Bit 12: 压栈错误)| - MSTKERR    (Bit 4: 压栈错误)  |
| - NOCP        (Bit 19: 无FPU)  | - IMPRECISERR (Bit 10: 异步错误)| - DACCVIOL   (Bit 1: 数据越权)  |
| - UNDEFINSTR  (Bit 16: 未定义) | - PRECISERR   (Bit 9:  精确总线)| - IACCVIOL   (Bit 0: 取指越权)  |
+----------------------------------------------------------------------------------------------------+
```

在 `firmware/ch10/arm/main.c` 中，我们实现了自动提取并落盘的 C 解码器：

```c
void hardfault_c_decoder(uint32_t *stacked_sp, uint32_t exc_return) {
    uint32_t fault_pc  = stacked_sp[6];
    uint32_t fault_lr  = stacked_sp[5];
    uint32_t cfsr      = SCB->CFSR;
    uint32_t hfsr      = SCB->HFSR;
    uint32_t fault_addr = 0;

    /* 检查是否为精确总线错误，并从 BFAR 提取故障物理地址 */
    if (cfsr & (1UL << 15)) { /* BFARVALID */
        fault_addr = SCB->BFAR;
    } else if (cfsr & (1UL << 7)) { /* MMARVALID */
        fault_addr = SCB->MMFAR;
    }

    /* 序列化转储至持久化安全快照区 */
    crash_dump_save(&g_captured_crash, FAULT_HARD_FAULT, fault_pc, fault_lr,
                    fault_addr, cfsr, get_system_timestamp_us());

    /* 针对受控测试：将堆栈中的 PC 向前跳过 2 字节（未定义指令长度），实现安全返回自愈 */
    stacked_sp[6] += 2;
}
```

在目标机测试中，我们通过内联汇编故意执行未定义指令 `__asm__ volatile(".short 0xde00");`。
Cortex-M3 硬件瞬时触发 HardFault，`hardfault_asm_entry` 准确将 MSP 现场交由 C 解码器，成功解码出崩溃 PC，并通过校验和保存至安全结构体中，完美达成现场抓取。


### 异步不精确总线错误（Imprecise BusFault）的调试陷阱与 DSB 锁相

在 Cortex-M4/M7 的故障排查中，最令工程师头疼的是 `SCB->CFSR` 中的 **`BFSR.IMPRECISERR` (Bit 10)**。
当发生不精确总线错误时，栈帧中保存的 PC 地址往往是指向一行完全风马牛不相及的正常指令（甚至是一个空操作 `nop`），而导致真正崩溃的内存写入指令早在几十个周期前就已经执行完毕了！

*微架构根因*：
现代高性能 Cortex-M 内核（如 Cortex-M4、M7）为了提高执行效率，在 CPU 核心与外部总线之间集成了硬件**写缓冲区（Write Buffer）**：
1. 当 CPU 执行一条外设写指令（如 `STR R0, [R1]`，向一个非法外设地址写数据）时，核心将数据推入写缓冲区后，便立即认为该指令已经完成，流水线毫不等待直接继续向下执行后续指令；
2. 数十个时钟周期后，写缓冲区在后台向总线矩阵发起实际物理总线写事务；
3. 此时外部总线返回了 `ERROR` 响应！总线控制器向 NVIC 报告 BusFault；
4. 然而，此时 CPU 的程序计数器（PC）早已经前进了多条指令！硬件在压栈时，只能将当前流水线正在执行的位置保存为断点，导致堆栈中的 PC 彻底失真。

为了在调试高难度死机缺陷时将不精确错误彻底还原为精确错误，系统工程师可利用辅助控制寄存器：

```c
/* 强制关闭 Cortex-M 写缓冲，将所有总线错误强制转化为精确错误 (Precise) */
void force_precise_bus_faults(void) {
    /* SCB->ACTLR 基地址: 0xE000_E008
     * 置位 DISDEFWBUF (Bit 1): 禁用写缓冲 */
    *(volatile uint32_t *)0xE000E008UL |= (1UL << 1);
    __asm__ volatile("dsb
 isb" ::: "memory");
}
```

关闭写缓冲后，CPU 每次执行 `STR` 均必须强制等待总线确认返回。
虽然这会使系统整体运行性能下降约 10%~20%，但任何非法的内存写操作都会在发生瞬间精确触发 `BFSR.PRECISERR`，并将引发错误的非法目标物理地址分毫不差地锁存在 **`SCB->BFAR`** 寄存器中，使隐藏极深的总线野指针瞬间原形毕露！

## 10.5 RISC-V 异常现场解码：mcause、mepc 与 mtval 的故障诊断 {#sec-edge.3.10.5}

与 ARM 复杂的嵌套硬件故障状态机相比，RISC-V 遵循极其优雅正交的三寄存器故障诊断哲学：
**任何同步异常与外部中断，其现场完全收拢在 `mcause`、`mepc` 与 `mtval` 三大控制状态寄存器中**。

### RISC-V 故障诊断三剑客

| CSR 地址 | 寄存器符号名称 | 访问权限 | 故障诊断物理语义与用途说明 |
|:--|:--|:--|:--|
| `0x342` | **`mcause`** | 读/写 | **机器模式异常原因寄存器**：<br>`Bit 31`：`0` 代表同步硬件异常，`1` 代表异步外部中断；<br>`Bits 30:0`：异常原因编号（如 2=非法指令，3=断点，5=加载访问错误，7=存储访问错误） |
| `0x341` | **`mepc`** | 读/写 | **发生异常的机器指令程序计数器**：硬件发生异常时，硬件自动将**触发该异常的指令物理地址**压入此寄存器！ |
| `0x343` | **`mtval`** (旧称 mbadaddr) | 读/写 | **机器模式故障值附加寄存器**：<br>- 若为地址访问越权/未对齐（Cause 4/5/6/7）：硬件自动在此存入**引起访问失败的非法物理目标内存地址**！<br>- 若为非法指令（Cause 2）：存入该未定义指令的原始机器码！ |

### RISC-V 裸机异常分发与崩溃转储实现

在 `firmware/ch10/rv32/main.c` 中，我们构建了可在 QEMU RISC-V `virt` 平台上实际执行的异常现场捕获系统：

```c
/* RISC-V 统一高级异常分发器 */
void default_trap_handler(void) {
    uint32_t mcause, mepc, mtval;
    __asm__ volatile("csrr %0, mcause" : "=r"(mcause));
    __asm__ volatile("csrr %0, mepc"   : "=r"(mepc));
    __asm__ volatile("csrr %0, mtval"  : "=r"(mtval));

    /* 检查是否为断点异常 (Cause 3) 或非法指令异常 (Cause 2) */
    if (mcause == 3 || mcause == 2) {
        /* 提取现场并生成高可信崩溃转储 */
        crash_dump_save(&g_captured_crash, FAULT_ILLEGAL_INSTRUCTION, 
                        mepc, 0, mtval, mcause, 9999);
        g_fault_handled = true;

        /* 将返回地址 mepc 向前步进 4 字节，跳过故障指令，避免无限陷入 */
        mepc += 4;
        __asm__ volatile("csrw mepc, %0" : : "r"(mepc) : "memory");
    } else {
        /* 其他无法自愈的致命故障：触发系统停机 */
        finish(1);
    }
}
```

在测试执行中，程序执行 `ebreak` 触发同步异常，分发器在 `mcause` 中准确读出数字 3，从 `mepc` 中提取出断点指令地址，写入持久化结构体并返回。
测试断言直接校验 `g_captured_crash.status_reg == 3`，证明了这一轻量级现场捕获在工业 RISC-V 芯片上的极高实用价值。


### RISC-V 同步异常全码表与 PMP 越权诊断

在 RISC-V 架构下，同步硬件异常的类型完全由 `mcause` 的低有效位进行精细化编码。
下表汇总标准 RISC-V 特权级规范定义的同步异常原因与 `mtval` 的对应语义：

| 异常原因码 (mcause) | 官方异常助记符 | 产生物理机理 | mtval 寄存器锁存内容 | 典型固件诊断对策 |
|--:|:--|:--|:--|:--|
| **0** | `Instruction address misaligned` | 取指地址未按指令长度对齐 (未使能 C 扩展跳转奇数地址) | 导致取指失败的目标 PC 地址 | 检查函数指针是否被损坏为奇数 |
| **1** | `Instruction access fault` | 取指物理地址落在未映射区域或被 PMP 规则拒绝 (X=0) | 导致越权的物理内存地址 | 检查 PMP 代码段执行权限配置 |
| **2** | `Illegal instruction` | 遇到未定义机器码，或在当前特权级执行未授权指令 | 触发异常的 32 位原始指令机器码 | 检查工具链指令集编译选项 |
| **3** | `Breakpoint` | 执行 `ebreak` 调试断点指令 | 当前断点指令本身的 PC 地址 | 软件断点处理或调试转储 |
| **4** | `Load address misaligned` | 读内存地址未满足数据宽度对齐 (在不支持非对齐的核心上) | 发生非对齐读的目标内存地址 | 检查结构体指针强转或启用软件模拟 |
| **5** | `Load access fault` | 读内存地址落在非法总线区域或 PMP 读禁止 (R=0) | 发生越权读操作的非法物理地址 | **精准捕获野指针读越界** |
| **6** | `Store/AMO address misaligned` | 写内存或原子操作地址未对齐 | 发生非对齐写的目标内存地址 | 检查 DMA 描述符或原子变量对齐 |
| **7** | `Store/AMO access fault` | 写内存地址落在只读 Flash 或 PMP 写禁止 (W=0) | 发生越权写操作的非法物理地址 | **精准捕获内存踩踏与只读区修改** |
| **11**| `Environment call from M-mode`| 机器模式执行 `ecall` 系统调用 | 0 或保留 | 机器模式系统服务调用分发 |

通过构建对 `mcause` 的集中解码表，RISC-V 固件能够以极低的代码体积（不到 50 条汇编指令），在毫秒级内完成对野指针非法访问（Cause 5/7）、非法指令（Cause 2）与内存越权（Cause 1）的高可信诊断与现场捕获。

## 10.6 x86 致命异常与保护机制：#GP、#PF 与双重错误 #DF 的 IST 纯净栈 {#sec-edge.3.10.6}

在 x86-64 工业边缘主机与车载域控制器（如基于 Intel Atom、Core 嵌入式系列）中，CPU 拥有极其强大的硬件分级保护与故障追踪机制。

### 核心硬件异常与错误码解码

x86-64 通过中断描述符表（IDT）前 32 个保留向量处理处理器异常：

| 异常向量号 | 助记符与名称 | 错误码压栈 | 核心产生机理与诊断手段 |
|--:|:--|:--|:--|
| **Vector 6** | **`#UD` (Invalid Opcode)** | 无错误码 | 遇到未定义指令机器码、或在未开启 SSE 时执行向量指令 |
| **Vector 13**| **`#GP` (General Protection)**| **包含 16 位错误码** | 特权指令越权执行、段描述符非法、向 MSR 写入不支持的值 |
| **Vector 14**| **`#PF` (Page Fault)** | **包含 32 位错误码** | **页表缺页或越权访问**：核心控制寄存器 `%cr2` 自动锁存引起故障的虚拟线性地址！ |
| **Vector 8** | **`#DF` (Double Fault)** | 错误码恒为 0 | 发生一次异常期间，在调用处理例程时**再次突发二次异常**（如内核栈溢出越界） |

在 `firmware/ch10/x86_fault.S` 中，我们给出了读取 `%cr2` 的汇编底层原语：

```nasm
/* experiments/ch10/x86_fault.S */
.text
.global decode_page_fault_x86
.type decode_page_fault_x86,@function
/* uint64_t decode_page_fault_x86(void);
 * 返回导致页故障的虚拟线性内存地址 (由硬件自动写入 CR2 寄存器) */
decode_page_fault_x86:
    movq    %cr2, %rax
    ret
.size decode_page_fault_x86, .-decode_page_fault_x86
.section .note.GNU-stack,"",@progbits
```

### 双重错误（#DF）与任务状态段中断栈表（IST）防御机制

在所有 x86 故障中，最具毁灭性的是**双重错误（Double Fault, `#DF`）**：
最典型的场景是**栈溢出（Stack Overflow）**：
1. 某递归函数耗尽了内核栈空间，指针越过栈底防护页（Guard Page）；
2. CPU 发起下一次压栈时，MMU 检测到非法访存，硬件试图触发 Page Fault（`#PF`，Vector 14）；
3. 然而，CPU 在调用 `#PF` 处理函数前，微架构必须首先将当前 `%ss`、`%rsp`、`%rflags`、`%cs`、`%rip` 压入当前内核栈；
4. 此时内核栈本身已经不可写！硬件在尝试压栈时**再次触发了一次缺页故障**！
5. 两个严重故障发生叠加，硬件瞬间陷入两难绝境！

若没有专门的微架构防御，系统将在下一周期触发**三重故障（Triple Fault）**，硬件逻辑强行向主板拉下 RESET# 信号，导致整机瞬间冷重启变黑屏，没有任何日志能够留下！

**x86-64 的救命稻草：中断栈表（Interrupt Stack Table, IST）**：
在 64 位长模式下，任务状态段（TSS）内部提供了 7 个独立的指针：`IST1` 到 `IST7`。
在配置 IDT 中断描述符时，操作系统将 `#DF` 描述符的 IST 字段绑定到 `IST1`。
当双重错误发生时，**CPU 硬件彻底无视当前已经粉身碎骨的 `%rsp` 栈指针，强行从 TSS 中装载 `IST1` 指向的一片绝对干净、独立的物理内存栈！**
这使得系统能够在一个完好无损的运行环境下执行 `#DF` 处理函数，将崩溃现场打印到串口或持久化保存，实现优雅自愈降级。


### x86-64 IDT 中断描述符表与 IST 栈切换微架构细节

在 64 位长模式下，x86 中断描述符表（IDT）的每个条目扩展为 **16 字节（128 位）**，以容纳 64 位的目标处理函数线性基地址：

```text
+----------------------------------------------------------------------------------------------------+
|                         x86-64 16 字节中断门描述符 (Interrupt Gate Descriptor)                      |
+----------------------------------------------------------------------------------------------------+
| 127 ... 96: 目标 ISR 线性基地址高 32 位 [63:32]                                                   |
| 95  ... 64: 保留必须填 0                                                                          |
| 63        : P (Present 存在标志, 1 = 有效)                                                         |
| 62 ... 48 : DPL (描述符特权级 0..3) | 0 | Type (0xE = 64位中断门, 0xF = 陷门) | 保留填 0           |
| 47 ... 32 : IST 索引 (Bits 2:0, 0 = 使用当前 RSP, 1..7 = 绑定 TSS.IST1..7 专用物理栈)            |
| 31 ... 16 : 目标代码段选择子 (Target Code Segment Selector, 如 0x08 = 内核代码段)                |
| 15 ...  0 : 目标 ISR 线性基地址低 16 位 [15:0]                                                    |
+----------------------------------------------------------------------------------------------------+
```

在配置双重错误（`#DF`，Vector 8）时，操作系统将该描述符的 `IST` 字段配置为 `0b001`（指向 `TSS.IST1`）：
- 当发生栈溢出导致的 `#DF` 时，CPU 硬件在微架构级别强制执行原子换栈：
  直接读取任务状态段（TSS）偏移 `+0x24` 处的 64 位纯净物理栈顶地址加载入 `%rsp`；
- 随后将引发故障时的 `%ss`、旧 `%rsp`、`%rflags`、`%cs`、`%rip` 与错误码（Error Code 恒为 0）顺序压入纯净栈；
- 这彻底阻断了由于当前栈被踩踏而连锁诱发三重故障（Triple Fault）导致整机冷黑屏的绝境，为操作系统记录崩溃转储（Kernel Panic Dump）守住了最坚固的一道防线。

## 10.7 崩溃上下文持久化存储与非易失 RAM 恢复契约 {#sec-edge.3.10.7}

### 内存布局与防冷启动覆写规划

在硬件触发看门狗复位或软件主动重启之前，最宝贵的财富是刚刚捕获的崩溃结构体 `CrashDump`。
如果将结构体放在普通的 `.bss` 或全局变量中，芯片重启执行 CRT0 汇编时，清零循环将瞬间把这一线索彻底抹平！

工业级自愈固件必须在 GNU 链接脚本中开辟专用的**非易失/保留 RAM 隔离区（Retained / No-Init RAM）**：

```ld
/* 专用于崩溃现场持久化的 No-Init RAM 分区 */
MEMORY
{
    FLASH (rx)      : ORIGIN = 0x08000000, LENGTH = 512K
    RAM (rwx)       : ORIGIN = 0x20000000, LENGTH = 127K
    RETAINED_RAM(rw): ORIGIN = 0x2001FC00, LENGTH = 1K   /* 位于 RAM 最末端 1KB */
}

SECTIONS
{
    /* 标注 NOLOAD: CRT0 启动汇编绝不清零、不重定位此段！ */
    .crash_dump_section (NOLOAD) :
    {
        . = ALIGN(8);
        _s_crash_dump = .;
        *(.crash_dump)
        . = ALIGN(8);
        _e_crash_dump = .;
    } > RETAINED_RAM
}
```

在 C 代码中，将转储对象强制绑定至该段：

```c
/* 物理断电但热重启不被清零的保留崩溃快照 */
__attribute__((section(".crash_dump"), aligned(8)))
static CrashDump g_persistent_crash_dump;
```

### 校验和与完整性防御契约

由于系统可能经历硬件冷上电（RAM 充满随机电气噪声）或电池跌落，不能仅凭内存中有数据就草率认为发生了合法崩溃。
在 `experiments/ch10/fault_recovery.c` 中，我们制定了严密的完整性校验契约：

```c
typedef struct {
    uint32_t magic;            /* 必须恒等于 0xDEADBEEF */
    uint32_t fault_reason;     /* 故障类别枚举 */
    uint32_t faulting_pc;      /* 导致崩溃的代码物理地址 */
    uint32_t faulting_lr;      /* 调用者返回地址 */
    uint32_t faulting_address; /* 访问违规目标物理内存地址 */
    uint32_t status_reg;       /* CFSR / mcause / 错误码 */
    uint32_t timestamp_us;     /* 崩溃发生时刻系统时间戳 */
    uint32_t checksum;         /* 异或求和校验码 */
} CrashDump;

bool crash_dump_validate(const CrashDump *dump) {
    if (!dump || dump->magic != CRASH_DUMP_MAGIC) return false;
    uint32_t expected = dump->magic ^ dump->fault_reason ^ dump->faulting_pc ^ 
                        dump->faulting_lr ^ dump->faulting_address ^ 
                        dump->status_reg ^ dump->timestamp_us ^ 0xA5A5A5A5U;
    return dump->checksum == expected;
}
```

在芯片复位重启的第一时间，诊断服务优先读取该结构并调用 `crash_dump_validate`：
- 若校验通过且 `magic == 0xDEADBEEF`：确认系统刚刚经历了一次非正常崩溃！立即将该快照打包，在后台通过 CAN 总线或低频串口发送给工业云端；
- 随后将 `magic` 写入清零标志，防止下一次冷启动发生误报。


### 应急 Flash 扇区循环转储（Emergency Flash Ring Dump）

在某些没有配备电池备份 SRAM（Battery-Backed RAM）的低成本嵌入式节点中，崩溃快照必须直接持久化写入片上或外部 SPI Flash 的预留诊断扇区：
- **物理约束**：Flash 的物理写入需要以页（Page, 如 256 字节）为单位，且写入前必须保证该物理块已被擦除（数据全为 `0xFF`）；
- **扇区环形槽位设计**：
  在专用的 4 KB 诊断扇区中，划分为 16 个 256 字节的快照槽位（Slots）。
  崩溃处理程序从头扫描扇区，寻找第一个 `magic == 0xFFFFFFFF` 的空白槽位，利用 Flash 的按页编程指令将当前崩溃结构体直接烧录进去；
- **磨损均衡与快速擦除**：
  只有当整整 16 个槽位全部被填满后，下一次异常发生时，固件才发起一次扇区擦除操作。
  这确保了即使在频繁调试或恶劣干扰工况下，Flash 物理扇区的擦写寿命（通常为 100,000 次）不会在短期内被耗尽。

## 10.8 复位原因分流与后验自愈：从 RESC 寄存器到安全模式跃迁 {#sec-edge.3.10.8}

### 复位原因状态寄存器（RESC）解复用

当微控制器完成启动汇编并进入 `main` 函数时，首要任务不是盲目开启外设，而是**问一问自己：我刚才是为什么复位的？**

微控制器内部集成了硬件状态锁存器，用于记录上一轮复位的物理根因。
以 Stellaris LM3S6965 的**复位原因寄存器（`SYSCTL_RESC`，基址 `0x400F_E05C`）**为例：

| 位偏移 | 符号名称 | 访问属性 | 硬件置位物理触发条件 | 启动后验自愈对策 |
|:--|:--|:--|:--|:--|
| `bit 0` | `MOSCFAIL` | 读/写1清 | 主石英晶振停振或失锁 | 切换至内部安全 RC 振荡器运行，上报时钟故障 |
| `bit 1` | `POR` | 读/写1清 | 主电源初次上电（Power-On Reset） | 执行系统全量冷启动、初始化所有外设与非易失参数 |
| `bit 2` | `BOR` | 读/写1清 | 供电电源发生瞬间跌落（Brown-Out Reset） | 检查外部供电健康度，记录欠压报警 |
| `bit 3` | `WDT` | 读/写1清 | **硬件看门狗超时发生复位** | **触发自愈分支！读取崩溃转储，进入安全降级模式** |
| `bit 4` | `SW` | 读/写1清 | 软件主动通过 `SYSRESREQ` 触发的受控重启 | 正常固件升级或软件自检重启 |
| `bit 5` | `EXT` | 读/写1清 | 外部物理 RST 引脚被人工按键拉低 | 人工维护状态 |

### 工业级复位自愈状态机决策架构

```c
/* 系统启动自愈引导决策器 */
void system_startup_triage(void) {
    uint32_t reset_cause = SYSCTL->RESC;
    
    /* 1. 优先读取持久化 RAM 中的崩溃转储快照 */
    bool has_valid_crash = crash_dump_validate(&g_persistent_crash_dump);

    if (reset_cause & SYSCTL_RESC_WDT) {
        /* 看门狗超时复位：表明上一轮发生了严重的任务死锁或失控！ */
        SYSCTL->RESC = SYSCTL_RESC_WDT; /* W1C 清除标志位 */
        
        if (has_valid_crash) {
            log_safety_event("Watchdog Reset with Valid Crash Dump", &g_persistent_crash_dump);
        }

        /* 自愈降级策略：禁止启动高功耗或危险执行机构，进入安全维护模式 */
        enter_safe_degraded_mode();
        return;
    }

    if (reset_cause & SYSCTL_RESC_POR) {
        SYSCTL->RESC = SYSCTL_RESC_POR;
        /* 正常上电全量引导 */
        enter_normal_operational_mode();
        return;
    }

    /* 其他异常复位分支处理... */
}
```

通过这一自愈状态机，系统彻底消除了“故障发生 $ o$ 重启 $ o$ 继续执行错误逻辑 $ o$ 再次崩溃”的致命死循环重启振荡（Crash Looping），为构建真正坚不可摧的工业级自治节点提供了终极保障。

### 系统分级降级自愈策略对照矩阵

在复位原因分析完毕后，系统引导程序根据物理根因与连续崩溃次数，动态裁决进入哪种**系统降级运行模式（System Degraded Mode）**：

| 复位物理根因 (RESC) | 持久化崩溃快照判定 | 连续异常计数 | 系统自愈裁决目标模式 | 执行机构与外设安全约束 |
|:--|:--|--:|:--|:--|
| **POR (冷上电复位)** | 无崩溃数据 (`0xFFFFFFFF`) | 0 | **全功能运行模式 (Full Mode)** | 开放所有外设、全额电压与主频运行 |
| **WDT (看门狗复位)** | 单次超时 (Token 超期) | 1 | **跛行回家模式 (Limp-Home Mode)** | 降低电机转速上限 50%、记录云端告警、重启所有任务 |
| **WDT (看门狗复位)** | 连续超时且 PC 位于同一函数 | $\ge 3$ | **安全隔离维护模式 (Safe Isolation)** | 物理封锁逆变器 PWM、拉响警报、仅保留 CAN 诊断通信 |
| **BOR (欠压跌落)** | 电源电压低于下限 | 任意 | **低功耗生存模式 (Survival Mode)** | 关断所有大电流外部执行器，等待外部供电电压平稳 |
| **MOSCFAIL (时钟失锁)**| 主晶振停振 | 任意 | **应急时钟降级模式 (Backup Clock)** | 强制切换至内部安全 RC 振荡器运行，降速维持基本通信 |

通过建立这一多维度的自愈状态机裁决表，设备摆脱了单一的“死机重启、再死机再重启”的震荡陷阱，真正具备了与工业高安全设备相符的自适应弹性生存能力。

## 10.10 本章陷阱 {#sec-edge.3.10.10}

::: errata 本章陷阱

1. **在 SysTick 或定时器中断服务例程中周期性喂狗**：
   - 现象：系统任务全部陷入死锁，主控制循环彻底冻结，但看门狗永远不复位，控制对象失控撞毁。
   - 原因：中断的硬件触发与操作系统任务调度完全脱节，盲目喂狗导致看门狗失去对业务层健康度的监控能力。
   ```c
   /* 致命伪安全反模式：在硬件滴答中断中盲目喂狗 */
   void SysTick_Handler(void) {
       wdt_feed_hardware(); /* 极其危险！业务任务死锁时中断仍在运行，看门狗形同虚设！ */
       os_tick_step();
   }
   ```
   - 修复：强制建立多任务心跳监管中心（`WatchdogSupervisor`），只有所有受控业务任务均在合法窗口内汇报单调递增的代际 Token 后，才在主任务中统一喂狗。

2. **忘记向看门狗锁定寄存器 WDTLOCK 写入解锁密钥**：
   - 现象：向 `WDTLOAD` 或 `WDTCTL` 写入初值无任何效果，看门狗依然以默认初值运行或未真正使能。
   - 原因：硬件看门狗在复位后处于总线写保护状态，未写入 `0x1ACCE551` 密钥之前的所有写操作均被硬件静默忽略。
   ```c
   /* 错误写法：未解锁直接写寄存器 */
   WDT_LOAD = 50000;  /* 无效写操作！硬件总线直接丢弃！ */
   WDT_CTL  = 0x03;   /* 看门狗根本未开启！ */
   
   /* 严格正确序列 */
   WDT_LOCK = 0x1ACCE551UL; /* 1. 显式写入安全密钥解锁总线写权限 */
   WDT_LOAD = 50000;        /* 2. 装填计数值 */
   WDT_CTL  = 0x03;         /* 3. 使能控制位 */
   WDT_LOCK = 0x00000000UL; /* 4. 立即重新上锁，防御野指针篡改 */
   ```
   - 修复：配置或重装载看门狗前，必须先写入解锁密钥，配置完成后立即写 0 重新上锁。

3. **在 HardFault 处理中假设当前栈指针恒等于 MSP**：
   - 现象：在带 RTOS 的系统中解码崩溃栈帧，提取出的 PC 与 LR 是毫无意义的内存乱码。
   - 原因：RTOS 任务运行在进程栈（PSP）上，异常发生时寄存器被自动压入了 PSP，而非内核的主栈（MSP）。
   ```armasm
   /* 错误汇编入口：盲目假定 MSP */
   hardfault_bad_entry:
       mrs     r0, msp
       b       hardfault_c_decoder /* 若崩溃发生在任务线程中，r0 指向错误的栈！ */
       
   /* 严格正确入口：检查 EXC_RETURN Bit 2 */
   hardfault_good_entry:
       tst     lr, #4
       ite     eq
       mrseq   r0, msp             /* Bit 2 == 0: 异常前使用 MSP (内核主栈) */
       mrsne   r0, psp             /* Bit 2 == 1: 异常前使用 PSP (任务私有栈) */
       mov     r1, lr
       b       hardfault_c_decoder
   ```
   - 修复：进入 HardFault 汇编入口后，必须首先检查 `LR`（EXC_RETURN）的 Bit 2，动态选择从 MSP 还是 PSP 读取栈帧。

4. **崩溃快照结构体未放置在持久化段导致启动清零**：
   - 现象：发生硬故障后系统复位，但在 `main` 函数中读取崩溃快照，内容全为 0。
   - 原因：结构体被分配在普通的 `.bss` 段中，芯片复位后 CRT0 启动代码的清零循环将其彻底抹去。
   ```c
   /* 错误写法：放在普通全局变量区 */
   CrashDump g_crash_dump; /* 位于 .bss 段，复位后被 CRT0 清零循环彻底覆灭！ */
   
   /* 正确写法：绑定到链接脚本的 NOLOAD 保留段 */
   __attribute__((section(".crash_dump"), aligned(8)))
   CrashDump g_persistent_crash_dump;
   ```
   - 修复：在链接脚本中开辟专用的 `.crash_dump` 段，并显式标注 `(NOLOAD)` 属性，确保启动汇编跳过清零。

5. **窗口看门狗提前喂狗引发硬件自杀式复位**：
   - 现象：系统偶尔突发意外重启，没有发生任何任务卡死，排查不出原因。
   - 原因：某任务执行过快或在空转循环中刷新看门狗，喂狗时刻早于窗口下限 $T_{early}$，被窗口看门狗判定为失控并强行复位。
   ```c
   /* 错误写法：无论何时只要有事件就喂狗 */
   void on_sensor_event(void) {
       WWDG_Refresh(); /* 若传感器事件发生极快，两次调用间隔 < T_early，硬件直接自杀复位！ */
   }
   ```
   - 修复：严格核算各任务的最小执行时间下限，或在监管中心前置平滑时间窗滤波。

6. **在 HardFault 处理函数内部再次触发二次故障（引发死锁锁定）**：
   - 现象：发生故障后系统既不重启也不打印日志，整个芯片处于锁定（Lockup）状态，电流异常。
   - 原因：解码器内部尝试通过串口发送格式化日志（`printf`），而串口本身发生总线错误；或解码器访问了非法空指针，导致致命异常递归嵌套。
   ```c
   /* 危险写法：在故障处理函数中调用高开销外设 */
   void hardfault_c_decoder(uint32_t *stacked_sp) {
       printf("PC = 0x%08X\n", stacked_sp[6]); /* 极其危险！动态内存/格式化极易引发嵌套故障！ */
   }
   ```
   - 修复：Fault 诊断代码必须保持极致极简，严禁在此处调用动态内存分配、复杂浮点格式化或带等待的外设驱动。

7. **忽略了 Cortex-M 异步总线错误（Imprecise BusFault）的延迟漂移**：
   - 现象：从栈帧解码出的 PC 地址指向一行完全正常的整型加法指令，而非引起崩溃的代码。
   - 原因：CPU 写缓冲区（Write Buffer）处于开启状态，前一条写坏地址的指令在后台总线发生错误时，CPU 流水线已经向前多执行了数条指令。
   ```c
   /* 调试对策：强制关闭写缓冲，将异步错误转为精确错误 */
   SCB->ACTLR |= (1UL << 1); /* DISDEFWBUF: 禁用默认写缓冲 */
   __asm__ volatile("dsb
 isb" ::: "memory");
   ```
   - 修复：在排查难以定位的精确错误时，可在调试阶段临时置位 `SCB->ACTLR.DISDEFWBUF` 禁用写缓冲，强制所有总线错误同步精确暴露在 `SCB->BFAR` 中。

8. **看门狗超时时间设置大于系统的物理 FTTI 预算**：
   - 现象：系统最终确实成功被看门狗复位了，但在复位前受控机械臂已经发生了物理碰撞冲顶。
   - 原因：看门狗超时时间单纯按“避免误报”拍脑袋设定为数秒，远超物理机构允许的数十毫秒最大容忍时间。
   - 修复：根据定理 10.1.1 严格计算 FTTI 上限，确保全链路检测、仲裁与安全态跃迁总耗时小于容限。

9. **在 RISC-V 异常服务程序中未将 mepc 前进即直接执行 mret**：
   - 现象：CPU 陷入同步异常例程后，一退出 `mret` 瞬间再次跌入异常，陷入永久死循环。
   - 原因：与外部中断不同，触发同步异常（如断点、非法指令）时，`mepc` 指向的就是发生故障的当前指令地址；若不修改，返回后 CPU 将再次重新执行这条导致崩溃的指令。
   ```riscv
   /* 错误写法：直接 mret */
   trap_entry:
       csrr    t0, mepc
       /* 处理异常... */
       mret        /* 重新执行崩溃指令，再次异常，死循环！ */

   /* 正确自愈返回写法：步进指令长度 */
   trap_entry:
       csrr    t0, mepc
       addi    t0, t0, 4   /* 跳过 4 字节非法指令 */
       csrw    mepc, t0
       mret
   ```
   - 修复：若打算在软件层跳过该指令自愈，必须根据指令长度显式将 `mepc` 增加 2 或 4 字节。

10. **复位后未清除 RESC 寄存器标志位导致误判连锁反应**：
    - 现象：系统在初次上电后，随后的每次软件重启都被诊断服务误判为“看门狗异常复位”。
    - 原因：`RESC` 寄存器的标志位在复位后由硬件保持，若软件不执行 W1C 写清零，历史的复位原因标志将永久残留。
    ```c
    /* 正确的复位状态获取与清除序列 */
    uint32_t reset_cause = SYSCTL->RESC;
    /* 立即 W1C 清零，防止污染下一次启动判定 */
    SYSCTL->RESC = reset_cause;
    ```
    - 修复：在读取并分类处理完复位原因后，必须立即向 `RESC` 写入对应掩码清除该标志位。

11. **x86 系统发生栈溢出时未为双重错误（#DF）配置独立 IST 栈**：
    - 现象：工控机在栈溢出瞬间直接黑屏冷重启，没有在控制台留下任何 Kernel Panic 崩溃信息。
    - 原因：发生二次压栈缺页故障引发 Triple Fault，主板硬件逻辑强制复位。
    ```c
    /* 配置 IDT #DF 描述符绑定 TSS.IST1 独立纯净物理栈 */
    set_idt_gate(8, (uint64_t)double_fault_entry, 0x08, 0x8E, 1 /* IST1 */);
    ```
    - 修复：在 64 位 TSS 中为 `#DF` 配置专用的 `IST1` 纯净物理栈，保证在栈顶粉碎时依然能输出崩溃报告。

12. **agent 错误案例：使用全局 volatile 变量在 ISR 中直接判断任务是否健康**：
    - 现象：系统运行几天后在偶发时序下突发假死，看门狗未能及时复位。
    - 原因：智能体代码写出 `if(task_flag == 1) wdt_feed();`，但在任务崩溃后该标志依然残留为 1，没有任何时间窗口与代际单调递增约束！
    ```c
    /* 致命的智能体生成代码错误：静态标志喂狗 */
    void SysTick_Handler(void) {
        if (g_task_running_flag == 1) {
            wdt_feed(); /* 致命漏洞！任务哪怕死锁崩溃，该变量依旧是 1，看门狗被彻底骗过！ */
        }
    }
    ```
    - 修复：必须采用带单调递增 Token 与窗口双向范围的 `WatchdogSupervisor` 状态机。
