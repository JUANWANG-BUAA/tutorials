**固件空中升级（Firmware Over-The-Air, FOTA / OTA）**是嵌入式系统维持全生命周期安全防护、修复未知缺陷、优化控制算法以及动态更新神经网络模型权重的唯一生命线。

在野外严苛电磁干扰、供电不稳或无线网络剧烈丢包的环境下，若升级流程存在设计漏洞，一次突发的电源跌落或断电即可能导致 Flash 中存在残缺的代码，使设备永久“变砖”（Bricking），造成无法挽回的工业事故。

## 12.1 固件空中升级生命周期与威胁模型 {#sec-edge.3.12.1}

### OTA 核心演进生命周期

一个完备且符合工业功能安全标准的 OTA 升级生命周期，绝非“把新固件写入 Flash 然后重启”那么简单，它必须被划分为 6 个严格受控且边界清晰的状态阶梯：

```text
+──────────────+      +──────────────+      +──────────────+
| 1. 固件发布   | ───► | 2. 传输与校验 | ───► | 3. 候选区暂存 |
| (离线签名/打包) |      | (分片/重传/SHA) |     | (写入 Slot 1) |
+──────────────+      +──────────────+      +──────────────+
                                                   │
                                                   ▼
+──────────────+      +──────────────+      +──────────────+
| 6. 永久确认   | ◄─── | 5. 试运行自检 | ◄─── | 4. 仲裁与重启 |
| (更新版本下限) |      | (看门狗/心跳/业务)|     | (标记 Trial)  |
+──────────────+      +──────────────+      +──────────────+
```

1. **固件编译、离线签名与打包（Release & Sign）**：
   在安全的构建服务器中，编译器生成目标代码 ELF/BIN 文件。
   打包工具计算固件哈希（SHA-256），利用产线烧录的私钥进行非对称签名（ECDSA P-256 或 RSA-3072），并将芯片架构、板级 ID、ABI 特性掩码与版本号封装进标准的镜像头部（Image Header）与类型-长度-值（TLV）元数据区。
2. **安全传输与完整性重组（Transport & Assembly）**：
   运行中的现有固件（Slot 0）通过工业总线（CAN/CAN FD、以太网或无线射频）分片接收升级包。
   传输协议必须具备分包确认、乱序重组与局部丢包重传机制。在此阶段，系统必须对通信信道提供基本的加密保护，防止窃听与篡改。
3. **备用槽位暂存与预校验（Staging & Pre-validation）**：
   将完整固件逐块烧录至备用分区（Slot 1）。
   烧录完成后，在擦写元数据前必须在内存中对 Slot 1 的魔数、尺寸、兼容性 ID、CRC 校验和与数字签名进行第一次完整性预检。若校验失败，直接清空备用槽位并向上层报告，绝不触发重启。
4. **升级请求与引导仲裁（Request & Arbitrate）**：
   预检成功后，向非易失性元数据区持久化写入“升级请求标记”，随后触发受控的系统软复位。
   系统重新上电后，首先进入不可篡改的第一阶段引导程序（Bootloader）。
   Bootloader 读取元数据，核验候选固件的合法性，**在跳转前必须先将“试运行次数已消耗”持久化标记写入 Flash**，然后才执行硬件移交。
5. **受限试运行与自主健康自检（Trial Run & Self-Test）**：
   候选固件接管硬件并启动。此时它处于“试运行状态（Trial / Testing）”。
   新固件必须在第 10 章所述的硬件看门狗超时时间（如 500 ms）内，完成包括外设通信自检、RAM 读写测试、传感器数据采样以及向看门狗监管线程注册心跳（Check-in）。
6. **状态确认与版本底线持久化（Commit & Floor Elevation）**：
   只有当新固件的所有关键自检指标全部合格，应用程序才通过系统调用触发元数据更新，将新固件标记为“已确认（Confirmed）”，并将非易失存储中的“固件版本下限（Floor Version）”提升为当前版本，彻底关闭旧固件的回滚通道；
   若在自检完成前系统发生 HardFault、死锁超时导致看门狗复位，或者关键外设初始化失败，Bootloader 在下次复位时将检测到试运行未确认违约，立刻触发**自动回滚（Automatic Rollback）**，无缝重返已确认的黄金旧固件！

### 边缘固件面临的安全威胁模型

在开放的现场部署中，固件升级通道是攻击者最青睐的攻击入口。系统设计必须针对以下威胁构筑坚固防线：

::: def OTA 威胁模型（Threat Model Matrix） {#def-edge.3.12.1.1}
1. **伪造固件注入（Forged Firmware Injection）**：攻击者窃听通信总线并向设备注入植入后门、木马的恶意二进制代码。
   *防线*：全流程非对称加密签名验证（如 ECDSA P-256），公钥证书固化于只读存储中，拒绝一切签名不匹配的代码。
2. **版本降级重放攻击（Version Downgrade / Rollback Attack）**：
   攻击者截获早先发布的、已知包含严重安全漏洞的历史合法固件版本，强行灌入设备。
   由于该历史固件拥有厂家的合法签名，简单的签名验证完全无法拦截！
   *防线*：**单调递增安全计数器（Anti-Rollback Security Counter）与版本底线锁（Version Floor）**。在元数据中维护只能单调增加的最低合法版本号，任何版本号低于当前底线的镜像均被物理拒绝。
3. **中间人篡改与通信畸变（Data Corruption in Transit）**：
   无线衰减或工业电磁脉冲导致传输数据发生单比特或突发错误翻转。
   *防线*：端到端 SHA-256 密码学散列校验与块级 CRC-32 校验，结合写后读回比对（Readback Verification）。
4. **升级中断与电源跌落撕裂（Power-Cut Incomplete State）**：
   在 Flash 擦除或编程写入的半途中突然停电，导致 Flash 处于未定义电荷状态，或元数据出现半写（Half-Written）撕裂。
   *防线*：**乒乓元数据双页轮换、代际递增序列号与二阶段提交（Two-Phase Commit）**，确保任意时刻至少存在一个完全合法、自洽的引导记录。
5. **物理故障注入与侧信道嗅探（Glitch & Side-Channel Attacks）**：
   攻击者通过瞬间降低供电引脚电压（Voltage Glitching）或拉偏时钟（Clock Glitching），诱导 CPU 在执行签名判定分支指令时发生跳转翻转。
   *防线*：双重条件校验、冗余校验流水线，以及在写 Flash 前执行关键状态的再次核验。
:::

### 差分升级（Delta Update）与全量升级的架构权衡

在物联网广域网（NB-IoT, Cat.1, LoRaWAN）等带宽极度受限（仅数 kbps 甚至几十 bps）且按流量计费的场景中，**差分空中升级（Delta FOTA / In-Place Binary Diff）**常常成为产品经理的热门诉求：
1. **差分算法数学原理（以 BSDiff / Courgette 为例）**：
   通过比对新旧两个 ELF/BIN 二进制文件，提取其中保持不变的代码块作为复制基准，仅生成记录地址重定位差值与新增字节的紧凑补丁包（Patch）；
   典型补丁包体积通常仅为全量固件的 **5% 至 15%**（例如 256 KB 固件的差分补丁仅 15 KB ~ 30 KB），显著缩减无线空口传输时间。
2. **边缘微控制器执行差分还原的沉重代价**：
   - **巨大 RAM 缓冲压力**：还原算法通常需要解压缩（如 bzip2 或 lzma），解压字典与控制块重建至少需要数十 KB 的临时 SRAM；而在仅有 32 KB ~ 64 KB 片上内存的 MCU 上，SRAM 往往在解压阶段直接耗尽！
   - **中间态断电灾难**：若在片上原地（In-Place）应用差分补丁，目标页必须先擦除再合成新指令。一旦在合成中间遭遇断电，原始代码已被部分破坏，而新代码尚未生成完毕，差分基准彻底丢失，系统面临无法逆转的死锁变砖风险！
3. **架构师选型黄金法则**：
   在片上 SRAM 小于 256 KB 的高可靠性工控设备中，**坚决优先采用 Direct-XIP 全量双区独立升级**！
   全量镜像具备自包含（Self-Contained）属性，不依赖任何历史版本的残余上下文，消除了版本链断裂与解密解压失败的单点故障风险。

::: ex 边缘非对称签名运算开销与微架构预算 {#ex-edge.3.12.1.1}
在算力紧缺的微控制器上引入密码学签名验证，必须对其算力与内存预算进行严谨的工程度量：
1. **密码学算法选型**：
   - RSA-2048：公钥验签速度极快（通常仅需数百次模乘），但公钥与签名体积较大（各 256 字节），且大数模幂运算需要较多临时 RAM；
   - ECDSA P-256（secp256r1）：公钥仅 64 字节，签名仅 64 字节，极度节省紧缺的 Flash 空间；但椭圆曲线点乘（Point Multiplication）包含大量模逆与模乘运算。
2. **微架构执行周期度量（以 100 MHz Cortex-M3 为例）**：
   - 纯软件优化的 ECDSA P-256 点乘验签大约耗费 **1,500 万至 2,500 万时钟周期**；
   - 在 100 MHz 核心主频下，单次验签耗时约 **150 ms 至 250 ms**；
   - 内存占用：纯 C 实现的微型密码学库（如 mbedTLS 或 TinyCrypt）在验签期间仅需占用 **1.5 KB 至 3.0 KB 的静态栈空间**，完全可容纳于 32 KB SRAM 中。
3. **系统工程决策**：
   200 毫秒的验签延迟在系统启动（Boot）阶段是完全可以接受的一次性成本（One-Time Cost）；但在正常运行时，绝不能在实时中断或高频采样控制流中调用非对称运算。
:::

### 产线安全启动密钥注入与根信任链（Root of Trust）

嵌入式设备的数字签名验证不是孤立存在的，它的有效性必须扎根于不可篡改的**硬件根信任（Hardware Root of Trust, RoT）**：
1. **一次性可编程熔丝（eFuse / OTP）**：
   在设备产线测试阶段，烧录工装通过调试接口向芯片内部的专有一字型电隔离熔丝阵列（eFuse）写入公钥摘要（OEM Root Public Key Hash, ROTPKH）；
   写入完成后，硬件永久熔断读写控制熔丝，使得该哈希值在物理层面变为不可逆的只读状态，任何后续软件指令或 JTAG 调试均无法篡改。
2. **信任链逐级度量延伸（Chain of Trust Extension）**：
   - **Stage 0（ROM Code）**：芯片内部出厂固化的只读代码。上电瞬间首先读取 Bootloader 镜像，计算其公钥哈希并与 eFuse 中的 ROTPKH 进行单向比对；
   - **Stage 1（Secure Bootloader）**：ROM Code 验证 Bootloader 签名通过后移交执行权。Bootloader 驻留在写保护的只读扇区中；
   - **Stage 2（Application Slots）**：Bootloader 依据内部固化的公钥，验证待更新的 Slot 0 / Slot 1 应用程序镜像签名；
   从物理熔丝到最终运行的工业业务控制逻辑，每一级代码在执行前必须受到上一级受信任实体的严格数学认证，形成环环相扣的安全闭环。

## 12.2 双区 Flash 物理分区与元数据布局 {#sec-edge.3.12.2}

### 片上 NOR Flash 的物理擦写特性与物理代际约束

微控制器的片上非易失存储几乎全部采用**嵌合 NOR Flash（Embedded NOR Flash）**。
与外挂 NAND Flash 或硬盘不同，NOR Flash 具备以下对固件更新产生决定性影响的物理法则：

- **读取特性**：支持字节/字粒度的随机寻址读取，CPU 可以像访问 SRAM 一样直接在 Flash 上执行指令（Execute-In-Place, XIP），无需预先将代码搬入 RAM。
- **写入法则（Bit Programming）**：写入操作只能将存储单元中的比特位从逻辑 `1` 改写为逻辑 `0`。**Flash 控制器绝对无法在不擦除的情况下将逻辑 `0` 改写为 `1`**！
- **擦除法则（Block/Page Erase）**：擦除是恢复逻辑 `1` 的唯一手段，且擦除具有粗糙的块粒度。对于德州仪器 Stellaris LM3S6965，最小擦除单位为 **1 KB 的页面（Page）**；对于 STM32F4，最小擦除扇区可达 16 KB 乃至 128 KB。擦除操作将整页内所有字节重置为 `0xFF`。
- **擦写寿命（Endurance）**：根据 LM3S6965 官方手册电气规范（第 22.1.6 节），保证的编程/擦除寿命（PECYC）为 **10,000 至 100,000 次**；且单页擦除时间（$T_{ERASE}$）长达 **20 毫秒至 25 毫秒**，单字编程时间（$T_{PROG}$）为 **20 微秒**。

上述物理约束宣告了：**“边运行程序边直接覆盖自身 Flash 代码”是绝对不可能的**！
因为擦除当前代码所在的 1 KB 页面会导致 CPU 下一条预取的指令立刻读出 `0xFFFFFFFF`（无效指令），直接诱发 HardFault 导致死机变砖。

### 异构微控制器的扇区物理拓扑差异

在工程设计双区 Flash 分区表时，必须极度审慎地核查目标芯片的扇区拓扑：

1. **等长均一扇区架构（Uniform Sectors）**：
   - 典型代表：TI Stellaris LM3S6965（全片由 256 个独立的 1 KB 页面构成）、Nordic nRF52840（4 KB 页面）。
   - *工程优势*：分区规划极度灵活，可将任意物理页规划为元数据页或代码槽位，无需担心跨扇区尺寸不对齐。
2. **非均一扇区架构（Non-Uniform Sectors）**：
   - 典型代表：STM32F407（Sector 0~3 为 16 KB，Sector 4 为 64 KB，Sector 5~11 为 128 KB）。
   - *工程挑战*：若采用 Direct-XIP，Slot 0 与 Slot 1 必须具备完全对称的物理尺寸与对齐边界。若将 Slot 0 放置在低端混合扇区，Slot 1 放置在高端 128 KB 扇区，擦写时间与扇区粒度不一致将导致固件更新逻辑极度脆弱！

### 片上嵌合 eFlash 与外部 SPI NOR Flash 的混合拓扑

在现代复杂边缘网关中，存储拓扑往往呈现片上（On-Chip eFlash）与片外（External SPI/QSPI NOR Flash）混合的形态：
1. **片上 eFlash 的总线特征**：
   - 直接挂载于 CPU 的高速内部总线（如 ARM AHB-Lite / AXI 总线）；
   - 支持单周期或极低等待周期（Wait States）读取，支持真正的并行随机指令预取与零延迟中断向量响应；
   - 缺点是受限于芯片半导体制造工艺（高压电荷泵与高密度逻辑单元难以整合），容量通常被限制在 128 KB ~ 2 MB 以内。
2. **片外 Quad-SPI / Octal-SPI NOR Flash 的特征**：
   - 典型代表：Winbond W25Q128（16 MB）、Macronix MX25R；
   - 通过 QSPI 控制器映射至 CPU 内存地址空间（如 `0x90000000`），支持硬件直接取指（QSPI XIP 模式）；
   - *升级优势*：外部 Flash 成本极低、容量充沛（数 MB 至数十 MB），可作为超大固件包（包括大体积深度学习权重、音视频资源与多语言字体文件）的天然暂存仓库；
   - *控制协议物理约束*：外部 SPI Flash 的写操作遵循严格的主从命令序列：
     每次写入前必须先发送 `0x06`（Write Enable, WREN）指令拉高状态寄存器的 `WEL` 位；
     擦除时需发送 `0x20`（4 KB 扇区擦除）并轮询状态寄存器 `0x05`（Read Status）的 `WIP`（Write-In-Progress）位，直至硬件电荷释放完成。

### 双区直读执行（Direct-XIP）与交换升级（Swap Mode）架构对比

为了解决原地覆写引发的系统崩溃，业界演进出了两种主流的双区拓扑：

| 拓扑模式 | 物理分区要求 | 升级过程机制 | 优点 | 缺点 / 架构代价 |
|:--|:--|:--|:--|:--|
| **带 Scratch 的交换模式 (Swap-using-scratch)** | Slot 0 (Active), Slot 1 (Staging), Scratch (暂存区) | 重启后 Bootloader 借助 Scratch 扇区，将 Slot 0 与 Slot 1 的代码块逐页对调搬运 | 应用程序链接地址固定，编译器永远只需以 Slot 0 基址生成镜像 | 升级需耗费数秒进行密集物理擦写，严重消耗 Flash 寿命，搬运中途掉电状态极度复杂 |
| **双区直读执行 (Direct-XIP / Dual-Bank)** | Slot 0 (Bank A), Slot 1 (Bank B), 无需 Scratch | 两个分区均为完全对等的执行槽位；Bootloader 根据元数据直接重定向向量表并跳转执行 | **零代码物理搬运，升级瞬间完成**；Flash 擦写次数减半，极大提升芯片寿命与安全性 | 两个槽位需要不同的链接地址，或要求固件采用位置无关代码（PIC），或依赖 MMU/重映射硬件 |

::: thm 闪存磨损与寿命倍率定理（Flash Wear & Lifespan Multiplier Theorem） {#thm-edge.3.12.2.1}
设应用程序镜像大小为 $S_{img}$，最小擦除页大小为 $S_{page}$，单块 Flash 的物理擦写耐久上限为 $N_{cycle}$。
在 Swap 模式下，每次固件更新需要将 $S_{img}$ 拆分为 $K = S_{img} / S_{page}$ 个块进行双向交换；Scratch 扇区在单次升级中必须被擦写 $K$ 次。
全系统能够承受的安全升级总次数上限受制于 Scratch 扇区：
$$N_{OTA}^{Swap} = \left\lfloor \frac{N_{cycle}}{S_{img} / S_{page}} \right\rfloor$$
而在 Direct-XIP 架构中，新镜像直接一次性写入备用槽位，无中间暂存擦写，各槽位轮流均匀磨损：
$$N_{OTA}^{Direct-XIP} = 2 \cdot N_{cycle}$$
两者的芯片使用寿命比值达到惊人的：
$$\text{Gain} = \frac{N_{OTA}^{Direct-XIP}}{N_{OTA}^{Swap}} = 2 \cdot \left( \frac{S_{img}}{S_{page}} \right)$$
例如对于 128 KB 镜像与 4 KB 页面，Direct-XIP 使得芯片物理耐久寿命直接提高 $2 \times 32 = 64$ 倍！
:::

### 链接脚本在 Direct-XIP 架构下的双区地址解耦

在 Direct-XIP 架构中，Slot 0 与 Slot 1 的物理 Flash 起始基址不同（例如 Slot 0 位于 `0x00010000`，Slot 1 位于 `0x00030000`）。
在缺乏硬件物理内存重映射（Hardware Remap / Alias）的微控制器上，固件开发者必须在工程层面解决**代码运行地址与链接地址强耦合**的矛盾：

```text
方案 A: 双二进制分别链接 (Dual-Binary Compilation)
├── App_Slot0.elf: 链接脚本硬编码 ORIGIN = 0x00010000
└── App_Slot1.elf: 链接脚本硬编码 ORIGIN = 0x00030000
    优点: 代码执行效率最高，完全使用标准绝对寻址；
    代价: 发布每次更新时必须构建两个二进制文件，OTA 下发时需根据当前活动槽位分发。

方案 B: 位置无关代码 (Position-Independent Code, PIC)
├── 使用 -fPIC -fPIE -mpic-register=r9 编译参数
└── 全局变量通过全局偏移表 (GOT) 相对寻址
    优点: 单一二进制文件可烧录至任意槽位运行；
    代价: 访存增加一层 GOT 间接指针解引用，指令体积膨胀 10%~15%，消耗一个通用寄存器。

方案 C: 现代微控制器硬件别名重映射 (Hardware Alias Remap)
└── 芯片内部总线矩阵提供重映射寄存器 (如 STM32 SYSCFG_MEMRMP 或 Dual-Bank Swap)
    优点: 硬件在物理层将当前活动 Bank 动态映射至 0x08000000，应用统一以 0 基址链接！
```

在本章配套的实验固件中，我们通过在编译脚本中传入参数 `-DAPP_BASE`，在链接阶段动态注入基址，清晰呈现了方案 A 的物理隔离本质。

## 12.3 掉电安全性与原子切换状态机 {#sec-edge.3.12.3}

### 乒乓元数据双页轮换机制

为了在无法支持原子写事务（Atomic Transactions）的裸机 NOR Flash 上实现强一致性，系统绝不能原地擦写元数据页。
我们将元数据划分为两个独立的擦除页：`Page 0` 与 `Page 1`。
在元数据头部引入单调递增的 32 位**代际序列号（Generation Counter）**。

读取规则（Read Protocol）：
1. 分别读取 `Page 0` 与 `Page 1` 的数据；
2. 校验页面的魔数（Magic Number `0x454D4554`）、内容有效性以及 CRC-32 校验和；
3. 检查尾部的**提交标记字（Commit Word）**是否已经被完全清零；
4. 若两页均合法有效，**选择代际号（Generation）较大的一页作为当前系统真实元数据**；
5. 若其中一页发生校验错误或提交标记未清零（表明上次写入中途掉电），系统静默废弃该页，自动采纳另一页的旧代际数据，实现天然掉电恢复！

写入规则（Two-Phase Write Protocol）：
假设当前有效数据位于 `Page 0`（代际号为 $G$），需要写入新状态：
1. **擦除备用页**：将 `Page 1` 整页擦除为全 `0xFF`；
2. **填充数据与 CRC**：将新状态的代际号设为 $G + 1$，计算除提交标记外的全部数据 CRC-32，将数据逐字写入 `Page 1`（此时偏移 28 的提交标记依然保持为 `0xFFFFFFFF`）；
3. **回读比对（Readback Verification）**：将 `Page 1` 已写入字节逐字节与内存缓冲区比对，确保没有任何闪码、坏位或总线错乱；
4. **提交翻转（Atomic Commit）**：仅在回读 100% 正确后，发出单次 32 位编程指令，将偏移 28 的提交标记从 `0xFFFFFFFF` 改写为 `0x00000000`！

::: thm 元数据二阶段提交原子性定理（Two-Phase Flash Commit Theorem） {#thm-edge.3.12.3.1}
在不支持多字事务的 NOR Flash 介质上，若将记录的有效性判定严格收敛于单个 32 位“提交字（Commit Word）”的翻转状态：
当且仅当该字全为 0 且数据区 CRC 校验完全匹配时记录方为有效。
由于 NOR Flash 的单字编程（1变0）为不可分割的物理电荷注入过程：
无论电源跌落在擦除期、数据写入期还是校验期，该记录因提交标记未满足条件均被判定为无效，系统状态恒定回退至上一有效代际；
系统绝不会解析出一个处于半擦除或半写入撕裂状态的虚假配置。
:::

::: def 元数据状态代际四元组与有效性判定式 {#def-edge.3.12.3.2}
在任意离散时刻 $t$，双区 OTA 控制器的非易失状态由五元组完全定义：
$$\mathcal{S}_t = \langle G, \, C, \, K, \, T, \, F \rangle$$
其中：
- $G \in \mathbb{N}^+$ 为单调递增代际编号（Generation），用于仲裁双备份页的新旧权属；
- $C \in \{0, 1\}$ 为当前已获得永久确认的黄金固件槽位（Confirmed Slot）；
- $K \in \{0, 1, \text{NONE}\}$ 为候选试运行固件槽位（Candidate Slot），约束 $K \neq C$；
- $T \in \{0, 1\}$ 为试运行已消耗标记（Trial Used）；
- $F \in \mathbb{N}^+$ 为不可逆转的固件版本底线（Version Floor）。

元数据有效性由三项布尔约束联合判定：
$$\text{Valid}(\mathcal{S}) \iff (\text{Magic} == 0x454D4554) \land (\text{CRC32}(\mathcal{S}_{payload}) == \text{CRC}_{stored}) \land (\text{CommitWord} == 0x00000000)$$
当且仅当 $\text{Valid}(\mathcal{S}) \equiv \text{TRUE}$ 时，该状态才被引导加载器承认为合法决策依据。
:::

元数据核心结构在 C 语言中严格定义如下：

```c
typedef struct {
    uint32_t magic;         /* 0x454D4554 ("EMET") */
    uint32_t generation;    /* 代际计数器，单调递增 */
    uint32_t confirmed;     /* 当前确认运行的槽位 (0 或 1) */
    uint32_t candidate;     /* 待升级的候选槽位 (0, 1 或 OTA_NONE=2) */
    uint32_t trial_used;    /* 试运行次数已消耗标记 (0: 未消耗, 1: 已消耗) */
    uint32_t floor;         /* 固件版本底线防降级锁 (单调递增) */
    uint32_t crc32;         /* 前 24 字节的 CRC-32 校验和 */
    uint32_t commit_word;   /* 提交标记: 0x00000000 表示有效, 0xFFFFFFFF 表示写入中 */
} __attribute__((packed)) OtaMetaRecord;
```

### 二阶段原子提交协议的 C 语言核心逻辑

在 `experiments/ch12/ota.c` 中，元数据页的更新函数 `commit_meta` 严格贯彻了二阶段提交的硬件物理法则：

```c
/* 乒乓元数据双页轮换与二阶段原子提交核心实现 */
static OtaStatus commit_meta(Nor *n, OtaMeta m, bool first) {
    uint8_t raw[32];
    if (m.generation == UINT32_MAX) return OTA_STATE; /* 严格防止 32 位代际序列号溢出回绕 */

    /* 1. 目标地址仲裁：永远写入当前非活动备用页 */
    uint32_t dst = first ? OTA_META0 : (m.page == OTA_META0 ? OTA_META1 : OTA_META0);

    /* 2. 组装待提交数据包并计算前 24 字节 CRC-32 */
    memset(raw, 0xff, sizeof(raw));
    put32(raw + 0, OTA_META_MAGIC);       /* 魔数 0x454D4554 ("EMET") */
    put32(raw + 4, m.generation + 1);     /* 代际序列号严格单调加 1 */
    put32(raw + 8, m.confirmed);          /* 黄金已确认槽位 */
    put32(raw + 12, m.candidate);         /* 候选试运行槽位 */
    put32(raw + 16, m.trial_used);        /* 试运行次数已消耗标记 */
    put32(raw + 20, m.floor);             /* 固件版本底线防降级锁 */
    put32(raw + 24, ota_crc32(raw, 24));  /* 保护前 24 字节内容的 CRC-32 */

    /* 3. 第一阶段：擦除目标备用页 */
    OtaStatus s = nor_erase(n, dst);
    if (s != OTA_OK) return s;

    /* 4. 第一阶段：写入前 28 字节内容（此时偏移 28 的 commit_word 依然保持全 0xFF） */
    for (unsigned k = 0; k < 28; k += 4) {
        s = nor_program(n, dst + k, raw + k);
        if (s != OTA_OK) return s;
    }

    /* 5. 关键回读校验：比对 Flash 已烧录数据是否与内存 100% 吻合 */
    if (memcmp(n->bytes + dst, raw, 28) != 0) return OTA_INVALID;

    /* 6. 第二阶段：仅在回读无误后，原子烧录全 0 的提交字！ */
    put32(raw + 28, 0x00000000);
    return nor_program(n, dst + 28, raw + 28);
}
```

读代码：整段逻辑没有任何歧义。在第 6 步成功执行前，该页在任何判定函数中均被认定为未就绪；一旦第 6 步写入成功，新代际状态即刻在物理层面正式生效！

### 掉电时序断点分类学

为了严谨证明系统在任意时钟周期的鲁棒性，我们将断电时钟时刻严格正交分解为 5 类场景：

1. **擦除中途掉电**：Flash 介质内部电荷泵正在释放负高压，部分晶体管处于亚阈值未定义导通状态。由于擦除未完成，回读校验必然失败；
2. **载荷写入中途掉电**：有效载荷部分写入，Header 尚未写入。由于未检测到合法 Header 魔数，该槽位被视作裸空间；
3. **Header 写入中途掉电**：载荷已写完，Header 仅写入前几个字段。由于 Header CRC-32 无法配平，预检拒绝发出升级请求；
4. **元数据写完但 Commit Word 写入前掉电**：元数据内容完整，CRC-32 正确，但 `commit_word == 0xFFFFFFFF`。解析器判定其为正在写入的半成品，强制弃用；
5. **Commit Word 单字撕裂（Torn Write）**：若在单字电荷注入微秒内掉电，导致 `commit_word` 读出非 0（例如 `0x0000FFFF`）。解析器严格执行 `commit_word == 0x00000000` 比较，撕裂字同样被彻底否决。

## 12.4 镜像完整性、数字签名与降级防范 {#sec-edge.3.12.4}

### 镜像文件结构与头部格式

每个存放于槽位中的固件镜像，必须包含一个固定位于镜像头部的紧凑元数据描述符。
参考工业级 MCUboot 规范，镜像头部包含以下关键字段：

| 偏移量 | 字段名称 | 类型 | 说明与物理约束 |
|:--|:--|:--|:--|
| `0x00` | `ih_magic` | `uint32_t` | 镜像专属魔数，固定为 `0x45494D47` (`"EIMG"`) |
| `0x04` | `ih_version` | `uint32_t` | 固件单调版本号（例如 1, 2, 3...） |

### 工业级 MCUboot TLV 链表遍历与零内存解析

在工业标准（如 MCUboot v2.2.0）规范中，位于镜像代码尾部的 TLV 元数据区结构如下：

```c
#define IMAGE_TLV_INFO_MAGIC      0x6907
#define IMAGE_TLV_PROT_INFO_MAGIC 0x6908

struct image_tlv_info {
    uint16_t it_magic;   /* TLV 区域魔数 */
    uint16_t it_tlv_tot; /* TLV 区域总字节大小 (包含本头部) */
};

struct image_tlv {
    uint8_t  it_type;   /* TLV 类型: SHA256(0x10), KEYHASH(0x01), SIG(0x22), SEC_CNT(0x50) */
    uint8_t  _pad;      /* 对齐填充 */

```

固件在 Flash 中遍历 TLV 链表时，**完全不需要在 SRAM 中分配任何动态链表节点**，只需通过指针步进在 Flash 上原位只读扫描：

```c
/* Flash 原位 TLV 只读扫描器：零动态内存开销 */
const uint8_t *find_tlv_record(const uint8_t *tlv_base, uint16_t tot_len, uint8_t target_type, uint16_t *out_len) {
    const struct image_tlv_info *info = (const struct image_tlv_info *)tlv_base;
    if (info->it_magic != IMAGE_TLV_INFO_MAGIC && info->it_magic != IMAGE_TLV_PROT_INFO_MAGIC) {
        return NULL;
    }
    const uint8_t *cur = tlv_base + sizeof(struct image_tlv_info);
    const uint8_t *end = tlv_base + tot_len;
    while (cur + sizeof(struct image_tlv) <= end) {
        const struct image_tlv *tlv = (const struct image_tlv *)cur;
        if (tlv->it_type == target_type) {
            *out_len = tlv->it_len;
            return cur + sizeof(struct image_tlv); /* 返回指向 Flash 中数据负载的直接指针 */
        }
        cur += sizeof(struct image_tlv) + tlv->it_len;
    }
    return NULL; /* 未检索到目标类型 */
}
```

### 数字签名认证与防降级攻击（Anti-Rollback）数学逻辑

在 `experiments/ch12/signature_test.py` 中，我们构建了标准的非对称签名验证流水线：
固件发布者使用保密的椭圆曲线私钥 $d$ 对包含头部与载荷的整包计算数字签名：
$$\text{Signature} = \text{Sign}_{d}\left(\text{SHA-256}(\text{Header} \parallel \text{Payload})\right)$$

微控制器 Bootloader 内部预埋有对应的公钥点 $Q = d \cdot G$。
在升级验证时，执行数学验证方程：
$$\text{Verify}_{Q}\left(\text{SHA-256}(\text{Header} \parallel \text{Payload}), \, \text{Signature}\right) \stackrel{?}{=} \text{TRUE}$$

即使签名完全合法，固件仍必须接受**固件版本底线（Firmware Floor）的硬性审查**：
$$V_{candidate} \ge \text{Floor}_{persisted}$$
只有当候选镜像的版本号大于等于当前已记录的底线版本时，才允许将其载入调度。
一旦新镜像成功通过自检并转正，系统执行底线提升：
$$\text{Floor}_{new} \leftarrow \max(\text{Floor}_{old}, \, V_{candidate})$$
此后，攻击者若尝试向设备重放即使带有合法官方签名的低版本固件（例如 $V = 1$ 的老版本固件），也会因无法通过单调底线检查而被硬件逻辑断然丢弃！

### 侧信道时序攻击防范与确定性签名机制

在安全引导的底层密码学实现中，系统程序员不仅要关注算法数学的正确性，还必须严密防范微架构层面的侧信道泄漏（Side-Channel Leakage）：
1. **常数时间比较算法（Constant-Time Memcmp）**：
   在核验哈希摘要或 HMAC 认证码时，标准的 C 语言 `memcmp` 在遇到第一个不匹配的字节时会立即提前退出返回非零值。
   攻击者可通过高精度示波器测量芯片的比较执行耗时（Timing Attack），逐字节推断出正确的哈希值！
   固件中必须强制使用恒定时间异或累加比较器：

```c
/* 恒定时间内存比对：防御时序侧信道攻击 */
int constant_time_memcmp(const void *a, const void *b, size_t n) {
    const unsigned char *p = (const unsigned char *)a;
    const unsigned char *q = (const unsigned char *)b;
    unsigned char result = 0;
    for (size_t i = 0; i < n; ++i) {
        result |= p[i] ^ q[i]; /* 无分支跳转，循环次数恒定为 n */
    }
    return (int)result;
}
```

2. **确定性随机数防私钥泄露（RFC 6979 规范）**：
   在传统的 ECDSA 签名过程中，若每次生成签名所使用的瞬态随机数 $k$ 质量不高、存在偏置或发生重用，攻击者通过截获同一私钥签署的两个不同固件，即可直接通过基础代数消元求解出生产私钥 $d$（索尼 PS3 私钥泄露即为此机理）！
   因此，现代工业签名打包工具必须严格采用 RFC 6979 确定性派生方案，将私钥与消息摘要通过 HMAC-SHA256 伪随机函数派生 $k$，彻底杜绝硬件伪随机数发生器（TRNG）故障引发的灾难。

### 保护区 TLV 格式与模型版本绑定

在现代端侧 AI 系统中，固件不仅包含 C 语言执行指令，还深度内嵌了神经网络权重（如第 11 章的振动分类 MLP 矩阵）。
若上层固件升级了控制逻辑，但底层的特征提取维度（`IN_DIM`）或定点缩放格式发生变更，而算法模型版本未同步更新，系统将产生严重的控制偏差。
为此，镜像 Header 中显式包含了 `ih_model_version` 与 `ih_feature_abi`。
Bootloader 在核验镜像时，不仅核验架构是否匹配，还必须比对硬件协处理器版本与板级接口掩码，形成“硬件-固件-模型”三位一体的原子兼容性认证。

## 12.5 Bootloader 到应用程序的硬件移交合同 {#sec-edge.3.12.5}

### 移交前的硬件现场清理契约（Clean Handoff Contract）

在很多初级开发者的代码中，从 Bootloader 跳转到应用程序通常被草率地写成一行简单的函数指针调用：
`((void (*)(void))app_reset_handler)();`
**在严肃的工业嵌入式领域，这是最致命的代码缺陷之一！**

Bootloader 也是一段复杂的嵌入式软件，在它运行期间，它通常初始化了串口输出调试信息、开启了 SysTick 用于延时、启用了外设中断、并在 SRAM 中建立了复杂的栈帧结构。
如果不加清理直接跳入应用程序，将引发下列灾难性后果：
1. **未决中断击穿**：Bootloader 开启的外设中断若在跳转瞬间触发，CPU 将索引 Bootloader 的旧向量表，跳转到早已失效的代码地址执行，导致系统崩溃；
2. **栈指针污染与内存溢出**：应用程序的 CRT0 假定栈顶处于整洁的 `_estack` 初始状态。若继承了 Bootloader 深度嵌套的脏栈指针，极易在随后的函数调用中发生栈溢出；
3. **特权级与寄存器状态污染**：如果 Bootloader 配置了 CONTROL 寄存器使用了非特权级或进程栈指针（PSP），应用程序启动时将无法访问特权系统控制寄存器。

::: method 架构级移交标准六步规约（Standard Handoff Contract） {#method-edge.3.12.5.1}
在跳转至应用程序入口指令前，Bootloader 必须严格按顺序履行以下 6 项硬件合同：
1. **全局硬关闭中断**：在 ARM 上执行 `cpsid i`（设置 PRIMASK），在 RISC-V 上执行 `csrci mstatus, 8` 并清空 `mie`，防止移交过程被任何异步中断打断；
2. **彻底禁用并重置系统定时器**：清零 SysTick CTRL、LOAD、VAL 寄存器，消除正在倒计时的滴答时钟；
3. **彻底清除 NVIC/PLIC 中断使能与未决标志**：遍历全部使能寄存器写入 `ICER` 彻底关闭外设中断，向全部清除挂起寄存器 `ICPR` 写入 `0xFFFFFFFF` 彻底抹除由于硬件总线残留电平造成的未决中断；
4. **重新对齐并加载目标栈指针**：从应用程序二进制头部第 0 个字读取其预定义的合法初始栈顶地址（`_estack`），通过 `msr msp, r1` 写入主栈指针，丢弃 Bootloader 的全部栈空间；
5. **重定位硬件向量表基址**：
   - ARM Cortex-M3/M4/M7：向系统控制块向量表偏移寄存器 `SCB->VTOR` 写入目标向量表物理地址，并执行内存屏障 `DSB; ISB`；
   - RISC-V：将目标陷阱入口地址写入机器模式陷阱向量基址寄存器 `csrw mtvec, t0`，并执行指令同步屏障 `fence.i`；
6. **无栈调用尾部跳转（Tail Jump）**：从目标向量表偏移 4 字节处读取复位处理函数地址（Reset_Handler），通过纯汇编无栈调用指令（ARM 使用 `bx r2`，RISC-V 使用 `jr t0`）直接跳转，绝不经过 C 语言函数调用规约压栈！
:::

### 跨架构控制权移交规约横向对比

不同指令集架构在底层异常向量、特权级模型与流水线同步机制上存在显著微架构差异，系统程序员在移植 Bootloader 时必须严格遵循对应的体系结构规约：

| 架构族系 | 向量表基址重定位方式 | 栈指针切换机制 | 指令缓存 / 流水线同步屏障 | 中断现场清理要求 |
|:--|:--|:--|:--|:--|
| **ARM Cortex-M3/M4/M7** | 写入 `SCB->VTOR` 寄存器；要求按向量表总字数向上取幂对齐（最低 128 字节） | 写入主栈指针 `msr msp, r1`；必须重置 `CONTROL` 寄存器为 0（特权级线程模式） | `dsb sy`（等待总线完成）后紧跟 `isb sy`（冲刷预取流水线） | 执行 `cpsid i`；清空 SysTick；向 `NVIC->ICER` 与 `NVIC->ICPR` 写入全 1 |
| **ARM Cortex-M0/M0+** | **早期修订版无 VTOR 寄存器**！必须通过硬件重映射引脚或在 RAM 建立跳转桩（Trampoline） | 同样通过 `msr msp, r1` 切换栈顶 | `isb sy` 刷新指令预取 | 执行 `cpsid i`；逐个关闭 NVIC 中断并清除挂起 |
| **RISC-V (RV32I/RV64I)** | 写入机器模式异常向量寄存器 `csrw mtvec, t0`（最低 2 位编码 Direct 或 Vectored 模式） | 直接通过汇编指令修改通用寄存器 `mv sp, a1`；同时必须重新加载应用全局指针 `gp` | **必须执行 `fence rw, rw` 与 `fence.i`**（强制使指令缓存失效并重新预取） | 执行 `csrci mstatus, 8`（关闭 MIE）；写入 `csrw mie, zero` 清空全部中断使能 |
| **x86-64 (传统/UEFI)** | 重新加载中断描述符表寄存器 `lidt [new_idtr]`；段界限与线性基址重载 | 修改栈顶寄存器 `mov rsp, new_stack_top` | 执行长跳转 `jmp far` 或序列化指令 `cpuid` 冲刷乱序指令发射管线 | 执行 `cli`（清除 IF 标志）；重新编程 8259A PIC 或本地 APIC 屏蔽外部中断 |

### ARM Cortex-M 架构 handoff 汇编实现

在 `firmware/ch12/arm/handoff.S` 中，我们以高度精简、严密的 Thumb 汇编实现了这一绝对安全的移交合同：

```armasm
.syntax unified
.cpu cortex-m3
.thumb
.text
.global handoff
.type handoff,%function
.thumb_func
/* r0: 目标应用程序向量表基址 (已核验证 128 字节对齐)
 * r1: 目标应用程序合法栈顶地址 (已核验位于 SRAM 边界内) */
handoff:
    cpsid   i                   /* 1. 关全局中断，冻结异步事件 */

    /* 2. 彻底复位 SysTick 定时器 */
    ldr     r2, =0xe000e010
    movs    r3, #0
    str     r3, [r2]            /* SysTick CTRL = 0 */
    str     r3, [r2, #4]        /* SysTick LOAD = 0 */
    str     r3, [r2, #8]        /* SysTick VAL  = 0 */

    /* 3. 清除 PendSV 与 SysTick 挂起标志 */
    ldr     r2, =0xe000ed04
    ldr     r3, =0x0a000000     /* PENDSVCLR | PENDSTCLR */
    str     r3, [r2]

    /* 4. 彻底禁用全部外设中断并清空挂起 (ICER / ICPR) */
    ldr     r2, =0xe000e004     /* ICTR.INTLINESNUM */
    ldr     r2, [r2]
    and     r2, r2, #15
    adds    r2, r2, #1          /* 计算芯片实现的 32 通道中断组数 */
    ldr     r3, =0xe000e180     /* NVIC_ICER0 */
    ldr     r4, =0xe000e280     /* NVIC_ICPR0 */
    mvn     r5, #0              /* 全 1 掩码 0xFFFFFFFF */
1:  str     r5, [r3], #4        /* 禁用 32 个中断 */
    str     r5, [r4], #4        /* 清除 32 个未决标志 */
    subs    r2, r2, #1
    bne     1b

    /* 5. 清除 BASEPRI 与 FAULTMASK，防止优先级遗留屏蔽 */
    movs    r2, #0
    msr     basepri, r2
    msr     faultmask, r2

    /* 6. 重装载应用程序向量表 VTOR 并同步流水线 */
    ldr     r3, =0xe000ed08     /* SCB->VTOR */
    str     r0, [r3]
    dsb     sy
    isb     sy

    /* 7. 读取应用复位入口，重置 CONTROL 模式，加载新 MSP 并跳转 */
    ldr     r2, [r0, #4]        /* r2 = app_vector[1] (Reset_Handler) */
    movs    r3, #0
    msr     control, r3         /* 确保处于特权级线程模式并使用 MSP */
    isb     sy
    msr     msp, r1             /* 切换主栈指针至应用栈顶！ */
    bx      r2                  /* 绝对尾跳转！从此进入全新世界 */
```

### RISC-V 架构 handoff 汇编实现

在 RISC-V 架构下，移交规约同样严苛。除了重设栈指针外，还必须妥善处理全局指针寄存器（`gp`）与指令缓存一致性：

```riscv
.text
.global handoff
.type handoff,@function
/* a0: 目标应用程序入口地址
 * a1: 目标应用程序新栈顶地址 */
handoff:
    /* 1. 禁用机器模式全局中断与定时器中断 */
    csrci   mstatus, 8          /* 清除 mstatus.MIE */
    csrw    mie, zero           /* 清空全部中断使能位 */

    /* 2. 重置机器模式异常向量入口基址 */
    addi    t0, a0, 256         /* 应用约定在入口偏移 256 字节建立独立陷阱向量 */
    csrw    mtvec, t0

    /* 3. 内存序与指令缓存同步屏障 */
    fence   rw, rw              /* 确保此前的总线写操作全网可见 */
    fence.i                     /* 关键：使本地 CPU 指令预取流水线彻底失效！ */

    /* 4. 切换栈指针，清空参数寄存器，绝对跳转 */
    mv      t0, a0
    mv      sp, a1
    li      a0, 0
    li      a1, 0
    jr      t0                  /* 跳转至应用 _start */
```

## 12.6 嵌入式 Flash 控制器驱动与写时序 {#sec-edge.3.12.6}

### TI Stellaris LM3S6965 闪存控制器寄存器剖析

以本书实验环境深度使用的德州仪器 LM3S6965 微控制器为例，片上 256 KB Flash 的控制完全由位于基地址 `0x400FD000` 的闪存控制器硬件管理（参考官方手册第 7 章与第 22 章）：

| 寄存器名称 | 物理偏移 | 访问权限 | 复位默认值 | 核心功能与硬件语义 |
|:--|:--|:--|:--|:--|
| **FMA** (Flash Memory Address) | `0x000` | R/W | `0x00000000` | 擦写目标地址寄存器。编程时要求 **4 字节对齐**；页擦除时要求 **1 KB 页面对齐**。软件未按对齐要求写入将导致不可预知硬件异常。 |
| **FMD** (Flash Memory Data) | `0x004` | R/W | `0x00000000` | 待写入的数据寄存器。存放即将烧录至 Flash 的 32 位整型数据。 |
| **FMC** (Flash Memory Control) | `0x008` | R/W | `0x00000000` | 闪存操作控制寄存器。必须写入写入密钥 **`WRKEY = 0xA442`**，否则所有写操作被硬件完全忽略！ |
| **USECRL** (USec Reload) | `0x140` | R/W | 芯片最大主频 | 微秒重装载寄存器。写入当前系统主频减 1（例如 20 MHz 写入 19），控制器借此生成精确的擦写高压脉冲时序。 |
| **FMPREn / FMPPEn** | `0x130 / 0x134` | R/W | `0xFFFFFFFF` | 闪存块保护寄存器。每比特控制 2 KB 物理块的读、执行与编程擦除权限。出厂默认全开。 |

在 FMC 控制寄存器中，最低 4 个控制位承担着发起硬件操作的职责：
- **Bit 0 (`WRITE`)**：字写入启动位。硬件耗时最长 **50 微秒**；完成后由硬件自动清零。
- **Bit 1 (`ERASE`)**：1 KB 单页擦除位。硬件耗时最长 **25 毫秒**；完成后由硬件自动清零。
- **Bit 2 (`MERASE`)**：全片质量擦除位（Mass Erase）。硬件耗时最长 **250 毫秒**。
- **Bit 3 (`COMT`)**：非易失性配置提交位。将保护配置永久固化进非易失寄存器中。

### 闪存底层驱动 C 语言核心实现

在裸机环境下，直接操作底层寄存器完成 Flash 字编程与页擦除的驱动实现如下：

```c
#define FLASH_BASE       0x400FD000u
#define FLASH_FMA        (*(volatile uint32_t *)(FLASH_BASE + 0x000))
#define FLASH_FMD        (*(volatile uint32_t *)(FLASH_BASE + 0x004))
#define FLASH_FMC        (*(volatile uint32_t *)(FLASH_BASE + 0x008))
#define FMC_WRKEY        (0xA442u << 16)
#define FMC_WRITE        (1u << 0)
#define FMC_ERASE        (1u << 1)

/* 编程单个 32 位整型字：必须 4 字节对齐 */
int flash_program_word(uint32_t addr, uint32_t data) {
    if (addr & 3u) return -1; /* 地址未对齐 */
    FLASH_FMD = data;
    FLASH_FMA = addr;
    FLASH_FMC = FMC_WRKEY | FMC_WRITE;
    while (FLASH_FMC & FMC_WRITE) {
        /* 硬件忙等待，最长 50 微秒 */
    }
    return (*(volatile uint32_t *)addr == data) ? 0 : -2;
}

/* 擦除单个 1 KB 物理页面：必须 1024 字节对齐 */
int flash_erase_page(uint32_t page_addr) {
    if (page_addr & 1023u) return -1; /* 页面未对齐 */
    FLASH_FMA = page_addr;
    FLASH_FMC = FMC_WRKEY | FMC_ERASE;
    while (FLASH_FMC & FMC_ERASE) {
        /* 硬件忙等待，最长 25 毫秒 */
    }
    return 0;
}
```

### 嵌入式 Flash 上的 EEPROM 仿真与环形日志设计

在嵌入式系统中，除了固件本身，系统还必须高频记录参数（如传感器校准系数、运行时间、代际计数器等）。
若每次修改参数都对同一个 1 KB Flash 页面执行“擦除-写入”，在数万次擦写后该页面晶体管将发生电荷击穿永久损坏！
为了在粗粒度擦除的 Flash 上安全记录高频小数据，业界广泛采用**环形日志追加（Circular Append Log）**的 EEPROM 仿真机制：

```c
/* 扇区环形追加记录头 */
typedef struct {
    uint16_t record_id;   /* 参数 ID */
    uint16_t length;      /* 数据长度 */
    uint32_t sequence;    /* 写入序号 (单调递增) */
    uint32_t crc32;       /* 校验和 */
    /* 紧跟数据字节... */
} __attribute__((packed)) LogRecordHeader;
```

其核心运行准则包括：
1. **顺序追加（Sequential Append）**：每次保存新参数时，从不擦除当前扇区，而是从扇区空闲偏移（字节全为 `0xFF` 的位置）顺序向后追加写入新记录；
2. **最新有效检索（Active Snapshot Search）**：系统启动时，从前向后扫描扇区，对于相同 `record_id` 的记录，以 `sequence` 最大且 CRC 合法的最后一条记录作为当前有效值；
3. **扇区垃圾回收（Garbage Collection, GC）**：当当前扇区剩余空间不足以写入新记录时，将所有参数的最新有效值一次性提取至 RAM，将对偶备用扇区整页擦除，将有效参数紧凑转录至备用扇区，随后将旧扇区释放。
这种设计将物理擦写频率降低了数十至数百倍，完美化解了 Flash 擦写寿命短板。

### 闪存加速器与预取缓存一致性刷新规约

在主频超过 100 MHz 的现代高性能微控制器（如 STM32F4/F7/H7、GD32F4）上，片上 Flash 的物理读取速度（通常仅 20 MHz ~ 30 MHz）远低于 CPU 核心主频。
为了消除等待周期，芯片通常集成了**闪存预取缓冲器与自适应实时加速器（如 ST ART Accelerator / Flash Cache）**：
1. **指令与数据缓存命中机理**：
   加速器内部集成了 16 至 64 行的指令 Cache 与分支目标缓存，提前流水线预取后续的 Flash 指令行；
2. **固件重写入后的致命缓存假死**：
   当 Bootloader 将新应用程序烧录至 Slot 1 后，如果曾经读取过该物理区域的旧数据，加速器的内部 Cache 依然固化着旧代码片段！
   若此时直接通过 `bx` 跳转，CPU 将绕过物理 Flash，直接从预取 Cache 中命中并执行已经被擦除的幽灵旧指令，导致逻辑不可预测；
3. **固件写后强制失效规约**：
   在 Flash 写入或擦除完成后、跳转执行前，系统程序员必须显式向闪存访问控制寄存器（如 `FLASH_ACR`）写入控制位：
   置位 `ICRST`（指令缓存复位）与 `DCRST`（数据缓存复位）位，强制清空全部闪存硬件加速 Cache，然后再重新使能 `ICEN` 与 `DCEN`，确保每一条执行的指令均源自物理 Flash 介质的最新电荷状态！

### 闪存操作期间的 CPU 总线挂起冻结机制

在固件编程与擦除期间，系统程序员必须清醒认识到微架构总线层面的巨大连锁反应：
根据 LM3S6965 官方手册第 7.3.1 节明确规定：
**“During a Flash memory operation (write, page erase, or mass erase) access to the Flash memory is inhibited. As a result, instruction and literal fetches are held off until the Flash memory operation is complete.”**

这意味着：
当 CPU 向 FMC 写入指令发起 1 KB 页擦除时，片上 Flash 控制器会向 Cortex-M3 的 ICode 与 DCode 总线直接拉低等待就绪信号（HREADYOUT = 0）。
**CPU 整个流水线将被硬件强制挂起整整 20 毫秒至 25 毫秒！**
在这长达 20 毫秒的时间内，CPU 无法从 Flash 中抓取任何新的指令，也无法读取 Flash 中的常数池数据。
如果系统在此期间发生中断，或者需要高频喂狗，执行代码必须预先加载至片上 SRAM 中执行（通过链接脚本指定段定位至 RAM），否则系统将面临严重的实时性饥饿与看门狗复位风险！

## 12.7 试运行自检、看门狗联动与自动回滚 {#sec-edge.3.12.7}

### 试运行状态下的生死契约

在 Direct-XIP 架构中，系统引导候选固件进入试运行状态，绝不代表升级已经成功。
候选固件可能存在深层次逻辑死锁、由于编译器版本不兼容引发的 HardFault、或由于未正确初始化某路传感器导致的死循环。

为此，Bootloader 与应用程序之间必须订立基于硬件看门狗的**生死试运行合同**：

```text
[Bootloader: 准备启动 Candidate]
       │
       ▼ 步骤 1: 将 trial_used = 1 物理写入 Flash 元数据页 (落盘先行!)
[Flash Commit: trial_used=1]
       │
       ▼ 步骤 2: 移交控制权并启动硬件看门狗
[应用接管: Candidate 运行]
       │
       ├─────────────────────────────────┐
       ▼ 正常路径: 业务全面自检合格        ▼ 异常路径: 发生 HardFault / 死锁
[ota_confirm()]                          [硬件看门狗超时 / 系统硬件复位]
       │                                         │
       ▼                                         ▼
[Confirmed = 1, Candidate = NONE]        [Bootloader 重新接管]
[Floor 提升至新版本]                       [检查发现 trial_used=1 且未转正!]
[升级宣告圆满成功!]                       [判定为非法固件, 立即自动回滚 Slot 0!]
```

*关键审计要点*：
为什么必须在跳转前将 `trial_used = 1` 物理落盘？
如果 Bootloader 仅仅在 RAM 中记录该标记，一旦新固件启动后由于供电突降发生死机重启，Bootloader 重新上电后将把该次死机误判为“新上电”，从而再次错误地跳转进死机固件，导致设备陷入无限重启的“死循环砖机”状态！
**“先标记已试运行，再执行跳转”是防砖机设计的不二法则。**

### 应用程序综合自检矩阵（Pre-Commit Health Checks）

在应用程序调用 `ota_confirm()` 永久确认新版本之前，必须执行一系列确定性的自检流水线：

```c
/* 应用程序启动后必须通过的五重门禁自检 */
bool app_run_pre_commit_health_check(void) {
    /* 1. 核心 RAM 走查测试 (March C- 极简自检) */
    if (!diagnostics_check_sram()) return false;

    /* 2. 关键通信接口自测 (向 CAN 总线或 UART 发送心跳回环) */
    if (!diagnostics_check_bus_communication()) return false;

    /* 3. 物理传感器采样合理性检验 (排除短路或断线浮空) */
    if (!diagnostics_check_sensor_rails()) return false;

    /* 4. 边缘 AI 推理基准校验 (运行单次黄金测试样本，检验 INT8 权重与乘法器) */
    if (!diagnostics_check_tensor_inference_baseline()) return false;

    /* 5. 向看门狗主管任务注册首个合法心跳 */
    if (!wdt_task_checkin(TASK_MAIN_ID, 1)) return false;

    return true; /* 全部合格，允许提交转正！ */
}
```

### 定量工业失败案例：通信死锁引发看门狗秒级回滚实录

在某型轨道交通车载制动监测网关的固件升级实测中，曾发生一起极具教学意义的真实软件缺陷案例：
- **故障引入机理**：新固件（Slot 1）在优化 CAN FD 接收处理时，在中断服务例程（ISR）内部引入了一段无超时的轮询等待逻辑（`while (!(CAN_STATUS & TX_READY));`）；
- **故障触发工况**：新固件试运行启动后，恰逢总线受到强电磁干扰出现短暂突发错误帧，CAN 控制器进入被动错误状态，发送就绪标志永久无法置位，中断服务例程陷入无限死循环！
- **时间链定量推导**：
  1. $T = 0\,\text{ms}$：Bootloader 核验 Slot 1 镜像合法，将 `trial_used = 1` 物理烧录进 Flash 元数据，执行 `handoff` 跳转至 Slot 1；
  2. $T = 12\,\text{ms}$：Slot 1 应用程序完成 CRT0 内存重定位与外设使能，启动第 10 章所述的硬件独立看门狗，超时窗口锁定为 $T_{WDT} = 200\,\text{ms}$；
  3. $T = 45\,\text{ms}$：总线突发干扰，CAN ISR 触发并陷入死锁；主循环任务被完全阻断，无法执行 `WatchdogSupervisor` 的心跳打卡；
  4. $T = 245\,\text{ms}$：硬件看门狗计数器下溢归零，看门狗电路强行拉低芯片 RESET 引脚，触发系统硬件复位；
  5. $T = 248\,\text{ms}$：Bootloader 重新上电并初始化，读取 `SYSCTL_RESC` 寄存器发现复位原因标志 `WDT = 1`；
  6. $T = 250\,\text{ms}$：读取 Flash 元数据，发现状态为 $\langle G=12, C=0, K=1, T=1, F=1 \rangle$；
     由于 `trial_used == 1` 且该镜像从未获得 `ota_confirm()` 提交确认，**状态机精准判定当前候选镜像存在致命缺陷**！
  7. $T = 252\,\text{ms}$：Bootloader 执行回滚决策，将 $K$ 重置为 `OTA_NONE`，重新装载黄金镜像 Slot 0，在第 255 毫秒顺利恢复车载制动监控通信，从故障发生到完全自愈总耗时仅 **255 毫秒**，彻底避免了列车保护性紧急制动的恶性事故！

### 智能体（Agent）生成 OTA 代码的典型灾难案例

::: errata 智能体生成 Bootloader 硬件移交代码的致命缺陷 {#errata-edge.3.12.9.1}
在针对大语言模型辅助生成的嵌入式 Bootloader 进行静态安全审计时，经常发现以下具有高度隐蔽性、但在真机上必然引发崩溃的代码：

```c
/* 智能体生成的错误代码：貌似“工整”，实则致命！ */
void jump_to_application(uint32_t app_vector_addr) {
    uint32_t *app_vector = (uint32_t *)app_vector_addr;
    uint32_t app_sp = app_vector[0];
    void (*app_reset)(void) = (void (*)(void))app_vector[1];

    /* 致命缺陷 1: 忘记关闭 SysTick 和清空中断未决标志！ */
    /* 致命缺陷 2: 仅在 C 语言中修改 VTOR，但未执行 DSB/ISB 指令屏障！ */
    SCB->VTOR = app_vector_addr;

    /* 致命缺陷 3: 在 C 语言函数体中直接修改 SP 寄存器！ */
    __set_MSP(app_sp);

    /* 致命缺陷 4: 通过 C 语言指针调用 Reset_Handler！ */
    app_reset(); /* 编译器在此处会生成利用旧栈或新栈的压栈指令，造成栈指针严重撕裂！ */
}
```

**机理解析与灾难后果**：
1. **栈指针撕裂（Stack Corruption）**：在 C 语言函数体内执行 `__set_MSP(app_sp)` 改变了当前栈底。而编译器在编译 `app_reset()` 函数调用时，可能需要使用当前栈帧保存临时寄存器或准备参数。在新旧栈交替的瞬间，函数的局部变量访问与返回地址将彻底乱套；
2. **流水线预取竞争（Instruction Fetch Hazard）**：写入 `SCB->VTOR` 后未插入 `DSB` 与 `ISB` 指令。ARM Cortex-M 的预取流水线可能依然保留着旧向量表的地址，当随后的首条指令引发异常时，依然跳转至 Bootloader 的旧处理函数；
3. **正确修复方案**：正如 §12.5 与 `handoff.S` 所示，移交必须由**纯汇编函数接管**，在全局关中断、复位 SysTick、清空 NVIC、写入 VTOR 并插入内存屏障后，在纯寄存器中完成栈指针装载并直接执行尾部分支指令 `bx`，彻底杜绝 C 语言运行时的干预！
:::

## 12.10 本章陷阱 {#sec-edge.3.12.10}

1. **直接覆写正在运行的代码页引发 CPU 硬件死锁**：NOR Flash 在擦除时整页变为 `0xFF`，并向总线拉低就绪信号。若在 Flash 中运行的代码试图擦除自身所在页面，CPU 预取立刻读出非法指令，直接引发不可恢复的 HardFault 死机。
2. **Bootloader 移交前漏关 SysTick 导致应用启动崩溃**：Bootloader 运行期若启动了 SysTick 定时器，在跳转前必须将其 CTRL 寄存器清零。否则在应用程序刚刚进入 Reset_Handler、C 运行时堆栈尚未初始化完成的微秒内，旧的 SysTick 滴答中断突然触发，系统将因执行空指针向量而当场崩溃。
3. **未清空 NVIC/PLIC 挂起寄存器引发残留中断击穿**：Bootloader 执行期间外设产生的残留电平可能已经置位了 `ICPR` 挂起寄存器。移交前若未通过向 `ICPR` 写入全 1 彻底清除，应用程序一旦开启中断，将立刻响应属于 Bootloader 历史周期的未决伪中断。
4. **元数据原地擦写导致中途断电直接变砖**：若在单页内原地擦除并重新写入元数据，一旦电源在擦除完成至写入完成之间断开，Flash 页面呈现全 `0xFF`，系统重启后无法找到任何合法引导信息，双区直接失效。必须严格采用双页代际轮换与二阶段提交机制。
5. **试运行状态仅保存在 RAM 未在跳转前落盘**：若 Bootloader 仅在内存中标记候选镜像已被试运行，一旦候选固件引发电源瞬态拉低或看门狗复位，重启后 Bootloader 会将状态当作“全新启动”再次死循环引导坏镜像。必须在执行跳转前将 `trial_used = 1` 物理烧入 Flash。
6. **签名校验仅检查有效载荷而漏掉镜像头部**：若数字签名仅覆盖 Payload，攻击者可通过篡改 Header 中的加载基址、执行权限或版本号实施越权攻击。签名与摘要必须严格覆盖从 Header 到 Payload 的全部连续字节。
7. **升级完成未提升版本底线导致被降级重放**：若仅验证数字签名合法，攻击者可将数年前发布的、带有官方合法签名的旧漏洞固件重新烧录。必须在元数据中维护单调递增的 `Floor` 计数器，拒绝一切版本低于底线的固件。
8. **修改 VTOR 后缺少 DSB 与 ISB 内存屏障**：ARM Cortex-M 的流水线具备预取缓冲。向 `SCB->VTOR` 写入新基址后，必须紧跟 `DSB`（确保总线写入完成）与 `ISB`（刷新指令流水线），否则首批异常响应可能依然基于旧向量表。
9. **误将 CRC-32 校验当作安全认证**：CRC-32 是一种**检错码（Error Detection Code）**，仅能防御物理信道的高斯白噪声与比特翻转；攻击者只需毫秒级算力即可构造出具有完全相同 CRC-32 值的恶意固件。安全升级必须依赖基于密码学私钥的数字签名（ECDSA / Ed25519）。
10. **Flash 擦除时间长达 20ms 导致外部看门狗饿死**：在执行 Flash 块擦除时，CPU 总线被硬件挂起多达 25 毫秒。如果板级硬件看门狗的喂狗窗口小于 25 毫秒，且未在擦除前提前刷新或在 SRAM 中执行周期性喂狗，芯片将在擦除过程中被硬件看门狗强行复位。
11. **RISC-V 固件移交漏执行 fence.i 导致取指脏数据**：在支持指令缓存（I-Cache）的 RISC-V 核心上，向内存烧录新镜像后必须执行 `fence.i` 指令刷新指令缓存。否则 CPU 可能继续从 I-Cache 中取用旧固件的缓存指令行，导致执行流发生未知错乱。
12. **应用链接脚本 RAM 区域与 Bootloader 堆栈发生隐蔽重叠**：若 Bootloader 预留的运行栈区与应用程序链接脚本中的 `.bss` / `.data` 物理内存发生重叠，在移交后若有任何残留指针或调试函数访问 Bootloader 空间，将直接践踏应用程序的核心数据。
