上一章给出异常入口，当前问题是把一次异常返回的目的地换成另一条任务流。
这不是把 `current` 指针改掉就结束了。
新任务的 SP、寄存器、返回地址与执行模式必须构成一致的状态。
旧任务可能停在普通调用边界，也可能被时钟打断在任意指令之间。
这两种入口要求不同的保存集合。

本章固定四个接口：AAPCS32、AAPCS64、RISC-V ILP32、SysV AMD64。
不将 Microsoft x64 调用约定混入 SysV 的栈布局。
不把 Cortex-M 的硬件压栈行为推广到 Cortex-A。
不把 RV32 的 `sw/lw` 栈槽照搬到 RV64。

可执行范围也先固定。
ARM 实验是无 FPU 的 Cortex-M3 裸机抢占调度。
RISC-V 实验是 RV32IM 的协作式任务切换，不开放中断。
x86-64 与 AArch64 提供协作切换汇编，已纳入交叉汇编和反汇编检查，尚未运行。
所有固件都是教学实现，不具备功能安全认证，也不是可直接部署的 RTOS 产品。

## 4.1 先给切换接口立合同 {#sec-edge.1.4.1}

### 调用边界与中断边界

设任务 A 调用 `yield()`。
编译器知道这是一次普通的外部函数调用。
它不会假设 caller-saved 寄存器在调用后仍保留原值。
必要的临时值已经由编译器放到栈或 callee-saved 寄存器中。
协作式切换只需满足该调用约定。

设定时器在任务 A 的乘法后、加法前触发。
编译器不知道这里会插入一次函数调用。
乘法结果可能仍在任意临时寄存器里。
异步入口必须恢复被打断代码全部可观察的处理器状态。
其中一部分可由硬件压栈，另一部分必须由软件保存。

::: def 保存集合合同 {#def-edge.1.4.1.1}
保存集合取决于入口，不取决于函数名字。
协作式切换满足 ABI 的 callee-saved 合同即可。
异步抢占必须覆盖被打断代码仍可使用的状态，包括必要的异常返回状态。
若允许浮点、向量或不同特权模式，这些状态也必须计入合同。
:::

| 架构与入口 | 关键寄存器集合 | SP 边界 | 返回机制 | 本章验证级别 |
|:--|:--|:--|:--|:--|
| Cortex-M3 异常抢占 | 硬件 R0–R3、R12、LR、PC、xPSR；软件 R4–R11、EXC_RETURN | 公共调用边界 8 B | `bx lr` 触发异常返回 | QEMU 实际运行 |
| RV32 协作调用 | ra、s0–s11、sp | ILP32 标准 ABI 为 16 B | `ret` | QEMU 实际运行 |
| AArch64 协作调用 | x19–x29、x30、sp；本例禁止 FP/SIMD | 16 B | `ret` | 交叉汇编 |
| x86-64 SysV 协作调用 | rbx、rbp、r12–r15、rsp，返回地址在栈 | 调用前 16 B；入口余 8 B | `ret` | 交叉汇编 |

这里 x30 不是 AAPCS64 意义下的普通 callee-saved 寄存器。
但切换函数必须保留自己的返回地址。
因此它仍出现在协作上下文中。
这与声称“x30 是 callee-saved”是两件事。

### TCB 偏移不是跨系统定律

本例把保存的 SP 放在 TCB 首成员。
这样 ARM 汇编可用 `[r1]` 直接取出 SP。
这是本实现的布局约定，不是所有 RTOS 必须遵循的架构规范。
另一个实现完全可以用生成的偏移常量访问不同成员位置。

```c
#include <stddef.h>
#include <stdint.h>

typedef struct {
    uint32_t *sp;
    uint32_t id;
} Task;

_Static_assert(offsetof(Task, sp) == 0, "assembly offset");
```

这段定义对应 `firmware/ch04/arm/main.c`。
在 32 位目标上指针占 4 B。
不要把主机上 64 位指针的 `sizeof(Task)` 当作目标布局证据。
交叉编译时的 `_Static_assert` 才检查目标布局。

本例另分配两块 1024 B 栈。
任务栈以 `_Alignas(8)` 约束。
MSP 使用 RAM 顶部单独保留的 2048 B 空间。
链接器断言阻止 BSS 侵入该空间。

### 三种状态的不同所有者

| 字段或资源 | 写入者 | 不变量 | 破坏后的现象 |
|:--|:--|:--|:--|
| TCB.sp | 初始化器、切换汇编 | 指向完整的软件保存帧 | 恢复时读取错误 PC |
| current | 调度临界区 | 指向正在获得处理器的任务 | 数据计数记到另一任务 |
| ready bitmap | 就绪队列操作 | 某位为 1 当且仅当该队列非空 | 调度到空链表 |
| wait_lock | 阻塞与唤醒路径 | BLOCKED 任务仅在一个等待集合 | 重复唤醒或丢任务 |
| mutex.owner | 获取与释放路径 | 有锁必须有有效所有者 | 错误归还优先级 |
| task stack | 当前任务及异常保存 | 栈边界与保存帧格式一致 | 静默覆盖相邻对象 |

运行者在本章主机调度模型中仍保留在就绪队列里。
因此 READY 的含义包含“可运行，可能正运行”。
不能同时引入另一个“运行者必须摘链”的实现习惯。
每次改变表示方式，都要重写相应不变量。

### 内存预算

仅计算 ARM 两任务固件：

```text
两个任务栈       2 × 1024 B = 2048 B
初始基本硬件帧   每任务 32 B，已经包含于任务栈
初始软件保存帧   每任务 36 B，已经包含于任务栈
每任务初始占用   68 B
两任务 TCB       2 × 8 B = 16 B（32 位目标）
MSP 预留         2048 B（链接边界，不代表最大已用深度）
```

68 B 不是整项任务的完整栈预算。
它没有包含任意 C 调用链的局部变量和溢出槽。
也不包含任务被中断前已经使用的栈。
真正配置要同时分析调用路径与异常嵌套。

本节出口：先写入口、保存集合、对齐、返回指令四项合同。
不能明确这四项时，不应开始抄切换汇编。

## 4.2 Cortex-M：让 PendSV 恢复另一条任务流 {#sec-edge.1.4.2}

### 为什么使用最低优先级

本实验把 PendSV 配置为最低可编程优先级。
SysTick 较高，普通任务在线程模式执行。
SysTick 只记滴答并设置 PendSV pending。
真正切换在 PendSV 中完成。

<pre class="layout" id="fig-edge-ch04-pendsv">
任务 A 使用 PSP-A
   │ SysTick 触发
   ▼
硬件将 A 的基本帧保存到 PSP-A
   │ Handler 使用 MSP，SysTick 设置 PENDSVSET
   ▼
SysTick 返回路径发现 PendSV 可执行
   │ 可通过 tail-chaining 进入 PendSV
   ▼
PendSV：保存 A.R4–R11 和 A.EXC_RETURN
   │ TCB-A.sp = 完整帧指针
   │ current = TCB-B
   ▼
恢复 B.R4–R11 和 B.EXC_RETURN
   │ PSP = B 的硬件帧地址
   ▼
BX LR：异常返回单元恢复 B 的基本帧
   │
   ▼
任务 B 使用 PSP-B，从它自己的 PC 继续
</pre>
读图：必须更换的不只是 PSP，还包括决定如何解包 PSP 的 EXC_RETURN。
图中没有声称硬件转换恒定耗时若干纳秒。
流水线、存储器等待与中断屏蔽都会影响实际延迟。

### 寄存器表：本实验实际触及的位

| 地址或名称 | 字段 | 本例写入 | 注意事项 |
|:--|:--|:--|:--|
| ICSR `0xE000ED04` | PENDSVSET bit 28 | `1u << 28` | 用直接写，不读改写整个状态寄存器 |
| SHPR3 `0xE000ED20` | PendSV 优先级 byte 2 | `0xFF` | 低位未实现时被忽略 |
| SHPR3 `0xE000ED20` | SysTick 优先级 byte 3 | `0x80` | 比 PendSV 更高 |
| SysTick LOAD `0xE000E014` | RELOAD[23:0] | 4095 | 周期为 4096 个所选时钟节拍 |
| SysTick CTRL `0xE000E010` | ENABLE、TICKINT、CLKSOURCE | 7 | 不据此推导板级墙钟频率 |
| CONTROL | SPSEL bit 1 | 2 | 线程使用 PSP，仍保留特权 |
| PRIMASK | bit 0 | 保存后置 1，再恢复 | 不用无条件开中断替代恢复 |

NVIC 的优先级数值越小，抢占优先级通常越高。
表中的 `0xFF` 是寄存器编码，不是“逻辑优先级 255 必然实现”。
本例不用 BASEPRI，因为 Cortex-M3 整数实验只需短小的单核临界区。
更复杂内核可以选择 BASEPRI，但必须与 ISR API 许可范围一并定义。

### 完整的软件保存帧

本例由低地址到高地址排列：

```text
TCB.sp +  0 : R4
       +  4 : R5
       +  8 : R6
       + 12 : R7
       + 16 : R8
       + 20 : R9
       + 24 : R10
       + 28 : R11
       + 32 : EXC_RETURN
       + 36 : R0             ← 恢复软件帧后写入 PSP
       + 40 : R1
       + 44 : R2
       + 48 : R3
       + 52 : R12
       + 56 : 线程 LR
       + 60 : 线程 PC
       + 64 : xPSR
```

软件帧为 9 个字，36 B。
硬件基本帧为 8 个字，32 B。
初始线程 SP 为 8 B 对齐。
保存软件帧后的地址不必本身仍为 8 B 对齐，因为它不是 C 调用栈顶。
调用 C 调度器时使用的是独立的 MSP。
本例在 MSP 上保存两个字，保持 AAPCS32 的公共接口对齐。

实际切换核心如下。
完整入口、向量和测试任务在 `firmware/ch04/arm/start.S`。

```armasm
PendSV_Handler:
    mrs r3, primask
    cpsid i
    mrs r0, psp
    stmdb r0!, {r4-r11, lr}
    ldr r1, =current
    ldr r2, [r1]
    str r0, [r2]

    push {r3, lr}
    bl select_next
    pop {r3, lr}

    ldr r1, =current
    ldr r1, [r1]
    ldr r0, [r1]
    ldmia r0!, {r4-r11, lr}
    msr psp, r0
    msr primask, r3
    bx lr
```

关键证据不是看到 `stmdb` 就认为正确。
需要核对保存与恢复寄存器集合完全对应。
`bl select_next` 会修改 LR，所以进入 C 前还要保护 Handler 的返回链接。
恢复任务的软件帧后，LR 再次装入该任务的 EXC_RETURN。
最终 `bx lr` 用的是新任务的返回描述，不是旧任务的。

### 首次运行与普通恢复共用格式

从未运行过的任务也要伪造一个合法保存帧。
初始化器不能只放一个 entry 指针。
本例设置：

```text
线程 PC          = task_entry 的 Thumb 函数地址
线程 LR          = fault（任务意外返回时失败退出）
xPSR.T           = 1，即 bit 24
EXC_RETURN       = 0xFFFFFFFD
R0–R3、R12       = 0
R4–R11           = 0
```

SVC_Handler 首次取 current.sp。
先弹出软件帧，再装入 PSP。
设置 CONTROL.SPSEL 后执行 ISB。
随后使用 EXC_RETURN 从基本硬件帧进入任务。
这不是普通函数 `ret`。

::: ex 示例 4.2.1 · 基本帧与浮点扩展帧不能互换 {#ex-edge.1.4.2.1}
若任务 A 的 EXC_RETURN 为 `0xFFFFFFFD`，任务 B 为 `0xFFFFFFED`，二者 bit 4 不同。
切换到 B 后仍沿用 A 的 LR，将按错误格式解释 B 的栈。
本例选择没有 FPU 的 Cortex-M3，从根源上排除混合浮点帧。
若扩展到 Cortex-M4F，必须逐任务保存 EXC_RETURN，按它决定 S16–S31 软件保存，并验证硬件 S0–S15 懒压栈状态。
:::

懒浮点压栈不是“中断一用 FPU 就污染线程”。
正确启用自动状态保存时，首次浮点指令会触发延迟保存。
将 ASPEN 和 LSPEN 一起清零并不等于强制自动保存。
需要 eager 自动保存时，应理解 ASPEN=1、LSPEN=0 的配置语义。
本章不向 Cortex-M3 实验中加入未经运行的 FPU 初始化代码。

## 4.3 RISC-V：ret、mret 与 mscratch 的三条边界 {#sec-edge.1.4.3}

### 先运行一个不涉及陷入的切换

RV32 实验通过普通 C 函数调用进入 `rv_switch`。
没有时钟抢占，没有 PMP 降权，没有中断嵌套。
入口参数由 a0、a1 传入。
a0 是旧任务保存 SP 的槽位地址。
a1 是新任务已经保存的 SP。

| 名称或字段 | 作用 | 本例是否改变 | 若扩展到异步抢占 |
|:--|:--|:--|:--|
| sp / x2 | 当前线程栈顶 | 是 | 还须考虑中断栈策略 |
| ra / x1 | 普通调用返回地址 | 保存与恢复 | 不能替代 mepc |
| s0–s11 | ABI 非易失寄存器 | 全部保存与恢复 | 仍需保留 |
| a0–a7、t0–t6 | caller-saved | 由调用边界合同处理 | 必须额外保存 |
| mepc `0x341` | 陷入返回 PC | 否 | 逐嵌套层保存 |
| mstatus `0x300` | MIE、MPIE、MPP 等状态 | 否 | 保存并校验返回模式 |
| mscratch `0x340` | 机器模式软件暂存 CSR | 否 | 可参与栈交换协议 |

普通协作调用不能擅自执行 `csrsi mstatus, 8`。
调用者可能本来就在关闭中断的区域里。
无条件打开 MIE 会破坏外层合同。
因此本实验的 rv_switch 完全不修改中断使能。
调用者负责进入可切换点。

### 栈帧宽度

本例保存 13 个字：ra 与 12 个 s 寄存器。
实际预留 64 B，剩余 12 B 用作对齐填充。
恢复后 SP 增加 64 B。
创建新任务时也预留同样的 64 B。

```text
offset  0   ra
offset  4   s0
offset  8   s1
offset 12   s2
offset 16   s3
...
offset 48   s11
offset 52   padding
offset 56   padding
offset 60   padding
```

这里的省略号是排布说明，不是实验源码。
可执行的 `switch.S` 中列出了全部保存与恢复指令。
为避免读者误把布局当代码，完整关键序列如下：

```riscv
rv_switch:
    addi sp, sp, -64
    sw ra, 0(sp)
    sw s0, 4(sp)
    sw s1, 8(sp)
    sw s2, 12(sp)
    sw s3, 16(sp)
    sw s4, 20(sp)
    sw s5, 24(sp)
    sw s6, 28(sp)
    sw s7, 32(sp)
    sw s8, 36(sp)
    sw s9, 40(sp)
    sw s10, 44(sp)
    sw s11, 48(sp)
    sw sp, 0(a0)
    mv sp, a1
    lw ra, 0(sp)
    lw s0, 4(sp)
    lw s1, 8(sp)
    lw s2, 12(sp)
    lw s3, 16(sp)
    lw s4, 20(sp)
    lw s5, 24(sp)
    lw s6, 28(sp)
    lw s7, 32(sp)
    lw s8, 36(sp)
    lw s9, 40(sp)
    lw s10, 44(sp)
    lw s11, 48(sp)
    addi sp, sp, 64
    ret
```

迁移到 RV64 时，不能只把 `-march` 改为 rv64。
每个 XLEN 栈槽变成 8 B。
需要 `sd/ld`，指针数组和初始帧也要随之改变。
RV32 ILP32E 的寄存器数量、栈对齐又不同，本例不覆盖它。

### 为什么这不是中断上下文

`ret` 是 `jalr x0, 0(ra)` 的伪指令。
它只改变控制流，不自动恢复 MPP 或 MPIE。
`mret` 根据 mepc 与 mstatus 完成特权返回。
两者不能靠“都是返回”而混用。

在一个标准机器陷入入口，硬件只更新少量 CSR。
不会自动把 a0、t0、ra 压入 RAM。
如果随后调用 C 分发器，所有仍被原程序使用的 caller-saved 值都必须先保存。
只保存四个寄存器再 `call` C 的快速入口，不满足异步恢复合同。

### mscratch 交换协议的前提

`csrrw sp, mscratch, sp` 能原子交换两个寄存器值。
它不自动判断当前来自 U 模式还是 M 模式。
也不自动分配嵌套中断栈。

若初始 mscratch 放内核栈，首次从用户任务进入时可完成换栈。
但在交换后 mscratch 已变成用户 SP。
此时若再允许同一入口嵌套，第二次盲目交换就会切回用户栈。
“用了原子指令”并不能弥补协议缺失。

安全的扩展至少要定义：

1. 如何判定陷入前特权级。
2. 哪些路径换栈，哪些路径留在当前内核栈。
3. 嵌套层数如何限制。
4. mepc 与 mstatus 何时保存。
5. 保存完前是否允许重新打开中断。
6. 恢复前是否先关闭可嵌套中断。
7. 如何恢复任务自己的中断状态。
8. 异常返回遇到非法地址时走哪个故障路径。

本例保留简单的协作切换，避免用不完整的陷入桩伪装为抢占内核。
出口能力是解释这条边界，不是声称已完成多核 M/S/U 调度。

## 4.4 x86-64 与 AArch64：同一合同的另两种实现 {#sec-edge.1.4.4}

### SysV AMD64 的返回地址在栈上

一次普通 `call` 在栈上压入 8 B 返回地址。
若调用前 RSP 为 16 B 对齐，函数入口 RSP 模 16 等于 8。
本例协作切换再保存 6 个 64 位寄存器，共 48 B。
保存后的 RSP 模 16 仍等于 8。

```asm
x86_switch:
    pushq %rbp
    pushq %rbx
    pushq %r12
    pushq %r13
    pushq %r14
    pushq %r15
    movq %rsp, (%rdi)
    movq %rsi, %rsp
    popq %r15
    popq %r14
    popq %r13
    popq %r12
    popq %rbx
    popq %rbp
    ret
```

源码是 `firmware/ch04/x86_switch.S`。
第一个参数 RDI 指向旧 SP 槽。
第二个参数 RSI 是新 SP。
新栈内容必须按弹出次序准备。
把 ARM 的“PC 单独一个字段”习惯直接套到这里会错位。

```text
新 SP +  0 : r15
      +  8 : r14
      + 16 : r13
      + 24 : r12
      + 32 : rbx
      + 40 : rbp
      + 48 : trampoline 的返回入口
      + 56 : 任务意外返回的兜底地址（若从函数入口直接启动）
```

精确初始化还要满足 trampoline 自身的 ABI。
若直接从 `ret` 进入一个 C 入口，该入口看到的 SP 必须模 16 等于 8。
不能只把新 SP 对齐到 16 就结束。

### Red zone 与中断是另一个合同

SysV 用户态叶函数可使用 RSP 以下的 red zone。
异步内核中断若直接在该区域压栈，会破坏这类假设。
内核代码通常使用 `-mno-red-zone`，并选择正确的异常栈。

本章的 x86_switch 不是 IDT 门入口。
没有处理异常错误码、CPL 切换、IST、RFLAGS、SIMD 保存。
不能放入 IDT 后当作中断处理器运行。
也不适用于 Windows x64 的 shadow space 规则。

### AAPCS64 的栈必须 16 B 对齐

AArch64 协作切换保存 x19–x29 与 x30。
SP 通过通用寄存器暂存后写入旧槽。
不能直接写出不存在的通用 `str sp, [x0]` 形式。
本例预留 112 B，其中 96 B 保存 12 个 X 寄存器，16 B 为填充。

```armasm
a64_switch:
    sub sp, sp, #112
    stp x19, x20, [sp, #0]
    stp x21, x22, [sp, #16]
    stp x23, x24, [sp, #32]
    stp x25, x26, [sp, #48]
    stp x27, x28, [sp, #64]
    stp x29, x30, [sp, #80]
    mov x9, sp
    str x9, [x0]
    mov sp, x1
    ldp x19, x20, [sp, #0]
    ldp x21, x22, [sp, #16]
    ldp x23, x24, [sp, #32]
    ldp x25, x26, [sp, #48]
    ldp x27, x28, [sp, #64]
    ldp x29, x30, [sp, #80]
    add sp, sp, #112
    ret
```

源码是 `firmware/ch04/a64_switch.S`。
本例仅覆盖整数上下文。
若允许普通 AAPCS64 FP/SIMD 调用，还须满足 v8–v15 的 ABI 保存义务。
异步抢占需要考虑的集合比这更多，不能停在 v8–v15。
使用 SVE、SME、PAC、MTE 等特性时还要重新审计上下文协议。

### 交叉汇编检查什么

`run_firmware.sh` 会生成这两个目标文件与反汇编。
编译能发现指令不合法、寄存器宽度不符等问题。
它不能发现新任务栈是否正确初始化，也不能证明动态切换成功。
因此本书状态明确记为“已编译，未运行”。

读者可检查：

```bash
cd edge
bash experiments/ch04/run_firmware.sh
# 产物位于 .build/ch04/
# x86-disassembly.txt
# a64-disassembly.txt
```

审查 x86 中的 6 次 push 与 6 次 pop 是否对应。
审查 AArch64 中 112 B 的减栈与加栈是否对应。
审查第二参数是否在换栈后仍能安全读取。
最后一步必须是将来在该 ISA 上实际运行，不用编译成功代替它。

## 4.5 位图调度、同优先级队列与栈预算 {#sec-edge.1.4.5}

### O(1) 要说清楚是哪一步

32 个固定优先级可用一个 32 位位图。
优先级 0 为最高时，ctz 得到最高就绪优先级。
位图为 0 必须先返回 idle 或 NONE。
GCC/Clang 的 `__builtin_ctz(0)` 不是合法业务输入。

```c
static int select_ready(void) {
    if (!bitmap) return NONE;
    return heads[(unsigned)__builtin_ctz(bitmap)];
}
```

这个函数的抽象操作数不随就绪任务数量增长。
但并不意味着它在所有处理器上都是“单周期”。
Cortex-M3 的 ctz 可能由 RBIT 与 CLZ 组合实现。
不带 Zbb 的 RISC-V 可能使用其他指令序列或辅助实现。
x86 的延迟还取决于微架构与依赖链。
应看目标反汇编，再测实现的周期上界。

### 一个优先级不只有一个任务

旧式教学错误是用 `ready[p] = task` 保存唯一指针。
第二个同级任务入队会覆盖第一个。
删除一个任务时直接清空该槽，又会误删同级其他任务。
本例每级使用双向 FIFO。
TCB 内的 next、prev 使已知任务摘链为 O(1)。

```text
priority 2: head → T0 ⇄ T1 ⇄ T3 ← tail
priority 5: head → T2           ← tail
bitmap bit 2 = 1
bitmap bit 5 = 1
```

删除 T1 后，priority 2 仍非空。
因此只能在 head 变为 NONE 时清位图。
移交优先级时先从旧级摘链，再改 effective，再插入新级。
顺序不能颠倒。

### 可执行不变量

`experiments/ch04/rtos_context_sim.c` 每轮状态变更后检查：

1. 位图中的 1 与非空队列一一对应。
2. 每个 READY 任务恰好在一个队列中。
3. BLOCKED 任务不在任何就绪队列里。
4. 每个队列中任务的 effective 等于队列编号。
5. next、prev 与 head、tail 一致。
6. 有效优先级不比基础优先级更低。
7. wait_lock 是否存在与 BLOCKED 状态一致。

这些断言不证明所有并发交错。
模型假设所有 API 被单核调度临界区串行化。
它们能找到表示错误，但不能代替 IRQ 锁或原子协议。

### 时间片轮转

一个任务耗尽时间片后，可在同优先级队列中摘链再入尾。
高优先级就绪任务仍然优先。
时间片不会赋予低优先级跨级运行权。
若最高优先级任务永久不阻塞，低级任务可能永久饥饿。
这是策略结果，不能指望 round-robin 跨级修复。

本模型用一次显式 remove/enqueue 验证同级轮转。
ARM 固件的两任务演示采用简单交替选择。
不要把二者混为一个完整可配置内核。
本章将机制拆开，分别给出证据。

### 栈的三项测量

软件水印只能说明某段测试中哪些字节仍保留填充值。
它不能证明所有输入下栈不溢出。
局部数组未写过的区域可能仍保留水印。
大步移动 SP 也可能跳过一个很小的 MPU guard。

栈审计应结合：

```text
静态调用路径：调用帧大小、嵌套层级、库函数最大帧
动态水印：压力用例后的最低未覆盖位置
硬件边界：可用 MPU 区域或 ARMv8-M PSPLIM/MSPLIM
```

Cortex-M3 与 Cortex-M7 常见的是 PMSAv7 MPU。
不能把 ARMv8-M 的 RBAR/RLAR 区间寄存器搬过来。
ARMv8-M 的 AP=00 表示特权读写，不是所有模式都禁止访问。
不同 MPU 版本的重叠优先规则也不同。
这就是为何本例不提供一个“通用 MPU 栈保护函数”。

### IRQ 栈预算

MSP 需承载 Handler 自身调用帧和可允许的嵌套。
PSP 需承载线程调用帧与首次硬件压栈。
PSP 已严重溢出时，首次异常自动压栈本身仍可能失败。
双栈不是“用户栈无论怎么坏，异常总能安全运行”的证明。

对于两个任务栈，每个分配 1024 B，只能说明静态预留。
`run.sh` 没有输出“最大栈深度已证明 68 B”。
实际扩展业务前要重新测量。
禁止将教学任务的浅调用链预算用于复杂推理或 printf。

## 4.6 优先级继承：修复反转，不承诺消除死锁 {#sec-edge.1.4.6}

### 一个可计算的截止时间失败案例

设 H 基础优先级 2，M 为 10，L 为 20。
数字越小优先级越高。
L 已获得锁 K。
t=1 ms 时 H 就绪并请求 K，被阻塞。
此后 L 尚需 3 ms CPU 时间才能释放 K。
H 获得 K 后需 1 ms 才完成。
M 在此时就绪，需要连续 8 ms。
H 的绝对截止时间为 t=6 ms。

没有 PIP 时：

```text
t=1..9   M 运行 8 ms；L 被抢占；H 等锁
 t=9..12 L 运行剩余 3 ms，释放锁
 t=12..13 H 运行 1 ms，完成
结论：13 ms > 6 ms，截止时间失败
```

有 PIP 时：

```text
t=1      H 阻塞，L 继承有效优先级 2
 t=1..4  L 完成临界区，M 不能抢占 L
 t=4..5  H 获得锁后完成
结论：5 ms <= 6 ms，在此模型中满足截止时间
```

这是一组人工设定的离散时间模型参数。
不是火星探路者号的实际任务时序。
不是板上测得的 PIP 延迟。
测试打印会明确使用 `MODEL` 标签。

### effective 的来源不止一把锁

有效优先级应考虑所有持有锁上的等待者。
L 释放 K1 后，可能仍持有 K2。
如果 K2 还有一个优先级 5 的等待者，L 应恢复到 5，而不是直接回到基础 20。
简单地在每把锁中记录一个 original_priority，无法普遍处理此情形。

传递式继承还会沿等待链传播。
若 H 等待 M 持有的 K1，M 又等待 L 持有的 K0，L 也必须继承 H。
仅提升直接 owner 会留下链尾反转。
本模型用固定点重算 effective 来表达这条规则。

```text
effective(T) = min(
    base(T),
    所有等待 T 所持互斥锁的任务的 effective
)
```

由于任务数量固定为 4，可迭代传播至多 NT 轮。
这是清楚可检查的教学算法。
不是高并发商用内核应采用的最高效实现。
不要因 select_ready 是 O(1)，就把优先级重算也写成 O(1)。

### 阻塞必须真正摘链

获取已有 owner 的锁时：

```text
1. 验证不会创建等待环
2. 从旧 effective 的就绪队列摘除当前任务
3. 将状态置为 BLOCKED
4. 设置 wait_lock
5. 重算并传播继承优先级
6. 迁移发生优先级改变的 READY 所有者
7. 再选择下一任务
```

若只改 state=BLOCKED，却留在位图队列，调度器仍可能选到它。
若只提 owner 的字段，却没迁移队列，位图查到的仍是旧级。
这两类错误都能被本章的表示断言发现。

### 解锁与直接移交

释放者必须等于 owner。
不允许任意任务解锁，也不允许 ISR 冒充一个没有 TCB 的所有者。
若有等待者，模型选有效优先级最高者。
同级等待者在当前小模型中按任务编号决胜，不声称严格 FIFO。

锁先直接移交给选中的等待者。
然后清除该任务 wait_lock，置 READY 并入队。
最后重算全部继承。
这样没有“锁先变空，再被后来者偷走”的窗口。
若业务要求同级等待严格 FIFO，应额外维护等待队列。

### PIP 不解决什么

PIP 不消除持锁者自身的长临界区。
不消除持锁者等待磁盘或硬件响应的时间。
也不自动消除 A→B 与 B→A 的锁环。
本模型显式检查等待链，在新增环前返回错误。
生产系统还可使用锁排序、优先级天花板与有界超时。
它们各有额外条件，不能全部统称为“加了 PIP 就不会死锁”。

### 响应时间分析

固定优先级单核抢占任务可用经典迭代式估算：

$$R_i = C_i + B_i + \sum_{j\in hp(i)}\left\lceil\frac{R_i}{T_j}\right\rceil C_j.$$

这里 C 是选定硬件与输入范围下的执行时间上界。
B 是协议和资源图给出的阻塞上界。
高优先级干扰集合 hp(i) 不能漏掉硬件 ISR。
若有释放抖动、非抢占区、总线干扰，还需扩展模型。

PIP 的作用之一是限制不相关中优先级任务造成的间接阻塞。
它不能自动为所有 C、B、T 提供数值。
测试通过也不能把观测到的最大耗时改名为已证明 WCET。
本节的 13 ms/5 ms 仅验证反转机制。

## 4.7 IPC：从 acquire/release 到中断 API 许可范围 {#sec-edge.1.4.7}

### 单生产者单消费者的两个方向

SPSC 的生产者独占 head，消费者独占 tail。
消费者读取生产者发布的 head 之前，必须建立数据可见性顺序。
生产者复用消费者释放的槽位之前，也必须建立反向顺序。
只在 push 中插入一个写屏障，不是完整 C 并发协议。

本例使用 C11 `_Atomic unsigned`。
对自己的索引使用 relaxed load。
对另一侧发布的索引使用 acquire load。
更新对外可见的索引用 release store。

```c
static bool push(Packet value) {
    unsigned h = atomic_load_explicit(&q.head, memory_order_relaxed);
    unsigned next = (h + 1u) & (CAP - 1u);
    if (next == atomic_load_explicit(&q.tail, memory_order_acquire))
        return false;
    q.data[h] = value;
    atomic_store_explicit(&q.head, next, memory_order_release);
    return true;
}

static bool pop(Packet *value) {
    unsigned t = atomic_load_explicit(&q.tail, memory_order_relaxed);
    if (t == atomic_load_explicit(&q.head, memory_order_acquire))
        return false;
    *value = q.data[t];
    atomic_store_explicit(&q.tail, (t + 1u) & (CAP - 1u), memory_order_release);
    return true;
}
```

完整定义与 pthread 测试在 `experiments/ch04/spsc.c`。
容量为 64，采用空一格判满，所以有效容量是 63。
测试先填满，再检查一次额外 push 失败。
随后读空，再检查 pop 失败。
最后两线程传送 200000 个带序号与反码的数据包。

### 语言模型不等于 CPU 强弱内存序

x86 的 TSO 不会让普通共享变量的 C 数据竞争自动合法。
编译器仍可以基于语言规则优化未定义行为。
`volatile` 对 MMIO 有用途，但不能替代共享线程索引上的原子同步。
本例让编译器依据目标 ISA 选择适当指令，而不是手写一个平台宏就宣称跨架构安全。

C11 acquire/release 只针对规定的内存对象协议。
不保证 DMA 已完成写入。
不使非一致性 D-Cache 自动失效。
也不代替写设备门铃前的 MMIO 屏障与平台 Cache 维护。
这条边界将在 DMA 章继续使用。

### 为什么要检查 lock-free

某些原子宽度会被编译为库函数或内部锁。
ISR 中调用它可能引入不可接受的重入或阻塞风险。
本章主机测试调用 `atomic_is_lock_free` 检查索引类型。
目标固件移植时还应检查生成的反汇编与链接依赖。
主机的 lock-free 结果不是另一块 MCU 的保证。

### 信号量、互斥锁和通知

| 机制 | 是否有 owner | 事件累计 | 谁能阻塞 | 栈与调度风险 |
|:--|:--|:--|:--|:--|
| mutex | 有 | 不是计数事件 | 普通任务 | 需定义 PIP、锁顺序、等待链 |
| binary semaphore | 无 | 最多保留一个可用状态 | 普通任务 | 多次事件可能合并 |
| counting semaphore | 无 | 有界计数 | 普通任务 | 需处理计数溢出 |
| SPSC queue | 槽位所有权协议 | 保留多个有效载荷 | 本例 API 不阻塞 | 满时由上层丢弃或重试 |
| event flags | 位集合 | 同一位重复置位会合并 | 普通任务 | 需定义 AND/OR 与清除规则 |

事件标志组不是天然单指令的完整唤醒机制。
位判定可以很短，但等待者遍历和就绪队列变更仍有成本。
必须明确最大等待者数量。
不要在持有调度临界区时执行无界数量的回调。

### ISR API 的具体合同

一个 ISR-safe 发送接口至少应满足：

1. 不调用任务级阻塞。
2. 不动态分配不可预测的堆对象。
3. 满队列时立即返回状态。
4. 仅在许可的中断优先级范围调用内核。
5. 用明确方式请求稍后的上下文切换。
6. 临界区时间具有可审计的界限。
7. 参数缓冲区在消费前不会失效。
8. 发生错误时有计数，不静默吞掉。

硬实时最高优先级中断可能被规定禁止调用内核。
它可先写入独占数据结构，再由较低优先级服务转发。
“所有 ISR 都可调用 FromISR”不是普遍规范。
需要查所选内核的端口配置。

## 4.8 四项实验、故障注入与复现出口 {#sec-edge.1.4.8}

### 环境与入口

本轮记录环境为 Darwin arm64 主机。
交叉编译器使用 Homebrew LLVM Clang 22.1.8。
链接器为 LLD 22.1.8。
模拟器为 QEMU 11.1.2。
完整版本输出由脚本保存到 `.build/ch04/versions.txt`。

```bash
cd edge
bash experiments/ch04/run.sh
```

脚本不会在找不到 QEMU 时退化成常量模拟并打印 PASS。
缺依赖、编译失败、模拟器超时均使命令失败。
每个 QEMU 子进程设 20 s 主机超时。
这个超时是防止测试挂死，不是任务实时性指标。

### 实验 A：主机调度状态机

编译启用 C11、`-O2`、`-Wall -Wextra -Werror`。
调度模型额外开启 AddressSanitizer 与 UndefinedBehaviorSanitizer。
同优先级 FIFO 测试检查摘除一个任务不会抹掉另一个任务。
PIP 测试检查被阻塞的 H 不可调度。
传递式继承测试检查 H→M→L 传播。
多锁测试检查释放第一把锁后仍保留第二把锁的捐赠。

实际关键输出：

```text
PASS same-priority FIFO: removing one task retains its peer
PASS priority inheritance: blocked waiter, owner boost, direct handover
PASS transitive donation, cycle rejection, remaining-lock donation
MODEL deadline: no-PIP finish=13ms MISS; PIP finish=5ms MEET (not hardware timing)
PASS scheduler invariants (single-core serialized teaching model)
```

此实验没运行真实线程切栈。
它验证调度数据结构与资源协议。
不能将 sanitizer 未报错当作任意并发正确性的证明。

### 实验 B：C11 并发 SPSC

两个 pthread 分别承担唯一生产者和唯一消费者。
每个包包含 sequence 与 inverse。
消费者断言精确的接收序号及反码。
输出如下：

```text
PASS C11 SPSC: 200000 ordered packets, full/empty/wrap tests
```

该输出是功能与压力测试，不是吞吐量基准。
没有给出每秒包数，因为没有按受控环境进行统计性能测量。
扩展成 MPSC 时必须重写槽位竞争协议。
不能通过让两个生产者一起调用 push 就获得多生产者队列。

### 实验 C：Cortex-M3 实际抢占

靶机为 QEMU `lm3s6965evb`。
向量表从地址 0 开始，RAM 从 `0x20000000` 开始。
启动汇编执行 data 搬移与 BSS 清零。
SVC 首次启动 PSP 任务。
SysTick 每 4096 个内核时钟节拍触发。

两个任务在汇编中各自给 R4 设不同的哨兵值。
R5–R11 也设定可检查的值。
每次调用 C task_step 后返回汇编核对寄存器。
C 函数本身要满足 AAPCS32，切换路径也要满足异常恢复合同。
任务内的忙循环提供异步 SysTick 抢占机会。
显式设置 PENDSVSET 另外验证主动让渡路径。

只有双方进度达到阈值、滴答次数至少 16、切换次数至少 256 才退出成功。
故障入口使用 semihosting 返回非零退出码。

```text
ARM PASS: integer registers, PSP, SysTick preemption
```

这个实验确实执行了 Cortex-M 指令和硬件异常模型。
它没有执行实体开发板的 Flash 总线或引脚电平。
因此没有板级 100 ns、0 jitter 一类结论。
把 QEMU 执行时间作为硅片中断延迟是错误的。

### 实验 D：RV32 实际协作切换

靶机为 QEMU `virt`，参数使用 `-bios none`。
程序从 `0x80000000` 运行。
UART0 MMIO 用于文本输出。
SiFive test finisher MMIO 用于给宿主返回成功或失败。

两个任务使用不同 s0 哨兵值。
s1–s11 也经过切换后检查。
两个栈顶严格 16 B 对齐。
每次普通函数调用在自己的栈中停住，再从相同调用点恢复。
运行超过 512 次切换后退出。

```text
RV32 PASS: cooperative ABI, 12 saved registers, 512 switches
```

该实验没有使能定时器或 PLIC。
不能将它的成功输出改写为“RV32 抢占内核通过”。
若未来加入机器定时器抢占，应另设 full trap-frame 实验。

### agent 错误案例：继承优先级但仍调度阻塞者

一个生成器可能把锁竞争实现成两行：

```text
owner.current_priority = waiter.current_priority
waiter.state = BLOCKED
```

这看起来写出了 PIP 的定义。
但它没有摘除 waiter，也没有迁移 owner 的就绪队列。
调度器仍在原来的位图中查找。
结果是 H 被标记为 BLOCKED，却继续被选为最高任务。
或者 M 抢占了仍留在低级队列的 L。

本例用不变量与下一任务断言同时拦截此错误。
当锁移交给等待者时，还必须同步清除 wait_lock。
这是表示与协议一致性问题，不靠再增加一个 DMB 就能修复。

另一个生成器错误是对两个任务使用相同的寄存器哨兵。
如果两个任务 R4 恰好都为 `0x44`，漏保存 R4 也可能不被发现。
本例让 R4/s0 随任务编号变化。
故障注入可验证检查器确实观察到寄存器串扰。

## 4.10 本章陷阱 {#sec-edge.1.4.10}

::: errata 本章陷阱

1. **恢复新 PSP 却沿用旧 EXC_RETURN**：现象是浮点任务切换后栈解析错位。原因是返回格式属于任务状态。修复是把 LR 中的 EXC_RETURN 纳入各任务软件保存帧，并用混合帧测试。
2. **R4–R11 被称为 caller-saved**：会误导异步入口只保存临时寄存器。它们通常属于 AAPCS32 非易失集合；硬件保存集合与 ABI 集合要分别列出，再检查并集。
3. **RV32 代码只改编译参数就支持 RV64**：指针被截断，栈槽宽度不符。修复需同时改变 ld/sd、XLEN 槽位、初始帧和静态断言。
4. **把协作式 ret 换成 mret**：没有设置 mepc/MPP 的上下文无法安全特权返回。修复是明确调用入口与陷入入口，分别设计保存帧。
5. **阻塞者只改 state 不摘链**：调度器再次选到 BLOCKED 任务。修复是把状态、等待链、就绪队列作为一次受保护的状态转换，并执行不变量检查。
6. **一个优先级只放一个任务指针**：同级第二任务覆盖第一任务。修复为每级队列，只有最后一个任务摘除后才清位图。
7. **释放一把锁就恢复基础优先级**：仍等待另一把锁的高优先级任务遭遇反转。修复是根据剩余所有捐赠重新计算有效优先级，并测试多锁持有。
8. **ctz(0) 被当作 idle 优先级**：结果不具有所需的语言保证。修复是先检查 bitmap 为零，并为 idle/NONE 写单独分支。
9. **volatile 索引加一条屏障就称为 C 无锁队列**：普通共享访问仍可能数据竞争，反向槽位释放也可能未同步。修复是 C11 原子双向 acquire/release 协议，且限定唯一生产者/消费者。
10. **中断里等待被当前中断打断的持锁任务**：ISR 自旋永不结束。修复为非阻塞 ISR 协议，或严格 IRQ-save 自旋锁并审计最大等待时间；SMP 中关本核中断不等于全局互斥。
11. **把 QEMU 运行的宿主耗时写为中断纳秒延迟**：模型没有再现板级总线。修复是只报告功能结果，硬件性能另给板卡、频率、仪器、次数与原始波形。
12. **把 S0–S15 懒压栈理解为不保存**：会给出关闭 ASPEN 的危险建议。修复是区分自动保存与延迟保存状态机；本章整数实验不启用未经验证的 FPU 路径。

:::

不能原样复用。
异步被打断代码的 a0–a7 与 t0–t6 可能仍保存活跃值，必须保护。
