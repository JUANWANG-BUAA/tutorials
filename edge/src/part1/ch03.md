在实时嵌入式系统的微观世界中，**中断系统是连接连续物理世界与离散数字计算的唯一物理纽带**。无论是雷达回波捕获、电机电流零点穿越检测，还是紧急碰撞传感器的触发，所有不可预测的外部物理事件，最终均通过电平跳变转化为中断控制器引脚上的电气信号。

然而，中断亦是破坏程序执行确定性最大的双刃剑。若中断控制器仲裁机制配置不当，低优先级外设可能引发灾难性的“中断风暴”（Interrupt Storm），将主循环与高优先级控制任务彻底饿死；若中断服务程序未遵循严格的重入规则与 ABI 约定，临界区变量被撕裂、浮点寄存器被意外篡改、栈指针非对齐引发的系统崩溃将频繁且无规律地上演。

不同的计算体系结构在中断控制器的微架构设计上走出了截然不同的道路：x86 依赖复杂的 Local APIC 与中断描述符表（IDT），具备强大的核间调度与向量分发能力；ARM Cortex-M 创造了行业事实标准的**嵌套向量中断控制器**（NVIC, Nested Vectored Interrupt Controller），通过硬件状态机深度介入压栈与咬尾，将中断延迟压榨至令人惊叹的 12 个时钟周期；而 RISC-V 采用了模块化正交设计，将核心私有的局部中断器（CLINT）与系统级平台中断控制器（PLIC）解耦，赋予芯片设计者极致的灵活性。

本章将直击三大架构中断系统的微架构核心：从中断控制器的物理寄存器拓扑、抢占优先级分组与硬件咬尾时序，到硬件滴答定时器（SysTick/MTIME）的精确微秒级非阻塞设计，再到中断服务例程中的浮点保护与不可重入陷阱，为构建零抖动、高鲁棒性的边缘系统提供全方位的底层支撑。

## 3.1 中断控制器架构微架构对比：ARM NVIC vs RISC-V PLIC/CLINT vs x86 Local APIC {#sec-edge.1.3.1}

中断控制器的本质是一个高并发、多输入、带优先级的**硬件仲裁与分发状态机**。它负责在同一时刻到达的数十个硬件中断请求中，快速裁决出最高优先级请求，并将其翻译为 CPU 内核可以执行的物理跳转向量。

| [ARM Cortex-M: NVIC 紧密集成微架构]                                                                |

+----------------------------------------------------------------------------------------------------+
| [RISC-V: 分层解耦架构 (CLINT + PLIC)]                                                             |

+----------------------------------------------------------------------------------------------------+

|  外部外设中断 ===&gt; [I/O APIC] === APIC 总线/MSI ===&gt; [Local APIC] ===&gt; CPU 中断引脚 (查 IDT 门)    |
+----------------------------------------------------------------------------------------------------+
</pre>
读图：ARM NVIC 将中断控制器深度内嵌于 CPU 核心流水线中，硬件自动执行现场保存，追求极致低时延；RISC-V 采用清晰解耦的分层设计，CLINT 负责单周期机器时钟，PLIC 负责外部设备的多路仲裁与网状路由；而 x86_64 采用面向多核服务器的分布式 APIC 架构，依赖 MSI/MSI-X 消息中断与内存映射寄存器。

### 1. x86_64 分布式 APIC 与中断门分发
在 x86_64 体系中，中断管理由两个核心硬件部件协同承担：
- **I/O APIC**：位于主板芯片组中，负责接收来自外部板载硬件外设（PCIe 设备、定时器、串口）的中断管脚信号，并将其格式化为通过系统总线分发的中断消息包（MSI/MSI-X）。
- **Local APIC (本地高级可编程中断控制器)**：直接集成在每个 CPU 物理核心内部。其寄存器组被映射在物理地址 `0xFEE0_0000`（通过 MSR `IA32_APIC_BASE` 可重定位）。
当 Local APIC 收到中断请求后，它根据内部的**任务优先级寄存器**（TPR, Task Priority Register）进行硬件阈值过滤。若优先级允许，CPU 通过访问中断描述符表（IDT, Interrupt Descriptor Table）检索 16 字节的中断门描述符（Interrupt Gate Descriptor），硬件自动将调用者的 `%ss`、`%rsp`、`%rflags`、`%cs`、`%rip` 压入当前特权级或 IST（Interrupt Stack Table）指定的物理堆栈中，随后跳转至目标线性地址执行。中断处理完毕后，软件必须显式向 Local APIC 的 EOI 寄存器（`0xFEE0_00B0`）写入 0，通知硬件当前中断已完成。

### 2. ARM Cortex-M NVIC 紧密耦合架构
ARM Cortex-M 针对实时控制设计了深度的硬软件协同机制。NVIC 不仅仅是一个外挂外设，而是直接与 CPU 执行流水线、总线矩阵及寄存器文件紧密焊死在一起：
- NVIC 挂载在私有外设总线（PPB）上，能够以零等待状态直接与 CPU 交换仲裁决策。
- 当中断发生时，内核总线接口自动启动**双字自动压栈流水线**，并行读取中断向量表；
- NVIC 支持中断咬尾（Tail-Chaining）、迟到中断（Late-Arriving）与到达弹出（Pop-Preemption）三大硬件级微架构优化，彻底消除了软件手工保存现场的耗时。

### 3. RISC-V 模块化解耦架构 (CLINT + PLIC + AIA)
RISC-V 架构严格区分局部事件与全局事件：
- **CLINT (Core-Local Interruptor)**：处理极其紧急的核心内部局部时钟与软件中断，直接置位 CPU 的 `mip` 寄存器对应位，完全绕过全局外设仲裁器。
- **PLIC (Platform-Level Interrupt Controller)**：汇聚板上多达 1023 个外部设备中断。每个中断拥有独立的 3 位优先级（0~7，0 代表禁用），CPU 核心通过 MMIO 访问读取 Claim 寄存器原子获取中断编号，处理完毕后再写回同一寄存器完成硬件握手。
- **AIA (Advanced Interrupt Architecture)**：新一代 RISC-V 规范引入了 IMSIC（直接支持消息信号中断）与 APLIC，进一步向高吞吐低延迟的多核系统逼近。

下表系统对比三大体系在中断微架构层面的关键指标：

| 评估维度 | ARM Cortex-M (NVIC) | RISC-V (PLIC + CLINT) | x86_64 (Local APIC) |
|:--|:--|:--|:--|
| **控制器物理集成度** | CPU 内核紧密集成（私有外设总线 PPB） | SoC 级外设总线挂载（Memory-Mapped） | CPU 核心私有集成（Local APIC 位于 `0xFEE00000`） |
| **中断向量处理方式** | **硬件全向量化**（硬件直达专属 ISR） | 统一异常入口（直连）或有限向量（Vectored） | 基于 IDT 描述符表的硬件向量跳转 |
| **上下文保存方式** | **硬件自动并行压栈** 8 个核心寄存器 | **纯软件手工压栈**（通用寄存器） | 硬件自动压栈返回地址与特权栈（SS/RSP/RFLAGS/CS/RIP） |
| **典型中断响应延迟** | **恒定 12 周期** ($\approx 70\,\text{ns}$) | $16 \sim 35$ 周期（含软件压栈与 Claim 读取） | 约 $100 \sim 300$ 周期（含特权检查与门跳转） |
| **咬尾中断硬件优化** | **支持**（消除 75% 出入栈周期） | 依赖软件多重循环处理挂起位 | 不支持（依赖操作系统内核驱动循环） |
| **抢占优先级分级** | 硬件支持抢占优先级与子优先级分组 | 仅支持全局单维优先级（0~7）与阈值过滤 | 支持 16 级优先级类（TPR/PPR 寄存器） |

### 4. x86_64 Local APIC 定时器与 EOI 握手实战实现
在 x86 裸机与实时内核开发中，Local APIC 位于物理地址 `0xFEE0_0000`。以下为初始化 APIC 定时器与中断完成（EOI）的标准实现：

```c
/* x86 Local APIC 寄存器物理内存映射偏移 */
#define APIC_BASE_VADDR         ((volatile uint32_t*)0xFEE00000UL)
#define APIC_REG_ID             (0x0020 / 4)
#define APIC_REG_EOI            (0x00B0 / 4)
#define APIC_REG_SVR            (0x00F0 / 4) /* 伪中断向量寄存器 */
#define APIC_REG_TIMER_LVT      (0x0320 / 4) /* 定时器局部向量表 */
#define APIC_REG_TIMER_INITCNT  (0x0380 / 4) /* 初始计数值 */
#define APIC_REG_TIMER_CURRCNT  (0x0390 / 4) /* 当前计数值 */
#define APIC_REG_TIMER_DIV      (0x03E0 / 4) /* 分频配置 */

void x86_local_apic_init(void) {
    /* 1. 使能 APIC 并设置伪中断向量号 (Spurious Vector 设为 0xFF, 使能位 Bit 8 置 1) */
    APIC_BASE_VADDR[APIC_REG_SVR] = 0x1FF;

    /* 2. 配置定时器分频比: 设置为 16 分频 */
    APIC_BASE_VADDR[APIC_REG_TIMER_DIV] = 0x03;

    /* 3. 配置定时器为周期触发模式 (Periodic Mode: Bit 17=1), 中断向量号设为 32 */
    APIC_BASE_VADDR[APIC_REG_TIMER_LVT] = (1U << 17) | 32;

    /* 4. 设定定时器重装载计数值 (启动定时器) */
    APIC_BASE_VADDR[APIC_REG_TIMER_INITCNT] = 1000000UL;
}

/* x86 中断服务程序必须执行的硬件完成确认 (EOI) */
void x86_apic_send_eoi(void) {
    /* 写入 0 通知 Local APIC 清除当前正在服务的中断位 (In-Service Register, ISR) */
    APIC_BASE_VADDR[APIC_REG_EOI] = 0U;
}
```

### 5. x86_64 中断描述符表 (IDT) 门描述符与 LIDT 汇编实现
在 64 位长模式下，IDT 包含 256 个条目，每个条目扩展为 **16 字节**（128 位），以容纳完整的 64 位虚拟入口地址：

```c
/* x86_64 16 字节中断门描述符结构体 */
typedef struct __attribute__((packed)) {
    uint16_t offset_low;      /* 目标代码段内偏移 [15:0] */
    uint16_t selector;        /* 目标代码段选择子 (内核代码段如 0x08) */
    uint8_t  ist;             /* 中断栈表索引 (Bits 2..0, 0=不使用IST, 1~7=使用对应IST栈) */
    uint8_t  type_attr;       /* 门属性: P(1位), DPL(2位), 0, Type(4位, 0xE为64位中断门) */
    uint16_t offset_mid;      /* 目标代码段内偏移 [31:16] */
    uint32_t offset_high;     /* 目标代码段内偏移 [63:32] */
    uint32_t zero;            /* 硬件保留字段，必须清零 */
} IdtEntry64;

typedef struct __attribute__((packed)) {
    uint16_t limit;           /* IDT 字节长度减 1 (通常 256 * 16 - 1 = 4095) */
    uint64_t base;            /* IDT 首个条目的 64 位线性基地址 */
} Idtr64;

static IdtEntry64 g_idt[256];

void x86_set_idt_gate(uint8_t vector, void* handler, uint8_t ist, uint8_t dpl) {
    uint64_t addr = (uint64_t)handler;
    g_idt[vector].offset_low  = (uint16_t)(addr & 0xFFFF);
    g_idt[vector].selector    = 0x08; /* 内核代码段选择子 */
    g_idt[vector].ist         = ist & 0x07;
    g_idt[vector].type_attr   = (1U << 7) | ((dpl & 0x03) << 5) | 0x0E; /* P=1, 64-bit Interrupt Gate */
    g_idt[vector].offset_mid  = (uint16_t)((addr >> 16) & 0xFFFF);
    g_idt[vector].offset_high = (uint32_t)((addr >> 32) & 0xFFFFFFFF);
    g_idt[vector].zero        = 0;
}

void x86_load_idt(void) {
    Idtr64 idtr;
    idtr.limit = sizeof(g_idt) - 1;
    idtr.base  = (uint64_t)&g_idt[0];
    __asm__ volatile("lidt %0" : : "m"(idtr) : "memory");
}
```

## 3.2 ARM NVIC 寄存器组详解与优先级分组机制 {#sec-edge.1.3.2}

在 ARM Cortex-M 中，NVIC 拥有专用的物理地址空间，挂载在**内部私有外设总线**（Internal Private Peripheral Bus, PPB, `0xE000_E000`）上。所有寄存器均支持 32 位字对齐访问，并具备原子置位与清除特性。

### 1. 核心寄存器组功能与物理位映射
为了杜绝在中断使能与清除过程中的读-改-写竞争，NVIC 采用了经典的**写 1 置位 / 写 1 清除**（Write-1-to-Set / Write-1-to-Clear）双寄存器设计：

| 寄存器组名称 | 物理基地址偏移 | 访问属性 | 功能与微架构语义说明 |
|:--|:--|:--|:--|
| `NVIC_ISER0-7` | `0xE000_E100` | 读/写1置位 | **中断设置使能寄存器**：向 bit $n$ 写入 1 开启对应中断；读出 1 表示当前已使能，写 0 无任何副作用 |
| `NVIC_ICER0-7` | `0xE000_E180` | 读/写1清除 | **中断清除使能寄存器**：向 bit $n$ 写入 1 彻底关闭对应中断；写 0 无副作用 |
| `NVIC_ISPR0-7` | `0xE000_E200` | 读/写1置位 | **中断挂起设置寄存器**：软件向 bit $n$ 写入 1 可强制将硬件中断置为挂起状态（软件触发硬件中断） |
| `NVIC_ICPR0-7` | `0xE000_E280` | 读/写1清除 | **中断挂起清除寄存器**：向 bit $n$ 写入 1 手工清除外设挂起状态 |
| `NVIC_IABR0-7` | `0xE000_E300` | 只读 | **中断活动状态寄存器**：bit $n$ 为 1 表示 CPU 当前正在执行该中断的服务程序，或被更高优先级中断打断挂起 |
| `NVIC_IPR0-59` | `0xE000_E400` | 读/写 | **中断优先级寄存器组**：每个中断独占 8 位字节空间，用于配置其逻辑优先级（通常仅实现高 4 位） |

### 2. 抢占优先级（Preempt Priority）与子优先级（Subpriority）分组
ARM Cortex-M 的优先级模型是嵌套抢占的精髓。在系统控制块中，`SCB->AIRCR` 寄存器的 `PRIGROUP[10:8]` 字段决定了 8 位优先级寄存器中，究竟前几位用于**抢占优先级**，后几位用于**子优先级**（响应优先级）：

```text
+----------------------------------------------------------------------------------------------------+
|                         SCB->AIRCR 优先级分组 (PRIGROUP) 物理切分模型                               |
+----------------------------------------------------------------------------------------------------+
| 芯片实际实现的 4 位优先级 (IPR[7:4]):                                                               |
| PRIGROUP = 3 (组 4: 4位抢占, 0位子优先级): [ Bit 7 | Bit 6 | Bit 5 | Bit 4 ] (16级绝对抢占)        |
| PRIGROUP = 4 (组 3: 3位抢占, 1位子优先级): [ Bit 7 | Bit 6 | Bit 5 ] [ Bit 4 ] (8级抢占, 2级子优先) |
| PRIGROUP = 5 (组 2: 2位抢占, 2位子优先级): [ Bit 7 | Bit 6 ] [ Bit 5 | Bit 4 ] (4级抢占, 4级子优先) |
| PRIGROUP = 6 (组 1: 1位抢占, 3位子优先级): [ Bit 7 ] [ Bit 6 | Bit 5 | Bit 4 ] (2级抢占, 8级子优先) |
| PRIGROUP = 7 (组 0: 0位抢占, 4位子优先级): [ 无抢占能力 ] [ Bit 7 | Bit 6 | Bit 5 | Bit 4 ] (0级抢占) |
+----------------------------------------------------------------------------------------------------+
```

::: def 中断抢占与仲裁两定律 {#def-edge.1.3.2.1}
1. **定律一（抢占裁决）**：只有当新到达中断的**抢占优先级数值严格小于**当前正在运行中断的抢占优先级时，硬件微架构才允许执行嵌套打断（Preemption）。抢占优先级相同的中断，无论其子优先级多高，**绝对无法打断正在运行的中断**！
2. **定律二（排队仲裁）**：当多个中断同时到达或在被屏蔽状态下同时处于挂起时，硬件仲裁器首先比较抢占优先级；若抢占优先级相同，则比较**子优先级**（数值越小越优先）；若子优先级依然相同，则由芯片物理**硬件中断编号**（IRQ Number）裁决，编号越小越先响应。
:::

::: ex 示例 3.1.1 · 工业伺服驱动器的优先级分组实战配置 {#ex-edge.1.3.2.1}
在伺服电机控制器中，存在三类典型中断：
- A 类（紧急保护）：过流/过温急停引脚中断（必须能打断一切）；
- B 类（高频控制）：PWM 定时器下溢 FOC 计算中断（20kHz 周期）；
- C 类（通信总线）：CAN 总线报文接收中断（毫秒级）。

合理的分组策略是将系统配置为 `PRIGROUP = 5`（2 位抢占优先级，2 位子优先级）：
- A 类中断配置为：抢占优先级 0，子优先级 0（最高优先级，随时抢占 B 与 C）；
- B 类中断配置为：抢占优先级 1，子优先级 0（可打断 C 类，但被 A 类抢占）；
- C 类中断配置为：抢占优先级 2，子优先级 0（最低执行权，无法打断 A 和 B）。

在 C 语言中，通过 CMSIS 标准库进行配置：
```c
/* 设置优先级分组为 Group 2 (2位抢占, 2位子优先级) */
/* 写入 AIRCR 必须携带硬件安全访问密钥 0x5FA */
NVIC_SetPriorityGrouping(5);

/* 配置 EXTI0 (急停) 为最高抢占优先级 (0, 0) */
NVIC_SetPriority(EXTI0_IRQn, NVIC_EncodePriority(5, 0, 0));
NVIC_EnableIRQ(EXTI0_IRQn);

/* 配置 TIM1 (FOC) 为次高抢占优先级 (1, 0) */
NVIC_SetPriority(TIM1_UP_TIM10_IRQn, NVIC_EncodePriority(5, 1, 0));
NVIC_EnableIRQ(TIM1_UP_TIM10_IRQn);
```

### 3. 裸机环境下脱离 CMSIS 的底层寄存器位操作实现
在极简固件或形式化验证环境中，不依赖任何第三方头文件直接操作硬件寄存器是系统级工程师的基本功：

```c
/* 纯寄存器级 NVIC 操作宏定义 */
#define NVIC_ISER_BASE      ((volatile uint32_t*)0xE000E100UL)
#define NVIC_ICER_BASE      ((volatile uint32_t*)0xE000E180UL)
#define NVIC_IPR_BASE       ((volatile uint8_t*)0xE000E400UL)
#define SCB_AIRCR           (*((volatile uint32_t*)0xE000ED0CUL))

/* 原子使能指定 IRQn 中断 */
static inline void raw_nvic_enable_irq(uint32_t irqn) {
    /* 确定目标寄存器组索引 (irqn / 32) 与位偏移 (irqn % 32) */
    NVIC_ISER_BASE[irqn >> 5] = (1UL << (irqn & 0x1FUL));
}

/* 原子禁用指定 IRQn 中断 */
static inline void raw_nvic_disable_irq(uint32_t irqn) {
    NVIC_ICER_BASE[irqn >> 5] = (1UL << (irqn & 0x1FUL));
}

/* 配置优先级分组为 Group 2 (2位抢占, 2位子优先级) */
static inline void raw_nvic_set_prigroup_2(void) {
    uint32_t aircr = SCB_AIRCR;
    aircr &= ~((0xFFFFUL << 16) | (0x07UL << 8)); /* 清除向量密钥与 PRIGROUP */
    /* 写入安全访问密钥 0x05FA 并设置 PRIGROUP = 5 */
    SCB_AIRCR = aircr | (0x5FAUL << 16) | (0x05UL << 8);
    __asm__ volatile("dsb" ::: "memory");
}

/* 设置指定 IRQn 的 4 位硬件优先级 */
static inline void raw_nvic_set_priority(uint32_t irqn, uint8_t preempt, uint8_t subprio) {
    /* STM32 使用高 4 位: [7:6] 为 preempt (0~3), [5:4] 为 subprio (0~3) */
    uint8_t prio = ((preempt & 0x03) << 6) | ((subprio & 0x03) << 4);
    NVIC_IPR_BASE[irqn] = prio;
}
```

### 4. 系统控制块异常控制与状态寄存器 (SCB->SHCSR) 深度解析
除了外设中断外，Cortex-M 的内核系统异常（MemManage、BusFault、UsageFault）并不归入常规的 `NVIC_ISER` 控制，而是由 `SCB->SHCSR`（System Handler Control and State Register, `0xE000_ED24`）统一管理：

| 位段 | 名称 | 访问属性 | 作用与安全语义说明 |
|:--|:--|:--|:--|
| `[16]` | `MEMFAULTENA` | 读/写 | 内存管理异常使能位：若清零，发生 MPU 违规时直接上访（Escalate）为致命 `HardFault` |
| `[17]` | `BUSFAULTENA` | 读/写 | 总线错误异常使能位：若清零，发生总线访问超时直接升级为 `HardFault` |
| `[18]` | `USGFAULTENA` | 读/写 | 用法错误使能位：若使能，除以零与非对齐访问可触发专用服务程序 |
| `[0]`  | `MEMFAULTACT` | 读/写 | MemManage 处于活动状态（当前正在处理） |
| `[1]`  | `BUSFAULTACT` | 读/写 | BusFault 处于活动状态 |
| `[3]`  | `USGFAULTACT` | 读/写 | UsageFault 处于活动状态 |
| `[7]`  | `SVCALLACT`   | 读/写 | SVC 系统调用处于活动状态 |
| `[10]` | `PENDSVACT`   | 读/写 | PendSV 上下文切换异常处于活动状态 |
| `[11]` | `SYSTICKACT`  | 读/写 | SysTick 滴答中断处于活动状态 |

在系统引导时，工业级固件必须显式激活三大可配置故障捕获，以便精确隔离与诊断错误，而非盲目跌入不可预测的 HardFault：
```c
/* 强制使能三大系统异常分级捕获 */
SCB->SHCSR |= (1UL << 16) | (1UL << 17) | (1UL << 18);
```

### 5. 可配置故障状态寄存器 (SCB->CFSR) 深度位域解码字典
当系统发生异常陷入 HardFault 时，最关键的诊断依据是 32 位寄存器 `SCB->CFSR`（`0xE000_ED28`）。在微架构中，它由三个独立的子状态寄存器直接拼装而成：
- **MMFSR (低 8 位, [7:0])**：内存管理故障状态寄存器；
- **BFSR (中 8 位, [15:8])**：总线故障状态寄存器；
- **UFSR (高 16 位, [31:16])**：用法故障状态寄存器。

| 寄存器分段 | 比特位 | 故障标志宏 | 物理根因与硬件触发条件分析 |
|:--|:--|:--|:--|
| **MMFSR** | `[0]` | `IACCVIOL` | 指令访问违规：MPU 判定当前取指地址无执行权限（XN 位保护生效） |
| **MMFSR** | `[1]` | `DACCVIOL` | 数据访问违规：对受 MPU 保护的只读或未授权物理区域执行了写入操作 |
| **MMFSR** | `[7]` | `MMARVALID`| `SCB->MMFAR` 寄存器有效：指示故障发生时的精确物理内存地址已被锁存 |
| **BFSR** | `[0]` | `IBUSERR`  | 指令总线错误：预取指期间总线返回错误响应（如读取未初始化的外部 SDRAM） |
| **BFSR** | `[1]` | `PRECISERR`| 精确数据总线错误：发生错误的内存物理地址已精准锁存在 `SCB->BFAR` 中 |
| **BFSR** | `[2]` | `IMPRECISERR`| **非精确总线错误**：写缓冲（Store Buffer）延迟写回时触发，PC 已越过出错指令！ |
| **BFSR** | `[7]` | `BFARVALID`| `SCB->BFAR` 寄存器有效：当前 BFAR 存储的值为触发总线异常的真实物理地址 |
| **UFSR** | `[0]` | `UNDEFINSTR`| 未定义指令：CPU 尝试执行未识别的机器指令码或协处理器不支持的指令 |
| **UFSR` | `[1]` | `INVSTATE` | 非法执行状态：试图在 Thumb 模式下执行传统的 ARM 32 位指令码，或 PC[0]=0 |
| **UFSR** | `[3]` | `NOCP`     | 协处理器未使能：尝试执行 FPU 硬件浮点指令，但 `CPACR` 寄存器尚未开启权限 |
| **UFSR** | `[4]` | `STKOF`    | 硬件栈溢出检测：ARMv8-M 架构专用硬件栈限位寄存器（MSPLIM/PSPLIM）越界 |
| **UFSR** | `[8]` | `UNALIGNED`| 非对齐访问错误：当 `SCB->CCR.UNALIGN_TRP=1` 时，执行非对齐读写指令立即抛出 |
| **UFSR** | `[9]` | `DIVBYZERO`| 除以零故障：当 `SCB->CCR.DIV_0_TRP=1` 时，执行除以零运算立即抛出 |

在开发底层故障自愈引擎时，利用 C 语言位操作可实现全自动的崩溃归因分析：

```c
/* 工业级崩溃状态机智能解码例程 */
void decode_cfsr_fault_reason(uint32_t cfsr) {
    uint8_t  mmfsr = (uint8_t)(cfsr & 0xFF);
    uint8_t  bfsr  = (uint8_t)((cfsr >> 8) & 0xFF);
    uint16_t ufsr  = (uint16_t)((cfsr >> 16) & 0xFFFF);

    if (mmfsr & (1U << 1)) {
        printf("[FAULT] MPU 数据访问违规! 出错地址: 0x%08X\n", SCB->MMFAR);
    }
    if (bfsr & (1U << 1)) {
        printf("[FAULT] 精确总线错误! 访问总线地址: 0x%08X\n", SCB->BFAR);
    }
    if (bfsr & (1U << 2)) {
        printf("[FAULT] 非精确总线错误 (由于写缓冲延迟, PC 可能已漂移)\n");
    }
    if (ufsr & (1U << 9)) {
        printf("[FAULT] 发生整数除以零指令错误!\n");
    }
    if (ufsr & (1U << 3)) {
        printf("[FAULT] 试图执行浮点指令但 FPU 协处理器未开启使能!\n");
    }
}
```

## 3.3 RISC-V 中断架构：mstatus、mie、mip 与 PLIC/CLINT 拓扑 {#sec-edge.1.3.3}

与 ARM 高度集成的单体 NVIC 不同，RISC-V 采用了清晰的解耦架构，将中断源划分为**局部中断**（Local Interrupts）与**全局外设中断**（Global / Platform-Level Interrupts）。

### 1. 核心局部中断器 (CLINT, Core-Local Interruptor)
CLINT 直接紧贴 CPU 核心流水线，仅负责两类最关键的机器模式内部中断：
- **软件中断（Software Interrupt）**：通过写入 `msip` 寄存器触发，常用于多核系统中的核间通信（IPI）或单核系统的任务让渡。
- **定时器中断（Timer Interrupt）**：由 64 位的实时自由递增计数器 `mtime` 与比较寄存器 `mtimecmp` 构成。当 `mtime >= mtimecmp` 时，硬件自动置位 `mip.MTIP`，向内核抛出时钟中断。

### 2. 平台级中断控制器 (PLIC, Platform-Level Interrupt Controller)
系统中的所有外部硬件外设（UART、SPI、CAN、DMA、GPIO）的中断线统一汇入 PLIC。PLIC 负责复杂的全局仲裁，并将最终胜出的中断通过一条全局外部中断线（`MEIP`）上报给 CPU 内核。

PLIC 的寄存器内存映射布局如下：
- `PLIC_PRIORITY_BASE` (`0x0C00_0000`)：中断源 1 到 1023 的优先级设置寄存器（每个 32 位，支持 0~7 级优先级）；
- `PLIC_PENDING_BASE` (`0x0C00_1000`)：中断源挂起位图数组；
- `PLIC_ENABLE_BASE` (`0x0C00_2000`)：每个 CPU 核心的目标中断使能位图；
- `PLIC_THRESHOLD_BASE` (`0x0C20_0000`)：核心当前运行优先级阈值寄存器；
- `PLIC_CLAIM_BASE` (`0x0C20_0004`)：核心中断索权与完成通知寄存器。

PLIC 的工作流由四个严格受控的寄存器阶段组成：

```c
/* RISC-V 外部中断分发例程 */
void handle_external_interrupt_plic(void) {
    /* 1. 索权: 读取 Claim 寄存器获取最高优先级中断 ID */
    uint32_t irq_id = *PLIC_CLAIM_REG;

    if (irq_id == 0) {
        return; /* 伪中断无害返回 */

    /* 2. 根据 ID 派发函数指针 */
    if (irq_id < MAX_EXTERNAL_IRQS && g_plic_irq_table[irq_id] != NULL) {
        g_plic_irq_table[irq_id]();
    }

    /* 3. 完成通知: 写回同一寄存器，重置硬件网关 */
    *PLIC_CLAIM_REG = irq_id;
}
```

### 3. RV32 下 mtimecmp 的有序分段写入
mtimecmp 是六十四位比较值，不是自由运行计数器本身。
以下限定小端、两个三十二位字访问、按程序顺序生效的 I/O 映射和单写者。
三次写不是原子事务；硬件可以观察中间值。
平台若采用不同定时器接口，应遵循其专门合同。

设 mtime=0x00000001_80000000，旧比较值为 0x00000001_90000000，新值为 0x00000002_00000005。
旧值和新值都在未来。
若先把低字直接改成 5，中间值变成 0x00000001_00000005，落到当前时间之前。
这才构成从两个未来截止点制造短暂过期的反例，不能用原本已过期的旧值举证。

```c
/* RV32 小端、有序 MMIO、单写者条件下的低字哨兵序列；不是原子更新。 */
void rv32_set_mtimecmp(volatile uint32_t *address, uint64_t target) {
    volatile uint32_t *low = address;
    volatile uint32_t *high = address + 1;
    *low = UINT32_MAX;
    __asm__ volatile("fence io,io" ::: "memory");
    *high = (uint32_t)(target >> 32);
    __asm__ volatile("fence io,io" ::: "memory");
    *low = (uint32_t)target;
    __asm__ volatile("fence io,io" ::: "memory");
}
```

第一个中间值不小于旧比较值，第二个不小于新比较值。
屏障域必须覆盖平台对设备访问的分类；旧稿的 o,w 不能直接保证后续设备输出事务排序。
MTIP 的撤销可能有传播延迟，设置未来截止点后仍可能观察到过渡性挂起。
目标本已过期时，触发中断是正确行为，不应被这套逻辑抹掉。
其他执行上下文若也写此寄存器，仍需独立串行化。
本轮 host 模型只检查中间值关系，不验证实体定时器或完整中断入口。

## 3.4 硬件压栈与出栈时序：自动压栈、咬尾中断与迟到中断 {#sec-edge.1.3.4}

ARM Cortex-M 能够在整个微控制器行业建立无可动摇的统治地位，其微架构中断流水线的**硬件自动化优化**功不可没。传统的处理器在响应中断时，必须依赖软件一条一条指令执行入栈操作；而 Cortex-M 完全交由底层硬件状态机并行推进。

### 1. 硬件自动压栈机制（Entry Sequence）
在 ARMv7-M 体系中，外部中断被 NVIC 仲裁选中并决定抢占后，硬件微架构状态机自动接管上下文保存流程。在理想的零等待（0 Wait-State）内存与单周期总线环境下，Cortex-M3/M4 的基准入栈序列理论耗时为 12 个时钟周期：
- **阶段一：状态机仲裁与栈指针准备**：内核流水线识别中断，完成当前执行指令的可打断收尾或等待；总线接口根据当前活动栈指针（MSP 或 PSP）计算压栈目标基址，并根据配置检查或施加 8 字节栈对齐。
- **阶段二：压栈写事务并发发起**：数据总线控制器顺序或突发发起写事务，将 **R0, R1, R2, R3, R12, LR, PC, xPSR** 共 8 个字推入物理堆栈。
- **阶段三：向量预取与目标译码**：指令总线并发从向量表中读取对应中断入口地址加载入 `PC`，同时将 `LR` 覆写为特殊的 `EXC_RETURN` 标记，流水线装填首条 ISR 指令。


### 2. 咬尾中断（Tail-Chaining）：消除 75% 的出入栈开销
在实际工业现场中，高频中断往往成簇到达（例如定时器中断触发后，紧接着外部通信引脚产生中断）。在传统的传统架构中，前一个中断退出时必须先完整出栈恢复 CPU 寄存器（耗费 12 周期），紧接着识别到新中断又完整重新压栈（耗费 12 周期），往复损耗高达 24 个周期。

Cortex-M 的微架构引入了天才的**咬尾中断**（Tail-Chaining）机制：
- 当前中断执行完毕准备返回时，NVIC 若检测到系统中依然存在挂起的中断；
- 硬件**彻底取消出栈操作**！堆栈中保存的 R0-xPSR 保持原样不动；
- 内核仅仅花费 **6 个时钟周期** 重新从向量表中读取下一个中断的入口地址更新到 `PC`，直接跳入新中断的执行体！
- 这一优化直接将中断切换时间从 24 周期缩减至 6 周期，效率暴增 **75%**。

### 3. 迟到中断（Late-Arriving）与弹出抢占（Pop-Preemption）
- **迟到中断（Late-Arriving）**：当 CPU 正在为低优先级中断 A 执行那 12 个周期的自动压栈过程中，突然到达了一个高优先级中断 B。此时硬件**不会中止压栈**，而是继续顺势完成栈帧保存；在压栈结束的第 12 周期，硬件直接将 `PC` 切换为高优先级中断 B 的入口地址！低优先级中断 A 则无缝转换为咬尾挂起状态，在 B 执行完毕后以 6 周期咬尾执行。
- **到达弹出（Pop-Preemption）**：当 CPU 正在执行出栈序列的初期，突然产生了一个高优先级中断。硬件状态机瞬间反转流水线，取消剩余的出栈读操作，直接复用当前栈指针重新切入中断。

### 4. 浮点惰性压栈（Lazy Stacking）机制与 EXC_RETURN 伪地址解码
当芯片配备了硬件单精度/双精度浮点单元（FPU）时，若每次中断都保存全部 32 个浮点寄存器（S0-S31），单次入栈开销将暴增至 30 个周期以上。Cortex-M4/M7 引入了**惰性浮点压栈**（Lazy Stacking，由 `FPU->FPCCR.LSPEN` 控制）：
- 发生中断时，硬件在物理堆栈中**仅预留 18 个双字的空间**（用于后续存放 S0-S15 及 FPSCR），但实际上并不向总线发送写请求；
- 如果该中断服务例程内部**全是纯整型指令**，则这 18 个字的浮点现场完全无需写入物理内存，中断依然保持 12 周期超速进入！
- 只有当中断内部**首次执行了一条浮点运算指令**时，硬件微架构才会暂停当前执行，在后台补齐浮点现场的实际写入。这一精妙机制在工业算法中极大保护了非浮点中断的硬实时响应能力。

在发生异常进入与返回时，连接寄存器 `LR` 中载入的不是真实的物理地址，而是由微架构硬件合成的 **`EXC_RETURN`** 魔法数值。软件通过解码 `LR` 的低 5 位，可以彻底洞察中断进入时的运行状态与栈帧类型：

| EXC_RETURN 魔法值 | 目标运行模式 | 目标恢复使用的栈指针 | 异常栈帧格式 | 典型应用场景 |
|:--|:--|:--|:--|:--|
| `0xFFFFFFF1` | Handler 模式 | 主栈指针 (MSP) | 标准基础帧 (8 双字, 32 字节) | 中断嵌套打断内核态 Handler 执行 |
| `0xFFFFFFE1` | Handler 模式 | 主栈指针 (MSP) | 扩展浮点帧 (26 双字, 104 字节)| 中断打断正在进行浮点计算的内核例程 |
| `0xFFFFFFF9` | Thread 模式  | 主栈指针 (MSP) | 标准基础帧 (8 双字, 32 字节) | 裸机无 RTOS 系统中的中断返回 |
| `0xFFFFFFE9` | Thread 模式  | 主栈指针 (MSP) | 扩展浮点帧 (26 双字, 104 字节)| 裸机系统在使用 FPU 时的中断返回 |
| `0xFFFFFFFD` | Thread 模式  | 进程栈指针 (PSP) | 标准基础帧 (8 双字, 32 字节) | **标准 RTOS 任务正常中断返回** |
| `0xFFFFFFED` | Thread 模式  | 进程栈指针 (PSP) | 扩展浮点帧 (26 双字, 104 字节)| **标准 RTOS 任务在使用 FPU 时的中断返回** |

读者可直接运行配套的 `experiments/ch03/run.sh` 脚本，在终端中观察仿真器对抢占与咬尾周期消除效果的真实数值输出。

## 3.5 RV32 整数异常框架：完整现场与不同返回 PC 合同 {#sec-edge.1.3.5}

RISC-V 异常入口不自动保存通用寄存器。
普通 C 调用可以破坏 caller-saved 寄存器，但被中断程序没有主动发起这个调用。

这不表示经过严格 ABI 证明的专用入口永远不能精简；但只保存四个寄存器后任意调用 C 是错误的。

旧稿只写出 f0–f3 又省略其余寄存器，且额外减 132 字节破坏调用前对齐，现撤下。
FS=Clean 不表示处理器可以任意覆盖浮点寄存器而不恢复。

## 3.6 硬件系统滴答：计数器、忙等与到期服务预算 {#sec-edge.1.3.6}

在实时操作系统与裸机控制框架中，**系统时钟滴答**（System Tick）是驱动任务时间片轮转、软件定时器到期判断与超时退出的物理心脏。

### 1. ARM SysTick 寄存器级架构
ARM Cortex-M 在内核核心内部固定集成了一个 24 位的向下递减计数器（SysTick）。寄存器布局不等于时钟和校准条件相同；应确认目标是否实现 SysTick、时钟源以及 CALIB 的 NOREF、SKEW 和 TENMS。

SysTick 由四个寄存器严格控制：

| 寄存器名称 | 物理基地址 | 访问属性 | 功能与位域定义 |
|:--|:--|:--|:--|
| `SysTick->CTRL` | `0xE000_E010` | 读/写 | **控制与状态寄存器**：<br>`[0]` `ENABLE` 计数器使能；<br>`[1]` `TICKINT` 计数到 0 时是否产生 SysTick 异常中断；<br>`[2]` `CLKSOURCE` 时钟源选择（`1` = 处理器内核时钟 HCLK，`0` = 外部参考分频时钟）；<br>`[16]` `COUNTFLAG` 只读标志，计数器减到 0 时硬件置 1，读取后自动硬件清零 |
| `SysTick->LOAD` | `0xE000_E014` | 读/写 | **重装载数值寄存器**：24 位有效数值（`0x0000_0001` 到 `0x00FF_FFFF`） |
| `SysTick->VAL`  | `0xE000_E018` | 读/写清零 | **当前计数器数值寄存器**：读取返回当前实时数值，向其写入任意值立即清零并重置 COUNTFLAG |
| `SysTick->CALIB`| `0xE000_E01C` | 只读 | 芯片出厂校准寄存器（标注 10ms 滴答所需的计数值） |

### 2. 轮询是忙等，不是非阻塞调用
下面循环占用当前执行上下文；中断仍可抢占，不等于调用者没有被阻塞。
本片段仅说明单回绕差值，条件是计数器持续运行、LOAD 和时钟不变、两次观察之间少于一个完整周期。
超出这些前提可能漏掉整周，不能当作通用准确延时函数。
整数 MHz 换算还会丢弃非整数部分；本例不是纳秒精度或 WCET 证明。
真正非阻塞接口应保存开始时刻，每次只判断一次到期并交回控制权。
调用者还需保证再次检查的频率，以及平台单调时钟的原子读取。

```c
/* 忙等原理片段：已知整数 MHz 时钟，不能漏过一整周。 */
void delay_us_busywait_example(uint32_t us) {
    /* 假定系统主频 SystemCoreClock = 168MHz, 每微秒时钟周期数 ticks_per_us = 168 */
    uint32_t ticks_per_us = SystemCoreClock / 1000000UL;
    uint64_t total_ticks = (uint64_t)us * ticks_per_us;
    
    uint32_t start_val = SysTick->VAL;
    uint32_t load_val  = SysTick->LOAD;
    uint64_t elapsed_ticks = 0;
    uint32_t last_val = start_val;

    while (elapsed_ticks < total_ticks) {
        uint32_t current_val = SysTick->VAL;
        
        if (current_val <= last_val) {
            /* 计数器在单周期内正常递减 */
            elapsed_ticks += (last_val - current_val);
        } else {
            /* 计数器递减到 0 发生了硬件重载 (Underflow Reload) */
            elapsed_ticks += (last_val + (load_val + 1u - current_val));
        }
        last_val = current_val;
    }
}
```

### 3. 线性链表扫描：不是时间轮，也不是 O(1)
在高并发嵌入式节点中，若为每个超时任务启动一个物理硬件定时器，外设资源将迅速枯竭。工程最佳实践是基于单一系统滴答驱动轻量级**时间轮**（Timer Wheel）或差分链表（Delta List）：

```c
typedef void (*TimerCallback)(void* arg);

typedef struct SoftTimer {
    uint32_t timeout_ticks;
    uint32_t reload_ticks;
    TimerCallback callback;
    void* arg;
    struct SoftTimer* next;
} SoftTimer;

static SoftTimer* g_timer_head = NULL;

/* 单所有者示意：遍历 O(N)；回调成本另算，不是生产 ISR 的有界实现。 */
void soft_timer_tick_update(void) {
    SoftTimer* curr = g_timer_head;
    while (curr != NULL) {
        if (curr->timeout_ticks > 0) {
            curr->timeout_ticks--;
            if (curr->timeout_ticks == 0) {
                /* 到期触发回调 */
                curr->callback(curr->arg);
                curr->timeout_ticks = curr->reload_ticks;
            }
        }
        curr = curr->next;
    }
}
```

### 4. 反例：只双读软件高位不能保证时间戳正确
以下保留为错误算法示意，不得当作可用时间接口。
硬件已经重装载而 ISR 尚未执行时，两次软件高位可以相等，却属于旧周期。
例如 LOAD=9、高位=7、VAL 从 1 经过回绕变成 9，旧合成值会从 78 倒退到 70。
读取 COUNTFLAG 也不能恢复多次丢失回绕，且它自身有读清副作用。
正确适配必须结合设备、挂起状态、最长屏蔽时间和并发协议，或选择足够宽的自由运行计数器。
生产级六十四位时间适配器仍未完成，不能用这份反例或 host 模型冒充。

```c
/* 错误反例：软件高位未变化，不代表硬件未回绕。 */
static volatile uint32_t g_systick_overflow_count = 0;

/* 在 SysTick_Handler 中递增高位计数器 */
void SysTick_Handler(void) {
    g_systick_overflow_count++;
}

uint64_t broken_time_us_double_read(void) {
    uint32_t high1, high2, low;
    uint32_t load = SysTick->LOAD;
    uint32_t ticks_per_us = SystemCoreClock / 1000000UL;

    /* 经典双读校验防撕裂算法 (Double-Read Verification) */
    do {
        high1 = g_systick_overflow_count;
        low   = SysTick->VAL;
        high2 = g_systick_overflow_count;
        /* 若在读取 low 的瞬间恰好发生中断并更新了高位计数器，则 high1 != high2，自动重试 */
    } while (high1 != high2);

    /* 结合高位周期与低位递减计数值合成 64 位绝对时钟脉冲数 */
    uint64_t total_ticks = ((uint64_t)high1 * (load + 1)) + (load - low);
    return total_ticks / ticks_per_us;
}
```
当活跃定时器数量达到数十个时，简单链表遍历将消耗较多中断执行时间。工业 RTOS 普遍采用**差分时间链表**（Delta List）：链表中的节点仅存储相对于前一个节点的**差分到期时间**。每次递减表头在无到期事件时可为 O(1)；同一次 tick 有 k 项到期则至少处理 O(k) 项，插入通常仍需 O(N)。回调的任意成本也必须单列。生产 ISR 应设服务预算并显式移交剩余工作，不能声称总成本严格 O(1)。

```c
/* 差分时间链表完整实现 */
typedef struct DeltaTimer {
    uint32_t delta_ticks;       /* 距离前一个节点的相对差分滴答数 */
    TimerCallback callback;     /* 到期回调函数 */
    void* arg;
    struct DeltaTimer* next;
} DeltaTimer;

static DeltaTimer* g_delta_list = NULL;

/* 插入定时器到差分链表 */
void delta_timer_insert(DeltaTimer* timer, uint32_t ticks, TimerCallback cb, void* arg) {
    timer->callback = cb;
    timer->arg = arg;

    uint32_t accum = 0;
    DeltaTimer** curr = &g_delta_list;

    while (*curr != NULL && (accum + (*curr)->delta_ticks) <= ticks) {
        accum += (*curr)->delta_ticks;
        curr = &((*curr)->next);
    }

    timer->delta_ticks = ticks - accum;
    timer->next = *curr;

    if (*curr != NULL) {
        (*curr)->delta_ticks -= timer->delta_ticks;
    }
    *curr = timer;
}

/* 单所有者示意：到期 k 项需 O(k) 加回调成本，尚无并发与 ISR 预算协议。 */
void delta_timer_tick_isr(void) {
    if (g_delta_list == NULL) return;

    /* 仅递减表头节点的差分计数器 */
    if (g_delta_list->delta_ticks > 0) {
        g_delta_list->delta_ticks--;
    }

    /* 检查表头是否到期 */
    while (g_delta_list != NULL && g_delta_list->delta_ticks == 0) {
        DeltaTimer* expired = g_delta_list;
        g_delta_list = g_delta_list->next;
        /* 执行到期回调 */
        expired->callback(expired->arg);
    }
}
```

## 3.7 中断延迟实测与抖动优化：流水线冲刷、中断嵌套与总线仲裁 {#sec-edge.1.3.7}

即使在具备硬件自动压栈的 ARM Cortex-M 体系中，中断响应延迟也并非绝对静态不变。微架构层面的多种物理因素会导致纳秒至微秒级的抖动。

下表汇总主流微控制器内核在芯片厂商与技术参考手册（TRM）中给出的标称理想硬件中断进入/退出周期数（基于 0 等待内存与单周期总线的前提；实体系统必须叠加存储等待与总线冲突）：

| 处理器内核微架构 | 手册标称入栈延迟 (Cycles) | 手册标称出栈延迟 (Cycles) | 标称咬尾优化 (Tail-Chaining) | 浮点扩展影响 | 依赖前提与备注 |
|:--|:--|:--|:--|:--|:--|
| **ARM Cortex-M0+** | **15 周期** (2级流水线) | 15 周期 | 无专用快速咬尾 (需完整出入栈) | 无硬件 FPU | 需单周期 I/O 与零等待存储 |
| **ARM Cortex-M3**  | **12 周期** (3级流水线) | 12 周期 | **6 周期** | 无硬件 FPU | 零等待 SRAM，向量表位于快速总线 |
| **ARM Cortex-M4**  | **12 周期** (3级流水线) | 12 周期 | **6 周期** | 扩展帧需额外写 18 字 | 未启用惰性保存时入栈需增加周期 |
| **ARM Cortex-M7**  | **14 周期** (双发射管线) | 14 周期 | **6 周期** | 双精度扩展需更多周期 | 受 AXI 交叉开关与 Flash 周期影响巨大 |
| **RISC-V (典型软中断)**| 取决于汇编保存集合 | 取决于汇编恢复集合 | 需软件调度器显式支持 | 需软件保存 `f0–f31` | 硬件不自动压栈，时间由汇编指令数决定 |
| **x86_64 (IDT/IRETQ)**| 硬件压栈 5 字 (数十周期) | `iretq` 出栈恢复 | 不支持硬件咬尾 | 需软件 `xsave`/`fxsave` | 受特权级切换与分页模式影响 |

### 1. 多周期指令执行与流水线冲刷（Pipeline Flush）
当外部中断信号到达引脚时，CPU 正在执行的指令决定了微架构能否立即响应：
- 若 CPU 正在执行单周期指令（如 `ADD`, `MOV`），流水线在当前周期结束后立即开始执行中断压栈。
- 若 CPU 此时恰好在执行**多周期不可拆分指令**（如硬件无符号除法 `UDIV` 耗时 $2 \sim 12$ 个周期，或者多寄存器连续内存写入 `STMIA`），微架构必须等待该指令的所有内存写事务彻底完成，才能正式拉起中断响应，从而产生数个时钟周期的抖动。
- **优化对策**：在硬实时关键路径上，开启编译器的 `-mno-unaligned-access` 杜绝非对齐多周期访存，并优先采用单周期乘法指令。

### 2. 存储器等待周期与总线矩阵冲突
在 Cortex-M7 中，中断向量表存放在片上 Flash 中。若此时某个高吞吐 DMA（如以太网或视频采集）正在全速占用 AXI 总线，且 Flash 恰好配置了 5 个等待周期：
$$T_{lat} = 12\,\text{Cycles (Core)} + 5\,\text{Cycles (Flash Wait)} + N_{\text{Bus-Stall}}$$
中断延迟瞬间被拉长至原本的两倍以上。
- **终极优化对策**：将中断向量表从 Flash 镜像动态拷贝至 **ITCM 紧耦合内存** 中，并通过重写 `SCB->VTOR = 0x00000000` 将向量基地址映射到 ITCM。由于 ITCM 直接直连 CPU 私有流水线，总线访问等待恒为 0，且绝对免疫任何外部 DMA 的总线抢占，中断响应延迟方可达到理论数学下界。

### 3. 中断锁相环抖动与外部引脚去抖滤波器
在工业现场中，许多微控制器 GPIO 引脚配备了硬件可编程数字滤波器（如 STM32 定时器的数字滤波通道）。若将去抖滤波器配置为 8 个采样时钟确认，当芯片时钟为 84MHz 时，引脚信号在进入 NVIC 前已经被硬件延迟了近 $100\,\text{ns}$。在测定与标定实际延迟指标时，必须将物理滤波时间与 CPU 内核时序严格区分。

### 4. 向量表位置与测量边界

若向量表和 ISR 位于慢速存储区域，取指和向量读取都可能影响延迟。
迁移前必须查目标总线手册，核实异常向量读取是否走预期端口。
不能因数据地址在 ITCM 范围，就推断所有系统读取必定零等待。
测试还要给出向量数量、对齐、时钟、触发源、GPIO 写延迟与测量仪器。
本书本轮没有实体开发板采样证据，因此删除旧草稿的 Flash/ITCM 精确周期“实测表”。
QEMU 功能验证不能填补这一硬件测量缺口。

## 3.8 agent 错误案例：中断内格式化与浮点上下文合同 {#sec-edge.1.3.8}

### 构造场景，不冒充现场事故

主任务与编码器 ISR 同时使用一个日志缓冲区。
ISR 内调用浮点格式化，使该中断的路径和栈使用显著增长。
如果格式化实现、堆锁或输出设备不支持这种重入，会出现缓冲区破坏、死锁或超时。
并不是所有 sprintf 实现都天然共享同一个静态缓冲区，必须检查具体 C 库及其配置。

### 浮点懒压栈的正确解释

在 Cortex-M4F/M7F 正确配置自动上下文保存时，惰性压栈先预留空间。
ISR 首次执行浮点指令会触发延迟保存，不会仅因缺少软件 vpush 就天然污染主任务。
因此在反汇编里看到 vdiv 不能单独证明保存缺失。
应核查 CONTROL.FPCA、FPCCR.ASPEN/LSPEN、EXC_RETURN、任务软件保存集合和栈边界。

| 配置字段 | 作用 | 不能据此推断 |
|:--|:--|:--|
| ASPEN=1 | 自动管理浮点上下文状态 | 所有 S0–S31 都由硬件保存 |
| LSPEN=1 | 允许延迟保存浮点低位现场 | ISR 使用 FPU 必然污染线程 |
| ASPEN=1、LSPEN=0 | 自动保存，不采用懒保存 | 浮点栈开销和时延为零 |
| EXC_RETURN bit 4 | 基本或扩展帧标识 | 可沿用上一个任务的 LR |

S16–S31 在任务切换时仍需按 ABI 与运行状态处理。
把 ASPEN 和 LSPEN 一起清零不是强制硬件完整压栈，旧草稿该建议已撤销。

### 修复与复现路径

ISR 只记录有界的原始数据，后台任务做格式化与输出。
满队列、硬件超时与非法参数分别计数。
整型路径同样要检查乘法溢出，不能因为“定点”就省略数值边界。

第四章提供了可以实际运行的无 FPU Cortex-M3 中断切换固件与 C11 队列实验：

```bash
cd edge
bash experiments/ch04/run.sh
```

其中 ARM 测试验证整数上下文，未验证 Cortex-M4F 的懒压栈。
要宣称 FPU 端口通过，必须另做使用不同浮点哨兵、嵌套中断和混合基本/扩展帧的靶机测试。

### FPU 端口验收矩阵

若未来增加 Cortex-M4F 或 M7F 靶机，至少执行以下组合。
不要只用一个没有浮点指令的整数任务作为验收证据。

| 被打断线程 | ISR | 任务切换 | 应检查的状态 |
|:--|:--|:--|:--|
| 整数 | 整数 | 无 | 基本帧、SP、EXC_RETURN |
| 浮点 | 整数 | 无 | 低位浮点帧预留与懒保存状态 |
| 浮点 | 浮点 | 无 | 首次浮点使用触发的保存、FPSCR |
| 浮点 | 整数 | 切到整数任务 | 每任务返回格式不串扰 |
| 整数 | 浮点 | 切到浮点任务 | FPCA 与保存集合一致 |
| 浮点 | 浮点嵌套 | 有 | 每层栈空间与现场恢复 |

每个任务应写入不同的浮点哨兵值。
只对所有任务填同一常数，可能漏过寄存器串扰。
还应检查 FPSCR 的舍入和异常状态，而不只是数值寄存器。
硬件若支持双精度，测试应覆盖其实际保存格式。
栈空间测量要同时包括扩展帧、嵌套帧和 C 处理函数局部变量。
检查器要能对故意破坏一项保存的变体报失败。
测试通过后再给出版本、编译选项、初始 FPCCR 与原始输出。
当前整数实验不填充这张矩阵为“全通过”。

## 3.10 本章陷阱 {#sec-edge.1.3.10}

::: errata 本章陷阱

1. **写 `SCB->AIRCR` 时遗漏写入向量密钥 (VECTKEY)**：修改优先级分组 `PRIGROUP` 时直接写入数值。现象：寄存器数值毫无变化，优先级分组修改完全无效。原因：ARM 硬件微架构为了防止程序跑飞时误改核心中断配置，强制要求向高 16 位写入专用安全密钥 `0x05FA`。修复：写入时必须携带密钥：`SCB->AIRCR = (0x5FAUL << 16) | (prigroup << 8);`。
2. **把惰性浮点压栈误读为不保存现场**：现象是审查者只因 ISR 出现 vdiv 就断定污染，并错误建议清除 ASPEN。原因是混淆自动保存与延迟保存。修复应核查 FPCCR、CONTROL.FPCA、EXC_RETURN、S16–S31 软件保存和栈空间；正确的懒保存会在首次浮点指令前完成所需低位现场保存。
3. **在多核或中断环境中调用非重入标准库函数**：在中断处理例程中直接调用 `sprintf`、`malloc` 或 `free`。现象：运行数小时后系统在堆内存管理链表遍历时死锁或突发 HardFault。原因：标准库函数内部包含非线程安全的全局状态变量。修复：中断服务程序严禁调用任何非重入库函数，所有日志格式化后置于后台线程处理。
4. **中断服务程序末尾遗漏总线同步屏障导致重复进入中断**：清除外设中断标志位后直接退出函数。现象：中断退出后瞬时无故再次进入同一中断（伪中断死锁）。原因：外设挂载在低速 APB 总线上，写清零数据在写缓冲器中排队，退出中断时外设中断线依然处于高电平。修复：在清零中断标志寄存器后显式调用 `__DSB()` 数据同步屏障指令。
5. **在 RISC-V 中断处理中遗漏保存与恢复 `mepc`**：在支持中断嵌套的 RISC-V 系统中，外层中断被内层中断抢占，内层中断覆写了 `mepc`。现象：内层中断执行完毕后，CPU 无法返回外层被抢占的业务代码，而是死循环执行内层中断入口。原因：RISC-V 的 `mepc` 是单例硬件寄存器，无法自动记忆嵌套层级。修复：进入中断后第一行必须将 `mepc` 压入当前私有栈中，退出前再从栈中恢复。
6. **误将子优先级配置为抢占依据**：在相同抢占优先级下，将某关键传感器中断的子优先级设为 0，通用通信中断设为 1，以为传感器能实时打断通信。现象：通信中断耗时过长时，传感器采样严重丢帧。原因：子优先级仅在排队竞争时有效，**同抢占优先级之间硬件严禁相互打断**。修复：关键传感器必须分配更低的抢占优先级数值。
7. **在 NVIC 使能中断前遗漏清除历史挂起标志**：芯片上电或初始化外设时，引脚噪声可能已经置位了内部挂起位；直接调用 `NVIC_EnableIRQ()`。现象：中断刚一使能，立刻突发执行一次虚假的历史中断。修复：在调用 `NVIC_EnableIRQ()` 之前，强制调用一次 `NVIC_ClearPendingIRQ()`。
8. **利用 SysTick 实现延时时未考虑 24 位计数器向下溢出重载边界**：在读取 `SysTick->VAL` 计算时间差时，使用简单减法未处理重装载回绕。现象：每次刚好跨越重装载周期时，计算出的延时时长突变为极大的错误数值。修复：显式判断当前值与上一次值的相对大小，跨越重载时加上 `LOAD` 周期补偿。
9. **在 RISC-V PLIC 处理中读取 Claim 后未写回 Completion 寄存器**：中断例程处理完外设后直接返回。现象：该外部设备此后产生的所有后续中断全部被物理拦截，系统永久失去响应。原因：PLIC 网关在收到写回 Completion 之前，判定该中断处于处理锁定状态，拒绝接收新脉冲。修复：ISR 退出前必须无条件执行 `*PLIC_CLAIM_REG = irq_id;`。
10. **在中断处理函数内部使用阻塞式轮询硬件标志位**：在 UART 或 I2C 中断中，使用 `while(!(USART1->SR & USART_SR_TC));` 等待发送完成。现象：若外设物理总线发生硬件拉死故障，整个 CPU 彻底在中断内部永久锁死，看门狗超时停机。修复：中断内部严禁任何无超时的死循环轮询，必须采用状态机或超时计数器退出机制。
11. **混淆中断向量号（Vector ID）与外部中断编号（IRQn）**：在配置 NVIC 寄存器时，误将 Cortex-M 向量表绝对索引（如 SysTick 向量号为 15）当作 `IRQn` 传入 `NVIC_SetPriority`。现象：系统内核崩溃，改写了未预期的中断优先级。原因：CMSIS 标准库中的 `IRQn` 对系统内部异常使用负数（SysTick 为 -1），外部中断从 0 计起。修复：严格使用 CMSIS 预定义的枚举类型宏（如 `SysTick_IRQn`）。
12. **将中断服务例程的函数指针赋予偶数地址**：自制向量表时未将函数指针最低位置 1。现象：中断触发的瞬间芯片立即触发 HardFault 锁定。原因：ARM Cortex-M 强制要求所有中断服务函数地址的 Bit 0 必须为 1，以标识 Thumb 执行状态。修复：确保链接器自动置位，或在动态装配向量表时显式执行 `(uint32_t)ISR_Handler | 1`。

:::

::: method 即时自测 {#method-edge.1.3.11.1}
**自测题**：
某工程师在 Cortex-M4 微控制器（配置了 4 位优先级硬件，`PRIGROUP = 4`，即 3 位抢占优先级，1 位子优先级）上开发了一套工业控制器。系统中存在两个中断源：
- 中断 A（定时器更新）：配置优先级数值为 `0x20`；
- 中断 B（外部故障输入）：配置优先级数值为 `0x30`。
请回答：
1. 中断 A 与中断 B 的抢占优先级和子优先级各是多少？
2. 当中断 B 正在执行时，中断 A 突然触发，中断 A 能否打断中断 B 形成嵌套抢占？
3. 反过来，当中断 A 正在执行时，中断 B 突然触发，中断 B 能否打断中断 A？如果不能，硬件将以何种机制执行中断 B？

::: sol
**解题思路与标准答案**：
1. **优先级解码计算**：
   - 芯片仅实现高 4 位优先级（Bit 7..4），`PRIGROUP = 4` 代表使用高 3 位作为抢占优先级（Bit 7..5），第 4 位作为子优先级（Bit 4）。
   - **中断 A（`0x20`）**：二进制为 `0b0010_0000`。
     高 4 位为 `0b0010`。前 3 位（Bit 7..5）为 `0b001 = 1`（抢占优先级）；第 4 位（Bit 4）为 `0b0 = 0`（子优先级）。故中断 A：**抢占优先级 = 1，子优先级 = 0**。
   - **中断 B（`0x30`）**：二进制为 `0b0011_0000`。
     高 4 位为 `0b0011`。前 3 位（Bit 7..5）为 `0b001 = 1`（抢占优先级）；第 4 位（Bit 4）为 `0b1 = 1`（子优先级）。故中断 B：**抢占优先级 = 1，子优先级 = 1**。
2. **中断 A 能否抢占中断 B**：
   - **不能！** 根据中断抢占第一定律，只有当抢占优先级数值严格小于当前运行优先级时才允许打断。中断 A 与中断 B 的抢占优先级均为 1（数值相同）。虽然中断 A 的子优先级为 0 高于中断 B 的子优先级 1，但在 Cortex-M 架构中，**子优先级只在挂起排队时起作用，相同抢占优先级绝对无法相互嵌套打断**！
3. **中断 B 能否抢占中断 A 及执行机制**：
   - 中断 B 同样不能打断中断 A（抢占优先级数值相同）。
   - **硬件执行机制**：中断 B 到达后被硬件置为挂起（Pending）状态。当中断 A 执行完毕退出时，NVIC 硬件检测到中断 B 处于挂起，瞬间激活**咬尾中断（Tail-Chaining）**机制：硬件跳过恢复现场出栈与重新压栈操作，保持栈帧不变，仅耗费 6 个时钟周期直接换入中断 B 的入口地址开始执行！
