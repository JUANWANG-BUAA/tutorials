前三章分别建立了外设 MMIO/DMA 的访问合同、CAN 现场总线协议栈以及 ADC 与定点滤波/FFT 核心。
然而，在工业振动监测、声学阵列、雷达中频采样与多通道生理信号采集中，系统面临的核心挑战不仅是单个样本的转换精度，而是**高吞吐、连续不断的数据流与高延迟、突发性存储/上报之间的吞吐与时间矛盾**。

一个以 100 kSPS 运行的 16 位 ADC 每秒产生 200 KB 数据，时钟刚性推进，绝不停歇。
而与之对接的持久化介质（如 SPI Flash、eMMC 或 SD 卡）在执行页写入或块擦除时，可能会出现长达数毫秒甚至数十毫秒的物理总线挂起。
若数据管道缺乏精确的缓冲容量预算与代际交接契约，采样 FIFO 将瞬时溢出，造成不可逆的连续丢样。

本章以处理器微架构、总线矩阵、DMA 引擎与流式缓冲管道为主线。
我们不探讨模拟放大电路或变压器隔离，而是聚焦于系统程序员必须掌控的**总线仲裁、双缓冲代际交接、缓存行一致性维护以及存储背压容量定理**。

实验分为两个严格隔离的层次。
第一层为主机 C11 管道模型，在 ASan/UBSan 监控下量化验证 5 ms 块擦除暂停下的队列容量边界、背压丢块与缓存失效后果。
第二层为 QEMU Cortex-M3 与 RV32IM 目标机固件，执行 128 块 Ping-Pong 缓冲区交接、校验和自检与变异失败检测。
本轮实验没有连接物理示波器或真实高速 ADC 芯片，所有时间与吞吐数据均明确标示为数学模型或目标仿真。

## 8.1 持续数据流与离散时钟：从 ADC 采样到存储管道的架构分层 {#sec-edge.2.8.1}

### 刚性数据源与弹性存储汇

高速数据采集系统的本质是一个**多时钟域、多吞吐速率的阻抗匹配管道**。
输入端是刚性推进的离散时间采样序列，输出端是具备不可预测突发延迟的存储或网络介质。

::: def 数据管道三级缓冲契约 {#def-edge.2.8.1.1}
高速连续数据采集系统必须划分为三个物理与时序解耦的层级：
1. **Tier 1 硬件级（DMA Ping-Pong / 双缓冲）**：紧贴外设 FIFO，由外设请求驱动 DMA 自动搬运，消除每次采样的 CPU 中断开销；
2. **Tier 2 驱动级（无锁 SPSC 环形块队列）**：以块（Block）为单元组织，吸收任务调度抖动与算法处理的不均匀耗时；
3. **Tier 3 存储级（大容量持久化缓冲与介质驱动）**：匹配存储设备的块擦除（Block Erase）与写等待特性，提供背压感知。
:::

若试图让 CPU 在每次 ADC 转换完成时通过中断读取单个寄存器并直接写入存储器，系统将在高采样率下瞬时瘫痪。
以 500 kSPS 采样率为例，采样间隔仅为 2 µs。
任何超过 2 µs 的关中断临界区或高优先级任务抢占，都将直接导致外设单字 FIFO 发生下溢或溢出。

在微观时序上，ADC 的每个转换周期包含三个明确阶段：
首先是采样保持放大器（SHA）连接输入信号的跟踪与采样时间 $t_{sample}$；
其次是内部比较器网络或逐次逼近逻辑运行的转换时间 $t_{conv}$；
最后是转换结果打入输出数据寄存器并置位标志的就绪时间 $t_{drdy}$。
若采样时钟为外部硬件定时器或专用引脚触发，转换结束脉冲（DRDY）在时间轴上以严格恒定的周期出现。
CPU 的执行流则受制于指令 Cache 命中率、流水线冲刷、中断屏蔽和操作系统任务调度，在微秒尺度上呈现高度离散的随机分布。
若没有专用的 DMA 硬件通道在纳秒级将数据搬出，两者在时钟域上的失配必然导致灾难性的样本丢弃。

### 多通道扫描与通道间相位倾斜

在工业三相电参数采集或音频立体声处理中，系统往往需要同时获取多个模拟通道的电压值。
不同微控制器的 ADC 架构在多通道实现上存在显著的微架构差异：

1. **时分复用顺序扫描（Interleaved Scanning）**：
   - 典型代表：多数单 ADC 芯片（如 STM32F4 ADC1 多通道扫描）。
   - 内部仅包含一个物理采样保持器与一套转换核。当配置为扫描模式时，模拟多路开关在通道 0、1、2 之间轮流切换。
   - 致命物理后果：**通道间存在非零的采样时差（Time Skew）**！通道 0 的采样时刻与通道 1 相差一个完整的 $t_{conv}$（例如 $1\,\mu\text{s}$）。若直接用这两个数值计算瞬时功率（$P = U \times I$）或相位差，时差将被直接放大为计算误差，高频时尤甚。
   - 固件补偿：若必须使用单 ADC，软件算法必须根据 $t_{conv}$ 的精确值进行线性插值或多项式相位校正。

2. **同步并行独立采样（Simultaneous Sampling）**：
   - 典型代表：集成多个独立 ADC 内核的微控制器（如双 ADC、三 ADC 同步模式）或专用 DAQ 芯片（如 AD7606）。
   - 拥有多套物理独立的采样保持开关与转换核，在同一个触发脉冲沿同时闭合开关。
   - 固件优势：通道间相位差在硬件上被压制在孔径抖动量级（亚纳秒级），软件无需任何复杂的相位插值即可直接对多通道样本进行点积计算。

### 孔径时间、有效延迟与孔径抖动

根据母本《数据采集基础知识》第 72–75 页的定义，采样保持电路的关键动态参数直接决定了高速采集的信号保真度上限：

- **孔径时间（Aperture Time, $t_a$）**：采样保持开关从接收到保持命令到完全断开所需的有限物理时间间隔（通常为数十皮秒至数纳秒）。在这一区间内，保持电容上的电压是输入信号在该时间段内的加权积分。
- **有效孔径延迟时间（Effective Aperture Delay, $t_e$）**：以输入端为基准，实际采样点相对于时钟触发边沿的固定时间差。它等于输入模拟缓冲延迟 $t_{da}$ 减去开关驱动逻辑延迟 $t_{dd}$ 再加上 $t_a / 2$。孔径延迟是一个可校准的固定常数，在单通道系统中仅引入固定的系统群延迟，不恶化信噪比；但在多个独立 ADC 的阵列同步中，芯片间的 $t_e$ 失配将破坏波束成形算法。
- **孔径抖动（Aperture Jitter, $\Delta t_{rms}$）**：孔径延迟在每次采样之间的随机时序涨落，通常服从高斯分布，单位为均方根皮秒（$\text{ps}_{rms}$）。

当被测模拟信号为高频正弦波 $V_{in}(t) = V_{fs} \sin(2\pi f_{in} t)$ 时，信号的最大电压变化率（Slew Rate）出现在过零点处：
$$\left. \frac{dV_{in}}{dt} \right|_{max} = 2\pi f_{in} V_{fs}$$
微小的时序抖动 $\Delta t_{rms}$ 将直接转化为不可消除的采样电压噪声：
$$\Delta V_{rms} = \left. \frac{dV_{in}}{dt} \right|_{max} \cdot \Delta t_{rms} = 2\pi f_{in} V_{fs} \Delta t_{rms}$$
由此推导出的理论信噪比（SNR）绝对物理上限为：
$$\text{SNR}_{jitter} = -20 \log_{10} \left( 2\pi f_{in} \Delta t_{rms} \right) \quad (\text{dB})$$

下表量化展示了不同输入信号频率与时钟抖动组合下的理论 SNR 上限：

| 输入信号频率 ($f_{in}$) | 孔径抖动 ($\Delta t_{rms}$) | 理论 SNR 上限 ($\text{dB}$) | 对应有效位数上限 (ENOB) | 实际系统影响评估 |
|--:|--:|--:|--:|:--|
| $1\,\text{kHz}$ | $1000\,\text{ps}$ ($1\,\text{ns}$) | $104.0\,\text{dB}$ | 约 17.0 位 | 工业低频测量，抖动影响完全淹没于量化噪声下 |
| $10\,\text{kHz}$ | $500\,\text{ps}$ | $90.1\,\text{dB}$ | 约 14.7 位 | 高保真音频采集，需要专用晶振支持 |
| $100\,\text{kHz}$ | $500\,\text{ps}$ | $70.1\,\text{dB}$ | 约 11.3 位 | 16 位 ADC 性能被时钟抖动严重压缩至 11 位！ |
| $100\,\text{kHz}$ | $50\,\text{ps}$ | $90.1\,\text{dB}$ | 约 14.7 位 | 必须选用低相噪 TCXO / 专用时钟发生器 |
| $1\,\text{MHz}$ | $50\,\text{ps}$ | $70.1\,\text{dB}$ | 约 11.3 位 | 超声探伤或雷达中频采样，抖动成为主要噪声源 |
| $1\,\text{MHz}$ | $5\,\text{ps}$ | $90.1\,\text{dB}$ | 约 14.7 位 | 仅昂贵的超低抖动射频时钟源方可达成 |

读表结论：如果在固件中试图对 100 kHz 的中频信号进行 16 位精度采集，而采样定时器的触发时钟来源于片内普通 RC 振荡器或未经抖动滤波的内部 PLL（抖动常常高达数百皮秒），那么无论 ADC 芯片本身指标多么优异，整个系统的有效位数（ENOB）在物理上绝不可能超过 11 位！
这证明了高精度数据采集必须将系统级时钟纯净度与总线流水线设计作为一个不可分割的整体来考量。

当采样率达到 1 MSPS 时，64 样本的数据块每隔 64 µs 就产生一个。
如果系统在 64 µs 内无法完成一次缓冲区切换和代际流转，硬件将直接在下一周期发生数据覆写。
因此，数据采集系统的吞吐量设计不能只看平均 CPU 占用率，必须保障每个阶段的最坏处理时限。

## 8.2 总线矩阵、DMA 引擎与仲裁开销：AHB/AXI 多主设备争用 {#sec-edge.2.8.2}

### 多主设备总线架构与交叉开关矩阵

在现代微控制器与工业 SoC 中，CPU 核心不再是唯一的总线控制者。
为了在多外设并发工况下维持高吞吐，系统内部普遍集成了**多层总线交叉开关矩阵**（Multi-Layer Bus Matrix）。
总线矩阵将多个主设备（Masters）与多个从设备（Slaves）解耦为平行的物理通道。
只要两个主设备访问的不是同一个从设备，它们发起的总线事务便能在同一时钟周期内完全并发推进，没有任何竞争与等待。

下表系统梳理主流计算体系中的总线矩阵架构、通道特征与仲裁策略：

| 总线架构体系 | 典型总线位宽 | 突发传输支持 | 仲裁与冲突机制 | 典型微控制器 / 处理器集成平台 |
|:--|:--|:--|:--|:--|
| **ARM 多层 AHB (AHB-Lite)** | 32 位 / 64 位 | 递增突发 (INCR4/8/16) | 固定优先级 (Fixed) 或轮询 (Round-Robin) | Cortex-M3/M4 (STM32F4, NXP LPC1700, LM3S) |
| **ARM AXI4 (多通道)** | 32 / 64 / 128 位 | 独立读写通道突发，支持乱序完成 | 多级 QoS 优先级标记、通道独立仲裁 | Cortex-M7 (STM32H7), Cortex-A53 (树莓派) |
| **RISC-V TileLink** | 32 位 / 64 位 | 基于消息的突发事务 (Burst/Get/Put) | 树状点对点路由器仲裁、无死锁保序协议 | SiFive FU540 / FE310 / 沁恒 CH32V 系列 |
| **x86 PCIe / 系统总线** | 64 位 / 128 位 | TLP 数据包突发 (Scatter-Gather DMA) | 根联合体 (Root Complex) 权重轮询仲裁 | 工业 PC / 边缘工控机主机总线 |

然而，当 CPU 正在全速执行关键算法（如定点 FFT），其代码或数据频繁访问某块物理内存（如 AXI-SRAM），而高速采集的 DMA 控制器恰好也试图将新样本写入该物理内存时，两个主设备发生碰撞。
此时，总线交叉矩阵的**硬件仲裁器（Arbiter）**必须介入。
仲裁器将强制暂停其中一个主设备的总线请求，向其插入一个或多个等待周期（Wait States），直到另一个主设备释放总线。
如果总线矩阵被配置为“CPU 优先”，且 CPU 正在执行紧凑的密集访存汇编循环，DMA 请求可能被长时间推迟。
外设内部的小容量硬件 FIFO 一旦被后续采样填满，将直接导致转换数据溢出丢失。

### 存储分区物理隔离与链接脚本布局

为了从根本上消除总线仲裁碰撞，系统架构师必须利用微控制器的**非对称多物理 SRAM 分区**：
以典型工业芯片（如 STM32F407）为例，内部包含 112 KB 的主 SRAM1、16 KB 的辅助 SRAM2，以及 64 KB 的核心耦合内存 CCMRAM。
- CPU 的工作栈、全局变量和算法运行集分配在 CCMRAM 或 SRAM1 中；
- 高速 DAQ DMA 缓冲区强制隔离在 SRAM2 中。
由于 SRAM1 与 SRAM2 挂载在 AHB 矩阵的不同从设备端口上，CPU 全速执行计算与 DMA 流式搬运数据走的是平行的内部物理导线，总线仲裁等待恒为 0！

在 GNU 链接脚本中，这一设计通过专用内存段与节区描述实现：

```ld
/* 专用于高速 DMA 数据管道的无竞争内存段定义 */
MEMORY
{
    FLASH (rx)      : ORIGIN = 0x08000000, LENGTH = 1024K
    CCMRAM (rw)     : ORIGIN = 0x10000000, LENGTH = 64K   /* CPU 专属，无 DMA 接入 */
    SRAM1 (rwx)     : ORIGIN = 0x20000000, LENGTH = 112K  /* 常规全局变量与堆栈 */
    SRAM2 (rw)      : ORIGIN = 0x2001C000, LENGTH = 16K   /* DMA 专属缓冲物理分区 */
}

SECTIONS
{
    /* 强制将 DAQ 流式双缓冲放置在 SRAM2，并严格 64 字节对齐 */
    .dma_section (NOLOAD) :
    {
        . = ALIGN(64);
        _s_dma_buffer = .;
        *(.dma_buffers)
        *(.dma_buffers*)
        . = ALIGN(64);
        _e_dma_buffer = .;
    } > SRAM2
}
```

在 C 代码中，缓冲区通过属性关键字声明绑定至该独立物理段：

```c
/* 强制放置于独立 SRAM2 物理分区的双缓冲区 */
__attribute__((section(".dma_buffers"), aligned(64)))
static int16_t g_dma_raw_stream[2 * DAQ_BLOCK_SIZE];
```

通过这一物理隔离布局，CPU 不仅消除了与 DMA 的总线冲突，更确保该缓冲区永远不会与通用堆栈变量发生内存覆写。

### 突发传输与单次传输的效率悬殊

在 AHB 与 AXI 总线上，每次数据传输通常分为**地址阶段（Address Phase）**与**数据阶段（Data Phase）**。
在单次传输（Single Transfer）模式下，搬运一个 16 位样本需要先发送一次地址，再写入一次数据，占用至少 2 个总线周期；若从设备存在等待周期，耗时进一步延长。
而在突发传输（Burst Transfer，如 4 拍、8 拍或 16 拍递增突发）模式下，DMA 仅需在起始发送一次基地址，随后总线硬件自动递增地址并连续完成后续数据的单周期流式写入。

假设系统需要搬运 64 个 16 位采样点（共 128 字节）：
- **采用单次传输（Single）**：总线需要发起 64 次独立的主设备仲裁与地址阶段。在 84 MHz AHB 总线上，累计总线开销至少为 $64 \times 2 = 128$ 个时钟周期（约 $1.52\,\mu\text{s}$）。在此期间，总线被反复加锁与释放，大幅挤压 CPU 的取指带宽。
- **采用 16 拍 32 位突发传输（INCR16 Burst）**：每次突发一次性搬运 64 字节数据。整批数据仅需 2 次突发即可彻底完成，总线开销骤降至约 $2 \times (1 + 16) = 34$ 个周期（约 $0.40\,\mu\text{s}$），总线占用率骤降 **73%**！

因此，高速数据采集驱动必须尽可能配置 DMA 支持外设或内存端的硬件突发模式。
为了支持突发传输，DMA 控制器内部通常集成了专用的硬件弹性 FIFO。

### DMA FIFO 水印阈值配置的权衡艺术

为了在突发传输与防止溢出之间取得最佳平衡，DMA 控制器允许配置**FIFO 水印触发阈值（Watermark Threshold）**：
例如，STM32 传统 DMA 包含 4 个字的内部 FIFO，支持将其配置为 1/4、1/2、3/4 或 Full 水印。
- **配置为 1/4 水印**：只要 FIFO 中积攒了 1 个字的数据，DMA 立即向总线申请写事务。优点是 FIFO 永远保留了 3/4 的安全余量，极端抗总线拥堵；缺点是只能执行单次或极短突发传输，总线开销大。
- **配置为 Full 水印**：必须等 FIFO 彻底积攒满 4 个字后，DMA 才发起一次 INCR4 突发传输。优点是总线效率达到顶峰；致命缺点是一旦此时总线矩阵正在被以太网或 CPU 密集占用，留给 DMA 的缓冲余量为 0！只要外设在此期间再产生一个新样本，DMA 内部 FIFO 立即报硬件溢出故障（FEIF 置位）。
在工业高可靠性设计中，**1/2 水印通常是兼顾突发效率与抗总线抖动能力的最佳平衡点**。

### 控制寄存器与状态位对照

以典型工业微控制器（STM32F4 传统 DMA 控制器与通用寄存器模型）为例，控制流式采集的核心寄存器如下：

| 寄存器偏移 | 寄存器名称 | 核心位域 | 硬件语义与操作约束 |
|:--|:--|:--|:--|
| `+0x00` | DMA_SxCR | `[0] EN` | 流使能位：配置前必须写 0 关闭，并等待硬件确认置 0 |
| `+0x00` | DMA_SxCR | `[8] CIRC` | 循环模式使能：1 为自动回绕，连续采集必须置 1 |
| `+0x00` | DMA_SxCR | `[9] DBM` | 双缓冲模式使能：置 1 时与 CIRC 配合，交替写入两个内存目标 |
| `+0x00` | DMA_SxCR | `[10] CT` | 当前目标指针 (Current Target)：0 代表正在写 Memory 0，1 代表 Memory 1 |
| `+0x00` | DMA_SxCR | `[14:13] MSIZE` | 内存数据宽度：`00`=8位，`01`=16位 (ADC典型值)，`10`=32位 |
| `+0x00` | DMA_SxCR | `[3] TCIE` | 传输完成中断使能：全缓冲填满时产生中断 |
| `+0x00` | DMA_SxCR | `[2] HTIE` | 半传输中断使能：半缓冲填满时产生中断 |
| `+0x04` | DMA_SxNDTR | `[15:0] NDT` | 剩余数据项计数：每次外设请求减 1，写 0 重载 |
| `+0x08` | DMA_SxPAR | `[31:0] PAR` | 外设数据寄存器物理地址 (如 ADC_DR) |
| `+0x0C` | DMA_SxM0AR | `[31:0] M0A` | 内存目标 0 物理地址 (必须 32 位或 Cache 行对齐) |
| `+0x10` | DMA_SxM1AR | `[31:0] M1A` | 内存目标 1 物理地址 (双缓冲模式专用) |
| `+0x14` | DMA_SxFCR | `[7] FEIE` | FIFO 错误中断使能：总线争用导致 DMA 内部 FIFO 溢出时报警 |

在配置 DMA 循环或双缓冲流时，必须严格遵循安全配置序列：
首先清除 `EN` 位，并轮询等待 `EN` 位真正清零；
随后写入外设地址、内存地址与项数；
最后清除所有可能残留的历史中断标志位（TCIF、HTIF、TEIF、DMEIF），再重新置位 `EN`。
若在历史中断标志未清除的情况下启动 DMA，控制器可能在使能瞬间产生虚假中断。

## 8.3 双缓冲与 Ping-Pong 机制：半传输/全传输中断与无锁代际交接 {#sec-edge.2.8.3}

### 为什么需要代际标记（Generation Token）

在双缓冲或循环 DMA 架构中，ISR 与工作任务之间存在一个经典的交接陷阱：
ISR 认为某个缓冲区已经填满并抛出通知，而工作任务可能由于高优先级线程打断，未能及时取出数据。
当下一个半区再次填满时，DMA 回绕并重新开始覆盖前一个半区！

如果软件仅通过一个简单的布尔标志（如 `bool data_ready`）进行通知，两次快速连续的中断将把标志置为相同的值。
工作任务苏醒后，无法分辨自己读取的是刚刚完成的新数据，还是已经被覆写了一半的脏数据。

::: def 缓冲区代际锁（Generation Handoff Contract） {#def-edge.2.8.3.1}
每一个被交付的数据块必须携带全局单调递增的序列号（Sequence Number）与代际标志。
生产者（DMA ISR）在填满缓冲区并完成校验和后，才原子置位就绪掩码。
消费者在读取前必须验证该缓冲区的状态仍处于“未被生产者回收”，读取完毕后显式清除就绪标记。
若生产者发现当前即将写入的缓冲区就绪标记依然被消费者持有，必须立即记录硬件级覆写故障（Overrun），而不是静默覆盖。
:::

### Ping-Pong 缓冲控制器实现

在 `experiments/ch08/daq_core.c` 中，我们实现了带代际序列号与覆盖陷阱的 Ping-Pong 控制器：

```c
typedef struct {
    uint32_t sequence;
    uint32_t timestamp_tick;
    int16_t  samples[DAQ_BLOCK_SIZE];
    uint32_t checksum;
} DaqBlock;

typedef struct {
    DaqBlock buffers[2];
    volatile uint32_t active_buf;     /* 当前由 DMA/ISR 填充的半区: 0 或 1 */
    volatile uint32_t ready_mask;     /* 就绪位掩码: bit0=buf0, bit1=buf1 */
    uint32_t next_seq;
    unsigned overrun_count;
} DaqPingPong;
```

当 DMA 半传输中断触发时，传入当前完成的半区数据与系统时间戳。
ISR 的核心逻辑必须是常数时间 $O(1)$，绝不允许在此处进行复杂的浮点运算或存储写盘：

```c
bool daq_pingpong_isr_step(DaqPingPong *pp, const int16_t *raw_input, uint32_t tick) {
    uint32_t active = pp->active_buf;
    
    /* 核心陷阱检查：该半区是否仍被消费者占用未释放？ */
    if (pp->ready_mask & (1u << active)) {
        pp->overrun_count++;
        return false; /* 致命覆写：消费者未及时消费上一轮数据！ */
    }

    DaqBlock *dst = &pp->buffers[active];
    dst->sequence = pp->next_seq++;
    dst->timestamp_tick = tick;
    for (unsigned i = 0; i < DAQ_BLOCK_SIZE; ++i) {
        dst->samples[i] = raw_input[i];
    }
    dst->checksum = daq_block_checksum(dst);

    /* 发布当前半区为就绪状态 */
    pp->ready_mask |= (1u << active);
    
    /* 切换活动半区，供下一次 DMA 传输使用 */
    pp->active_buf = active ^ 1u;
    return true;
}
```

消费端通过轮询或信号量唤醒后，提取就绪块并校验数据完整性：

```c
DaqResult daq_pingpong_consume(DaqPingPong *pp, DaqBlock *out_block, unsigned *buf_idx) {
    unsigned target = 2;
    if (pp->ready_mask & 1u) target = 0;
    else if (pp->ready_mask & 2u) target = 1;
    else return DAQ_ERR_EMPTY;

    DaqBlock *src = &pp->buffers[target];
    if (src->checksum != daq_block_checksum(src)) {
        return DAQ_ERR_CORRUPT;
    }

    *out_block = *src;
    if (buf_idx) *buf_idx = target;

    /* 消费完毕：原子释放该半区归还给生产者 */
    pp->ready_mask &= ~(1u << target);
    return DAQ_OK;
}
```

这段代码在 ARM Cortex-M3 固件（`firmware/ch08/arm/main.c`）中进行了 128 块连续数据流转验证。
若在变异测试中故意破坏序列号检查或反转比较条件，固件自检将瞬时捕获并触发明确的 FAIL 退出。

### 真实硬件中的 HT 与 TC 中断分发序列

在真实的裸机或 RTOS 驱动中，DMA 控制器通过单一物理中断线向 NVIC 报告事件。
ISR 内部必须精确解复用**半传输标志（HTIF）**与**传输完成标志（TCIF）**：

```c
/* 真实的 DMA 流中断服务例程标准实现模板 */
void DMA2_Stream0_IRQHandler(void) {
    uint32_t isr_status = DMA2->LISR;

    /* 1. 处理半传输中断 (Buffer 0 填满，DMA 正在写入 Buffer 1) */
    if (isr_status & DMA_LISR_HTIF0) {
        /* W1C 清除半传输标志位 */
        DMA2->LIFCR = DMA_LIFCR_CHTIF0;
        
        /* 提取 Buffer 0 并在消费端标记就绪 */
        daq_pingpong_isr_step(&g_dma_pp, &g_dma_raw_buffer[0], get_system_ticks());
        
        /* 通知后台处理任务 (通过 RTOS 信号量或直接任务通知) */
        notify_worker_task_from_isr();
    }

    /* 2. 处理全传输完成中断 (Buffer 1 填满，DMA 已回绕至 Buffer 0) */
    if (isr_status & DMA_LISR_TCIF0) {
        /* W1C 清除全传输标志位 */
        DMA2->LIFCR = DMA_LIFCR_CTCIF0;
        
        /* 提取 Buffer 1 并在消费端标记就绪 */
        daq_pingpong_isr_step(&g_dma_pp, &g_dma_raw_buffer[DAQ_BLOCK_SIZE], get_system_ticks());
        
        /* 通知后台处理任务 */
        notify_worker_task_from_isr();
    }

    /* 3. 错误标志排查 (FIFO 溢出或总线传输错误) */
    if (isr_status & (DMA_LISR_TEIF0 | DMA_LISR_FEIF0)) {
        DMA2->LIFCR = DMA_LIFCR_CTEIF0 | DMA_LIFCR_CFEIF0;
        record_dma_hardware_fault();
    }
}
```

必须注意：清除标志必须写清除寄存器（如 LIFCR / HIFCR）。
严禁在此处进行任何浮点运算、格式化打印或阻塞等待操作。
若 ISR 执行时间超过了半个缓冲区的填充时间，当下一次中断到达时，前一次中断尚未退出，系统将立即出现中断积压与采样覆写。


### SPSC 无锁环形块队列的内存序契约

在 Tier 2 驱动层中，工作任务提取出 Ping-Pong 缓冲区数据后，需要将数据块转存至跨线程的 SPSC（单生产者单消费者）环形块队列中。
许多初学者误以为在单核微控制器上，只要将队列的 `head` 与 `tail` 声明为 `volatile` 即可保证并发安全。
在包含乱序发射、写缓冲（Store Buffer）或编译器指令重排的环境中，这是极其危险的漏洞。

在 `experiments/ch08/daq_core.c` 中，SPSC 队列的入队（Push）与出队（Pop）操作具有严格的内存屏障契约：

```c
/* SPSC 块队列的严格入队实现 */
DaqResult daq_queue_push(DaqBlockQueue *q, const DaqBlock *blk) {
    if (!q || !blk) return DAQ_ERR_PARAM;
    uint32_t cap = (q->capacity > 1 && q->capacity <= DAQ_RING_BLOCKS) ? q->capacity : DAQ_RING_BLOCKS;
    uint32_t next_head = (q->head + 1u) % cap;
    
    /* 1. 检查队列是否已满 (tail 由消费端更新，生产端仅读取) */
    if (next_head == q->tail) {
        q->dropped_blocks++;
        return DAQ_ERR_FULL;
    }
    
    /* 2. 将整个 140 字节的数据块拷贝至当前 head 指向的槽位 */
    q->slots[q->head] = *blk;
    
    /* 3. 内存屏障：确保数据块的所有内存写事务在更新 head 指针前彻底对全局可见！ */
    /* ARM: __asm__ volatile("dsb st" ::: "memory"); */
    /* RISC-V: __asm__ volatile("fence w, w" ::: "memory"); */
    
    /* 4. 更新生产者索引 */
    q->head = next_head;
    return DAQ_OK;
}
```

在上述入队流程中，第 2 步写数据负载与第 4 步更新 `head` 指针之间，必须保证强烈的**存储-存储排序（Store-Store Ordering）**。
如果硬件或优化器将两者的执行顺序颠倒，消费端读取到了新更新的 `head` 指针，随即从该槽位读取数据，而此时数据负载的一半内容还在 CPU 的写缓冲区中尚未写入物理 RAM！
消费端将提取出半新半旧的撕裂数据块。
在 RISC-V 目标机测试（`firmware/ch08/rv32/main.c`）中，每次入队后均显式执行 `fence w, rw` 指令，杜绝微架构写缓冲延迟导致的脏数据外溢。

同理，出队操作必须确保在读取数据负载完毕后，才推进 `tail` 指针：

```c
/* SPSC 块队列的严格出队实现 */
DaqResult daq_queue_pop(DaqBlockQueue *q, DaqBlock *blk) {
    if (!q || !blk) return DAQ_ERR_PARAM;
    if (q->head == q->tail) {
        return DAQ_ERR_EMPTY;
    }
    
    uint32_t cap = (q->capacity > 1 && q->capacity <= DAQ_RING_BLOCKS) ? q->capacity : DAQ_RING_BLOCKS;
    
    /* 1. 从当前 tail 指向的槽位拷贝数据负载 */
    *blk = q->slots[q->tail];
    
    /* 2. 读读/读写屏障：确保数据已完全加载后再更新 tail */
    /* RISC-V: __asm__ volatile("fence r, rw" ::: "memory"); */
    
    /* 3. 更新消费端索引，释放槽位给生产端 */
    q->tail = (q->tail + 1u) % cap;
    return DAQ_OK;
}
```

若将该架构扩展至多生产者多消费者（MPMC）场景，必须引入原子比较并交换指令（CAS，如 ARM 的 `LDREX/STREX` 或 RISC-V 的 `AMO` 扩展）。
然而，CAS 在高冲突工况下会引发持续的自旋重试，产生不可预测的延迟毛刺。
因此在硬实时 DAQ 管道中，**最佳架构始终是保持单生产者（DMA/ISR）与单消费者（处理任务）的一对一 SPSC 解耦拓扑**。

## 8.4 缓存一致性与非时间性流式存储：Cache Invalidate、Clean 与 x86/ARM/RISC-V 屏障 {#sec-edge.2.8.4}

### DMA 与 Cache 一致性的两个方向

在配备了一级数据缓存（D-Cache）的高性能处理器（如 Cortex-M7、Cortex-A53、RV64、x86-64）上，DMA 直接读写物理内存，而不会自动通知 CPU 的私有 L1 Cache。
根据母本《ARM64体系结构编程与实践》第 16 章与第 18 章的规范，必须严格区分两个方向的数据流：

1. **从设备到内存（RX DMA，数据采集接收）**：
   - 目标：ADC/外设通过 DMA 将采样数据写入内存，随后由 CPU 读取。
   - 风险：CPU 内部的 D-Cache 中可能保留了先前该地址处的旧缓存副本。若 CPU 直接读取，将读到过时的脏数据；更致命的是，若该 Cache 行在未来被意外写回物理内存，CPU 缓存的陈旧内容将把 DMA 刚刚写好的新采样数据彻底覆灭！
   - 规则：**在 CPU 读取 DMA 缓冲区之前，必须对该内存区间执行 Cache Invalidate（使失效）操作**。失效操作将强制废弃 Cache 中的所有副本，确保下一次读操作直达物理 RAM。

2. **从内存到设备（TX DMA，数据回放或存储下发）**：
   - 目标：CPU 准备好数据，通知 DMA 读取内存并发送给存储或 DAC 设备。
   - 风险：CPU 最新计算生成的数据可能仍驻留在写回型（Write-Back）D-Cache 中，尚未真正刷入物理 RAM。DMA 直接从物理 RAM 读取，将读到全 0 或历史残余数据。
   - 规则：**在启动 DMA 发送之前，必须对该内存区间执行 Cache Clean（清洗/写回）操作**，强制将脏 Cache 行写回物理存储器。

### 跨架构缓存维护与内存屏障指令对照

| 架构体系 | RX DMA 读前失效指令 | TX DMA 写后清洗指令 | 存储提交屏障 | 非时间性 (Streaming) 存储指令 |
|:--|:--|:--|:--|:--|
| **ARMv7-M (M7)** | `SCB_InvalidateDCache_by_Addr` | `SCB_CleanDCache_by_Addr` | `dsb st; isb` | 不支持非时间性指令，依赖 MPU 属性 |
| **ARMv8-A (A64)**| `dc ivac, Xt` (按物理地址失效) | `dc cvac, Xt` (按物理地址清洗) | `dsb sy` / `dsb ish` | `stnp Wt1, Wt2, [Xn]` (Non-temporal Pair) |
| **RISC-V (Zicbom)**| `cbo.inval (a0)` | `cbo.clean (a0)` | `fence w, w` / `fence io, w` | 扩展规范定义中，当前依赖 PMA 非缓存配置 |
| **x86_64** | `clflush / clflushopt (%rdi)` | `clwb (%rdi)` (仅写回不失效) | `sfence` (写屏障) | `movnti %rax, (%rdi)` / `movntdq %xmm0, (%rdi)` |

### 为什么必须使用按虚拟地址失效（dc ivac）而非按组/路失效（dc isw）

在 ARMv8-A 与 Cortex-M7 体系中，许多初学者试图通过循环遍历 Cache 的 Set 和 Way 来执行全局失效。
在 DMA 数据流转中，**这是极其危险的致命反模式**：
1. **非原子性与外部干扰**：遍历所有的 Set 与 Way 需要成百上千条机器指令。在遍历期间，后台中断或多核线程依然在运行，新的 Cache 行随时可能被重新分配并标记为 Dirty。
2. **多核/多线程漂移**：按 Set/Way 操作仅作用于执行该指令的当前本地物理核心。如果操作系统随后将任务调度至另一个 CPU 核心执行，目标核心的本地 Cache 依然是过时的。
3. **正确做法**：必须使用**按物理/虚拟地址失效（dc ivac, By Address）**指令！它不仅能精准作用于目标 DMA 缓冲区的确切地址范围，而且在多核系统中会自动通过一致性互连总线（如 CCI-400 / CCN-504）向全系统所有 CPU 核心广播失效请求。

### x86-64 非时间性流式存储（Non-Temporal Stores）

在 x86-64 架构下进行多通道高吞吐数据流转（如 100 MB/s 的高速采集卡流向主机内存）时，若使用传统的 `movq` 指令拷贝数据，所有采样的庞大数据将把 CPU 的 L1/L2/L3 缓存迅速填满并冲刷殆尽。
这被称为**缓存污染（Cache Pollution）**。
导致控制算法和操作系统的核心工作集被逐出缓存，引发严重的性能抖动。

x86-64 提供了专用的**非时间性存储指令**（Non-Temporal Stores，如 `movnti`、`movntdq`）：

```nasm
/* experiments/ch08/x86_stream.S */
.global daq_stream_copy_x86
.type daq_stream_copy_x86,@function
/* rdi = 目的地址 (必须 64 位或 128 位对齐), rsi = 源地址, rdx = 64位四字计数 */
daq_stream_copy_x86:
    testq   %rdx, %rdx
    jz      .L_done
.L_loop:
    movq    (%rsi), %rax
    movnti  %rax, (%rdi)    /* 绕过 CPU Cache，直接写入写合并缓冲 (WC Buffer) 与物理内存 */
    addq    $8, %rsi
    addq    $8, %rdi
    decq    %rdx
    jnz     .L_loop
    sfence                  /* 严格写屏障：确保所有流式弱序写操作彻底落入全局物理内存 */
.L_done:
    ret
```

非时间性写入利用处理器的**写合并缓冲区（Write-Combining Buffer）**直接向系统总线批量提交突发写事务，完全不分配任何 CPU Cache 行。
执行流式写入后，必须跟随一条 `sfence` 指令，因为非时间性存储在弱内存序模型下是弱序提交的，必须通过屏障确保对后续消费者立即可见。

### 缓存行伪共享（False Sharing）防御

在定义 DMA 缓冲区与环形队列结构体时，必须防止不同角色的变量落在同一个 Cache 行内部：

```c
/* 致命伪共享错误：DMA 缓冲区与状态变量在同一 Cache 行内 */
struct BadDaqLayout {
    uint8_t dma_rx_buf[48];  /* 48 字节: DMA 正在写入物理 RAM */
    volatile uint32_t state; /* 4 字节: CPU 频繁通过 Cache 读写 */
};

/* 正确隔离设计：强制按 Cache 行边界对齐与填充 */
struct GoodDaqLayout {
    uint8_t dma_rx_buf[64] __attribute__((aligned(64))); /* 独占整整一个 Cache Line */
    volatile uint32_t state __attribute__((aligned(64)));  /* 独立 Cache Line */
};
```

若 `dma_rx_buf` 与 `state` 共享同一个 64 字节 Cache 行，当 CPU 修改 `state` 时，该 Cache 行被标记为 Dirty；随后 DMA 在物理 RAM 中写入了新的采样数据；当 CPU 稍后写回该 Cache 行时，旧的 `dma_rx_buf` 缓存数据将强行覆盖 DMA 的新数据，造成极其隐蔽、难以复现的周期性数据崩溃。


### 写合并缓冲区（WC Buffer）与总线事务打包

为了深入理解非时间性流式存储（Non-Temporal Stores）的底层优势，必须剖析现代高性能处理器（如 x86-64 与高端 ARM/RISC-V 核心）的内部存储子系统：

1. **写回型（Write-Back）缓存的传统开销**：
   - 当 CPU 执行常规存储指令（如 `movq %rax, (%rdi)`）写入一个不在 L1 缓存中的地址时，硬件首先触发一次**写分配（Write-Allocate）**；
   - 内存控制器必须先从外部 DRAM 总线将包含该地址的整整一个 64 字节 Cache 行读取到 L1 Cache 中（产生读总线事务与等待）；
   - 随后 CPU 在 L1 Cache 中修改目标字，并将其标记为 Dirty。
   - 当该 Cache 行稍后被逐出时，又必须通过写事务刷回 DRAM。
   - **后果**：对于纯流式写入的采集数据，CPU 根本不需要读取旧数据，但传统的写分配机制导致每次写入前白白浪费了一次昂贵的外部 DRAM 读总线事务，总线带宽被凭空吞噬了一半！

2. **非时间性存储的微架构通道**：
   - 当执行 `movnti` 或 `movntdq` 时，CPU 硬件识别到该访问带有非时间性提示（Non-Temporal Hint）；
   - 硬件完全绕过 L1/L2/L3 缓存与写分配状态机，直接将 64 位或 128 位的数据写入核心内部专用的**写合并缓冲区（Write-Combining Buffer, WCB）**；
   - WCB 内部包含若干个 64 字节的合并寄存器。当 CPU 连续写入同一个 Cache 行大小的内存区间时，WCB 将零散的写入原子合并为一个完整的 64 字节全行；
   - 一旦整整 64 字节被填满，或者执行了显式内存屏障指令 `sfence`，WCB 直接向系统 PCIe / DDR 总线发起一次单周期的突发全行写事务（Burst Full-Line Write）；
   - **结论**：彻底消除了预取读 DRAM 的开销，消除了 L1/L2/L3 的脏行逐出，将外部内存写带宽压榨至理论物理极限。

在 `experiments/ch08/x86_stream.S` 与 `a64_stream.S` 中，我们分别实现了跨 x86 与 ARM64 的流式非时间性拷贝汇编。
在 x86 汇编中，循环体内使用 `movnti` 连续写入，并在退出循环后紧随一条 `sfence` 指令；
在 AArch64 汇编中，利用 `STP` 寄存器对写入，并在退出后执行 `DSB ST` 保证所有写事务落盘。
这两套汇编例程在本轮实验中均通过了真实的目标机交叉汇编与指令反汇编检验，反汇编结果记录在 `.build/ch08/` 目录下。

## 8.5 存储管道背压与突发滞留：Flash 块擦除暂停与队列深度上界 {#sec-edge.2.8.5}

### 存储介质的突发延迟特性

数据采集系统的终端通常是持久化非易失介质。
各种主流嵌入式存储介质在写入时具有显著的不对称时延：

| 介质类型 | 单页写入典型耗时 | 块擦除 (Block Erase) 典型耗时 | 写入单位 | 擦除单位 |
|:--|--:|--:|:--|:--|
| SPI NOR Flash (W25Q128) | $0.7 \sim 3\,\text{ms}$ | **$40 \sim 400\,\text{ms}$** (扇区擦除) | 256 字节 (Page) | 4 KB (Sector) / 64 KB (Block) |
| SPI NAND / Raw NAND | $200 \sim 600\,\mu\text{s}$ | **$2 \sim 10\,\text{ms}$** | 2 KB / 4 KB (Page) | 128 KB / 256 KB (Block) |
| eMMC / SD Card | $200 \sim 1000\,\mu\text{s}$ | **$5 \sim 50\,\text{ms}$** (内部 GC 垃圾回收) | 512 字节 (Sector) | 依控制器内部映射块而定 |
| 片上内嵌 Flash (eFlash) | $20 \sim 40\,\mu\text{s}$ | **$10 \sim 100\,\text{ms}$** (扇区擦除) | 4 字节 / 32 字节 | 16 KB / 128 KB (Sector) |

绝大多数闪存介质在执行块擦除操作期间，整片芯片处于物理繁忙状态（BUSY 引脚拉低，状态寄存器 WIP 位置 1），期间拒绝接收任何新的编程或读取请求！
在这段长达数毫秒甚至上百毫秒的物理静默期内，前端的 ADC 数据流依然在以微秒级的速率持续涌入。

### 存储队列容量定理与恢复排空条件

::: thm 突发存储队列最小安全容量定理 {#thm-edge.2.8.5.1}
设传感器采样率为 $R_{sample}$（样本/秒），每个样本占用 $W$ 字节，持久化介质的最坏情况写入/擦除阻塞时间为 $T_{stall}^{max}$（秒），单数据块容量为 $S_{block}$ 样本。
则 Tier 2 块队列的绝对最小安全深度 $Q_{depth}^{min}$（块数）必须严格满足：
$$Q_{depth}^{min} \ge \left\lceil \frac{R_{sample} \times T_{stall}^{max}}{S_{block}} \right\rceil + M_{safety}$$
其中 $M_{safety} \ge 1$ 为安全裕量因子，用于补偿任务上下文切换延迟、中断排队延迟与双缓冲代际交接等待。
:::

若队列深度小于此理论下界，在最坏擦除停顿发生时，SPSC 队列必然被写满，后续数据块将被迫丢弃。

除了容量满足 $Q_{depth}^{min}$ 外，系统在擦除恢复后能否恢复稳态，还取决于**排空速率（Drain Rate）**与采样速率的相对关系：
设存储介质在脱离擦除状态后的峰值连续写入吞吐量为 $R_{drain}$（样本/秒）。
若 $R_{drain} \le R_{sample}$，系统在擦除结束后仅能勉强消化当前新产生的数据，此前积压在队列中的 $Q_{depth}^{min}$ 个历史数据块将**永远无法被排空**！
下一次擦除到来时，队列将瞬时发生雪崩式连续溢出。
因此，系统的持续写入带宽必须严格满足盈余约束：
$$R_{drain} \gt R_{sample}$$
清空积压所需的恢复时间为：
$$T_{recovery} = \frac{R_{sample} \times T_{stall}^{max}}{R_{drain} - R_{sample}}$$
在工业系统设计中，两次相邻块擦除之间的时间间隔，必须严格大于 $T_{stall}^{max} + T_{recovery}$。

### 失败案例推导与数字证据

我们在 `experiments/ch08/daq_core.c` 的 `daq_calculate_budget` 中固化了这套数学计算，并在 `test_host.c` 中通过实际模拟执行了正向与负向实验：

- **场景设定**：
  - 单通道 16 位 ADC，采样率 $R_{sample} = 100\,\text{kSPS}$；
  - 单数据块包含 64 个样本，块周期为 $T_{block} = 64 / 100000 = 640\,\mu\text{s}$；
  - 存储介质为 NAND Flash，最坏块擦除时间 $T_{stall} = 5000\,\mu\text{s}$（5 毫秒）。
- **理论计算**：
  - 在 5 ms 停顿期间产生的数据量：$100000 \times 0.005 = 500$ 个样本；
  - 500 个样本折合块数：$500 / 64 \approx 7.81$ 块；
  - 向上取整得 8 块，加 1 块安全裕量，理论最小深度为 **9 块**。
- **仿真与断言验证**：
  - **充分队列测试（深度 = 16 块）**：在第 30 块时注入 8 个步骤（约 5.12 ms）的消费端完全阻塞，队列在此期间动态累积至 8 块就绪；当擦除恢复后，存储消费端在后续连续步骤中全力出队，**丢块数恒等于 0**。
  - **受限队列测试（深度 = 4 块）**：相同数据流与相同 5 ms 擦除停顿，当第 4 块推入后队列被物理打满；主机断言精确捕获到 **丢弃 6 个完整数据块**（共 384 个样本丢失），触发明确的 `OVERRUN DETECTED`。

```text
MODEL pipeline: adequately sized queue (depth=16) sustained 5ms stall with 0 drops
MODEL pipeline: undersized queue (depth=4) dropped 6 blocks during 5ms stall (OVERRUN DETECTED)
MODEL budget: 100kSPS stream + 10ms erase stall requires min 17 blocks queue buffer
```

如果工程师在设计固件时仅凭“RAM 资源紧张”随意分配一个 4 块的小队列，系统在平时低负载或小文件写入时表现正常，一旦遭遇 Flash 跨物理块擦除，就会产生静默丢样。
这种丢样往往随外部温度和 Flash 老化次数而随机漂移，极难在台架测试中通过简单打印定位。


### 具备迟滞特性的动态背压控制状态机（Hysteresis Controller）

在严苛的工业边缘部署中，仅仅依靠增大 Tier 2 队列深度并不总是足够的。
如果外部存储介质由于磨损严重或突发坏块重映射（Bad Block Remapping），擦除暂停时间从正常的 5 ms 意外飙升至 30 ms，任何有限深度的内存队列终将面临枯竭。

为了防止系统在发生极端超限时直接发生不可控的硬崩溃，高安全数据管道必须内置**自适应背压降级与迟滞流控状态机**：

```c
/* 具备高低双水印迟滞特性的背压控制器 */
typedef enum {
    DAQ_FLOW_NORMAL,     /* 正常状态: 全速 100% 原始采样流写入 */
    DAQ_FLOW_DEGRADED,   /* 降级状态: 2:1 抽取下采样或开启有损压缩 */
    DAQ_FLOW_CRITICAL    /* 紧急状态: 丢弃低优先级辅助通道，仅保留安全关键数据 */
} DaqFlowState;

typedef struct {
    DaqFlowState state;
    uint32_t high_watermark_blocks;  /* 高水位阈值: 如 75% 队列容量 */
    uint32_t low_watermark_blocks;   /* 低水位恢复阈值: 如 25% 队列容量 */
    uint32_t degraded_events;
} DaqFlowController;

void daq_flow_control_step(DaqFlowController *ctrl, uint32_t current_occupancy) {
    switch (ctrl->state) {
    case DAQ_FLOW_NORMAL:
        /* 队列堆积超过 75%，存储介质明显遭遇突发阻塞，主动进入降级模式 */
        if (current_occupancy >= ctrl->high_watermark_blocks) {
            ctrl->state = DAQ_FLOW_DEGRADED;
            ctrl->degraded_events++;
            activate_hardware_decimation_2x();
        }
        break;

    case DAQ_FLOW_DEGRADED:
        /* 迟滞特性：必须等队列回落到 25% 安全水位以下，才恢复全速模式 */
        if (current_occupancy <= ctrl->low_watermark_blocks) {
            ctrl->state = DAQ_FLOW_NORMAL;
            restore_full_rate_sampling();
        }
        break;

    case DAQ_FLOW_CRITICAL:
        /* 紧急恢复逻辑 */
        break;
    }
}
```

*微架构迟滞原理*：
若不设置双水印迟滞（例如仅设置单一的 50% 阈值），当队列占用在 50% 附近轻微波动时，控制状态机将在“全速”与“降级”之间发生极其剧烈的高频抖荡（Thrashing）。
每一次状态切换都涉及滤波器重新初始化、采样时钟分频调整与文件格式重新标定，引发二次系统瘫痪。
通过设置 75% 高水位触发降级、25% 低水位才恢复常态，系统获得了一个宽阔的稳定运行安全滞回区间。

## 8.6 比较器亚稳态、闪码与连续码差值排查 {#sec-edge.2.8.6}

### 高速 ADC 内部比较器的物理亚稳态

在核读母本《数据采集基础知识》第 92–96 页关于比较器亚稳态与闪码（Sparkle Codes）的论述中，揭示了高速采样另一层极其隐蔽的硬件失真机制。

在 Flash 架构或高速流水线/SAR 架构 ADC 内部，包含一组高速锁存比较器。
当模拟输入差分电压 $\Delta V_{in}$ 极小、恰好处于比较器判定阈值边界附近时，比较器内部的再生放大器需要经过较长的建立时间才能达到有效逻辑电平。
输出电压随时间的变化关系满足：
$$V_o(t) = A \cdot \Delta V_{in} \cdot e^{t / \tau}$$
其中 $A$ 为前置放大器增益，$\tau$ 为锁存器的再生时间常数。

当采样速率 $f_s$ 极高时，留给比较器建立逻辑电平的时间 $t$ 被严重压缩。
如果输出逻辑在中间未决电平处被数字解码器强行采样，原本连续递增的温度计编码（Thermometer Code）将发生比特位翻转。
例如本应输出 `011` 或 `100` 的信号，由于单比特亚稳态，被错误解码为 `000` 或 `111`。
在数字信号曲线上，这表现为单个孤立的**全量程尖峰毛刺**，被称为**闪码（Sparkle Code）**。

### 连续码差值排查与误码率（BER）计算

根据母本物理第 95 页的测试方法学，若输入信号为频率受控的低频正弦波，在每个采样点之间，理论模拟电压的变化率被严格限制在 1 LSB 以内：
$$f_{in} \le \frac{f_s}{\pi \cdot 2^N}$$
此时，连续两个采样样本 $S_n$ 与 $S_{n-1}$ 之间的差值绝不可能超过 1 LSB 加上高斯噪声容限 $\Delta_{limit}$。

在固件预处理管道中，我们可以部署一段极简的**硬件闪码抑制与误码统计滤波器**：

```c
/* 连续码差值排查与闪码剔除滤波器 */
typedef struct {
    int16_t last_valid_sample;
    int16_t max_allowed_delta;
    uint32_t sparkle_count;
} DaqSparkleFilter;

int16_t daq_filter_sparkle(DaqSparkleFilter *flt, int16_t sample) {
    int32_t diff = (int32_t)sample - flt->last_valid_sample;
    if (diff < 0) diff = -diff;

    if (diff > flt->max_allowed_delta) {
        /* 检测到闪码/孤立尖峰：记录误码并用上一有效样本插值替代 */
        flt->sparkle_count++;
        return flt->last_valid_sample;
    }

    flt->last_valid_sample = sample;
    return sample;
}
```

按照母本公式，整个系统的误码率（Bit Error Rate, BER）定义为：
$$\text{BER} = \frac{E_{sparkle}}{2 \cdot T_{test} \cdot f_s}$$
其中分母中的系数 2 是因为闪码产生跳变与从闪码恢复正常数值时，差值检测器会连续记录两次超限。
这一排查机制在声学定位或地震波检测等对瞬态脉冲极其敏感的应用中，是防御前端硬件比较器缺陷的关键屏障。


### 温度计码解码气泡错误（Bubble Error）与伪格雷码防御

为了从数字逻辑层面彻底看清闪码（Sparkle Code）的产生机理，我们考察典型 3 位全并行 Flash ADC 的比较器解码网络：
- 3 位 Flash ADC 包含 7 个比较器。当输入模拟电压处于第 4 级阶梯时，理论上比较器输出从低到高应为严格连续的温度计码：`0001111`（低 4 位为 1，高 3 位为 0），经逻辑优先编码器转换为纯二进制码 `100`（数字 4）。
- **气泡错误（Bubble Error）的产生**：
  若由于比较器亚稳态、电源噪声或高频走线延迟差异，第 3 个比较器的输出电平建立迟缓，在时钟选通瞬间被判定为 0，而第 4 个比较器由于轻微负失调被判定为 1。比较器输出向量呈现出 `0001011`！
  在连续的“1”序列中间夹杂了一个“0”，如同液体中浮起的孤立气泡，被称为**气泡错误**。
- **灾难性错误编码**：
  如果数字后端采用最简的“检测 0 到 1 跃迁点”逻辑进行二进制编码，该异常向量将同时在第 2 位和第 4 位触发两次跃迁检测，导致输出码发生严重非线性跃变（如从 4 突变为 0 或 7），在波形上产生剧烈的全量程脉冲飞点。

为了防御气泡错误，先进高速 ADC 芯片在硬件层普遍采用**三输入多数表决逻辑（Majority-of-Three Voting）**或**伪格雷码中间折叠层**：
每个比较器的有效输出由其相邻的左右两个比较器共同仲裁决断。
在固件算法层面，若前端芯片没有硬件去气泡电路，数据采集管道必须在 Tier 1 之后紧随连续差值剔除算子（§8.6 滤波器），在进入定点 FFT 或控制闭环前将孤立毛刺彻底抹平。

## 8.7 实验一：主机多级流式管道仿真、背压丢帧与缓存一致性模型 {#sec-edge.2.8.7}

### 实验设计与执行命令

实验代码位于 `experiments/ch08/`，遵循统一自动化测试契约：

```bash
cd edge
bash experiments/ch08/run.sh
```

脚本首先在宿主环境编译并运行 `test_host.c`，使用 AddressSanitizer 与 UndefinedBehaviorSanitizer 杜绝内存越界。
随后编译 ARM 与 RV32 固件并在 QEMU 中执行，最后调用 `run_mutations.sh` 进行变异测试。

| 模块文件 | 测试对象 | 验证手段 | 验证边界与限制 |
|:--|:--|:--|:--|
| `daq_core.c` | Ping-Pong 状态机、SPSC 环形队列、容量预算计算 | 单元自检 + 循环回绕断言 | 标量实现，不替代硬件 DMA 接口 |
| `test_host.c` | 多级流式管道仿真、5 ms 擦除停顿、缓存一致性模型 | 离散步进模拟 + 差值断言 | 模拟器步进时延，非实体总线波形 |
| `x86_stream.S` | x86 非时间性流式存储指令 (`movnti` + `sfence`) | 交叉汇编与指令反汇编 | 宿主 Darwin 环境未动态执行 |
| `a64_stream.S` | AArch64 成对流式写入 (`stp` + `dsb st`) | 交叉汇编与指令反汇编 | 目标架构未动态执行 |

### 核心测试场景与输出判定

1. **Ping-Pong 缓冲交替测试**：
   - 验证 `active_buf` 在 0 与 1 之间交替切换；
   - 验证 `ready_mask` 按位原子发布与消费释放；
   - 验证连续写入两次未消费时，精准触发 `overrun_count` 递增并返回 false。
2. **SPSC 队列容量与满丢弃测试**：
   - 将队列推入至 `capacity - 1` 项，验证占用数精准匹配；
   - 继续推入第 `capacity` 项时，立即捕获 `DAQ_ERR_FULL` 错误并递增 `dropped_blocks`；
   - 连续弹出全部项，验证 FIFO 顺序与最后返回 `DAQ_ERR_EMPTY`。
3. **5 ms 块擦除停顿的充分与不足队列对照**：
   - 深度为 16 的队列，在 5 ms 停顿内吸收 8 个突发块，总丢块数恒等于 0；
   - 深度为 4 的队列，在 5 ms 停顿内溢出，精准报告丢失 6 个数据块。
4. **缓存一致性失效应验**：
   - 在 DRAM 写入 0x99 新数据后，未执行 Invalidate 时读取 Cache 依然得到旧数据 0x11；
   - 执行 Invalidate 后重新读取，成功恢复最新数据 0x99。


### 实验一主机测试完整日志与数值判定核对

在执行 `experiments/ch08/run.sh` 时，主机仿真器输出如下确凿的数值判定证据：

```text

```

日志中的每一行输出均对应严谨的不变量断言（Assertion）：
- 第一行验证 `daq_core_selftest` 中的 22 个边界状态转移断言全部满足；
- 第二行证明在深度为 16 的队列中，经过 100 步模拟流转并经历第 30 步的 8 拍（约 5.12 ms）擦除冻结后，所有生产数据被完整消费且零丢块；
- 第三行证明将深度压缩为 4 后，相同测试流程捕获到 6 块丢失，精准验证定理 8.5.1；

所有测试均在 Clang ASan 与 UBSan 的内存影子监控下运行，排除了任何堆栈越界与未定义算术行为。

## 8.8 实验二：ARM Cortex-M3 与 RV32 目标机流式固件及变异回归 {#sec-edge.2.8.8}

### 固件架构与执行流程

本实验提供两个独立的裸机目标机固件，分别在 QEMU ARM Cortex-M3 与 QEMU RV32IM 虚拟平台上执行真实的机器指令。

- **ARM Cortex-M3 固件** (`firmware/ch08/arm/`)：
  - `start.S`：初始化异常向量表，将 `.data` 段从 Flash 拷贝至 RAM，清零 `.bss` 段。
  - `main.c`：运行 `daq_core_selftest()`，随后启动一个包含 128 个数据块的端到端流式管道循环。
  - 模拟 DMA 将合成采样推入 Ping-Pong 缓冲区；工作任务弹出缓冲区并校验 16 位累加校验和；随后将数据块推入 SPSC 队列并在消费端逐一验证序列号的绝对连续性。
  - 成功完成 128 块流转且零丢块后，通过 Semihosting 打印 `ARM DAQ PASS: Ping-Pong DMA buffers, SPSC queue, checksum, 128 blocks` 并退出 0。

- **RV32IM 固件** (`firmware/ch08/rv32/`)：
  - `start.S`：设置全局指针 `gp` 与栈指针 `sp`，清零 `.bss` 段。
  - `main.c`：运行核心自检，随后执行 64 块带显式 `fence w, rw` 内存屏障的流式队列写入与弹出。
  - 验证存储容量预算算法在 200 kSPS 与 4 ms 停顿参数下的输出是否严格等于 14 块。
  - 成功后通过 UART0 打印 `RV32 DAQ PASS: SPSC block queue, FENCE ordering, budget verification` 并向 Syscon 端口（`0x100000`）写入 `0x5555` 正常退出。

### 破坏性变异测试（Negative Testing）

按照严谨的工程验证规范，测试套件不仅要证明“代码在正常情况下通过”，更必须证明“当代码注入关键缺陷时，测试能立即捕获并拒绝”。

`experiments/ch08/run_mutations.sh` 实现了两项目标机级破坏性变异：

1. **ARM 变异：颠倒序列号有效性检查**：
   - 在临时构建目录下生成 `arm_bad_seq.c`，将验证比较条件反转；
   - 重新编译、链接并启动 QEMU ARM；
   - 目标机在处理第 0 块数据时立即判定失败，执行 `bkpt 0xab` 输出 `ARM DAQ FAIL` 并以退出码 1 异常终止；
   - 脚本断言检测到退出码 1，输出 `MUTATION PASS: ARM sequence mismatch detected, explicit FAIL exit=1`。

2. **RV32 变异：破坏容量预算算法**：
   - 在临时构建目录下生成 `rv_bad_budget.c`，故意反转预算校验条件；
   - 重新编译、链接并启动 QEMU RV32；
   - 目标机在启动第一周期判定预算不匹配，向 Syscon 端口写入 `0x13333` 触发异常终止；
   - 脚本断言检测到退出码 1，输出 `MUTATION PASS: RV32 budget calculation mutation detected, explicit FAIL exit=1`。

这两项变异均在隔离的 `.build/ch08/mutations/` 目录下完成，没有污染任何原始工程源文件。


### 实验二目标机固件日志与底层退出协议

在调用 `experiments/ch08/run_firmware.sh` 时，宿主脚本启动 QEMU 仿真环境并捕获控制台输出：

```text
==> [Ch08] 编译并运行 ARM Cortex-M3 与 RV32 目标机 DAQ 流式固件...
ARM DAQ PASS: Ping-Pong DMA buffers, SPSC queue, checksum, 128 blocks
RV32 DAQ PASS: SPSC block queue, FENCE ordering, budget verification
==> [Ch08] 运行 DAQ 固件破坏性变异测试...
MUTATION PASS: ARM sequence mismatch detected, explicit FAIL exit=1
MUTATION PASS: RV32 budget calculation mutation detected, explicit FAIL exit=1
==> [Ch08] 实验验证全部通过！
```

两套裸机目标固件分别采用了平台标准的无操作系统退出机制：
1. **ARM Cortex-M3 Semihosting 协议**：
   通过内联汇编 `bkpt 0xab` 向仿真器注入系统调用。寄存器 `r0` 传入操作码 `0x20`（`SYS_EXIT`），`r1` 传入参数块指针（包含应用退出参数 `0x20026` 与退出码 0）。
   当发生任何校验和不匹配、块序列跳跃或丢块时，固件执行 `finish(1)`，QEMU 进程以退出码 1 终止并被宿主测试脚本捕获。
2. **RV32IM Syscon 硬件电源控制协议**：
   在 QEMU RISC-V `virt` 平台上，物理地址 `0x100000` 映射为虚拟机的电源与系统控制寄存器。
   固件通过 MMIO 写入 `0x5555` 触发虚拟机正常下电关机（宿主返回退出码 0）；若发生自检失败，则写入 `0x13333` 触发故障断电，宿主返回退出码 1。
这两套退出协议确保了测试断言直接由目标机器代码在硬件虚拟层执行，彻底杜绝了依靠外部打印“假字符”冒充测试成功的虚假验证。

## 8.10 本章陷阱 {#sec-edge.2.8.10}

::: errata 本章陷阱

1. **在每次 ADC 采样完成时使用单一全局变量传递数据**：
   - 现象：高采样率下波形严重畸变，大量采样点丢失或重复。
   - 原因：CPU 处理速率存在任务切换抖动，单一全局变量在被消费前即被下一次硬件采样覆写。
   - 修复：强制使用硬件 DMA 双缓冲（Ping-Pong）或循环缓冲交接。

2. **DMA 缓冲区与 CPU 共享变量落在同一个 Cache 行内（伪共享）**：
   - 现象：系统偶尔出现随机数据块损坏或状态标志锁死，难以复现。
   - 原因：DMA 写入物理 RAM 时，CPU 写入邻近的共享变量并回写脏 Cache 行，覆盖了 DMA 刚刚写好的新数据。
   - 修复：所有 DMA 缓冲区必须使用 `__attribute__((aligned(32)))` 或 `aligned(64)` 严格独占 Cache 行。

3. **在 RX DMA 启动后、CPU 读取前遗漏执行 Cache Invalidate**：
   - 现象：CPU 读出的采样数据全部是全 0 或历史残余波形，示波器测量 ADC 引脚电平完全正常。
   - 原因：CPU 命中了 L1 数据缓存中的陈旧副本，没有从物理 RAM 重新读取 DMA 写入的新数据。
   - 修复：在 CPU 读取已就绪的 DMA 半区之前，显式调用物理地址 Cache Invalidate 维护指令。

4. **在 TX DMA 启动前遗漏执行 Cache Clean**：
   - 现象：存储器或 DAC 设备收到的数据包内容错乱，大部分是未初始化的全 0。
   - 原因：CPU 计算生成的数据依然滞留在写回型 D-Cache 中，未刷新至物理 RAM。
   - 修复：在写寄存器启动 DMA 发送之前，显式调用 Cache Clean 并在其后插入 `DSB ST` 屏障。

5. **存储写队列深度未考虑 Flash 块擦除时间**：
   - 现象：系统运行几十秒后突发丢帧或数据断流，且丢帧点始终位于 Flash 跨物理块边界时刻。
   - 原因：Flash 块擦除期间总线挂起 5~50 ms，固件设置的队列深度无法容纳停顿期间积累的连续采样流。
   - 修复：根据定理 §8.5.1，按最坏块擦除时间与采样带宽重新计算最小安全队列深度 $Q_{depth}^{min}$。

6. **在没有关 DMA 的情况下直接动态修改 DMA 缓冲区基地址**：
   - 现象：系统抛出 HardFault 或 DMA 传输错误中断（TEIF 置位）。
   - 原因：绝大多数微控制器 DMA 控制器在 `EN=1` 运行期间禁止改写配置寄存器。
   - 修复：必须先写 `EN=0`，轮询等待硬件确认置 0，清除历史标志后方可修改基址并重新使能。

7. **在双缓冲模式中用普通布尔值替代代际序列号**：
   - 现象：长时间高负载运行下，后台存储偶尔存入重复的历史块，总采样点数偏少。
   - 原因：若两次 DMA 中断之间工作任务未能及时响应，布尔标志无法区分当前缓冲区是否已被覆写。
   - 修复：每个数据块必须内嵌单调递增的 `sequence` 编号并在消费前执行校验和检验。

8. **误将 x86 普通 `mov` 拷贝用于数十兆字节的实时数据流**：
   - 现象：开启数据采集后，操作系统的实时控制回路或 GUI 界面出现显著的周期性卡顿。
   - 原因：连续的大容量内存拷贝导致 CPU L1/L2/L3 缓存被彻底污染，关键热点指令和数据被逐出。
   - 修复：改用非时间性流式存储指令（`movnti` / `movntdq`），并在末尾执行 `sfence` 提交。

9. **在 RISC-V 平台流式队列写入中遗漏内存屏障 `FENCE`**：
   - 现象：多核或乱序核心下，消费端读取到了已更新的 `head` 指针，但读出的数据内容是未初始化的脏数据。
   - 原因：编译器或弱序微架构将数据负载写入与索引指针更新进行了指令重排。
   - 修复：在写入数据块之后、更新队列头指针之前，必须插入 `fence w, w` 明确写屏障。

10. **忘记清除 DMA 传输完成（TC）与半传输（HT）中断标志**：
    - 现象：一旦产生第一次 DMA 中断，系统便永久陷入 ISR 无法返回主任务，主循环被彻底饿死。
    - 原因：NVIC 识别到中断引脚电平未释放，持续重复拉起中断服务程序。
    - 修复：ISR 入口或出口必须通过写清除寄存器（W1C）显式清零对应的 `TCIF` / `HTIF` 标志位。

11. **忽视高速比较器亚稳态导致的闪码（Sparkle Codes）**：
    - 现象：高速采样信号的频谱底噪异常抬高，时域波形上偶发单点的全量程尖峰毛刺。
    - 原因：输入信号在阈值附近导致高速比较器输出未决，二进制解码产生错误跳转。
    - 修复：在数据预处理链路中部署连续码差值滤波器，识别并抑制超过极限变化率的闪码。

12. **agent 错误案例：使用栈上局部大数组作为 DMA 目标缓冲区**：
    - 现象：程序运行若干个采样周期后发生内存踩踏或不可预测的死机崩溃。
    - 原因：智能体代码在函数内部定义了 `uint16_t dma_buf[1024]`，并将该指针传给 DMA 启动传输；一旦函数返回，栈帧被释放并被后续函数复用，而后台 DMA 依然在往该物理内存持续写入数据！
    - 修复：所有 DMA 缓冲区必须具有静态存储期（`static` 或全局变量），或者在专用的堆内存池中静态预分配并锁定。

:::

若此时保持队列深度为 16，原本能通过 5 ms 停顿的系统将立即报告溢出并丢弃数据块。
这直接证明了块容量、采样率与擦除停顿时间的强耦合约束。

进阶实验：尝试在 `test_host.c` 中将擦除停顿时间从 5 ms 逐步延长至 15 ms。
观察队列峰值占用（High Water Mark）如何线性爬升，并在何时击穿 16 块的物理容量上限。
同时可修改消费端的排空倍率 $R_{drain} / R_{sample}$，观察擦除恢复后队列积压完全清零所需的物理恢复步数。
当排空倍率接近 1.0 时，恢复时间呈双曲线发散，直观印证定理 8.5.1 的稳态判据。
