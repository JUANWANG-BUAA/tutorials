# 《Linux 系统与内核》写作总则

> 本文件是**所有作者（人或代理）的共同契约**。动笔前先读完；每章交付前按 §9 自检。

## 1. 这本书的定位

一本**面向有 C 基础、用过 Linux 但知识碎片化**的读者的系统教程。目标是把「命令行 → 系统编程 → 内核 → 网络 → 云原生」连成一条路径，并用真实项目压成工程能力。

不是翻译，不是读书笔记，不是 API 手册。**每一节都要回答一个具体问题**，并用路径、边界、证据三样东西支撑。

## 3. 篇幅与密度

| 章类型 | 目标行数 | 说明 |
|:--|:--|:--|
| 普通章（第 0/1/4/5 篇） | 380–550 行 | 4–7 个 H2 小节 |
| 重点章（第 2/3 篇） | 500–700 行 | 6–9 个 H2 小节 |
| 项目章 | 1200–2200 行 | 按 Stage 组织，含完整核心代码 |

**密度要求**：不写「本章将介绍……」这类空话；每 15–25 行至少有一个信息点（事实、代码、命令、图、表、边界）。禁止为凑行数重复。

## 4. 语言与语气

- 中文为主，术语首次出现给英文与缩写：`写时复制（copy-on-write, COW）`。
- 第二人称「你」，但不用「小伙伴们」「让我们」。
- 句子短。一段只讲一件事。避免「综上所述」「值得注意的是」滥用。
- 结论要带条件：「在 Linux 6.8 上」「对普通文件」「除非 `O_DIRECT`」。
- 不写绝对化断言；把「总是/一定/绝不」换成可验证的表述。
- 代码注释用中文，变量名用英文。

## 5. 语义盒用法

| 类型 | 用它讲什么 | 每章数量 |
|:--|:--|:--|
| `def` | 精确定义、接口语义、结构 | 2–5 |
| `thm` | 可证明的结论、保证、边界 | 0–3 |
| `ex` | 手算、代码走查、故障复盘 | 1–3 |
| `intuition` | 白话解释「为什么」 | 每个难点后 1 个 |
| `method` | 步骤、清单、排障顺序 | 1–3 |
| `errata` | 常见误解、版本差异、陷阱 | 1–3 组，每组 3–6 条 |
| `think` | 设计取舍、开放问题 | 0–2 |
| `note` | 延伸、历史、工具 | 0–3 |
| `proof` | 推导（可折叠） | 按需 |
| `sol` | 习题答案（可折叠） | 每个自测 |

规则：

- 盒子标题格式：`::: def 定义 2.2.1 · 文件描述符 {#def-2.2.1}`；
- 编号手工写全，全书唯一；锚点必须与编号一致；
- `ex`/`thm`/`method` 内可嵌 `proof`/`sol`，**不要**在 `proof` 里再嵌盒子；
- 盒子必须平铺闭合：先关内层，再关外层；连续空行不要出现在盒子边界。

## 6. 代码规范

- 语言：C17 + POSIX.1-2008；内核代码以 Linux 6.8 为准。
- 用户态编译：`cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -g`。
- 每个示例必须**能编译**（除非明确标注伪代码）。不能编译的片段要标 `text` 而不是 `c`。
- 错误处理不能省：检查返回值，处理 `EINTR`/短读/短写/`errno`。
- 资源清理用 `goto cleanup` 或清晰的分支；不要泄漏 fd/内存。
- 代码块前用一句话说明「这段在做什么」，块后说明「关键行/预期输出」。
- 不贴大段内核源码；只保留能说明路径的 5–25 行，并标注文件与函数。
- 命令示例用 `bash` 块；真实会话用 `terminal` 块（见 §7）。

## 7. 终端、表格、图

### 终端

```html
<div class="terminal" data-title="bash · ubuntu 24.04">
<pre><span class="p">$</span> uname -r
6.8.0-xx-generic
<span class="p">$</span> ss -lnt | head
State  Recv-Q Send-Q Local Address:Port
LISTEN 0      4096   0.0.0.0:22</pre>
</div>
```

用 `<div class="terminal">` 时，内部 Markdown 不解析；只放纯文本与 `<span>`。

### 表

- 表头必须有单位或说明；数值列右对齐（Markdown 用 `---:`）。
- 对比表用 `class="compare"`，系统调用表用 `class="syscall"`。
- 表后需要一句「这张表说明什么」，不要放养。

### 图

- 图由 `tools/build_figures.py` 生成，页面用 `{{#include ../assets/figures/<name>.md}}` 引入；
- 每张图必须有 `<title>`、`<desc>`、`<figcaption>`；
- 图后必须有一段「读图」文字（图注已含「读图：」，正文再补一句结论）；
- 没有合适生成图时，用 `<pre class="layout">` 或 `<pre class="tree">` 画 ASCII 布局，不要硬凑图片；
- 图内文字 ≥ 9px，颜色只用 CSS 变量。

## 8. 交叉引用与链接

- 同篇：`[2.3](ch03.md)`；跨篇：`[3.12](../part3/ch12.md)`；项目：`[项目 A](../projects/pa.md)`。
- 锚点：`[定义 2.2.1](ch02.md#def-2.2.1)`；也可写 `[@def-2.2.1]`。
- 不链接到不存在的页面；构建后跑链接检查。
- 母本引用只写「母本对应」表，不写页码（版本不同页码会漂）。

## 9. 交付前自检

1. `mdbook build` 通过（在 `linux/` 下）；
2. 本章行数在目标区间；
3. 每个 H2 有编号，编号与文件名/章号一致；
4. 至少 1 张图或 1 个布局图、2 个代码/命令块、1 组 `errata`、1 组自测；
5. 盒子全部闭合，锚点唯一；
6. 所有代码能编译（至少 `cc -fsyntax-only`）；
7. 没有 TODO/占位符/「本章正在编写」；
8. 末尾有「母本对应」与「下一站」。

## 10. 禁止事项

- 禁止大段摘录母本原文；用自己的话重写，例子尽量自己设计。
- 禁止把 API 手册抄成列表；每个 API 要讲「什么时候用、失败是什么、和谁容易混」。
- 禁止无版本的绝对断言；禁止「据说」「网上说」。
- 禁止在正文里写「如图片所示」而不给读图结论。
- 禁止用 emoji 装饰正文。
- 禁止修改 `SUMMARY.md`、`book.toml`、`theme/`、`tools/`（除图生成脚本外）。
