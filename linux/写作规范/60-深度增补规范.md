# 深度增补规范（第三轮）

> 背景：第一轮做到了「章级覆盖 0 缺口」，但单章 400–700 行，面对 Kerrisk 1200 页、奔跑吧 758 页的母本，深度不足。本轮目标不是再加「覆盖率」，而是**逐章把知识点讲透**。
> 判定标准不是行数，而是：读者读完这一章，能否不看原书就说出该章每个 API/机制的语义、边界、失败模式、内核路径，并写出可运行代码。

## 2. 每章必须补到的「深度六件」

### 2.1 API/机制总表

每个系统调用/接口一张表，列：

- 签名与头文件；
- 参数（尤其 flags/struct 字段）逐位/逐字段解释；
- 返回值（成功/失败/短读/0/部分写）；
- `errno` 清单（该 API 真实会返回的，不要泛泛写「失败」）；
- 与相邻 API 的区别/选择。

### 2.2 内核路径

用户态 API → glibc 包装 → syscall → 内核函数 → 数据结构 → 驱动/设备。标文件与函数（Linux 6.8），只贴 5–20 行关键源码。

### 2.3 可运行代码

每章至少 3 个完整程序（不是片段），覆盖：

- 正常路径；
- 至少两个错误/边界路径（EINTR、短读/短写、权限、fd 耗尽、O_APPEND 竞争、mmap SIGBUS、信号打断等）；
- 一个「观测/验证」程序或脚本。

全部用 `-std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror` 编译；代码块前说明「这段验证什么」，后说明「预期输出/关键行」。

### 2.4 实验与证据

至少 2 个 `strace`/`/proc`/`perf`/`bpftrace` 实验，给命令、预期输出、如何读。不要只写「可以用 strace 看」。

### 2.5 边界与陷阱

每章至少 8–15 条 `errata` 级别的坑，按「现象 → 原因 → 修复」写；包含版本差异（Linux 6.8 vs 4.x/5.x、glibc/musl、NFS、容器）。

### 2.6 结构体/字段/常量

涉及结构体的章，给字段表（类型、含义、谁维护、何时变）；涉及 flags 的章，给位表。不要只写「详见 man」。

## 3. 逐章写法

- 保留现有 `# x.y 标题`、`chapter-index`、已有 H2；**在合适位置插入新的 H2/H3**，编号延续（如 2.2.9、2.2.10），锚点唯一。
- 每个新 H2 开头一句话说明「这一节回答什么问题」，不要「本章将介绍」。
- 原有内容不删除、不改写结论；发现错误可在原处修正并注明。
- 每章末尾保留「母本对应」「下一站」；新增内容若对应母本小节，在母本表加行。
- 代码、表格、命令优先；解释只写「为什么/边界」，不写教科书式铺垫。

## 5. 交付前自检

1. `wc -l` 达到目标区间；
2. `cc -fsyntax-only` 或实际编译新增代码；
3. `python3 tools/check_book.py` 无新增问题；
4. `mdbook build` exit 0，页面级 WARN 不增加；
5. 新增 H2 编号连续、锚点唯一；
6. 每个新增 API 有语义/返回值/errno/例子；
7. 报告里列「新增 H2 清单 + 代码清单 + 未实测项」。

## 6. 禁止

- 禁止用「综上所述/值得注意的是/我们可以看到」凑行数；
- 禁止把同一段话换个说法重复；
- 禁止只给 API 列表不给失败语义；
- 禁止把内核源码整段粘贴；
- 禁止为了行数删掉原有表格/例子。

## 7. 多架构 × 多语言 variant 写法

页面里用：

```html
<div class="variant" data-arch="x86-64" data-lang="asm">

```asm
...
```

</div>
```

- `data-arch`：`x86-64` / `arm64` / `riscv64` / `all`
- `data-lang`：`c` / `rust` / `asm` / `all`
- 同一页可有多组；`theme/js/variants.js` 注入页面顶部切换器，选择写入 `localStorage`。
- 每个 variant 的 fenced code 会被正常高亮/复制；不要在一个 variant 里再嵌 variant。
- 只给「确实存在差异」的代码做多版本；纯算法题不必硬凑三架构。
- 新增 variant 后必须 `mdbook build`，并在 `book/part1/chXX.html` 里确认渲染成 `<pre><code>`。
