# Linux 教材化改造总纲（2026-10-29）

> 本文件是 Linux 卷「教材化改造」的施工图。与 `00-写作总则.md` 冲突时，以本文件为准；00 继续管代码、盒子、链接、图的底线。改造按篇推进，不要求一轮改完 85 章。

## 1. 目标读者与四个问题

目标读者：有 C 语言基础、但**非科班或基础碎片化**的本科生和研究生；用过 Linux，却没有系统学过操作系统、组成原理和计算机网络。

要解决的四件事：

1. **新手不友好**：默认读者懂太多。改为先给场景、再给概念；术语第一次出现就解释；每节开头说清「这一节回答什么」。
2. **阅读不友好**：一章一页 1000–2000 行，打开就劝退。改为「章总览 + 单元路线 + 每节小结 + 章末五件套」，让读者随时知道自己在哪。
3. **主线不清晰**：18 个 H2 平铺，读者不知道哪几节是一组。改为每章一条主线，每节标注它在主线中的位置。
4. **原著遗漏多**：5 份核查报告的 B 表仍有约 60–73 条实质漏节。改为每节重写前核读母本对应页，把 B 表条目作为该节验收项。

非目标：

- 不在一轮里重写全部 85 章；按篇、按章推进。
- 不把书改成 API 手册；不以行数或盒子数量作为唯一验收。
- 不引入新依赖，不改共享 `tools/`、`shared/theme/`、`theme/`。
- 不为了「教材化」删掉原有的边界、版本条件、实测标注。

## 1.1 母本优先级：Kerrisk 与 CSAPP 是主干

改造不是「五本书平均参考」。每篇先立主干，再用其他书补细节：

| 篇 | 第一主干 | 第二底座 | 补充与对照 |
|:--|:--|:--|:--|
| 第 0 篇 命令行与 Shell | **Kerrisk** 第 1–2 章（内核/用户态、系统调用、fd 模型） | **CSAPP** 第 1、10 章（hello 程序、I/O、fd 表） | 鸟哥、Shotts、shell-book 补命令与发行版操作 |
| 第 1 篇 计算机系统 | **CSAPP** 第 1–12 章 | **Kerrisk** 第 7、24–27 章（内存、进程） | OSTEP 补 OS 理论，李治军补实现视角 |
| 第 2 篇 系统编程 | **Kerrisk** 全篇 | **CSAPP** 第 8–12 章（异常、VM、I/O、并发） | 鸟哥补工具，OSTEP 补理论 |
| 第 3 篇 内核 | **奔跑吧 Linux 内核** / OSTEP | **CSAPP** 第 9 章（虚拟内存） | **Kerrisk** 第 7、24–27、49、62、64 章补用户态接口与边界 |
| 第 4 篇 网络 | **深入理解 Linux 网络** / 谢希仁 | **CSAPP** 第 11 章（网络编程） | **Kerrisk** 第 56–63 章补 socket API |
| 第 5 篇 云原生 | **深入理解 Linux 网络** + 内核书 | **Kerrisk** 第 28、39 章（进程、能力） | CSAPP 第 9 章补地址空间 |

写作时的顺序：

1. 先读**第一主干**的对应页，确定这一节必须讲清的机制、API、边界。
2. 再读**第二底座**的对应页，找「非科班读者缺的那一层」：CSAPP 的程序/硬件视角，或 Kerrisk 的 API/错误语义。
3. 最后用补充书补命令、发行版差异、历史与淘汰内容。
4. 正文里不写「Kerrisk 说」「CSAPP 说」；把结论消化成自己的讲解，来源只放章末「母本对应」表。

判定标准：如果一节只读了鸟哥或只读了博客，就不算完成；至少要能说出「Kerrisk 在这节讲了哪几个 API/errno，CSAPP 在这节给了哪张图或哪条程序路径」。

## 1.2 Linux 实测环境（2026-10-29 起可用）

本书的正文基线是 Ubuntu 24.04 + GNU 工具，而开发机是 macOS。以前只能写「本机未实测」，现在有真的 Linux：

```bash
ssh ubuntu24          # Parallels Ubuntu 24.04.5 LTS，aarch64
```

已核实的版本与能力（2026-10-29 实测）：

| 项 | 值 | 对写作的意义 |
|:--|:--|:--|
| `grep` | GNU grep 3.11 | `grep -P` 可用；BRE 的 `a\+` 能匹配 |
| `sed` | GNU sed 4.9 | `-i` 可以不带后缀且不生成备份；`2~5` 步长地址可用 |
| `awk` | **mawk 1.3.4**（`gawk` 默认未装） | 讲 `gensub`、`PROCINFO["sorted_in"]`、`-i inplace` 之前必须先装 gawk 或改口径 |
| `bash` | 5.2.21 | 与章导语的 5.2 一致；macOS 本机是 5.3.20，两套口径要分开写 |
| 内核 | `7.0.0-38-generic`，cgroup v2（`cgroup2fs`），根文件系统 ext4 | 信号、`flock`、ACL、capability、`/proc`、namespace、cgroup 都能真跑 |
| 已装工具 | `strace`、`lsof`、`perf`、`getfacl`/`setfacl`、`getcap`/`setcap`、`ip` | 0.3/0.4/0.8 那些「需 Linux 主机」的实验现在有真输出 |
| **sudo** | **需要密码，自动化不可用** | 派单必须写清特权边界：`mkfs`/`losetup`/`mount`/`fdisk`/`mdadm`/`lvcreate`/`apt install`/`dpkg -i`/改 `/etc` 全部禁止；只能 root 看到的证据写「需 root，本机未实测」并给命令 |
| 磁盘 | `/dev/sda2` ext4，约 64 GiB，已用 42%；inode 4128768、用 10% | 免特权可读的 `lsblk`/`df -i`/`findmnt`/`/sys/block/*` 都是真证据 |

| systemd | 255.4-1ubuntu8.18，**`systemctl --user` 与 `journalctl --user` 免特权可用** | 0.12 的 unit/依赖/重启策略实验可以做在用户实例上，不碰系统实例 |
| 网络观测 | `ip`、`ss`、`dig`、`nslookup`、`resolvectl`、`nc`、`curl`、`wget`、`mtr` 可用；`tcpdump` 需 `CAP_NET_RAW` | 0.13 的观测类命令能真跑；抓包按「需特权，本机未实测」处理，改用 `ss -ti`/`nstat` 作证据 |
| 未安装 | `gawk`、`shellcheck`（`fio`/`bc` 等待逐章确认） | 引用这些工具的特性前必须先 `command -v`，没有就标未实测，不许装包 |

派单时的规矩：

1. 凡是 Linux 专有行为（GNU 工具选项语义、`/proc`、信号递送、ACL、capability、cgroup、systemd），**优先在 `ubuntu24` 上跑**，把「本机未实测」降级为「macOS 未实测，Ubuntu 24.04 实测如下」。
2. 报告里注明是在哪台机器上跑的；BSD 与 GNU 结果不同的，两套都留，别只写一套。
3. VM 是共享资源：用完把 `/tmp` 里自己建的文件删掉，不改系统配置（要装包先问用户）。**临时文件必须以「篇+章」双位前缀命名**：`lab<篇>c<章>_`，例如第 0 篇 0.12 用 `lab0c12_`、第 1 篇 1.2 用 `lab1c02_`。2026-10-29 曾因两章都用 `lab12_` 前缀而在同一台 VM 上发生命名撞车风险（`lab12_a.c` 同时可能是 0.12 与 1.2 的实验文件），派单必须显式写清前缀。
4. 已经由此翻案的一条：`[a-z]` 在 glibc 的 `en_US.UTF-8` 下**没有**把 `B` 算进去（Ubuntu 24.04 实测只匹配 `a b`），旧稿里「glibc 按 collation 展开会包含 B」属推测，写作时不要再当结论用。

## 2. 一章的页面结构

每章由七页组成，全部放在 `src/partN/`：

```text
chXX-overview.md    章总览（SUMMARY 里该章的入口）
chXX.md             正文（逐节重写）
chXX-summary.md     章末总结
chXX-recall.md      闭卷回忆卡
chXX-exercises.md   分层习题（A 概念 / B 推理 / C 实操，全解）
chXX-checklist.md   学习目标自检表
chXX-errata.md      本章勘误与版本注记
```

- SUMMARY 中章条目指向 `chXX-overview.md`，正文与五件套作为子条目缩进排列。
- 总览只回答「这一章讲什么、按什么路线走、每节问什么」，不重复正文结论。
- 总结负责「每节一览（核心问题 / 关键结论 / 典型陷阱）+ 一条主线 + 看到问题先选工具」。
- 自检表接管原来的「本章出口检查」；正文不再保留十几行的出口检查表。
- 勘误页只收本章的版本敏感事实、常见误解、与母本/课件的差异；正文里的 `errata` 盒保留。
- 正文页只保留：导语、各节、母本对应、下一站。不再堆章末清单。

规则：

- 每节开头第一句必须是「这一节回答：……」，不要用「本章将介绍」。
- 每节至少一个具体例子（命令、输出、代码或故障）；例子先于抽象总结。
- 每节最多一个比喻；比喻必须能解释机制，不能只装饰。
- 每节结尾必须有「小结」和「即时自测」；自测 2–4 题，覆盖记忆、辨析、应用、迁移中的至少三类。
- 盒子配平：`::: def` 与 `:::` 成对；`::: method` 里套 `::: sol` 时先关 `sol` 再关 `method`。
- 显式锚点沿用原编号（`sec-0.1.3`、`def-0.1.3`），全书唯一；不新建两套编号。
- 正文里不写「母本」「本轮」「门禁」「证据链」这类审计口吻；来源写在章末「母本对应」表。

## 5. rustwiki 语言规则

1. **先场景，后定义**：先给命令、输出、报错或问题，再给名词和定义。
2. **短段**：一段 1–4 句，平均 60–120 字；一句话只说一件事，单句不超过约 35 字。
3. **人称**：用「你」称呼读者；需要共同操作时用「我们」；不用「笔者」「本文」「读者」。
4. **术语首现三件套**：中文（English，缩写）+ 一句大白话 + 一个最小例子。
5. **代码先跑再讲**：代码块前说「先运行 / 先猜输出」，块后逐行解释关键行；错误示例要给出报错与修复。
6. **一节只回答一个问题**：不要把三个不相干的主题塞进同一个 H2；必须合并时，用 H3 分开。
7. **每节收束**：2–3 句小结 + 一句「如果只记住一件事」+ 即时自测。
8. **过渡句**：上一节留下的问题，下一节第一段要接住；不用「下面我们来看」。
9. **少堆抽象名词**：把「机制 / 策略 / 抽象 / 边界」换成具体动作和对象；必须用时先用例子解释。
10. **允许口语，但不口水**：可以用「先别急」「你可能会问」「跑一下试试」，每节最多两处；不用 emoji，不用「小伙伴们」。

## 5.1 非科班读者的八条规则

1. **先补缺的那一层**：讲 `fork` 前先讲「进程是什么、为什么要有地址空间」；讲 inode 前先讲「文件为什么需要元数据」。不要假设读者学过操作系统。
2. **没有它会怎样**：每个抽象先给一个反例或故障，再给定义。比如先展示「两个进程同时写日志为什么交错」，再讲 `O_APPEND` 的原子性。
3. **一个抽象，一个日常类比，一条可观察证据**：类比解释「为什么」，命令/程序证明「确实如此」；类比每节最多一个。
4. **每个系统调用给最小可运行 C 程序**：完整到能 `cc` 编译；先跑，再讲参数、返回值、`errno`、内核路径。
5. **每节回答一次「我只写应用层，为什么也要懂」**：把机制连到读者会遇到的 bug、性能问题或排障场景。
6. **术语首现必须解释**：页表、inode、fd、中断、DMA、TCP 窗口、cgroup 等，第一次出现用 2–3 句大白话，不要求读者自己去查。
7. **不用「显然」「众所周知」「不难看出」**：非科班读者卡住时，往往就是这些词跳过的那一步。
8. **先建立正面模型，再讲边界**：先让读者能跑通、能画出一条路径，再补版本差异、失败模式和历史包袱。

## 6. 覆盖核读纪律

每节重写前，按下面顺序核读母本：

2. 只抽目标页，不整本转换：

   ```bash

   ```

3. 读完后合上 PDF，用自己的话写；不摘录原文，不编造命令输出。

## 7.1 可疑输出块（假终端）

教材里最危险的不是错字，是一段看起来非常真的终端输出。固定 PID、`VmRSS: 12345 kB`、`real 0m3.2s`、`[1]+  Stopped` 这类具体值，只要块内没有「实测 / 未实测 / 示意」的口径标注，读者就会当成可复现的事实。

规则：改造某一节时，凡是重写范围内出现的具体运行现场值，**只有两种处置**——在真机（macOS 或 `ubuntu24`）重跑换成真输出并标机器；或改写成「怎么观察 + 看到什么算命中」的判读描述。原样保留不算处置。`tools/check_suspect.py` 按章计数（启发式，命中不等于一定是编的），每章改完该章必须清零。2026-10-29 基线：全书 12 处，分布在 8 章（0.7、0.9 各 3，0.13/0.14/1.8/2.3/2.7/5.2 各 1）。

## 8. 验收门禁

每一章改完，按顺序跑：

```bash
cd /Users/juanwang/Desktop/tutorials/linux
python3 tools/check_loss.py          # 体量不倒退
python3 tools/check_book.py          # 结构、锚点、链接、盒子
python3 tools/check_kits.py          # 章末件覆盖清点
python3 tools/check_numbering.py       # 节号断档、重号、章尾重复检查表（本章改完应清零）
python3 tools/check_suspect.py partN/chXX  # 本章的可疑输出块（清零）
python3 tools/check_terms.py         # 术语首现是否有解释（全书按阅读顺序）
python3 tools/textbook_lint.py src/partN/chXX.md  # 行文体检（非阻塞）
PATH=/usr/bin:$PATH mdbook build .  # 全量构建；必须用带 markdown-it-py 的解释器（见下）
python3 tools/check_html.py          # 复核交付 HTML 的标签栈
```

**构建前必须确认解释器**。`book.toml` 里预处理器写的是 `command = "python3 tools/mathbook.py"`，而本机 `/opt/homebrew/bin/python3` **没有** `markdown-it-py`，`/usr/bin/python3` 有；PATH 里 homebrew 优先时构建会直接失败：

```text
mathbook: 需要 markdown-it-py 来渲染盒子内的 Markdown。
ERROR The "mathbook" preprocessor exited unsuccessfully with exit status: 1
```

危险的地方在于：不同失败路径对 `book/` 的处理不一样，**不能假设产物还在**。2026-10-29 实测到两种：

- 预处理器失败（`mathbook` 缺 `markdown-it-py`，exit 1）：mdBook 在渲染前中止，`book/` 里留着上一版产物——这时 `check_html` 会对着旧产物报「通过」，是最容易骗过验收的一种。
- mdBook 自身 panic（exit 101，如 `pop too far processing \`partN/chXX.md\``）：`book/` 已被清空，`find book -name '*.html' | wc -l` 为 0，`check_html` 会报「最新产物：（空）」。

所以判据是三条一起看：构建日志里有 `INFO HTML book written to`、`find book -name '*.html' | wc -l` 不少于当前 SUMMARY 页数、`check_html` 通过。任一不满足就是没构建成功，不能拿旧产物当验收。

**构建必须避开写者**。mdBook 会先清空 `book/` 再逐文件渲染，而渲染中途读到某个正在被代理改写的 `.md`（半截状态）会让它 panic——2026-10-29 就是这样：同一份 `part1/ch01.md` 在代理停笔后重新取一次，构建就正常了，而那次 panic 已经把 `book/` 清空。所以：**有正文代理在跑时不要跑全量构建**，构建验收留到一波写者全部交回之后统一做一次。要定位真正的断标签，用 `check_html` 与逐文件渲染（`tools/mathbook.py` 可直接 import 调 `parse_tree`/`render_tree`，用 `/usr/bin/python3` 跑），不要靠反复全量构建去撞。长期解法是给 homebrew 的 python3 装上仓库 `requirements.txt` 里那一行（属环境改动，先问用户）。

`mdbook build` 的 WARN 不要逐条追。它自带的平衡检查器会把代码块里**已正确转义**的 `&lt;` 先解码再当作标签起点，于是 `exec 9<"$f"`、`done < <(...)` 这类行会引发一串 `unclosed <p>/<div>/<pre>` 报警。判据是 `tools/check_html.py`：它解析真正交付的 HTML，能抓到真的断标签（未闭合的 `<div>`/`<pre>`/多余的 `</div>`），也能容忍 `p`/`li` 的隐式闭合。它报 0 问题就是产物没问题，不用管 WARN 条数。

然后人工检查三件事：

1. **新手视角**：随机抽一节，假设读者只学过 C 和基础命令，能否读懂第一屏？
2. **主线视角**：只看章总览，能否说出这一章分几个单元、每个单元解决什么？
3. **覆盖视角**：对照本章「母本对应」与 B 表，随机抽两条，正文能否找到落点？

最后按 [`72-章节审读表.md`](72-章节审读表.md) 填「主线 / 文段 / 行文」三视角评分；有 0 分项、或关键项平均低于 1.5，不进入下一章。审读记录写入 `写作规范/REVIEW-LOG.md`。
