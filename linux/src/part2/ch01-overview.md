# 2.1 系统编程基础：系统调用、错误与可移植性 · 本章导航

::: preview 这一章在讲什么
第 0 篇你在终端里看「行为」，第 1 篇你懂了程序怎么变成进程、`printf` 怎么跳到 libc。这一章开始写产生这些行为的程序，而中间那层很薄的边界就是**系统调用（system call，用户程序请求内核做事的唯一入口，靠一条特殊指令进内核）**。它不讲任何一个具体子系统，只立三条贯穿第 2 篇的规则：**怎么进内核**（2.1.1–2.1.2）、**怎么报告失败**（2.1.3–2.1.4、2.1.10）、**怎么不把平台细节写死**（2.1.5–2.1.8、2.1.11–2.1.13），最后用内核路径与 `strace`/`/proc` 把三条规则变成读数（2.1.14–2.1.15）。后面 18 章里出现的每一个「为什么我这里不对」，几乎都能追回这三条之一。
:::

## 本章回答什么

- **一次 `read` 到底穿过什么**：用户态的 glibc 包装 → 陷入指令 → 内核入口 → 按编号查表 → 返回值放回原寄存器 → glibc 把负数翻译成 `-1` 加 `errno`；两次「翻译」发生在哪（2.1.1）。
- **系统调用和库函数差在哪**：`man` 的分节不是本质；判据是「有没有执行陷入指令」与「语义由谁保证」。`getpid` 每次都进内核，`clock_gettime` 常走 vDSO（内核映射到用户空间的一小段代码，不需要切换特权级），差一个数量级（2.1.2）。
- **`errno` 的七条规则**：成功不清零、判断只看返回值、线程私有（每个线程一份，不是进程级一个变量）、打印前先存进局部变量、`pthread_*` 直接返回错误码、`EINTR` 是打断不是失败、`strerror` 不保证线程安全（2.1.3）。
- **错误处理怎么写成三层**：`errMsg` 打印并返回、`errExit` 打印并退出、中间层透传 `errno`；`err.c` 的三个设计点与「该不该 `exit`」的判断顺序（2.1.4）。
- **同一份代码为什么在别人机器上编不过**：特性测试宏控制**声明是否可见**，`-D_GNU_SOURCE` 打开全部，显式 `-D_POSIX_C_SOURCE=200809L` 会让 `accept4`/`pipe2`/`strdup` 失去声明；宏必须写在第一个系统头之前（2.1.5、2.1.11）。
- **数字为什么不能抄**：`sysconf`/`pathconf`/`fpathconf` 的 `-1` 有两种含义（调用前必须清 `errno`）；`_SC_OPEN_MAX` 在本机 glibc 上只是 `RLIMIT_NOFILE` 软限制的投影；`NAME_MAX` 随文件系统变（2.1.6、2.1.12）。
- **机器证据从哪拿**：`uname`、`sysinfo`（内存字段要乘 `mem_unit`）、`/proc` 的文本投影与 `sysfs` 的对象模型，以及「别用列位置取数」这条纪律（2.1.7）。
- **提交前的十条可移植性检查**：不写裸数字、`size_t`/`pid_t` 不用 `int` 装、`char` 在 ARM 上默认无符号所以 `getchar` 要用 `int` 接、同一份代码用两种宏各编一次（2.1.8）。
- **系统调用 ABI 长什么样**：四架构的陷入指令、调用号寄存器、参数寄存器与返回寄存器；为什么第四个参数在 x86-64 是 `r10`；为什么最多六个参数、超了改传结构体；坏指针得到 `EFAULT` 而不是 `SIGSEGV`（2.1.9）。
- **错误码的深水区**：`strerror_r` 有 GNU/XSI 两个不兼容签名；`EAGAIN == EWOULDBLOCK`；`errno` 到 HTTP 状态码与进程退出码的映射表；退出码只有 8 位（2.1.10）。
- **命令行解析**：`getopt_long` 的 `struct option`、六种返回值、`:` 与 `?` 的分工、重排与 `POSIXLY_CORRECT`、长选项缩写为什么危险（2.1.13）。
- **落到内核与落到读数**：`do_sys_openat2` 为什么先占 fd 再打开、`vfs_read` 那十几行怎么解释 `MAX_RW_COUNT` 截断与 `EBADF`；`strace -yy` 的 fd 复用、`-e inject` 免改代码注入错误、`/proc/self/fdinfo/N` 与 `/proc/self/syscall`（2.1.14–2.1.15）。
- **哪些结论会搬家**：三组跨节陷阱（2.1.16）、本章小结与证据口径（2.1.17），以及换架构换 libc 之后要复核什么（[勘误页](ch01-errata.md)）。

## 读完你会

- 在白纸上画出一次 `read(fd, buf, n)` 的六步路径，并指出「内核返回 `-errno`」与「libc 返回 `-1` 加 `errno`」这两个翻译点各在哪一层。
- 说出 `syscall`、`int 0x80`、`svc #0`、`ecall` 四条陷入指令分别属于哪个架构，以及调用号与参数寄存器怎么排。
- 不查正文写出 `errMsg`/`errExit`，并解释为什么函数第一句是 `int saved = errno;`、为什么用 `vsnprintf`、`errExitEN` 什么时候必须用。
- 用两条编译命令复现「`accept4` 报隐式声明却链接成功」，并说清运行时为什么可能把参数解释错。
- 写出正确的 `sysconf` 调用形状（先 `errno = 0`，返回后区分「不确定」与「失败」），并解释 `-1` 的两种含义。
- 用 `getrlimit(RLIMIT_NOFILE)`、`ulimit -n`、`/proc/self/limits`、`/proc/sys/fs/nr_open` 四个读数回答「我还能开多少 fd」，并说出 `EMFILE` 先撞哪一个。
- 给 `err.c` 加上 `errExitEN`，把 `pthread_mutex_lock` 的返回值（不是 `errno`）正确打印出来。
- 用 `strerror_r` 的可移植写法（按 `_GNU_SOURCE` 分支或 `strerror_l`）取错误文本，并解释 GNU 版为什么不能假设返回值等于自己的缓冲区。
- 写一个 `getopt_long` 解析器，同时吃下 `-n3`、`-n 3`、`--count=3`、`--color`（可选参数）、`--`，并在缺参数与未知选项时给出不同退出码。
- 用 `strace -f -yy -e trace=%file,%desc` 读出 fd 复用与 `pipe2`，用 `-e inject=openat:error=EACCES:when=1` 不改代码就走进错误分支，用 `/proc/self/fdinfo/3` 读出 `pos`/`flags`。
- 把本章任何一条读数写成「哪个架构、哪个内核、哪个 libc、哪条命令」，凡是换机器就不成立的，落到[勘误与版本注记](ch01-errata.md)那一张表里。

## 这条主线怎么走

**第一段，边界与成本（2.1.1–2.1.2）。** 先把「进内核」这件事拆开：CPU 只给了一个受控入口，一条陷入指令把特权级从用户态切到内核态，内核按编号查表决定做什么。所以「系统调用」的本质是一次被审查的远程调用，不是一次普通函数调用。紧接着要分清谁负责什么：`printf` 在用户态格式化，`write` 才进内核；`malloc` 在堆上切块，`mmap` 才找内核；`getpid` 每次都进内核，`clock_gettime` 常常不进。这一段的落点是一句判据——**有没有执行那条陷入指令，语义由谁保证**——和一个量级：陷入一次的代价比读一次 vDSO 高一个数量级。

**第二段，失败怎么报告（2.1.3–2.1.4）。** C 没有异常，失败靠「特殊返回值 + `errno`」，而这套机制的七个坑几乎人人踩一遍：成功不清零、`errno` 可能是上一次的、`fprintf` 会改写它、线程函数根本不设它、`EINF` 类「被打断」不是错误。2.1.3 用 `errno_demo.c` 把三条规则变成可复现的输出；2.1.4 把它整理成三层：能恢复就返回 `-1` 并保留错误，不能恢复但进程还有别的事就记日志继续，配置解析失败这类才 `errExit`。

**第三段，不把平台写死（2.1.5–2.1.8）。** 系统编程里最贵的一类 bug 是「我这能跑」。头文件只在你声明了标准等级时才暴露对应接口，所以特性测试宏是契约而不是编译选项；限制分两层——`sysconf` 看系统、`pathconf` 看文件系统，`-1` 还有「不确定」这层含义；`uname`/`sysinfo`/`/proc` 是拿运行时证据的地方；2.1.8 把前面所有条目压成十条提交前检查，其中「`char` 在 ARM 上默认无符号」这条能解释为什么有些 bug 在 x86 上永远测不出来。

**第四段，往深处看（2.1.9–2.1.13）。** 2.1.9 回答「同一条 `read` 凭什么在四个架构上编成不同机器码」：ABI 规定陷入指令、调用号寄存器与参数顺序，寄存器用满就只剩六个参数位，超了改传结构体；`EFAULT` 说明内核不信任用户指针。2.1.10 处理错误码的后半程：转成文本、识别等价码、映射成对外协议与退出码。2.1.11 把 2.1.5 的宏补成矩阵，并指出宏不只控制声明还控制结构体布局。2.1.12 把 2.1.6 的两个接口接到 `RLIMIT_*` 上，回答「三个数为什么打架」。2.1.13 用一个完整解析器把「接口选型」落到命令行。

**第五段，取证与收口（2.1.14–2.1.17）。** 前四段是契约，这一段是读数：`do_sys_openat2` 与 `vfs_read` 解释「为什么 fd 在安装前不会被抢走」「为什么一次 `read` 读不完 3 GiB」；`strace` 与 `/proc` 教你不改代码就看到失败原因与 fd 状态；2.1.16 把跨节陷阱按主题分三组，2.1.17 把全章收成三段主线、三条判据和一份证据账目——逐条打勾在[自检表](ch01-checklist.md)。

一句话主线：**先把「谁进内核、谁翻译错误、谁保证语义」三层分清楚，再把所有常数改成运行时查询、所有失败改成先看返回值再读 `errno`、所有接口可用性改成显式声明标准等级；遇到分歧，用 `strace` 与 `/proc` 拿到读数，而不是用「我这能跑」收尾。**

## 环境口径

- **测试 VM**：Ubuntu 24.04.5，**aarch64（ARM64，不是 x86-64）**、内核 `7.0.0-38-generic`、GCC 13.3.0、glibc 2.39、4 vCPU、约 12 GiB 内存。可用：`cc`/`gcc`、`make`、`strace`（6.8）、`getconf`、`uname`、`ulimit`、`namei`、`sysctl`（读）、`/proc`、`/sys`、`bash` 的重定向与 `exec 3<file`。
- **不可用**：`sudo` 与 `perf`。所以 2.1.14 结尾的 `sudo bpftrace`/`sudo perf probe` 一律按「未实测」读（替代见[习题集](ch01-exercises.md) C5）；2.1.7 里写 `/proc/sys/vm/*` 这类要 root 的动作不能照跑；`prlimit` 只能改自己的进程。
- **正文读数的归属**（已在本机逐条复跑核对）：2.1.2 的三个纳秒数、2.1.6 的 `limits` 输出（`machine=x86_64`、内核 6.8.0、8 CPU）、2.1.9 的 `abi_probe` 数字、2.1.15 的 `strace` 行（`/lib/x86_64-linux-gnu/libc.so.6`）都标着或暗示 x86-64，在本书 aarch64 机器上对不上。本机实测：`SYS_read`=63、`SYS_write`=64、`SYS_openat`=56、`SYS_statx`=291；`_SC_NPROCESSORS_ONLN`=4；`_SC_OPEN_MAX`=1024（等于 `ulimit -n` 的软限制，而硬限制是 1048576）；`_SC_PAGESIZE`=4096；`_SC_ARG_MAX`=2097152；`/tmp` 在 ext4 根分区上，`NAME_MAX`=255、`PATH_MAX`=4096。逐行对照见[勘误页](ch01-errata.md)第 3 节「复跑校正」与[习题集](ch01-exercises.md) C2。
- **两条额外的权限边界**：`/proc/sys/kernel/yama/ptrace_scope` 本机是 1，所以 `strace -p <PID>` 附着会报 `ptrace(PTRACE_SEIZE...): Operation not permitted`，读别人的 `/proc/PID/syscall` 也报 `Operation not permitted`——取证一律用「在 strace 下启动」和 `/proc/self/...`。`cc -m32` 在本机不被支持（`unrecognized command-line option`），所以 32 位 ABI 的 `EOVERFLOW`/`_TIME_BITS=64` 那组结论按未实测读。
- **2.1.14 的函数名**按「Linux 6.8 + x86-64 入口」写（`arch/x86/entry/entry_64.S`、`sys_call_table[257]`）。本机是内核 7.0.0-38 的 aarch64，入口换到 `arch/arm64/kernel/entry.S` 的 `el0_svc`/`do_syscall` 一侧，`openat` 的编号也不是 257；VFS 与 ext4 那几层的函数名是内核通用代码，跨架构仍成立。
- **写作机**：macOS（Apple 芯片，arm64）。它可以编译本章的 C 程序，但没有 `/proc`、没有 `strace`，`errno` 数值也不同（实测 `EAGAIN`=35、`ENOTSUP`=45、页大小 16384）；用它只能对照「换一个 libc/架构会怎样」，所有第 2 篇实验回 Linux 做。
