Unix 的文件 I/O 模型只有五个函数：`open`、`read`、`write`、`lseek`、`close`。设备、管道、socket、终端，全都套进这个模型。**「一切皆文件」不是哲学口号，而是一组统一的方法表**：每个打开的文件对象都挂着一张 `file_operations`，`read` 最终调到哪，由这张表决定。

这一章只讲这五个函数在**普通文件**上的语义。管道、socket、`epoll`、终端分别在 [2.14](../part2/ch14.md)、[2.16](../part2/ch16.md)、[2.18](../part2/ch18.md)、[2.19](../part2/ch19.md) 展开；但短读、短写、`EINTR` 这些纪律是通用的，从这里开始就要养成。

## 2.2.1 三层对象：fd、open file description、inode {#sec-2.2.1}

这一节回答：同一个文件打开两次，两个 fd 各读各的、偏移互不相干；`dup` 出来的两个 fd 却会把位置互相推过去。差别出在哪一层？

::: preview 先抓住一件事
`fd` 是进程私有表里的一个下标，表项指向「这一回打开」的状态（偏移与标志），那份状态再指向文件本身。判断两个 fd 共享不共享偏移，只问一句：它们是不是同一次打开。`dup`、`fork` 是同一次，第二次 `open` 就不是。
:::

::: def 定义 2.2.1 · 文件描述符（file descriptor） {#def-2.2.1}
文件描述符是进程内**文件描述符表**的一个非负整数下标。表项指向一个**打开文件描述**（open file description，内核里是 `struct file`），后者再指向 **inode**。`fd` 只在所属进程内有效；`fork()` 后子进程复制一份表，表项仍指向同一个 `struct file`。
:::

三层对象各管一件事：

| 层 | 内核对象 | 保存什么 | 谁共享 |
|:--|:--|:--|:--|
| fd 表 | `files_struct` | 下标 → `struct file *` | 同一进程的线程共享；`fork` 后各自一份 |
| 打开文件描述 | `struct file` | 偏移 `f_pos`、状态标志、引用计数、`f_op` | `dup`/`fork` 后共享 |
| inode | `struct inode` | 文件类型、权限、大小、时间、数据块位置 | 所有打开同一文件的进程共享 |

{{#include ../assets/figures/fd-table.md}}

这张图解释了两个常见困惑：

1. **同一个文件被打开两次，偏移不共享**。`open()` 两次得到两个 `struct file`，各有 `f_pos`；一个读到 100 字节，另一个仍在 0。
2. **`dup()`/`fork()` 后偏移共享**。两个 fd 指向同一个 `struct file`，任何一个 `read` 都推进同一个 `f_pos`。多进程写同一个日志文件时，这正是「输出交错」的根源之一。

::: intuition 为什么要有「打开文件描述」这一层
如果 fd 直接指向 inode，那么「偏移」和「打开标志」就没有地方放：同一个文件被两个进程用不同模式打开（一个读、一个追加），需要两套偏移与标志。`struct file` 就是这层「一次打开会话」的状态。它把**文件本身**（inode）与**这次打开的行为**（偏移、flags）分开，`dup` 才能既共享偏移又不复制 inode。
:::

### 手推：同一路径为什么读出了不同字符

设普通文件内容为 `ABCDE`，没有其他进程改文件，下面按顺序执行；`a`、`b`、`c` 表示 fd 变量，不是固定的 fd 号。

```text
a = open("letters", O_RDONLY)
b = dup(a)
c = open("letters", O_RDONLY)
read(a, buf, 2)
read(b, buf, 1)
read(c, buf, 1)
close(a)
read(b, buf, 1)
```

| 操作完成后 | 这次读到 | a/b 共用的打开文件描述偏移 | c 的打开文件描述偏移 |
|:--|:--|--:|--:|
| 三次打开/复制 | — | 0 | 0 |
| `read(a, ..., 2)` | `AB` | 2 | 0 |
| `read(b, ..., 1)` | `C` | 3 | 0 |
| `read(c, ..., 1)` | `A` | 3 | 1 |
| `close(a)` | — | 3，b 仍持有引用 | 1 |
| `read(b, ..., 1)` | `D` | 4 | 1 |

读表时先找「操作改的是哪一层」。`close(a)` 删除 a 的表项，不会关闭 b 的表项；同一路径的第二次 `open` 共享 inode，却不会共享偏移。这也是 `fork` 后父子轮流读文件时需要同步的原因。

迁移题：若最后一行之前执行 `lseek(b, 0, SEEK_SET)`，b 和 c 下一次各读一个字节会得到什么？先画两个打开文件描述，再核对：b 读到 `A`，c 仍从自己的偏移 1 读到 `B`。若你预测两边一起回到开头，回看本节三层表；若认为 b 已随 a 关闭，回看上表的引用关系。

### 2.2.1 小结

三层各有各的共享范围：fd 表按进程分（同一进程的线程共用一张，`fork` 各得一份拷贝），打开文件描述按「一次打开」分（偏移 `f_pos`、状态标志、引用计数都住在这一层），inode 按文件分（类型、权限、大小、数据块位置）。`close` 只删自己那一格表项，引用计数归零才轮到释放上两层。本节的推表演练的就是这条：`read(b)` 读到 `C`，是因为 b 与 a 共用同一个 `struct file`；`read(c)` 读到 `A`，是因为 c 有自己的偏移。偏移属于一次打开而不是属于文件，想清楚这一句，`fork` 后父子轮流读、多进程追加写同一个日志导致输出交错，都只是它的推论。还有一条容易被编号骗到：fd 号本身没有含义，`dup` 只保证返回「当前最小空闲号」，别把 0、1、2 当成特殊豁免，它们和后开的 fd 在三层结构上完全同构。如果只记住一件事：**fd 不是文件的编号，而是「这次打开」在你进程里的门牌号；判断共享，永远看两个 fd 背后是不是同一个 `struct file`。**

::: method 即时自测 · 2.2.1
**Q1（记忆）** 三层对象分别是什么？当前偏移和打开标志存在哪一层，文件权限又存在哪一层？

**Q2（辨析）** `dup(fd)` 得到的两个 fd，与第二次 `open(同一路径)` 得到的两个 fd，差别发生在哪一层？`fork` 之后子进程手里的 fd 号一定和父进程相同吗？相同是否意味着「同一层」？

**Q3（应用）** 父子进程读 `fork` 之前就打开好的同一个 fd，结果两边读到的字节一段也不重复。有人说这是 bug，要「各自从头读一遍」。给出你的判断，并写出改法；顺便说明为什么「在子进程里 `lseek(fd, 0, SEEK_SET)`」不解决这个需求。

::: sol 答案
**A1** fd 表（`files_struct`，下标 → `struct file *`）、打开文件描述（`struct file`：偏移、状态标志、引用计数、`f_op`）、inode（文件类型、权限、大小、时间、数据块位置）。偏移在第二层，权限在第三层。
**A2** `dup` 只复制表项，两个 fd 指向同一个 `struct file`，偏移共享；第二次 `open` 新建一个 `struct file`，只有 inode 相同，偏移各自独立。`fork` 复制整张 fd 表，号通常相同，但表项仍指向同一个 `struct file`——号相同不等于同一层，它本来就是同一份打开会话的两个入口。
**A3** 不是 bug，是机制的正常结果：父子共用一次打开会话，任何一次 `read` 都推进同一个 `f_pos`，多进程分片读文件正靠这个。要各自从头读，就在 `fork` 之后各自重新 `open` 一次，得到两个 `struct file`。子进程里 `lseek` 回开头改的是那个共享的 `f_pos`，父进程下一次 `read` 也会跟着从头开始，两边从「互不重复」变成「互相回退」。
:::

## 2.2.2 open 与 openat：flags、mode 与原子性 {#sec-2.2.2}

这一节回答：`open(path, O_RDWR | O_CREAT, 0644)` 的第三个参数什么时候才被内核看一眼？为什么「先 `access()` 判断存在、再 `open()`」写出来像锁，跑起来却同时起了两个守护进程？

::: preview 先抓住一件事
一次 `open` 只回答两件事：以什么模式打开（读、写、读写三选一，编码在 `flags` 的低位），以及要不要创建。`mode` 只在这一次真要创建时才被读，读进去还要被 `umask` 清掉几位。
:::

::: def 定义 2.2.2 · `open()` 的访问模式与创建标志 {#def-2.2.2}
`open(path, flags, mode)` 的 `flags` 由三部分组成：

- **访问模式**（低两位，必须有且仅有一个）：`O_RDONLY`(0)、`O_WRONLY`(1)、`O_RDWR`(2)；
- **创建/截断**：`O_CREAT`、`O_EXCL`、`O_TRUNC`、`O_NOCTTY`；
- **行为修饰**：`O_APPEND`、`O_NONBLOCK`、`O_SYNC`/`O_DSYNC`、`O_DIRECT`、`O_CLOEXEC`、`O_TMPFILE`。

`mode` 只在带 `O_CREAT` 或 `O_TMPFILE` 时有意义，且**会被 `umask` 清位**：最终权限 = `mode & ~umask`。
:::

最常用的一组：

```c
int fd = open(path, O_RDONLY);                                  /* 只读打开，文件必须存在 */
int fd = open(path, O_WRONLY | O_CREAT | O_TRUNC, 0644);        /* 创建或截断，最终权限受 umask */
int fd = open(path, O_RDWR | O_CREAT | O_EXCL, 0600);           /* 原子地「创建新文件」，已存在则 EEXIST */
int fd = open(path, O_WRONLY | O_APPEND | O_CREAT, 0644);       /* 每次写都追加到当前末尾 */
```

`openat()` 多一个 `dirfd` 参数：

```c
int fd = openat(dirfd, "conf/nginx.conf", O_RDONLY);
int fd = openat(AT_FDCWD, "/etc/hosts", O_RDONLY);   /* 等价于 open() */
```

`openat` 的价值不只是「省一个路径」：

- **避免 TOCTOU**：先 `open(dir)`，再 `openat(dirfd, "file")`，即使目录被 rename，解析仍锚定在同一个目录 inode 上；
- **限制逃逸**：配合 `O_NOFOLLOW`、`openat2()` 的 `RESOLVE_BENEATH`，可以禁止 `..` 跳出沙箱；
- **线程安全**：不依赖进程级 `cwd`，多线程改 `chdir` 不会影响其他线程的相对路径。

### 两个必须记住的原子性

::: thm 定理 2.2.1 · `O_CREAT|O_EXCL` 与 `O_APPEND` 的原子性 {#thm-2.2.1}
在本地文件系统上：

1. `open(path, O_CREAT|O_EXCL, mode)` 的「检查不存在 + 创建」是一个原子操作（atomic operation：中间不可被打断，对外表现为一步完成）。两个进程同时调用，只有一个成功，另一个得到 `EEXIST`。
2. `open(path, O_WRONLY|O_APPEND)` 后，每次 `write()` 的「定位到末尾 + 写」是一个原子操作。多个进程追加写同一文件，不会互相覆盖（但**不保证整条记录不交错**，见下）。
:::

`O_EXCL` 是**锁文件**与**临时文件**的正确做法：

```c
/* 正确：原子创建锁文件 */
int fd = open("/var/run/mydaemon.pid", O_WRONLY | O_CREAT | O_EXCL, 0644);
if (fd == -1 && errno == EEXIST) {
    /* 已有实例在跑，或上次崩溃留下 stale 文件 */
}
```

错误做法是先 `access()` 再 `open()`：两条语句之间另一个进程可以插进来，两个进程都认为自己拿到了锁。

`O_APPEND` 的原子性只保证「写到当前末尾」，**不保证多个 `write` 的字节不交错**。如果两个进程各写一行 200 字节，内核不会把两次 `write` 拆开，但若一次 `write` 分多次系统调用（或 stdio 缓冲多次 flush），行与行仍可能穿插。要保证整条记录原子，要么单次 `write` 写完，要么加文件锁。

::: errata 关于 `O_APPEND` 的三个误解
1. **「`O_APPEND` 能保证多进程日志不交错」**——只在「一条记录一次 `write`」时成立。用 `fprintf` + 行缓冲，或多条 `write` 拼一条记录，仍会交错。
2. **「先 `lseek(fd, 0, SEEK_END)` 再 `write` 等价于 `O_APPEND`」**——不等价。两条语句之间别的进程可以追加，你的写会覆盖别人的数据。`O_APPEND` 把这两步合成一个原子操作。
3. **「NFS 上 `O_APPEND` 也一样」**——NFS 的追加语义依赖服务器实现，旧版本可能不原子；跨网络不要假设本地语义。
:::

### `O_CLOEXEC`：一个必须默认打开的开关

`fork()` 后 `exec()` 会保留所有没有 `FD_CLOEXEC` 的 fd。父进程打开的日志、socket、数据库连接会泄漏给子程序。更糟的是多线程下 `open()` + `fcntl(F_SETFD)` 之间有窗口：另一个线程刚好 `fork+exec`，fd 就漏过去了。

```c
/* 正确：创建时就带 CLOEXEC，原子 */
int fd = open(path, O_RDONLY | O_CLOEXEC);

/* 错误：两步之间可能被 fork+exec 抢先 */
int fd = open(path, O_RDONLY);
fcntl(fd, F_SETFD, FD_CLOEXEC);
```

新代码应默认使用 `O_CLOEXEC`；`dup()` 用 `fcntl(fd, F_DUPFD_CLOEXEC, 0)` 或 `dup3(fd, newfd, O_CLOEXEC)`。

### `O_TMPFILE`：匿名临时文件

```c
int fd = open("/tmp", O_TMPFILE | O_RDWR, 0600);
/* 写入数据；需要命名时： */
linkat(fd, "", AT_FDCWD, "/tmp/final", AT_EMPTY_PATH);
```

文件从创建到 `linkat` 之前没有名字，崩溃也不会留下垃圾；适合「先写完整、再原子发布」的场景。需要文件系统支持（ext4/XFS/tmpfs 均支持）。

上面那行 `linkat(fd, "", AT_FDCWD, "/tmp/final", AT_EMPTY_PATH)` 有一个**权限前提**要先说清楚：`linkat(2)` 手册写着「使用 `AT_EMPTY_PATH` 需要 `CAP_DAC_READ_SEARCH`」，很多资料据此说普通用户这一步会直接失败。**本机的实测结论相反**：ubuntu 24.04.5 / aarch64、内核 7.0.0-38、`CapEff=0000000000000000`（有效能力为空）的普通用户，这一条返回 `0` 并真的建出了名字。完整读数与边界在 [2.2.9](ch02.md#sec-2.2.9) 的 `O_TMPFILE` 一节；这里要记住的是：**这一步能不能过，取决于内核版本而不是手册文字，别把它当可以依赖的失败点，也别把 `/proc/self/fd/N` 那条回退当唯一活路**。

### 2.2.2 小结

`flags` 三段各司其职：访问模式（读、写、读写，三选一）、创建与截断（`O_CREAT`/`O_EXCL`/`O_TRUNC`/`O_NOCTTY`）、行为修饰（追加、非阻塞、同步、`O_CLOEXEC` 等）。`mode` 只在这次真要创建时才被读，读进去还要被 `umask` 清位，所以打印出来的「你以为的权限」和磁盘上的权限常差一截。能指望的原子性只有两处：`O_CREAT|O_EXCL` 把「检查不存在 + 创建」合成一步，`O_APPEND` 把「定位到末尾 + 写入」合成一步；其余「先看一眼再动手」都留出竞争窗口，`O_APPEND` 也管不了整条记录是否交错。`openat` 用 `dirfd` 把解析锚死在一个目录 inode 上，一并躲开 TOCTOU、`..` 逃逸和进程级 `cwd` 三个问题。`O_CLOEXEC` 必须在 `open` 时就给，事后 `fcntl` 补一步就已经有了窗口。如果只记住一件事：**判断一段 I/O 代码安不安全，就数它把几步合成了一次内核调用——合成得越少，窗口越多。**

**Q1（记忆）** `open` 的 `flags` 分成哪三段？`mode` 在什么条件下才被内核读到？落在磁盘上的权限怎么算出来？

**Q2（辨析）** 先 `lseek(fd, 0, SEEK_END)` 再 `write`，为什么不等于 `O_APPEND`？`open()` 之后紧跟 `fcntl(fd, F_SETFD, FD_CLOEXEC)` 为什么仍可能把 fd 漏给子程序？`O_RDONLY | O_WRONLY` 和 `O_WRONLY | O_RDWR` 这两种写法各发生什么？

**Q3（应用）** 某守护进程用 `access(pidfile, F_OK)` 判断有没有别的实例，再用 `open(pidfile, O_WRONLY | O_CREAT, 0644)` 写 pid。两台机器上同时启动，两个实例都认为自己是唯一的。改哪一处？改完之后，怎么把「另一个实例正在跑」和「上次崩溃留下的死文件」分开？

::: sol 答案
**A1** 访问模式、创建与截断、行为修饰三段。`mode` 只在 `flags` 里有 `O_CREAT`（或 `O_TMPFILE`）时才被读，其它情况下这个参数根本不存在于语义里，漏写或写成垃圾都不影响结果。落盘的权限是 `mode & ~umask`，所以 `0666` 在 `umask=022` 的会话里变成 `0644`。
**A2** `lseek` 与 `write` 是两次调用，中间别的进程可以追加，你就把自己的字节写在别人中间，覆盖掉尾部；`O_APPEND` 把这两步合进一次内核调用，定位用的是写入那一刻的真实末尾。`fcntl` 那两步之间，另一个线程可能已经 `fork+exec`，新程序继承到这个 fd 时 `FD_CLOEXEC` 还没设上，所以要 `open(path, ... | O_CLOEXEC)` 一次到位。`O_RDONLY` 是 0，`O_RDONLY | O_WRONLY` 化简成 `O_WRONLY`，只读的意图静悄悄丢掉；`O_WRONLY | O_RDWR` 拼出 3，不是合法的访问模式，内核直接拒绝这次 `open`。
**A3** 换成 `open(pidfile, O_WRONLY | O_CREAT | O_EXCL, 0644)`，失败且 `errno == EEXIST` 时才去读文件里的 pid 并 `kill(pid, 0)` 探活。`access`+`open` 的顺序让两个进程都能通过检查，`O_EXCL` 把检查与创建合成一步，只剩一个能成功。区分两种情况要靠内容而不是存在性：pid 还活着就是别人在跑；pid 不存在或是自己，就是 stale 文件，可以接管。探活本身仍是两步，但此时锁的持有者已经由 `O_EXCL` 定下来了，不会有两个「赢家」。NFS 上的边界见 [2.2.16](ch02.md#sec-2.2.16)。
:::

## 2.2.3 read 与 write：返回值到底承诺了什么 {#sec-2.2.3}

这一节回答：`read(fd, buf, 4096)` 返回 100，是出错了、读完了、还是没读完？`write` 请求 5 字节只返回 3，剩下 2 字节去哪了？

::: preview 先抓住一件事
返回值回答的是「这次搬了几个字节」，不是「成不成功」：正数是部分完成，0 对 `read` 一般是到了末尾、对 `write` 一般是请求长度本来就是 0，只有 -1 才轮到 `errno` 说话。
:::

::: def 定义 2.2.3 · `read()`/`write()` 的返回语义 {#def-2.2.3}
`ssize_t read(int fd, void *buf, size_t count)`：

- 返回 `>0`：实际读到的字节数，**可能小于 `count`**（短读）；
- 返回 `0`：EOF（对普通文件是读到末尾；对管道/终端是写端全部关闭）；
- 返回 `-1`：错误，`errno` 说明原因；`EINTR` 表示被信号打断，通常应重试。

`ssize_t write(int fd, const void *buf, size_t count)`：

- 返回 `>0`：实际写入的字节数，**可能小于 `count`**（短写）；
- 返回 `0`：极少见，通常意味着 `count==0`；
- 返回 `-1`：错误；`EINTR` 可重试，`EAGAIN` 表示非阻塞 fd 暂时不可写。
:::

### 短读与短写不是「异常」

对**普通文件**，`read` 通常返回请求的字节数（除非到了 EOF 或被信号打断）；但对**管道、终端、socket、慢设备**，短读是常态。`write` 同理：管道缓冲区满、socket 发送缓冲区满、磁盘配额、信号打断，都会导致只写一部分。

下面的循环适用于阻塞 fd，且调用者需要「读满或遇到 EOF」「写完或报错」的语义。出错前可能已经传输了部分字节，`-1` 不表示可以把整个操作从头重做；非阻塞事件循环应保存进度，见后面的 `EAGAIN` 小节。

```c
/* 读满 count 字节，除非 EOF 或出错；返回实际字节数，出错返回 -1 */
ssize_t read_full(int fd, void *buf, size_t count)
{
    size_t done = 0;
    char *p = buf;
    while (done < count) {
        ssize_t n = read(fd, p + done, count - done);
        if (n == -1) {
            if (errno == EINTR) continue;      /* 被信号打断，重试 */
            return -1;
        }
        if (n == 0) break;                     /* EOF */
        done += (size_t)n;
    }
    return (ssize_t)done;
}

/* 写完全部 count 字节，除非出错；返回实际字节数，出错返回 -1 */
ssize_t write_full(int fd, const void *buf, size_t count)
{
    size_t done = 0;
    const char *p = buf;
    while (done < count) {
        ssize_t n = write(fd, p + done, count - done);
        if (n == -1) {
            if (errno == EINTR) continue;
            return -1;
        }
        if (n == 0) { errno = EIO; return -1; }  /* 不该发生；防止死循环 */
        done += (size_t)n;
    }
    return (ssize_t)done;
}
```

以写出 `HELLO` 为例，请求长度为 5。第一次 `write` 返回 2 后，`done=2`，下一次必须传 `p+2` 和长度 3；若这次返回 `-1/EINTR`，进度仍是 2，重试的还是 `LLO`；最后返回 3，才得到 `done=5`。若每次都传 `p` 和长度 5，就会重复写出前缀。若中途是 `EAGAIN`，应保留 `done=2` 并等待可写，不能在事件循环里原地忙重试。

::: errata 五个高频错误
1. **`if (read(fd, buf, n) != n) error();`**——把短读当错误。管道/终端/信号下必错。
2. **`write(fd, buf, n);` 不检查返回值**——短写时静默丢数据。日志、网络、磁盘满时最危险。
3. **`EINTR` 一律当失败**——`read`/`write`/`open`/`close` 都可能被信号打断。要么重试，要么用 `sigaction` 的 `SA_RESTART`（但不能覆盖所有情况）。
4. **`read` 返回 0 后继续读**——EOF 后再次 `read` 仍返回 0；循环不退出会空转。
5. **`count` 为 0 时 `read` 返回 0**——这不是 EOF，不能拿来判断文件结束。
:::

### `EINTR` 与 `SA_RESTART`

慢系统调用（`read`/`write`/`open`/`wait`/`accept` 等）在阻塞期间收到信号，若信号处理器是用 `signal()` 或 `sigaction()` 且**未设** `SA_RESTART`，调用会返回 `-1`、`errno=EINTR`。

```c
struct sigaction sa = {0};
sa.sa_handler = on_signal;
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_RESTART;     /* 让可重启的调用自动重启 */
sigaction(SIGCHLD, &sa, NULL);
```

`SA_RESTART` 不是万能：`poll`/`epoll_wait`/`select`/`msgrcv` 等**不会**自动重启；即使设了，也可能因为超时语义需要自己处理。库函数应始终处理 `EINTR`，不要依赖调用者设了 `SA_RESTART`。

### 非阻塞 I/O 与 `EAGAIN`

`O_NONBLOCK` 下，没有数据可读/缓冲区满时，`read`/`write` 返回 `-1`、`errno=EAGAIN`（或 `EWOULDBLOCK`，两者在 Linux 上同值）。这不是错误，是「现在不行，等通知」：

```c
ssize_t n = read(fd, buf, sizeof buf);
if (n == -1) {
    if (errno == EAGAIN || errno == EWOULDBLOCK) {
        /* 等 epoll 通知，稍后再试 */
    } else if (errno == EINTR) {
        /* 重试 */
    } else {
        /* 真错误 */
    }
}
```

`EAGAIN` 与 `EINTR` 的区别：前者是**状态**（现在不可用），后者是**事件**（被信号打断）。两者都可能需要重试，但 `EAGAIN` 通常要等 fd 就绪，不能忙等。

### 2.2.3 小结

`read`/`write` 的返回值同时扛着三种信息：搬了多少字节、到没到末尾（只有 `read` 的 0）、错没错（-1）。把正数当错误退出，会在管道和 socket 上丢数据；把 `read` 的 0 当「读到 0 字节的数据」继续用缓冲区，会拿到上一轮的旧内容；把 `EINTR` 一律当失败，会让一个定时器信号打断整条传输。循环必须带上进度：偏移往后挪、长度减去已完成的，出错前已经搬走的字节不作废，`-1` 不等于「可以从头重做」。`EINTR` 是事件，重试就行；`EAGAIN` 是状态，要等 fd 就绪，原地忙等只会把 CPU 烧光。库代码自己处理 `EINTR`，别指望调用者设了 `SA_RESTART`，因为 `poll`/`epoll_wait`/`select` 那批调用设了也不会重启。如果只记住一件事：**先按返回值分诊（正数=还要继续，0=分对象判断，-1=才看 `errno`），再谈别的。**

::: sol 答案
**A1** 一是真到了文件末尾（普通文件读尽），二是这次请求长度本来就是 0（`count == 0`，POSIX 允许直接返回 0，不算 EOF）；对管道和 socket，读端还会在写端全部关闭时拿到 0。`write` 返回 0 极少见，通常就是 `count == 0`。`errno` 只在返回 -1 时有意义，返回值是正数或 0 时它可能是上一次失败留下的残留值。

**A3** 去掉之后，如果某个 fd 真的连续返回 0（不合法的实现、或被驱动当成「写不下也不再报错」），`done` 永远不涨，循环死转，程序卡住而不是报错——这一行是防死循环的保险丝，不是常规错误路径。那条简写有两个错：每次仍传 `p` 和 `count`，等于把开头那段反复重写，数据错位；`done` 与请求长度都不减，永远写不完。更要命的是 `n == -1` 时 `done += (size_t)n` 会把 -1 转成极大无符号值，`done` 暴涨到大于 `count` 才退出，函数「假装成功」返回。正确写法是每次传 `p + done` 和 `count - done`，并且先判 `n == -1`（再分 `EINTR`/其它）才动 `done`。

## 2.2.4 close、dup、fcntl 与文件偏移 {#sec-2.2.4}

这一节回答：`close()` 返回 -1 到底该不该重试？`dup`、`dup2`、`fcntl(F_DUPFD)` 复制的是那一格表项还是文件本身？`read`/`write`/`lseek` 管不了的操作，为什么要留给一个 `ioctl`？

::: preview 先抓住一件事
`close` 失败时 Linux 已经把 fd 释放掉了，重试可能关掉别人刚开到的同号 fd，所以只记录不重试。`dup`/`dup2`/`F_DUPFD` 复制的是「同一次打开」，新 fd 与老 fd 共用偏移。剩下的设备专用操作交给 `ioctl`。
:::

### `close()` 的返回值不是废纸

`close(fd)` 成功返回 0，失败返回 -1。失败时 **fd 是否已释放是实现相关的**：Linux 上 `close()` 会先释放 fd，再返回错误（例如 NFS 的写回错误）。因此**不要重试 `close()`**：重试可能关掉另一个线程刚打开的同号 fd。

正确做法：

```c
if (close(fd) == -1) {
    /* 记录错误；不要重试 close */
    log_error("close: %s", strerror(errno));
}
```

对需要确保数据落盘的场景，先 `fsync(fd)`，再 `close(fd)`；不要用 `close` 的返回值判断数据是否安全。

### `dup` 与 `dup2`

```c
int fd2 = dup(fd);                 /* 新 fd，共享同一 struct file（偏移、flags） */
int fd3 = dup2(fd, 1);             /* 把 fd 复制到 1（stdout），原子关闭原 1 */
int fd4 = fcntl(fd, F_DUPFD_CLOEXEC, 0);  /* 新 fd 带 CLOEXEC */
```

`dup2` 的原子性很重要：`close(1); dup(fd);` 在多线程下可能被别的线程抢走 fd 1；`dup2(fd, 1)` 一步完成。

### `fcntl`：改标志、复制 fd、文件锁

```c
int flags = fcntl(fd, F_GETFL);
fcntl(fd, F_SETFL, flags | O_NONBLOCK);   /* 可改：O_APPEND/O_NONBLOCK/O_ASYNC */
/* 不能改访问模式（O_RDONLY/O_WRONLY/O_RDWR）——它在 open 时固定 */
```

`fcntl` 还是文件锁（`F_SETLK`/`F_SETLKW`）的入口，见 [2.3](ch03.md)。

### 偏移：`lseek`、`pread`、`pwrite`

```c
off_t pos = lseek(fd, 0, SEEK_END);       /* 返回新偏移；失败 -1 */
ssize_t n = pread(fd, buf, count, offset); /* 从指定偏移读，不改变 f_pos */
ssize_t m = pwrite(fd, buf, count, offset);
```

`pread`/`pwrite` 把「定位 + 读写」合成一个原子操作，且不改变共享偏移。多线程读同一文件时，用 `pread` 比 `lseek`+`read` 安全。

这四个接口的返回值判错方式互不相同，把判断写错比把逻辑写错更难查。`lseek` 返回的是新偏移，0 完全合法（文件开头就是偏移 0），只有 -1 才是错。`open`、`dup`、`fcntl(F_DUPFD)` 返回的是 fd 号，而 0 是一个合法 fd（标准输入就是这个号），所以判断要写 `== -1` 或 `< 0`；写成 `if ((fd = open(p, O_RDONLY)) <= 0) err;` 会把 stdin 当成打开失败，在重定向过的脚本里随机出错。`read`/`write` 又是另一套：0 有自己的含义（2.2.3）。三套判据背后是同一个问题——返回值到底是「编号」「位置」还是「字节数」，先问清这个，`<=0` 这种写法就出不来。

::: think 为什么 `lseek` 在管道上会失败
管道不是随机访问设备，没有「偏移」概念。`lseek` 返回 `-1`、`errno=ESPIPE`。这不是缺陷，而是统一 I/O 模型的边界：**同一组函数，不同文件类型支持的操作不同**。判断一个 fd 支持什么，用 `fstat` 看类型，或直接处理 `ESPIPE`/`EINVAL`。
:::


### `ioctl`：剩下的那半边接口 {#sec-2.2.4.1}

`read`/`write`/`lseek` 覆盖不了设备的所有操作：设置终端窗口大小、读网卡寄存器、给文件系统打标签、查询块设备扇区大小，都走 `ioctl`。

```c
#include <sys/ioctl.h>
int ioctl(int fd, unsigned long request, ...);   /* 第三个参数通常是指针 */
```

`request` 不是随便一个整数，而是用宏编码的 32 位值：

| 位段 | 宏 | 含义 |
|:--|:--|:--|
| 方向 | `_IOC_NONE/_IOC_READ/_IOC_WRITE/_IOC_READ\|_IOC_WRITE` | 数据流向 |
| 大小 | `_IOC_SIZEBITS`（通常 14 位） | 第三个参数指向的结构体大小 |
| 类型 | `_IOC_TYPEBITS`（8 位） | 设备/子系统的 magic |
| 序号 | `_IOC_NRBITS`（8 位） | 命令编号 |

常用构造宏：`_IO(type,nr)`、`_IOR(type,nr,type)`、`_IOW(type,nr,type)`、`_IOWR(type,nr,type)`。例如 `TIOCGWINSZ` 是「读 `struct winsize`」，`FIONREAD` 是「读一个 `int`」，`FS_IOC_GETFLAGS` 是「读文件 flags」。

```c
/* ioctl_demo.c — 三个真实 request：窗口大小、可读字节数、文件 flags */
#include <fcntl.h>
#include <linux/fs.h>      /* FS_IOC_GETFLAGS */
#include <stdio.h>
#include <sys/ioctl.h>
#include <unistd.h>

int main(void)
{
    struct winsize ws;
    if (ioctl(STDOUT_FILENO, TIOCGWINSZ, &ws) == 0)
        printf("terminal: %ux%u\n", ws.ws_col, ws.ws_row);
    else
        perror("TIOCGWINSZ");       /* 重定向到文件时 ENOTTY 是正常的 */

    int n = 0;
    if (ioctl(STDIN_FILENO, FIONREAD, &n) == 0)
        printf("stdin readable: %d bytes\n", n);

    int fd = open("/tmp/ioctl-demo", O_CREAT | O_RDWR | O_CLOEXEC, 0644);
    if (fd >= 0) {
        int fl = 0;
        if (ioctl(fd, FS_IOC_GETFLAGS, &fl) == 0)
            printf("inode flags: %#x\n", fl);
        close(fd);
    }
    return 0;
}
```

`errno` 的分工：

- `ENOTTY`：这个 fd/设备不支持该 request（最常见；把终端 ioctl 用在普通文件上）。
- `EINVAL`：request 认识，但参数值/结构体内容不合法。
- `EFAULT`：第三个参数指向的地址不可访问。
- `EPERM`：需要 `CAP_SYS_ADMIN`/`CAP_NET_ADMIN` 等。

::: errata ioctl 的四个危险
1. **内核不校验你的指针类型**：`ioctl(fd, FIONREAD, &long_var)` 只写 4 字节，剩下的字节不变；传错结构体会写坏栈。
2. **`_IOR/_IOW` 的大小是 ABI 的一部分**：32 位/64 位程序对同一 request 的结构体大小可能不同，驱动要 compat_ioctl。
3. **不要把 `ioctl` 当通用「发命令」接口**：新子系统优先 netlink/sysfs/configfs；ioctl 的 request 空间是稀缺资源。
4. **`ENOTTY` 不是「不是 tty」**：它只是「这个 fd 不支持这个 request」；普通文件也会返回它。
:::

### 2.2.4 小结

五件事一套判据。`close` 的返回值不能扔：Linux 上失败时 fd 已经释放，重试只会关掉别人的同号 fd，正确动作是记录；要保证数据就先 `fsync` 再 `close`。`dup`/`dup2`/`F_DUPFD` 复制的是表项，新旧 fd 共用偏移与打开标志，`dup2` 强在「关掉目标 fd + 装新表项」一步完成，`F_DUPFD_CLOEXEC` 和 `dup3` 才能顺带把 close-on-exec 一起给定。`fcntl` 改得了 `O_APPEND`/`O_NONBLOCK`/`O_ASYNC`，改不了访问模式——那在 `open` 时就固定了。`lseek` 挪的是共享偏移，`pread`/`pwrite` 把位置当参数、不碰共享状态，多线程因此能安全共用一个 fd。`ioctl` 是内核给设备留的私有后门，命令号与参数类型都由驱动定义，`ENOTTY` 只说明「这条命令这里不认」。如果只记住一件事：**先看返回值是「编号」「位置」还是「字节数」，再决定 0 和 -1 各代表什么——0 号 fd 和偏移 0 都是合法值。**

::: method 即时自测 · 2.2.4

**Q2（辨析）** `dup(fd)` 与第二次 `open(同一路径)` 得到的两个 fd，差别在哪一层？`lseek(fd, 0, SEEK_SET)` 返回 0、`open(p, O_RDONLY)` 返回 0，这两个 0 是一回事吗？`ioctl` 返回 -1/`ENOTTY` 能不能当「这个 fd 不是终端」的判据？

**Q3（应用）** 一个多线程服务用 `lseek(fd, off, SEEK_SET)` 紧接 `read(fd, buf, n)` 让各线程读同一文件的不同位置，结果读回来的内容经常错位到别人的区间。给出两种改法，说明哪一种不需要额外同步、为什么；顺便回答「给每个线程 `dup` 一个 fd」能不能解决。

**A1** 不重试。Linux 的实现是先释放 fd（表项已经删掉、引用计数已减），再把错误码返回来，所以重试等于拿一个已经归还的号再 `close` 一次——那个号很可能刚被另一个线程 `open` 到，你会关掉别人的文件。顺序是 `write`（或批量写）→ `fsync(fd)` → `close(fd)`，持久化由 `fsync` 负责，`close` 的返回值只用来发现「写回阶段失败」这类错误。
**A2** `dup` 复制表项，两个 fd 指向同一个 `struct file`，偏移共享；第二次 `open` 新建 `struct file`，只有 inode 相同。两个 0 都合法：一个是偏移 0（文件开头），一个是 fd 0（标准输入），都不代表失败，所以判据是 `== -1` 或 `< 0`。不能。`ENOTTY` 的语义是「这个 fd 背后的对象不支持这条 request」，普通文件、管道用它都会返回它；要判终端用 `isatty()` 或 `fstat` 看类型位。
**A3** 改法一：`pread(fd, buf, n, off)`——位置和读写合成一次调用，不读写那个共享的 `f_pos`，线程之间不需要再加锁。改法二：每个线程自己 `open` 一份，得到各自的 `struct file` 和各自的偏移，代价是多占 fd 且要注意 `O_CLOEXEC`。`dup` 解决不了：它复制的表项指向同一个 `struct file`，偏移仍然是共享的，`lseek` 照样互相覆盖。只保留 `lseek`+`read` 的话就得给每次「定位+读」加一把锁，性能与简洁都不如 `pread`。
:::

:::

## 2.2.5 原子性：文件系统层面的「要么全做，要么不做」 {#sec-2.2.5}

这一节回答：为什么发布一个配置文件要先写临时文件、再 `rename`，直接改目标不行吗？已经对文件 `fsync` 了，为什么还要给目录再 `fsync` 一次？

::: preview 先抓住一件事
别人任何时刻去看，只看到完整的旧状态或完整的新状态，看不到做了一半——这就是「原子」。文件系统只把三件事做成这样：换一个名字、检查加创建、定位加追加；一整组操作要原子，它不提供。
:::

单条系统调用是原子的，但**多条系统调用之间不是**。文件系统提供了几个原语，把常见组合变成原子操作：

| 需求 | 正确原语 | 错误做法 |
|:--|:--|:--|
| 创建新文件，已存在则失败 | `open(O_CREAT\|O_EXCL)` | `access()` + `open()` |
| 追加写 | `open(O_APPEND)` + 单次 `write` | `lseek(END)` + `write` |
| 原子替换文件 | `rename(tmp, dst)` | 先 `unlink(dst)` 再 `rename` |
| 原子交换两个文件 | `renameat2(..., RENAME_EXCHANGE)` | 两次 `rename` |
| 不覆盖地重命名 | `renameat2(..., RENAME_NOREPLACE)` | `access()` + `rename` |
| 原子创建硬链接 | `link(tmp, dst)` | 先检查再 `link` |

`rename()` 的原子性只保证**同一文件系统内**：目标要么是旧文件，要么是新文件，不会出现「不存在」的中间态。跨文件系统会返回 `EXDEV`，需要「复制到临时文件 + `fsync` + `rename`」的发布流程。

### 为什么是这几个原语，而不是「给一段文件加事务」

原子不是「快」，是「不可分割」：它规定的不是耗时，而是别人在中间时刻去看会看到什么。文件系统能把这几件事做成一步，是因为它们全都收敛到一处元数据的改动。

`rename()` 最能说明问题。目录本身也是一个文件，里面存的是一条条「名字 → inode 号」的目录项，改名改的就是这个数据块里的一处内容。配上文件系统的日志（journal：先把意图记下来，再动真实块，崩溃后照日志重放或撤销），这一处改动要么完整生效要么完全没发生，任何进程在任意时刻去看，都不会撞上「名字不见了」或「半个新文件」。

「把 1 GiB 数据搬进这个文件」做不到同样的保证：数据散在几十万个块里，逐块分配、逐块写，崩溃必然留下中间态。所以原语只覆盖元数据级别的组合——检查加创建、定位加写入、换一个名字、加一个链接，代价固定，效果确定。想要「一组操作要么全做要么全不做」，那是事务，文件系统不提供，得靠数据库自己的 WAL（write-ahead log，先写日志再改数据）加上这里的 `rename` 拼出来。

**持久化的顺序**（写文件并确保崩溃后可见）：

```c
int fd = open(tmp, O_WRONLY | O_CREAT | O_TRUNC, 0644);
write_full(fd, data, len);
fsync(fd);                 /* 1. 数据落盘 */
close(fd);
rename(tmp, dst);          /* 2. 原子替换 */
fsync(dirfd);              /* 3. 目录项落盘（关键且常被忘） */
```

第 3 步常被忽略：`rename` 修改的是目录项，目录本身也需要 `fsync`，否则崩溃后可能看不到新名字。这是「数据库/配置原子发布」的标准套路，详见 [2.3](ch03.md) 与 [3.12](../part3/ch12.md)。

::: ex 例 2.2.3 · 先猜这两个进程的锁文件结局 {#ex-2.2.3}
实例 A、B 在两台 CPU 上同时启动，都要抢 `app.pid` 这个锁文件。写法一：`access("app.pid", F_OK)` 发现不存在，于是 `open("app.pid", O_WRONLY|O_CREAT, 0644)` 写入自己的 pid。写法二：直接 `open("app.pid", O_WRONLY|O_CREAT|O_EXCL, 0644)`，拿到 fd 就写入自己的 pid。先猜：两种写法各自的结局是什么——有几个实例以为自己拿到了锁？输家是「启动失败」还是「毫不知情」？

::: sol 解答
写法一的结局是**两个实例都以为自己拿到了锁**：A 查完到建完之间的窗口里，B 的 `access` 看到的还是「不存在」，两边都建、都写 pid，后写的把先写的盖掉，日志里只剩一个 pid，两个进程却都在跑。写法二的结局是**赢家只有一个**：`O_EXCL` 把「检查不存在」和「创建」并成一次内核调用，输家直接拿到 `EEXIST`，当场知道该退出。窗口的长度不固定——测试里可能一年不出事，出事那天往往是启动脚本同时拉起两个实例。
:::
:::

### 两条语句与一条调用差在哪一刻

把「`access()` 判存在 + `open()`」和「`open(O_CREAT|O_EXCL)`」摆到同一条时间轴上，窗口就露出来了。设实例 A、B 同时启动，锁文件还不存在：

| 时刻 | `access()` + `open()` | `open(O_CREAT\|O_EXCL)` |
|:--|:--|:--|
| t1 | A 查：不存在 | A 创建成功，拿到 fd |
| t2 | B 查：还是不存在（A 尚未建完） | B 创建失败，`errno=EEXIST` |
| 结局 | 两边都写 pid，都以为自己是唯一实例 | 赢家只有一个，输家立刻知道 |

窗口的长度不固定，短到微秒、长到被调度器拉开几毫秒；测试环境里可能一年都不出事，出事那天通常是 systemd 同时拉起两个实例，或者目录里正好躺着上次的残留文件。把两步合成一次内核调用，窗口不是变小而是不存在——这是判断这类代码唯一有用的标准。

### 这条边界上还会踩到的四个点

第一，`rename` 默认覆盖：目标存在就直接换掉，不报错。要拒绝覆盖得用 `renameat2(..., RENAME_NOREPLACE)`，目标已存在时它返回 `EEXIST`；老内核或不支持的文件系统返回 `EINVAL`，这两个错误码的处理方式完全不同，不能合并成一句「失败了」。

第二，临时文件必须和目标在同一个目录、同一个文件系统。`TMPDIR=/tmp`（本机常是 tmpfs）而目标在磁盘上时，`rename` 直接 `EXDEV`，流程退回「复制 + 改名」，而复制过程中按原路径去读的人拿到的是半成品。

第三，只对文件 `fsync` 不够。改名改的是目录的数据，目录页还脏着就掉电，会留下「旧文件还在、新名字没出现」这种最难复现的丢数据；目录要单独 `open(dir, O_RDONLY | O_DIRECTORY)` 再 `fsync`。

第四，这些原语各挡一个窗口，挡不住一整个业务流程。「读配置 → 内存里改 → 写回」即使每一步都不出错，两个进程仍会互相覆盖对方的修改——那需要文件锁，或者在文件头放一个版本号、写回时校验版本、失败就重读重试。

### 2.2.5 小结

原子性不是性能设定，是可观察性设定：它规定别人在中间时刻去看会看到什么。能指望的原语都落在元数据上——`O_CREAT|O_EXCL` 合成检查与创建，`O_APPEND` 合成定位与写入，`rename` 换一个目录项，`link` 加一个名字。它们各自只挡住一个具体窗口，挡不住整段流程：读、改、写回三个动作即使每个都原子，两个进程照样互相覆盖，那要锁或版本号。崩溃可见性那条链有一套固定顺序，数据 `fsync` → `rename` → 目录 `fsync`，少最后一步就可能出现「内容更新了但名字没换」或「新文件消失了」；临时文件和目标不同文件系统时，`rename` 连做都做不到，直接 `EXDEV`。NFS 上这几条语义还要看服务器实现，见 [2.2.16](ch02.md#sec-2.2.16)。如果只记住一件事：**原子性只有「一次内核调用」这一种来源，凡是拆成两条语句的方案，就一定存在一个窗口。**

::: method 即时自测 · 2.2.5
**Q1（记忆）** 本节表格里「追加写」和「原子替换文件」两条，正确原语各自把哪两件事合成了一步？「原子」在这里指的是什么？

**Q2（辨析）** `renameat2(..., RENAME_NOREPLACE)` 比「先 `access()` 再 `rename()`」多了什么保证？为什么 `fsync(fd)` 之后还要对目录 `fsync`？临时文件放在 `/tmp`、目标文件放在数据盘上，这套流程在哪一步断掉？

**Q3（应用）** 某服务把配置「读进内存 → 修改 → 以 `O_TRUNC` 写回同一路径」，两个实例同时改之后，配置文件成了一半 A 一半 B 的东西。写出「原子发布」的完整调用顺序，并给出每一步存在的理由；再说清这套顺序还解决不了哪一类并发问题。

::: sol 答案
**A1** `O_APPEND` 把「定位到当前文件末尾」和「写入」合成一步；`rename(tmp, dst)` 把「让这个名字指向新 inode」和「指向旧 inode」之间的切换合成一步。「原子」指的是别的进程在任何时刻观察，只会看到两个完整状态之一，不会看到中间态——它约束的是可见性，不是速度。
**A2** `access`+`rename` 之间别人可以正好创建出目标，你的改名把它覆盖掉；`RENAME_NOREPLACE` 把「目标不存在」的检查与改名合进一次调用，目标在位时返回 `EEXIST`，老内核或不支持的文件系统返回 `EINVAL`。`fsync(fd)` 只保证那个 inode 的数据（和它自己的元数据）落到磁盘，改名写的是**目录文件**的数据块，那一页还留在页缓存里；掉电后目录回到改名前的状态，新名字就没了。跨设备时 `rename` 直接失败返回 `EXDEV`，只能退回复制，而复制期间按目标路径去读的人会看到半成品，所以临时文件必须与目标同目录。
**A3** 顺序：在同目录用 `open(tmp, O_WRONLY|O_CREAT|O_EXCL, mode)` 建临时文件（`O_EXCL` 防止别人的同名 tmp 被你用覆盖的方式抢掉）→ 循环 `write` 写完全部新内容 → `fsync(tmpfd)` → `close(tmpfd)` → `rename(tmp, cfg)` → `dirfd = open(".", O_RDONLY|O_DIRECTORY)` → `fsync(dirfd)` → `close(dirfd)`。理由依次是：写 tmp 让任何时刻去读配置的人都拿不到半截文件；`fsync` 保证内容先于名字安全；`rename` 完成不可分割的切换；目录 `fsync` 保证这次切换本身在崩溃后还留着。它解决不了「两个实例各自基于自己那份内存改」的丢失更新：两边都能成功发布，后发的覆盖先发的。这类要并发控制的问题得靠文件锁（见 [2.3](ch03.md)）或在配置里带版本号、写回前重读校验。
:::

## 2.2.6 fd 泄漏与 `/proc/self/fd` {#sec-2.2.6}

这一节回答：为什么文件明明删掉了，磁盘空间还是没回来？一个 fd 忘了关，进程是怎么在某个瞬间从「一切正常」变成「什么都打不开」的？

::: preview 先抓住一件事
fd 的上限按**进程**算，用完之后所有需要新 fd 的动作一起失败，现场比内存泄漏突然得多、也免费得多：数一下 `/proc/<pid>/fd` 就知道。删掉的文件空间没回来，通常是还有 fd 指着它——inode 要等最后一个引用关掉才真正释放。
:::

fd 是有限资源。泄漏的表现：`Too many open files`、`accept` 失败、连接随机断。排查三步：

```bash
# 1. 看进程当前 fd 数与上限
ls /proc/$PID/fd | wc -l
cat /proc/$PID/limits | grep 'open files'

# 2. 看 fd 指向什么
ls -l /proc/$PID/fd

# 3. 看哪些 fd 是最近打开的（需要 strace 跟踪）
strace -f -e trace=openat,close -p $PID 2>&1 | tail -50
```

`/proc/self/fd` 是一个魔法目录：读它时，内核把当前进程的 fd 表投影成符号链接，链接目标是打开的文件路径。对已删除文件，链接显示 `(deleted)`——这是「磁盘空间没释放」的经典原因：文件被删了，但仍有进程持有 fd。

```bash
$ ( : > /tmp/del.demo; exec 4<>/tmp/del.demo; rm -f /tmp/del.demo; sleep 60 ) &
$ lsof +L1
COMMAND     PID     USER   FD   TYPE DEVICE SIZE/OFF NLINK    NODE NAME
pipewire 106783 juanwang   36u   REG    0,1     2312     0    2809 /memfd:pipewire-memfd:flags=0x0000000f,type=2,size=2312 (deleted)
pipewire 106783 juanwang   39u   REG    0,1     2312     0    2810 /memfd:pipewire-memfd:flags=0x0000000f,type=2,size=2312 (deleted)
pipewire 106783 juanwang   42u   REG    0,1     2312     0    1767 /memfd:pipewire-memfd:flags=0x0000000f,type=2,size=2312 (deleted)
sleep    107035 juanwang    4u   REG    8,2        0     0 2883714 /tmp/del.demo (deleted)
```

口径：以上是 ubuntu 24.04.5 / aarch64、lsof 4.95.0 上**普通用户**（非 root、`sudo` 不可用）的本机实测；最后那行的 `/tmp/del.demo` 就是上面那条子 shell 造出来的「已删但仍被持有」的文件。读法与三条更正：

- **`DEVICE` 是 `8,2`**（`/dev/sda2`，ext4，`df -T` 可核对），不是旧版正文写的 `253,0`——`253,0` 是 x86 上 device-mapper 常见的major，本机没有它。`SIZE/OFF`、`NODE` 每次跑都不同，唯一稳定的判据是 **`NLINK` 列为 0** 加上名字后面的 `(deleted)`。
- 持有它的那行显示成 `sleep`，不是 `bash`：bash 把子 shell 的**最后一条命令**直接 `exec` 掉了，fd 表跟着继承过去，`lsof` 只按当前进程名报。按名字找进程会找不到，按 `NODE`/`/proc/<pid>/fd` 才稳。
- 本机以普通用户身份只能看见**自己**进程的持有关系（前三行是同用户的 pipewire memfd，`DEVICE 0,1` 是 tmpfs）。旧版那行 `app 1234 root 5w … /var/log/app.log (deleted)` 属于 **root 视角**，本机 `sudo` 不可用，**未实测**——它的形状（`NLINK 0` + `(deleted)`）是对的，数字和用户名是编的。免 `lsof` 的替代读数随时可取：`ls -l /proc/<pid>/fd | grep '(deleted)'`。

`/dev/fd/N` 是 `/proc/self/fd/N` 的符号链接（在 devtmpfs 上）。`open("/dev/fd/N", ...)` 不是「按路径重新打开文件」，而是**复制当前进程的 fd N**（类似 `dup`）：它继承同一个 `struct file` 的偏移与状态。shell 的进程替换 `<(cmd)` 就是让 `cmd` 的 stdout 成为一个 fd，再把 `/dev/fd/63` 传给程序。

```c
int fd = open("/dev/fd/0", O_RDONLY);   /* 复制 stdin，而不是重新打开终端 */
```

三个边界：

- `O_PATH` 打开的 fd 只能用于 `fstat`/`openat`/`fchdir` 等，不能 `read/write`；`/dev/fd/N` 对 `O_PATH` fd 的行为依内核而异。
- 对 socket/pipe，`open("/dev/fd/N")` 可能返回 `ENXIO`/`ENODEV`，因为「重新打开」对这类对象没有意义。
- `O_CLOEXEC` 的 fd 在 `exec` 后消失，`/dev/fd/N` 也就不存在；脚本里依赖它时要确认没有 close-on-exec。

::: method 处理 fd 泄漏的检查清单
1. 每个 `open`/`socket`/`accept`/`dup` 是否都有对应的 `close`（包括错误分支）？
2. `fork` 后子进程是否只保留需要的 fd？是否默认 `O_CLOEXEC`？
3. 长连接服务是否给空闲连接设了超时？`epoll` 是否在 `EPOLLERR/EPOLLHUP` 时关闭并 `epoll_ctl(DEL)`？
4. 是否把 fd 存进容器后忘了在析构/异常路径释放？（C 里用 `goto cleanup`，C++ 用 RAII）
5. 上限是否合理？`ulimit -n`、systemd `LimitNOFILE`、`fs.file-max` 三层都要看。
:::

### 为什么上限卡在进程这一层

fd 表按进程分配，上限是 `RLIMIT_NOFILE`（分软硬两层，软限是你现在撞到的那堵墙，硬限是你允许自己抬高到哪儿）。这么设计是因为「一个进程能同时开多少文件」正好是隔离的单位：只要给每个进程设限，就不会有一个失控的程序把全系统的 `fs.file-max` 吃光。代价是两种「开不开」长得几乎一样，内核却给了不同的错误码：`EMFILE` 是**这个进程**到顶，`ENFILE` 是**整台机器**到顶，后者往往意味着有别的进程在漏，或者限根本就没抬。查泄漏时先分清是哪一种，方向完全不同。

和内存泄漏对比一下，差别就很实用。内存泄漏的曲线是慢慢爬，几小时甚至几天才出事，进程还一直「看起来健康」；fd 泄漏是 1024 个格子内一切正常，填满之后 `open`、`socket`、`accept`、`epoll_create` 在同一秒钟全部失败。更麻烦的是它常带一个二次事故：程序想打开自己的日志记录失败，于是直接退出，现场跟着没了。好消息是证据不要钱——`ls /proc/<pid>/fd | wc -l` 一条命令就给出数字，`ls -l /proc/<pid>/fd` 直接给出每个 fd 指向哪里，不需要符号表、不需要重启进程。

漏的写法就那么几种，而且都不在「正常路径」上：错误分支提前 `return`，跳过了后面的 `close`；循环里每次 `open`、只在循环外 `close` 一次；`dup` 或 `fdopen` 出来的第二个 fd 被当成「同一条记录」而没人负责关；把 fd 塞进长期存活的对象，析构时忘了关；`fork` 后子进程继承整张表又没设 `O_CLOEXEC`，泄漏就顺着 `exec` 传给了别人。至于「删了文件空间没回来」，判据是 `NLINK` 列为 0 加名字后面的 `(deleted)`，各列具体读数见本节上面的读数块。

### 2.2.6 小结

fd 泄漏有三件事值得背下来。单位是进程：`RLIMIT_NOFILE` 的软限决定你什么时候撞墙，`EMFILE` 和 `ENFILE` 分别指向「你到顶了」和「机器到顶了」，先看错误码再决定查谁。症状是断崖：填满之前毫无征兆，之后所有要新 fd 的调用一起失败，别拿内存泄漏那种「慢慢涨」的思路去找它。证据是免费的：数一下 `/proc/<pid>/fd`，再 `ls -l` 看每个 fd 指向哪儿，`strace` 看谁只开不关。删掉的文件还占空间，是因为 inode 上还挂着引用， `(deleted)` 那行就是它的名牌。防的办法不在排查清单里，在写法里：打开时就 `O_CLOEXEC`，每个 `open` 在同一函数里配对 `close`，错误分支走 `goto cleanup` 或 RAII。如果只记住一件事：**fd 泄漏的现场一直摆在 `/proc/<pid>/fd` 里，难的是你愿不愿意先去数那一下。**

## 2.2.7 完整示例：一个正确的文件复制程序 {#sec-2.2.7}

这一节回答：一份「能跑」的复制代码离「正确」还差哪几行？中途崩溃时，留下的是一份完整的新文件，还是一个半截的目标文件？

::: preview 先抓住一件事
这段代码把本章纪律落成五步：打开输入、造临时名、循环搬数据、`fsync` 后 `close`、`rename` 后再 `fsync` 目录，每条错误分支都要清掉临时文件。最关键的一行是 `write_full(out, buf, n)`——按这次真正读到的 `n` 写，不是按缓冲区大小写。
:::

下面这个 `copy.c` 把本章的纪律串起来：`O_CLOEXEC`、`O_EXCL` 可选、短读/短写、`EINTR`、`fsync`、错误分支清理。

```c
/* copy.c — 用法: ./copy SRC DST */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

#define BUF_SIZE (256 * 1024)

static void die(const char *what)
{
    fprintf(stderr, "copy: %s: %s\n", what, strerror(errno));
    exit(EXIT_FAILURE);
}

static ssize_t read_full(int fd, void *buf, size_t count)
{
    size_t done = 0;
    char *p = buf;
    while (done < count) {
        ssize_t n = read(fd, p + done, count - done);
        if (n == -1) {
            if (errno == EINTR) continue;
            return -1;
        }
        if (n == 0) break;
        done += (size_t)n;
    }
    return (ssize_t)done;
}

static int write_full(int fd, const void *buf, size_t count)
{
    size_t done = 0;
    const char *p = buf;
    while (done < count) {
        ssize_t n = write(fd, p + done, count - done);
        if (n == -1) {
            if (errno == EINTR) continue;
            return -1;
        }
        if (n == 0) { errno = EIO; return -1; }
        done += (size_t)n;
    }
    return 0;
}

int main(int argc, char *argv[])
{
    if (argc != 3) {
        fprintf(stderr, "usage: %s SRC DST\n", argv[0]);
        return EXIT_FAILURE;
    }

    int in = open(argv[1], O_RDONLY | O_CLOEXEC);
    if (in == -1) die(argv[1]);

    /* 先创建临时文件，写完再 rename，避免半成品覆盖目标 */
    char tmp[4096];
    snprintf(tmp, sizeof tmp, "%s.tmp.%ld", argv[2], (long)getpid());
    int out = open(tmp, O_WRONLY | O_CREAT | O_EXCL | O_CLOEXEC, 0644);
    if (out == -1) { close(in); die(tmp); }

    char *buf = malloc(BUF_SIZE);
    if (!buf) { close(in); close(out); unlink(tmp); die("malloc"); }

    for (;;) {
        ssize_t n = read_full(in, buf, BUF_SIZE);
        if (n == -1) { close(in); close(out); unlink(tmp); die("read"); }
        if (n == 0) break;
        if (write_full(out, buf, (size_t)n) == -1) {
            close(in); close(out); unlink(tmp); die("write");
        }
    }

    if (fsync(out) == -1) { close(in); close(out); unlink(tmp); die("fsync"); }
    if (close(out) == -1) { close(in); unlink(tmp); die("close out"); }
    if (close(in) == -1) { unlink(tmp); die("close in"); }

    if (rename(tmp, argv[2]) == -1) { unlink(tmp); die("rename"); }

    /* 目录项落盘；打开目录需要 O_DIRECTORY */
    int dir = open(".", O_RDONLY | O_DIRECTORY | O_CLOEXEC);
    if (dir != -1) { fsync(dir); close(dir); }

    free(buf);
    return EXIT_SUCCESS;
}
```

编译与验证：

```bash

truncate -s 100M big.bin
./copy big.bin big.copy
cmp big.bin big.copy && echo "identical"
strace -e trace=openat,read,write,fsync,rename ./copy big.bin big.copy 2>&1 | tail -20
```

::: sol 解答
管道上不会：本机实测（2.2.12 的 `shortio.c`）第一次只落进 65536 字节，返回正值、`errno` 为 0，紧接着再写才拿到 `EAGAIN`。普通文件上通常一次写满，但磁盘配额、`RLIMIT_FSIZE`、信号打断或 `O_NONBLOCK` 设备都可能让它短写。无论哪种，**正确处理方式相同**：循环写剩余部分，直到写完或真错误。上面的 `write_full` 就是最小实现。

如果 `write` 返回 `-1` 且 `errno == ENOSPC`，不要重试；先清理空间。如果 `errno == EAGAIN`，说明 fd 是非阻塞的，应该等可写事件（`epoll`）而不是忙等。

### 逐段读：五步各挡住哪一种事故

前两步管「进门」和「不留半成品」。输入用 `O_RDONLY | O_CLOEXEC` 打开：按最小权限来，且就算后面有人 `fork+exec`，这个 fd 也不会漏给子程序（2.2.2）。输出走临时名加 `O_CREAT | O_EXCL`：整个复制过程中目标文件一直保持着完整的旧内容，出错或崩溃留下的只有 `.tmp.<pid>` 这种临时文件，而不是半截的新文件；`O_EXCL` 还顺手挡住两个进程同时往同一目标复制时互相踩。

后三步管「搬干净」和「收得稳」。循环里 `read_full` 允许短读，只有返回 0 才算读完；`write_full` 只写这次真正读到的字节。收尾顺序是 `fsync(out)` → `close(out)` → `rename` → `fsync(目录)`，前三步见 2.2.5 与 2.2.8。第五步藏在每条错误分支里：`unlink(tmp)`，别把垃圾留在别人的目录里。

和最常见的朴素写法对比，差别才看得清。用 `fopen`/`fread`/`fwrite` 直接写目标：`fwrite` 返回的个数不足时，你分不清是「就这么大」还是「磁盘满了」，不查 `ferror` 就没有人知道；中途失败留下的是半截目标文件，原来的内容已经没了。系统调用版本把每次传输的数量都摆在返回值上，每次失败都带 `errno`，代价是代码多出几十行。到底对不对，用本节上面那段命令里的 `cmp` 和 `strace` 自己核对。

三个坑都真会踩。`write_full(out, buf, (size_t)n)` 若写成 `BUF_SIZE`，短读之后会把缓冲区里的残留字节再写一遍：长度对、内容错。`snprintf(tmp, sizeof tmp, ...)` 在目标名很长时静默截断，你得到的是另一个名字的文件，且不报任何错。目标权限被硬编码成 `0644`，还要再过一层 `umask`，源文件是 `0600` 也不会保留——要保权限就得先 `fstat` 再 `fchmod`。

### 2.2.7 小结

这个程序没有用任何一个新函数，它只是把前面几节的规则按顺序摆对：打开时定好模式与 `O_CLOEXEC`，创建时用 `O_EXCL` 抢一个独占的临时名，搬运时按返回值推进而不是按请求长度推进，收尾时先 `fsync` 再 `close`、`rename` 之后再补一次目录 `fsync`，每条失败路径都 `unlink`。判据也具体：短读不是错误、返回 0 才结束；`close` 的失败要记录但不能重试；崩溃后目录里只该多出临时文件，不该出现半截目标。它同时留了三处「还能更好」的缺口——临时名只带 pid、权限没继承、大缓冲区靠 `malloc` 一次成功。如果只记住一件事：**「原子发布」的全部诀窍是先写到别的名字上，确认落盘之后再用一次 `rename` 换上去——不被看到半成品靠改名，内容真掉到设备上靠 `fsync`，这两件事谁都替代不了谁。**

## 2.2.8 性能与页缓存 {#sec-2.2.8}

这一节回答：程序一路返回成功，机器重启后文件却是半截的，中间哪一步骗了你？想提吞吐，先换更大的缓冲区，还是先少调几次 `fsync`？

::: preview 先抓住一件事
`write` 返回时，数据多半只进了 page cache（页缓存：内核用内存暂存文件内容的地方），「等磁盘」被挪到后台回写。换来的是吞吐，代价是「返回成功」不再等于「掉电也还在」。要真落盘就 `fsync`，改名后的目录项还要再 `fsync` 一次目录。
:::

{{#include ../assets/figures/io-path.md}}

四个常被忽略的事实：

1. **`write()` 返回只代表数据进了 page cache**（除非 `O_DIRECT`/`O_SYNC`）。机器掉电时，未回写的数据会丢；进程崩溃不会丢（页缓存仍在内核）。
2. **`read()` 命中 page cache 时完全不碰磁盘**。第一次读触发预读（readahead），顺序读的吞吐远高于随机读。
3. **`fsync()` 的代价是等待设备确认**。批量写 + 一次 `fsync` 远快于每条记录 `fsync`；数据库的 WAL 就是按这个原则设计的。
4. **`O_DIRECT` 绕过 page cache，但要求对齐**（缓冲区地址、偏移、长度都按块大小对齐）。除非你在写数据库/存储引擎，否则不要轻易用。

```c
/* 建议内核预读：顺序读用 POSIX_FADV_SEQUENTIAL，随机读用 RANDOM */
posix_fadvise(fd, 0, 0, POSIX_FADV_SEQUENTIAL);
/* 不再需要这部分缓存：DONTNEED 可以释放 page cache */
posix_fadvise(fd, 0, 0, POSIX_FADV_DONTNEED);
```

::: method 文件 I/O 性能排查顺序
1. **确认瓶颈在 I/O 还是 CPU**：`iostat -x 1` 看 `%util`、`await`、`aqu-sz`；
2. **看是否命中缓存**：`free -h` 的 `buff/cache`、`/proc/meminfo` 的 `Cached`；
3. **看读写比例与块大小**：`iostat -x` 的 `r/s`、`w/s`、`rareq-sz`、`wareq-sz`；
4. **看是否同步写**：`strace -c -e trace=fsync,fdatasync`；
5. **看文件系统与挂载选项**：`findmnt -T /path`，是否有 `noatime`、`discard`；
6. **最后才调内核参数**：`vm.dirty_ratio`、`vm.dirty_background_ratio`、`vm.swappiness`。

### 页缓存建议：`posix_fadvise` 与 `madvise` {#sec-2.2.8.1}

`posix_fadvise(fd, offset, len, advice)` 不改变数据，只告诉内核「这段文件我打算怎么用」：

| advice | 含义 | 典型场景 |
|:--|:--|:--|
| `POSIX_FADV_NORMAL` | 默认 | 恢复默认 |
| `POSIX_FADV_SEQUENTIAL` | 顺序读，预读加倍 | 大文件扫描 |
| `POSIX_FADV_RANDOM` | 随机读，关闭预读 | 数据库索引 |
| `POSIX_FADV_WILLNEED` | 提前读入页缓存 | 启动预取 |
| `POSIX_FADV_DONTNEED` | 尝试丢弃干净页 | 备份后释放缓存 |
| `POSIX_FADV_NOREUSE` | 提示页替换算法可忽略该区间的访问；Linux 2.6.18–6.2 上是 no-op，6.3+ 只影响已映射页 | 大文件流式读（不保证「读一次就丢弃」） |

这张表里最容易误用的是 `NOREUSE`：它**不会**把数据从页缓存里赶出去；要释放缓存用 `POSIX_FADV_DONTNEED`（上一行），且只对干净页生效。

`madvise(addr, len, advice)` 作用于 **mmap 的虚拟区间**，不是 fd；`MADV_SEQUENTIAL/RANDOM/WILLNEED/DONTNEED` 与 fadvise 对应，`MADV_HUGEPAGE`/`MADV_NOHUGEPAGE` 控制 THP。

::: errata fadvise 不是「立即释放」
`POSIX_FADV_DONTNEED` 只丢弃**干净**页；脏页要先回写。它也不保证立刻回收，只是给内核一个提示。不要把 `fadvise(DONTNEED)` 当成 `drop_caches` 或内存泄漏的解药。
:::

### 页缓存把成本挪到哪里去了

内核为什么不干脆等磁盘写完再返回？因为「写 4 KiB 进内存」和「让设备确认」的成本差了几个量级：进内存是几百纳秒，等闪存是几十微秒，等机械盘是几毫秒。每次都等，程序的时间就全花在等待上。页缓存的方案是先收下、立刻返回，把同一文件短时间内的多次写攒成一次大块顺序写，再按脏页水位交给设备——`vm.dirty_background_ratio` 决定后台回写什么时候开始，`vm.dirty_ratio` 决定写者什么时候被迫自己停下来等。

这条设计直接给出两个判据。一是**攒批比换大缓冲区值钱**：同样写完 40 MiB，每次 4 KiB 要 10240 次系统调用，每次 256 KiB 只要 160 次；而真正落到设备上的次数由内核合并决定，跟你切多细无关。二是**同步点很贵**：每条记录一次 `fsync`，等于把攒批的收益原地退回去。数据库把多个事务的同步合并成一次，才有 WAL 的组提交。

新手混得最多的三件事：`fflush` 之后数据就安全了吗？没有，它只把 C 库的用户态缓冲交给内核，仍停在页缓存。进程崩溃数据会丢吗？不会，页缓存属于内核，进程死了它还在，会丢的是整机掉电时那些还没回写的脏页。`fsync(fd)` 返回就万事大吉了吗？新建或改名过的文件还要对那个目录再 `fsync` 一次，否则数据在、名字可能不在。这三步在内核里各走到哪一层，2.2.17 有完整路径。

### 2.2.8 小结

判据只有一句：`write` 返回说明「内核收到了」，`fsync` 返回才说明「设备收下了」。页缓存把等磁盘从每次调用挪到后台回写，顺序读靠预读、顺序写靠合并，所以收益来自「少而大的写入」和「更少的同步点」，不是把 `read` 循环改得更花哨。`posix_fadvise` 与 `madvise` 都只是提示：`SEQUENTIAL`/`RANDOM` 调预读，`DONTNEED` 只丢干净页，`NOREUSE` 既不赶缓存也不保证读一次就扔。`O_DIRECT` 真的绕过页缓存，代价是地址、长度、偏移三者都要对齐。如果只记住一件事：**崩溃丢的是用户态缓冲，掉电丢的是页缓存里的脏页——先分清你的对手是哪一个，才知道要不要 `fsync`。**

**Q2（辨析）** `fflush(fp)` 和 `fsync(fd)` 是一回事吗？`POSIX_FADV_NOREUSE` 和 `POSIX_FADV_DONTNEED` 谁真能把内存腾出来？`O_SYNC` 和 `O_DIRECT` 都被人说成「绕缓存」，绕的是同一层吗？

**Q3（应用）** 一个服务往本地文件逐条写日志，每条记录后面都 `fsync` 一次，QPS 怎么都上不去。给出两处改动，并说清各自牺牲了什么。

::: sol 答案
**A1** `write` 成功时数据通常只在页缓存里，还没上设备；`fsync` 返回才等到设备确认（含元数据的那部分要另外 `fsync` 目录）。进程崩溃不丢页缓存里的内容，因为它归内核；整机掉电会丢还没回写的脏页。
**A2** 不是一回事：`fflush` 只把用户态缓冲倒进内核，`fsync` 才把内核里的脏页推到设备。腾内存只能靠 `DONTNEED`，而且只对干净页生效；`NOREUSE` 是给替换算法的一句提示。`O_SYNC` 不绕页缓存，数据照走内存，只是每次写都等到设备确认；`O_DIRECT` 才真的绕开页缓存，并要求对齐。
**A3** 一处是把「每条一次 `fsync`」改成「一批一次」或按时间合并，代价是崩溃窗口从一条日志变成一批；另一处是改用 `fdatasync`，只同步数据、能省就省掉元数据，或者干脆把日志写成追加大缓冲、只在关键检查点同步。两者牺牲的都是「这一刻已经落盘」这个保证，不是数据本身。
:::

## 2.2.9 `open` flags 全表：从 `O_RDONLY` 到 `O_TMPFILE` {#sec-2.2.9}

这一节回答：`open` 的第三个参数之前，那一串 `O_*` 到底各改了什么行为？哪些能组合，哪些组合会被内核静默忽略？

::: preview 先抓住一件事
这二十来个 `O_*` 不是一张平铺的清单，而是四类：**访问模式**（`O_RDONLY`/`O_WRONLY`/`O_RDWR`，三选一，不能相加）、**行为位**（`O_APPEND`、`O_NONBLOCK`、`O_SYNC` 这类，可以累加）、**创建与截断**（`O_CREAT`/`O_EXCL`/`O_TRUNC`/`O_TMPFILE`）、**路径解析与 fd 继承**（`O_PATH`、`O_NOFOLLOW`、`O_DIRECTORY`、`O_CLOEXEC`）。八进制值这一栏要当成「本机档案」读：aarch64 与 x86-64 的高位标志分属两套定义，抄错一位就把 `O_DIRECT` 念成了 `O_DIRECTORY`。
:::

2.2.2 给了最常用的四个组合。真实程序还会遇到 `O_PATH`、`O_TMPFILE`、`O_DIRECT`、`O_SYNC` 这些「用错就性能塌方或直接失败」的标志。先把它们按作用域分组：

| 组 | flag | x86-64 八进制（文献值，未实测） | aarch64 八进制（本机实测） | 作用 | 失败/边界 |
|:--|:--|--:|--:|:--|:--|
| 访问模式 | `O_RDONLY` | 0 | 0 | 只读 | 与 `O_WRONLY`/`O_RDWR` 互斥 |
| | `O_WRONLY` | 01 | 01 | 只写 | |
| | `O_RDWR` | 02 | 02 | 读写 | |
| 创建 | `O_CREAT` | 0100 | 0100 | 不存在则创建，需 `mode` | 父目录不可写 `EACCES` |
| | `O_EXCL` | 0200 | 0200 | 与 `O_CREAT` 合用，已存在则 `EEXIST` | 单独用被忽略 |
| | `O_TRUNC` | 01000 | 01000 | 存在则截断为 0 | 对 FIFO/终端未定义 |
| | `O_TMPFILE` | 020200000 | **020040000** | 在目录中创建无名文件 | 需文件系统支持，否则 `EOPNOTSUPP` |
| 偏移/阻塞 | `O_APPEND` | 02000 | 02000 | 每次写前定位到末尾 | 与 `pwrite` 在 Linux 上冲突 |
| | `O_NONBLOCK` | 04000 | 04000 | 非阻塞 | 对普通文件基本无效 |
| | `O_ASYNC` | 020000 | 020000 | 可读/可写时发 `SIGIO` | Linux 上 open 时无效，需 `F_SETFL` + `F_SETOWN` |
| 同步 | `O_DSYNC` | 010000 | 010000 | 数据+必要元数据落盘 | 每次 `write` 等设备 |
| | `O_SYNC` | 04010000 | 04010000 | 数据+全部元数据落盘 | 比 `O_DSYNC` 更贵 |
| | `O_RSYNC` | 与 `O_SYNC` 同值 | 与 `O_SYNC` 同值（`04010000`） | 读也同步 | Linux 上等同 `O_SYNC` |
| 缓存/对齐 | `O_DIRECT` | 040000 | **0200000** | 绕过 page cache | 地址/偏移/长度要对齐，否则 `EINVAL` |
| | `O_NOATIME` | 01000000 | 01000000 | 读不更新 atime | 非属主且无 `CAP_FOWNER` 返回 `EPERM` |
| 路径解析 | `O_NOFOLLOW` | 0400000 | **0100000** | 最后一段是符号链接则 `ELOOP` | 只作用于最后一段 |
| | `O_DIRECTORY` | 0200000 | **040000** | 必须是目录，否则 `ENOTDIR` | 常与 `O_PATH` 合用 |
| | `O_PATH` | 010000000 | 010000000 | 只取「路径句柄」，不打开读写 | `read`/`write` 返回 `EBADF` |
| fd 继承 | `O_CLOEXEC` | 02000000 | 02000000 | `exec` 时关闭 | 创建时原子设置 |
| 历史 | `O_LARGEFILE` | 0100000 | **0**（用户态宏）；内核 UAPI 头写 `0400000` | 64 位偏移 | 64 位平台无效果 |

两列的口径不同，别混着用。**x86-64 那一列来自文献**：本套件没有 x86 机器，那一列一个数都没有实测过，只能当「另一套表的形状」读。**aarch64 那一列是本机实测**——ubuntu 24.04.5 / aarch64、glibc 2.39，把每个宏 `printf("%o", …)` 打出来（`O_DIRECT`、`O_NOFOLLOW` 要 `_GNU_SOURCE` 才可见）。

两列共有**五行**不同：`O_TMPFILE`、`O_DIRECT`、`O_NOFOLLOW`、`O_DIRECTORY`、`O_LARGEFILE`。后四个不是「数值大小变了」，而是**同一组八进制值被两两换了名字**：本机打印出来的是 `040000`、`0200000`、`0100000`、`0400000` 这四个数，分配给 `O_DIRECTORY=040000`、`O_DIRECT=0200000`、`O_NOFOLLOW=0100000`、`O_LARGEFILE=0400000`；表左那列（文献值，未实测）给的是同样这四个数，但分配成 `O_DIRECT=040000`、`O_DIRECTORY=0200000`、`O_LARGEFILE=0100000`、`O_NOFOLLOW=0400000`——`O_DIRECT` 与 `O_DIRECTORY` 互换、`O_LARGEFILE` 与 `O_NOFOLLOW` 互换。所以照抄的后果不是「差一点」，而是**成对念反**：把本机的 `040000` 当 `O_DIRECT` 读，就会把一个「必须是目录」的 fd 看成「绕过页缓存」。

`O_TMPFILE` 跟着遭殃，因为它是 `__O_TMPFILE | O_DIRECTORY`（本机 `bits/fcntl-linux.h` 原文 `(020000000 | __O_DIRECTORY)`），`020000000 | 040000` = 本机实测的 `020040000`，而按表左那列的 `__O_DIRECTORY`（`0200000`）就得 `020200000`。`O_LARGEFILE` 还要再叠一层：本机用户态宏直接展开成 **0**（LP64 下应用程序不需要传这一位），而内核 UAPI 头 `asm/fcntl.h` 写着 `0400000`——同一个名字在两个头文件里不是一回事，`fdinfo` 那一格用的是内核那套（2.2.18 有实测对照与差法）。

反过来，**低位与同步类的标志两架构相同**：`O_CREAT`、`O_EXCL`、`O_TRUNC`、`O_APPEND`、`O_NONBLOCK`、`O_ASYNC`、`O_DSYNC`、`O_SYNC`、`O_NOATIME`、`O_PATH`、`O_CLOEXEC` 在本机打印出来与 x86-64 列逐位一致。这一句同时也是旧版本那条免责声明的更正：它当时举的例子是「`O_DIRECT`、`O_SYNC` 可能不同」，实测下来 `O_SYNC`/`O_DSYNC` 两架构同值，真正随架构变的是上面那五个。结论不变而且更强：**源码里只用宏，不要把任何一个八进制数写死**；要读别人机器上的 `fdinfo`、`strace` 数值，先在本机把宏打印一遍再对位。

### `O_PATH`：一个只有「路径」的 fd

`O_PATH` 打开的文件描述符不能读、不能写、不能 `mmap`，但可以：

- 作为 `*at()` 系列的 `dirfd`（`openat`、`fstatat`、`unlinkat`、`linkat` 的源）；
- `fstat` 取属性；
- `readlink("/proc/self/fd/N")` 取回路径；
- 配合 `O_NOFOLLOW` 安全地「引用一个符号链接本身」。

它对权限的要求也不同：只需要路径上各级目录的 `x` 位，不需要目标文件本身的读权限。这让它成为「先锚定、后操作」的理想句柄。

```c
int pfd = open("/srv/data", O_PATH | O_DIRECTORY | O_CLOEXEC);
int fd  = openat(pfd, "config.json", O_RDONLY | O_NOFOLLOW);
```

`O_PATH` 的 fd 还有一个特殊能力：可以传给 `fchdir`，也可以作为 `execveat` 的 `dirfd`（配合 `AT_EMPTY_PATH`）。它不能传给 `read`/`write`/`fchmod` 这类需要「已打开文件」的调用。

### `O_TMPFILE`：没有名字的文件

```c
int fd = open("/srv/app", O_TMPFILE | O_WRONLY | O_CLOEXEC, 0644);
/* 写入、fsync，然后给它一个名字 */
linkat(fd, "", AT_FDCWD, "/srv/app/conf.new", AT_EMPTY_PATH);
```

`O_TMPFILE` 的路径参数必须是**目录**，内核在该目录所在文件系统里创建一个没有目录项的 inode。它适合「先写完整、再原子发布」：写一半崩溃不会留下垃圾文件。限制：

- 文件系统必须支持（ext4、XFS、tmpfs、btrfs 支持；部分网络文件系统不支持）；
- `linkat(fd, "", ..., AT_EMPTY_PATH)` 不检查「谁创建的」：任何持有该 fd 的进程都能链接——fd 经 `SCM_RIGHTS` 传给另一个进程后，对方同样可以 `linkat`；
- 不能跨文件系统：`linkat` 的目标目录与临时文件必须同属一个文件系统，否则 `EXDEV`；
- 如果打开时带了 `O_EXCL`，则**永久不能** `linkat`（用于纯临时文件）；
- `AT_EMPTY_PATH` 这一步要不要特权：**手册要，本机内核没有拦**。`linkat(2)` 写的是「The caller must have the `CAP_DAC_READ_SEARCH` capability in order to use this flag」，还专门给 `ENOENT` 留了「带 `AT_EMPTY_PATH` 但没有这个能力」这一条错误。本机（ubuntu 24.04.5 / aarch64、内核 7.0.0-38、`uid=1000`、`/proc/self/status` 里 `CapEff=0000000000000000`，即有效能力为空，`capsh --decode` 确认 `cap_dac_read_search` 只在 bounding set 不在 effective set）实测四种 fd 全部返回 `0`：`O_TMPFILE|O_RDWR` 的 fd、`O_RDONLY` 的 fd、`O_WRONLY` 的 fd、以及 `O_PATH` 的 fd。`strace` 能证明这不是走了什么回退——每个用例都只有一次 `linkat(3, "", AT_FDCWD, "...", AT_EMPTY_PATH) = 0`。边界也实测了：把自家文件 `chmod 000`（同一个进程随后 `open(..., O_RDONLY)` 报 `errno=13 (Permission denied)`），再用 `O_PATH` fd 去 `linkat(AT_EMPTY_PATH)`，仍然返回 `0`，而新名字读起来还是 `Permission denied`——建硬链接本来就不需要读权限，这条不是提权口子。结论：**别把「普通用户这步必然失败」写进设计**，也别用它当安全边界；跨内核的可移植写法依然是 `linkat(AT_FDCWD, "/proc/self/fd/N", ..., AT_SYMLINK_FOLLOW)`（本机实测同样返回 `0`，两条路都通）。

### `O_NOFOLLOW` 与 `O_DIRECTORY`

`O_NOFOLLOW` 只检查**路径的最后一段**。`open("/a/b/link", O_NOFOLLOW)` 在 `link` 是符号链接时返回 `ELOOP`（不是 `EINVAL`，也不是 `EMLINK`）；中间目录里的符号链接仍会被跟随。要禁止整条路径中的符号链接，用 `openat2` 的 `RESOLVE_NO_SYMLINKS`（2.2.10）。

`O_DIRECTORY` 要求打开对象是目录，否则 `ENOTDIR`。它常与 `O_PATH` 组合，得到一个「只能当锚点」的目录 fd；`opendir` 内部也会检查目录类型。

### `O_SYNC`、`O_DSYNC`、`O_ASYNC`

三个名字很像，语义完全不同：`O_DSYNC` 在 `write` 返回前把**数据**和「读回数据所必需的元数据」落盘；`O_SYNC` 连 mtime/ctime 等全部元数据都要落盘，等价于每次写完 `fsync`；`O_ASYNC` 与同步无关，它是 fd 可读/可写时发 `SIGIO`；Linux 上在 `open` 时指定它没有实质效果，必须用 `F_SETFL` 开启并配合 `F_SETOWN`，`epoll` 时代基本不用。`O_SYNC` 的代价是一次 4 KiB 写要等设备确认，机械盘上可能是毫秒级；批量导入时 `O_DSYNC` 或「写完统一 `fsync`」通常快一个数量级。

```c
/* openflags.c — 验证 O_PATH/O_NOFOLLOW/O_DIRECTORY/O_TMPFILE 的边界 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

static void show_err(const char *what)
{
    printf("%-38s -> %s\n", what, strerror(errno));
}

int main(void)
{
    char path[] = "/tmp/openflags.XXXXXX";
    int tfd = mkstemp(path);
    if (tfd == -1) { perror("mkstemp"); return 1; }
    if (write(tfd, "x", 1) != 1) { perror("write"); return 1; }
    close(tfd);

    /* 1. O_PATH：能 fstat，不能 read */
    int pfd = open(path, O_PATH | O_CLOEXEC);
    if (pfd == -1) { perror("open O_PATH"); return 1; }
    struct stat st;
    printf("O_PATH fstat: %s\n", fstat(pfd, &st) == 0 ? "ok" : strerror(errno));
    errno = 0;
    char c;
    ssize_t n = read(pfd, &c, 1);
    printf("O_PATH read: n=%zd errno=%d (%s)\n", n, errno, strerror(errno));

    char proc[64], target[256];
    snprintf(proc, sizeof proc, "/proc/self/fd/%d", pfd);
    ssize_t k = readlink(proc, target, sizeof target - 1);
    if (k > 0) { target[k] = '\0'; printf("O_PATH 指向: %s\n", target); }
    close(pfd);

    /* 2. O_NOFOLLOW：最后一段是符号链接 -> ELOOP */
    char link[] = "/tmp/openflags.link";
    unlink(link);
    if (symlink(path, link) == -1) { perror("symlink"); return 1; }
    errno = 0;
    int lfd = open(link, O_RDONLY | O_NOFOLLOW);
    printf("open(symlink, O_NOFOLLOW): fd=%d errno=%d (%s)\n",
           lfd, errno, strerror(errno));
    if (lfd != -1) close(lfd);

    /* O_PATH|O_NOFOLLOW 可以拿到链接本身 */
    lfd = open(link, O_PATH | O_NOFOLLOW | O_CLOEXEC);
    printf("open(symlink, O_PATH|O_NOFOLLOW): %s\n",
           lfd == -1 ? strerror(errno) : "ok");
    if (lfd != -1) close(lfd);
    unlink(link);

    /* 3. O_DIRECTORY 对普通文件 -> ENOTDIR */
    errno = 0;
    int dfd = open(path, O_RDONLY | O_DIRECTORY);
    printf("open(file, O_DIRECTORY): fd=%d errno=%d (%s)\n",
           dfd, errno, strerror(errno));
    if (dfd != -1) close(dfd);

    /* 4. O_TMPFILE：无名文件，linkat 给它名字 */
    int anon = open("/tmp", O_TMPFILE | O_RDWR | O_CLOEXEC, 0600);
    if (anon == -1) {
        show_err("open(/tmp, O_TMPFILE)");
    } else {
        if (write(anon, "tmp", 3) != 3) perror("write tmpfile");
        char named[] = "/tmp/openflags.linked";
        unlink(named);
        char proc[64];
        snprintf(proc, sizeof proc, "/proc/self/fd/%d", anon);
        /* AT_EMPTY_PATH：手册要求 CAP_DAC_READ_SEARCH，本机非特权实测直接返回 0；
         * 老内核上它会失败，那时再走 /proc 路径 */
        if (linkat(anon, "", AT_FDCWD, named, AT_EMPTY_PATH) == -1 &&
            linkat(AT_FDCWD, proc, AT_FDCWD, named, AT_SYMLINK_FOLLOW) == -1)
            show_err("linkat");
        else
            printf("O_TMPFILE linkat: ok -> %s\n", named);
        close(anon);
        unlink(named);
    }

    /* 5. F_GETFL 读回状态标志（访问模式不可改，但可读） */
    int fd = open(path, O_WRONLY | O_APPEND | O_NONBLOCK | O_CLOEXEC);
    if (fd == -1) { perror("open flags"); return 1; }
    int fl = fcntl(fd, F_GETFL);
    printf("F_GETFL: append=%d nonblock=%d accmode=%d\n",
           !!(fl & O_APPEND), !!(fl & O_NONBLOCK), fl & O_ACCMODE);
    close(fd);
    unlink(path);
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 openflags.c -o openflags
./openflags
# O_PATH fstat: ok
# O_PATH read: n=-1 errno=9 (Bad file descriptor)
# O_PATH 指向: /tmp/openflags.6jbhh1
# open(symlink, O_NOFOLLOW): fd=-1 errno=40 (Too many levels of symbolic links)
# open(symlink, O_PATH|O_NOFOLLOW): ok
# open(file, O_DIRECTORY): fd=-1 errno=20 (Not a directory)
# O_TMPFILE linkat: ok -> /tmp/openflags.linked
# F_GETFL: append=1 nonblock=1 accmode=1
```

八行都是 ubuntu 24.04.5 / aarch64（内核 7.0.0-38）本机实测原样输出（旧版正文这里少贴了两行：`O_PATH 指向:` 与 `open(symlink, O_PATH|O_NOFOLLOW): ok`）。`/tmp/openflags.6jbhh1` 的随机后缀由 `mkstemp` 决定，每次跑都不同，其余各行逐字可复现。特别说明第 7 行：**它的 `ok` 来自第一条 `linkat(..., AT_EMPTY_PATH)` 本身成功**，不是走 `/proc/self/fd/N` 的回退——程序里那两条 `linkat` 是「第一条失败才试第二条」的短路写法，本机第一条就返回 0，所以第二条根本没执行（把回退删掉重跑，读数不变，仍是 `ok`；这一条与 [2.2.2](ch02.md#sec-2.2.2) 补的权限说明是一对）。

`O_NOFOLLOW` 的错误码是 `ELOOP` 而不是 `EINVAL`，这是排障时最容易查错的地方。`F_GETFL` 的返回值里包含访问模式（用 `O_ACCMODE` 掩出低两位），不要把它当成纯状态位；`O_CLOEXEC` 属于 fd 标志，用 `F_GETFD` 查。

::: errata `open` flags 的六个坑
1. **「`O_TRUNC` 加 `O_RDONLY` 也能截断」**——POSIX 说未定义；Linux 上可能截断，但不要依赖。要截断就显式用 `O_WRONLY`/`O_RDWR`。
2. **「`O_EXCL` 可以单独用于锁」**——没有 `O_CREAT` 时它被忽略；锁文件必须 `O_CREAT|O_EXCL`。
3. **「`O_APPEND` 的 fd 上 `pwrite` 在指定偏移写」**——Linux 违反 POSIX，仍追加到末尾（见 2.2.14）。
4. **「`O_DIRECT` 只要文件系统支持就行」**——缓冲区地址、偏移、长度都要对齐；栈上的 `char buf[4096]` 不保证 4096 对齐，必须 `posix_memalign`。
5. **「`O_NONBLOCK` 对普通文件没用，所以可以随便加」**——对普通文件确实基本无效，但它会改变 `open` 自身在 FIFO/设备上的阻塞行为；对 FIFO 只读打开且无写者时，`O_NONBLOCK` 决定是立刻成功还是阻塞。
6. **「`O_CLOEXEC` 只影响 `exec`，不影响 `fork`」**——正确，但 `fork` 后子进程继承 fd；如果子进程立刻 `exec`，`CLOEXEC` 才生效。要在 `fork` 后就关闭，得在子进程里显式 `close` 或用 `close_range`。
:::


### 临时文件：`mkstemp`、`tmpfile` 与 `O_TMPFILE` 怎么选 {#sec-2.2.9.1}

自己拼 `/tmp/myapp-XXXX` 再 `open(O_CREAT|O_EXCL)` 看似安全，但很容易在「检查—创建」之间被抢占。标准库的 `mkstemp` 把「生成唯一名 + `O_CREAT|O_EXCL|O_RDWR` + 0600」合成一个调用：

```c
#include <stdlib.h>
char tmpl[] = "/tmp/myapp-XXXXXX";     /* 必须是可写的 char 数组 */
int fd = mkstemp(tmpl);                 /* 成功返回 fd，tmpl 被改写为实际路径 */
if (fd < 0) { perror("mkstemp"); return 1; }
unlink(tmpl);                           /* 立刻删名：fd 仍可用，进程退出自动回收 */
write(fd, "data", 4);
close(fd);
```

| 方案 | 名字 | 权限 | 自动删除 | 适用 |
|:--|:--|:--|:--|:--|
| `mkstemp` | 有，返回路径 | 0600 | 手动 `unlink` | 需要把路径交给别的程序 |
| `tmpfile()` | 无 | 0600 | `fclose` 自动删 | 纯本进程临时流 |
| `O_TMPFILE` | 无 | 由 mode/umask | 不 `linkat` 就自动回收 | 先写完整、再原子发布 |

::: errata 临时文件的三个坑
1. **`mkstemp` 的模板必须以 6 个 `X` 结尾**；少一个就失败，多一个不会被替换。
2. **不要在 `mkstemp` 后再 `chmod` 成 0644**：临时文件默认 0600 是有意的；要给别的用户读，用 `fchmod` 并确认路径/目录权限。
3. **`tmpfile()` 在 `disk full` 时可能返回 NULL**；它底层用 `O_TMPFILE` 或 `mkstemp+unlink`，不是「一定成功」。
:::

### 2.2.9 小结

flags 这张表的正确用法是先分类、再查值。分类决定「能不能组合」：访问模式是三选一的位段，`O_RDONLY|O_WRONLY` 得到的是 `O_RDWR` 而不是报错；行为位可以累加，但 `O_ASYNC` 在 `open` 时基本无效，要靠 `F_SETFL` + `F_SETOWN` 才真生效；`O_EXCL` 单独给出会被内核忽略，必须和 `O_CREAT` 一起才有意义；`O_TRUNC` 对 FIFO 与终端是未定义行为。查值决定「这台机器上到底是多少」：本机是 aarch64，`O_DIRECT` 为 `0200000`、`O_DIRECTORY` 为 `040000`、`O_NOFOLLOW` 为 `0100000`，而 x86-64 那一列是文献值、本套件没有 x86 机器可测——三对值在两架构之间是**成对互换**的，不是「随便哪一位不同」。如果只记住一件事：**把八进制值当机器档案查，别当常识背；跨架构抄表前先 `grep` 一次本机头文件。**

## 2.2.10 `openat2` 与路径解析的安全边界 {#sec-2.2.10}

这一节回答：怎样保证「打开的文件一定在我指定的目录下」，即使路径里有 `..` 和符号链接？

::: preview 先抓住一件事
`openat2` 把「路径怎么解析」从隐式约定变成**显式参数**：`dfd` 决定从哪个目录起算，`resolve` 位决定能不能穿符号链接、能不能越出 `dfd` 所在的根。它解决的是 `open` 那一套里最阴的一类竞态——你的路径字符串在内核逐步解析的过程中被别人改了目录或换成软链接。判据很硬：不支持这些位时它返回 `EOPNOTSUPP`，而不是静默降级，所以「用了就等于安全」不成立，得处理报错。
:::

`openat(dirfd, "../etc/passwd", ...)` 可以逃出 `dirfd` 指向的目录；`O_NOFOLLOW` 只挡最后一段。Linux 5.6 引入的 `openat2` 把「解析约束」变成一组显式 flag：

```c
#include <linux/openat2.h>
#include <sys/syscall.h>

struct open_how {
    __u64 flags;      /* 与 open 的 flags 相同 */
    __u64 mode;       /* 与 open 的 mode 相同 */
    __u64 resolve;    /* RESOLVE_* 约束 */
};

long openat2(int dirfd, const char *pathname,
             struct open_how *how, size_t size);
```

`size` 必须等于（或小于）当前内核认识的 `sizeof(struct open_how)`；传大了返回 `E2BIG`，传小了按旧版本解释。glibc 2.37 起提供包装，老 glibc 用 `syscall(SYS_openat2, ...)`。

| `resolve` 位 | 含义 | 违规时 `errno` |
|:--|:--|:--|
| `RESOLVE_BENEATH` | 不允许 `..` 或绝对路径逃出 `dirfd` | `EXDEV` |
| `RESOLVE_IN_ROOT` | 把 `dirfd` 当作 `/`，绝对路径和 `..` 都被限制在其中 | 不逃逸，直接解析 |
| `RESOLVE_NO_MAGICLINKS` | 禁止 `/proc/self/fd/N` 这类魔法链接 | `ELOOP` |
| `RESOLVE_NO_SYMLINKS` | 禁止路径中任何符号链接 | `ELOOP` |
| `RESOLVE_NO_XDEV` | 禁止跨越挂载点 | `EXDEV` |
| `RESOLVE_CACHED` | 只查缓存，不触发 I/O | `EAGAIN` |

`RESOLVE_BENEATH` 和 `RESOLVE_IN_ROOT` 的区别是「逃逸是错误还是被夹住」：前者返回 `EXDEV`，后者把 `..` 限制在根内，像 `chroot` 但不改进程状态。做沙箱/解压工具时，`IN_ROOT` 更宽容，`BENEATH` 更适合「必须留在这个目录」的断言。

```c
/* safeopen.c — 用 openat2(RESOLVE_BENEATH) 把路径限制在目录内 */
#include <errno.h>
#include <fcntl.h>
#include <linux/openat2.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/syscall.h>
#include <unistd.h>

static int open_beneath(int dirfd, const char *path)
{
    struct open_how how = {
        .flags = O_RDONLY | O_CLOEXEC,
        .resolve = RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS,
    };
    return (int)syscall(SYS_openat2, dirfd, path, &how, sizeof how);
}

int main(void)
{
    char dir[] = "/tmp/safeopen.XXXXXX";
    if (!mkdtemp(dir)) { perror("mkdtemp"); return 1; }

    char inside[256];
    snprintf(inside, sizeof inside, "%s/ok.txt", dir);
    int fd = open(inside, O_WRONLY | O_CREAT | O_TRUNC, 0600);
    if (fd == -1) { perror("create"); return 1; }
    if (write(fd, "ok", 2) != 2) { perror("write"); return 1; }
    close(fd);

    int dfd = open(dir, O_RDONLY | O_DIRECTORY | O_CLOEXEC);
    if (dfd == -1) { perror("open dir"); return 1; }

    int ok = open_beneath(dfd, "ok.txt");
    printf("inside:  fd=%d %s\n", ok, ok == -1 ? strerror(errno) : "ok");
    if (ok != -1) close(ok);

    errno = 0;
    int bad = open_beneath(dfd, "../etc/passwd");
    printf("escape:  fd=%d errno=%d (%s)\n", bad, errno, strerror(errno));
    if (bad != -1) close(bad);

    errno = 0;
    int abs = open_beneath(dfd, "/etc/passwd");
    printf("absolute:fd=%d errno=%d (%s)\n", abs, errno, strerror(errno));
    if (abs != -1) close(abs);

    close(dfd);
    unlink(inside);
    rmdir(dir);
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 safeopen.c -o safeopen
./safeopen
# inside:  fd=4 ok
# escape:  fd=-1 errno=18 (Invalid cross-device link)
# absolute:fd=-1 errno=18 (Invalid cross-device link)
```

三行是 ubuntu 24.04.5 / aarch64（内核 7.0.0-38）本机实测，连跑两次同值。**`inside` 报的是 fd=4 而不是 3**：程序在调用 `open_beneath` 之前，已经先 `open(inside)`（拿 3）、`close` 掉，再 `open(dir, O_RDONLY|O_DIRECTORY)` 把 **3 重新占住**当 `dirfd`，所以这次新开的 fd 只能落到 4。fd 号取决于「此前谁被打开、谁被关掉」，**不能当可复现常数**引用——判读只看它是不是 `-1` 和 `errno` 是什么，别看具体号；想在别人的输出里对上号，得先对齐前面的调用序列。

`EXDEV` 看起来像「跨设备」，实际是 `RESOLVE_BENEATH` 对逃逸的统一错误码。这是 `openat2` 最反直觉的一点：**错误码不描述原因，只描述类别**。排障时先看 `resolve` 位，再看路径。

旧内核没有 `openat2`，`syscall` 返回 `ENOSYS`。回退方案是「逐段 `openat` + `O_NOFOLLOW`」：自己把路径按 `/` 拆开，拒绝 `..`，每一段都用 `O_NOFOLLOW|O_DIRECTORY` 打开，最后一段再按需要打开。这比直接 `open` 安全，但仍要处理符号链接竞态。

::: think `openat2` 能不能替代 `chroot`
不能。`chroot` 改的是进程的根目录，影响之后所有路径解析；`openat2` 只约束**这一次**解析。真正的沙箱还需要 mount namespace（挂载命名空间：内核把挂载点集合隔成互相看不见的几套，容器各自持有自己的那一套）、`pivot_root`、seccomp 和 capability 收缩。`openat2` 是「单次路径解析的护栏」，不是「进程隔离」。
:::

### 2.2.10 小结

`openat2` 的价值不在「多一个带旗标的 open」，而在把两件事同时说清楚：起点是谁、允许怎么走。`dfd` + 绝对路径仍是既有语义；`RESOLVE_BENEATH` 让解析过程不许越过 `dfd` 这一层，`RESOLVE_NO_SYMLINKS` 干脆禁止穿越软链接，`RESOLVE_CACHED` 只是「不许阻塞」的性能提示，命中不了就返回 `EAGAIN`。这组合起来挡住的正是「按名字打开」的 TOCTOU 窗口：路径解析的每一级都是一次查表，任何一级在查之前被换掉，你打开的就不是你以为的那个文件。如果只记住一件事：**权限与隔离要落在「怎么解析路径」这一层，而不是落在「先 stat 再 open」这种能被插队的两步之间。**

::: method 即时自测 · 2.2.10
**Q1（记忆）** 说出 `resolve` 三个位的名字，各自挡的是哪种情况；哪一个不改变安全性、只改变阻塞行为？

**Q2（辨析）** 为什么「先 `realpath` 解析软链接、再 `open`」不能替代 `RESOLVE_NO_SYMLINKS`？

**Q3（应用）** 你的容器内工具要在宿主给定的目录里打开文件，`openat2` 返回 `EOPNOTSUPP`。给出两条应对方案并说明各自把风险留在了哪里。

::: sol 答案
**A1** `RESOLVE_BENEATH`：解析结果不许越出 `dfd` 指向的目录（挡 `../` 与绝对路径逃逸）；`RESOLVE_NO_SYMLINKS`：路径任一段是软链接即失败（挡「名字没变、目标变了」）；`RESOLVE_CACHED`：只走快路径，需要阻塞取锁或回源就返回 `EAGAIN`（纯性能语义）。改变阻塞行为的是 `RESOLVE_CACHED`。

**A3** 其一：退回 `openat(dfd, rel, O_NOFOLLOW|O_DIRECTORY|O_CLOEXEC)` 逐级手工解析，自己保证每一级都不用软链接——风险留在自己写的循环里，路径每一级都要防，且不同内核版本对 `O_NOFOLLOW` 的作用范围细节不完全一致。其二：把「不许越界」交给外部边界（用只读 bind mount 或独立 mount namespace 把目录圈起来）——风险从代码转移到部署：一旦有人改启动参数、忘了挂这一层，程序内部毫无察觉。两种都比「直接 `open` 绝对路径」好，也都要在文档里写明前提。

## 2.2.11 `mode`、`umask` 与创建权限 {#sec-2.2.11}

这一节回答：`open(..., 0666)` 创建出来的文件为什么常常是 0644？谁改了权限？

::: preview 先抓住一件事
新建文件的权限是 `mode & ~umask`，两件事各由不同主体决定：`mode` 是程序写死的，`umask` 是**调用进程**的会话设置。所以「我明明传了 0644，为什么建出来是 0600」通常不是 bug，而是环境；反过来「程序传 0666、umask 是 022」就会得到 0644。要精确控制权限，就别依赖 umask：创建时给 mode，再 `fchmod` 修正——顺序与竞态见本节小结。
:::

`open` 的 `mode` 只在 `O_CREAT`/`O_TMPFILE` 时参与，内核计算最终权限的公式是：

```text
最终权限 = mode & 07777 & ~umask
```

`umask` 是进程级状态，默认通常是 `022`，所以 `0666 & ~022 = 0644`。`umask` 不是「减去权限」，而是「屏蔽位」：它只清位，不加位。

```bash
umask 077
touch secret.txt
stat -c '%a %n' secret.txt     # 600 secret.txt
umask 022
```

`umask` 影响所有创建接口：`open`、`mkdir`、`mkfifo`、`mknod`、`socket` 绑定的文件、`sem_open` 创建的 POSIX 信号量文件。它在 `fork` 后继承，在 `exec` 后保留；多线程共享同一个值，工作线程里改它会影响其他线程。

### 特殊位与目录继承

`mode` 的低 12 位包含 setuid(04000)、setgid(02000)、sticky(01000)。创建时可以直接带上，但：

- `open` 创建的文件带 setuid/setgid，后续 `chown` 会清掉；
- 目录的 setgid 位有特殊含义：在该目录下新建的文件继承目录的**属组**，新建的子目录继续带 setgid；
- sticky 位只对目录有意义：只有文件属主、目录属主或 root 能删除目录里的项（`/tmp` 的 `1777`）。

```bash
mkdir /srv/shared && chgrp dev /srv/shared && chmod 2775 /srv/shared
touch /srv/shared/a          # a 的组是 dev，不是创建者的主组
```

### 默认 ACL 会插一脚

如果父目录设置了默认 ACL（`setfacl -d`），新建文件的权限不再只由 `mode & ~umask` 决定：内核以默认 ACL 为模板，把 `mode` 中**没有请求的权限位**从 ACL 的 mask 里清掉。`umask` 仍生效，但作用在 mask 上；命名用户的条目可能保留，有效权限受 mask 限制；文件不会因 ACL 获得执行位，除非创建时请求了 `x`。同一个 `open(..., 0666)` 在不同目录里创建出不同 ACL，原因就在这里。

### `mode=0` 与 `O_CREAT`

`open(path, O_CREAT|O_WRONLY, 0)` 会创建一个**所有权限位为 0** 的文件。普通用户之后连自己都打不开（root 可以），只能 `chmod` 补救。这不是「用默认权限」，而是「显式请求 0000」。`creat(path, mode)` 是 `open(path, O_WRONLY|O_CREAT|O_TRUNC, mode)` 的别名，同样受 `umask` 影响。

::: errata 创建权限的五个坑
1. **「`umask` 是减法」**——是位屏蔽，`mode & ~umask`；`umask 022` 对 `0600` 没有影响。
2. **「`open` 的 `mode` 可以省略」**——带 `O_CREAT`/`O_TMPFILE` 时是可变参数，省略是未定义行为，通常拿到栈上的垃圾值，创建出权限诡异的文件。
3. **「`chmod` 不受 `umask` 影响」**——正确；`chmod` 设置的是精确权限，只有创建时受 `umask` 约束。
4. **「目录的 setgid 只影响目录自身」**——它还决定新建文件的属组与子目录的继承。
5. **「默认 ACL 会覆盖 `umask`」**——两者共同作用：`umask` 清 mode 位，默认 ACL 提供模板，最后 mask 再限制命名条目。
:::

### 2.2.11 小结

这一节把「权限从哪来」拆成三个时刻。创建时刻：`open(..., O_CREAT, mode)` 的 mode 会立刻被 umask 削一位，`chmod` 之后到文件被命名之前不存在中间状态，所以想避开竞态就一次给对 mode（例如 `0600`）再按需 `fchmod`。修改时刻：`chmod`/`fchmod` 改的是 inode 上的权限位，只有属主或特权能做；`fchmod` 用 fd 而不是路径，免受「路径被换」的困扰。命名时刻：目录的 setgid 位会让新建文件继承父目录的组、粘滞位（`S_ISVTX`）让目录里的文件只有属主能删——这两条是共享目录能安全工作的前提。如果只记住一件事：**程序要声明的是「我要的权限」，不是「我期望环境配合」；凡是依赖 umask 的默认值，换一台机器就会变。**

::: method 即时自测 · 2.2.11
**Q1（记忆）** 写出 `mode=0666`、`umask=022` 与 `umask=077` 两种情况下新建文件的权限，并说明谁在什么时候削的位。

**Q2（辨析）** 为什么「先 `open(..., O_CREAT, 0600)` 再 `fchmod(fd, 0644)`」比「直接 `open(..., O_CREAT, 0644)`」更安全？两者在什么场景下结果不同？

**Q3（应用）** 你的服务在容器里跑，同一段代码开发机建出 `-rw-r--r--`、生产机建出 `-rw-------`。给出两条排查命令和一个不依赖环境的修法。

::: sol 答案
**A1** 前者得 `0644`（`0666 & ~0022`），后者得 `0600`（`0666 & ~0077`）。削位发生在内核创建 inode 的那一刻，用的就是发起 `open` 的那个进程的 umask——它是进程属性而非文件属性，所以同一目录里两个不同 umask 的进程会建出不同权限的文件。

## 2.2.12 `read`/`write` 的完整返回矩阵 {#sec-2.2.12}

这一节回答：`read`/`write` 除了 `-1` 和「请求的字节数」，还可能返回什么？每个 `errno` 该重试还是该放弃？

::: preview 先抓住一件事
`read`/`write` 的返回值不是「成功 / 失败」两态，而是**五种形态**：写满、短、零、`-1`+`EINTR`、`-1`+其他。真正让人丢数据的是第二种——`write` 返回一个正数但小于请求长度，它**不是错误**，`errno` 还是 0；把它当成功继续往下走，数据就永久少了一截。所以这一节的用法是两步：先看返回值落在哪一格，再按错误码决定「原地重试」「等就绪事件」还是「放弃并告警」。判据记住一句：只有 `-1` 才配查 `errno`，非负返回值都要拿它和请求长度比。
:::

2.2.3 给了三条返回值规则。这里把「什么情况下返回多少」和「每个错误码怎么办」补全。

### 返回值的五种形态

| 返回值 | `read` 含义 | `write` 含义 | 处理 |
|:--|:--|:--|:--|
| `== count` | 读满 | 写完 | 继续下一块 |
| `0 < n < count` | 短读：EOF、缓冲不足、信号 | 短写：缓冲满、配额、信号 | 推进偏移，继续 |
| `0` | EOF（普通文件/管道写端关闭） | `count==0` 或设备特殊语义 | `read` 结束循环；`write` 视为完成 |
| `-1` + `EINTR` | 被信号打断，可能已传部分 | 同左 | 重试剩余部分 |
| `-1` + 其他 | 真错误 | 真错误 | 按错误码处理 |

`count == 0` 时，Linux 的 `read`/`write` 返回 0，且**可能不检查 fd 是否有效**（POSIX 允许实现选择）。不要用 `read(fd, buf, 0)` 探测 fd 是否可读。

### `read` 的错误码

| `errno` | 触发条件 | 是否重试 |
|:--|:--|:--|
| `EBADF` | fd 未打开、或不是读模式（含 `O_PATH`） | 否 |
| `EFAULT` | 缓冲区不可访问 | 否（调用方 bug） |
| `EINVAL` | fd 不适合读（如目录）、`O_DIRECT` 未对齐、偏移非法 | 否 |
| `EISDIR` | Linux 上对目录 `read` | 否，改用 `getdents` |
| `EAGAIN`/`EWOULDBLOCK` | `O_NONBLOCK` 且暂无数据 | 是，等可读事件 |
| `EINTR` | 阻塞中被信号打断 | 是 |
| `EIO` | 设备/文件系统错误 | 否，告警 |
| `ENOMEM` | 内核缓冲区不足 | 可退避重试 |
| `ETIMEDOUT` | 网络文件系统/设备超时 | 视语义 |

### `write` 的错误码

| `errno` | 触发条件 | 是否重试 |
|:--|:--|:--|
| `EBADF` | fd 未打开、或不是写模式 | 否 |
| `EFAULT` | 缓冲区不可访问 | 否 |
| `EINVAL` | `O_DIRECT` 未对齐、fd 不支持写 | 否 |
| `EFBIG` | 超过 `RLIMIT_FSIZE` 或文件系统最大文件 | 否 |
| `ENOSPC` | 设备/文件系统满 | 否，先清理 |
| `EDQUOT` | 用户/组配额超限 | 否，先清理 |
| `EPIPE` | 管道/socket 读端已关闭 | 否；默认还会收到 `SIGPIPE` |
| `EAGAIN` | `O_NONBLOCK` 且缓冲满 | 是，等可写事件 |
| `EINTR` | 阻塞中被信号打断 | 是 |
| `EIO` | 设备错误 | 否 |
| `EPERM` | 追加-only/immutable 文件，或 `O_APPEND` 受限 | 否 |
| `EROFS` | 只读文件系统 | 否 |

`EPIPE` 默认会先触发 `SIGPIPE`，进程直接终止；服务端通常 `signal(SIGPIPE, SIG_IGN)` 或对 socket 用 `MSG_NOSIGNAL`，让 `write` 返回 `EPIPE` 而不是被杀。

### 短读/短写的真实来源

短读不是「异常」，而是以下情况的正常表现：

1. 读到文件末尾，剩余不足 `count`；
2. 管道缓冲区里只有这么多；
3. 终端处于行模式，一次只给一行；
4. 信号在传输部分数据后到达（Linux 返回已读字节数，而不是 `EINTR`）；
5. `O_DIRECT` 的尾块不足一个对齐单位；
6. `/proc`、`/sys` 的许多文件一次只产生一页左右的数据，`st_size` 还是 0；
7. 设备驱动按自己的块大小返回。

短写同理：管道容量（默认 64 KiB）、socket 发送缓冲、`RLIMIT_FSIZE`、磁盘配额、非阻塞设备。**唯一正确的处理是循环**，但循环要区分「这次写了 0」：`write` 返回 0 且 `count > 0` 时，继续循环会死锁，应该报 `EIO`。

```c
/* shortio.c — 制造短读、短写、EAGAIN、ENOSPC、EPIPE、EISDIR */
#include <errno.h>
#include <fcntl.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static volatile sig_atomic_t got_pipe;

static void on_pipe(int sig) { (void)sig; got_pipe = 1; }

int main(void)
{
    int p[2];
    if (pipe2(p, O_CLOEXEC | O_NONBLOCK) == -1) { perror("pipe2"); return 1; }

    size_t big = 1u << 20;
    char *buf = malloc(big);
    if (!buf) { perror("malloc"); return 1; }
    memset(buf, 'A', big);

    /* 1. 非阻塞管道：第一次短写，第二次 EAGAIN */
    errno = 0;
    ssize_t n = write(p[1], buf, big);
    printf("write 1MiB to pipe: n=%zd errno=%d (%s)\n", n, errno, strerror(errno));
    errno = 0;
    n = write(p[1], buf, big);
    printf("write again:        n=%zd errno=%d (%s)\n", n, errno, strerror(errno));

    /* 2. 读端只取一部分：短读 */
    char tmp[65536];
    errno = 0;
    n = read(p[0], tmp, sizeof tmp);
    printf("read 64KiB:         n=%zd errno=%d\n", n, errno);

    /* 3. 空管道再读：EAGAIN */
    errno = 0;
    n = read(p[0], tmp, sizeof tmp);
    printf("read empty:         n=%zd errno=%d (%s)\n", n, errno, strerror(errno));

    /* 4. /dev/full：ENOSPC */
    int full = open("/dev/full", O_WRONLY | O_CLOEXEC);
    if (full != -1) {
        errno = 0;
        n = write(full, "x", 1);
        printf("write /dev/full:    n=%zd errno=%d (%s)\n", n, errno, strerror(errno));
        close(full);
    }

    /* 5. 读目录：EISDIR */
    int dir = open("/tmp", O_RDONLY | O_DIRECTORY | O_CLOEXEC);
    if (dir != -1) {
        errno = 0;
        n = read(dir, tmp, 16);
        printf("read directory:     n=%zd errno=%d (%s)\n", n, errno, strerror(errno));
        close(dir);
    }

    /* 6. 读端关闭后写：EPIPE（默认还会 SIGPIPE，这里先接管） */
    struct sigaction sa = {0};
    sa.sa_handler = on_pipe;
    sigemptyset(&sa.sa_mask);
    if (sigaction(SIGPIPE, &sa, NULL) == -1) { perror("sigaction"); return 1; }
    close(p[0]);
    errno = 0;
    n = write(p[1], "x", 1);
    printf("write broken pipe:  n=%zd errno=%d (%s) sigpipe=%d\n",
           n, errno, strerror(errno), (int)got_pipe);

    close(p[1]);
    free(buf);
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 shortio.c -o shortio
./shortio
# write 1MiB to pipe: n=65536 errno=0 (Success)
# write again:        n=-1 errno=11 (Resource temporarily unavailable)
# read 64KiB:         n=65536 errno=0
# read empty:         n=-1 errno=11 (Resource temporarily unavailable)
# write /dev/full:    n=-1 errno=28 (No space left on device)
# read directory:     n=-1 errno=21 (Is a directory)
# write broken pipe:  n=-1 errno=32 (Broken pipe) sigpipe=1
```

注意第一条 `write` 的返回值：管道容量是 64 KiB，所以 1 MiB 只写进去 65536 字节，**没有报错**。任何「`write` 返回非负就认为写完了」的代码都会丢数据。

::: method 处理短读/短写的决策顺序
1. `n == -1` 且 `errno == EINTR`：重试，不推进偏移。
2. `n == -1` 且 `errno == EAGAIN`：等 fd 就绪（`epoll`/`poll`），不要忙等。
3. `n == 0`（读）：EOF；`write` 返回 0 且 `count > 0`：报 `EIO`，不要死循环。
4. `0 < n < count`：推进 `buf` 与剩余长度，继续。
5. 其他 `errno`：按 2.2.12 的表决定重试、退避或失败。
:::

### 2.2.12 小结

把返回值矩阵和错误码矩阵合起来读，会得到一个和直觉相反的结论：**`read`/`write` 的「正常」区间很宽**。上面 `shortio.c` 在本机（aarch64 Ubuntu 24.04.5）复跑，向管道一次 `write` 1 MiB 只落进 65536 字节，返回正值、`errno` 为 0；紧接着再写才拿到 `EAGAIN`(11)。也就是说「短写」在管道、socket、终端、`/proc` 这些对象上是默认行为，不是异常事件，而 `count==0` 时 Linux 直接返回 0、甚至可能不校验 fd 是否有效，拿它探测「有没有数据可读」也不成立。

错误码这一侧要分成三堆：`EINTR`、`EAGAIN` 属于「你没做错，换个时间再来」，前者原地重试同一批字节，后者必须挂到 `epoll`/`poll` 上等就绪事件、不能忙等；`EINVAL`、`EFAULT`、`EBADF`、`EISDIR` 属于「调用方 bug」，重试一百次也是同样的错，改代码不改时序；`ENOSPC`、`EDQUOT`、`EIO`、`EROFS`、`EPERM` 属于「环境不允许」，程序能做的是清理、退避或把错误原样报给用户。

最后一条边界是 `EPIPE`：默认行为是先投递 `SIGPIPE` 杀掉自己，`errno` 都来不及看，所以服务端要么 `SIG_IGN` 要么给 socket 加 `MSG_NOSIGNAL`，把「对端跑了」从进程死亡降级成一个可处理的返回值。**如果只记住一件事：非负返回值一律和请求长度比一次，`errno` 只在 `-1` 时读——短写不是错误，是必须循环的信号。**

::: method 即时自测 · 2.2.12
**Q1（记忆）** `read`/`write` 的返回值有哪五种形态？哪两种情况下 `errno` 根本不该被读取？

**Q2（辨析）** 本机向管道 `write(1MiB)` 返回 65536 且 `errno=0`，为什么这不是错误？`EAGAIN` 与 `EINTR` 都要求「再来一次」，两者重试的方式有什么本质区别？

**Q3（应用）** 一段代码写成 `if (write(fd, buf, n) < 0) perror("write");` 就把数据当已落盘，请指出它会在哪三种真实场景丢数据，并说出改法；如果它写的是 socket，还要额外处理什么？

::: sol 答案
**A1** 等于请求长度、大于 0 且小于请求长度、等于 0、`-1`+`EINTR`、`-1`+其他错误码。`errno` 只在前两种非负形态之后不该读——它未被系统调用改动，读了也没有意义；正确动作是拿返回值与 `count` 比。返回 0（`count==0` 时）也属于「不保证设置 `errno`」的一格。
**A2** 因为管道的容量就是 64 KiB，内核把能装下的部分装进去了，这次调用没有失败，短写只是「缓冲区装不下」的正常结果；把它当错误去查 `errno` 查不到，当成功继续则会丢掉剩下的 960 KiB。`EINTR` 是阻塞期间来了信号，重试还是同一批字节、原地再来即可；`EAGAIN` 是非阻塞对象上「现在没数据/没空间」，原地重试会变成忙等、把 CPU 打满，必须回到 `epoll`/`poll` 等该 fd 变为可读或可写再调用。
**A3** 三种场景：① 管道/socket 缓冲装不下（本机实测 65536）；② 磁盘配额或空间将满时先短写再 `EDQUOT`/`ENOSPC`；③ 传输部分字节后被信号打断，返回值是已写字节数而非 `-1`。改法是循环：每次按返回的 `n` 前移 `buf`、把剩余长度减去 `n`，`n==0` 且仍有剩余则报 `EIO` 退出，`-1`+`EINTR` 原地重试。写 socket 还要额外处理 `SIGPIPE`——默认直接杀进程，要么 `signal(SIGPIPE, SIG_IGN)`，要么发送时带 `MSG_NOSIGNAL`，让对端关闭变成可检查的 `EPIPE`。

## 2.2.13 `lseek`：偏移、`SEEK_DATA`/`SEEK_HOLE` 与稀疏文件 {#sec-2.2.13}

这一节回答：`lseek` 除了「移动文件指针」还能做什么？为什么 `lseek` 到文件末尾之外不会立刻占磁盘？

::: preview 先抓住一件事
`lseek` 是一次**纯内存操作**：它只改 open file description 里的偏移 `f_pos`，不碰页缓存、不碰磁盘，所以「`lseek` 到 1 GiB」既不会慢、也不会让文件真的变成 1 GiB。由此产生两个可以分开理解的量：`st_size` 是逻辑大小（偏移能写到的最远处），`st_blocks * 512` 是实际占用的数据块。中间没写过的部分叫**空洞**，读它返回 0、不占磁盘。`SEEK_DATA`/`SEEK_HOLE` 这两个特殊 `whence` 就是让程序能问出「数据到底在哪几段」，从而跳过空洞——备份、复制、`cp --reflink` 一类工具靠它保住稀疏结构。
:::

```c
off_t lseek(int fd, off_t offset, int whence);
```

`whence` 取 `SEEK_SET`（绝对）、`SEEK_CUR`（相对当前）、`SEEK_END`（相对末尾）。成功返回**新偏移**，失败返回 `-1`。`lseek` 只改 `struct file` 里的 `f_pos`，不触发任何 I/O。

| `errno` | 触发条件 |
|:--|:--|
| `EBADF` | fd 未打开或不可寻址 |
| `ESPIPE` | 管道、FIFO、socket、终端（不可随机访问） |
| `EINVAL` | `whence` 非法，或结果偏移为负 |
| `EOVERFLOW` | 结果超出 `off_t` 能表示的范围 |
| `ENXIO` | `SEEK_DATA`/`SEEK_HOLE` 的起点超出文件末尾 |

### 超出末尾的 `lseek` 不分配空间

```c
int fd = open("hole.bin", O_RDWR | O_CREAT | O_TRUNC, 0644);
lseek(fd, 1024 * 1024, SEEK_SET);   /* 偏移 1 MiB，但文件大小仍是 0 */
write(fd, "x", 1);                  /* 现在大小是 1 MiB + 1，中间是空洞 */
```

`lseek` 到 1 MiB 只改偏移；`write` 之后文件逻辑大小变成 1 MiB+1，但中间 1 MiB 是**空洞**，不占数据块。读这些位置返回 0。`st_size` 是逻辑大小，`st_blocks * 512` 是实际占用（见 [2.5](ch05.md)）。

::: ex 例 2.2.2 · 先猜这个稀疏文件的两个大小读数 {#ex-2.2.2}
把上面三行跑完再 `close`，然后 `stat -c '%s %b' hole.bin`。先猜 `%s` 与 `%b` 各打出什么量级的数，以及 `du hole.bin` 和 `du --apparent-size hole.bin` 哪个更接近 `%s`。

::: sol 解答
`%s`（`st_size`）是 **1048577**——逻辑大小，由最远写到过的偏移决定，`lseek` 本身不改它，`write` 那 1 字节把它顶到 1 MiB+1。`%b`（`st_blocks`）是个位数（本机 8 块上下，每块 512 字节）——只有最后一字节所在的块被分配，中间 1 MiB 是空洞。`du --apparent-size` 按 `st_size` 报，接近 1 MiB；`du` 按块占用报，只有几 KB。两个大小读数不一致正是稀疏文件的指纹：备份工具若只看 `st_size` 会把空洞也当数据抄满。
:::
:::

### `SEEK_DATA` 与 `SEEK_HOLE`

Linux 3.1 起支持两个特殊的 `whence`，用来在稀疏文件中跳读：

- `lseek(fd, off, SEEK_DATA)`：返回 `off` 之后**第一个包含数据**的偏移；`off` 本身在数据区则返回 `off`。
- `lseek(fd, off, SEEK_HOLE)`：返回 `off` 之后**第一个空洞**的偏移；如果后面全是数据，返回文件末尾。

两者都可能返回 `ENXIO`（`SEEK_DATA` 时 `off >= 文件大小`）。文件系统可以保守地「把所有区域都报告为数据」（例如某些不支持 hole 的文件系统），这时 `SEEK_HOLE` 只返回 EOF，程序仍然正确，只是没省 I/O。

```c
/* sparse_scan.c — 用 SEEK_DATA/SEEK_HOLE 列出文件的逻辑区段 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

int main(void)
{
    const char *path = "sparse_scan.bin";
    int fd = open(path, O_RDWR | O_CREAT | O_TRUNC | O_CLOEXEC, 0600);
    if (fd == -1) { perror("open"); return 1; }

    const off_t size = 4 * 1024 * 1024;
    if (ftruncate(fd, size) == -1) { perror("ftruncate"); return 1; }

    /* 在 0 和 2 MiB 处各写 4 KiB 数据，其余是空洞 */
    char page[4096];
    memset(page, 'D', sizeof page);
    if (pwrite(fd, page, sizeof page, 0) != (ssize_t)sizeof page) {
        perror("pwrite 0"); return 1;
    }
    if (pwrite(fd, page, sizeof page, 2 * 1024 * 1024) != (ssize_t)sizeof page) {
        perror("pwrite 2M"); return 1;
    }
    if (fsync(fd) == -1) { perror("fsync"); return 1; }

    struct stat st;
    if (fstat(fd, &st) == -1) { perror("fstat"); return 1; }
    printf("logical=%lld bytes, allocated=%lld bytes\n",
           (long long)st.st_size, (long long)st.st_blocks * 512);

    off_t off = 0;
    while (off < st.st_size) {
        errno = 0;
        off_t data = lseek(fd, off, SEEK_DATA);
        if (data == -1) {
            if (errno == ENXIO) break;          /* 后面全是空洞 */
            perror("SEEK_DATA"); break;
        }
        off_t hole = lseek(fd, data, SEEK_HOLE);
        if (hole == -1) { perror("SEEK_HOLE"); break; }

        printf("data [%lld, %lld)  %lld bytes\n",
               (long long)data, (long long)hole, (long long)(hole - data));
        if (hole <= off) {                       /* 防御：避免死循环 */
            fprintf(stderr, "no progress at %lld\n", (long long)off);
            break;
        }
        off = hole;
    }

    close(fd);
    unlink(path);
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 sparse_scan.c -o sparse_scan
./sparse_scan
# logical=4194304 bytes, allocated=8192 bytes
# data [0, 4096)  4096 bytes
# data [2097152, 2101248)  4096 bytes
```

`allocated=8192` 说明只有两个 4 KiB 数据块真正占了磁盘；中间 2 MiB 的空洞不占空间。`SEEK_DATA`/`SEEK_HOLE` 是 `cp --sparse=always`、`tar -S`、备份工具保留稀疏结构的底层依据。

::: errata `lseek` 的五个坑
1. **「`lseek` 会触发磁盘 I/O」**——不会，它只改内存里的偏移；真正读写在后续 `read`/`write`。
2. **「`lseek(fd, 0, SEEK_END)` 返回文件大小就一定是大小」**——对普通文件通常是，但对某些设备/`/proc` 文件返回 0；用 `fstat` 的 `st_size`。
3. **「`SEEK_DATA` 在所有文件系统上都精确」**——文件系统可以保守报告；只把它当优化，不当正确性依赖。
4. **「`lseek` 的偏移可以随便设负数」**——结果偏移为负返回 `EINVAL`；`SEEK_CUR` 向前越过 0 也失败。
5. **「`O_APPEND` 下 `lseek` 能改变写位置」**——不能；本地文件系统上带 `O_APPEND` 的 `write` 总是原子地定位到末尾（NFS 的边界见 2.2.16），`lseek` 的设置被忽略。
:::

### 2.2.13 小结

这一节把「偏移」和「磁盘占用」这两件被常常混为一谈的事拆开了。`lseek` 的成功返回是新偏移、失败才看 `errno`，`ESPIPE` 是最高频的一个：管道、FIFO、socket、终端都不可随机访问，这正好和 2.2.12 的短读语义对上——它们按字节流交付，没有「位置」这个概念。真正需要记住的是稀疏文件的三行实测：`sparse_scan.c` 在本机 ext4（`/dev/sda2`）上跑出 `logical=4194304 bytes, allocated=8192 bytes`，逻辑 4 MiB 只占 8 KiB 磁盘，`SEEK_DATA` 精确报出 `[0, 4096)` 和 `[2097152, 2101248)` 两段。这条能力有明确的下限：Linux 3.1 起才支持这两个 `whence`，且文件系统可以保守地把所有区域都报告成数据——这时 `SEEK_HOLE` 直接返回文件末尾，程序逻辑仍然正确，只是省不下 I/O。所以它的定位是**优化**而不是**正确性**：跳过空洞去读可以，把「`SEEK_HOLE` 说这里是洞」当成「这里一定是 0」来判断则不行。加上 errata 里那条最容易踩的组合：`O_APPEND` 下 `lseek` 的设置会被后续 `write` 忽略，试图靠它改变写位置是无效的。**如果只记住一件事：`st_size` 是逻辑大小、`st_blocks*512` 才是磁盘占用，两者不等就说明文件是稀疏的，而 `lseek` 本身永远不做 I/O。**

## 2.2.14 `pread`/`pwrite` 与分散聚集 I/O {#sec-2.2.14}

这一节回答：多线程读同一个 fd，为什么 `lseek` + `read` 会串数据？怎样一次系统调用读写多段缓冲区？

::: preview 先抓住一件事
这一层的三个家族各自解决一件不同的事。`pread`/`pwrite` 把**偏移从「fd 里的状态」变成「调用时的参数」**，于是「先 `lseek` 再 `read`」这两步合并成一个原子动作，多线程共用一个 fd 时不再互相踩位置。`readv`/`writev` 解决的是**内存侧的碎片**：头和体分处两块内存，不必先 memcpy 拼成一个缓冲才能发出一次 I/O，代价是返回值变成「总字节数」，短写后要按段推进而不能整组重试。`preadv2`/`pwritev2` 再往前一步，把**同步语义也变成每次调用的参数**（`RWF_DSYNC`、`RWF_NOWAIT`），省掉为一次特殊写而改整个 fd 的标志。三件事的共同点是：把原来必须靠「共享状态 + 多次调用」完成的操作，压成「参数 + 单次调用」。
:::

### `pread`/`pwrite`：把偏移变成参数

```c
ssize_t pread(int fd, void *buf, size_t count, off_t offset);
ssize_t pwrite(int fd, const void *buf, size_t count, off_t offset);
```

它们从 `offset` 读写，**不改变 `f_pos`**，因此两个线程用同一个 fd 也不会互相踩偏移。返回值与 `read`/`write` 相同：可能短读/短写，`-1` 时看 `errno`。

| `errno` | 说明 |
|:--|:--|
| `ESPIPE` | 管道/FIFO/socket 不支持随机访问（Linux 上 `pread` 返回 `ESPIPE`） |
| `EINVAL` | `offset` 为负、`O_DIRECT` 未对齐 |
| `EBADF` | fd 模式不对 |
| `EINTR`/`EAGAIN` | 同 `read`/`write` |

::: errata Linux 的 `pwrite` + `O_APPEND`
POSIX 规定 `pwrite` 忽略 `O_APPEND`，在 `offset` 处写。Linux 的内核实现**不遵守**：如果 fd 带 `O_APPEND`，`pwrite` 仍然追加到末尾，`offset` 被忽略。可移植代码要么不要在同一 fd 上混用，要么先 `fcntl` 清掉 `O_APPEND`。这个问题在 man 2 pwrite 的 BUGS 里有记录，长期未修。
:::

### `readv`/`writev`：一次调用，多段缓冲

```c
struct iovec {
    void  *iov_base;   /* 缓冲区起始地址 */
    size_t iov_len;    /* 长度 */
};

ssize_t readv(int fd, const struct iovec *iov, int iovcnt);
ssize_t writev(int fd, const struct iovec *iov, int iovcnt);
```

它们把多段内存拼成一次 I/O，减少系统调用次数，也避免为「头 + 体」临时拼一块大缓冲。返回值是**总字节数**，可能小于所有 `iov_len` 之和。

| 约束 | 值/错误 |
|:--|:--|
| 最大段数 | `sysconf(_SC_IOV_MAX)`，Linux 通常 1024；glibc 只是系统调用的薄包装，不会替你拆分数组——超过 `IOV_MAX` 直接返回 `EINVAL`，要更多段就分批调用 |
| 总长度 | 不能超过 `SSIZE_MAX`；超过可能 `EINVAL` |
| 空 `iov` | `iovcnt==0` 时返回 0 |
| 错误 | `EFAULT`、`EBADF`、`EINVAL`、`EINTR`、`EAGAIN` |
| 原子性 | 整组不是原子的；管道上单次 `writev` ≤ `PIPE_BUF` 才保证不交错 |

短写后不能「重试整个数组」，否则会重复写已经写出的部分。正确做法是推进 `iovec`：跳过已写满的段，把当前段的首地址和长度按剩余量切短。2.3.3 的 `writev_full()` 给了完整实现，这里补一个使用 `preadv2`/`pwritev2` 的例子。

### `preadv2`/`pwritev2` 与 `RWF_*`

```c
ssize_t preadv2(int fd, const struct iovec *iov, int iovcnt,
                off_t offset, int flags);
ssize_t pwritev2(int fd, const struct iovec *iov, int iovcnt,
                 off_t offset, int flags);
```

`flags` 是每次 I/O 的行为提示：

| flag | 含义 | 典型错误 |
|:--|:--|:--|
| `RWF_HIPRI` | 高优先级 I/O（配合 `O_DIRECT`） | 不支持时忽略或 `EOPNOTSUPP` |
| `RWF_DSYNC` | 本次写等同 `O_DSYNC` | 设备不支持 `EINVAL` |
| `RWF_SYNC` | 本次写等同 `O_SYNC` | 同上 |
| `RWF_NOWAIT` | 不等待 I/O，缓存未命中直接返回 | `EAGAIN` |
| `RWF_APPEND` | 本次写追加到末尾（4.16+） | 与 `O_APPEND` 类似 |

`RWF_NOWAIT` 适合「有活就干，没活就切走」的线程池：它不会因为缺页（page fault：要访问的那一页还不在物理内存，内核得先把它装进来）或回写而阻塞，但会在数据不在 page cache 时返回 `EAGAIN`。这比 `O_NONBLOCK` 对普通文件更可控。

```c
/* rwv.c — pwritev2(RWF_DSYNC) 写头+体，preadv2(RWF_NOWAIT) 读回 */
#include <errno.h>
#include <fcntl.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>
#include <sys/uio.h>
#include <unistd.h>

struct hdr { uint32_t len; uint32_t crc; };

int main(void)
{
    const char *path = "rwv_demo.bin";
    int fd = open(path, O_RDWR | O_CREAT | O_TRUNC | O_CLOEXEC, 0600);
    if (fd == -1) { perror("open"); return 1; }

    const char *body = "scatter-gather";
    struct hdr h = { .len = (uint32_t)strlen(body), .crc = 0 };
    struct iovec out[2] = {
        { .iov_base = &h, .iov_len = sizeof h },
        { .iov_base = (void *)body, .iov_len = strlen(body) },
    };

    ssize_t n = pwritev2(fd, out, 2, 0, RWF_DSYNC);
    if (n == -1) { perror("pwritev2"); return 1; }
    printf("pwritev2 wrote %zd bytes\n", n);

    struct hdr back = {0};
    char buf[64] = {0};
    struct iovec in[2] = {
        { .iov_base = &back, .iov_len = sizeof back },
        { .iov_base = buf, .iov_len = sizeof buf - 1 },
    };

    errno = 0;
    n = preadv2(fd, in, 2, 0, RWF_NOWAIT);
    if (n == -1 && (errno == EAGAIN || errno == EOPNOTSUPP)) {
        printf("RWF_NOWAIT unsupported/unavailable (%s), fallback\n",
               strerror(errno));
        n = preadv(fd, in, 2, 0);
    }
    if (n == -1) { perror("preadv2"); return 1; }

    printf("read %zd bytes: len=%u body=%s\n", n, back.len, buf);
    close(fd);
    unlink(path);
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 rwv.c -o rwv
./rwv
# pwritev2 wrote 22 bytes
# read 22 bytes: len=14 body=scatter-gather
```

上面两行是 ubuntu 24.04.5 / aarch64（内核 7.0.0-38）本机实测，同一份源码连跑两次同值；`RWF_NOWAIT` 那行「unsupported，fallback」本机没有打印，说明这台机器上走的是成功路径。`pwritev2` 返回 **22 = 8 字节头 + 14 字节体**：`struct hdr` 是两个 `uint32_t`，本机 `printf("%zu\n", sizeof(struct hdr))` 打出的就是 **8**——把这段结构体改成只有一个 `uint32_t` 才会得到「4 字节头」那种算法。读回那行同样是 22：第二个 `iovec` 给的是 63 字节的缓冲，但文件只有 22 字节，所以 `preadv2` 在填满第一段（8 字节）后从第二段只取走剩下的 14 字节就返回，`len=14 body=scatter-gather` 与写进去的一致。如果 `RWF_DSYNC` 不被文件系统支持，`errno` 可能是 `EINVAL`；生产代码应降级到普通 `pwritev` + `fdatasync`，而不是直接失败。

::: method 选择 `read` 家族的顺序
1. 单段、顺序、单线程：`read`/`write`。
2. 多线程共享 fd、需要指定偏移：`pread`/`pwrite`。
3. 多段缓冲（头+体、多个字段）：`readv`/`writev`。
4. 需要每次 I/O 的同步/非阻塞语义：`preadv2`/`pwritev2` + `RWF_*`。
5. 超大文件、需要绕过缓存：`O_DIRECT` + 对齐缓冲（2.3.8）。
:::

### 2.2.14 小结

选家族的依据只有一个问题：**偏移和缓冲区，谁该由谁决定**。顺序单线程读一个文件时 `read`/`write` 就够，多出来的参数只会增加噪声；一旦多个线程共用同一个 fd，`lseek`+`read` 就是两个调度点，中间被别人改偏移，数据会从错误的位置读出来——`pread`/`pwrite` 把偏移做成参数之后，这个竞态从根上消失，因为它们不改 `f_pos`。

上表那一行 errata 是本节最容易中的一次坑：Linux 的 `pwrite` 在 fd 带 `O_APPEND` 时**不遵守 POSIX**，`offset` 被忽略、仍然写到末尾，所以「用了 `pwrite` 就一定写在我指定的位置」在这台机器上不成立，混用前要先 `fcntl` 清掉 `O_APPEND`。

向量侧的关键是返回值语义变了：`writev` 返回的是**整组的总字节数**，本机实测 `rwv.c` 里 `struct hdr` 为 8 字节、体 14 字节，`pwritev2` 返回 22；读回时第二段给了 63 字节的空间，文件却只有 22 字节，于是它填满第一段后从第二段只取 14 字节就返回——短写/短读在多段场景下是**跨段推进**的，重试整个数组等于把已写出的段再写一遍，正确做法是整段跳过、当前段把 `iov_base` 前移并砍短 `iov_len`（2.3.3 的 `writev_full()`）。段数上限本机 `sysconf(_SC_IOV_MAX)` 实测 1024，超过时 `writev` 直接 `EINVAL`，glibc 不会替你拆分数组。`RWF_*` 这一层则要按「不支持就报错」设计：`RWF_NOWAIT` 可能返回 `EAGAIN` 或 `EOPNOTSUPP`，`RWF_DSYNC` 在不支持的文件系统上可能是 `EINVAL`，生产代码要写降级路径，而不是让一次可选优化变成故障。**如果只记住一件事：共享 fd 就永远别把偏移留在 fd 里，多段就永远别整组重试。**

::: method 即时自测 · 2.2.14
**Q1（记忆）** `pread` 相对 `lseek`+`read` 多保证了什么？`readv` 的返回值和 `read` 有什么不同？`IOV_MAX` 本机是多少、超了会怎样？

**Q2（辨析）** 同一 fd 带 `O_APPEND` 时调用 `pwrite(fd, buf, n, 100)`，Linux 上实际写到哪？为什么说这是「内核与 POSIX 不一致」而不是「程序写错」？`RWF_NOWAIT` 与 `O_NONBLOCK` 都能避免阻塞，区别在哪？

**Q3（应用）** `pwritev2(fd, iov, 3, 0, RWF_DSYNC)` 返回 22，而三段 `iov_len` 之和是 40。请按本机实测的数字说明哪些段已完整写出，写出下一轮该提交哪几段、怎么改 `iov_base`/`iov_len`；并说明为什么直接 `pwritev2(fd, iov, 3, 0, ...)` 再来一次是错的。

::: sol 答案
**A1** 一次调用里完成「定位 + 传输」，且**不改动 `f_pos`**，因此共享同一 fd 的线程不会互相踩偏移；`lseek`+`read` 是两步、中间存在调度点。`readv` 返回的是整组缓冲实际搬运的**总字节数**，可能只覆盖前几段加中间某段的一部分；`read` 只关心一段。本机 `sysconf(_SC_IOV_MAX)` 实测 1024，`iovcnt` 超过它时 `writev` 直接返回 `EINVAL`(22)，glibc 只是薄包装、不会自动分批，要更多段必须自己拆成多次调用。
**A2** 实际写到文件末尾，`offset` 为 100 被忽略——Linux 内核实现不遵守 POSIX「`pwrite` 忽略 `O_APPEND`」的规定，man 2 pwrite 的 BUGS 里长期记录着这条。说它不是「程序写错」，是因为程序按规范写的、拿到的是未文档化的行为，只能靠经验规避；所以可移植做法是别在同一 fd 上混用，或先 `fcntl` 清掉 `O_APPEND`。`O_NONBLOCK` 是 fd 的**长期状态**，对该 fd 的每次读写都生效；`RWF_NOWAIT` 是**本次调用**的提示，只影响这一次，数据不在页缓存或需要等待时立刻返回 `EAGAIN`，很适合线程池里「有活就干、没活就切走」而不改变 fd 语义。
**A3** 本机这个例子的段划分是 8 字节头 + 14 字节体（合计 22）；换成 40 字节的三段来说，返回 22 意味着前面的段已被填满、恰好有一段只写了一部分。下一轮应当：整段写完的段直接跳过，从第一个未写完的段开始提交，即传 `&iov[i]` 和 `iovcnt - i`，并把该段的 `iov_base` 前移已写字节、`iov_len` 减去同一数值；其后各段原样保留。直接重试整个数组是错的，因为已写出的那 22 字节会再被写第二遍，文件内容里出现重复段——这类损坏不会报错，只会在读的时候发现记录对不上。
:::

## 2.2.15 fd 生命周期：`dup3`、`close_range` 与 `/proc/self/fd` {#sec-2.2.15}

这一节回答：`fork`/`exec` 前后怎样精确控制「哪些 fd 还在」？`dup2` 和 `dup3` 差在哪？

::: preview 先抓住一件事
fd 的生命周期只有三个值得单独管住的时刻：**创建**（`open`/`dup` 系列，决定这个号从哪来、带不带 `CLOEXEC`）、**继承**（`exec` 时带 `FD_CLOEXEC` 的自动关闭，不带的原样传给新程序）、**销毁**（`close`，且它失败时的处理方式和普通系统调用相反——不能重试）。`dup3` 和 `close_range` 存在的理由都是「把原本要两步、因此有竞态窗口的操作合成一次调用」：前者在复制的同时原子地设上 `CLOEXEC`，后者在内核里一次关掉一段 fd，不会被信号或并发 `open` 插进来。判据也很具体：`dup3(oldfd, oldfd, …)` 返回 `EINVAL` 而 `dup2` 返回 `newfd`；`close_range` 在 5.9 之前的内核上返回 `ENOSYS`。
:::

### `dup3`：带 `CLOEXEC` 的原子复制

```c
int dup3(int oldfd, int newfd, int flags);
```

`dup3` 与 `dup2` 的区别只有两点，但都很关键：

1. `flags` 只接受 `O_CLOEXEC`，在复制的同时原子设置 `FD_CLOEXEC`；
2. `oldfd == newfd` 时返回 `EINVAL`（`dup2` 直接返回 `newfd`）。

失败：`EBADF`（`oldfd` 无效）、`EINVAL`（`flags` 非法或两参数相等）、`EMFILE`（超过 `RLIMIT_NOFILE`）。`dup3` 在 Linux 2.6.27 引入，glibc 2.9 起有包装。

```c
int newfd = dup3(oldfd, 1, O_CLOEXEC);   /* 原子把 oldfd 复制到 stdout，并带 CLOEXEC */
```

### `close_range`：一次关闭一段 fd

```c
int close_range(unsigned int first, unsigned int last, unsigned int flags);
```

Linux 5.9 引入，glibc 2.34 起有包装。它关闭 `[first, last]` 区间内的所有 fd，等价于循环 `close`，但**在内核里一次完成**，不会因为信号或并发 `open` 而漏掉。常用 flag：

| flag | 含义 |
|:--|:--|
| `0` | 直接关闭 |
| `CLOSE_RANGE_UNSHARE` | 先 unshare fd 表，避免影响共享该表的线程/进程（等价于 `unshare(CLONE_FILES)` 后再关，但更省） |
| `CLOSE_RANGE_CLOEXEC` | 不关闭，只设置 `FD_CLOEXEC`（本机 `man 2 close_range` 标为 Linux 5.11 起） |

`first > last` 返回 `EINVAL`；内核不支持返回 `ENOSYS`，回退是 `for (fd = first; fd <= last; fd++) close(fd);`。`close_range(3, ~0U, 0)` 是「exec 前清空所有非标准 fd」的标准写法，比遍历 `/proc/self/fd` 可靠。

```c
/* fdlife.c — dup3、F_DUPFD_CLOEXEC、close_range 与 fd 计数 */
#include <dirent.h>
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/syscall.h>
#include <unistd.h>

static int count_fds(void)
{
    DIR *d = opendir("/proc/self/fd");
    if (!d) return -1;
    int n = 0;
    struct dirent *de;
    while ((de = readdir(d)) != NULL)
        if (de->d_name[0] != '.') n++;
    closedir(d);
    return n - 1;                    /* 减去 opendir 自己占的那个 */
}

int main(void)
{
    int a = open("/etc/hosts", O_RDONLY | O_CLOEXEC);
    int b = open("/etc/hosts", O_RDONLY | O_CLOEXEC);
    if (a == -1 || b == -1) { perror("open"); return 1; }

    int c = dup3(a, 100, O_CLOEXEC);
    printf("a=%d b=%d dup3(a,100,CLOEXEC)=%d a_cloexec=%d\n", a, b, c,
           !!(fcntl(a, F_GETFD) & FD_CLOEXEC));

    int d = fcntl(b, F_DUPFD_CLOEXEC, 3);
    printf("F_DUPFD_CLOEXEC(b,3)=%d\n", d);

    printf("fds before close_range: %d\n", count_fds());

    /* 只关我们自己造的 100 与 d，避免误关 stdout/stderr */
    if (c != -1) close(c);
    if (d != -1) close(d);
    errno = 0;
#ifdef SYS_close_range
    if (syscall(SYS_close_range, 100U, 200U, 0U) == -1)
        printf("close_range: %s（老内核？）\n", strerror(errno));
#else
    printf("SYS_close_range 不可用\n");
#endif

    printf("fds after close_range:  %d\n", count_fds());

    close(a);
    close(b);
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 fdlife.c -o fdlife
./fdlife
# a=3 b=4 dup3(a,100,CLOEXEC)=100 a_cloexec=1
# F_DUPFD_CLOEXEC(b,3)=5
# fds before close_range: 7
# fds after close_range:  5
```

::: ex 例 2.2.4 · 先猜 `F_DUPFD_CLOEXEC(b, 3)` 返回几 {#ex-2.2.4}
上面的代码已经跑出第一行 `a=3 b=4`，`dup3(a,100,CLOEXEC)` 又占走了 100。带着这个局面猜两个数：`F_DUPFD_CLOEXEC(b, 3)` 的返回值是几？`fds before close_range` 那一行又会打出几？

::: sol 解答
返回值是 **5**，不是参数里的 3。`F_DUPFD_CLOEXEC` 找的是「不小于第三个参数的最小未用 fd」，而此刻 0、1、2 是标准流，3 和 4 已被 `a`、`b` 拿走，3 被占用，内核只能往下给 5。`fds before close_range` 打出 **7**：三个标准流 + `a`(3) + `b`(4) + `dup3` 造的 100 + 这次复制出的 5，正好七个；数目录时 `opendir` 自己还会占一个 fd，所以代码里用 `n - 1` 把它扣掉。这一格报的是「此刻 fd 表的占用情况」，不是这个调用的常数。
:::
:::

四行都是 ubuntu 24.04.5 / aarch64（内核 7.0.0-38）本机实测，连跑两次同值；第一行现在直接把 `a=3 b=4` 打出来，就是为了给后面两行做对照。`F_DUPFD_CLOEXEC(b,3)` 为什么**不可能**是 3：`F_DUPFD`/`F_DUPFD_CLOEXEC` 的返回值是「不小于第三个参数的最小未用 fd」，而执行到这一行时 `a`、`b` 两次 `open("/etc/hosts")` 已经分别拿走 3 和 4，`dup3` 又占了 100——3 已被占用，内核只能给下一个空位，本机就是 **5**（`a_cloexec=1` 那一格检查的是 `a` 自身的 `FD_CLOEXEC`，来自 `open` 时给的 `O_CLOEXEC`，不是 stdin）。换句话说这一格报的是「**此刻 fd 表的占用情况**」，不是这个调用的常数：把同一份源码插到别的调用序列后面，返回的号就跟着变，能复现的是「它一定等于当时最小的空闲号」这条规则。

`count_fds()` 的结果包含 `stdin/stdout/stderr`（3 个），所以数字比「自己打开的 fd 数」大 3。`close_range` 关闭区间后，fd 号立刻可被复用；如果之后还有代码持有这些数字，就会指向新打开的对象——这正是「关闭 fd 后不要再用旧数字」的原因。

### `close()` 的错误与重试

`close(fd)` 失败时返回 `-1`，`errno` 可能是 `EBADF`（fd 未打开）、`EINTR`（被信号打断）、`EIO`（NFS 写回失败）。**不要重试 `close`**：Linux 上 fd 在返回前已经释放，重试可能关掉另一个线程刚打开的同号 fd。正确处理是记录错误，继续。

::: errata fd 生命周期的五个坑
1. **「`dup2` 和 `dup3` 只差一个 flag」**——`dup3` 在 `oldfd == newfd` 时返回 `EINVAL`，`dup2` 返回 `newfd`；依赖这个行为做「确保 fd 已打开」的代码会坏。
2. **「`close_range(3, ~0U, 0)` 在任何内核上都能用」**——5.9 之前返回 `ENOSYS`；glibc 2.34 之前没有声明，需要 `syscall(SYS_close_range, ...)`。
3. **「`close` 返回 `EINTR` 要重试」**——不要；fd 可能已经释放。
4. **「`/proc/self/fd` 里的数字就是稳定的 fd 列表」**——读目录本身会占一个 fd；并发 `open`/`close` 时列表随时变。
5. **「`FD_CLOEXEC` 只在 `open` 时能设」**——`fcntl(F_SETFD)`、`dup3`、`F_DUPFD_CLOEXEC`、`close_range(CLOEXEC)` 都能设，但只有创建时设置才是原子的。
:::

### 2.2.15 小结

把 `fdlife.c` 的四行输出连起来读，fd 表的行为就清楚了：本机实测 `a=3 b=4 dup3(a,100,CLOEXEC)=100 a_cloexec=1`，紧接着 `F_DUPFD_CLOEXEC(b,3)=5`——不是 3，因为 3 已经被 `a` 占了；`fds before close_range: 7` 里含 `stdin/stdout/stderr`、`a`、`b`、`c=100`、`d=5`，加上 `opendir` 自己占的那一个再减一，正好对上；关掉 `c`、`d` 之后剩 5。这一格再次印证 2.2.1 的说法：**fd 号是「当时最小的空闲位」，不是稳定身份**，任何把 fd 号当常量存起来的代码都会在并发场景里错位。

三个 API 的取舍也由此决定：要「复制并保证不泄漏给子进程」，用 `dup3(..., O_CLOEXEC)` 或 `fcntl(F_DUPFD_CLOEXEC)`，别用 `dup2` 之后再 `fcntl(F_SETFD)`——那中间如果同时有线程 `exec`，新程序就拿到了这个 fd；要在 `exec` 前清场，写 `close_range(3, ~0U, …)`，本机 `man 2 close_range` 给的示例用的甚至是 `CLOSE_RANGE_UNSHARE`，原因很实际：**多线程进程里 `flag=0` 关的是整张共享表，会把兄弟线程正在用的 fd 一起关掉**，先 unshare 再关才只影响自己。

版本下限也要按「拿不到就退回循环」写：`dup3` 是 Linux 2.6.27 / glibc 2.9（本机 `man 2 dup3` 原文），`close_range` 是 Linux 5.9 / glibc 2.34，更早的环境没有别的办法，只能遍历并逐个 `close`——而遍历 `/proc/self/fd` 本身还要占一个 fd，读到 1023 这种上限时也常常在目录刷新时拿到已失效的号。最后一条反直觉的规则要背下来：`close` 返回 `-1`（哪怕是 `EINTR` 或 NFS 的 `EIO`）**都不要重试**，因为 fd 在返回前已经释放，重试可能关掉另一个线程刚打开的同号 fd，正确动作是记录错误继续走。**如果只记住一件事：`CLOEXEC` 只在创建那一步设置才算原子，`close` 的失败只配被记录、不配被重试。**

## 2.2.16 原子性再审视：`O_APPEND`、`O_EXCL`、`rename` 的边界 {#sec-2.2.16}

这一节回答：`O_APPEND` 到底保证到哪一步？`O_EXCL` 在 NFS 上还可信吗？`rename` 的原子性有没有例外？

::: preview 先抓住一件事
「原子」这个词在这三个调用上指的范围**一个比一个小**，弄混就会写出看似正确的代码。`O_APPEND` 的原子范围是「**这一次** `write` 的定位+写入」，不管「这条记录」；`O_EXCL` 的原子范围是「**判断不存在 + 创建**」这两步合并，跨客户端（NFS）就落到服务器实现头上；`rename` 的原子范围是「**目录项替换**」，数据落盘完全不在它的承诺里。三句话的共同教训是：原子性只覆盖内核里那一个动作，凡是你把它和别的动作拼成一条流程，竞态窗口就回来了——所以本节每条保证都配一个「超出范围会怎样」的反例，并用一个可复跑的并发实验把 `O_APPEND` 的边界量出来。
:::

2.2.5 给了正确原语对照表。这里补「保证的边界」和「什么时候会失效」。

### `O_APPEND` 保证什么

在本地文件系统上，`write` 的「取末尾偏移 + 写入」在 inode 锁内完成，所以多个进程各自 `open(O_APPEND)` 并**单次 `write`** 不会互相覆盖。它**不保证**：

- 多次 `write` 组成的记录不交错；
- `writev` 的多段被视为一个不可分割的日志条目（整次调用定位一次，但写入过程仍可能被拆）；
- NFS 上跨客户端仍然原子（服务器实现相关）；
- `pwrite` 尊重你给的偏移（Linux 上仍追加）。

要保证「一条记录不交错」，记录必须一次 `write` 且长度不超过文件系统的原子写上限（普通文件没有 `PIPE_BUF` 那样的常量，实践上单次几 KiB 是安全的，但不是规范保证）。更强的要求用文件锁（2.3.6）。

### `O_EXCL` 的边界

`open(O_CREAT|O_EXCL)` 在本地文件系统上原子。几个例外：

- **NFSv2** 不支持原子独占创建，两个客户端可能都成功；NFSv3 起用 `CREATE` 的 exclusive 模式，通常可靠，但服务器实现仍有差异；
- 路径最后一段是**符号链接**时，`O_EXCL` 让 `open` 返回 `EEXIST`（即使链接悬空），这是安全特性：不会跟随链接创建目标；
- `O_EXCL` 不带 `O_CREAT` 时被忽略；
- `O_TMPFILE|O_EXCL` 创建的文件永远不能 `linkat`。

锁文件还要处理 **stale lock**：进程崩溃后文件还在，但没人持锁。正确做法不是「看文件存在就退出」，而是「`open(O_CREAT|O_EXCL)` 失败后，尝试对已有文件加锁，判断持有者是否还活着」，或者直接用 `flock`/`fcntl` 锁（锁随进程退出自动释放）。

### `rename` 的原子性边界

`rename(old, new)` 在同一文件系统内保证：`new` 要么指向旧内容，要么指向新内容，不会出现「不存在」的中间态。边界：

| 场景 | 结果 |
|:--|:--|
| 跨文件系统 | `EXDEV`，需「复制 + `fsync` + `rename` + 删除」 |
| `old` 是目录，`new` 是非空目录 | `ENOTEMPTY` |
| `old` 是目录，`new` 是文件 | `ENOTDIR` |
| `old` 是文件，`new` 是目录 | `EISDIR` |
| `new` 存在且是只读文件 | 允许（权限看目录，不看文件） |
| `new` 是挂载点 | `EBUSY` |
| 目标在另一个挂载命名空间 | 可能成功但不可见，取决于挂载传播 |

`rename` 只保证**目录项替换**原子，不保证数据落盘。数据要先 `fsync`，目录项要再 `fsync` 父目录（2.3.7）。

上面这几条边界不能只靠嘴说，`O_APPEND` 尤其容易被误当成「日志行天然不会乱」。下面这个实验把它量出来：8 个进程各写 200 条 64 字节的定长记录，每条记录的头部写着「进程号 + 该进程内的序号」，填充字节按进程号取不同字母，因此**任何一条被覆盖、被截断、被交错，校验函数都能报出来**。对照组去掉 `O_APPEND`，改成每次写之前 `lseek(fd, 0, SEEK_END)`——也就是很多代码里「手工追加」的写法。

```c
/* append_race.c — 8 个进程各写 200 条 64 字节定长记录：O_APPEND 与 lseek(END)+write 对照 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

#define NPROC  8
#define NREC   200
#define RECLEN 64

static void build(char *r, int p, int i)
{
    int head = snprintf(r, RECLEN, "p%02d r%04d ", p, i);
    memset(r + head, (char)('a' + p), RECLEN - head - 1);
    r[RECLEN - 1] = '\n';
}

static void verify(const char *path)
{
    int fd = open(path, O_RDONLY | O_CLOEXEC);
    if (fd == -1) { perror("open verify"); exit(1); }
    off_t sz = lseek(fd, 0, SEEK_END);
    char *buf = malloc((size_t)sz + 1);
    if (!buf) { perror("malloc"); exit(1); }
    if (pread(fd, buf, (size_t)sz, 0) != (ssize_t)sz) { perror("pread"); exit(1); }
    close(fd);

    int next[NPROC];
    for (int i = 0; i < NPROC; i++) next[i] = 0;
    long long in_order = 0, bad_shape = 0, bad_seq = 0;
    for (off_t off = 0; off + RECLEN <= sz; off += RECLEN) {
        const char *r = buf + off;
        int p, seq, shape_ok = 0;
        if (sscanf(r, "p%d r%d", &p, &seq) == 2 && p >= 0 && p < NPROC
            && r[RECLEN - 1] == '\n') {
            shape_ok = 1;
            for (int k = 10; k < RECLEN - 1; k++)
                if (r[k] != (char)('a' + p)) { shape_ok = 0; break; }
        }
        if (!shape_ok) { bad_shape++; continue; }
        if (seq != next[p]) { bad_seq++; continue; }
        next[p]++;
        in_order++;
    }
    printf("bytes=%lld  in-order=%lld  bad_shape=%lld  bad_seq=%lld\n",
           (long long)sz, in_order, bad_shape, bad_seq);
    free(buf);
}

int main(int argc, char **argv)
{
    int append = (argc > 1 && strcmp(argv[1], "append") == 0);
    const char *path = "/tmp/lab2c2_append.bin";

    int seed = open(path, O_WRONLY | O_CREAT | O_TRUNC | O_CLOEXEC, 0644);
    if (seed == -1) { perror("seed open"); return 1; }
    close(seed);

    for (int p = 0; p < NPROC; p++) {
        pid_t pid = fork();
        if (pid == -1) { perror("fork"); return 1; }
        if (pid == 0) {
            char rec[RECLEN];
            int flags = O_WRONLY | O_CREAT | O_CLOEXEC | (append ? O_APPEND : 0);
            int fd = open(path, flags, 0644);
            if (fd == -1) { perror("child open"); _exit(1); }
            for (int i = 0; i < NREC; i++) {
                build(rec, p, i);
                if (!append && lseek(fd, 0, SEEK_END) == -1) _exit(1);
                if (write(fd, rec, RECLEN) != RECLEN) {
                    fprintf(stderr, "short write errno=%d\n", errno);
                    _exit(1);
                }
            }
            close(fd);
            _exit(0);
        }
    }
    for (int p = 0; p < NPROC; p++) {
        int st = 0;
        if (wait(&st) == -1) { perror("wait"); return 1; }
        if (!WIFEXITED(st) || WEXITSTATUS(st) != 0)
            printf("a child exited nonzero (status 0x%x)\n", st);
    }
    printf("mode=%s expected=%lld\n", append ? "O_APPEND" : "lseek+write",
           (long long)NPROC * NREC * RECLEN);
    verify(path);
    unlink(path);
    return 0;
}
```

对照组去掉 `O_APPEND`、改成 `lseek(END)` + `write`，每条 64 字节记录仍由**一次** `write` 提交。先猜两个数的走向：`bad_shape`（畸形记录）会是 0 吗？`bad_seq`（序号断裂）呢？总长度会等于 `expected=102400` 吗？想清楚「两个进程算出同一个末尾偏移」时文件里会发生什么，再看解答。

::: sol 解答
`bad_shape` 是 **0**，`bad_seq` 是几百，总长度**小于** 102400。两个进程把 `lseek(END)` 跑在同一个偏移上，后到的 `write` 把先到那条记录**整条原地盖掉**——内核不会把单次 `write` 的字节拆开和别人拼接，所以没有「半个 A 拼上半个 B」的畸形行；丢的是整条记录，文件因此比预期短，按进程号推进的序号出现跳号。症状不是日志串行，而是**悄悄丢记录**，长度对不上时才露馅。
:::
:::

本机（ubuntu 24.04.5 / aarch64，ext4）实测，`expected=102400` 是 8×200×64 的算术值。两边读法不一样：`O_APPEND` 那一行**字节数、条数、序号全对上**，1600 条一条不少；对照组每次跑的结果都不同（75584、71936、58048），因为它输掉的是竞态，具体丢多少取决于调度——这正是竞态的输出特征。

更要看失败的**形态**：三组对照的 `bad_shape` 都是 0，`bad_seq` 却有几百。`bad_shape=0` 说明没有「半个 A 拼上半个 B」的字节级交错，因为每条记录仍是**一次** `write` 提交的，内核不会把单次写的字节拆开；坏在 `bad_seq` 和总长度上——两个进程算出同一个末尾偏移，后者把前者的整条记录原地盖掉，文件因此比预期短、序号因此断裂。

所以「`lseek`+`write` 追加」的典型症状不是日志串行，而是**悄悄丢记录**，比串行更难发现：长度对不上时才露馅。真要把多条写拼成一条记录又不交错，得用 `writev` 一次提交，或者把「组装+单次写」整个锁进临界区（2.3.3、2.3.6）。

::: errata 原子性的五个边界
1. **「`O_APPEND` 保证日志行不交错」**——只在「一行一次 `write`」时成立；`fprintf` 的多段写仍会交错。
2. **「`O_EXCL` 在 NFS 上也原子」**——NFSv2 不可靠；跨客户端要加锁服务或使用 `link()` 技巧。
3. **「`rename` 跨文件系统也能原子」**——返回 `EXDEV`，必须先复制到目标文件系统再 `rename`。
4. **「`rename` 后数据一定落盘」**——只保证目录项原子；数据与目录都需要 `fsync`。
5. **「临时文件放 `/tmp` 最安全」**——跨文件系统 `rename` 会失败；临时文件必须与目标同目录，且用 `O_EXCL` 或 `O_TMPFILE` 创建。
:::

### 2.2.16 小结

**给每个「原子」都问一句「原子到哪一步为止」。** `O_APPEND` 的实验把答案钉死了：单次 `write` 提交定长记录时，8 进程 × 200 条在 `O_APPEND` 下 `bytes=102400 in-order=1600 bad_seq=0`，去掉它改用 `lseek(END)`+`write`，同一段代码三次跑出 75584、71936、58048——**结果每轮都不同**，这是竞态的输出特征，也是它在测试环境里侥幸通过、在生产里持续丢数据的原因。

`bad_shape=0` 是另一半教训：`O_APPEND` 不保证的是「多次写组成的一条」，一旦每条记录只由一次 `write` 提交，它反而给得很足（定位和写入在同一把 inode 锁内完成）。所以规则可以写得很短：**一条记录 = 一次系统调用**，做不到就 `writev`，再做不到就加锁；长度字段（`len=`）是最后一道保险，让读端能按边界切开重读。

`O_EXCL` 的边界是「本地文件系统内原子」，出了本地就要看服务器实现（NFSv2 明确不可靠），并且它有个常被当作 bug 的安全特性：末段是符号链接时直接 `EEXIST`，哪怕链接悬空——这正是「不跟随链接创建」的防线；而锁文件真正的麻烦不是竞态而是 stale lock，进程崩溃后文件还在、没人持锁，靠「存在即退出」永远解不开，要配合 `flock`/`fcntl` 这类随进程释放的锁。`rename` 的边界最容易高估：它保证的只有目录项替换那一瞬间，`EXDEV`、`ENOTDIR`、`EISDIR`、`EBUSY` 都写在上面那张表里，且**不含数据落盘**——写完临时文件不 `fsync`、`rename` 后不 `fsync` 父目录，断电后就会看到「文件存在但全是 0」的经典现场（2.3.7）。

**如果只记住一件事：三种「原子」各自的范围都小于一条完整的业务流程，越界的那一段必须自己加锁或加 `fsync`。**

::: method 即时自测 · 2.2.16

**Q2（辨析）** 「`open(O_CREAT|O_EXCL)` 对一个悬空符号链接返回 `EEXIST`」是缺陷还是特性？`rename` 承诺了什么、没承诺什么？为什么说「临时文件放 `/tmp`」不安全？

**Q3（应用）** 一个多进程服务把日志写成「两次 `write`：先 `write("seq=7 len=41 ")`，再 `write(body)`」，本地文件系统、都带 `O_APPEND`，运维反馈文件长度对但偶尔读出畸形行。请按本节结论判断这是否矛盾，并给出两种修法与各自的代价。

::: sol 答案
**A1** `O_APPEND` 组 `bytes=102400 in-order=1600 bad_shape=0 bad_seq=0`，说明「定位到末尾 + 写入」在这次调用内不可分割，记录一条不丢；对照组总量随轮次变化（75584/71936/58048），说明两个进程算出同一个末尾偏移、后者整条覆盖前者，文件比预期短。`bad_shape=0` 是因为每条记录仍由**一次** `write` 提交，内核不会拆单次写的字节，所以没有字节级交错；`bad_seq` 高则是整条记录被别的进程替换后，按进程号推进的序号出现跳号——症状表现为「悄悄丢数据」而不是「串行」。
**A2** 是特性：`O_EXCL` 的语义包含「末段是符号链接就失败」，即使链接悬空，这样独占创建才不可能被诱导去写别人指定的目标（常见于 `/tmp` 里的替换攻击）；把它当缺陷去「先 `unlink` 再 `open`」反而重新打开了竞态窗口。`rename` 只承诺同文件系统内的**目录项替换**是原子的，即 `new` 在任何时刻都指向旧内容或新内容之一；它不承诺数据已落盘、不承诺跨设备（`EXDEV`）、也不承诺目录类目标的特殊情况（`ENOTEMPTY`/`ENOTDIR`/`EISDIR`/`EBUSY`）。临时文件放 `/tmp` 不安全的根因是它常常与目标文件不在同一文件系统上：最后一步 `rename` 直接 `EXDEV` 失败，只能退化成「复制 + 删」，中途失败就留下半成品；正确做法是把临时文件建在目标同目录，用 `O_EXCL` 或 `O_TMPFILE` 创建。
**A3** 不矛盾，而且这正是本节区分出来的两种失败。`O_APPEND` 只保证**单次** `write` 的定位+写入原子，两次 `write` 就是两个调度点：另一个进程的记录头可以插在「头」与「体」之间，于是出现畸形行；而总长度仍是所有写请求之和，长度字段自然对得上——用「文件长度对」当健康检查会完全漏掉这类损坏。两种修法：① 把头和体拼成一次提交，用 `writev`（一次调用，内核层面无插入点），代价是要正确处理短写后的按段推进、且段数受 `IOV_MAX`（本机实测 1024）限制；② 把「格式化 + 单次写」整个放进临界区，用 `flock`/`fcntl` 或进程内互斥锁，代价是并发吞吐下降、且只在同一台机器的同一批进程间有效（NFS 上还要看锁服务）。两种做法都建议保留 `len=` 字段，让读端能按记录边界切分与自检。

## 2.2.17 内核路径：`openat2`、`read`/`write` 与回写 {#sec-2.2.17}

这一节回答：`write` 返回成功时，数据到底在哪一层？`fsync` 之后又到了哪一层？

::: preview 先抓住一件事
`write` 返回成功，数据只到了**页缓存**——内核内存里的一层拷贝，不在磁盘上。从页缓存到磁盘还隔着回写线程与文件系统提交两道关，`fsync`/`fdatasync` 才是等设备确认的那一步。带住这条链，「写成功为什么还会丢」就都有答案了。
:::

2.1.14 给了 `openat`/`read` 的骨架。这里补 `write` 与回写路径，因为「写成功不等于落盘」的所有讨论都落在这条链上。

### `write` 的路径

先说口径，因为这张表的入口两层属于**另一台机器**。旧版按 x86-64 + Linux 6.8 叙述：陷入后落到 `entry_SYSCALL_64`，由 `do_syscall_64` 查 `sys_call_table[1]`——`1` 是 x86-64 的 `write` 号。**本套件没有 x86 机器，x86-64 那一侧的函数名与调用号一个都没有实测过**，只能当读源码得到的形状。本套件的测试机是 aarch64 + 内核 7.0.0-38-generic，同一件事的名字全换了：`write` 的调用号是 **64**（`grep -n '#define __NR_write ' /usr/include/asm-generic/unistd.h` → 本机第 174 行 `#define __NR_write 64`），陷入走的是同步异常向量 `el0_svc`，分派在 `invoke_syscall`，包装函数是 `__arm64_sys_write`。

aarch64 那一列的函数名不是猜的。`kptr_restrict=1` 只把**地址**遮成 0、**不遮符号名**，所以普通用户在 `/proc/kallsyms` 里能查到「这台内核到底有没有这个函数」（它证明存在性，不证明调用顺序，顺序仍然是读源码）：

```text
$ grep -wE 'el0_svc|invoke_syscall|__arm64_sys_write|ksys_write|vfs_write|new_sync_write' /proc/kallsyms
0000000000000000 t invoke_syscall
0000000000000000 T vfs_write
0000000000000000 T ksys_write
0000000000000000 T __arm64_sys_write
0000000000000000 t el0_svc
$ grep -cw entry_SYSCALL_64 /proc/kallsyms
0
$ grep -cw do_syscall_64 /proc/kallsyms
0
$ grep -cw new_sync_write /proc/kallsyms
0
```

上面这段是 ubuntu 24.04.5 / aarch64 本机实测（`wc -l < /proc/kallsyms` 打出 233440，不是空文件）。注意 `sys_call_table` 这个符号本机**也有**（`D sys_call_table`）——表和 `write` 都在，变的只有下标：x86-64 是 1，本机是 64。还有一条要防的误读：本机查不到的 `new_sync_write`、`iov_iter_ubuf`、`copy_page_from_iter_atomic`、`generic_write_sync`、`ext4_bio_write_page`、`__filemap_get_folio`，**不等于内核里没有这些函数**——静态内联、改名或从 `.c` 挪进头文件的实现都不进 `kallsyms`；反过来说，也不能因为表里写了就当本机核过。下面这张表加了一列，逐行写清这台机器上到底查得到查不到：

`generic_perform_write()` 的核心循环（删节）：

```c
for (;;) {
    struct folio *folio = __filemap_get_folio(mapping, pos >> PAGE_SHIFT,
                                FGP_WRITEBEGIN, mapping_gfp_mask(mapping));
    size_t offset = pos & (PAGE_SIZE - 1);
    size_t bytes = min_t(size_t, bytes, PAGE_SIZE - offset);

    a_ops->write_begin(file, mapping, pos, bytes, &folio);
    copied = copy_page_from_iter_atomic(&folio->page, offset, bytes, i);
    a_ops->write_end(file, mapping, pos, bytes, copied, folio);
    pos += copied; written += copied;
    balance_dirty_pages_ratelimited(mapping);
}
```

这段代码解释了三个现象：

1. **`write` 返回时数据在 page cache，不在磁盘**。`copy_page_from_iter_atomic` 只把用户数据拷进内核页；`write_end` 把页标记为脏，之后由回写线程刷盘。
2. **`balance_dirty_pages` 会主动限速**。脏页超过 `vm.dirty_ratio` 时，`write` 会被内核睡眠拖慢，而不是无限占用内存。
3. **`O_SYNC`/`O_DSYNC` 在 `write_iter` 返回前调用 `generic_write_sync`**，最终走 `vfs_fsync_range` → `file->f_op->fsync` → ext4 的 `ext4_sync_file`，这才是等设备确认的地方。

### `openat2` 的额外检查

`do_sys_openat2` 在普通 `open` 路径上多了一步 `build_open_flags`，它校验 `how->flags` 与 `how->resolve` 的合法组合。非法组合返回 `EINVAL`，例如：

- `O_TMPFILE` 没有搭配 `O_WRONLY`/`O_RDWR`；
- `resolve` 带了未知位；
- `how->mode` 在非创建场景非 0；
- `how->flags` 带了 `O_CREAT` 但没有 `mode`。

路径解析在 `path_openat` 里，`open_last_lookups` 处理最后一段；`RESOLVE_BENEATH`/`IN_ROOT` 的检查在 `link_path_walk` 的每一步比较 `nd->path` 与根，逃逸时返回 `-EXDEV`。

::: note 回写与 `fsync` 的关系
`fsync(fd)` 做两件事：把该文件的所有脏页回写（`filemap_write_and_wait_range`），再让文件系统提交元数据（ext4 的日志提交）。`fdatasync(fd)` 只保证数据与「读回数据必需的元数据」，不保证 mtime 等。`sync()` 刷所有文件系统，`syncfs(fd)` 只刷该 fd 所在文件系统。对数据库 WAL，`fdatasync` 通常够；对「重命名发布」，目录的 `fsync` 不能省。
:::

### 2.2.17 小结

`write` 的路径是一条「层层转交」的链：libc 装寄存器陷入 → 按调用号分派到 `__arm64_sys_write`（本机名，x86-64 是另一个名字）→ `ksys_write`/`vfs_write` 做权限与范围检查 → 文件系统的 `write_iter` 把用户数据拷进页缓存并把页标脏 → 脏页攒够了由回写线程刷盘。`write` 返回成功只走到「拷进页缓存」那一步；`balance_dirty_pages` 还会在脏页太多时反过来限速你的 `write`。要「设备确认」只有 `O_SYNC`/`O_DSYNC` 或显式 `fsync`/`fdatasync` 这几条路，它们等的是 `ext4_sync_file` 那一层。`openat2` 那一侧多的是一次 `build_open_flags` 合法性检查与逐步的根边界比较，非法组合直接 `EINVAL`，逃逸返回 `EXDEV`。跨架构要分开记的只有入口三件（陷入方式、调用号、包装函数名）；VFS 以下的层次名是契约，本机在 `/proc/kallsyms` 里逐个查得到。**如果只记住一件事：`write` 的成功是「进了内核的账」，`fsync` 的成功才是「进了磁盘的账」，两本账之间还隔着一整个回写队列。**

## 2.2.18 两个实验：`strace` 解码 flags 与 `/proc/self/fdinfo` {#sec-2.2.18}

这一节回答：怎样确认一个程序真正用了哪些 flags、fd 当前处于什么状态？

::: preview 先抓住一件事
别背 flags 的八进制位——用 `strace` 看**名字**，或用「开两个只差一个标志的 fd」的**差法**读 `/proc/self/fdinfo`。这两个实验把「我以为程序开了什么」变成「机器上它开了什么」，也是全章排查 fd 泄漏与权限位疑案的标准动作。
:::

- **前面 5 行是动态链接器干的活**，不是 `copy` 的逻辑：`copy` 是动态链接的，`ld.so.cache` 与 `libc.so.6` 的 `openat`/`read`/`close` 一定排在最前面。旧版把 `openat("/etc/hosts")` 直接写成第 1 行，是按静态/过滤后的形状写的。
- 正因为那 5 行存在，`head -12` 在本机**看不到**发布的全过程，要用 `head -20`；而照旧版的行序去数 `when=N`，就会把故障注入打到动态链接器身上（见下面故障注入那条）。
- `O_EXCL` 出现在临时文件的 `openat` 里，说明程序防止并发覆盖；`0644` 是 `mode` 参数，实际权限还要 `& ~umask`。
- `read` 的最后一次返回 `0`，这是 EOF，不是错误。本机 `/etc/hosts` 是 **235** 字节（`wc -c < /etc/hosts` 可核），所以第一轮 `read` 返回 235、第二轮的 `count` 变成 `261909`（= 262144 − 235，是 `read_full` 在同一缓冲里续读的残余长度），不是旧版写的 221。
- `fsync(4)` 与 `fsync(3)` 分别对应「文件数据」与「目录项」，缺一个都不算完整发布。
- `-yy` 把 fd 映射到路径；没有它只能看到 `read(3, ...)`，fd 复用时会误判——本机 `3` 这个数字在同一个程序里先后是 `ld.so.cache`、`libc.so.6`、`/etc/hosts`、目录 `.`，四次归属完全不同。
- 这条命令**不会打印 `rename` 那行**：`-e` 的名单里没有它。要看发布那一步，把 `rename` 加进 `-e trace=` 名单。

故障注入：让 `openat` 返回 `EACCES`，验证错误分支是否清理临时文件——**`when` 数的是「第几次匹配」，包括动态链接器那两次**，所以本机 `when=1` 打在 `ld.so.cache` 上，`copy` 本身照样跑完（实测：程序退出码 0，`/tmp/x` 正常写出 235 字节），`ls /tmp/x.tmp.*` 报「清理正确」是**假通过**：

```bash
strace -e trace=openat -e inject=openat:error=EACCES:when=4 ./copy /etc/hosts /tmp/x
ls /tmp/x.tmp.* 2>/dev/null && echo "临时文件泄漏" || echo "清理正确"
```

本机实测 `when=4` 才打到目标临时文件那次 `openat`：`openat(AT_FDCWD, "/tmp/x.tmp.111241", O_WRONLY|O_CREAT|O_EXCL|O_CLOEXEC, 0644) = -1 EACCES (Permission denied) (INJECTED)`，程序报 `copy: /tmp/x.tmp.111241: Permission denied` 退出，`/tmp/x` 和 `/tmp/x.tmp.*` 都不残留。本机的 `openat` 次序是 1=`ld.so.cache`、2=`libc.so.6`、3=`/etc/hosts`、4=临时文件、5=目录 `.`，所以 `when=3` 打源文件、`when=5` 打目录 `fsync` 那步——**先数清楚序再选 `when`**。

### 实验二：`/proc/self/fdinfo` 与 `(deleted)`

```bash
exec 3<>/tmp/fdinfo.demo
cat /proc/self/fdinfo/3
# pos:    0
# flags:  0400002
# mnt_id: 35
# ino:    2883709

ls -l /proc/self/fd/3
# lrwx------ 1 juanwang juanwang 64 ... 3 -> /tmp/fdinfo.demo
```

口径：ubuntu 24.04.5 / aarch64（内核 7.0.0-38）本机实测，同一条命令连跑两次四行全同。同一台机器上把只读打开换成 `exec 3</etc/hosts`，得到的是 `pos: 0`、`flags: 0400000`、`mnt_id: 35`、`ino: 2755550`。`pos` 是这个 `struct file` 的共享偏移——`printf abcde >&3` 之后再读一次就变成 `pos: 5`。`mnt_id` 与 `ino` 是**机器与挂载相关**的读数，不能跨机引用：本机 `mnt_id: 35` 在 `/proc/self/mountinfo` 第一列查到的是 `8:2 / / rw,relatime … ext4 /dev/sda2`（根挂载），`ino: 2883709` 与 `stat -c %i /tmp/fdinfo.demo` 相等；换一台机器、重新挂载一次、甚至只是重建这个文件，这两个数就都变。

`flags` 这一格是本章照抄别处读数最容易翻车的地方：旧版正文按 x86-64 的语义解释它（`0100002` 去掉 `O_LARGEFILE` 的 `0100000` 剩 `02`），而本机同一个实验打印的是 `0400002`。

**不要去争「这一位到底是不是 `O_LARGEFILE`」——同一个名字在本机的三个头文件里是三个不同的数**：

| 在哪里查 `O_LARGEFILE` | 本机值 | 本机原文 |
|:--|--:|:--|
| 用户态 `<fcntl.h>`（`cc -std=c17 -D_GNU_SOURCE -dM -E -include fcntl.h`） | **0** | `bits/fcntl.h`：`#ifdef __ILP32__ … 0400000 #else … 0`，LP64 的 aarch64 走 0 这一支 |
| 内核 UAPI 头 `<linux/fcntl.h>`（`asm/fcntl.h`） | **0400000** | `#define O_LARGEFILE	0400000` |
| glibc 通用兜底 `bits/fcntl-linux.h` | **0100000** | `#ifndef __O_LARGEFILE` / `# define __O_LARGEFILE 0100000`——在 aarch64 上被第一行挡掉，不参与展开 |

同一次 `cc -dM` 里还能查到：`O_NOFOLLOW` 才是本机用户态的 `0100000`，`O_DIRECTORY=040000`、`O_DIRECT=0200000`、`O_CLOEXEC=02000000`（`O_DIRECT`、`O_NOFOLLOW` 要 `_GNU_SOURCE` 才可见）。这一格打印的是内核里的 `f_flags`，不是你以为的「你传给 `open` 的那串宏」，所以上面任何一张表都可能与它错位。

**所以逐位念 `flags` 不能靠记忆，要用差法**：开两个只差一个标志的 fd，看这一格多了哪一位。本机实测（同一个普通文件，一次进程里逐个 `open` 后读各自的 `fdinfo`）：

| 打开方式 | `fdinfo` 的 `flags` | 差出来的那一位 |
|:--|--:|:--|
| `O_RDONLY` | `0400000` | 基线：内核自己那一位永远在里面 |
| `O_WRONLY` | `0400001` | `1` = `O_WRONLY` |
| `O_RDWR` | `0400002` | `2` = `O_RDWR` |
| `O_RDWR` \| `O_APPEND` | `0402002` | `02000` = `O_APPEND` |
| `O_RDWR` \| `O_NOFOLLOW` | `0500002` | **`0100000`——本机用户态这一位是 `O_NOFOLLOW`** |
| `O_RDWR` \| `O_DIRECT` | `0600002` | `0200000` = `O_DIRECT` |
| `O_RDONLY` \| `O_DIRECTORY`（目录） | `0440000` | `040000` = `O_DIRECTORY` |
| `O_RDONLY` \| `O_CLOEXEC` | `02400000` | `02000000` = `O_CLOEXEC` |
| `O_RDWR` \| `O_SYNC` | `04410002` | `04010000` = `O_SYNC` |
| `O_RDWR` \| `O_DSYNC` | `0410002` | `010000` = `O_DSYNC` |
| `O_RDWR` \| `O_NONBLOCK` | `0404002` | `04000` = `O_NONBLOCK` |
| `O_WRONLY` \| `O_TRUNC` | `0400001` | 差不出来：`O_TRUNC` 只作用在打开那一刻，不作为状态保留 |

决定性的一对是 `O_RDWR` 的 `0400002` 与 `O_RDWR|O_NOFOLLOW` 的 `0500002`：多出来的正是 `0100000`，而这一位在 x86-64 的表里写着 `O_LARGEFILE`、在本机的用户态头文件里写着 `O_NOFOLLOW`。换句话说，**只有差法能告出这一位是「刚刚被我加上的那个标志」**，任何「背表拆位」都会在跨架构时拆错。另一条不用猜的路是看 `strace` 打出的**名字**：`strace -e trace=openat` 里那行 `openat(..., O_RDWR|O_CREAT|O_TRUNC, 0600)` 才是可读事实，数字只是它的编码。

删除文件但不关闭 fd：

```bash
exec 4>/tmp/fdinfo.deleted
rm /tmp/fdinfo.deleted
ls -l /proc/self/fd/4      # -> /tmp/fdinfo.deleted (deleted)
lsof +L1 | grep fdinfo     # 找到仍持有它的进程
```

`(deleted)` 表示目录项没了但 inode 还有引用；`df` 不会降，直到 fd 关闭。这是「日志轮转后磁盘不释放」的标准原因。

### 2.2.18 小结

两个实验合起来是一套取证手法：**`strace` 看调用序列与 flags 名字，`fdinfo` 看单个 fd 的当前状态**。`strace -yy` 把 fd 映射成路径，是认「这个 3 到底是谁」的唯一可靠办法；数 `when=N` 之前要先数清动态链接器占了前几次匹配，否则故障注入会打错目标、程序照常跑完还骗你说「清理正确」。`fdinfo` 的 `flags` 一格打印的是内核里的 `f_flags`，与你在用户态宏上背出的数可能错位——`O_LARGEFILE` 一个名字在本机三个头文件里三个值——所以逐位认标志靠差法，或者干脆看 `strace` 打出的名字。`pos` 是共享偏移、`mnt_id`/`ino` 是机器与挂载相关的读数，都不能跨机引用。`(deleted)` + `lsof +L1` 则是「日志轮转磁盘不降」的标准侦破路径。**如果只记住一件事：flags 与 fd 状态都不要靠记忆断言，当场用 `strace` 的名字或 `fdinfo` 的差法取一个读数。**

**A1** `-yy` 把 fd 映射到路径（如 `3</etc/hosts>`），不带它只能看到 `read(3, ...)`，fd 复用时会误判——本机 `3` 在同一个程序里先后是 `ld.so.cache`、`libc.so.6`、`/etc/hosts`、目录 `.`。`when` 数的是「第几次匹配」且**包含**动态链接器那两次 `openat`，所以 `when=1` 只会打在 `ld.so.cache` 上，`copy` 本身照样跑完；此时临时文件没被创建、`ls /tmp/x.tmp.*` 报「清理正确」，但清理逻辑根本没被测到，是假通过。先数清楚序（本机是 1=`ld.so.cache`、2=`libc.so.6`、3=源文件、4=临时文件、5=目录）再选 `when`。
**A2** 因为这一格打印的是内核里的 `f_flags`，而同一个名字在不同头文件里值不同：本机用户态 `<fcntl.h>` 的 `O_LARGEFILE` 是 0（LP64 支线），内核 UAPI 是 `0400000`，glibc 兜底是 `0100000`，而且本机用户态的 `0100000` 其实是 `O_NOFOLLOW`——x86-64 的拆位表在本机直接拆错。两种不靠背表的方法：① 差法——开两个只差一个标志的 fd，看 `flags` 多出哪一位；② 看 `strace -e trace=openat` 打出的**名字**（`O_RDWR|O_CREAT|O_TRUNC`），那是可读事实，数字只是编码。
**A3** 命令序列：`ls -l /proc/*/fd 2>/dev/null | grep deleted`（或 `lsof +L1`）找到仍持有被删文件的进程 → `ls -l /proc/PID/fd/N` 确认 `(deleted)` → 对应到是哪个未关闭的 fd（常见是轮转后没重新 `open` 的旧句柄）→ 修程序或重启进程。命中判据：路径后缀 `(deleted)` 且 `df` 占用不降。数据要等所有引用都关闭（最后一个 fd `close`）才释放，因为 `(deleted)` 只是目录项没了、inode 还被打开文件描述引用着。`pos` 是这个 `struct file` 的共享偏移（写一次就变）；`mnt_id`、`ino` 跟机器、挂载与文件重建相关（本机 `mnt_id: 35` 是根挂载的编号，换机即失效）——三个数都只属于取它的那次现场，抄进通用文档就是假读数。
:::
:::

## 2.2.19 本章陷阱清单 {#sec-2.2.19}

这一节回答：前面十八节的坑，按「哪一步被当成了整件事」怎么归类？踩坑时先查哪一句？

::: preview 先抓住一件事
两组陷阱共享同一个病根：**把「一次系统调用成功」当成「整个操作完成」**。创建漏传 `mode`、短读当 EOF、`close` 后重试、`fsync` 只刷文件不刷目录——都是跨调用的组合缺了显式原语。先背这个病根，八条坑就都挂得上去。
:::

::: errata 创建与读写循环的四个坑
1. **现象**：`open(path, O_CREAT|O_WRONLY)` 创建的文件权限是随机值。**原因**：漏了第三个参数 `mode`。**修复**：带 `O_CREAT`/`O_TMPFILE` 必须传 `mode`。
2. **现象**：锁文件在进程崩溃后永久残留。**原因**：`O_EXCL` 文件不会自动删除。**修复**：改用 `fcntl`/`flock` 锁，或记录 PID 并检测存活。
3. **现象**：`read` 返回 100 而不是 4096，循环提前结束。**原因**：把短读当 EOF。**修复**：只在 `n == 0` 时结束。
4. **现象**：`write` 返回 65536，程序认为 1 MiB 写完了。**原因**：管道/socket 短写。**修复**：循环推进缓冲区。
:::

::: errata fd 生命周期与持久化的四个坑
1. **现象**：`dup2(fd, fd)` 之后 fd 被关闭。**原因**：误以为 `dup2` 会复制；相同参数直接返回。**修复**：判断 `oldfd != newfd`，或改用 `dup3` 并处理 `EINVAL`。
2. **现象**：`close` 返回 `EINTR` 后重试，关掉了别人的 fd。**原因**：Linux 上 fd 已释放。**修复**：记录错误，不重试。
3. **现象**：`exec` 后子进程继承了数据库连接。**原因**：fd 没有 `CLOEXEC`。**修复**：`O_CLOEXEC`、`F_DUPFD_CLOEXEC`、`close_range(CLOEXEC)`。
4. **现象**：`fsync` 文件后断电，改名后的文件仍丢失。**原因**：目录项没 `fsync`。**修复**：`fsync(file)` → `rename` → `fsync(dir)`。
:::

### 2.2.19 小结

这些坑的共性是：**把「一次系统调用成功」当成「整个操作完成」**。跨调用的组合需要显式原语来补：定位+写要 `O_APPEND` 或 `pread`，检查+创建要 `O_CREAT|O_EXCL`，替换要 `rename`，落盘要「文件 `fsync` + 目录 `fsync`」。排查顺序也可以写成一句：先问「这一步的原子边界到哪为止」，再问「失败时谁负责清理」，最后才看返回值细节。**如果只记住一件事：每个坑的修复都不是「加个判断」，而是换一个把组合包进单次调用的原语。**

::: method 即时自测 · 2.2.19
**Q1（记忆）** 两组陷阱各覆盖哪四个坑？它们共同的病根是什么？

**Q2（辨析）** 「只要所有系统调用都检查返回值，就不会踩这八个坑。」对不对？举一个检查了返回值仍然中招的坑。

**Q3（应用）** 一段代码写配置：`open(O_CREAT|O_WRONLY)` → `write` → `fsync` → `close` → `rename` → 退出。逐条对照两组陷阱，指出它可能踩的坑并写出修复后的调用序列。

::: sol 答案
**A1** 第一组（创建与读写循环）：漏传 `mode`、stale 锁文件、短读当 EOF、短写当完成。第二组（fd 生命周期与持久化）：`dup2(fd,fd)` 反而关闭、`close` 遇 `EINTR` 重试、`exec` 泄漏无 `CLOEXEC` 的 fd、`rename` 后没 `fsync` 目录。共同病根是把一次系统调用的成功当成整个业务步骤的完成。
**A2** 不对。stale 锁文件（`O_EXCL` 创建后进程崩溃）每一次返回值都检查了也照样中招——它缺的不是返回值判断，而是「锁随进程释放」这个语义，要换 `flock`/`fcntl`；`rename` 后数据丢失同理，`write`/`fsync`/`rename` 每步都成功也可能丢目录项，缺的是父目录那次 `fsync`。返回值检查只覆盖「调用当场失败」，覆盖不了「组合顺序错误」。
**A3** 可能踩：① `O_CREAT` 那次若 `mode` 依赖 umask 而没有显式传，权限不可预期；② 写配置的 `write` 可能短写；③ `fsync` 文件后直接 `rename`，没有 `fsync` 父目录，断电后旧配置也丢；④ `O_CREAT|O_WRONLY` 没带 `O_EXCL`/`O_TRUNC` 语义不明确，没带 `CLOEXEC` 则 `exec` 会泄漏。修复序列：`open(目标同目录临时名, O_WRONLY|O_CREAT|O_EXCL|O_CLOEXEC, 0644)` → 循环 `write_full` → `fsync(fd)` → `close(fd)` → `rename(临时名, 目标)` → `open(父目录, O_RDONLY|O_DIRECTORY)` → `fsync(目录fd)` → `close`。锁文件场景另用 `flock`，别用 `O_EXCL` 文件当锁。
:::
:::

## 2.2.20 本章小结 {#sec-2.2.20}

这一节回答：二十节读完，你手上多了哪几样能当场验证的能力？哪一段还只是「认得名词」？

::: preview 先抓住一件事
这一章只留下三样东西：一张「fd → 打开文件描述 → inode」的三层图、一个「返回值五形态 + 组合靠原语」的读写习惯、一套「用 `strace` 与 `fdinfo` 当场取证」的动作。判据是——给你一个「日志丢了几行、磁盘没满却写不进」的现场，你能说出哪一层在骗你，并用一条命令证实。
:::

**第一段，模型与五个调用（2.2.1–2.2.4）。** fd 是进程 fd 表里的一个小整数，真正持有偏移与状态标志的是「打开文件描述」，inode 管磁盘上的字节与元数据——`dup` 之后共享偏移、同一路径开两次则各算各的，全由这三层决定。`open` 的 flags 分访问/创建/状态三组，`mode` 还要过 `umask`；`read`/`write` 的返回值有「全成、部分、0、`EINTR`、`EAGAIN`」五种形态，循环只在 `n == 0` 时终止；`close` 不重试、`dup2`/`dup3` 管复制、`fcntl` 管状态位、`lseek` 管偏移。这一段立的是**模型**——偏移住哪层、返回值承诺了什么。

**第二段，原子性与完整程序（2.2.5–2.2.7）。** `O_CREAT|O_EXCL` 把「检查+创建」、`O_APPEND` 把「定位+写」各自合成一步，`access()+open()` 与 `lseek(END)+write` 的竞争窗口就在这对比里现形；fd 泄漏用 `/proc/self/fd` 与 `lsof +L1` 查，`(deleted)` 解释「轮转后 `df` 不降」。2.2.7 的 `copy.c` 把短读短写、`fsync`、错误清理拼成一份能抄走的骨架。这一段立的是**纪律**——组合操作必须换原子原语，而不是加判断。

**第三段，页缓存与接口全表（2.2.8–2.2.11）。** `write` 返回时数据在页缓存，落盘要靠回写与 `fsync` 家族；flags 全表、`O_TMPFILE` 三种做法、`openat2` 的 `RESOLVE_*` 护栏、`umask` 与默认 ACL 共同决定新建权限。这一段立的是**边界**——每个标志改什么、用错报哪个 `errno`。

**第四段，返回矩阵与偏移、向量 I/O（2.2.12–2.2.15）。** 12 个错误码按「重试/退避/放弃」分派，`EINTR` 是事件、`EAGAIN` 是状态；`lseek` 加 `SEEK_DATA`/`SEEK_HOLE` 能问出稀疏文件的空洞；`pread`/`writev` 解决多线程共享偏移与短写推进；`fork`/`exec` 前后哪些 fd 还在，由 `CLOEXEC` 与 `close_range` 说了算。这一段立的是**接口级判断**——什么场景换哪个调用。

**第五段，边界、内核路径与取证（2.2.16–2.2.19）。** 三种「原子」各自的范围都小于一条完整业务流程；`write` 的内核链解释「写成功为什么还会丢」；`strace` 看名字与序列、`fdinfo` 用差法读 flags，是不改代码就能拿到的证据；最后两组陷阱把「一次调用成功 ≠ 整件事完成」这个病根挂满全章。这一段立的是**追问**——现象出现时先定位层次，再选工具。

逐条打勾的达标表已移交章末的[学习目标自检表](ch02-checklist.md)，正文不再挂表。留在这里的是三条判据：

- **能解释**：偏移为什么住在「打开文件描述」这一层；`O_APPEND` 与 `lseek+write` 差在哪一步；`write` 返回成功后数据在哪、断电丢不丢；`fdinfo` 的 `flags` 为什么不能背表拆位；`(deleted)` 为什么不释放空间。
- **能操作**：写出处理短读/短写/`EINTR` 的循环并一次编译通过；按「临时文件 → `fsync` → `rename` → 目录 `fsync`」的顺序做一次原子发布；用 `strace -yy` 认出调用序列里的动态链接器行与目标行；用差法解一个 `fdinfo flags`；用 `lsof +L1` 定位持有 `(deleted)` 的进程。
- **能判断**：这个组合操作的原子边界到哪为止、越界那段谁负责；这个返回值该重试、退避还是放弃；这个读数属于哪台机器、能不能抄进文档；失败形态是「丢记录」还是「串行」，分别指向哪个缺陷。

如果只记住一件事：**每个 fd 背后有三层对象，每次调用成功只完成一步——偏移问「打开文件描述」，组合问「原子原语」，落盘问「`fsync`」，剩下的一切读数都当场用 `strace` 或 `fdinfo` 验证。**

::: errata 本章的口径边界
1. **读数只属于它那台机器**：本章的耗时、调用号、`fdinfo` 位值、`mnt_id`/`ino`、管道容量都来自具体一台机器与一个内核（跑测量的机器是 Ubuntu 24.04.5 的 aarch64 环境）；x86-64 的 flags 八进制表与本机 `0400002` 这类读数换架构就换数，别当 Linux 的常数抄。2.2.9 的 flags 全表与 2.2.18 的差法表若与其他机器的读数混用，按各自块上的标注读。
2. **形状而不是读数**：2.2.17 的路径表来自内核源码的层次与命名（本机用 `/proc/kallsyms` 核过符号存在性），内核版本不同就可能改名、内联；`strace`、`fdinfo` 的输出格式也随版本变化。要带走的是「先查哪一层」，不是某个字段名。
3. **只按语义描述、未逐项量化的部分**：NFS 上 `O_EXCL`/锁的行为随服务器实现变化，本章只写「NFSv2 明确不可靠、跨客户端要锁服务」这条边界，没有某台 NFS 服务器的实测记录；stale lock 的检测与恢复、日志轮转的完整方案放在习题与自检表里。
:::

::: method 即时自测 · 2.2
**Q1** 两个进程各自 `open("log", O_WRONLY|O_APPEND)`，各写一行 100 字节。会不会互相覆盖？会不会交错？

**Q2** `read(fd, buf, 4096)` 返回 100，可能的原因有哪些？列出至少三种。

**Q3** 为什么 `open(O_CREAT|O_EXCL)` 比 `access()` + `open()` 安全？在 NFS 上还安全吗？

**Q4** `write()` 返回成功，进程被 `kill -9`，数据会丢吗？机器断电呢？

::: sol 答案
**A1** 不会互相覆盖（`O_APPEND` 保证每次写定位到末尾是原子的）；但一行 100 字节若由多次 `write` 完成，仍可能与其他进程的写交错。一次 `write` 写完一行则不会交错。

**A2** ① 管道/终端/socket 缓冲区里只有 100 字节；② 被信号打断后部分读取；③ 读到文件末尾只剩 100 字节；④ 非阻塞 fd 当前只有 100 字节；⑤ 设备/驱动按块返回。

**A3** `O_EXCL` 把「检查 + 创建」合成一个原子操作，消除了 TOCTOU 窗口。NFSv2 的 `O_EXCL` 不可靠；NFSv3+ 通常支持，但跨服务器仍需谨慎，建议用 `link()` 或专用锁服务。

**A4** 进程被 `kill -9` 不会丢：数据已在 page cache，内核会继续回写。机器断电会丢：除非已 `fsync`/`O_SYNC` 或文件系统有日志保证（日志只保证元数据一致性，不保证数据不丢）。
