上一篇你在 shell 里敲命令，看到的是「行为」；从这一篇起，你要写产生这些行为的程序。中间隔着一层很薄的边界：**系统调用（system call）**。所有文件、进程、信号、socket 的能力，最终都收敛成几十个带编号的入口。

这一章不教你任何一个具体子系统，只讲三条贯穿全篇的规则：**怎么进内核、怎么报告失败、怎么不把平台细节写死**。后面 18 章会反复用到它们，这里的每一个错误写法都会在后面变成真实的 bug。


## 2.1.1 一次系统调用穿过什么 {#sec-2.1.1}

这一节回答：我写的 `read(fd, buf, 100)` 怎么会唤醒一个只有操作系统才能碰的通道？这条路上哪几步是 libc 干的、哪几步是内核干的？

::: preview 先抓住一件事
一次读文件是两段路的拼接：libc 把你的调用翻译成「几号调用、参数放哪几个寄存器」，CPU 的陷入指令把特权级从用户态切到内核态，内核按号查表干活，再用一个负数把结果带回来。分界线只有一条：**用户态看到 `-1` 加 `errno`，内核侧看到 `-errno`**。
:::

这一章会反复出现五个词，先用一句白话把它们摆正，后文不再逐个加注：**系统调用**（进程请内核办事的编号与入口，是用户态唯一能合法进内核的路）；**页表**（把虚拟地址一级级翻译成物理地址的那张多层表，内核改它就等于改「这个进程能看见哪些内存」）；**虚拟内存**（每个进程都觉得自己在一段连续、独占地地址空间上运行，实际由页表拼出来）；**中断**（外设或定时器把 CPU 从手头指令上拽走、交给内核处理的事件）；**inode**（一个文件的身份证，存类型、权限、大小和数据在哪些块——文件名只是指向它的一条目录项）。

后面还会撞见五个：**缺页**（地址翻译失败时硬件触发的那次异常，内核由此现场分配页、从文件读入，或者干脆杀掉进程）；**namespace**（把 PID、挂载点、网络栈这些「全局」换成每个容器各自的一套视野）；**cgroup**（内核按组给 CPU、内存、IO 限额与计费的机制）；**epoll**（一次向内核登记一大批 fd、只等谁就绪的接口）；**io_uring**（把 I/O 请求成批排队提交、完成也成批取阅的接口）。


用户程序不能直接调用内核函数。CPU 提供了受控的入口：一条特殊指令把特权级从用户态（ring 3）切到内核态（ring 0），同时把控制权交给内核预先注册的入口地址。x86-64 上这条指令是 `syscall`；32 位时代是 `int 0x80`；ARM64 上是 `svc #0`。

一次 `read(fd, buf, n)` 的完整路径：

<pre class="layout">
        用户态                                  内核态
┌────────────────────────┐
│ main()                 │
│   read(fd, buf, n)     │ ① 调用 glibc 包装函数（不是内核）
│        │               │
│ glibc: read()          │ ② syscall 号 → %rax
│   mov  &#36;0, %eax        │    fd → %rdi, buf → %rsi, n → %rdx
│   syscall  ────────────┼──③ 特权级切换，RIP 跳到 entry_SYSCALL_64
└────────────────────────┘            │
                                      ↓
                           ┌──────────────────────────┐
                           │ entry_SYSCALL_64         │ ④ 保存用户寄存器
                           │  → do_syscall_64         │    按 %rax 查表
                           │  → ksys_read             │
                           │  → vfs_read              │
                           │  → file->f_op->read_iter │
                           └──────────────────────────┘
                                      │
                                      ↓ ⑤ 返回值放回 %rax
                           ┌──────────────────────────┐
                           │ ≥0：字节数               │
                           │ &lt;0：-errno（内核约定）   │
                           └──────────────────────────┘
        用户态                         │
┌────────────────────────┐            │
│ glibc: 检查 %rax        │ ←──────────┘
│  若为负：errno = -rax   │ ⑥ 转成 -1 + errno
│  返回 -1                │
└────────────────────────┘
</pre>

读图时抓住两个「翻译」：内核用**负数返回值**表示错误（`-ENOENT`、`-EINVAL`），glibc 把它翻译成 C 世界的 `-1` 加 `errno`；系统调用号与参数寄存器是 ABI 的一部分，不同架构不同，所以**永远不要自己写 `syscall` 指令**，用 libc 包装或 `syscall(2)`。

内核入口本身在 `arch/x86/entry/entry_64.S`，分派逻辑在 `arch/x86/entry/common.c` 的 `do_syscall_64()`：它从 `sys_call_table` 按编号取函数指针。这张表就是「系统调用号 → 实现」的全部秘密，第 3 篇会展开，这里只需知道**编号是内核 ABI，不是 libc 的私有约定**。上面那张图是 **x86-64 视角**。本套件的测试机是 aarch64，同一条路径换一套名字与寄存器：特权级不叫 ring 3/ring 0 而叫 EL0/EL1，陷入指令是 `svc #0`，**调用号放 `x8`**（不是 `%rax`），参数依次放 `x0`–`x5`，返回值回到 `x0`。这台机器上 `read` 的编号是 63，不是图里的 0：

```c
/* aarch64 上这一次 read 真正发生的事（编号取自 /usr/include/asm-generic/unistd.h） */
register long x8 __asm__("x8") = 63;   /* __NR_read，x86-64 上是 0 */
register long x0 __asm__("x0") = fd;   /* 参数一：fd */
register long x1 __asm__("x1") = (long)buf;
register long x2 __asm__("x2") = n;
__asm__ volatile("svc #0" : "+r"(x0) : "r"(x8), "r"(x1), "r"(x2) : "memory");
/* 返回后 x0 若是 -2，就是 -ENOENT；glibc 把它变成 -1 + errno=2 */
```

内核侧的名字也跟着换。在这台内核（7.0.0-38-generic）上查符号表就能看到入口链：`grep -wE 'el0_svc|invoke_syscall|__arm64_sys_read|ksys_read|vfs_read' /proc/kallsyms` 给出 `el0_svc` → `invoke_syscall` → `__arm64_sys_read` → `ksys_read` → `vfs_read`，五个都在，而 x86 的 `do_syscall_64` 一个都没有（本机 `kptr_restrict` 把地址遮成 0，但符号名照样可读，所以这条命令验证的是「有没有这个函数」，不是地址）。

::: intuition 为什么不让用户程序直接调内核函数
内核函数运行在 ring 0，能改页表、关中断、碰任何物理地址。如果用户程序能任意跳进去，隔离就没了。`syscall` 指令做的事是：**只允许跳到唯一一个入口**，入口再按编号查表，参数必须经过 `copy_from_user` 这类检查。所谓「系统调用」，本质是「一次被审查的、有固定 ABI 的远程调用」。
:::

### `syscall` 与 `int 0x80` 的区别

在 x86-64 内核上两者都能进内核，但语义不同：

| 维度 | `syscall`（x86-64） | `int 0x80`（i386 兼容） |
|:--|:--|:--|
| 系统调用号 | `arch/x86/entry/syscalls/syscall_64.tbl` | `syscall_32.tbl`，编号不同 |
| 参数传递 | `rdi/rsi/rdx/r10/r8/r9` | `ebx/ecx/edx/esi/edi/ebp` |
| 指针宽度 | 64 位 | 截断为 32 位 |
| 返回 | `rax`，负数表示错误 | `eax`，负数表示错误 |
| 性能 | 快（不经过中断控制器） | 慢（要走中断门） |

在 64 位程序里用 `int 0x80` 调 `SYS_write`，用的是 **32 位系统调用号**，参数被截断到 32 位。把栈上的指针传进去，高 32 位丢失，轻则 `EFAULT`，重则写坏地址。这类代码在旧教程里很常见，不要抄。

### vDSO：不进入内核的「系统调用」

`gettimeofday()`、`clock_gettime(CLOCK_REALTIME)`、`time()`、`getcpu()` 这几类调用极其频繁，但只需要读内核维护的几个变量。内核把一小段代码映射到每个进程的地址空间，叫 **vDSO**（virtual dynamic shared object）：

```bash
$ LD_SHOW_AUXV=1 /bin/true | grep -E 'AT_SYSINFO_EHDR|AT_PLATFORM'
AT_SYSINFO_EHDR:      0xe754ab064000
AT_PLATFORM:          aarch64
$ grep -E 'vdso|vvar' /proc/self/maps
f668d907c000-f668d9080000 r--p 00000000 00:00 0   [vvar]
f668d9080000-f668d9082000 r-xp 00000000 00:00 0   [vdso]
```

实测机是 Ubuntu 24.04.5 aarch64（内核 7.0.0-38）。三行读数各说一件事。第一行：vDSO 的入口地址由内核在 exec 时通过辅助向量（auxiliary vector，内核交给进程的一组启动参数）递过来，程序里 `dl_iterate_phdr` 取到的基址与 `AT_SYSINFO_EHDR` 完全相等——这就是 libc 找到那段代码的方式。第二、三行：ARM64 上除了 `[vdso]` 还多一块 `[vvar]`，前者是代码（`r-xp`）、后者只是数据页（`r--p`），`clock_gettime` 读的时间基准落在 `vvar` 里，代码本身不存数据。

两个容易踩的操作细节：**地址每次都不同**（连续三次分别在 `0xe754ab…`、`0xe4c26f…`、`0xf3dfa6…`，因为 `/proc/sys/kernel/randomize_va_space=2`；要复现固定地址得 `setarch -R` 关掉 ASLR），所以任何把这类地址抄进笔记的人都会在下次对不上。`/proc/self/auxv` 是**二进制**的，`head -20` 只会给你乱码，要么用 `LD_SHOW_AUXV=1` 让 glibc 翻译，要么自己 `od`：这台机器上 `0x21 0x…` 那一对就是 `AT_SYSINFO_EHDR`（33），`0x33` 是 `AT_MINSIGSTKSZ`（51），值 4720——这个数是 ARM64 特有的，因为它的信号帧要按 SIMD 状态对齐；x86-64 上没有这一项。

glibc 的 `clock_gettime` 会先看 vDSO 有没有提供实现；有就直接在用户态读完返回，**没有系统调用、没有特权级切换**。这就是为什么「取时间」比「`getpid`」快一个数量级（2.1.2 有测量）。vDSO 是内核与 libc 之间的性能约定，不是通用机制：你不能把自己写的函数塞进去。

### 2.1.1 小结

一条 `read` 走六步：libc 的包装函数把参数按约定放好、陷入指令把特权级从用户态切到内核态、内核入口保存现场并按调用号查表、具体实现干活、结果放回返回值寄存器（负数即错误）、libc 再翻回 `-1` 加 `errno`。记住这条路径有三个用处。判断「是不是系统调用」看有没有一次特权级切换，而不是看 man 手册排第几节。知道为什么不能手写陷入指令、不能抄旧教程里的 `int 0x80`：调用号和寄存器编组是架构的 ABI，抄来的代码换个架构就调错函数。明白 vDSO 是内核为「只读几个变量」这类调用开的用户态通道，它不切换特权级，所以取时间比取 pid 便宜得多（2.1.2 有实测）。如果只记住一件事：**分层的地方在特权级切换那一步，别处的名字都可能骗你。**

::: method 即时自测 · 2.1.1
**Q1（记忆）** 按顺序说出一次 `read` 从用户代码到返回所经过的环节，并指出错误码是在哪一步从 `-errno` 变成 `-1` 加 `errno` 的。

**Q2（辨析）** vDSO 里的 `clock_gettime` 没有进入内核，这和「系统调用是用户程序进入内核的受控入口」矛盾吗？它还算不算系统调用？

**Q3（应用）** 你接手的老代码写着 `syscall(0, buf, 100)` 想读文件，在本机的 ARM64 上拿到的却是别的结果。用两个事实解释这件事，并给出改法与验证手段。

::: sol 答案
**A1** 用户代码 → libc 包装函数 → 调用号与参数放进约定的寄存器 → 陷入指令切到内核态 → 内核入口保存用户寄存器、按调用号查表 → 具体实现（`vfs_read` 一类）干活 → 结果放回返回值寄存器 → libc 检查并翻译。`-errno` 变成 `-1` 加 `errno` 发生在最后一步，在 libc 里，不在内核里。
**A2** 不矛盾，也不算系统调用。vDSO 是内核映射进每个进程地址空间的一小段代码，运行在用户态、读的是内核维护的共享数据，全程没有特权级切换，所以它是内核与 libc 之间的性能约定。「受控入口」说的是真要改状态时的那条唯一通道；man 手册把它列在第 2 节，只表示这个语义仍由内核保证。
**A3** 两个事实：调用号是架构 ABI，同一个数字在不同架构指向不同函数（x86-64 与 ARM64 的具体号码见 2.1.2 的 errata）；参数用哪几个寄存器、指针多宽也由 ABI 规定，抄来的片段常常连这两处一起抄错。改法是别写裸数字，用 `SYS_read` 这类宏，或者干脆调 `read`/`pread` 包装函数。验证手段：`strace -e trace=read` 跑一遍，看它确实落在 `read` 上、参数对不对。
:::
:::

## 2.1.2 系统调用与库函数：谁负责什么 {#sec-2.1.2}

这一节回答：`printf` 和 `write` 都能把字打到屏幕上，按什么标准选？`man` 手册把它排在第 2 节，能不能当成「这就是系统调用」的证据？

::: preview 先抓住一件事
libc 负责方便：缓冲、格式化、把内核的负数换成 `-1` 加 `errno`；内核负责事实：数据真的进了 page cache（页缓存，内核用内存缓存文件内容的那层）、fd 真的分配了。判据不是 man 排第几节，而是有没有一次特权级切换——同在第 2 节里，`getpid` 每次都切，`clock_gettime` 通常不切。
:::

`man` 手册的分节是第一道线索：

| 分节 | 内容 | 例子 |
|:--|:--|:--|
| 2 | 系统调用（内核入口的薄包装） | `man 2 read`、`man 2 fork` |
| 3 | 库函数（libc 实现） | `man 3 printf`、`man 3 malloc` |
| 7 | 概念、协议、约定 | `man 7 signal`、`man 7 tcp` |

但分节不是本质区别。`fork()` 在 man 2，`malloc()` 在 man 3；`getpid()` 名义上是系统调用，实际每次都进内核；`clock_gettime()` 名义上是系统调用，实际常走 vDSO。判断标准只有一条：**这个函数是否直接或间接执行了一条陷入内核的指令，以及它承诺的语义由谁保证**。

几个常被混淆的对：

| 你调用的 | 实际发生什么 | 谁保证语义 |
|:--|:--|:--|
| `printf` | 格式化到用户态缓冲区，满/换行才 `write` | libc（C 标准） |
| `write` | 一次系统调用，数据进 page cache | 内核（POSIX） |
| `malloc` | 在堆上切一块，必要时 `brk`/`mmap` | libc |
| `mmap` | 建立 VMA，建立映射 | 内核 |
| `getpid` | 读 `task_struct->pid`（glibc 2.25 后每次都进内核） | 内核 |
| `clock_gettime` | 通常读 vDSO，不陷入内核 | 内核 + libc 协作 |

`syscall(2)` 是 libc 提供的**通用逃生口**：当某个系统调用还没有包装函数（新内核特性、小众接口），可以用

```c
long syscall(long number, ...);   /* 参数按 ABI 顺序传，最多 6 个 */
```

它仍然会做 `errno` 翻译，但**不做任何类型检查**：参数类型、指针有效性全靠你自己。新代码优先用包装函数；只有 man 手册明确说「glibc 没有提供包装」时才用 `syscall()`。

### 最小测量：vDSO 与真正的系统调用差多少

下面这个程序用三个循环对比 `syscall(SYS_getpid)`、`getpid()` 和 `clock_gettime(CLOCK_MONOTONIC)`。它顺便演示了「基准测试要防止编译器优化掉结果」的写法。

```c
/* syscall_cost.c — 测量一次系统调用的量级 */
#include <stdio.h>
#include <time.h>
#include <unistd.h>
#include <sys/syscall.h>

#define N 1000000

static double now_ns(void)
{
    struct timespec ts;
    if (clock_gettime(CLOCK_MONOTONIC, &ts) == -1) {
        perror("clock_gettime");
        return 0;
    }
    return (double)ts.tv_sec * 1e9 + (double)ts.tv_nsec;
}

int main(void)
{
    volatile long sink = 0;          /* volatile：阻止循环被整体删除 */
    double t0, t1;

    t0 = now_ns();
    for (int i = 0; i < N; i++)
        sink += syscall(SYS_getpid);
    t1 = now_ns();
    printf("syscall(SYS_getpid)      %6.1f ns/次\n", (t1 - t0) / N);

    t0 = now_ns();
    for (int i = 0; i < N; i++)
        sink += getpid();
    t1 = now_ns();
    printf("getpid()                 %6.1f ns/次\n", (t1 - t0) / N);

    t0 = now_ns();
    for (int i = 0; i < N; i++) {
        struct timespec ts;
        if (clock_gettime(CLOCK_MONOTONIC, &ts) == -1)
            return 1;
        sink += ts.tv_nsec;
    }
    t1 = now_ns();
    printf("clock_gettime(MONOTONIC) %6.1f ns/次\n", (t1 - t0) / N);

    printf("sink=%ld\n", sink);       /* 让上面的累加真的发生 */
    return 0;
}
```

编译与运行：

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 syscall_cost.c -o syscall_cost
./syscall_cost
```

在测试 VM（Ubuntu 24.04.5 aarch64、内核 7.0.0-38、GCC 13.3.0、glibc 2.39、4 vCPU）上连跑两次，数量级比绝对值重要：

<div class="terminal" data-title="bash · ubuntu 24.04.5 / aarch64（实测）">
<pre><span class="p">&#36;</span> ./syscall_cost
syscall(SYS_getpid)        134.1 ns/次
getpid()                   133.5 ns/次
clock_gettime(MONOTONIC)    14.6 ns/次
<span class="p">&#36;</span> ./syscall_cost
syscall(SYS_getpid)        139.1 ns/次
getpid()                   139.1 ns/次
clock_gettime(MONOTONIC)    15.4 ns/次
<span class="p">&#36;</span> ./empty_loop          <span class="c"># 同一个循环，只把系统调用换成 sink+=i</span>
空转循环 sink+=i             0.2 ns/次
</pre>
</div>

`syscall()` 与 `getpid()` 几乎一样，说明 `getpid` 没有走 vDSO；`clock_gettime` 快一个数量级，因为它大概率没有进内核。最后一行是必须的对照：同一个循环体空转只要 0.2 ns，所以 134 ns 里约 99.8% 都是「进内核」这件事本身，不是计时器的开销。

「大概率」这个词可以用 `strace` 钉死——同一个程序里三种调用各做 1000 次，`strace -c` 只统计真正进内核的那些：

```text
 99.71    0.008529           4      2000           getpid
  0.11    0.000009           3         3           brk
```

`clock_gettime` **一行都没有**：它一次也没进内核，14.6 ns 全花在用户态读 `vvar` 里的时间基准；而 `getpid` 出现 2000 次（两条路径各 1000），证实 `getpid` 每次都走 `svc`。这台机器上每次陷入约 130–140 ns，比常见的「x86 上 300 ns」说法快一截——所以**别把任何一台机器的陷入成本当常数**：换机器、换内核、开不开缓解特性（spectre/meltdown 的软件缓解会显著改变这条路径）都会动它，引用时连机器一起写。

注意这是**单次调用**的成本，不含上下文切换；真正昂贵的系统调用（`read` 未命中、`fsync`、`wait`）时间花在等设备或等子进程上，不在这里。

::: errata 关于系统调用的三个误解
1. **「`printf` 是系统调用」**——不是。它最终可能调用 `write`，但格式化、缓冲都在用户态。`strace` 里看到的是 `write`，不是 `printf`。
2. **「系统调用一定切换进程」**——不一定。同一进程从用户态陷入内核态再返回，叫**模式切换**（mode switch），不是上下文切换（context switch）。没有调度到别的进程时，开销只是保存/恢复寄存器。
3. **「系统调用号可以写死」**——系统调用号是**架构相关**的 ABI。`SYS_read` 在 x86-64 是 0，在 ARM64 是 63。写死数字的代码换个架构就调错函数。
:::

### 2.1.2 小结

分层的实质是「谁保证什么」：libc 保证接口好用、跨机器一致（格式化、缓冲、把 `-errno` 翻成 `-1` 加 `errno`），内核保证能力与语义（分配 fd、把数据交给 page cache、管进程）。man 手册的分节只是线索，会被两件事打乱：vDSO 让一个「第 2 节的函数」根本不进内核，glibc 的历史缓存又让 `getpid` 的行为换过版本。本节的三个读数正好把这条分界线量出来（见上面的读数块）。三件事顺手记下：`printf` 是攒满缓冲区或遇到换行才 `write`，所以 `fork` 之前不 flush 会重复输出；`malloc` 平时只在用户态切堆，堆不够时才 `brk` 或 `mmap`；`syscall()` 是 libc 留的逃生口，翻 `errno` 但不检查参数类型。如果只记住一件事：**先问「这个语义由谁保证」，再问「它在 man 第几节」。**

## 2.1.3 返回值与 `errno` 的七条规则 {#sec-2.1.3}

这一节回答：为什么我用 `perror` 打出来的错误，是我这行代码从没制造过的？`errno = 0` 这行到底该写在哪里、能不写吗？

::: preview 先抓住一件事
`errno` 是一张便签，不是当前状态：函数失败时把原因编号写在里面，成功时不保证擦掉。所以顺序永远是三步——先看返回值定成败，确认失败才读它，读完立刻存进局部变量再去打印。
:::

C 没有异常。系统调用和大多数 libc 函数用「特殊返回值 + `errno`」报告失败。这套机制简单，但几乎每个初学者都会踩同样的坑。

::: def 定义 2.1.1 · `errno` 与失败约定 {#def-2.1.1}
`errno` 是一个**线程局部**的 `int` 左值（glibc 里展开为 `(*__errno_location())`）。函数失败时把它设为一个 `E*` 常量；成功时**不保证清零**。因此：

- 判断失败看**返回值**，不看 `errno` 是否非零；
- 只有在返回值表明失败后，读 `errno` 才有意义；
- 需要在后续调用之后继续用这个错误码时，先存进局部变量。
:::

七条规则，按重要性排序：

1. **先看返回值，再看 `errno`**。`errno == 0` 不代表成功；`errno != 0` 也不代表这次失败（可能是上一次留下的）。
2. **成功不清 `errno`**。这是 POSIX 明确允许的。要复用 `errno` 做判断，先手动 `errno = 0`。
3. **`errno` 是线程局部的**。两个线程各自失败，互不覆盖。不要把它当进程级状态传递。
4. **保存后再做别的事**。`fprintf`、`strerror`、`free` 都可能改 `errno`；错误处理函数入口第一件事是 `int saved = errno;`。
5. **不是所有函数都设 `errno`**。C 标准库的 `strtol` 用 `errno`，但 `snprintf` 截断不设；`pthread_*` 系列**直接返回错误码**，不碰 `errno`。
6. **`EINTR` 是「被打断」，不是「失败」**。可重试的调用要区分它（2.1.4 给封装）。
7. **`strerror` 不保证线程安全**。多线程用 `strerror_r`，注意它有两个不兼容的版本：GNU 版返回 `char *`，XSI 版返回 `int`。

第 5 条值得单独说：POSIX 线程函数返回 0 表示成功，返回错误码表示失败，**错误码就是返回值本身**。写成 `if (pthread_mutex_lock(&m) == -1)` 永远不成立；正确写法是判断 `rc != 0`，再把 `rc`（不是 `errno`）传给 `strerror`。

### 一个能复现三条规则的实验

下面程序依次演示：成功不清 `errno`、失败时 `errno` 的值、`EINTR` 的判定。它同时给出 `errMsg`/`errExit` 的标准写法。

```c
/* errno_demo.c — errno 的三条规则 */
#include <errno.h>
#include <fcntl.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static void errMsg(const char *msg)
{
    int saved = errno;                    /* 必须先保存 */
    fprintf(stderr, "err: %s: %s\n", msg, strerror(saved));
    errno = saved;                        /* 还原，方便调用者继续判断 */
}

static void errExit(const char *msg)
{
    errMsg(msg);
    exit(EXIT_FAILURE);
}

static volatile sig_atomic_t got_alarm;

static void on_alarm(int sig)
{
    (void)sig;
    got_alarm = 1;
}

int main(void)
{
    int e;

    /* 规则 1+2：失败设置 errno，成功不清除 */
    errno = 0;
    int fd = open("/nonexistent/file", O_RDONLY);
    if (fd != -1)
        errExit("open 不应成功");
    e = errno;
    printf("open 失败: errno=%d (%s)\n", e, strerror(e));

    int ok = open("/etc/hosts", O_RDONLY);
    if (ok == -1)
        errExit("open /etc/hosts");
    printf("成功之后 errno 仍是 %d (%s)\n", errno, strerror(errno));
    close(ok);

    /* 规则 6：EINTR 是打断，不是错误 */
    struct sigaction sa = {0};
    sa.sa_handler = on_alarm;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;                      /* 不设 SA_RESTART */
    if (sigaction(SIGALRM, &sa, NULL) == -1)
        errExit("sigaction");

    int p[2];
    if (pipe(p) == -1)
        errExit("pipe");

    alarm(1);
    char c;
    ssize_t n = read(p[0], &c, 1);        /* 管道无数据，阻塞；1 秒后被 SIGALRM 打断 */
    if (n == -1 && errno == EINTR) {
        printf("read 被 SIGALRM 打断, got_alarm=%d\n", (int)got_alarm);
    } else {
        fprintf(stderr, "预期 EINTR, 实际 n=%zd errno=%d\n", n, errno);
        return EXIT_FAILURE;
    }

    close(p[0]);
    close(p[1]);
    return EXIT_SUCCESS;
}
```

编译运行：

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -g errno_demo.c -o errno_demo
./errno_demo; echo "exit=$?"
```

预期输出：

成功之后 errno 仍是 2 (No such file or directory)

</div>

第二行是关键证据：`open("/etc/hosts")` 成功了，`errno` 仍然是 2。任何「`errno != 0` 就认为出错」的代码在这里都会误判。

### 2.1.3 小结

`errno` 是一个每线程独有的整数变量（线程局部，两个线程各自失败不会互相覆盖）：函数失败时把原因编号写进去，成功时不保证清零，所以「非零就是出错」必然误判——本节读数块里「`open` 成功了但值还是上一个错误」那一行就是证据。用它的正确顺序是三步：返回值定成败，确认失败才读它，读到先 `int saved = errno` 再打印，因为 `fprintf`、`strerror`、`free` 都可能改写它。两类例外要单独记：`pthread_*` 把错误码直接当返回值，压根不写 `errno`；`EINTR` 表示「被信号打断了，可以重来」，不是失败。要把编号变文字就找 `strerror`，但它的线程安全版本有两个互不兼容的签名。如果只记住一件事：**`errno` 只能回答「为什么失败」，永远不能回答「有没有失败」。**

**Q1（记忆）** `errno` 里的值是谁写进去的？谁不保证在成功时把它清掉？什么时候读它才有意义？为什么多线程程序里读 `errno` 不会读到别的线程的错误？

**Q2（辨析）** `snprintf` 把字符串截断了，`errno` 会告诉我们吗？`pthread_mutex_lock` 失败时该看返回值还是看 `errno`？「`errno != 0` 就认为出错」为什么必然误判？

**Q3（应用）** 有人写了 `if (ret == -1) { sleep(1); perror("op"); }`，打出来的错误和真正原因不符。指出问题出在哪一行、`sleep` 在这里算不算嫌疑，并改写。

::: sol 答案
**A1** 失败时由被调用的函数写入；成功时 POSIX 不保证清零，所以它可能还是很久以前那次失败留下的值。只有返回值表明失败之后读它才有意义。每个线程有自己的一份（glibc 里它是一次函数调用返回的地址），所以线程之间不覆盖；但也别把它当进程级状态跨线程传。
**A2** 都不会。`snprintf` 截断靠返回值（返回「本来需要多少字节」）发现，不写 `errno`；`pthread_mutex_lock` 成功返回 0、失败返回错误码本身，判断写 `rc != 0`，把 `rc` 传给 `strerror`，读 `errno` 只会拿到无关的残留值。误判的原因就是第一条：成功不清零，非零不代表这次失败。
**A3** 嫌疑就在 `sleep`。打印用的是「此刻的 `errno`」，而 `sleep` 内部会调别的系统调用，被信号提前唤醒时它会改写 `errno`；任何夹在失败与打印之间的函数都有这个风险。改法：失败后立刻 `int saved = errno;`，再 `sleep`，最后 `fprintf(stderr, "op: %s\n", strerror(saved));` 用存下来的值。

## 2.1.4 错误处理的工程封装 {#sec-2.1.4}

这一节回答：`perror("open"); exit(1);` 这种写法到底哪里不够？一个错误应该由谁来打印、由谁来终止进程？

::: preview 先抓住一件事
三层做法按「这个错误谁能处理」来分：能恢复的返回 `-1`、把 `errno` 原样留给上层；要记录但还能继续的用 `errMsg`；只有启动阶段那种「活着也是错」才用 `errExit`。判据只有一条——把 `exit` 写进库函数，就是替所有调用者做决定。
:::

教科书示例常写 `if (fd == -1) { perror("open"); exit(1); }`。真实程序不能处处 `exit`：库函数要返回错误，守护进程要记录并继续，服务端要回一个 500 而不是退出。实践中有三层：

| 层 | 行为 | 适用 |
|:--|:--|:--|
| `errMsg` | 打印并返回，`errno` 保持不变 | 库、可恢复错误 |
| `errExit` | 打印并 `exit(EXIT_FAILURE)` | 启动阶段、不可恢复 |
| `errno` 透传 | 返回 `-1`，让调用者决定 | 所有中间层 |

一个够用的最小实现（`err.c`，每个示例都链接它）：

```c
/* err.c — 变参错误处理：默认取 errno，也可显式传错误号 */
#include <errno.h>
#include <stdarg.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void vErr(int errnum, const char *fmt, va_list ap)
{
    char buf[1024];
    int saved = errno;                    /* 保留调用者的 errno */

    vsnprintf(buf, sizeof buf, fmt, ap);
    fprintf(stderr, "%s: %s\n", buf, strerror(errnum));
    errno = saved;                        /* 返回时还原 */
}

void errMsg(const char *fmt, ...)
{
    va_list ap;
    int saved = errno;

    va_start(ap, fmt);
    vErr(saved, fmt, ap);
    va_end(ap);
}

void errExit(const char *fmt, ...)
{
    va_list ap;
    int saved = errno;

    va_start(ap, fmt);
    vErr(saved, fmt, ap);
    va_end(ap);
    exit(EXIT_FAILURE);
}

void errExitEN(int errnum, const char *fmt, ...)
{
    va_list ap;

    va_start(ap, fmt);
    vErr(errnum, fmt, ap);
    va_end(ap);
    exit(EXIT_FAILURE);
}
```

三个设计点：

1. **`vErr` 先保存 `errno`**，函数返回前还原。这样调用者 `errMsg(...); return -1;` 时，`errno` 还是原始错误。
2. **`vsnprintf` 而不是 `snprintf`**：变参函数必须用 `va_list` 版本。缓冲区固定 1024，超长截断——错误信息不需要无限长。
3. **`errExitEN` 接受显式错误号**：用于 `pthread_*` 这类「返回错误码、不设 `errno`」的接口。

`perror`、`strerror`、`errExit` 是三件不同的东西，别当成一个。`perror("open")` 往标准错误打一行「open: 原因」再返回，原因取自**此刻**的 `errno`：它不能带格式化参数、不能换输出目标，也没法只把那段文字给你。`strerror(e)` 相反，它返回描述文字让你自己排版，但那段文字可能躺在静态缓冲区里，下一次调用就被覆盖，多线程里更不安全——要线程安全的版本得用 `strerror_r`。

`errExit` 是 Kerrisk 在《The Linux Programming Interface》里的封装，把两边的长处合起来：消息可以像 `printf` 一样带格式化参数，打到标准错误之后再 `exit(EXIT_FAILURE)`；`errMsg` 就是它去掉退出的那一半。名字里带 `EN` 的版本表示「错误号我显式给你」，专门伺候 `pthread_*` 这一类不写 `errno` 的接口。

一次真实的选择是这样的。`read_config()` 里 `open` 失败，做法取决于它此刻在谁的身体里。作为库函数被别人的代码调用：`errMsg("read_config: %s", path)`，然后 `return -1`，`errno` 原样留下。作为 `main()` 的第一步：`errExit("read_config")`，因为没有配置，后面每一步都会错。作为已经 `accept` 了连接的服务端里的一次失败：既不退出也不往标准错误上堆日志，而是把错误码换成一条响应发给客户端，日志记一行，关掉这条连接继续服务（映射表在 2.1.10）。三种写法共用同一个前置动作：先把 `errno` 存进局部变量。

这一层新手最常犯的三个错：在库函数里 `exit`，一个可有可无的配置文件打不开，就带走了整个进程；对 `pthread_mutex_lock` 的返回值用 `errMsg`，于是打印出来的是很久以前某次别的失败留下的错误；以及在错误处理路径里再分配内存或打开日志文件——内存紧张时 `malloc` 正好失败，你打出来的就成了「Cannot allocate memory」，真原因永远丢掉。标准错误是那条最不容易失败的路，所以本书的 `errMsg` 只用它。

::: method 选择错误处理方式的顺序
1. 这个错误**调用者能恢复**吗（`EAGAIN`、`EINTR`、`ENOENT`）？能 → 返回 `-1` 并保留 `errno`。
2. 不能恢复，但**进程还有别的事要做**（一个连接坏了）？→ 记录日志，关闭该连接，继续。
3. 不能恢复且**继续运行会出错**（配置解析失败、特权丢失）？→ `errExit`。
4. 在**信号处理器**里？→ 只能用 `write` + 预格式化字符串，**不能**用 `fprintf`/`strerror`（见 [2.10](ch10.md)）。
:::

### 2.1.4 小结

错误处理分三层，选哪一层只问一件事：这个错误谁有能力处理。能恢复的返回 `-1`、把 `errno` 原样留给上层；要记录但还能继续的用 `errMsg`；只有启动阶段那种「活着也是错」才用 `errExit`。三个封装函数能站稳，靠的是同一个约定——入口 `int saved = errno`、出口还原，于是打印路径上再调 `vsnprintf`、`fprintf` 都不会把原始错误改掉；`errExitEN` 专门服务 `pthread_*` 这类「错误码就是返回值、不写 `errno`」的接口。`perror` 和 `strerror` 不是替代品：前者固定往标准错误打一行、只认此刻的 `errno`，后者只给你一段文字自己排版。如果只记住一件事：**打印错误之前先保存 `errno`，打印完还原它。**

::: method 即时自测 · 2.1.4
**Q1（记忆）** `perror`、`strerror`、`errExit` 各自把结果放在哪里？哪一个能带格式化参数、哪一个会结束进程、哪一个的返回值可能被下次调用覆盖？

**Q2（辨析）** `errMsg("pthread_mutex_lock")` 打出来的是「No such file or directory」，跟锁毫无关系。解释原因，并给出正确的调用形式。

**Q3（应用）** 把 `if (fd == -1) { perror("open"); exit(1); }` 改成本节三层里的两种写法：一段在库函数里，一段在 `main()` 的第一步。说明改完之后，`errno` 在返回给调用者时分别是什么状态。

::: sol 答案
**A1** `perror` 直接写标准错误，格式固定为「你的字符串: 原因」，原因取自当前 `errno`，不能带格式化参数，也不退出。`strerror` 不输出任何东西，返回一段描述文字供你排版；它可能指向静态缓冲区，下次调用就被覆盖，线程安全版是 `strerror_r`。`errExit` 能带格式化参数，打完之后 `exit(EXIT_FAILURE)`，是三者里唯一会结束进程的那个（`errMsg` 是它去掉退出的那一半）。
**A2** 因为 `pthread_*` 系列把错误码当返回值，从来不写 `errno`；`errMsg` 去读 `errno`，读到的是本线程上一次真正的失败留下的残留值。正确形式是把返回值显式交出去：`int rc = pthread_mutex_lock(&m); if (rc != 0) errExitEN(rc, "pthread_mutex_lock");`。
**A3** 库函数版：`if (fd == -1) { errMsg("open %s", path); return -1; }`——本书的 `errMsg` 已在内部保存并还原 `errno`，所以返回时调用者读到的仍是 `open` 的原始原因。启动版：`if (fd == -1) errExit("open %s", path);`——打印后进程结束，`errno` 里是什么已经没人再读。两种写法的分界不是「谁更正式」，而是调用者手里还有没有选择。
:::
:::

## 2.1.5 特性测试宏：为什么 `-D_GNU_SOURCE` 是必需的 {#sec-2.1.5}

这一节回答：man 手册明明说 `accept4` 声明在 `<sys/socket.h>` 里，我照抄了 `#include`，编译器为什么还说「未声明」？`-D_GNU_SOURCE` 改变的是库，还是头文件里的 `#ifdef`？

::: preview 先抓住一件事
特性测试宏不安装、不链接任何东西，它只是头文件里一大片 `#ifdef` 的总开关，决定「哪些声明对你可见」。于是三件事可以同时成立：函数在库里、链接找得到、编译时看不见。看不见声明，编译器只能自己猜参数。
:::

同一个头文件，在不同宏定义下暴露不同的声明。这不是发行版的怪癖，而是 POSIX 的设计：**头文件必须能同时服务「严格标准模式」和「实现扩展模式」**。

::: def 定义 2.1.2 · 特性测试宏（feature test macro） {#def-2.1.2}
特性测试宏是在**包含任何系统头文件之前**定义的预处理宏，用来告诉 libc「我要求哪一版标准、允许哪些扩展」。它控制的是**声明是否可见**，不改变运行时行为。定义晚了（在 `#include <stdio.h>` 之后）等于没定义。
:::

常用组合：

| 宏 | 含义 | 典型用途 |
|:--|:--|:--|
| `_POSIX_C_SOURCE=200809L` | 只要 POSIX.1-2008 | 可移植的库 |
| `_XOPEN_SOURCE=700` | POSIX + XSI，`700` 对应 SUSv4 | 需要 `openpty` 等 XSI 接口 |
| `_DEFAULT_SOURCE` | glibc 默认扩展（`MSG_NOSIGNAL`、`strdup` 等） | 不写宏时的默认状态 |
| `_GNU_SOURCE` | 打开**全部**：POSIX + BSD + GNU | Linux 上的系统程序 |

关键细节：**一旦你显式定义了 `_POSIX_C_SOURCE`，glibc 就不再默认定义 `_DEFAULT_SOURCE`**。于是 `accept4`、`pipe2`、`dup3`、`signalfd`、`epoll_create1`、`MSG_NOSIGNAL` 会失去声明。C17 下未声明函数是警告（`-Werror` 变错误），链接时可能碰巧成功——这是最坏的组合：**能跑，但行为未定义**。

复现这个坑：

```bash
# 只声明 POSIX.1-2008，accept4 不在其中
cc -std=c17 -D_POSIX_C_SOURCE=200809L -Wall -Wextra -Werror -fsyntax-only accept4_demo.c
# 报错：implicit declaration of function 'accept4'; did you mean 'accept'?

# 换成 _GNU_SOURCE
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -fsyntax-only accept4_demo.c
# 通过
```

本书统一在**编译命令**里用 `-D_GNU_SOURCE`，源码不再重复 `#define`——命令行已定义时再定义一次，`-Werror` 下会报 `macro redefined`。原因不是「Linux 专用」，而是本章之后的接口有大量 Linux 扩展（`epoll`、`inotify`、`signalfd`、`accept4`、`pipe2`）；要跨到 BSD/macOS，应把扩展隔离在平台层，核心逻辑只用 `_POSIX_C_SOURCE=200809L`。

::: errata 特性测试宏的四个坑
1. **「在 `.c` 文件里 `#define _GNU_SOURCE` 就行」**——必须在这之前没有任何 `#include`。最稳妥是编译命令 `-D_GNU_SOURCE`，而不是源文件里写。
2. **「定义了 `_GNU_SOURCE` 还能再定义 `_POSIX_C_SOURCE` 来限制」**——不能。`_GNU_SOURCE` 会强制打开所有扩展，后定义的 `_POSIX_C_SOURCE` 不会收回。
3. **「头文件里定义宏」**——头文件被包含时可能已经有系统头文件进去了，顺序不可控。特性测试宏只能出现在**翻译单元的最前面**或编译命令行。
4. **「`-std=c17` 会关掉 POSIX 声明」**——`-std=c17` 把 `__STRICT_ANSI__` 打开，glibc 会因此隐藏一部分默认扩展；这正是「同一份代码 `-std=gnu17` 能编、`-std=c17` 不能」的常见原因。本书用 `-std=c17` 加 `-D_GNU_SOURCE`，两者同时显式写出。
:::

### 2.1.5 小结

特性测试宏控制的是**可见性**：glibc 的头文件里到处是 `#ifdef`，宏决定哪些声明进入你的翻译单元，库本身一个字节都没变。生效位置只有一个——第一个系统头之前，因为 `<features.h>` 只在第一次被包含时算完那些内部开关，来晚了不再重算。两个后果要记住。显式定义 `_POSIX_C_SOURCE` 之后，glibc 不再默认打开 `_DEFAULT_SOURCE`，`accept4`、`pipe2`、`strdup` 因此失去声明，可符号还在共享库里，于是凑成最坏的组合：编译给警告、链接通过、运行未定义。`_GNU_SOURCE` 是全开，后面再写 `_POSIX_C_SOURCE` 收不回来。本书把宏放在命令行、和 `-std=c17` 一起显式写出，就是让「依赖了哪些扩展」这件事写在构建命令里。如果只记住一件事：**编译不过不等于函数不存在，先问「谁把声明挡住了」。**

::: method 即时自测 · 2.1.5
**Q1（记忆）** `_POSIX_C_SOURCE`、`_XOPEN_SOURCE`、`_DEFAULT_SOURCE`、`_GNU_SOURCE` 分别打开什么？为什么本书把宏写在编译命令里，而不是源文件第一行？

**Q2（辨析）** 「函数在库里、链接找得到、编译时看不见」能同时成立，说明问题出在哪一层？同一段代码 `-std=gnu17` 能编、`-std=c17` 不能编，差别来自编译器还是 libc？

**Q3（应用）** 你按可移植的要求把宏换成 `-D_POSIX_C_SOURCE=200809L`，结果 `strdup` 报未声明。给出两种修法，并说明哪一种更利于日后迁到别的系统、为什么。

::: sol 答案
**A1** `_POSIX_C_SOURCE=200809L` 只要 POSIX.1-2008 的接口；`_XOPEN_SOURCE=700` 在它之上再加 XSI 那一批（如 `openpty`）；`_DEFAULT_SOURCE` 是不写宏时 glibc 默认给的扩展集（`strdup`、`strcasecmp`、`MSG_NOSIGNAL` 这类 BSD/SVID 接口）；`_GNU_SOURCE` 全部打开再加 GNU 独有接口。放命令行是因为宏必须在任何系统头之前生效，源文件里写会被一次意外的前置 `#include` 废掉；命令行已定义时再 `#define` 一次，`-Werror` 下还会报宏重定义。
**A2** 说明问题在「声明可见性」这一层，不在链接层：C 语言对未声明的函数按隐式声明处理，编译器自己猜返回类型和参数表，链接器只按符号名在共享库里找。`-std=c17` 打开 `__STRICT_ANSI__`，被隐藏的那部分开关写在 glibc 的头文件里，所以差别最终体现在 libc 的 `#ifdef` 上——编译器只是那个开关的来源，不是它自己删了声明。
**A3** 快修法：改回 `-D_GNU_SOURCE`，或者把默认集一起请回来（`-D_POSIX_C_SOURCE=200809L -D_DEFAULT_SOURCE`），`strdup` 的声明就重新可见。更利于移植的修法：把用到 `strdup`、`accept4` 这类扩展的代码收进一个平台层文件，只在那一层定义 `_GNU_SOURCE`，核心逻辑坚持只用 POSIX 的接口。迁到 BSD 或 macOS 时只需要重写平台层，而不是在每个 `.c` 里找哪些调用是扩展。
:::
:::

## 2.1.6 运行时才知道的限制：`sysconf` 与 `pathconf` {#sec-2.1.6}

这一节回答：`<limits.h>` 里明明印着 `OPEN_MAX`，手册为什么还让我用 `sysconf` 去查？查回来一个 `-1`，是「这项限制没有上限」还是「我查错了」？

::: preview 先抓住一件事
编译期的常量只能保证「这台机器、这次编译时不超出」，而真实限制可能来自内核配置、挂载的文件系统或本进程的资源限制。判据只有一条：返回 `-1` 时必须看 `errno`——为零表示这项限制不确定，非零才是查询失败；所以调用前先 `errno = 0`。
:::

`OPEN_MAX`、`NAME_MAX`、`PAGESIZE` 这些常量，有些在 `<limits.h>` 里有宏，有些没有。原因很实际：**限制可能随内核配置、挂载的文件系统、进程的 `RLIMIT_*` 变化**，编译期写死就会错。

三个查询接口：

```c
long sysconf(int name);                       /* 系统级：页大小、CPU 数、fd 上限 */
long pathconf(const char *path, int name);    /* 路径所在文件系统：NAME_MAX、PATH_MAX */
long fpathconf(int fd, int name);             /* 同上，用已打开的 fd */
```

::: def 定义 2.1.3 · `sysconf`/`pathconf` 的返回值语义 {#def-2.1.3}
三者都返回 `long`，且都有**三种**结果：

- `>= 0`：限制值；
- `-1` 且 `errno == 0`：该限制**不确定**（indeterminate），没有固定上限；
- `-1` 且 `errno != 0`：查询本身失败（`EINVAL` 表示名字不合法）。

因为 `-1` 有二义性，**调用前必须 `errno = 0`**，返回后再查 `errno`。这是本章最容易写错的一个 API。
:::

常用名字：

| 名字 | 含义 | 备注 |
|:--|:--|:--|
| `_SC_PAGESIZE` | 内存页大小 | 通常 4096，ARM64 可为 16384 |
| `_SC_OPEN_MAX` | glibc 返回 `RLIMIT_NOFILE` 软限制 | 不是系统 fd 总数上限 |
| `_SC_CLK_TCK` | `times()` 的时钟频率 | `/proc/PID/stat` 的时间单位 |
| `_SC_NPROCESSORS_ONLN` | 在线 CPU 数 | Linux 扩展（`_GNU_SOURCE`） |
| `_SC_ARG_MAX` | `exec` 参数+环境总长 | 实际还受栈大小限制 |
| `_PC_NAME_MAX` | 单个文件名最大长度 | 随文件系统变，ext4 是 255 |
| `_PC_PATH_MAX` | 路径最大长度 | Linux 上通常 4096，但**不是保证** |

`pathconf` 的 `_PC_PATH_MAX` 有个陷阱：它返回的是「这个文件系统上路径的最大长度」，而 Linux 的路径解析本身没有硬上限（`openat2` 也只看总长）。真正可靠的结论是：**不要分配 `PATH_MAX` 字节的栈缓冲区然后假设够用**；用 `getcwd(NULL, 0)` 或 `realpath(path, NULL)` 让 libc 分配，遇 `ERANGE` 再扩容。

### 一次性把环境查清楚

```c
/* limits.c — 查询运行时限制；注意 errno 的用法 */
#include <errno.h>
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/utsname.h>

/* -1 有两种含义：调用前必须清零 errno，返回后才能区分 */
static void show(const char *label, long v)
{
    if (v == -1 && errno != 0)
        printf("%-24s 查询失败: %s\n", label, strerror(errno));
    else if (v == -1)
        printf("%-24s 不确定（无固定上限）\n", label);
    else
        printf("%-24s %ld\n", label, v);
}

int main(void)
{
    struct utsname u;

    if (uname(&u) == -1) {
        perror("uname");
        return EXIT_FAILURE;
    }
    printf("%s %s %s\n\n", u.sysname, u.release, u.machine);

    errno = 0; show("_SC_PAGESIZE",         sysconf(_SC_PAGESIZE));
    errno = 0; show("_SC_OPEN_MAX",         sysconf(_SC_OPEN_MAX));
    errno = 0; show("_SC_CLK_TCK",          sysconf(_SC_CLK_TCK));
    errno = 0; show("_SC_ARG_MAX",          sysconf(_SC_ARG_MAX));
    errno = 0; show("_SC_NPROCESSORS_ONLN", sysconf(_SC_NPROCESSORS_ONLN));

    putchar('\n');
    errno = 0; show("_PC_NAME_MAX(/tmp)", pathconf("/tmp", _PC_NAME_MAX));
    errno = 0; show("_PC_PATH_MAX(/tmp)", pathconf("/tmp", _PC_PATH_MAX));
    errno = 0; show("_PC_NAME_MAX(/)",    pathconf("/", _PC_NAME_MAX));
    return EXIT_SUCCESS;
}
```

编译与运行：

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 limits.c -o limits
./limits
```

这组数字里最值得记的是 `_SC_OPEN_MAX` 与 `ulimit -n` **相等**（都是 1024），而 `/proc/sys/fs/nr_open` 是 1048576。上一段那句「`_SC_OPEN_MAX` 是本进程软限制的投影」不是推论，是这个机器上当场对出来的等式。同一台机器换一个会话（比如从 systemd 拉起的图形终端、或 `ulimit -n 4096` 之后的 shell），这个数就会跟着变——所以它既不是「系统上限」，也不是常数。

`_SC_OPEN_MAX` 的语义随实现而变。Linux/glibc 的实现是返回本进程的 `RLIMIT_NOFILE` **软限制**（Kerrisk 第 11 章，p177 明确把 `_SC_OPEN_MAX` 与 `RLIMIT_NOFILE` 对应），所以它通常与 `ulimit -n` 一致，而不是与 `/proc/sys/fs/nr_open` 一致。把它当成「系统能打开的文件总数」会得出错误结论：系统总量还受 `nr_open`/`file-max` 与其他进程占用约束。要拿本进程的软/硬限制，用 `getrlimit(RLIMIT_NOFILE, &rl)` 或读 `/proc/self/limits`。

::: ex 例 2.1.3 · 先猜这台机器「最多能开多少文件」报哪个数 {#ex-2.1.3}
`sysconf(_SC_OPEN_MAX)` 回答的是「最多能打开多少个文件」。先猜：这台 Ubuntu 24.04.5 aarch64 上它打印 1024 还是 1048576？再猜：这个数、`ulimit -n`、`/proc/sys/fs/nr_open` 三个读数里，谁和谁相等？

::: sol 解答
打印 1024。本节上面的实测读数块里，`_SC_OPEN_MAX` 与 `ulimit -n` 是同一个数（1024），`nr_open` 单独是 1048576，对不上。原因是 glibc 把这个查询实现成本进程 `RLIMIT_NOFILE` 软限制的投影——`ulimit -n` 显示的也是这同一个软限制，所以两者相等是机制的必然，不是巧合。

答 1048576 的人多半是把天花板当成了额度：那是内核给单个进程划的 fd 号上限，2.1.12 那张三层表里 `getrlimit` 的硬限制也是这个数，属于另外一层。更要紧的是这一格既不是「系统能开多少文件」也不是常数——正文里已经写了，换一个会话、或在改过 `ulimit -n` 的 shell 里，它立刻跟着变。程序要按软限制规划，撞上的才是硬限制。
:::
:::

### 2.1.6 小结

`sysconf` 查系统与本进程这一级，`pathconf`/`fpathconf` 查某个文件系统那一级，用途是同一个：运行时问这台机器，替掉 `<limits.h>` 里按某台机器写死的常量。三处要小心。`-1` 有二义性：`errno` 为 0 表示「这项限制不确定、没有固定上限」，非 0 才是查询失败，所以调用前必须清零 `errno`。`_SC_OPEN_MAX` 在 glibc 上只是本进程 `RLIMIT_NOFILE` 软限制的投影，不是系统能打开的文件总数。`_PC_PATH_MAX` 说的是这个文件系统上的路径上限，不等于你分配一块那么大的缓冲区就够用——长路径该让 libc 按需分配（`getcwd`、`realpath` 传 `NULL`），遇 `ERANGE` 再扩。页大小这类值换架构会变，本节的读数块只对这台机器成立。如果只记住一件事：**抄常量是把别的机器的限制带进你的程序，现查才是把问题交还给这台机器。**

## 2.1.7 `uname`、`sysinfo`、`/proc` 与 `sysfs`：拿证据的地方 {#sec-2.1.7}

这一节回答：想知道内核版本、这台机器还能给出多少内存、某个进程正开着哪些文件——是该写 C 代码调 `sysinfo`，还是该读 `/proc`？容器里读到的数字算谁的？

::: preview 先抓住一件事
四个接口回答四个问题：`uname` 给内核启动时定死的那几个字符串，`sysinfo` 给一次拿全的系统总量，`/proc` 给按进程与内核对象组织的文本视图，`/sys` 给设备和驱动暴露的属性。写程序要数值就用前两个加 `sysconf`，排障看具体对象就读 `/proc`。
:::

**`uname(2)`**：填 `struct utsname`，六个字段 `sysname`/`nodename`/`release`/`version`/`machine`/`domainname`。返回 0 或 -1（`EFAULT`）。它读的是内核启动时固定的字符串，不反映运行时变化。

**`sysinfo(2)`**：填 `struct sysinfo`，给 uptime、负载、内存总量/可用量、进程数。两个坑：

- 内存字段单位是 `mem_unit` 字节，不是字节；老内核上 `mem_unit` 可能大于 1；
- `freeram` 不含可回收的 page cache，用 `MemAvailable` 更接近「应用还能拿多少」。

```c
/* sysinfo_demo.c — 内存字段必须乘以 mem_unit */
#include <stdio.h>
#include <sys/sysinfo.h>

int main(void)
{
    struct sysinfo si;
    if (sysinfo(&si) == -1) { perror("sysinfo"); return 1; }

    unsigned long unit = si.mem_unit ? si.mem_unit : 1;
    printf("uptime %ld s, procs %u\n", si.uptime, si.procs);
    printf("totalram %lu MiB, freeram %lu MiB\n",
           si.totalram * unit >> 20, si.freeram * unit >> 20);
    return 0;
}
```

`/proc` 是**进程和内核状态的文本投影**，`sysfs`（挂在 `/sys`）是**设备与驱动的对象模型**。两者都不是普通磁盘文件，读写由内核的回调函数即时生成。

| 路径 | 内容 | 典型用途 |
|:--|:--|:--|
| `/proc/self/status` | 进程状态、UID、内存、线程数 | 排障第一站 |
| `/proc/self/maps` | 虚拟内存区域 | 看 `[vdso]`、共享库、堆 |
| `/proc/self/fd/` | fd 表投影 | 查泄漏、看 `(deleted)` |
| `/proc/meminfo` | 内存明细 | `MemAvailable`、`Cached` |
| `/proc/sys/vm/*` | 可调参数 | `dirty_ratio`、`swappiness` |
| `/sys/class/net/eth0/` | 网卡属性 | `mtu`、`operstate`、统计计数 |
| `/sys/fs/cgroup/` | cgroup v2 层级 | 容器资源限制 |

`/proc` 的数字列宽会变，**不要用 `awk '{print $2}'` 依赖列位置**；用 `grep '^VmRSS:'` 再取第二个字段，或者直接读结构化接口（`/proc/PID/stat` 的字段顺序是稳定的，但单位要换算）。

::: note `/proc` 是可写的，但不是文件
向 `/proc/sys/vm/dirty_ratio` 写 `echo 20 > ...` 会调用内核的 `sysctl` 处理函数，不是写磁盘。同理，读 `/proc/self/mem` 能读写自己的地址空间（调试器就是这么做的），但偏移必须是有效映射，否则 `EIO`。把 `/proc` 当普通文件 `mmap` 或 `seek` 到任意位置，会得到看似莫名其妙的结果。
:::

`sysinfo` 和 `/proc/meminfo` 的差别不只在单位。前者一次调用给全、字段少、程序里好算，但每个内存字段都得乘 `mem_unit`；后者字段细、单位直接印在文本里、人能读，程序解析就得按行首匹配。同一件事在两边名字也不同：`sysinfo` 里的 `freeram` 对应不到 `/proc/meminfo` 里那个更接近「应用还能拿到多少」的 `MemAvailable`——后者把可回收的缓存算进去了。想知道「还能不能多申请一块内存」，看后者；想一次抓一组总量做阈值判断，用前者。

容器里最容易看错的是 `uname`。镜像换成另一个发行版、装另一套用户态库，`uname` 的输出一个字都不会变，因为容器共享宿主内核，它报的是宿主内核的版本。判断「这个环境到底是什么」要同时看两处：内核那边看 `uname` 或 `/proc/version` 里的 release，用户态那边看发行版自己留下的记录文件。两边不一致在容器里是常态，不是故障。

读 `/proc` 的坑上面说了一个（按行首匹配，不按列号取），还有两个要单独讲。第一个是单位：`/proc/self/status` 把单位印在同一行末尾，`/proc/PID/stat` 里的时间用的是「时钟节拍」（内核按固定间隔累加的计数），要除以 `sysconf(_SC_CLK_TCK)` 才是秒——这正是上一节强调「运行时查接口」的一个理由。

第二个坑是时点：这些内容在你读的那一刻现算，两次读取之间进程早就变了，脚本里比对两个文件的状态时不要假设它们同步。也别拿 `ls -l` 看到的长度去预分配缓冲区，那是元数据里的数字，和你能读出的字节数无关；老实循环 `read`，直到返回 0。加上前面说的「按行首匹配而不是按列号取」，这三条合起来就是读 `/proc` 的安全姿势。

### 2.1.7 小结

这四类接口各管一层：`uname` 是内核启动时就定死的字符串，容器里它报宿主；`sysinfo` 是一次拿全的系统总量，每个内存字段都要乘 `mem_unit`；`/proc` 是按进程与内核对象组织的文本视图，排障时是第一站；`/sys` 是设备与驱动的属性模型。选哪个取决于你要什么：程序里做判断用 `sysinfo` 和 `sysconf`，查「这个进程现在什么样」读 `/proc`，查设备与容器的边界读 `/sys`。两个通用陷阱是单位和字段位置：`mem_unit` 要乘、时间要除 `_SC_CLK_TCK`，取字段按行首匹配而不是按列号。至于「还能用多少内存」，答案是 `MemAvailable`，不是 `freeram`。如果只记住一件事：**先问这个数字是谁、在什么时刻算出来的，再决定读哪个接口。**

## 2.1.8 可移植性检查清单 {#sec-2.1.8}

这一节回答：十条清单里，哪几条违反了之后编译器一声不响、只在换机器时才炸？`getopt` 和 `getopt_long` 的差别为什么正好是可移植性的标本？

::: preview 先抓住一件事
清单按「改起来最便宜」排序，但真正危险的是几条静音的：`char` 有没有符号、`long` 多宽、系统调用号与错误码写成数字、拍脑袋按 `PATH_MAX` 分配的缓冲区。判据只有一条：同一份代码用 `_GNU_SOURCE` 和 `_POSIX_C_SOURCE=200809L` 各编一遍，让扩展依赖自己现身。
:::

「我的机器上能跑」不是可移植性。下面这份清单按「改起来最便宜」排序：

::: method 提交前的可移植性检查
1. **特性测试宏在命令行**：`-D_GNU_SOURCE` 或 `-D_POSIX_C_SOURCE=200809L`，不在源文件中间 `#define`。
2. **不用裸数字**：系统调用号用 `SYS_*`，信号用 `SIG*`，权限用 `S_IRUSR` 这类宏，`errno` 用 `E*`。
3. **不用 `int` 存 `size_t`/`off_t`/`pid_t`**：用 `ssize_t`、`off_t`、`pid_t`；打印用 `%zd`、`%jd`（配 `intmax_t`）或 `PRIdMAX`。
4. **限制运行时查**：`sysconf`/`pathconf`/`getrlimit`，不抄 `OPEN_MAX`、`NAME_MAX`。
5. **对齐与字节序**：跨网络/跨文件格式用 `htonl`/`ntohl`；结构体别直接 `write` 到文件。
6. **路径拼接**：用 `snprintf` + 检查返回值，不 `strcat`；不假设 `/tmp` 可写、`/bin/sh` 存在。
7. **错误码按名字判断**：`errno == EAGAIN`，不写 `errno == 11`。
8. **`long` 不等于指针**：Windows LLP64 下 `long` 是 32 位；用 `intptr_t`/`uintptr_t`。
9. **`char` 的符号性**：ARM 上 `char` 默认无符号，`char c = getchar(); if (c == EOF)` 会永远不成立。用 `int` 接 `getchar`。
10. **编译两次**：`-std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror` 与 `-std=c17 -D_POSIX_C_SOURCE=200809L` 各编一次，看扩展依赖在哪。
:::

第 9 条值得展开：`EOF` 是 `-1`，`getchar()` 返回 `int`。把返回值存进 `char`，在无符号 `char` 的平台上 `0xFF` 变成 `255`，与 `-1` 比较永远不等，循环不终止。这类 bug 在 x86 上测不出来，在 ARM 上必现。

### 一个具体的扩展边界：`getopt` 与 `getopt_long`

`getopt` 是 POSIX 接口，声明在 `<unistd.h>`；`--long` 形式的选项来自 GNU 扩展 `getopt_long`（`<getopt.h>`）。本书的示例大多只有一两个参数，手写 `strcmp` 够用；参数一多，标准库版本至少统一处理了捆绑短选项（`-abc`）、`-n3`/`-n 3`、`--` 终止符和错误消息。

```c
int ch;
while ((ch = getopt(argc, argv, ":n:o:h")) != -1) {
    switch (ch) {
    case 'n': count = atoi(optarg); break;
    case 'o': out = optarg; break;
    case 'h': usage(argv[0]); return 0;
    case ':': fprintf(stderr, "-%c needs an argument\n", optopt); return 2;
    default:  fprintf(stderr, "unknown option -%c\n", optopt); return 2;
    }
}
argc -= optind;
argv += optind;                  /* 剩下的才是操作数 */
```

`optstring` 开头的 `:` 关闭 `getopt` 自己的报错，并让缺参数返回 `:` 而不是 `?`；`optopt` 保存出错的选项字符。GNU 版默认重排 `argv`，把选项集中到前面；要保持「遇到第一个操作数就停」，在 `optstring` 开头加 `+`（或设 `POSIXLY_CORRECT`）。长选项用 `getopt_long` 的 `struct option`，`flag` 为 `NULL` 时返回 `val`。

### 2.1.8 小结

可移植性不是「多试几台机器」，而是把「这台机器的事实」换成「接口保证的事实」：用宏划定依赖边界，用 `SYS_*`、`E*`、`S_IRUSR` 替掉裸数字，用 `sysconf`、`getrlimit` 替掉抄来的常量，用 `intptr_t` 替掉「`long` 一定装得下指针」的假设。清单里最容易漏的是三种静默失败：`char` 默认无符号的平台上 `getchar` 循环等不到 `EOF`；`size_t` 用 `%d` 打印被截断；`long` 在 LLP64 上装不下指针。它们在开发机上都不报警。`getopt` 与 `getopt_long` 正好是这条边界的标本：短选项属于 POSIX，长选项属于 GNU，重排、缩写这些行为差异要用 `+`、`POSIXLY_CORRECT`、`--` 显式控制。清单最后一条其实是个动作：编两遍。如果只记住一件事：**写下一个数字或一个类型之前，先问它是本机事实还是接口保证。**

**Q2（辨析）** 为什么「在 `-D_GNU_SOURCE` 下能编过」不能证明代码可移植？`getopt` 会不会重排 `argv`、`--color always` 算不算带了参数——这两件事共同说明了什么？

**Q3（应用）** 你要把只在自己机器上跑通的一个命令行工具，交给用不同 CPU 架构、不同发行版的同事。按本节清单给出提交前要跑的两条编译命令，说明它们分别暴露什么问题。

::: sol 答案
**A1** `char c = getchar(); if (c == EOF)`：`char` 默认无符号时 `EOF` 变成 255，循环不终止，用 `int` 接返回值。`printf("%d", strlen(s))`：`size_t` 被按 32 位有符号解释，可能打出负数，用 `%zu`。把指针存进 `long`：LP64 上两者同宽所以本机没事，LLP64 上 `long` 只有 32 位会截断，用 `intptr_t`/`uintptr_t`。写死系统调用号、猜 `PATH_MAX` 缓冲区属于同一类。
**A2** 因为 `_GNU_SOURCE` 把所有扩展的声明都打开，代码可以随意使用只有 Linux/glibc 才有的接口；编过只说明「在这套 libc 上看得见」，换一套实现就没有那些符号。那两个例子说明可移植性包含**行为**，不只是「能不能编译」：同一个 `getopt`，GNU 实现会重排 `argv`、把选项挪到前面，BSD 实现和设了 `POSIXLY_CORRECT` 的实现在第一个操作数处就停；同一个长选项，`--color=always` 才带上参数，`--color always` 里的 `always` 会被当成操作数。要控制就显式写 `+`、`--`，或者先用 `_POSIX_C_SOURCE=200809L` 编一遍，把扩展依赖逼出来。
**A3** 第一条：`-std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror`，这是本书示例的默认口径，保证警告升级为错误、扩展接口可用。第二条：`-std=c17 -D_POSIX_C_SOURCE=200809L`，凡是报「未声明」的调用就是你对 glibc 扩展的依赖，也正是换系统后最先出问题的地方。两条都在本机跑，还挡不住架构差异——`char` 的符号性、`long` 的宽度只有在对方架构上（或交叉编译）编一次才会暴露，所以清单第 9 条要配一次真实的目标架构编译。
:::

## 2.1.9 系统调用 ABI：寄存器、参数上限与返回约定 {#sec-2.1.9}

这一节回答：同一条 `read` 在不同架构上凭什么能编成不同的机器码，而源码不变？`syscall(2)` 为什么最多只能传六个参数？

::: preview 先抓住一件事
进内核靠的是一份二进制约定，不是 C 原型：调用号进哪个寄存器、参数按什么顺序排满六个、返回值用负数表示错误，都由架构定死。装不下的第七个参数，内核的做法是改成「传一个结构体指针」。
:::

系统调用是**跨特权级的函数调用**，但它没有 C 的函数原型可依赖。调用号放哪个寄存器、参数按什么顺序放、返回值怎么表示，全部由架构的 ABI 固定。glibc 的包装函数就是把 C 调用翻译成这套寄存器约定的一小段汇编。

| 架构 | 陷入指令 | 调用号 | 参数寄存器（依次） | 返回值 |
|:--|:--|:--|:--|:--|
| x86-64 | `syscall` | `rax` | `rdi`、`rsi`、`rdx`、`r10`、`r8`、`r9` | `rax` |
| i386 | `int 0x80` | `eax` | `ebx`、`ecx`、`edx`、`esi`、`edi`、`ebp` | `eax` |
| ARM64 | `svc #0` | `x8` | `x0`–`x5` | `x0` |
| RISC-V 64 | `ecall` | `a7` | `a0`–`a5` | `a0` |

x86-64 用 `r10` 而不是 `rcx` 传第四个参数，因为 `syscall` 指令本身会用 `rcx` 保存返回地址。这个细节无法从 C 源码看出来，但决定了手写汇编时必须用 `r10`。

::: def 定义 2.1.4 · 系统调用 ABI {#def-2.1.4}
系统调用 ABI 是「用户态与内核态之间传递调用号、参数、返回值」的二进制约定。它包括：陷入指令、调用号所在寄存器、参数寄存器顺序、返回值寄存器、错误表示法（内核用 `-errno`）、以及哪些寄存器由内核保证保留。ABI 一旦发布就不能改，否则所有已编译的程序都会坏掉。
:::

### 为什么参数最多六个

六个参数不是内核随便定的，而是**寄存器数量与返回地址占用**的结果：x86-64 的调用约定里，能自由用于传参的寄存器刚好六个；再多就要用栈，而 `syscall` 指令切换栈的过程由内核控制，用户栈指针不能直接当参数传。因此超过六个参数的系统调用一律改成「传一个指向结构体的指针」：

| 调用 | 参数形态 | 原因 |
|:--|:--|:--|
| `mmap` | 六个标量 | 刚好用满 |
| `clone3` | `struct clone_args *` | 参数持续增加，用结构体带 `size` 做版本演进 |
| `openat2` | `struct open_how *` | 同上，`size` 字段允许未来扩展 |
| `io_uring_setup` | `struct io_uring_params *` | 输入输出共用一块结构 |
| `bpf` | `union bpf_attr *` | 命令多、参数差异大 |

结构体方案还解决了**扩展性**：`clone3` 的 `size` 字段让内核知道用户态用的是哪个版本的结构，新字段可以追加而不破坏旧程序。这是「ABI 只能加不能改」的具体实现手法。

```c
/* abi_probe.c — 观察 ABI 常量、错误返回与 >6 参数的结构体入口 */
#include <errno.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>
#include <sys/syscall.h>
#include <time.h>
#include <unistd.h>

int main(void)
{
    printf("sizeof(off_t)=%zu sizeof(time_t)=%zu sizeof(long)=%zu\n",
           sizeof(off_t), sizeof(time_t), sizeof(long));

    /* 1. 坏指针不会 SIGSEGV，内核返回 EFAULT */
    errno = 0;
    long r = syscall(SYS_getrandom, (void *)0x1, (size_t)16, 0u);
    printf("getrandom(bad) = %ld, errno=%d (%s)\n",
           r, errno, strerror(errno));

    /* 2. syscall() 也做 errno 翻译：内核返回 -ENOSYS，这里看到 -1 */
    errno = 0;
    r = syscall(SYS_getpid);
    printf("syscall(SYS_getpid)=%ld errno=%d\n", r, errno);

    /* 3. 调用号是架构相关的，必须用 SYS_* 而不是数字 */
    printf("SYS_read=%d SYS_write=%d SYS_openat=%d\n",
           (int)SYS_read, (int)SYS_write, (int)SYS_openat);
#ifdef SYS_statx
    printf("SYS_statx=%d\n", (int)SYS_statx);
#endif
#ifdef SYS_clone3
    printf("SYS_clone3=%d（参数是 struct clone_args *）\n", (int)SYS_clone3);
#endif
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 abi_probe.c -o abi_probe
./abi_probe
# ubuntu 24.04.5 / aarch64 上实测输出：
# sizeof(off_t)=8 sizeof(time_t)=8 sizeof(long)=8
# getrandom(bad) = -1, errno=14 (Bad address)
# syscall(SYS_getpid)=76726 errno=0
# SYS_read=63 SYS_write=64 SYS_openat=56
# SYS_statx=291
# SYS_clone3=435（参数是 struct clone_args *）
```

第一行输出在 32 位系统上会不同：`sizeof(time_t)` 可能是 4，`sizeof(off_t)` 也可能是 4。这不是「编译器的选择」，而是 ABI 与特性宏共同决定的（2.1.11 展开）。

编号那几行才是本节最该抄进笔记的东西，而且它们**只在 aarch64 上成立**。`SYS_read` 在这里是 63，在 x86-64 上是 0；`SYS_openat` 是 56 对 257；`SYS_getpid` 是 172 对 39。想自己核对，不用记表：`grep '__NR_read \|__NR_openat' /usr/include/asm-generic/unistd.h`——aarch64 的 `asm/unistd.h` 只有一行 `#include <asm-generic/unistd.h>`，编号全在通用那张表里；x86-64 用的是自己的 `unistd_64.h`。两条附带的硬事实：这台机器的头文件里**根本没有 `__NR_open`**，aarch64 没有 `open` 系统调用，glibc 的 `open()` 一律翻译成 `openat`；而 `0` 号在 aarch64 上是 `io_setup`，所以 `syscall(0, ...)` 不会像 x86-64 那样执行 `read`。`clone3` 两边都是 435 纯属巧合，别把它当成「编号会对齐」的证据。

### `EFAULT`：内核如何对待坏指针

用户态传一个野指针给 `read`，进程**不会**收到 `SIGSEGV`；内核的 `copy_to_user`/`copy_from_user` 会捕获缺页，返回未拷贝的字节数，系统调用最终返回 `-EFAULT`。这条规则非常重要：

- 内核不能用用户态的解引用指令直接访问用户内存，否则一个恶意指针就能让内核崩溃；
- `access_ok()` 只检查地址范围是否落在用户空间，不保证页已映射；
- 真正的映射检查发生在拷贝时，失败就返回 `EFAULT`。

因此「用 `read` 探测一个地址是否可写」不可靠：`EFAULT` 只说明这次拷贝失败，不说明地址永久无效；反过来，`access_ok` 通过也不代表不会 `EFAULT`。

::: errata 关于系统调用入口的四个误解
1. **「`syscall()` 是直接执行 `syscall` 指令」**——glibc 的 `syscall()` 是一小段 C/汇编包装：按 ABI 排寄存器、执行架构的陷入指令（x86-64 `syscall`、ARM64 `svc`），把负返回值翻译成 `-1` 加 `errno`。它不做 vDSO 分派（vDSO 是 `clock_gettime` 这类**具体函数**的优化路径），也不做用户指针检查——传野指针照样 `EFAULT`。
2. **「内核返回 -1 表示错误」**——内核返回的是 `-errno`（如 `-2` 表示 `ENOENT`）；只有 libc 包装才把它变成 `-1` 加 `errno`。看 `strace` 的 `= -1 ENOENT` 是 libc 视角。
3. **「系统调用号可以跨架构复用」**——`SYS_read` 在 x86-64 是 0，在 ARM64 是 63。写死数字的代码换架构就调错函数，且编译器不会报错。
4. **「被 seccomp 拦截会收到信号」**——默认动作是杀进程，但 `SECCOMP_RET_ERRNO` 可以让调用直接返回指定错误码，看起来像普通失败；容器里「`openat` 突然返回 `EPERM`」常常是 seccomp 而不是权限。
:::

### 32 位时间与 `EOVERFLOW`

`time_t` 在 32 位 ABI 上是 32 位有符号数，2038 年会溢出。Linux 5.1 起提供了一整套 `*time64` 系统调用，glibc 2.34 起在 32 位上默认用 64 位 `time_t` 编译（`_TIME_BITS=64`）。这带来两个可观察后果：

1. 32 位程序读大文件的 `stat` 可能返回 `EOVERFLOW`，因为 `st_size` 放不下；用 `stat64` 或定义 `_FILE_OFFSET_BITS=64` 解决。
2. 直接 `syscall(SYS_clock_gettime, ...)` 在 32 位新 glibc 上可能调错——用户态结构是 64 位的，内核旧入口期望 32 位。**不要绕过包装函数**，除非你在写 libc。

::: ex 例 2.1.4 · 先猜 `syscall(0, fd, buf, n)` 在这台机器上干什么 {#ex-2.1.4}
x86-64 的笔记上写着「0 号是 `read`」，有人照抄成 `syscall(0, fd, buf, n)`，在这台 aarch64 机器上跑。先猜：它会读出字节、返回 `ENOSYS`（表示没有这个调用），还是干第三件事？再猜：这个程序里明明调了 `open()`，`grep __NR_open` 在这台机器的头文件里搜得到吗？

::: sol 解答
`ENOSYS` 是最不该猜的那个。本节上面的读数已经给出原因：这台机器上 63 号才是 `read`，0 号被 `io_setup` 占了（io_uring 建事件环的调用，第一个参数是「要几个事件」，跟 fd 没关系）。调用照样被受理、照样带回一个值，只是读不到你要的那几个字节；编译器不报，`errno` 也不会告诉你「号写错了」。它具体返回什么，在本机上跑一遍这条命令就知道：`strace -e trace=io_setup,read ./prog`，看它落在哪个调用名上。

第二问搜不到，而且这不是笔误：aarch64 根本没有 `open` 这个系统调用，glibc 的 `open()` 一律翻译成 `openat`（本机 `SYS_openat=56`）。所以「头文件里 grep 不到某个 `__NR_`」有两种完全不同的原因——名字写错了，或者这台机器上压根没有这个入口，分开它们靠的是 `strace`，不是编译器。
:::
:::

### 2.1.9 小结

系统调用没有 C 原型可依，能依的是架构定死的四件事：陷入指令、调用号在哪个寄存器、六个参数寄存器按什么顺序排、返回值寄存器用负数表示 `-errno`。同一份源码能在两个架构上编出不同机器码，靠的是 glibc 包装函数按本机 ABI 重排寄存器，`SYS_read` 这类宏由本机头文件给出。六个参数是物理上限，超出来的接口一律改成「带 `size` 字段的结构体指针」，`clone3`、`openat2`、`bpf` 都是这个形状，`size` 顺带解决了版本演进。坏指针不会让进程在拷贝那一刻崩掉：内核兜住缺页，带回一个 `EFAULT`，所以「用 `read` 探测地址可写」不成立。本节的数字属于 x86-64 的形状，换架构就换一套（见上面的读数块）。如果只记住一件事：**凡是「几号调用、哪个寄存器」这类数字都属于架构，不能抄。**

::: method 即时自测 · 2.1.9
**Q1（记忆）** x86-64 与 ARM64 各用哪个寄存器放调用号？返回值在哪个寄存器？第四个参数在 x86-64 上放哪里，为什么不用 `rcx`？

**Q2（辨析）** 把一个野指针交给 `read`，进程会收到 `SIGSEGV` 还是拿到别的什么？「内核返回 -1 就是失败」这句话错在哪？

**Q3（应用）** 一个封装要传七个值给内核，寄存器只有六个。写出你选的接口形态，说明它的结构体里为什么通常带一个长度字段；再给出一条命令，用来确认程序真的调用了你以为的那个系统调用。

::: sol 答案
**A1** x86-64 调用号在 `rax`、返回值也在 `rax`，参数依次是 `rdi`、`rsi`、`rdx`、`r10`、`r8`、`r9`；第四个用 `r10` 是因为 `syscall` 指令自己把返回地址存进 `rcx`（`r11` 存标志位）。ARM64 调用号在 `x8`，参数是 `x0`–`x5`，返回值在 `x0`。
**A2** 都不是 `SIGSEGV`：调用返回 `-1`，`errno` 是 `EFAULT`。内核不直接用解引用指令访问用户内存，`copy_from_user` 一类拷贝会兜住缺页，把失败变成一个错误码带回来。另一处错在把两层混成一层——内核侧返回的是 `-errno`（`-2` 就是 `ENOENT`），`-1` 加 `errno` 是 libc 翻译给用户态的形态。
**A3** 六个寄存器装不下时，内核接口的通行做法是把参数收进一个结构体、只传指针，例如 `clone3` 收 `struct clone_args *`、`openat2` 收 `struct open_how *`。结构体带一个长度字段，内核就能判断调用方用的是哪一版布局，以后往后追加新字段也不会破坏旧程序。确认手段是 `strace -e trace=clone3,openat2 ./prog`，看它落在哪个调用上、参数指针是否如预期。

## 2.1.10 `errno` 的深水区：`strerror_r`、别名与错误映射 {#sec-2.1.10}

这一节回答：为什么同一个 `strerror_r` 有两种签名？`EAGAIN` 和 `EWOULDBLOCK` 是同一个数吗？错误码该怎样变成 HTTP 状态码或退出码？

::: preview 先抓住一件事
错误码有三种出口：转成给人看的文字、判断是不是同一件事、换成对外协议。三条路各有一个坑——`strerror_r` 有两种不兼容的签名，等价错误码在 Linux 上恰好相等而 POSIX 允许不等，进程退出码只剩八位。
:::

2.1.3 给了七条规则，但真实代码还要处理三件事：**把错误码转成字符串**、**识别等价的错误码**、**把错误码映射成对外协议**。

### `strerror_r` 的两个不兼容版本

POSIX 版（XSI）返回 `int`：0 成功，非 0 是错误码。GNU 版返回 `char *`：可能指向你给的缓冲区，也可能指向静态字符串。同一个函数名，签名不同，取决于 `_GNU_SOURCE`：

```c
/* POSIX/XSI：返回 int */
int strerror_r(int errnum, char *buf, size_t buflen);

/* GNU：返回 char *，可能忽略 buf */
char *strerror_r(int errnum, char *buf, size_t buflen);
```

写可移植代码的稳妥做法是用 `strerror_l`（POSIX.1-2008）或自己判断：

```c
static const char *err_text(int e, char *buf, size_t n)
{
#if defined(__GLIBC__) && defined(_GNU_SOURCE)
    return strerror_r(e, buf, n);        /* GNU：直接返回字符串 */
#else
    if (strerror_r(e, buf, n) != 0)
        snprintf(buf, n, "errno %d", e);
    return buf;
#endif
}
```

GNU 版有一个坑：当错误码未知时，它返回的可能是 `"Unknown error 1234"` 这样的**静态字符串**，而不是写进 `buf`；调用者不能假设返回值一定等于 `buf`，也不能 `free` 它。

### 等价的错误码

| 名字对 | Linux 上是否相等 | 说明 |
|:--|:--|:--|
| `EAGAIN` / `EWOULDBLOCK` | 相等（11） | 非阻塞「暂时不可用」 |
| `ENOTSUP` / `EOPNOTSUPP` | 相等（95） | 操作不支持；POSIX 允许不同 |
| `EDEADLK` / `EDEADLOCK` | 相等（35） | 历史别名 |
| `ENODATA` / `ENOATTR` | Linux 只有 `ENODATA` | macOS 用 `ENOATTR`，跨平台代码要 `#ifdef` |
| `ENOTSUP` / `ENOSYS` | 不相等 | 前者「这个对象不支持」，后者「内核没这个调用」 |

判断时写名字，不写数字；但**不要假设两个名字一定不等**。例如 `if (errno == ENOTSUP || errno == EOPNOTSUPP)` 在 Linux 上是重复条件，编译器可能警告 `-Wlogical-op`（GCC），写成 `errno == EOPNOTSUPP` 就够，跨平台再包一层宏。

### 错误码到对外语义的映射

服务端不能把 `errno` 直接返回给客户端，但也不该一律 500。一张最小映射表：

| `errno` | HTTP | 是否重试 | 备注 |
|:--|:--|:--|:--|
| `ENOENT` | 404 | 否 | 资源不存在 |
| `EACCES` / `EPERM` | 403 | 否 | 权限或 LSM 拒绝 |
| `EINVAL` | 400 | 否 | 参数非法，常是调用方 bug |
| `ENOSPC` / `EDQUOT` | 507 | 否 | 磁盘/配额满 |
| `EMFILE` / `ENFILE` | 503 | 是（退避） | 本进程/系统 fd 耗尽 |
| `EAGAIN` / `EWOULDBLOCK` | 503 + `Retry-After` | 是 | 暂时不可用 |
| `ETIMEDOUT` | 504 | 视语义 | 上游超时 |
| `EINTR` | — | 是 | 不应到达协议层，循环内重试 |
| `EIO` | 500 | 否 | 设备/文件系统错误，需告警 |

进程退出码则用 `sysexits.h` 的 `EX_USAGE`(64)、`EX_DATAERR`(65)、`EX_NOINPUT`(66)、`EX_UNAVAILABLE`(69)、`EX_OSERR`(71)、`EX_IOERR`(74)。退出码只有 8 位，`exit(256)` 实际变成 0，这是脚本里「程序失败了但 `$?` 是 0」的常见原因。

```c
/* strerror_demo.c — 三种取错误文本的方式与等价错误码 */
#include <errno.h>
#include <stdio.h>
#include <string.h>

static void show(int e)
{
    char buf[128];
    const char *s = strerror_r(e, buf, sizeof buf);   /* GNU 版 */
    printf("%-12s %3d  %s\n", "errno", e, s);
}

int main(void)
{
    show(ENOENT);
    show(EACCES);
    show(EINVAL);
    show(ENOSPC);

    printf("\nEAGAIN=%d EWOULDBLOCK=%d equal=%d\n",
           EAGAIN, EWOULDBLOCK, EAGAIN == EWOULDBLOCK);
    printf("ENOTSUP=%d EOPNOTSUPP=%d equal=%d\n",
           ENOTSUP, EOPNOTSUPP, ENOTSUP == EOPNOTSUPP);

    errno = ENOENT;
    printf("\n%%m 直接打印当前 errno: %m\n");          /* glibc 扩展 */
    printf("显式错误码: %s\n", strerror(ENOSPC));
    return 0;
}
```


`%m` 是 glibc 的 `printf` 扩展，等价于 `strerror(errno)`，不消耗参数。它方便，但不可移植；日志库里用 `strerror_r` 更稳。

::: errata `errno` 转换的五个坑
1. **「`strerror_r` 返回 0 就是成功」**——只有 XSI 版如此；GNU 版返回指针，永远非 0。
2. **「`strerror` 返回的字符串可以长期保存」**——它可能指向静态缓冲区，下一次调用会被覆盖；多线程下更不安全。
3. **「错误码是负数」**——用户态 `errno` 是正的；负数只出现在内核返回值里。
4. **「`errno` 会被 `printf` 保留」**——`printf` 内部可能调用 `malloc`/`write`，失败时改写 `errno`；打印错误前先保存。
5. **「`EINTR` 应该报告给用户」**——它表示「被信号打断」，绝大多数情况应重试，不应变成 500。
:::

### 2.1.10 小结

从 `errno` 到「说得出口的错误」要走三段，每段都可能出错。转文字这一段：`strerror` 返回的那段话可能在静态缓冲区里，下次调用就被覆盖；`strerror_r` 的 GNU 版返回指针（可能根本不写你给的缓冲区），XSI 版返回 `int`，用哪个由 `_GNU_SOURCE` 决定，所以可移植写法要么自己分支，要么改用 `strerror_l`。认别名这一段：Linux 上 `EAGAIN` 与 `EWOULDBLOCK` 都是 11、`ENOTSUP` 与 `EOPNOTSUPP` 都是 95，但 POSIX 允许它们不同；比较时写名字不写数字，也别把一对别名写成 `||` 让编译器警告重复条件。换协议这一段：`ENOENT` 是 404、`EMFILE` 是 503 加退避、`EINTR` 不该出现在协议层，而退出码只剩八位可用。如果只记住一件事：**先确定这个错误码要去哪儿，再选用哪个函数。**

## 2.1.11 特性测试宏矩阵与 ABI 宏 {#sec-2.1.11}

这一节回答：`_GNU_SOURCE`、`_POSIX_C_SOURCE`、`_XOPEN_SOURCE`、`_DEFAULT_SOURCE` 之间是什么关系？`_FILE_OFFSET_BITS=64` 为什么能改变结构体布局？

::: preview 先抓住一件事
特性宏管两件事：哪些声明你看得见，哪些类型和结构体按哪套布局算。`_FILE_OFFSET_BITS=64` 属于第二件——它把 `off_t` 变成 64 位，`struct stat` 的尺寸跟着变，所以它不是编译期的注释，而是 ABI 的一部分。
:::

2.1.5 讲了「宏控制声明可见性」。但特性测试宏不只控制函数声明，还控制**类型定义与结构体布局**。最典型的是 `_FILE_OFFSET_BITS=64`：它让 `off_t`、`stat`、`mmap` 的偏移参数全部变成 64 位，从而改变 `struct stat` 的大小和 `stat` 符号的版本。

### 宏之间的关系

| 你定义的 | glibc 等价打开 | 典型可见接口 |
|:--|:--|:--|
| `_POSIX_C_SOURCE=200809L` | POSIX.1-2008 | `posix_memalign`、`clock_gettime`、`sigaction` |
| `_XOPEN_SOURCE=700` | POSIX.1-2008 + XSI | `openpty`、`log2`、`crypt` |
| `_DEFAULT_SOURCE` | POSIX + BSD + SVID 默认集 | `strdup`、`strcasecmp`、`MSG_NOSIGNAL` |
| `_GNU_SOURCE` | 上面全部 + GNU 扩展 | `accept4`、`pipe2`、`memfd_create`、`%m` |
| `_ISOC11_SOURCE` | C11 库扩展 | `aligned_alloc` |
| `_FILE_OFFSET_BITS=64` | 大文件 ABI | `off_t` 变 64 位，`stat` 重定向到 `stat64` |
| `_TIME_BITS=64` | 64 位 `time_t`（需同时定义 `_FILE_OFFSET_BITS=64`） | 32 位系统上的 2038 安全 |

`_GNU_SOURCE` 会**隐式定义** `_DEFAULT_SOURCE`、`_POSIX_C_SOURCE=200809L`、`_XOPEN_SOURCE=700`、`_ISOC99_SOURCE`、`_ISOC11_SOURCE`。反过来不成立：定义了 `_POSIX_C_SOURCE` 之后，glibc 不再默认给 `_DEFAULT_SOURCE`，BSD 扩展全部消失。

### 顺序：宏必须在第一个系统头之前

```c
/* 正确：翻译单元最前面 */
#define _GNU_SOURCE
#include <stdio.h>

/* 错误：features.h 已经被间接包含，宏来晚了 */
#include <stdio.h>
#define _GNU_SOURCE
#include <unistd.h>       /* 看不到 accept4 */
```

`<features.h>` 是 glibc 的「总开关」，任何系统头都会先包含它。它只在第一次被包含时根据当时的宏计算 `__USE_*` 系列，之后再定义特性宏不会重新计算。所以本书统一用编译命令 `-D_GNU_SOURCE`，从翻译单元的第 0 个字符就生效。

### 用 `_Static_assert` 锁住 ABI

特性宏配错时，最可怕的不是编译失败，而是**静默用错 ABI**。例如 32 位程序没有定义 `_FILE_OFFSET_BITS=64`，`off_t` 是 32 位，`lseek` 到 3 GiB 会失败或截断。可以用编译期断言把假设写死：

```c
#include <assert.h>
#include <sys/types.h>

_Static_assert(sizeof(off_t) == 8, "需要 64 位 off_t：加 -D_FILE_OFFSET_BITS=64");
_Static_assert(sizeof(time_t) >= 8, "需要 64 位 time_t：加 -D_TIME_BITS=64");
```

这比运行时报错早得多，也比注释可靠。

```c
/* feature_matrix.c — 打印当前翻译单元实际生效的特性宏 */
#include <features.h>
#include <stdio.h>
#include <time.h>
#include <unistd.h>

int main(void)
{
    printf("glibc %d.%d\n", __GLIBC__, __GLIBC_MINOR__);
#ifdef __USE_GNU
    printf("__USE_GNU=1（GNU 扩展可见）\n");
#else
    printf("__USE_GNU=0\n");
#endif
#ifdef __USE_XOPEN2K8
    printf("__USE_XOPEN2K8=1（POSIX.1-2008 可见）\n");
#else
    printf("__USE_XOPEN2K8=0\n");
#endif
#ifdef __USE_MISC
    printf("__USE_MISC=1（BSD/SVID 默认集可见）\n");
#else
    printf("__USE_MISC=0\n");
#endif
    printf("sizeof(off_t)=%zu sizeof(time_t)=%zu\n",
           sizeof(off_t), sizeof(time_t));
#ifdef _FILE_OFFSET_BITS
    printf("_FILE_OFFSET_BITS=%d\n", _FILE_OFFSET_BITS);
#else
    printf("_FILE_OFFSET_BITS 未定义（32 位上意味着 32 位 off_t）\n");
#endif
    return 0;
}
```

```bash
# 三种组合各编一次，比较输出
cc -std=c17 -Wall -Wextra -Werror -O2 feature_matrix.c -o fm_default
cc -std=c17 -D_POSIX_C_SOURCE=200809L -Wall -Wextra -Werror -O2 feature_matrix.c -o fm_posix
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 feature_matrix.c -o fm_gnu

```

三者最明显的差别是 `__USE_GNU` 与 `__USE_MISC`：默认编译（`-std=c17` 且无宏）连 `strdup` 都可能没有声明，而 `_GNU_SOURCE` 全开。

### 把 2.1.5 引用的 `accept4_demo.c` 补全

2.1.5 用一条 `cc ... -fsyntax-only accept4_demo.c` 演示「符号在库里、声明看不见」，但没给那份源码，这里补上。它同时是 Linux 扩展接口的一个典型样本：`accept4` 属于扩展集，只声明 POSIX.1-2008 时它没有声明，本书统一用命令行上的 `-D_GNU_SOURCE`。

它要解决的真实问题是「拿到的新 fd 来不及设置」。用 `accept` 再加两次 `fcntl` 也能做到「关闭时自动释放 + 非阻塞」，但那两步之间有一个窗口：如果这期间有别的线程 `fork` 后 `exec`，这个 fd 就会漏进子进程。`accept4` 把两件事压成一次调用，标志位由内核在创建 fd 时一并设好，没有那个窗口。

```c
/* accept4_demo.c — 完整可编译源码；宏写在编译命令行，见 2.1.5
   编译：cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 \
            accept4_demo.c -o accept4_demo
   本节不贴它的运行输出：要走完这段代码需要一个真的客户端连进来，
   那部分实验放到讲 socket 的小节里做。 */
#include <arpa/inet.h>
#include <errno.h>
#include <fcntl.h>
#include <netinet/in.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/socket.h>
#include <time.h>
#include <unistd.h>

static void die(const char *msg)
{
    int saved = errno;                    /* 打印之前先保存（2.1.3 规则 4） */
    fprintf(stderr, "%s: %s\n", msg, strerror(saved));
    errno = saved;
    exit(EXIT_FAILURE);
}

int main(void)
{
    int listenfd = socket(AF_INET, SOCK_STREAM | SOCK_CLOEXEC, 0);
    if (listenfd == -1)
        die("socket");

    int on = 1;
    if (setsockopt(listenfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof on) == -1)
        die("setsockopt");

    struct sockaddr_in local;
    memset(&local, 0, sizeof local);
    local.sin_family = AF_INET;
    local.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    local.sin_port = 0;                   /* 端口填 0：让内核挑一个空闲端口 */
    if (bind(listenfd, (struct sockaddr *) &local, sizeof local) == -1)
        die("bind");
    if (listen(listenfd, 128) == -1)
        die("listen");

    socklen_t len = sizeof local;
    if (getsockname(listenfd, (struct sockaddr *) &local, &len) == -1)
        die("getsockname");
    printf("waiting on 127.0.0.1:%u\n", (unsigned) ntohs(local.sin_port));

    for (;;) {
        struct sockaddr_in peer;
        socklen_t plen = sizeof peer;
        int connfd = accept4(listenfd, (struct sockaddr *) &peer, &plen,
                             SOCK_CLOEXEC | SOCK_NONBLOCK);
        if (connfd == -1) {
            int saved = errno;            /* 分支里还要调别的函数 */
            switch (saved) {
            case EINTR:                   /* 被信号打断：重来，不是失败 */
                continue;
            case EAGAIN:                  /* 监听 fd 非阻塞且队列已空 */
            case ECONNABORTED:            /* 连接在返回前被对端关掉 */
                continue;
            case EMFILE:                  /* 本进程 fd 用光 */
            case ENFILE:                  /* 系统级 fd 用光 */
            case ENOBUFS:
            case ENOMEM:                  /* 资源暂时不足：退避后重试 */
                {
                    struct timespec ts = { .tv_sec = 0, .tv_nsec = 100000000 };
                    nanosleep(&ts, NULL);
                    continue;
                }
            default:
                errno = saved;
                die("accept4");           /* EBADF、EINVAL 等属于编程错误 */
            }
        }

        /* 两个 flag 已由内核在创建 fd 时设好，不需要再补 fcntl。
           这里读一次标志位，只是证明 O_NONBLOCK 真的在这个 fd 上。 */
        int fl = fcntl(connfd, F_GETFL);
        if (fl == -1)
            die("fcntl(F_GETFL)");
        printf("connfd=%d  O_NONBLOCK=%d\n", connfd, (fl & O_NONBLOCK) != 0);

        close(connfd);
        break;
    }

    close(listenfd);
    return 0;
}
```

读这份代码要带走三点。第一，`saved` 又出现了两次——`die` 之前、`switch` 之前各一次，因为分支里还要调 `nanosleep` 和 `fprintf`，它们都可能改写 `errno`。第二，`EINTR`、`EAGAIN`、`ECONNABORTED` 都走 `continue`，只有编程错误才结束进程，这就是 2.1.4 那个判断顺序在 socket 上的样子。第三，把 `accept4` 换成 `accept`、去掉那两个 `SOCK_*` 标志改用 `fcntl` 补上，只声明 POSIX 的编译命令就能编过——代码的能力没变，变的还是头文件让你看见多少。

::: errata 特性宏与 ABI 的五个坑
1. **「`-std=gnu17` 等于 `_GNU_SOURCE`」**——不等。`gnu17` 只关掉 `__STRICT_ANSI__`，让 GCC 扩展可用；glibc 的 `_GNU_SOURCE` 仍要显式定义。
2. **「`_FILE_OFFSET_BITS=64` 只是宏，不改 ABI」**——它会把 `stat`/`fstat`/`lseek`/`mmap` 的声明重定向到 64 位版本，`struct stat` 布局随之改变；混用不同宏编译的目标文件会破坏 ABI。
3. **「头文件里可以定义 `_GNU_SOURCE`」**——头文件可能在被包含前已经引入了系统头，顺序不可控；只放在源文件第一行或命令行。
4. **「`_TIME_BITS=64` 可以单独用」**——glibc 要求同时定义 `_FILE_OFFSET_BITS=64`，否则编译报错。
5. **「`__USE_GNU` 可以手写」**——它由 `<features.h>` 计算，手写无效且可能破坏头文件逻辑；只能通过特性宏间接控制。
:::

### 2.1.11 小结

这一节把 2.1.5 的「可见性」推到第二层：特性宏同时决定类型宽度和结构体布局。`_FILE_OFFSET_BITS=64` 让 `off_t` 变成 64 位，`stat`、`fstat`、`lseek` 的声明被重定向到大文件版本，`struct stat` 的尺寸跟着变；`_TIME_BITS=64` 还要求先定义前者，否则编译直接报错。`__USE_*` 那批开关由 `<features.h>` 在第一次被包含时算完，之后补定义特性宏不会重算，所以宏只能出现在翻译单元第 0 个字符或编译命令行上。用宏编出来的两套目标文件混着链接，尺寸对不上，坏的是运行时而不是编译时，所以把关键假设写成 `_Static_assert` 比注释可靠。`accept4_demo.c` 是这条链的一个小样本：代码没变，换个宏就从「编不过」变成「编得过」，库一个字节都没动。如果只记住一件事：**特性宏改的是 ABI，不只是能不能看见一个函数名。**

## 2.1.12 限制查询：`sysconf`、`pathconf` 与 `getrlimit` {#sec-2.1.12}

这一节回答：`sysconf(_SC_OPEN_MAX)`、`ulimit -n`、`/proc/sys/fs/nr_open` 三个数为什么有时相同、有时不同？程序该信哪一个？

::: preview 先抓住一件事
「最多能开多少个文件」有三个数：`sysconf(_SC_OPEN_MAX)` 是本进程软限制的另一种读法，`ulimit -n` 是同一个数的 shell 视图，`/proc/sys/fs/nr_open` 是内核给单个进程划的天花板。程序按软限制分配，撞上的是硬限制，超不过的是内核那一层。
:::

2.1.6 讲了 `sysconf` 的返回值二义性。真实程序还要面对**三层限制**：

| 层 | 查询方式 | 例子 | 谁受限 |
|:--|:--|:--|:--|
| 内核全局上限 | `/proc/sys/fs/nr_open`、`/proc/sys/fs/file-max` | `nr_open` 默认 1048576 | 所有进程 |
| 进程资源限制 | `getrlimit(RLIMIT_NOFILE)` | 软限制 1024，硬限制 1048576 | 单个进程 |
| POSIX 查询接口 | `sysconf(_SC_OPEN_MAX)` | glibc 返回软限制；其他实现可能不同 | 本进程 |

在 Linux/glibc 上，`sysconf` 不是独立的第三层，而是 `RLIMIT_NOFILE` 软限制的投影（Kerrisk 第 11 章）。要判断还能开多少 fd，仍应以 `getrlimit` 为准：

```c
struct rlimit rl;
if (getrlimit(RLIMIT_NOFILE, &rl) == -1)
    errExit("getrlimit");
printf("soft=%llu hard=%llu\n",
       (unsigned long long)rl.rlim_cur, (unsigned long long)rl.rlim_max);

/* 在硬限制内提高软限制；超过硬限制返回 EPERM */
rl.rlim_cur = rl.rlim_max;
if (setrlimit(RLIMIT_NOFILE, &rl) == -1 && errno == EPERM)
    fprintf(stderr, "没有权限提高 fd 上限\n");
```

### 常用 `sysconf` 名字

名字与读数都来自这台 Ubuntu 24.04.5 aarch64（内核 7.0.0-38、glibc 2.39）上的一次 `sysconf` 实测；换成别的机器，带「跟着会话/机器变」标记的那几行一定会变：

| 名字 | 含义 | 本机实测 | 注意 |
|:--|:--|--:|:--|
| `_SC_PAGESIZE` | 页大小 | 4096 | 必须用它，不能写死；ARM64 内核也可配成 16/64 KiB |
| `_SC_PHYS_PAGES` | 物理页数 | 3051987 | 乘页大小 ≈ 11.6 GiB，与 `free -h` 对得上；跟着机器变 |
| `_SC_AVPHYS_PAGES` | 可用页数 | 2596320 | 不含可回收缓存；**瞬时值**，两次调用就会不同 |
| `_SC_NPROCESSORS_ONLN` | 在线 CPU | 4 | 容器里可能被 cgroup 限制，与 `nproc` 一致 |
| `_SC_CLK_TCK` | `times()` 频率 | 100 | `/proc/PID/stat` 的 jiffies 要按它换算 |
| `_SC_ARG_MAX` | 参数+环境上限 | 2097152 | 还受栈 `RLIMIT_STACK`（本机 8 MiB）限制 |
| `_SC_IOV_MAX` | `readv` 段数上限 | 1024 | 不是 `IOV_MAX` 宏 |
| `_SC_SEM_VALUE_MAX` | 信号量最大值 | 2147483647 | |
| `_SC_SIGQUEUE_MAX` | 排队信号数 | 43361 | 本机它等于 `RLIMIT_SIGPENDING`，不是常数 |
| `_SC_ATEXIT_MAX` | `atexit` 注册数 | 2147483647 | 实际受内存限制 |
| `_SC_LOGIN_NAME_MAX` | 登录名长度 | 256 | |
| `_SC_HOST_NAME_MAX` | 主机名长度 | 64 | 与 `getconf HOST_NAME_MAX` 一致 |
| `_SC_SYMLOOP_MAX` | 符号链接层数 | **-1，`errno` 仍为 0** | 意思是「这项没有固定上限」，不是查询失败；glibc 内部用 `40` 当默认值，但那是库的实现细节，不是 `sysconf` 的读数 |

最后两行是本节最想让你记住的形态：`_SC_SIGQUEUE_MAX` 这种「看起来像系统常数」的数其实是当前进程的 `RLIMIT_SIGPENDING`；`_SC_SYMLOOP_MAX` 返回 -1 而 `errno` 没被写，正好是 2.1.6 那条判据的现场——**`-1` 有二义性，查之前必须把 `errno` 清零**，这里 `errno` 保持 0 才说明它是「不确定」而不是「出错」。

### `pathconf` 是「这个文件系统」的限制

`pathconf(path, name)` 作用于路径所在的文件系统。`_PC_NAME_MAX` 在 ext4 是 255，在 eCryptfs 可能只有 143；`_PC_PATH_MAX` 通常是 4096，但 Linux 的路径解析并没有硬性总长限制，`openat2` 只看实际字符串长度。`_PC_PIPE_BUF` 更有用：它决定一次 `write` 到管道是否原子（≤ `PIPE_BUF` 保证不交错）。

```c
long pipe_buf = fpathconf(pipefd[1], _PC_PIPE_BUF);
/* 常见 4096；超过它的一次 write 可能被拆开，与其他写者交错 */
```

`pathconf` 的 `-1` 同样有二义性：`errno == 0` 表示「不确定」，否则是错误。它比 `sysconf` 更容易踩这个坑，因为「不确定」在文件系统上很常见。

```c
/* limits2.c — 三层限制一起看：rlimit、sysconf、pathconf */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/resource.h>
#include <unistd.h>

static void sc(const char *name, int key)
{
    errno = 0;
    long v = sysconf(key);
    if (v == -1 && errno != 0)
        printf("%-24s error: %s\n", name, strerror(errno));
    else if (v == -1)
        printf("%-24s 不确定\n", name);
    else
        printf("%-24s %ld\n", name, v);
}

static void pc(const char *name, int fd, int key)
{
    errno = 0;
    long v = fpathconf(fd, key);
    if (v == -1 && errno != 0)
        printf("%-24s error: %s\n", name, strerror(errno));
    else if (v == -1)
        printf("%-24s 不确定\n", name);
    else
        printf("%-24s %ld\n", name, v);
}

int main(void)
{
    struct rlimit rl;

    if (getrlimit(RLIMIT_NOFILE, &rl) == -1) { perror("getrlimit"); return 1; }
    printf("RLIMIT_NOFILE soft=%llu hard=%llu\n",
           (unsigned long long)rl.rlim_cur, (unsigned long long)rl.rlim_max);

    if (getrlimit(RLIMIT_NPROC, &rl) == 0)
        printf("RLIMIT_NPROC  soft=%llu hard=%llu\n",
               (unsigned long long)rl.rlim_cur, (unsigned long long)rl.rlim_max);
    if (getrlimit(RLIMIT_MEMLOCK, &rl) == 0)
        printf("RLIMIT_MEMLOCK soft=%llu hard=%llu\n",
               (unsigned long long)rl.rlim_cur, (unsigned long long)rl.rlim_max);

    putchar('\n');
    sc("_SC_PAGESIZE", _SC_PAGESIZE);
    sc("_SC_OPEN_MAX", _SC_OPEN_MAX);
    sc("_SC_IOV_MAX", _SC_IOV_MAX);
    sc("_SC_ARG_MAX", _SC_ARG_MAX);
    sc("_SC_NPROCESSORS_ONLN", _SC_NPROCESSORS_ONLN);

    int fd = open("/tmp", O_RDONLY | O_DIRECTORY | O_CLOEXEC);
    if (fd == -1) { perror("open /tmp"); return 1; }
    putchar('\n');
    pc("_PC_NAME_MAX(/tmp)", fd, _PC_NAME_MAX);
    pc("_PC_PATH_MAX(/tmp)", fd, _PC_PATH_MAX);
    pc("_PC_PIPE_BUF(/tmp)", fd, _PC_PIPE_BUF);
    close(fd);

    int p[2];
    if (pipe(p) == -1) { perror("pipe"); return 1; }
    int sz = fcntl(p[1], F_GETPIPE_SZ);          /* Linux 扩展 */
    printf("\npipe capacity=%d bytes\n", sz);
    /* 上限现查，不写死：这一版本程序自己去读 /proc，而不是打印一个抄来的数 */
    int pf = open("/proc/sys/fs/pipe-max-size", O_RDONLY);
    if (pf != -1) {
        char b[32]; ssize_t n = read(pf, b, sizeof b - 1);
        if (n > 0) { b[n] = '\0'; printf("F_SETPIPE_SZ max=%s", b); }
        close(pf);
    } else {
        printf("F_SETPIPE_SZ max=查询失败: %s\n", strerror(errno));
    }
    close(p[0]);
    close(p[1]);

    /* 试超硬限制：EPERM */
    if (getrlimit(RLIMIT_NOFILE, &rl) == 0) {
        rlim_t old = rl.rlim_max;
        rl.rlim_cur = old;
        rl.rlim_max = old + 1;
        if (setrlimit(RLIMIT_NOFILE, &rl) == -1)
            printf("setrlimit 超硬限制: %s\n", strerror(errno));
    }
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 limits2.c -o limits2
./limits2
ulimit -n; cat /proc/sys/fs/nr_open
```

三条命令里，`ulimit -n` 与 `_SC_OPEN_MAX` 应一致（都反映本进程软限制）；`nr_open` 是内核全局上限，通常远大于两者。程序应按软限制分配 fd 表，而不是按 `nr_open`；否则会先撞上 `EMFILE`。

::: method 限制排查顺序
1. 先看**进程**：`cat /proc/PID/limits`，确认 soft/hard 与 `Max open files`。
2. 再看**内核**：`sysctl fs.nr_open fs.file-max`、`/proc/sys/fs/pipe-max-size`。
3. 再看**文件系统**：`stat -f /path`、`fpathconf` 的 `NAME_MAX`/`PIPE_BUF`。
4. 最后看**容器/cgroup**：`systemd` 的 `LimitNOFILE=`、Kubernetes 的 `ulimits`、`/sys/fs/cgroup/.../pids.max`。
5. 不要用 `_SC_OPEN_MAX` 推断系统总量；glibc 上它等于本进程软限制，其他 libc 可能不同。
:::


### `RLIMIT_*` 全表：超限时到底发生什么 {#sec-2.1.12.1}

`getrlimit/setrlimit` 不只用于 fd。每个资源超限的后果不同：有的返回 `errno`，有的发信号，有的直接 `SIGKILL`。

| 资源 | 限制什么 | 超限后果 |
|:--|:--|:--|
| `RLIMIT_CPU` | CPU 秒数（软/硬） | 软限发 `SIGXCPU`；硬限发 `SIGKILL` |
| `RLIMIT_FSIZE` | 单个文件最大字节数 | 写超限发 `SIGXFSZ`；忽略信号则 `write` 返回 `EFBIG` |
| `RLIMIT_CORE` | core 文件最大字节数 | 超过则截断 core；0 表示不写 |
| `RLIMIT_DATA` | `brk`/数据段大小 | `brk/sbrk` 返回 `ENOMEM`；`mmap` 是否计入取决于内核 |
| `RLIMIT_STACK` | 主线程栈大小 | 栈溢出 `SIGSEGV`；`pthread` 栈不受它限制 |
| `RLIMIT_NOFILE` | fd 数量 | `open/socket` 返回 `EMFILE` |
| `RLIMIT_NPROC` | 每 real UID 的进程/线程数 | `fork/clone` 返回 `EAGAIN` |
| `RLIMIT_MEMLOCK` | `mlock`/`mmap(MAP_LOCKED)` 的字节数 | `mlock` 返回 `ENOMEM`/`EPERM` |
| `RLIMIT_AS` | 虚拟地址空间总字节数 | `mmap/brk` 返回 `ENOMEM`；不是 RSS 上限 |
| `RLIMIT_SIGPENDING` | 每 real UID 排队信号数 | `sigqueue` 返回 `EAGAIN` |
| `RLIMIT_MSGQUEUE` | POSIX mq 字节数 | `mq_open/mq_send` 返回 `EMFILE`/`EAGAIN` |
| `RLIMIT_NICE` | nice 可调范围 | `setpriority` 被限制；`EPERM` |
| `RLIMIT_RTPRIO` | 实时优先级上限 | `sched_setscheduler` 返回 `EPERM` |
| `RLIMIT_RTTIME` | 实时任务连续运行微秒数 | 超限发 `SIGXCPU`/`SIGKILL` |

规则：

- 软限制是当前生效值，硬限制是软限制的上限；`rlim_cur <= rlim_max`。
- 非特权进程可以降低硬限制，但**不能再升回**；提高硬限制需要 `CAP_SYS_RESOURCE`。
- `fork`/`exec` 继承；`exec` 会保留限制（setuid 程序也一样，除非被 PAM/系统策略改）。
- `prlimit(2)` 可以跨进程读写另一个进程的限制（需要权限），比 `setrlimit` 更适合排障。

### 2.1.12 小结

限制有三层，越往下越难改：内核全局的 `fs.file-max` 与 `fs.nr_open`、本进程的 `RLIMIT_*`（软硬两个值）、路径所在文件系统的 `pathconf`。glibc 的 `sysconf(_SC_OPEN_MAX)` 只是软限制的另一种读法，不能拿来推断系统总量；`pathconf` 更容易返回「不确定」，所以两类查询前都要 `errno = 0`，否则 `-1` 的含义说不清。超限的后果按资源分三种：返回错误码（`EMFILE`、`EAGAIN`、`ENOMEM`）、发信号（`SIGXCPU`、`SIGXFSZ`）、直接 `SIGKILL`；提高硬限制要特权，降下去就升不回来。排障顺序是先看进程（`/proc/PID/limits`）、再看内核（`sysctl`）、再看文件系统（`fpathconf`），最后才怀疑容器与 cgroup。如果只记住一件事：**「上限是多少」得先问「谁的上限」，否则三个数看着都一样，只有一个是你要的。**

## 2.1.13 命令行解析：`getopt_long` 的完整用法 {#sec-2.1.13}

这一节回答：怎样写一个既支持 `-n 3`、`-n3`、`--count=3`，又能在出错时给出正确退出码的参数解析器？

::: preview 先抓住一件事
`getopt_long` 的返回值不止「一个选项字符」：`'?'` 是未知选项、`':'` 是缺参数（前提是你让 `optstring` 以 `:` 开头）、`-1` 才表示解析结束。选项和操作数能不能混排，由三个开关决定：`optstring` 开头的 `+`、环境变量 `POSIXLY_CORRECT`、命令行里的 `--`。
:::

2.1.8 给了一个 `getopt` 片段。真实工具还需要长选项、可选参数、子命令和「选项与操作数混排」的控制。

### `struct option` 与返回值

```c
struct option {
    const char *name;      /* 长选项名，不带 "--" */
    int         has_arg;   /* no_argument / required_argument / optional_argument */
    int        *flag;      /* NULL：返回 val；非 NULL：把 val 写进 *flag，返回 0 */
    int         val;       /* 返回值或写入 *flag 的值 */
};
```

`getopt_long` 的返回值：

- 短选项字符：正常；
- `val`（当 `flag == NULL`）：长选项匹配；
- `0`（当 `flag != NULL`）：已把值写进 `*flag`；
- `'?'`：未知选项或参数缺失（`opterr` 为 0 时不打印）；
- `':'`：`optstring` 以 `:` 开头且缺少参数；
- `-1`：解析结束。

长选项支持**唯一前缀缩写**：`--cou` 能匹配 `--count`，但如果有 `--count` 和 `--color` 两个前缀相同的选项，缩写会返回 `'?'` 并报「ambiguous」。脚本里不要依赖缩写，版本一加选项就可能歧义。

### 三个影响解析顺序的开关

| 写法 | 行为 |
|:--|:--|
| `getopt(argc, argv, "n:o:")` | GNU 默认**重排** `argv`，把选项移到前面，操作数留在 `optind` 之后 |
| `getopt(argc, argv, "+n:o:")` | 遇到第一个非选项就停止，保持 POSIX 顺序 |
| 环境变量 `POSIXLY_CORRECT` | 等价于加 `+`，全局生效 |
| `--` | 强制结束选项解析，后面的都当操作数 |

`optind` 是下一个待处理参数的下标。解析结束后，`argv[optind]` 起是操作数。GNU 扩展允许把 `optind` 重置为 0 来重新解析（`optind = 0` 会重新初始化，包括 `POSIXLY_CORRECT` 检查）；`optind = 1` 只是回到开头，不重新初始化内部状态。

```c
/* opts.c — getopt_long：短选项、长选项、可选参数、错误处理 */
#include <errno.h>
#include <getopt.h>
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void usage(const char *prog)
{
    fprintf(stderr,
            "usage: %s [-v] [-n COUNT] [-o FILE] [--color[=WHEN]] INPUT...\n"
            "  -n, --count=N      重复次数（默认 1）\n"
            "  -o, --output=FILE  输出文件（默认 stdout）\n"
            "  -v, --verbose      打印解析结果\n"
            "      --color[=WHEN] auto/always/never\n", prog);
}

static long parse_count(const char *s)
{
    char *end = NULL;
    errno = 0;
    long v = strtol(s, &end, 10);
    if (errno != 0 || end == s || *end != '\0' || v <= 0 || v > INT_MAX) {
        fprintf(stderr, "invalid count: %s\n", s);
        exit(EXIT_FAILURE);
    }
    return v;
}

int main(int argc, char *argv[])
{
    static const struct option longopts[] = {
        { "count",   required_argument, NULL, 'n' },
        { "output",  required_argument, NULL, 'o' },
        { "verbose", no_argument,       NULL, 'v' },
        { "color",   optional_argument, NULL, 'c' },
        { "help",    no_argument,       NULL, 'h' },
        { NULL, 0, NULL, 0 },
    };
    long count = 1;
    const char *output = NULL;
    const char *color = "auto";
    int verbose = 0;
    int ch;

    opterr = 0;                     /* 自己打印错误，避免 glibc 的措辞 */
    while ((ch = getopt_long(argc, argv, ":n:o:vh", longopts, NULL)) != -1) {
        switch (ch) {
        case 'n':
            count = parse_count(optarg);
            break;
        case 'o':
            output = optarg;
            break;
        case 'v':
            verbose = 1;
            break;
        case 'c':
            color = optarg ? optarg : "always";
            if (strcmp(color, "auto") && strcmp(color, "always") &&
                strcmp(color, "never")) {
                fprintf(stderr, "bad --color value: %s\n", color);
                return 2;
            }
            break;
        case 'h':
            usage(argv[0]);
            return 0;
        case ':':
            fprintf(stderr, "option -%c requires an argument\n", optopt);
            return 2;
        case '?':
        default:
            if (optopt)
                fprintf(stderr, "unknown option -%c\n", optopt);
            else
                fprintf(stderr, "unknown option: %s\n", argv[optind - 1]);
            return 2;
        }
    }

    if (optind >= argc) {
        fprintf(stderr, "%s: missing INPUT\n", argv[0]);
        return 2;
    }

    if (verbose) {
        printf("count=%ld output=%s color=%s operands=%d\n",
               count, output ? output : "(stdout)", color, argc - optind);
        for (int i = optind; i < argc; i++)
            printf("  operand[%d]=%s\n", i - optind, argv[i]);
    }

    /* 这里只演示解析；真实程序在此处理 argv[optind..argc-1] */
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 opts.c -o opts
./opts -v -n3 a.txt b.txt
./opts --count=2 --color --output=/tmp/x a.txt
./opts --count            # 退出码 2：缺参数
./opts --col=never a.txt  # 唯一前缀缩写
./opts -- -n             # "-n" 是操作数，不是选项
POSIXLY_CORRECT=1 ./opts a.txt -v   # -v 不再被解析
```

最后一条命令展示了 `POSIXLY_CORRECT` 的影响：在 POSIX 模式下，`a.txt` 之后的 `-v` 被当成操作数。很多脚本依赖 GNU 重排，换到 POSIX 模式或 BSD 上行为会变，所以**选项应写在操作数前面**，不要依赖重排。

::: errata `getopt` 的五个坑
1. **「`optarg` 可以长期保存」**——它指向 `argv` 内部，生命周期与 `argv` 相同，通常没问题；但不要 `free` 它，也不要假设下一次解析后还指向同一个字符串。
2. **「`optind` 初始一定是 1」**——库函数或多次解析后不是；重新解析前设 `optind = 0`（GNU）或保存/恢复。
3. **「`getopt` 是线程安全的」**——它用全局状态（`optind`/`optarg`/`optopt`），多线程同时解析会互相踩。
4. **「长选项缩写总是可用」**——只有唯一前缀才行；新增一个同前缀选项就会让旧脚本报 ambiguous。
5. **「`-n 3` 和 `-n3` 行为一样」**——对必需参数是的；对 `optional_argument` 长选项，`--color always` 不会把 `always` 当参数，必须写 `--color=always`。
:::

### 2.1.13 小结

一个解析器的好坏，出错那一次才看得出来。`opterr = 0` 把措辞权拿回自己手里，`':'` 与 `'?'` 分成两个分支：前者是「这个选项要带参数」，后者是「不认识的选项」，提示不同但都属于用法错，退出码要和真正的运行失败分开。数字参数交给 `strtol`，并检查 `errno`、结尾字符和范围，`atoi` 出错时什么都告诉不了你。`optarg` 指向 `argv` 内部，可以读、不要 `free`；`optind` 之后全是操作数，`--` 是留给用户的逃生门，让 `-n` 这样的字符串能当文件名。两个依赖要躲开：GNU 默认重排 `argv`，看着方便，代价是同一行命令在 BSD 或 `POSIXLY_CORRECT=1` 下含义变了；长选项缩写只在唯一前缀时有效，将来新增一个同前缀选项就会让旧脚本报 ambiguous。`optind`/`optarg`/`optopt` 是全局状态，多线程里别并发解析。如果只记住一件事：**选项与操作数的边界是 `optind`，别把它交给默认行为去猜。**

## 2.1.14 内核路径：`openat` 与 `read` 落到文件系统 {#sec-2.1.14}

这一节回答：从 `openat` 到 ext4 真正读磁盘，中间经过哪些函数？出问题时该在哪个层次加观测？

::: preview 先抓住一件事
`openat` 在内核里只做四件事：翻译标志位、解析路径拿到一个 `struct file`、在 fd 表里占一个号、最后把两者装到一起。`read` 的核心是十几行检查：能不能读、指针像不像用户地址、长度要不要截断，剩下的活交给方法表 `f_op->read_iter`。
:::

2.1.1 给了入口与分派的轮廓。这里把两条最常用的路径补到函数级。

先说口径，因为这两套名字属于两台机器。下面第一张表按 **x86-64 的源码**写（`arch/x86/…`、`do_syscall_64`、`sys_call_table[257]`，257 是 x86-64 的 `openat` 号），来自读源码的形状，**本套件没有 x86 机器，未实测**。本套件的测试机是 aarch64，对应那一列的函数名不是猜的——直接在这台内核（7.0.0-38-generic）上查 `grep -wE 'el0_svc|invoke_syscall|__arm64_sys_read|ksys_read|vfs_read' /proc/kallsyms`，五个符号全部存在，`do_syscall_64` 一个都没有：

```text
t invoke_syscall
T el0_svc
T __arm64_sys_read
T ksys_read
T vfs_read
```

| 层次 | x86-64（读源码的形状，未实测） | aarch64 7.0.0-38（符号在本机可查） |
|:--|:--|:--|
| 硬件入口 | `entry_SYSCALL_64`（`arch/x86/entry/entry_64.S`） | `el0_svc`（同步异常向量，来自 `SVC` 指令） |
| 分派 | `do_syscall_64` → `sys_call_table[257]` | `invoke_syscall` 按 `x8` 里的编号查 `sys_call_table` |
| 系统调用包装 | `__x64_sys_read` | `__arm64_sys_read` |
| VFS（把各种文件系统统一成一套 inode 与文件操作的中间层） | `ksys_read` → `vfs_read` | 同名，`ksys_read` → `vfs_read`（本机可查） |

所以读这两列的正确方式是：**层与层之间的契约相同，符号名与寄存器编号不同**。第 3 篇会展开这张表在内核里怎么长出来。

### `openat` 的路径

| 层次 | 位置 | 关键动作 |
|:--|:--|:--|
| libc | `sysdeps/unix/sysv/linux/openat.c` | 排寄存器、`syscall` |
| 入口 | `arch/x86/entry/entry_64.S` | `entry_SYSCALL_64` 保存寄存器（aarch64 上是 `el0_svc`） |
| 分派 | `arch/x86/entry/common.c` | `do_syscall_64` → `sys_call_table[257]`（aarch64 是 `invoke_syscall`，编号在 `x8`，`openat` 是 56） |
| 系统调用 | `fs/open.c` | `do_sys_openat2`：`build_open_flags`、`getname`、`get_unused_fd_flags` |
| 路径解析 | `fs/namei.c` | `do_filp_open` → `path_openat` → `link_path_walk` |
| 打开 | `fs/open.c` | `vfs_open` → `do_dentry_open` → `file->f_op->open` |
| 文件系统 | `fs/ext4/file.c` | `ext4_file_open`（或 `generic_file_open`） |
| 返回 | `fs/file.c` | `fd_install` 把 `struct file *` 装进 fd 表 |

`do_sys_openat2()` 的形状（删节）：

```c
static long do_sys_openat2(int dfd, const char __user *filename,
                           struct open_how *how)
{
    struct open_flags op;
    int fd = build_open_flags(how, &op);
    struct filename *tmp;

    if (fd)
        return fd;
    tmp = getname(filename);
    if (IS_ERR(tmp))
        return PTR_ERR(tmp);

    fd = get_unused_fd_flags(how->flags);
    if (fd >= 0) {
        struct file *f = do_filp_open(dfd, tmp, &op);
        if (IS_ERR(f)) {
            put_unused_fd(fd);
            fd = PTR_ERR(f);
        } else {
            fd_install(fd, f);
        }
    }
    putname(tmp);
    return fd;
}
```

关键点是**先分配 fd，再打开文件**：`get_unused_fd_flags` 在 fd 表里占一个号，`do_filp_open` 失败就 `put_unused_fd` 归还。这样返回给用户态的 fd 在安装前不会被其他线程抢走。`fd_install` 之后，fd 才真正可用。

### `read` 的路径

| 层次 | 位置 | 关键动作 |
|:--|:--|:--|
| libc | `sysdeps/unix/sysv/linux/read.c` | `syscall(SYS_read, ...)` |
| 系统调用 | `fs/read_write.c` | `ksys_read` → `vfs_read` |
| 检查 | `fs/read_write.c` | `FMODE_READ`、`access_ok`、`rw_verify_area`、`MAX_RW_COUNT` 截断 |
| 文件系统 | `include/linux/fs.h` | `file->f_op->read_iter` |
| ext4 | `fs/ext4/file.c` | `ext4_file_read_iter` → `generic_file_read_iter` |
| 页缓存 | `mm/filemap.c` | `filemap_read` → `filemap_get_pages` → `page_cache_sync_readahead` |
| 缺页/读盘 | `mm/filemap.c` | `filemap_read_folio` → `address_space->a_ops->read_folio` |
| 块层 | `fs/ext4/inode.c` | `ext4_mpage_readpages` / `ext4_bio_write_page` |

`vfs_read()` 的核心只有十几行：

```c
ssize_t vfs_read(struct file *file, char __user *buf, size_t count, loff_t *pos)
{
    ssize_t ret;

    if (!(file->f_mode & FMODE_READ))
        return -EBADF;
    if (!(file->f_mode & FMODE_CAN_READ))
        return -EINVAL;
    if (unlikely(!access_ok(buf, count)))
        return -EFAULT;

    ret = rw_verify_area(READ, file, pos, count);
    if (ret)
        return ret;
    if (count > MAX_RW_COUNT)
        count = MAX_RW_COUNT;
    return file->f_op->read_iter(file, buf, count, pos);
}
```

由此可以解释三个现象：

1. **`read` 的 `count` 超过约 2 GiB 会被截断**。`MAX_RW_COUNT` 是 `INT_MAX & PAGE_MASK`（约 2 GiB），一次 `read` 不可能读更多。
2. **`read` 对只写 fd 返回 `EBADF`**，而不是 `EINVAL`；对不支持读的 fd（如某些设备）返回 `EINVAL`。
3. **坏缓冲区返回 `EFAULT`**，因为 `access_ok` 先拦一层，真正的拷贝失败再由 `copy_to_user` 返回。

`struct file` 里与性能相关的字段：`f_mode`（读/写能力）、`f_flags`（`O_NONBLOCK` 等）、`f_pos`（共享偏移）、`f_op`（方法表）、`f_mapping`（page cache 的 `address_space`）、`f_inode`。`fdget()` 是 `read` 系列的第一步：它把 fd 转成 `struct file *` 并禁止并发关闭；`fdget_pos()` 额外锁住 `f_pos`，用于需要偏移的调用。

### 两张表叠起来看

它们共享同一个结构：**每一层只认上一层给的契约**。`fd_install` 之前，用户态什么也没拿到；之后用户态手里只是一个 `int`，内核侧对应的才是 fd 表里的那个指针。`read` 这一侧同理——`vfs_read` 不知道文件躺在哪个文件系统上，它只调 `file->f_op->read_iter`，ext4、tmpfs、socket 各自填一份方法表（方法表：一组函数指针，表示「这类文件会做哪些动作」）。这正是 2.1.2 那句「语义由内核保证」在代码里的形状：语义写在与文件系统无关的十几行里，具体实现写在方法表里。

一个具体例子能把层次对上。`openat(fd, "a/b", O_RDONLY)` 解析路径时，`a` 与 `b` 各要查一次目录项：缓存里有就直接用，没有才让 ext4 去读那个目录块。同一个 fd 连着 `read` 两次，第二次如果那几页已经在页缓存里，`filemap_read` 直接把数据交出去，块层一次都没去。于是「`read` 很慢」这句话至少可能出在三个地方——路径解析、缺页、真正读盘——加观测的位置由这个分层决定，不是随手在调用前后各取一次时间。

这段路上有两个新手最容易误解的点。一是把 fd 当成文件：fd 只是本进程表里的下标，`fork` 之后父子共享同一个 `struct file`，也就共享 `f_pos`，两边各读一段，读到的是相邻的两段而不是同样的内容。二是把请求量当成承诺量：`count` 超过 `MAX_RW_COUNT` 会被截断，返回的字节数小于你要的数是合法结果，循环续读才是正确写法。两个点都能在表里找到对应的行，但要用得上，得先把「下标、打开文件、索引节点（inode，内核里代表文件本身的那份记录）」三个对象分清。

::: note 为什么 `strace` 看不到 `vfs_read`
`strace` 只观察系统调用边界，看到的是 `read(3, ...) = 12`。`vfs_read`、`filemap_read`、`ext4_file_read_iter` 都在内核里，要观察它们得用 `perf probe`、`bpftrace` 或 `ftrace`。例如：

```bash
sudo bpftrace -e 'kfunc:vfs_read { @[comm] = count(); }'
sudo perf probe -k /usr/lib/debug/boot/vmlinux-$(uname -r) vfs_read
```

符号可能被内联（`vfs_read` 在部分配置下是 `static inline` 或被 LTO 合并），探不到时换 `ksys_read` 或 `__x64_sys_read`。
:::

### 2.1.14 小结

`openat` 在内核里的顺序是：入口查表 → `do_sys_openat2` 翻译标志、把路径字符串取进内核、在 fd 表里占号 → 逐级解析路径拿到 `struct file` → 调文件系统自己的 open → 最后 `fd_install` 安装。占号在前、安装在后是刻意设计：打开失败就 `put_unused_fd` 归还，这个号不会在「已经可用」和「还没打开完」之间被人抢走。`read` 那侧的 `vfs_read` 只做三件检查（能力、地址、长度），真正干活的是 `f_op->read_iter`，所以 `EBADF` 与 `EINVAL` 的分工、超过约 2 GiB 的截断、坏指针的 `EFAULT` 都能在十几行里解释。换内核版本时函数名会变（可能改名、内联或拆分成 `__x64_sys_read` 这类带前缀的入口），层次与契约比名字更值得记。如果只记住一件事：**fd 是下标，`struct file` 才是那个「正打开着的东西」。**

::: method 即时自测 · 2.1.14
**Q1（记忆）** 按顺序说出 `openat` 从进入内核到返回用户态的几个关键步骤，并指出 fd 号是在哪一步占下的、安装在哪一步。

**Q2（辨析）** 读一个只写打开的 fd 返回什么错误？读一个「存在但不支持读」的对象返回什么？为什么 `read(fd, buf, 3GiB)` 不太可能一次给你 3 GiB？

**Q3（应用）** 用户报「打开一个很深目录里的文件很慢」。按本节分层说出你会先怀疑的两层、各用什么手段观察，并解释为什么 `strace` 单独用不够。

::: sol 答案
**A1** libc 的包装按 ABI 排好寄存器陷入 → 内核入口保存现场、按调用号查表 → `do_sys_openat2`：`build_open_flags` 把用户标志翻译成内核标志、`getname` 把路径从用户空间取进来 → `get_unused_fd_flags` 占号 → `do_filp_open`/`path_openat`/`link_path_walk` 逐级解析 → `vfs_open`、`do_dentry_open` 调文件系统的 open → 成功才 `fd_install`，失败则 `put_unused_fd` 归还。号在 `get_unused_fd_flags` 占，安装在 `fd_install`。
**A2** 只写打开的 fd 里没有读能力（`f_mode` 不含 `FMODE_READ`），返回 `EBADF`；fd 有效但对象不支持读时，方法表那层拒绝，返回 `EINVAL`。请求 3 GiB 会被 `MAX_RW_COUNT` 截断，实际最多读到约 2 GiB，所以返回的字节数小于请求长度是合法的短读，不是错误，接着续读剩下的就行。
**A3** 先怀疑路径解析这一层：每级目录都要查目录项，缓存里没有就得读盘，用 `namei -l` 看哪一级慢、`ls -di` 看目录项在不在缓存。再怀疑缓存与块层这一层：首次访问才真正读盘，热读时 `filemap_read` 直接返回。`strace` 只看得见最外面那道门——它能告诉你这次 `openat` 花多久、返回哪个错误码，但分不清时间花在解析、缺页还是读盘；往里要看内核函数，得换 `perf`/`bpftrace` 这类探针，而且符号可能已被内联。

## 2.1.15 两个实验：用 `strace` 与 `/proc` 拿证据 {#sec-2.1.15}

这一节回答：怎么在不改代码、不装调试器的情况下，看清一个程序到底调了哪些系统调用、fd 处于什么状态？

::: preview 先抓住一件事
不改代码拿证据有两条路：`strace` 站在系统调用边界上，看得见哪次调用失败、返回哪个错误码，还能注入一个假错误去走错误分支；`/proc` 站在进程里面，看得见 fd 指向什么、偏移到哪、正卡在哪个调用号。两条都看不见内核函数的内部。
:::

### 实验一：`strace` 看文件打开与 fd 复用

```bash
strace -f -yy -s 128 -e trace=%file,%desc ./limits2 2>&1 | head -30
```

`-f` 跟线程/子进程，`-yy` 把 fd 翻译成路径，`-s 128` 放宽字符串截断，`-e trace=%file,%desc` 只看文件与 fd 相关调用。典型输出：

<div class="terminal" data-title="bash · ubuntu 24.04.5 / aarch64 · strace 6.8（实测）">
<pre><span class="p">&#36;</span> strace -yy -e trace=%file,%desc ./limits2 2&gt;&amp;1 | head -14
execve("./limits2", ["./limits2"], 0xffffc86b0f90 /* 17 vars */) = 0
openat(AT_FDCWD&lt;/tmp/lab2c01&gt;, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3&lt;/etc/ld.so.cache&gt;
openat(AT_FDCWD&lt;/tmp/lab2c01&gt;, "/lib/aarch64-linux-gnu/libc.so.6", O_RDONLY|O_CLOEXEC) = 3&lt;/usr/lib/aarch64-linux-gnu/libc.so.6&gt;
openat(AT_FDCWD&lt;/tmp/lab2c01&gt;, "/tmp", O_RDONLY|O_CLOEXEC|O_DIRECTORY) = 3&lt;/tmp&gt;
pipe2([3&lt;pipe:[300064]&gt;, 4&lt;pipe:[300064]&gt;], 0) = 0
fcntl(4&lt;pipe:[300064]&gt;, F_GETPIPE_SZ)   = 65536
close(3&lt;/tmp&gt;)                          = 0
close(4&lt;pipe:[300064]&gt;)                 = 0
</pre>
</div>

读法：

- `= 3` 后面的 `</etc/ld.so.cache>` 是 `-yy` 的功劳，说明 fd 3 被复用：动态链接器关闭后，`/tmp` 又拿到 3。**fd 号是复用的**，日志里只记数字会指错对象。
- `O_RDONLY|O_CLOEXEC|O_DIRECTORY` 是 `strace` 解码**用户态这一次调用真正传进去的位**（打印顺序由 strace 版本决定，别把它当字节级格式背）。这里不会出现 `O_LARGEFILE`：aarch64 的用户态把它定义成 0，64 位 ABI 不需要应用传这个位；可同一个 fd 在 `/proc/self/fdinfo` 那一格里却有 `0400000`——那是内核内部的 `f_flags` 带上的同名位。两个视图回答的不是同一个问题，读 `flags` 时按 2.1.15 的差法逐位对照，别把两边当成同一次调用的重复表述。
- `pipe2([...], 0)` 这一行纠正了一个很常见的说法。程序里调的是 `pipe()`，`strace` 却打出 `pipe2`——glibc 2.39 在 aarch64 上确实把 `pipe()` 实现成 `pipe2(..., 0)`，**但第二个参数是 0，没有 `O_CLOEXEC`**。同一程序里显式调用 `pipe2(p, O_CLOEXEC)` 的那一行才会打出 `O_CLOEXEC`。所以「`pipe()` 原子地设置 close-on-exec」在这台机器上不成立：它仍然是一次 `pipe2` 加之后单独的 `FD_CLOEXEC` 设置（如果代码自己去设的话）；把「原子」当成默认保证，`fork`+`exec` 的窗口就还在。
- 失败行会写成 `= -1 ENOENT (No such file or directory)`；`ENOENT` 是符号名，括号里是 `strerror` 文本。

常用变体：

```bash
# 只统计耗时与调用次数
strace -c -e trace=openat,read,write ./limits2

# 只看某个路径
strace -e trace=openat -P /etc/hosts ./limits2

# 故障注入：让第一次 openat 返回 EACCES，验证错误分支
strace -e inject=openat:error=EACCES:when=1 ./limits2
```

`-e inject` 是测试错误路径的利器：不用改代码、不用造权限，就能让 `openat` 返回指定 `errno`。注意 `when=1` 是「第 1 次匹配」，`+` 后缀可表示「从第 N 次起每次都注入」（如 `when=2+`）。

### 实验二：`/proc/self/fdinfo` 读 fd 状态

`/proc/self/fd` 给的是符号链接，`/proc/self/fdinfo/N` 给的是**这个 fd 的内核状态**：

```bash
exec 3</etc/hosts
cat /proc/self/fdinfo/3
# pos:    0
# flags:  0400000
# mnt_id: 35
# ino:    2755550
```

`pos` 是这个 fd 在内核 `struct file` 里的当前偏移（读 20 字节之后再 cat 一次就变 20，`lseek` 到 42 就变 42）；`mnt_id` 是挂载 ID，能和 `/proc/self/mountinfo` 第一列对上（本机 35 那条正是根挂载 `ext4 /dev/sda2`）；`ino` 是 inode 号，和 `stat -c %i /etc/hosts` 一致。**这两个数是机器身份**：换一台机器、甚至重新挂载一次都会变，绝不能当常数抄进笔记或用来跨机器比对。

`flags` 是八进制的打开标志，也是**照抄别处读数最容易翻车的一格**。这台机器上只读打开 `/etc/hosts` 得到 `0400000`，可你写 `printf("%o", O_LARGEFILE)` 得到的是 **0**——同一个名字在两边不是一回事。原因：这一格打印的是内核里的 `f_flags`，它带着内核自己加的位（内核 UAPI 头 `asm/fcntl.h` 把 `O_LARGEFILE` 定义为 `0400000`，用于内核内部），而 aarch64 的用户态 `<fcntl.h>` 把它定义成 0，因为 64 位 ABI 根本不需要应用程序传这个位。同一个 fd 在 `strace` 里那条 `openat` 也确实只显示 `O_RDONLY|O_CLOEXEC`。

**所以逐位念 `flags` 不能靠记忆，要用差法**：拿两个只差一个标志的 fd，看这一格多了哪一位。同一台机器上实测（`/etc/hosts` 不可写，写模式改用自建文件）：

| 打开方式 | `fdinfo` 的 `flags` | 与你传的标志差多少 |
|:--|:--|:--|
| `O_RDONLY` | `0400000` | 基线（内核自己那一位总在里面） |
| `O_WRONLY` | `0400001` | +1，就是 `O_WRONLY` |
| `O_RDWR` | `0400002` | +2 |
| `O_RDWR\|O_APPEND` | `0402002` | `O_APPEND` 是 `02000` |
| `O_WRONLY\|O_TRUNC` | `0400001` | 看不出 `O_TRUNC`（`01000`）——它只作用在打开那一刻，不作为状态保留 |
| `O_RDWR\|O_DIRECT` | `0600002` | `O_DIRECT` 是 `0200000` |
| `O_RDONLY\|O_CLOEXEC` | `02400000` | `O_CLOEXEC` 是 `02000000` |

对照用的本机用户态宏值（`cc -dM -E -include fcntl.h` 查得，需要 `_GNU_SOURCE` 才看得到 `O_DIRECT`/`O_NOFOLLOW`）：`O_APPEND=02000`、`O_DIRECT=0200000`、`O_NOFOLLOW=0100000`、`O_DIRECTORY=040000`、`O_CLOEXEC=02000000`、`O_LARGEFILE=0`。注意 `0100000` 这一位在 aarch64 的用户态是 `O_NOFOLLOW`；很多 x86-64 资料把 `flags: 0100000` 解释成 `O_LARGEFILE`（x86 上该位确实是 `00100000`，那条属于另一套表，本套件没有 x86 机器、未实测），在 ARM64 上照抄就把含义念反了。

```bash
# 十六进制/八进制互转，确认 flag 位
printf '%o\n' 0x241    # 1101
cat /proc/self/mountinfo | awk -v id=28 '$1==id'
```

另一个有用的文件是 `/proc/self/syscall`：它显示当前线程**正在执行**的系统调用号与参数。对一个阻塞在 `read` 的进程：

```bash
$ cat /proc/self/syscall
63 0x3 0xfffff699cebf 0x1 0x0 0x0 0xfffff699cda7 0xfffff699ce80 0xf6ea6938124c
$ cat /proc/self/wchan
anon_pipe_read
```

第一列是**当前正在执行的调用号**：这台 aarch64 机器上 `63` 就是 `read`（x86-64 上是 0，别把两台的数当同一个），后面依次是参数寄存器 `x0…x5`（`0x3` 是 fd、`0x1` 是要读的字节数）、栈指针与程序计数器。这个进程正是主线程卡在管道 `read` 上、由另一个线程采样得到的，旁边那条 `wchan` 直接给出内核里的等待函数名 `anon_pipe_read`——两行合起来就回答了「它卡在哪个调用、卡在哪个等待点」。

`self` 这个字在这里救了我们一次：跨进程读会被拒。同一台机器上读别人的进程得到的是原文报错，不是空文件：

```text
$ cat /proc/73964/syscall
cat: /proc/73964/syscall: Operation not permitted
$ cat /proc/sys/kernel/yama/ptrace_scope
1
```

`ptrace_scope=1` 意味着非 root 只能跟踪自己的子进程，而 `syscall` 这一格按同样的规则把关。所以「用 `cat /proc/<pid>/syscall` 巡检别人的进程」这类脚本在本机免 `sudo` 是跑不通的——要这个能力就得起 `ptrace` 附加权限的工具（`strace -p` 同样受限），或者以同一用户身份从父进程发起。

两个工具各自还有一个必须先答的问题。`strace` 是附加在被观察进程上的，它会让每一次调用都变慢，所以别拿被 `strace` 跑过的耗时去说「程序本来就这么慢」；attach 到别人的进程需要权限，容器里还常因为缺 `ptrace` 能力直接被拒。`/proc/self` 这个名字更容易骗人：`self` 永远是「正在读它的那个进程」。在 shell 脚本里 `cat /proc/self/fdinfo/3`，看到的是 shell 自己的 fd，不是你调试的那个程序；要查别人就写成 `/proc/PID/...`。

::: method 用证据定位「打开失败」

### 2.1.15 小结

`strace -yy` 的价值在于把 fd 号翻译回路径：fd 是复用的下标，动态链接器刚关掉的 3 号，下一秒可能就是 `/tmp`，日志里只留数字迟早指错对象。`-e inject=openat:error=EACCES:when=1` 让你在不动权限、不造文件的前提下走一遍错误分支，这是检查「错误处理有没有真的写对」最便宜的办法，`when=` 决定注入第几次。`/proc/self/fdinfo/N` 给的是内核里那份状态——`pos` 是这个 fd 的当前偏移（`fork` 后父子共享的就是它），`flags` 用八进制写打开标志，`mnt_id` 能和 `mountinfo` 对上；`/proc/self/syscall` 给的是此刻正在执行的调用号与参数寄存器，用来回答「它卡在哪个调用」。两条路的分工是：先在系统调用边界确认哪次调用失败，再进 `/proc` 确认那个 fd 的真实身份。如果只记住一件事：**fd 号会复用，凡是要留日志，就在它还在的时候把身份记下来。**

## 2.1.16 本章陷阱清单 {#sec-2.1.16}

这一节回答：十几节的坑散在各个 API 旁边，如果只让你记三条规律，是哪三条？提交代码之前该按什么顺序回头查？

::: preview 先抓住一件事
这些坑没有一个是语法错误，全是「把 A 层的保证当成了 B 层的保证」：把 fd 当布尔、把 `errno` 当当前状态、把 `sysconf` 当系统总量、把调用号当常量。认出认错的那一层，坑就自己缩小了。
:::

前面各节的 `errata` 分散在具体 API 旁。这里按「现象 → 原因 → 修复」把跨节陷阱按主题分成三组，作为提交前的检查表。

::: errata fd、`errno` 与类型假设的五个坑
1. **现象**：`if (!fd) { /* 当成失败 */ }`，偶尔把成功当失败。**原因**：fd 0 是合法描述符（stdin）。**修复**：判断 `fd == -1`，不要用真假值。
2. **现象**：`errno` 打印出来是上一次的错误。**原因**：成功不清 `errno`，且 `printf` 可能改写它。**修复**：失败后立刻保存 `int saved = errno`。
3. **现象**：换到 ARM 机器后 `getchar` 循环不结束。**原因**：`char` 无符号，`EOF`(-1) 变成 255。**修复**：用 `int` 接返回值。
4. **现象**：`printf("%d", strlen(s))` 在 64 位下输出负数。**原因**：`size_t` 是无符号 64 位，`%d` 按 32 位有符号解释。**修复**：用 `%zu`。
5. **现象**：32 位程序 `stat` 大文件返回 `EOVERFLOW`。**原因**：`off_t` 是 32 位。**修复**：`-D_FILE_OFFSET_BITS=64`，并用 `_Static_assert` 锁住。
:::

::: errata 特性宏、ABI 与资源限制的四个坑
1. **现象**：`syscall(0, ...)` 在 ARM 上行为诡异。**原因**：写死了 x86-64 的调用号。**修复**：用 `SYS_read` 等宏。
2. **现象**：`_SC_OPEN_MAX` 与 `ulimit -n` 不一致。**原因**：可能查询的是另一个进程/另一 libc，或查询后软限制被改。**修复**：以 `getrlimit(RLIMIT_NOFILE)` 为准。
3. **现象**：`strerror_r` 编译报「返回类型不匹配」。**原因**：GNU 版与 XSI 版签名不同。**修复**：用 `strerror_l`，或按 `_GNU_SOURCE` 分支。
4. **现象**：定义了 `_POSIX_C_SOURCE` 后 `strdup`/`accept4` 找不到声明。**原因**：显式 POSIX 宏关闭了 `_DEFAULT_SOURCE`。**修复**：加 `_DEFAULT_SOURCE`/`_GNU_SOURCE`，或用编译命令统一。
:::

::: errata 环境与跨层组合的三个坑
1. **现象**：`access(path, W_OK)` 通过，`open` 却 `EACCES`。**原因**：`access` 用 real UID，`open` 用 effective UID；或检查与打开之间有 TOCTOU。**修复**：直接 `open` 并处理错误；需要按 effective 检查时用 `faccessat(..., AT_EACCESS)`。
2. **现象**：容器里 `openat` 对合法路径返回 `EPERM`。**原因**：seccomp 过滤器返回 `EPERM`，不是文件权限。**修复**：查 `docker inspect` 的 `SecurityOpt`/`seccomp`，或 `strace` 确认调用被拦。
3. **现象**：子进程 `exit()` 后日志重复。**原因**：`fork` 复制了 stdio 缓冲区，父子各 flush 一次。**修复**：`fork` 前 `fflush`，子进程用 `_exit`（详见 [2.4](ch04.md)）。
:::

这三组坑的共同点是：**错误不在语法，而在对「谁保证什么」的误解**。ABI 保证调用号与寄存器，libc 保证 `errno` 翻译，内核保证 `-errno` 与 `EFAULT`；越过任何一层做假设，都会在换架构、换 libc、换内核时暴露。

三组的排查成本也差得很远。第一组（fd、`errno`、类型假设）在换编译器或换架构时暴露，症状直接：循环不结束、`%d` 打出负数，通常一小时内定位。第二组（特性宏、ABI、资源限制）在换构建配置时暴露，症状是「能编能跑但行为怪」，最难查——隐式声明让编译器替你猜参数，读到的限制与实际生效的限制差一个数量级时，你只会觉得「有时候够用」。第三组（环境与跨层）在换部署环境时暴露，症状最像 bug 却最不是 bug：`access` 与 `open` 用的身份不同，seccomp 能把调用拦成 `EPERM`，`fork` 前没 flush 的缓冲区让日志重复一遍。

一次演练能把三组串起来。程序在开发机上一直正常，换到容器里变成「日志偶尔少一半」。`strace -f -yy` 看到某个 fd 上的 `write` 返回 `EAGAIN`（第一组：非阻塞 fd 上的短写没处理，续写的循环缺了）；`/proc/PID/limits` 显示软限制只有启动器给的那点，和开发机的 `ulimit -n` 不是一个数（第二组：把 `_SC_OPEN_MAX` 当成两边一样的常数）；`dmesg` 里还有一条 seccomp 记录（第三组：看着像权限问题，其实是被过滤器拦下）。三个原因叠在一个现象上，收拾它们的不是背坑表，而是每次都先问「这条保证是谁给的」。

### 2.1.16 小结

十二个坑分三组，分组标准不是 API，而是「谁保证什么」。第一组是语言与内核之间的约定：0 是合法的 fd，所以判失败要写 `== -1`；`EOF` 要用 `int` 接；`size_t` 要配 `%zu`。第二组是 libc 与本进程之间的约定：成功不清 `errno`，`_SC_OPEN_MAX` 只是软限制的另一种读法，`strerror_r` 的签名跟着特性宏变。第三组是运行现场：real 与 effective 身份不同，seccomp 会把调用变成错误码，`fork` 会连缓冲区一起复制。三组暴露的时机不同——换编译器、换构建配置、换部署环境——症状也不同：立刻错、能跑但怪、看着像 bug。回头检查按这三组走就够了。如果只记住一件事：**每个坑都是把 A 层的保证当成了 B 层的保证。**

**Q3（应用）** 写出你自己版本的「提交前三查」：每查配一条命令或一个编译选项，说明它抓的是哪一组。

::: sol 答案
**A1** 第一组是 fd、`errno` 与类型假设，例如「用 `if (!fd)` 判失败」或「用 `char` 接 `getchar` 的返回值」。第二组是特性宏、ABI 与资源限制，例如「写死系统调用号」或「把 `sysconf(_SC_OPEN_MAX)` 当系统总量」。第三组是环境与跨层组合，例如 `access` 与 `open` 之间的竞态（TOCTOU，检查完再到打开之间状态可能被改掉）、`fork` 前不 flush 导致日志重复。
**A2** 前两处：`access` 按 real UID 判断，`open` 按 effective UID 执行，setuid 程序上两者分开；检查与打开之间还有一个窗口，路径或权限可能在这中间被改掉。后一句错在把两个不同东西当同一个：`_SC_OPEN_MAX` 反映查询那一刻某个进程的软限制，可能查的是另一个进程、另一个 shell，或者查完之后有人改了限制；不一致不代表坏，代表你问的对象不对，该用 `getrlimit` 现查现用。
**A3** ①换编译器与换架构这一查：CI 里同时编 32 位与 64 位（或交叉编 aarch64），并开 `-Wall -Wextra -Werror`，抓第一组的类型假设和第二组的隐式声明。②构建配置这一查：把 `-std=c17 -D_GNU_SOURCE` 固定成一条命令，再用 `_Static_assert` 把 `off_t`、`time_t` 的宽度写死成断言，宏忘了就编不过。③现场这一查：在容器与真机各跑一次 `cat /proc/self/limits` 和 `strace -f -yy`，比对软限制与真实调用，抓第二组的限制读法与第三组的环境差异。
:::
:::

## 2.1.17 本章小结 {#sec-2.1.17}

这一节回答：十七节读完，你手上多了哪几样能验证的能力？哪一段还只是「认得名词」？

::: preview 先抓住一件事
这一章只留下三样东西：一条穿过特权级的路径、一个「先看返回值再读 `errno`」的习惯、一套「常数不许写死」的纪律。判据是——给你一个「在我这儿好好的」的现场，你能说出哪一层在骗你，并用一条命令证实。
:::

**第一段，边界与失败（2.1.1–2.1.4）。** 一次 `read` 走六步：libc 排寄存器、陷入指令切特权级、内核入口按号查表、实现干活、结果放回返回值寄存器、libc 把负数翻成 `-1` 加 `errno`。这条路径回答的是「什么才算系统调用」。失败那一侧：`errno` 只在返回值表明失败之后才有意义，成功不清零，打印之前先保存；`errMsg`、`errExit`、`errExitEN` 按「调用者还能不能恢复」分三层。这一段立的是**读法**——怎么读一条路径、怎么读一个错误。

**第二段，不把平台写死（2.1.5–2.1.8）。** 头文件只在你声明了标准等级时才把接口交给你，所以特性宏是契约而不是编译选项。限制要运行时查：`sysconf` 看系统、`pathconf` 看文件系统，返回 `-1` 还分「不确定」与「查询失败」两种。`uname`、`/proc`、`sysfs` 是拿现场证据的地方，2.1.8 把这些压成提交前的检查清单。这一段立的是**纪律**——哪个数不许写死、哪句话不许靠猜。

**第三段，深水区与取证（2.1.9–2.1.16）。** 前一半把规则推到接口级：调用号与参数寄存器是架构的 ABI，六个用满就改成传一个带 `size` 的结构体；错误码的后半程是转文本、认别名、换对外协议；特性宏不只管声明可见性，还管 `off_t` 与 `struct stat` 的布局；三层 fd 限制里程序该按软限制分配；`getopt_long` 把「我这能跑」变成能规定的退出码与用法。

后一半往里看：`do_sys_openat2` 与 `vfs_read` 解释 `EBADF`、`EFAULT` 和短读从哪一层来；`strace` 与 `/proc` 教你不改代码就拿到证据；2.1.16 把跨节陷阱按「谁保证什么」归成三组。这一段立的是**追问**——现象出现时先定位层次，再选工具。

逐条打勾的达标表已移交章末的[学习目标自检表](ch01-checklist.md)，正文不再挂表。留在这里的是三条判据：

- **能解释**：`-errno` 与「`-1` 加 `errno`」分属哪两层；vDSO 为什么不算一次陷入；`sysconf` 返回 `-1` 的两种含义；`_FILE_OFFSET_BITS=64` 为什么会改变结构体大小；`accept4` 比 `accept` 再加两次 `fcntl` 多保证了什么。
- **能操作**：写出保存并还原 `errno` 的 `errMsg`；同一个文件分别用 `-D_POSIX_C_SOURCE=200809L` 与 `-D_GNU_SOURCE` 各编一次，看懂报错出在哪一层；用 `sysconf`、`pathconf`、`getrlimit` 现查限制；用 `strace -e inject=` 注入一次失败，确认错误分支真的被执行到。
- **能判断**：这个错误调用者能不能恢复；三个数里哪个是本进程的上限、哪个是系统的；这段代码换架构或换 libc 会不会坏；一个读数属于哪台机器，能不能拿来当证据。

如果只记住一件事：**每次调用都先问「谁保证这个语义」，每个常数都先问「它在哪台机器上成立」。这两个问题问完，本章的内容就都用上了。**

::: errata 本章的口径边界
1. **读数只属于它那台机器**：本章的耗时、调用号、页数、fd 上限都来自具体一台机器与一个内核，读数块上标的架构与版本就是它的适用范围；跑测量的机器是 Ubuntu 24.04.5 的 aarch64 环境。系统调用号、页大小、`_SC_*` 这类数值换架构就换数，别当 Linux 的常数抄。若某个读数块标的架构与测量机不同，按那个块自己的标注读，不要与别的块混着用。
2. **形状而不是读数**：2.1.14 的两张路径表来自内核源码的层次与命名，属于「读源码得到的形状」，内核版本不同就可能改名、拆分或被内联；`strace`、`fdinfo` 的输出格式也随版本变化。这类内容要带走的是「先查哪一层」，不是某个字段名。
3. **只按语义描述、未逐项量化的部分**：`-e inject=` 的错误注入、`prlimit` 跨进程改限制、容器里 seccomp 把调用变成 `EPERM`，本章讲清楚它们各自发生在哪一层、怎么验证，但没有给出每台机器的具体记录；动手步骤与验收标准放在自检表和习题集里。
:::

::: method 即时自测 · 2.1
**Q1** 一次 `read` 从用户代码到返回，错误码在哪一步被翻译？`clock_gettime` 通常比 `getpid` 快一个数量级，这和「系统调用要陷入内核」矛盾吗？

**Q2** `open` 成功返回后 `errno` 一定是 0 吗？为什么 `errExit` 要在 `fprintf` 之前先保存它？举一个不保存就会把原因印错的场景。

**Q3** glibc 上 `sysconf(_SC_OPEN_MAX)` 返回的到底是什么？为什么不能把它当成「这台机器能打开的文件总数」？要现查该用哪个接口？

**Q4** 编译命令只给 `-D_POSIX_C_SOURCE=200809L` 时 `accept4` 报隐式声明，链接却成功。为什么链接能成功？运行时可能出什么事？宏为什么建议写在命令行而不是源文件第一行？

::: sol 答案
**A1** 翻译发生在最后一层、在 libc 里：内核侧返回的是 `-errno`（`-2` 就是 `ENOENT`），glibc 的包装函数检查返回值，把它换成 `-1` 并写 `errno`。不矛盾——`clock_gettime` 对常见时钟走 vDSO，那是内核映射进每个进程地址空间的一小段代码，运行在用户态、读内核维护的共享数据，全程没有特权级切换，严格说它不是一次系统调用，但语义仍由内核保证；`getpid` 没有这条捷径，每次都要陷入。
**A2** 不一定。POSIX 只要求失败时设置 `errno`，不要求成功时清零，所以它可能还是很久以前那次失败留下的值。`fprintf`、`strerror` 内部可能调 `malloc`、`write` 或 locale 相关函数，这些都可能改写 `errno`：`open` 留下 `ENOENT`，`fprintf` 为分配缓冲区失败把它改成 `ENOMEM`，于是打印出「Cannot allocate memory」，真实原因丢了。做法是入口 `int saved = errno`，打印用 `saved`，返回前还原。
**A3** 本进程 `RLIMIT_NOFILE` 的软限制。它不是系统总量：上面还有 `fs.nr_open`（单个进程能拿到的号的天花板）与 `fs.file-max`（全系统），别的进程也在占用，而且软限制随时可能被 `setrlimit` 改掉。现查现用要么 `getrlimit(RLIMIT_NOFILE, &rl)` 读软硬两值，要么 `cat /proc/self/limits`。
**A4** 因为共享库里确实有 `accept4` 这个符号，链接器按名字就能找到；编译期没看到声明，就按 C 的隐式声明规则把它当成「返回 `int`、参数表未知」的函数。参数里一旦有指针或 64 位整数，或者换到另一种调用约定的架构，参数就会被错解，行为未定义——「碰巧能跑」不是证据。宏必须生效在第一个系统头文件之前：`<features.h>` 只在第一次被包含时算完那些开关，源文件里补定义会被一次意外的前置 `#include` 废掉，命令行则从翻译单元第 0 个字符就生效。
:::
:::
