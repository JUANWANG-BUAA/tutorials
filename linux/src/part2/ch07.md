到 [2.6](ch06.md) 为止，我们处理的对象都是「一个进程内部的文件」。从这一章开始，主角变成**进程本身**：它怎么被创建、怎么结束、结束后谁来收尸。

Unix 的进程模型只有两个原语：`fork()` 复制当前进程，`execve()` 用新程序替换当前进程的地址空间（[2.8](ch08.md)）。所有 shell、服务管理器、容器运行时，都是这两条原语加 `wait()` 的组合。理解它们的语义边界，比记住参数列表重要得多：`fork()` 的「复制」是逻辑上的，物理内存靠 COW 延迟分配；`exit()` 的「结束」也不是一瞬间，进程会先变成僵尸，等父进程确认后才真正消失。

这一章的主线是「**创建与销毁都是协议，不是函数调用**」。父子之间有继承规则（fd、信号、凭证）、有通知机制（`SIGCHLD`）、有回收义务（`wait`）。任何一环漏掉，症状都不是报错，而是资源慢慢泄漏：僵尸堆积、fd 泄漏、内存翻倍。

## 2.7.1 `fork()` 的返回值与继承清单 {#sec-2.7.1}

这一节回答：`fork()` 调用一次为什么返回两次？父子之间哪些东西是复制的、哪些是共享的、哪些被清零？

::: preview 先抓住一件事
`fork()` 的返回值是父子两条执行路径的唯一分岔口：同一行代码之后，父进程拿到子进程 PID、子进程拿到 0，两边从此各走各的。而「复制」这个词要拆成三类才准确——复制的是 fd 表、页表（page table：记录虚拟地址到物理页映射的那张表）、凭证、信号掩码；共享的是 fd 表项指向的打开文件描述（所以文件偏移是同一个）、`MAP_SHARED` 的物理页；清零的是未决信号和定时器。判据很实用：凡是「清零」的东西，子进程里都要重新设置；凡是「共享」的东西，一方改动另一方立刻看得见。
:::

::: def 定义 2.7.1 · `fork()` 的语义 {#def-2.7.1}
`pid_t fork(void)` 创建一个新进程。调用一次，返回两次：

- 父进程中返回**子进程 PID**（`> 0`）；
- 子进程中返回 **0**；
- 失败时父进程返回 `-1`，`errno` 为 `EAGAIN`（进程数或 `RLIMIT_NPROC` 超限）、`ENOMEM`（内核内存不足）或 `ENOSYS`（平台不支持）。

子进程是父进程的**逻辑副本**：地址空间按 COW 共享物理页，fd 表被复制但表项指向同一个打开文件描述，信号处置被继承，未决信号被清空。
:::

最小可用的创建与回收：

```c
pid_t pid = fork();
if (pid == -1) {
    perror("fork");
    exit(EXIT_FAILURE);
}
if (pid == 0) {
    /* 子进程：这里只能看到自己 */
    _exit(0);
}
/* 父进程：pid 是子进程号 */
int status;
if (waitpid(pid, &status, 0) == -1) {
    perror("waitpid");
    exit(EXIT_FAILURE);
}
```

`fork()` 之后，父子是两个独立的调度实体，谁先运行由调度器决定。**不要假设子进程先跑或父进程先跑**：这是 [2.7.6](#sec-2.7.6) 里竞争条件的根源，也是 shell 管道实现必须小心的地方。

### 继承清单

「复制」这个词太粗。内核在 `copy_process()` 里逐项决定：哪些复制、哪些共享、哪些清零。

| 对象 | `fork()` 后 | 说明 |
|:--|:--|:--|
| 地址空间 | COW 共享物理页 | 页表复制，PTE 只读；写时复制 |
| fd 表 | 复制，表项指向同一 `struct file` | 共享偏移与文件状态标志；`FD_CLOEXEC` 位也被复制 |
| 文件锁（`fcntl` 记录锁） | **不继承** | 子进程不持有父进程的记录锁 |
| `flock()` 锁 | 继承（共享同一 open file description） | 与记录锁语义不同，见 [2.3](ch03.md) |
| 信号处置 | 继承 | `SIG_IGN`/处理器地址都复制 |
| 未决信号 | **清空** | 子进程从空信号集开始 |
| 信号掩码 | 继承 | `sigprocmask` 的设置跟着走 |
| 定时器 | **不继承** | `alarm`/`setitimer` 在子进程中清零 |
| 进程组、会话 | 继承 | 子进程在同一进程组；`setsid` 要自己调 |
| 资源限制 | 继承 | `RLIMIT_*` 复制 |
| 凭证 | 继承 | UID/GID 四件套与 capability 都复制（[2.9](ch09.md)） |
| `umask`、`cwd`、`chroot` | 继承 | 都复制 |
| 内存映射 `MAP_SHARED` | 共享同一物理页 | 子进程写入父进程可见，**不触发 COW** |

这张表解释了三类高频 bug：子进程「莫名其妙」写到了父进程的共享映射；父进程的 `alarm` 在子进程里消失导致超时不生效；子进程继承了大量没关的 fd，把下游程序的输入卡住。

::: errata 关于 `fork()` 的五个误解
1. **「`fork` 会把父进程内存复制一份」**——逻辑上复制，物理上共享。只有某一方写入的页才复制，见 [2.7.2](#sec-2.7.2)。
2. **「父子进程的 fd 是各自独立的」**——fd 表独立，但表项指向同一个 `struct file`，**文件偏移共享**。父进程读 100 字节，子进程的 `read` 从 101 开始。
3. **「`fork` 后子进程会收到父进程未处理的信号」**——未决信号被清空。父进程阻塞着的 `SIGUSR1` 不会传给子进程。
4. **「`fork` 会继承父进程的 `alarm`」**——不会。定时器在子进程中清零，这是 `SIGALRM` 超时逻辑在 fork 后失效的原因。
5. **「`fork` 失败只会因为内存不够」**——`EAGAIN` 更常见：`RLIMIT_NPROC`、cgroup（control group：内核按组限制资源用量的机制）的 `pids.max`、全局 `kernel.pid_max` 都会触发。
:::

### 本机实测：fork 之后到底谁先跑

「不要假设谁先跑」这句话光说没有说服力，量一次就有。裁判办法是**让父子各往同一个管道写一个字节**，父进程等子进程退出后按到达顺序读回来：单字节写在管道上是原子的，所以字节顺序就是谁先调用 `write` 的顺序，不受打印缓冲干扰。

```c
/* fork_first.c — fork 之后谁先跑：用管道字节到达顺序当裁判，数 N 轮 */
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

int main(int argc, char **argv)
{
    int n = (argc > 1) ? atoi(argv[1]) : 200;
    if (n <= 0) n = 200;
    int p[2];
    if (pipe(p) == -1) { perror("pipe"); return 1; }

    int parent_first = 0, child_first = 0;
    for (int i = 0; i < n; i++) {
        pid_t pid = fork();
        if (pid == -1) { perror("fork"); return 1; }
        if (pid == 0) {
            if (write(p[1], "C", 1) != 1) _exit(1);
            _exit(0);
        }
        if (write(p[1], "P", 1) != 1) { perror("write P"); return 1; }
        int st = 0;
        if (waitpid(pid, &st, 0) == -1) { perror("waitpid"); return 1; }
        char b[2] = {0, 0};
        if (read(p[0], b, 2) != 2) { perror("read"); return 1; }
        if (b[0] == 'P') parent_first++;
        else if (b[0] == 'C') child_first++;
        else { fprintf(stderr, "unexpected byte %d\n", (int)b[0]); return 1; }
    }
    printf("rounds=%d parent_first=%d child_first=%d\n", n, parent_first, child_first);
    close(p[0]);
    close(p[1]);
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 fork_first.c -o fork_first
./fork_first 1000
# rounds=1000 parent_first=991 child_first=9
./fork_first 1000
# rounds=1000 parent_first=999 child_first=1
```

两行都是 ubuntu 24.04.5 / aarch64（内核 7.0.0-38-generic）本机实测。读法是：**父进程先跑是常态，但不是规律**——1000 轮里出现了 9 次和 1 例子进程先跑，而且两轮的例外次数还不一样。任何依赖「父进程一定先执行完这几行」的代码，出错概率就是这千分之几，在长跑服务里等于必然出错。要保证顺序只能显式同步：`waitpid`、管道消息、信号量或文件锁（[2.7.6](#sec-2.7.6)、[2.15](ch15.md)）。

顺带核一件容易被抄错的事：老资料里说可以用 `/proc/sys/kernel/sched_child_runs_first` 切换这个默认行为，**本机内核上这个文件不存在**（`cat` 报 `No such file or directory`，`ls /proc/sys/kernel/ | grep -i child` 为空），所以别把它当可调旋钮写进脚本。再看 `fork()` 在这台机器上到底是哪个系统调用：

```bash
strace -f -e trace=clone,clone3,fork,vfork ./fork_first 1
# clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD,
#       child_tidptr=0xf4ac06558fd0) = 5568
# --- SIGCHLD {si_signo=SIGCHLD, si_code=CLD_EXITED, si_pid=5568, si_status=0, ...} ---
grep -nE '#define __NR_(fork|vfork|clone|clone3) ' /usr/include/asm-generic/unistd.h
# 566:#define __NR_clone 220
# 781:#define __NR_clone3 435
```

本机实测的两点结论：glibc 的 `fork()` 走的是 `clone`（号 220），标志是 `CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD`，不是 `clone3`；而 aarch64 的通用调用号表里根本没有 `__NR_fork` 与 `__NR_vfork`（grep 只命中 clone 与 clone3），这两个接口在用户态是 libc 用 `clone` 拼出来的。子进程退出时父进程收到的 `SIGCHLD` 带着 `si_code=CLD_EXITED`、`si_status=0`，这正是 [2.7.6](#sec-2.7.6) 里 `waitid` 能拿到的那份信息。

### 2.7.1 小结

`fork()` 一次调用返回两次，执行流从返回值那里分成父子两条。失败只在父进程一侧返回 `-1`，最常见的原因是 `EAGAIN`，也就是进程数触到了限制，而不是内存不够。

继承清单按「复制 / 共享 / 清零」三类记，比笼统说「子进程是父进程的副本」准确。fd 表被复制，但表项指向同一个打开文件描述，所以偏移和文件状态标志是共享的：子进程 `lseek` 一下，父进程下次 `read` 的位置就跟着变了。`MAP_SHARED` 的物理页同样共享，写入立刻互相可见。未决信号与定时器则被清零，父进程设的 `alarm` 在子进程里并不存在。

本机实测补了两条容易被老资料带偏的口径。一是 fork 之后父进程先跑只是常态，不是规律：1000 轮里两轮分别出现 9 次和 1 次子进程先跑，所以需要顺序就得显式同步。二是 glibc 的 `fork()` 在 aarch64 上发的是 `clone`（号 220，带 `SIGCHLD`），通用调用号表里没有 `fork` 与 `vfork`。如果只记住一件事，那就是：**父子是两个独立的调度实体，共享的对象要当成「对方随时会改」来设计，需要顺序的地方必须自己同步。**

::: method 即时自测 · 2.7.1
**Q1（记忆）** `fork()` 在父进程、子进程、失败时各返回什么？继承清单里哪两样东西被**清零**、哪一样被**共享**而不是复制？

**Q2（辨析）** 父进程打开一个文件读到偏移 100，然后 `fork()`；子进程 `lseek(fd, 0, SEEK_SET)` 后读 10 字节。父进程接着 `read(fd, buf, 10)` 会从哪个偏移开始？为什么？如果父进程希望互不影响，有哪两种做法？

**Q3（应用）** 本机 `fork_first 1000` 两轮分别得到 `parent_first=991 child_first=9` 与 `999/1`。有人据此说「把循环改成 100 轮就不会出现子进程先跑，所以可以依赖父进程先执行」。请判断这个推理错在哪，并给出两种能保证顺序的做法。

::: sol 答案
**A1** 父进程返回子进程 PID（>0），子进程返回 0，失败时父进程返回 `-1` 并设 `errno`（`EAGAIN`/`ENOMEM`/`ENOSYS`）。被清零的是**未决信号**与**定时器**（`alarm`/`setitimer`）；被共享而不是复制的是 **fd 表项指向的打开文件描述**（因此文件偏移与文件状态标志共享），另外 `MAP_SHARED` 映射的物理页也共享。
**A2** 从偏移 **10** 开始。因为 `fork` 复制的是 fd 表，父子两个 fd 指向同一个打开文件描述，偏移量存在那个描述里而不是 fd 里；子进程把偏移改成 0 再读 10 字节，偏移就变成 10，父进程紧接着读自然从 10 开始。两种做法：① 子进程改用 `pread`（偏移作为参数、不改共享偏移，见 [2.2.14](ch02.md#sec-2.2.14)）；② 父子各自 `open` 一次得到独立的打开文件描述，或在 `fork` 后立刻关掉自己不用的一侧（配合 `FD_CLOEXEC` 防止泄漏给 `exec` 出来的程序）。
**A3** 错在把「频率低」当成「不会发生」。两轮例外次数不同（9 与 1）正说明它取决于调度与系统负载，是不可复现的竞态；轮数少只是降低撞上的概率，长跑服务里累计次数足够多就必然撞上，而且这种 bug 在测试环境几乎抓不到。保证顺序的做法：① 父进程 `waitpid` 等子进程完成后再继续（shell 就是这么做的）；② 用管道/信号量做显式握手——子进程完成动作后写一个字节或 `sem_post`，父进程阻塞读到才往下走；也可以用 `SIGUSR1` 同步，但**必须在 `fork` 之前就阻塞该信号**，否则信号可能在父进程装好处理器之前到达而丢失。
:::

## 2.7.2 写时复制：页表、引用计数与断裂点 {#sec-2.7.2}

这一节回答：`fork()` 既然「复制」了地址空间，为什么一个占 256 MiB 的进程 fork 之后内存没有翻倍？复制究竟发生在哪一刻？

::: preview 先抓住一件事
写时复制（copy-on-write，COW：先让父子共用同一批物理页，直到有人要写才真正复制那一页）把 `fork()` 的成本从「拷贝全部数据」降到「复制页表 + 给物理页加引用计数」。断裂点是第一次写：内核把私有可写页的页表项改成只读，谁写谁触发缺页异常（page fault：访问的页没有可用映射时，CPU 把控制权交给内核处理的一次异常），内核这时才分配新页、复制内容、把新页给写的那一方。由此得到两个反直觉的判据：改一个字节也要复制整页（普通页 4 KiB）；而 RSS 不翻倍并不代表没发生 COW，因为子进程是「换掉映射」而不是「多留一份」。`MAP_SHARED` 完全不参与这套机制——它本来就是共享同一物理页。
:::

`fork()` 最容易被误解的地方是「复制」。如果真复制，一个 8 GiB 的进程 fork 一次就要 8 GiB 空闲内存，shell 早就不可用了。实际做法是：

1. 内核为子进程复制**页表**（不是数据页），把所有私有可写 PTE 改成只读；
2. 每个物理页的引用计数加一；
3. 任一方写入只读页时触发缺页异常，内核判断是 COW 缺页，分配新页、复制内容、改 PTE 为可写，并把原页引用计数减一。

<pre class="layout">
 fork 前                          fork 后（未写）                子进程写入后
┌──────────┐                    ┌──────────┐  ┌──────────┐      ┌──────────┐  ┌──────────┐
│ 父页表    │                    │ 父页表    │  │ 子页表    │      │ 父页表    │  │ 子页表    │
│ PTE 可写  │                    │ PTE 只读  │  │ PTE 只读  │      │ PTE 可写  │  │ PTE 可写  │
└────┬─────┘                    └────┬─────┘  └────┬─────┘      └────┬─────┘  └────┬─────┘
     │                               └──────┬──────┘                 │               │
     ▼                                      ▼                        ▼               ▼
┌──────────┐                          ┌──────────┐             ┌──────────┐   ┌──────────┐
│ 物理页 A  │                          │ 物理页 A  │             │ 物理页 A  │   │ 物理页 B  │
│ refcount=1│                          │ refcount=2│             │ refcount=1│   │ refcount=1│
└──────────┘                          └──────────┘             └──────────┘   └──────────┘
                                       写保护，共享             原页留给父进程    新页复制给子进程
</pre>

读图：COW 的关键不是「复制」，而是「**先共享、后分裂**」。fork 的代价从「拷贝全部数据」降到「处理已建立的页表映射 + 增加引用计数」；不能仅凭预留的虚拟地址范围估算页表复制量。对仍被父子共享的私有匿名页，第一次写会触发以页为单位的复制（普通页通常 4 KiB）：即使只改一个字节，也要隔离整页。若页已经独占，内核也可能直接恢复可写权限，无须再复制。

::: intuition 为什么 COW 对 fork+exec 特别划算
`fork()` 之后紧接着 `execve()` 是最常见的组合。子进程在 `exec` 之前通常只改几十个页（栈、少量全局变量），`exec` 一到，整个地址空间被丢弃。如果 fork 真的复制全部内存，这些复制全是白费。COW 让「fork + exec」的成本约等于「复制页表 + 加载新程序」。
:::

::: thm 定理 2.7.1 · COW 不改变的可见性规则 {#thm-2.7.1}
设父子进程在 `fork()` 时映射了同一段内存：

- 若映射是 `MAP_PRIVATE`（包括普通的堆、栈、`.data`），双方的写入互不可见，各自触发 COW；
- 若映射是 `MAP_SHARED`（包括 `mmap(MAP_SHARED|MAP_ANONYMOUS)` 与共享文件映射），**不触发 COW**，双方看到同一物理页，写入立刻互相可见，同步要自己做（[2.15](ch15.md)）；
- 通过 `read`/`write` 访问的文件内容不属于地址空间，共享与否由 fd 决定，与 COW 无关。
:::

下面的程序分配 256 MiB 并逐页触碰，fork 后分别打印 `VmRSS`，再让子进程每页写一个字节。先预测：子进程换成了自己的物理页，但映射的驻留页数量没有因此翻倍。程序同时用共享整数验证 `MAP_SHARED` 的可见性。

```c
/* cow_probe.c：观察 fork 的 COW 与 MAP_SHARED 的可见性 */
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/wait.h>
#include <unistd.h>

#define REGION_MB 256

static void die(const char *msg)
{
    perror(msg);
    exit(EXIT_FAILURE);
}

/* 读 /proc/self/status 的 VmRSS；非 Linux 返回 -1 */
static long rss_kb(void)
{
    FILE *fp = fopen("/proc/self/status", "r");
    if (fp == NULL)
        return -1;
    char line[256];
    long kb = -1;
    while (fgets(line, sizeof line, fp) != NULL) {
        if (strncmp(line, "VmRSS:", 6) == 0) {
            if (sscanf(line + 6, "%ld", &kb) != 1)
                kb = -1;
            break;
        }
    }
    fclose(fp);
    return kb;
}

int main(void)
{
    /* _exit 不刷新 stdio；禁用缓冲，重定向输出时也能看到子进程的行 */
    if (setvbuf(stdout, NULL, _IONBF, 0) != 0)
        die("setvbuf");
    long page_size = sysconf(_SC_PAGESIZE);
    if (page_size <= 0)
        die("sysconf page size");
    size_t len = (size_t)REGION_MB << 20;
    char *priv = mmap(NULL, len, PROT_READ | PROT_WRITE,
                      MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (priv == MAP_FAILED)
        die("mmap private");

    /* 逐页触碰，确保每一页都真正分配了物理页 */
    for (size_t i = 0; i < len; i += (size_t)page_size)
        priv[i] = 1;

    int *shared = mmap(NULL, (size_t)page_size, PROT_READ | PROT_WRITE,
                       MAP_SHARED | MAP_ANONYMOUS, -1, 0);
    if (shared == MAP_FAILED)
        die("mmap shared");
    *shared = 1000;

    printf("parent before fork : rss=%ld kB shared=%d\n", rss_kb(), *shared);

    pid_t pid = fork();
    if (pid == -1)
        die("fork");

    if (pid == 0) {
        printf("child  after fork  : rss=%ld kB shared=%d\n", rss_kb(), *shared);

        /* 写共享页：不触发 COW，父进程应看到 2000 */
        *shared = 2000;

        /* 每页写一个字节：每一页都触发一次 COW 复制 */
        for (size_t i = 0; i < len; i += (size_t)page_size)
            priv[i] = 2;

        printf("child  after write : rss=%ld kB shared=%d\n", rss_kb(), *shared);
        _exit(0);
    }

    int status;
    while (waitpid(pid, &status, 0) == -1) {
        if (errno != EINTR)
            die("waitpid");
    }

    /* 父进程的私有页没有被复制，RSS 不变；共享页已变 */
    printf("parent after child : rss=%ld kB shared=%d\n", rss_kb(), *shared);
    if (WIFEXITED(status))
        printf("child  exit        : exited %d\n", WEXITSTATUS(status));
    else if (WIFSIGNALED(status))
        printf("child  exit        : signal %d\n", WTERMSIG(status));

    munmap(priv, len);
    munmap(shared, (size_t)page_size);
    return EXIT_SUCCESS;
}
```

编译与运行（Linux）：

```bash

./cow_probe
# parent before fork : rss=263284 kB shared=1000
# child  after fork  : rss=262876 kB shared=1000
# child  after write : rss=263264 kB shared=2000
# parent after child : rss=263668 kB shared=2000
# child  exit        : exited 0
```

这五行是 ubuntu 24.04.5 / aarch64（内核 7.0.0-38-generic、页大小 4096）本机实测。先读数量级：映射并逐页触碰了 256 MiB，`VmRSS` 约 263 MB（256 MiB 数据 + 程序自身、libc、页表开销），fork 之后子进程立刻就有同量级的 RSS（262876 kB），因为它继承了全部映射；子进程把每一页都写了一个字节之后 RSS 仍是 263264 kB，父进程也还在 263668 kB——两边都没有翻倍。这就是 COW 的可观测结果：子进程把「指向共享旧页」的映射换成「指向私有新页」，旧页留给父进程，所以驻留页数量不变而物理页总数增加了。再读 `shared` 那一列：子进程写 `*shared = 2000` 之后，父进程读到的也是 2000，因为 `MAP_SHARED|MAP_ANONYMOUS` 不参与 COW，父子映射的是同一物理页。

仍要核对关系而不是背固定数值：`VmRSS` 是近似计数，受回收、换出、采样时刻影响，几十 kB 的差异不能用来证明或否定 COW；非 Linux 环境返回的 `-1` 表示观测接口不可用。要看「哪些页真的分裂了」，得在父子都存活的采样点读各自的 `/proc/<pid>/smaps`，比较 `Private_Dirty` 与 `Shared_Dirty`，而不是等子进程退出后再看。

关键在第二、三行：fork 刚完成时，父子的页表都映射了原有驻留页；写入后，子进程把「指向共享旧页」换成「指向私有新页」，并未同时保留两份映射。因此**RSS 不翻倍也可能发生了大量 COW**。字段口径可对照 [proc_pid_status(5)](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html) 与 [proc_pid_smaps(5)](https://man7.org/linux/man-pages/man5/proc_pid_smaps.5.html)。

**先猜**：下表三个时刻的「父 RSS / 子 RSS / 合计实际物理页 / 父 PSS / 子 PSS」各是多少？特别是第二行——子进程写了 2 页之后，它的 RSS 会变成 6 吗？合计物理页会变成 8 吗？先把自己的答案写下来再往下看。

迁移题：若子进程只写其中 1 页，父子 RSS、PSS 和合计物理页各是多少？答案是 RSS 各 4 页，PSS 各 `1 + 3/2 = 2.5` 页，物理页共 5 页。若算出子 RSS 为 5，回看「替换映射」；若把 PSS 算成 4，回看共享页分摊。

### 一个顺手的用法：把内存问题关进子进程

COW 还带来一个工程上的便利：**父进程的内存需求可以被「冻结」**。把一段可能泄漏、可能把堆搞得很碎的调用放进子进程执行，父进程 `fork` 后只 `wait`，那么这段代码造成的所有堆变化都发生在子进程的地址空间里，子进程一退出全部归还内核，父进程的堆回到 fork 前那一刻的样子。拿不到源码、无法修泄漏的第三方库尤其适合这么包一层。代价是结果只能靠退出码（8 位）或 IPC 传回来，而且每次都要付一次 fork 与调度的成本。

### 2.7.2 小结

COW 的做法是先共享、后分裂。fork 时内核复制页表、把私有可写页的页表项改成只读、给物理页加引用计数；真正的复制推迟到某一方第一次写那一页，由缺页异常触发。粒度是整页，本机为 4 KiB，所以改一个字节也要复制 4096 字节。

本机 `cow_probe` 的五行读数印证了这一点：256 MiB 映射下父子 RSS 都停在约 263 MB，没有翻倍；而 `MAP_SHARED` 的整数从 1000 变成 2000，父进程也读到 2000。私有页走 COW、共享页不走，这是本节最该分清的界线。选指标时也要注意，RSS 会把共享页重复计入两个进程，看实际占用应当用 PSS（按映射它的进程数分摊），而且要趁父子都活着时采样。

COW 还让最常见的 `fork` + `exec` 组合几乎不浪费：子进程在 exec 前只碰几十个页，exec 一到整个地址空间被丢弃，那些复制本来就是白做的。内核曾在「父先跑」与「子先跑」之间反复调整，理由之一正是这种场景下的页复制没有收益。如果只记住一件事，那就是：**COW 的断裂点是第一次写，粒度是整页；`MAP_SHARED` 不在这套机制里，它的可见性是立刻的，同步要你自己做。**

## 2.7.3 多线程程序中的 `fork()`：为什么只允许 async-signal-safe 调用 {#sec-2.7.3}

这一节回答：多线程程序里 `fork()` 之后，子进程为什么可能一调用 `malloc` 就永远卡住？哪些函数还能安全调用？

::: preview 先抓住一件事
`fork()` 只复制调用它的那个线程，别的线程在子进程里凭空消失——但它们持有的锁还在，以「已上锁」的状态被原样复制进子进程内存。于是子进程去拿那把锁，就永远等不到一个已经不存在的释放者。这就是 POSIX 规定「多线程程序中 fork 之后、exec 之前只能调用 async-signal-safe（异步信号安全：不依赖任何可能被别的线程持有的内部锁的函数）」的原因，`malloc`、`printf`、`pthread_mutex_lock`、`syslog` 都不在名单里。判据很硬：这不是概率问题的托词，本节有一个必然卡死的可复现实验，以及一个加了钩子就必然通过的对照。
:::

`fork()` 只复制**调用线程**，其他线程在子进程中不存在。但其他线程持有的锁、正在写的缓冲区、正在更新的数据结构，都以「被复制的一份」留在子进程内存里。子进程如果去拿那把锁，就永远等不到释放者——因为持有者线程已经不存在了。

::: def 定义 2.7.2 · `fork()` 后子进程的调用限制 {#def-2.7.2}
POSIX 规定：在多线程程序中，`fork()` 之后、`execve()` 之前，子进程只能调用 **async-signal-safe** 函数（见 [2.10](ch10.md) 的列表）。`malloc()`、`printf()`、`pthread_mutex_lock()`、`syslog()` 都不在其中。原因是这些函数可能依赖被其他线程持有的内部锁。
:::

最典型的死锁场景：

1. 线程 A 调用 `malloc()`，拿到 glibc 的 `arena` 锁，尚未释放；
2. 线程 B 调用 `fork()`，子进程复制了「锁已被持有」的内存状态；
3. 子进程调用 `malloc()`（哪怕只是 `printf` 内部），发现锁被占，永久阻塞。

这个窗口很窄，但在高并发服务里会稳定出现，而且 `gdb` 附加进去只能看到子进程卡在 `__lll_lock_wait`，看不出所以然。

### 本机实测：一个必然卡死的对照实验

上面说的是 `malloc` 的内部锁，窗口窄、不好复现。换成**你自己的一把互斥锁**，同一件事就变成确定性的：让一个线程持锁不放，主线程 `fork`，子进程去拿同一把锁。子进程里持锁线程不存在，锁却是「已锁」状态，于是必然卡住。为了不让实验挂死，子进程先 `alarm(3)` 兜底，父进程用 `waitpid` 看它是怎么结束的；对照组只多注册一个 `pthread_atfork` 的 child 钩子，在子进程里把那把锁解开。

```c
/* mt_fork_deadlock.c — 别的线程持锁时 fork：子进程拿同一把锁会卡死；加 atfork 子钩子可解 */
#include <errno.h>
#include <pthread.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

static void *holder(void *arg)
{
    (void)arg;
    if (pthread_mutex_lock(&lock) != 0) { perror("holder lock"); exit(1); }
    for (;;) pause();                 /* 持锁不放，模拟「正在临界区里」的线程 */
    return NULL;
}

static void child_hook(void) { pthread_mutex_unlock(&lock); }

int main(int argc, char **argv)
{
    int use_atfork = (argc > 1 && strcmp(argv[1], "atfork") == 0);
    if (use_atfork && pthread_atfork(NULL, NULL, child_hook) != 0) {
        perror("pthread_atfork"); return 1;
    }

    pthread_t t;
    if (pthread_create(&t, NULL, holder, NULL) != 0) { perror("pthread_create"); return 1; }
    usleep(100000);                   /* 让对方确实拿到锁 */

    pid_t pid = fork();
    if (pid == -1) { perror("fork"); return 1; }
    if (pid == 0) {
        alarm(3);                     /* 兜底：卡死就被 SIGALRM 杀掉，不让实验挂住 */
        if (pthread_mutex_lock(&lock) != 0) _exit(2);
        _exit(0);                     /* 拿到锁才会走到这里 */
    }

    int st = 0;
    if (waitpid(pid, &st, 0) == -1) { perror("waitpid"); return 1; }
    printf("mode=%s ", use_atfork ? "atfork" : "plain");
    if (WIFSIGNALED(st))
        printf("child killed by signal %d (%s)\n", WTERMSIG(st), strsignal(WTERMSIG(st)));
    else if (WIFEXITED(st))
        printf("child exited %d\n", WEXITSTATUS(st));
    fflush(stdout);
    _exit(0);                         /* 父进程不 pthread_join：holder 还在 pause */
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -pthread mt_fork_deadlock.c -o mt_fork
./mt_fork
# mode=plain child killed by signal 14 (Alarm clock)
./mt_fork atfork
# mode=atfork child exited 0
# 把源码里的 fork() 换成 _Fork()（glibc 2.34+）重编，再跑对照组：
./mt_fork atfork
# mode=atfork child killed by signal 14 (Alarm clock)
```

前三行都是 ubuntu 24.04.5 / aarch64（glibc 2.39）本机实测，可反复复现。`signal 14` 就是 `SIGALRM`：子进程没能拿到锁、也没能走到 `_exit(0)`，是被自己设的 3 秒闹钟杀掉的——这正是「卡死」的可观测形式。对照组只多了一个 child 钩子，子进程正常退出 0，因为钩子在 fork 之后把那把「持有者已不存在」的锁解开了。第三行把 `fork()` 换成 `_Fork()` 之后，即使注册了同一个钩子也照样卡死，这就直接证明了下面勘误里那条：`_Fork()` 不跑 atfork 处理器，锁状态照旧被复制，限制并没有消失。这个对照同时说明了 `pthread_atfork` 的能力边界：它能救你自己注册的锁，救不了 glibc `malloc` 的 arena 锁、`stdio` 的 `FILE` 锁、NSS 解析器的锁——那些你根本无从注册钩子。

### 正确的三种写法

**写法一：fork 后只做 exec。** 子进程只调用 `execve`（以及 `_exit`），不碰任何库函数：

```c
pid_t pid = fork();
if (pid == 0) {
    /* 只允许 async-signal-safe：execve 与 _exit 都在列表里 */
    execve("/bin/true", (char *const[]){ "true", NULL }, environ);
    _exit(127);          /* exec 失败：用 _exit，不 flush、不跑 atexit */
}
```

**写法二：在 fork 前把状态收干净。** 例如先 `fflush(NULL)`、暂停其他线程、确保没有线程持锁。这需要应用自己设计，glibc 无法代劳。

**写法三：用 `pthread_atfork()` 注册处理器。** 它在 fork 前后提供三个钩子：

```c
#include <pthread.h>

static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

static void prepare(void) { pthread_mutex_lock(&lock); }       /* fork 前，父进程 */
static void parent_hook(void) { pthread_mutex_unlock(&lock); } /* fork 后，父进程 */
static void child_hook(void) { pthread_mutex_unlock(&lock); }  /* fork 后，子进程 */

int register_hooks(void)
{
    return pthread_atfork(prepare, parent_hook, child_hook);
}
```

`prepare` 在 fork 之前按注册的**逆序**执行，`parent`/`child` 在 fork 之后按**正序**执行。它只能解决你**自己知道**的锁；glibc `malloc`、`stdio`、DNS 解析器内部的锁不在你的控制范围内。所以 `pthread_atfork` 是缓解手段，不是许可证。

::: errata 关于多线程 fork 的四个误解
1. **「子进程会继承所有线程」**——只复制调用 `fork()` 的那个线程，其他线程消失。子进程的 `gettid()` 与父进程调用者不同。
2. **「`fork` 后调用 `printf` 没事，我试过」**——没事是概率事件。锁恰好没被持有时能跑通，压力下必现。
3. **「`pthread_atfork` 能解决所有死锁」**——只能处理你注册的锁。`malloc` 的 arena 锁、`stdio` 的 `FILE` 锁、NSS 的锁都不归你管。
4. **「glibc 2.34 的 `_Fork()` 没有这个问题」**——`_Fork()` 跳过 atfork 处理器、不运行 `fork` 的兼容逻辑，语义更接近裸系统调用，但**锁状态依然被复制**，限制并没有消失。
:::

工程上的结论：**多线程程序不要 fork 出「继续跑业务逻辑」的子进程**。要并行就用线程或线程池（[2.12](ch12.md)、[2.13](ch13.md)）；要执行外部程序就用 `posix_spawn()`（[2.7.4](#sec-2.7.4)）或先 fork 再立刻 exec。

### 2.7.3 小结

问题的根源是一句话：锁的状态被复制了，锁的持有者没有被复制。子进程里只剩调用 `fork` 的那个线程，别的线程持有的互斥锁、glibc `malloc` 的 arena 锁、`stdio` 的 `FILE` 锁都停在「已上锁」，谁去拿谁就永久阻塞。

本机的对照实验把这件事做成了确定性现象。不加钩子时，子进程被自己设的 `alarm(3)` 杀掉，父进程收到 `signal 14`；注册一个 `pthread_atfork` 的 child 钩子把那把锁解开后，子进程正常退出 0。把 `fork()` 换成 `_Fork()` 之后，即使注册了同一个钩子也照样卡死，因为 `_Fork` 不运行 atfork 处理器。

三种正确写法按优先级排：fork 后立刻 exec，子进程只碰 `execve` 与 `_exit`，两者都在 async-signal-safe 名单里；或者在 fork 前把状态收干净，例如 `fflush(NULL)`、确保没有线程正在临界区；或者用 `pthread_atfork` 注册钩子，prepare 按逆序、parent/child 按正序执行，但它只管得住你自己注册的锁。要并行计算就用线程，要跑外部程序就用 `posix_spawn`。如果只记住一件事，那就是：**多线程程序 fork 出来的子进程，在 exec 之前只能调用 async-signal-safe 函数，`printf` 和 `malloc` 都不行；「我试过没事」只是没撞上那把锁。**

## 2.7.4 `vfork()`、`clone()` 与 `posix_spawn()` {#sec-2.7.4}

这一节回答：既然 `fork()` 已经有 COW，为什么还存在 `vfork()` 和 `posix_spawn()`？「线程」和「进程」在内核眼里差在哪几个标志位？

::: preview 先抓住一件事
这三个名字其实是**同一件事的三档省力程度**。`clone()` 是底层接口，用 flags 逐项决定「地址空间、fd 表、信号处置、线程组」是共享还是复制——`fork` 和 `pthread_create` 都只是它的不同 flag 组合。`vfork()` 是历史产物：子进程直接借用父进程的地址空间、父进程被挂起，省掉页表复制，代价是子进程几乎什么都不能做。`posix_spawn()` 是现代答案：把「创建 + 立刻执行新程序」合成一个调用，中间的有限动作（重定向、关 fd、设信号掩码）用参数描述，于是多线程程序也不必承担 fork 的锁风险。判据：本机 `strace` 能看到 `posix_spawn` 实际发的是 `clone3(CLONE_VM|CLONE_VFORK|CLONE_CLEAR_SIGHAND)`——它走的正是 vfork 那条省力路线。
:::

`vfork()` 是 fork 的历史优化：子进程**共享**父进程的地址空间，父进程被挂起，直到子进程 exec 或退出。

```c
pid_t pid = vfork();
if (pid == 0) {
    /* 不能修改任何变量，不能 return，不能调用 exit */
    execl("/bin/ls", "ls", "-l", (char *)NULL);
    _exit(127);
}
```

它的规则比 fork 更苛刻：子进程修改栈上的变量会破坏父进程；`return` 会破坏调用栈；`exit()` 会 flush 父进程的 stdio 缓冲区。`vfork()` 的唯一正当用途是「立刻 exec」，而这个用途已经被 `posix_spawn()` 覆盖。

「共享父进程地址空间」不是抽象说法，可以直接看见。下面这个程序**故意做被禁止的事**（子进程改父进程的变量），只为把共享关系暴露出来；`volatile` 是为了防止编译器把 `x` 优化进寄存器，`setvbuf` 关缓冲是为了让每次 `printf` 立刻 `write`，避免子进程动到共享的 stdio 缓冲区：

```c
/* vfork_share.c — vfork 的子进程共享父进程内存：改一个变量，父进程看得见（仅演示，属未定义行为） */
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void)
{
    if (setvbuf(stdout, NULL, _IONBF, 0) != 0) { perror("setvbuf"); return 1; }
    volatile int x = 100;
    printf("before vfork : x=%d pid=%ld\n", x, (long)getpid());

    pid_t pid = vfork();
    if (pid == -1) { perror("vfork"); return 1; }
    if (pid == 0) {
        x = 200;                  /* 改的就是父进程那份内存 */
        printf("child        : x=%d pid=%ld\n", x, (long)getpid());
        _exit(0);                 /* 必须 _exit：不能 exit()，也不能 return */
    }

    printf("after vfork  : x=%d  <- 父进程看到了子进程的修改\n", x);
    int st = 0;
    if (waitpid(pid, &st, 0) == -1) { perror("waitpid"); return 1; }
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -g vfork_share.c -o vfork_share
./vfork_share
# 实测：ubuntu 24.04.5 / aarch64，glibc 2.39（PID 为当次真值）
# before vfork : x=100 pid=10787
# child        : x=200 pid=10788
# after vfork  : x=200  <- 父进程看到了子进程的修改
```

三行是 ubuntu 24.04.5 / aarch64（glibc 2.39）本机实测。把同一份源码里的 `vfork()` 换成 `fork()` 重编重跑，父进程那一行打的是 `x=100`（本机实测 `before fork : x=100 pid=11412` / `after fork : x=100` / `child : x=200 pid=11413`；行尾那句提示文字是程序里写死的，别被它误导，看数值），而且这次是父进程先打印——又一次印证 [2.7.1](#sec-2.7.1) 的「谁先跑不确定」。差别的原因就是 fork 走 COW，子进程改的是自己那一页。这一对差别就是 vfork 的全部价值与全部危险：它省掉了页表复制，代价是子进程与父进程共用一份内存，所以 SUSv3 把它标为过时、SUSv4 直接删掉了它；子进程在 exec 或 `_exit` 之前除了极少数操作（如 `close` 一个 fd）什么都不能做，连从调用 `vfork` 的函数里 `return` 都是未定义行为。写新代码不要用它。

`clone()` 是 fork 的底层实现，通过 flags 决定共享哪些资源：

| flag | 效果 | 用途 |
|:--|:--|:--|
| `CLONE_VM` | 共享地址空间 | 线程 |
| `CLONE_FILES` | 共享 fd 表 | 线程 |
| `CLONE_FS` | 共享 `cwd`/`umask`/`chroot` | 线程 |
| `CLONE_SIGHAND` | 共享信号处置 | 线程（必须与 `CLONE_VM` 同用） |
| `CLONE_THREAD` | 放入同一线程组 | pthread |
| `CLONE_NEWPID` | 新 PID 命名空间 | 容器 |
| `CLONE_NEWNS` | 新挂载命名空间 | 容器 |
| `CLONE_PARENT` | 子进程的父进程是调用者的父进程 | 特殊场景 |

`pthread_create()` 在 Linux 上就是同一套创建接口加一组「全都共享」的标志。本机 `strace -f -e trace=clone,clone3` 一个只创建并 join 一个线程的程序，实测发出的是：

```text
clone3({flags=CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|CLONE_SYSVSEM|
        CLONE_SETTLS|CLONE_PARENT_SETTID|CLONE_CHILD_CLEARTID,
        exit_signal=0, stack=0xe28f140f0000, stack_size=0x80ea60, tls=0xe28f148ff8e0})
```

（ubuntu 24.04.5 / aarch64、glibc 2.39 实测；旧资料写的 `clone(...)` 在本机已换成 `clone3`。）对照 [2.7.1](#sec-2.7.1) 里 `fork` 的那一行 `clone(flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD)`，差别一目了然：线程把地址空间、fd 表、`cwd`/`umask`、信号处置**全部共享**并放进同一线程组，而且 **`exit_signal=0`——线程结束不给父进程发 `SIGCHLD`**，进程结束才发（`SIGCHLD`）。栈也是 libc 自己传的（`stack_size=0x80ea60`，约 8 MiB 默认值），而 `fork` 那一行 `child_stack=NULL` 表示由内核复制父进程的映射。所以「线程」和「进程」在 Linux 里不是两套机制，而是同一套创建接口的不同 flag 组合（第 3 篇会从内核侧展开）。

`posix_spawn()` 把「fork + exec」封装成一个调用，并允许在两者之间做有限的文件操作：

```c
#include <fcntl.h>
#include <spawn.h>
#include <string.h>

extern char **environ;

posix_spawn_file_actions_t fa;
posix_spawn_file_actions_init(&fa);
/* 子进程里：把 stdout 重定向到文件，关闭一个不需要的 fd */
posix_spawn_file_actions_addopen(&fa, STDOUT_FILENO, "out.log",
                                 O_WRONLY | O_CREAT | O_TRUNC, 0644);
posix_spawn_file_actions_addclose(&fa, 3);

pid_t pid;
int rc = posix_spawn(&pid, "/bin/echo",
                     &fa, NULL,
                     (char *const[]){ "echo", "hello", NULL }, environ);
posix_spawn_file_actions_destroy(&fa);
if (rc != 0) {                 /* 注意：返回错误码，不设置 errno */
    fprintf(stderr, "posix_spawn: %s\n", strerror(rc));
    return EXIT_FAILURE;
}
```

两个必须记住的细节：`posix_spawn()` **成功返回 0，失败返回错误码本身**（不是 `-1` 再查 `errno`）；它无法表达「子进程需要调用任意函数」的需求，`posix_spawnattr` 只支持有限的标志（信号掩码、调度策略、`POSIX_SPAWN_SETSID` 等）。

返回值口径与它实际走的系统调用都能在本机量出来。下面这个程序先 spawn 一个存在的程序、再 spawn 一个不存在的路径，两次都把 `errno` 显式清零后观察：

```c
/* spawn_probe.c — posix_spawn 的返回值口径：成功 0、失败返回错误码而不是 -1/errno */
#include <errno.h>
#include <spawn.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>

extern char **environ;

int main(void)
{
    char *const av[] = { "echo", "hello-from-spawn", NULL };
    pid_t pid = 0;
    errno = 0;
    int rc = posix_spawn(&pid, "/bin/echo", NULL, NULL, av, environ);
    printf("posix_spawn(/bin/echo)      rc=%d pid=%ld errno=%d\n", rc, (long)pid, errno);
    if (rc == 0) {
        int st = 0;
        if (waitpid(pid, &st, 0) == -1) { perror("waitpid"); return 1; }
        printf("child exit=%d\n", WIFEXITED(st) ? WEXITSTATUS(st) : -1);
    }

    pid_t bad = 0;
    errno = 0;
    rc = posix_spawn(&bad, "/nonexistent/xyz", NULL, NULL, av, environ);
    printf("posix_spawn(bad path)       rc=%d (%s) errno=%d\n", rc, strerror(rc), errno);
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 spawn_probe.c -o spawn_probe
./spawn_probe
# 实测：ubuntu 24.04.5 / aarch64，glibc 2.39（PID 为当次真值，失败行连跑两次同值）
# hello-from-spawn
# posix_spawn(/bin/echo)      rc=0 pid=10790 errno=0
# child exit=0
# posix_spawn(bad path)       rc=2 (No such file or directory) errno=2
strace -f -e trace=clone,clone3,vfork,execve ./spawn_probe
# clone3({flags=CLONE_VM|CLONE_VFORK|CLONE_CLEAR_SIGHAND, exit_signal=SIGCHLD,
#         stack=0xe8660610d000, stack_size=0x9000}, 88) = 10983
# [pid 10983] execve("/bin/echo", ["echo", "hello-from-spawn"], ...) = 0
# [pid 10984] execve("/nonexistent/xyz", ...) = -1 ENOENT (No such file or directory)
```

以上都是 ubuntu 24.04.5 / aarch64、glibc 2.39 本机实测，失败那行连跑两次同值。有两处要按实测订正旧说法：

1. `errno` 并非「一定不被设置」。本机失败时 `rc=2`（`ENOENT`）而 `errno` 也变成了 2，尽管调用前刚清零。POSIX 只保证「返回值是错误码」，`errno` 会不会被顺带改动属实现细节——所以判 `rc`，不要判 `errno`，也不要因为看到 `errno` 有值就以为它是 `-1` 那套约定。
2. **glibc 2.39 走的是 `clone3` 而不是 `clone`**，标志为 `CLONE_VM|CLONE_VFORK|CLONE_CLEAR_SIGHAND`、`exit_signal=SIGCHLD`，并自带一块 `stack_size=0x9000` 的栈。`CLONE_VM|CLONE_VFORK` 正是 vfork 那条「共享地址空间 + 挂起父进程」的省力路线，`CLONE_CLEAR_SIGHAND` 则把信号处置清成默认，省掉子进程继承一堆处理器带来的麻烦。所以「比手写 fork+exec 少一次页表复制」这个结论成立，但具体调用名要按本机 `strace` 写，别照抄老资料里的 `clone`。

::: note 该用哪个
- 执行外部程序、不需要复杂父子通信：`posix_spawn()`；
- 需要精细控制子进程（改 uid、设 rlimit、进命名空间）：`fork()` + 在子进程里调 `async-signal-safe` 函数 + `execve()`；
- 需要「子进程继续跑一段自己的代码」：线程，不是进程。
:::

### 2.7.4 小结

三个接口可以放在同一条轴上理解：共享的资源越多，创建越便宜，子进程能做的事也越受限制。`clone`/`clone3` 是这条轴本身，flags 逐项决定地址空间、fd 表、`cwd`/`umask`、信号处置、线程组是共享还是复制。本机实测 `fork` 发的是 `clone(CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD)`（号 220），`pthread_create` 发的是 `clone3`，带 `CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|…` 且 `exit_signal=0`。最后这一位就是差别所在：线程结束不通知父进程，进程结束才发 `SIGCHLD`。

`vfork` 走到轴的一端，连页表都不复制，子进程直接用父进程的内存。本机实验里子进程把 `x` 改成 200，父进程立刻看到 200；换成 `fork` 则父进程仍是 100。代价是子进程在 exec 或 `_exit` 之前几乎什么都不能做，SUSv4 已把它删掉，新代码不该再用。

`posix_spawn` 是这条省力路线的安全封装。本机 `strace` 显示它发 `clone3(CLONE_VM|CLONE_VFORK|CLONE_CLEAR_SIGHAND)`，既省下页表复制，又不把信号处置带进新程序，还能用 `file_actions` 描述重定向与关 fd。用它要记两件事：判返回值 `rc` 而不是 `errno`（本机失败时 `rc=2`，`errno` 也被置成 2，可见 errno 不可依赖）；它表达不了「子进程跑任意代码」这种需求。如果只记住一件事，那就是：**执行外部程序用 `posix_spawn`，需要精细控制就 fork 后只调 async-signal-safe 函数再 exec，要并行跑自己的代码就用线程，`vfork` 留给读老代码时认。**

::: sol 答案
**A1** `CLONE_VM` 共享地址空间，`CLONE_FILES` 共享 fd 表，`CLONE_THREAD` 放入同一线程组（`getpid` 相同、`gettid` 不同）。本机实测：`fork` 发 **`clone`（号 220）**、`exit_signal` 为 **`SIGCHLD`**；`pthread_create` 发 **`clone3`（号 435）**、`exit_signal=0`。`posix_spawn` 成功返回 **0**，失败返回**错误码本身**（如 `ENOENT`=2），不是 `-1`。
**A2** `fork` 走 COW：子进程起初与父进程共享物理页，但页表项被改成只读，子进程写 `x` 时触发缺页、内核复制那一页给子进程，所以父进程的 `x` 仍是 100。`vfork` 不复制页表也不设写保护，子进程用的就是父进程那份内存，写 `x` 直接改到父进程头上，故父进程看到 200。不能调 `exit()` 是因为它会 flush 并关闭 **父进程的** stdio 缓冲区、还会跑父进程注册的 `atexit` 处理器；不能 `return` 是因为子进程用的是父进程的栈帧，返回会破坏父进程的调用栈——两者都属未定义行为，正确收尾只有 `_exit()` 或成功的 `exec`。
**A3** 关键序列：`posix_spawn_file_actions_init(&fa)`；`posix_spawn_file_actions_addopen(&fa, STDOUT_FILENO, "/var/log/rotate.log", O_WRONLY|O_CREAT|O_APPEND, 0644)`；准备 `char *const av[] = {"logrotate", "/etc/logrotate.conf", NULL}`；`int rc = posix_spawn(&pid, "/usr/sbin/logrotate", &fa, NULL, av, environ)`；`posix_spawn_file_actions_destroy(&fa)`；**判 `if (rc != 0)` 并用 `strerror(rc)` 报错**（不要查 `errno`），成功则 `waitpid(pid, &st, 0)` 回收并用 `WIFEXITED`/`WEXITSTATUS` 解码。改用「fork 后在子进程 malloc 拼 argv」会踩两条坑：① 多线程程序 fork 后子进程只能调 async-signal-safe 函数，`malloc` 不在名单里，可能撞上别的线程持有的 arena 锁而永久卡死（[2.7.3](#sec-2.7.3) 的本机实验就是确定性复现）；② 子进程若用 `exit()` 收尾还会把 fork 时复制来的 stdio 缓冲区再 flush 一遍，造成重复输出（[2.7.5](#sec-2.7.5)）。
:::

## 2.7.5 进程终止：`exit()`、`_exit()` 与退出处理程序 {#sec-2.7.5}

这一节回答：进程「结束」为什么不是一瞬间？`exit()` 与 `_exit()` 差在哪几步，为什么 fork 之后用错会让输出重复？

::: preview 先抓住一件事
`exit()` 是库函数，它在进内核之前还要做三件事：逆序跑 `atexit` 处理器、flush 并关闭所有 stdio 流、删掉 `tmpfile()` 的临时文件；`_exit()` 是系统调用，直接进内核，这三件都不做。差别在 fork 之后会变成真 bug：stdio 缓冲区连同里面的数据被复制给了子进程，父子各自 `exit()` 就各 flush 一次，同一行输出出现两遍。判据：库函数与框架代码在子进程里一律用 `_exit()`，把 flush 的责任留给明确知道自己在做什么的人；退出状态只有低 8 位能传给父进程。
:::

::: def 定义 2.7.3 · `exit()` 与 `_exit()` {#def-2.7.3}
`void exit(int status)` 是**库函数**，它按顺序做四件事：

1. 按注册的**逆序**调用 `atexit()`/`on_exit()` 注册的函数；
2. flush 并关闭所有打开的 stdio 流；
3. 删除 `tmpfile()` 创建的临时文件；
4. 调用 `_exit(status)`。

`void _exit(int status)` 是**系统调用**，直接进入内核：关闭所有 fd、释放内存与锁、把退出状态留给父进程，然后变成僵尸。它**不** flush stdio、**不**运行 `atexit`。
:::

退出状态只有低 8 位能传给父进程：`exit(256)` 在父进程看来是 0。shell 约定 `128 + 信号编号` 表示「被信号杀死」，但这是 shell 的约定，不是内核的：`waitpid` 的 `status` 里，被信号杀死时 `WIFSIGNALED` 为真，`WTERMSIG` 给出信号号，退出码字段根本不存在。

### 经典 bug：fork 后 stdio 缓冲区被复制

`printf` 写到终端时是行缓冲，写到文件时是全缓冲。如果 fork 之前缓冲区里还有未 flush 的数据，子进程会**复制整个缓冲区**；父子各自 `exit()` 时各 flush 一次，输出就重复了。

下面这个程序把差异做成开关：

```c
/* exit_vs_exit.c：演示 fork 后 stdio 缓冲区被复制 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static void on_exit_handler(void)
{
    /* 故意用 printf：它写进同一个 stdio 缓冲区 */
    printf("[atexit] pid=%ld runs handler\n", (long)getpid());
}

int main(int argc, char **argv)
{
    int use_exit = (argc > 1 && strcmp(argv[1], "exit") == 0);

    if (atexit(on_exit_handler) != 0) {
        fprintf(stderr, "atexit failed\n");
        return EXIT_FAILURE;
    }

    /* 没有换行：数据留在 stdio 缓冲区里，不立即 write */
    printf("buffered-before-fork");

    pid_t pid = fork();
    if (pid == -1) {
        perror("fork");
        return EXIT_FAILURE;
    }

    if (pid == 0) {
        if (use_exit)
            exit(0);        /* flush 复制来的缓冲区 + 跑 atexit */
        _exit(0);           /* 直接进内核，什么都不做 */
    }

    int status;
    if (waitpid(pid, &status, 0) == -1) {
        perror("waitpid");
        return EXIT_FAILURE;
    }
    printf("\nchild done, exit=%d\n", WIFEXITED(status) ? WEXITSTATUS(status) : -1);
    return EXIT_SUCCESS;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -g exit_vs_exit.c -o exit_vs_exit
./exit_vs_exit _exit > out1.txt; ./exit_vs_exit exit > out2.txt
```

```text
# 实测：ubuntu 24.04.5 / aarch64，glibc 2.39（PID 为当次真值，要看行的构成而不是具体号）
$ ./exit_vs_exit _exit > out1.txt ; cat out1.txt
buffered-before-fork
child done, exit=0
[atexit] pid=10780 runs handler
$ ./exit_vs_exit exit > out2.txt ; cat out2.txt
buffered-before-fork[atexit] pid=10784 runs handler
buffered-before-fork
child done, exit=0
[atexit] pid=10783 runs handler
```

以上两次运行都是 ubuntu 24.04.5 / aarch64（glibc 2.39）本机实测，PID 是当次真值、每次跑都会变，要看的是**行的构成**而不是具体号。两次都有父进程的那行 `[atexit] pid=10780/10783`，这是正常的：父进程本来就要走 `exit()`。差别在子进程：`out2.txt` 里多出的 `pid=10784` 是子进程，它先跑 `atexit`、再把「fork 时复制来的缓冲区」flush 出来，于是 `buffered-before-fork` 出现了两次，而且第一次还和子进程的 `[atexit]` 挤在同一行（因为原字符串没有换行）；`out1.txt` 里只有一次，因为子进程 `_exit()` 什么都没做。

修复方式只有两个：fork 之前 `fflush(NULL)`，或者子进程一律 `_exit()`。**库函数与框架代码应默认 `_exit()`**，把 flush 的责任留给明确知道自己在做什么的调用者。

::: errata 关于进程终止的四个误解
1. **「`exit(1)` 和 `return 1` 在 `main` 里不同」**——在 `main` 里等价（C 标准保证 `return` 会走 `exit`）。在其他函数里 `return` 只是返回，不终止进程。
2. **「`exit()` 会立即停止所有线程」**——`exit()` 会终止整个进程（包括其他线程），但在此之前会跑 atexit 与 flush。`_exit()` 跳过这些步骤。
3. **「`atexit` 注册的函数按注册顺序执行」**——逆序（LIFO）。先注册的后执行，适合「后申请的资源先释放」。
4. **「退出码可以任意大」**——只有低 8 位有效。`exit(1000)` 父进程看到的是 232。
:::

### 本机实测：退出码的低 8 位

上面那条「低 8 位」不是推测，跑一遍就有：

```c
/* exitcode.c — 退出码只有低 8 位：父进程用 WEXITSTATUS 解码 */
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>
int main(void)
{
    const int codes[] = { 0, 1, 255, 256, 1000 };
    for (size_t i = 0; i < sizeof codes / sizeof codes[0]; i++) {
        pid_t pid = fork();
        if (pid == -1) { perror("fork"); return 1; }
        if (pid == 0) _exit(codes[i]);
        int st = 0;
        if (waitpid(pid, &st, 0) == -1) { perror("waitpid"); return 1; }
        printf("child _exit(%4d) -> WIFEXITED=%d WEXITSTATUS=%d\n",
               codes[i], WIFEXITED(st) ? 1 : 0, WEXITSTATUS(st));
    }
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 exitcode.c -o exitcode
./exitcode
# child _exit(   0) -> WIFEXITED=1 WEXITSTATUS=0
# child _exit(   1) -> WIFEXITED=1 WEXITSTATUS=1
# child _exit( 255) -> WIFEXITED=1 WEXITSTATUS=255
# child _exit( 256) -> WIFEXITED=1 WEXITSTATUS=0
# child _exit(1000) -> WIFEXITED=1 WEXITSTATUS=232
```

ubuntu 24.04.5 / aarch64 本机实测。`256 & 0xFF == 0`、`1000 & 0xFF == 232`，与输出逐行对上。所以**退出码只能当「小枚举」用**（0 成功、1–125 自定义、126/127 留给 shell 的「不可执行/找不到命令」、128+N 留给「被信号 N 杀死」这套 shell 约定），要传大整数或结构化结果就得走管道、文件或共享内存。还要注意 `WIFEXITED` 与 `WIFSIGNALED` 是互斥的两条路：被信号杀死时根本没有退出码字段，`WEXITSTATUS` 的值无意义，必须先判 `WIFSIGNALED` 再取 `WTERMSIG`。

::: ex 例 2.7.2 · 退出码能传回多大的数 {#ex-2.7.2}
**先猜**：子进程分别 `_exit(0)`、`_exit(1)`、`_exit(255)`、`_exit(256)`、`_exit(1000)`，父进程用 `WEXITSTATUS` 各读到什么？哪几个会与子进程写下的数不同？先把自己的五个答案写出来再对照。

本机实测（就是上面 `exitcode` 的输出）：0→0、1→1、255→255、256→0、1000→232。后两个不同，因为 `256 & 0xFF = 0`、`1000 & 0xFF = 232`，高位在进内核时就被丢掉了。

迁移题：若子进程想用退出码报告「处理了 1000 条记录」，父进程会读到什么？这个信息还能还原吗？该怎么改？答：父进程读到 232，且无法从 232 反推 1000（`0x3E8` 与 `0x1E8`、`0x2E8` 的低 8 位都是 `0xE8`）；正确做法是把计数写进管道、文件或共享内存，退出码只用来表示成功或失败。
:::

### 2.7.5 小结

进程终止分成用户态收尾与内核收尾两段。`exit()` 负责前者：逆序跑 `atexit`/`on_exit`、flush 并关闭 stdio 流、删掉 `tmpfile()` 的临时文件，然后才调 `_exit()`。`_exit()` 直接进内核，关 fd、释放内存与锁、留下退出状态，进程变成僵尸等父进程回收。

两段的分界在 fork 之后会出问题。stdio 缓冲区被原样复制给子进程，父子各 `exit()` 就各 flush 一次：本机 `exit_vs_exit` 的对照输出里，子进程用 `exit` 那次 `buffered-before-fork` 出现两次，用 `_exit` 那次只出现一次。修法有两个，fork 前 `fflush(NULL)`，或者子进程一律 `_exit()`；库与框架代码应默认后者，把 flush 的责任留给明确知道自己在做什么的调用者。

退出状态这一侧，本机实测确认了只有低 8 位有效：`_exit(256)` 父进程看到 0，`_exit(1000)` 看到 232。所以退出码适合当小枚举用，大结果要走 IPC。被信号杀死时走的是另一条路，用 `WIFSIGNALED` 判、用 `WTERMSIG` 取信号号；`128+N` 只是 shell 的显示约定，不是内核给的退出码。如果只记住一件事，那就是：**`exit` 与 `_exit` 的差别全在进内核之前那三步，而 fork 会把这三步的作用对象（缓冲区、atexit 名单）复制一份，所以子进程里默认用 `_exit`。**

::: method 即时自测 · 2.7.5
**Q1（记忆）** `exit()` 在调用 `_exit()` 之前按顺序做哪三件事？`atexit` 处理器按什么顺序执行？退出状态有多少位能传给父进程？

**Q2（辨析）** 本机 `exit_vs_exit exit` 的输出里 `buffered-before-fork` 出现两次，而 `_exit` 版本只有一次。请逐步说明两次分别是谁 flush 的；为什么第一次出现时还和 `[atexit]` 挤在同一行？

**Q3（应用）** 一个子进程用 `_exit(1000)` 报告「处理了 1000 条记录」，父进程 `WEXITSTATUS` 得到 232，运维据此以为出错。请指出设计错在哪，给出两种正确传法；如果子进程是被 `SIGKILL` 杀死的，父进程应该怎么判、怎么取信号号？

::: sol 答案
**A1** 三件事按顺序：① 按注册的**逆序**调用 `atexit()`/`on_exit()` 注册的函数；② flush 并关闭所有打开的 stdio 流；③ 删除 `tmpfile()` 创建的临时文件；然后调用 `_exit(status)`。`atexit` 是 **LIFO 逆序**（先注册的后执行，适合「后申请的资源先释放」）。退出状态只有**低 8 位**有效。
**A2** fork 之前 `printf("buffered-before-fork")` 没有换行，重定向到文件时 stdio 是全缓冲，数据留在缓冲区里；fork 把整个缓冲区复制给子进程。`exit` 版本：子进程 `exit(0)` 先跑它继承来的 `atexit` 处理器（打出 `[atexit] pid=10784`，写进同一个缓冲区），再 flush 缓冲区，于是「复制来的 `buffered-before-fork` + 刚写的 `[atexit]`」一起落盘，这就是第一次出现且挤在同一行的原因（原字符串末尾没有 `\n`）；随后父进程 `waitpid` 返回、打印 `child done` 并走自己的 `exit()`，把它那份缓冲区里的 `buffered-before-fork` 再 flush 一次，这是第二次。`_exit` 版本里子进程直接进内核、不跑 atexit 也不 flush，所以只有父进程那一次。
**A3** 错在把退出码当数据通道：它只有 8 位，`1000 & 0xFF = 232`，信息已经丢失且无法还原。两种正确传法：① 子进程把计数写进管道或临时文件，父进程 `waitpid` 后读回（退出码只用来表示成功/失败）；② fork 前建 `MAP_SHARED|MAP_ANONYMOUS` 映射，子进程写计数、父进程读（注意它不走 COW，需同步）。若子进程被 `SIGKILL` 杀死，父进程应先用 `WIFSIGNALED(st)` 判为真，再用 `WTERMSIG(st)` 取到 9；此时 `WIFEXITED` 为假、`WEXITSTATUS` 无意义，shell 显示的 137（128+9）只是它的约定。

## 2.7.6 僵尸、孤儿与 `wait` 家族 {#sec-2.7.6}

这一节回答：进程已经退出了，为什么 `ps` 里还看得到它？谁来负责让它彻底消失，父进程不管会怎样？

::: preview 先抓住一件事
进程终止后内核不能立刻把它抹掉，因为退出状态和资源用量还没人取走——这段「已死但还留着户口」的状态就是僵尸（zombie，`ps` 状态位 `Z`）。它占的不是内存页，而是一个 PID 加一份 `task_struct` 记账信息，所以 `kill -9` 对它无效：它已经死了，再杀一次没有意义。唯一的出路是父进程调用 `wait` 家族取走状态；父进程若先死，子进程成为孤儿（orphan），被过继给 PID 1 或最近的 subreaper 由它回收。判据：僵尸堆积的真实后果是 PID 耗尽，症状是「进程数看着没满，`fork` 却返回 `EAGAIN`」。
:::

进程终止后并不会立刻消失。内核要保留它的退出状态、资源用量，等父进程来取。这段时间里进程处于 `TASK_ZOMBIE` 状态。

{{#include ../assets/figures/proc-states.md}}

读图：`TASK_ZOMBIE` 是「已退出、等 `wait`」，它占的是 `task_struct` 与少量记账信息，**不是内存页**。图中从 `TASK_RUNNING` 有一条 `exit()` 指向 `ZOMBIE`，再从 `ZOMBIE` 经 `wait()` 到 `EXIT_DEAD`；只有走完这条线，PID 才会被回收。`TASK_TRACED` 是另一条支路：被 `ptrace` 暂停的进程不响应普通信号，调试器退出时要负责让它继续或终止。

::: def 定义 2.7.4 · 僵尸与孤儿 {#def-2.7.4}
- **僵尸（zombie）**：已终止但父进程尚未 `wait` 的进程。`ps` 中状态为 `Z`，仍占用 PID 与 `task_struct`。
- **孤儿（orphan）**：父进程先于它终止的进程。内核把它过继给 `init`（PID 1）或最近的 `subreaper`，由后者负责回收。
:::

僵尸不能用 `kill -9` 消灭——它已经死了。唯一的办法是父进程调用 `wait` 家族，或者父进程自己退出（僵尸被过继给 init 后回收）。如果父进程长期不回收，PID 会被耗尽：`fork` 开始返回 `EAGAIN`，系统看起来「进程数没满但创建不了进程」。

这件事不用等线上事故，本机就能确定性地看见。下面这个程序让子进程立刻退出，父进程先读 `/proc/<pid>/stat` 的第三个字段（状态位），再 `waitpid`，然后再读一次：

```c
/* zombie_probe.c — 子进程退出后、父进程 wait 前它是 Z；wait 之后 /proc 条目消失 */
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

static char state_of(pid_t p)
{
    char path[64];
    snprintf(path, sizeof path, "/proc/%ld/stat", (long)p);
    FILE *f = fopen(path, "r");
    if (!f) return '?';
    int pid = 0; char comm[256] = {0}; char st = '?';
    if (fscanf(f, "%d %255s %c", &pid, comm, &st) != 3) st = '!';
    fclose(f);
    return st;
}

int main(void)
{
    pid_t pid = fork();
    if (pid == -1) { perror("fork"); return 1; }
    if (pid == 0) _exit(7);
    usleep(100000);                     /* 让子进程确实先退出 */
    printf("before wait: child=%ld state=%c\n", (long)pid, state_of(pid));
    int st = 0;
    if (waitpid(pid, &st, 0) == -1) { perror("waitpid"); return 1; }
    printf("after  wait: child=%ld state=%c  ('?' = /proc 条目已消失)\n",
           (long)pid, state_of(pid));
    printf("reaped: WIFEXITED=%d code=%d\n", WIFEXITED(st) ? 1 : 0, WEXITSTATUS(st));
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -g zombie_probe.c -o zombie_probe
./zombie_probe
# before wait: child=15043 state=Z
# after  wait: child=15043 state=?  ('?' = /proc 条目已消失)
# reaped: WIFEXITED=1 code=7
```

三行是 ubuntu 24.04.5 / aarch64 本机实测（PID 每次不同，看状态位）。`wait` 之前是 `Z`，`wait` 之后连 `/proc/15043/` 这个目录都没了（`fopen` 失败返回 `?`），而退出码 7 是在 `wait` 之后才拿到的——这三件事正好说明僵尸期存在的理由：状态必须留到有人来取，取完才销户。也顺便解释了为什么僵尸不占内存：它的地址空间在退出时已经释放，留下的只是内核里那份记账。

```c
/* reap_children.c：用 waitpid 处理退出、被杀、停止与继续 */
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

#define NCHILD 4

int main(void)
{
    for (int i = 0; i < NCHILD; i++) {
        pid_t pid = fork();
        if (pid == -1) {
            perror("fork");
            return EXIT_FAILURE;
        }
        if (pid == 0) {
            switch (i) {
            case 0:
                _exit(0);                       /* 正常退出，码 0 */
            case 1:
                _exit(7);                       /* 正常退出，码 7 */
            case 2:
                raise(SIGTERM);                 /* 被信号杀死 */
                _exit(1);                       /* 不会到这里 */
            default:
                raise(SIGSTOP);                 /* 先停住，等父进程放行 */
                _exit(3);                       /* SIGCONT 之后退出 */
            }
        }
    }

    int alive = NCHILD;
    int status;

    while (alive > 0) {
        pid_t pid = waitpid(-1, &status, WUNTRACED | WCONTINUED);
        if (pid == -1) {
            if (errno == EINTR)
                continue;
            if (errno == ECHILD)
                break;                          /* 没有子进程了 */
            perror("waitpid");
            return EXIT_FAILURE;
        }

        if (WIFEXITED(status)) {
            printf("pid=%ld exited   code=%d\n", (long)pid, WEXITSTATUS(status));
            alive--;
        } else if (WIFSIGNALED(status)) {
            printf("pid=%ld signaled sig=%d%s\n", (long)pid, WTERMSIG(status),
                   WCOREDUMP(status) ? " (core dumped)" : "");
            alive--;
        } else if (WIFSTOPPED(status)) {
            printf("pid=%ld stopped  sig=%d -> SIGCONT\n", (long)pid, WSTOPSIG(status));
            if (kill(pid, SIGCONT) == -1) {
                perror("kill SIGCONT");
                return EXIT_FAILURE;
            }
        } else if (WIFCONTINUED(status)) {
            printf("pid=%ld continued\n", (long)pid);
        }
    }

    printf("all %d children reaped\n", NCHILD);
    return EXIT_SUCCESS;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -g reap_children.c -o reap_children
./reap_children
# 实测：ubuntu 24.04.5 / aarch64（PID 与事件顺序为当次真值，顺序每次可能不同）
# pid=15046 exited   code=0
# pid=15047 exited   code=7
# pid=15048 signaled sig=15
# pid=15049 stopped  sig=19 -> SIGCONT
# pid=15049 continued
# pid=15049 exited   code=3
# all 4 children reaped
```

这七行是 ubuntu 24.04.5 / aarch64 本机实测。**输出顺序不固定**（谁先被调度谁先报），但四类事件都会出现：两个 `exited`（码 0 与 7）、一个 `signaled`（`sig=15` 即 `SIGTERM`）、一个 `stopped`（`sig=19` 即 `SIGSTOP`）+ `continued` + `exited`（码 3）。核心在 `waitpid` 的第一个参数 `-1`（等待任意子进程）与 `WUNTRACED | WCONTINUED`：不加这两个标志，停止与继续事件不会返回，父进程会以为子进程「还没结束」，那个 `raise(SIGSTOP)` 的孩子就永远停在那里。还要注意 `alive--` 只在 `exited` 与 `signaled` 两支里做——`stopped`/`continued` 不是终止事件，减了就会提前退出循环、留下真正的僵尸。

### 等待的四种接口

| 接口 | 能等到什么 | 额外信息 | 典型用途 |
|:--|:--|:--|:--|
| `wait(&status)` | 任一子进程退出 | 无 | 只有一个子进程 |
| `waitpid(pid, &st, flags)` | 指定/任一组子进程 | 退出码、信号、停止 | 常规回收 |
| `waitid(idtype, id, &si, flags)` | 同上，粒度更细 | `siginfo_t`：`si_code`、`si_uid`、`si_status` | 需要区分「谁杀的」 |
| `wait3/wait4` | 任一子进程 | 额外 `struct rusage` | 资源统计（[2.8](ch08.md)） |

`waitid` 的 `siginfo_t` 比 `status` 字更清楚：

```c
siginfo_t si;
if (waitid(P_PID, pid, &si, WEXITED | WNOHANG) == -1) { /* 错误 */ }
if (si.si_pid == 0) {
    /* WNOHANG：没有可回收的子进程 */
} else if (si.si_code == CLD_EXITED) {
    /* 正常退出，码在 si_status */
} else if (si.si_code == CLD_KILLED || si.si_code == CLD_DUMPED) {
    /* 被信号杀死，信号号在 si_status */
} else if (si.si_code == CLD_STOPPED) {
    /* 停止，信号号在 si_status */
}
```

注意 `si.si_pid == 0` 才是「没有事件」，不是 `-1`。`waitid` 在 `WNOHANG` 且无子进程可等时返回 0，这是它与 `waitpid` 最容易混的地方。

### `SIGCHLD` 的坑

用信号驱动回收很自然：注册 `SIGCHLD` 处理器，在处理器里 `while (waitpid(-1, &st, WNOHANG) > 0)`。但有两个坑：

1. **信号会合并**。三个子进程几乎同时退出，标准信号只记一次未决，处理器可能只被调用一次。所以处理器里必须用 `while` 循环把已退出的子进程**全部**回收，不能只 `waitpid` 一次。
2. **`WNOHANG` 循环必须在返回 0 或 -1 时退出**。循环条件用 `> 0`，不要写成死循环；子进程还没退出时 `waitpid` 会返回 0。

如果完全不想管僵尸，可以在**创建子进程之前**把 `SIGCHLD` 设为 `SIG_IGN`，或给 `sigaction` 加 `SA_NOCLDWAIT`：

```c
struct sigaction sa = {0};
sa.sa_handler = SIG_IGN;
sa.sa_flags = SA_NOCLDWAIT;      /* 子进程退出时直接回收，不产生僵尸 */
sigemptyset(&sa.sa_mask);
if (sigaction(SIGCHLD, &sa, NULL) == -1) {
    perror("sigaction");
    exit(EXIT_FAILURE);
}
```

代价是**再也拿不到退出状态**：`waitpid` 返回 `ECHILD`。本机实测（ubuntu 24.04.5 / aarch64）：设好 `SIG_IGN|SA_NOCLDWAIT` 后 fork 一个 `_exit(5)` 的子进程，等 100 ms 再查，`/proc/<pid>/stat` **已经不存在**（没有僵尸期），紧接着 `waitpid(pid, &st, 0)` 返回 `-1`、`errno=10`（`ECHILD`，"No child processes"）。所以这条路只适合「fire-and-forget」的子进程：你放弃的不只是僵尸，还有退出码与「谁杀的」这类信息。

### 父进程先死：`PR_SET_PDEATHSIG`

服务常需要「父进程崩溃时子进程跟着退出」。Linux 提供 `prctl(PR_SET_PDEATHSIG, sig)`：

```c
#ifdef __linux__
#include <sys/prctl.h>

static void setup_parent_death_signal(pid_t expected_parent)
{
    if (prctl(PR_SET_PDEATHSIG, SIGTERM) == -1) {
        perror("prctl");
        exit(EXIT_FAILURE);
    }
    /* 竞态：父进程可能在 prctl 之前就死了，信号不会补发 */
    if (getppid() != expected_parent)
        _exit(1);
}
#endif
```

顺序不能反：先 `prctl`，再检查 `getppid()`。如果父进程在两次调用之间退出，`getppid()` 会变成 1（或 subreaper），检查失败直接退出；如果先检查再 `prctl`，父进程恰好死在中间，子进程就永远收不到信号。

::: method 僵尸与孤儿的排查顺序
1. `ps -eo stat,ppid,pid,comm | awk '$1 ~ /^Z/'` 找出僵尸及其父进程；
2. 看父进程在做什么：`cat /proc/{ppid}/stack`（需 root）、`strace -p {ppid}`，确认它是否卡在 `read`/`accept` 上忘了 `wait`；
3. 检查 `SIGCHLD` 是否被设为 `SIG_IGN` 或 `SA_NOCLDWAIT`——如果是，`waitpid` 必然 `ECHILD`，这不是 bug；
4. 检查父进程是否注册了 `SIGCHLD` 处理器但只 `waitpid` 一次；
5. 若父进程是容器里的 PID 1，确认它是否实现了回收逻辑；没有就用 `--init` 或 `tini`；
6. 孤儿排查用 `ps -eo pid,ppid,stat,comm`，找 `ppid=1` 但仍在跑的业务进程，确认它是否该被过继。
:::

### 2.7.6 小结

回收是父子之间的一项约定，不是可选的礼貌动作。本机 `zombie_probe` 量出了它的两端：子进程 `_exit(7)` 之后、父进程 `wait` 之前，`/proc/<pid>/stat` 的状态位是 `Z`；`waitpid` 一返回，那个 `/proc` 目录就消失了，退出码 7 也是这时才拿到。僵尸期存在的理由就是状态还没人取，它占的是 PID 与 `task_struct`，不是内存页，所以 `kill -9` 对它无效。

回收侧要分清四类事件。`waitpid(-1, &st, WUNTRACED|WCONTINUED)` 才会把停止与继续也报上来，本机 `reap_children` 的七行输出里 `exited`、`signaled`、`stopped`、`continued` 齐全；计数只能在真正终止的那两支里减，否则会把停住的孩子当成已结束。用 `SIGCHLD` 驱动回收时有两个坑：标准信号会合并，处理器里必须 `while (waitpid(-1, &st, WNOHANG) > 0)` 把已退出的收干净；循环条件必须是 `> 0`，返回 0 表示还有孩子但没退出。

想彻底不管僵尸，可以设 `SIG_IGN`/`SA_NOCLDWAIT`，代价本机也量过：`/proc` 条目立刻消失，`waitpid` 报 `errno=10`（`ECHILD`），退出码与信号信息一并放弃。父进程先死的情形靠过继解决，交给 PID 1 或最近的 subreaper；要让「父死子随」则用 `prctl(PR_SET_PDEATHSIG)`，顺序必须是先 prctl 再查 `getppid()`，否则中间那个窗口会漏掉信号。如果只记住一件事，那就是：**每个 fork 都要在代码里指出谁在什么时候 wait，指不出来就是僵尸泄漏；容器里的 PID 1 尤其要自己实现回收，否则用 `--init` 或 `tini` 兜底。**

**A1** 僵尸是**已终止但父进程尚未 `wait`** 的进程（`ps` 状态 `Z`），占用 PID 与 `task_struct` 及少量记账信息；孤儿是**父进程先于它终止**的进程，被过继给 PID 1 或最近的 subreaper 负责回收。僵尸不占内存页，因为地址空间在终止时已释放，留下的只是内核记账。要收停止与继续事件需加 **`WUNTRACED | WCONTINUED`**。`waitid` 在 `WNOHANG` 且无可回收子进程时**返回 0**，并以 **`si.si_pid == 0`** 表示「没有事件」，不是返回 `-1`。

## 2.7.7 `fork()` 的内核路径：从 `kernel_clone()` 到 `copy_process()` {#sec-2.7.7}

这一节回答一个问题：用户态一次 `fork()`，内核按什么顺序复制哪些对象，失败时又按什么顺序回滚？只有把顺序记住，才能解释「为什么子进程的 fd 已复制、但记录锁没复制」这类看似矛盾的现象。

::: preview 先抓住一件事
内核把 `fork`/`vfork`/`clone`/`clone3` 四个入口收敛到同一个 `kernel_clone()`，再进 `copy_process()` 按固定顺序逐项复制：先 `dup_task_struct` 复制进程描述符，再依次处理凭证、信号、fd 表、地址空间、线程组，最后 `copy_thread` 造出子进程的内核栈与寄存器现场，`wake_up_new_task` 让它可调度。顺序就是回滚顺序的依据：任何一步失败，前面已复制的对象要按相反次序释放，这也是「fd 复制了但记录锁没复制」这类现象的来源——记录锁根本不在复制清单里。读这一节要分清两件事：机制与顺序跨架构相同，入口符号名与调用号跨架构全不同，本节的本机口径是 aarch64。
:::

### 一次 fork 的调用链

先说口径。旧版按 x86-64 叙述：走 `syscall` 指令进入 `entry_SYSCALL_64`，由 syscall 表分派到 `__x64_sys_fork`，并称「Linux 6.8 的 `kernel/fork.c`」。本套件没有 x86 主机，那一侧的符号名一个都没实测过（本机 `/proc/kallsyms` 里 `entry_SYSCALL_64`、`do_syscall_64`、`__x64_sys_fork` 全为 0 命中），只能当读源码得到的形状。本套件的测试机是 aarch64 + 内核 `7.0.0-38-generic`，同一件事的名字是：陷入走同步异常向量 `el0_svc`，分派在 `invoke_syscall`，包装函数带 `__arm64_` 前缀。而且 [2.7.1](#sec-2.7.1) 已经实测过：aarch64 的调用号表里没有 `__NR_fork`/`__NR_vfork`，glibc 的 `fork()` 发的是 `clone`（号 220），所以本机这条链的入口是 `__arm64_sys_clone`。内核侧仍然定义了 `fork`/`vfork` 入口，四个入口收敛到同一个 `kernel_clone()`：

| 用户态入口 | 内核入口 | 关键参数 | 子进程如何返回 |
|:--|:--|:--|:--|
| `fork()` | `SYSCALL_DEFINE0(fork)` | `exit_signal = SIGCHLD` | 复制当前栈，返回 0 |
| `vfork()` | `SYSCALL_DEFINE0(vfork)` | `CLONE_VM \| CLONE_VFORK \| SIGCHLD` | 共享栈，父进程挂起 |
| `clone(fn, stack, flags, ...)` | `SYSCALL_DEFINE5(clone)` | 用户给 `flags` 与子栈 | 切到新栈，返回 0 |
| `clone3(&args, size)` | `SYSCALL_DEFINE2(clone3)` | `struct clone_args` | 切到新栈，返回 0 |

这张表的符号名可以在本机免 root 核对一半。`kptr_restrict` 只遮地址不遮名字，所以普通用户能在 `/proc/kallsyms` 里查「这台内核有没有这个函数」——它证明**存在性**，不证明调用顺序（顺序仍是读源码）：

```text
# 实测：ubuntu 24.04.5 / aarch64，内核 7.0.0-38-generic，grep -cw 各符号 /proc/kallsyms
el0_svc                  1

__arm64_sys_clone        1
__arm64_sys_clone3       1
__arm64_sys_fork         1

```

三点判读。① 入口链与 `kernel_clone`/`copy_process`/`dup_fd`/`copy_sighand`/`copy_signal`/`copy_thread`/`wake_up_new_task` 本机逐个查得到，说明这条链的中间部分在这台机器上成立。② `__arm64_sys_fork` 与 `__arm64_sys_vfork` 符号存在，但用户态用不到——aarch64 的调用号表里没有 `__NR_fork`/`__NR_vfork`（[2.7.1](#sec-2.7.1) 实测），内核定义了入口却没接进这张表；「符号在」不等于「这个架构上能调到」。③ `copy_files`、`copy_mm` 查不到不等于内核没有这两个函数：静态函数、被内联或改名的实现都不进 `kallsyms`，所以不能因为表里写了就当本机核过，也不能因为查不到就说书里写错了。x86 那三个名字全为 0，正是「另一台机器」的证据。

`fork()`/`vfork()` 的 `SYSCALL_DEFINE0` 只负责把参数填成 `kernel_clone_args`，真正的复制在 `copy_process()`。下面这段是 `kernel_clone()` 的主干（形状取自 `kernel/fork.c`，本机没有内核源码树、**未逐行核对**，省略错误分支）：

```c
pid_t kernel_clone(struct kernel_clone_args *args)
{
	u64 clone_flags = args->flags;
	struct completion vfork;
	struct pid *pid;
	struct task_struct *p;
	pid_t nr;

	p = copy_process(NULL, trace, NUMA_NO_NODE, args);
	if (IS_ERR(p))
		return PTR_ERR(p);

	pid = get_task_pid(p, PIDTYPE_PID);
	nr = pid_vnr(pid);

	if (clone_flags & CLONE_PARENT_SETTID)
		put_user(nr, args->parent_tid);

	if (clone_flags & CLONE_VFORK) {
		p->vfork_done = &vfork;
		init_completion(&vfork);
		get_task_struct(p);
	}

	wake_up_new_task(p);

	if (clone_flags & CLONE_VFORK) {
		if (!wait_for_vfork_done(p, &vfork))
			ptrace_event_pid(PTRACE_EVENT_VFORK_DONE, pid);
	}
	put_pid(pid);
	return nr;
}
```

读这段代码要抓住三件事：

1. **`copy_process()` 返回的是 `struct task_struct *`，不是 PID**。PID 在复制完成后才通过 `pid_vnr()` 取出来；`CLONE_PARENT_SETTID` 就是在这一刻把 PID 写回父进程给的地址。
2. **新进程在 `wake_up_new_task()` 之前不可运行**。所有资源复制完成后才入队，所以子进程看不到「复制到一半」的状态。
3. **`vfork` 的父进程阻塞点不在调度器里，而在 `wait_for_vfork_done()` 的 completion 上**；子进程 `exec` 或 `exit` 时 `complete_vfork_done()` 唤醒它。这解释了为什么 `vfork` 子进程不 exec 会把父进程永久挂起。

### `copy_process()` 的资源复制顺序

`copy_process()` 逐项复制，任何一步失败都跳到对应的 `bad_fork_cleanup_*` 标签回滚。Linux 6.8 的顺序如下（`kernel/fork.c`，节选）：

```c
	retval = copy_semundo(clone_flags, p);
	retval = copy_files(clone_flags, p, args->no_files);
	retval = copy_fs(clone_flags, p);
	retval = copy_sighand(clone_flags, p);
	retval = copy_signal(clone_flags, p);
	retval = copy_mm(clone_flags, p);
	retval = copy_namespaces(clone_flags, p);
	retval = copy_io(clone_flags, p);
	retval = copy_thread(p, args);
```

把函数名翻译成用户态可见对象：

| 内核函数 | 复制的对象 | 用户态可见后果 | 对应 flags |
|:--|:--|:--|:--|
| `dup_task_struct()` | `task_struct`、内核栈 | 新 PID/TID、独立调度实体 | 总是 |
| `copy_creds()` | `cred`、capability 集合 | UID/GID 四件套、cap 继承 | 总是（`CLONE_THREAD` 时共享） |
| `copy_files()` | `files_struct`、fd 表 | fd 表独立、表项指向同一 `struct file` | `CLONE_FILES` 则共享 |
| `copy_fs()` | `fs_struct` | `cwd`、`root`、`umask` 独立 | `CLONE_FS` 则共享 |
| `copy_sighand()` | `sighand_struct` | 信号处置表独立 | `CLONE_SIGHAND` 则共享 |
| `copy_signal()` | `signal_struct` | 未决信号清空、定时器清零、`RLIMIT_*` 复制 | `CLONE_THREAD` 则共享 |
| `copy_mm()` | `mm_struct`、页表 | COW 共享物理页 | `CLONE_VM` 则共享 |
| `copy_namespaces()` | `nsproxy` | 命名空间成员关系 | `CLONE_NEW*` 则新建 |
| `copy_io()` | `io_context` | AIO 上下文 | `CLONE_IO` 则共享 |
| `copy_thread()` | 寄存器、栈指针、TLS | 子进程从哪条指令开始跑 | `CLONE_SETTLS` 设 TLS |

这张表能解释两个常见疑问。**第一，为什么 `fork` 后父子 fd 偏移共享，但 `cwd` 不共享**：fd 表复制后表项仍指向同一个 `struct file`（偏移在 `struct file` 里），而 `fs_struct` 是每个进程一份的副本，子进程 `chdir` 不影响父进程。**第二，为什么 `fork` 后 `alarm` 消失**：`copy_signal()` 为新进程分配了新的 `signal_struct`，定时器字段被清零；只有 `CLONE_THREAD` 才共享 `signal_struct`。

::: def 定义 2.7.5 · `copy_process()` 的失败回滚 {#def-2.7.5}
`copy_process()` 内部用 `goto bad_fork_cleanup_*` 形成一条与复制顺序相反的清理链：`copy_thread` 失败清理 `io`，`copy_io` 失败清理 `namespaces`，一直到 `copy_files` 失败清理 `semundo`。任一资源复制失败，已经建立的资源全部释放，`fork()` 返回 `-1`，父进程看不到半成品子进程。
:::

### COW 在页表层的实现

`copy_mm()` 在 `CLONE_VM` 未设置时调用 `dup_mm()`，后者复制 `mm_struct` 并调用 `dup_mmap()` 遍历每一个 `vm_area_struct`。对私有可写映射，`copy_page_range()` 复制页表项，并把父子双方的 PTE 都设为只读；这一步不复制数据页。可以用下面的控制流示意（`mm/memory.c`，非逐行源码）：

```text
copy_page_range(dst_mm, src_mm, vma):
    for each page table page covering vma:
        copy the page-table page
        for each present PTE:
            if PTE is writable and vma is private:
                ptep_set_wrprotect(src)   # 父进程也变只读
                pte = pte_wrprotect(pte)  # 子进程只读
                get_page(page)            # 引用计数 +1
            install pte into child
```

写入时缺页，`do_wp_page()` 判断 `PageAnon()` 与 `page_count()`：引用计数为 1 时可以直接恢复可写（没有别人共享），大于 1 时才真正分配新页并复制。这解释了一个容易忽略的优化：**如果 fork 后父进程先退出，子进程写那页时引用计数已降为 1，内核不必复制**。

::: note 页表复制的成本与 `CLONE_VM`
`fork()` 的成本受 VMA 数量、已建立的页表映射、页类型等影响，不能仅按**虚拟地址空间大小**线性估算。一个预留 1 TiB、只触碰 4 KiB 的稀疏匿名映射，并不因此拥有覆盖整个范围的末级页表页。`CLONE_VM` 共享地址空间，省去了这部分复制；具体快多少要在目标负载上测量，代价则是地址空间不再隔离。
:::

### `clone()` 的 flags 位表

`clone()` 的 `flags` 是一个 64 位整数，低 8 位是「子进程退出时发给父进程的信号」（`CSIGNAL` 掩码 `0xff`，`fork` 用 `SIGCHLD`，线程用 0），其余位选择共享哪些资源。下表按位列出 Linux 6.8 支持的标志：

| flag | 值 | 共享/新建什么 | 典型使用者 |
|:--|--:|:--|:--|
| `CLONE_VM` | `0x00000100` | 共享地址空间与页表 | 线程、`vfork` |
| `CLONE_FS` | `0x00000200` | 共享 `fs_struct`（cwd/root/umask） | 线程 |
| `CLONE_FILES` | `0x00000400` | 共享 fd 表 | 线程 |
| `CLONE_SIGHAND` | `0x00000800` | 共享信号处置表 | 线程 |
| `CLONE_PIDFD` | `0x00001000` | 返回 pidfd 到 `parent_tid` | 服务管理器 |
| `CLONE_PTRACE` | `0x00002000` | 子进程继续被 trace | 调试器 |
| `CLONE_VFORK` | `0x00004000` | 父进程挂起到子进程 exec/exit | `vfork`、`posix_spawn` |
| `CLONE_PARENT` | `0x00008000` | 子进程的父进程是调用者的父进程 | 特殊代理进程 |
| `CLONE_THREAD` | `0x00010000` | 同一线程组（同 TGID） | pthread |
| `CLONE_NEWNS` | `0x00020000` | 新 mount 命名空间 | 容器 |
| `CLONE_SYSVSEM` | `0x00040000` | 共享 System V 信号量 undo 列表 | 线程 |
| `CLONE_SETTLS` | `0x00080000` | 设置子进程 TLS | pthread |
| `CLONE_PARENT_SETTID` | `0x00100000` | 把子 PID 写到父进程给的地址 | 线程库 |
| `CLONE_CHILD_CLEARTID` | `0x00200000` | 子进程退出时清零 `child_tid` 并 futex 唤醒 | pthread join |
| `CLONE_DETACHED` | `0x00400000` | 已废弃，忽略 | — |
| `CLONE_UNTRACED` | `0x00800000` | 阻止父进程强制 `CLONE_PTRACE` | 调试器 |
| `CLONE_CHILD_SETTID` | `0x01000000` | 把子 TID 写到子进程地址 | 线程库 |
| `CLONE_NEWCGROUP` | `0x02000000` | 新 cgroup 命名空间 | 容器 |
| `CLONE_NEWUTS` | `0x04000000` | 新 UTS 命名空间（hostname） | 容器 |
| `CLONE_NEWIPC` | `0x08000000` | 新 IPC 命名空间 | 容器 |
| `CLONE_NEWUSER` | `0x10000000` | 新 user 命名空间 | 无根容器 |
| `CLONE_NEWPID` | `0x20000000` | 新 PID 命名空间 | 容器 |
| `CLONE_NEWNET` | `0x40000000` | 新网络命名空间 | 容器 |
| `CLONE_IO` | `0x80000000` | 共享 `io_context` | 很少用 |
| `CLONE_CLEAR_SIGHAND` | `0x100000000` | 子进程信号处置全部复位 | 5.5+ |
| `CLONE_INTO_CGROUP` | `0x200000000` | 子进程直接放进指定 cgroup v2 | 5.7+ |

几条组合规则在内核里是硬性的，违反直接 `EINVAL`：

- `CLONE_THREAD` 必须同时有 `CLONE_SIGHAND`；
- `CLONE_SIGHAND` 必须同时有 `CLONE_VM`；
- `CLONE_THREAD` 不能与 `CLONE_NEWUSER`/`CLONE_NEWPID` 同用；
- `CLONE_NEWUSER` 不能与 `CLONE_FS` 同用（用户命名空间的 `fs_struct` 语义会冲突）；
- `CLONE_PIDFD` 与 `CLONE_PARENT_SETTID` 指向同一地址时非法；
- `CLONE_VM` 但既没有 `CLONE_THREAD` 也没有 `CLONE_VFORK` 时，内核会警告并拒绝（容易出现两个进程共享地址空间却互不协调）。

::: errata 关于 `clone()` 的四个误解
1. **「`clone` 的 `stack` 参数是栈底」**——它是**栈顶**，且必须按 16 字节对齐（x86-64 的 ABI 要求）。传 `buf` 而不是 `buf + size`，子进程一压栈就写坏相邻内存。
2. **「`CLONE_VM` 就是线程」**——线程还需要 `CLONE_THREAD`（同 TGID、共享 `signal_struct`）。只有 `CLONE_VM` 的两个进程共享地址空间，但各自有独立的信号与退出状态，`ps -L` 看不到第二个线程。
3. **「`clone` 子进程可以 `return`」**——glibc 包装函数在 `fn` 返回后会走退出路径，但如果你用裸 `syscall(SYS_clone)`，子进程返回到调用点继续执行父进程的代码，几乎必然出错。裸 clone 的子进程必须自己 `syscall(SYS_exit, 0)`。
4. **「`CLONE_CHILD_CLEARTID` 只是清个变量」**——它还会在清零后执行 `futex(FUTEX_WAKE)`，这是 `pthread_join` 的底层机制。清错地址会让 join 永久睡眠。
:::

### `clone3()`：结构体版本与大小协商

`clone()` 的参数已经多到需要 5 个寄存器加栈上传参，Linux 5.3 引入 `clone3()`，把所有参数放进一个可扩展的结构体：

```c
struct clone_args {
    __aligned_u64 flags;        /* 同 clone 的 flags */
    __aligned_u64 pidfd;        /* CLONE_PIDFD：返回 pidfd 的地址 */
    __aligned_u64 child_tid;    /* CLONE_CHILD_SETTID */
    __aligned_u64 parent_tid;   /* CLONE_PARENT_SETTID */
    __aligned_u64 exit_signal;  /* 子进程退出信号，默认 SIGCHLD */
    __aligned_u64 stack;        /* 子进程栈顶 */
    __aligned_u64 stack_size;   /* 5.5+：栈大小，用于自动增长 */
    __aligned_u64 tls;          /* CLONE_SETTLS */
    __aligned_u64 set_tid;      /* 5.7+：指定 PID 数组地址 */
    __aligned_u64 set_tid_size; /* 数组长度，按 PID 命名空间层级 */
    __aligned_u64 cgroup;       /* 5.7+：CLONE_INTO_CGROUP 的目标 cgroup fd */
};
```

`clone3()` 的第二个参数是结构体大小，内核用「大小协商」实现向前兼容：旧内核看到比自己认识的结构体更大时返回 `EINVAL`，调用者应退回到较小的结构体或 `clone()`。glibc 没有为 `clone3` 提供包装，需要用 `syscall(SYS_clone3, &args, sizeof args)`，并且必须处理 `ENOSYS`（旧内核或 seccomp 拦截）：

```c
long ret = syscall(SYS_clone3, &args, sizeof args);
if (ret == -1 && errno == ENOSYS) {
    /* 退回 clone()：功能子集，但至少能跑 */
    ret = clone(child_fn, stack_top, (int)args.flags, NULL);
}
```

`clone3` 独有的能力是 `set_tid`：它允许调用者在**新 PID 命名空间**里指定子进程的 PID，容器运行时用它构造「容器内 PID 1」以及可预测的进程号。没有 `CAP_CHECKPOINT_RESTORE`（或 `CAP_SYS_ADMIN`）时会被拒绝，这是 `EPERM` 的来源之一。

### `vfork()` 的真实语义

`vfork()` 不是「更快的 fork」，而是「借用父进程地址空间的 fork」：内核用 `CLONE_VM | CLONE_VFORK` 创建子进程，父进程在 `wait_for_vfork_done()` 上睡眠，直到子进程调用 `execve()` 或 `_exit()`。子进程与父进程共享**同一套页表和同一个栈**，所以：

- 子进程修改任何局部变量，父进程恢复后看到的是被改过的值；
- 子进程从函数 `return`，会返回到父进程的调用栈，行为未定义；
- 子进程调用 `exit()`，会 flush 父进程的 stdio 缓冲区并运行父进程的 `atexit` 处理器；
- 子进程调用 `longjmp()`、信号处理器、任何可能改栈的库函数，都可能破坏父进程。

正确写法只有一个形状：

```c
pid_t pid = vfork();
if (pid == 0) {
    execve(path, argv, environ);   /* 唯一目的 */
    _exit(127);                    /* exec 失败也必须 _exit */
}
```

现代代码不应再手写 `vfork`。`posix_spawn()` 在 glibc 里正是用 `clone(CLONE_VM | CLONE_VFORK)` 实现，把「共享地址空间、立刻 exec、失败只 `_exit`」封装好，还额外处理了 signal mask、调度属性、file actions（[2.7.4](#sec-2.7.4)）。`vfork` 唯一还有意义的场景是极老的内核或没有 `posix_spawn` 的嵌入式 libc。

::: intuition 为什么 vfork 曾经很重要
在没有 COW 的早期 Unix 上，`fork` 要物理复制整个地址空间，而 `fork` 之后往往立刻 `exec`，复制全是浪费。`vfork` 用「共享 + 挂起父进程」把这次复制降为零。COW 出现后，`fork+exec` 的成本已经接近页表复制，`vfork` 的收益只剩下「不复制页表」；但它的约束和未定义行为远多于收益。
:::

### 失败账本：`fork`/`clone` 的 errno

| errno | 触发条件 | 怎么确认 |
|:--|:--|:--|
| `EAGAIN` | 达到 `RLIMIT_NPROC`（按**真实 UID** 统计，不是按进程）；达到 `kernel.threads-max`；cgroup v2 `pids.max`；`kernel.pid_max` 耗尽；user namespace 的 `pids.max` | `ulimit -u`、`cat /proc/sys/kernel/threads-max`、`cat /sys/fs/cgroup/pids.max`、`cat /proc/sys/kernel/pid_max` |
| `ENOMEM` | 内核无法分配 `task_struct`、内核栈、页表；内存 cgroup 到顶 | `dmesg`、`/sys/fs/cgroup/memory.events` 的 `oom` 计数 |
| `EPERM` | `clone` 请求了需要特权的 flag（如 `CLONE_NEWPID` 无 `CAP_SYS_ADMIN`、`CLONE_INTO_CGROUP` 无权限） | 检查 capability 与 seccomp |
| `EINVAL` | flags 组合非法、`clone3` 结构体大小不被支持、栈未对齐 | 对照上一节的组合规则 |
| `ENOSYS` | 内核不支持 `clone3`，或被 seccomp 过滤 | `grep clone3 /proc/kallsyms`（需 root）或试 `clone()` |
| `EFAULT` | `parent_tid`/`child_tid`/`set_tid` 指向不可写内存 | 检查指针与 `CLONE_*_SETTID` 是否配对 |

`RLIMIT_NPROC` 的统计口径值得单独记：它按**真实用户 ID** 统计该用户当前拥有的进程/线程数，而不是按单个进程。一个以 `nobody` 运行的服务 fork 出 200 个线程后，同一 UID 下的另一个进程也可能开始 `EAGAIN`。容器里更常见的上限是 cgroup `pids.max`，它统计的是 cgroup 内的任务数（线程也算），与 `RLIMIT_NPROC` 相互独立。

下面这个程序用 `clone()` 手工构造一个「共享地址空间、但不共享线程组」的子进程，并与 `fork()` 对比，验证 flags 到底共享了什么。

```c
/* clone_demo.c：clone(CLONE_VM|...) 与 fork() 的可见性对比 */
#include <errno.h>
#include <sched.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/syscall.h>
#include <sys/wait.h>
#include <unistd.h>

#define STACK_SIZE (1u << 20)

static int shared_counter;        /* clone 子进程直接改这里 */
static pid_t child_tid;           /* CLONE_CHILD_SETTID 写入子 TID */
static char child_stack[STACK_SIZE] __attribute__((aligned(16)));

static void die(const char *msg)
{
    perror(msg);
    exit(EXIT_FAILURE);
}

static int clone_child(void *arg)
{
    (void)arg;
    shared_counter = 42;          /* 共享地址空间：父进程可见 */
    /* 不再手工写 child_tid：让 CLONE_CHILD_SETTID 自己写，才能验证该 flag */
    return 0;
}

int main(void)
{
    int flags = CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND |
                CLONE_CHILD_SETTID | SIGCHLD;

    /* 栈顶 = 数组末地址；x86-64 要求 16 字节对齐 */
    /* glibc clone 变参顺序：arg, parent_tid, tls, child_tid */
    pid_t pid = clone(clone_child, child_stack + STACK_SIZE, flags,
                      NULL, NULL, NULL, &child_tid);
    if (pid == -1)
        die("clone");

    int status;
    if (waitpid(pid, &status, 0) == -1)
        die("waitpid clone child");
    printf("clone: pid=%ld tid=%ld shared_counter=%d exited=%d\n",
           (long)pid, (long)child_tid, shared_counter,
           WIFEXITED(status) ? WEXITSTATUS(status) : -1);

    /* 对照：fork 的子进程写同一变量，父进程看不到 */
    shared_counter = 0;
    pid = fork();
    if (pid == -1)
        die("fork");
    if (pid == 0) {
        shared_counter = 99;      /* COW：子进程私有副本 */
        _exit(0);
    }
    if (waitpid(pid, &status, 0) == -1)
        die("waitpid fork child");
    printf("fork : pid=%ld shared_counter=%d (父进程仍是 0)\n",
           (long)pid, shared_counter);
    return EXIT_SUCCESS;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -g clone_demo.c -o clone_demo
./clone_demo
```

```text
# 实测：ubuntu 24.04.5 / aarch64，内核 7.0.0-38-generic（PID 为当次真值，连跑两次同结构）
clone: pid=23399 tid=23399 shared_counter=42 exited=0
fork : pid=23400 shared_counter=0 (父进程仍是 0)
```

第一行里 `pid == tid` 是因为没有 `CLONE_THREAD`：子进程是新线程组的组长。`shared_counter=42` 证明 `CLONE_VM` 让父子看到同一份物理页；第二行证明 `fork` 的 COW 隔离。

「把 `CLONE_VM` 去掉会怎样」这件事值得真跑，因为直觉答案错的。本机实测三档（ubuntu 24.04.5 / aarch64）：

```text
# 实测：改 flags 后重编重跑，PID/TID 为当次真值
原样（CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_CHILD_SETTID|SIGCHLD）
  clone: pid=23399 tid=23399 shared_counter=42 exited=0
只去掉 CLONE_VM（保留 CLONE_SIGHAND）
  clone: Invalid argument                     # errno=EINVAL，程序直接失败
同时去掉 CLONE_VM 与 CLONE_SIGHAND
  clone: pid=24492 tid=0 shared_counter=0 exited=0
```

第二档直接失败，`errno` 为 `EINVAL`。原因是 `CLONE_SIGHAND` 要求同时有 `CLONE_VM`：共享信号处置必须建立在共享地址空间之上（见 [2.7.4](#sec-2.7.4) 的 flag 表），内核在 `copy_process` 的参数校验阶段就拒绝了这种组合。

第三档跑通，两个读数都能说明内存隔离了。`shared_counter=0` 是直接的证据；`tid=0` 是间接的证据——`CLONE_CHILD_SETTID` 让内核在子进程自己的地址空间里写 `child_tid` 变量，没有 `CLONE_VM` 时这一写落在子进程的私有副本上，父进程那份仍是初值 0。所以 flags 虽然可组合，组合之间却有依赖约束，试错时看 `errno` 比猜语义快。

::: ex 例 2.7.3 · 去掉一个 flag 会怎样 {#ex-2.7.3}
**先猜**：`clone` 的 flags 原本是 `CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_CHILD_SETTID|SIGCHLD`。现在只去掉 `CLONE_VM`，程序会 (a) 照样跑、只是共享变量看不到了，(b) 直接失败，还是 (c) 跑通且 `child_tid` 正常写回？先选一个再往下看。

本机实测选 **(b)**：`clone: Invalid argument`，`errno=EINVAL`。原因是 `CLONE_SIGHAND` 依赖 `CLONE_VM`，内核在参数校验阶段就拒绝了。把 `CLONE_SIGHAND` 一并去掉才跑通，此时 `shared_counter=0`、`tid=0`。

迁移题：为什么 `tid=0` 反而成了内存隔离的证据？答：`CLONE_CHILD_SETTID` 让内核在子进程自己的地址空间里写 `child_tid`；没有 `CLONE_VM` 时父子内存已隔离，这一写落在子进程的私有副本上，父进程那份仍是初值 0。若共享地址空间，父进程就会读到子进程的真实 TID。
:::

### 2.7.7 小结

四个用户态入口收敛到同一个 `kernel_clone()`，再进 `copy_process()` 按固定顺序逐项复制，最后 `copy_thread` 造出子进程的内核栈与寄存器现场、`wake_up_new_task` 让它可调度。记住这个顺序的用处是解释继承清单：fd 表在复制清单里，所以偏移共享；`fcntl` 记录锁不在清单里，所以子进程不持有父进程的记录锁。失败时按相反次序回滚，这也是 `fork` 的 errno 表能分成「参数与约束」「资源上限」「内核内存」三类的原因。

本机的符号核对给这条链补了两个边界。一是入口名按架构换：aarch64 上是 `el0_svc` → `invoke_syscall` → `__arm64_sys_clone`，x86 那三个名字在本机 `kallsyms` 里全为 0 命中。二是「符号存在」不等于「这个架构能调到」：`__arm64_sys_fork` 与 `__arm64_sys_vfork` 都查得到，但调用号表里没有 `__NR_fork`/`__NR_vfork`，用户态实际走的是 `clone`。反过来，`copy_files`、`copy_mm` 查不到也不代表内核没有这两个函数，静态或内联的实现不进 `kallsyms`。如果只记住一件事，那就是：**机制与复制顺序跨架构相同，入口符号与调用号跨架构全不同；核对时把「查得到」「查不到」「用得到」当成三件事分开判。**

::: method 即时自测 · 2.7.7
**Q1（记忆）** `fork`/`vfork`/`clone`/`clone3` 四个入口在内核里收敛到哪个函数？`copy_process()` 之后紧接着哪两步让子进程真正能跑？

**Q2（辨析）** 本机 `kallsyms` 里 `__arm64_sys_fork` 命中 1 次，但 `/usr/include/asm-generic/unistd.h` 里没有 `__NR_fork`。这两件事矛盾吗？`copy_mm` 命中 0 次，能否据此说内核没有这个函数？

**Q3（应用）** 你把 `clone` 的 flags 从 `CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_CHILD_SETTID|SIGCHLD` 改成只去掉 `CLONE_VM`，程序报 `EINVAL`。请说出根因与两种可行改法，并解释为什么改通之后父进程读到的 `child_tid` 是 0。

::: sol 答案
**A1** 收敛到 `kernel_clone()`，真正的复制在 `copy_process()`。之后两步是 `copy_thread`（造子进程的内核栈与寄存器现场，让它从返回 0 的位置开始执行）与 `wake_up_new_task`（把子进程放进调度器，使它可被调度）。带 `CLONE_VFORK` 时父进程还会在 `wait_for_vfork_done` 上挂起，直到子进程 exec 或退出。
**A2** 不矛盾。内核用 `SYSCALL_DEFINE0` 定义了 `fork`/`vfork` 入口，所以符号存在；但 aarch64 的系统调用表没有给它们分配调用号，用户态无法直接发起，glibc 改用 `clone`（号 220）实现同样的语义。「符号在」与「这个架构上能调到」是两件事。`copy_mm` 命中 0 次也不能说明内核没有它：静态函数、被内联或改名的实现都不进 `kallsyms`，查不到只说明「这张符号表里没有这个名字」。
**A3** 根因是 `CLONE_SIGHAND` 依赖 `CLONE_VM`，去掉后者就构成非法组合，内核在参数校验阶段返回 `EINVAL`。两种改法：① 把 `CLONE_SIGHAND` 一并去掉（本机实测可行，得到 `shared_counter=0`）；② 保留 `CLONE_VM`，改用别的方式隔离内存——但那样就回到共享地址空间，达不到隔离目的，所以真要隔离就选 ①，或直接用 `fork`。改通之后父进程读到 `child_tid` 为 0，是因为 `CLONE_CHILD_SETTID` 让内核在**子进程的**地址空间里写那个变量；没有 `CLONE_VM` 时父子内存已隔离，这一写落在子进程的私有副本上，父进程那份保持初值 0。
:::

## 2.7.8 `wait` 家族：从 `wait()` 到 `waitid()` 的全选项 {#sec-2.7.8}

这一节回答：`wait`、`waitpid`、`waitid`、`wait3`、`wait4` 到底差在哪，`waitid` 的 `idtype` 和 flags 怎么组合，`WNOWAIT` 与 `P_PIDFD` 解决什么问题，`rusage` 的每个字段从哪里来。

::: preview 先抓住一件事
五个接口不是五种能力，而是同一件事的五种取法：等谁（任一 / 指定 PID / 进程组 / pidfd）、等哪些事件（退出 / 停止 / 继续）、要不要阻塞、要不要附带资源统计。`wait` 最简，`waitpid` 加上「等谁」和「非阻塞」，`waitid` 把事件选择显式化并改用 `siginfo_t` 交付结果，`wait3`/`wait4` 再多给一份 `rusage`。两个最容易读反的地方：`waitid` 成功返回 0 而不是子进程 PID，`WNOWAIT` 是「看了但不收尸」而不是「不等待」。
:::

### 五个等待接口的矩阵

| 接口 | 签名要点 | 能等到的事件 | 额外输出 | 限制 |
|:--|:--|:--|:--|:--|
| `wait` | `pid_t wait(int *status)` | 任一子进程退出/停止 | 无 | 无法指定进程，无法非阻塞 |
| `waitpid` | `pid_t waitpid(pid_t pid, int *status, int options)` | 指定/任一组子进程 | 无 | `pid` 语义有四种重载 |
| `waitid` | `int waitid(idtype_t idtype, id_t id, siginfo_t *infop, int options)` | 按 ID 类型选，事件由 flags 选 | `siginfo_t` | 成功返回 0，失败 -1 |
| `wait3` | `pid_t wait3(int *status, int options, struct rusage *ru)` | 任一子进程 | `rusage` | 已过时，BSD 兼容 |
| `wait4` | `pid_t wait4(pid_t pid, int *status, int options, struct rusage *ru)` | 指定/任一子进程 | `rusage` | `waitpid` + 资源统计 |

`waitpid` 的第一个参数有四种语义，这是它最容易读错的地方：

| `pid` 取值 | 等待谁 |
|:--|:--|
| `> 0` | PID 等于 `pid` 的那个子进程 |
| `-1` | 任意一个子进程 |
| `0` | 与调用者在**同一进程组**的任意子进程 |
| `< -1` | 进程组 ID 等于 `-pid` 的任意子进程 |

`waitid` 把「等谁」和「等什么事件」拆成两个参数，因此表达能力更强：

| `idtype` | `id` 的含义 | 引入版本 |
|:--|:--|:--|
| `P_ALL` | 忽略 `id`，等待任意子进程 | POSIX |
| `P_PID` | 等待 PID 等于 `id` 的子进程 | POSIX |
| `P_PGID` | 等待进程组等于 `id` 的子进程 | POSIX |
| `P_PIDFD` | `id` 是 pidfd（不是 PID） | Linux 5.4 |

`P_PIDFD` 的价值在于消除 PID 回绕带来的竞态：`pidfd_open(pid)` 得到的 fd 绑定到那个进程对象，即使目标退出、PID 被复用，fd 也不会指向新进程。服务管理器（systemd、容器运行时）用 pidfd 发信号、等待退出，避免「kill 错进程」。

### `waitid` 的 flags 与事件选择

| flag | 值 | 含义 | 备注 |
|:--|--:|:--|:--|
| `WEXITED` | `0x4` | 等待退出事件 | 与 `WSTOPPED`/`WCONTINUED` 可组合 |
| `WSTOPPED` | `0x2` | 等待停止事件 | 等价于 `waitpid` 的 `WUNTRACED` |
| `WCONTINUED` | `0x8` | 等待 `SIGCONT` 继续事件 | Linux 2.6.10+ |
| `WNOHANG` | `0x1` | 非阻塞，没有事件立即返回 | 返回 0，`si_pid == 0` |
| `WNOWAIT` | `0x01000000` | 只取信息，不回收子进程 | 子进程仍是僵尸，可再次等待 |
| `__WNOTHREAD` | `0x20000000` | 只等调用线程的子进程 | Linux 专有 |
| `__WALL` | `0x40000000` | 等待所有子进程，包括 `clone` 的 | Linux 专有 |
| `__WCLONE` | `0x80000000` | 只等 `clone` 且退出信号不是 `SIGCHLD` 的 | Linux 专有 |

`waitid` 必须至少指定一个事件位，否则 `EINVAL`。`waitpid` 的 `options` 则是另一套常量（`WNOHANG`、`WUNTRACED`、`WCONTINUED`），两套名字相似但值不同，不能混用。

::: errata 关于 `waitid` 的三个误解
1. **「`waitid` 返回子进程 PID」**——成功时返回 **0**，子进程信息在 `siginfo_t` 里。用返回值判断「等到了谁」会永远得到 0。
2. **「`WNOHANG` 没事件时 `si_pid` 是 -1」**——`waitid` 返回 0，`si_pid == 0`；`-1` 只表示出错（如 `ECHILD`）。
3. **「`WNOWAIT` 等于不等待」**——它照常阻塞等待事件，只是**不把子进程从僵尸队列摘除**。事件已经被「看过」，下次 `wait` 仍能拿到同一个退出状态。
:::

### 状态字与 `siginfo_t` 的解码

`wait`/`waitpid`/`wait4` 返回的 `int status` 是位打包的，必须用宏解码，不能直接和退出码比较：

| 宏 | 含义 | 位布局（Linux/glibc） |
|:--|:--|:--|
| `WIFEXITED(status)` | 正常退出 | `(status & 0x7f) == 0` |
| `WEXITSTATUS(status)` | 退出码低 8 位 | `(status >> 8) & 0xff` |
| `WIFSIGNALED(status)` | 被信号杀死 | `((status & 0x7f) + 1) >> 1 > 0` |
| `WTERMSIG(status)` | 致死信号编号 | `status & 0x7f` |
| `WCOREDUMP(status)` | 是否产生 core | `status & 0x80` |
| `WIFSTOPPED(status)` | 被信号停止 | `(status & 0xff) == 0x7f` |
| `WSTOPSIG(status)` | 停止信号编号 | `(status >> 8) & 0xff` |
| `WIFCONTINUED(status)` | 被 `SIGCONT` 继续 | `status == 0xffff` |

`waitid` 的 `siginfo_t` 把这些信息拆成字段：`si_pid`（谁）、`si_uid`（真实 UID）、`si_status`（退出码或信号号）、`si_code`（事件类型）。`si_code` 的取值决定了 `si_status` 怎么读：

| `si_code` | 含义 | `si_status` 是什么 |
|:--|:--|:--|
| `CLD_EXITED` | 正常退出 | 退出码（0–255） |
| `CLD_KILLED` | 被信号杀死，无 core | 信号编号 |
| `CLD_DUMPED` | 被信号杀死，有 core | 信号编号 |
| `CLD_TRAPPED` | 被 ptrace 捕获 | 陷阱信号 |
| `CLD_STOPPED` | 被信号停止 | 停止信号 |
| `CLD_CONTINUED` | 被 `SIGCONT` 继续 | `SIGCONT` |

`CLD_*` 与 `WIF*` 是两套编码，不要交叉使用：`si_code == CLD_EXITED` 时读 `si_status`，而不是 `WEXITSTATUS(si_status)`。

### `WNOWAIT`：先看后收

`WNOWAIT` 的经典用途是「两阶段回收」：先确认子进程的死因与资源用量，再决定是否回收。比如一个监控进程想记录每个子进程的 `rusage`，又不想在记录过程中让 PID 被复用；或者调试器想在回收前读取 `/proc/{pid}/stat`。

```c
siginfo_t si = {0};
if (waitid(P_PID, pid, &si, WEXITED | WNOWAIT) == -1)
    /* 错误 */;
/* 此时子进程仍是僵尸：/proc/<pid>/stat 的 state 是 Z */
/* 读完信息后，再真正回收 */
if (waitpid(pid, NULL, 0) == -1)
    /* 错误 */;
```

注意 `WNOWAIT` 与 `WNOHANG` 可以组合：`WEXITED | WNOHANG | WNOWAIT` 表示「如果有已退出的子进程，只报告不回收」。这对「先扫一遍所有僵尸再统一处理」很有用。

### `wait4` 与 `rusage` 的字段

`wait4()` 在回收的同时把子进程（及其已回收的后代）的资源统计写到 `struct rusage`。字段来自内核的 `task_struct` 累加，单位要看清：

| 字段 | 单位 | 含义 | 何时为 0 |
|:--|:--|:--|:--|
| `ru_utime` | `timeval` | 用户态 CPU 时间 | 子进程没跑够一个 tick |
| `ru_stime` | `timeval` | 内核态 CPU 时间 | 同上 |
| `ru_maxrss` | KiB | 峰值 RSS | 子进程从未驻留（几乎不可能） |
| `ru_minflt` | 次 | 次缺页（无 I/O） | 页全部预热 |
| `ru_majflt` | 次 | 主缺页（有 I/O） | 全部命中页缓存 |
| `ru_inblock` | 块（512 B） | 读磁盘次数 | 全走页缓存 |
| `ru_oublock` | 块（512 B） | 写磁盘次数 | 写被缓存吸收 |
| `ru_nvcsw` | 次 | 自愿上下文切换 | 从不阻塞 |
| `ru_nivcsw` | 次 | 非自愿上下文切换 | 从不被抢占 |
| `ru_nsignals` | 个 | 收到的信号数 | 无信号 |

`ru_maxrss` 在 Linux 上是 **KiB**，在 macOS/BSD 上是字节；跨平台代码要除以 1024 的差异。`ru_inblock`/`ru_oublock` 统计的是实际块设备 I/O，不是 `read`/`write` 调用次数，页缓存命中时不增加。

::: note `wait3`/`wait4` 的可移植性
`wait3`/`wait4` 是 BSD 遗产，POSIX 没有标准化。`wait4` 在 Linux、macOS、FreeBSD 都有，但 `struct rusage` 的字段和单位有差异。可移植代码要么用 `waitpid` + `getrusage(RUSAGE_CHILDREN)`（统计所有已回收子进程的累计值），要么自己封装 `wait4` 并用 `#ifdef` 处理单位。
:::

### 内核侧：`do_wait()` 的控制流

`wait4()` 进入内核后走 `kernel_wait4()` → `do_wait()`。控制流可以用下面的伪代码概括（`kernel/exit.c`，非逐行源码）：

```text
do_wait(wo):
    repeat:
        for each child p of current:
            ret = wait_consider_task(wo, 0, p)
            if ret != 0: return ret          # 找到事件或出错
        if wo->notask_error == 0 and wo->wo_flags & WNOHANG:
            return 0                          # 非阻塞：无事件
        set_current_state(TASK_INTERRUPTIBLE)
        if signal_pending(current): return -ERESTARTSYS
        schedule()                            # 睡眠，等 SIGCHLD 唤醒
    until 有事件
```

关键点：

- **`wait` 的唤醒靠 `SIGCHLD`**：子进程退出时 `do_notify_parent()` 给父进程发 `SIGCHLD`，父进程从 `schedule()` 醒来重新扫描。如果 `SIGCHLD` 被阻塞，`wait` 仍能被唤醒（内核在 `wait_task_zombie()` 里直接 `wake_up_parent()`），但用户态的 `sigsuspend` 等不到。
- **`WNOWAIT` 在 `wait_consider_task()` 里体现为「报告但不 `release_task()`」**：事件被复制到 `siginfo`，子进程留在僵尸链上。
- **`ECHILD` 在扫描不到任何子进程时设置**；`WNOHANG` 且有子进程但无事件时返回 0，不设置 `errno`。

下面这个程序把 `waitid` 的停止、退出、`WNOWAIT` 与 `wait4` 的 `rusage` 串起来，并直接读 `/proc/{pid}/stat` 验证僵尸状态。

```c
/* waitid_peek.c：WSTOPPED → 手动 SIGCONT → WNOWAIT 窥视 → wait4 回收 */
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/resource.h>
#include <sys/wait.h>
#include <unistd.h>

static void die(const char *msg)
{
    perror(msg);
    exit(EXIT_FAILURE);
}

/* 读 /proc/<pid>/stat 的第三个字段（state）；comm 可能含空格，先找最后一个 ')' */
static char proc_state(pid_t pid)
{
    char path[64], buf[512];
    snprintf(path, sizeof path, "/proc/%ld/stat", (long)pid);
    FILE *fp = fopen(path, "r");
    if (fp == NULL)
        return '?';
    if (fgets(buf, sizeof buf, fp) == NULL) {
        fclose(fp);
        return '?';
    }
    fclose(fp);
    char *p = strrchr(buf, ')');
    if (p == NULL || p[1] != ' ')
        return '?';
    return p[2];
}

int main(void)
{
    pid_t pid = fork();
    if (pid == -1)
        die("fork");

    if (pid == 0) {
        /* 子进程：先分配并触碰 8 MiB，制造可观测的 rusage */
        size_t len = 8u << 20;
        char *p = malloc(len);
        if (p == NULL)
            _exit(120);
        for (size_t i = 0; i < len; i += 4096)
            p[i] = 1;
        raise(SIGSTOP);             /* 停在这里等父进程 */
        p[0] = 2;                   /* 继续后改一页 */
        _exit(7);
    }

    siginfo_t si;
    memset(&si, 0, sizeof si);

    /* 1. 等停止事件：WSTOPPED 不能省 */
    if (waitid(P_PID, (id_t)pid, &si, WSTOPPED) == -1)
        die("waitid WSTOPPED");
    printf("stopped : code=%d status=%d state=%c\n",
           si.si_code, si.si_status, proc_state(pid));
    if (si.si_code != CLD_STOPPED || si.si_status != SIGSTOP) {
        fprintf(stderr, "unexpected stop event\n");
        return EXIT_FAILURE;
    }

    if (kill(pid, SIGCONT) == -1)
        die("kill SIGCONT");

    /* 2. 等退出事件，但先不回收 */
    memset(&si, 0, sizeof si);
    if (waitid(P_PID, (id_t)pid, &si, WEXITED | WNOWAIT) == -1)
        die("waitid WEXITED|WNOWAIT");
    printf("peek    : code=%d status=%d state=%c\n",
           si.si_code, si.si_status, proc_state(pid));
    if (si.si_code != CLD_EXITED || si.si_status != 7) {
        fprintf(stderr, "unexpected exit event\n");
        return EXIT_FAILURE;
    }

    /* 3. 真正回收，同时拿 rusage */
    struct rusage ru;
    int status;
    if (wait4(pid, &status, 0, &ru) == -1)
        die("wait4");
    printf("reaped  : exited=%d code=%d maxrss=%ldKiB minflt=%ld\n",
           WIFEXITED(status), WEXITSTATUS(status),
           (long)ru.ru_maxrss, (long)ru.ru_minflt);
    printf("after   : /proc/%ld/stat state=%c (进程已消失)\n",
           (long)pid, proc_state(pid));

    /* 4. 再等一次：ECHILD */
    errno = 0;
    if (waitid(P_PID, (id_t)pid, &si, WEXITED | WNOHANG) == -1)
        printf("again   : errno=%d (%s)\n", errno, strerror(errno));
    else
        printf("again   : si_pid=%d\n", (int)si.si_pid);
    return EXIT_SUCCESS;
}
```

```text
# 实测：ubuntu 24.04.5 / aarch64，glibc 2.39（PID 与 maxrss/minflt 为当次真值，连跑两次略有浮动）
stopped : code=5 status=19 state=T
peek    : code=1 status=7 state=Z
reaped  : exited=1 code=7 maxrss=8864KiB minflt=2080
after   : /proc/26606/stat state=? (进程已消失)
again   : errno=10 (No child processes)
```

关键行是 `peek`：`si_code=1`（`CLD_EXITED`）、`si_status=7`，而 `/proc` 里状态仍是 `Z`，说明 `WNOWAIT` 只报告不回收。`reaped` 行里 `maxrss` 约为 8 MiB 加上 libc/栈，`minflt` 是子进程触碰 8 MiB 产生的次缺页数；这两个值每次跑会有几 KiB、几个页的浮动（第二次实测是 `maxrss=8872KiB minflt=2079`），不要当固定常数背。

`stopped` 那一行的 `code=5` 值得单独核一下：本机编译打印 `<sys/wait.h>` 的常量得到 `CLD_EXITED=1 CLD_KILLED=2 CLD_DUMPED=3 CLD_TRAPPED=4 CLD_STOPPED=5 CLD_CONTINUED=6`，所以 **5 才是「被停止」，2 是「被信号杀死」**，两者含义完全不同。旧稿这里写成 2，已按实测订正。常量值由 libc 提供、不同实现可能不同，代码里一律用宏而不是硬编码数字。

::: method 选哪个等待接口
1. 只有一个子进程、不需要统计：`waitpid(pid, &st, 0)`；
2. 要处理停止/继续：`waitpid(pid, &st, WUNTRACED | WCONTINUED)`，或 `waitid` 显式选事件；
3. 要死因与 UID：`waitid`，读 `si_code`/`si_uid`；
4. 要资源用量：`wait4`，或 `waitid` + `getrusage(RUSAGE_CHILDREN)`（累计值，不是单个子进程）；
5. 要避免 PID 复用竞态：`pidfd_open` + `waitid(P_PIDFD, ...)`；
6. 要先观察后回收：`WNOWAIT`，读完 `/proc` 或 `rusage` 再 `waitpid`。
:::

### 2.7.8 小结

选接口时按四个问题走：等谁、等哪些事件、要不要阻塞、要不要资源统计。`wait` 只回答「有孩子结束了吗」，`waitpid` 加上「等谁」与 `WNOHANG`，`waitid` 把事件选择显式化并改用 `siginfo_t` 交付，`wait3`/`wait4` 再多给一份 `rusage`。`waitpid` 的第一个参数有四种语义（正数、0、-1、小于 -1），这是最容易读错的地方。

`waitid` 有两处与 `waitpid` 相反，本机都核过。成功时它返回 0 而不是子进程 PID，子进程信息在 `siginfo_t` 里；`WNOHANG` 且无事件时也是返回 0，靠 `si_pid == 0` 区分。`WNOWAIT` 的意思是「报告但不回收」：本机 `waitid_peek` 里 `peek` 那一步读到 `si_code=1`、`si_status=7`，而 `/proc/<pid>/stat` 的状态仍是 `Z`，直到后面 `wait4` 才真正收尸。同一份输出还纠正了一个常量：`CLD_STOPPED` 在本机 glibc 2.39 上是 5，2 是 `CLD_KILLED`，两者含义完全不同，代码里要用宏不要写数字。

需要长期持有子进程引用时用 `pidfd_open` + `waitid(P_PIDFD, …)`，避免 PID 被复用之后等错对象；要资源用量就用 `wait4`，或 `waitid` 配 `getrusage(RUSAGE_CHILDREN)`，但后者是累计值、不是单个子进程的。如果只记住一件事，那就是：**`waitid` 成功返回 0、`WNOWAIT` 看了不收尸，这两条与 `waitpid` 的直觉相反，写错就会漏回收或等错进程。**

**Q1（记忆）** `waitid` 成功时返回什么？`WNOHANG` 且没有事件时怎么判断？本机 `CLD_EXITED`、`CLD_KILLED`、`CLD_STOPPED` 各是多少？

**Q2（辨析）** `WNOWAIT` 与 `WNOHANG` 都带「不」字，它们各自否定的是什么？本机 `waitid_peek` 的哪一行读数证明了 `WNOWAIT` 的语义？为什么 `getrusage(RUSAGE_CHILDREN)` 不能当作「刚才那个子进程」的用量？

**Q3（应用）** 一个监控程序要「先记录子进程的死因与 UID，再回收」，并且要防止 PID 复用导致等错对象。请写出接口与关键 flag 的组合，说明每一步读到什么、以及为什么这个顺序不能颠倒。

::: sol 答案
**A1** `waitid` 成功返回 **0**，子进程信息放在 `siginfo_t`（`si_pid`、`si_code`、`si_status`、`si_uid`）。`WNOHANG` 且无可回收子进程时同样返回 0，靠 **`si_pid == 0`** 判断「没有事件」，而不是靠返回 `-1`。本机 glibc 2.39 实测：`CLD_EXITED=1`、`CLD_KILLED=2`、`CLD_STOPPED=5`（另有 `CLD_DUMPED=3`、`CLD_TRAPPED=4`、`CLD_CONTINUED=6`）。
**A2** `WNOHANG` 否定的是「阻塞」：没有事件就立刻返回，不等待。`WNOWAIT` 否定的是「回收」：照常阻塞等到事件、把信息给你，但不把子进程从僵尸队列摘除，它仍占着 PID。本机 `waitid_peek` 的 `peek : code=1 status=7 state=Z` 这一行就是证据——已经读到退出信息，`/proc` 状态却仍是 `Z`，直到 `reaped` 那一步之后 `after` 行才显示 `/proc` 条目消失。`getrusage(RUSAGE_CHILDREN)` 统计的是**所有已回收子进程的累计值**，多个子进程时无法归因到某一个，所以要单个用量就用 `wait4` 的 `struct rusage` 出参。
**A3** 组合：子进程创建后立刻 `pidfd_open(pid, 0)` 拿到 pidfd（持有它就不怕 PID 被复用）；然后 `waitid(P_PIDFD, pidfd, &si, WEXITED | WNOWAIT)` 阻塞等退出，读到 `si_code`（区分 `CLD_EXITED`/`CLD_KILLED`/`CLD_DUMPED`）、`si_status`（退出码或信号号）、`si_uid`，此时子进程仍是僵尸，可以从容记录日志或读 `/proc/<pid>/`；记录完再 `waitid(P_PIDFD, pidfd, &si, WEXITED)`（不带 `WNOWAIT`）或 `waitpid(pid, &st, 0)` 真正回收，最后 `close(pidfd)`。顺序不能颠倒：先回收就再也读不到 `/proc/<pid>/` 与现场信息；不用 pidfd 而只用 PID，则在「记录」与「回收」之间 PID 可能被新进程复用，导致等错对象或回收错进程。
:::

:::

## 2.7.9 本章小结 {#sec-2.7.9}

这一节回答：把这一章合上，你应当能独立做出哪三件事？

::: preview 先抓住一件事
这一章从头到尾只在讲一件事：**创建与销毁都是协议，不是函数调用**。`fork` 规定了父子之间复制什么、共享什么、清零什么；`exit`/`_exit` 规定了结束前谁负责收尾；`wait` 家族规定了状态由谁取走、什么时候销户。三段协议任何一环没人负责，症状都不是报错，而是资源慢慢泄漏。
:::

主线分三段。第一段是创建：`fork` 的返回值把执行流分成两条，继承清单按复制/共享/清零三类记，COW 把「复制」推迟到第一次写，粒度是整页；`clone`/`clone3` 是同一套机制的 flag 组合，`vfork` 与 `posix_spawn` 是这条轴上更省力也更受约束的两档。第二段是终止：`exit` 在进内核前跑 atexit、flush stdio、删临时文件，`_exit` 直接进内核，退出码只有低 8 位。第三段是回收：僵尸占 PID 与 `task_struct` 而不占内存页，父进程必须 `wait`，这之前要先分清四类事件与五个接口的差别。

给自己三条判据。① 看到一个 `fork`，能立刻说出「谁在什么时候 wait」；说不出来就是僵尸泄漏。② 看到一段 fork 后的子进程代码，能判断它调用的函数是否在 async-signal-safe 名单里；多线程程序里这条尤其要命。③ 引用任何数字前能分清它是规范条款、本机读数，还是随架构与 glibc 变的量——本章实测过 `fork` 在 aarch64 上走 `clone`（号 220）、`posix_spawn` 走 `clone3`、`CLD_STOPPED` 是 5 而不是 2，这三条照抄 x86 老资料都会错。

如果只记住一件事，那就是：**每个进程都要有人负责收尸，每个共享对象都要当成对方随时会改，每个顺序假设都要换成显式同步。**

下一站是 [2.8 程序执行与子进程监控](ch08.md)：本章的子进程常常「立刻 exec」，那一半协议——`execve` 保留什么、丢掉什么，`system()`/`popen()` 替你做了什么、代价是什么——在那里展开。逐条达标线已经移到[学习目标自检表](ch07-checklist.md)，那里有 20 条可以当场做的动作；闭卷回忆用[回忆卡](ch07-recall.md)，动手练用[习题集](ch07-exercises.md)。

::: method 即时自测 · 2.7
**Q1** 父进程有一个 1 GiB 的匿名私有映射，fork 后子进程立刻 `_exit`。这期间物理内存会增加 1 GiB 吗？为什么？

**Q2** 父进程打开 `/tmp/log`（`O_WRONLY|O_APPEND`），fork 后子进程先写 100 字节，父进程再写 100 字节。两次写的偏移各是多少？如果父进程在 fork 前 `dup` 了 fd，结论变吗？

**Q3** 子进程用 `exit(0)` 而不是 `_exit(0)`，在什么条件下会看到重复输出？为什么在终端上常常看不到？

**Q4** 一个服务每秒 fork 一个子进程执行任务，但从不 `wait`。三天后 `fork` 返回 `EAGAIN`。解释原因和修复。

**Q5** `waitpid(-1, &st, WNOHANG)` 返回 0 和返回 -1 且 `errno==ECHILD` 分别意味着什么？

::: sol 答案
**A1** 不会。fork 只复制页表并把 PTE 标只读，物理页引用计数加一。子进程 `_exit` 前没有写入，就没有 COW 复制。地址空间的虚拟大小是 1 GiB，但驻留集与父进程共享。

**A2** 子进程写的是 0→100（`O_APPEND` 每次写定位到当前末尾，fork 时文件大小是 0）；父进程写的是 100→200。因为 fd 表虽复制，表项指向同一 `struct file`，偏移与 `O_APPEND` 状态共享。`dup` 不改变结论：`dup` 本来就指向同一 `struct file`。

**A3** 当 fork 前 stdio 缓冲区非空时。最常见的是 stdout 被重定向到文件或管道（全缓冲），数据一直攒着；终端是行缓冲，通常上一条输出以换行结尾、缓冲区已空，所以看不到——但不保证，本程序故意不写换行，在终端上同样会重复。修复：fork 前 `fflush(NULL)`，或子进程用 `_exit`。

**A4** 子进程退出后成为僵尸，父进程不 `wait`，PID 与 `task_struct` 不释放。累计到 `kernel.pid_max` 或 cgroup `pids.max` 后，`fork` 返回 `EAGAIN`。修复：父进程用 `waitpid(-1, ..., WNOHANG)` 定期回收，或设 `SA_NOCLDWAIT`/`SIG_IGN`（放弃退出状态），或调整架构不再每任务 fork。

**A5** 返回 0：有子进程存在，但没有已退出/停止的（`WNOHANG` 下正常）；返回 -1 且 `ECHILD`：没有可等待的子进程了（都已回收，或 `SIGCHLD` 被忽略）。两者都不是错误，但处理逻辑不同。
:::
