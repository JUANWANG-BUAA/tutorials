[2.5](ch05.md) 把文件当成一个 inode（存放文件元数据的索引节点）看。但 inode 没有名字：名字在**目录**里，目录把「名字 → inode 号」的映射存成目录项（dentry）。硬链接是多个名字指向同一个 inode；符号链接是一个独立 inode，内容是另一个路径。理解了这层，你才能解释 `rm` 之后磁盘空间为什么没释放、`mv` 为什么有时是瞬时的、`inotify` 为什么收到的事件比你预期的少。

这一章的最后一部分讲文件事件。轮询 `stat` 既慢又漏，`inotify` 把「文件变了」变成「fd 可读」，这是现代服务重载配置、同步工具、构建系统的基础。但它有合并与溢出，不是可靠的消息队列。

## 2.6.1 目录也是文件：`dirent` 与 `readdir` {#sec-2.6.1}

这一节回答：目录在磁盘上长什么样、和普通文件差在哪？`readdir` 返回的东西归谁、顺序有没有保证？`d_type` 什么时候不可信？

::: preview 先抓住一件事
目录是「名字 → inode 号」的映射表：目录项里只有名字和 inode 号（多数原生文件系统名字上限 255 字节），文件大小、权限、时间全在 inode 里。所以目录的 `st_size` 是目录项占的字节数、不是内容总大小；内核**不提供**对目录的 `read()`/`write()`——读目录只能走 `readdir`（底层 `getdents64`），改目录只能经 `open(O_CREAT)`/`link`/`mkdir`/`symlink`/`unlink`/`rmdir` 间接进行。`readdir` 四条纪律见下：区分 EOF 与错误、`d_name` 会被覆盖、顺序不定、`d_type` 可能是 `DT_UNKNOWN`。
:::

目录在磁盘上是一串「目录项」，每项至少包含 `(名字, inode 号)`。`st_size` 是这些项占的字节数，不是「目录里文件的总大小」。目录的 `x` 位允许穿过，`r` 位允许读目录项，`w` 位允许增删项。

```c
#include <dirent.h>
DIR *opendir(const char *path);
struct dirent *readdir(DIR *dir);
int closedir(DIR *dir);
```

`struct dirent` 的关键字段：

| 字段 | 含义 |
|:--|:--|
| `d_ino` | inode 号 |
| `d_off` | 下一个目录项的偏移（`telldir`/`seekdir` 用） |
| `d_reclen` | 这一项的长度（变长） |
| `d_type` | 类型：`DT_REG`/`DT_DIR`/`DT_LNK`/…，可能是 `DT_UNKNOWN` |
| `d_name` | 名字，以 `\0` 结尾，**长度不定** |

四条纪律：

1. **`readdir` 返回 NULL 时，必须区分 EOF 与错误**。它不设 `errno` 为 0，所以调用前手动 `errno = 0`，循环结束后检查 `errno`。
2. **`d_name` 的内存在下一次 `readdir` 后可能被覆盖**。要保留就 `strdup`。
3. **顺序不定**。`readdir` 返回的是文件系统内部的哈希/树顺序，不是字母序；要排序自己收集后 `qsort`。
4. **`d_type` 可能是 `DT_UNKNOWN`**（某些文件系统不记录类型）。此时要 `fstatat(dirfd(dir), name, ..., AT_SYMLINK_NOFOLLOW)` 补齐。

`readdir_r` 已被标记为废弃（glibc 2.24 起）：它要求调用者提供缓冲区，容易算错长度，而且并不比 `readdir` 更安全——`readdir` 对同一个 `DIR *` 是线程安全的（内部加锁），不同 `DIR *` 互不影响。

```c
/* lsdir.c — 遍历目录，打印名字与类型；处理 DT_UNKNOWN */
#include <dirent.h>
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/stat.h>

static char type_of(const struct dirent *de, int dfd)
{
    if (de->d_type != DT_UNKNOWN)
        return de->d_type == DT_DIR ? 'd' : de->d_type == DT_LNK ? 'l' :
               de->d_type == DT_REG ? '-' : '?';

    struct stat st;
    if (fstatat(dfd, de->d_name, &st, AT_SYMLINK_NOFOLLOW) == -1)
        return '?';
    return S_ISDIR(st.st_mode) ? 'd' : S_ISLNK(st.st_mode) ? 'l' :
           S_ISREG(st.st_mode) ? '-' : '?';
}

int main(int argc, char *argv[])
{
    const char *path = argc > 1 ? argv[1] : ".";
    DIR *d = opendir(path);
    if (!d) { perror("opendir"); return 1; }

    int dfd = dirfd(d);
    struct dirent *de;

    errno = 0;                         /* 关键：区分 EOF 与错误 */
    while ((de = readdir(d)) != NULL) {
        if (strcmp(de->d_name, ".") == 0 || strcmp(de->d_name, "..") == 0)
            continue;
        printf("%c %s\n", type_of(de, dfd), de->d_name);
        errno = 0;
    }
    if (errno != 0)
        perror("readdir");

    if (closedir(d) == -1)
        perror("closedir");
    return 0;
}
```

`dirfd(d)` 拿到目录流底层的 fd，配合 `fstatat` 可以在不拼路径的情况下取属性——这也是避免 `chdir` 竞态的标准手法。每个 `DIR *` 底下确实藏着一个打开的目录 fd，且 **`opendir` 自动给它设了 `FD_CLOEXEC`**（SUSv3 要求，`exec` 时自动关闭）——但你自己 `open` 的目录 fd 不会，要显式带 `O_CLOEXEC`。`fdopendir(fd)` 则是把已打开的目录 fd 包成目录流：成功后 fd 归 `DIR` 管理，不能再单独 `close`，见 [2.6.6](ch06.md#sec-2.6.6) 的 `dirwalk`。

遍历期间目录被修改怎么办？SUSv3 明说：对 `readdir` 是否返回「自 `opendir`/`rewinddir` 之后新增或已删的条目」**不做保证**，但只保证「调用 `opendir` 时已存在的条目都会返回」。要稳定快照就自己收集后处理（[2.6.7](ch06.md#sec-2.6.7) 的 `scandir` 正是干这个的）。

### 目录流的位置：`telldir`/`seekdir`

```c
long telldir(DIR *dir);
void seekdir(DIR *dir, long loc);
void rewinddir(DIR *dir);
```

`telldir` 返回一个**不透明**的位置值，只能交给同一个 `DIR *` 的 `seekdir` 使用；它不对应字节偏移，也不保证跨进程/跨文件系统可移植。目录在遍历期间被修改时，`seekdir` 的行为未定义（可能跳过或重复项）。需要「可恢复的遍历」时，自己记录已处理的文件名，而不是保存 `telldir` 的值。

### 2.6.1 小结

目录读取的全部要点可以压成一张四条纪律的清单：**① `errno=0` 区分 EOF 与错误**——`readdir` 返回 NULL 有两种可能，它自己不用返回值区分，调用前重置、循环后检查；**② `d_name` 的内存在下一次调用时被覆盖**——libc 复用同一个 `struct dirent`，要保留名字必须 `strdup`；**③ 顺序不定**——ext4 的 htree 目录按哈希序返回，`ls` 的字母序是 `ls` 自己排的，要有序自己 `qsort` 或用 `scandir`；**④ `d_type` 是优化不是保证**——部分文件系统（某些 NFS、FUSE）返回 `DT_UNKNOWN`，此时用 `fstatat(dirfd(dir), name, ..., AT_SYMLINK_NOFOLLOW)` 补齐。两个结构事实：目录的 `st_size` 是目录项占用不是内容总大小；`DIR *` 底下有 fd 且 `opendir` 自动设 `FD_CLOEXEC`。`telldir`/`seekdir` 的位置值不透明、目录变更时行为未定义，可恢复遍历自己记账。如果只记住一件事：**readdir 返回 NULL 先查 errno；d_name 下一次调用就失效——要留必须 strdup。**

::: method 即时自测 · 2.6.1
**Q1（记忆）** `readdir` 循环的标准写法里，`errno` 在哪几处被触碰、各为什么？

**Q2（辨析）** 「目录的 `st_size` 是目录里所有文件大小之和」「`d_type=DT_UNKNOWN` 说明这个文件类型未知」——各错在哪？

**Q3（应用）** 要对目录内容做「排序后的稳定快照」，用哪条路？为什么 `telldir` 保存位置不够？

::: sol 答案
**A1** 两处：循环体每次调用 `readdir` **前** `errno = 0`（清掉上一次或其他调用残留），循环**结束后**检查 `errno != 0` 才算错误（否则是正常 EOF）。只在前置一次、循环内不重置的写法会在长循环里被无关系统调用（进程请求内核服务的入口）的 `errno` 污染。

**A2** 第一句错：`st_size` 是目录项占的字节数（ext4 通常是 4096 的倍数），目录项里只有 `(名字, inode 号)`，文件大小在 inode 里。第二句错：`DT_UNKNOWN` 说明**文件系统没有提供**类型信息（某些 NFS、FUSE 不填这一位），不是文件类型真的未知——用 `fstatat(dirfd(d), name, &st, AT_SYMLINK_NOFOLLOW)` 就能补齐。

**A3** 用 `scandir`（或自己收集 + `qsort`）：它一次性把条目复制进独立分配的数组，之后目录怎么变都不影响快照。`telldir` 的位置值只对同一个 `DIR *` 有意义且不透明，目录遍历期间被修改后 `seekdir` 行为未定义，而且就算位置可靠，目录内容也变了——「稳定快照」要的是**数据副本**，不是**游标**。
:::
:::


## 2.6.2 硬链接与符号链接 {#sec-2.6.2}

这一节回答：硬链接与符号链接在 inode 层面差在哪？哪些调用解引用符号链接、哪些不解？为什么 `rm` 之后数据可能还在？

::: preview 先抓住一件事
硬链接是**同一个 inode 的第二个名字**（目录项层面的多对一，`nlink` 计数）；符号链接是**独立 inode**，内容是目标路径字符串（内容层面的引用，不计入目标 `nlink`、可以悬空）。内核对符号链接链的解引用有限制：每个路径部件至少 8 次（`_POSIX_SYMLOOP_MAX`）、整条路径约 40 次，超限 `ELOOP`。`st_nlink` 降 0 且没有进程持有打开 fd，数据才释放——`rm` 删的是名字，不是数据。
:::

<pre class="tree">
目录项（名字 → inode）              inode                    数据
/tmp/a.txt ────────────────────► #12345 (S_IFREG, nlink=2) ──► "hello\n"
/tmp/b.txt ────────────────────► #12345
/tmp/s.link ──► #12346 (S_IFLNK, nlink=1) ──► 内容 "/tmp/a.txt"
                     │
                     └── 解析时重新查 /tmp/a.txt，可能指向别的 inode，也可能不存在
</pre>

读图：硬链接是**同一个 inode 的第二个名字**，`nlink` 加一，删掉一个名字只是减一，数据要到 `nlink==0` 且没有进程打开才释放。符号链接是**独立 inode**，内容是目标路径字符串；它不增加目标的 `nlink`，目标可以不存在（悬空链接），也可以被替换。

两个常被漏掉的细节（Kerrisk §18.2）：符号链接的目标**既可以是绝对路径也可以是相对路径**，相对路径以**链接自身所在目录**为参照点——`/usr/bin/../lib/x` 里 `..` 相对的是链接所在的目录，不是进程 `cwd`；ext 系文件系统还有 fast symlink 优化——目标字符串 ≤60 字节时直接存进 inode 的数据块指针区，不占数据块（Kerrisk 统计过一个系统上 97% 的符号链接享受此优化）。硬链接的两条限制：**必须同文件系统**（目录项存 inode 号，而 inode 号只在单文件系统内唯一）、**不能对目录建**（会在树里造环，使遍历与「目录内容不大于子内容」的约定失效）——两条都能用符号链接绕开。

```c
#include <unistd.h>
int link(const char *oldpath, const char *newpath);
int linkat(int olddirfd, const char *oldpath, int newdirfd, const char *newpath, int flags);
int symlink(const char *target, const char *linkpath);
int symlinkat(const char *target, int newdirfd, const char *linkpath);
ssize_t readlink(const char *path, char *buf, size_t bufsiz);
ssize_t readlinkat(int dirfd, const char *path, char *buf, size_t bufsiz);
int unlink(const char *path);
int unlinkat(int dirfd, const char *path, int flags);   /* AT_REMOVEDIR 删目录 */
```

失败语义：

- `link`：`EXDEV`（跨文件系统）、`EPERM`（目标是非空目录或受保护文件）、`EMLINK`（链接数上限）、`EEXIST`；
- `symlink`：`EEXIST`、`ENAMETOOLONG`、`EPERM`；**不检查 target 是否存在**；
- `readlink`：返回写入 `buf` 的字节数，**不加 `\0`**；`buf` 太小会截断并返回 `bufsiz`（不报错），所以要判断 `n == bufsiz`；
- `unlink`：`ENOENT`、`EACCES`（目录无写权限）、`EISDIR`（用 `unlink` 删目录）、`EBUSY`（挂载点）。

`link()` 对符号链接的行为在 Linux 上是「给链接本身建硬链接」，POSIX 说实现定义；要链接目标，用 `linkat(..., AT_SYMLINK_FOLLOW)`。删除符号链接用 `unlink`，删的是链接本身。

解引用与否的完整分界（Kerrisk 表 18-1 的精神）：**解引用**的有 `stat`/`open`/`chmod`/`chown`/`opendir`/`exec`/`truncate` 等大多数；**不解引用**的有 `lstat`/`readlink`/`unlink`/`rmdir`/`rename`（两个参数都不）/`symlink`（目标字符串不解析）/Linux 的 `link`。一条铁约定：路径**中间的目录部分总是解引用**——`/somedir/file` 里 `somedir` 是链接，任何调用都会跟过去，分野只在最后一段。需要「同一功能两套」时系统成对提供：`stat`/`lstat`、`open` 的 `O_NOFOLLOW`、`*at` 家族的 `AT_SYMLINK_NOFOLLOW`。

::: ex 例 2.6.2 · 先猜对符号链接做 link 会得到什么 {#ex-2.6.2}

`s.link` 是指向 `data.txt` 的符号链接。先猜：`ln s.link h.link`（对符号链接建硬链接）之后，`h.link` 是普通文件还是符号链接？`cat h.link` 输出什么？用 shell 验证。

::: sol 解答
Linux 上 `link()` **不**解引用 oldpath：`h.link` 是符号链接 `s.link` 的硬链接——它自己也是符号链接，内容同样是 `data.txt`。验证：`D=/tmp/lab2c06p_$(date +%s); mkdir $D; cd $D; echo hi > data.txt; ln -s data.txt s.link; ln s.link h.link; ls -l` 可见 `h.link -> data.txt`（`l` 类型），`cat h.link` 输出 `hi`（解引用两层后落到真文件）。这与 SUSv3 相悖（SUSv3 要求路径名解析默认解引用），SUSv4 改口「由实现定义」并给出 `linkat` 的 `AT_SYMLINK_FOLLOW`——跨平台代码别依赖 `link` 对符号链接的行为，要么先 `realpath` 再 `link`，要么显式用 `linkat`。另外注意：`h.link` 的 `st_nlink=1`——符号链接之间互为硬链接只影响链接自己的 inode，与 `data.txt` 无关。
:::
:::

### 完整示例：三种名字

```c
/* linkdemo.c — 硬链接、符号链接、unlink 后的 nlink */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

static void show(const char *path)
{
    struct stat st;
    if (lstat(path, &st) == -1) { perror(path); return; }
    printf("%-12s type=%c nlink=%lu size=%lld\n", path,
           S_ISLNK(st.st_mode) ? 'l' : S_ISREG(st.st_mode) ? '-' : '?',
           (unsigned long)st.st_nlink, (long long)st.st_size);
}

int main(void)
{
    const char *file = "link_demo.txt";
    const char *hard = "hard.link";
    const char *soft = "soft.link";

    int fd = open(file, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd == -1) { perror("open"); return 1; }
    if (write(fd, "hello\n", 6) != 6) { perror("write"); return 1; }
    close(fd);

    unlink(hard); unlink(soft);        /* 允许重复运行 */
    if (link(file, hard) == -1) { perror("link"); return 1; }
    if (symlink(file, soft) == -1) { perror("symlink"); return 1; }

    show(file);
    show(hard);
    show(soft);

    char buf[256];
    ssize_t n = readlink(soft, buf, sizeof buf - 1);
    if (n == -1) { perror("readlink"); return 1; }
    if (n == (ssize_t)sizeof buf - 1) fprintf(stderr, "readlink 可能被截断\n");
    buf[n] = '\0';
    printf("soft.link -> %s\n", buf);

    if (unlink(hard) == -1) { perror("unlink hard"); return 1; }
    show(file);                        /* nlink 从 2 变 1 */

    unlink(soft);
    unlink(file);
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 linkdemo.c -o linkdemo
./linkdemo
# link_demo.txt type=- nlink=2 size=6
# hard.link    type=- nlink=2 size=6
# soft.link    type=l nlink=1 size=10
# soft.link -> link_demo.txt
# link_demo.txt type=- nlink=1 size=6
```

注意 `soft.link` 的 `size=10` 是目标字符串 `link_demo.txt` 的长度，不是目标文件大小。

### `realpath`：把路径解析成绝对路径

```c
#include <stdlib.h>
char *realpath(const char *path, char *resolved);
```

传 `resolved=NULL` 时由 libc `malloc`，调用者 `free`。它解析所有符号链接、`..`、`.`，返回绝对路径；失败返回 NULL，`errno`：`ENOENT`（路径不存在）、`ELOOP`（循环链接）、`EACCES`、`ENAMETOOLONG`。不要自己用 `PATH_MAX` 栈缓冲区（见 [2.1](ch01.md)）。

`realpath` 也不能用来做安全判断：它解析完到 `open` 之间，路径仍可能被换掉。要锚定目录，用 `open(dir)` + `openat(dirfd, name, O_NOFOLLOW)`。


### `dirname`/`basename`：路径拆分的可重入版本 {#sec-2.6.2.1}

```c
#include <libgen.h>
char *d = dirname("/a/b/c.txt");   /* 返回 "/a/b"；可能修改入参 */
char *b = basename("/a/b/c.txt");  /* 返回 "c.txt"；可能修改入参 */
```

这两个函数**可能修改传入的字符串**，且返回静态/入参内部指针；多线程要用 `dirname_r`/`basename_r`（GNU 扩展）或自己复制：

```c
char path[] = "/a/b/c.txt";
char *tmp1 = strdup(path), *tmp2 = strdup(path);
printf("%s / %s\n", dirname(tmp1), basename(tmp2));
free(tmp1); free(tmp2);
```

规则：`dirname("/a/b/")` 得 `/a`，`basename("/a/b/")` 得 `b`；`dirname("foo")` 得 `.`，`basename("/")` 得 `/`。尾斜杠与根路径是测试重点。Kerrisk 表 18-3 还有两条容易记错的：`dirname("..")` 得 `.`、`basename("..")` 得 `..`；`pathname` 为 NULL 或空串时两者都返回 `.`——所以「拼接 dirname + / + basename 还原原路径」对 `/`、`..`、空串这三类输入要单独核对。

### 2.6.2 小结

两种链接的结构差别决定全部行为差异：硬链接是目录项层面的多对一（同 inode、`nlink` 计数、地位平等、限同文件系统、不能对目录），符号链接是内容层面的路径引用（独立 inode、内容是字符串、相对目标以链接位置为参照、不计入目标 `nlink`、可悬空、可跨文件系统可指向目录）。符号链接的读数陷阱：`lstat` 的 `st_size` 是**目标路径字符串的字节数**（本机 `linkdemo` 里 `size=10` 对应 `link_demo.txt`），不是目标文件大小；`st_nlink=1` 恒真（没人给它建硬链接时）。解引用规则记三条：**`unlink`/`rename`/`readlink`/Linux 的 `link` 不解引用**，`stat`/`open`/`chmod` 解引用，**路径中间的目录部分永远解引用**；层数限制每个部件 ≥8 次、整条路径 40 次，超限 `ELOOP`。`readlink` 不加 `\0`、截断不报错（返回值 == `bufsiz` 就换大缓冲重试）；`realpath` 一次解析全部链接与 `.`/`..`，但结果仍是快照，安全锚定要 `open` + `openat(O_NOFOLLOW)`。`dirname`/`basename` 会改入参、`/` 与 `..` 与空串三类输入要单独核对。如果只记住一件事：**硬链接是同一 inode 的多个名字，符号链接是内容为路径的独立文件——删名字不删数据，数据等 nlink 与 fd 双归零。**

## 2.6.3 `mkdir`、`rmdir`、`rename` 与 `unlink` {#sec-2.6.3}

这一节回答：`rename` 原子到什么程度、边界在哪？`unlink` 之后 inode 和数据什么时候释放？`mkdir` 的 mode 和特殊位怎么落？

::: preview 先抓住一件事
`rename` 只改目录项、不搬数据：同一文件系统内**原子**（目标要么旧、要么新），old 与 new 指向**同一文件**时成功且无任何变化（POSIX 规定，防 `rename("x","x")` 误删），跨文件系统 `EXDEV`。`unlink` 删名字、inode 与数据等「`nlink==0` **且**无打开 fd」双归零才释放。`mkdir` 的实际权限是 `mode & ~umask`，setgid 从父目录继承、setuid 恒清零。
:::

```c
int mkdir(const char *path, mode_t mode);      /* 实际权限 mode & ~umask */
int mkdirat(int dirfd, const char *path, mode_t mode);
int rmdir(const char *path);                   /* 只能删空目录 */
int rename(const char *oldpath, const char *newpath);
int renameat2(int olddirfd, const char *oldpath,
              int newdirfd, const char *newpath, unsigned int flags);
```

失败语义：

| 调用 | 常见 errno |
|:--|:--|
| `mkdir` | `EEXIST`、`ENOENT`（父目录不存在）、`EACCES`、`EROFS` |
| `rmdir` | `ENOTEMPTY`、`EBUSY`（挂载点）、`EACCES` |
| `rename` | `EXDEV`、`EISDIR`/`ENOTDIR`、`ENOTEMPTY`（目录非空）、`EBUSY` |
| `renameat2` | 上面的 + `EINVAL`（flags 不支持）、`EEXIST`（`RENAME_NOREPLACE`） |

`rename` 在同一文件系统内是原子的：目标要么旧、要么新。它还能把文件从一个目录移到另一个目录（同一文件系统），这是 `mv` 瞬时完成的原因。跨文件系统返回 `EXDEV`，`mv` 会退化成「复制 + 删除」。

`rename` 的边界规则（Kerrisk §18.4，全部值得背）：

- **old 与 new 指向同一文件时，成功且无任何变化**——`rename("x","y")` 在 `x`、`y` 是同一文件的硬链接时**不会**删掉 `x`。这条源于早期 BSD 的同文件检查方式，后被 POSIX 固化；「newpath 存在就覆盖」的直觉在此失效，因为同文件判定优先。
- **两个参数都不解引用符号链接**：old 是链接就搬运链接本身；new 是链接就把它当普通路径名覆盖掉。
- old 是**文件**而 new 是**目录**路径 → `EISDIR`；old 是目录而 new 是非空目录 → `ENOTEMPTY`；new 是挂载点 → `EBUSY`。
- old 是目录时 new **不能包含 old 作前缀**（`/home/mtk` → `/home/mtk/bin` 报 `EINVAL`）——否则目录树成环。
- 改名不影响其他硬链接、不影响持有打开 fd 的进程：fd 指向打开文件描述，与名字无关。

`mkdir` 的 mode 细节（Kerrisk §18.6）：实际权限 = `mode & ~umask`；**setgid 位从父目录继承**（保证目录树下新文件的组归属一致），**setuid 位恒被清零**（对目录无意义），粘滞位 `S_ISVTX` 若设置则生效（`/tmp` 的 1777）。新目录含 `.` 与 `..` 两个条目，但 SUSv3 只要求路径解析能解释它们、**不要求物理存在**——可移植代码别假设 `readdir` 能列出。`mkdir` 只建最后一级：`mkdir("a/b/c")` 要求 `a/b` 已存在（`mkdir -p` 的补齐是命令自己做的）。`rmdir` 只删空目录，且对最后一段是符号链接的情况**不解引用**直接报 `ENOTDIR`。

`renameat2` 的三个有用 flags：

- `RENAME_NOREPLACE`：目标存在则 `EEXIST`，不覆盖；
- `RENAME_EXCHANGE`：原子交换两个路径；
- `RENAME_WHITEOUT`：overlayfs（容器镜像的联合挂载文件系统）专用。

`unlink` 删除目录项后，inode 的 `nlink` 减一；如果还有进程持有打开的 fd，数据不会释放，直到最后一个 fd 关闭。这就是「`rm` 了文件但 `df` 没降」的原因：

```bash
lsof +L1 | grep deleted       # 找出持有已删除文件的进程
```

`remove(path)` 是便利函数：能删文件就 `unlink`，能删空目录就 `rmdir`。它的错误码混了两套，排障时不如显式调用清晰。

::: ex 例 2.6.3 · 先猜 rename 同一个文件的两个名字会发生什么 {#ex-2.6.3}

::: sol 解答
返回 **0**，`x`、`y` 都还在，`nlink` 仍是 2——什么都没发生。验证：`D=/tmp/lab2c06p_$(date +%s); mkdir $D; cd $D; echo hi > x; ln x y; python3 -c "import os; print(os.rename('x','y'))"` 打印 `0`，`ls` 两个名字都在、`stat -c %h x` 是 2。规则与直觉相反：直觉是「newpath 已存在 → 覆盖 → `y` 变成 `x` 的内容、`x` 消失」，但「覆盖」的实现在内核里被「old 与 new 是否同一文件」的检查短路——这条检查的存在正是为了保证 `rename("x","x")`、`rename("x","./x")`、`rename("x","d/../x")` 不会把文件删掉，其行为源自早期 BSD，POSIX 沿用。工程含义：用「先 rename 到临时名再 rename 回来」做原子替换时，**临时名绝不能是目标文件的另一个硬链接**，否则替换静默无效。

### `chdir` 与 `fchdir`：进程级状态

```c
int chdir(const char *path);
int fchdir(int fd);
```

成功返回 0，失败 -1；`errno`：`ENOENT`、`ENOTDIR`、`EACCES`。`cwd` 是**进程级**状态，同进程的所有线程共享；一个线程 `chdir` 会影响其他线程的相对路径解析。服务端程序不应靠 `chdir` 切换工作目录，而应把目录 fd 存下来，用 `openat`：

```c
int dirfd = open("/srv/data", O_RDONLY | O_DIRECTORY | O_CLOEXEC);
if (dirfd == -1) errExit("open dir");

int fd = openat(dirfd, "conf/app.json", O_RDONLY | O_NOFOLLOW);
if (fd == -1) errExit("openat");
```

这样即使别的线程改了 `cwd`，路径仍锚定在 `dirfd` 上；`O_NOFOLLOW` 防止最后一段是符号链接（配合 `openat2` 的 `RESOLVE_BENEATH` 可以禁止 `..` 逃逸）。`fchdir` 用于临时切换后恢复，但在多线程程序里同样要加锁。临时切换再恢复的两个写法里，`fchdir` 更高效：`chdir` 回去要重新走一遍路径解析，`fchdir` 直接切换到 fd 指向的 inode（Kerrisk 练习 18-9 让你实测，差距在长路径下明显）；`getcwd` 则受「内核一页内存」限制——本机页 4096，超长 cwd 的返回不可靠，这也是服务程序「锚目录 fd、不玩 `chdir`」的又一个理由。

### 2.6.3 小结

改名字的三个调用各有一条「主线 + 边界」：`rename` 的主线是**只动目录项不搬数据**（同文件系统原子、`mv` 跨盘退化为复制+删除），边界是**同文件成功且无变化**、**两参数不解引用**、目录改名时 new 不能含 old 前缀（`EINVAL`）；`unlink` 的主线是**删名字**，边界是 inode 与数据的**双计数释放**（`nlink==0` 且无 fd——`rm` 后空间不降的根因，`lsof +L1`/`/proc/*/fd` 找持有者），且删目录在 Linux 报 `EISDIR`（SUSv3 说 `EPERM`，两个都查）、删符号链接删的是链接本身；`mkdir` 的主线是 `mode & ~umask`，边界是**setgid 从父目录继承、setuid 恒清零**、只建最后一级、新目录的 `.`/`..` 不保证物理存在。`chdir`/`fchdir` 是进程级状态：`cwd` 全线程共享，服务程序用「目录 fd + `openat`」替代 `chdir`；`getcwd` 受一页内存限制。如果只记住一件事：**rename 只动目录项（同文件系统原子、同文件无变化）；unlink 删名字不删数据——nlink 与 fd 双归零才释放。**

## 2.6.4 遍历目录树：`nftw` {#sec-2.6.4}

这一节回答：整棵树的遍历为什么要交给 `nftw`？flags 与回调协议怎么配合？为什么回调里不能 `longjmp`？

::: preview 先抓住一件事
`nftw` 默认对树做**未排序的前序遍历**（目录先于其内容）；`FTW_DEPTH` 切成后序（先子后父，删树用），`FTW_PHYS` 不跟随符号链接（推荐），`FTW_MOUNT` 不跨挂载点。回调返回 0 继续、非 0 停止。`nopenfd` 是同时打开的目录 fd 上限、不是深度上限——超限时 `nftw` 关闭再重开，变慢但不会失败。回调里**不能 `longjmp`**：内部状态动态分配，跳过清理就泄漏。
:::

手写递归要处理符号链接、挂载点、权限不足、深度限制，容易漏。`nftw` 把这些封装好：

```c
#include <ftw.h>
int nftw(const char *path,
         int (*fn)(const char *path, const struct stat *st, int type, struct FTW *ftw),
         int nopenfd, int flags);
```

`fn` 的返回值为 0 继续，非 0 则停止遍历并成为 `nftw` 的返回值。`type` 是 `FTW_F`（文件）、`FTW_D`（目录）、`FTW_DNR`（不可读目录）、`FTW_NS`（`stat` 失败）、`FTW_SL`（符号链接，仅在 `FTW_PHYS` 下）。`ftw->level` 是深度，`ftw->base` 是路径中文件名的偏移。

`flags`：

| flag | 含义 |
|:--|:--|
| `FTW_PHYS` | 不跟随符号链接（推荐） |
| `FTW_MOUNT` | 不跨挂载点 |
| `FTW_DEPTH` | 后序遍历（先子后父，适合删除） |
| `FTW_CHDIR` | 遍历时 `chdir` 到每个目录（会影响多线程） |

`nftw` 的回调没有 `void *userdata`，要累加就用文件级静态变量；这也意味着它不适合重入。

```c
/* du2.c — 用 nftw 统计目录占用（st_blocks * 512），不跟随符号链接 */
#include <ftw.h>
#include <stdio.h>
#include <stdlib.h>

static unsigned long long total;

static int add_blocks(const char *path, const struct stat *st, int type, struct FTW *ftw)
{
    (void)path;
    (void)ftw;
    if (type == FTW_F || type == FTW_D)
        total += (unsigned long long)st->st_blocks * 512;
    return 0;
}

int main(int argc, char *argv[])
{
    if (argc != 2) { fprintf(stderr, "usage: %s DIR\n", argv[0]); return 1; }

    if (nftw(argv[1], add_blocks, 16, FTW_PHYS) == -1) {
        perror("nftw");
        return 1;
    }
    printf("%llu bytes (%llu KiB)\n", total, total / 1024);
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 du2.c -o du2
./du2 /usr/include | tail -1
```

`nopenfd=16` 是同时打开的文件描述符（fd，内核发给进程的打开文件凭据）上限；遍历很深的树时，`nftw` 会提前关闭一些目录 fd。它不会因为深度耗尽而失败，但会变慢。这个参数是历史包袱（早期 UNIX 每进程只有 20 个 fd 的年代必须省着用），现代系统给 10 或更多即可。两个补充语义：`FTW_DNR`（目录不可读）时 `nftw` 不会尝试子树、`stat` 失败时回调收到 `FTW_NS` 且 `st` 无效——两种失败都要在回调里分型处理；提前终止遍历**唯一**合法方式是回调返回非 0，从回调里 `longjmp` 会跳过 `nftw` 的清理逻辑（目录 fd、动态分配的路径栈），至少泄漏资源。需要「跳过子树而不终止」时用 glibc 扩展 `FTW_ACTIONRETVAL`，见 [2.6.7](ch06.md#sec-2.6.7) 与 `fts` 的对照。

### 2.6.4 小结

`nftw` 的价值在于把「手写递归必漏的四件事」变成 flags：符号链接（`FTW_PHYS` 不跟随，链接以 `FTW_SL` 回调；不加则解引用、悬空链接报 `FTW_SLN`）、挂载点（`FTW_MOUNT`）、遍历顺序（默认前序、`FTW_DEPTH` 后序——删树必用）、深度（`nopenfd` 超限关重开、变慢不失败）。回调协议：签名 `(path, stat, typeflag, FTW*)`，`ftw->level` 深度、`ftw->base` 文件名在 path 中的偏移；返回 0 继续、非 0 立即停止且 `nftw` 返回该值。失败分型：`FTW_DNR`（目录读不了，子树放弃）、`FTW_NS`（stat 失败，st 不可用）。回调没有 `userdata` 参数，状态只能文件级静态变量传——不适合重入/多线程；**回调里禁止 `longjmp`**。如果只记住一件事：**遍历树用 nftw 而不是手写递归——FTW_PHYS 管链接、FTW_DEPTH 管删除、返回非 0 是唯一的提前终止方式。**

**Q3（应用）** 统计目录占用时把符号链接目标也算了进去，怎么修？

::: sol 答案
**A1** `nftw(root, rm_cb, 16, FTW_PHYS | FTW_DEPTH)`。`FTW_DEPTH` 后序遍历——先子后父，否则删父目录时里面还有内容（`rmdir` 只删空目录）；`FTW_PHYS` 不跟随符号链接——删链接本身而不是把目标子树删一遍。回调里对 `FTW_F`/`FTW_SL` 用 `unlink`、对 `FTW_DP`（后序的目录）用 `rmdir`。

**A2** 第一句错：`nopenfd` 是**同时打开**的目录 fd 上限不是深度上限——超限时 `nftw` 记录进度、关闭再重开目录 fd，只是变慢不会失败。第二句错：返回非 0 是走 `nftw` 的正常停止路径（它有机会清理）；`longjmp` 直接跳过清理逻辑，目录 fd 和动态分配的遍历状态全部泄漏，而且 `nftw` 自己的栈帧状态被跳过，行为不可预期。

**A3** 加 `FTW_PHYS`：默认（不带它）`nftw` 解引用符号链接，链接指向的子树被完整走一遍、体积重复计入；加了之后链接以 `typeflag=FTW_SL` 回调一次、自己决定计不计（通常计 `st_size` 或直接跳过）。对照 `du` 验证：`du` 默认不跟随链接。
:::
:::


## 2.6.5 `inotify`：把文件变化变成事件 {#sec-2.6.5}

这一节回答：inotify 的使用模型是什么？事件怎么读、怎么对应到文件？它和轮询 `stat` 比好在哪、又差在哪？

::: preview 先抓住一件事
四步模型：`inotify_init1` 建实例得 fd → `inotify_add_watch` 加监控得 `wd` → 对 fd `read` 取 `struct inotify_event` 数组 → `close` 自动清全部 watch。fd **可读就说明有事发生**，可挂 `poll`/`epoll`。三条红线提前立好：事件会**合并**（不能计数）、队列会**溢出**（`IN_Q_OVERFLOW` 后全量重扫）、**不递归**（子目录自己加 watch）。
:::

```c
#include <sys/inotify.h>
int inotify_init1(int flags);                  /* IN_NONBLOCK | IN_CLOEXEC */
int inotify_add_watch(int fd, const char *path, uint32_t mask);
int inotify_rm_watch(int fd, int wd);
```

`inotify_add_watch` 返回一个 watch descriptor（`wd`），同一个路径重复添加会返回同一个 `wd` 并更新 mask。失败返回 -1，`errno`：`ENOENT`、`EACCES`、`ENOSPC`（watch 数量超限）、`EINVAL`（mask 为空）。两个容易漏的语义（Kerrisk §19.2）：**读权限是一次性检查**——加 watch 那一刻要求你对路径有读权限，之后即便权限被收走，事件照发不误（监控的是 inode，不是每次操作重新鉴权）；mask 里可以带**行为位**（`IN_ONLYDIR`「不是目录就报 `ENOTDIR`」、`IN_DONT_FOLLOW`「监控符号链接本身」、`IN_ONESHOT`「只报一次」、`IN_MASK_ADD`「把新 mask 或进现有 mask 而不是替换」），它们不是事件、是 `add_watch` 的行为开关。

常用事件掩码：

| 掩码 | 触发时机 |
|:--|:--|
| `IN_CREATE` / `IN_DELETE` | 目录内创建/删除条目 |
| `IN_MOVED_FROM` / `IN_MOVED_TO` | `rename` 的两端 |
| `IN_MODIFY` | 文件内容被写 |
| `IN_ATTRIB` | 元数据变化（权限、时间、xattr） |
| `IN_CLOSE_WRITE` | 可写打开的 fd 被关闭（最可靠的内容写完信号） |
| `IN_DELETE_SELF` / `IN_MOVE_SELF` | 被监视对象本身被删/被移走 |
| `IN_IGNORED` | watch 被内核移除（删除或 `rm_watch`） |
| `IN_Q_OVERFLOW` | 事件队列溢出（`wd == -1`） |
| `IN_ISDIR` | 事件针对目录（与其他位组合） |

读取事件：

```c
struct inotify_event {
    int      wd;
    uint32_t mask;
    uint32_t cookie;      /* rename 配对用 */
    uint32_t len;         /* name 的长度，含 \0 与填充 */
    char     name[];      /* 变长，可能为空 */
};
```

`read` 返回的缓冲区里是**若干个完整事件**，每个事件占 `sizeof(struct inotify_event) + ev->len` 字节。缓冲区至少 `sizeof(struct inotify_event) + NAME_MAX + 1`；太小会 `EINVAL`。遍历时要按事件长度推进，不能按字节。

```c
/* watchdir.c — 监听一个目录，打印事件；处理溢出与 EINTR */
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/inotify.h>
#include <unistd.h>

#define MASK (IN_CREATE | IN_DELETE | IN_MOVED_FROM | IN_MOVED_TO | \
              IN_MODIFY | IN_ATTRIB | IN_CLOSE_WRITE | IN_DELETE_SELF | IN_MOVE_SELF)

int main(int argc, char *argv[])
{
    if (argc != 2) { fprintf(stderr, "usage: %s DIR\n", argv[0]); return 1; }

    int fd = inotify_init1(IN_CLOEXEC);
    if (fd == -1) { perror("inotify_init1"); return 1; }

    int wd = inotify_add_watch(fd, argv[1], MASK);
    if (wd == -1) { perror("inotify_add_watch"); return 1; }

    char buf[4096] __attribute__((aligned(__alignof__(struct inotify_event))));
    printf("watching %s (wd=%d)\n", argv[1], wd);
    fflush(stdout);

    for (;;) {
        ssize_t n = read(fd, buf, sizeof buf);
        if (n == -1) {
            if (errno == EINTR) continue;
            perror("read");
            break;
        }

        for (char *p = buf; p < buf + n; ) {
            const struct inotify_event *ev = (const struct inotify_event *)p;

            if (ev->mask & IN_Q_OVERFLOW) {
                fprintf(stderr, "queue overflow: events lost, rescan needed\n");
            } else {
                printf("wd=%d mask=%#x%s%s%s\n", ev->wd, ev->mask,
                       (ev->mask & IN_ISDIR) ? " DIR" : "",
                       ev->len ? " name=" : "",
                       ev->len ? ev->name : "");
                fflush(stdout);
            }
            p += sizeof(struct inotify_event) + ev->len;
        }
    }

    close(fd);
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 watchdir.c -o watchdir
mkdir -p /tmp/w && ./watchdir /tmp/w &
echo hi > /tmp/w/a.txt        # IN_CREATE, IN_MODIFY, IN_CLOSE_WRITE
mv /tmp/w/a.txt /tmp/w/b.txt  # IN_MOVED_FROM + IN_MOVED_TO（cookie 相同）
```

### 三个必须知道的限制

1. **事件会合并**。在两次 `read` 之间，同一文件的多次 `IN_MODIFY` 可能只报一次；连续相同的 `IN_CREATE`/`IN_DELETE` 也可能合并。`inotify` 不是逐条日志，不能用来精确计数。
2. **队列会溢出**。默认 `max_queued_events=16384`；溢出时收到 `IN_Q_OVERFLOW`，之前的事件丢失。正确反应是**全量重扫**，而不是继续增量处理。
3. **不递归**。`inotify_add_watch` 只监视指定目录本身；子目录要自己 `readdir` 后逐个添加，而且「先 readdir 再 add_watch」之间有新目录创建的竞态。常见做法是加完 watch 后再扫一遍，或接受可能漏掉新目录的第一个事件。

相关上限在 `/proc/sys/fs/inotify/` 下：

```bash
cat /proc/sys/fs/inotify/max_queued_events   # 16384
cat /proc/sys/fs/inotify/max_user_watches    # 通常 65536 或更高
cat /proc/sys/fs/inotify/max_user_instances  # 128
```

`fanotify` 是另一套接口，能挂在整个挂载点上并拿到文件 fd，适合杀毒/审计；它需要 `CAP_SYS_ADMIN`，日常文件同步用 `inotify` 就够。

::: ex 例 2.6.5 · 先猜 chmod 收走读权限后事件还来吗 {#ex-2.6.5}

程序对 `f.txt` 建了 watch（mask 含 `IN_MODIFY|IN_ATTRIB`）。之后另一个进程 `chmod 000 f.txt` 再往里写。先猜：程序还能收到 `IN_MODIFY` 事件吗？`IN_ATTRIB` 呢？

::: sol 解答
**都收到**。`inotify_add_watch` 的读权限检查是**一次性**的（加 watch 那一刻）；watch 建立后权限怎么变都影响不了事件投递。`chmod 000` 本身先触发一条 `IN_ATTRIB`（元数据变了——权限属于 inode 状态），随后写内容触发 `IN_MODIFY`，两条都会到达。注意区分两件事：「收得到事件」和「有权读内容」没有关系——收到 `IN_MODIFY` 后去 `open` 这个 000 的文件照样 `EACCES`。这个设计也解释了 watch 为什么挂在 inode 上而不是每次操作检查：监控是「订阅 inode 的变化」，不是「代办访问控制」。完整事件语义（合并、`IN_IGNORED`、`wd` 复用）在 [2.6.11](ch06.md#sec-2.6.11)。
:::
:::

::: errata 关于目录与事件五个误解
1. **「`readdir` 按字母序」**——不保证。`ls` 自己排序，`readdir` 不排。
2. **「`readdir` 返回的 `d_name` 可以直接存进数组」**——下次 `readdir` 可能覆盖，必须拷贝。
3. **「`unlink` 之后空间立刻释放」**——有进程持有 fd 时不释放；`lsof +L1` 能看到 `(deleted)`。
4. **「`inotify` 会为每个写操作报一次」**——会合并，且可能溢出；要可靠，得配合定期全量扫描。
5. **「`inotify_add_watch` 会递归监视子目录」**——不会，只监视你指定的那一个目录。
:::

### 2.6.5 小结

inotify 的使用模型四步走：`inotify_init1(IN_CLOEXEC|IN_NONBLOCK)` → `inotify_add_watch`（同一路径重复添加返回同一 `wd` 并更新 mask；读权限一次性检查，之后权限变了事件照发）→ 对 fd `read` 事件数组（fd 可读即有事，可挂 `poll`/`epoll`/信号驱动 I/O）→ `close` 自动清全部 watch。mask 两类位要分清：**事件位**（`IN_CREATE`/`IN_DELETE`、`IN_MOVED_FROM`/`IN_MOVED_TO`、`IN_MODIFY`、`IN_ATTRIB`、`IN_CLOSE_WRITE`、`IN_DELETE_SELF`/`IN_MOVE_SELF`、`IN_IGNORED`、`IN_Q_OVERFLOW`、`IN_ISDIR`）与**行为位**（`IN_ONLYDIR`/`IN_DONT_FOLLOW`/`IN_ONESHOT`/`IN_MASK_ADD`）。三条红线：合并（不能计数）、溢出（重扫）、非递归（子目录自加）。如果只记住一件事：**inotify 是「fd 可读即有事」的订阅模型——watch 的读权限只在加的那一刻查一次，之后权限怎么变事件照发。**

::: method 即时自测 · 2.6.5
**Q1（记忆）** inotify 使用四步是什么？退出时为什么不用逐个 `rm_watch`？

**Q2（辨析）** 「`inotify_add_watch` 对同一目录调两次会建两个 watch」「加了 watch 后 `chmod 000`，事件就断了」——各错在哪？

**Q3（应用）** 要确保监控对象一定是目录（防符号链接、防普通文件混入），`add_watch` 怎么写？

::: sol 答案
**A1** init（建实例得 fd）→ add_watch（得 `wd`、可多次）→ read（取事件数组，可配 poll/epoll）→ close。`close(fd)` 时内核自动清理该实例的全部 watch——不需要逐个 `rm_watch`；`rm_watch` 只用于运行中途撤掉单个 watch（且会触发一条 `IN_IGNORED`）。

**A2** 第一句错：同一实例对同一路径重复 `add_watch` 返回**同一个** `wd` 并用新 mask **替换**旧 mask（除非带 `IN_MASK_ADD` 则是或进去）——它天然幂等，递归监听靠这一点放心重复加。第二句错：读权限是**一次性**检查（加 watch 时）；之后权限被收走，事件照发——收到事件后去 `open` 才会遇到 `EACCES`。

**Q3/A3** `inotify_add_watch(fd, path, MASK | IN_ONLYDIR)`——路径不是目录时返回 -1、`errno=ENOTDIR`。这比「先 `stat` 判断是不是目录再 add」安全：两步之间路径可能被换成符号链接（TOCTOU），`IN_ONLYDIR` 让判定与建立在一个原子调用里完成；要顺带防符号链接再加 `IN_DONT_FOLLOW`（监控链接本身而不是目标）。
:::

## 2.6.6 `getdents64` 与 `struct dirent` 的真实布局 {#sec-2.6.6}

这一节回答：`readdir` 返回的 `d_name` 为什么下一次调用就失效？`d_off` 到底是什么？目录项在磁盘上长什么样？

::: preview 先抓住一件事
`readdir(3)` 是 libc 对 `getdents64(2)` 的封装：内核返回的是**变长记录流**（每条 `struct linux_dirent64`，按 `d_reclen` 推进、8 字节对齐），libc 把它搬进复用的同一个 `struct dirent`——这就是 `d_name` 下次调用就失效的根因。`d_off` 是不透明的游标值（只配 `telldir`/`seekdir`），不是字节偏移。ext4 的 htree 目录按哈希序返回，顺序既非字母序也非 inode 序。
:::

`readdir(3)` 是 libc 对 `getdents64(2)` 的封装。内核返回的不是「一个 dirent 数组」，而是一段**变长记录**：

```c
struct linux_dirent64 {
    ino64_t        d_ino;      /* inode 号 */
    off64_t        d_off;      /* 下一个目录项的偏移（不透明） */
    unsigned short d_reclen;   /* 本条记录的总长度 */
    unsigned char  d_type;     /* 类型，可能是 DT_UNKNOWN */
    char           d_name[];   /* 名字，NUL 结尾，后面可能有填充 */
};
```

`getdents64(fd, buf, count)` 返回写入 `buf` 的字节数，`0` 表示目录读完；调用者必须按 `d_reclen` 逐条推进，不能按 `sizeof(struct dirent)` 跳。`d_name` 的长度是 `strlen(d_name)+1`，但记录会被对齐到 8 字节，所以 `d_reclen` 通常大于「头部 + 名字」。

`struct dirent`（libc 版本）多了一个 `d_type` 字段，`d_name` 通常是 256 字节的数组。**libc 在 `readdir` 内部复用同一个 `struct dirent`**，每次调用覆盖它；这就是「`d_name` 下次调用就失效」的原因。要保留名字必须 `strdup`。

| 字段 | 含义 | 注意 |
|:--|:--|:--|
| `d_ino` | inode 号 | 与 `stat` 的 `st_ino` 对应；`.`/`..` 也有 |
| `d_off` | 下一项偏移 | 不透明，只给 `seekdir`/`telldir`；不是字节偏移 |
| `d_reclen` | 记录长度 | 遍历时按它推进 |
| `d_type` | 类型 | `DT_UNKNOWN` 时需要 `fstatat` 补齐 |
| `d_name` | 名字 | NUL 结尾；不保证是合法 UTF-8 |

`d_type` 是「优化」而不是「保证」：ext4/XFS 通常填，部分文件系统（如某些 NFS、FUSE）返回 `DT_UNKNOWN`。用 `d_type` 判断类型前先处理 `DT_UNKNOWN`，否则会把普通文件误判为未知。

### 目录项不是「文件内容」

目录的 `st_size` 是目录项占用的字节数（ext4 上通常是 4096 的倍数），不是「目录里所有文件大小之和」。目录项里只有 `(名字, inode 号)` 和类型；文件大小、时间、权限都在 inode 里。删除一个目录项只改目录文件，不动 inode（除非链接数降为 0）。

`getdents64` 不保证顺序，也不保证「遍历期间目录不变时一定看到所有新增项」；SUSv3 只要求「调用 `opendir`/`rewinddir` 时已存在的项都能返回」。需要稳定快照就自己排序/复制。

```c
/* dirwalk.c — 用 openat + fdopendir 递归遍历，避免拼路径与 cwd 竞态 */
#include <dirent.h>
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

static int walk(int dfd, const char *label, int depth)
{
    if (depth > 8) {
        fprintf(stderr, "depth limit at %s\n", label);
        return 0;
    }

    int fd = openat(dfd, label, O_RDONLY | O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC);
    if (fd == -1) {
        fprintf(stderr, "openat %s: %s\n", label, strerror(errno));
        return -1;
    }

    DIR *d = fdopendir(fd);          /* 成功后 fd 归 DIR 所有 */
    if (!d) { perror("fdopendir"); close(fd); return -1; }

    struct dirent *de;
    errno = 0;
    while ((de = readdir(d)) != NULL) {
        if (!strcmp(de->d_name, ".") || !strcmp(de->d_name, "..")) continue;

        char type = '?';
        if (de->d_type == DT_DIR) type = 'd';
        else if (de->d_type == DT_REG) type = '-';
        else if (de->d_type == DT_LNK) type = 'l';
        else if (de->d_type == DT_UNKNOWN) {
            struct stat st;
            if (fstatat(dirfd(d), de->d_name, &st, AT_SYMLINK_NOFOLLOW) == 0)
                type = S_ISDIR(st.st_mode) ? 'd' :
                       S_ISREG(st.st_mode) ? '-' :
                       S_ISLNK(st.st_mode) ? 'l' : '?';
        }

        printf("%*s%c %s\n", depth * 2, "", type, de->d_name);
        if (type == 'd') {
            /* 以当前目录 fd 为锚点递归；label 只在本层有效 */
            walk(dirfd(d), de->d_name, depth + 1);
        }
        errno = 0;
    }
    if (errno != 0) perror("readdir");

    closedir(d);                     /* 同时关闭 fd */
    return 0;
}

int main(int argc, char *argv[])
{
    const char *root = argc > 1 ? argv[1] : ".";
    int fd = open(root, O_RDONLY | O_DIRECTORY | O_CLOEXEC);
    if (fd == -1) { perror("open root"); return 1; }

    printf("%s\n", root);
    walk(fd, ".", 0);                /* 打开 root 自身 */
    close(fd);
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 dirwalk.c -o dirwalk
mkdir -p /tmp/tree/a/b && touch /tmp/tree/a/b/c /tmp/tree/x
./dirwalk /tmp/tree
# /tmp/tree
#   d a
#     d b
#       - c
#   - x
```

`fdopendir(fd)` 成功后，`fd` 由 `DIR *` 管理，不能再单独 `close`；`closedir` 会关它。`walk()` 里用 `dirfd(d)` 作为下一层的锚点，避免「先拼路径再 `opendir`」的竞态：即使目录被改名，`dirfd` 仍指向同一个 inode。

::: errata 目录读取的五个坑
1. **「`d_name` 可以存进数组」**——下一次 `readdir` 会覆盖；必须拷贝。
2. **「`d_type` 一定准确」**——可能是 `DT_UNKNOWN`；用 `fstatat` 补。
3. **「`d_off` 是字节偏移」**——不透明值，只给 `seekdir`；不同文件系统含义不同。
4. **「`readdir` 按字母序」**——不排序；`ls` 自己排。
5. **「目录的 `st_size` 是内容总大小」**——是目录项占用；文件大小在 inode 里。
:::

### 2.6.6 小结

`readdir` 之下是**变长记录**：内核的 `struct linux_dirent64`（`d_ino`/`d_off`/`d_reclen`/`d_type`/`d_name[]`）按 `d_reclen` 推进、记录 8 字节对齐（所以 `d_reclen` ≥ 头部 + 名字），`getdents64` 返回 0 表示目录读完。libc 版 `struct dirent` 是搬运工：内部复用同一个结构，`d_name` 下次调用即失效——这就是四条纪律里「要留必须 `strdup`」的实现层根因。`d_off` 不透明（只配 `telldir`/`seekdir`）、`d_type` 是文件系统可选优化（本机 ext4/tmpfs 都填，NFS/FUSE 可能 `DT_UNKNOWN`）。目录项只有 `(名字, inode 号)` 与类型：文件大小、时间、权限全在 inode 里；目录的 `st_size` 是项占用。顺序由文件系统决定（ext4 htree 哈希序），SUSv3 只保证「`opendir`/`rewinddir` 时已存在的项都会返回」。递归遍历的标准防竞态写法：`openat(O_DIRECTORY|O_NOFOLLOW)` + `fdopendir` + `dirfd(d)` 作下一层锚点——目录被改名也锚得住。如果只记住一件事：**readdir 返回的是 libc 内部复用的一块内存——d_name 下一次调用就没了；底层 getdents64 是按 d_reclen 推进的变长记录。**

**A2** 第一句错：记录 8 字节对齐且 `d_name` 变长，`d_reclen` = 头部 + `strlen(name)+1` + 填充，与 libc 固定结构大小无关。第二句错：`d_off` 是不透明的「下一项位置」，ext4 上是 htree 哈希相关值不是字节偏移；它唯一的合法用途是存起来交给同一个 `DIR *` 的 `seekdir`，目录变更后行为未定义。

**A3** 两个理由：**防竞态**——拼路径 `parent + "/" + name` 后再 `opendir`，两次调用之间子目录可能被改名/删除/替换成符号链接；`dirfd(d)` 锚定已打开的 inode，`openat(dirfd, name, O_NOFOLLOW)` 从锚点出发，中途替换无效。**防逃逸**——`O_NOFOLLOW` 拒绝最后一段是符号链接的目录，树遍历不会顺着链接跑到别的子树（`nftw` 的 `FTW_PHYS` 是同一思想的封装版）。
:::

## 2.6.7 `scandir`、`fts` 与 `nftw` 的选择 {#sec-2.6.7}

这一节回答：遍历一个目录/一棵树，什么时候用 `scandir`、`fts`、`nftw`，什么时候自己写递归？

::: preview 先抓住一件事
一条决策线：**单目录要排序快照**用 `scandir`（一次性复制+可自定义比较器）；**整棵树的统计/删除**用 `nftw`（flags 封装，回调模型）；**要在遍历中动态决定跳过谁、先看一层再递归**用 `fts`（句柄+迭代模型，灵活性最高）；**要并发、取消、每线程独立遍历**自己写递归（目录 fd 锚定版）。`nftw` 回调无 `userdata`、不可重入；`fts` 目录会回来两次（前序 `FTS_D`、后序 `FTS_DP`）。
:::

| 接口 | 层级 | 排序 | 主要用途 | 限制 |
|:--|:--|:--|:--|:--|
| `readdir` | 单目录 | 无 | 最小、最可控 | 自己处理 `d_type`/错误 |
| `scandir` | 单目录 | 有（`alphasort`/`versionsort`/自定义） | 需要排序的列表 | 一次性分配整个数组 |
| `fts` | 整棵树 | 可配置 | 需要跳过子树、读取子项、处理符号链接 | BSD 系，非 POSIX |
| `nftw` | 整棵树 | 前序/后序 | 统计、删除、权限修复 | 回调无 `userdata`，不可重入 |
| 自己递归 | 整棵树 | 任意 | 需要精细控制/并发/取消 | 要自己处理 fd 上限与竞态 |

`scandir`：

```c
int scandir(const char *dirp, struct dirent ***namelist,
            int (*filter)(const struct dirent *),
            int (*compar)(const struct dirent **, const struct dirent **));
```

成功返回项数，失败 -1；`namelist` 与每个元素都要 `free`。`alphasort` 用 `strcoll`（受 locale 影响），`versionsort` 做版本号排序（`file2` < `file10`）。过滤函数返回非 0 表示保留。

`nftw` 的关键是 `flags` 与回调返回值（Kerrisk 18.9，p326–330）：

| flag/返回值 | 作用 |
|:--|:--|
| `FTW_PHYS` | 不跟随符号链接；`type=FTW_SL` |
| `FTW_MOUNT` | 不跨挂载点 |
| `FTW_DEPTH` | 后序遍历（先子后父，适合删除） |
| `FTW_CHDIR` | 遍历时 `chdir` 到每个目录（多线程危险） |
| `FTW_ACTIONRETVAL` | 让回调返回 `FTW_SKIP_SUBTREE`/`FTW_SKIP_SIBLINGS`/`FTW_STOP` |
| 返回 0 | 继续 |
| 返回非 0 | 停止，`nftw` 返回同一个值 |

`nftw` 的回调没有 `void *userdata`，只能靠文件级静态变量传状态；这使它不适合重入/多线程。需要「跳过某个子树」时，`FTW_ACTIONRETVAL` + `FTW_SKIP_SUBTREE` 比在回调里判断路径更清晰。`nopenfd` 是同时打开的目录 fd 上限（不是深度上限）；超过时 `nftw` 会关闭并重开，变慢但不会失败。

::: think 为什么 `nftw` 不能 `longjmp` 跳出
`nftw` 内部动态分配遍历状态（目录 fd、路径栈）。从回调 `longjmp` 出去会跳过它的清理逻辑，至少泄漏 fd/内存。要提前终止，让回调返回非 0；要跳过子树，用 `FTW_SKIP_SUBTREE`。这也是「库函数回调里不要随便 `longjmp`」的通用规则。
:::

`fts` 是这五个接口里唯一用「句柄 + 迭代」模型的（`fts(3)`，BSD 系，glibc 也提供）：

```c
FTS *fts_open(char *const *path_argv, int options,
              int (*compar)(const FTSENT **, const FTSENT **));
FTSENT *fts_read(FTS *ftsp);            /* 迭代返回下一个条目 */
int fts_set(FTS *ftsp, FTSENT *f, int instr);
int fts_close(FTS *ftsp);
```

`fts_read` 驱动整个遍历：目录会回来两次（前序 `FTS_D`、后序 `FTS_DP`），文件与符号链接各一次（`FTS_F`/`FTS_SL`）。`FTS_PHYSICAL`（`lstat` 语义）与 `FTS_LOGICAL`（`stat` 语义）二选一；`FTS_XDEV` 不跨设备号；`FTS_NOSTAT` 跳过 stat，此时 `fts_info` 为 `FTS_NSOK`、`fts_statp` 无效。对 `FTS_D` 条目调 `fts_set(ftsp, f, FTS_SKIP)` 可以整棵跳过子树——`nftw` 的 `FTW_SKIP_SUBTREE`（需 `FTW_ACTIONRETVAL`）就是它的晚辈。错误分两层：单个条目失败（`fts_info` 为 `FTS_DNR`/`FTS_ERR`/`FTS_NS`）时返回有效 `FTSENT`，错误码在 `fts_errno`；遍历整体失败时 `fts_read` 返回 `NULL` 并设置 `errno`——所以每次调用前要 `errno = 0`。

```c
/* fts_skip.c — 前序遍历当前目录树，跳过名为 .git 的子树 */
/* cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 fts_skip.c */
#include <errno.h>
#include <fts.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void)
{
    char *const paths[] = { ".", NULL };
    FTS *t = fts_open(paths, FTS_PHYSICAL | FTS_NOSTAT, NULL);
    if (t == NULL) {
        perror("fts_open");
        return EXIT_FAILURE;
    }
    for (;;) {
        errno = 0;                    /* 区分「遍历结束」与「遍历出错」 */
        FTSENT *e = fts_read(t);
        if (e == NULL)
            break;
        if (e->fts_info == FTS_D && strcmp(e->fts_name, ".git") == 0) {
            if (fts_set(t, e, FTS_SKIP) == -1) {
                perror("fts_set");
                exit(EXIT_FAILURE);
            }
            continue;                 /* 整棵子树不再访问 */
        }
        if (e->fts_info == FTS_F)
            printf("%s\n", e->fts_path);
        if (e->fts_info == FTS_DNR || e->fts_info == FTS_ERR ||
            e->fts_info == FTS_NS)
            fprintf(stderr, "%s: %s\n", e->fts_path, strerror(e->fts_errno));
    }
    if (errno != 0) {
        perror("fts_read");
        fts_close(t);
        return EXIT_FAILURE;
    }
    if (fts_close(t) == -1) {
        perror("fts_close");
        return EXIT_FAILURE;
    }
    return EXIT_SUCCESS;
}
```

`fts_children(ftsp, 0)` 是另一条读法：停在某个 `FTS_D` 上时一次拿回它的全部子项链表，适合「先看一层再决定递归谁」的 GUI/工具型遍历。

### 2.6.7 小结

四个接口按「需要什么控制力」排序：`readdir`（最小单目录，自己管一切）→ `scandir`（单目录的**排序快照**：filter 回调保留、`alphasort`/`versionsort`/自定义比较器，数组与元素都要 `free`；`versionsort` 正确处理 `file2 < file10`）→ `nftw`（整树回调模型：flags 封装链接/挂载点/顺序，`FTW_ACTIONRETVAL` 可跳子树，但无 `userdata`、不可重入、回调禁 `longjmp`）→ `fts`（整树**句柄+迭代**模型：目录两次回调 `FTS_D`/`FTS_DP`，`fts_set(FTS_SKIP)` 跳子树、`fts_children` 先看一层、`FTS_PHYSICAL`/`FTS_LOGICAL` 二选一、错误双层——单条目 `fts_info=FTS_DNR/FTS_ERR/FTS_NS` 带 `fts_errno`，整体失败才返回 NULL 设 `errno`，所以循环内每次 `errno=0`）。自己递归是并发/取消场景的最后选择，代价是竞态与 fd 管理全自己扛。如果只记住一件事：**nftw 是回调模型（一次性走完），fts 是迭代模型（走到哪改到哪）——要在遍历中做决定，用 fts。**

## 2.6.8 `*at` 家族与目录 fd 编程 {#sec-2.6.8}

这一节回答：`openat`/`unlinkat`/`renameat` 这些带 `at` 的调用，除了多一个参数，还解决了什么问题？

::: preview 先抓住一件事
`*at` 家族把「相对路径的锚点」从进程 `cwd` 换成**目录 fd**。Kerrisk §18.11 给了两个动机：**防 TOCTOU**（`open("a/b/c")` 解析前缀期间 `a/b` 可被替换；先 `open` 目标目录拿 fd 再 `openat`，前缀替换失效）与**每线程虚拟工作目录**（`cwd` 是进程级共享的，各线程持自己的目录 fd 就有私有 cwd）。`AT_FDCWD`（-100）退回老行为。
:::

`*at` 系列把「相对路径的锚点」从进程 `cwd` 改成**目录 fd**。这在多线程、沙箱、需要防 TOCTOU 的场景里是必需的：

| 调用 | 作用 | 关键 flags |
|:--|:--|:--|
| `openat(dirfd, path, flags, mode)` | 打开 | `O_NOFOLLOW`、`O_PATH`、`O_DIRECTORY` |
| `fstatat(dirfd, path, &st, flags)` | 取属性 | `AT_SYMLINK_NOFOLLOW`、`AT_EMPTY_PATH` |
| `unlinkat(dirfd, path, flags)` | 删除 | `AT_REMOVEDIR` 删目录 |
| `renameat(olddirfd, old, newdirfd, new)` | 改名 | 跨目录 |
| `renameat2(..., flags)` | 带语义的改名 | `RENAME_NOREPLACE`/`EXCHANGE`/`WHITEOUT` |
| `linkat(olddirfd, old, newdirfd, new, flags)` | 硬链接 | `AT_SYMLINK_FOLLOW`、`AT_EMPTY_PATH` |
| `symlinkat(target, newdirfd, new)` | 符号链接 | target 不解析 |
| `readlinkat(dirfd, path, buf, size)` | 读链接 | 不跟随最后一段 |
| `mkdirat`/`mknodat` | 创建目录/设备 | `mode` 受 `umask` |
| `fchmodat`/`fchownat`/`utimensat` | 改元数据 | `AT_SYMLINK_NOFOLLOW` |
| `execveat(dirfd, path, argv, envp, flags)` | 执行 | `AT_EMPTY_PATH`、`AT_SYMLINK_NOFOLLOW` |

`dirfd` 可以是 `AT_FDCWD`（用 `cwd`），也可以是 `open(dir, O_PATH|O_DIRECTORY)` 得到的 fd。用目录 fd 的好处：

- **不受其他线程 `chdir` 影响**；
- **目录被 rename 后仍锚定同一个 inode**；
- 配合 `O_NOFOLLOW`/`openat2` 可以阻止符号链接逃逸；
- 可以用 `openat(dirfd, "..", ...)` 但仍要小心 `..` 逃逸（用 `openat2` 的 `RESOLVE_BENEATH`）。

`AT_EMPTY_PATH` 让「空路径」表示 `dirfd` 本身（`fstatat`/`linkat`/`execveat`），常与 `O_PATH`/`O_TMPFILE` 配合；`linkat` 的 `AT_EMPTY_PATH` 通常需要 `CAP_DAC_READ_SEARCH`，普通用户用 `/proc/self/fd/N` 替代。

::: errata `*at` 的五个坑
1. **「`openat` 的 `dirfd` 必须是目录 fd」**——是的；传普通文件 fd 返回 `ENOTDIR`。
2. **「`AT_FDCWD` 是常量 0」**——它是特殊负值（`-100`），不要当 fd 用。
3. **「`unlinkat` 默认能删目录」**——必须带 `AT_REMOVEDIR`，否则 `EISDIR`。
4. **「`linkat` 默认跟随符号链接」**——Linux 上 `linkat` 默认不跟随；要跟随加 `AT_SYMLINK_FOLLOW`。
5. **「`*at` 自动阻止 `..` 逃逸」**——不会；`openat(dirfd, "../x")` 仍可逃出，需 `openat2` 的 `RESOLVE_BENEATH`。
:::

### 2.6.8 小结

`*at` 家族（Kerrisk 表 18-2，SUSv4 纳入规范）的实质是**把路径解析的起点参数化**：`dirfd` 是已打开的目录 fd 或 `AT_FDCWD`（-100，等价老接口），绝对路径则忽略 `dirfd`。两个动机各有变现：防 TOCTOU——「先 `open` 目录拿 fd、再 `openat`」使路径前缀替换失效，配合 `O_NOFOLLOW` 与 `openat2` 的 `RESOLVE_BENEATH` 构成完整的防逃逸组合；每线程虚拟 cwd——`cwd` 进程级共享，目录 fd + `openat` 模拟线程私有工作目录，`fchdir`/`chdir` 方案在多线程下不可救药。常用 flags 记三个：`AT_SYMLINK_NOFOLLOW`（不跟随最后一段）、`AT_EMPTY_PATH`（空路径指 `dirfd` 本身）、`AT_REMOVEDIR`（`unlinkat` 删目录）。`dirfd(DIR*)` 把目录流转成 fd，是 `readdir` 遍历与 `*at` 调用的桥。如果只记住一件事：**目录 fd 是路径的锚点——openat 从锚点解析，cwd 变不改、前缀换不动；但它不防 .. 逃逸，那要 openat2。**

::: method 即时自测 · 2.6.8
**Q1（记忆）** `openat` 的 `dirfd` 传 `AT_FDCWD`、普通文件 fd、目录 fd 三种值各什么行为？

**Q2（辨析）** 「用了 `openat` 就没有符号链接风险」「`unlinkat(dfd, "d", 0)` 可以删空目录」——各错在哪？

**Q3（应用）** 写「安全地打开 `/srv/app/uploads/<name>`（`name` 来自网络输入）」的调用序列。

::: sol 答案
**A1** `AT_FDCWD`（-100）：相对 `cwd` 解析，等价老接口。普通文件 fd：`ENOTDIR`——`dirfd` 必须是目录。目录 fd：相对**该目录 inode** 解析，与 `cwd` 无关、与目录是否被改名无关。

**A2** 第一句错：`openat` 只把锚点换成了 `dirfd`，路径中段的符号链接照样解析、最后一段不 `O_NOFOLLOW` 也照样跟随；防链接要 `O_NOFOLLOW`（最后一段）+ `RESOLVE_BENEATH`（全路径限子树）。第二句错：`unlinkat` 删目录**必须**带 `AT_REMOVEDIR`；flags=0 时对目录返回 `EISDIR`（等价 `unlink` 的行为）。

**A3** 四步：① `int root = open("/srv/app/uploads", O_RDONLY|O_DIRECTORY|O_CLOEXEC);`（锚定，uploads 本身路径是常量）；② 校验 `name`：不含 `/`、不是 `.`/`..`（应用层白名单）；③ `int fd = openat(root, name, O_RDONLY|O_NOFOLLOW|O_CLOEXEC);`——`name` 若是攻击者放的符号链接，`O_NOFOLLOW` 返回 `ELOOP`；④ 失败处理 `ELOOP`/`ENOENT`/`EACCES` 分支。更严的话用 `openat2(root, name, &(struct open_how){.resolve = RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS}, sizeof(...))` 一步禁掉 `..` 与全部符号链接。
:::
:::



### `mount(2)` 与 `umount2(2)`：命令背后的系统调用 {#sec-2.6.8.1}

`mount /dev/sdb1 /mnt` 最终调用：

```c
#include <sys/mount.h>
int mount(const char *source, const char *target,
          const char *fstype, unsigned long flags, const void *data);
int umount2(const char *target, int flags);
```

容器/命名空间里最常用的 flags：

| flag | 作用 | 典型用法 |
|:--|:--|:--|
| `MS_BIND` | 绑定挂载（把一棵子树挂到另一个点） | `mount("/src", "/dst", NULL, MS_BIND, NULL)` |
| `MS_REC` | 递归（配合 bind/rprivate） | `MS_BIND|MS_REC` |
| `MS_PRIVATE` | 挂载事件不传播 | 容器启动时把 `/` 设为 private |
| `MS_SLAVE` | 单向接收传播 | 需要接收宿主挂载 |
| `MS_NOSUID/MS_NODEV/MS_NOEXEC` | 安全选项 | 容器 rootfs |
| `MS_REMOUNT` | 改已有挂载的 flags | 重新挂载 `/` 为 ro |

```c
/* 让挂载事件不再传播到宿主；容器 pivot_root 前的标准动作 */
mount(NULL, "/", NULL, MS_REC | MS_PRIVATE, NULL);

/* 绑定挂载一个目录，并递归 */
mount("/host/data", "/container/data", NULL, MS_BIND | MS_REC, NULL);

/* 卸载但即使 busy 也 detach（懒卸载） */
umount2("/container/data", MNT_DETACH);
```

::: errata mount 的四个坑
1. **`MS_BIND` 忽略 `fstype/data`**：绑定挂载不是「重新格式化」，只是引用同一棵子树。
2. **传播是默认开的**：systemd 把 `/` 设为 shared；容器里不先 `MS_PRIVATE`，挂载会漏到宿主。
3. **`umount2(MNT_DETACH)` 不是「立即释放」**：还有进程持有该挂载时，它只是从命名空间摘掉，资源等引用归零才释放。
4. **普通用户不能 `mount`**：需要 `CAP_SYS_ADMIN`；用户命名空间里可以有受限的 mount，但受 `MS_NOSUID` 等限制。
:::

## 2.6.9 `renameat2` 的四种语义 {#sec-2.6.9}

这一节回答：`rename` 已经原子了，`renameat2` 的 `RENAME_NOREPLACE`/`EXCHANGE` 又解决什么？

::: preview 先抓住一件事
两个新原语都是「先检查再动作」做不到的：`RENAME_NOREPLACE` 是**原子地占住一个名字**（目标存在 `EEXIST` 不覆盖——先 `access` 再 `rename` 两步之间会被抢）；`RENAME_EXCHANGE` 是**原子地互换两个已存在的路径**（一边不存在 `ENOENT`——版本切换的底层原语，读的一方永远看到完整的一个）。
:::

```c
int renameat2(int olddirfd, const char *oldpath,
              int newdirfd, const char *newpath, unsigned int flags);
```

| flags | 语义 | 目标存在时 |
|:--|:--|:--|
| `0` | 普通 `rename` | 原子替换 |
| `RENAME_NOREPLACE` | 不覆盖 | `EEXIST` |
| `RENAME_EXCHANGE` | 原子交换两个路径 | 两边都必须存在，否则 `ENOENT` |
| `RENAME_WHITEOUT` | overlayfs 白化 | 仅 overlayfs 支持 |

`RENAME_NOREPLACE` 是「原子地创建目标名」的另一种方式：先写临时文件，再 `renameat2(..., RENAME_NOREPLACE)`，如果目标已存在就失败，不会覆盖别人的文件。`RENAME_EXCHANGE` 适合「原子切换两个版本」：`current` 与 `next` 互换，读的一方永远看到完整的一个。

边界（与 `rename` 相同）：

- 同一文件系统，否则 `EXDEV`；
- `old` 是目录、`new` 是非空目录 → `ENOTEMPTY`；
- `old` 是目录、`new` 是文件 → `ENOTDIR`；反之 `EISDIR`；
- `new` 是挂载点 → `EBUSY`；
- `RENAME_EXCHANGE` 下两个路径可以是文件/目录混合，但都必须存在；
- NFS/overlayfs 对 flags 支持不一，可能 `EINVAL`/`EOPNOTSUPP`。

```c
/* renamex.c — RENAME_NOREPLACE 与 RENAME_EXCHANGE 的行为 */
#include <errno.h>
#include <fcntl.h>
#include <linux/fs.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static int write_file(const char *path, const char *s)
{
    int fd = open(path, O_WRONLY | O_CREAT | O_TRUNC | O_CLOEXEC, 0600);
    if (fd == -1) return -1;
    ssize_t n = write(fd, s, strlen(s));
    close(fd);
    return n == (ssize_t)strlen(s) ? 0 : -1;
}

static void show(const char *path)
{
    char buf[64] = {0};
    int fd = open(path, O_RDONLY | O_CLOEXEC);
    if (fd == -1) { printf("%s: %s\n", path, strerror(errno)); return; }
    ssize_t n = read(fd, buf, sizeof buf - 1);
    close(fd);
    printf("%s = %.*s\n", path, n > 0 ? (int)n : 0, buf);
}

int main(void)
{
    unlink("rx_a"); unlink("rx_b");
    if (write_file("rx_a", "AAA") == -1 || write_file("rx_b", "BBB") == -1) {
        perror("write_file"); return 1;
    }

    errno = 0;
    int rc = renameat2(AT_FDCWD, "rx_a", AT_FDCWD, "rx_b", RENAME_NOREPLACE);
    printf("NOREPLACE onto existing: rc=%d errno=%d (%s)\n",
           rc, errno, strerror(errno));

    errno = 0;
    rc = renameat2(AT_FDCWD, "rx_a", AT_FDCWD, "rx_c", RENAME_NOREPLACE);
    printf("NOREPLACE onto free name: rc=%d errno=%d (%s)\n",
           rc, errno, strerror(errno));

    errno = 0;
    rc = renameat2(AT_FDCWD, "rx_c", AT_FDCWD, "rx_b", RENAME_EXCHANGE);
    printf("EXCHANGE: rc=%d errno=%d (%s)\n", rc, errno, strerror(errno));
    show("rx_b");
    show("rx_c");

    unlink("rx_a"); unlink("rx_b"); unlink("rx_c");
    return 0;
}
```

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 renamex.c -o renamex
./renamex
# NOREPLACE onto existing: rc=-1 errno=17 (File exists)
# NOREPLACE onto free name: rc=0 errno=0 (Success)
# EXCHANGE: rc=0 errno=0 (Success)
# rx_b = AAA
# rx_c = BBB
```

`NOREPLACE` 的目标存在时返回 `EEXIST`，不是 `ENOTEMPTY`/`EACCES`。`EXCHANGE` 后 `rx_b` 与 `rx_c` 的内容互换，但两个名字都还在；这正是「原子切换 symlink/current 版本」的底层原语。

::: errata `renameat2` 的四个坑
1. **「`RENAME_NOREPLACE` 等于先 `access` 再 `rename`」**——不等；前者原子，后者有 TOCTOU。
2. **「`RENAME_EXCHANGE` 可以有一边不存在」**——不行，两边都必须存在，否则 `ENOENT`。
3. **「所有文件系统都支持 flags」**——老内核 `ENOSYS`，NFS/overlayfs 可能 `EINVAL`/`EOPNOTSUPP`。
4. **「`renameat2` 能跨文件系统」**——不能，跨设备 `EXDEV`；`mv` 会退化为复制+删除。
:::

### 2.6.9 小结

`renameat2`（Linux 3.15+）在 `rename` 的原子替换之外补了三种 flags：`RENAME_NOREPLACE`（目标存在 `EEXIST`，语义 = 「原子地不覆盖别人」——安全发布的标准姿势：写临时文件 → `NOREPLACE` 上终名，失败说明有人抢先，自己重试，全程无 TOCTOU 窗口）；`RENAME_EXCHANGE`（两边都必须存在 `ENOENT`，原子互换——`current`/`next` 版本切换原语，文件/目录可以混合交换）；`RENAME_WHITEOUT`（仅 overlayfs 有意义，容器镜像层的构建原语）。与 `rename` 相同的约束原样适用：同文件系统（`EXDEV`）、目录目标非空 `ENOTEMPTY`、old/new 是同一文件时成功且无变化。支持面三层检查：内核 ≥3.15（否则 `ENOSYS`）、文件系统实现（NFS/部分 FUSE 可能 `EINVAL`/`EOPNOTSUPP`）、flags 特定（`WHITEOUT` 只认 overlayfs）。如果只记住一件事：**NOREPLACE 是「原子占位」，EXCHANGE 是「原子互换」——两者都是先检查再动作做不到的原语。**

## 2.6.10 链接保护：`fs.protected_*` {#sec-2.6.10}

这一节回答：为什么普通用户不能给 `/etc/passwd` 建硬链接？`/tmp` 里的符号链接为什么有时打不开？

::: preview 先抓住一件事
`fs.protected_hardlinks=1`：在全局可写 sticky 目录里建硬链接，要求你是**文件属主**或有读写权——挡「把 root 的文件硬链进我的目录再读它」（`nlink` 计数让属主检查失效的老攻击）。`fs.protected_symlinks=1`：sticky 目录里**跟随**符号链接，要求链接属主或目标属主 == 跟随者——挡「放个指向 `/etc/shadow` 的链接骗特权程序」。这些是 `open` 报 `EACCES` 而非 `ENOENT` 的隐藏出处。
:::

Linux 用一组 sysctl 限制「跟随/创建链接」的行为，默认值因发行版而异：

| sysctl | 默认（常见） | 作用 |
|:--|:--|:--|
| `fs.protected_hardlinks` | 1 | 只有属主或对源文件有读写权限时才能建硬链接 |
| `fs.protected_symlinks` | 1 | sticky 目录中的符号链接：只有链接属主或目标属主能跟随 |
| `fs.protected_fifos` | 2 | 禁止在全局可写 sticky 目录创建 FIFO（除非属主） |
| `fs.protected_regular` | 2 | 禁止在 sticky 目录打开不属于自己的普通文件（防 `O_CREAT` 攻击） |

`protected_hardlinks=1` 阻止「把 root 的 `/etc/shadow` 硬链接到我的目录，再通过我的文件读它」这类攻击；`protected_symlinks` 阻止「在 `/tmp` 放一个指向 `/etc/shadow` 的链接，骗 root 程序跟随」。这些检查在 `may_linkat`/`may_follow_link` 里完成，失败返回 `EPERM`/`EACCES`。

这也是「为什么 `open("/tmp/link")` 有时返回 `EACCES` 而不是 `ENOENT`」的原因之一。排障时先看 `sysctl fs.protected_*`，再看文件属主与 sticky 位；不要把所有 `EACCES` 都归因于 `chmod`。

::: note 容器里的默认值
容器通常继承宿主机的 sysctl；`docker run --privileged` 或 `--security-opt` 可能改变它们。Kubernetes 的 `securityContext` 也可能设置 `readOnlyRootFilesystem`/`allowPrivilegeEscalation`。跨环境行为不一致时，先 `sysctl -a | grep fs.protected` 对齐。
:::

### 2.6.10 小结

四个 sysctl 各管一类「在共享目录里滥用链接」的攻击面：`fs.protected_hardlinks=1` 管建硬链接（sticky+全局可写目录里要求属主或有读写权，防「硬链提权文件的读通道」——硬链接共享 inode，绕开了属主检查）；`fs.protected_symlinks=1` 管跟随符号链接（同目录里要求链接属主或目标属主 == 跟随者，防「骗特权程序跟随恶意链接」）；`fs.protected_fifos=2`、`fs.protected_regular=2` 管在 sticky 目录创建 FIFO / `O_CREAT` 打开已有普通文件（防对已知路径的投毒）。内核侧实现位置：`may_linkat`/`may_follow_link`，失败 `EPERM`/`EACCES`。**默认值是发行版开的不是内核编译默认**（内核文档默认 0；Ubuntu 16.04+ 全收紧，本机实测 1/1/2/2）——同一程序换发行版行为可能不同，`/tmp` 里的 `EACCES` 排障顺序：先 sysctl、再看属主与 sticky 位、最后才轮到普通权限。如果只记住一件事：**/tmp 这类共享 sticky 目录里的链接是被 sysctl 单独看管的——EACCES 未必是 chmod 问题，先查 fs.protected_*。**

## 2.6.11 inotify 的完整事件语义 {#sec-2.6.11}

这一节回答：inotify 会丢事件吗？`IN_IGNORED` 与 `IN_ONESHOT` 有什么区别？`wd` 为什么会复用？

::: preview 先抓住一件事
inotify 的核心是**内核事件队列**：事件有序（`IN_MOVED_FROM` 恒先于 `IN_MOVED_TO`，rename 配对靠相同 `cookie`），但**新事件与队列尾 `wd/mask/cookie` 全同时被合并丢弃**（不能计数）、队列超 `max_queued_events` 时**丢事件放 `IN_Q_OVERFLOW`**（`wd=-1`，收到必须全量重扫）。`IN_IGNORED` 三种来源（`rm_watch`、对象被删、文件系统卸载）；`IN_ONESHOT` 触发后**没有** `IN_IGNORED`；`wd` 会被复用——收到 `IN_IGNORED` 立即删 `wd→path` 映射。
:::

`inotify` 的核心是一个**内核事件队列**，`read` 从队列取 `struct inotify_event`：

```c
struct inotify_event {
    int      wd;       /* watch descriptor；溢出时为 -1 */
    uint32_t mask;     /* 事件位 */
    uint32_t cookie;   /* rename 配对；其他事件为 0 */
    uint32_t len;      /* name 的长度，含 NUL 与填充 */
    char     name[];   /* 变长；监视对象自身事件时为空 */
};
```

一条事件的长度是 `sizeof(struct inotify_event) + len`；缓冲区至少 `sizeof(struct inotify_event) + NAME_MAX + 1`，否则 `read` 返回 `EINVAL`。`len` 包含 NUL 与对齐填充，不能假设 `len == strlen(name)+1`。

### 掩码与行为位

| 位 | 类型 | 作用 |
|:--|:--|:--|
| `IN_ACCESS` | 事件 | 读 |
| `IN_MODIFY` | 事件 | 写 |
| `IN_ATTRIB` | 事件 | 元数据（权限、时间、xattr、链接数） |
| `IN_CLOSE_WRITE`/`IN_CLOSE_NOWRITE` | 事件 | 关闭可写/只读 fd |
| `IN_OPEN` | 事件 | 打开 |
| `IN_CREATE`/`IN_DELETE` | 事件 | 目录内创建/删除 |
| `IN_DELETE_SELF`/`IN_MOVE_SELF` | 事件 | 监视对象自身被删/被移走 |
| `IN_MOVED_FROM`/`IN_MOVED_TO` | 事件 | rename 的两端，`cookie` 相同 |
| `IN_UNMOUNT` | 事件 | 文件系统被卸载（随后 `IN_IGNORED`） |
| `IN_Q_OVERFLOW` | 事件 | 队列溢出，`wd=-1`，事件丢失 |
| `IN_IGNORED` | 事件 | watch 被移除（`rm_watch`、删除、卸载） |
| `IN_ISDIR` | 修饰 | 事件对象是目录 |
| `IN_ONLYDIR` | 行为 | 路径不是目录则 `ENOTDIR` |
| `IN_DONT_FOLLOW` | 行为 | 不跟随符号链接 |
| `IN_EXCL_UNLINK` | 行为 | 不报告已 unlink 但仍打开的文件事件 |
| `IN_MASK_ADD` | 行为 | 把新掩码 OR 进现有 watch |
| `IN_ONESHOT` | 行为 | 只报告一次，然后自动移除 |

### 合并、顺序与丢失

- **合并**：新事件与队列**尾部**事件的 `wd/mask/cookie/name` 完全相同时，内核丢弃新事件。所以「同一文件连续写 100 次」可能只看到 1 次 `IN_MODIFY`；不能用来计数。
- **顺序**：队列有序；rename 的 `IN_MOVED_FROM` 一定在 `IN_MOVED_TO` 之前。
- **溢出**：`max_queued_events`（默认 16384）满后，内核丢弃事件并放一个 `IN_Q_OVERFLOW`；收到它必须**全量重扫**，不能继续增量。
- **`IN_IGNORED`**：`rm_watch`、对象被删、文件系统卸载都会产生；`IN_ONESHOT` 触发后**不会**产生 `IN_IGNORED`。
- **`wd` 复用**：watch 被移除后，`wd` 可能被下一次 `inotify_add_watch` 复用；收到 `IN_IGNORED` 后要把 `wd → path` 映射删掉，否则新 watch 的事件会被错认成旧路径。
- **非递归**：只监视指定目录本身；子目录要自己加。

`/proc/sys/fs/inotify/` 下三个上限：`max_queued_events`、`max_user_instances`、`max_user_watches`。`ioctl(fd, FIONREAD, &n)` 可以看当前排队字节数。

几个值得单说的细节（Kerrisk §19.3/19.4）：`IN_ATTRIB` 的触发面比直觉宽——权限、所有权、链接计数、扩展属性、大小等元数据变化都算（`chmod`/`chown`/`link`/`setxattr` 各来一条）；`cookie` 目前**只有 rename 在用**（MOVED_FROM 与 MOVED_TO 各带同一值），其余事件恒为 0；`read` 缓冲区小于一个完整事件时返回 `EINVAL`（内核 2.6.21 之前返回 0，老代码有兼容坑）；合并判断的是**队列尾部**——「连续 100 次 `IN_MODIFY` 之间穿插了别的 `IN_CLOSE_WRITE`」就不会被合并掉，所以「丢没丢、丢多少」依赖操作模式，这正是不能拿它当计数的实证。

::: errata inotify 的六个坑
1. **「每个 `write` 都会报一次 `IN_MODIFY`」**——会合并；要精确计数用 fanotify/审计或应用层日志。
2. **「`IN_IGNORED` 一定会有」**——`IN_ONESHOT` 触发后没有；不要等它来清理映射。
3. **「溢出后继续增量处理」**——事件已丢；必须全量重扫。
4. **「`wd` 永久对应一个路径」**——会被复用；收到 `IN_IGNORED` 立即删映射。
5. **「`inotify` 递归监视」**——不递归；`IN_CREATE|IN_ISDIR` 后要自己加。
6. **「`read` 缓冲区小一点没关系」**——小于一个事件会 `EINVAL`；至少 `sizeof(event)+NAME_MAX+1`。
:::

### 2.6.11 小结

inotify 事件语义的完整版分四块记：**队列性质**——有序（FROM 先于 TO）、尾部合并（`wd/mask/cookie` 全同则丢新事件，穿插其他事件就不合并，故计数与频率都不可靠）、溢出（`max_queued_events` 满后丢事件放 `IN_Q_OVERFLOW`、`wd=-1`，唯一正确应对是全量重扫）。**`IN_IGNORED`**——三种来源（显式 `rm_watch`、对象被删、文件系统卸载；`IN_UNMOUNT` 后还跟着一条），`IN_ONESHOT` 触发后没有它；收到就删 `wd→path` 映射，因为 **`wd` 会被复用**，不删就把新 watch 的事件归到旧路径。**读取纪律**——缓冲区至少 `sizeof(struct inotify_event)+NAME_MAX+1`（小了 `EINVAL`），按 `sizeof+ev->len` 推进（`len` 含 NUL 与对齐填充），`FIONREAD` 可查排队字节数。**watch 本体**——挂在 inode 上（rename 后仍有效，另发 `IN_MOVE_SELF`），读权限一次性检查，同路径重复添加幂等（更新 mask 返回同一 `wd`）。如果只记住一件事：**inotify 队列有序但会合并、会溢出——收到 IN_Q_OVERFLOW 全量重扫，收到 IN_IGNORED 立即删 wd 映射。**

## 2.6.12 递归监听与溢出恢复 {#sec-2.6.12}

这一节回答：怎样监听整棵目录树，并在「新建子目录」与「队列溢出」两种情况下都不漏事件？

::: preview 先抓住一件事
递归监听的标准结构四句诀：**先加根、遍历加满、事件补新、溢出重扫**——`nftw` 给每个目录加 watch；`IN_CREATE|IN_ISDIR`/`IN_MOVED_TO|IN_ISDIR` 触发对新目录递归补加；`IN_IGNORED` 删映射；`IN_Q_OVERFLOW` 全量重扫。「先 readdir 再 add」之间有竞态窗口，**加完再扫一遍**才稳。
:::

递归监听的正确结构是「**先加根，再遍历加子目录；事件驱动补加；溢出全量重扫**」：

1. `inotify_init1(IN_CLOEXEC|IN_NONBLOCK)`；
2. `nftw(root, add_watch, ..., FTW_PHYS)` 给每个目录加 watch，`wd → path` 存进表；
3. 循环 `read`；对每个事件：
   - `IN_Q_OVERFLOW`：重新 `nftw` 全量扫描（已存在的 watch 会返回同一 `wd`，更新映射即可）；
   - `IN_CREATE|IN_ISDIR` 或 `IN_MOVED_TO|IN_ISDIR`：对新目录 `nftw` 加 watch；
   - `IN_IGNORED`/`IN_DELETE_SELF`/`IN_MOVE_SELF`：删除 `wd` 映射；
4. 退出时关闭 inotify fd，内核自动清理所有 watch。

「先 readdir 再加 watch」之间有窗口：新目录可能在遍历后、加 watch 前创建。解决办法是**加完 watch 后再扫一遍**，或接受「可能漏掉新目录的第一个事件」，在下一次事件/定期扫描时补上。生产级实现通常两者都做。

```c
/* watchrec.c — 递归 inotify；处理新建目录、IN_IGNORED 与溢出重扫 */
#include <errno.h>
#include <ftw.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/inotify.h>
#include <unistd.h>

#define MAX_WD 65536
#define MASK (IN_CREATE | IN_DELETE | IN_MOVED_FROM | IN_MOVED_TO | \
              IN_MODIFY | IN_ATTRIB | IN_CLOSE_WRITE | \
              IN_DELETE_SELF | IN_MOVE_SELF | IN_ONLYDIR)

static int gfd = -1;
static char *gpath[MAX_WD];
static volatile sig_atomic_t gstop;

static void on_sigint(int sig) { (void)sig; gstop = 1; }

static int add_one(const char *path)
{
    int wd = inotify_add_watch(gfd, path, MASK);
    if (wd == -1) {
        if (errno != ENOENT && errno != ENOTDIR)
            fprintf(stderr, "add_watch %s: %s\n", path, strerror(errno));
        return -1;
    }
    if (wd < MAX_WD) {
        free(gpath[wd]);
        gpath[wd] = strdup(path);
    }
    return wd;
}

static int add_tree_cb(const char *path, const struct stat *st, int type,
                       struct FTW *ftw)
{
    (void)st; (void)ftw;
    if (type == FTW_D || type == FTW_DP) add_one(path);
    return 0;
}

static void add_tree(const char *root)
{
    if (nftw(root, add_tree_cb, 16, FTW_PHYS) == -1)
        fprintf(stderr, "nftw %s: %s\n", root, strerror(errno));
}

static void handle(const struct inotify_event *ev)
{
    const char *dir = (ev->wd >= 0 && ev->wd < MAX_WD) ? gpath[ev->wd] : NULL;
    const char *name = ev->len ? ev->name : "";

    if (ev->mask & IN_Q_OVERFLOW) {
        fprintf(stderr, "queue overflow: full rescan\n");
        add_tree(".");                 /* 示例：以当前目录为根；生产代码用保存的 root */
        return;
    }

    printf("mask=%#x dir=%s%s%s\n", ev->mask,
           dir ? dir : "?", name[0] ? "/" : "", name);

    if (ev->mask & IN_IGNORED) {
        if (ev->wd >= 0 && ev->wd < MAX_WD) {
            free(gpath[ev->wd]);
            gpath[ev->wd] = NULL;
        }
        return;
    }

    if ((ev->mask & IN_ISDIR) &&
        (ev->mask & (IN_CREATE | IN_MOVED_TO)) && dir && name[0]) {
        char path[4096];
        snprintf(path, sizeof path, "%s/%s", dir, name);
        add_tree(path);                /* 新目录可能带一整棵子树 */
    }
}

int main(int argc, char *argv[])
{
    const char *root = argc > 1 ? argv[1] : ".";
    if (chdir(root) == -1) { perror("chdir"); return 1; }

    gfd = inotify_init1(IN_CLOEXEC | IN_NONBLOCK);
    if (gfd == -1) { perror("inotify_init1"); return 1; }

    struct sigaction sa = {0};
    sa.sa_handler = on_sigint;
    sigemptyset(&sa.sa_mask);
    if (sigaction(SIGINT, &sa, NULL) == -1) { perror("sigaction"); return 1; }

    add_tree(".");

    char buf[65536] __attribute__((aligned(__alignof__(struct inotify_event))));
    while (!gstop) {
        ssize_t n = read(gfd, buf, sizeof buf);
        if (n == -1) {
            if (errno == EINTR) continue;
            if (errno == EAGAIN) { usleep(100000); continue; }
            perror("read");
            break;
        }
        for (char *p = buf; p < buf + n; ) {
            const struct inotify_event *ev = (const struct inotify_event *)p;
            handle(ev);
            p += sizeof(struct inotify_event) + ev->len;
        }
    }

    close(gfd);
    for (int i = 0; i < MAX_WD; i++) free(gpath[i]);
    return 0;
}
```

mkdir -p /tmp/wr/a/b
touch /tmp/wr/a/b/c
mv /tmp/wr/a /tmp/wr/a2

`IN_ONLYDIR` 保证 `add_watch` 只接受目录，避免把普通文件当成目录监视。`chdir(root)` 是为了让 `nftw(".")` 与新目录路径一致；生产代码应保存 root 的目录 fd，用 `openat` 拼路径，避免进程 `cwd` 被其他线程改掉。

::: method 递归 inotify 的检查清单
1. 初始化是否带 `IN_CLOEXEC`/`IN_NONBLOCK`？
2. 是否给**每个**子目录加了 watch，而不只是根？
3. 新目录事件是否在 `IN_CREATE|IN_ISDIR`/`IN_MOVED_TO|IN_ISDIR` 后补加？

### 2.6.12 小结

递归监听的正确结构是状态机不是循环：**初始基线**（`nftw(FTW_PHYS)` 对每个目录 `add_watch`，`wd→path` 入表；加完**再扫一遍**补「遍历与加 watch 之间」新建的目录——重复 `add_watch` 幂等所以安全）；**事件驱动**（`IN_CREATE|IN_ISDIR`/`IN_MOVED_TO|IN_ISDIR` 对新目录递归 `nftw` 补加——一条 `mkdir -p a/b/c` 触发链式三次补加；`IN_IGNORED`/`IN_DELETE_SELF`/`IN_MOVE_SELF` 删映射）；**故障恢复**（`IN_Q_OVERFLOW` 全量重扫重建基线，增量处理立即作废）。`IN_ONLYDIR` 保证 add_watch 只接受目录；`chdir(root)` 对齐 `nftw(".")` 与新目录路径只是示例取巧，生产代码保存 root 的目录 fd 用 `openat` 拼路径。竞态窗口的坦白：「先 readdir 再 add」之间创建的目录会漏第一个事件——两种补偿（加完再扫、或接受漏报靠下次事件补）生产级实现都做。如果只记住一件事：**递归 inotify = nftw 建满 watch + 事件补新目录 + IN_IGNORED 删映射 + 溢出全量重扫——加完再扫一遍补竞态窗口。**

## 2.6.13 内核路径：`readdir` 与 inotify {#sec-2.6.13}

这一节回答：`readdir` 在内核里是谁在填目录项？`inotify_add_watch` 之后事件怎么排队？

::: preview 先抓住一件事
两条路径一张表记住：`getdents64` 走 `iterate_dir` → 文件系统的 `iterate_shared`（ext4 是 `ext4_readdir`，htree 按哈希序）→ `filldir64` 填用户缓冲；inotify 的 watch 经 `fsnotify_add_inode_mark` **挂在 inode 上**——所以 rename 后 watch 仍有效、`IN_MOVE_SELF` 另发一条。
:::

### `readdir`/`getdents64`

| 层次 | 位置 | 动作 |
|:--|:--|:--|
| 系统调用 | `fs/readdir.c` | `__do_sys_getdents64` → `iterate_dir` |
| 公共层 | `fs/readdir.c` | `iterate_dir` 检查 `FMODE_PATH`、调用 `file->f_op->iterate_shared` |
| 文件系统 | `fs/ext4/dir.c` | `ext4_readdir` 遍历目录页/htree |
| 输出 | `fs/readdir.c` | `dir_emit` → `filldir64` 把 `(ino, off, type, name)` 写进用户缓冲 |
| 返回 | `fs/readdir.c` | 返回字节数；缓冲满时返回已填部分 |

`dir_emit` 的 `type` 来自 `d_type`；`DT_UNKNOWN` 表示文件系统没提供。`ext4_readdir` 对 htree 目录会按哈希顺序返回，所以 `readdir` 的顺序不是字母序，也不是 inode 序。

### inotify

| 层次 | 位置 | 动作 |
|:--|:--|:--|
| 系统调用 | `fs/notify/inotify/inotify_user.c` | `__do_sys_inotify_add_watch` → `inotify_add_watch` |
| 查找/创建 | 同上 | `inotify_find_inode`、`inotify_new_watch` |
| 注册 | `fs/notify/mark.c` | `fsnotify_add_inode_mark` 挂到 inode 的 mark 列表 |
| 事件 | `fs/notify/inotify/inotify_user.c` | `inotify_handle_inode_event` → `inotify_queue_event` |
| 队列 | 同上 | 追加到 `inotify_inode_mark`/group 的 event list；合并尾部相同事件 |
| 读取 | 同上 | `inotify_read` 把事件拷到用户缓冲；无事件时阻塞/EAGAIN |

`inotify` 的 watch 挂在 **inode** 上（不是路径），所以 rename 后 watch 仍有效；`IN_MOVE_SELF` 通知你对象被移走。`IN_IGNORED` 在 mark 被移除时产生；`IN_Q_OVERFLOW` 在 group 队列超限时产生，`wd=-1`。

::: note fanotify 与 inotify 的分工
`fanotify` 挂在 mount/vfsmount 上，能拿到文件 fd、支持权限事件（`FAN_OPEN_PERM`），适合杀毒/审计；需要 `CAP_SYS_ADMIN`。`inotify` 轻量、无需特权，适合配置重载、文件同步。两者都不保证「不丢事件」；需要强一致就用日志/审计子系统。
:::

### 2.6.13 小结

`readdir` 的内核路径是「VFS（虚拟文件系统，内核里对上统一接口、对下调各文件系统的一层）统一入口、文件系统各自填」：`getdents64` 系统调用（`fs/readdir.c` 的 `iterate_dir`）检查 fd 权限后调 `file->f_op->iterate_shared`，ext4 的 `ext4_readdir` 遍历目录块/htree，经 `dir_emit`（`filldir64`）把 `(ino, off, type, name)` 写进用户缓冲，返回字节数、缓冲满时返回已填部分——一次 `read` 多条变长记录的来源就在这。顺序由文件系统决定：htree 目录按哈希序，**不是**字母序也不是 inode 序。inotify 的内核路径是「mark 挂 inode、事件进 group 队列」：`inotify_add_watch` → `inotify_find_inode`/`inotify_new_watch` → `fsnotify_add_inode_mark`（`fs/notify/mark.c`）挂到 inode 的 mark 链表；文件操作经 fsnotify 钩子触发 `inotify_handle_inode_event`，事件进 group 队列（尾部合并在这层做），`inotify_read` 搬给用户。**watch 挂 inode 不挂路径**是这节的枢纽结论：rename 被监控对象后 watch 照常工作、另发 `IN_MOVE_SELF`；`IN_IGNORED` 在 mark 被移除时产生。如果只记住一件事：**目录内容由文件系统填（顺序文件系统说了算）；inotify 的 watch 挂在 inode 上——所以跟路径无关、rename 不断。**

::: method 即时自测 · 2.6.13
**Q1（记忆）** 从 `getdents64(fd, buf, n)` 到缓冲区里有数据，经过哪几层？

**Q2（辨析）** 「watch 挂在路径字符串上，rename 后就失效」「inotify 的事件合并发生在用户 read 时」——各错在哪？

**Q3（应用）** overlayfs 容器里 inotify 收不到「镜像层文件」的事件，用这节的分层表怎么解释？

::: sol 答案
**A1** 系统调用入口（`fs/readdir.c` 的 `__do_sys_getdents64`）→ `iterate_dir`（VFS 层：查 fd 可读、调文件系统钩子）→ 文件系统的 `iterate_shared`（ext4 是 `ext4_readdir`，逐目录块/htree 项）→ `dir_emit`/`filldir64` 把每项写进用户缓冲 → 返回本次填充的字节数（缓冲满则截断到完整项）。

**A2** 第一句错：watch 经 `fsnotify_add_inode_mark` 挂在 **inode** 上——rename 对象只改目录项不改 inode，watch 照常投递，只是另发 `IN_MOVE_SELF` 告知「对象被移走」；失效的是你自己的 `wd→path` 映射（路径字符串过时了），不是 watch。第二句错：合并发生在**内核入队时**——新事件与队列尾部事件比较（`inotify_queue_event`），与用户态 `read` 无关；`read` 只是搬运已排队的完整事件。

**A3** inotify 的 mark 挂在**当前挂载命名空间可见的 inode** 上；overlayfs 对下层（镜像层）文件是按需复制（copy-up）的合并视图——下层文件没有经过你 watch 的 inode，事件自然不产生。容器里可靠的姿势是：只监听可写层里真实发生操作的路径，或挂载点级别用 fanotify（按 mount 监控），并把「下层变化」交给镜像重建而不是事件订阅。
:::
:::


## 2.6.14 两个实验：`strace` 看 `getdents64` 与 `/proc` 看 inotify 上限 {#sec-2.6.14}

这一节回答：怎样确认程序用的是 `getdents64` 而不是 `read`？怎样知道 inotify 为什么加不上 watch？

::: preview 先抓住一件事
两个取证入口：`strace -e trace=openat,getdents64,close`（本机 strace 6.8 要**显式列调用名**，`%stat` 类调用类会静默为空）确认目录读取的真身；`/proc/sys/fs/inotify/` 三道上限（每实例队列 / 每 UID 实例数 / 每 UID watch 数）——`inotify_add_watch` 的 `ENOSPC` 是 **watch 配额耗尽**，不是磁盘满。
:::

### 实验一：`strace` 跟踪目录读取

```bash
strace -yy -e trace=openat,getdents64,close ./dirwalk /tmp/tree 2>&1 | head -15
```

典型输出：

<div class="terminal" data-title="bash · ubuntu 24.04 / strace 6.8">
<pre><span class="p">&#36;</span> strace -e trace=openat,getdents64 ./dirwalk /tmp/tree 2&gt;&amp;1 | head -8
openat(AT_FDCWD, "/tmp/tree", O_RDONLY|O_DIRECTORY|O_CLOEXEC) = 3&lt;/tmp/tree&gt;
openat(3&lt;/tmp/tree&gt;, ".", O_RDONLY|O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC) = 4&lt;/tmp/tree&gt;
getdents64(4&lt;/tmp/tree&gt;, 0x..., 32768) = 80
getdents64(4&lt;/tmp/tree&gt;, 0x..., 32768) = 0
close(4&lt;/tmp/tree&gt;) = 0
</pre>
</div>

读法：

- `getdents64` 返回 80 字节，是一次读到的多条变长记录；返回 0 表示目录读完。
- 缓冲区大小（32768）由 glibc 的 `DIR` 决定，不是固定的 `sizeof(struct dirent)`。
- `openat(3, ".", O_DIRECTORY|O_NOFOLLOW)` 是 `fdopendir` 内部打开目录流；`-yy` 把 fd 映射到路径。
- 如果看到 `read(3, ...)` 而不是 `getdents64`，说明程序在读普通文件，不是目录。

### 实验二：inotify 上限与 watch 数

```bash
cat /proc/sys/fs/inotify/max_queued_events
cat /proc/sys/fs/inotify/max_user_instances
cat /proc/sys/fs/inotify/max_user_watches

# 统计当前用户的 inotify 实例（需要 root 或同用户）
find /proc/*/fd -lname 'anon_inode:inotify' 2>/dev/null | wc -l

# 观察 watch 数（需要 bpftrace/内核支持）
sudo bpftrace -e 'kprobe:inotify_add_watch { @ = count(); }'
```

`max_user_watches` 是**每个真实 UID** 的 watch 总数；达到上限时 `inotify_add_watch` 返回 `ENOSPC`。`max_user_instances` 限制 `inotify_init` 的次数；`max_queued_events` 限制每个实例的队列长度。`ENOSPC` 不一定是磁盘满，inotify 的 `ENOSPC` 表示 watch 配额耗尽。

::: method inotify 排障顺序
1. `inotify_add_watch` 失败：`ENOENT`（路径消失）、`ENOTDIR`（`IN_ONLYDIR`）、`EACCES`（无读权限）、`ENOSPC`（watch 配额）。
2. 收不到事件：确认监视的是**目录**还是文件；子目录是否单独加了 watch。
3. 事件太少：可能是尾部合并；用 `IN_MASK_ADD` 确认掩码没被覆盖。
4. 事件太多/丢失：看 `max_queued_events` 与 `IN_Q_OVERFLOW`；溢出后全量重扫。
5. `wd` 错乱：`IN_IGNORED` 后没删映射，或 `wd` 被复用。
:::

### 2.6.14 小结

两个实验各拿一个「真身」：实验一证明 glibc 程序读目录走的是 `getdents64`（`openat(..., O_DIRECTORY) = 3` → `getdents64(3, 0x..., 32768) = 80` → `= 0` → `close`），缓冲 32768 由 glibc `DIR` 决定、80 是一次取到的变长记录总字节、返回 0 是 EOF；看到 `read()` 说明读的是普通文件。**strace 的类名（`%stat`）在本机 6.8 上静默为空**——显式列调用名是唯一可靠写法（与 2.5 章同一坑）。实验二把三道上限对号入座：`max_queued_events`（每实例队列，`inotify_init` 时快照）、`max_user_instances`（每真实 UID 实例数）、`max_user_watches`（每真实 UID watch 总数，大树上递归监听最先撞的是它）——`ENOSPC` 在这里是**配额耗尽**不是磁盘满；实例是匿名 inode，`find /proc/*/fd -lname 'anon_inode:inotify' | wc -l` 免特权可数（同用户范围）。`sudo` 不可用挡住改 sysctl 与 `bpftrace`，这部分按未实测读（[勘误页](ch06-errata.md)）。如果只记住一件事：**取证先问「真身是什么调用」——显式列名 strace，/proc 读 inotify 三道上限；ENOSPC 在这里是配额不是磁盘。**

::: method 即时自测 · 2.6.14
**Q1（记忆）** 三道上限各限什么、各自的计量单位（每实例还是每 UID）？

**Q2（辨析）** 「`strace -e trace=%stat ./prog` 没输出说明程序没调 stat 类调用」「`inotify_add_watch` 报 `ENOSPC` 先去清磁盘」——各错在哪？

**Q3（应用）** 递归监听 `/home` 大树时报 `ENOSPC`，三层检查怎么做？

::: sol 答案
**A1** `max_queued_events`：**每实例**的事件队列长度（init 时快照生效，溢出发 `IN_Q_OVERFLOW`）；`max_user_instances`：**每真实 UID** 可建实例数；`max_user_watches`：**每真实 UID** 的 watch 总数（跨实例累计）。

**A2** 第一句错：本机 strace 6.8 上 `%stat` 这类调用类**静默匹配不到**（不报错、零输出）；必须显式列名（`stat,lstat,newfstatat,statx,...`）。空输出先怀疑写法再怀疑程序。第二句错：这里的 `ENOSPC` 是 watch **配额**耗尽（`max_user_watches`），与磁盘空间无关——清磁盘没用；正确动作是读 `/proc/sys/fs/inotify/max_user_watches`、减 watch 数或（有权限时）调高。

**A3** ① 数 watch：`max_user_watches` 与你的树里目录总数对账（每目录一个 watch，谁在共享配额——同 UID 的其他进程）；② 减用量：只监听业务关心的子树、合并实例；③ 有权限才调 sysctl（本机不可做）；④ 结构性兜底：对超大树改「轮询关键目录 + inotify 热点」混合方案。另外确认报错确实是 `add_watch` 的 `ENOSPC`（配额）而不是 `read`/磁盘的 `ENOSPC`。

## 2.6.15 本章陷阱清单 {#sec-2.6.15}

这一节回答：前面十四节的坑，按「名字层被当成了内容层」怎么归类？排查时先问哪一句？

::: preview 先抓住一件事
三组陷阱共享同一个病根：**把「名字层」当成「内容层」**——`rm` 当成删数据（其实删名字）、`rename` 当成搬文件（其实只改目录项）、`inotify` 当成可靠日志（其实是尽力而为的通知）。先背病根，十二个坑都挂得上去；每一类的修复都不是换参数，而是**先问「这个调用动了哪一层、计数归零了吗」**。
:::

::: errata 目录遍历与硬链接的四个坑
1. **现象**：`readdir` 返回的 `d_name` 存进数组后乱码。**原因**：内部缓冲区被下一次调用覆盖。**修复**：`strdup`。
2. **现象**：遍历目录时 `d_type` 是 `DT_UNKNOWN`。**原因**：文件系统不提供类型。**修复**：`fstatat(..., AT_SYMLINK_NOFOLLOW)`。
3. **现象**：`unlink` 删目录失败。**原因**：`unlink` 不能删目录。**修复**：`rmdir`/`unlinkat(..., AT_REMOVEDIR)`。
4. **现象**：`link` 跨文件系统失败。**原因**：硬链接必须同 FS。**修复**：用符号链接或复制。
:::

::: errata 符号链接与 rename 的四个坑
1. **现象**：符号链接循环导致 `ELOOP`。**原因**：超过 40 次解引用。**修复**：`readlink` 检查链路，避免自指。
2. **现象**：`rename` 返回 `EXDEV`。**原因**：跨文件系统。**修复**：复制到目标 FS + `fsync` + `rename`。
3. **现象**：`renameat2(RENAME_NOREPLACE)` 返回 `EEXIST`。**原因**：目标已存在。**修复**：这是预期语义；需要覆盖就用普通 `rename`。
4. **现象**：`open` 在 `/tmp` 的链接上返回 `EACCES`。**原因**：`fs.protected_symlinks`。**修复**：检查 sysctl 与链接/目标属主。
:::

::: errata inotify 的四个坑
1. **现象**：`inotify` 只收到一次 `IN_MODIFY`。**原因**：尾部事件合并。**修复**：不要用 inotify 计数；需要精确日志用应用层。
2. **现象**：`inotify` 完全收不到子目录事件。**原因**：不递归。**修复**：对子目录逐个 `add_watch`，并在新建目录时补加。
3. **现象**：`inotify_add_watch` 返回 `ENOSPC`。**原因**：`max_user_watches` 用尽。**修复**：减少 watch/提高 sysctl/复用 watch。
4. **现象**：`IN_Q_OVERFLOW` 后状态错乱。**原因**：事件已丢，继续增量处理。**修复**：全量重扫。
:::

### 2.6.15 小结

十二个坑按病根分三组，每组记一句「先查什么」：**目录遍历组**（`d_name` 覆盖、`DT_UNKNOWN`、`unlink` 删目录、跨 FS 硬链接）先查「我拿到的是引用还是副本、`errno` 是谁的」；**符号链接与 rename 组**（`ELOOP`、`EXDEV`、`NOREPLACE` 的 `EEXIST`、`/tmp` 的 `EACCES`）先查「这个调用解引用吗、这个错误是预期分支还是故障（`fs.protected_*` 也在 `EACCES` 的出处里）」；**inotify 组**（合并、非递归、配额 `ENOSPC`、溢出错乱）先查「队列尾是不是同事件、watch 覆盖了吗、上限读了没」。共同的元规则：错误码先分型再处理——`EEXIST` 对 `NOREPLACE` 是正常语义、`ENOSPC` 对 inotify 是配额、`EACCES` 在 sticky 目录可能是 sysctl——同一个 errno 在不同调用里含义完全不同。如果只记住一件事：**先问「这个调用动了名字层还是内容层」，再问「这个 errno 在这个调用里是什么意思」——十二个坑全是这两问没问的后果。**

::: method 即时自测 · 2.6.15
**Q1（记忆）** 三组坑的「先查什么」各是哪一句？

**Q2（辨析）** 「所有坑都能靠多检查返回值避免」——对不对？举一个反例。

**Q3（应用）** 线上服务「inotify 事件与磁盘实际状态不一致」，按哪几步定位？

**A1** 遍历组：「拿到的是引用还是副本、`errno` 是谁的」（`d_name` 生命周期、EOF 与错误）；链接/rename 组：「这个调用解引用吗、这个 errno 是预期还是故障」（`EEXIST`/`EACCES` 的分型）；inotify 组：「队列尾同事件吗、watch 覆盖了吗、上限多少」（合并/幂等/配额）。

**A2** 不对。返回值检查防不住**语义层**的坑：`rename("x","y")` 在 `x`、`y` 是同文件时返回 0 但什么都不做（返回值完全正常）；inotify 不报错但事件被合并/溢出丢弃（成功路径上静默丢信息）；`readdir` 顺序不定也不算错误。这些要靠理解机制 + 主动验证（对照 `stat`、定期对账），不是查返回值能兜住的。

**A3** 四步：① 读 `/proc/sys/fs/inotify/*` 对账 watch 数与队列上限；② 复查映射维护——`IN_IGNORED` 后删没删、`wd` 复用后有没有旧映射残留；③ 确认增量基线——最近有没有 `IN_Q_OVERFLOW`（或重启/断线）后没重扫；④ 拿 `find`/`stat` 对一个子树做「磁盘真相」与内存状态的对账，差异点就是漏事件的位置；查出来通常是「溢出没重扫」或「新目录没补 watch」二者之一。

## 2.6.16 本章小结 {#sec-2.6.16}

这一节回答：十六节读完，你对「名字层」多了哪几样能当场验证的能力？哪一段还只是「认得名词」？

::: preview 先抓住一件事
本章的全部结论挂在一句话上：**名字与内容是两层**——目录项存映射、inode 存属性、数据存内容；`link`/`unlink`/`rename`/inotify 全部只动名字层。读代码时先问「这个调用动了哪一层」，再问「这个 errno 在这个调用里是什么意思」，本章的坑基本都躲得开。
:::

**第一段，名字的两层结构（2.6.1–2.6.3）。** 目录是「名字 → inode 号」的映射表：`st_size` 是项占用、`r`/`w`/`x` 各管列名/增删/穿过、内核不给 `read()`/`write()`。`readdir` 四条纪律（`errno=0`、`d_name` 覆盖、顺序不定、`DT_UNKNOWN` 补齐）底下是 `getdents64` 的变长记录。两种链接一张三层图：硬链接是同 inode 的多名字（`nlink` 计数），符号链接是内容为路径的独立 inode（可悬空）。`unlink` 删名字、数据等 `nlink` 与 fd **双归零**；`rename` 只动目录项——同文件系统原子、同文件成功且无变化、两参数不解引用。这一段立的是**名字与内容的生命周期能分开算账**。

**第二段，遍历与锚定（2.6.4–2.6.8）。** 整树遍历交给 `nftw`（`FTW_PHYS`/`FTW_DEPTH`/`FTW_MOUNT`，回调禁 `longjmp`，要动态决定就用 `fts` 的迭代模型）；`*at` 家族把路径锚点从进程 `cwd` 换成目录 fd——防 TOCTOU 与每线程虚拟 cwd 两个动机，`O_NOFOLLOW` + `openat2` 的 `RESOLVE_BENEATH` 补全防逃逸。这一段立的是**路径解析可以也应该被锚定**。

**第三段，改名语义与防护（2.6.9–2.6.10）。** `renameat2` 的 `NOREPLACE`（原子占位）与 `EXCHANGE`（原子互换）是「先检查再动作」做不到的原语；`fs.protected_hardlinks`/`protected_symlinks` 在共享 sticky 目录里看管链接的建与跟——`/tmp` 的 `EACCES` 未必是 `chmod` 问题。这一段立的是**原子性的工程价值与防护的分层**。

**第四段，事件订阅（2.6.5、2.6.11–2.6.14）。** inotify 四步模型、事件/行为两类掩码位、读权限一次性检查；三个限制（尾部合并、队列溢出 `IN_Q_OVERFLOW`、非递归）各有应对（不计数、全量重扫、事件补 watch）；`IN_IGNORED` 三来源、`wd` 复用要删映射；watch 挂 inode 所以 rename 不断。这一段立的是**它是通知不是队列**。

**第五段，收口（2.6.13–2.6.16）。** 内核分层（`iterate_dir` → 文件系统 `iterate_shared`；mark 挂 inode、事件进 group 队列）；取证两件套（`strace` 显式列调用名、`/proc/sys/fs/inotify/` 三道上限）；十二个坑按「先查哪一句」归成三组。

逐条打勾的达标表已移交章末的[学习目标自检表](ch06-checklist.md)，正文不再挂表。留在这里的是三条判据：

- **能解释**：`rm` 后空间为什么不降、`lsof +L1` 在看什么；`rename` 为什么同文件系统才原子、同文件时为什么「成功且无变化」；inotify 为什么收不到子目录事件、`wd` 为什么会认错路径；`/tmp` 里的 `EACCES` 有哪几种出处。
- **能操作**：写出处理 `DT_UNKNOWN` 与 `errno` 的 `readdir` 循环；用 `NOREPLACE`/`EXCHANGE` 各做一次原子改名；目录 fd 锚定的 `openat` + `O_NOFOLLOW` 访问；递归 inotify 的三件事（补 watch、删映射、溢出重扫）落在代码里。
- **能判断**：「空间不降/事件丢失/`EACCES` 来路不明」各定位到哪一层（双计数、合并还是溢出、sysctl 还是权限）；`EEXIST`/`ENOSPC`/`EACCES` 在不同调用里各是什么意思；引用任何上限数字前先说清它属于哪个内核、哪块盘。

如果只记住一件事：**rm 删的是名字不是数据，inotify 订阅的是名字的变化不是可靠日志——名字层与内容层各有各的生命周期。**

::: errata 本章的口径边界
1. **读数只属于它那台机器**：本章终端输出按 Ubuntu 24.04.5（aarch64，内核 7.0.0-38）口径给出；inotify 三道上限（本机 16384/128/1048576）、`fs.protected_*`（本机 1/1/2/2，发行版开的不是内核默认）、`lsof`/`bpftrace` 的有无，换环境就换，见[勘误页](ch06-errata.md)。
2. **形状而不是读数**：2.6.13 的内核调用链（`iterate_dir`、`fsnotify_add_inode_mark`、`inotify_handle_inode_event`）来自 6.x 源码的层次与命名，版本改名/内联风险照旧；要带走的是「watch 挂 inode、事件进队列、合并加入队时」三个结论，不是符号名。
3. **只按语义描述、未逐项实测的部分**：`IN_Q_OVERFLOW` 的现场（要 16384+ 事件的生产速率）、`RENAME_EXCHANGE` 在 NFS/FUSE 的 `EINVAL`、`DT_UNKNOWN` 的 NFS/FUSE 现场、改 sysctl 后的行为——本机无第二块盘且 `sudo` 不可用，全部按「机制结论 + 未实测」读。
:::

::: method 即时自测 · 2.6
**Q1** `readdir` 循环结束后返回 NULL，怎么判断是正常读完还是出错？

**Q2** 一个文件有两个硬链接，`nlink=2`。`unlink` 其中一个后，另一个还能打开吗？数据什么时候释放？

**Q3** `readlink(buf, sizeof buf)` 返回的值等于 `sizeof buf`，说明什么？

**Q4** `rename("/a/x", "/b/x")` 返回 `EXDEV`，为什么？`mv` 会怎么处理？

**Q5** `inotify` 监听了 `/data`，在 `/data/sub` 里创建文件，会收到事件吗？收到 `IN_Q_OVERFLOW` 后该怎么办？

::: sol 答案
**A1** `readdir` 不设置 `errno` 来区分；调用前 `errno=0`，循环结束后若 `errno != 0` 则是错误，否则是正常 EOF。注意循环体内每次调用前也要重置，避免上一次的残留。

**A2** 能打开。`unlink` 只删除一个目录项并把 `nlink` 减到 1；inode 和数据仍在。数据在 `nlink==0` **且**没有进程持有打开 fd 时释放；`lsof +L1`（本机未装用 `/proc/*/fd` 找 `(deleted)`）可以找到仍持有它的进程。

**A3** 缓冲区可能太小，`readlink` 截断了目标路径（它返回放入缓冲区的字节数，不报 `ERANGE`，也不加 `\0`）。应该用更大的缓冲区重试，并自己补 `\0`。

**A4** 源和目标不在同一个文件系统（挂载点不同），`rename` 不能跨设备。`mv` 会退化为「复制到目标临时文件 + 保留元数据 + `rename` + 删除源」，并因此**不再原子**。

**A5** 不会，`inotify` 不递归；只监听 `/data` 本身。收到 `IN_Q_OVERFLOW` 说明队列溢出、事件已丢失，必须做一次全量重扫（`readdir`/`stat` 建立当前状态基线），再从当前状态继续增量监听——继续处理残缺增量只会越走越偏。
:::
