# 2.2 勘误与版本注记

这一页收本章所有「换一台机器、换一个架构、换一个 libc、换一个内核、换一个会话就不成立」的东西：`open` flags 的八进制值、系统调用号、`/proc/self/fdinfo` 的读数、`mnt_id` 与 inode 号、管道容量、fd 号、`errno` 数值、内核函数名与源文件路径，以及母本版本覆盖不到的新接口。正文的 `errata` 盒讲的是**理解**陷阱（「以为 `O_APPEND` 能保证不交错」这类）；这一页讲的是**搬家**问题——你的结论昨天在这台机器上成立，今天换台机器就不成立，而且失败时不报错、只是给一个看起来照样合理的数。这一章恰好是全书最容易搬家的地方之一，因为它的两张表整列写的都是别的架构的数。

**本章基线**：正文与套件里标「本机实测」的读数，来自本书的 Ubuntu 24.04.5 虚拟机——**aarch64（ARM64，不是 x86-64）**、内核 `7.0.0-38-generic`、GCC 13.3.0（`13.3.0-6ubuntu2~24.04.1`）、glibc 2.39、4 vCPU、页大小 4096、根文件系统 `/dev/sda2` ext4。可用工具（逐个 `command -v` 确认过）：`cc`/`gcc`、`strace` 6.8、`lsof`、`iostat`、`getconf`、`stat`、`du`、`truncate`、`findmnt`、`filefrag`、`python3`、`docker`（免 sudo，`docker run --rm busybox uname -m` 打印 `aarch64`）。**不可用**：`sudo`（`sudo -n true` 报「需要密码」）、`perf` 的计数器（`/usr/bin/perf` 这个文件在，但 `perf stat true` 每行都是 `<not supported>`）。**写作机**：macOS（Apple 芯片，arm64），没有 `/proc`、没有 `strace`，`errno` 数值不同（`EAGAIN`=35），页大小 16384——只能用来对照「换一个 libc/架构会怎样」。凡标「未实测」的，看末节。

## 1. 二十一条容易搬家的结论

| 看起来像 | 实际是 | 怎么验证 |
|:--|:--|:--|
| 「`open` 是个系统调用，编号 2，可以照 x86 的表查」 | **aarch64 上 `open` 根本没有系统调用**：`asm-generic/unistd.h` 里没有 `__NR_open`，glibc 的 `open()` 直接走 `openat`（本机编号 **56**）。x86-64 才有 `__NR_open`=2。照抄 x86 的调用表，`open` 那一行整个是错的 | `grep '__NR_open$' /usr/include/asm-generic/unistd.h`（本机无匹配）；`strace -e trace=open,openat ./prog` 只出现 `openat`；`grep -n '__NR_openat ' /usr/include/asm-generic/unistd.h` → 158 行 =56 |
| 「系统调用号哪里都一样，`syscall(0,…)` 就是 `read`」 | aarch64 与 x86-64 的号**完全不同**：`read` 0→**63**、`write` 1→**64**、`openat` 257→**56**、`getpid` 39→**172**、`statx` 332→**291**；`clone3` 两边都是 435 是**巧合**，不是「新调用号在尾部对齐」的规律。本机 `syscall(0,…)` 打到的是 `io_setup`（编号 0），传 `1` 当参数实测 `-1 errno=14 (EFAULT)`，不是 `read` | `grep -nE 'define __NR_(read|write|openat|getpid|statx|clone3|io_setup)\b' /usr/include/asm-generic/unistd.h`；`strace -e trace=read ./prog` 看 `read(0, NULL, 0) = 0` 旁的 `SYS_read`=63；跑一段 `syscall(0,1)` 打印 `errno` |
| 「`fdinfo` 的 `flags: 0100002` 是本机读数，去掉 `O_LARGEFILE`(`0100000`) 就是 `O_RDWR`」 | 那是 **x86-64** 的读法。本机（aarch64）同一个 `exec 3<>file` 实测是 **`flags: 0400002`**：`0400000` 是 aarch64 的 `O_LARGEFILE`，低位 `2` 才是 `O_RDWR`。而在 aarch64 上 `0100000` 是 **`O_NOFOLLOW`**——用 x86 的表去解本机的数，会把「普通读写 fd」解释成「带符号链接保护」，含义整个错掉 | `exec 3<>/tmp/x; cat /proc/self/fdinfo/3`；`grep -nE 'O_(NOFOLLOW\|LARGEFILE\|DIRECT\|DIRECTORY)' /usr/include/aarch64-linux-gnu/asm/fcntl.h`（本机原文：`O_DIRECTORY 040000`、`O_NOFOLLOW 0100000`、`O_DIRECT 0200000`、`O_LARGEFILE 0400000`）；普通 `O_RDONLY` 的 fd 实测 `flags: 0400000` |
| 「`mnt_id: 28`、`ino: 1234567` 是本章的常数」 | 两个数都**每台机器、每次挂载都不同**，不能当常数引用，也不能跨机器比较。本机 `/etc/hosts` 实测 `mnt_id: 35`、`ino: 2755550`；`mnt_id 35` 在 `mountinfo` 里对应根挂载 `/dev/sda2 ext4` | `cat /proc/self/fdinfo/<N>` 之后 `awk '$1==35' /proc/self/mountinfo` 对一下；换一台机器这两个数一定不同 |
| 「2.2.9 那张 flags 全表的八进制列可以直接用」 | 整列标的是 x86-64。本机有**四行**不同：`O_DIRECTORY` 0200000→**040000**、`O_NOFOLLOW` 0400000→**0100000**、`O_DIRECT` 040000→**0200000**、`O_LARGEFILE` 0100000→**0400000**；`O_TMPFILE` 因为等于 `__O_TMPFILE\|O_DIRECTORY`，也跟着变成 **020040000**（正文列的是 020200000）。低位的 `O_CREAT`/`O_EXCL`/`O_TRUNC`/`O_APPEND`/`O_NONBLOCK`/`O_ASYNC`/`O_CLOEXEC`/`O_PATH`/`O_SYNC`/`O_DSYNC`/`O_NOATIME` 本机与 x86 相同 | 打印一次：`printf("%#o %#o %#o %#o %#o\n", O_DIRECTORY, O_NOFOLLOW, O_DIRECT, O_LARGEFILE, O_TMPFILE)`（本机得 `040000 0100000 0200000 0 020040000`；注意 glibc 的 `O_LARGEFILE` 宏展开成 0，与内核头里的 `0400000` 不是同一个东西）；对照 `grep -n "#define O_" /usr/include/aarch64-linux-gnu/asm/fcntl.h` |
| 「`O_DIRECT`/`O_SYNC` 这类高位标志的八进制值一套通用；`strace` 打出的名字-数值对应也到处一样」 | 它们分属**内核 asm-generic/架构头**与 **glibc** 两套定义：本机内核 aarch64 头给 `O_LARGEFILE 0400000`，而 glibc `bits/fcntl-linux.h` 里还留着 x86 风格的兜底 `__O_LARGEFILE 0100000`——**同一个数字名在三处可能各有定义**。`strace` 是按当前架构的头文件解码的，所以它打出的**名字**是可信的，抄下的**数字**要按本机重取 | `grep -n '__O_LARGEFILE\|O_LARGEFILE' /usr/include/aarch64-linux-gnu/bits/fcntl-linux.h /usr/include/aarch64-linux-gnu/asm/fcntl.h` 三处一起看；`strace -e trace=openat ./prog` 读名字而不是数字 |
| 「glibc 的 `pipe()` 会用 `pipe2` 原子地把 `O_CLOEXEC` 设好」 | **常见误传**。本机 glibc 2.39/aarch64 下 `strace` 实测 `pipe()` 发出的是 `pipe2([3, 4], 0)`——第二个参数是 0，**不带 `O_CLOEXEC`**。只有你显式写 `pipe2(p, O_CLOEXEC)` 才会带上；「现代 libc 都帮你加了 CLOEXEC」这类说法在这里不成立 | `strace -e trace=pipe,pipe2 ./prog` 看第二参数；正文 `shortio.c` 用的是 `pipe2(p, O_CLOEXEC \| O_NONBLOCK)`，那里才会打印出带 flag 的调用 |
| 「页大小是 4096、`_SC_OPEN_MAX` 是系统上限，可以写进代码或笔记」 | 两个都跟着机器与会话变。本机 `getconf PAGESIZE`=4096，但 ARM64 内核可以编译成 16 KiB 页（写作机 macOS 就是 16384），一切「按页对齐」的推导都要重算；`getconf _SC_OPEN_MAX` 本机 =**1024**，它只是当次 SSH 会话 `ulimit -n` 的投影，换个登录方式或启动器就不同；硬上限 **1048576** 来自 `/proc/sys/fs/nr_open` | `getconf PAGESIZE`、`getconf _SC_OPEN_MAX`、`ulimit -n`、`ulimit -Hn`、`cat /proc/sys/fs/nr_open`、`grep 'open files' /proc/self/limits` 六个读数放在一起看；代码里用 `sysconf(_SC_PAGESIZE)` 而不是字面量 4096 |
| 「`errno` 的数值到处一样，可以硬编码」 | **Linux 各架构相同**（都用 `asm-generic`）：本机实测 `EBADF`=9、`EAGAIN`=11、`ENOTDIR`=20、`EISDIR`=21、`EINVAL`=22、`ENOSPC`=28、`EPIPE`=32、`EXDEV`=18、`ELOOP`=40、`EMFILE`=24，与 x86-64 一致。但换一个内核系列（MIPS/Alpha）或换 BSD/macOS 就不同——写作机上 `EAGAIN`=35。所以数字可以读，不可以写进源码 | `python3 -c "import errno; print(errno.EAGAIN, errno.ELOOP, errno.EXDEV)"` 在两台机器各跑一次；源码里永远用宏 |
| 「`inside: fd=3`、`F_DUPFD_CLOEXEC(b,3)=3`、`mnt_id: 28` 这类具体号是正文事实」 | **fd 号取决于这个程序此前开了什么、关了什么**，不是可复现常数。本机实测：`safeopen` 的 `inside` 是 **fd=4**（前面那次 `open`+`close` 之后，`open(dir)` 占掉 3），`fdlife` 的 `F_DUPFD_CLOEXEC(b,3)` 返回 **5**（3、4 已被两次 `open` 占用）。`before/after close_range` 的 7/5 能对上是巧合：它含 stdio 三个与 `opendir` 自己那一个 | 跑 `./safeopen`、`./fdlife`；`ls /proc/self/fd` 看当前占用；把「返回不小于第三参数的最小可用 fd」这条规则用上就能预测 |
| 「`pwritev2` 写「4 字节头 + 14 字节体」= 18 字节」 | 正文 `rwv.c` 里的 `struct hdr { uint32_t len; uint32_t crc; };` 是 **8 字节**，8+14=**22**；本机实测两行都是 22（`pwritev2 wrote 22 bytes`、`read 22 bytes: len=14 body=scatter-gather`）。**18 与「4 字节头」是正文的一处待修读数**，不是你跑错了 | 跑 `./rwv`；`cc - <<< '#include <stdint.h>… printf("%zu\n", sizeof(struct hdr));'` 或直接加一行 `printf("%zu\n", sizeof(struct hdr));` 打印结构体大小 |
| 「管道一次能写 65536 字节是常量」 | 65536 = 默认管道容量 = **16 页 × 4 KiB**。页大小换成 16 KiB、或有人 `F_SETPIPE_SZ` 调过、或 `pipe-max-size` 策略不同，这个数就变；`/proc/sys/fs/pipe-max-size` 本机是 1048576，那是能申请的上限不是默认值。正文「1 MiB 只写进 65536」这条**结论**成立，**数字**要本机重取 | `./shortio` 看第一行；`getconf PAGESIZE`；`fcntl(F_GETPIPE_SZ)` 实测本机 65536；`cat /proc/sys/fs/pipe-max-size` |
| 「临时文件放 `/tmp`、目标放别处，`rename` 一定 `EXDEV`」 | 取决于挂载表。本机 `/tmp`、`/etc`、家目录**同在** `/dev/sda2` ext4（`findmnt -T` 三者都给 `/`），所以跨这些目录的 `rename` 会**成功**，正文那条「必须同目录」在本机复现不出来；要看到 `EXDEV` 得用另一个挂载，本机可用的是 `/dev/shm`（独立 tmpfs）。另外 `mv` 跨设备时会自己降级成「复制 + 删除」，**不报错**，所以用 `mv` 试是试不出 `rename(2)` 的真行为 | `findmnt -T /tmp /etc/hosts ~`；`df -T /`；`python3 -c "import os; os.rename('/tmp/x','/dev/shm/y')"` 得到 `errno=18 (Invalid cross-device link)` |
| 「`linkat(fd, "", ..., AT_EMPTY_PATH)` 任何进程都能用」 | 普通用户需要 `CAP_DAC_READ_SEARCH`；不带这个能力时 `AT_EMPTY_PATH` 那条会失败。正文的 `openflags.c` 之所以能打印 `O_TMPFILE linkat: ok`，是因为它**预置了回退**：改走 `linkat(AT_FDCWD, "/proc/self/fd/N", ..., AT_SYMLINK_FOLLOW)`。把回退删掉再跑，就能看到失败分支 | 跑 `./openflags`；把程序里那行 `if (linkat(...AT_EMPTY_PATH) == -1 && linkat(...AT_SYMLINK_FOLLOW) == -1)` 改成只留第一条再编译，看错误码；`capsh --print`（若装了）或直接按 uid 判断 |
| 「`O_DIRECT` 只要文件系统支持就行，栈上 `char buf[4096]` 也能用」 | 本机实测三件事：栈数组写 → **`EINVAL`(22)**；`posix_memalign(4096)` 的缓冲 + 8192 长度 → 成功；同一对齐缓冲**长度改 100** 或**偏移改 1000** → 都是 `EINVAL`。地址、偏移、长度**三个都要**按块对齐，少一个就失败；换文件系统（tmpfs、NFS）还可能是 `EOPNOTSUPP` 或直接不支持 | 写一个三行的探测程序：同一 fd 上分别用栈缓冲、对齐缓冲+8192、对齐缓冲+100、对齐缓冲偏移 1000 各 `write` 一次打印 `errno`；`findmnt -T <路径>` 确认文件系统类型 |
| 「`POSIX_FADV_NOREUSE` 会把数据丢出页缓存；`posix_fadvise` 失败要看 `errno`」 | `NOREUSE` 不丢数据（Linux 2.6.18–6.2 上是 no-op，6.3+ 只影响已映射页），要释放用 `DONTNEED`，且 `DONTNEED` 只对**干净页**生效、只是提示不是命令。`posix_fadvise` **返回错误码而不设 `errno`**，判返回值本身（本机实测 `rc=0`、`errno` 保持 0） | `int rc = posix_fadvise(fd,0,0,POSIX_FADV_DONTNEED); printf("%d/%d\n", rc, errno);` 看 rc 而不是 errno；`strace -e trace=fadvise64 ./prog` |
| 「`lsof +L1` 那行 `253,0 / 1073741824 / root / 12345` 是实测现场」 | 那是**示例形状**，不是本机读数。本机 `DEVICE` 列是 **`8,2`**（`/dev/sda2`），`SIZE`/`NODE` 每次不同，而且普通用户跑 `lsof +L1` 只能看见**自己**进程的持有关系（别人进程的名字会被挡），正文那行是 root 视角下的 `/var/log/app.log` | `lsof +L1 \| grep <你的临时文件名>`；`df -T` 看设备号；`ls -l /proc/<自己pid>/fd \| grep '(deleted)'` 作免 lsof 的替代 |
| 「`strace` 里 `read(3, ...)` 的 3 一直指同一个文件」 | fd 会**复用**：正文 2.2.18 那段 `copy` 的输出里，3 先是 `/etc/hosts`，`close(3)` 之后又变成目录 `.`。不加 `-yy` 只看数字，会把「读了什么」判错；这也是 `close` 不能重试的同一类风险 | 同一条命令加 `-yy` 再跑一次：`strace -yy -e trace=openat,read,close ./copy ...`，对比两次输出里 `3` 的归属 |
| 「`/usr/bin/perf` 存在就说明能取性能读数」 | 本机 `perf stat true` 每一行都是 `<not supported>`（没有 root、PMU 不可访问），只有墙钟时间可用。所以本章不引用任何 IPC、cache miss、分支失败率读数；替代是 `strace -c`/`-T`、`/proc/self/io`（`rchar` 与 `read_bytes` 的差说明有没有真走块设备）、`/usr/bin/time` 计时 | `perf stat true 2>&1 \| head -6` 看 `<not supported>`；`strace -c -e trace=fsync,fdatasync ./prog`；`cat /proc/self/io` |
| 「内核路径那几个函数名与源文件路径是跨架构、跨版本固定的」 | VFS 与 ext4 层（`vfs_write`、`generic_file_write_iter`、`generic_perform_write`、`balance_dirty_pages`）是内核通用代码，跨架构成立；但**系统调用入口**按架构不同：正文按 x86-64 + Linux 6.8 写（`entry_SYSCALL_64`、`sys_call_table[1]`），本机是 aarch64 + 内核 7.0.0-38，入口在 `arch/arm64/kernel/entry.S` 的 `el0_svc` 一侧，包装函数是 `__arm64_sys_*`。函数名会随版本重构（`vfs_read` 在部分配置下被内联），不要当常数 | 免 root 能核的是**边界读数**而不是内核符号：`grep -n '__NR_read\b\|__NR_write\b' /usr/include/asm-generic/unistd.h` 确认本机号是 63/64（不是 x86 的 0/1）、`grep -n io_setup /usr/include/asm-generic/unistd.h` 确认号 0 归 `io_setup`；`/proc/kallsyms` 要 root，按未实测处理（[2.1.15](ch01.md#sec-2.1.15) 已给过同类边界） |
| 「K（Linux/UNIX 系统编程手册）与 CSAPP 的中文版能覆盖本章这些接口」 | K 的中文版覆盖到 Linux 3.2：`O_TMPFILE`、`openat2`、`close_range`、`preadv2`/`RWF_*`、`SEEK_DATA`/`SEEK_HOLE` 的细节都在它之后，本章这些一律按 man-pages 与本机头文件写。CSAPP 中文第 3 版是**纯扫描版**（整页图片、没有文本层），只能按目录与章节号核对落点，不能引句子与页码 | 在 K 的目录里找 `openat2`/`close_range` 是否成节（找不到即未覆盖）；CSAPP PDF 里选中一段文字若复制为空、`pdftotext` 输出为空，即扫描版。本书只写「CSAPP 第 10 章」这类章节号 |

## 3. 本章未实测项

下面这些**没有本机证据**，引用前请当作待验证的形状、量级或方法，不要抄成事实：

- **x86-64 侧的全部具体数值**：2.2.9 那张表的整列八进制、2.2.18 的 `flags: 0100002`、系统调用号 `read`=0/`write`=1/`open`=2/`openat`=257/`getpid`=39/`statx`=332。本机是 aarch64，读不到 x86 的 `asm/fcntl.h` 与 `unistd.h`，这些数只能按「正文标注的 x86-64 参考值」引用，不能与本机读数混在一张表里比较。
- **需要 root / 内核特权的读数**：`dmesg`（本机上被 `dmesg_restrict` 挡住）、写 `/proc/sys/vm/*`（`dirty_ratio` 限速那条只能读不能改，所以「写者被拖慢」的具体量级未在本机验证）、`strace -p` 别人的进程（`ptrace_scope`）、`perf` 计数器、`/proc/kallsyms` 与任何内核符号级观测（所以 2.2.17 那张九层表里的**函数名**没有一个是本机核过的，按源码阅读结果对待）、`mount -o` 换选项、`prlimit` 改别人进程。
- **需要特殊文件系统或设备的场景**：NFS 上 `O_APPEND`/`O_EXCL` 的真实语义（本机没有 NFS 服务端，NFSv2 不原子那条只有文献依据）、`O_TMPFILE` 在网络文件系统上的 `EOPNOTSUPP`、配额触发的 `EDQUOT`（要管理员建配额）、append-only/immutable 触发的 `EPERM`（要 `chattr +A`，需 root）、只读挂载的 `EROFS`（要 `mount -o remount,ro`）、目标是挂载点的 `rename` → `EBUSY`（本机可 `mount --bind`，但要 root）、真实磁盘写满的 `ENOSPC`（本机只用 `/dev/full` 模拟，它是「设备谎报满」而不是文件系统满）。
- **断电/崩溃类结论**：「`rename` 后没 `fsync` 目录，崩溃后可能看不到新名字」这条只有机制依据与文献记录，本机无法安全地制造掉电（要外部电源控制或强制重启，且重启后 `/tmp` 会被清空，影响别的批次）。同理「脏页回写窗口内断电丢数据」按未实测对待。
- **页是否真的被丢掉**：`posix_fadvise(POSIX_FADV_DONTNEED)` 之后观测页缓存是否释放，需要 `mincore()` 或 `/proc/self/pagemap`（后者读 PFN 要 `CAP_SYS_ADMIN`）；本机只核到调用返回 0，没核「页确实不在了」。
- **多进程压力下的交错与覆盖对照**：正文 2.2.16 建议的「N 个进程各写一条定长记录，比较文件长度与每条完整性」这个实验**本套件没有跑压力**，题面给的是「怎么跑 + 看到什么算命中」，没有给本机计数；`O_APPEND` 交错（[B2](ch02-exercises.md#ex-2.2-B2)）同理。
- **`RWF_NOWAIT` 与 `RWF_DSYNC` 的失败分支**：本机 `rwv.c` 走的是成功路径，没有触发 `EAGAIN`/`EOPNOTSUPP`/`EINVAL`，所以「不支持时怎么降级」只有代码形状，没有本机读数。
- **`iostat`/`free` 的具体数字**：`%util`、`await`、`aqu-sz`、`buff/cache` 都随负载与设备变，本套件只确认命令能跑，没有取数；正文那六步排查顺序里的读数请按「当场取」理解。
- **`ioctl_demo.c` 的 `inode flags: 0x80000`**：这是本机 ext4 上那个 inode 的原始 flags（`FS_IOC_GETFLAGS`），换文件系统（tmpfs 会直接 `ENOTTY`）或换目录就不同；`TIOCGWINSZ` 那行也取决于会话有无终端。
- **容器内的差异**：`docker` 免 sudo 可用（本机跑过 `busybox`），但容器里的 fd 上限、挂载表、seccomp 与宿主不同，本章没有任何一条结论是在容器里核过的。
- **`lsof`、`filefrag`、`iostat` 之外的 sysstat 类命令**：本机确认存在，但正文没用到它们的输出细节，未逐项复跑。

## 4. 发现新问题怎么记

按「**现象 → 命令与输出 → 版本与环境 → 建议改法**」四段记，不要只写「我这里不对」：

1. **现象**：哪一节哪一处、你预期看到什么、实际看到什么。要具体到「`fdlife` 第二行打印 5，正文写 3」这种可定位的粒度，不要写「输出对不上」。
2. **命令与输出**：粘贴**原样**命令与原样输出，中间不要加解释、不要修空格。多行读数请把触发它的那一步一起给（例如 `exec 3<>/tmp/x` 与 `cat /proc/self/fdinfo/3` 成对出现）。改了源码再发现的差异，要说明改了哪一行——像「把 `linkat` 的回退删掉」这类改动会直接改变错误码，不写就等于没证据。
3. **版本与环境**：`uname -a` 与 `uname -m`、`cat /etc/os-release | head -2`、`gcc --version | head -1`、`ldd --version | head -1`、`getconf PAGESIZE`、`ulimit -n`、`findmnt -T <涉及的路径>`、`strace -V | head -1`、是否有 `sudo`（`sudo -n true` 的结果）、命令跑在 SSH 会话还是脚本里（决定有没有终端）。涉及数值时先声明口径：POSIX/man 条款、本机工具输出、量级示例，还是未实测。
4. **建议改法**：给出你认为正文应该改成什么（换成本机值、加一句「随架构变」、把示例标成「示意输出」、或把这条挪进本页），并给出可复核的依据——本机头文件的原文行、`man` 手册段落、或重跑两次的稳定输出。**同一个读数要复跑两次**才够：本机 `mnt_id`/`ino`/fd 号这类每次都变的数，只有「两次同值」才配写进正文；一次跑出来的「像真的」的输出，处置方式只有两种——重跑换成真输出，或改写成「怎么观察 + 看到什么算命中」的判读描述，留在原样不算处理。
