计算机里的所有信息——整数、浮点数、字符、指针、指令——最终都是位（bit）。位本身没有类型，类型是**解释位的方式**：同一串 32 个位，按无符号解释是 4294967295，按补码解释是 -1，按 IEEE 754 单精度解释是一个 NaN。C 语言的类型系统做的核心事情，就是规定「这块内存用哪种解释」。

这一章讲三组规则：整数怎么编码、运算怎么溢出、浮点怎么近似。三组规则都有精确的数学定义，也都有容易被编译器利用的边界（未定义行为）。理解它们不是为了应付面试题，而是为了在调试器里看到 `0xffffffff` 时，能立刻判断它是 -1、是 `UINT_MAX`、还是一个被截断的指针。

约定：除非特别说明，字长 $w=32$，字节序为小端，编译器为 GCC 13、平台 x86-64。文中所有位运算例子都可以用 `printf` 验证。

## 1.2.1 位、字节、字与十六进制 {#sec-1.2.1}

这一节回答：计算机里的信息用什么「单位制」数？十六进制凭什么无处不在？`sizeof` 报的数字，哪些能带到别的平台、哪些不能？

::: preview 先抓住一件事
三层单位各管各的：位（bit）是最小信息单元，字节（byte）是最小可寻址单元（位数由 `CHAR_BIT` 给出，标准不保证它是 8），字（word）是机器的自然处理宽度。十六进制不是另一套数学，是二进制的速记：一位恰好对应 4 位二进制，分组就能现场换算。`int`/`long`/指针多宽，不靠印象，查数据模型。
:::

### 单位制：位、字节、字

先跑一段小程序把本机的「单位表」打印出来（源文件 `lab12_a.c`，`cc -std=c17 -O2 lab12_a.c`）：

```c
#include <stdio.h>
#include <limits.h>
int main(void)
{
    printf("char=%zu short=%zu int=%zu long=%zu long long=%zu ptr=%zu size_t=%zu\n",
           sizeof(char), sizeof(short), sizeof(int), sizeof(long),
           sizeof(long long), sizeof(void *), sizeof(size_t));
    printf("CHAR_BIT=%d INT=[%d,%d]\n", CHAR_BIT, INT_MIN, INT_MAX);
    return 0;
}
```

两台机器输出完全相同（macOS arm64 + Apple clang 21 与 Ubuntu 24.04.5 aarch64 + gcc 13.3，均 `-O2` 实测）：

```text
char=1 short=2 int=4 long=8 long long=8 ptr=8 size_t=8
CHAR_BIT=8 INT=[-2147483648,2147483647]
```

`sizeof(char)==1` 是标准写死的，其余数字标准只给「至少多宽」的下限；`CHAR_BIT=8` 也是本机实测——标准只要求一个 `unsigned char` 至少表示 256 个值。取值区间的门规在 1.2.2。字长指 CPU 通用寄存器的宽度：x86-64 与 ARM64 都是 64 位，但实测 `int` 仍是 4 字节——「机器一次处理 64 位」和「`int` 占 32 位」是两件事，混为一谈是后面很多「为什么这里截断了」的根源。

### 十六进制：二进制的速记

一位十六进制对应 4 位二进制，两位恰好一个字节，所以内存地址、位掩码、颜色值都用它写。记住 8 个映射，换算不再需要计算器：

| 十六进制 | 二进制 | 十六进制 | 二进制 |
|:--:|:--:|:--:|:--:|
| 0 | 0000 | 8 | 1000 |
| 1 | 0001 | 9 | 1001 |
| 2 | 0010 | A | 1010 |
| 3 | 0011 | B | 1011 |
| 4 | 0100 | C | 1100 |
| 5 | 0101 | D | 1101 |
| 6 | 0110 | E | 1110 |
| 7 | 0111 | F | 1111 |

正向：把 `0x3F8A` 按 4 位一组展开；反向：十进制不断除 16 取余。两段循环让程序替你对答案（接在上面 `main` 里）：

```c
unsigned v = 0x3F8Au;
printf("v=%u  %%#X=%#X\n", v, v);              /* %#X 自动带上 0X 前缀 */
for (int i = 3; i >= 0; i--) {
    unsigned n = (v >> (i * 4)) & 0xFu;          /* 每个十六进制位展开成 4 位 */
    printf("%X = %u%u%u%u  ", n, (n >> 3) & 1u, (n >> 2) & 1u, (n >> 1) & 1u, n & 1u);
}
for (unsigned t = 16266u; t; t /= 16u)           /* 16266 转十六进制：除 16 取余 */
    printf("%X", t % 16u);
```

两台机器输出一致：

```text
v=16266  %#X=0X3F8A
3 = 0011  F = 1111  8 = 1000  A = 1010
A8F3
```

`0x3F8A` 按权展开 $3\times16^3+15\times16^2+8\times16+10=16266$，与第一行对上；余数从低到高读，16266 反过来写就是 `A8F3`。注意 `%#X` 输出大写 `0X`，想要小写 `0x` 用 `%#x`。

### 数据模型：哪些数字能跨平台带走

`int`、`long`、指针三者的宽度组合叫数据模型（data model，ABI 对基本类型宽度的约定）：LP64 是 32/64/64（Linux 与 macOS 的 64 位系统），LLP64 是 32/32/64（Windows 的 64 位：指针 8 字节但 `long` 仍 4），ILP32 是 32/32/32（32 位系统）。名字里的 L/I/P 就指 `long`/`int`/pointer。实测值 `long=8 ptr=8` 符合 LP64；**到了 Windows 上这两个数就会分家**。

判据不是背数字：移植前在目标平台跑一遍上面的 `sizeof` 程序；写跨平台代码时，凡要装指针、文件大小、内核对象编号的地方，用 `stdint.h` 的 `int32_t`/`int64_t`（精确宽度）和 `size_t`/`intptr_t`/`off_t`（角色类型），别用裸 `int`/`long`。系统接口一律 typedef 也是这个原因——Linux 2.2 之前用户 ID 用 16 位表示，2.4 起变 32 位，裸类型写的代码会被内核升级直接打碎。字节序顺带埋一句：多字节对象的字节存放顺序，1.2.3 用 `show_bytes` 亲眼看，完整规则留给 1.2.6 与 1.2.11。

::: def 定义 1.2.1 · 字长与数据模型（word size & data model） {#def-1.2.1}
字长是 CPU 通用寄存器与地址总线的位宽，决定机器一次自然处理多少位。数据模型按 `int`/`long`/指针三者的宽度命名：LP64 是 32/64/64，LLP64 是 32/32/64，ILP32 是 32/32/32。C 标准只承诺 `sizeof(char)==1`、`CHAR_BIT` 至少 8、各类型的最小范围；其余宽度全部由实现决定，要用就实测。
:::

::: ex 例 1.2.1 · 先猜输出，再动手算 {#ex-1.2.1}
把程序里的 `0x3F8Au` 换成 `3000u` 再跑 `printf("%#x\n", w)`。先猜输出，再手算验证：3000 的十六进制与按 4 位分组的二进制各是什么？

::: sol 解答
手算：3000 = 187×16 + 8；187 = 11×16 + 11（B）；11 = 0×16 + 11（B）。余数从低到高读是 8、B、B，得 `0xBB8`；分组展开 `1011 1011 1000`。两台机器实测 `printf` 给出 `0xbb8`。注意 3000 不是 4 位对齐的漂亮数——分组换算的便利只在「从十六进制读二进制」，从十进制出发仍要做除法。
:::
:::

::: think 思考 · 为什么押注十六进制而不是八进制
选速记法只看一件事：分组边界对不对。八进制 3 位一组，8 位字节被切成不对称的「3+3+2」，读一个字节要跨两个八进制位；十六进制 4 位一组，两位正好铺满一个字节，半字节（nibble）的边界也看得见。所以位掩码、寄存器手册、颜色值全用十六进制，八进制只活在 `chmod` 这类历史接口里。
:::

### 1.2.1 小结

① 位、字节、字是三层单位，`CHAR_BIT` 和字长都要实测，C 标准只给下限；② 十六进制与二进制的换算就是按 4 位分组，`%#x` 自动带前缀；③ `int`/`long`/指针的宽度由数据模型决定，LP64 与 LLP64 在 `long` 上分家。如果只记住一件事，那就是：**宽度是查出来、跑出来的，不是背出来的。**

::: errata 常见错误清单（1.2.1 节）
1. **「字长就是 `int` 的宽度」**——x86-64/ARM64 字长 64 位，`int` 仍是 32 位（实测 `int=4`）。
2. **「`sizeof(long)==8` 走到哪都成立」**——LP64 成立，Windows 的 LLP64 上是 4；判据是目标平台的数据模型，或实测。
3. **「一个字节 8 位是 C 标准规定的」**——标准只规定 `CHAR_BIT` 至少 8；可移植代码按宏算位宽，别硬乘 8。
4. **「字节序会影响源文件和字符串」**——文本逐字节存放，与字节序无关；受影响的是把多字节整数/浮点当字节数组读写的那一刻（1.2.6）。
:::

## 1.2.2 无符号、补码与取值范围 {#sec-1.2.2}

这一节回答：有符号数为什么偏偏用「补码」这种编码，而不是最自然的「符号位 + 绝对值」？`-1` 到底是数还是位模式？为什么 `-128` 恰好比 `127` 多出一个？

::: preview 先抓住一件事
补码（two's complement）不是编码谜题，是一条硬件决策：**让有符号加法的位级规则与无符号完全相同**——加法器只需一套电路，减法靠「取反加一」也并进同一条通路。在模 $2^w$ 的世界里，`unsigned char` 上的 `-1` 与 `255` 是同一个全 1 位模式，不同的只是解释。
:::

### 同一个位向量的两种读法

无符号数的编码最直接：位向量 $\vec{x}$ 的值是

$$
B2U_w(\vec{x}) = \sum_{i=0}^{w-1} x_i 2^i .
$$

补码把最高位（符号位，sign bit）的权重取负：

$$
B2T_w(\vec{x}) = -x_{w-1}2^{w-1} + \sum_{i=0}^{w-2} x_i 2^i .
$$

同一个位向量 `1111 1011`（`0xFB`）：按无符号读是 251，按 8 位补码读是 -5。别背展开式，跑一遍（`lab12_b.c`，`cc -std=c17 -O2`）：

```c
uint8_t u = 0xFBu;
int8_t  s = (int8_t)0xFBu;
printf("0xFB as uint8_t=%d, as int8_t=%d\n", u, s);
printf("(unsigned char)(-1)=%#x, (signed char)255=%d\n",
       (unsigned char)(-1), (signed char)255u);
```

两机输出逐字相同（Apple clang 21 arm64 / Ubuntu gcc 13.3 aarch64，`-O0` 与 `-O2` 亦同）：

```text
0xFB as uint8_t=251, as int8_t=-5
(unsigned char)(-1)=0xff, (signed char)255=-1
```

第二行是枢纽：-1 装进 `unsigned char` 得 255，255 装进 `signed char` 得 -1，全 1 位模式一动没动——模 256 下它们是同一个刻度。`0xFB` 不是「一个数」，是「位向量 + 解释」。

### 模 $2^w$：补码圆环与一套加法器

<pre class="layout">
                    0x00 (0)
             0x7F (127)   0xFF (-1)
          0x7E (126)       0xFE (-2)
          ...                  ...
          0x02 (2)         0x82 (-126)
          0x01 (1)         0x81 (-127)
                    0x80 (-128)
        顺时针：+1；从 0x7F 到 0x80 是「正溢出」到 TMin
</pre>

圆环把硬件动机画出来了：加 1 是顺时针走一格，从 0 逆时针就是负数，而 $-b \equiv 2^w - b$ 按位写恰是 $\sim b + 1$——减法借加法：$a - b$ 就是 $a + \sim b + 1$、丢进位。**圆上的位级「挪格」动作对两种读法完全相同**，这就是加减共用一条电路的含义。差别在事后：同一条加法用进位 CF 与溢出 OF 分别记录两种读法的越界（判据在 [1.2.9](#sec-1.2.9) 表四）。圆环没有终点，溢出后仍是合法位模式、只是数学值错了；C 把有符号溢出定为未定义行为而不是「回绕」。

### 取值范围：为什么负数多一个

$$
TMin_w = -2^{w-1},\qquad TMax_w = 2^{w-1}-1,\qquad UMax_w = 2^w-1 .
$$

| 宽度 $w$ | $TMin$ | $TMax$ | $UMax$ |
|--:|--:|--:|--:|
| 8 | -128 | 127 | 255 |
| 16 | -32768 | 32767 | 65535 |
| 32 | -2147483648 | 2147483647 | 4294967295 |
| 64 | -9223372036854775808 | 9223372036854775807 | 18446744073709551615 |

不对称数一数就明白：0 和正数用掉 $2^{w-1}$ 个模式，负数只剩同样多——最负那个（8 位的 `0x80`）注定没有正对应。`limits.h` 打印实测（两机同输出）：

```text
INT_MIN=-2147483648 INT_MAX=2147483647  -INT_MAX=-2147483647
-tmin=-2147483648, -tmin==tmin? 1
```

第三行要小心：对 `volatile int` 的 `INT_MIN` 取负是 **UB**；`-O0` 下观察到它回绕成自己，是硬件走了一步，不是语言承诺。再摸圆环边界（两机实测）：`(unsigned char)(255+1)=0` 是标准定义良好的回绕；`(int8_t)(127+1)` 得 -128、`(int8_t)(-128-1)` 得 127——算术先按 `int` 算（1.2.3 的提升）再截回 8 位，有符号转窄类型是实现定义，gcc/clang 都截低位。两种命运别混成一个。

### 手写补码三步法

::: method 手算一个位模式的补码值
1. 看最高位：是 0，直接按无符号读。
2. 是 1：全部取反、加 1（丢掉超过 $w$ 位的进位），得到绝对值的位模式，再添负号。
3. 验算：原位模式与取负后的位模式按 $w$ 位相加应得全 0。
:::

三个手算例：`0xFB` → $-5$（与程序吻合）；`0xFFFFFFF0` → $-16$；`0x80` 取反加一**又回到 `0x80`**——「绝对值 128」装不进 8 位正数区，三步法在 `TMin` 上退化。

::: def 定义 1.2.2 · 补码（two's complement） {#def-1.2.2}
最高位权重为负的位向量编码：$B2T_w(\vec{x}) = -x_{w-1}2^{w-1} + \sum_{i=0}^{w-2} x_i 2^i$，值域 $[-2^{w-1},\, 2^{w-1}-1]$。关键性质：加减法按位走模 $2^w$，与无符号同规则；取负是 $\sim x + 1$；$TMin$ 的相反数不可表示。C17 还允许原码/反码，C23 起强制补码；本机 gcc/clang 都是补码。
:::

::: ex 例 1.2.2 · 圆环上的两步，哪步没走 {#ex-1.2.2}
先猜三行输出，再跑（`lab12_h.c`，`cc -std=c17 -O2 lab12_h.c`）：

```c
unsigned char c = 200;
c = (unsigned char)(c + 56);
printf("c=%u\n", c);
signed char d = -128;
printf("d-1=%d\n", d - 1);
printf("(unsigned char)(d-1)=%u\n", (unsigned char)(d - 1));
```

最容易猜错的是第二行：8 位圆环上 $-128$ 逆时针一格应该是 $+127$，所以很多人报 127。

::: sol 解答
实测两机一致：`c=0`、`d-1=-129`、`(unsigned char)(d-1)=127`。第一行 256 超出 8 位，回绕到 0，模 256 定义良好。第二行的陷阱是**提升**：`d - 1` 先转成 `int` 再算，$-129$ 装得下，8 位圆环根本没被走到。第三行才真的截断：$-129 \bmod 256 = 127$。结论：想让一个数走 8 位圆环，必须让它**以 8 位类型参与运算或赋值**。
:::
:::

::: think 思考 · C 标准为什么拖到 C23 才钦定补码
标准是「实现之间」的契约。C89 签署时，原码机（早期 Cray）与反码机（UNIVAC 系列）还在签合同，钦定补码等于宣布它们不合法；旧机器退场后，C23 才把「有符号即补码」写进正文。启示：依赖具体位模式的代码，可移植承诺最脆弱。
:::

### 1.2.2 小结

① 补码让加减共用一条通路，事后才用不同标志判断两种溢出；② `-1` 与 `255` 在 8 位上是同一个位模式，「数」= 模式 + 解释；③ 范围不对称源于 $2^w$ 个模式对半分，`TMin` 没有相反数。如果只记住一件事，那就是：**先在圆环上想位，再给圆环套解释（类型）**。手算速查与 4 位补码全表在 [1.2.9](#sec-1.2.9) 表二。

::: errata 常见错误清单（1.2.2 节）
1. **「补码就是取反加一」**——取反加一是「求相反数」的算法，不是编码定义；定义是最高位权重为负，抓住它才知道 `0x80` 为什么是 -128。
2. **「有符号溢出会回绕成负数」**——位模式还在圆环上，但 C 定为 UB，编译器可假设它不发生。硬件回绕不等于语言保证（1.2.4 实测）。
3. **「`char` 默认有符号」**——实现定义，同架构也翻脸：实测 Apple clang（arm64）`CHAR_MIN=-128`、Ubuntu gcc（aarch64）`CHAR_MIN=0`。二进制字节一律写 `uint8_t`/`int8_t`。
4. **「`-INT_MIN` 会得到正数」**——相反数不可表示；实测回绕成 `INT_MIN` 自己，是 UB 下的硬件行为，一次都不能依赖。
:::

::: method 即时自测 · 1.2.2
**Q1（记忆）** 写出 $B2T_w$ 的公式与 $TMin_w$、$TMax_w$。为什么负数比正数多一个？

**Q2（辨析）** `(unsigned char)(-1)` 与 `(signed char)255` 的位模式各是什么？这两种转换哪种是标准保证、哪种是实现定义？

**Q3（应用）** 手算 8 位补码 `0x9C` 的值，并用三步法验算。

**Q4（迁移）** 循环 `for (int8_t i = 0; i < n; i++)` 中 `i = i + 1` 会不会溢出 UB？改成 `unsigned char i` 呢？

::: sol 答案
**A1** $B2T_w=-x_{w-1}2^{w-1}+\sum_{i=0}^{w-2}x_i2^i$；$TMin=-2^{w-1}$，$TMax=2^{w-1}-1$。$2^w$ 个模式里非负数（含 0）占一半，最负的没有正对应。
**A2** 位模式都是 `0xFF`（全 1）。负数转无符号是定义良好的模 $2^w$；超范围值转有符号窄类型是实现定义，gcc/clang 都截低位。
**A3** 取反 `0x63`、加 1 得 `0x64` = 100，所以是 $-100$；验算 `0x9C + 0x64 = 0x100`，丢进位得全 0。
**A4** 都不是运算层面的 UB：`i+1` 与 `i++` 先提升为 `int`，128 装得下，截断发生在写回 `int8_t` 的实现定义转换（两机实测 -128）；`unsigned char` 回绕永远定义良好。运算本身越界（`int x = INT_MAX; x + 1;`）才是 UB。
:::

## 1.2.3 符号扩展、截断与类型转换 {#sec-1.2.3}

这一节回答：8 位装进 16 位时，空出来的高位填什么？反过来截窄，保留的是哪几位？`int` 碰上 `unsigned`，比较按谁的规矩走？

::: preview 先抓住一件事
三条规则都由两问决定。变宽：源表达式类型有符号，高位复制符号位（符号扩展）；无符号，高位填 0（零扩展）——都保持数值。变窄：只保留低 $w$ 位，再按目标类型重新解释，不是四舍五入。混号运算：同宽时先把有符号转成无符号再比，这是 C 里最隐蔽的 bug 产地。
:::

### 场景：一台程序，六次转换

先跑再讲。`lab12_c.c` 的 `main` 节选（完整文件 `cc -std=c17 -O2 lab12_c.c`），两台机器逐字输出相同：

```c
int8_t   a8  = (int8_t)0x8Fu;
int16_t  wid = a8;                     /* 源类型有符号：符号扩展 */
uint16_t uwid = (uint8_t)0x8Fu;        /* 源类型无符号：零扩展 */
int16_t  direct = (int16_t)0x8F;       /* 0x8F 是 int，值是 143 */
int32_t  x = 0x1FF;
/* (int8_t)x 与 (uint8_t)x：截断后按目标类型重读 */
int  num = -1; unsigned size = 1;
printf("num(-1) > size(1) ? %d\n", num > size);
```

```text
(int8_t)0x8F = -113, 位模式 0x8f
int8_t -> int16_t: -113, 位模式 0xff8f（高 8 位全 1）
uint8_t -> uint16_t: 143, 位模式 0x8f
(int16_t)0x8F 直接 = 143（0x8F 本身是 int，无扩展）
(int8_t)0x1FF = -1, (uint8_t)0x1FF = 255
(unsigned)(-1) = 4294967295
(int)UINT_MAX = -1
num(-1) > size(1) ? 1   <-- 错答案
sizeof(short)=2, sizeof(sh+sh)=4, typeof 提升为 int
ea+eb=300（不是 (unsigned char) 回绕的 44）
```

### 变宽：符号扩展 vs 零扩展

判据只看一件事——**当前参与转换的类型有没有符号**，不看这个数「本来想表达什么」。8 位 `0x8F` 按 `int8_t` 是 -113，扩到 16 位高 8 位填符号位 1：

```text
0x8F        = 1000 1111                 = -113 (int8)
0xFF8F      = 1111 1111 1000 1111       = -113 (int16)
0x008F      = 0000 0000 1000 1111       = +143（错误：零扩展）
```

为什么填 1 保值：高 8 位全 1 的净贡献是 $-2^{15} + (2^8 + \cdots + 2^{14}) = -256$，正好把 143 拉回 -113；零扩展净贡献为 0，只适合无符号。第 2、3 行实测正是这两个位模式。

### 变窄：截断是保留低位

第 5 行：`0x1FF`（511）截到 8 位，保留 `0xFF`——按 `int8_t` 重读是 -1，按 `uint8_t` 重读是 255；截断只「切高位 + 换眼镜」。第 4 行是常见错误：`0x8F` 字面量的类型是 `int`（143），截到 16 位还是 143；先写 `(int8_t)` 才有符号扩展、得 -113。

### 整型提升：运算至少在 `int` 里发生

整型提升（integer promotion，比 `int` 窄的类型在表达式里先转成 `int` 再运算）解释了 1.2.2 例里 `d-1` 为什么是 -129。实测：`sizeof(sh+sh)` 报 4；`unsigned char` 的 200 与 100 相加得 300，**没有**在 8 位圆环上回绕成 44。想让它绕，必须显式转回窄类型。

### 混号比较：`num > size` 错得安静

`num` 是 -1、`size` 是 1，`num > size` 却输出 1（第 8 行，两机一致）：同宽的 `int` 与 `unsigned` 混合时，`num` 先按「加 $2^{32}$」转成 `4294967295` 再比。反方向 `(int)UINT_MAX` 是 -1（实测；实现定义，gcc/clang 都按补码重读）。`cc -Wall` 其实喊过：clang 报 `comparison of integers of different signs`，gcc 报 `comparison of integer expressions of different signedness`。这类比较写进 `for (unsigned i = n; i >= 0; i--)` 就是死循环——无符号恒不小于 0。

### 眼见为实：`show_bytes`

怀疑某次转换时，别猜，把对象的字节直接打印出来（源文件 `lab12_g2.c`，`cc -std=c17 -O2`）：

```c
#include <stdio.h>
#include <stdint.h>
#include <limits.h>
static void show_bytes(const void *p, size_t n)
{
    const unsigned char *b = p;
    for (size_t i = 0; i < n; i++)
        printf(" %02x", b[i]);
    putchar('\n');
}
int main(void)
{
    printf("CHAR_MIN=%d -> char 默认%s\n", CHAR_MIN,
           CHAR_MIN == 0 ? " unsigned" : " signed");
    uint32_t x = 0x01234567u;
    int16_t  s = -113;          /* 0xFF8F：符号扩展后的位模式 */
    int8_t   t = (int8_t)0x8F;  /* 单独一个字节，符号性由类型说了算 */
    printf("x :"); show_bytes(&x, sizeof x);
    printf("s :"); show_bytes(&s, sizeof s);
    printf("t :"); show_bytes(&t, sizeof t);
    return 0;
}
```

两台机器实测字节行完全相同，只有第一行不同：

```text
macOS clang：CHAR_MIN=-128 -> char 默认 signed
Ubuntu gcc ：CHAR_MIN=0 -> char 默认 unsigned
x : 67 45 23 01
s : 8f ff
t : 8f
```

读法：`x` 的低字节 `67` 排在最低地址——两台 ARM64 都是小端（little-endian，低字节放低地址；大端相反）；`s` 的 `8f ff` 就是手推的 `0xFF8F`；`t` 单独一个 `8f`，「是 -113 还是 143」在内存里根本不存在，要等类型裁决。字节序完整规则与对齐留给 [1.2.6](#sec-1.2.6) 和 [1.2.11](#sec-1.2.11)。

::: method 判定流程 · 面对任何一条转换/比较表达式
1. 问**源表达式的当前类型**：十六进制字面量默认 `int`；声明过 `int8_t` 不等于运算是 8 位。
2. 问方向：变宽——源有符号做符号扩展、无符号做零扩展；变窄——保留低 $w$ 位、按目标类型重新解释。
3. 混号——同宽时「有符号转无符号」；窄类型先提升；见 `-Wsign-compare` 就把两侧统一类型。
4. 拿不准就跑 `show_bytes` 或 `printf("%#x")`，让位模式替你说话。
:::

先猜：这两行在 Apple clang 21（arm64）与 gcc 13.3（aarch64）上输出一样吗？

::: think 思考 · 为什么同宽混号是「转无符号」而不是「转大类型」
两个方向总要牺牲一头：负数转无符号毁掉「-1」的直觉，大无符号转有符号毁掉 `0x80000000` 的价值。规则选了保住无符号：`unsigned` 承载位模式，转换保值，硬件的无符号比较器也更便宜。代价就是实测那类错答案——规则不可谈判，能谈判的只有写法：比较前两侧显式同型。
:::

### 1.2.3 小结

① 扩展方式由**源表达式当前的类型**定符号性，不由数值本意定；② 截断只保留低位、再按目标类型重读；③ 运算之前先有整型提升，8 位「回绕」要显式转回窄类型才发生；④ 同宽混号比较有符号转无符号，错答案不报错但 `-Wall` 会喊。如果只记住一件事，那就是：**转换看当前类型，别看字面心意。** 完整转换规则表在 [1.2.9](#sec-1.2.9) 表五。

::: errata 常见错误清单（1.2.3 节）
1. **「`0x8F` 是一个 8 位量」**——字面量的类型是 `int`（带 `u` 后缀是 `unsigned`），没有符号扩展；要 8 位语义必须写 `(int8_t)0x8F`。
2. **「截断是取绝对值或四舍五入」**——截断只保留低 $w$ 位，`0x1FF` 截到 8 位是 `0xFF`，按有符号重读是 -1，与 511 的「大小」再无关系。
3. **「`char` 就是 `int8_t`」**——`char` 符号性实现定义：两台 ARM64 实测 `CHAR_MIN` 分别是 -128 与 0。序列化、算术都写精确类型。
4. **「负数和 unsigned 比较时负数小」**——`-1 > 0u` 为真（实测），因为 -1 先被转成了 `UINT_MAX`。
:::

**Q2（辨析）** `(int16_t)0x8F` 与 `(int16_t)(int8_t)0x8F` 各是多少？差别出在哪一步？

## 1.2.4 整数运算与溢出 {#sec-1.2.4}

这一节回答：运算结果「装不下」时到底会发生什么？为什么无符号和有符号是两种命运？编译器会怎样「利用」这个区别？

::: preview 先抓住一件事
溢出有两种命运。无符号是模 $2^w$ 运算，标准**定义良好**：`UINT_MAX + 1` 就是 0，哪个编译器都一样。有符号溢出是未定义行为（undefined behavior，UB）：不是「回绕成负数」，而是授权编译器假设它不发生、并在这个假设上优化——折常量、删循环都从这里来。下面给两台机器的真实输出。
:::

### 无符号：标准担保的回绕

$$
x +_w^u y = (x + y) \bmod 2^w .
$$

实测（`lab12_d.c`，两机 `-O0` 与 `-O2` 相同）：

```text
UINT_MAX+1u=0  0u-1u=4294967295
```

第二行是这类 bug 的日常形态：用无符号存「差」，被减数小的时刻得到 `UINT_MAX`。回绕不报错，无符号「更安全」只在先判大小后成立。

### 有符号：UB 不是回绕，是被当成假设

跑一段程序（`lab12_d.c` 节选，`cc -std=c17 -O2`；`main` 把参数转成 `int x`）：

```c
int gt(int x) { return x + 100 > x; }

int has_wrap(int *a, int n)
{
    for (int i = 1; i < n; i++)
        if (a[i] + i < a[i])   /* 若真回绕，INT_MAX 这一项会命中 */
            return i;
    return -1;
}
```

传入 `x = 2147483600`（加 100 超过 `INT_MAX`）与数组 `{0, INT_MAX}`，四组真实结果：

| 机器 · 优化级别 | `gt(2147483600)` | `has_wrap` |
|:--|--:|--:|
| Apple clang 21（arm64）· `-O0` | 0 | 1 |
| Apple clang 21（arm64）· `-O2` | 1 | -1 |
| Ubuntu gcc 13.3（aarch64）· `-O0` | 1 | -1 |
| Ubuntu gcc 13.3（aarch64）· `-O2` | 1 | -1 |

反汇编把话挑明：`-O2` 下两台机器的 `gt` 都只剩 `mov w0, #1` / `ret`；Ubuntu 的 `has_wrap` 只剩 `mov w0, #0xffffffff` / `ret`，**整个扫描循环被删**（clang `-O2` 运行结果同样是 -1）。编译器不是「没看出会溢出」，而是拿「有符号加法不溢出」当公理。

更能迷惑人的是同一程序里的两种答案（`chk.c` 实测于两台：同一句 `x + 100 > x`，一份强制真算、一份交给编译器发挥）：

```text
x=2147483600 x+100=-2147483596  cmp(volatile)=0
non-volatile: y+100=-2147483596  cmp=1
```

加法真的回绕了（两行都打印出负数），但非 `volatile` 的那次比较被折成了 1——同一个表达式，在编译器手里有两个答案。`volatile` 在这里是取证工具，不是修复手段。

::: def 定义 1.2.4 · 定义良好、实现定义、未定义 {#def-1.2.4}
C 给行为发「三档牌照」。**定义良好**：标准直接规定结果（无符号回绕）。**实现定义**：标准给候选、编译器挑一个并写进文档（有符号转窄类型、`char` 默认符号性）。**未定义**：什么都不保证，编译器还可假设它不发生来做优化（有符号溢出、除零、移位量不小于位宽）。前两档实测后可依赖，第三档实测通过也不能依赖。
:::

### 怎么安全地写：先检测，后使用

```c
int r;
int ovf = __builtin_add_overflow(INT_MAX, 1, &r);
printf("add_overflow(INT_MAX,1): ovf=%d r=%d\n", ovf, r);
ovf = __builtin_mul_overflow(100000, 100000, &r);
printf("mul_overflow(1e5,1e5): ovf=%d r=%d\n", ovf, r);
```

两台机器 `-O0`、`-O2` 输出都相同：

```text
add_overflow(INT_MAX,1): ovf=1 r=-2147483648
mul_overflow(1e5,1e5): ovf=1 r=1410065408
```

契约看返回值：`ovf=1` 表示溢出，此时**不要读结果** `r`。`__builtin_add_overflow`/`_sub_`/`_mul_` 由 GCC 与 Clang 同时支持；内核在 `linux/overflow.h` 包成 `check_add_overflow`/`check_sub_overflow`。标准 C 一直没有这类接口：可移植检测需要「目标位宽边界 + OF/CF 硬件标志」的抽象，事实标准只能落在编译器内建上。手写「同号相加结果异号」也成立，但符号组合与提升容易漏，完整判据在 [1.2.9](#sec-1.2.9) 表四。另两个选项：`-fwrapv` 把溢出改口成回绕，是 GCC 方言；`-fsanitize=undefined`（UBSan）是取证工具，两台机器实测都能抓到现形，Ubuntu gcc 输出：

```text
lab12_d.c:7:32: runtime error: signed integer overflow: 2147483600 + 99 cannot be represented in type 'int'
lab12_d.c:18:35: runtime error: division of -2147483648 by -1 cannot be represented in type 'int'
```

### 除法的两条边界

1. **整数除法向零截断**：实测 `-7/2 = -3`、`-7%2 = -1`（两机一致）——余数符号跟着被除数。用 `%` 分桶前先想清楚负输入。
2. **`INT_MIN / -1` 是 UB**：商 $2^{31}$ 装不进 `int`。两台 ARM64 实测都**没有**崩溃：gcc 两个优化级与 clang `-O0` 给出硬件 `sdiv` 的回绕值 `INT_MIN`，**clang `-O2` 给出 -1**——UB 被优化器利用的直接样本。x86-64 上 `idiv` 触发 `#DE`、收 `SIGFPE` 的本机未实测（无 x86-64），口径见 1.2.9 表四。除数为 0 同样是 UB。标准为什么选「发牌照」而不是「强制回绕」？规定回绕等于在最热的算术路径上绑死优化；发牌照，编译器就能把「不溢出」当免费公理，代价由写代码的人用检测来付。

::: method 判定流程 · 这段代码会不会溢出
1. 找**运算的静态类型**：`int8_t + 1` 先提升，在 `int` 里算；字面量默认 `int`。
2. 无符号：只会回绕——检查点变成「会不会想要负数」（`a - b`、`i >= 0` 的循环）。
3. 有符号：数学结果能否超出 $[TMin, TMax]$？重灾区是乘法、`count * size` 类累加、用户输入的上界。
4. 兜底用 `__builtin_add_overflow`/`_sub_`/`_mul_`（内核用 `check_*_overflow`），别手写同号判据。
5. 抓现场用 `-fsanitize=undefined` 重跑——`-O0` 下「看起来会回绕」不是证据。
:::

函数 `int gt(int x) { return x + 100 > x; }`，用 `cc -O2 -S` 看汇编。先猜：几条指令？`x` 取 2147483600 时返回什么？

::: sol 解答

:::

::: think 思考 · UB 是编译器的恶意吗
不是，它是一份「你违约在先」的合同：一旦违反，编译器在公理「不发生」上推出的一切结论都生效，哪怕现实里加法确实回绕了。排障时先问「有没有 UB」再问「编译器是不是有 bug」。语言层的另一种选择（Rust 在 debug 下对溢出直接 panic）对照见 1.2.18。
:::

### 1.2.4 小结

① 无符号回绕定义良好，有符号溢出是 UB，两种命运不能混谈；② UB 的危险在编译器拿它当假设：`gt` 折成常量、`has_wrap` 循环消失、`INT_MIN/-1` 在 clang `-O2` 给出 -1，全是实测；③ 兜底用 `__builtin_*_overflow`，抓现场用 UBSan。如果只记住一件事，那就是：**「跑出来是回绕」证明不了「语言承诺回绕」。** 硬件标志与检测函数的对照在 [1.2.9](#sec-1.2.9) 表四。

::: errata 常见错误清单（1.2.4 节）
1. **「无符号减法不会出问题」**——`0u - 1` 是 `UINT_MAX`（实测）。用无符号表示差值，先判大小。
2. **「有符号溢出会回绕，我见过」**——`-O2` 的 `gt` 连加法指令都没生成；clang 对 `INT_MIN/-1` 直接给 -1。你看到的「回绕」是 UB 在 `-O0` 下的偶然形状。
3. **「开 `-fwrapv` 就能放心溢出」**——那是 GCC 方言，代码依旧不可移植；正确做法是检测。
:::

::: method 即时自测 · 1.2.4
**Q1（记忆）** 无符号溢出和有符号溢出在 C 标准里分别是什么地位？各举一个本节实测的例子。

**Q2（辨析）** `int8_t i = 127; i = i + 1;` 与 `int x = INT_MAX; x = x + 1;`，哪个触发 UB？为什么？

**Q3（应用）** `int n = atoi(user); void *p = malloc(n * sizeof(int));` 指出风险：`n * sizeof(int)` 的运算类型是什么？给出修复。

## 1.2.5 位运算与移位 {#sec-1.2.5}

这一节回答：六个位运算符里哪些是工程里天天用的？`a & b == c` 到底算了什么？用移位代替乘 2、除 2，在负数和出界移位量上会发生什么？

::: preview 先抓住一件事
位运算的日常被掩码（mask，按位挑出/放入感兴趣的那几位）三个动作包揽：置位、清位、取位，其余「奇技淫巧」按需再查。最大的坑是优先级：`&` 结合得比 `==` 松，`a & b == c` 实际算的是 `a & (b == c)`，两台编译器都直接出警告。移位的三条边界性质还各不相同：有符号左移溢出是 UB，移位量不小于位宽是 UB，有符号右移是实现定义。
:::

### 场景：置位、清位、翻转、取位一次跑完

六个位运算符：`&`（与）、`|`（或）、`^`（异或）、`~`（取反）、`<<`、`>>`，前四个逐位独立运算。先跑 `lab12_e.c` 前几行（`cc -std=c17 -O2 lab12_e.c`）：

```c
unsigned flags = 0x5Au;              /* 0101 1010 */
flags |=  (1u << 0);                 /* 置位 bit 0 */
flags &= ~(1u << 3);                 /* 清位 bit 3 */
flags ^=  (1u << 1);                 /* 翻转 bit 1 */
printf("%#X, bit2=%u\n", flags, (flags >> 2) & 1u);
```

两台机器实测相同：

```text
0X51, bit2=0
```

按位推一遍：`0101 1010` 置 bit0 → `0101 1011`；清 bit3 → `0101 0011`；翻 bit1 → `0101 0001` = `0x51`。四个惯用法当公式背：置位 `x |= 1u << k`、清位 `x &= ~(1u << k)`、翻转 `x ^= 1u << k`、取位 `(x >> k) & 1u`，每条都带 `u` 后缀。异或的 `x ^ x = 0`、`x ^ 0 = x`、`x ^ y ^ y = x` 支撑「找只出现一次的数」与轻量校验；`^` 交换两个数的奇技不推荐。

### 优先级：`&` 比 `==` 松

`if (n & 1 == 0)`（`n = 6`，想判偶数）——实测两机都走 else：先算 `1 == 0` 得 0，再算 `n & 0`。`-Wall` 原话（实测 stderr）：

```text
clang：  warning: & has lower precedence than ==; == will be evaluated first [-Wparentheses]
gcc：    warning: suggest parentheses around comparison in operand of ‘&’ [-Wparentheses]
```

写成 `if ((n & 1) == 0)` 就对了。规则一句话：**位运算符出现在任何表达式里，先套括号。** 这个优先级是历史遗留：位运算符沿用了早期算术运算的结合位置，改会砸烂存量代码，只能靠警告救。

::: def 定义 1.2.5 · 算术右移与逻辑右移（arithmetic vs logical right shift） {#def-1.2.5}
逻辑右移：高位补 0，对无符号数恰是 $\lfloor x / 2^k \rfloor$。算术右移：高位复制符号位，对补码数相当于**向 $-\infty$ 取整**的除法。C 里有符号右移用哪一种是实现定义；本机 gcc 与 clang（ARM64）实测都是算术右移。
:::

### 移位：三条边界，三种性质

实测输出（两台机器逐字相同，`lab12_e.c` / `lab12_j.c`，`-O0` 与 `-O2` 一致）：

```text
-8>>1=-4, -8/2=-4
-7>>1=-4, -7/2=-3
0xF0000000u>>28=0XF
(1u << 33) 运行时=0x2
(1UL << 64) 运行时=0x1
(int)(1 << 31) 运行时=-2147483648
```

逐条对号。**右移**：`-8>>1` 与 `-8/2` 相等不是规律——`-7>>1=-4` 而 `-7/2=-3`：算术右移向下取整、C 除法向零截断，在负奇数上分道（编译器「加偏置再右移」的补法见 1.2.9 表三）；「左移乘 2、右移除 2」对负数不成立。**左移**：`1 << 31` 有符号越界，属 UB；实测 `-O0` 观察到 `INT_MIN`，是硬件形状不是承诺，写 `1u << 31` 才是定义良好的模 $2^{32}$。**移位量出界**：`1u << 33`、`1UL << 64` 同为 UB；两台 ARM64 运行期计数下实测给出 `0x2` 与 `0x1`（硬件按 5/6 位掩码）——本机可观察形状而已，编译器对常量移位量有权另给答案，x86-64 未实测。无符号右移永远逻辑：`0xF0000000u >> 28` 得 `0xF`。

### 高频位技巧

| 表达式 | 作用 | 例子（$x=\texttt{0xB0}$，实测） |
|:--|:--|:--|
| `x & (x - 1)` | 清除最低位的 1 | → `0XA0` |
| `x & -x` | 取出最低位的 1 | → `0X10` |
| `x ^ (x >> 1)` | 二进制转格雷码 | → `0XE8` |
| `__builtin_popcount(x)` | 1 的个数 | → 3 |
| `__builtin_ctz(x)` | 最低位 1 的下标 | → 4 |
| `__builtin_clz(0x0F)` | 前导 0 的个数（32 位） | → 28 |

判 2 的幂：`x` 非 0 且 `x & (x-1)` 为零。`x & -x` 是树状数组（Fenwick tree）的推进步；`ctz`/`clz` 是位图分配器找空位的原语，`popcount` 数集合基数。三个内建对 0 都未定义，先判零。完整版在 1.2.12 的工具箱程序。

::: intuition 为什么 `x & -x` 能取出最低位的 1
设 `x` 最低位的 1 在第 $k$ 位。$-x = \sim x + 1$：取反后低 $k$ 位全 1、第 $k$ 位变 0；加 1 进位把低 $k$ 位归零、第 $k$ 位变回 1，更高位全部取反。两者相与，只剩第 $k$ 位。推导不依赖位宽——实测 `0xB0` 得 `0x10`。
:::


### 逻辑运算与位运算：`&&`、`||`、`!` 不是 `&`、`|`、`~` {#sec-1.2.5.1}

`&&`/`||` 短路求值、结果只有 0/1；`&`/`|` 两边都求值、逐位运算。短路会改变副作用：

```c
int p = 0;
if (p != NULL && *p == 1) { ... }   /* 安全：p 为 NULL 时不解引用 */
if (p != NULL & *p == 1)  { ... }   /* 仍会解引用 p，崩溃 */
```

`!` 把任何值折成 0/1，`~` 逐位取反——四者不能互换。混号比较的坑见 1.2.3 实测。

::: method 判定流程 · 移位安全三连问
1. 操作数的**静态类型**：无符号左右移都定义良好（模 $2^w$）；有符号左移不得越界，右移方向是实现定义。
2. 移位量在 $[0, w)$ 内吗？出界是 UB；计数来自变量时先显式取掩码（`k &= 31u`，1.2.12 的 `rotl32` 就这么写），别赌硬件掩码。
3. 想要「除以 $2^k$ 且向零取整」？有符号用 `/`，别用 `>>`——负奇数上实测差 1。
:::

::: ex 例 1.2.5 · 哪一行的位测试悄悄失败 {#ex-1.2.5}
先猜两条 `if` 各走哪个分支，再跑（`lab12_k.c`）：

```c
unsigned m = 0x06u;                     /* bit1 与 bit2 都置着 */
if (m & 0x4 == 0x4) puts("bit2 已置位");
else puts("没置");
if ((m & 0x4) == 0x4) puts("加括号后：bit2 确实置位");
```

::: sol 解答
实测两机一致：先「没置」，再「加括号后：bit2 确实置位」。第一条算的是 `m & (0x4 == 0x4)` = `0x06 & 0x01` = 0，位测试失真；换 `m = 0x07` 它又「碰巧为真」——结果随数据摆动才最恶毒。`-Wparentheses` 会报警（原话见上），但位运算一律套括号才是写法纪律。
:::
:::

::: think 思考 · 既然有乘除法，为什么还要位运算
有些接口的语义本来就是「位」：设备寄存器、ELF 标志位、内核 UAPI 的 flag、分配器位图——不是数值，是一组开/关。`x |= 1u << k` 说的是「第 k 个开关拨到开」，位运算在工程里是接口语言，不是性能暗器；性能那部分编译器早就会自己做。
:::

### 1.2.5 小结

① 掩码四式（置/清/翻/取）覆盖位运算日常，全部带 `u` 后缀；② `&` 比 `==` 松，`a & b == c` 是实测能翻车的静默 bug，两台编译器都警告；③ 移位三条边界性质不同：有符号左移越界 UB、移位量出界 UB、有符号右移实现定义，负数右移不等于除 2。如果只记住一件事，那就是：**位运算表达式先加括号，移位之前查类型和计数。** 移位与除法的等价关系全表在 [1.2.9](#sec-1.2.9) 表三。

::: errata 常见错误清单（1.2.5 节）
1. **「`if (flags & MASK == MASK)` 在测位」**——实际测的是 `flags & 1`（实测走错分支）。写 `(flags & MASK) == MASK`。
2. **「`1 << 31` 得到 `INT_MIN` 可以放心用」**——有符号左移越界是 UB，`-O0` 的回绕只是硬件形状。位构造一律 `1u << 31`。
3. **「移位量自动按位宽取模」**——两台 ARM64 运行期实测给出模 32/64 的结果，但语言层面是 UB：常量折叠与别的编译器有权另给答案，别赌。
4. **「`x >> 1` 永远等于 `x / 2`」**——`-7` 实测一个 -4 一个 -3；`__builtin_ctz(0)` 也属「看着能用」：对 0 未定义（`clz(0)` 同），先判非零。
:::

::: method 即时自测 · 1.2.5
**Q1（记忆）** 写出置位、清位、翻转、取位四个惯用法（操作数 `x`、位号 `k`）。

**Q2（辨析）** `1u << 32`、`1 << 31`、`(-8) >> 1` 在 C 标准里的地位各是什么？本机上各实测到什么？

**Q3（应用）** 手算 `0x69 ^ 0x5A` 与 `0x69 & 0x5A`（按 4 位分组）。

**Q4（迁移）** `O_RDWR` 值为 2，代码写 `if (flags & O_RDWR == O_RDWR)` 想测读写标志。指出两处错误，给出正确写法。

::: sol 答案
**A1** 置位 `x |= 1u << k`；清位 `x &= ~(1u << k)`；翻转 `x ^= 1u << k`；取位 `(x >> k) & 1u`。
**A2** 前两个是 UB（移位量出界 / 有符号左移越界），第三个实现定义（本机都算术右移）。实测 `0x1`、`INT_MIN`、-4——UB 的实测值不构成保证。
**A3** `0110 1001` 与 `0101 1010`：异或得 `0x33`，与得 `0x48`。
**A4** 一错在优先级：`O_RDWR == O_RDWR` 得 1，变成 `flags & 1`；二错在语义：值 2 是两位字段里的编码而非单标志。正解 `(flags & O_ACCMODE) == O_RDWR`；「多个标志都在」用 `(flags & (A | B)) == (A | B)`。
:::

## 1.2.6 字节序、对齐与结构体布局 {#sec-1.2.6}

这一节回答：一个多字节整数，哪个字节放在低地址？结构体成员之间那些看不见的空档为什么必须存在？为什么不能把内存里的结构体直接 `fwrite` 进文件或网络？

::: preview 先抓住一件事
字节序只决定多字节整数的字节存放顺序；本节两台机器同为小端，对照输出逐字相同，差异要到跨平台协议里才显形。对齐（alignment）是「地址必须是某值整数倍」的硬件要求，编译器为此插填充：成员合计 10 字节、实测 `sizeof` 24。两条规则共同指向：**原始内存不是可传输的格式**。
:::

### 场景：打印一个 `uint32_t` 的四个字节

1.2.3 用 `show_bytes` 看过 `0x01234567` 存成 `67 45 23 01`；现在扩到网络字节序转换（`lab1c02_a.c`，`cc -std=c17 -O2`）：

```c
uint32_t x = 0x01234567u;
show_bytes("x raw   ", &x, 4);            /* 从最低地址起逐字节打印 */
uint32_t n = htonl(x);                    /* 主机字节序 -> 网络字节序 */
show_bytes("htonl(x)", &n, 4);
printf("ntohl(htonl(x))==x ? %d ; ntohl(x)==x ? %d\n",
       ntohl(htonl(x)) == x, ntohl(x) == x);
```

两台机器实测输出逐字相同（macOS arm64 + Apple clang 21；Ubuntu 24.04.5 aarch64 + gcc 13.3）：

```text
x raw      : 67 45 23 01
htonl(x)   : 01 23 45 67
ntohl(htonl(x))==x ? 1 ; ntohl(x)==x ? 0
```

第一行：最低地址放着最低有效字节 `67`——小端（little-endian，低字节放低地址）；反过来叫大端（big-endian）。x86-64 与 AArch64 都默认小端（本机两臂都是 aarch64，无 x86-64 可跑；x86-64 的小端文件头见 1.2.16 的 `readelf` 输出），**两台同为小端，对照看不出差别；差异在跨平台协议里**。第二行：转换后的存放顺序是大端——网络字节序就是大端。第三行：往返能还原，但 `ntohl(x)` 不等于 `x`：小端机器上真的翻转字节，大端机器上恒等——所以一律走函数接口，不手写换字节。

::: def 定义 1.2.6 · 字节序与网络字节序（endianness & network byte order） {#def-1.2.6}
字节序是多字节标量在内存中的存放顺序：小端把最低有效字节放在最低地址，大端相反。网络字节序是 IP/TCP 等协议规定的大端；头文件 arpa/inet.h 的 `htons`/`htonl`/`ntohs`/`ntohl` 在主机序与网络序之间转换。
:::

### 对齐为什么存在

对齐（alignment）用大白话说，就是「这类数据的地址必须是某个值的整数倍」。硬件层面有两条理由：访问粒度——内存按自然块取数，跨块的一次 8 字节取数要拆成两次；原子性——对齐访问能被硬件一次完成，未对齐的可能被拆开，某些架构直接 fault。C 因此要求对象地址是其对齐值的倍数，编译器在成员之间插入填充（padding）。用 `offsetof`/`sizeof` 打印布局，两台机器实测逐字相同：

```text
A: size=12 c=0 i=4 d=8
B: size=24 c=0 d=8 e=16
C: size=16 d=0 c=8 e=9
```

A 的 `int` 要 4 对齐只能从 4 起，中间 3 字节是填充；B 成员合计 10 字节、实测 24；C 把 `double` 挪到最前，只占 16。**把大成员放前面通常省填充**，但真正该记的是规则：组成数组时后面的元素也要对齐，所以总大小必须向上取整到最大对齐值的倍数。

### packed 的代价

`#pragma pack(1)` 与 `__attribute__((packed))` 能取消填充，代价是成员可能未对齐访问。实测（同一程序，两台机器逐字相同）：

```c
struct hdr        { uint8_t ver; uint32_t len; };
struct hdr_packed { uint8_t ver; uint32_t len; } __attribute__((packed));
uint32_t *p = (uint32_t *)&hp.len;   /* 故意取 packed 成员地址 */
volatile uint32_t v = *p;            /* 故意未对齐解引用 */
```

```text
hdr: sizeof=8 len_off=4 ; packed: sizeof=5 len_off=1
hdr        : a5 00 00 00 44 33 22 11
hdr_packed : a5 44 33 22 11
(&hp.len)&1 = 1
unaligned read=11223344 -> no fault here
```

打包后 `len` 落在偏移 1，`&hp.len` 是奇数指针，两个编译器都发了 `-Waddress-of-packed-member` 警告（实测 stderr）。故意解引用它：两台 ARM64 都**没有**触发对齐异常——如实报告：ARMv8 普通加载由硬件自动处理，代价在性能与单副本原子性；fault 风险在原子指令、设备内存与部分旧核心上——「本机不崩」不是语言保证。

### 序列化同时踩坑的真实形态

把 `struct wire { uint32_t magic; uint16_t len; char kind; };` 当线格式：实测 `sizeof` 是 8，`fwrite` 落盘 `04 03 02 01 06 00 57 00`；格式规范里只有 6 字节、magic 为大端。按规范解析时两个坑同时踩中：magic 字节序倒着（主机是小端），尾部还多一个填充字节；换平台填充还会挪。同形炸弹也藏在 `memcmp` 与 `qsort` 里：填充字节的值未定，两个「内容相等」的结构体可能按字节比出不等。正确做法是逐字段序列化（serialization，把对象拉平成有公开规范的字节串）：写时转定宽类型再 `htonl`，读时 `memcpy` 进本地对齐变量——`stat`、`sockaddr`、ELF 头同理。

::: ex 例 1.2.6 · 先猜这个文件多大 {#ex-1.2.6}
声明 `struct wire w[2]` 与 `struct C { double d; char c; char e; } arr[2]`，整块 `fwrite` 进文件：共多少字节，多少不携带字段信息？

::: sol 解答
实测 `sizeof` 是 8 和 16：文件共 48 字节、14 个填充（`wire` 每条 1、`C` 每条 6），magic 还倒着存。同机读回正常，到大端机器或按规范手写的解析器里全错——整块落盘等于把编译器私有契约发布成文件格式。
:::
:::

::: think 思考 · 为什么内存布局不配当交换格式
内存布局是「编译器 + 架构 + 编译选项」的私人契约，格式是跨年代机器的公共契约。直接落盘省下的几行序列化代码，抵不过格式随编译器或平台改变。
:::

::: method 判定流程 · 要把一段内存传出边界
1. 问边界：同进程同架构 `memcpy` 可以；跨进程、文件、网络先问规范。
2. 问整数：定宽类型 + 定字节序（网络大端），写 `htonl`、读 `ntohl`。
3. 问填充：不整结构体转储，逐字段序列化、`memcpy` 进对齐变量。
4. 问符号性：裸字节用 `uint8_t`（`char` 符号实现定义，1.2.3）。
:::

### 1.2.6 小结

① 两台 ARM64 都是小端，字节序差异要到协议与文件边界才显形，转换一律走 `htonl`/`ntohl`；② 对齐源自访问粒度与原子性，布局要实测不要背；③ `packed` 省空间、丢对齐访问，没 fault 不等于保证不 fault。如果只记住一件事，那就是：**原始内存不是可传输的格式，跨边界必须逐字段序列化。** 对齐值表、布局规则、位域与 `packed`/`alignas` 的完整讨论在 [1.2.11](#sec-1.2.11)。

::: errata 常见错误清单（1.2.6 节）
1. **「我的机器字节序就是代码里的字节序」**——文件与网络按规范不按主机：实测 `htonl` 小端翻转、大端恒等。
2. **「结构体大小等于成员大小之和」**——B 成员合计 10 字节、实测 24。
3. **「`memcmp` 为 0 结构体就相等」**——填充字节的值未定。
4. **「`packed` 最多就是变慢」**——未对齐访问丢单副本原子性，原子指令与设备内存路径上是真 fault。
:::

## 1.2.7 IEEE 754 浮点 {#sec-1.2.7}

这一节回答：浮点的那 32/64 个位怎么切成三段？0.1 为什么存不下却打印得像 0.1？零、无穷、NaN 在位模式上各长什么样？

::: preview 先抓住一件事
IEEE 754 把一个数写成符号、阶码（移码）、尾数三段：$(-1)^S \times 1.f \times 2^{E-\text{bias}}$。移码把阶码整体搬进非负区，比较大小能复用整数的无符号比较电路。0.1 这类十进制小数在二进制里是无限循环小数，存进去只能取近似——实测存储值 0.10000000000000000555（`%.20g`，两台机器相同）。范围与精度共用固定位数，压一头就松另一头。
:::

### 场景：把位模式打印出来

1.2.2 说「数 = 位模式 + 解释」，浮点是这句话最极端的例子：同样 32 位，按 IEEE 754 解释可以是 1.0，也可以是 `+∞` 或 NaN。用 `memcpy` 把对象字节拷出来打印（`lab1c02_b.c`，`cc -std=c17 -O2 -lm`）：

```c
static uint32_t fbits(float f) { uint32_t u; memcpy(&u, &f, 4); return u; }
static uint64_t dbits(double d) { uint64_t u; memcpy(&u, &d, 8); return u; }
printf("0.0       f=%08X  d=%016llX\n", fbits(0.0f), (unsigned long long)dbits(0.0));
printf("-0.0      f=%08X  d=%016llX\n", fbits(-0.0f), (unsigned long long)dbits(-0.0));
printf("1.0       f=%08X  d=%016llX\n", fbits(1.0f), (unsigned long long)dbits(1.0));
printf("0.5       f=%08X  d=%016llX\n", fbits(0.5f), (unsigned long long)dbits(0.5));
printf("+inf      f=%08X  d=%016llX\n", fbits(INFINITY), (unsigned long long)dbits(INFINITY));
printf("inf-inf   d=%016llX isnan=%d\n",
       (unsigned long long)dbits(INFINITY - INFINITY), isnan(INFINITY - INFINITY));
```

两台机器实测输出逐字相同：

```text
0.0       f=00000000  d=0000000000000000
-0.0      f=80000000  d=8000000000000000
1.0       f=3F800000  d=3FF0000000000000
0.5       f=3F000000  d=3FE0000000000000
+inf      f=7F800000  d=7FF0000000000000
inf-inf   d=7FF8000000000000 isnan=1
```

两个读法。其一：`0.0`、`0.5`、`1.0` 从小到大，位模式 `00000000 < 3F000000 < 3F800000` 也严格递增——这是阶码用移码的效果，正数比大小和整数的无符号比较是同一条电路。其二：`+inf` 是阶码全 1、尾数全 0；NaN 是阶码全 1、尾数非 0；`+0` 与 `-0` 只差一个符号位。

### 三段：符号、阶码、尾数

IEEE 754 单精度（`float`）32 位、双精度（`double`）64 位：

<pre class="layout">
float  31 30            23 22                                    0
       ┌─┬────────────────┬───────────────────────────────────────┐
       │S│   exp (8 bit)  │            frac (23 bit)              │
       └─┴────────────────┴───────────────────────────────────────┘
&#8203;
double 63 62                       52 51                           0
       ┌─┬──────────────────────────┬───────────────────────────────┐
       │S│       exp (11 bit)       │          frac (52 bit)        │
       └─┴──────────────────────────┴───────────────────────────────┘
</pre>

规格化数的值是

$$
(-1)^S \times 1.f \times 2^{E - \text{bias}},
$$

单精度 bias 是 127，双精度是 1023；$1.f$ 是「隐含的前导 1 加上尾数小数部分」。两条边界：阶码字段全 0 不是「最小指数」，而是零与非规格化数（非规格化数没有隐含 1）的标记；全 1 标记无穷与 NaN。

::: def 定义 1.2.7 · 移码（biased notation / excess-K） {#def-1.2.7}
移码把阶码存成「真实指数 + bias」（127/1023），让整个指数范围搬进非负区。阶码字段因此直接是无符号整数：比较两个阶码不用先处理符号，浮点的大小比较能复用整数那套无符号比较电路；正数的位模式也因此随数值单调递增（负数破坏单调性，全序折叠技巧留给 1.2.10）。
:::

手算一个例子：$0.15625$。

1. 转二进制：$0.15625 = 5/32 = 0.00101_2$。
2. 规格化：$0.00101_2 = 1.01_2 \times 2^{-3}$。
3. 符号 $S=0$；阶码 $E = -3 + 127 = 124 = \texttt{0111 1100}_2$。
4. 尾数小数部分 `.01`，补齐 23 位：`0100 0000 0000 0000 0000 000`。
5. 拼起来：`0 01111100 01000000000000000000000` = `0x3E200000`。

验证：阶码字段 124 对应 $2^{-3}$，尾数 `01` 是 $0.25$，值 $1.25 \times 2^{-3} = 0.15625$；把符号位翻成 1 就是 `0xBE200000` = $-0.15625$。程序里打印 `fbits(0.15625f)`，实测正是 `3E200000`，与手算吻合。

特殊值由阶码字段的两条边界区分：

| 阶码字段 | 尾数 | 含义 |
|:--|:--|:--|
| 全 0 | 全 0 | $\pm 0$ |
| 全 0 | 非 0 | 非规格化数，没有隐含 1，逐渐下溢 |
| 既非全 0 也非全 1 | 任意 | 规格化数，按上面的公式解释 |
| 全 1 | 全 0 | $\pm\infty$ |
| 全 1 | 非 0 | NaN，`0.0/0.0`、`inf-inf` 这类无效运算的结果 |

非规格化数的精确边界、逐字段取值表与位模式排序技巧，都留给 [1.2.10](#sec-1.2.10)。

### 0.1 为什么存不下

0.15625 = 5/32，是 $2$ 的负幂的有限和，存得精确；0.1 = 1/10 的分母带了因子 5，二进制下是无限循环小数（$0.000110011\ldots_2$），24/53 位必须截停。用 `%.20g` 打印存储值，两台机器逐字相同：

```text
0.1f      bits=3DCCCCCD stored=0.10000000149011611938
0.1       bits=3FB999999999999A stored=0.10000000000000000555
0.3       bits=3FD3333333333333 stored=0.2999999999999999889
```

名叫 0.1 的变量装的一直是一个略大的数；打印出 `0.1` 是 `printf` 四舍五入的显示层把戏。

::: ex 例 1.2.7 · 0.1 + 0.2 等于 0.3 吗 {#ex-1.2.7}
先猜 `(0.1+0.2)==0.3`（`double`）与 `(0.1f+0.2f)==0.3f`（`float`）两个表达式的真假。

::: sol 解答
两台机器实测：`double` 为假，`0.1+0.2` 打印出 `0.30000000000000004`（`%.17g`）；`float` 却为真。机理：0.1、0.2、0.3 各自是不同位置的近似，两个近似相加还要再舍入一次——最后「恰好相等」还是「差一点」取决于三个近似各自落在哪，`float` 的真值属巧合，不是精度更好。
:::
:::

### 范围与精度共用一块饼

位数是固定预算：`float` 的 32 位里 8 位阶码管范围（约 $10^{\pm38}$）、24 位有效值管精度（约 7 位十进制）；`double` 用 64 位换来约 $10^{\pm308}$ 与约 16 位十进制。要范围就得从尾数抠位数，反过来也一样——这是浮点的基本 trade-off，两头不能都白拿。

::: think 思考 · 为什么用二进制分数而不是十进制
IEEE 754 选「二进制分数 × 2 的幂」，因为阶码与尾数的运算能直接复用整数那套电路。标准后来增加了十进制浮点扩展，但主流编译器的 `float`/`double` 仍是二进制——想让 0.1 真是 0.1，出路是整数「分」或十进制库（见 1.2.8），不是「更精确一点」的二进制。
:::

### 1.2.7 小结

① 三段各司其职：符号位管正负，移码阶码管范围并让比较走无符号电路，尾数管精度；② 特殊值藏在阶码字段的边界——全 0 是 0 与非规格化，全 1 是无穷与 NaN；③ 0.1 这类写不成有限二进制分数的数只能存近似，`%.20g` 实测就是证据。如果只记住一件事，那就是：**浮点变量里是二进制分数，不是你写的十进制。** 逐字段取值、非规格化边界与 ULP 在 [1.2.10](#sec-1.2.10)。

::: errata 常见错误清单（1.2.7 节）
1. **「阶码全 0 是最小的指数」**——它是零与非规格化数的标记；最小正规格化数对应阶码字段 1。
2. **「0.1 存不准，但 `%.1f` 打印回来了」**——那是显示层四舍五入，存储值是 `0.10000000000000000555`（`%.20g` 实测）。
3. **「NaN 是一种特殊数值，可以写 `x == NAN` 判断」**——NaN 与任何值（含自身）比较都为假，要用 `isnan`。
4. **「`float` 与 `double` 只是精度不同，其它一样」**——规则相同但近似落点不同：实测 `0.1f+0.2f==0.3f` 真、`0.1+0.2==0.3` 假。
:::

::: method 即时自测 · 1.2.7
**Q1（记忆）** `float` 的三段各占几位、各管什么？单精度与双精度的 bias 是多少？

**Q2（辨析）** 为什么 `0.5` 的位模式 `3F000000` 小于 `1.0` 的 `3F800000` 不是巧合？负数还成立吗？

**Q3（应用）** 手算 $-0.15625$ 的 32 位位模式。

**Q4（迁移）** 日志里一个 `double` 打印成 `0.000000`，下游偶发除出 `inf`。给出两种候选位模式，各用一行代码判定。

::: sol 答案
**A1** 符号 1 位（正负）、阶码 8 位（范围与比较）、尾数 23 位（精度）；bias 为 127 与 1023。
**A2** 阶码是移码，字段值越大真实指数越大，正数位模式随数值单调递增（实测 `3F000000 < 3F800000`）；负数相反——符号位 1 时字段越大值越小，单调性被破坏。
**A3** `0.15625` 是 `3E200000`，只翻最高位：`BE200000`。
**A4** 候选是 `-0.0` 与 NaN。`isnan(x)` 为真即 NaN；否则 `signbit(x)` 为真就是 `-0.0`（实测 `1.0/-0.0` 得 `-inf`，1.2.8）。
:::

## 1.2.8 舍入、精度陷阱与比较 {#sec-1.2.8}

这一节回答：舍入到底怎么选最后一位？为什么同一堆数换个加法顺序结果就变？比较两个浮点数，究竟该用 `==` 还是容差？

::: preview 先抓住一件事
每次浮点运算都要舍入一次，默认规则是「就近、平局取偶」：实测 `rint(0.5)` 得 0，不是 1。舍入带来两类反直觉：大数吃小数——`1e16+1.0` 还是 `1e16`（实测 ulp(1e16) = 2）；加法失去结合律——实测 `((1e16+1)+1)-1e16` 得 0 而 `(1e16+(1+1))-1e16` 得 2。比较之前先处理 NaN 与 ±0，然后才轮到「绝对容差还是相对容差」。
:::

### 场景：吸收、顺序、特殊值一次跑完

`lab1c02_c.c` 节选（`cc -std=c17 -O2 -lm`），先把七组判定打印出来：

```c
double a = 1e16, b = 1.0, c = -1e16, d = 1.0;
printf("1.0+1e-16 == 1.0 ? %d\n", (1.0 + 1e-16) == 1.0);
printf("1e16+1.0 == 1e16 ? %d ; ulp(1e16)=%.1f\n",
       (1e16 + 1.0) == 1e16, nextafter(1e16, 2e16) - 1e16);
printf("(a+b)+c = %.17g ; a+(b+c) = %.17g\n", (a + b) + c, a + (b + c));
printf("((a+b)+d)+c = %.17g ; (a+(b+d))+c = %.17g\n",
       ((a + b) + d) + c, (a + (b + d)) + c);
printf("rint default: 0.5->%.1f 1.5->%.1f 2.5->%.1f -2.5->%.1f\n",
       rint(0.5), rint(1.5), rint(2.5), rint(-2.5));
printf("-0.0==0.0 ? %d ; signbit(-0.0)=%d ; 1.0/-0.0=%g\n",
       (-0.0 == 0.0), signbit(-0.0), 1.0 / -0.0);
printf("NAN==NAN ? %d ; isnan=%d ; isfinite(inf)=%d\n",
       NAN == NAN, isnan(NAN), isfinite(INFINITY));
```

两台机器实测输出逐字相同：

```text
1.0+1e-16 == 1.0 ? 1
1e16+1.0 == 1e16 ? 1 ; ulp(1e16)=2.0
(a+b)+c = 0 ; a+(b+c) = 0
((a+b)+d)+c = 0 ; (a+(b+d))+c = 2
rint default: 0.5->0.0 1.5->2.0 2.5->2.0 -2.5->-2.0
-0.0==0.0 ? 1 ; signbit(-0.0)=1 ; 1.0/-0.0=-inf
NAN==NAN ? 0 ; isnan=1 ; isfinite(inf)=0
```

### 机制：舍入怎么选，误差怎么累积

舍入模式（rounding mode）决定「真实结果落在两个可表示数中间时取哪一个」。默认规则是就近取偶（round-to-nearest, ties-to-even）：取更近的一边；正好在中点时取尾数最低位为 0 的那个。`rint` 实测行就是证据：0.5 取 0、1.5 取 2、2.5 取 2（向零方向的 `-2.5` 取 -2）——按「四舍五入」该得 1 和 3；实测 `lround(2.5)` 才得 3，那是另一种舍入。取偶不是审美：平局在两侧均匀分布，长期累加才不会系统性偏一个方向。头文件 fenv.h 的 `fesetround` 能切换模式，但库函数和编译期常量都假设默认模式，普通程序不该改。

舍入的代价是三种陷阱。**吸收（absorption）**：两数数量级差超过半个 ulp，小的那个直接消失——实测 `1e16+1.0` 仍是 `1e16`（ulp(1e16)=2），`1.0+1e-16` 仍是 1.0。**灾难性抵消（catastrophic cancellation）**：相近的两数相减，前头一致的有效位全消掉，剩下的是各自的舍入误差——实测 `(1e16+1.0)-1e16` 得 0，那个 1 在减法之前就已经丢了。**整数转浮点**：`float` 只有 24 位有效位，实测 `(float)16777217`（$2^{24}+1$）得 `16777216.0`。

精度位数由宏给出，两台机器实测：

```text
两机相同：FLT_MANT_DIG=24 FLT_EPSILON=1.192092896e-07
          DBL_MANT_DIG=53 DBL_EPSILON=2.220446049e-16
macOS clang ：sizeof(long double)=8  LDBL_MANT_DIG=53  LDBL_EPSILON=2.220446049e-16
Ubuntu gcc  ：sizeof(long double)=16 LDBL_MANT_DIG=113 LDBL_EPSILON=1.925929944e-34
```

::: def 定义 1.2.8 · 机器精度与有效位数（machine epsilon） {#def-1.2.8}
机器精度 $\epsilon$ 是「1 与下一个可表示数的间隔」，决定一次舍入的相对误差下限：单精度 24 位有效二进制位，$\epsilon = 2^{-23} \approx 1.19 \times 10^{-7}$，约合 7 位十进制；双精度 53 位，$\epsilon = 2^{-52} \approx 2.22 \times 10^{-16}$，约合 16 位。它不等同于十进制有效位数，也不保证 $n$ 次累加后还在——误差按累加次数增长。`long double` 的宽度是实现定义：实测 Ubuntu aarch64 给 113 位四精度，macOS arm64 把它当 `double`（53 位）——「用 `long double` 提精度」不能跨平台带。
:::

### 求和顺序：三个数看不出，第四个数才见分晓

拿 `{1e16, 1, -1e16}` 考结合律会挫败直觉：实测 `(a+b)+c` 与 `a+(b+c)` 在两台机器上都得 0。原因是就近取偶——`1e16+1` 恰在两个可表示数中点，偶数端是 `1e16`；`1+(-1e16)` 同理舍成 `-1e16`，两种结合都把那个 1 丢了。再补一个 1：`(a+(b+d))+c` 先算 `1+1=2`，精确；`1e16+2` 本身可表示，实测得 2，而 `((a+b)+d)+c` 仍得 0。结论：小数能不能活下来，看它先有没有聚齐超过半个 ulp——求和顺序是语义问题，不是风格问题。大量累加按数量级升序加或用 Kahan 补偿求和；并行归约与串行结果逐位不同是浮点语义，不是 bug。

::: ex 例 1.2.8 · 先猜三个和 {#ex-1.2.8}
不运行程序：`((1e16+1)+1)-1e16` 与 `(1e16+(1+1))-1e16` 各是多少？`(0.1+0.2)+0.3` 与 `0.1+(0.2+0.3)` 相等吗？

::: sol 解答
实测两机：前者 0、后者 2；`0.1+0.2+0.3` 按左结合打印 `0.60000000000000009`，改括号打印 `0.59999999999999998`，两个 `==` 判定为假——全在实测输出里。差别都来自「舍入发生在哪一步」：`(a+b)+c` 每一步单独被吸收，`b+d` 先凑出能活下来的 2；0.2 与 0.3 的近似相加恰好凑出精确的 0.5，先加它就走另一条舍入路径。
:::
:::

### 比较：`==`、绝对容差、相对容差各用在哪

实测三行先定调：`NAN==NAN` 为假——NaN 参与的比较全为假，判 NaN 用 `isnan`，判「数值可用」用 `isfinite`；`-0.0==0.0` 为真——相等与同号是两件事，要区分符号用 `signbit`（实测 `1.0/-0.0` 得 `-inf`）。绝对容差 `fabs(a-b) < 1e-9` 会在两头同时翻车：实测 `1e-30` 与 `2e-30` 相差被判「相等」（相对差 100%），`1e9` 与 `1e9+1` 的同一判定为假（相对差十亿分之一）。普适写法是相对容差 $|a-b| \le \epsilon \cdot \max(|a|,|b|)$；金额别用浮点，用整数「分」或十进制库。

::: method 判定流程 · 比较两个浮点数
1. NaN 排除了吗？可能来自除法或外部输入就先 `isnan`/`isfinite`——NaN 让 `==`、`<`、`>` 全假。
2. 要求逐位可复现（缓存键、序列化回来核对）？容差不是答案；让两边出自同一条运算路径，或干脆比较位模式。
3. 业务自带精度（「保留两位小数」）？按业务精度处理后再比较。
4. 一般数值比较：相对容差，对接近 0 的用 `fmax` 兜底；别拿一个绝对 eps 套所有数量级。
:::

::: think 思考 · 容差是不是越大越保险
把 eps 放大等于放弃比较：真正的精度损失往往发生在上游——输入转换、累加顺序、`float` 混进 `double`。先用 `%.20g` 看清两边的真实值，再决定判据；容差治不了已经丢掉的位。
:::

### 1.2.8 小结

① 默认舍入就近取偶，`rint(0.5)` 得 0、`1e16+1` 被吸收都是实测；② 加法不满足结合律：三元素看不出差别，第四个数把 0 变 2，同样是实测；③ 比较先处理 NaN 与 ±0，绝对容差两头翻车，通用判据是相对容差，金额用整数分。如果只记住一件事，那就是：**浮点「相等」是两次落在同一个可表示数，不是数学上的相等。** 舍入模式全表、ULP 公式与 FMA 双重舍入在 [1.2.10](#sec-1.2.10)。

::: errata 常见错误清单（1.2.8 节）
1. **「浮点运算不确定」**——两台 IEEE 754 机器逐位相同（本节全部输出可证）；真正改变最低位的是 FMA 收缩、`-ffast-math` 和 `long double` 宽度差异。
2. **「`0.1f == 0.1` 为真」**——`0.1f` 提升后是 0.10000000149011611938，`double` 的 0.1 是 0.10000000000000000555（均实测 `%.20g`），不等。
3. **「用容差总安全」**——绝对容差实测两头同时翻车；对逐位复现场景，容差掩盖真实差异。
4. **「`float` 累加只是差一点」**——1 在 1e16 旁边完全消失（实测）；误差随累加次数与顺序增长。
:::

## 1.2.9 手算速查：进制、补码、移位与溢出 {#sec-1.2.9}

这一节回答：手边没有计算器、也不想开 Python 时，怎样在三十秒内把一条位运算表达式算对，并且知道每条规则的边界压在哪。

[1.2.1](#sec-1.2.1)–[1.2.5](#sec-1.2.5) 每讲一条规则都在两台机器上跑过一次：`0xFB` 的两种读法、`num > size` 的错答案、`-7>>1` 与 `-7/2` 差的那 1，都留在那里。这一遍不复述那些实测表，只做两件事：把结论压成五张能查的表，把每条规则的越界后果分清楚——定义良好、实现定义、未定义行为，三档不能混。

::: preview 先抓住一件事
手算只有一个动作：**先在位上算，再选解释**。宽度一定，加减移位全在模 $2^w$ 的圆环上做，做完才问「按无符号读还是按补码读」。表一给圆环的边界常数，表二把 4 位圆环整个铺开，表三管移位和除法，表四管「越界了没有、谁告诉你越界的」，表五管换读法时位怎么动。
:::

### 场景：同一行 UB 代码，两个编译器给出两对答案

`x << 33`（移位量出界，1.2.5 已定性为 UB）在两台机器上都被 `-Wall` 点名，但跑出来的数完全不同。先跑（`lab1c02_warn.c`，`cc -std=c17 -Wall -Wextra -O2`）：

```c
unsigned a = 1u;
printf("%u %u\n", a << 33, 1u >> 32);
```

警告原话（两机实测 stderr）：

```text
clang： warning: shift count >= width of type [-Wshift-count-overflow]
gcc：   warning: left shift count >= width of type [-Wshift-count-overflow]
```

程序输出（两机不同，各为实测）：

```text
macOS Apple clang 21：159793536 159793368
Ubuntu gcc 13.3：     0 0
```

`0 0` 已经是「按硬件掩码解释不了」的形状，clang 那一对数更没法说：既不是 0，也不是 8，两个值还相差 168。未定义行为不承诺任何可解释的结果——这正是速查表存在的理由：**规则查表，不查我机器上跑出来是什么。**

### 如果你从没手算过补码

只做两个动作。先看最高位：是 0，剩下按无符号读，读出来就是值。是 1，说明这串位想表达的是负数：全部取反、加 1 读出大小，再添负号。拿 `0x9C` 走一遍——最高位 1；取反得 `0x63`；加 1 得 `0x64` = 100，所以原值是 $-100$。验算：`0x9C + 0x64 = 0x100`，丢掉超出 8 位的进位剩全 0，说明两位在圆环上正好互为相反数。这就是 [1.2.2](#sec-1.2.2) 的三步法，不需要背 $B2T_w$ 的展开式。

表里唯一的异常行是 `1000`：取负后仍是 `1000`。$|TMin|=8$ 装不进 4 位的正数区（最大是 7），所以「$TMin$ 的相反数不可表示」；C 里对 `INT_MIN` 取负是 UB，32 位那一版 1.2.2 已经实测过。

这张表也不用背：五行程序就能生成并自检——对每个位模式算 `(~p + 1) & 0xF`，再按「最高位是 1 就减 16」读补码值。两台机器 16 行输出逐字相同，节选头尾四行：

```text
7 u= 7 t=  7 | -x=9 t= -7
8 u= 8 t= -8 | -x=8 t= -8 <= 不对称
9 u= 9 t= -7 | -x=7 t=  7
F u=15 t= -1 | -x=1 t=  1
```

**手算例 1**：`0xFFFFFFF0` 作为 `int` 是多少？做法：全 1 前缀说明是负数，先取负看大小——`~0xFFFFFFF0 + 1 = 0x00000010 = 16`，所以原值是 $-16$。作为 `unsigned` 则是 $2^{32} - 16 = 4294967280$。

::: ex 例 1.2.9 · 四道手算题，先答再对答案 {#ex-1.2.9}
先猜：四道题里哪一道会踩到「负数右移是算术还是逻辑」这个坑？

不查表、不开程序，写出四行：① 8 位补码 `0x9C` 的十进制值；② 4 位圆环上 `0xB + 6` 的位模式，按无符号和按补码各是多少；③ `int x = 0xFFFFFFF0;` 时 `x >> 4` 与 `(unsigned)x >> 4`；④ `unsigned short a = 65535; int b = a;` 里 `b` 是多少，换成 `short a = -1; unsigned b = a;` 又是多少。

::: sol 解答
① $-100$，上面刚走过一遍。② $11+6=17$，模 16 得 1，位模式 `0001`：两种读法都是 1——**圆环上的加法和读法无关**，这正是补码能省掉一套加法器的原因。③ 前者算术右移、高位补符号位 1，得 `0xFFFFFFFF`（也就是 -1）；后者逻辑右移补 0，得 `0x0FFFFFFF`。④ 前者 65535：`unsigned short` 提升成 `int`，`int` 装得下，走零扩展；后者 4294967295：先提升为 `int` 的 -1，再按模 $2^{32}$ 转无符号。②③④ 都跑过，两机逐字相同：`0xB+6(4bit)=1`、`x>>4=FFFFFFFF` 与 `(unsigned)x>>4=0FFFFFFF`、`b=65535 bu=4294967295`。

### 表三：移位与除法的等价关系

| 表达式 | 数学值 | 前提 | 常见误用 |
|:--|:--|:--|:--|
| `x << k`（无符号） | $x \cdot 2^k \bmod 2^w$ | $0 \le k < w$ | $k \ge w$ 是 UB |
| `x << k`（有符号非负） | $x \cdot 2^k$ | 不溢出 | 溢出是 UB，不是回绕 |
| `x >> k`（无符号） | $\lfloor x / 2^k \rfloor$ | $0 \le k < w$ | 对负数不适用（无符号没有负数） |
| `x >> k`（有符号，算术） | $\lfloor x / 2^k \rfloor$ | 实现定义，GCC 为算术右移 | 不等于 C 的 `/` |
| `x / 2^k`（有符号） | 向零截断 | 恒定义：除数是正数，`TMin/2` 也不越界 | 与 `>>` 只在 $x \ge 0$ 时相同；负数常差 1 |

「越界只在除数为 $-1$」这半句要说全。`INT_MIN` 分别除以 2、1、4、$-2$，两机实测（`volatile` 强制真算）依次得 -1073741824、-2147483648、-536870912、1073741824：商全在 `int` 里，没有 UB。唯一装不下的是 $TMin/-1=2^{31}$，那是除数为 $-1$ 的情形，1.2.4 已实测过它的两种形状。

最后一列的「差 1」也不只在 $-7$ 上碰巧出现。把 `x>>2` 和 `x/4` 扫一遍（`lab1c02_div.c`，两机逐字相同）：

```text
x          x>>2  x/4
-9          -3    -2    <= 不等
-8          -2    -2
-7          -2    -1    <= 不等
-5          -2    -1    <= 不等
-1          -1    0     <= 不等
 0           0     0
 5           1     1
 7           1     1
 2147483647  536870911 536870911
```

规律一目了然：非负数上两者相等；负数只要被丢掉的低 $k$ 位里有一位是 1，`>>` 就比 `/` 小 1（`-8`、`0` 这种整除的不差）。算术右移向 $-\infty$ 取整，C 的除法向零截断，两条取整方向在负数上分家——这才是「移位代替除以 $2^k$」必须补偏置的原因。

编译器实测生成的正是这个补法。`int div4(int x){return x/4;}` 在 `-std=c17 -O2` 下，Ubuntu gcc 13.3 给出四条指令；Apple clang 21 顺序不同（`add`、`cmp`、`csel`、`asr`），动作一致：

```asm
div4_signed:
    cmp   w0, 0
    add   w1, w0, #3         /* 偏置 2^k-1 */
    csel  w0, w1, w0, lt     /* 只有 x<0 才用 x+3 */
    asr   w0, w0, 2          /* 算术右移 */
    ret

div4_unsigned:
    lsr   w0, w0, 2          /* 无符号：不需要偏置，直接逻辑右移 */
    ret
```

读法就一句：`csel` 只在 `x<0` 的分支挑 `x+3`，偏置只活在负数一侧——机器码把上面那张扫描表照抄了一遍。x86-64 上同一条优化写作 `leal 3(%rdi)` + `cmovnsl` + `sarl $2`，本机没有 x86 硬件、**未实测**，只给方向对照。

### 表四：溢出判定

| 运算 | 何时溢出 | 硬件标志（x86 / ARM64） | C 里的检测 |
|:--|:--|:--|:--|
| 有符号加 `a+b` | `a`、`b` 同号且结果异号 | `OF` / `V` | `__builtin_add_overflow` |
| 有符号减 `a-b` | `a`、`b` 异号且结果符号与 `a` 不同 | `OF` / `V` | `__builtin_sub_overflow` |
| 有符号乘 `a*b` | 真实积超出 $[TMin,TMax]$ | `OF`（双操作数 `imul`）/ `V` | `__builtin_mul_overflow` |
| 无符号加 `a+b` | 最高位有进位 | `CF` / `C` | 结果 `< a` |
| 无符号乘 `a*b` | 高位非零 | `CF` / `C` | `a != 0 && r / a != b` |
| 除法 `a/b` | `b==0` 或 `a==TMin && b==-1` | x86 `#DE` → `SIGFPE`；ARM64 `sdiv` 静默给回绕值 | 先判 `b`，再判边界 |

无符号的溢出是**定义良好**的回绕，有符号溢出是 UB。表中「C 里的检测」一列之所以全部推荐内建函数，是因为手写判定在类型提升、位宽混用时会悄悄失效；内建函数由编译器按目标位宽生成，且不会触发 UB。

::: def 定义 1.2.9 · 条件码（condition code；x86 的 OF/CF 与 ARM64 的 NZCV） {#def-1.2.9}
算术指令除了写回结果，还留下几位「刚才发生了什么」的状态，合称条件码。ARM64 把它们放在 NZCV 四个标志位里：N 记结果是否为负、Z 记是否为零、C 记无符号是否进了位（减法里方向相反，C=1 表示没借位）、V 记有符号是否溢出。x86-64 的对应物是 `OF`（有符号溢出）与 `CF`（无符号进/借位）。同一次加法、两种读法：判无符号越界看 C/CF，判有符号越界看 V/OF。
:::

「两种读法共用一套条件码」可以直接取证：一行内联汇编做 `adds`/`subs`，再把 NZCV 读回来（`lab1c02_flag.c`，两机输出逐字相同）：

```text
add INT_MAX+1   r=-2147483648  N=1 Z=0 C=0 V=1
add -1+1        r=0            N=0 Z=1 C=1 V=0
add 100+200     r=300          N=0 Z=0 C=0 V=0
add (u)-1+2     r=1            N=0 Z=0 C=1 V=0
sub 0-1         r=-1           N=1 Z=0 C=0 V=0
sub TMin-1      r=2147483647   N=0 Z=0 C=1 V=1
```

四行就够读懂表四。第 1 行只有 V=1：有符号越界，无符号侧 `0x7FFFFFFF+1` 没进位。第 2、4 行只有 C=1：`0xFFFFFFFF+1`、`+2` 都进了位，有符号读法却完全正常。第 5 行 `0-1` 借了位，C=0——**减法里 C 的方向是反的**。第 6 行按无符号够减（C=1）、按补码越界（V=1），一次减法同时给两种读法各留一个答案。x86-64 的 `OF`/`CF` 本机没有硬件，未实测，只保留名称对应。

**手算例 2**：`int a = 0x7FFFFFFF; a + 1` 的机器结果是什么？位模式相加得 `0x80000000`，按补码是 $TMin$，`OF=1`——ARM64 上就是 V=1，上面第 1 行实测的正是它。C 程序里这一行是 UB，`-O2` 下编译器可以假定它不发生；用 `volatile` 或 `__builtin_add_overflow` 才能观察真实机器行为。

同一条假设还能开关。`int gt(int x){ return x + 100 > x; }`（1.2.4 的主角）两机 `-O2` 下对 2147483600 都返回 1；加上 `-fwrapv` 后**两机都返回 0**（实测）。`-fwrapv` 不是修复，是把「溢出等于回绕」重新写回编译器的公理表，代价是丢掉依赖那条公理的优化。

### 表五：有符号与无符号的转换

| 转换 | 规则 | 例子（$w=32$） |
|:--|:--|:--|
| 有符号 → 同宽无符号 | $x<0$ 时 $x+2^w$ | `(unsigned)-1` → 4294967295 |
| 无符号 → 同宽有符号 | $x \ge 2^{w-1}$ 时 $x-2^w$ | `(int)0x80000000u` → -2147483648 |
| 宽 → 窄 | 保留低 $w$ 位，丢弃高位 | `(int8_t)0x1FF` → -1 |
| 窄 → 宽（有符号） | 符号扩展 | `(int)0x8F` 若源自 `int8_t` → -113 |
| 窄 → 宽（无符号） | 零扩展 | `(unsigned)0x8F` → 143 |
| 混合运算 | 有符号转无符号后再算 | `-1 < 0u` → 0 |

**手算例 3**：`unsigned short a = 65535; int b = a;` 的结果？`unsigned short` 先整型提升为 `int`（`int` 能表示 0–65535），所以 `b == 65535`，不发生符号扩展。若写成 `short a = -1; unsigned b = a;`，`a` 提升为 `int` 的 -1，再转 `unsigned` 得 4294967295，而不是 65535。两机实测同一行输出 `b=65535 bu=4294967295`，与例 1.2.9 的第 ④ 题对得上。

::: method 手算位运算题的固定动作
1. 先看最高位定符号；最高位 0 直接按无符号读。
2. 最高位 1 时，取反加一得到绝对值，再添负号。
3. 加减法一律在位上做，丢弃最高位进位；结果按目标类型解释。
4. 比较大小前先问「按有符号还是无符号」，两者用不同条件码（ARM64 是 V 与 C）。
5. 移位前先问「左移会不会溢出、右移的对象是不是负数、移位量够不够 $w$」。
6. 判不出越界时，别看结果猜：查表四的判据，或直接换成 `__builtin_*_overflow`。
:::

::: errata 常见误解（1.2.9 节）
1. **「`x >> k` 就是 `x / 2^k`」**——扫描表里 `-9`、`-7`、`-5`、`-1` 四个值各差 1；编译器为此只在负数分支加偏置（实测四条指令）。
2. **「`INT_MIN / 2` 很危险」**——商 $-2^{30}$ 在范围内，两机实测正常；越界的只有 `TMin / -1`，别把除数是 2 和除数是 $-1$ 混成一档。
3. **「移位量出界我机器上是 0，就能当地图用」**——同一行代码 gcc 给 `0`、clang 给两个说不通的数，两者都带警告。想要「按 32 取模」就自己写 `k &= 31u`（1.2.12 的 `rotl32` 就是这么写的）。
4. **「条件码只有一个，溢出就是溢出」**——同一次 `TMin-1` 里 C=1（无符号够减）而 V=1（有符号越界），各说一种读法；减法里 C=1 的意思还是「没借位」。
:::

### 1.2.9 小结

① 手算只有一个动作：先在位上算，再选解释；表一给边界常数，表二到表五给动作。② 这一遍新钉的边界都跑了两机：移位与除法差 1（扫描表 + 负数分支的偏置代码）、除法越界只在 `TMin/-1`、`-fwrapv` 能把 `gt` 从 1 改回 0、NZCV 同时记着两种读法；x86-64 的 `OF`/`CF` 与 `leal` 序列本机无硬件，未实测。③ 三档牌照不能混：同一行 `a<<33` 在两机上给出两个不同答案，就是最直白的提醒。如果只记住一件事，那就是：**越界的后果查表，不查你这台机器今天恰好跑成什么。**

## 1.2.10 IEEE 754 逐字段：非规格化、舍入与 ULP {#sec-1.2.10}

这一节回答：浮点三个字段逐位摊开是什么；「阶码全 0」那一档到底装住了哪些数；一次舍入的误差上限怎么量；浮点的位模式为什么不能直接拿来排序。

[1.2.7](#sec-1.2.7) 已经把三段公式、特殊值和「0.1 存不准」跑过一遍，[1.2.8](#sec-1.2.8) 实测过吸收、求和顺序和默认舍入下的 `rint`。这一遍不复述那些现场，只看规则和边界：把 `float` 的七个关键位模式实测出来，用 `nextafter` 量 ULP，真的切换四种舍入模式，再把 FMA 在两台机器上的默认行为测清楚。

::: preview 先抓住一件事
「阶码字段全 0」不是「指数最小」，而是「放弃隐含 1」。这一段叫非规格化数（subnormal，写不成规格化形式的极小数），它把 0 到最小规格化数之间填成一格一格等宽的台阶，每格 $2^{-149}$。相邻两个可表示数之间的那一格就叫一个 ULP（unit in the last place，最后一位的一个单位）——它是「差几个可表示数」的尺子，舍入误差、FMA 的差别、`nextafter` 全都按它说话。
:::

### 场景：七个位模式，一次跑完

`float` 的边界都压在阶码字段的 0 和 255 上。把七个位模式按字节灌进 `float`，再用 `%.20g` 打印存储值（`lab1c02_fp.c`，`cc -std=c17 -O2 -lm`；两台机器输出逐字相同）：

```text
00000000 exp=  0 frac=000000  0
00000001 exp=  0 frac=000001  1.4012984643248170709e-45
007FFFFF exp=  0 frac=7FFFFF  1.1754942106924410755e-38
00800000 exp=  1 frac=000000  1.175494350822287508e-38
7F7FFFFF exp=254 frac=7FFFFF  3.4028234663852885981e+38
7F800000 exp=255 frac=000000  inf
7FC00000 exp=255 frac=400000  nan
```

三行读法。`007FFFFF` 与 `00800000` 位模式只差 1，值只差 $1.4\times10^{-45}$，没有跳变；`exp` 从 0 变 1 的那一刻，隐含的前导 1 才出现；最后两行是阶码全 1 的两支——尾数全 0 记无穷，尾数非 0 记 NaN。下面把这些边界和它们的算术推导对上号。

### 字段与取值

| 字段 | `float` 位区间 | `double` 位区间 | 作用 |
|:--|:--|:--|:--|
| `s`（符号） | bit 31 | bit 63 | 0 为正，1 为负（含 `-0.0`） |
| `exp`（阶码） | bit 30–23（8 位） | bit 62–52（11 位） | 偏置指数，bias 127 / 1023 |
| `frac`（尾数） | bit 22–0（23 位） | bit 51–0（52 位） | 规格化数省略前导 1 |
| bias | 127 | 1023 | $E = exp - bias$ |

三种编码的完整取值规则（$s$ 为符号位，$f$ 为 `frac` 解释出的小数）：

$$
v = \begin{cases}
(-1)^s \times 0.f \times 2^{1-bias}, & exp = 0 \quad \text{（非规格化）}\\
(-1)^s \times 1.f \times 2^{exp-bias}, & 0 < exp < \text{全 1} \quad \text{（规格化）}\\
\pm\infty \text{ 或 NaN}, & exp = \text{全 1}
\end{cases}
$$

先回答一个没人问的问题：位里为什么存偏置指数（把真实指数加上 127/1023 再存），而不是直接存补码？因为浮点要比大小。阶码存成非负字段，两个正浮点数比大小就能先比阶码字段、再比尾数字段，全程走无符号整数那条比较电路；真实指数若按补码存，每一步都得先看符号位。[1.2.7](#sec-1.2.7) 实测过 `0.0 < 0.5 < 1.0` 对应 `00000000 < 3F000000 < 3F800000`，正是这条设计的结果；负数一侧单调性被符号位破坏，补救见下面的全序键。

非规格化数的阶码固定为 $1-bias$，不是 $0-bias$。这个「1」是 IEEE 754 的设计技巧：让最大的非规格化数与最小的规格化数无缝衔接。以 `float` 为例：

| 位模式 | 含义 | 十进制近似 |
|:--|:--|--:|
| `0x00000000` | `+0.0` | 0 |
| `0x00000001` | 最小正非规格化数 $2^{-149}$ | $1.40129846 \times 10^{-45}$ |
| `0x007FFFFF` | 最大非规格化数 $(1-2^{-23}) \times 2^{-126}$ | $1.17549421 \times 10^{-38}$ |
| `0x00800000` | 最小正规格化数 $2^{-126}$ | $1.17549435 \times 10^{-38}$ |
| `0x7F7FFFFF` | 最大有限值 $(2-2^{-23}) \times 2^{127}$ | $3.40282347 \times 10^{38}$ |
| `0x7F800000` | $+\infty$ | — |
| `0x7FC00000` | quiet NaN（默认） | — |

表里第 3、4 行那对相邻就是「逐渐下溢」（gradual underflow，往下越界时一位一位掉，而不是突然跳到 0）。若没有非规格化数，最小规格化数与 0 之间会有一段 $2^{-126}$ 宽的真空，减法结果会被突然冲成 0。

真空不是哲学问题，是算账问题。设 $a$、$b$ 都在 $2^{-130}$ 附近，$a-b$ 的真实结果可能只有 $10^{-40}$，比最小正规格化数还小。有非规格化数，它落进那段等宽的台阶，只是每格的**相对**误差变大；没有它，直接归 0，后面那句除法就从「很准」变成「除零」。这段里 ULP 是常数 $2^{-149}$：没有隐含 1，尾数每加 1 就恰好加 $2^{-149}$（场景实测第 2 行 `0x00000001` 正是这个值）。

::: def 定义 1.2.10 · 非规格化数与最小可表示值（subnormal / true minimum） {#def-1.2.10}
阶码字段全 0 且尾数字段非 0 的编码：$v=(-1)^s\times 0.f\times 2^{1-bias}$，没有隐含 1。`float` 的最小正非规格化数是 $2^{-149}$（位模式 `0x00000001`），最大非规格化数 $(1-2^{-23})\times2^{-126}$，紧挨着最小正规格化数 $2^{-126}$。`double` 同理是 $2^{-1074}$ 与 $2^{-1022}$：实测 `nextafter(0.0,1.0)` 给位模式 `0000000000000001`、值 $4.9406564584124654418\times10^{-324}$。阶码固定取 $1-bias$ 而不是 $0-bias$，就是为了让两段在交界处无缝。
:::

**手算例 4**：`0x3E200000`（0.15625）的逐字段拆法在 [1.2.7](#sec-1.2.7) 已经走过一遍，这次换一个非规格化的位模式练手。

::: ex 例 1.2.10 · 拆一个非规格化位模式 {#ex-1.2.10}
先猜：这个位模式的阶码是全 0 还是全 1？它比最小规格化数大还是小？

`0x00400000` 是哪个数？反过来，$2^{-127}$ 的 `float` 位模式是什么？再问一个：把 `0x00800000` 的位模式减 1，值掉多少？

::: sol 解答
`0x00400000`：阶码字段是 0，走非规格化那条式子；尾数的 bit22 置 1，即 $f=0.1_2=0.5$；值 $0.5\times2^{-126}=2^{-127}$。第二个问题就是它自己——同一个位模式，反推正向。第三问：`0x00800000` 减 1 得 `0x007FFFFF`，从最小正规格化数掉到最大非规格化数，差正好一格 $2^{-149}$，**交界处的间距和段内一样宽**。两机实测：`0x00400000` 打出 `5.8774717541114375398e-39`，与 `pow(2.0,-127.0)` 逐字相同；那两个相邻位模式之差是 `1.4012984643248170709e-45`，即 $2^{-149}$。

### ULP 与机器精度

ULP（unit in the last place）是相邻两个可表示数之间的间距。对规格化数，

$$
\text{ulp}(x) = 2^{\lfloor \log_2 |x| \rfloor - (p-1)},
$$

其中 $p$ 是有效位数（`float` 为 24，`double` 为 53）。所以 `float` 在 $[1,2)$ 内的 ULP 是 $2^{-23}$，在 $[2,4)$ 内是 $2^{-22}$；`double` 在 $[1,2)$ 内是 $2^{-52}$。

| 区间 | `float` ULP | `double` ULP |
|:--|--:|--:|
| $[1,2)$ | $1.1920929 \times 10^{-7}$ | $2.220446 \times 10^{-16}$ |
| $[2,4)$ | $2.3841858 \times 10^{-7}$ | $4.440892 \times 10^{-16}$ |
| $[2^{20},2^{21})$ | $0.125$ | $2.3283064 \times 10^{-10}$ |
| $[2^{23},2^{24})$ | $1$ | $1.8626451 \times 10^{-9}$ |

这张表不用背公式去凑：`nextafter(x, 2x) - x` 直接把每一格的宽度量出来（`lab1c02_fp.c`，两机逐字相同）：

```text
float  [1,2)       ulp=1.192092896e-07
float  [2,4)       ulp=2.384185791e-07
float  [2^20,2^21) ulp=0.125
float  [2^23,2^24) ulp=1
double [1,2)       ulp=2.220446049e-16
double [2^23,2^24) ulp=1.862645149e-09
```

量出来的数和公式逐项对上，说明 ULP 只取决于「阶码那一段多宽」，与尾数具体是多少无关——非规格化段是唯一例外（那里没有隐含 1，整段恒为 $2^{-149}$）。

表里最后两行解释了两个经典现象：`float` 在 $2^{24}$ 之后连「加 1」都表示不了；`float` 在 $2^{23}$ 附近 ULP 已经是 1，所以实测 `(16777216.0f + 1.0f) == 16777216.0f` 为真（两机一致）——1 落在半格以内，被就近舍回了。

### 四种舍入模式

IEEE 754 规定五种舍入方向，C 的 `<fenv.h>` 暴露其中四种：

| `fesetround` 参数 | 规则 | 1.5 的结果 | -1.5 的结果 |
|:--|:--|--:|--:|
| `FE_TONEAREST`（默认） | 就近，平局取偶 | 2 | -2 |
| `FE_DOWNWARD` | 向 $-\infty$ | 1 | -2 |
| `FE_UPWARD` | 向 $+\infty$ | 2 | -1 |
| `FE_TOWARDZERO` | 向 0 | 1 | -1 |

这张表可以直接跑出来：`fesetround` 切换模式，`nearbyint` 按当前模式取整（`lab1c02_round.c`，四行平局点，两机输出逐字相同）：

```text
FE_TONEAREST : 0.5->0 1.5->2 2.5->2 -2.5->-2
FE_DOWNWARD  : 0.5->0 1.5->1 2.5->2 -2.5->-3
FE_UPWARD    : 0.5->1 1.5->2 2.5->3 -2.5->-2
FE_TOWARDZERO: 0.5->0 1.5->1 2.5->2 -2.5->-2
```

同一组平局点给出四种答案；`FE_TONEAREST` 行的 0.5→0、2.5→2、-2.5→-2 就是「平局取偶」。对照 [1.2.8](#sec-1.2.8) 的实测：`lround(2.5)` 仍给 3——它按 C 自己的规则取整，不看这个开关。

还有一个坑也跑出来了：把上面那四个待舍入的值写成普通数组常量（去掉 `volatile`），四行输出全部塌回 `FE_TONEAREST` 那一行——编译器在编译期就把 `nearbyint` 折成了常量，而它只认默认模式，`fesetround` 是运行期的事。想让编译器尊重运行期环境需要 `#pragma STDC FENV_ACCESS ON`，两家编译器对它的支持都不完整（本机未实测）。工程结论更简单：**别在优化过的代码里依赖运行期切换的舍入模式。**

默认的「就近取偶」（round-to-nearest, ties-to-even）在手算时的动作是：找到相邻的两个可表示数，取更近的；正好在中点时，看哪一个的尾数最低位是 0。用 3 位有效位表示 $2.5 = 10.1_2$：候选是 $10.0_2=2$ 与 $11.0_2=3$，中点取偶得 $10.0_2=2$。$3.5=11.1_2$ 的候选是 $11.0_2=3$ 与 $100.0_2=4$，取偶得 $100.0_2=4$。

「取偶」为什么不是审美偏好，[1.2.8](#sec-1.2.8) 已经说过一句话：平局在两侧均匀分布，长期累加才不会系统性偏向一个方向。这里补上它的量化版本——误差本身有硬上界。

一次舍入的相对误差有硬上界：在规格化范围内，

$$
\left| \frac{\text{fl}(x) - x}{x} \right| \le \frac{\epsilon}{2}, \qquad \epsilon = 2^{-(p-1)} .
$$

`float` 的 $\epsilon = 2^{-23} \approx 1.19 \times 10^{-7}$，所以「约 7 位十进制有效数字」；`double` 是 $2^{-52} \approx 2.22 \times 10^{-16}$，约 16 位。这是**单次**运算的界，$n$ 次累加的最坏误差会按 $n\epsilon$ 增长（向前误差分析），不是 $n$ 次都保持 $\epsilon/2$。

::: intuition 为什么浮点加法不满足结合律
这一段是纸面推导，不是实测（同型现象的实测在 [1.2.8](#sec-1.2.8)：三个数看不出、第四个数把 0 变成 2）。$(a+b)+c$ 与 $a+(b+c)$ 各自发生两次舍入，舍入点不同。取 $a=1.0$、$b=2^{-24}$、$c=2^{-24}$（`float`）：$a+b$ 恰好落在 $1.0$ 与 $1+2^{-23}$ 的中点，平局取偶舍回 $1.0$，再加 $c$ 仍是 $1.0$；而 $b+c=2^{-23}$，加到 $a$ 上得 $1+2^{-23}$。差别不在数学，在「哪一步被舍掉」。并行归约改变求和顺序，因此结果可能与串行版本逐位不同——这不是 bug，是浮点语义。
:::

### 浮点数的全序：位模式排序技巧

把浮点位模式当无符号整数比：符号位为 0 的那一半随数值单调递增，符号位为 1 的那一半反过来——字段越大，值越小。所以「直接比位模式」在跨过 0 的那一刻就错：`-0.0` 的位模式 `0x8000…` 远大于 `+0.0` 的 `0x0000…`，而 IEEE 754 的 `==` 又判它们相等。要让无符号比较等价于浮点比较，做一次符号折叠：

```c
#include <stdint.h>
#include <string.h>

/* 把 double 的位模式映射成单调的无符号键：键序 == 浮点序（NaN 除外） */
static uint64_t fkey(double d)
{
    uint64_t u;
    memcpy(&u, &d, sizeof u);
    return u ^ ((u >> 63) ? UINT64_MAX : 0x8000000000000000ULL);
}
```

键值实测（`lab1c02_fp.c`，两机逐字相同）：

```text
-inf      bits=FFF0000000000000 key=000FFFFFFFFFFFFF
-1        bits=BFF0000000000000 key=400FFFFFFFFFFFFF
-0        bits=8000000000000000 key=7FFFFFFFFFFFFFFF
0         bits=0000000000000000 key=8000000000000000
1         bits=3FF0000000000000 key=BFF0000000000000
inf       bits=7FF0000000000000 key=FFF0000000000000
```

键严格递增，顺序与浮点值一致；把键当 `uint64_t` 排序就得到浮点升序，还不用为 `-0.0` 与 `+0.0` 写比较分支——折叠后它们是两个相邻的键，而 `==` 仍判相等。`NaN` 不参与全序，排序前要单独剔除。

### 融合乘加与双重舍入

FMA（fused multiply-add，融合乘加：一条指令算完 $a\times b+c$，只在最后舍入一次）与「先乘后加」的结果可能差一个 ULP。下面这组数是纸面推导的确定性算术，不是实测：

```text
a = 1 + 2^-23, b = 1 - 2^-23, c = -1      （float）
a*b 精确值 = 1 - 2^-46
先乘后加：fl(a*b) = 1.0，再加 -1 得 0
FMA：      fl(1 - 2^-46 - 1) = -2^-46（可表示）
```

会不会真的收缩，取决于编译器和选项，这一半是实测。`a*b+c` 写成独立函数、`-std=c17 -O2` 编译（`lab1c02_fma2.c`）：

```text
Ubuntu gcc 13.3  默认                ：fmul + fadd，结果 0
Ubuntu gcc 13.3  -ffp-contract=fast  ：fmadd，结果 -1.4210854715202003717e-14
macOS clang 21   默认                ：fmadd，结果 -1.4210854715202003717e-14
macOS clang 21   -ffp-contract=off   ：fmul + fadd，结果 0
```

同一行源码，两台机器的默认值相反：Apple clang 在 `-std=c17` 下就收缩；gcc 13.3 在标准兼容模式下不收缩，要显式 `-ffp-contract=fast`（`-Ofast` 也会把它打开，实测同样给 fmadd）。更老的编译器各模式默认值如何，本机只有这两个版本，**未实测**，不当结论用。工程口径只有一条：要逐位可复现就显式钉 `-ffp-contract=off`，或加 `#pragma STDC FP_CONTRACT OFF`（支持度因编译器而异）；想确定地用 FMA 就调 `fmaf()`，两机实测都给出 $-2^{-46}$。

另一个方向是双重舍入：x87 的 80 位寄存器把 `double` 运算结果先舍入到 64 位有效位，再存回 53 位，可能得到与 SSE 直接舍入不同的最低位。x86-64 的 `double` 运算默认走 SSE2，不受影响；但 `long double` 在 x86-64 Linux 上就是 80 位 x87 格式，跨平台时要注意它与 `double` 的差别。AArch64 上没有 x87，本机两台的 `long double` 宽度本就不同（[1.2.8](#sec-1.2.8) 实测：macOS 8 字节 / 53 位有效，Ubuntu 16 字节 / 113 位），x87 那条双重舍入路径在这里无从复现，未实测。

::: errata 关于 IEEE 754 的五个精确说法
1. **「非规格化数的阶码是 0」**——字段值是 0，但有效阶码是 $1-bias$；公式里写成 $2^{-126}$ 才对。
2. **「`float` 能精确表示所有 7 位十进制数」**——只能保证 6–7 位**相对**精度；`0.1f` 本身就不精确，`16777217` 也存不下。
3. **「`x == x` 对 NaN 为真」**——IEEE 754 规定 NaN 与任何值（含自身）的无序比较都为假，所以 `x != x` 是判断 NaN 的经典写法（更清楚的是 `isnan`）。
4. **「`-0.0 == 0.0` 为假」**——比较为真；但 `1.0/(-0.0)` 是 $-\infty$，`signbit(-0.0)` 为真。相等与同号是两件事。
5. **「舍入误差总是随机正负抵消」**——只有在平局取偶、输入分布对称时才近似成立；固定模式的累加（如 `+= 0.1`）会产生可预测的漂移。
:::

### 1.2.10 小结

① 阶码字段的两条边界各定义一段：全 0 放弃隐含 1（非规格化段，整段 ULP 恒为 $2^{-149}$），全 1 交给无穷和 NaN。② ULP 与误差上限是量出来的：`nextafter` 在四个区间给的宽度和公式逐项对上，$2^{23}$ 附近「加 1」直接被舍回。③ 四种舍入模式真切换过（编译期折叠会让开关失效），FMA 收不收缩两机默认相反（实测四组），所以「逐位可复现」必须显式钉选项。如果只记住一件事，那就是：**浮点的误差不是噪声，是一个能用 ULP 数出来的量。** 三段公式与特殊值的现场在 [1.2.7](#sec-1.2.7)，吸收与求和顺序的实测在 [1.2.8](#sec-1.2.8)。

**Q2（辨析）** 「`float` 的 ULP 是 $1.19\times10^{-7}$」这句话错在哪？`1e16` 处的 ULP 又是多少？

**A4** 一：两边都显式加 `-ffp-contract=off`（clang 默认收缩，实测必须显式关掉），代价是丢掉 FMA 的速度与一次舍入的精度；二：把乘加写成 `fmaf(a,b,c)`，两边都走同一条收缩路径，代价是换不了不支持 FMA 的目标机时要退回到 `#pragma STDC FP_CONTRACT OFF` + 手写两步。两种都比「不管」好，因为默认值本来就不一致。

## 1.2.11 字节序、对齐与结构体布局的完整规则 {#sec-1.2.11}

这一节回答：对齐值到底从哪来、填充能插在哪、联合体与位域怎么算大小、`packed` 改了什么，以及同一份源码跨平台时到底哪一行会变。

[1.2.6](#sec-1.2.6) 已经在现场看过三件事：小端机器上 `htonl` 真的翻转字节、A/B/C 三个结构体的 `sizeof` 是 12/24/16、packed 成员落在奇地址上读也没崩。这一遍不复述那张表，只补规则本身——对齐值、四条布局规则、位域与柔性数组、改布局的工具——并把两台机器的差异跑出来：确实有一行会变。

::: preview 先抓住一件事
结构体布局不是「字段长度之和」。每个成员的偏移必须是**它自己对齐值**的整数倍，结构体的大小必须是**最大对齐值**的整数倍，凑不齐的位置都由填充补上。四条规则在手，任何结构体都能在纸上算出 `sizeof` 和每个 `offsetof`；唯一的平台变量是类型自身的对齐值，而本机两台机器恰好在 `long double` 上给了不同答案。
:::

### 场景：你算的偏移，比编译器少了 3 字节

第一次读别人的结构体，多数人默认「偏移 = 前面字段长度之和」：`char c; int i;` 里 `i` 该在 1。把 `offsetof` 打出来就死心了（`lab1c02_layout.c`，`cc -std=c17 -Wall -Wextra -Werror -O2`，两机逐字相同）：

```text
struct S1 size=12 align=4  struct S1.c=0  struct S1.i=4  struct S1.d=8
```

`i` 在 4，不是 1；`d` 在 8；整个结构体 12 字节，而三个成员加起来只有 6。中间那 6 个字节不属于任何字段，它们只为两件事存在：让 `i` 自己落在 4 的倍数上，让 `S1` 组成数组时下一个元素也落在 4 的倍数上。

### 对齐值表（LP64；本机两台的实测值）

| 类型 | `sizeof` | 对齐值 | 备注 |
|:--|--:|--:|:--|
| `char` / `signed char` / `unsigned char` | 1 | 1 | 任何地址都合法 |
| `short` | 2 | 2 | 偏移必须是偶数 |
| `int` / `unsigned` | 4 | 4 | |
| `long` / `unsigned long` / 指针 | 8 | 8 | LP64 |
| `long long` | 8 | 8 | |
| `float` | 4 | 4 | |
| `double` | 8 | 8 | |
| `long double` | 16 | 16 | **仅 Ubuntu aarch64 实测**；macOS arm64 是 8 / 8 |
| `_Bool` | 1 | 1 | |
| 数组 | $n \times$ 元素大小 | 元素对齐 | 元素之间无填充 |
| 结构体 | 见规则 | 成员最大对齐值 | |
| 联合体 | 最大成员大小（向上取整） | 成员最大对齐值 | |

除 `long double` 那一行，表里每个数都在两台机器上实测过且相同（Apple clang 21 / Ubuntu gcc 13.3，同为 aarch64 LP64）。实测差异只有 `long double`：Ubuntu 给 128 位四精度（`sizeof` 16、`_Alignof` 16），macOS 把它当 `double`（8/8），同一个结构体因此两边大小不同，实测见下面的 `S6`。x86-64 System V 除同一行外基本相同，但本机没有 x86 硬件，那部分**未实测**。

### 四条布局规则

1. **成员偏移**：每个成员的偏移必须是**自身对齐值**的整数倍，不足则在它前面插填充。
2. **结构体对齐**：结构体的对齐值等于所有成员对齐值的最大值（含嵌套结构体）。
3. **结构体大小**：`sizeof` 必须是结构体对齐值的整数倍，不足则在**尾部**补填充。这样数组中每个元素都对齐。
4. **嵌套**：内层结构体先按自己的规则算完大小与对齐，再作为一个整体参与外层布局。

::: def 定义 1.2.11 · 对齐值与填充（alignment requirement & padding） {#def-1.2.11}
每个类型自带一个对齐值（`_Alignof(T)` 给出，单位是字节）：这种对象的地址必须是它的整数倍。编译器为满足这条要求，在成员前面插入的无名字节叫填充（padding）。结构体的对齐值等于所有成员对齐值的最大值（嵌套结构体也算一个成员，取它自己的对齐值），`sizeof` 再向上取整到这个最大值的倍数。把对象塞进 `char` 数组并不能取消对齐要求——`char` 的对齐是 1，被包住的成员仍要求自己的地址是 4 或 8 的倍数。
:::

按这四步手算，再用程序验一遍（`lab1c02_layout.c`；下表除 `S6` 外两机逐字相同）：

| 结构体 | 成员偏移 | 内部填充 | 尾部填充 | `sizeof` |
|:--|:--|--:|--:|--:|
| `struct S1 { char c; int i; char d; }` | 0, 4, 8 | 3 | 3 | 12 |
| `struct S2 { char c; double d; char e; }` | 0, 8, 16 | 7 | 7 | 24 |
| `struct S3 { double d; char c; char e; }` | 0, 8, 9 | 0 | 6 | 16 |
| `struct S4 { char a; short b; int c; long d; }` | 0, 2, 4, 8 | 1 | 0 | 16 |
| `struct S5 { char a[3]; short b; char c; }` | 0, 4, 6 | 1 | 1 | 8 |
| `struct S6 { char c; long double ld; }` | 0, 16 / 0, 8 | 15 / 7 | 0 | **32（Ubuntu）/ 16（macOS）** |
| `union U1 { char c[9]; int i; }` | 0, 0 | 0 | 3 | 12 |

```text
struct S2 size=24 align=8  c=0  d=8   e=16
struct S3 size=16 align=8  d=0  c=8   e=9
struct S6 size=32 align=16 c=0  ld=16    <-- Ubuntu gcc 13.3
struct S6 size=16 align=8  c=0  ld=8      <-- macOS clang 21
```

`S6` 那两行是本节唯一的实测跨机差异，来源就是 `long double` 的对齐值：16 的机器上 `c` 后面补 15 字节，8 的机器上只补 7。把结构体大小写进文件格式或共享内存布局时，这一行就是分水岭。

`S2` 与 `S3` 的成员完全相同，只是顺序不同，大小差 8 字节。把最大的成员放前面通常最省空间，但规则不是「降序排列」这么简单：`S4` 按 1/2/4/8 升序排列反而没有内部填充，因为它正好是自然对齐的顺序。真正的判据是「每个成员的偏移是否已经对齐」。

::: ex 例 1.2.11 · 手算一个嵌套结构体 {#ex-1.2.11}
先猜：按 `alignof` 逐层算，这个结构体的 `sizeof` 会比字段长度之和大多少？

```c
struct inode_key {
    char  dev;          /* 0, 对齐 1 */
    struct {            /* 对齐 4，偏移必须是 4 的倍数 */
        int  ino;       /* 4 */
        int  gen;       /* 8 */
    } id;               /* 大小 8，对齐 4 */
    short mode;         /* 12，对齐 2 */
    char  name[5];      /* 14，对齐 1，占 14..18 */
};                      /* 最大对齐 4，大小向上取整到 20 */
```
`id` 从偏移 4 开始（0 后面补 3 字节），`mode` 在 12，`name` 在 14，成员合计 19，向上取整到 20。若把 `name[5]` 换成 `name[6]`，成员合计涨到 20，`sizeof` 仍是 20——尾部填充从 1 变成 0。**加一个字节可能不改变大小**，这是容量规划时最容易算错的地方。实测（`struct nested`，两机逐字相同）：`size=20 align=4  dev=0  id=4  mode=12  name=14`，四步规则一条都对得上。
:::

### 联合体、位域与柔性数组

联合体（`union`）的所有成员共享起始地址，大小是最大成员的大小按最大对齐值向上取整。`U1` 中 `char[9]` 占 9 字节，`int` 要求 4 对齐，所以大小是 12。联合体常用于「同一块内存的多种解释」：协议解析、变体类型（tagged union）、浮点位操作。

位域（bitfield，把整数字段按位切开声明的成员写法）的布局由实现定义。本机的两个编译器——Apple clang 21 与 Ubuntu gcc 13.3，都是 aarch64——都按「从低位到高位、尽量塞进同一个存储单元」分配：

```c
struct flags {
    unsigned a : 3;    /* bit 0–2 */
    unsigned b : 5;    /* bit 3–7 */
    unsigned c : 8;    /* bit 8–15 */
    unsigned d : 16;   /* bit 16–31 */
};                     /* sizeof = 4，对齐 4 */
```

`a=5, b=17, c=0xAB, d=0xBEEF` 打包成 `0xBEEFAB8D`。两机实测逐字相同，把结构体按字节摊开看得最清楚：

```text
struct flags size=4 align=4
flags 打包=0xBEEFAB8D 字节: 8d ab ef be
```

`8d ab ef be` 正是 `0xBEEFAB8D` 在小端机器上的存放顺序（[1.2.3](#sec-1.2.3) 的 `show_bytes` 第一次看过这条规则）。装不下就换单元：`unsigned a : 20; unsigned b : 14;` 在两机上都得到 `sizeof` 8——第一个 4 字节单元只剩 12 位，塞不进 14 位，`b` 从第二个单元的低 14 位起，实测字节是 `ff ff 0f 00 ff 3f 00 00`。

两条限制记牢：跨编译器时不要依赖位域顺序，网络协议和文件格式要用手写的移位与掩码（[1.2.12](#sec-1.2.12) 的 `pack`/`unpack` 就是这么做的）；位域成员也不能取偏移或地址，两机实测都直接报错（clang 报 `cannot compute offset of bit-field 'b'`，gcc 报 `attempt to take address of bit-field structure member 'b'`）。位域只适合编译器内部的标志集合。

柔性数组（flexible array member）必须是最后一个成员且不占空间：

```c
struct packet {
    uint16_t len;
    uint8_t  kind;
    uint8_t  data[];   /* 不占 sizeof，按需 malloc(sizeof + n) */
};                     /* sizeof = 4（2 + 1 + 1 尾部填充） */
```

实测（两机逐字相同）：`sizeof=4`、`_Alignof=2`、`len` 在 0、`kind` 在 2、`data` 在 3。分配写 `malloc(sizeof(struct packet) + n)`，`data[0]` 落在偏移 3，末尾那 1 字节凑数的填充不影响使用。柔性数组只解决「变长尾巴」，不改变前面字段的对齐规则。

### 改变布局的工具

| 手段 | 效果 | 代价 |
|:--|:--|:--|
| `__attribute__((packed))` | 取消所有填充 | 成员可能未对齐；原子指令与设备内存路径上可能 fault |
| `#pragma pack(n)` | 把对齐上限压到 n | 同上，且是编译器的方言 |
| `_Alignas(64)` / `alignas` | 提高对齐（如缓存行） | 浪费空间；栈上大对齐可能失败 |
| `__attribute__((aligned(64)))` | 同上（GCC 语法） | 同上 |
| 重排成员 | 减少填充，零运行时代价 | 改变 ABI，需重新编译所有使用者 |

同一份源码、三种手段的实际效果（`lab1c02_pack.c`，两机逐字相同）：

```text
base   size=12 align=4 a=0 b=4 c=8      /* uint8_t/uint32_t/uint16_t 的默认布局 */
pack2  size=8  align=2 a=0 b=2 c=6      /* #pragma pack(2)：对齐上限压到 2 */
packed size=7  align=1 a=0 b=1 c=5      /* packed：填充全消，尺寸等于字段之和 */
sorted size=8  order2 size=8             /* 重排成员：不花一分钱省下 4 字节 */
```

`base` 的 12 字节里有 5 个不属于任何字段；把成员排成 4/2/1（`sorted`）或 1/2/4（`order2`）都只剩 8 字节，两种排法这次收益相同，判据仍是「偏移是否已经对齐」。抬高对齐是另一个方向：实测 `struct { char c; _Alignas(64) int i; }` 得 `size=128 align=64`，`i` 被推到偏移 64——为缓存行隔离付的空间代价很实在。

`packed` 最危险的用法是对成员取地址：

```c
struct __attribute__((packed)) hdr {
    uint8_t  ver;
    uint32_t len;
};
struct hdr h;
uint32_t *p = &h.len;      /* 偏移 1：这是个奇数指针 */
```

两个编译器都对这一行发 `-Waddress-of-packed-member` 警告（实测），`offsetof` 打印出来 `len` 确实在 1。解引用它：本机的普通加载在两台 ARM64 上都**没有** fault（[1.2.6](#sec-1.2.6) 实测），但那是本机形状，不是保证——原子指令、设备内存映射和部分旧核心上是真 fault 路径，而且逐字段访问还可能被拆成两次读。解析外部格式的正确做法是把字节逐字段 `memcpy` 进本地对齐变量，而不是把整块内存强转成 packed 指针。

### 出边界之后：谁规定字节怎么排

对齐管的是本机内存里的排布；对象一出边界，说话的就换成协议文档。实测 `struct sockaddr_in`：两机 `sizeof` 都是 16，`sin_port` 在偏移 2、`sin_addr` 在 4，这两个字段的内容按网络字节序（大端）存放，`htons`/`htonl`/`ntohs`/`ntohl` 是主机序和它之间的唯一通道（用法与实测输出见 [1.2.6](#sec-1.2.6)）。`sin_family` 不属于线上格式，它是本机字段：实测 macOS 上是 1 字节、glibc 上是 2 字节——同一个结构体、同一个总大小，字段宽度却不同，这正是「按 `offsetof` 硬啃别人结构体」会翻车的地方。

坑也不只在网络：跨机器的文件、磁带、共享内存撞的是同一堵墙，所以需要一套公共编码规则。把对象拉平成有规范的字节串叫信号编集（marshalling），历史标准有 XDR（RFC 1014）、ASN.1-BER、CORBA、XML：每种类型定死字节序与位宽，每个数据项再额外带上类型（必要时加长度）。更常见的省事做法是全编码成文本、用换行符分隔——好处是能拿 `nc` 手敲一行协议去调试。两条路的共同点只有一个：**线上格式由文档定义，不由编译器定义**；逐字段序列化 + 定宽类型 + `htonl`/`ntohl`，就是本节所有规则的落点。

::: note 什么时候布局会进入性能路径
结构体数组的每个元素都按对齐值排布，一个 24 字节的结构体在 64 字节缓存行里只能放 2 个（浪费 16 字节）。把「热字段」聚在一起、把冷字段拆到旁路数组（SoA），能显著减少缓存行占用，详见 [1.6](ch06.md)。另外，多线程下两个高频写的变量若落在同一缓存行，会因缓存行争用（false sharing）导致性能骤降；`alignas(64)` 是标准解法。
:::

::: errata 常见误解（1.2.11 节）
1. **「`sizeof` 等于成员大小之和」**——`base` 的 12 字节里有 5 个不属于任何字段（实测）；`S2` 成员合计 10 字节、`sizeof` 24。
2. **「成员按大小降序排一定最省」**——`S4` 按 1/2/4/8 升序排也是零内部填充。判据是「每个成员的偏移是否已对齐」，不是排序方向。
3. **「加了 `packed` 最多是变慢」**——结构体对齐被拉到 1，成员可以落在奇地址；本机普通加载不崩，不等于原子操作（靠单条硬件指令完成的读改写，比如 `<stdatomic.h>` 的原子访问）也不崩，未对齐的原子访问在 ARM64 上是 fault 路径（本机未实测）。
4. **「位域可以当线格式用」**——布局实现定义（本机的两个编译器只是恰好一致），而且不能对位域取偏移/地址：两机实测都直接报错。线格式要手写移位与掩码。
5. **「对齐只影响性能，不影响正确性」**——它决定 ABI。含 `long double` 的结构体在两机上实测 32 与 16 字节，跨机共享内存或落盘时两边读到的字段根本不是同一批字节。
:::

### 1.2.11 小结

① 四条规则管完所有布局：成员偏移对齐自己、结构体对齐取最大值、大小向上取整、嵌套按整体算；七种结构体加一个嵌套例子，实测与手算逐条对上。② 本节唯一的实测跨机差异来自 `long double`（Ubuntu 16/16、macOS 8/8），`S6` 因此是 32 与 16；其余基础类型在两机上完全一致，x86-64 System V 只作对照、未实测。③ `packed`、`#pragma pack(n)`、`_Alignas` 都能量出效果（12→8→7、64 字节隔离），重排成员是免费的；对象一出边界，规则换成协议文档。如果只记住一件事，那就是：**结构体的大小是「对齐之后的结果」，不是字段之和；要跨边界就得逐字段编码。**

## 1.2.12 完整程序一：整型位操作工具箱 {#sec-1.2.12}

这一节回答：怎么把本章的整数规则组装成一组「不靠运气的」函数，并且每个函数的输出都能对着看。

[1.2.4](#sec-1.2.4) 已经给了 `__builtin_*_overflow` 的返回值契约，[1.2.5](#sec-1.2.5) 给了置位、清位、翻转、取位四个惯用法，[1.2.9](#sec-1.2.9) 把越界后果列成了表。这一遍不复述那些现场，只做一件事：把动作组装成九个小函数，两台机器各编译各跑一次，输出贴在下面。

::: preview 先抓住一件事
工具箱里每个函数都同一个取舍：**宁可多写两行掩码，也不把边界交给硬件或编译器**。`rotl32` 先把计数 `&= 31u`，`sign_extend` 只用无符号加减（不碰实现定义的有符号右移），`align_up` 只在 2 的幂上用位技巧。这些函数不依赖「本机跑出什么」，所以可以直接放进真实代码；它们的返回值也都实测过，不是我推测的。
:::

### 场景：这个 bug 在两台上都「不存在」

循环左移最常见的写法是这样的：

```c
static uint32_t rotl_naive(uint32_t x, unsigned k)
{
    return (x << k) | (x >> (32u - k));   /* k == 0 时右移 32 位 */
}
```

`k = 0` 时右移量是 32，出界，属 UB（[1.2.5](#sec-1.2.5)）。实测 `rotl_naive(0x12345678u, 0)`：两台机器都返回 `0x12345678`（`lab1c02_rot.c`，`-O2`），看起来完全正确。这正是最难缠的一类代码——单测全绿，换个编译器或优化级别就换答案。修法不是补测试，是把出界挡在函数内部：先 `k &= 31u`，再对 `k == 0` 直接返回。

### 工具箱源码

整份文件如下，编译命令写在第一行注释里；两台机器都用了 `-Werror`，能干净编过：

```c
/* bits_tool.c — 编译：cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -g bits_tool.c */
#include <stdio.h>
#include <stdint.h>
#include <limits.h>
#include <string.h>

/* 溢出检测：返回 1 表示没溢出；返回 0 时 *out 里是回绕值，按契约调用方不要读它 */
static int checked_add(int a, int b, int *out)
{
    return !__builtin_add_overflow(a, b, out);
}

static int checked_mul(int a, int b, int *out)
{
    return !__builtin_mul_overflow(a, b, out);
}

/* 循环左移：k 先掩到 0..31，再单独处理 k==0，避免 x >> 32 这个 UB */
static uint32_t rotl32(uint32_t x, unsigned k)
{
    k &= 31u;
    if (k == 0)
        return x;
    return (x << k) | (x >> (32u - k));
}

/* 把低 w 位（1..32）按补码符号扩展到 32 位：只用无符号加减，不碰有符号右移 */
static int32_t sign_extend(uint32_t x, unsigned w)
{
    uint32_t m = 1u << (w - 1u);
    x &= (w == 32u) ? UINT32_MAX : ((1u << w) - 1u);
    return (int32_t)((x ^ m) - m);
}

/* 字节序翻转：用掩码+移位，展示 bswap 的等价实现，不依赖任何字节序宏 */
static uint32_t bswap32(uint32_t x)
{
    return ((x & 0x000000FFu) << 24) | ((x & 0x0000FF00u) << 8) |
           ((x & 0x00FF0000u) >> 8)  | ((x & 0xFF000000u) >> 24);
}

/* 向上取整到 a 的倍数，a 必须是 2 的幂：对齐计算的写法（1.2.11 的填充就是它） */
static size_t align_up(size_t n, size_t a)
{
    return (n + a - 1u) & ~(a - 1u);
}

/* 位域打包：a:3 b:5 c:8 d:16，从低位起 */
static uint32_t pack(uint32_t a, uint32_t b, uint32_t c, uint32_t d)
{
    return (a & 0x7u) | ((b & 0x1Fu) << 3) | ((c & 0xFFu) << 8) |
           ((d & 0xFFFFu) << 16);
}

static void unpack(uint32_t v, uint32_t *a, uint32_t *b, uint32_t *c, uint32_t *d)
{
    *a = v & 0x7u;
    *b = (v >> 3) & 0x1Fu;
    *c = (v >> 8) & 0xFFu;
    *d = (v >> 16) & 0xFFFFu;
}

/* 数 1 的个数：不依赖内建函数，清最低位 1 的循环（x & (x-1)） */
static int bitcount(uint32_t x)
{
    int n = 0;
    while (x) { x &= x - 1u; n++; }
    return n;
}

int main(void)
{
    int r = 0;
    printf("checked_add(INT_MAX,1)   ok=%d r=%d\n", checked_add(INT_MAX, 1, &r), r);
    printf("checked_add(100,200)     ok=%d r=%d\n", checked_add(100, 200, &r), r);
    printf("checked_mul(65536,65536) ok=%d\n", checked_mul(65536, 65536, &r));
    printf("checked_mul(100000,100000) ok=%d\n", checked_mul(100000, 100000, &r));

    printf("rotl32(0x80000001,1)=0x%08X rotl32(0x12345678,8)=0x%08X rotl32(0x1,32)=0x%08X\n",
           rotl32(0x80000001u, 1), rotl32(0x12345678u, 8), rotl32(0x1u, 32));

    printf("sign_extend(0x8F,8)=%d sign_extend(0x1FF,8)=%d sign_extend(0x8000,16)=%d "
           "sign_extend(0x80000000,32)=%d\n",
           sign_extend(0x8Fu, 8), sign_extend(0x1FFu, 8), sign_extend(0x8000u, 16),
           sign_extend(0x80000000u, 32));

    printf("bswap32(0x01234567)=0x%08X __builtin_bswap32 同值=%d\n",
           bswap32(0x01234567u), bswap32(0x01234567u) == __builtin_bswap32(0x01234567u));

    printf("align_up(13,8)=%zu align_up(16,8)=%zu align_up(1,64)=%zu\n",
           align_up(13, 8), align_up(16, 8), align_up(1, 64));

    printf("bitcount(0xB0)=%d popcount(0xB0)=%d ctz(0xB0)=%d clz(0x0F)=%d\n",
           bitcount(0xB0u), __builtin_popcount(0xB0u),
           __builtin_ctz(0xB0u), __builtin_clz(0x0Fu));

    uint32_t v = pack(5, 17, 0xAB, 0xBEEF);
    uint32_t a, b, c, d;
    unpack(v, &a, &b, &c, &d);
    printf("packed=0x%08X -> a=%u b=%u c=0x%X d=0x%X\n", v, a, b, c, d);
    return 0;
}
```

### 两台机器的真实输出

两台各自 `-std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -g` 编译，**零警告**通过；运行输出逐字相同（一次贴出，不必分两栏）：

```text
checked_add(INT_MAX,1)   ok=0 r=-2147483648
checked_add(100,200)     ok=1 r=300
checked_mul(65536,65536) ok=0
checked_mul(100000,100000) ok=0
rotl32(0x80000001,1)=0x00000003 rotl32(0x12345678,8)=0x34567812 rotl32(0x1,32)=0x00000001
sign_extend(0x8F,8)=-113 sign_extend(0x1FF,8)=-1 sign_extend(0x8000,16)=-32768 sign_extend(0x80000000,32)=-2147483648
bswap32(0x01234567)=0x67452301 __builtin_bswap32 同值=1
align_up(13,8)=16 align_up(16,8)=16 align_up(1,64)=64
bitcount(0xB0)=3 popcount(0xB0)=3 ctz(0xB0)=4 clz(0x0F)=28
packed=0xBEEFAB8D -> a=5 b=17 c=0xAB d=0xBEEF
```

### 逐行对着输出读

- 第 1 行：`ok=0` 说明 `INT_MAX+1` 的溢出被捕获；`r` 里是回绕值 `INT_MIN`，但契约是「失败就别读它」——这里打印只是为了看一眼形状。
- 第 2 行：`ok=1 r=300` 才是正常路径；两个返回值合起来说明 `checked_*` 的真假含义不是「结果对不对」，而是「能不能用结果」。
- 第 5 行：`rotl32(0x80000001,1)` 把最高位的 1 接回最低位，得 `0x00000003`；`rotl32(0x1,32)` 走 `k &= 31u` 加 `k == 0` 早退，返回原值，全程没有出界移位。
- 第 6 行：`sign_extend(0x1FF,8)` 先截到 `0xFF` 再扩展，得 -1；少了截断那步就是 +511。`sign_extend(0x80000000,32)` 专门走 `w == 32u ? UINT32_MAX : ...` 那个分支——因为 `1u << 32` 本身就是 UB，必须提前绕开。两行合起来才覆盖函数的两个边界。
- 第 7 行：手写 `bswap32` 与 `__builtin_bswap32` 同值（实测 `同值=1`）。反汇编更能说明问题：把这个函数单独编译（非 `static`、`-O2 -S`）实测，两台的编译器都把那一长串 `and/or/shift` 折成一条 AArch64 的 `rev w0, w0`，与内建版本生成的指令完全一样。x86-64 上对应指令叫 `bswap`，本机无 x86 硬件，未实测。
- 第 8 行：`align_up` 就是 [1.2.11](#sec-1.2.11) 四条规则的算式版本——`13→16`、已对齐的 `16` 不动、`1→64`。前提是这个 `a` 必须是 2 的幂。
- 第 9 行：`bitcount` 用「清最低位 1」的循环，与 `__builtin_popcount` 给出同一个 3；`ctz`、`clz` 对 0 未定义（[1.2.5](#sec-1.2.5)），调用前先判非零。
- 第 10 行：`pack` 打出 `0xBEEFAB8D`，和 [1.2.11](#sec-1.2.11) 位域结构体的实测字节 `8d ab ef be` 是同一个数。这两台机器上恰好一致，但那份一致来自实现选择，所以线格式仍要用手写的移位与掩码。

如果你平时只写算术表达式，可能会问：这些不是编译器的事吗？编译器能替你优化乘除，却替不了你猜**接口**。`pack` 里 `c` 只留 8 位，是因为对方文档写着「第 8–15 位是类型」；`sign_extend(0x8000,16)` 存在，是因为某个 ioctl 传回来的是 16 位有符号值，塞进 `int` 之前得自己补符号。这里位不是性能技巧，是别人给你的格式——而格式这种东西，不看文档就没有「一看就懂」的余地。

::: def 定义 1.2.12 · 循环移位（rotate） {#def-1.2.12}
普通移位把移出的位丢掉、另一端补 0；循环移位（rotate，把移出的位从另一端接回来）满足 $|x|$ 的位宽不变：$\mathrm{rotl32}(x,k)=(x\ll k)\mid(x\gg(32-k))$，只在 $0<k<32$ 有定义。C 没有 rotate 运算符，得自己写，而两个端点都是坑：$k=0$ 让 $32-k$ 变成 32，$k\ge 32$ 让两次移位同时出界。本节的做法是先 `k &= 31u`、再对 0 特判；ARM64 有 `ror` 指令、x86 有 `rorx`/`ror`，编译器认得这个模式就会折成一条指令（`rotl64` 实测见下面的自测答案）。
:::

::: ex 例 1.2.12 · 先猜三行，再对实测 {#ex-1.2.12}
把 `sign_extend(0x80000000,32)` 换成 `sign_extend(0x7FFFFFFF,32)`，输出是什么？`align_up(24,16)` 呢？把 `pack` 的第 3 个参数从 `0xAB` 改成 `0x1AB`，读回来的 `c` 是多少？

::: sol 解答
第一个还是 2147483647：$0x7FFFFFFF \oplus 0x80000000 = 0xFFFFFFFF$，减 $2^{31}$ 回到 $0x7FFFFFFF$，最高位本来是 0 就没什么可扩展的。第二个 32（24 向上进到 16 的倍数）。第三个是 `0xAB`：`c` 只有 8 位，`0x1AB & 0xFF = 0xAB`，**超宽的高位在掩码里静默消失，不报错**——这是位打包最常见的数据丢失方式。三条实测（两机相同）：`sign_extend(0x7FFFFFFF,32)=2147483647 align_up(24,16)=32`、`pack(...,0x1AB,...)=0xBEEFAB8D c=0xAB`（打包值与原来一模一样，丢失完全无痕）。
:::
:::

### 换平台时，工具箱会缺什么

连「现成的字节序函数」都不是跨平台契约。glibc 的 `<endian.h>` 提供 `htobe32`/`le32toh` 一族，但实测在 Ubuntu gcc 13.3 上按 `-std=c17` 直接编译会报 `implicit declaration of function 'htobe32'`，加上 `-D_DEFAULT_SOURCE` 才认；macOS 这边根本没有 `<endian.h>`（实测 `fatal error: 'endian.h' file not found`），换成 `<sys/endian.h>`（实测 `htobe32(1)` 给 `0x01000000`）或 `<libkern/OSByteOrder.h>` 的 `OSSwapInt32`。所以工具箱里偏偏是 `bswap32` 这种「笨办法」最稳：不找头文件、不看宏，走到哪都一样。

::: errata 常见误解（1.2.12 节）
1. **「`rotl32(x,0)` 会返回 0」**——朴素写法在 `x >> (32-0)` 上就 UB 了，两台机器实测都「恰好」返回原值；正确实现同样返回原值，区别是它有定义。
2. **「`checked_add` 返回 0 时 `r` 是可靠的回绕值」**——实测它写回 `INT_MIN`，但契约是失败即不读；真要靠回绕做事，回到 [1.2.4](#sec-1.2.4) 的结论：那是实现层形状，不是语言承诺。
3. **「手写掩码版比 `__builtin_bswap32` 慢」**——两机实测折成同一条 `rev` 指令，这里没有性能差别，不值得为此留一份「优化版」代码。
4. **「`pack` 会帮我检查参数越界」**——它只做 `&` 掩码，多余高位静默消失（实测 `0x1AB` 打包成 `0xAB`，输出与合法输入完全相同）。
5. **「`align_up(n, a)` 对任意 `a` 都能用」**——`a` 必须是 2 的幂；否则 `(n + a - 1) & ~(a - 1)` 算的是另一件事，而且悄无声息。
:::

### 1.2.12 小结

① 九个函数、一条编译命令：两台机器在 `-O0` 与 `-O2` 下的输出逐字相同（实测比对一致），`w == 32`、`k == 0`、掩码截断三个边界分支都跑到。② 取舍只有一条：越界的口子在函数内部关掉，不靠硬件掩码、也不靠编译器开恩。③ 与编译器和库的对照同样实测过：手写 `bswap32` 被折成 `rev`，`<endian.h>` 在 glibc 要 `-D_DEFAULT_SOURCE`、在 macOS 干脆没有。如果只记住一件事，那就是：**位操作的「跑出来对」不等于「有定义」，函数里得自己把 0、$w$、超宽三种输入挡掉。** 规则与边界在 [1.2.9](#sec-1.2.9) 的表里，同一种纪律用到浮点上是下一节。

::: method 即时自测 · 1.2.12
**Q1（记忆）** `rotl32` 为什么 `k &= 31u` 和 `k == 0` 早退两个都要写？只留一个会怎样？

**Q2（辨析）** `sign_extend(x, 8)` 与「先 `(uint8_t)x` 再交给 `(int8_t)`」结果一样吗？差别在哪一层？

**Q3（应用）** 按本节纪律给 64 位写 `rotl64`，列出必须处理的三个点，并说出 `rotl64(0x8000000000000001, 1)` 与 `rotl64(1, 64)` 的结果。

::: sol 答案
**A1** 只留 `k &= 31u`：`k` 掩成 0 之后 `32u - k` 仍是 32，右移照样出界；只留 `k == 0` 特判：`k = 33` 这类输入依旧越界。两条挡的是两种输入，缺一不可。
**A2** 数值一样，层次不同。后者依赖「超范围值转有符号窄类型」这条**实现定义**规则（gcc/clang 恰好都截低位）；`sign_extend` 全程只用无符号加减与按位运算，是**定义良好**的。要把边界写进自己的代码、而不是指望所有实现都一样，就是这个区别。
**A3** ① 计数先 `k &= 63u`；② 对 `k == 0` 早退，避开 `64u - k == 64`；③ 字面量一律带 `u`/`ULL` 后缀、类型钉死 `uint64_t`，中间量不留 `int`（否则 `1 << 63` 又是越界）。实测（两机相同）：`rotl64(0x8000000000000001,1)=0x0000000000000003`、`rotl64(0x1,64)=0x0000000000000001`。

## 1.2.13 完整程序二：浮点位模式分析器 {#sec-1.2.13}

这一节回答：日志里出现 `nan`、`-0`、`1e308` 时，怎么确认它的**位模式**而不是靠打印猜测？`float` 的 32 位各是哪一段？

::: preview 先抓住一件事
浮点数的「值」和「位」是两回事：`-0.0 == 0.0` 为真，但它们的位模式不同；`nan != nan` 为真，但它确实是同一个位模式。**判据只有一种：把位打印出来**。

这个程序把任意 `float` 拆成符号、阶码、尾数，判断它属于零、非规格化、规格化、无穷还是 NaN，并测量 ULP、演示四种舍入模式。它解决一个实际问题：日志里出现 `nan` 或 `-0` 时，怎样确认位模式而不是猜。

```c
/* fp_analyze.c — 编译：cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 fp_analyze.c -lm */
#include <stdio.h>
#include <stdint.h>
#include <string.h>
#include <math.h>
#include <fenv.h>
#include <limits.h>

#pragma STDC FENV_ACCESS ON

static uint32_t fbits(float f) { uint32_t u; memcpy(&u, &f, sizeof u); return u; }
static float ffrom(uint32_t u) { float f; memcpy(&f, &u, sizeof f); return f; }

static const char *classify(float f)
{
    uint32_t u = fbits(f);
    unsigned exp = (u >> 23) & 0xFFu;
    unsigned frac = u & 0x7FFFFFu;
    if (exp == 0xFFu)
        return frac ? "NaN" : "Inf";
    if (exp == 0)
        return frac ? "Subnormal" : "Zero";
    return "Normal";
}

static void dump(float f)
{
    uint32_t u = fbits(f);
    unsigned s = u >> 31, e = (u >> 23) & 0xFFu, fr = u & 0x7FFFFFu;
    printf("%-10s bits=%08X s=%u exp=%3u(0x%02X) frac=0x%06X value=%a\n",
           classify(f), u, s, e, e, fr, (double)f);
}

int main(void)
{
    puts("== 分类 ==");
    dump(0.0f); dump(-0.0f); dump(1.0f); dump(0.15625f);
    dump(ffrom(0x00000001u));   /* 最小非规格化 */
    dump(ffrom(0x007FFFFFu));   /* 最大非规格化 */
    dump(ffrom(0x00800000u));   /* 最小规格化 */
    dump(ffrom(0x7F7FFFFFu));   /* 最大有限 */
    dump(ffrom(0x7F800000u));   /* +inf */
    dump(ffrom(0x7FC00000u));   /* quiet NaN */

    puts("\n== ULP ==");
    float one = 1.0f;
    printf("ulp(1.0f)=%a = %.10g\n", nextafterf(one, INFINITY) - one,
           (double)(nextafterf(one, INFINITY) - one));
    printf("ulp(2.0f)=%a\n", nextafterf(2.0f, INFINITY) - 2.0f);
    printf("ulp(0.0f)=%a\n", nextafterf(0.0f, 1.0f));

    puts("\n== 0.1+0.2 ==");
    double a = 0.1, b = 0.2;
    printf("a+b=%.17g  eq 0.3? %d  diff=%.3g\n", a + b, (a + b) == 0.3,
           fabs((a + b) - 0.3));

    puts("\n== 舍入模式（rint 遵循当前模式）==");
    double vals[] = {2.5, 3.5, -1.5};
    int modes[] = {FE_TONEAREST, FE_DOWNWARD, FE_UPWARD, FE_TOWARDZERO};
    const char *names[] = {"TONEAREST", "DOWNWARD", "UPWARD", "TOWARDZERO"};
    for (int m = 0; m < 4; m++) {
        if (fesetround(modes[m]) != 0) { puts("fesetround failed"); return 1; }
        printf("%-11s", names[m]);
        for (int i = 0; i < 3; i++)
            printf(" rint(%.1f)=%+.1f", vals[i], rint(vals[i]));
        putchar('\n');
    }
    fesetround(FE_TONEAREST);

    puts("\n== 精度损失 ==");
    printf("(float)16777217 = %.1f\n", (double)(float)16777217);
    printf("(float)INT_MAX  = %.1f\n", (double)(float)INT_MAX);
    printf("1e16+1 == 1e16 ? %d\n", (1e16 + 1.0) == 1e16);
    printf("nan==nan ? %d, isnan ? %d\n", (int)(NAN == NAN), isnan(NAN));
    return 0;
}
```

Ubuntu 24.04.5（aarch64，GCC 13.3）上的真实输出（`%a` 是 C99 的十六进制浮点格式）：

**编译时踩到一个坑**：这个程序带着 `#pragma STDC FENV_ACCESS ON`，而 GCC 13.3 尚未实现它，`-Wall -Wextra -Werror` 下会直接报 `ignoring '#pragma STDC FENV_ACCESS' [-Werror=unknown-pragmas]` 并中止编译。两种处置：加 `-Wno-unknown-pragmas`（本书实测，输出与上面一致），或改用 clang（它认这个 pragma）。**「代码来自书上、照抄编不过」这类问题，先看编译器版本对标准特性的支持，而不是怀疑代码逻辑。**

`0x1.fffffcp-127` 这一行值得停一下：它等于 $(2-2^{-23}) \times 2^{-127}$，与公式 $(1-2^{-23}) \times 2^{-126}$ 是同一个数，只是规格化写法不同。`ulp(0.0f)=0x1p-149` 说明在 0 附近 ULP 不是 $2^{-23}$，而是最小非规格化数；ULP 是**分段常数**，不是全局常数。

### 1.2.13 小结

位模式分析器的三件事：**分类**（零/非规格化/规格化/无穷/NaN 由 `exp` 与 `frac` 决定）、**ULP**（相邻可表示数的间距，`ulp(1.0f)=2^-23`、`ulp(0.0f)=2^-149`）、**舍入**（`rint` 遵循 `fesetround`，四种模式在 2.5/3.5/-1.5 上各不相同）。如果只记住一件事，那就是**遇到浮点异常先把位打出来**——`%a` 十六进制浮点比 `%f` 有用得多。

::: method 即时自测 · 1.2.13
**Q1（记忆）** `float` 的 32 位怎么分段？`exp` 为 0 与 255 时各代表什么？

**Q2（辨析）** `ulp(1.0f)` 与 `ulp(2.0f)` 差在哪？为什么 `ulp(0.0f)` 反而是最小的非规格化数？

**Q3（应用）** 一个服务打印出 `x=-0.000000`，你要确认它是 `-0.0` 还是很小的负数。写出判据。

::: sol 答案
**A1** 1 位符号 + 8 位阶码（偏置 127）+ 23 位尾数。`exp=0` 表示零或非规格化数（`frac=0` 是零），`exp=255` 表示无穷（`frac=0`）或 NaN（`frac≠0`）。

**A2** `ulp(1.0f)=2^-23`，`ulp(2.0f)=2^-22`——阶码加一，间距翻倍。零附近没有规格化数，最近的数是 `2^-149`，所以 `nextafterf(0,1)` 给出它。

**A3** 打位：`printf("%08X", fbits(x))`，`0x80000000` 就是 `-0.0`；或者 `signbit(x) && x == 0.0f`。不要靠 `printf("%f")` 的符号位判断——它会把 `-1e-9` 也打印成 `-0.000000`。
:::

## 1.2.14 完整程序三：不依赖 libc 的字节序验证（x86-64 汇编） {#sec-1.2.14}

这一节回答：不经过 `printf`、不经过 libc，怎样让 CPU 直接把「它把 `0x01234567` 存成了哪四个字节」交出来？原文给的是 x86-64 汇编；这一版把同一段逻辑用 aarch64 汇编写一遍，在 Ubuntu 24.04 上真跑，再把 x86-64 版本编成目标文件、只读不跑。原因在环境：写作机没有能链接 x86-64 ELF 的链接器，虚拟机也没有用户态 qemu，x86 二进制在这两台机器上都执行不了。

::: preview 先抓住一件事
字节序是**存储约定**，不是指令行为。CPU 把 4 个字节从内存搬到 `write` 的缓冲区时不会做任何转换；`0x01234567` 在 little-endian 机器上就是 `67 45 23 01`。汇编程序只做两件事：把这个常量放进 `.rodata`，用 `write` 系统调用（system call，用户程序请求内核代它写文件的受控入口）原样输出；再求 1 到 10 的和，用 `exit` 交回退出码 55。全程没有 `main`，也没有 libc。
:::

前两个程序都借了 C 库：`printf` 帮你格式化，`memcpy` 帮你取字节。把这两层拿掉，程序只剩三条路——把数据放进某个节、用系统调用把字节写到 fd 1、用系统调用退出。下面的 aarch64 版本是完整可运行的最小例子（`endian_a64.s`）：

```asm
# endian_a64.s — as -o endian_a64.o endian_a64.s && ld -o endian_a64 endian_a64.o
        .section .rodata
val:    .word 0x01234567          # 小端存放为 67 45 23 01

        .text
        .globl _start
_start:
        mov     x0, #1            # fd = stdout
        adrp    x1, val
        add     x1, x1, :lo12:val # buf = &val
        mov     x2, #4            # count = 4
        mov     x8, #64           # __NR_write
        svc     #0

        mov     x1, #10
        mov     x0, #0
1:      add     x0, x0, x1
        subs    x1, x1, #1
        b.ne    1b                # sum = 1 + ... + 10 = 55

        and     x0, x0, #0x7f
        mov     x8, #93           # __NR_exit
        svc     #0
```

逐段读：

- `_start` 是链接器默认入口，没有 C 运行时帮你准备 `argc/argv`，也没有 `main` 的返回路径；退出必须自己发 `exit`（aarch64 是 93，x86-64 是 60）。
- `adrp` 取 `val` 所在页的基地址，`add ... :lo12:` 补上页内偏移。这是 aarch64 的「PC 相对取地址」组合，对应 x86-64 的 `lea val(%rip), %rsi`：两者都让位置无关代码在任何加载地址上都能找到常量。
- `write` 的 aarch64 系统调用号是 64，参数在 `x0/x1/x2`；x86-64 是 1，参数在 `rdi/rsi/rdx`。系统调用号与寄存器约定都是 ABI 的一部分，不是「汇编语言」本身。
- 循环从 10 加到 1，和是 55；`and x0, x0, #0x7f` 把退出码截到 7 位。`exit` 只取低 8 位，shell 再把它显示成 0–255。

Ubuntu 24.04.5（aarch64，binutils 2.42）上的真实会话：

```text
$ as -o endian_a64.o endian_a64.s
$ ld -o endian_a64 endian_a64.o
$ ./endian_a64 > out.bin
$ echo "exit=$?"
exit=55
$ od -An -tx1 out.bin

```

`objdump -s -j .rodata endian_a64` 也能看到同一组字节（`4000b0 67452301`）；`readelf -h` 给出 `Machine: AArch64`、`Data: 2's complement, little endian`。`file` 与 `ldd` 确认它没有动态依赖：

```text

$ ldd endian_a64
	not a dynamic executable
```

x86-64 版本还在，只是这台机器上只能走到目标文件。源码骨架相同，差别在寄存器与系统调用号：

```asm
# endian_x86.s — clang --target=x86_64-linux-gnu -c endian_x86.s -o endian_x86.o
        .section .rodata
val:    .long 0x01234567
        .text
        .globl _start
_start:
        movl   $1, %eax           # SYS_write
        movl   $1, %edi
        leaq   val(%rip), %rsi
        movl   $4, %edx
        syscall
        movq   $10, %rcx
        xorl   %eax, %eax
.Lsum:
        addq   %rcx, %rax
        decq   %rcx
        jne    .Lsum
        andl   $0x7F, %eax
        movl   %eax, %edi
        movl   $60, %eax          # SYS_exit
        syscall
```

在 macOS arm64 上用 Apple clang 21 交叉汇编（`clang --target=x86_64-linux-gnu -c`）能成功产出 `endian_x86.o`；把它拷到 Ubuntu 上，`readelf` 和 `objdump -s` 都能读，`objdump -d` 则明确拒绝：

```text

$ readelf -r endian_x86.o
```

这组输出把边界划得很清楚：ELF 头、重定位（relocation，链接器要回填的地址占位）、节里的字节都是**架构无关的容器**，aarch64 上的 binutils 能读；反汇编需要 x86-64 的指令解码器，这台 binutils 没编进去。链接和运行更不行——没有 x86 的 `ld`、没有 x86 内核、没有用户态 qemu。所以 x86 版的 `lea`、`syscall`、退出码 55 全部是**未实测**，只能按 ABI 推导；真正跑通的是上面的 aarch64 版。

::: ex 例 1.2.14 · 先猜后改 {#ex-1.2.14}
把 `val` 改成 `.word 0x89ABCDEF`、`mov x2, #4` 保持不变，`od` 会打出哪四个字节？退出码会变吗？再把 `mov x2, #4` 改成 `#2` 呢？

::: sol 解答
先猜：little-endian 把最低有效字节放在最低地址，所以 `0x89ABCDEF` 输出 `ef cd ab 89`；退出码由循环决定，与常量无关，仍是 55；`count` 改成 2 只写前两个字节 `ef cd`。在 Ubuntu 上照改真跑，输出正是 `ef cd ab 89` 与 `ef cd`，两次 `exit=55`（实测）。**这题的关键不是算对，而是意识到「写多少字节」和「值是多少」是两条独立的线。**
:::

::: errata 关于这段汇编的三个误判
1. **「退出码 55 证明和一定是 55」**——`exit` 只看低 8 位，程序又先 `and 0x7f`；和若是 183 或 311，退出码同样是 55。要证明和，得把和写进 stdout，而不是塞进退出码。
2. **「字节序由 `syscall` 决定」**——`write` 只搬内存里的字节，不做任何转换；`67 45 23 01` 是 `.word` 在小端机器上的存放结果。换一台大端机器，同样的 `.word` 会输出 `01 23 45 67`（本机无大端硬件，未实测）。
3. **「x86 版也能在这台机器上跑」**——只能汇编到 `.o`；`objdump -d` 报 `can't disassemble for architecture UNKNOWN!`，链接与运行都没有环境。把「编过」当成「跑过」是这一节最容易犯的错。
:::

### 1.2.14 小结

① aarch64 版用 `as` + `ld` 真跑：`67 45 23 01`、`exit=55`，`objdump -s` 与 `readelf -h` 对得上。② x86-64 版只在 macOS 上交叉汇编到 `.o`，Ubuntu 上能读头、重定位和 `.rodata` 字节，不能反汇编，更不能运行。③ 两版共享同一个结论：字节序是存储约定，`write` 只搬字节；系统调用号和寄存器约定随架构变。如果只记住一件事，那就是：**先确认你在哪台机器上、能走到「汇编 / 链接 / 运行」的哪一步，再谈输出。**

## 1.2.15 实验一：用 gdb 观察溢出、转换与结构体布局 {#sec-1.2.15}

这一节回答：gdb 能不能把「溢出后的值、转换后的位、结构体的偏移」直接打给你？在这台 Ubuntu 24.04 aarch64 上，答案是一半能、一半不能；不能的那一半，正好把「工具失败时怎么继续取证」练一遍。

::: preview 先抓住一件事
gdb 15.1 能断点、能看寄存器、能算字面量；一旦要读程序里的变量或结构体类型，就打印 `Unable to fetch SVE/SSVE vector length: Invalid argument.`，然后什么也不给。原因不在你的程序：这台虚拟机的 CPU 没有 SVE（Scalable Vector Extension，可伸缩向量扩展），gdb 去取向量长度失败。溢出改用 UBSan（UndefinedBehaviorSanitizer，未定义行为检查器），转换与布局改用 `printf`/`offsetof`，结构体再用 DWARF 调试信息核一遍。
:::

### 场景：程序跑得动，gdb 却打不出变量

实验程序把 `S2`/`S5` 和两个整数放在全局变量里。用全局不是为了省事，而是先排除「`-O0` 下局部变量被优化掉」这个干扰——如果连全局都读不出，问题就不在优化。

```c
/* layout3.c — cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -g -O0 -o layout3 layout3.c */
#include <stdio.h>
#include <limits.h>

struct S2 { char c; double d; char e; };
struct S5 { char a[3]; short b; char c; };

struct S2 g_s2 = {'A', 1.5, 'Z'};
struct S5 g_s5 = {{1, 2, 3}, 0x1234, 9};
int g_i = INT_MAX;
unsigned g_u = 0;

int main(void)
{
    printf("%zu %zu %d %u\n", sizeof g_s2, sizeof g_s5, g_i, g_u);
    return 0;
}
```

```text
$ cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -g -O0 -o layout3 layout3.c
$ ./layout3
24 8 2147483647 0
```

程序本身没有问题：`S2` 24 字节、`S5` 8 字节、`INT_MAX` 原样、`u` 是 0。接下来把 gdb 接上。

### gdb 还能做什么

```text
$ gdb -q -batch -ex 'break main' -ex run -ex 'info registers cpsr' ./layout3
Breakpoint 1 at 0x760: file layout3.c, line 15.
Unable to fetch SVE/SSVE vector length: Invalid argument.
cpsr           0x1000              [ EL=0 BTYPE=0 SSBS ]
```

断点命中，`cpsr` 也读出来了；那条 SVE 警告在这里只是警告，命令仍然成功。`cpsr` 是 aarch64 的当前程序状态寄存器，x86-64 对应的是 `eflags`/`rflags`——旧稿里的 `info registers eflags` 在这台机器上根本没有这个寄存器。断点地址随编译变，`pc` 还随 ASLR 变；行号按本节源码，看形状即可。

字面量不查符号表，所以能算：

```text
$ gdb -q -batch -ex 'break main' -ex run -ex 'p (int)0xFFFFFFF0' -ex 'p/u (unsigned)-1' ./layout3
Breakpoint 1 at 0x760: file layout3.c, line 15.
Unable to fetch SVE/SSVE vector length: Invalid argument.
$1 = -16
$2 = 4294967295
```

`sizeof(struct S2)` 也一样，只要不启动进程，gdb 直接从调试信息里读：

```text
$ gdb -q -batch -ex 'p sizeof(struct S2)' ./layout3
$1 = 24
```

这行很关键：`sizeof` 是编译期常量，不需要运行。下面会看到，一旦 `run` 之后，同一个查询反而失败。

### gdb 坏在哪

```text
$ gdb -q -batch -ex 'break main' -ex run -ex 'p g_i' ./layout3
Breakpoint 1 at 0x760: file layout3.c, line 15.
Unable to fetch SVE/SSVE vector length: Invalid argument.
Unable to fetch SVE/SSVE vector length: Invalid argument.
$ echo $?
1
```

没有 `$1`，没有值，退出码 1。`p g_i` 读的是程序里的全局变量，gdb 需要解析符号、可能还要展开栈帧；这条路径碰到 SVE 取寄存器失败，整个表达式就放弃了。`p sizeof(struct S2)` 在 `run` 之后也同样失败（两条警告、无输出），尽管它在 `run` 之前刚给出 24。

`disassemble main` 更严重：它会让 gdb 自己 abort，报错末尾是 `A fatal error internal to GDB has been detected, further debugging is not possible.  GDB will now terminate.`。这不是你的程序段错误，是 gdb 内部的异常没被接住。结论：这台机器上的 gdb 只能当「寄存器查看器 + 字面量计算器」，不能当源码级调试器。下面三条替代路径分别接管溢出、转换和布局。

### 溢出：让 UBSan 指出行号

gdb 读不出变量，但「有符号溢出是 UB」这件事不需要变量视图也能证明。把加法放进一个不会被编译器折叠的位置，再让 UBSan 插桩：

```c
/* ovf.c */
#include <stdio.h>
#include <limits.h>

int main(void)
{
    volatile int i = INT_MAX;
    int j = i + 1;          /* 第 6 行 */
    printf("%d\n", j);
    return 0;
}
```

```text
$ cc -std=c17 -Wall -Wextra -g -O0 -fsanitize=undefined -fno-sanitize-recover=all -o ovf ovf.c
$ ./ovf
ovf.c:6:9: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
exit=1
```

`volatile` 让编译器不能在编译期把 `INT_MAX + 1` 折成一个常量；`-fno-sanitize-recover=all` 让第一个错误直接以非零码退出。UBSan 报的是 `文件:行:列`，这是语言层的判据，不是「这台 CPU 的加法标志位怎么变」。aarch64 的 `add` 会回绕，x86 的 `add` 会置 OF，但两者都不能把 C 的 UB 变成有定义；要看硬件怎么做，才用 `objdump -d`。

### 转换：printf 打出五个结果

```c
/* conv_demo.c */
#include <stdio.h>
#include <stdint.h>

int main(void)
{
    char c = -1;
    printf("(int)0xFFFFFFF0=%d (unsigned)-1=%u (int8_t)0x8F=%d "
           "(int16_t)0x8F=%d char(-1)=%d\n",
           (int)0xFFFFFFF0, (unsigned)-1, (int)(int8_t)0x8F,
           (int)(int16_t)0x8F, c);
    return 0;
}
```

```text
$ cc -std=c17 -Wall -Wextra -O0 -o conv_demo conv_demo.c
$ ./conv_demo
(int)0xFFFFFFF0=-16 (unsigned)-1=4294967295 (int8_t)0x8F=-113 (int16_t)0x8F=143 char(-1)=255
```

逐个读：

- `(int)0xFFFFFFF0` 给 -16：`0xFFFFFFF0` 的类型是 `unsigned int`，转成 `int` 是「实现定义」；这台二进制补码机器按位重解释，换一个非补码机器可能不同（本机没有那种机器，未实测）。
- `(unsigned)-1` 给 4294967295：有符号转无符号是定义良好的，规则是加 $2^{32}$。
- `(int8_t)0x8F` 给 -113：8 位补码，最高位是符号位。
- `(int16_t)0x8F` 给 143：16 位能放下 143，**不会**从第 7 位扩展符号。这正是「先转 16 位再当 8 位用」的经典错误。
- `char(-1)` 给 255：aarch64 Linux 的 GCC 默认让 `char` 无符号；x86-64 Linux 默认有符号（x86 侧未实测，按 ABI 文档）。跨平台序列化不要用裸 `char` 存负数。

### 布局：offsetof 与 DWARF

gdb 的变量视图坏了，但布局本来就是编译期常量，用 `offsetof` 直接打印：

```c
/* layout_print.c */
#include <stdio.h>
#include <stddef.h>

struct S2 { char c; double d; char e; };
struct S5 { char a[3]; short b; char c; };

int main(void)
{
    printf("S2 size=%zu c=%zu d=%zu e=%zu\n", sizeof(struct S2),
           offsetof(struct S2, c), offsetof(struct S2, d), offsetof(struct S2, e));
    printf("S5 size=%zu a=%zu b=%zu c=%zu\n", sizeof(struct S5),
           offsetof(struct S5, a), offsetof(struct S5, b), offsetof(struct S5, c));
    return 0;
}
```

```text
$ cc -std=c17 -Wall -Wextra -O0 -o layout_print layout_print.c
$ ./layout_print
S2 size=24 c=0 d=8 e=16
S5 size=8 a=0 b=4 c=6
```

对着 [1.2.11](#sec-1.2.11) 的四条规则读：`S2` 的 `c` 在 0，`d` 要求 8 对齐，所以 1–7 是填充；`d` 占 8–15，`e` 在 16；最大对齐 8，`sizeof` 向上取整到 24，尾部 17–23 是 7 字节填充。`S5` 的 `a[3]` 占 0–2，`b` 要求 2 对齐，3 号字节填充，`b` 在 4–5，`c` 在 6，尾部 7 号字节填充到 8。这些数字没有一个是「字段长度相加」直接得到的。

如果连源码都不想改，可以读 DWARF（调试信息格式，编译器把类型、变量、行号写进目标文件的那部分）。把同一个 `layout3.c` 用 `-g` 再编一份（`cc -g -O0 -o layout3_g layout3.c`），`readelf --debug-dump=info` 会把结构体条目摊开：

```text
$ readelf --debug-dump=info layout3_g | sed -n '/DW_AT_name.*S2/,+30p'
    <81>   DW_AT_name        : S2
    <84>   DW_AT_byte_size   : 24
    ...
    <93>   DW_AT_data_member_location: 0
    ...
    <9d>   DW_AT_data_member_location: 8
    ...
    <a7>   DW_AT_data_member_location: 16
```

节选，省略号处是文件号、行号、类型引用等 DWARF 行。`DW_AT_byte_size` 是 24，三个成员的 `DW_AT_data_member_location` 是 0/8/16，和 `offsetof` 的输出逐项对上。`pahole` 能把这类信息直接画成结构体图，但这台机器没装（`command -v pahole` 无输出，未安装），所以用 binutils 自带的 `readelf`。

::: method 工具坏了，怎么继续取证
1. 先跑程序本身，确认不是程序错（`./layout3` 有正常输出）。
2. 编译期常量：`sizeof`/`offsetof`/`printf`，或 `readelf --debug-dump=info` 读 DWARF。
3. 运行时 UB：`-fsanitize=undefined,float-cast-overflow`，让 sanitizer 给行号。
4. 指令层：`objdump -d`；文件层：`readelf -h/-S/-r`。
5. 把工具版本与报错原文一起记下来；不要用「应该是」补失败的那一步。
:::

::: errata 这台机器上的 gdb 与旧稿的四处出入
1. **「gdb 打不出变量就是没加 `-g`」**——`-g` 在；同一个二进制 `./layout3` 正常跑，`p sizeof(struct S2)` 在 `run` 前还能给 24，`run` 后失败。这是 gdb 的环境问题，不是编译选项。
2. **「`set var i = i + 1` 能看到 C 的回绕」**——它改的是目标进程的存储，不经过 C 表达式的语义。C 的有符号溢出是 UB；要判 UB，用 UBSan，不要用 gdb 的赋值。
3. **「结构体偏移只能靠 gdb」**——`offsetof`、DWARF、`pahole`（若安装）都能给；gdb 只是其中一条路。
4. **「aarch64 也有 `eflags`」**——aarch64 用 `cpsr`（以及 `nzcv` 条件标志），`eflags` 是 x86 的名字；旧稿的 `info registers eflags` 在这台机器上不成立。
:::

### 1.2.15 小结

① gdb 可用的一半：断点、`info registers`、字面量、`run` 之前的 `sizeof`；坏的一半：任何程序符号/类型求值，报 `Unable to fetch SVE/SSVE vector length`，`disassemble` 甚至让 gdb abort。② 三条替代路径都跑通了：UBSan 报 `ovf.c:6:9: signed integer overflow`；`printf` 给出 `-16 / 4294967295 / -113 / 143 / 255`；`offsetof` 与 DWARF 都给出 `S2 24 (0/8/16)`、`S5 8 (0/4/6)`。③ 工具失败不是终点，换一种工具把同一个结论钉死。如果只记住一件事，那就是：**先判断你要看的是编译期常量、运行时 UB 还是指令，再选工具；gdb 不是唯一的眼睛。**

## 1.2.16 实验二：用 objdump/readelf 读常量与浮点指令 {#sec-1.2.16}

这一节回答：`0.15625f` 和 `0.1` 在目标文件里到底以什么形式存在？为什么一个能塞进指令、另一个要去 `.rodata`？x86-64 的 `.o` 拿到 aarch64 机器上，`readelf` 能读什么、`objdump` 为什么拒绝？

::: preview 先抓住一件事
浮点常量有三种归宿：能编码进指令的立即数（AArch64 的 `fmov`）、由几条整数指令拼出来的位模式（`mov`/`movk` + `fmov`）、以及只读数据节（`.rodata.cst4/cst8`）。`readelf -h` 读 ELF 头，`objdump -s` 读节内容，`objdump -d` 才需要目标架构的反汇编器；三者不是一回事。
:::

浮点常量在目标文件里长什么样？写一个只有三个函数的小文件（`fc.c`）：

```c
float  fc(void) { return 0.15625f; }
double dc(void) { return 0.1; }
int    add(int a, int b) { return a + b; }
```

在 Ubuntu 24.04.5（aarch64，GCC 13.3）上编译并反汇编：

```text
$ cc -O2 -c fc.c -o fc.o
$ objdump -d fc.o | sed -n '/<fc>:/,$p'
0000000000000000 <fc>:
   0: 1e289000  fmov s0, #1.562500000000000000e-01
   4: d65f03c0  ret
   8: d503201f  nop
   c: d503201f  nop

0000000000000010 <dc>:
  10: 90000000  adrp x0, 0 <fc>
  14: fd400000  ldr d0, [x0]
  18: d65f03c0  ret
  1c: d503201f  nop

0000000000000020 <add>:
  20: 0b010000  add w0, w0, w1
  24: d65f03c0  ret
```

三个函数给出三种不同的「常量落脚点」：

- `fc` 的 0.15625 等于 $1.25 \times 2^{-3}$。AArch64 的 `fmov` 立即数能编码 8 位二进制有效位，所以常量直接进了指令，没有访存。注意反汇编打印的是 `1.5625e-01`，即 0.15625，不是 1.56。
- `dc` 的 `double` 0.1 没有这种立即数编码。`adrp` 取常量所在页的基地址，`ldr d0, [x0]` 再把 8 个字节装进浮点寄存器；地址的低 12 位由链接器回填。
- `add` 编译成 `add w0, w0, w1`。AArch64 的整数加法是三操作数；x86-64 常用 `lea` 同时做基址加变址，但那是 x86 的形状，本节不在 aarch64 上执行 x86 指令。

`dc` 的常量在 `.rodata.cst8` 里，`objdump -s` 能直接把字节打出来：

```text
$ objdump -s -j .rodata.cst8 fc.o
 0000 9a999999 9999b93f                    .......?
```

小端读法：`9a 99 99 99 99 99 b9 3f` 是 `0x3FB999999999999A`，正是 `double` 的 0.1（与 [1.2.7](#sec-1.2.7) 手算、[1.2.13](#sec-1.2.13) 的 `f64` 输出逐位相同）。目标文件里的 `adrp`/`ldr` 还是半成品，偏移是 0，重定位表记录着「链接时把 `.rodata.cst8` 填进来」：

```text
$ objdump -dr fc.o | sed -n '/<dc>:/,+4p'
0000000000000010 <dc>:
  10: 90000000  adrp x0, 0 <fc>
      10: R_AARCH64_ADR_PREL_PG_HI21 .rodata.cst8
  14: fd400000  ldr d0, [x0]
      14: R_AARCH64_LDST64_ABS_LO12_NC .rodata.cst8
```

`R_AARCH64_ADR_PREL_PG_HI21` 填 `adrp` 的页偏移，`R_AARCH64_LDST64_ABS_LO12_NC` 填 `ldr` 的页内偏移。`readelf -r fc.o` 给的是同一组信息，只是排成表格。

ELF 头把「这是什么机器、什么字节序」写在最前面：

```text
$ readelf -h fc.o | grep -E 'Class|Data|Machine'
  Class:                             ELF64
  Data:                              2's complement, little endian
  Machine:                           AArch64
```

`Data: little endian` 是文件头的 `EI_DATA` 字节（偏移 5），`Machine: AArch64` 是 `e_machine` 字段；加载器先看这两个字段，再决定怎么解释后面的多字节值。

### 第四种归宿：0.1f 连数据节都不去

再写两个函数（`fc2.c`）：`f01` 返回 `0.1f`，`d05` 返回 `0.5`。

```c
float  f01(void) { return 0.1f; }
double d05(void) { return 0.5; }
```

```text
$ cc -O2 -c fc2.c -o fc2.o
$ objdump -d fc2.o | sed -n '/<f01>:/,/<d05>:/p'
0000000000000000 <f01>:
   0: 529999a0  mov w0, #0xcccd                 // #52429
   4: 72a7b980  movk w0, #0x3dcc, lsl #16
   8: 1e270000  fmov s0, w0
   c: d65f03c0  ret

0000000000000010 <d05>:
```

`0.1f` 的位模式是 `0x3DCCCCCD`，编译器用 `mov`/`movk` 在通用寄存器 `w0` 里拼出这个 32 位数，再 `fmov s0, w0` 送进浮点寄存器；`fc2.o` 里根本没有 `.rodata.cst4`。`0.5` 是 $2^{-1}$，`fmov` 立即数能直接编码，也不需要数据节。把四个常量放在一起：

| 常量 | 函数 | 编译结果 | 数据节 |
|:--|:--|:--|:--|
| `0.15625f` | `fc` | `fmov s0, #...` | 无 |
| `0.1f` | `f01` | `mov` + `movk` + `fmov s0, w0` | 无 |
| `0.1`（double） | `dc` | `adrp` + `ldr d0, [x0]` | `.rodata.cst8` |
| `0.5`（double） | `d05` | `fmov d0, #0.5` | 无 |

所以「常量在不在 `.rodata`」不是语言问题，是编译器在你这个目标上的选择：能编码进指令就编码，不能编码就用整数指令拼，拼起来不划算才放数据节。

x86-64 的目标文件走的是另一条路。在 macOS 上用 Apple clang 21 交叉编译同一份 `fc.c`（`clang --target=x86_64-linux-gnu -O2 -c fc.c -o fc_x86.o`），拷到 Ubuntu 上：

```text
$ readelf -h fc_x86.o | grep Machine
  Machine:                           Advanced Micro Devices X86-64
$ objdump -s -j .rodata.cst4 fc_x86.o
 0000 0000203e
$ objdump -s -j .rodata.cst8 fc_x86.o
 0000 9a999999 9999b93f
$ objdump -d fc_x86.o
objdump: can't disassemble for architecture UNKNOWN!
```

数据节能读：`.rodata.cst4` 的 `00 00 20 3e` 按小端是 `0x3E200000`，即 `0.15625f`；`.rodata.cst8` 与 aarch64 的 0.1 字节完全相同——IEEE 754 的位模式不随架构变。重定位也在（`readelf -r fc_x86.o` 给出 `R_X86_64_PC32` 指向 `.LCPI0_0` 等），说明这些常量确实要被指令引用。

不能读的是指令：`objdump` 没有 x86-64 的解码器，报 `can't disassemble for architecture UNKNOWN!`。所以「x86-64 用 `movss` 从 `.rodata.cst4` 取 0.15625」这句话，本节只能说到「数据节与重定位对得上」；具体指令序列未反汇编，也未运行，**未实测**。旧稿里的 `movss`/`lea` 输出不要再当作本节证据。

::: ex 例 1.2.16 · 先猜后查 {#ex-1.2.16}
把 `fc` 的返回值从 `0.15625f` 改成 `0.1f`，`objdump -d` 里还会是一条 `fmov` 吗？`.rodata.cst4` 会出现吗？把 `dc` 改成 `0.5` 呢？

::: sol 解答
先猜：0.1f 的位模式 `0x3DCCCCCD` 有效位太多，`fmov` 立即数装不下；但编译器也未必把它放进 `.rodata.cst4`。实测（`fc2.c`，Ubuntu gcc 13.3）它用 `mov w0, #0xcccd` + `movk w0, #0x3dcc, lsl #16` + `fmov s0, w0` 三条指令拼出来，`.rodata.cst4` 根本不存在。`0.5` 是 $2^{-1}$，直接 `fmov d0, #5.000000000000000000e-01`，也没有数据节。**结论要按编译器实测改口：常量放哪里是代码生成策略，不是「float 一定进 cst4、double 一定进 cst8」。**
:::
:::

::: errata 读目标文件的四个坑
1. **「`fmov` 里的 `1.5625e-01` 是 1.56」**——指数是 `e-01`，值是 0.15625；把科学计数法的小数点看错，会把 0.15625 当成 1.56，后面的位模式全对不上。
2. **「`objdump -s -j .rodata` 一定能找到常量」**——节名可能是 `.rodata.cst4`/`.rodata.cst8`；名字写错时 `objdump` 直接报 `section '.rodata' mentioned in a -j option, but not found in any input file`。先 `readelf -S` 看节名。
3. **「`readelf -h` 说 little endian 就能在本机跑」**——头里还有 `Machine`；x86-64 的 `.o` 在 aarch64 上能读头、读数据，不能反汇编、不能链接运行。可读 ≠ 可执行。
4. **「`objdump -d` 失败说明文件损坏」**——失败原因常是「这个 binutils 没编进该架构的解码器」，`readelf`/`objdump -s` 仍然正常。判据是报错原文，不是猜测。
:::

### 1.2.16 小结

① 四个常量、四种归宿：`0.15625f` 和 `0.5` 进 `fmov` 立即数，`0.1f` 用 `mov`/`movk` 拼进通用寄存器，`0.1` 的 `double` 进 `.rodata.cst8`；这些都在 Ubuntu aarch64 上反汇编确认。② `objdump -dr`/`readelf -r` 能看到 `R_AARCH64_ADR_PREL_PG_HI21` 与 `R_AARCH64_LDST64_ABS_LO12_NC`，目标文件里的地址是半成品，链接器回填。③ x86-64 的 `.o` 只能读头、重定位和数据节；`objdump -d` 报 `can't disassemble for architecture UNKNOWN!`，指令序列未实测。如果只记住一件事，那就是：**先分清你要读的是文件结构、数据字节还是指令——`readelf`、`objdump -s`、`objdump -d` 是三把不同的钥匙。**

## 1.2.17 十二条陷阱：现象、原因与修复 {#sec-1.2.17}

这一节回答：这一章的规则落到代码里，最常见的十二种「看起来能跑、其实靠运气」的写法各是什么？每一条都按「现象 → 原因 → 修复」记；先猜哪几条在你机器上真的会崩，再看实测。

::: preview 先抓住一件事
十二条里最危险的不是必然报错的，而是「这台机器恰好对」的：`INT_MIN / -1` 在 x86 上是 `SIGFPE`，在 aarch64 上静默返回 `INT_MIN`；`char` 在 x86-64 Linux 有符号、在 aarch64 Linux 无符号；`(int16_t)0x8F` 是 143，不是 -113。先把这三点记住，再看表。
:::

| # | 现象 | 原因 | 修复 |
|--:|:--|:--|:--|
| 1 | `printf("%d", sizeof x)` 打印负数或截断 | `sizeof` 是 `size_t`（无符号 64 位），`%d` 按 `int` 读 | 用 `%zu`，或转 `(unsigned long)` 配 `%lu` |
| 2 | `(int16_t)0x8F` 得 143，不是 -113 | `0x8F` 的类型是 `int`，转 16 位不扩展符号 | 先 `(int8_t)` 再提升，或用 `sign_extend` |
| 3 | `-1 < 0u` 为假 | 混合运算把 `int` 转成 `unsigned` | 比较前统一类型；开 `-Wsign-compare` |
| 4 | `for (unsigned i = n; i >= 0; i--)` 死循环 | 无符号永远不小于 0 | 用 `i != 0` 或 `for (size_t i = n; i-- > 0;)` |
| 5 | `1 << 31` 得到负数或 UB | 有符号左移溢出 | 用 `1u << 31` 或 `UINT32_C(1) << 31` |
| 6 | `INT_MIN / -1` 在 x86 上 `SIGFPE`，在 aarch64 上得 `INT_MIN` | 商 $2^{31}$ 不可表示；x86 `idiv` 触发 `#DE`，aarch64 `sdiv` 不陷 | 除法前判 `b == 0 \|\| (a == INT_MIN && b == -1)` |
| 7 | `abs(INT_MIN)` 仍是负数 | 相反数不可表示 | 用 `llabs` 并先转 `long long`，或显式处理边界 |
| 8 | 同一份序列化代码在 ARM 上解析错 | `char` 默认无符号/有符号不同，或结构体布局不同 | 用 `uint8_t`/`int8_t`，逐字段序列化，不 `fwrite` 结构体 |
| 9 | `packed` 成员取地址后解引用，某些 ARM 核或原子访问崩溃 | 成员可能非对齐；本书 aarch64 的普通加载没崩，但原子/设备内存路径会 | 用 `memcpy` 逐字段读出；开 `-Waddress-of-packed-member` |
| 10 | `memcmp(&a, &b, sizeof a)` 对相同内容可能返回非 0 | 填充字节的值未定义 | 逐成员比较，或初始化时 `memset` 清零 |
| 11 | `0.1f == 0.1` 为假 | `float` 提升为 `double` 后值不同 | 比较用容差；需要精确时用整数/十进制 |
| 12 | `scanf("%f", &d)`（`d` 是 `double`）崩溃或错值 | `%f` 要 `float *`，`double` 要用 `%lf` | 检查格式串与指针类型；开 `-Wformat` |

先看一组在 Ubuntu 24.04.5（aarch64，GCC 13.3）上真跑出来的结果：

```text
$ ./traps
char(-1)=255  -1<0u=0  (int8_t)0x8F=-113  (int16_t)0x8F=143
abs(INT_MIN)=-2147483648
0.1f==0.1 -> 0
```

- `char(-1)=255`：aarch64 Linux 的 GCC 默认 `char` **无符号**；同样的源码在 x86-64 Linux 上会打 -1（x86 侧未实测，按 ABI 文档）。这就是第 8 条「序列化在 ARM 上解析错」的根。
- `-1<0u=0`：比较前 `-1` 被转成 `4294967295`，不是「负数小于零」。
- `(int8_t)0x8F=-113`、`(int16_t)0x8F=143`：截到 8 位才有符号，截到 16 位没有。
- `abs(INT_MIN)=-2147483648`：相反数不可表示，glibc 的 `abs` 原样返回。
- `0.1f==0.1 -> 0`：`float` 0.1 提升成 `double` 后与 `double` 0.1 不是同一个位模式。

第 1 条不用运行也能看见，编译器会给警告：

```text
$ cc -std=c17 -Wall -Wextra -c sizefmt.c -o /dev/null
sizefmt.c:2:38: warning: format '%d' expects argument of type 'int', but argument 2 has type 'long unsigned int' [-Wformat=]
```

`sizeof` 的类型是 `size_t`，在这台 LP64 机器上是 `unsigned long`；`%d` 按 `int` 取参数，宽度对不上。`-Wformat` 已经点了名，`-Werror` 会把它变成编译失败——这类问题最好在编译期解决，不要留到运行时看「打印出来的数怪怪的」。

第 5、6 条是 UB，普通运行看不出对错，让 UBSan 报：

```text
$ ./ub
ub.c:7:17: runtime error: left shift of 1 by 31 places cannot be represented in type 'int'
ub.c:8:15: runtime error: division of -2147483648 by -1 cannot be represented in type 'int'
-2147483648 -2147483648
exit=0
```

两行 `runtime error` 是语言层的判据；后面打印的两个 `-2147483648` 是这台 CPU 的实际结果（aarch64 的 `sdiv` 返回 `INT_MIN`，左移按位截断），不是 C 的承诺。`exit=0` 是因为这里没加 `-fno-sanitize-recover`，UBSan 报完继续跑；加上它会在第一条错误处以非零码退出。x86 的 `idiv` 会触发 `#DE`，进程收到 `SIGFPE`——x86 侧本节未实测，只按指令语义说明。

补充两条不算「陷阱」但常被忽略的边界：

- **位域布局**：`unsigned a:3` 从低位还是高位开始、能否跨存储单元，都是实现定义；跨编译器/网络协议不要用位域。
- **浮点的编译选项**：`-ffast-math` 会关闭 NaN/Inf 语义、假设无符号零、允许重排；它不是「更快的 IEEE」，而是「另一套语义」。金融、科学计算、需要逐位复现的场景不要开。

::: ex 例 1.2.17 · 先猜哪台机器会崩 {#ex-1.2.17}
同样一句 `int q = INT_MIN / -1;`，在 x86-64 Linux 和 aarch64 Linux 上各会发生什么？`1 << 31` 呢？

::: sol 解答
先猜：很多人会答「都崩溃」。实测与指令语义给出的答案是：x86-64 的 `idiv` 发现商 $2^{31}$ 超出 32 位有符号范围，触发 `#DE`，进程收到 `SIGFPE`；aarch64 的 `sdiv` 不陷，直接返回 `INT_MIN`（本节实测，`q` 打印为 -2147483648）。`1 << 31` 两边都是 UB，编译器可以给 `INT_MIN`，也可以假设它不发生；UBSan 会报 `left shift of 1 by 31 places cannot be represented in type 'int'`。**「会不会崩」是平台行为，「是不是 UB」是语言行为；写代码要按后者判。**
:::
:::

::: errata 这一节最容易记反的四件事
1. **「`INT_MIN / -1` 一定崩溃」**——只有 x86 的 `idiv` 会陷；aarch64 的 `sdiv` 静默返回 `INT_MIN`。不崩不等于没 UB。
2. **「`char` 默认有符号」**——平台相关；aarch64 Linux 的 GCC 默认无符号（实测 `char(-1)=255`），x86-64 Linux 默认有符号（未实测）。
3. **「`memcmp` 返回 0 就代表结构体相等」**——填充字节的值未定义，两个成员完全相同的结构体可能因填充不同而不等；逐成员比较。
4. **「`abs(INT_MIN)` 会返回正数」**——相反数不可表示；实测原样返回 `INT_MIN`，要先用 `llabs` 并处理边界。
:::

### 1.2.17 小结

① 十二条按四族记：宽度与格式（1、2）、符号性与移位（3、4、5、6、7）、布局与边界（8、9、10）、浮点与输入（11、12）。② 实测把三条「书上的断言」改了口：`char` 在 aarch64 无符号、`INT_MIN/-1` 在 aarch64 不崩、`abs(INT_MIN)` 仍是负数；UBSan 把两条 UB 钉在行号上。③ 修复的共同点是「不要靠这台机器的结果」，把宽度、符号、对齐、边界显式写进类型和判断。如果只记住一件事，那就是：**先问「这条行为是语言定义的、实现定义的，还是这台机器碰巧的」，再决定要不要写进代码。**

::: method 即时自测 · 1.2.17
**Q1（记忆）** 第 2 条里 `(int8_t)0x8F` 与 `(int16_t)0x8F` 各得多少？为什么？

**Q2（辨析）** 为什么 `INT_MIN / -1` 在 x86 上崩、在 aarch64 上不崩？这不崩说明表达式有定义吗？

**Q3（应用）** 把 `for (unsigned i = n; i >= 0; i--)` 改成两种正确写法，并说明各自的边界。

**Q4（迁移）** 你的日志里 `char` 字段在 x86 上是 -1、在 ARM 上是 255。写出两条修复，并说明哪条改的是数据格式、哪条改的是类型。

::: sol 答案
**A1** `(int8_t)0x8F` 得 -113，`(int16_t)0x8F` 得 143。8 位补码的最高位是 1，按符号解释为负；16 位能完整放下 143，最高位是 0，不发生符号扩展。
**A2** x86 的 `idiv` 在商超出范围时触发 `#DE`，内核把它变成 `SIGFPE`；aarch64 的 `sdiv` 不检查溢出，返回 `INT_MIN`。不崩只说明硬件没陷，C 标准仍把这条除法列为 UB，编译器可以假设它不发生。
**A3** 写法一：`for (size_t i = n; i != 0; i--)`，循环体看到的是 `n-1 ... 0`，如果业务需要处理 `i == n`，要在循环前单独做；写法二：`for (size_t i = n; i-- > 0;)`，循环体看到 `n-1 ... 0`，判断在自减之后，不会下溢。两种都不要用 `i >= 0`。
**A4** 数据格式：序列化时用 `uint8_t` 并显式规定 `0xFF` 表示 -1（或改用有符号的 `int8_t` 并写清补码），这样跨平台字节一致；类型：把裸 `char` 改成 `signed char`/`unsigned char`，让符号性由源码钉死。前者改的是线上格式，后者改的是本机类型；跨机器传输必须两条都做。
:::
:::

## 1.2.18 C 与 Rust 的表示语义对照 {#sec-1.2.18}

这一节回答：同一台机器、同一套补码与 IEEE 754，C 和 Rust 对这些位的「承诺」差在哪？先把口径说清：本节只做**文档级对照**，Rust 侧没有在实验机上编译运行（Ubuntu 实验机没有安装 Rust，`command -v rustc` 无输出）；C 侧的数字标了「Ubuntu 实测」。

::: preview 先抓住一件事
差别不在「Rust 更安全」这句口号，而在四件事：溢出是 UB 还是有定义、越界转换是 UB 还是饱和、布局由 `repr(C)` 还是默认布局决定、未初始化与别名由谁负责。C 的 UB 让编译器可以假设「不会发生」；Rust 把一部分行为写进语言定义，把另一部分收进 `unsafe`。
:::

### 逐条对照

| 行为 | C17 | Rust（release 默认） | Rust（debug 默认） |
|:--|:--|:--|:--|
| 有符号整数溢出 | 未定义行为（UB） | 回绕（二进制补码） | panic |
| 无符号整数溢出 | 回绕，定义良好 | 回绕 | panic |
| 移位量 ≥ 位宽 | UB | 按位宽掩码（不保证可移植） | panic |
| 有符号右移 | 实现定义（GCC 算术右移） | 算术右移 | 算术右移 |
| 宽转窄整数 | 实现定义（通常截断） | `as` 截断，定义良好 | 同左 |
| 负整数转无符号 | 定义良好（加 $2^w$） | `as` 截断（同左） | 同左 |
| 浮点转整数越界 | UB | 饱和（1.45+） | 饱和 |
| NaN 转整数 | UB | 0 | 0 |
| 结构体布局 | 实现定义，同一 ABI 内稳定 | `repr(Rust)` 可重排；`repr(C)` 与 C 一致 | 同左 |
| 数组越界 | UB | 边界检查，panic | 边界检查，panic |
| 未初始化内存 | 读是 UB | `MaybeUninit`，读需 `unsafe` | 同左 |
| 空指针解引用 | UB | `unsafe` 下的 UB；安全代码用 `Option<&T>` | 同左 |
| 指针别名 | `restrict` 违反是 UB | `&mut` 独占，违反是 UB（`unsafe` 才可能） | 同左 |

三行值得展开：

- **溢出**：C 的 UB 让编译器可以假设「不会溢出」，从而把 `i + 1 > i` 优化成恒真；Rust 的 release 模式把溢出定义为「按补码回绕」，debug 模式则 panic。要显式控制，用 `wrapping_add`、`checked_add`、`saturating_add`、`overflowing_add`，而不是依赖构建模式。
- **浮点转整数**：C 的 `(int)1e300` 是 UB。在这台 aarch64 上实测给 `2147483647`，`(int)NaN` 给 `0`（硬件 `fcvtzs` 的饱和/置零行为）；x86-64 的 `cvttsd2si` 给 `INT_MIN`（文献值，本机无 x86，未实测）。Rust 的 `as` 从 1.45 起规定饱和：`1e300 as i64` 得 `i64::MAX`，`NaN as i64` 得 0。同样是「越界」，C 让你自己兜底，Rust 把结果写进语言。
- **布局**：`repr(C)` 不是「更安全的 C」，而是「按 C 的 ABI 排布」；默认 `repr(Rust)` 允许编译器重排字段。C 侧的 `CfgC { uint8_t a; uint32_t b; uint8_t c; }` 实测 `size=12 a=0 b=4 c=8`；Rust 的 `#[repr(C)]` 按定义应与这个布局一致，但本节没有 Rust 工具链，具体大小未实测，不贴数字。

`CfgC` 的 12 字节把 [1.2.11](#sec-1.2.11) 的规则又走了一遍：`u8` 在 0，`u32` 要 4 对齐，1–3 填充，`b` 在 4–7，`c` 在 8，尾部 9–11 填充到 4 的倍数。Rust 的 `repr(C)` 承诺同一套排布；默认布局只承诺「字段不重叠」，不承诺顺序。

### 一段示意代码，不是运行结果

Rust 侧下面这段只用来对照 API，**未编译**（实验机没有 `rustc`）：

```rust
// 示意，未编译；语义按 Rust 标准库文档
let a: i32 = i32::MAX;
let _ = a.checked_add(1);     // None
let _ = a.wrapping_add(1);    // i32::MIN
let _ = a.saturating_add(1);  // i32::MAX
let _ = (1e300f64) as i64;    // i64::MAX（饱和）
let _ = f64::NAN as i64;      // 0
```

这里每个方法名就是它的语义：`checked_*` 返回 `Option`，`wrapping_*` 明确回绕，`saturating_*` 夹到边界，`overflowing_*` 同时返回值和溢出标志。不要靠「release 会回绕」写业务逻辑；要哪种语义就调哪个方法。

::: method 什么时候必须用 repr(C) 布局
1. 与 C/Rust 之外的代码共享结构体（FFI、内核 UAPI、驱动）。
2. 结构体直接映射到文件/网络格式（ELF 头、`sockaddr`、协议首部）。
3. 需要 `offsetof` 或依赖字段顺序的序列化。
4. 把结构体放进 `static` 并被汇编/链接脚本按名字引用。
其余场景用默认布局，让编译器减小体积；不要为了「稳定」给所有结构体加 `repr(C)`，那会放弃优化填充的机会。
:::

::: ex 例 1.2.18 · 先猜布局 {#ex-1.2.18}
先猜：C 的 `struct CfgC { uint8_t a; uint32_t b; uint8_t c; }` 在 LP64 上是 12 字节（实测）。把它原样写成 Rust 的 `#[repr(C)]` 结构体，大小是 12、8 还是 16？如果把 `#[repr(C)]` 去掉，你能只凭语言规范说出大小吗？

::: sol 解答
`#[repr(C)]` 按 C 的 ABI 排布，所以还是 12：`a` 在 0，`b` 在 4，`c` 在 8，尾部补到 4 的倍数。去掉 `repr(C)` 后**不能**只凭语言规范给出确定值：默认 `repr(Rust)` 允许编译器重排字段，具体大小取决于编译器版本与目标；本节没有 Rust 工具链，未实测，所以不写「一定是 8」。**能确定的是「`repr(C)` 与 C 一致」，不能确定的是「默认布局长什么样」。**
:::
:::

::: errata C 程序员写 Rust 最常踩的六个坑
1. **「`as` 和 C 的强制转换一样」**——Rust 的 `as` 对整数截断、对浮点转整数饱和；C 的越界转换是 UB。跨语言对比时先统一语义。
2. **「release 也会检查溢出」**——release 默认关闭 `overflow-checks`，有符号/无符号都回绕；要检查用 `checked_*` 或显式开启。
3. **「结构体字段顺序就是声明顺序」**——默认 `repr(Rust)` 不保证；跨 FFI 必须 `repr(C)`。
4. **「C 的 `(int)1e300` 一定得 `INT_MIN`」**——aarch64 实测给 `2147483647`，x86-64 的 `cvttsd2si` 给 `INT_MIN`；UB 的意思就是「没有保证」，换架构就换答案。
5. **「`unsafe` 只是语法糖」**——`unsafe` 块里编译器不再保证别名/越界/初始化的规则，违反仍是 UB；它不是「关掉检查」，而是「由你负责」。
6. **「Rust 没有 UB」**——安全代码没有，`unsafe` 代码有；`get_unchecked`、`from_raw_parts`、`transmute` 都能制造 UB。
:::

### 1.2.18 小结

① C 与 Rust 的差别是「承诺」：C 把很多边界留给 UB/实现定义，Rust 把一部分写进语言（饱和、panic、借用规则），把另一部分收进 `unsafe`。② 三行最常混：溢出、浮点转整数、布局；C 侧 `CfgC=12`、`(int)1e300=2147483647`、`(int)NaN=0` 是 Ubuntu 实测，Rust 侧按文档、未编译。③ FFI 用 `repr(C)`，溢出用 `checked_*`/`wrapping_*`，不要靠构建模式。如果只记住一件事，那就是：**跨语言传值，先问「布局谁保证、越界谁负责」，再问语法怎么写得像。**

**Q1（记忆）** Rust 的有符号溢出在 debug 与 release 下各是什么行为？`checked_add` 返回什么类型？

**Q2（辨析）** C 的 `(int)1e300` 与 Rust 的 `1e300f64 as i64` 各是什么语义？为什么不能说「都得到一个数」？

**Q3（应用）** 一个 `#[repr(C)]` 结构体的 C 版本是 `size=12 a=0 b=4 c=8`，Rust 版本的大小是多少？默认布局的版本呢？

**Q4（迁移）** 你要把 Rust 结构体直接 `write` 进文件给 C 程序读。列出两条必须做的事，并说明不做会怎样。

::: sol 答案
**A1** debug 默认 panic（`overflow-checks` 开）；release 默认回绕（`overflow-checks` 关，按补码）。`checked_add` 返回 `Option<T>`：成功 `Some(和)`，溢出 `None`。

**A4** 一，结构体加 `#[repr(C)]`，否则字段顺序和填充由编译器决定，C 侧读到的偏移可能全错；二，逐字段按固定宽度（`u32`/`i64`）和固定字节序编码，不要 `write` 整个结构体，否则填充字节和主机字节序会泄漏到文件里。两条分别解决「布局」和「编码」。

::: preview 先抓住一件事
表示问题的固定顺序：**类型与宽度 → 符号性 → 字节序 → 对齐/布局 → 浮点边界 → 语言承诺（UB / 实现定义 / 有定义）**。六步走完，再决定用哪个工具、看哪条证据。本章所有「这台机器上是这样」的结论，都只在这六步的最后一层。

### 一条主线：从位到承诺

这一章从最小的单位走到语言的承诺，分五段：

1. **位与整数（1.2.1–1.2.5）**：位、字节、字、十六进制是读写表示的语言；补码让 `-x = ~x + 1` 成立；符号扩展、截断、`int ↔ unsigned` 有各自规则；有符号溢出是 UB，无符号是回绕；移位量越界是 UB。
2. **字节序、布局与浮点（1.2.6–1.2.8）**：小端把最低有效字节放在低地址，`htonl` 在需要时真的翻字节；结构体有对齐与填充；IEEE 754 把 32/64 位切成符号、阶码、尾数；`0.1 + 0.2` 不等于 `0.3` 是舍入的结果，比较要用容差。
3. **手算与全规则（1.2.9–1.2.11）**：补码、移位、溢出、IEEE 字段都能在纸上算；四条布局规则管完 `sizeof`/`offsetof`；含 `long double` 的 `S6` 在两台机器上实测 32 与 16 字节，是本章唯一一个基础类型的跨机差异。
4. **程序与实验（1.2.12–1.2.17）**：位操作工具箱把边界关进函数；浮点分析器把 `nan`/`-0` 打成位模式；aarch64 汇编真跑出 `67 45 23 01`、退出码 55；gdb 在这台 VM 上只成功了一半，UBSan/DWARF 接住溢出与布局；`objdump`/`readelf` 把「文件结构 / 数据字节 / 指令」分成三层；十二条陷阱最后收口。
5. **C 与 Rust（1.2.18）**：同一套位，C 把边界留给 UB/实现定义，Rust 把一部分写进语言、把另一部分收进 `unsafe`；跨 FFI 的结构体用 `repr(C)`，溢出用 `checked_*`/`wrapping_*`。

一句话主线：**先建立「位—字节—整数—布局—浮点」的表示模型，再用三个程序和两个实验把它钉到真实工具上，最后用 C/Rust 对照补上「语言承诺」这一层。**

### 六句话，能讲出来才算过

1. 先看类型与宽度，再看值；`sizeof` 是 `size_t`，打印用 `%zu`。
2. 有符号溢出是 UB，无符号是回绕；不要把「这台机器回绕了」当成 C 的保证。
3. 字节序是存储约定，不是指令行为；跨边界要逐字段编码，不能 `fwrite` 整个结构体。
4. 结构体大小是「对齐之后的结果」，不是字段之和；`offsetof`、DWARF、`pahole` 都能给偏移。
5. 浮点是分段常数 ULP；异常先打位模式（`%a` 或 `memcpy` 到整数），比较用容差。
6. 跨语言先问「布局谁保证、越界谁负责」；`repr(C)` 和 `checked_*` 是两个不同问题的答案。

### 看到问题先选工具

| 症状 | 第一动作 | 为什么 |
|:--|:--|:--|

::: method 即时自测 · 1.2
**Q1（记忆）** 32 位补码 `0xFFFFFFF0` 作为 `int` 和 `unsigned` 分别是多少？如何用一行代码验证？

**Q2（辨析）** `int8_t x = 0x80;` 的值是多少？`-x` 在 8 位补码里是多少？在 C 里对 `INT_MIN` 取负会发生什么？

**Q3（应用）** `struct { char c; double d; char e; }` 的 `sizeof` 是多少？把 `double` 移到最前面会变成多少？

**Q4（迁移）** 为什么 `0.1 + 0.2 == 0.3` 是假？如果要比较这两个表达式，应该怎么写？

::: sol 答案
**A1** 作为 `int` 是 -16（`~0xF + 1`，[1.2.15](#sec-1.2.15) 实测 `(int)0xFFFFFFF0` 就是这个值）；作为 `unsigned` 是 $2^{32}-16=4294967280$，算术结果，不依赖机器。验证：`printf("%d %u\n", (int)0xFFFFFFF0u, 0xFFFFFFF0u);`。
**A2** `0x80` 按 8 位补码是 -128。`-x` 仍是 `0x80`（-128 的相反数不可表示）；在 C 里对 `int8_t` 的 -128 取负会先提升为 `int`，得到 128；对 `INT_MIN` 取负是 UB，结果取决于编译器与硬件，不能写进可移植代码。
**A3** 24 字节（偏移 0、8、16，尾部填充到 8 的倍数）。把 `double` 放最前：`double` 0，`char` 8，`char` 9，总大小 16（两机实测，见 [1.2.11](#sec-1.2.11) 的 `S2`/`S3`）。
**A4** 0.1 和 0.2 都不能用二进制有限位精确表示，相加后舍入得到 `0.30000000000000004`，而字面量 0.3 是另一个近似值。比较应使用容差：`fabs((0.1+0.2)-0.3) < 1e-12`，或改用整数/十进制类型。
