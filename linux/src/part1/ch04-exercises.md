# 1.4 习题集

三组分层：A 组概念判断（口答即可）、B 组诊断推理（写出步骤）、C 组动手实验（在虚拟机里跑，`perf` 需要 Linux）。**全部附解答**；先独立完成，再展开对照。

## 怎么用

1. 先读题，不看解答，给自己 2–3 分钟找思路；
2. 卡住了，回到对应小节的「即时自测」重读，不要直接看答案；

## A 组 · 概念判断

::: ex 例 1.4-A1 · ISA 与微架构 {#ex-1.4-A1}

「同一 ISA 的两个实现，性能不会差太多」——这句话对吗？用两个微架构参数说明你的判断，并解释为什么主频高低不能单独用来比性能。

::: sol 解答

不对。ISA 只保证可见状态与语义一致，时序完全由微架构决定：发射宽度（4 宽与 8 宽的理想 IPC 上限差一倍）、ROB 与物理寄存器数量（决定能同时容纳多少条未完成指令）、缓存容量与流水线深度都会拉开差距。性能 = 指令数 × CPI ÷ 频率，三项都要看；主频高但 CPI 大、或缓存小导致缺失多，照样慢。所以比较两个实现要报 IPC 和缺失率，而不是只看 GHz。

:::
:::

::: ex 例 1.4-A2 · Y86-64 的定位 {#ex-1.4-A2}

Y86-64 是 x86-64 的子集吗？它能跑 Linux 吗？它把立即数固定成 8 字节是「落后」还是取舍？

::: sol 解答

都不是、不能、是取舍。Y86-64 只借用了 x86-64 的寄存器名和部分助记符，编码、指令集和异常模型都不同，x86-64 的二进制在它上面跑不了；它也没有系统调用、页表和设备，跑不了任何真实程序。固定 8 字节立即数是为了让译码简单到能在纸上画出来，代价是指令变长——真实 x86-64 用 1–15 字节的变长编码换代码密度，换来的是复杂得多的定界与预译码。

:::
:::

::: ex 例 1.4-A3 · 指令字节数 {#ex-1.4-A3}

说出 `call`、`mrmovq`、`popq`、`nop`、`jXX` 各占几字节。为什么 `jXX` 和 `call` 没有 `rA:rB` 字节？这给取指带来什么麻烦？

::: sol 解答

`call` 9、`mrmovq` 10、`popq` 2、`nop` 1、`jXX` 9。跳转类的目标地址是纯常量，不需要寄存器字段，所以第 2 字节起就是 8 字节目的地址。麻烦在于：译码器必须先看 `icode` 才能决定「有没有寄存器字节」，进而决定常量从第 2 还是第 3 字节读、指令有多长——这就是变长取指的第一难点，也是解释器里最容易写错的分支。

:::
:::

::: ex 例 1.4-A4 · HCL 的语义 {#ex-1.4-A4}

`word aluA = [ icode in { IRRMOVQ, IOPQ } : valA; … 1 : 0; ];` 在硬件里是什么？漏掉最后一行会怎样？为什么 HCL 里不能写 `x = x + 1`？

::: sol 解答

一个多路选择器：选择信号是 `icode`，输出按顺序匹配、第一个为真的分支胜出。漏掉默认分支时，条件全不满足的那个周期输出没有定义，综合会推出锁存器、仿真给出未知值——这和 C 里 `switch` 漏 `default`（只是不执行）完全不同。`x = x + 1` 在 HCL 里是「x 等于 x+1」的循环定义，构成组合环；真正的状态必须由时钟边沿更新的寄存器（PC、条件码、寄存器堆、内存）承担。

:::
:::

::: ex 例 1.4-A5 · 转发还是暂停 {#ex-1.4-A5}

下面四组相邻指令，哪些只靠转发就够、哪些必须停一拍？说明理由：
① `addq %rax,%rbx` 后 `mrmovq (%rbx),%rcx`；② `mrmovq (%rax),%rbx` 后 `addq %rbx,%rcx`；③ `irmovq $8,%rcx` 后 `addq %rcx,%rdi`；④ `addq %rax,%rbx` 后紧跟另一条写 `%rbx` 的 `addq`，再后面第三条要用 `%rbx`。

::: sol 解答

①③只需转发：产生结果的是 ALU 类指令，结果在 E 阶段末就有了，紧跟着那条指令在下一拍的 E 就能用上。②必须停一拍：load 的数据要到 M 阶段末才回来，`E_dstM` 命中 `D_srcA`/`D_srcB` 时冻结 PC 与 `F`/`D`、往 E 插气泡。④不用额外停，但转发的优先级要写对：第三条应拿更新的那条（更靠前的流水级），即 W 优先于 M 优先于寄存器堆，且目的寄存器编号匹配且非 `RNONE` 才旁路。

:::
:::

::: ex 例 1.4-A6 · 分支预测 {#ex-1.4-A6}

「把 `if` 换成 `cmov` 或掩码就一定更快」——对吗？「同一份代码，把数据排序后快了十倍」又说明什么？

::: sol 解答

不对。`cmov` 把控制依赖变成数据依赖，代价是两条路径都可能要算，而且源操作数若可能触发异常就不能这样换；分支高度可预测时，预测正确的代价接近 0，改成无分支反而多做事。排序带来大收益说明瓶颈是预测器的**历史**而不是数据本身：随机比较没有可利用的历史，miss 率接近抛硬币；排序后变成一长串同方向，两位计数器几乎全中。这也是基准测试必须用真实数据分布的原因。

:::
:::

::: ex 例 1.4-A7 · 乱序的语义承诺 {#ex-1.4-A7}

乱序执行会改变程序结果吗？精确异常靠什么保证？既然按序提交，为什么还要推测执行？

::: sol 解答

不会。ISA 规定的按序语义由 ROB 的提交顺序维持：执行可以乱序、并发，但只有队首指令能提交，寄存器与内存的状态在提交那一刻才对软件可见，因此异常报告的位置也是精确的。推测执行是为了不空等分支：预测之后先把后面的指令取进来执行，结果放在 ROB 里不提交，猜对了就直接退休、猜错了丢弃。要记住副作用不都可控——Spectre 利用的正是推测执行留下的缓存状态，而不是错误的提交结果。

:::
:::

::: ex 例 1.4-A8 · 顺序与内存序 {#ex-1.4-A8}

一段多线程代码在 x86-64 上跑了一年没错，搬到 ARM 服务器后偶发读到旧值。有人说「是移植引入的 bug」。你怎么判断？该改什么？

::: sol 解答

先怀疑内存序而不是移植 bug。单核上处理器只保证不破坏你自己的地址依赖，多核之间可见顺序由内存模型约束：x86-64 是 TSO，普通 load/store 不会看到明显的重排（store 之间仍可能被缓冲），所以数据竞争常常「碰巧能跑」；ARM 是弱序，两个核看到的写顺序可能不同。修法是不要依赖硬件强度：用 C11/C++ 的 `memory_order` 与 `atomic_thread_fence`，或平台屏障（x86 的 `lock` 前缀/`mfence`、ARM 的 `dmb`、`ldar`/`stlr`），并用 TSan 复核。展开见 [1.12.9](ch12.md#sec-1.12.9)。

:::
:::

## B 组 · 诊断推理

::: ex 例 1.4-B1 · 多出来的一拍 {#ex-1.4-B1}

一段 6 条指令的程序按五级流水线手算，比理想时序表多出一拍，CPI 从 1.67 涨到 1.83。时序表显示停住的那条指令在 D 阶段重复了一次。写出你的定位过程和两种改法。

::: sol B1 核对

先看谁在等谁：D 阶段重复说明后一条指令要的两个源操作数里，有一个是前一条 `mrmovq` 的目的寄存器，即 `E_icode == IMRMOVQ` 且 `E_dstM` 命中 `D_srcA`/`D_srcB`——这是 load-use，转发救不了，只能停一拍（load 数据在 M 末才可用）。两种改法：① 把与 load 无关的指令（计数器自增、地址推进）提到 load 与使用之间，填掉这一拍；② 用多累加器或多缓冲把这条依赖链拆开，让下一拍的 E 有别的活干。判断改没改对，就重填时序表看气泡数量，不要凭感觉。

:::
:::

::: ex 例 1.4-B2 · IPC 低、分支缺失高 {#ex-1.4-B2}

`perf stat` 报出 IPC 明显小于 1、分支缺失率十几个百分点、缓存缺失率只有个位数。最可能的瓶颈是什么？给出定位步骤和两条修复思路，并说明为什么不能直接断定「改成无分支一定快」。

::: sol B2 核对

瓶颈是控制冒险，不是访存。步骤：`perf record -e branch-misses` 找热点函数，再 `perf annotate` 看具体是哪条条件跳转在错；确认它在热循环里、且数据分布让方向不可预测（例如随机阈值判断）。修复：① 改数据布局让分支方向变得连续（先排序或分桶，见 [1.4.15](ch04.md#sec-1.4.15) 的实验）；② 用查表或掩码把判断变成数据。不能直接断定第二点更快，是因为 `cmov` 会把两条路径都算一遍，只有分支真的不可预测时才划算；如果这段代码同时是内存带宽瓶颈（缓存缺失率也高），改分支收益会被缺失掩盖。

:::
:::

::: ex 例 1.4-B3 · 换了更大的 ROB 也不快 {#ex-1.4-B3}

把程序从 4 宽、ROB 224 项的老核挪到 6 宽、ROB 512 项的新核，IPC 几乎不动。程序是链表遍历，每个节点一次指针解引用。用 ROB/窗口这套模型解释现象，并给出真正有效的两条改法。

::: sol B3 核对

用 N = T × L 看：窗口再大，如果一次只能有一个缺失在飞（MLP=1），平均停留时间 L 就由一整次访存延迟决定，上限是 L 分之一，跟发射宽度和 ROB 项数无关；老核就已经贴着这个上限，新核的额外窗口无处可用。有效的两条路：① 提高 MLP——把遍历改成分组预取或先收集地址再批量读，让多个缺失同时在飞；② 减少 miss 本身——换布局（数组、SoA）或加一级索引，见 [1.5.8](ch05.md#sec-1.5.8) 与 [1.6.6](ch06.md#sec-1.6.6)。ROB 提供的是并发度预算，不是延迟消除。

:::
:::

::: ex 例 1.4-B4 · 新加的指令没执行 {#ex-1.4-B4}

你在 [1.4.13](ch04.md#sec-1.4.13) 解释器的 `prog` 数组里，`jne` 之后、`halt` 之前追加了 `irmovq $0x800,%rsp` 和 `rmmovq %rax,0(%rsp)`，想验证结果被写进内存。运行后仍然打印 `status=2 steps=43 pc=0x2b`，新指令一条也没跑。写出你的排查思路。

::: sol B4 核对

现象是「程序在 0x2b 就停了」。按 `jne` 的编码：1 字节 `icode:ifun` + 8 字节目的地址 = **9 字节**，所以 `jne` 之后第一条指令应当正好落在 0x2b。如果你的数组里 `jne` 那行写成 `0x74, 0x14` 后面跟了 8 个 0（10 字节），0x2b 处就剩一个多余的 `0x00`——`0x00` 的 icode 是 0，译码成 `halt`，于是解释器在循环结束时立刻停机，追加的指令根本没被取到。排查顺序：① 逐行数字节，确认每条指令的长度与注释里的地址一致；② 打印 `pc` 与 `mem[pc]`，看停机时取到的是哪一字节；③ 删掉多余的 0（`irmovq` 那行回到 0x2b 起始）再跑，`rsp`、内存与 `steps` 就都对了。这也解释了为什么手写机器码要从第 2 还是第 3 字节读常量：错一个字节，后面整段全部错位。

:::
:::

::: ex 例 1.4-B5 · `andq` 之后 `jne` 不跳 {#ex-1.4-B5}

用解释器实现「判零」：先 `andq %rcx,%rcx` 想把 ZF 置上，再 `jne` 提前退出。结果 ZF 一直是 0，循环一直跑到 `steps` 上限。为什么？正文哪两处说法不一致？怎么绕开？

::: sol B5 核对

Y86-64 的解释器只在 `addq`/`subq` 之后更新条件码（`setcc = (ifun <= 1)`），`andq`/`xorq` 不写 ZF/SF/OF，所以 `jne` 的条件永远不成立。正文 [1.4.2](ch04.md#sec-1.4.2) 的指令表把 `andq`/`xorq` 也标成「设标志」，与 [1.4.13](ch04.md#sec-1.4.13) 的实现和说明冲突，以解释器为准（真实 x86-64 的 `and`/`xor` 是设 ZF/SF 的，别把两边记混）。绕开办法是记住「标志只能由加减产生」：要判 `%rcx` 是否为 0，先 `irmovq $0,%rbx` 备一个零，再 `subq %rcx,%rbx`（算 `rbx = 0 - rcx`，同时设 ZF），然后用 `je`/`jne` 判；`rbx` 是牺牲品，每轮要重新置零。Y86-64 没有寄存器与立即数混合的 `OPq`，也没有 `testq`/`cmp`，所以这种「多一条指令、换一个 scratch」的绕法会经常遇到——这正是 ISA 指令面窄的代价。

想自己验，跑两遍：第一遍 `irmovq $5,%rcx`、`irmovq $2,%rbx`、`andq %rcx,%rbx`（`62 13`）、`halt`，打印出来 `rbx=0` 但 `ZF` 仍是 0——`andq` 算对了，标志一位没动；第二遍 `irmovq $5,%rcx`、`irmovq $5,%rbx`、`subq %rcx,%rbx`（`61 13`）、`halt`，`rbx=0` 且 `ZF=1`——只有加减写标志。

:::
:::

::: ex 例 1.4-B6 · 分支惩罚与流水线深度 {#ex-1.4-B6}

有人说「流水线加深只是为了提频率，代价可以忽略；反正预测器很准」。请用「预测正确」与「预测错误」两种情况算一笔账，说明这句话漏掉了什么。

::: sol B6 核对

预测正确时代价接近 0，所以深流水线的收益确实能兑现；但错误代价与级数同阶：分支越晚解析，已经取进流水线的错误路径指令越多，冲刷就要丢十几条，现代深流水线一次要付十几到二十周期。所以真实公式里错误率是乘在「冲刷周期」上的：CPI = 基础 + 分支比例 × 错误率 × 冲刷周期，加深流水线会同时放大第三项。Pentium 4 推到 31 级后失败代价与功耗失控、回到 14–19 级并把面积投给预测器（BTB、TAGE、返回栈），就是在补这笔账。漏掉的还有前端与功耗：每级流水寄存器自身的 setup/hold 与时钟偏斜开销随级数上升。

:::
:::

## C 组 · 动手实验

::: ex 例 1.4-C1 · 跑通 Y86-64 解释器 {#ex-1.4-C1}

把 [1.4.13](ch04.md#sec-1.4.13) 的 `y86.c` 抄下来编译运行，核对输出。

::: sol C1 核对

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 y86.c -o y86
./y86; echo "exit=$?"
```

应得到 `status=2 steps=43 pc=0x2b ZF=1 SF=0 OF=0` 与 `rax=55 rcx=0 rdx=1`，退出码 0。`status=2` 是 HLT；`steps=43` 可以手算核对：2 条 `irmovq` + 10 次循环 × 4 条 + 1 条 `halt` = 43；`rax` 是 10+9+…+1 = 55。验收标准：不用看代码就能说出 `rcx` 为什么归零、`rdx` 为什么恒为 1。

:::
:::

::: ex 例 1.4-C2 · 改一个字节，看现象放大 {#ex-1.4-C2}

把机器码里 `subq %rdx,%rcx` 的功能码从 `0x61` 改成 `0x60` 再跑一次，观察输出。

::: sol C2 核对

```bash
sed 's/0x61, 0x21,/0x60, 0x21,/' y86.c > y86_bad.c
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 y86_bad.c -o y86_bad
./y86_bad; echo "exit=$?"
```

`0x60` 是 `addq`：计数器只增不减，`jne` 永远成立，循环不终止。程序靠 `steps` 的 1000 上限跳出，于是打印 `status=1 steps=1000`（1 是 AOK，不是 HLT），退出码非 0。这个现象对应陷阱表第 12 条：功能码在低 4 位，sub 必须是 `0x61`。

:::
:::

::: ex 例 1.4-C3 · 手编三条并让它真的执行 {#ex-1.4-C3}

在 `halt` 之前追加 `irmovq $0x800,%rsp`、`rmmovq %rax,0(%rsp)`、`mrmovq 0(%rsp),%rcx`，让结果先写进内存再读回来。

::: sol C3 核对

字节依次是 `30 f4 00 08 00 00 00 00 00 00`（10 字节）、`40 04` 后跟 8 个 0（10 字节）、`50 14` 后跟 8 个 0（10 字节）。`rA:rB` 要按「`rB = rB OP rA`」与「`M[rB+D] = rA`」的语义排：`rmmovq %rax,0(%rsp)` 是 `40 04`（rA=rax=0、rB=rsp=4），`mrmovq 0(%rsp),%rcx` 是 `50 14`（rA=rcx=1、rB=rsp=4）。验收：打印出的 `rcx` 与 `rax` 都是 55，`steps` 比原来多 3 条。如果你发现程序仍停在 `pc=0x2b`、`steps=43` 不变，就是 `jne` 那行多了一个 0 字节，它被译码成 `halt`——回到 [例 1.4-B4](#ex-1.4-B4) 修长度。

:::
:::

::: ex 例 1.4-C4 · 依赖链与独立链 {#ex-1.4-C4}

编译 [1.4.14](ch04.md#sec-1.4.14) 的 `ilp.c`，分别跑 mode 0 与 mode 1，比较每次更新的时间。

::: sol C4 核对

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 ilp.c -o ilp
./ilp 20000000 0
./ilp 20000000 1
```

两种模式的 `sink` 是确定的：mode 0 为 `7662709483399116036`，mode 1 为 `12204093859886912516`，先用它对错实现。每次更新的时间看趋势：正文在 Apple M1、clang 15、`-O2` 下测到依赖链约 1.710 ns、四条独立链约 0.425 ns，同样的墙钟时间做了四倍更新；绝对数值随机器和频率变化，不要拿别人的数字当自己的基线。解释要点：独立链的乘法不比依赖链快，是四条链之间没有 RAW，发射宽度才用得上。

:::
:::

::: ex 例 1.4-C5 · 分支可预测性实验 {#ex-1.4-C5}

编译 [1.4.15](ch04.md#sec-1.4.15) 的 `bpred.c`，跑随机数据与排序数据两次。

::: sol C5 核对

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 bpred.c -o bpred
./bpred 0
./bpred 1
```

两次的 `sum` 必须相同，正文里是 `100450803`；不同就说明你改坏了。时间上排序版本明显更快（正文的一次运行是 5.770 ms 对 0.518 ms），因为随机比较没有可供预测器利用的历史，而排序后变成一长串同方向。想拿到 miss 率的直接证据要在 Linux 虚拟机里做下一题；没有 `perf` 时，这个时间差本身就是证据。

::: ex 例 1.4-C6 · 用 perf stat 读流水线瓶颈 {#ex-1.4-C6}

在 Linux 虚拟机里对上面两个程序跑 `perf stat`，说出瓶颈类型。（macOS 上没有 `perf`，这一步必须在 Linux 里做。）

::: sol C6 核对

```bash
perf stat -e cycles,instructions,branches,branch-misses ./bpred 0
perf stat -e cycles,instructions,branches,branch-misses ./bpred 1
perf stat -d ./ilp 200000000 0
cat /proc/sys/kernel/perf_event_paranoid
```

读法按四步走：① IPC = instructions/cycles，先跟理论上限比；② IPC 低先看 `branch-misses` 占比，再看 `stalled-cycles-frontend`（取指/译码供不上）与 `stalled-cycles-backend`（执行/访存）；③ IPC 高但仍慢，看 `cycles` 与耗时之比推出的实际频率，再看缓存与 TLB 缺失；④ 需要细粒度就用 `-e` 指定事件。若事件显示 not supported，把 `perf_event_paranoid` 调低或加 `sudo`；只想限定用户态用 `-e instructions:u`。两项都跑完后，你应该能用一句话说清「`bpred 0` 是分支受限、`ilp` 依赖链版是延迟受限」，并解释为什么不能靠换更大的 ROB 解决后者。
