性能优化最容易犯的错误是「凭直觉改代码」。直觉通常盯着指令条数，而现代 CPU 的瓶颈在依赖链、缓存缺失、分支失败、内存带宽——这四者与指令条数的关系都很弱。一个循环从 100 条指令减到 80 条，可能毫无变化；把一条依赖链拆成四条，可能直接快 4 倍。

这一章讲一套可复现的方法：先定义度量，再找瓶颈，再针对瓶颈改写，最后用同一基准验证。所有例子都以 x86-64、GCC 13 `-O2` 为背景；ARM64 的结论类似，延迟数字不同。文中的「周期」指 CPU 核心时钟周期，具体纳秒数随频率变化。

前置提醒：优化必须在**正确性**之后。开启 `-ffast-math`、手写无分支、改变求和顺序，都可能改变浮点结果；涉及金额、科学计算、可复现性时，先确认误差预算。

## 1.5.1 度量：CPE、延迟与吞吐 {#sec-1.5.1}

这一节回答：说「优化后快了 3 倍」时，这个 3 倍是怎么量出来的？为什么同一段代码换一台机器，数字就对不上？

::: preview 先抓住一件事
性能不是单个数字，而是「机器 + 输入 + 计时口径」下的一组数。先固定口径，再谈快慢；没有口径的「快 3 倍」不可复现。
:::

先跑一条会被拒绝的命令：

<div class="terminal" data-title="bash · Ubuntu 24.04 aarch64">
<pre><span class="p">&#36;</span> perf stat -e cycles true
Error:
No supported events found.
Access to performance monitoring and observability operations is limited.
...
perf_event_paranoid setting is 4:
</pre>
</div>

这台 VM 的 `perf_event_paranoid` 是 4，普通账户连 `task-clock` 这类软件事件都拿不到。于是本节不用周期做单位，改用墙钟时间除以元素个数：**ns/elem**。两者的关系是

$$
\text{CPE}=\frac{C(n)}{n},\qquad
\text{ns/elem}=\frac{T(n)}{n}\times 10^9.
$$

CPE（cycles per element，每元素周期数）的分子 $C(n)$ 是总周期数，分母是元素个数；只有能读周期计数器时才算得出来。ns/elem 的分子 $T(n)$ 是总时间（秒）。二者都描述「摊到每个元素上的成本」，但**不能混着比**：同一台机器上知道频率后，0.5 ns/elem 可以换算成 CPE；换了频率，换算系数就变了。跨机器只比 ns/elem，等于把频率与微架构的差异一起吞掉。若循环有固定启动开销 $c$，总周期数可写成 $c+kn$，CPE 随 $n$ 增大趋近 $k$；所以 $n$ 要足够大，启动开销才不会盖过斜率。本节以及后面标「VM 实测」的数字，机器都是这台 Ubuntu 24.04.5 aarch64；换机器只比较趋势，不比较绝对值。

**先分清延迟和吞吐。** 延迟（latency）是一条操作从输入到结果的时间；吞吐（throughput）是单位时间能完成多少条互相独立的操作。下一次操作必须等上一次结果，你受延迟限制；多条操作互不依赖，你受吞吐限制。

用 4 MiB 的 `uint32_t` 数组做对照：一种顺序求和，一种按随机单环逐跳追逐。

```c
/* 顺序：地址由 i 算出，每次 load 互不依赖 */
for (size_t i = 0; i < n; i++) s += a[i];
/* 追逐：下一次 load 的地址来自上一次 load 的结果 */
for (size_t i = 0; i < n; i++) p = next[p];
```

VM 实测（Ubuntu 24.04.5 aarch64，GCC 13.3 `-O2`，9 次取最小）：

| 访问方式 | 4 MiB 工作集 | 成本类型 |
|:--|--:|:--|
| 顺序求和 | 0.47–0.50 ns/elem | 吞吐型，可重叠 |
| 随机追逐 | 2.2–2.6 ns/hop | 延迟型，必须等 |

顺序循环的地址独立，CPU 可以同时发多条 load；追逐的下一条地址要等上一条数据回来，只能串行。两者相差约 5 倍，但**这个倍数不是普适常数**。把追逐的工作集从 256 KiB 加到 4 MiB、64 MiB，同一台 VM 上是 0.95、2.22、18.97 ns/hop：工作集越大，单次等待越长。这个实验不需要任何 PMU（performance monitoring unit，性能监控单元）事件。

**再看指令级并行。** 对 512 KiB 的 `double` 数组求和，单累加器与四累加器：

```c
double s = 0;
for (i = 0; i < n; i++) s += a[i];            /* 一条依赖链 */
double s0=0,s1=0,s2=0,s3=0;
for (i = 0; i + 4 <= n; i += 4) {             /* 四条独立链 */
    s0 += a[i]; s1 += a[i+1]; s2 += a[i+2]; s3 += a[i+3];
}
```

VM 实测：单累加器 0.63 ns/elem，四累加器 0.16 ns/elem，约 3.9 倍。加法总数没变，变的是从「等上一次加法」改成「四条链并行」。这就是 [1.5.5](#sec-1.5.5) 与 [1.5.6](#sec-1.5.6) 要展开的 ILP（instruction-level parallelism，指令级并行）。

**计时口径要写全。** 本节所有循环都用同一个骨架：

```c
for (int r = 0; r < 9; r++) {
    uint64_t t0 = now_ns();
    result = work(data, n);
    uint64_t t1 = now_ns();
    if (t1 - t0 < best) best = t1 - t0;    /* 取最小值，不取平均 */
}
printf("%.3f ns/elem\n", (double)best / n);
```

`clock_gettime(CLOCK_MONOTONIC)` 给墙钟；`CLOCK_PROCESS_CPUTIME_ID` 或 `getrusage` 的 `ru_utime`/`ru_stime` 给 CPU 时间；`/proc/PID/schedstat` 的第二字段给「在运行队列里等了多久」。一次 64 MiB 追逐的 `/usr/bin/time -v` 输出：

```text
Ubuntu 24.04.5 aarch64 实测，一次运行：
User time (seconds): 3.55
System time (seconds): 0.01
Percent of CPU this job got: 99%
Elapsed (wall clock) time (h:mm:ss or m:ss): 0:03.56
Involuntary context switches: 47
```

用户态 3.55 s、系统态 0.01 s，说明几乎不进内核；墙钟 3.56 s 与 CPU 时间几乎相同，47 次非自愿切换没有造成明显等待。在更忙的机器上，这一项会变大，所以取最小值、重复多轮。

::: def 定义 1.5.1 · 关键路径（critical path） {#def-1.5.1}
数据依赖图中从循环入口到出口的最长路径。CPE 不可能低于关键路径上各操作延迟之和除以迭代次数；多累加器、循环展开、重结合（reassociation）的本质，都是把一条长链拆成多条短链。
:::

::: ex 例 1.5.1 · 先猜再跑 {#ex-1.5.1}
同一台 VM、同一个 4 MiB 数组：顺序求和 0.47–0.50 ns/elem。改成随机单环追逐，先猜每次多少 ns、慢几倍；再猜工作集换成 64 MiB 后是多少。

::: sol 解答
4 MiB 追逐实测 2.2–2.6 ns/hop，约 5 倍；64 MiB 是 18.97 ns/hop，约 40 倍。猜 2 倍的人通常只想到「多一次跳转」，漏掉了「下一次地址依赖上一次数据」；猜 100 倍的人则把最坏情况当成了平均值。
:::
:::

::: errata 关于性能度量的四个误解
1. **「CPE 可以跨机器直接比」**——CPE 含频率与微架构；只有同机前后对比才有意义。
2. **「取平均比取最小更客观」**——平均把调度、频率爬升、中断都算进来；比较硬件上限用最小值，描述用户体验才看分布（p50 是中位数，p99 是 99% 请求都不超过的值）。
3. **「跑一次就够了」**——冷缓存、频率未爬升、编译器还没热，第一次通常偏慢；至少预热一轮，再重复 5–9 次。
4. **「perf 不能跑就没有数据」**——墙钟、CPU 时间、`ru_utime`/`ru_stime`、`schedstat` 的 `run_delay` 都不需要 PMU；它们回答不了流水线利用率，但能回答「慢在哪一段」。
:::

### 1.5.1 小结

① 先固定机器、输入、计时口径，再谈倍数；② CPE 是周期口径，本机拿不到周期，就报 ns/elem 并标机器；③ 延迟看依赖链，吞吐看独立操作，工作集大小会改变等待成本。如果只记住一件事，那就是：**没有口径的性能数字，只是一句口号。**

::: method 即时自测 · 1.5.1
**Q1（记忆）** CPE 的分子和分母各是什么？没有 PMU 时，本节用什么替代？
**Q2（辨析）** 顺序求和 0.47 ns/elem，随机追逐 2.2 ns/hop。为什么不能把这两个数直接当成「随机访问慢 4.7 倍」的普适结论？
**Q3（应用）** 单累加器 0.63 ns/elem，四累加器 0.16 ns/elem。加法次数变了吗？为什么反而更快？

::: sol 答案
**A1** 分子是总周期数 $T$，分母是元素个数 $n$；没有 PMU 时用墙钟时间除以 $n$，单位 ns/elem。
**A2** 2.2 ns/hop 对应 4 MiB 工作集；换成 64 MiB 时同一台机器是 18.97 ns/hop。倍数随工作集变，不是常数。
**A3** 加法总次数不变；四条累加链互不依赖，CPU 可以同时发射，把「等上一次结果」的串行链拆成四条并行链。
:::
:::

## 1.5.2 编译器能做什么、不能做什么 {#sec-1.5.2}

这一节回答：编译器在 `-O2` 下已经会做常量传播、死代码消除、公共子表达式消除、强度削减、循环不变量外提、内联和指令调度，为什么它不肯把你写的循环直接变成向量指令？

::: preview 先抓住一件事
编译器只做「不改变可观察行为」的变换。别名、外部调用、未定义行为（undefined behavior，UB，语言标准不规定结果的行为）是三道闸；`restrict` 是你签字放弃别名假设，签错就错，不是一句「优化提示」。
:::

看同一个函数的两版：

```c
void scale_plain(double *a, const double *b, size_t n)
{
    for (size_t i = 0; i < n; i++)
        a[i] = a[i] * 2.0 + b[i];
}

void scale_restrict(double *restrict a, const double *restrict b, size_t n)
{
    for (size_t i = 0; i < n; i++)
        a[i] = a[i] * 2.0 + b[i];
}
```

`a` 和 `b` 都指向 `double`，编译器必须假设它们可能重叠：写 `a[i]` 可能改到后面要读的 `b[j]`。所以 `-O2` 下两版生成同一种标量循环（Ubuntu 24.04 aarch64，GCC 13.3 实测）：

```asm
ldr d0, [x0, x3, lsl 3]      # a[i]
ldr d1, [x1, x3, lsl 3]      # b[i]
fadd d0, d0, d0
fadd d0, d0, d1
str d0, [x0, x3, lsl 3]      # 写回 a[i]
add x3, x3, 1
cmp x2, x3
bne .L3
```

每个元素 8 条指令，没有向量化。换到 `-O3`，差别出现了：`scale_restrict` 直接进入一次处理两个 `double` 的循环；`scale_plain` 先插一段运行时检查，检查不过就退回上面的标量循环，通过才走向量路径。`restrict` 的作用不是「打开优化开关」，而是**删掉这次运行时检查**，让编译器从第一行就按「不重叠」生成代码。

```asm
# scale_restrict 的 -O3 内层：q 寄存器一次装两个 double
ldr q0, [x0, x3]
ldr q1, [x1, x3]
fadd v0.2d, v0.2d, v0.2d
fadd v0.2d, v0.2d, v1.2d
str q0, [x0, x3]
add x3, x3, 16
cmp x3, x4
bne .L23
```

同样 8 条指令，现在处理两个元素。**同一份 C，只差一个关键字，生成两套代码。**

但 `restrict` 是承诺，不是请求。两个指针真的重叠时，行为未定义。下面故意让 `b[i]` 指向上一轮刚被写过的 `a[i-1]`：

```c
double arr[8] = {1,2,3,4,5,6,7,8};
scale_plain(arr + 1, arr, 7);       /* a=arr+1, b=arr */
/* 另一份 buf 上调用 scale_restrict(buf + 1, buf, 7) */
```

VM 实测（Ubuntu 24.04.5 aarch64，`-O3`）：

```text
plain   : 1 5 11 19 29 41 55 71
restrict: 1 5 8 11 14 17 20 23
```

`plain` 按顺序算：第二轮读到的 `b[1]` 是第一轮刚写过的 5。`restrict` 版一次装两个元素，读的是写之前的旧值，于是从第三个数开始分叉。**这不是「优化没生效」，是程序违反了承诺，编译器按承诺生成的代码不再符合顺序语义。** 换个编译器可能给出别的结果；UB 没有「正确输出」可言。

::: ex 例 1.5.2 · 先猜哪个结果对 {#ex-1.5.2}
`arr` 初值 1–8，`a = arr+1`、`b = arr`、`n = 7`。先手算 `scale_plain` 的输出，再猜 `scale_restrict` 在 `-O3` 下会不会不同、从第几个数开始不同。

::: sol 解答
手算：`arr[1]=2*2+1=5`，`arr[2]=3*2+5=11`，`arr[3]=4*2+11=19`，得到 1 5 11 19 29 41 55 71。`restrict` 版实测 1 5 8 11 14 17 20 23：它一次读入两个旧值再写回，从第三个数（8 而不是 11）开始偏离。差异来自「先读后写」与「边读边写」的顺序，不是浮点误差。
:::
:::

**函数调用**是第二道闸。编译器若能证明一个调用不写内存、结果只依赖参数，就可以把它提出循环；证明不了就只能每次调用。`strlen` 是最常见的例子：[1.5.3](#sec-1.5.3) 会用一台 VM 上的实测展示「能证明」与「经过函数指针后证明不了」的差别。

**内联**让小函数消失，把调用开销变成指令调度机会。`static inline` 只是建议，编译器有权拒绝；`-flto`（链接时优化）能跨 `.c` 文件内联；`always_inline` 可以强制，但滥用会让代码膨胀、I-cache 压力上升。判断是否内联，看 `objdump` 里循环内还有没有 `bl`，而不是看源码写没写 `inline`。

::: errata 关于编译器优化的五个误解
1. **「`-O3` 一定比 `-O2` 快」**——`-O3` 的向量化与展开可能增加代码体积、降低指令缓存（I-cache）命中；本例在 `-O2` 下两版完全相同，`-O3` 才分叉。要实测。
2. **「`restrict` 只是提示，违反最多不优化」**——它是承诺；违反是未定义行为，实测已经算出不同结果。
3. **「`inline` 一定展开」**——`inline` 是建议；递归函数、取地址的函数、过大的函数通常不会展开。
4. **「`volatile` 能让代码更快/更安全」**——它只保证每次访问都真的发生，阻止编译器缓存；不提供原子性，也不提供内存屏障，通常让性能变差。
5. **「编译器会自动把 `a*a*a*a` 变成 `(a*a)*(a*a)`」**——浮点下不会，改变结合顺序会改变结果（除非 `-ffast-math`）；有符号整数溢出是 UB，编译器可能重排，但不能依赖。
:::

### 1.5.2 小结

① 编译器在「不改变可观察行为」的范围内很强，别名、外部调用、UB 是边界；② `restrict` 是承诺不是开关，违反承诺结果就错；③ 判断内联与向量化看汇编，不看源码关键字。如果只记住一件事，那就是：**先保证语义，再谈让编译器放手。**

::: method 即时自测 · 1.5.2
**Q1（记忆）** `restrict` 向编译器承诺了什么？违反承诺的后果是什么？
**Q2（辨析）** 同一份 `scale` 代码，`-O2` 下两版汇编相同，`-O3` 下才分叉。为什么优化级别会改变「别名」的影响？
**Q3（应用）** 你把 `scale_restrict` 用在两个确实重叠的数组上，得到的结果与顺序版本不同。这是编译器 bug 吗？应该怎么改？

::: sol 答案
**A1** 承诺两个 `restrict` 指针访问的对象不重叠；违反是未定义行为，编译器可以按不重叠生成代码，结果可能错。
**A2** `-O2` 没有做这条向量化，别名不构成阻碍；`-O3` 想一次处理两个元素，必须先排除重叠，`restrict` 让编译器省掉运行时检查与标量回退。
**A3** 不是；程序违反了语言契约。去掉 `restrict`，或保证两个数组不重叠（例如先复制到独立缓冲区）再调用。
:::
:::

## 1.5.3 消除循环低效与重复计算 {#sec-1.5.3}

这一节回答：循环体里只多用了一次 `strlen(s)`，为什么字符串从 4 KiB 长到 64 KiB，时间会从微秒变成几十毫秒？

::: preview 先抓住一件事
优化的第一步不是展开，而是删掉不必要的工作。编译器能证明时会替你搬出循环，证明不了就自己搬；O(n²) 常常不是算法写错，而是一次「看起来无害」的重复调用。
:::

看同一段求和的三种写法：

```c
/* A：直接写 strlen */
for (size_t i = 0; i < strlen(s); i++) sum += (unsigned char)s[i];

/* B：把 strlen 藏进 volatile 函数指针，编译器看不透 */
size_t (*volatile len)(const char *) = strlen;
for (size_t i = 0; i < len(s); i++) sum += (unsigned char)s[i];

/* C：先取长度 */
size_t n = strlen(s);
for (size_t i = 0; i < n; i++) sum += (unsigned char)s[i];
```

VM 实测（Ubuntu 24.04.5 aarch64，GCC 13.3 `-O2`，重复多趟取总时间再摊平；4 KiB 跑 100 趟，64 KiB 跑 20 趟）：

| 字符串长度 | A 直接 `strlen` | B 函数指针 | C 先取长度 |
|--:|--:|--:|--:|
| 4 KiB | 1.15 µs/趟 | 201 µs/趟 | 1.15 µs/趟 |
| 64 KiB | 20.4 µs/趟 | 40.7 ms/趟 | 18.7 µs/趟 |

A 和 C 几乎一样，因为编译器把 `strlen(s)` 提到了循环外；B 慢了 175 倍（4 KiB）到 2000 倍（64 KiB）。看汇编最清楚：

```asm
# A：strlen 在循环外只调用一次
bl strlen
.Lloop:
    ldrb w2, [x1], #1
    add x0, x0, x2
    cmp x1, x3
    b.ne .Lloop

# B：循环体里每次 blr，重新扫描整串
.Lloop2:
    blr x1
    cmp x0, x19
    b.hi .Lloop2
```

B 的 `len(s)` 每轮都从 `s` 开头扫到结尾，n 轮共扫 n×n 个字节，总工作量是 $O(n^2)$。A 能变快，是因为编译器知道 `strlen` 不写内存、结果只依赖参数，于是把它当成循环不变量；一旦调用经过 `volatile` 函数指针，编译器不敢再假设，只能每轮真调。C 是手动版，无论编译器能不能证明都成立；但若循环体真的会修改 `s`，长度就会变，C 的前提不成立，必须重新计算或先复制一份。

**第二类重复计算在依赖链上。** 下面两行都做「线性同余 + 取模」，`m` 是 2 的幂但在运行期才知道：

```c
x = (x * 1103515245u + 12345u) % m;       /* 除法 */
x = (x * 1103515245u + 12345u) & (m - 1); /* 位与 */
```

VM 实测（4 Mi 次迭代，`m = 1<<20`）：取模 3.7–3.9 ns/次，位与 1.3 ns/次，约 3 倍。汇编里取模是 `udiv` 加 `msub`，位与只是一条 `and`；更关键的是 `x` 的下一轮依赖这一轮结果，除法延迟直接压在关键路径上。反过来，如果被除的数不进入下一轮（比如独立的 `i % m`），同一台 VM 上两者都是 0.47–0.50 ns/次，差别消失——**不是 `%` 天生慢，是它挡在依赖链上才慢**。

::: ex 例 1.5.3 · 先猜慢多少 {#ex-1.5.3}
同样 4 KiB 字符串，A（直接 `strlen`）是 1.15 µs/趟。把 `strlen` 藏进 `volatile` 函数指针（B），先猜慢几倍；再猜字符串换成 64 KiB 时倍数会变大还是变小。

::: sol 解答
4 KiB 实测 201 µs/趟，约 175 倍；64 KiB 是 40.7 ms/趟，约 2000 倍。倍数随 `n` 增大，因为 B 是 O(n²)、A 是 O(n)；字符串翻 16 倍，时间约翻 256 倍。猜「固定慢几倍」的人，把每次调用的开销当成了常数，漏掉了每次调用扫描的字节数也在变。
:::
:::

::: errata 关于循环低效的五个误解
1. **「编译器一定会把 `strlen` 提出循环」**——只有它能证明字符串不被修改时才敢；经过函数指针、外部调用或 `volatile` 就不敢。
2. **「把 `%` 换成 `&` 一定快」**——只有在依赖链上才明显；独立取模实测没有差别。
3. **「循环展开总是更快」**——展开会增加代码体积与寄存器压力，尾部处理也更容易写错；[1.5.5](#sec-1.5.5) 会给边界。
4. **「重复调用只是多几条指令」**——`strlen` 每轮重扫会把 O(n) 变成 O(n²)，量级变了。
5. **「先取长度一定安全」**——循环体若修改字符串，缓存的长度就过期；要么重新计算，要么先复制一份只读快照。
:::

### 1.5.3 小结

① 先把循环不变量、重复调用、低效抽象移出去；② 编译器能证明时自动做，证明不了就手写，手写版要保证语义不变；③ 取模与位与的差距只在依赖链上显现。如果只记住一件事，那就是：**先删工作，再谈调度。**

## 1.5.4 减少调用与消除不必要的内存引用 {#sec-1.5.4}

这一节回答：循环里每轮调用一个带边界检查的小函数、每轮写回同一个指针，真的会让程序变慢吗？为什么有时改了却没差别？

::: preview 先抓住一件事
调用本身不贵，贵的是它挡住了优化；内存引用也不总贵，贵的是它反复打断依赖链或阻止向量化。先看汇编，再决定改不改。
:::

先看一个「逐元素取数」的接口：

```c
struct ivec { size_t len; const int *data; };

__attribute__((noinline)) int get(const struct ivec *v, size_t i)
{
    if (i >= v->len) abort();          /* 每次调用都检查 */
    return v->data[i];
}

long sum_get(const struct ivec *v)
{
    long s = 0;
    for (size_t i = 0; i < v->len; i++) s += get(v, i);
    return s;
}

long sum_direct(const struct ivec *v)
{
    long s = 0;
    const int *a = v->data;
    for (size_t i = 0; i < v->len; i++) s += a[i];
    return s;
}
```

VM 实测（Ubuntu 24.04.5 aarch64，GCC 13.3 `-O2`，9 次取最小）：`sum_get` 是 0.47–0.73 ns/elem，`sum_direct` 是 0.23–0.25 ns/elem，差 2–3 倍。汇编里原因很直接：

```asm
# sum_get：每轮一次调用
.Lloop:
    bl get
    ...
    b.ne .Lloop

# sum_direct：一次装 4 个 int，向量累加
.Lloop2:
    ldr q1, [x0], #16
    saddw v0.2d, v0.2d, v1.2s
    ...
    b.ne .Lloop2
```

`get` 每轮都要重新比较下标、跳转、返回；更关键的是，调用把循环切成了「一次只处理一个元素」的形状，编译器没法向量化。把边界检查提到循环外、暴露连续指针，或提供批量接口，都能让循环回到右边那种形状。这里用 `noinline` 是故意的：真实代码里编译器可能内联，差别就会缩小；**先 `objdump` 看循环里还有没有 `bl`，再决定要不要手改**。

**再看内存引用。** 同一个累加，写成「每轮写回 `*dest`」与「先放局部变量」：

```c
__attribute__((noinline)) void add_mem(double *dest, const double *src, size_t n)
{
    for (size_t i = 0; i < n; i++) *dest += src[i];
}

__attribute__((noinline)) void add_reg(double *dest, const double *src, size_t n)
{
    double acc = *dest;
    for (size_t i = 0; i < n; i++) acc += src[i];
    *dest = acc;
}
```

为了把这条内存引用的代价单独放大，先用 `-O1` 编译（它不做标量替换），再看 `-O2`。VM 实测（2 MiB 源数组，9 次取最小）：`-O1` 下 `add_mem` 2.20、`add_reg` 0.61 ns/elem，差 3.6 倍；`-O2` 下两版都是 0.57–0.60 ns/elem，差别落进噪声。

`-O1` 的循环每轮都读一次 `*dest`、写一次 `*dest`；`-O2` 把读提到了循环外，只保留每轮写回：

```asm
# -O1：读、加、写都在循环里
.L3:
    ldr d0, [x0]
    ldr d1, [x1], 8
    fadd d0, d0, d1
    str d0, [x0]
    cmp x3, x1
    b.ne .L3

# -O2：读提到循环外，循环里只剩写
ldr d0, [x0]
.L18:
    ldr d1, [x1], 8
    fadd d0, d0, d1
    str d0, [x0]
    cmp x1, x2
    b.ne .L18
```

把「每轮读内存变量」改成「寄存器里累加、最后写回一次」，叫标量替换（scalar replacement）。`-O1` 没做，手写版就快 3.6 倍；`-O2` 已经替你做了一半（读已提出），手写版只剩「少写回几次」，在这台机器上落进噪声。**这不是说标量替换没用，而是说：先确认编译器做到哪一步，再决定手写哪一半。**

::: ex 例 1.5.4 · 先猜哪一档会消失 {#ex-1.5.4}
`add_mem` 在 `-O1` 下比 `add_reg` 慢 3.6 倍。先猜：换到 `-O2`，这个差距会保留、缩小，还是消失？再猜 `sum_get` 与 `sum_direct` 的差距会不会也消失。

::: sol 解答
`-O1` 的差距来自每轮多一次 `*dest` 读取与写回；`-O2` 把读取提到循环外，实测两版都是 0.57–0.60 ns/elem，差距消失。`sum_get` 的差距不会消失：`-O2` 仍不敢把带边界检查的 `get` 内联（这里用 `noinline` 固定住），循环仍是「一次一个元素 + 一次调用」；把检查提出去、暴露连续指针后才回到向量化形状。
:::
:::

::: errata 关于调用与内存引用的四个误解
1. **「函数调用只有几纳秒，内联一定划算」**——调用会挡住向量化与循环变换；实测的 2–3 倍主要来自「循环形状被切碎」，不是那几条跳转指令。
2. **「编译器总会做标量替换」**——`-O2` 对 `*dest += src[i]` 会提读取，但 `-O1` 不会；遇到不透明调用、`volatile` 或复杂别名，`-O2` 也可能保守。
3. **「手写局部变量一定更快」**——`-O2` 下实测两版一样；手写是给「编译器不敢」的场景兜底，不是万能加速键。
4. **「内存引用一定比寄存器慢」**——同一个地址的 store 后紧接 load 可由 store buffer（存储缓冲，store 先排队再写入缓存）转发，未必慢；真正贵的是它出现在依赖链上，或让编译器不敢重排。
:::

### 1.5.4 小结

① 先看调用是否把循环切碎、挡住向量化，再看那几纳秒的调用开销；② 内存引用要看它是否在依赖链上，`-O2` 常已做标量替换；③ 手写局部变量、批量接口、`restrict` 都是「让编译器看见不重叠/连续」的手段。如果只记住一件事，那就是：**优化的是循环形状，不是源码行数。**

::: method 即时自测 · 1.5.4
**Q1（记忆）** 什么是标量替换？本节哪个编译选项已经替我们做了一半？
**Q2（辨析）** `sum_get` 比 `sum_direct` 慢 2–3 倍。差距主要来自「调用指令本身」还是「调用阻止了优化」？用汇编证据说明。
**Q3（应用）** 你的热点循环每轮调用 `check_and_get(i)`，函数里检查 `i < len` 后返回 `data[i]`。改哪三处最可能有效？

::: sol 答案
**A1** 把反复读写的内存变量提升到寄存器，循环结束再写回；`-O2` 已把 `*dest` 的读取提到循环外。
**A2** 主要是后者：`sum_get` 每轮 `bl get`，循环一次只处理一个元素；`sum_direct` 用 `ldr q1` + `saddw` 一次处理四个。调用指令只有几条，但它让编译器失去了向量化的循环形状。
**A3** 把边界检查提到循环外（先验证一次 `len`）、暴露连续指针或批量接口、让 `get` 可内联（去掉 `noinline`/跨文件障碍，或改宏/内联函数）。
:::

## 1.5.5 循环展开与多累加器 {#sec-1.5.5}

这一节回答：把循环体复制四份、把 `s +=` 拆成四个变量，哪一步才是循环真正变快的原因？

::: preview 先抓住一件事
展开只摊薄比较、跳转、指针更新这几条控制指令；四份加法仍写在同一个累加器上，依赖链一点没短。把一条链拆成四条互不相干的链，才动到关键路径。
:::

同一份数据、同一个求和，四种写法。数组 512 KiB（65536 个 `double`），每种跑 9 趟取最小：

```c
/* A：不展开，一条链 */
for (size_t i = 0; i < n; i++) s += p[i];

/* B：展开 4 次，仍是一条链 */
for (; i + 4 <= n; i += 4)
    { s += p[i]; s += p[i+1]; s += p[i+2]; s += p[i+3]; }

/* C：展开 4 次，4 个累加器 */
for (; i + 4 <= n; i += 4)
    { s0 += p[i]; s1 += p[i+1]; s2 += p[i+2]; s3 += p[i+3]; }
```

VM 实测（Ubuntu 24.04.5 aarch64，GCC 13.3，9 次取最小）：

| 写法 | 累加器 | `-O2` ns/elem | `-O2 -fno-tree-vectorize` ns/elem |
|:--|--:|--:|--:|
| A 不展开 | 1 | 0.523 | 0.526 |
| B 展开 4 次 | 1 | 0.521 | 0.533 |
| C 展开 4 次 | 4 | 0.144 | 0.158 |
| C' 展开 8 次 | 8 | 0.077 | 0.087 |

B 与 A 几乎相同，展开看起来白做了。原因是展开省下的东西本来就便宜：每 4 个元素少 3 次比较和跳转，摊到每个元素不到一条指令。循环里的主成本是每个元素一次 load 加一次加法，而加法要等上一次加法的结果。

C 快了 3.6 倍，靠的不是「一次处理四个」，而是四条加法写进了四个不同变量。看汇编，差别只在目标寄存器：

```asm
# B：4 条 fadd 全写 d0，仍是一条依赖链
fadd d0, d0, d1
fadd d0, d0, d3
fadd d0, d0, d2
fadd d0, d0, d1
# C：4 条 fadd 写 d1/d3/d0/d2，互不等待
fadd d1, d1, d7
fadd d3, d3, d6
fadd d0, d0, d5
fadd d2, d2, d4
```

一台机器上「四条链」是否够用，取决于一次浮点加的延迟和吞吐之比。这里 8 条链又比 4 条快 1.9 倍，说明 4 条还没把延迟藏满；[1.5.6](#sec-1.5.6) 会用链数扫描把这个上限测出来，而不是照抄一张延迟表。

::: def 定义 1.5.5 · 循环展开（loop unrolling） {#def-1.5.5}
把 $k$ 次迭代的循环体合并成一份，$k$ 叫展开因子（unroll factor）。展开不改变数据依赖图；只有把 $k$ 份计算写进 $k$ 个不同累加器，关键路径才从「$k$ 次串行」变成「$k$ 条并行」。展开因子与累加器个数是两个独立参数，可以只加一个。
:::

代价有三样。第一，尾部：`i + 4 <= n` 之后的 0–3 个元素要单独收尾，写错就漏算。第二，寄存器：8 个累加器加地址、长度、临时值，寄存器不够时编译器会把累加器溢出到栈上，收益归零。第三，浮点结果会变：四个部分和最后合并的顺序不同，末位可能差 1 ulp；要逐位复现时不能这么改。整数版本还会遇到有符号溢出的未定义行为，想让回绕成立就用无符号类型。

::: ex 例 1.5.5 · 先猜哪一版快 {#ex-1.5.5}
A 是 0.523 ns/elem。先猜 B（展开 4 次、单累加器）会快多少；再猜 C（4 个累加器）是 2 倍、4 倍还是更多。

::: sol 解答
B 实测 0.521，基本没变；C 是 0.144，约 3.6 倍。猜 B 快 4 倍的人把「指令少了」当成「依赖短了」——展开后仍是 `s` 等 `s`，每条加法要等前一条算完（这台机器上单链就是 0.57 ns/次）。猜 C 只有 2 倍的人，低估了单链时 CPU 大部分时间在空等。
:::
:::

::: errata 关于展开的四个误解
1. **「展开越多越快」**——超过寄存器与 I-cache 能承受的范围就退化；本例 8 条仍赚，是因为这台机器浮点吞吐高，换一台可能 4 条就到顶。
2. **「`-O2` 会自动做浮点多累加器」**——不会。改变加法结合顺序会改变结果，编译器必须等你写 `-ffast-math` 或自己拆变量。
3. **「多累加器与顺序累加结果相同」**——浮点下部分和合并顺序不同，末位可能不同；要可复现就先固定合并顺序并记录。
4. **「展开能顺带向量化」**——`-O2` 本来就向量化，展开的收益要和 `-fno-tree-vectorize` 对照才分得清。
:::

### 1.5.5 小结

① 展开省的是循环控制，多累加器拆的是依赖链，两者别混为一谈；② 收益上限由「延迟 ÷ 吞吐」和寄存器数量共同决定，要测不要背；③ 尾部、浮点顺序、有符号溢出是三个必须交代的代价。如果只记住一件事，那就是：**先画依赖链，再决定展开几次、开几个累加器。**

::: method 即时自测 · 1.5.5
**Q1（记忆）** 展开因子和累加器个数分别改变什么？哪一个会缩短关键路径？
**Q2（辨析）** B 版展开了 4 次却和 A 一样快。用汇编说明原因。
**Q3（应用）** 你把 8 累加器版本放进一个只有 16 个通用寄存器的 32 位目标上，实测反而变慢。最可能发生了什么？

::: sol 答案
**A1** 展开因子减少循环控制指令的条数；累加器个数决定依赖链的条数。只有后者缩短关键路径。
**A2** B 的 4 条 `fadd` 目标都是 `d0`，每条都要等上一条；展开只少了比较和跳转，而这两项摊到每个元素不到一条指令。
**A3** 寄存器不够，编译器把部分累加器溢出到栈，循环里多了 load/store；另外代码体积变大也可能压低 I-cache 命中。

## 1.5.6 ILP、关键路径与延迟界 {#sec-1.5.6}

这一节回答：为什么把一条加法链拆成两条，时间几乎正好减半，拆到八条却不再减？

::: preview 先抓住一件事
一个循环要么被关键路径的延迟卡住，要么被功能单元的吞吐卡住，取两者中更紧的那个。把链数从 1 加到 8，测出时间在什么地方不再下降，就同时量出了这台机器的延迟与吞吐。
:::

写两组内核：浮点加链、整数乘加链，每组都提供 1、2、4、8 条独立链。迭代 3355 万次，`-O2 -fno-tree-vectorize` 编译，每档跑 5 趟取最小：

```c
/* 4 条链的写法，其余档位同理 */
double a0=x, a1=x, a2=x, a3=x;
for (uint32_t i = 0; i < ITER; i++) {
    a0 += c; a1 += c; a2 += c; a3 += c;
}
```

VM 实测（Ubuntu 24.04.5 aarch64，GCC 13.3）：

| 链数 | 浮点加 ns/op | 整数乘加 ns/op |
|--:|--:|--:|
| 1 | 0.574 | 1.015 |
| 2 | 0.292 | 0.471 |
| 4 | 0.141 | 0.237 |
| 8 | 0.094 | 0.125 |

浮点加从 1 条到 2 条是 1.97 倍，2 到 4 是 2.07 倍，4 到 8 只剩 1.5 倍。前两段是延迟受限：每加一条链，就多一条能同时推进的独立工作。最后一段撞上了吞吐上限：这台机器每纳秒最多做完约 10.6 次浮点加（$1/0.094$），再开链也没用。

整数乘加不一样，4 到 8 还有 1.9 倍，到 8 条才刚接近上限 $1/0.125=8$ 次/纳秒。两条曲线的拐点不同，因为「延迟 ÷ 吞吐」不同：浮点加约 6，整数乘加约 8。

**下界怎么算。** 先画依赖图，再只把关键路径上的延迟相加；与链无关的 load、乘法可以提前算好等着，不能一起加进去。

::: thm 延迟界与吞吐界 {#thm-1.5.6}
设一次迭代的关键路径长度为 $L$（单位：拍），拆成 $k$ 条互不依赖的链，功能单元每拍能完成 $T$ 次该操作，则
$$
\mathrm{CPE}\ \ge\ \max\!\left(\frac{L}{k},\ \frac{1}{T}\right).
$$
$k$ 增加到 $k \ge L\cdot T$ 以后，下界由吞吐项接管，继续加链没有收益。
:::

拿它读上面的数：单链 0.574 ns/op 是 $L$ 折算成时间的实测值，8 条链的 0.094 是 $1/T$ 折算成时间的实测值，两者之比 6.1 与单位无关，就是「要几条链才饱和」。这比背一张延迟表可靠：同一份代码换一台机器，$L$ 和 $T$ 都会变。

**最常见的算错法**是把「load 延迟 + 乘延迟 + 加延迟」全加起来。`s += a[i]*b[i]` 里，`a[i]`、`b[i]` 的 load 和乘法都不在累加链上，CPU 可以提前把它们算完；单累加器时真正的链只有 `s` 的加法。[1.5.1](#sec-1.5.1) 实测单累加器 0.63、四累加器 0.16 ns/elem，比值 3.9，和上面 4 条链的 4.07 倍对得上。

::: ex 例 1.5.6 · 先猜拐点 {#ex-1.5.6}
浮点加链从 4 条加到 8 条，先猜能快多少；整数乘加链同样从 4 加到 8，再猜一次。两题都先写下理由，再看实测。

::: sol 解答
浮点加 0.141 → 0.094，1.5 倍；整数乘加 0.237 → 0.125，1.9 倍。浮点加的单链延迟只有吞吐的约 6 倍，4 条链已经藏掉大半延迟；整数乘加是 8 倍，4 条还不够。猜「都还能翻倍」的人默认了延迟可以无限藏，忘了吞吐是硬上限。
:::
:::

::: errata 关于 ILP 的四个误解
1. **「把延迟表上的数相加就是下界」**——只有关键路径上的操作才相加；独立操作能重叠。
2. **「链开得越多越快」**——超过 $L\cdot T$ 后收益为零，还要付寄存器和代码体积的代价。
3. **「延迟是架构常数，可以照抄」**——同一指令在不同微架构上差一倍很常见；本文的数字只属于这台 VM。
4. **「指令条数少就快」**——单链版本指令最少，却最慢；限制它的是依赖，不是条数。
:::

### 1.5.6 小结

① 先画依赖图，找出真正串行的那条链；② 下界是「关键路径 ÷ 链数」与「吞吐倒数」的较大者；③ 用链数扫描实测拐点，比抄延迟表可靠。如果只记住一件事，那就是：**优化的对象是依赖链，不是指令表。**

::: method 即时自测 · 1.5.6
**Q1（记忆）** 写出延迟界与吞吐界合在一起的下界公式，并说明每个符号的含义。
**Q2（辨析）** 有人说 `s += a[i]*b[i]` 的下界是「load 4 + mul 4 + add 4 = 12 拍」。错在哪？
**Q3（应用）** 你的循环单链 0.80 ns/op，8 条链 0.10 ns/op。要开几条链才能接近饱和？再往上加有意义吗？

::: sol 答案
**A1** $\mathrm{CPE}\ge\max(L/k,\,1/T)$：$L$ 是关键路径拍数，$k$ 是独立链数，$T$ 是每拍能完成的操作数。

## 1.5.7 分支友好与无分支代码 {#sec-1.5.7}

这一节回答：同一句 `if (a[i] > 0)`，数据随机时比排好序慢四倍；改成掩码后随机数据也不慢了——该改代码，还是改数据？

::: preview 先抓住一件事
分支本身不贵，猜错才贵。现代编译器已经把简单条件变成条件选择指令，手写无分支往往只是重复它的工作；只有当「写哪里」也依赖条件时，人才有明显收益。
:::

做一个「挑出正数」的压缩：1 Mi 个 `int`（4 MiB），正负各约一半，输出到另一个数组。两版内核：

```c
/* 分支版：只在为正时写，写地址随条件变 */
for (size_t i = 0; i < n; i++)
    if (p[i] > 0) q[k++] = p[i];

/* 无分支版：先无条件写，再用比较结果推进下标 */
for (size_t i = 0; i < n; i++) {
    int v = p[i];
    q[k] = v;
    k += (v > 0);
}
```

VM 实测（Ubuntu 24.04.5 aarch64，GCC 13.3 `-O2`，7 次取最小）：

| 数据顺序 | 分支版 | 无分支版 |
|:--|--:|--:|
| 随机正负 | 1.408 ns/elem | 0.271 ns/elem |
| 升序排列后 | 0.333 ns/elem | 0.269 ns/elem |

随机数据下分支版慢 5.2 倍。看汇编，分支版内层有一条 `b.le` 跳过 store；无分支版没有随数据改变方向的分支，只有一条无条件的 `str` 和一条 `cinc`（条件自增），剩下的 `cmp`/`b.ne` 只是循环计数：

```asm
# 分支版：方向随数据变
cmp  w1, #0
b.le .Lskip
str  w1, [x2, x0, lsl 2]
add  x0, x0, #1
.Lskip:

# 无分支版：写总是发生，下标用 cinc 条件加一
str  w1, [x2, x0, lsl 2]
cmp  w1, #0
cinc x0, x0, gt
```

排好序后，分支方向只转变一次，预测器几乎不再猜错，分支版从 1.408 降到 0.333。无分支版对数据顺序不敏感，随机和有序都是 0.27 左右——它根本不猜。

**但别急着把所有 `if` 都改掉。** 换一个只求和的循环：`if (p[i] > 0) s += p[i];` 与手写掩码版 `s += v & ~(v >> 31);`，实测 0.252 与 0.256 ns/elem，没有差别。因为 `-O2` 已经把前者的 `if` 转成 `cmgt` + `and`，还顺手向量化了：

```asm
cmgt v1.4s, v0.4s, #0      # 生成掩码
# 这里省略 4 条 sxtl/sxtl2，把 32 位掩码扩成 64 位
and  v3.16b, v3.16b, v4.16b # 按掩码清零
add  v2.2d, v2.2d, v3.2d    # 累加
```

两版最后生成同一种形状，手写掩码只是把编译器做过的事又写了一遍。**先 `objdump` 看有没有 `b.*`，再决定要不要手改。**

::: def 定义 1.5.7 · 分支预测失败（branch misprediction） {#def-1.5.7}
CPU 在分支结果出来前就沿预测方向取指执行。猜错时要丢弃已做的工作、从正确地址重新取指，这段空转叫预测失败惩罚。惩罚的拍数随微架构变，本文不引用具体拍数，只比较同一台机器上的墙钟。
:::

三个方向，按代价从低到高排：

1. **改数据顺序**：把同类的键排在一起、分桶、先分区再处理。排序本身是 $O(n\log n)$，只在「同一批数据要扫很多遍」或「数据本来就有序」时划算。
2. **改代码形态**：掩码、条件选择、查表。适合分支体很小、且两支都能安全提前计算的情况；如果一支要除法、要解引用可能为空的指针，无分支版反而更慢。
3. **把分支移到循环外**：先扫一遍判断「是否全正」，再选一个没有分支的专用循环。多一遍扫描换掉内层分支。

`__builtin_expect(err != 0, 0)` 只影响代码布局，把冷路径挪远，不改变语义，也不改变分支方向。现代 CPU 的动态预测器主要看运行历史，这个提示的收益依场景而定，不要把它当加速开关。

无分支版还有一个容易忽略的要求：它每个元素都写一次 `q`，所以 `q` 必须能容纳 `n` 个元素，而不只是 `k` 个。缓冲区按 `k` 分配会越界。

::: ex 例 1.5.7 · 先猜谁更快 {#ex-1.5.7}
随机数据下分支版 1.408 ns/elem。先猜：排好序后它会降到多少？再猜无分支版排好序后会不会也跟着变快？

::: sol 解答
分支版排好序是 0.333，快 4.2 倍：方向只转变一次，预测器几乎全对。无分支版仍是 0.269，和随机的 0.271 一样——它没有分支可猜，数据顺序与它无关。排序同时改变了分支方向与访存顺序，这两个因素靠无分支版做对照才拆得开：无分支版排序前后不变，说明收益主要来自预测，不是缓存。
:::
:::

::: errata 关于分支的四个误解
1. **「无分支一定更快」**——要无条件算出两支的结果；分支体里有除法、调用或可能无效的访存时，反而更慢。
2. **「三元表达式一定生成条件选择指令」**——编译器按代价模型决定，可能仍生成分支；看汇编确认。
3. **「先把数据排序总没错」**——排序要花 $O(n\log n)$，只扫一遍时常常倒亏；它适合重复扫描或流式统计。
4. **「`likely`/`unlikely` 能显著提速」**——它们只改布局；真正的收益来自减少不可预测分支或改变数据顺序。
:::

### 1.5.7 小结

① 分支的代价在猜错，不在指令本身；② 改数据顺序和改代码形态都能消掉猜错，前者常更便宜，后者要看分支体是否能安全提前计算；③ 简单条件编译器已经会 if-convert，先看汇编再动手。如果只记住一件事，那就是：**先问这个分支能不能不猜，再问能不能不写。**

::: method 即时自测 · 1.5.7
**Q1（记忆）** 分支预测失败的代价是什么？本节用什么量它？
**Q2（辨析）** 压缩循环里无分支版快 5 倍，求和循环里两版一样快。差别在哪？
**Q3（应用）** 一个解析器按首个字节分派到 20 种消息类型，输入顺序随机。你能想到哪两种不改分派表的优化？

::: sol 答案
**A1** 丢弃预测方向上已做的工作并重新取指；本节不报拍数，用同机墙钟 ns/elem 对比。
**A2** 压缩循环的分支保护一次「写到哪里」，写地址依赖条件，编译器不能安全地提前写；求和循环的 `if` 只选一个值，`-O2` 已把它转成掩码加向量加法。
**A3** 按类型分桶后批量处理，让分支方向连续；或先统计各类型数量、为高频类型写专用循环，把分派移到循环外。
:::

## 1.5.8 存储层次优化：分块、SoA 与预取 {#sec-1.5.8}

这一节回答：当瓶颈从 ALU 转到内存，改循环顺序、分块、换数据布局、加预取，哪一招真的有效？

::: preview 先抓住一件事
先让最内层访问连续，再谈分块；分块不是越大越好，块大小要试出来。SoA 只在「只碰一部分字段」时大赢；预取只对硬件猜不到的地址有用，距离太近反而更慢。
:::

**第一步是循环顺序，不是分块。** 512×512 的 `double` 矩阵乘，三个版本：`ijk`（内层读 `B` 的一列）、`ikj`（内层读 `B` 的一行）、64×64 分块。

```c
/* ijk：内层 k，B[k][j] 的步长是 N，每步跳 4 KiB */
for (int i = 0; i < N; i++)
  for (int j = 0; j < N; j++) {
    double s = 0;
    for (int k = 0; k < N; k++) s += A[i][k] * B[k][j];
    C[i][j] = s;
  }

/* ikj：内层 j，B[k][j] 与 C[i][j] 都连续 */
for (int i = 0; i < N; i++)
  for (int k = 0; k < N; k++) {
    double a = A[i][k];
    for (int j = 0; j < N; j++) C[i][j] += a * B[k][j];
  }
```

VM 实测（Ubuntu 24.04.5 aarch64，GCC 13.3 `-O2`，5 次取最小，三次运行的范围）：

| 版本 | 时间 | ns/MAC |
|:--|--:|--:|
| `ijk` | 70–78 ms | 0.52–0.58 |
| `ikj` | 21–22 ms | 0.15–0.17 |
| 64×64 分块 | 25–27 ms | 0.19–0.20 |

只换循环顺序就快 3.4 倍。分块在这个尺寸上没有继续赢：`ikj` 的内层已经在顺序读 `B` 的一行、顺序写 `C` 的一行，两条流都能待在 L1；再加一层块循环只多了下标运算。**分块解决的是「同时有太多条流互相挤」，不是「循环看起来不够高级」。**

**分块在转置上收益更明显。** 1024×1024 的 `double`，朴素写法按列写 `dst`，每次写跨 8 KiB：

```c
for (int i = 0; i < N; i++)
  for (int j = 0; j < N; j++) dst[j][i] = src[i][j];           /* 朴素 */

for (int ii = 0; ii < N; ii += B)
  for (int jj = 0; jj < N; jj += B)
    for (int i = ii; i < ii + B; i++)
      for (int j = jj; j < jj + B; j++) dst[j][i] = src[i][j]; /* 分块 */
```

VM 实测（同一台，5 次取最小）：

| 版本 | 时间 | 说明 |
|:--|--:|:--|
| 朴素 | 11.2 ms | 每次写都踩新缓存行（缓存与内存之间搬运的固定块） |
| B=8 | 1.8 ms | 块偏小，外层循环开销上来 |
| B=16 | 1.3 ms | 比朴素快 8.6 倍 |
| B=32 | 6.0 ms | 比 B=16 慢 4.6 倍 |
| B=64 | 7.1 ms | |

块从 16 加到 32，容量并没有不够：32×32×8 = 8 KiB，读块加写块共 16 KiB，而常见的 L1 至少有 32 KiB。更可能的原因是同时打开的行数翻倍——32 条读流加 32 条写流，缓存组冲突和预取器要跟踪的流数一起上升。这一条是机制推断，数字是实测；能复现的结论是：**块大小要试，不能只按容量公式算。**

::: def 定义 1.5.8 · 分块（blocking / tiling） {#def-1.5.8}
把大循环按某一维切成边长为 $B$ 的小块，使块内读写的数据能同时驻留在某一级缓存。$B$ 的容量下界由「块内字节数 × 同时活跃的数组数 ≤ 缓存容量」给出；但真实最优值还受相联度、预取器跟踪的流数、循环开销影响，通常要在目标机器上扫一遍。
:::

**换布局：AoS 与 SoA。** 粒子结构 24 字节（`x,y,z,vx,vy,vz` 各 4 字节）。AoS 把六个字段放在一起，SoA 把同名字段各放一个数组。

```c
struct particle { float x, y, z, vx, vy, vz; };  /* AoS */
float sx[N], sy[N], sz[N], svx[N], svy[N], svz[N]; /* SoA */
```

VM 实测（26 万个粒子，`-O2`，7 次取最小）：

| 内核 | AoS | SoA |
|:--|--:|--:|
| 更新 x、y、z 三个字段 | 0.480 ns/elem | 0.364 ns/elem |
| 只更新 x | 0.329 ns/elem | 0.087 ns/elem |

只更新 `x` 时，AoS 每个元素要跨 24 字节，一条 64 字节缓存行装 2.67 个粒子，真正用到的只有其中 4 字节；SoA 的 `sx` 是连续数组，整条缓存行都用得上，实测快 3.8 倍。六个字段全用时，AoS 的 0.480 与 SoA 的 0.364 只差 1.3 倍——SoA 仍然略快，是因为六条独立流更容易向量化，不是因为它「永远更好」。AoS 在按对象整体传递、字段少、代码改动小的场景仍然合理。

**预取只对猜不到的地址有用。** 64 MiB 的整数数组上做随机 gather，每次查表约 4.0–5.0 ns；在循环里提前 64 个元素发 `__builtin_prefetch(&data[idx[i+64]], 0, 1)`，降到 3.3–3.7 ns，同一进程内快 10%–25%。单次 DRAM 访问的延迟在 [1.5.1](#sec-1.5.1) 里是 78–134 ns，这里摊到每次查找只有 4 ns，因为循环里同时有多个缺失在飞；预取要藏的是这条流水线的等待，不是单次延迟。把距离缩到 8，反而从 1.78 升到 2.24 ns/lookup：数据还没到就该用了，多出来的指令和缓存污染全是净亏。

```c
for (size_t i = 0; i < n; i++) {
    __builtin_prefetch(&data[idx[i + 64]], 0, 1);  /* 提前约 64 次访存 */
    s += data[idx[i]];
}
```

顺序访问不用手写预取，硬件预取器已经会做；指针追逐、哈希探查、稀疏矩阵这类地址由数据决定的访问，才是软件预取的用武之地。

::: note 非临时存储（NT store）
对「写一次、不再读」的大数组，普通 store 会先把缓存行读进来（RFO），白占带宽。x86 的 `movntdq`、ARM 的 `stnp` 一类非临时写可以绕过缓存直接写内存。它适合流式写（视频编码、大规模初始化），不适合随后还要读的数据。本节未在 VM 上实测这一项，用时以目标机器的指令集手册为准。
:::

::: ex 例 1.5.8 · 先猜哪个块更快 {#ex-1.5.8}
转置实验里 B=16 是 1.3 ms。先猜 B=32 会更快、差不多，还是更慢；再猜「只更新 x」时 SoA 比 AoS 快几倍。

::: sol 解答
B=32 实测 6.0 ms，比 B=16 慢 4.6 倍；B=64 是 7.1 ms。猜「更大块一定更好」的人只算了容量，没算同时活跃的流数。只更新 x 时 AoS 0.329、SoA 0.087，约 3.8 倍；猜 6 倍的人按「24 字节里只用 4 字节」算，忽略了硬件预取和乱序执行已经挽回了一部分。
:::
:::

::: errata 关于存储层次的四个误解
1. **「分块越大，复用越多」**——超过某个块大小后，同时活跃的流与组冲突会让它变慢；本例 32 比 16 慢 4.6 倍。
2. **「矩阵乘先分块」**——先看循环顺序；本例 `ikj` 已经顺序访问，分块没有再赢。
3. **「SoA 永远比 AoS 快」**——全字段更新只差 1.3 倍；SoA 的收益来自「只碰一部分字段」或向量化，不是布局本身有魔力。
4. **「预取免费，加了总不亏」**——距离太近会增加指令与污染，本例距离 8 比不预取更慢。
:::

### 1.5.8 小结

① 先改循环顺序让内层连续，再考虑分块；② 块大小由容量、相联度、活跃流数共同决定，要扫一遍而不是套公式；③ SoA 的收益与「用了多少字段」成正比，预取的收益与「硬件猜不到」成正比。如果只记住一件事，那就是：**先让数据被顺序地用完，再谈让硬件提前拿。**

::: method 即时自测 · 1.5.8
**Q1（记忆）** 分块的块大小由哪两类因素决定？各举一个。
**Q2（辨析）** 矩阵乘 512×512 上，`ikj` 21 ms，64×64 分块 26 ms。为什么分块没有更快？
**Q3（应用）** 一个粒子系统每帧只读 `x` 做碰撞检测，写回 `x`。你会选 AoS 还是 SoA？如果每帧要读写全部六个字段呢？

::: sol 答案
**A1** 容量类：块内字节数、缓存大小与相联度；动态类：同时活跃的读/写流数、预取器跟踪能力、循环开销。
**A2** `ikj` 的内层已经顺序读 `B` 一行、顺序写 `C` 一行，两条流都在 L1；分块只增加下标与循环开销，没有减少缺失。
**A3** 只碰 `x` 选 SoA：连续数组整行有效，实测快 3.8 倍；六个字段全用时 AoS 也可以，差距只有 1.3 倍，按代码改动成本选。
:::
:::

## 1.5.9 用 perf 定位瓶颈与优化清单 {#sec-1.5.9}

这一节回答：`perf` 是 Linux 上定位性能瓶颈的默认工具，可当它在这台机器上打不开计数器时，你还能靠什么判断「慢在流水线、缓存还是分支」？

::: preview 先抓住一件事
`perf stat` 把性能拆成 IPC、缓存缺失、分支失败三组数；没有 PMU 时，墙钟、规模扫描和 `objdump -d` 的静态指令数能给出同一类判断。工具可以换，判据不能少。
:::

先在这台 VM 上跑一次：

<div class="terminal" data-title="bash · Ubuntu 24.04.5 aarch64 实测">
<pre><span class="p">&#36;</span> perf record -g ./matmul
Error:
Failure to open event 'armv8_pmuv3_0/cycles/Pu' on PMU 'armv8_pmuv3_0' which will be removed.
...
perf_event_paranoid setting is 4:
</pre>
</div>

`perf stat -d ./matmul` 也一样：事件行只有 `<not supported>`，最后只剩墙钟。`/proc/sys/kernel/perf_event_paranoid` 的值是 4，普通账户没有 `CAP_PERFMON`，也没有 sudo 去改这个开关。于是这一节不使用任何计数器读数。

**perf 本来要回答三个问题。** 第一，流水线是不是在等：IPC（instructions per cycle，每周期退休的指令数）低，说明有停顿。第二，是不是在等内存：末级缓存缺失高，说明工作集超出了缓存。第三，是不是在猜分支：`branch-misses` 高，说明控制流不可预测。三组数对应三类改法：拆依赖、改布局、改分支。

**没有计数器，就把这三问换成三个实验。** 工作集从 256 KiB 扫到 64 MiB，追逐成本 0.95 → 2.22 → 18.97 ns/hop，说明缓存层级在起作用；同一段压缩循环，数据随机 1.408 ns/elem、排序后 0.333，说明分支预测在起作用；链数取 1、4、8 条，0.574 → 0.141 → 0.094 ns/op，说明瓶颈从延迟转到吞吐。这三组数分别来自 [1.5.1](#sec-1.5.1)、[1.5.7](#sec-1.5.7)、[1.5.6](#sec-1.5.6)，没有一个是 PMU 读数。

**指令数也能估。** `objdump -d` 数出内层循环的静态指令条数，乘以迭代次数，再除以墙钟，就是每秒退休的指令数；除以标定频率，就是 IPC 的估算值：

$$
\mathrm{IPC}\approx \frac{I_{\text{loop}}\times \text{迭代次数}}{T\times f}.
$$

用 [1.5.12](#sec-1.5.12) 的矩阵乘做例子。512×512 的乘加共 $512^3=1.34\times10^8$ 个 MAC；编译器把 j 方向两个元素合并成一条向量，`mm_ijk` 与 `mm_ikj` 的内层都是 8 条指令处理 2 个 MAC，总指令数约 $5.4\times10^8$。两者墙钟分别是 72–75 ms 与 21.7–23.0 ms，取 $f\approx4.0$ GHz：

| 内核 | 内层指令 / 2 MAC | 总指令估算 | 墙钟 | IPC 估算 |
|:--|--:|--:|--:|--:|
| `mm_ijk` | 8 | 5.4×10⁸ | 72–75 ms | 约 1.8 |
| `mm_ikj` | 8 | 5.4×10⁸ | 21.7–23.0 ms | 5.8–6.2 |

两版的指令数几乎一样，时间却差 3.3 倍。结论不是「`ijk` 指令多」，而是「`ijk` 每条指令都在等」：内层每次取 `B[k][j]` 都跨 4 KiB，缓存行只用到 8 字节。这正是 `perf stat` 会用「低 IPC + 高 cache-misses」告诉你的东西。

::: def 定义 1.5.9 · IPC 与静态计数折算 {#def-1.5.9}
IPC 是单位周期退休的指令数，衡量流水线填得满不满。没有 PMU 时，可以用「内层静态指令数 × 迭代次数 ÷ 墙钟 ÷ 频率」估算。它假设循环体是主要耗时，且编译后没有换一套向量宽度；换编译选项或换机器都要重新数。
:::

::: ex 例 1.5.9 · 先猜谁的 IPC 高 {#ex-1.5.9}
两段循环做同样多的 MAC，内层都是 8 条指令处理 2 个 MAC；一段 72–75 ms，一段 21.7–23.0 ms。先猜哪段的 IPC 高、差几倍；再猜「给慢的那段减少指令」能不能追平。

::: sol 解答
快的那段 IPC 约 5.8–6.2，慢的约 1.8，差 3 倍多。两段指令数相同，慢的原因是每次 load 跨 4 KiB，流水线大部分时间在等数据；减指令只能动那 8 条里的一两条，追不平。要先改循环顺序或布局，让内层连续。
:::
:::

::: method 优化清单（按收益排序）
1. **换算法/数据结构**：$O(n^2)\to O(n\log n)$，或哈希替代线性查找；收益最大，先做。
2. **改循环顺序与布局**：让内层连续读、连续写；[1.5.8](#sec-1.5.8) 的 `ikj` 比 `ijk` 快 3 倍多。
3. **删重复工作**：循环不变量、重复调用、`%` 换 `&`；[1.5.3](#sec-1.5.3) 的 `strlen` 案例差 175–2000 倍。
4. **拆依赖链**：多累加器、展开、重结合；[1.5.5](#sec-1.5.5) 从 0.523 降到 0.077 ns/elem。
5. **消不可预测分支**：排序、掩码、特化；[1.5.7](#sec-1.5.7) 从 1.408 降到 0.333。
6. **换数据布局**：只碰一部分字段时用 SoA；[1.5.8](#sec-1.5.8) 只更新 `x` 时快 3.8 倍。
7. **最后才手写 SIMD/汇编**：前面的账没算清，手写汇编常常只是把同样的等待换个写法。
:::

::: errata 关于 profiling 的四个误解
1. **「装了 perf 就能用」**——还要看 `perf_event_paranoid`、`CAP_PERFMON` 和虚拟机是否暴露 PMU；这台 VM 前两样就不满足。
2. **「IPC 高就一定快」**——IPC 是比值；一条向量指令干两份活，IPC 可能更低，但程序更快。要比同一段工作的墙钟。
3. **「指令少就快」**——[1.5.5](#sec-1.5.5) 的展开版指令更少却不变快；限制它的是依赖链。
4. **「没有 perf 就测不了」**——墙钟、规模扫描、静态计数都不需要 PMU；它们给的是区间和趋势，不是精确的 miss 数。
:::

### 1.5.9 小结

① `perf` 的三组数对应三类瓶颈，没有 PMU 时可以用工作集、数据顺序、链数三个实验替代；② 静态指令数 × 迭代 ÷ 墙钟 ÷ 频率，可以估出 IPC，用来区分「指令多」和「在等待」；③ 优化按收益排序，先算法、再布局、最后微调。如果只记住一件事，那就是：**先确定在等什么，再决定改什么。**

::: method 即时自测 · 1.5.9
**Q1（记忆）** `perf stat` 的哪三组数分别对应流水线、缓存、分支？
**Q2（辨析）** 两段循环指令数相同，一段 IPC 约 1.8、一段约 6.0。能说前者「指令效率低」吗？
**Q3（应用）** 一个循环每元素 12 条指令，处理 2×10⁸ 个元素用了 0.6 s，频率 4 GHz。估 IPC；如果只有 1.0，下一步查什么？

::: sol 答案
**A1** IPC 看流水线停顿；`cache-references`/`cache-misses` 看缓存；`branch-misses` 看分支预测。
**A2** 不能。两段做同样的工作，指令数一样；IPC 低说明它在等内存或依赖，不是指令本身低效。
**A3** 指令数 2.4×10⁹，IPC ≈ 2.4×10⁹/(0.6×4×10⁹)=1.0。先查工作集是否超过缓存、内层是否跨步；再看依赖链是否太长。
:::
:::

## 1.5.10 CPE 与性能模型：把「快了多少」算出来 {#sec-1.5.10}

这一节回答：优化前后到底快了多少、上限在哪里，能不能在上机前用一张纸算出来？

::: preview 先抓住一件事
CPE 把墙钟换成「每个元素几个周期」；没有 PMU 时，先用一条 1 周期的整数加链标定频率，再把 ns/elem 折算成 CPE。模型只给下界，预测准不准要用实测校验。
:::

先看两组数。[1.5.5](#sec-1.5.5) 里，单累加器 0.523 ns/elem，八累加器 0.077；[1.5.6](#sec-1.5.6) 里，一条链 0.574 ns/op，八条链 0.094。有人说「快了 6.8 倍」，有人说「快了 6.1 倍」，都对，但基线不同。要放在一张表里比，先把时间换成 CPE。

**频率可以自己标定。** 这台 VM 的 `/proc/cpuinfo` 不报实时频率（只有 BogoMIPS 48.00），`cpufreq` 目录也不存在。找一条延迟已知的依赖链：整数加法的延迟是 1 周期，每轮四次依赖加，循环开销与加法链并行，测出的 ns/add 就是一周期的长度。

```c
/* 核心循环：aarch64 内联汇编，省略计时与打印；x86 换成 add $1, %0 */
uint64_t x = 1;
for (uint64_t i = 0; i < n / 4; i++) {
    __asm__ volatile("add %0, %0, #1" : "+r"(x));
    __asm__ volatile("add %0, %0, #1" : "+r"(x));
    __asm__ volatile("add %0, %0, #1" : "+r"(x));
    __asm__ volatile("add %0, %0, #1" : "+r"(x));
}
```

VM 实测（10 亿条加法，3 次）：0.251、0.257、0.252 ns/add，折合 3.9–4.0 GHz。下面统一取 $f=4.0$ GHz，即 1 周期 $=0.25$ ns。

::: def 定义 1.5.10 · CPE 与折算频率 {#def-1.5.10}
CPE（cycles per element，每元素周期数）是总周期数除以元素个数。读不到周期计数器时，$\mathrm{CPE}\approx \text{ns/elem}\times f$，其中 $f$ 用已知延迟的依赖链标定。CPE 只在同一台机器、同一频率下有可比性。
:::

把 1.5.6 的表折算过来：1 条链 0.574 ns ≈ 2.30 CPE，4 条 0.141 ≈ 0.56，8 条 0.094 ≈ 0.38。**模型只有两个参数**：单链的关键路径 $L$，和吞吐上限 $1/T$。从 1 条链读出有效 $L=2.30$（含循环开销），从 8 条链读出 $1/T=0.38$，下界是

$$
\mathrm{CPE}(k)\ \ge\ \max\!\left(\frac{L}{k},\ \frac{1}{T}\right).
$$

拿它预测中间档：

| 链数 $k$ | 模型下界 CPE | 预测 ns/op | 实测 ns/op |
|--:|--:|--:|--:|
| 1 | 2.30 | 0.575 | 0.574 |
| 2 | 1.15 | 0.288 | 0.292 |
| 4 | 0.575 | 0.144 | 0.141 |
| 8 | 0.38 | 0.095 | 0.094 |

第 1 行是标定用的，不算预测；2、4 行才是预测，都落在实测的 0.004 ns 以内；8 行已经撞到吞吐上限。拐点在 $k=L\cdot T=2.3/0.38\approx6$：少于 6 条，加链能摊薄延迟；多于 6 条，只剩吞吐上限，再加链没有收益。

**模型也会失效。** [1.5.12](#sec-1.5.12) 的 `ikj` 是 0.166 ns/MAC，折 0.66 CPE；`ijk` 是 0.55 ns/MAC，折 2.2 CPE。两者都高于「每周期两次双精度 FMA」这个理想下界 0.25 CPE，说明限制它们的是访存与循环开销，不是 ALU。模型给的是核心内的下界；实际 CPE 比下界高一个量级时，先去查缓存和带宽。

**Amdahl 定律给的是另一个上限。** 若程序里比例为 $p$ 的部分加速 $s$ 倍，整体加速比是

$$
S=\frac{1}{(1-p)+p/s}.
$$

假设一份程序 60% 的时间在矩阵乘、40% 在 I/O；把 `ijk` 换成 `ikj`（3.3 倍），整体只有 $1/(0.4+0.6/3.3)\approx1.7$ 倍，不是 3.3 倍。即使矩阵乘快到不花时间，上限也只有 $1/0.4=2.5$ 倍。这就是「只优化热点」的正确读法：热点决定收益，非热点决定天花板。

::: ex 例 1.5.10 · 先猜中间档 {#ex-1.5.10}
已知 1 条链 0.574 ns、8 条链 0.094 ns。先猜 2 条链和 4 条链各是多少；再猜「延迟是吞吐的几倍」。

::: sol 解答
2 条 0.292、4 条 0.141。按「除以链数」猜，2 条应是 0.287、4 条 0.144，与实测只差 0.002–0.004；但 8 条按除以 8 应是 0.072，实际 0.094，说明已经撞上吞吐墙。延迟/吞吐比 $0.574/0.094\approx6.1$，所以 6 条左右就饱和。
:::
:::

::: errata 关于性能模型的四个误解
1. **「CPE 可以跨机器直接比」**——CPE 含频率与微架构；同一份代码换一台机器，$L$ 和 $T$ 都会变。
2. **「模型算出的下界就是实际时间」**——下界只算核心内的关键路径与吞吐，缓存缺失、分支失败、循环开销都在外面。
3. **「`/proc/cpuinfo` 的频率可以直接用」**——虚拟机常常不报实时频率；用 1 周期依赖链标定，比抄一个标称值可靠。
4. **「Amdahl 说明优化没用」**——它说明天花板由未优化部分决定；要提整体，先找占比最大的 $p$。
:::

### 1.5.10 小结

① 先用 1 周期依赖链标定频率，再把 ns/elem 折算成 CPE；② 模型只有 $L$ 与 $1/T$ 两个参数，从 1 条链和饱和链读出，中间档可以预测；③ 实际 CPE 远高于模型下界时，瓶颈在缓存/带宽；整体收益还要过 Amdahl 这一关。如果只记住一件事，那就是：**先把时间换成周期，再谈快了百分之几。**

::: method 即时自测 · 1.5.10
**Q1（记忆）** 没有 PMU 时，CPE 怎么从墙钟折算？频率怎么标定？
**Q2（辨析）** 1 条链 0.574 ns、8 条链 0.094 ns。为什么 8 条不是 0.072？
**Q3（应用）** 程序 70% 的时间在可加速 4 倍的循环里，整体最多快多少？循环无限快呢？

::: sol 答案
**A1** CPE ≈ ns/elem × f；用一串依赖的整数加法（延迟 1 周期）测 ns/add，其倒数就是 GHz。
**A2** 8 条链已经撞上吞吐上限 $1/T=0.38$ CPE；除以 8 得到 0.29 CPE，低于这个上限，做不到。
**A3** $1/(0.3+0.7/4)\approx2.1$ 倍；循环无限快时 $1/0.3\approx3.3$ 倍。
:::
:::

## 1.5.11 别名、restrict 与编译器的不敢 {#sec-1.5.11}

这一节回答：`restrict` 到底让编译器多做了什么？为什么同一段代码，有时加了快一倍，有时一点差别都没有？

::: preview 先抓住一件事
`restrict` 不是加速开关，而是一句承诺：这块内存只通过这个指针访问。它删掉的是编译器为「可能重叠」准备的检查与退路；删掉之后能不能更快，取决于循环形状和优化级别。
:::

先看一个最简单的三数组相加：

```c
void addv(long *a, const long *b, const long *c, long n)
{
    for (long i = 0; i < n; i++) a[i] = b[i] + c[i];
}
void addv_r(long *restrict a, const long *restrict b,
            const long *restrict c, long n)
{
    for (long i = 0; i < n; i++) a[i] = b[i] + c[i];
}
```

VM 实测（4 Mi 个 `long`，每数组 32 MiB，9 次取最小）：

| 编译 | `addv` ns/elem | `addv_r` ns/elem |
|:--|--:|--:|
| `-O2` | 0.32–0.34 | 0.29–0.32 |
| `-O3` | 0.204–0.208 | 0.205 |

`-O2` 下两版生成同一段标量循环，逐条相同；表里 0.03 ns 的差来自运行顺序与代码对齐，不能归因于 `restrict`。`-O3` 下都向量化，时间差不到 1%。**在这段代码上，`restrict` 量不出收益。** 看汇编，它确实改了一处：`addv` 在进入向量循环前有 3 条比较，检查 `a` 与 `b`、`c` 是否重叠；不重叠才走向量，重叠就退回标量。`addv_r` 没有这段检查，直接进循环。

```asm
# addv（-O3）：进向量循环前的重叠检查（示意，省略地址）
cmp  x4, x0
ccmp x5, x0, #0x4, ne
b.ne .Lscalar
# addv_r（-O3）：没有检查，直接向量化
ldr  q0, [x1, x4]
ldr  q1, [x2, x4]
add  v0.2d, v0.2d, v1.2d
str  q0, [x0, x4]
```

检查只有 3 条指令，摊到 4 Mi 个元素上不到一纳秒，所以时间上看不见。

**换一个循环形状，差别就出来了。** 把 1.5.12 的 `mm_ikj` 内层单独拿出来，用 `malloc` 的三个指针编译（这样编译器不能假设 `C` 与 `B` 不重叠）：

| 编译 | 普通指针 | `restrict` |
|:--|--:|--:|
| `-O2` | 35.8–40.9 ms | 35.8–39.0 ms |
| `-O3` | 21.8–24.5 ms | 13.9–17.1 ms |

`-O3` 下 restrict 快 1.5–1.6 倍。汇编里，普通版每轮 k 都要比较 `C` 的行与 `B` 的行是否重叠；检查本身不贵，贵的是它把内层锁在「一次处理 2 个 double」的形状，编译器不敢再展开。`restrict` 删掉检查后，内层一次处理 4 个 double。`-O2` 下两版都没向量化，所以也没有差别。

::: def 定义 1.5.11 · restrict 承诺 {#def-1.5.11}
`restrict` 修饰一个指针，承诺在它的生命周期内，所指对象只通过它或由它派生的指针访问。编译器据此可以重排 load/store、删除重叠检查、向量化与展开。违反承诺是未定义行为（UB），不是「最多不优化」。
:::

**为什么编译器要这么小心。** C 的规则是：写 `a[i]` 可能改到后面要读的 `b[j]`；只要两个指针类型相同、又都可能指向同一块内存，编译器就必须按「可能重叠」处理。它有两个选择：不向量化、不重排，或者生成一段运行时检查，不重叠走向量、重叠走标量。这段检查叫循环版本化（loop versioning）。`restrict` 让编译器跳过这一步。

**承诺的代价。** [1.5.2](#sec-1.5.2) 已经演示过：`scale_restrict(arr+1, arr, 7)` 的结果从 `1 5 11 19…` 变成 `1 5 8 11…`。指针真的重叠时，向量版读的是写之前的旧值，结果与顺序语义不同。这不是编译器 bug，是程序违反了契约。

两条相邻的规则也常被混在一起：

- `memcpy(dst, src, n)` 的签名带 `restrict`，它承诺两块内存不重叠；重叠时必须用 `memmove`。用 `memcpy` 处理重叠区间是 UB，在某些实现上「碰巧能用」，换编译器就出错。
- 严格别名（strict aliasing）禁止用不兼容类型的指针访问同一对象：`*(uint32_t *)&f` 是 UB；要按位看浮点，用 `memcpy` 到 `uint32_t`。`-fno-strict-aliasing` 能关掉这类优化，但热循环会变慢；正确做法是改代码。

Rust 把同一承诺写进类型：`&mut T` 保证独占，`&T` 保证共享只读，安全代码里构造不出两个重叠的可写引用；需要原地拆两半时用 `split_at_mut`。这不是「Rust 更快」，而是把口头承诺变成编译期检查。

::: ex 例 1.5.11 · 先猜哪段会变快 {#ex-1.5.11}
同样是加 `restrict`：一段是 4 Mi 元素的逐元素相加，一段是 512×512 矩阵乘的内层。先猜哪段会快、大概快多少；再猜 `-O2` 下会怎样。

::: sol 解答
逐元素相加在 `-O3` 下两版都是 0.205 ns/elem，量不出差别；`-O2` 下两版都是标量，也一样。矩阵乘内层在 `-O3` 下从 22–24 ms 降到 14–17 ms，约 1.5–1.6 倍；`-O2` 下两版都 36–41 ms，没有差别。区别在循环形状：前者的检查只在循环外做一次，后者每轮 k 都要检查，还挡住了展开。
:::
:::

::: errata 关于别名的四个误解
1. **「`restrict` 只是提示，违反了也没事」**——它是承诺；违反是 UB，向量化后的结果可能在任何输入上都错。
2. **「加了 `restrict` 一定更快」**——逐元素相加实测没有差别；收益取决于检查是否在循环内、是否挡住展开。
3. **「`memcpy` 和 `memmove` 可以互换」**——重叠区间必须用 `memmove`；`memcpy` 的 `restrict` 承诺不重叠。
4. **「`-fno-strict-aliasing` 没有代价」**——它关掉一整类别名优化；先修类型双关，再考虑关开关。
:::

### 1.5.11 小结

① 别名让编译器不敢重排、向量化、展开；它要么保守，要么加运行时检查；② `restrict` 删掉检查与退路，收益依循环形状而定，本例简单相加量不出、矩阵乘内层约 1.6 倍；③ 违反承诺是 UB，`memcpy` 与严格别名两条规则别混。如果只记住一件事，那就是：**`restrict` 买的是「编译器敢不敢」，不是「CPU 快不快」。**

## 1.5.12 完整程序一：四种矩阵乘与 CPE 实测 {#sec-1.5.12}

这一节回答：把 [1.5.8](#sec-1.5.8) 的四种矩阵乘放进同一个程序，用同一份数据量，时间和折算 CPE 到底差多少？

::: preview 先抓住一件事
四种写法共用一份 512×512 数据：先换循环顺序，`ikj` 比 `ijk` 快 3.3 倍；分块与展开在这个规模上都没有赢。CPE 用标定频率折算，不是 PMU 读数。
:::

矩阵乘是检验「局部性 + ILP」的最好载体：$C=A\times B$，三重循环有 6 种排列，访存模式不同，性能能差一个数量级。下面的程序把 [1.5.8](#sec-1.5.8) 的四种写法放进同一个文件，用同一份数据、同一个校验，量出时间、GFLOP/s 与折算 CPE。程序用全局数组，编译器能看见 A、B、C 是三个独立对象；别名的账留到 [1.5.11](#sec-1.5.11)。

```c
/* matmul.c — 四种矩阵乘 + 计时 + 校验
 * cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 matmul.c
 */
#include <stdio.h>
#include <string.h>
#include <time.h>

#define N 512                  /* 改成 1024 可看更大规模 */
#define BS 64                  /* N 必须是 BS 的整数倍 */
static double A[N][N], B[N][N], C[N][N], REF[N][N];

static double now(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec + (double)ts.tv_nsec * 1e-9;
}

/* i-j-k：内层沿 B 的列走，步长 N*8 字节 */
static void mm_ijk(void)
{
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++) {
            double s = 0.0;
            for (int k = 0; k < N; k++) s += A[i][k] * B[k][j];
            C[i][j] = s;
        }
}

/* i-k-j：内层沿 B 的一行、C 的一行连续走 */
static void mm_ikj(void)
{
    memset(C, 0, sizeof C);
    for (int i = 0; i < N; i++)
        for (int k = 0; k < N; k++) {
            double x = A[i][k];
            for (int j = 0; j < N; j++) C[i][j] += x * B[k][j];
        }
}

/* 分块 i-k-j，块边长 BS */
static void mm_block(void)
{
    memset(C, 0, sizeof C);
    for (int ii = 0; ii < N; ii += BS)
        for (int kk = 0; kk < N; kk += BS)
            for (int jj = 0; jj < N; jj += BS)
                for (int i = ii; i < ii + BS; i++)
                    for (int k = kk; k < kk + BS; k++) {
                        double x = A[i][k];
                        for (int j = jj; j < jj + BS; j++)
                            C[i][j] += x * B[k][j];
                    }
}

/* 分块 + 内层 j 方向展开 4 路 */
static void mm_block4(void)
{
    memset(C, 0, sizeof C);
    for (int ii = 0; ii < N; ii += BS)
        for (int kk = 0; kk < N; kk += BS)
            for (int jj = 0; jj < N; jj += BS)
                for (int i = ii; i < ii + BS; i++)
                    for (int k = kk; k < kk + BS; k++) {
                        double x = A[i][k];
                        int j = jj;
                        for (; j + 3 < jj + BS; j += 4) {
                            C[i][j]     += x * B[k][j];
                            C[i][j + 1] += x * B[k][j + 1];
                            C[i][j + 2] += x * B[k][j + 2];
                            C[i][j + 3] += x * B[k][j + 3];
                        }
                        for (; j < jj + BS; j++)
                            C[i][j] += x * B[k][j];
                    }
}

typedef void (*kernel)(void);

static void run(const char *name, kernel f)
{
    double best = 1e30;
    for (int r = 0; r < 3; r++) {
        double t0 = now(); f(); double t1 = now();
        if (t1 - t0 < best) best = t1 - t0;
    }
    double err = 0.0;
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++) {
            double d = C[i][j] - REF[i][j];
            if (d < 0) d = -d;
            if (d > err) err = d;
        }
    printf("%-8s n=%d %8.1f ms %6.2f GFLOP/s maxerr=%.3g\n",
           name, N, best * 1e3, 2.0 * N * N * N / best / 1e9, err);
}

int main(void)
{
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++) {
            A[i][j] = (double)((i * 17 + j * 3) % 100) / 100.0;
            B[i][j] = (double)((i * 29 + j * 7) % 100) / 100.0;
        }
    mm_ijk();
    memcpy(REF, C, sizeof C);
    run("ijk", mm_ijk);
    run("ikj", mm_ikj);
    run("block64", mm_block);
    run("block4", mm_block4);
    return 0;
}
```

编译并运行：

```text
$ cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 matmul.c -o matmul
$ ./matmul
ijk      n=512     73.0 ms   3.68 GFLOP/s maxerr=0
ikj      n=512     22.3 ms  12.03 GFLOP/s maxerr=0
block64  n=512     26.2 ms  10.23 GFLOP/s maxerr=0
block4   n=512     25.5 ms  10.55 GFLOP/s maxerr=0
```

这是 VM 上的一次运行；3 次运行的逐项范围如下（Ubuntu 24.04.5 aarch64，GCC 13.3 `-O2`，每版 3 次取最小）：

| 版本 | 时间 | GFLOP/s | ns/MAC | CPE（按 4.0 GHz 折算） |
|:--|--:|--:|--:|--:|
| `ijk` | 72.7–75.0 ms | 3.6–3.7 | 0.54–0.56 | 2.2 |
| `ikj` | 21.7–23.0 ms | 11.7–12.4 | 0.162–0.171 | 0.65–0.68 |
| `block64` | 25.9–26.5 ms | 10.1–10.4 | 0.193–0.197 | 0.77–0.79 |
| `block4` | 25.1–25.8 ms | 10.4–10.7 | 0.187–0.192 | 0.75–0.77 |

**第一件事：换循环顺序就快 3.3 倍。** `ijk` 的内层沿 `j` 走，每次取 `B[k][j]` 都跨 $512\times8=4096$ 字节；一条 64 字节缓存行只用到 8 字节。`ikj` 的内层同时顺序读 `B` 的一行、顺序读写 `C` 的一行，整条缓存行都用得上。指令数几乎一样（[1.5.9](#sec-1.5.9) 算过，都是 8 条处理 2 个 MAC），差的是等待。

**第二件事：分块没有赢。** `block64` 25.9–26.5 ms，比 `ikj` 慢 15%–20%。512 的规模下，`B` 的一行 4 KiB、`C` 的一行 4 KiB，`ikj` 的两条流已经能待在缓存里；分块只是把同样的流切成小块，多了一层下标与循环开销。这和 [1.5.8](#sec-1.5.8) 的结论一致：**分块解决的是「同时有太多条流互相挤」，不是「循环看起来不够高级」。**

**第三件事：手写展开没有额外收益。** `block4` 25.5 ms，和 `block64` 的 26.2 ms 在噪声内。`-O2` 已经把内层 `j` 循环向量化，四路展开只是把编译器做过的事又写了一遍；[1.5.5](#sec-1.5.5) 的结论在这里同样成立：展开省的是控制指令，不改依赖链。

**把时间换成 CPE。** 512×512 的乘加共 $512^3=1.34\times10^8$ 个 MAC。取 [1.5.10](#sec-1.5.10) 标定的 $f=4.0$ GHz，`ikj` 的 0.166 ns/MAC 折 0.66 CPE，`ijk` 的 0.55 ns/MAC 折 2.2 CPE。与 [1.5.8](#sec-1.5.8) 记录的 0.15–0.17 与 0.52–0.58 ns/MAC 是同一量级。**3.3 倍的差距全部来自访存，不是浮点单元。**

这 22 ms 是「编译器知道三个数组不重叠」时的数。把同样的 `mm_ikj` 改成三个 `malloc` 指针，`-O2` 下会掉到 36–41 ms，因为编译器要按可能重叠生成代码；加 `restrict` 或换 `-O3` 才能拿回来一部分，细节在 [1.5.11](#sec-1.5.11)。

::: ex 例 1.5.12 · 先猜谁赢 {#ex-1.5.12}
先猜：分块 + 四路展开（`block4`）能不能赢过简单的 `ikj`？再猜 `ikj` 的 CPE 是 `ijk` 的几分之一。

::: sol 解答
不能。`block4` 25.5 ms，`ikj` 22.3 ms；分块与展开都没有改变「内层连续」这个关键，反而多了循环开销。CPE 是 0.66 对 2.2，约 1/3.3，与时间比一致；差距来自 `ijk` 每次跨 4 KiB 的列访问。
:::
:::

::: errata 关于矩阵乘的四个误解
1. **「分块一定更快」**——512 的规模下 `block64` 比 `ikj` 慢 15%–20%；块大小与工作集要一起看。
2. **「GFLOP/s 可以跨机器直接比」**——它含频率、编译器向量宽度与缓存容量；只适合同机、同编译选项的前后对比。
3. **「`maxerr=0` 说明浮点结果逐位一致」**——它只说明这份数据、这个求和顺序下一致；换顺序或换展开，末位仍可能不同。
4. **「展开越多越快」**——`block4` 与 `block64` 一样快；`-O2` 已经向量化，手写展开没有额外收益。
:::

### 1.5.12 小结

① 先换循环顺序，让内层连续；本例 `ikj` 比 `ijk` 快 3.3 倍；② 分块与展开在这个规模上没有赢，因为 `ikj` 的两条流已经够友好；③ 用标定频率把 ns/MAC 折成 CPE，才能和 1.5.5、1.5.6 的模型放在一张表里。如果只记住一件事，那就是：**先把访问变成连续的，再谈分块和展开。**

::: method 即时自测 · 1.5.12
**Q1（记忆）** `ijk` 与 `ikj` 的内层分别怎么访问 `B`？
**Q2（辨析）** `block4` 与 `block64` 几乎一样快，说明展开没用吗？
**Q3（应用）** 把 `N` 改成 1024 重编译，`ijk` 的时间会按 8 倍涨还是更多？为什么？

::: sol 答案
**A1** `ijk` 的内层固定 `i`、`j`，沿 `k` 走，`B[k][j]` 的步长是 `N*8`；`ikj` 的内层固定 `i`、`k`，沿 `j` 走，`B[k][j]` 与 `C[i][j]` 都连续。
**A2** 不能。它说明在这个内核里编译器已经向量化，手写四路展开没有额外收益；换编译器或关掉向量化，结论可能不同。
**A3** 更多。MAC 数涨 8 倍，但工作集从 6 MiB 涨到 24 MiB，`B` 的列访问更容易缺失；`ijk` 会超线性变慢，`ikj` 的流式访问受影响较小。
:::

## 1.5.13 完整程序二：restrict 与别名的实测 {#sec-1.5.13}

这一节回答：把 [1.5.11](#sec-1.5.11) 的两段内核放进同一个程序、喂同一份数据，怎么做到「先证明结果对，再谈快多少」？为什么同一份源码换个函数边界，数字就变了？

::: preview 先抓住一件事
`restrict` 的收益只能在同一份二进制里量：先验结果逐元素相同，再交替计时两列。这台 VM 上，矩阵乘 `-O3` 从 19.5–22.3 ms 降到 11.7–13.4 ms，快约六成；逐元素相加在 `-O3` 下两版都是 2 路向量，量不出差别。
:::

1.5.11 给的是两段摘出来的内核和一张时间表，缺验证环节：万一两版结果不同，那个「快」就没有意义。这里把四个内核放进一个文件，`addv`/`addv_r` 与 `mm_ikj`/`mm_ikj_r` 共用一份数据、一个计时函数，先比结果，再比时间。

```c
/* alias_bench.c — 同内核两种指针限定：addv 与 mm_ikj
 * cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 alias_bench.c -o a2
 * cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O3 alias_bench.c -o a3
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>

#define N 512
#define REP 9

static double now(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec + (double)ts.tv_nsec * 1e-9;
}

/* noinline：内核若被内联进 main，两个版本会被合成一段，量不出差异 */
static void __attribute__((noinline))
addv(long *a, const long *b, const long *c, long n)
{
    for (long i = 0; i < n; i++) a[i] = b[i] + c[i];
}

static void __attribute__((noinline))
addv_r(long *restrict a, const long *restrict b, const long *restrict c, long n)
{
    for (long i = 0; i < n; i++) a[i] = b[i] + c[i];
}

/* 三个 malloc 指针：编译器看不到「两数组不重叠」，必须按可能重叠生成 */
static void __attribute__((noinline))
mm_ikj(double *C, const double *A, const double *B)
{
    memset(C, 0, (size_t)N * N * sizeof *C);
    for (int i = 0; i < N; i++)
        for (int k = 0; k < N; k++) {
            double x = A[i * N + k];
            for (int j = 0; j < N; j++) C[i * N + j] += x * B[k * N + j];
        }
}

static void __attribute__((noinline))
mm_ikj_r(double *restrict C, const double *restrict A, const double *restrict B)
{
    memset(C, 0, (size_t)N * N * sizeof *C);
    for (int i = 0; i < N; i++)
        for (int k = 0; k < N; k++) {
            double x = A[i * N + k];
            for (int j = 0; j < N; j++) C[i * N + j] += x * B[k * N + j];
        }
}

int main(void)
{
    const long n = 1L << 22;                 /* 4 Mi 个 long，每数组 32 MiB */
    long *a = malloc((size_t)n * sizeof *a), *ar = malloc((size_t)n * sizeof *ar);
    long *b = malloc((size_t)n * sizeof *b), *c = malloc((size_t)n * sizeof *c);
    double *C = malloc((size_t)N * N * sizeof *C), *D = malloc((size_t)N * N * sizeof *D);
    double *A = malloc((size_t)N * N * sizeof *A), *B = malloc((size_t)N * N * sizeof *B);
    if (!a || !ar || !b || !c || !C || !D || !A || !B) { perror("malloc"); return 1; }
    for (long i = 0; i < n; i++) { b[i] = i; c[i] = 2 * i; }

    double tp = 1e30, tr = 1e30;
    for (int r = 0; r < REP; r++) {
        double t0 = now(); addv(a, b, c, n);   double t1 = now();
        addv_r(ar, b, c, n);                   double t2 = now();
        if (t1 - t0 < tp) tp = t1 - t0;
        if (t2 - t1 < tr) tr = t2 - t1;
    }
    long diff = 0, bad = 0;
    for (long i = 0; i < n; i++) {
        if (a[i] != ar[i]) diff++;           /* 两版是否逐元素相同 */
        if (a[i] != 3 * i) bad++;            /* 是否等于解析解 */
    }
    printf("addv   n=%ld plain=%.3f restrict=%.3f ns/elem  diff=%ld bad=%ld\n",
           n, tp / n * 1e9, tr / n * 1e9, diff, bad);

    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++) {
            A[i * N + j] = (double)((i * 17 + j * 3) % 100) / 100.0;
            B[i * N + j] = (double)((i * 29 + j * 7) % 100) / 100.0;
        }
    double mp = 1e30, mr = 1e30;
    for (int r = 0; r < 3; r++) {
        double t0 = now(); mm_ikj(C, A, B);    double t1 = now();
        mm_ikj_r(D, A, B);                     double t2 = now();
        if (t1 - t0 < mp) mp = t1 - t0;
        if (t2 - t1 < mr) mr = t2 - t1;
    }
    double err = 0.0;
    for (int i = 0; i < N * N; i++) {
        double d = C[i] - D[i];
        if (d < 0) d = -d;
        if (d > err) err = d;
    }
    printf("mm_ikj N=%d   plain=%.1f restrict=%.1f ms  maxerr=%.3g\n",
           N, mp * 1e3, mr * 1e3, err);
    free(a); free(ar); free(b); free(c);
    free(C); free(D); free(A); free(B);
    return 0;
}
```

| 编译 | 内核 | 普通指针 | `restrict` | 倍数 |
|:--|:--|--:|--:|--:|
| `-O2` | `addv`（ns/elem） | 0.257–0.273 | 0.195–0.209 | 1.3 |
| `-O2` | `mm_ikj`（ms） | 35.9–37.0 | 19.5–19.9 | 1.8 |
| `-O3` | `addv`（ns/elem） | 0.196–0.212 | 0.193–0.215 | 1.0 |
| `-O3` | `mm_ikj`（ms） | 19.5–22.3 | 11.7–13.4 | 1.6 |

**先看正确性。** `diff=0` 是把 `a` 与 `ar` 逐元素比，`bad=0` 是拿结果与解析解 `3*i` 比；矩阵乘的 `maxerr=0` 只说明这份数据、这个求和顺序下两版一致。`restrict` 不改语义，它只允许编译器换执行顺序；输入不重叠时，两种顺序算出的整数和完全相同。

**`-O3` 的矩阵乘快约六成。** 上面这一跑是 19.5–19.8 → 11.7–12.5 ms；换一次相邻会话，同一份二进制跑出过 22.3 → 13.4 ms，正好与 1.5.11 记的 21.8–24.5 → 13.9–17.1 落在同一档。绝对值随 VM 上别的负载浮动，倍数稳定在 1.6–1.7。原因在汇编：普通版每轮 k 都要比较 `C` 的行与 `B` 的行是否重叠，内层停在一次 2 个 double；`restrict` 版删掉比较，一次 4 个。

**`-O3` 的逐元素相加量不出差别。** 两版都编成 `ldr q0`/`ldr q1` 加 `add v0.2d`，都是 2 路；那 3 条重叠检查被提到循环外，摊到 4 Mi 个元素上不到 0.01 ns。0.196–0.212 与 0.193–0.215 的重叠是运行噪声，不是 `restrict` 的效果。

**`-O2` 行反过来，而且与 1.5.11 的记录不同。** 本节编出的二进制里，`-O2` 下 `addv_r` 已经是 2 路、`addv` 还是标量，所以快三成；1.5.11 记的是两版都停在标量。同一段源码，换个函数边界、有没有被特化，`-O2` 的向量化就落到不同版本上。这不是谁写错，是 `-O2` 的代价模型本来就贴着边界走。**跨节只比 `-O3` 那一行，`-O2` 只比同一张表里的两列。**

把这个数与 1.5.12 放在一起看更有意思：那里的 `ikj` 用三个全局数组，`-O2` 下 21.7–23.0 ms；这里换成三个 `malloc` 指针，普通版掉到 35.9–36.4 ms，加上 `restrict` 才回到 19.5–19.9 ms。同一个内核，只因为编译器没法证明三个指针不重叠，就要多花六成时间。库函数如果收的是 `double *` 而不是 `restrict` 指针，这份代价会转嫁给每个调用者。

两段基准的重复次数不同，这也是有意的：`addv` 单次不到 1 ms，第一次还要付缺页（访问的页不在内存、要内核补进来）的代价，所以在程序内跑 9 次取最小；矩阵乘一次 20–36 ms，跑 3 次就够。取最小压掉的是调度与缺页，报区间是把整个程序再跑几次——两者都写进结论，差异是不是噪声才判断得出来。

::: def 定义 1.5.13 · 基准的可见性 {#def-1.5.13}
一段基准要同时交代三件事：结果对不对（`diff`/`maxerr`）、两版是否真被编成不同的机器码（`noinline` 加 `objdump` 看）、两列是否来自同一次运行同一份数据。缺一条，量到的倍数就可能来自编译器的安排，而不是 CPU 的差异。
:::

程序里四个内核都加了 `__attribute__((noinline))`。去掉它，GCC 会把内核内联进 `main`：`-O3` 下两版都变成 12.6 ms 上下，你会得出「`restrict` 没用」的结论。1.5.11 的汇编结论能成立，前提也是两段内核各自独立编译。`objdump` 里它们还叫 `addv.constprop.0`：GCC 把长度 `n` 当常量特化了一份，所以看汇编要认这个名字，别只看 `addv`。

::: errata 关于这两个基准的四个提醒
1. **「`-O2` 与 `-O3` 的行可以直接拼着看」**——不能。`-O2` 行在本节与 1.5.11 就不一致，因为它由函数边界与特化决定；`-O3` 行才是稳定的对照。
2. **「`maxerr=0` 说明浮点逐位一致」**——它只覆盖这份输入；换求和顺序或展开宽度，末位仍可能不同。整数那两行的 `diff=0` 才是强结论。
3. **「9 次取最小就是稳定值」**——取最小压掉的是干扰，不是波动；表里的区间来自把整个程序跑 3 次，报区间比报一个最小值诚实。
4. **「`restrict` 只写在定义上就行」**——声明与定义分开时两边都要写；只写一处，另一处看到的仍是普通指针，检查还在。
:::

### 1.5.13 小结

① 先校验后计时：`diff=0`、`bad=0` 通过之后，「快」才有意义；② 内核要 `noinline`、两版要交替跑，否则你量到的是内联后的同一段代码；③ `-O3` 下矩阵乘快约六成、逐元素相加无差别，`-O2` 的行随函数边界移动，不可跨节比。如果只记住一件事，那就是：**先确认两版真的不同，再谈快了多少。**

## 1.5.14 实验一：用 perf 定位瓶颈 {#sec-1.5.14}

这一节回答：这台 VM 上 `perf` 连一个事件都打不开，实验还做不做得成？换到能跑的机器上，那张表又该按什么顺序读？

::: preview 先抓住一件事
`perf` 不给数，作废的只是「读计数器」这一步，实验本身仍然成立：把故障原文留下来、把判读表写好、把不依赖 PMU 的三条替代路径跑通。本节没有任何 `perf` 计数是实测的。
:::

先复现故障：查开关，再跑一次统计。

<div class="terminal" data-title="bash · Ubuntu 24.04.5 aarch64 实测">
<pre><span class="p">$</span> cat /proc/sys/kernel/perf_event_paranoid
4
<span class="p">$</span> perf stat -e cycles,instructions,branches,branch-misses ./m128 ikj
Error:
No supported events found.
Access to performance monitoring and observability operations is limited.
Consider adjusting /proc/sys/kernel/perf_event_paranoid setting to open
access to performance monitoring and observability operations for processes
without CAP_PERFMON, CAP_SYS_PTRACE or CAP_SYS_ADMIN Linux capability.
...
perf_event_paranoid setting is 4:</pre>
</div>

这个 4 不是谁手改的：`/etc/sysctl.conf` 与 `/etc/sysctl.d/` 里都没有这一项，是发行版内核的默认值。它比 `perf` 自己列出的「2 = 禁止内核态剖析」更严——`perf stat --all-user -e cycles`（只统计用户态）与 `-e task-clock`（纯软件计时）都被拒了同一句。`perf record` 的报错更具体：

```text
$ perf record -o perf.data ./m128 ikj
Error:
Failure to open event 'armv8_pmuv3_0/cycles/Pu' on PMU 'armv8_pmuv3_0' which will be removed.
```

读法：`cycles` 事件落在 `armv8_pmuv3_0` 这个 PMU 上，打开被拒，perf 就把这个 PMU 从候选里划掉，于是后面所有事件都找不到。

`./m128` 是 1.5.12 的程序改两处编出来的：`#define N 128`，以及用 `argv[1]` 只跑一个内核（`ijk` 或 `ikj`）——一次不到 1 ms，失败几秒内就能复现，而打不开计数器与程序大小无关。

**判读表按「先总量、再分层」排。** 第一列是你该先看的字段，第三列是本章已经测过的等价证据——没有计数器时，那些证据同样能指向同一个结论：

| 看到什么 | 说明 | 先改什么 | 本章的等价证据 |
|:--|:--|:--|:--|
| IPC 低、LLC 缺失高 | 工作集超出末级缓存 | 循环顺序、分块 | `ijk` 73 ms vs `ikj` 22 ms（[1.5.12](#sec-1.5.12)） |
| IPC 低、L1 缺失高 | 内层跨步或未对齐 | 内层连续、少跨步 | cachegrind 的 D1 缺失率 49.7% vs 8.5%（[1.5.15](#sec-1.5.15)） |
| `branch-misses` 占比高 | 控制流不可预测 | 排序、掩码、特化 | 1.408 / 0.271 / 0.333 ns/elem（[1.5.7](#sec-1.5.7)） |
| 后端停顿高 | 执行单元或 load/store 在等 | 拆依赖链、减少访存 | 链数 1→8：0.574 → 0.094 ns/op（[1.5.6](#sec-1.5.6)） |
| 前端停顿高 | 取指/译码供不上 | 减小代码体积、少内联 | 本节无实测 |

顺序不能倒：IPC 先回答「它在不在等」，LLC 与 L1 回答「在等谁」，分支与前后端停顿回答「等多久、等在哪一级」。先看分支失败率再看 IPC，很容易把「缓存在等」误诊成「分支猜错」。

::: def 定义 1.5.14 · 采样剖析 {#def-1.5.14}
`perf record` 不是逐条指令计数，而是按固定频率打断程序，记下此刻的指令地址与调用栈；跑够久之后，把成千上万个样本按函数与指令聚合，落得最多的就是热点。它给的是时间分布，不是精确计数：样本太少时结论会跳，函数很短时可能一个样本都拿不到。
:::

这也解释了为什么 `record` 要跑几百毫秒以上、为什么热点行会漂几条指令。要的是「哪一段在花时间」这个分布，不是「第几条指令执行了几次」这个精确值；后者只有计数器能给。

**三条不依赖 PMU 的替代路径。** 一是墙钟加规模扫描：把工作集从 256 KiB 扫到 64 MiB，每跳成本 0.95 → 2.22 → 18.97 ns，缓存层级的台阶自己会露出来（[1.5.8](#sec-1.5.8)）。二是静态计数折算：`objdump -d` 数内层指令，乘迭代次数除墙钟，得到 IPC 的估算值（[1.5.9](#sec-1.5.9)）；本例两版指令数相同、IPC 差 3 倍，正好把「指令多」排除掉。三是 cachegrind：软件模拟缓存，给确定性的缺失数（下一节）。三条路的精度依次升高，代价也依次升高：墙钟给区间，静态计数给量级，cachegrind 给确定的次数。

换到能跑 `perf` 的机器（`perf_event_paranoid` ≤ 2，或你有 `CAP_PERFMON`），按这个顺序做：

```bash
perf stat -d ./matmul                       # 总量：IPC、L1/LLC、分支
perf record -g -e cycles:u ./matmul         # 采样，带调用图
perf report --stdio --sort symbol | head -20
perf annotate --stdio mm_ijk                # 逐指令占比
```

`-d` 会把 L1/LLC 与 `stalled-cycles-frontend/backend` 一起展开；`annotate` 把采样占比标到指令上，`ijk` 的热点应当落在跨步的 `B[k][j]` load 上。具体百分比要在那台机器上看，不要照抄别人的数。顺序也固定：先 `stat` 看总量，再 `record` 看热点。

::: errata 关于 perf 实验的四个误会
1. **「把 `perf_event_paranoid` 调低就行」**——先要 `sudo`，再要内核允许；这台 VM 的 `sudo` 要密码，所以只能记命令、不改配置。云主机还可能根本不暴露 PMU，调低也没用。
2. **「`--all-user` 能绕开权限」**——实测报同一句 `No supported events found`。它只限定统计范围，不改变谁能打开事件。
3. **「打不开就是没有 PMU」**——两种失败要分开：报错里出现 `perf_event_paranoid` 与 `CAP_PERFMON`，是权限；事件名直接报 `not supported`，是硬件或虚拟机没暴露。
4. **「`annotate` 的热点行就是根因」**——采样点会往后漂几条指令（skid），热点只是「问题出现在这附近」；要结合占比与周围指令判断。
:::

### 1.5.14 小结

① 这台 VM 的 `perf` 只回一句 `No supported events found`，`perf_event_paranoid=4`，`--all-user` 与 `task-clock` 都救不回来；② 判读顺序是 IPC → LLC/L1 → 分支 → 前后端停顿，本章每个字段都能找到已测的等价证据；③ 没有计数器时，规模扫描、静态计数、cachegrind 三条路都能给出方向，精度与代价一起升高。如果只记住一件事，那就是：**工具可以缺席，判据不能缺席。**

::: method 即时自测 · 1.5.14
**Q1（记忆）** `perf stat --all-user` 为什么在这台机器上也失败？
**Q2（辨析）** 有人说「`perf` 打不开就测不了性能」。用本章的三个实验反驳他。
**Q3（应用）** 在一台能跑 `perf` 的机器上，`perf stat -d` 显示 IPC 0.8、LLC 缺失 30%、分支失败 0.2%。先改什么？为什么不是分支？

::: sol 答案
**A1** `--all-user` 只把统计范围限制在用户态，不改变权限；`perf_event_paranoid=4` 下普通账户连用户态事件也打不开。
**A2** 墙钟加规模扫描能看出缓存台阶（0.95 → 22 → 18.97 ns）；静态指令数折算能估 IPC（1.8 vs 5.8–6.2）；cachegrind 能给确定性缺失率（49.7% vs 8.5%）。三者都不需要 PMU。
**A3** 先改访存：LLC 缺失 30% 说明工作集超出末级缓存，IPC 0.8 是它在等内存的结果；分支失败 0.2% 很低，不是瓶颈。先换循环顺序或分块，再看 IPC 是否回升。
:::
:::

## 1.5.15 实验二：用 cachegrind 量化缺失 {#sec-1.5.15}

这一节回答：没有 PMU 权限，怎么拿到一组「换台机器也复现得出来」的缺失数，又怎么保证读出来的不是模拟器的假象？

::: preview 先抓住一件事
Valgrind 的 cachegrind 用软件模拟缓存，同一条命令跑两次给同一组数。`N=128` 上实测：两版指令数只差 0.7%，`D1` 缺失率却是 49.7% 对 8.5%。指令数不是原因，访问模式才是。
:::

先把规模缩到 `N=128`，跑得快些：512 的版本在 cachegrind 下也只要 1.4 秒，128 只要几秒；128 时三块矩阵共 384 KB，而模拟的 D1 只有 16 KB，跨步访问的代价照样暴露。命令与真实输出（valgrind 3.22，Ubuntu 24.04.5 aarch64）：

| 内核 | I refs | D refs | D1 misses | D1 缺失率 | LLd misses |
|:--|--:|--:|--:|--:|--:|
| `ijk` | 8,697,291 | 2,164,919 | 1,075,191 | 49.7% | 9,570 |
| `ikj` | 8,754,853 | 3,229,869 | 274,809 | 8.5% | 13,168 |

**第一件事：指令数几乎一样，缺失差几倍。** `I refs` 差 0.7%，`D1` 缺失次数是 1.08M 对 0.27M（3.9 倍），缺失率 49.7% 对 8.5%（5.9 倍）。把 2.1M 个 MAC 摊开，`ijk` 每个乘加要付 0.51 次 D1 缺失，`ikj` 只付 0.13 次。这和 [1.5.12](#sec-1.5.12) 的 73 ms 对 22 ms 是同一件事的两种量法：一个量时间，一个量原因。

**第二件事：差在一条缓存行只用 8 字节。** `ijk` 的内层沿 `j` 走，每次取 `B[k][j]` 都跨 1024 字节（`N=128` 时一行 1 KiB），一条 64 字节的行里只用到一个 double；`ikj` 的内层连续扫过整行，一个行内的 8 个 double 都用到。`D1mr` 的差距就是这么来的。

次数只是一半，另一半是每次缺失打到哪一级：同样一次 `D1` 缺失，止步于末级和直达内存，代价差一个数量级。所以读这张表要连 `LLd` 一起看，只看 `D1` 会把「末级接得住」的那些缺失算贵了——这也是 [1.5.12](#sec-1.5.12) 里 73 ms 与 22 ms 的由来。**报倍数时一定要带 `N` 与缓存容量。**

**第三件事：末级缺失不能当结论。** `N=128` 时两版 `LLd` 都是 0.4%，看起来「末级没问题」。但 384 KB 的工作集与模拟的 256 KB 末级同量级，大头刚好塞得下。换成 `N=512`（三块矩阵 6 MiB）再跑：`ijk` 的末级缺失率从 0.4% 涨到 50.1%，`ikj` 涨到 8.4%，`LLd` 与 `D1` 几乎重合——这时末级也装不下了。**读 cachegrind 要先看它模拟的容量与你的工作集，再决定哪一行可信。**

要看逐函数、逐行的数，编译时加 `-g`，再用：

```bash
cg_annotate cg_ijk.out --show=Ir,Dr,D1mr,DLmr | head -40
```

输出开头会打印它假定的缓存配置：本节这次是 `D1 16384 B, 64 B, 4-way`、`LL 262144 B, 8-way`。`cg_annotate` 的阈值默认 0.1%，占比更小的函数不会出现。

::: def 定义 1.5.15 · cg_annotate 的列名 {#def-1.5.15}
`Ir` 是取到的指令数，`Dr` 是数据读次数，`D1mr` 是 L1 数据缓存读缺失，`DLmr` 是末级数据缓存读缺失；`m` 是 miss、`r` 是 read，写侧对应 `Dw`、`D1mw`、`DLmw`。这六列就是 cachegrind 的全部词汇，其余都是它们的组合与比值。
:::

它最实用的用法是 A/B 对照：同一份数据、只改一处（循环顺序、块大小、SoA），前后各跑一次，比 `D1mr` 与 `DLmr` 有没有按预期下降，再回头看墙钟。缺失数降了而时间没降，说明瓶颈换地方了——这正是 [1.5.9](#sec-1.5.9) 说的「先确定在等什么」。

::: errata 关于 cachegrind 的四个提醒
1. **「默认 L1 是 32 KB」**——这是旧口径。3.22 在检测不到配置时用 `D1 16 KB`（`cg_annotate` 头部会打印）。容量不同，缺失率就不能和别人比。
2. **「valgrind 里打印的时间也是性能」**——同一次运行，程序自己报 18.88 ms 与 15.03 ms，原生只有零点几毫秒。模拟器串行执行、不建乱序与预取，时间只能用来判断「跑了多久」。
3. **「cachegrind 的缺失数等于真机 PMU」**——它不模拟预取、多核共享与乱序，绝对值只在自己和自己比时有意义。
4. **「函数表里没有我的函数，说明没跑」**——内核被内联进 `main` 时，函数表只剩 `main`；加 `-g` 或 `noinline` 才分得开（[1.5.13](#sec-1.5.13)）。
:::

### 1.5.15 小结

① cachegrind 用软件模拟缓存，给的是可复现的缺失数，不是时间；② 本例两版指令数只差 0.7%，D1 缺失率 49.7% 对 8.5%，把 [1.5.12](#sec-1.5.12) 的时间差归因到了 `B` 的列访问；③ 读数前先看它模拟的容量与 `N`，`N` 一换，末级那一行就换结论；④ 拿它做 A/B，看缺失数有没有按预期降，降了而时间没降就说明瓶颈已经换地方。如果只记住一件事，那就是：**先看模拟的是什么缓存，再信它给的缺失率。**

::: method 即时自测 · 1.5.15
**Q1（记忆）** cachegrind 输出的 `I refs`、`D1 misses`、`LLd misses` 各是什么？
**Q2（辨析）** 两版 `LLd` 都是 0.4%，能说「末级缓存不是瓶颈」吗？
**Q3（应用）** `N` 从 128 换成 512 后，`ikj` 的 D1 缺失率几乎没变（8.5% → 8.4%），`ijk` 的末级缺失率却从 0.4% 跳到 50.1%。为什么？

::: sol 答案
**A1** `I refs` 是取到的指令条数；`D1` 是 L1 数据缓存缺失次数；`LLd` 是末级数据缓存缺失次数（它们都是模拟计数，不是 PMU 读数）。
**A2** 不能。`N=128` 的工作集 384 KB 与模拟的 256 KB 末级同量级，大部分访问塞得下；换成 512 就不成立。
**A3** `ikj` 内层连续，每行 8 个 double 都用满，L1 缺失率由访问模式决定，与总规模关系不大；`ijk` 的 L1 缺失率一直在 50% 左右，规模小时这些缺失被末级接住，规模一过 6 MiB 末级也接不住，`LLd` 就跟着涨到 50%。
:::
:::

## 1.5.16 十二条优化陷阱 {#sec-1.5.16}

这一节回答：前面十一节的手段都学会了，为什么照着做还是可能白忙一场？十二条最常见的坑按「错在哪一步」分成四组，每组三条。

::: preview 先抓住一件事
陷阱的根源往往不是「不知道技巧」，而是「验证方式错了」：测错与算错让你得出错误结论，写错与选错让你改坏代码或改错地方。每组三条，都能在本章找到实测落点。
:::

本章的失败案例其实只错在四个位置：**测**（量到的不是想量的）、**算**（模型套错对象）、**写**（改坏了语义）、**选**（手段与瓶颈不匹配）。按这四组记，比背一张十二行的表有用，因为每组内部是同一个病根。

### 测错：量到的不是想量的

**① 优化了但没快，因为瓶颈不在 CPU。** 代码改得再漂亮，只要时间花在 I/O、锁、内存带宽或缺页（访问的页不在内存里）上，墙钟就不会动。判据是先确认热点真在 CPU 里：[1.5.12](#sec-1.5.12) 的 `ijk` 与 `ikj` 指令数几乎相同，时间差 3.3 倍，差别全在等内存；反过来，如果 IPC 不低而墙钟不掉，就该去查系统调用（程序请求内核代劳的入口）与等待，而不是继续改循环。

**② 基准测的是优化本身，不是程序。** 两个内核被内联进 `main` 后，[1.5.13](#sec-1.5.13) 的 `-O3` 两版都是 12.6 ms 上下——你测到的是编译器合并后的同一段代码。更隐蔽的是「被消除」：循环没有副作用、结果没人用，整段会被删掉。判据是 `objdump` 里两版指令真的不同，或者用 `noinline` 与 `black_box` 把结果钉住。

**③ 一次运行就下结论。** 第一次跑要付缺页与冷缓存，之后还要看频率调节和同机邻居。判据是把整个程序跑 3 次报区间：`0.196–0.212` 与 `0.193–0.215` 的重叠，本身就在告诉你「这一行没有差别」。

### 算错：模型套错了对象

**④ 把指令条数当时间。** [1.5.9](#sec-1.5.9) 的两版内层都是 8 条指令处理 2 个 MAC，时间差 3 倍。指令数只能排除「指令多」这一种解释，解释不了「在等」。

**⑤ CPE 跨机器比。** CPE 含频率与微架构（[1.5.10](#sec-1.5.10)），同一份代码换台机器，关键路径与吞吐上限都会变；0.66 CPE 只在测它的那台机器上有意义。

**⑥ 只算延迟不算吞吐。** 下界是 $\max(L/k,\,1/T)$，不是 $L/k$。[1.5.6](#sec-1.5.6) 的 8 条链是 0.094 ns，不是 0.574/8=0.072——加链到某个数之后，只剩吞吐上限。

### 写错：优化改变了语义

**⑦ 违反 `restrict` 承诺。** 调用方传了重叠区间，向量版读到写之前的旧值；`memcpy` 处理重叠区间同理（[1.5.11](#sec-1.5.11)）。这不是「不优化」，是未定义行为。

**⑧ 改了求和顺序还以为结果不变。** 浮点加法不满足结合律；`-ffast-math` 允许编译器重排，末位就变。要重排就先证明误差在预算内。

**⑨ 展开过头。** [1.5.5](#sec-1.5.5) 的展开把 0.523 降到 0.144 ns/elem，收益来自多累加器破依赖链，不是指令变少；再加到 16 路，寄存器不够，值被挤回栈，反而多出 load/store。

### 选错：手段与瓶颈不匹配

**⑩ 该换算法却在微调循环。** $O(n^2)$ 的循环优化得再好也追不上 $O(n\log n)$；[1.5.9](#sec-1.5.9) 的清单把它排第一，就是这个原因。

**⑪ 分块与 SoA 背口诀。** [1.5.12](#sec-1.5.12) 的 `block64` 比 `ikj` 慢 15%–20%：分块解决的是「同时有太多条流互相挤」，不解决「循环看着不高级」。

**⑫ 把编译选项当优化。** `-O3` 只改编译器敢做什么，改不了算法与数据布局；`-ffast-math` 换的是正确性，不是速度。

::: def 定义 1.5.16 · 负优化 {#def-1.5.16}
负优化（pessimization）指改动之后指标没变好、复杂度与风险却上升的修改。判据只有一条：同一份基准、同一台机器、同一组输入，前后各跑一次，时间或缺失数至少有一项按预期变化；否则回退。复杂度也算成本，读不懂的热循环比慢一点的热循环更贵。
:::

::: errata 三个「优化常识」的反例
1. **「清单上的手段都值得做」**——手段有前置条件。分块要工作集超出缓存才有用，展开要依赖链是瓶颈才有用；[1.5.12](#sec-1.5.12) 里两样都没赢。
2. **「快了两倍就说明方法对」**——先看基线是谁。拿 `-O0` 或关掉向量化的版本当基线，任何改动都「快两倍」；基线必须是发布用的那套选项。
3. **「优化一次就完事」**——换机器、换编译器、换规模，瓶颈会搬家；[1.5.15](#sec-1.5.15) 的 `N` 从 128 换到 512，末级那一行的结论就反了。
:::

### 1.5.16 小结

① 测错的两种典型是「瓶颈不在 CPU」与「测的是被内联/被消除后的代码」，都靠 `objdump` 与区间排除；② 算错多半是把指令数或单机 CPE 当成普适结论；③ 写错与选错的代价最高，一个改坏语义，一个改错层级。如果只记住一件事，那就是：**先证明量到的是真东西，再谈优化。**

::: method 即时自测 · 1.5.16
**Q1（记忆）** 四组陷阱分别对应哪一步出错？
**Q2（辨析）** 你把一个循环展开了 4 路，时间没变，是不是说明展开没用？
**Q3（应用）** 服务端 QPS 掉了 30%，你怀疑是某个热函数。按本节的顺序，第一件事做什么？

::: sol 答案
**A1** 测（量错对象：瓶颈不在 CPU、代码被内联或消除、单次运行）、算（模型套错：指令数当时间、CPE 跨机、只算延迟）、写（改坏语义：违反 `restrict`、改求和顺序、展开过头）、选（层级错：不换算法、背口诀、把编译选项当优化）。
**A2** 不能。先确认两版真的编译成了不同代码（`objdump`），再看限制它的是不是依赖链；若瓶颈在缓存或分支，展开本来就不会有收益。
**A3** 先确认热点与瓶颈位置：采样看时间花在哪个函数，再看它是等 CPU、等内存还是等 I/O；只有在 CPU 上、且瓶颈是依赖链或指令数时，才轮到改写循环。
:::
:::

## 1.5.17 本章小结 {#sec-1.5.17}

这一节回答：这一章学完，你手上多了哪几把尺子？拿到一段「跑得慢」的代码，能不能先算、再测、最后才改？

::: preview 先抓住一件事
判据是：**给你一个循环，你能先算出它的 CPE 下界与瓶颈在哪一级，再拿这台机器去核对；核对不上时说得出是模型漏了哪一项，而不是「再试一个优化」。**
:::

这一章的主线是**从「感觉慢」到「算得清」**。1.5.1–1.5.5 建尺子与第一批手法：CPE、延迟、吞吐三个度量；编译器能做什么、不敢做什么（别名与 UB）；消除循环低效与重复计算；减少调用与不必要的内存引用；循环展开与多累加器。1.5.6–1.5.8 把「为什么快」讲成模型：关键路径与延迟界决定下界，分支预测与无分支代码改变代价，分块、SoA 与预取改的是存储层次那一头。1.5.9–1.5.11 讲怎么定位与怎么算账：没有计数器时用比值与墙钟，有计数器时读 IPC 与缺失率；把「快了多少」写成 CPE 与阿姆达尔定律的账；`restrict` 与别名是编译器「不敢优化」的典型来源。

1.5.12–1.5.16 全部是实测：四种矩阵乘（73 / 22 / 26 / 25 ms，`ikj` 与分块最快）；`restrict` 在同一程序同一选项下让矩阵乘 `-O3` 从 19.5–22.3 ms 降到 11.7–13.4 ms，而逐元素相加两版毫无差别——**「restrict 有没有用」取决于瓶颈是算力还是搬运**；cachegrind 给出 `D1` 缺失率 49.7% 对 8.5%、`N=512` 时末级缺失从 0.4% 涨到 50.1%；`perf` 在本机被 `perf_event_paranoid=4` 挡住，于是 1.5.14 写成「读数怎么判 + 拿不到时用什么替代」。

逐条打勾的达标表在[学习目标自检表](ch05-checklist.md)。这里只留判据：

- **能算**：一个循环的 CPE 下界（延迟 ÷ 展开度、吞吐约束取大者）、展开与多累加器带来的下界变化、分块后的工作集与块大小约束、阿姆达尔定律给出的加速上限。
- **能测**：用 `clock_gettime` 做逐元素计时并剔除固定开销；用 `-O2/-O3`、`-fno-tree-vectorize`、`noinline` 做对照实验，确认自己测的是优化本身而不是内联或常量折叠；用 cachegrind 数 `D1mr`/`DLmr`。
- **能判断**：瓶颈在算力、在搬运、还是在分支；`restrict` 该不该加、加了为什么可能没用；分块什么时候白干；跨机器只比趋势不比值。

如果只记住一件事，那就是**优化要先算再测**：先写出「这个循环的下界是多少、瓶颈在哪一级」，再拿机器验证；反过来「改一改试试」只能得到一堆无法复现的数字——本章每一个倍数后面都跟着它的前提（编译器版本、优化级别、工作集大小），换一个前提就不成立。

::: errata 本章的口径边界
1. **跨节只比 `-O3`**：1.5.11 的 `-O2` 行与 1.5.13 的 `-O2` 测量不一致（前者两版都 35.8–40.9 ms，后者 restrict 版 19.5–19.9 ms），成因是函数边界与 `-O2` 的向量化取舍——比较 restrict 的收益请统一看 `-O3`。
2. **`perf` 在本机不可用**：`perf_event_paranoid=4`，连 `task-clock` 都被拒；本章的缺失数来自 cachegrind 模拟与手算，不是 PMU 读数。
3. **数字绑定机器**：所有 ns 与 ms 都来自那台 4 vCPU 的 aarch64 虚拟机；换机器只保留趋势，不保留比值。
:::

**下一站**：本章的所有优化都建立在「缓存与内存之间搬了多少」这件事上，但缓存为什么有效、缺失从哪来、组相联怎么算，本章只是借用。下一章 [1.6 存储器层次结构](ch06.md) 把这些变成可算的模型；再往下，[1.7 链接与加载](ch07.md) 讲程序怎么变成能跑的二进制。

::: method 即时自测 · 1.5
**Q1（算）** 一个循环每元素一次浮点加法，只有一个累加器；加法延迟 4 周期、吞吐 2 条/周期。CPE 下界是多少？改成 4 个累加器呢？再问：什么时候 4 个累加器也不再带来收益？

**Q2（测）** 你要证明「`restrict` 让这段矩阵乘快了六成」。给出至少两条必须做的对照，并说明如果不做会得出什么假结论。

**Q3（判）** `perf stat` 显示 IPC 0.4、末级缺失率高、分支失败率很低。先优化哪一头？如果 `perf` 完全不可用，你用什么两条证据替代？

**Q4（算）** 一段程序 60% 的时间在可向量化的内层循环、25% 在不可并行的归约、15% 在 I/O。把内层循环优化到原来的 1/4，整体加速比是多少？上限受什么限制？

::: sol 答案
**A1** 单累加器：关键路径是「上一次加法结果 → 下一次加法」，CPE = 4 周期（每元素）。4 个累加器把关键路径切成 4 条独立链，CPE 降到 4/4 = 1 周期/元素；但这时吞吐约束是每周期 2 条加法，即 0.5 周期/元素，取大者仍是 1。再往上加累加器不会更快，因为已经撞到吞吐或前端发射上限——这时的瓶颈从「依赖链」换成了「每拍能发几条」。

**A2** 必须做两条：① 同一份源码、同一优化级别，只改 `restrict` 一个变量（并保留 `noinline` 之类防止内联改变形态）；② 报告重复次数与波动范围，别拿单次最小值当结论。若不做，最常见的假结论是「restrict 没用」——一旦函数被内联、循环被重排，restrict 的收益会被别的优化吃掉或掩盖，你测到的其实是内联而不是 restrict（1.5.13 就复现了这个假象）。

**A3** 先看搬运：IPC 低而末级缺失高，说明大部分时间在等内存，优先做分块、改布局（AoS→SoA）、减少工作集，而不是抠指令。`perf` 不可用时用两条替代证据：① 剥离版对照（只扫 B / 只扫 C 的循环，时间随步长而非运算量变化）；② cachegrind 的 `D1mr`/`DLmr` 随块大小下降、而墙钟不降，说明瓶颈已不在缓存而在算力。

**A4** 内层循环 0.60 → 0.15，总时间 0.15 + 0.25 + 0.15 = 0.55，加速比约 1/0.55 ≈ 1.82。上限由不可并行也不可优化的那部分决定：归约 0.25 与 I/O 0.15 若都不动，极限是 1/0.40 = 2.5；这就是阿姆达尔定律在本章的具体用法。
:::
