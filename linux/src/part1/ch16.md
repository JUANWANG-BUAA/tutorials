## 1.16.1 四阶段流水线：C 与 Rust 的同一张图 {#sec-1.16.1}

这一节回答：从 `hello.c` 到可执行文件，中间到底有几个程序在接力？`cc` 与 `rustc` 又是在哪一步汇合的？

::: preview 先抓住一件事
`cc`/`gcc` 是驱动程序，不是编译器；它按顺序调用预处理、编译、汇编、链接四个程序。Rust 前端走到 LLVM IR 后，最后一步同样调用系统 `cc`/`ld`。两种语言在 ELF 这一层汇合，所以链接错误长得很像。
:::

先在 Ubuntu 24.04（aarch64、GCC 13.3.0）上把四步拆开，每步只喂给下一步一个文件，看体积怎么变：

```bash
gcc -E lab1c16_hello.c -o lab1c16_hello.i
gcc -S lab1c16_hello.i -o lab1c16_hello.s
gcc -c lab1c16_hello.s -o lab1c16_hello.o
gcc lab1c16_hello.o -o lab1c16_hello
wc -c lab1c16_hello.c lab1c16_hello.i lab1c16_hello.s lab1c16_hello.o lab1c16_hello
```

实读五个体积：源文件 76 字节、预处理后 21274 字节、汇编 565 字节、目标文件 1616 字节、可执行文件 70320 字节。`.i` 变大，是因为一行 `#include <stdio.h>` 把整个头文件展开进来；`.o` 只剩指令、符号和待填的重定位；链接后的 70 KB 还包括启动文件、libc 调用桩和动态链接信息。

| 阶段 | C 命令 | Rust 命令 | 输入 → 输出 | 能检查什么 |
|:--|:--|:--|:--|:--|
| 预处理 | `cc -E` | `rustc -Zunpretty=expanded`（nightly） | `.c` → `.i`；`.rs` → 展开源码 | 宏、`#include`、条件编译 |
| 编译 | `cc -S` | `rustc --emit=asm` | 源码 → 汇编 | 优化、内联、向量化 |
| 汇编 | `cc -c` / `as` | `rustc --emit=obj` | 汇编 → `.o` | 指令编码、重定位 |
| 链接 | `cc`（内部 `collect2`→`ld`） | `rustc`（内部调 `cc`/`ld`） | `.o` + 库 → 可执行文件 | 符号、GOT/PLT、段布局 |
| LLVM IR | `clang -S -emit-llvm` | `rustc --emit=llvm-ir` | 源码 → `.ll` | 跨语言优化、LTO 输入 |
| MIR | — | `rustc -Zunpretty=mir`（nightly） | Rust 源码 → MIR | 借用检查、优化前语义 |

`cc` 自己不读 C 语法。它读命令行，拼出 `cc1` 的参数，再拼出汇编器与链接器的参数。想看它最后拼了什么，用 `gcc -v hello.c -o hello`，输出末尾那条 `collect2` 就是真正的链接命令。在本机截到的关键片段是：

```text
collect2 ... -dynamic-linker /lib/ld-linux-aarch64.so.1 ... -pie -z now -z relro
  -o lab1c16_hello ... Scrt1.o crti.o crtbeginS.o ... -lgcc -lc ...
  crtendS.o crtn.o
```

三个信息值得记住。第一，`Scrt1.o`/`crti.o`/`crtbeginS.o` 是启动代码，负责在 `main` 之前布置运行环境。第二，`-lc` 把 libc 接进来，`-lgcc` 提供编译器辅助例程。第三，`-pie -z now -z relro` 是 Ubuntu 的加固默认值，所以生成的可执行文件类型是 `ET_DYN`（位置无关可执行文件），不是老式的 `ET_EXEC`。

Rust 的前半段不同：`rustc` 自己做词法、语法、类型检查，生成 HIR，再做借用检查与单态化，产出 MIR，最后把 LLVM IR 交给 LLVM 生成目标文件。后半段完全相同：它调系统链接器。写作机（macOS arm64、`rustc 1.99.1`）实测 `rustc --print link-args` 的第一个词就是 `cc`；`rustc --emit=llvm-ir` 对 76 字节源码产出 7788 字节 `.ll`。但这台机器的产物是 Mach-O，`readelf` 读不了；VM 又没有 `rustc`，所以 Rust 的链接与运行标为「未实测（VM 无 rustc）」。

把两条流水线叠在一起看：C 的 `cpp → cc1 → as` 对应 Rust 的「展开与类型检查 → MIR → LLVM 后端」；之后都交给 `ld`。差异集中在前端语义（宏与头文件 vs 宏 2.0 与 crate），不在链接。

为什么先看 `.o` 而不是最终文件？`.o` 里的节、符号、重定位都完整，地址还是从 0 开始的占位值；链接后地址被分配、`.rela.text` 被消费掉，线索就断了。`objdump -dr` 在 `.o` 上能逐行标出重定位，在可执行文件上只剩最终地址。

::: def 定义 1.16.1 · 驱动程序 {#def-1.16.1}
驱动程序（driver）是按配置把多个程序串起来的命令行外壳。`cc` 不解析 C，只决定调用哪个预处理器、编译器、汇编器和链接器，并把 `-O2`、`-g`、`-L` 这类选项翻译成各阶段认识的参数。
:::

::: errata 三个流水线误解
1. **「`cc` 就是编译器」**：它只是驱动；`cc -v` 里真正的编译程序是 `cc1`，链接由 `collect2` 调 `ld`。
2. **「Rust 自带链接器，不碰系统工具链」**：`rustc` 只负责生成目标文件，最终仍调 `cc`/`ld`；交叉编译时链接器选错，报错形态和 C 完全一样。
3. **「每一步都必须落盘」**：默认中间文件在临时目录，跑完就删；要留证据就显式写 `-o`，或用 `-save-temps`。
:::

### 1.16.1 小结

流水线的主干是「前端产出目标文件，链接器负责拼装」。C 的四步可以手工拆，Rust 的前端更复杂，但两者在 `.o` 之后走同一条路；看到 `undefined reference` 时，先定位是编译阶段没生成符号，还是链接阶段没找到库。如果只记住一件事：**驱动只是调度员，真正决定产物的是每一阶段的输入与选项**。

## 1.16.2 ELF：节、符号与重定位 {#sec-1.16.2}

这一节回答：一个 `.o` 里到底留下了什么？`readelf` 的每一列该怎样读，哪些信息链接后就消失？

::: preview 先抓住一件事
ELF 用同一套容器装三种文件：可重定位目标文件、可执行文件和共享库。目标文件里最有用的不是指令，而是**节表、符号表和重定位表**；链接器正是按后两张表把占位地址填成真地址。
:::

还是用 1.16.1 的四步，但这次停在 `.o`。在 Ubuntu 24.04（aarch64、GCC 13.3.0）上编译下面的示例，再分别读头和表：

```c
/* lab1c16_elf.c — 观察节、符号与重定位 */
#include <stdio.h>

int g_init = 42;
int g_zero;
static int s_init = 7;
static int s_zero;
const char banner[] = "elf-demo";

__attribute__((weak)) int weak_fn(void) { return 1; }
int add(int a, int b) { return a + b; }

int main(void)
{
    printf("%s: %d\n", banner,
           add(g_init, g_zero) + s_init + s_zero + weak_fn());
    return 0;
}
```

```bash
gcc -std=c17 -O0 -fno-pie -c lab1c16_elf.c -o lab1c16_elf.o
gcc -no-pie lab1c16_elf.o -o lab1c16_elf
readelf -h lab1c16_elf.o | grep -E 'Type|Machine'
readelf -SW lab1c16_elf.o | grep -E '\.(text|data|bss|rodata|symtab|rela)'
readelf -sW lab1c16_elf.o | grep -E 'g_init|g_zero|s_init|banner|weak_fn|printf'
readelf -rW lab1c16_elf.o
```

实读结果：`.o` 的 `Type` 是 `REL`、`Machine` 是 `AArch64`；可执行文件的 `Type` 是 `DYN`，因为 Ubuntu 默认生成 PIE。节表里 `.text` 占 `0xac` 字节、标志 `AX`；`.data` 与 `.rodata` 是 `PROGBITS`；`.bss` 是 `NOBITS`，文件偏移有值但文件里不占这 8 字节。符号表里 `s_init` 是 `LOCAL`、`Ndx=3`（`.data`），`g_zero` 是 `GLOBAL`、`Ndx=4`（`.bss`），`weak_fn` 是 `FUNC WEAK`、`Ndx=1`，`printf` 是 `NOTYPE GLOBAL UND`。

| 文件类型 | `readelf -h` 的 Type | 谁生成 | 典型用途 |
|:--|:--|:--|:--|
| 可重定位目标文件 | `REL` | 编译器/汇编器 | 交给链接器，地址未定 |
| 可执行文件 | `EXEC` 或 `DYN` | 链接器 | 直接加载；PIE 是 `DYN` |
| 共享库 | `DYN` | `cc -shared` | 运行时由 `ld.so` 映射 |

**节（section）是链接器视图，段（segment）是加载器视图。** 链接器按节合并 `.text`、分配 `.data`；加载器只看程序头里的段，把「可读可执行」「可读写」映射进内存。一个段通常包含多个节，所以 `readelf -S` 与 `readelf -l` 的行数对不上是正常的。

符号表的三列要会读。`Bind` 是绑定强度：`LOCAL` 只在本文件可见，`GLOBAL` 可被其他文件引用，`WEAK` 可被强符号覆盖。`Type` 是种类：`FUNC` 函数、`OBJECT` 变量、`NOTYPE` 未标注。`Ndx` 是所在节索引：数字表示「在这个节里」，`UND` 表示「本文件只引用、不定义」，`ABS` 表示绝对值。强符号重复定义会报 `multiple definition`；弱符号机制正是 `__attribute__((weak))` 与 C++ 内联函数的基础。

重定位表回答「哪里要填、填谁、怎么填」。`readelf -rW` 在示例里列出 15 条 `.rela.text`：对 `printf` 的调用是 `R_AARCH64_CALL26`，对 `banner` 的取址是 `R_AARCH64_ADR_PREL_PG_HI21` 加 `R_AARCH64_ADD_ABS_LO12_NC`，同文件的 `add` 也是 `CALL26`。每条记录包含偏移、类型、符号和加数；链接器按类型把符号地址编码进指令。

同一个示例换到 x86-64，名字就变了。写作机用 clang 21 交叉编译一个只调用 `printf` 的小文件，VM 的 `readelf` 读出：

```text
0000000000000011  0000000500000004 R_X86_64_PLT32  0000000000000000 printf - 4
```

`PLT32` 表示「调用点相对 PLT 桩的 32 位偏移」，加数 `-4` 是 PC 相对寻址的修正。aarch64 则是 `CALL26 printf + 0`。两者含义相同：**目标文件不写死绝对地址，把绑定留到链接或加载**。注意这只是 `-c` 层面的对照：GCC 13.3 出 aarch64，clang 21 出 x86，两个编译器、两个架构，不能拿指令条数或代码大小互比；x86 的 `.o` 只能在 VM 上读，不能链接运行。本机 clang 21 没有 RISC-V 后端，RISC-V 的重定位名只按文档列出，未实测。

::: def 定义 1.16.2 · 重定位 {#def-1.16.2}
重定位（relocation）是目标文件里的一条「待填地址」记录：它指明在哪个偏移、用哪种编码、填哪个符号的地址。链接器处理 `.rela.text` 这类静态重定位；动态链接器在加载或首次调用时处理 `.rela.dyn`/`.rela.plt`。
:::

::: errata 三个 ELF 常见误解
1. **「加了 `-g` 才有符号表」**：`.symtab` 默认为链接而生成；`-g` 增加的是 `.debug_*`。`strip` 删 `.symtab` 与调试节，但保留动态链接需要的 `.dynsym`。
2. **「`.bss` 有 64 MiB，文件就该大 64 MiB」**：`.bss` 是 `SHT_NOBITS`，文件里只有一个节头，加载时映射零页，首次写才分配物理页。
3. **「`readelf -r` 列出的重定位运行时要处理」**：`.rela.text` 在链接时就被消费；运行时还在的是 `.rela.dyn`/`.rela.plt`，由 `ld.so` 处理。
:::

::: ex 例 1.16.2 · 先猜：一个等号改了什么 {#ex-1.16.2}
示例里 `int g_zero;` 是未初始化全局，`nm`/`readelf -s` 显示它是 `GLOBAL`、`Ndx=4`（`.bss`），`.bss` 是 `NOBITS`。先猜：只把它改成 `int g_zero = 7;`，四样读数里哪些会变——`.o` 的文件字节数、`size` 的 `data`/`bss` 两栏、`Ndx`、`.bss` 的节大小？哪一样最容易被想反？

::: sol 解答
四样全变，两个 `size` 读数一起变才最容易被忽略。VM 上 GCC 13.3 实测两份 `.o`：`size` 从 `text 300 / data 8 / bss 8` 变成 `text 300 / data 12 / bss 4`——`data+bss` 的和与 `dec` 都是 316，一点没变，变的是**这两个字节要不要落盘**；`readelf -S` 里 `.data` 的 Size 从 `0x8` 涨到 `0xc`、`.bss` 从 `0x8` 缩到 `0x4`；`g_zero` 的 `Ndx` 从 4 变成 3，值从 `0x0` 变成 `0x4`（它排到了 `.data` 里 `g_init` 之后）。想反的那一样是文件大小：`ls -l` 读出 2424 → 2432，多的不是 4 而是 8 字节——`.data` 涨 4 之后各节按对齐重排，`.bss` 本来不占空间，所以省下来的那 4 字节不会从文件里退回去。结论：初值改变的是「谁来存这 8 个字节」，不是「程序要用多少内存」。
:::
:::

### 1.16.2 小结

读 ELF 的顺序是「先看类型，再看节，再看符号，最后看重定位」。类型决定这是不是可执行文件，节告诉你数据放在哪，符号告诉你谁定义谁引用，重定位告诉你链接器还要改哪几个字节；四步都对上，才谈得上「看懂了一个 `.o`」。顺序反了，容易把运行时的动态重定位误当成链接时问题。如果只记住一件事：**`.o` 里所有地址都是待填的占位值，重定位表就是待办清单**。

::: method 即时自测 · 1.16.2
**Q1（记忆）** `Ndx` 列的 `UND`、`ABS` 和数字分别表示什么？
**Q2（辨析）** 为什么 `.bss` 在文件里几乎不占空间，`size` 却把它单列一栏？
**Q3（应用）** 看到一个符号是 `WEAK`，另一个文件里同名符号是 `GLOBAL`，链接后哪个生效？

::: sol 答案
**A1** `UND` 表示本文件只引用未定义；`ABS` 表示绝对值、不属于任何节；数字是节索引，表示定义在该节内。
**A2** `.bss` 是 `NOBITS`，文件只存节头；运行时它占地址空间与内存，所以 `size` 用 `bss` 列单独统计。
**A3** 强符号 `GLOBAL` 覆盖弱符号 `WEAK`；若两个都是强符号才报 `multiple definition`。
:::

## 1.16.3 静态库、动态库与 GOT/PLT {#sec-1.16.3}

这一节回答：`.a` 与 `.so` 到底差在哪？一次 `printf` 调用又怎样经过 GOT/PLT 落到 libc？

::: preview 先抓住一件事
`.a` 是 `.o` 的归档，链接时按需抽取，代码进最终文件；`.so` 整库映射，运行时由 `ld.so` 按 SONAME 查找。共享库必须用 `-fPIC` 编译；外部调用走「调用点 → PLT 桩 → GOT 表项 → libc」。
:::

库不是「一种文件」，而是两种交付方式：**静态库**（`.a`，一组 `.o` 的归档，链接时按需抽取）和**共享库**（`.so`，运行时由 `ld.so` 映射）。同一个 `mathlib.c` 可以同时产出两者。下面的 `mathlib` 是本章的完整程序一：头文件、实现、主程序、版本脚本一应俱全。

<div class="variant" data-arch="all" data-lang="c">

```c
/* mathlib.h — 公开接口；C 与 Rust FFI 都用它 */
#ifndef MATHLIB_H
#define MATHLIB_H

#include <stddef.h>

struct pair { long a; long b; };

long math_sum(const long *xs, size_t n);
long pair_sum(struct pair p);
long math_dot(const long *a, const long *b, size_t n);
const char *math_version(void);

#endif
```

</div>

<div class="variant" data-arch="all" data-lang="c">

```c
/* mathlib.c — 编译成 libmath.a 和 libmath.so */
#include "mathlib.h"

long math_sum(const long *xs, size_t n)
{
    long s = 0;
    for (size_t i = 0; i < n; i++)
        s += xs[i];
    return s;
}

long math_dot(const long *a, const long *b, size_t n)
{
    long s = 0;
    for (size_t i = 0; i < n; i++)
        s += a[i] * b[i];
    return s;
}

long pair_sum(struct pair p)
{
    return p.a + p.b;
}

const char *math_version(void)
{
```

构建静态库与共享库（Ubuntu 24.04 aarch64、GCC 13.3.0 实测）：

```bash
# 1) 统一用 -fPIC 编译，静态库也能受益于 PIC（略有开销）
cc -std=c17 -D_GNU_SOURCE -O2 -Wall -Wextra -Werror -fPIC -c mathlib.c -o mathlib.o

# 2) 静态库：ar 归档；链接时只抽取用到的成员
ar rcs libmath.a mathlib.o

# 3) 共享库：SONAME 是运行时依赖的名字；版本脚本限制导出
cc -shared -Wl,-soname,libmath.so.1 \
   -Wl,--version-script=mathlib.map mathlib.o -o libmath.so.1.0
ln -sf libmath.so.1.0 libmath.so.1
ln -sf libmath.so.1 libmath.so

# 4) 链接：动态版用 -lmath，静态版直接给 .a
cc -std=c17 -D_GNU_SOURCE -O2 -Wall -Wextra -Werror main.c \
   -L. -lmath -Wl,-rpath,'$ORIGIN' -o app-dynamic
cc -std=c17 -D_GNU_SOURCE -O2 -Wall -Wextra -Werror main.c libmath.a -o app-archive

# 5) 验证
./app-dynamic && ./app-archive
readelf -d app-dynamic | grep -E 'NEEDED|RPATH|RUNPATH|BIND'
readelf -d libmath.so.1.0 | grep SONAME
nm -D --defined-only libmath.so.1.0
ldd app-dynamic
```

两个程序都打印 `mathlib 1.0: sum=10 dot=300`。`readelf -d app-dynamic` 实读到三条 `NEEDED`（`libmath.so.1`、`libc.so.6`、`ld-linux-aarch64.so.1`）、`RUNPATH` 为 `[$ORIGIN]`、`FLAGS` 为 `BIND_NOW`；`libmath.so.1.0` 的 `SONAME` 是 `libmath.so.1`；`nm -D` 只列出三个带版本后缀的符号，如 `math_sum@@MATHLIB_1.0`。`LD_DEBUG=bindings` 会打出「哪个文件把符号绑到哪个库」的行，例如 `binding file ./app-dynamic ... to .../libmath.so.1: normal symbol 'math_sum'`。

`-Wl,-rpath,'$ORIGIN'` 把「到可执行文件所在目录找库」写进 `DT_RUNPATH`（新链接器）或 `DT_RPATH`（老链接器）。shell 里必须用单引号包住 `$ORIGIN`，否则会被展开成空串；这是构建脚本最常见的坑之一。还要注意：`app-archive` 只把 `libmath` 的代码放进了可执行文件，**不代表全静态**；它仍然 `NEEDED libc.so.6`，本机两个版本都在 70 KB 量级，静态版并没有更小。要真正不依赖 `ld.so`，得加 `-static`。

::: def 定义 1.16.3 · SONAME {#def-1.16.3}
SONAME（shared object name）是共享库写进自己动态段的「运行时名字」，链接器把它抄进可执行文件的 `NEEDED`。`libmath.so.1.0` 是文件名，`libmath.so.1` 是 SONAME；升级到 `1.1` 时只要 SONAME 不变，已编译的程序不必重链。
:::

### GOT/PLT：一次外部调用发生了什么

动态库的代码在链接时不知道自己在进程里的加载地址，因此不能把 `printf` 的绝对地址写死。ELF 用**位置无关代码（PIC）** + **GOT/PLT** 解决：

<pre class="layout">
调用点（.text）                   .plt                         .got.plt
call printf@plt  ───────────────▶ printf@plt:
                                    jmp *printf@GOT(%rip) ───▶ [printf 的真实地址]
                                    push $reloc_index                 ▲
                                    jmp plt0                          │
                                                                      │
第一次调用：GOT 里是 plt0 的 resolver 地址 ──▶ ld.so 解析 ──▶ 写回 GOT
之后调用：jmp *GOT 直接到 libc，不再进 resolver
</pre>

- **GOT（Global Offset Table）** 是数据段里的一张指针表，保存外部符号的运行时地址。
- **PLT（Procedure Linkage Table）** 是一小段代码桩，第一次调用负责触发解析，之后只是间接跳转。
- **延迟绑定（lazy binding）** 只有真正调用到的函数才解析；`-Wl,-z,now` 则改成加载时全部解析。注意本机构建的 `app-dynamic` 动态段直接带 `BIND_NOW`，因为 Ubuntu 的 GCC 13.3 驱动默认传 `-z now`（1.16.1 的链接行里能看到）；要看 lazy，得显式加 `-Wl,-z,lazy` 重建。
- **`-fno-plt`** 让调用点直接 `call *printf@GOT(%rip)`，省掉 PLT 一跳，但需要 GOT 可读；现代发行版常用。
- **RELRO** 把 GOT 在重定位后设为只读，防止 GOT 劫持；`-Wl,-z,relro,-z,now` 是完整 RELRO。

观察命令：

```bash

objdump -d -j .plt app-dynamic
objdump -d -j .plt.sec app-dynamic 2>/dev/null   # -fcf-protection 下可能有 .plt.sec

# 动态重定位：JUMP_SLOT 对应 PLT，GLOB_DAT 对应数据符号
readelf -rW app-dynamic | grep -E 'JUMP_SLOT|GLOB_DAT|RELATIVE'

# 动态段：NEEDED、SONAME、RPATH/RUNPATH、BIND_NOW、FLAGS
readelf -dW app-dynamic

# 运行时绑定过程（只看 mathlib 相关）
LD_DEBUG=bindings ./app-dynamic 2>&1 | grep -E 'math_(sum|dot|version)|printf' | head
```

`LD_DEBUG=bindings` 的输出会显示每个符号从哪个对象解析到哪个地址；如果看到 `binding file ./app-dynamic ... to .../libmath.so.1: normal symbol 'math_sum'`，说明动态链接器按 `NEEDED` 找到了库。找不到时先看 `ldd`，再看 `DT_RUNPATH`，最后看 `LD_LIBRARY_PATH` 和 `/etc/ld.so.cache`（`ldconfig -p`）。

::: errata 共享库的四个常见误解
1. **「库文件存在，链接就不该报 `undefined reference`」**：传统 `ld` 单遍扫描，`-lmath` 放在引用它的 `.o` 之前时，归档成员一个都不会被抽取；调换顺序或改用 `--start-group`。
2. **「`-Wl,-rpath,$ORIGIN` 不加引号也行」**：shell 会先展开 `$ORIGIN`，写进动态段的是空串；必须写成 `'$ORIGIN'`。
3. **「`-fPIE` 可以替代 `-fPIC`」**：进 `.so` 的目标文件要用 `-fPIC`；`-fPIE` 是给可执行文件的，塞进共享库可能报 `relocation ... can not be used when making a shared object`。
4. **「动态链接默认一定是延迟绑定」**：是否 lazy 由链接选项决定；加固发行版常默认 `-z now`，本机就是如此。
:::

### 1.16.3 小结

`.a` 与 `.so` 的差别不在打包格式，而在交付时机：前者在链接时把成员代码放进可执行文件，后者把绑定推迟到加载或首次调用。SONAME 决定运行时要找哪个名字，`RUNPATH` 决定去哪找，`-fPIC` 决定这段代码能不能被映射到任意地址；GOT/PLT 则是这套延迟绑定在指令层的实现。如果只记住一件事：**库存在不等于链接成功，链接成功不等于运行找得到**。

## 1.16.4 优化：`-O2` 与 `-C opt-level=3` 各做什么 {#sec-1.16.4}

这一节回答：`-O2` 与 `-C opt-level=3` 到底各开了什么？为什么同一个优化等级，在不同编译器上看到的代码形状会不一样？

::: preview 先抓住一件事
优化等级不是「速度旋钮」，而是一组优化 pass 的名字。GCC 的 `-O2` 与 LLVM 的 `opt-level=3` 是两套不同的管道；能比较的是同一编译器、同一版本、同一架构下的产物，跨编译器只能比「有没有做某类变换」，不能比绝对值。
:::

先用同一段求和循环，在 Ubuntu 24.04（aarch64、GCC 13.3.0）上编四个等级，只看 `-S` 与 `size`：

```c
/* lab1c16_opt.c — 只看 sum 的生成结果 */
#include <stddef.h>
#include <stdio.h>

__attribute__((noinline))
long sum(const long *a, size_t n)
{
    long s = 0;
    for (size_t i = 0; i < n; i++)
        s += a[i];
    return s;
}

int main(void)
{
    long a[64];
    for (size_t i = 0; i < 64; i++) a[i] = (long)i;
    printf("%ld\n", sum(a, 64));
    return 0;
}
```

```bash
for o in 0 1 2 3; do
  gcc -std=c17 -Wall -Wextra -O$o -S lab1c16_opt.c -o lab1c16_opt-O$o.s
  gcc -std=c17 -Wall -Wextra -O$o lab1c16_opt.c -o lab1c16_opt-O$o
done
size lab1c16_opt-O0 lab1c16_opt-O1 lab1c16_opt-O2 lab1c16_opt-O3
```

实读 `text` 段：`-O0` 2085 字节、`-O1` 2007 字节、`-O2` 2071 字节、`-O3` 2159 字节。等级升高，体积并不单调下降：`-O1` 最小，`-O3` 反而比 `-O0` 大 74 字节，因为它做了向量化并展开尾部。

汇编形状更直观。`-O0` 的 `sum` 每次迭代都从栈上取数组指针、下标和累加值，再写回栈：

```asm
ldr x0, [sp, 24]      // i
lsl x0, x0, 3
ldr x1, [sp, 8]       // a
add x0, x1, x0
ldr x0, [x0]          // a[i]
ldr x1, [sp, 16]      // s
add x0, x1, x0
str x0, [sp, 16]
```

`-O2` 把 `s` 放进寄存器，循环缩成「指针后移、比较、加法」四条主体指令，没有向量化：

```asm
ldr x1, [x2], 8
add x0, x0, x1
cmp x2, x3
bne .L3
```

`-O3` 在这段循环上生成了 NEON 向量版本：一次 `ldr q1` 取两个 64 位元素，`add v0.2d` 并行累加，最后 `addp d0, v0.2d` 归约，再单独处理奇数尾部。

换一个编译器，同一个 `-O2` 就不是这个形状。写作机用 clang 21 交叉编译同一段求和的 x86-64 版本（只到 `-S`/`-c`，不链接运行），`-O2` 已经出现 `movdqu`/`paddq` 的 SSE2 两路向量化，`-O3` 再展开成四路。也就是说，**「`-O2` 会不会向量化」取决于编译器与版本**，不能把 GCC 13.3 aarch64 的读数搬到 clang 21 x86 上。

Rust 侧的命令形状是 `rustc -C opt-level=0/2/3 --emit=asm`，`cargo --release` 默认 `opt-level=3`。VM 没有 `rustc`，这一段的运行与产物一律标「未实测（VM 无 rustc）」；写作机的 `rustc 1.99.1` 能出汇编，但产物是 Mach-O，不能拿 `readelf` 读，也不能和上面的 ELF 混比。能说的只有映射关系：`-C opt-level` 交给 LLVM 的优化管道；Rust 还会保留边界检查、别名元数据和 panic 分支，所以即使等级相同，也不等于 C 的 `-O3` 逐条等价。

| 开关 | C（GCC 13.3） | Rust（1.99.1） | 主要影响 |
|:--|:--|:--|:--|
| 基础优化 | `-O2` | `-C opt-level=2`（release 默认 3） | 内联、常量传播、DCE、循环简化 |
| 激进优化 | `-O3` | `-C opt-level=3` | 向量化、循环展开、更多内联 |
| 体积优先 | `-Os` | `-C opt-level=s` | 减小代码，可能牺牲速度 |
| 目标 CPU | `-march=`/`-mtune=` | `-C target-cpu=` | 使用 AVX/NEON 等扩展 |
| 溢出检查 | 有符号溢出是 UB，默认不检查 | debug 默认检查，release 默认关闭 | Rust 可用 `-C overflow-checks=on` |
| 调试断言 | `-DNDEBUG` 控制 `assert` | `-C debug-assertions=on/off` | 影响 `debug_assert!` |
| 代码单元 | 无 | `-C codegen-units=1` | 更多跨单元内联，编译更慢 |
| LTO | `-flto` | `-C lto=fat`/`thin` | 跨文件/跨 crate 优化 |

::: errata 优化等级不是「越高越快」
1. **「`-O3` 一定比 `-O2` 快」**：本机 GCC 13.3 aarch64 上，`-O3` 的 `text` 比 `-O2` 大 88 字节；是否更快要看输入与缓存，必须同机同版本计时，不能只看等级。
2. **「`-O2` 在哪个编译器上都一样」**：GCC 13.3 的 `-O2` 在这段循环上没向量化，clang 21 的 `-O2` 已经向量化；等级名相同，管道不同。
3. **「`-march=native` 编出的包哪儿都能跑」**：它使用构建机的指令集扩展，换到不支持该扩展的机器会 `SIGILL`；发布包用基线。
4. **「Rust 的 `opt-level=3` 自动带 LTO」**：不会；`codegen-units` 默认 16，跨单元内联受限，要显式开 LTO 并调小单元数。
5. **「`-fno-strict-aliasing` 修好了 bug」**：它只关掉编译器的别名假设，UB 仍在；正确修法是用 `memcpy`/`union`/`char *` 表达别名。
6. **「`unsafe` 会自动变快」**：优化器仍受别名、边界与 panic 路径约束，去掉检查不等于一定更快。
:::

::: ex 例 1.16.4 · 先猜：四档谁最大 {#ex-1.16.4}
同一段求和源码在 VM 上用 GCC 13.3（aarch64）编四档，先猜 `text` 从大到小的排序，并猜「等级越高体积越小」这句常见说法错在哪。

::: sol 解答
实读是 `-O0` 2085、`-O1` 2007、`-O2` 2071、`-O3` 2159 字节——既不是单调下降，也不是「`-O2` 一定比 `-O0` 小」。`-O1` 最小（只做便宜的优化，体积不涨）；`-O2` 略回升；`-O3` 最大，因为它在这个循环上做了 NEON 向量化并额外展开尾部，多出的指令换的是运行时间而不是体积。「体积随等级单调」之所以是错觉：优化器同时在做两件方向相反的事——删冗余（变小）和展开/向量化/内联（变大），哪边赢取决于源码形状。同一段代码换 clang 21 交叉编 x86-64，`-O2` 就已经向量化（`movdqu`/`paddq`），说明「哪一档开始变大」还取决于编译器，不能只记等级名。
:::
:::

### 1.16.4 小结

优化发生在 IR 上：前端把源码变成中间表示，优化器按等级选择 pass，后端再生成指令。`-O2` 与 `-O3` 的差别是「多开哪些变换」，不是「保证快多少」；看到体积或时间数字，先问编译器、版本、架构和完整命令行。本节的字节数只属于这组源码、这台 Ubuntu 24.04 VM 与 GCC 13.3.0（aarch64）；只有同版本、同架构、同命令行才可比，换任一项先重跑再引用。如果只记住一件事：**优化等级只在同一工具链内可比，跨编译器只比形状与机制**。

## 1.16.5 LTO、节回收、可见性与 strip {#sec-1.16.5}

这一节回答：为什么加了 `-flto` 之后 `nm` 里少了个函数？`strip` 删掉符号表，动态链接为什么照样能跑？

::: preview 先抓住一件事
LTO 把「每个 `.c` 单独优化」换成「整个程序一起优化」；节回收删掉没有任何人引用的代码；`strip` 只删调试节和静态符号表，不碰运行时绑定要用的 `.dynsym`。三者都在缩小产物，但删掉的东西完全不同。
:::

先做一个两文件实验：`t_help.c` 里只有 `helper`，`t_main.c` 里有 `compute` 和 `main`。同一份源码普通编一次、`-flto=auto` 编一次，都留在 `-O2`：

```c
/* t_help.c */
long helper(long x) { return x * 2 + 1; }

/* t_main.c */
#include <stdio.h>
long helper(long x);
long compute(long x) { return helper(x) + helper(x + 1); }
int main(void) { printf("%ld\n", compute(20)); return 0; }
```

```bash
cc -O2 t_help.c t_main.c -o plain
cc -O2 -flto=auto t_help.c t_main.c -o lto
size plain lto
nm plain | grep -E ' (T|t) (helper|compute|main)'
nm lto   | grep -E ' (T|t) (helper|compute|main)'
```

Ubuntu 24.04（aarch64、GCC 13.3.0）实读：`plain` 的 `text` 是 1798 字节，`lto` 是 1650 字节；`nm plain` 列出 `helper`、`compute`、`main` 三个 `T`，`nm lto` 只剩 `main`。反汇编 `plain` 的 `compute` 能数到两条 `bl <helper>`；`lto` 里已经找不到独立的 `compute`，它被内联进 `main` 后连同符号一起消失。

机制在「编译器一次能看到多少」。没有 LTO，编译器每次只看一个 `.c`，不知道别的文件里 `helper` 的代码长什么样，只能留一次真实调用。`-flto` 让 `.o` 里存的不是最终机器码，而是中间表示（IR）；链接时由链接器加载的 LTO 插件把这些 IR 合成一个整体，再交给优化器。跨文件内联、跨文件常量传播、跨文件死代码删除因此才成立。代价是链接变慢、内存占用上升，因为所有 IR 必须留到最后一步。

第二个手段是节回收。默认一个 `.c` 的所有函数挤在同一个 `.text` 节里，链接器没法按函数丢弃。加 `-ffunction-sections -fdata-sections` 后，每个函数、每个变量各成一节：

```bash
cc -O2 -c t_main.c -o sec_off.o
cc -O2 -ffunction-sections -fdata-sections -c t_main.c -o sec_on.o
readelf -SW sec_on.o | grep '\.text\.'
```

实读到 `.text.compute` 与 `.text.startup.main` 两节；不加选项时只有一个 `.text`。这时再加 `-Wl,--gc-sections`，链接器从入口函数出发做可达性分析，没人引用的节整段删掉。用一个带未调用函数的 `lto_b.c` 对照：不加选项 `text` 1749 字节，加了 1641 字节，那个函数连同符号从 `nm` 里消失。

::: def 定义 1.16.5 · 链接时优化 {#def-1.16.5}
链接时优化（Link Time Optimization，LTO）是把编译器的中间表示保留到链接阶段，由链接器调用的插件统一优化后再生成机器码的构建方式。它交换的是「编译快、链接慢」——用更长的链接时间，换编译器本来看不到的跨文件信息。
:::

第三件事是可见性。共享库默认把所有非 `static` 函数写进 `.dynsym`，别的程序能链、能 `LD_PRELOAD`。`-fvisibility=hidden` 把默认可见性改成隐藏，版本脚本再放行白名单。两个手段叠加过量，导出会变成空——这是本机实测到的：

```bash
cc -shared -fPIC -O2 mathlib.c -o libmath-open.so
cc -shared -fPIC -O2 -fvisibility=hidden \
   -Wl,--version-script=mathlib.map mathlib.c -o libmath-hidden.so
nm -D --defined-only libmath-open.so     # 三个 math_ 函数
nm -D --defined-only libmath-hidden.so   # 只剩版本节点 MATHLIB_1.0
```

拿 `libmath-hidden.so` 去链 `main.c`，链接器直接报 `undefined reference to 'math_sum'`。修法不是删版本脚本，而是在要导出的函数上写 `__attribute__((visibility("default")))`，或只用版本脚本一种手段。判断标准永远是 `readelf --dyn-syms`，不是「我写了导出列表」。

`strip` 删的是另一批东西。对前面 1.16.3 的 `app-dynamic` 实测：`strip --strip-all` 后文件从 70592 字节降到 67496 字节，`readelf -SW` 里再也找不到 `.symtab` 与 `.debug_*`，但 `.dynsym` 还在，程序照常跑。原因是动态链接只认 `.dynsym`，而崩溃栈里的函数名依赖 `.symtab` 与 `.debug_line`。所以发布版可以 strip，但要另存一份未 strip 的产物，或用 `objcopy --only-keep-debug` 分离出 debug 文件。

Rust 侧的写法是 `[profile.release]` 里的 `lto = "fat"`、`codegen-units = 1`、`strip = "symbols"`。这几项的效果方向与上面相同，但 VM 没有 `rustc`/`cargo`，体积与符号变化一律标「未实测（VM 无 rustc）」，不要拿 C 的字节数类比。还有一个常见说法要打折：本机 binutils 2.42 下，用普通 `ar` 打包 LTO 对象后经 `cc` 链接并没有报 `plugin needed to handle lto object`，因为 `cc` 自己会加载插件；这个报错取决于 binutils 版本与调用路径，不能当成必然。

| 手段 | 删掉/改动什么 | 拿什么复核 |
|:--|:--|:--|
| `-flto=auto` | 跨文件重复计算、可内联的调用 | `nm`、`size`、`objdump -d` |
| `-ffunction-sections` + `--gc-sections` | 未被引用的整个函数/变量节 | `readelf -SW`、`nm` |
| `-fvisibility=hidden` + 版本脚本 | 动态符号表里的非白名单项 | `readelf --dyn-syms` |
| `strip` | `.symtab`、`.debug_*` | `nm`、`readelf -SW`、崩溃栈 |

::: errata 裁剪手段的三个误解
1. **「`strip` 会把动态符号也删掉，所以库不能 strip」**：默认保留 `.dynsym`；本机 strip 后 `nm -D` 照常列出导出。
2. **「`-flto` 就是多开一个优化等级」**：它改的是优化发生的位置，跨文件信息只在链接期才有；单独加 `-O3` 拿不到同样的内联。
3. **「加了 `--gc-sections` 就一定变小」**：前提是函数已经分节；不配 `-ffunction-sections` 时链接器只有一整块 `.text`，什么都删不掉。
:::

### 1.16.5 小结

三条路解决三个不同问题：LTO 让优化器看见整个程序，节回收让链接器扔掉没人要的代码，可见性与 strip 让发布产物少暴露信息。它们的共同前提是先有「更细的边界」——IR、独立的节、明确的导出列表；边界不存在，后面的删除就无从谈起。如果只记住一件事：**裁剪的收益来自「本来就是死代码」，不是来自开关本身**。

**Q2（辨析）** 为什么本机 `-fvisibility=hidden` 加版本脚本后导出是空的，而单用版本脚本正常？

## 1.16.6 `no_std`、panic 与 `abort`：把运行时拆掉 {#sec-1.16.6}

这一节回答：一个普通程序默认背着哪些看不见的依赖？把标准库拆掉以后，缺的那几块由谁补上？

::: preview 先抓住一件事
Rust 的 `std` 与 C 的 libc 是同一层东西：文件、线程、堆、panic 展开都靠它们。`#![no_std]` 只留 `core`；C 的对应做法是 `-ffreestanding -nostdlib`。两者的共同代价是：入口、出错动作、内存来源都得你自己指定。
:::

先用 C 做一次，因为这台 VM 能直接跑。下面这段不包含任何头文件，也不调用 libc，只把两个系统调用号（进程请内核办事时传的编号，比如 `write` 是 64、`exit` 是 93）塞进寄存器，用 `svc #0` 进内核：

```c
/* lab1c16_free2.c — aarch64 freestanding：write(1, msg, n) 然后 exit(0) */
typedef unsigned long usize;
static long sys_write(int fd, const char *buf, usize n)
{
    register long x8 __asm__("x8") = 64;      /* __NR_write */
    register long x0 __asm__("x0") = fd;
    register long x1 __asm__("x1") = (long)buf;
    register long x2 __asm__("x2") = n;
    __asm__ volatile("svc #0" : "+r"(x0) : "r"(x8), "r"(x1), "r"(x2) : "memory");
    return x0;
}
static void sys_exit(long code)
{
    register long x8 __asm__("x8") = 93;      /* __NR_exit */
    register long x0 __asm__("x0") = code;
    __asm__ volatile("svc #0" :: "r"(x8), "r"(x0) : "memory");
    __builtin_unreachable();
}
void _start(void)
{
    static const char msg[] = "freestanding ok\n";
    sys_write(1, msg, sizeof msg - 1);
    sys_exit(0);
}
```

```bash
cc -std=c17 -ffreestanding -nostdlib -static -Wl,-e,_start -O2 lab1c16_free2.c -o free2
./free2; echo "rc=$?"          # freestanding ok + rc=0
ls -l free2                     # 1632 字节
readelf -hW free2 | grep -E 'Type|Entry'
ldd free2                       # not a dynamic executable
size free2                      # text 129 / data 0 / bss 0
```

实读（VM 复跑，GCC 13.3.0-6ubuntu2~24.04.1）：可执行文件 1632 字节，`text` 只有 129 字节、`data`/`bss` 都是 0，`Type` 是 `EXEC`（不是 PIE），入口 `0x400110` 正好是 `_start`；`ldd` 说 `not a dynamic executable`，`nm -u` 一行未定义符号都没有，`./free2` 打印后返回 `rc=0`。同一份代码在 x86-64 上要把 `svc #0` 换成 `syscall`、系统调用号换成 1 与 60；VM 是 aarch64，x86 版本未实测。

这段代码值得停一下，因为它最初的写法是**错的**，而且错得查不出来。早先 `_start` 里把 `exit` 的那条 `svc` 直接写在这个函数里：

```c
void _start(void)
{
    static const char msg[] = "freestanding ok\n";
    register long x8 __asm__("x8") = 93;      /* 看起来像「退出」 */
    register long x0 __asm__("x0") = 0;
    sys_write(1, msg, sizeof msg - 1);
    __asm__ volatile("svc #0" :: "r"(x8), "r"(x0) : "memory");
    for (;;) { }
}
```

`objdump -d` 给出的是五行指令、一个死循环（实测原文）：

```text
  400110:	adrp	x1, 400000 <_start-0x110>
  400114:	mov	x8, #0x40                  	// #64
  400118:	add	x1, x1, #0x130
  40011c:	mov	x0, #0x1                   	// #1
  400120:	mov	x2, #0x10                  	// #16
  400124:	svc	#0x0
  400128:	svc	#0x0
  40012c:	b	40012c <_start+0x1c>
```

**那个 93 从来没有出现在指令里。** `sys_write` 被内联后，编译器为它把 64 装进 `x8`；接着它看到第二个 `svc` 的操作数是 `"r"(x8)`，就照用寄存器里现成的值——于是第二条 `svc` 又执行了一次 `write`，`x0` 此时是上一次调用的返回值 16（当成 fd 用，得到 `EBADF`），然后落进 `for(;;)`。程序照样打印那行字，看起来一切正常，但**永远不会退出**：`timeout 5 ./free` 的退出码是 124。

修法只有一句：把每条 `svc` 关进一个自己的 `asm` 块，让「装编号」和「陷入」之间没有任何可能被优化的余地。改后的反汇编多出两行，正是缺的那两行：

```text
  400128:	mov	x8, #0x5d                  	// #93
  40012c:	mov	x0, #0x0                   	// #0
  400130:	svc	#0x0
```

这也是「register variable + 内联汇编」这条语言的通行规矩：**跨语句、跨调用的寄存器变量不是承诺**，GCC 的手册把它列在「值可能不符合你的期待」的情形里。裸机与内核代码里最常见的写法就是把每个系统调用封装成一个独立小函数，正是这个原因。

没了 libc，你少的是三样东西。第一是启动代码：正常程序先跑 `_start`，由它准备参数、调用 `main`、再用 `exit` 收尾；`-nostdlib` 把这段拿走，所以要 `-Wl,-e,_start` 亲手指定入口。第二是系统调用包装：`printf`、`write` 这些函数本体都在 libc 里，没了它们就得自己写内联汇编。第三是出错时的默认动作：没有 `abort`、没有栈展开、没有 `atexit`，进程不能返回，只能 `exit` 或死循环。顺带一提，平时能 `return 0` 就退出，也是启动代码在背后替你调用 `exit`。

只写应用层的人也会碰到这套东西。容器镜像从 `scratch` 起步、静态链接的 Go/Rust 二进制、救援环境里没有 libc 的工具，都是「把运行时拆掉」的产物；排查它们时，`ldd` 说 `not a dynamic executable` 不是异常，而是设计。反过来，如果某个静态二进制在容器里起不来，先怀疑它其实还依赖 `/etc` 下的配置文件或 DNS 库，而不是「少了 libc」。

Rust 的情况对称，只是「默认的那层」叫 `std`。`std` 依赖操作系统提供文件、线程、时钟、动态内存和 panic 展开；写内核模块、引导程序、固件时这些都没有，于是用 `#![no_std]` 只链接 `core`（可选再链接 `alloc`）。`core` 里只有语言本身需要的东西：整数、浮点、切片、`Option`、`Result`；`alloc` 加上 `Vec`、`String`、`Box`，但要求你先提供一个分配器；`compiler_builtins` 补上目标平台没有的运算例程。一个最小静态库长这样：

```rust
// nostd.rs — 未实测（VM 无 rustc）
#![no_std]
use core::panic::PanicInfo;

#[panic_handler]
fn panic(_info: &PanicInfo) -> ! { loop {} }

#[no_mangle]
pub extern "C" fn no_std_add(a: i32, b: i32) -> i32 { a.wrapping_add(b) }
```

```bash
# 未实测（VM 无 rustc）：写作机 rustc 1.99.1 能编译，但产物是 Mach-O
rustc --edition 2021 --crate-type staticlib -C panic=abort -C opt-level=2 \
      nostd.rs -o libnostd.a
cc -std=c17 -Wall -Wextra nostd_c.c libnostd.a -o nostd_c
```

`#[panic_handler]` 是 `no_std` 的硬性要求：panic 发生时没有 `std` 帮忙打印和退出，必须由你决定「打印到串口」还是「停机」。这也是库和二进制常打架的地方——库定义一次、二进制又定义一次，就会报重复定义。真正上裸机还要 `#![no_main]`、自己写 `_start`、提供链接脚本和中断向量表（一张放在固定地址的表，硬件出事时按它找到你写的处理函数）；用 `alloc` 时还要 `#[global_allocator]`。这句话只写形状、不给产物：VM 没有 Rust 工具链，上面 `rustc`/`cc` 两步都标「未实测（VM 无 rustc）」，判据是编译报错里说「缺失」还是「重复」，不是体积数字。

::: def 定义 1.16.6 · freestanding 环境 {#def-1.16.6}
freestanding（独立环境）指编译器只假设语言本身可用、不假设有宿主操作系统的编译目标。C 用 `-ffreestanding -nostdlib` 进入，Rust 用 `#![no_std]` 进入；两者都保留语言核心（整数运算、指针、控制流），但拿掉文件、线程、堆与格式化输出。
:::

::: errata `panic=abort` 的四个连带影响
1. **`catch_unwind` 失效**：abort 策略下 panic 直接终止进程，不展开栈，捕获不到。
2. **析构不保证执行**：`Drop` 在 abort 时不会运行；panic 跨 `extern "C"` 边界仍是未定义行为。
3. **体积变小但不等于零成本**：panic 的格式化代码仍在，除非用 `panic_immediate_abort`（nightly）或自定义 handler。
4. **测试行为变化**：`#[should_panic]` 在 abort 下无法工作；库作者不能假设调用方使用 unwind。
:::

::: ex 例 1.16.6 · 先猜：`nm` 里还剩几个 `U` {#ex-1.16.6}
1632 字节那个 `-ffreestanding -nostdlib` 产物（VM 实测：`text` 129 字节、`Type: EXEC`、入口 `0x400110`、`ldd` 报 `not a dynamic executable`、`nm -u` 为空、`./free2` 返回 `rc=0`）。先猜两件事：把源码里的 `write` 换成 `printf("hi\n")` 并保持这两个编译选项，报错出现在编译期还是链接期、报什么？同一份 freestanding 目标文件，`nm` 里 `U`（未定义）项应该是零还是不为零？

::: sol 解答
报错在**链接期**，VM 实测原文三行：`/usr/bin/ld: /tmp/ccithjbV.o: in function '_start':`、`lab1c16_ns.c:(.text+0x10): undefined reference to 'printf'`、`collect2: error: ld returned 1 exit status`。编译器不关心 `printf` 有没有实现，它只按声明生成一条调用；实现本来在 libc，而 `-nostdlib` 恰好把它拿掉了，于是 `ld` 找不到定义。第二个猜测：本节那份示例自己用内联汇编写了 `write`/`exit`，所以 `nm -u` 实测为空（0 行）；只要留下任何一个 libc 调用（`printf`、`malloc`、`memcpy`），未定义项就不会为空。

`_start` 缺失反而是最阴的一种：同一台 VM 上不写 `_start` 直接链，实测得到的是 `/usr/bin/ld: warning: cannot find entry symbol _start; defaulting to 000000000040010c`——**只是警告，链接照样成功**，产物入口落到 `0x40010c`，运行结果完全不可预期。「没了 libc」不改变语言，改变的是一批符号从「有默认实现」变成「你要么自己实现，要么链回来」——这也是 1.16.6 说「去掉运行时等于接手它的全部责任」的确切含义。
:::
:::

### 1.16.6 小结

`no_std` 不是「什么都不链接」，而是「把默认的那层运行时换成你自己写的」。C 的 freestanding 程序证明了这一点：1632 字节、`text` 129 字节的产物里没有 libc，但 `_start`、系统调用和退出路径一个都不能少。Rust 只是把这些位置显式化成 `#![no_std]`、`#[panic_handler]`、`panic=abort`。如果只记住一件事：**去掉运行时，等于接手它的全部责任**。

**Q2（辨析）** 为什么 `no_std` 静态库在 C 侧链接时常配 `-C panic=abort`？

## 1.16.7 C/Rust FFI、bindgen 与 cbindgen {#sec-1.16.7}

这一节回答：C 与 Rust 互相调用时，谁保证两边看到的内存布局一样？手写的声明又靠什么不漂移？

::: preview 先抓住一件事
跨语言调用要守四份契约：符号名、内存布局、内存所有权、错误与 panic。ABI 只替你保证前两份；后两份靠你自己写进头文件注释和调用约定。`bindgen`/`cbindgen` 解决的是「声明和实现对不上」，不是「语义对不上」。
:::

先确认 ABI 到底在哪一层生效。下面这个 16 字节结构体，在 Ubuntu 24.04（aarch64、GCC 13.3.0、`-O2`）上编译后只剩两条指令：

```c
/* lab1c16_pair.c */
struct pair { long a; long b; };
long pair_sum(struct pair p) { return p.a + p.b; }
struct pair make_pair(long a, long b) { struct pair p = {a, b}; return p; }
```

```bash
cc -std=c17 -O2 -c lab1c16_pair.c -o pair.o
objdump -d pair.o | sed -n '/<pair_sum>:/,+2p'
```

实读 `pair_sum` 的函数体是 `add x0, x0, x1` 加 `ret`：结构体没有被「传地址」，两个 `long` 直接放进 `x0`、`x1`。`make_pair` 也只有一条 `ret`，返回值同样在 `x0`、`x1`。这就是 ABI 的作用——只要两边都按 AAPCS64 传参，C 与 Rust 不需要知道对方是哪种语言。

| 项 | x86-64 SysV | ARM64 AAPCS64 | RISC-V 64 psABI |
|:--|:--|:--|:--|
| 整数/指针参数 | `rdi, rsi, rdx, rcx, r8, r9` | `x0`–`x7` | `a0`–`a7` |
| 浮点参数 | `xmm0`–`xmm7` | `v0`–`v7` | `fa0`–`fa7` |
| 返回值 | `rax`（128 位用 `rdx:rax`） | `x0`（`x0:x1`） | `a0`（`a0:a1`） |
| 调用/返回 | `call`/`ret` | `bl`/`ret` | `jal`/`ret` |
| 栈对齐 | 16 字节 | 16 字节 | 16 字节 |
| 结构体按值 | 按八字节分类 | HFA 或整数对 | ≤2×XLEN 走寄存器 |

C 侧头文件是契约，Rust 侧必须逐字匹配。`long` 在这台 VM 上是 8 字节（`sizeof(long)=8`、`sizeof(size_t)=8`、`sizeof(void*)=8` 实测），但 Windows 的 LLP64 里 `long` 是 4 字节；`char` 是否有符号也由目标平台决定。跨平台代码一律用 `int32_t`/`int64_t`/`size_t`，别让声明去猜。

::: def 定义 1.16.7 · FFI {#def-1.16.7}
FFI（Foreign Function Interface，外部函数接口）是两种语言之间「按 C ABI 调用彼此函数」的约定。它规定参数怎么放寄存器、结构体怎么布局、符号叫什么名字；它不规定谁释放内存、出错返回什么、panic 能不能穿过边界。
:::

### Rust 导出给 C（未实测）

Rust 侧要同时满足两件事：`extern "C"` 把 ABI 换成 C 的，`#[no_mangle]` 阻止编译器改名。少了后者，符号会变成 `_ZN...` 或 `_R...`，C 链接时报 `undefined reference`。下面写成 `crate-type = staticlib`，由 C 侧链接：

```rust
// lab1c16_ffi.rs — 未实测（VM 无 rustc）
#[no_mangle]
pub extern "C" fn rust_add(a: i32, b: i32) -> i32 { a.wrapping_add(b) }

/// # Safety
/// `xs` 必须指向至少 `n` 个 `i32`，且整个调用期间有效。
#[no_mangle]
pub unsafe extern "C" fn rust_sum(xs: *const i32, n: usize) -> i32 {
    if xs.is_null() { return 0; }
    let mut s = 0i32;
    for i in 0..n { s = s.wrapping_add(unsafe { *xs.add(i) }); }
    s
}
```

```c
/* lab1c16_ffi_c.c — 调用 Rust 静态库 */
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

extern int32_t rust_add(int32_t a, int32_t b);
extern int32_t rust_sum(const int32_t *xs, size_t n);

int main(void)
{
    int32_t xs[] = {1, 2, 3, 4};
    printf("rust_add=%d rust_sum=%d\n", rust_add(2, 3), rust_sum(xs, 4));
    return 0;
}
```

```bash
# 未实测（VM 无 rustc）：写作机的 rustc 1.99.1 产物是 Mach-O，不能参与这条链接
rustc --edition 2021 --crate-type staticlib -C panic=abort -O \
      lab1c16_ffi.rs -o librustffi.a
cc -std=c17 -Wall -Wextra lab1c16_ffi_c.c librustffi.a -o ffi_c
nm librustffi.a | grep -E 'rust_add|rust_sum'   # 期望看到 T，而不是 _ZN/_R
```

判据只看 `nm` 与运行结果：符号名不带前缀、程序打印 `rust_add=5 rust_sum=10`。若看到 `_R` 开头，是忘了 `#[no_mangle]`；若链接报缺 `rust_eh_personality`，是没加 `-C panic=abort`。Rust 2024 edition 起要写 `#[unsafe(no_mangle)]`，这是语法变化，不是行为变化。

### C 导出给 Rust（未实测）

反过来，Rust 调 C 要写 `extern "C"` 声明块、指定库，并把调用包进 `unsafe`——编译器无法验证 C 那边的指针是否有效。

```rust
// lab1c16_use_c.rs — 未实测（VM 无 rustc）
use std::os::raw::{c_char, c_long};

#[link(name = "math", kind = "static")]
extern "C" {
    fn math_sum(xs: *const c_long, n: usize) -> c_long;
    fn math_version() -> *const c_char;
}

fn main() {
    let a = [1 as c_long, 2, 3, 4];
    let s = unsafe { math_sum(a.as_ptr(), 4) };
    let v = unsafe { std::ffi::CStr::from_ptr(math_version()) };
    println!("{}: sum={}", v.to_string_lossy(), s);
}
```

```bash
# C 静态库这一半可在 VM 复现（命令见 1.16.3）；rustc 这一步未实测
cc -std=c17 -O2 -fPIC -c mathlib.c -o mathlib.o && ar rcs libmath.a mathlib.o
rustc --edition 2021 -O lab1c16_use_c.rs -L . -l static=math -o use_c
```

`kind = "static"` 表示链接 `libmath.a`；换成 `.so` 时写 `"dylib"`，并保证运行期能找到（`rpath` 或 `LD_LIBRARY_PATH`）。`-L .` 是搜索目录，漏了会报 `cannot find -lmath`。还有一条不在类型系统里的约定：C 返回的 `const char *` 归谁释放、活多久，Rust 侧看不到；`CStr::from_ptr` 只是借来看，不负责释放。

### bindgen 与 cbindgen：让声明自动同步

手写 `extern "C"` 最容易犯的错不是语法，而是「头文件改了、Rust 声明没改」。两个工具各管一个方向：

| 工具 | 方向 | 输入 | 输出 | 本机状态 |
|:--|:--|:--|:--|:--|
| `bindgen` | C → Rust | C 头文件 | `bindings.rs` | 未安装（还需 `libclang`） |
| `cbindgen` | Rust → C | Rust crate | `.h` | 未安装 |

本机 `command -v bindgen cbindgen` 都返回空，所以下面只给调用形状，不抄生成结果：

```bash
# wrapper.h 只放 #include，避免把系统头整个展开
printf '#include "mathlib.h"\n' > wrapper.h
bindgen wrapper.h --allowlist-function 'math_.*' --allowlist-type 'pair' \
        --no-layout-tests -o bindings.rs

# 反向：从 Rust crate 生成 C 头
cbindgen --config cbindgen.toml --crate mathlib --output mathlib.h
```

`--allowlist-function` 是关键：不加白名单时，`bindgen` 会把头文件里间接引入的 `size_t`、`FILE` 等一并生成，产出几百行用不上的绑定，还随 libclang 版本漂移。生成的 `.h` 应带 `#ifdef __cplusplus extern "C"` 保护和 `int64_t`/`size_t` 这类定宽类型。

真正防漂移的不是「记得重新生成」，而是把生成物提交进仓库，在 CI 里跑 `git diff --exit-code -- bindings.rs mathlib.h`：谁改了结构体却没重新生成，红的就是那条命令。工具只能保证「声明和实现对得上」，保证不了「语义对得上」——所有权、错误码、panic 仍然要人写。

::: errata FFI 的六个边界
1. **`String`/`Vec` 直接跨边界**：布局不是 C ABI，C 侧无法释放。用裸指针加长度，并约定谁释放。
2. **缺 `#[repr(C)]`**：Rust 默认可以重排字段，C 侧按自己的偏移读会读错。
3. **`slice::from_raw_parts` 收空指针**：C 允许 `free(NULL)`，Rust 这条要求非空且对齐；先判断 `is_null()`。
4. **panic 穿过 `extern "C"`**：未定义行为。边界内 `catch_unwind`，或 `panic=abort`；要传播就用 `extern "C-unwind"`。
5. **`errno` 被覆盖**：C 侧失败后要立刻读；中间插一次 `printf` 就可能把 `errno` 改掉。
6. **重复释放**：`Box::from_raw` 接管后 C 侧不能再 `free`；成对提供 `foo_new`/`foo_free` 最稳。
:::

### 1.16.7 小结

FFI 的边界是四层：ABI 决定的寄存器与布局、符号名决定的链接、所有权决定的释放、panic 与错误码决定的失败语义。ABI 可以用 `objdump` 当场验证——16 字节结构体真的走 `x0`/`x1`；后三层只能靠约定和工具链约束。如果只记住一件事：**能链上不等于能安全调用**。

::: method 即时自测 · 1.16.7
**Q1（记忆）** `extern "C"` 与 `#[no_mangle]` 各解决什么问题？
**Q2（辨析）** 为什么 `#[repr(C)]` 是结构体跨边界的前提，而普通 Rust 结构体不行？
**Q3（应用）** C 侧传进来一个空指针和长度 0，Rust 侧直接建 slice 会怎样，怎么改？

::: sol 答案
**A1** `extern "C"` 换 ABI（参数与返回值怎么放寄存器）；`#[no_mangle]` 保留符号原名，让 C 链接器找得到。
**A2** 默认布局允许编译器重排字段、插入填充；`#[repr(C)]` 强制按 C 规则排列，两边偏移才一致。
**A3** `slice::from_raw_parts` 要求非空且对齐，空指针是未定义行为；先 `is_null()` 返回，或返回空切片。
:::

## 1.16.8 实验一：从 ELF 读到 GOT/PLT 的四层读数 {#sec-1.16.8}

这一节回答：不靠 `ldd` 的一句话，怎样用四个工具钉死「这个 `math_sum` 来自哪个库、走哪次重定位、落到哪条桩」？

::: preview 先抓住一件事
读数分四层：文件类型与节、动态段、重定位表、运行时绑定。每一层只能用对应命令读，上一层解释不了下一层；`ldd` 只回答「找得到」，回答不了「绑到谁」。
:::

先按 1.16.3 构建 `app-dynamic`（`libmath.so.1` 放当前目录，`RUNPATH` 为 `$ORIGIN`）。这台 VM 是 aarch64，所以下文的重定位名与 PLT 形状都是 AArch64 的。这套手续在换基础镜像时最有用：同一个二进制在 A 镜像里绑定新版库、在 B 镜像里找到旧版同名库，只有读出 `binding file ...` 那一行，才能确认它到底链到了哪个文件。

**第一层：文件是什么。** 先确认它是位置无关可执行文件，再看 PLT 与 GOT 是否存在：

```bash
readelf -hW app-dynamic | grep -E 'Type|Machine|Entry'
readelf -SW app-dynamic | grep -E '\.(plt|got|text|rela\.plt|dynamic|dynsym)'
```

实读：`Type` 是 `DYN (Position-Independent Executable file)`，`Machine` 是 `AArch64`，入口 `0x940`；`.plt` 占 `0xb0` 字节、`.got` 占 `0x98`、`.text` 占 `0x218`、`.rela.plt` 占 `0xd8`。注意没有 `.got.plt`——那是 x86 教材里的常见名字，aarch64 上 PLT 的重定位表叫 `.rela.plt`，表本身仍是 `.got`。

**第二层：它依赖谁、去哪找。** 动态段是 `ld.so` 唯一的说明书：

```bash
readelf -dW app-dynamic | grep -E 'NEEDED|RUNPATH|FLAGS'
```

实读到三条 `NEEDED`：`libmath.so.1`、`libc.so.6`、`ld-linux-aarch64.so.1`；`RUNPATH` 为 `[$ORIGIN]`；`FLAGS` 为 `BIND_NOW`，`FLAGS_1` 为 `NOW PIE`。`NEEDED` 记的是 SONAME 而不是文件名，`RUNPATH` 给出搜索目录，`BIND_NOW` 说明这台机器默认做了加载时绑定（1.16.1 的链接行里有 `-z now`）。

**第三层：哪里要填、填谁。** 重定位表把「PLT 槽」和「普通数据指针」分开：

```bash
readelf -rW app-dynamic | grep -E 'R_AARCH64_(JUMP_SLOT|RELATIVE)'
```

实读到 9 条 `JUMP_SLOT` 和 4 条 `RELATIVE`。其中与本章库有关的三条带版本后缀：`math_sum@MATHLIB_1.0`、`math_dot@MATHLIB_1.0`、`math_version@MATHLIB_1.0`。`JUMP_SLOT` 是给 PLT 用的函数槽，`RELATIVE` 是 PIE 基址加上固定偏移的数据指针；前者由符号解析决定，后者不需要找符号。

**第四层：桩长什么样、谁调它。** 反汇编只取 `.plt` 和 `main`：

```bash
objdump -d -j .plt app-dynamic | sed -n '/<math_sum@plt>:/,+3p'
objdump -d app-dynamic | sed -n '/<main>:/,/^$/p' | grep 'bl.*@plt'
```

实读到 `math_sum@plt` 在 `0x7e0`，四条指令依次是 `adrp x16`（取 GOT 所在页）、`ldr x17, [x16, #3992]`（从 GOT 读函数地址）、`add x16, x16, #0xf98`（算出这条槽的地址，供解析器回写）、`br x17`（跳过去）。`main` 里对应的调用是 `bl 7e0 <math_sum@plt>`。x86-64 的同一步是 `jmp *math_sum@GOTPCREL(%rip)`，本机没有 x86 运行环境，这个名字按文档给出，未实测。

**第五层：运行时到底绑到谁。** 前四层都是静态证据，最后一层要跑起来：

```bash
LD_DEBUG=bindings ./app-dynamic 2>&1 | grep -E 'math_(sum|dot|version)'
LD_DEBUG=libs ./app-dynamic 2>&1 | grep -E 'find library=libmath|trying file=.*libmath'
```

实读到的绑定行长这样：`binding file ./app-dynamic [0] to /tmp/lab1c16/libmath.so.1 [0]: normal symbol 'math_sum' [MATHLIB_1.0]`；`libs` 一侧先是 `find library=libmath.so.1 [0]; searching`，接着 `trying file=/tmp/lab1c16/libmath.so.1`。这两句合起来才证明「按 SONAME 找到了文件，又把符号绑到了这个文件」。

::: def 定义 1.16.8 · 四层读数 {#def-1.16.8}
这一节的四层读数指四步可独立复核的：`readelf -h/-S` 定文件与节，`readelf -d` 定依赖与搜索路径，`readelf -r` 定待填项，`LD_DEBUG` 定运行期绑定。前一步的结论是后一步的前提，任何一步缺失，结论都只能算猜测。
:::

最后用打桩把「绑定发生在运行期」变成可执行的反证：

```c
/* lab1c16_interpose.c — 替身实现，返回固定值 */
#include <stddef.h>
long math_sum(const long *xs, size_t n) { (void)xs; (void)n; return 999; }
```

```bash
cc -shared -fPIC -O2 lab1c16_interpose.c -o libinterpose.so
LD_PRELOAD=./libinterpose.so ./app-dynamic     # 实读 sum=999 dot=300
```

程序输出 `mathlib 1.0: sum=999 dot=300`：`math_version` 与 `math_dot` 仍是原实现，只有 `math_sum` 被换掉。这说明调用点写死的只是「PLT 槽的地址」，槽里装谁由加载器决定。生产环境不要拿 `LD_PRELOAD` 做热修复：它依赖加载顺序与权限，setuid 程序会直接忽略它。

::: errata 三个容易读错的地方
1. **照着 x86 教材找 `.got.plt`**：aarch64 上只有 `.got` 与 `.rela.plt`；`grep .got.plt` 空手而归不代表没有 PLT。
2. **用 `ldd` 当绑定证据**：`ldd` 只说明库找得到；两个库同 SONAME 时它看不出真正绑到哪个对象，要看 `LD_DEBUG=bindings`。
3. **把 `JUMP_SLOT` 条数当函数调用数**：本机 9 条里只有 3 条属于 `math_*`，其余是 libc 与启动代码；条数由链接器决定，不由源码调用次数决定。
:::

### 1.16.8 小结

一条可靠的结论要四层读数对齐：文件类型对得上、动态段里有 `NEEDED`、重定位表里有对应的 `JUMP_SLOT`、运行时 `LD_DEBUG` 报出绑定对象。缺任何一层，「这个符号来自 libmath」都只是推测；补上 `LD_PRELOAD`，还能证明这层绑定确实发生在运行期。如果只记住一件事：**`ldd` 是结论的封面，不是结论本身**。

::: sol 答案

## 1.16.9 实验二：用 perf、size、cargo 看优化与 LTO {#sec-1.16.9}

这一节回答：`perf` 打不开、VM 里又没有 `cargo` 的时候，怎么仍然把「优化等级」变成一组能复算的数字？

::: preview 先抓住一件事
这台 VM 上 `perf` 装了但用不了，Rust 工具链根本没装。能用的替代是三样：`clock_gettime` 加 `/usr/bin/time` 拿墙钟，`size` 与 `readelf -SW` 拿体积，`nm` 与 `objdump -d` 拿形状。它们给不出 IPC 和 cache miss，但足以回答「这个开关动了哪一段代码、动了多少」。前提是在同一批次里比：绝对时间换一批就整体漂约 1.6 倍。
:::

### 先把失败写下来：`perf` 到底不给什么

```bash
cat /proc/sys/kernel/perf_event_paranoid
perf --version
perf stat -e cycles,instructions,branches,branch-misses ./opt-O2
```

实读三样：paranoid 是 `4`；`perf version 7.0.14`，与内核同源，不是「没装」；`perf stat` 的完整报错是 `Error:`、`No supported events found.`、`Access to performance monitoring and observability operations is limited.`，末尾点名 `perf_event_paranoid setting is 4`。改它要 root，而 `sudo` 不可用，所以硬件事件这条路在本环境是死的。

不带 `-e` 的 `perf stat ./opt-O2` 反而能跑完，但计数栏是 `<not supported> cpu-cycles:u`，只剩 elapsed、user、sys 三个时间量；混进 `instructions` 时整条命令直接失败，不是「少给一个数」。判读：**这台机器给时间，不给计数**，所以本节不出现 IPC、分支失败率、cache miss 三类数字。

### 替代实验：两个文件、五档构建

```c
/* lab1c16_work.c — 一个可内联的小函数 + 两个热点循环 */
#include <stddef.h>
long scale(long x, long k) { return (x * 3 + k) ^ (x >> 3); }
long reduce_dot(const long *xs, const long *ys, size_t n)
{
    long s = 0;
    for (size_t i = 0; i < n; i++)
        s += scale(xs[i], ys[i]) * 2 - (xs[i] & 7);
    return s;
}
/* reduce_str 同量级，但 k 由上一次迭代算出，归约链断不开 */
```

驱动 `lab1c16_drv.c` 放两个 1 Mi 元素的静态数组、40 轮调用，用 `clock_gettime(CLOCK_MONOTONIC)` 只夹计算段，末尾连结果带毫秒一起打印——五档都打同一行 `sum=439443752222720 extra=45270974290984960`。

```bash
for O in 0 2 3; do
  cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O$O lab1c16_drv.c lab1c16_work.c -o opt-O$O
done
cc -std=c17 -D_GNU_SOURCE -Os           lab1c16_drv.c lab1c16_work.c -o opt-Os
cc -std=c17 -D_GNU_SOURCE -O2 -flto=auto lab1c16_drv.c lab1c16_work.c -o opt-lto

for b in opt-O0 opt-O2 opt-O3 opt-Os opt-lto; do
  for i in 1 2 3 4 5; do ./$b | sed 's/.*ms=//'; done   # 同批连跑，取中位数
  /usr/bin/time -f "real=%e user=%U maxrss=%MkB" ./$b
done
size opt-O0 opt-O2 opt-O3 opt-Os opt-lto
for b in opt-O0 opt-O2 opt-O3 opt-Os opt-lto; do
  readelf -SW $b | grep -E '\] \.text '                  # 第 6 列才是节大小
done
```

### 读数：两批之间发生了什么

读数都来自这台 VM（GCC 13.3.0、aarch64、binutils 2.42）；墙钟是同一批次连跑 5 次的区间，单位毫秒。

| 档位 | `.text` | `size` 的 text | 第一批 ms | 第二批 ms |
|:--|--:|--:|--:|--:|
| `-O0` | 1116 | 2874 | 261–271 | 163–171 |
| `-O2` | 864 | 2624 | 114–117 | 68–69 |
| `-O3` | 1008 | 2846 | 97–101 | 58 |
| `-Os` | 808 | 2564 | 117–120 | 68–70 |
| `-O2 -flto=auto` | 812 | 2510 | 96–130 | 58–59 |

两批的绝对值差约 1.6 倍，比值却几乎不变：`-O2`/`-O3` 第一批 1.17、第二批 1.19；`-O0`/`-O3` 第一批 2.66、第二批 2.81。这就是没有 PMU 时的口径：**只报同批次内的比值，绝对值一律带批次**。第二批是跑热之后的读数，调度与频率都在动。

形状证据三条，都不需要 `perf`：

- 向量化问编译器自己：`cc -O3 -fopt-info-vec -c lab1c16_work.c -o /dev/null` 实读一行 `lab1c16_work.c:9:26: optimized: loop vectorized using 16 byte vectors`；同一命令换成 `-O2` 输出为空。GCC 13 把 `-ftree-vectorize` 放在 `-O3`，1.16.4 给过结论。
- 内联看 `objdump -d` 的调用条数：`reduce_dot` 在 `-O0` 是 42 条指令、含 1 条 `bl`（真调 `scale`）；`-O2` 缩到 20 条、0 条 `bl`；`-O3` 反而 44 条，出现 `v0.2s`、`v2.16b` 这类 NEON 寄存器写法。指令数涨 17%、时间降 16%——「指令数少所以快」在这里刚好反着。
- 符号看 `nm`：`opt-O0` 45 行、13 个 `T`；`opt-lto` 只剩 42 行、10 个 `T`，`scale`、`reduce_dot`、`reduce_str` 三个名字全消失，只留 `main`、`now_ms` 和启动代码。`nm` 变少不是 bug，是 1.16.5 说的跨文件内联。

LTO 的时间结论要老实：第一批它比 `-O3` 慢且散（96–130 对 97–101），第二批 58 对 58 打平。这个两文件、40 轮的程序上，LTO 换来的是 `.text` 从 1008 降到 812（约 19%）和三个符号消失，**换不到稳定的墙钟收益**——「开了 LTO」不等于「快了」。

再补裁剪读数：`lab1c16_pad.c` 加 6 个没人调用的函数和一张 32 KiB 常量表。

| 构建 | `size` 的 text | `.rodata` | `nm` 里 `pad_*` |
|:--|--:|--:|--:|
| `-O2`（不分节） | 35746 | 0x8030（32816 B） | 7 |
| `-O2 -ffunction-sections -fdata-sections -Wl,--gc-sections` | 2572 | 0x1a（26 B） | 0 |

节回收删的就是那张表：整节没人引用，数据一起扔。调试分离实测一次：`-g3` 构建 115408 字节 → `objcopy --only-keep-debug` 得到 50520 字节的 `.debug` → `strip --strip-debug` 后主文件 70992 字节 → `--add-gnu-debuglink` 只加回一个 16 字节的 `.gnu_debuglink` 节；`.text` 仍是 0x3ec，`.symtab` 仍在——删它的是 `--strip-all`。

::: def 定义 1.16.9 · 同批次对照 {#def-1.16.9}
同一批次指：同一台机器、同一次开机、同一份输入，连续交替跑完所有档位，每档至少 5 次取中位数、报告写成区间。跨批次的绝对值只说明这台机器的负载状态，支持不了「某档更快」；比档位，比的是同批次内的比值。
:::

Rust 侧照旧只有命令形状：VM 上 `cargo --version`、`rustc --version` 都返回 `command not found`，`/usr/lib/rust` 不存在；写作机的 `rustc 1.99.1` 产出 Mach-O，上面四样读数一样做不了。所以**整段 Rust 标「未实测（VM 无 rustc）」**。可迁移的只有对应关系：`cargo build --release` 的默认 `opt-level=3` 约等于这里的 `-O3` 档，`lto="fat"` 对应 `-flto=auto`，`strip="symbols"` 对应 `strip --strip-debug`，而 `codegen-units=1` 在 C 里没有对应开关——GCC 每次只看一个 `.c`，跨文件要靠 LTO 补。`cargo bloat`、`cargo llvm-lines` 要先装子命令，本环境未安装；复核 Linux 上的 Rust 产物，用的还是这组 `size`/`nm`/`readelf -SW`。

::: ex 例 1.16.9 · 先猜 `-Os` 会不会更慢 {#ex-1.16.9}
`-Os` 的 `.text` 是五档最小的 808 字节，比 `-O2` 少 56、比 `-O3` 少 200。先猜：这段热点的墙钟会不会也排到最后？再猜：什么条件下「体积小」才换来「更慢」？

::: sol 解答
第二批 `-Os` 是 68–70 ms，与 `-O2` 的 68–69 ms 同档；第一批 117–120 对 114–117，只慢约 3%。因为 `-Os` 没退到 `-O1`：内联与标量优化照做，少的只是展开、向量化这类「变大」的变换，而这个循环卡在 1 Mi 数组的访存与归约链上，条数不是瓶颈。

要「体积小换来更慢」，得让代码形状本身成为瓶颈：热点装得进 L1-i、靠展开拆依赖链时才见效。这台机器上正是 `-O3` 靠 16 字节向量换了 16%，而 `-Os` 拿不到那次向量化。所以先问「时间花在哪」，再选档位。
:::
:::

::: errata 这组读数的四条边界
1. **绝对值跨批次作废**：`-O0` 从 261–271 掉到 163–171，五档一起掉；只报比值。
2. **IPC、分支失败率、cache miss 一个都没有**：`perf_event_paranoid=4` 且无 root；本节的「为什么快」只由 `.text` 字节、`bl` 条数、`-fopt-info-vec` 一行支撑。
3. **`size` 的 `text` 既不是 `.text` 也不是文件大小**：`-O0` 档 `text` 2874、`.text` 1116、文件 70808；`bss` 16777224 是那两个静态数组，文件里一字节不占。
4. **LTO 的收益不自动包含时间**：这里它换来 19% 的 `.text` 与三个符号，时间同批打平或更散；换一份源码形状就可能反过来。
:::

### 1.16.9 小结

`perf` 不可用时「优化等级」仍然可测：墙钟给相对快慢，`size`/`readelf` 给体积，`nm`/`objdump` 给形状，`-fopt-info-vec` 给「这个变换发生了没有」，四类读数在同一批次里配对看。先把 `perf stat` 的失败原文记下来，再声明哪些结论本环境拿不到。如果只记住一件事：**没有 PMU 就不写 IPC，但比值、节大小、符号数、向量化诊断四样照样能取证**。

**Q2（辨析）** 同一份源码，`-O3` 的 `reduce_dot` 比 `-O2` 多 24 条指令，墙钟却少约 16%。这两件事矛盾吗？

**Q3（应用）** 同事说「我这儿 `-O0` 是 90 ms，你的 163 ms 是错的」。写出反驳要用的三条证据，和一条不该拿来反驳的。

**Q4（迁移）** 只有 `cargo build --release` 的产物，手边是 Linux 机器但没有 Rust。你打算复核哪三件事？

## 1.16.10 十二条工具链陷阱 {#sec-1.16.10}

这一节回答：前十节讲「应该怎样」，这一节讲「现场长什么样」——看到一条现象，第一个该跑的命令是哪条？

::: preview 先抓住一件事
十二条分四组：编译、链接、优化与裁剪、跨语言。每条都写成「现象 → 原因 → 先查什么」，而「先查什么」必须是一条命令加一个可对读的字段，不是一句「检查一下」。能在本书 VM（aarch64、GCC 13.3.0）复现的给了实读；换架构或换语言的那几条写明未实测。
:::

| # | 现象 | 原因 | 先查什么 |
|--:|:--|:--|:--|
| 1 | 改了头文件，行为没变也不报错 | 增量构建按时间戳重编，某个 `.o` 还是旧布局 | `nm`/`size` 做新旧 `.o` 对照；拿不准就删目标文件重编 |
| 2 | 同一份 `cc -Werror` 一台过一台炸 | 告警集随编译器版本变，有些还要优化等级才出现 | `cc --version` 与完整 flags；`-Wno-error` 看清是哪条规则 |
| 3 | 换台机器就 `SIGILL` | `-march=native`、`-C target-cpu=native` 按构建机指令集发射 | `objdump -d` 找新指令；发布改基线 |
| 4 | `undefined reference`，库就在旁边 | 传统 `ld` 单遍扫描：`-lfoo` 排在引用它的 `.o` 之前，成员一个都不抽 | `nm main.o` 的 `U`；库挪到 `.o` 之后，循环依赖用 `--start-group` |
| 5 | 运行报 `cannot open shared object file` | `NEEDED` 记 SONAME 不记文件名；`$ORIGIN` 被展开成空串；不在缓存里 | `readelf -d` 的 `NEEDED`/`RUNPATH`、`ls -l libfoo.so*`、`LD_DEBUG=libs` |
| 6 | 没加 `-fPIC` 也链接成功 | aarch64 的页相对项本来就能重定位；那句报错是 x86-64 的绝对 32 位项 | `readelf -rW x.o` 看数据访问经不经 GOT |
| 7 | 升 `-O3` 更慢；Rust release 仍慢 | 展开与向量化让代码变大；release 默认 `codegen-units=16`、LTO 关 | 同批次墙钟比值 + `readelf -SW` 的 `.text` |
| 8 | `-O0` 对、`-O2` 错 | UB（未初始化、越界、严格别名）在低等级被「碰巧」掩盖 | 高等级下的告警 → 逐条回滚优化，定位哪条变换 |
| 9 | `nm` 少符号、体积骤降、栈全是地址 | 内联删符号、节回收删整节、`strip` 删 `.symtab` 但留 `.dynsym` | 两个产物 `readelf -SW` 对照 + `nm -D` |
| 10 | C 找不到 Rust 的 `math_sum` | Rust 默认 mangling，`extern "C"` 只改 ABI 不改符号名 | `nm -D --defined-only`；有没有 `#[no_mangle]` |
| 11 | FFI 结构体错位、`long` 少一位 | Rust 默认布局不保证顺序；LP64 的 `long` 8 字节、LLP64 4 字节 | `#[repr(C)]` + `int64_t`/`size_t`；生成物提交并在 CI diff |
| 12 | `catch_unwind` 捕不到，或 handler 缺失/重复 | abort 不展开栈；`#[panic_handler]` 只能在最终二进制定义一次 | 报错文案点名缺失还是重复；`readelf -SW` 看 `.eh_frame` |

### 分组读法

**编译组（1–3）** 三条改的都是环境不是你的代码：陈旧 `.o` 靠 `nm`/`size` 对照，`-Werror` 的差异靠 `cc --version` 与完整 flags，`SIGILL` 靠 `objdump -d` 里的新助记符。第 2 条本机实读：一份故意写坏的类型双关加一个未初始化变量，`-O0 -Wall -Wextra` 只报 `'u' is used uninitialized [-Wuninitialized]`，换成 `-O2` 才多报一条 `... will break strict-aliasing rules [-Wstrict-aliasing]`——告警跟着优化等级走。第 3 条只有一台机器，跨机 `SIGILL` 未复现。

**链接组（4–6）** 4、5 是「找不到」，6 是「不报错」。第 6 条本机实读：非 PIC 的 `.o` 里数据访问是 `R_AARCH64_ADR_PREL_PG_HI21` 加 `R_AARCH64_ADD_ABS_LO12_NC`，`cc -shared` 直接成功；加 `-fPIC` 后同一处换成 `R_AARCH64_ADR_GOT_PAGE` 加 `R_AARCH64_LD64_GOT_LO12_NC`，符号才走 GOT。那句 `relocation ... can not be used when making a shared object` 只有 x86-64 的绝对 32 位项 `R_X86_64_32` 才会给你。4、5 的复现见 1.16.3 与习题 [B1](ch16-exercises.md#ex-1.16-B1)、[B2](ch16-exercises.md#ex-1.16-B2)、[C2](ch16-exercises.md#ex-1.16-C2)；`$ORIGIN` 要用单引号包住，`RUNPATH` 为空就是被 shell 吃掉了。

**优化与裁剪组（7–9）** 数字都来自 1.16.9：`.text` 从 864 到 1008、这段循环快约 16%，换访存密集的循环就不一定；`nm` 从 45 行到 42 行、三个名字消失；`.rodata` 从 32816 字节到 26。第 8 条补一句：本机那份样例 `-O1 -fsanitize=undefined,address` 跑起来一条都没报——sanitizer 看不见未初始化读与别名违规，能看见的只有告警。附带：LTO 静态库理论上要 `gcc-ar` 配套，但本机 binutils 2.42 用普通 `ar` 也没报 `plugin needed to handle lto object`，它取决于版本与调用路径（1.16.5）。

**跨语言组（10–12）全链未实测**：VM 没有 `rustc`/`cargo`，bindgen 与 cbindgen 也没装，三条只给命令与判据。符号名看 `nm -D --defined-only` 与 `nm libx.a | grep -E 'math_sum|_ZN|_R'`——`extern "C"` 只改 ABI 不改名，原名要 `#[no_mangle]`（2024 edition 起写 `#[unsafe(no_mangle)]`）。布局靠 `#[repr(C)]` 加固定宽度类型；声明由 bindgen（C→Rust）或 cbindgen（Rust→C）生成、提交进仓库，CI 里 `git diff --exit-code` 卡住「头文件改了而声明没重生成」。panic 那条看报错文案是「缺失」还是「重复」：`#![no_std]` 的库不定义 `#[panic_handler]`，只有最终二进制定义一次；`panic=abort` 后 `catch_unwind` 捕不到、`Drop` 不保证执行，要跨边界传播只能 `extern "C-unwind"` 且两侧运行时都支持，否则退回 `Result` 加进程隔离。

::: ex 例 1.16.10 · 先猜「链接没报错」能说明什么 {#ex-1.16.10}
你把一个没加 `-fPIC` 的 `.o` 拿去 `cc -shared`，在这台 aarch64 VM 上链接成功、没有任何警告。先猜：这能不能说明这个 `.so` 没问题？再猜：换成 x86-64，同一条命令最可能给你什么？

::: sol 解答
不能。链接器只拒绝它必须拒绝的重定位类型；aarch64 上数据访问走 `R_AARCH64_ADR_PREL_PG_HI21` 这类页相对项，本来就能重定位，所以「非 PIC」在这一步是静默的（本机实测 `cc -shared` 成功）。判据不在报错，在 `readelf -rW`：加了 `-fPIC`，同一处变成 `R_AARCH64_ADR_GOT_PAGE` 加 `R_AARCH64_LD64_GOT_LO12_NC`，符号经 GOT 才可抢占。

换到 x86-64，同一条命令最可能报 `relocation R_X86_64_32 against '.data' ... can not be used when making a shared object`——绝对 32 位项没法用 GOT 替代。「有没有报错」是架构属性，「要不要 `-fPIC`」是共享库属性，两件事别混；x86-64 那条本环境没机器复跑，按文档口径给。
:::
:::

::: errata 用这十二条的三个错误姿势
1. **把 x86-64 的报错名当通用**：`R_X86_64_32`、`.got.plt` 在 aarch64 上都不存在（本机是 `.got` 与 `R_AARCH64_*`）；照旧教材 `grep` 空手而归，不代表没问题。
2. **背结论不背条件**：十二条每条都绑着编译器版本、架构与调用路径；换基础镜像、换发行版、换 GCC 版本，先重跑再引用，配套看[勘误页](ch16-errata.md)。
3. **把「先查什么」写成「检查一下」**：每条都要落到一条命令和一个字段——`nm` 的 `U`、`readelf -d` 的 `RUNPATH`、`readelf -SW` 的 `.dynsym`、`objdump -d` 的 `bl` 条数。
:::

### 1.16.10 小结

十二条的共同结构：现象一句话，结论要由一条命令的一个字段支撑。能在本机复现的第 2、6、9 条给了实读，换架构或换语言的第 3、10、11、12 条标未实测。顺序也固定：先问「变的是工具还是代码」，再看「找不到还是找错」，最后才怀疑优化。只记住一件事：**报错不存在不等于问题不存在——aarch64 上不加 `-fPIC` 照样链接成功**。

::: method 即时自测 · 1.16.10
**Q1（记忆）** 十二条分哪四组？每组一条最典型的现象。

**Q2（辨析）** 第 6 条说「等不到报错」，第 9 条说「看不见东西了」。这两种「看不见」分别骗你得出什么结论？

**Q3（应用）** 同事的程序 `-O2` 下结果错、`-O0` 下对，`-fsanitize=address,undefined` 也没报。写出接下来三步和每步的依据。

**A1** 编译、链接、优化与裁剪、跨语言四组；典型现象分别是陈旧 `.o` 不改行为、`undefined reference`、`-O3` 变慢、C 找不到 Rust 的 `math_sum`。

## 1.16.11 本章小结 {#sec-1.16.11}

这一节回答：把「源码到二进制」这条链走通之后，你手上多了哪些能查的东西？出问题时，第一个该看的是源码、命令行还是产物？

::: preview 先抓住一件事
判据是：**给你一个陌生的可执行文件与一句「为什么变慢了/为什么找不到符号」，你能沿「四阶段 → ELF 里的证据 → 链接与优化开关 → 运行时行为」这条链，指出问题落在哪一段，并说出用哪条命令证明。**
:::

这一章的主线是**一条流水线上四个可检查的产物**。1.16.1–1.16.3 立骨架：预处理/编译/汇编/链接各自吃什么吐什么、ELF 的节-符号-重定位三张视图、静态库与带 SONAME 的共享库以及 GOT/PLT 的代价。1.16.4–1.16.7 讲「谁在替你决定」：`-O2`/`-O3` 与 Rust `opt-level` 各自的边界、LTO 与 `--gc-sections` 与可见性三者如何互相牵制、`no_std` 与 panic 策略如何决定运行时形状、FFI 双向调用里 `#[repr(C)]`/`extern "C"`/`build.rs` 各补哪一块。1.16.8–1.16.10 是两条实验与十二条陷阱：从 ELF 读到 GOT/PLT 的四层读数、用 `size`/`nm`/墙钟看优化与 LTO 的实际效果（`perf` 在本机不可用，已写明替代），再把工具链的坑归成「编译 / 链接 / 优化 / 跨语言」四组。

逐条打勾的达标表在[学习目标自检表](ch16-checklist.md)。这里只留判据：

- **能解释**：为什么同一份 C 在 `-O2` 与 `-O3` 下汇编不同、`--gc-sections` 为什么必须配 `-ffunction-sections`、LTO 为什么让 `static` 与可见性变成性能问题、`no_std` 少了什么又留下什么。
- **能操作**：用 `readelf -h/-S/-s/-r` 与 `nm` 读一个产物；构建 `.a` 与带 SONAME 的 `.so` 并解释 `NEEDED`；用 `size` 对比开/关 LTO 的段尺寸；用 `strace`/`LD_DEBUG` 看加载期行为。
- **能判断**：符号找不到是链接顺序、可见性还是版本节点；变慢了是优化没生效还是被内联/向量化改了形态；跨语言报错该改属性、改构建脚本还是改错误映射。

如果只记住一件事，那就是**别只读源码，要读产物**：命令行上的开关最终都落在 ELF 的节、符号和重定位里——`readelf`/`nm`/`size` 看到的那一份，才是编译器真正做出来的东西。

::: errata 本章的三条口径边界
1. **Rust 侧多为未实测**：VM 没有 rustc/cargo/clippy/miri，Rust 相关结论标「未实测（VM 无 Rust 工具链）」；写作机产物是 Mach-O，不能与 Linux 的 ELF 结论混用。
2. **性能数字绑定编译器与机器**：所有耗时都注明 GCC 13.3 / aarch64 / 优化级别，换编译器只比趋势。
3. **`perf` 不可用**：`perf_event_paranoid=4`，计数类结论一律来自 `size`/`nm`/墙钟与手算，没有一条来自 PMU。
:::

::: method 即时自测 · 1.16
**Q1（记忆）** 四阶段各产出什么中间产物？哪一步之后才有「地址」这件事？

**Q2（判断）** 加了 `--gc-sections` 但体积没变小，最可能缺了哪个编译选项？怎么验证？

**Q3（操作）** 一个 `.so` 里有 `foo`，可执行文件却报 `undefined reference to 'foo'`。给出两条命令分别排除「链接顺序」与「符号可见性/版本」。

**Q4（判断）** 开 LTO 后某个 `static` 函数变快了、另一个变慢了。给出你的解释路径与要看的两样证据。

::: sol 答案
**A1** `cpp` 出 `.i`、编译器出 `.s`、汇编器出 `.o`、链接器出可执行/共享对象。有了至少一个 `.o` 就有段内偏移，但**最终的地址与段布局由链接器决定**（重定位之后才成立）。

**A2** 最可能缺 `-ffunction-sections`/`-fdata-sections`：没有切细的节，回收器无段可回收。验证：`size -A 二进制` 对比开关前后各段尺寸，或 `readelf -S` 看 `.text` 是否还是一整块。

**A3** 链接顺序：`nm --defined-only libfoo.so`（或 `ar t libfoo.a` 加 `nm`）确认成员里真有 `foo`，再用 `-Wl,--start-group` 试验；可见性/版本：`readelf -sW libfoo.so | grep foo` 看它是 `GLOBAL`/`WEAK`/`HIDDEN`，必要时 `readelf -V` 看版本节点。

**A4** 解释路径：LTO 把跨编译单元的内联与可见性一起改了——`static` 可能被彻底内联而变快，也可能因跨单元合并后被搬到别处、失去原本更友好的寄存器分配或对齐而变慢。两样证据：`nm`/`objdump -d` 看该函数是否还存在（被内联掉就没了），`size -A` 看 `.text` 尺寸与段布局变化；再用同一优化级别的墙钟重复测量确认不是噪声。
