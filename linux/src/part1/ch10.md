[1.9](ch09.md) 把内存变成了页表（虚拟地址到物理地址的映射表）里的映射；但程序真正与外界交换数据，靠的是一组以整数 `fd` 为句柄的接口。Unix 把这个接口压到极简：`open`、`read`、`write`、`lseek`、`close`。磁盘文件、终端、管道、socket、设备，全都套进同一套方法表。

这一章的重点不是背 API，而是三件事：**返回值的语义**（短读/短写/EOF/`EINTR`）、**数据在哪一层**（用户缓冲区、内核 page cache、设备缓存）、**接口怎么选**（fd、stdio、RIO、mmap）。[2.2](../part2/ch02.md) 会从系统编程角度重讲 `open` 的标志与原子性；这里先把「读写的边界」和「I/O 路径」建立起来。

## 1.10.1 Unix I/O：四个动作与一类句柄 {#sec-1.10.1}

这一节回答：磁盘文件、终端、管道、socket 长得完全不一样，为什么程序里都只用同一个整数参数来操作？

::: preview 先抓住一件事
Unix 把输入输出压成四个动作：`open` 拿到一个**文件描述符**（file descriptor，fd），`read`/`write` 搬字节，`lseek` 挪位置，`close` 归还。fd 是进程私有表里的下标，0/1/2 只是约定，不是特权。`read` 返回 0 是读到末尾（EOF），返回 -1 才是错误；把两者混在一起，后面所有短读、重试的 bug 都从这里长出来。
:::

### 场景：先关掉 0 号，再打开一个文件

先猜一下：`close(0)` 之后再 `open` 一个文件，新 fd 是 3 还是 0？

```c
/* fd_basic.c：四个动作各跑一次 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int main(void)
{
    char buf[16];
    ssize_t n;
    long long off;

    close(0);                                  /* 故意空出 0 号 */
    int fd = open("/etc/hostname", O_RDONLY);
    printf("open -> fd %d\n", fd);

    n = read(fd, buf, 8);
    printf("read 8 -> %zd\n", n);
    off = (long long)lseek(fd, 0, SEEK_CUR);
    printf("lseek CUR -> %lld\n", off);
    off = (long long)lseek(fd, 0, SEEK_END);
    printf("lseek END -> %lld\n", off);

    errno = 0;
    n = read(fd, buf, 8);                      /* 此时已在末尾 */
    printf("read at EOF -> %zd errno=%s\n", n, strerror(errno));

    int w = open("/tmp/lab1c10_w", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    errno = 0;
    n = read(w, buf, 1);                       /* 打开方式不允许读 */
    printf("read on O_WRONLY -> %zd errno=%s\n", n, strerror(errno));

    int p[2];
    if (pipe(p) == -1) return 1;
    errno = 0;
    off = (long long)lseek(p[0], 0, SEEK_CUR); /* 管道不可定位 */
    printf("lseek on pipe -> %lld errno=%s\n", off, strerror(errno));
    return 0;
}
```

Ubuntu 24.04.5 aarch64（gcc 13.3）实测：

```text
open -> fd 0
read 8 -> 8
lseek CUR -> 8
lseek END -> 21
read at EOF -> 0 errno=Success
read on O_WRONLY -> -1 errno=Bad file descriptor
lseek on pipe -> -1 errno=Illegal seek
```

逐行读：

- 第一行回答了开头的问题：新 fd 是 0。`open` 返回**当前进程最小的空闲 fd**，不是「下一个编号」。
- `read 8 -> 8`：请求 8 字节，实际读到 8 字节。返回值是搬运的字节数，不是成功/失败标志。
- 两次 `lseek`：这个文件长 21 字节，`SEEK_END` 直接算出 21。`lseek` 只改打开文件描述里的偏移，不读磁盘。
- `read at EOF -> 0`：偏移已在末尾，返回 0，`errno` 保持原样。0 是「没有更多数据」，不是错误。
- 最后两行是错误形态：返回 -1，原因在 `errno`（`EBADF` 表示这个 fd 不以该方式打开，`ESPIPE` 表示对象不支持定位）。

这里有个容易写错的地方：把 `read(...)` 和 `strerror(errno)` 放进同一个 `printf`，参数求值顺序不确定，`strerror` 可能先跑。上面的代码先调用、后打印，输出才可靠。

::: def 定义 1.10.1 · 文件描述符（file descriptor，fd） {#def-1.10.1-fd}
fd 是一个非负小整数，作为进程 fd 表的下标。表项指向内核的**打开文件描述**（open file description），其中记录当前偏移和打开标志；打开文件描述再指向 inode（文件系统里记录这个文件元数据的结构）。同一进程两次 `open` 同一路径得到两个 fd、两个描述、两个独立偏移；`fork` 出的子进程与 `dup` 出来的新 fd 才共享同一个描述。
:::

四个动作的返回值各有约定，这张表值得记住最后一列：

| 动作 | 接口 | 成功 | 失败 |
|:--|:--|:--|:--|
| 打开 | `open`/`openat` | 最小的空闲 fd | -1 |
| 读 | `read` | 实际读到的字节数，0 表示 EOF | -1 |
| 写 | `write` | 实际写入的字节数，可能小于请求 | -1 |
| 定位 | `lseek` | 新偏移 | -1 |
| 关闭 | `close` | 0 | -1 |

读和写是同一动作的两个方向，所以「四个动作」是打开、读写、定位、关闭。`read`/`write` 的返回值同时承担三种信息：字节数、EOF（只有 `read` 的 0）、错误（-1）。后面讲的短读、短写、`EINTR`，全是在这三者之间做区分。

### 同一类句柄，不同的对象

fd 只是入口，读写的真正含义取决于它指向什么：

| 类型 | `S_IS*` 宏 | 用 fd 读写时的行为 |
|:--|:--|:--|
| 普通文件 | `S_ISREG` | 字节序列，可 `lseek`，短读只发生在末尾或信号之后 |
| 目录 | `S_ISDIR` | 可以 `open`/`fstat`，不能用 `read` 读，要用 `readdir` |
| 字符设备 | `S_ISCHR` | 终端、`/dev/null`，按设备语义，行缓冲由终端驱动决定 |
| 块设备 | `S_ISBLK` | 磁盘，通常经由文件系统访问，裸设备需要权限 |
| FIFO | `S_ISFIFO` | 管道，读阻塞到有数据，短读是常态 |
| socket | `S_ISSOCK` | 网络/本地通信，`read`/`write` 等价 `recv`/`send` |
| 符号链接 | `S_ISLNK` | 打开时跟随目标，`O_NOFOLLOW` 才拒绝 |

这张表说明：「一切皆文件」是说一切都能套进这套动作，不是说行为都一样。普通文件可以 `lseek`，管道不行（上面实测 `ESPIPE`）；目录能打开、能 `fstat`，但不能用 `read` 读（1.10.3 会实测到 `EISDIR`）。

0/1/2 也只是三个编号。shell 可以把它们重定向到文件、管道或 socket；在 `ssh` 里跑上面的程序，0/1/2 全是管道。程序不该假设「fd 1 一定连着终端」，日志库尤其如此。

### 第二个实验：`O_APPEND` 到底保证什么

下面两段代码都让两个 fd 各写 3 字节，区别只在第二段带了 `O_APPEND`：

```c
/* append_demo.c：同样的两次 write，一次普通打开，一次 O_APPEND */
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>

static void put(int fd, const char *s)
{
    if (write(fd, s, 3) != 3) perror("write");
}

static void show(const char *tag, const char *p)
{
    char buf[16] = {0};
    int fd = open(p, O_RDONLY);
    ssize_t n = read(fd, buf, sizeof buf - 1);
    close(fd);
    printf("%-7s content=\"%.*s\" (%zd bytes)\n", tag, (int)n, buf, n);
}

int main(void)
{
    const char *p = "/tmp/lab1c10_app";
    int a, b;

    a = open(p, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    b = open(p, O_WRONLY);
    lseek(a, 0, SEEK_END);
    lseek(b, 0, SEEK_END);
    put(a, "AAA");
    put(b, "BBB");                 /* 两个描述都以为自己在 0 处写 */
    show("plain", p);
    close(a);
    close(b);

    unlink(p);
    a = open(p, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    b = open(p, O_WRONLY | O_APPEND);
    lseek(a, 0, SEEK_SET);         /* 故意把偏移挪回文件头 */
    lseek(b, 0, SEEK_SET);
    put(a, "CCC");
    put(b, "DDD");
    show("append", p);
    close(a);
    close(b);
    unlink(p);
    return 0;
}
```

实测输出：

```text
plain   content="BBB" (3 bytes)
append  content="CCCDDD" (6 bytes)
```

第一段：两个打开文件描述各自记录偏移，`lseek` 到末尾时文件还是空的，两者都得到 0；`AAA` 写在 0 处，`BBB` 也写在 0 处，把 `AAA` 覆盖掉。第二段：虽然 `lseek` 把偏移挪到了 0，`O_APPEND` 让每次 `write` 先把偏移设到当前文件末尾、再写，于是 `CCC`、`DDD` 依次接在后面。

边界要记清：`O_APPEND` 保证的是「定位到末尾 + 写入」这一步不可分割，不是「你的连续两次 `write` 中间不会插进别人」。单写者、单 fd 时，普通 `lseek` + `write` 也不会出错，`O_APPEND` 是给多写者准备的；日志要整段独占，仍得靠锁。本机 ext4 上如此；NFS 的追加语义取决于服务器实现，本机没有 NFS 挂载，未实测。

::: ex 例 1.10.1 · 先猜连续四次 `read` 的返回值 {#ex-1.10.1}
文件 `/etc/hostname` 长 21 字节，内容以 `juanwang` 开头。打开后连续做四次 `read(fd, buf, 8)`，每次各返回多少？哪一次才是 EOF？

::: sol 解答
实测依次是 8、8、5、0：前两次读满，第三次只剩 5 字节，第四次到末尾返回 0。中间那次 5 就是**短读**，属于正常结果；只有 0 表示 EOF。如果把 5 当错误退出，会丢掉最后 5 个字节；如果把 0 当「读到 0 字节的数据」继续处理，会拿旧缓冲区内容当新数据。
:::
:::

::: errata 四个动作的坑
1. **「`read` 返回 0 就是出错」**——0 是 EOF，错误是 -1。实测末尾 `read` 返回 0 且 `errno` 不变；把 0 当错误退出，会让正常的文件读完就报错。
2. **「`read` 一次能读满请求的字节数」**——管道、socket、终端都可能提前返回。实测向管道写 200000 字节只收下 65536（1.10.4），读侧同理，必须循环。
3. **「`read` 返回 -1 就是失败」**——`EINTR` 也是 -1：信号在阻塞期间到达，`read` 没读到任何东西就返回。实测读空管道被 `SIGALRM` 打断，返回 -1/`Interrupted system call`，重试即可（1.10.4）。
4. **「`close` 成功就落盘了」**——`close` 只归还 fd。数据在内核的 page cache（页缓存，用内存缓存文件内容的地方）里，掉电仍可能丢；要持久化得 `fsync`（1.10.6、1.10.15）。
5. **「`O_APPEND` 等于给文件加锁」**——它只让单次 `write` 原子地追加；两次 `write` 之间别人仍可插入。
6. **「`O_DIRECT` 打开就能读」**——它要求缓冲区地址、长度、文件偏移都按块对齐。实测 ext4 上 4096 对齐的缓冲区、长度 4096、偏移 0 成功；`malloc` 的缓冲区、偏移 1、长度 100 都返回 `EINVAL`。对齐单位随文件系统和设备变化，换机器前要重新确认。
:::

### 1.10.1 小结

① 四个动作加一个整数句柄，把文件、管道、设备、socket 收进同一套接口，语义由对象决定；② `read` 的 0、-1、正数是三种不同结果，`errno` 只对 -1 有意义；③ `O_APPEND` 保护的是单次追加动作，不是整段日志。如果只记住一件事，那就是：**返回值和 `errno` 是这套接口的全部信息，永远先看返回值再谈别的。**

::: method 即时自测 · 1.10.1
**Q1（记忆）** `open` 返回的 fd 是「下一个编号」还是「最小空闲编号」？0/1/2 分别约定成什么？

**Q2（辨析）** `read` 返回 0 与返回 -1 各说明什么？`errno` 在哪种情况下才有意义？

**Q3（应用）** 两个进程各自 `open` 同一个日志文件、都先 `lseek` 到末尾再 `write`，日志丢了一段。改哪一个打开标志能解决？它保证到什么程度？

**Q4（迁移）** 一段代码对目录 fd 调 `read` 得到 -1/`EISDIR`，对管道 fd 调 `lseek` 得到 -1/`ESPIPE`。这两次失败是「fd 无效」吗？

::: sol 答案
**A1** 最小空闲编号（实测 `close(0)` 后 `open` 得到 0）；0/1/2 约定为标准输入、标准输出、标准错误，但可以被重定向成管道或文件。
**A2** 0 是 EOF（没有更多数据），-1 是错误；`errno` 只在返回 -1 时有意义，且要先清零、紧接着读。
**A3** 加 `O_APPEND`：每次 `write` 原子地定位到末尾。它不保证两次 `write` 之间没有别人插入，整段独占要另加锁。
**A4** 不是。fd 有效，是对象类型不支持这个动作；错误码已经说明了原因（目录不可读、管道不可定位）。
:::

## 1.10.2 元数据：stat 与文件身份 {#sec-1.10.2}

这一节回答：`ls -l` 里的大小、链接数、权限是从哪儿读出来的？两条路径在什么条件下算「同一个文件」？

::: preview 先抓住一件事
文件名不是文件的身份。内核对每个文件维护一个 **inode**（索引节点），里面存类型、权限、大小、时间、数据块位置；`stat` 把这批**元数据**（metadata）复制到用户态。判断「是不是同一个文件」只看两件事：`st_dev`（哪个设备）与 `st_ino`（哪个 inode）。名字可以有好几个（硬链接），也可以随时被换掉。
:::

### 场景：给同一份数据造三个名字

先准备一个目录（Ubuntu 24.04.5，`/tmp` 是 ext4）：

```bash
mkdir -p /tmp/lab1c10_meta/sub
printf 0123456789 > /tmp/lab1c10_meta/a.txt
ln /tmp/lab1c10_meta/a.txt /tmp/lab1c10_meta/b.txt     # 硬链接
ln -s a.txt /tmp/lab1c10_meta/l.txt                    # 符号链接
truncate -s 1048576 /tmp/lab1c10_meta/sparse.bin       # 稀疏文件
```

先猜两件事：`a.txt` 与 `b.txt` 的 inode 号相同吗？`l.txt` 的 `st_size` 是目标的 10 字节，还是 `a.txt` 这 5 个字符？

```c
/* stat_id.c：同一批字段，lstat 看链接本身 */
#define _GNU_SOURCE
#include <stdio.h>
#include <sys/stat.h>
#include <sys/sysmacros.h>

static void show(const char *tag, const char *p)
{
    struct stat st;
    if (lstat(p, &st) == -1) { perror(p); return; }
    printf("%-9s size=%-8lld blocks=%-4lld blksize=%-5ld nlink=%lu ino=%-7llu dev=%u:%u mode=%06o\n",
           tag, (long long)st.st_size, (long long)st.st_blocks,
           (long)st.st_blksize, (unsigned long)st.st_nlink,
           (unsigned long long)st.st_ino, major(st.st_dev), minor(st.st_dev),
           (unsigned)st.st_mode);
}

int main(void)
{
    const char *A = "/tmp/lab1c10_meta/a.txt";
    const char *B = "/tmp/lab1c10_meta/b.txt";
    const char *L = "/tmp/lab1c10_meta/l.txt";

    show("file", A);
    show("hardlink", B);
    show("symlink", L);
    show("sparse", "/tmp/lab1c10_meta/sparse.bin");
    show("dir", "/tmp/lab1c10_meta");
    show("chardev", "/dev/null");
    show("procfs", "/proc/self/status");

    struct stat a, b, l, sl;
    if (stat(A, &a) == -1 || stat(B, &b) == -1 ||
        lstat(L, &l) == -1 || stat(L, &sl) == -1)
        return 1;
    printf("a vs b: same dev+ino? %d\n",
           a.st_dev == b.st_dev && a.st_ino == b.st_ino);
    printf("link: stat ino=%llu, lstat ino=%llu\n",
           (unsigned long long)sl.st_ino, (unsigned long long)l.st_ino);
    return 0;
}
```

实测输出（`cc -std=c17 -O2`）：

```text
file      size=10       blocks=8    blksize=4096  nlink=2 ino=177186  dev=8:2 mode=100664
hardlink  size=10       blocks=8    blksize=4096  nlink=2 ino=177186  dev=8:2 mode=100664
symlink   size=5        blocks=0    blksize=4096  nlink=1 ino=177187  dev=8:2 mode=120777
sparse    size=1048576  blocks=0    blksize=4096  nlink=1 ino=177192  dev=8:2 mode=100664
dir       size=4096     blocks=8    blksize=4096  nlink=3 ino=177176  dev=8:2 mode=040775
chardev   size=0        blocks=0    blksize=4096  nlink=1 ino=6       dev=0:7 mode=020666
procfs    size=0        blocks=0    blksize=1024  nlink=1 ino=787301  dev=0:28 mode=100444
a vs b: same dev+ino? 1
link: stat ino=177186, lstat ino=177187
```

逐行读，六个结论：

- `file` 与 `hardlink` 的 `dev`、`ino`、`nlink` 全相同（177186，链接数 2）：两个名字指向同一个 inode，硬链接只是多了一条目录项。
- `symlink` 的 `size=5` 是链接目标字符串 `a.txt` 的长度，不是目标的 10；`mode=120777` 的类型位是链接。最后一行给出对照：`stat` 跟到目标的 177186，`lstat` 看到链接本身的 177187。
- `sparse` 文件逻辑大小 1 MiB，`blocks=0`：一个数据块都没分配，读出来全是 0。`ls -l` 看 `st_size`，`du` 看 `st_blocks`。
- `dir` 的大小是 4096（目录也占块），`nlink=3`：目录的链接数等于 2 加子目录数（`.`、父目录中的条目、`sub`）。
- `chardev` 的 `size=0`，但 `dev=0:7` 是设备号：字符设备没有「文件内容」，读写走设备驱动。
- `procfs` 的 `size=0`、`blksize=1024`，内容却是每次读时现生成的。`/proc` 里的大小不可当字节数用。

::: def 定义 1.10.2 · inode 与文件身份 {#def-1.10.2}
inode 是文件系统里描述一个文件的记录：类型、权限、属主、大小、时间戳、数据块位置、链接数。目录项只保存「名字 → inode 号」。文件身份用 `(st_dev, st_ino)` 这一对值表示：不同设备上 inode 号可能重复，单看 `st_ino` 不够；`st_nlink` 归零且没有进程打开时，数据块才被回收。
:::

### 字段怎么读

`struct stat` 有十几个字段，常用的就下面这些：

| 字段 | 含义 | 容易踩的地方 |
|:--|:--|:--|
| `st_dev`、`st_ino` | 设备号、inode 号 | 文件身份只看这一对，不看名字 |
| `st_mode` | 类型位 + 权限位 | 判断类型用 `S_ISREG` 等宏，取权限要 `& 07777` |
| `st_nlink` | 硬链接数 | 目录的链接数等于 2 加子目录数 |
| `st_size` | 逻辑字节数 | 对目录、`/proc`、设备不代表内容长度 |
| `st_blocks` | 已分配的 512 字节块数 | 稀疏文件可以是 0；`du` 用它算占用 |
| `st_blksize` | 推荐的 I/O 大小 | 只是建议值，不是磁盘扇区；常等于文件系统块大小，但不保证 |
| `st_atim`、`st_mtim`、`st_ctim` | 访问、内容修改、状态变更时间 | `ctim` 不是创建时间 |

两个单位要分清。`st_blocks` 的单位固定是 512 字节，和文件系统块大小无关：实测 10 字节的文件 `blocks=8`，正好 4096 字节，因为 ext4 按 4 KiB 分配。`st_blksize` 在普通文件上是 4096，在 `/proc/self/status` 上是 1024——它跟着文件系统走，不能当成「磁盘扇区」。

`st_ctim` 在 `chmod`、`chown`、`rename`、`link` 之后都会变，所以它既不是创建时间，也不是内容修改时间。`struct stat` 里根本没有创建时间；`statx` 有这个字段（`stx_btime`），但要看文件系统是否记录。

### 四个入口，选对参照物

| 接口 | 是否跟随符号链接 | 相对谁解析 |
|:--|:--|:--|
| `stat(path, &st)` | 跟随 | 当前工作目录 |
| `lstat(path, &st)` | 不跟随 | 当前工作目录 |
| `fstat(fd, &st)` | 已打开对象 | fd |
| `fstatat(dirfd, path, &st, flags)` | 由 `AT_SYMLINK_NOFOLLOW` 控制 | `dirfd` |

遍历目录时，先 `open(dir, O_DIRECTORY)` 拿到 `dirfd`，再用 `fstatat(dirfd, name, &st, AT_SYMLINK_NOFOLLOW)`。这样名字相对已打开的目录解析，不受当前工作目录被别人 `chdir` 的影响；要「打开后再确认身份」，就先 `open`，再 `fstat` 那个 fd——fd 钉住了 inode，路径再怎么改名都换不掉它。

::: ex 例 1.10.2 · 先猜这个文件占多少磁盘 {#ex-1.10.2}
`truncate -s 1048576 sparse.bin` 造出一个 1 MiB 的文件。先猜：`ls -l` 显示多大？`du -B1` 显示多大？读它一个字节，读到的是什么？

::: sol 解答
实测 `ls -l` 显示 1048576，`du -B1` 显示 0，`stat` 给出 `size=1048576 blocks=0`。这个文件一个数据块都没分配，读出来全是 0 字节（`\0`）。`truncate` 只改了 inode 里的长度，没写数据；只有真正写入某个块时，文件系统才分配它。所以「文件多大」和「占多少磁盘」是两个问题，备份、配额、镜像估算时不能混。
:::
:::

### 名字会换，inode 不会

实测同一份数据：`mv a.txt c.txt` 之后，`c.txt` 的 ino 仍是 177186，`b.txt` 也还是 177186；随后 `printf new > a.txt` 新建同名文件，新 `a.txt` 的 ino 是 177230，`nlink` 回到 1。也就是说：

- 改名不换 inode，只换目录项里的名字；
- 「删掉再建同名文件」得到的是新 inode，旧 inode 只被还开着的 fd 撑着；
- 拿「路径 + 上次的 `stat`」当身份会认错对象。要跟踪一个文件，应该保存 `(st_dev, st_ino)`，或者干脆一直握着 fd。

::: errata 元数据的六个误解
1. **「`st_ctim` 是创建时间」**——是 inode 状态变更时间，`chmod` 也会刷新它。Linux 的 `stat` 没有创建时间字段。
2. **「`st_size` 就是磁盘占用」**——稀疏文件实测 `size=1048576`、`blocks=0`；`du` 与 `ls -l` 不一致是正常的。
3. **「`/proc` 里的文件大小为 0 就是空文件」**——`/proc/self/status` 的 `size=0`，内容在 `read` 时生成，长度事先不知道。
4. **「目录大小 4096 就是里面有 4096 字节的名字」**——目录大小是目录文件自身占的块，和项数没有线性关系；项多到装不下时文件系统会扩块或改成树形索引。
5. **「路径能代表文件」**——同一条路径在两次 `stat` 之间可能被 `rename` 换成另一个 inode（TOCTOU，time-of-check to time-of-use：检查和使用之间对象被换掉）。安全校验要 `open` 后 `fstat` 同一个 fd。
6. **「`st_mode` 可以直接和 `0644` 比」**——它含类型位（实测普通文件是 `100664`）。比较权限要先 `& 07777`。
:::

### 1.10.2 小结

① `stat` 把 inode 里的元数据复制出来，`size`、`blocks`、`blksize`、`nlink` 各有各的单位和用途；② 文件身份是 `(st_dev, st_ino)`，名字只是目录项，改名不换 inode、重建才换；③ `stat`/`lstat`/`fstat`/`fstatat` 的差别在「跟不跟随符号链接」和「相对谁解析」。如果只记住一件事，那就是：**要认文件就认 `(dev, ino)` 或 fd，不要认路径。**

## 1.10.3 目录：不是文本文件 {#sec-1.10.3}

这一节回答：`cat` 一个目录为什么直接报错，而 `ls` 既能列出名字、又不用把目录「读成文本」？

::: preview 先抓住一件事
目录在内核里是一组**目录项**（directory entry）：每条记录保存「名字 → inode 号」，可能还带类型。它不是字节流，`read()` 一个目录 fd 会返回 -1/`EISDIR`。列目录要用 `readdir`，它底下是 `getdents64` 系统调用（程序请求内核代劳的入口），返回的是一串**变长记录**。记录长度按 8 字节对齐，名字在固定偏移之后；顺序由文件系统决定，不要假设 `.` 在最前。
:::

### 场景：直接读目录，再拆一条记录

准备一个小目录（Ubuntu 24.04.5，ext4）：

```bash
mkdir -p /tmp/lab1c10_dir/sub
printf x > /tmp/lab1c10_dir/a.txt
printf y > /tmp/lab1c10_dir/b.txt
ln -s a.txt /tmp/lab1c10_dir/l.txt
```

先猜两件事：`cat /tmp/lab1c10_dir` 会打印什么？`getdents64` 返回的第一条记录，名字是 `.` 吗？

```c
/* list_raw.c：绕过 readdir，直接看内核返回的记录 */
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <errno.h>
#include <fcntl.h>
#include <unistd.h>
#include <dirent.h>
#include <sys/syscall.h>

struct raw_dirent {
    unsigned long long d_ino;
    long long          d_off;
    unsigned short     d_reclen;
    unsigned char      d_type;
    char               d_name[];
};

static const char *tn(unsigned char t)
{
    switch (t) {
    case DT_REG: return "REG";
    case DT_DIR: return "DIR";
    case DT_LNK: return "LNK";
    case DT_FIFO: return "FIFO";
    case DT_UNKNOWN: return "UNKNOWN";
    default: return "?";
    }
}

int main(void)
{
    const char *path = "/tmp/lab1c10_dir";

    int dfd = open(path, O_RDONLY | O_DIRECTORY);
    char b[8];
    errno = 0;
    ssize_t n = read(dfd, b, sizeof b);
    printf("read() on directory -> %zd errno=%s\n", n, strerror(errno));

    char buf[4096];
    long len = syscall(SYS_getdents64, dfd, buf, sizeof buf);
    printf("getdents64 -> %ld bytes\n", len);
    long off = 0;
    for (int k = 0; k < 3 && off < len; k++) {
        struct raw_dirent *d = (struct raw_dirent *)(buf + off);
        printf("rec%d off=%-2ld ino=%-7llu reclen=%-2u type=%-3s name=%s\n",
               k, off, d->d_ino, d->d_reclen, tn(d->d_type), d->d_name);
        off += d->d_reclen;
    }
    printf("first 24 bytes:");
    for (int i = 0; i < 24; i++) printf(" %02x", (unsigned char)buf[i]);
    printf("\nfixed part=19 bytes, d_name at 19, reclen aligned to 8\n");
    close(dfd);

    DIR *dp = opendir(path);
    struct dirent *e;
    int total = 0, unk = 0, dirs = 0, regs = 0, lnks = 0;
    while ((e = readdir(dp)) != NULL) {
        total++;
        if (e->d_type == DT_UNKNOWN) unk++;
        else if (e->d_type == DT_DIR) dirs++;
        else if (e->d_type == DT_REG) regs++;
        else if (e->d_type == DT_LNK) lnks++;
    }
    closedir(dp);
    printf("entries=%d DIR=%d REG=%d LNK=%d UNKNOWN=%d\n",
           total, dirs, regs, lnks, unk);
    return 0;
}
```

实测输出（`cc -std=c17 -O2`）：

```text
read() on directory -> -1 errno=Is a directory
getdents64 -> 168 bytes
rec0 off=0  ino=177197  reclen=32 type=LNK name=l.txt
rec1 off=32 ino=177193  reclen=24 type=DIR name=.
rec2 off=56 ino=177194  reclen=24 type=DIR name=sub
first 24 bytes: 2d b4 02 00 00 00 00 00 11 4a 99 ca 65 c3 eb 20 20 00 0a 6c 2e 74 78 74
fixed part=19 bytes, d_name at 19, reclen aligned to 8
entries=6 DIR=3 REG=2 LNK=1 UNKNOWN=0
```

四个读法：

- 第一行：目录 fd 有效，但 `read` 拒绝按字节流读，`errno` 是 `EISDIR`。目录内容只能通过 `getdents64`/`readdir` 取。
- 第二行：内核一次返回 168 字节，这是六条变长记录拼在一起的**缓冲**，不是六个结构体数组；下一条记录的起点要靠当前记录的 `reclen` 推。
- 第一条记录的名字是 `l.txt`，`.` 反而在第二条：**目录顺序由文件系统决定**。ext4 开目录索引后按名字哈希排，所以「`.` 一定第一条」是错的。
- `reclen` 是 24 或 32，不是 `sizeof(struct dirent)`；名字越长记录越长，并且补齐到 8 的倍数。十六进制里偏移 18 处是 `0a`（`DT_LNK`），偏移 19 起是 `6c 2e 74 78 74`（`l.txt`），说明名字从偏移 19 开始。

最后一行：`readdir` 遍历到 6 项（含 `.` 与 `..`），其中 3 个目录、2 个普通文件、1 个符号链接，没有一项是 `DT_UNKNOWN`。

::: def 定义 1.10.3 · 目录项（directory entry） {#def-1.10.3}
目录项是目录文件里的一条记录，至少包含名字和 inode 号。`getdents64` 返回的每条记录由固定头（8 字节 inode、8 字节下一位置、2 字节记录长度、1 字节类型）加上以 `\0` 结尾的名字组成，整体按 8 字节对齐。`readdir` 是 glibc 对这层记录的封装，返回指向内部缓冲区的 `struct dirent *`。
:::

### 一条记录怎么算长度

记录头固定 19 字节，名字以 `\0` 结尾，整条再补齐到 8 的倍数：

```text
reclen = round_up(19 + strlen(name) + 1, 8)
"."     -> 19 + 1 + 1 = 21 -> 24
"sub"   -> 19 + 3 + 1 = 23 -> 24
"l.txt" -> 19 + 5 + 1 = 25 -> 32
```

这正好对上实测的三条 `reclen`。字段的含义与用法：

| 字段 | 长度 | 含义 | 注意 |
|:--|--:|:--|:--|
| `d_ino` | 8 | inode 号 | 与 `stat` 的 `st_ino` 同源，但仍要配 `st_dev` 才算身份 |
| `d_off` | 8 | 下一条记录的位置 | 对用户是不透明值，只能交给 `telldir`/`seekdir`，不要自己加减 |
| `d_reclen` | 2 | 本条记录长度 | 下一条从 `buf + reclen` 开始 |
| `d_type` | 1 | 类型（4=DIR、8=REG、10=LNK、0=UNKNOWN） | 可能不可用，见下 |
| `d_name` | 变长 | 名字，`\0` 结尾，不含 `/` | 最长 255 字节 |

`d_off` 不要当字节偏移理解。实测在 `/tmp` 上第一条记录的 `d_off` 是 4294967296，远大于目录大小——它是文件系统给的游标，含义随实现变化，只能原样传回 `seekdir`。

`d_type` 是加速项，不是保证。本机 ext4 的 `/tmp`、procfs 的 `/proc/self`、sysfs 的 `/sys/class/net` 都返回了具体类型（`UNKNOWN` 计数为 0），但 XFS、NFS 等文件系统可能只给 `DT_UNKNOWN`——本机没有这两类挂载，未实测。所以遍历代码要留兜底：`d_type == DT_UNKNOWN` 时对名字做 `fstatat(dirfd, name, &st, AT_SYMLINK_NOFOLLOW)`。这也是 `ls` 在部分网络文件系统上变慢的原因。

`readdir` 返回的指针指向 `DIR` 内部缓冲区，下一次 `readdir` 会覆盖它；要留住名字就 `strdup` 或拷进自己的数组。同一个 `DIR` 被多个线程共用时，返回的记录会彼此穿插；多线程遍历就让每个线程 `opendir` 自己的 `DIR`。

::: ex 例 1.10.3 · 先猜这条目录记录多长 {#ex-1.10.3}
目录里有一个普通文件 `a.txt`。它的目录项 `reclen` 是多少？如果把名字改成 `ab.txt`，`reclen` 会变吗？

::: sol 解答
`19 + 5 + 1 = 25`，补齐到 8 的倍数得 32；`ab.txt` 是 6 个字符，`19 + 6 + 1 = 26`，补齐后仍是 32。名字 1 到 4 个字符落在 24（`19 + 4 + 1 = 24` 正好整除），5 到 12 个字符落在 32。这也说明目录文件的大小按块增长，和文件个数不是线性关系。
:::
:::

::: errata 目录的六个坑
1. **「`cat` 目录报错是权限不够」**——实测报 `EISDIR`，`errno` 说得清清楚楚：对象类型不支持 `read`。加 `sudo` 也没用。
2. **「`readdir` 按字母序返回」**——实测 `.` 排在 `l.txt` 后面。顺序由文件系统决定，要排序就自己收集后 `qsort`。
3. **「`d_type` 一定准」**——可能是 `DT_UNKNOWN`；即使有值，也只应作为提示，关键判断仍可 `fstatat` 确认。
4. **「保存 `readdir` 返回的指针就行」**——下一次调用会覆盖同一块缓冲区，之前保存的指针全部失效。
5. **「按 `sizeof(struct dirent)` 往后走」**——记录是变长的，必须用 `d_reclen`；`readdir` 已经替你做了这件事。
6. **「目录也能 `write`」**——目录内容由内核维护，用户态只能通过 `mkdir`、`unlink`、`rename`、`link` 改它，没有「往目录里写一条记录」的接口。
:::

### 1.10.3 小结

① 目录是「名字 → inode」的记录集合，不是文本，`read` 会得到 `EISDIR`；② 记录变长、按 8 字节对齐，名字在固定头之后，遍历要靠 `reclen` 或 `readdir`；③ 顺序和 `d_type` 都只是文件系统给的提示，不能当保证。如果只记住一件事，那就是：**列目录用 `readdir`，要稳定顺序就自己排序，要可靠类型就 `fstatat`。**

::: method 即时自测 · 1.10.3
**Q1（记忆）** `getdents64` 一条记录的固定头有多少字节？名字从第几字节开始？

**Q2（辨析）** 为什么 `read(dirfd, buf, 8)` 返回 -1，而同样的 fd 上 `getdents64` 能成功？

**Q3（应用）** 遍历时把每个 `struct dirent *` 存进数组，循环结束后打印名字，为什么全是最后一个？

**Q4（迁移）** 一个程序在 NFS 挂载上遍历时 `d_type` 全是 `DT_UNKNOWN`，它原来按类型跳过目录。怎样改才不会漏？

::: sol 答案
**A1** 19 字节：8 字节 inode、8 字节 `d_off`、2 字节 `reclen`、1 字节 `d_type`；名字从偏移 19 开始，含结尾 `\0`，整条按 8 对齐。
**A2** `read` 只接受字节流对象，目录不是；`getdents64` 是专门为目录定义的接口，返回记录而不是字节。
**A3** `readdir` 复用同一块内部缓冲区，数组里存的是同一个地址，最后一次调用把它覆盖了；应复制名字。
**A4** 对 `DT_UNKNOWN` 的项做 `fstatat` 判断类型；也可干脆对所有项都 `fstatat`，只是多一次系统调用。
:::

## 1.10.4 RIO：把短读、短写和缓冲包起来 {#sec-1.10.4}

这一节回答：`read`/`write` 已经会用了，为什么还要再写一个 RIO 包？因为「请求多少」和「实际拿到多少」从来不是一回事。

::: preview 先抓住一件事
一次 `read`/`write` 可能只完成一部分，也可能被信号打断（`EINTR`）而一个字节都没动。正确做法是循环：读到 0 为止、写到写完为止、遇到 `EINTR` 重试。把这三个循环和一块用户态缓冲区封起来，就是**健壮 I/O**（robust I/O，RIO）。它看起来像 stdio，但没有全局锁，缓冲区归调用者所有。
:::

### 场景一：被闹钟打断的 `read`

先猜：一个阻塞在空管道上的 `read`，1 秒后收到 `SIGALRM`，会返回什么？

```c
/* eintr.c：读空管道，1 秒后被闹钟打断 */
#define _GNU_SOURCE
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static volatile sig_atomic_t hit;

static void on_alarm(int s) { (void)s; hit = 1; }

int main(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = on_alarm;           /* sa_flags 为 0：系统调用不自动重启 */
    sigaction(SIGALRM, &sa, NULL);

    int p[2];
    if (pipe(p) == -1) return 1;
    char buf[8];
    alarm(1);
    errno = 0;
    ssize_t n = read(p[0], buf, sizeof buf);
    printf("read -> %zd errno=%s hit=%d\n", n, strerror(errno), (int)hit);

    if (write(p[1], "OK", 2) != 2) return 1;
    n = read(p[0], buf, sizeof buf);
    printf("retry -> %zd bytes\n", n);
    return 0;
}
```

实测输出：

```text
read -> -1 errno=Interrupted system call hit=1
retry -> 2 bytes
```

`read` 返回 -1，`errno` 是 `EINTR`，但管道里并没有少数据：这次读**一个字节都没取走**。handler 返回后程序从 `read` 的下一条继续跑，于是第二行能读到后来写进去的 `OK`。

所以 `EINTR` 不是「读失败」，是「这次没读，你可以再来一次」。处理方式就是原样重试。如果把 `sa_flags` 设成 `SA_RESTART`，内核会自动重启这类阻塞调用，多数时候看不到 `EINTR`；但不是所有接口都能重启（`poll` 的超时行为、部分设备驱动就不同），所以库代码一律显式处理，不赌默认值。

::: def 定义 1.10.4 · 健壮 I/O（robust I/O，RIO） {#def-1.10.4}
RIO 是「把系统调用的不完整结果处理干净」的一层薄封装：无缓冲版 `rio_readn`/`rio_writen` 用循环补足短读短写并对 `EINTR` 重试；带缓冲版 `rio_read`/`rio_readlineb` 在用户态攒一块数据，减少系统调用次数。它不改变 `read`/`write` 的语义，只保证调用者拿到「请求的数量」或「明确的 EOF/错误」。
:::

### 场景二：请求 200000 字节，只收下 65536

`EINTR` 只是「重来」的一种。更常见的是「做了一半」：`read` 只读到一部分，`write` 只写进去一部分。下面的程序把两种循环写在一起：

```c
/* rio_unbuf.c：无缓冲的健壮读与写 */
#define _GNU_SOURCE
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

static void on_alarm(int s) { (void)s; }

static ssize_t rio_readn(int fd, void *usrbuf, size_t n)
{
    size_t nleft = n;
    char *bufp = usrbuf;
    while (nleft > 0) {
        ssize_t rc = read(fd, bufp, nleft);
        if (rc < 0) {
            if (errno == EINTR) continue;      /* 被打断：重来 */
            return -1;
        }
        if (rc == 0) break;                     /* EOF：可能不够 n */
        nleft -= (size_t)rc;
        bufp += rc;
    }
    return (ssize_t)(n - nleft);
}

static ssize_t rio_writen(int fd, const void *usrbuf, size_t n)
{
    size_t nleft = n;
    const char *bufp = usrbuf;
    while (nleft > 0) {
        ssize_t rc = write(fd, bufp, nleft);
        if (rc < 0) {
            if (errno == EINTR) continue;
            return -1;
        }
        if (rc == 0) { errno = EIO; return -1; }  /* 防止空转 */
        nleft -= (size_t)rc;
        bufp += rc;
    }
    return (ssize_t)n;
}

int main(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = on_alarm;
    sigaction(SIGALRM, &sa, NULL);

    int q[2];
    if (pipe(q) == -1) return 1;
    if (write(q[1], "hello", 5) != 5) return 1;
    close(q[1]);
    char small[64];
    printf("rio_readn(64) on 5-byte pipe -> %zd\n", rio_readn(q[0], small, 64));
    close(q[0]);

    int r[2];
    if (pipe(r) == -1) return 1;
    pid_t pid = fork();
    if (pid == 0) {
        close(r[1]);
        usleep(2000000);
        char tmp[65536];
        while (read(r[0], tmp, sizeof tmp) > 0) { }
        _exit(0);
    }
    close(r[0]);
    static char big[200000];
    memset(big, 'x', sizeof big);
    alarm(1);                       /* 写阻塞时被闹钟打断 */
    errno = 0;
    ssize_t first = write(r[1], big, sizeof big);
    printf("write(200000) -> %zd errno=%s\n", first, strerror(errno));
    ssize_t rest = rio_writen(r[1], big + first, sizeof big - (size_t)first);
    printf("rio_writen() -> %zd\n", rest);
    close(r[1]);
    waitpid(pid, NULL, 0);
    return 0;
}
```

实测输出：

```text
rio_readn(64) on 5-byte pipe -> 5
write(200000) -> 65536 errno=Success
rio_writen() -> 134464
```

三段读法：

- 第一行：要 64 字节，管道里只有 5 字节且写端已关。`rio_readn` 读到 EOF 就停，返回 5。返回值小于 `n` 不一定是错误——调用者拿到的就是「实际有多少」。
- 第二行：一次 `write` 只收下 65536 字节，`errno` 还是 `Success`。管道缓冲区容量就这么大，剩下的一次交不进去；这次写还被闹钟打断，内核把「已经复制的部分」如实返回。短写不是错误，只是没写完。
- 第三行：`rio_writen` 从第 65536 字节继续写，循环 134464 字节全部交给内核。

什么时候会遇到短写：管道或 socket 的发送缓冲区满、fd 设了 `O_NONBLOCK`、写大块时被信号打断。普通文件通常一次写满，但磁盘满、配额、`RLIMIT_FSIZE` 也会让写入提前结束或直接失败。`write` 返回 0 且 `n > 0` 属于异常，循环里必须当错误处理，否则永远转下去。

短读同理：管道和 socket 「有多少给多少」，终端按行返回，普通文件一般读满，除非已到末尾或被信号打断。**所以凡是 `read`/`write`，都要按循环写，不能假设一次就够。**

### 带缓冲：294 次系统调用压成 3 次

无缓冲版解决了「不完整」，但每次只读一个字节时，系统调用次数会跟着字节数走。带缓冲版在用户态攒 8 KiB，`readlineb` 从缓冲区里逐字节取：

```c
/* rio_line.c：带缓冲的按行读；-c 则退化成逐字节 read，用来对照 */
#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

#define RIO_BUFSIZE 8192

typedef struct {
    int     rio_fd;
    ssize_t rio_cnt;        /* 缓冲区里还有多少未读字节 */
    char   *rio_bufptr;     /* 下一个未读字节 */
    char    rio_buf[RIO_BUFSIZE];
} rio_t;

static void rio_readinitb(rio_t *rp, int fd)
{
    rp->rio_fd = fd;
    rp->rio_cnt = 0;
    rp->rio_bufptr = rp->rio_buf;
}

static ssize_t rio_read(rio_t *rp, char *usrbuf, size_t n)
{
    while (rp->rio_cnt <= 0) {                 /* 只有空了才进内核 */
        ssize_t rc = read(rp->rio_fd, rp->rio_buf, sizeof(rp->rio_buf));
        if (rc < 0) {
            if (errno != EINTR) return -1;
        } else if (rc == 0) {
            return 0;                          /* EOF */
        } else {
            rp->rio_cnt = rc;
            rp->rio_bufptr = rp->rio_buf;
        }
    }
    size_t cnt = (size_t)rp->rio_cnt < n ? (size_t)rp->rio_cnt : n;
    memcpy(usrbuf, rp->rio_bufptr, cnt);
    rp->rio_bufptr += cnt;
    rp->rio_cnt -= (ssize_t)cnt;
    return (ssize_t)cnt;
}

static ssize_t rio_readlineb(rio_t *rp, char *usrbuf, size_t maxlen)
{
    size_t i = 0;
    char c;
    if (maxlen == 0) return -1;
    while (i + 1 < maxlen) {                   /* 给结尾 \0 留位置 */
        ssize_t rc = rio_read(rp, &c, 1);
        if (rc == 0 && i == 0) return 0;       /* 一行都没读到就 EOF */
        if (rc <= 0) break;
        usrbuf[i++] = c;
        if (c == '\n') break;
    }
    usrbuf[i] = '\0';
    return (ssize_t)i;                         /* 返回实际存放的字节数 */
}

int main(int argc, char **argv)
{
    int lines = 0;
    if (argc > 1 && strcmp(argv[1], "-c") == 0) {
        char c;
        while (read(0, &c, 1) == 1)
            if (c == '\n') lines++;
        printf("raw lines=%d\n", lines);
        return 0;
    }

    rio_t rp;
    char line[128];
    rio_readinitb(&rp, 0);
    while (rio_readlineb(&rp, line, sizeof line) > 0)
        lines++;
    printf("rio lines=%d\n", lines);
    return 0;
}
```

用 100 行的文件对照系统调用次数（只数 `read`，`grep -c` 数行）：

```bash
seq 1 100 > /tmp/lab1c10_lines.txt
strace -e trace=read ./rio_line     < /tmp/lab1c10_lines.txt 2>&1 | grep -c '^read('   # 3
strace -e trace=read ./rio_line -c  < /tmp/lab1c10_lines.txt 2>&1 | grep -c '^read('   # 294
```

实测 3 与 294。缓冲版的三次是：动态链接器读 ELF 头一次、`read(0, buf, 8192)` 一次读进 292 字节、末尾 EOF 一次。逐字节版是 292 次单字节 `read`、1 次 EOF，再加动态链接器那 1 次。

三个不变量值得记住：

- `rio_read` 只在缓冲区空时进内核，一次要 8 KiB；返回给调用者的字节数可以小于请求。
- `rio_readlineb` 的 `maxlen` 包含结尾 `\0`，所以最多存 `maxlen - 1` 个字符；行太长就截断，靠「最后一个字符是不是 `\n`」判断还有没有剩余。
- `EINTR` 重试、EOF 返回 0、其它错误返回 -1；`rio_writen` 对 `write` 返回 0 的情况设 `EIO`，避免死循环。

::: ex 例 1.10.4 · 先猜三次 `readlineb` 各返回多少 {#ex-1.10.4}
输入是一行 20 个字符加换行（共 21 字节），`maxlen = 8`。连续调用三次 `rio_readlineb`，每次返回多少？哪一次的最后是 `\n`？

::: sol 解答
实测三次都返回 7，名字分别是 `0123456`、`789ABCD`、`EFGHIJ` + 换行；第三次的最后一个字符是 `\n`。因为 `maxlen - 1 = 7`，每次最多存 7 个字符，第 8 个位置留给 `\0`。这也说明「返回 7」不等于「读到了完整一行」，调用者要自己看末尾有没有换行，决定是拼接还是丢弃。
:::
:::

::: errata RIO 的六个坑
1. **「`EINTR` 就是读失败」**——这次读没取走任何字节，原样重试即可。实测返回 -1/`Interrupted system call`，重试后读到 2 字节。
2. **「返回值小于请求就是 EOF」**——短读可能只是「暂时只有这么多」。实测 `rio_readn(64)` 从 5 字节的管道返回 5，那是 EOF；而管道里持续有数据时也可能先返回一部分。判断 EOF 只看某次 `read` 是否返回 0。
3. **「短写说明出错了」**——实测 `write(200000)` 返回 65536，`errno` 仍是 `Success`。错误要看 -1，不是看「没写满」。
4. **「带缓冲读过之后还能直接 `read(fd)`」**——缓冲区里可能还压着数据，直接 `read` 会跳过它们。同一 fd 只能用一层：要么全用 `rio_*`，要么全用裸 `read`。
5. **「`readlineb` 返回 n 就是读了 n 个字符的一整行」**——`maxlen` 含 `\0`，超长行会被截断；要靠末尾有没有 `\n` 判断。
6. **「RIO 等于 stdio」**——RIO 没有全局锁，也没有 `fork` 后自动清缓冲的机制；`fork` 出来的子进程会连带复制未读数据，父子各读一份。要并发就用每线程自己的 `rio_t`。
:::

### 1.10.4 小结

① `read`/`write` 的三种不完整结果——`EINTR`、短读、短写——都要用循环收尾，`read` 返回 0 才是 EOF；② 无缓冲的 `rio_readn`/`rio_writen` 负责「补足」，带缓冲的 `rio_read`/`rio_readlineb` 负责「少进内核」，实测 294 次降到 3 次；③ 缓冲层和裸 fd 不能混用，`readlineb` 的 `maxlen` 含结尾 `\0`。如果只记住一件事，那就是：**系统调用只保证「做了一部分」，完整性要你自己的循环来保证。**

## 1.10.5 共享文件、dup2 与重定向 {#sec-1.10.5}

这一节回答：两个 fd 什么时候共享文件偏移？`dup2` 具体改了什么？为什么 `cmd >out 2>&1` 与 `cmd 2>&1 >out` 的输出去向不同？

::: preview 先抓住一件事
fd 表项本身不保存偏移；真正记录偏移和状态标志的是**打开文件描述**（open file description）。`open` 每次都新建一个描述；`dup`/`dup2` 让两个 fd 指向同一个描述；`fork` 复制 fd 表，但保留里面的指针。于是共享描述的 fd 共享偏移、共享 `O_APPEND`。重定向就是「`open` 目标文件，`dup2` 到 0/1/2，再关掉临时 fd」。
:::

fd → 打开文件描述 → inode 的三层结构在 [2.2.1](../part2/ch02.md#sec-2.2.1) 已有完整图；这里只取两个直接后果：偏移共享，以及 `dup2` 换目标。

### 场景：一次 fork、两次 open、一次 dup2

先猜三件事：`fork` 后子进程把偏移挪到 2、写 5 字节，父进程看到的偏移是多少？两个独立的 `open` 各写 3 字节，谁的内容留下？`dup2(fd, 1)` 之后向 fd 1 写 2 字节，`lseek(fd)` 会前进吗？

```c
/* lab1c10_shared.c：共享偏移、独立偏移与 dup2 */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static void wr(int fd, const char *s)
{
    size_t n = strlen(s);
    if (write(fd, s, n) != (ssize_t)n) perror("write");
}

int main(void)
{
    const char *p = "/tmp/lab1c10_shared.txt";
    int fd = open(p, O_RDWR | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("open"); return 1; }

    wr(fd, "0123456789");
    printf("A write 10 -> pos=%lld\n", (long long)lseek(fd, 0, SEEK_CUR));

    pid_t pid = fork();
    if (pid == 0) {
        lseek(fd, 2, SEEK_SET);
        wr(fd, "CHILD");
        _exit(0);
    }
    waitpid(pid, NULL, 0);
    printf("B parent after child -> pos=%lld\n",
           (long long)lseek(fd, 0, SEEK_CUR));

    int a = open(p, O_WRONLY);
    int b = open(p, O_WRONLY);
    lseek(a, 0, SEEK_SET);
    lseek(b, 0, SEEK_SET);
    wr(a, "AAA");
    printf("C after a writes: a=%lld b=%lld\n",
           (long long)lseek(a, 0, SEEK_CUR), (long long)lseek(b, 0, SEEK_CUR));
    wr(b, "BBB");

    char buf[64] = {0};
    int r = open(p, O_RDONLY);
    if (r < 0) return 1;
    ssize_t n = read(r, buf, sizeof buf - 1);
    close(r);
    printf("D content=%s (%zd bytes)\n", buf, n);

    fflush(stdout);                    /* 缓冲区先清空，免得写进下面的文件 */
    int d = open(p, O_RDWR);
    int saved = dup(STDOUT_FILENO);
    if (d < 0 || saved < 0) { perror("open/dup"); return 1; }
    if (dup2(d, STDOUT_FILENO) < 0) { perror("dup2"); return 1; }
    wr(STDOUT_FILENO, "ZZ");
    long long pos = (long long)lseek(d, 0, SEEK_CUR);
    int fl = fcntl(d, F_GETFL);
    if (fcntl(d, F_SETFL, fl | O_APPEND) == -1) perror("F_SETFL");
    int seen = fcntl(STDOUT_FILENO, F_GETFL);
    if (dup2(saved, STDOUT_FILENO) < 0) perror("dup2 restore");
    close(saved);
    printf("E write via fd1 -> pos(d)=%lld, O_APPEND on fd1=%d\n",
           pos, (seen & O_APPEND) != 0);
    printf("F dup2(d,d)=%d\n", dup2(d, d));

    close(d); close(a); close(b); close(fd);
    return 0;
}
```

Ubuntu 24.04.5 aarch64（gcc 13.3，`cc -std=c17 -O2`）实测：

```text
A write 10 -> pos=10
B parent after child -> pos=7
C after a writes: a=3 b=0
D content=BBBHILD789 (10 bytes)
E write via fd1 -> pos(d)=2, O_APPEND on fd1=1
F dup2(d,d)=6
```

六行输出可以读出五件事：

- A→B：父进程写 10 字节后偏移在 10；子进程 `lseek` 到 2 再写 5 字节，偏移到 7；父进程随后读到的也是 7。`fork` 复制的是 fd 表，表项仍指向同一个打开文件描述。
- C：两个独立 `open` 各有各的偏移。a 写了 3 字节，偏移是 3；b 一次都没写，偏移仍是 0。
- D：b 从 0 开始写 `BBB`，把 a 的 `AAA` 覆盖掉；原内容里的 `CHILD` 只剩 `HILD`。这是「独立打开 + 都从 0 写」的典型覆盖。
- E：`dup2(d, 1)` 后，fd 1 与 d 指向同一个描述。向 fd 1 写 2 字节，`lseek(d)` 得到 2；通过 d 设上的 `O_APPEND`，在 fd 1 上也能读到。偏移和状态标志都共享。
- F：`dup2(d, d)` 不关闭也不复制，直接返回 d 本身（这次 d 是 6 号）。

::: def 定义 1.10.5 · 重定向（redirection） {#def-1.10.5}
重定向是在不改程序代码的前提下，把某个标准 fd（0/1/2）改指向另一个打开文件描述。实现步骤是 `open` 目标、`dup2` 到目标 fd、`close` 临时 fd；shell 的 `>`、`<`、`2>&1` 是它的语法。重定向只换 fd 表项指向的对象，不复制数据，也不改变已打开描述里的偏移。
:::

### `dup2` 的边界与恢复现场

`dup2(oldfd, newfd)` 做两件事：如果 `newfd` 已经打开，先把它关掉；然后让 `newfd` 指向 `oldfd` 的打开文件描述。关闭与复制在内核里是一步完成的，中间没有「newfd 暂时空着」的窗口。返回值就是 `newfd`；`oldfd` 无效或 `newfd` 越界时返回 -1，`errno` 为 `EBADF`。`oldfd == newfd` 时直接返回，不关闭也不改标志。

重定向的完整套路是「保存、切换、写完、刷新、恢复」（片段，省略了外层函数与头文件）：

```text
int saved = dup(STDOUT_FILENO);          /* 先留一条回终端的路 */
int fd = open(path, O_WRONLY | O_CREAT | O_TRUNC, 0644);
if (saved == -1 || fd == -1) { perror("dup/open"); return 1; }

dup2(fd, STDOUT_FILENO);                 /* 1 号改指向文件 */
close(fd);                               /* fd 1 仍持有描述，可以关 */
printf("this line goes to the file\n");
fflush(stdout);                          /* 切回之前必须刷 */

dup2(saved, STDOUT_FILENO);              /* 1 号回到终端 */
close(saved);
printf("this line goes to the terminal\n");
```

`fflush` 不是可有可无的礼貌。`stdout` 的缓冲区属于 `FILE *`，不属于 fd 1。`dup2` 只换了 fd 1 指向的对象，缓冲区里还没交出去的字节，会在下一次刷新时写进**新的**目标。切换前不刷，旧目标的数据会漏进文件；恢复前不刷，文件的数据会漏回终端。上面的程序在 `dup2(d, 1)` 之前也刷了一次，就是为了不让终端上已经打印的 A–D 行跟着进文件。

### shell 的重定向：从左到右复制「当前值」

`>`、`2>&1` 不是特殊语法，而是 shell 在 `fork` 之后、`exec` 之前做的 `open` + `dup2`。关键在于 shell **从左到右**处理重定向，`2>&1` 复制的是此刻 fd 1 指向的对象，不是「以后 fd 1 去哪，fd 2 就跟到哪」。

用一个只打印两行的小程序验证：

```c
/* lab1c10_redir.c */
#include <stdio.h>
int main(void)
{
    printf("stdout line\n");
    fprintf(stderr, "stderr line\n");
    return 0;
}
```

```bash
./lab1c10_redir > o1 2>&1
sh -c './lab1c10_redir 2>&1 > o2' > t2 2>&1
```

实测（Ubuntu 24.04.5）：

```text
== o1 ==
stderr line
stdout line
== o2 ==
stdout line
== t2 ==
stderr line
```

- `> o1 2>&1`：先把 fd 1 指向 `o1`，再让 fd 2 复制 fd 1，两者都进 `o1`。
- `2>&1 > o2`：先让 fd 2 复制**当时**的 fd 1（终端），再把 fd 1 改指 `o2`。结果 stderr 留在终端（被外层 `sh` 收进 `t2`），stdout 进 `o2`。
- `o1` 里 `stderr line` 反而排在 `stdout line` 前面。程序明明是先 `printf` 后 `fprintf`，但 stdout 重定向到文件后变成全缓冲，直到退出才刷新；stderr 默认无缓冲，立刻写出。重定向不但换目标，还会改变 stdio 的缓冲模式，下一节会拆开这条路径。

要观察某个 fd 此刻指向谁，可以读 `/proc/self/fd/1` 这个符号链接；`ls -l /proc/self/fd` 也能看到整张表。细节留到 1.10.10，这里先记住：重定向留下的痕迹就在 fd 表里。

::: ex 例 1.10.5 · 先猜三次操作后的偏移 {#ex-1.10.5}
父进程打开文件并写 10 字节。第一步，`fork` 后子进程 `lseek(fd, 2, SEEK_SET)` 写 5 字节，父进程的偏移是多少？第二步，父进程另开一个 fd 写 3 字节，两个 fd 的偏移各是多少？第三步，`dup2(fd, 1)` 后向 fd 1 写 2 字节，`lseek(fd)` 是多少？

::: sol 解答
实测依次是 7、3 与 0、2。`fork` 共享打开文件描述，子进程的写入推进了父进程看到的偏移；另开的 fd 有自己的描述，父进程写 3 字节只把自己的偏移推到 3，新 fd 仍在 0；`dup2` 让 fd 1 与 fd 共享描述，写 2 字节后 `lseek(fd)` 是 2。偏移属于描述，不属于 fd 号。
:::
:::

::: errata 共享与重定向的六个误解
1. **「`dup2` 会复制一份偏移」**——不复制，两个 fd 共享同一个偏移。实测通过 fd 1 写 2 字节，`lseek(d)` 立刻变成 2。
2. **「`fork` 后父子写同一文件一定互相覆盖」**——继承来的 fd 共享偏移，子进程写到哪里，父进程的偏移就跟到哪里；只有各自 `open` 才会各从 0 开始、互相覆盖。
3. **「`dup2(fd, fd)` 会先关闭再复制」**——相同时是空操作，直接返回 `fd`，描述和标志都不动。
4. **「`close(fd)` 之后 fd 1 也不能用了」**——`close` 只减引用计数；fd 1 还指着同一个描述，读写与偏移都照常。
5. **「`>out 2>&1` 与 `2>&1 >out` 等价」**——前者两者进文件，后者只有 stdout 进文件。实测后者 stderr 仍在终端。
6. **「重定向后 `printf` 立刻进文件」**——stdio 有自己的缓冲区；不 `fflush` 就切换，数据会写进错误的目标，文件里的行序也可能与代码顺序不同。
:::

### 1.10.5 小结

① fd 表项指向打开文件描述，`open` 新建描述，`dup`/`dup2`/`fork` 共享描述，所以偏移与状态标志跟着描述走；② `dup2` 原子地关闭 `newfd` 再复制，重定向就是 `open` + `dup2` + `close`，恢复现场还要 `dup` 一次；③ shell 从左到右处理重定向，`2>&1` 复制的是当前值，stdio 缓冲还会改变文件里的行序。如果只记住一件事，那就是：**共享的是描述，不是 fd 号；换目标之前先 `fflush`。**

## 1.10.6 I/O 路径：从 write 到磁盘 {#sec-1.10.6}

这一节回答：`write` 返回成功时，数据到底在哪一层？为什么刚写完的文件立刻能读，拔掉电源却可能丢？

::: preview 先抓住一件事
一次写要穿过三层：**用户态缓冲**（stdio/RIO）→ **内核 page cache** → **块层与设备**。`write` 通常只走到第二层：数据被拷进 page cache，页被标成脏，函数就返回；真正的下盘由回写线程稍后做。`fsync`/`fdatasync` 才是「等到落盘」的接口。`read` 命中 page cache 时完全不进块层。`close` 只归还 fd，不负责刷盘。
:::

{{#include ../assets/figures/io-path.md}}

读图只看两条线：实线是写路径，`write()` 把数据拷进 page cache 就返回，脏页由回写线程择机交给块层；虚线是读路径，命中 page cache 就根本不经过块层。图里的「持久介质」才是掉电后仍然存在的那一层。

### 场景一：`_exit` 一调用，12 字节全没了

先猜：用 `fprintf` 往文件写 12 字节，然后调用 `_exit(0)`，文件里有多少字节？

```c
/* lab1c10_stdio.c：同样的 fprintf，三种退出方式 */
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int main(int argc, char **argv)
{
    FILE *f = fopen("/tmp/lab1c10_stdio.out", "w");
    if (f == NULL) return 1;
    setvbuf(f, NULL, _IOFBF, 4096);        /* 强制全缓冲，便于观察 */
    fprintf(f, "hello stdio\n");

    if (argc > 1 && strcmp(argv[1], "exit") == 0)
        _exit(0);                          /* 不刷新用户态缓冲 */
    if (argc > 1 && strcmp(argv[1], "flush") == 0) {
        fflush(f);
        _exit(0);
    }
    return 0;                              /* 正常退出：fclose 刷新 */
}
```

```bash
cc -std=c17 -O2 -o lab1c10_stdio lab1c10_stdio.c
for m in normal exit flush; do
    ./lab1c10_stdio $m
    printf '%-7s %s bytes\n' "$m" "$(stat -c %s /tmp/lab1c10_stdio.out)"
done
strace -e trace=write ./lab1c10_stdio normal 2>&1 | grep '^write(3'
```

Ubuntu 24.04.5 实测：

```text
normal  12 bytes
exit    0 bytes
flush   12 bytes
write(3, "hello stdio\n", 12)           = 12
```

三行文件大小说明三层里的第一层：`fprintf` 只把 12 字节放进 `FILE` 的缓冲区，还没进内核。正常 `return` 会走 `exit`，由它刷新所有打开的流；`fflush` 手动刷新；`_exit` 直接结束进程，缓冲区随进程消失。strace 那一行是刷新时唯一的一次 `write(3, ...)`，数据这才从用户缓冲区进入 page cache。

### 场景二：`write` 返回了，脏页还在内存里

第二层是 page cache。下面这个程序写 16 MiB，然后从 `/proc/meminfo` 读 `Dirty`（待回写的脏页字节数），再 `fsync` 一次，看它怎么变：

```c
/* lab1c10_dirty.c：write 之后的 Dirty、st_blocks 与 fsync */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <time.h>
#include <unistd.h>

static long meminfo_kb(const char *key)
{
    FILE *f = fopen("/proc/meminfo", "r");
    char line[160];
    long v = -1;
    size_t klen = strlen(key);
    if (f == NULL) return -1;
    while (fgets(line, sizeof line, f) != NULL) {
        if (strncmp(line, key, klen) == 0 && line[klen] == ':') {
            if (sscanf(line + klen + 1, " %ld", &v) != 1) v = -1;
            break;
        }
    }
    fclose(f);
    return v;
}

static double now_ms(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec * 1e3 + (double)ts.tv_nsec / 1e6;
}

int main(void)
{
    const char *p = "/tmp/lab1c10_dirty.bin";
    size_t n = 16u << 20;
    char *buf = malloc(n);
    if (buf == NULL) return 1;
    memset(buf, 'x', n);

    printf("Dirty before      = %ld kB\n", meminfo_kb("Dirty"));
    int fd = open(p, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) return 1;

    double t0 = now_ms();
    ssize_t w = write(fd, buf, n);
    double t1 = now_ms();
    if (w != (ssize_t)n) { fprintf(stderr, "short write: %zd\n", w); return 1; }
    printf("write(%zu)       = %zd, %.1f ms\n", n, w, t1 - t0);
    printf("Dirty after write = %ld kB\n", meminfo_kb("Dirty"));

    struct stat st;
    if (fstat(fd, &st) == 0)
        printf("st_size=%lld st_blocks=%lld\n",
               (long long)st.st_size, (long long)st.st_blocks);

    int r = open(p, O_RDONLY);
    if (r < 0) return 1;
    char b[8] = {0};
    ssize_t rn = read(r, b, sizeof b);
    close(r);
    printf("read before fsync = %zd bytes, first=%c\n", rn, b[0]);

    double t2 = now_ms();
    if (fsync(fd) == -1) perror("fsync");
    double t3 = now_ms();
    printf("fsync             = %.1f ms\n", t3 - t2);
    printf("Dirty after fsync = %ld kB\n", meminfo_kb("Dirty"));

    close(fd);
    unlink(p);
    free(buf);
    return 0;
}
```

Ubuntu 24.04.5 实测（`Dirty` 的绝对值随后台负载变化，看增量）：

```text
Dirty before      = 10400 kB
write(16777216)       = 16777216, 3.9 ms
Dirty after write = 26784 kB
st_size=16777216 st_blocks=32768
read before fsync = 8 bytes, first=x
fsync             = 1.8 ms
Dirty after fsync = 10400 kB
```

读这六行要抓住三件事：

- `Dirty` 从 10400 涨到 26784，增量正好 16384 kB，也就是 16 MiB。`write` 返回时，这 16 MiB 是内核里的脏页，不在磁盘上。写只花了 3.9 ms，这个量级更像内存带宽，而不是在等设备。
- `st_blocks=32768` 说明 32768 个 512 字节块已经分配给这个文件。分配的是块的位置，不等于块里的数据已经落到持久介质；这两件事由文件系统的元数据和 page cache 的脏状态分别记录。
- `read` 在 `fsync` 之前就能读回 8 字节，因为读命中了同一批 page cache。`fsync` 之后 `Dirty` 回到 10400，表示这 16 MiB 已经交给设备并完成回写。能读回、块已分配，都不能单独证明「已落盘」；只有 `fsync` 返回才给了这个保证（前提是设备对 flush 请求诚实）。

::: def 定义 1.10.6 · page cache、脏页与回写 {#def-1.10.6}
page cache（页缓存）是内核用内存缓存文件内容的区域，以页（常见 4 KiB）为单位，按 inode 的 `address_space` 组织。`write` 把用户数据拷进对应的页，并把页标成**脏页**（dirty page）；回写（writeback）线程稍后把脏页交给块层。`fsync`/`fdatasync` 等这个文件的脏页与必要元数据真正写完。缓存页可以回收：干净的页直接丢弃，脏页要先回写。
:::

把常见操作按「数据最远到哪一层」排一张表：

| 操作 | 数据最远到哪 | 掉电会丢吗 |
|:--|:--|:--|
| `printf`/`fprintf` | stdio 用户缓冲区 | 会，可能连内核都没进 |
| `write` | page cache（脏页） | 会，除非已经回写 |
| `mmap` 写 | page cache（脏页） | 会，除非 `msync` |
| `fsync(fd)` | 文件数据 + 元数据到设备 | 通常不会（设备需支持 flush） |
| `fdatasync(fd)` | 数据 + 取回数据所需的元数据 | 通常不会，通常比 `fsync` 少写元数据 |
| `O_SYNC` 写 | 每次 `write` 都等到设备 | 不会，代价大 |
| `O_DIRECT` | 绕过 page cache，直接到设备 | 取决于设备缓存 |
| `close(fd)` | 只释放 fd | 不保证任何落盘 |

所以「`write` 成功」只说明数据进了 page cache。数据库提交、配置发布、日志落盘这类场景，必须显式同步。一个常被写错的原子替换顺序是（片段，`write_all` 是「写满」的辅助函数）：

```text
int fd = open("config.tmp", O_WRONLY | O_CREAT | O_TRUNC, 0644);
write_all(fd, data, len);
fsync(fd);                         /* 先把临时文件的数据刷到设备 */
close(fd);
rename("config.tmp", "config");    /* 目录项原子替换 */
int dfd = open(".", O_RDONLY | O_DIRECTORY);
fsync(dfd);                        /* 再让 rename 这个目录项持久 */
close(dfd);
```

只 `fsync` 文件不够。`rename` 改的是目录项，目录也是文件；目录 fd 的 `fsync` 才把「名字指向新 inode」这件事写下去。少了最后一步，掉电后可能看到旧名字、新名字，甚至临时文件还在，但不会看到写了一半的 `config`。

### stdio 的三种缓冲

`FILE *` 在 fd 之上又加了一层用户态缓冲。它什么时候把数据交给内核，由模式决定：

| 模式 | 何时刷新 | 典型场景 |
|:--|:--|:--|
| `_IOFBF` 全缓冲 | 缓冲区满、`fflush`、`fclose` | 重定向到文件 |
| `_IOLBF` 行缓冲 | 遇到 `\n`、缓冲区满、`fflush` | 终端 |
| `_IONBF` 无缓冲 | 每次调用都写 | `stderr` |

stdout 连终端时默认行缓冲，重定向到文件时默认全缓冲；stderr 默认无缓冲。这解释了 1.10.5 里 `o1` 的行序：`stderr line` 立刻写出，`stdout line` 攒到退出才写，于是文件里顺序颠倒。

`fork` 后子进程会复制父进程的 stdio 缓冲区。父子都走 `exit` 时，同一批字节被刷新两次，输出重复。子进程用 `_exit`，或者在 `fork` 前 `fflush(NULL)`。

混用 stdio 和 fd 还有预读问题：`fgets` 可能已经让 stdio 从内核多读了 4 KiB，fd 的偏移跑到缓冲区末尾之后；此时直接 `read(fd, ...)` 会跳过 stdio 还没交出的数据。要么全程用 stdio，要么全程用 fd；必须混用时，先 `fflush`（写方向）或 `fseek`（读方向）对齐。

::: ex 例 1.10.6 · 先猜掉电后文件里有什么 {#ex-1.10.6}
程序 `write(fd, buf, 16 MiB)` 返回 16777216，紧接着机器断电。先猜三件事：文件大小为多少？内容读出来是什么？`stat` 里的 `st_blocks` 能证明数据已经在磁盘上吗？如果 `write` 之后调用过 `fsync`，答案会变吗？

::: sol 解答
实测 `write` 返回后 `Dirty` 增加 16384 kB，`st_size=16777216`、`st_blocks=32768`，`read` 也能读回内容。但这些都是 page cache 里的事实：`st_blocks` 只说明块已分配，`read` 只说明缓存命中，断电后尚未回写的数据会丢。`fsync` 返回后 `Dirty` 回到基线，这时数据与元数据已经交给设备；只要设备对 flush 诚实，文件就是完整的新内容。没有 `fsync` 时，文件可能长度已变、内容却是旧块或空洞，取决于回写进度。
:::
:::

::: errata 关于「写成功」的六个误解
1. **「`write` 返回请求长度就是落盘了」**——只代表数据进了 page cache，页还是脏的；落盘要 `fsync`/`fdatasync`。
2. **「`close` 会顺带刷盘」**——`close` 只减引用、释放 fd；脏页仍留在 page cache，由回写线程处理。
3. **「`st_blocks` 分配了、`read` 能读回，就证明在磁盘上」**——分配和读回都发生在缓存层。实测写 16 MiB 后立刻能读，`Dirty` 还多着 16384 kB。
4. **「`rename` 返回就完成了原子替换」**——目录项替换在内存里完成；要抗掉电，`rename` 之后还要 `fsync` 父目录。
5. **「`fsync` 与 `fdatasync` 完全一样」**——`fdatasync` 只同步数据和取回数据所需的元数据，可能省掉 `mtime` 等无关项；文件大小变化时两者仍可能都要写 inode。
6. **「`_exit` 和 `exit` 一样会刷新 stdio」**——`_exit` 不跑 `atexit`、不刷 `FILE` 缓冲区；实测同样的 `fprintf`，`_exit` 留下 0 字节，正常退出留下 12 字节。
:::

### 1.10.6 小结

① 写路径分三层：stdio 用户缓冲、page cache、块层与设备；`write` 只保证数据进了第二层，`fsync`/`fdatasync` 才等到第三层；② 读命中 page cache 时不进块层，能读回不等于在磁盘上；③ `close` 不刷盘，`rename` 之后还要 `fsync` 目录；stdio 的三种缓冲会改变数据进入内核的时机。如果只记住一件事，那就是：**`write` 成功只说明「内核收下了」，持久化要另外发命令。**

::: method 即时自测 · 1.10.6
**Q1（记忆）** 写路径的三层各叫什么？`write` 正常返回时，数据最远到了哪一层？

**Q2（辨析）** `fsync`、`fdatasync`、`O_SYNC` 三者在「何时等设备」上有什么差别？

**Q3（应用）** 用「临时文件 + `rename`」发布配置，写出完整的持久化顺序，并说明每一步防的是什么。

**Q4（迁移）** 一个程序用 `printf` 打日志，重定向到文件后最后几行总是丢；换成 `fprintf(stderr, ...)` 就好了。两种解释各是什么？

::: sol 答案
**A1** 用户态缓冲（stdio/RIO）、page cache、块层与设备。`write` 返回时数据在 page cache，页是脏的。
**A2** `fsync` 等该文件的数据与全部元数据；`fdatasync` 只等数据与取回数据所需的元数据，通常少一次元数据写；`O_SYNC` 让每次 `write` 都等到设备，最慢但每次写都有持久化语义。
**A3** 写 `config.tmp` → `fsync(config.tmp)`（防数据没下盘）→ `close` → `rename` 到 `config`（原子换名）→ `fsync` 目录 fd（防改名没下盘）。少了目录同步，掉电后可能回到旧名字。
**A4** stdout 重定向到文件后是全缓冲，程序 `_exit`、崩溃或没 `fflush` 时缓冲区丢失；stderr 默认无缓冲，每次调用都直接 `write`。也可能是 stdout 的缓冲在 `fork` 后被父子各刷一次，但「丢最后几行」更像没刷新。
:::
:::

## 1.10.7 该用哪个 I/O 接口 {#sec-1.10.7}

这一节回答：同样是把数据搬进搬出，为什么有时该用 stdio，有时该用裸 fd，有时该用 mmap、`epoll`（事件通知接口：一次等待一批 fd 谁就绪）甚至 `io_uring`（异步 I/O 接口：请求放进共享队列，由内核完成后再通知）？

::: preview 先抓住一件事
选接口看三笔成本：**系统调用次数**（用户态/内核态切换）、**数据拷贝次数**（用户缓冲 ↔ page cache ↔ 设备）、**等待方式**（阻塞、非阻塞、异步）。stdio 用缓冲换系统调用，mmap 用缺页（page fault：访问还没装进内存的页时，内核把它补上）换 `read`，零拷贝（zero-copy：省掉内核态与用户态之间那次拷贝）用内核内搬运换用户态拷贝。没有全能接口，只有和场景匹配的取舍。
:::

### 场景：1000 行日志与 4 MiB 顺序读

先猜两组数字：用 `printf` 和用 `write` 各输出 1000 行日志，各产生多少次 `write` 系统调用？顺序读一个 4 MiB 文件，`read` 循环和 `mmap` 各产生多少次 `read`？

```c
/* lab1c10_iface.c：同一任务，四种接口 */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/stat.h>
#include <unistd.h>

static unsigned long sum_fd(int fd)
{
    unsigned char buf[65536];
    unsigned long sum = 0;
    ssize_t n;
    while ((n = read(fd, buf, sizeof buf)) > 0)
        for (ssize_t i = 0; i < n; i++) sum += buf[i];
    return sum;
}

static unsigned long sum_mmap(const char *p)
{
    int fd = open(p, O_RDONLY);
    struct stat st;
    if (fd < 0 || fstat(fd, &st) == -1) return 0;
    unsigned char *m = mmap(NULL, (size_t)st.st_size, PROT_READ,
                            MAP_PRIVATE, fd, 0);
    unsigned long sum = 0;
    if (m == MAP_FAILED) return 0;
    for (off_t i = 0; i < st.st_size; i++) sum += m[i];
    munmap(m, (size_t)st.st_size);
    close(fd);
    return sum;
}

int main(int argc, char **argv)
{
    if (argc < 2) return 1;
    if (strcmp(argv[1], "stdio") == 0) {
        for (int i = 0; i < 1000; i++)
            printf("line %04d\n", i);
    } else if (strcmp(argv[1], "raw") == 0) {
        char line[32];
        for (int i = 0; i < 1000; i++) {
            int n = snprintf(line, sizeof line, "line %04d\n", i);
            if (write(1, line, (size_t)n) != n) return 1;
        }
    } else if (strcmp(argv[1], "read") == 0 && argc > 2) {
        int fd = open(argv[2], O_RDONLY);
        if (fd < 0) return 1;
        printf("sum=%lu\n", sum_fd(fd));
        close(fd);
    } else if (strcmp(argv[1], "mmap") == 0 && argc > 2) {
        printf("sum=%lu\n", sum_mmap(argv[2]));
    }
    return 0;
}
```

Ubuntu 24.04.5 实测（只摘 `strace -c` 的 calls 列）：

| 任务 | 接口 | 系统调用次数 | 说明 |
|:--|:--|--:|:--|
| 1000 行日志 | `printf` | 3 次 `write` | stdio 攒满 4 KiB 再写 |
| 1000 行日志 | `write` | 1000 次 `write` | 每行一次系统调用 |
| 4 MiB 顺序读 | `read` 循环 | 66 次 `read` | 1 次 ELF 头 + 64 次 64 KiB + 1 次 EOF |
| 4 MiB 顺序读 | `mmap` | 1 次 `read` | 只有 ELF 头；数据靠缺页 |

两边算出的校验和相同，说明结果一样，差别只在路径。`printf` 的 3 次来自 10 000 字节除以 4 KiB 缓冲区；`write` 版每行 10 字节也发一次调用，次数跟着行数走。`read` 版的 66 次全是 fd 3：1 次动态链接器读 ELF 头，64 次各搬 64 KiB，最后 1 次返回 0 表示 EOF。`mmap` 版程序自己一次 `read` 都没调，页由缺页按需装进地址空间。

### 三笔成本怎么算

- **系统调用**：一次调用要切换特权级、保存现场。1000 行小日志用 `write` 是 1000 次切换，用 stdio 是 3 次；行越短、量越大，缓冲越值。
- **拷贝**：`write` 把用户缓冲区拷进 page cache 一次；stdio 先拷进 `FILE` 缓冲，再拷进 page cache，多一次内存拷贝。`mmap` 把文件页直接映射进地址空间，用户代码读页，省掉 `read` 的显式拷贝，但每次缺页都要进内核。
- **等待**：阻塞接口让线程睡到数据就绪；非阻塞接口立刻返回 `EAGAIN`，由 `epoll` 通知；`io_uring` 把请求放进共享队列，由内核异步完成。等待方式决定了「一个线程能管多少连接」。

::: def 定义 1.10.7 · I/O 接口的成本模型 {#def-1.10.7}
比较 I/O 接口时看三项：系统调用次数、数据拷贝次数、等待方式。缓冲（stdio、RIO）减少系统调用但增加一次用户态拷贝；`mmap` 减少显式拷贝但增加缺页；零拷贝（`sendfile`、`splice`、`copy_file_range`）省掉用户态那一段，内核内仍要搬运。三项都为零的接口不存在，选型就是决定哪一项可以接受。
:::

把常见需求放回这张表：

| 需求 | 首选 | 理由与边界 |
|:--|:--|:--|
| 读元数据、目录、设备控制 | 裸 fd（`stat`/`ioctl`/`readdir`） | stdio 不覆盖这些语义 |
| 格式化文本输入输出 | stdio（`printf`/`fscanf`） | 缓冲与格式化成熟；别拿它写 socket |
| 网络/管道上可靠读写 | RIO 或手写循环 | 必须处理短读短写与 `EINTR` |
| 大文件随机访问、多进程共享 | `mmap` | 省拷贝、按页缺页；截断会触发 `SIGBUS` |
| 大量并发连接 | `epoll` + 非阻塞 fd | 一个线程管很多连接；代码复杂度上升 |
| 极高 IOPS（每秒 I/O 次数）、批量提交 | `io_uring` | 减少系统调用；内核 5.1+，容器里可能被 seccomp（系统调用过滤）限制 |
| 必须落盘的日志 | `write` + `fsync`/`fdatasync` | 明确持久化边界；每次同步都等设备 |
| 大块文件到文件/socket | `sendfile`/`copy_file_range`/`splice` | 省用户态拷贝；跨文件系统或对端类型有限制 |

### 四个常见反例

**用 stdio 写 socket。** `fprintf(sockfp, ...)` 可能先攒在 `FILE` 缓冲里，可能只写出一部分，错误还藏在 `FILE` 状态里，要等 `fflush` 或 `ferror` 才发现。网络代码要么用 `send` 循环，要么用 1.10.4 的 RIO，明确处理短写和 `EINTR`。

**以为 mmap 一定更快。** 顺序扫一遍 4 MiB，`mmap` 省掉 65 次 `read`，却要处理几十次缺页；文件被别的进程 `truncate` 后继续访问会收到 `SIGBUS`。它适合反复随机访问、多进程共享只读数据，不适合「读一遍就扔」的小文件。

**把 O_DIRECT 当性能开关。** 它绕过 page cache，要求缓冲区地址、长度、偏移都按块对齐；不对齐直接 `EINVAL`，对齐了也可能因为失去预读与合并而更慢。数据库自管缓存时才有意义。

**为了少一次拷贝上 io_uring（异步 I/O 接口）。** 它把提交与完成放进共享内存环，适合高并发批量 I/O；但编程模型、错误处理和容器兼容性都更复杂。普通文件顺序读写用不上它。

::: ex 例 1.10.7 · 先猜换小缓冲区后的系统调用次数 {#ex-1.10.7}
1000 行 `line 0000` 到 `line 0999` 一共 10 000 字节。4 KiB 缓冲的 `printf` 产生 3 次 `write`；把 stdout 的缓冲区改成 1 KiB，会产生几次？改成无缓冲呢？

::: sol 解答
实测 1 KiB 缓冲是 10 次：10 000 字节按 1 KiB 切，前 9 次各装满 1024 字节，最后一次 784 字节。无缓冲时（`_IONBF`）每次 `printf` 都直接写，理论上是 1000 次。验证命令是 `stdbuf -o1024 strace -c -e trace=write ./lab1c10_iface stdio`，看 `write` 行的 calls 列。缓冲区越小，系统调用越多、单次写入越短；缓冲区越大，用户态占用的内存和「数据压在缓冲里」的时间越长。
:::
:::

::: errata 接口选型的六个误解
1. **「stdio 一定比裸 `write` 慢」**——小记录、多次写时反过来：实测 1000 行日志 stdio 只发 3 次 `write`，裸写发 1000 次。stdio 多一次内存拷贝，但省掉大量特权级切换。
2. **「mmap 一定比 `read` 快」**——省掉显式拷贝和系统调用，却增加缺页与 TLB（translation lookaside buffer，CPU 里的页表项缓存）压力；读一遍就扔的小文件未必划算，文件被截断还会触发 `SIGBUS`。
3. **「socket 上也能随便用 `fprintf`」**——stdio 会缓冲、可能只写一部分，错误要等刷新才暴露；网络代码要用 `send` 循环或 RIO。
4. **「`O_DIRECT` 是性能开关」**——它绕过 page cache，要求地址、长度、偏移对齐；失去预读和写合并后，很多负载反而更慢。
5. **「零拷贝就是一次拷贝都没有」**——`sendfile`/`splice` 仍要 DMA（direct memory access，设备直接读写内存，不占 CPU 搬运）在设备与内存之间搬，只是省掉内核态与用户态之间那一次。
6. **「用了缓冲就不用处理短写」**——`FILE` 的缓冲不改变底层 `write` 可能短写的事实；`fflush` 失败、`ferror` 置位时，数据可能只出去一部分。
:::

### 1.10.7 小结

① 选接口比较三笔成本：系统调用、数据拷贝、等待方式；② stdio 用一次额外拷贝换掉大量系统调用，mmap 用缺页换掉显式 `read`，零拷贝省掉用户态那段搬运；③ 网络与管道优先保证完整性（循环、`EINTR`、非阻塞），大文件随机访问才考虑 mmap，持久化则始终要 `fsync`。如果只记住一件事，那就是：**先看数据形状和完整性要求，再谈哪个接口「快」。**

## 1.10.8 文件描述符的完整语义：表、标志与生命周期 {#sec-1.10.8}

这一节回答：一个 fd 整数背后到底存了哪些状态？哪些随 `dup` 共享、哪些不共享？fd 什么时候真正关闭，用尽了又会怎样？

::: preview 先抓住一件事
fd 只是进程 fd 表的下标，表项指向**打开文件描述**。偏移和状态标志（`O_APPEND`、`O_NONBLOCK`）存在描述里，所以 `dup`/`fork` 之后共享；`FD_CLOEXEC` 存在 fd 表项里，每个 fd 各有一份，`dup` 不会带过去。`close` 只减引用计数，最后一个引用消失才释放描述；`unlink` 之后只要还有 fd 开着，数据就还在。fd 用尽时，进程级是 `EMFILE`，系统级是 `ENFILE`。
:::

### 场景：一次 dup、一次 exec、一次 unlink

先猜四件事：`dup` 之后在其中一个 fd 上设 `O_APPEND`，另一个看得到吗？在 `dup` 出来的 fd 上设 `FD_CLOEXEC`，`exec` 之后哪个 fd 还在？`fork` 后子进程只 `lseek` 不写，父进程的偏移会变吗？`unlink` 之后已打开的 fd 还能读吗？

```c
/* lab1c10_fdsem.c：偏移、两套标志、exec、unlink 与 EMFILE */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/resource.h>
#include <sys/stat.h>
#include <sys/wait.h>
#include <unistd.h>

static int show_fds(void)
{
    for (int fd = 0; fd < 32; fd++) {
        struct stat st;
        if (fstat(fd, &st) != 0) continue;
        char p[64], t[256];
        snprintf(p, sizeof p, "/proc/self/fd/%d", fd);
        ssize_t n = readlink(p, t, sizeof t - 1);
        if (n >= 0) {
            t[n] = '\0';
            printf("fd %d -> %s\n", fd, t);
        }
    }
    return 0;
}

int main(int argc, char **argv)
{
    if (argc > 1 && strcmp(argv[1], "show") == 0)
        return show_fds();

    const char *p = "/tmp/lab1c10_fdsem.txt";
    int f1 = open(p, O_RDWR | O_CREAT | O_TRUNC, 0644);
    if (f1 < 0) { perror("open"); return 1; }
    if (write(f1, "0123456789", 10) != 10) return 1;

    int f3 = dup(f1);
    lseek(f1, 5, SEEK_SET);
    if (write(f1, "XY", 2) != 2) return 1;
    printf("dup offset: f1=%lld f3=%lld\n",
           (long long)lseek(f1, 0, SEEK_CUR), (long long)lseek(f3, 0, SEEK_CUR));

    int fl = fcntl(f3, F_GETFL);
    if (fl == -1 || fcntl(f3, F_SETFL, fl | O_APPEND) == -1) perror("F_SETFL");
    printf("O_APPEND: f1=%d f3=%d\n",
           !!(fcntl(f1, F_GETFL) & O_APPEND),
           !!(fcntl(f3, F_GETFL) & O_APPEND));

    int fdfl = fcntl(f3, F_GETFD);
    if (fdfl == -1 || fcntl(f3, F_SETFD, fdfl | FD_CLOEXEC) == -1) perror("F_SETFD");
    printf("FD_CLOEXEC: f1=%d f3=%d\n",
           !!(fcntl(f1, F_GETFD) & FD_CLOEXEC),
           !!(fcntl(f3, F_GETFD) & FD_CLOEXEC));

    fflush(stdout);
    pid_t pid = fork();
    if (pid == 0) {
        execl("/proc/self/exe", "fdsem", "show", NULL);
        _exit(127);
    }
    waitpid(pid, NULL, 0);

    pid = fork();
    if (pid == 0) {
        lseek(f1, 1, SEEK_CUR);
        _exit(0);
    }
    waitpid(pid, NULL, 0);
    printf("after child lseek +1: f1=%lld\n", (long long)lseek(f1, 0, SEEK_CUR));

    close(f3);
    lseek(f1, 0, SEEK_SET);
    char b[16] = {0};
    ssize_t n = read(f1, b, sizeof b - 1);
    printf("after close(f3): f1 reads %zd bytes = %s\n", n, b);

    if (unlink(p) == -1) perror("unlink");
    char lp[64], tgt[256];
    snprintf(lp, sizeof lp, "/proc/self/fd/%d", f1);
    ssize_t ln = readlink(lp, tgt, sizeof tgt - 1);
    if (ln >= 0) { tgt[ln] = '\0'; printf("link after unlink: %s\n", tgt); }
    lseek(f1, 0, SEEK_SET);
    n = read(f1, b, sizeof b - 1);
    printf("read after unlink: %zd bytes\n", n);
    close(f1);
    printf("file still exists after close: %d\n", access(p, F_OK) == 0);

    fflush(stdout);
    pid = fork();
    if (pid == 0) {
        struct rlimit rl = { 32, 32 };
        if (setrlimit(RLIMIT_NOFILE, &rl) == -1) { perror("setrlimit"); _exit(1); }
        int cnt = 0, fd;
        while ((fd = open("/dev/null", O_RDONLY)) >= 0) cnt++;
        printf("EMFILE test: opened=%d errno=%s\n", cnt, strerror(errno));
        fflush(stdout);
        _exit(0);
    }
    waitpid(pid, NULL, 0);
    return 0;
}
```

逐段读：

- `dup offset`：f1 先 `lseek` 到 5，写 2 字节后偏移 7；f3 是 `dup` 出来的，看到的也是 7。两个 fd 号不同，描述同一个。
- `O_APPEND`：通过 f3 设上的状态标志，在 f1 上读出来也是 1。状态标志属于打开文件描述，`dup` 之后共享。
- `FD_CLOEXEC`：f1 是 0，f3 是 1。描述符标志属于 fd 表项，在一个 fd 上设置不会影响另一个；`dup` 给新 fd 的 `FD_CLOEXEC` 默认是关闭的，要带就用 `F_DUPFD_CLOEXEC` 或再 `fcntl` 一次。
- `exec` 后的 fd 列表：fd 3（f1）还在，fd 4（f3）已经消失，因为 f3 带了 `FD_CLOEXEC`。0/1/2 是本次 `ssh` 会话的管道，后面的编号每次运行都不同，不必记。
- `after child lseek +1`：子进程只挪了偏移、没写数据，父进程从 7 看到 8。`fork` 复制 fd 表，表项指向同一个描述。
- `close(f3)` 之后 f1 仍读出 10 字节 `01234XY789`：引用计数从 2 减到 1，描述还在。内容里 `XY` 覆盖了原来的 `56`。
- `unlink` 之后 `/proc/self/fd/3` 的目标带上 ` (deleted)`，仍能读 10 字节；`close(f1)` 之后 `access` 返回 0（不存在），数据块这时才释放。
- `EMFILE test`：子进程把 `RLIMIT_NOFILE` 设成 32，0/1/2 已占用，成功打开 29 个（fd 3–31），第 30 次失败，`errno` 是 `EMFILE`。

::: def 定义 1.10.8 · 打开文件描述（open file description） {#def-1.10.8}
内核中由 `open` 创建、可被多个 fd 引用的对象，保存**文件偏移**、**状态标志**（`O_APPEND`、`O_NONBLOCK`、`O_ASYNC` 等）、引用计数和操作函数表。fd 表项指向它，它再指向 inode。`dup`、`dup2`、`fork` 与 `SCM_RIGHTS`（在 Unix socket 上传 fd 的辅助数据）都让多个 fd 共享同一个描述；再次 `open` 同一路径则新建描述、偏移独立。
:::

三层结构可以用一张表固定下来：

| 层 | 内核对象 | 由谁持有 | 关键内容 |
|:--|:--|:--|:--|
| 进程级 fd 表 | `struct files_struct` → `fdtable` | 每个进程一份 | 「fd 号 → `struct file *`」的数组，外加每个 fd 的描述符标志 |
| 打开文件描述 | `struct file` | 可被多个 fd、多个进程共享 | 偏移 `f_pos`、状态标志 `f_flags`、引用计数、`f_op` |
| inode | `struct inode` | 每个文件系统对象一份 | 类型、权限、大小、数据块位置、时间戳 |

`open` 做两件事：新建一个 `struct file`，再在当前进程 fd 表里找**编号最小**的空位填入指针。`fork` 只复制 fd 表，不复制 `struct file`；`dup` 只新增一个表项，也不复制 `struct file`。哪些状态共享，看表项指向谁：

| 操作 | 偏移 | 状态标志 | 说明 |
|:--|:--|:--|:--|
| `open` 同一路径两次 | 各自独立 | 各自独立 | 两个 `struct file` |
| `dup(fd)` / `dup2(fd, n)` | **共享** | **共享** | 同一个 `struct file` |
| `fork` 之后 | **共享** | **共享** | 子进程复制 fd 表，指针相同 |
| 传递 fd（`SCM_RIGHTS`） | **共享** | **共享** | 接收方拿到同一个打开文件描述 |

这也回答「父子进程各写同一个日志会不会互相覆盖」：用 `fork` 继承的 fd，偏移共享，不会各从 0 写；父子各自 `open`，偏移独立，会覆盖，除非加 `O_APPEND`。

### fd 标志与状态标志

同一个 fd 上有两套标志，`fcntl` 用不同的命令读写：

| 类别 | 存放位置 | 读 | 写 | 是否随 `dup` 共享 |
|:--|:--|:--|:--|:--|
| 描述符标志 | fd 表项 | `F_GETFD` | `F_SETFD` | 否，每个 fd 独立 |
| 状态标志 | `struct file` | `F_GETFL` | `F_SETFL` | 是，共享 |

描述符标志目前只有一位有意义：`FD_CLOEXEC`。它决定 `execve` 时这个 fd 是否被关闭。状态标志包括 `O_APPEND`、`O_NONBLOCK`、`O_ASYNC`、`O_DIRECT`（部分可改）。`open` 时的 `O_CLOEXEC` 是**原子地**设置 `FD_CLOEXEC`；先 `open` 再 `fcntl(F_SETFD)` 在多线程程序里有窗口：另一个线程可能在这之间 `fork` + `exec`，把不该继承的 fd 泄漏给子程序。

```text
/* 正确：打开即带 CLOEXEC，避免 fork/exec 竞争 */
int fd = open(path, O_RDONLY | O_CLOEXEC);

/* 也可以对已有 fd 复制出一个带 CLOEXEC 的新 fd */
int nfd = fcntl(fd, F_DUPFD_CLOEXEC, 0);

/* 修改状态标志必须先读再写，不能覆盖其他位 */
int flags = fcntl(fd, F_GETFL);
if (flags == -1) { /* errno */ }
if (fcntl(fd, F_SETFL, flags | O_NONBLOCK) == -1) { /* errno */ }
```

`F_SETFL` 只能改一部分标志：`O_APPEND`、`O_NONBLOCK`、`O_ASYNC`、`O_DIRECT`（在部分文件系统上）、`O_NOATIME`。`O_CREAT`、`O_TRUNC`、`O_EXCL` 这类「打开时的一次性动作」改了也没意义，内核会忽略。

### fd 用尽：两种 errno

每个进程的 fd 数量受 `RLIMIT_NOFILE` 限制，系统全体受 `fs.file-max` 与内存限制。两者失败时的 `errno` 不同：

| 情形 | `errno` | 含义 | 排查 |
|:--|:--|:--|:--|
| 进程 fd 表满 | `EMFILE` | 达到 `RLIMIT_NOFILE` 软限制 | `ulimit -n`、`ls /proc/<pid>/fd \| wc -l` |
| 系统文件表满 | `ENFILE` | 全局上限或内存不足 | `cat /proc/sys/fs/file-nr` |
| fd 不存在/已关闭 | `EBADF` | 用了无效 fd，或方向不对（读只写 fd） | 检查返回值与 `fcntl(fd, F_GETFD)` |
| `dup2` 的 `newfd` 越界 | `EBADF` | `newfd` 超出 `RLIMIT_NOFILE` 或为负 | 先校验范围 |
| `open` 路径不存在 | `ENOENT` | 路径或中间目录缺失 | `strace -e openat` |

实测那一行 `opened=29` 就是 `RLIMIT_NOFILE=32` 减去 0/1/2 的结果；第 30 次 `open` 返回 -1，`errno` 是 `EMFILE`。`ENFILE` 要等系统级文件表满，普通用户很难构造，本机未实测；排查它要看 `/proc/sys/fs/file-nr` 的第一个数（已分配）与第三个限制。

`EMFILE` 在服务器上很常见：每个连接一个 fd，`accept` 返回 `EMFILE` 后如果继续 `accept`，会空转。正确做法是预留一个「救急 fd」：检测到 `EMFILE` 时关闭它，`accept` 一个连接后立刻关闭，给自己留出打日志和退出的余地（片段，`listenfd` 是监听 socket）：

```text
/* 救急 fd 模式：accept 遇到 EMFILE 时腾出一个 fd，避免死循环 */
int idlefd = open("/dev/null", O_RDONLY | O_CLOEXEC);
for (;;) {
    int conn = accept4(listenfd, NULL, NULL, SOCK_CLOEXEC);
    if (conn == -1) {
        if (errno == EMFILE && idlefd >= 0) {
            close(idlefd);
            conn = accept(listenfd, NULL, NULL);   /* 接受后立刻关闭，丢弃 */
            if (conn >= 0) close(conn);
            idlefd = open("/dev/null", O_RDONLY | O_CLOEXEC);
        }
        continue;                                   /* 其他错误：记录并继续 */
    }
    /* 处理连接 */
}
```

### 引用计数：fd 什么时候真正关闭

`close(fd)` 做两件事：删除 fd 表项；把对应 `struct file` 的引用计数减一。计数归零时才调用文件的 `release` 操作，inode 的打开计数也才减一。所以：

- `dup` 出来的两个 fd，关掉一个，另一个仍可读写，偏移继续共享；实测关掉 f3 后 f1 仍读出 10 字节。
- `fork` 后子进程退出，父进程的 fd 不受影响；反过来，父进程先退出也不影响子进程继续用这个 fd。
- 一个文件被 `unlink` 后，只要还有进程持有打开的 fd，数据块就不会释放——实测链接带 `(deleted)` 仍可读，关掉最后一个 fd 后文件名与数据一起消失。这是临时文件的常用手法（`O_TMPFILE` 或 `open` 后立刻 `unlink`）。
- `close` 因 `EINTR`、`EIO` 失败（返回 -1）时，fd 的状态是**未定义**的：Linux 上 fd 已经释放（`EBADF` 除外），但不要重试 `close`，否则可能关掉另一个线程刚打开的同号 fd。

::: ex 例 1.10.8 · 先猜 fd 用尽与 unlink 的结局 {#ex-1.10.8}
把 `RLIMIT_NOFILE` 设成 32，进程已占用 0/1/2，然后循环 `open("/dev/null")`。先猜：能成功几次？失败时 `errno` 是什么？另一个实验：打开文件、写入、`unlink`，此时 `/proc/self/fd` 里的链接显示什么？磁盘空间什么时候真正释放？

::: sol 解答
实测成功 29 次（fd 3 到 31），第 30 次返回 -1，`errno=EMFILE`（`Too many open files`）。`unlink` 之后链接目标带 ` (deleted)` 后缀，已打开的 fd 仍能读出 10 字节；直到最后一个 fd `close`，inode 的链接数与打开计数都归零，数据块才释放。名字消失与空间释放是两个时刻，中间由打开的文件描述撑着。
:::

::: errata 关于 fd 的六个误解
1. **「fd 就是文件」**——fd 是进程 fd 表的下标，指向打开文件描述；同一个文件可以有多个 fd，同一个描述也可以被多个进程共享。
2. **「`dup2` 会复制偏移」**——不复制，两个 fd 共享同一个偏移；向其中一个写，另一个的 `lseek` 立刻看到变化（实测 7 与 7）。
3. **「`dup` 出来的新 fd 会继承 `FD_CLOEXEC`」**——不会，`dup` 给新 fd 的描述符标志是空的；要带就用 `F_DUPFD_CLOEXEC`，或在 `open` 时直接给 `O_CLOEXEC`。
4. **「`EMFILE` 与 `ENFILE` 是一回事」**——`EMFILE` 是当前进程达到 `RLIMIT_NOFILE`，`ENFILE` 是系统级文件表满；前者调自己的限制，后者要看整机。
5. **「`close` 返回 -1 应该重试」**——Linux 上 fd 已经释放，重试可能关掉另一个线程刚复用的同号 fd；记录错误，但不要把 fd 再交给 `close`。
6. **「0/1/2 一定存在且连着终端」**——守护进程常把它们重定向到 `/dev/null` 或直接关闭；库函数不能假设这三个 fd 可用，更不能假设它们是终端。
:::

### 1.10.8 小结

① fd 表在进程级，打开文件描述可被多个 fd/进程共享，inode 描述文件本身；② 偏移与状态标志跟着描述走，`FD_CLOEXEC` 跟着 fd 表项走，`exec` 只关闭带该标志的 fd；③ `close` 减引用计数，`unlink` 后由仍打开的 fd 撑着数据，fd 用尽要分清 `EMFILE` 与 `ENFILE`。如果只记住一件事，那就是：**fd 是表项，描述才是状态；共享与否看它们指向哪一层。**

## 1.10.9 read/write 的返回值：短读、短写、EINTR 与 EAGAIN {#sec-1.10.9}

这一节回答：`read`/`write` 只返回一个整数，你怎么从它判断「搬完了没有、还该不该继续、是不是出事了」？

1.10.4 把 `EINTR` 和短读短写包进了 `rio_readn`/`rio_writen`，等于先告诉你「要写循环」。这一节回到裸 `read`/`write`，补上循环之前的那一步：把返回值的种类认全。种类认错了，循环写得再工整也没用。

::: preview 先抓住一件事
返回值同时编码三件事：搬了多少字节、有没有到末尾、有没有出错。小于请求的正数只是「做了一部分」，不是错误；0 对 `read` 才是 EOF；只有 -1 才有 `errno` 可看，而 `errno` 里的 `EINTR`、`EAGAIN` 都不算失败。一次 `write` 从不保证写完。
:::

### 场景：八种返回值，加一次睡眠

先用二十秒猜一下：对同一个空管道，阻塞读、非阻塞读、一次写 1 MiB、读 0 字节，四个返回值分别是什么？再猜：睡 5 秒的 `nanosleep` 在第 1 秒被闹钟打断，它会把「还剩多久」告诉你吗？

```c
/* lab1c10_rv2.c：把 read/write 的返回值与 nanosleep 的剩余时间一次跑完 */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <time.h>
#include <unistd.h>

static void on_alarm(int s) { (void)s; }

static void show(const char *tag, ssize_t n, int e)
{
    printf("%-8s n=%6zd errno=%s(%d)\n", tag, n, strerror(e), e);
}

int main(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = on_alarm;
    sa.sa_flags = 0;                       /* 不自动重启 */
    sigaction(SIGALRM, &sa, NULL);

    char b[8];
    int p[2];
    if (pipe(p) == -1) return 1;

    /* A 短读：写入 5 字节后关闭写端 */
    if (write(p[1], "hello", 5) != 5) return 1;
    close(p[1]);
    errno = 0;
    show("A short", read(p[0], b, sizeof b), errno);

    /* B EOF：同一读端再来一次 */
    errno = 0;
    show("B eof", read(p[0], b, sizeof b), errno);
    close(p[0]);

    /* C EINTR：空管道阻塞读，1 秒后被 SIGALRM 打断 */
    int q[2];
    if (pipe(q) == -1) return 1;
    alarm(1);
    errno = 0;
    show("C eintr", read(q[0], b, sizeof b), errno);
    alarm(0);

    /* C2 nanosleep 被打断：剩余时间写回 rem */
    struct timespec req = { 5, 0 }, rem = { 0, 0 };
    alarm(1);
    errno = 0;
    int rc = nanosleep(&req, &rem);
    printf("C2 sleep rc=%d errno=%s(%d) rem=%ld.%03lds\n", rc, strerror(errno),
           errno, (long)rem.tv_sec, rem.tv_nsec / 1000000);
    alarm(0);

    /* D EAGAIN：读端设成非阻塞，管道仍空 */
    int fl = fcntl(q[0], F_GETFL);
    if (fl == -1 || fcntl(q[0], F_SETFL, fl | O_NONBLOCK) == -1) return 1;
    errno = 0;
    show("D eagain", read(q[0], b, sizeof b), errno);

    /* E 短写：非阻塞写 1 MiB 进容量 64 KiB 的管道 */
    static char big[1 << 20];
    memset(big, 'x', sizeof big);
    fl = fcntl(q[1], F_GETFL);
    if (fl == -1 || fcntl(q[1], F_SETFL, fl | O_NONBLOCK) == -1) return 1;
    errno = 0;
    show("E shortw", write(q[1], big, sizeof big), errno);

    /* F count 为 0 */
    errno = 0;
    show("F zero", write(q[1], big, 0), errno);

    /* G EPIPE：读端关闭后继续写 */
    close(q[0]);
    signal(SIGPIPE, SIG_IGN);
    errno = 0;
    show("G epipe", write(q[1], big, 16), errno);

    /* H 短读的另一种形态：管道里只有 100 字节，却要 65536 */
    int r[2];
    if (pipe(r) == -1) return 1;
    if (write(r[1], big, 100) != 100) return 1;
    static char huge[65536];
    errno = 0;
    show("H bigask", read(r[0], huge, sizeof huge), errno);
    close(r[0]);
    close(r[1]);
    return 0;
}
```

Ubuntu 24.04.5 aarch64（gcc 13.3，`cc -std=c17 -O2`）实测，九行输出：

```text
A short  n=     5 errno=Success(0)
B eof    n=     0 errno=Success(0)
C eintr  n=    -1 errno=Interrupted system call(4)
C2 sleep rc=-1 errno=Interrupted system call(4) rem=3.998s
D eagain n=    -1 errno=Resource temporarily unavailable(11)
E shortw n= 65536 errno=Success(0)
F zero   n=     0 errno=Success(0)
G epipe  n=    -1 errno=Broken pipe(32)
H bigask n=   100 errno=Success(0)
```

把九行摊成一张表，每一行对应一种「下一步」：

| 行 | 请求 | 返回 | `errno` | 判读与下一步 |
|:--|:--|--:|:--|:--|
| A | `read` 8，管道里 5 | 5 | 不变 | 短读：先收下，再读一次看是不是 EOF |
| B | `read` 8，已空 | 0 | 不变 | EOF：结束循环 |
| C | `read` 8，阻塞 | -1 | `EINTR` | 一个字节没搬，原样重试 |
| C2 | `nanosleep` 5 s | -1 | `EINTR` | `rem` 给出剩余 3.998 s，接着睡剩下的 |
| D | `read` 8，非阻塞 | -1 | `EAGAIN` | 现在没数据，等事件；不是 EOF |
| E | `write` 1 MiB，非阻塞 | 65536 | 不变 | 短写：从第 65537 字节续写 |
| F | `write` 0 字节 | 0 | 不变 | 你要求搬 0 字节，不是 EOF |
| G | `write` 16，读端已关 | -1 | `EPIPE` | 停写；内核同时发 `SIGPIPE`，被忽略才看得到返回值 |
| H | `read` 65536，管道里 100 | 100 | 不变 | 请求再大也只拿现有的，短读与 EOF 是两件事 |

九行里只有三行是 -1，下一步却各不相同：C 原样重试、D 去等事件、G 别再写。A、E、H 返回正数却不等于「做完了」；B 与 F 都返回 0，含义却相反。表里的 4、11、32 只是 Linux 的取值，代码里用宏判断。

### 0 的两种来源

0 只有两种来源：`read` 在 `count > 0` 时返回 0，是真到末尾；`count` 本身为 0 时，内核什么都没做（F 行）。`write` 只有 `count == 0` 才该返回 0；`count > 0` 却返回 0 属于异常，应当按 `EIO` 处理，否则循环会空转。把 `read` 的 0 一律当 EOF，会在「长度参数被算成 0」的边界上提前收工。

::: def 定义 1.10.9 · 部分完成（partial completion）与未完成 {#def-1.10.9}
**部分完成**：一次 `read`/`write` 只搬了请求量的一部分，返回值是正数且小于 `count`，`errno` 不变。**未完成**：返回 -1，一个字节都没搬；`errno` 区分原因，`EINTR` 可原样重试，`EAGAIN` 要等事件，其余按错误处理。两种情形都不等于「失败退出」。
:::

### EINTR 与 EAGAIN：两种「没做成」

`EINTR`（interrupted system call）表示系统调用在完成前被信号处理函数打断。它不是失败：内核没有搬任何数据就退出，handler 返回后可以原样再来。C 行就是这么来的：`read` 阻塞在空管道上，第 1 秒被 `SIGALRM` 打断，返回 -1/`EINTR`。1.10.4 的 `rio_readn` 里那句 `if (errno == EINTR) continue;` 就是全部处理，本节不再重写循环。`sigaction` 带 `SA_RESTART` 时，内核会自动重启一部分慢调用，多数时候你见不到它；但不是所有调用都能重启，库代码不该赌这个默认值。

`EAGAIN` 是另一回事：fd 设了 `O_NONBLOCK`，此刻没有数据可读（或没有空间可写），内核立刻返回，让你去等事件。Linux 上 `EAGAIN` 与 `EWOULDBLOCK` 同值，判断一个就够。正确反应不是忙等，而是把 fd 交给 `epoll`/`poll`，等可读或可写通知后再来。D 行与 C 行看着一样都是 -1，区别全在 `errno`：一个让你立刻重来，一个让你先去睡。

睡眠类调用最能看出两者的区别：C2 行里闹钟在第 1 秒打断 5 秒的 `nanosleep`，它返回 -1/`EINTR`，同时把还剩多久写回第二个参数——实测 `rem=3.998s`（每次运行在 3.99–4.00 s 之间浮动）。所以 `EINTR` 不总是「原样重来」：`nanosleep` 要拿剩余时间接着睡，`read`/`write` 才原样重试。

还有一条与返回值有关的硬边界：Linux 把单次 `read`/`write` 的 `count` 截到 `MAX_RW_COUNT`（`0x7ffff000`，即 2147479552，约 2 GiB）。传更大的数不报错，内核只处理这么多，返回值自然小于请求——这种短写与缓冲区无关，是接口上限。这条来自内核源码里的常量，本机没有构造 2 GiB 缓冲区去复现。

::: errata 返回值的六个误解
1. **「返回 -1 才是出问题，返回正数就是成功」**——短读短写返回正数，却只完成了一部分；`read` 返回 0 更不是成功。
2. **「`read` 返回 0 一定是 EOF」**——`count` 为 0 时也返回 0（实测 F 行）。先检查自己的长度参数。
3. **「`EINTR` 要把整个缓冲区重读」**——被打断前若已搬了一部分，返回值是正数而不是 -1；只有 -1 才是「一点没动」。
4. **「`EAGAIN` 等于对端关闭」**——`EAGAIN` 是「现在没有」，0 才是「不会再有」。H 行请求 65536 只拿 100，也不是 EOF。
5. **「`errno` 为 0 就说明成功」**——成功时内核不清 `errno`，它会留着上一次的错误；只能看返回值。
6. **「`EINTR` 一律原样重试」**——`nanosleep` 被打断后，剩余时间只写在第二个参数里（不传就丢了）；实测传了就拿到 `rem=3.998s`，要拿它接着睡，而不是把原来的 5 秒再睡一遍。
:::

### 1.10.9 小结

① `read`/`write` 的返回值编码「搬了多少、有没有到头、有没有出错」，短计数是常态不是错误；② 0 要看调用和 `count`，`write` 返回 0 且 `count > 0` 是异常；③ `EINTR` 原样重试、`EAGAIN` 等事件、`EPIPE` 停止写，`errno` 只在 -1 时可信。如果只记住一件事，那就是：**返回值是「做了多少」，不是「成功或失败」。**

## 1.10.10 dup2、原子重定向与 /proc/self/fd {#sec-1.10.10}

这一节回答：`dup2` 的「原子」到底保证哪一段？重定向装好之后，你怎么从进程内部确认 fd 真的指向了目标？

1.10.5 已经验证过共享偏移、`fork` 继承、`dup2` 换目标和 `fflush` 的时机。这一节补三件它没讲透的事：`dup2` 与「先 `close` 再 `dup`」差在哪、`FD_CLOEXEC` 为什么会在复制时丢掉、`/proc/self/fd` 这张实况表怎么读。最后用一次实测把追加重定向的顺序坑钉死。

::: preview 先抓住一件事
`dup2` 把「关掉 `newfd`」和「让 `newfd` 指向 `oldfd` 的描述」做成一步，中间没有空窗；但它会**清掉** `newfd` 上的 `FD_CLOEXEC`，重定向到 1 号之后，`exec` 出来的子进程照样继承它。`/proc/self/fd` 是每个进程一张的实况表。追加重定向时，`>` 和 `2>>` 落在同一个文件上会各管一个偏移，后写的盖掉先写的。
:::

### 场景一：strace 里没有 close(1)

重定向的写法 1.10.5 已经给过，这里只看内核收到了什么。把本节程序跑一遍 `strace`，摘出与 1 号有关的几行：

```bash
$ strace -e trace=openat,close,dup2,dup3 ./lab1c10_dupv2 2>&1 | grep -E 'dupv2|dup3'
openat(AT_FDCWD, "/tmp/lab1c10_dupv2.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644) = 3
dup3(3, 1, 0)                           = 1
openat(AT_FDCWD, "/tmp/lab1c10_dupv2.txt", O_RDONLY|O_CLOEXEC) = 3
dup3(3, 6, 0)                           = 6
dup3(3, 7, O_CLOEXEC)                   = 7
openat(AT_FDCWD, "/tmp/lab1c10_dupv2.txt", O_WRONLY) = 1
dup3(4, 1, 0)                           = 1
```

前两行就是一次 `dup2(3, 1)`：**没有 `close(1)`**。glibc 把它实现成 `dup3(3, 1, 0)`，内核在同一次系统调用里完成「关掉旧的 1 号」和「让 1 号指向 3 号的描述」，中间没有一刻 1 号是空的。

最后两行是反例：先 `close(1)` 再 `open` 同一个文件，内核把刚空出来的 1 号分给了它。多线程程序里这个空窗就是 bug——别的线程或信号处理函数在这两步之间 `open` 任何文件，都会抢走 1 号。`dup2` 的价值不在少写一行，而在于没有这个窗口。

```c
/* lab1c10_dupv2.c：dup2 的原子性、FD_CLOEXEC、/proc/self/fd 与 close 空窗 */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

/* 报告一律走 stderr，免得 stdout 被换掉后看不见 */
static void target(int fd, const char *tag)
{
    char p[32], t[256];
    snprintf(p, sizeof p, "/proc/self/fd/%d", fd);
    ssize_t n = readlink(p, t, sizeof t - 1);
    if (n < 0) { dprintf(2, "%-6s fd %d: (none)\n", tag, fd); return; }
    t[n] = '\0';
    dprintf(2, "%-6s fd %d -> %s cloexec=%d\n", tag, fd, t,
            (fcntl(fd, F_GETFD) & FD_CLOEXEC) ? 1 : 0);
}

int main(int argc, char **argv)
{
    if (argc > 1 && strcmp(argv[1], "list") == 0) {   /* exec 之后的子进程 */
        for (int fd = 0; fd < 8; fd++) target(fd, "child");
        return 0;
    }

    int fd = open("/tmp/lab1c10_dupv2.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) return 1;
    target(1, "before");
    if (dup2(fd, 1) < 0) return 1;                    /* 一步换掉 1 号 */
    target(1, "after");
    if (write(1, "via fd 1\n", 9) != 9) return 1;
    close(fd);                                        /* 1 号仍持有描述 */

    int a = open("/tmp/lab1c10_dupv2.txt", O_RDONLY | O_CLOEXEC);
    if (a < 0) return 1;
    int b = dup2(a, 6);                               /* 复制会清掉 CLOEXEC */
    int c = dup3(a, 7, O_CLOEXEC);                    /* dup3 才能带上 */
    dprintf(2, "dup2->%d cloexec6=%d  dup3->%d cloexec7=%d\n", b,
            (fcntl(6, F_GETFD) & FD_CLOEXEC) ? 1 : 0, c,
            (fcntl(7, F_GETFD) & FD_CLOEXEC) ? 1 : 0);

    errno = 0;
    int same = dup3(a, a, 0);                         /* 同一号：EINVAL */
    dprintf(2, "dup3(a,a)=%d errno=%s\n", same, strerror(errno));

    /* 反例：先关 1 号再 open，空出来的 1 号会被别人拿走 */
    int saved = dup(1);
    close(1);
    int stolen = open("/tmp/lab1c10_dupv2.txt", O_WRONLY);
    dprintf(2, "after close(1), open -> fd %d\n", stolen);
    if (stolen >= 0) close(stolen);
    dup2(saved, 1);                                   /* 装回终端 */
    close(saved);

    if (fork() == 0) {
        execl("/proc/self/exe", "dupv2", "list", (char *)NULL);
        _exit(127);
    }
    wait(NULL);
    return 0;
}
```

Ubuntu 24.04.5 aarch64（gcc 13.3）实测；0/1/2 是本次 `ssh` 会话的管道，编号每次不同：

```text
before fd 1 -> pipe:[265117] cloexec=0
after  fd 1 -> /tmp/lab1c10_dupv2.txt cloexec=0
dup2->6 cloexec6=0  dup3->7 cloexec7=1
dup3(a,a)=-1 errno=Invalid argument
after close(1), open -> fd 1
child  fd 0 -> pipe:[265116] cloexec=0
child  fd 1 -> /tmp/lab1c10_dupv2.txt cloexec=0
child  fd 2 -> pipe:[265118] cloexec=0
child  fd 3: (none)
child  fd 4: (none)
child  fd 5: (none)
child  fd 6 -> /tmp/lab1c10_dupv2.txt cloexec=0
child  fd 7: (none)
```

五行输出：

- `before/after`：1 号从会话管道换成文件，两行的 `cloexec` 都是 0。3 号是用 `O_CLOEXEC` 打开的，照样没把标志带过来。
- `dup2->6 cloexec6=0`：**`dup2` 会清掉新 fd 上的 `FD_CLOEXEC`**。要保留只能走 `dup3(a, 7, O_CLOEXEC)`，所以 7 号是 1、6 号是 0。`dup3` 是 Linux 专有接口，`oldfd == newfd` 时直接返回 `EINVAL`（`dup2` 在同样情况下返回成功）。
- `after close(1), open -> fd 1`：这就是空窗的证据——1 号关掉之后，下一个 `open` 立刻把它填上。`dup2` 里没有这一步。
- 子进程里 3、7 号不见了，6 号还在：三个 fd 指同一个文件，只有一个熬过 `exec`，因为 `FD_CLOEXEC` 是**每个 fd 一份**的（1.10.8）。
- 0/1/2 原样继承。这既是重定向能被 `exec` 带进子程序的原因，也是服务进程必须显式处理三个标准 fd 的原因。

用 `/proc/self/fd` 可以直接看到这张表：

```bash
$ ls -l /proc/self/fd
lr-x------ 1 juanwang juanwang 64 Oct 30 23:08 0 -> pipe:[269054]
l-wx------ 1 juanwang juanwang 64 Oct 30 23:08 1 -> pipe:[269055]
l-wx------ 1 juanwang juanwang 64 Oct 30 23:08 2 -> pipe:[269056]
lr-x------ 1 juanwang juanwang 64 Oct 30 23:08 3 -> /proc/110391/fd
```

这是 `ssh` 会话里的结果（日期、uid、pid、inode 号每次不同）：没分配终端时 0/1/2 是管道，坐在终端前会显示 `/dev/pts/N`；最后一项是 `ls` 自己打开目录占的 fd 3。

`/proc/self/fd` 是内核为每个进程现生成的符号链接目录，目标就是打开文件描述对应的对象。用 `readlink` 就能读到它；管道显示 `pipe:[inode]`，文件名后会带 ` (deleted)`——这是排查「磁盘空间没释放」的第一手证据。

一个完整的小工具：打印当前进程的 fd 表并标注每个 fd 的类型与目标。它同时演示了 `fcntl(F_GETFL)`、`readlink` 与 `dirfd` 的用法：

```c
/* lab1c10_fds.c：列出本进程打开的 fd、类型、访问模式与目标 */
#ifndef _GNU_SOURCE
#define _GNU_SOURCE
#endif
#include <dirent.h>
#include <fcntl.h>
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

static void describe(int fd)
{
    struct stat st;
    if (fstat(fd, &st) == -1)
        return;

    const char *kind = S_ISREG(st.st_mode) ? "file" :
                       S_ISDIR(st.st_mode) ? "dir" :
                       S_ISCHR(st.st_mode) ? "chr" :
                       S_ISFIFO(st.st_mode) ? "fifo" :
                       S_ISSOCK(st.st_mode) ? "sock" : "other";

    int fl = fcntl(fd, F_GETFL);
    if (fl == -1)
        return;
    const char *mode = (fl & O_ACCMODE) == O_RDONLY ? "r" :
                       (fl & O_ACCMODE) == O_WRONLY ? "w" : "rw";

    char path[64], target[PATH_MAX];
    snprintf(path, sizeof path, "/proc/self/fd/%d", fd);
    ssize_t n = readlink(path, target, sizeof target - 1);
    if (n < 0)
        return;
    target[n] = '\0';

    printf("%3d  %-5s %-2s %s%s\n", fd, kind, mode, target,
           (fcntl(fd, F_GETFD) & FD_CLOEXEC) ? "  [cloexec]" : "");
}

int main(void)
{
    DIR *d = opendir("/proc/self/fd");
    if (d == NULL) {
        perror("opendir");
        return 1;
    }
    int self = dirfd(d);               /* 目录流自己的 fd，最后跳过 */
    struct dirent *e;
    while ((e = readdir(d)) != NULL) {
        if (e->d_name[0] == '.')
            continue;
        int fd = atoi(e->d_name);
        if (fd != self)
            describe(fd);
    }
    closedir(d);
    return 0;
}
```

把它跑在重定向环境里，能同时看到 shell 留下的痕迹：

```bash
$ printf 'hello\n' > /tmp/lab1c10_readme.md
$ ./lab1c10_fds 3</tmp/lab1c10_readme.md 4>/tmp/lab1c10_out.txt
  0  fifo  r  pipe:[277263]
  1  fifo  w  pipe:[277264]
  2  fifo  w  pipe:[277265]
  3  file  r  /tmp/lab1c10_readme.md
  4  file  w  /tmp/lab1c10_out.txt
```

`3<` 与 `4>` 是 shell 在 `exec` 前用 `open` + `dup2` 装好的，程序自己完全没有参与。再把 `2>&1` 加在末尾跑一次，fd 1 与 fd 2 会显示**同一个** `pipe:[...]`：它们是同一个打开文件描述上的两个 fd，这正是 1.10.5 说的「共享的是描述」。

所以 `nohup`、`daemon`、`systemd` 都要显式处理 0/1/2：它们不是「程序的属性」，而是继承来的 fd 表。

::: note `O_TMPFILE`：没有名字的临时文件
`open("/tmp", O_TMPFILE | O_RDWR, 0600)` 在目录里创建一个没有名字的 inode，只能通过返回的 fd 访问；`linkat(fd, "", AT_FDCWD, path, AT_EMPTY_PATH)` 可以稍后给它命名。它避免了「先 `mkstemp` 再 `unlink`」的竞争与残留，是临时文件、原子写盘（写完后 `linkat` 到目标名）的现代做法。
:::

### 追加重定向：两个偏移，后写的盖掉先写的

把 stdout 和 stderr 记进同一个日志，常见写法是 `> log 2>> log`。用下面这个只打印两行的程序试一下：

```c
/* lab1c10_app.c：先写 stdout、再写 stderr，用来看两个偏移 */
#include <stdio.h>

int main(void)
{
    printf("OUT line\n");                 /* 重定向到文件后是全缓冲 */
    fprintf(stderr, "ERR line\n");        /* 无缓冲，立刻落盘 */
    return 0;
}
```

```bash
$ ./lab1c10_app > /tmp/lab1c10_app.log 2>> /tmp/lab1c10_app.log
$ cat /tmp/lab1c10_app.log
OUT line
$ wc -c < /tmp/lab1c10_app.log
9
```

`ERR line` 不见了，文件里只剩 9 字节。原因不是覆盖写权限，而是两个偏移：`>` 打开时偏移是 0，不带 `O_APPEND`；`2>>` 带 `O_APPEND`，每次写都先跳到文件末尾。stderr 无缓冲，先写，落在 0–8；stdout 攒到进程退出才刷，而它的偏移还停在 0，于是把前 9 字节原样盖掉。日志少了一行，而且从内容上看不出来。

改成 `> log 2>&1`，两个 fd 共用同一个描述和偏移，实测 18 字节两行都在，先 `ERR line` 后 `OUT line`；bash 的 `&>> log` 效果相同。判断标准只有一条：两个 fd 是不是同一个描述——`2>>` 一定是另一个。

::: errata 关于 dup2 与 /proc/self/fd 的五个误解
1. **「`dup2` 只是 `close` + `dup` 写成一行」**——`close(1)` 后 1 号是空的，实测下一个 `open` 立刻拿到 1；`dup2` 没有这个窗口。
2. **「`dup2` 会保留 `FD_CLOEXEC`」**——会清掉。实测 3 号带 `O_CLOEXEC`，`dup2` 出来的 6 号是 0，`dup3` 出来的 7 号才是 1。
3. **「`dup3` 与 `dup2` 完全等价」**——`dup3(a, a, 0)` 返回 -1/`EINVAL`，`dup2(a, a)` 返回 `a`；而且 `dup3` 是 Linux 专有。
4. **「`/proc/self/fd` 显示的一定是文件名」**——管道显示 `pipe:[inode]`，删除后带 ` (deleted)`；`ls` 那项的 3 号是它自己的目录 fd。
5. **「`>log 2>>log` 两个都是追加」**——`>` 不带 `O_APPEND`、偏移从 0 开始，`2>>` 带；实测 stderr 那一行被后刷的 stdout 整段盖掉。
:::

### 1.10.10 小结

① `dup2` 把「关 `newfd`」与「复制描述」做成一步，换成 `close` + `dup` 就留下一个实测可复现的空窗；② `FD_CLOEXEC` 属于 fd 表项，`dup2` 会清掉，要保留用 `dup3`；③ `/proc/self/fd` 是实时 fd 表，管道显示 inode，删除显示 `(deleted)`；④ 判断追加重定向只看两个 fd 是不是同一个描述。如果只记住一件事，那就是：**原子性保证「中间没人能插进来」。**

## 1.10.11 完整程序一：把 EINTR、EAGAIN、短读、短写放进一个程序 {#sec-1.10.11}

这一节回答：四种情形放进同一个程序，`read_full`/`write_full` 该在哪一步重试、在哪一步把控制权交回调用者？

1.10.9 把返回值分成了「部分完成」「`EINTR`」「`EAGAIN`」三类；三类混进同一个循环时，最容易写错的是「谁负责重试」。下面这个程序把四种情形压进一次运行，每个函数只做一件事。

::: preview 先抓住一件事
`EINTR` 在库函数内部吞掉——它一个字节都没搬，重试一定安全。`EAGAIN` 必须原样返回给调用者——它意味着「现在没有，等事件」，库函数无权替调用者决定等多久、怎么等。短读短写靠循环补足，进度用返回值或出参带出来。
:::

### 三个辅助函数：谁重试、谁上报

`read_full` 负责「读满或读到 EOF」，`write_full` 负责「写完或明确失败」，`sleep_full` 负责「睡够或报错」。三者对 `EINTR` 的处理一样：重试；对 `EAGAIN` 的处理也一样：不重试，交回调用者。

```c
/* lab1c10_robust.c：EINTR、EAGAIN、短读、短写放进一个程序 */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

static volatile sig_atomic_t alarms;

static void on_alarm(int s) { (void)s; alarms++; }

static void set_nonblock(int fd)
{
    int fl = fcntl(fd, F_GETFL);
    if (fl == -1 || fcntl(fd, F_SETFL, fl | O_NONBLOCK) == -1) {
        perror("fcntl");
        exit(1);
    }
}

static double now_ms(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec * 1e3 + (double)ts.tv_nsec / 1e6;
}

/* 读满 n 字节，读到 EOF 提前返回；EINTR 重试并计数 */
static ssize_t read_full(int fd, void *buf, size_t n, int *eintr)
{
    size_t left = n;
    char *p = buf;
    while (left > 0) {
        ssize_t rc = read(fd, p, left);
        if (rc < 0) {
            if (errno == EINTR) { (*eintr)++; continue; }
            return -1;
        }
        if (rc == 0) break;
        left -= (size_t)rc;
        p += rc;
    }
    return (ssize_t)(n - left);
}

/* 写完 n 字节；已写入的进度由 done 带出 */
static ssize_t write_full(int fd, const void *buf, size_t n, size_t *done)
{
    size_t left = n;
    const char *p = buf;
    *done = 0;
    while (left > 0) {
        ssize_t rc = write(fd, p, left);
        if (rc < 0) {
            if (errno == EINTR) continue;
            return -1;
        }
        if (rc == 0) { errno = EIO; return -1; }
        left -= (size_t)rc;
        p += rc;
        *done = n - left;
    }
    return (ssize_t)n;
}

/* 睡够 ms 毫秒；被打断后用剩余时间接着睡，返回被打断的次数 */
static int sleep_full(long ms)
{
    struct timespec req = { ms / 1000, (ms % 1000) * 1000000L };
    int calls = 0;
    while (nanosleep(&req, &req) == -1) {
        if (errno != EINTR) return -1;
        calls++;
    }
    return calls;
}
```

三个函数的分工值得逐条看：

- `read_full` 返回「实际拿到多少」，小于 `n` 就是 EOF 提前收工；`eintr` 出参记录被打断几次，用来验证重试真的发生过。
- `write_full` 用 `done` 带出已写字节数。失败时返回 -1，但 `done` 告诉你写到哪儿——这是短写之后「从哪儿续」的唯一依据。
- `sleep_full` 把剩余时间写回同一个结构体再传进去，被打断几次就循环几次；返回 -1 说明不是 `EINTR`，而是真错误。

### main：四种情形各来一次

同一个文件的 `main` 里没有新接口，只有四个场景：短读、`EINTR`、`EAGAIN`、短写，最后加一个睡眠重试。

```c
int main(void)
{
    struct sigaction sa = {0};
    sa.sa_handler = on_alarm;
    sa.sa_flags = 0;                       /* 不设 SA_RESTART */
    if (sigaction(SIGALRM, &sa, NULL) == -1) return 1;

    char buf[256];
    int a[2], b[2], c[2];
    int e = 0;
    ssize_t n;

    /* 1) 短读：请求 256，管道里只有 100，写端已关 */
    if (pipe(a) == -1) return 1;
    memset(buf, 'z', 100);
    if (write(a[1], buf, 100) != 100) return 1;
    close(a[1]);
    n = read_full(a[0], buf, sizeof buf, &e);
    printf("1 short read  -> %zd retries=%d\n", n, e);
    n = read_full(a[0], buf, sizeof buf, &e);
    printf("2 eof         -> %zd retries=%d\n", n, e);
    close(a[0]);

    /* 2) EINTR：子进程 2 秒后写入，父进程阻塞读，1 秒时被闹钟打断 */
    if (pipe(b) == -1) return 1;
    pid_t pid = fork();
    if (pid == 0) {
        close(b[0]);
        usleep(2000000);
        if (write(b[1], "OK", 2) != 2) _exit(1);
        _exit(0);
    }
    close(b[1]);
    double t0 = now_ms();
    alarm(1);
    e = 0;
    n = read_full(b[0], buf, 2, &e);
    alarm(0);
    printf("3 eintr       -> %zd retries=%d elapsed=%.0fms alarms=%d\n",
           n, e, now_ms() - t0, (int)alarms);
    close(b[0]);
    waitpid(pid, NULL, 0);

    /* 3) EAGAIN：非阻塞读空管道，必须立刻返回，不能自旋 */
    if (pipe(c) == -1) return 1;
    set_nonblock(c[0]);
    e = 0;
    t0 = now_ms();
    n = read_full(c[0], buf, sizeof buf, &e);
    printf("4 eagain      -> %zd errno=%s retries=%d elapsed=%.3fms\n",
           n, strerror(errno), e, now_ms() - t0);

    /* 4) 短写：非阻塞写 1 MiB 进没人读的管道 */
    set_nonblock(c[1]);
    static char big[1 << 20];
    memset(big, 'x', sizeof big);
    size_t done = 0;
    ssize_t w = write_full(c[1], big, sizeof big, &done);
    printf("5 short write -> %zd errno=%s written=%zu of %zu\n",
           w, strerror(errno), done, sizeof big);
    close(c[0]);
    close(c[1]);

    /* 5) 睡眠被闹钟打断：用剩余时间接着睡 */
    t0 = now_ms();
    alarm(1);
    int calls = sleep_full(3000);
    alarm(0);
    printf("6 sleep       -> calls=%d elapsed=%.0fms alarms=%d\n",
           calls, now_ms() - t0, (int)alarms);
    return 0;
}
```

```bash
$ cc -std=c17 -Wall -Wextra -Werror -O2 -o lab1c10_robust lab1c10_robust.c && ./lab1c10_robust

2 eof         -> 0 retries=0
```

连跑几次，时间那三处只在 2000–2010 ms、0.003–0.007 ms、3000–3010 ms 之间浮动，其余数值完全一致。

- 第 1 行：请求 256 字节，管道里只有 100 且写端已关，`read_full` 读到 EOF 收工，返回 100。`retries=0` 说明它没白转圈。
- 第 2 行：同一读端再读，返回 0，`read_full` 直接返回 0。0 与 100 的差别只有调用者关心：前者是「没有了」，后者是「只给了这么多」。
- 第 3 行：`retries=1` 是本节唯一一次真重试。第一次 `read` 在第 1 秒被 `SIGALRM` 打断，函数内部 `continue`；第二次阻塞到第 2 秒，子进程写入后拿到 2 字节。`elapsed=2005ms` 说明它确实等满了 2 秒，而不是提前返回。
- 第 4 行：非阻塞读空管道，`read_full` 把 `EAGAIN` 原样交出。`elapsed=0.007ms` 是关键证据——它立刻返回，没有自旋。
- 第 5 行：请求 1 MiB，只写进 65536 字节就把管道填满，剩下的遇到 `EAGAIN`。`done=65536` 告诉调用者续写要从哪里开始。
- 第 6 行：3 秒的睡眠被闹钟打断 1 次（`alarms=2` 是因为前面第 3 行已经响过一次），`sleep_full` 用剩余时间接着睡，总耗时仍是 3007 ms。

第 3 行与第 4 行是两条规则的分界：`EINTR` 能证明「没有进展、重试安全」，库函数自己吞；`EAGAIN` 需要等待策略（等多久、等谁、超时怎么办），只能交回调用者。库函数替调用者忙等，等于把「怎么等」这个决定藏进一个看不见的循环。

第 5 行还暴露了本程序的一个缺陷：`write_full` 用 `done` 带出了进度，`read_full` 只返回 -1，遇到 `EAGAIN` 时前面读到的字节数就丢了。生产代码要么让它也带出 `done`，要么在调用前保证 fd 是阻塞的。同一套接口，读和写的进度语义要对齐，否则调用者没法判断「重来一次会不会重复处理」。

::: errata 这是四个容易踩的点
1. **「`EINTR` 重试时把缓冲区倒回开头」**——单次调用被打断确实一个字节没搬，但外层循环可能已经搬了几轮；指针从头再读会重复处理已收下的数据。
2. **「`EAGAIN` 也该原地重试」**——那是忙等。实测非阻塞读 0.007 ms 就返回，正确做法是交给 `epoll`，等可读通知。
3. **「`read_full` 返回 -1 就说明什么都没读到」**——它可能已读到一部分，最后一步才遇到 `EAGAIN`；第 5 行的写法就有这个隐患。
4. **「`nanosleep` 被打断就重睡整段」**——要用 `rem` 里的剩余时间；第 6 行 `calls=1`、总耗时仍是 3 秒。
:::

### 1.10.11 小结

① `EINTR` 在库函数里吞掉并计数，`EAGAIN` 原样抛出，短读短写靠循环补足，EOF 只认返回 0；② 进度要用返回值或出参带出来，否则调用者不知道「续到哪」；③ 睡眠类调用被打断后要用剩余时间接着睡。如果只记住一件事，那就是：**能自己证明「重试安全」的错误才重试，其余交给调用者。**

**Q1（记忆）** `read_full` 遇到 `EINTR` 和 `EAGAIN` 分别怎么处理？为什么不同？

**Q2（辨析）** 第 5 行 `write_full` 返回 -1，`done=65536`。调用者接下来该做什么？

**Q3（应用）** 把第 3 行的 `alarm(1)` 删掉，程序会怎样？把 `sa_flags` 改成 `SA_RESTART` 又会怎样？

**Q4（迁移）** 一个 `epoll` 服务器用 `read_full` 读请求，某次返回 -1/`EAGAIN` 但已经读到 30 字节。直接丢弃重来会出什么问题？

::: sol 答案
**A1** `EINTR` 重试（`continue`），因为内核没搬任何数据，重试不会重复；`EAGAIN` 返回 -1 交给调用者，因为要等事件，库函数不该替它决定等多久。
**A2** 从 `buf + done` 继续写剩下的 983040 字节；若是非阻塞 fd，就挂一个可写事件，等通知再续，而不是原地重试。
**A3** 两种改法都实测 `retries=0`、`elapsed≈2008 ms`：没有闹钟时一直阻塞到子进程写入；`SA_RESTART` 时闹钟照样响了（`alarms=1`），但 `read` 被内核重启，没返回 `EINTR`。
**A4** 那 30 字节已经从管道读走，丢弃就丢了请求开头，下一次读从中间开始，解析会错位。要么让 `read_full` 带出进度，要么把已读部分留在自己的缓冲里等下次拼接。

## 1.10.12 完整程序二：read/write 与零拷贝复制对照 {#sec-1.10.12}

这一节回答：同一个文件复制一遍，`read`/`write`、`copy_file_range`、`sendfile` 各发多少次系统调用？省下来的到底是哪一段？

1.10.7 已经给过选型表和四项成本；这里不重讲选型，只把三条路径写成同一份可编译代码，真跑一遍，用系统调用次数说话。

::: preview 先抓住一件事
`read`/`write` 复制 64 MiB 要 2048 次系统调用（64 KiB 一块，读一次写一次）；`copy_file_range` 和 `sendfile` 各只要 **1 次**。省掉的不是数据本身，而是「用户态缓冲区」这一段来回，以及跟着它走的系统调用。耗时在本机抖得厉害，不能当结论；次数是稳定的。

### 三条路径，同一份代码

三个函数只差中间那一行：`read`+`write` 走用户缓冲区，另两条让内核自己搬。调用次数各自计数，最后由 `main` 打印。

```c
/* lab1c10_copy2.c：read/write、copy_file_range、sendfile 复制同一文件 */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <sys/sendfile.h>
#include <sys/stat.h>
#include <time.h>
#include <unistd.h>

static double now_sec(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec + (double)ts.tv_nsec / 1e9;
}

/* 三条路径共用：打开源与目标；返回 -1 表示打开失败 */
static int open_pair(const char *src, const char *dst, int *in, int *out)
{
    *in = open(src, O_RDONLY);
    *out = open(dst, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    return (*in < 0 || *out < 0) ? -1 : 0;
}

static double copy_rw(const char *src, const char *dst, off_t size, long *calls)
{
    static char buf[1 << 16];
    int in, out;
    if (open_pair(src, dst, &in, &out) == -1) return -1;
    double t0 = now_sec();
    off_t left = size;
    *calls = 0;
    while (left > 0) {
        ssize_t r = read(in, buf, sizeof buf);
        (*calls)++;
        if (r <= 0) break;
        for (ssize_t off = 0; off < r; ) {          /* 短写：接着写 */
            ssize_t w = write(out, buf + off, (size_t)(r - off));
            (*calls)++;
            if (w <= 0) goto done;
            off += w;
        }
        left -= r;
    }
done:
    close(in);
    close(out);
    return now_sec() - t0;
}

static double copy_cfr(const char *src, const char *dst, off_t size, long *calls)
{
    int in, out;
    if (open_pair(src, dst, &in, &out) == -1) return -1;
    double t0 = now_sec();
    off_t left = size;
    *calls = 0;
    while (left > 0) {
        ssize_t n = copy_file_range(in, NULL, out, NULL, (size_t)left, 0);
        (*calls)++;
        if (n <= 0) break;
        left -= n;
    }
    close(in);
    close(out);
    return now_sec() - t0;
}

static double copy_sf(const char *src, const char *dst, off_t size, long *calls)
{
    int in, out;
    if (open_pair(src, dst, &in, &out) == -1) return -1;
    double t0 = now_sec();
    off_t left = size;
    *calls = 0;
    while (left > 0) {
        ssize_t n = sendfile(out, in, NULL, (size_t)left);
        (*calls)++;
        if (n <= 0) break;
        left -= n;
    }
    close(in);
    close(out);
    return now_sec() - t0;
}

int main(int argc, char **argv)
{
    if (argc < 3) return 1;
    struct stat st;
    if (stat(argv[1], &st) == -1) return 1;
    off_t size = st.st_size;
    long c = 0;
    double t;

    t = copy_rw(argv[1], argv[2], size, &c);
    printf("read/write      %.3fs  %ld calls\n", t, c);
    t = copy_cfr(argv[1], argv[2], size, &c);
    printf("copy_file_range %.3fs  %ld calls\n", t, c);
    t = copy_sf(argv[1], argv[2], size, &c);
    printf("sendfile        %.3fs  %ld calls\n", t, c);
    return 0;
}
```


`read` 与 `write` 各比程序自己数的多 1 次。加上 `-y` 重跑，能看到那一次 `read` 是动态链接器读 `libc.so.6` 的 ELF 头（832 字节），那一次 `write` 是退出前把三行结果一次刷出。真正的搬运仍是 1024 + 1024。

省掉的到底是哪一段：`read`/`write` 把数据从 page cache 拷进你的缓冲区，再从缓冲区拷回目标文件的 page cache，每块都要两次陷入内核；`copy_file_range` 与 `sendfile` 在 page cache 与目标之间直接搬，用户态只发一次请求。前者的成本随块数线性增长，后者的系统调用成本是一次性的。

把三条路径摊开看：`read`/`write` 是「磁盘 → page cache → 你的缓冲区 → 目标 page cache → 磁盘」，用户态那一段来回各一次；`copy_file_range` 在同一个文件系统内可以让内核直接复制页（btrfs/XFS 上甚至走 reflink，几乎不搬数据），跨文件系统则可能返回 `EXDEV`；`sendfile` 原本为「文件 → socket」设计，把 page cache 的页直接挂到发送队列。三者都不改变「数据最终要落到目标」这件事，只改变中间经过谁的手。

时间那一列**不能当结论**。本机连跑几次，`read/write` 在 0.011–0.095 s 之间跳（`strace` 下是 0.095 s，因为每次调用都被记录），`copy_file_range` 在 0.007–0.013 s 之间。要报吞吐，得先固定缓存状态、对齐块大小、取多次的中位数；本节只报次数，因为次数是确定的。

::: errata 零拷贝的五个误解
1. **「零拷贝就是一次拷贝都没有」**——磁盘到 page cache 的 DMA 搬运仍在，网卡不支持 scatter-gather 时也可能多一次；省掉的是**内核态与用户态之间**那一次。
2. **「`sendfile` 的 `out` 必须是 socket」**——2.6.33 起可以是普通文件，本实验就是文件到文件。
3. **「`copy_file_range` 一定比 `read`/`write` 快」**——实测两者在同一量级来回跳；它省的是系统调用与用户态拷贝，不承诺吞吐。
4. **「系统调用次数与块大小无关」**——`read`/`write` 的次数 ≈ 文件大小 ÷ 缓冲大小 × 2；缓冲从 64 KiB 调到 1 MiB，64 MiB 的文件就只剩 128 次。
5. **「`copy_file_range` 返回 0 表示出错」**——0 表示源文件已到末尾，循环该结束了；出错才返回 -1。
:::

### 1.10.12 小结

① `read`/`write` 复制 64 MiB 要 2048 次系统调用，`copy_file_range` 与 `sendfile` 各 1 次；② 省掉的是「page cache ↔ 用户缓冲区」这一段来回和随之而来的陷入次数，不是数据本身；③ 耗时在本机抖动大，只能报次数，报吞吐要先固定缓存与块大小。如果只记住一件事，那就是：**零拷贝省的是「经过用户态」这件事，不是「搬数据」这件事。**

## 1.10.13 完整程序三：不拼长路径的目录遍历 {#sec-1.10.13}

这一节回答：`snprintf` 拼出来的路径为什么会「太长」？为什么「先拼路径再 `stat`」在并发改名与符号链接面前会读到别的东西？`openat` 一族怎么把「一个长字符串」换成「锚点 + 名字」？

::: preview 先抓住一件事
路径在系统调用里不是字符串，而是**一串「目录 fd + 名字」**。`open("/a/b/c")` 让内核从根开始逐段解析；`openat(dirfd, "c")` 从你手上的目录出发只解析最后一段。后者让每段名字都短、让「检查的目录」与「使用的目录」是同一个对象，也让符号链接环在 `O_NOFOLLOW` 面前直接失败而不是无限下钻。
:::

先看失败现场。下面这个朴素遍历器用 `snprintf` 把父路径和目录项拼起来，再 `stat`：

```c
/* naive walk：拼路径 + stat，仅用于对照 */
char buf[PATH_MAX];
int n = snprintf(buf, sizeof buf, "%s/%s", path, e->d_name);
if (n >= (int)sizeof buf) { /* 路径太长 */ }
```

在本机造一棵 22 层、每层目录名 200 字节的树（最深那条相对路径 4439 字节），两个实现跑同一棵树：

```text
# 实测（Ubuntu 24.04.5 aarch64，GCC 13.3）
$ ./naive_walk lab1c10_deep
path too long at depth 20 (need 4233)
dirs=20 files=0

$ ./walk lab1c10_deep
root   : lab1c10_deep
dirs   : 22
files  : 1 (4 bytes)
links  : 0
others : 0
```

朴素版在第 20 层就拼不下了：`PATH_MAX` 是 4096，`need 4233` 直接超限；就算没超，它每层都要重新解析整条路径，中间任何一层被改名，后面的 `stat` 就可能落到另一个对象上。`openat` 版一路下钻，路径从不变长——它拿着的始终是「当前目录的 fd」。

```c

/* walk.c：用 openat/fdopendir 遍历目录树，不拼长路径、不跟随符号链接 */
#ifndef _GNU_SOURCE
#define _GNU_SOURCE
#endif
#include <dirent.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <unistd.h>

#define MAX_DEPTH 32

struct totals {
    unsigned long dirs, files, links, others;
    unsigned long long bytes;
};

static void walk(int dfd, int depth, struct totals *t)
{
    DIR *d = fdopendir(dfd);            /* 接管 fd 的所有权 */
    if (d == NULL) {
        close(dfd);
        return;
    }

    struct dirent *e;
    while ((e = readdir(d)) != NULL) {
        if (strcmp(e->d_name, ".") == 0 || strcmp(e->d_name, "..") == 0)
            continue;

        struct stat st;
        /* 关键：相对 dirfd 解析，且不跟随符号链接 */
        if (fstatat(dirfd(d), e->d_name, &st, AT_SYMLINK_NOFOLLOW) == -1)
            continue;

        if (S_ISDIR(st.st_mode)) {
            t->dirs++;
            if (depth + 1 >= MAX_DEPTH) {
                fprintf(stderr, "达到深度上限，跳过：%s\n", e->d_name);
                continue;
            }
            int sub = openat(dirfd(d), e->d_name,
                             O_RDONLY | O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC);
            if (sub == -1) {
                perror(e->d_name);      /* 权限不足等：记录后继续 */
                continue;
            }
            walk(sub, depth + 1, t);    /* walk 内部会关闭 sub */
        } else if (S_ISREG(st.st_mode)) {
            t->files++;
            t->bytes += (unsigned long long)st.st_size;
        } else if (S_ISLNK(st.st_mode)) {
            t->links++;
        } else {
            t->others++;
        }
    }
    closedir(d);                        /* 同时关闭底层 dirfd */
}

int main(int argc, char **argv)
{
    const char *root = argc > 1 ? argv[1] : ".";
    int fd = open(root, O_RDONLY | O_DIRECTORY | O_CLOEXEC);
    if (fd == -1) {
        perror("open");
        return 1;
    }

    struct totals t = {0};
    walk(fd, 0, &t);

    printf("root   : %s\n", root);
    printf("dirs   : %lu\n", t.dirs);
    printf("files  : %lu (%llu bytes)\n", t.files, t.bytes);
    printf("links  : %lu\n", t.links);
    printf("others : %lu\n", t.others);
    return 0;
}
```

三个设计点：

1. **`O_NOFOLLOW`**：如果目录项其实是符号链接，`openat` 返回 `ELOOP`，不会跑到目标目录里形成环。遍历不可信目录树时必须加——但注意它只管**最后一段**，路径中间段的符号链接要靠逐层 `openat` 自然挡住。
2. **`fdopendir` 接管 fd**：成功后不能再 `close(dfd)`，`closedir` 会关；失败时 fd 仍归调用者。这是最容易写错的所有权转移，写错就是双重关闭或 fd 泄漏。
3. **递归深度上限**：符号链接被挡住了，但硬链接目录（需要 root）和极深目录仍可能耗尽栈或 fd。生产工具通常用显式栈而不是递归。

::: ex 例 1.10.13 · 先猜哪一层会失败 {#ex-1.10.13}
同一棵 22 层、每层 200 字节目录名的树：朴素版会在第几层失败？`openat` 版会不会因为「路径总长超过 `PATH_MAX`」而失败？如果树里有一个指回上层的符号链接，两个版本各会怎样？

::: sol 解答
朴素版在第 20 层失败：前 20 层每层约 201 字节（200 名字 + 1 斜杠），加根名约 12 字节，`snprintf` 需要 4233 字节，超过 4096。`openat` 版不会失败：它每次只处理一个目录项的名字（200 字节，远小于单段上限 255），累积的「路径」只是内核里的一串 dentry，不受 `PATH_MAX` 约束——实测 22 层全部走完，`dirs=22 files=1`。符号链接环：朴素版用 `stat` 会跟随链接，回到上层后再次进入，直到耗尽 fd 或栈；`openat` 版在打开该目录项时因 `O_NOFOLLOW` 直接拿到 `ELOOP`，把它记进 `links` 不进入——在带 `loop` 与 `dangling` 的测试树上实测 `links: 2`。
:::
:::

::: errata 两个容易记反的边界
1. **`PATH_MAX` 不是「文件系统真实上限」**：它是单一系统调用里路径字符串的长度上限（Linux 上 4096），相对路径与逐段 `openat` 都可以绕开它；真正的单段名字上限是 255 字节。
2. **`O_NOFOLLOW` 只管最后一段**：`openat(dirfd, "a/b")` 里 `a` 是符号链接不会被它拦住；要全程不跟随，就逐层 `openat` 并每层都带这个标志。
:::

### 1.10.13 小结

把路径当成字符串拼，是在跟三个东西作对：长度上限、并发改名、符号链接环。`openat` 一族把它们逐个拆掉——名字变短、锚点固定、环被标志挡住。如果只记住一件事，那就是：**「我检查的那个目录」和「我接下来用的那个目录」必须是同一个 fd**。

::: method 即时自测 · 1.10.13

**Q2（判断）** 一个遍历器对每个目录项调用 `stat(path)` 判断类型。在「遍历期间有人不断改名」的目录里，它可能出什么错？换成 `openat + fstat` 后消失的是哪一类？

## 1.10.14 实验一：用 strace 看缓冲、短读与 write 合并 {#sec-1.10.14}

这一节回答：`printf` 到底发了几次 `write`？`strace` 的三个开关（`-c`、`-e trace=`、`-y`）各回答哪个问题？「短读」在系统调用层长什么样？

::: preview 先抓住一件事
用户态看到的是「一次 `printf`」，内核看到的是「一次 `write`」，两者之间隔着一层 stdio 缓冲。`strace` 的位置就在这条缝上：它数的是**系统调用**，不是函数调用。看懂这一点，你就不会再把「`printf` 很慢」和「`write` 很多次」混为一谈。
:::

先准备一个小程序：同样的 300 行，一种走 stdio，一种每行直接 `write`：

```c
/* buf.c：mode 0 走 fwrite（全缓冲），mode 1 每行一次 write */
char line[64];
for (int i = 0; i < 300; i++) {
    int n = snprintf(line, sizeof line, "line %03d\n", i);
    if (mode == 0) fwrite(line, 1, n, stdout);
    else           if (write(1, line, n) < 0) return 1;
}
```

**步骤 1：数 `write` 的次数**

```bash
cc -O2 -o buf buf.c
strace -c -e trace=write ./buf 0 > /dev/null
strace -c -e trace=write ./buf 1 > /dev/null
```

```text
# 实测（Ubuntu 24.04.5 aarch64，GCC 13.3）
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
100.00    0.000000           0         1           write      ← mode 0
100.00    0.002320           7       300           write      ← mode 1
```

300 行的总字节数是 2700，小于 glibc 默认的 4 KiB 缓冲，所以 mode 0 只在退出时刷一次；mode 1 每行一次，正好 300 次。**把输出接到终端再跑一次，mode 0 会变成 300 次**——终端是行缓冲，这就是 `_IOFBF` 与 `_IOLBF` 的差别。

**步骤 2：让 fd 号带上路径**

```bash
strace -y -e trace=openat,write ./buf 0 > /dev/null
```

```text
openat(AT_FDCWD</tmp>, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3</etc/ld.so.cache>
openat(AT_FDCWD</tmp>, "/lib/aarch64-linux-gnu/libc.so.6", O_RDONLY|O_CLOEXEC) = 3</usr/lib/aarch64-linux-gnu/libc.so.6>
write(1</dev/null>, "line 000\nline 001\nline 002\nline "..., 2700) = 2700
```

`-y` 把 3 号 fd 翻译成 `/etc/ld.so.cache`、把 1 号翻译成 `</dev/null>`。排查「到底写到了哪个文件」「这个 fd 是谁打开的」时，它比读代码快得多；注意同一次程序运行里 fd 号会被复用（两个 `openat` 都返回 3），所以**不能只凭 fd 号追踪对象**，要看它当时的绑定。

**步骤 3：短读长什么样**

`cat` 用 128 KiB 缓冲，读一个 12813 字节的文件：

```text
read(3, "# Network servic"..., 131072)  = 12813
read(3, "", 131072)                     = 0
```

第一次返回 12813 而不是 131072，这不是错误：文件就那么大，`read` 读到结尾就返回实际字节数。再读一次返回 0，才是 EOF。管道的短读更明显——父进程分两次写、子进程每次 `read` 64 字节，实测：

```text
first read: n=5 data=hello
second read: n=5 data=world
third read (EOF): n=0
```

**步骤 4：聚合表与它的边界**

```bash
strace -c ./buf 0 > /dev/null
```

输出按系统调用聚合：`openat` 2 次、`close` 2 次、`ioctl` 与 `faccessat` 各 1 次（libc 的 locale 探测）。**`strace` 会把每次系统调用放大几十倍**，这张表只能用来数次数与找意外调用，不能用来测性能。

::: errata 三个常见读错
1. **「`printf` 慢」不等于「`write` 多」**：缓冲命中时根本没有系统调用；反过来，`write` 多也不一定慢（可以合并成一次大写入）。
2. **`strace -c` 的 `seconds` 不是程序耗时**：它统计的是被追踪调用的耗时，且含 ptrace 开销。
3. **`-y` 只对「当前有 fd 的对象」有效**：已经 `close` 的 fd 显示不出路径，fd 号复用后也可能指向新对象。
:::

### 1.10.14 小结

`strace` 把「函数调用」与「系统调用」分开给你看：缓冲决定了两者的比例，短读与 EOF 是返回值的语义，`-y` 与 `-c` 是两个不同视角的索引。如果只记住一件事，那就是：**调 `strace` 之前先说清你要数的是次数、是对象、还是耗时——三者要用不同开关。**

::: method 即时自测 · 1.10.14
**Q1（记忆）** 同样 300 行输出，为什么重定向到文件时 `write` 只有 1 次，接到终端时变成 300 次？

**Q2（判断）** `strace -c` 显示某程序 `read` 用了 3 秒，能否断定程序的 I/O 是瓶颈？为什么？

**Q3（实验）** 用 `strace -y` 观察一个打开两个文件又都关掉的程序，说明为什么「两次 `openat` 都返回 3」不是错误。

::: sol 答案
**A1** 重定向到文件时 stdout 是全缓冲（4 KiB），300 行共 2700 字节，攒满之前不落地，退出时一次刷出；终端是行缓冲，遇到 `\n` 就调用一次 `write`，所以 300 行 300 次。

**A3** fd 号是「进程内最小可用编号」，关掉后会被下一次 `open` 复用。两次 `openat` 都返回 3 说明第一次的 3 已被 `close`，不是内核出错；要追踪对象得看每次 open 的返回值与 `-y` 翻译出的路径绑定。
:::

## 1.10.15 实验二：page cache、O_DIRECT 与 fsync 的证据 {#sec-1.10.15}

这一节回答：怎么**证明**第二次读没碰磁盘，而不是靠「感觉快了」？`O_DIRECT` 想绕开的是哪一层、绕开了多少？`write` 返回成功与数据落盘之间隔着什么？

::: preview 先抓住一件事
内核给每个进程记账：`rchar` 数「你读了多少字节」，`read_bytes` 只数「真正发给块设备的字节」。两个数一减，就是 page cache 替你挡下来的量。这一节的所有结论都用这两个计数和 `/proc/meminfo` 的 `Dirty` 说话，不用「应该会」。
:::

**步骤 1：同一个文件读三遍，看 `rchar` 与 `read_bytes`**

```c
/* io.c：连续读三遍，每遍后打印 /proc/self/io 的四个字段 */
size_t got = 0; ssize_t n;
while ((n = read(fd, buf, 1<<20)) > 0) got += n;
```

```text
# 实测（Ubuntu 24.04.5 aarch64，ext4，/usr/bin/dockerd 79,791,520 字节）
-- after read pass 1 --
rchar: 81156308
read_bytes: 0
-- after read pass 2 --
rchar: 160947936
read_bytes: 0
```

两遍读的 `rchar` 各涨约 8000 万字节，而 `read_bytes` 始终是 **0**——说明这两遍一个字节都没发给块设备，全部由 page cache 提供。同一文件连读三次的墙钟也印证这一点：

```text
pass 1: 79791520 bytes, 0.0339 s (2354.3 MB/s)
pass 2: 79791520 bytes, 0.0044 s (18290.0 MB/s)
pass 3: 79791520 bytes, 0.0043 s (18664.9 MB/s)
```

第一次 2354 MB/s 已经含了一部分缓存（这个文件此前被读过），第二、三次 18 GB/s 是纯内存带宽的量级。**结论要这样下**：`read_bytes == 0` 才是「没碰磁盘」的证据，墙钟只是旁证。

**步骤 2：`O_DIRECT` 把 `read_bytes` 打出来**

同一程序用 `O_DIRECT` 读 1 MiB（缓冲区必须页对齐，`posix_memalign`）：

```text
O_DIRECT read: 1048576
-- after O_DIRECT read --
rchar: 161996621          （+1,048,576）
read_bytes: 1048576       （+1,048,576）
```

`rchar` 与 `read_bytes` 同时增加 1 MiB：这一读真的下去了。`O_DIRECT` 绕开的是 **page cache**，不绕开文件系统与块层——它保证数据直接从设备进出你的缓冲区，代价是对齐要求与失去缓存加速。

**步骤 3：`write` 返回 ≠ 落盘**

```text
# 64 MiB 顺序写 + fsync（实测）
write 67108864 bytes: 0.017 s, fsync: 0.004 s
```

`write` 只把数据拷进 page cache 就返回；`fsync` 才等它落到设备。这里 `fsync` 比 `write` 还快，是因为这块盘本身很快、且写是顺序的——**单次测量不能下「fsync 很便宜」的结论**，要看 `Dirty` 堆积：

```bash
grep -E 'Dirty|Writeback' /proc/meminfo
```

`Dirty` 是待回写字节数，`Writeback` 是正在回写的字节数。大量写入后 `Dirty` 会涨到几十上百 MB，随回写线程工作再降下来；`fsync` 的作用就是「等到这个文件的脏页清零」，而不是「立刻把整机脏页都刷掉」。

::: errata 三处容易讲错
1. **「第二次读快是因为 CPU 缓存」**：CPU 缓存只有几 MB，读 80 MB 文件时它装不下；快的是 page cache（内存），证据就是 `read_bytes == 0`。
2. **「`O_DIRECT` 等于绕过内核」**：它只绕 page cache，仍要过 VFS（内核里文件系统之上的统一接口层）、文件系统与块层，也仍要遵守对齐约束。
3. **「`sync` 与 `fsync` 一样」**：`fsync(fd)` 只保证这一个文件的脏页落盘（含元数据），`sync()` 是整机；生产代码用前者。
:::

### 1.10.15 小结

`/proc/self/io` 的 `rchar` 与 `read_bytes` 之差是 page cache 的账本；`O_DIRECT` 把这块账本关掉，让每一次读都出现在 `read_bytes` 里；`fsync` 等的正是那份账清零。如果只记住一件事，那就是：**判断「有没有碰磁盘」看 `read_bytes`，别看墙钟。**

::: method 即时自测 · 1.10.15
**Q1（记忆）** `rchar` 与 `read_bytes` 各统计什么？什么情况下两者相等？

**Q2（判断）** 一个进程读 1 GiB 文件，`rchar` 涨了 1 GiB，`read_bytes` 只涨 8 MiB。这说明什么？下一次读会更快还是更慢？

**Q3（实验）** 用 `O_DIRECT` 读一个 1 MiB 缓冲区但不用 `posix_memalign` 对齐，会发生什么？给出 `errno` 与原因。

::: sol 答案
**A1** `rchar` 统计 `read`/`recv` 等调用返回的字节总数（用户态看到的量）；`read_bytes` 统计真正从块设备读入的字节数（page cache 缺失才增加）。当缓存全不命中、每次读都下到设备时两者相等；`O_DIRECT` 下也基本相等（除了元数据）。

**A2** 说明绝大部分由 page cache 提供，只有 8 MiB 真正从设备读入（可能是冷页或预读边界）。若文件仍被缓存，下一次读更快；但缓存可能被别的 I/O 挤掉，所以「更快」不是保证——要看 `/proc/meminfo` 的 `Cached` 与内存压力。

**A3** `read` 返回 `-1`，`errno` 为 `EINVAL`：`O_DIRECT` 要求缓冲区地址、长度与文件偏移按逻辑块大小（通常 512 或 4096 字节）对齐，未对齐的缓冲会被直接拒绝。
:::

## 1.10.16 十三条系统级 I/O 陷阱 {#sec-1.10.16}

这一节回答：这些坑里，哪几个会**静默丢数据**、哪几个会**静默挂死**、哪几个只是**看起来慢**？遇到其中一条，先跑哪条命令确认？

::: preview 先抓住一件事
系统级 I/O 的坑几乎都能归到四句话：**返回值不等于请求**（短读短写）、**成功不等于生效**（缓冲与 page cache）、**关了不等于没了**（fd 复用与多线程）、**写了不等于落了**（fsync 与目录项）。按这四句归类，十三条就不用背。
:::

| # | 现象 | 原因 | 修复 |
|--:|:--|:--|:--|
| 1 | `read` 只返回一部分就继续解析 | 把短读当成完整报文 | 循环读到所需长度或 EOF |
| 2 | `write` 返回小于请求长度被忽略 | 管道/socket 缓冲区不足 | 循环写，非阻塞时等 `EPOLLOUT` |
| 3 | 收到信号后程序退出 | 把 `EINTR` 当致命错误 | 重试；或 `SA_RESTART` |
| 4 | 非阻塞读把 `EAGAIN` 当 EOF | 混淆「暂无数据」与「对端关闭」 | `EAGAIN` 等事件，`0` 才是 EOF |
| 5 | `close` 后仍用 fd | fd 号被新 `open` 复用 | 关闭后置 -1；用 RAII/`goto cleanup` |
| 6 | 多线程下 `dup2` 覆盖别人的 fd | 关闭与复制不是原子的组合 | 用 `dup3`，或加锁并集中管理 |
| 7 | `fork` 后子进程重复输出 | 继承了 stdio 缓冲且调用 `exit` | 子进程用 `_exit` |
| 8 | 混用 `FILE *` 与 `read` 丢数据 | stdio 预读把 fd 偏移推前 | 切换前 `fflush`/`fseek`，或统一接口 |
| 9 | 日志行交错 | 一条日志分多次 `write` | 拼成一次 `write`；`O_APPEND` 只保证单次原子 |
| 10 | 重定向顺序写反 | `2>&1 >out` 先复制再改 1 | 记牢「从左到右、复制当前值」 |
| 11 | `fsync` 后仍丢数据 | 只同步了文件，没同步目录项 | `rename` 后 `fsync` 父目录 fd |
| 12 | `O_DIRECT` 读失败 `EINVAL` | 缓冲区/偏移/长度未对齐 | 用 `posix_memalign`，按块大小对齐 |
| 13 | `EMFILE` 后 accept 空转 | 没有预留救急 fd | 预留 `/dev/null` fd，丢弃一个连接后补回 |

**第一组（1–4）：返回值语义。** 短读、短写、`EINTR`、`EAGAIN` 四件事的共同点是「系统调用说的是它做了多少，不是你要了多少」。先查什么：在调用点打印返回值与 `errno`，再看代码里有没有 `while` 循环把「要 N 字节」变成「读到 N 字节或 EOF」。

**第二组（5–7）：生命周期与所有权。** 关闭后的 fd 号会被复用，`dup2` 的「关闭 + 复制」不是一个原子动作，`fork` 之后子进程继承了 stdio 缓冲。先查什么：`grep` 每个 `close` 之后是否还有使用；子进程是否用 `_exit`；多线程里是否有共享的 fd 表结构。

**第三组（8–10）：缓冲与接口混用。** 混用 `FILE *` 与 `read` 会丢数据（stdio 预读把 fd 偏移推前），日志被拆成多次 `write` 会交错，重定向顺序写反会让 `stderr` 落到终端而不是文件。先查什么：同一 fd 上是否同时有 stdio 与原始 I/O；日志行是否一次 `write` 写出；重定向从左到右读一遍。

**第四组（11–13）：持久化与资源上限。** `fsync` 不覆盖目录项、`O_DIRECT` 未对齐报 `EINVAL`、`EMFILE` 之后 `accept` 空转。先查什么：`rename` 之后有没有 `fsync` 父目录；`O_DIRECT` 的缓冲区是否 `posix_memalign`；进程是否预留了一个救急 fd。

::: errata 三个关于「文件已写入」的误解
1. **「`write` 返回成功，进程崩溃也不丢」**——数据只在 page cache；进程崩溃不影响内核回写，但机器掉电会丢。要抗掉电必须 `fsync`。
2. **「`fsync` 一次就够」**——新建文件后 `fsync(fd)` 只保证数据与 inode；目录项（文件名）要 `fsync` 目录 fd 才持久。`rename` 原子替换的经典写法是「写临时文件 → `fsync` → `rename` → `fsync` 目录」。
3. **「`O_APPEND` 能保证多进程日志不交错」**——它只保证单次 `write` 的「定位到末尾 + 写」是原子的。一次日志若分成 `write(时间)`、`write(内容)`、`write(换行)` 三次，仍会与其他进程交错。
:::


### 1.10.16 小结

十三条按「返回值 / 生命周期 / 缓冲 / 持久化」四组归位之后，每组的排查起点都是同一条命令：看返回值、看 fd 归属、看缓冲状态、看落盘证据。如果只记住一件事，那就是：**系统调用只承诺它实际做了多少，剩下的部分要你的循环与检查来补齐。**

::: method 即时自测 · 1.10.16
**Q1（判断）** 一段代码 `write(fd, buf, len)` 返回 1024 而 `len` 是 65536，程序直接返回成功。它属于哪一组陷阱？先查什么？

**Q2（判断）** 服务重启后日志最后几行丢失，但进程是正常退出的。列出两条最可能的原因与对应的验证命令。

**Q3（实验）** 写一个「先 `fsync` 文件、再 `rename`」的程序，故意不同步目录，然后在 `rename` 后立刻掉电（可用 `echo b > /proc/sysrq-trigger` 模拟，需 root；没有 root 就说明为什么这一步做不到），说明可能的结果。

::: sol 答案
**A1** 第一组（返回值语义）。先查调用点有没有循环写；`write` 返回小于请求长度是合法的（管道/socket 缓冲不足、信号打断），必须继续写剩余部分，非阻塞时等 `EPOLLOUT`。

**A2** ① 日志没 `fsync`（或只在部分路径 `fsync`），数据停在 page cache，进程正常退出也不会落盘——用 `strace -e trace=write,fsync` 确认有没有 `fsync`；② 写的是临时文件 + `rename`，但没 `fsync` 父目录，崩溃后文件名回滚——用 `ls -li` 对比 inode 与 `ls` 时间，或在测试机上重现。

**A3** 没 root 时做不到真正的掉电模拟，只能说明机制：`fsync(fd)` 保证数据与 inode，`rename` 是原子的元数据操作，但「新名字」这一目录项本身要 `fsync` 父目录 fd 才持久。不同步目录就掉电，可能出现「旧名字还在、新名字没出现」或「两个名字指向不同 inode」；正确顺序是「写临时文件 → `fsync(tmpfd)` → `rename` → `fsync(dirfd)`」。
:::
:::

## 1.10.17 本章小结 {#sec-1.10.17}

这一节回答：这一章学完，你看到「文件」与「I/O」这两个词，能不能立刻分成三张图——**句柄的身份、数据的路径、错误的语义**？

::: preview 先抓住一件事
判据是：**给你一个「写进去了但读不到」「读到了但不对」「跑得好好的但 fd 用光」的现场，你能先说清是哪一层的问题，再挑一条命令去证实**，而不是先改缓冲大小。
:::

这一章的主线是**从一个 fd 到一条完整的数据路径**。1.10.1–1.10.4 立句柄：Unix I/O 的四个动作（`open`/`read`/`write`/`close`）、`stat` 与文件身份（`(st_dev, st_ino)` 才算「同一个文件」）、目录不是文本文件、RIO 怎样把短读短写与缓冲包起来。1.10.5–1.10.8 立路径与语义：共享偏移与 `dup2` 重定向、从 `write` 到磁盘要经过 page cache 与回写、三种接口（原始 I/O、stdio、零拷贝）的成本对照、以及 fd 表/打开文件表/引用计数这套完整语义。

1.10.9–1.10.12 是二刷与完整程序：返回值的四种情形（0、短、`EINTR`、`EAGAIN`）、`dup2` 的原子性与 `/proc/self/fd`、把四种返回值放进一个可编译程序、`read/write` 与零拷贝复制的对照。1.10.13–1.10.16 全部是实测：`openat` 遍历一棵相对路径 4439 字节的深树（朴素版在第 20 层 `path too long`，`openat` 版走完 22 层）；`strace` 数出 300 行 stdio 只有 1 次 `write`、逐行 `write` 是 300 次；`/proc/self/io` 证明热读 `read_bytes` 为 0、`O_DIRECT` 让 1 MiB 全部下设备；最后把十三类坑归成「返回值 / 生命周期 / 缓冲 / 持久化」四组。

逐条打勾的达标表在[学习目标自检表](ch10-checklist.md)。这里只留判据：

- **能解释**：短读为什么合法、`0` 与 `EAGAIN` 的区别、`write` 成功与落盘之间隔着什么、`dup2` 为什么要原子、`(st_dev, st_ino)` 为什么比路径可靠。
- **能操作**：写一个「读到 N 字节或 EOF」的循环；用 `strace -c -e trace=write` 数系统调用；用 `/proc/self/io` 的 `rchar`/`read_bytes` 判断有没有碰磁盘；用 `openat` 逐层遍历目录。
- **能判断**：该用 stdio、原始 I/O 还是零拷贝；日志该不该 `fsync`、`rename` 后要不要同步目录；`EMFILE` 出现时先查泄漏还是先调上限。

如果只记住一件事，那就是**系统调用只承诺它实际做了多少**：读了多少、写了多少、同步到哪一层，都要你用循环、返回值与 `fsync` 去补齐——本章每一个实验都是在给这句话找证据。

::: errata 本章的口径边界
1. **`O_DIRECT` 的可用性依文件系统而定**：本机 ext4 上 `open(..., O_DIRECT)` 成功，别的文件系统（如部分 tmpfs 与 overlayfs（联合挂载文件系统））会直接 `EINVAL`；不要把它当通用优化。
2. **`fsync` 的耗时无法用单次数值代表**：实测 64 MiB 顺序写后 `fsync` 只花 0.004 s，这是设备与写模式共同决定的；评估持久化成本要重复测量并看 `Dirty` 堆积。
3. **`ENFILE`/`EMFILE` 需要把系统或进程打满才能复现**，本章未实测；`EMFILE` 的行为（`accept` 空转）按接口语义描述，验证方法在习题集。
:::

**下一站**：文件是「已经有名字的数据」，下一章 [1.11 网络编程](ch11.md) 把同一套 fd 抽象套到 socket 上——`read`/`write` 换成 `send`/`recv`，短读短写变成字节流边界，`select`/`epoll` 让你同时照看很多条连接。

::: method 即时自测 · 1.10
**Q1（记忆）** `read` 返回 0、返回 -1 且 `errno==EAGAIN`、返回小于请求长度，三者各是什么意思？

**Q2（判断）** 两次 `open("/tmp/a")` 得到两个 fd，`stat` 的 `(st_dev, st_ino)` 相同。这两个 fd 共享文件偏移吗？`fork` 之后呢？

**Q3（实验）** 用 `strace -c -e trace=write` 比较「逐行 `printf`」与「一次 `fwrite` 拼好再写」的系统调用次数，并解释差异来源。

**Q4（判断）** 一个服务每处理一个连接就 `open` 一个日志文件却忘了 `close`。它最先出现什么错误？如何在不重启的情况下确认？

::: sol 答案
**A1** 0 是 EOF（对端关闭或读到文件尾）；-1 且 `EAGAIN` 是「暂无数据，稍后再来」（非阻塞）；返回小于请求长度是短读——正常现象，继续读剩余部分即可，不是错误。

**A2** 两次 `open` 得到两个独立的「打开文件表项」，各自有偏移，**不共享**；`fork` 之后父子共享同一打开文件表项，**共享偏移**（这是 `O_APPEND` 与 `dup2` 语义的基础）。

**A3** 逐行 `printf` 在行缓冲（终端）下每行一次 `write`，重定向到文件时全缓冲、几千行合成一次；一次 `fwrite` 拼好再写无论哪种模式都只有很少几次。差异来源是 stdio 的缓冲模式（`_IOLBF`/`_IOFBF`）与缓冲大小（默认 4 KiB）。

**A4** 最先出现 `EMFILE`（进程 fd 用光），随后 `accept`/`open` 全部返回 -1。确认方法：`ls /proc/<pid>/fd | wc -l` 与 `cat /proc/<pid>/limits | grep 'open files'` 对比，再按 fd 指向的路径统计（`ls -l /proc/<pid>/fd`）找出重复打开的同一文件。
:::
