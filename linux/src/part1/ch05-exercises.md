# 1.5 习题集

三组分层：A 组概念判断（口答即可）、B 组诊断推理（写出「现象 → 瓶颈类型 → 先测什么 → 怎么改」）、C 组动手实验（能在本机或 Linux 虚拟机里跑）。**全部附解答**；先独立完成，再展开对照。

## 怎么用

1. 先读题，不看解答，给自己 2–3 分钟找思路；
2. B 组务必把「瓶颈类型」写成五个候选之一：依赖链、load/store 转发、分支预测失败、缓存缺失、别名挡住向量化；
3. 卡住了回对应小节的「即时自测」重读，不要直接看答案；
4. C 组的每条命令都要真的跑，跑不通先看[勘误与版本注记](ch05-errata.md)的事件名与工具可用性；
5. 做错的题记一个记号，三天后只重做记号题，并去[自检表](ch05-checklist.md)勾对应行。

## A 组 · 概念判断

::: ex 例 1.5-A1 · 指令少了就等于快了吗 {#ex-1.5-A1}

有人把循环体从 10 条指令删到 8 条，宣称提速 25%。这句话错在哪？请用延迟、吞吐、CPE 三个概念说明「什么情况下删指令几乎没用」。

::: sol 解答

CPE 由「关键路径上的延迟」和「资源吞吐」中较大的那个决定，跟指令条数没有直接关系。若循环只有一个累加器，每元素的界就是那条加法链的延迟（浮点 4 周期），剩下 8 条指令全都能并行、不占关键路径——删掉两条仍然每 4 周期一次，实测可能一点不动。相反，把一条链拆成四条，指令总数反而增加，CPE 却可以从 4 降到约 1。**先看界由谁定，再决定要不要删指令。**
:::
:::

::: ex 例 1.5-A2 · `-O0` 上测出来的结论能不能推广 {#ex-1.5-A2}

在 `-O0` 下测得「手工展开快一倍」，为什么这个结论对发布版基本无效？正确的测法是什么？

::: sol 解答

`-O0` 不做寄存器分配、不做内联、每次访问都落内存，代码形态和 `-O2` 完全是两份程序；展开在那种形态下省掉的循环控制开销，在 `-O2` 下本来就不存在，而 `-O2` 自己可能已经向量化。正确做法：用与发布一致的 `-O2`（加 `-g` 方便定位），同一份数据、同一份校验，一次只改一个变量；再配一次 `-O2 -fno-tree-vectorize`，把「展开收益」和「向量化收益」拆开。
:::
:::

::: ex 例 1.5-A3 · 编译器敢不敢提升 strlen {#ex-1.5-A3}

三种循环体分别判断：编译器能否把 `strlen(s)` 提到循环外。① 循环体只调用 `process(s[i])`，而 `process` 是同一翻译单元里已定义的纯函数；② 循环体调用来自其他翻译单元的未知函数；③ `s` 被声明为 `volatile char *`。

::: sol 解答

① 可以：能看见定义、能证明不改写 `s`，等价于循环不变量外提。② 不行：跨翻译单元且没有 LTO 时，编译器不能证明被调函数不修改这段内存，只能每次重算。③ 不行：`volatile` 的语义就是「每次访问都必须真的发生」，它禁止缓存也禁止外提——这也是「`volatile` 只会让性能变差，不提供原子性与内存屏障」这条误解的来源。手工修法始终有效：先 `size_t n = strlen(s);`。
:::
:::

::: ex 例 1.5-A4 · 三句关于别名与类型的判断 {#ex-1.5-A4}

判断对错并说明理由：① `restrict` 只是提示，违反了最多是没优化；② 区间可能重叠时 `memcpy` 与 `memmove` 可以互换；③ 加 `-fno-strict-aliasing` 是免费的保险。

::: sol 解答

① 错。`restrict` 是程序员替编译器作的承诺，违反是未定义行为：编译器已经据此重排 load/store、向量化，结果可以在任何输入上都错。② 错。`memcpy` 的签名带 `restrict`，即承诺不重叠；重叠必须用 `memmove`。③ 错。它关掉一整类优化，热循环可能明显变慢；正确做法是修代码——用 `memcpy` 做按字节复制，或按 C11 用 `union` 类型双关（读取非活跃成员仍是实现定义）。
:::
:::

::: ex 例 1.5-A5 · 无分支什么时候更慢 {#ex-1.5-A5}

写出无分支绝对值，并给出两种「无分支反而更慢」的情形。为什么 `if (x < 0) ...` 不一定会生成分支？

::: sol 解答

`int mask = x >> 31; return (x ^ mask) - mask;`——负数掩码全 1，取反加一；非负掩码全 0。更慢的两种情形：① 一边代价很高——除法、函数调用，或者会缺页（那一页还没装进物理内存，要由内核把那页装进来）的访存，无分支要把两边都算出来；② 分支方向本来高度可预测，预测器几乎不出错，你却引入了双倍数据通路。`if` 不一定生成分支，因为编译器按代价模型选择：两个简单值常折成 `cmov`（x86）或条件选择（ARM64），也可能折成算术，看汇编而不是看源码写法。另外这个写法对 `INT_MIN` 仍取负溢出，是未定义行为。
:::
:::

::: ex 例 1.5-A6 · 分块一定更快吗 {#ex-1.5-A6}

正文 1.5.12 里 `block64` 没赢过 `ikj`。给出「该做分块」与「先别做分块」各一条判据，再说块大小怎么估。

::: sol 解答

该做分块：工作集明显大于末级缓存，或 `perf stat` 的 LLC-load-misses 很高；`B` 的访问步长是整行，缓存行利用率只有 1/8 这类结构性问题（缓存行是一次从内存搬进缓存的那一整块）。先别做：末级缓存很大、循环已经是流式连续访问（正文那台机器 `ikj` 已经约 8.32 GFLOP/s，分块的额外循环开销反而拖慢）。块大小按「同时驻留的几个块装得下目标层级」估：三个双精度块约 $3B_s^2 \times 8$ 字节，256 KiB 时 $B_s$ 约 100，取 64 或 96，并且要是缓存行大小的倍数；容量口径以目标机为准。
:::
:::

::: ex 例 1.5-A7 · Amdahl 与「先优化谁」 {#ex-1.5-A7}

热点占运行时间的 90%，被加速 10 倍，整体加速比是多少？这说明「先做微优化」错在哪？

::: sol 解答

$S = 1/((1-p)+p/s) = 1/(0.1+0.09) \approx 5.26$，不是 10。非热点的 $(1-p)$ 决定天花板：把只占 5% 的东西优化十倍，整体只有约 1.05 倍。所以顺序必须是先用 `perf record` 找热点（找出 $p$），再决定动哪一层；跳过定位直接改指令，就是在一个小 $p$ 上做文章。
:::
:::

::: ex 例 1.5-A8 · 展开的代价与一次只改一个变量 {#ex-1.5-A8}

列出展开过度带来的三种代价。设计一个实验，把「展开收益」与「向量化收益」分开。

::: sol 解答

三种代价：寄存器压力导致值被溢出回栈；代码体积增大、I-cache 命中率下降；尾部需要额外处理，循环次数不是展开因子倍数时更明显。实验设计：同一份代码跑三组——`-O2 -fno-tree-vectorize`（只看展开与调度）、`-O2`（展开加向量化）、`-O2 -fno-tree-vectorize` 且不展开（基线）。比较三组 CPE，就能算出展开贡献多少、向量化贡献多少；每次只改一个变量，并记录前后 CPE 与 IPC。
:::
:::

## B 组 · 诊断推理

每题给出五个候选瓶颈：**依赖链 / load-store 转发 / 分支预测失败 / 缓存缺失 / 别名挡住向量化**。写出你的判断、先测什么、怎么改。

::: ex 例 1.5-B1 · 指令删了一堆，时间不动 {#ex-1.5-B1}

一个浮点求和循环：`for (…) s += a[i] * b[i];`。你把取模、边界判断都消掉，指令数下降 20%，时间没变；`perf` 显示 IPC 约 1，分支失败率不到 1%，热点集中在一条 `addsd`。瓶颈是什么？怎么改？

::: sol 解答

**依赖链**。每次加法等上一次结果，界是浮点加法延迟 4；你删的是链外的指令，所以界不变——这正好解释「时间不动、IPC 也不动」。改法：用 4 个独立累加器，最后合并，界变成 $\max(4/4,\ 1/2)=1$；或者授权编译器重排浮点加法顺序。注意这会改变求和顺序，需要逐位一致时不能这么改。验收：CPE 从接近 4 落到接近 1，且 `perf annotate` 的热度从加法摊到多条链。
:::
:::

::: ex 例 1.5-B2 · 全部命中 L1，写读交织的循环还是慢 {#ex-1.5-B2}

循环先把结果写进 `p[i]`，紧接着从同一个 `p[i]` 读出来累加。缓存缺失几乎没有，分支也很规整，IPC 却很低。瓶颈是什么？两条改法？

::: sol 解答

**load/store 转发（写后读同地址的依赖链）**。store 不直接写缓存，先进 store buffer；load 必须等 store 的地址与数据就绪并判定是否同址，才能拿到值。于是这条链的延迟叠加进 CPE，而不是被 load 吞吐决定。改法：① 把这个值留在寄存器里参与累加，不绕内存一圈；② 拆成两个循环——先写完 `p[]`，再整段读来累加，让 store 在中间提交完。Linux 的 Intel 机器上可以用 `perf list` 找 store-forward 类事件并计数（正文标注为未实测口径，事件名因微架构而异）；没有 PMU 就用「拆开前后各测一次 CPE」来判定。
:::
:::

::: ex 例 1.5-B3 · 数据一排序就快了 {#ex-1.5-B3}

统计一段数据里满足某条件的元素个数：随机数据慢，先排序再统计反而快很多；缓存缺失和指令数两组几乎一样。瓶颈是什么？除了排序还有什么招？

::: sol 解答

**分支预测失败**。条件在随机数据上方向接近抛硬币，每次失败都要冲刷流水线（正文给的量级是十几到二十周期）；排序后条件变成「前段全真、后段全假」，几乎不失败。另外三招：把分支移到循环外做特化（按条件分块处理）；用无分支形式（掩码、条件选择），前提是分支体很便宜；`__builtin_expect` 只影响代码布局，收益通常是几个百分点，指望它解决随机方向是不现实的。验收看 `branch-misses` 是否下降。
:::
:::

::: ex 例 1.5-B4 · IPC 0.6、LLC 缺失很高 {#ex-1.5-B4}

`perf stat` 显示 IPC 明显偏低、LLC-load-misses 很高、分支失败率 1% 左右，热点集中在一条按列跨步的 load。瓶颈是什么？按什么顺序处理？

::: sol 解答

**缓存缺失**（工作集或访问步长问题），不是 ALU。顺序：① 先换循环顺序，让内层按行连续访问（正文的 `ikj` 与 `ijk` 就是这个差别，实测差一个数量级）；② 再看要不要分块，让复用在块内发生；③ 结构层面换布局（AoS 换 SoA、缩小元素宽度）；④ 最后才考虑预取，因为它只是把等待提前。判据：改完后 LLC 缺失率下降、IPC 抬起来，两者一起看才算闭环。
:::
:::

::: ex 例 1.5-B5 · 同样的循环，一处向量化一处没有 {#ex-1.5-B5}

两个函数体完全相同的循环，`a[i] = b[i] + c[i]` 的版本被向量化，另一份只在参数上少了 `restrict` 的没有走向量化路径，汇编里出现了指针相减再比较常数的几条指令。瓶颈是什么？这段检查值不值得？

::: sol 解答

**别名挡住向量化**。那几条 `sub`/`cmp`（x86 上是 `subq`/`cmpq`）就是运行时的重叠检查：编译器不信任指针不重叠，于是先生成检查，不重叠时走向量化分支、重叠时退回标量。值不值得取决于循环长度——长循环里检查几乎免费，短循环或每次调用只处理几个元素时，检查和双份代码可能得不偿失。`restrict` 直接删掉检查与兜底路径；但它只是承诺，重叠时是未定义行为。另一条判据：正文那台机器上 `plain` 与 `restrict` 两版校验一致而时间差三倍多，差的正是「敢不敢假设不重叠」。
:::
:::

::: ex 例 1.5-B6 · 加了大量内联之后前端停顿变高 {#ex-1.5-B6}

一个「什么都内联」的库版本：后端停顿不明显，`stalled-cycles-frontend` 显著升高，代码段体积涨了几倍，某些路径反而变慢。瓶颈是什么？怎么收手？

::: sol 解答

**都不在五个候选里，是前端取指/I-cache**：指令太多太散，译码供不上，热点代码被换出。这属于「优化过度」的一类，判据是前端停顿与代码体积同时上升。收手方式：只对真正的小热函数强制内联，冷路径改成函数调用或 `noinline`；用 `perf stat` 对比 `stalled-cycles-frontend`，用 `size` 看体积变化；`-O3` 相对 `-O2` 变慢的常见原因也在这里。
:::
:::

::: ex 例 1.5-B7 · 两次运行差 30%，还有一个版本完全测不出差异 {#ex-1.5-B7}

两种麻烦：① 同一份二进制连跑五次，时间相差 30%；② 你写了一个「只累加不输出」的微基准，编译器优化后快得离谱。各是什么问题？怎么修？

::: sol 解答

① 基准不可信，不是性能问题：调频、迁移到别的核、后台负载、冷缓存都会造成这个量级。修：绑核（`taskset -c 2`）、把调频 governor 定成 performance、先跑预热再计时、重复多次取最小值、关掉其他负载；跨机器比较时改用周期数而不是墙钟。② 微基准测了个空：死代码消除把整个循环删了。修：把结果真正消费掉（打印、存进 `volatile` 变量、喂给 `black_box`，或加一条空的内联汇编屏障），再检查汇编里还剩不剩下那圈 load/store。留一条底线：**基准不可信时，任何收益数字都不作数。**
:::
:::

## C 组 · 动手实验

计时与汇编类在本机（macOS 或 Linux）都能做；`perf` 与 `cachegrind` 需要 Linux，环境按[实验环境](../env.md) 的 Ubuntu 24.04 虚拟机准备。

::: ex 例 1.5-C1 · 复现四种矩阵乘 {#ex-1.5-C1}

把正文 1.5.12 的 `matmul.c` 原样抄下来编译运行，分别取 $n=512$ 与 $n=1024$，核对四个内核的相对关系。

::: sol 解答

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 matmul.c -o matmul
./matmul 512
./matmul 1024
```

程序自带校验：四行的 `maxerr` 都必须是 0，否则说明你改动过访问顺序而结果不等。要看的是**关系**而不是绝对值：`ijk` 比 `ikj` 慢一个数量级（内层沿 `j` 时 `B` 的步长是整行，正文那台机器算出约 13.6 对 0.77 周期/乘加）；`block64` 与 `block4` 在 L2 很大的机器上多半不超过 `ikj`。正文那组数值是 Apple M1、clang 15、`-O2`；换机器一定重测，别抄毫秒数。
:::
:::

::: ex 例 1.5-C2 · 优化级别与向量化报告 {#ex-1.5-C2}

同一份源码在 `-O0/-O1/-O2/-O3` 下各出一份汇编，数一数指令条数，并让编译器报告循环有没有被向量化。

::: sol 解答

```bash
for opt in O0 O1 O2 O3; do
  cc -$opt -S matmul.c -o mm-$opt.s
  grep -c '^[[:space:]]' mm-$opt.s     # 粗略数一下指令行
done
cc -O2 -Rpass=loop-vectorize -Rpass-missed=loop-vectorize -c matmul.c -o /dev/null
```

Clang 用 `-Rpass…` 系列报告；GCC 对应 `-fopt-info-vec -fopt-info-vec-missed`。读 remark 时要小心：**「vectorized loop」不等于没有别名代价**——带运行时重叠检查的循环也会报告已向量化，正文 1.5.11 的 `addv` 就是这种结构。要确认代价去哪了，还得看汇编（C3）。顺带记录 `-O3` 是否比 `-O2` 慢：向量化与展开增大代码体积时，某些负载确实会倒退。
:::
:::

::: ex 例 1.5-C3 · 看清 restrict 删掉了什么 {#ex-1.5-C3}

用正文 1.5.13 的两个函数，出一份「带 `restrict`」和「不带」的汇编，找出重叠检查与向量化路径的差异。

::: sol 解答

```bash
cc -O2 -fno-inline -S alias_bench.c -o ab.s
grep -n "^_addv" ab.s            # macOS 的符号带下划线前缀；Linux 上标签就是 addv:
awk '/^_addv:/,/^_addv_r:/' ab.s | grep -n "sub\|cmp\|b\."
awk '/^_addv_r:/,/\.cfi_endproc/' ab.s | grep -n "sub\|cmp"
```

不加 `-fno-inline` 时，两个 `static` 函数会被并进 `main`，看不到独立循环。要看到的东西：不带 `restrict` 的版本里先出现「两个指针相减、和常数比较、据此跳转」的几条（ARM64 是 `sub x8, x0, x1` 配 `cmp x8, #64` 与 `b.lo`；x86-64 是 `subq`/`cmpq`/`setb`/`je`，见正文 1.5.11），后面还跟着标量兜底循环；带 `restrict` 的版本里没有这组距离检查，直接从成对的 load/store 开始（ARM64 `ldp`/`stp`，x86 `movupd`/`addpd`）。时间侧的实测口径见正文：同一数据、校验一致、`restrict` 版明显更快。
:::
:::

::: ex 例 1.5-C4 · 用 perf 分内核定位瓶颈 {#ex-1.5-C4}

在 Linux 虚拟机里对 `matmul.c` 做总量采样，再想办法只看一个内核。记录 IPC、缓存缺失、分支失败率。

::: sol 解答

```bash
perf stat -d ./matmul 512
perf record -g ./matmul 512 && perf report --stdio | head -20
perf annotate --stdio -s mm_ijk | head -40
# 只统计用户态、权限受限时
perf stat -e task-clock,instructions,cycles --all-user ./matmul 512
```

三个要点：① 事件名先 `perf list` 确认，`L1-dcache-load-misses`、`LLC-load-misses` 这类是 Intel/AMD 的叫法，ARM64 的虚拟机上名字不同，不可用就退回通用字段；② 报 `Permission denied` 时看 `kernel.perf_event_paranoid`，容器里多半没有 PMU，云主机的 vCPU 也可能计数全 0；③ 四个内核混在一次运行里，IPC 会被平均掉——想看单个内核，就编四个只跑一个内核的小程序分别采样。正文 1.5.9 与 1.5.14 的输出是**示意图**，不是你机器的读数。
:::
:::

::: ex 例 1.5-C5 · 没有 PMU 时用 cachegrind 量化缺失 {#ex-1.5-C5}

用 cachegrind 跑一次正文的 `matmul`，从逐函数表里比较 `mm_ijk` 与 `mm_ikj` 的数据缺失。

::: sol 解答

```bash
valgrind --version        # 先确认装没装
valgrind --tool=cachegrind --cache-sim=yes \
    --cachegrind-out-file=cg.out ./matmul 128
cg_annotate cg.out | head -40
```

先把 $n$ 调到 128 甚至更小：cachegrind 慢 20–50 倍，$n=512$ 会跑很久。然后读逐函数表的 `Dr`（数据引用）、`D1mr`（L1 读缺失）与 `DLmr`（末级读缺失）：按列访问的 `mm_ijk` 应当明显高于按行访问的 `mm_ikj`，而两者的指令数接近——这就是「差距来自访存而不是指令」的确定性证据。它模拟的是简化缓存（默认 32 KB L1、64 字节行），不建模预取、乱序与多核共享，**绝对值别当真，只做 A/B 比较**。
:::

::: ex 例 1.5-C6 · 把 CPE 的两项拟合出来 {#ex-1.5-C6}

把正文 1.5.3 的两个求和函数包成一个小程序，扫一排 $n$，拟合 $T(n)=c+kn$，估出固定开销与每元素成本，再和 1.5.6 算的下界比。

::: sol 解答

```c
/* 计时骨架照抄 1.5.1 那段：main 读一个指数 k，取 n = 1 << k */
for (int r = 0; r < 20; r++) {
    t0 = now_ns();  s = sum_naive(n);  t1 = now_ns();
    best = (r == 0 || t1 - t0 < best) ? t1 - t0 : best;
}
printf("naive n=%zu  %.3f ns/elem  chk=%g\n", n, (double)best / n, s);
```

```bash
cc -O2 -g -o cpe_probe cpe_probe.c
for k in 15 16 18 20 22 24; do ./cpe_probe $k; done
```

做法：用两个足够大的 $n$ 求斜率 $k=(T_2-T_1)/(n_2-n_1)$，再回代求 $c$；小 $n$ 段算出的 CPE 明显高于渐近值，那正是固定开销 $c$ 在起作用，所以别拿最小的点估斜率。换机器比较时优先看周期数：用 `perf stat` 拿 `cycles`，或按正文口径把纳秒换算成周期（正文按 3.2 GHz 估，频率不确定时这步只是量级）。判定标准：实测 CPE 落在下界附近（浮点单累加器接近 4、四累加器接近 1）说明指令层已没多少空间，该动布局或算法；远高于下界才回头找分支、调用或缓存缺失。顺手对比 `sum_naive` 与 `sum_unrolled` 的斜率，就能亲眼看到「两条链 vs 四条链」的差别，注意两者末位可能不同——浮点求和顺序变了。
:::

::: ex 例 1.5-C7 · 分支实验：随机数据与排序数据 {#ex-1.5-C7}

实现一个「数组里大于某阈值的元素计数」，数据分别用随机与已排序两组，`-O2` 下测时间；Linux 上同时看分支失败率。

::: sol 解答

```bash
cc -O2 -o branch branch.c
./branch random   ;  ./branch sorted
perf stat -e branches,branch-misses ./branch random
perf stat -e branches,branch-misses ./branch sorted
```

预期关系：排序组更快、`branch-misses` 明显更低；随机组的分支失败率会接近抛硬币。注意两个坑：① 数组别太小，否则整段都在 L1，分支效应会被缓存效应盖住；② 结果一定要打印或喂给 `black_box`，否则整个循环被删掉，两组都会「一样快」。延伸做第三个版本：把 `if` 改成 `sum += (x >= t)` 之类的无分支写法，比较三组——如果无分支版不比随机版快多少，说明你原本就受限于数据通路而不是控制流。
