[1.16](ch16.md) 讲了 C/Rust 的工具链与 FFI：同一套 ELF、同一套 ABI、同一个链接器。但 Rust 真正改变系统编程的，不是语法，而是**把资源生命周期和错误路径变成类型系统的一部分**。这一章把所有权、`Result`、`unsafe` 放进文件、线程、socket 三个真实场景，再回看 Linux 内核里的 Rust 模块。

## 1.17.1 所有权、借用与生命周期：三条硬约束 {#sec-1.17.1}

这一节回答：Rust 的所有权、借用、生命周期这三条规则，在系统编程里各挡掉哪一类 C 事故？

::: preview 先抓住一件事
一个值只有一个所有者，借用不能活得比所有者久，可变借用同时只能有一个。三条分别对应 fd/锁的自动释放、悬垂指针的排除、数据竞争的编译期排除。所有权不是「自动 `free`」，而是把「谁负责释放」写进类型。
:::

先看一个真实的 C 片段。下面几行在同一进程里先后打开两个文件，中间 `close` 一次：

```c
int a = open("/tmp/lab1c17_a.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
close(a);
int b = open("/tmp/lab1c17_b.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
write(a, "written via stale fd\n", 21);   /* a 已经关闭 */
```

在 VM 上实测（Ubuntu 24.04 aarch64、GCC 13.3）：`a = 3`、`b = 3`，`write` 返回 `21`，而 `lab1c17_b.txt` 里真的出现了这行字。原因不是内核「记住」了旧 fd，而是 **fd 只是进程 fd 表的下标**：`close(3)` 让 3 空出来，下一次 `open` 又拿到 3，旧句柄于是变成指向新文件的合法数字。编译器不报错，内核也不报错。

Rust 的所有权不是「内存管理风格」，而是一组**在编译期检查的资源使用规则**。在系统编程里，它主要约束三件事：

| 约束 | 系统编程含义 | C 的对应风险 |
|:--|:--|:--|
| 一个值只有一个所有者 | fd、缓冲区、锁守卫随作用域自动释放 | 忘记 `close`/`free`、double-free |
| 借用不能超过所有者生命周期 | `&[u8]` 指向的缓冲区不能被提前释放 | 悬垂指针、use-after-free |
| 可变借用独占 | 同一时刻只有一个 `&mut`，编译期排除数据竞争 | 两个线程写同一结构体 |

::: def 定义 1.17.1 · 所有权与借用 {#def-1.17.1}
**所有权**（ownership）：每个值在任意时刻只有一个所有者；所有者离开作用域时，值的 `Drop` 运行，资源随之释放。**借用**（borrow）是临时访问权：`&T` 只读，`&mut T` 独占可写，且借用不得比所有者活得更久。把裸 fd 交给 `File`，等于同时把 `close` 的责任交给它。
:::

```rust
// ownership.rs — 所有权随作用域释放；rustc --edition 2021 ownership.rs
use std::fs::File;
use std::io::{self, Read};

fn read_all(path: &str) -> io::Result<Vec<u8>> {
    let mut f = File::open(path)?;      // 失败自动返回 Err
    let mut buf = Vec::new();
    f.read_to_end(&mut buf)?;
    Ok(buf)                              // f 在函数结束时自动 close
}

fn main() -> io::Result<()> {
    let data = read_all("/etc/hosts")?;
    println!("{} bytes", data.len());
    Ok(())
}
```

<div class="variant" data-arch="all" data-lang="c">

```c
/* ownership.c — 同样的读取；每条错误路径都要自己 close
 * cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror ownership.c -o ownership
 */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

static int read_all(const char *path, char **out, size_t *out_len)
{
    int fd = open(path, O_RDONLY);
    if (fd < 0)
        return -1;
    size_t cap = 4096, len = 0;
    char *buf = malloc(cap);
    if (!buf) { close(fd); errno = ENOMEM; return -1; }
    for (;;) {
        if (len == cap) {
            char *nb = realloc(buf, cap * 2);
            if (!nb) { free(buf); close(fd); errno = ENOMEM; return -1; }
            buf = nb; cap *= 2;
        }
        ssize_t n = read(fd, buf + len, cap - len);
        if (n < 0) {
            if (errno == EINTR) continue;
            free(buf); close(fd); return -1;
        }
        if (n == 0) break;
        len += (size_t)n;
    }
    close(fd);
    *out = buf; *out_len = len;
    return 0;
}

int main(void)
{
    char *buf = NULL; size_t len = 0;
    if (read_all("/etc/hosts", &buf, &len) < 0) {
        perror("read_all"); return 1;
    }
    printf("%zu bytes\n", len);
    free(buf);
    return 0;
}
```

</div>

C 版本要处理 `open`、`malloc`、`realloc`、`read` 的每一条失败路径，并在每条路径上 `close`/`free`；漏一条就是 fd 泄漏或内存泄漏。Rust 的 `?` 在返回 `Err` 时仍会运行 `Drop`，`File` 的 `Drop` 负责 `close`，`Vec` 的 `Drop` 负责释放缓冲区。这不是「Rust 更聪明」，而是**析构顺序由类型系统保证**。

口径先说清：上面这段 Rust 只给出代码与预期行为，**未实测（本机无 Rust 或产物为 Mach-O）**。C 版本的字节数可以随时在 VM 上复算；Rust 版本请在自己的 Linux 上跑过再引用输出。

### 借用与生命周期：把「谁活得久」写进类型

<div class="variant" data-arch="all" data-lang="rust">

```rust
// borrow.rs — 借用检查器拒绝悬垂引用；以下函数若去掉注释会编译失败
fn first_word(s: &str) -> &str {
    s.split_whitespace().next().unwrap_or("")
}

// fn dangling() -> &str {
//     let s = String::from("hello");
//     &s[..]                 // error: `s` does not live long enough
// }

struct Parser<'a> {
    input: &'a str,
    pos: usize,
}

impl<'a> Parser<'a> {
    fn new(input: &'a str) -> Self {
        Self { input, pos: 0 }
    }
    fn rest(&self) -> &'a str { &self.input[self.pos..] }
}

fn main() {
    let text = String::from("hello world");
    println!("{}", first_word(&text));
    let p = Parser::new(&text);
    println!("{}", p.rest());
}
```

</div>

`Parser<'a>` 的生命周期参数表示：`Parser` 不能比它借用的 `input` 活得更久。C 里对应的是「文档约定 + 调用者自律」；Rust 把它变成编译错误。上面那句 `error: s does not live long enough` 属于编译器输出，本环境没有 Rust 工具链，**未实测（本机无 Rust 或产物为 Mach-O）**；你可以在自己的 Linux 上把这行注释放开复现。

没有借用检查时，这类错误要等到运行时才现形。把同样的「借用长于所有者」写成 C，用 AddressSanitizer 编译：

```c
char *borrowed = m->text;   /* 借用 m 内部的缓冲区 */
free(m->text);
free(m);
printf("%s\n", borrowed);   /* 所有者已释放，借用还在用 */
```

VM 实测（`cc -g -fsanitize=address`）报 `ERROR: AddressSanitizer: heap-use-after-free`，位置在 `printf` 那一行，并给出「24-byte region … freed by thread T0 here」。也就是说：C 的违反契约要**跑到了**才被发现，而且只在开了 sanitizer 时；Rust 在编译期就拒绝。代价是类型签名变复杂，尤其是返回引用的函数、trait object、异步代码。经验法则是：**先让编译器推断，只有签名必须表达「返回值和某个参数同寿命」时才手写 `'a`**。

::: errata 所有权的四个常见误解
1. **「Rust 没有内存泄漏」**：`Box::leak`、`Rc` 循环引用、`mem::forget` 都能泄漏；所有权防的是 use-after-free/double-free，不是所有资源泄漏。
2. **「`&mut` 就是 C 的指针」**：`&mut T` 还要求独占（no aliasing），编译器会据此做优化；把同一个 `&mut` 别名给两个线程是 UB。
3. **「`Drop` 一定运行」**：`panic=abort`、`process::exit`、`mem::forget` 都不会运行 `Drop`；系统编程里要显式处理这些路径。
4. **「一个值只有一个所有者，所以 fd 一定安全」**：`File` 只能保证它自己不再重复关闭；把 `as_raw_fd()` 的数字交给别人长期保存，等于把 fd 又借了出去，那个数字仍会被下一次 `open` 复用。
:::

### 1.17.1 小结

三条规则各管一类事故：唯一所有者管「谁释放」，借用寿命管「谁还活着」，独占借用管「谁能改」。在系统编程里，它们分别把 fd/锁的释放、悬垂引用、数据竞争从运行时的运气变成编译期的检查；但 `Drop` 不保证一定执行，泄漏也仍然可能。如果只记住一件事：**所有权回答的是「这块资源由谁负责」，不是「它一定不会泄漏」**。

**Q1（记忆）** 三条规则分别对应 C 里的哪三类事故？
**Q2（辨析）** 为什么 `close(fd)` 之后再用同一个数字 `write` 可能成功，而且写进另一个文件？
**Q3（应用）** 一个函数从 C 库拿到 `int fd` 并返回 `File`，这段转换该不该标 `unsafe`？要写清什么前置条件？

::: sol 答案
**A1** 唯一所有者对应忘记 `close`/`free` 与 double-free；借用寿命对应悬垂指针与 use-after-free；`&mut` 独占对应两个线程同时写同一结构体。
**A2** fd 是进程 fd 表的下标，`close` 只让该下标空出来；下一次 `open` 复用同一个数字，旧数值于是指向新文件，内核只认数字不认「句柄身份」。
**A3** 该标 `unsafe`，因为编译器无法验证 `fd` 有效、也无法知道所有权是否已经转移；`// SAFETY:` 要写「fd 由调用者移交，此后不再使用，且 `File` 会负责 `close`」。
:::

## 1.17.2 错误：`Result`、`?` 与 `errno` 的边界 {#sec-1.17.2}

这一节回答：C 的「返回 -1、设置 `errno`」到了 Rust 里变成什么？哪些错误码必须你自己重试，哪些应该交给 `poll`/`epoll`（批量等待 fd 事件的内核接口）？

::: preview 先抓住一件事
裸系统调用失败时**返回 `-errno`**，libc 包装把它改成 `-1` 并把原因写进 `errno`；Rust 的 `std::io` 在 libc 之上把这两样合成 `io::Error`。`errno` 只在失败后那一瞬间有效，成功的调用不会清零它。
:::

先跑一段 C。程序先用内联汇编发一次 `write(-1, ...)`，再用 libc 的 `write` 做同一件事，最后连续 `open` 一个不存在的路径和一个存在的路径：

```c
errno = 0;
long r = raw_write(-1, "x", 1);        /* aarch64: x8=64, svc #0 */
printf("raw  write(-1) = %ld, errno = %d\n", r, errno);
errno = 0;
ssize_t w = write(-1, "x", 1);
printf("libc write(-1) = %zd, errno = %d\n", w, errno);
```

VM 实测（Ubuntu 24.04 aarch64、GCC 13.3）输出：

```text
raw  write(-1) = -9, errno = 0 (Success)
libc write(-1) = -1, errno = 9 (Bad file descriptor)
open missing: fd=-1 errno=2 (No such file or directory)
open hosts:   fd=3 errno=2  (成功不清 errno)
```

四行读三件事。第一，裸调用返回 `-9`，就是 `-EBADF`，`errno` 根本没被动过：`errno` 是 libc 的设置，不是内核写的。第二，libc 把 `-9` 翻译成 `-1` 加 `errno=9`，所以 C 代码「先判 `-1`、再看 `errno`」这两步是有来历的。第三，`open("/etc/hosts")` 成功返回 3，`errno` 仍停在上一次的 2——**成功不清 `errno`**，任何「先看 `errno`、再看返回值」的顺序都是错的。

Rust 把错误分成两类：**可恢复错误**用 `Result<T, E>`，**不可恢复错误**用 `panic!`。系统编程的绝大多数失败（`EACCES`、`ENOENT`、`EINTR`、`EAGAIN`）都是可恢复的，应该走 `Result`，而不是 `unwrap()`。

::: def 定义 1.17.2 · `errno` 与 `io::Error` {#def-1.17.2}
`errno` 是线程私有的整数，只有在一次调用**失败返回**之后才有意义；成功的调用不会把它清零。Rust 的 `io::Error` 保存失败瞬间的错误码：`kind()` 给分类（`NotFound`、`PermissionDenied`），`raw_os_error()` 给原始数字，`last_os_error()` 才去读当前线程的 `errno`。
:::

<div class="variant" data-arch="all" data-lang="rust">

```rust
// errors.rs — 自定义错误、?、errno 映射；rustc --edition 2021 errors.rs
use std::error::Error;
use std::fmt;
use std::fs::File;
use std::io::{self, Read};

#[derive(Debug)]
enum LoadError {
    Io(io::Error),
    Empty,
}

impl fmt::Display for LoadError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            LoadError::Io(e) => write!(f, "io: {e}"),
            LoadError::Empty => write!(f, "file is empty"),
        }
    }
}

impl Error for LoadError {
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        match self {
            LoadError::Io(e) => Some(e),
            LoadError::Empty => None,
        }
    }
}

impl From<io::Error> for LoadError {
    fn from(e: io::Error) -> Self { LoadError::Io(e) }
}

fn load(path: &str) -> Result<Vec<u8>, LoadError> {
    let mut f = File::open(path)?;       // io::Error -> LoadError
    let mut buf = Vec::new();
    f.read_to_end(&mut buf)?;
    if buf.is_empty() { return Err(LoadError::Empty); }
    Ok(buf)
}

fn main() {
    match load("/etc/hosts") {
        Ok(b) => println!("{} bytes", b.len()),
        Err(e) => {
            eprintln!("load failed: {e}");
            if let Some(src) = e.source() { eprintln!("caused by: {src}"); }
            std::process::exit(1);
        }
    }
}
```

</div>

C 的错误处理是「返回值 + `errno`」：`open` 返回 `-1`，`errno` 保存原因；`read` 返回 `-1`/`0`/正数；`write` 可能短写。Rust 的 `std` 把这些映射成 `io::Error`，但**不会自动重试所有 `EINTR`**，也不会把 `EAGAIN` 变成「等待」。

上面 `LoadError` 那段 Rust **未实测（本机无 Rust 或产物为 Mach-O）**：`?` 在这里做的是 `From<io::Error>` 转换，`source()` 保住原始 `io::Error`，所以打印链路不会丢 `raw_os_error()`。这是类型层面的保证，运行输出请在你的 Linux 上复跑。

| C 错误 | `errno` | Rust `ErrorKind` | 正确处理 |
|:--|:--|:--|:--|
| 文件不存在 | `ENOENT` | `NotFound` | 返回错误/创建文件 |
| 权限不足 | `EACCES`/`EPERM` | `PermissionDenied` | 提示用户/提权 |
| 被信号打断 | `EINTR` | `Interrupted` | 重试（裸 syscall 必须自己重试） |
| 非阻塞暂无数据 | `EAGAIN`/`EWOULDBLOCK` | `WouldBlock` | 交给 `poll/epoll`/async |
| 管道读端关闭 | `EPIPE` | `BrokenPipe` | 停止写，忽略 `SIGPIPE` |
| 磁盘满 | `ENOSPC` | `StorageFull`（较新） | 清理/报错 |
| 参数非法 | `EINVAL` | `InvalidInput` | 修正调用 |

`io::Error::last_os_error()` 读取当前线程的 `errno`；`raw_os_error()` 取原始整数；`from_raw_os_error(n)` 反向构造。**必须在失败后立刻读**，因为中间任何库调用都可能覆盖 `errno`：

<div class="variant" data-arch="all" data-lang="rust">

```rust
// errno.rs — 读 errno 的正确与错误姿势
use std::fs::File;
use std::io;

fn main() {
    match File::open("/definitely/not/here") {
        Ok(_) => unreachable!(),
        Err(e) => {
            // 正确：e 已经保存了失败瞬间的 errno
            println!("kind={:?} raw={:?}", e.kind(), e.raw_os_error());
            // 错误：先做别的事再读 last_os_error，可能已被覆盖
            let _ = std::env::var("PATH");
            println!("last_os_error={:?}", io::Error::last_os_error().raw_os_error());
        }
    }
}
```

</div>

这段 Rust 同样**未实测（本机无 Rust 或产物为 Mach-O）**；它要说明的是：`e` 已经携带失败瞬间的错误码，而 `last_os_error()` 读的是「此刻」的线程 `errno`，两者可能不同。

::: errata Rust 不会自动帮你处理 EINTR
`File::write`/`File::read` 在标准库里对 `EINTR` 做了重试，但直接调 `libc::write`/`nix::unistd::write` 不会；`accept`、`connect`、`openat` 等裸调用也要自己判断 `ErrorKind::Interrupted`。`EAGAIN` 不是错误，非阻塞 fd 要交给 `poll/epoll` 或 async runtime。另外 `ErrorKind` 是 `#[non_exhaustive]`，`match e.kind()` 必须带 `_` 分支；`kind()` 给的是分类，精确原因仍要看 `raw_os_error()`。
:::

### ABI 边界：寄存器与调用指令

| 项 | x86-64 SysV | ARM64 AAPCS64 | RISC-V 64 psABI |
|:--|:--|:--|:--|
| 整数/指针参数 | `rdi, rsi, rdx, rcx, r8, r9` | `x0`–`x7` | `a0`–`a7` |
| 返回值 | `rax` | `x0` | `a0` |
| 调用/返回 | `call`/`ret` | `bl`/`ret` | `jal`/`ret`（`call` 伪指令） |
| 被调用者保存 | `rbx, rbp, r12`–`r15` | `x19`–`x29` | `s0`–`s11` |
| 栈对齐 | 16 字节 | 16 字节 | 16 字节 |
| 系统调用 | `syscall` | `svc #0` | `ecall` |

Rust 的 `extern "C"` 按这张表传参；`std::os::unix` 只是在 libc 之上包了一层，不改变 ABI。FFI 结构体用 `#[repr(C)]`，整数用固定宽度类型，才能让三套架构都读到相同偏移。

### 系统调用边界：三套指令（与 C 对照）

Rust 的 `std` 最终也要发系统调用。下面三段汇编是 `write(1, msg, len)` 的最小入口，用来对照 C 的 `syscall()` 与 Rust 的 `asm!`：

这三段不是「Rust 专属」：C 的 `syscall(SYS_write, ...)` 最终也走到同一条指令。差别在错误约定：**裸系统调用返回 `-errno`，libc 包装返回 `-1` 并设置 `errno`**。Rust 的 `std::io` 在 libc 之上做映射；如果你用 `asm!` 直接发系统调用，就要自己把负返回值转成 `io::Error::from_raw_os_error((-ret) as i32)`。

### 1.17.2 小结

`errno` 是「一次失败的原因」，不是「全局状态」；它保存在线程里，成功不清零，任何中间调用都可能覆盖。Rust 把「返回值 + errno」合并成 `io::Error`，用 `kind()` 分类、用 `raw_os_error()` 保留原始码，但**重试策略没有跟着搬过来**：`EINTR` 要不要重试、`EAGAIN` 要不要等，仍然由调用点决定。如果只记住一件事：**先判返回值，再读错误码，最后才决定重试还是交给事件循环**。

## 1.17.3 `unsafe` 的边界：小、可证明、封装 {#sec-1.17.3}

这一节回答：什么时候非写 `unsafe` 不可？一块能过审查的 `unsafe`，必须交代清楚哪几件事？

::: preview 先抓住一件事
`unsafe` 不是「关掉检查」，而是「编译器无法验证的前置条件，由你证明」。可审查的 `unsafe` 范围小、每块有 `// SAFETY:` 理由、对外只暴露安全 API。写不出理由，就说明边界没画清。
:::

先看没有这层边界时会发生什么。下面三行 C 把同一个指针释放了两次：

```c
char *p = malloc(16);
free(p);
free(p);   /* 第二次释放 */
```

VM 实测（`cc -g -fsanitize=address`）报 `ERROR: AddressSanitizer: attempting double-free`，位置在第二次 `free` 那一行。不开 sanitizer 时它可能静默通过，然后在某次 `malloc` 时炸在无关的位置。Rust 里对应的是 `Box::from_raw` 只能接管一次：第二次调用本身就是 `unsafe`，违反前置条件属于未定义行为，编译器不会替你查。

`unsafe` 的边界因此不是「哪些行加了关键字」，而是**一条对外承诺**：函数内部可以碰裸指针、裸 fd、未初始化内存，但调用者看到的安全签名必须成立。好的 `unsafe` 有三个特征：范围小、每块有 `// SAFETY:` 说明、对外暴露安全 API。坏的做法是把整个模块包进 `unsafe`，让调用者替你还债。

::: def 定义 1.17.3 · `unsafe` 契约 {#def-1.17.3}
`unsafe` 块或 `unsafe fn` 表示：这段代码的正确性依赖若干**编译器无法检查的前置条件**。写它的人负责证明这些条件成立，并用 `// SAFETY:` 写下证明；读它的人据此审查。`unsafe` 只放开五类操作——解引用裸指针、调用 `unsafe fn`、访问 `static mut`、实现 `unsafe trait`、访问 union 字段——不改变所有权与借用规则。
:::

<div class="variant" data-arch="all" data-lang="rust">

```rust
// safe_fd.rs — 用 RAII 封装 raw fd；rustc --edition 2021 safe_fd.rs
use std::io;
use std::os::fd::{FromRawFd, RawFd};
use std::os::unix::io::AsRawFd;
use std::fs::File;

/// 拥有所有权的 fd；Drop 时关闭。
pub struct OwnedFd(File);

impl OwnedFd {
    /// # Safety
    /// `fd` 必须是有效的、由调用者转移所有权的文件描述符。
    pub unsafe fn from_raw(fd: RawFd) -> Self {
        // SAFETY: 调用者保证 fd 有效且所有权转移；File 会负责 close。
        OwnedFd(unsafe { File::from_raw_fd(fd) })
    }

    pub fn write_all(&mut self, buf: &[u8]) -> io::Result<()> {
        use std::io::Write;
        self.0.write_all(buf)
    }

    pub fn raw(&self) -> RawFd { self.0.as_raw_fd() }
}

fn main() -> io::Result<()> {
    let f = std::fs::OpenOptions::new().write(true).open("/dev/null")?;
    let fd = f.as_raw_fd();
    std::mem::forget(f);                       // 避免双重关闭
    let mut owned = unsafe { OwnedFd::from_raw(fd) };
    owned.write_all(b"x")?;
    Ok(())
}
```

</div>

这段代码故意展示了「所有权转移」的微妙处：`File` 已经拥有 fd，如果既保留 `File` 又构造 `OwnedFd`，就会 double-close。`mem::forget(f)` 放弃原 `File` 的所有权，再由 `OwnedFd` 接管。真实代码应优先用 `File`/`OwnedFd` 标准类型，不要手写这层。

口径要说清：这段 Rust **未实测（本机无 Rust 或产物为 Mach-O）**。它的价值在签名：`pub unsafe fn from_raw(fd: RawFd)` 把「fd 有效且所有权移交」写成调用者必须满足的条件，安全方法 `write_all` 则不再要求调用者懂 fd。坏签名正好相反：安全函数内部偷偷做 `from_raw_fd`，把无效 fd 的后果推给运行时。

### `unsafe` 的检查清单

| 操作 | 必须证明什么 | 常见错误 |
|:--|:--|:--|
| `*ptr` 解引用 | 指针非空、对齐、指向有效对象、生命周期内 | 悬垂、越界、别名违反 |
| `slice::from_raw_parts` | 非空（长度 0 也要求非空）、对齐、`len` 不越界 | 空指针 + 0 长度 |
| `transmute` | 大小相同、位模式合法、无 padding 歧义 | 把 `bool` 传成 2 |
| `Box::from_raw` | 指针来自 `Box::into_raw`，只接管一次 | 重复释放 |
| `extern "C"` 调用 | ABI、类型、所有权、panic 边界 | 传 `String`、panic 跨边界 |
| `impl Send/Sync` | 内部状态真的可跨线程 | 手写 `unsafe impl` 掩盖 `Rc` |

`// SAFETY:` 不是注释礼仪，而是审查线索：如果写不出「为什么这里安全」，就说明边界没画清。可以用 Miri 检查一部分 UB：

```bash
rustup component add miri
cargo +nightly miri test
# 或单文件：cargo +nightly miri run
```

这些命令在 VM 上**未实测（本机无 Rust 或产物为 Mach-O）**。Miri 抓不到所有问题：系统调用会被拦截或忽略，FFI 与并发时序也不在它的模型里；它能抓的是越界、悬垂、未初始化读、别名违规。对 `unsafe` 密集的 crate，Miri + ASan + fuzz 是组合拳。

::: errata `unsafe` 的四个误解
1. **「写了 `unsafe` 就会 UB」**：`unsafe` 只是把前置条件的证明交给你；正确使用的 `unsafe` 不产生 UB。反过来，没有 `unsafe` 的代码也可能因为依赖里的 `unsafe`、`build.rs` 或 FFI 而出错。
2. **「`unsafe` 块越大越省事」**：范围越大，需要同时成立的条件越多，审查成本按组合增长；正确做法是收进一个函数，对外只留安全签名。
3. **「Miri 通过就没有 UB」**：Miri 只跑它能模拟的执行路径；系统调用、FFI、并发交错都可能绕过它。
4. **「加了 `#[no_mangle]` 就能被 C 调用」**：符号名对了，ABI 还可能是错的；`extern "C"` 管调用约定，`#[no_mangle]` 管符号名，两者都要。
:::

### 1.17.3 小结

`unsafe` 的边界不按行数画，按承诺画：对外是安全签名，对内是能写出来的前置条件，中间用 `// SAFETY:` 连起来。审查时先看签名，再看每块的理由，最后看有没有把 `unsafe` 泄漏给调用者。如果只记住一件事：**写不出 `// SAFETY:` 的理由，就说明这块 `unsafe` 还不该存在**。

## 1.17.4 文件：C 的每一条错误路径 vs Rust 的 `?` {#sec-1.17.4}

这一节回答：一次文件复制在 C 里要写几条失败路径？Rust 的 `?` 和 `Drop` 省掉哪几条，又留下哪几条必须你自己决定？

::: preview 先抓住一件事
`read` 会被信号打断（`EINTR`），`write` 可能只写一部分，`close` 的错误既不能重试也不能覆盖。Rust 的 `io::copy` 替你处理前两条，`Drop` 会关 fd 却吞掉 `close` 的错误；「读到 EOF 才算完」「先截断再读」这些语义仍然要你决定。
:::

先看三个在 VM 上真跑出来的读数（Ubuntu 24.04 aarch64、GCC 13.3）：

```text
read  = -1 errno=4 (Interrupted system call) hit=1
write = 65536 errno=0 (Success)
```

第一行是空管道上的 `read` 被 `SIGALRM` 打断，返回 `-1`/`EINTR`，**不是 EOF**；第二行是往空管道写 1 MiB（`1048576` 字节），只写进 `65536` 字节，`errno` 还是 0——**短写不是错误**。把「返回值 ≤ 0 就当结束」写进循环，文件会在某个信号之后被读短，或者在管道写满时悄悄丢数据。

同一个实验里还有两处：`copy` 用 64 KiB 缓冲把 `/etc/hosts`（`235` 字节）复制到 `/tmp`，`cmp` 通过；而把同一个路径同时当源和目标，`copy` 返回 0，目标文件却变成 **0 字节**——`O_TRUNC` 在 `read` 之前就清空了源。这三处合起来说明一件事：判断 I/O 是否完成的标准不是「有没有报错」，而是「写入量是否等于请求量、读到的是不是 0」。

::: def 定义 1.17.4 · 短读与短写 {#def-1.17.4}
**短读**：`read` 返回的字节数小于请求但大于 0，表示这次只拿到这么多，后面还有；**短写**：`write` 只接受了请求的一部分，返回值小于请求长度，不一定是错误。两者都必须用循环推进指针和剩余长度；只有 `read` 返回 0 才是常规文件或管道的 EOF。
:::

文件 I/O 是所有权和错误处理最好的试金石，也是本章的**完整程序一**：fd 需要关闭、缓冲区需要释放、`read` 可能短读、`write` 可能短写、`open` 可能被信号打断。C 版本把这些都摊在代码里；Rust 版本用 `File`/`Vec` 的 `Drop` 和 `io::Result` 把「正常路径」变短，但**错误语义仍需你决定**（重试、传播、还是转换）。

<div class="variant" data-arch="all" data-lang="c">

```c
/* copy.c — 处理 EINTR、短读、短写；cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror copy.c -o copy */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>

static int write_all(int fd, const char *p, size_t n)
{
    while (n > 0) {
        ssize_t w = write(fd, p, n);
        if (w < 0) {
            if (errno == EINTR) continue;
            return -1;
        }
        if (w == 0) { errno = EIO; return -1; }   /* 不该发生，但不能死循环 */
        p += (size_t)w;
        n -= (size_t)w;
    }
    return 0;
}

static int copy_file(const char *src, const char *dst)
{
    int in = open(src, O_RDONLY | O_CLOEXEC);
    if (in < 0) return -1;
    int out = open(dst, O_WRONLY | O_CREAT | O_TRUNC | O_CLOEXEC, 0644);
    if (out < 0) { int e = errno; close(in); errno = e; return -1; }

    char buf[65536];
    int rc = 0;
    for (;;) {
        ssize_t n = read(in, buf, sizeof buf);
        if (n < 0) {
            if (errno == EINTR) continue;
            rc = -1; break;
        }
        if (n == 0) break;
        if (write_all(out, buf, (size_t)n) < 0) { rc = -1; break; }
    }
    int saved = errno;
    if (close(in) < 0 && rc == 0) { rc = -1; saved = errno; }
    if (close(out) < 0 && rc == 0) { rc = -1; saved = errno; }
    errno = saved;
    return rc;
}

int main(int argc, char **argv)
{
    if (argc != 3) {
        fprintf(stderr, "usage: %s SRC DST\n", argv[0]);
        return 2;
    }
    if (copy_file(argv[1], argv[2]) < 0) {
        perror("copy");
        return 1;
    }
    return 0;
}
```

// copy.rs — 标准库版本；rustc --edition 2021 copy.rs -o copy
use std::fs::{self, File};
use std::io::{self, Write};

fn copy_file(src: &str, dst: &str) -> io::Result<u64> {
    let meta = fs::metadata(src)?;
    println!("src mode = {:o}", meta.permissions().mode());

    let mut inp = File::open(src)?;
    let mut out = File::create(dst)?;
    let n = io::copy(&mut inp, &mut out)?;   // 内部处理短读/短写/EINTR

        eprintln!("usage: {} SRC DST", args[0]);
        std::process::exit(2);

C 版本里最容易漏的三处：

1. **`read` 的 `EINTR`**：信号处理器打断 `read` 时返回 `-1`/`EINTR`，不是 EOF；不重试会把一次信号当成读失败。VM 上那行 `read = -1 errno=4` 就是它。
2. **`write` 的短写**：`write(fd, p, 65536)` 可能只写 4096 字节，尤其对 pipe/socket；必须循环推进指针和剩余长度。VM 上 1 MiB 只写进 64 KiB，`errno` 仍是 0。
3. **`close` 的错误**：`close` 可能返回 `EIO`（尤其 NFS），但 fd 已经关闭；不要重试 `close`，也不要覆盖前一个错误。C 版本用 `saved` 保存第一个错误。

Rust 的 `io::copy` 处理了前两条；`File` 的 `Drop` 负责关闭，但 `close` 的错误会被丢弃（`flush`/`sync_all` 报告的是写入与落盘，不是 `close`）。对可靠性要求高的程序，要显式 `sync_all()`，并在需要时用 `File::into_raw_fd` + `libc::close` 检查返回值。这段 Rust **未实测（本机无 Rust 或产物为 Mach-O）**；能对照的是语义：`?` 只改变错误怎么向上走，不改变哪一步该重试、哪一步该放弃。

::: errata 文件 API 的四个边界
- `O_TRUNC` 会立刻截断目标文件；如果源文件和目标文件相同，先截断再读会得到空文件——VM 上就是 0 字节。`cp` 检测同一 inode，自己的 `copy` 也要检测（`fstat` 比较 `st_dev/st_ino`）。
- `open` 的 `mode` 只在 `O_CREAT` 时生效，且会被 `umask` 掩掉；`0644` 实际可能是 `0640`。
- 非阻塞 fd 的 `read` 返回 `EAGAIN`，不是 EOF；`io::copy` 在非阻塞 fd 上可能返回 `WouldBlock`。
- `File::create` 等价于 `O_WRONLY|O_CREAT|O_TRUNC`，标准库在支持的平台上默认加 `O_CLOEXEC`；这条来自实现与文档，**未实测（本机无 Rust 或产物为 Mach-O）**。C 侧要显式加，避免 `exec` 泄漏 fd。
:::

### 1.17.4 小结

C 的 `copy_file` 把每条失败路径摊开：`read` 的 `EINTR`、`write` 的短写、`close` 的错误、同文件截断。Rust 的 `?` 和 `Drop` 缩短的是「正常路径」与清理代码，不是错误语义；`io::copy` 替你循环，但 `close` 错误仍被吞。如果只记住一件事：**`?` 只负责把错误往上送，重试与否永远是你的决定**。

**Q2（辨析）** 为什么 `write` 返回 65536 而请求是 1048576，却不算错误？
**Q3（应用）** 自己写 `copy` 时，怎样避免「源和目标同一个文件」导致数据全丢？

::: sol 答案
**A1** `-1` 表示失败，看 `errno`（`EINTR` 要重试，`EAGAIN` 要等就绪）；`0` 表示 EOF；正数是这次读到的字节数，可能小于请求。
**A2** 管道有容量上限，非阻塞写只能接受当前放得下的部分，返回实际写入量，`errno` 不变；调用者要循环写完剩余部分。
**A3** 打开目标前先 `fstat` 两边，比较 `st_dev` 与 `st_ino`；相同就拒绝，或先写临时文件再 `rename`，不要用 `O_TRUNC` 直接开。
:::
:::

## 1.17.5 线程：`pthread` 与 `Arc<Mutex>` / scoped threads {#sec-1.17.5}

这一节回答：同一个「4 个线程各给一个计数器加 10 万次」，C 和 Rust 各写一遍，两门语言的「检查者」分别在哪一刻介入、各漏掉什么？

::: preview 先抓住一件事
C 的线程契约——共享数据要加锁、传给线程的指针要活得比线程久——写在文档和约定里，检查者是编译器之外的东西：sanitizer、valgrind、代码审查。Rust 把其中「借用超寿命」和「能不能跨线程」两条变成编译错误；锁顺序、poisoning、死锁仍然归你。锁与内存序的成本账在 [1.12](ch12.md) 已经实测过，本节不重算，只看**同一件事在两种语言里怎么写、谁负责检查**。
:::

::: ex 例 1.17.5 · 先猜：不加锁的循环会数成多少 {#ex-1.17.5}
4 个线程各执行 10 万次 `g++`，共享变量 `g` 不加任何锁。先猜：在 4 vCPU 的机器上跑三次，`g` 离 400000 差多少？编译器或运行时谁会提醒你？

::: sol 解答
VM 实测（Ubuntu 24.04 aarch64、GCC 13.3、`-O0 -pthread`，跑三次）：`g=310174`、`g=224501`、`g=205284`——没有一次接近 400000，少的接近一半。GCC 一声不响，内核也无从知道。想让它「响」，得请外部工具：本想把无锁版交给 ThreadSanitizer 看现场，但 TSan 在这台 VM 上直接 `FATAL: ThreadSanitizer: unexpected memory mapping`（内核 7.0 的 mmap 布局与 TSan 不合，**未实测成功**）。Rust 的答案发生在编译期：`g++` 这个写法根本没有对应物——共享可变必须经 `&mut`、`Mutex` 或原子类型，三者由编译器强制你选一个。
:::
:::

下面是本章的**完整程序二**（C 与 Rust 两版）。C 版把约定摊在代码里：`struct counter` 手动配对 `pthread_mutex_lock`/`unlock`，工作函数返回 `void *`，`main` 负责 `join` 每一个线程——少 join 一个，主线程先退，其余线程跟着没了，编译器不会拦。

<div class="variant" data-arch="all" data-lang="c">

```c
/* threads.c — 4 个线程各加 100000 次；cc ... -pthread threads.c -o threads */
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>

struct counter {
    pthread_mutex_t mu;
    long value;
};

static void *worker(void *arg)
{
    struct counter *c = arg;
    for (int i = 0; i < 100000; i++) {
        if (pthread_mutex_lock(&c->mu) != 0) abort();
        c->value++;
        if (pthread_mutex_unlock(&c->mu) != 0) abort();
    }
    return NULL;
}

int main(void)
{
    struct counter c;
    pthread_t th[4];
    if (pthread_mutex_init(&c.mu, NULL) != 0) return 1;
    c.value = 0;
    for (int i = 0; i < 4; i++)
        if (pthread_create(&th[i], NULL, worker, &c) != 0) return 1;
    for (int i = 0; i < 4; i++)
        if (pthread_join(th[i], NULL) != 0) return 1;
    printf("value=%ld\n", c.value);
    pthread_mutex_destroy(&c.mu);
    return c.value == 400000 ? 0 : 1;
}
```

</div>

VM 上按注释行编译运行（`-pthread` 不能省）：输出 `value=400000`、`exit=0`，4 线程 × 10 万次一个不丢。创建成本在 1.12 记过账：一次 `pthread_create`+`join` 约 0.102 ms，`fork`+`wait` 约 0.192 ms；加锁、原子、局部累加三档分别是 97.9、25.8、0.8 ms。本节换的是「写法与检查者」，不是重新算账。

Rust 版做同一件事，只多一个区别——数据在锁里面，而不是锁和数据各摆各的：

<div class="variant" data-arch="all" data-lang="rust">

```rust
// threads.rs — scoped threads + Mutex；rustc --edition 2021 threads.rs -o threads
use std::sync::Mutex;
use std::thread;

fn main() {
    let counter = Mutex::new(0u64);
    thread::scope(|s| {
        for _ in 0..4 {
            s.spawn(|| {
                for _ in 0..100_000 {
                    let mut v = counter.lock().unwrap();
                    *v += 1;
                }
            });
        }
    });
    let v = counter.into_inner().unwrap();
    println!("value={v}");
    assert_eq!(v, 400_000);
}
```

</div>

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -pthread threads.c -o threads
rustc --edition 2021 threads.rs -o threads-rs
./threads && ./threads-rs
```

只有 C 版的前两行实测过；`rustc` 那两行**未实测（VM 无 Rust 工具链）**，threads.rs 在写作机 rustc 1.99.1 上编译通过。

Rust 版没有 `Arc`，因为 `thread::scope` 承诺所有子线程在作用域结束前 join，闭包才能借用栈上的 `counter`。把 `scope` 换成 `spawn`、代码一字不改，编译直接失败——这是写作机 rustc 1.99.1 的实测报错：

```text
error[E0373]: closure may outlive the current function, but it
borrows `counter`, which is owned by the current function
```

C 里对应的是「不报错」：`&c` 照样传进 `pthread_create`，`main` 先返回就是悬垂，运行时看运气。线程确实要活过当前栈帧时，Rust 逼你交所有权而不是交引用——`Arc<Mutex<T>>` 版：

```rust
// arc_threads.rs — 线程活过栈帧：Arc + move + join；写作机编译通过，运行未实测（VM 无 Rust 工具链）
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0u64));
    let mut hs = Vec::new();
    for _ in 0..4 {
        let c = Arc::clone(&counter);          // move 走的是引用计数，不是数据
        hs.push(thread::spawn(move || {
            for _ in 0..100_000 { *c.lock().unwrap() += 1; }
        }));
    }
    for h in hs { h.join().unwrap(); }
    println!("value={}", *counter.lock().unwrap());
}
```

`Arc`（atomic reference counter，原子引用计数）给每个线程一份「共同所有者」，`move` 闭包满足 `spawn` 的 `'static` 要求；`lock()` 返回的守卫是 1.17.1 的所有权规则在线程里的落点——离开作用域自动解锁，忘记 unlock 这种事故在 Rust 里编译不过去。

`Send`/`Sync` 管的是「跨线程资格」：`T: Send` 表示值能搬到别的线程，`T: Sync` 表示 `&T` 能安全共享。`Rc`（非原子引用计数）不是 `Send`，把它塞进 `spawn` 的实测报错（写作机 rustc 1.99.1）：

```text
error[E0277]: `Rc<Vec<u8>>` cannot be sent between threads safely
```

C 没有这一步：`pthread_create` 收 `void *`，传什么编译器都放行，引用计数要你自己保证原子。两边分工因此很清楚：**Rust 编译器查「别名与跨界」，不查「锁顺序与死锁」；C 两者都不查，全靠你加外部工具。**

| 关注点 | C `pthread` | Rust `std::thread` |
|:--|:--|:--|
| 创建/加入 | `pthread_create`/`pthread_join` | `thread::spawn`/`JoinHandle::join` |
| 共享所有权 | 裸指针 + 约定 | `Arc<T>`/`&T`（scoped） |
| 互斥 | `pthread_mutex_t` | `Mutex<T>`（数据在锁内） |
| 条件变量 | `pthread_cond_t` | `Condvar` |
| 线程局部 | `__thread`/`pthread_key_t` | `thread_local!` |
| 数据竞争 | TSan/约定 | `Send`/`Sync` 编译期检查 |
| 锁中毒 | 无 | `Mutex` poisoning（可 `into_inner` 忽略） |

::: errata 并发不是「换个类型就安全」
1. **`Arc<Mutex<T>>` 仍会死锁**：两把锁顺序不一致、或持锁调用回调；Rust 不检查锁顺序。
2. **`Mutex` poisoning 不是万能**：panic 后锁被标记 poisoned；`unwrap()` 会再次 panic，`into_inner()` 可取回但可能处于不一致状态。
3. **`thread::scope` 不是「无限并发」**：作用域结束会 join，长任务会阻塞退出；需要后台线程用 `spawn` + 生命周期管理。
4. **`Rc`/`RefCell` 不能跨线程**：`Rc` 不是 `Send`，`RefCell` 不是 `Sync`；编译器会拦住，但 `unsafe impl Send` 可以绕过，后果自负。
:::

### 1.17.5 小结

同一件事两种写法：C 用「裸指针 + 约定」，检查者是外部工具，而本 VM 连 TSan 都起不来；Rust 用 `scope`/`Arc` 两种所有权形状，把「借用超寿命」和「跨界资格」变成编译错误，两条错误信息在写作机上都拿到了实测。锁的账没有变：mutex/atomic/local 的 97.9、25.8、0.8 ms 在哪个语言里都一样花，死锁与 poisoning 也一个都不少。如果只记住一件事：**`thread::scope` 是生命周期契约，`Arc` 是所有权契约，而锁的语义两边都得自己负责**。

::: method 即时自测 · 1.17.5
**Q1（记忆）** `thread::scope` 里的闭包为什么能借用栈上的 `Mutex`，`thread::spawn` 为什么不能？

**Q2（辨析）** 「这段 Rust 没有 `unsafe`，所以并发一定正确」——对吗？给出两个它管不到的例子。

**Q3（应用）** 把 C 版 `threads.c` 的 `worker` 传参从 `&c` 改成指向 `main` 局部变量的指针、且主线程提前 `return`，两边语言各发生什么？

::: sol 答案
**A1** `scope` 保证作用域结束前 join 所有子线程，借用不会比所有者活得久，契约成立；`spawn` 的线程可能活过当前栈帧，所以要求 `'static`，借用局部数据会得到 E0373。

**A2** 不对。编译器只查别名与跨界：锁顺序不一致导致的死锁、panic 后 `into_inner()` 拿回不一致状态，这两类都不触发编译错误。

**A3** C：编译照过，运行是悬垂指针未定义行为，好坏看运气和调度。Rust：等价代码在 `spawn` 处直接编译失败（E0373），必须先改成 `Arc` 移交所有权。

## 1.17.6 Socket：C 的 accept 循环与 Rust 的 `TcpListener` {#sec-1.17.6}

这一节回答：TCP echo 服务器把 `socket`/`bind`/`listen`/`accept`/`read`/`write`/`close` 串成一条真实路径，C 版每条都要自己动手，Rust 版到底接走了哪几条、哪几条照样咬人？

::: preview 先抓住一件事
C 版要手写四件事：`SIGPIPE` 不忽略就整个进程被杀、`accept` 被信号打断要重试、`write` 短写要循环、fd 要逐个 `close`。Rust 的 `TcpStream` 接走 fd 释放，`write_all` 接走短写，`read` 帮你重试 `EINTR`；但 TCP 没有消息边界与语言无关，两版又都是**一次只服务一个连接的串行循环**——代码短不等于自动并发。
:::

::: ex 例 1.17.6 · 先猜：往死对端写一个字节，进程怎么死 {#ex-1.17.6}

`socketpair` 建一对 socket，`close` 掉另一端，然后往还开着的那端 `write(fd, "x", 1)`。先猜：`write` 有机会返回吗？进程最后的状态码是多少？

::: sol 解答
VM 实测（Ubuntu 24.04 aarch64、GCC 13.3）两次运行：默认 disposition 下 `write` 根本没返回——进程被 `SIGPIPE` 杀死，shell 里 `$?=141`（128+13），那行 `printf` 没有执行。加一行 `signal(SIGPIPE, SIG_IGN)` 再跑，错误回到正常通道：`write=-1 errno=32 (Broken pipe)`，进程活到 `exit=0`。所以 C 侧的第一行防御不是循环也不是锁，是**先把 SIGPIPE 缴械，让「写死对端」变成可处理的 errno**。Rust 标准库在启动时忽略 `SIGPIPE`，把同一事件变成 `ErrorKind::BrokenPipe`（文档与实现约定，Linux 上**未实测（VM 无 Rust 工具链）**）。
:::
:::

下面是本章的**完整程序三**（C 与 Rust 两版）。C 版 `echo.c` 把前面几节的错误处理全部叠上：`SIGPIPE` 忽略、`accept`/`read` 的 `EINTR` 重试、`write_all` 防短写、`SO_REUSEADDR` 防重启绑定失败。

<div class="variant" data-arch="all" data-lang="c">

```c
/* echo.c — 单线程 TCP echo；cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror echo.c -o echo */
#include <arpa/inet.h>
#include <errno.h>
#include <netinet/in.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/socket.h>
#include <unistd.h>

static int write_all(int fd, const char *p, size_t n)
{
    while (n > 0) {
        ssize_t w = write(fd, p, n);
        if (w < 0) { if (errno == EINTR) continue; return -1; }
        if (w == 0) { errno = EIO; return -1; }
        p += (size_t)w; n -= (size_t)w;
    }
    return 0;
}

int main(int argc, char **argv)
{
    int port = argc > 1 ? atoi(argv[1]) : 7878;
    signal(SIGPIPE, SIG_IGN);              /* 对端关闭后 write 返回 EPIPE，而不是杀死进程 */

    int s = socket(AF_INET, SOCK_STREAM, 0);
    if (s < 0) { perror("socket"); return 1; }
    int one = 1;
    setsockopt(s, SOL_SOCKET, SO_REUSEADDR, &one, sizeof one);

    struct sockaddr_in addr;
    memset(&addr, 0, sizeof addr);
    addr.sin_family = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
    addr.sin_port = htons((unsigned short)port);
    if (bind(s, (struct sockaddr *)&addr, sizeof addr) < 0) { perror("bind"); return 1; }
    if (listen(s, 16) < 0) { perror("listen"); return 1; }
    fprintf(stderr, "listening on 127.0.0.1:%d\n", port);

    for (;;) {
        int c = accept(s, NULL, NULL);
        if (c < 0) { if (errno == EINTR) continue; perror("accept"); return 1; }
        char buf[4096];
        for (;;) {
            ssize_t n = read(c, buf, sizeof buf);
            if (n < 0) { if (errno == EINTR) continue; perror("read"); break; }
            if (n == 0) break;                 /* 对端关闭 */
            if (write_all(c, buf, (size_t)n) < 0) { perror("write"); break; }
        }
        close(c);
    }
}
```

</div>

VM 实测：`./echo 7878` 后台起服务，stderr 打出 `listening on 127.0.0.1:7878`；`printf 'hello\n' | nc -N 127.0.0.1 7878` 原样收回 `hello`，退出码 0。再用 `strace -f -e trace=accept,accept4` 盯服务端，看到的调用是：

```text
accept(3, NULL, NULL)                   = 4
```

glibc 的 `accept()` 走的是 `accept` 本身，不是 `accept4`。Rust 标准库据称用 `accept4(SOCK_CLOEXEC)` 省一次 `fcntl`，这台机器没有 Rust 产物可对照，**未实测（VM 无 Rust 工具链）**——这条正好留作 1.17.9 的 `strace` 练习。

Rust 版把同一台服务器收进 `TcpListener`/`TcpStream`：

<div class="variant" data-arch="all" data-lang="rust">

```rust
// echo.rs — 单线程 TCP echo；rustc --edition 2021 echo.rs -o echo-rs
use std::io::{self, Read, Write};
use std::net::TcpListener;

fn main() -> io::Result<()> {
    let listener = TcpListener::bind(("127.0.0.1", 7878))?;
    eprintln!("listening on 127.0.0.1:7878");
    for conn in listener.incoming() {
        let mut stream = conn?;               // 连接错误：返回 Err，退出循环
        let mut buf = [0u8; 4096];
        loop {
            match stream.read(&mut buf) {
                Ok(0) => break,                // EOF
                Ok(n) => stream.write_all(&buf[..n])?,
                Err(e) if e.kind() == io::ErrorKind::Interrupted => continue,
                Err(e) => return Err(e),
            }
        }
    }
    Ok(())
}
```

</div>

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror echo.c -o echo
rustc --edition 2021 echo.rs -o echo-rs
./echo 7878 &
printf 'hello\n' | nc 127.0.0.1 7878
./echo-rs &
printf 'hello\n' | nc 127.0.0.1 7878
```

实测过的是前两行加 `nc` 那次往返；`rustc`/`./echo-rs` 两行**未实测（VM 无 Rust 工具链）**，echo.rs 在写作机 rustc 1.99.1 上编译通过。串行的判据不用跑也能从代码读出来：服务循环里 `read`/`write_all` 都是阻塞调用，前一个连接没到 EOF，`accept` 永远不会被再次执行。

两版的循环结构一模一样，因此坑也一模一样：**都是单线程、一次处理一个连接**，第二个客户端要等第一个关闭；`for conn in incoming()` 不自动并发。要并发，C 侧上 `fork`/线程/`epoll`（1.12 实测过那条路），Rust 侧上 `thread::spawn` 或 async runtime。还有一条两边都不替你办的：TCP 是字节流，客户端连发 `ab` 和 `cd`，服务端一次 `read` 可能收到 `abcd`，也可能 `ab`、`cd` 两次——消息边界必须由协议自己给（长度前缀或分隔符），换语言不解决。

| 关注点 | C | Rust |
|:--|:--|:--|
| socket 所有权 | `int` fd，手动 `close` | `TcpStream`，`Drop` 关闭 |
| 地址解析 | `getaddrinfo` + `sockaddr` | `ToSocketAddrs`/`SocketAddr` |
| 错误 | `-1` + `errno` | `io::Result` |
| 短写 | 自己循环 | `write_all` |
| `EINTR` | 自己重试 | `read`/`write` 多数自动重试，裸调用不 |
| 并发 | `fork`/pthread/epoll | `thread`/`tokio`/`async-std` |
| 背压（队列满时让生产者等） | `read` 大小 + 阻塞 | 同样；`read` 返回 `WouldBlock` 要处理 |

::: errata socket 编程的四个坑
1. **不忽略 `SIGPIPE`**：对端关闭后 `write` 触发 `SIGPIPE`，默认终止进程；C 要 `signal(SIGPIPE, SIG_IGN)` 或 `send(..., MSG_NOSIGNAL)`，Rust 标准库内部处理，但裸 `libc::write` 不会。
2. **`accept` 的 `EINTR`**：信号打断 `accept` 返回 `-1`/`EINTR`；不重试会误退出。
3. **TCP 没有消息边界**：一次 `read` 可能读到半个请求或两个请求；协议要自带长度前缀/分隔符。
4. **`SO_REUSEADDR` 不是万能**：它解决 TIME_WAIT 绑定问题，不解决端口被另一个进程占用；`SO_REUSEPORT` 才是多进程共享端口。
:::

### 1.17.6 小结

C 版 echo 的每条防御——`SIGPIPE`、`EINTR`、短写、`close`——都在 VM 上有对应的实测形状：141 与 `errno=32` 是同一件事的两副面孔，`accept(3, NULL, NULL) = 4` 是 glibc 的真实调用名。Rust 版接走的是「资源与循环」两件事：fd 归 `Drop`，短写归 `write_all`；接不走的是协议语义（消息边界）、信号语义（`SIGPIPE` 要在库的层面对待）和并发模型（串行就是串行）。如果只记住一件事：**读一段网络代码，先数它替你挡住了哪几条错误路径，再看它有没有偷偷假设「一次 read 等于一个请求」**。

## 1.17.7 `std::os::unix`、`libc`、`nix`、`rustix`：四层选择 {#sec-1.17.7}

这一节回答：同一件「读 `/etc/hosts` 的 inode 和权限」，放在 Rust 访问 Unix 的四层里各怎么写？每层要你自己负责的检查各多了什么？

::: preview 先抓住一件事
四层只差在两件事上：还剩多少 `unsafe`，错误长什么样。`std` 与 `std::os::unix` 返回 `io::Result`、基本没有 `unsafe`；`libc` 层照抄 C 的 `-1` + `errno`，转换由你写；`nix`/`rustix` 在 libc 上做安全封装，把错误变成 `Errno` 或 `io::Result`。选层依据只有两条：`std` 覆不覆盖这个操作，要不要逐字段匹配内核头文件。
:::

::: ex 例 1.17.7 · 先猜：输出里哪个数字才是文件的真名 {#ex-1.17.7}
一个 C 程序 `open` 后 `fstat`，打印一行 `fd=? ino=? mode=? size=?`。先猜：四个数里，哪个「重新打开同一个文件」就可能变、哪个怎么开都不变？

::: sol 解答
`fd` 是进程 fd 表的下标：VM 实测 `fd=3`（0/1/2 之后的第一个空位），换个时机打开就可能不是 3。`ino=2755542` 是文件在文件系统里的身份，怎么打开都不变，只有删了重建才变；`mode=644`、`size=235` 是元数据，那个 235 与 1.17.4 里复制的 `/etc/hosts` 字节数完全对上。记法就一句：**fd 是把手，ino 才是文件**——1.17.1 的 stale-fd 事故正是把把手当成了文件。
:::
:::

Rust 访问 Unix 接口有四层，越往下越接近 C，越需要 `unsafe`：

| 层 | 代表 | 优点 | 代价 |
|:--|:--|:--|:--|
| 标准库跨平台 | `std::fs`、`std::net`、`std::thread` | 安全、可移植、维护成本低 | 只覆盖常见操作，细节不可控 |
| `std::os::unix` | `MetadataExt`、`PermissionsExt`、`AsRawFd` | 暴露 Unix 细节，仍是安全 API | 仅 Unix；部分平台差异要 `cfg` |
| `libc` crate | `libc::open`、`libc::epoll_wait` | 与 C 一一对应，最灵活 | 全 `unsafe`，错误码/结构体自己管 |
| `nix`/`rustix` | `nix::unistd::read`、`rustix::fs::open` | 对 libc 的安全封装，错误转 `Errno`/`io::Error` | 额外依赖；API 版本差异 |

```rust
// unix_ext.rs — 用 std::os::unix 读 inode、权限、fd；rustc --edition 2021 unix_ext.rs
use std::fs::File;
use std::os::unix::fs::{MetadataExt, PermissionsExt};
use std::os::unix::io::AsRawFd;

fn main() -> std::io::Result<()> {
    let f = File::open("/etc/hosts")?;
    let m = f.metadata()?;
    println!("fd={} ino={} mode={:o} uid={} gid={} size={}",
             f.as_raw_fd(), m.ino(), m.permissions().mode(),
             m.uid(), m.gid(), m.size());
    Ok(())
}
```

</div>

<div class="variant" data-arch="all" data-lang="c">

```c
/* stat_demo.c — 与上面等价的 C 版本
 * cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror stat_demo.c -o stat_demo
 */
#include <stdio.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>

int main(void)
{
    int fd = open("/etc/hosts", O_RDONLY | O_CLOEXEC);
    if (fd < 0) { perror("open"); return 1; }
    struct stat st;
    if (fstat(fd, &st) < 0) { perror("fstat"); close(fd); return 1; }
    printf("fd=%d ino=%llu mode=%o uid=%u gid=%u size=%lld\n",
           fd, (unsigned long long)st.st_ino, st.st_mode & 07777,
           st.st_uid, st.st_gid, (long long)st.st_size);
    close(fd);
    return 0;
}
```

</div>

先把表读成两栏：上面两层里，错误与清理由编译器和标准库负责；到 `libc` 一层，你回到 C 的约定——`-1`、`errno`、处处 `unsafe`；`nix`/`rustix` 再把约定翻回 Rust 侧，代价是多一个依赖、多一处版本跟进。

C 版在 VM 编译运行的真实输出（Ubuntu 24.04 aarch64、GCC 13.3）：

```text
fd=3 ino=2755542 mode=644 uid=0 gid=0 size=235
```

上面 Rust 版输出的是同一行形状：`as_raw_fd`/`ino`/`mode`/`uid`/`gid`/`size` 的数据来源就是同一次 `fstat`，只是错误走 `io::Result`。第二层的意义在这里看得最清：你能拿到 Unix 的全部细节，却不需要写一个 `unsafe`。

`std::os::unix` 还有几个高频扩展：

- `std::os::unix::ffi::OsStrExt`/`OsStringExt`：路径是字节序列，不是 UTF-8；`as_bytes()`/`from_bytes()` 处理非 UTF-8 文件名。
- `std::os::unix::process::CommandExt`：`uid`/`gid`/`pre_exec`/`exec`，用于降权或替换进程。
- `std::os::unix::net::UnixListener`/`UnixStream`：Unix domain socket。
- `std::os::unix::fs::FileTypeExt`：判断 socket/device/fifo。
- `std::os::unix::io::{AsRawFd, FromRawFd, IntoRawFd}`：与 C/FFI 交换 fd 的边界；`from_raw_fd`/`into_raw_fd` 是 `unsafe`/所有权转移点。

路径单独是字节而非字符串，因为内核把文件名当字节串：合法文件名可以含不是 UTF-8 的字节，急着 `to_str()` 就可能悄悄丢掉一个文件。

### 直接调 `libc`：错误映射要自己写

<div class="variant" data-arch="all" data-lang="rust">

```rust
// libc_pid.rs — 直接声明 libc 函数，不依赖 libc crate
// rustc --edition 2021 libc_pid.rs -o libc_pid
use std::ffi::CStr;
use std::os::raw::{c_char, c_int};

extern "C" {
    fn getpid() -> c_int;
    fn strerror(errnum: c_int) -> *const c_char;
}

fn main() {
    let pid = unsafe { getpid() };
    let msg = unsafe { CStr::from_ptr(strerror(2)) };  // ENOENT = 2
    println!("pid={pid} errno2={}", msg.to_string_lossy());
}
```

</div>

口径：`unix_ext.rs` 与 `libc_pid.rs` 两段在写作机 rustc 1.99.1 上编译通过，**未实测（VM 无 Rust 工具链）**；C 版 `stat_demo` 是 VM 实测。`libc_pid.rs` 演示的是第三层最省的形态：不装 `libc` crate，自己 `extern "C"` 声明要用的两个 C 函数——代价是函数原型、返回约定、`errno` 读法从此全靠你对着 man 页负责，编译器只保证 ABI，不保证你抄的签名是对的。

用 `libc` crate 时，`libc::open` 返回 `-1` 并设置 `errno`；Rust 侧要 `io::Error::last_os_error()`。用 `nix` 时，返回 `Result<T, Errno>`；用 `rustix` 时，返回 `io::Result<T>` 并尽量用 `rustix::fs::openat` 等避免 TOCTOU。三者不是互斥的：应用层用 `std`，需要 `epoll`/`io_uring`（内核批量异步 I/O 接口）/`seccomp` 时下沉到 `rustix` 或 `libc`。

::: errata 选择 FFI 层的四个判断
1. **能用 `std` 就用 `std`**：`File`/`TcpStream`/`thread` 已经处理了大部分 `EINTR` 和资源释放。
2. **需要 `O_DIRECT`/`epoll`/`io_uring`/`seccomp`**：`std` 不覆盖，选 `rustix`（安全、活跃）或 `nix`（成熟、API 稳定）。
3. **要匹配内核头文件/ioctl 结构体**：直接用 `libc` + `bindgen`，但把所有 `unsafe` 收进一个小模块。
4. **跨平台库**：`cfg(target_os = "linux")`/`cfg(unix)` 分层，不要把 Linux 专属常量暴露到公共 API。
:::

### 1.17.7 小结

四层是同一个 `fstat` 穿四件衣服：C 版你手动管 fd、`errno`、每条错误路径（VM 实测 `fd=3 ino=2755542 mode=644`）；`std::os::unix` 版细节全在、`unsafe` 归零；`libc` 层回到 C 的错误约定，映射代码由你写；`nix`/`rustix` 再包一层安全壳，多换一层依赖。检查责任的迁移一句话：**每往下走一层，编译器少查一样，多出来的一律算到你的审查清单上**。如果只记住一件事：**先问 `std` 覆不覆盖，再问要不要贴内核头，两问都答「不」就别下沉**。

## 1.17.8 Linux 内核 Rust 模块：用户态经验的边界 {#sec-1.17.8}

这一节回答：你在用户态攒下的四条 Rust 经验——`std`、全局分配器、`Mutex`、panic——哪几条能原样搬进内核模块，哪几条必须整个换成另一个版本？

::: preview 先抓住一件事
内核 Rust 的语法和类型系统与用户态完全一致，换的是宿主：没有 `std`、没有 `libc`，panic 默认不展开，分配要走内核分配器并显式带 `GFP_KERNEL` 一类标志，`Result`/`Arc`/`Mutex` 全是 `kernel` crate 的版本，注册 C 接口走 `#[vtable]` 而不是 `extern "C"`。所有权检查还在，但它认识的每一个接口都换了一遍。
:::

::: ex 例 1.17.8 · 先猜：你这台内核把 Rust 打开了吗 {#ex-1.17.8}
VM 是 Ubuntu 24.04、内核 `7.0.0-38-generic`。先猜：它的构建配置里 `CONFIG_RUST` 开了没有？模块目录里有没有现成的 Rust 模块可以 `modprobe`？

::: sol 解答
读 `/boot/config-7.0.0-38-generic` 的 VM 实测：`CONFIG_RUST=y`、`CONFIG_RUST_IS_AVAILABLE=y`、`CONFIG_RUSTC_SUPPORTS_ARM64=y`，连构建期编译器版本都写着——`CONFIG_RUSTC_VERSION_TEXT="rustc 1.91.1 (ed61e7d7e 2025-11-07)"`。可再到 `/usr/lib/modules/$(uname -r)/kernel/rust` 看一眼：目录不存在，这台机器的发行版没随内核带任何 Rust 模块。「内核支持 Rust」与「你能直接写一个 Rust 模块装上」是两件事：后者还需要内核源码树、匹配的工具链和 `make LLVM=1` 的构建路径。
:::
:::

Linux 6.1 起 Rust 进入主线。内核提供自己的 `kernel` crate：`Result`、`Arc`、`Mutex`、`SpinLock`、`FileOperations`、`MiscDevice` 等；panic 不展开、不能随便阻塞，睡眠与原子上下文由内核而不是运行库来管。

下面是一个**概念性**的 misc 设备模块骨架，用来对照用户态的所有权/错误/FFI；它不能在用户态编译，必须在 Linux 内核树中构建：

```rust,ignore
// 需要 kernel tree：CONFIG_RUST=y，make LLVM=1
use kernel::prelude::*;
use kernel::miscdev;
use kernel::file::{File, Operations};
use kernel::sync::{Arc, Mutex};

module! {
    type: EchoModule,
    name: "rust_echo",
    author: "tutorial",
    description: "minimal Rust misc device",
    license: "GPL",
}

struct EchoModule {
    _misc: miscdev::Registration<Self>,
    state: Arc<Mutex<u64>>,
}

#[vtable]
impl Operations for EchoModule {
    fn open(_shared: &Self, _file: &File) -> Result<()> {
        Ok(())
    }

    fn write(_shared: &Self, _file: &File, data: &[u8], _offset: u64) -> Result<usize> {
        Ok(data.len())                 // 真实驱动要 copy_from_user / 处理 offset
    }
}

impl kernel::Module for EchoModule {
    fn init(_module: &'static ThisModule) -> Result<Self> {
        let state = Arc::new(Mutex::new(0), GFP_KERNEL)?;
        let misc = miscdev::Registration::new_pinned(
            c"rust_echo", state.clone())?;
        Ok(EchoModule { _misc: misc, state })
    }
}
```

这段代码的教学价值在于对照，而不是直接运行：

| 用户态 Rust | 内核 Rust | 差异 |
|:--|:--|:--|
| `std::io::Result` | `kernel::Result` | 错误码是内核 `errno` 的负数 |
| `Box::new`/`Vec` | `KBox`/`KVec` + `GFP_KERNEL` | 分配可能睡眠/失败，需显式标志 |
| `std::sync::Mutex` | `kernel::sync::Mutex` | 自旋/睡眠锁语义不同，不能跨中断（打断当前指令流的事件）随便用 |
| `panic!` 展开 | `panic!` 终止/`BUG` | 内核通常不允许 unwind |
| `extern "C"` | `#[vtable]`/`FileOperations` | 通过内核 trait 表注册，不直接暴露 ABI |
| `Drop` 释放 | `Drop` + 生命周期约束 | 对象可能被并发引用，需 `Arc`/pin |

内核 Rust 的 `unsafe` 边界更硬：DMA（外设直接读写内存）缓冲区、用户指针、锁顺序、中断上下文、`GFP_ATOMIC` 与睡眠规则，编译器都帮不了。写内核模块前先把[第 3 篇](../part3/ch01.md)的 C 内核路径读一遍；Rust 只是换语言，不会替你做内核语义的正确性证明。

::: note 不要把用户态 crate 直接搬进内核
`std`、`libc`、`tokio`、`serde`（默认）都不能直接用；内核 crate 需要 `#![no_std]`、内核分配器、内核同步原语。上游内核 Rust 仍快速演进，API 随版本变化；示例代码必须按目标内核版本核对，不能把 6.1 的 API 当成长期稳定 ABI。
:::

::: def 定义 1.17.8 · 内核 Rust 环境 {#def-1.17.8}
`no_std` 的 Rust 运行环境，四条与用户态的硬性差异：panic 策略是终止（`abort`/`BUG`）而非 unwind；没有默认全局分配器，堆分配走 `KBox`/`KVec` 并显式传 `GFP_KERNEL` 一类的分配标志，失败是返回 `Result` 的 `Err` 而不是 abort；同步原语是内核自己的 `Mutex`/`SpinLock`，用错上下文（在不可睡眠处拿睡眠锁）是内核 bug 而不是编译错误；与 C 的接口通过 `#[vtable]` 的 trait 表注册，不逐个导出 `extern "C"` 符号。
:::

### 1.17.8 小结

五个差异一张表：`Result`、分配器、`Mutex`、panic、注册方式，全部换掉；用户态练出的所有权、借用、`Send`/`Sync` 三件检查工具没有失效，只是它们对面站着的接口全变了。DMA 缓冲区、用户指针、中断上下文、锁顺序，这些连内核 Rust 的 `unsafe` 都查不了，仍要拿内核语义去证明——本节骨架是概念性的，**未实测（VM 无 Rust 工具链，本机也没有内核树构建环境）**，签名以目标内核源码树为准。如果只记住一件事：**Rust 进内核换的是语言，不换你在内核里该负的责任**。

**Q1（记忆）** 用户态 Rust 与内核 Rust 的五个差异是哪五个？

**Q2（辨析）** 为什么不能把 `tokio` 直接搬进内核模块？给出两条理由（提示：线程与分配）。

**Q3（应用）** 内核函数里 `let v = KVec::with_capacity(n, GFP_KERNEL)?;` 和用户在 `main` 里 `Vec::with_capacity(n)`，失败路径有什么不同？

## 1.17.9 实验一：用 strace 看 Rust/C 的真实系统调用 {#sec-1.17.9}

这一节回答：「Rust 标准库替你做了某件事」这类话，怎样在 Linux 上变成一条能核对的读数？哪些部分你现在就能测，哪些部分这台机器注定测不到？

::: preview 先抓住一件事
系统调用是唯一的裁判席：`File::open` 到底发了哪条指令、短写有没有被循环补完、`SIGPIPE` 打死进程时内核记了什么账，都能在 `strace` 里一行行看到。这一节把**能测的一侧全部真跑**（C，VM 实测），把**测不到的一侧明确写在未实测**（Rust 产物，VM 没有 `rustc`）。两侧形状恰好相同，正是本章论证的支点，也是最容易被读歪的地方。
:::

::: ex 例 1.17.9 · 先猜：被信号杀死的 write，strace 里有没有返回值那一行 {#ex-1.17.9}
一个 C 程序往已经没有读端的管道写 1 个字节，不忽略 `SIGPIPE`。先猜：`strace` 的输出里那次 `write` 会不会留下一行返回值？进程最后的状态码是多少？

::: sol 解答
VM 实测（Ubuntu 24.04 aarch64、GCC 13.3）留下三行：

```text
write(4, "x", 1)                        = -1 EPIPE (Broken pipe)
--- SIGPIPE {si_signo=SIGPIPE, si_code=SI_USER, si_pid=35008, si_uid=1000} ---
+++ killed by SIGPIPE +++
```

返回行确实存在——内核已经把 `-EPIPE` 记进账里；可那行 `printf` 没有执行，shell 看到的是 `141`（128+13）。所以 [1.17.6](ch17.md#sec-1.17.6) 那句「`write` 根本没返回」和「返回了 `-1`/`EPIPE`」是同一件事的两个观察面：**内核层面有返回值，用户代码层面接不到**。加一行 `signal(SIGPIPE, SIG_IGN)` 再跑，`--- SIGPIPE ... ---` 还在（strace 记的是递送，不管你是否忽略），但紧跟着出现 `write(1, "write_to_dead_pipe = -1, errno ="..., 50) = 50` 和 `+++ exited with 0 +++`：错误回到正常通道。
:::
:::

命令就是本章完整程序一的 C 版加一层追踪：

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror lab1c17_sp.c -o lab1c17_sp
strace -e trace=openat,read,write,close ./lab1c17_sp
# Rust 侧同一组命令在这里是「未实测（VM 无 Rust 工具链）」：
# rustc --edition 2021 -g copy.rs -o copy-rs-dbg
# strace -f -e trace=openat,read,write,close ./copy-rs-dbg /etc/hosts /tmp/b
```

C 侧的关键读数（VM 实测）：

```text
openat(AT_FDCWD, "/etc/hosts", O_RDONLY|O_CLOEXEC) = 3
openat(AT_FDCWD, "/tmp/lab1c17/out.txt", O_WRONLY|O_CREAT|O_TRUNC|O_CLOEXEC, 0644) = 4
read(3, "127.0.0.1 localhost\n127.0.1.1 ju"..., 4096) = 235
write(4, "127.0.0.1 localhost\n127.0.1.1 ju"..., 235) = 235
close(3)                                = 0
close(4)                                = 0
```

四件事一次读完。第一，这里是 `openat` 不是 `open`：aarch64 的 glibc 早就把 `open` 走成 `openat`，第一个参数 `AT_FDCWD` 表示「相对当前目录」。第二，两组 flag 恰好是 `File::open`（`O_RDONLY|O_CLOEXEC`）与 `File::create`（`O_WRONLY|O_CREAT|O_TRUNC|O_CLOEXEC` 加 `0644`）的文档形状。第三，`= 235` 与 1.17.4、1.17.7 里 `/etc/hosts` 的 `size=235` 完全对上。第四，错误路径同样能测：`openat(AT_FDCWD, "/definitely/not/here", O_RDONLY) = -1 ENOENT (No such file or directory)`，这就是 Rust 侧 `NotFound` 的上一层长相。

边界要说到底：上面这行 C 里的 `O_CLOEXEC` 是你自己写进 `open` 的。Rust 的 `File::open` 加不加，靠的是标准库实现，这台机器上没有它的产物。所以这次实验证明的是**这条形状在 Linux 上真实存在**，不是 **Rust 也发这一条**。

::: def 定义 1.17.9 · strace 的三种行 {#def-1.17.9}
**调用行** `名字(参数) = 返回值`：一次系统调用一行，停在用户态与内核态的边界上记账。**信号行** `--- SIGNAME {...} ---`：记一次递送，被你忽略的信号照样出现。**终结行** `+++ killed by SIGNAME +++` 或 `+++ exited with N +++`：进程的死法。只有第一类带返回值，所以「有没有 `= -1 EPIPE`」判的是内核记没记账，「有没有终结行」判的才是你的代码收没收到错误。
:::

### 线程与 socket：同一套读法换三个场景

把 1.17.5 的 4 线程计数器套上 `strace -f -e trace=clone,clone3,futex`，VM 实测三条：创建走的是 `clone3` 而不是 `clone`，flags 一长串 `CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|CLONE_SETTLS|CLONE_PARENT_SETTID|CLONE_CHILD_CLEARTID`，`exit_signal=0`、`stack_size=0x80ea60`（约 8 MiB），返回值是内核 TID；40 万次 `lock`/`unlock` 整场只有 60 行 `futex(`；`-f` 还会插进 `strace: Process 43170 attached` 这类附着行，输出交叉，判读前先按 pid 分栏。socket 那条在 1.17.6 实测过：`accept(3, NULL, NULL) = 4`，是 `accept`，不是 `accept4`。

::: errata strace 读数的四个误读
1. **「`-e trace=open` 没输出就是没打开文件」**：glibc 在 aarch64 上把 `open` 实现成 `openat`，过滤写 `trace=open` 会一条抓不到；写 `openat` 或 `trace=file`。
2. **「`futex` 次数等于加锁次数」**：实测 40 万次加解锁只有 60 行 `futex`，差三个数量级——无竞争的 `pthread_mutex` 快路径是一次原子 CAS，不进内核。真正该警惕的是 `futex` 突然成倍上涨，那才说明锁在排队。
3. **「看见 `= -1 EPIPE` 就说明程序处理了这个错误」**：那行是内核记账，`SIGPIPE` 在返回值交回你的代码之前就递送到了；判据是终结行和 shell 里的 141。
4. **「Rust 一定带 `O_CLOEXEC`，我验证过了」**：你验证的是 C 版显式写出的 flag。VM 上没有 Rust 产物，Rust 侧那条仍是实现与文档口径，**未实测（VM 无 Rust 工具链）**。
:::

### 1.17.9 小结

这一节的产出是一批能复算的读数和一条清楚的边界。C 侧全部 VM 实测：`openat` 的 flag 形状、`= 235`、`-1 ENOENT`、`-1 EPIPE` 紧跟 `+++ killed by SIGPIPE +++`、`clone3` 与 60 行 `futex`。Rust 侧全部未实测（VM 无 Rust 工具链）：`copy-rs-dbg` 的调用序列、`accept4(SOCK_CLOEXEC)` 到底用不用、`O_CLOEXEC` 到底加不加，都得你在有 `rustc` 的 Linux 上补齐。取证的动作固定为三步：**先写下预期（几条 `read`、`close` 配不配对、短写会不会拆成多行），再跑，再拿读数去对预期**。如果只记住一件事：**`strace` 只告诉你内核收到了什么，不告诉你这句话是哪门语言发的**。

## 1.17.10 实验二：cargo check/clippy/miri 与 FFI 错误映射 {#sec-1.17.10}

这一节回答：`cargo check`、`clippy`、`miri`、`strace` 各查哪一层、各漏哪一层？C 侧的「返回 `-1` 再设 `errno`」到 Rust 侧的 `Result`，转换到底发生在哪一行？

::: preview 先抓住一件事
四件工具不是从松到紧的四档，而是四个互不重叠的层：`cargo check` 只管类型与借用，`clippy` 只管它默认开启的那批误用模式，`miri` 管未定义行为，`strace` 管内核真正收到了什么。「上一层通过」永远推不出「下一层没问题」。FFI 的错误映射则只有一条铁律：`errno` 不跨边界传值，它是当前线程的一块内存，所以转换必须发生在失败那一次的下一行。
:::

::: ex 例 1.17.10 · 先猜：这段代码有几处会让 clippy 报错 {#ex-1.17.10}
一个 `cargo new --bin` 的 crate，`main` 里同时放着：`load("/etc/hosts").unwrap()`、`5_000_000_000usize as u32` 的静默截断、`let _unused = File::open("/nope");`、以及 `CStr::from_ptr(null())`。先猜：`cargo clippy -- -D warnings` 会拦下几条？

::: sol 解答
写作机实测（macOS arm64、rustc 与 clippy 1.99.1，产物是 Mach-O）：**一条都不拦**。`cargo check` 零错误零警告，`cargo clippy -- -D warnings` 同样通过；只有把 restriction 组显式打开——`cargo clippy -- -D clippy::unwrap_used`——才在第 16 行报出那个 `unwrap()`。三条原因各不同：`unwrap_used`/`expect_used` 属 restriction，默认关；`as` 截断的 `cast_possible_truncation` 属 pedantic，默认关；把 `Result` 绑给 `_unused` 变量就不算「未使用」。同一天在另一段代码上，默认 lint 集确实会拦：`f.read(&mut buf)?;` 丢掉返回值，报 `error: read amount is not handled`，附一句 `#[deny(clippy::unused_io_amount)]` on by default。结论是「clippy 通过」只说明你的代码没踩中它默认那批模式，不说明没有 `unwrap`、没有截断。
:::
:::

### 四层检查：这台上哪些跑得起来

| 工具 | 查什么 | 本环境状态 |
|:--|:--|:--|
| `cargo check` | 类型、借用、生命周期；不生成代码、不链接 | 写作机实测（Mach-O 产物） |
| `cargo clippy -- -D warnings` | 默认 lint 集里的常见误用 | 写作机实测（同上） |
| `cargo +nightly miri test` | 解释器级 UB：别名、越界、未初始化 | 未实测（VM 无 Rust；写作机 nightly 未装 `miri` 组件） |
| `strace` / `readelf` / `size` | 内核收到的调用、产物形状 | C 侧 VM 实测；Rust 侧未实测 |

三条实测之外的话要说清。`miri` 是 UB 检查器不是系统测试替代品：它跑的是受控解释器，系统调用会被拦截或忽略，能覆盖哪些随 nightly 版本变，所以「`miri test` 通过」既不证明并发时序正确，也不证明错误路径跑过——本环境没有它的读数，这条只能当定性结论读。`perf` 在这台 VM 上被 `perf_event_paranoid` 挡住，ThreadSanitizer 起不来（1.17.5 实测过），所以性能与竞争这两层在正文里一律没有数字。还有一条实测到的 cargo 陷阱：同一个 `#[link(name = "cerrno", kind = "static")]`，用 `rustc --edition 2021 ffi_errno.rs -L . -l static=cerrno` 编得过、跑得起来，交给 cargo 就报 `Undefined symbols for architecture arm64: "_c_open_missing"`——cargo 要靠 `build.rs` 输出 `cargo:rustc-link-search` 与 `cargo:rustc-link-lib` 才认这个静态库。

### FFI 错误映射：一次真的跨边界

C 侧只有四行，故意做成 libc 的失败形状（VM 与写作机同源代码各编一次）：

```c
#include <errno.h>
int c_open_missing(void) { errno = ENOENT; return -1; }
```

Rust 侧接管它，`extern` 块在 edition 2024 起要写成 `unsafe extern`（写作机实测报错：needs `unsafe` before the extern keyword）：

```rust
unsafe extern "C" { fn c_open_missing() -> i32; }

fn main() {
    let rc = unsafe { c_open_missing() };
    if rc < 0 {
        let e = std::io::Error::last_os_error();
        println!("rc={rc} kind={:?} raw={:?}", e.kind(), e.raw_os_error());
    }
}
```

写作机实测输出：`rc=-1 kind=NotFound raw=Some(2)`（Mach-O 产物）。这一行把映射链走完了：C 返回 `-1`、`errno` 停在 2，libc 把同一个线程 `errno` 交给 `last_os_error()`，`kind()` 分类成 `NotFound`，`raw_os_error()` 保留 2。同一份程序里还做了覆盖实验（VM 实测）：

```text
step1 fd=-1 errno=2 (No such file or directory)
step2 rc=-1 errno=17 (File exists)
saved=2 now=17  lost=YES
```

中间只多了一次 `mkdir` 失败，原来的 2 就没了——这就是「先保存再打印」在 FFI 侧不是风格而是必要条件。更要紧的是数字本身不跨平台：VM 实测 `EAGAIN=11 EWOULDBLOCK=11 EPIPE=32 ENOENT=2 EINTR=4`，写作机同一份 C 打出 `EAGAIN=35 EWOULDBLOCK=35 EPIPE=32 ENOENT=2 EINTR=4`。`raw_os_error()` 是给你**比对**用的，不是给你把 11 硬写进 `if` 用的。

::: def 定义 1.17.10 · FFI 错误映射的三个方向 {#def-1.17.10}
**C → Rust**：负返回值或 `-1` 是信号，紧随其后读 `errno`（`io::Error::last_os_error()`），立刻 `raw_os_error()` 存下来；**Rust → C**：把 `Result` 在边界收成 C 的约定（`-1` + 自己写 `errno`，或返回 `NULL`），panic 不许跨出去；**约定层**：`nix` 收成 `Errno`、`rustix` 收成 `io::Error`、内核 Rust 的 `kernel::Error` 直接是负 errno。三个方向共用一条规则：**跨界只传值，不传「错误」这个概念**。
:::

panic 不跨边界这条也实测了：在 `pub extern "C" fn` 里 `panic!`，写作机（rustc 1.99.1）先打印 panic 消息，再打印 `panic in a function that cannot unwind` 与 `thread caused non-unwinding panic. aborting.`，进程以 `exit=134`（128+6，`SIGABRT`）结束——`after` 那行永远不执行。这是实现行为不是语言保证（见[勘误页](ch17-errata.md)）：要传播用 `extern "C-unwind"` 且两边运行时都支持，要隔离就在边界内 `catch_unwind` 或整体 `panic=abort`。

::: errata 把这层检查当成那层检查
1. **「`cargo check` 过了就能发布」**：`check` 不生成代码也不链接，上面那个 `_c_open_missing` 就是 check 通过、`cargo run` 链接失败。
2. **「`clippy -D warnings` 通过等于没有 `unwrap()`」**：实测同一份带 `unwrap` 的代码在默认 lint 集下零报错，要 `-D clippy::unwrap_used` 才抓得到。
3. **「`miri` 通过等于并发正确」**：`miri` 查 UB，不查时序与死锁，而且系统调用会被拦；本环境连它的读数都没有。
4. **「`raw_os_error()` 的数字可以写进常量表」**：`EAGAIN` 在 VM 上是 11、在写作机上是 35，实测；比对请走 `ErrorKind` 或目标平台的头文件。
:::

### 1.17.10 小结

四件工具各查一层，本环境的能力边界也就近画清了：`cargo check`、`cargo clippy`、FFI 映射、panic 跨边界在写作机上真跑过（产物 Mach-O，结论只到「形状与语义」，不到「Linux 上的 ELF 表现」）；`miri`、`size`、`nm`、`strace` 的 Rust 侧和整台 VM 的 Rust 侧一律未实测（VM 无 Rust 工具链）。FFI 的映射链则三处咬合：`-1` 是 ABI 层的值、`errno` 是线程里的一块内存、`last_os_error()` 只在那一块还没被覆盖时读得到。如果只记住一件事：**每层工具的「通过」只否掉它自己那类错误，跨层推论要一条一条实测**。

## 1.17.11 十二条 Rust 系统编程陷阱 {#sec-1.17.11}

这一节回答：把本章散在十一节里的失败现场收成一份能贴在屏幕边的清单，它应该长什么样——每条要能说出第一现场、机制解释，以及三十秒内能做的第一个动作。

::: preview 先抓住一件事
十二坑分四组，各对应一条编译期约束的失效面：所有权组是「资源归谁」被绕过，错误组是「失败走哪条路」被糊掉，`unsafe` 组是「前置条件写在哪」没人签字，FFI 组是「跨界只传值不传概念」被忘记。读法固定三段：**现象**（你实际看到的第一个信号）→ **原因**（机制层的解释，能指到条款或实现）→ **先查什么**（一条命令、一个 grep、一次断点）。
:::

::: ex 例 1.17.11 · 先猜：把 `as_ptr` 交给 C 之后再 `push`，谁会报错 {#ex-1.17.11}
Rust 侧 `let p = v.as_ptr(); c_consume(p); v.push(0);`，C 那边还留着 `p` 稍后再读。先猜：编译器、`miri`、内核，三者里谁会拦下这一步？

::: sol 解答
三个都不拦。编译器只保证 `as_ptr()` 那一刻指针有效，它不知道指针已经交出去；`push` 可能触发重新分配，旧缓冲区当场失效，这一步在类型层完全合法。`miri` 只在「被检查的那条执行真的解引用了旧指针」时报警，而解引用发生在 C 里，`miri` 看不到（本环境未实测）。内核看到的只是一次普通的读内存，它不知道那块已经被释放。同一类「数字还有效、身份已经变」的事故在 1.17.1 里 C 版实测过：`close(3)` 之后 `write(3, ...)` 返回 `21`，内容写进了另一个文件。判据一条：**交出去的是指针还是所有权，只有你自己知道；`as_ptr` 之后别让容器再动**。
:::
:::

::: def 定义 1.17.11 · 陷阱的三段读法 {#def-1.17.11}
**现象**：能被观察到的第一现场——错误码、退出码、编译器编号（如 E0373/E0277）、`strace` 的一行。**原因**：机制层解释，必须能指到语言条款、库实现或内核约定。**先查什么**：三十秒内能做完的一个动作。只写得出前两段、给不出动作的，按笔记处理，不算一条陷阱。
:::

### 一、所有权（1–4）

**1. 一个 fd 出现两个所有者。** 现象：另一个线程刚打开的文件被关掉，或者数据写进了不该写的文件。原因：`as_raw_fd()` 交出的是 fd 表下标这个整数，所有权仍在 `File` 手里，它 `Drop` 时照样 `close`；`into_raw_fd()` 之后再把原对象交给别人，就是两条 `close` 路径。先查：这个整数离开 Rust 之后，原对象还在不在作用域里；`// SAFETY:` 有没有写明「所有权已移交」。

**2. `Drop` 没跑。** 现象：日志最后一段丢了、临时文件没关、子进程留下没回收的 fd。原因：`std::process::exit`、`panic=abort`、`mem::forget`、`Box::leak`、`Rc` 环都不触发析构；`Drop` 也不能返回错误，`close`/`fsync` 失败被静吞。先查：退出路径是不是绕过了作用域；关键落盘有没有显式 `flush()`/`sync_all()`。

**3. 用了 `Arc<Mutex<T>>` 就以为并发安全。** 现象：进程卡死不出结果，或者 panic 之后拿回的数据明显是半截。原因：编译器只查别名与跨界，锁顺序、优先级反转、poisoning 后的不一致状态都不在检查范围；跨 `.await` 持 `std::sync::MutexGuard` 还会让任务饿死。先查：把加锁点按文件顺序列一遍看是否反序；`clippy` 的 `await_holding_lock` 有没有被 `#[allow]` 掉。

**4. 借用活得比所有者久。** 现象：`thread::spawn` 报 E0373、把 `Rc` 塞进线程报 E0277（两条都在写作机 rustc 1.99.1 上实测）；单线程里 `RefCell` 同时拿着 `borrow()` 和 `borrow_mut()` 则在运行时 panic。原因：`spawn` 的线程可以活过当前栈帧，要求 `'static`；`Rc` 不是 `Send`、`RefCell` 不是 `Sync`，它们的检查被推迟到了运行时或直接交给编译器。先查：能不能换成 `thread::scope`（作用域结束前 join，栈上借用就合法）；不行就 `Arc` + `move` 交所有权，绝不用 `unsafe impl Send` 把报错压下去。

### 二、错误（5–7）

**5. 库代码里到处 `unwrap()`。** 现象：一个 `ENOENT` 把整个调用方的进程打崩，日志里只有一段 panic。原因：`Result` 表达的正是「这里可恢复」，`unwrap` 把它降级成 panic；`clippy` 默认不抓（实测：`-D warnings` 零报错，要 `-D clippy::unwrap_used`）。先查：`grep -n 'unwrap()'`；库函数返回值改成 `Result`，把决定权留给二进制入口。

**6. `?` 把上下文丢了。** 现象：只看到 `No such file or directory (os error 2)`，不知道是哪个路径、哪一步。原因：`io::Error` 只带错误码，不带调用点；`ErrorKind` 又是 `#[non_exhaustive]`，`match e.kind()` 少了 `_` 分支将来会编译不过。先查：自定义错误有没有实现 `Error::source()`、`Display` 里有没有拼进路径与操作名；对外分类用 `kind()`，精确原因留 `raw_os_error()`。

**7. 把 `errno` 当全局状态、把 `EINTR`/短写当 EOF。** 现象：报出来的错误码和真实原因不符；文件被读短了一截。原因：`last_os_error()` 读的是「此刻」的线程 `errno`，VM 实测一次失败的 `mkdir` 就把 2 改成 17（`saved=2 now=17 lost=YES`）；`File::read` 会重试 `EINTR`，`libc::read`/`nix` 裸调用不会。先查：失败点与读错误码之间有没有任何函数调用；三态（负值/0/正数）在代码里是不是分开写的；`read` 是否该换成 `read_exact`、`write` 是否该换成 `write_all`。

### 三、`unsafe`（8–9）

**8. `unsafe` 块越写越大，`// SAFETY:` 越来越少。** 现象：一个 `unsafe fn` 里三十行业务代码，评审没人说得出哪一条前置条件成立。原因：`unsafe fn` 的契约对调用者是隐式的（Rust 2024 起 `extern` 块、`no_mangle` 都要显式写 `unsafe`，写作机实测过这条报错），一旦整块吞掉，编译器与人都失去了落点。先查：能不能把不需要证明的部分挪出块外；每块前是否有一句「为什么此刻成立」。

**9. 指针来源已经失效。** 现象：偶发数据错乱、崩溃位置每次不同。原因：`Vec::as_ptr` 交出后 `push`/`reserve`/`shrink` 会重新分配；`mem::transmute` 延长寿命只是让编译器闭嘴；`&mut` 被别名给两处是 UB。先查：这个指针是哪个容器的内部缓冲、容器后来动没动；需要跨调用稳定就 `Box::leak` 或固定缓冲区。

### 四、FFI（10–12）

**10. panic 跨过 `extern "C"`。** 现象：C 侧调进来之后进程直接 abort——写作机实测 `panic in a function that cannot unwind`、`thread caused non-unwinding panic. aborting.`、`exit=134`。原因：C 帧没有 unwind 表，展开越过未知帧是 UB，当前实现在边界处终止；这是实现行为，不是可依赖的语义。先查：边界函数里有没有 `unwrap`/切片索引/`panic!`；要隔离就 `catch_unwind` 或 `panic=abort`，要传播就 `extern "C-unwind"` 且两边运行时都支持。

**11. 布局、字节与宽度不匹配。** 现象：C 侧读到字段错位，或字符串越过结尾；换台机器数字就变。原因：默认 `repr(Rust)` 不保证字段顺序；`&str` 不以 NUL 结尾；`usize` 在 32 位目标是 32 位；Unix 文件名是字节序列，不是 UTF-8。先查：跨界结构体有没有 `#[repr(C)]`、整数是不是 `u32`/`u64`；字符串走 `CString::new`（内部有 NUL 会报错而不是截断）；路径用 `OsStr`/`as_bytes()`，别急着 `to_str()`。

**12. 分配器与释放路径不配对。** 现象：`free(): invalid pointer`、double free，或者只在某台机器上崩。原因：`Box::into_raw` 交出去的内存必须回到 Rust 侧同一分配器的 `Box::from_raw`，C 的 `free` 不认识它；反过来 C `malloc` 的内存也不能被 Rust 的 `Drop` 收走。先查：这条内存从哪只手出来，就必须回到哪只手；grep 一遍有没有第二条释放路径。

::: errata 四个「这不是 Rust 的锅」
1. **死锁**不是类型系统漏检，是锁顺序——`Arc<Mutex<_>>` 管不到（坑 3）。
2. **`as` 截断**不是 lint 该替你记住的事，是类型选择——默认 lint 集不抓（坑 5、11）。
3. **`SIGPIPE` 打死服务**不是并发 bug，是信号 disposition：VM 实测 `exit=141`、`-1 EPIPE`（1.17.6、1.17.9）。
4. **内核模块编译不过**不是 Rust 不稳定，是内核 Rust 的 API 随版本漂移，`Arc::new(.., GFP_KERNEL)` 这类签名要按目标内核核对（1.17.8）。
:::

### 1.17.11 小结

十二坑其实是同一句话的十二种违反方式：**编译器只查它认识的那三件事——谁拥有、错误走哪条路、能不能跨界；其余一律落到你写的 `// SAFETY:`、你的错误类型和你的退出路径上**。四组的排查动作也不同：所有权组看数字与对象是否配成一对，错误组看返回值与读码时机，`unsafe` 组看每块有没有一句理由，FFI 组看值、布局、分配器三样是否两头一致。如果只记住一件事：**遇到「Rust 怎么会这样」，先把现象翻译成一段 errno、一个退出码或一行 `strace` 输出，再去找原因**。

## 1.17.12 本章小结 {#sec-1.17.12}

这一节回答：把 C 的系统编程换成 Rust，到底换掉了什么、什么一点没换？哪些错误从「运行时才发现」变成了「编译期拒绝」，哪些仍然只能靠你自己证明？

::: preview 先抓住一件事
判据是：**给你一段会泄漏 fd、会吞掉 `EINTR`、会在 `unsafe` 里越界的 C 代码，你能改写成一个把这三件事分别交给「类型系统 / 返回值 / `// SAFETY:` 注释」的 Rust 版本，并说清剩下哪一段仍然要人负责。**
:::

这一章的主线是**「谁负责检查」的重新分工**。1.17.1–1.17.3 立三条硬约束：所有权与借用把资源释放变成编译期事实（`Drop` 不运行的场景只剩 `mem::forget`、`Rc` 环、进程被杀这几类），`Result` + `?` 把错误变成必须回应的返回值，`unsafe` 划定「小、可证明、封装」的边界。1.17.4–1.17.7 把它落到系统编程四件事上：文件的每条错误路径、线程与共享状态、socket 的 `accept` 循环与 `SIGPIPE`/短写、以及 `std` / `std::os::unix` / `libc` / `nix` / `rustix` 这四层封装各换来什么、失去什么。

1.17.8–1.17.11 收口到现实约束：内核里的 Rust 与用户态 Rust 是两套运行时（没有 `std`、不能 panic 跨 FFI、分配器与错误处理都不同），实验一节用 `strace` 看 Rust 与 C 发出的**同一批系统调用**（`openat`、`read`、`close`、`EPIPE`/141），一节讲 `cargo check`/`clippy`/`miri` 各能抓什么、抓不到什么，最后收成十二条陷阱。

逐条打勾的达标表在[学习目标自检表](ch17-checklist.md)。这里只留判据：

- **能解释**：为什么 `File` 出作用域就关、`?` 展开成什么、`unsafe` 的「前置条件」写在哪儿、为什么 `Arc<Mutex<T>>` 的锁不能靠 `Drop` 跨线程保证顺序。
- **能操作**：把一段 C 的错误路径改写成 `Result` + `match errno`；给一个 `unsafe fn` 补 `# Safety` 与调用点的 `// SAFETY:`；用 `strace -e trace=openat,read,close,write` 对比两种语言的实际调用序列。
- **能判断**：什么时候该下探到 `libc`/`rustix`、什么时候 `unsafe` 是必要的、panic 为什么不能跨过 FFI 边界、miri 报的 UB 与 TSan 报的竞争分别在哪个层面。

如果只记住一件事，那就是**Rust 把「约定」变成了「类型」，但没有把「证明」变成免费**：所有权管得住单一所有权资源，管不住内核视角下的 fd 复用、信号打断与设备语义——那些仍然要你在 `unsafe` 块外面写清楚、在返回值里传出去。

**下一站**：本章的内核 Rust 一节只给了对照表。真正的裸机与特权级切换在 [1.18 RISC-V 裸机](ch18.md)：从 M 态固件、S 态 trap 到时钟抢占，看一个内核最小需要什么。

::: method 即时自测 · 1.17
**Q1（记忆）** `File` 出作用域会 `close`，但哪三类情况不会运行 `Drop`？

**Q2（判断）** 一个 Rust 程序里 `read` 返回 `ErrorKind::Interrupted`。它等价于 C 里的什么？正确处理是什么？如果直接 `?` 上抛会怎样？

**Q3（实验）** 你要证明「Rust 与 C 发出的系统调用一样」。给出命令与要看的三行输出，并说明为什么不能用运行时间来比。

**Q4（判断）** FFI 边界上的 `extern "C" fn` 里可能 panic。为什么这是错的？给出两种正确写法。

::: sol 答案
**A1** `mem::forget` 主动放弃；`Rc`/`Arc` 循环引用导致计数永不归零；进程被 `SIGKILL` 或直接 `_exit` 退出（正常 `main` 返回才会析构）。这也是「RAII 不是 GC」的边界。

**A2** 等价于 `read` 返回 -1 且 `errno == EINTR`。正确处理是重试同一次读（必要时先处理已设的标志）；直接 `?` 上抛会把「可重试的暂停」当错误传给用户，表现为随机失败的读取。

**A3** `strace -e trace=openat,read,close,write ./prog`（或 `strace -c` 数次数），看 `openat` 的路径与 flags、`read` 的返回字节数、结尾是否有 `close`。不能比时间：Rust 的运行时初始化、panic 钩子、内存分配策略都不同，比的是**系统调用序列是否等价**，不是快慢。

**A4** panic 展开会跨过 C 栈帧，导致未定义行为（跳过 C 的清理、或撞上 `no unwind` 直接 abort）。两种写法：① 在边界函数内 `catch_unwind` 并把 panic 转成错误码/NULL 返回；② 边界函数返回 `Result`，在最外层用 `match` 转成 C 可见的错误码，保证函数体内没有任何能 panic 的路径（不索引越界、不 `unwrap`）。
