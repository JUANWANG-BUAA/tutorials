C 是「可移植的汇编」这一说法只对了一半。C 标准规定的是抽象机器的行为，编译器把它翻译成目标 ISA 的指令；同一段 C 在 x86-64、ARM64、RISC-V 上生成的指令差别很大，但**调用约定、栈布局、数据布局**这些概念是相通的。学会一种 ISA 的读法，换架构只需要换寄存器名和指令表。

这一章以 x86-64（System V ABI，Linux 使用）为主。选择它是因为绝大多数服务器、桌面 Linux 都在这个架构上，反汇编和调试资料最多。ARM64 只讲与正文相关的部分：寄存器、参数传递、`bl/ret`、`ldp/stp`、条件分支。Y86-64 是第 [1.4](ch04.md) 章的教学 ISA，这里不混入。

读汇编的目标不是手写汇编，而是三件事：验证编译器是否按你的意图优化；在崩溃现场从寄存器与栈还原程序状态；理解高级语言构造的代价。三者都需要你能把一条指令拆成「操作数从哪来、结果到哪去、标志位怎么变」。

## 1.3.1 寄存器、数据格式与调用约定 {#sec-1.3.1}

这一节回答：函数调用时，参数和返回值到底放在哪里？为什么有些寄存器函数用完必须还原，有些却可以随手改写？

::: preview 先抓住一件事
x86-64 有 16 个 64 位通用寄存器，它们是 CPU 内部按名字访问的存储格。System V AMD64 调用约定给前六个整数参数安排了固定座位：`%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9`，返回值放 `%rax`。寄存器还分两族：调用者保存的，函数可以随手改写；被调用者保存的，函数想用就得先存、返回前还原。
:::

先看一段 C。它把六个参数按不同倍数加起来：

```c
long mix(long a, long b, long c, long d, long e, long f)
{
    return a + 2*b + 3*c + 4*d + 5*e + 6*f;
}
```

`mix(1,2,3,4,5,6)` 按 C 语义应得 91。先猜一件事：这 6 个参数里，有几个需要通过栈传递？

在 macOS arm64 上用 clang 交叉生成 x86-64 汇编（Apple clang 21.0.0，`clang --target=x86_64-linux-gnu -O2 -S`）。块内省略 `.cfi_*` 与对齐填充，指令原样保留：

```asm
mix:
    leaq    (%rdi,%rsi,2), %rax
    leaq    (%rdx,%rdx,2), %rdx
    addq    %rax, %rdx
    leaq    (%rdx,%rcx,4), %rax
    leaq    (%r8,%r8,4), %rcx
    addq    %rax, %rcx
    leaq    (%r9,%r9,2), %rax
    leaq    (%rcx,%rax,2), %rax
    retq
```

同一份 C 在 `ubuntu24`（Ubuntu 24.04.5，aarch64，GCC 13.3，`gcc -O2 -S`）上：

```asm
mix:
    add     x2, x2, x2, lsl 1
    add     x1, x0, x1, lsl 1
    add     x1, x1, x2
    add     x4, x4, x4, lsl 2
    add     x3, x1, x3, lsl 2
    add     x5, x5, x5, lsl 1
    add     x3, x3, x4
    add     x0, x3, x5, lsl 1
    ret
```

两段都没有读写栈的指令：x86-64 的六个参数落在 `%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9`，aarch64 的六个参数落在 `x0`–`x5`。`leaq` 和 `add ... lsl` 在做「乘 2、乘 3、乘 4」这类小常数乘法，细节留到 [1.3.2](#sec-1.3.2)。x86 上这段程序未实测（验证环境没有 x86 CPU）；91 是按 C 语义手算的，aarch64 上实跑得到 91。

`%rax`、`%rdi` 这些名字就是寄存器（register，CPU 内部按名字访问的小块存储）。x86-64 的 16 个通用寄存器各有不同宽度的别名：

| 64 位 | 32 位 | 16 位 | 8 位 | 用途（System V） | 谁保存 |
|:--|:--|:--|:--|:--|:--|
| `%rax` | `%eax` | `%ax` | `%al` | 返回值；也是累加器 | 调用者 |
| `%rbx` | `%ebx` | `%bx` | `%bl` | 通用 | 被调用者 |
| `%rcx` | `%ecx` | `%cx` | `%cl` | 第 4 个参数；移位量 | 调用者 |
| `%rdx` | `%edx` | `%dx` | `%dl` | 第 3 个参数；除法高位 | 调用者 |
| `%rsi` | `%esi` | `%si` | `%sil` | 第 2 个参数 | 调用者 |
| `%rdi` | `%edi` | `%di` | `%dil` | 第 1 个参数 | 调用者 |
| `%rbp` | `%ebp` | `%bp` | `%bpl` | 帧指针（可选） | 被调用者 |
| `%rsp` | `%esp` | `%sp` | `%spl` | 栈指针 | 被调用者 |
| `%r8`–`%r9` | `%r8d`–`%r9d` | `%r8w`–`%r9w` | `%r8b`–`%r9b` | 第 5、6 个参数 | 调用者 |
| `%r10`–`%r11` | `%r10d`–`%r11d` | `%r10w`–`%r11w` | `%r10b`–`%r11b` | 临时寄存器 | 调用者 |
| `%r12`–`%r15` | `%r12d`–`%r15d` | `%r12w`–`%r15w` | `%r12b`–`%r15b` | 通用 | 被调用者 |

表里最该先记住的是 `%rsp` 和 `%rbp`：`%rsp` 是栈指针（stack pointer），总指向当前栈顶；`%rbp` 是帧指针（frame pointer），编译器可选地用它标记当前函数栈帧（stack frame，函数在栈上占用的那段空间）的底部。`%rip` 不在表里，它是指令指针（instruction pointer），指向下一条要执行的指令，不能当普通寄存器随便写。

「谁保存」这一列是调用约定（calling convention，函数之间关于参数、返回值、寄存器归属的约定）的核心。**调用者保存**（caller-saved）的寄存器，被调用函数可以随意改写；调用者若还想用原值，必须在 `call` 前自己保存。**被调用者保存**（callee-saved）的寄存器，被调用函数想用就得在入口保存、出口还原，调用者可以放心地假设它返回后不变。可以把它想成借工具：公共工具谁用谁收，借来的笔用完放回原处。

看一个必须跨过函数调用保住局部值的例子：

```c
long f(long);
long g(long x)
{
    long a = x + 1;
    return f(x) + a;
}
```

x86-64 的编译结果：

```asm
g:
    pushq   %rbx
    movq    %rdi, %rbx
    callq   f@PLT
    addq    %rbx, %rax
    incq    %rax
    popq    %rbx
    retq
```

aarch64 的编译结果：

```asm
g:
    stp     x29, x30, [sp, -32]!
    mov     x29, sp
    str     x19, [sp, 16]
    mov     x19, x0
    add     x19, x19, 1
    bl      f
    add     x0, x19, x0
    ldr     x19, [sp, 16]
    ldp     x29, x30, [sp], 32
    ret
```

`x` 必须活过一次 `call`：返回后还要用 `x` 和 `x+1` 算 `f(x) + a`。x86-64 把 `x` 放进 `%rbx`，入口 `pushq %rbx`、出口 `popq %rbx`，`f` 返回后再 `incq` 补上 `+1`；`%rbx` 正是被调用者保存的寄存器。aarch64 直接把 `x+1` 放进 `x19`，用 `str`/`ldr` 存取；同时用 `stp x29, x30` 保存帧指针和返回地址 `x30`，因为 `bl` 会把返回地址写进 `x30`。x86-64 不用手动保存返回地址，`callq` 已经把它压栈了。

数据宽度靠指令后缀区分。同一个 `mov`，搬 1 字节叫 `movb`，搬 8 字节叫 `movq`：

| C 类型 | 宽度 | 整数指令后缀 | 典型指令 |
|:--|--:|:--:|:--|
| `char` | 1 字节 | `b` | `movb`、`addb` |
| `short` | 2 字节 | `w` | `movw`、`addw` |
| `int` | 4 字节 | `l` | `movl`、`addl` |
| `long`、指针 | 8 字节 | `q` | `movq`、`addq` |
| `float` | 4 字节 | — | `movss`、`addss` |
| `double` | 8 字节 | — | `movsd`、`addsd` |

`l` 是 long word 的缩写，在 x86 的历史里指 32 位，不是 C 的 `long`；C 的 `long` 在 x86-64 上是 8 字节，用 `q`（quad word）。浮点指令用 `ss`/`sd` 区分单精度和双精度，不走整数后缀。

C 的整数提升会让窄类型先变成 32 位再运算。看这个函数：

```c
long widths(char c, short s, int i, long l)
{
    return c + s + i + l;
}
```

x86-64（macOS 上 clang 21 交叉汇编，`-O2`）：

```asm
widths:
    addl    %esi, %edi
    addl    %edx, %edi
    movslq  %edi, %rax
    addq    %rcx, %rax
    retq
```

aarch64（`ubuntu24`，GCC 13.3，`-O2`）：

```asm
widths:
    sxth    w1, w1
    add     w1, w1, w0, uxtb
    add     w1, w1, w2
    add     x0, x3, w1, sxtw
    ret
```

`c + s + i` 的类型是 `int`，所以两边的加法都在 32 位寄存器里做；最后要和 64 位的 `l` 相加，才把 32 位结果扩展到 64 位：x86 用 `movslq`（符号扩展），aarch64 用 `sxtw`。aarch64 还先用 `sxth` 和 `uxtb` 把 `short`、`char` 规整到 32 位；x86-64 这边直接使用调用者传进来的 32 位值。另外，`char` 是否有符号由实现决定：x86-64 Linux 默认有符号，aarch64 Linux 默认无符号，同一段 C 在两边可能给出不同结果。

::: def 定义 1.3.1 · System V AMD64 ABI {#def-1.3.1}
Linux、BSD、macOS 在 x86-64 上使用的二进制接口约定（application binary interface，ABI）：函数之间怎么传参、怎么放返回值、哪些寄存器归谁保存。整数和指针参数依次放 `%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9`，第 7 个起从右向左压栈；浮点参数用 `%xmm0`–`%xmm7`；返回值在 `%rax`（128 位整数在 `%rdx:%rax`，浮点在 `%xmm0`）。`call` 前栈指针要 16 字节对齐；`%rbx`、`%rbp`、`%r12`–`%r15` 由被调用者保存。
:::

::: ex 例 1.3.1 · 先猜参数坐哪，再看汇编 {#ex-1.3.1}
还是 `mix(1,2,3,4,5,6)`。先猜三件事：6 个参数有几个上栈？函数体里有没有一条访存指令？返回值最后放在哪个寄存器？

::: sol 解答
0 个参数上栈，函数体没有访存指令，返回值在 `%rax`。x86-64 的前六个整数参数正好占满 `%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9`；汇编里只有 `leaq`、`addq`、`retq`，没有 `(%rsp)` 或 `(%rdi)` 这类内存操作数。按 C 语义结果是 1+4+9+16+25+36=91；x86 上未实测，aarch64 上实跑为 91。
:::
:::

::: errata 关于寄存器的五个误解
1. **「`%rax` 是返回值，调用前后不会变」**——它是调用者保存的。`call` 返回后，`%rax` 只保证是本次调用的返回值，不保证还是你调用前放进去的数。
2. **「被调用者保存就是每个函数都会保存 `%rbx`」**——只有用到才保存。`mix` 一条 `push` 都没有，因为它根本没碰 `%rbx`。
3. **「参数寄存器顺序是 x86 的通用规则」**——这是 System V ABI 的规则。Windows x64 用 `%rcx`、`%rdx`、`%r8`、`%r9`，同一个函数在 Windows 上编译，参数坐的位置就变了。
4. **「32 位程序就是 64 位程序加 `-m32`」**——`-m32` 生成的是 i386 ABI：参数主要走栈、指针 4 字节、系统调用（程序请求内核代劳的入口）号和结构体对齐都不同，不是换个开关那么简单。
5. **「`char` 一定是有符号的」**——C 标准把 `char` 的符号性交给实现。x86-64 Linux 默认有符号，aarch64 Linux 默认无符号；把 `char` 当小整数跨架构传，先确认这一条。
:::

### 1.3.1 小结

① 16 个通用寄存器各有宽度别名，前六个整数参数坐 `%rdi`–`%r9`，返回值在 `%rax`；② 调用者保存的寄存器函数可以随手改，被调用者保存的必须原样还；③ 数据宽度看后缀，窄类型先提升到 32 位再运算。如果只记住一件事，那就是：**读一个函数的汇编，先找参数从哪来、返回值到哪去，再看它保存了哪些寄存器。**

::: method 即时自测 · 1.3.1
**Q1（记忆）** System V AMD64 ABI 的前六个整数参数分别放在哪些寄存器？返回值放在哪？

**Q2（辨析）** `%rbx` 和 `%rcx` 都是通用寄存器，为什么 `g` 保存了 `%rbx`，却没有保存 `%rcx`？

**Q3（应用）** 一个函数只调用了 `%r10` 和 `%r11`，入口没有 `push`，出口没有 `pop`。这违反调用约定吗？

**Q4（迁移）** 同一份 C 在 x86-64 Linux 和 aarch64 Linux 上编译，`char` 参数的扩展指令可能不同。原因是什么？给出验证命令。

## 1.3.2 操作数与寻址模式 {#sec-1.3.2}

这一节回答：`8(%rdi)` 和 `(%rdi,%rsi,8)` 各表示哪个地址？为什么 C 里的 `a[i]` 不用先算 `i * sizeof(long)`？

::: preview 先抓住一件事
x86-64 的内存操作数（operand，指令里被读写的对象：寄存器、内存或立即数）是一个地址算式：位移 + 基址 + 变址 × 比例。比例只能是 1、2、4、8，正好对应 `char`、`short`、`int`、`long` 的宽度。`lea` 只算这个地址、不读内存；`%rip` 相对寻址让同一段代码加载到任何地址都能找到全局变量。
:::

先看一行 C：

```c
long idx(long *a, long i) { return a[i]; }
```

`a` 在 `%rdi`，`i` 在 `%rsi`。先猜：取 `a[i]` 需要几条指令？要不要先算 `i * 8`？

x86-64 的编译结果只有一条访存指令：

```asm
idx:
    movq    (%rdi,%rsi,8), %rax
    retq
```

aarch64 的编译结果同样只有一条：

```asm
idx:
    ldr     x0, [x0, x1, lsl 3]
    ret
```

两边都把「基址 + 下标 × 8」做进了指令的寻址模式（addressing mode，指令里描述地址怎么算的格式）。x86-64 写成 `(%rdi,%rsi,8)`，aarch64 写成 `[x0, x1, lsl 3]`；`8` 和 `lsl 3` 都是「下标乘以 8」，不是先做一条乘法再访问。

AT&T 语法的操作数顺序是「源, 目的」，寄存器带 `%`，立即数带 `$`。`movq $8, %rax` 把常数 8 放进 `%rax`；`movq %rax, %rbx` 把 `%rax` 的值复制到 `%rbx`；`movq 8(%rdi), %rax` 把内存地址 `%rdi+8` 处的 8 字节读进 `%rax`。Intel 语法把顺序反过来，`objdump -M intel` 可以切换；这里统一用 AT&T，与 GCC/clang 的 `-S` 默认输出一致。

内存操作数的通用形式是：

$$
D(\text{Base}, \text{Index}, \text{Scale}) = M[D + \text{Base} + \text{Index} \times \text{Scale}]
$$

其中 `Scale` 只能是 1、2、4、8。这个形式覆盖了大多数数组和结构体访问：

| 写法 | 地址 | 典型 C 来源 |
|:--|:--|:--|
| `(%rdi)` | `M[rdi]` | `*p` |
| `8(%rdi)` | `M[rdi+8]` | `p->next`（偏移 8） |
| `(%rdi,%rsi,8)` | `M[rdi + 8*rsi]` | `a[i]`，`long a[]` |
| `4(%rdi,%rsi,4)` | `M[rdi + 4*rsi + 4]` | `a[i+1]`，`int a[]` |
| `(%rdi,%rsi,1)` | `M[rdi+rsi]` | 字节数组 `s[i]` |
| `0x10(%rip)` | `M[rip+0x10]` | 全局变量、字符串常量 |

把表里的形式逐个落到汇编上。同一份 C：

```c
struct node { long value; struct node *next; };

long idx(long *a, long i)   { return a[i]; }
int  idx4(int *a, long i)   { return a[i + 1]; }
long second(struct node *p) { return p->next->value; }
long scale(long x, long y)  { return x + 4*y + 7; }
long g = 42;
long get(void)              { return g; }
```

x86-64（macOS 上 clang 21 交叉汇编，`-O2`）：

```asm
idx:
    movq    (%rdi,%rsi,8), %rax
    retq
idx4:
    movl    4(%rdi,%rsi,4), %eax
    retq
second:
    movq    8(%rdi), %rax
    movq    (%rax), %rax
    retq
scale:
    leaq    (%rdi,%rsi,4), %rax
    addq    $7, %rax
    retq
get:
    movq    g(%rip), %rax
    retq
```

aarch64（`ubuntu24`，GCC 13.3，`-O2`）：

```asm
idx:
    ldr     x0, [x0, x1, lsl 3]
    ret
idx4:
    add     x1, x1, 1
    ldr     w0, [x0, x1, lsl 2]
    ret
second:
    ldr     x0, [x0, 8]
    ldr     x0, [x0]
    ret
scale:
    add     x0, x0, x1, lsl 2
    add     x0, x0, 7
    ret
get:
    adrp    x0, .LANCHOR0
    ldr     x0, [x0, #:lo12:.LANCHOR0]
    ret
```

逐条对照：

- `long a[i]`：x86 的 scale 是 8，aarch64 是 `lsl 3`（2^3=8），都是「下标乘 8」。`int a[i+1]` 多一个 4 字节位移：x86 直接写 `4(...)`；aarch64 的 `ldr` 这一形式不能同时带变址和立即数，所以先 `add x1,x1,1`，再按 `lsl 2` 寻址，变成两条指令。
- `p->next->value`：先 `8(%rdi)` 取出 `next`，再从 `(%rax)` 取出 `value`；aarch64 是两条 `ldr`，偏移 8 写在方括号里。
- `x + 4*y + 7`：x86 一条 `leaq (%rdi,%rsi,4)` 就把「基址 + 变址×4」算完，再 `addq $7`；aarch64 没有 `lea`，用两条 `add`，其中 `add x0,x0,x1,lsl 2` 把移位并进了加法。
- `g`：x86 用 `%rip` 相对寻址，指令里存的是「目标 - 下一条指令」的 32 位偏移；aarch64 用 `adrp` 取页基址、`ldr` 加页内偏移。两种写法都让代码加载到不同地址时仍能找对全局变量。

`%rip` 相对寻址是位置无关代码（position-independent code，PIC，加载到哪儿都能正确运行、不依赖固定地址的代码）的基础。把上面的 C 编成 `addr.x86.o` 后跑 `readelf -r`，能看到一条 `R_X86_64_PC32` 重定位（relocation，链接器把最终地址写进占位字段的过程）；这里是 clang 21 的结果，偏移 0x43、addend 为 -4。链接器要填的不是 `g` 的绝对地址，而是 `g - 下一条指令地址`。减 4 是在补偿「PC（program counter，程序计数器，这里就是 `%rip`）已经走过这个 4 字节位移字段」。这一段在 [1.7](ch07.md) 讲 GOT/PLT 时会再展开。

`lea`（load effective address，加载有效地址）只做地址计算，不访问内存。它看起来像内存操作数，但 CPU 只算、不读：

```asm
leaq 7(%rdi,%rsi,4), %rax     # %rax = %rdi + 4*%rsi + 7
leaq (%rdi,%rdi,2), %rax      # %rax = 3*%rdi
leaq (%rdi,%rdi,4), %rax      # %rax = 5*%rdi
leaq (%rdi,%rdi,8), %rax      # %rax = 9*%rdi
```

编译器常用 `lea` 做「乘以 3/5/9 再加常数」的快速运算：一条指令完成，不设标志位，也不占乘法器。`scale` 里的 `leaq (%rdi,%rsi,4)` 是「x + 4y」，不是「读地址 x+4y 处的内存」。这段在 x86 上未实测（验证环境没有 x86 CPU），指令语义来自架构定义；aarch64 用两条 `add` 得到同一个地址算式。

::: intuition 为什么比例只给 1/2/4/8
这四个数正好是 C 的 `char`、`short`、`int`、`long` 的宽度。硬件把「基址 + 变址 × 元素大小」做成地址生成器，编译器就不必先算 `i * 8` 再相加。指令集在这里固化了常见数据布局的假设；比例若不是 2 的幂，就得拆成移位和加法，`lea` 的 3/5/9 就是这么来的。
:::

::: ex 例 1.3.2 · 先猜几条指令 {#ex-1.3.2}
对 `int a[]` 取 `a[i+1]`：先猜 x86-64 和 aarch64 各需要几条指令完成「算地址 + 读内存」，再对照上面的 `idx4`。

::: sol 解答
x86-64 一条 `movl 4(%rdi,%rsi,4), %eax`：位移 4 和比例 4 同时在寻址模式里。aarch64 两条：先 `add x1,x1,1`，再 `ldr w0,[x0,x1,lsl 2]`，因为这一形式的 `ldr` 不能同时带变址和立即数偏移。两条路线的指令数不同，地址算式相同。
:::
:::

::: errata 关于寻址的五个误解
1. **「`lea` 会读内存」**——不会。它只把算出来的地址放进目的寄存器；`leaq 8(%rdi),%rax` 不访问 `%rdi+8`。
2. **「AT&T 的 `movq %rax,%rbx` 是 `%rbx` 到 `%rax`」**——反了。AT&T 是「源, 目的」，这条把 `%rax` 写进 `%rbx`；Intel 语法才是 `mov rbx, rax` 的顺序。
3. **「比例可以写任意整数」**——硬件只认 1、2、4、8。乘 3、5、9 要用 `lea` 组合，乘其他常数要靠移位和加法，或者 `imul`。
4. **「`8(%rdi)` 表示地址 8」**——它表示内存地址 `%rdi+8` 处的内容；单独的 `$8` 才是常数 8。
5. **「`%rip` 是当前指令的地址」**——执行时它已经指向下一条指令。RIP 相对位移按「目标 - 下一条指令」编码，重定位里的 -4 就是这件事的痕迹。
:::

### 1.3.2 小结

① 内存操作数 = 位移 + 基址 + 变址 × 比例，比例 1/2/4/8 对应四种常见宽度；② `lea` 只算地址，常被借来做小常数乘法；③ `%rip` 相对寻址让代码与加载地址无关。如果只记住一件事，那就是：**看到 `(%rdi,%rsi,8)`，先把它读成「rdi + 8×rsi 处的一个 8 字节数」。**

## 1.3.3 数据传送与算术逻辑 {#sec-1.3.3}

这一节回答：为什么一条 `mov` 要有 `movb`、`movw`、`movl`、`movq` 四个版本？`z * 48` 在汇编里为什么常常看不到 `imul`？

::: preview 先抓住一件事
传送和运算指令用后缀标宽度：`b` 是 1 字节，`w` 是 2 字节，`l` 是 4 字节，`q` 是 8 字节。写 32 位寄存器会顺手把对应 64 位寄存器的高 32 位清零，所以 `movl %edi,%eax` 就是「零扩展到 64 位」。常数乘法常被编译器拆成移位和 `lea`，这叫强度削减；`lea` 只算地址，不设标志位。
:::

看一个算术函数：

```c
long arith(long x, long y, long z)
{
    long t1 = x + y;
    long t2 = z * 48;
    long t3 = t1 & 0xFFFF;
    return t2 + t3;
}
```

先猜：`z * 48` 会不会编译成一条 `imul`？

x86-64（macOS 上 clang 21 交叉汇编，`-O2`）：

```asm
arith:
    addl    %edi, %esi
    leaq    (%rdx,%rdx,2), %rcx
    shlq    $4, %rcx
    movzwl  %si, %eax
    addq    %rcx, %rax
    retq
```

aarch64（`ubuntu24`，GCC 13.3，`-O2`）：

```asm
arith:
    add     x2, x2, x2, lsl 1
    add     x0, x0, x1
    lsl     x2, x2, 4
    add     x0, x2, w0, uxth
    ret
```

两边都没有 `imul`。`z * 48` 被拆成 `3z << 4`：x86 先 `leaq (%rdx,%rdx,2)` 得到 `3z`，再 `shlq $4` 乘 16；aarch64 先 `add x2,x2,x2,lsl 1` 得到 `3z`，再 `lsl x2,x2,4`。移位和 `lea` 通常比乘法便宜，编译器在常数乘法上做这种强度削减（strength reduction，把昂贵运算换成等价但更便宜的运算）。

`t1 & 0xFFFF` 只需要 `x+y` 的低 16 位，所以 x86 用 32 位的 `addl` 就够了，最后 `movzwl %si,%eax` 取低 16 位并零扩展到 32 位；aarch64 则先做 64 位 `add`，再用 `uxth` 截低 16 位。两条路线不同，结果都只保留低 16 位。

常用指令按功能分几族。表里的标志位（flag，CPU 用一位记录运算结果某种状态的开关）在 [1.3.4](#sec-1.3.4) 展开：

| 指令 | 效果 | 标志位 |
|:--|:--|:--|
| `mov src, dst` | `dst = src` | 不改 |
| `movzXX` / `movsXX` | 零扩展 / 符号扩展传送 | 不改 |
| `lea addr, dst` | `dst = addr` | 不改 |
| `add` / `sub` | 加 / 减 | 改 CF、ZF、SF、OF |
| `imul src, dst` | 有符号乘法，保留低位 | 改 CF、OF |
| `and` / `or` / `xor` | 位运算 | 改 SF、ZF，清 CF、OF |
| `inc` / `dec` | 加 1 / 减 1 | 改 SF、ZF、OF，**不改 CF** |
| `neg` / `not` | 取负 / 按位取反 | `neg` 改标志，`not` 不改 |
| `sal` / `sar` / `shl` / `shr` | 移位 | 改 CF、ZF、SF、OF（视位数） |

几条容易踩的规则：

- **两个操作数不能同时是内存。** `addq (%rdi), %rax` 和 `addq %rax, (%rdi)` 都合法；`addq (%rdi), (%rsi)` 不合法，想这么干得先 `mov` 到一个寄存器。
- **写 32 位寄存器会清零高 32 位。** `movl %edi, %eax` 之后，`%rax` 的高 32 位一定是 0。写 8 位或 16 位寄存器没有这个效果，`movb %dil, %al` 只改最低字节。
- **`imul` 有两个常用形式。** 双操作数 `imulq %rsi, %rax` 只保留低 64 位，C 的 `long` 乘法通常用它；单操作数 `imulq %rsi` 把 128 位结果放进 `%rdx:%rax`。有符号和无符号的低位结果相同，所以无符号乘法也可能看到 `imul`。
- **`inc`/`dec` 不改 CF。** 需要把上一条运算的进位带进多精度加法时，`inc` 会让 `adc` 读到一个过期的 CF；这种场合换成 `add $1`。不需要 CF 时编译器照用 `inc`，上一节 `g` 里的 `incq %rax` 就是例子。

零扩展和符号扩展是两个方向。看这对函数：

```c
long sext(int x)      { return x; }
long zext(unsigned x) { return x; }
```

x86-64（macOS 上 clang 21 交叉汇编，`-O2`）：

```asm
sext:
    movslq  %edi, %rax
    retq
zext:
    movl    %edi, %eax
    retq
```

aarch64（`ubuntu24`，GCC 13.3，`-O2`）：

```asm
sext:
    sxtw    x0, w0
    ret
zext:
    uxtw    x0, w0
    ret
```

`int` 是 32 位，`long` 是 64 位，返回时要把 32 位扩成 64 位。`sext` 保留符号，用 `movslq` 或 `sxtw`；`zext` 把源当无符号数，高 32 位补 0，x86 用一条 `movl` 就完成了——写 `%eax` 自动清零 `%rax` 的高半，aarch64 则显式写 `uxtw`。这就是「32 位写清零」最常用的一面。

::: ex 例 1.3.3 · 先猜用哪条指令 {#ex-1.3.3}
对 `long zext(unsigned x) { return x; }`，先猜：编译器会用 `movq %rdi,%rax`、`movl %edi,%eax`，还是 `movslq %edi,%rax`？这三个选择在结果上差在哪？

::: sol 解答
用 `movl %edi, %eax`。`unsigned` 是 32 位，返回 `long` 要零扩展；x86-64 规定写 32 位寄存器会清零高 32 位，所以这一条同时完成「搬 32 位」和「高半补 0」。`movq` 会连同高 32 位一起搬，但那 32 位是调用者留下的垃圾，不保证为 0；`movslq` 做符号扩展，`x` 最高位为 1 时会得到负数，语义就错了。aarch64 上对应的是 `uxtw`。x86 上未实测（验证环境没有 x86 CPU），结论来自指令语义。
:::
:::

::: errata 关于传送与算术的五个误解
1. **「`movl` 只改低 32 位，高 32 位保持原样」**——在 x86-64 上写 32 位寄存器会把高 32 位清零。`movb`、`movw` 才只改对应的窄部分。
2. **「`inc` 和 `add $1` 完全等价」**——结果一样，标志位不一样：`inc`/`dec` 不改 CF。多精度加法里用 `adc` 接着 `inc`，CF 可能是错的。
3. **「`lea` 会设置标志位」**——不会。`lea` 只算地址，标志位保持原样；这也是编译器敢把它塞进算术序列的原因。
4. **「无符号乘法必须用 `mul`」**——只保留低 64 位时，`imul` 和 `mul` 的低半相同，编译器常用 `imul`；`mul` 的无符号语义体现在 128 位全结果和 CF/OF 上。
5. **「常数乘法一定编译成 `imul`」**——乘 2 的幂用移位，乘 3/5/9 用 `lea`，乘 48 这种数拆成 `3z << 4`。具体怎么拆随编译器和优化级别变，别背死一条序列。
:::

### 1.3.3 小结

① 传送和运算按宽度带后缀，32 位写会清零高半；② 零扩展与符号扩展是两种语义，`movl`/`movslq`、`uxtw`/`sxtw` 各管一边；③ 常数乘法常被强度削减成移位和 `lea`。如果只记住一件事，那就是：**看到 `movl` 写寄存器，先想到它会顺手把高 32 位清零。**

## 1.3.4 条件码、比较与跳转 {#sec-1.3.4}

这一节回答：`if (x < 0)` 编译后为什么先做一次减法或按位与，再看几个标志位？`jg` 和 `ja` 只差一个字母，为什么不能互换？

::: preview 先抓住一件事
CPU 用四个条件码记住最近一次运算的结果：CF（进位）、ZF（为零）、SF（符号）、OF（溢出）。`cmp` 和 `test` 只设标志、不写结果；条件跳转和条件传送都读这几个标志。有符号比较用 `jg/jl`，无符号比较用 `ja/jb`，同一组标志位有两种解释。
:::

看一个分段函数：

```c
long classify(long x)
{
    if (x < 0) return -1;
    if (x == 0) return 0;
    return 1;
}
```

先猜：这段代码会编译出几条跳转？

x86-64（macOS 上 clang 21 交叉汇编，`-O2`）：

```asm
classify:
    testq   %rdi, %rdi
    sets    %al
    setg    %cl
    subb    %al, %cl
    movsbq  %cl, %rax
    retq
```

aarch64（`ubuntu24`，GCC 13.3，`-O2`）：

```asm
classify:
    cmp     x0, 0
    cset    x0, ne
    csinv   x0, x0, xzr, ge
    ret
```

两边都没有跳转。x86 先 `testq %rdi,%rdi`（自己与自己按位与），只设标志；`sets %al` 把「SF=1」写成 1 字节的 0/1，`setg %cl` 把「大于 0」写成 0/1；`subb %al,%cl` 做 `(x>0) - (x<0)`；最后 `movsbq` 把这一字节符号扩展成 64 位返回值。结果正好是 x < 0 得 -1、x = 0 得 0、x > 0 得 1。aarch64 用 `cset`/`csinv` 组合出同样的值：x ≥ 0 时保留 `cset` 的 0/1，x < 0 时让 `csinv` 取反零得到 -1。aarch64 上实跑 `classify(-5)`、`classify(0)`、`classify(5)` 得到 -1、0、1；x86 上未实测（验证环境没有 x86 CPU）。

四个条件码（condition code，CPU 用几个标志位记住上一次运算结果的机制）：

| 标志 | 名称 | 含义 |
|:--|:--|:--|
| `CF` | 进位 | 无符号加法进位 / 减法借位 |
| `ZF` | 零 | 结果为 0 |
| `SF` | 符号 | 结果的最高位为 1（按有符号看是负数） |
| `OF` | 溢出 | 有符号运算溢出了结果范围 |

`cmp a, b` 在 AT&T 语法里算 `b - a`，只设标志、不写回操作数；`test a, b` 算 `b & a`，同样只设标志，并且把 CF、OF 清零。顺序容易记反：`cmpq %rsi, %rdi` 算的是 `%rdi - %rsi`，所以后面跟 `jg` 时，判断的是「`%rdi` 大于 `%rsi`」。

条件跳转读这些标志：

| 指令 | 条件 | C 语义（`cmp b, a` 后） |
|:--|:--|:--|
| `je` / `jz` | `ZF=1` | `a == b` |
| `jne` / `jnz` | `ZF=0` | `a != b` |
| `js` | `SF=1` | 结果为负（`b=0` 时即 `a<0`） |
| `jg` | `ZF=0 && SF=OF` | `a > b`（有符号） |
| `jge` | `SF=OF` | `a >= b` |
| `jl` | `SF!=OF` | `a < b` |
| `jle` | `ZF=1 \|\| SF!=OF` | `a <= b` |
| `ja` | `CF=0 && ZF=0` | `a > b`（无符号） |
| `jb` | `CF=1` | `a < b`（无符号） |

有符号和无符号用不同指令，是因为同一组标志有两种解释。`-1` 和 `0` 比较：按有符号是 -1 < 0，按无符号是 2^64 - 1 > 0，位模式完全相同。编译器根据 C 类型选 `jg` 还是 `ja`；选错，负数就会排到很大的位置。

看四个小函数，先猜 `max` 和 `umax` 的指令差在哪：

```c
long max(long a, long b)                    { return a > b ? a : b; }
long umax(unsigned long a, unsigned long b) { return a > b ? a : b; }
int  lt(long a, long b)                     { return a < b; }
```

x86-64（macOS 上 clang 21 交叉汇编，`-O2`）：

```asm
max:
    movq    %rsi, %rax
    cmpq    %rsi, %rdi
    cmovgq  %rdi, %rax
    retq
umax:
    movq    %rsi, %rax
    cmpq    %rsi, %rdi
    cmovaq  %rdi, %rax
    retq
lt:
    xorl    %eax, %eax
    cmpq    %rsi, %rdi
    setl    %al
    retq
```

aarch64（`ubuntu24`，GCC 13.3，`-O2`）：

```asm
max:
    cmp     x1, x0
    csel    x0, x1, x0, ge
    ret
umax:
    cmp     x1, x0
    csel    x0, x1, x0, cs
    ret
lt:
    cmp     x0, x1
    cset    w0, lt
    ret
```

`max` 和 `umax` 只差条件：`cmovg` 用有符号「大于」，`cmova` 用无符号「高于」；aarch64 对应 `ge` 和 `cs`（进位位置位，等价于无符号大于等于）。`lt` 先把 `%eax` 清零，再 `setl %al`；`set` 只写一个字节，不先把高位清零，返回值的高 24 位就是旧的垃圾。

`cmov`（conditional move，条件传送）和 `set` 都是「不跳转」的写法。编译器偏爱它们，因为跳转可能预测失败，代价比一条条件传送高。但 `cmov` 有一个硬条件：源操作数必须能安全地无条件算出来。`p ? *p : 0` 不能直接改成「先读 `*p`，再按条件选」——`p` 为空时，读 `*p` 已经段错误了。这种场合只能用分支。

条件跳转并没有消失，带副作用的 `if` 仍会编译成跳转。`void store_if(long x) { if (x != 0) g = x; }` 在 x86-64 上：

```asm
store_if:
    testq   %rdi, %rdi
    je      .LBB0_2
    movq    %rdi, g(%rip)
.LBB0_2:
    retq
```

aarch64 用 `cbz` 跳过存储：

```asm
store_if:
    cbz     x0, .L1
    adrp    x1, .LANCHOR0
    str     x0, [x1, #:lo12:.LANCHOR0]
.L1:
    ret
```

`je` 和 `cbz` 与 `set`/`cmov` 正好相反：前者改变控制流，后者只改数据。读到一条 `je`，先问「它跳过的这段有没有副作用」；读到一条 `cmov`，先问「源操作数无条件算出来安全吗」。

::: ex 例 1.3.4 · 先猜有没有跳转 {#ex-1.3.4}
`classify` 有两条 `if`，先猜它编译后有几条跳转、几条 `set`。再看上面的汇编，解释为什么优化器敢把分支消掉。

::: sol 解答
零条跳转、两条 `set`（`sets` 和 `setg`），外加一条 `subb`。两个分支都只返回常数，没有副作用，优化器可以把「走哪条路」变成「算出一个 -1/0/1 的值」：`sets` 给出 x < 0，`setg` 给出 x > 0，两者相减就是分段结果。aarch64 同样没有跳转，用 `cset`/`csinv` 完成。x86 上未实测，结论来自编译器输出。
:::
:::

::: errata 关于条件码的五个误解
1. **「`cmp` 会修改操作数」**——不会。`cmp` 只做减法并设标志；要写回结果用 `sub`。
2. **「`test` 和 `cmp` 一样」**——`test` 做按位与，常用来判断「是否为零」或「某一位是否为 1」；`cmp` 做减法，用来比大小。
3. **「`jg` 和 `ja` 可以互换」**——不能。`jg` 按有符号解释，`ja` 按无符号解释；比较负数或指针时混用，结果会反。
4. **「`set` 会把整个寄存器写成 0 或 1」**——只写目标字节。要把结果当 32/64 位整数用，先清零或零扩展。
5. **「`cmov` 总比分支快」**——源操作数必须能安全地无条件求值。可能越界的指针解引用不能塞进 `cmov`，否则本来不会发生的访问会先发生。
:::

### 1.3.4 小结

① `cmp`/`test` 只设 CF、ZF、SF、OF，条件跳转和 `set`/`cmov` 读它们；② 有符号用 `jg/jl`，无符号用 `ja/jb`，位模式相同、解释不同；③ 小分支常被 `set`/`cmov` 消掉，但源操作数必须能安全求值。如果只记住一件事，那就是：**先看 C 类型是有符号还是无符号，再决定读哪个跳转条件。**

## 1.3.5 if、switch、循环的汇编形态 {#sec-1.3.5}

这一节回答：一段带 `if`、`switch` 和 `for` 的 C，编译后控制流长什么样？为什么同样的 `switch`，有时变成一张表，有时变成一串比较？

::: preview 先抓住一件事
`if` 有两种常见译法：两边都有副作用时用条件跳转；两边都能安全求值时，用 `cmov`/`csel` 把分支变成一次选择。`switch` 在 case 密集、各分支块又互不相同时，常编译成跳转表（jump table，把各 case 的目标地址或偏移排成一张表，用下标直接取）：一次越界检查，再用下标取出目标地址跳过去；case 稀疏时退回比较树。循环的 `for`、`while`、`do-while` 在优化后往往收敛成同一种「入口判断 + 循环体 + 回边」。
:::

先看一个没有副作用的绝对值函数：

```c
long absdiff(long x, long y)
{
    long r;
    if (x < y) r = y - x;
    else       r = x - y;
    return r;
}
```

先猜：编译后会不会出现条件跳转？

x86-64（macOS 上 clang 21 交叉汇编，`--target=x86_64-linux-gnu -O1 -S`）：

```asm
absdiff:
    movq    %rdi, %rax
    subq    %rsi, %rax
    subq    %rdi, %rsi
    cmovgeq %rsi, %rax
    retq
```

aarch64（`ubuntu24`，Ubuntu 24.04.5，aarch64，GCC 13.3，`-O1 -S`）：

```asm
absdiff:
    sub     x2, x1, x0
    sub     x3, x0, x1
    cmp     x0, x1
    csel    x0, x3, x2, ge
    ret
```

两条路都算了：x86 先把 `x-y` 放 `%rax`、`y-x` 放 `%rsi`；`subq %rdi,%rsi` 用 `y-x` 设置标志，`cmovge` 在 `y >= x`（也就是 `x <= y`）时把 `%rsi` 选进 `%rax`。aarch64 把两个差分别放 `x2`、`x3`，`cmp x0,x1` 后 `csel` 按 `x >= y` 选 `x-y`，否则选 `y-x`。这样没有跳转，流水线不会因预测失败而清空。代价是两条路都执行；如果某条路可能解引用空指针，就不能这么改，编译器会退回分支。以上 x86 汇编由交叉编译器生成，写作机没有 x86 CPU，运行结果未实测。

把 `if` 换成有副作用的写法：

```c
long g;
void store_if(long x) { if (x != 0) g = x; }
```

x86-64 编译出一条 `je`，aarch64 用 `cbz` 跳过存储：

```asm
store_if:                    # x86-64
    testq   %rdi, %rdi
    je      .LBB1_2
    movq    %rdi, g(%rip)
.LBB1_2:
    retq
```

```asm
store_if:                    # aarch64
    cbz     x0, .L4
    adrp    x1, .LANCHOR0
    str     x0, [x1, #:lo12:.LANCHOR0]
.L4:
    ret
```

`g = x` 是副作用，不能无条件执行，这时只能改控制流。读到一个 `je`/`cbz`，先问它跳过的块里有什么副作用；读到一个 `cmov`/`csel`，先问两条路无条件算是否安全。

`switch` 的第一种形态是跳转表。下面每个 case 都改全局变量，编译器没法把结果合并成一个算式：

```c
long g;
void pickv(int x)
{
    switch (x) {
    case 0: g += 10; break;
    case 1: g -= 22; break;
    case 2: g ^= 35; break;
    case 3: g |= 48; break;
    default: g = -1; break;
    }
}
```

x86-64（clang 21，`-O1`，只摘控制流，`...` 表示省略分支体）：

```asm
pickv:
    cmpl    $3, %edi
    ja      .LBB0_1
    movl    %edi, %eax
    leaq    .LJTI0_0(%rip), %rcx
    movslq  (%rcx,%rax,4), %rax
    addq    %rcx, %rax
    jmpq    *%rax
...
.LJTI0_0:
    .long   .LBB0_3-.LJTI0_0
    .long   .LBB0_4-.LJTI0_0
    .long   .LBB0_5-.LJTI0_0
    .long   .LBB0_6-.LJTI0_0
```

`cmpl $3,%edi; ja` 是越界检查。`ja` 按无符号比较，负下标会变成很大的无符号数，也会走 `default`。表项不是 8 字节绝对地址，而是 4 字节的「目标 - 表基址」偏移；`movslq` 把它符号扩展成 64 位，加上表基址 `%rcx`，再 `jmpq *%rax`。相对偏移让表留在只读数据段，加载到任何地址都不必重定位，表也小一半。

同一段 C 在 aarch64 上，GCC 13.3 这次没有生成表，而是比较树：

```asm
pickv:
    cmp     w0, 2
    beq     .L21
    cmp     w0, 2
    bgt     .L22
    cbz     w0, .L23
    cmp     w0, 1
    bne     .L27
...
```

这四个 case 上，GCC 13.3 选择了比较树。跳转表是编译器的选择，不是 `switch` 的语义；同一段 C 换编译器、换优化级别，形态就可能变，不必把某一种形状记成固定规则。

case 稀疏时，跳转表会浪费大量表项。把 case 改成 0、10、100、1000（函数名 `sparse`），x86-64 上得到的是一棵按范围切分的比较树：

```asm
sparse:
    cmpl    $99, %edi
    jg      .LBB3_3
    testl   %edi, %edi
    je      .LBB3_2
    cmpl    $10, %edi
    jne     .LBB3_9
    movl    $11, %eax
    retq
...
```

先按 99 把范围切成两半，再在每半里比较。0 到 1000 如果建表要 1001 项，绝大多数都指向 `default`，不划算。这种形状叫比较树或判定树（decision tree）；最坏情况比较次数是对数级，但每次比较都要一次条件跳转。

循环的三种写法在优化后很接近。看 `for` 版本：

```c
long sum(long *a, long n)
{
    long s = 0;
    for (long i = 0; i < n; i++) s += a[i];
    return s;
}
```

x86-64（clang 21，`-O1`）：

```asm
sum:
    testq   %rsi, %rsi
    jle     .LBB1_1
    xorl    %ecx, %ecx
    xorl    %eax, %eax
.LBB1_4:
    addq    (%rdi,%rcx,8), %rax
    incq    %rcx
    cmpq    %rcx, %rsi
    jne     .LBB1_4
    retq
.LBB1_1:
    xorl    %eax, %eax
    retq
```

aarch64（GCC 13.3，`-O1`）：

```asm
sum:
    cmp     x1, 0
    ble     .L32
    mov     x2, x0
    add     x3, x0, x1, lsl 3
    mov     x0, 0
.L31:
    ldr     x1, [x2], 8
    add     x0, x0, x1
    cmp     x2, x3
    bne     .L31
.L29:
    ret
.L32:
    mov     x0, 0
    b       .L29
```

两边都先判断 `n <= 0`，再进循环体，最后一条回边跳回循环头。x86 保留了下标 `i`（`%rcx`），用 `(%rdi,%rcx,8)` 寻址；aarch64 把下标换成了指针 `x2`，`ldr x1,[x2],8` 在取数后自动把指针加 8。后者就是归纳变量优化（induction variable optimization）：把「每次算 `a + 8i`」变成「指针自己往前走」。

`while` 版本 `while (n > 0) { s += *a++; n--; }` 在 `-O1` 下生成同一种循环形状，只是下标与指针的用法可能不同；`do-while` 只是保证循环体至少执行一次，入口判断的位置不同。优化器会把能证明的边界提到入口，三种写法常常只剩一种骨架。

::: ex 例 1.3.5 · 先猜跳转表的两个细节 {#ex-1.3.5}
看 `pickv` 的汇编，先猜两件事：`cmpl $3,%edi` 后面为什么用 `ja` 而不是 `jg`？表项为什么写 `.long .LBB0_3-.LJTI0_0`，而不是 `.quad .LBB0_3`？

::: sol 解答
`ja` 是无符号「高于」。`x` 是 `int`，负数的位模式按无符号看大于 3，正好落进 `default`；若用 `jg`，负数会被当成「不大于 3」，接着用负下标读表，越界。表项用 32 位相对偏移，是为了位置无关：表放在只读数据段，加载地址变了也不用改表项；`.quad` 绝对地址会引入重定位，表也占两倍空间。
:::
:::

::: errata 关于控制流的五个误解
1. **「`switch` 一定生成跳转表」**——不一定。case 稀疏、分支块可以合并、或者编译器成本模型认为比较更便宜时，都会生成比较树。同一段 C 在 clang/x86-64 与 GCC/aarch64 上就给出了不同形态。
2. **「`ja` 和 `jg` 只差有符号/无符号，随便用」**——边界检查要用 `ja`。负下标按无符号看是巨大值，`ja` 会把它挡在表外；`jg` 放它过去就会读越界。
3. **「`for`、`while`、`do-while` 的汇编一定不同」**——优化后经常相同。真正的语义差别只有 `do-while` 至少执行一次；入口判断可以被优化器提前或复制。
4. **「`cmov` 总比跳转快」**——源操作数必须能安全地无条件求值。可能缺页（访问的页不在内存，内核要先把它换入）或解引用空指针的表达式不能塞进 `cmov`，否则本来不发生的访问会先发生。
5. **「跳转表一定是 O(1)，所以总更快」**——间接跳转也可能预测失败，还要防 Spectre 一类推测执行攻击；case 很少时，几次直接比较往往更便宜。
:::

### 1.3.5 小结

① `if` 有副作用就用条件跳转，能安全求值就用 `cmov`/`csel`；② `switch` 密集且分支块各不相同时常生成跳转表，表项是相对偏移，稀疏时退回比较树；③ 循环优化后常收敛为「入口判断 + 循环体 + 回边」，下标可能被换成指针。如果只记住一件事，那就是：**先看分支有没有副作用，再看编译器选了跳转还是条件传送。**

::: method 即时自测 · 1.3.5
**Q1（记忆）** 跳转表的表项在 `pickv` 里是几个字节？`movslq` 和 `addq %rcx,%rax` 各做什么？

**Q2（辨析）** `absdiff` 没有跳转，`store_if` 有跳转。两段 C 的差别是什么？

**Q3（应用）** 把 `sum` 的 `for` 循环改写成 `while (n-- > 0) s += *a++;`，循环末尾的减一与比较会变成什么样？

**Q4（迁移）** 一个 `switch` 有 100 个连续 case，每个分支都执行同一句 `g++` 后 `break`。编译器可能不建表，为什么？

::: sol 第 1 题答案
**A1** 每项 4 字节，存的是「目标地址 - 表基址」的 32 位偏移。`movslq` 把偏移符号扩展成 64 位；`addq %rcx,%rax` 加上表基址，得到目标的绝对地址。

::: sol 第 2 题答案
**A2** `absdiff` 两个分支都只是算术，没有副作用，两条路都能安全求值，所以用 `cmov` 选结果；`store_if` 的分支写全局变量，是有副作用，不能无条件执行，只能用条件跳转。
:::

::: sol 第 3 题答案
**A3** `n-- > 0` 把「比较」和「减一」放进同一个条件：先比较旧值是否大于 0，再把 `n` 减一。循环体末尾不再单独写 `n--`，但入口仍要判断 `n` 的初值，不能无条件先执行。aarch64 上常见的是 `cmp` 加 `sub`/`cset` 组合，具体形状随优化级别变。
:::

::: sol 第 4 题答案
**A4** 100 个分支做的事完全一样，编译器可以把它们合并成「范围检查 + 一次 `g++`」，不需要 100 个表项，也不需要 100 次比较。跳转表只在各分支无法合并时才有优势。
:::
:::



## 1.3.6 栈帧、call/ret 与参数传递 {#sec-1.3.6}

这一节回答：调用一个函数时，返回地址、参数、局部变量在栈上怎么排？为什么第 7 个参数和第 1 个参数的取法完全不同？

::: preview 先抓住一件事
`call` 把返回地址压栈再跳转，`ret` 从栈顶弹出地址跳回去。x86-64 的前 6 个整数参数放寄存器，第 7 个起由调用者压栈；aarch64 有 8 个参数寄存器，第 9 个才上栈。被调用函数用序言建立栈帧、用尾声拆除；x86-64 要求 `call` 前 `%rsp` 16 字节对齐，aarch64 要求 `sp` 始终 16 字节对齐。x86-64 的叶子函数还能直接用栈指针以下的 128 字节红区。
:::

先看 9 个参数的调用。选 9 个，是为了让两种 ABI 都把一部分参数放到栈上：

```c
long callee9(long a, long b, long c, long d, long e,
             long f, long g, long h, long i);

long caller9(void)
{
    return callee9(1, 2, 3, 4, 5, 6, 7, 8, 9);
}
```

x86-64（macOS 上 clang 21 交叉汇编，`--target=x86_64-linux-gnu -O2 -S`）：

```asm
caller9:
    pushq   %rax
    subq    $8, %rsp
    movl    $1, %edi
    movl    $2, %esi
    movl    $3, %edx
    movl    $4, %ecx
    movl    $5, %r8d
    movl    $6, %r9d
    pushq   $9
    pushq   $8
    pushq   $7
    callq   callee9@PLT
    addq    $32, %rsp
    popq    %rcx
    retq
```

aarch64（`ubuntu24`，GCC 13.3，`-O2 -S`）：

```asm
caller9:
    sub     sp, sp, #32
    mov     x0, 9
    mov     x7, 8
    mov     x6, 7
    mov     x5, 6
    mov     x4, 5
    stp     x29, x30, [sp, 16]
    add     x29, sp, 16
    mov     x3, 4
    mov     x2, 3
    str     x0, [sp]
    mov     x1, 2
    mov     x0, 1
    bl      callee9
    ldp     x29, x30, [sp, 16]
    add     sp, sp, 32
    ret
```

x86-64 的参数 1–6 在 `%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9`；7、8、9 按从右到左压栈，所以离返回地址最近的是 7。`pushq %rax` 先把栈从 8 调到 0，`subq $8` 又调回 8；三次参数压栈再把它变成 0，`call` 压入返回地址后，`callee9` 入口正好是 8。收尾的 `popq %rcx` 只是把这 8 字节弹掉，弹出的值不用。`call` 前 `%rsp % 16 == 0` 是 ABI 的硬要求；不对齐时，用到 `movaps` 的 SSE 代码会直接崩溃。

aarch64 的前 8 个参数在 `x0`–`x7`，第 9 个放在 `[sp]`。`bl` 把返回地址写进 `x30`，不压栈，所以 `callee9` 入口的 `[sp]` 就是第 9 个参数。x86 侧只做了交叉编译，没有在 x86 CPU 上运行；aarch64 侧在 `ubuntu24` 上编译，运行中的寄存器现场未测（原因见 [1.3.8](#sec-1.3.8)）。这是两种 ABI 最容易混淆的一处：

| 位置（callee 入口） | x86-64 | aarch64 |
|:--|:--|:--|
| 返回地址 | `0(%rsp)`，`call` 压入 | `x30` 寄存器 |
| 第 7 个参数 | `8(%rsp)` | `x6` |
| 第 8 个参数 | `16(%rsp)` | `x7` |
| 第 9 个参数 | `24(%rsp)` | `0(%rsp)` |

需要局部变量和递归时，编译器会建立完整的栈帧。看递归求和：

```c
long rsum(long n)
{
    if (n <= 0) return 0;
    return n + rsum(n - 1);
}
```

`-O0` 下 x86-64 的序言、递归调用与尾声：

```asm
rsum:
    pushq   %rbp
    movq    %rsp, %rbp
    subq    $32, %rsp
    movq    %rdi, -16(%rbp)
    cmpq    $0, -16(%rbp)
    jg      .LBB2_2
...
.LBB2_2:
    movq    -16(%rbp), %rdi
    subq    $1, %rdi
    callq   rsum
...
    addq    $32, %rsp
    popq    %rbp
    retq
```

aarch64 的同一段：

```asm
rsum:
    stp     x29, x30, [sp, -32]!
    mov     x29, sp
    str     x0, [sp, 24]
    cmp     x0, 0
    bgt     .L7
    mov     x0, 0
    b       .L8
.L7:
    ldr     x0, [sp, 24]
    sub     x0, x0, #1
    bl      rsum
...
.L8:
    ldp     x29, x30, [sp], 32
    ret
```

x86 的 `call` 自动把返回地址压在当前栈顶；aarch64 的 `bl` 只改 `x30`，所以递归前必须先把 `x29`（帧指针）和 `x30`（返回地址）存进栈帧，否则下一次 `bl` 会覆盖返回地址。`stp x29,x30,[sp,-32]!` 一次完成「减栈指针 + 存两个寄存器」，`ldp ... [sp],32` 是反向操作。

以 9 个参数为例，x86-64 建立帧指针后的栈长这样：

<pre class="layout">
高地址
        ┌──────────────────────────┐
        │ 第 9 个参数               │ 32(%rbp)
        │ 第 8 个参数               │ 24(%rbp)
        │ 第 7 个参数               │ 16(%rbp)
        ├──────────────────────────┤
        │ 返回地址                  │ 8(%rbp)
        ├──────────────────────────┤
        │ 保存的旧 %rbp             │ 0(%rbp)  ← %rbp 指向这里
        ├──────────────────────────┤
        │ 局部变量 / 临时空间        │ -8(%rbp), -16(%rbp), ...
        ├──────────────────────────┤
        │ 对齐填充                  │  ← %rsp
        └──────────────────────────┘
低地址
</pre>

读这张图抓住三点：

1. `%rbp` 指向「保存的旧 `%rbp`」，所以 `8(%rbp)` 是返回地址，`16(%rbp)` 是第 7 个参数，往上依次是第 8、9 个。
2. 参数 1–6 在寄存器里；被调用函数若需要它们的地址（比如 `&x`），才在序言里写到栈上。
3. `%rsp` 在函数执行期间会移动，局部变量用 `%rbp` 相对寻址更稳定；`-O2` 默认省略帧指针，改用 `%rsp` 相对寻址，调试器回溯时依赖 CFI（`.eh_frame`）信息。
4. aarch64 的 `x29` 指向帧的最低地址，返回地址在 `8(x29)`，局部变量常在正偏移（比如 `24(x29)`）；方向和这张 x86 图相反，不要照搬负偏移。

::: def 定义 1.3.6 · 栈帧（stack frame） {#def-1.3.6}
一次函数调用在栈上占用的区域，包含：调用者压入的栈参数、返回地址（x86-64 在栈上，aarch64 在 `x30`）、保存的帧指针与被调用者保存的寄存器、局部变量、临时空间和对齐填充。`%rbp`/`x29` 指向帧基址，`%rsp`/`sp` 指向栈顶。帧大小在编译期确定（`alloca` 和变长数组除外），由序言分配、尾声释放。
:::

叶子函数（不再调用其他函数）在 x86-64 上可以使用红区（red zone）：`%rsp` 以下 128 字节保证不被信号处理程序或中断处理程序改写。中断（interrupt）是硬件或定时器打断当前执行流、转去运行处理程序的机制。函数可以直接拿红区当临时空间，不调整 `%rsp`。同一段 C：

```c
long leaf(long x)
{
    volatile long a[4];
    a[0] = x; a[1] = x + 1; a[2] = x + 2; a[3] = x + 3;
    return a[0] + a[3];
}
```

x86-64（clang 21，`-O2`）没有一条调整 `%rsp` 的指令：

```asm
leaf:
    movq    %rdi, -40(%rsp)
    leaq    1(%rdi), %rax
    movq    %rax, -8(%rsp)
    leaq    2(%rdi), %rax
    movq    %rax, -24(%rsp)
    addq    $3, %rdi
    movq    %rdi, -32(%rsp)
    movq    -40(%rsp), %rax
    addq    -32(%rsp), %rax
    retq
```

aarch64 没有红区，必须先 `sub sp,sp,#32`，用完再 `add`：

```asm
leaf:
    sub     sp, sp, #32
    add     x3, x0, 1
    mov     x1, sp
    add     x2, x0, 2
    str     x0, [sp]
    add     x0, x0, 3
    str     x3, [x1, 8]
    str     x2, [x1, 16]
    str     x0, [x1, 24]
    ldr     x2, [sp]
    ldr     x0, [x1, 24]
    add     sp, sp, 32
    add     x0, x2, x0
    ret
```

`-40(%rsp)`、`-8(%rsp)` 都落在红区内。aarch64 的过程调用标准没有红区，编译器只能老老实实减栈指针。写内联汇编或信号处理代码时，别假设 x86 的红区在别的架构上也存在。

::: ex 例 1.3.6 · 先猜第 7 个参数在哪 {#ex-1.3.6}
同一个 `callee9(1,...,9)`，先猜两件事：x86-64 的 `callee9` 入口，第 7 个参数在 `%rsp` 往上第几字节？aarch64 的 `callee9` 入口，第 9 个参数又在哪？

::: sol 解答
x86-64 第 7 个在 `8(%rsp)`：`0(%rsp)` 是 `call` 压入的返回地址，7 是最后压栈的参数，离返回地址最近；8、9 分别在 `16(%rsp)`、`24(%rsp)`。aarch64 第 9 个在 `0(%rsp)`：前 8 个在 `x0`–`x7`，`bl` 不压栈，调用者预先放在 `[sp]`。x86-64 的 callee 入口是 `sp % 16 == 8`；aarch64 的 `sp` 始终 16 字节对齐，入口是 0。
:::
:::

::: errata 关于栈帧的五个误解
1. **「第 7 个参数一定在栈上」**——这是 x86-64 System V 的规则。aarch64 有 8 个参数寄存器，第 7 个在 `x6`；换 ABI 就要重算。
2. **「`call` 和 `jmp` 一样」**——`call` 会压返回地址，`jmp` 不会。手工 `jmp` 进函数再 `ret`，弹出来的是栈顶的旧值，跳到哪取决于栈上原有什么。
3. **「`%rbp` 总是帧指针」**——`-O2` 默认省略帧指针，`%rbp` 可能被当普通寄存器用。调试优化过的程序，回溯靠 `.eh_frame` 里的 CFI，不要假设 `%rbp` 链还在。
4. **「栈帧大小等于局部变量之和」**——还要加保存的寄存器、对齐填充、临时溢出槽。编译器常把多个小变量塞进同一个 8 字节槽。
5. **「红区每个架构都有」**——只有 x86-64 的 ABI 规定了 128 字节红区。aarch64 的叶子函数也要显式减 `sp`，不要照搬 x86 的写法。
:::

### 1.3.6 小结

① `call` 压返回地址、`ret` 弹出，aarch64 用 `bl`/`x30` 完成同一件事；② x86-64 前 6 个整数参数走寄存器、第 7 个起上栈，aarch64 是前 8 个走寄存器、第 9 个上栈；③ 序言建立帧、尾声拆除，`call` 前 `%rsp` 要 16 字节对齐；④ 红区只属于 x86-64。如果只记住一件事，那就是：**先看 ABI 有几个参数寄存器，再决定去寄存器还是栈上找参数。**

::: method 即时自测 · 1.3.6
**Q1（记忆）** x86-64 和 aarch64 各有多少个整数参数寄存器？第 7 个参数在两边分别放在哪？

**Q2（辨析）** 为什么 aarch64 的 `rsum` 序言要保存 `x30`，而 x86-64 的 `rsum` 不用显式保存返回地址？

**Q3（应用）** 一个 x86-64 函数入口是 `%rsp % 16 == 8`，它要调用一个参数全部在寄存器里的函数，且没有局部变量。最少要怎样调整栈指针才能 `call`？

**Q4（迁移）** 把 x86-64 的叶子函数 `leaf` 原样搬到 aarch64，只把寄存器名换掉，会发生什么？

::: sol 第 1 题答案
**A1** x86-64 有 6 个：`%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9`，第 7 个在 `8(%rsp)`。aarch64 有 8 个：`x0`–`x7`，第 7 个在 `x6`。
:::

::: sol 第 2 题答案
**A2** aarch64 的 `bl` 把返回地址写进 `x30`，递归调用会覆盖它，所以必须在序言把 `x30` 存进栈帧；x86-64 的 `call` 每次把返回地址压到栈上，递归层次各有一份，不需要额外保存。
:::

::: sol 第 3 题答案
**A3** 入口是 8，`call` 前要变成 0，所以执行一条 `subq $8, %rsp`，`call` 之后再 `addq $8, %rsp`。这条减法不承载参数，只为对齐。
:::

::: sol 第 4 题答案
**A4** x86 版本把局部数组放在 `-40(%rsp)` 等红区位置，没有减 `sp`；aarch64 没有红区，`-40(%rsp)` 已经在当前栈帧之外，可能被下一次调用或信号覆盖。必须先 `sub sp,sp,#32` 再存，返回前加回去。
:::
:::


## 1.3.7 数组、结构体与联合体的布局 {#sec-1.3.7}

这一节回答：`a[i]` 的地址怎么算？结构体里为什么有空洞？联合体为什么能用同一块 4 字节既表示 `int` 又表示 `float`？

::: preview 先抓住一件事
数组是连续存放的，元素地址 = 基址 + 下标 × 元素大小；二维数组按行主序摊平成一维。结构体按声明顺序放成员，但每个成员要满足自己的对齐要求，成员之间和结构体末尾都可能有填充。联合体的所有成员从同一地址开始，大小取最大成员。指令里的比例 1/2/4/8 就是为这些尺寸准备的。
:::

对 `T A[N]`，元素 `A[i]` 的地址是

$$
\&A[i] = A + i \times \text{sizeof}(T).
$$

二维数组 `T A[R][C]` 按行主序（row-major）存放，`A[i][j]` 的地址是

$$
\&A[i][j] = A + (i \times C + j) \times \text{sizeof}(T).
$$

`int A[4][5]` 里，`sizeof(int)=4`，所以 `&A[2][3] = A + (2*5+3)*4 = A + 52`。行主序意味着按行遍历时相邻元素在内存里也相邻，对缓存更友好；第 [1.6](ch06.md) 章会量化这个差别。

结构体的布局光看声明看不出来，直接打印：

```c
struct Point  { int x, y; };
struct Rect   { struct Point tl, br; };
struct Mixed  { char c; int i; char d; };
struct Padded { char c; long l; short s; };
struct Bits   { unsigned a:3; unsigned b:5; unsigned c:8; int d:4; };
struct Flex   { unsigned long n; int data[]; };
union  Value  { int i; float f; unsigned char bytes[4]; };
```

补上 `<stdio.h>` 和 `<stddef.h>`，在 `main` 里打印：

```c
int main(void)
{
    union Value v;
    printf("Point=%zu Rect=%zu Mixed=%zu Padded=%zu Bits=%zu Flex=%zu Value=%zu\n",
           sizeof(struct Point), sizeof(struct Rect), sizeof(struct Mixed),
           sizeof(struct Padded), sizeof(struct Bits), sizeof(struct Flex),
           sizeof(union Value));
    printf("Rect.br=%zu Mixed.i=%zu Mixed.d=%zu Padded.l=%zu Padded.s=%zu\n",
           offsetof(struct Rect, br), offsetof(struct Mixed, i),
           offsetof(struct Mixed, d), offsetof(struct Padded, l),
           offsetof(struct Padded, s));
    printf("align: Point=%zu Rect=%zu Mixed=%zu Padded=%zu\n",
           _Alignof(struct Point), _Alignof(struct Rect),
           _Alignof(struct Mixed), _Alignof(struct Padded));
    v.f = 1.0f;
    printf("1.0f bytes: %02x %02x %02x %02x\n",
           v.bytes[0], v.bytes[1], v.bytes[2], v.bytes[3]);
    return 0;
}
```

在 `ubuntu24`（aarch64，GCC 13.3）上编译运行，`sizeof`、`offsetof` 与 `_Alignof` 的输出是：

```text
Point=8 Rect=16 Mixed=12 Padded=24 Bits=4 Flex=8 Value=4
Rect.br=8 Mixed.i=4 Mixed.d=8 Padded.l=8 Padded.s=16
align: Point=4 Rect=4 Mixed=4 Padded=8
1.0f bytes: 00 00 80 3f
```

同一组 `sizeof`/`offsetof` 数字，用 `_Static_assert` 在 x86-64 目标上编译通过（`clang --target=x86_64-linux-gnu -fsyntax-only`）；x86-64 上的运行输出未实测。这些常见布局在两个 ABI 上一致，但不要把它当成跨架构保证：32 位 x86 的 `long` 是 4 字节，结构体大小会变。

逐项读这四行：

- `Point` 两个 `int`，4 字节对齐，共 8 字节；`Rect` 两个 `Point`，共 16 字节，`br` 在偏移 8。
- `Mixed` 是 `char, int, char`：`c` 在 0，`i` 要对齐到 4，所以 1–3 是填充；`d` 在 8；结构体整体对齐 4，末尾再填 3 字节，共 12。
- `Padded` 是 `char, long, short`：`l` 要对齐到 8，所以 1–7 是填充；`s` 在 16；整体对齐 8，末尾填 6 字节，共 24。
- `Bits` 的四个位域占 3+5+8+4=20 位，落在同一个 4 字节单元里；`Flex` 的 `data[]` 不占 `sizeof`，所以只有 `n` 的 8 字节。

二维数组的地址计算会被编译器拆成「乘行宽、加列偏移」：

```c
int grid(int (*a)[5], long i, long j) { return a[i][j]; }
```

x86-64（macOS 上 clang 21 交叉汇编，`--target=x86_64-linux-gnu -O2 -S`）：

```asm
grid:
    leaq    (%rsi,%rsi,4), %rax
    leaq    (%rdi,%rax,4), %rax
    movl    (%rax,%rdx,4), %eax
    retq
```

aarch64（GCC 13.3，`-O2`）：

```asm
grid:
    add     x1, x1, x1, lsl 2
    add     x1, x0, x1, lsl 2
    ldr     w0, [x1, x2, lsl 2]
    ret
```

x86 先用 `leaq (%rsi,%rsi,4)` 算 `5i`，再 `leaq (%rdi,%rax,4)` 算 `a + 20i`，最后 `(%rax,%rdx,4)` 加 `4j`。aarch64 同样先算 `5i`（`x1 + x1<<2`），再 `a + 20i`，最后按 `lsl 2` 取 `4j`。行宽 5 不是 2 的幂，所以「乘 5」单独出现；列下标乘 4 则直接塞进寻址模式。

结构体数组的下标要乘整个结构体的大小。`struct Padded` 是 24 字节，取 `p[i].l`：

```c
long parr(struct Padded *p, long i) { return p[i].l; }
```

x86-64（clang 21，`-O2`）：

```asm
parr:
    leaq    (%rsi,%rsi,2), %rax
    movq    8(%rdi,%rax,8), %rax
    retq
```

aarch64（GCC 13.3，`-O2`）：

```asm
parr:
    add     x1, x1, x1, lsl 1
    add     x1, x0, x1, lsl 3
    ldr     x0, [x1, 8]
    ret
```

x86 先算 `3i`，再用比例 8 得到 `24i`，最后加成员偏移 8；aarch64 先算 `3i`，再 `<<3` 得到 `24i`，`ldr` 的立即数 8 就是 `l` 的偏移。结构体越大，下标乘法的代价越高；把「数组的结构体」改成「结构体的数组」（每个字段一个数组）有时能减少这种乘法，但会改变访问局部性，要按实际访问模式选。

位域（bit-field）把几个小字段塞进同一个存储单元。`struct Bits` 的 `b` 从第 3 位开始、宽 5 位：

```c
int bits_b(struct Bits *p) { return p->b; }
```

```asm
bits_b:                     # x86-64
    movl    (%rdi), %eax
    shrl    $3, %eax
    andl    $31, %eax
    retq
```

```asm
bits_b:                     # aarch64
    ldr     w0, [x0]
    ubfx    x0, x0, 3, 5
    ret
```

x86 先右移 3 位把 `b` 挪到最低位，再用 `31`（5 个 1）掩码；aarch64 有一条 `ubfx`（unsigned bit field extract，无符号位域提取），一条指令完成「右移 + 掩码」。位域在内存里谁占高位、谁占低位由 ABI 规定，不要拿结构体直接写文件或发网络包。

联合体（union）的所有成员共享起始地址，大小取最大成员：

```c
int u2i(union Value *p) { return p->i; }
```

x86-64 是 `movl (%rdi), %eax; retq`，aarch64 是 `ldr w0, [x0]; ret`。`Value` 只有 4 字节，`i`、`f`、`bytes[4]` 都从偏移 0 开始。把 `1.0f` 写进去再按字节读，得到 `00 00 80 3f`：最低字节在前，最高字节 `3f` 里放着符号位和指数的高 7 位。按 `int` 读则是 `0x3f800000`，也就是 1065353216。

C 标准说「读联合体里非当前写入的成员」是实现定义行为（implementation-defined），GCC 和 clang 都支持这种类型双关（type punning）；要完全可移植，用 `memcpy` 把字节复制到目标类型，编译器通常也会优化成一条 `mov`。

柔性数组成员（flexible array member）`int data[]` 不占 `sizeof`，但可以从结构体末尾直接索引：

```c
int flex(struct Flex *p, long i) { return p->data[i]; }
```

x86-64 的 `movl 8(%rdi,%rsi,4), %eax` 和 aarch64 的 `add x1,x0,x1,lsl 2; ldr w0,[x1,8]` 都把 `data` 当成偏移 8 的数组。分配时一次给足：`malloc(sizeof(struct Flex) + n * sizeof(int))`。这是内核与协议栈里常见的「头部 + 载荷」布局，代价是按值赋值只带走头部、带不走载荷，`sizeof` 也不含载荷。

### 变长数组与 `alloca`：运行时调整栈指针 {#sec-1.3.7.1}

C99 的变长数组（variable-length array，VLA）`int a[n];` 在运行时按 `n` 调整栈指针：编译器生成「取 `n`、乘元素大小、向上对齐、减 `sp`/`%rsp`」的序列，`sizeof(a)` 也变成运行时值。VLA 不能初始化，不能做结构体成员；C11 把它改为可选，C++ 不支持。`alloca` 类似，但在当前函数栈上分配，函数返回即失效；在循环里无界调用会一路吃掉栈，直到碰到保护页。

::: ex 例 1.3.7 · 先猜两个结构体的大小 {#ex-1.3.7}
`Mixed { char c; int i; char d; }` 的成员只占 1+4+1=6 字节，为什么 `sizeof` 是 12？`Padded { char c; long l; short s; }` 只占 1+8+2=11 字节，为什么是 24？

::: sol 解答
`Mixed` 的 `i` 要 4 字节对齐，`c` 后面填 3 字节，`i` 在偏移 4，`d` 在偏移 8；结构体整体对齐取最大成员对齐 4，末尾再填 3 字节，总共 12。`Padded` 的 `l` 要 8 字节对齐，`c` 后面填 7 字节，`l` 在 8，`s` 在 16；整体对齐 8，末尾填 6 字节到 24。填充不是浪费，是让每个成员落在硬件要求的边界上。
:::
:::

::: errata 关于数据布局的五个误解
1. **「结构体大小等于成员大小之和」**——要把每个成员的对齐填充和末尾填充算进去。成员顺序换一下，大小可能从 24 变成 16。
2. **「联合体大小等于成员大小之和」**——联合体共享内存，大小取最大成员，再按最大对齐向上取整。
3. **「二维数组就是指针的数组」**——`int A[4][5]` 是一整块连续的 80 字节，`A[i]` 不是指针；`int **p` 才是「指针指向指针」，两者的寻址方式完全不同。
4. **「位域布局可以跨平台直接读写」**——位域的顺序、跨存储单元的方式由 ABI 决定。把 `struct Bits` 直接写进文件，换编译器可能读错。
5. **「`sizeof` 包含柔性数组的载荷」**——不包含。`sizeof(struct Flex)` 只有 8，载荷要自己按 `n` 分配、自己记住长度。
:::

### 1.3.7 小结

① 数组地址 = 基址 + 下标 × 元素大小，二维数组按行主序摊平；② 结构体按声明顺序放成员，对齐要求在成员之间和末尾留下填充；③ 联合体共享起始地址，大小取最大成员；④ 位域和柔性数组都依赖 ABI，不要直接序列化。如果只记住一件事，那就是：**看到结构体，先画偏移表，再算 `sizeof`，不要拿成员大小硬加。**

## 1.3.8 用 objdump 与 gdb 读机器码 {#sec-1.3.8}

这一节回答：拿到一个二进制，怎样从地址找到函数、从助记符读回源码结构？程序跑起来后，又怎样把 `pc`、`sp` 与栈上的值对上？

::: preview 先抓住一件事
`objdump` 是静态视角：它按符号表把 `.text` 一段段反汇编，给出地址、机器码和助记符。`gdb` 是动态视角：它在断点处停下，让你看寄存器、栈和内存。读现场的顺序是「`pc` 落在哪条指令 → 操作数是什么 → 地址指向哪里 → 值是多少」；优化过的代码没有帧指针，回溯要靠 `.eh_frame` 里的 CFI 信息。
:::

先准备一个带调试信息的程序。`sum` 对数组求和，`main` 传入 4 个元素：

```c
#include <stdio.h>

long sum(long *a, long n)
{
    long s = 0;
    for (long i = 0; i < n; i++) s += a[i];
    return s;
}

int main(void)
{
    long a[4] = {1, 2, 3, 4};
    printf("%ld\n", sum(a, 4));
    return 0;
}
```

```bash
gcc -O1 -g -fno-stack-protector demo.c -o demo
./demo
10
```

`objdump -d` 按地址顺序反汇编。`--no-show-raw-insn` 省掉机器码，只看助记符：

```text
$ objdump -d --no-show-raw-insn demo | sed -n '/<sum>:/,+14p'
0000000000000798 <sum>:
 798:	cmp	x1, #0x0
 79c:	b.le	7c0 <sum+0x28>
 7a0:	mov	x2, x0
 7a4:	add	x3, x0, x1, lsl #3
 7a8:	mov	x0, #0x0
 7ac:	ldr	x1, [x2], #8
 7b0:	add	x0, x0, x1
 7b4:	cmp	x2, x3
 7b8:	b.ne	7ac <sum+0x14>
 7bc:	ret
 7c0:	mov	x0, #0x0
 7c4:	b	7bc <sum+0x24>
```

左边是地址，冒号后是助记符；`<sum+0x28>` 是目标相对函数入口的偏移。`b.le 7c0` 表示「小于等于 0 就跳到 0x7c0」，也就是 `n<=0` 时直接返回 0。地址 `0x798` 是链接时分配的偏移；程序是 PIE（position-independent executable，位置无关可执行文件），加载后还要加上基址。具体地址会随编译器和链接选项变化，读法不变。

加 `-S` 能把源码和汇编交错显示，条件是编译时带 `-g`：

```text
$ objdump -d -S --no-show-raw-insn demo | sed -n '/<sum>:/,+12p'
0000000000000798 <sum>:
long sum(long *a, long n)
{
    long s = 0;
    for (long i = 0; i < n; i++)
 798:	cmp	x1, #0x0
 79c:	b.le	7c0 <sum+0x28>
 7a0:	mov	x2, x0
 7a4:	add	x3, x0, x1, lsl #3
    long s = 0;
 7a8:	mov	x0, #0x0
```

一行源码下面跟着它编译出的几条指令；优化后一条源码可能对应多条指令，也可能完全没有指令。

符号表给出函数的起止。`readelf -s` 的 `Value` 是偏移，`Size` 是字节数：

```text
$ readelf -s demo | grep -E ' sum$| main$'
    88: 0000000000000798    48 FUNC    GLOBAL DEFAULT   13 sum
    94: 00000000000007c8    68 FUNC    GLOBAL DEFAULT   13 main
$ nm -n demo | grep -E ' T (sum|main)$'
0000000000000798 T sum
00000000000007c8 T main
```

`sum` 从 `0x798` 开始、长 48 字节，`0x798+48=0x7c8` 正好是 `main` 的起点。这个关系很有用：即使 `objdump` 不能反汇编，符号表也能告诉你函数的边界。`nm` 的 `T` 表示这个符号在 `.text` 段、是全局的。

`gdb` 不启动进程也能反汇编：

```text
$ gdb -q -batch -ex "disassemble /m sum" ./demo
Dump of assembler code for function sum:
4	{
5	    long s = 0;
   0x00000000000007a8 <+16>:	mov	x0, #0x0
...
7	        s += a[i];
   0x00000000000007ac <+20>:	ldr	x1, [x2], #8
   0x00000000000007b0 <+24>:	add	x0, x0, x1
...
End of assembler dump.
```

`/m` 带源码，`<+16>` 是相对函数入口的偏移（上面的输出有省略）。`disassemble /r sum` 还会给出机器码，下面摘三条：

```text
   0x0000000000000798 <+0>:	f100003f	cmp	x1, #0x0
   0x000000000000079c <+4>:	5400012d	b.le	0x7c0 <sum+40>
...
   0x00000000000007ac <+20>:	f8408441	ldr	x1, [x2], #8
```

aarch64 的指令定长 4 字节，所以地址每次加 4；x86-64 的指令 1–15 字节不等，地址的跳法要看每条指令的长度。这一段与 [1.3.10](#sec-1.3.10) 的机器码编码接得上。

进程跑起来后，断点、单步和寄存器查看用这些命令：

```text
(gdb) break sum
(gdb) run
(gdb) info registers x0 x1 sp pc
(gdb) x/4gx $sp
(gdb) x/6i $pc
(gdb) stepi
(gdb) info registers pc
(gdb) finish
(gdb) info registers x0
(gdb) bt
(gdb) info frame
```

`break sum` 按符号下断点，不写死地址；PIE 加载后由动态链接器决定基址，gdb 会自己换算。`info registers` 看参数、栈指针和程序计数器；aarch64 的参数在 `x0`、`x1`，x86-64 在 `%rdi`、`%rsi`。`x/4gx $sp` 以 8 字节为单位看栈顶 4 个值，`x/6i $pc` 看当前指令附近。`stepi` 单步一条机器指令，不是一行源码；`finish` 跑到当前函数返回，返回值在 `x0`/`%rax`。`bt` 打印调用栈，`info frame` 给出当前帧的返回地址、保存的寄存器和栈边界。

::: note 这台 VM 上的 gdb 为什么没有运行现场
`ubuntu24` 的 gdb 15.1 可以静态反汇编，但一执行 `run` 就报：

```text
Unable to fetch SVE/SSVE vector length: Invalid argument.
```

随后 gdb abort。原因是这个虚拟机/容器环境对 aarch64 SVE 寄存器的探测失败，不是命令写错。因此本节只贴了不启动进程的 `disassemble` 输出，运行中的寄存器与栈现场未实测；x86-64 上同样没有运行现场。读现场的方法不依赖具体数值，下面照常给出。
:::

x86 侧的对象文件也能用 GNU 工具读，但只能读 ELF 元数据，不能反汇编。把 `access.c` 用 clang 交叉编成 x86-64 的 `.o`，在 `ubuntu24` 上：

```text
$ readelf -h access.x86.o | grep Machine
  Machine:                           Advanced Micro Devices X86-64
$ readelf -s access.x86.o | grep rect_br_x
     3: 0000000000000000     4 FUNC    GLOBAL DEFAULT    2 rect_br_x
$ nm access.x86.o | head -3
0000000000000030 T bits_b
0000000000000040 T flex
0000000000000010 T grid
$ objdump -d access.x86.o
objdump: can't disassemble for architecture UNKNOWN!
```

`readelf` 和 `nm` 读的是 ELF 头、节表和符号表，这些结构与指令集无关，所以 aarch64 主机也能解析 x86-64 的 `.o`。`objdump -d` 需要对应架构的反汇编后端；这个 GNU binutils 只编了 aarch64 后端，遇到 x86-64 的机器码只能报错。符号大小仍有信息：`rect_br_x` 是 4 字节，与「一条 `movl 8(%rdi),%eax` 加一条 `retq`」相符——这是把汇编文本和符号大小对照出来的，不是反汇编结果。

读崩溃现场按四步走：

1. 用 `bt` 或 `info frame` 找到出事的 `pc`，再用 `x/i $pc` 看它落在哪条指令。
2. 用 `info registers` 看这条指令的操作数：源寄存器、目的寄存器、栈指针。
3. 若操作数是内存，按「位移 + 基址 + 变址 × 比例」算出地址，再用 `x/gx 地址` 看那里存了什么。
4. 若 `pc` 是 0 或明显非法的地址，先怀疑返回地址被写坏：栈溢出、越界写数组、函数指针被覆盖，都会让 `ret` 弹到一个不存在的地址。

优化过的代码没有帧指针，`bt` 依赖 `.eh_frame` 的 CFI（call frame information，调用帧信息）；它通常仍能工作，但内联函数会被折叠，栈上可能显示 `??`。这时 `info frame` 给出的 `saved rip`/`saved pc` 比 `bt` 的名字更可靠。

::: ex 例 1.3.8 · 先猜符号大小怎么用 {#ex-1.3.8}
`readelf -s` 显示 `sum` 在 `0x798`、大小 48，`main` 在 `0x7c8`。先猜：`0x798 + 48` 等于多少？这个和能帮你做什么？

::: sol 解答
`48 = 0x30`，`0x798 + 0x30 = 0x7c8`，正好是 `main` 的起点。符号大小给出了函数的地址范围，反汇编时可以只看到 `0x7c8` 为止；即使 `objdump` 不能反汇编，也能从符号表判断函数边界。反过来，如果两个函数之间还有空隙，那段通常是编译器插入的对齐填充（`nop`）。
:::
:::

::: errata 关于反汇编与调试的五个误解
1. **「`objdump` 默认是 Intel 语法」**——默认是 AT&T（源, 目的，寄存器带 `%`）。`-M intel` 只对 x86 后端有效；在 aarch64 上会报 `unrecognised disassembler option: intel`。
2. **「符号表里的地址就是运行时的绝对地址」**——可执行文件是 PIE 时，符号值是相对基址的偏移；加载后要加上随机化的基址。`objdump` 显示的是链接时的偏移。
3. **「`objdump` 能反汇编任何 ELF」**——它需要对应架构的后端。作者的 aarch64 环境读 x86-64 的 `.o` 时，`readelf`/`nm` 正常，`objdump -d` 报 `can't disassemble for architecture UNKNOWN!`。
4. **「`stepi` 和 `step` 一样」**——`stepi` 执行一条机器指令，`step` 执行一行源码。一行 C 可能对应多条指令，调试优化代码时两者差别很大。
5. **「`bt` 永远准确」**——没有帧指针时，`bt` 靠 CFI 展开；内联、尾调用、手写汇编都可能让它显示 `??` 或跳过一帧。要核对 `info frame` 与栈上的返回地址。
:::

### 1.3.8 小结

① `objdump` 按符号和节表静态反汇编，`-S` 需要 `-g`，`-M intel` 只限 x86；② `readelf`/`nm` 读 ELF 元数据，不需要指令集后端，符号大小能给出函数边界；③ `gdb` 的 `break`/`run`/`info registers`/`x`/`stepi`/`finish`/`bt` 把静态指令接到运行状态。如果只记住一件事，那就是：**先看 `pc` 落在哪条指令，再顺着操作数去查寄存器和内存。**

## 1.3.9 ARM64 对照：寄存器、调用与寻址 {#sec-1.3.9}

这一节回答：同一段 C 换到 ARM64 上，寄存器和寻址会变成什么形状？这些形状差异，为什么反过来会影响你读 x86 汇编的习惯？

::: preview 先抓住一件事
ARM64（AArch64）是 load/store 架构：算术指令只碰寄存器，内存只能靠 `ldr`/`str` 搬进搬出；指令定长 4 字节，没有 x86 那种「基址 + 变址 × 比例 + 位移」塞进一条操作数的写法。代价是要多几条地址计算，回报是指令边界固定，一条 `ldp`/`stp` 能搬两个寄存器。调用用 `bl` 把返回地址写进 `x30` 而不是压栈，所以非叶子函数必须自己保存 `x30`。
:::

先看一段同时暴露「寻址」和「调用」的 C：

```c
long g = 7;
long pick(long *a, long i) { return a[i] + a[i + 2]; }
struct P { long x, y; };
long field(struct P *p) { return p->x + p->y; }
long *addr(void) { return &g; }
```

x86-64 一侧（写作机 macOS，`clang --target=x86_64-linux-gnu -O2 -S`，省掉 `.cfi_*` 与对齐伪指令）：

```asm
pick:
    movq    16(%rdi,%rsi,8), %rax
    addq    (%rdi,%rsi,8), %rax
    retq
field:
    movq    8(%rdi), %rax
    addq    (%rdi), %rax
    retq
addr:
    leaq    g(%rip), %rax
    retq
```

aarch64 一侧（`ubuntu24`，Ubuntu 24.04.5，GCC 13.3，`gcc -O2 -S`）：

```asm
pick:
    add     x2, x0, x1, lsl 3
    ldr     x0, [x0, x1, lsl 3]
    ldr     x1, [x2, 16]
    add     x0, x1, x0
    ret
field:
    ldp     x1, x0, [x0]
    add     x0, x1, x0
    ret
addr:
    adrp    x0, .LANCHOR0
    add     x0, x0, :lo12:.LANCHOR0
    ret
```

同一份 C，x86 的 `pick` 两条指令，aarch64 四条。多出来的两条在算什么？`a[i]` 的地址。x86 的 `16(%rdi,%rsi,8)` 一条就完成「基址 + 变址 × 8 + 位移 16」，地址在加载单元里算，不落寄存器；aarch64 没有这种操作数，必须先 `add x2, x0, x1, lsl 3` 算出 `&a[i]`，才能用 `ldr x0, [x0, x1, lsl 3]` 取出 `a[i]`。

第二条 `ldr x1, [x2, 16]` 最容易被读错：偏移是 **16 字节**，不是 2。ARM64 的立即数偏移按字节计；只有寄存器变址才带 `lsl` 缩放。x86 则把比例 8 和位移 16 写在同一对括号里。`field` 的对比更直白：x86 两条 `movq`/`addq`，aarch64 用一条 `ldp x1, x0, [x0]` 同时取出 `p->x` 和 `p->y`，再用一条 `add` 相加——这是定长编码换来的「一条指令搬两个」。

`addr` 展示了取全局变量地址的两套办法：x86 用 RIP 相对寻址 `leaq g(%rip)`，一条指令、一条重定位；aarch64 用 `adrp` 取 4 KiB 页基址、`add ... :lo12:` 补页内偏移，两条指令。

编译出的函数有多大，符号表能直接回答（两边的 `.o` 都送到 `ubuntu24`，用 `readelf -sW` 读，实测）：

| 函数 | x86-64 字节 | aarch64 字节 |
|:--|--:|--:|
| `pick` | 10 | 20 |
| `field` | 8 | 12 |
| `addr` | 8 | 12 |

定长 4 字节没有让代码变短，反而更长：x86 把「算地址」压进了操作数。同一组函数也在 `ubuntu24` 上真跑过，`printf` 输出 `pick=60 field=300 *addr=7`，与手算一致。

寄存器与约定的对应关系：

| 概念 | x86-64 | AArch64 |
|:--|:--|:--|
| 通用寄存器 | 16 个（`%rax`–`%r15`） | 31 个（`x0`–`x30`），另有 `sp` 与零寄存器 `xzr` |
| 32 位视图 | `%eax` 等 | `w0`–`w30` |
| 整数参数 | `%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9`（6 个） | `x0`–`x7`（8 个） |
| 返回值 | `%rax` | `x0`（第二个返回值 `x1`） |
| 间接返回地址 | 隐藏指针占 `%rdi` | 隐藏指针用 `x8` |
| 栈指针 | `%rsp` | `sp`，任何时刻 16 字节对齐 |
| 帧指针 | `%rbp`（可选） | `x29`（可选） |
| 返回地址 | `call` 自动压栈 | `bl` 写入 `x30` |
| 调用/返回 | `call` / `ret` | `bl` / `ret` |
| 被调用者保存 | `%rbx`、`%rbp`、`%r12`–`%r15` | `x19`–`x28`、`x29`、`sp`；浮点 `v8`–`v15` 的低 64 位 |
| 条件执行 | `cmov` | `csel`、`csinc`、`csinv`、`csneg` |
| 访存 | 操作数可直接指内存 | 只能 `ldr`/`str`/`ldp`/`stp` |

表里最该盯住的是「返回地址」那一行：`x30` 不在「被调用者保存」一列。它是链接寄存器（link register），存的是**调用者**的返回地址；被调用函数只要还想返回，就不能随便改写它。

寻址模式逐项对照：

| 形式 | x86-64 | AArch64 |
|:--|:--|:--|
| 寄存器间接 | `(%rdi)` | `[x0]` |
| 基址 + 立即数 | `8(%rdi)` | `[x0, 8]`（立即数按字节） |
| 基址 + 变址 × 比例 | `(%rdi,%rsi,8)` | `[x0, x1, lsl 3]`（`lsl 0`–`lsl 4`） |
| 先算地址再用 | `leaq` | `add x2, x0, x1, lsl 3` |
| 全局符号 | `leaq g(%rip)` | `adrp` + `add ... :lo12:` |
| 大立即数 | `movabsq $imm64` | `movz` + 若干 `movk` |
| 自动增减指针 | 无 | pre-index `[x0, 8]!`、post-index `[x0], 8` |

pre-index 与 post-index 是 ARM64 独有的：`str x0, [x1, 8]!` 先把 `x1` 加 8 再存；`ldr x0, [x1], 8` 先取值再把 `x1` 加 8。编译器用它把「取元素 + 指针前进」合成一条，x86 要两条。

调用这一侧，`bl`（branch with link）把返回地址写进 `x30` 再跳；`ret` 默认跳回 `x30`。函数只要再调别人，`x30` 就会被覆盖，所以必须先在入口保存。下面这个函数调用外部 `g`，两边的序言正好对照（同一份 C，`volatile` 局部变量逼它真的落栈）：

```asm
# x86-64：call 已经把返回地址压栈，没有 x30 要存
caller:
    pushq   %rax
    movq    %rdi, (%rsp)
    movq    (%rsp), %rdi
    callq   g@PLT
    addq    (%rsp), %rax
    popq    %rcx
    retq
```

```asm
// aarch64：一条 stp 同时分配 32 字节栈并保存 x29、x30
caller:
    stp     x29, x30, [sp, -32]!
    mov     x29, sp
    str     x0, [sp, 24]
    ldr     x0, [sp, 24]
    bl      g
    ldr     x1, [sp, 24]
    ldp     x29, x30, [sp], 32
    add     x0, x0, x1
    ret
```

`stp x29, x30, [sp, -32]!` 一条指令完成三件事：`sp -= 32`、存 `x29`、存 `x30`；末尾 `ldp x29, x30, [sp], 32` 反着做一遍。方括号里的 `!` 是 pre-index（写回基址），方括号外的 `, 32` 是 post-index。x86 没有对应写法，所以要 `push`、`sub`、`pop` 分几条做。

::: def 定义 1.3.9 · AArch64 调用约定 {#def-1.3.9}
AAPCS64（ARM Architecture Procedure Call Standard）规定：前 8 个整数/指针参数放 `x0`–`x7`，浮点参数放 `v0`–`v7`，返回值用 `x0`（第二个 `x1`）或 `v0`；大于 16 字节的返回值由调用者提供缓冲区，地址放在 `x8`；`sp` 必须 16 字节对齐；被调用者要保证 `x19`–`x28`、`x29` 与 `v8`–`v15` 的低 64 位在返回时不变。`x30` 是返回地址，不属于被调用者保存寄存器。
:::

条件选择也换了形态。x86 的 `cmov` 要两个源都算好；ARM64 的 `csel x0, x1, x2, lt` 按标志位从两个寄存器里选一个，另有 `csinc`/`csinv`/`csneg` 做「选完再 +1/取反」。判零并有专门的 `cbz`/`cbnz`，测位有 `tbz`/`tbnz`，都把「比较 + 分支」压成一条。读 x86 时你会习惯「`cmp` 后一定跟 `jcc`」，读 ARM64 时要习惯「条件可能已经藏在 `csel`、`cbz` 里」。

::: ex 例 1.3.9 · 先猜 `ldr` 的偏移是几 {#ex-1.3.9}
`pick` 里 `a[i+2]` 编译成了 `ldr x1, [x2, 16]`，其中 `x2 = a + i*8`。先猜：如果改成 `a[i+3]`，这条指令的偏移会变成多少？为什么编译器不写成 `[x2, x1, lsl 3]` 再加一次？

::: sol 解答
偏移变成 24：`3 × 8`。立即数偏移按字节计，`+2` 个 `long` 就是 16 字节。编译器不重复用变址，是因为 `x2` 已经是 `&a[i]`，再叠一个变址等于把 `i` 算两遍；一个立即数就够。这也是读 ARM64 反汇编最容易错的地方：看到 `[x0, 32]` 要先想元素宽度，32 可能是 4 个 `long`，也可能是 8 个 `int`。
:::
:::

::: errata 关于 ARM64 的五个误解
1. **「`x30` 是被调用者保存寄存器」**——它是链接寄存器，存调用者的返回地址。被调用函数只要再调别人就必须自己保存，但它不在「返回时保证不变」的名单里。
2. **「`w0` 和 `x0` 是两个寄存器」**——同一个寄存器的 32 位视图。写 `w0` 会把 `x0` 高 32 位清零，读 `w0` 只看低 32 位。
3. **「ARM64 有和 `lea` 对应的指令」**——没有。算地址用 `add`（可带 `lsl`）或 `adrp` 加页内偏移；取全局符号地址是两条指令。
4. **「`ldr` 的偏移写元素个数」**——立即数偏移按字节；只有寄存器变址才带 `lsl` 缩放。`[x2, 16]` 是 16 字节，不是 16 个元素。
5. **「定长指令所以代码更短」**——相反。同一段 `pick`、`field`、`addr`，aarch64 是 20/12/12 字节，x86 是 10/8/8 字节。定长换来的是取指和译码简单，不是密度。
:::

### 1.3.9 小结

① ARM64 是 load/store 架构，地址必须先在寄存器里算好，x86 把「基址 + 变址 × 比例 + 位移」压进一条操作数；② 立即数偏移按字节，寄存器变址才按 `lsl` 缩放；③ `bl` 把返回地址放进 `x30`，非叶子函数用 `stp`/`ldp` 保存 `x29`、`x30`，x86 的 `call` 已经替你压栈。如果只记住一件事，那就是：**读 ARM64 先找地址是怎么算出来的，读 x86 先找地址算在哪个操作数里。**

::: method 即时自测 · 1.3.9
**Q1（记忆）** 前 8 个整数参数在哪些寄存器？返回值在哪？大于 16 字节的结构体返回，地址放在哪个寄存器？

**Q2（辨析）** `pick` 在两种 ISA 下分别是几条指令？多出来的指令在做什么，为什么 x86 不需要？

**Q3（应用）** 看到 `str x0, [x1, 16]!`，说出执行后 `x1` 的值和内存被写的位置。

**Q4（迁移）** 你要在 ARM64 上手写一个只做加法的叶子函数，需要序言吗？如果它内部要 `bl` 一个函数呢？

::: sol 第 1 题答案
**A1** 整数参数 `x0`–`x7`，返回值 `x0`（第二个 `x1`），大结构体返回的隐藏指针在 `x8`。
:::

::: sol 第 2 题答案
**A2** x86 两条，aarch64 四条。多出来的是 `add x2, x0, x1, lsl 3` 和「用 `x2` 加立即数再取一次」。x86 的 `16(%rdi,%rsi,8)` 在加载单元里算地址，不占指令也不占寄存器。
:::

::: sol 第 3 题答案
**A3** pre-index：先把 `x1` 加 16，再把 `x0` 存到新地址。执行后 `x1` 指向原地址 +16，数据写在 `x1` 的新值处。
:::

::: sol 第 4 题答案
**A4** 纯叶子函数不需要序言，`add x0, x0, x1` 后直接 `ret` 即可。一旦内部有 `bl`，`x30` 会被覆盖，必须先 `stp x29, x30, [sp, -16]!` 保存、返回前 `ldp` 恢复。
:::
:::

## 1.3.10 机器码：从汇编到字节 {#sec-1.3.10}

这一节回答：`objdump` 左边那一串十六进制是什么？为什么 `movq %rax,(%rdi)` 是 3 个字节，而 `movq $1,%rax` 要 7 个？读懂编码后，崩溃地址附近的字节、JIT 生成的代码、以及「为什么这条指令比那条短」都不再是黑箱。

::: preview 先抓住一件事
x86-64 的指令是变长的，一条指令由「可选前缀 + opcode + 寻址字节（ModRM/SIB）+ 位移 + 立即数」拼接而成，长度 1–15 字节。ARM64 相反：每条指令固定 4 字节，寄存器编号写在固定的位段里。变长的代价是译码器必须先找指令边界，好处是能把「基址 + 变址 × 比例 + 位移」压进一条；定长的代价是地址要单独算，好处是取指和译码简单。
:::

先把「字节从哪来」这件事做实，免得对着助记符猜。做法是：每条指令单独放进一个 32 字节对齐的符号里，交叉汇编成 `.o`，再用 `readelf -x .text` 读原始字节、`readelf -s` 读长度。写入 `enc.s`，在写作机上 `clang --target=x86_64-linux-gnu -c enc.s`，把 `.o` 送到 `ubuntu24` 上读：

```text
$ readelf -x .text enc.x86.o | sed -n '3,6p'
  0x00000000 48890766 2e0f1f84 00000000 00662e0f H..f.........f..
  0x00000010 1f840000 00000066 0f1f8400 00000000 .......f........
  0x00000020 488b0766 2e0f1f84 00000000 00662e0f H..f.........f..
  0x00000030 1f840000 00000066 0f1f8400 00000000 .......f........
$ readelf -sW enc.x86.o | grep ' i_'
     1: 0000000000000000     3 NOTYPE  GLOBAL DEFAULT    2 i_store
     2: 0000000000000020     3 NOTYPE  GLOBAL DEFAULT    2 i_load
     3: 0000000000000040     4 NOTYPE  GLOBAL DEFAULT    2 i_add8
```

`0x00` 处三个字节 `48 89 07` 就是 `movq %rax,(%rdi)`，全长为 3；`0x20` 处 `48 8b 07` 是 `movq (%rdi),%rax`，也是 3。两个符号之间那一串 `66 2e 0f 1f 84 ...` 是汇编器插入的多字节 `nop` 填充，对齐用，不是指令的延续。

x86-64 的通用布局如下（CSAPP 图 3-2 的简化）：

<pre class="layout">
┌──────────┬──────────┬────────┬────────┬────────┬──────────┬─────────┐
│ 前缀(可选) │ REX(可选) │ opcode │ ModRM  │ SIB    │ disp     │ imm     │
│ 0-4 字节  │ 1 字节    │ 1-3 字节│ 1 字节  │ 1 字节  │ 1/2/4/8  │ 1/2/4/8 │
└──────────┴──────────┴────────┴────────┴────────┴──────────┴─────────┘
</pre>

REX 前缀的位布局是 `0100WRXB`：

| 位 | 名称 | 作用 |
|:--|:--|:--|
| W | 宽度 | 1 表示 64 位操作数（`movq` 而非 `movl`） |
| R | 扩展 reg | 把 ModRM 的 reg 字段从 3 位扩到 4 位（访问 `%r8`–`%r15`） |
| X | 扩展 index | 把 SIB 的 index 字段扩到 4 位 |
| B | 扩展 base/rm | 把 ModRM 的 rm 或 opcode 内嵌寄存器扩到 4 位 |

ModRM 一个字节拆成三段：`mod`（2 位，寻址方式）、`reg`（3 位，寄存器或 opcode 扩展）、`rm`（3 位，寄存器或内存基址）。`mod=11` 表示两边都是寄存器；`mod=00/01/10` 表示 rm 是内存，位移分别是 0、1 字节、4 字节。`rm=100` 时后面再跟一个 SIB 字节；`rm=101` 且 `mod=00` 表示 RIP 相对寻址。

SIB 拆成 `scale`（2 位：1/2/4/8）、`index`（3 位）、`base`（3 位）。`index=100` 表示没有变址（因为 `%rsp` 不能当变址寄存器）。

### 十条指令的字节，逐条对过

| 汇编（AT&T） | 字节 | 长度 | 拆解 |
|:--|:--|--:|:--|
| `movq %rax, (%rdi)` | `48 89 07` | 3 | REX.W；`89` 是 mov r64→r/m64；ModRM `00 000 111` = `[rdi]` |
| `movq (%rdi), %rax` | `48 8b 07` | 3 | `8b` 方向相反：r/m64→r64，ModRM 完全相同 |
| `addq $8, %rdi` | `48 83 c7 08` | 4 | `83 /0 ib`；ModRM `11 000 111`；imm8=8 |
| `leaq 8(%rdi,%rsi,4), %rax` | `48 8d 44 b7 08` | 5 | ModRM `01 000 100`（disp8+SIB）；SIB `10 110 111`（×4, rsi, rdi） |
| `movl $1, %eax` | `b8 01 00 00 00` | 5 | `b8+rd` 的 imm32；写 32 位寄存器自动清零高 32 位 |
| `jmp *%rax` | `ff e0` | 2 | `ff /4`；ModRM `11 100 000` |
| `xorl %eax, %eax` | `31 c0` | 2 | `31` 是 xor r32→r/m32；ModRM `11 000 000` |
| `movq $1, %rax` | `48 c7 c0 01 00 00 00` | 7 | `c7 /0` 的 imm32，符号扩展到 64 位 |
| `movabsq $0x1122334455667788, %rax` | `48 b8 88 77 66 55 44 33 22 11` | 10 | `b8+rd` 的 imm64，小端存放 |
| `callq f` / `retq` | `e8 00 00 00 00` / `c3` | 5 / 1 | `call rel32` 的位移由链接器填，`.o` 里是 0 加重定位 |

字节序在这里有两层：**指令各字段按编码顺序排列**，而**立即数与位移按小端存放**。`movl $1,%eax` 的 `01 00 00 00` 就是小端的 1。反汇编器先按 opcode 表确定长度，再按 ModRM/SIB 决定后续字节，任何一步错位都会把后面几条指令解成乱码——这是分析被截断的代码时常见的现象。


### ARM64：一条指令就是一个 32 位字

同样的做法搬到 ARM64，把三条只差寄存器顺序的 `add` 各自汇编：

```asm
add x0, x1, x2
add x2, x1, x0
add x0, x2, x1
```

`ubuntu24` 上 `gcc -c` 之后 `readelf -x .text`（文件里是小端，读成 32 位字要反过来）：

| 指令 | 文件里的字节 | 32 位字 |
|:--|:--|:--|
| `add x0, x1, x2` | `20 00 02 8b` | `0x8b020020` |
| `add x2, x1, x0` | `22 00 00 8b` | `0x8b000022` |
| `add x0, x2, x1` | `40 00 01 8b` | `0x8b010040` |

三个字只差几个位段，拆开就看得见：`Rd` 在 bit[4:0]，`Rn` 在 bit[9:5]，`Rm` 在 bit[20:16]。拿 `0x8b010040` 验证：低 5 位 `0x00` 是 `Rd=x0`；右移 5 位取 5 位得 `0x02`，是 `Rn=x2`；右移 16 位取 5 位得 `0x01`，是 `Rm=x1`——与源码 `add x0, x2, x1` 一致。这就是定长编码的好处：不用猜长度，字段位置固定，读机器码可以像查表。

其余几条也用同一方法量过：`ldr x3, [x0, x1, lsl 3]` 是 `03 78 61 f8`（字 `0xf8617803`）；`mov x0, #1` 是 `20 00 80 d2`（字 `0xd2800020`，4 字节，比 x86 的 `movl $1,%eax` 的 5 字节还短）；`bl f` 是 `00 00 00 94`（字 `0x94000000`，低 26 位是相对偏移，`.o` 里为 0 加重定位）；`ret` 是 `c0 03 5f d6`（字 `0xd65f03c0`，它就是 `br x30` 的别名）。

定长还带来一个读代码时的判据：aarch64 的函数地址必然是 4 的倍数，`.text` 大小必然是 4 的倍数；x86 的函数起点只保证对齐到 16，指令可以落在任意字节。上一节量过的 `pick` 是 20 字节（5 条），x86 是 10 字节（2 条）——定长没有让代码更短。

### 为什么短指令重要

`xorl %eax, %eax`（`31 c0`，2 字节）比 `movl $0, %eax`（`b8 00 00 00 00`，5 字节）短，而且不产生对 `%eax` 旧值的依赖（寄存器重命名会切断依赖链）。编译器因此普遍用 `xor` 清零。其余几条都是量过的：

- `movq $1, %rax` 是 `48 c7 c0 01 00 00 00`（7 字节，imm32 符号扩展）；若常量超出 32 位有符号范围，必须用 `48 b8` + 8 字节立即数（10 字节）。
- `leaq 1(%rdi), %rax` 是 `48 8d 47 01`（4 字节）；写成 `movq %rdi,%rax; addq $1,%rax` 是 7 字节，还多一次写寄存器。
- 条件传送 `cmovl %rsi,%rdi` 是 4 字节；`je` 的短跳转（rel8）是 `74 xx` 2 字节，长跳转（rel32）是 `0f 84 xx xx xx xx` 6 字节。跳得远就要 6 字节，这是链接器排布基本块时会考虑的成本。

指令长度直接影响取指带宽与 I-cache 命中率。热循环里把一条 7 字节指令换成 3 字节，可能让循环整体跨过 32 字节取指边界；收益要用 `perf stat` 的 `i-cache` 相关计数验证，不能凭直觉。

### 常见 opcode 速查

| opcode | 指令族 | 方向/说明 |
|:--|:--|:--|
| `88` / `89` | `mov r8/r64 → r/m` | 89 是 32/64 位，88 是 8 位 |
| `8a` / `8b` | `mov r/m → r8/r64` | 与 88/89 方向相反 |
| `01` / `03` | `add r → r/m` / `add r/m → r` | 其余算术同理：29/2b sub、21/23 and、31/33 xor |
| `39` / `3b` | `cmp r/m, r` / `cmp r, r/m` | 只设标志位 |
| `85` | `test r/m, r` | 常配合 `%rax,%rax` 判零 |
| `8d` | `lea` | 只算地址 |
| `83` | 组 1 的 imm8 形式 | `/0 add /1 or /4 and /5 sub /7 cmp` |
| `c7` | `mov imm32 → r/m` | `/0`，立即数符号扩展到 64 位 |
| `e8` | `call rel32` | 相对调用，链接器填偏移 |
| `c3` | `ret` | 从栈顶取返回地址 |
| `0f 05` | `syscall` | 系统调用，参数在 rdi/rsi/rdx/r10/r8/r9 |
| `0f 1f` | `nop` 多字节形式 | 对齐填充 |


`syscall` 的参数约定值得单独记：它用 `%r10` 而不是 `%rcx` 传第 4 个参数，因为 `syscall` 指令本身会把返回地址放进 `%rcx`、把标志位放进 `%r11`。用户态函数调用（SysV ABI）与系统调用（kernel ABI）是两套寄存器约定，混用会得到莫名其妙的 `ENOSYS` 或错误参数。

ARM64 的系统调用是另一套形状：编号放 `x8`（不是 `x0`），参数从 `x0` 起排到 `x5`，陷入指令是 `svc #0`，机器码 `0xd4000001`。下面这段不链接 libc 的程序，在 `ubuntu24` 上真跑过，输出 `hello` 后以 0 退出：

```asm
_start:
    mov     x0, #1              // fd = 1
    adrp    x1, msg
    add     x1, x1, :lo12:msg
    mov     x2, #6              // 长度
    mov     x8, #64             // __NR_write
    svc     #0
    mov     x0, #0
    mov     x8, #93             // __NR_exit
    svc     #0
```

`gcc -nostdlib -static` 之后用 `objdump -d` 看，`mov x8, #0x40` 的机器码是 `d2800808`，两条 `svc` 都是 `d4000001`——全是 4 字节，字段位置固定，和前面手拆的 `add` 同一个规律。

::: note 变长编码的代价
x86 的译码器必须先判断指令边界，再译码；一条 15 字节的指令可能横跨两个 16 字节取指块。现代 Intel/AMD 用「译码缓存 + uop 缓存」绕开重复译码，但一次性冷代码仍受译码带宽限制。这也是为什么 RISC 架构（ARM64 定长 4 字节）在同样工艺下前端更简单——代价是代码密度通常更低，上一节量的 `pick` 就是 20 字节对 10 字节。
:::

::: ex 例 1.3.10 · 先猜这两个操作数各几字节 {#ex-1.3.10}
`addq $8, %rdi` 编码成 `48 83 c7 08`（4 字节），`addq $1000, %rdi` 却更长。先猜：第二个操作数会变成几字节？如果把 `$8` 换成 `$1`，长度会变吗？

::: sol 解答
`$1000` 超出 imm8 的表示范围（-128–127），必须改用 `81 /0 id` 形式，立即数占 4 字节：`48 81 c7 e8 03 00 00`，全长 7 字节。换成 `$1` 仍是 imm8 形式（`48 83 c7 01`），4 字节不变——编码器不因为值小就省掉那个字节。这就是「指令长度取决于操作数的编码方式，不取决于数值本身」。
:::
:::

::: errata 关于机器码的五个误解
1. **「一条汇编对应固定字节数」**——`addq $8` 是 4 字节、`addq $1000` 是 7 字节，同一条助记符长度可以变。要看操作数的编码形式。
2. **「`movl $1,%eax` 只改 `%eax`」**——写 32 位寄存器会把高 32 位清零。这不是编码问题，而是 x86-64 的寄存器语义，很多手写汇编的人第一次遇到「高 32 位莫名变 0」就栽在这里。
3. **「立即数在文件里按大端存」**——`movabsq $0x1122334455667788` 存成 `88 77 66 55 44 33 22 11`，是小端。指令各字段的排列顺序与立即数的字节序是两回事。
4. **「`e8 00 00 00 00` 表示调用地址 0」**——`.o` 里的 `rel32` 还没填，旁边有一条 `R_X86_64_PLT32` 重定位；链接时才变成相对偏移。
5. **「ARM64 也是 4 字节，所以字段位置随便」**——字段位置是硬编码的：`Rd` 在 bit[4:0]、`Rn` 在 bit[9:5]、`Rm` 在 bit[20:16]。手算机器码时要按位段填，不是按顺序排。
:::

### 1.3.10 小结

① x86-64 指令由前缀、opcode、ModRM、SIB、位移、立即数拼成，长度 1–15 字节，变化来自操作数的编码形式；② 字节可以从 `.o` 的 `.text` 直接读出来，不必依赖反汇编器，`readelf -x` 与 `readelf -s` 配合就能逐条核对；③ ARM64 每条 4 字节，寄存器编号占固定位段，读机器码可以按位拆。如果只记住一件事，那就是：**指令长度是编码形式决定的，不是助记符决定的。**

## 1.3.11 参数与返回值的完整规则 {#sec-1.3.11}

这一节回答：超过 6 个参数、浮点、结构体、大返回值，各自走哪条路？为什么同一份 C 在两个架构上，同一个结构体会落在完全不同的位置？

::: preview 先抓住一件事
SysV AMD64 把参数分成两套独立计数：整数和指针走 `%rdi`…`%r9`，浮点走 `%xmm0`…`%xmm7`，谁先满谁走栈。结构体先按大小和字段分类：≤16 字节拆进寄存器，>16 字节整块放到栈上。返回值同理，大于 16 字节由调用者提供缓冲区，地址作为隐藏参数悄悄加在最前面。ARM64 的三处不同最值得记：前 8 个整数参数进 `x0`–`x7`，大结构体按引用传指针，大返回值的隐藏指针放 `x8`。
:::

1.3.1 的「六个整数参数在 `%rdi`…`%r9`」是简化版。真实规则要额外处理三件事：浮点参数、结构体参数、大结构体返回。先看参数怎么分座位：

### 整数、浮点与栈

| 参数类别 | 前几个放寄存器 | 超出后 |
|:--|:--|:--|
| 整数/指针 | `%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9` | 从右向左压栈，`8(%rsp)` 是第 7 个 |
| `float`/`double` | `%xmm0`–`%xmm7` | 压栈，每个占 8 字节 |
| `long double` | 栈上（16 字节对齐） | 压栈；返回值才用 `st0` |
| 混合参数 | 整数与浮点**各自计数**，互不占位 | 各自超出部分压栈 |

「各自计数」是第一个反直觉点：`f(int a, double x, int b, double y, ..., int g)` 的第 7 个整数参数仍然走栈，即使前面只用了两个整数寄存器。

```c
long many(long a, long b, long c, long d, long e, long f, long g, long h)
{
    return a + b + c + d + e + f + g + h;
}
```

x86-64 的编译结果（`clang --target=x86_64-linux-gnu -O2 -S`）：

```asm
many:
    addq    %rdi, %rsi          # b += a
    leaq    (%rdx,%rcx), %rax   # c + d
    addq    %rsi, %rax
    addq    %r8, %rax
    addq    %r9, %rax
    addq    8(%rsp), %rax       # g：第 7 个参数
    addq    16(%rsp), %rax      # h：第 8 个参数
    retq
```

注意是 `8(%rsp)` 而不是 `0(%rsp)`：`call` 已经把 8 字节返回地址压在栈顶，第一个栈参数在返回地址之上。这也解释了为什么 `-O0` 的函数入口先 `push %rbp`，之后同样的参数变成 `16(%rbp)`。

同一份 C 在 `ubuntu24` 上（GCC 13.3，`gcc -O2 -S`）：

```asm
many:
    add     x0, x0, x1
    add     x0, x0, x2
    add     x0, x0, x3
    add     x0, x0, x4
    add     x0, x0, x5
    add     x0, x0, x6
    add     x0, x0, x7
    ret
```

一条栈访问指令都没有：ARM64 有 8 个整数参数寄存器，`g` 和 `h` 还在 `x6`、`x7` 里。参数表不是「每台机器都 6 个」的经验值，而是各 ABI 写死的数字。

### 结构体按值传递

结构体不是「一律压栈」，而是按大小与字段类型分类（ABI 里叫 classification）：

1. 大小超过 16 字节 → `MEMORY` 类，在栈上传一份副本。
2. 大小 ≤ 16 字节 → 按 8 字节切成一个或两个「八字节」，每块分类为 `INTEGER`（整数、指针）或 `SSE`（float、double）。
3. 含非对齐字段、或字段跨越八字节边界导致无法归类 → `MEMORY`。
4. 混合分类（一块 INTEGER、一块 SSE）按各自类别分开传。

| 结构体 | 大小 | 分类 | 参数位置 | 返回位置 |
|:--|--:|:--|:--|:--|
| `struct P { long x, y; }` | 16 | INTEGER, INTEGER | `%rdi`、`%rsi` | `%rax`、`%rdx` |
| `struct Q { double a, b; }` | 16 | SSE, SSE | `%xmm0`、`%xmm1` | `%xmm0`、`%xmm1` |
| `struct R { long x; double y; }` | 16 | INTEGER, SSE | `%rdi`、`%xmm0` | `%rax`、`%xmm0` |
| `struct S { char c[24]; }` | 24 | MEMORY | 栈上副本，首字节在 `8(%rsp)` | 隐藏指针（`%rdi`） |
| `struct T { char c; }` | 1 | INTEGER | `%dil`（`%rdi` 低 8 位） | `%al` |

五个函数一起编译，结果直接印证（`ss` 返回 `s.c[8]`，注意偏移是 16 不是 8）：

```asm
sp:                          # long sp(struct P p)
    leaq    (%rdi,%rsi), %rax
    retq

sq:                          # double sq(struct Q q)
    mulsd   %xmm1, %xmm0
    retq

sr:                          # double sr(struct R r)
    cvtsi2sd %rdi, %xmm1
    addsd   %xmm1, %xmm0
    retq

ss:                          # long ss(struct S s)
    movsbq  16(%rsp), %rax   # 结构体从 8(%rsp) 起，c[8] 在 16(%rsp)
    retq

st:                          # long st(struct T t)
    movsbq  %dil, %rax       # 单字节结构体在 rdi 的最低字节
    retq
```

`ss` 的 16 最容易算错：栈参数从 `8(%rsp)` 起，`c[8]` 再加 8 字节，落在 `16(%rsp)`。

ARM64 在同样五个函数上给出另一套形状（`gcc -O2 -S`）：

```asm
sp:                          // add x0, x0, x1
    add     x0, x0, x1
    ret
sq:                          // 两个 double 是 HFA，进 d0、d1
    fmul    d0, d0, d1
    ret
sr:                          // 整数部分进 x0，浮点部分进 d0，两个寄存器堆
    scvtf   d0, x0
    fmov    d1, x1
    fadd    d0, d0, d1
    ret
ss:                          // 24 字节结构体：按引用，x0 是指针
    ldrb    w0, [x0, 8]
    ret
st:
    and     x0, x0, 255      // 高 56 位未定义，必须自己清
    ret
```

三处差异都是真的编译结果，不是笔误：`struct S` 在 x86 上被复制到栈，在 ARM64 上只传一个指针（`ldrb w0, [x0, 8]` 直接从调用者的副本里读）；`struct R` 在 x86 上挤进 `%rdi` 和 `%xmm0` 两个不同的寄存器堆，ARM64 也分成 `x0` 和 `d0`；`struct T` 的 1 个字节在 ARM64 上必须 `and x0, x0, 255` 清高位，因为 ABI 只保证低 8 位有效。

::: note 按引用传参的可见后果
ARM64 的「大结构体按引用」意味着被调用函数拿到的是可写内存。C 语义要求按值传参不能改动调用者的对象，所以编译器在需要时自己复制；但如果函数把参数地址转手存起来（比如赋给全局指针），你会在 ARM64 上观察到与 x86 不同的生命周期。写跨架构代码时，别依赖「大结构体一定被复制」。
:::

### 返回值与可变参数

| 返回类型 | x86-64 位置 | AArch64 位置 |
|:--|:--|:--|
| 整数/指针 ≤ 8 字节 | `%rax` | `x0` |
| 16 字节整数结构体 | `%rax:%rdx` | `x0:x1` |
| `float`/`double` | `%xmm0` | `v0` |
| 两个 SSE 八字节 | `%xmm0:%xmm1` | `v0:v1`（HFA 最多 4 个） |
| `long double` | `%st0`（x87 栈） | `v0`（128 位） |
| 大于 16 字节 | 调用者提供的隐藏指针，放在 `%rdi` | 调用者提供的隐藏指针，放在 `x8` |

`rp` 和 `mk` 展示了返回值的两条路。`struct P` 只有 16 字节，直接拆进两个寄存器：

```asm
rp:                          # struct P rp(long a, long b)
    movq    %rsi, %rdx       # 返回结构体的第二个字段
    movq    %rdi, %rax       # 第一个字段
    retq
```

`struct S` 有 24 字节，走隐藏指针：调用者分配空间，把地址作为第 0 个参数放进 `%rdi`，被调用者写完再把同一地址放进 `%rax`。

```asm
mk:                          # struct S mk(void)
    movq    %rdi, %rax       # 隐藏指针在 rdi，先记下来
    xorps   %xmm0, %xmm0
    movups  %xmm0, (%rdi)    # 写前 16 字节
    movq    $0, 16(%rdi)     # 写后 8 字节
    retq
```

这个隐藏指针会改变整条参数序列：`long f(struct S s, int x)` 的 `x` 实际在 `%rsi`，不是 `%rdi`。ARM64 把它换成了 `x8`，调用点一眼看得出来：

```asm
use:                         // long use(void) { return mk().c[8]; }
    stp     x29, x30, [sp, -48]!
    mov     x29, sp
    add     x8, sp, 24       // x8 = 临时缓冲区地址
    bl      mk
    ldrb    w0, [sp, 32]     // 返回值在缓冲区 +8 处
    ldp     x29, x30, [sp], 48
    ret
```

`add x8, sp, 24` 就是「分配 24 字节临时对象」的那一步。x86 的 `%rdi` 和 ARM64 的 `x8` 都是 ABI 硬编码，不是编译器随意挑的。

`long double` 的差别更大：x86 上它按 16 字节压在栈上（`fldt 8(%rsp)`），返回时放 x87 栈顶 `%st0`；ARM64 上它是 IEEE 128 位，进 `v0`，而且加减乘除要调用 `__addtf3` 这类软件例程——`twice` 的编译结果是先 `bl __addtf3` 再返回。

可变参数函数（`printf` 一类）在 x86 上多一条规则：调用者把**用到的向量寄存器个数**放进 `%al`。编译 `printf("%d %f\n", n, x)` 得到 `movb $1, %al`、再 `call printf@PLT`——一个 `double` 在 `%xmm0` 里，所以是 1。被调用者的 `va_start` 靠这个数决定要保存几个 XMM 寄存器；手写汇编忘了设 `%al`，浮点参数会读到垃圾值。ARM64 没有这个计数器：变参调用约定要求固定参数照常用 `x0`–`x7` 和 `v0`–`v7`，`va_start` 一律把这两组寄存器整体存进 `va_list`。


### 与 syscall、Windows 的差异

| 约定 | 整数参数 | 第 4 个 | 栈对齐 | 备注 |
|:--|:--|:--|:--|:--|
| SysV AMD64（Linux 用户态） | rdi, rsi, rdx, rcx, r8, r9 | `%rcx` | `call` 前 16 字节 | 本书默认口径 |
| Linux syscall（x86-64） | rdi, rsi, rdx, r10, r8, r9 | `%r10` | 内核负责 | `syscall` 破坏 rcx/r11 |
| Windows x64 | rcx, rdx, r8, r9 | `%r9` | 16 字节 + 32 字节影子空间 | 调用者预留 shadow space |
| AArch64（Linux） | x0–x7 | `x3` | 16 字节 | 前 8 个整数/指针 |

::: errata 关于参数传递的六个误解
1. **「结构体一律压栈」**——≤16 字节的结构体会被拆进寄存器；只有 `MEMORY` 类才压栈。
2. **「浮点参数也占整数寄存器」**——两套寄存器独立计数，`f(int, double, int)` 的第二个 `int` 仍在 `%esi`。
3. **「返回值总在 `%rax`」**——浮点在 `%xmm0`，大结构体走隐藏指针，`long double` 在 x87 栈。
4. **「第 7 个参数在 `0(%rsp)`」**——返回地址占了栈顶 8 字节，第一个栈参数在 `8(%rsp)`。
5. **「ARM64 也把大结构体复制到栈上」**——按引用传指针，`struct S` 的编译结果是 `ldrb w0, [x0, 8]`，一个字节都没复制。
6. **「大返回值的隐藏指针总在第一个参数寄存器」**——x86 用 `%rdi`，ARM64 用 `x8`。在 ARM64 上写 `struct S f(int x)`，`x` 仍在 `x0`，不会被隐藏指针挤走。
:::


### 浮点参数、返回值与指令 {#sec-1.3.11.1}

x86-64 的浮点用 SSE/AVX 寄存器，不走通用寄存器：

| 用途 | 寄存器 | 说明 |
|:--|:--|:--|
| 浮点参数 | `%xmm0`–`%xmm7` | 与整数参数分开计数；超出走栈 |
| 浮点返回值 | `%xmm0` | `float`/`double` 都是 |
| 变参 `%al` | `%al` | 调用变参函数时，`%al` 存「用了多少个向量寄存器」 |
| 标量指令 | `movss/movsd`、`addss/addsd`、`mulss/mulsd` | `ss`=单精度，`sd`=双精度 |
| 转换 | `cvtss2sd`、`cvtsd2ss`、`cvttss2si`、`cvtsi2sd` | 截断用 `cvtt`（向零） |
| 比较 | `ucomiss/ucomisd` | 设 ZF/PF/CF；NaN 时 PF=1，要用 `jp` 先判 |

```c
/* fp.c — 浮点参数/返回值；cc -O2 -S fp.c */
double scale(double x, float k) { return x * (double)k; }
```

```asm
# x86-64 SysV：x=xmm0, k=xmm1（float 只用低 32 位）
scale:
    cvtss2sd %xmm1, %xmm1      # float -> double
    mulsd    %xmm1, %xmm0      # x * k
    ret                        # 返回 xmm0
```

::: errata 浮点的四个坑
1. **`float` 参数在 `%xmm` 里也占 128 位寄存器，但只写低 32 位**；高位是垃圾，不要假设清零。
2. **比较要用 `ucomisd` + `jp`**：NaN 与任何值比较都「无序」，直接 `je/jne` 会误判。
3. **`cvtsd2si` 默认按当前舍入模式**；要截断用 `cvttsd2si`。C 的 `(int)d` 是向零截断。
4. **变参函数**（`printf`）必须把 `%al` 设为向量寄存器个数，否则 callee 保存 XMM 时会读错；编译器自动做，手写汇编要自己设。
:::

::: ex 例 1.3.11 · 先猜这个结构体落在哪几个寄存器 {#ex-1.3.11}
```c
struct M { char c[8]; double d; };
double mm(struct M m) { return m.c[0] + m.d; }
```
`struct M` 正好 16 字节。先猜：它在 x86-64 上会占用哪些寄存器？`c` 和 `d` 会不会挤在同一个寄存器里？

::: sol 解答
按 8 字节切两块：第一块全是 `char`，分类 `INTEGER`，进 `%rdi`；第二块是 `double`，分类 `SSE`，进 `%xmm0`。编译结果正是 `movsbl %dil, %eax`（取 `c[0]`，动的是 `%rdi` 的最低字节）加 `cvtsi2sd`、`addsd %xmm1, %xmm0`（`d` 在 `%xmm0`）。ARM64 上形状相同、寄存器不同：`and w0, w0, 255` 取 `c[0]`，`fmov d0, x1` 把第二块从整数寄存器搬进浮点寄存器。记住那句判断：**分类看的是每一块里有没有浮点，而不是整个结构体有没有浮点**。
:::
:::

### 1.3.11 小结

① 参数分两套计数：整数 6 个寄存器、浮点 8 个寄存器，互相不占位；② 结构体按「8 字节一块」分类，≤16 字节进寄存器，>16 字节在 x86 上复制到栈、在 ARM64 上按引用传指针；③ 大返回值的隐藏指针 x86 放 `%rdi`、ARM64 放 `x8`，变参调用 x86 还要设 `%al`。如果只记住一件事，那就是：**先量大小、再切八字节、再按块分类，结构体的去向就能推出来。**

## 1.3.12 栈帧细节：对齐、红区与帧指针 {#sec-1.3.12}

这一节回答：编译器为什么总在序言里凑一个「整除 16」的减法？那块没用 `sub` 就敢写的内存是什么？帧指针到底省掉了什么、又付出了什么？

::: preview 先抓住一件事
x86-64 的 ABI 要求 `call` 执行前 `%rsp` 是 16 的倍数，所以函数入口处 `%rsp % 16 == 8`（返回地址已入栈）。为了对齐，序言里的减量总是 16 的倍数。SysV 还给叶子函数留了 128 字节红区：不调 `sub` 也能用 `%rsp` 以下的空间。帧指针 `%rbp` 在 `-O1` 以上默认被省略；ARM64 反而几乎总保留 `x29`，因为 `x30` 本来就要存。
:::

`call` 压入 8 字节返回地址，所以函数入口处 `%rsp % 16 == 8`。对齐规则是给 SSE 准备的：`movaps`/`movapd` 要求 16 字节对齐，栈上的 `__m128` 变量、对齐的 `double` 数组都靠它。编译器因此在序言里凑：

```asm
caller:
    pushq   %rbp              # rsp: 8 -> 0 (mod 16)
    movq    %rsp, %rbp
    subq    $16, %rsp         # 16 是 16 的倍数，对齐保持
    ...
    addq    $16, %rsp
    popq    %rbp
    retq
```

aarch64 没有入口偏移这回事：`sp` 在任何时刻都必须 16 字节对齐；`stp`/`ldp` 的立即数按访问宽度缩放（64 位寄存器按 8，128 位向量按 16），写错倍数汇编器当场拒绝。把 `stp q0, q1, [sp, #8]` 交给 `gcc -c`，得到的是：

```text
Error: immediate value must be a multiple of 16 at operand 3 -- `stp q0,q1,[sp,#8]'
```

所以序言写成 `stp x29, x30, [sp, -32]!`，一条指令同时完成「减 32」和「存两个寄存器」，对齐天然保持。

对齐违规在 ARM64 上能真看到。下面两个函数做同一件事——把两个 128 位向量寄存器存到 `sp`——只差栈指针是否对齐：

```asm
misalign:
    sub     sp, sp, #8      // sp 变成 8 mod 16
    stp     q0, q1, [sp]    // 要求 16 字节对齐
    add     sp, sp, #8
    ret
aligned:
    sub     sp, sp, #32
    stp     q0, q1, [sp]
    ldp     q0, q1, [sp]
    add     sp, sp, #32
    ret
```

`ubuntu24` 上真跑，`aligned` 先返回并打印 `aligned ok`，随后 `misalign` 触发总线错误：

```text
$ ./almain
aligned ok
Bus error (core dumped)
$ echo $?
135
```

135 = 128 + 7，信号 7 是 `SIGBUS`。归零的是「栈指针必须对齐」这条硬规则：这台机器的内核为用户态开启了栈对齐检查，`sp` 不对齐时做 16 字节存取会同步异常，而不是悄悄慢一点。

x86-64 上同样的错误表现为 `SIGSEGV`（`movaps` 遇到非对齐地址）。这一条本书**没有实测**：写作机和虚拟机都是 aarch64，没有可运行 x86 代码的 CPU 或模拟器，只能按 ABI 规则与指令语义说明。你在 x86 机器上可以用最小程序验证：`subq $8, %rsp` 之后调一个用 `movaps` 的函数。

红区（red zone）是 SysV 的另一条特性：**叶子函数**可以直接使用 `%rsp` 以下 128 字节，不必调整栈指针，信号处理程序也不会踩到这块（内核递送信号时会跳过它）。`-O2` 的叶子函数因此常出现负偏移而不见 `sub`：

```asm
leaf:                        # long leaf(long x)，内含 volatile long buf[2]
    movq    %rdi, -24(%rsp)  # 没有 sub，直接写 rsp 以下
    addq    %rdi, %rdi
    movq    %rdi, -8(%rsp)
    movq    -24(%rsp), %rax
    addq    -8(%rsp), %rax
    retq
```

同一份 C 在 ARM64 上没有这种写法。AAPCS64 不设红区，`sp` 以下的内存不归当前函数所有，叶子函数也要自己 `sub`：

```asm
leaf:
    sub     sp, sp, #16
    str     x0, [sp]
    lsl     x0, x0, 1
    str     x0, [sp, 8]
    ldr     x1, [sp]
    ldr     x0, [sp, 8]
    add     sp, sp, #16
    add     x0, x1, x0
    ret
```

红区只对叶子函数安全：一旦 `call` 别的函数，返回地址和 callee 的栈帧就会压进这块区域，`-24(%rsp)` 里存的值当场被覆盖。


帧指针 `%rbp` 在 x86-64 上从 `-O1` 起默认被省略（`-fomit-frame-pointer`），省下来的寄存器可以派别的用场，代价是调试器无法沿 `%rbp` 链回溯。同一个函数编两次就能看出差别：

```asm
# 默认 -O2：没有 rbp 链
caller:
    pushq   %rax
    movq    %rdi, (%rsp)
    movq    (%rsp), %rdi
    callq   g@PLT
    addq    (%rsp), %rax
    popq    %rcx
    retq

# 加 -fno-omit-frame-pointer：多出建链与拆链
caller:
    pushq   %rbp
    movq    %rsp, %rbp
    subq    $16, %rsp
    movq    %rdi, -8(%rbp)
    movq    -8(%rbp), %rdi
    callq   g@PLT
    addq    -8(%rbp), %rax
    addq    $16, %rsp
    popq    %rbp
    retq
```

ARM64 这一侧反过来了：`ubuntu24` 上 GCC 13.3 在 `-O2` 和 `-O2 -fno-omit-frame-pointer` 下给出**完全相同**的序言：

```asm
caller:
    stp     x29, x30, [sp, -32]!
    mov     x29, sp
    str     x0, [sp, 24]
    ldr     x0, [sp, 24]
    bl      g
    ldr     x1, [sp, 24]
    ldp     x29, x30, [sp], 32
    add     x0, x0, x1
    ret
```

原因在于返回地址的存放位置：x86 的 `call` 已经把它压栈，`%rbp` 是纯开销；ARM64 的 `bl` 把它放进 `x30`，非叶子函数反正要存 `x30`，`stp x29, x30` 顺手把 `x29` 也存了，几乎不额外花钱。所以「帧指针一定拖慢程序」在 ARM64 上不成立，在 x86 上也只是多一两条指令，真正的影响是少一个通用寄存器和少一层间接寻址。

::: ex 例 1.3.12 · 先猜这个减法改成 24 会怎样 {#ex-1.3.12}
函数 `f` 有三个 `long` 局部变量（共 24 字节），还要调用 `g`。序言是 `pushq %rbp`（`%rsp` 从 8 变成 0 mod 16）加 `subq $32, %rsp`，局部变量放在 `-8`、`-16`、`-24`，最后一个 8 字节空着。先猜：如果把 `subq $32` 改成 `subq $24`，`g` 里的 `movaps` 会不会崩？为什么？

::: sol 解答
会崩。函数入口 `%rsp % 16 == 8`，`pushq` 之后是 0，`subq $24` 之后变成 8；`call g` 再压 8 字节，`g` 的入口就是 0 mod 16，而 ABI 规定被调用者入口应为 8 mod 16。`g` 里任何假设「`%rsp + 8` 是 16 的倍数」的对齐访问都会落到错误地址上。多出来的 8 字节不是浪费，是让减量保持 16 的倍数；编译器从不把栈帧压到「刚刚好」。
:::
:::

::: errata 关于栈帧的五个误解
1. **「栈帧大小等于局部变量之和」**——还要加保存的寄存器、对齐填充、canary，并且总和向上取到 16 的倍数。
2. **「红区是所有函数都能用的」**——只有叶子函数安全。一旦 `call`，返回地址就压在红区顶上。
3. **「ARM64 也有红区」**——没有。AAPCS64 要求 `sp` 始终指向有效内存，叶子函数也要先 `sub`。
4. **「`-fno-omit-frame-pointer` 一定让程序变慢」**——在 ARM64 上它常是零成本，因为 `x30` 本来要存；在 x86 上多两条指令、少一个寄存器。
5. **「栈溢出只会读到垃圾」**——越界写会改掉 saved `rbp` 与返回地址，`ret` 时跳到攻击者选的地址；这不是「读到脏数据」级别的问题。
:::



### 栈帧与缓冲区溢出：从越界写到 ROP {#sec-1.3.12.1}

一个典型的栈帧（x86-64，向下增长）：

<pre class="layout">
  高地址
  ┌──────────────┐
  │ 调用者的栈    │
  ├──────────────┤
  │ 返回地址      │  ← 溢出首先改写这里
  ├──────────────┤
  │ 保存的 rbp    │
  ├──────────────┤
  │ 局部缓冲区    │  ← char buf[64]
  └──────────────┘  ← rsp
  低地址
</pre>

```c
/* vuln.c — 典型栈溢出；不要在生产代码里写 */
#include <stdio.h>
#include <string.h>
void vulnerable(const char *s)
{
    char buf[64];
    strcpy(buf, s);        /* 没有长度检查 */
    puts(buf);
}
int main(int argc, char **argv)
{
    if (argc > 1) vulnerable(argv[1]);
    return 0;
}
```

`buf` 占 64 字节，紧接着是保存的帧指针（8 字节），再往上是返回地址（8 字节）：**写 72 字节就改到帧指针，写 80 字节就改到返回地址**（这是关掉栈保护时的布局；开了保护，canary 会插在 `buf` 和帧记录之间）。在 `ubuntu24` 上把这 80 个字节真喂进去，两种编译选项给出两种死法：

```text
$ gcc -O0 vuln.c -o vuln_sp
$ ./vuln_sp $(python3 -c 'print("A"*80)')
*** stack smashing detected ***: terminated
$ echo $?
134
```

134 = 128 + 6，`SIGABRT`，来自 `__stack_chk_fail`——Ubuntu 的 GCC 默认开 `-fstack-protector-strong`，返回前比对 canary，发现被改就直接终止。关掉保护再看：

```text
$ gcc -O0 -fno-stack-protector vuln.c -o vuln_nosp
$ ./vuln_nosp $(python3 -c 'print("A"*80)')
Bus error (core dumped)
$ echo $?
135
```

135 = 128 + 7，`SIGBUS`。原因是 `ret` 跳到 `0x4141414141414141`，这个地址低两位是 `01`，不是 4 的倍数，ARM64 的 PC 对齐检查直接报总线错误；在 x86-64 上同样的事通常表现为 `SIGSEGV`。同一个 bug，退出信号都不同。

攻击者要的不是崩溃，是控制：把返回地址改成 `system("/bin/sh")`、`execve` 的入口，或一串 ROP（return-oriented programming）链（x86 上经典的 `pop rdi; ret` → `/bin/sh` → `system`）。

::: note 实验时怎么避免误伤
上面的程序只给自己喂参数，崩的也只是它自己。做这类实验时不要用 `sudo` 跑，也不要把 `-fno-stack-protector` 的二进制留在共享目录；虚拟机是共享资源，崩溃转储会占空间。
:::


现代防御是分层的：

| 防御 | 编译/运行开关 | 作用 |
|:--|:--|:--|
| 栈 canary | `-fstack-protector-strong` | 返回前检查哨兵，溢出即 `__stack_chk_fail` |
| NX | `-z noexecstack`（默认） | 栈不可执行，挡住 shellcode |
| ASLR | `/proc/sys/kernel/randomize_va_space=2` | 栈/库/堆地址随机化 |
| PIE | `-fPIE -pie` | 主程序基址也随机化 |
| RELRO | `-Wl,-z,relro,-z,now` | GOT 只读，挡住 GOT 覆盖 |
| FORTIFY | `-D_FORTIFY_SOURCE=3 -O2` | 编译期/运行期检查 `strcpy` 等 |
| CET/ shadow stack | `-fcf-protection=full` + CPU 支持 | 硬件校验返回地址 |

安全写法：

```c
char buf[64];
if (snprintf(buf, sizeof buf, "%s", s) >= (int)sizeof buf) {
    /* 截断；按业务决定报错还是继续 */
}
```

`gets` 已在 C11 移除；`strcpy/sprintf/strcat` 在未知长度输入上都不安全。审计时先搜这三个函数，再搜 `%n` 与 `printf(user_input)`。


### 递归：栈帧的重复与深度上限 {#sec-1.3.12.2}

递归函数每调用一次就建一个新栈帧；栈大小固定，深度等于「栈上限 ÷ 每帧字节数」。下面这个函数有一块 64 字节的 `volatile` 数组，编译器没法把它优化掉：

```c
long depth(long n)
{
    volatile long pad[8];          /* 64 字节 */
    pad[0] = n;
    if (n == 0) return pad[0];
    return depth(n - 1) + 1;
}
```

`gcc -O1 -fno-stack-protector -S` 给出的序言是 `stp x29, x30, [sp, -80]!`——每层 80 字节。`ubuntu24` 的栈上限是 8 MiB（8192 KiB），除一下约 104857 层。真跑一遍，用两个深度夹住这个数：

```text
$ ulimit -s
8192
$ ./deep 100000
n=100000
$ echo $?
0
$ ./deep 110000
Segmentation fault (core dumped)
$ echo $?
139
```

100000 层通过，110000 层 `SIGSEGV`（139 = 128 + 11），与 8388608 ÷ 80 ≈ 104857 的计算吻合。这不是「大概几十万」的经验值，是可以算出来的边界：**换掉帧大小，边界跟着换**。

尾递归在 C 里**不保证**被优化成循环，GCC `-O2` 有时会做、有时不做，`-O0` 一定不做。真需要深递归时，要么显式改写成迭代，要么调大栈（`setrlimit(RLIMIT_STACK)`，或创建线程时用 `pthread_attr_setstacksize` 指定线程栈）。

### 1.3.12 小结

① 入口处 `%rsp % 16 == 8`，所以栈帧减量总是 16 的倍数，`call` 前 `%rsp` 必须对齐；不对齐在 ARM64 上是 `SIGBUS`，在 x86 上是 `SIGSEGV`；② SysV 的红区让叶子函数免去 `sub`，AAPCS64 没有红区，叶子函数也要先调整 `sp`；③ 帧指针在 x86 上是可省的开销，在 ARM64 上常与保存 `x30` 合并，几乎免费；④ 递归深度可以按「栈上限 ÷ 帧大小」算出来，再实测验证。如果只记住一件事，那就是：**栈上的每个字节位置都是 ABI 算出来的，不是编译器随手放的。**

## 1.3.13 完整程序一：手写 x86-64 汇编函数库 {#sec-1.3.13}

这一节回答：不用编译器，自己写一组符合 SysV 约定的 x86-64 函数，最少要写哪些指令？在只有 aarch64 机器的环境里，这份代码能验收哪一步，哪一步只能标「未实测」？

::: preview 先抓住一件事
叶子函数不需要栈帧：参数在寄存器里，结果放 `%rax`，只要不碰 `%rbx`、`%rbp`、`%r12`–`%r15`，连 `push` 都不用写。唯一的例外是参数多到寄存器装不下：第 7 个整数参数不在寄存器里，而在返回地址之上，读它是 `8(%rsp)`。这份库在写作机上只能交叉汇编成 `.o`，链接与运行都没有实测。
:::

前几节都在读编译器的输出。这一节反过来：先写，再让工具挑错。库里五个函数——求和、测字符串长度、交换两个 `long`、六个参数相加、七个参数相加——全是叶子函数，不 `call` 别人，也不长期占用任何被调用者保存寄存器。

```asm
# frame.s — 手写 x86-64 叶子函数库（AT&T 语法）
        .text

        .globl sum_to
        .type  sum_to, @function
sum_to:                         # long sum_to(long n)
        xorl   %eax, %eax
        testq  %rdi, %rdi
        jle    .Lsum_done
.Lsum_loop:
        addq   %rdi, %rax
        decq   %rdi
        jne    .Lsum_loop
.Lsum_done:
        ret
        .size  sum_to, .-sum_to

        .globl my_strlen
        .type  my_strlen, @function
my_strlen:                      # size_t my_strlen(const char *s)
        xorl   %eax, %eax
.Lstr_loop:
        cmpb   $0, (%rdi,%rax)
        je     .Lstr_done
        incq   %rax
        jmp    .Lstr_loop
.Lstr_done:
        ret
        .size  my_strlen, .-my_strlen

        .globl swap_pair
        .type  swap_pair, @function
swap_pair:                      # void swap_pair(long *a, long *b)
        movq   (%rdi), %rax
        movq   (%rsi), %rdx
        movq   %rdx, (%rdi)
        movq   %rax, (%rsi)
        ret
        .size  swap_pair, .-swap_pair
```

三个函数各有一个考点。`sum_to` 用 `%rdi` 既做计数器又做加数，循环体三条指令；`jle` 是有符号判断，`n <= 0` 时直接返回 0。`my_strlen` 的 `(%rdi,%rax)` 就是 `s[i]`，`cmpb $0` 只比较一个字节。`swap_pair` 先把两个值都读进寄存器再写回，两个指针指向同一对象时也不会丢值。同一个文件接着写后两个函数：

```asm
        .globl add6
        .type  add6, @function
add6:                           # long add6(long a, ..., long f)
        leaq   (%rdi,%rsi), %rax
        addq   %rdx, %rax
        addq   %rcx, %rax
        addq   %r8, %rax
        addq   %r9, %rax
        ret
        .size  add6, .-add6

        .globl add7
        .type  add7, @function
add7:                           # long add7(long a, ..., long g)
        leaq   (%rdi,%rsi), %rax
        addq   %rdx, %rax
        addq   %rcx, %rax
        addq   %r8, %rax
        addq   %r9, %rax
        addq   8(%rsp), %rax    # 第 7 个参数在返回地址之上
        ret
        .size  add7, .-add7

        .section .note.GNU-stack,"",@progbits
```

`add6` 把六个参数寄存器全用上：`%rdi`、`%rsi`、`%rdx`、`%rcx`、`%r8`、`%r9`；第一条 `leaq (%rdi,%rsi), %rax` 只做加法，不碰内存。`add7` 的第七个参数没有寄存器可用，只能从栈上取。函数入口处 `(%rsp)` 是 `call` 压进来的返回地址，所以第一个栈参数在 `8(%rsp)`。这里没有序言，偏移才恰好是 8；一旦 `push` 一条，偏移就变。

先交叉汇编，再读目标文件：

```text
$ clang --target=x86_64-linux-gnu -c frame.s -o frame.o
$ file frame.o
frame.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
```

把 `frame.o` 送到 `ubuntu24`，符号表能读出每个函数的边界（实测）：

```text
$ readelf -sW frame.o | grep FUNC
     1: 0000000000000000    16 FUNC    GLOBAL DEFAULT    2 sum_to
     2: 0000000000000010    14 FUNC    GLOBAL DEFAULT    2 my_strlen
     3: 000000000000001e    13 FUNC    GLOBAL DEFAULT    2 swap_pair
     4: 000000000000002b    17 FUNC    GLOBAL DEFAULT    2 add6
     5: 000000000000003c    22 FUNC    GLOBAL DEFAULT    2 add7
$ readelf -rW frame.o
```

`.text` 一共 82 字节（`0x52`），五个函数首尾相接，中间没有填充。没有重定位，是因为代码里既没有外部符号，也没有绝对地址；所有跳转都是段内相对偏移。

验收能到哪一步，这张表要说清楚：

| 检查 | 命令 | 结果 |
|:--|:--|:--|
| 目标格式 | `file` | ELF 64-bit x86-64 |
| 函数边界 | `readelf -sW` | 16/14/13/17/22 字节 |
| 重定位 | `readelf -rW` | 无 |
| 反汇编 | `objdump -d` | 失败：`can't disassemble for architecture UNKNOWN!` |

最后一行不是命令写错。`ubuntu24` 上的 GNU objdump 只编进了 aarch64 后端，拿到 x86-64 的 `.o` 会先认出 `file format elf64-little`，再拒绝反汇编。要逐条看指令，得换一台 x86-64 机器。

链接与运行同理：写作机没有 x86 的 C 运行库与加载器，虚拟机没有 x86 CPU，也没有装 `qemu-x86_64`。下面这段 C 只用来确认接口形状，**运行输出未实测**：

```c
/* use_frame.c — 在 x86-64 Linux 上：cc -O2 use_frame.c frame.s -o use_frame */
#include <stdio.h>
long sum_to(long);
unsigned long my_strlen(const char *);
void swap_pair(long *, long *);
long add6(long, long, long, long, long, long);
long add7(long, long, long, long, long, long, long);

int main(void)
{
    long a = 1, b = 2;
    swap_pair(&a, &b);
    printf("%ld %lu %ld %ld %ld\n", sum_to(10), my_strlen("hello"),
           a, b, add6(1,2,3,4,5,6) + add7(1,2,3,4,5,6,7));
    return 0;
}
```

按 ABI 推算，输出应是 `55 5 2 1 49`：`sum_to(10)=55`，`"hello"` 长度 5，交换后 `a=2`、`b=1`，`add6` 得 21、`add7` 得 28，相加 49。这是推算，不是跑出来的。

::: ex 例 1.3.13 · 先猜把 `jle` 换成 `jbe` 会怎样 {#ex-1.3.13}
`sum_to` 用 `testq %rdi, %rdi` 后接 `jle` 处理 `n <= 0`。先猜：如果换成无符号条件的 `jbe`，传入 `n = -1` 时会立刻返回 0，还是进入循环？如果进入，会转多少次？

::: sol 解答
会进入循环，而且几乎转满 2^64 次。`testq` 对任何非零值都置 `ZF=0`、`CF=0`；`jbe` 的条件是 `CF=1` 或 `ZF=1`，此时不成立，于是落入循环体。`%rdi` 从 -1 一路 `decq`，要减到 0 才让 `jne` 失效，也就是 2^64 次。有符号判断不能随手换成无符号判断。
:::
:::

::: errata 关于手写汇编的五个误解
1. **「叶子函数不用栈帧，所以不用管 `%rsp`」**——`call` 已经压了 8 字节返回地址。`add7` 必须按 `8(%rsp)` 读第一个栈参数，任何 `push` 都会把这个偏移改掉。
2. **「`readelf` 能读，就说明能运行」**——它读的是 ELF 头和符号表，与 CPU 能不能执行这段机器码无关。
3. **「`.size` 只是给人看的注释」**——它写进符号表，`readelf -sW` 的 Size 列就是它；漏写会显示 0，函数边界也就没了。
4. **「AT&T 语法里 `%` 和 `$` 可省」**——寄存器必须带 `%`，立即数必须带 `$`；省掉会被当成符号名，汇编阶段就报错。
5. **「六个参数以后全在栈上」**——x86-64 是前 6 个整数在寄存器，第 7 个起在栈；ARM64 是前 8 个在寄存器，第 9 个起在栈。
:::

### 1.3.13 小结

① 叶子函数的最小合规写法是「参数从寄存器取、结果放 `%rax`、不碰被调用者保存寄存器」，不需要序言；② 第 7 个整数参数在 `8(%rsp)`，偏移从函数入口算起，加一条 `push` 就变；③ 交叉汇编能验收语法、符号和长度，不能验收执行。如果只记住一件事，那就是：**手写汇编先对齐 ABI，再谈指令优不优化。**

## 1.3.14 完整程序二：C 侧的 ABI 验证程序 {#sec-1.3.14}

这一节回答：不写一行汇编，只靠一个 C 程序，怎么确认「结构体到底走寄存器还是栈」？同一份源码在 x86-64 与 AArch64 上编译，调用点会差在哪里？

::: preview 先抓住一件事
`sizeof` 和 `offsetof` 只能证明布局，证明不了传参。传参规则要看调用点：x86-64 把 16 字节的结构体按字段拆进 `%rdi`/`%rsi` 或 `%xmm0`/`%xmm1`，24 字节的整块复制到调用者栈上。AArch64 的规则不同：不超过 16 字节的复合类型按双字连续放进 `x0`、`x1`，只有「齐次浮点聚合」才进 `d0`、`d1`；超过 16 字节则传副本地址。同一个 `struct R`，两边落在完全不同的寄存器里。
:::

程序只做三件事：打印五个结构体的大小与偏移；把每种结构体按值传给一个函数；再传七个整数，在 x86-64 上让第 7 个参数越过寄存器上限。为了让调用点保留下来，编译时加 `-fno-inline`；平时不需要这个开关。

```c
/* abi_demo.c — gcc -std=c17 -D_GNU_SOURCE -Wall -Wextra -O2 -fno-inline abi_demo.c */
#include <stdio.h>
#include <stddef.h>

struct P { long x, y; };            /* 16 B，两个整数成员 */
struct Q { double a, b; };          /* 16 B，两个 double */
struct R { long x; double y; };     /* 16 B，一整数一浮点 */
struct S { char c[24]; };           /* 24 B，超过 16 */
struct T { char c; };               /* 1 B */

long   sp(struct P p) { return p.x + p.y; }
double sq(struct Q q) { return q.a * q.b; }
double sr(struct R r) { return (double)r.x + r.y; }
long   ss(struct S s) { return s.c[0] + s.c[23]; }
long   st(struct T t) { return t.c; }

long seven(long a, long b, long c, long d, long e, long f, long g)
{
    return a + b + c + d + e + f + g;
}

int main(void)
{
    printf("sizeof P=%zu Q=%zu R=%zu S=%zu T=%zu\n",
           sizeof(struct P), sizeof(struct Q), sizeof(struct R),
           sizeof(struct S), sizeof(struct T));
    printf("offsets R: x=%zu y=%zu\n",
           offsetof(struct R, x), offsetof(struct R, y));

    struct P p = {20, 22};
    struct Q q = {1.5, 4.0};
    struct R r = {3, 0.5};
    struct S s = {{'A'}};
    struct T t = {'z'};
    s.c[23] = 'B';
    printf("sp=%ld sq=%.1f sr=%.1f ss=%ld st=%ld seven=%ld\n",
           sp(p), sq(q), sr(r), ss(s), st(t), seven(1, 2, 3, 4, 5, 6, 7));
    return 0;
}
```

在 `ubuntu24` 上编译运行（实测）：

```text
$ gcc -std=c17 -D_GNU_SOURCE -Wall -Wextra -O2 -fno-inline abi_demo.c -o abi_demo
$ ./abi_demo
sizeof P=16 Q=16 R=16 S=24 T=1
offsets R: x=0 y=8
sp=42 sq=6.0 sr=3.5 ss=131 st=122 seven=28
```

`sizeof` 与 `offsetof` 在 x86-64 和 AArch64 上完全一样——LP64 的布局规则是共通的。所以这两行只能证明「字段怎么排」，回答不了「参数怎么传」。要回答传参，只能看调用点。

先看 x86-64。写作机没有 Linux 头文件，用 `clang --target=x86_64-linux-gnu -nostdinc -I stub -S` 生成同一份源码的汇编（`stub` 里只有一个 `printf` 原型和一个 `size_t`），下面是调用点与 `ss` 的节选：

```asm
	movl	$20, %edi
	movl	$22, %esi
	callq	sp
	movsd	.LCPI6_0(%rip), %xmm0
	movsd	.LCPI6_1(%rip), %xmm1
	callq	sq
	movl	$3, %edi
	movsd	.LCPI6_2(%rip), %xmm0
	callq	sr
	movq	$7, (%rsp)
	...
	callq	seven

ss:
	movsbq	8(%rsp), %rcx
	movsbq	31(%rsp), %rax
	addq	%rcx, %rax
	retq
```

`P` 走 `%edi`/`%esi`，`Q` 走 `%xmm0`/`%xmm1`，`R` 走 `%edi` + `%xmm0`：x86-64 把结构体切成八字节，每块单独判定「整数还是 SSE」。`S` 没有进寄存器，调用前 24 字节被复制到 `(%rsp)`；`call` 压入返回地址后，被调用者看到的数据从 `8(%rsp)` 开始——这就是 `ss` 里 `8(%rsp)` 与 `31(%rsp)` 的来历。`seven` 的第 7 个参数同样在 `8(%rsp)`。

AArch64 一侧是 `ubuntu24` 上 `objdump -d abi_demo` 的真输出：

```asm
00000000000009e0 <sp>:
 9e0:	8b010000 	add	x0, x0, x1
 9e4:	d65f03c0 	ret
00000000000009f0 <sq>:
 9f0:	1e610800 	fmul	d0, d0, d1
 9f4:	d65f03c0 	ret
0000000000000a00 <sr>:
 a00:	9e620000 	scvtf	d0, x0
 a04:	9e670021 	fmov	d1, x1
 a08:	1e612800 	fadd	d0, d0, d1
 a0c:	d65f03c0 	ret
0000000000000a10 <ss>:
 a10:	39400001 	ldrb	w1, [x0]
 a14:	39405c00 	ldrb	w0, [x0, #23]
 a18:	0b000020 	add	w0, w1, w0
```

`sp` 用 `x0`/`x1`，`sq` 用 `d0`/`d1`，这两条与 x86 同构。`sr` 不一样：`y` 从 `x1` 进来，`fmov d1, x1` 只是把整数寄存器里的位搬进浮点寄存器。原因是 AAPCS64 对不超过 16 字节的复合类型不按字段分「整数/浮点」，而是整块按双字放进通用寄存器；只有成员全为浮点的齐次聚合（HFA）才用 SIMD 寄存器。`ss` 收到的是指针：`[x0]` 与 `[x0, #23]`，24 字节的副本由调用者准备好，地址放 `x0`。

| 结构体 | 字节 | x86-64 | AArch64 |
|:--|--:|:--|:--|
| `P` | 16 | `%rdi`、`%rsi` | `x0`、`x1` |
| `Q` | 16 | `%xmm0`、`%xmm1` | `d0`、`d1`（HFA） |
| `R` | 16 | `%rdi` + `%xmm0` | `x0` + `x1` |
| `S` | 24 | 调用者栈上整块，`8(%rsp)` 起 | `x0` 指向调用者的副本 |
| `T` | 1 | `%edi` 的低字节 | `w0` 的低字节 |

这张表里最容易被背错的是 `S`：x86-64 超过 16 字节的结构体并不「传地址」，而是整块复制到调用者的栈上；AArch64 才是传副本地址。另一个暗坑是 `char` 的符号性：`ss` 里 x86 用 `movsbq`（符号扩展），AArch64 用 `ldrb`（零扩展）。两份平台约定不同，跨架构传 `char` 时写成 `signed char` 或 `unsigned char`，别依赖默认值。

::: ex 例 1.3.14 · 先猜把 `struct S` 缩到 16 字节会怎样 {#ex-1.3.14}
`S` 现在是 `char c[24]`，x86 调用点要复制 24 字节到栈上。先猜：如果把 `S` 改成 `char c[16]`，`ss` 的调用点会变成什么样？`ss` 内部还会访问 `8(%rsp)` 吗？

::: sol 解答
会从「整块压栈」变成「两个八字节进寄存器」：`edi` 放前 8 字节，`rsi` 放后 8 字节，栈上不再复制。`ss` 也随之改成读 `%dil` 与 `%rsi` 的高字节。实际编译出的调用点是 `movl $65, %edi` 加 `movabsq $0x4200000000000000, %rsi`（'B' 在第二个八字节的最高位），`ss` 里则是 `movsbl %dil, %eax` 与 `sarq $56, %rsi`。分类规则只认大小与字段类型，改一个长度，整条传参路径就换了。
:::
:::

::: errata 关于 ABI 验证的五个误解
1. **「`sizeof` 一样，ABI 就一样」**——布局相同、传法可以不同。`S` 在两边都是 24 字节，一边压栈、一边传指针。
2. **「超过 16 字节的结构体都传指针」**——那是 AArch64 的规则；x86-64 的 MEMORY 类是把整块放到调用者栈上。
3. **「AArch64 也按 INTEGER/SSE 拆八字节」**——没有这个分类。`R` 的两个双字都走通用寄存器，浮点成员不单独进 `d` 寄存器。
4. **「`-O2` 反汇编一定能看到调用点」**——函数被内联后调用就消失了。要观察传参，加 `-fno-inline`，或把被调函数放到另一个源文件。
5. **「`char` 在哪个平台都一样」**——x86-64 Linux 默认有符号，AArch64 Linux 默认无符号；`ss` 里 `movsbq` 与 `ldrb` 的差别就是它。
:::

### 1.3.14 小结

① `sizeof`/`offsetof` 只验证布局，传参规则必须看调用点；② x86-64 按八字节把结构体拆进整数或 SSE 寄存器，超过 16 字节整块压栈；③ AArch64 不超过 16 字节的复合类型整块进通用寄存器，HFA 才进 SIMD，超过 16 字节传副本地址；④ `char` 的默认符号性两边不同。如果只记住一件事，那就是：**同一个结构体，在两套 ABI 里可能走完全不同的寄存器。**

## 1.3.15 完整程序三：ARM64 对照实现 {#sec-1.3.15}

这一节回答：把 1.3.13 的五个函数用 AArch64 重写，除了换寄存器名，哪里必须改写法？这次能真跑，跑出来的结果和指令长度又说明了什么？

::: preview 先抓住一件事
AArch64 的前 8 个整数参数在 `x0`–`x7`，第 9 个才上栈；返回地址放在 `x30`，不占栈，所以手写的叶子函数读栈参数用 `[sp]`，而 x86 要读 `8(%rsp)`。叶子函数同样不需要序言。与 1.3.13 不同，这一节有真正的 CPU：汇编、链接、运行、反汇编都能在本机完成，五个函数全部实测。
:::

五个函数与 1.3.13 一一对应，只把名字加上 `a64_` 前缀，避免和 C 库符号撞车。循环用 `subs` 降计数并置标志，字符串用 `ldrb` 一次读一个字节。`sum_to` 先挡掉 `n <= 0`，否则负数会一路减到回绕，和 x86 版本语义不一致。

```asm
// frame64.s — 手写 AArch64 叶子函数库
        .text

        .globl a64_sum_to
        .type  a64_sum_to, %function
a64_sum_to:                     // long a64_sum_to(long n)：n 在 x0
        mov     x1, x0
        mov     x0, #0
        cmp     x1, #0
        b.le    .Lsum_done
.Lsum_loop:
        add     x0, x0, x1
        subs    x1, x1, #1
        b.ne    .Lsum_loop
.Lsum_done:
        ret
        .size  a64_sum_to, .-a64_sum_to

        .globl a64_strlen
        .type  a64_strlen, %function
a64_strlen:                     // size_t a64_strlen(const char *s)：s 在 x0
        mov     x1, x0
        mov     x0, #0
.Lstr_loop:
        ldrb    w2, [x1, x0]
        cbz     w2, .Lstr_done
        add     x0, x0, #1
        b       .Lstr_loop
.Lstr_done:
        ret
        .size  a64_strlen, .-a64_strlen

        .globl a64_swap_pair
        .type  a64_swap_pair, %function
a64_swap_pair:                  // void a64_swap_pair(long *a, long *b)
        ldr     x2, [x0]
        ldr     x3, [x1]
        str     x3, [x0]
        str     x2, [x1]
        ret
        .size  a64_swap_pair, .-a64_swap_pair

        .globl a64_add6
        .type  a64_add6, %function
a64_add6:                       // long a64_add6(long a..f)：x0..x5
        add     x0, x0, x1
        add     x0, x0, x2
        add     x0, x0, x3
        add     x0, x0, x4
        add     x0, x0, x5
        ret
        .size  a64_add6, .-a64_add6

        .globl a64_add7
        .type  a64_add7, %function
a64_add7:                       // long a64_add7(long a..g)：x0..x6
        add     x0, x0, x1
        add     x0, x0, x2
        add     x0, x0, x3
        add     x0, x0, x4
        add     x0, x0, x5
        add     x0, x0, x6
        ret
        .size  a64_add7, .-a64_add7

        .section .note.GNU-stack,"",%progbits
```

`a64_add7` 是这一节最该对照的地方：七个参数全在 `x0`–`x6`，函数体一次内存访问都没有。1.3.13 的 `add7` 却必须读 `8(%rsp)`，因为 x86-64 只有 6 个整数参数寄存器。

在 `ubuntu24` 上汇编、链接、运行（实测）：

```text
$ gcc frame64.s drive64.c -o drive64
$ ./drive64
sum_to(10)=55
strlen("hello")=5
swap: a=2 b=1
add6=21 add7=28
```

驱动是普通 C，把原型写全即可。再补两个边界值：`a64_sum_to(-5)` 与 `a64_sum_to(0)` 都返回 0（实测），与 x86 版本的 `jle` 分支对齐。

函数长度用 `readelf -sW frame64.o` 读，反汇编用 `objdump -d`。`a64_sum_to` 的开头是（实测）：

```asm
0000000000000000 <a64_sum_to>:
   0:	aa0003e1 	mov	x1, x0
   4:	d2800000 	mov	x0, #0x0
   8:	f100003f 	cmp	x1, #0x0
   c:	5400008d 	b.le	1c <a64_sum_to+0x1c>
  10:	8b010000 	add	x0, x0, x1
  14:	f1000421 	subs	x1, x1, #0x1
  18:	54ffffc1 	b.ne	10 <a64_sum_to+0x10>
```

每条 4 字节，地址每次加 4，没有「下一条指令从哪开始」的问题；`aa0003e1` 是 `mov x1,x0`，`8b010000` 是 `add x0,x0,x1`，`d65f03c0` 是 `ret`。

| 函数 | x86-64 字节 | AArch64 字节 |
|:--|--:|--:|
| `sum_to` | 16 | 32 |
| `my_strlen` | 14 | 28 |
| `swap_pair` | 13 | 20 |
| `add6` | 17 | 24 |
| `add7` | 22 | 28 |

五个函数在 AArch64 上全部更长，差距最大的是 `sum_to`（16 对 32）。原因不是 AArch64 指令更笨，而是每条都占满 4 字节：`add6` 两边都是 6 条指令（x86 是 1 条 `lea` 加 4 条 `add` 再返回，AArch64 是 5 条 `add` 再返回），x86 靠变长编码压到 17 字节，AArch64 固定 6 × 4 = 24 字节。`add7` 更典型：两边都是 7 条指令，x86 22 字节，AArch64 28 字节，差的 6 字节全在编码长度上。

::: ex 例 1.3.15 · 先猜给 `a64_add7` 再加两个参数会怎样 {#ex-1.3.15}
`a64_add7` 取 7 个参数，全在寄存器里。先猜：加成 8 个参数时，函数体会不会多出一条从栈上读的指令？加成 9 个呢？

::: sol 解答
8 个参数时不会。`x0`–`x7` 正好八个寄存器，第 8 个参数直接进 `x7`，函数体只多一条 `add x0, x0, x7`，仍然是 4 字节。加到 9 个才会出现栈访问：第 9 个参数由调用者放在自己的栈上，被调用者在入口处从 `[sp]` 读——注意不是 `[sp, 8]`，因为返回地址在 `x30`，没有压栈。x86-64 在参数超过 6 个时就已经要读 `8(%rsp)`，这是两套约定最实际的分界。
:::
:::

::: errata 关于 ARM64 手写函数的五个误解
1. **「`x30` 由被调用者自动保存」**——没有这回事。叶子函数不碰 `x30` 才安全；一旦 `bl` 别人，必须先用 `stp x29, x30, [sp, -16]!` 存起来。
2. **「第一个栈参数在 `[sp, 8]`」**——那是 x86 的布局。AArch64 的返回地址在 `x30`，栈顶就是第一个栈参数，读 `[sp]`。
3. **「`subs` 和 `sub` 只差一个字母」**——`subs` 会写 NZCV，循环末尾的 `b.ne` 靠它；换成 `sub`，标志位停在上一次写标志的指令上，循环次数就不对了。
4. **「写 `w0` 和写 `x0` 是一回事」**——写 `w0` 会把 `x0` 的高 32 位清零。返回值只用到 32 位时没差别，算地址时会截断指针。
5. **「定长指令所以代码更短」**——同一组五个函数全部更长。定长换的是译码简单，不是密度。
:::

### 1.3.15 小结

① AArch64 的前 8 个整数参数在 `x0`–`x7`，第 9 个才上栈，且第一个栈参数在 `[sp]`；② 返回地址在 `x30`，叶子函数不需要序言，非叶子函数要自己保存 `x29`/`x30`；③ 每条指令固定 4 字节，同样 7 条指令比 x86 的变长编码长。如果只记住一件事，那就是：**同一段逻辑，ARM64 用寄存器换内存，x86 用编码换寄存器。**

## 1.3.16 实验一：用 gdb 逐条执行并观察栈帧 {#sec-1.3.16}

这一节回答：gdb 在真实环境里到底能做哪几件事？这台 aarch64 虚拟机上，哪些功能可用、哪些一碰就退，为什么？不能单步时，又怎样观察栈帧？

::: preview 先抓住一件事
gdb 有两个半边。静态半边读符号、反汇编、把源码行和指令对齐，不需要运行程序；动态半边 `run`、`stepi`、`bt`、`x` 要在目标进程上取寄存器和内存。本机的 gdb 15.1 在 AArch64 上初始化 SVE 向量长度失败，`run` 直接退出；静态半边完全可用。实验因此拆成两段：先用 `disassemble` 读出第 9 个参数的位置，再用一个探针程序在运行期打印帧指针链。
:::

先选函数。1.3.11 用 8 个参数演示过 x86 的栈参数；到了 ARM64，8 个参数全在 `x0`–`x7`，一个字节都不上栈，看不出想看的东西。要看到栈参数，必须写 9 个。这不是巧合，正是两套约定「6 个」与「8 个」的分界。

```c
/* many9.c — gcc -std=c17 -D_GNU_SOURCE -Wall -Wextra -g -O0 -o many9 many9.c */
#include <stdio.h>

long many9(long a, long b, long c, long d, long e,
           long f, long g, long h, long i)
{
    long s = a + b + c + d + e + f + g + h + i;
    return s;
}

int main(void)
{
    printf("%ld\n", many9(1, 2, 3, 4, 5, 6, 7, 8, 9));
    return 0;
}
```

先运行，确认函数本身没问题：`./many9` 输出 `45`（实测）。

接下来让 gdb 做它能做的部分——只读不跑。`info functions` 找到符号，`disassemble /r` 把机器码与汇编并排（实测，节选）：

```text
$ gdb -q -batch ./many9 -ex "info functions many9" -ex "disassemble /r many9"
All functions matching regular expression "many9":

File many9.c:
3:	long many9(long, long, long, long, long, long, long, long, long);
Dump of assembler code for function many9:
   0x0000000000000758 <+0>:	d10143ff	sub	sp, sp, #0x50
   0x000000000000075c <+4>:	f9001fe0	str	x0, [sp, #56]
   ...
   0x00000000000007b0 <+88>:	f94003e0	ldr	x0, [sp]
   0x00000000000007b4 <+92>:	8b000020	add	x0, x1, x0
   0x00000000000007b8 <+96>:	f9402be1	ldr	x1, [sp, #80]
   ...
End of assembler dump.
```

序言先 `sub sp, sp, #0x50`，把栈帧定为 80 字节；接着 `x0`–`x7` 依次存到 `[sp+56]` 到 `[sp]`；最后 `ldr x1, [sp, #80]` 取第 9 个参数。80 不是魔法数，它就是帧大小：参数在调用者的栈上，当前 `sp` 比调用者的 `sp` 低了 80 字节。给 `many9` 加两个 `volatile long` 局部变量，序言变成 `sub sp, sp, #0x70`，这条偏移就变成 112（实测）。

再看动态半边（实测）：

```text
$ gdb -q -batch ./many9 -ex "break many9" -ex run
Breakpoint 1 at 0x77c: file many9.c, line 6.
Unable to fetch SVE/SSVE vector length: Invalid argument.
$ echo $?
1
```

断点能设，因为那只是往符号地址上记一笔；`run` 一启动目标进程就失败。SVE 是 ARM 的可伸缩向量扩展，gdb 15.1 在建立目标描述时要读向量长度，这台虚拟机的内核返回 `EINVAL`。程序没有跑起来，`bt`、`x`、`stepi` 依赖同一套目标状态，在这台机器上也不要指望。

| 操作 | 本机 | 依赖 |
|:--|:--|:--|
| `info functions` | 可用 | 符号表 |
| `disassemble /r` | 可用 | 机器码 |
| `disassemble /m` | 可用 | 调试行号 |
| `info line` | 可用 | 调试行号 |
| `run`、`stepi`、`bt`、`x` | 不可用 | 目标进程状态 |

这不是「gdb 坏了」，而是这一套 gdb、内核与虚拟化组合的边界。换一台能正常 `run` 的 ARM64 或 x86 主机，同一组命令就能用。

不能单步，就直接问运行中的程序。下面这个探针用编译器内建函数取帧指针，再把 `bt` 与 `info frame` 关心的三件事打印出来：

```c
/* probe.c — gcc -std=c17 -Wall -Wextra -g -O0 -o probe probe.c */
#include <stdio.h>
#include <stdint.h>

__attribute__((noinline))
long many9(long a, long b, long c, long d, long e,
           long f, long g, long h, long i)
{
    volatile long s = a + b + c + d + e + f + g + h + i;
    uintptr_t fp = (uintptr_t)__builtin_frame_address(0);
    printf("i 在 fp 之上: %d\n", (uintptr_t)&i > fp);
    printf("[fp] 指向调用者帧: %d\n", *(uintptr_t *)fp > fp);
    printf("[fp+8] == 返回地址: %d\n",
           *(uintptr_t *)(fp + 8) == (uintptr_t)__builtin_return_address(0));
    return s;
}

int main(void)
{
    printf("many9=%ld\n", many9(1, 2, 3, 4, 5, 6, 7, 8, 9));
    return 0;
}
```

`ubuntu24` 上运行（实测）：

```text
$ gcc -std=c17 -Wall -Wextra -g -O0 -o probe probe.c
$ ./probe
i 在 fp 之上: 1
[fp] 指向调用者帧: 1
[fp+8] == 返回地址: 1
many9=45
```

三行 `1` 分别对应三条事实：第 9 个参数不在本帧，而在调用者帧；`[x29]` 存着上一帧的 `x29`；`[x29+8]` 存着 `x30`，也就是返回地址。`bt` 就是顺着这条链一帧一帧往上走的，`info frame` 打印的也是这些字段。

在 x86-64 主机上，命令换成下面这组（**未实测**，本机没有 x86 运行环境）：

```text
(gdb) break many9
(gdb) run
(gdb) info registers rdi rsi rdx rcx r8 r9 rsp rbp
(gdb) x/4gx $rsp        # [0]=返回地址，[1]=g，[2]=h，[3]=i
(gdb) bt
(gdb) info frame
(gdb) stepi
(gdb) x/6i $pc
```

x86 的 9 个参数里，前 6 个在寄存器，第 7、8、9 个分别在 `8(%rsp)`、`16(%rsp)`、`24(%rsp)`。ARM64 要到第 9 个才上栈，所以同一段 gdb 命令，两边的 `x/4gx` 会看到不同的东西。

::: ex 例 1.3.16 · 先猜 `[sp, #80]` 里的 80 是什么 {#ex-1.3.16}
`many9` 的 `disassemble` 里，第 9 个参数从 `[sp, #80]` 读。先猜：80 是 ABI 规定的固定偏移，还是这份编译结果的帧大小？如果给函数加两个 `long` 局部变量，这个数会变吗？

::: sol 解答
是本帧大小，不是固定偏移。序言 `sub sp, sp, #0x50` 把 `sp` 减了 80，而第 9 个参数留在调用者的 `sp` 处，两者正好差 80。加两个 `volatile long` 后，序言变成 `sub sp, sp, #0x70`，读取偏移随之变成 `[sp, #112]`（实测）。这也是为什么不能背「第 9 个参数在 [sp, #80]」：要先看序言减了多少。
:::
:::

::: errata 关于 gdb 实验的五个误解
1. **「gdb 装好了就能 `run`」**——本机 `run` 在启动目标时因 SVE 向量长度查询失败而退出，程序根本没跑。`break` 能设不代表能运行。
2. **「8 参数函数在 ARM64 上能看到栈参数」**——8 个整数参数正好占满 `x0`–`x7`，第 9 个才上栈。拿 8 参数函数做实验，只会看到 8 次寄存器保存。
3. **「ARM64 和 x86 一样，第 7 个参数就上栈」**——x86-64 是 6 个寄存器，ARM64 是 8 个。同一个函数，两边的栈参数起点不同。
4. **「`disassemble` 必须先 `run`」**——不需要。它读的是 ELF 里的代码与符号，静态就能用；也正因如此，它在本机仍然可用。
5. **「`__builtin_frame_address` 是标准 C」**——它是 GCC/Clang 扩展，而且依赖帧指针。开了优化、函数被内联后，拿到的可能不是你以为的那一帧。
:::

### 1.3.16 小结

① gdb 的静态半边（符号、反汇编、行号）不需要运行程序，在本机可用；动态半边（`run`、`stepi`、`bt`、`x`）因 SVE 初始化失败不可用；② ARM64 的 8 参数函数看不到栈参数，必须写到 9 个，第 9 个在 `[sp + 帧大小]`；③ 帧指针链是 `[x29]` 指上一帧、`[x29+8]` 存返回地址，探针程序能在没有 gdb 时把这三件事打印出来。如果只记住一件事，那就是：**先确认工具能做到哪一步，再设计实验。**

## 1.3.17 实验二：objdump 与 readelf 看机器码、重定位 {#sec-1.3.17}

这一节回答：同一份 C，`objdump` 能给你什么、`readelf` 又能给你什么？当反汇编器直接拒绝这份文件时，你还能从里面读出哪些事实？

::: preview 先抓住一件事
`objdump` 把字节翻成指令，`readelf` 直接读文件结构，重定位（relocation）是「链接前还没填上的地址」清单。三样对照，才看得出 `call` 后面四个字节为什么是 0、`adrp` 为什么要配一条 `ldr`。这台 aarch64 机器上的 GNU objdump 对 x86 目标只回一句 `can't disassemble for architecture UNKNOWN!`——这句话本身就是判据：文件没坏，是工具没编进这个后端。
:::

先写一份同时含三类引用的 C：一个全局变量、一个外部函数、一个 24 字节的结构体。

```c
/* lab1c03_reloc.c */
struct S { char c[24]; };

extern long ext(long);          /* 外部符号：制造 PLT 调用 */
long g = 7;                     /* .data */
static const long K = 1000;     /* .rodata */

long use_globals(void) { return g + K; }
long call_ext(long x)   { return ext(x) + 1; }
long ss(struct S s)     { return s.c[0] + s.c[8] + s.c[23]; }
```

`K` 是小常量，`-O2` 会把它折进指令，所以最后只剩一个 `.data` 引用。两边各编一次：写作机上用 clang 交叉出 x86-64 目标文件，`ubuntu24` 上用 GCC 出 aarch64 目标文件。

```text
$ clang --target=x86_64-linux-gnu -O2 -c lab1c03_reloc.c -o lab1c03_reloc_x86.o
$ file lab1c03_reloc_x86.o
lab1c03_reloc_x86.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
$ gcc -O2 -c lab1c03_reloc.c -o lab1c03_reloc_a64.o        # ubuntu24
```

把 x86 的对象文件传到 `ubuntu24`，先看符号表（实测）：

```text
$ readelf -sW lab1c03_reloc_x86.o | grep -E 'FUNC|OBJECT'
     3: 0000000000000000    13 FUNC    GLOBAL DEFAULT    2 use_globals
     4: 0000000000000000     8 OBJECT  GLOBAL DEFAULT    4 g
     5: 0000000000000010    11 FUNC    GLOBAL DEFAULT    2 call_ext
     7: 0000000000000020    25 FUNC    GLOBAL DEFAULT    2 ss
```

三个函数首尾相接：`use_globals` 占 `0x0`–`0xc` 共 13 字节，`call_ext` 从 `0x10` 起 11 字节，`ss` 从 `0x20` 起 25 字节，`.text` 一共 57 字节。`g` 是 `OBJECT`，在 4 号节（`.data`），8 字节。这份清单只说明「有什么、多大」，不说明「里面是什么指令」。

再看重定位（实测）：

```text
$ readelf -rW lab1c03_reloc_x86.o
Relocation section '.rela.text' at offset 0x1d0 contains 2 entries:
    Offset             Info             Type               Symbol's Value  Symbol's Name + Addend
0000000000000008  0000000400000002 R_X86_64_PC32          0000000000000000 g - 4
0000000000000012  0000000600000004 R_X86_64_PLT32         0000000000000000 ext - 4
```

两条都是「这里先留空，链接时填」。`Offset` 是被改的字节位置；`Addend` 里的 `-4` 不是负偏移，而是因为 x86 的 PC 相对寻址从「下一条指令」算起，要补上自己这 4 字节。`PC32` 用于数据，`PLT32` 用于外部函数：后者可能被动态链接器接管，所以走 PLT。

指令长什么样？写作机上换一个 objdump 就能看：

```text
$ objdump -d lab1c03_reloc_x86.o        # 写作机：LLVM objdump 21
0000000000000000 <use_globals>:
       0: b8 e8 03 00 00          movl   $0x3e8, %eax
       5: 48 03 05 00 00 00 00    addq   (%rip), %rax
       c: c3                      retq
0000000000000010 <call_ext>:
      10: 50                      pushq  %rax
      11: e8 00 00 00 00          callq  0x16 <call_ext+0x6>
      16: 48 ff c0                incq   %rax
      19: 59                      popq   %rcx
      1a: c3                      retq
0000000000000020 <ss>:
      20: 48 0f be 44 24 08       movsbq 0x8(%rsp), %rax
      26: 48 0f be 4c 24 10       movsbq 0x10(%rsp), %rcx
      2c: 48 01 c1                addq   %rax, %rcx
      2f: 48 0f be 44 24 1f       movsbq 0x1f(%rsp), %rax
      35: 48 01 c8                addq   %rcx, %rax
      38: c3                      retq
```

三处正好对上重定位表：`5:` 那条 `addq` 的位移从第 8 字节开始，所以第一条 `Offset` 是 `8`；`11:` 的 `e8` 后面四个零从第 `0x12` 字节开始，所以第二条是 `12`。`callq 0x16` 是未链接时的假目标，真实地址要等链接器按 `PLT32` 填。

`ss` 里的三个偏移更值得停一下：`0x8`、`0x10`、`0x1f`。24 字节结构体整块放在调用者栈上，被调用者看到的第 0 个字节就在 `8(%rsp)`（`(%rsp)` 是返回地址），于是 `c[8]` 落在 `16(%rsp)`、`c[23]` 落在 `31(%rsp)`。**`c[8]` 的偏移是 16，不是 8**——漏算一个返回地址，就整整差 8 字节。

同一份文件在 `ubuntu24` 上交给 GNU objdump（实测）：

```text
$ objdump -d lab1c03_reloc_x86.o
lab1c03_reloc_x86.o:     file format elf64-little

objdump: can't disassemble for architecture UNKNOWN!
```

它认出了 `elf64-little`，但没有 x86 后端。这句报错不是「文件坏了」：`readelf` 刚刚从同一个文件里读出了符号和重定位。反汇编只是 objdump 的一项能力，缺后端就是缺，换工具或换机器即可。

同一份 C 在 `ubuntu24` 上编成 aarch64 目标文件，objdump 就能连指令带重定位一起给你（实测）：

```text
$ objdump -dr lab1c03_reloc_a64.o
0000000000000000 <use_globals>:
   0: 90000000   adrp  x0, 0 <use_globals>
        0: R_AARCH64_ADR_PREL_PG_HI21  .data
   4: f9400000   ldr   x0, [x0]
        4: R_AARCH64_LDST64_ABS_LO12_NC  .data
   8: 910fa000   add   x0, x0, #0x3e8
   c: d65f03c0   ret
0000000000000010 <call_ext>:
  10: a9bf7bfd   stp   x29, x30, [sp, #-16]!
  14: 910003fd   mov   x29, sp
  18: 94000000   bl    0 <ext>
        18: R_AARCH64_CALL26  ext
  1c: 91000400   add   x0, x0, #0x1
  20: a8c17bfd   ldp   x29, x30, [sp], #16
  24: d65f03c0   ret
  28: d503201f   nop
0000000000000030 <ss>:
  30: 39400001   ldrb  w1, [x0]
  34: 39402003   ldrb  w3, [x0, #8]
  38: 39405c02   ldrb  w2, [x0, #23]
  3c: 0b030020   add   w0, w1, w3
  40: 0b020000   add   w0, w0, w2
  44: 92402400   and   x0, x0, #0x3ff
  48: d65f03c0   ret
```

三个差别一眼可见：

1. **取一个全局变量要两条指令、两条重定位。** `adrp` 只能算到 4 KiB 页基址，低 12 位由随后的 `ldr` 补；x86 一条 `addq (%rip), %rax` 加一条 `PC32` 就够。
2. **调用外部函数用 `bl`，重定位是 `CALL26`。** 26 位立即数左移两位，覆盖 ±128 MiB；x86 的 `call rel32` 覆盖 ±2 GiB。
3. **`ss` 收到的是指针。** 24 字节超过 16，AArch64 传副本地址，所以是 `[x0]`、`[x0, #8]`、`[x0, #23]`；x86 是整块压栈，所以是 `8(%rsp)`、`16(%rsp)`、`31(%rsp)`。同一个 `char` 加法，x86 用 `movsbq` 符号扩展、aarch64 用 `ldrb` 零扩展，因为两平台裸 `char` 的默认符号性不同（[1.3.14](#sec-1.3.14)）。

再补一个量级：同一份源码，x86 的 `.text` 57 字节，aarch64 的 76 字节（`readelf -SW` 的节大小实测，含各自的填充 `nop`）。这个差不是「谁更先进」，是编码方式与 ABI 的组合结果。

::: def 定义 1.3.17 · 重定位（relocation） {#def-1.3.17}
目标文件里的「待填空位」记录：哪一段字节、按什么规则、填入哪个符号的地址。编译时不知道最终地址——外部函数在别的库，全局变量在别的节——所以先写 0，再留一条 `R_X86_64_PC32`、`R_AARCH64_CALL26` 这样的记录；链接器据此算出真值写回。`readelf -r` 看清单，`objdump -dr` 把清单贴在对应指令下面。
:::

::: errata 关于反汇编与重定位的四个误解
1. **「objdump 报错说明文件坏了」**——`readelf` 能从同一个文件读出符号与重定位；缺的是 objdump 的架构后端，不是文件。
2. **「重定位是错误」**——它是链接前的正常状态。可执行文件里通常已经没有 `.rela.text`，除非留着动态链接的跳转槽。
3. **「`- 4` 表示往后退 4 字节」**——它是 PC 相对寻址的修正量：目标地址减去「下一条指令」的地址，不是减去本条。
4. **「反汇编里的 `callq 0x16` 就是调用目标」**——未链接时那是占位，`0x16` 只是下一条指令的地址；真实目标在链接后才有。
:::

### 1.3.17 小结

① `readelf -sW` 给符号与长度、`readelf -rW` 给待填空位、`objdump -d` 给指令，三样对照才完整；② x86 的 `PC32`/`PLT32` 只需一个 32 位位移，AArch64 取全局要 `adrp`+`ldr` 两条重定位，调用是 `CALL26`；③ 反汇编器缺后端时，报错原文就是判据，别把它当成文件损坏。如果只记住一件事，那就是：**机器码里的 0 不代表 0，先看有没有一条重定位指着它。**

::: method 即时自测 · 1.3.17
**Q1（记忆）** `R_X86_64_PC32` 与 `R_X86_64_PLT32` 分别出现在哪条指令上？`Offset` 指向哪里？

**Q2（辨析）** 为什么 `ss` 里 `c[8]` 在 x86 是 `16(%rsp)`，而 aarch64 是 `[x0, #8]`？

**Q3（应用）** `objdump -d` 对 x86 目标报 `can't disassemble for architecture UNKNOWN!`，你手上还有哪些命令能继续验收这个文件？

**Q4（迁移）** 一条 `bl` 的立即数是 0，下面挂着 `R_AARCH64_CALL26`。链接后这个 0 会变成什么？目标太远时会怎样？

::: sol 答案
**A1** `PC32` 在 `use_globals` 的 `addq (%rip), %rax` 上，`PLT32` 在 `call_ext` 的 `callq` 上；`Offset` 指向被填的那 4 个字节的起始位置，即 `8` 与 `0x12`。

**A2** x86 把 24 字节结构体整块复制到调用者栈上，被调用者看到的结构体从 `8(%rsp)` 起（`(%rsp)` 是返回地址），所以 `c[8]` 在 `16(%rsp)`；AArch64 超过 16 字节传副本地址，`x0` 指向结构体开头，`c[8]` 就是 `[x0, #8]`。

**A3** `file`、`readelf -h/-sW/-rW`、`size`、`nm`：格式、符号、长度、重定位都能验；要看指令，换一台 x86 机器，或换一个带 x86 后端的反汇编器（写作机的 LLVM objdump 就能读）。

**A4** 链接器把 26 位字段填成「目标与本条之差除以 4」。超出 ±128 MiB 时，链接器要么插入跳板（veneer），要么报 `relocation truncated to fit`，取决于目标文件格式与选项。
:::
:::

## 1.3.18 三架构 × 双语言：同一个函数的六种实现 {#sec-1.3.18}

这一节回答：同一段求和，x86-64、AArch64、RISC-V 各长什么样？换成 Rust 又差在哪？在只到汇编层的证据面前，哪些话能说、哪些不能说？

::: preview 先抓住一件事
六格里有四格有真汇编：三种 ISA 的 C 版本，加 x86-64 的 Rust 版本；Rust 的 ARM64 与 RISC-V 版本没装目标库，只能标未实测。这一节**没有任何跨架构运行时间**——能比的只有指令形状、编码长度，以及编译器替你做了什么变换。
:::

被实现的函数与 1.3.13 的 `sum_to` 同义：

```c
/* lab1c03_sum.c */
long sum_to(long n)          /* 1 + 2 + ... + n，n <= 0 时返回 0 */
{
    long s = 0;
    for (long i = 1; i <= n; i++)
        s += i;
    return s;
}
```

三条命令，三个架构，都只停到 `-S`：

```text
$ clang --target=x86_64-linux-gnu -O2 -S lab1c03_sum.c -o sum_x86.s          # 写作机，clang 21
$ /opt/homebrew/opt/llvm@22/bin/clang --target=riscv64-linux-gnu -O2 -S lab1c03_sum.c -o sum_rv.s
$ gcc -O2 -S lab1c03_sum.c -o sum_a64.s                                      # ubuntu24，GCC 13.3
```

写作机的 Apple clang 21 里没有 RISC-V 后端（`--print-targets` 只列 aarch64、arm、wasm、x86），RISC-V 那一格用的是同机 Homebrew LLVM 22.1.8 的 clang。先交代这一点，免得你以为三格出自同一套编译器。

### 三个 C 版本

x86-64（clang 21，`-O2`，实测汇编层）：

```asm
sum_to:
        testq   %rdi, %rdi
        jle     .LBB0_1
        leaq    -1(%rdi), %rax
        leaq    -2(%rdi), %rcx
        mulq    %rcx
        shldq   $63, %rax, %rdx
        leaq    (%rdx,%rdi,2), %rax
        decq    %rax
        retq
.LBB0_1:
        xorl    %eax, %eax
        retq
```

循环没了。clang 认得出这是等差数列，直接换成闭式：一次 64×64→128 位乘法算 `(n-1)(n-2)`，`shldq` 把 128 位积右移一位取一半，再加 `2n` 减 1；`jle` 挡住 `n <= 0`，负数不进乘法。

AArch64（GCC 13.3，`-O2`，实测汇编层）：

```asm
sum_to:
        cmp     x0, 0
        ble     .L4
        add     x2, x0, 1
        mov     x1, 1
        mov     x0, 0
.L3:
        add     x0, x0, x1
        add     x1, x1, 1
        cmp     x1, x2
        bne     .L3
        ret
.L4:
        mov     x0, 0
        ret
```

同一优化级别，GCC 没做闭式变换，循环还在，一轮 4 条。所以下面比较指令条数时要记住：有一半差异来自编译器选择，不是 ISA 决定的。

RISC-V 64（clang 22.1.8，`-O2`，实测汇编层）：

```asm
sum_to:
        blez    a0, .LBB0_2
        slli    a1, a0, 1
        addi    a2, a0, -1
        addi    a0, a0, -2
        mul     a3, a2, a0
        mulhu   a0, a2, a0
        slli    a0, a0, 63
        srli    a3, a3, 1
        or      a0, a0, a3
        add     a0, a0, a1
        addi    a0, a0, -1
        ret
```

和 x86 是同一个闭式公式，但 128 位积的处理不同：RV64 的 `mul` 只给低 64 位，高位要靠 `mulhu` 再拼；它没有 x86 的 `rdx:rax` 双寄存器结果，也没有一条 `shld` 能跨两个寄存器移位。

### Rust 那一格

写作机的 rustc 1.99.1 装了 `x86_64-unknown-linux-gnu` 标准库，所以 Rust 只有 x86 这一格有真汇编（实测汇编层）：

```text
$ rustc -O --crate-type cdylib --emit asm --target x86_64-unknown-linux-gnu lab1c03_sum.rs -o sum_rust_x86.s
```

```asm
sum_to:
        testq   %rdi, %rdi
        jle     .LBB0_1
        movl    $1, %ecx
        cmpq    $28, %rdi
        jae     .LBB0_4
        ...
.LBB0_6:
        paddq   %xmm1, %xmm0
        paddq   %xmm2, %xmm0
        paddq   %xmm1, %xmm3
        paddq   %xmm4, %xmm1
        addq    $-4, %rax
        jne     .LBB0_6
        ...
.LBB0_8:
        addq    %rcx, %rax
        incq    %rcx
        cmpq    %rdi, %rcx
        jle     .LBB0_8
        retq
```

Rust 版本没有换成闭式乘法，而是走 SSE 向量化：一次 `paddq` 加四个 64 位整数，剩下不足四个的尾巴用标量循环 `.LBB0_8` 补。原因不在「Rust 更笨」，在语义：C 的有符号溢出是未定义行为，编译器可以假设它不发生，于是敢把循环换成公式；Rust 的 `+=` 在 release 下**定义为回绕**，编译器不能假设不溢出，只能老实地加，顺手把它向量化。

六格的证据状态：

| 实现 | 工具与选项 | 输出形状 | 状态 |
|:--|:--|:--|:--|
| C · x86-64 | clang 21，`-O2 -S` | 闭式乘法，快路径 9 条 | 实测（汇编层） |
| C · AArch64 | GCC 13.3，`-O2 -S` | 保留循环，一轮 4 条 | 实测（汇编层） |
| C · RV64 | clang 22.1.8，`-O2 -S` | 闭式乘法，快路径 12 条 | 实测（汇编层） |
| Rust · x86-64 | rustc 1.99.1，`-O --emit asm` | SSE 向量化 | 实测（汇编层） |
| Rust · AArch64 | — | 目标库未安装 | 未实测 |
| Rust · RV64 | — | 目标库未安装 | 未实测 |

后两格不是「懒得写」：`rustc --print target-libdir --target aarch64-unknown-linux-gnu` 指向的目录不存在，`ubuntu24` 上也没有 `rustc`（`command -v rustc` 空）。装目标库要联网下载，这里不装，所以只标状态。

### 三套 ABI 的对照

| 维度 | x86-64 | AArch64 | RV64GC |
|:--|:--|:--|:--|
| 指令长度 | 1–15 字节 | 固定 4 字节 | 固定 4 字节（C 扩展可 2 字节） |
| 通用寄存器 | 16 | 31 + `xzr` | 32（`x0` 恒 0） |
| 整数参数 | rdi, rsi, rdx, rcx, r8, r9 | x0–x7 | a0–a7 |
| 返回值 | rax | x0 | a0 |
| 返回地址 | 栈 | x30（LR） | ra |
| 条件机制 | RFLAGS（CF/ZF/SF/OF） | NZCV（可选设置） | 无标志，比较即分支 |
| 系统调用 | `syscall`（rax 编号） | `svc #0`（x8 编号） | `ecall`（a7 编号） |

这张表说明的是「换架构时哪些名字要换」，不是「谁更快」。表里没有一行是跑出来的时间，因为手边没有一台机器能同时执行三种 ISA 的代码；指令条数也只能在「同一编译器、同一选项」下比，而三格用了两个编译器。

### 两种语言怎么接上

Rust 要想被 C 调用，边界只有三句话：导出用 `#[no_mangle] pub extern "C" fn`，参数和返回值必须是 FFI-safe 类型，结构体要加 `#[repr(C)]`；C 要调 Rust 就把生成的 `.a` 一起链接，符号名与 C 版本完全相同；回调里不能让 panic 穿过 `extern "C"` 边界。这三条与 1.3.11 的参数规则是同一套东西，只是换了个执行者。

::: note 为什么 Rust 版本值得在系统课里出现
不是因为「更安全」这句口号，而是因为它把一些 C 里靠约定维持的东西变成了语言规则：整数溢出的行为在 debug/release 下不同但**有定义**；数组越界一定 panic（除非 `get_unchecked`）；`repr(Rust)` 的结构体允许编译器重排字段，跨 FFI 必须写 `#[repr(C)]`；跨 FFI 的 panic 会 abort，而不是悄悄展开。这些规则与 1.2、1.3 讲的 ABI/表示是同一套知识，只是换了一个执行者。
:::

::: errata C 与 Rust 混编的五个坑
1. **「Rust 结构体直接传给 C」**——默认 `repr(Rust)` 不保证字段顺序，必须 `#[repr(C)]`；嵌套类型也要逐层 `repr(C)`。
2. **「`as` 转换和 C 的强制转换一样」**——Rust 的 `as` 在整数间截断、浮点转整数饱和（NaN → 0），没有 UB；C 的越界转换是 UB。两者结果可能不同。
3. **「release 下溢出会 panic」**——release 默认 `overflow-checks = false`，回绕；要 panic 得在 `Cargo.toml` 里显式开启。
4. **「Rust 函数不会崩」**——`unwrap`、数组越界、除零都会 panic；panic 穿越 `extern "C"` 边界会 abort 整个进程。
5. **「`#[no_mangle]` 就能被 C 调用」**——还要 `extern "C"` 指定调用约定，且参数类型必须是 FFI-safe（不能用 `String`/`Vec` 直接传）。
:::

### 1.3.18 小结

① 三种 ISA 的参数、返回值、返回地址、条件机制各有一套名字，换架构先换这张表；② `-O2` 下同一个函数可能被判成三种形状——闭式乘法、保留循环、向量化——其中一半差在编译器，不在 ISA；③ 只有汇编层证据时，能说编码和 ABI，不能说服性能。如果只记住一件事，那就是：**比较架构先固定编译器与选项，否则你比的是编译器。**

## 1.3.19 十二条汇编陷阱 {#sec-1.3.19}

这一节回答：读汇编、写汇编、跨 ABI 调函数时，坑集中在哪几处？每一条的现象、根因、改法分别是什么？

::: preview 先抓住一件事
十二条归成三组：**寄存器归谁保存**、**栈与参数的边界**、**工具与语义的假设**。判断任何一条只需问两句：这个值现在归谁管？它此刻在哪个地址？第 1–9 条在 x86-64 上，第 10、11 条在 AArch64 上，第 12 条两边都适用。
:::

先看真实现场。1.3.12 把 `sp` 故意错开 8 字节再存 16 字节，程序当场 `Bus error (core dumped)`，`echo $?` 得 135 = 128 + 7，信号是 `SIGBUS`（实测，ubuntu24）。同一次实验里往 64 字节的 `buf` 写 80 字节：默认栈保护下 canary 比对失败，`SIGABRT`，退出码 134；关掉保护后 `ret` 跳到 `0x4141414141414141`，PC 不对齐又变成 135。同一个 bug，两种死法。

栈深也能算。同样是 80 字节帧的递归函数，10 万层通过，11 万层 `SIGSEGV`（139，实测），与 8 MiB 默认栈除以 80 字节的估算吻合。栈溢出不是「大概几十万层」的玄学。

| # | 现象 | 原因 | 修复 |
|--:|:--|:--|:--|
| 1 | 调用库函数后局部变量变成垃圾 | 用了 callee-saved 寄存器（rbx/rbp/r12–r15）却没保存 | 入口 `push`，出口 `pop`，或用 caller-saved（rax/rcx/rdx/rsi/rdi/r8–r11） |
| 2 | 调用 `printf` 时 `SIGSEGV`，崩在 `movaps` | `call` 前 `%rsp` 不是 16 的倍数 | 调整 `sub` 的字节数为 16 的倍数 |
| 3 | 可变参数函数读到垃圾浮点值 | 没设置 `%al`（向量寄存器个数） | `movb $n, %al` 再调用 |
| 4 | `call` 之后参数寄存器里的值变了 | 参数寄存器是 caller-saved | 调用前存到栈或 callee-saved 寄存器 |
| 5 | `mov (%rax), (%rbx)` 汇编报错 | x86 不允许内存到内存 | 经一个寄存器中转 |
| 6 | 写 `%eax` 后 `%rax` 高 32 位变 0，误以为出错 | x86-64 规定 32 位写清零高 32 位 | 这是特性；需要保留高位就用 64 位指令 |
| 7 | 负数扩展后值不对 | 用了 `movzbl`（零扩展）而非 `movsbl` | 按源类型选 `movz`/`movs` |
| 8 | 乘法后 `%rdx` 被踩 | 单操作数 `imulq` 把 128 位积写进 `rdx:rax` | 用双操作数 `imul`，或先保存 `%rdx` |
| 9 | 返回大结构体的函数调用后栈错乱 | 忘了隐藏指针占 `%rdi`，后续参数整体后移 | 按 ABI 把隐藏指针算作第 0 个参数 |
| 10 | AArch64 函数 `ret` 跳飞 | 非叶子函数没保存 `x30` | `stp x29,x30,[sp,#-16]!` / `ldp` 恢复 |
| 11 | AArch64 在 `sp` 以下存局部值，数据莫名被改 | AAPCS64 没有红区，`sp` 以下是未分配区 | 先 `sub sp, sp, #16` 再存，别抄 x86 的 128 字节 |
| 12 | 内联汇编「偶尔」算错 | 没写 `"memory"` clobber 或 `volatile`，被优化器重排/删除 | 明确输入输出约束与 clobber，必要时 `asm volatile` |

第 2 条与第 11 条最容易互相抄错。x86-64 的 16 字节对齐是硬要求：`movaps` 这类指令碰上不对齐的操作数就异常；AArch64 的 `sp` 始终 16 字节对齐，但**没有** x86 那种 128 字节红区，`sp` 以下写进去的值随时可能被信号帧盖掉。

::: def 定义 1.3.19 · 红区（red zone） {#def-1.3.19}
x86-64 SysV ABI 允许叶子函数在 `%rsp` 以下 128 字节内直接读写，不必先 `sub` 调整栈指针；这段「不用申请就能用」的空间叫红区。信号处理函数可能覆盖它，所以只有确定不会被信号打断时才能用。AArch64 的 AAPCS64 没有这条约定，`sp` 以下就是未分配区。
:::

补充三条与工具链相关的边界：

- **`.note.GNU-stack`**：手写 `.s` 若不含这个节，链接器会警告「executable stack」，并让整个进程栈可执行（安全风险）。现代 GCC/Clang 的 C 代码自动带这个标记，手写汇编要自己加。
- **`-fomit-frame-pointer`**：`-O1` 以上默认开启，栈回溯依赖 CFI/ORC 信息；`perf record -g` 拿不到调用图时先检查这个选项。
- **内联汇编的 `"+r"` 与 `"=r"`**：`=` 表示只写，`+` 表示读写。把读写约束写成只写，编译器可能复用同一个寄存器承载两个值，产生难以复现的错误。

::: errata 四个关于汇编的误解
1. **「手写汇编一定比 C 快」**——现代编译器在寄存器分配、指令选择、向量化上通常优于手写；手写汇编的价值在于访问 C 无法表达的指令（`cpuid`、特殊屏障）或精确控制 ABI。
2. **「`lea` 比 `add` 快」**——在多数微架构上两者同延迟；`lea` 的优势是不改标志位、能一次做「基址+变址×比例」，不是绝对更快。
3. **「`-O0` 的汇编能代表程序行为」**——`-O0` 把变量放在栈上、禁止内联，与发布版本差异巨大；用它验证语义可以，用它评估性能会得出完全错误的结论。
4. **「x86 的红区在 AArch64 上照用」**——没有红区。第 11 条旧说法「访问栈下 128 字节崩溃」也不准确：多数时候不会立刻崩，而是被信号帧覆盖，过一阵才以别的形式出错。
:::

### 1.3.19 小结

① 前九条都在问「这个寄存器、这段栈归谁」，答对了改法自然出来；② 后三条在问「工具和 ABI 的假设是什么」，跨架构照抄是最常见的错；③ 退出码是线索：134 多半是 canary，135 是 `SIGBUS`（对齐），139 是 `SIGSEGV`（越界或栈溢出）。如果只记住一件事，那就是：**先分清是「归谁管」错了，还是「在哪个地址」错了，再动代码。**

**Q2（辨析）** 同样是栈指针不对齐，为什么 x86 上可能崩在 `movaps`，AArch64 上却报 `SIGBUS`？

**Q3（应用）** 你写了一个 AArch64 函数，内部 `bl` 了 `printf`，返回后调用者的局部变量错乱。先查哪两条？

**A1** 134 = `SIGABRT`（canary 校验失败）；135 = `SIGBUS`（`sp` 不对齐或 PC 不对齐）；139 = `SIGSEGV`（递归 11 万层）。三个都出自 1.3.12 的实测。

**A3** ① `x30` 没保存——`bl` 会覆盖返回地址；② 用到的 `x19`–`x28` 没保存，它们是 callee-saved。

**A4** 会写到 `sp` 以下：AArch64 没有红区，那块空间不属于本帧，信号处理或下一次调用会覆盖它。正确做法是先 `sub sp, sp, #16` 再存。

## 1.3.20 本章小结 {#sec-1.3.20}

这一节回答：这一章学完，你能独立读懂哪一段汇编、做哪一次实验，又在哪些地方必须承认「这台机器上看不见」？

::: preview 先抓住一件事
判据是：**给你一段 C，你能先说出它该长成什么样——参数放哪、栈帧多大、循环还是闭式——再打开工具核对；核对不上时，说得出是编译器换了形状，还是这台机器根本不给你看。**
:::

这一章的主线是**从 C 回到机器，再从机器回到 ABI**。

第一段（1.3.1–1.3.8）是 x86-64 的基础与读机器码。16 个通用寄存器、6 个整数参数寄存器、`lea` 的地址算式、数据宽度后缀、`cmp`/`test` 的标志位、`if`/`switch`/循环的形状、`call`/`ret` 的栈帧、数组与结构体的偏移，最后用 `objdump` 与 `gdb` 把源码行、指令、机器码对起来。这一段只回答两个问题：**值在哪，控制流去哪。**

第二段（1.3.9–1.3.12）是 ARM64 对照与 ABI 细节。`x0`–`x7` 收前 8 个参数，返回地址在 `x30`，`stp`/`ldp` 成对搬运，条件码要显式设置；ABI 细节则落在一串具体数字上：第 9 个参数才上栈且在 `[sp]`，24 字节结构体在 x86 从 `8(%rsp)` 起、`c[8]` 落在 `16(%rsp)` 而不是 8，`sp` 错位 8 字节换来 `Bus error` 和退出码 135，canary 被覆盖是 134，80 字节帧的递归 10 万层过、11 万层崩。

第三段（1.3.13–1.3.19）是五份代码、两个实验和一组陷阱。`frame.s` 的五个 x86 叶子函数只交叉汇编成 `.o`，长度 16/14/13/17/22 字节；`abi_demo.c` 证明 `sizeof` 相同不等于传参相同；`frame64.s` 在 ARM64 上汇编、链接、实跑；`probe.c` 用帧指针链替代 `bt`；`lab1c03_reloc.c` 把符号、重定位、反汇编摆在一起。实验一（gdb）因 SVE 初始化失败只做了静态 `disassemble` 与探针；实验二（objdump/readelf）在 aarch64 机器上对 x86 目标拿到 `can't disassemble for architecture UNKNOWN!`，于是改用 `readelf` 加写作机的 LLVM objdump 补齐。最后十二条陷阱把「归谁保存、在哪个地址、工具的假设」各归一类。

逐条打勾的达标表在[学习目标自检表](ch03-checklist.md)。这里只留三条判据：

- **能解释**：`leaq 8(%rdi,%rsi,4)` 算的是什么、为什么不读内存；`cmpq` 之后 `jl` 与 `jb` 的分界；同一个 24 字节结构体为什么在两套 ABI 里一个压栈、一个传地址。
- **能操作**：`readelf -sW` 读函数边界、`readelf -rW` 读待填地址、`objdump -dr` 把重定位贴在指令下、`size` 比代码体积；反汇编器缺后端时换工具，而不是怀疑文件。
- **能判断**：`-O2` 下循环消失是编译器换了形状（x86 闭式 9 条、AArch64 保留循环 10 条、Rust 向量化），不是架构优劣；`gdb run` 失败是 SVE 的边界，不是程序有 bug；偏移差 8、参数位置不对，先怀疑自己漏算了返回地址或隐藏指针。

如果只记住一件事，那就是**汇编不背指令表，只回答两个问题：值现在在哪、下一步去哪**；ABI 就是这两问的公共答案。

::: method 即时自测 · 1.3
**Q1（算）** `leaq 8(%rdi,%rsi,4), %rax` 计算什么？若 `%rdi=1000`、`%rsi=3`，结果是多少？它会读内存吗？

**Q2（辨）** 一个有 8 个 `long` 参数的函数，第 8 个参数在 x86-64 与 AArch64 上分别在哪里？进入函数时 `%rsp` 指向什么？

**Q3（判）** 你在 `readelf -rW` 里看到一条 `R_X86_64_PLT32`，对应指令是 `e8 00 00 00 00`。这四个零是什么意思？`objdump -d` 拒绝反汇编时，下一步查什么？

**Q4（迁）** 同一段 `sum_to`，x86 的 clang 输出闭式乘法，AArch64 的 GCC 保留循环，Rust 走 SSE 向量化。你能据此说哪个更快吗？说出两条不能的理由。

::: sol 答案
**A1** `%rax = %rdi + 4*%rsi + 8 = 1000 + 12 + 8 = 1020`。`lea` 只算地址，不访问内存，也不改标志位。

**A2** x86-64：第 7、8 个都在栈上，分别在 `8(%rsp)`、`16(%rsp)`；AArch64：前 8 个都在 `x0`–`x7`，第 8 个在 `x7`。进入函数时 `%rsp` 指向 `call` 压入的返回地址。

**A3** 四个零是 `call rel32` 的位移占位，等链接器按 `PLT32` 填成「目标减下一条指令」。objdump 拒绝时先用 `readelf -h/-sW/-rW`、`size`、`nm` 验收格式与符号，再换带 x86 后端的工具或换机器看指令。

**A4** 不能。① 三格用了两个编译器（clang 与 GCC），形状差异有一半来自编译器；② 没有任何跨架构运行时间，指令条数不等于时间，流水线、缓存、分支预测都不在汇编文本里。
