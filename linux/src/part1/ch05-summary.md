## 一条主线

这一章从「感觉」走到「算得出来」：**先用 CPE 和延迟/吞吐定一个下界，再按「编译器敢做什么」改写循环，最后用 `perf` 和同一份基准验证瓶颈是否真的移走。** 每次动手前问四件事：这个循环的 CPE 下界是多少？当前实测离下界多远？差距是依赖链、缓存、分支还是别名造成的？改完之后用同一个基准再量一次，收益来自哪一层说得清吗？前三个答案齐了才动代码，一次只改一处、重测一次。

## 看到问题先选工具

| 症状 | 第一动作 | 为什么 |
|:--|:--|:--|
| 想知道「到底差多少」 | 测 CPE：多个 $n$ 拟合 $T(n)=c+kn$ | 斜率才是每元素成本，总时间会骗人。 |
| 想知道还能快几倍 | 用延迟/吞吐表算下界（1.5.6、1.5.10） | 离下界近就别再改指令，改结构。 |
| 想看编译器做了什么 | `cc -O2 -S`，再配 `-Rpass=loop-vectorize` | 源码里的 `inline` 不算数，汇编才算。 |
| 怀疑别名锁住了循环 | 加 `restrict` 前后各出一份汇编 | 距离检查与标量兜底会显式出现在汇编里。 |
| 不知道热点在哪个函数 | `perf record -g` + `perf report` | Amdahl 里的 $p$ 要用采样找。 |
| IPC 低、不知道卡哪 | `perf stat -d` 看 LLC 缺失与前后端停顿 | 后端停顿加高缺失是访存，前端是取指与代码体积。 |
| 没有 PMU 权限（容器/macOS） | `valgrind --tool=cachegrind` + `cg_annotate` | 软件模拟慢但确定，只做相对比较。 |
| 分支多且方向随机 | 数 `branch-misses`，再试排序或特化 | 预测失败一次是十几到二十周期。 |
| 计时忽快忽慢 | 绑核、定频、多次取最小值、先预热 | 调度与调频的噪声能盖过你要看的那点收益。 |

## 能否讲出这八句话

1. CPE 是每元素周期数，$T(n)=c+kn$；比实现要比斜率，比前先让 $n$ 够大、重复取最小值。
2. 延迟决定一条依赖链的速度，吞吐决定独立操作能并行多少；CPE 的下界取「链上延迟之和」与「吞吐倒数」中较大的那个。
3. 编译器在 `-O2` 下会做常量传播、外提、内联、向量化，但不敢改变可观察行为：别名、未定义行为、外部调用都会锁住它。
4. 展开只是减少循环控制开销，真正提速靠多累加器把一条长链拆成几条短链；浮点还要允许重排。
5. 一次 DRAM 访问比几百条 ALU 指令更贵，所以优先级是减少缓存缺失、再减少内存引用、最后才是指令数。
6. 分支本身不慢，预测失败才慢；无分支要付「两边都算」的代价，可能更慢。
7. `restrict` 是你替编译器作的承诺，违反是未定义行为；它能删掉运行时重叠检查，也让 load/store 不再互相等待。
8. 优化顺序不能颠倒：算法、局部性、重复计算、ILP、向量化、指令微调；每一步都要用 CPE 或 `perf` 量化，Amdahl 决定总上限。
