### 1.19.1.1 先数一遍你手里有哪些散件

你不是从零开始：CPU 有特权级、程序有 ELF 布局、地址翻译在 1.9 学过、`fork` 后父子共享打开文件、RISC-V 能从 M 态降到 S 态。散件都在，缺的是一根线把它们连起来。
本章反复用到八个词，先用一句白话捡回来，后文不再加注：

- **页表**（把虚拟地址切成三段、一级级查下去的那张表）回答「这个地址对应哪块物理内存」。
- **系统调用**（进程请内核办事的编号与入口）是用户态唯一能合法进内核的路。
- **中断**（硬件把 CPU 从手头指令上拽走的事件）让内核不必等程序主动让出 CPU。
- **inode**（索引节点，一个文件的身份证）存类型、大小和数据在哪些块。
- **文件描述符**（每个进程自己那张小表的下标）把 inode、管道、终端统一成一个整数。
- **缺页**（地址翻译失败时硬件触发的那次异常）给内核现场分配页的机会。
- **写时复制**（COW，`fork` 后父子先共用同一份物理页）只在真要写时才复制。
- **DMA**（外设绕过 CPU 直接读写内存）意味着「等 I/O 完成」等的是设备中断。

这一章只排序，不重讲概念。顺序借 rCore 最有价值的东西：先问「应用还缺什么」，再引入硬件机制——内核不是一次设计出来的，是被需求一步步逼出来的。下表右列是你已学过、本章只借用的。

### 1.19.1.2 八个阶段：一张能当地图读的表

每行只回答：这一阶段比上一阶段多解决了什么。从左往右是「需求 → 机制 → 抽象 → 类型」。阶段 1、2 合在 1.19.2，3、4 合在 1.19.3。

| 阶段 | 应用需求 | 新增硬件机制 | 新增内核抽象 | `myrcore` 的 Rust 类型 | 典型失败 |

| 8 IPC/并发 | 协作、共享 | IPI、原子指令 | pipe、signal、线程、锁 | `Arc<Semaphore>`、`Condvar` | 竞态、丢失唤醒 |

### 1.19.1.3 五个问题：每节都要回答的那五问

阶段表告诉你往哪走，五问告诉你每站检查什么：前两问决定要不要翻硬件手册，中间两问决定代码怎么写，最后一问决定你敢不敢说它对了。

1. **应用要什么**：它看到的接口是系统调用、文件、信号，还是「`0x1000` 就是我的地址」。这问答不出，内核会写成一组没人要的功能。
2. **硬件给什么**：特权级、CSR、页表、中断、原子指令，这一阶段用哪一件。硬件只给「不这么做就出事」的机制，不给抽象。
3. **内核存什么**：新结构体有哪些字段、谁分配、谁释放、什么时候改。
4. **Rust 怎么表达**：`&mut`、`Arc`、`Weak`、`Mutex`，还是只能 `unsafe`。所有权把「谁负责释放」变成类型。
5. **怎么验证**：反汇编看指令、断点看寄存器、主机程序看逻辑。**本章硬边界**：没有 RISC-V 硬件与 QEMU/GDB，rCore 只借机制事实、示例独立重写、不声称读过具体行号，所有运行输出标「未实测（无 RISC-V 硬件/QEMU）」。

::: def 定义 1.19.1 · 内核演进的阶段（stage） {#def-1.19.1}
阶段是「一组新抽象 + 让它成立所必需的那件新硬件机制」的最小配对。只加抽象、不加硬件机制的改动，是把上一阶段改好了，不是新阶段。
:::

## 1.19.2 阶段 1–2：从裸机到批处理 {#sec-1.19.2}

这一节回答：一段用户代码被放进内存跑起来之后，怎么保证它改不动内核、做完能正常退出？

::: preview 批处理只新增一件事：一条特权级边界
阶段 1 的裸机里所有代码都跑在 S 态，「应用」只是内核的一个函数，谁都能改谁的内存。阶段 2 把它变成一串外部字节：链接到 `0x8040_0000` 这样的固定地址，由内核复制到约定位置，`sret` 降到 U 态执行；应用想要任何服务，只能用 `ecall` 主动回 S 态。跑完一个再换下一个，这就是批处理。CSR、`stvec`、`TrapFrame` 在 1.18 已讲透，本节只用不重讲；「用户态陷入内核」这条路径的通用形态见 1.8 异常控制流。
:::

### 应用镜像放在哪

批处理内核把每个应用链接到固定地址，例如 app0 在 `0x8040_0000`、app1 在 `0x8060_0000`，彼此不重叠；内核自己在 `0x8020_0000`。应用 ELF 的入口就是它的第一条指令，内核只把 `.text/.data` 字节复制到目标地址，然后 `sret` 到入口——注意这里没有「调用」，只有「交接」。

<pre class="layout">
0x8020_0000  内核 .text/.rodata/.data/.bss
0x8040_0000  app0 的 .text/.rodata/.data/.bss
0x8060_0000  app1 的 .text/.rodata/.data/.bss
</pre>

应用链接脚本把 `BASE_ADDRESS` 设成 `0x8040_0000`，入口 `_start` 里只做一件事：把系统调用号放进 `a7`，参数放进 `a0`–`a5`，`ecall`。它不需要知道内核在哪，也不需要链接 `libc`。

### 加载器与第一次 `sret`

内核启动后，先把应用字节复制到 `APP_BASE`，再设置 `sepc` 和 `sstatus`：

| 步骤 | 代码 | 作用 |
|--:|:--|:--|
| 1 | `copy_nonoverlapping(src, APP_BASE, len)` | 把应用放到约定地址 |
| 2 | `csrw stvec, trap_entry` | 装好 U→S 的入口 |
| 3 | `csrw sscratch, sp` | 保存内核栈顶，trap 时交换 |
| 4 | `sstatus.SPP=0, SPIE=1, SIE=0` | 返回目标是 U，返回后开中断 |
| 5 | `csrw sepc, APP_BASE` | 返回地址 = 应用入口 |
| 6 | `sret` | 降级到 U，开始跑应用 |

这六步里最容易错的是第 3 步。`sret` 到 U 后，`sp` 还是内核栈；应用一压栈就踩内核数据。正确做法是给 U 态准备独立栈，`sret` 前把 `sp` 换过去，trap 入口再用 `sscratch` 换回内核栈——rCore 教程在批处理阶段同样按「每个应用一套内核栈加用户栈」来解决这件事，我们沿用机制、类型与命名独立设计。下面的示例**没有**铺用户栈，它能跑是因为应用只有两条指令、根本不碰栈；这是示例的边界，不是通用做法。

::: ex 例 1.19.2 · 两条指令的旅程
应用一共 8 个字节：`addi a7, zero, 2`（系统调用号 2 = exit）和一条 `ecall`。先猜：这条 `ecall` 在 U 态执行时 CPU 跳到哪里？handler 拿到的 `sepc` 指向 `ecall` 自己还是下一条？如果处理完不改 `sepc` 就 `sret`，会发生什么？

猜完再对：`ecall` 按 `stvec` 进 S 态，`sepc` 记录的是 `ecall` **自己**所在的地址；号 2 走退出分支、直接关机，回不回得去无所谓。换成 `write`（号 1）就不同：handler 必须 `tf.sepc += 4` 再 `sret`，否则应用原地重启这条 `ecall`，永远退不出——这就是阶段表里那个「`sepc` 未 +4」。
:::

### 完整程序：`myrcore` 批处理内核

这个程序把上面所有东西装进四个文件：`main.rs`、`entry.asm`、`trap.asm`、`linker.ld`。它把那段 8 字节应用加载到 `0x8040_0000`，在 U 态执行，`ecall` 回到 S 态后分发、打印并关机。在装了 `riscv64gc-unknown-none-elf` target 的机器上可以 `cargo build --release`；本套件没有构建、没有运行——未实测（无 RISC-V 硬件/QEMU）。

<div class="variant" data-arch="riscv64" data-lang="rust">

```rust
// src/main.rs：myrcore 批处理内核（阶段 2）
#![no_std]
#![no_main]

use core::arch::{asm, global_asm};
use core::fmt::{self, Write};
use core::panic::PanicInfo;

global_asm!(include_str!("entry.asm"));
global_asm!(include_str!("trap.asm"));

const APP_BASE: usize = 0x8040_0000;
const SBI_PUTCHAR: usize = 0x01;
const SBI_SRST: usize = 0x5352_5354;

// 应用机器码：addi a7, zero, 2; ecall
static APP: [u8; 8] = [
    0x93, 0x08, 0x20, 0x00, // addi a7, zero, 2
    0x73, 0x00, 0x00, 0x00, // ecall
];

extern "C" {
    fn __s_trap_entry();
}

#[inline(always)]
fn sbi_call(eid: usize, fid: usize, a0: usize, a1: usize) -> (isize, usize) {
    let (err, val): (isize, usize);
    unsafe {
        asm!("ecall", in("a7") eid, in("a6") fid,
             inlateout("a0") a0 => err, inlateout("a1") a1 => val,
             options(nostack));
    }
    (err, val)
}

struct Console;
impl Write for Console {
    fn write_str(&mut self, s: &str) -> fmt::Result {
        for b in s.bytes() { let _ = sbi_call(SBI_PUTCHAR, 0, b as usize, 0); }
        Ok(())
    }
}
pub fn print_fmt(args: fmt::Arguments) {
    let mut c = Console;
    c.write_fmt(args).unwrap();
}
#[macro_export]
macro_rules! print {
    ($($arg:tt)*) => { $crate::print_fmt(format_args!($($arg)*)) };
}
#[macro_export]
macro_rules! println {
    () => { $crate::print!("\n") };
    ($($arg:tt)*) => { $crate::print!("{}\n", format_args!($($arg)*)) };
}

fn shutdown(failure: bool) -> ! {
    let _ = sbi_call(SBI_SRST, 0, 0, failure as usize);
    loop { core::hint::spin_loop(); }
}

#[repr(C)]
pub struct TrapFrame { pub x: [usize; 32], pub sepc: usize, pub sstatus: usize }

#[no_mangle]
pub extern "C" fn rust_main() -> ! {
    println!("batch: load app at {:#x}", APP_BASE);
    unsafe {
        // 1) 复制应用
        core::ptr::copy_nonoverlapping(APP.as_ptr(), APP_BASE as *mut u8, APP.len());
        // 2) 装 trap 入口
        asm!("csrw stvec, {}", in(reg) __s_trap_entry as usize);
        // 3) 保存内核栈顶，trap 时与用户 sp 交换
        asm!("csrw sscratch, sp");
        // 4) sstatus: SPP=U, SPIE=1, SIE=0
        let mut ss: usize;
        asm!("csrr {}, sstatus", out(reg) ss);
        ss &= !(1 << 1);
        ss = (ss & !(1 << 8)) | (1 << 5);
        asm!("csrw sstatus, {}", in(reg) ss);
        // 5) 返回地址 = 应用入口
        asm!("csrw sepc, {}", in(reg) APP_BASE);
        // 6) 降级到 U
        asm!("sret", options(noreturn));
    }
}

#[no_mangle]
pub extern "C" fn s_trap_handler(tf: &mut TrapFrame) {
    let scause: usize;
    unsafe { asm!("csrr {}, scause", out(reg) scause) };
    if scause == 8 {
        match tf.x[17] { // a7
            1 => { let _ = sbi_call(SBI_PUTCHAR, 0, tf.x[10], 0); }
            2 => { println!("batch: app exit"); shutdown(false); }
            _ => println!("batch: unknown syscall {}", tf.x[17]),
        }
        tf.sepc += 4;
    } else {
        println!("batch: trap {:#x} at {:#x}", scause, tf.sepc);
        shutdown(true);
    }
}

#[panic_handler]
fn panic(_: &PanicInfo) -> ! { shutdown(true) }
```

这里有一个关键设计：**应用是字节数组，不是链接进来的函数**。一旦它成为「外部镜像」，内核就不能用函数调用去调它，只能用 `sret` 把 CPU 交给它。这是用户态和内核态的分界线，也是后面所有隔离的前提。

### 同一阶段的 C 视角

C 内核通常把应用编译成独立 ELF，再用 `objcopy -O binary` 转成 `.bin` 嵌进内核镜像；加载器做的事和 Rust 版一字不差。差别只在所有权：C 版本没有 `Drop`，栈、页表、fd 表都要显式释放；Rust 版可以把「释放页表」写进 `Drop`，但内核里通常仍然显式 `free`，因为 `Drop` 可能在中断上下文里触发分配器，语义不清晰。本书没有给出可编译的 C 版批处理内核，需要时按 Rust 结构自己重写。

::: errata 阶段 1–2 的四个坑
1. **`sepc` 没 +4**：`sret` 后重新执行那条 `ecall`，应用永远退不出。
2. **U 态没有独立栈**：`sret` 后 `sp` 仍是内核栈，应用一压栈就改内核数据。
3. **`sscratch` 没设**：第一次 trap 时 `csrrw sp, sscratch, sp` 把 `sp` 换成 0，随后 load fault。
4. **应用镜像超过预留区间**：`0x8040_0000` 开始的应用覆盖下一个应用或内核数据；链接脚本必须限制大小。
:::

### 1.19.2 小结

批处理内核就是「六步加载器 + 一个按 `a7` 分发的 trap handler」：应用是字节不是函数，交接靠 `sret`，回来靠 `ecall`，回得去的前提是 `sepc += 4` 和一条真正的用户栈。如果只记住一件事：阶段 2 新增的不是功能，是一条特权级边界——之后任务、地址空间、进程都是在这条线上加东西。

## 1.19.3 阶段 3–4：多任务与抢占 {#sec-1.19.3}

这一节回答：内核怎么让两个任务轮流跑？为什么一次切换只需保存 14 个 `usize` 而不是全部寄存器？时钟中断又是怎样把「愿意让」变成「必须让」的？

::: preview 协作与抢占只差一个中断源
阶段 3 给每个任务一条自己的内核栈和一份 `TaskContext`，任务靠 `yield` 主动交出 CPU；阶段 4 只加一件事——时钟中断，让交不交 CPU 不再取决于自觉。两阶段共用同一台切换机器：`__switch` 换栈、换 callee-saved。调度算法（FCFS、RR、时间片取多大）在 1.13 讲过，本节只讲它怎么在 RISC-V 上落地；caller/callee-saved 的划分来自 1.15 的调用约定，trap 现场来自 1.18.7，都不重讲。
:::

### 任务切换只保存 callee-saved

RISC-V 的调用约定把寄存器分成 caller-saved（`ra`、`t0`–`t6`、`a0`–`a7`）与 callee-saved（`sp`、`s0`–`s11`）。任务切换发生在内核里，编译器已经按 ABI 把 caller-saved 保存在当前任务的内核栈上；`__switch` 只需要保存「换栈之后仍然要恢复」的那部分：

| 字段 | 偏移（RV64） | 为什么保存 |
|:--|--:|:--|
| `ra` | 0 | 返回地址，决定 `__switch` 返回到哪 |
| `sp` | 8 | 内核栈指针，换任务就是换栈 |
| `s0`–`s11` | 16–104 | callee-saved，被调用者必须保持 |

`TaskContext` 是 `#[repr(C)]` 的 14 个 `usize`，`__switch(prev, next)` 把当前寄存器存进 `prev`，再从 `next` 恢复。切换完成后，`ret` 会返回到 `next` 上次调用 `__switch` 的下一条指令——看起来像「从没切换过」，但已经在另一个任务的内核栈上。

### Rust 的任务控制块与调度器

<div class="variant" data-arch="riscv64" data-lang="rust">

```rust
use core::sync::atomic::{AtomicUsize, Ordering};
use alloc::sync::Arc;
use spin::Mutex;

#[repr(C)]
#[derive(Clone, Copy, Default)]
pub struct TaskContext {
    pub ra: usize,
    pub sp: usize,
    pub s: [usize; 12], // s0..s11
}

pub enum TaskState { Ready, Running, Zombie }

pub struct Task {
    pub pid: usize,
    pub state: TaskState,
    pub ctx: TaskContext,
    pub kstack: usize,
    pub trap_cx: usize, // 用户 trap frame 的内核地址
}

pub struct Scheduler {
    pub current: Option<Arc<Mutex<Task>>>,
    pub ready: alloc::collections::VecDeque<Arc<Mutex<Task>>>,
    pub next_pid: AtomicUsize,
}

impl Scheduler {
    pub fn push(&mut self, task: Arc<Mutex<Task>>) {
        self.ready.push_back(task);
    }

    /// 取出下一个任务；调用者负责在合适的时候 __switch
    pub fn pick(&mut self) -> Option<Arc<Mutex<Task>>> {
        self.ready.pop_front()
    }
}
```

</div>

这里出现本章第一个「Rust 逼你面对所有权」的地方：`current` 和 `ready` 都持有 `Arc<Mutex<Task>>`，而任务自己可能又持有「父任务」或「等待队列」的引用。如果全用 `Arc`，会形成循环引用，任务永远不会释放；正确做法是**所有权方向用 `Arc`，反向引用用 `Weak`**。Linux 用 `task_struct` 的 `parent` 裸指针 + `children` 链表，靠锁和引用计数手工维护；Rust 把这件事变成类型系统的一部分。

调度器的核心循环只有三行：`pick` 一个任务、`__switch` 过去、任务返回后把它放回队列。真正难的是「什么时候切换」：协作式靠 `yield` 系统调用，抢占式靠时钟中断。谁先被 `pick`、片切多长，是 1.13 的算法问题；这里实现的是机制。

### 时钟中断把「让出」变成「抢占」

1.18.8 已经搭好 `stvec`、`sie.STIE`、`sstatus.SIE` 和 SBI `set_timer`，这条硬件链路不再重讲；现在只回答「tick 到了，内核该干什么」。答案是三件事，一件都不多：

| 动作 | 代码 | 注意 |
|:--|:--|:--|
| 重新装定时器 | `set_next_timer()` | 不装就只有一次 tick |
| 增加 tick 计数 | `TICKS.fetch_add(1, Relaxed)` | 用原子，避免多 hart 竞争 |
| 标记需要调度 | `need_resched.store(true, Relaxed)` | 真正切换在 trap 返回前 |

定时器 trap 和 `ecall` 走同一个入口，区别只在 `scause`：中断的 bit63=1、编号 5（S 态定时器），`ecall` 是 `scause=8`。所以调度代码不用分两套——trap 返回前查同一个 `need_resched` 标记。不要在 handler 里直接 `__switch`：trap frame 还压在当前任务的内核栈上，现场没落完就换栈，等于把半截中断现场扔进别的任务的栈。Linux 的 `preempt_schedule_irq` 也是「先标记、返回前再切」的同款思路。

::: ex 例 1.19.3 · 一次切换里 `ret` 回哪
任务 A 在 `__switch(&mut a.ctx, &b.ctx)` 里：`sd ra,0(a0)` 存的是「A 调用 `__switch` 的下一条指令」，`sd sp,8(a0)` 存 A 的内核栈。先猜：最后那条 `ret` 用的是谁的 `ra`？A 下一轮被切回来时，从哪儿「醒来」？

猜完再对：`ret` 用的 `ra` 刚被 `ld ra,0(a1)` 换成了 B 上次调用 `__switch` 的返回地址，所以这次「返回」落进 B 的代码；A 要等下轮 `__switch` 装回它的 `ra/sp`，才从自己栈上的返回点继续。两个任务各自「以为」自己刚从中断或 `yield` 回来，被切走的时间正是它们中间的空白。这也是为什么 `__switch` 之后的代码不能想当然认为还在原来那个任务里。
:::

::: errata 关于「只保存 14 个寄存器」的三个误读
1. **「少存了就是 bug」**——`a0`–`a7`、`t0`–`t6` 是 caller-saved：编译器早把它们放进各自的内核栈帧，换栈等于换好了它们（1.15）。
2. **「用户寄存器也不用存」**——`__switch` 只管内核侧现场；用户侧 32 个 `x` 每次 trap 都由 `TrapFrame` 全量落盘（1.18.7），两套现场别混。
3. **「切换=换地址空间」**——阶段 3、4 的任务还共用同一份内存，`satp` 到阶段 5 才登场；现在换的只是栈与 callee-saved。
:::

### 1.19.3 小结

多任务是「每任务一条内核栈 + 一份 `TaskContext`」，抢占是给同一台切换机器接上时钟中断、让 trap 代替自觉。`__switch` 的 `ret` 落在别的任务里，是本节最反直觉的一步；tick handler 只置 `need_resched`、不在中断里直接切换，是最不能省的一步。如果只记住一件事：调度算法是 1.13 的问题，换栈换现场是本节的问题，别混成一个。本节没有给出任何运行输出：切换现场要靠 GDB 断点看 `sp` 与 `ra`，本机无 RISC-V 硬件与 QEMU，未实测。

## 1.19.4 阶段 5：地址空间与 Sv39 {#sec-1.19.4}

这一节回答：MMU 怎么给每个应用一份「假装的独占内存」？页表这棵由物理页组成的树，在内核里谁拥有、谁释放？

::: preview 地址空间 = 一棵页表树 + 一份内核账本
Sv39 就是 1.9 那套层级页表换成 RISC-V 的位段与 CSR 名字：39 位 VA 按 9+9+9+12 拆开，`satp` 装根页表页号，PTE 带 `V/R/W/X/U/G/A/D` 八个标志。硬件只走页表；内核还要留一份 `MapArea` 账本，才知道「这段地址本来该有什么权限、该不该存在」。本节先手算一次翻译，再看 Rust 侧的所有权分层。页表原理、TLB、内部碎片都在 1.9，不重讲。
:::

### Sv39 的地址拆分

Sv39 使用 39 位虚拟地址：低 12 位页内偏移，往上每 9 位一级，共三级（level 2/1/0）。`satp` 的 `MODE=8` 表示 Sv39，`PPN` 指向根页表（level 2）的物理页号。

| 位 | 字段 | 用途 |
|:--|:--|:--|
| `63:60` | `MODE` | 8=Sv39，0=Bare，9=Sv48，10=Sv57 |
| `59:44` | `ASID` | 地址空间标识，减少 TLB 刷新 |
| `43:0` | `PPN` | 根页表物理页号（PA >> 12） |

| VA 位 | 级别 | 页表索引 | 页大小 |
|:--|:--|:--|--:|
| `38:30` | level 2 | `VPN[2]` | 1 GiB |
| `29:21` | level 1 | `VPN[1]` | 2 MiB |
| `20:12` | level 0 | `VPN[0]` | 4 KiB |
| `11:0` | — | 页内偏移 | — |

PTE 的低 10 位是权限，高 44 位是物理页号：

| 位 | 名称 | 含义 |
|--:|:--|:--|
| 0 | `V` | 有效 |
| 1 | `R` | 可读 |
| 2 | `W` | 可写 |
| 3 | `X` | 可执行 |
| 4 | `U` | 用户可访问 |
| 5 | `G` | 全局映射 |
| 6 | `A` | 已访问（硬件可能不自动置位） |
| 7 | `D` | 已脏 |
| `53:10` | `PPN` | 物理页号 |

一个合法的叶子 PTE 必须满足：`V=1`，且 `R=1` 或 `X=1`（`W=1` 而 `R=0` 的组合保留）。非叶子 PTE 的 `R/W/X` 必须全 0；哪一位是 1，它就不是指向下一级页表，而是大页叶子。遍历从 `satp` 的根页开始，按 VPN 逐级取 PTE，停在叶子上——这套判定是整节代码的核心，写错就是「把页表项当大页」或「把大页当页表」。

::: def 定义 1.19.4 · 地址空间（Sv39 版） {#def-1.19.4}
一个地址空间 = 一张三级页表（根页的物理页号写进 `satp`）+ 内核记账用的 `MapArea` 列表。硬件只认页表：每次取指或访存按 `VPN[2]/VPN[1]/VPN[0]` 逐级走，命中叶子 PTE 就拼出 PA；`MapArea` 让内核自己记得哪段地址该有什么权限。这本账在 fork/exec 时怎么改，见 1.19.5 与 1.8，不在本节展开。
:::

::: ex 例 1.19.4 · 手算 VA 0x4012_3456
先猜三个数：`VPN[2]`、`VPN[1]`、`VPN[0]` 各是多少？若 level 1 的 PTE 是叶子（2 MiB 大页），`VPN[0]` 还用得上吗？

按 9+9+9+12 拆：`VPN[2] = (va >> 30) & 0x1ff = 16`；`VPN[1] = (va >> 21) & 0x1ff = 0`；`VPN[0] = (va >> 12) & 0x1ff = 0x123`；页内偏移 `va & 0xfff = 0x456`。若遍历在 level 1 停下，`VPN[0]` 这 9 位就不再是索引，要和偏移拼成 21 位的大页内偏移——这正是下面 `sv39.rs` 里 `mask = (1 << (12 + 9*level)) - 1` 的来历。
:::


### Rust 的页表类型：谁拥有物理页

页表不是一个「数组」，而是一棵由物理页组成的树。Rust 里可以用 `Vec<PageTableEntry>` 或裸指针 + 分配器；关键问题是**谁负责释放子页表**。`myrcore` 的做法是：

<div class="variant" data-arch="riscv64" data-lang="rust">

```rust
use core::ptr::NonNull;

pub struct PageTable {
    root: NonNull<PageTableEntry>, // 指向 512 项的根页
    frames: alloc::vec::Vec<NonNull<PageTableEntry>>, // 拥有所有子页
}

impl Drop for PageTable {
    fn drop(&mut self) {
        // 先释放子页，再释放根页；顺序反了会 use-after-free
        for frame in self.frames.drain(..) {
            unsafe { frame.drop_in_place() };
        }
    }
}

#[repr(C)]
#[derive(Clone, Copy)]
pub struct PageTableEntry(pub usize);

impl PageTableEntry {
    pub fn is_valid(&self) -> bool { self.0 & 1 != 0 }
    pub fn is_leaf(&self) -> bool { self.0 & 0b1110 != 0 }
    pub fn ppn(&self) -> usize { (self.0 >> 10) & ((1 << 44) - 1) }
}
```

</div>

`Drop` 里必须小心：页表项可能指向「共享页」（例如 COW 的物理页），不能见到 PTE 就释放。`frames` 只拥有**页表页**，不拥有映射的数据页；数据页由 `FrameAllocator` 或 `Arc<Frame>` 管理。这是 Rust 类型系统帮不上忙的地方——它不知道 PTE 的语义，只能靠你写对。

### 完整程序：一个可在主机上跑的 Sv39 遍历器

下面这个程序不依赖 QEMU，用 `Vec<[u64;512]>` 模拟物理页，构造三级页表，映射一个 4 KiB 页和一个 2 MiB 大页，然后翻译地址，把每一级的索引和 PTE 打出来。页表是数组模拟的，所以它在主机 `rustc` 上就能直接跑——下面这份输出是复跑得到的真产物（写作机 macOS arm64、`rustc 1.99.1`），不是纸面推演。

<div class="variant" data-arch="all" data-lang="rust">

```rust
// sv39.rs：主机上的 Sv39 页表构造/遍历器
const PTE_V: u64 = 1 << 0;
const PTE_R: u64 = 1 << 1;
const PTE_W: u64 = 1 << 2;
const PTE_X: u64 = 1 << 3;
const PTE_U: u64 = 1 << 4;

struct Sv39 {
    frames: Vec<[u64; 512]>, // 每个元素是一个 4 KiB 页表页
    root: usize,
}

impl Sv39 {
    fn new() -> Self {
        let mut frames = Vec::new();
        frames.push([0u64; 512]);
        Self { frames, root: 0 }
    }

    fn alloc(&mut self) -> usize {
        self.frames.push([0u64; 512]);
        self.frames.len() - 1
    }

    fn index(va: usize, level: usize) -> usize {
        (va >> (12 + 9 * level)) & 0x1ff
    }

    /// 确保 va 在 level 上有一个子页表，返回子页在 frames 中的下标
    fn ensure(&mut self, va: usize, level: usize) -> usize {
        let mut frame = self.root;
        for l in (level + 1..=2).rev() {
            let i = Self::index(va, l);
            let pte = self.frames[frame][i];
            if pte & PTE_V == 0 {
                let child = self.alloc();
                self.frames[frame][i] = ((child as u64) << 10) | PTE_V;
                frame = child;
            } else {
                frame = (pte >> 10) as usize;
            }
        }
        frame
    }

    /// 映射 4 KiB 页（level 0）
    fn map4k(&mut self, va: usize, pa: usize, flags: u64) {
        let frame = self.ensure(va, 0);
        let i = Self::index(va, 0);
        self.frames[frame][i] = ((pa as u64 >> 12) << 10) | flags | PTE_V;
    }

    /// 映射 2 MiB 大页（level 1）
    fn map2m(&mut self, va: usize, pa: usize, flags: u64) {
        let frame = self.ensure(va, 1);
        let i = Self::index(va, 1);
        self.frames[frame][i] = ((pa as u64 >> 12) << 10) | flags | PTE_V;
    }

    /// 返回 (物理地址, 命中的 PTE, 页大小)
    fn translate(&self, va: usize) -> Option<(usize, u64, usize)> {
        let mut frame = self.root;
        for level in (0..=2).rev() {
            let i = Self::index(va, level);
            let pte = self.frames[frame][i];
            if pte & PTE_V == 0 {
                return None;
            }
            if pte & (PTE_R | PTE_W | PTE_X) != 0 {
                // 叶子：大页要保留低位的偏移
                let mask = (1usize << (12 + 9 * level)) - 1;
                let pa = (((pte >> 10) as usize) << 12) | (va & mask);
                return Some((pa, pte, 1 << (12 + 9 * level)));
            }
            frame = (pte >> 10) as usize;
        }
        None
    }
}

fn main() {
    let mut pt = Sv39::new();
    // 4 KiB 页：VA 0x1000 -> PA 0x8000_1000，可读写
    pt.map4k(0x1000, 0x8000_1000, PTE_R | PTE_W);
    // 2 MiB 大页：VA 0x4000_0000 -> PA 0x8000_0000，可读写执行
    pt.map2m(0x4000_0000, 0x8000_0000, PTE_R | PTE_W | PTE_X);

    for va in [0x1000usize, 0x1abc, 0x4000_0000, 0x4012_3456, 0x5000] {
        match pt.translate(va) {
            Some((pa, pte, size)) => println!(
                "VA {:#010x} -> PA {:#010x}  PTE {:#x}  page {} KiB",
                va, pa, pte, size / 1024
            ),
            None => println!("VA {:#010x} -> unmapped", va),
        }
    }
    println!("root frame = {}, frames = {}", pt.root, pt.frames.len());
}
```

怎么算命中：`0x1abc` 与 `0x1000` 应落在同一 PTE、只差偏移，说明一个 4 KiB 映射覆盖整页；`0x4012_3456` 应报 `2048 KiB`，说明遍历在 level 1 就停；`0x5000` 应是 unmapped 而不是 panic，说明无效 PTE 走「未映射」分支。注意大页那行保留了 21 位偏移（`0x12_3456`）：把 `mask` 写成固定的 `0xfff`，大页翻译会丢掉高位偏移，这是页表代码最常见的 bug。最后一行 `frames = 4` 也值得停一秒：两份映射用掉 4 个页表页——根页表，加上第一个 VA 沿 level 2、level 1 各新建的一页，再加上第二个 VA 在 level 2 上落到不同条目后新建的一页；level 0 没建，因为它是大页。这就是「地址散得越开、页表本身越吃内存」的最小证据，也是内核要为常用区间复用高位条目的理由。

### 内核里的地址空间：`MapArea` 与 `MemorySet`

rCore 用 `MapArea` 表示「一段连续的虚拟地址 + 权限 + 映射类型」，`MemorySet` 是 `Vec<MapArea>` 加根页表。`myrcore` 用同样的分层，但字段命名独立：

| 结构 | 字段 | 谁改 | 什么时候 |
|:--|:--|:--|:--|
| `MapArea` | `vpn_range`、`perm`、`map_type` | 创建时 | `from_elf`、`mmap` |
| `MemorySet` | `areas`、`page_table` | `push`/`remove` | fork、exec、mmap |
| `PageTable` | `root`、`frames` | `map`/`unmap` | 页表操作 |
| `FrameAllocator` | 空闲物理页 | 分配/释放 | 缺页、fork、栈增长 |

Rust 的所有权在这里体现为「`MemorySet` 拥有 `PageTable`，`PageTable` 拥有页表页，数据页由 `Arc<Frame>` 共享」。fork 时复制 `MemorySet`，把数据页标成 COW；写缺页时再分配新页并复制。`Arc` 的引用计数让「最后一个持有者释放物理页」变得可证明，但 COW 的 PTE 权限修改仍然要 `unsafe`——类型系统到这里就帮不上你了。

### 1.19.4 小结

Sv39 把 39 位 VA 切成 9+9+9+12，`satp`（`MODE=8` 加 44 位 PPN）把根页表交给硬件，遍历停在 `V=1` 且 `R/W/X` 任一为 1 的 PTE 上——大页与小页只差「在哪一级停、留几位偏移」。内核侧的所有权一条线：`MemorySet` 拥有 `MapArea` 与 `PageTable`，`PageTable` 只拥有页表页，数据页归 `FrameAllocator` 或 `Arc<Frame>`。如果只记住一件事：偏移掩码跟着 level 走，写死的 `0xfff` 是大页翻译的头号 bug。

## 1.19.5 阶段 6：进程、fork/exec/wait {#sec-1.19.5}

这一节回答：一个程序怎么变成能创建别的程序、能等它结束、能被人收尸的进程？fork、exec、wait 各自动了内核里的哪张表？

::: preview 进程 = 地址空间 + 现场 + fd 表 + 一条父子边
阶段 5 给了每个应用自己的内存，还没说它归谁、死后谁收。PCB 把 `MemorySet`、内核栈、`TrapFrame`、fd 表和父子关系绑成一个对象：fork 复制它，exec 换掉地址空间却保住 pid 与 fd，wait 收走退出码再销毁它。三个调用难的都是所有权。用户侧语义见 [1.8](ch08.md)，fd 那三层表见 [1.10](ch10.md)。
:::

### PCB：把五个已有对象绑成一个

| 字段 | 类型 | 作用 | 什么时候改 |
|:--|:--|:--|:--|
| `pid` | `usize` | 进程标识 | 创建时分配，回收时释放 |
| `state` | `Ready/Running/Blocked/Zombie` | 调度状态 | 调度与 wait |
| `trap_cx` | `TrapFrame` | 用户侧 32 个寄存器现场 | 每次 trap 覆盖 |
| `kstack` | `usize` | 内核栈顶，trap 入口与它换 `sp` | 创建时分配 |
| `memory_set` | `MemorySet` | 地址空间 | fork 复制、exec 替换 |
| `fd_table` | `Vec<Option<Arc<dyn File>>>` | 打开的文件 | open/close/fork |
| `parent` | `Weak<Mutex<Process>>` | 父进程 | 创建时设置 |
| `children` | `Vec<Arc<Mutex<Process>>>` | 子进程 | fork 增、wait 删 |
| `exit_code` | `i32` | 退出码 | `exit` 写、`wait` 读 |

表里两个 Rust 决定值得停一下：`parent` 用 `Weak`，`children` 用 `Arc`。父进程可以先退出而子进程照跑——Linux 把它过继给 init 或最近的 subreaper，父进程的对象不能被一条反向引用按住。两边都用 `Arc` 就是循环计数，谁也到不了 0，PCB 永不释放。Linux 靠裸指针加 `tasklist_lock`/RCU 维持方向；Rust 把它写进类型，代价是读每个字段都要 `lock()`——持锁去调一个会阻塞的函数就是自造死锁。

### fork：复制表，共享打开的文件

`fork` 的用户语义只有一句（1.8）：父子从同一条指令之后继续，父拿到子 pid、子拿到 0。内核侧是七步，每步都可能失败：

| 步 | 做什么 | 失败怎么回滚 |
|--:|:--|:--|
| 1 | 分配 pid、PCB、内核栈 | 归还 pid 与已分配物理页 |
| 2 | 复制 `MemorySet`，父子两侧的页都标成只读 COW | 释放已建的子页表 |
| 3 | 复制 `TrapFrame`，`sepc` 指向 `ecall` 的下一条 | 同上 |
| 4 | 克隆 fd 表：`Vec` 复制，元素走 `Arc::clone` | 关掉已复制的 fd |
| 5 | 把子进程挂进父的 `children` | 解除这条父子边 |
| 6 | 子的 `a0=0`，父的 `a0=pid` | — |
| 7 | 两者各自从 trap 返回用户态 | — |

分水岭在第 4 步：**表是复制的，打开的文件是共享的**。父子拿到同一个 fd 数字，`Arc<dyn File>` 却指向同一个打开文件对象，偏移只有一份：子进程读走 10 字节，父进程下一次 `read` 就从新位置继续。POSIX 要求这样，Linux 靠 `struct file` 的引用计数做到（[1.10](ch10.md) 的 fd 表 → 打开文件 → inode）。COW 本身见 1.19.4。

::: ex 例 1.19.5 · 谁读到下一行
文件里是 `abc\ndef\n`，程序 `open` 后 `fork`，父子各调一次 `read(fd, buf, 4)`。先猜：两边都读到 `abc`，还是一人一行？如果 `fork` 前父进程已经读过 1 字节，答案变不变？

一人一行：偏移只有一份，`abc\n` 归先跑到的那个。`fork` 前读过 1 字节就整体后移，第一个 `a` 谁也读不到。想让两边从头读，`lseek` 会把对方一起拨回去，只能让子进程再 `open` 一次。
:::

### exec：先建新地址空间，再换旧的

`exec` 不创建进程：它把当前 PCB 的 `memory_set` 换成新 ELF 的地址空间、`trap_cx` 重置到新入口、`a0` 归零，然后回用户态；pid、fd 表、当前目录、信号掩码全部保留（1.8）——shell 就靠这条不变式把标准输入接给新程序。要命的是失败：`execve` 返回 -1 时进程必须和调用前一模一样，所以只能「先读 ELF → 建全新页表 → 全部成功才替换」。

<div class="variant" data-arch="riscv64" data-lang="rust">

```rust
pub fn sys_fork(parent: &Arc<Mutex<Process>>) -> Result<usize, SysError> {
    let mut parent = parent.lock();
    let child = Process::new_child(&parent)?;      // 分配 PCB/pid
    let child = Arc::new(Mutex::new(child));

    // 复制地址空间；失败时 child 的 Drop 会释放已分配页
    child.lock().memory_set = parent.memory_set.fork()?;
    // 复制 fd 表：Arc 克隆，共享 file offset
    child.lock().fd_table = parent.fd_table.clone();
    // 子进程从 fork 返回 0
    child.lock().trap_cx.x[10] = 0;
    // 父进程返回子 pid
    parent.trap_cx.x[10] = child.lock().pid;
    parent.children.push(child.clone());

    Ok(child.lock().pid)
}

pub fn sys_exec(proc: &Arc<Mutex<Process>>, path: &str) -> Result<(), SysError> {
    let elf = load_elf(path)?;                     // 先在用户内存里解析
    let mut new_set = MemorySet::from_elf(&elf)?;  // 新页表，失败不影响旧地址空间
    let entry = elf.entry;
    let mut p = proc.lock();
    p.memory_set = new_set;                        // 原子替换；旧 MemorySet 在这里 Drop
    p.trap_cx.sepc = entry;
    p.trap_cx.sstatus = (p.trap_cx.sstatus & !(1 << 8)) | (1 << 5);
    Ok(())
}
```

</div>

`p.memory_set = new_set;` 这一行是 Rust 的高光时刻：旧 `MemorySet` 在赋值瞬间 `Drop`，页表页按顺序还给分配器，不给「新页表已生效、旧页表还挂在某处」留窗口；C 版要手写 `free_page_table(old)`，这类窗口正是历史漏洞的温床（`Drop` 的边界见 1.17）。另一处易漏的是 `load_elf(path)`：路径与 ELF 段都在用户地址空间，取值要先走 1.19.4 的翻译，段布局见 1.7、按需加载见 1.9，失败给 `EFAULT`。

### wait 与 exit：zombie 是笔没销的账

`exit(code)` 不销毁进程：它置 Zombie、写 `exit_code`、唤醒睡在 `wait` 上的父进程，然后把自己摘出运行队列；地址空间在这一步释放，PCB 和 pid 却留着。孩子还挂在父的 `children` 里，只剩一个号和一个退出码——这就是 zombie。Linux 一模一样：`ps` 里的 `<defunct>` 不是一个进程，是一笔没销的账（1.8）。

`wait4` 做三件事：在 `children` 里按 pid 挑一个（`-1` 是任意一个）；它还没死就把当前进程挂进等待队列并调度走；它已是 zombie 就取走退出码、把它摘掉，PCB 这时归零、pid 这时归还。`children` 是空的就返回 `ECHILD`。三个细节不能省：睡前的检查必须在持锁期间完成，否则「检查—孩子退出—我去睡」会把唤醒丢在锁外，父进程永远睡下去（1.12）；醒来要用 `while` 重查，因为叫醒你的可能是另一个孩子（虚假唤醒）；`wait` 自己也会被信号打断而返回 `-EINTR`（1.8）。时间片怎么分是 1.13 的事，本节只管账本上少了哪一行。

::: errata 阶段 6 的五个坑
1. **`satp` 改了但没 `sfence.vma`**：旧 TLB 项仍有效，用户访问到已撤销的映射。
2. **`fork` 复制页表却没标 COW**：父子写同一物理页。
3. **`exec` 先释放旧地址空间再解析新 ELF**：解析失败时进程没有地址空间，只能被杀。
4. **`parent` 用 `Arc`**：父子循环引用，进程永不释放；反向引用要 `Weak`。
5. **`wait` 在锁外检查条件**：检查到睡眠之间孩子退出，唤醒丢失，父进程永久睡眠。
:::

### 1.19.5 小结

进程不是「在跑的程序」，而是内核账本上一个有地址空间、有现场、有 fd 表、有父亲的对象：fork 复制账本却共享打开的文件，exec 换掉地址空间但保住 pid 与 fd，exit 留下 zombie 这笔账，wait 才把它销掉。只记一件事：三个调用改的都是所有权方向，`children` 用 `Arc`、`parent` 用 `Weak`。

## 1.19.6 阶段 7：文件系统——从块设备到路径 {#sec-1.19.6}

这一节回答：设备只认「第几块、512 字节」，程序却说要读 `hello.txt` 的第 3 到第 13 个字节——这中间的翻译由哪几张表完成？为什么目录也是一种文件？

::: preview 先抓住一件事
四张表接力：**超级块**告诉你这张盘的规则（魔数、inode 数、数据区从哪开始）；**inode**（索引节点，存一个文件的所有元数据：类型、大小、数据块号）回答「这个文件的内容在哪些块」；**目录项**回答「这个名字对应哪个 inode」；**fd 表**回答「这个进程打开过哪些文件」。加上块缓存，就凑成一个能开、能读、能列目录的最小文件系统。本节的判据很硬：把 `Vec<u8>` 当成盘，用真字节读写一遍，能列出来、读回来，布局就说清楚了。
:::

**应用需求**：程序能按名字打开文件、读写字、列目录，重启后数据还在。**硬件机制**：块设备（virtio-blk / SD / NVMe）。**内核抽象**：超级块、inode、目录项、文件描述符、块缓存。

### 一个最小 FS 的磁盘布局

`myfs` 把磁盘按 512 字节分块，前几块是元数据：

| 块号 | 内容 | 关键字段 |
|--:|:--|:--|
| 0 | 超级块 | `magic`、`inode_count`、`data_start` |
| 1 | inode 位图 | 每个 bit 表示一个 inode 是否已用 |
| 2 | 数据位图 | 每个 bit 表示一个数据块是否已用 |
| 3 … | inode 区 | 每个 inode 32 字节：`mode`、`size`、`direct[4]` |
| `data_start` … | 数据区 | 文件内容、目录项数组 |

inode 的 `direct[4]` 是四个直接块号，够教学用；生产 FS 会用多级间接块、extent、B+ 树。目录也是一种文件：它的数据区是一组 `DirEntry { inode, name }`，按名字线性查找。

| 对象 | 关键操作 | Rust 类型 | Linux 对应 |
|:--|:--|:--|:--|
| 块设备 | `read_block`/`write_block` | `trait BlockDevice` | `block_device_operations` |
| 块缓存 | 读入、标记脏、回写 | `Arc<Mutex<BlockCache>>` | `address_space`/page cache |
| inode | `read_at`/`write_at`/`find` | `Arc<Inode>` | `struct inode` |
| 目录项 | 名字 → inode | `DirEntry` | `struct dentry` |
| fd 表 | fd → 打开文件 | `Vec<Option<Arc<dyn File>>>` | `files_struct` |

### `File` trait：一切皆文件

rCore 用 `File` trait 把普通文件、标准输入输出、管道统一成 `read/write`。`myrcore` 用同样的抽象，但把 `lseek` 也放进 trait：

<div class="variant" data-arch="riscv64" data-lang="rust">

```rust
pub trait File: Send + Sync {
    fn read(&self, buf: &mut [u8]) -> Result<usize, SysError>;
    fn write(&self, buf: &[u8]) -> Result<usize, SysError>;
    fn seek(&self, pos: SeekFrom) -> Result<usize, SysError>;
}

pub struct FdTable {
    pub fds: Vec<Option<Arc<dyn File>>>,
}

impl FdTable {
    pub fn alloc(&mut self, file: Arc<dyn File>) -> usize {
        if let Some(fd) = self.fds.iter().position(|f| f.is_none()) {
            self.fds[fd] = Some(file);
            return fd;
        }
        self.fds.push(Some(file));
        self.fds.len() - 1
    }
}
```

</div>

`Arc<dyn File>` 是 trait object + 引用计数：fd 表、`fork` 后的子进程、`dup` 出来的 fd 都可以共享同一个打开文件。Rust 的 `Send + Sync` 约束强制你思考「这个文件对象能不能跨线程/跨 hart 共享」；管道需要内部可变性，所以要用 `Mutex` 或 `UnsafeCell` + 自旋锁。

### 完整程序：构造并读回一个 `myfs` 镜像

下面的程序在内存里构造一个 8 块的镜像，写入超级块、根目录（`.`、`hello.txt`）和文件内容，然后解析回来列目录、读文件。它可以直接在主机上跑，也可以把 `Vec<u8>` 换成 `BlockDevice` 写进 virtio 盘。

<div class="variant" data-arch="all" data-lang="rust">

```rust
// myfs.rs：最小文件系统镜像的构造与解析
use std::convert::TryInto;

const BLOCK: usize = 512;
const MAGIC: u32 = 0x4d59_4653; // "MYFS"
const INODE_SIZE: usize = 32;
const DIRENT_SIZE: usize = 32;

#[derive(Clone, Copy)]
struct Inode {
    mode: u16,          // 1=file, 2=dir
    size: u32,
    direct: [u32; 4],
}

#[derive(Clone, Copy)]
struct DirEntry {
    inode: u32,
    name: [u8; 28],
}

fn put_u32(buf: &mut [u8], off: usize, v: u32) {
    buf[off..off + 4].copy_from_slice(&v.to_le_bytes());
}
fn get_u32(buf: &[u8], off: usize) -> u32 {
    u32::from_le_bytes(buf[off..off + 4].try_into().unwrap())
}

fn write_inode(img: &mut [u8], idx: usize, ino: &Inode) {
    let off = 3 * BLOCK + idx * INODE_SIZE;
    img[off..off + 2].copy_from_slice(&ino.mode.to_le_bytes());
    put_u32(img, off + 4, ino.size);
    for (i, b) in ino.direct.iter().enumerate() {
        put_u32(img, off + 8 + i * 4, *b);
    }
}

fn read_inode(img: &[u8], idx: usize) -> Inode {
    let off = 3 * BLOCK + idx * INODE_SIZE;
    let mut direct = [0u32; 4];
    for i in 0..4 {
        direct[i] = get_u32(img, off + 8 + i * 4);
    }
    Inode {
        mode: u16::from_le_bytes(img[off..off + 2].try_into().unwrap()),
        size: get_u32(img, off + 4),
        direct,
    }
}

fn write_dirent(img: &mut [u8], block: usize, slot: usize, e: &DirEntry) {
    let off = block * BLOCK + slot * DIRENT_SIZE;
    put_u32(img, off, e.inode);
    img[off + 4..off + 32].copy_from_slice(&e.name);
}

fn main() {
    let data_start = 4u32;
    let mut img = vec![0u8; 8 * BLOCK];

    // 超级块
    put_u32(&mut img, 0, MAGIC);
    put_u32(&mut img, 4, 2);          // inode 数
    put_u32(&mut img, 8, data_start); // 数据区起始块

    // inode 0 = 根目录，inode 1 = hello.txt
    write_inode(&mut img, 0, &Inode { mode: 2, size: 64, direct: [data_start, 0, 0, 0] });
    write_inode(&mut img, 1, &Inode { mode: 1, size: 13, direct: [data_start + 1, 0, 0, 0] });

    // 根目录的两个目录项
    let mut dot = DirEntry { inode: 0, name: [0; 28] };
    dot.name[0] = b'.';
    write_dirent(&mut img, data_start as usize, 0, &dot);

    let mut hello = DirEntry { inode: 1, name: [0; 28] };
    hello.name[..9].copy_from_slice(b"hello.txt");
    write_dirent(&mut img, data_start as usize, 1, &hello);

    // 文件内容
    let content = b"hello, myfs!\n";
    let off = (data_start as usize + 1) * BLOCK;
    img[off..off + content.len()].copy_from_slice(content);

    // 解析回来
    assert_eq!(get_u32(&img, 0), MAGIC);
    let root = read_inode(&img, 0);
    println!("root: mode={} size={} direct={:?}", root.mode, root.size, root.direct);
    for slot in 0..2 {
        let eoff = root.direct[0] as usize * BLOCK + slot * DIRENT_SIZE;
        let ino = get_u32(&img, eoff);
        let name = &img[eoff + 4..eoff + 32];
        let end = name.iter().position(|&b| b == 0).unwrap_or(28);
        println!("dir[{}]: inode={} name={}", slot, ino, String::from_utf8_lossy(&name[..end]));
    }
    let file = read_inode(&img, 1);
    let foff = file.direct[0] as usize * BLOCK;
    println!("hello.txt: {}", String::from_utf8_lossy(&img[foff..foff + file.size as usize]));
    println!("image bytes = {}", img.len());
}
```

</div>

五行分别对应块 0 超级块、块 3 的 inode 0、块 4 的两个目录项（每条 32 字节，所以第二条在 2080）、块 5 的文件内容。前两行的读法：`5346 594d` 是小端存的 `0x4d59_4653`（"MYFS"），紧跟的 `0200 0000` 是 inode 数、`0400 0000` 是 `data_start=4`；inode 0 里 `0200` 是 `mode=2`（目录）、`4000` 是 `size=64`（两条 32 字节的目录项）、`0400 0000` 是 `direct[0]=4`。

后三行的读法：目录项前 4 字节是 inode 号、后 28 字节是名字，`.` 指向 inode 0 自己，`hello.txt` 指向 inode 1；而块 5 那 13 个字节才是文件真正的内容，`0a` 是结尾的换行。注意整个链条上没有一处出现「文件名」——内核找内容时用的是 inode 号，名字只在目录项这一步参与一次翻译。

这个程序把「磁盘布局」变成了可打印的字节，你可以用 `xxd`/`hexdump -C` 对照每个字段的偏移。真正接入内核时，只需把 `Vec<u8>` 换成 `BlockDevice::read_block/write_block`，把 `main` 换成系统调用；布局不变。

### 1.19.6 小结

从块设备到路径，中间只多了三张表和一层缓存：超级块定规则，inode 记「内容在哪些块」，目录项记「名字对应哪个 inode」，块缓存决定这些块被读多少次才真落到设备上。`open("hello.txt")` 因此在内核里是一条固定的查找链：拆路径 → 每一级在目录数据区线性（或哈希）找名字 → 拿到 inode → 建一个打开文件 → 在 fd 表里找最小空槽返回。如果只记住一件事：**文件名不是对象的身份，inode 才是**——所以硬链接可以让两个名字指向同一个 inode，而 `rename` 只是改目录项。

## 1.19.7 阶段 8：IPC、线程与同步 {#sec-1.19.7}

这一节回答：两个独立执行的程序怎么把数据交给对方，而且既不多给也不空等？同一个进程里两个线程同时改一个变量，凭什么结果还是对的？

::: preview 先抓住一件事
三件工具各解决一个问题：**pipe**（管道，内核里的一块环形缓冲区）解决「跨进程单向流」，它的语义难点全在边界——读空要睡、写满要睡、对端全关要返回 0 或报错；**线程**解决「同一个地址空间里多一条执行流」，共享地址空间、独占内核栈和现场；**锁**解决「两个执行流碰同一份数据」，靠原子指令 + 内存序（Acquire/Release 规定的可见性顺序）把读—改—写挤成一步。本节所有数字都是主机上真跑出来的：加锁那一路每次都恰好 40000，不加锁的那一路三次跑丢了一万左右的增量——这就是「碰巧对」和「对」的区别。
:::

**应用需求**：进程之间传数据、共享资源；一个进程内多个执行流。**硬件机制**：原子指令（`amoswap`/`lr/sc`）、IPI、`fence`。**内核抽象**：pipe、signal、线程、mutex、semaphore、condvar。

### pipe：内核里的一块环形缓冲区

pipe 有两个 fd：读端和写端，共享一个 `Pipe` 对象。`Pipe` 内部是环形缓冲区 + 读写位置 + 等待队列：

<div class="variant" data-arch="riscv64" data-lang="rust">

```rust
pub struct Pipe {
    buf: [u8; 4096],
    read: usize,
    write: usize,
    len: usize,
    readers: usize,
    writers: usize,
}

impl Pipe {
    pub fn read(&mut self, out: &mut [u8]) -> usize {
        let n = out.len().min(self.len);
        for i in 0..n {
            out[i] = self.buf[(self.read + i) % self.buf.len()];
        }
        self.read = (self.read + n) % self.buf.len();
        self.len -= n;
        n
    }

    pub fn write(&mut self, data: &[u8]) -> usize {
        let n = data.len().min(self.buf.len() - self.len);
        for i in 0..n {
            self.buf[(self.write + i) % self.buf.len()] = data[i];
        }
        self.write = (self.write + n) % self.buf.len();
        self.len += n;
        n
    }
}
```

</div>

`pipe` 的语义全在边界上，而边界用一份「不会睡」的主机版本最容易看清。下面把上面那个结构原样搬进一个可跑程序（去掉 `readers`/`writers` 两个计数，因为演示里没有阻塞路径），按六个动作依次调用（写作机 macOS arm64、`rustc 1.99.1` 实测）：

<div class="variant" data-arch="all" data-lang="all">

```bash
rustc -O lab1c19_pipe.rs -o lab1c19_pipe && ./lab1c19_pipe
```

</div>

```text
1 write(3000) -> 3000
2 read(4096)  -> 3000   len=0
3 read(4096)  -> 0   len=0
4 write(5000) -> 4096   len=4096
5 write(10)   -> 0   len=4096
6 read(100)   -> 100   len=3996
7 write(10)   -> 10   len=4006
8 read(4096)  -> 4006   len=0
pointers: read=3010 write=3010 (buf=4096)
byte[0] of last read = 98 (98='b', 100='d')
```

三个读数值得停一下。第 2 步：要 4096 只给 3000，这就是**短读**——`read` 返回「小于请求」是正常结果，不是错误，应用程序必须循环读到 0 或 EOF。第 4、5 步：写 5000 只收下 4096，紧接着写 10 个字节直接返回 0——缓冲区真的没有位置了；在这一行，真内核不会返回 0，而是让写端睡眠（读端全关时改返回错误并发 `SIGPIPE`），这也是「管道满」唯一的观测方式。最后一行两个指针都停在 3010，说明数据被读完时 `read == write`，而中间发生过一次回绕（3000 个 `a` 之后又写进 4096 个 `b`，起点早已越过缓冲区末尾）；`byte[0] = 98` 正是 `'b'`，环形复用没把新旧数据接错。

pipe 的语义细节：读空 pipe 要睡眠（除非写端全关，返回 0）；写满要睡眠（除非读端全关，返回 `EPIPE` + `SIGPIPE`）。`readers`/`writers` 计数决定「返回 0」还是「阻塞」。Rust 的借用检查器不允许你在持 `&mut Pipe` 时睡眠再唤醒（锁 guard 跨 await/阻塞点），所以内核里通常用 `Mutex<Pipe>` + `Condvar`，在循环里重新检查条件。

### 线程：共享地址空间，独立内核栈

线程与进程的区别只在「是否共享地址空间」：

| 维度 | 进程 | 线程 |
|:--|:--|:--|
| 地址空间 | 独立 `MemorySet` | 共享 `Arc<MemorySet>` |
| 内核栈 | 独立 | 独立 |
| trap frame | 独立 | 独立 |
| fd 表 | `fork` 复制 | 共享 `Arc<FdTable>` |
| 调度单位 | 进程/线程 | 线程 |

`myrcore` 用 `Thread` 表示调度实体，`Process` 持有 `Arc<MemorySet>` 和 `Arc<FdTable>`；`clone` 系统调用根据 flags 决定共享哪些资源。Linux 用 `clone(CLONE_VM|CLONE_FILES|...)` 表达同一件事，`task_struct` 既是进程也是线程。

### 完整程序：自旋锁、丢失的增量与顺序控制

内核里的锁只有几行，但要相信它，得看它在真并发下守不守得住。先看 C 的形状（单 hart 下甚至不需要原子指令，多 hart 必须靠 `amoswap` 或 `lr/sc`）：

<div class="variant" data-arch="riscv64" data-lang="c">

```c
/* 内核自旋锁：单 hart 下的最小实现；多 hart 需要 amoswap 或 lr/sc */
#include <stdatomic.h>

typedef struct { atomic_flag flag; } spinlock_t;

static inline void spin_lock(spinlock_t *lk)
{
    while (atomic_flag_test_and_set_explicit(&lk->flag, memory_order_acquire))
        __asm__ volatile("pause");
}

static inline void spin_unlock(spinlock_t *lk)
{
    atomic_flag_clear_explicit(&lk->flag, memory_order_release);
}
```

</div>

下面这份主机程序把同一件事翻译成 Rust，并且**同时跑两条路**：一条加锁、一条不加锁，各 4 个线程累加 10000 次；最后用条件变量把两个线程的打印顺序钉住。条件变量在这里起的就是「一次性信号量」的作用——`P` 是 `wait`，`V` 是 `notify_one`。

<div class="variant" data-arch="all" data-lang="rust">

```rust
// lab1c19_sync.rs — 自旋锁 / 无锁对照 / 条件变量定顺序
use std::sync::atomic::{AtomicBool, AtomicU64, Ordering};
use std::sync::{Arc, Condvar, Mutex};
use std::thread;
use std::time::Duration;

struct SpinLock(AtomicBool);

impl SpinLock {
    fn lock(&self) {
        // Acquire：临界区里的读写不许提到加锁之前
        while self.0.swap(true, Ordering::Acquire) {
            thread::yield_now();
        }
    }
    fn unlock(&self) {
        // Release：临界区里的写必须在解锁前对他人的 Acquire 可见
        self.0.store(false, Ordering::Release);
    }
}

const N: u64 = 10_000;

fn main() {
    let lock = Arc::new(SpinLock(AtomicBool::new(false)));
    let safe = Arc::new(AtomicU64::new(0));
    let racy = Arc::new(AtomicU64::new(0));

    let mut hs = Vec::new();
    for _ in 0..4 {
        let (l, s) = (lock.clone(), safe.clone());
        hs.push(thread::spawn(move || {
            for _ in 0..N {
                l.lock();
                s.store(s.load(Ordering::Relaxed) + 1, Ordering::Relaxed);
                l.unlock();
            }
        }));
    }
    for _ in 0..4 {
        let r = racy.clone();
        hs.push(thread::spawn(move || {
            for _ in 0..N {
                let v = r.load(Ordering::Relaxed); // 读—改—写之间没有任何屏障
                r.store(v + 1, Ordering::Relaxed);
            }
        }));
    }
    for h in hs {
        h.join().unwrap();
    }
    println!("counter      = {}", safe.load(Ordering::Relaxed));
    println!("lost-update  = {} （应为 {}，差额即被覆盖的次数）",
             racy.load(Ordering::Relaxed), 4 * N);

    // 条件变量：worker 必须先睡，main 放行后才打印
    let pair = Arc::new((Mutex::new(false), Condvar::new()));
    let pair2 = pair.clone();
    let worker = thread::spawn(move || {
        let (m, cv) = &*pair2;
        let mut g = m.lock().unwrap();
        while !*g {
            g = cv.wait(g).unwrap(); // 原子地放锁 + 睡
        }
        println!("worker");
    });
    thread::sleep(Duration::from_millis(50));
    println!("main");
    let (m, cv) = &*pair;
    *m.lock().unwrap() = true;
    cv.notify_one();
    worker.join().unwrap();
}
```

两张脸对比得非常干净：加锁那一路三次都是 40000，一分不少；不加锁的那一路丢了一万上下（`40000 − 32016 = 7984`），而且**每次都丢得不一样**。这就是「竞争条件」最容易骗人的地方——它不是偶尔崩，而是每次都给你一个看着合理、实则偏小的数字。丢增量的机理就在中间那两行：线程 A 读到 `v`，被抢走，线程 B 也读到同一个 `v`、写回 `v+1`，A 回来再写 `v+1`，两次自增只留下一次。

真正的难点是**内存序**：`lock` 用 `Acquire`、`unlock` 用 `Release`，否则临界区里的写可能被重排到锁外。C11 的 `atomic_*` 同理；`Relaxed` 在 x86-64 上可能「碰巧对」，在 RISC-V 的弱内存模型上会出错。上面那段无锁代码在两种硬件上都会丢，因为它丢的不是顺序而是**原子性**——再强的内存序也救不了「读和写是两条指令」；反过来，把中间两行换成一条 `r.fetch_add(1, Ordering::Relaxed)`，不加锁也三次跑出 40000（同一台写作机实测：`fetch_add(Relaxed) = 40000` ×3）。把「原子性」和「顺序」这两个变量分开，才是本节要教的判断力。

### 信号：异步的通知

signal 是「软件中断」：内核在 trap 返回用户态前检查 `pending` 位图，若有未阻塞的信号，就把用户栈改造成「信号处理函数 + `siginfo` + 返回地址」，然后 `sret` 到 handler。handler 返回时执行 `sigreturn`，恢复原现场。Linux 用 `rt_sigframe`，rCore chapter7 用简化版。

| 步骤 | 做什么 | 陷阱 |
|--:|:--|:--|
| 1 | 设置 `pending` 位 | 多线程共享/不共享 pending |
| 2 | 检查 `blocked` 掩码 | `SIGKILL`/`SIGSTOP` 不可阻塞 |
| 3 | 在用户栈构造 frame | 栈空间不足、对齐 |
| 4 | `sepc=handler`，`a0=sig` | 返回地址要指向 trampoline |
| 5 | handler `ret` 到 trampoline | trampoline 执行 `sigreturn` |
| 6 | `sigreturn` 恢复现场 | 恢复被中断的 syscall 返回值 |

### 1.19.7 小结

这一节有三个「边界」，各对应一类真实 bug。管道的边界是空与满：实测里 `read` 要 4096 只拿到 3000、`write` 要 5000 只收下 4096、下一次直接写返回 0——短读短写是常态，睡眠与 `SIGPIPE` 才是那一行内核代码要做的事。线程的边界是共享什么：共享 `Arc<MemorySet>` 与 `Arc<FdTable>`，独占内核栈和 trap frame，`clone` 的 flags 就是这份清单，所以「线程和进程差在哪」不是定义题而是配置题。锁的边界是原子性与顺序：加锁四次一万次恰好 40000，不加锁三次丢七千到一万两千，而一条 `fetch_add(Relaxed)` 不加锁也对——**丢增量怪的是「两条指令」，不是「重排」**。

如果只记住一件事：**并发 bug 的表现通常是「数字偏小」而不是「崩溃」，所以任何并发计数器都要和它应有的总数对照，而不是看程序有没有报错。**

## 1.19.8 一次 `read` 的完整路径 {#sec-1.19.8}

这一节回答：用户在 shell 里按一次回车，`cat` 读四个字节，从这条指令到磁盘控制器再到回来，内核里究竟经过几双手？每一双手失手时，用户看到的错误码是哪一个？

::: preview 先抓住一件事
十一层，但可以归成四段：**进门**（第 1–3 层，`ecall` → trap 入口 → 按号分发）、**查证件**（第 4–5 层，fd 合不合法、地址合不合法、fd 表里有没有这个对象）、**干活**（第 6–10 层，`File` 多态 → inode → 块缓存 → 设备 → 中断收尾）、**出门**（第 11 层，把字节数写回 `a0`、`sepc += 4`、`sret`）。整条路上只有第 10 层是异步的，前面全是同步等待；而用户能感知的每个 `errno`，都能在这张表里指回唯一一层。
:::

把前面的抽象串起来：用户调用 `read(fd, buf, len)`，内核里到底经过哪些层？

| 层 | 代码/函数 | 关键动作 | 失败 |
|--:|:--|:--|:--|
| 1 | 用户 `ecall` | `a7=63`（read），`a0=fd`，`a1=buf`，`a2=len` | — |
| 2 | `__s_trap_entry` | 换栈、保存 32 寄存器、`scause=8` | 栈非法 |
| 3 | `syscall()` | 按 `a7` 分发到 `sys_read` | 未知 syscall |
| 4 | `sys_read` | 检查 `fd` 范围、`buf` 用户地址合法 | `EBADF`/`EFAULT` |
| 5 | `FdTable[fd]` | `Arc<dyn File>` 克隆 | `None` |
| 6 | `File::read` | 普通文件/pipe/stdio 多态 | `EINTR`/`EPIPE` |
| 7 | `Inode::read_at` | 文件偏移 → 块号 | 越界 |
| 8 | `BlockCache::get` | 命中返回；未命中发 I/O | 超时 |
| 9 | `BlockDevice::read_block` | virtio queue + `wfi` | DMA 错误 |
| 10 | 中断 handler | 唤醒等待者、标记完成 | 丢失中断 |
| 11 | 返回用户 | 写 `a0=读取字节数`，`sepc+=4` | — |

这张表最有用的读法是**从错误码倒推层号**。`EBADF` 一定是第 4 或第 5 层：fd 是负数、超出 `fds.len()`，或者那个槽是 `None`（前一次 `close` 留下的空洞）；它绝不会来自第 7 层。`EFAULT` 只在第 4 层判：`buf` 落在内核地址区间，或者跨了一页而第二页没映射——这一层必须在任何拷贝发生之前检查，否则用户传一个 `0x8000_0000` 就能改写内核。`EINTR` 属于第 6 层：睡眠中的 `read` 被信号打断，返回而不是硬等到底。`EPIPE` 是第 6 层的另一端：读端全关，写管道既睡不到也写不进。

第 8 层和第 9 层的失败在教学内核里通常不做：块缓存不命中就发 I/O，virtio 队列没完成就一直 `wfi`（等待中断的指令），这也是为什么「丢失中断」在这里的表现是**整机卡死而不是报错**——没有超时机制，就没有错误码可返回。



第二件事：**同步与异步只有一条缝**。第 1 到第 9 层都跑在这次 `ecall` 的调用栈上，第 10 层是另一次 trap——它由设备发起，与被读的程序无关，进的却是 1.19.7 那个 `__s_trap_entry`（保存现场的代码完全相同，区别只在 `scause`：这里是高位为 1 的外部中断，那里是 8）。所以「一次系统调用」在内核里并不是一段连续的指令流，它可能是：进来、睡下、被中断叫醒、继续、出去。理解了这条缝，才理解为什么 `read` 能返回比请求少的字节数（见 [1.19.7](ch19.md#sec-1.19.7) 的短读实测）。

第三件事：第 7 层到第 8 层之间有一次「地址换算的两跳」。文件偏移先经 inode 的 `direct[]` 变成块号（`off / 512` 落在第几个直接块，见 [1.19.6](ch19.md#sec-1.19.6) 实测过的字节布局），块号再经页表变成内核虚拟地址（见 [1.19.4](ch19.md#sec-1.19.4)）——因为块缓存本身驻留在内核映射的页里。用户态的 `buf` 则是第三个地址空间里的地址，最后那次拷贝跨了两份页表。这三跳各自都可能失败，而它们失败时用户看到的都是同一个 `EFAULT` 或同一个卡死，这就是为什么排障必须回到层。

这条路径可以用 GDB 一站一站验证（下面的命令与断点形状来自 rCore 类内核的常见布局；**本机没有 QEMU 与 RISC-V 工具链，这段未实测（无 RISC-V 硬件/QEMU）**，能核实的只有断点函数名的拼写是否与你的 crate 一致）：

```bash

  -ex 'target remote :1234' \
  -ex 'b sys_read' -ex 'b myfs::Inode::read_at' \
  -ex 'b virtio_blk::read_block' \
  -ex 'c'
# 命中后：
#   p/x $a0        fd
#   p/x $a1        用户 buf
#   p/x $a2        len
#   bt             看调用链
#   info registers satp scause sepc
```

::: errata 这条路径上四个容易搞错的点
1. **把 `scause=8` 当成 S 态的 `ecall`**：8 是「从 U 态陷入」，9 才是「从 S 态陷入」。内核自己触发 `ecall` 走的是另一条分发，判错会把内核 panic 当作用户请求。
2. **在第 6 层之后才检查 `buf`**：地址合法性必须在写入用户缓冲区之前查；一旦开始写，非法地址要么直接 fault（在内核态 fault 通常是停机），要么写进恰好映射在那里的内核数据。
3. **以为 `sepc += 4` 是给 `read` 的**：所有同步异常返回都要前进 4 字节（RV64 定长指令），否则回到用户态会重新执行那条 `ecall`，看起来像「`read` 被调用了两次」。
4. **把块缓存命中当成第 8 层的成功**：命中确实不碰设备，但**仍然要走完第 6、7 层**——所以「文件读很快」和「第一次读很慢」是同一份代码，差别只在第 8 层是否落到 9、10 层。这也是 `posix_fadvise`、预读这类优化能改延迟却改不了正确性的原因。
:::

### 1.19.8 小结

一次 `read` 是十一层、四段路、一条异步缝、三次地址换算。这张表的价值不在背诵，而在两件事：拿着 `errno` 能指回唯一一层，拿着「卡死」能认出是第 9/10 层没有超时。如果只记住一件事：**内核的层不是抽象装饰，每一层只负责一种失败；把错误码翻译成层号，排障就从「猜」变成「查」。**

## 1.19.9 设计对照：rCore、Linux 与 `myrcore` {#sec-1.19.9}

这一节回答：把本章这十一个小节读完，你手里那个几千行的内核和第 1 篇里那个跑在你机器上的内核，差在哪几处？哪些差别是「机制不同」，哪些只是「工程量的不同」？

::: preview 先抓住一件事
对照只做一件事：把每个机制钉到**它在两边的名字**上，然后指出教学内核省略的那部分解决了什么问题。调度（RR vs CFS/EEVDF）、地址空间（`MemorySet` vs `mm_struct`/VMA）、页表（Sv39 三级 vs 四/五级）、进程（`TaskControlBlock` vs `task_struct`）、文件（`myfs`+`File` trait vs VFS+ext4）、同步（`SpinLock` vs `spinlock`/`mutex`/`rwsem`/RCU）。第二张表讲的是 Rust 特有的那笔账：所有权在五个位置白帮你、在三个位置逼你写 `unsafe`——判据是「这段代码要同时被两方引用吗」。
:::

| 维度 | rCore（教学） | Linux 6.8 | `myrcore`（本章） |
|:--|:--|:--|:--|
| 调度 | 简单 RR/优先级 | CFS/EEVDF + RT + deadline | RR + tick |
| 地址空间 | `MemorySet`/`MapArea` | `mm_struct`/`vma` | `MemorySet`/`MapArea` |
| 页表 | Sv39 三级 | 四级/五级，`pgd/p4d/pud/pmd/pte` | Sv39 三级 |
| 进程 | `TaskControlBlock` | `task_struct` | `Process`/`Thread` |
| 文件 | easy-fs + `File` trait | VFS + ext4/xfs/btrfs | `myfs` + `File` trait |
| 同步 | 自旋锁/信号量/条件变量 | `spinlock`/`mutex`/`rwsem`/RCU | `SpinLock`/`Semaphore` |

这张表说明：rCore 不是「小 Linux」，它把 Linux 的**机制**抽出来，去掉了工程复杂度（RCU、cgroup、namespace（把同一个内核切成互不可见的视野）、日志、多核负载均衡）。读 rCore 的正确姿势是「看它如何用最小代码实现一个机制」，而不是「背它的结构体名」。

三行对照值得单独说。**调度**：`myrcore` 的 RR 加 tick 就是「到点就换」，Linux 的 CFS/EEVDF 要解决的是「换了之后怎么算公平」——权重、虚拟运行时间、可抢占时延这些概念在教学内核里一个都不需要（[1.13](ch13.md) 讲调度器时能看到它们各自的代价）。**页表**：Sv39 是三级、每级 9 位、页大小 4 KiB；x86-64 是四级（LA57 五级），中间多了 `p4d` 这一层，且大页是 2 MiB/1 GiB 两档（[1.9](ch09.md)）。机制一样——都是「按虚拟地址的位切片去索引一张物理页」——层数和档位是工程选择。**文件**：`File` trait 对应 Linux 的 `struct file_operations`，`myfs` 的 inode 对应 VFS 的 `struct inode`；Linux 那一侧真正难的是日志、并发写一致性与崩溃恢复，教学内核直接把这块砍掉（[1.10](ch10.md)、[1.13](ch13.md)）。

看到这张表之后，最该带走的一个判断是：**教学内核缺的不是「聪明的算法」，而是「崩溃之后还能对上账」的机制**。位图分配器不会因为你掉电就丢已分配的块，但 journal、写时复制、`fsync` 语义会决定掉电后有多少数据回来；多核不均衡不会让程序错，但缺了 RCU 的读侧无锁就会让读延迟随写者数量涨。学完这一章再回头看第 1 篇里那些「为什么 Linux 要这么麻烦」的段落，答案基本都是同一句：因为有人会在半夜断电。

### Rust 所有权在五个地方帮了你，在三个地方逼你写 `unsafe`

| 场景 | Rust 的帮助 | 代价 |
|:--|:--|:--|
| 页表释放 | `Drop` 保证不泄漏 | 共享页要手动区分，`Drop` 不能无脑释放 |
| fd 表共享 | `Arc` 引用计数 | 循环引用要用 `Weak` |
| 进程父子 | `Weak` 表达非拥有关系 | 每次 upgrade 要处理 `None` |
| 锁 | `Mutex<T>` 把数据和锁绑定 | 持锁跨阻塞点会死锁 |
| 缓冲区 | 切片长度检查 | 用户指针仍是 `unsafe` |
| 页表 PTE | 类型区分 PTE/PA | 位操作全靠 `unsafe` |
| 中断上下文 | `Send/Sync` 约束 | 自旋锁不能睡眠 |
| DMA | `&mut [u8]` 独占 | 设备写内存要 `unsafe`/`volatile` |

::: intuition 为什么内核代码里 `unsafe` 不可避免？
因为内核要表达「这块物理页同时被页表、DMA、用户映射三方引用」这种硬件事实，而 Rust 的类型系统只知道「谁持有 `&mut`」。`UnsafeCell`、`Arc`、`Mutex` 都是把硬件协议翻译成类型协议的工具；翻译不了的部分，就必须用 `unsafe` + 注释说明不变量。好的内核 Rust 代码不是「没有 `unsafe`」，而是「每个 `unsafe` 都能说清前提」。
:::

本章那三个真跑过的程序正好是这张表的三块小证据。[1.19.6](ch19.md#sec-1.19.6) 的 `myfs` 里没有一个 `unsafe`：`Vec<u8>` 的切片越界会 panic，所以「把 `direct[0]` 写成 0 结果读到超级块」这类错在主机版里只是数字不对，在内核版里却是把块 0 当成文件内容——同样的逻辑，宿主语言替你挡住了一半。

[1.19.7](ch19.md#sec-1.19.7) 的自旋锁用 `Arc<AtomicU64>` 而不是 `static mut`，编译器逼你为「四个线程共享一个计数器」写明共享方式，这一条就是表里「fd 表共享：`Arc` 引用计数」那一行。而 `SpinLock` 内部那个 `swap`——它必须用原子指令，因为「两个 hart 同时抢锁」在类型系统里没有对应物；这就是表里第三类：硬件协议翻译不成类型协议时，`unsafe` + 一句不变量注释是唯一的写法。

### 1.19.9 小结

对照表的正确用法是当「翻译器」：在读 Linux 时把名字换回你写过的东西（`task_struct` ↔ `Process`/`Thread`，`file_operations` ↔ `File` trait，VMA ↔ `MapArea`），在读教学内核时反问「Linux 在这里多出来的那三千行在解决什么」。本章跑过的三个主机程序给出了回答的下半句：Rust 帮你的地方（切片检查、`Arc`、`Drop`、`Mutex` 绑数据）都是「同一时刻只有一方」，逼你 `unsafe` 的地方（PTE 位段、中断上下文、DMA）都是「同一块内存同时被多方引用」。如果只记住一件事：**教学内核与真内核的差，主要在「崩溃以后」和「同时发生」这两类场景上，而不是在算法聪明与否上。**

## 1.19.10 实验：QEMU、GDB 与 objdump {#sec-1.19.10}

这一节回答：一个从没跑过 RISC-V 的人，凭什么相信自己写的内核？手上只有一台 x86/ARM 机器时，本章哪些结论能真验证、哪些只能停在纸面？

::: preview 先抓住一件事
证据分三级，强度递减：**运行**（QEMU 里真跑起来、看到打印）最强也最难拿到；**产物**（`readelf`/`nm`/`objdump` 读 ELF 的入口、段、符号）不需要目标机，一台普通 Linux 就够；**算术**（`satp` 的位段、页表索引切片）纸面和主机程序都能验。这一节把三级分开摆明：实验一、二的 QEMU/GDB 部分在本套件的两台机器上都跑不了（写作机是 macOS arm64、无 RISC-V 工具链；测试 VM 上 `qemu-system-riscv64`、`gdb-multiarch`、`riscv64-linux-gnu-as` 三个命令的存在性检查是真跑过的，结果就在下面），所以每一条都配了能真做的替代，替代全部复跑过。
:::

### 实验一：批处理内核与系统调用

<div class="variant" data-arch="riscv64" data-lang="all">

```bash
cargo build --release
qemu-system-riscv64 -machine virt -nographic -bios default \
  -kernel target/riscv64gc-unknown-none-elf/release/myrcore -s -S
# 另一个终端
gdb-multiarch target/riscv64gc-unknown-none-elf/release/myrcore \
  -ex 'target remote :1234' \
  -ex 'b rust_main' -ex 'b s_trap_handler' -ex 'c'
```

</div>

在 `s_trap_handler` 断点处检查：`p/x $scause` 应为 8，`p/x $sepc` 应指向应用里的 `ecall`，`p/x $a7` 应为 2。继续后应看到 `batch: app exit`。

**未实测（无 RISC-V 硬件/QEMU）**，缺口要说清：测试 VM 上这条存在性检查是真跑的。

```text
ubuntu@ubuntu:~$ command -v qemu-system-riscv64 gdb-multiarch riscv64-linux-gnu-as
ubuntu@ubuntu:~$ echo "exit=$?"
exit=1
```

一行路径都没打印、退出码 1，意味着三个命令都不在 `PATH` 里；VM 上装不了它们——`sudo` 需要密码，而本套件的实验全程免 `sudo`。

能真做的是把同一套判断用在**形状最像的产物**上：一个不依赖 libc、入口自己指定的静态 ELF。下面这 36 字节代码在测试 VM（Ubuntu 24.04 aarch64）上真编真跑，读数全部来自那次执行：

```text
ubuntu@ubuntu:/tmp$ as lab1c19_free.s -o lab1c19_free.o && ld -e _start -o lab1c19_free lab1c19_free.o
ubuntu@ubuntu:/tmp$ ./lab1c19_free
freestanding ok
ubuntu@ubuntu:/tmp$ ls -l lab1c19_free
-rwxrwxr-x 1 juanwang juanwang 1072 Oct 31 17:11 lab1c19_free
ubuntu@ubuntu:/tmp$ readelf -hW lab1c19_free | grep -E 'Class|Type|Machine|Entry'
  Class:                             ELF64
  Type:                              EXEC (Executable file)
  Machine:                           AArch64
  Entry point address:               0x4000b0
ubuntu@ubuntu:/tmp$ nm lab1c19_free | grep -E ' T | d '
00000000004100d4 d msg
00000000004000b0 T _start
ubuntu@ubuntu:/tmp$ size lab1c19_free
   text	   data	    bss	    dec	    hex	filename
     36	     17	      0	     53	     35	lab1c19_free
```

三个读数对应内核启动的三个致命问题。`Type: EXEC` 而不是 `DYN`：这不是位置无关可执行文件，加载地址就是链接地址，等价于裸机内核「代码必须在 `0x8020_0000`」那个前提。`Entry point address: 0x4000b0` 与 `nm` 里 `_start` 的地址**完全相同**：说明 `-e _start` 真的写进了 ELF 头，固件跳过去就是这里——内核第一条指令错了后面全错，而这一点在没有调试器时也能确认。`readelf -lW` 给出两个 `LOAD`（`R E` 在 `0x400000`、`RW` 在 `0x4100d4`），把「哪段可执行、哪段可写」摆明；`objdump -d` 里那条 `adr x1, 4100d4 <msg>` 正是跨段的 PC 相对引用：

```text
  4000b0:	d2800808 	mov	x8, #0x40                  	// #64
  4000b4:	d2800020 	mov	x0, #0x1                   	// #1
  4000b8:	100800e1 	adr	x1, 4100d4 <msg>
  4000bc:	d28001e2 	mov	x2, #0xf                   	// #15
  4000c0:	d4000001 	svc	#0x0
  4000c4:	d2800ba8 	mov	x8, #0x5d                  	// #93
  4000cc:	d4000001 	svc	#0x0
  4000d0:	14000000 	b	4000d0 <_start+0x20>
```

把这套手续换成 RISC-V，只需要相信一件事：链接脚本给的 `BASE_ADDRESS` 会同时出现在 ELF 入口和 `stvec` 的写入值里。这一步在本套件只有纸面证据，是真需要 QEMU 才能确认的部分。

### 实验二：页表与 `satp`

将 1.19.4 的 `Sv39` 移植到内核后，在 `satp` 写入处下断点：

<div class="variant" data-arch="riscv64" data-lang="all">

```bash
gdb-multiarch ... -ex 'b MemorySet::activate' -ex 'c'
# 命中后
p/x $satp          # 应为 0x8000000000000000 | root_pa >> 12
p/x (($satp & 0xffffffffff) << 12)  # 由 PPN（低 44 位）算根页表物理地址
x/8gx root_page_table
```

</div>

**GDB 部分未实测（同上）**，但这条算式可以真算。`satp` 是位段：bit 63..60 是 `MODE`（Sv39 = 8）、bit 59..44 是 `ASID`、bit 43..0 是根页表的 PPN。取 `root_pa = 0x8004_0000` 代一遍：

```text
PPN  = 0x8004_0000 >> 12           = 0x80040
satp = (8 << 60) | 0x80040         = 0x8000_0000_0008_0040
反解 = (satp & 0xffff_ffff_ffff) << 12 = 0x8004_0000   # 回到原地址
MODE = satp >> 62 = 2（即 bit63=1、mode=8）
```

两个坑正好落在这几位上。`root_pa` 忘了右移 12，写进去的是字节地址而不是页号，硬件按 PPN 再乘 4 KiB，根页表会指到 4096 倍远的地方；`MODE` 没置 bit 63（写成 `0 | root_pa >> 12`），Sv39 根本不生效，所有虚拟地址直接当物理地址用——表现是「开了页表反而不报错，但隔离完全没起作用」，比崩溃更难发现。

用 [1.19.4](ch19.md#sec-1.19.4) 那份主机页表程序（本套件的写作机上复跑过，输出含 `frames = 4`）算出同一个 VA 的三级索引，再和 GDB 里的 PTE 对照；如果对不上，先检查 `satp` 的 `MODE` 是否为 8。

### 实验三：文件系统镜像

这一条完整可跑，不碰 RISC-V。把 [1.19.6](ch19.md#sec-1.19.6) 的 `myfs.rs` 编出来运行、再把镜像落盘转储，写作机上实测：

```text
$ rustc -O myfs.rs -o myfs && ./myfs
root: mode=2 size=64 direct=[4, 0, 0, 0]
dir[0]: inode=0 name=.
dir[1]: inode=1 name=hello.txt
hello.txt: hello, myfs!
image bytes = 4096
$ xxd -l 16 -s 1536 lab1c19_myfs.img
00000600: 0200 0000 4000 0000 0400 0000 0000 0000  ....@...........
```

要生成可转储的镜像文件，在 `main` 末尾加一行 `std::fs::write("lab1c19_myfs.img", &img).unwrap();`，上面的 `xxd` 就是这么拿到的。注意 stdout 打印的是**解析结果**，`xxd` 读的是**字节**——两者一致才叫验证过；只打印不转储，写字段的偏移和读字段的偏移可能同时写错而互相抵消。改两个值各试一次：把 `direct[0]` 从 4 改成 5、把 `size` 从 13 改成 12，看哪一行读数先不对，比读十遍代码有用。

### 实验四：只用产物读数，也能定位「没输出」

把三级证据合起来用一次。假设 `myrcore` 启动后毫无打印（教学内核最常见的第一个 bug），按下面顺序查能省掉整个下午：先 `readelf -hW` 看 `Entry` 是否等于链接脚本的 `BASE_ADDRESS`（不等于 → `-T linker.ld` 没生效，或 `_start` 名字不对）；再 `nm` 确认 `__s_trap_entry` 在符号表里且类型是 `T`（不在 → `global_asm!` 那段没编进来，`stvec` 会跳往随机地址）；再 `size` 看 `text` 是不是只有一两百字节（若是几十 KB，说明链进了 `std`，裸机上必然死在缺页）；三步全在主机完成，不需要 QEMU。剩下那类必须真跑才能定位：入口对了但 `sscratch` 没初始化（见 [1.18.7](ch18.md#sec-1.18.7) 的坑 5），它的表现是「一条指令都没执行完就 triple fault」。

::: errata 本节实验环境的四个硬限制
1. **没有 QEMU**：`qemu-system-riscv64` 在测试 VM 上不存在（实测 `command -v` 退出码 1），写作机是 macOS arm64 也没有；所以本章所有「M 态 → S 态 → U 态」的运行序列只有纸面证据。
2. **没有 RISC-V 工具链**：`riscv64-linux-gnu-as`/`-gcc` 都没有；写作机 `clang --target=riscv64` 汇编时直接报 `Unknown command line argument '-riscv-add-build-attributes'`（实测原文），连 `.o` 都出不来。
3. **`gdb-multiarch` 缺失**：断点、`p/x $scause`、`x/8gx` 三类读数的**具体数值**都标未实测，能给的只有期望值与判据。
4. **主机程序不等于目标机行为**：`myfs.rs`、`sv39.rs`、`lab1c19_sync.rs` 跑通证明的是算法与布局，不证明硬件时序、DMA 与真实缺页路径。
:::

### 1.19.10 小结

这一节教的不是命令，而是**给证据分级**：运行 > 产物 > 纸面。本章不少结论只能停在后两级——手上没有 RISC-V 硬件、没有 QEMU、没有交叉工具链，这三件事都在正文里写明，而不是把预期输出伪装成实测。能真跑的三条全跑了：`myfs` 的字节布局（含 `xxd` 转储）、`sv39` 的三级切片（含 `frames = 4`）、并发累加的 40000 与丢的一万上下。如果只记住一件事：**先说自己站在哪一级证据上，再说结论**——这条比本章任何一张表都耐用。

**Q1（记忆）** 本节三个主机可跑的实验各自证明了哪一层？

**Q2（辨析）** `readelf -h` 看到 `Type: DYN` 而不是 `EXEC`，对裸机内核意味着什么？为什么它只是产物级证据？

**Q3（应用）** 有人说「我的内核在 QEMU 里跑通了，所以 `satp` 一定写对了」。用实验二的位段分析反驳这句，并给出一个不需要 GDB 的检查。

::: sol 答案
**A1** `myfs` 证明第 7–8 层（偏移→块号→字节，以及目录项与 inode 的字段位置）；`sv39` 证明地址翻译（三级切片、大页停在 level 1、`frames = 4` 说明页表自身的开销）；`lab1c19_sync` 证明并发语义（加锁 40000、无锁丢七千到一万两千、`fetch_add` 不加锁也对）。
**A2** 意味着它被链成位置无关可执行文件，真正加载地址由运行时的加载器决定——裸机没有加载器，固件按 `Entry` 跳过去，若链接地址与实际放置地址不一致，第一条指令就取错。它是产物级证据，因为你从 ELF 头读出了这个事实、完全不必执行它；但也仅此而已：`DYN` 不能告诉你跳过去之后会不会立刻 fault。
**A3** 「跑通」只覆盖被走到的那条路径。`MODE` 没置 bit 63 时页表根本不参与翻译，内核若恰好只用恒等映射（虚拟 = 物理）就能一路跑通，而隔离与越界检查从未生效——正是实验二点出的「比崩溃更难发现」。不依赖 GDB 的检查：`objdump -d` 找到写 `satp` 的那条 `csrw`，看它前面构造值的指令是不是 `(8<<60)` 与 `ppn` 的或；或者把 1.19.4 那份主机翻译器拿来，喂进内核用的同一组常量，比对算出的 `satp` 十六进制值。
:::

本章留下的不是一套代码，而是三样东西：一张**八阶段地图**（每一步都能问「应用需求/硬件机制/内核抽象」），一条**贯穿路径**（一次 `read` 的十一层，错误码能指回唯一一层），一套**证据分级**（运行 > 产物 > 纸面，本章大量结论只到第二级，并且写明了）。收口只做两件事：把主线重述成三段，把口径边界摊开——哪些数字真跑过、哪些没有，你之后引用时得负这个责任。
:::

**主线三段。** 第一段立骨架：[1.19.1](ch19.md#sec-1.19.1) 把八个阶段和五个问题摆成地图；[1.19.2](ch19.md#sec-1.19.2) 用批处理内核立起第一条特权级边界——加载器六步、用户栈、`sscratch` 存内核栈顶，以及 `sret` 只换 `sepc`/`sstatus` 而不换 `sp` 这个硬件事实。

第二段长机制：[1.19.3](ch19.md#sec-1.19.3) 的 `TaskContext` 只保存 14 个 callee-saved，靠 ABI 约定把剩下的交给编译器；时钟中断把「愿意让」变成「必须让」。[1.19.4](ch19.md#sec-1.19.4) 的 Sv39 是三级切片，`MemorySet`/`MapArea` 是内核那一侧的账本。[1.19.5](ch19.md#sec-1.19.5) 把 fork/exec/wait 拆成「谁拥有哪份资源」；[1.19.6](ch19.md#sec-1.19.6) 把磁盘布局摊到字节级；[1.19.7](ch19.md#sec-1.19.7) 把并发逼到一个数上——加锁 40000、无锁丢一万上下。第三段收口：[1.19.8](ch19.md#sec-1.19.8) 用一张十一层表把前面所有抽象串成一条路径；[1.19.9](ch19.md#sec-1.19.9) 拿 Linux 做对照，并算清 Rust 所有权帮了五处、逼你 `unsafe` 三处；[1.19.10](ch19.md#sec-1.19.10) 把证据分成三级。

**三条判据。** *能解释*：给你任一 `errno`（`EBADF`/`EFAULT`/`EPIPE`/`EINTR`），能指出它诞生在第几层，并说出这一层为什么必须先于拷贝执行。*能操作*：不查资料写出 `TrapFrame` 的偏移表、`__switch` 要保存的寄存器清单、`satp` 的位段拼法，且知道 `sfence.vma` 为什么不能省。*能判断*：面对「我的内核跑通了」这句话，能追问走的是哪条路径、有没有可能页表根本没生效；面对一个性能或正确性结论，能说出它站在哪一级证据上。

如果只记住一件事：**这几千行代码证明了机制本身不难——难的是「崩溃之后还能对上账」和「同时发生也不出错」。** Linux 那几百万行不在算法上，而在这两件事上。

### 本章的口径边界

::: errata trap 与任务切换的四个坑
1. **`sepc` 不 +4**：系统调用返回后死循环。
2. **`sscratch` 没设**：第一次 trap 时 `sp=0`，load fault。
3. **`__switch` 保存了 caller-saved**：多余且可能破坏编译器假设；只保存 `ra/sp/s0..s11`。
4. **切换任务不换 `sp`**：两个任务共用一个内核栈，返回地址互相覆盖。
:::

::: errata Sv39 地址空间的三个坑
1. **`satp` 改了不 `sfence.vma`**：旧 TLB 项让用户访问到已撤销的页。
2. **PTE 的 `W=1` 但 `R=0`**：保留组合，硬件可能触发 page fault。
3. **大页翻译丢高位偏移**：`mask` 写成 `0xfff`，2 MiB 页只保留 4 KiB 偏移。
:::

::: errata 进程、pipe 与同步的五个坑
1. **`fork` 后父子共享 fd 但复制了 file offset**：POSIX 要求共享 offset；复制会导致读位置错乱。
2. **`parent` 用 `Arc`**：父子循环引用，进程永不释放。
3. **`wait` 在锁外检查条件**：丢失唤醒，父进程永久睡眠。
4. **pipe 读端全关，写端仍阻塞**：应返回 `EPIPE` 并发送 `SIGPIPE`。
5. **持自旋锁睡眠**：中断关闭 + 调度器无法运行，系统死锁。
:::

### 达标自检与证据账目

达标自检全部移交章末的[学习目标自检表](ch19-checklist.md)（22 条，分概念、动手、实验、口径四组，每条都写成能当场做的动作）。这里只留一句判据：**S 组那几条不要按「读过」算达标，要按「跑过或明确标了未实测」算。**

::: method 即时自测 · 1.19
**Q1** `__switch` 只保存 `ra/sp/s0–s11`，为什么不保存 `a0–a7` 和 `t0–t6`？切换完成后 `ret` 返回到哪里？

**Q2** `fork` 复制哪些资源、共享哪些？`exec` 失败时为什么必须保留旧地址空间？zombie 进程由谁、在什么条件下回收？

**Q3** Sv39 下，VA `0x0000_0040_0800_1000` 的三级页表索引 `VPN[2]/VPN[1]/VPN[0]` 与页内偏移各是多少？若根页表在物理地址 `0x8030_0000`，`satp` 应写入什么值？

**Q4** pipe 的读端全部关闭后，写端继续 `write` 会怎样？反过来写端全关，读端继续 `read` 呢？持自旋锁的任务睡眠为什么是死锁？

::: sol 答案
**A1** 切换点是一次普通函数调用：按调用约定，caller-saved 寄存器在进入 `__switch` 前已由编译器保存在当前任务的内核栈上（或视为失效）；只有换栈后仍要恢复的 callee-saved（`s0–s11`）和决定去留的 `ra`、`sp` 需要写进 `TaskContext`。恢复 `next` 的 `ra` 后，`ret` 跳到 `next` 上次调用 `__switch` 的下一条指令——看起来像正常返回，实际已在另一个任务的内核栈上。

**A2** `fork` 分配新 pid/PCB/内核栈，复制 `MemorySet`（COW）与 `TrapFrame`；fd 表是「复制表、共享打开文件」——`Arc` 克隆后父子共享同一个 file offset，POSIX 要求如此。`exec` 必须先解析 ELF、建好新页表，全部成功后才原子替换 `MemorySet`；若先释放旧的，解析失败时进程就没有地址空间了。zombie 由父进程 `wait` 取走退出码并释放 PCB；`parent` 指针要用 `Weak`，否则父子循环引用、进程永不释放。

**A3** 按位拆：VPN[2] = (VA >> 30) & 0x1ff = 256（bit 38），VPN[1] = (VA >> 21) & 0x1ff = 64（bit 27），VPN[0] = (VA >> 12) & 0x1ff = 1（bit 12），offset = 0。`satp = (8 << 60) | 0x80300`——MODE=8 选 Sv39，PPN = 0x8030_0000 >> 12 = 0x80300。写入后要 `sfence.vma`，否则旧 TLB 项还在。

**A4** 读端全关：写端 `write` 返回 `-EPIPE` 并触发 `SIGPIPE`（未被忽略/阻塞时进程被杀），不再阻塞。写端全关：读端把缓冲区剩余数据读完后再 `read` 返回 0（EOF）。持自旋锁时中断关闭、调度器无法运行，睡眠的任务永远不会醒来释放锁，其他任务原地自旋等锁，系统停摆；等待应交给互斥锁 + 等待队列，且「检查条件必须在持锁时进行」以防丢失唤醒。
:::
