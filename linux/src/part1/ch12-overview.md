# 1.12 并发编程 · 本章导航

::: preview 这一章在讲什么
两个执行流同时读写同一块内存，凭什么不会互相踩？这一章把这个问题压成三件事：**共享状态由谁排序**（数据竞争与 happens-before）、**等待用什么表达**（互斥锁、条件变量、信号量、futex）、**任务与 fd 各交给谁**（线程池还是事件循环）。1.12.1–1.12.7 给「会用」，1.12.8–1.12.16 补「用对」，1.12.17 收口。
:::

## 这一章回答什么

先记住三个词：**并发**是「多个任务在时间上重叠」，单核分时也算；**并行**是「同一时刻真的在算」，要有多核；**数据竞争**是两个线程无同步地访问同一内存、至少一个在写，C11 把它定义为未定义行为，不是「概率问题」。

- **共享地址空间换来了什么、又拿走了什么**：线程共享全局变量、堆与 fd 表，创建比进程便宜；代价是任何一个 `counter++` 都可能丢更新，任何一次回调都可能重入。
- **等待怎样表达才不出错**：互斥锁保护不变量；条件变量必须配 `while` 并在持锁时改条件；信号量有计数、条件变量没有记忆；顺序颠倒就会在缓冲区满/空时死锁。
- **任务多了怎么办、fd 多了怎么办**：线程池把「每个请求一个线程」换成「固定 worker + 有界队列」，队列满时用背压或拒绝；事件循环把「每条连接一个执行流」换成「一个线程照看全部 fd」，代价是不能阻塞。
- **「会用」之后怎样「用对」**：`pthread_*` 返回错误码而不设 `errno`；joinable 线程不 join 就是泄漏；`volatile` 不建立顺序；`relaxed` 只保证原子；锁在无竞争时根本不进内核。
- **出了问题怎样取证**：TSan 报「两次访问 + 各自栈」，helgrind 报锁序，`ps -L` 看 `wchan`，`strace` 数 `futex`，`taskset` 把线程钉在核上复现争用。

## 读完你会

- 用一句话区分并发与并行，并用 Amdahl 定律说明「4 核、90% 可并行」的加速比上限约 3.08。
- 写出竞争程序（`race_lab.c`），解释 `-O0` 下 4 个线程各加 100 万次为什么只得到 200 万左右，而 `-O2` 可能「算对」仍是未定义行为；用互斥锁、原子操作、局部累加三种方式修复。
- 写出信号量版有界缓冲区，说清 `empty`/`full`/`mutex` 的初值与「先等资源、再拿锁」的顺序。
- 实现一个带背压和优雅关闭的线程池，指出 `shutdown` 与「队列非空」两个判断的先后为什么不能写反。
- 解释 `pthread_create`/`pthread_join` 的错误码语义、joinable 与 detached 的资源归属，以及 8 MiB 只是虚拟栈。
- 用 `release` 存 + `acquire` 读发布数据，说清 `relaxed`、`seq_cst`、`volatile` 各自的边界。
- 用 futex 的三态状态字解释「无竞争加锁为什么没有系统调用」，用 TSan/helgrind/`ps`/`strace` 组一条证据链。
- 在「10 万条长连接」与「每请求 100 ms 磁盘 I/O」两个场景里给出模型选择与理由。

- 系统调用与网络：[1.10.8 fd 的完整语义](../part1/ch10.md#sec-1.10.8)（共享 fd 表、共享文件偏移）、[1.11.11 四种并发模型](../part1/ch11.md#sec-1.11.11)、[1.11.12 边沿触发 epoll](../part1/ch11.md#sec-1.11.12)。1.12.7 把单 reactor 扩成「线程池 + 多 reactor」。

- 环境：本书复现环境是 Ubuntu 24.04.5 虚拟机（aarch64、内核 7.0.0-38-generic、GCC 13.3.0、4 vCPU）。`pthread`、`taskset`、`strace`、`valgrind`、`gdb` 已安装；`sudo` 不可用。`perf` 的硬件事件被 `perf_event_paranoid=4` 挡住，`perf c2c` 报 `no PMU supports the memory events`，所以 1.12.15 的 `perf` 部分按「未实测」读。TSan 在本机直接运行会报 `unexpected memory mapping`，要加 `setarch -R`（详见[勘误页](ch12-errata.md)）。

## 怎么读

- **第一次读**：按段走 1.12.1–1.12.7，每节做完「即时自测」再往下。1.12.2 与 1.12.3 是全章的脊梁：前者解释「竞争是什么」，后者解释「等待怎样写才不丢通知」。这两节没读懂，后面的线程池只会变成抄代码。
- **正在排一个具体的故障**：先看[章末总结](ch12-summary.md)的「症状 → 机制 → 命令」表，再跳到对应小节。进程卡死、CPU 为 0 看 1.12.12；计数偶发少、压测才复现看 1.12.2 与 1.12.15；线程数或内存持续涨看 1.12.8；队列在涨、CPU 不高看 1.12.13；容器里 `pthread_create` 返回 `EAGAIN` 看 1.12.13 与勘误页。
- **要动手**：1.12.4 的生产者-消费者、1.12.5 的线程池、1.12.11 的读写锁基准、1.12.12 的 AB/BA 死锁、1.12.15 的 TSan 与伪共享都给了完整源码。建议顺序是 race → 生产者-消费者 → 线程池 → 死锁 → TSan，先跑通再看解释；编译选项与实测读数见[习题集](ch12-exercises.md) C 组。
- **准备面试**：1.12.2 的三步与三种修法、1.12.3 的 `while`、1.12.4 的信号量顺序、1.12.9 的 release/acquire、1.12.10 的 futex 快路径是五处必答；把[习题集](ch12-exercises.md) A 组做完，再做 B 组。
- **怕数字搬家**：本章标「VM 实测」的读数来自本书虚拟机（见[勘误与版本注记](ch12-errata.md)）；`perf c2c`、x86-64 的代码生成、helgrind 的 20–100 倍开销都按「形状示例」或「未实测」读。
