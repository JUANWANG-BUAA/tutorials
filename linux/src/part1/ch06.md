第 [1.5](ch05.md) 章反复出现一个结论：当 CPE 的下界从 ALU 转向内存，优化手段就变成「提高局部性」。这一章把「局部性」落到硬件：缓存有多少组、每组多少路、一次缺失要多少周期、替换策略如何决定下一次是否命中。

存储层次的核心矛盾是**速度与容量不可兼得**。寄存器最快但只有几百字节，DRAM 有几十 GB 但延迟是寄存器的几百倍。缓存在两者之间插入多层小的快速存储，利用时间局部性与空间局部性，让「平均访问时间」接近上层，而「容量」接近下层。

这一章的数字以典型 x86-64 服务器/桌面为背景：L1 32–48 KiB、L2 512 KiB–1 MiB、L3 8–32 MiB、缓存行（缓存与内存之间搬运数据的固定块）64 B、DRAM 延迟 80–100 ns。ARM64 手机/服务器 SoC 的绝对值不同，但结构与分析方法相同。

## 1.6.1 存储技术：从 SRAM 到 SSD {#sec-1.6.1}

这一节回答：CPU 取一个数，为什么有时等 1 纳秒、有时等 100 纳秒？这些层级各用什么器件，凭什么有快慢之分？

::: preview 先抓住一件事
存储层次不是「把几种内存按速度排队」，而是一条链：每一层都是下一层的缓存，上一层的命中把下一层的延迟藏起来。容量与速度不可兼得，所以快的必然小、大的必然慢。参数可以从系统里读，但虚拟机常常把容量藏起来；读不到时，用指针追逐量出的台阶仍然能告诉你分了几层。
:::

### 先读参数：这台 VM 只肯给你一半

Linux 上查缓存参数有两条路：`getconf` 和 `/sys/devices/system/cpu/cpu0/cache/`。在 `ubuntu24`（Ubuntu 24.04.5 aarch64，4 vCPU）上跑：

```bash
getconf -a | grep CACHE
lscpu -C
```

实测输出（节选）：

```text
LEVEL1_DCACHE_SIZE                 0
LEVEL1_DCACHE_LINESIZE             64
LEVEL2_CACHE_SIZE                  0
LEVEL3_CACHE_SIZE                  0

NAME ONE-SIZE ALL-SIZE WAYS TYPE        LEVEL SETS PHY-LINE COHERENCY-SIZE
L1d                         Data            1
L1i                         Instruction     1
L2                          Unified         2
```

`LEVEL1_DCACHE_LINESIZE=64` 是真的：这台 VM 的缓存行（cache line，相邻两层之间搬运的最小单位）是 64 字节。但 `SIZE`、`WAYS`、`SETS` 全是 0 或空白。0 不是「没有缓存」，是「这个接口不知道」——虚拟机监控器（hypervisor，把宿主 CPU 切开给多个 guest 的那层软件）没有把缓存拓扑暴露给 guest。`/sys/.../index0/` 下只有 `level`、`type`、`shared_cpu_list` 等属性，没有 `size`。所以「读参数」在这台机器上只能拿到行大小。

对比写作机（macOS 27.2，Apple M5 Pro，arm64）：

```text
hw.perflevel0.l1dcachesize: 131072
hw.perflevel0.l2cachesize: 16777216
hw.perflevel1.l1dcachesize: 65536
hw.cachelinesize: 128
```

这些是字节数：一档核心的 L1 数据缓存 128 KiB、L2 16 MiB；另一档 L1 数据 64 KiB、L2 8 MiB；缓存行 128 字节。同一台机器有两种核心，参数按 `perflevel` 分组——**「这颗 CPU 的 L1 是多少」本身就不是一个单值**。

### 一张表建立量级，但别当规格书

| 层级 | 器件 | 典型容量（x86-64 桌面/服务器） | 典型延迟 | 掉电后 |
|:--|:--|--:|--:|:--:|
| 寄存器 | SRAM | 几百 B–几 KiB | < 1 ns | 丢 |
| L1 | SRAM | 32–48 KiB | ~1 ns（4–5 周期） | 丢 |
| L2 | SRAM | 512 KiB–1 MiB | ~4 ns（12–20 周期） | 丢 |
| L3 | SRAM | 8–32 MiB | ~15 ns（40–70 周期） | 丢 |
| 主存 | DRAM | 16–512 GiB | ~80–100 ns | 丢 |
| SSD | NAND 闪存 | 256 GiB–数 TB | ~20–100 µs（4 KiB 读） | 留 |
| HDD | 磁盘 | 数 TB | ~5–10 ms（随机 4 KiB） | 留 |

这张表是**文档级典型值，不是本机实测**，只用来看数量级：从 L1 到 DRAM 差约 100 倍，从 DRAM 到 SSD 又差约 1000 倍，从 SSD 到 HDD 再差约 100 倍。买机器、做容量规划要看具体型号；写代码时记「每下一层大约差一个数量级」就够了。

表里只列延迟；带宽是另一条轴：顺序大块看带宽，随机小块看延迟和 IOPS。SSD 的顺序读能到 GB/s，但 4 KiB 随机读的瓶颈在 IOPS 和队列深度；HDD 反过来，顺序读靠高密度盘片，随机读被寻道拖垮。

### 为什么 SRAM 快、DRAM 慢、SSD 更慢

SRAM（static random-access memory，静态随机存取存储器）用 6 个晶体管存 1 位，不需要刷新，读写由电路直接完成，所以快；代价是面积大、成本高，只能做小容量。DRAM（dynamic random-access memory，动态随机存取存储器）用 1 个晶体管加 1 个电容存 1 位，电容会漏电，必须周期性刷新；密度高、便宜，但访问要经过行选、列选和读出放大，延迟高一个数量级。

SSD 没有机械部件，但 NAND 闪存有另一套约束：读写的单位是页（常见 4–16 KiB），擦除的单位是块（几百页）；**写之前必须先擦除**，而擦除慢、寿命有限。于是 SSD 内部要做地址映射、垃圾回收和磨损均衡，上层看到的一次 4 KiB 随机写，可能触发多次页搬迁——这就是写放大。HDD 则靠机械臂寻道和盘片旋转：随机访问要等寻道（几毫秒）和旋转（7200 RPM 约 8.3 ms 一圈），顺序访问才能摊薄。

::: def 定义 1.6.1 · 存储层次与缓存行 {#def-1.6.1}
存储层次（memory hierarchy）把不同速度、容量、成本的存储按层组织，每一层都是下一层的缓存：L1 缓存 L2 的内容，L2 缓存 L3，L3 缓存主存，主存缓存磁盘上的文件。缓存行是相邻两层之间搬运的最小单位，这台 VM 是 64 字节，写作机是 128 字节。一次缺失会把整行搬上来，所以行内数据能否被用完，决定这次搬运值不值。
:::

CPU 之外，内核还插了一层：页缓存（page cache，内核用空闲内存缓存文件页）让第二次 `read` 不碰磁盘；目录项缓存（dcache）、inode 缓存（inode 是文件元数据在内存里的那份记录）、块层缓存又各自缓存不同对象。一次 `read` 可能依次命中页缓存 → 文件系统 → 块层 → 设备缓存。缓存也不只数据缓存：TLB（translation lookaside buffer，地址翻译缓存）缓存页表项，uop cache 缓存译码后的指令。第 [1.10](ch10.md) 章会展开页缓存。

### 参数读不到，就量台阶

容量被藏起来，延迟曲线藏不住。用**指针追逐**（pointer chasing，下一次访问的地址由上一次读出的值决定）：CPU 无法提前算地址，硬件预取也插不上手，循环一次就是一次真实访存。程序把 4 KiB 到 64 MiB 的数组按随机置换串成一个环，先走一圈预热，再计时（GCC 13.3，`-O2`，每档取 3 次最好成绩）：

```bash
gcc -O2 -std=c17 lab1c06_chase.c -o lab1c06_chase
for s in 4096 131072 262144 1048576 8388608 16777216 67108864; do
    ./lab1c06_chase $s
done
```

这台 VM 上实测：

| 工作集 | 每次访存 | 相对 4 KiB |
|:--|--:|--:|
| 4 KiB | 1.07 ns | 1.0 |
| 128 KiB | 1.06 ns | 1.0 |
| 256 KiB | 2.32 ns | 2.2 |
| 1 MiB | 4.79 ns | 4.5 |
| 8 MiB | 15.04 ns | 14.1 |
| 16 MiB | 78.19 ns | 73.1 |
| 64 MiB | 134.42 ns | 125.6 |

曲线有三个平台：4–128 KiB 都在 1 纳秒附近，这是 L1；256 KiB–8 MiB 从 2.3 爬到 15 纳秒，这是 L2；16 MiB 以上跳到 78–134 纳秒，这是 DRAM。参数表里 `SIZE=0`，但台阶把层级说清楚了。**注意这是这台 VM 的数，不是定律**：换一台机器，拐点会挪，平台高度会变；同机不同次测量也会差几个百分点（1.1.21 在同一 VM 上量到 64 MiB 约 129–132 ns）。能复用的是「看拐点判断层级」这个方法。

::: errata 关于存储参数的误解
1. **「`getconf` 返回 0 就是没有缓存」**——0 表示接口不知道。虚拟机、容器或老内核都可能拿不到拓扑；这时读 `/sys` 也可能只有 `level` 和 `type`。
2. **「L1 一定是 32 KiB、缓存行一定是 64 字节」**——x86-64 常见 32–48 KiB 和 64 B，但 Apple M5 Pro 的 L1 数据缓存按核心档位是 64 KiB 或 128 KiB，行大小 128 B。写死这些数字的代码换机器就会错。
3. **「SSD 没有寻道，所以随机读和顺序读一样快」**——SSD 没有机械寻道，但仍有页/块粒度、FTL 映射、垃圾回收和读放大；4 KiB 随机读的 IOPS 远高于 HDD，顺序大块读的吞吐通常仍是随机读的数倍。
4. **「DRAM 延迟就是 100 纳秒」**——它随频率、通道数、NUMA 远近和虚拟化变化；本机 64 MiB 工作集量到 134 ns，另一台机器可能是 80 ns。
:::

::: ex 例 1.6.1 · 先猜台阶从哪来 {#ex-1.6.1}
同一台 VM，4 KiB 工作集 1.07 ns/次，64 MiB 工作集 134.42 ns/次。先猜：把数组从 4 KiB 改成 64 MiB，慢的倍数更接近 10、100 还是 1000？如果 `getconf` 说 L1 是 0 字节，这个倍数还测得到吗？

::: sol 解答
$134.42 / 1.07 \approx 126$，接近 100 倍。`getconf` 为 0 只说明接口拿不到容量，不影响硬件行为；指针追逐仍然会在工作集超过 L1 时变慢，在超过 L2 时再跳一级。倍数不是定律：换一台机器可能只有 40 倍或 200 倍，但「跨一层差一个数量级」的形状通常还在。
:::
:::

### 1.6.1 小结

① 每一层都是下一层的缓存，快、小、贵与慢、大、便宜必须配对；② SRAM 靠晶体管、DRAM 靠电容刷新、SSD 靠页读写块擦除、HDD 靠机械运动，差异来自器件而不是软件；③ 参数可以被虚拟化藏起来，但指针追逐量出的台阶不会说谎。如果只记住一件事，那就是：**先看工作集落在哪个平台，再谈一次访存要多久。**

::: method 即时自测 · 1.6.1
**Q1（记忆）** SRAM 与 DRAM 各用几个器件存 1 位？为什么 DRAM 需要刷新？

**Q2（辨析）** 这台 VM 的 `getconf LEVEL1_DCACHE_SIZE` 是 0，但指针追逐在 4 KiB 工作集上只要 1.07 ns。这两件事矛盾吗？

**Q3（应用）** 一台机器上 64 MiB 指针追逐是 134 ns/次，4 KiB 是 1.07 ns/次。估算慢多少倍，并说明这个倍数能不能直接搬到另一台机器。

**Q4（迁移）** 你要在 VM 里判断「L2 大概多大」，但 `getconf` 全是 0。写出测量方案：改哪个变量、看曲线的什么特征、为什么不能用顺序扫描。

::: sol 答案
**A1** SRAM 用 6 个晶体管存 1 位，不需要刷新；DRAM 用 1 个晶体管加 1 个电容，电容漏电，必须周期性刷新。
**A2** 不矛盾。0 是「接口不知道」，不是「没有缓存」。延迟是硬件真实行为，1.07 ns 说明 4 KiB 工作集落在 L1；容量参数只是没暴露。
**A3** $134.42 / 1.07 \approx 126$ 倍。不能直接搬：拐点位置、平台高度、CPU 频率和虚拟化都不同；能搬的是「跨层大约一个数量级」这个形状。
**A4** 固定指针追逐程序，只改工作集大小（4 KiB 到 64 MiB），画「工作集–ns/次」曲线；平台结束、延迟开始爬升的拐点就是该层容量。不能用顺序扫描，因为预取和带宽会把延迟藏起来，量到的是吞吐而不是层级。
:::
:::

## 1.6.2 局部性：时间与空间 {#sec-1.6.2}

这一节回答：同一份数据、同样多的加法，为什么只交换两层循环的顺序，时间就差 6 倍？

::: preview 先抓住一件事
缓存不是「记住所有东西」，它赌你接下来会用到刚用过的东西，或者它旁边的地址。这个赌注叫局部性（locality）。赌对了，1 纳秒就够；赌错了，一次访存要等 100 纳秒。本机实测：32 MiB 矩阵按行 2.6–2.9 ms、按列 14.4–17.2 ms，约 5–6.5 倍；同一份 64 MiB 数据，顺序扫描 0.316 ns/元素，指针追逐 134 ns/次，差约 425 倍。
:::

### 同一份矩阵，两种走法

`double a[2048][2048]` 占 $2048^2 \times 8 = 32$ MiB。下面这个程序只做两件事：按行求和、按列求和。两边都要加 419 万个 `double`，加法次数完全一样：

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <time.h>
#define N 2048
static double a[N][N];
static double now(void) {
    struct timespec t; clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec + t.tv_nsec / 1e9;
}
int main(void) {
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++) a[i][j] = (double)(i + j) / N;
    double s = 0, t0 = now();
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++) s += a[i][j];      /* 行优先 */
    double t1 = now();
    for (int j = 0; j < N; j++)
        for (int i = 0; i < N; i++) s += a[i][j];      /* 列优先 */
    double t2 = now();
    printf("32 MiB matrix: row %.1f ms  col %.1f ms  ratio %.2f  sum %.0f\n",
           (t1 - t0) * 1e3, (t2 - t1) * 1e3, (t2 - t1) / (t1 - t0), s);
    return 0;
}
```

在这台 VM 上编译运行（GCC 13.3，`-O2`；两次分别绑到 `cpu0` 和 `cpu1`，各取 3 次最好成绩）：

```text
$ taskset -c 0 ./lab1c06_locality
32 MiB matrix: row 2.9 ms  col 14.4 ms  ratio 4.98  sum 8384512
$ taskset -c 1 ./lab1c06_locality
32 MiB matrix: row 2.7 ms  col 17.2 ms  ratio 6.29  sum 8384512
```

`sum` 只是防止编译器把循环优化掉，具体值随浮点舍入可能差一点；要看的是 row、col 和 ratio。

行优先时，最内层 `j` 每次加 1，地址加 8 字节，一个 64 B 行装 8 个 `double`，8 次访问只用取一次；列优先时，最内层 `i` 每次加 1，地址却加 $2048 \times 8 = 16$ KiB，每取一个元素就换一行，行里另外 7 个 `double` 要等下一轮列循环才用到，那时早被挤出去了。理论上缺失比是 8:1；实测约 5–6.5 倍（单次运行在 4.5–7.7 之间波动），不是整整 8 倍：行优先那一路也有强制性缺失，列优先那一路的固定步长可能被预取器部分识别，L2/L3 也会接住一部分。

### 局部性到底在赌什么

**时间局部性**（temporal locality）：刚访问过的地址，很可能很快再次访问。循环里的累加变量、反复调用的热函数都是这一类；缓存让同一个块多待一会儿。

**空间局部性**（spatial locality）：一个地址被访问，它旁边的地址很可能也要用。顺序遍历数组、顺序执行指令都是这一类；缓存行一次搬一整块，就是为了让块内剩下的字节也被用完。

**工作集**（working set）是你在一段时间内反复访问的数据量，它决定你落在哪一层；**步长**（stride）是相邻两次访问的地址差，它决定一个缓存行能被用几次。4 KiB 工作集和 128 KiB 工作集都在 L1 里，1 ns 上下；一旦工作集越过 L2，数字就跳到几十纳秒。不是「数组越大越慢」，是「工作集跨过了哪条线」。

在这台 VM 上，同一份 64 MiB 数据还能做另一个对照：顺序整型累加只要 0.316 ns/元素（2.6 ms 扫完 838 万个 8 字节整数），指针追逐要 134.42 ns/次，差约 425 倍。两边搬的字节数一样，差别只在访问顺序：顺序时预取器把下一行提前拉来；指针追逐时下一次地址要等上一次结果，预取器无从下手。

::: ex 例 1.6.2 · 先猜差几倍 {#ex-1.6.2}
缓存行 64 B，`double` 8 B，行优先每个块用 8 次，列优先每个元素换一行。先猜：列优先应该比行优先慢几倍？实测只有 5–6.5 倍，为什么不是整整 8 倍？

::: sol 解答
按「每个块被用几次」算，理论上行优先 8 次访问摊 1 次缺失，列优先 1 次访问摊 1 次缺失，缺失比 8:1，所以先猜 8 倍。实测更低，因为行优先那一路也有第一次访问的强制性缺失，列优先那一路的 16 KiB 固定步长可能被硬件预取器部分识别，部分数据还能落在 L2/L3；另外计时包含循环开销。**倍数由「缺失次数 × 缺失代价」共同决定，不能只数缺失次数。**
:::
:::

::: errata 关于局部性的误解
1. **「列优先就是完全随机访问」**——它有固定步长 16 KiB，仍是一种空间模式；只是每取一个元素就换一行，缓存行里的其余 7 个 `double` 用不上。预取器能帮一点，但帮不完。
2. **「数组越大越慢」**——在这台 VM 上，4 KiB 和 128 KiB 的工作集都在 L1，实测都是 1 ns 上下；变慢发生在工作集跨过 L1/L2/DRAM 的容量线时。
3. **「局部性只对数组有用」**——链表、哈希表、代码本身也有局部性。随机分布的链表节点每次跳到一个新行，是指针追逐最坏的形状；把节点改成池式分配、按访问顺序重排，能明显改善。
4. **「行优先永远最快」**——C 是行主序，Fortran/BLAS 是列主序；规则不是「i 在外层」，而是「最内层沿着内存连续的方向走」。
5. **「预取能消掉列优先的代价」**——预取提高的是带宽和在途量，不能消除「下一次访问要等当前行」的延迟；本机实测仍差约 5–6 倍。
:::

### 1.6.2 小结

① 局部性分时间与空间：前者让同一个块多待一会儿，后者让一次搬块覆盖多次访问；② 同一份 32 MiB 矩阵只换循环顺序就差约 5–6.5 倍，同一份 64 MiB 数据顺序扫描与指针追逐差约 425 倍；③ 决定性能的是工作集跨过哪条容量线、步长浪费了多少行内数据。如果只记住一件事，那就是：**先问相邻两次访问挨不挨着，再问数据有多少。**

::: method 即时自测 · 1.6.2
**Q1（记忆）** 时间局部性和空间局部性各说什么？缓存行主要利用哪一条？

**Q2（辨析）** 同一台 VM 上，矩阵行/列只差约 6 倍，顺序扫描与指针追逐却差约 425 倍。两个倍数为什么差这么多？

**Q3（应用）** 一个 100 万节点的链表，节点随机分布，工作集 64 MiB。给出三种改善局部性的改法，并说明各自改变了什么。

**Q4（迁移）** 你接手一段 Fortran 风格的矩阵代码，数组按列主序存放。最内层循环应该沿哪个下标走？先用什么办法确认布局？

::: sol 答案
**A1** 时间局部性：刚访问过的地址很可能再次访问；空间局部性：一个地址被访问，相邻地址很可能也被访问。缓存行利用空间局部性。
**A2** 矩阵行/列仍是同一个数组，列优先只浪费行内 7 个元素，缺失比约 8:1；指针追逐每次跳到一个新行，且下一次地址依赖上一次结果，预取器完全失效，所以接近「每次访存都等 DRAM」，差距被放大到几百倍。
**A3** ① 把节点改成数组或池式分配，让地址连续；② 按访问顺序重排节点（需要额外一遍预处理）；③ 把热字段抽出来做 SoA（把结构体数组拆成按字段的数组），减小每个节点占用的行数。三者都在减少「每次访问换一行」。
**A4** 沿列下标（Fortran 的第一个下标变化最快，内存连续）。确认布局：打印相邻元素的地址差，或看语言/库文档；不要凭 C 的行主序直觉套上去。
:::
:::

## 1.6.3 缓存组织：组相联与地址拆分 {#sec-1.6.3}

这一节回答：一个 32 KiB 的缓存，怎么用一个 32 位地址判断「这个数在不在」？为什么地址要被切成三段？

::: preview 先抓住一件事
缓存不是一张「地址→数据」的大表，而是一个二维数组：组 × 路。地址的低位选块内偏移，中间位选组，高位当标签去比对。三个参数 $S$（组数）、$E$（每组路数）、$B$（块大小）决定容量，也决定冲突怎么发生；相联度就是「多留几条路」与「多一套比较器」之间的交换。
:::

### 三个参数，三段地址

一个组相联缓存用三个参数描述：$S$ 组（sets）、每组 $E$ 路（ways，相联度）、每块 $B$ 字节（缓存行）。总容量是

$$
C = S \times E \times B .
$$

一个 $m$ 位的地址被切成三段：低位 $b$ 位是块内偏移（offset），接着 $s$ 位是组索引（index），剩下 $t$ 位是标记（tag）：

$$
\underbrace{\text{tag}}_{t}\ \underbrace{\text{index}}_{s}\ \underbrace{\text{offset}}_{b},
\qquad s = \log_2 S,\quad b = \log_2 B,\quad t = m - s - b .
$$

<pre class="layout">
32 位地址，S=64 组，E=8 路，B=64 B：
 31                          12 11          6 5          0
┌──────────────────────────────┬──────────────┬────────────┐
│          tag (20 bit)        │ index (6 bit)│ offset (6) │
└──────────────────────────────┴──────────────┴────────────┘
组 23 ┌──────┬──────┬──────┬─────┬──────┐
      │ way0 │ way1 │ way2 │ ... │ way7 │  每路：valid + tag + 64 B 数据
      └──────┴──────┴──────┴─────┴──────┘
</pre>

一次访问分三步：先用 index 选中一个组；再把 tag 与该组所有路的 tag 并行比较，同时检查 valid 位；任一匹配就是命中，用 offset 取出块内字节，全不匹配就是缺失，从下层取整块，再挑一路替换。

**为什么 index 取中间位？** 最低的 $b$ 位在一个块内变化，必须留给 offset；最高的 $t$ 位变化最慢，如果拿它们当 index，一大片相邻的块会挤进同一个组，冲突会非常严重。中间这 $s$ 位每过一个块才加 1，正好把连续的块摊到不同组里。

::: ex 例 1.6.3 · 先猜落在第几组 {#ex-1.6.3}
32 位地址空间，缓存 32 KiB、8 路、64 B 块。地址 `0x0000A5C8` 的 offset、index、tag 各是多少？先心算再往下看。再把缓存换成 32 KiB 直接映射（$E=1$），同一个地址落在第几组？

::: sol 解答
先算参数：$S = 32768 / (8 \times 64) = 64$，所以 $s=6$，$b=6$，$t=32-6-6=20$。

- offset：`0xA5C8 & 0x3F = 0x08`，即 8；
- index：`(0xA5C8 >> 6) & 0x3F = 0x17`，即 23；
- tag：`0xA5C8 >> 12 = 0xA`，即 10。

所以它落在第 23 组、块内偏移 8、标记 10。若第 23 组某路的 valid=1 且 tag=0xA，命中；否则缺失。

直接映射时 $S = 32768 / 64 = 512$，$s=9$，$b=6$，$t=17$。同一个地址：offset 仍是 8，index 变成 `(0xA5C8 >> 6) & 0x1FF = 0x97`（151），tag 变成 `0xA5C8 >> 15 = 1`。**同一个地址，缓存几何一换，三段的位置和宽度全变了。**
:::
:::

### 元数据不是免费的

32 KiB、8 路、64 B 的缓存有 $64 \times 8 = 512$ 个块。每块要存 20 位 tag、1 位 valid、写回时还要 1 位 dirty，按位算是 $512 \times 22 = 11{,}264$ 位 $= 1{,}408$ 字节，约占 32 KiB 的 4.3%。这还没算 LRU/伪 LRU 的年龄位、ECC 和阵列外围电路。**32 KiB 是数据数组的容量，整块 SRAM 比它大**。

相联度是折中：$E=1$ 是直接映射（direct-mapped），每组只有一条路，比较器最省，但两个块争同一组时必然互相驱逐；$S=1$ 是全相联（fully associative），任何块可以放任何位置，冲突最少，但每一路都要比较器，容量做不大，通常只用于 TLB 这类很小的结构。8 路、16 路是 L1/L2 常见的折中。

### 在你的机器上能读到什么

在 `ubuntu24` 上：

```bash
getconf LEVEL1_DCACHE_LINESIZE   # 实测 64
getconf LEVEL1_DCACHE_SIZE       # 实测 0
lscpu -C                         # 实测只列 L1d/L1i/L2，WAYS/SETS 空白
```

行大小 64 B 是真的；容量、相联度、组数都被虚拟化藏了，算不出 $S$。写作机（Apple M5 Pro）能读到一档 L1 数据缓存 128 KiB（另一档 64 KiB）、行大小 128 B，但相联度同样没暴露；如果**假设** 8 路，才有 $S = 131072 / (8 \times 128) = 128$，$s=7$，$b=7$，$t=18$。这个 128 组是假设推出来的，不是读出来的——**三个参数缺一个，地址就拆不完整**。

::: def 定义 1.6.2 · 组相联缓存（set-associative cache） {#def-1.6.2}
每组有 $E$ 路的缓存。地址的 index 选中组，tag 与组内 $E$ 个 tag 并行比较；任一匹配且 valid 则命中。$E=1$ 是直接映射，$S=1$ 是全相联。相联度是「冲突缺失」与「硬件成本/命中延迟」的折中。
:::

::: errata 关于地址拆分的误解
1. **「index 就是地址最低的几位」**——最低的 $b$ 位是块内 offset；index 是紧接着的 $s$ 位。把两者弄反，算出的组号会全错。
2. **「tag 存的是完整地址」**——tag 只存剩下的高位；index 和 offset 由地址本身提供，不需要重复存。
3. **「相联度越高越好」**——相联度降低冲突缺失，但比较器、命中延迟和功耗都上升；全相联只适合很小的结构。
4. **「32 KiB 缓存就有 32 KiB 数据」**——数据数组是 32 KiB，tag/valid/dirty 还要占约 4.3%，真实 SRAM 更大。
5. **「`getconf` 读不到容量就没法分析」**——可以量延迟曲线，也可以查 CPU 型号的文档；但要知道哪些数字是读出来的、哪些是假设的。
:::

### 1.6.3 小结

① 缓存由 $S$、$E$、$B$ 三个参数定死，容量 $C=S \times E \times B$；② 地址按 offset、index、tag 从低到高切，index 取中间位是为了把连续块摊开；③ 相联度是冲突与成本的折中，参数读不全时不要把假设当实测。如果只记住一件事，那就是：**先算 $S$ 和 $B$，再谈一个地址落在哪一组。**

::: method 即时自测 · 1.6.3
**Q1（记忆）** 写出 $C$、$s$、$b$、$t$ 四个公式，并说明 $m$ 是什么。

**Q2（辨析）** 为什么 index 不取地址最低位，也不取最高位？

**Q3（应用）** 64 KiB、4 路、64 B 块、32 位地址：求 $S$、$s$、$b$、$t$，并算出 `0x0000A5C8` 的组号和 tag。

**Q4（迁移）** 容量不变，把相联度从 4 路加倍到 8 路：$S$、$s$、$t$ 各怎么变？冲突缺失和比较器数量各怎么变？

::: sol 答案
**A1** $C=S \times E \times B$；$s=\log_2 S$；$b=\log_2 B$；$t=m-s-b$，$m$ 是地址位数。
**A2** 最低位在块内变化，必须留给 offset；最高位变化最慢，拿来当 index 会让相邻的块挤进同一组，冲突严重。中间位每块加 1，能把连续块摊到不同组。
**A3** $S=65536/(4 \times 64)=256$，$s=8$，$b=6$，$t=18$。offset 8，index 151，tag 2。
**A4** 容量不变时 $S$ 减半，$s$ 减 1，$t$ 加 1；冲突缺失下降，比较器数量翻倍；每个块的 tag 多 1 位，tag 存储略增。
:::
:::

## 1.6.4 命中、缺失、替换与写策略 {#sec-1.6.4}

这一节回答：一次访存怎么判命中？没命中时，缓存满了换谁？写操作要不要先把块读进来？多核同时写同一行又会怎样？

::: preview 先抓住一件事
命中只查两件事：这一路的 valid 是不是 1，tag 是不是和地址高位相同。没命中分三类：第一次、冲突、容量。真正拖慢程序的是缺失代价：本机 L1 1.07 ns、DRAM 134 ns，差 125 倍；按本机端点估算，缺失率从 1% 涨到 10%，AMAT 就从 2.4 ns 涨到 14.5 ns。写策略和多核一致性，都是在这笔账上做取舍。
:::

### 命中只看两件事

一个组里有 $E$ 路，每路有 valid 位、tag 和数据。命中（hit）就是：index 选中的组里，至少有一路 valid=1 且 tag 与地址高位相等；缺失（miss）就是一路都没有。命中时用 offset 取块内字节；缺失时从下一层搬整块，再挑一路替换。tag 是并行比较的——$E$ 路同时比，这也是相联度越高、命中延迟越大的原因。

缺失不是一种原因。按「换成同样容量的全相联缓存后还会不会缺」来分，有三类（3C）：

| 类型 | 原因 | 能否避免 | 典型对策 |
|:--|:--|:--|:--|
| 强制性（compulsory） | 第一次访问，缓存里必然没有 | 不能，只能预取 | 预取、增大块 |
| 冲突性（conflict） | 多个块映射到同一组，互相驱逐 | 能 | 提高相联度、改变布局 |
| 容量性（capacity） | 工作集大于缓存 | 能（减小工作集） | 分块、压缩、SoA |

SoA（structure of arrays）是把「结构体数组」拆成「按字段的数组」：只频繁访问某几个字段时，不必把整个结构体搬进缓存。区分方法是同一访问序列跑不同容量、不同相联度的模拟器；容量变大后消失的是容量性，相联度变大后消失的是冲突性，怎么变都消失不了的是强制性。

::: def 定义 1.6.3 · 三类缺失（3C） {#def-1.6.3}
强制性缺失：块第一次被访问，缓存里必然没有。冲突性缺失：块本身还在缓存容量内，但被映射到同一组的其他块挤掉了；换成全相联同容量缓存就会命中。容量性缺失：工作集大于缓存，即使全相联也装不下。三类按「全相联同容量下是否仍缺失」划分，不重不漏。
:::

::: ex 例 1.6.4 · 先猜命中几次 {#ex-1.6.4}
一个 2 组、每组 1 路、64 B 行的缓存（总共 128 B），依次访问块首地址 `0x000`、`0x040`、`0x080`、`0x000`、`0x040`。先猜 5 次里有几次命中；再把每组改成 2 路，猜命中几次。

::: sol 解答
index 取地址第 6 位（`0x40` 那一位），tag 是更高位。

直接映射：`0x000` 组 0/tag 0 缺；`0x040` 组 1/tag 0 缺；`0x080` 组 0/tag 1 缺，挤掉 `0x000`；`0x000` 组 0/tag 0 缺，挤掉 `0x080`；`0x040` 组 1/tag 0 命中。**1 次命中、4 次缺失。**

2 路：组 0 能同时放 tag 0 和 tag 1，组 1 放 tag 0；前两次缺失后，后三次全命中，**2 次缺失、3 次命中**。两块数据本来装得下 128 B 缓存，直接映射却因为挤在同一组丢了两次——这就是冲突缺失。
:::
:::

### 平均访问时间：把命中率和代价乘起来

把命中时间和缺失代价合成一个数，就是平均访问时间（average memory access time，AMAT）：

$$
\text{AMAT} = \text{hit time} + \text{miss rate} \times \text{miss penalty}.
$$

用本机两个端点估算：hit time 取 1.07 ns，miss penalty 按 134 ns 算。缺失率 1% 时，AMAT $= 1.07 + 0.01 \times 134 = 2.41$ ns；缺失率 10% 时，AMAT $= 1.07 + 0.1 \times 134 = 14.51$ ns。**缺失率每降一个百分点，省下 1.34 ns，比命中时间本身还多。** 这是估算，不是实测：真实缺失代价还包括传输、排队和写回，缺失率也不会均匀分布；多级缓存要把公式嵌套，L1 的 miss penalty 是 L2 的 AMAT。

这笔账解释了两件事：把 L1 命中时间从 1.07 ns 优化到 0.9 ns，收益不到 0.2 ns；把缺失率从 10% 降到 1%，收益是 12 ns。所以分块、改布局、减少工作集，常常比换更快的内存更划算。

### 组满了换谁

替换策略决定「组满了换哪一路」：

- **LRU**（least recently used，最近最少使用）：换最久没被访问的路。命中率高，但每一路都要记年龄，真 LRU 的硬件成本高；实际多用伪 LRU（树形、时钟）近似。
- **随机**：不记历史，随机挑一路。实现最简单，高相联度下平均表现不差。
- **FIFO**（first in, first out，先进先出）：按进入顺序换，可能把热点行换走，较少单独使用。

没有哪种策略在所有访问序列上都最好。理论上的最优策略（Belady）要预知未来，只能当上界；硬件选策略看的是成本、可预测性和最坏情况。

### 写：先改缓存还是直接写下层

写命中时有两种做法。**写穿透**（write-through）每次写都更新缓存和下一层，简单、不需要 dirty 位，但流量大；**写回**（write-back）只改缓存并置 dirty 位，等这一路被驱逐时才写回下一层，流量小，但需要 dirty 位和一致性协议。典型 L1/L2 用写回。

写缺失时也有两种做法。**写分配**（write-allocate）先把块读进缓存再改；**非写分配**（no-write-allocate）直接写到下一层，不占缓存。写回通常配写分配，写穿透常配非写分配。

写回 + 写分配有一个副作用：对一个没在缓存里的地址写 1 个字节，也要先把整行读进来，这叫 RFO（read-for-ownership，写前先取得这一行的所有权）。对「写一次、不再读」的大数组，RFO 白搬了整行；非临时存储（non-temporal store）可以绕过缓存直接写内存，适合这种流式写。x86 与 ARM64 都有对应指令或提示，名字随架构不同。

还要区分**持久化**：写回缓存是易失的，脏数据在掉电时会丢；`fsync`/`fdatasync` 把文件数据推到存储设备，才算落盘。缓存一致性只保证多核看到同一份数据，不保证断电后还在。

### 多核：同一行归谁

多核还要维护**缓存一致性**（cache coherence，保证一个核的写最终能被其他核看到）。MESI 是常见协议，每行处于四个状态之一：

| 状态 | 含义 | 本地读 | 本地写 |
|:--|:--|:--|:--|
| M（Modified） | 本核独占，已修改，内存副本是旧的 | 命中 | 直接写 |
| E（Exclusive） | 本核独占，干净 | 命中 | 转 M，无总线事务 |
| S（Shared） | 多个核共享，干净 | 命中 | 先让其他副本失效，再转 M |
| I（Invalid） | 本核副本无效 | 缺失，向总线/内存取 | 先取得独占权，再写 |

关键是**写之前必须拿到独占权**。两个线程写同一行的不同变量时，行在两个核之间来回弹，叫伪共享（false sharing，逻辑上不共享数据，却共享同一缓存行）。修法是让热变量各占一行：

```c
#include <stdalign.h>
struct counters {
    alignas(64) long a;
    alignas(64) long b;
};
```

代价是 8 字节的变量占 128 字节。高频写的计数器值得；只读或低频的结构不值得。`perf c2c` 能统计 cache-to-cache 迁移，但这台 VM 的 `perf` 普通账户读不到硬件计数（`perf_event_paranoid=4`，`perf stat` 只报 `<not supported>`），本机未实测；没有 `perf` 时，用「放一起/分开」两版程序的墙钟时间对比。MESI 只是一个例子，真实 CPU 还有 MOESI、MESIF 等变体；这里只要记住：写要独占，伪共享按行发生。

::: errata 关于命中、替换与写的误解
1. **「命中率越高一定越快」**——要看 AMAT：命中率高但缺失代价极大的缓存，可能输给命中率略低、缺失代价小的组合。先算账，再谈命中率。
2. **「硬件用的是真 LRU」**——高相联度下真 LRU 的年龄位和更新逻辑太贵，常见的是伪 LRU（树形、时钟），它只是近似。
3. **「写回会丢数据，所以都用写穿透」**——写回的脏数据在掉电时确实会丢，但写穿透也不能保证落盘；持久化要靠 `fsync` 一类的接口。写回因为流量小，仍是 L1/L2 的主流。
4. **「写分配总是更好」**——写分配会让「写一次、不再读」的流式写先做 RFO，白搬整行；这种场景用非写分配或非临时存储更合适。
5. **「伪共享是逻辑错误」**——它不影响结果正确性，只影响性能；变量逻辑上独立，却因为共享缓存行而互相拖慢。
6. **「`perf c2c` 一定能查伪共享」**——它需要 PMU（performance monitoring unit，性能监控单元）和权限；这台 VM 的 `perf_event_paranoid=4`，`perf stat` 只报 `<not supported>`，本机未实测。
:::

### 1.6.4 小结

① 命中只看 valid 和 tag，缺失按 3C 分类；② AMAT 把命中时间与缺失代价乘起来，缺失率的小变化会被 100 倍的代价放大；③ 替换策略是成本与命中率的折中，写策略要同时选「写穿/写回」和「写分配/非写分配」；④ 多核写同一行要先拿独占权，伪共享按缓存行发生。如果只记住一件事，那就是：**先问这次缺失属于哪一类，再问这笔代价由谁付。**

::: method 即时自测 · 1.6.4
**Q1（记忆）** 3C 各是什么？哪一类无法避免，哪两类可以通过改变缓存或程序来减少？

**Q2（辨析）** 本机 hit time 1.07 ns、miss penalty 按 134 ns 算。缺失率 1% 和 10% 的 AMAT 各是多少？为什么说「降一个百分点的缺失率」比「把命中时间减半」更值？

**Q3（应用）** 一个循环交替访问 `p` 和 `p + 4096`。缓存 32 KiB、8 路、64 B 行。它们会落到同一组吗？如果互相驱逐，给出两种改法。

**Q4（迁移）** 两个线程各写 `struct { long a; long b; }` 的 `a` 和 `b`，程序正确但很慢。解释原因、给出改法，并说明没有 `perf` 时怎么验证改法有效。

::: sol 答案
**A1** 强制性：第一次访问，无法避免；冲突性：多个块映射到同一组，可通过提高相联度或改布局减少；容量性：工作集大于缓存，可通过分块、压缩、减小工作集减少。
**A2** 1% 时 $1.07 + 0.01 \times 134 = 2.41$ ns；10% 时 $1.07 + 0.1 \times 134 = 14.51$ ns。降一个百分点省 1.34 ns，而把 1.07 ns 的命中时间减半只省约 0.5 ns，所以前者更值。
**A3** 会。两者相差 4096 B，index 位相同，落到同一组；8 路下如果还有别的冲突也会互相驱逐。改法：给其中一个数组加 64 B 的填充错开组号；或把循环改成先批量读 `p`、再批量读 `p+4096`；提高相联度也有效，但要看硬件是否允许。
**A4** `a` 和 `b` 在同一缓存行，两个核写同一行会让行来回弹（伪共享）。改法：用 `alignas(64)` 让 `a`、`b` 各占一行，或每个线程用局部变量最后合并。没有 `perf` 时，跑「紧挨着」和「分开」两版，比较多轮墙钟时间；分开版稳定更快就说明有效。
:::
:::

## 1.6.5 矩阵乘与分块：把缺失算清楚 {#sec-1.6.5}

这一节回答：同一个三重循环，只把 `j` 和 `k` 换个位置，1024 阶矩阵乘就从 1579 ms 掉到 301 ms；把边长从 1024 改成 1000，`ijk` 又从 1579 ms 掉到 638 ms。这两次变快，各自省掉了什么？

::: preview 先抓住一件事
缺失数可以先手算，再拿机器核对：内层循环每跨进一个没见过的缓存行，就记一次缺失。`ijk` 沿 `B` 的列走，每一步都换行，缺失约 $N^3$；`ikj` 沿 `B` 的行走，每 8 个 `double` 才换一行，缺失约 $N^3/8$。实测两者差 5.2 倍，方向对上了，倍数没对上——时间还受算力和带宽限制。分块能把工作集压进缓存，但前提是它本来装不下；装得下时，分块几乎白干。
:::

### 先把两个版本跑出来

矩阵用一维数组模拟行主序：`A[i*n+k]` 就是 $A_{ik}$。两个函数只差最内层循环走哪一维：

```c
/* ijk：内层沿 B 的列走，地址每步跳 n*8 字节 */
for (size_t i = 0; i < n; i++)
    for (size_t j = 0; j < n; j++) {
        double s = 0.0;
        for (size_t k = 0; k < n; k++)
            s += A[i * n + k] * B[k * n + j];
        C[i * n + j] = s;
    }

/* ikj：内层沿 B、C 的行走，地址连续 */
memset(C, 0, n * n * sizeof *C);
for (size_t i = 0; i < n; i++)
    for (size_t k = 0; k < n; k++) {
        double a = A[i * n + k];
        for (size_t j = 0; j < n; j++)
            C[i * n + j] += a * B[k * n + j];
    }
```

在 `ubuntu24`（4 vCPU aarch64，GCC 13.3，`-O2`）上各跑三次取最好成绩，实测：

```bash
gcc -O2 -std=c17 matmul.c -o matmul
./matmul 1024 ijk    # 实测 best-of-3
./matmul 1024 ikj    # 实测 best-of-3
```

| 版本 | $N=1000$ | $N=1024$ |
|:--|--:|--:|
| `ijk`（`k` 在内层） | 638.1 ms | 1579.3 ms |
| `ikj`（`j` 在内层） | 284.3 ms | 301.3 ms |

这张表有两处可比：同一行横着看，`ijk` 比 `ikj` 慢 5.2 倍；同一列竖着看，`ijk` 在边长变小、活变少之后反而快了 2.5 倍。第二处更蹊跷，留到最后用组号算术解释。

总浮点运算是 $2N^3 \approx 2.15$ GFLOP。`ikj` 用 301 ms 跑完，相当于 7.1 GFLOPS——已经贴着这台机器单核的算力上限。所以 301 ms 不是「内存已经很快」，而是「处理器算满了」，这也解释了为什么再优化缓存对它帮助有限。

### 手算：内层每换一个块，就记一次缺失

$B_{kj}$ 的地址是 $k \times 8N + j \times 8$ 字节。`ijk` 的内层走 $k$：每次跳 $8N$ 字节，$N=1024$ 时是 8192 B，远大于 64 B 的行，所以每读一个 $B_{kj}$ 都落在新行上。内层 $N$ 次，就有 $N$ 次缺失；外层 $N^2$ 次，共 $N^3$ 次。$A$ 那一侧沿 $k$ 连续，每行用 8 次，摊到 $N^3/8$。合计约 $1.1N^3$。

`ikj` 的内层走 $j$：`B` 与 `C` 都按行连续，各自每 8 个 `double` 一次缺失，各 $N^3/8$；$A_{ik}$ 提到寄存器里，只在外层读 $N^2/8$ 次。这里有个容易算错的地方：$C$ 的行只有 8 KiB，在内层被反复写，写完就留在 L1 里，真正缺的只有第一次碰它的 $N^2/8$ 次，不是 $N^3/8$ 次。于是 `ikj` 的缺失主要来自 $B$，约 $N^3/8$。

两者之比 $N^3 / (N^3/8) \approx 8$。墙钟只有 5.2 倍，差额来自两件事：一是 `ikj` 已经撞到算力上限，缺失再少也快不下去；二是缺失会重叠——多个缺失同时在途时，单次代价被摊薄。

### 分块：把工作集压进缓存

块内三个子矩阵同时被碰：$3B_s^2$ 个 `double`。要把它装进 32 KiB 的 L1（按典型桌面参数估算；这台 VM 读不到容量，见 1.6.1）：

$$
3B_s^2 \times 8 \le 32 \times 1024 \Rightarrow B_s^2 \le 1365 \Rightarrow B_s \le 36 .
$$

若目标换成 512 KiB 的 L2，上限放宽到 $B_s \le 147$。取 $B_s=32$，工作集 24 KiB，块内 `A` 的一行、`B` 的一块、`C` 的一块反复复用。代码形状是 `ii-kk-jj-i-k-j`：

```c
for (size_t ii = 0; ii < n; ii += bs)
  for (size_t kk = 0; kk < n; kk += bs)
    for (size_t jj = 0; jj < n; jj += bs)
      for (size_t i = ii; i < ii + bs && i < n; i++)
        for (size_t k = kk; k < kk + bs && k < n; k++) {
            double a = A[i * n + k];
            for (size_t j = jj; j < jj + bs && j < n; j++)
                C[i * n + j] += a * B[k * n + j];
        }
```

最内层 `j` 连续访问 `B` 与 `C`，`a` 提到寄存器，块内三块数据反复复用。在同一个 $N=1024$ 上扫块大小，两次运行各取 best-of-3，实测：

| $B_s$ | 第一次 | 第二次 |
|:--|--:|--:|
| 16 | 480.1 ms | 425.1 ms |
| 32 | 335.6 ms | 330.9 ms |
| 48 | 370.9 ms | 304.6 ms |
| 64 | 383.4 ms | 318.5 ms |
| 128 | 374.9 ms | 326.9 ms |
| 256 | 376.8 ms | 343.3 ms |

两点读法。同一档两次运行能差 10–20%，所以只看趋势，不追单点。32 到 256 都落在 300–385 ms，和 `ikj` 的 301 ms 打平，没有更快。

原因不在代码写得不好，在前提不成立：$N=1024$ 时 `ikj` 同时碰三行（`A` 一行、`B` 一行、`C` 一行），每行 8 KiB，合计 24 KiB，本来就装得进 L1。工作集装得下，分块就没有可省的东西。它的用武之地是 $N$ 更大、或层级更多（L2 一块、L1 一块、寄存器一块）的时候，再配合打包（packing）让块内数据连续。

::: def 定义 1.6.5 · 分块与工作集 {#def-1.6.5}
分块（blocking，也叫 tiling）把循环按维度切成边长为 $B_s$ 的小块，让块内用到的几个子矩阵同时留在缓存里。工作集是一段时间内反复访问的字节数；分块是否有效，取决于「工作集 ≤ 目标缓存容量」这条不等式，而不取决于块本身。块太小，循环与边界开销占比重；块太大，工作集又溢出。
:::

### 边长取 2 的幂，为什么反而撞车

现在回答开头那个 2.5 倍。用 cachegrind 数缺失（它模拟的缓存是 16 KiB、4 路、64 B 行，共 64 组）：`ijk` 在 $N=192$ 时 D1 缺失 2175 万，在 $N=200$ 时 526 万——多干 13% 的活，缺失少 4.1 倍。

算术在这里：组号等于 $(\text{addr}/64) \bmod 64$。行距是 $8N$ 字节，$N=1024$ 时 8192 B，正好 128 个块，$128 \bmod 64 = 0$——所有 $B$ 的行都落在同一组。4 路只留得住 4 行，走一列要来回换 $N$ 次。$N=1000$ 时行距 8000 B，125 个块，125 与 64 互质，相邻行轮流落进 64 个组。

真实处理器常对组索引做散列（把高位异或进来）来打散这种别名，所以真机不一定像模拟器那么惨。但 1579 ms 对 638 ms 说明：至少这台 VM 上没有完全打散。边长取整百、或给每行末尾补几个元素（padding），是同一件事的两种做法。

::: errata 关于矩阵乘与分块的误解
1. **「缺失少 8 倍，时间就快 8 倍」**——实测是 5.2 倍。`ikj` 的 301 ms 已经贴着算力上限，缺失再少也换不来时间；缺失还会重叠，多个缺失同时在途时单次代价被摊薄。
2. **「分块一定大幅提速」**——$N=1024$ 时最好 304.6 ms，和 `ikj` 的 301.3 ms 打平。分块的前提是工作集装不下；装得下时它只是多写了四层循环。
3. **「边长取 2 的幂最安全」**——`ijk` 在 $N=1024$ 要 1579.3 ms，在 $N=1000$ 只要 638.1 ms，活还少了 7%。2 的幂让行距正好是 64 的整数倍，整列挤进同一组。
4. **「`C` 也要 $N^3/8$ 次缺失」**——`C` 的行在内层反复写，命中后就留在 L1，只有第一次碰它要付 $N^2/8$。把 `C` 的缺失也算成 $N^3/8$，会把 `ikj` 的缺失高估约一倍。
:::

::: ex 例 1.6.5 · 先猜换边长能快多少 {#ex-1.6.5}
`ijk` 在 $N=1024$ 时 1579.3 ms。先猜：把边长改成 1000（计算量少 7%），时间会更接近 1470 ms、900 ms 还是 640 ms？再猜：给 `ijk` 加一层分块，能不能救回来？

::: sol 解答
实测 638.1 ms，接近第三个猜测——省下的不是算力，是缺失。$N=1024$ 时 $B$ 的 1024 行全挤在同一组，4 路缓存等于只有 4 行有效；$N=1000$ 时行摊到 64 个组，一次列扫描的冲突大幅减少。

分块救不回来。块内 $B$ 的子块仍是 $B_s$ 行、行距仍是 $8N$ 字节，按同样的组号算术，这 $B_s$ 行依然落进同一组。要救得改布局：把 $B$ 转置、或按块打包成连续的小矩阵，让块内数据真的相邻。
:::
:::

### 1.6.5 小结

① 缺失能手算：内层每跨一个缓存行算一次，`ijk` 约 $N^3$、`ikj` 约 $N^3/8$；② 时间不是缺失数的线性函数，算力上限与缺失重叠都会改倍数，8 倍缺失只换来 5.2 倍时间；③ 分块的有效性由「工作集 ≤ 缓存容量」决定，装得下就不必分；④ 边长与缓存组数的整除关系会制造冲突缺失，2 的幂常常是最差的一档。如果只记住一件事，那就是：**先算工作集装不装得下，再决定要不要分块。**

::: method 即时自测 · 1.6.5
**Q1（记忆）** `ijk` 与 `ikj` 的缺失为什么分别是 $N^3$ 和 $N^3/8$？`C` 的缺失为什么只有 $N^2/8$？

**Q2（辨析）** 缺失差 8 倍，墙钟只差 5.2 倍。给出两个能解释差额的原因。

**Q3（应用）** L1 32 KiB、L2 512 KiB，三个 $B_s \times B_s$ 的 `double` 子块同时活跃。$B_s$ 的上限各是多少？

**Q4（迁移）** 一个 $4096 \times 4096$ 的矩阵按列求和要 400 ms，按行求和只要 40 ms。你会先查什么？给出两条互不相同的修法。

::: sol 答案
**A1** `ijk` 内层走 $B$ 的列，步长 $8N$ 字节，每次都是新行，共 $N^3$ 次；`ikj` 内层走行，每 8 个 `double` 一次缺失，`B` 摊到 $N^3/8$。`C` 的行只有 8 KiB，写一次就留在 L1，只有首次访问付 $N^2/8$。
**A2** 一是 `ikj` 已撞到算力上限（7.1 GFLOPS），缺失再少也快不了；二是多个缺失可以同时在途，单次代价被摊薄，缺失数不直接等于等待时间。
**A3** $3B_s^2 \times 8 \le 32768$ 得 $B_s \le 36$；对 512 KiB 得 $B_s \le 147$。前者决定能否常驻 L1，后者决定能否常驻 L2。
**A4** 先查访问顺序与缓存行：按列求和时相邻元素隔 32 KiB，每次都是新行。修法一，交换循环顺序或分块；修法二，转置后按行求和；修法三，若列方向必须走，给每行补 padding 错开组号。
:::
:::

## 1.6.6 缓存友好代码：分块、SoA、预取 {#sec-1.6.6}

这一节回答：知道缓存行是 64 B、L1 装不下大数组之后，改代码到底有哪三板斧？每一板治什么病，哪一板常被吹过头？

::: preview 先抓住一件事
让访问连续，比换更快的缓存更管用：同一份 64 MiB 数据，每次取下一个 `double` 花 0.59 ns，跨一个缓存行取一个就变成 1.49 ns，每 512 B 才取一个则到 6.87 ns。分块、SoA、预取都在这条曲线上做文章，但每板都有前提。SoA 就是最好的例子：换个写法测，同一个程序从「快 1.0–1.2 倍」变成「快 2.4–2.8 倍」，差别不在代码，在测量方式。
:::

### 第一板斧：让内层走连续的那一维

C 的二维数组按行存放，`a[i][j]` 下一个元素是 `a[i][j+1]`，不是 `a[i+1][j]`。所以「内层循环走哪一维」直接决定每次访存能不能用满一整行。下面这个程序在 64 MiB 的 `double` 数组上按不同步长求和，每个步长跑三次取最好成绩：

```c
for (size_t stride = 1; stride <= 64; stride *= 2) {
    double s = 0.0, t0 = now_sec();
    for (size_t i = 0; i < n; i += stride) s += a[i];
    double t1 = now_sec();
    printf("stride=%2zu %.3f ns/touch\n", stride,
           (t1 - t0) * 1e9 / (double)((n + stride - 1) / stride));
}
```

这台 VM 上实测（`-O2`，best-of-3）：

| 步长（`double`） | 每次 touch | 落在哪里 |
|--:|--:|:--|
| 1 | 0.592 ns | 连续，每行用满 |
| 2 | 0.698 ns | 隔一个取一个，每行仍用一半 |
| 4 | 0.770 ns | 每行用两个 |
| 8 | 1.487 ns | 正好一行取一个 |
| 16 | 2.906 ns | 跳过的行比用到的多 |
| 32 | 4.669 ns | 同上，更稀 |
| 64 | 6.870 ns | 每 512 B 才碰 8 B |

单位是「每次 touch 的墙钟时间」，不是一次访存的延迟。这里 0.59 ns 甚至小于 1.6.1 指针追逐量到的 L1 延迟 1.06 ns，两者不矛盾：指针追逐的地址依赖上一次的结果，只能一次一次等；这个循环的每次访问彼此独立，处理器可以同时挂起多个缺失，量到的是吞吐。

步长从 1 到 8，时间只慢 2.5 倍，但每次 touch 买到的有效字节从 64 B 掉到 8 B——按「每有效字节」算，成本差了 20 倍。连续访问时每行搬来的 64 B 都被用上，稀疏访问时用完 8 B 就扔掉 56 B。这就是空间局部性的价格。

### 第二板斧：分块

分块把「一次处理多少数据」压到缓存装得下，思路与边界已在 [1.6.5](#sec-1.6.5) 算过：三个 $B_s \times B_s$ 的 `double` 子块要满足 $3B_s^2 \times 8 \le$ 目标层容量。它的前提是工作集本来装不下；装得下时，分块与已缓存友好的顺序版本打平。卷积、stencil、动态规划、矩阵乘都能用同一个套路，区别只在「同时活跃的子块有几个」。

### 第三板斧：SoA，结论取决于测法

结构体数组（array of structures，AoS）把一条记录的字段放在一起；按字段拆成几个数组叫 SoA（structure of arrays）。只频繁访问其中一个字段时，AoS 每次都要把整条记录搬进缓存。用 4M 个粒子、每个 24 B 试一下，只对 `x` 求和：

```c
struct particle { double x, y, z; };    /* AoS：24 B 一条 */

/* 版本一：单个累加器 */
for (size_t i = 0; i < N; i++) s += aos[i].x;

/* 版本二：四个独立累加器，打断依赖链 */
for (size_t i = 0; i + 3 < N; i += 4) {
    a0 += aos[i].x;     a1 += aos[i + 1].x;
    a2 += aos[i + 2].x; a3 += aos[i + 3].x;
}
```

两版都在这台 VM 上实测，SoA 侧是对应的 `xs[i]`：

| 版本 | AoS | SoA | 倍数 |
|:--|--:|--:|--:|
| 单个累加器 | 0.682 / 0.757 ns | 0.669 / 0.615 ns | 1.02–1.23 |
| 四个累加器 | 0.344 / 0.399 ns | 0.143 ns | 2.37–2.79 |

同一份数据、同一个字段，换一种写法，结论从「几乎没差别」变成「快 2.4–2.8 倍」。原因在第一版：`s += ...` 是一条串行的加法依赖链，4M 次加法本身就要约 0.6 ns/次，内存再快也显不出来。第二版用四个累加器把链拆成四条，内存差异才浮出来，接近 24 B : 8 B 的字节比。

::: def 定义 1.6.6 · 缓存友好的三个条件 {#def-1.6.6}
一段循环对缓存友好，要同时满足三件事：时间局部性（同一个块在短时间内被反复用）、空间局部性（取了一个字节，同行的其他字节也用得上）、工作集可容纳（活跃字节数不超过目标层的容量）。三板斧各治一种病：连续访问修空间局部性，分块修工作集，SoA 修「只用一个字段却搬了整条记录」的浪费。
:::

### 预取与对齐：微调，不是主线

硬件预取器识别顺序与固定步长，命中率高、不占指令位；对指针追逐、哈希探测、稀疏矩阵这类地址算不出来的访问，可以用软件预取提前把行拉进来：

```c
for (size_t i = 0; i < n; i++) {
    __builtin_prefetch(&a[i + 16], 0, 1);   /* 读，提前 16 个元素 */
    s += a[i] * b[i];
}
```

提前量按「内存延迟 ÷ 每次迭代时间」估：延迟 80 ns、每次迭代 2 ns，就提前约 40 个元素。太早会污染缓存，太晚来不及。这段没有实测：预取的收益要跟硬件预取器比高低，而这台 VM 的硬件计数器读不到（原因见 [1.6.8](#sec-1.6.8)），只剩墙钟对比，噪声与收益同量级，测出来也不敢下结论。能说的是方向：顺序循环里软件预取多半没用，随机访问里才值得试。

对齐是另一件事。`malloc` 返回的地址保证对齐到 `max_align_t`（常见 16 字节），`aligned_alloc(64, size)` 能按缓存行对齐，`size` 必须是 64 的倍数。对齐只保证一个元素不跨行；顺序扫描时它带来的收益远小于访问顺序本身。

::: errata 关于缓存友好代码的误解
1. **「SoA 一定比 AoS 快几倍」**——单累加器版本只快 1.0–1.2 倍，四累加器版本才 2.4–2.8 倍。差的不是布局，是测量有没有被依赖链盖住。
2. **「顺序访问一定最快」**——顺序只保证每一行被用满，不保证算得快。累加依赖链、分支、指令条数都可能先成为瓶颈。
3. **「软件预取总是有用」**——顺序循环里硬件预取已经够用，软件预取往往只多占一条指令和一个填充缓冲，还可能把有用的行挤出去。
4. **「对齐到 64 B 就能提速」**——顺序扫描时收益很小；它的用处是避免跨行和 SIMD 未对齐 load，不是万能加速器。
5. **「分块是万灵药」**——[1.6.5](#sec-1.6.5) 里分块与 `ikj` 打平；工作集装得下时，多写的四层循环只增加复杂度。
:::

::: ex 例 1.6.6 · 先猜两个 SoA 版本差多少 {#ex-1.6.6}
4M 个粒子，AoS 每条 24 B，SoA 三个数组。只把 AoS 改成 SoA 求和 `x`。先猜：能快几倍？如果两版都用单个 `s +=` 累加，倍数会不会变？

::: sol 解答
四个累加器版本：AoS 0.344–0.399 ns/元素，SoA 0.143 ns/元素，快 2.4–2.8 倍，接近 24 B : 8 B 的 3 倍。单累加器版本：1.02–1.23 倍，几乎看不出差别。

原因是 4M 次串行加法本身就要 0.6 ns/次上下，正好把 SoA 省下的那点时间盖住。所以「SoA 有用吗」这个问题，必须先问「这个循环的瓶颈是内存还是别的」。
:::
:::

### 1.6.6 小结

① 三板斧各治一种病：连续访问修空间局部性、分块修工作集、SoA 修字段浪费；② 每板都有前提，前提不成立时收益在噪声里；③ 预取与对齐是微调，先把访问顺序和布局改对；④ 测法本身会改变结论，依赖链一盖，2.8 倍也能测成 1.0 倍。如果只记住一件事，那就是：**先让每一行被用满，再谈缓存大小。**

::: method 即时自测 · 1.6.6
**Q1（记忆）** 缓存友好的三个条件是什么？三板斧分别修哪一个？

**Q2（辨析）** 64 MiB 数组上步长 1 是 0.592 ns/次，步长 8 是 1.487 ns/次。为什么步长 1 反而比 1.6.1 里 L1 的 1.06 ns 还快？

**Q3（应用）** 一个粒子结构体 24 B，要遍历 4M 条只读 `x`。给出两种改法，并说明各自在什么条件下才有效。

**Q4（迁移）** 一个哈希表探测循环，每次探测要跳到另一个桶。你会先试哪一板斧？为什么？怎么在没有性能计数器的机器上判断有没有效？
::: sol 答案
**A1** 时间局部性、空间局部性、工作集可容纳。连续访问修空间局部性，分块修工作集，SoA 修「只用部分字段却搬整条记录」。
**A2** 指针追逐的地址依赖上一次读出的值，只能串行等待，量到的是延迟；步长 1 的循环每次访问独立，处理器能同时挂起多个缺失、还有预取，量到的是吞吐。
**A3** 改法一，拆成 SoA 三个数组，只扫 `xs`；改法二，保持 AoS 但把循环拆成多累加器，让编译器向量化。前者在「只读部分字段且记录较大」时有效，后者在「瓶颈是依赖链」时有效；两个一起用才拿到 2.4–2.8 倍。
**A4** 先用 SoA 或按桶预取：探测地址算不出来，硬件预取帮不上。没有计数器时，固定数据规模跑多轮取最好成绩，比「改前/改后」两版的中位数；差异若小于同一版本两次运行的波动，就当没效。

## 1.6.7 TLB、页与 NUMA {#sec-1.6.7}

这一节回答：缓存行 64 B 管的是「一次搬多少」，页 4 KiB 管的是「一次翻译多少」。翻译为什么也要缓存，缺了会怎样？大页和 NUMA 各自又在省什么？

::: preview 先抓住一件事
每次访存都要先把虚拟地址翻成物理地址，而页表本身在内存里，逐级查会多出好几次访存；TLB（translation lookaside buffer，地址翻译缓存）就是页表项的缓存，命中时翻译和取数同时完成。TLB 的覆盖范围等于「项数 × 页大小」：64 项 × 4 KiB 只有 256 KiB，换成 2 MiB 页就是 128 MiB。这台 VM 实测：页 4 KiB，1 GiB 匿名内存的页表占 2100 kB，而且 NUMA 只有一个节点——远程访问在这里量不到。
:::

### 翻译这一层，也要缓存

进程看到的是虚拟地址，内存条认的是物理地址。页表（page table）就是记录「虚拟页号 → 物理页框号」的那张表；中间的映射按页组织，页是翻译的最小单位：同一页内的 4096 个字节共用一个物理页号，只改页内偏移不改变翻译结果。如果每个页都单独存一个表项，表会大到装不下，所以页表本身分四级、按需分配，48 位虚拟地址切成 4 段各 9 位再加 12 位页内偏移：

<pre class="layout">
VA:   47..39    38..30    29..21    20..12    11..0
      ┌───────┬────────┬────────┬────────┬───────┐
      │ 第1级 │ 第2级  │ 第3级  │ 第4级  │ offset│
      └───┬───┴───┬────┴───┬────┴───┬────┴───────┘
          │       │        │        │
  根寄存器 → 表 → 表 → 表 → 末级表 → 物理页框
      （x86-64 叫 PML4/PDPT/PD/PT，ARM64 叫 PGD/PUD/PMD/PTE）
</pre>

每级表项 8 字节，装着下一级表的物理地址。完整走一遍是 4 次访存，只是这些表项通常已被缓存，实际到 DRAM 的常只有 1–2 次。

TLB 把「走一遍树」压成「查一次表」。它的项数与相联度是硬件参数，具体值随微架构变：桌面处理器常见 L1 数据 TLB 64 项、4–8 路，二级 TLB 上千项。这些数字是文档级典型值，这台 VM 的系统接口不暴露 TLB 参数，读不到。

覆盖范围是这一节最该记住的算术：

| 配置 | 覆盖范围 | 谁在用 |
|:--|--:|:--|
| 64 项 × 4 KiB | 256 KiB | L1 dTLB 的典型规模 |
| 1536 项 × 4 KiB | 6 MiB | 二级 TLB 的典型规模 |
| 1536 项 × 2 MiB | 3 GiB | 同一批项换成大页 |
| 64 项 × 2 MiB | 128 MiB | 小 TLB 配大页 |

工作集一旦超过覆盖范围，每换一页就多一次翻译。大页（huge page）的道理就在这里：不动 TLB 的项数，只把每项管的地盘放大 512 倍。

### 页表本身占多少内存

页表不是免费的。写一个程序映射 1 GiB 匿名内存、每页写一个字节，然后读它的状态：

```bash
./tlb_footprint 1 &          # mmap 1 GiB，逐页写一个字节，然后 pause
pid=$!
grep -E 'VmRSS|VmPTE' /proc/$pid/status
```

这台 VM 上实测：`VmRSS` 1050048 kB，`VmPTE` 2100 kB。算术对得上：$1\ \text{GiB} / 4\ \text{KiB} = 262144$ 个页表项，每项 8 B，共 2 MiB = 2048 kB；多出的几十 kB 是栈、代码段和堆自己的页表。按这个比例，一个映射 1 TiB 的进程光页表就要 2 GiB。

页表项多了，TLB 就更装不下——两件事是同一个问题的两面。系统默认用透明大页（transparent huge page，THP）来缓解：内核在合适的时候把 512 个连续小页合成一个 2 MiB 大页。这台 VM 的开关是 `always [madvise] never`，即默认只对显式 `madvise(MADV_HUGEPAGE)` 的区域生效；`HugePages_Total` 为 0，说明没配显式大页池。

### 大页的代价

大页省的是翻译次数，赔的是粒度。一个 2 MiB 大页里只要有一小块活跃，整页都要占着内存；进程退出或回收时，拆页、清零、迁移的成本都比小页高。分配大页还要连续物理内存，长时间运行的机器容易碎到分不出来。所以数据库、JVM、DPDK 这类「大块内存 + 随机访问」的负载用大页收益明显，而对象小而散的进程未必。

### NUMA：内存也有远近

前面所有延迟数字都假设「内存只有一个」。多路服务器上不成立：每个 CPU 插槽挂着本地内存，访问别人的内存要过互连。先看这台机器：

```bash
numactl --hardware
```

实测输出只有一个节点：`available: 1 nodes (0)`，容量 11921 MB，`node distances` 里 0 到 0 是 10。单节点意味着这台 VM 上没有「远程内存」，NUMA 的延迟差在这里量不到，只能按文档级描述：双路机器上跨节点访问常是本地延迟的 1.4–2 倍，带宽也更低，第 3 篇讲调度时再展开。

能在这台机器上做的，是看清接口：`numactl --cpunodebind=0 --membind=0 ./prog` 把进程的 CPU 与内存都钉在节点 0；默认策略是「本地优先」，首次触碰内存的线程决定这块内存落在哪个节点。线程被迁移到另一个节点后继续访问老内存，就变成远程访问——这是 NUMA 上最常见的性能坑。

::: def 定义 1.6.7 · TLB 与覆盖范围 {#def-1.6.7}
TLB 是页表项的缓存，键是虚拟页号，值是物理页号加权限位。覆盖范围 = 项数 × 页大小，超出范围的部分每换一页就要重新翻译。命中时翻译与 L1 取数并行，不额外花时间；缺失要逐级读页表，叫页表遍历（page walk），每级都可能再缺一次。
:::

::: ex 例 1.6.7 · 先猜覆盖范围与页表大小 {#ex-1.6.7}
一台机器 L1 数据 TLB 64 项、二级 TLB 1536 项，页 4 KiB。先猜：只用 L1 能覆盖多大范围？换成 2 MiB 大页呢？再猜：映射 1 GiB 匿名内存的进程，页表占多少内存？

::: sol 解答
$64 \times 4\ \text{KiB} = 256\ \text{KiB}$；$64 \times 2\ \text{MiB} = 128\ \text{MiB}$。二级 TLB 两档分别是 $1536 \times 4\ \text{KiB} = 6\ \text{MiB}$ 与 $1536 \times 2\ \text{MiB} = 3\ \text{GiB}$。

页表：$262144 \times 8\ \text{B} = 2\ \text{MiB}$。这台 VM 实测 2100 kB，两者对得上，差额来自进程里其他映射。中间级页表只有几页（上级表项少得多），可以忽略；真正吃内存的是末级这张表，它随映射大小线性增长。
:::
:::

::: errata 关于 TLB、大页与 NUMA 的误解
1. **「一次 TLB 缺失就是 4 次内存访问」**——四级表项通常已被缓存，真正到 DRAM 的常常只有 1–2 次；最坏情况才是 4 次。
2. **「大页总是更快」**——内部碎片、缺页（page fault，访问的页还没装进内存时由硬件触发、内核接手的那次异常）时清零 2 MiB 的成本、分配连续物理内存的难度都是代价。小对象多的进程可能更慢。
3. **「透明大页默认是 always」**——这台 VM 是 `[madvise]`，只有显式标记的区域才合并；不同发行版与内核版本默认值不一样，动手前先读 `/sys/kernel/mm/transparent_hugepage/enabled`。
4. **「NUMA 是标配」**——这台 VM 只有 1 个节点，`numactl` 的距离表只有一行。单节点机器上谈 NUMA 调优没有意义，先看 `numactl --hardware`。
5. **「页表很小，可以忽略」**——1 GiB 映射约 2 MiB 页表，1 TiB 就是 2 GiB；页表本身也吃缓存和 TLB。
:::

### 1.6.7 小结

① 页是翻译的最小单位，TLB 是页表项的缓存，覆盖范围 = 项数 × 页大小；② 页表占的内存与映射大小成正比，1 GiB 约 2 MiB，这部分开销也参与缓存竞争；③ 大页用粒度换覆盖范围，代价是碎片和回收成本；④ NUMA 让「内存延迟」变成变量，单节点机器上量不到，接口是 `numactl` 与「本地优先」。如果只记住一件事，那就是：**缓存行管一次搬多少，页和 TLB 管一次翻译多少，两笔账要分开算。**

::: method 即时自测 · 1.6.7
**Q1（记忆）** TLB 的覆盖范围怎么算？64 项配 4 KiB 页、配 2 MiB 页各是多少？

**Q2（辨析）** 有人说「TLB 缺失一定多 4 次访存」。这句话哪里不准确？

**Q3（应用）** 一个进程映射 4 GiB 匿名内存，页 4 KiB。估算末级页表占多少内存；换成 2 MiB 大页后呢？

**Q4（迁移）** 你在双路服务器上跑一个多线程程序，线程会被调度到两个插槽。怎么判断它有没有吃到远程内存的亏？给出两条可做的动作。
::: sol 答案
**A1** 项数 × 页大小。$64 \times 4\ \text{KiB} = 256\ \text{KiB}$；$64 \times 2\ \text{MiB} = 128\ \text{MiB}$。
**A2** 4 次是最坏情况。四级表项通常被缓存，实际到 DRAM 的常是 1–2 次；页表遍历本身也会命中缓存，还会挤占数据缓存。
**A3** $4\ \text{GiB} / 4\ \text{KiB} = 1048576$ 项，每项 8 B，末级表 8 MiB。用 2 MiB 大页时页数除以 512，末级表约 16 KiB——省下的不只是 TLB 项，还有页表本身。
**A4** 先看 `numactl --hardware` 确认有两个节点；再用 `numastat -p <pid>` 或 `/proc/<pid>/numa_maps` 看内存落在哪个节点；若大量内存在远端，用 `numactl --cpunodebind --membind` 绑定，或把线程与内存按节点分组。
:::
:::

## 1.6.8 用 perf 与 cachegrind 量化 {#sec-1.6.8}

这一节回答：想确认「缺失到底发生在哪一行」，用哪个工具？没有权限碰硬件计数器时，还能拿到什么？

::: preview 先抓住一件事
有两条路。`perf` 读硬件计数器：快、真实，但要有权限——这台 VM 的 `perf_event_paranoid` 是 4，普通账户连软件事件都开不了，`perf stat` 直接报 `No supported events found`。`cachegrind` 是模拟器：不要权限、结果可复现、能精确到源码行，代价是它换了台「模型机器」（默认 L1 16 KiB、LL 256 KiB），而且慢几十倍。合理的分工是：用 `cachegrind` 找哪一行缺失多，再想办法在真机上核对方向。
:::

### 先试 perf：权限是第一道关

```bash
perf stat -e cache-misses true
```

这台 VM 上实测，命令没跑起来就退出：

```text
Error:
No supported events found.
Access to performance monitoring and observability operations is limited.
```

原因是 `/proc/sys/kernel/perf_event_paranoid` 的值是 4。这个文件控制非特权账户能用多少性能事件：数值越小越宽松，2 以上连内核态采样都受限，4 是「除极少数情况外全禁」。改成 1 需要 root，这台 VM 的 sudo 要密码，自动化用不了。

于是「用 `perf` 验证」在这台机器上做不了。剩下三件事：读系统暴露的几何参数（`getconf` 与 `/sys/devices/system/cpu/cpu0/cache/`，1.6.1 试过，只拿到行大小 64 B）、用墙钟对比两个版本、用模拟器数缺失。

### cachegrind：换一台模型机器来数

cachegrind 是 valgrind 的一个工具：它逐条解释机器码，并维护一个假缓存，每次访存都记账。先确认装没装：

```bash
command -v valgrind && valgrind --version    # 实测为 v3.22.0
```

拿 1.6.5 的矩阵乘来试。`-g` 编译才有行号，`--cache-sim=yes` 其实是默认值，写出来更清楚：

```bash
gcc -O2 -g -std=c17 matmul.c -o matmul_g
valgrind --tool=cachegrind --cache-sim=yes \
    --cachegrind-out-file=cg.ijk.out ./matmul_g 192 ijk 1
cg_annotate cg.ijk.out | head -30
```

`cg_annotate` 开头会自报模型参数。这台机器上是：

```text
I1 cache:         16384 B, 64 B, 4-way associative
D1 cache:         16384 B, 64 B, 4-way associative
LL cache:        262144 B, 64 B, 8-way associative
```

这三行是编译进 cachegrind 的默认模型，**不是你这台机器的缓存**。真机 L1 常见 32–48 KiB、LL 从几 MB 到几十 MB（文档级典型值；这台 VM 读不到容量，见 1.6.1）。所以它回答的是「在 16 KiB 与 256 KiB 的假机器上会发生多少次缺失」，适合比较版本之间的相对关系，不适合当成真机缺失数。

$N=192$、四个版本，这台 VM 上实测：

| 版本 | D1 缺失 | LLd 缺失 |
|:--|--:|--:|
| `ijk` | 2174.6 万 | 269.5 万 |
| `ikj` | 271.2 万 | 271.2 万 |
| 分块 $B_s=32$ | 46.6 万 | 5.7 万 |
| 分块 $B_s=64$ | 104.7 万 | 5.0 万 |

四行读法。`ijk` 与 `ikj` 的 D1 缺失之比是 $2174.6 / 271.2 = 8.0$，正好是 1.6.5 手算的 8 倍；两者的 LLd 几乎一样（269.5 万对 271.2 万），因为三个 288 KiB 的矩阵已经超出 256 KiB 的假 LL，谁都要把数据从末级搬一遍。分块 32 把 D1 压到 `ikj` 的 1/5.8，LLd 压到 1/47。分块 64 的 LLd 更低（5.0 万），D1 却涨回 104.7 万——块越大，末级里能留的复用越多，L1 越装不下。这两列是取舍，不是「越小越好」。

### 缺在哪一行

`cg_annotate` 最有用的部分是逐行列计数。`ikj` 的内层长这样（这台 VM 上实测，$N=192$）：

```text
-- Auto-annotated source: matmul.c
   Ir            D1mr        DLmr        Dw
   85,155,840    1           1           0            for (size_t j = 0; j < n; j++)
  106,168,320    2,668,611   2,668,611   21,233,664   C[i * n + j] += a * B[k * n + j];
```

列名要认：`Ir` 是指令读次数，`D1mr` 是 L1 数据读缺失，`DLmr` 是末级读缺失，`Dw` 是数据写次数。这一行 `+=` 吃掉 99.2% 的 L1 读缺失和 99.3% 的末级读缺失——不用猜了，要改的就是这一行，或者它外面那层循环顺序。

`cg_annotate` 按函数、按文件、按行三级汇总，实际输出每行还带百分比。常见顺序是先看函数级找最贵的那几个，再下钻到行；只改最贵的一行，常常就能拿回大半收益。

::: def 定义 1.6.8 · 硬件计数器与模拟器 {#def-1.6.8}
硬件计数器（performance monitoring unit，PMU）在芯片上数事件，反映真实执行，但受权限与可用事件集限制；同时数多个事件时，硬件会把有限的计数器多路复用、再按比例缩放，读数只是估计。模拟器逐条解释指令并维护一个假缓存，计数精确、可复现，但容量、相联度、替换策略都是编译期固定的，也不模拟预取器和多核一致性协议。
:::

::: ex 例 1.6.8 · 先猜分块后哪一层降得多 {#ex-1.6.8}
$N=192$，`ikj` 的 D1 缺失 271.2 万、LLd 缺失 271.2 万。先猜：分成 $B_s=32$ 的块后，哪一层降得更多？再把块改成 64，两列会怎么走？

::: sol 解答
实测 $B_s=32$：D1 46.6 万（1/5.8），LLd 5.7 万（1/47）——末级降得更狠。原因是分块把「每一遍都重新流一遍 `B`」变成「块内复用」：`B` 的那一块只从末级取一次，之后在 L1 里被复用 $B_s$ 次。

改成 $B_s=64$：LLd 5.0 万（更少），D1 104.7 万（更多）。块变大，块内复用更多、末级流量更省；但 $3 \times 64^2 \times 8 = 96$ KiB 超出 16 KiB 的假 L1，装不下，D1 缺失就涨回来。两列此消彼长，选块大小就是选在哪一层让步。
:::
:::

::: errata 关于用工具量化缓存的误解
1. **「装了 perf 就能用」**——这台 VM 的 `perf_event_paranoid` 是 4，`perf stat` 直接报 `No supported events found`。不是命令写错，是权限。
2. **「cachegrind 的数就是真机缺失数」**——它模拟 16 KiB L1、256 KiB LL，真机常见 32–48 KiB 与几 MB 级末级。绝对值搬不过去，版本间的相对关系可以。
3. **「`D1mr` 大就说明代码差」**——还要看缺失率与总访问数。一亿次访存里 100 万次缺失，比一百万次访存里 20 万次缺失要好。
4. **「valgrind 慢，所以不能做性能实验」**——它不该用来测时间。cachegrind 慢几十倍，但计数重复性好，重跑一遍数字一样。
5. **「模拟器通过了就不用量真机」**——预取、TLB、多核一致性都不在模型里。1.6.5 里 1579 ms 对 638 ms 的现象，模拟器只能解释方向，倍数还得墙钟来定。
:::

### 1.6.8 小结

① `perf` 要权限，`paranoid=4` 时普通账户拿不到事件；② `cachegrind` 不要权限、能精确到行，但它模拟的是参数写死的假缓存；③ 分工是：模拟器找「哪一行」，墙钟和系统接口核「真机是不是这样」；④ 读数要看缺失率与总访问数，只看绝对值会被工作集大小骗。如果只记住一件事，那就是：**先问工具数的是哪台机器，再问它数出来的差意味着什么。**

::: method 即时自测 · 1.6.8
**Q1（记忆）** `Ir`、`D1mr`、`DLmr`、`Dw` 各是什么？cachegrind 默认的 L1 与 LL 各多大？

**Q2（辨析）** 同事说「cachegrind 显示末级缺失 270 万，所以真机也要 270 万次内存访问」。这句话哪里不对？

**Q3（应用）** `perf stat` 报 `No supported events found`。列出三条不改权限也能做的替代方案。

**Q4（迁移）** 一段卷积的 `cg_annotate` 显示 90% 的 D1 缺失集中在三行内层代码上。下一步改什么？怎么确认改对了？
::: sol 答案
**A1** `Ir` 指令读次数，`D1mr` L1 数据读缺失，`DLmr` 末级读缺失，`Dw` 数据写次数。默认模型：L1 16 KiB、4 路，LL 256 KiB、8 路，行都是 64 B。
**A2** 那个数是 256 KiB 假末级上的结果，真机末级大得多，整个工作集可能装得下；模型也不模拟预取。它只能用来比较版本，不能当绝对值。
**A3** 一，读 `getconf` 与 `/sys/devices/system/cpu/cpu0/cache/` 的几何参数；二，墙钟对比两个版本，多轮取最好成绩；三，用 cachegrind 数缺失，再在真机上验方向。
**A4** 先改这三行的访问顺序或分块，让内层走连续维度；再看 `cg_annotate` 的 `D1mr`/`DLmr` 是否下降，并用墙钟确认真机也变快。两者方向不一致时，以墙钟为准。
:::
:::

## 1.6.9 存储技术：从 SRAM 到 SSD 的数量级 {#sec-1.6.9}

这一节回答：同样叫「一次访问」，为什么 L1 命中能塞进一个循环迭代，而一次 SSD 随机读要等几十万条指令？[1.6.1](#sec-1.6.1) 已把各层器件、层级表和本机的延迟台阶量过，这里不重贴那些表，只把数量级换算成写代码时能用的三个数：周期、在途请求数、写放大。

::: preview 先抓住一件事
3 GHz 下 1 ns 约 3 个周期；一次 63 µs 的 SSD 随机读约 19 万个周期，按每周期 3 条指令算，相当于 57 万条指令的时间。软件不能让 SSD 变快，只能决定这次访问要不要发生，以及能不能让更多请求同时在途。
:::

### 把五层延迟放到同一把尺子上

| 事件 | 典型延迟 | 3 GHz 下周期 | 折合指令（IPC=3） |
|:--|--:|--:|--:|
| L1 命中 | 1 ns | 3 | 9 |
| L2 命中 | 4 ns | 12 | 36 |
| DRAM 命中 | 100 ns | 300 | 900 |
| SSD 4 KiB 随机读 | 63 µs | 189 000 | 57 万 |
| HDD 4 KiB 随机读 | 10 ms | 3000 万 | 9000 万 |

前两列是文档级典型值；后两列是按 3 GHz、每周期 3 条指令换算出来的，不是实测。本机 [1.6.1](#sec-1.6.1) 指针追逐量到 4 KiB 工作集 1.07 ns、64 MiB 工作集 134 ns，与表里的 1 ns/100 ns 同一量级，可以拿来做锚点。

这张表最直接的用法，是比较「省一次什么」和「优化多少条指令」。一次 SSD 随机读要等 57 万条指令的时间；把读之后的循环优化 10%，只省 5.7 万条指令的时间。所以先减少随机读的次数，再谈指令级优化。

### 本机实测：页缓存与 O_DIRECT 差两个数量级

在 `ubuntu24`（aarch64，GCC 13.3）上造一个 64 MiB 文件，用 4 KiB 对齐的缓冲分别测三种读法。核心循环只有几行（片段，省略了变量声明与完整错误处理）：

```c
int fd = open(path, O_RDONLY | O_DIRECT);
for (int i = 0; i < 4096; i++) {
    x ^= x << 13; x ^= x >> 7; x ^= x << 17;      /* xorshift 产生偏移 */
    off_t off = (off_t)(x % (FSIZE / 4096)) * 4096;
    if (pread(fd, buf, 4096, off) != 4096) { /* 错误处理 */ }
}
```

`buf` 必须按 4 KiB 对齐（`posix_memalign`），否则 `O_DIRECT` 读会返回 `EINVAL`。把 `O_DIRECT` 去掉、按顺序读完整文件，就是页缓存那一行；把缓冲改成 64 KiB、顺序读，就是顺序那一行。

同一文件连跑两次，实测：

| 读法 | 每次 4 KiB | 折算 |
|:--|--:|--:|
| 页缓存顺序读 | 0.48–1.53 µs | 2.7–8.5 GB/s |
| O_DIRECT 随机 4 KiB | 63–74 µs | 1.35–1.58 万 IOPS |
| O_DIRECT 顺序 64 KiB | — | 1.2 GB/s |

三点读法。第一，页缓存命中不是磁盘速度：第二次 0.48 µs，第一次 1.53 µs，差三倍，因为第一次还要把文件页装进页缓存，稳定后约 8.5 GB/s。第二，O_DIRECT 随机读 63–74 µs，是 [1.6.1](#sec-1.6.1) 量到的 DRAM 134 ns 的约 470–550 倍。第三，顺序 1.2 GB/s 是随机 63 MB/s 的约 19 倍；介质没变，变的是「一次搬多少」和「有多少请求在途」。

### 带宽、IOPS 与在途请求

顺序访问看带宽（GB/s），随机访问看 IOPS（每秒完成的 I/O 次数），两者不能直接互换。4 KiB × 1.5 万 IOPS 只有约 63 MB/s；同一块盘顺序读能到 1.2 GB/s，差了 19 倍。

单线程同步 `pread` 一次只有一个请求在途，吞吐约等于 $1 / 63\ \mu s \approx 1.6$ 万 IOPS。若设备标称 50 万 IOPS，而单次延迟仍是 63 µs，则至少要有 $500000 \times 63\ \mu s \approx 32$ 个请求同时在途。这就是多队列 NVMe、`io_uring`（Linux 的异步 I/O 接口，一次提交一批请求）和线程池的价值：不是把单次延迟变小，而是把等待重叠起来。

::: def 定义 1.6.9 · 带宽、IOPS 与队列深度 {#def-1.6.9}
带宽是单位时间搬的字节数，顺序大块访问看它；IOPS 是单位时间完成的 I/O 次数，随机小块访问看它。队列深度是在途请求数，稳态下满足「在途请求数 = 吞吐 × 单次延迟」。延迟不变时，想提高吞吐只能加深队列；队列超过设备并行度后，多出来的请求只会排队。
:::

### 写放大与寿命：一笔可以算的账

写放大（write amplification，WA）等于 NAND 实际写入字节除以主机写入字节。垃圾回收搬迁、页内修改都会让它大于 1。

一块 1 TB 的 SSD 标称 600 TBW（total bytes written，总写入字节），按 5 年保修算：$600 / (1 \times 365 \times 5) \approx 0.33$ DWPD（drive writes per day，每天整盘写入次数）。若 WA = 3，主机只能写 200 TB，DWPD 降到约 0.11。同样的盘，写放大三倍，寿命账就缩三倍。

对策不是「少写」，而是「让写变成大块、顺序、可预测」：日志先追加再合并、`fstrim` 告诉 SSD 哪些块空了、文件系统按块分配。第 2 篇讲文件 I/O 时会再遇到这些接口。

::: errata 关于数量级与存储介质的误解
1. **「IOPS 高就是带宽高」**——4 KiB 随机 1.5 万 IOPS 只有约 63 MB/s；同样设备顺序读能到 1.2 GB/s。随机看 IOPS，顺序看带宽，两条轴不能直接换算。
2. **「页缓存命中也是磁盘速度」**——页缓存命中走的是 DRAM，实测 0.48 µs/4 KiB，比 O_DIRECT 的 63 µs 快两个数量级；它省掉的是设备访问，不是把磁盘变快。
3. **「O_DIRECT 一定更快」**——本机顺序页缓存读 8.5 GB/s，O_DIRECT 顺序读只有 1.2 GB/s。O_DIRECT 的用处是绕过缓存、控制落盘时机，不是无条件加速。
4. **「TBW 用完盘立刻坏」**——TBW 是保修指标，不是硬故障点；超过之后坏块管理会更吃力，但盘不会在写到第 600 TB 的那一秒停住。
5. **「矩阵乘 `ikj` 的缺失是 $N^3/4$」**——按 [1.6.5](#sec-1.6.5) 的手算，$B$ 是 $N^3/8$，$C$ 只有 $N^2/8$；把 $B$、$C$ 都按 $N^3/8$ 相加才得到 $N^3/4$，但 $C$ 的行写一次就留在 L1，不能重复计。本节及后面一律用 $N^3/8$ 这个口径。
:::

::: ex 例 1.6.9 · 先猜页缓存与 O_DIRECT 差多少 {#ex-1.6.9}
同一台 VM：页缓存顺序读 0.48 µs/4 KiB，O_DIRECT 随机读 63 µs/4 KiB。先猜：两者差多少倍？如果单次随机读 63 µs，要跑到 50 万 IOPS，至少要有多少个请求同时在途？

::: sol 解答
$63 / 0.48 \approx 131$ 倍；和第一次的 1.53 µs 比是 41 倍。差距来自两件事：页缓存命中走内存，O_DIRECT 要走设备和队列。

在途数 $= 500000 \times 63 \times 10^{-6} \approx 31.5$，所以至少 32 个。单线程同步读只有 1 个在途，实测约 1.6 万 IOPS，正好对上。
:::
:::

### 1.6.9 小结

① 把延迟换成同一把尺子：一次 SSD 随机读约 19 万个周期，一次 HDD 随机读约 3000 万个周期；② 顺序看带宽、随机看 IOPS，单线程同步读的吞吐被「延迟 × 1 个在途」封顶；③ 写放大把主机写入放大成 NAND 写入，TBW 与 DWPD 是这笔账的两端。如果只记住一件事，那就是：**先问这次访问落在哪一层，再问有多少请求能同时在途。**

::: method 即时自测 · 1.6.9
**Q1（记忆）** 写出「在途请求数 = 吞吐 × 延迟」这三个量的关系，并说明队列深度指什么。

**Q2（辨析）** 同一块盘，顺序读 1.2 GB/s，4 KiB 随机读只有 63 MB/s。是介质在随机访问时变慢了吗？

**Q3（应用）** 一块 1 TB SSD 标称 600 TBW，写放大为 3，按 5 年算 DWPD 是多少？

**Q4（迁移）** 单次 4 KiB 随机读 100 µs，程序能保持 8 个请求同时在途。估算吞吐；若设备最多支持 64 个在途，理论上限是多少？

::: sol 答案
**A1** 在途请求数 = 吞吐 × 单次延迟；队列深度就是同时在途的请求数。延迟不变时，吞吐与在途数成正比。
**A2** 不是。介质单次延迟没变，随机访问把「一次搬 64 KiB」拆成「每次只搬 4 KiB」，且请求之间没有重叠；顺序读靠大块传输和预取把带宽吃满。
**A3** 主机可写 $600/3 = 200$ TB；$200 / (1 \times 365 \times 5) \approx 0.11$ DWPD。
**A4** $8 / 100\ \mu s = 8$ 万 IOPS；$64 / 100\ \mu s = 64$ 万 IOPS。后者是理论上限，实际还受设备并行度、队列调度和 CPU 限制。
:::
:::

## 1.6.10 组相联缓存：地址怎么拆、命中怎么算 {#sec-1.6.10}

这一节回答：[1.6.3](#sec-1.6.3) 的公式会算之后，为什么 L1 常见 32 KiB、8 路，而不是 64 KiB？为什么 Apple 的 128 KiB L1 要配 16 KiB 页，搬到 4 KiB 页的机器上就会出问题？地址拆分的后果不只在「落在第几组」，还在「index 位能不能放进页内偏移」。

::: preview 先抓住一件事
[1.6.3](#sec-1.6.3) 已给 $C=S \times E \times B$ 和 tag/index/offset 的切法，这里不再推一遍。这一节只看位域的两个工程后果：index 的末位如果越过页内偏移，VIPT 缓存会出现同一物理行两份副本（别名）；同一段地址在不同几何下，组号和 tag 会整段改变。命中仍是 valid + tag，但 tag 比较能不能和地址翻译并行，取决于 index 位落在哪里。
:::

### 一张表：几何变了，位域怎么变

用 48 位虚拟地址、64 B 块，把常见几何排开。$S=C/(E \times B)$，$s=\log_2 S$，$b=6$，$t=48-s-b$：

| 容量 $C$ | 路数 $E$ | 组数 $S$ | $s$ | $b$ | $b+s$ | 48 位 tag | index 末位 |
|--:|--:|--:|--:|--:|--:|--:|:--|
| 32 KiB | 8 | 64 | 6 | 6 | 12 | 36 | 页内（4 KiB 页正好） |
| 48 KiB | 12 | 64 | 6 | 6 | 12 | 36 | 页内 |
| 32 KiB | 4 | 128 | 7 | 6 | 13 | 35 | 页外（bit 12） |
| 64 KiB | 8 | 128 | 7 | 6 | 13 | 35 | 页外（bit 12） |
| 128 KiB | 8 | 128 | 7 | 7 | 14 | 34 | 16 KiB 页内，4 KiB 页外 |

前两行的 $b+s=12$，index 从 bit 6 到 bit 11，正好落在 4 KiB 页的 12 位偏移里；第三、四行 index 用到 bit 12，超出 4 KiB 页；第五行用 128 B 块，$b=7$，index 到 bit 13，只有 16 KiB 页（偏移 14 位）才装得下。

这解释了 [1.6.1](#sec-1.6.1) 读到的两个现象：x86 常见 32 KiB 8 路或 48 KiB 12 路，两种几何的 $s$ 都是 6；Apple M5 Pro 的一档 L1 数据缓存是 128 KiB、行 128 B，若按 8 路算，$s=7$、$b=7$，合计 14 位，正好等于 16 KiB 页的偏移宽度（macOS arm64 用 16 KiB 页）。**相联度和块大小不是随手挑的，它们和页大小一起决定 index 能不能落进页内。**

### index 越过页内偏移会怎样

L1 为了快，常常用虚拟地址的 index 先选组，同时用 TLB 把虚拟页号翻成物理页号，再拿物理 tag 比较。这种结构叫 VIPT（virtually indexed, physically tagged，虚拟索引、物理标记）：选组和翻译并行，命中延迟不叠加。

只要 index 位全部落在页内偏移里，虚拟地址和物理地址的这几位就相同，选出的是同一组；同一个物理行无论通过哪个虚拟地址访问，都落在同一组，不会出现两份。反过来，index 越过页内偏移时，两个虚拟地址可以映射到同一物理页，却因为虚拟地址高位不同选到不同组；同一物理行就在缓存里出现两份，这叫别名（alias）。硬件要检测并合并，或者操作系统按页着色（page coloring）把容易冲突的页错开。

检查口诀是一行不等式：$b+s \le$ 页偏移位数。4 KiB 页是 12，16 KiB 页是 14，64 KiB 页是 16。PIPT（physically indexed, physically tagged，物理索引、物理标记）不受这条限制，但要等翻译完才能选组，命中延迟多一段；大容量 L2/L3 常用 PIPT。

::: def 定义 1.6.10 · VIPT 与别名 {#def-1.6.10}
VIPT 缓存用虚拟地址的 index 选组、用物理地址的 tag 确认。index 位全部落在页内偏移里时，同一个物理行不会因虚拟地址不同而落到两个组；index 越过页内偏移时，同一物理行可能出现两份副本，叫别名。约束是一行不等式：块内偏移位数加组索引位数不超过页偏移位数。
:::

### 手算一个 48 位地址

取 `0x7ffd1234B7E8`，缓存 32 KiB、8 路、64 B。按 [1.6.3](#sec-1.6.3) 的公式，$s=6$、$b=6$：

- offset：`0x...7E8 & 0x3F = 0x28`，即 40；
- block：`0x7ffd1234B7E8 >> 6`；set：`block & 63 = 31`；
- tag：`0x7ffd1234B7E8 >> 12 = 0x7FFD1234B`。

所以它落在第 31 组、块内偏移 40、标记 `0x7FFD1234B`。若第 31 组某一路 valid=1 且 tag 相等，命中；否则缺失。

拆地址的代码可以写成一个函数，位运算比 `%`、`/` 更贴近硬件：

```c
static void split(uintptr_t a, unsigned s, unsigned b,
                  uint64_t *tag, unsigned *set, unsigned *off)
{
    uint64_t block = a >> b;
    *off = (unsigned)(a & ((1u << b) - 1));
    *set = (unsigned)(block & ((1u << s) - 1));
    *tag = block >> s;
}
```

`%`、`/` 也能算，但 `&`、`>>` 要求 $S$、$B$ 是 2 的幂；硬件几何本来就是 2 的幂，所以代码里用位运算。把 $s=6$、$b=6$ 代进去，得到 set=31、off=40、tag=`0x7FFD1234B`。

同一个地址换成 64 KiB、8 路（$s=7$）：offset 仍是 40，set 变成 95，tag 变成 `0x3FFE891A5`。**地址没变，几何一变，三段全变**；把缓存参数硬编码进程序，换一台机器就会错。

### 命中怎么算：两个并行

一次命中分三步：用 index 选组；组内 $E$ 路 tag 并行比较，valid=1 且 tag 相等即命中；用 offset 取块内字节。和 [1.6.3](#sec-1.6.3) 相比，这里要补的是「并行」二字：

- index 选组与 TLB 翻译并行（VIPT），所以命中延迟里通常不含一整趟页表遍历；
- 组内 $E$ 路 tag 比较也是并行的，相联度增加的是比较器和功耗，不是 $E$ 倍的命中延迟；
- 但 TLB 缺失会把翻译这一路拖长，index 再快也要等物理 tag 才能确认命中。所以 [1.6.7](#sec-1.6.7) 的 TLB 覆盖范围会反过来影响这里的有效延迟。

::: errata 关于地址位域的误解
1. **「tag 位数固定」**——tag 是剩下的高位：48 位地址、64 B 块、8 路下是 36 位；换 128 B 块或 4 路，tag 就变。写死 36 位的代码换几何就错。
2. **「index 位总在页内」**——4 KiB 页只有 12 位偏移；64 KiB、8 路、64 B 的缓存 index 用到 bit 12，已经越过页边界，VIPT 下需要别名处理。
3. **「VIPT 就是虚拟地址缓存」**——VIPT 只有 index 用虚拟地址，tag 仍是物理地址；它不是把整个缓存做成虚拟地址索引，否则进程切换时无法共享同一物理行。
4. **「相联度越高越好」**——相联度降低冲突，但比较器面积、功耗和命中延迟都上升；高相联度还会让 index 位数变少，反而改变别名行为。
5. **「L1 做到 64 KiB 一定更快」**——容量变大可能让 index 越过页内偏移，VIPT 要加别名检测或改 PIPT，命中延迟可能吃掉容量收益。
:::

::: ex 例 1.6.10 · 先猜 64 KiB L1 能不能直接 VIPT {#ex-1.6.10}
64 KiB、8 路、64 B 块，页 4 KiB。先猜：$s$、$b$、$b+s$ 各是多少？这个几何能不能直接用 VIPT？如果把页换成 16 KiB 呢？

::: sol 解答
$S=65536/(8 \times 64)=128$，$s=7$，$b=6$，$b+s=13$。4 KiB 页的偏移只有 12 位，index 用到 bit 12，越过页边界，直接 VIPT 会有别名风险；要用 PIPT、加别名检测，或者按页着色。

16 KiB 页的偏移是 14 位，$13 \le 14$，可以直接 VIPT。Apple 的 128 KiB L1 配 128 B 行，$s=7$、$b=7$、$b+s=14$，正好卡在 16 KiB 页的边界上；这也说明「L1 多大」和「页多大」是配套决定的。
:::
:::

### 1.6.10 小结

① 位域由 $C$、$E$、$B$ 决定，但 index 的末位不能越过页内偏移，否则 VIPT 会出现别名；② 同一个地址换几何，set、tag、offset 会整段改变，缓存参数不能硬编码；③ 命中的两个并行是「index 与翻译并行」「$E$ 路 tag 比较并行」，TLB 缺失仍会拖长有效延迟。如果只记住一件事，那就是：**先看 $b+s$ 有没有超过页偏移，再谈 L1 能做多大。**

**Q2（辨析）** 为什么 48 KiB、12 路的 L1 在 4 KiB 页上也能用 VIPT，而 64 KiB、8 路就不行？

**Q4（迁移）** 一台机器标称 64 KiB、4 路、64 B 的 L1，页 4 KiB。你会先检查什么？给出两种让 VIPT 继续工作的办法。

**A4** 先算 $S=65536/(4 \times 64)=256$，$s=8$，$b=6$，$b+s=14>12$，会越过页边界。办法一，改用 PIPT；办法二，按页着色或加别名检测；换 16 KiB 页也能让 $14 \le 14$。

## 1.6.11 替换、写策略与一致性 {#sec-1.6.11}

这一节回答：[1.6.4](#sec-1.6.4) 已经把 LRU、FIFO、随机和写穿、写回列过一遍，为什么还要再算？因为那张表只说了「有哪些策略」，没说「策略在什么访问序列上会失效」，也没算「一次写到底搬多少字节」。这一节补三笔账：LRU 在循环扫描上的 0 命中、写分配的 RFO 流量、缓存一致性与内存顺序的边界。

::: preview 先抓住一件事
替换策略赌的是「最近用过的还会用」。循环扫描 9 个块、缓存只有 8 路时，这个赌注每次都输：36 次访问 0 命中；同样序列换随机替换，一次运行命中 22 次。写这边，普通 store 对不在缓存里的行要先读 64 B 再写 64 B，1 GiB 的写会变成 2 GiB 流量。一致性这边，MESI 只保证同一行有最新副本，不保证两个变量谁先可见。
:::

### 替换：LRU 的假设什么时候不成立

LRU 的规则是「换最久没用的那一路」。它假设最近用过的块还会被用；循环扫描恰好相反：9 个块轮流访问，每次访问的块都是「最久没用」的那一块。

- 8 路缓存、9 个块（地址相隔 4 KiB，全部落在同一组）：第 1 轮 9 次全缺；第 9 次把第 1 块换出，下一轮第 1 块又把第 2 块换出……4 轮 36 次访问，0 命中。
- 同样 36 次、同样 8 路，随机替换一次运行命中 22 次（[1.6.12](#sec-1.6.12) 的模拟器可复现，种子固定）。稳态下 9 个块里有 8 个在缓存，命中率接近 $8/9$。
- FIFO 在这条序列上也得到 0 命中：它换最早进入的，遇到定长循环时同样留不住下一轮要用的块。
- 这不是「随机一定比 LRU 好」，而是「没有一种策略对所有序列最优」。真实 CPU 用 RRIP 一类按重用距离预测的策略，或者把新块插到 LRU 位置而不是 MRU 位置，专门对抗扫描。
- 软件能做的：先看访问序列有没有循环或扫描；大数组顺序扫描会冲掉热点，分块或改变遍历顺序比换策略更直接（[1.6.5](#sec-1.6.5)）。

### 写：三笔流量

- **写回 + 写分配**：写一个不在缓存里的 8 B，先把整行 64 B 读进来（RFO，read-for-ownership，写前先取得这一行的所有权），驱逐时再写回 64 B。一次写带来 64 B 读 + 64 B 写。
- **写穿**：每次写都到下一层；同一行写 1000 次，可能产生 1000 次下层写事务。写缓冲能合并一部分，但流量仍大于写回的一次 64 B 驱逐。
- **非临时存储**：绕过缓存直接写，1 GiB 的 `memset` 只写 1 GiB，不做 RFO；代价是之后马上读会缺失。

算一笔：1 GiB 缓冲区用普通 store 写，假设每一行开始时都不在缓存，按 64 B 行算，RFO 读 1 GiB + 写回 1 GiB = 2 GiB 内存流量；非临时写约 1 GiB。差值就是 RFO。

持久化是另一层：写回缓存的 dirty 行掉电会丢；`fsync` 把文件数据和元数据推到设备，但设备自己的写缓存还要 FUA/barrier 才保证落盘。

### 一致性：coherence 不等于 consistency

MESI 保证「同一缓存行在所有核看来只有一个最新副本」，这叫缓存一致性（cache coherence）。它不保证「两个不同地址的写，其他核看到的顺序和你程序里的顺序一样」，这叫内存一致性（memory consistency）。

| 线程 A 的程序顺序 | 线程 B 可能观察到 |
|:--|:--|
| `data = 42;` 然后 `flag = 1;` | `flag == 1`，但 `data` 仍是 0 |

编译器可以把 `flag = 1` 提前到 `data = 42` 之前，CPU 也可以把两个写放进存储缓冲后按别的顺序可见。在 ARM64 上，B 可能看到 flag=1 而 data 还是 0；x86 的 TSO 较强，但编译器重排仍然要防。

C11 的修法是给两个操作加上 release/acquire 语义：

```c
#include <stdatomic.h>
int data;
_Atomic int flag;

void publish(void)
{
    data = 42;
    atomic_store_explicit(&flag, 1, memory_order_release);
}

int consume(void)
{
    while (atomic_load_explicit(&flag, memory_order_acquire) == 0)
        ;
    return data;
}
```

在 `ubuntu24`（aarch64）上把这两个函数编成汇编（`gcc -O2 -S`，实测），release store 是 `stlr`，acquire load 是 `ldar`。这两条指令既约束编译器也约束 CPU 的重排；x86 的 TSO 让 release/acquire 在多数情况下只剩编译器屏障，要 `seq_cst` 时才常见 `lock` 前缀或 `mfence`。只加 `volatile` 不够：它只阻止编译器把变量缓存到寄存器，不建立跨变量的顺序。

伪共享是 coherence 的代价（[1.6.4](#sec-1.6.4) 已讲），内存顺序是 consistency 的代价，两者不是一回事。

::: def 定义 1.6.11 · 缓存一致性与内存一致性 {#def-1.6.11}
缓存一致性（cache coherence）管同一个地址：所有核对同一行的读写看到同一个顺序，MESI 是常见实现。内存一致性（memory consistency）管不同地址：一个核先写 A 再写 B，另一个核能不能先看到 B 再看到 A。前者由缓存协议保证，后者由内存模型和屏障指令保证。
:::

::: errata 关于替换、写与一致性的误解
1. **「LRU 是最优替换策略」**——LRU 对循环扫描最差：9 个块、8 路时 36 次访问 0 命中。最优策略要预知未来，只能当上界。
2. **「随机替换一定比 LRU 差」**——同一条循环上随机一次运行命中 22/36，LRU 是 0。策略要和访问序列配对看。
3. **「写回一定比写穿省流量」**——写一次、不再读的流式写，写回的 RFO 会先把整行读进来；这种场景非临时存储更省。
4. **「MESI 保证程序里的写顺序」**——MESI 只管同一行的一致性，不保证不同地址的可见顺序；跨线程传递数据要 release/acquire 或屏障。
5. **「`volatile` 能替代原子操作（不可被打断的一次读改写）」**——`volatile` 阻止编译器把变量缓存在寄存器里，但它既不保证原子性，也不建立跨变量的顺序，更不阻止 CPU 重排。
6. **「`fsync` 返回就一定落到盘片」**——`fsync` 把数据推到设备，设备自己的易失写缓存还要靠 FUA/barrier 刷新；具体行为看文件系统与设备配置。
:::

::: ex 例 1.6.11 · 先猜 LRU 与随机谁命中多 {#ex-1.6.11}
9 个块循环访问、缓存 8 路、共 4 轮 36 次。先猜：LRU 命中几次？随机替换命中几次？再把 1 GiB 普通写和 1 GiB 非临时写比，内存流量差多少？

::: sol 解答
LRU 0 次；随机替换在一次固定种子的运行里 22 次（稳态约 $8/9$）。原因是循环长度 9 大于相联度 8：LRU 每次换掉的正好是下一轮最先要用的块，随机则保留了一个随机的 8 块子集。

普通写按 64 B 行算，RFO 读 1 GiB、写回 1 GiB，共约 2 GiB；非临时写约 1 GiB。差值是 RFO 的那 1 GiB，不是写本身。
:::
:::

### 1.6.11 小结

① 替换策略没有全局最优：LRU 在循环扫描上 0 命中，随机在同一条序列上能留住大部分块；② 写分配的 RFO 会把「写 1 GiB」变成「读 1 GiB + 写 1 GiB」，流式写要考虑非临时存储；③ 缓存一致性管同一行，内存一致性管不同地址的顺序，跨线程传数据要 release/acquire 或屏障。如果只记住一件事，那就是：**先看访问序列和写入模式，再问该换哪个策略。**

::: method 即时自测 · 1.6.11
**Q1（记忆）** 缓存一致性和内存一致性各管什么？MESI 管哪一个？

**Q2（辨析）** 8 路缓存、9 个块循环，LRU 0 命中。这能说明缓存太小吗？

**Q3（应用）** 1 GiB 缓冲区用普通 store 写，按 64 B 行、写分配 + 写回算，内存流量大约多少？换成非临时写呢？

**Q4（迁移）** 线程 A 写 `data` 再写 `flag`，线程 B 看到 `flag` 后读 `data`。在 ARM64 上要加什么？只加 `volatile` 够不够？

::: sol 答案
**A1** 缓存一致性管同一个地址的读写顺序，MESI 管这个；内存一致性管不同地址的可见顺序，由内存模型和屏障指令保证。
**A2** 不能。9 个块只有 576 B，远小于 32 KiB 缓存；问题是它们全落在同一组，8 路留不住 9 个块，属于冲突缺失。
**A3** 普通写约 2 GiB（RFO 读 1 GiB + 写回 1 GiB）；非临时写约 1 GiB，省掉 RFO。
**A4** 用 release store 写 `flag`、acquire load 读 `flag`（C11 原子操作或对应屏障）；`volatile` 不够，它不建立跨变量的顺序。
:::
:::

## 1.6.12 完整程序一：组相联缓存模拟器 {#sec-1.6.12}

这一节回答：工作集只有 576 B，为什么在 32 KiB 的 8 路缓存里 100% 缺失？[1.6.10](#sec-1.6.10) 说 index 位决定组号，[1.6.11](#sec-1.6.11) 说 LRU 怕循环扫描；把两者放进同一个程序，就能看到「容量够、相联度不够」的冲突缺失。

::: preview 先抓住一件事
模拟器只做三件事：地址拆成 tag/set/offset；组内查 tag；缺失时按 LRU、FIFO 或随机选一路。它不模拟预取、写回、多核和 TLB，所以只用来比较几何与访问序列，不能当真机缺失数（真机口径见 [1.6.8](#sec-1.6.8)）。两条内置 trace 分别回答「顺序扫描会不会冲突」和「小工作集会不会因为映射挤爆」。
:::

### 程序

```c
/* csim.c - 组相联缓存模拟器：LRU / FIFO / 随机
 * cc -O2 -std=c17 -Wall -Wextra -Werror csim.c -o csim
 * ./csim 32768 8 64 lru
 */
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <string.h>

#define EMPTY UINT64_MAX

typedef struct {
    int sets, ways, block, policy;      /* 0=LRU 1=FIFO 2=随机 */
    uint64_t *tag, *stamp, clock, rng;
    unsigned long hits, misses;
} cache_t;

static int init(cache_t *c, int size, int ways, int block, int policy)
{
    if (ways <= 0 || block <= 0) return -1;
    memset(c, 0, sizeof *c);
    c->block = block; c->ways = ways; c->policy = policy;
    c->sets = size / (ways * block);
    c->rng = 0x9e3779b97f4a7c15ULL;
    c->tag = malloc((size_t)c->sets * ways * sizeof *c->tag);
    c->stamp = malloc((size_t)c->sets * ways * sizeof *c->stamp);
    return (c->sets > 0 && c->tag && c->stamp) ? 0 : -1;
}

static void reset(cache_t *c)
{
    for (int i = 0; i < c->sets * c->ways; i++) c->tag[i] = EMPTY, c->stamp[i] = 0;
    c->clock = c->hits = c->misses = 0;
}

static int access(cache_t *c, uint64_t addr)
{
    uint64_t blockno = addr / (uint64_t)c->block;
    int set = (int)(blockno % (uint64_t)c->sets);
    uint64_t tag = blockno / (uint64_t)c->sets;
    int base = set * c->ways, victim = -1;
    c->clock++;
    for (int w = 0; w < c->ways; w++)
        if (c->tag[base + w] == tag) {
            if (c->policy == 0) c->stamp[base + w] = c->clock;
            return ++c->hits;
        }
    for (int w = 0; w < c->ways && victim < 0; w++)
        if (c->tag[base + w] == EMPTY) victim = w;
    if (victim < 0 && c->policy == 2) {
        c->rng ^= c->rng << 13; c->rng ^= c->rng >> 7; c->rng ^= c->rng << 17;
        victim = (int)(c->rng % (uint64_t)c->ways);
    } else if (victim < 0) {
        victim = 0;
        for (int w = 1; w < c->ways; w++)
            if (c->stamp[base + w] < c->stamp[base + victim]) victim = w;
    }
    c->tag[base + victim] = tag; c->stamp[base + victim] = c->clock;
    c->misses++;
    return 0;
}

static void run(const char *name, cache_t *c, int kind)
{
    reset(c);
    if (kind == 0) {                    /* 16 KiB 顺序，两遍 */
        for (int r = 0; r < 2; r++)
            for (int i = 0; i < 16384; i++) access(c, (uint64_t)i);
        printf("%-8s accesses=32768 hits=%lu miss=%lu\n", name, c->hits, c->misses);
    } else {                            /* 9 个页，4 轮 */
        for (int r = 0; r < 4; r++)
            for (int p = 0; p < 9; p++) access(c, (uint64_t)p * 4096);
        printf("%-8s accesses=36    hits=%lu miss=%lu\n", name, c->hits, c->misses);
    }
}

int main(int argc, char **argv)
{
    int size = argc > 1 ? atoi(argv[1]) : 32768;
    int ways = argc > 2 ? atoi(argv[2]) : 8;
    int block = argc > 3 ? atoi(argv[3]) : 64;
    int pol = argc > 4 && strcmp(argv[4], "fifo") == 0 ? 1
            : argc > 4 && strcmp(argv[4], "rand") == 0 ? 2 : 0;
    cache_t c;
    if (init(&c, size, ways, block, pol) != 0) { fprintf(stderr, "bad geometry\n"); return 1; }
    printf("size=%d ways=%d block=%d sets=%d policy=%s\n", size, ways, block, c.sets,
           pol == 0 ? "lru" : pol == 1 ? "fifo" : "rand");
    run("seq16k", &c, 0);
    run("stride9", &c, 1);
    free(c.tag); free(c.stamp);
    return 0;
}
```

在 `ubuntu24` 上编译（GCC 13.3，`-O2`），按 32 KiB、64 B 行跑五种几何，一次运行的结果：

| 几何（32 KiB，64 B 行） | seq16k 命中/缺失 | stride9 命中/缺失 |
|:--|--:|--:|
| 1 路（512 组） | 32512 / 256 | 21 / 15 |
| 8 路 LRU（64 组） | 32512 / 256 | 0 / 36 |
| 16 路（32 组） | 32512 / 256 | 27 / 9 |
| 8 路随机 | 32512 / 256 | 22 / 14 |
| 8 路 FIFO | 32512 / 256 | 0 / 36 |

`seq16k` 是 16 KiB 数组顺序扫两遍：第一遍每块一次强制性缺失，共 $16384/64=256$ 次，第二遍全命中。五种几何的这两列完全一样，因为 16 KiB 装得进 32 KiB，顺序访问没有冲突。

`stride9` 是 9 个地址、相隔 4 KiB、循环 4 轮，共 36 次访问，工作集只有 $9 \times 64 = 576$ B。同一份工作集，命中数从 27 掉到 0：

- **8 路 LRU：0 命中**。32 KiB、8 路、64 B 有 64 组，index 是 bit 6–11；4 KiB 步长只改 bit 12，而 bit 12 是 tag。9 个页全落在第 0 组，8 路装不下 9 个块，每次访问都把下一轮要用的块换出去。
- **1 路：21 命中**。直接映射有 512 组，4 KiB 步长让组号每次加 64，9 个页摊到 9 个不同的组（第 9 个绕回第 0 组），只有首尾两个页互相冲突，15 次缺失。
- **16 路：27 命中**。32 组，9 个页仍落在同一组，但 16 路装得下 9 个块；第一轮 9 次缺失，后面 27 次全命中。
- **8 路随机：22 命中**。随机替换在 9 个块里保留一个随机的 8 块子集，稳态命中率接近 $8/9$，和 [1.6.11](#sec-1.6.11) 的结论对上。

这组数说明两件事：工作集 576 B 远小于 32 KiB，**容量不是问题**；8 路装不下 9 个同组块，**冲突缺失可以独立于容量发生**。[1.6.6](#sec-1.6.6) 的步长实验看的是墙钟，这里看的是命中数，两者不矛盾：一个数时间，一个数事件。

### 换容量，映射也跟着换

把缓存从 32 KiB 加到 64 KiB、仍是 8 路，`stride9` 变成 27 命中 / 9 缺失（实测）。这不是「多装了数据」，而是 index 多了一位：64 KiB、8 路有 128 组，index 变成 bit 6–12，4 KiB 的 bit 12 从 tag 进入 index；9 个页分到第 0 组和第 64 组，每组最多 5 个，8 路装得下。

**容量一改，组号就改；不能只用「大了就能装下」解释命中率。** 但 [1.6.10](#sec-1.6.10) 的约束还在：64 KiB、8 路在 4 KiB 页上 index 越过页边界，VIPT 有别名风险。模拟器不建模别名，所以不能只凭 27/9 说 64 KiB 一定更好。

### 程序里容易写错的三处

1. **LRU 和 FIFO 不能共用同一个时间戳语义**。命中时要更新 LRU 的 `stamp`，但不能更新 FIFO 的 `stamp`；FIFO 记的是插入时间，命中就改会把它退化成 LRU。代码里用 `if (c->policy == 0)` 把两者分开。
2. **每条 trace 前要 `reset`**。不清 `tag`、`stamp` 和计数，上一条 trace 的状态会污染下一条，命中率看着像「越跑越好」。
3. **`access` 的粒度由调用者决定**。`seq16k` 按字节调用，`stride9` 每个页调用一次；换成 8 B 元素的 trace，一次访问要按 8 B 算，不能把「访问次数」和「字节数」混在一起。

::: errata 关于缓存模拟器的误解
1. **「步长越大，缺失一定越高」**——4 KiB 步长在 32 KiB 直接映射上是 21/36 命中，在 8 路上是 0/36。决定冲突的是步长与 index 位的关系，不是步长本身。
2. **「工作集小于缓存就不会缺」**——576 B 的工作集在 32 KiB 缓存里 8 路 LRU 全缺；块全挤在同一组，容量再大也救不了。
3. **「相联度越高越好」**——同样是 32 KiB，1 路 21 命中、8 路 0 命中、16 路 27 命中，不是单调曲线；相联度改变的是每组能放几块，也改变了哪几位是 index。
4. **「模拟器的缺失数就是真机」**——它不模拟预取、写回、TLB 和多核一致性；只能比较几何与序列，真机数要看 [1.6.8](#sec-1.6.8) 的 `perf`/`cachegrind` 口径。
5. **「FIFO 就是 LRU 换个名字」**——插入时间和最近使用时间是两个量；命中时更新 `stamp`，FIFO 就悄悄变成了 LRU。
:::

::: ex 例 1.6.12 · 先猜三种相联度各命中几次 {#ex-1.6.12}
32 KiB、64 B 行、9 个页循环 4 轮（36 次）。先猜：1 路、8 路 LRU、16 路各命中几次？再把容量换成 64 KiB、8 路，猜命中几次。

::: sol 解答
1 路 21 次，8 路 0 次，16 路 27 次。1 路有 512 组，9 个页摊开，只有首尾冲突；8 路有 64 组，9 个页全挤在第 0 组，8 路装不下；16 路有 32 组，仍在同一组，但 16 路装得下 9 个块。

64 KiB、8 路是 27 次：128 组让 4 KiB 的 bit 12 进入 index，9 个页分到两个组，每组最多 5 个。注意这是模拟器的数，没算 VIPT 别名。
:::
:::

### 1.6.12 小结

① 模拟器把地址拆成 tag/set/offset，组内查 tag，缺失时按策略选一路；② 同样的 576 B 工作集，8 路 0 命中、16 路 27 命中、1 路 21 命中，冲突缺失与容量无关，与「块落在几组」有关；③ 容量从 32 KiB 加到 64 KiB 会改变 index 位，命中率可能跳变；④ 模拟器只数事件，不建模预取、TLB 和别名，真机绝对值另算。如果只记住一件事，那就是：**先问 9 个块落在几组，再问缓存有多少字节。**

::: method 即时自测 · 1.6.12
**Q1（记忆）** 模拟器把一次访问拆成哪三步？`set`、`tag` 各由哪个除法得到？

**Q2（辨析）** 9 个页的工作集只有 576 B，32 KiB 的 8 路缓存为什么 0 命中？

**Q3（应用）** 32 KiB、16 路、64 B，`stride9` 为什么是 27 命中？换成 64 B 块、8 路、64 KiB 呢？

**Q4（迁移）** 把块大小从 64 B 改成 128 B，32 KiB、8 路、`stride9` 会怎样？先算组数再回答。

::: sol 答案
**A1** 用 `blockno = addr / block` 求块号，`set = blockno % sets`，`tag = blockno / sets`；再用 `set` 选组、用 `tag` 比较。
**A2** 32 KiB、8 路有 64 组，index 是 bit 6–11；4 KiB 步长只改 bit 12（tag），9 个页全落在第 0 组。8 路装不下 9 个块，LRU 每次换掉的正好是下一轮要用的块。
**A3** 16 路有 32 组，9 个页仍同组，但 16 路装得下，第一轮 9 次缺失后全命中。64 KiB、8 路有 128 组，bit 12 进入 index，9 个页分到两组，也是 27 命中。
**A4** $32768/(8 \times 128)=32$ 组，4 KiB 步长仍只改 tag 位，9 个页同组；8 路装不下 9 个块，仍是 0 命中。块变大没有改变「同组块数」这个约束。
:::
:::

## 1.6.13 完整程序二：AoS 与 SoA 的实测 {#sec-1.6.13}

这一节回答：一条记录 16 字节、只读其中 4 字节的字段，AoS 要比 SoA 多搬 4 倍字节、多 4 倍缺失，为什么墙钟只慢 1.2–2.2 倍？

::: preview 先抓住一件事
布局改的是「每读一个元素要搬多少字节」：16 B 的记录只取 4 B，剩下 12 B 跟着整条缓存行一起搬上来。cachegrind 把这个差别数成精确的 4.0 倍缺失，墙钟只给 1.2–2.2 倍，而且工作集越大越接近上限。差的这一截不是误差：真机上多个缺失同时在途，顺序流还有预取，缺失的个数不等于等待的时间。[1.6.6](#sec-1.6.6) 用两个累加器版本讲过「测法会盖住结论」，这里把程序补全，再加两样东西：规模扫描与逐行缺失计数。
:::

### 程序：同一份数据，两种摆法

两条求和路径走同一批数值。`sum_aos` 每次读一条 16 B 的记录、只取 `x`；`sum_soa` 读一个纯 `float` 数组。两侧都用 4 个累加器，免得把加法依赖链的账算到内存头上（单累加器会把 2.8 倍压成 1.0 倍，[1.6.6](#sec-1.6.6) 有实测）。规模从命令行给，每个版本跑 5 轮取最好。

```c
/* soa.c — AoS 与 SoA：只读一个字段要搬多少字节
 * cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 soa.c -o soa
 * ./soa 8388608
 */
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

struct particle { float x, y, z, w; };          /* AoS：16 B 一条 */

static double now(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec + (double)ts.tv_nsec * 1e-9;
}

static double sum_aos(const struct particle *a, size_t n)
{
    float s0 = 0, s1 = 0, s2 = 0, s3 = 0;
    for (size_t i = 0; i + 3 < n; i += 4) {
        s0 += a[i].x;     s1 += a[i + 1].x;
        s2 += a[i + 2].x; s3 += a[i + 3].x;
    }
    return (double)(s0 + s1 + s2 + s3);
}

static double sum_soa(const float *x, size_t n)
{
    float s0 = 0, s1 = 0, s2 = 0, s3 = 0;
    for (size_t i = 0; i + 3 < n; i += 4) {
        s0 += x[i];     s1 += x[i + 1];
        s2 += x[i + 2]; s3 += x[i + 3];
    }
    return (double)(s0 + s1 + s2 + s3);
}

int main(int argc, char **argv)
{
    size_t n = argc > 1 ? strtoul(argv[1], NULL, 0) : (8u << 20);
    struct particle *aos = malloc(n * sizeof *aos);
    float *sx = malloc(n * sizeof *sx);
    float *sy = malloc(n * sizeof *sy);
    float *sz = malloc(n * sizeof *sz);
    float *sw = malloc(n * sizeof *sw);
    if (!aos || !sx || !sy || !sz || !sw) { perror("malloc"); return 1; }

    for (size_t i = 0; i < n; i++) {
        aos[i].x = sx[i] = (float)(i & 255);
        aos[i].y = sy[i] = 1.0f;
        aos[i].z = sz[i] = 2.0f;
        aos[i].w = sw[i] = 3.0f;
    }

    double ta = 1e9, ts = 1e9;
    volatile double sink = 0;
    for (int r = 0; r < 5; r++) {
        double t0 = now();
        sink += sum_aos(aos, n);
        double t1 = now();
        sink += sum_soa(sx, n);
        double t2 = now();
        if (t1 - t0 < ta) ta = t1 - t0;
        if (t2 - t1 < ts) ts = t2 - t1;
    }
    double ua = 4.0 * (double)n;                /* 有用字节：只读 x */
    double la = (double)n * sizeof *aos;        /* 实际搬进行里的字节 */
    double us = 4.0 * (double)n;
    printf("N=%zu\n", n);
    printf("AoS %7.3f ms  %5.3f ns/elem  useful %6.2f GB/s  line %6.2f GB/s\n",
           ta * 1e3, ta * 1e9 / (double)n, ua / ta / 1e9, la / ta / 1e9);
    printf("SoA %7.3f ms  %5.3f ns/elem  useful %6.2f GB/s  line %6.2f GB/s\n",
           ts * 1e3, ts * 1e9 / (double)n, us / ts / 1e9, us / ts / 1e9);
    printf("ratio=%.2fx  sink=%.0f\n", ta / ts, sink);
    free(aos); free(sx); free(sy); free(sz); free(sw);
    return 0;
}
```

`-O2` 不能省：`-O0` 下循环与调用开销会盖住内存的差别。用 8M 元素跑一次：

```bash
gcc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 soa.c -o soa
./soa 8388608
```

实测输出（`ubuntu24`，GCC 13.3，4 vCPU）：

```text
N=8388608
AoS   2.173 ms  0.259 ns/elem  useful  15.44 GB/s  line  61.77 GB/s
SoA   1.277 ms  0.152 ns/elem  useful  26.28 GB/s  line  26.28 GB/s
ratio=1.70x  sink=10663918080
```

`useful` 只算真正用到的 4 B/元素，`line` 按每元素实际搬进缓存的 16 B 算。AoS 的 `useful` 只有 SoA 的六成左右，不是它搬得少，是分子漏掉了白搬的 12 B；看 `line` 那一列，它每秒搬的字节反而是 SoA 的两倍多。SoA 两列相等，因为它的缓存行里全是 `x`。

换四个规模，每个规模各跑 8 次，取读数范围：

| 规模 | AoS（ns/元素） | SoA（ns/元素） | 倍数 | AoS 行带宽 |
|--:|--:|--:|--:|--:|
| 256 K | 0.18–0.20 | 0.144–0.147 | 1.24–1.36 | 82–87 GB/s |
| 1 M | 0.20–0.25 | 0.14–0.16 | 1.3–1.8 | 70–72 GB/s |
| 8 M | 0.23–0.28 | 0.14–0.16 | 1.5–1.8 | 50–62 GB/s |
| 32 M | 0.27–0.32 | 0.14–0.16 | 1.7–2.2 | 40–45 GB/s |

这张表有三处读法。第一，倍数随规模上升：256 K 是 1.24，32 M 到 2.2。工作集小，AoS 白搬的 12 B 大多还在缓存里；工作集超过末级，白搬的每一字节都要走一次 DRAM，倍数才往 4 靠。第二，SoA 的 ns/元素几乎不动（0.14–0.16），AoS 从 0.18 爬到 0.32——SoA 卡在加法吞吐上，AoS 卡在搬运上。第三，AoS 的**行带宽**自己也从 87 掉到 40 GB/s：连「搬」都不是免费的，工作集一大，页表与末级都吃紧。

所以「16 B : 4 B 必然换来 4 倍时间」不成立。4 倍是字节比，也是缺失比；时间比还要看另一侧有没有别的瓶颈先到顶。

### cachegrind 数一遍：正好 4.0 倍

N=1M，加 `-g` 重编，让 cachegrind 把每次访存记下来：

```bash
gcc -std=c17 -D_GNU_SOURCE -Wall -Wextra -O2 -g soa.c -o soa_g
valgrind --tool=cachegrind --cache-sim=yes --cachegrind-out-file=cg.soa ./soa_g 1048576
cg_annotate cg.soa | grep -E 's2 \+='
```

`cg_annotate` 把两条内层循环分开报（这是这台 VM 上的实测）：AoS 的 `s2 += a[i + 2].x` 一行 D1 读缺失 1,310,720，旁边 `s0 += a[i].x` 一行只有 5 次；SoA 的 `s2 += x[i + 2]` 一行 327,685。程序跑 5 轮，所以这两个数是 5 轮合计：

| 循环 | D1mr（5 轮） | 每轮 | 每元素 |
|:--|--:|--:|--:|
| AoS 只读 `x` | 1,310,725 | 262,145 | 0.25 次 |
| SoA 只读 `x` | 327,685 | 65,537 | 0.0625 次 |

比值 $262145 / 65537 = 4.0$，与 16 B : 4 B 完全一致。0.25 次/元素也能直接算：一行 64 B 装 4 条记录，每 4 个元素付一次缺失；SoA 一行装 16 个 `float`，每 16 个元素一次。

这里有个容易踩的坑：cachegrind 数的是整个进程，循环跑 5 轮就数 5 轮。看到 131 万不要以为「一次求和缺了 131 万次」，那是 5 轮的总和；先换成每轮或每元素的率，才不会错。

::: def 定义 1.6.13 · AoS、SoA 与行利用率 {#def-1.6.13}
结构体数组（array of structures，AoS）把一条记录的所有字段放在一起，`a[i].x` 与 `a[i].y` 相邻；拆分数组（structure of arrays，SoA）把同一字段连续放，`x[i]` 的下一个元素是 `x[i+1]`。行利用率是一行里被用到的字节除以行大小：16 B 的记录只读 4 B 字段时，一行 64 B 装 4 条记录、用掉 16 B，AoS 是 1/4；SoA 是 1。缺失数大致与行利用率成反比。
:::

### 什么时候值得换布局

四个前提同时成立才值得改：记录里字段多、一次只读少数几个（行利用率不高于 1/4）；循环能向量化，不被依赖链或分支卡住；工作集大于末级缓存，白搬的字节真的要去 DRAM；这个循环在 profile 里排得上号。

反过来，三种情况别改：按 id 随机访问单条记录，AoS 一条记录碰一行，SoA 要跳三个数组、多三次 TLB 查找；写多读少，SoA 的写要打散到多个数组，写合并变差；工作集本来就装得下，256 K 那行只差 1.2 倍。

::: ex 例 1.6.13 · 先猜倍数往哪边走 {#ex-1.6.13}
同一份代码，只把规模从 1 M 加到 32 M（AoS 侧工作集从 16 MB 到 512 MB）。先猜：倍数会变大、变小还是不变？再猜：cachegrind 的缺失比 4.0 与墙钟比 1.4，哪一个能搬到另一台机器上？

::: sol 解答
变大：实测从 1.3–1.8 走到 1.7–2.2。规模小的时候，AoS 白搬的 12 B 大多还留在缓存里；工作集超过末级，白搬的字节才真的落到 DRAM，字节比才转成时间比。它也不会到 4：SoA 一侧早就卡在加法吞吐上（0.14–0.16 ns/元素，不随规模变），再省字节也快不下去。

两个都不能直接搬。缺失比 4.0 是布局的固有比例，换机器仍然成立；墙钟比取决于机器多快、预取多强、缺失能重叠多少。要用缺失比判断「值不值得改」，用墙钟比判断「改完能拿多少」。
:::
:::

::: errata 关于 AoS 与 SoA 的误解
1. **「缺失多 4 倍，时间就慢 4 倍」**——实测 1.2–2.2 倍。多个缺失可以同时在途，顺序流还有预取提前拉行；缺失数只说明搬了多少次，不说明等了多少时间。
2. **「SoA 一定比 AoS 快」**——256 K 时只快 1.24 倍；若循环被单累加器的依赖链卡住，差距会被压到 1.0（[1.6.6](#sec-1.6.6)）。
3. **「`effective GB/s` 高就是效率高」**——AoS 的 useful 只有十几 GB/s，是分子只算 4 B；按行字节算它有 50–62 GB/s，比 SoA 还高。分母不同，不能横着比。
4. **「cachegrind 的时间比可以拿来预测性能」**——模型里每次缺失是固定代价、不许重叠，同一个程序它给出 2.5 倍，真机只有 1.4–1.8 倍。
5. **「倍数是个常数」**——同一份代码，倍数随工作集从 1.24 走到 2.2；工作集决定白搬的字节要不要真的走 DRAM。
:::

::: note Rust 里的 AoS/SoA
Rust 的 `Vec<Particle>` 就是 AoS，`struct SoA { x: Vec<f32>, y: Vec<f32> }` 就是 SoA。借用检查器不允许同时可变借用 `x` 与 `y` 的同一元素，却允许同时借用两个不同的 `Vec` 字段，所以 SoA 在 Rust 里更容易写出无别名、可向量化的循环。游戏引擎的 ECS（实体组件系统）偏爱 SoA，也有这一层原因。
:::

### 1.6.13 小结

① AoS 与 SoA 的差别落在行利用率上：16 B 记录只读 4 B，AoS 用到一行的 1/4，SoA 用到整行；② 缺失比精确等于字节比（4.0），墙钟比只有 1.2–2.2，因为缺失可重叠、预取接住了顺序流；③ 倍数随工作集增长，不是常数；④ 换布局的四个前提缺一不可，随机访问单条记录时 AoS 反而更好。如果只记住一件事，那就是：**布局决定搬多少字节，机器决定这些字节要等多久。**

## 1.6.14 实验：用 cachegrind、perf 与 sysfs 看缓存 {#sec-1.6.14}

这一节回答：sysfs、`perf`、cachegrind 三样东西同时在手，先按什么顺序用？各自能看到什么，看不到什么？

::: preview 先抓住一件事
顺序是「读几何 → 数事件 → 验方向」：先用 sysfs 与 `getconf` 问硬件，再用 cachegrind 数缺失，最后用墙钟确认真机上也变快。这台 VM 只能走完前两步：几何字段缺失或为 0，`perf` 被 `perf_event_paranoid=4` 关死，连 2 MiB 匿名大页都没落地。做实验的规矩是把「哪一步没做成、为什么」记下来，不能拿模拟器的数当真机。
:::

### 步骤一：读几何，别猜

三条命令问同一件事，答案可能互相打架：

```bash
getconf -a | grep CACHE
lscpu -C
for d in /sys/devices/system/cpu/cpu0/cache/index*; do
    printf "%s level=%s type=%s size=%s ways=%s line=%s\n" "$(basename $d)" \
        "$(cat $d/level)" "$(cat $d/type)" \
        "$(cat $d/size 2>/dev/null || echo 无此属性)" \
        "$(cat $d/ways_of_associativity 2>/dev/null || echo 无此属性)" \
        "$(cat $d/coherency_line_size 2>/dev/null || echo 无此属性)"
done
```

`ubuntu24` 上的实测（节选）：

```text
LEVEL1_DCACHE_SIZE                 0
LEVEL1_DCACHE_LINESIZE             64
LEVEL2_CACHE_SIZE                  0
...
index0 level=1 type=Data size=无此属性 ways=无此属性 line=无此属性
index1 level=1 type=Instruction size=无此属性 ways=无此属性 line=无此属性
index2 level=2 type=Unified size=无此属性 ways=无此属性 line=无此属性
```

三处判读。一，`getconf` 只有 `LINESIZE` 是 64，其余是 0——0 表示「不知道」，不表示「没有」。二，sysfs 的 `index0` 连 `size`、`ways_of_associativity`、`coherency_line_size` 三个文件都不存在，比 0 更彻底：虚拟化层根本没把拓扑报给 guest。三，`lscpu -C` 只列出 `L1d`／`L1i`／`L2` 三行，`WAYS`、`SETS`、`COHERENCY-SIZE` 全空。

结论：这台机器上**唯一可信的参数是行大小 64 B**。往下的推演只能用它；容量与相联度要么靠测量反推（[1.6.1](#sec-1.6.1) 的指针追逐），要么用模拟器的固定模型。

### 步骤二：perf——先看权限，再看事件

```bash
command -v perf && perf --version
cat /proc/sys/kernel/perf_event_paranoid
perf stat -e cache-misses true
```

实测：

```text
perf version 7.0.14
4
Error:
No supported events found.
```

`paranoid=4` 是这套内核里最严的一档，普通账户连软件事件都开不了。这不是命令写错；改 `/proc/sys/kernel/perf_event_paranoid` 需要 root，而这台 VM 的 sudo 要密码。

没有权限时还剩三条路：读 `/proc/meminfo` 的 `HugePages_*`、`/sys/kernel/mm/transparent_hugepage/enabled` 这类状态字段（免特权可读）；在能改 `paranoid` 的机器上跑同一组 `-e` 事件；用 cachegrind 顶替「数缺失」这一半。dTLB 缺失数没有替代品，只能退到「换页大小前后比墙钟」。

### 步骤三：cachegrind 数一组，看清缺在哪一层

实验程序把 [1.6.5](#sec-1.6.5) 的两个内核抄成一份，再加两个变体：只扫 `B`（不写 `C`）、只扫 `C`（不读 `B`），共用同一组矩阵，边长 192，用 `argv` 选入口。每个入口单独跑一遍 cachegrind（`-g` 编译才有行号）：

```bash
gcc -O2 -g -std=c17 mm.c -o mm
valgrind --tool=cachegrind --cache-sim=yes --cachegrind-out-file=cg.ikj ./mm 192 ikj
cg_annotate cg.ikj | head -20
```

四个入口的实测计数：

| 入口 | D1 缺失 | LLd 缺失 | 说明 |
|:--|--:|--:|:--|
| `ijk` | 7,254,828 | 904,387 | $B$ 按列走，约 $N^3$ |
| `ikj` | 910,312 | 909,851 | 与「只扫 `B`」几乎相等 |
| 只扫 `B` | 901,082 | 900,621 | $B$ 自己的 $N^3/8$ |
| 只扫 `C` | 25,384 | 24,923 | $C$ 的行留下，只有 $N^2/8$ 量级 |

四条判读。第一，`ijk` 的 725 万与 $N^3 = 7.08$ M 几乎相等，说明每个 $B$ 元素都付了一次缺失。第二，`ikj` 与「只扫 `B`」相差不到 1%，缺失几乎全在 $B$ 身上。第三，「只扫 `C`」只有 2.5 万——$C$ 的行写一次就留在缓存里，这就是 [1.6.5](#sec-1.6.5) 说 `ikj` 约 $N^3/8$、而不是 $N^3/4$ 的道理。第四，[1.6.8](#sec-1.6.8) 那张表的 2175 万／271 万正好是这里的 3 倍：它的程序每个内核跑三遍取最好，cachegrind 把三遍都数了进去；两者的比值都是 8.0。

### 步骤四：大页——先确认前提成立

大页这步先读状态，不急着测：

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
cat /sys/kernel/mm/transparent_hugepage/hpage_pmd_size
grep -i huge /proc/meminfo | head -5
```

```text
always [madvise] never
2097152
AnonHugePages:         0 kB
FileHugePages:    151552 kB
HugePages_Total:       0
```

开关是 `madvise`、透明大页的粒度是 2 MiB，`khugepaged` 也在跑。那就试一次「申请 64 MiB、`madvise` 之后再落页」：

```c
/* anon_huge() 读 /proc/meminfo，打印 AnonHugePages 那一行 */
char *p = mmap(NULL, SZ, PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);   /* 必须页对齐 */
memset(p, 1, SZ);
anon_huge("先 touch 一遍：");
madvise(p, SZ, MADV_HUGEPAGE);
memset(p, 2, SZ);
anon_huge("madvise 之后再 touch：");
```

实测输出：

```text
先 touch 一遍： AnonHugePages:         0 kB
madvise 之后再 touch：AnonHugePages:         0 kB
```

`madvise` 返回 0，不报错，可一个 2 MiB 大页都没生成。所以「大页有没有生效」要读 `AnonHugePages` 判断，不能看 `madvise` 的返回值；这台 VM 上没生效，接下来就不该拿它做 dTLB 前后的对比。在支持 THP 的机器上，同一程序应看到这个数涨到接近 64 MiB。

顺带一个坑：第一次用 `malloc` 拿的缓冲区直接 `madvise`，返回 `EINVAL`。`MADV_HUGEPAGE` 要求起始地址按页对齐，`malloc` 的返回值不保证；换成 `mmap` 就好了。

### 步骤五：内存山——台阶被依赖链盖住

把「工作集 × 步长」一次扫完，是 [1.6.6](#sec-1.6.6) 之外另一种看法：每个格子是一项读吞吐，台阶对应缓存层，斜坡对应步长浪费。在这台 VM 上跑 4×3 的网格，读数从 32 KiB／步长 8 的 19 GB/s，到 64 MiB／步长 512 的 1.1 GB/s——数字是对的，台阶却看不出来：单个 `sink += buf[i]` 的加法依赖链先把吞吐封在 13–28 GB/s（[1.5.10](ch05.md#sec-1.5.10) 算过这条链），起伏和台阶一样高。想看清台阶，要么换多个累加器，要么直接用 [1.6.1](#sec-1.6.1) 的指针追逐——它把依赖链和预取一起绕开了。

::: method 一份实验记录该有的五列
1. **测什么**：缺失数、墙钟，还是状态字段？三者不能混着写。
2. **在哪台机器**：VM 还是裸机、几个核、内核版本；跨机器比较之前先看这一列。
3. **工具与模型**：cachegrind 的 L1／LL 参数要抄进记录，它是假机器，不是被测的那台。
4. **重复次数**：cachegrind 数的是整个进程，循环几轮就乘几；墙钟要跑 5–8 次给范围，不给单点。
5. **没做成的部分**：没权限、字段缺失、大页没生效，写在结论旁边，别留白。
:::

::: ex 例 1.6.14 · 先猜单次是多少 {#ex-1.6.14}
有人把 [1.6.8](#sec-1.6.8) 的表当成「一次运行的缺失数」，据此说 `ikj` 在 $N=192$ 缺 271 万次。先猜：真跑一次是多少？再猜：把同一个内核改成跑 10 轮，cachegrind 的计数与墙钟各会怎样？

::: sol 解答
90 万上下（271.2 万 ÷ 3）。那个程序每个内核跑三遍取最好成绩，cachegrind 数的是整个进程，三遍都进了账；单遍实测 910,312，与「只扫 `B`」的 901,082 相差不到 1%。

跑 10 轮，计数线性涨到 10 倍——模拟器逐条解释指令，结果完全确定，重跑一次数字一样。墙钟不会跟着涨 10 倍：程序取的是 10 轮里最好的一轮，稳态下这个值基本不变。所以「计数」和「计时」对重复次数的反应完全不同，写实验记录时必须分开写。
:::
:::

::: errata 关于三件工具的误解
1. **「sysfs 里有 `size` 就是真机容量」**——这台 VM 连 `size` 属性都没有；有属性的机器上，报出来的值也可能是虚拟化层给的近似值。
2. **「装了 `perf` 就能数事件」**——`paranoid=4` 时 `perf stat` 直接报 `No supported events found`。这不是事件名写错，是权限；`-e` 换多少个名字都一样。
3. **「cachegrind 报 16 KiB L1，说明我的 L1 是 16 KiB」**——那三行是编译进 cachegrind 的模型参数，与被测机器无关。
4. **「`madvise` 返回 0 就是大页生效」**——返回 0 只说明参数合法、地址对齐；有没有真的用上 2 MiB 大页，要读 `/proc/meminfo` 的 `AnonHugePages`。
5. **「模拟器的缺失数可以预测墙钟」**——同一个 AoS 程序，cachegrind 给出 2.5 倍、真机只有 1.4–1.8 倍（[1.6.13](#sec-1.6.13)）。模型里每次缺失是固定代价，真机上缺失可以重叠。
:::

### 1.6.14 小结

① 顺序是读几何、数事件、验方向：sysfs 回答「硬件报了什么」，cachegrind 回答「缺了多少次」，墙钟回答「真机快了多少」；② 这台 VM 上只有行大小 64 B 可信，`perf` 因 `paranoid=4` 不可用，2 MiB 匿名大页也没落地；③ cachegrind 的模型参数不是真机，计数还会随重复次数成倍增长；④ 大页这类优化要先读状态字段确认前提，再谈效果。如果只记住一件事，那就是：**先问工具数的是哪台机器、数了几遍，再问数出来的差意味着什么。**

::: method 即时自测 · 1.6.14
**Q1（记忆）** 实验的推荐顺序是哪三步？每一步各回答什么问题？

**Q2（辨析）** `getconf` 说 L1 是 0，cachegrind 说 L1 是 16 KiB。哪个是真的？

**Q3（应用）** 在 `paranoid=4` 的机器上，你想知道一个循环的缺失多不多。写出两条可执行的替代路径，并说明各自的局限。

**Q4（迁移）** 一台机器 `madvise(MADV_HUGEPAGE)` 返回 0，但 `AnonHugePages` 不动。下一步该查什么？给出两个方向。

::: sol 答案
**A1** 读几何（sysfs 与 `getconf` 报了什么）、数事件（cachegrind 数出缺多少）、验方向（墙钟确认真机也变快）。三步分别对应「硬件自述」「事件计数」「真实时间」。
**A2** 两个都不是「这台机器的 L1 容量」。0 是接口不知道；16 KiB 是 cachegrind 编译进去的模型。真机容量要靠指针追逐量台阶（[1.6.1](#sec-1.6.1)）反推。
**A3** 一，用 cachegrind 数缺失，局限是模型固定、不建模预取；二，用墙钟比两版程序，局限是只能看差别、说不清缺在哪一层。两者方向一致才算结论成立。
**A4** 先看 `/sys/kernel/mm/transparent_hugepage/enabled` 与 `hpage_pmd_size`，确认策略与粒度；再看 `/proc/meminfo` 的 `HugePages_*` 与 `AnonHugePages`，判断是「没申请到」还是「申请了没合并」。方向二：换 `mmap` 保证页对齐，或改用显式 hugetlbfs 预留的页池。
:::
:::

## 1.6.15 十二条缓存与存储陷阱 {#sec-1.6.15}

这一节回答：前面十几节的结论，落到排障现场分别长什么样？哪几条最容易把人带偏？

::: preview 先抓住一件事
十二条按「算错、测错、写错、选错」分四组。每条都配同一套问法：这条现象能被哪个数证实，改哪一处能让那个数动。跳过前一半就会犯最常见的错——把容量当成唯一变量，或者把模拟器、工具状态里的数当成真机的事实。
:::

| # | 现象 | 先查什么 | 常见误判 |
|--:|:--|:--|:--|
| 1 | 加大缓存后程序没变快 | 块是否全挤在同一组（[1.6.12](#sec-1.6.12) 的 576 B 0 命中） | 容量不够，继续加 |
| 2 | 按 4 KiB 步长访问极慢 | 行距 ÷ 64 与组数是否互质 | 步长大所以慢，改成 2 KiB |
| 3 | 多线程扩展性差 | 两个线程写的变量是否同一行 | 先怪锁，其实是伪共享 |
| 4 | `memset` 大缓冲区慢 | 写分配：写之前有没有先把行读进来 | 内存带宽到顶了 |
| 5 | 矩阵乘 `ikj` 的缺失比估算多一倍 | 逐数组算，$C$ 的行是否常驻 | 按 $N^3/4$ 估，把 $B$、$C$ 各算一份 |
| 6 | SSD 随机写比顺序慢、寿命掉得快 | 请求大小、队列深度、写放大 | 写得太多，其实是写得碎 |
| 7 | 结构体数组遍历慢 | 行利用率：一条记录多少字节、用掉多少 | 数组太大 |
| 8 | 分块后更慢或没变化 | 工作集是否本来就装得下（[1.6.5](#sec-1.6.5)） | 块没调对，继续扫块大小 |
| 9 | `perf` 打不开、miss 数全 0 | `perf_event_paranoid` 与容器权限 | 事件名写错，换 `-e` |
| 10 | 大页没生效 | `AnonHugePages` 是否增长、地址是否页对齐 | `madvise` 返回 0 就成了 |
| 11 | NUMA 机器上性能抖动 | 线程与内存是否同节点 | 机器坏了，重装系统 |
| 12 | cachegrind 与真机差很多 | 模型参数与重复次数 | 真机缺失就是这个数 |

### 四组陷阱，四种问法

**算错组（1、2、5、8）**都输在一条算术上：组号是 $(\text{addr}/64) \bmod S$，行距与 $S$ 的整除关系决定块落在哪几组。9 个页、576 B 的工作集能在一台 32 KiB 的缓存里 0 命中（[1.6.12](#sec-1.6.12)），因为 9 个块挤在同组，8 路装不下。这一类不用换机器，纸笔就能证伪。

**测错组（9、10、12）**输在没读工具的前提。`perf` 在 `paranoid=4` 下一个事件也不给；`madvise` 返回 0 只说明参数合法，大页有没有落地要看 `AnonHugePages`；cachegrind 的 16 KiB／256 KiB 是编译进去的模型。三个工具都「能用」，但用之前要问它数的是哪台机器、数了几遍（[1.6.14](#sec-1.6.14)）。

**写错组（3、4、7）**输在布局与写策略：两个线程写同一行的两个变量，行在核间来回弹（[1.6.11](#sec-1.6.11)）；`memset` 先按写分配把行读进来；只读一个字段却搬整条记录（[1.6.13](#sec-1.6.13)，缺失正好 4.0 倍）。

**选错组（6、11）**输在把介质与拓扑当成均匀的：SSD 的随机写要经过页／块粒度与垃圾回收，跨节点访存比本地贵一截（[1.6.7](#sec-1.6.7)）。这两条改代码没用，要改数据放置。

### 第 5 条单独说：系数是 $N^3/8$，不是 $N^3/4$

`ikj` 内层沿 `j` 走，$B$ 与 $C$ 都按行连续。$B$ 的每个元素只在这一遍用一次，一行 8 个 `double` 搬进来正好用满，于是每 8 个元素一次缺失，合计 $N^3/8$——这是**一个数组**的账。

$C$ 也按行扫，但它的行在内层被反复写，写完就留在 L1，只有第一次碰它要付钱：$N^2/8$（[1.6.5](#sec-1.6.5) 逐行算过）。把 $B$、$C$ 各按 $N^3/8$ 相加得到 $N^3/4$，等于把 $C$ 算了两遍，而它并没有每次都从内存重来。[1.6.14](#sec-1.6.14) 的实测正好对上：$N=192$ 时只扫 $C$ 的入口缺 2.5 万次，只扫 $B$ 的入口缺 90 万次。

所以 `ikj` 按 $N^3/8$ 估。要用 $N^3/4$，前提是 $C$ 的行也装不进 L1（行特别长，或 L1 特别小）——那是另一台机器上的账，得重新算。

::: ex 例 1.6.15 · 先猜加内存有没有用 {#ex-1.6.15}
同事说：「服务器内存从 32 GB 加到 128 GB，这个双重循环还是慢。」先猜：加内存改变了哪一层、没改变哪一层？再猜：他的循环是 9 个 4 KiB 页轮流访问，加内存之后命中率会变吗？

::: sol 解答
只改了主存容量，L1／L2／L3 一个字节都没变。循环的瓶颈若是缓存容量或冲突，加内存完全无效；只有工作集大到要在主存与磁盘之间换页时，加内存才有用。

9 个页的情况命中率不变。9 个块挤在同一组，8 路装不下，这是冲突缺失，与主存多大无关（[1.6.12](#sec-1.6.12)：576 B 工作集、0 命中）。要改的是布局或相联度，不是内存条。
:::
:::

::: errata 关于存储层级的误解
1. **「SSD 没有寻道，随机读写一样快」**——NAND 有页／块粒度与垃圾回收，4 KiB 随机写仍比顺序写慢一个数量级，写放大还会缩短寿命。
2. **「L3 是所有核共享的，越大越好」**——跨核访问 L3 仍有几十个周期的延迟与带宽争用；能放进 L2 的热数据别指望 L3。
3. **「预取总是有用」**——预取错了会浪费带宽、污染缓存；随机访问或带宽已饱和时，它可能让性能更差。
4. **「十二条背下来就够了」**——每一条都绑着条件：缓存几何、块大小、工具权限、页大小。换机器、换内核版本，条件要重查。
:::

### 1.6.15 小结

① 十二条分四组：算错组查一条算术，测错组查工具前提，写错组查布局与写策略，选错组查介质与拓扑；② 每条都先找「能被证实的数」，再动手改；③ 系数要按数组算：`ikj` 的 $B$ 是 $N^3/8$，$C$ 只有 $N^2/8$，$N^3/4$ 把 $C$ 重复计了一次；④ 陷阱不是清单，是「条件 + 判据」的组合。如果只记住一件事，那就是：**先问这条现象能被哪个数证实，再问改哪一处能让那个数动。**

::: method 即时自测 · 1.6.15
**Q1（记忆）** 十二条分哪四组？每组各举一条。

**Q2（辨析）** `ikj` 的缺失为什么是 $N^3/8$ 而不是 $N^3/4$？在什么条件下 $N^3/4$ 反而对？

**Q3（应用）** 一个双线程程序，两个线程各写 `struct { long a; long b; }` 的 `a` 和 `b`，结果正确但扩展性差。写出诊断顺序与两种改法。

**Q4（迁移）** 有人说「cachegrind 显示末级缺失 270 万，所以真机也要搬 270 万次」。按本章的口径，这句话有几处要改？

::: sol 答案

## 1.6.16 手算矩阵乘的缓存流量：分块为什么有效 {#sec-1.6.16}

这一节回答：分块能把矩阵乘的字节流量从 68 GB 压到 410 MB，为什么墙钟一点没快？

::: preview 先抓住一件事
流量账能算，而且要和机器对上：把字节数除以运行时间，得到「每秒搬了多少」，再和实测带宽比。比完会发现 `ikj` 每秒只搬 28 GB 左右，离这台 VM 的顺序读上限还有余量；它的 2.15 GFLOP 却正好用满 7.1 GFLOPS 的单核算力。分块把字节压到 1/21，压的是已经不紧的那一头，所以快不了。[1.6.5](#sec-1.6.5) 已经用实测讲过这个现象，这一节把它算成账：字节、算术强度、拐点。
:::

### 两笔账：朴素版与 ikj

$N=1024$ 时每个矩阵 8 MB，远大于末级缓存，所以每跨一步、每换一行，都要真的去内存取。两种内层的账完全不同：

```c
/* ijk：内层沿 B 的列走，地址步长 N*8 字节 */
for (i) for (j) { s = 0; for (k) s += A[i*n+k] * B[k*n+j]; C[i*n+j] = s; }

/* ikj：内层沿 B、C 的行走，每 8 个元素换一行 */
for (i) for (k) { a = A[i*n+k]; for (j) C[i*n+j] += a * B[k*n+j]; }
```

| 版本 | 内层每一步搬的字节 | 缺多少次 | 总流量（$N=1024$） |
|:--|:--|--:|--:|
| `ijk` | 64 B 整行，只用其中 8 B | 约 $N^3$ | 68.7 GB |
| `ikj` | 8 B，一行 64 B 用满 | 约 $N^3/8$ | 8.6 GB |

两个数的算法一样：缺失次数乘 64 B。`ijk` 每读一个 $B_{kj}$ 都落在新行上，$1.07 \times 10^9$ 次乘 64 B 就是 68.7 GB；`ikj` 每 8 个元素才换一行，$1.34 \times 10^8$ 次乘 64 B 是 8.6 GB。矩阵本身只有 8 MB，两个版本都把它搬了几百上千遍。

这个账有个前提：矩阵远大于末级缓存。$N=192$ 时 $B$ 只有 288 KiB，几乎装得进 cachegrind 那个 256 KiB 的假末级，再用「每次都缺」的上界去估就会高出一个数量级——[1.6.14](#sec-1.6.14) 的实测里 `ijk` 的末级缺失只有 90 万次（约 58 MB），而按 $N^3$ 算的上界是 453 MB。**先确认工作集真的超出缓存，再用这个上界。**

### 分块省的是字节

把 $i,j,k$ 各切成边长 $b$ 的块，内层在 $b \times b$ 的子矩阵上乘加。块内三个子矩阵同时活跃：

$$
3b^2 \times 8 \le \text{L2} \quad\Longrightarrow\quad b \le \sqrt{\frac{\text{L2}}{24}}.
$$

L2 为 256 KB 时 $b \le 104$，取 64 留余量；L2 为 1 MB 时 $b \le 208$，取 128 或 256。$b=64$、$N=1024$ 时各矩阵的流量：

| 矩阵 | 流量公式 | $N=1024,b=64$ |
|:--|:--|--:|
| $A$ | $n^2 \times 8$，被 $(n/b)^2$ 个块复用 | 8 MB |
| $B$ | $(n/b)^3 \times b^2 \times 8 = n^3/b \times 8$ | 134 MB |
| $C$ | 读一次写一次，约 $B$ 的两倍 | 268 MB |
| 合计 | — | 约 410 MB |

对照上面的两笔账：比 `ijk` 的 68.7 GB 少约 170 倍，比 `ikj` 的 8.6 GB 少约 21 倍。这就是「分块为什么有效」的全部理由——**它把内存流量压了一个数量级**。

### 拐点：算术强度与机器平衡

只算字节还不够，要把它和算力放在同一把尺子上。**算术强度**（arithmetic intensity）是每搬 1 字节做多少次浮点运算；**机器平衡点**是峰值算力除以可持续带宽。

- `ikj`：每元素 2 次浮点、搬 8 B，强度 $2/8 = 0.25$。
- 分块 $b=64$：2.15 GFLOP 对应 0.41 GB，强度约 5.2。
- 这台 VM：单核双精度约 7.1 GFLOPS（[1.6.5](#sec-1.6.5) 的 301 ms 对应的就是它），顺序读 512 MB 工作集实测约 33 GB/s（同一台机器 64 MB 工作集能到 74 GB/s，工作集越大越低），平衡点约 $7.1/33 \approx 0.22$。

强度低于平衡点，程序在等带宽，省字节有用；高于平衡点，程序在等算力，省字节白省。`ikj` 的 0.25 刚过线，分块的 5.2 早在线的右边。于是时间下限被算力钉住：$2.15\ \text{GFLOP} / 7.1\ \text{GFLOPS} \approx 303$ ms，实测 301.3 ms——已经贴底，分块再省字节也压不下去。

### 实测：边长加到 2048 也不赢

把边长翻倍，工作量涨 8 倍。在这台 VM 上实测（同一份代码，3 次取最好）：

| 版本 | $N=1024$ | $N=2048$ |
|:--|--:|--:|
| `ikj` | 301.3 ms | 2408.8 ms |
| 分块 $b=32$ | 331–336 ms | 3048.0 ms |
| 分块 $b=64$ | 318–383 ms | 2641.4 ms |
| 分块 $b=128$ | 327–375 ms | 2945.4 ms |

`ikj` 从 301.3 到 2408.8，正好 8.0 倍——线性，说明边长翻倍也没把它推进带宽的斜坡。分块 64 反而慢 10%：多出来的四层循环与边界判断要花钱，而它省下的字节本来就不紧。

### 块大小怎么选

| 约束 | 公式 | 例子（L1 32 KB，L2 256 KB） |
|:--|:--|:--|
| 三个块放进 L2 | $3b^2 \cdot 8 \le L2$ | $b \le 104$ |
| 一个块放进 L1 | $b^2 \cdot 8 \le L1$ | $b \le 64$ |
| 块是缓存行的倍数 | $b \times 8 \bmod 64 = 0$ | $b$ 取 8 的倍数 |
| 避免 4 KB 别名 | $b \times 8$ 不是 4096 的倍数 | $b=64$ 时 512 B，安全 |

工程上取 32、64、128 三个值各测一遍，不要用「越大越好」的直觉：块太大，$3b^2 \times 8$ 超出 L2，等于没分；块太小，循环与边界开销占比高。

### TLB 与预取

分块顺带改善 TLB：朴素版沿列走，每步跨 $N \times 8$ 字节，$N=1024$ 时一步 8 KiB，跨两三页——几乎每一步都换页；分块后一个 $b \times b$ 块只落在几页里。这台 VM 读不到 PMU，判据只能自己算：`getconf PAGE_SIZE` 给 4096，`/proc/meminfo` 的 `Hugepagesize` 给 2048 kB，再用 [1.6.7](#sec-1.6.7) 的「TLB 项数 × 页大小」估覆盖范围；要看差别，就用两版程序的墙钟比。

预取只在朴素版上有意义：它的步长是 8 KiB 且随 $N$ 变，硬件预取器跟不住；`ikj` 的步长是 8 B，硬件预取已经够用，软件预取只是多一条指令。

```c
for (int k = 0; k < n; k++) {
    __builtin_prefetch(&B[(k + 8) * n + j], 0, 1);  /* 提前 8 行 */
    s += A[i * n + k] * B[k * n + j];
}
```

提前量按「内存延迟 ÷ 每次迭代时间」估：80 ns ÷ 2 ns 约 40 个元素。太早会污染缓存，太晚来不及。这台 VM 上没做这个对比——收益与运行噪声同量级，测出来不敢下结论。

::: method 判断「要不要分块」的四步
1. **算强度**：每元素几次浮点、搬几字节，相除。`ikj` 是 0.25，分块是 5 左右。
2. **找拐点**：单核算力 ÷ 可持续带宽。本机约 0.22 次浮点/字节。
3. **比一比**：强度在拐点右边就不分块；在左边，按 $\sqrt{\text{L2}/24}$ 选块，上下各试一档。
4. **验结果**：同一份输入比对数值，边界块单独处理。
:::

::: ex 例 1.6.16 · 先猜带宽减半谁先垮 {#ex-1.6.16}
同一台机器，可持续带宽从 33 GB/s 掉到 8 GB/s，算力不变。先猜：`ikj` 与分块 64 谁先变慢、慢多少？分块这时能赢几倍？

::: sol 解答
`ikj` 先垮。它每秒要搬 28.5 GB，带宽 8 GB/s 时时间下限变成 $8.6/8 \approx 1.08$ s，是原来的 3.6 倍。分块只要 410 MB，$0.41/8 \approx 51$ ms，仍受 303 ms 的算力下限约束，几乎不变。

于是分块赢约 3.6 倍。同一个程序、同一台机器，只把带宽换掉，结论就从「分块没用」翻成「分块有用」——所以「要不要分块」问的不是代码，而是机器平衡点。
:::
:::

::: errata 关于流量与分块的误解
1. **「省 170 倍字节就快 170 倍」**——算力下限 303 ms 摆在那里，`ikj` 的 301 ms 已经在底上。
2. **「分块总是更快」**——$N=1024$ 时最好的一档也只和 `ikj` 同档，$N=2048$ 慢 10%；这台 VM 上它是负收益。
3. **「$N$ 越大分块越有用」**——边长从 1024 到 2048，`ikj` 仍是 8.0 倍线性，没有被推进带宽斜坡。
4. **「算术强度越高越好」**——超过平衡点之后再提强度，时间不再降，只多出循环复杂度。
5. **「块越大复用越多」**——$3b^2 \times 8$ 一旦超出 L2，块内数据自己就装不下，等于没分。
:::

### 1.6.16 小结

① 字节账按「缺失次数 × 行大小」算：`ijk` 是 68.7 GB，`ikj` 是 8.6 GB，分块 $b=64$ 约 410 MB；② 这个上界只在矩阵远大于末级时成立，$N=192$ 时要用实测校准；③ 省字节能不能变成省时间，看算术强度在机器平衡点的哪一侧；④ 这台 VM 的平衡点约 0.22 次浮点/字节，`ikj` 的 0.25 刚过线，所以分块省下的 21 倍流量换不来时间。如果只记住一件事，那就是：**先算强度、再找拐点，最后才决定要不要分块。**

::: method 即时自测 · 1.6.16
**Q1（记忆）** 字节账怎么算？`ijk`、`ikj`、分块 $b=64$ 在 $N=1024$ 时各是多少？

**Q2（辨析）** 分块把流量压到 1/21，墙钟却没变。用「算术强度」解释这件事。

**Q3（应用）** 一台机器峰值 50 GFLOPS、可持续带宽 10 GB/s。`ikj` 在它上面要不要改成 1.6.5 的分块？给出算式。

**Q4（迁移）** 为什么 $N=192$ 时不能用 68 GB 去估 `ijk` 的流量？给出你自己的判据。

::: sol 答案
**A1** 缺失次数乘 64 B。`ijk` 约 $N^3$ 次 → 68.7 GB；`ikj` 约 $N^3/8$ 次 → 8.6 GB；分块 64 约 410 MB。
**A2** `ikj` 的强度是 0.25 次浮点/字节，这台机器的平衡点是 0.22，已经在算力一侧；分块把强度提到 5，越过了拐点，省下的带宽不是瓶颈，时间下限由 2.15 GFLOP ÷ 7.1 GFLOPS ≈ 303 ms 决定。
**A3** 平衡点 $50/10 = 5$ 次浮点/字节。`ikj` 的 0.25 远在左边，是带宽受限，应当分块；分块后强度约 5，正好到拐点，预期收益接近流量比的平方根级别，要实测确认。
**A4** 判据是「矩阵是否远大于末级缓存」。$N=192$ 时 $B$ 只有 288 KiB，接近 256 KiB 的末级，多数列访问在末级就命中，不会每次都去内存；这时要用 cachegrind 或墙钟校准，不能套上限。
:::
:::

## 1.6.17 本章小结 {#sec-1.6.17}

这一节回答：这一章学完，你能独立算出哪几笔账、测出哪几个数、又在哪些地方必须承认「这台机器上看不见」？

::: preview 先抓住一件事
判据是：**给你一段循环，你能先算出它该搬多少字节、该缺多少次，再拿一台机器去核对——核对不上时，说得出是账算错了，还是这台机器本来就不给你看。**
:::

这一章的主线是**一次访问要走多远**：1.6.1–1.6.4 从 SRAM 到 SSD 立起层次结构与量级，再用局部性、组相联、命中/缺失/替换/写策略把这套层次变成可算的模型；1.6.5–1.6.8 把它落到矩阵乘与分块、缓存友好代码、TLB 与大页、以及 `perf`/cachegrind 两种观测手段上。1.6.9–1.6.12 走第二遍：把量级表读成数量级感，把 32 位地址拆成 tag/index/offset，把替换与写策略讲到一致性，最后写一个能跑出命中率的组相联模拟器。1.6.13–1.6.16 全部换成真机读数：AoS 与 SoA 的差距随工作集从 1.24 倍长到 2.2 倍，cachegrind 给出 262,145 对 65,537 的单轮缺失，最后用「字节数 ÷ 时间」把分块为什么在这台机器上不赢算成账。

逐条打勾的达标表在[学习目标自检表](ch06-checklist.md)。这里只留判据：

- **能算**：由容量、相联度、块大小算组数与 tag/index/offset；由步长推算缺失次数（`ijk` 约 $N^3$、`ikj` 约 $N^3/8$，而 `C` 的行常驻 L1、只付 $N^2/8$——把 `C` 也按 $N^3/8$ 算就把 `ikj` 高估了）；由工作集反推分块大小。
- **能测**：用 `clock_gettime` 做逐元素计时、用 cachegrind 拿 `D1mr`/`DLmr`、用 `getconf`/`/proc/cpuinfo` 查这台机器愿意告诉你的缓存参数；测不出来时，说得出是哪一道门挡住了。
- **能判断**：什么时候该分块（工作集装不下）、什么时候分块白干（已经撞到算力或带宽上限）、什么时候该换布局（AoS → SoA）、什么时候数字换台机器就作废。

如果只记住一件事，那就是**缓存优化的收益永远来自「复用发生在被驱逐之前」**：分块、SoA、预取都只是这一句话的不同写法；而它成不成立，取决于工作集与容量的关系、以及这台机器到底给不给你看它的容量与计数器。

::: errata 本章的三条口径边界
1. **容量与相联度：**这台 VM 不透传缓存容量（`/sys/devices/system/cpu/cpu0/cache/` 下相关属性读不到），正文里的容量只用于手算示例与 cachegrind 的模拟参数，不是本机硬件参数。
2. **`perf` 不可用：**`perf_event_paranoid=4`，硬件事件被挡住；本章所有「缺失数」要么来自 cachegrind 的模拟，要么来自手算上界，没有一条来自 PMU。
3. **分块不是万灵药：**$N=2048$ 的实测里 `ikj` 2409 ms、分块 64 反而 2641 ms——当内层已经贴着算力上限时，减少缺失不再换来时间。
:::

**下一站**：知道了数据要搬多远，下一步是「程序怎么变成一个能跑的东西」——编译器产出目标文件，链接器把符号拼成可执行文件，加载器把它映射进地址空间。符号解析、重定位、PLT/GOT、PIE 与 `LD_PRELOAD` 都在 [1.7 链接与加载](ch07.md)；本章的分块与局部性会在 [1.9 虚拟内存](ch09.md) 里换成页与 TLB 的语言再讲一遍。

::: method 即时自测 · 1.6
**Q1（算）** 32 位地址、64 B 块、8 路组相联、容量 32 KiB：组数、index 位数、offset 位数、tag 位数各是多少？

**Q2（算）** $N=1024$ 的 `double` 矩阵乘，`ijk` 与 `ikj` 各约缺多少次、各搬多少字节？为什么两者之比约 8，墙钟却只有 5 倍左右？

**Q3（判）** 一台机器的 L2 是 256 KiB，你要给 $N=1024$ 的矩阵乘选块大小。写出约束式并给出一个取值；如果实测发现分块没变快，先查哪两件事？

**Q4（测）** 手边只有 `clock_gettime`，没有 `perf`。你怎么证明「这段循环慢在缓存而不是算力」？给出至少两条互相独立的证据。

::: sol 答案
**A1** 组数 $S = 32768/(8 \times 64) = 64$，index 6 位、offset 6 位、tag $= 32 - 6 - 6 = 20$ 位。

**A2** `ijk` 内层沿 `B` 的列走，步长 $8N$ 字节，每次都是新行，约 $N^3 \approx 1.07 \times 10^9$ 次，乘 64 B 约 68.7 GB；`ikj` 每 8 个元素换一行，约 $N^3/8 \approx 1.34 \times 10^8$ 次，约 8.6 GB。比值 8 是缺失数之比，不是时间之比：`ikj` 已经把单核算力跑满（301 ms 对 2.15 GFLOP，约 7.1 GFLOPS），缺失再少也快不下去，而且多个缺失同时在途会把单次代价摊薄。

**A3** 约束是三个 $b \times b$ 块同时驻留：$3b^2 \times 8 \le 256\ \text{KiB}$，得 $b \le 104$，取 64 留余量。没变快先查两件事：工作集是不是本来就装得下（装得下时缺失本来就不多，分块只剩开销），以及是不是已经撞到算力/带宽上限（此时缺失不是瓶颈）。

**A4** ① 做「只扫 `B`、只扫 `C`」两个剥离版本，如果时间随访问步长而不是随运算量变化，慢在搬运；② 用 cachegrind 数 `D1mr`/`DLmr`，缺失数随块大小下降而时间不降，说明瓶颈已不在缓存；③ 把同一算法换成 SoA 布局，时间显著下降而运算条数不变——三条里有两条同向即可下结论，单看时间不行。
:::
:::
