[1.1](ch01.md) 把 `hello.c` 走了一遍「预处理—编译—汇编—链接—加载」。那里只掀开了链接阶段的一角：可执行文件里有一个 `puts@plt`，真正的 `puts` 在 `libc.so.6` 里，运行时才被接上。这一章把这一角完全打开。

链接器面对的不是源代码，而是一组**可重定位目标文件**和**归档库**。它要解决两个问题：同一个符号在多个文件里出现时听谁的（符号解析）；指令里留下的地址空洞填什么（重定位）。这两个问题决定了你日常遇到的一多半构建错误：`multiple definition`、`undefined reference`、`cannot find -lxxx`、`symbol lookup error`。

加载则是另一个程序的工作。内核只把 `PT_LOAD` 段映射进地址空间，动态链接器 `ld.so` 接着解析依赖、填 GOT、调用构造函数，最后才跳到 `_start`。把链接与加载分开看，你才能理解「编译通过、链接失败、运行时报找不到符号」分别发生在哪一层。

## 1.7.1 链接器在流水线中的位置 {#sec-1.7.1}

这一节回答：你敲下 `gcc hello.c -o hello`，实际被依次叫起来的是哪几个程序？链接器拿到的输入是什么，它又把什么交给内核？

::: preview 先抓住一件事
`gcc` 是驱动，不是编译器。它依次调用预处理、编译、汇编，最后让 `collect2` 去调 `ld`。链接器只认可重定位目标文件（`.o`，类型 `ET_REL`）和归档库（`.a`），产物是 `ET_EXEC` 或 `ET_DYN`。这条边界解释了最常见的一类事故：语法全对，`-c` 也能过，一到链接就 `undefined reference`。
:::

### 1.7.1 让驱动自己交代

在 VM（Ubuntu 24.04.5 / aarch64 / GCC 13.3）上编一份两行的 `hello.c`，打开 `-v`。下面把 `collect2` 那一行按空格拆开，只留关键项（实测整理，内容未改）：

```text
/usr/libexec/gcc/aarch64-linux-gnu/13/collect2
-dynamic-linker
/lib/ld-linux-aarch64.so.1
-pie
.../Scrt1.o
.../crti.o
.../crtbeginS.o
-lc
.../crtendS.o
.../crtn.o
```

三个读点。第一，`Scrt1.o` 这些启动对象不是你写的，`_start` 就来自这里；PIE 链接用 `Scrt1.o`，非 PIE 换成 `crt1.o`。第二，`-dynamic-linker` 把解释器路径写进 `PT_INTERP`，内核装载时先映射它，再跳到 `_start`（1.7.5 展开）。第三，`-lc` 由驱动补上，你只写了源码。

`-pie -z now -z relro` 是发行版的默认加固组合：产物是位置无关可执行文件，动态符号在装载时一次绑完。换发行版或加 `-no-pie`，这行会变；判断依据永远是 `gcc -v`，不是记忆。

`collect2` 是 `ld` 的包装：先调用 `ld`，再检查输出里的构造与析构符号，必要时补一段汇总代码。`.init_array`、`.fini_array` 这两个数组最后由运行时代码在 `main` 前后遍历。调用链记住一条就够：`gcc → cc1 → as → collect2 → ld`。

### 1.7.1 链接器的四步

链接器只做四件事，每一步都对应一类报错：

| 步骤 | 做什么 | 失败时的典型报错 |
|:--|:--|:--|
| 符号解析 | 给每个未定义符号找到唯一强定义 | `undefined reference to 'foo'` |
| 合并节 | 把所有 `.text`/`.data`/`.rodata` 拼成输出节 | 很少直接报错 |
| 重定位 | 按重定位表改写指令与数据里的地址 | `relocation truncated to fit` |
| 布局 | 分配虚拟地址、生成程序头、设定入口 | `section .text will not fit` |

从一份 C 程序出发，输入有两类。`.o` 是 `ET_REL`，每个节都从地址 0 起算，指令里的地址是占位；`.a` 只是 `ar` 打包的一串 `.o`，没有额外魔法。输出是 `ET_EXEC` 或 `ET_DYN`：前者地址在链接期定死，后者只定相对布局，装载时再加基址——PIE 与 `.so` 都属于后者。

### 1.7.1 编译过、链接不过

写一个只有声明、没有定义的函数：

```c
/* missing.c */
extern int missing(void);
int main(void) { return missing(); }
```

`gcc -c missing.c` 退出码 0，`nm missing.o` 里只有一行 `U missing`。换成完整链接 `gcc missing.c -o missing`，实测输出：

```text
/usr/bin/ld: /tmp/ccpbEpZH.o: in function `main':
missing.c:(.text+0x8): undefined reference to `missing'
collect2: error: ld returned 1 exit status
```

编译器只检查声明与调用是否匹配，它不知道别的 `.o` 里有没有定义。链接器才拿着全部 `.o` 与库，给每个 `U` 找唯一一个定义；找不到就停在这里，运行时的事还轮不到。

::: def 定义 1.7.1 · 静态链接与动态链接 {#def-1.7.1}
**静态链接**在构建时把被引用模块的代码与数据复制进可执行文件，产物不依赖外部库文件；**动态链接**只在产物里记录共享库名字与符号引用，把绑定推迟到装载时或首次调用，由动态链接器完成。分界不是「有没有库」，而是「绑定发生在构建期还是运行期」。
:::

::: errata 关于链接位置的五个误解
1. **「`gcc` 就是编译器」**——它是驱动；真正编代码的是 `cc1`，汇编是 `as`，链接是 `collect2` 背后的 `ld`。
2. **「`gcc -c` 过了，程序就能跑」**——`-c` 只到目标文件，符号表与重定位表都还是未结清的账。
3. **「链接器会把 `.c` 拼起来」**——它只读 `.o` 与 `.a`，源码在编译阶段就退场了。
4. **「`-lc` 是我写的」**——驱动自动补；只有 `-nostdlib` 才拿掉，代价是 `_start`、`__libc_start_main` 与全部 libc 符号都要自己补。
5. **「PIE 只影响安全」**——它还改变 `e_type`（`ET_DYN` 对 `ET_EXEC`）与地址的定法，`readelf -h` 第一眼就能看出来。
:::

### 1.7.1 小结

① `gcc` 是调度员，真正的链接由 `collect2` 调 `ld` 完成；驱动替你补启动对象、解释器路径与 `-lc`。② 链接器只吃 `.o` 与 `.a`，做符号解析、合并节、重定位、布局四件事。③ `-c` 通过只证明单个文件内部自洽，跨文件的定义与地址要到链接期才结账。如果只记住一件事，那就是：**看到 `undefined reference` 先想链接器缺了哪个定义，不要回头改语法。**

**Q2（辨析）** `fatal error: foo.h: No such file or directory` 与 `undefined reference to 'foo'`，各发生在哪个阶段？

**Q3（应用）** `gcc -v` 里出现 `-dynamic-linker /lib/ld-linux-aarch64.so.1`。这个路径被写进 ELF 的哪里？谁读它、什么时候读？

**Q4（迁移）** 交叉编译时能编出 `.o`，却常常链不出可执行文件。用本节的四步解释缺的是哪一步的什么材料。

::: sol 答案

**A3** 写进 `PT_INTERP` 段。内核在 `execve` 装载时读取，映射解释器后把控制权交给它，再由它跳到程序入口。
**A4** 缺的是布局与重定位所需的启动对象和目标平台 libc：`Scrt1.o`/`crti.o`/`crtn.o` 与 `libc.so`。`-c` 只做编译与汇编，不需要这些；链接一步既要把它们拼进来，也要按目标平台的规则填地址。

## 1.7.2 ELF：节、段与符号表 {#sec-1.7.2}

这一节回答：同一个 ELF 文件，为什么链接器按「节」工作、内核按「段」工作？符号表里一行的 `LOCAL`、`GLOBAL`、`UND`，各自决定了什么？

::: preview 先抓住一件事
ELF 是同一个容器装的三种身份：`.o`（`ET_REL`）、可执行文件（`ET_EXEC` 或 `ET_DYN`）、共享库（`ET_DYN`）。节是链接器拼接的抽屉，段是内核映射的整页；`.o` 只有节、没有程序头。符号表把名字连到「哪个节、什么类型、是否已定义」，`strip` 只删编辑用的 `.symtab`，运行时用的 `.dynsym` 必须留下。
:::

### 1.7.2 先认身份：`e_type` 与程序头

先看一个 `.o`，再看一个可执行文件：

```text
$ readelf -hW elf.o | grep -E 'Type|Machine|Entry|program headers'
  Type:                              REL (Relocatable file)
  Machine:                           AArch64
  Entry point address:               0x0
  Number of program headers:         0
$ readelf -lW elf.o
There are no program headers in this file.
```

`ET_REL` 里每个节都从地址 0 起算，还没有「装到进程里」这回事，所以没有程序头。可执行文件不同：`readelf -hW hello` 报 `Type: DYN`、`Entry point 0x680`，程序头表随之出现。入口是 `Scrt1.o` 里的 `_start`，不是 `main`；`main` 的地址在符号表里另有一行。

### 1.7.2 节：链接器的抽屉

`readelf -SW elf.o` 的节表（实测节选，地址列全为 0）：

```text
[Nr] Name              Type            Address          Off    Size   ES Flg Lk Inf Al
[ 1] .text             PROGBITS        0000000000000000 000040 00006c 00  AX  0   0  4
[ 2] .rela.text        RELA            0000000000000000 000350 0000d8 18   I 10   1  8
[ 3] .data             PROGBITS        0000000000000000 0000ac 000004 00  WA  0   0  4
[ 4] .bss              NOBITS          0000000000000000 0000b0 000004 00  WA  0   0  4
[ 5] .rodata           PROGBITS        0000000000000000 0000b0 000004 00   A  0   0  8
[10] .symtab           SYMTAB          0000000000000000 000138 0001e0 18     11  15  8
```

`AX` 是可执行、`WA` 是可写可分配，`A` 只读可分配。`.bss` 的类型是 `NOBITS`：它和 `.rodata` 共用文件偏移 `0xb0`，但在文件里一个字节都不占；`static char pool[64 << 20];` 只让内存里的 `.bss` 变大，不会让二进制膨胀 64 MiB。`.rela.text` 的 `0xd8` 字节按每条 24 字节算，正好 9 条待填账，链接后这张表消失——但 PIE 产物仍会留下给 `ld.so` 的表，1.7.4 再分。

### 1.7.2 段：内核的映射单

`readelf -lW hello` 的实测节选：

```text
  INTERP         0x000238 0x0000000000000238 0x0000000000000238 0x00001b 0x00001b R   0x1
      [Requesting program interpreter: /lib/ld-linux-aarch64.so.1]
  LOAD           0x000000 0x0000000000000000 0x0000000000000000 0x0008bc 0x0008bc R E 0x10000
  LOAD           0x00fd90 0x000000000001fd90 0x000000000001fd90 0x000280 0x000288 RW  0x10000
  GNU_RELRO      0x00fd90 0x000000000001fd90 0x000000000001fd90 0x000270 0x000270 R   0x1
  GNU_STACK      0x000000 0x0000000000000000 0x0000000000000000 0x000000 0x000000 RW  0x10
```

一条 `LOAD` 是 `R E`，装 `.interp`、`.dynsym`、`.text`、`.rodata` 这些只读或可执行内容；另一条是 `RW`，装 `.dynamic`、`.got`、`.data`、`.bss`。`readelf -lW` 末尾的 Section to Segment mapping 会直接告诉你每个节归哪条段；`.symtab`、`.strtab` 不在任何 `LOAD` 里，所以不会被映射进进程。

这里只有两条 `LOAD`，不是常见示意图里的三条：链接器把只读段与代码段合进了同一条 `R E` 映射。段数随链接脚本、页大小与权限组合变化，判断依据是 `readelf -l`，不是背数字。

::: def 定义 1.7.2 · 节、段与符号表 {#def-1.7.2}
**节**（section）是链接器处理的最小单位：`.text` 放指令，`.data` 放已初始化数据，`.bss` 放未初始化数据，`.rela.text` 记待填地址。**段**（segment）是内核映射的单位，由程序头描述，一条 `PT_LOAD` 可以覆盖多个节，按页对齐、按权限合并。**符号表**把名字映射到「所在节 + 偏移 + 类型 + 绑定」，`.symtab` 供链接与调试，`.dynsym` 供运行期动态链接。
:::

### 1.7.2 符号表：一行一个名字

`readelf -sW elf.o` 的实测节选：

```text
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     6: 0000000000000000    32 FUNC    LOCAL  DEFAULT    1 local_add
    15: 0000000000000000     4 OBJECT  GLOBAL DEFAULT    3 g_init
    16: 0000000000000000     4 OBJECT  GLOBAL DEFAULT    4 g_zero
    17: 0000000000000000     4 OBJECT  GLOBAL DEFAULT    5 msg
    18: 0000000000000020    76 FUNC    GLOBAL DEFAULT    1 main
    19: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND puts
```

四个字段各有分工。`Type` 说这是函数、对象还是未分类；`Bind` 说链接时谁能让步——`LOCAL` 的 `local_add` 来自 `static`，只在当前目标文件内可见；`Ndx` 说符号落在第几个节，`UND` 表示还没找到定义；`Vis` 说动态链接时是否对外可见，`HIDDEN` 的符号不进 `.dynsym`。`g_zero` 的 `Ndx` 是 4，对应上面第 4 个节 `.bss`。

### 1.7.2 `strip` 删掉的是哪张表

复制一份 `hello` 执行 `strip`，实测从 70,312 字节降到 67,496 字节；`readelf -SW` 里 `.symtab` 消失，`.dynsym` 还在（10 项），`nm hello_stripped` 报 `no symbols`。原因很直接：`.symtab` 是给链接器、调试器和 `nm` 看的编辑视图；`.dynsym` 是 `ld.so` 运行时要查的导出/导入清单。两者内容有重叠，职责不同。

::: ex 例 1.7.1 · 先猜 `strip` 的账 {#ex-1.7.1}
先猜：`strip` 之后文件会小一半吗？`.dynsym` 会不会一起消失？如果程序还要动态链接 `puts`，哪张表绝对不能删？

::: sol 解答
不会小一半：实测只从 70,312 降到 67,496（约 4%），因为装载必需的段一个没少，删掉的是 `.symtab`/`.strtab` 这类不映射的编辑信息。`.dynsym` 必须留下：`puts` 的 `UND` 项与版本节点都记在里面，删了 `ld.so` 就没法解析。判据是 `readelf -SW` 里还剩不剩 `.dynsym`，以及 `readelf -sW` 还能不能列出 `puts@GLIBC_2.17`。
:::
:::

::: errata 关于 ELF 结构的六个误解
1. **「ELF 就是可执行文件」**——`.o` 是 `ET_REL`，可执行是 `ET_EXEC`/`ET_DYN`，共享库也是 `ET_DYN`；三者共用容器，字段不同。
2. **「`.bss` 占文件空间」**——它是 `NOBITS`，文件里只有一个节表项；实测它与 `.rodata` 共用偏移 `0xb0`。
3. **「`PT_LOAD` 一定有三条」**——VM 上这份 `hello` 实测两条（`R E` 与 `RW`）；条数由链接脚本和权限合并决定。
4. **「入口就是 `main`」**——入口是 `_start`，`main` 由 `__libc_start_main` 调用；`readelf -h` 的 `Entry point` 与 `nm main` 是两个地址。
5. **「`strip` 后动态链接会坏」**——删的是 `.symtab`；`.dynsym` 仍在，`puts` 照常解析。
6. **「节地址就是运行时地址」**——`ET_REL` 的节地址全为 0；`ET_DYN` 的地址是相对基址的偏移，装载时才加随机基址。
:::

### 1.7.2 小结

① 先看 `e_type`：`ET_REL` 只有节、没有程序头，`ET_EXEC`/`ET_DYN` 才有段可映射。② 节是链接器的拼接单位，段是内核的映射单位；`.bss` 是 `NOBITS`，`.symtab` 不进入任何 `LOAD`。③ 符号表的 `Type`/`Bind`/`Ndx`/`Vis` 决定链接行为，`strip` 删 `.symtab` 留 `.dynsym`。如果只记住一件事，那就是：**排链接错误看节与符号表，排装载与权限问题看段。**

::: method 即时自测 · 1.7.2
**Q1（记忆）** 节与段各自服务谁？`.o` 为什么没有程序头？

**Q2（辨析）** `.bss` 与 `.rodata` 在文件里的偏移相同，能说明它们内容一样吗？

**Q3（应用）** `readelf -sW` 某行是 `0000000000000000 0 NOTYPE GLOBAL DEFAULT UND puts`。链接器要拿它做什么？做完后这一行会变成什么？

**Q4（迁移）** 一个 64 MiB 的静态数组放在 `.bss`，`ls -l` 几乎不变；换成 `= {1}` 初始化后文件暴涨。用节类型解释这两笔账。

::: sol 答案
**A1** 节服务链接器（拼接、重定位），段服务内核（按页映射、设权限）。`.o` 还没分配运行时地址，没有可映射的段，所以程序头数为 0。
**A2** 不能。偏移相同只是因为 `.bss` 是 `NOBITS`、不占文件字节，链接器让下一个节复用同一偏移；`.bss` 在内存里按需映射到零页，第一次写才分配物理页，`.rodata` 的内容在文件里。
**A3** 链接器要给它找一个唯一强定义，把 `UND` 改成具体节号与偏移；找不到就报 `undefined reference`。链接完成后该行不再是 `UND`，`Value` 变成最终地址（PIE 下是相对偏移）。
**A4** 未初始化数组进 `.bss`（`NOBITS`），文件只记大小；写成 `= {1}` 后整个数组进 `.data`（`PROGBITS`）；实测 16 MiB 数组的两份产物是 70,368 与 16,847,584 字节。
:::
:::

## 1.7.3 符号解析：强、弱与归档顺序 {#sec-1.7.3}

这一节回答：两个文件定义了同一个名字，链接器听谁的？静态库只换了个 `-l` 顺序，为什么就从能链变成不能链？`int counter;` 写两遍，为什么 GCC 9 能过、GCC 13 却报错？

::: preview 先抓住一件事
解析规则只有三句话：强碰强报错，强碰弱取强，弱碰弱取先出现的那个。归档库不是整包塞入，而是按命令行顺序扫一遍，谁解决了当前的未定义符号就抽谁。顺序错了不是「优化问题」，是直接 `undefined reference`。还有一条历史包袱：未初始化全局变量在旧默认下是 `COMMON`，会被静默合并；GCC 10 起默认 `-fno-common`，它变成普通强定义。
:::

### 1.7.3 强、弱与未定义

先做一个可覆盖的默认实现。`weak.c` 里把 `plugin_init` 声明为弱符号，`plugin.c` 提供强定义：

```c
/* weak.c */
#include <stdio.h>
int __attribute__((weak)) plugin_init(void) { return -1; }
int main(void) {
    if (plugin_init() == 0) puts("plugin: ready");
    else puts("plugin: absent");
    return 0;
}
/* plugin.c */
int plugin_init(void) { return 0; }
```

VM 上实测：

```text
$ gcc -O0 weak.c -o weak_alone && ./weak_alone
plugin: absent
$ gcc -O0 weak.c plugin.c -o weak_strong && ./weak_strong
plugin: ready
$ nm weak_alone | grep plugin_init
00000000000007d8 W plugin_init
$ nm weak_strong | grep plugin_init
0000000000000830 T plugin_init
```

`nm` 的 `W` 是弱定义，`T` 是强定义。单独链接时用弱默认值，加入 `plugin.o` 后强定义覆盖它。弱符号也可以只有声明：`extern int maybe(void) __attribute__((weak));` 时，`printf("%p", (void *)maybe)` 实测打印 `(nil)`；所以调用前必须写 `if (maybe)`，否则跳到地址 0。

::: def 定义 1.7.3 · 强符号、弱符号与 COMMON {#def-1.7.3}
函数与已初始化的全局变量是**强符号**；带 `__attribute__((weak))` 的定义是**弱符号**；只有声明、没有定义的引用是**未定义符号**（`UND`）。规则：

1. 两个强定义同名 → `multiple definition`；
2. 一个强定义加任意多个弱定义 → 取强定义；
3. 多个弱定义 → GNU ld 取命令行上先出现的那个（VM 实测 `pick=1`），标准只要求任选一个，别依赖顺序；
4. `COMMON` 符号（旧默认下的未初始化全局变量）会合并，取体积最大的那个。
:::

第 3 条常被记成「选体积最大的」，那只适用于 `COMMON`，不适用于显式弱定义。第 4 条则是历史包袱：两个文件都写 `int counter;`，早年的链接器把它们并成一个 common 符号；如果一边当 `int`、一边当 `double` 用，运行时就读到错的值。GCC 10 起默认 `-fno-common`，未初始化全局变量进 `.bss` 并算强定义，静默合并变成链接错误。

### 1.7.3 归档：按需抽取，只扫一遍

静态库是 `ar` 打包的一串 `.o`。造一个依赖链：`main` 调 `foo`，`foo` 调 `bar`。

```bash
gcc -c amain.c foo.c bar.c
ar rcs libfoo.a foo.o
ar rcs libbar.a bar.o
```

先按错误顺序链接：

```text
$ gcc amain.o -L. -lbar -lfoo -o order_bad
/usr/bin/ld: ./libfoo.a(foo.o): in function `foo':
foo.c:(.text+0x8): undefined reference to `bar'
collect2: error: ld returned 1 exit status
$ gcc amain.o -L. -lfoo -lbar -o order_ok && ./order_ok
foo=8
```

链接器从左到右走一遍：遇到 `.o` 就加入；遇到 `.a`，只用当前还没解决的符号去抽成员，抽完继续看新引入的未定义符号，直到这个库不再贡献新成员。错误顺序里，`libbar.a` 先被扫过，那时还没人引用 `bar`；等 `libfoo.a` 抽出 `foo.o` 带出 `bar` 时，`libbar.a` 已经翻篇了。规则一句话：**被依赖的库放右边。**

互相依赖的两个库，把顺序排反就会留下未定义符号。VM 上实测：`-lcb -lca` 报 `undefined reference to 'cb'`，加上 `-Wl,--start-group` 与 `-Wl,--end-group` 后链接成功。`--start-group` 让组内库反复扫描，代价是更慢；`--whole-archive` 则强制装入所有成员，常用于注册表式插件。

### 1.7.3 COMMON：从静默合并到链接错误

两个文件都写 `int counter;`，第三个文件用 `extern int counter;` 读写它。GCC 13 默认链接的实测报错：

```text
/usr/bin/ld: c2.o:(.bss+0x0): multiple definition of `counter'; c1.o:(.bss+0x0): first defined here
```

给两个文件都加 `-fcommon` 重编，链接通过，运行打印 `3 3`；`readelf -sW c1c.o` 里 `counter` 的 `Ndx` 变成 `COM`、`Size` 为 4。也就是说，旧行为把两个定义并成一个「待定大小」的公共块，最后按最大者分配。它省事，却把类型不一致藏到了运行期；现在默认报错，是把问题提前到链接期。

::: errata 关于符号解析的六个误解
1. **「声明了就能链接」**——声明只告诉编译器签名，定义必须来自某个 `.o` 或库；`undefined reference` 是「找不到定义」，不是「头文件没包含」。
2. **「多个 `int x;` 一定报错」**——`-fcommon` 下会合并成 `COM`；GCC 10 起默认 `-fno-common` 才报错。判断依据是编译选项。
3. **「静态库会整个装进去」**——只抽解决当前未定义符号的成员；没被引用的成员不进产物。
4. **「`-lfoo` 会搜索整个磁盘」**——只在 `-L` 指定目录、默认库目录里找 `libfoo.so`/`libfoo.a`，运行期找 `.so` 是另一套路径。
5. **「弱符号可以直接调用」**——只有声明没有定义时地址为 0；调用前必须 `if (func)` 判空。
6. **「库顺序无所谓」**——归档只扫一遍；被依赖者放右边，循环依赖用 `--start-group`。
:::

::: ex 例 1.7.2 · 先猜报错指向谁 {#ex-1.7.2}
先猜：把 `gcc amain.o -L. -lfoo -lbar` 改成 `-lbar -lfoo`，报错会指向 `foo` 还是 `bar`？错误信息里为什么点名的是 `libfoo.a(foo.o)`，而不是 `main`？

::: sol 解答
报错指向 `bar`：`foo.c:(.text+0x8): undefined reference to 'bar'`。点名 `libfoo.a(foo.o)` 是因为 `foo.o` 是此刻正在被链接的成员——它由 `libfoo.a` 抽出，自身又带进一个新的未定义符号 `bar`；而 `libbar.a` 已经在命令行上被扫过，不会再回头。`main` 的未定义符号 `foo` 已经解决了，所以报错不再提它。
:::
:::

### 1.7.3 小结

① 强碰强报错，强碰弱取强，弱碰弱取先出现的那个；`COMMON` 合并是旧默认，GCC 10 起默认不再发生。② 归档按命令行顺序扫一遍，只抽解决当前未定义符号的成员，所以依赖关系要从左到右排。③ 循环依赖用 `--start-group`，要强制全量装入用 `--whole-archive`。如果只记住一件事，那就是：**链接顺序是被依赖者的顺序，不是字母顺序，也不是「看起来顺眼」的顺序。**

## 1.7.4 重定位：把地址填进指令 {#sec-1.7.4}

这一节回答：`.o` 里 `bl` 后面明明是 `0`，链接后怎么变成能跳到 `puts@plt` 的位移？链接器改的到底是哪几个字节，公式里的 `-4` 又是谁的补偿？

::: preview 先抓住一件事
重定位条目是一张欠条：改哪个偏移、用哪个符号、按哪种类型算、加数是多少。aarch64 的 `CALL26` 在链接后实测从 `94000000` 变成 `97fffff8`，就是 `(0x630 - 0x650) / 4 = -8` 填进 26 位字段。x86-64 的 `PC32`/`PLT32` 用字节位移，加数常是 `-4`；VM 上没有 x86 反汇编器，这一路只实测到重定位表，指令字节与运行结果未实测。
:::

### 1.7.4 先看一张欠条

```c
/* reloc.c */
#include <stdio.h>
int g = 5;
int main(void) { puts("reloc"); return g; }
```

在 VM 上只编译不链接：`gcc -O2 -c reloc.c -o reloc.o`。`readelf -rW reloc.o` 实测有五条：

```text
Offset             Info             Type                        Symbol's Name + Addend
0000000000000004  0000000500000113 R_AARCH64_ADR_PREL_PG_HI21  .rodata.str1.8 + 0
0000000000000008  0000000500000115 R_AARCH64_ADD_ABS_LO12_NC   .rodata.str1.8 + 0
0000000000000010  0000000f0000011b R_AARCH64_CALL26            puts + 0
0000000000000014  0000000300000113 R_AARCH64_ADR_PREL_PG_HI21  .data + 0
000000000000001c  000000030000011d R_AARCH64_LDST32_ABS_LO12_NC .data + 0
```

`Offset` 是字段在节内的偏移，不是虚拟地址；`Type` 同时说明「改哪几位、以什么为单位」；最后一列是符号与加数。`objdump -dr reloc.o` 里，这些位置全是零：

```asm
   4: 90000000  adrp x0, 0        // R_AARCH64_ADR_PREL_PG_HI21 .rodata.str1.8
   8: 91000000  add  x0, x0, #0x0 // R_AARCH64_ADD_ABS_LO12_NC  .rodata.str1.8
  10: 94000000  bl   0 <puts>     // R_AARCH64_CALL26           puts
  14: 90000000  adrp x0, 0        // R_AARCH64_ADR_PREL_PG_HI21 .data
  1c: b9400000  ldr  w0, [x0]     // R_AARCH64_LDST32_ABS_LO12_NC .data
```

### 1.7.4 链接后：三处字段各填了什么

完整链接 `gcc -O2 reloc.c -o reloc` 后，同一段变成（实测）：

```asm
0000000000000640 <main>:
 640: a9bf7bfd  stp  x29, x30, [sp, #-16]!
 644: 90000000  adrp x0, 0 <__abi_tag-0x278>
 648: 911ee000  add  x0, x0, #0x7b8
 650: 97fffff8  bl   630 <puts@plt>
 654: 90000100  adrp x0, 20000 <__data_start>
 65c: b9401000  ldr  w0, [x0, #16]
```

配合 `nm -n reloc`：`main` 在 `0x640`，`g` 在 `0x20010`；字符串在 `.rodata` 的 `0x7b8`。三笔账逐个对：

- `bl` 在 `0x650`，`puts@plt` 在 `0x630`。26 位立即数以 4 字节为单位，`(0x630 - 0x650) / 4 = -8`，编码 `0x94000000 | 0x3fffff8 = 0x97fffff8`。
- `adrp` 在 `0x644`，字符串在 `0x7b8`。两者同在页 `0x0`，页差为 0，所以 `adrp` 的编码还是 `0x90000000`；真正变的是配对的 `add`，低位填 `0x7b8`。
- `adrp` 在 `0x654`，`g` 在 `0x20010`。页差 `0x20000` 即 32 页，编码成 `0x90000100`；`ldr` 的 12 位字段以 4 字节缩放，`0x10 / 4 = 4`，反汇编显示 `#16`。

第二笔最容易被读错：**`adrp` 没变不等于链接器没动它**，只是页差恰好为零。判断动没动，要拿重定位类型去对字段，而不是只看原始字节。

::: def 定义 1.7.4 · 重定位条目 {#def-1.7.4}
一条重定位记录四件事：**偏移**（改哪个字段）、**符号**（用谁的值）、**类型**（改几位、按什么公式、以字节还是指令为单位）、**加数**（显式修正量）。ELF64 的一条 RELA 是 24 字节，`readelf -SW` 的 `ES` 列 `0x18` 就是它。公式里 `S` 是符号地址、`P` 是被改字段地址、`A` 是加数、`L` 是 PLT 桩地址。x86-64、aarch64、RISC-V 用 RELA，加数写在条目里；i386 用 REL，加数藏在被改字段中，链接器要先读旧值再计算。类型的取值范围也是合同的一部分：`CALL26` 只能跳 ±128 MiB，超了就是 `relocation truncated to fit`。
:::

### 1.7.4 x86-64 对照：`-4` 是谁的补偿

在 macOS 上用 `clang --target=x86_64-linux-gnu -O2 -c` 编同一份逻辑的 `.o`，拿到 VM 上用 `readelf -rW` 读（实测）：

```text
0000000000000004  R_X86_64_PC32   .L.str - 4
0000000000000009  R_X86_64_PLT32  puts - 4
000000000000000f  R_X86_64_PC32   g - 4
```

三条加数都是 `-4`。原因不在编译器脾气：`P` 定义为**被改字段的地址**，而 x86 的相对位移是「目标减下一条指令」。字段占 4 字节，下一条指令在 `P + 4`，所以 `S + A - P` 里的 `A` 必须补 `-4`，才能得到 `S - (P + 4)`。

x86-64 常打交道的几种类型（标注「未实测」的行只按 ABI 列算式，VM 上没有对应产物）：

| 类型 | 算式 | 用在哪 | 证据 |
|:--|:--|:--|:--|
| `R_X86_64_64` | `S + A` | 64 位绝对地址、函数指针表 | 未实测 |
| `R_X86_64_PC32` | `S + A - P` | RIP 相对取数据或字符串 | 实测（交叉 `.o`） |
| `R_X86_64_PLT32` | `L + A - P` | `call` 到 PLT 桩 | 实测（交叉 `.o`） |
| `R_X86_64_32` | `S + A`，零扩展 | 非 PIE 的 32 位绝对地址 | 实测（`-fno-pic`） |
| `R_X86_64_32S` | `S + A`，符号扩展 | 需要负数地址的非 PIE 代码 | 未实测 |
| `R_X86_64_GOTPCREL` | `GOT(S) + A - P` | PIC 代码经 GOT 取地址 | 未实测 |

把课本里那组地址代进去（设定值，不是这台机器的 dump）：`S = 0x401030`、`A = -4`、`P = 0x401141`，则 `rel32 = 0x401030 - 4 - 0x401141 = -0x115`，补码 `0xfffffeeb`，指令字节是 `e8 eb fe ff ff`。执行完这条 5 字节 `call` 后 `%rip = 0x401145`，加 `-0x115` 正好回到 `0x401030`。

这一路的指令字节与运行没有实测：VM 上执行 `objdump -d reloc_x86.o` 的实际结果是 `objdump: can't disassemble for architecture UNKNOWN!`。能读的只有 ELF 头、符号与重定位表。

::: ex 例 1.7.3 · 先猜 `bl` 的四个字节 {#ex-1.7.3}
先猜：`.o` 里 `bl` 是 `94000000`，链接后调用 `0x630` 处的 `puts@plt`，指令自身在 `0x650`。四个字节会变成什么？是填 `0x630 - 0x650` 的字节差，还是别的数？

::: sol 解答
不是字节差，而是「指令条数差」：aarch64 的 `BL` 用 26 位立即数，单位是 4 字节。`(0x630 - 0x650) / 4 = -8`，也就是 `0x3fffff8`；与操作码 `0x94000000` 相或，得 `0x97fffff8`，与 `objdump -d` 实测一致。反推：`0x650 + (-8 × 4) = 0x630`。这也解释了为什么它不需要 x86 那样的 `-4`：`P` 就是指令自身地址，位移直接按指令计数，没有「字段起点比下一条指令早 4 字节」的问题。
:::
:::

::: errata 关于重定位的七个误解
1. **「`-4` 是编译器 bug」**——它是「`P` 指字段、CPU 用下一条指令」这一定义带来的修正；x86-64 的 `PC32`/`PLT32` 都带它。
2. **「链接完就没有重定位了」**——`.rela.text` 被链接器销账，但 PIE 产物仍有给 `ld.so` 的表：VM 上 `reloc` 实测 `.rela.dyn` 8 条、`.rela.plt` 5 条。
3. **「`adrp` 编码没变就是没处理」**——页差为零时编码当然不变；要看配对的 `add`/`ldr` 低位有没有变。
4. **「REL 与 RELA 可以混用」**——按架构定：x86-64、aarch64、RISC-V 用 RELA，i386 用 REL；VM 上没有 i386 工具链，未实测。
5. **「`CALL26` 的 26 位是字节偏移」**——它按指令计，实际范围是 ±128 MiB；`ADRP` 的 21 位按页计，范围 ±4 GiB。
6. **「`objdump -d` 什么架构都能反汇编」**——VM 对 x86-64 的 `.o` 实测报 `can't disassemble for architecture UNKNOWN!`；跨架构只能用 `readelf` 读表。
7. **「重定位溢出只会发生在大程序」**——链接脚本把段放远、代码映射到高地址，小程序一样会 `truncated to fit`。
:::

### 1.7.4 小结

① 重定位条目 = 偏移 + 符号 + 类型 + 加数；RELA 把加数写在表里，REL 藏在字段里。② aarch64 的 `CALL26` 按 4 字节计、`ADRP` 按页计、`ADD/LDST` 用 12 位页内偏移；链接后 `bl` 从 `94000000` 变成 `97fffff8`，可手算复核。③ x86-64 的 `PC32`/`PLT32` 用字节位移，`-4` 补的是「字段起点到下一条指令」的差；这条路只实测了重定位表。如果只记住一件事，那就是：**先看类型与加数，再谈填进去的数值——不同架构的「同一个跳转」用的是不同单位。**

**Q1（记忆）** 重定位条目的四要素是什么？RELA 与 REL 的加数各放在哪里？

**Q2（辨析）** 「链接后 `.rela.text` 消失」与「链接后没有任何重定位」，哪句对？举出 VM 上的一个反例。

**Q3（应用）** aarch64 的 `bl` 位于 `0x1000`，目标在 `0x0ff0`。写出它的 26 位立即数、完整 32 位编码，并说明反推落点。

**Q4（迁移）** 链接后 `adrp` 仍是 `90000000`，`add` 却从 `#0x0` 变成 `#0x7b8`。用页差解释这两条，并说明怎样判断 `adrp` 到底有没有被处理。

::: sol 答案
**A1** 偏移、符号、类型、加数。RELA 把加数显式记在条目里（x86-64、aarch64、RISC-V）；REL 的加数存在被改字段中，链接器先读旧值（i386）。
**A2** 前句对。`.rela.text` 在链接时结清，但 PIE 产物留给 `ld.so` 的表还在：VM 实测 `.rela.dyn` 8 条、`.rela.plt` 5 条。
**A3** `(0x0ff0 - 0x1000) / 4 = -4`，立即数 `0x3fffffc`，编码 `0x94000000 | 0x3fffffc = 0x97fffffc`。反推：`0x1000 + (-4 × 4) = 0x0ff0`。
**A4** 两条指令在页 `0x0`，字符串在 `0x7b8` 也在页 `0x0`，页差为 0，所以 `adrp` 的 21 位字段填 0、编码不变；页内偏移由 `add` 承担。判断依据是重定位表里 `adrp` 那条的符号与类型，以及配对指令的低位是否被写入，不能只看 `adrp` 的原始字节。
:::
:::

## 1.7.5 加载：从 execve 到 _start {#sec-1.7.5}

这一节回答：`execve` 把 ELF 文件读进来之后，究竟把哪些字节放到了进程的哪个地址？为什么入口常常不是 `main`，甚至不是你自己写的代码？`_start` 第一次拿到的那张栈上，摆着什么？

::: preview 先抓住一件事
内核在 `execve` 里只做四类事：校验 ELF 头、按程序头把 `PT_LOAD` 映射进地址空间、把 `argc`/`argv`/`envp` 与辅助向量（auxv）摆到新栈、把程序计数器设成入口。有 `PT_INTERP` 时，这个入口属于 `ld.so`，不属于你的 `_start`；`ld.so` 做完重定位才跳 `AT_ENTRY`。VM 实测：`hello` 的 `_start` 在 `0x640`，`/lib/ld-linux-aarch64.so.1` 的入口在 `0x1aa40`；同一次运行的 `AT_BASE` 正好等于 maps 里 `ld.so` 的映射起点。
:::

### 1.7.5 先看 execve 之后没了什么

在 VM（Ubuntu 24.04.5 / aarch64 / GCC 13.3）上编一份只有 `puts` 的 `hello.c`，用 `strace` 只跟 `execve`：

```text
$ strace -e trace=execve ./hello
execve("./hello", ["./hello"], 0xffffcab4a010 /* 17 vars */) = 0
hello, loader
+++ exited with 0 +++
```

输出里没有一条 `mmap`。这不是因为程序没映射内存，而是主程序的映射发生在 `execve` 内部：内核读程序头、建映射、摆栈，做完才把控制权交回用户态。`strace` 记录的是用户态发起的系统调用（程序请求内核代劳的入口），内核自己做的事不会单独成行。判断一个地址空间怎么来的，要看 `/proc/<pid>/maps`。

### 1.7.5 程序头：内核照单抓药

`readelf -lW hello` 的实测节选：

```text
Elf file type is DYN (Position-Independent Executable file)
Entry point 0x640

  Type           Offset   VirtAddr           PhysAddr           FileSiz  MemSiz   Flg Align
  INTERP         0x000238 0x0000000000000238 0x0000000000000238 0x00001b 0x00001b R   0x1
      [Requesting program interpreter: /lib/ld-linux-aarch64.so.1]
  LOAD           0x000000 0x0000000000000000 0x0000000000000000 0x00089c 0x00089c R E 0x10000
  LOAD           0x00fd90 0x000000000001fd90 0x000000000001fd90 0x000280 0x000288 RW  0x10000
  GNU_RELRO      0x00fd90 0x000000000001fd90 0x000000000001fd90 0x000270 0x000270 R   0x1
```

一条 `PT_LOAD` 给内核五样东西：文件里的起点 `Offset`、要去的虚拟地址 `VirtAddr`、文件里有多少字节 `FileSiz`、内存里要占多少 `MemSiz`、页权限 `Flg`。`FileSiz < MemSiz` 的差额就是 `.bss`：文件里没有这些字节，内核在映射尾部补零；第二条 `LOAD` 的 `0x288 - 0x280 = 8` 字节就是这类尾巴。

这里只有两条 `LOAD`：`R E` 一条装代码与只读数据，`RW` 一条装可写数据。x86-64 上常见四条（R、RX、R、RW 分开），条数由链接脚本、页大小与权限组合决定，别把某个数字当定律。判断依据永远是 `readelf -l`。

`INTERP` 那一行给出解释器路径。内核打开它、把它映射进来，再把入口设成解释器的入口。把二进制拷到没有这个路径的系统上，`execve` 会直接失败，报 `No such file or directory`——缺的不是你的程序，是解释器。

### 1.7.5 maps：两条 LOAD 为什么会变成三行

让一个进程睡一会儿，再从外面读它的 maps（VM 实测，地址每次运行都不同）：

```text
$ ./hold & pid=$!
$ grep hold /proc/$pid/maps
aae7b8340000-aae7b8341000 r-xp 00000000 ... /tmp/lab1c07/hold
aae7b835f000-aae7b8360000 r--p 0000f000 ... /tmp/lab1c07/hold
aae7b8360000-aae7b8361000 rw-p 00010000 ... /tmp/lab1c07/hold
```

`hold` 只有两条 `LOAD`，maps 里却有三行：`RW` 那条被 `GNU_RELRO`（relocation read-only，重定位后只读）从中间切开，前一段（`.dynamic`、`.got`）在重定位后被 `mprotect` 改成只读，所以显示成 `r--p`；后一段（`.data`、`.bss`）仍是 `rw-p`。**数 maps 的行数推不出程序头条数**，两者中间隔着权限调整。`ld.so` 自己没有 `PT_INTERP`，它是被内核直接映射的；`[stack]` 一行不来自任何文件，是内核在 `execve` 里新建的。

### 1.7.5 `_start` 手里的栈

入口地址由 ELF 头给出，`readelf -h` 报 `0x640`。反汇编过去，第一条不是 `main`：

```asm
0000000000000640 <_start>:
 640: d503201f  nop
 64c: aa0003e5  mov  x5, x0
 650: f94003e1  ldr  x1, [sp]
 654: 910023e2  add  x2, sp, #0x8
 658: 910003e6  mov  x6, sp
 65c: f00000e0  adrp x0, 1f000
 660: f947f800  ldr  x0, [x0, #4080]
 66c: 97ffffe1  bl   5f0 <__libc_start_main@plt>
```

内核把 `sp` 指到新栈顶，栈上依次是 `argc`、`argv` 指针数组、`NULL`、`envp` 指针数组、`NULL`、auxv 键值对，最后 `AT_NULL`。所以 `ldr x1, [sp]` 取到 `argc`，`add x2, sp, #8` 得到 `argv`，`mov x6, sp` 把栈顶留给 libc。`x0` 里的 `main` 不是立即数，而是从全局偏移表（global offset table, GOT）的槽里取出来的——连入口代码取 `main` 的地址都要经过一次表查找。

`x5` 来自进程入口时的 `x0`，是内核交给 `ld.so`、`ld.so` 再转交的 `rtld_fini`；`x3`/`x4` 是 `init`/`fini`。这些参数按 aarch64 调用约定排进 `x0`–`x6`，然后 `bl __libc_start_main`。`_start` 不返回：`__libc_start_main` 调完 `main` 会走退出链，不回到这里。

### 1.7.5 有解释器时，内核先跳到谁

`readelf -h /lib/ld-linux-aarch64.so.1` 实测入口 `0x1aa40`。内核把 PC 设到这里，同时通过 auxv 告诉 `ld.so` 三件事：主程序的程序头在哪（`AT_PHDR`）、主程序入口在哪（`AT_ENTRY`）、自己被装在哪（`AT_BASE`）。`ld.so` 做完依赖装载与重定位，才跳 `AT_ENTRY`，也就是上面那个 `_start`。

把 `LD_SHOW_AUXV=1` 和 `/proc/self/maps` 放进同一次运行，能直接对上（VM 实测，节选）：

```text
AT_PHDR:              0xbfe691aa0040
AT_BASE:              0xe37f51975000
AT_ENTRY:             0xbfe691aa2cc0
bfe691aa0000-bfe691aa7000 r-xp ... /usr/bin/cat
e37f51975000-e37f5199c000 r-xp ... /usr/lib/aarch64-linux-gnu/ld-linux-aarch64.so.1
```

`AT_PHDR - 0x40`（`cat` 的 `e_phoff` 是 `0x40`）等于 `0xbfe691aa0000`，正是 `cat` 的第一条映射；`AT_ENTRY - 基址 = 0x2cc0`，正是 `readelf -h /usr/bin/cat` 报的入口；`AT_BASE` 则精确等于 `ld.so` 的映射起点。三个数不是三个随机地址，而是同一次地址空间布局随机化（address space layout randomization, ASLR）抽出的三个基址加固定偏移。静态链接的程序没有解释器，同一份 `aux.c` 的静态版实测 `AT_BASE=0 AT_ENTRY=0x400640`，入口固定，内核直接跳 `_start`。

::: def 定义 1.7.5 · 加载、解释器与初始栈 {#def-1.7.5}
**加载**（loading）是内核把 ELF 的程序头翻译成一组页映射，并把入口地址装进 PC 的过程。**解释器**（interpreter）是 `PT_INTERP` 指向的动态链接器；有它时内核先跳它，由它完成依赖装载与重定位后再跳 `AT_ENTRY`。**初始栈**由内核在 `execve` 里新建，按 `argc → argv → NULL → envp → NULL → auxv → AT_NULL` 排列；`AT_PHDR`、`AT_ENTRY`、`AT_BASE` 是其中三项，分别指主程序程序头、主程序入口、解释器基址。
:::

::: ex 例 1.7.5 · 先猜 `AT_BASE` 是谁的基址 {#ex-1.7.5}
先猜：`AT_BASE` 是主程序被加载到的基址，还是 `ld.so` 的基址？如果程序是静态链接的，这一项是多少？

上面那次 `cat` 的实测里，`AT_BASE=0xe37f51975000`，maps 中 `cat` 从 `0xbfe691aa0000` 开始，`ld.so` 从 `0xe37f51975000` 开始。把三个数对一遍，再用 `readelf -h /usr/bin/cat` 的入口 `0x2cc0` 验证 `AT_ENTRY`。

::: sol 解答
`AT_BASE` 是解释器的基址，不是主程序的。证据是它精确等于 maps 里 `ld-linux-aarch64.so.1` 的 `r-xp` 起点；主程序的基址要用 `AT_PHDR - e_phoff` 算，`0xbfe691aa0040 - 0x40 = 0xbfe691aa0000`。`AT_ENTRY - 0xbfe691aa0000 = 0x2cc0`，与 `cat` 的 `e_entry` 一致。静态链接没有解释器，VM 实测 `AT_BASE=0`，`AT_ENTRY` 就是固定的 `0x400640`。判据一句话：**`AT_BASE` 跟着解释器走，主程序的基址跟着 `AT_PHDR` 走。**
:::
:::

::: errata 关于加载的五个误解
1. **「入口就是 `main`」**——入口是 `_start`（实测 `0x640`），`main` 由 `__libc_start_main` 调用；崩溃在 `_start` 之前时，别在业务代码里找。
2. **「`PT_LOAD` 一定是三条」**——本机这份 `hello` 实测两条；x86-64 常见四条。条数由链接脚本与权限合并决定。
3. **「maps 有几行就有几条 `PT_LOAD`」**——`GNU_RELRO` 会把一条 `RW` 段切成 `r--` 与 `rw-` 两行；实测两条 `LOAD` 对应三行。
4. **「内核会解析符号、做重定位」**——内核只校验、映射、摆栈、设入口；符号与重定位是 `ld.so` 的事。
5. **「`.bss` 在文件里有一块零」**——`.bss` 是 `NOBITS`，文件里不占字节；`MemSiz > FileSiz` 的差额由内核补零。
:::

### 1.7.5 小结

① `execve` 的内核侧只做校验、映射、摆栈、设入口四件事，`strace` 看不到主程序的映射，因为那些映射发生在系统调用内部。② 有 `PT_INTERP` 时内核先跳 `ld.so`，`ld.so` 靠 `AT_PHDR`/`AT_ENTRY`/`AT_BASE` 接手，做完重定位才跳 `_start`；`_start` 从 `sp` 上取 `argc`/`argv`，再调 `__libc_start_main`。③ `DYN` 的基址随机、`EXEC` 的地址固定，但两者的栈都随机。如果只记住一件事，那就是：**先分清你看到的是内核装载的映射，还是 `ld.so` 后来加的映射，再谈地址。**

::: method 即时自测 · 1.7.5
**Q1（记忆）** 按顺序说出 `execve` 内核侧的四类动作，以及初始栈上 `argc` 到 `auxv` 的排列。

**Q2（辨析）** 同一个程序 `readelf -l` 报两条 `PT_LOAD`，`/proc/<pid>/maps` 里却有三行它的映射。哪条观察错了？

**Q3（应用）** `readelf -h ./prog` 报 `Type: DYN`、入口 `0x740`，某次运行 `AT_ENTRY=0xaf8539610c58`。求这次运行的基址，并说明 `0xaf8539610c58 - 0x740` 是否等于基址。

::: sol 答案
**A1** 校验 ELF 头；按程序头映射 `PT_LOAD`（含补零）；把 `argc`/`argv`/`envp`/auxv 摆到新栈；把入口装进 PC。栈上顺序是 `argc`、`argv[]`、`NULL`、`envp[]`、`NULL`、auxv 键值对、`AT_NULL`。
**A2** 都没错。两条 `LOAD` 是文件里的事实，三行是运行时权限调整后的结果：`GNU_RELRO` 把 `RW` 段的前半段改成只读，`mprotect` 按页切，于是多出一行。
**A3** 基址 = `AT_ENTRY - 0x740 = 0xaf8539610000`。`0xaf8539610c58` 是入口的运行时地址，减去文件内偏移 `0x740` 才是基址；直接拿 `AT_ENTRY` 当基址会多出 `0x740`。
:::

## 1.7.6 动态链接：ld.so、GOT 与 PLT {#sec-1.7.6}

这一节回答：可执行文件里没有 `libc` 的代码，`puts` 是怎么被接上的？`ld.so` 按什么顺序找库，`RUNPATH` 为什么救不了「依赖的依赖」？

::: preview 先抓住一件事
动态链接把「绑定」拆成两段：链接期 `ld` 只记下 `NEEDED` 里的 soname（共享库的稳定运行名）和符号引用；运行期 `ld.so` 按搜索顺序找到文件、建 link map（依赖链表）、做重定位，把 GOT 槽填成真实地址。VM 实测：`RUNPATH=$ORIGIN` 的程序能找到直接依赖 `libfoo2.so.1`，却找不到它依赖的 `libbar.so.2`，报 `cannot open shared object file`；换回老式 `DT_RPATH` 才传递。
:::

### 1.7.6 先让 `readelf -d` 交代依赖

一个共享库用 `gcc -O0 -fPIC -shared -Wl,-soname,libfoo.so.1 foo.c -o libfoo.so.1` 生成，再建软链 `libfoo.so`；使用者用 `-L. -lfoo -Wl,-rpath,'$ORIGIN'` 链接。`readelf -dW` 的关键行（VM 实测）：

```text
0x0000000000000001 (NEEDED)   Shared library: [libfoo.so.1]
0x0000000000000001 (NEEDED)   Shared library: [libc.so.6]
0x000000000000001d (RUNPATH)  Library runpath: [$ORIGIN]
0x000000000000000e (SONAME)   Library soname: [libfoo.so.1]
```

`NEEDED` 是运行期要找的文件名，不是链接时你写的 `-lfoo`，也不是 `libfoo.so`。链接器在 `libfoo.so` 里读到 `SONAME`，把 `libfoo.so.1` 抄进主程序；运行期 `ld.so` 只认这个字符串。soname 是库的「稳定名字」：真实文件可以是 `libfoo.so.1.2.3`，开发软链是 `libfoo.so`，运行软链是 `libfoo.so.1`。升级小版本只换真实文件，`NEEDED` 不用重链。

`RPATH`/`RUNPATH` 是写进文件的搜索目录，`$ORIGIN` 表示「可执行文件所在目录」。链接时用单引号包住，别让 shell 先把 `$ORIGIN` 展开成空串。

### 1.7.6 五步搜索：一次 `LD_DEBUG=libs` 的现场

`ld.so` 找库的顺序（Linux 6.x）：

1. 有 `DT_RPATH` 且没有 `DT_RUNPATH` 时，搜 `DT_RPATH` 的目录；
2. 搜 `LD_LIBRARY_PATH`（安全执行模式下忽略）；
3. 搜 `DT_RUNPATH` 的目录；
4. 查 `/etc/ld.so.cache`（`ldconfig` 生成）；
5. 搜默认目录 `/lib`、`/usr/lib` 及其多架构变体。

`LD_DEBUG=libs ./use_foo` 把同一次搜索打出来（VM 实测，去掉行首进程号）：

```text
find library=libfoo.so.1 [0]; searching
 search path=/tmp/lab1c07 (RUNPATH from file ./use_foo)
  trying file=/tmp/lab1c07/libfoo.so.1
find library=libc.so.6 [0]; searching
 search path=/tmp/lab1c07 (RUNPATH from file ./use_foo)
  trying file=/tmp/lab1c07/libc.so.6
 search cache=/etc/ld.so.cache
  trying file=/lib/aarch64-linux-gnu/libc.so.6
calling init: /lib/ld-linux-aarch64.so.1
calling init: /lib/aarch64-linux-gnu/libc.so.6
calling init: /tmp/lab1c07/libfoo.so.1
initialize program: ./use_foo
transferring control: ./use_foo
```

三处读点。第一，`RUNPATH` 对每个 `NEEDED` 都会试一遍，所以 `libc.so.6` 也先在 `/tmp/lab1c07` 找了一次，没找到才查缓存。第二，`LD_DEBUG` 输出走标准错误，行首数字是进程号，多进程时靠它分行；用 `LD_DEBUG=libs,bindings` 可以一次看两件事。第三，`calling init` 的顺序是「被依赖者先跑」：`ld.so`、`libc`、`libfoo`，最后才 `transferring control`。

`LD_LIBRARY_PATH` 常被当成万能钥匙，但它有三个局限：位置固定在 `RPATH` 之后、安全执行模式下被整体忽略、对进程树里所有子进程都生效。长期方案是把 `RUNPATH` 写进文件，或把库装进缓存覆盖的目录再跑 `ldconfig`。

### 1.7.6 `RUNPATH` 为什么救不了间接依赖

再造一条链：`use_foo2` 依赖 `libfoo2.so.1`，`libfoo2.so.1` 依赖 `libbar.so.2`，三个文件放在同一目录，`use_foo2` 带 `RUNPATH=$ORIGIN`。VM 实测：

```text
$ ./use_foo2
./use_foo2: error while loading shared libraries: libbar.so.2: cannot open shared object file: No such file or directory
$ LD_LIBRARY_PATH=. ./use_foo2
foo=8
$ ./use_foo2_rpath
foo=8
```

`libbar.so.2` 明明就在 `$ORIGIN`，为什么找不到？因为 `DT_RUNPATH` 只作用于「携带它的那个对象」的直接依赖。`use_foo2` 的 `RUNPATH` 能帮它找 `libfoo2.so.1`，但 `libfoo2.so.1` 自己没有 `RUNPATH`，它找 `libbar.so.2` 时不会回头借主程序的。把链接选项换成 `-Wl,--disable-new-dtags,-rpath,'$ORIGIN'`，产物里变成 `DT_RPATH`，同一条链就能跑（上面第三个 `foo=8`）。

`DT_RPATH` 会沿依赖链传递，`DT_RUNPATH` 不会；新链接器默认生成后者。这也是 `$ORIGIN/../lib` 在多层依赖里时灵时不灵的原因。实测 `LD_DEBUG=libs` 里，`RPATH` 的 `search path` 行排在 `LD_LIBRARY_PATH` 行之前。

### 1.7.6 GOT 与 PLT：桩里的四条指令

`hello` 的 `puts@plt` 在 aarch64 上长这样（VM 实测）：

```asm
0000000000000630 <puts@plt>:
 630: f00000f0  adrp x16, 1f000
 634: f947e611  ldr  x17, [x16, #4040]
 638: 913f2210  add  x16, x16, #0xfc8
 63c: d61f0220  br   x17
```

`adrp` 算出 GOT 所在页 `0x1f000`，`ldr` 从 `0x1f000 + 0xfc8 = 0x1ffc8` 取出一个地址放进 `x17`，`add` 把槽地址 `0x1ffc8` 留在 `x16`，`br x17` 跳过去。`readelf -x .got hello` 里这个槽的初值是 `0x5d0`，也就是 `.plt` 的第一项。

第一次调用先进入 `0x5d0` 的公共桩，它从 GOT 里取解析器地址并跳过去；解析器把 `0x1ffc8` 改写成 `puts` 的真实地址，再跳过去。之后同一调用点仍然走这四条指令，但 `br x17` 直接落在 libc，不再进解析器。这就是延迟绑定。

这台 Ubuntu 24.04 的 `gcc` 默认给产物打 `FLAGS BIND_NOW`（`readelf -dW hello` 可见），解析在装载期就做完，所以看不到「第一次调用才绑定」；要复现得显式 `-Wl,-z,lazy`。绑定时刻的实测顺序、`statistics` 计数与 RELRO 页边界，[1.1.19](ch01.md#sec-1.1.19) 已经量过，这里不重复。

x86-64 的 PLT 桩是另一种形状（常见 `push` 索引再 `jmp plt0`），指令字节与运行结果在本机没有环境，未实测。`dlopen` 则在运行期显式加载库：`RTLD_NOW` 立刻解析、`RTLD_LAZY` 推迟；`RTLD_LOCAL` 默认不把库符号放进全局作用域，`RTLD_GLOBAL` 才放进去；`dlclose` 只减引用计数，不保证卸载。

::: def 定义 1.7.6 · 动态链接器、soname 与 GOT/PLT {#def-1.7.6}
**动态链接器**（`ld.so`）是 `PT_INTERP` 指向的程序，负责按 `NEEDED` 找库、建 link map、做重定位、跑初始化，最后跳 `AT_ENTRY`。**soname** 是库的稳定运行名，链接器把它抄进主程序的 `NEEDED`，运行期按它找文件。**GOT** 是一张地址表，运行期由 `ld.so` 填写；**PLT** 是一小段跳转桩，让调用点先经过表再进库。`RPATH` 沿依赖链传递，`RUNPATH` 只作用于直接依赖。
:::

::: ex 例 1.7.6 · 先猜 `$ORIGIN` 为什么失灵 {#ex-1.7.6}
先猜：`use_foo2` 的 `RUNPATH` 写着 `$ORIGIN`，`libbar.so.2` 也在 `$ORIGIN`，为什么 `ld.so` 说找不到？把 `libbar.so.2` 搬到 `/usr/lib` 或设 `LD_LIBRARY_PATH` 都能解决，哪种是长期方案？

::: sol 解答
`RUNPATH` 只对携带它的对象的直接依赖生效。`use_foo2` 的直接依赖是 `libfoo2.so.1`，`$ORIGIN` 帮它找到了；`libbar.so.2` 是 `libfoo2.so.1` 的直接依赖，而 `libfoo2.so.1` 没有 `RUNPATH`，所以 `use_foo2` 的目录不会被继承。三种修法：给 `libfoo2.so.1` 也写 `RUNPATH`（每个库各自负责自己的依赖）；把 `libbar.so.2` 装进默认目录或 `/etc/ld.so.cache` 覆盖的目录（长期、系统级）；用 `LD_LIBRARY_PATH`（临时，且影响整个进程树）。`DT_RPATH` 能传递，但新链接器默认不生成它。
:::
:::

::: errata 关于动态链接的五个误解
1. **「`-lfoo` 找到什么，运行期就加载什么」**——链接期找 `libfoo.so`，运行期按 `NEEDED` 里的 soname 找 `libfoo.so.1`；两者不是同一个字符串。
2. **「`RUNPATH` 会传给依赖的依赖」**——不会；要传递只能用老式 `DT_RPATH`，或给每个库都写。
3. **「`LD_LIBRARY_PATH` 排第一」**——有 `DT_RPATH` 且无 `DT_RUNPATH` 时，`RPATH` 先搜；实测 `LD_DEBUG` 里 `RPATH` 行在 `LD_LIBRARY_PATH` 行之前。
4. **「`ldd` 只是读文件」**——glibc 的 `ldd` 会真的启动动态链接器；对不可信二进制用 `readelf -d` 或 `objdump -p`。
5. **「PLT 桩的字节是通用的」**——aarch64 是 `adrp/ldr/add/br` 四条，x86-64 是另一种形状；别背字节，按架构读反汇编。
:::

### 1.7.6 小结

① 链接期只留 `NEEDED` 的 soname 与符号引用，运行期 `ld.so` 才找文件、建映射、填 GOT。② 搜索顺序是 `RPATH`（仅当无 `RUNPATH`）→ `LD_LIBRARY_PATH` → `RUNPATH` → 缓存 → 默认目录；`RUNPATH` 只管直接依赖，`RPATH` 才传递。③ PLT 是跳转桩，GOT 是地址表；本机默认 `BIND_NOW`，延迟绑定要显式要求。如果只记住一件事，那就是：**先用 `readelf -d` 看 `NEEDED` 与 `RUNPATH`，再用 `LD_DEBUG=libs` 看它到底搜了哪。**

## 1.7.7 PIC、PIE 与安全加固 {#sec-1.7.7}

这一节回答：为什么同一个「读全局变量」的动作，在共享库、PIE（position-independent executable，位置无关可执行文件）和非 PIE 可执行文件里生成的指令不一样？`-fPIC`、`-fPIE`、`-pie` 各改变哪一步？`readelf` 的哪几行能证明一个二进制开了 NX、canary 与 RELRO？

::: preview 先抓住一件事
位置无关代码（position-independent code, PIC）的约束是：代码段里不出现「链接期就要定死」的绝对地址。编译器用两条路满足它——PC 相对寻址，以及经 GOT 的间接寻址。VM 实测：`-fPIC -shared` 里的 `get_g` 先 `adrp/ldr` 从 GOT 取出 `g` 的地址再解引用；`-no-pie` 的同一动作直接 `adrp` 加页内偏移。PIE 也不等于「所有变量都走 GOT」：可执行文件自己的全局变量不可被抢占，仍然直接寻址。
:::

### 1.7.7 先看两种访问全局变量的方式

共享库 `libg.so` 里 `int g; int get_g(void) { return g; }`，`-O2 -fPIC -shared` 编译后（VM 实测）：

```asm
0000000000000590 <get_g>:
 590: f00000e0  adrp x0, 1f000
 594: f947e400  ldr  x0, [x0, #4040]
 598: b9400000  ldr  w0, [x0]
 59c: d65f03c0  ret
```

`adrp` 算到 GOT 页，`ldr` 从槽里取出「`g` 的地址」，第二条 `ldr` 才读值。`readelf -rW libg.so` 里对应一条 `R_AARCH64_GLOB_DAT ... g + 0`：槽由 `ld.so` 在装载时填。为什么库访问自己的全局变量也要绕表？因为共享库的 `g` 是可抢占的（preemptible），主程序或别的库可能定义同名符号，库不能假设「我说的 `g` 就是我这份」。

非 PIE 可执行文件不走 GOT（VM 实测 `pic_exec` 的 `main`）：

```asm
 4006b0: 90000113  adrp x19, 420000
 4006c0: b9404262  ldr  w2, [x19, #64]
```

地址在链接期就定死，`adrp` 直接给出 `g` 所在页，`ldr` 加页内偏移。PIE 可执行文件的同一处（`pic_pie` 的 `main`）也是直接寻址：

```asm
 7b4: 90000113  adrp x19, 20000
 7c8: b9401262  ldr  w2, [x19, #16]
```

这看起来反直觉：PIE 的基址明明是随机的，怎么敢直接写页内偏移？因为 `-fPIE` 假设「本可执行文件不会被别的模块插入同名符号」，自己的全局变量不可抢占，页内偏移在链接期就固定；变的只是基址，而 `adrp` 本身就是 PC 相对的，跟着基址一起漂。

同一份 `pic.c` 的栈保护变量给出了另一组对照。PIE 版从 GOT 取 `__stack_chk_guard`（`adrp/ldr/ldr`），重定位是 `R_AARCH64_GLOB_DAT`；非 PIE 版直接 `adrp/add` 算出地址，`__stack_chk_guard` 在可执行文件里有一份副本，`ld.so` 用 `R_AARCH64_COPY` 把 libc 的初值复制过来。两种写法都在保护栈，但一个共享地址、一个各自持有副本。

### 1.7.7 三个开关各管什么

| 选项组合 | 产物 | 基址 | 典型用途 |
|:--|:--|:--|:--|
| `-fno-pic -no-pie` | `ET_EXEC` | 固定（本机 `0x400000` 起） | 老式二进制、内核模块 |
| `-fPIE -pie` | `ET_DYN` | 随机 | 现代发行版默认可执行文件 |
| `-fPIC -shared` | `ET_DYN` | 随机 | 共享库 |
| `-fPIC -pie` | `ET_DYN` | 随机 | 少见，但合法 |

`-fPIC`/`-fPIE` 是编译期开关，决定生成什么样的寻址代码；`-pie`/`-no-pie` 是链接期开关，决定产物类型 `ET_DYN` 还是 `ET_EXEC`。两者不能互相替代。只加 `-pie` 而不改编译选项，链接器会直接拒绝（VM 实测，节选）：

```text
/usr/bin/ld: ... relocation R_AARCH64_ADR_PREL_PG_HI21 against symbol `__stack_chk_guard@@GLIBC_2.17' ... can not be used when making a shared object; recompile with -fPIC
/usr/bin/ld: final link failed: bad value
```

报错点名的是 `__stack_chk_guard`，根因却是「用 `-fno-pic` 编出的绝对寻址代码，被要求装进一个可以搬到任意地址的 `ET_DYN`」。修法是重编，不是加链接选项。

### 1.7.7 加固项逐条用 `readelf` 读

Ubuntu 24.04 的 GCC 13 默认就带两项加固（VM 实测）：`echo | gcc -O2 -dM -E - | grep FORTIFY` 报 `#define _FORTIFY_SOURCE 3`；`gcc -Q --help=common -O2` 里 `-fstack-protector-strong` 是 `[enabled]`。再加上默认的 PIE、`BIND_NOW`、`RELRO`，一个不加任何选项的产物已经有多层防护。

逐项看同一个 `pic.c` 的默认产物（VM 实测）：

```text
GNU_STACK      0x000000 ... 0x000000 0x000000 RW  0x10
GNU_RELRO      0x00fd68 ... 0x000298 0x000298 R   0x1
0x000000000000001e (FLAGS)              BIND_NOW
0x000000006ffffffb (FLAGS_1)            Flags: NOW PIE
```

`GNU_STACK` 是 `RW`，没有 `E`，说明栈不可执行（NX）。`GNU_RELRO` 覆盖 `.init_array`、`.fini_array`、`.dynamic`、`.got`：重定位做完后 `ld.so` 用 `mprotect` 把这段改成只读，GOT 劫持的空间被压掉。`BIND_NOW` 让全部符号在装载期解析，配合 `RELRO` 才是 full RELRO；只加 `-z relro` 不加 `-z now`，延迟绑定的那部分 GOT 仍要可写。

栈保护看符号：默认产物里 `readelf -sW` 能查到 `__stack_chk_fail` 与 `__stack_chk_guard`（本机 4 条相关符号）；加 `-fno-stack-protector` 后是 0 条。FORTIFY 看 `__*_chk`：`pic.c` 里的 `strcpy`/`printf` 在 `-O2` 下变成 `__strcpy_chk`/`__printf_chk`，这两个符号出现在动态符号表里。运行时越界，默认产物报 `*** buffer overflow detected ***`（FORTIFY 先拦），加 `-U_FORTIFY_SOURCE` 后报 `*** stack smashing detected ***`（canary 兜底），两者退出码都是 134（VM 实测）。

三个反例也能量出来：`-Wl,-z,norelro` 让 `GNU_RELRO` 整行消失；`-Wl,-z,execstack` 把 `GNU_STACK` 变成 `RWE`；`-fno-stack-protector` 让 `stack_chk` 符号归零。`checksec` 在本机没装，不用它也能查：

| 加固项 | 看哪一行 | 命中长什么样 |
|:--|:--|:--|
| NX | `readelf -l` 的 `GNU_STACK` | 权限只有 `RW`，没有 `E` |
| canary | `readelf -s` | 有 `__stack_chk_fail`/`__stack_chk_guard` |
| RELRO | `readelf -l` 的 `GNU_RELRO` | 段存在，且覆盖 `.got` |
| BIND_NOW | `readelf -d` 的 `FLAGS` | `BIND_NOW` |
| PIE | `readelf -h` 的 `Type` | `DYN`，且 `FLAGS_1` 有 `PIE` |
| FORTIFY | `readelf -s` | 有 `__*_chk` 调用 |

::: def 定义 1.7.7 · PIC、PIE 与几层加固 {#def-1.7.7}
**PIC** 是一套「代码不依赖固定地址」的编译约定：模块内用 PC 相对，跨模块或可抢占的符号经 GOT。**PIE** 是把可执行文件也按 PIC 约定编译、再链接成 `ET_DYN`，让内核给它随机基址。**NX** 靠段权限禁止执行栈和堆；**canary** 在栈帧里放哨兵，返回前比对；**RELRO** 在重定位后把 GOT 等区域改成只读；**FORTIFY** 在编译期把已知大小的库调用换成带检查的 `__*_chk` 版本。它们防的是不同的事，不能互相代替。
:::

::: ex 例 1.7.7 · 先猜 PIE 的全局变量走不走 GOT {#ex-1.7.7}
先猜：PIE 的代码可以在任意基址运行，那么它访问自己定义的全局变量 `g` 时，是不是一定要经过 GOT？共享库里的 `g` 呢？非 PIE 的 `__stack_chk_guard` 为什么会出现 `COPY` 重定位？

::: sol 解答
不是所有访问都走 GOT。PIE 可执行文件里，自己的全局变量不可被抢占，`-fPIE` 直接生成 `adrp` 加页内偏移（实测 `pic_pie` 的 `main` 就是 `adrp x19, 20000; ldr w2, [x19, #16]`），基址随机只影响 `adrp` 的页基址。共享库里的 `g` 可被主程序或别的库覆盖，所以 `-fPIC` 走 GOT（实测 `get_g` 的 `adrp/ldr/ldr` 与 `R_AARCH64_GLOB_DAT`）。非 PIE 的 `__stack_chk_guard` 是 libc 里的数据对象，可执行文件在 `.bss` 留副本，`ld.so` 启动时复制初值，这条重定位就是 `R_AARCH64_COPY`；PIE 不需要副本，用 `GLOB_DAT` 共享 libc 的那一份。
:::
:::

::: errata 关于 PIC 与加固的六个误解
1. **「PIE 就是加了 `-pie`」**——编译期还要 `-fPIE`；只加 `-pie` 会把 `-fno-pic` 的绝对寻址代码链成 `ET_DYN`，链接器直接报错（实测）。
2. **「PIE 里所有变量都走 GOT」**——自己的、不可抢占的全局变量直接寻址；只有可抢占或外部的符号才经 GOT。
3. **「`-fPIC` 没有代价」**——多一次表查找、占一个寄存器，热路径上有成本；共享库必须付，可执行文件可用 `-fPIE` 少付一点。
4. **「NX 是编译器选项」**——NX 是页权限，由 `GNU_STACK` 与内核的映射决定；`-z execstack` 能把它关掉。
5. **「有 canary 就每个函数都查」**——`-fstack-protector-strong` 只保护有数组或取地址的局部变量的函数；`-fno-stack-protector` 下符号直接消失。
6. **「RELRO 是加密 GOT」**——它只是重定位后 `mprotect` 成只读；延迟绑定的槽仍必须可写，所以 full RELRO 要 `-z now` 配合。
:::

### 1.7.7 小结

① PIC 的约束是「代码段里没有链接期定死的绝对地址」，实现手段是 PC 相对与 GOT；`-fPIC`/`-fPIE` 管生成，`-pie` 管产物类型，两者不能互相替代。② PIE 不等于所有变量都走 GOT：自己的不可抢占符号可以直接寻址，共享库的可抢占符号才绕表。③ 加固要逐项读：`GNU_STACK` 看 NX、`__stack_chk_*` 看 canary、`GNU_RELRO` 与 `FLAGS BIND_NOW` 看 GOT 保护、`__*_chk` 看 FORTIFY。如果只记住一件事，那就是：**先问「这个地址在链接期能不能定死」，再决定它该走 PC 相对还是 GOT。**

::: method 即时自测 · 1.7.7
**Q1（记忆）** `-fPIC`、`-fPIE`、`-pie` 各在哪个阶段起作用？分别产出什么类型的文件？

**Q2（辨析）** 「PIE 的代码位置无关，所以它访问任何全局变量都要经 GOT。」这句话哪一半对、哪一半错？用本节的两段反汇编说明。

**Q3（应用）** 一个二进制 `readelf -h` 报 `Type: EXEC`，`readelf -l` 没有 `GNU_RELRO`，`readelf -s` 没有 `__stack_chk_fail`。逐项说出它缺了哪层加固，并给出重新编译的选项。

**Q4（迁移）** 同一个库在 x86-64 与 aarch64 上各编一次，`readelf -r` 的类型名不同，但「经 GOT 取地址」这件事相同。说明判断「是否走了 GOT」应该看指令还是看类型名，为什么。

::: sol 答案
**A1** `-fPIC`/`-fPIE` 在编译期决定寻址代码；`-pie`/`-no-pie` 在链接期决定 `ET_DYN` 还是 `ET_EXEC`。`-fPIC -shared` 产共享库，`-fPIE -pie` 产 PIE 可执行文件。

**A3** `EXEC` 说明不是 PIE；没有 `GNU_RELRO` 说明没开 RELRO；没有 `__stack_chk_fail` 说明没开栈保护。重编用 `-fPIE -pie -Wl,-z,relro,-z,now -fstack-protector-strong`，再按 `readelf` 逐项复核。

## 1.7.8 库打桩：在链接期和运行期换实现 {#sec-1.7.8}

这一节回答：不改库源码，怎样把 `malloc` 或 `puts` 换成自己的版本？`--wrap` 与 `LD_PRELOAD` 各自在哪一刻生效，又会漏掉哪些调用？

::: preview 先抓住一件事
打桩分两个时刻：链接期用 `--wrap` 改写**当前链接**里的未定义引用；加载期用 `LD_PRELOAD` 把库插到符号搜索顺序的最前面。VM 实测：`--wrap=malloc` 在 `-O0` 下打印每次分配，`-O2` 下 `malloc`/`free` 被整体优化掉，钩子一次都没跑；`LD_PRELOAD` 的 `puts` 钩子能接管 `hello`，但静态链接的 `hello` 完全不理它。
:::

| 时机 | 手段 | 影响范围 | 典型场景 |
|:--|:--|:--|:--|
| 编译期 | `#define`、函数指针、依赖注入 | 单个源码 | 单元测试替换依赖 |
| 链接期 | `-Wl,--wrap=符号` | 当前这次链接 | 统计、故障注入 |
| 加载期 | `LD_PRELOAD=./hook.so` | 该进程及其子进程 | 全局观测、兼容层 |

### 1.7.8 链接期：`--wrap` 改的是引用

```c
/* wrapdemo.c：gcc -O0 -Wl,--wrap=malloc wrapdemo.c -o wrapdemo */
#include <stdio.h>
#include <stdlib.h>
void *__real_malloc(size_t n);
void *__wrap_malloc(size_t n)
{
    void *p = __real_malloc(n);
    fprintf(stderr, "[wrap] malloc(%zu) = %p\n", n, p);
    return p;
}
int main(void)
{
    setvbuf(stdout, NULL, _IONBF, 0);
    char *p = malloc(16);
    free(p);
    puts("done");
    return 0;
}
```

VM 实测输出：

```text
$ ./wrapdemo
[wrap] malloc(16) = 0xad721688a2a0
done
```

`--wrap=malloc` 让链接器把当前链接里所有**未定义引用** `malloc` 改写成 `__wrap_malloc`，把 `__real_malloc` 解析成原来的 `malloc`。`nm wrapdemo` 里能看到 `T __wrap_malloc`，却看不到 `__real_malloc`——后者被解析后就是 libc 的 `malloc`。地址随 ASLR 变，不表示每次分配都不同。

把同一份源码改成 `-O2` 再链接，输出只剩 `done`：`malloc(16)` 与 `free(p)` 被编译器配对消除，调用点根本不存在，链接器没有东西可改。这条边界比语法更重要：**`--wrap` 只改链接期还存在的未定义引用**，内联掉的、被优化掉的、共享库内部已经绑定的调用，它都够不着。

### 1.7.8 加载期：`LD_PRELOAD` 与 `RTLD_NEXT`

```c
/* hook_puts.c：gcc -O2 -fPIC -shared -D_GNU_SOURCE hook_puts.c -o libhook.so */
#include <dlfcn.h>
#include <unistd.h>
static int (*real_puts)(const char *);
int puts(const char *s)
{
    if (real_puts == 0)
        real_puts = (int (*)(const char *))dlsym(RTLD_NEXT, "puts");
    (void)!write(STDERR_FILENO, "[hook] ", 7);
    return real_puts(s);
}
```

VM 实测：

```text
$ ./hello2
hello, loader
$ LD_PRELOAD=./libhook.so ./hello2
[hook] hello, loader
```

`LD_PRELOAD` 让 `libhook.so` 先于 `NEEDED` 里的库进入搜索范围，`hello2` 对 `puts` 的未定义引用就绑到了钩子；`nm -D libhook.so` 里 `puts` 是 `T`、`dlsym` 是 `U`。钩子自己不能直接调 `puts`，否则递归；`dlsym(RTLD_NEXT, "puts")` 从「当前对象之后」继续找，拿到 libc 的真实地址。`LD_DEBUG=bindings` 实测两行：一行是主程序绑到 `./libhook.so` 的 `puts`，另一行是钩子再绑到 libc 的 `puts`。

符号搜索顺序还有两条硬边界，都能实测。主程序自己定义了 `puts` 时，`LD_PRELOAD` 抢不走：`./own_puts` 加不加预加载都打印 `own:hello`。静态链接的程序根本不进 `ld.so`，`LD_PRELOAD` 不生效：实测仍打印 `hello, loader`，`readelf -l` 里 `INTERP` 计数为 0，`readelf -d` 报 `There is no dynamic section in this file`。

### 1.7.8 哪些调用会漏掉

- **静态链接**：没有 `PT_INTERP`、没有 `.dynamic`，`LD_PRELOAD` 没有入口可插；`--wrap` 仍可用，因为它在链接期就改掉了引用。
- **内联或消除**：`-O2` 下 `malloc`/`free` 配对、`strlen` 常量折叠、`printf` 改写，调用点可能不存在；先看 `nm`/`objdump` 确认还有没有引用。
- **共享库内部调用**：`--wrap` 只改当前这次链接里的未定义引用；`libfoo.so` 内部对 `puts` 的调用在它自己链接时就绑好了，主程序加 `--wrap` 不影响。
- **主程序自己的定义**：可执行文件的全局符号优先于预加载库，除非把主程序的符号藏起来（`-fvisibility=hidden` 或 `static`）。

写钩子还有两个实现细节。`dlsym` 自身可能调用 `malloc`，所以 `malloc` 钩子里要先设「正在解析」标志，避免递归；析构函数里不要用 `printf`，它可能分配内存，也可能在 `_exit` 收场的进程里根本不执行，报告用 `write` 更稳。

### 1.7.8 钩子没生效，先查哪三样

1. 目标是不是静态链接：`readelf -l ./prog | grep INTERP` 没有输出，`LD_PRELOAD` 就无从下手。
2. 调用点还在不在：`nm ./prog | grep ' U puts'` 有 `U` 才可能在链接或加载时被改写；`objdump -d` 里找不到 `puts@plt`，说明调用被内联或改写了。
3. 到底绑到谁：`LD_DEBUG=bindings ./prog 2>&1 | grep puts`，看 `binding file ... to ...` 的目标是不是你的钩子。

`cannot open shared object file` 属于加载期找库失败，不是打桩失败；先按 1.7.6 的顺序查 `NEEDED` 与搜索路径，再怀疑钩子。

::: def 定义 1.7.8 · 库打桩 {#def-1.7.8}
**库打桩**（interposition）是用自己的实现替换库函数，同时保留一条通往原实现的路。`--wrap=符号` 在链接期把未定义引用改名为 `__wrap_符号`，并把 `__real_符号` 指回原实现；`LD_PRELOAD` 在加载期把指定共享库排到搜索顺序前面，用同名符号覆盖后面的库。前者只影响当前链接，后者影响整个进程；两者都绕不过静态链接、内联与主程序自身的定义。
:::

::: ex 例 1.7.8 · 先猜 `-O2` 下钩子为什么没跑 {#ex-1.7.8}
先猜：同一份 `wrapdemo.c`，`-O0` 能看到 `[wrap] malloc(16)`，`-O2` 一行都没有。是链接器把 `--wrap` 忘了吗？怎样在不降回 `-O0` 的前提下确认调用点还在不在？

::: sol 解答
不是链接器忘了，是调用点没了。`-O2` 看出 `malloc(16)` 的结果只被 `free`，整对操作对外没有可观察效果，于是全部删掉；没有 `malloc` 引用，`--wrap` 自然没有东西可改写。确认办法是看产物而不是猜：`nm wrapdemo_o2 | grep malloc` 没有 `U malloc`，`objdump -d` 里也找不到对 `malloc` 的调用。要让钩子重新有活干，可以给分配结果加一个可观察的副作用（写进 `volatile` 全局、传给 `printf`），或者换一个不会被消除的调用；再不行才退回 `-O0`，但那会连别的优化一起关掉。
:::
:::

::: errata 关于打桩的五个误解
1. **「`--wrap` 是运行期替换」**——它在链接期改引用，必须重新链接；运行期换实现用 `LD_PRELOAD`。
2. **「`LD_PRELOAD` 能换任何函数」**——静态链接、内联、主程序自身定义、`-Bsymbolic` 绑死的库内调用，都能让它失效（静态链接与主程序定义本机实测）；setuid/setgid 程序还整体忽略它（未实测，本机没有 root）。
3. **「`dlsym(RTLD_DEFAULT, ...)` 和 `RTLD_NEXT` 差不多」**——前者从搜索范围开头找，会找到钩子自己；后者从当前对象之后找。
4. **「钩子里可以直接 `printf`」**——`printf` 可能分配内存、可能在 `_exit` 路径上不执行；统计报告用 `write`，并防 `dlsym` 递归。
5. **「glibc 2.34 之后还必须加 `-ldl`」**——`dlopen`/`dlsym` 已并入 libc；本机不加 `-ldl` 也能编过并运行，加了也无害。
:::

### 1.7.8 小结

① `--wrap` 在链接期改写未定义引用，只影响当前链接；`LD_PRELOAD` 在加载期抢占符号，影响整个进程。② 两者都有边界：静态链接、内联/消除、共享库内部调用、主程序自身定义，都会让钩子失灵。③ 写钩子时 `RTLD_NEXT` 找原实现、标志位防递归、`write` 代替 `printf`。如果只记住一件事，那就是：**先确定调用点在不在、绑没绑死，再谈用哪种打桩。**

## 1.7.9 ELF 文件布局：逐字段读一个目标文件 {#sec-1.7.9}

这一节回答：`readelf -h` 打印的那些字段，在文件里各占第几个字节？节头表、符号、重定位项从哪里开始，下一项又在哪里？把结构摊开后，工具输出就不再是魔法。

::: preview 先抓住一件事
ELF64 的头是固定 64 字节，字段偏移由 ABI 写死；节头表是一串 64 字节的项，起点由 `e_shoff` 给出，第 i 项就在 `e_shoff + 64*i`。节名不在节头里，`sh_name` 只是一个指向 `.shstrtab` 的偏移。VM 上这份 `demo.o` 的 `e_shoff` 是 `0x478`，第 1 项 `.text` 的 64 字节可以逐段读出来。
:::

### 1.7.9 先看头 64 字节

写一份有三个全局对象的小文件，只编译不链接：

```c
/* demo.c */
#include <stdio.h>
int g_init = 7;
int g_zero;
static int local_add(int a, int b) { return a + b; }
int main(void) { printf("%d\n", local_add(g_init, g_zero)); return 0; }
```

`gcc -O0 -c demo.c -o demo.o`，VM 上产物 1,976 字节。`readelf -hW` 的关键行：

```text
Class:                             ELF64
Data:                              2's complement, little endian
Type:                              REL (Relocatable file)
Machine:                           AArch64
Start of section headers:          1144 (bytes into file)
Size of this header:               64 (bytes)
Size of section headers:           64 (bytes)
Number of section headers:         13
Section header string table index: 12
```

前 64 字节用 `xxd -l 64 demo.o` 直接看（VM 实测）：

```text
00000000: 7f45 4c46 0201 0100 0000 0000 0000 0000
00000010: 0100 b700 0100 0000 0000 0000 0000 0000
00000020: 0000 0000 0000 0000 7804 0000 0000 0000
00000030: 0000 0000 4000 0000 0000 4000 0d00 0c00
```

逐段对：偏移 0 的 `7f 45 4c 46` 是魔数，`02` 是 64 位，`01` 是小端，`01` 是 ELF 版本；偏移 `0x10` 的 `01 00` 是 `e_type=ET_REL`，`0x12` 的 `b7 00` 是 183（AArch64）；`0x28` 的 `78 04 00 00` 是 `e_shoff=0x478`；`0x3a` 起依次是 `e_shentsize=64`、`e_shnum=13`、`e_shstrndx=12`。`e_phoff` 与 `e_phnum` 都是 0——`.o` 还没有程序头，程序头是链接成可执行文件后才出现的。

### 1.7.9 节头：数组、名字与偏移

`readelf -SW demo.o` 的节选（地址列全为 0）：

```text
[Nr] Name              Type            Address          Off    Size   ES Flg Lk Inf Al
[ 1] .text             PROGBITS        0000000000000000 000040 000068 00  AX  0   0  4
[ 2] .rela.text        RELA            0000000000000000 000338 0000a8 18   I 10   1  8
[10] .symtab           SYMTAB          0000000000000000 000138 0001c8 18     11  15  8
[12] .shstrtab         STRTAB          0000000000000000 000410 000061 00      0   0  1
```

第 1 项的节头从 `0x478 + 1*64 = 0x4b8` 开始。`xxd -s 0x4b8 -l 64 demo.o` 实测：

```text
000004b8: 2000 0000 0100 0000 0600 0000 0000 0000
000004c8: 0000 0000 0000 0000 4000 0000 0000 0000
000004d8: 6800 0000 0000 0000 0000 0000 0000 0000
000004e8: 0400 0000 0000 0000 0000 0000 0000 0000
```

按表读：`sh_name=0x20`，去 `.shstrtab` 的第 `0x20` 个字节看，正好是 `.text`（它恰好是 `.rela.text` 的后半段）；`sh_type=1`（PROGBITS）；`sh_flags=6`（ALLOC 加 EXEC）；`sh_addr=0`；`sh_offset=0x40`；`sh_size=0x68`（104 字节）；`sh_link=0`、`sh_info=0`；`sh_addralign=4`；`sh_entsize=0`（不是表，没有固定项）。这十项与 `readelf -SW` 那一行逐列对得上。

`.symtab` 的第 10 项则给出另一种信息：`sh_type=2`、`sh_offset=0x138`、`sh_size=0x1c8`、`sh_link=11`（指向 `.strtab`）、`sh_info=15`、`sh_entsize=24`。`sh_link` 让符号名有地方可查，`sh_info` 告诉你有多少项属于 LOCAL，`sh_entsize` 让你能用 `0x1c8 / 24 = 19` 算出符号项数。

### 1.7.9 符号与重定位：24 字节一项

符号表起点 `0x138`，第 15 项 `g_init` 在 `0x138 + 15*24 = 0x2a0`。`xxd -s 0x2a0 -l 24 demo.o` 实测：

```text
000002a0: 1800 0000 1100 0300 0000 0000 0000 0000
000002b0: 0400 0000 0000 0000
```

`st_name=0x18`，去 `.strtab`（0x300）第 24 个字节看，是 `g_init`；`st_info=0x11`，高 4 位 1 是 GLOBAL，低 4 位 1 是 OBJECT；`st_shndx=3`，指向第 3 个节 `.data`；`st_value=0`、`st_size=4`。注意 `st_value` 在 `.o` 里是节内偏移，不是运行时地址。

重定位表 `.rela.text` 的起点 `0x338`，第一条 24 字节实测：

```text
00000338: 2800 0000 0000 0000 1301 0000 0f00 0000
00000348: 0000 0000 0000 0000
```

`r_offset=0x28`，正是 `.text` 里那次 `adrp` 的偏移；`r_info` 的低 32 位是 `0x113`（`R_AARCH64_ADR_PREL_PG_HI21`），高 32 位是 15，指向符号表第 15 项 `g_init`；`r_addend=0`。这条记录与 1.7.4 那张 `readelf -rW` 表的第一行是同一笔账，只是这里从字节层看它。

::: def 定义 1.7.9 · ELF64 的四种定长项 {#def-1.7.9}
**ELF 头** 64 字节，`e_shoff`、`e_shnum`、`e_shstrndx` 把你带到节头表与节名表。**节头** 64 字节：`sh_name` 是节名在 `.shstrtab` 的偏移，`sh_offset`/`sh_size` 给内容位置，`sh_link` 指向关联表，`sh_info` 给附加信息，`sh_entsize` 给表项大小。**符号** 24 字节：`st_name` 进 `.strtab`，`st_info` 高 4 位绑定、低 4 位类型，`st_shndx` 是节号。**重定位** 24 字节（RELA）：`r_offset` 是待改位置，`r_info` 高 32 位符号索引、低 32 位类型，`r_addend` 是加数。程序头另算 56 字节一项，只有可执行文件与共享库才有；VM 上 `hello` 实测两条 `PT_LOAD`，x86-64 常见四条，条数不是定律。
:::

::: ex 例 1.7.9 · 先猜第 10 项节头在哪 {#ex-1.7.9}
先猜：`e_shoff=0x478`、`e_shentsize=64`，第 10 项 `.symtab` 的节头从文件哪个偏移开始？它的 `sh_link`、`sh_info`、`sh_entsize` 各应是多少？只用 `xxd`，能不能读出 `sh_offset=0x138`？

::: sol 解答
第 10 项起点是 `0x478 + 10*0x40 = 0x6f8`。实测这 64 字节里 `sh_type=2`、`sh_offset=0x138`、`sh_size=0x1c8`、`sh_link=11`、`sh_info=15`、`sh_entsize=24`。`sh_link=11` 指向第 11 项 `.strtab`；`sh_info=15` 说明前 15 项是 LOCAL，符号表共 `0x1c8/24=19` 项，第 15 项正是第一个 GLOBAL 符号 `g_init`。命令是 `xxd -s 0x6f8 -l 64 demo.o`。
:::
:::

::: errata 关于 ELF 布局的五个误解
1. **「ELF 头是 52 字节」**——那是 ELF32；ELF64 是 64 字节，`e_shoff` 在偏移 40，`e_shnum` 在 60。
2. **「节头表紧跟在 ELF 头后面」**——起点由 `e_shoff` 给出；这份 `demo.o` 的节头在 `0x478`，前面隔着 `.text`、`.symtab` 等内容。
3. **「`sh_name` 就是节名字符串」**——它是 4 字节偏移；符号名更绕一层，要用 `st_name` 加上 `sh_link` 指向的 `.strtab`。
4. **「`.o` 里 `sh_addr` 是运行时地址」**——`ET_REL` 的 `sh_addr` 全是 0；运行时地址要到链接后的 `ET_EXEC`/`ET_DYN` 才有。
5. **「`e_shnum` 永远等于节头个数」**——节数超过 65535 时 `e_shnum=0`，真实数量在 0 号节头的 `sh_size` 里；这份文件只有 13 项，所以能直接读。
:::

### 1.7.9 小结

① ELF64 头固定 64 字节，`e_shoff`/`e_shnum`/`e_shstrndx` 把你带到节头表与节名表。② 节头 64 字节、符号 24 字节、RELA 24 字节；名字都是偏移，`sh_link` 决定去哪个字符串表找。③ `sh_info` 在 `.symtab` 里是第一个 GLOBAL 的下标，在 RELA 里是被重定位的目标节。如果只记住一件事，那就是：**先读头拿 `e_shoff`，再按固定项长跳，任何字段都能手算出来。**

**Q2（辨析）** 同一个 `0x18`，出现在节头的 `sh_name` 与符号的 `st_name` 里，含义一样吗？各自去哪个表找字符串？

**Q3（应用）** 一个 `.o` 的 `e_shoff=0x500`、`e_shnum=9`、`e_shentsize=64`，文件至少多大？第 4 项节头从哪开始？

**Q4（迁移）** `demo.o` 的 `.bss` 是 `Off=0xac`、`Size=4`，下一个 `.rodata` 是 `Off=0xb0`。`.bss` 的 4 个字节在文件里占了吗？为什么文件大小不因此增加 4 字节？

::: sol 答案
**A1** 64、64、24、24 字节。`e_shoff` 在偏移 40，`e_shstrndx` 在偏移 62。
**A2** 不一样。`sh_name` 是节名在 `.shstrtab` 的偏移；`st_name` 是符号名在 `.strtab` 的偏移，后者的表由 `sh_link` 指出。
**A3** 至少 `0x500 + 9*64 = 0x740` 字节；第 4 项在 `0x500 + 4*64 = 0x600`。
**A4** 没占。`.bss` 是 `SHT_NOBITS`，`sh_offset=0xac` 只是一个记账位置，文件里没有对应字节；`.rodata` 从 `0xb0` 开始是对齐的结果。文件大小只算真正有字节的节。
:::
:::

## 1.7.10 符号解析：强、弱、COMMON 与归档顺序 {#sec-1.7.10}

这一节回答：1.7.3 已经给出强、弱、COMMON 的取舍规则，也复现过 `-fcommon` 与默认设置的差别；那些规则背后还有几笔账没结：`int counter;` 在 C 里凭什么能写两遍？`--whole-archive` 与 `--start-group` 都在解决「顺序不对」，为什么不能互换？同一个 `foo`，静态库和共享库为什么会给出两个答案？`memcpy@@GLIBC_2.17` 的版本标签又是谁写进去的？

::: preview 先抓住一件事
COMMON 不是链接器的怪癖，而是 C 的 tentative definition 与旧链接器「公共块」约定的合谋；GCC 10 改默认后，旧库要单独用 `-fcommon` 兼容。`--whole-archive` 改的是「成员要不要全拿」，`--start-group` 改的是「同一组库扫几轮」。静态库成员在链接期被抽出后引用就绑死；共享库的内部调用默认可被主程序抢占，`-Bsymbolic` 才把绑定收回本地。
:::

### 1.7.10 COMMON 的来历：tentative definition

C 标准里，文件作用域的 `int counter;` 没有初始化、也没有 `extern`，叫**暂定定义**（tentative definition）。它可以在同一个编译单元里出现多次，编译器最后把它们并成一个定义。跨编译单元时，C 只允许一个定义；旧 Unix 链接器却把这类符号放进一个公共块，允许多个 `.o` 各写一份，最后取最大体积合并。这样做省事：头文件里写 `int counter;`，每个 `.c` 包含它都不会报错，链接器替你把空间并成一块。

VM 上用 `-fcommon` 编两份都写 `int counter;` 的文件：

```text
$ gcc -O0 -fcommon -c c1.c c2.c
$ nm c1.o | grep counter
0000000000000004 C counter
$ gcc -fcommon c1.o c2.o cmain.o -o common_ok -Wl,--warn-common
/usr/bin/ld: c2.o and c1.o: warning: multiple common of `counter'
$ ./common_ok
counter=3
```

`nm` 的 `C` 就是 common，后面的 `4` 是体积。`readelf -sW c1.o | grep counter` 给出同一件事：`Ndx` 列是 `COM`，`Size` 是 4。`--warn-common` 不改变行为，只在链接时把每个重复的公共块报出来；接手旧库时先加它跑一遍，能看清哪些符号还在靠合并过日子。

默认的 `-fno-common` 会把 `int counter;` 放进 `.bss` 并算强定义，两个文件再链接就是 `multiple definition`；这段报错 1.7.3 已经贴过，这里只看 `nm` 的变化：`C` 变成了 `B`。迁移的正确做法是「一个 `.c` 里写 `int counter;`，头文件里写 `extern int counter;`」；`-fcommon` 只留给暂时改不动的第三方目标文件。不要用 `static` 图省事：那会让每个 `.c` 得到自己的副本，链接错误消失了，计数却各算各的。

读旧产物时，`nm` 的字母比背规则更快：

| 字母 | 含义 | 本节点到的例子 |
|:--|:--|:--|
| `T`/`t` | `.text` 里的函数（大写全局，小写 local） | `main`、`local_add` |
| `B`/`b` | `.bss` 里的强定义 | `-fno-common` 下的 `counter` |
| `C` | COMMON 公共块 | `-fcommon` 下的 `counter` |
| `W`/`w` | 弱定义 | 1.7.3 的 `plugin_init` |
| `U` | 未定义，等别人提供 | `printf` |

### 1.7.10 `--whole-archive` 与 `--start-group`：抽取策略 vs 扫描轮次

1.7.3 只用一句话带过这两个选项，这里把差别量出来。先看一个没有被引用的成员。`libreg.a` 里的 `reg.o` 有一个构造函数和一个 `plugin_name` 字符串，主程序只打印 `main`。VM 实测：

```text
$ ./use_normal
main
$ ./use_whole
reg: init
main
$ ls -l use_normal use_whole
-rwxrwxr-x 1 ... 70312 ... use_normal
-rwxrwxr-x 1 ... 70544 ... use_whole
```

普通 `-lreg` 不抽取任何成员，因为主程序没有未定义符号指向它；`--whole-archive` 把归档里每个成员都当成命令行上的 `.o`，`reg.o` 被无条件加入，构造函数于是运行。代价是体积（这里多 232 字节）和重复定义风险：两个归档都带同名强符号时，全量装入会立刻撞车。`--whole-archive` 要配 `--no-whole-archive` 收尾，否则后面所有库都会被全量装入。

再看循环依赖。`libca3.a` 的 `ca_start.o` 调 `cb`，`libcb2.a` 的 `cb2.o` 又调 `ca_inner`，而 `ca_inner.o` 还在 `libca3.a` 里。VM 实测：

```text
$ gcc g2main.o -L. -lca3 -lcb2 -o g3_bad
/usr/bin/ld: ./libcb2.a(cb2.o): in function `cb':
cb2.c:(.text+0x8): undefined reference to `ca_inner'
$ gcc g2main.o -L. -Wl,--start-group -lca3 -lcb2 -Wl,--end-group -o g3_ok
$ ./g3_ok
8
```

`libca3.a` 先被扫过，抽走 `ca_start.o`；等 `libcb2.a` 抽出 `cb2.o` 带出 `ca_inner` 时，第一轮已经结束。`--start-group` 让组内库反复扫描，直到一整轮没有新成员被抽出；它仍然只抽需要的成员，不改变「按需」这条规则。

| 选项 | 改什么 | 会全拿吗 | 典型场景 |
|:--|:--|:--|:--|
| `--whole-archive` | 抽取策略：每个成员都加入 | 会 | 注册表、插件表、需要固定节布局的固件 |
| `--start-group` | 扫描轮次：组内反复扫描 | 不会 | 两个或多个 `.a` 循环依赖 |

### 1.7.10 静态库与共享库：链接期定死，还是运行期裁决

同名的 `foo` 在两个地方各有一份，链接器给不出统一答案，因为绑定发生的时刻不同。先造一个共享库：

```c
/* plib.c：gcc -O0 -fPIC -shared plib.c -Wl,-soname,libpre.so.1 -o libpre.so.1 */
int foo(void) { return 1; }
int call_foo(void) { return foo(); }
```

主程序自己也定义 `foo`，但只调用库里的 `call_foo`：

```c
/* pmain.c */
#include <stdio.h>
int call_foo(void);
int foo(void) { return 2; }
int main(void) { printf("call_foo=%d\n", call_foo()); return 0; }
```

把 `plib.c` 加 `-Wl,-Bsymbolic` 重建为 `libpre_b.so.1`，再用同一条命令链出 `preempt_b`。VM 实测：默认链接的 `./preempt` 打印 `call_foo=2`，用 `-Wl,-Bsymbolic` 重建的库 `./preempt_b` 打印 `call_foo=1`。默认情况下，共享库里的 `foo` 是**可抢占的**（preemptible）：`ld.so` 在全局符号表里先找到主程序的那份，就把库内对 `foo` 的调用接过去。`-Bsymbolic` 在链接库时就把库内引用绑到自己的 `foo`，不再给运行期抢占留机会；代价是库内对它们的调用不再能被外部实现替换。

静态库走的是另一条路。`libfoo.a` 里的 `foo.o` 被抽出后，链接器当场把 `call_foo` 对 `foo` 的引用解析到具体目标（PIE 下是相对位移）；运行时没有符号查找，主程序再定义 `foo` 也改不了。若 `foo.o` 根本没被引用，它不会进产物，它的构造函数也不会跑。共享库相反：只要 `NEEDED` 里有它，整个文件被映射，所有 `PT_LOAD` 和初始化函数都进场，哪怕你只调一个函数。

| 维度 | 静态库 `.a` | 共享库 `.so` |
|:--|:--|:--|
| 抽取单位 | 按需抽 `.o`，未引用不进 | 整个文件映射 |
| 绑定时刻 | 链接期，绑定定死（PIE 下是相对偏移） | 装载期或首次调用 |
| 主程序能否覆盖库内调用 | 不能 | 默认能，`-Bsymbolic` 可关 |
| 构造函数 | 只有被抽出的成员才跑 | 库被加载就跑 |

`--as-needed` 是共享库侧的「按需」：这次链接没有任何符号用到某个 `.so`，链接器就不把它写进 `NEEDED`；`--no-as-needed` 强制保留。它管的是「依赖要不要留下」，与 `--whole-archive` 的「成员要不要加入」不是一回事。

链接时还有两个常一起问的选项。`-static` 把 libc 也链进来，产物不再依赖 `ld.so`，代价是拿不到库的安全更新。`--gc-sections` 要配合编译期的 `-ffunction-sections -fdata-sections`，把每个函数与变量放进独立节，链接器才能按引用关系删掉没用的节；它不改变符号解析规则，只减小产物。嵌入式与 initramfs 常把这套组合与 `-static` 一起用。

### 1.7.10 符号版本与可见性

glibc 的同一个 `memcpy` 有多个版本。VM 上 `nm -D /lib/aarch64-linux-gnu/libc.so.6 | grep ' memcpy'` 给出 `memcpy@@GLIBC_2.17`；`@@` 表示默认版本，单个 `@` 表示非默认版本。链接这份 `demo_now` 时，`readelf -V` 记下两条需求：

```text
Version needs section '.gnu.version_r' contains 1 entry:
  File: libc.so.6  Cnt: 2
  Name: GLIBC_2.17  Flags: none  Version: 3
  Name: GLIBC_2.34  Flags: none  Version: 2
```

`printf` 要 `GLIBC_2.17`，启动代码要 `GLIBC_2.34`。装载时 `ld.so` 拿这些标签去库里核对；缺了就是 `version 'GLIBC_2.xx' not found`，这跟「找不到文件」是两层问题：前者是符号版本对不上，后者是路径没搜到。要显式取旧版本，可以用 `dlvsym`；要给别人提供多版本，写版本脚本。

可见性决定一个符号是否进入 `.dynsym`。`-fvisibility=hidden` 加 `__attribute__((visibility("default")))` 只导出白名单，减少 PLT/GOT 项，也让 `dlsym(RTLD_NEXT, ...)` 找不到被藏起来的符号——1.7.8 里钩子失效的一种原因就在这里。

::: def 定义 1.7.10 · 公共块、全量归档与符号抢占 {#def-1.7.10}
**COMMON**（公共块）是旧链接器对多个未初始化全局定义的合并方式：取最大体积，`nm` 记 `C`，`readelf` 的 `Ndx` 显示 `COM`。**全量归档**（`--whole-archive`）把归档每个成员都加入链接，不管有没有引用；**分组重扫**（`--start-group`）让组内库反复扫描，直到没有新成员被抽出。**符号抢占**（preemption）是运行期全局符号查找的规则：先出现的定义覆盖后出现者，所以共享库内部对可抢占符号的调用可能落到主程序。
:::

::: ex 例 1.7.10 · 先猜哪个选项会让没引用的构造函数跑 {#ex-1.7.10}
先猜：`libreg.a` 里的 `reg.o` 有一个构造函数，主程序没有引用它的任何符号。普通 `-lreg`、`-Wl,--whole-archive -lreg -Wl,--no-whole-archive`、`-Wl,--start-group -lreg -Wl,--end-group` 三种链接，哪种会让 `reg: init` 打印？二进制会变大吗？

::: sol 解答
只有 `--whole-archive` 会。普通链接没有未定义符号指向 `reg.o`，不抽取；`--start-group` 仍然按需抽取，没有需求就不抽，只是多扫几轮。实测普通产物 70,312 字节，全量产物 70,544 字节，差 232 字节；构造函数只在成员被加入时注册，所以 `reg: init` 只在全量版出现。
:::
:::

::: errata 关于符号解析的六个误解
1. **「COMMON 是 C 标准规定的跨文件行为」**——标准只允许一个定义；暂定定义在同一编译单元内合并，跨文件的公共块是 Unix 链接器的扩展。
2. **「`-fcommon` 是新代码的修法」**——它只用于兼容旧目标文件；新代码应改成一处定义、其余 `extern`，否则类型不一致仍会藏到运行期。
3. **「`--whole-archive` 与 `--start-group` 可以互换」**——前者全拿成员，后者只多重扫、仍按需抽取；一个会让没引用的构造函数跑，另一个不会。
4. **「共享库内部的调用一定落在自己库里」**——默认可被主程序抢占（实测 `call_foo=2`）；`-Bsymbolic` 才把它绑回本地（`call_foo=1`）。
5. **「`nm` 的 `C` 与 `B` 只差一个字母」**——`C` 是 common，`B` 是 `.bss` 里的强定义；前者可合并，后者再撞就是 `multiple definition`。
6. **「`@@` 只是显示格式」**——`@@` 标默认版本，`@` 标非默认版本；链接器会把需求写进 `.gnu.version_r`，装载时逐条核对。
:::

### 1.7.10 小结

① COMMON 是暂定定义与旧公共块约定的历史产物；`nm` 的 `C`、`--warn-common`、`-fcommon` 是排查旧库的三件工具。② `--whole-archive` 全拿成员，`--start-group` 只多重扫、仍按需抽取。③ 静态库在链接期定死，共享库在运行期按全局符号表裁决；`-Bsymbolic` 收回本地绑定，`@@` 标默认版本。如果只记住一件事，那就是：**先问「这个符号在哪一刻绑定」，再决定是调顺序、换选项还是改定义。**

**Q4（迁移）** 接手一个旧库，链接时出现大量重复符号，但源码暂时不能改。先用哪个链接选项把重复的公共块列出来？临时兼容与最终修法各是什么？

::: sol 答案

## 1.7.11 重定位：把地址填进指令 {#sec-1.7.11}

这一节回答：1.7.4 跟着链接器把 `.rela.text` 一笔笔销掉；可执行文件和共享库里为什么还留着 `.rela.dyn` 与 `.rela.plt`？这些账由谁在什么时候填，`-z now` 又改变了什么？

::: preview 先抓住一件事
`.o` 里的重定位是「链接器待办」；`ET_DYN` 产物里的重定位是「`ld.so` 待办」。VM 实测：同一个 `demo.c`，`.o` 只有 `.rela.text` 7 条与 `.rela.eh_frame` 2 条；链接后 `.rela.dyn` 8 条、`.rela.plt` 5 条。`-z now` 不会删掉 `.rela.plt`，只把「何时解析」从首次调用提前到装载。
:::

### 1.7.11 先数三张表

| 文件 | 表 | 条数（VM 实测） | 谁处理 | 何时 |
|:--|:--|--:|:--|:--|
| `demo.o` | `.rela.text` | 7 | `ld` | 静态链接 |
| `demo.o` | `.rela.eh_frame` | 2 | `ld` | 静态链接 |
| `demo_now` | `.rela.dyn` | 8 | `ld.so` | 装载时 |
| `demo_now` | `.rela.plt` | 5 | `ld.so` | 装载时（`BIND_NOW`）或首次调用（lazy） |

`demo_now` 是默认链接产物，`readelf -rW` 的两段（实测，节选）：

```text
Relocation section '.rela.dyn' at offset 0x480 contains 8 entries:
000000000001fd90  0000000000000403 R_AARCH64_RELATIVE                        750
000000000001ffd8  0000000400000401 R_AARCH64_GLOB_DAT     0000000000000000 _ITM_deregisterTMCloneTable + 0
Relocation section '.rela.plt' at offset 0x540 contains 5 entries:
000000000001ffa8  0000000300000402 R_AARCH64_JUMP_SLOT    0000000000000000 __libc_start_main@GLIBC_2.34 + 0
000000000001ffc8  0000000900000402 R_AARCH64_JUMP_SLOT    0000000000000000 printf@GLIBC_2.17 + 0
```

这里 `r_offset` 已经是虚拟地址：`0x1fd90` 是 `.init_array` 的槽，`0x1ffc8` 是 `.got` 里给 `printf@plt` 用的槽。`R_AARCH64_RELATIVE` 没有符号名，它的值是 `B + 0x750`；`nm -n demo_now` 显示 `0x750` 是 `frame_dummy`，装载后这个槽里就是「基址 + 0x750」。`GLOB_DAT` 与 `JUMP_SLOT` 有符号，装载时把符号的真实地址写进槽。

### 1.7.11 类型账本：谁在什么时候填

| aarch64 类型 | x86-64 对应 | 算式 | 用在哪 | 谁填 |
|:--|:--|:--|:--|:--|
| `R_AARCH64_RELATIVE` | `R_X86_64_RELATIVE` | `B + A` | PIE 内部的绝对地址（`.init_array`、函数指针） | `ld.so` 装载 |
| `R_AARCH64_GLOB_DAT` | `R_X86_64_GLOB_DAT` | `S` | GOT 中的符号地址（数据或函数指针） | `ld.so` 装载 |
| `R_AARCH64_JUMP_SLOT` | `R_X86_64_JUMP_SLOT` | `S` | GOT 中的函数入口（PLT 槽） | `ld.so`（now 或 lazy） |
| `R_AARCH64_ABS64` | `R_X86_64_64` | `S + A` | 64 位绝对地址 | `ld`（链接期） |
| `R_AARCH64_PREL32` | `R_X86_64_PC32` | `S + A - P` | `.eh_frame` 里的相对偏移 | `ld`（链接期） |
| `R_AARCH64_CALL26` | `R_X86_64_PLT32` | `S/L + A - P`，按 4 字节 | `bl` 调用 | `ld`（链接期） |
| `R_AARCH64_COPY` | `R_X86_64_COPY` | 复制 `S` 的内容 | 非 PIE 可执行文件的 libc 数据副本 | `ld.so` 装载 |

`S` 是符号地址，`A` 是加数，`P` 是被改字段地址，`L` 是 PLT 桩地址，`B` 是加载基址。aarch64 的 `RELATIVE`、`GLOB_DAT`、`JUMP_SLOT`、`PREL32`、`CALL26` 都在本节或 1.7.4 的 `readelf` 输出里出现过；`ABS64` 与 `COPY` 按 ABI 列出，这份 PIE 产物里没有，未实测。x86-64 那一列按 ABI 名字对照，VM 上没有 x86 反汇编器逐条验证。

### 1.7.11 `-z now` 改的是时刻，不是表

同一个程序再链一次，加 `-Wl,-z,lazy`，比较动态段（VM 实测）：

```text
$ readelf -dW demo_now | grep -E 'FLAGS|BIND_NOW'
0x000000000000001e (FLAGS)              BIND_NOW
0x000000006ffffffb (FLAGS_1)            Flags: NOW PIE
$ readelf -dW demo_lazy | grep -E 'FLAGS|BIND_NOW'
0x000000006ffffffb (FLAGS_1)            Flags: PIE
```

`demo_now` 的 `.rela.plt` 仍然是 5 条，`demo_lazy` 也是 5 条；差别只在 `FLAGS`。`BIND_NOW` 让 `ld.so` 在交出控制权之前把所有 `JUMP_SLOT` 解析完；lazy 则把解析推迟到第一次经过 `printf@plt`。两种情况下表都必须留在文件里，因为装载器需要这份「待填清单」。

`-z now` 常与 `-z relro` 一起用：全部解析完后 `ld.so` 用 `mprotect` 把 GOT 改成只读，延迟绑定就没有机会再写槽了。想观察首次调用，用 `-Wl,-z,lazy` 链接，再加 `LD_DEBUG=bindings`；想看装载期一次解析完，用 `LD_BIND_NOW=1` 跑默认产物。

::: def 定义 1.7.11 · 运行期重定位表 {#def-1.7.11}
**`.rela.dyn`** 是给 `ld.so` 的数据类重定位表，常见类型有 `RELATIVE`、`GLOB_DAT`、`COPY`，目标是 GOT、`.init_array`、`.data.rel.ro` 等位置。**`.rela.plt`** 每个 PLT 项一条 `JUMP_SLOT`，槽里放被调函数的地址。**立即绑定**（`BIND_NOW`）在装载时解析全部 `JUMP_SLOT`；**延迟绑定**（lazy）在首次调用时解析。`r_offset` 在 `ET_REL` 里是节内偏移，在可执行文件或共享库里是虚拟地址。
:::

::: ex 例 1.7.11 · 先猜 `-z now` 后 `.rela.plt` 剩几条 {#ex-1.7.11}
先猜：`demo_now` 默认带 `BIND_NOW`，`.rela.plt` 有 5 条；如果把链接选项换成 `-z lazy`，这 5 条会变成 0 条、1 条，还是不变？`.rela.dyn` 的 8 条会变吗？

::: sol 解答
都不变：`demo_lazy` 实测仍是 `.rela.plt` 5 条、`.rela.dyn` 8 条，变的是 `readelf -dW` 里的 `FLAGS`——`BIND_NOW` 消失。`-z now` 改的是「何时解析」，不是「要不要记录」；表是给 `ld.so` 的待办清单，lazy 只是把其中 `JUMP_SLOT` 的勾选推迟到首次调用。`.rela.dyn` 里的 `RELATIVE` 与 `GLOB_DAT` 无论如何都要在装载时填，所以条数也不变。
:::
:::

::: errata 关于运行期重定位的六个误解
1. **「`-z now` 会删掉 `.rela.plt`」**——实测仍是 5 条；它只把解析时刻提前，表是装载器的工作清单。
2. **「`r_offset` 永远是节内偏移」**——在 `ET_REL` 里是节内偏移，在 `ET_EXEC`/`ET_DYN` 里是虚拟地址。
3. **「`RELATIVE` 的加数就是绝对地址」**——加数是链接期偏移，装载时还要加基址 `B`；`0x750` 单独看不是地址。
4. **「`.rela.dyn` 全是 GOT」**——它还覆盖 `.init_array`、`.fini_array`、`.data.rel.ro` 等位置。
5. **「`JUMP_SLOT` 只在首次调用时才有」**——表在文件里就有，变的是槽里的值：先是 PLT 桩地址，解析后才是真实函数地址。
6. **「`BIND_NOW` 就是 RELRO」**——前者管解析时刻，后者管页权限；只有两者配合，GOT 才会在解析完后变成只读。
:::

### 1.7.11 小结

① `.o` 的表由 `ld` 销账，`ET_DYN` 的表由 `ld.so` 填；`RELATIVE`/`GLOB_DAT` 在装载时处理，`JUMP_SLOT` 可以在首次调用时处理。② `-z now` 只改时刻，表还在；它和 RELRO 配合才能把 GOT 变只读。③ `r_offset` 的含义随文件类型变，读表前先看 `e_type`。如果只记住一件事，那就是：**先问这张表是给链接器还是给装载器的，再谈它填什么。**

## 1.7.12 完整程序：不依赖 libelf 解析 ELF {#sec-1.7.12}

这一节回答：不装 libelf、不包含 `<elf.h>`，怎样在 macOS 或任意机器上读一个交叉编译出来的 `.o`？程序只按 1.7.9 的偏移跳，能不能和 `readelf` 对上四处数字？

::: preview 先抓住一件事
这个程序只做四件事：读 ELF 头、按 `e_shoff` 遍历节头、按 `sh_link` 找字符串表、按 `sh_entsize` 算符号与重定位的条数。VM 上它读 `demo.o` 的输出与 `readelf` 对得上：`e_shoff=0x478`、`shnum=13`、`.symtab` 19 项、`.rela.text` 7 项。边界是只支持小端 ELF64，且没有处理扩展节号与压缩节。
:::

程序如下，编译命令在文件头注释里。它只依赖 `stdio`、`stdint`、`stdlib`、`string`，不链接 libelf，也不包含 `<elf.h>`；目标文件从哪儿交叉编译来都行，只要它是小端 ELF64。

```c
/* elfdump.c — 不依赖 libelf，直接按文件布局解析 ELF64
 * 编译：cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 elfdump.c
 * 运行：./elfdump demo.o
 */
#include <stdio.h>
#include <stdint.h>
#include <string.h>
#include <stdlib.h>

typedef struct __attribute__((packed)) {
    unsigned char e_ident[16];
    uint16_t e_type, e_machine;
    uint32_t e_version;
    uint64_t e_entry, e_phoff, e_shoff;
    uint32_t e_flags;
    uint16_t e_ehsize, e_phentsize, e_phnum, e_shentsize, e_shnum, e_shstrndx;
} Ehdr;

typedef struct __attribute__((packed)) {
    uint32_t sh_name, sh_type;
    uint64_t sh_flags, sh_addr, sh_offset, sh_size;
    uint32_t sh_link, sh_info;
    uint64_t sh_addralign, sh_entsize;
} Shdr;

typedef struct __attribute__((packed)) {
    uint32_t st_name;
    unsigned char st_info, st_other;
    uint16_t st_shndx;
    uint64_t st_value, st_size;
} Sym;

static const char *sh_type_name(uint32_t t)
{
    switch (t) {
    case 1: return "PROGBITS";
    case 2: return "SYMTAB";
    case 3: return "STRTAB";
    case 4: return "RELA";
    case 8: return "NOBITS";
    case 9: return "REL";
    case 11: return "DYNSYM";
    default: return "OTHER";
    }
}

static const char *sym_type_name(unsigned t)
{
    switch (t) {
    case 0: return "NOTYPE";
    case 1: return "OBJECT";
    case 2: return "FUNC";
    case 3: return "SECTION";
    case 4: return "FILE";
    case 5: return "COMMON";
    case 6: return "TLS";
    default: return "?";
    }
}

int main(int argc, char **argv)
{
    if (argc != 2) { fprintf(stderr, "usage: %s <elf64>\n", argv[0]); return 2; }
    FILE *f = fopen(argv[1], "rb");
    if (!f) { perror("fopen"); return 1; }
    if (fseek(f, 0, SEEK_END) != 0) { perror("fseek"); return 1; }
    long size = ftell(f);
    rewind(f);
    unsigned char *buf = malloc((size_t)size);
    if (!buf) { perror("malloc"); return 1; }
    if (fread(buf, 1, (size_t)size, f) != (size_t)size) { perror("fread"); return 1; }
    fclose(f);

    if (size < (long)sizeof(Ehdr) || memcmp(buf, "\177ELF", 4) != 0) {
        fprintf(stderr, "%s: not an ELF file\n", argv[1]);
        return 1;
    }
    const Ehdr *eh = (const Ehdr *)buf;
    printf("ELF%d type=%u machine=%u entry=0x%llx shoff=0x%llx shnum=%u shstrndx=%u\n",
           buf[4] == 2 ? 64 : 32, eh->e_type, eh->e_machine,
           (unsigned long long)eh->e_entry, (unsigned long long)eh->e_shoff,
           eh->e_shnum, eh->e_shstrndx);

    const Shdr *sh = (const Shdr *)(buf + eh->e_shoff);
    const Shdr *shstr = &sh[eh->e_shstrndx];
    const char *strtab = (const char *)(buf + shstr->sh_offset);

    printf("\n[节头] idx name                 type      addr             off      size\n");
    for (int i = 0; i < eh->e_shnum; i++) {
        const char *name = strtab + sh[i].sh_name;
        printf("      %2d %-20s %-9s 0x%012llx 0x%06llx %6llu\n", i, name,
               sh_type_name(sh[i].sh_type), (unsigned long long)sh[i].sh_addr,
               (unsigned long long)sh[i].sh_offset, (unsigned long long)sh[i].sh_size);
    }

    for (int i = 0; i < eh->e_shnum; i++) {
        if (sh[i].sh_type != 2 && sh[i].sh_type != 11) continue;   /* SYMTAB / DYNSYM */
        const Sym *sym = (const Sym *)(buf + sh[i].sh_offset);
        size_t n = sh[i].sh_size / sizeof(Sym);
        const char *names = (const char *)(buf + sh[sh[i].sh_link].sh_offset);
        printf("\n[符号表 %s] %zu 项（前 20 项）\n", strtab + sh[i].sh_name, n);
        for (size_t k = 1; k < n && k <= 20; k++) {
            const char *nm = names + sym[k].st_name;
            if (!*nm) nm = "(null)";
            printf("  %-24s value=0x%08llx size=%5llu bind=%u type=%s shndx=%u\n",
                   nm, (unsigned long long)sym[k].st_value,
                   (unsigned long long)sym[k].st_size, sym[k].st_info >> 4,
                   sym_type_name(sym[k].st_info & 0xf), sym[k].st_shndx);
        }
    }
    free(buf);
    return 0;
}
```

编译并运行（VM 实测，aarch64；节头全列，符号表只留 6 行）：

```text

       6 .comment             PROGBITS  0x000000000000 0x0000b4     46

       8 .eh_frame            PROGBITS  0x000000000000 0x0000e8     80
```

四处对账：

- 文件大小 1,976 字节 = `0x7b8`；`e_shoff + 13*64 = 0x478 + 0x340 = 0x7b8`，节头表正好顶到文件末尾。
- `.symtab` 的 `Size=456`，除以 24 得 19，与 `readelf -sW` 的 `contains 19 entries` 一致。
- `.rela.text` 的 `Size=168`，除以 24 得 7，与 `readelf -rW` 的 7 条一致。
- `main` 的 `value=0x20`、`size=72`，与 `readelf -sW` 的 `0000000000000020 72 FUNC GLOBAL 1 main` 一致；`.o` 里 `value` 是节内偏移。

程序里没有打印 `sh_link`，但它在这一行用到了：

```c
const char *names = (const char *)(buf + sh[sh[i].sh_link].sh_offset);
```

`sh_link` 把 `.symtab` 带到 `.strtab`，符号名才有地方取；`shndx=65521` 是 `SHN_ABS`，说明 `demo.c` 这个 FILE 符号不落在任何节里；`shndx=0` 是 `UND`，`printf` 还没找到定义。`(null)` 来自 `st_name=0`：字符串表第 0 个字节是 NUL，程序用占位符把它显示出来。

边界也要说清：程序只检查长度与魔数，不检查 `class` 与字节序；它假设节头 64 字节、符号 24 字节、RELA 24 字节，不处理 `e_shnum=0` 的扩展节号、`SHT_GROUP`、压缩节与 `.gnu.hash`。代码用 `__attribute__((packed))` 直接解引用，严格对齐的宿主需要改成 `memcpy` 逐字段读。给它一个文本文件，它在魔数检查处退出：

```text
$ ./elfdump elfdump.c
elfdump.c: not an ELF file
```

::: def 定义 1.7.12 · 手工解析 {#def-1.7.12}
**手工解析**（manual parsing）是不调用 libelf、按 ABI 固定偏移把文件读成数组与结构体：先用 `e_shoff` 找节头表，再用 `sh_offset`/`sh_size` 找节内容，用 `sh_link` 找关联的字符串表，用 `sh_entsize` 算表项数。它的价值是能读任意架构的 ELF，代价是边界要自己查：class、字节序、扩展节号、越界与压缩节。
:::

::: ex 例 1.7.12 · 先猜节头表末尾在哪 {#ex-1.7.12}
先猜：`demo.o` 的 `e_shoff=0x478`、`e_shnum=13`、每项 64 字节；节头表最后一项的最后一个字节在文件什么位置？这个位置和 `ls -l demo.o` 的 1,976 字节是什么关系？

::: sol 解答
最后一项从 `0x478 + 12*64 = 0x778` 开始，到 `0x778 + 64 = 0x7b8` 结束；`0x7b8` 正是 1,976。也就是说，链接器把节头表放在文件末尾，表后没有别的字节。这个关系不是巧合，而是 ELF 写入器的布局选择；换一个文件，节头表也可能在中间，判据始终是 `e_shoff`，不是「文件末尾」。
:::
:::

::: errata 关于手工解析的五个误解
1. **「不包含 `<elf.h>` 就不能读 ELF」**——结构是 ABI 公开的，按偏移读即可；`<elf.h>` 只是把常量与结构体写好，省你抄一遍。
2. **「`e_shoff` 一定在文件末尾附近」**——它由写入器决定；这份 `demo.o` 恰好顶到末尾，别的文件可能把节头表放在中间。
3. **「节头数就是 `e_shnum`」**——超过 65535 个节时 `e_shnum=0`，真实数量在 0 号节头的 `sh_size` 里；程序没有处理这个扩展。
4. **「`st_value` 就是地址」**——在 `ET_REL` 里它是节内偏移；到可执行文件里才是虚拟地址。
5. **「字符串表可以直接当 C 字符串用」**——表里是许多以 NUL 结尾的字符串，`st_name`/`sh_name` 是偏移；越界或没有 NUL 都会让程序读飞。
:::

### 1.7.12 小结

① 手工解析的路线是「头 → 节头表 → 节内容 → 字符串表」，四级偏移全部来自文件里的字段。② 程序输出与 `readelf` 可以对账：节头位置、节数、符号项数、重定位条数，各自都能用 `size / entsize` 复算。③ 这套代码只覆盖小端 ELF64 的主干；扩展节号、压缩节与越界检查是真实工具多出来的部分。如果只记住一件事，那就是：**工具不是魔法，它只是把 `e_shoff` 之后的字节按固定长度切开。**

::: method 即时自测 · 1.7.12

**A3** `0x1c8/24=19` 项；`sh_info=15` 表示前 15 项是 LOCAL，第 15 项是第一个 GLOBAL 符号，在 `demo.o` 里就是 `g_init`。
**A4** `machine=62` 是 x86-64；`183` 是 AArch64。程序现在只按小端解释，`buf[5]` 即使是 `02`（大端）也不会拒绝，而是读出错误的值；要支持大端，先加 `buf[5]` 判断，再把所有多字节读取改成大端顺序。

## 1.7.13 完整程序：LD_PRELOAD 与 `--wrap` 打桩 {#sec-1.7.13}

这一节回答：1.7.8 已经把两种打桩的边界讲清了，真正能抄走、能编译、能对着输出判读的最小程序长什么样？

::: preview 先抓住一件事
两个程序共用一个靶子：靶子里 `puts` 打印一行字，`getuid` 打印一个数字。`LD_PRELOAD` 钩子在加载期把这两个符号接到自己的实现上，运行结果里的数字变成 4242、`puts` 的文字被换掉；`--wrap=puts` 在链接期只改当前这次链接里的 `puts` 引用，程序里仍留一条 `__real_puts` 通往 libc。VM（Ubuntu 24.04 / aarch64 / GCC 13.3）实测两条路都通；静态链接的靶子完全不理 `LD_PRELOAD`。
:::

机制与边界在 1.7.8，这里不重讲。下面只给三个完整文件、四条编译命令和输出判读；你按顺序抄，应该得到同样的行，只有 `uid` 的原值随账户而变。以下输出均在 VM 实测，`nm` 里的地址会随编译选项与 GCC 版本变化。

### 1.7.13 公共靶子：一个 `puts` 加一个 `getuid`

```c
/* lab1c07_prog.c — 被观测的靶子
 * 编译：gcc -O2 -Wall -Wextra -Werror lab1c07_prog.c -o lab1c07_prog
 */
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    printf("uid=%ld\n", (long)getuid());
    puts("real main done");
    return 0;
}
```

```text
$ gcc -O2 -Wall -Wextra -Werror lab1c07_prog.c -o lab1c07_prog
$ ./lab1c07_prog
uid=1000
real main done
```

`uid=1000` 是 VM 普通账户的真实值，你的机器可能不是 1000。这个靶子故意不写别的逻辑：两个调用点都在 `main` 里，符号都是动态链接的未定义引用，正好给两种打桩各留一个抓手。

### 1.7.13 加载期：一个钩子换掉两个符号

```c
/* lab1c07_hook.c — LD_PRELOAD 钩子，两个符号各演示一种改法
 * 编译：gcc -O2 -Wall -Wextra -Werror -fPIC -shared \
 *          lab1c07_hook.c -o lab1c07_hook.so
 */
#define _GNU_SOURCE
#include <dlfcn.h>
#include <stdio.h>
#include <unistd.h>

static int (*real_puts)(const char *);
static uid_t (*real_getuid)(void);
static int resolving;

int puts(const char *s)
{
    (void)s;
    if (!real_puts && !resolving) {
        resolving = 1;
        real_puts = (int (*)(const char *))dlsym(RTLD_NEXT, "puts");
        resolving = 0;
    }
    if (!real_puts)
        return -1;
    return real_puts("[hook] puts intercepted");
}

uid_t getuid(void)
{
    if (!real_getuid && !resolving) {
        resolving = 1;
        real_getuid = (uid_t (*)(void))dlsym(RTLD_NEXT, "getuid");
        resolving = 0;
    }
    if (!real_getuid)
        return (uid_t)-1;
    (void)real_getuid;
    return (uid_t)4242;
}
```

```text
$ gcc -O2 -Wall -Wextra -Werror -fPIC -shared lab1c07_hook.c -o lab1c07_hook.so
$ LD_PRELOAD=./lab1c07_hook.so ./lab1c07_prog
uid=4242
[hook] puts intercepted
```

`puts` 简单：拿到真函数后不转交原字符串，直接打印自己的话，所以「替换」一眼可见。`getuid` 演示「改返回值」：先 `dlsym(RTLD_NEXT, "getuid")` 证实原实现存在并取到地址，再忽略它、返回 4242。两个函数共用 `resolving` 标志，因为 `dlsym` 内部可能再次调用 libc 的分配或字符串函数，没有这个开关，钩子会递归。

判读分三处。第一，`nm -D lab1c07_hook.so` 里 `puts`、`getuid` 是 `T`，`dlsym` 是 `U`，说明钩子确实导出了同名符号、又依赖下一层的解析接口。第二，`LD_DEBUG=bindings ./lab1c07_prog 2>&1 | grep -E 'puts|getuid'` 会看到主程序先绑到 `./lab1c07_hook.so`，钩子自己再绑到 `libc.so.6`，这就是 `RTLD_NEXT` 的「下一层」。第三，`LD_PRELOAD` 只对动态链接程序有效；把靶子换成 `gcc -O2 -static`，预加载被无视：

```text
$ gcc -O2 -static lab1c07_prog.c -o lab1c07_prog_static
$ LD_PRELOAD=./lab1c07_hook.so ./lab1c07_prog_static
uid=1000
real main done
$ readelf -lW ./lab1c07_prog_static | grep -c INTERP
0
```

没有 `PT_INTERP`，就没有 `ld.so` 来读 `LD_PRELOAD`；程序里的 `getuid` 在静态链接时已经绑死。这不是钩子写错，而是入口根本不存在。

### 1.7.13 链接期：`--wrap` 只改本次链接的引用

```c
/* lab1c07_wrap.c — 链接期包装，单文件即可
 * 编译：gcc -O2 -Wall -Wextra -Werror lab1c07_wrap.c \
 *          -Wl,--wrap=puts -o lab1c07_wrap
 */
#include <stdio.h>

int __real_puts(const char *s);

int __wrap_puts(const char *s)
{
    if (fputs("[wrap] ", stdout) == EOF)
        return EOF;
    return __real_puts(s);
}

int main(void)
{
    puts("real main done");
    return 0;
}
```

```text
$ gcc -O2 -Wall -Wextra -Werror lab1c07_wrap.c -Wl,--wrap=puts -o lab1c07_wrap
$ ./lab1c07_wrap
[wrap] real main done
$ nm lab1c07_wrap | grep puts
                 U fputs@GLIBC_2.17
                 U puts@GLIBC_2.17
0000000000000820 T __wrap_puts
```

`nm` 里同时出现 `U puts` 和 `T __wrap_puts`，初看像没替换成功。其实两条账各走各的：`main` 里原来的 `puts` 引用被链接器改名为 `__wrap_puts`，所以它成了本文件的强定义；`U puts` 来自 `__real_puts` 的声明，链接器把 `__real_puts` 解析回 libc 的真 `puts`，于是仍留一条未定义引用。`fputs` 是包装函数自己新引入的依赖。判据不是「还有没有 `U puts`」，而是「原来那个调用点是不是进了 `__wrap_puts`」：`objdump -d lab1c07_wrap` 里 `main` 的 `bl` 目标应是 `__wrap_puts`，而不是 `puts@plt`。

这条边界要和 1.7.8 连起来看：`--wrap` 在链接期改的是**当前这次链接的未定义引用**。同一条命令里链接进来的共享库，其内部对 `puts` 的调用在库自己构建时就绑好了，`--wrap` 够不到；只有把调用点放在主程序、且调用没有被 `-O2` 内联或改写成别的函数时，包装才会发生。所以调试打桩失败，先看 `objdump` 的调用点，再看 `nm` 的 `U`/`T`，不要只看输出文字。

::: errata 抄这两个程序时最容易返工的三处
1. **`__real_puts` 忘了声明**——C17 已不允许隐式函数声明，配 `-Werror` 会直接编译失败；声明必须与 `puts` 的原型一致，返回 `int`、参数 `const char *`。
2. **`LD_PRELOAD=lab1c07_hook.so` 不带路径**——动态链接器不搜当前目录；写 `./lab1c07_hook.so` 或绝对路径，否则报 `cannot be preloaded`。
3. **以为 glibc 2.34 之后还非要 `-ldl`**——`dlsym` 已并入 libc，本机不加 `-ldl` 也能编过并运行；老系统才需要补。
:::

### 1.7.13 小结

① 一个靶子、一个钩子、一个包装程序，三者各自独立编译，输出能互相对上：`uid=4242` 证明 `getuid` 被换，`[hook]` 证明 `puts` 被换，`[wrap]` 证明链接期引用被改名。② `LD_PRELOAD` 靠 `ld.so` 在加载期抢先绑定，静态链接没有这个入口；`--wrap` 靠链接器改引用，只管当前链接。③ 判读顺序是「调用点在不在 → 绑到谁 → 有没有被优化掉」，不是背命令。如果只记住一件事，那就是：**先确认程序是动态链接、调用点还在，再谈钩子为什么不生效。**

## 1.7.14 Rust 与链接：同一套 ELF，不同的名字 {#sec-1.7.14}

这一节回答：Rust 产物已经是普通 ELF，为什么 `nm` 里找不到你写的函数名、C 程序也链不上它导出的符号？Rust 在链接前后额外加了哪几层？

::: preview 先抓住一件事
Rust 不改 ELF 容器，改的是「名字」和「运行时」。当前 rustc 默认的 v0 符号修饰把 crate、模块、泛型实例都编进符号名，所以 `nm` 里看到的是一串 `_R...`；要让 C 按名字找到，必须 `#[no_mangle] pub extern "C"`，结构体还要 `#[repr(C)]`。另一个差异在库里：`rlib` 只能由 rustc 接着链，`staticlib` 会把 Rust 标准库和 panic 运行时一起打进 `.a`，`cdylib` 才产出给 C 用的 `.so`。glibc 版本下限由构建 std 的机器决定，不会因为你的源码「写得保守」而降低。
:::

VM 上没有 rustc（`command -v rustc` 无输出），本节命令未在 aarch64 Linux 实测；下面讲的是 rustc 的稳定接口与链接产物差异，不是终端输出。需要自己验证时，在装了 Rust 的 Linux 机器上按文中的命令逐条跑。

### 1.7.14 名字：v0 修饰与 `#[no_mangle]`

Rust 默认给每个函数、静态变量和泛型实例生成一个全局唯一的名字，规则叫 v0 符号修饰（v0 mangling）。`nm` 里看到的是 `_RNv...` 这类编码，里面含 crate 名、模块路径、泛型参数和实例化哈希；同名函数在不同 crate 里不会撞车，代价是 C 链接器不认识它。

```rust
/* lib.rs — 两个导出方式只差一个属性，链接结果完全不同 */
pub fn parse_config() -> u32 { 1 }

#[no_mangle]
pub extern "C" fn rust_add(a: i32, b: i32) -> i32 {
    a + b
}
```

`#[no_mangle]` 关掉符号修饰，`extern "C"` 换掉调用约定；两个都要，缺一不可。只写 `#[no_mangle]` 而保留 Rust ABI，C 侧按 C 约定传参就会读到错误的寄存器/栈位置。反过来，只写 `extern "C"` 不加 `#[no_mangle]`，名字仍是 `_R...`，C 链接器报 `undefined reference to rust_add`。需要自定义名字时用 `#[export_name = "foo"]`，它同样不会替你改 ABI。

`pub` 只控制 Rust 语言内的可见性，不等于导出到动态符号表。`cdylib` 默认只把 `#[no_mangle]`/`#[export_name]` 的符号放进 `.dynsym`；`pub fn` 即使被别的 crate 调用，也不会出现在 C 的 `nm -D` 里。查导出用 `nm -D libfoo.so`，不要用 `nm` 的静态符号表下结论。

### 1.7.14 crate 类型决定链接产物

| crate 类型 | 产物 | 谁能接着链 | 关键差异 |
|:--|:--|:--|:--|
| `rlib`（默认库） | `.rlib` | 常规只给 rustc | 含 Rust 元数据与对象，给 Rust crate 用；`cc` 不认识 |
| `staticlib` | `.a` | `cc`/`ld` | 把 Rust std、依赖与 panic 运行时一起打包，体积大；C 侧要补系统库 |
| `cdylib` | `.so` | `cc`/`ld`、`dlopen` | 只导出 C ABI 符号，std 静态链进库内，适合插件与 FFI |
| `dylib` | `.so` | 只能 rustc | Rust ABI 不稳定，跨编译器版本易崩，不要给 C 用 |

生成命令分别是 `rustc --crate-type rlib lib.rs`、`--crate-type staticlib`、`--crate-type cdylib`。Cargo 项目在 `Cargo.toml` 的 `[lib] crate-type = ["cdylib", "staticlib"]` 里声明；一个 crate 可以同时产出两种，方便测试与发布。

`staticlib` 最容易被低估：它不是「只有你的代码的 `.a`」，而是把 `libstd`、`libcore`、分配器、panic 展开代码和依赖 crate 全部打进去。C 程序链接它时，除了 `-lfoo`，通常还要按链接器报错补 `-lpthread`、`-ldl`、`-lm`；glibc 2.34 之后 `dl`/`pthread` 并入了 libc，老系统仍要补。两个 `staticlib` 同时进一个 C 程序，可能出现重复的 Rust 运行时符号，先查 `nm` 里是否有两份 `rust_eh_personality` 一类符号。

### 1.7.14 边界：布局、panic 与链接参数

Rust 默认的结构体布局（`repr(Rust)`）允许编译器重排字段、压缩填充，所以不能直接交给 C。跨 FFI 的结构体、联合体和带字段的枚举一律加 `#[repr(C)]`；无字段枚举可以用 `#[repr(u32)]` 固定宽度。带数据的 Rust 枚举即使加了 `#[repr(C)]`，也不等于 C 的 `enum`，C 侧应把它当成带标签的 `struct`，或者只传整数标签加独立的联合体。`Option<&T>` 一类类型有可用的 niche 优化，也不要把它当成跨语言契约，FFI 结构体一律用 `#[repr(C)]` 固定。

panic 默认展开。展开一旦穿过 `extern "C"` 边界，Rust 运行时会直接 abort，而不是让 C 的 `longjmp` 接住；要在边界内 `catch_unwind`，或者把库编成 `-C panic=abort`。后者还会去掉展开表、缩小体积，适合 `cdylib`；代价是库内任何 panic 都直接终止进程。需要让 C++ 异常穿过 Rust 栈时，才用 `extern "C-unwind"`，并且两端都要支持。

链接参数有三层入口。`rustc -C linker=clang -C link-arg=-Wl,-z,now` 改单次编译；Cargo 的 `[target.aarch64-unknown-linux-gnu] rustflags = ["-C", "link-arg=-fuse-ld=lld"]` 改一个目标；`build.rs` 里的 `cargo:rustc-link-search=native=...` 与 `cargo:rustc-link-lib=static=foo` 把第三方库交给 rustc。`#[used]` 只阻止编译器删除，不阻止链接器 `--gc-sections` 回收；要把数据真正留在最终文件里，链接脚本里还得有 `KEEP`，或者让一个导出符号引用它。

glibc 下限是最容易在部署时爆的一条。官方预编译的 `std` 是在某台构建机上编的，它会记录自己需要的最高 `GLIBC_2.x`；用 `readelf --version-info ./prog | grep GLIBC_` 能看到实际要求。要跑在更老的发行版上，只有三条路：在更老的构建机上编、换 `musl` 目标做静态链接、或用 `cargo-zigbuild` 一类工具按老 glibc 编；`-C target-cpu` 和 `-C opt-level` 都改不了这个下限。

::: errata 关于 Rust 链接的四个误解
1. **「`#[no_mangle]` 就够给 C 用了」**——它只改名字，不改 ABI；还要 `extern "C"`，结构体还要 `#[repr(C)]`。
2. **「`nm -C` 一定能还原 Rust 符号」**——`-C` 主要是 C++ 解码器，Rust v0 是否支持取决于 binutils 版本；不确定时用 `rustfilt` 或 `llvm-nm --demangle`。
3. **「Rust 程序默认不依赖 libc」**——`x86_64-unknown-linux-gnu` 等目标仍动态链接 libc；只有 `musl` 目标或显式静态链接才不带 `.so` 依赖。
4. **「`#[used]` 保证数据进最终二进制」**——它只管编译器；链接器开了 `--gc-sections` 仍可能删掉无人引用的节，要配 `KEEP` 或导出符号。
:::

### 1.7.14 小结

① Rust 的链接差异首先是名字：默认 v0 修饰，跨语言要 `#[no_mangle] pub extern "C"`，布局要 `#[repr(C)]`。② 库的形态决定交付方式：`rlib` 给 rustc，`staticlib` 把 std 一起打进 `.a`，`cdylib` 才给 C 和 `dlopen`。③ panic、LTO、`#[used]` 与 glibc 下限都在链接前后加了一层，判据始终是 `nm`、`readelf --version-info` 与链接器报错。如果只记住一件事，那就是：**Rust 没有换掉 ELF，它只是在符号名和运行时上多加了几条规则。**

**A1** `#[no_mangle]` 改符号名，`extern "C"` 改调用约定；返回结构体时再加 `#[repr(C)]` 固定布局。
**A2** 产物类型不对。`rlib` 含 Rust 元数据，是给 rustc 继续链接的，不是 `ar` 归档的普通 `.a`；改用 `staticlib` 或 `cdylib`。
**A3** Rust 的 panic 展开穿过了 `extern "C"` 边界，运行时选择 abort。修法是在导出函数内 `catch_unwind` 把 panic 转成错误码，或整库用 `-C panic=abort` 并保证不 panic 到边界外。
:::
:::

## 1.7.15 实验：读一个真实可执行文件的链接信息 {#sec-1.7.15}

这一节回答：手上只有一个编译好的 aarch64 可执行文件，按什么顺序读它的链接信息？哪些数字能互相对上，哪些地址每次运行都会变？

::: preview 先抓住一件事
顺序是「文件类型 → 头 → 段 → 动态依赖 → 重定位与符号 → 反汇编 → 加载器日志」，每一步只回答一个问题。VM 上这个 `hello` 是 PIE：入口 `0x680` 是 `_start` 不是 `main`；两条 `LOAD` 一条只读可执行、一条可读写；`NEEDED` 只有 `libc.so.6`；`puts` 在 `.rela.plt` 里是一条 `JUMP_SLOT`，aarch64 的 PLT 桩是 `adrp/ldr/add/br` 四条指令，不是 x86 的 `jmp *GOT`。
:::

以下输出全部在 VM（Ubuntu 24.04.5 / aarch64 / GCC 13.3 / binutils 2.42 / glibc 2.39）实测。`ldd` 括号里的映射地址随 ASLR 每次变化，文中已省去；其余数字可以直接复现。

```c
/* lab1c07_hello.c — 本节的靶子 */
#include <stdio.h>

int main(void)
{
    puts("hello, linker");
    return 0;
}
```

```text
$ gcc -O2 -g lab1c07_hello.c -o lab1c07_hello
$ file lab1c07_hello
lab1c07_hello: ELF 64-bit LSB pie executable, ARM aarch64, version 1 (SYSV), dynamically linked, interpreter /lib/ld-linux-aarch64.so.1, BuildID[sha1]=0d42036533e187292f24d62a65dc189f7410bf34, for GNU/Linux 3.7.0, with debug_info, not stripped
```

`file` 一行先给三个身份：64 位小端、ARM aarch64、PIE 可执行文件。`interpreter` 指向 `/lib/ld-linux-aarch64.so.1`，说明它是动态链接；`with debug_info` 来自 `-g`，与链接行为无关，但会让 `.symtab` 更大。`BuildID` 与构建路径、时间有关，换一次编译就会变；`for GNU/Linux 3.7.0` 是 ABI 标记，不是要求内核 3.7。

### 1.7.15 第一眼：头与段

```text
$ readelf -hW lab1c07_hello | grep -E 'Type|Machine|Entry|Number of'

  Machine:                           AArch64
  Entry point address:               0x680
  Number of program headers:         9
  Number of section headers:         35
```

`Type: DYN` 是 PIE 的标志：文件里存的是相对偏移，装载时由内核选一个随机基址。`Entry point 0x680` 不是 `main`，而是启动对象里的 `_start`；后面 `nm` 会看到 `main` 在 `0x640`。9 个程序头里只有两条 `LOAD` 真正做映射：

三条读点。第一，`INTERP` 段里就是 `ld.so` 的路径，内核在 `execve` 时读它，映射完解释器再把控制权交过去（1.7.5）。第二，两条 `LOAD` 的权限不同：`R E` 装代码与只读数据，`RW` 装 `.dynamic`、`.got`、`.data`、`.bss`；`MemSiz 0x288` 比 `FileSiz 0x280` 多出的 8 字节就是 `.bss`，文件里不占空间。第三，`GNU_RELRO` 覆盖 `0x1fd90–0x20000`，正好是 `.got` 所在的那一页；它让这段在重定位完成后变成只读，对应 1.7.7 的加固。

### 1.7.15 第二眼：动态依赖、重定位与符号

```text
$ readelf -dW lab1c07_hello | grep -E 'NEEDED|FLAGS'

	/lib/ld-linux-aarch64.so.1
```

```text
0000000000000798 T _fini
00000000000005b8 T _init
0000000000000640 T main
0000000000000680 T _start
$ nm -D lab1c07_hello
```

`_start` 在 `0x680`，与 ELF 头的 `Entry point` 对上；`main` 在 `0x640`，落在 `.text` 的 `[0x640, 0x798)` 内；`_fini` 恰好在 `0x798`，是 `.text` 的结束地址。`nm -D` 只列动态符号表：`puts`、`abort`、`__libc_start_main` 是 `U`（未定义，等 `ld.so` 填），`__cxa_finalize` 等是 `w`（弱引用，找不到也不报错）。

### 1.7.15 第三眼：PLT 与加载器

```text
$ objdump -d --section=.plt lab1c07_hello | sed -n '/<puts@plt>:/,+4p'
0000000000000630 <puts@plt>:
 630:	f00000f0 	adrp	x16, 1f000 <__FRAME_END__+0x1e748>
 634:	f947e611 	ldr	x17, [x16, #4040]
 638:	913f2210 	add	x16, x16, #0xfc8
 63c:	d61f0220 	br	x17
$ objdump -d --section=.text lab1c07_hello | sed -n '/<main>:/,+5p'
0000000000000640 <main>:
 640:	a9bf7bfd 	stp	x29, x30, [sp, #-16]!
 644:	90000000 	adrp	x0, 0 <__abi_tag-0x278>
 648:	911ee000 	add	x0, x0, #0x7b8
 64c:	910003fd 	mov	x29, sp
 650:	97fffff8 	bl	630 <puts@plt>
```

aarch64 的 PLT 桩不是 x86 的 `jmp *GOT`，而是「`adrp` 算出 GOT 页基址 → `ldr` 把槽里的目标地址取到 `x17` → `add` 把槽地址留给解析器 → `br x17` 跳过去」。第一次调用时槽里是解析器入口，绑定后 `ld.so` 把 `puts` 的真实地址写进 `0x1ffc8`，后续同样四条指令直接跳 libc。`main` 里的 `bl 630 <puts@plt>` 就是 1.7.6 说的那个调用点。

```text
$ LD_DEBUG=libs ./lab1c07_hello 2>&1 | sed -E 's/^[[:space:]]*[0-9]+:[[:space:]]?//' | grep -v '^$' | sed -n '1,6p'
find library=libc.so.6 [0]; searching

  trying file=/lib/aarch64-linux-gnu/libc.so.6
calling init: /lib/ld-linux-aarch64.so.1
calling init: /lib/aarch64-linux-gnu/libc.so.6
initialize program: ./lab1c07_hello
$ LD_DEBUG=bindings ./lab1c07_hello 2>&1 | sed -E 's/^[[:space:]]*[0-9]+:[[:space:]]?//' | grep puts

```

加载器先查缓存，找到 `/lib/aarch64-linux-gnu/libc.so.6`，然后初始化 `ld.so` 自己、`libc`，最后把控制权交给程序；`bindings` 那行说明 `puts` 最终绑到了 libc，而不是别的同名库。把这两段日志和 `readelf -d` 的 `NEEDED` 对着看，就能回答「这个程序到底依赖谁、谁先初始化、某个符号绑到了哪里」。

::: def 定义 1.7.15 · 入口、GOT 槽与重定位偏移 {#def-1.7.15}
**入口地址**是内核映射完解释器后跳转的第一条指令，PIE 下是文件内偏移；**GOT 槽**是数据段里存放函数或变量地址的 8 字节单元；**重定位项的 `Offset`** 指的是这个槽的虚拟地址，`Symbol + Addend` 才是要写进去的值。`nm` 打印符号地址，`readelf -r` 打印槽地址，`objdump` 打印指令地址，三者不能混着抄。
:::

::: errata 读真实二进制时的四个错位
1. **「入口点就是 `main`」**——入口是 `_start`（`0x680`），`main` 在 `0x640`，两者相差 `0x40`；`readelf -h` 只给前者。
2. **「`ldd` 的地址可以抄进报告」**——那是本次运行的映射地址，ASLR 每次不同；要写就写「地址随 ASLR 变」。
3. **「`readelf -r` 的 `Offset` 是函数地址」**——它是 GOT 槽地址；绑定前槽里通常是解析器入口或 0，绑定后才变成函数地址。
4. **「`nm` 没输出就是没符号」**——`nm` 默认读 `.symtab`，`strip` 后为空；动态符号要用 `nm -D`，调试符号要用 `readelf -sW`。
:::

### 1.7.15 小结

① 先 `file` 定身份，再 `readelf -h` 看 `Type`/`Machine`/`Entry`，`readelf -l` 看 `INTERP` 与两条 `LOAD`。② `readelf -d` 给依赖与绑定策略，`readelf -r` 给 GOT 槽，`nm` 与 `objdump` 把符号和调用点对上。③ 四个数能互相校验：入口 `0x680` 等于 `_start`，`main 0x640` 在 `.text` 内，`.rela.plt 0x78/24=5`，`puts` 的 `JUMP_SLOT` 槽在 `.got` 范围内。如果只记住一件事，那就是：**读到地址先问它是符号地址、槽地址还是指令地址。**

::: method 即时自测 · 1.7.15
**Q1（记忆）** 依次写出本节用的六条命令，并说出每条只回答哪一个问题。

**Q2（辨析）** `readelf -h` 的 `Entry point 0x680` 与 `nm` 的 `main 0x640`，为什么不是同一个地址？`0x680` 那条指令属于谁？

**Q3（应用）** `readelf -rW` 里 `puts` 的 `JUMP_SLOT` 偏移是 `0x1ffc8`，而 `objdump` 里 `puts@plt` 在 `0x630`。这两个地址各是什么？绑定前后 `0x1ffc8` 的内容怎么变？

**Q4（迁移）** 换一个 `-no-pie` 编译的同类程序，`Type`、`Entry`、`RELATIVE` 数量会怎么变？先预测，再用 `readelf` 验证。

::: sol 答案
**A1** `file` 定文件类型与架构；`readelf -h` 看类型、机器、入口；`readelf -l` 看段与解释器；`readelf -d` 看 `NEEDED` 与绑定策略；`readelf -r` / `nm` 看槽与符号；`objdump` / `LD_DEBUG` 看调用点与绑定结果。
**A2** `0x680` 是 `_start`，来自启动对象，负责从内核手里接栈、调用 `__libc_start_main`；`main` 是 `0x640`，由 `__libc_start_main` 再调用。入口不是 `main`，这是两份不同代码的地址。
**A3** `0x1ffc8` 是 `.got` 里的槽地址，`0x630` 是 `.plt` 里的桩地址。绑定前槽里是解析器入口（`-z now` 下启动时就会改），绑定后写入 libc 中 `puts` 的真实地址；PLT 桩每次只负责从槽里取地址再 `br`。
**A4** `Type` 从 `DYN` 变 `EXEC`，入口变成链接期定死的绝对地址；`RELATIVE` 会大幅减少甚至消失，因为不再需要「基址加偏移」的重定位，但 `JUMP_SLOT` 仍在。
:::
:::

## 1.7.16 十二条链接陷阱 {#sec-1.7.16}

这一节回答：链接与加载出错时，怎样从一句报错迅速判断它属于哪一层，并用一条命令证实，而不是靠猜？

::: preview 先抓住一件事
十二条陷阱可以归成四层：符号解析（1–4）、加载期绑定（5–6）、地址与库路径（7–8）、构建选项与运行时（9–12）。每条都按「现象 → 原因 → 修复 → 怎么验证」写；验证命令优先用 `nm`、`readelf`、`objdump`、`LD_DEBUG`，它们分别回答「符号在不在」「段和依赖长什么样」「调用点是谁」「最后绑到谁」。下面三条最常被误判的另给实测输出：归档只扫一遍、`LD_PRELOAD` 不生效、glibc 版本要求。
:::

| # | 现象 | 原因 | 修复 | 怎么验证 |
|--:|:--|:--|:--|:--|
| 1 | `undefined reference to 'foo'` | `foo` 没有定义被链进来，或提供定义的库排在引用者左边 | 把库放到 `.o` 右边；循环依赖用 `--start-group` | `nm -A *.o *.a` 找 `T foo`；`-Wl,--trace-symbol=foo` 看谁提供 |

| 9 | `--wrap=x` 没替换成功 | 调用被内联/改写，或目标在共享库内部、链接期已绑死 | 关内联、把调用点放到主程序；或改用 `LD_PRELOAD` | `objdump -d ./prog` 看 `bl` 目标；`nm ./prog` 看 `__wrap_x` |
| 10 | Rust 符号在 `nm` 里找不到 | 默认 v0 修饰；LTO/`--gc-sections` 把未引用项删掉 | `#[no_mangle] pub extern "C"`；`#[used]`；查 `-C lto` | `nm -D lib.so`；用 `rustfilt` 解码 `_R...` |
| 11 | 旧系统报 `version 'GLIBC_2.34' not found` | 构建机的 glibc 高于目标机，符号版本节点不存在 | 在旧系统构建；换 `musl` 静态链接；按老 glibc 交叉构建 | `readelf --version-info ./prog`；`objdump -T ./prog` 看最高版本 |
| 12 | 插件/构造函数库没被加载 | `--as-needed` 判定「没有符号被引用」，把库从 `NEEDED` 丢掉 | `-Wl,--no-as-needed`；或显式 `dlopen` | `readelf -d ./prog` 看 `NEEDED` 是否含该库；运行看构造输出 |

### 1.7.16 归档只扫一遍：一条实测链

准备两个归档：`libfoo.a` 里的 `foo()` 调 `bar()`，`libbar.a` 里的 `bar()` 打印一行；主程序只调 `foo()`。把 `-lbar` 写在 `-lfoo` 左边：

```text
$ gcc main.c -L. -lbar -lfoo -o bad
/usr/bin/ld: ./libfoo.a(foo.o): in function `foo':
foo.c:(.text+0x8): undefined reference to `bar'
collect2: error: ld returned 1 exit status
```

原因不是 `libbar.a` 里没有 `bar`，而是链接器扫到 `libbar.a` 时，主程序还没有任何未定义的 `bar`，所以 `bar.o` 根本没被抽出来；等扫 `libfoo.a` 拉进 `foo.o`、带出对 `bar` 的引用时，`libbar.a` 已经过去了。归档默认只扫一遍，不会回头。两种修法都实测过：

```text
$ gcc main.c -L. -lfoo -lbar -o good && ./good
bar
$ gcc main.c -L. -Wl,--start-group -lbar -lfoo -Wl,--end-group -o grouped && ./grouped
bar
```

调换顺序让 `libbar.a` 排在 `libfoo.a` 右边；`--start-group` 让组内的库反复扫描直到没有新符号。`--whole-archive` 则把所有成员无条件拉进来，能解决循环依赖，但产物会变大，也可能引入重复定义，能用顺序或 group 就不要用它。

### 1.7.16 `LD_PRELOAD` 不生效：先看有没有 `ld.so`

同一份钩子，动态链接的靶子能改掉 `uid`，静态链接的靶子完全不动：

```text
$ gcc -O2 -static lab1c07_prog.c -o lab1c07_prog_static
$ LD_PRELOAD=./lab1c07_hook.so ./lab1c07_prog_static
uid=1000
real main done
$ readelf -lW ./lab1c07_prog_static | grep -c INTERP
0
$ readelf -dW ./lab1c07_prog_static
There is no dynamic section in this file.
```

没有 `PT_INTERP` 就没有 `ld.so` 参与，`LD_PRELOAD` 这个环境变量根本没有生效的机会；静态链接时 `getuid` 已经被解析成 libc 里的具体地址。若程序是动态链接却仍不生效，按顺序查三处：`nm ./prog` 里是不是主程序自己定义了同名 `T puts`（可执行文件的定义优先于预加载库）；`objdump -d ./prog` 里调用点是否还在（`-O2` 可能把 `puts` 改写或内联）；`LD_DEBUG=bindings ./prog` 里这个符号最后绑到了谁。三处都排除了，再怀疑钩子本身。

### 1.7.16 glibc 版本要求：符号版本不是装饰

```text
$ objdump -T lab1c07_hello | grep GLIBC
0000000000000000      DF *UND*	0000000000000000 (GLIBC_2.34) __libc_start_main
0000000000000000  w   DF *UND*	0000000000000000 (GLIBC_2.17) __cxa_finalize
0000000000000000      DF *UND*	0000000000000000 (GLIBC_2.17) abort
0000000000000000      DF *UND*	0000000000000000 (GLIBC_2.17) puts
```

`puts` 只要求 `GLIBC_2.17`，但 `__libc_start_main` 要求 `GLIBC_2.34`；启动代码一进来就要调它，所以整个程序的实际下限是 2.34，而不是 2.17。`readelf --version-info` 的 `.gnu.version_r` 会把同样的事实列成 `Name: GLIBC_2.34`，两个工具互相印证。把这份二进制拷到 glibc 2.31 的机器上，加载器会报 `version 'GLIBC_2.34' not found` 并拒绝启动；VM 只有 glibc 2.39，这条报错未实测，但版本节点是文件里的硬要求，不随发行版改名而消失。

修复不是「升级目标机」这一条。更常见的是在旧发行版或旧容器里构建，让符号版本降下来；或者换 `musl` 目标做静态链接，彻底绕开 glibc 版本；或者用 `cargo-zigbuild`、交叉工具链按目标 glibc 编。`-static` 也能绕开，但 glibc 的 NSS/DNS 在静态链接下有已知限制，不能当万能药。

::: errata 三个最容易被当成「链接器坏了」的判断
1. **「库明明有符号，链接器却说找不到」**——先看 `-l` 顺序与归档单遍扫描；`nm -A lib.a` 证明符号在，不代表这次链接会把它抽出来。
2. **「`LD_PRELOAD` 是万能的」**——静态链接、主程序自身定义、内联/改写、`-Bsymbolic` 绑死的库内调用，都会让它失效；先查 `PT_INTERP` 与调用点。
3. **「静态链接最稳」**——它绕开了 glibc 版本，但也拿不到库的安全修复，NSS/DNS 还有已知限制；发布前要按目标环境选，不是默认答案。
:::

### 1.7.16 小结

① 先分层：符号解析看 `nm`，加载绑定看 `readelf -d` 与 `LD_DEBUG`，地址与库路径看 `readelf -r`/`-d`，构建选项看链接命令行。② 归档只扫一遍，顺序与 `--start-group` 不是优化而是语义；`LD_PRELOAD` 只对动态链接程序有效；glibc 下限由符号版本节点决定。③ 每条陷阱都要落到一条可复现的验证命令，输出对不上就说明判断还差一层。如果只记住一件事，那就是：**报错先定位层，再用工具证明，不要先改代码。**

::: method 即时自测 · 1.7.16
**Q1（辨析）** `libbar.a` 里确实有 `bar`，`gcc main.c -L. -lbar -lfoo` 却报 `undefined reference to 'bar'`。用「扫描一遍」解释，并给出两种修法。

**Q2（应用）** 一个动态链接程序设了 `LD_PRELOAD=./hook.so`，`puts` 仍打印原文。写出三条排查命令及各自能排除的原因。

**Q3（迁移）** 你的二进制在 Ubuntu 24.04 上能跑，在 CentOS 7 上报 `GLIBC_2.34 not found`。给出两种交付层面的修法，并说明各自代价。

::: sol 答案
**A1** 扫 `libbar.a` 时主程序只引用 `foo`，没有未定义的 `bar`，所以 `bar.o` 不被抽出；随后扫 `libfoo.a` 拉进 `foo.o` 才产生 `bar` 引用，但 `libbar.a` 已扫过且不回头。修法：把 `-lbar` 放到 `-lfoo` 右边，或用 `-Wl,--start-group -lbar -lfoo -Wl,--end-group`。
**A2** `readelf -l ./prog` 看有没有 `INTERP`（排除静态链接）；`nm ./prog` 看主程序是否自己定义了 `T puts`（排除主程序抢占）；`objdump -d ./prog` 看调用点是否还在（排除内联/改写）；最后 `LD_DEBUG=bindings ./prog` 看实际绑定目标。
**A3** 一是在 CentOS 7 或同代 glibc 的构建环境里重编，代价是工具链旧、CI 多一套；二是改用 `musl` 目标静态链接，代价是没有 glibc 的 NSS/DNS 行为、体积变大，且依赖 musl 的兼容性。升级目标机不是交付方单方面能做的修复。
:::
:::

## 1.7.17 本章小结 {#sec-1.7.17}

这一节回答：这一章学完，给你一个二进制，你能不能从「它是怎么被拼出来的」讲到「它跑起来时谁先动手」？报错时，能不能先定位到层，而不是先改代码？

::: preview 先抓住一件事
判据是：**看到 `undefined reference`、`cannot open shared object file`、`symbol version not found` 三种报错，你能立刻说出它发生在链接期、加载期还是符号标签层，并报出对应的第一条命令。**
:::

这一章的主线是**从 .o 到进程**。1.7.1–1.7.4 讲链接器与它的原料：链接在流水线里的位置、ELF 的节与段与符号表、符号解析（强、弱、COMMON 与归档只扫一遍）、重定位（`S + A - P` 与各类型的算式）。1.7.5–1.7.8 讲跑起来这一段：`execve` 到 `_start` 的分工、`ld.so` 用 `DT_NEEDED` 找库并按五步搜索、GOT/PLT 的首次绑定与之后的一次跳转、PIE 与加固（`BIND_NOW`、`GNU_RELRO`）、以及链接期与运行期两种打桩。

1.7.9–1.7.16 是第二遍：逐字段读一个 `.o`（Ehdr/Shdr/Sym/Rela）、把 COMMON、`--whole-archive`、`--start-group` 与符号版本补成完整的故事、看运行期的 `.rela.dyn` 与 `.rela.plt`（`-z now` 不删表）、写一个不依赖 libelf 的 ELF 解析器与 `readelf` 对账。最后四个节都是手上活：`LD_PRELOAD` 与 `--wrap` 的完整程序（`uid=4242`、`[hook]`、`[wrap]` 三行输出互相对上）、Rust 的 v0 名字与 `cdylib`/`staticlib` 的交付形态、读一个真实可执行文件的六条命令（入口 `0x680`、`main 0x640`、`.rela.plt` 5 项）、以及十二条陷阱。

逐条打勾的达标表在[学习目标自检表](ch07-checklist.md)。这里只留判据：

- **能解释**：函数只声明不定义为什么编译不报错、`libfoo.so` 与 `libfoo.so.1` 谁进了 `NEEDED`、`DT_RPATH` 与 `DT_RUNPATH` 的优先级为什么相反、`LD_PRELOAD` 在静态链接与 `_exit` 收场的程序上为什么不生效。
- **能操作**：用 `nm --defined-only` 定位库成员、用 `readelf -d` 取 `NEEDED`/`BIND_NOW`/`GNU_RELRO`、用 `LD_DEBUG=libs` 看搜索路径、用 `readelf -r` 数和核对 GOT 槽、用 `readelf -V` 做符号版本的差集。
- **能判断**：报错属于哪一层（编译期、链接期、加载期、符号标签层）、该先跑哪条命令、`-static`/`-rpath`/`LD_LIBRARY_PATH` 三种手段各治什么问题与各有什么代价。

如果只记住一件事，那就是**链接与加载是两个不同时间的事**：链接器在构建时把符号拼成地址并把依赖记成 soname，加载器在运行时按 soname 找回文件、按 reloc 表填地址；绝大多数「莫名其妙」的报错，都是把这两段时间混成了一段。

::: errata 本章的口径边界
1. **架构绑定**：正文里带具体地址与字节的 x86-64 输出只是形状示例（VM 是 aarch64，无交叉运行环境）；aarch64 的 `PT_LOAD` 实测 2 条、解释器是 `/lib/ld-linux-aarch64.so.1`，别拿 x86-64 的段数当定律。
2. **默认加固依发行版**：`BIND_NOW`/`GNU_RELRO` 是这台 Ubuntu 24.04 的默认，换发行版要重查；`-z lazy` 才能看到延迟绑定。
3. **`LD_PRELOAD` 的边界**：静态链接、被内联或删除的调用、以及经 `_exit` 收场的程序（`ls`/`cat`）都看不到钩子报告——这不是打桩失败。
:::

::: method 即时自测 · 1.7
**Q1（记忆）** 写出链接四步与各自最典型的一类报错；再说清「函数只声明不定义，编译器为什么不报警」。

**Q2（算）** 已知 `S = 0x401030`、`A = -4`、`P = 0x401141`，按 `S + A - P` 算出 32 位结果与字节串（小端）。

**Q3（判）** `error while loading shared libraries: libfoo.so.1: cannot open shared object file` 与 `version 'FOO_2.0' not found` 分别属于哪一层？各先跑哪条命令？

**Q4（实验）** 一个程序只在 `main` 里调用 `bar()`，`bar` 在 `libbar.a` 里，`libbar.a` 又依赖 `libfoo.a`。`gcc main.o -lbar -lfoo` 失败、`gcc main.o -lfoo -lbar` 成功，解释原因并给出第三种修法。

::: sol 答案
**A1** 符号解析（`undefined reference`）、合并节（少见，表现为段冲突）、重定位（`relocation truncated to fit`）、布局（地址分配）。编译只管「声明在不在、类型对不对」，看不到别的 `.o` 里有没有定义——解析留给链接器，所以只声明不定义能编过、链不过。

**A2** `0x401030 + (-4) - 0x401141 = -0x115`，32 位补码为 `0xfffffeeb`，小端字节串 `eb fe ff ff`（`e8` 是 call 的操作码，前面那条字节）。

**A3** 前者是路径层：加载器按 `NEEDED` 里的 soname 找不到文件，先 `readelf -d` 取 `NEEDED`、再 `LD_DEBUG=libs` 看它搜过哪些目录；后者是符号标签层：文件找到了，但需求表里的版本节点对不上，先 `readelf -V` 看需求、再 `nm -D` 看导出集做差集。

**A4** 归档只从左到右扫一遍：`-lbar` 时 `bar` 被抽出，它引用 `foo`，但 `-lfoo` 还没出现；轮到 `-lfoo` 时没有未解析符号再需要它，成员不被抽出。反过来顺序，`-lfoo` 先出现时 `foo` 还没被需要，同样会失败——真正的原因是「谁先被需要」，所以第三种修法是 `-Wl,--start-group -lbar -lfoo -Wl,--end-group`（或把依赖写成 `-lbar -lfoo -lbar`，但那是权宜）。
:::
:::
