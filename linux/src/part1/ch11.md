[1.10](ch10.md) 把 fd 统一成了字节流的句柄。socket 是这套抽象的一个特例：`read`/`write` 的语义不变，短读、短写、`EINTR`、`EAGAIN` 一条都不用改；变的是**对端**——字节不再来自磁盘，而来自另一台机器上的进程。

网络编程的难点不在 API 数量，而在**边界**：TCP 是字节流，不保留消息边界；连接是四元组，不是「一个 socket」；`accept` 返回的是新 fd；`close` 不等于对方立刻收到；超时、重传、分片由内核处理，应用只能看到「慢」和「断」。这一章先把协议分层与 socket 生命周期讲清楚，再落到两个能跑的服务器上。

协议部分以谢希仁《计算机网络》第 1–6 章为骨架：分层、IP、TCP/UDP、应用层；实现部分以 CSAPP 第 11 章和 Kerrisk 第 58 章为骨架。所有代码以 Linux 6.8、IPv4 为例，IPv6 的差异在 `getaddrinfo` 处点出。

## 1.11.1 客户端-服务器模型与协议分层 {#sec-1.11.1}

这一节回答：两个程序隔着网络，凭什么一个只管发字节、另一个只管收字节，中间的寻址、重传和排队都不用你写？

::: preview 先抓住一件事
网络应用只有两种角色：客户端**主动发起**连接，服务器在某个端口上**循环等待**连接。分层不是四个进程，而是一条路径上逐层加首部、逐层剥首部；你的代码只写应用层的那几个字节。
:::

先做一个最小实验。下面这条命令让 `nc` 在本机 18116 端口当服务器，收到什么就回 `pong`（Ubuntu 24.04.5 aarch64 实测）：

```bash
{ printf 'pong\n'; sleep 5; } | nc -l 127.0.0.1 18116 > lab1c11_req3 &
```

再从同一个 shell 用 bash 的 `/dev/tcp` 当客户端，发一行 `ping`，并趁连接还没关掉看 `ss`：

```text
# 实测；客户端与服务端在同一台机器上
$ ss -ltn 'sport = :18116'
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port
LISTEN 0      1          127.0.0.1:18116      0.0.0.0:*
$ ss -tan 'sport = :18116 or dport = :18116'
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port
LISTEN 0      1          127.0.0.1:18116      0.0.0.0:*
ESTAB  5      0          127.0.0.1:39032      127.0.0.1:18116
ESTAB  0      0          127.0.0.1:18116      127.0.0.1:39032
$ cat lab1c11_req3
ping
```

同一个 `ping\n`，在三处有三种样子：服务器进程读到的文件内容是 `ping`；`ss` 看到的是两条 `ESTAB` 记录，一条 `39032 → 18116`，一条 `18116 → 39032`；网络上跑的是带 TCP/IP 首部的字节。三者说的是同一次交互，只是观察点不同。

**分层**（layering）就是把这件事拆成几段：应用层定义“`ping` 是什么意思”，运输层负责“送到哪个端口、丢了要不要重传”，网络层负责“送到哪台主机”，链路层负责“下一跳怎么走”。发送时每层加自己的首部，叫**封装**（encapsulation）；接收时逐层剥掉，再按首部里的编号把数据交给正确的上层，叫**分用**（demultiplexing）。

<pre class="layout">
应用层   ping\n
         │ 加 TCP 首部（源端口、目的端口、序号、校验和……）
运输层   [ TCP 首部 20B ][ ping\n ]
         │ 加 IP 首部（源 IP、目的 IP、协议号……）
网络层   [ IP 首部 20B ][ TCP 首部 20B ][ ping\n ]
         │ 加以太网首部 14B 与 FCS 4B（回环没有这一段）
链路层   [ 以太网首部 14B ][ IP 包 ... ][ FCS 4B ]
</pre>

首部长度是“无选项时”的最小值；TCP 时间戳等选项会把 20 字节撑大。回环连接不经过以太网，链路层换成 loopback 设备，所以抓包时看不到这 14 字节——图是按以太网画的。

| 层 | 数据单元 | 这一层的地址 | 典型协议 |
|:--|:--|:--|:--|
| 应用层 | 报文 message | 域名 / URL | DNS、HTTP、SSH |
| 运输层 | 段 segment / 数据报 datagram | 端口 | TCP、UDP、QUIC |
| 网络层 | 包 packet | IP 地址 | IPv4、IPv6、ICMP |
| 链路层 | 帧 frame | MAC 地址 | Ethernet、Wi-Fi |
| 物理层 | 比特 bit | — | 双绞线、光纤、无线电 |

这张表只回答“谁负责什么”。真正把一条连接钉死的是**四元组**（4-tuple）：源 IP、源端口、目的 IP、目的端口，再加协议号。服务器的监听 socket 只绑定“本地 IP:端口”这半边；每来一个客户端，内核用四元组建一条连接记录，`accept` 把这条记录交给你，返回一个新的 fd。所以同一台机器的 18116 端口可以同时服务很多客户端，靠的不是很多端口，而是四元组的不同组合。

**这跟写应用有什么关系？** 你调用 `write` 时，只提供 `ping\n` 这 5 个字节；源端口、目的端口、序号、校验和都是内核补的。反过来，`read` 返回的也只有应用数据，IP 首部和 TCP 首部已经被内核剥掉。你唯一要负责的是：把应用层的“消息”讲清楚，别指望 TCP 帮你保留边界——这是 1.11.6 的主题。

::: ex 例 1.11.1 · 先猜这 5 个字节是谁排的队 {#ex-1.11.1}
上面的 `ss` 里，客户端一行 `Recv-Q` 是 5，服务器一行是 0。先猜：这 5 个字节是 `ping\n` 还是 `pong\n`？为什么另一端的队列是空的？

::: sol 解答
是 `pong\n`。服务器进程已经把 `ping\n` 读走并回了 `pong\n`，但客户端还没执行 `read`，所以 5 个字节留在客户端的接收队列里；服务器的 `Recv-Q` 为 0，因为它已经把请求读完了。`Recv-Q` 数的是“已到达内核、还没被应用读走”的字节，不是“网络上正在飞”的字节。
:::
:::

::: errata 常见错误清单（1.11.1 节）
1. **「分层就是四个进程在传数据」**——应用在你的进程里，TCP/IP 与链路层处理通常在内核里；分层是代码路径与首部的层次，不是四个进程。
2. **「端口号就是进程号」**——端口标识的是传输层端点，一个进程可以同时持有多个端口，多个进程也能用 `SO_REUSEPORT` 共享同一端口。
3. **「服务器必须先知道客户端端口才能回包」**——监听 socket 只知道本地端口；客户端端口在 SYN 里带来，内核用四元组建连接记录后，服务器才知道。
4. **「`127.0.0.1` 是这台机器的对外地址」**——它是回环地址，只有本机能访问；要让别的机器连进来，得绑定实际网卡地址或 `INADDR_ANY`。
5. **「回环连接也会走以太网」**——回环走 loopback 设备，没有以太网首部与 FCS；按以太网图去数偏移会对不上。
:::

### 1.11.1 小结

① 客户端发起、服务器在固定端口循环等待，这是网络应用的基本形态；② 分层是逐层加首部与剥首部，应用只看见自己的字节；③ 一条连接由四元组唯一标识，监听 socket 只绑定本地半边。如果只记住一件事，那就是：**`ss` 里的两条 `ESTAB` 是同一条连接的两端，不是两条连接。**

::: method 即时自测 · 1.11.1
**Q1（记忆）** 四元组由哪四项组成？监听 socket 绑定了其中哪几项？

**Q2（辨析）** `ss` 输出两条 `ESTAB`，一条本地端口 39032、一条本地端口 18116。这是两条连接吗？

**Q3（应用）** 客户端 `write` 了 5 个字节，服务器 `read` 为什么可能一次读到 5 个，也可能先读到 2 个？

**Q4（迁移）** 服务器只绑定 `127.0.0.1:18116`，另一台机器为什么连不上？要改哪一行？

::: sol 答案
**A1** 源 IP、源端口、目的 IP、目的端口（再加协议号）。监听 socket 只绑定本地 IP 与本地端口这两项。
**A2** 不是。这是同一条连接的两个端点：客户端端点 `39032 → 18116`，服务器端点 `18116 → 39032`；连接表里是一条记录。
**A3** TCP 是字节流，`read` 的返回只保证“最多这么多字节”，不保证一次读满。5 个字节可能被分成多个段到达，也可能被应用一次取走；要靠循环读和应用层边界判断“读完了没有”。
**A4** 回环地址只在本机路由表里有效。把 `sin_addr` 改成 `INADDR_ANY`（或实际网卡地址）才能让外部连进来；同时要确认防火墙放行。
:::
:::

## 1.11.2 IP、端口与字节序 {#sec-1.11.2}

这一节回答：`bind` 之前为什么一定要 `htons`？少写这一层转换，服务器会绑到哪个端口上？

::: preview 先抓住一件事
IP 地址选主机，端口选主机上的服务端点；协议规定端口与 IP 在首部里用**大端**（网络字节序），而常见的 x86-64 与 AArch64 主机都按小端运行。两台实验机都是小端，所以把同一个程序搬过去，输出逐字相同——差异不在机器之间，而在“主机序”与“网络序”之间。漏掉 `htons` 不会报错，只会绑到另一个端口。
:::

IPv4 地址是 32 位，写成点分十进制；IPv6 地址是 128 位，写成冒号十六进制。端口是 16 位，取值 0–65535。地址选主机，端口选主机上的服务端点，两者在首部里都要按网络序存放。

先看字节。下面是一个只打印 `uint16_t` 与 `uint32_t` 内存布局的小程序，在 Ubuntu 24.04.5 aarch64、GCC 13.3 上实测：

```text
# 实测；同一程序在 macOS arm64 上输出逐字相同
port raw     a0 46
htons        46 a0
ip raw       01 00 00 7f
htonl        7f 00 00 01
htons(18080)=0xa046  htonl=0x0100007f  roundtrip=1
inet_pton    7f 00 00 01
sizeof(struct sockaddr_in)=16
```

`18080` 是 `0x46A0`。小端机器按低字节在前的顺序存成 `a0 46`；`htons` 把它翻成 `46 a0`，这才是首部里“先高字节、后低字节”的网络序。`0x7f000001` 同理：主机里存 `01 00 00 7f`，转换后是 `7f 00 00 01`。`inet_pton("127.0.0.1")` 直接写出 `7f 00 00 01`，因为它产生的就是网络序，**不需要再 `htonl`**。

::: def 定义 1.11.2 · 网络字节序（network byte order） {#def-1.11.2}
IP/TCP/UDP 首部里的多字节整数按大端存放：最高有效字节在最低地址。`htons`/`htonl` 把 16/32 位整数从主机序转到网络序，`ntohs`/`ntohl` 转回来；在小端机器上它们真的翻转字节，在大端机器上是恒等操作。
:::

**为什么两台机器对照看不出差别？** 本书的 macOS 开发机是 arm64，VM 是 aarch64，都是小端；同一个程序在两边打印的字节完全一样。要看见“主机序不同”的对照，需要一台大端机器，或者直接比较“未转换”与“已转换”两组字节。后者在同一台机器上就能做，上面的 `port raw` 与 `htons` 两行就是。

漏掉转换的后果可以实测。`lab1c11_bind.c` 用两种写法绑定同一个端口，再用 `getsockname` 读回内核认定的值：

```c
/* 关键就这两行；其余是 socket/bind/getsockname */
addr.sin_port = htons(18081);   /* 正确：主机序 -> 网络序 */
addr.sin_port = 18081;          /* 错误：小端内存里是 a1 46 */
```

```text
# 实测
$ ./lab1c11_bind net
net: bound port 18081
$ ./lab1c11_bind raw
raw: bound port 41286
$ ./lab1c11_bind priv
priv: bind failed: Permission denied (errno=13)
```

`18081` 是 `0x46A1`；不做转换时内存里是 `a1 46`，内核按网络序读成 `0xA146`，也就是 41286。程序没有报错，`ss` 也会显示 41286——客户端连 18081 只会得到 `Connection refused`。这类“端口差了一位”的故障，先看 `bind` 后 `getsockname` 的值，比猜防火墙快。

端口号 0 是特例：`bind` 时写 0 表示“内核帮我挑一个”，挑完必须用 `getsockname` 读回来，否则你不知道该告诉客户端连哪里。客户端没有显式 `bind` 源端口时，内核从临时端口范围里分配源端口；本机 `/proc/sys/net/ipv4/ip_local_port_range` 是 `32768 60999`，不是 IANA 建议的 49152–65535。

| 范围 | 用途 |
|:--|:--|
| 0 | `bind` 时让内核挑一个端口；`getsockname` 读回 |
| 1–1023 | 知名端口；非 root 默认不能绑定（本机 `ip_unprivileged_port_start=1024`） |
| 1024–49151 | 注册端口，8080、3306 等常落在这里 |
| 49152–65535 | IANA 建议的临时端口段；Linux 实际用上面的 `ip_local_port_range` |

绑定 80 的失败路径实测为 `EACCES`；成功绑定需要 root 或 `CAP_NET_BIND_SERVICE`，本机 `sudo` 不可用，**成功路径未实测**。不要把“能 bind 1024 以下”当成普通用户权限。

地址字符串不要手写 `sscanf("%d.%d.%d.%d")`，也不要再用 `inet_addr`：前者不检查 0–255，后者用 `INADDR_NONE` 表示错误，和广播地址 `255.255.255.255` 撞值。用 `inet_pton`/`inet_ntop`，它们同时支持 IPv4 与 IPv6。

需要“名字 + 服务名 → 地址列表”时，用 `getaddrinfo`。本机实测（`lab1c11_resolve.c`）：

```text
$ ./lab1c11_resolve localhost http
family=AF_INET type=STREAM host=127.0.0.1 port=80
$ ./lab1c11_resolve ::1 http
family=AF_INET6 type=STREAM host=::1 port=80
```

同一个 VM 上 `localhost` 只回了 IPv4 一条，直接写 `::1` 才看到 IPv6；不要假设“localhost 一定同时有 A 和 AAAA”。返回的链表要逐个尝试，完整字段与 `EAI_*` 错误码在 1.11.8。

点分十进制只是表示法；子网划分、CIDR 聚合、路由查找与 DNS 的层级解析不在本章展开，分别见 [4.3 网络层](../part4/ch03.md) 与 [4.7 应用层](../part4/ch07.md)。

::: ex 例 1.11.2 · 先猜内核认成哪个端口 {#ex-1.11.2}
把 `sin_port = htons(18081)` 改成 `sin_port = 18081`，程序不报错。先猜 `getsockname` 会返回多少，再解释 `41286` 是怎么从 `0x46A1` 算出来的。

::: sol 解答
返回 41286。`18081 = 0x46A1`，小端内存是 `a1 46`；内核按网络序读这两个字节，得到 `0xA146 = 41286`。`bind` 只检查端口是否可用，不检查你是不是忘了转换，所以错误会推迟到客户端连不上才暴露。
:::
:::

::: errata 常见错误清单（1.11.2 节）
1. **「`htons` 只是显示格式」**——它改的是内存里的字节顺序；不做转换，内核读出的端口就不是你写的那个。
2. **「`inet_addr` 可以替代 `inet_pton`」**——`inet_addr` 用 `INADDR_NONE` 表示失败，与 `255.255.255.255` 冲突，也不支持 IPv6。
3. **「端口 0 是无效端口」**——`bind` 写 0 是让内核分配；必须 `getsockname` 读回。
4. **「`sockaddr_in` 的所有字段都要 `htons`」**——只有 `sin_port` 与 `sin_addr` 是网络序；`sin_family` 是主机序，`sin_zero` 置零即可。
5. **「49152–65535 就是 Linux 的临时端口」**——那是 IANA 建议；本机实际是 `32768–60999`。
:::

### 1.11.2 小结

① IP 选主机、端口选端点，二者在首部里都是网络序（大端）；② 两台实验机都是小端，跨机对照看不出差异，但“未转换 vs 已转换”在同一台机器上就能看见；③ 漏掉 `htons` 不报错，只会绑到另一个端口。如果只记住一件事，那就是：**凡是进首部的整数，先问一句“这是主机序还是网络序”。**

::: method 即时自测 · 1.11.2
**Q1（记忆）** `htons(18080)` 的返回值写成十六进制是多少？在小端内存里存成哪两个字节？

**Q2（辨析）** 为什么 `inet_pton` 的结果不需要再 `htonl`，而 `inet_addr` 的结果也不该再转？

**Q3（应用）** 服务器 `bind` 时写端口 0，客户端怎么知道该连哪个端口？

**Q4（迁移）** 你把程序从 x86-64 搬到一台大端机器，`htons` 的行为会变吗？`sin_port = 18081` 这种漏转换的写法会变对吗？

::: sol 答案
**A1** `0xA046`；小端内存是 `46 a0`，正好是网络序的两个字节。
**A2** 两者都直接产生网络序的 32 位地址；再 `htonl` 会把它翻回主机序，反而错。
**A3** 服务器 `getsockname` 读回内核分配的端口，再通过日志、配置或服务注册告诉客户端；客户端不能猜。
**A4** `htons` 在大端机器上是恒等操作，返回值仍是 `0xA046`；漏转换的 `sin_port` 在大端上恰好就是网络序，反而“碰巧正确”。所以“在我机器上能跑”不是理由，字节序要按协议写。
:::
:::

## 1.11.3 socket API 与 TCP 生命周期 {#sec-1.11.3}

这一节回答：`socket`、`bind`、`listen`、`accept`、`connect` 各把连接推进到哪一步？为什么 `ss` 会同时出现 `LISTEN`、`ESTAB`、`FIN-WAIT-2`、`CLOSE-WAIT`、`TIME-WAIT`？

::: preview 先抓住一件事
服务器的主干是 `socket → bind → listen → accept`，客户端是 `socket → connect`。`listen` 只是把 fd 挂牌成监听 socket，`accept` 才取走一条已完成握手的连接，并返回**新的 fd**。`close` 是关闭的起点，不是终点：主动关闭方最后停在 `TIME_WAIT`。
:::

```text
服务器：socket() → bind() → listen() → accept() → read/write → close()
客户端：socket() →                 connect() → read/write → close()
```

把两边的调用放进一个程序，最直观。父进程监听一个由内核挑的端口，子进程连上来，双方交换一行（`lab1c11_pair.c`，Ubuntu 24.04.5 aarch64 实测）：

```c
#ifndef _GNU_SOURCE
#define _GNU_SOURCE
#endif
#include <arpa/inet.h>
#include <netinet/in.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/socket.h>
#include <sys/wait.h>
#include <unistd.h>

static void die(const char *m) { perror(m); exit(1); }

int main(void)
{
    int lfd = socket(AF_INET, SOCK_STREAM, 0);
    if (lfd < 0)
        die("socket");

    struct sockaddr_in a = { .sin_family = AF_INET,
                             .sin_addr.s_addr = htonl(INADDR_LOOPBACK),
                             .sin_port = 0 };
    if (bind(lfd, (struct sockaddr *)&a, sizeof(a)) < 0)
        die("bind");
    socklen_t len = sizeof(a);
    if (getsockname(lfd, (struct sockaddr *)&a, &len) < 0)
        die("getsockname");
    if (listen(lfd, 4) < 0)
        die("listen");
    printf("lfd=%d server port=%u\n", lfd, ntohs(a.sin_port));
    fflush(stdout);

    pid_t pid = fork();
    if (pid < 0)
        die("fork");
    if (pid == 0) {
        int fd = socket(AF_INET, SOCK_STREAM, 0);
        if (fd < 0)
            die("socket");
        if (connect(fd, (struct sockaddr *)&a, sizeof(a)) < 0)
            die("connect");
        if (write(fd, "ping", 4) != 4)
            die("write");
        char buf[8] = {0};
        ssize_t n = read(fd, buf, sizeof(buf) - 1);
        printf("client got %zd: %s\n", n, buf);
        fflush(stdout);
        close(fd);
        _exit(0);
    }

    int cfd = accept(lfd, NULL, NULL);
    if (cfd < 0)
        die("accept");
    printf("accept -> cfd=%d\n", cfd);
    char buf[8] = {0};
    ssize_t n = read(cfd, buf, sizeof(buf) - 1);
    printf("server got %zd: %s\n", n, buf);
    if (write(cfd, "pong", 4) != 4)
        die("write");
    close(cfd);
    close(lfd);
    waitpid(pid, NULL, 0);
    return 0;
}
```

```text

client got 4: pong
accept -> cfd=4

```

父进程的监听 fd 是 3，`accept` 返回 4；子进程里的客户端 socket 也是 4。**fd 号是每个进程自己的表**，两个 4 不是同一个对象。子进程打印后必须 `fflush`，因为它用 `_exit` 退出，不会刷新继承来的 stdio 缓冲区——不刷新就会看不到 `client got` 这一行。

`strace` 能把调用顺序与返回值钉死（另一次运行，端口 18082，省略 PID 前缀）：

```text

bind(3, {sa_family=AF_INET, sin_port=htons(18082), sin_addr=inet_addr("127.0.0.1")}, 16) = 0
listen(3, 4)                            = 0

connect(4, {sa_family=AF_INET, ...}, 16) = 0
```

前四行来自父进程：3 是监听 socket，`accept` 返回 4。最后一行来自子进程：它自己的 4 是客户端 socket。两边能对话，是因为内核把两个端点配成了一条连接。

### 一次连接在 `ss` 里怎么走

把上面的程序加上几个 `sleep`，在四个时刻抓 `ss`，就能看到状态迁移（端口 18082，`ss -tan` 实测，省略无关行）：

| 时刻 | 服务器侧 | 客户端侧 | 关键行 |
|:--|:--|:--|:--|
| `listen` 后 | `LISTEN` | — | `LISTEN 0 4 127.0.0.1:18082` |
| `connect` 后 | `ESTAB` | `ESTAB` | 两条 `ESTAB`，端口 18082 与 46582 互为对端 |
| 服务器先 `close` | `FIN-WAIT-2` | `CLOSE-WAIT` | 客户端 `Recv-Q` 为 1 |
| 客户端再 `close` | `TIME-WAIT` | — | `TIME-WAIT 0 0 127.0.0.1:18082 ...` |

连接建立要三次握手：客户端发 SYN，服务器回 SYN+ACK 并进入 `SYN-RCVD`，客户端回 ACK 后两边都进 `ESTABLISHED`。关闭要四次挥手：主动关闭方发 FIN，进入 `FIN-WAIT-1`；收到 ACK 后进 `FIN-WAIT-2`；对端读到 EOF 后进 `CLOSE-WAIT`，等自己的应用 `close` 再发 FIN，进 `LAST-ACK`；主动方收到这个 FIN 后回 ACK，进 `TIME-WAIT`。

`TIME-WAIT` 持续 2×MSL。Linux 把 `TCP_TIMEWAIT_LEN` 固定为约 60 秒，所以一条主动关闭的连接会在 `ss` 里挂一分钟左右。它做两件事：最后一个 ACK 丢了还能重发；让这条旧连接的迷路报文在网络里消散，不至于串到复用了同一四元组的新连接上。哪一端主动 `close`，`TIME-WAIT` 就出现在哪一端；短连接服务器常常是主动关闭方，所以 `TIME-WAIT` 多。注意 `/proc/sys/net/ipv4/tcp_fin_timeout` 的 60 管的是 `FIN-WAIT-2`，不是 `TIME-WAIT`，两个“60 秒”别混为一谈。

客户端 `CLOSE-WAIT` 那一行的 `Recv-Q` 是 1，不是还有 1 字节数据。FIN 本身占一个序号，本机把它记在接收队列里；应用再 `read` 一次会拿到 0（EOF），这个 1 才消失。**看到 `CLOSE-WAIT` 堆积，先查应用是不是忘了 `close`**，而不是查网络。

队列要单独说。`listen(fd, backlog)` 的 `backlog` 限制的是**已完成握手、等待 `accept` 取走**的全连接队列；本机 `net.core.somaxconn` 是 4096，实际上限取两者较小值。`ss -lnt` 在监听 socket 上，`Recv-Q` 是当前排队的连接数，`Send-Q` 是 backlog 上限（上面 `listen(3, 4)` 就显示 4）。半连接队列（收到 SYN、还没完成握手）是另一个队列。队列满时 Linux 默认丢弃或忽略 ACK，客户端会重传，表现是“连接慢”而不是“连接被拒”；这条路径在 1.11.16 用计数再看一次。

`accept` 返回的新 fd 绑定这条连接的四元组；监听 fd 继续停在 `LISTEN` 接新连接。新 fd 在 Linux 上**不继承**监听 fd 的 `O_NONBLOCK`，要非阻塞就在 `accept4` 里带 `SOCK_NONBLOCK | SOCK_CLOEXEC`。`close` 只是把当前进程的 fd 引用减一；如果这个 socket 还被 `fork` 出的子进程持有，连接不会因为父进程 `close` 而断开。

| 选项 | 作用 | 什么时候用 |
|:--|:--|:--|
| `SO_REUSEADDR` | 允许绑定处于 `TIME_WAIT` 的本地地址 | 服务器重启时 |
| `SO_REUSEPORT` | 多个 socket 绑同一端口，内核分流 | 多进程/多线程 accept |
| `TCP_NODELAY` | 关闭 Nagle 合并 | 交互式/低延迟协议 |
| `SO_LINGER` | 控制 `close` 时等待还是发 RST | 需要精确关闭语义时 |

选项的完整语义与坑在 1.11.9；这里只要记住：`SO_REUSEADDR` 解决的是“重启时 `bind` 失败”，不是“`TIME_WAIT` 占着端口所以服务坏了”。`TIME_WAIT` 是协议的正常状态，不是泄漏。

::: ex 例 1.11.3 · 先猜 `TIME-WAIT` 落在哪一端 {#ex-1.11.3}
程序里服务器先 `close`，客户端 6 秒后才 `close`。先猜：`ss` 里的 `TIME-WAIT` 会出现在 18082 这一端还是 46582 这一端？`CLOSE-WAIT` 那一行的 `Recv-Q` 为 1，这 1 个字节是什么？

::: sol 解答
`TIME-WAIT` 出现在 18082 这一端，因为服务器是主动关闭方；客户端先进入 `CLOSE-WAIT`，等它 `close` 后发 FIN，服务器回 ACK 才进 `TIME-WAIT`。`Recv-Q` 的 1 不是数据，是尚未被 `read` 取走的 FIN 占的序号；再读一次得到 0，队列归零。
:::
:::

::: errata 常见错误清单（1.11.3 节）
1. **「`listen` 之后就能直接 `read` 客户端数据」**——监听 fd 没有连上任何对端；必须先 `accept` 拿到连接 fd，读写出错通常是 `ENOTCONN`。
2. **「backlog 是服务器最多能接受的连接数」**——它限制的是已完成握手、等待 `accept` 的队列；已建立的连接可以远多于 backlog，超出部分会被丢弃或让客户端重传。
3. **「`close` 返回后对端立刻读到 EOF」**——`close` 只是把 FIN 排进发送队列，返回时 ACK 还没回来；前面的数据也可能还没被对端读走。
4. **「`TIME-WAIT` 是端口泄漏，服务写坏了」**——它是主动关闭方的正常状态，持续 2×MSL；大量短连接会积累，但不是错误，`SO_REUSEADDR` 只影响重启时能否 `bind`。
5. **「`accept` 的新 fd 继承监听 fd 的非阻塞标志」**——Linux 上不继承；要非阻塞就用 `accept4` 显式带 `SOCK_NONBLOCK`。
6. **「`CLOSE-WAIT` 堆积是网络问题」**——对端已经关了，本端应用还没 `close`；先查代码里的 fd 生命周期。
:::

### 1.11.3 小结

① `socket/bind/listen/accept` 把服务器从“有一个 fd”推进到“有一条连接”，`connect` 在客户端做对应的事；② `accept` 返回新 fd，监听 fd 继续接客，fd 号只在各自进程内有意义；③ 状态迁移由谁先 `close` 决定，主动关闭方进 `TIME-WAIT`。如果只记住一件事，那就是：**`LISTEN` 是挂牌，`ESTAB` 才是连接；`close` 之后还有四次挥手。**

**Q3（应用）** `listen(fd, 4)` 之后同时有 10 个客户端完成握手，但服务器还没 `accept`。第 5 个会得到明确的“拒绝”吗？

**A1** 服务器 `socket → bind → listen → accept`；客户端 `socket → connect`。`accept` 返回新 fd，`socket` 也返回新 fd，但 `accept` 的是连接 fd。

**A3** 不会。全连接队列按 `backlog=4` 限制（实际边界因内核实现略有出入，还受 `somaxconn` 限制），多出来的连接可能被丢弃或忽略 ACK，客户端重传，表现为慢或超时；要区分“拒绝”（RST）与“排队溢出”。
**A4** 出现在客户端。客户端会占用一个临时端口约 60 秒；短连接压测时可能耗尽临时端口。`TIME-WAIT` 在 Linux 里固定约 60 秒，`tcp_fin_timeout` 调不了它；通常靠连接复用，而不是去改内核参数。

## 1.11.4 一个 fork 并发的 echo 服务器 {#sec-1.11.4}

这一节回答：一个服务器怎样同时服务多个客户端，而每个连接的处理代码仍像“只服务一个客户端”那样顺序读写？

::: preview 先抓住一件事
`accept` 留在父进程的循环里，每取到一条连接就 `fork` 一个子进程；子进程拿着连接 fd 顺序 `read`/`write`，父进程继续 `accept`。父子各自关掉自己不需要的那一半 fd，`SIGCHLD` 负责回收。并发上限是进程数，不是端口数。
:::

### 场景：三个客户端同时连上来

服务器在 18115 端口监听，三个客户端各发一行，然后停 4 秒再关（`nc -N` 在 stdin 结束时发 FIN）：

```bash
./lab1c11_echo 18115 &
for n in A B C; do
  (printf 'hello-%s\n' "$n"; sleep 4) | nc -N 127.0.0.1 18115 > "lab1c11_out$n" &
done
```

趁三个连接都开着，看 `ss` 与进程表（Ubuntu 24.04.5 aarch64 实测；端口、PID 与 inode（socket 在文件系统里的编号）随运行变化，PID/inode 用占位符）：

一条 `LISTEN`、六条 `ESTAB`，因为三条连接各有两端；三个子进程状态都是 `S`（可中断睡眠），不是 `Z`（僵尸）；子进程的 fd 表里只有 0、1、2 和连接 socket 4，没有监听 fd 3——父进程在 `fork` 后立刻 `close(cfd)`，子进程在 `fork` 后立刻 `close(lfd)`。三个客户端各收到自己的那一行，没有串线：每条连接在内核里是独立的四元组，子进程各读各的 fd。

客户端关掉后，`pgrep -P <server-pid>` 返回空——`SIGCHLD` 处理函数把子进程回收了。如果只 `waitpid` 一次，标准信号不排队，剩下的子进程会变成僵尸；这就是处理函数里要循环 `waitpid(-1, ..., WNOHANG)` 的原因。

### 服务器代码

```c
/* echo_server.c：cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 */
#ifndef _GNU_SOURCE
#define _GNU_SOURCE
#endif
#include <arpa/inet.h>
#include <errno.h>
#include <signal.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/wait.h>
#include <unistd.h>

static void reap(int signo)
{
    (void)signo;
    int saved = errno;
    while (waitpid(-1, NULL, WNOHANG) > 0)
        ;
    errno = saved;
}

static int write_all(int fd, const char *buf, size_t n)
{
    while (n > 0) {
        ssize_t w = write(fd, buf, n);
        if (w < 0) {
            if (errno == EINTR)
                continue;
            return -1;
        }
        if (w == 0) {
            errno = EIO;
            return -1;
        }
        buf += (size_t)w;
        n -= (size_t)w;
    }
    return 0;
}

static void serve(int fd)
{
    char buf[4096];
    for (;;) {
        ssize_t n = read(fd, buf, sizeof(buf));
        if (n < 0) {
            if (errno == EINTR)
                continue;
            break;
        }
        if (n == 0)
            break;
        if (write_all(fd, buf, (size_t)n) < 0)
            break;
    }
}

static void die(const char *msg)
{
    perror(msg);
    exit(1);
}

int main(int argc, char **argv)
{
    if (argc != 2) {
        fprintf(stderr, "usage: %s <port>\n", argv[0]);
        return 2;
    }
    int port = atoi(argv[1]);
    if (port <= 0 || port > 65535) {
        fprintf(stderr, "bad port\n");
        return 2;
    }

    int lfd = socket(AF_INET, SOCK_STREAM, 0);
    if (lfd < 0)
        die("socket");
    int on = 1;
    setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof(on));

    struct sockaddr_in a = {
        .sin_family = AF_INET,
        .sin_port = htons(port),
        .sin_addr.s_addr = htonl(INADDR_ANY),
    };
    if (bind(lfd, (struct sockaddr *)&a, sizeof(a)) < 0)
        die("bind");
    if (listen(lfd, 128) < 0)
        die("listen");

    struct sigaction sa = { .sa_handler = reap,
                            .sa_flags = SA_RESTART | SA_NODEFER };
    sigemptyset(&sa.sa_mask);
    sigaction(SIGCHLD, &sa, NULL);

    printf("echo server listening on %d\n", port);
    fflush(stdout);
    for (;;) {
        int cfd = accept(lfd, NULL, NULL);
        if (cfd < 0) {
            if (errno == EINTR)
                continue;
            die("accept");
        }
        pid_t pid = fork();
        if (pid < 0) {
            perror("fork");
            close(cfd);
            continue;
        }
        if (pid == 0) {
            close(lfd);
            serve(cfd);
            close(cfd);
            _exit(0);
        }
        close(cfd);
    }
}
```

关键点：

- 父进程 `close(cfd)` 后，子进程仍持有这条连接；fd 是引用计数，关闭一个副本不影响另一个。
- 子进程 `close(lfd)`，否则监听 fd 会留在子进程里；只要还有一个子进程活着，端口就一直被占着，重启时旧进程的残留会挡路。
- `SIGCHLD` 处理函数循环 `waitpid(WNOHANG)`；标准信号不排队，只回收一个会留下僵尸。
- `SA_RESTART` 让 `accept` 被信号打断后自动重启；代码仍处理 `EINTR`，因为并非所有调用都会重启。
- 子进程用 `_exit`，避免刷新从父进程继承的 stdio 缓冲区；代价是子进程自己的 `printf` 也要手动 `fflush`，否则看不到输出（1.11.3 的 `client got` 就是这个坑）。
- `write_all` 处理短写：socket 的 `write` 可能只写一部分，必须循环到 `n == 0`；`EINTR` 要继续，`write` 返回 0 视为错误。

这个模型的并发上限是进程数。连接数上千时，`fork` 的页表复制和上下文切换成本变高；[1.12](ch12.md) 会给出线程池与 `epoll`（批量等待 fd 事件的内核接口）两个替代方案。`fork` 版的好处是隔离：一个连接崩溃不会带走整个服务器；坏处是每个连接一个进程，内存与调度开销都随连接数线性增长。

::: ex 例 1.11.4 · 先猜同时连三个客户端会多出几个进程 {#ex-1.11.4}
三个客户端同时连上时，服务器一共几个进程？子进程的 fd 表里有没有监听 fd？三个客户端都断开后，`ps` 里还能看到子进程吗？

::: sol 解答
一共 4 个：1 个父进程 + 3 个子进程。子进程的 fd 表里没有监听 fd，因为 `fork` 后立刻 `close(lfd)`；父进程的 fd 表里没有连接 fd，因为 `accept` 后把 `cfd` 交给了子进程并 `close(cfd)`。客户端断开后，`SIGCHLD` 处理函数循环 `waitpid(WNOHANG)` 把三个子进程都回收了，`ps` 里看不到；如果只回收一个，另外两个会以 `Z` 状态留着。
:::
:::

::: errata 常见错误清单（1.11.4 节）
1. **「`fork` 后父子共享同一张 fd 表，关一个另一个也关」**——fd 表是复制的，表项指向同一个打开文件描述；父进程 `close(cfd)` 只减引用计数，子进程的副本仍可读写。
2. **「子进程不用关监听 fd，反正用不到」**——它会一直持有监听 socket，端口在子进程存活期间无法真正释放；连接多了还会泄漏 fd。
3. **「`SIGCHLD` 来几次就会排队几次，处理函数回收一个就够」**——标准信号不排队，多个子进程同时退出可能只递送一次；必须循环 `waitpid` 到没有可回收的为止。
4. **「有了 `SA_RESTART` 就不用处理 `EINTR`」**——`SA_RESTART` 只对部分可重启的调用有效；`accept`/`read` 仍可能返回 `EINTR`，代码要自己 `continue`。
5. **「`fork` 版能轻松撑上万连接」**——每个连接一个进程，页表、栈、调度都是成本；连接数上千就该考虑线程池或 `epoll`（1.12）。
6. **「`_exit` 与 `exit` 一样」**——`exit` 会刷新 stdio、跑 `atexit`；子进程用 `exit` 可能把父进程缓冲区里的内容再刷一遍。用 `_exit`，需要输出就自己 `fflush`。
:::

### 1.11.4 小结

① 父进程只负责 `accept`，子进程只负责一条连接的 `read`/`write`，并发就落在进程上；② 父子各自关掉不需要的 fd，连接靠引用计数活到最后一个副本关闭；③ `SIGCHLD` 必须循环回收，`_exit` 不刷新 stdio。如果只记住一件事，那就是：**监听 fd 留在父进程，连接 fd 交给子进程，两边都只保留自己需要的那一半。**

## 1.11.5 HTTP 与一个最小 Web 服务器 {#sec-1.11.5}

这一节回答：1.11.4 的 echo 服务器把读到的字节原样送回；HTTP 服务器凭什么知道一条请求在哪里结束，响应又该在哪里停下？

::: preview 先抓住一件事
HTTP 报文不是「一次 read」，而是落在 TCP 字节流上的一段格式：请求行、头部、空行、正文。头部结束只有一个可靠判据 `\r\n\r\n`；响应必须用 `Content-Length`、chunked 或关闭连接告诉客户端正文到哪为止。
:::

先看一次真实交互。下面的服务器在 18091 端口返回当前目录的 `index.html`，用 `curl -v` 访问（Ubuntu 24.04.5 aarch64 实测）：

```text
$ curl -sv --http1.1 http://127.0.0.1:18091/index.html
*   Trying 127.0.0.1:18091...
* Connected to 127.0.0.1 (127.0.0.1) port 18091
> GET /index.html HTTP/1.1
> Host: 127.0.0.1:18091
> User-Agent: curl/8.5.0
> Accept: */*
>
< HTTP/1.1 200 OK
< Content-Length: 52
< Content-Type: text/html; charset=utf-8
< Connection: close
<
{ [52 bytes data]
* Closing connection
<!doctype html>
<title>lab1c11</title>
hello, world
```

`>` 开头是 curl 发出的请求，`<` 开头是服务器回的响应，单独一个 `>` 是头部后的空行。线上每行以 `\r\n` 结尾，所以头部结束标记是最后一个头部的 CRLF 加空行的 CRLF，合起来是 `\r\n\r\n`。请求行由方法、目标、版本组成；HTTP/1.1 要求 `Host`，`User-Agent` 和 `Accept` 是 curl 加的。响应形状相同：状态行、头部、空行、正文。

同一请求发给 `python3 -m http.server`，响应行变成 `HTTP/1.0 200 OK`，头部多了 `Server: SimpleHTTP/0.6 Python/3.12.3` 与 `Date`，curl 会打印 `HTTP 1.0, assume close after body`。版本不同，边界规则相同：头看 `\r\n\r\n`，正文看长度或 EOF。

::: def 定义 1.11.5 · HTTP 报文边界 {#def-1.11.5}
HTTP/1.1 的头部从请求行（或状态行）开始，到第一个空行结束；线上空行的完整标记是 `\r\n\r\n`。头部没有长度字段，只能靠这个标记切分；正文长度由 `Content-Length`、chunked 或连接关闭决定。
:::

为什么不能找 `\n\n`？RFC 9112 规定行结束是 CRLF；部分服务器宽容地接受裸 LF，但代理和旧客户端不一定。按 `\r\n\r\n` 切，至少不会把「自己这边能过、代理那边被拒」的请求当成正常。正文里也可能出现 `\r\n\r\n`，只能在头部区域找第一个。

下面的 `lab1c11_httpserv.c` 把这条规则写成能跑的静态文件服务器：一次服务一个连接，只处理 GET，把 URL 路径映射到当前目录。

```c
/* lab1c11_httpserv.c：最小静态文件服务器
   cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -o lab1c11_httpserv lab1c11_httpserv.c */
#ifndef _GNU_SOURCE
#define _GNU_SOURCE
#endif
#include <arpa/inet.h>
#include <errno.h>
#include <fcntl.h>
#include <signal.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/stat.h>
#include <unistd.h>

static int write_all(int fd, const char *buf, size_t n)
{
    while (n > 0) {
        ssize_t w = write(fd, buf, n);
        if (w < 0) {
            if (errno == EINTR)
                continue;
            return -1;
        }
        if (w == 0) {
            errno = EIO;
            return -1;
        }
        buf += (size_t)w;
        n -= (size_t)w;
    }
    return 0;
}

static void send_error(int cfd, int code, const char *reason)
{
    char body[128];
    int n = snprintf(body, sizeof(body), "%d %s\n", code, reason);
    char head[256];
    int h = snprintf(head, sizeof(head),
                     "HTTP/1.1 %d %s\r\nContent-Length: %d\r\n"
                     "Content-Type: text/plain\r\nConnection: close\r\n\r\n",
                     code, reason, n);
    if (h > 0 && (size_t)h < sizeof(head)) {
        (void)write_all(cfd, head, (size_t)h);
        (void)write_all(cfd, body, (size_t)n);
    }
}

static void handle(int cfd)
{
    char req[4096];
    size_t used = 0;

    while (used < sizeof(req) - 1) {
        ssize_t n = read(cfd, req + used, sizeof(req) - 1 - used);
        if (n < 0) {
            if (errno == EINTR)
                continue;
            return;
        }
        if (n == 0)
            break;
        used += (size_t)n;
        req[used] = '\0';
        if (strstr(req, "\r\n\r\n") != NULL)
            break;
    }
    if (used == 0)
        return;
    if (strstr(req, "\r\n\r\n") == NULL) {
        send_error(cfd, 400, "Bad Request");
        return;
    }

    char method[8], uri[512], version[16];
    if (sscanf(req, "%7s %511s %15s", method, uri, version) != 3) {
        send_error(cfd, 400, "Bad Request");
        return;
    }
    if (strcmp(method, "GET") != 0) {
        send_error(cfd, 405, "Method Not Allowed");
        return;
    }
    if (uri[0] != '/' || strstr(uri, "..") != NULL) {
        send_error(cfd, 403, "Forbidden");
        return;
    }

    const char *rel = strcmp(uri, "/") == 0 ? "/index.html" : uri;
    char path[1024];
    int pn = snprintf(path, sizeof(path), ".%s", rel);
    if (pn <= 0 || (size_t)pn >= sizeof(path)) {
        send_error(cfd, 414, "URI Too Long");
        return;
    }

    struct stat st;
    if (stat(path, &st) < 0 || !S_ISREG(st.st_mode)) {
        send_error(cfd, 404, "Not Found");
        return;
    }

    int fd = open(path, O_RDONLY);
    if (fd < 0) {
        send_error(cfd, 403, "Forbidden");
        return;
    }

    const char *ctype = strstr(path, ".html") ? "text/html; charset=utf-8" :
                        strstr(path, ".css")  ? "text/css; charset=utf-8" :
                        strstr(path, ".js")   ? "application/javascript" :
                                                "application/octet-stream";
    char head[512];
    int h = snprintf(head, sizeof(head),
                     "HTTP/1.1 200 OK\r\nContent-Length: %lld\r\n"
                     "Content-Type: %s\r\nConnection: close\r\n\r\n",
                     (long long)st.st_size, ctype);
    if (h <= 0 || (size_t)h >= sizeof(head) ||
        write_all(cfd, head, (size_t)h) < 0) {
        close(fd);
        return;
    }

    char buf[8192];
    for (;;) {
        ssize_t n = read(fd, buf, sizeof(buf));
        if (n < 0) {
            if (errno == EINTR)
                continue;
            break;
        }
        if (n == 0)
            break;
        if (write_all(cfd, buf, (size_t)n) < 0)
            break;
    }
    close(fd);
}

int main(int argc, char **argv)
{
    if (argc != 2) {
        fprintf(stderr, "usage: %s <port>\n", argv[0]);
        return 2;
    }
    int port = atoi(argv[1]);
    if (port <= 0 || port > 65535) {
        fprintf(stderr, "bad port\n");
        return 2;
    }

    signal(SIGPIPE, SIG_IGN);            /* 客户端提前关闭时不要杀死服务器 */

    int lfd = socket(AF_INET, SOCK_STREAM, 0);
    if (lfd < 0) {
        perror("socket");
        return 1;
    }

    int on = 1;
    setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof(on));

    struct sockaddr_in addr;
    memset(&addr, 0, sizeof(addr));
    addr.sin_family = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);
    addr.sin_port = htons((uint16_t)port);

    if (bind(lfd, (struct sockaddr *)&addr, sizeof(addr)) < 0) {
        perror("bind");
        close(lfd);
        return 1;
    }
    if (listen(lfd, 128) < 0) {
        perror("listen");
        close(lfd);
        return 1;
    }

    printf("http server on http://127.0.0.1:%d/\n", port);
    for (;;) {
        int cfd = accept(lfd, NULL, NULL);
        if (cfd < 0) {
            if (errno == EINTR)
                continue;
            perror("accept");
            break;
        }
        handle(cfd);
        close(cfd);
    }

    close(lfd);
    return 0;
}
```

服务器的骨架仍是 1.11.4 的 `socket → bind → listen → accept`，变的是 `handle` 里的读法。关键有三处。

第一处是读循环。`read` 只说明这一次拿到多少字节，代码把字节追加到 `req`、补 `\0`，再用 `strstr(req, "\r\n\r\n")` 找头部结束。`EINTR` 要继续，`n == 0` 说明对端提前关了连接。缓冲区 4096 字节；填满还没找到空行就是头部超长，必须报错，不能拿半截请求解析。

第二处是循环之后的检查。很多教学代码在这里直接 `sscanf`，这是最危险的捷径：只要前几个字节能拼出「方法 + 路径」，解析就会「成功」。代码在循环后补了 `strstr(...) == NULL` 就返回 400；生产服务器通常区分 400（不完整）与 431（头部太大），并给头部总大小、单行长度、头部数量设上限。

第三处是响应边界。`Content-Length: 52` 来自 `stat` 的文件大小，`Connection: close` 说明这个连接只服务一次。两者同时出现时客户端按长度读；只关连接不给长度，HTTP/1.0 靠 EOF 判断，HTTP/1.1 的 keep-alive 客户端会一直等。`write_all` 只把字节交给内核，不保证对端收到；对端提前关闭会触发 `SIGPIPE`，所以开头忽略了它。

只读一次 `recv` 会怎样？把循环换成一句 `recv(cfd, req, sizeof req - 1, 0)`，再把同一请求拆成两段发送。实测（Ubuntu 24.04.5 aarch64）：

```text
# 实测；第一段 8 字节，1 秒后发第二段
$ { printf 'GET /ind'; sleep 1; printf 'ex.html HTTP/1.1\r\nHost: x\r\n\r\n'; } | nc -N 127.0.0.1 18086
HTTP/1.1 200 OK
Content-Length: 3
Content-Type: text/plain
Connection: close

ok
# 服务器端 stderr
one recv: n=8 text=[GET /ind]
sscanf parsed method=GET uri=/ind
```

服务器只看到 `GET /ind`，`sscanf` 却返回 2：它把 `GET` 当方法、`/ind` 当完整路径，于是回了 200。客户端收到语法合法的响应，但请求的后半段 `ex.html HTTP/1.1...` 在回复之后才到，已经被丢掉。换成本节的循环服务器，同一对分段会先累积到 37 字节，找到 `\r\n\r\n` 后再解析，返回 52 字节的 `index.html`（实测）。

::: errata HTTP 服务器的四个常见坑
1. **「一次 `read` 就是一条请求」**——回环常一次读满 88 字节，只说明这次恰好拼成一包；判据是 `\r\n\r\n`，不是 `read` 次数。
2. **「`sscanf` 成功就说明请求合法」**——它只按空白分词，`GET /ind` 也能解析出两个字段，但路径并不完整。
3. **「不写 `Content-Length` 也能 keep-alive」**——没有长度、没有 chunked、又不关连接，客户端只能等超时。
4. **「`write` 返回就代表客户端收到」**——`write` 只把字节放进本机发送缓冲区，真正的确认在 TCP 层。
:::


### MIME 类型与 CGI：静态与动态内容的分界 {#sec-1.11.5.1}

静态服务器按扩展名给 `Content-Type`：`.html` 用 `text/html; charset=utf-8`，`.css` 用 `text/css`，未知类型用 `application/octet-stream`。少了 `charset`，中文可能乱码；把 HTML 标成 `text/plain`，浏览器就不渲染。

CGI 是最早的动态内容办法：服务器 `fork` 子进程，把请求元数据放进环境变量，正文写到 stdin，子进程的 stdout 就是响应。它每个请求一个进程，现代多用 FastCGI 或反向代理；但「环境变量 + stdin/stdout」仍是理解网关的起点。

### 1.11.5 小结

① HTTP 请求与响应都是「行 + 头 + 空行 + 正文」，头部结束只能靠 `\r\n\r\n`；② 服务器要循环读到这个序列并设缓冲区上限，解析成功不等于请求完整；③ 响应必须用 `Content-Length`、chunked 或关闭连接告诉客户端正文在哪结束。如果只记住一件事：**先找 `\r\n\r\n`，再谈解析；先定正文长度，再谈 keep-alive。**

## 1.11.6 字节流边界、MTU 与 TCP/UDP 选择 {#sec-1.11.6}

这一节回答：TCP 明明按顺序把字节送到了，为什么你 `write` 两次、对端 `read` 一次也能读全？应用凭什么把一条消息从字节流里切出来？

::: preview 先抓住一件事
TCP 只保证字节有序到达，不保留「你写了几次」；消息边界必须由应用层自己定义。常用三种办法：长度前缀、分隔符、关闭连接。MTU 决定一个 IP 包能装多少，MSS 决定一条 TCP 段能装多少应用数据；选 TCP 还是 UDP，先问「丢一条能不能忍」。
:::

先做一个会失败的假设。服务器连发两条 100 字节的消息，客户端只 `read` 一次、缓冲区给 4096。第一次 `read` 可能返回 100，也可能返回 200，还可能只返回 60——取决于两条消息是否被合进同一个段、是否被拆分。三次都「成功」，但你对「一条消息」的判断全错了。

TCP 是**字节流**（byte stream），不是消息流。它只维护字节的顺序与可靠性，不记录应用的写入次数。`write` 两次与 `write` 一次 200 字节，在对端看来没有区别。

::: def 定义 1.11.6 · 消息边界与 MSS {#def-1.11.6}
**消息边界**（message boundary）是应用层用来判断「一条消息到哪里结束」的规则，TCP 不提供。**MSS**（Maximum Segment Size）是一条 TCP 段能携带的应用数据上限，通常由路径 MTU 减去 IP 与 TCP 首部得到；以太网 MTU 1500 时，IPv4 的 MSS 是 1460，IPv6 是 1440。
:::

三种划界办法：

| 方案 | 线上长什么样 | 怎么读 | 适合 |
|:--|:--|:--|:--|
| 长度前缀 | `[4 字节大端长度][body]` | 先读满 4 字节，再按长度读 body | 二进制协议、RPC |
| 分隔符 | `hello\nworld\n` | 循环读到 `\n`，剩余字节留给下一条 | 文本协议、Redis RESP |
| 关闭连接 | 响应发完就 `close` | `read` 返回 0 即结束 | 一次性响应、HTTP/1.0 |

定长记录是长度前缀的特例：长度写在协议规范里，不占线上字节。HTTP 是组合拳：头部用 `\r\n\r\n` 分隔，正文用 `Content-Length` 或 chunked 定长，最后才轮到关连接。

长度前缀的坑在「先读满」：`read` 可能只拿到 2 字节，必须循环；长度字段本身也要校验上限，否则对端报一个 4 GB，你的缓冲区就炸了。分隔符的坑在「转义」：正文里出现分隔符怎么办？要么禁止（如 HTTP 头部），要么转义，要么像 RESP 那样先给长度。

### MTU 与 MSS：一个包能装多少

以太网 MTU 通常 1500 字节。IPv4 首部 20 字节、TCP 首部 20 字节，所以 TCP 单段最大载荷 MSS = 1460；IPv6 首部 40 字节，MSS = 1440。首部带选项时还会再少几字节。

本机实测（Ubuntu 24.04.5 aarch64）：

```text
$ ip link show enp0s5 | head -1
2: enp0s5: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP mode DEFAULT group default qlen 1000
$ ip link show lo | head -1
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN mode DEFAULT group default qlen 1000
$ ping -c 1 -M do -s 1472 10.211.55.1
1 packets transmitted, 1 received, 0% packet loss, time 0ms
$ ss -tin state established | grep ':80 '
	 cubic ... mss:1460 pmtu:1500 ... (节选)
```

`-s 1472` 加 8 字节 ICMP 首部与 20 字节 IP 首部正好 1500；`-M do` 禁止分片，能通说明路径允许 1500。回环 MTU 是 65536，所以本机回环上看不到 1460 的限制。

超过 MTU 的 IP 包会被分片（IPv4 路由器可分片，IPv6 通常由源端分片），接收端重组。分片丢失会导致整个包重传，性能很差；路径 MTU 发现（PMTUD）靠 ICMP「需要分片」消息调整 MSS，ICMP 被防火墙丢弃时会出现「小包能通、大包卡住」的黑洞。

### TCP 还是 UDP

| 维度 | TCP | UDP |
|:--|:--|:--|
| 连接 | 面向连接，三次握手 | 无连接，直接 `sendto` |
| 可靠性 | 确认、重传、有序 | 不保证到达、顺序、去重 |
| 边界 | 字节流，无消息边界 | 保留数据报边界 |
| 拥塞控制 | 有（cwnd、慢启动） | 无，应用自己控制 |
| 首部 | 20 字节起 | 8 字节 |
| 典型用途 | HTTP、SSH、数据库 | DNS、视频、游戏、QUIC 底层 |

UDP 的 `sendto` 成功只表示「交给了本机网络栈」，不代表对端收到；需要可靠性就在应用层实现序号、确认、重传，或者直接用 QUIC。UDP 也可以 `connect`，之后用 `send`/`recv`，好处是内核记录对端并回传 ICMP 错误，但它仍然不可靠。

::: errata 边界与 MTU 的五个误解
1. **「`write` 两次，对端就 `read` 两次」**——TCP 不保留写入次数，合包与拆包都可能发生。
2. **「UDP 有边界，所以不会丢」**——边界保留，但到达、顺序、去重都不保证。
3. **「MTU 1500 就是一次能发 1500 字节应用数据」**——要减掉 IP 与 TCP 首部，IPv4 只剩 1460。
4. **「分片由接收端负责，发端不用管」**——IPv4 路由器可分片，IPv6 通常源端分片；任一片丢失都要重传整包。
5. **「回环也是 MTU 1500」**——本机 `lo` 的 MTU 是 65536，回环测试不能代替真实网卡。
:::

### 1.11.6 小结

① TCP 只给有序字节流，消息边界要应用层自己定；② 长度前缀、分隔符、关闭连接是三种基本划法，HTTP 是「分隔符 + 长度」的组合；③ MTU 1500 下 IPv4 的 MSS 是 1460、IPv6 是 1440，分片会放大丢包代价。如果只记住一件事：**`read` 的返回长度只说明「这次到了多少」，不说明「一条消息结束了」。**

## 1.11.7 排障：从 socket 到报文 {#sec-1.11.7}

这一节回答：服务「连不上」「连上了没响应」「响应被截断」时，先看哪个证据、按什么顺序看，才能不靠猜？

::: preview 先抓住一件事
顺序固定为：先 `ss` 看内核里的连接状态与队列，再用 `strace -e trace=network` 看进程发出的系统调用，最后才抓包看线上字节。前两步不需要特权；抓包需要 `CAP_NET_RAW`，没有权限时用 `ss -ti` 的 `mss`/`rtt` 与重传统计替代。
:::

先起一个能复现的服务。本节的 HTTP 服务器监听 18091，请求一次后正常关闭。把排查分成三步，每一步只回答一个问题；下面的 PID 用 `<pid>` 代替，临时端口随运行变化。

### 第一步：`ss` 问「内核认为连接在哪」

```text
# 实测；Ubuntu 24.04.5 aarch64
$ ss -tlnp 'sport = :18091'
State  Recv-Q Send-Q Local Address:Port  Peer Address:PortProcess
LISTEN 0      128          0.0.0.0:18091      0.0.0.0:*    users:(("lab1c11_httpser",pid=<pid>,fd=3))
$ ss -tanp 'sport = :18091 or dport = :18091'
State     Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
LISTEN    0      128          0.0.0.0:18091      0.0.0.0:*     users:(("lab1c11_httpser",pid=<pid>,fd=3))
TIME-WAIT 0      0          127.0.0.1:18091    127.0.0.1:47702
```

`State` 先分三类：没有 `LISTEN` 说明服务没起来或绑错地址；只有 `SYN-SENT` 说明对端不回 SYN+ACK（防火墙、路由、端口未监听）；有 `ESTAB` 说明连接已建立。`Recv-Q`/`Send-Q` 在监听 socket 上是 accept 队列长度与 backlog 上限，在连接 socket 上是「已到达内核、应用还没读走」与「应用写了、内核还没发完」的字节数。

后者可以单独造出来：服务器 `accept` 后不读，客户端发 5000 字节，再看：

```text
$ ss -tanp 'sport = :18094 or dport = :18094'
State Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
LISTEN 0      1          127.0.0.1:18094      0.0.0.0:*     users:(("python3",pid=<pid>,fd=3))
ESTAB  0      0          127.0.0.1:35786    127.0.0.1:18094 users:(("python3",pid=<pid>,fd=3))
ESTAB  5000   0          127.0.0.1:18094    127.0.0.1:35786 users:(("python3",pid=<pid>,fd=4))
```

服务端 `Recv-Q` 是 5000，客户端 `Send-Q` 是 0：字节已经到了服务端内核，只是应用没读。看到 `Recv-Q` 持续上涨，先查应用是不是卡住或读得太慢，不要先怀疑网络。

### 第二步：`strace` 问「进程到底发了什么」

`ss` 只说明内核状态，不说明进程调用了什么。用 `strace -f -e trace=network,read,write` 跟住服务器，再发一次请求：

```text
# 实测；省略 PID 前缀
socket(AF_INET, SOCK_STREAM, IPPROTO_IP) = 3
bind(3, {sa_family=AF_INET, sin_port=htons(18093), sin_addr=inet_addr("0.0.0.0")}, 16) = 0
listen(3, 128)                          = 0
accept(3, NULL, NULL)                   = 4
read(4, "GET /index.html HTTP/1.1\r\nHost: "..., 4095) = 88
write(4, "HTTP/1.1 200 OK\r\nContent-Length:"..., 98) = 98
write(4, "<!doctype html>\n<title>lab1c11</"..., 52) = 52
```

这条链能回答三件事：`accept` 返回 4，说明连接进来了；`read` 返回 88，说明请求到了应用；两次 `write` 返回 98 与 52，说明响应头与正文都交给了内核。如果 `read` 返回 0，是对端先关；如果卡在 `read`，是请求没到齐；如果 `write` 返回 `EPIPE`，是对端已经关了。

`-e trace=network` 只留网络系统调用；加上 `read,write` 才能看到字节数。`-f` 跟子进程，fork 服务器不加就看不到子进程的读写。`strace` 会拖慢程序、改变时序，偶发问题可能因此消失，这是它的代价。

### 第三步：抓包问「线上到底是什么字节」

`tcpdump` 能看到 TCP 首部、握手、重传与 RST，但本机没有权限：

```text
$ tcpdump -i any -nn -c 1 'tcp port 18093'
tcpdump: any: You don't have permission to perform this capture on that device
(socket: Operation not permitted)
```

需要 root 或 `CAP_NET_RAW`，本节环境不满足，**抓包未实测**。没有权限时，用 `ss -ti` 看每条连接的 `mss`、`rtt`、`retrans`，用 `nstat -az TcpRetransSegs` 看全局重传；它们回答不了「报文里是什么」，但能区分「没发出去」「发了没回」「回了被丢」。

三类症状的入口可以压成一张表：

| 症状 | `ss` 先看 | `strace` 先看 |
|:--|:--|:--|
| 连不上 | 有没有 `LISTEN`、是否停在 `SYN-SENT` | `connect` 的返回值与 `errno` |
| 连上没响应 | `ESTAB` 后 `Recv-Q` 是否上涨 | 有没有 `read`、`read` 返回多少 |
| 响应被截断 | `CLOSE-WAIT`、`Send-Q` 是否残留 | `write` 返回值与 `EPIPE` |

这张表只是入口：三类症状都可能出在对端、本机或中间设备，排障要求两侧能解释同一个数字。

::: errata 排障的四个误区
1. **「先抓包最直接」**——抓包要特权、输出大、还看不出应用读没读；`ss` 与 `strace` 更快定位到层。
2. **「`Recv-Q` 大就是网络堵」**——连接 socket 上的 `Recv-Q` 是应用没读，监听 socket 上才是 accept 队列。
3. **「`tcpdump` 没权限说明网络坏了」**——那只是本机缺 `CAP_NET_RAW`，与被测连接无关。
4. **「`strace` 看到 `write` 成功就代表对端收到」**——`write` 成功只代表字节进了本机发送缓冲区。
:::

### 1.11.7 小结

① 先用 `ss` 看状态与队列，分清「没连上」「连上没读」「写了没发完」；② 再用 `strace` 看系统调用的参数与返回值，把问题钉到某一侧；③ 最后才抓包，没有 `CAP_NET_RAW` 就用 `ss -ti` 与 `nstat` 替代。如果只记住一件事：**先问内核状态，再问进程行为，最后才问线上字节。**

::: method 即时自测 · 1.11.7
**Q1（记忆）** 排障的三步顺序是什么？哪一步需要特权？

**Q2（辨析）** 监听 socket 与连接 socket 上的 `Recv-Q` 各表示什么？看到 5000 该先查什么？

**Q3（应用）** `strace` 里 `accept` 返回 4，但一直没有 `read(4, ...)`。最可能的原因是什么？

**Q4（迁移）** 生产机没有 `CAP_NET_RAW`，你想判断「是没发出去还是发了没回」，能用哪些不需要特权的证据？

::: sol 答案
**A1** `ss` → `strace -e trace=network` → 抓包。抓包需要 root 或 `CAP_NET_RAW`。
**A2** 监听 socket 上是已完成握手、等待 `accept` 的连接数（上限是 backlog）；连接 socket 上是已到达内核、应用还没读走的字节数。看到 5000 先查应用是否卡住或读得太慢。
**A3** 客户端连上了但没发数据，或应用在 `accept` 后卡在别处；也可能请求还在路上。看客户端 `Send-Q` 与 `strace` 的后续调用。
**A4** `ss -ti` 看 `mss`/`rtt`/`retrans`，`nstat -az TcpRetransSegs` 看重传，`ss -s` 看全局队列；再结合应用日志与 `strace` 的返回值。
:::
:::

## 1.11.8 `getaddrinfo` 全字段：hints、flags 与错误 {#sec-1.11.8}

这一节回答：1.11.2 只用了 `getaddrinfo` 的最小形式；真正写客户端和服务器时，`hints` 里哪些字段要填、`AI_PASSIVE` 改变了什么、失败时 `EAI_AGAIN` 与 `EAI_NONAME` 该不该重试？

::: preview 先抓住一件事
`getaddrinfo` 把「名字 + 服务」变成一条 `addrinfo` 链表；`hints` 只填四个输入字段，其余清零。客户端用 `AF_UNSPEC` 逐个候选 `connect`，服务器用 `AI_PASSIVE` + `node = NULL` 逐个候选 `bind`。失败返回 `EAI_*` 而不是 `errno`：`EAI_AGAIN` 是临时失败，可以退避重试；`EAI_NONAME` 是确定不存在，重试没有意义。
:::

`struct addrinfo` 有八个字段，只有四个是输入：

| 字段 | 方向 | 含义 | 常见取值 |
|:--|:--|:--|:--|
| `ai_flags` | 输入 | 行为开关 | `AI_PASSIVE`、`AI_NUMERICHOST`… |
| `ai_family` | 输入 | 地址族 | `AF_UNSPEC`、`AF_INET`、`AF_INET6` |
| `ai_socktype` | 输入 | 套接字类型 | `SOCK_STREAM`、`SOCK_DGRAM` |
| `ai_protocol` | 输入 | 协议 | 0（按 type 选）、`IPPROTO_TCP` |
| `ai_addrlen` | 输出 | `ai_addr` 的长度 | 传给 `bind`/`connect` |
| `ai_addr` | 输出 | 指向 `sockaddr` 的指针 | 直接使用 |
| `ai_canonname` | 输出 | 规范主机名 | 仅 `AI_CANONNAME` 的第一个结果 |
| `ai_next` | 输出 | 下一条结果 | 链表，最后 `freeaddrinfo` |

核心代码只有几行：

```c
struct addrinfo hints = {0};          /* 必须清零，否则字段是栈上的垃圾 */
hints.ai_family = AF_UNSPEC;
hints.ai_socktype = SOCK_STREAM;
struct addrinfo *res = NULL;
int rc = getaddrinfo(node, service, &hints, &res);
if (rc != 0) {
    fprintf(stderr, "getaddrinfo: %s\n", gai_strerror(rc));
    return -1;
}
for (struct addrinfo *p = res; p != NULL; p = p->ai_next) {
    int fd = socket(p->ai_family, p->ai_socktype, p->ai_protocol);
    if (fd < 0) continue;
    if (connect(fd, p->ai_addr, p->ai_addrlen) == 0) { /* 用这个 fd */ break; }
    close(fd);
}
freeaddrinfo(res);
```

同样的循环把 `connect` 换成 `bind` + `listen`，就是服务器的候选链。链表用完必须 `freeaddrinfo`，否则每次解析都漏一块内存。关键在 `AI_PASSIVE` 与 `node = NULL`：前者让解析器返回通配地址，后者表示「不指定主机」。本机实测（`lab1c11_gai`，Ubuntu 24.04.5 aarch64）：

```text
$ ./lab1c11_gai client localhost http
0: family=AF_INET type=SOCK_STREAM proto=6 host=127.0.0.1 port=80 canon=(null)
total=1 mode=client(AF_UNSPEC)
$ ./lab1c11_gai client ip6-localhost http
0: family=AF_INET6 type=SOCK_STREAM proto=6 host=::1 port=80 canon=(null)
total=1 mode=client(AF_UNSPEC)
$ ./lab1c11_gai server 8080
0: family=AF_INET type=SOCK_STREAM proto=6 host=0.0.0.0 port=8080 canon=(null)
1: family=AF_INET6 type=SOCK_STREAM proto=6 host=:: port=8080 canon=(null)
total=2 mode=server(AI_PASSIVE)
$ ./lab1c11_gai client nonexistent.invalid 80
getaddrinfo rc=-2: Name or service not known
$ ./lab1c11_gai numeric localhost 80
getaddrinfo rc=-2: Name or service not known
```

`localhost` 只回了 IPv4，`ip6-localhost` 才是 IPv6；`AF_UNSPEC` 只是「不限制」，不保证两个族都有。`AI_PASSIVE` + `NULL` 则同时给出 `0.0.0.0` 与 `::`。

`ai_flags` 里最常用的五位：

| flag | 作用 | 什么时候用 | 坑 |
|:--|:--|:--|:--|
| `AI_PASSIVE` | `node == NULL` 时返回通配地址 | 服务器 `bind` 前 | `node` 非空时被忽略 |
| `AI_NUMERICHOST` | 禁止 DNS，只接受数字地址 | 禁止解析、减少延迟 | 传域名返回 `EAI_NONAME` |
| `AI_NUMERICSERV` | 服务必须是数字端口 | 避免查 `/etc/services` | 传 `"http"` 返回 `EAI_NONAME` |
| `AI_ADDRCONFIG` | 只返回本机已配置的地址族 | 双栈客户端挑可达族 | 容器只有 loopback 时可能过滤掉 IPv6 |
| `AI_V4MAPPED` | 无 IPv6 结果时返回 `::ffff:a.b.c.d` | 只想要 IPv6 socket 的双栈程序 | 需与 `AF_INET6` 同用 |

`AI_V4MAPPED` 常和 `AF_INET6` 一起用：程序只建 IPv6 socket，解析器把 IPv4 地址包成 `::ffff:127.0.0.1`。不设它时，`AF_INET6` 查询拿不到 IPv4 结果，候选链可能为空。

失败时的返回值不是 `errno`，而是 `EAI_*` 码；`errno` 只在 `EAI_SYSTEM` 时有意义。`EAI_SERVICE` 与 `EAI_NONAME` 也容易混：前者是服务名与 `ai_socktype` 不匹配（如 `domain` 配 `SOCK_STREAM`），后者是名字本身不存在。本机的 `gai_strerror` 字面输出：

```text
$ ./lab1c11_gai codes
EAI_AGAIN (-3): Temporary failure in name resolution
EAI_NONAME (-2): Name or service not known
EAI_SERVICE (-8): Servname not supported for ai_socktype
EAI_FAMILY (-6): ai_family not supported
EAI_SYSTEM (-11): System error
```

区别在「重试有没有意义」：

- `EAI_SYSTEM` 是解析器内部的系统调用失败（如创建 socket 失败），这时才去看 `errno`；其余 `EAI_*` 与 `errno` 无关。
- `EAI_AGAIN`：解析器暂时拿不到答案——DNS 超时、SERVFAIL、上游不可达。等一会儿再试可能成功，适合指数退避。
- `EAI_NONAME`：名字或服务确定不存在——域名拼错、NXDOMAIN，或 `AI_NUMERICHOST` 收到了域名。重试只会重复失败，应该报错。

`nonexistent.invalid` 的返回链能看清这一点：`getaddrinfo` 走 NSS 的 `dns` 模块，向 `127.0.0.53:53` 发查询，收到 NXDOMAIN，于是返回 `EAI_NONAME`。`dig` 与 `strace` 两侧的证据一致：

```text
# 实测；省略 sendmmsg 的 iov 内容
$ dig nonexistent.invalid | grep status:
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 17128
$ strace -e trace=network ./lab1c11_gai client nonexistent.invalid 80
connect(3, {sa_family=AF_INET, sin_port=htons(53), sin_addr=inet_addr("127.0.0.53")}, 16) = 0
sendmmsg(3, [{msg_hdr={... iov_base="\324\276\1 \0\1..."...}}], 2, MSG_NOSIGNAL) = 2
recvfrom(3, "\324\276\201\203\0\1..."..., 2048, 0, ...) = 60
getaddrinfo rc=-2: Name or service not known
```

`EAI_AGAIN` 在本机没有造出来：VM 的解析器对测试名字立即回 NXDOMAIN，要复现超时得让 DNS 查询无人应答，需要改 `/etc/resolv.conf` 或停掉解析器，本书没有做，**EAI_AGAIN 未实测**。

::: errata `getaddrinfo` 的五个坑
1. **「`hints` 不用清零」**——未填字段是栈上的垃圾，`ai_flags` 随机位会让结果完全变样。
2. **「`AI_PASSIVE` 对客户端也有用」**——它只在 `node == NULL` 时返回通配地址；客户端误用会去连 `0.0.0.0`。
3. **「`AF_UNSPEC` 一定返回 IPv4 + IPv6」**——`localhost` 在本机只有 IPv4；要两个族都有，得先有对应的地址与记录。
4. **「失败看 `errno`」**——先看返回值是不是 `EAI_*`，只有 `EAI_SYSTEM` 才去读 `errno`。
5. **「`EAI_AGAIN` 和 `EAI_NONAME` 都是失败，随便重试」**——前者可退避重试，后者重试无意义。
:::

### 1.11.8 小结

## 1.11.9 socket 选项：`SO_REUSEADDR`、`SO_REUSEPORT` 与 `TCP_NODELAY` {#sec-1.11.9}

这一节回答：代码没改、只是重启服务，`bind` 为什么报 `Address already in use`？两个进程能不能同时监听 8080？为什么关掉 Nagle，交互会变快？

::: preview 先抓住一件事
`socket` 的默认值是给「一次连接」设计的，不是给「长期在线的服务器」设计的。`SO_REUSEADDR` 让你在 `TIME_WAIT` 还没消失时重新 `bind` 同一端口；`SO_REUSEPORT` 让多个进程合法地共享同一端口，由内核分流新连接；`TCP_NODELAY` 关掉 Nagle，用更多小包换更低的往返延迟。三个选项各修一段不同的行为，谁也替代不了谁。
:::

先造一次重启。服务器监听 8082，处理一个请求后主动关闭连接；马上再 `bind` 同一端口（实测，Ubuntu 24.04.5 aarch64）：

```text
reuse=0 bind: 98 Address already in use
reuse=1 bind ok
State     Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
TIME-WAIT 0      0          127.0.0.1:8082    127.0.0.1:56058
```

占着端口的不是进程，而是一个已经没有进程、只剩内核状态的连接。主动关闭的一方进入 `TIME_WAIT`，Linux 默认停留 60 秒（`2 × MSL`；`net.ipv4.tcp_fin_timeout` 管的是 `FIN_WAIT_2`，不是它）。这段时间端口仍被登记，新 `bind` 冲突，返回 `EADDRINUSE`（errno 98）。想连实验一起做：第一任服务器要开一次 `SO_REUSEADDR`，再关掉它重试，就能看到同一行报错。

::: def 定义 1.11.9 · 端口复用与 `TIME_WAIT`
**`TIME_WAIT`** 是 TCP 主动关闭方发完最后一个 ACK 后停留的状态，作用是让迟到的旧报文在网络里消散，并在最后一个 ACK 丢失时还能回应对端重发的 FIN。**端口复用**指旧连接尚未完全消失时，允许新 socket 使用同一个本地端口；Linux 用 `SO_REUSEADDR` 与 `SO_REUSEPORT` 两个开关，分别处理「旧状态残留」与「多个监听者共存」。
:::

`SO_REUSEADDR` 只做一件事：`bind` 时忽略「地址相同、状态为 `TIME_WAIT`」的冲突。它必须在 `bind` 之前设置：

```c
int on = 1;
if (setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof on) == -1)
    perror("SO_REUSEADDR");
```

两个边界要说清。第一，它救不了「另一个进程正在 `LISTEN` 同一地址端口」——那是真有人在用。第二，`TIME_WAIT` 的那条连接会继承**当初监听 socket** 的复用标记：实验里若第一任服务器没开 `SO_REUSEADDR`，第二任即使开了也照样 `EADDRINUSE`。所以正确姿势是从第一版代码起就开，而不是等出事再加。

`SO_REUSEPORT` 是另一层：它允许多个 socket 绑定完全相同的地址与端口，内核按四元组哈希把每条新连接交给其中一个。实测：

```text
plain 2nd bind: 98 Address already in use
SO_REUSEPORT 2nd bind ok
State  Recv-Q Send-Q Local Address:Port Peer Address:PortProcess
LISTEN 0      8            0.0.0.0:8083      0.0.0.0:*
LISTEN 0      8            0.0.0.0:8083      0.0.0.0:*
```

两条 `LISTEN` 指向同一端口，`ss` 不会替你区分谁是谁。约束有三个：所有监听者都要设置该选项且属于同一 uid；只在 `bind` 时检查一次；连接建立后固定在某个 socket 上，没有迁移。它适合 prefork 式多 acceptor：每个 worker 各跑一个事件循环、各有一个 listen fd，省掉多个进程抢同一个 accept 队列的惊群。

`TCP_NODELAY` 在协议层（`IPPROTO_TCP`），关的是 Nagle 算法。Nagle 把「还有未确认小包」时的新数据攒起来，等 ACK 或攒够一个 MSS 再发；它和对端延迟 ACK（最多等约 40 ms 再确认）叠加，会让请求-响应型协议出现固定停顿。SSH、Redis、RPC 这类每次几十字节又马上等回复的协议通常打开它；大文件下载保持默认更省小包。

```c
int one = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &one, sizeof one);
```

代价是包变多、首部开销变大；而且它只影响本端发送，管不了对端会不会延迟确认。`accept` 返回的新 fd 不继承监听 fd 上的 `TCP_NODELAY`，要在每条连接上单独设。

| 选项 | 改的是 | 修什么症状 | 不要指望它 |
|:--|:--|:--|:--|
| `SO_REUSEADDR` | `bind` 的冲突判定 | 重启时 `EADDRINUSE` | 抢别人正在 `LISTEN` 的端口 |
| `SO_REUSEPORT` | 同端口多监听者 | 多进程分流的部署 | 把一条连接搬到另一个进程 |
| `TCP_NODELAY` | 本端发送时机 | 小请求的固定延迟 | 提升带宽或降低丢包 |

::: errata 关于 socket 选项的三个误解
1. **「`SO_REUSEADDR` 能让两个进程同时监听」**——不能；同端口共存要 `SO_REUSEPORT`，且双方都得设置。
2. **「`TIME_WAIT` 是 bug，调小就好」**——它保护新连接不被旧报文污染；调小换来的是更隐蔽的串包。
3. **「所有服务都该开 `TCP_NODELAY`」**——批量传输打开它只增加小包与首部开销，要按流量类型决定。
:::

### 1.11.9 小结

① 重启时的 `EADDRINUSE` 多半是主动关闭方留下的 `TIME_WAIT`，`SO_REUSEADDR` 在 `bind` 前打开即可绕过；② 同端口多监听是 `SO_REUSEPORT` 的职责，内核按四元组分流且连接不迁移；③ `TCP_NODELAY` 用小包换低延迟，只影响本端发送。如果只记住一件事：**先分清端口是被「进程」占着，还是被「状态」占着。**

::: method 即时自测 · 1.11.9

## 1.11.10 HTTP 报文边界与 TINY 的解剖 {#sec-1.11.10}

这一节回答：`curl` 怎么知道响应已经读完了？TINY 那两百多行里，哪几行决定报文边界，哪些它故意没写？

::: preview 先抓住一件事
HTTP 报文是「文本头 + 可选 body」，头和 body 用两套规则划界：头靠 `\r\n\r\n`（1.11.5），body 靠 `Content-Length`、chunked 或关闭连接（1.11.6 的三种划法）。TINY 是 CSAPP 第 11.6 节的迭代式 HTTP/1.0 服务器，它把四种情形简化成一种：用文件大小写 `Content-Length`，发完就关。看懂它没写的那几块，就知道生产服务器在忙什么。
:::

1.11.5 的服务器只回了「头部 + 一行正文」，1.11.7 的 `strace` 现场里响应头 98 字节、正文 52 字节，`curl -v` 看到的 `Content-Length: 52` 与之对应。客户端读完这 52 字节就收手，不需要等连接关闭——这就是长度边界带来的确定性。再看四种情形：

| 场景 | body 边界 | 客户端怎么读 |
|:--|:--|:--|
| 有 `Content-Length` | 定长 | 读满指定字节数即停 |
| `Transfer-Encoding: chunked` | 分块 | 读十六进制块长 + 数据 + 空行，块长 0 结束 |
| 无长度、非 chunked | 关闭连接 | 一直读到 `read` 返回 0 |
| `HEAD`、`204`、`304` | 立即结束 | 没有 body，即使带了 `Content-Length` 也不读 |

chunked 的线上字节长这样：

```text
HTTP/1.1 200 OK\r\n
Transfer-Encoding: chunked\r\n
\r\n
5\r\n
hello\r\n
6\r\n
 world\r\n
0\r\n
\r\n
```

块长是**十六进制**，块数据后必须跟 `\r\n`；最后一块长度为 0，后面可以跟 trailer，再以空行结束。解析要用 `strtoul(s, NULL, 16)`，用 `atoi` 会把 `1a` 读成 1。请求侧同理：请求行 + 头 + 空行，有 body 时按 `Content-Length` 或 chunked 读；头部的结束标志永远是 `\r\n\r\n`。

::: def 定义 1.11.10 · 报文边界（framing）
**framing** 是「一条消息在哪里开始、在哪里结束」的规则。HTTP 把它拆成两层：头部 framing 固定为 `\r\n\r\n`；body framing 由 `Content-Length`（定长）、`Transfer-Encoding: chunked`（分块）或连接关闭（EOF）三选一；`HEAD`、`204`、`304` 由协议直接规定「没有 body」。
:::

### TINY 的源码结构

TINY 只有一个 `main` 加四个辅助函数，串起来是一条直线：

| 函数 | 源码级做什么 | 边界在哪里断 |
|:--|:--|:--|
| `main` | `open_listenfd` 后循环 `accept`，每个连接调 `doit`，返回即 `close` | 一条连接一个请求，隐式 `Connection: close` |
| `doit` | `rio_readlineb` 读请求行，`sscanf` 拆出方法、URI、版本，只认 `GET`，再调 `read_requesthdrs`、`parse_uri`、`serve_static` | 请求行按 `\n` 切，不校验长度 |
| `read_requesthdrs` | 循环 `rio_readlineb` 直到读到空行，读到的头全部丢弃 | 只找「空行」，不解析任何头字段 |
| `parse_uri` | 在 `?` 处切断，前半当文件名，后半当 CGI 参数 | 不做百分号解码，不做 `..` 规范化 |
| `serve_static` | `stat` 取大小与类型，目录则拼 `index.html`，`open` + `mmap`，按 `st_size` 写 `Content-Length`，再 `rio_writen` 正文 | body 边界来自「文件多大」，不是协议分析 |

最关键的一行在 `read_requesthdrs`：它把 `Host`、`Content-Length`、`Connection` 全部读掉、全部扔掉。GET 没有 body 时这无害；可一旦有人发 POST，请求 body 还留在内核接收缓冲区里，TINY 既不知道有多长、也不会读走它。短连接把这个错误掩盖了——`close` 一关，剩下的字节一起消失。若给它加 keep-alive，这些字节就会被当成下一条请求的开头，这叫请求走私的雏形。

`serve_static` 的 `Content-Length` 来自 `stat` 的 `st_size`，这也解释了 1.11.5 里为什么「先 `stat` 再写头」：头部一旦发出，长度就改不了了。文件在 `stat` 与 `mmap` 之间被改写，响应长度就会和实际字节对不上——生产服务器要么先打开文件再 `fstat`，要么接受这种竞态。

TINY 故意省略的东西，恰好是生产服务器的主要工作：

- **没有 keep-alive**：每请求一连接，握手成本重复付。
- **没有并发**：单线程串行，一个慢客户端阻塞后面所有连接。
- **没有超时**：slowloris 用极慢的头发送就能耗住连接。
- **没有路径规范化**：`GET /../etc/passwd` 只要拼得出路径就会打开；`%2e%2e%2f` 还能绕过字符串检查。
- **没有请求体处理**：如上，POST 的 body 无人读。

所以 TINY 的价值不是「能上线」，而是「把 HTTP 的最小闭环压到能一眼看完」：解析请求行、扔掉头、映射文件、写长度和正文。

::: errata 关于 HTTP 边界的三个误解
1. **「有 `Content-Length` 就一定有 body」**——`HEAD`、`204`、`304` 是例外，长度字段存在但正文为空。
2. **「chunked 的块长按十进制读」**——十六进制，且块后必须跟 `\r\n`；用 `atoi` 会读错。
3. **「TINY 读了头就等于读了整个请求」**——它丢掉了 `Content-Length`，请求 body 留在流里；短连接把问题藏了起来。
:::

### 1.11.10 小结

① 头部边界只有一种——`\r\n\r\n`；body 边界有四种——定长、chunked、EOF、无 body；② chunked 的块长是十六进制，块后跟 `\r\n`，0 块收尾；③ TINY 用「文件大小 + 关闭连接」解决了静态 GET，代价是丢掉所有头字段、没有并发与超时。如果只记住一件事：**读 HTTP 先问「头在哪结束」，再问「body 由谁定长」。**

::: method 即时自测 · 1.11.10

**Q2（辨析）** TINY 的 `read_requesthdrs` 读完头就丢弃。为什么短连接下看不出问题，加了 keep-alive 就出事？

**Q3（应用）** 一个响应写着 `Transfer-Encoding: chunked`，第一块是 `1a\r\n`。这一块有多少字节？该用什么函数解析？

::: sol 答案

## 1.11.11 并发模型：进程、线程、事件循环与 io_uring（内核异步 I/O 接口） {#sec-1.11.11}

这一节回答：一台机器、一个服务，凭什么同时招呼几千条连接？四种并发模型到底把「等待」放在了哪里？

::: preview 先抓住一件事
并发模型的差别不在「谁更快」，而在三件事：阻塞发生在哪个执行单元、每条连接的状态存在哪里、一个连接出错会波及谁。进程最隔离也最贵，线程便宜一半但仍占栈，事件循环把等待压进内核、用一个线程管所有 fd，io_uring（把 I/O 请求成批排队提交、完成也成批取阅的接口）再把「搬数据」也交给内核。选型先看你要同时等多少条空闲连接，而不是看基准测试排名。
:::

1.11.4 的 fork echo 能跑，但一千条空闲连接就是一千个进程：每个进程一套页表、一个地址空间，切换还要换 TLB（地址翻译缓存）。换成线程，地址空间共享了，可每个线程默认 8 MiB 栈（`ulimit -s`），一千个就是 8 GiB 虚拟内存（每线程独占的地址空间视图），调度器里还挂着一千个可运行实体。可这些连接大多数时间什么都不干——只是在等对端发字节。事件循环正是冲着这个浪费来的：一个线程、一张 fd 表、每条连接一个几 KB 的缓冲区。

| 模型 | 代表 | 每连接成本 | 等待放在哪 | 主要代价 |
|:--|:--|:--|:--|:--|
| 每连接一进程 | TINY、Apache prefork | 页表 + 独立地址空间（MB 级） | 进程阻塞在 `read` | `fork` 贵，连接数受限 |
| 每连接一线程 | Apache worker、传统 Java | 栈（默认 8 MiB，可调）+ TCB | 线程阻塞在 `read` | 锁竞争、切换、栈内存 |
| 事件循环 | nginx、Redis、Node.js | 一个 fd + 用户态缓冲（KB 级） | 全部挂在 `epoll_wait` | 回调复杂，一处阻塞卡死全局 |
| 异步 I/O | io_uring、IOCP | 提交/完成队列项 | 内核代劳 | 内核版本、编程模型新 |

「线程版撑不住」的真正原因常常不是创建线程，而是**每个线程的栈**和**同时在跑的线程数**。把栈调到 64 KiB、用线程池复用，几千连接也能撑；但每个请求都要等网络时，线程大多在睡眠，内存与切换照样付。

### select、poll、epoll 的分界

三者都在回答「哪几个 fd 现在可读」，差别在每次询问要交多少东西给内核：

| 接口 | 每次调用 | 连接上限 | 触发方式 | 关键限制 |
|:--|:--|:--|:--|:--|
| `select` | 全量拷 fd 集，返回后重建 | `FD_SETSIZE`（通常 1024） | 水平 | 位图，fd 号不能大 |
| `poll` | 全量拷 `pollfd` 数组 | 受内存与 fd 限制 | 水平 | 返回后仍要遍历全部 |
| `epoll` | 注册一次，只取就绪链表 | 受 `RLIMIT_NOFILE` | 水平/边沿 | 仅 Linux；`fork` 后共享有坑 |

`epoll` 省在**内核维护了就绪链表**：`epoll_ctl` 把 fd 注册进红黑树，事件到来时挂到就绪链表，`epoll_wait` 只返回链表里的项，不需要每次把全部 fd 拷进内核再扫一遍。但「快」有前提：连接大多空闲、事件稀疏。所有连接都持续有数据时，`epoll_wait` 每次返回一大把，用户态处理成本一点没少。

水平触发（level-triggered，LT）是默认：缓冲区还有数据，下次 `epoll_wait` 继续报。边沿触发（edge-triggered，ET）只在状态变化时报一次，**必须一次读到 `EAGAIN`**，否则剩下的数据不会再有新事件。所以 ET 不是「性能开关」，而是一份契约：fd 非阻塞 + 读循环读到 `EAGAIN` + 写侧自己缓冲没发完的字节。1.11.12 会把这三点写成代码。

::: def 定义 1.11.11 · 就绪通知与完成通知
**就绪通知**（readiness）只说「现在读不会阻塞」，真正的 `read` 仍要你自己发起；`select`、`poll`、`epoll` 都属于这一类。**完成通知**（completion）由内核替你把数据搬进你给的缓冲区，做完再报告「这件事完成了」；io_uring、POSIX AIO、Windows IOCP 属于这一类。前者是「告诉我什么时候能动手」，后者是「你动手，做完叫我」。
:::

### io_uring：把等待也交给内核

io_uring 用两个环形队列对接用户态与内核：提交队列 SQ 放请求（opcode、fd、缓冲区、长度），完成队列 CQ 放结果（返回值、用户数据）。应用填好一批 SQE，一次 `io_uring_enter` 提交；内核做完后写 CQE，应用一次收一批。这既能省系统调用，也让「读、写、accept、超时」用同一套接口排队。

本机实测只验证到建环（Ubuntu 24.04.5 aarch64，内核 7.0.0-38-generic）：

```text
$ ./lab1c11_uring
io_uring_setup -> 3 errno=0 (ok)
```

`io_uring_setup` 返回了 fd，说明内核允许创建环；但完整的「提交 SQE → 收 CQE → echo 回数据」这条数据路径本节没有写，**io_uring 的提交/完成回环未实测**。它也不总是可用：部分发行版用 `kernel.io_uring_disabled` 关闭它，容器里的 seccomp 也常直接拒绝。

还有一条常被忽略的上限：本机 `ulimit -n` 是 1024，一个线程想持有上万连接，先得把这个软限制提上去，否则 `accept4` 会以 `EMFILE` 失败。模型选对了，资源上限没调，照样卡在 1024。

::: errata 关于并发模型的四个误解
1. **「epoll（批量等待 fd 事件的内核接口）一定比 select 快多少倍」**——事件稀疏时才明显；全部活跃时用户态处理成本仍在，倍数是场景决定的。
2. **「线程池能解决 C10K」**——线程池省的是创建开销，阻塞在 `read` 的线程照样一个占一个。
3. **「io_uring 一定更快」**——批量提交对小请求有帮助，但版本、权限、调试成本都要算进去。
4. **「ET 只是性能开关，随时可换」**——ET 要求非阻塞与读到 `EAGAIN`；换成阻塞 fd，事件循环会直接卡死。
:::

### 1.11.11 小结

① 四种模型的差别在「等待放哪」：进程/线程各阻塞各的，事件循环把等待收进 `epoll_wait`，io_uring 连搬数据都交给内核；② `epoll` 快在内核维护就绪链表，前提是事件稀疏；③ ET 是契约不是开关，配非阻塞并读到 `EAGAIN` 才成立。如果只记住一件事：**先数空闲连接，再选模型；先看 fd 上限，再谈一万连接。**

## 1.11.12 完整程序：边沿触发的 epoll echo 服务器 {#sec-1.11.12}

这一节回答：边沿触发、非阻塞、单线程这三件事落到代码是什么样？写错哪一行，客户端会直接收到 connection reset？

::: preview 先抓住一件事
一个线程管所有连接，靠的是四条约定：监听 fd 与连接 fd 都非阻塞；全部注册为 `EPOLLET`；每次事件都把 `read` 或 `accept4` 做到 `EAGAIN`；写不完的字节留在用户态缓冲区，等 `EPOLLOUT` 再发。少任何一条，事件循环就会丢事件或卡死。下面这份 `lab1c11_epoll.c` 能直接编译运行，输出是本书虚拟机的真实记录。
:::

程序把「读到的字节先抄进自己的缓冲区、能写多少写多少」做成了显式状态：每条连接一个 `struct conn`，里面是 fd、已缓冲长度、已发送偏移和「对端已关」标记。这样即使一次 `write` 只发出一半，剩余部分也不会丢。

```c
/* lab1c11_epoll.c：单线程、边沿触发、非阻塞的 echo 服务器 */
#ifndef _GNU_SOURCE
#define _GNU_SOURCE
#endif
#include <arpa/inet.h>
#include <errno.h>
#include <fcntl.h>
#include <netinet/in.h>
#include <signal.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/epoll.h>
#include <sys/socket.h>
#include <unistd.h>

#define MAX_EVENTS 64
#define OUT_SIZE   (64 * 1024)

struct conn {
    int fd;
    int in_epoll;                    /* 1 表示已 ADD 进 epoll */
    int peer_closed;                 /* 读到 EOF，但还有数据没写完 */
    size_t out_len, out_off;
    char out[OUT_SIZE];
};

static void close_conn(int ep, struct conn *c)
{
    epoll_ctl(ep, EPOLL_CTL_DEL, c->fd, NULL);
    close(c->fd);
    fprintf(stderr, "close fd=%d\n", c->fd);
    free(c);
}

/* 把连接关心的事件写回 epoll：始终读，有积压才写 */
static int arm(int ep, struct conn *c)
{
    struct epoll_event ev;
    memset(&ev, 0, sizeof ev);
    ev.events = EPOLLIN | EPOLLRDHUP | EPOLLET;
    if (c->out_off < c->out_len)
        ev.events |= EPOLLOUT;
    ev.data.ptr = c;
    if (!c->in_epoll) {              /* 新连接第一次进来要 ADD，不是 MOD */
        if (epoll_ctl(ep, EPOLL_CTL_ADD, c->fd, &ev) == -1)
            return -1;
        c->in_epoll = 1;
        return 0;
    }
    return epoll_ctl(ep, EPOLL_CTL_MOD, c->fd, &ev);
}

static void handle_read(int ep, struct conn *c)
{
    char buf[8192];
    for (;;) {                       /* 边沿触发：读到 EAGAIN 才算干净 */
        ssize_t n = read(c->fd, buf, sizeof buf);
        if (n > 0) {
            if (c->out_len + (size_t)n > OUT_SIZE) {
                close_conn(ep, c);   /* 慢客户端：积压超过上限就断开 */
                return;
            }
            memcpy(c->out + c->out_len, buf, (size_t)n);
            c->out_len += (size_t)n;
            fprintf(stderr, "read fd=%d n=%zd\n", c->fd, n);
        } else if (n == 0) {
            fprintf(stderr, "eof fd=%d\n", c->fd);
            c->peer_closed = 1;
            break;
        } else if (errno == EINTR) {
            continue;
        } else if (errno == EAGAIN || errno == EWOULDBLOCK) {
            break;
        } else {
            close_conn(ep, c);
            return;
        }
    }
    if (arm(ep, c) == -1)
        close_conn(ep, c);
    else if (c->peer_closed && c->out_off == c->out_len)
        close_conn(ep, c);           /* 没有待写数据，可以关了 */
}

static void handle_write(int ep, struct conn *c)
{
    while (c->out_off < c->out_len) {
        ssize_t n = write(c->fd, c->out + c->out_off, c->out_len - c->out_off);
        if (n > 0) {
            c->out_off += (size_t)n;
            fprintf(stderr, "write fd=%d n=%zd\n", c->fd, n);
        } else if (n == -1 && errno == EINTR) {
            continue;
        } else if (n == -1 && (errno == EAGAIN || errno == EWOULDBLOCK)) {
            break;
        } else {
            close_conn(ep, c);
            return;
        }
    }
    if (c->out_off == c->out_len) {  /* 写空：复位，重新只关心可读 */
        c->out_off = c->out_len = 0;
        if (c->peer_closed) {
            close_conn(ep, c);
            return;
        }
    }
    if (arm(ep, c) == -1)
        close_conn(ep, c);
}

int main(int argc, char **argv)
{
    if (argc != 2) {
        fprintf(stderr, "usage: %s <port>\n", argv[0]);
        return 2;
    }
    int port = atoi(argv[1]);
    if (port <= 0 || port > 65535) {
        fprintf(stderr, "bad port\n");
        return 2;
    }

    signal(SIGPIPE, SIG_IGN);

    int lfd = socket(AF_INET, SOCK_STREAM | SOCK_NONBLOCK | SOCK_CLOEXEC, 0);
    if (lfd == -1) {
        perror("socket");
        return 1;
    }
    int on = 1;
    setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof on);

    struct sockaddr_in addr;
    memset(&addr, 0, sizeof addr);
    addr.sin_family = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);
    addr.sin_port = htons((uint16_t)port);
    if (bind(lfd, (struct sockaddr *)&addr, sizeof addr) == -1) {
        perror("bind");
        return 1;
    }
    if (listen(lfd, 128) == -1) {
        perror("listen");
        return 1;
    }

    int ep = epoll_create1(EPOLL_CLOEXEC);
    if (ep == -1) {
        perror("epoll_create1");
        return 1;
    }

    struct epoll_event ev;
    memset(&ev, 0, sizeof ev);
    ev.events = EPOLLIN | EPOLLET;
    ev.data.ptr = NULL;              /* NULL 表示监听 fd */
    if (epoll_ctl(ep, EPOLL_CTL_ADD, lfd, &ev) == -1) {
        perror("epoll_ctl");
        return 1;
    }

    struct epoll_event evs[MAX_EVENTS];
    printf("epoll echo server on port %d\n", port);

    for (;;) {
        int n = epoll_wait(ep, evs, MAX_EVENTS, -1);
        if (n == -1) {
            if (errno == EINTR)
                continue;
            perror("epoll_wait");
            break;
        }
        for (int i = 0; i < n; i++) {
            struct conn *c = evs[i].data.ptr;
            if (c == NULL) {         /* 监听 fd：一次把新连接全部取完 */
                for (;;) {
                    int fd = accept4(lfd, NULL, NULL, SOCK_NONBLOCK | SOCK_CLOEXEC);
                    if (fd == -1) {
                        if (errno == EAGAIN || errno == EWOULDBLOCK)
                            break;
                        if (errno == EINTR)
                            continue;
                        if (errno == EMFILE || errno == ENFILE) {
                            fprintf(stderr, "fd exhausted\n");
                            break;
                        }
                        perror("accept4");
                        break;
                    }
                    struct conn *nc = calloc(1, sizeof *nc);
                    if (nc == NULL) {
                        close(fd);
                        continue;
                    }
                    nc->fd = fd;
                    fprintf(stderr, "accept fd=%d\n", fd);
                    if (arm(ep, nc) == -1) {
                        close(fd);
                        free(nc);
                    }
                }
                continue;
            }

            uint32_t e = evs[i].events;
            if (e & EPOLLERR) {
                close_conn(ep, c);
                continue;
            }
            if (e & EPOLLOUT)
                handle_write(ep, c);
            else if (e & (EPOLLIN | EPOLLRDHUP | EPOLLHUP))
                handle_read(ep, c);
        }
    }
    close(ep);
    close(lfd);
    return 0;
}
```

### 跑起来看现场

先编译、启动（实测；Ubuntu 24.04.5 aarch64，GCC 13.3.0）：

```text
$ gcc -O2 -Wall -Wextra -o lab1c11_epoll lab1c11_epoll.c
$ ./lab1c11_epoll 8080
listening port=8080 lfd=3 ep=4
```

再起一个客户端：发 12 字节，先不读，停 1 秒让 `ss` 拍一张现场：

```text
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
LISTEN 0      128          0.0.0.0:8080       0.0.0.0:*     users:(("lab1c11_epoll",pid=<pid>,fd=3))
ESTAB  0      0          127.0.0.1:8080     127.0.0.1:33050 users:(("lab1c11_epoll",pid=<pid>,fd=5))
ESTAB  12     0          127.0.0.1:33050    127.0.0.1:8080  users:(("python3",pid=<pid>,fd=3))
```

服务端方向的两个数字都是 0：echo 已经写完，接收缓冲也读空了。客户端那一行 `Recv-Q 12` 正是回显的 12 字节——内核已经替它收下，应用还没 `read`。这就是 1.11.7 里「`Recv-Q` 是应用没读走的字节」在一条活连接上的样子。

服务端的 stderr 是这条连接的完整轨迹：

```text
accept fd=5
read fd=5 n=12
write fd=5 n=12
eof fd=5
close fd=5
```

`read` 一次拿 12 字节，`write` 一次发回 12 字节；客户端读走并退出后，服务端读到 EOF，确认输出缓冲已空才关。若在 `peer_closed` 为真时立刻 `close`，尚未发完的回显会被 RST 截断。

关键行只有四处：

- `accept4(..., SOCK_NONBLOCK | SOCK_CLOEXEC)`：新连接一出生就非阻塞，且 `exec` 时不泄漏 fd。
- 监听 fd 也用 `EPOLLET`：必须在一次事件里 `accept4` 到 `EAGAIN`，否则新连接留在队列里等不到下一次通知。
- `handle_read` 循环到 `EAGAIN`：这是 ET 的全部语义，读一半就返回等于主动丢事件。
- 写侧自己缓冲：`EAGAIN` 时保留 `out_off`，把 `EPOLLOUT` 加进关注集，下次接着发。

### 一行写错会怎样

这份代码的第一版在 `arm()` 里对新连接也调 `EPOLL_CTL_MOD`，而新 fd 根本不在 epoll 里。`epoll_ctl` 返回 `ENOENT`，`arm` 失败，代码立刻 `close(fd)`；客户端那边看到的是：

```text
ConnectionResetError: [Errno 104] Connection reset by peer
```

`ss` 里连接一闪而过，stderr 只有 `accept fd=5`、没有 `read`。这就是 `in_epoll` 字段的由来：第一次进 epoll 必须 `ADD`，之后才是 `MOD`。事件循环的 bug 大多长这样——不是逻辑算错，而是「注册」和「修改」用混了。

`OUT_SIZE` 是 64 KiB，超过就断开慢客户端，这是最朴素的背压（队列满时让生产者等，而不是无限缓冲）；没有超时才是真正的缺口：空闲连接会一直占着内存，生产实现要给每条连接记最后活跃时间，用 `timerfd` 或时间轮定期清理。

::: errata 关于 epoll 代码的四个误解
1. **「注册监听 fd 后就不用管了」**——ET 下必须每次事件把 `accept4` 做到 `EAGAIN`，否则连接堆在队列里。
2. **「`read` 返回正数就说明读完了」**——只说明这次到了这么多；ET 要求继续读到 `EAGAIN`。
3. **「`EPOLLOUT` 一直开着最省事」**——可写是常态，一直注册会让 `epoll_wait` 每次都返回，白烧 CPU；有积压才加。
4. **「对端关闭就立刻 `close`」**——还有未发数据时会发 RST，客户端收到的是截断或 `ECONNRESET`。
:::

### 1.11.12 小结

① 单线程管多连接靠「非阻塞 + ET + 读到 `EAGAIN` + 用户态写缓冲」四件套；② 新连接进 epoll 用 `ADD`，之后才是 `MOD`，弄混会让连接刚建立就被关；③ 现场证据是 `ss` 的 `Recv-Q` 与服务端 stderr 的 `accept/read/write/eof/close` 序列。如果只记住一件事：**ET 不是「通知更少」，而是「你必须一次把活干完」。**

## 1.11.13 完整程序：手写 HTTP 客户端 {#sec-1.11.13}

这一节回答：`curl` 一行就完成的事，换成一个 C 程序到底要自己处理哪几段字节？为什么一次 `read` 常常读不全整个响应？

::: preview 先抓住一件事
客户端只做四件事：拼请求、把它发完、收到能判边界、按边界截断。请求侧要处理短写与 `EINTR`；响应侧不能假设一次 `read` 拿到全部——头部按 `\r\n\r\n` 找，正文按 `Content-Length` 截，没有长度才靠 EOF。下面这份 `lab1c11_httpget.c` 在 Ubuntu 24.04.5 上真跑过，每次 `read` 的字节数都打在 stderr 上。

```text
eof total=216
```

第一次 `read` 拿到 185 字节，正好是状态行加全部头部；第二次 31 字节才是正文；第三次返回 0，表示对端关闭。完整响应由三次 `read` 拼起来，`curl` 看起来「一次就完」，只是它内部做了同样的事，没有打印。

为什么服务器不一次发完？`python3 -m http.server` 在写头之前要先查 MIME 与文件元数据，头部与正文也是两次 `write`：先把状态行和头部刷出去，再分块拷贝文件内容。TCP 只保证字节顺序，不保证「一次写对应一次读」。所以客户端必须把「读」写成循环，直到能判断边界为止。

::: def 定义 1.11.13 · 响应边界的三级判据 {#def-1.11.13}
HTTP 响应的正文长度按优先级判定：① 头部有 `Content-Length`，就按这个字节数截断；② 有 `Transfer-Encoding: chunked`，就按块解码，直到长度为 0 的块；③ 两者都没有，则以连接关闭（`read` 返回 0）为界。头部本身永远以第一个 `\r\n\r\n` 结束。
:::

顺序不能反。先按 `Content-Length` 截，可以不管连接是否还开着，也支持 keep-alive；先等 EOF，遇到 keep-alive 的连接就会一直等到超时。

下面是完整程序，编译命令是 `gcc -O2 -Wall -Wextra -o lab1c11_httpget lab1c11_httpget.c`。

```c
/* lab1c11_httpget.c：手写 HTTP/1.1 GET 客户端
   gcc -O2 -Wall -Wextra -o lab1c11_httpget lab1c11_httpget.c */
#ifndef _GNU_SOURCE
#define _GNU_SOURCE
#endif
#include <arpa/inet.h>
#include <errno.h>
#include <netdb.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <strings.h>
#include <sys/socket.h>
#include <unistd.h>

#define RESP_MAX (1 << 20)          /* 演示用：响应上限 1 MiB */

static int send_all(int fd, const char *p, size_t n)
{
    while (n > 0) {
        ssize_t w = write(fd, p, n);        /* socket 上 write == send */
        if (w > 0) { p += w; n -= (size_t)w; }
        else if (w == -1 && errno == EINTR) continue;
        else return -1;
    }
    return 0;
}

/* 读到 EOF 或缓冲满；返回字节数，-1 出错。每段都报到 stderr。 */
static ssize_t read_all(int fd, char *buf, size_t cap)
{
    size_t used = 0;
    while (used < cap - 1) {
        ssize_t n = read(fd, buf + used, cap - 1 - used);
        if (n > 0) {
            used += (size_t)n;
            fprintf(stderr, "read n=%zd total=%zu\n", n, used);
        } else if (n == 0) {
            fprintf(stderr, "eof total=%zu\n", used);
            break;
        } else if (errno == EINTR) {
            continue;
        } else {
            perror("read");
            return -1;
        }
    }
    buf[used] = '\0';
    return (ssize_t)used;
}

int main(int argc, char **argv)
{
    if (argc < 2 || argc > 4) {
        fprintf(stderr, "usage: %s <host> [port] [path]\n", argv[0]);
        return 2;
    }
    const char *host = argv[1];
    const char *port = argc > 2 ? argv[2] : "80";
    const char *path = argc > 3 ? argv[3] : "/";

    struct addrinfo hints, *res = NULL;
    memset(&hints, 0, sizeof hints);
    hints.ai_family   = AF_UNSPEC;      /* 候选地址全给我，先试通哪个算哪个 */
    hints.ai_socktype = SOCK_STREAM;

    int rc = getaddrinfo(host, port, &hints, &res);
    if (rc != 0) {
        fprintf(stderr, "getaddrinfo: %s\n", gai_strerror(rc));
        return 1;
    }

    int fd = -1;
    for (struct addrinfo *p = res; p != NULL; p = p->ai_next) {
        fd = socket(p->ai_family, p->ai_socktype, p->ai_protocol);
        if (fd == -1)
            continue;
        if (connect(fd, p->ai_addr, p->ai_addrlen) == 0)
            break;                          /* 成功 */
        close(fd);
        fd = -1;                            /* 换下一个候选地址 */
    }
    freeaddrinfo(res);
    if (fd == -1) {
        perror("connect");
        return 1;
    }

    char req[1024];
    int n = snprintf(req, sizeof req,
                     "GET %s HTTP/1.1\r\nHost: %s:%s\r\nUser-Agent: lab1c11\r\n"
                     "Accept: */*\r\nConnection: close\r\n\r\n", path, host, port);
    if (n <= 0 || (size_t)n >= sizeof req) {
        close(fd);
        return 2;
    }
    if (send_all(fd, req, (size_t)n) == -1) {
        perror("send");
        close(fd);
        return 1;
    }

    char *resp = malloc(RESP_MAX);
    if (resp == NULL) {
        close(fd);
        return 1;
    }
    ssize_t total = read_all(fd, resp, RESP_MAX);
    close(fd);
    if (total <= 0) {
        fprintf(stderr, "no response\n");
        free(resp);
        return 1;
    }

    char *head_end = strstr(resp, "\r\n\r\n");
    if (head_end == NULL) {
        fprintf(stderr, "malformed: no header end (%zd bytes)\n", total);
        free(resp);
        return 3;
    }
    *head_end = '\0';                       /* 头部单独成串 */
    char *body = head_end + 4;
    size_t have = (size_t)total - (size_t)(body - resp);
    size_t body_len = have;

    printf("--- status line ---\n%s\n", strtok(resp, "\r\n"));
    printf("--- headers ---\n");
    for (char *line = strtok(NULL, "\r\n"); line != NULL; line = strtok(NULL, "\r\n")) {
        printf("%s\n", line);
        if (strncasecmp(line, "Content-Length:", 15) == 0) {
            long cl = strtol(line + 15, NULL, 10);
            if (cl >= 0)
                body_len = (size_t)cl;      /* 有长度就以它为准 */
        }
    }
    if (body_len > have) {
        fprintf(stderr, "short body: want %zu have %zu\n", body_len, have);
        free(resp);
        return 3;                           /* 声明比实际多：响应被截断 */
    }
    printf("--- body (%zu of %zu bytes read) ---\n", body_len, have);
    fwrite(body, 1, body_len, stdout);
    if (body_len == 0 || body[body_len - 1] != '\n')
        putchar('\n');

    free(resp);
    return 0;
}
```

### 关键只有四处

- `getaddrinfo` 之后逐个 `connect`：`AF_UNSPEC` 可能返回多个候选，任一个成功就停，失败的 fd 立刻关掉。这就是 1.11.8 说的「协议无关客户端」的落地形态。
- `send_all` 循环到 `n == 0`：socket 的 `write` 可能只写一部分，`EINTR` 要重试，其他错误直接失败。本机这条请求只有 93 字节，一次就写完；换到拥塞链路就不一定。
- `read_all` 读到 EOF 或缓冲满：它不判断边界，只把字节搬回来，每段往 stderr 打一行。边界判断留给后面的 `strstr` 与 `Content-Length`。
- `strtok` 只是图省事：它把分隔符改写成 `\0`，会破坏原缓冲区。真实实现应改成不修改数据的扫描，因为同一个缓冲区后面还要取 `body`。

请求那 93 字节是 `GET / HTTP/1.1`、`Host`、`User-Agent`、`Accept`、`Connection: close` 与空行的总和。`Connection: close` 明确告诉服务器「回完就关」，这样即使响应没有长度字段，`read_all` 也能靠 EOF 停下来；代价是每个请求都要新建连接。

### 退出码也是接口

一个能放进脚本的客户端，失败必须能区分。这份程序的退出码是（逐项实测）：

| 退出码 | 含义 | 触发方式 | 实测输出 |
|--:|:--|:--|:--|
| 0 | 成功 | 正常 200 | `ok=0` |
| 1 | 解析、连接或读写失败 | 端口没人监听；域名不存在 | `connect: Connection refused`；`getaddrinfo: Name or service not known` |
| 2 | 用法错误 | 参数个数不对 | `usage: ...` |
| 3 | 响应不完整 | 头部声明长度大于实际收到 | `short body: want 100 have 10` |

第 3 种最容易被忽略。服务器写 `Content-Length: 100`，实际只发 10 字节就关闭；`read_all` 会正常读到 EOF 并返回 10，如果程序不比对长度，就会把残缺正文当成功。用一个故意这么发的小服务器验证，退出码是 3，stderr 是 `short body: want 100 have 10`。

::: errata 关于 HTTP 客户端的三个误解
1. **「`read` 一次就是一条响应」**——本机实测第一次只拿到 185 字节的头部，正文在第二次。任何「读一次就解析」的代码跨网段都会碎。
2. **「响应一定有 `Content-Length`」**——HTTP/1.0 与 `Connection: close` 的响应常常没有，chunked 响应也没有。没有长度时只能读到 EOF，这正是本程序必须等 `read` 返回 0 的原因。
3. **「连接关闭等于出错」**——`Connection: close` 是正常收尾。把 EOF 当错误，会把每一条 HTTP/1.0 响应都判成失败。
:::

这份客户端还有两个明确缺口：不解析 chunked，只把原始块打印出来；也没有超时，对端不发数据会一直阻塞在 `read`。生产客户端要给 `connect` 与 `read` 设置截止时间，并在 `EINTR` 之外处理 `EAGAIN`。

### 1.11.13 小结

① 请求侧的关键是「发完」：`send_all` 处理短写与 `EINTR`；② 响应侧的关键是「判边界」：先找 `\r\n\r\n`，再按 `Content-Length`、chunked、EOF 的顺序截断；③ 一次 `read` 只是字节流的一段，实测 185 + 31 + 0 才是完整响应。如果只记住一件事：**客户端的所有正确性，都建立在「读不满是常态」这个前提上。**

## 1.11.14 完整程序：`getaddrinfo` 标志浏览器 {#sec-1.11.14}

这一节回答：同一个域名，只改 `ai_flags`，为什么返回的地址数量、顺序、地址族都会变？每个开关到底改了解析器的哪一步？

::: preview 先抓住一件事
`getaddrinfo` 的输入只有三样：主机名、服务名、`hints`。`ai_flags` 不是「偏好」，而是硬开关：`AI_NUMERICHOST` 直接禁止 DNS，`AI_PASSIVE` 让空主机名变成通配地址，`AI_V4MAPPED` 把 IPv4 地址包装成 IPv6 形式。把这些开关的结果打出来对照，比背表有用。
:::

编译成 `./lab1c11_gai`（`gcc -O2 -Wall -Wextra -o lab1c11_gai lab1c11_gai.c`）后，先在虚拟机上跑三组（实测）：

```text
[1] family=AF_INET6 socktype=1 proto=6 addr=::      port=8080 canon=-
$ ./lab1c11_gai -n example.com 80

$ ./lab1c11_gai -c example.com https
```

第一组是服务器写法：主机名传 `-`（程序转成 `NULL`）再加 `AI_PASSIVE`，得到 `0.0.0.0` 与 `::` 两个通配地址，正好对应「监听所有网卡」。第二组是客户端写法：`-n` 打开 `AI_NUMERICHOST`，解析器看到 `example.com` 不是数字地址，直接返回 `EAI_NONAME`，一次 DNS 都没发。第三组加了 `AI_CANONNAME`，只有链表第一项带规范名，后面几项是 `-`。

`-` 这个约定是本程序自己的，不是 `getaddrinfo` 的语法：`node` 传 `NULL` 才表示「本机」。`AI_PASSIVE` 只在这种情况下生效；主机名照常给，单独打开它什么都不会变。

::: def 定义 1.11.14 · 候选地址链表 {#def-1.11.14}
`getaddrinfo` 返回的是一条 `struct addrinfo` 链表，每一项是一组「地址族 + 套接字类型 + 协议 + 地址」的完整组合。调用方必须逐项尝试：客户端依次 `connect`，服务器依次 `bind`；用完调用一次 `freeaddrinfo` 释放整条链，不能只 `free` 头节点。
:::

```c
/* lab1c11_gai.c：把 getaddrinfo 的 flags 效果打印出来
   gcc -O2 -Wall -Wextra -o lab1c11_gai lab1c11_gai.c */
#ifndef _GNU_SOURCE
#define _GNU_SOURCE
#endif
#include <arpa/inet.h>
#include <errno.h>
#include <netdb.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/socket.h>
#include <unistd.h>

static void usage(const char *prog)
{
    fprintf(stderr,
        "usage: %s [-p] [-n] [-4|-6] [-c] [-a] [-m] <host|-> <service>\n"
        "  -p  AI_PASSIVE       host 为 - 时返回通配地址\n"
        "  -n  AI_NUMERICHOST|AI_NUMERICSERV  禁止 DNS 与服务名查询\n"
        "  -4  AF_INET          -6  AF_INET6\n"
        "  -c  AI_CANONNAME     返回规范主机名\n"
        "  -a  AI_ADDRCONFIG    只返回本机已配置的地址族\n"
        "  -m  AI_V4MAPPED|AI_ALL  只查 IPv6 时把 IPv4 映射进来\n", prog);
}

int main(int argc, char **argv)
{
    struct addrinfo hints;
    memset(&hints, 0, sizeof hints);
    hints.ai_family   = AF_UNSPEC;
    hints.ai_socktype = SOCK_STREAM;

    int opt;
    while ((opt = getopt(argc, argv, "pn46cam")) != -1) {
        switch (opt) {
        case 'p': hints.ai_flags |= AI_PASSIVE; break;
        case 'n': hints.ai_flags |= AI_NUMERICHOST | AI_NUMERICSERV; break;
        case '4': hints.ai_family = AF_INET; break;
        case '6': hints.ai_family = AF_INET6; break;
        case 'c': hints.ai_flags |= AI_CANONNAME; break;
        case 'a': hints.ai_flags |= AI_ADDRCONFIG; break;
        case 'm': hints.ai_flags |= AI_V4MAPPED | AI_ALL; break;
        default: usage(argv[0]); return 2;
        }
    }
    if (argc - optind != 2) {
        usage(argv[0]);
        return 2;
    }

    const char *host = strcmp(argv[optind], "-") == 0 ? NULL : argv[optind];
    const char *serv = argv[optind + 1];

    struct addrinfo *res = NULL;
    int rc = getaddrinfo(host, serv, &hints, &res);
    if (rc != 0) {
        /* EAI_SYSTEM 时真正的原因在 errno，gai_strerror 只给一句话 */
        fprintf(stderr, "getaddrinfo: %s (EAI=%d)%s\n", gai_strerror(rc), rc,
                rc == EAI_SYSTEM ? strerror(errno) : "");
        return 1;
    }

    printf("hints: family=%s flags=0x%x\n",
           hints.ai_family == AF_INET ? "AF_INET" :
           hints.ai_family == AF_INET6 ? "AF_INET6" : "AF_UNSPEC",
           hints.ai_flags);

    int i = 0;
    for (struct addrinfo *p = res; p != NULL; p = p->ai_next) {
        char hbuf[NI_MAXHOST] = "?", sbuf[NI_MAXSERV] = "?";
        if (getnameinfo(p->ai_addr, p->ai_addrlen, hbuf, sizeof hbuf,
                        sbuf, sizeof sbuf,
                        NI_NUMERICHOST | NI_NUMERICSERV) != 0) {
            strcpy(hbuf, "!");
        }
        printf("[%d] family=%-7s socktype=%d proto=%d addr=%s port=%s canon=%s\n",
               i++,
               p->ai_family == AF_INET ? "AF_INET" :
               p->ai_family == AF_INET6 ? "AF_INET6" : "other",
               p->ai_socktype, p->ai_protocol, hbuf, sbuf,
               p->ai_canonname ? p->ai_canonname : "-");
    }
    freeaddrinfo(res);                    /* 必须释放整条链表 */
    return 0;
}
```

`::ffff:104.20.23.154` 是 IPv4 映射地址：128 位的 IPv6 地址后 32 位装 IPv4。这样只写 IPv6 的代码也能连 IPv4 对端。`AI_V4MAPPED` 只在 `ai_family == AF_INET6` 时有意义；`AF_UNSPEC` 下打开它，输出看不出变化。

| 开关 | 作用 | 实测证据 |
|:--|:--|:--|
| `AI_PASSIVE`（0x1） | 主机名为空时返回通配地址 | `0.0.0.0` 与 `::` |
| `AI_CANONNAME`（0x2） | 第一项填规范主机名 | `canon=example.com`，第二项 `canon=-` |
| `AI_NUMERICHOST`（0x4） | 禁止 DNS 查询 | `-n example.com` → `EAI=-2` |
| `AI_NUMERICSERV`（0x400） | 服务名必须是数字 | `-n 1.1.1.1 https` → `EAI=-2` |
| `AI_ADDRCONFIG`（0x20） | 只回本机配置了地址的族 | 本机有全局 IPv6，输出与默认相同 |
| `AI_V4MAPPED`（0x8）+`AI_ALL`（0x10） | 无 AAAA 时用映射地址补齐 | `::ffff:104.20.23.154` |

`AI_ADDRCONFIG` 这一行要小心解释：它只在本机「没有某一族的全局地址」时才过滤。本书虚拟机有全局 IPv6 地址，这条解析路径又只拿到 A 记录，所以开关前后输出一样；这不代表开关没生效。

::: errata 关于 `EAI_*` 的四个易错点
1. **「`-2` 就是域名不存在」**——本机 `-6 example.com` 得到的是 `-5`（`EAI_NODATA`），不是 `-2`。「有 A 无 AAAA」在不同 glibc 版本下的归类不同，判断「域名不存在」不能只看 `EAI_NONAME`。
2. **「`EAI_NODATA` 说明域名没有 AAAA」**——本机 DNS 只回 A 记录：`dig +short AAAA one.one.one.one @1.1.1.1` 有结果，而走本地解析器的 `getaddrinfo` 拿不到。`-5` 只说明「这条路没拿到」，不是域名的属性。
3. **「flags 的数值可以硬编码」**——`0x2`、`0x404` 是 glibc 的值，别的 libc 不一定相同。代码里只写宏，打印时再显示数值。
4. **「`AI_CANONNAME` 每项都有规范名」**——只有第一项有，后续项是 `NULL`；遍历时不做判空会崩。
:::

`EAI_AGAIN` 属于另一类错误：解析器临时失败（上游超时、SERVFAIL），语义是「等会儿再试」，不是「这个名字不存在」。本机没有稳定复现条件，这一条未实测；正确处理是有限次退避重试，不能把它和 `EAI_NONAME` 一起报成「域名错误」。

### 1.11.14 小结

① `hints` 只有三个输入字段起作用：`ai_family`、`ai_socktype`、`ai_flags`；② `AI_PASSIVE` 改变「空主机名」的含义，`AI_NUMERICHOST` 直接短路 DNS，`AI_V4MAPPED` 只在 `AF_INET6` 下补齐；③ 返回的是一条链表，客户端逐项 `connect`、服务器逐项 `bind`，最后 `freeaddrinfo` 整条释放。如果只记住一件事：**flag 改的是解析器的行为，不是网络的属性，所以同一个域名可以有两种完全不同的答案。**

## 1.11.15 实验一：用 ss、tcpdump、strace 看连接生命周期 {#sec-1.11.15}

这一节回答：一条连接从 SYN 到 TIME_WAIT，不读内核源码、也不抓包，只用普通用户能跑的命令，能看到多少？

::: preview 先抓住一件事
`ss` 看状态与队列，`strace` 看进程发了哪些系统调用，`tcpdump` 看线上字节，三者按「内核视图 → 系统调用视图 → 报文视图」由粗到细。本机没有 `CAP_NET_RAW`，`tcpdump` 抓不了包，这一段只给命令与判读，不冒充实测。
:::

环境：Ubuntu 24.04.5 aarch64，普通用户，`sudo` 不可用。对端用 `python3 -m http.server 8080`，它监听时调 `listen(5)`，正好用来读 backlog 列。

**第一步：发起一次真实请求。** 另一个终端跑 `curl -sv http://127.0.0.1:8080/`，`>` 是客户端发出的字节，`<` 是服务端回的（实测）：

```text
> GET / HTTP/1.1
> Host: 127.0.0.1:8080
> User-Agent: curl/8.5.0
> Accept: */*
>
< HTTP/1.0 200 OK
< Server: SimpleHTTP/0.6 Python/3.12.3
< Content-Length: 31
<
* Closing connection
```

此刻 `ss -lnt '( sport = :8080 )'` 显示：

```text
State  Recv-Q Send-Q Local Address:Port Peer Address:Port
LISTEN 0      5      127.0.0.1:8080    0.0.0.0:*
```

监听行 `Recv-Q` 是 0，`Send-Q` 是 5。**这两个列在 LISTEN 行与 ESTAB 行含义完全不同**：LISTEN 行 `Recv-Q` 是已完成握手、还没被 `accept` 取走的连接数；`Send-Q` 是 `listen` 的 backlog 上限。Python 写的是 `listen(5)`，所以是 5；写 128 就是 128（1.11.16 会看到被 `somaxconn` 截断的情况）。

**第二步：让数据停在接收队列里。** 起一个只 `accept`、不 `read` 的服务器，再让客户端发 5000 字节后不动：

```bash
# 终端 1：收下连接但不读
$ python3 - <<'PY'
import socket, time
s = socket.socket(); s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(("127.0.0.1", 9000)); s.listen(5)
c, _ = s.accept()
time.sleep(30)
PY
# 终端 2：发 5000 字节后不动
$ python3 - <<'PY'
import socket, time
c = socket.create_connection(("127.0.0.1", 9000))
c.sendall(b"A" * 5000)
time.sleep(30)
PY
```

终端 3 看（实测）：

```text
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port
ESTAB  5000   0      127.0.0.1:9000     127.0.0.1:44904
ESTAB  0      0      127.0.0.1:44904    127.0.0.1:9000
```

服务端这行 `Recv-Q 5000`：内核已替应用收下 5000 字节，应用一次都没 `read`。客户端 `Recv-Q` 是 0，因为它只发不收。**同一条连接两端各有一份 socket，各有一套队列**，看哪一端就查哪一端的四元组。

**第三步：看关闭过程。** 让客户端发完就 `close`，服务器仍不关：

```bash
$ python3 -c 'import socket; c=socket.create_connection(("127.0.0.1",9000)); c.sendall(b"A"*5000); c.close()'
```

`ss -tan '( sport = :9000 or dport = :9000 )'` 实测：

```text
State      Recv-Q Send-Q Local Address:Port  Peer Address:Port
LISTEN     0      5          127.0.0.1:9000       0.0.0.0:*
CLOSE-WAIT 5001   0          127.0.0.1:9000     127.0.0.1:53562
FIN-WAIT-2 0      0          127.0.0.1:53562    127.0.0.1:9000
```

客户端发了 FIN，进入 `FIN-WAIT-2`；服务端内核回了 ACK，但应用没 `close`，停在 `CLOSE-WAIT`，`Recv-Q` 是 5001——5000 字节数据加 1 字节 FIN 标记。**大量 `CLOSE-WAIT` 只有一个原因：应用忘了 `close`。**

**第四步：用 strace 看系统调用。** 对客户端抓（实测）：

```text
$ strace -e trace=connect,write,read,close -s 48 ./lab1c11_httpget 127.0.0.1 8080 /
connect(3, {sa_family=AF_INET, sin_port=htons(8080), sin_addr=inet_addr("127.0.0.1")}, 16) = 0
write(3, "GET / HTTP/1.1\r\nHost: 127.0.0.1:8080\r\nUser-Agent"..., 93) = 93
read(3, "HTTP/1.0 200 OK\r\nServer: SimpleHTTP/0.6 Python/3"..., 1048575) = 185
read(3, "hello from lab1c11 http server\n", 1048390) = 31
read(3, "", 1048359)                    = 0
close(3)                                = 0
```

一次 `write` 93 字节把请求发完，三次 `read` 分别是 185、31、0。`strace` 不解释协议，只告诉你「进程向内核要了什么」；把三次 `read` 与 1.11.13 的边界判据对上，就知道客户端为什么必须循环读。

**第五步：TIME_WAIT 与 `SO_REUSEADDR`。** 服务端先 `close`，它就进 `TIME_WAIT`。下面用 9010 上的最小服务端复现（端口换掉，避免和第 1 步的 8080 混在一起），实测：

```text
State     Recv-Q Send-Q Local Address:Port Peer Address:Port
TIME-WAIT 0      0      127.0.0.1:9010    127.0.0.1:36936
```

立刻用同一端口再 `bind`，并且**不**设 `SO_REUSEADDR`，得到 `bind: Address already in use`，退出码 1；把 `setsockopt(..., SO_REUSEADDR, ...)` 加回去就成功（拿 1.11.4 的 echo 服务器，注释掉那一行再编译即可复现）。`TIME_WAIT` 占的是「四元组」而不是端口本身，要等 2MSL 才消失；`SO_REUSEADDR` 允许新连接复用端口，但不会让两条完全相同的四元组并存。要数总量就加状态过滤：`ss -tan state time-wait '( sport = :9010 )'`；去掉过滤条件，列出的就是全机所有等待中的连接。

**第六步：抓包（本机未实测）。** 需要 `CAP_NET_RAW`，普通用户执行会得到 `You don't have permission to perform this capture on that device`。有权限时命令是：

```bash
$ sudo tcpdump -i lo -nn -c 20 'tcp port 8080'
```

判读只看四个标记：`[S]` 是 SYN，`[S.]` 是 SYN+ACK，`[.]` 是纯 ACK，`[F.]` 是 FIN+ACK。`-nn` 禁止反解，避免 DNS 干扰时序；`-i lo` 抓回环，换成实际网卡才看得到跨机流量。正常的建连是 `[S] → [S.] → [.]`；如果在 `[S]` 之后直接看到 `[R]`，说明对端没有监听端口，内核替它回了 RST，这正是 `Connection refused` 的报文形态。这一段的具体输出不做展示。

::: errata 关于连接观测的三个误解
1. **「`ss` 的 `Recv-Q` 永远是字节数」**——LISTEN 行是「排队等 `accept` 的连接数」，ESTAB 行才是未读字节数。同一个列名，两种量纲。
2. **「`TIME_WAIT` 是服务端的 bug」**——它是主动关闭方的正常状态，保证最后一个 ACK 丢失时还能重传。数量大说明短连接多，不说明泄漏。
3. **「抓不到包说明没有流量」**——没有 `CAP_NET_RAW` 时 `tcpdump` 直接报权限错误，和有没有流量无关。先看命令的退出状态，再看包。
:::

### 1.11.15 小结

① `ss` 给状态与队列：LISTEN 行看 backlog，ESTAB 行看未读字节，CLOSE-WAIT 看应用是否忘了 `close`；② `strace` 给系统调用：一次 `write` 93 字节、三次 `read` 185/31/0，与客户端循环读一一对应；③ `TIME_WAIT` 属于主动关闭方，`SO_REUSEADDR` 解决重启失败，抓包要额外权限。如果只记住一件事：**先问「我在看哪一端的哪个队列」，再看数字。**

## 1.11.16 实验二：backlog 溢出与 epoll 的观测方式 {#sec-1.11.16}

这一节回答：`listen` 的 backlog 到底限住了什么？队列满了客户端会看到什么？epoll 服务器在 500 条空闲连接下，凭什么几乎不花 CPU？

::: preview 先抓住一件事
backlog 限的是「已完成握手、等待 accept」的队列长度，内核还会用 `somaxconn` 再截一刀；队列满时新连接先超时，`nstat` 的 `ListenOverflows` 会涨。epoll 的代价随「发生事件的连接数」增长，不随「已注册的连接数」增长，这是它和 `poll` 的分水岭。
:::

**实验 A：看清 backlog 的上限。** 先读系统上限（实测）：

```bash
$ cat /proc/sys/net/core/somaxconn
4096
```

再让 Python 用 `listen(5000)` 监听，然后看 `ss`：

```bash
$ python3 -c 'import socket,time; s=socket.socket(); s.bind(("127.0.0.1",9005)); s.listen(5000); time.sleep(5)' &
$ ss -lnt '( sport = :9005 )'
State  Recv-Q Send-Q Local Address:Port Peer Address:Port
LISTEN 0      4096       127.0.0.1:9005      0.0.0.0:*
```

`Send-Q` 是 4096 而不是 5000：`listen` 的参数会被 `somaxconn` 截断。**要放大 backlog，必须同时改代码里的参数与这个系统上限**，只改一边没用。`Recv-Q` 是 0，因为没有待 `accept` 的连接。

**实验 B：把队列塞满。** 服务器 `listen(1)` 后睡 30 秒、不 `accept`；客户端连 50 次，每次超时 0.3 秒：

```bash
# 终端 1：服务器
$ python3 - <<'PY'
import socket, time
s = socket.socket(); s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(("127.0.0.1", 9008)); s.listen(1)
time.sleep(30)
PY
# 终端 2：客户端
$ python3 - <<'PY'
import socket
ok = tout = 0
for i in range(50):
    try:
        s = socket.create_connection(("127.0.0.1", 9008), timeout=0.3)
        s.close(); ok += 1
    except TimeoutError:
        tout += 1
print("ok", ok, "timeout", tout)
PY
ok 2 timeout 48
```

50 次里只有 2 次完成握手，其余 48 次在 0.3 秒内没等到 SYN+ACK，由客户端主动超时。那一刻的监听行（实测）：

```text
State  Recv-Q Send-Q Local Address:Port Peer Address:Port
LISTEN 2      1      127.0.0.1:9008    0.0.0.0:*
```

`Send-Q 1` 是 `listen(1)` 的有效 backlog；`Recv-Q 2` 是已完成的连接数——内核的判据是「超过 backlog 才拒」，所以队列能到 `backlog + 1` 条。再看计数器（实测差值）：

```text
$ nstat -az TcpExtListenOverflows TcpExtListenDrops
TcpExtListenOverflows           62
TcpExtListenDrops               62
```

跑之前是 14，跑完 62，正好加 48，与客户端 48 次超时对上。`ListenOverflows` 数的是「accept 队列满导致的丢弃」，`ListenDrops` 是它的超集，还包含 SYN 队列溢出。

::: def 定义 1.11.16 · 两个队列 {#def-1.11.16}
服务器在 `listen` 之后有两个队列：**SYN 队列**放「收到 SYN、还没走完三次握手」的连接；**accept 队列**放「握手已完成、等应用 `accept`」的连接。`backlog` 约束的是 accept 队列，`somaxconn` 是它的系统上限。`ss -lnt` 的 `Recv-Q` 是 accept 队列长度，`Send-Q` 是有效 backlog。
:::

队列满时客户端看到的不是一种结局，而是两种：SYN 被丢，客户端只能重传，表现为「很慢最后超时」；连接被内核重置，才会立刻 `Connection refused`。所以线上「偶发连接超时」优先查 backlog 与 `accept` 速度，而不是先怀疑网络。

**实验 C：epoll 的观测方式。** 用 1.11.12 的 `lab1c11_epoll` 起服务，让 500 条连接连上后什么都不发、停 4 秒再关，同时用 `strace -c` 统计（实测，节选）：

```text
$ strace -f -c -o /tmp/ep.txt ./lab1c11_epoll 9004
$ python3 - <<'PY'
import socket, time
cs = [socket.create_connection(("127.0.0.1", 9004)) for _ in range(500)]
time.sleep(4)
for c in cs: c.close()
PY
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 28.64    0.014709           9      1501           epoll_ctl
 27.83    0.014292           9      1500           write
 17.07    0.008764          17       502           close
 11.00    0.005651          11       504         4 accept4
  9.21    0.004728           9       501           read
  0.47    0.000241          16        15         2 epoll_pwait
------ ----------- ----------- --------- --------- ----------------
100.00    0.051352          10      4726         7 total
```

四个数字各对应一件事：`epoll_ctl` 1501 次 = 监听 fd 的 1 次 `ADD` + 每条连接 `ADD`、`MOD`、`DEL` 各一次；`accept4` 504 次里有 4 次返回 `EAGAIN`，说明 ET 的 accept 循环每次取到空为止；`read` 501 次，约 500 次是每条连接读到 EOF；`write` 1500 次不是回显，而是每条连接三行 stderr 日志。**500 条连接，`epoll_wait` 只被调用 15 次**——glibc 把它实现成 `epoll_pwait`，所以统计里看到的是这个名字。它只在有事件时返回；`poll` 则要每次把 500 个 fd 拷进内核并线性扫描。

这里要克制：`strace -c` 的 `seconds` 是系统调用耗时总和，0.051 秒不等于 CPU 占用率，`strace` 本身还有开销。500 条空闲连接占的是内核内存与 fd 表项，不是 CPU 时间，这两笔账要分开算。能下的结论只有一个：**等待的代价与连接总数无关，与事件批次有关。**

::: errata 关于 backlog 与 epoll 的三个误解
1. **「backlog 是并发连接上限」**——它只限「等待 accept」的队列；`accept` 之后连接离开队列，服务器可以同时持有远超 backlog 的连接。
2. **「调大 backlog 能治好 accept 慢」**——队列只是缓冲；应用 `accept` 慢，队列迟早再满。真正的修法是让 accept 循环不被业务阻塞。
3. **「`epoll_wait` 次数应随连接数增长」**——空闲连接不产生事件。次数暴涨通常说明有人在频繁 `MOD`，或把 `EPOLLOUT` 一直开着。
:::

### 1.11.16 小结

① 有效 backlog 是 `min(listen 参数, /proc/sys/net/core/somaxconn)`，`ss -lnt` 的 `Send-Q` 就是它；② `Recv-Q` 是已完成握手的排队数，实测 `listen(1)` 能排到 2 条；③ 队列满表现为超时，`ListenOverflows` 的增量与客户端超时次数对得上；④ epoll 的调用量随事件批次而不是连接数增长。如果只记住一件事：**backlog 是缓冲，不是容量；accept 的速度才决定队列会不会满。**

::: method 即时自测 · 1.11.16
**Q1（记忆）** `listen(5000)` 而 `somaxconn` 是 4096 时，`ss -lnt` 的 `Send-Q` 显示多少？为什么？

**Q2（辨析）** `listen(1)` 的服务器，`ss` 却显示 `Recv-Q 2`，是内核没遵守 backlog 吗？

**Q3（应用）** 客户端大量「连接超时」而不是「连接被拒」，应该先查哪两个量？

**Q4（迁移）** 500 条空闲连接下 `epoll_wait` 只返回 15 次，换成 `poll` 后固定开销变在哪里？

::: sol 答案
**A1** 4096。`listen` 的 backlog 会被 `somaxconn` 截断，`Send-Q` 显示的是截断后的有效值。
**A2** 不是。内核的判据是「队列长度超过 backlog 才拒绝」，所以允许排到 `backlog + 1`；`Send-Q` 仍是 1。
**A3** `ss -lnt` 的 `Recv-Q`（是否等于 `Send-Q`）与 `nstat` 的 `TcpExtListenOverflows` 增量；前者看队列是否满，后者看丢了多少次。
**A4** 每次 `poll` 都要把全部 fd 从用户态拷进内核并线性扫描一遍，即使没有事件也付这份固定成本；连接数上万时它就是 C10K 的主因。
:::
:::

## 1.11.17 十三条网络编程陷阱 {#sec-1.11.17}

这一节回答：这些坑里，哪几个表现为「连接建立不了」、哪几个是「建立了但数据不对」、哪几个是「跑久了才出问题」？遇到其中一条，第一条命令该跑什么？

::: preview 先抓住一件事
网络编程的坑几乎都能归到四句话：**连接不是消息**（字节流没有边界）、**成功不是送达**（写进缓冲区不等于对端收到）、**关闭不是终止**（`TIME_WAIT`、`RST`、`SIGPIPE` 各有语义）、**名字不是地址**（`getaddrinfo` 与双栈）。按这四句归类，十三条不用背。
:::

| # | 现象 | 原因 | 修复 |
|--:|:--|:--|:--|
| 1 | 服务重启 `bind: Address already in use` | 旧连接处于 `TIME_WAIT` | 开 `SO_REUSEADDR`，且在 `bind` 前设置 |
| 2 | `accept` 返回 `EMFILE` 后空转 | fd 耗尽，循环继续 | 预留救急 fd；限流；`accept` 后立即关闭 |
| 3 | 客户端收到 `RST` | 服务器 `SO_LINGER=0` 或对已关闭连接写 | 检查关闭语义；忽略 `SIGPIPE`/用 `MSG_NOSIGNAL` |
| 4 | 请求被截断 | 一次 `read` 当成完整请求 | 按 `\r\n\r\n` 与 `Content-Length` 循环读 |
| 5 | 响应尾部丢失 | 对端关闭前没读完 | 读到 EOF 或按长度读满 |
| 6 | 大响应卡住 | 没处理短写/`EAGAIN` | 写循环 + `EPOLLOUT` 缓冲 |
| 7 | `curl` 正常、浏览器卡住 | 缺 `Content-Length` 或 keep-alive 边界 | 明确长度或 `Connection: close` |
| 8 | 路径穿越读到 `/etc/passwd` | URI 未规范化 | `realpath` + 前缀校验，或 `openat`/`O_NOFOLLOW` |
| 9 | 中文 URL 404 | 未做百分号解码 | 解码后再映射文件；注意 `%2e%2e` |
| 10 | IPv6 环境连不上 | 只监听了 `0.0.0.0` | `AF_UNSPEC` + `AI_PASSIVE`，或双栈 `::` |
| 11 | 连接数一多就慢 | `select`/`poll` 线性扫描 | `epoll` + 非阻塞 + 边沿触发 |
| 12 | 空闲连接突然消失 | NAT/防火墙超时 | 应用层心跳；调小 `TCP_KEEPIDLE` |
| 13 | `send` 返回成功但对方没收到 | 只写进本机发送缓冲区 | 应用层 ACK；`SO_LINGER` 只影响关闭 |

**第一组（1、2、10、11）：连接建立不了或建立得很差。** `TIME_WAIT` 抢端口、`EMFILE` 空转、只监听 `0.0.0.0` 漏掉 IPv6、`select` 线性扫描拖慢大连接数。先查什么：`ss -lnt` 看 `Send-Q`（backlog）、`ss -tan` 看状态分布、`ls /proc/<pid>/fd | wc -l` 看 fd 数。

**第二组（4–7、13）：连上了但数据不对。** 短读当完整请求、响应尾部丢失、`EAGAIN` 没处理、keep-alive 少了边界、`send` 成功但对方没收到。先查什么：在服务器端打印 `read`/`write` 的返回值，用 `curl -v` 看实际收到多少字节，用 `ss -tn` 看 `Recv-Q`/`Send-Q` 是否堆积。

**第三组（3、8、9、12）：安全与寿命。** `RST`/`SIGPIPE`、路径穿越、百分号解码、NAT 超时踢掉空闲连接。先查什么：`strace -e trace=write,sendto` 看有没有 `EPIPE`；请求路径先 `realpath` 再比前缀；空闲连接加应用层心跳。

::: errata 三个关于「连接已建立」的误解
1. **「`connect` 成功就代表服务可用」**——只代表 TCP 握手完成；应用可能还没 `accept`，或已经过载。健康检查要发真实请求。
2. **「`close` 后对端立刻知道」**——FIN 只表示「我没有数据要发了」；对端可能还有数据在路上。半关闭要用 `shutdown(fd, SHUT_WR)`。
3. **「`SO_REUSEPORT` 能接管已有连接」**——它只影响新连接的分配；已有连接固定在原 socket 上，进程崩溃后连接随之消失。
:::


### 1.11.17 小结

十三条按「建立 / 数据 / 安全与寿命」三组归位之后，每组的排查起点都是同一条命令：看状态（`ss`）、看返回值（`strace`/日志）、看边界（报文长度与连接生命周期）。如果只记住一件事，那就是：**TCP 只保证字节按序到达，不保证「一次读就是一条消息」，也不保证「写成功就是对方收到」。**

::: method 即时自测 · 1.11.17
**Q1（判断）** 服务重启时报 `bind: Address already in use`，`ss -tan` 显示大量 `TIME_WAIT`。设 `SO_REUSEADDR` 能解决什么、不能解决什么？

**Q2（判断）** `curl` 访问正常，浏览器一直转圈。最可能是哪一条陷阱？如何用 `curl -v` 证实？

**Q3（实验）** 写一个最小服务器，故意不处理短读（一次 `recv` 就解析）。用 `nc` 把请求分两次发，观察它的响应；再改成循环读，比较结果。

::: sol 答案
**A1** `SO_REUSEADDR` 允许在 `TIME_WAIT` 期间重新 `bind` 同一端口（前提是四元组不冲突），解决「重启抢不到端口」；它不能让旧连接的 `TIME_WAIT` 消失，也不改变主动关闭方进入 `TIME_WAIT` 的语义。真正的长期方案是让客户端主动关闭，或接受 `TIME_WAIT` 的存在。

**A2** 第 7 条：缺 `Content-Length` 或 keep-alive 边界，浏览器在等「还有没有更多数据」，而 `curl` 收到 EOF 就结束。用 `curl -v` 看响应头有没有 `Content-Length`/`Transfer-Encoding`，以及连接是否在响应后关闭。

**A3** 不处理短读时，服务器只看到 `GET /ind` 就按不完整请求处理（可能回 400 或回错内容）；改成「读到 `\r\n\r\n`、再按 `Content-Length` 读满」后，同样的分段发送能得到正确响应——这正是 1.11.6 讲的「字节流没有消息边界」在代码里的样子。
:::
:::

## 1.11.18 本章小结 {#sec-1.11.18}

这一节回答：这一章学完，给两台机器之间的一次请求，你能不能说清「名字怎么变成地址、连接怎么建立、字节怎么划界、一条线程怎么照看很多条连接」？

::: preview 先抓住一件事
判据是：**给你一个「连不上」「连上了但不回」「回了但缺一半」「连接一多就卡」的现场，你能先分清是名字解析、连接生命周期、字节流边界还是会话模型的问题，再挑一条命令去证实。**
:::

这一章的主线是**从名字到字节流**。1.11.1–1.11.4 立地基：客户-服务器模型与封装分用、IP 与端口和大端字节序、socket API 与 TCP 状态机、一个 `fork` 并发的 echo 服务器。1.11.5–1.11.8 把 HTTP 放上去：最小 Web 服务器、字节流边界与 MTU、从 socket 到报文的排障顺序、`getaddrinfo` 的 hints 与错误码。

1.11.9–1.11.16 是二刷与完整程序：`SO_REUSEADDR`/`SO_REUSEPORT`/`TCP_NODELAY` 的取舍、TINY 的源码解剖、四种并发模型（进程/线程/事件循环/`io_uring`）、边沿触发的 `epoll` echo、手写 HTTP 客户端与 `getaddrinfo` 标志浏览器，最后是两个实验：`ss`/`tcpdump`/`strace` 看连接生命周期，以及 backlog 溢出与 `epoll` 的观测方式。1.11.17 把十三类坑归成「建立 / 数据 / 安全与寿命」三组。

真实读数贯穿全章：`curl -v` 的 `Content-Length: 52`、单次 `recv` 只读到 `GET /ind` 却回了 200、`ss` 里 `Recv-Q 5000`、`strace` 的 `read=88`/`write=98/52`、`getaddrinfo("nonexistent.invalid")` 的 `EAI_NONAME`、`epoll` 服务器的真实运行输出。

逐条打勾的达标表在[学习目标自检表](ch11-checklist.md)。这里只留判据：

- **能解释**：四元组为什么唯一确定一条连接、`TIME_WAIT` 为什么存在、`SO_REUSEADDR` 解决的是哪一半问题、为什么「一次 `read` 就是一条消息」是错的、`epoll` 边沿触发为什么要配非阻塞。
- **能操作**：用 `getaddrinfo` 写一个不写死地址族的客户端；用 `ss -lnt`/`ss -tan` 读 backlog 与状态；用 `strace -e trace=network` 看收发返回值；用 `epoll` 写一个边沿触发的 echo。
- **能判断**：`bind: Address already in use` 先查什么、连接一多就慢该换模型还是换参数、`send` 成功意味着什么、`tcpdump` 拿不到权限时用什么替代。

如果只记住一件事，那就是**TCP 是字节流，不是消息队列**：它保证字节按序到达，不保证「一次读一条消息」，也不保证「写成功就是对方收到」——本章几乎所有坑都是这句话的推论。

::: errata 本章的三条口径边界
1. **`tcpdump` 未实测**：本机无 `CAP_NET_RAW`，抓包相关段落只给命令与判读，替代证据是 `ss`、`strace`、`/proc/net/tcp`。
2. **特权端口未实测**：`sudo` 不可用，80/443 绑定会 `EACCES`；所有实验用 8080。
3. **双栈与大端未实测**：两台机器都是小端，IPv6 双栈行为按 `getaddrinfo` 与 `ss` 的输出描述，未在纯 IPv6 环境验证。
:::

::: method 即时自测 · 1.11
**Q1（记忆）** 一条 TCP 连接由哪四元组唯一确定？`bind` 与 `connect` 各指定其中哪几个？

**Q2（判断）** 服务器一次 `recv` 只收到 `GET /ind`，就按请求处理并回了 200。这属于哪一类错误？正确做法是什么？

**Q3（实验）** `ss -lnt` 的 `Send-Q` 列对监听 socket 表示什么？把它调小到 1，再用并发连接压一下，观察 `ss` 与客户端超时。

**Q4（判断）** 10 万条长连接、每连接偶尔有数据，用线程模型还是事件循环？说出两条理由与一条代价。

::: sol 答案
**A1** 源 IP、源端口、目的 IP、目的端口。`bind` 指定本端的 IP/端口（服务器），`connect` 指定对端 IP/端口并隐式选定本端临时端口；四元组在连接期间唯一。

**A2** 属于「把字节流当消息」的错误（1.11.6/1.11.17 第 4 条）。正确做法是循环读到 `\r\n\r\n` 拿到头部、再按 `Content-Length` 读满正文；`recv` 返回多少只能说明「这次到了多少字节」。

**A3** 对监听 socket，`Send-Q` 是已完成三次握手、等待 `accept` 的队列长度上限（backlog）。调到 1 后并发连接会出现握手成功但排队、客户端 `connect` 变慢或超时；这也是「`connect` 成功不代表服务可用」的证据之一。

**A4** 事件循环：① 每个线程 8 MiB 虚拟栈 + 内核调度开销，10 万线程不现实；② 长连接大部分时间空闲，事件循环用 `epoll` 只处理活跃 fd。代价是不能阻塞——任何一次同步 I/O 或长计算都会卡住全部连接，需要多 reactor 或把阻塞操作移出事件线程。
:::
:::
