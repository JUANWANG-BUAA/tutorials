## 1.14.1 从门到指令：组成的最小模型 {#sec-1.14.1}

这一节回答：一台能跑 Linux 的机器，最少要有哪几件东西，一行 `c = a + b;` 才能真的落到电路上？

::: preview 先抓住一件事
把机器砍到只剩五件东西，程序照样能跑：**寄存器文件、运算器、控制单元、MMU、存储与中断（硬件或软件打断指令流的事件）**。它们之间那份「谁能看见什么」的协议就是 ISA；而程序员看到的世界永远是「一条指令执行完，再执行下一条」。
:::

先看一行反汇编。下面是 `sum3` 在 VM 上的真实产物（Ubuntu 24.04，GCC 13.3，`gcc -O2 -c sum3.c` 之后 `objdump -d`）：

```text
   0:	8b010000 	add	x0, x0, x1
   4:	8b020000 	add	x0, x0, x2
   8:	d65f03c0 	ret
```

最左是地址，中间是四个字节的机器码，右边是译码后的助记符。这一行恰好把五件东西点了名：地址来自 PC（program counter，程序计数器，指向下一条要取的指令），字节存在指令存储器里，`x0`/`x1` 是寄存器文件里的格子，`add` 由运算器执行，最后的 `ret` 要跳走，就得由控制单元改 PC。

### 五件东西，各管一段

<pre class="layout">
  CPU
  ├── 寄存器文件（16/31/32 个通用寄存器 + PC + 标志）
  ├── ALU / 乘法器 / 浮点单元
  ├── 控制单元（取指、译码、发射、退休）
  └── MMU（页表基址、TLB、权限检查）
        │
        ├── L1 I/D cache ── L2 ── L3 ── DRAM
        └── 中断控制器（APIC/GIC/PLIC）── 定时器、设备
</pre>

**寄存器文件**（register file）是一小排能在一拍内读写的格子，指令按编号直接点它的名。没有它，连一次加法都得先访存。

**运算器**包括整数 ALU（arithmetic logic unit，算术逻辑单元）、乘法器和浮点单元。它是一团组合逻辑：输入稳定后要经过若干级门，输出才稳定，这段延迟直接压低了时钟周期（1.14.7 会把它算成一个数）。

**控制单元**负责取指、译码、发射、退休。它把 `8b010000` 这 32 位拆成 opcode、Rd、Rn、Rm 几个字段，再按字段打开或关闭数据通路上的多路选择器。你看到的「指令」，在电路上就是一组开关的位置。

**MMU**（memory management unit，内存管理单元）把程序里的地址先翻译成物理地址，再按页表里的权限位决定这次访问允不允许。没有它，一条用户态的 `ldr` 就能读内核内存；有了它，同一个虚拟地址在不同进程里指向不同物理页。

**存储层次与中断控制器**：L1/L2/L3 与 DRAM 把平均访存时间拉低；中断控制器（x86 的 APIC、ARM 的 GIC、RISC-V 的 PLIC）把定时器、网卡、键盘的事件送进 CPU。没有中断，阻塞在 `read` 上的进程永远等不到数据，时间片也没法轮转。

### 最小循环

无论上面五件怎么实现，程序执行的最小循环只有一条：

```text
PC → 取指 → 译码 → 取操作数 → 执行 → 访存 → 写回 → PC+4/跳转
```

现代 CPU 把这条顺序拆成十几级，还允许后面的指令先跑（乱序执行）；但对程序员可见的语义仍然是「一条指令接着一条指令，寄存器与内存按序变化」。编译器和内核都押在这个假象上：只要你不写数据竞争，就不必关心真实执行顺序；要碰共享内存，才需要屏障和原子指令（1.14.13）。

### 从一个门到一条指令

拆到最小：两个输入进一个与门、一个异或门，就是一位全加器，和是 `a⊕b⊕cin`，进位是 `ab + cin(a⊕b)`。把 64 个这样的单元串起来就是 64 位加法器，代价是进位要从最低位一路传到最高位，共 64 级门；真实芯片改用超前进位或树形结构，把它压到 $\log_2 64 = 6$ 级的量级。

`add x0, x0, x1` 落在这条通路上就是三个动作：读 `x0`、`x1`，过加法器，写回 `x0`。`sub` 与比较走同一套加法器，只是有一路输入取反、进位初值设为 1。所谓「指令」，就是控制单元对这条通路做的一次配置。

想自己验一遍，只需要两行命令：

```bash
cc -O2 -c sum3.c -o sum3.o && objdump -d sum3.o
```

读法是看**地址间隔**：aarch64 上是 `0、4、8`，每条 4 字节；x86-64 上是 `0、4、7`，最后那条 `ret` 只占 1 字节。这就是定长与变长的第一个可见差别，三套汇编的完整对照在 1.14.3。

::: def 定义 1.14.1 · 体系结构状态 {#def-1.14.1-state}
体系结构状态（architectural state）是程序员和编译器能看到、且必须逐条维护的全部状态：通用寄存器、PC、条件标志、当前特权级，以及经 MMU 映射后的地址空间。cache 里有什么、重排序缓冲排到第几条、分支预测器猜了什么，都属于微架构（microarchitecture），只影响快慢，不影响程序结果。
:::

::: errata 组成模型的四个误解
1. **「寄存器就是 CPU 里的 cache」**——不是。寄存器由指令按编号直接寻址，cache 由地址索引；把变量放进寄存器是编译器干的活，硬件不会替你搬。
2. **「乱序执行会让结果不确定」**——单线程下硬件保证可见结果与顺序执行一致。只有多线程共享内存又没同步时，才可能出现「读到旧值」的数据竞争。
3. **「MMU 只在多进程时才派上用场」**——单进程也要：内核与用户态靠同一套页表机制做权限隔离，缺页（访问的页不在内存里）处理、`mmap` 全部走它。
4. **「中断只是通知一下」**——没有中断，设备完成、定时器到期都进不了内核，`read` 不返回，调度器也无法抢占。
:::

### 1.14.1 小结

① 五件东西：寄存器文件、运算器、控制单元、MMU、存储与中断；② 最小循环是取指到写回再改 PC，乱序只改时间不改结果；③ 一条 `add` 就是控制单元在加法器通路上打开的一组开关。如果只记住一件事，那就是：**看一条指令，先问它动了哪几样状态，再问这条路径有多长。**

::: method 即时自测 · 1.14.1
**Q1（记忆）** 组成的最小模型里，哪一件负责「地址翻译与权限检查」？哪一件决定时间片能不能轮转？

**Q2（辨析）** 有人说「寄存器比内存快，所以编译器会把所有变量都放进寄存器」。这句话哪里不成立？

**Q3（应用）** `objdump -d` 里 aarch64 的地址是 `0、4、8`，x86-64 是 `0、4、7`。这两个序列分别说明了什么？

**Q4（迁移）** 一块嵌入式板子为了省电关掉了 MMU。普通 Linux 发行版的用户态程序还能跑吗？说明理由。

::: sol 答案
**A1** MMU 负责地址翻译与权限检查；中断控制器（连同定时器）负责把时间片到期的事件送进内核。
**A2** 寄存器数量有限（16/31/32 个），又是指令编码里的字段，装不下任意多的变量；不够用得溢出到栈上。编译器做的是寄存器分配。
**A3** `0、4、8` 说明每条指令固定 4 字节（AArch64）；`0、4、7` 说明指令变长，前两条各 4 字节、`ret` 只占 1 字节（x86-64）。
**A4** 普通发行版的用户态程序跑不起来：地址隔离、缺页、写时复制都依赖 MMU。Linux 有 no-MMU 的移植（用 uClinux 一路的改法），但没有地址隔离，`fork` 只能用 `vfork` 语义。
:::

## 1.14.2 ISA 是什么：寄存器、指令格式与特权级 {#sec-1.14.2}

这一节回答：ISA 这份「软硬件合同」到底写死了哪几样东西？三套 ISA 在这些东西上差多少，哪些差异其实来自 ABI？

::: preview 先抓住一件事
ISA 只规定**看得见的状态、指令怎么编码、谁能执行哪些指令**这三类事；流水线几级、cache 多大，它一个字都不写。参数放哪个寄存器属于 ABI，是 ISA 之上再签的一层合同——所以同一个 x86-64，在 Linux 和 Windows 上参数寄存器并不相同。
:::

同一件事——把两个寄存器相加——三家写出来是这样（编码都是在本机编译后用 `objdump` 读出来的）：

```text
x86-64    48 01 d0        add %rdx, %rax      3 字节，目标必须是源之一
AArch64   8b010000        add x0, x0, x1      4 字节，三个寄存器都能不同
RISC-V    00a58533        add a0, a1, a0      4 字节，rd 可与两个源都不同
```

三条指令干的是同一件事，编码长度却差 1 字节，字段位置也完全不同。ISA 规定的就是这种「位怎么摆、状态怎么变」。

::: def 定义 1.14.2 · 指令集架构 {#def-1.14.2}
指令集架构（instruction set architecture，ISA）是软件与硬件之间的合同，规定五类东西：① 程序员可见的状态（寄存器集合与位宽、PC、条件标志）；② 指令编码与寻址方式；③ 特权级，以及哪些指令只能在核心态执行；④ 内存模型、原子与屏障语义；⑤ 异常与中断的入口。它不规定流水线深度、cache 大小、乱序窗口——那些属于微架构。
:::

### 三套骨架的硬数字

| 维度 | x86-64 | AArch64 | RISC-V 64 |
|:--|:--|:--|:--|
| 指令长度 | 变长 1–15 字节 | 固定 4 字节 | 基础 4 字节；C 扩展下常用指令 2 字节 |
| 通用寄存器 | 16 个 | 31 个 | 32 个（`x0` 恒 0） |
| 整数参数寄存器 | 6 个：`rdi,rsi,rdx,rcx,r8,r9` | 8 个：`x0`–`x7` | 8 个：`a0`–`a7` |
| 第 7 个整数参数 | 栈上 | `x6` | `a6` |
| 第 9 个整数参数 | 栈上 | `[sp]` | `[sp]` |
| 零寄存器 | 无（`xor eax,eax`） | `xzr` | `x0` |
| 返回地址寄存器 | 无，`call` 压栈 | `x30`（LR） | `x1`（`ra`） |
| 栈指针 | `rsp` | `sp` | `sp`（`x2`） |
| 特权级 | ring 0–3 | EL0–EL3 | M/S/U |
| 陷入指令 | `syscall` | `svc #0` | `ecall` |
| 系统调用入口约定 | 号在 `rax`，参数 `rdi,rsi,rdx,r10,r8,r9` | 号在 `x8`，参数 `x0`–`x5` | 号在 `a7`，参数 `a0`–`a5` |
| 风格 | CISC，变长、内存操作数 | RISC，Load/Store | RISC，Load/Store、极简 |

表里别只记「几个」。x86 的 16 个通用寄存器里只有 6 个能传参，这是 ABI 的选择，不是 ISA 的禁令；ARM64 的 31 个寄存器里，`x30` 被 `bl` 征用为返回地址，也不能随便当临时寄存器。

### 指令格式的三种形状

x86 的一条指令是「前缀 + opcode + ModRM + SIB + 位移 + 立即数」，各段都可缺省，所以 1 到 15 字节都可能。把 `48 8d 04 37` 拆开：`48` 是 REX.W（声明 64 位操作），`8d` 是 `lea` 的 opcode，`04` 是 ModRM（mod=00、reg=000 表示 `rax`、rm=100 表示「后面跟 SIB」），`37` 是 SIB（scale=1、index=`rsi`、base=`rdi`）。拼起来正是 `lea (%rdi,%rsi),%rax`。

AArch64 强制 32 位，字段位置固定：`8b010000` 的高 11 位是 ADD（移位寄存器型）的标识，`Rm`、`Rn`、`Rd` 各占 5 位，分别是 `x1`、`x0`、`x0`。定长让译码简单，代价是立即数挤不进太多位——`add` 的立即数版本只有 12 位。

RISC-V 的 R 型分五段：`funct7 | rs2 | rs1 | funct3 | rd | opcode`。`00a58533` 拆出来是 opcode=`0x33`、funct3=`000`、funct7=`0000000`、rs1=`a1`、rs2=`a0`、rd=`a0`，即 `add a0,a1,a0`。手算三种格式的完整过程放在 1.14.12。

### 特权级：用户态能碰什么

三套 ISA 都把特权分成几级：x86 的 ring 0–3、AArch64 的 EL0–EL3（exception level，异常级）、RISC-V 的 M/S/U（machine/supervisor/user）。Linux 只用最外层跑用户程序，内核跑在 ring 0 / EL1 / S。

用户态唯一受控的进内核方式是陷入指令：x86 的 `syscall`、ARM64 的 `svc #0`（supervisor call）、RISC-V 的 `ecall`（environment call）。三条指令做的事一样——把 PC 换成内核预先登记的入口地址，同时把特权级升上去。系统调用号放在哪（`rax`/`x8`/`a7`）是内核 ABI 的决定，1.14.5 专门讲。

在这个边界上，写错一条指令的后果很直接：用户态执行「改页表基址」「关中断」这类特权指令，CPU 会立刻陷入异常，内核转手给你 `SIGILL` 或 `SIGSEGV`。

::: errata 关于 ISA 的四个误解
1. **「ISA 规定了参数寄存器」**——ISA 只规定寄存器存在。参数坐哪是 ABI 的事：同一套 x86-64 ISA，Windows 用 `rcx,rdx,r8,r9` 开头，和 Linux 不同。
2. **「ARM64 只有 31 个寄存器，比 RISC-V 少，所以更弱」**——31 是因为 5 位寄存器字段留了一个编码给 `sp`/`xzr`；数量不是性能指标。`x31` 在多数指令里当 `xzr`，在访存基址和 `add sp` 形式里当 `sp`，这是最容易读错的一处。
3. **「RISC-V 的 `x0` 和 ARM64 的 `xzr` 完全等价」**——都恒为 0，但用法有差别：RISC-V 的 `x0` 写在任何位置都被丢弃，`addi x0,x0,0` 就是标准的 `nop`。
4. **「用户态什么指令都能执行，只是没权限读设备」**——特权指令在用户态根本执行不了，触发的是异常，不是「返回错误」。
:::

### 1.14.2 小结

① ISA 规定状态、编码、特权、内存模型与异常入口五件事；② 三套 ISA 的骨架差异集中在寄存器数量、指令长度与零寄存器；③ 参数寄存器与系统调用号是 ISA 之上的 ABI，跨架构时最先变的就是它们。如果只记住一件事，那就是：**看到「第几个参数在哪个寄存器」，先问这是哪一层合同规定的。**

::: method 即时自测 · 1.14.2
**Q1（记忆）** 三套 ISA 的陷入指令分别叫什么？系统调用号分别放在哪个寄存器？

**Q2（辨析）** 「x86-64 有 16 个通用寄存器，所以最多能传 16 个整数参数。」错在哪？

**Q3（应用）** 给你 `8b010000`，不查表说出它的三个寄存器字段分别是什么，并写出对应汇编。

**Q4（迁移）** 同事把 Linux 上写的 x86-64 手写汇编搬到 Windows x64，参数全乱了。用本节两个概念解释。

::: sol 答案
**A1** x86-64 是 `syscall`，号在 `rax`；AArch64 是 `svc #0`，号在 `x8`；RISC-V 是 `ecall`，号在 `a7`。
**A2** 能传几个参数由 ABI 规定，不是寄存器总数。SysV 只指定 6 个整数参数寄存器，第 7 个起走栈；多出来的寄存器要留给临时值和被调用者保存。
**A3** `Rm=x1`、`Rn=x0`、`Rd=x0`，即 `add x0, x0, x1`（x0 = x0 + x1）。
**A4** ISA 相同、ABI 不同：Windows x64 的前四个整数参数是 `rcx,rdx,r8,r9`，第 5 个起走栈；Linux 的 SysV 用 `rdi,rsi,rdx,rcx,r8,r9`。按 Linux 的表写，参数和返回值都会错位。
:::
:::

## 1.14.3 同一段 C，三种汇编 {#sec-1.14.3}

这一节回答：同一段 C 编译到三套 ISA，三份汇编到底差在哪三件事上？为什么指令条数一样，字节数却不一样？

::: preview 先抓住一件事
差别几乎不在「加法怎么做」，而在**参数放哪、返回值放哪、返回地址放哪**。前两件由 ABI 决定，第三件由 ISA 决定；字节数的差别则来自指令长度与压缩扩展。
:::

先别往下翻，猜三个数：下面这个函数编到三套架构，各几条指令、各几字节？

```c
/* sum3.c */
long sum3(long a, long b, long c)
{
    return a + b + c;
}
```

答案是三家都 3 条指令，字节数是 8、12、12——RISC-V 打开 C 扩展后只剩 6 字节。下面三份都是编译器的产物，不是手写的。

### x86-64：8 字节

写作机（macOS arm64，Homebrew clang 22）交叉编译，`clang --target=x86_64-linux-gnu -O2 -S`：

```asm
sum3:
	leaq	(%rdi,%rsi), %rax
	addq	%rdx, %rax
	retq
```

`objdump -d` 读出的字节是 `48 8d 04 37`、`48 01 d0`、`c3`，4+3+1 = 8 字节。

### AArch64：12 字节

VM 上（Ubuntu 24.04，GCC 13.3）用 `gcc -O2 -S`：

```asm
sum3:
	add	x0, x0, x1
	add	x0, x0, x2
	ret
```

字节是 `8b010000`、`8b020000`、`d65f03c0`，每条 4 字节，共 12 字节。

### RISC-V 64：12 字节，开了 C 扩展变 6 字节

写作机 clang 22，`clang --target=riscv64-linux-gnu -O2 -c`：

```asm
	add	a0, a1, a0
	add	a0, a0, a2
	ret
```

`-march=rv64g` 下字节是 `00a58533`、`00c50533`、`00008067`，共 12 字节；换成 `-march=rv64gc`，同样三条压成 `952e`、`9532`、`8082`，只剩 6 字节。

### 差异一：两操作数还是三操作数

x86 的 `add` 只能改两个操作数之一，所以它先用 `leaq (%rdi,%rsi), %rax` 一步完成「a+b 并放进返回值寄存器」，再 `addq %rdx, %rax` 把 c 加进去。`lea` 本是算地址的指令（load effective address），因为能算「基址 + 变址×比例」且不写标志位，编译器常拿它做加法。

ARM64 与 RISC-V 是三操作数：目的寄存器和两个源都可以不同。返回值寄存器 `x0`/`a0` 又恰好就是第一个参数寄存器，于是两条 `add` 原地累加即可，不需要搬。

条数一样，写法不一样。只背「sum3 是两条 add 加一条 ret」，换到 x86 上就会找不到 `add` 前面那条 `lea`。

### 差异二：返回地址放在哪

x86 的 `call` 把下一条指令的地址压栈，`ret` 再从栈顶弹出到 PC。所以叶函数（不再调用别的函数的函数）一条 `push` 都不用。

AArch64 的 `bl`（branch with link）把返回地址写进 `x30`，`ret` 跳到 `x30`。叶函数同样不碰栈；一旦函数体里还有 `bl`，就得先把 `x30` 存起来，否则第二次 `bl` 会覆盖第一次的返回地址。

RISC-V 的 `jal`/`call` 把返回地址写进 `ra`（就是 `x1`），`ret` 是伪指令 `jalr x0, 0(ra)`——跳到 `ra` 指向的地址，并把返回地址写进 `x0`，等于丢弃。非叶函数要 `sd ra, ...(sp)` 再 `ld` 回来。

三家的 `ret` 长得一样，做的事完全不同：x86 读栈，ARM64 读 `x30`，RISC-V 读 `ra`。所以拿一份汇编去对照另一家时，`ret` 那一行没有任何参考价值。

### 差异三：条数不等于字节数

指令条数只反映译码次数；字节数才决定 I-cache 里能装多少。x86 把「常用指令短、不常用指令长」做成编码，所以 3 条只要 8 字节；AArch64 每条固定 4 字节，简单、对齐，但一条也省不下；RISC-V 的基础编码也是 4 字节，靠 C 扩展把最常用的几十条压成 2 字节，于是同一段代码变成 6 字节。

同一段 C 换个编译器，寄存器分配就会变。同样的 aarch64 目标，用 clang 22 编出来是：

```asm
	add	x8, x1, x0
	add	x0, x8, x2
	ret
```

中间结果放在 `x8`，结果仍是 12 字节。ABI 只规定 `x0` 是返回值，没规定中间用哪个临时寄存器——所以背汇编要背规则，别背某台机器的输出。

### 汇编不能互搬

把上面那份 x86 的 `.s` 直接交给 AArch64 汇编器（`clang --target=aarch64-linux-gnu -c`），会得到：

```text
lab1c14_sum3_x86.s:4:11: error: unknown token in expression
    leaq (%rdi,%rsi), %rax
          ^
```

寄存器名、寻址语法、助记符全是目标相关的。`--target` 只够生成汇编和 `.o`，链接与运行另说（1.14.6）。

::: def 定义 1.14.3 · ABI {#def-1.14.3}
ABI（application binary interface，应用二进制接口）是 ISA 之上的一层约定：函数之间怎么传参、返回值放哪、哪些寄存器由调用者保存、哪些由被调用者保存、栈怎么对齐、结构体怎么拆进寄存器和栈。ISA 决定「有哪些寄存器」，ABI 决定「哪个寄存器干什么」。同一个 ISA 可以有多套 ABI，Linux 与 Windows 的 x86-64 就不是一套。
:::

::: errata 三份汇编的四个误解
1. **「同一段 C 的汇编是唯一的」**——编译器、版本、优化级别都会改寄存器分配。本节的 aarch64 就用 clang 与 GCC 拿到了两种写法。
2. **「指令条数一样，代码就一样大」**——8 / 12 / 12，RVC 下 6。
3. **「`ret` 在三套 ISA 上是同一条指令」**——x86 弹栈、ARM64 跳 `x30`、RISC-V 是 `jalr x0,0(ra)`。
4. **「改改寄存器名就能把 x86 汇编搬到 ARM64」**——真实结果是 `unknown token in expression`，连汇编都过不去。
:::

### 1.14.3 小结

① 三份汇编的加法部分几乎一样，差别在参数与返回值寄存器、以及返回地址机制；② x86 靠 `lea` 把「算加法」和「放进返回值寄存器」合成一步，ARM64/RISC-V 靠三操作数原地累加；③ 字节数看指令长度与压缩扩展，条数说明不了大小。如果只记住一件事，那就是：**读陌生架构的汇编，先找「参数从哪进、结果从哪出、返回地址存在哪」，再看算术。**

## 1.14.4 调用约定：三张表 {#sec-1.14.4}

这一节回答：函数调用时「参数放哪、谁负责保存、栈怎么对齐、返回地址谁管」由谁规定？三套 ABI 的表怎么读，才不会把 x86 的规则套到 ARM64 上？

::: preview 先抓住一件事
调用约定可以压成三张表：**参数与返回值、保存责任、栈与返回地址**。最容易搬错的是第 7 个参数的位置——x86-64 只有 6 个整数参数寄存器，第 7 个起在栈上；ARM64 与 RISC-V 有 8 个，第 7、8 个还在寄存器里，第 9 个才进栈。
:::

### 表一：参数与返回值

| 项 | x86-64 SysV | AArch64 AAPCS64 | RISC-V psABI |
|:--|:--|:--|:--|
| 整数参数 | `rdi,rsi,rdx,rcx,r8,r9`（6 个） | `x0`–`x7`（8 个） | `a0`–`a7`（8 个） |
| 浮点参数 | `xmm0`–`xmm7` | `v0`–`v7` | `fa0`–`fa7` |
| 返回值 | `rax`（128 位在 `rdx:rax`） | `x0`（`x1:x0`） | `a0`（`a1:a0`） |
| 第 7 个整数参数 | `[rsp+8]` | `x6` | `a6` |
| 第 9 个整数参数 | `[rsp+24]` | `[sp]` | `[sp]` |

拿一个 9 个 `long` 参数的函数验证。x86-64（写作机 clang 22，`-O2 -S`）里读第 7、8、9 个参数的是这三行：

```asm
	movq	24(%rsp), %rax
	movq	16(%rsp), %r10
	movq	8(%rsp), %r11
```

偏移从 `8(%rsp)` 起步，因为 `call` 已经把返回地址压在栈顶，`rsp` 正指着它。AArch64 上第 9 个参数是 `ldr x9, [sp]`，RISC-V 上是 `ld t0, 0(sp)`——第 7、8 个还在 `x6`/`x7`、`a6`/`a7` 里，根本没上栈。

注意 `[sp]` 是**入口时**的位置。函数一旦 `sub sp, sp, #64` 建了帧，同一个参数就变成 `[sp+64]`：VM 上 `gcc -O0 -S` 编出的九参数函数里，前八个 `x0`–`x7` 被 `str` 到 `[sp,56]` 直到 `[sp]`，第 9 个用 `ldr x1, [sp, 64]` 取回。

浮点与整数**分开计数**。`f(double a, long b, double c)` 里，`a` 在 `xmm0`/`v0`/`fa0`，`b` 在 `rdi`/`x0`/`a0`，`c` 在 `xmm1`/`v1`/`fa1`，互不占用名额。

### 表二：保存责任

| 项 | x86-64 SysV | AArch64 AAPCS64 | RISC-V psABI |
|:--|:--|:--|:--|
| 被调用者保存 | `rbx,rbp,r12–r15` | `x19`–`x29` | `s0`–`s11` |
| 调用者保存 | 其余通用寄存器 | `x0`–`x18` | `t0`–`t6`、`a0`–`a7` |
| 栈指针 | `rsp` 必须还原 | `sp` 必须还原 | `sp` 必须还原 |

规则只有一句：**被调用者保存的寄存器，你用了就必须原样还回去；没用到就一个都不用保存。** 所以你常看到有的函数入口有 `push %rbx`，有的一个都没有——那不是偷懒，是它没碰 `%rbx`。

`x30` 要单独说：它不是参数寄存器，是返回地址。AArch64 把它列在「调用者保存」一侧，但非叶函数必须自己存——不存就会在第二次 `bl` 时丢掉自己的返回地址。

### 表三：栈与返回地址

| 项 | x86-64 SysV | AArch64 AAPCS64 | RISC-V psABI |
|:--|:--|:--|:--|
| 栈增长方向 | 向低地址 | 向低地址 | 向低地址 |
| 调用时栈对齐 | 16 字节 | 16 字节 | 16 字节 |
| 返回地址 | 栈（`call` 压入） | `x30`（LR） | `ra`（`x1`） |
| 红区 | `rsp` 以下 128 字节 | 无 | 无 |
| 帧指针 | `rbp`（可选） | `x29`（可选） | `s0`/`fp`（可选） |

红区（red zone）是 x86-64 独有的：`rsp` 以下的 128 字节，叶函数可以直接写，不必先 `sub rsp`，因为信号处理会跳过这一块。ARM64 与 RISC-V 没有这个约定，叶函数想用栈就得先调整 `sp`。

栈对齐 16 字节是硬要求，不是建议。`movaps`、`ldp`/`stp` 这类一次搬 16 字节的指令，在未对齐的地址上会直接异常。

::: def 定义 1.14.4 · 调用约定 {#def-1.14.4}
调用约定（calling convention）是 ABI 里管「函数之间怎么交接」的那部分：参数放哪几个寄存器、多出来的放栈上什么位置、返回值放哪、哪些寄存器由调用者保存、哪些由被调用者保存、栈指针怎么对齐、谁负责把返回地址存下来。它不决定代码快不快，但决定两个编译单元能不能正确连在一起。
:::

::: errata 三张表最容易搬错的四条
1. **「第 7 个参数在三套 ABI 上都在栈上」**——只对 x86-64 成立。ARM64 与 RISC-V 各有 8 个参数寄存器，第 7、8 个在 `x6`/`x7`、`a6`/`a7`，第 9 个才在 `[sp]`。照 x86 的上限写 ARM64 汇编，会把 `g`/`h` 从 `[sp,#32]`/`[sp,#40]` 取，算出来是错的。
2. **「系统调用和函数调用共用同一组参数寄存器」**——x86-64 的 `syscall` 会把返回地址存进 `rcx`、标志存进 `r11`，所以系统调用的第 4 个参数改用 `r10`：`write(fd, buf, n)` 用 `rdi`、`rsi`、`rdx`，再往后的参数才轮到 `r10`。ARM64 与 RISC-V 不受影响，仍是 `x0`–`x5`、`a0`–`a5`。
3. **「ARM64 的返回地址也在栈上」**——在 `x30`。只有函数自己再 `bl` 时才会覆盖，所以只有非叶函数才存它。
4. **「被调用者保存 = 每个函数都保存一遍」**——只有用到才保存。叶函数的入口常常一条 `push` 都没有。
:::

::: ex 例 1.14.4 · 先猜第 9 个参数在哪 {#ex-1.14.4}
一个 9 个 `long` 参数的函数 `f(a,b,c,d,e,f,g,h,i)`，在 x86-64、AArch64、RISC-V 64 上各编译一次。先猜：三套 ABI 里，`g`、`h`、`i` 分别从哪取？如果三者都从栈上取，说明什么？

::: sol 解答
x86-64：只有 6 个整数参数寄存器（`rdi,rsi,rdx,rcx,r8,r9`），`g`、`h`、`i` 都在栈上（入口 `[rsp+8]`、`[rsp+16]`、`[rsp+24]`，因为 `[rsp]` 是返回地址）。AArch64：8 个参数寄存器 `x0–x7`，`g`、`h` 在 `x6`/`x7`，只有 `i` 在栈上（`[sp]`，建帧后 `[sp+32]`）。RISC-V 64：8 个参数寄存器 `a0–a7`，`i` 在 `[sp]`。**三者都从栈上取**才是错的——那正是勘误第 1 条点名的错误，把 x86 的上限套到了 ARM64/RISC-V。
:::
:::

### 1.14.4 小结

① 表一定参数与返回值，表二定保存责任，表三定栈与返回地址；② x86-64 是 6 个整数参数，ARM64 与 RISC-V 是 8 个，第 9 个才进栈；③ 红区与系统调用的 `r10` 是 x86 独有的两处坑。如果只记住一件事，那就是：**先数参数，再查表；表查错，汇编全错。**

::: method 即时自测 · 1.14.4
**Q1（记忆）** 写一个 9 个 `long` 参数的函数，第 7、8、9 个参数在三套 ABI 下分别在哪？

**Q2（辨析）** 一个函数入口有 `push %rbx`，另一个没有。哪个更「守规矩」？

**Q3（应用）** x86-64 上用汇编发起 `write(1, buf, 5)`，几个参数寄存器里各放什么？

**Q4（迁移）** 一份 ARM64 汇编在入口处 `stp x29, x30, [sp, #-16]!`，说明这个函数可能是什么类型？为什么不是每个函数都这样？

::: sol 答案
**A1** x86-64：第 7、8、9 个都在栈上，入口偏移是 `[rsp+8]`、`[rsp+16]`、`[rsp+24]`。AArch64：第 7、8 个在 `x6`、`x7`，第 9 个在 `[sp]`。RISC-V：第 7、8 个在 `a6`、`a7`，第 9 个在 `[sp]`。
**A2** 都对。`%rbx` 是被调用者保存的，用了才需要 `push`；没用到的函数不保存，不违反约定。
**A3** `rax`=1（`write` 的系统调用号），`rdi`=1（fd），`rsi`=`buf` 的地址，`rdx`=5（长度）。只有 3 个参数时用不到 `r10`。
**A4** 说明它可能是非叶函数：`bl` 会覆盖 `x30`，所以要把 `x30`（连同帧指针 `x29`）存到栈上。叶函数不调用别人，`x30` 不会被改，不需要保存。

## 1.14.5 系统调用入口：三种指令 {#sec-1.14.5}

这一节回答：用户态的一条 `write` 怎样跨过特权边界进内核？三套 ISA 的陷入指令、系统调用号与参数寄存器各是什么，为什么 x86-64 的第 4 个参数不放在 `rcx`？

::: preview 先抓住一件事
进内核只要一条指令：x86-64 的 `syscall`、AArch64 的 `svc #0`、RISC-V 的 `ecall`。容易记错的不是指令，而是配套的三张表：**号放哪个寄存器、参数放哪几个寄存器、返回值在哪**。号表是内核 ABI，不是 ISA：`write` 在 x86-64 是 1，在 ARM64 与 RISC-V 是 64。
:::

C 里写 `write(1, "hello", 5)`，glibc 最后做的事不是普通函数调用，而是把号与参数摆进约定的寄存器，再执行一条陷入指令。下面三段是去掉 libc 包装后的最小写法；指令字节是汇编后用 `objdump`/`llvm-objdump` 读出来的。

```asm
# x86-64
    mov    $1, %rax          # SYS_write
    mov    $1, %rdi          # fd
    lea    msg(%rip), %rsi   # buf
    mov    $5, %rdx          # count
    syscall                  # 0f 05
```

```asm
// AArch64
    mov    x8, #64           // SYS_write
    mov    x0, #1            // fd
    adr    x1, msg           // buf
    mov    x2, #5            // count
    svc    #0                // d4000001
```

```asm
# RISC-V 64
    li     a7, 64            # SYS_write
    li     a0, 1             # fd
    la     a1, msg           # buf
    li     a2, 5             # count
    ecall                    # 00000073
```

三套写法逐行对应，只有寄存器名与助记符不同。`svc #0` 里的 0 不是调用号，是立即数；号在 `x8`。`ecall` 没有操作数，号在 `a7`。x86 的 `syscall` 也没有操作数，号在 `rax`。

| 项 | x86-64 | AArch64 | RISC-V 64 |
|:--|:--|:--|:--|
| 陷入指令 | `syscall`（`0f 05`） | `svc #0`（`d4000001`） | `ecall`（`00000073`） |
| 号寄存器 | `rax` | `x8` | `a7` |
| 参数寄存器 | `rdi,rsi,rdx,r10,r8,r9` | `x0`–`x5` | `a0`–`a5` |
| 返回值 | `rax` | `x0` | `a0` |

### 为什么 x86-64 的第 4 个参数是 `r10`

x86-64 的函数调用用 `rcx` 传第 4 个参数，`syscall` 却把它征用了：CPU 执行 `syscall` 时，把下一条指令的地址写进 `rcx`，把 `RFLAGS` 写进 `r11`，以便 `sysret` 返回。内核要读第 4 个参数时，`rcx` 里已经是返回地址，所以 Linux 的系统调用 ABI 把第 4 个参数挪到 `r10`。

拿一个真正有 4 个参数的系统调用 `openat(dirfd, path, flags, mode)` 验证：

```asm
# x86-64，写作机 clang 21 --target=x86_64-linux-gnu -c 后 objdump -d
    mov    $257, %rax        # SYS_openat
    mov    $-100, %rdi       # AT_FDCWD
    lea    path(%rip), %rsi
    mov    $0x241, %rdx      # O_WRONLY|O_CREAT|O_TRUNC
    mov    $0644, %r10       # mode：第 4 个参数只能放 r10
    syscall
```

`mov $0644, %r10` 编成 `49 c7 c2 a4 01 00 00`。如果把 `%r10` 换成 `%rcx`，内核读到的 `mode` 会是 `syscall` 刚写进去的返回地址，创建出来的文件权限自然不对；返回后 `rcx` 又变成用户态的返回地址。`write` 只有 3 个参数，用不到 `r10`，所以「用 `write` 演示第 4 个参数」是个坏例子——它根本走不到那一格。

AArch64 与 RISC-V 没有这个问题：`svc` 与 `ecall` 不占用通用寄存器保存返回地址，参数按 `x0`–`x5`、`a0`–`a5` 顺序摆即可，第 4 个参数就是 `x3`、`a3`。

### 号表：同一件事，两套编号

系统调用号由内核分配。x86-64 维护自己的号表（内核源码里的 `arch/x86/entry/syscalls/syscall_64.tbl`），ARM64 与 RISC-V 遵循 asm-generic 的 `unistd.h`。两套号表在少数调用上碰巧相同，大多数不同：

| 调用 | x86-64 | asm-generic（ARM64 / RISC-V） |
|:--|--:|--:|
| `write` | 1 | 64 |
| `openat` | 257 | 56 |
| `exit` | 60 | 93 |
| `io_destroy` | 207 | 1 |

最后一行是陷阱：ARM64 的 1 是 `io_destroy`，不是 `write`。把 x86-64 的 `mov $1, %rax` 原样搬到 ARM64，调用的不是写文件，而是一个销毁异步 I/O 上下文的调用，通常会以 `-EINVAL` 失败（未实测）。

查号表的办法很简单：在 ARM64/RISC-V 机器上 `grep __NR_write /usr/include/asm-generic/unistd.h`，在 x86-64 机器上看 `asm/unistd_64.h`。但**不要在源码里硬编码数字**：用 `<sys/syscall.h>` 的 `SYS_write`，或者直接调 libc 的 `syscall()`，换架构时让头文件去选号。VM 上实测这两行分别是 `#define __NR_write 64` 与 `#define __NR_io_destroy 1`；x86-64 的号表本机没有 x86 头文件，未在 VM 上复核。

### 系统调用没有第 7 个参数

函数调用里，x86-64 只有 6 个整数参数寄存器，第 7 个起在栈上；ARM64 有 `x0`–`x7` 八个，RISC-V 有 `a0`–`a7` 八个，第 9 个才进栈（1.14.4）。这套规则**不要套到系统调用上**：Linux 的系统调用 ABI 最多 6 个参数，x86-64 用 `rdi,rsi,rdx,r10,r8,r9`，ARM64 用 `x0`–`x5`，RISC-V 用 `a0`–`a5`，没有「第 7 个参数」这回事。参数更多的接口（如 `clone3`）改成传一个结构体指针，由内核按结构体布局读取。

### 返回与错误

内核把结果放在返回寄存器里：成功是非负数，失败是一个落在 `-4095` 到 `-1` 的负 errno。libc 的包装函数会检查这个范围，把它转成 `-1` 并设置 `errno`；你手写汇编时没有这层包装，必须自己判。比如 x86-64 上可以 `cmp $-4095, %rax`，无符号比较大于等于就进错误分支。ARM64 与 RISC-V 同样把负 errno 放在 `x0`、`a0`，只是比较指令不同。

::: def 定义 1.14.5 · 系统调用入口 {#def-1.14.5-entry}
系统调用入口是用户态进入内核的固定约定：一条陷入指令（`syscall`/`svc #0`/`ecall`）、一个放调用号的寄存器（`rax`/`x8`/`a7`）、一组放参数的寄存器、一个放返回值的寄存器，以及「负值即 errno」的错误约定。号表由内核维护，属于内核 ABI；陷入指令与寄存器名字属于 ISA 与平台 ABI。
:::

::: errata 系统调用入口的五个误解
1. **「`write` 的号在哪儿都是 1」**——x86-64 是 1，ARM64/RISC-V 是 64；ARM64 的 1 是 `io_destroy`。
2. **「x86-64 第 4 个参数还是 `rcx`」**——`syscall` 把返回地址写进 `rcx`、标志写进 `r11`，第 4 个参数改用 `r10`。只有 3 个参数的 `write` 看不出这一点。
3. **「系统调用和函数调用共用参数规则」**——函数调用 x86 第 7 个参数在栈上，系统调用最多 6 个参数，根本没有第 7 个；ARM64/RISC-V 的函数调用还有 8 个参数寄存器。
4. **「`svc #0` 的 0 是系统调用号」**——0 是立即数；号在 `x8`。`ecall` 同理，号在 `a7`。
5. **「`syscall` 只改 `rax`」**——它还改 `rcx` 与 `r11`；手写汇编或内联汇编要把这两个寄存器列进 clobber 列表。
:::

### 1.14.5 小结

① 三条陷入指令分别是 `syscall`、`svc #0`、`ecall`，号在 `rax`、`x8`、`a7`；② x86-64 的第 4 个参数是 `r10`，因为 `syscall` 覆盖 `rcx`/`r11`；③ 号表是内核 ABI，ARM64/RISC-V 用 asm-generic，`write` 是 64 不是 1。如果只记住一件事，那就是：**跨架构时先查号表与参数寄存器，别把 x86 的 `rcx` 和 1 一起带过去。**

## 1.14.6 编译到三套架构：工具链与验证 {#sec-1.14.6}

这一节回答：手边只有一台 aarch64 虚拟机和一台 macOS，怎样把同一段 C 变成三种架构的汇编与目标文件？哪些结论能当场验证，哪些只能标「未实测」？

::: preview 先抓住一件事
`-S` 出汇编、`-c` 出目标文件，这两步只要编译器后端；**链接与运行**还要目标平台的 sysroot、启动文件、libc 和链接器。所以本节所有命令都停在 `-c`，验证也只验到「文件是不是那个架构、指令字节对不对」。
:::

### 三条命令，三个来源

| 目标 | 编译器 | 命令 | 能验证到 |
|:--|:--|:--|:--|
| AArch64 | VM 的 GCC 13.3（原生） | `gcc -O2 -S`、`gcc -O2 -c` | 汇编、`.o`、`readelf -h` |
| x86-64 | 写作机 Apple clang 21 | `clang --target=x86_64-linux-gnu -O2 -S/-c` | 汇编、`.o`、`objdump -d` |
| RISC-V 64 | 写作机 Homebrew LLVM 22 | `clang --target=riscv64-linux-gnu -O2 -S/-c` | 汇编、`.o`、`llvm-objdump -d` |

Apple clang 21 的 `--print-targets` 里没有 riscv64，只有 Homebrew 的 LLVM 22 才注册了 `riscv64`。VM 上也没有 `riscv64-linux-gnu-gcc`、没有 `qemu-riscv64`；所以 RISC-V 只能用 clang 22 的 `-S`/`-c`。三个工具链在本环境的使用上限是：**都能出汇编与目标文件；两个交叉目标不能链接，VM 的原生 GCC 能链接，但本节不碰链接与运行**。

### `-S` 与 `-c` 分别给你什么

`-S` 停在汇编：你能读寄存器、比较指令条数，但还没有机器码。`-c` 继续汇编成 ELF 可重定位文件（relocatable），里面有机器码、符号表和重定位项，但外部符号还没解析。`-S` 的文本会随编译器版本变化，`-c` 的机器码只对同一目标与同一 ABI 有意义。

三个目标各编一次 `sum3.c`，`file` 的输出是：

```text
lab1c14_sum3_x86.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
lab1c14_sum3_rv.o: ELF 64-bit LSB relocatable, UCB RISC-V, RVC, double-float ABI, version 1 (SYSV), not stripped
lab1c14_sum3_arm.o: ELF 64-bit LSB relocatable, ARM aarch64, version 1 (SYSV), not stripped
```

`readelf -h`（macOS 上用 `llvm-readelf -h`）把 ELF 头的 `e_machine` 字段译成 `Machine` 名字：

| 目标 | `file` 的架构串 | `Machine` | `e_machine` |
|:--|:--|:--|--:|
| x86-64 | `x86-64` | `Advanced Micro Devices X86-64` | 62 |
| AArch64 | `ARM aarch64` | `AArch64` | 183 |
| RISC-V 64 | `UCB RISC-V` | `RISC-V` | 243 |

这三个编号不是背出来的，是 2026-10-31 在写作机与 VM 上读 ELF 头得到的；`readelf -h` 只显示名字，编号要用脚本或 `od` 读。拿到一个陌生 `.o`，先看这两处，比看文件名可靠。

### 为什么链接一定失败

在写作机上去掉 `-c`、直接给输出文件（要求链接），会得到：

```text
ld: unknown options: --hash-style=gnu --eh-frame-hdr -dynamic-linker ...
clang: error: linker command failed with exit code 1 (use -v to see invocation)
```

表面原因是 macOS 的 `ld` 不认识 GNU 链接选项；深层原因是这台机器上没有目标平台的 sysroot、`crt1.o`、`libc.so` 和动态链接器。`--target` 只改代码生成，不会把一整套 Linux 用户态搬过来。同理，`#include <stdio.h>` 的交叉编译会直接失败：

```text
lab1c14_hello.c:1:10: fatal error: 'stdio.h' file not found
```

所以要练 `-S`/`-c`，示例必须是不带头文件的自由函数；要编真实程序，得装交叉工具链或指定 `--sysroot`。这不属于本环境，标「未实测」。

### 三个检查，按顺序做

1. **看架构**：`file` 或 `readelf -h`，确认 `Machine` 与 `e_machine`。
2. **看指令**：`objdump -d`（x86-64/AArch64）或 `llvm-objdump -d`（RISC-V），核对助记符与字节。
3. **看尺寸**：`readelf -S` 的 `.text` 大小，或最后一条指令的偏移加长度；`size` 的 `text` 还含只读数据与对齐填充，不等于纯指令字节。

第三步在 RISC-V 上有个坑：默认 `rv64gc` 含 C 扩展，`li a0,1`、`li a2,5` 会压成 2 字节，`ecall` 仍是 4 字节。`llvm-objdump` 的输出里偏移会出现 `0、4、6、a、e` 这样的混合序列；如果按固定 4 字节去数，后面全错位。上面 `file` 输出里的 `RVC` 就是在提醒你：这个目标开了压缩指令。

### 不能验的三件事

**链接**：两个交叉目标失败，错误见上；VM 的原生 GCC 能链接 aarch64，但本节的产物都停在 `-c`。**运行**：VM 没有 `qemu-aarch64`/`qemu-riscv64`，macOS 不能执行 ELF；aarch64 产物本来能在 VM 上直接跑，本次也没有跑，所以没有任何运行输出与耗时。**计时与 CPI**：要运行才能测，本节不给数字；跨架构的真实 CPI 见 1.14.8 的「未实测」说明。

::: def 定义 1.14.6 · 交叉编译 {#def-1.14.6-cross}
交叉编译是在一种机器（host）上生成另一种机器（target）的代码。目标三元组（target triple）如 `x86_64-linux-gnu` 固定了 CPU、操作系统与 ABI；编译器后端负责指令选择与寄存器分配，sysroot 负责提供目标平台的头文件、库、启动文件与动态链接器。只有后端、没有 sysroot，最多做到 `-S`/`-c`。
:::

::: errata 工具链的五个误解
1. **「`clang --target` 就是交叉工具链」**——它只换后端；没有 sysroot、`crt1.o`、`-lc` 与目标链接器，链接一定失败。
2. **「`-c` 成功就说明能跑」**——`.o` 是可重定位文件，符号未解析、没有入口、没有动态链接器；能不能跑还要看链接与内核。
3. **「同一段 C 的汇编是唯一的」**——编译器、版本、优化级别都会改寄存器分配与指令选择；本节三份只是各自工具链的产物。
4. **「`file` 说是 x86-64 就能在 macOS 上跑」**——`file` 只报架构与格式；这是 ELF，macOS 要 Mach-O，格式不对照样不能执行。
5. **「macOS 上有 `readelf`」**——没有；用 Homebrew LLVM 的 `llvm-readelf`，或者在 Linux VM 上读。
:::

### 1.14.6 小结

① `-S` 出汇编、`-c` 出目标文件，两者都只依赖编译器后端；② 链接与运行需要 sysroot、目标 libc 与链接器，本环境做不到；③ 验证顺序是 `file`/`readelf -h` 看架构，再 `objdump -d` 看字节。如果只记住一件事，那就是：**能出汇编不等于能跑，先看 ELF 头，再看指令字节。**

## 1.14.7 时钟与功耗：一条指令的时间下限 {#sec-1.14.7}

这一节回答：一条指令最快能多快执行完？主频为什么停在 5 GHz 附近，而不是继续翻倍？

::: preview 先抓住一件事
一条指令的时间下限是一个时钟周期 $T_{\text{clk}}$；$T_{\text{clk}}$ 由最长组合路径加上几笔物理税决定：触发器延迟、门延迟、建立时间、时钟偏斜与抖动。频率上不去，一半是路径太长，一半是电压不能再降——动态功耗随 $V^2 f$ 走，漏电还随电压与温度涨。
:::

### 关键路径决定周期

一条 `add` 要走完「读寄存器 → 过 ALU → 写回」。寄存器由时钟沿驱动，输出要等 $T_{\text{cq}}$ 才稳定；ALU 的门一级级延迟；写回的数据必须在下一个时钟沿前 $T_{\text{setup}}$ 时间稳定。再加上时钟树到达不同触发器的时间差（skew）和电源噪声造成的周期抖动（jitter），得到：

$$
T_{\text{clk}} \ge T_{\text{cq}} + T_{\text{logic,max}} + T_{\text{setup}} + T_{\text{skew}} + T_{\text{jitter}}.
$$

$T_{\text{logic,max}}$ 是关键路径上所有门与连线的延迟之和。想提频，只能缩短它（加深流水线、改电路）或换更快的工艺。加深流水线会把一条指令拆成更多级，频率上去了，但分支误预测时要清空更多级（1.14.8）；换工艺会降低电压与门延迟，但漏电占比上升。

手算一个 7 nm 核：$T_{\text{cq}}=30$ ps、关键路径 14 级 FO4（每级 9 ps，共 126 ps）、连线 40 ps、$T_{\text{setup}}=20$ ps、skew 15 ps、jitter 10 ps，则

$$
T_{\text{clk}} \ge 30+126+40+20+15+10 = 241\ \text{ps},\qquad f_{\max} \le 4.15\ \text{GHz}.
$$

这是**算式示例**：换一组门延迟，结果就变。它只说明数量级——一条指令的下限在几百皮秒，对应几个 GHz。

### 工艺、电压与频率

| 工艺节点 | FO4 反相器延迟 | 典型 Vdd | 可持续 $f_{\max}$ | 漏电占动态功耗 |
|:--|--:|--:|--:|--:|
| 28 nm | 20–25 ps | 0.9–1.0 V | 2.5–3.5 GHz | 10–20% |
| 16 nm | 12–16 ps | 0.8–0.9 V | 3.5–4.5 GHz | 20–30% |
| 7 nm | 8–10 ps | 0.75–0.85 V | 4.2–5.0 GHz | 25–40% |
| 5 nm | 6–8 ps | 0.70–0.80 V | 4.8–5.5 GHz | 30–45% |
| 3 nm | 5–7 ps | 0.65–0.75 V | 5.2–6.0 GHz | 35–50% |

**数字来源与口径**：这张表是公开工艺评述与厂商产品规格的数量级，不是本书实测；不同标准单元库、电压点、温度会让结果偏移 20% 以上。工艺节点名也不是同一个物理量：Intel 7、TSMC N7、Samsung 7LPP 的命名并不等价，不能按「7」这个数字直接比频率。

表里有两件事：FO4 延迟从 28 nm 到 7 nm 降了一半多，从 7 nm 到 3 nm 只再降三四成；电压在 1 V 附近降不动，动态功耗却与 $V^2$ 成正比。Dennard 缩放在 2000 年代中期失效，指的就是电压与电流不能随尺寸等比缩小、功耗密度反而上升；主频停在 5 GHz 附近、转向多核，是这道账的结果。

### 功耗的两笔账

$$
P_{\text{total}} = \underbrace{\alpha C_{\text{eq}} V^2 f}_{\text{动态}} + \underbrace{I_{\text{leak}} V}_{\text{静态}}.
$$

动态功耗来自翻转的电容：$\alpha$ 是每周期真正翻转的电容比例，$C_{\text{eq}}$ 是等效电容；静态功耗是漏电，不翻转也在耗。举例：3 GHz、1.0 V、200 nF、$\alpha=0.1$ 的芯片，动态功耗是 $0.1 \times 200\,\text{nF} \times 1^2 \times 3\,\text{GHz} = 60$ W；漏电按动态功耗的 25% 计（15 W），总功耗 75 W。电压降到 0.85 V，动态功耗约 43 W；频率下调时降得更多。

只降频，动态功耗线性下降，静态功耗不变，漏电占比反而上升；同时降压，动态功耗按平方下降。但电压一低，门延迟变大，$f_{\max}$ 也跟着掉，所以 DVFS（动态电压频率调节）必须把电压与频率成对调。时钟树要驱动全芯片触发器，公开资料给的量级是动态功耗的 20–40%，clock gating 关的就是这部分。

### 一条指令的时间下限，不等于程序的快慢

$T_{\text{clk}}$ 只是单条指令在流水线一级里的下限。依赖链上的 `add` 可能每周期退休一条，但一次除法、一次 cache miss 要几十到几百个周期，真实快慢由 CPI 与命中率决定（1.14.8、1.14.10）。看到「4 GHz」不要直接换算成「一条指令 0.25 ns」：那是理想吞吐上限，不是实测延迟。

### 实验 1.14.A：频率与 IPC（未实测）

先看机器报什么：`lscpu`、`/proc/cpuinfo` 的 `cpu MHz`、`cpupower frequency-info`（装了才有）也能给线索，但 `cpu MHz` 是瞬时采样，turbo 只维持很短时间。要测周期数，标准工具是 `perf stat -e cycles,instructions`。本环境跑 `perf stat true`，`cpu-cycles` 一栏显示 `<not supported>`——虚拟机没有暴露性能计数器，所以**本节没有任何实测频率或 CPI**。

没有 `perf` 时：用 `clock_gettime(CLOCK_MONOTONIC)` 包住固定的依赖链循环，记录总时间与迭代次数，算每次迭代的纳秒数，乘以频率、除以展开后的指令条数，估 CPI。这个数混了频率与 IPC，不能单独当频率；要固定指令条数、防止循环被优化掉，并对照 `cpu MHz`。判读比数字重要：`cpu MHz` 随负载升高说明 turbo 在工作；时间随数据规模跳变，先怀疑 cache。

::: def 定义 1.14.7 · 关键路径与时钟周期 {#def-1.14.7-clk}
关键路径（critical path）是组合逻辑中从输入到输出延迟最长的那条路径；时钟周期 $T_{\text{clk}}$ 必须不短于它加上触发器与时钟开销，频率 $f=1/T_{\text{clk}}$。关键路径决定的是「一条指令最早多久能完成一级」，不是程序的整体速度；后者还要乘上 CPI。
:::

::: errata 时钟与功耗的五个误解
1. **「主频越高越快」**——只在同一微架构、同一指令流下成立。新架构在整数负载上可以打赢频率更高的老架构；跨架构比 GHz 没有意义。
2. **「TDP 就是最大功耗」**——TDP 是散热设计参考值。Intel 的 PL1/PL2、AMD 的 PPT 都允许短时间超过 TDP，持续时间由固件与温度决定。
3. **「工艺节点越小，频率一定越高」**——节点主要提升密度与能效；互连电阻、漏电、散热可能让频率不升反降。
4. **「降频一定省电」**——只降频不降压，静态功耗占比上升；同时降压才按 $V^2$ 显著省电。
5. **「标称频率就是持续频率」**——加速频率通常只维持很短时间，全核持续频率更低；看冷却与功耗墙。
:::

### 1.14.7 小结

① $T_{\text{clk}}$ 由触发器延迟、关键路径、建立时间、skew 与 jitter 相加得到，$f_{\max}=1/T_{\text{clk}}$；② 工艺越小、电压越低，频率上限越高，但漏电与功耗密度会反噬；③ 动态功耗按 $V^2 f$ 走，降压比只降频有效。如果只记住一件事，那就是：**频率是路径长度与电压共同定的物理上限，不是厂商的意愿。**

## 1.14.8 五级流水线：理想 CPI 与真实惩罚 {#sec-1.14.8}

这一节回答：5 级流水线跑 5 条指令为什么只要 9 个周期？真实程序的 CPI 为什么总大于 1，多出来的部分从哪来？

::: preview 先抓住一件事
理想情况下，$n$ 条指令在 $k$ 级流水线上要 $k+(n-1)$ 个周期，$n$ 很大时 CPI 趋近 1；真实 CPI 是 $1+\text{stalls}/n$，停顿来自结构、数据、控制三类冒险。**分支误预测一次十几拍，cache miss 一次上百拍**，它们才是 CPI 的大头。
:::

### 流水线图与理想公式

经典五级流水把一条指令拆成 IF（取指）、ID（译码）、EX（执行）、MEM（访存）、WB（写回）。相邻指令在不同级重叠：

```text
周期      1   2   3   4   5   6   7   8   9
I1       IF  ID  EX  MEM  WB
I2           IF  ID  EX  MEM  WB
I3               IF  ID  EX  MEM  WB
I4                   IF  ID  EX  MEM  WB
I5                       IF  ID  EX  MEM  WB
```

`n` 条指令、`k` 级流水、无停顿的理想周期数是 $k+(n-1)$。5 条指令 9 个周期，1000 条指令 1004 个周期，CPI 是 1.004；同样 1000 条指令非流水线要 5000 个周期，加速比 4.98，极限是 5。公式：

$$
\text{cycles} = k + (n-1) + \text{stalls},\qquad \text{CPI} = 1 + \frac{\text{stalls}}{n}.
$$

`stalls` 是流水线停顿的总周期数。理想 CPI 是 1，只说明「每级都能接上下一条」；任何一级等不到数据、取指被分支打断，都会把 1 抬高。

### 三类冒险，三种停顿

| 冒险 | 典型场景 | 代价（拍） | 主要解法 |
|:--|:--|--:|:--|
| 结构 | 取指与访存抢同一端口；除法器只有一个 | 1–n | 分离 I/D cache、多端口、增加执行单元 |
| 数据 RAW | `add %rax,%rbx` 后紧跟 `mov %rbx,%rcx` | 0（转发）或 1–2 | 转发、暂停、编译器调度 |
| 数据 load-use | `mov (%rdi),%rax` 后立刻用 `%rax` | 1 | 提前加载、重排、软件流水 |
| 控制 | 条件分支结果未出 | 15–20 | 分支预测、延迟槽、谓词执行 |
| WAW/WAR | 寄存器复用 | 0（重命名后消失） | 寄存器重命名（1.14.9） |

表中的代价是公开微架构资料的典型量级（Intel 优化手册、Agner Fog 的微架构文档），不是本机实测；同一类冒险在不同 CPU 上可以差几拍。转发（forwarding）把 EX 的结果直接送到下一条的 EX 输入，所以大多数 RAW 不用停；但 load 的数据要到 MEM 末尾才可用，下一条若在 EX 就要用，只能停一拍。编译器把加载尽量提前，就是在填这一拍。

### 分支预测：把控制冒险压到几个百分点

分支预测的基本单位是 2 位饱和计数器：四个状态（强不跳、弱不跳、弱跳、强跳）按实际方向每次移动一格，只有跨过中点才改变预测。两位状态让循环边界只错两次（进入与退出），而不是每次迭代都错。现代处理器用 TAGE/ITTAGE 一类的多表历史预测器，把全局分支历史哈希进多个表，公开资料给出的准确率是 97–99%；返回地址栈（RSB）专门预测 `ret`。

把准确率代进 CPI：设分支占 20%，误预测惩罚 15 拍，则

| 预测准确率 | 误预测率 | 额外 CPI | 总 CPI |
|--:|--:|--:|--:|
| 99% | 1% | 0.030 | 1.03 |
| 95% | 5% | 0.150 | 1.15 |
| 90% | 10% | 0.300 | 1.30 |
| 80% | 20% | 0.600 | 1.60 |

这张表是**算术结果**，不是实测：额外 CPI = 分支占比 × 误预测率 × 惩罚。它说明两件事。第一，准确率从 99% 掉到 90%，CPI 从 1.03 涨到 1.30，慢约 26%；分支密集的代码对预测器格外敏感。第二，把误预测率从 5% 压到 1%，CPI 从 1.15 降到 1.03，快约 12%——收益不如前一条的损失大。优化要挑「占比大、惩罚重」的那一项，而不是盲目追求 99.9%。

### 真实 CPI：未实测，只能给判读方法

真实 CPI 要用性能计数器测。标准命令是 `perf stat -e cycles,instructions,branches,branch-misses ./prog`：CPI = `cycles / instructions`，分支 MPKI（每千条指令的误预测数）= `branch-misses / instructions × 1000`。本环境跑 `perf stat true`，`cpu-cycles` 一栏显示 `<not supported>`——虚拟机没有暴露性能计数器，所以**本节没有真实 CPI 读数**，上面所有 CPI 都是公式推出来的。

没有 `perf` 时，只能退一步：用 `clock_gettime(CLOCK_MONOTONIC)` 计时，用 `objdump -d` 数出循环体的指令条数，再用「时间 × 频率 ÷ 指令条数」估 CPI；频率取下界时结果偏小。这个值同时混进了频率、cache 与调度噪声，只能做同一台机器、同一输入下的相对比较；跨机器比较没有意义。判读经验（公开资料与工程常识，不是本机实测）：标量单发射的 CPI 通常在 1 附近；多发射/SMT（同时多线程）可以小于 1；CPI 到 2 以上，先怀疑 cache miss 与分支误预测，再怀疑前端取指。一次 DRAM 访问的延迟是几十纳秒，按 3 GHz 折算就是上百拍——这就是「cache miss 一次上百拍」的来源。

::: def 定义 1.14.8 · CPI 与 IPC {#def-1.14.8-cpi}
CPI（cycles per instruction）是平均每条指令花掉的时钟周期数，IPC 是它的倒数。理想标量流水线的 CPI 趋近 1；多发射、SMT 下可以小于 1。CPI 把频率之外的停顿折算成一个数，是比较两版代码、两种编译选项时最直接的口径。
:::

::: errata 流水线与分支预测的五个坑
1. **「CPI 一定 ≥ 1」**——多发射、SMT 下 CPI 可以小于 1；IPC 才是更直观的指标。
2. **「误预测惩罚等于流水线级数」**——还要加上前端重取、BTB（分支目标缓冲）缺失、指令 cache miss；实际惩罚可能比级数更大。
3. **「分支预测器看源码里的 `if`」**——它看指令地址与历史；同一段代码换一份数据分布，命中率可以完全不同。
4. **「转发能消除所有数据冒险」**——load-use 仍需停一拍；转发解决的是 ALU 结果，不是内存结果。
5. **「`__builtin_expect` 能显著提速」**——它主要影响代码布局与内联，现代预测器会自己学习；没有 profiler 指导时乱标可能让热路径变冷。
:::

### 1.14.8 小结

① 理想周期是 $k+(n-1)$，$n$ 大时 CPI 趋近 1；② 真实 CPI 是 $1+\text{stalls}/n$，停顿来自结构、数据、控制三类冒险；③ 分支误预测十几拍、cache miss 上百拍，是 CPI 的主要来源。如果只记住一件事，那就是：**先算理想周期，再把每类停顿折算成 CPI，别把「流水线五级」当成「每条指令一拍」。**

## 1.14.9 乱序执行：窗口、重命名与依赖链 {#sec-1.14.9}

这一节回答：CPU 在等一次 cache miss 时，凭什么还能继续执行后面的指令？为什么把一条累加链拆成四条，程序就能快几倍？

::: preview 先抓住一件事
乱序执行把「按程序顺序取指、按程序顺序退休」与「操作数就绪就发射」分开：窗口（ROB）决定能看多远，寄存器重命名消除假依赖，真正卡住并行的是 RAW 依赖链的长度。
:::

顺序流水线遇到一条 load miss，后面所有指令都得等。乱序处理器改了两件事：一是指令进入后端后不再按序执行，谁的操作数齐了谁先算；二是退休仍按程序顺序，异常、中断和别的核看到的寄存器状态与顺序执行一样。类似餐厅：前台按号收单，后厨谁的材料先到谁先炒，但出餐必须按号。

窗口有多大？下表是 Skylake 级微架构的公开数字（Intel 优化手册、Agner Fog 文档的量级），**只当量级，不是本机读数**；不同代际差几十项很常见。

| 结构 | 作用 | 量级 | 满了会怎样 |
|:--|:--|--:|:--|
| ROB（重排序缓冲区） | 按序退休 | 200 余项 | 停止取指 |
| 保留站 | 等操作数 | 约 100 项 | 发射受限 |
| 物理寄存器 | 重命名 | 数百个 | 重命名停顿 |
| load/store 缓冲 | 乱序访存 | 各数十项 | 访存阻塞 |

ROB 是「窗口」的本体：它记录所有在途指令，退休指针只能从头走。窗口填满，前端就得停；窗口越大，越能盖住一次长延迟。这也是为什么一次 DRAM 访问（上百拍）会吃掉大半个窗口。

重命名解决的是假依赖。`mov %rbx,%rax` 之后再 `mov %rcx,%rax`，两条都写 `%rax`，按名字看是 WAW，但后一条并不需要前一条的值。处理器给每次写分配新的物理寄存器，两条各写各的，WAW/WAR 就消失了。剩下的是 RAW：后一条真要读前一条的结果，这条链只能等。

看一个具体循环：

```c
for (int i = 0; i < n; i++) sum += a[i];
```

若 `sum` 是 `float`，每次加法要等上一次的 4 拍（公开微架构资料里浮点加法延迟的量级），一条链的吞吐只有 0.25 条/拍。改成四个累加器：

```c
float s0=0,s1=0,s2=0,s3=0;
for (int i = 0; i < n; i += 4) {
    s0 += a[i]; s1 += a[i+1]; s2 += a[i+2]; s3 += a[i+3];
}
sum = (s0+s1)+(s2+s3);
```

四条链互不依赖，可以同时在 4 拍后各出一个结果，平均 1 条/拍；若机器每拍能发射 2 条浮点加，拆到 8 条链才能吃满。这不是编译器的魔法，是把「延迟受限」改成「吞吐受限」：**先看瓶颈是链长还是宽度，再决定拆几条。**

::: def 定义 1.14.9 · 指令级并行 {#def-1.14.9-ilp}
指令级并行（instruction-level parallelism，ILP）是同一时刻能重叠执行的指令数。它受两件事限制：程序里有多少条互不依赖的指令（真依赖链），以及机器窗口、发射宽度、执行单元有多少（资源）。重命名能消掉假依赖，消不掉真依赖。
:::

::: errata 乱序执行的四个坑
1. **“乱序执行会改变结果”**——退休按序，异常按序，架构状态与顺序执行一致；被重排的只是内部时序。
2. **“有乱序就不用管依赖”**——RAW 仍然串行；链表遍历、指针追逐、单累加器都是延迟受限，拆链才有用。
3. **“窗口越大越好”**——窗口大能盖住更多 miss，但功耗、面积与验证成本都上升；服务器与手机的取舍不同。
4. **“`volatile` 能让循环更快”**——它禁止编译器合并与重排访问，通常更慢，也不解决硬件依赖。
:::

### 1.14.9 小结

① 乱序 = 乱序发射 + 按序退休，窗口（ROB）决定能看多远；② 重命名消掉 WAW/WAR，RAW 依赖链仍要串行；③ 把一条长链拆成几条短链，是把延迟受限改成吞吐受限。如果只记住一件事，那就是：**先找依赖链，再谈发射宽度；链不拆，窗口再大也白搭。**

**A1** ROB 记录在途指令、保证按序退休；保留站让操作数就绪的指令先发射。退休按序，异常与中断才能看到确定的架构状态。
**A2** 名字上是 WAW，实际没有数据流动；重命名后写不同物理寄存器，不用等。
**A3** 4 条链每条 4 拍出一个结果，合计 1 条/拍；要吃满 2 条/拍，需要 8 条链。
**A4** 窗口项数与「能盖住多少拍」不是一回事：还取决于每项占用时间、发射宽度、miss 是否阻塞 ROB 头部，以及具体微架构；公开数字只能给量级。
:::
:::

## 1.14.10 Cache 地址拆分与 AMAT：手算一个组相联缓存 {#sec-1.14.10}

这一节回答：给一个地址，怎样判断它落在哪一组、和谁抢同一个位置？一次访存平均要多少拍，降缺失率和降命中时间哪个更划算？

::: preview 先抓住一件事
组相联缓存的地址拆成 `tag | index | offset` 三段：offset 选块内字节，index 选组，tag 用来比对。AMAT 把每层「命中时间 + 缺失率 × 下一层代价」串起来，缺失率的收益会被下一层代价放大。
:::

先声明口径：下面这组缓存参数是**题设**，不是本机读数。虚拟机通常不透传 cache 几何，`getconf` 读到的数字不能当成物理 L1 的真值；要拿真机参数，得在物理机上看 `getconf -a | grep LEVEL1_DCACHE` 或查 CPU 厂商文档。题目本身只需要容量、相联度、块大小三个数。

设 L1 数据缓存 32 KiB、8 路组相联、块 64 B，虚拟地址 48 位。组数由容量除以「每组的字节数」：

$$
\text{sets}=\frac{32\,\text{KiB}}{8\times 64\,\text{B}}=64,\quad
\text{offset}=\log_2 64=6,\quad
\text{index}=\log_2 64=6,\quad
\text{tag}=48-6-6=36.
$$

三个字段各管一件事：offset 决定访问落在 64 B 块里的哪个字节，6 位正好覆盖 0–63；index 决定去哪个组查，64 组需要 6 位；剩下的高位是 tag，用来确认组里的这一块是不是你要的地址。所谓「8 路」，就是每个组并排放 8 个 tag 比较器，一次可以同时比对 8 个块。

地址从高到低是 `tag(36) | index(6) | offset(6)`。拿 `0x0000_7fff_1234_5678` 手算：

| 字段 | 算法 | 结果 |
|:--|:--|:--|
| offset | `0x678 & 0x3f` | `0x38`（56） |
| index | `(0x678 >> 6) & 0x3f` | 25 |
| tag | 地址 `>> 12` | `0x7fff12345` |

同一个组的地址只要求 index 相同，也就是低 12 位里的第 6–11 位相同。下面三个地址都落在组 25：

| 地址 | 低 12 位 | tag | 关系 |
|:--|:--|:--|:--|
| `0x7fff12345678` | `0x678` | `0x7fff12345` | 基准 |
| `0x7fff12346678` | `0x678` | `0x7fff12346` | +4 KiB，同组不同 tag |
| `0x7fff12349678` | `0x678` | `0x7fff12349` | +16 KiB，同组不同 tag |

8 路意味着一个组只能放 8 个 tag。若程序同时顺序扫描 9 个相距 4 KiB 的数组，第 9 个流会把最早进入的 tag 挤掉，之后每次访问都 miss——容量明明够，却因映射到同一组而用不上，这叫**冲突缺失**。把数组间距改成 4 KiB + 64 B，或把 9 个流分块处理，就能错开组号。

平均访存时间按层展开：

$$
\text{AMAT}=t_{L1}+m_{L1}\left(t_{L2}+m_{L2}\left(t_{L3}+m_{L3}t_{\text{DRAM}}\right)\right).
$$

设 L1 命中 4 拍、局部缺失率 5%；L2 命中 12 拍、局部缺失率 20%；L3 命中 40 拍、局部缺失率 10%；DRAM 200 拍：

$$
\text{AMAT}=4+0.05\left(12+0.2\left(40+0.1\times200\right)\right)
=4+0.05\times24=5.2\ \text{拍}.
$$

做两次灵敏度：L1 缺失率从 5% 降到 2%，AMAT 变成 $4+0.02\times24=4.48$ 拍，快约 14%；L2 命中时间从 12 拍降到 8 拍，AMAT 变成 $4+0.05\times20=5.0$ 拍，只快约 4%。**降缺失率通常比降命中时间划算**，因为括号里的 24 拍会被缺失率整倍放大。这两个百分比都是相对 5.2 拍算的，换一组命中时间比例会变，但「缺失率更划算」的结论不变。

::: def 定义 1.14.10 · AMAT 与局部缺失率 {#def-1.14.10-amat}
AMAT（average memory access time）是一次访存的平均延迟：第一层命中时间，加上「本层缺失率 × 下一层代价」，逐层递归。式中的缺失率必须是**局部缺失率**（本层 miss 数 / 本层访问数），不是「miss 数 / 总指令数」的全局缺失率；混用会把 AMAT 算小。
:::

::: errata Cache 手算的五个坑
1. **“这组参数是本机读数”**——容量、相联度、块大小是题设；VM 不透传缓存几何，换机器要重新取数，不能把 32 KiB/8 路当通用事实。
2. **“cache line 一定是 64 B”**——x86 常见 64 B，部分 ARM64 是 128 B；块大小一变，offset 位数与组数都变。
3. **“用虚拟地址算出的组号就是物理组号”**——VIPT 缓存用虚拟地址低位做 index，但受页大小与别名限制；真实索引最终由物理地址决定。
4. **“两个数组就会冲突”**——8 路要 9 个同组流才发作；2 个流只是占两个 way。
5. **“L2 命中说明 L3 有副本”**——L3 可能是非包含或排他的，L2 有数据不代表 L3 有。
:::

::: method 实验 1.14.B · 用 stride 看组冲突（选做）
分配一个远大于 L3 的 `int` 数组，用 1、16、1024、8192 四种 stride 扫描，记录 `ns/elem`；若某个 stride 明显变慢，先怀疑同组冲突。注意 `1u << 26` 个 `int` 是 256 MiB，不是 64 MiB。VM 不透传几何、`perf` 不可用，所以只记时间差，不报 miss 数。
:::

::: ex 例 1.14.10 · 先猜一组地址落在哪 {#ex-1.14.10}
缓存：容量 32 KiB、8 路组相联、块 64 B、32 位地址。先猜：组数、index 位数、offset 位数、tag 位数各是多少？地址 `0x0000A5C8` 的 index 与 tag 是多少？

::: sol 解答
组数 `S = 32768/(8×64) = 64`，index 6 位，offset 6 位，tag = 32−6−6 = 20 位。`0xA5C8` 的低 6 位是 offset：`0xC8 & 0x3F = 0x08`；接下来 6 位是 index：`(0xA5C8 >> 6) & 0x3F = 0x17`（十进制 23）；剩下的高位是 tag：`0xA5C8 >> 12 = 0xA`。判读顺序是「先 offset、再 index、最后 tag」——写反了就会把 tag 当组号。
:::
:::

### 1.14.10 小结

① 组数 = 容量 /（块大小 × 相联度），地址拆成 `tag | index | offset`；② 同组地址只要求 index 相同，9 个同组流才会把 8 路挤爆；③ AMAT 逐层展开，缺失率的收益被下一层代价放大。如果只记住一件事，那就是：**先算组数，再算 AMAT；缺失率比命中时间更值得优化。**

::: method 即时自测 · 1.14.10
**Q1（记忆）** 32 KiB、8 路、64 B 的缓存有多少组？48 位地址的 tag/index/offset 各几位？

**Q2（辨析）** 地址 `0x7fff12346678` 与 `0x7fff12345678` 在同一个组吗？它们的 tag 相同吗？

**Q3（应用）** 按题设的命中时间与缺失率，把 L1 缺失率从 5% 降到 2%，AMAT 从 5.2 拍降到多少？快多少？

**Q4（迁移）** 为什么 9 个相距 4 KiB 的数组会冲突，而 2 个不会？改间距为什么能缓解？

::: sol 答案
**A1** 组数 = 32 KiB / (8 × 64 B) = 64；offset 6 位、index 6 位、tag = 48 − 12 = 36 位。
**A2** 在同一个组：两者低 12 位都是 `0x678`，index 都是 25。tag 不同，分别是 `0x7fff12345` 与 `0x7fff12346`，所以是同一组里的两个不同块。
**A3** $4+0.02\times24=4.48$ 拍，从 5.2 拍降约 14%；因为 24 拍的下一层代价被整倍缩小。
**A4** 4 KiB 间距恰好让 index 相同，8 路能容纳 8 个流；第 9 个流必须挤掉一个，之后交替 miss。改间距改变 index，把 9 个流分散到不同组即可。

## 1.14.11 三架构栈帧：第 7 个参数之后 {#sec-1.14.11}

这一节回答：参数超过 6 个、函数又有局部变量时，三套 ABI 的栈帧如何排布？第 7、8、9 个参数到底在寄存器还是栈上？

::: preview 先抓住一件事
三家的上限不一样：**x86-64 只有 6 个整数参数寄存器**，第 7 个起在栈上；**ARM64 有 8 个（`x0`–`x7`）、RISC-V 有 8 个（`a0`–`a7`）**，第 7、8 个仍在寄存器里，第 9 个才进栈。把三套都按 x86 的 6 个来写，`g`/`h` 就会取错位置，这也是三套 ABI 最容易被互相照抄的一处。
:::

[1.14.4](#sec-1.14.4) 给了六个参数以内的对照。把第 7、8、9 个参数和局部变量一起看，差异才完整：**x86-64 入口时的栈顶第一个字是返回地址，第 7 个参数从 `[rsp+8]` 开始；ARM64/RISC-V 没有栈上的返回地址，第 9 个参数才是入口 `[sp]` 的第一个字。** 三套 ABI 都要求调用点的栈 16 字节对齐，所以带调用的帧大小通常是 16 的倍数。

| 项 | x86-64 SysV | ARM64 AAPCS64 | RISC-V LP64D |
|:--|:--|:--|:--|
| 整数参数寄存器 | 6 个（`rdi,rsi,rdx,rcx,r8,r9`） | 8 个（`x0`–`x7`） | 8 个（`a0`–`a7`） |
| 第 7 个参数 `g` | 入口 `[rsp+8]` | `x6` | `a6` |
| 第 8 个参数 `h` | 入口 `[rsp+16]` | `x7` | `a7` |
| 第 9 个参数 `i` | 入口 `[rsp+24]` | 入口 `[sp]` | 入口 `[sp]` |
| 建帧后 `i` | `[rbp+32]` | `[sp+32]` | `[sp+32]` |
| 返回地址 | 栈（`call` 压入） | `x30` | `ra`（`x1`） |

表里的「建帧后」指下面代码的 32 字节帧；帧一改，偏移全部重算。写作机 clang 21 用 `--target=aarch64-linux-gnu -O0 -S` 编九参数函数，`x0`–`x7` 全部被 `str` 到栈、第 9 个从入口 `[sp]` 取回；x86-64 版本从 `16/24/32(%rbp)` 取 `g`/`h`/`i`。下面手写版本为对照做了简化。这张表只对「按 32 字节建帧」的写法负责；编译器一开优化，参数常被直接留在寄存器或搬到别的槽，`-O0` 才最接近教科书布局。

先看 x86-64：`call` 把返回地址压栈，所以入口 `[rsp]` 是返回地址，`[rsp+8]` 才是 `g`。再执行 `push %rbp`，`rsp` 又减 8；把 `rbp` 设成新的 `rsp` 后，`g`、`h`、`i` 的偏移整体加 8，变成 `16/24/32(%rbp)`。这也是为什么读 `[rbp+8]` 会读到返回地址。ARM64 与 RISC-V 的 `bl`/`call` 只把返回地址放进 `x30`/`ra`，不压栈；第 9 个参数由调用者在自己的栈顶预留 8 字节，所以被调函数入口的 `[sp]` 就是 `i`。函数用 `stp ... [sp,#-32]!` 或 `addi sp,sp,-32` 建 32 字节帧后，`i` 移到 `[sp+32]`；`g`/`h` 始终在 `x6`/`x7`、`a6`/`a7`，根本不占栈槽。寄存器参数不占栈槽，取 `g`/`h` 只是一条寄存器读，不产生访存。

这也解释了「同一个第 9 个参数，为什么偏移都是 `[sp+32]`」：两家都不在栈上放返回地址，建帧大小又相同；一旦帧改成 48 字节，偏移就变成 `[sp+48]`。x86 则还要多算 `push %rbp` 的那 8 字节。所以看反汇编时，先找 `sp` 减了多少、返回地址存在哪，再套偏移；只背一个 `[sp+32]`，换个函数就失效。

同一函数：9 个 `long` 参数 `a`–`i`、两个局部变量 `x`/`y`、一次对 `helper` 的调用。先看参数怎么进栈，再看局部变量和返回地址怎么排：

**x86-64**

```asm
# 入口：[rsp]=返回地址，[rsp+8]=g，[rsp+16]=h，[rsp+24]=i
f:
    pushq   %rbp
    movq    %rsp, %rbp
    subq    $32, %rsp
    movq    %rdi, -8(%rbp)      # local x
    movq    %rsi, -16(%rbp)     # local y
    movq    16(%rbp), %rax      # g
    addq    24(%rbp), %rax      # h
    addq    32(%rbp), %rax      # i
    movq    %rax, %rdi
    call    helper
    addq    -8(%rbp), %rax
    addq    -16(%rbp), %rax
    leave
    ret
```

**ARM64**

```asm
// 入口：g=x6，h=x7，[sp]=i
f:
    stp     x29, x30, [sp, #-32]!
    mov     x29, sp
    str     x0, [sp, #16]       // local x
    str     x1, [sp, #24]       // local y
    add     x0, x6, x7          // g + h
    ldr     x9, [sp, #32]       // i（入口 [sp]，建帧后 +32）
    add     x0, x0, x9
    bl      helper
    ldr     x9, [sp, #16]
    ldr     x10, [sp, #24]
    add     x0, x0, x9
    add     x0, x0, x10
    ldp     x29, x30, [sp], #32
    ret
```

**RISC-V**

```asm
# 入口：g=a6，h=a7，[sp]=i
f:
    addi    sp, sp, -32
    sd      ra, 24(sp)
    sd      a0, 0(sp)           # local x
    sd      a1, 8(sp)           # local y
    add     a0, a6, a7          # g + h
    ld      t0, 32(sp)          # i
    add     a0, a0, t0
    call    helper
    ld      t0, 0(sp)
    ld      t1, 8(sp)
    add     a0, a0, t0
    add     a0, a0, t1
    ld      ra, 24(sp)
    addi    sp, sp, 32
    ret
```

::: errata 第 7 个参数之后最容易搬错的四条
1. **“第 7、8 个参数在三套 ABI 上都在栈上”**——只对 x86-64 成立。ARM64 的 `g`/`h` 在 `x6`/`x7`，RISC-V 在 `a6`/`a7`；只有第 9 个 `i` 在入口 `[sp]`。照 x86 写成 `[sp,#32]`/`[sp,#40]` 读 `g`/`h`，读到的是别的参数或未初始化的槽，结果直接算错。
2. **“ARM64/RISC-V 的返回地址也在栈上”**——在 `x30`/`ra`；只有非叶函数调用别人时，才需要自己把它存进栈；x86-64 的 128 B 红区只属于 x86，另两家不能往 `sp` 以下写。
3. **“x86 的 `[rbp+8]` 是第 7 个参数”**——那是 `call` 压入的返回地址，第 7 个在 `[rbp+16]`；两个偏移差 8 字节，正好是一个返回地址。
4. **“建帧不改变参数偏移”**——`push rbp`、`stp ... [sp,#-32]!`、`addi sp,sp,-32` 都会移动栈指针，取参偏移必须跟着帧大小重算；帧指针 `rbp`/`x29` 只是另一套参照，`sp` 才是真正的锚点。
:::

### 1.14.11 小结

① x86-64 只有 6 个整数参数寄存器，第 7、8、9 个在栈上；② ARM64/RISC-V 各有 8 个，第 7、8 个在 `x6`/`x7`、`a6`/`a7`，第 9 个才在 `[sp]`；③ 返回地址在 x86 的栈里、ARM64 的 `x30`、RISC-V 的 `ra`。第 7、8 个在寄存器，是 ARM64/RISC-V 与 x86-64 最大的结构差异，三家的差别几乎都落在这一格。如果只记住一件事，那就是：**先数「寄存器能装几个」，再算「栈上第几个」，别把 x86 的 6 当成三家通用。**

::: method 即时自测 · 1.14.11
**Q1（记忆）** 9 个 `long` 参数的函数，第 7、8、9 个参数在三套 ABI 下分别在哪里？

**Q2（辨析）** 为什么 ARM64 版本不需要 `ldr x9, [sp, #32]` 去取 `g`？如果写了会取到什么？

## 1.14.12 指令编码：手算三种格式 {#sec-1.14.12}

这一节回答：给定一条汇编，怎样不查汇编器就写出它的字节？三种 ISA 的字段布局差在哪？

::: preview 先抓住一件事
x86-64 是变长编码，一条指令由 opcode、ModR/M、SIB、位移、立即数按需拼接；ARM64 与 RISC-V 是定长 32 位，但字段位置不同：ARM64 把操作数放在固定几位，RISC-V 把立即数打散到多个位段。手算顺序永远是「先定格式，再摆字段，最后拼十六进制」。
:::

本节只做手算，不调用汇编器；工具对答案的办法放在 1.14.14，RISC-V 部分按未实测处理。

先看 **x86-64**。`mov 0x10(%rdi,%rsi,4),%eax` 的字节是 `8b 44 b7 10`，从前往后拆：

| 字节 | 字段 | 位 | 含义 |
|:--|:--|:--|:--|
| `8b` | opcode | — | `MOV r32, r/m32`，方向是从内存读到寄存器 |
| `44` | ModR/M | `01 000 100` | mod=01（disp8）、reg=000（eax）、r/m=100（有 SIB） |
| `b7` | SIB | `10 110 111` | scale=2（×4）、index=110（rsi）、base=111（rdi） |
| `10` | disp8 | `0x10` | 有符号 8 位位移 |

ModR/M 的 mod=01 表示后面跟 1 字节位移；reg=000 是目标 `eax`；r/m=100 不是寄存器，而是告诉 CPU「后面还有 SIB」。SIB 的 scale=2 表示索引左移 2 位，即乘 4；index=110 是 `rsi`，base=111 是 `rdi`。有效地址就是 `rdi + rsi×4 + 0x10`。这条指令没有 REX 前缀，因为三个寄存器都在前 8 个；换成 `r8`–`r15` 就要加 REX。

**ARM64** 的 32 位字从高位到低位固定。`add x0, x0, x1` 的编码是 `0x8B010000`：

| 位 | 字段 | 值 |
|:--|:--|:--|
| 31 | sf | 1（64 位） |
| 30 | op | 0（ADD） |
| 29 | S | 0（不设标志） |
| 28:24 | 固定 | `01011` |
| 23:22 | shift | `00` |
| 21 | 固定 | 0 |
| 20:16 | Rm | 1（`x1`） |
| 15:10 | imm6 | 0 |
| 9:5 | Rn | 0（`x0`） |
| 4:0 | Rd | 0（`x0`） |

拼起来是 `1000 1011 0000 0001 0000 0000 0000 0000`，即 `0x8B010000`。`ldr x0,[x1,#8]` 是 `0xF9400420`：`size=11`（64 位）、`111001`、`opc=01`（load）、`imm12=1`（8 字节偏移按 8 缩放）、`Rn=1`、`Rt=0`。注意 `add x0,x0,#1` 是 `0x91000400`，属于立即数版，字段布局与寄存器版不同，手算前先确定「立即数还是寄存器」。

**RISC-V** 也是 32 位，但六种格式的字段布局不同，立即数的位置尤其不一样：

| 格式 | 字段顺序（高位到低位） | 立即数范围 | 典型指令 |
|:--|:--|:--|:--|
| R | funct7 / rs2 / rs1 / funct3 / rd / opcode | 无 | `add`、`sub` |
| I | imm[11:0] / rs1 / funct3 / rd / opcode | 12 位有符号 | `addi`、`ld`、`jalr` |
| S | imm[11:5] / rs2 / rs1 / funct3 / imm[4:0] / opcode | 12 位有符号 | `sd`、`sw` |
| B | imm[12\|10:5] / rs2 / rs1 / funct3 / imm[4:1\|11] / opcode | 13 位有符号，2 的倍数 | `beq`、`bne` |
| U | imm[31:12] / rd / opcode | 20 位，左移 12 | `lui`、`auipc` |
| J | imm[20\|10:1\|11\|19:12] / rd / opcode | 21 位有符号，2 的倍数 | `jal` |

`add a0,a0,a1` 是 R 型：`funct7=0000000`、`rs2=01011`（`a1`）、`rs1=01010`（`a0`）、`funct3=000`、`rd=01010`、`opcode=0110011`，拼出 `0x00B50533`。`addi a0,a0,1` 是 I 型：`imm=1`、`rs1=01010`、`funct3=000`、`rd=01010`、`opcode=0010011`，得到 `0x00150513`。`sd ra,8(sp)` 是 S 型：`imm[11:5]=0`、`rs2=00001`（`ra`）、`rs1=00010`（`sp`）、`funct3=011`、`imm[4:0]=01000`、`opcode=0100011`，得到 `0x00113423`。B 型的立即数按 `imm[12|10:5|4:1|11]` 打散，`bne a0,a1,+8` 是 `0x00B51463`。

把三套放在一起看，手算的难点不在算术，而在「位从哪边数」。x86 按字节从低地址往高地址写，ModR/M 与 SIB 谁先谁后由 mod 与 r/m 决定；ARM64 与 RISC-V 按 31 到 0 从高到低填，但 RISC-V 的立即数被拆到不相邻的位段。写十六进制时先把 32 位分组，再从高位往低位拼，比从右往左凑更不容易错。三套编码都能用字段表复现，但字段名与位宽不同；背表不如记住「谁在高位、谁是 opcode」。

::: def 定义 1.14.12 · 指令编码 {#def-1.14.12-encoding}
指令编码（instruction encoding）是把汇编指令映射成二进制位的规则：哪些位选寄存器、哪些位放立即数、哪些位是操作码。定长 ISA 的字段位置由手册固定，一条指令就是一个 32 位字；变长 ISA 用 opcode 与后续字节扩展，长度由前缀和 ModR/M 等字段共同决定。
:::

::: errata 指令编码的六个坑
1. **“ModR/M 的 reg 一定是寄存器”**——不少 opcode 把它当扩展操作码；`/0`–`/7` 的数字就是 reg 字段。
2. **“x86 只有 8 个通用寄存器”**——REX.R/X/B 扩展 reg/index/base 的最高位；没有 REX 前缀时只能编码前 8 个。
3. **“ARM64 的 ADD 只有一种编码”**——寄存器版、立即数版、带进位版是不同的编码族，字段布局不一样。
4. **“RISC-V 的立即数是连续的”**——B/J 型把立即数打散，手算必须按位段拼，不能直接左移。
5. **“字节序无所谓”**——x86/ARM64/RISC-V 小端机器上，32 位字面值与内存字节序相反；`0x8B010000` 在内存里是 `00 00 01 8b`。
6. **“RISC-V 指令都是 4 字节”**——开启 C 扩展后，常用指令压缩成 2 字节；反汇编时不能按固定 4 字节切分。
:::

### 1.14.12 小结

① x86-64 是变长编码，按 opcode、ModR/M、SIB、位移、立即数依次拼；② ARM64 是定长 32 位，字段位置固定，先分清寄存器版与立即数版；③ RISC-V 也是 32 位，但六种格式的立即数位置不同，B/J 型要按位段拆。x86 的变长与两家的定长，是这三种格式最根本的差别；手算前先问「这条属于哪个编码族」，这一步不能省。如果只记住一件事，那就是：**先确定格式，再按字段填位，最后才拼十六进制；顺序反了，错一位都看不出来。**

## 1.14.13 RISC/CISC 与内存模型：litmus 实验 {#sec-1.14.13}

这一节回答：同样是「先写自己的变量，再读对方的变量」，为什么在 x86 上可能读到两个 0，而照源码顺序推演这个结果根本不该出现？

::: preview 先抓住一件事
内存模型是 ISA 合同里最不显眼的一条：它不规定代码怎么写，只规定**别的核允许看到什么顺序**。x86 的 TSO 只保住三类顺序，Store→Load 仍可重排；ARM64 与 RISC-V 更松。验证它的标准工具是 litmus 小测试，不是拿一段业务代码碰运气。
:::

RISC 与 CISC 的界线今天已经模糊：x86 前端把变长指令译成 µop，内部很像 RISC；ARM64 也加了复杂寻址与向量指令。真正的差别落在**译码成本、代码密度与生态**上，而不在内存序（多个核各自看到的写操作先后顺序）。x86 平均 3–4 字节一条指令，译码要先切边界；ARM64/RISC-V 定长 4 字节、字段固定，但 RISC-V 的 C 扩展又把常用指令压回 2 字节。这几件事决定「代码多大、译码多难」，与「两个核谁先看见谁的写」是两套独立合同。

**litmus 测试**（litmus test）是几行并发小程序：每个核执行两三条访存，最后检查一组寄存器。它在顺序一致（sequential consistency）下只有一个结果，在弱内存模型下可能多出几个。Dekker 是最小的一例：

```text
初始：X = 0, Y = 0
P0:  X = 1;  r1 = Y
P1:  Y = 1;  r2 = X
```

按顺序一致推：若 `r1=0`，说明 P0 读 `Y` 发生在 P1 写 `Y` 之前；同理 `r2=0` 说明 P1 读 `X` 发生在 P0 写 `X` 之前。再叠上每个核自己的程序顺序，四个事件首尾相接会绕成一个环，所以 `r1=r2=0` 不可能。硬件只要允许其中一次读提前，这个环就断开了。

| 重排 | x86-64（TSO） | ARM64 | RISC-V（RVWMO） |
|:--|:--|:--|:--|
| Load → Load | 禁止 | 允许 | 允许 |
| Load → Store | 禁止 | 允许 | 允许 |
| Store → Store | 禁止 | 允许 | 允许 |
| Store → Load | **允许** | 允许 | 允许 |
| 全屏障 | `mfence` / `lock` 前缀 | `dmb ish` | `fence rw,rw` |

x86 的 TSO（total store order）只保证「写按程序顺序被看见」，读却可以抢在同核前面的写之前完成；Dekker 恰好踩在 Store→Load 上。要排除 `r1=r2=0`，x86 在两次访问之间加 `mfence`，或把 store 换成带 `lock` 的 `xchg`；ARM64 加 `dmb ish`；RISC-V 加 `fence rw,rw`。换成 acquire/release 语义也行，它只约束一个方向，比全屏障便宜。

C11 的写法不绑架构：

```c
#include <stdatomic.h>
static atomic_int x, y, r1, r2;

void p0(void)
{
    atomic_store_explicit(&x, 1, memory_order_relaxed);
    atomic_thread_fence(memory_order_seq_cst);
    r1 = atomic_load_explicit(&y, memory_order_relaxed);
}
```

`p1` 与 `p0` 对称。本机 aarch64 VM 上 `gcc -O2 -S` 给出 `p0` 的形状（只编译，未运行，略去标签与 `.cfi`）：

```text
	str	w1, [x0]        // X = 1
	dmb	ish             // seq_cst 全屏障
	add	x1, x0, 4
	ldr	w1, [x1]        // r1 = Y
	add	x0, x0, 8
	stlr	w1, [x0]        // r1 的 seq_cst 写回
```

那条 `dmb ish` 就是你写在 C 里的 fence 落到指令上的样子：编译器没有把它优化掉，因为原子操作（不可被打断的读改写）与 fence 都不能跨过。

**本机不能跑 x86/ARM 并发 litmus**：没有 x86 运行环境，arm64 也只是虚拟机，虚拟化的调度与时钟不能代表硅片的弱序行为；QEMU 也没装。所以本节只给「x86-TSO / ARM 弱序」的纸面结论与代码形状，不给「跑一百万轮命中几次」的读数。要数字只有两条路：真机 x86 与真机 ARM 各跑 $10^6$–$10^7$ 轮统计；或装 herd7 用架构模型做穷举，`herd7 -model x86tso.cat dekker.litmus`。

::: def 定义 1.14.13 · 内存模型与 litmus {#def-1.14.13}
内存模型（memory model）规定多核程序中一次读能看到哪些写、哪些重排被允许，是 ISA 合同的一部分，和流水线深度无关。litmus 测试是只含少量访存与观察点的并发小程序；它的「允许结果集」由内存模型决定，因此既能暴露重排，也能用来比较两套架构。
:::

::: errata 内存模型的五个坑
1. **「x86 强序，所以不用屏障」**——TSO 仍允许 Store→Load 重排，Dekker 与消息传递都要 `mfence` 或锁定指令。
2. **「`volatile` 是 CPU 屏障」**——它只约束编译器不合并、不缓存该对象的访问，不生成 CPU 屏障，也不保证原子性。
3. **「`dmb ish` 与 `dmb ishst` 可以互换」**——`ishst` 只约束 store，管不住 load 与后续 store 的顺序。
4. **「全部改成 relaxed 更快」**——每放松一处都要证明同步关系，漏一个就是数据竞争；先对了再谈快。
5. **「QEMU 能验证弱内存模型」**——QEMU 用户态不是架构内存模型的参考实现，只能验证程序逻辑。
:::

::: ex 例 1.14.13 · 先猜 litmus 会不会出现 0/0 {#ex-1.14.13}
两个线程各执行「写自己的变量、读对方的变量」（Dekker litmus）。先猜：在 x86-64 与 ARM64 上，两边都读到 0 的结果会出现吗？各需要加什么才能排除？

::: sol 解答
x86-64 的 TSO 允许 Store→Load 重排，所以 `r1==0 && r2==0` 会出现；ARM64 是弱序，更容易出现。排除办法：x86 上加 `mfence`（或把 store 换成 `xchg`），ARM64 上加 `dmb ish`；C11 里用 `seq_cst` 或 `release`/`acquire` 组合。**本机不能跑 x86/ARM 的并发 litmus**（没有 x86 运行环境，arm64 也是虚拟机），这一题只能按内存模型给纸面结论，验证要在真机上跑 `herd7`。
:::
:::

### 1.14.13 小结

① RISC/CISC 的差别在译码、密度与生态，不在内存序；② 内存模型规定「别的核能看见什么顺序」，x86 TSO 仍允许 Store→Load，ARM64/RISC-V 四类都可能；③ 用 litmus 看允许结果、用屏障排除弱行为，本机只能给纸面结论与代码形状。如果只记住一件事，那就是：**判断并发正确性，先问这段代码依赖哪条顺序，再看那条顺序在目标架构上要不要屏障。**

::: method 即时自测 · 1.14.13
**Q1（记忆）** x86-64、ARM64、RISC-V 的全屏障指令各是什么？Dekker 里 `r1=r2=0` 依赖哪一类重排？

**Q2（辨析）** 「x86 是强序，所以两个线程一写一读不用同步」这句话错在哪？把 store 换成 `xchg` 为什么也能排除？

**Q3（应用）** 把 C11 代码里的 `atomic_thread_fence` 删掉、全部用 `relaxed`，在 ARM64 上可能看到什么？在 x86 上呢？

**Q4（迁移）** 同事说「我在 QEMU 里跑了一万轮都没出现，所以 ARM 不会重排」。你怎么回应？给出两种可替代的取证方式。

**A1** `mfence`（或 `lock` 前缀）、`dmb ish`、`fence rw,rw`；依赖 Store→Load 重排。

**A2** TSO 只禁止 Load→Load、Load→Store、Store→Store，Store→Load 仍允许。`xchg` 隐含锁语义，等于在 store 与后续 load 之间插了全屏障。

**A3** ARM64 上两个 relaxed 访问可被重排，`r1=r2=0` 可能出现；x86 上仍有 Store→Load 窗口，同样可能出现，只是概率低。要排除必须加屏障或 acquire/release。

**A4** QEMU 用户态不是内存模型参考实现，没出现不等于不允许；应改用真机多轮统计，或用 herd7 的 `x86tso.cat`/ARM 模型穷举允许结果。

## 1.14.14 三架构实验：从 C 到字节 {#sec-1.14.14}

这一节回答：手边只有 `-S`、`-c`、`readelf` 与 `nm`，怎样把同一段 C 变成三套汇编与三份目标文件，并读出可信的字节数与指令数？

::: preview 先抓住一件事
这组实验只做**静态取证**：编译到汇编与目标文件，数字节、数指令行、读 `Machine`。链接要 sysroot，运行要真机或 QEMU，本机两样都没有，所以本节不写任何运行结果，也不写运行时间。
:::

先解决一个工具问题。VM 的 GNU `objdump -d` 只支持本机 aarch64，反汇编不了 x86-64 与 RISC-V；但 `objdump -h`、`nm`、`readelf` 读的是 ELF 头与符号表，与目标架构无关。这就是只用静态工具也能跨三套架构取证的原因。

**实验 A：同一函数的三套产物。** `sum3.c` 只有一行 `return a + b + c;`：

```bash
for t in x86_64 aarch64 riscv64; do
  clang --target=$t-linux-gnu -O2 -c sum3.c -o sum3-$t.o
  clang --target=$t-linux-gnu -O2 -S sum3.c -o sum3-$t.s
  printf '%-8s text=%s insn=%s\n' "$t" \
    "$(objdump -h sum3-$t.o | awk '/\.text/{print $3}')" \
    "$(awk '/^\t/ && $1 !~ /^\./' sum3-$t.s | wc -l)"
done
```

第二行数的是汇编里的指令行：以制表符开头、又不是 `.` 开头的行；标签、注释与 `.cfi` 指令都不计。这是在 `objdump -d` 不能跨架构时的替代口径。

VM 上 clang 18.1.3 的实测（编译产物，未运行）：

| ISA | 三行汇编 | 指令行 | `.text` 字节 | `e_machine` |
|:--|:--|--:|--:|--:|
| x86-64 | `leaq` / `addq` / `retq` | 3 | 8 | 62 |
| AArch64 | `add x8,x1,x0` / `add x0,x8,x2` / `ret` | 3 | 12 | 183 |
| RISC-V（默认 `rv64gc`） | `add` / `add` / `ret` | 3 | 6 | 243 |

同一段 C、同一个 clang、同样 `-O2`，指令行都是 3，字节数却是 8/12/6：x86 的 `leaq` 3 字节、`addq` 3 字节、`retq` 1 字节；AArch64 三条各 4 字节；RISC-V 默认开 C 扩展，两条 `add` 与 `ret` 各压成 2 字节。**指令条数相同，代码密度不同**，所以两个数要分开数。

再关掉压缩：`clang --target=riscv64-linux-gnu -march=rv64g -O2 -c sum3.c` 之后，`sum3` 回到 12 字节，与 AArch64 持平。只改一个编译选项，字节数就翻倍，说明「默认配置」本身也是实验变量。

**实验 B：读 ELF 的身份。** 不看反汇编，也能确认手里是什么文件：

```bash
readelf -h sum3-riscv64.o | grep -E 'Class|Machine|Type'
od -An -tu2 -j18 -N2 sum3-riscv64.o     # e_machine 字段，偏移 18
```

`Machine` 打印助记名；`od` 读原始两字节，三份产物分别是 62/183/243。`Type: REL` 说明这是可重定位目标文件，不是可执行文件；能不能跑与这个字段无关，与有没有链接、有没有目标机器的内核有关。

**实验 C：函数级的字节。** `size` 给整段 `.text`，含对齐填充；`nm -S --size-sort` 给每个符号的起止差，更接近「这个函数占多少」：

```bash
nm -S --size-sort sum3-x86_64.o
```

这一步也能反过来用：拿到一个陌生的 `.o`，先用 `nm -S` 看符号大小，再决定要不要读反汇编。两个命令都只读文件，不需要目标架构的工具链。

口径边界要写清：**本机不能链接、不能跑**。VM 没有 `riscv64-linux-gnu-gcc`，clang 交叉编译缺 sysroot 头文件（`bits/libc-header-start.h` 找不到），所以 `-c` 只对不依赖 libc 的代码稳定。aarch64 有本机 gcc，链接不是本节的取证目标；本节按「只到静态读数」的口径停在这里，x86 与 RISC-V 的运行一律未实测。

::: errata 跨架构实验的六个坑
1. **「`-S`/`-c` 成功就能链接运行」**——差 sysroot、`crt1.o`、`-lc` 与目标机器的内核；本节只到目标文件。
2. **「`objdump` 什么架构都能反汇编」**——VM 的 GNU binutils 只编入 aarch64；`-h`/`nm`/`readelf` 能读任意 ELF，`-d` 不行。
3. **「`.text` 就是纯指令字节」**——含对齐填充；函数级数字用 `nm -S` 更准。
4. **「`Machine` 号相同就 ABI 相同」**——ELF 只认架构，参数寄存器与系统调用号是 ABI/内核 ABI 的事。
5. **「不同编译器编出来的字节可以横向比」**——GCC 与 clang、不同版本的向量化策略都不同；本节固定同一个 clang。
6. **「RISC-V 指令都是 4 字节」**——默认 `rv64gc` 含 C 扩展，反汇编与数字节都不能按固定 4 字节切。
:::

### 1.14.14 小结

① 跨架构的静态取证靠 ELF 头、符号表与 `-S` 行数，不靠反汇编；② 同一个 clang、同一组选项下，`sum3` 的指令行都是 3，字节数是 8/12/6，差在编码长度与 RVC；③ 链接与运行需要 sysroot 与目标机器，本机没有，相关结论只能标未实测。如果只记住一件事，那就是：**先确认手里是哪个架构的目标文件，再数字节与指令；两件事都不需要能运行。**

## 1.14.15 代码尺寸与性能：同一算法的三套指令账 {#sec-1.14.15}

这一节回答：同一份「数组求和」编译到三套 ISA，各占多少字节、多少条指令？这笔账能说明什么，又不能说明什么？

::: preview 先抓住一件事
只数两个静态量：**字节数**（`nm -S`、`objdump -h`）与**指令行数**（`-S` 后按行过滤）。本机 `perf` 不可用，本节不写运行时间，也不拿跨架构的周期数作比较；先学会记账，再谈快慢。
:::

同一个算法，两种写法：

```c
/* size_lab.c — 同一函数的两种写法 */
long sum_array(const long *a, int n) {
    long s = 0;
    for (int i = 0; i < n; i++) s += a[i];
    return s;
}
long sum_unrolled(const long *a, int n) {
    long s = 0; int i = 0;
    for (; i + 4 <= n; i += 4) s += a[i] + a[i+1] + a[i+2] + a[i+3];
    for (; i < n; i++) s += a[i];
    return s;
}
```

用同一个编译器（VM 上 clang 18.1.3）、同一组选项（`-O2`），只换 target：

```bash
for t in x86_64 aarch64 riscv64; do
  clang --target=$t-linux-gnu -O2 -c size_lab.c -o size-$t.o
  clang --target=$t-linux-gnu -O2 -S size_lab.c -o size-$t.s
  printf '%-8s text=%s insn=%s\n' "$t" \
    "$(objdump -h size-$t.o | awk '/\.text/{print $3}')" \
    "$(awk '/^\t/ && $1 !~ /^\./' size-$t.s | wc -l)"
done
```

实测（编译产物，未运行）：

| ISA / 选项 | `sum_array` | `sum_unrolled` | 整段 `.text` | 指令行 |
|:--|--:|--:|--:|--:|
| x86-64 | 141 B | 221 B | 365 B | 92 |
| AArch64 | 140 B | 364 B | 504 B | 126 |
| RISC-V `rv64gc` | 24 B | 108 B | 132 B | 51 |
| RISC-V `rv64g` | 40 B | 164 B | 204 B | 51 |

先看最直观的一行：RISC-V 的 `rv64g` 与 `rv64gc` 指令行都是 51，字节数却是 204 与 132。**指令条数一样，代码尺寸不同**，差在 C 扩展把常用指令压成 2 字节。反过来，x86 的 `sum_array` 141 字节、AArch64 140 字节，几乎一样，但整段指令行一个是 92、一个是 126；x86 用变长编码把更多工作塞进更少的字节。

不能从这张表直接读出「谁更快」。`sum_unrolled` 在三家都比 `sum_array` 大（221 对 141、364 对 140、108 对 24），它只是把循环开销换成了代码体积；是否更快取决于 `n`、对齐、cache 与分支预测，这些要运行才谈得上，而运行读数不在本节口径内。更要注意 AArch64 的展开版 364 字节：同一个编译器在不同后端做了不同的自动向量化，这个差距是编译器决策，不是 ISA 的优劣。跨架构只比「同一架构两种写法」，或「同一算法三套 ISA 的字节与指令数」；绝对时间与周期数不比。

`size` 的 `text` 是整段，含对齐填充；`nm -S --size-sort` 给每个符号的起止差，更接近「这个函数占多少」。两个数对不上时，以符号大小与地址范围为准：

```bash
nm -S --size-sort size-x86_64.o
```

记账时把三列写在一起：函数名、字节数、指令行。只写一个数，过两天就说不清它是哪个函数、哪组选项；三列并排，换机器时才知道是哪一列变了。同一份代码的两次编译，只要有一列变了，先查 target、`-march` 与编译器版本，不要先怀疑 ISA。

### 原子指令与屏障：三套 ISA 的同一件事 {#sec-1.14.15.1}

| 操作 | x86-64 | ARM64 | RISC-V |
|:--|:--|:--|:--|
| 原子加 | `lock add` | `ldadd`/`ldxr+stxr` | `amoadd.w/d` |
| CAS | `lock cmpxchg` | `cas`/`ldaxr+stlxr` | `amoswap`/`lr+sc` |
| 读-改-写 | `lock xchg` | `swpal` | `amoswap` |
| 全屏障 | `mfence` | `dmb ish` | `fence rw,rw` |
| 读屏障 | `lfence` | `dmb ishld` | `fence r,r` |
| 写屏障 | `sfence` | `dmb ishst` | `fence w,w` |

C11 的 `atomic_compare_exchange_strong` 在 x86 上落 `lock cmpxchg`，ARM64 落 `ldaxr/stlxr` 或 `cas`，RISC-V 落 `lr/sc`；`memory_order_seq_cst` 还要额外的全屏障，`acquire/release` 只需单向屏障。写可移植代码用 `<stdatomic.h>`，不要手写 `volatile`，也不要假设 x86 的 TSO。

原子指令的代价不在指令本身，而在**缓存行（缓存与内存之间搬运的固定块）独占**：多核同时 CAS 同一 cache line 会来回弹跳，吞吐随核数下降。分片计数器、per-CPU 变量、RCU 都是绕开它的办法。本机没有 `perf c2c`，看不见 HITM，只能用「单线程 vs 多线程同地址 CAS」的吞吐对比判断弹跳，而且这属于运行实验，读数不在本节。另一个边界是「不能睡眠」：持锁或原子上下文里不能调用可能睡眠的分配器，否则内核会报 `BUG: sleeping function called from invalid context`。

### 1.14.15 小结

① 代码尺寸看字节、译码压力看指令数，两个量必须分开记；② 同一编译器、同一选项下，三套 ISA 的字节数差在编码长度与压缩扩展，指令数差在编译器后端的向量化决策；③ 静态账只能回答「占多大」，回答不了「跑多快」。如果只记住一件事，那就是：**先数字节与指令，再谈时间；没有运行读数时，不要把代码大小当成性能结论。**

::: method 即时自测 · 1.14.15

**Q2（辨析）** `sum_unrolled` 的字节数比 `sum_array` 大，是否说明它一定更慢？还缺哪些条件才能判断？

**Q4（迁移）** 本机没有 `perf`，你要向同事证明「这段循环的瓶颈在缓存而不是算力」。哪些证据可以给，哪些话不能说？

::: sol 答案
**A1** x86 变长：`leaq` 3 + `addq` 3 + `retq` 1 = 8；AArch64 定长三条各 4 = 12；RISC-V 默认 `rv64gc` 两条 `add` 与 `ret` 各压成 2 字节 = 6。

**A3** `rv64g` 没有 C 扩展，每条 4 字节；`rv64gc` 把常用指令压成 2 字节，指令条数不变而字节数减半。两者是两本账：指令数反映译码次数，字节数反映 I-cache 占用。

## 1.14.16 本章小结 {#sec-1.14.16}

这一节回答：这一章学完，给你一段陌生汇编或一个跨架构差异，你能按什么顺序判断，又能在哪些地方诚实地说「这台机器上看不见」？

::: preview 先抓住一件事
判据是：**看到一个差异，先问它属于哪层合同——组成、ISA、ABI 还是内核 ABI；再问能不能用字节数、指令数或一条命令取证。取不到证，就说出是哪道门挡住了。**
:::

这一章的主线是**同一段 C 在四层合同上的三次投影**。1.14.1–1.14.6 先立契约：组成的最小模型、ISA 规定的五类东西、ABI 补上的参数与保存规则、内核 ABI 决定的系统调用入口；`sum3` 的三套汇编就是这三层合同的合影，参数、返回值、返回地址各由其中一层决定。1.14.7–1.14.10 把「快」拆成三笔账：频率由关键路径与物理税封顶，CPI 由流水线与分支误预测抬高，访存由地址拆分与 AMAT 决定；三笔账乘起来才是时间，任何一笔都不能用「换个编译器」代替。1.14.11–1.14.15.1 再把规则落回可验证的地方：第 7 个参数之后在哪、一条指令的字节怎么拼、litmus 允许哪些重排、原子指令与缓存行弹跳如何收场，最后用三架构实验把字节数与指令数变成读数。

逐条打勾的达标表在[学习目标自检表](ch14-checklist.md)，这里只留三条判据：

- **能读能算**：给你任意一套的 10 条汇编，按「参数寄存器 → 返回值与 `ret` → 栈调整 → 访存 → 算术分支」画出栈帧；给你 48 位地址与缓存参数，拆出 tag/index/offset 并算 AMAT；给你一条 ARM64 或 RISC-V 指令，按字段表拼出 32 位编码。
- **能测**：用 `clang --target` 做 `-S`/`-c`，用 `readelf -h` 认 `Machine`、用 `nm -S` 数字节、用 `-S` 的指令行数代替 `objdump -d`；知道 `perf`、QEMU、交叉链接在本机都不可用，把没有读数的结论降级成「未实测」。
- **能判断**：跨架构差异先归层——寄存器数量是 ISA，参数位置是 ABI，`write` 的号是内核 ABI，重排是内存模型；再判断哪些数字换编译器、换机器就作废，哪些是合同规定、换不掉。

如果只记住一件事，那就是**同一段 C 的差异几乎从不来自「加法怎么做」，而来自四层合同各自的规定；数字只是合同的读数，读数必须带机器、编译器与口径。**

::: errata 本章的三条口径边界
1. **第 7、8 个参数不在栈上**：x86-64 只有 6 个整数参数寄存器；ARM64 与 RISC-V 有 8 个，第 7、8 个在 `x6`/`x7`、`a6`/`a7`，第 9 个才进栈。按「三家都只有 6 个」读栈帧会算错。
2. **`perf` 与 litmus 没有本机读数**：`perf` 不可用；x86 与 ARM 的并发 litmus 也不能在这台 aarch64 VM 上跑。相关结论是纸面推导与代码形状，不是实测。
3. **字节数属于工具输出**：8/12/6 与 141/140/24 都是「某个编译器、某组选项」的读数，不是 ISA 常数；换 clang 版本、换 `-march`，数字就会变。
:::

**下一站**：[1.15 汇编与调用约定](ch15.md#sec-1.15.1) 把这三套汇编放进完整函数：`call`/`bl`/`jal` 怎么保存返回地址、序言与尾声怎么建栈、第 7 个参数之后怎么传、内联汇编怎么写。[1.15.5 参数传递](ch15.md#sec-1.15.5) 会把 1.14.11 的栈帧扩成完整程序；第 3 篇的 `entry_SYSCALL_64` 与 `el0_svc` 则会把 1.14.5 的三条陷入指令接成内核路径。

::: method 即时自测 · 1.14
**Q1（读）** `sum3` 在三套 ISA 上各是 3 条指令，为什么字节数是 8/12/6？参数、返回值、返回地址分别在哪？

**Q2（算）** 9 个 `long` 参数的函数，第 7、8、9 个在三种 ABI 下从哪里取？x86-64 的 128 字节红区为什么另外两家没有？

**Q3（测）** 只有 `-S`/`-c`、`readelf` 与 `nm`，没有 `perf`、不能链接：你怎么证明 x86-64 的 `sum3` 是 8 字节？哪些结论你不能下？

**Q4（判）** Dekker 在 x86 上为什么可能出现 `r1=r2=0`？三套架构各用什么指令排除？为什么本机不能给出实测次数？

::: sol 答案
**A1** x86 是变长编码：`leaq` 3 字节、`addq` 3 字节、`retq` 1 字节；AArch64 三条各 4 字节；RISC-V 默认 `rv64gc` 把两条 `add` 与 `ret` 压成 2 字节。参数在三家分别是 `rdi/rsi/rdx`、`x0`–`x2`、`a0`–`a2`，返回值在 `rax`/`x0`/`a0`，返回地址在栈顶、`x30`、`ra`。

**A2** x86-64 前 6 个在寄存器，第 7–9 个在入口 `[rsp+8]`、`[rsp+16]`、`[rsp+24]`；ARM64 第 7、8 个在 `x6`/`x7`，第 9 个在 `[sp]`；RISC-V 第 7、8 个在 `a6`/`a7`，第 9 个在 `0(sp)`。红区是 SysV 给叶函数的 128 字节「`rsp` 以下不用调整栈」的空间，信号处理会避开；AAPCS64 与 RISC-V psABI 没有这个约定。

**A3** 用 `clang --target=x86_64-linux-gnu -O2 -c` 出目标文件，再 `nm -S` 看 `sum3` 的符号大小是 8，`objdump -h` 看 `.text` 也是 8；指令行用 `-S` 数出 3。不能下的是「运行多快」与「链接后多大」：没有目标机器的链接器与内核，运行时间、动态指令数都没有证据。

**A4** TSO 允许 Store→Load 重排，Dekker 正好踩在这条缝上。x86 用 `mfence` 或 `lock` 指令，ARM64 用 `dmb ish`，RISC-V 用 `fence rw,rw`。本机没有 x86 运行环境，arm64 只是 VM，虚拟化行为不能代表硅片弱序，所以只能给纸面结论；要次数得上真机或 herd7。
:::
:::
