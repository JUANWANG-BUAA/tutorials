## 1.18.1 RISC-V 寄存器与 CSR {#sec-1.18.1}

这一节回答：机器只有 32 个通用寄存器和一小把 CSR，凭什么既能支撑用户程序的「函数调用」，又能支撑内核的「特权级切换」？为什么有的东西要压栈保存，有的东西只在寄存器里换一下就完成了交接？

::: preview 先抓住一件事
通用寄存器 `x0`–`x31` 属于「正在跑的这个程序」，谁保存它们是软件之间的 ABI 约定；CSR（Control and Status Register，控制与状态寄存器）属于「机器当前的状态」，字段由规范定义，只能用专门的指令读写。函数调用靠 `ra` 和栈交接，trap 交接不压栈，而是改 `mstatus`/`sepc`/`scause` 这块仪表盘。记住这组对照：通用寄存器是账本，CSR 是仪表盘。
:::

你在 [1.15](ch15.md) 已经用过这些寄存器：参数走 `a0`–`a7`，返回值用 `a0`/`a1`，`s0`–`s11` 被调用者负责保存。RV64 有 32 个，`x0` 被硬连线成常量 0——写它不生效、读它恒为 0，所以 `li zero, 5` 是空操作，`add rd, rs, x0` 就是「移动」。

ABI 给这 32 个寄存器配了一套别名，重点不在名字，在「谁负责保存」这一分工：caller-saved（`t0`–`t6`、`a0`–`a7`）被调用者可以随便覆盖，调用者想留住就得提前挪到 `s` 寄存器或压栈；callee-saved（`s0`–`s11`、`sp`）被调用者返回前必须恢复原值。

| 别名 | 编号 | 用途 | 谁保存 |
|:--|:--|:--|:--|
| `zero` | x0 | 恒 0，写不进 | — |
| `ra` | x1 | 返回地址 | caller-saved |
| `sp` | x2 | 栈指针 | callee-saved |
| `a0`–`a7` | x10–x17 | 参数 / 返回值 | caller-saved |
| `t0`–`t6` | x5–x7, x28–x31 | 临时 | caller-saved |
| `s0`–`s11` | x8–x9, x18–x27 | 跨调用保留 | callee-saved |

到 1.18.3 你会看到 ABI 之外的一层特殊用法：SBI 把 EID（Extension ID，扩展编号）钉死在 `a7`、FID（Function ID，功能编号）钉死在 `a6`，借用参数寄存器传「功能号」。

另一类是 CSR。它们数量少，但每个字段都是一个开关：现在处于哪个特权级、中断（硬件把 CPU 从手头指令上拽走、交给内核处理的那类事件）开没开、出了 trap 该跳到哪、trap 的原因是什么。它们不能用普通 `ld`/`sd` 访问，只有三条指令能直接操作 CSR。

::: def 定义 1.18.1 · CSR 的三条指令 {#def-1.18.1}
- `csrrw rd, csr, rs1`：整写，`csr ← rs1`，旧值进 `rd`。
- `csrrs rd, csr, rs1`：置位，`csr ← csr | rs1`，旧值进 `rd`。
- `csrrc rd, csr, rs1`：清位，`csr ← csr & ~rs1`，旧值进 `rd`。
伪指令 `csrr rd, csr` 展开成 `csrrs rd, csr, x0`：和 0 或起来一个位都不置，可 `rd` 仍然拿到旧值——所以它是「纯读」；`csrw csr, rs` 是 `csrrw x0, csr, rs`，旧值丢进 `x0` 扔掉，只写不读。
:::

```asm
        csrr   a0, mcause        # 伪指令 = csrrs a0, mcause, x0
        la     t0, s_trap_entry
        csrw   stvec, t0         # = csrrw x0, stvec, t0，直接模式入口
        csrsi  sstatus, 1 << 1   # 置 sstatus 的 bit1（SIE），开 S 态中断
```

这四行读出两层意思：`csrr` 一个位都不改只取旧值，`csrw` 不存旧值只写，`csrsi` 直接把立即数或进某一位。内核「开中断总闸」正是靠 `csrsi`/`csrrs` 置位，而不是整字覆盖——因为 `sstatus` 里还有别的字段不能动。

CSR 自己又按特权分成两套：`m` 前缀那套归 M 态，`s` 前缀那套归 S 态，字段一一对应。低一级看不到高一级——在 S 态执行 `csrr t0, mstatus` 会触发 illegal instruction，只能读自己那套 `sstatus`。

| CSR（M 态 / S 态对应） | 它决定什么 | trap 时谁动它 |
|:--|:--|:--|
| `mstatus` / `sstatus` | 特权级、中断总闸、返回目标级 | 进/出 trap 时被硬件改 |
| `mepc` / `sepc` | 本次 trap 回来后要跳的 PC | 硬件在入口写入 |
| `mtvec` / `stvec` | trap 跳去的入口地址与模式 | 硬件在入口读取 |
| `mcause` / `scause` | 是中断还是异常、哪一个原因 | 硬件在入口写入 |
| `mtval` / `stval` | 出错的地址或指令 | 硬件在入口写入 |

`satp`（根页表指针）只有 S 态有，M 态那套里对应项叫别的名字；1.18.4 里 `satp=0` 意味着关地址翻译，这时链接地址就是物理地址。这套 `mstatus`/`sstatus`/`sepc`/`stvec`/`scause` 的命名，和 1.19 从 rCore 看内核时讲的是同一批。

::: ex 例 1.18.1 · 先猜：一条 csrrs 改了什么 {#ex-1.18.1}
设 `sstatus` 此刻的值是 `0x2`（只有 bit1 置位），执行 `csrrs a0, sstatus, x0`。先猜：`sstatus` 的新值是多少？`a0` 是多少？再想想，如果写成 `csrrw a0, sstatus, x0`，结果会不会不一样？

::: sol 解答
`csrrs …, x0` 和 `x0`=0 或，不置任何位，`sstatus` 仍是 `0x2`，`a0` 拿到执行前的旧值 `0x2`——这就是「纯读」。但 `csrrw a0, sstatus, x0` 完全不同：它把 `x0`（0）整字写进 `sstatus`，于是 `sstatus` 被清成 `0x0`。所以「读 CSR」必须用 `csrr`/`csrrs …, x0`，绝不能用 `csrw`。
:::
:::

### 1.18.1 小结

通用寄存器是软件之间用 ABI 约定的账本，caller-saved / callee-saved 分工靠栈在函数间交接；CSR 是机器仪表盘，只能用 `csrrw`/`csrrs`/`csrrc` 碰，`csrr` 靠 `x0`「不置位、取旧值」实现纯读，且 `m` 套、`s` 套按特权分层。如果只记住一件事，那就是：**函数调用时硬件什么都不帮你存，靠软件压栈；trap 发生时硬件先把几个 CSR 写好了，通用寄存器才轮到软件自己存。**

::: errata 关于 CSR 读写的误解
1. **「用 `ld`/`sd` 就能读 CSR」**——CSR 不在内存地址空间里，普通访存指令读不到，必须走三条 `csr*` 指令。
2. **「`csrrs` 一定会改写 CSR」**——当 `rs1=x0` 时一个位都没置，`csrr` 就是这种写法，是纯读。
3. **「S 态也能读 `mstatus`」**——`m` 前缀 CSR 只有 M 态能访问，越级就是 illegal instruction；S 态有自己那套 `sstatus`。
4. **「`x0` 也是普通寄存器，可以存值」**——它硬连线为 0，存不进东西；trap 入口里的 x0 槽只是占位（1.18.7 会讲）。
:::

::: method 即时自测 · 1.18.1
**Q1（记忆）** 直接操作 CSR 的三条指令是什么？旧值进到哪里？

**Q2（辨析）** 为什么说 `csrrs a0, sstatus, x0` 是「纯读」？`csrrw a0, sstatus, x0` 能做到同样的事吗？

**Q3（应用）** 你在 S 态要打开 `sstatus` 的 bit1（SIE）而不动其他字段，该用哪条指令？为什么不能用 `csrw`？

**Q4（迁移）** S 态代码执行 `csrr t0, mstatus` 会 illegal instruction，但 `csrr t0, sstatus` 正常，为什么？

::: sol 答案
**A1** `csrrw`（整写）、`csrrs`（置位）、`csrrc`（清位）；`rd≠x0` 时都把 CSR 的旧值写进 `rd`。
**A2** 和 `x0`=0 或起来不置任何位，CSR 不变而 `a0` 取到旧值。`csrrw a0, sstatus, x0` 不行：它把 0 整字写进 `sstatus`，等于清零，是「写 0」不是「读」。
**A3** 用 `csrsi sstatus, 2`（或先 `li t0, 2; csrrs sstatus, sstatus, t0` 之类的置位形式），只 OR 进 bit1。`csrw` 是整字覆盖，不先读出原值做或，就会破坏别的字段。
**A4** `m` 前缀 CSR 只属于 M 态，S/U 越级访问是非法指令；`sstatus` 是 S 态自己的状态寄存器，S 态读它合法。这套 CSR 命名与 1.19 一致。
:::
:::

## 1.18.2 三特权级与 trap {#sec-1.18.2}

这一节回答：硬件为什么要有三个特权级？trap 发生时硬件自己做哪五件事、又明确地「不做」哪件事？

::: preview 先抓住一件事
特权级不是贴在软件身上的三种标签，而是硬件逐条指令核实的三档档位：档位不够，执行一条 `csrr` 就当场 illegal instruction。trap 发生时硬件只负责把几块仪表盘写好（`sepc`/`scause`/`stval`、跳 `stvec`、关中断、切级），通用寄存器一个都不保存——保存现场从这一刻起才是「软件的事」。
:::

先想没有特权级会怎样：任何应用执行一条 `csrci mstatus, 2` 就把全局中断关了，定时器失灵、调度停摆，恶意程序甚至能让整台机器「看起来死机」。所以必须有一个硬件层面的门槛：有些指令、某些寄存器，只允许某些档位碰。RISC-V 给了三档：

- **M（Machine）**：最高档，跑固件（通常是 OpenSBI）。时钟、IPI、关机这类「服务整机」的事在这里做。
- **S（Supervisor）**：内核跑在这一档——Linux、教学内核都是。它能管自己的 trap 向量和页表（`satp`），但碰 `m` 前缀 CSR 或受 PMP 保护的设备就 fault。
- **U（User）**：应用。任何特权指令、任何 CSR 访问都是 illegal。

方向只有一句话：`ecall` 只能向上，`sret`/`mret` 只能向下。

```text
U (用户) --ecall--> S (内核) --ecall--> M (固件/SBI)
   ^                  |                  |
   +------ sret ------+------ mret -----+
```

严格说，trap 默认全部先落到 M；被 `medeleg` 委托的异常才直接落到 S（委托链在 1.18.7 串起来）。本节按「U 的 `ecall` 已委托给 S」的教学口径写：U 发起的 `ecall` 进 S，S 侧硬件把 `scause` 写成 8（Environment call from U-mode）；未委托时它先落 M，`mcause` 同样是 8。S 发起的 `ecall` 进 M，M 侧看到 `mcause=9`（from S-mode），OpenSBI 的 SBI 服务就靠它；`mcause=11` 是 M 自己遇到 `ecall`，基本等于固件出了 bug。这三个编号是读 trap 日志时最常查的。

::: def 定义 1.18.2 · trap 入口的硬件五步 {#def-1.18.2}
以 S 侧处理为例，硬件按顺序自动做完：
1. 把触发 trap 的那条指令的 PC 写入 `sepc`；
2. 把原因编码写入 `scause`，附加信息（如出错地址）写入 `stval`；
3. 读取 `stvec`，跳过去——这是软件提前装好的入口；
4. 把 `sstatus.SIE` 推入 `SPIE` 并清零 `SIE`：trap 处理期间默认关中断；
5. 特权级切到 S，并在 `SPP` 记录返回的目标级。
五步里没有一步保存通用寄存器——那是 trap 入口汇编的活（1.18.7 的 34 槽 `TrapFrame` 干的就是这件事）。
:::

入口汇编至少要有这个形状（教学最小版，只保存 caller-saved）：

```asm
# 最小 trap 入口（S 模式，保存 caller-saved）
trap_entry:
    addi sp, sp, -256
    sd   ra, 0(sp)
    sd   t0, 8(sp)
    ...
    csrr a0, scause
    csrr a1, sepc
    call trap_handler
    ld   ra, 0(sp)
    ...
    addi sp, sp, 256
    sret
```

两处要点破。其一，`...` 里藏着一套完整的存/取寄存器指令，demo 只存 caller-saved 够用，真内核要存全套。其二，这段没有换栈：trap 从 U 来时 `sp` 是用户栈指针，内核直接往里 `sd` 等于往用户地址空间写现场。正确做法是用 `sscratch` 在入口把 `sp` 与内核栈顶对调（1.18.7 讲为什么它被称为「第一次 trap 的生死线」）。

`mret`/`sret` 也不是「函数返回」：不恢复任何通用寄存器，只做三件事——PC 取 `sepc`（或 `mepc`）、按 `SPP`（或 `MPP`）切回目标级、用 `SPIE` 恢复 `SIE`；返回后目标级字段被清成最低档。所以 `mret` 可以回 S、也可以直接回 U；`sret` 默认回 U，但 `SPP=1` 时回的是 S。

::: ex 例 1.18.2 · 先猜：sepc 里是哪个地址 {#ex-1.18.2}
用户程序在地址 `0x8000_1234` 执行一条 `ecall`（标准指令定长 4 字节）。先猜：进入 S 态 trap 后 `sepc` 是多少？硬件会不会顺手帮你加 4？被 trap 的用户程序，它的 `ra`、`t0` 此刻被硬件存到了哪里？

::: sol 解答
`sepc = 0x8000_1234`，指向 `ecall` 这条指令本身；硬件不加 4，跳过它（`sepc += 4`）是 handler 的责任，忘了加就会 `sret` 后原地重陷。`ra`、`t0` 等通用寄存器哪儿也没去——硬件不保存任何通用寄存器，还活着但随时会被 handler 覆盖，所以入口第一步就得压栈。
:::
:::

### 1.18.2 小结

三档特权是硬件逐指令核实的档位：`ecall` 向上（U→S 记 `scause=8`，S→M 记 `mcause=9`），`sret`/`mret` 向下且只改 PC、特权级和中断闸。进 trap 硬件做满五步——写 `sepc`、写 `scause`/`stval`、跳 `stvec`、关中断、切级——然后停手。如果只记住一件事，那就是：**trap 是「硬件只干一半」的切换，保存现场、`sepc` 加 4、换内核栈，全归入口代码。**

::: errata 关于特权级与 trap 的误解
1. **「特权级只是标签，S 也能读写 `mstatus`」**——越级访问 CSR 是 illegal instruction；S 态只有 `s` 前缀那套，每次访存还要过 PMP。
2. **「trap 时硬件会自动把寄存器压栈」**——硬件只写几个 CSR，不往内存压一个字节。
3. **「`sret` 类似 `ret`，回去现场就恢复了」**——`sret` 不恢复任何通用寄存器；现场是靠 trap 入口自己存、自己取回来的。
4. **「`ecall` 之后硬件自动跳到下一条指令」**——`sepc` 记的就是 `ecall` 本身，加 4 是软件的事。
:::

::: method 即时自测 · 1.18.2
**Q1（记忆）** 按顺序说出进 trap 的硬件五步；其中保存了哪些寄存器？

**Q2（辨析）** `scause=8` 和 `mcause=9` 分别是哪个特权级发出的 `ecall`？U 态的 `ecall` 若没被委托给 M，M 侧看到的 `mcause` 是多少？

**Q3（应用）** 用户程序发起一次系统调用后陷入死循环，GDB（未实测）看到 PC 反复停在同一条 `ecall` 上。用 `sepc` 的语义解释最可能的 bug。

**Q4（迁移）** `mret` 回 S 还是回 U 由什么决定？`sret` 能回 S 吗？

::: sol 答案
**A1** 写 `sepc`；写 `scause`/`stval`；跳 `stvec`；把 `SIE` 推入 `SPIE` 并清零；切级并记 `SPP`。通用寄存器一个都不保存，只动 CSR。
**A2** 8 来自 U 态的 `ecall`，9 来自 S 态的 `ecall`（由 M 态的 OpenSBI 接走，这正是 SBI 的陷入手段）。U 的 `ecall` 被委托时 S 侧记 `scause=8`；没委托时先落 M，`mcause` 记 8。11 则是 M 自己遇到 `ecall`。
**A3** handler 忘了 `sepc += 4`：`sret` 回到 `ecall` 本身，再执行、再 trap，无限循环。
**A4** 由 `mstatus.MPP` 决定，可以回 S 也可以回 U；`sret` 按 `sstatus.SPP` 走，`SPP=1` 时回到 S。
:::
:::

## 1.18.3 SBI：内核与固件的契约 {#sec-1.18.3}

这一节回答：S 态内核不碰硬件，怎么打印一个字符、怎么关机？SBI 到底是指令、设备，还是系统调用？

::: preview 先抓住一件事
SBI（Supervisor Binary Interface）是一套 ABI：S 态内核与 M 态固件约定的「调用帧」。功能号放 `a7`（EID）和 `a6`（FID），参数放 `a0`–`a5`，用一条普通的 `ecall` 陷入 M；固件按约定把结果写回 `a0`（错误码）与 `a1`（值）再 `mret` 回来。它不是硬件指令，也不属于内核——换掉固件实现，只要契约守得住，内核一行不用改。
:::

先看两件 S 态自己做不了的事：关机，和给整机设闹钟。CLINT 的 `mtimecmp` 在常见固件配置下被 PMP 挡住，S 态直接 `sd` 到 `0x0200_4000` 是 store access fault；关机最后总得有人动机器级资源。可内核又确实需要输出、需要 IPI、需要定时器。办法不是发明一堆新指令，而是**把能力差距收敛成一份契约**：我不行、你行，那我把「哪个服务、什么参数」写进你我都看得见的寄存器，`ecall` 上去，你把结果放回同一批寄存器。这份契约就是 SBI。

::: def 定义 1.18.3 · SBI 调用帧 {#def-1.18.3}
一次 SBI 调用 = `a7`←EID（Extension ID，扩展编号）、`a6`←FID（Function ID，功能编号）、`a0`–`a5`←参数，执行 `ecall`；返回时 `a0`=错误码（`SBI_SUCCESS=0`，失败为负）、`a1`=值。几个 EID 其实是 ASCII 编码：TIME `0x54494D45`（"TIME"）、SRST `0x53525354`（"SRST"）、DBCN `0x4442434E`（"DBCN"）、IPI `0x735049`（"sPI"）。`0x00`–`0x08` 这批裸数字是最早的 legacy EID，putchar、关机都在这里。
:::

常用扩展与参数（完整表在 SBI 规范里，这里只放本书会用的）：

| 功能 | EID | FID | 参数 | 返回值 |
|:--|--:|--:|:--|:--|
| 控制台输出（legacy） | `0x01` | — | `a0=字符` | 无 |
| 关机（legacy） | `0x07` | — | 无 | 不返回 |
| 发 IPI（legacy） | `0x08` | — | `a0=hart mask` | — |
| 设置定时器（TIME） | `0x54494D45` | `0` | `a0=绝对时间` | `a0=error` |
| 发 IPI（IPI） | `0x735049` | `0` | `a0=hart mask`, `a1=mask` | `a0=error` |
| 系统复位（SRST） | `0x53525354` | `0` | `a0=type`（0 关机）, `a1=reason` | 不返回 |
| 调试控制台写（DBCN） | `0x4442434E` | `2` | `a0=字节数`, `a1=物理地址`, `a2=偏移` | `a0=error`, `a1=已写` |

两个容易记错的编号：**legacy 关机是 `0x07`，不是 `0x08`**；`0x08` 是 legacy 发 IPI。现代关机用 SRST 扩展 `0x53525354`，成功时不返回。legacy 控制台 `0x01` 每次只喂一个字节，v0.2 之后的正式通道是 DBCN 的 `write`（FID 2），一次能写一段。TIME 的 `a0` 给的是**绝对时间**：先 `rdtime` 读当前 `mtime`，再加间隔——写「间隔」是 1.18.8 的第一大坑。

不信可以问编译器。把调用帧写成一个 C 函数：

```c
long sbi_call(long eid, long fid, long a0, long a1)
{
    register long r_a0 __asm__("a0") = a0;
    register long r_a1 __asm__("a1") = a1;
    register long r_a7 __asm__("a7") = eid;
    register long r_a6 __asm__("a6") = fid;
    __asm__ volatile("ecall" : "+r"(r_a0), "+r"(r_a1)
                     : "r"(r_a7), "r"(r_a6) : "memory");
    return r_a0;
}
```

Ubuntu 24.04 VM（aarch64，clang 18.1.3）带 RISC-V 后端，下面是它用 `clang --target=riscv64-unknown-elf -march=rv64gc -mabi=lp64d -O2 -S` 编译上边这个函数**实测**得到的汇编（只到 `.s`；链接与运行未实测，VM 上没有 riscv64 链接器、没有 QEMU）：

```asm
sbi_call:                               # @sbi_call
# %bb.0:
	mv	a7, a0
	mv	a6, a1
	mv	a0, a2
	mv	a1, a3
	#APP
	ecall
	#NO_APP
	ret
```

盯着那四条 `mv`：按 C 约定，四个参数进门时在 `a0`–`a3`（依次是 eid、fid、arg0、arg1）；SBI 要的是另一套布局，所以编译器先做一轮寄存器洗牌——`mv a7, a0` 把 EID 挪进 `a7`，`mv a6, a1` 把 FID 挪进 `a6`，再把真正的 arg0/arg1 送回 `a0`/`a1`。洗牌之后唯一的「动作」就是一条 `ecall`。这段汇编坐实了两件事：SBI 没有任何专属指令；所谓「调用固件」，物理上就是一组寄存器约定加一次 trap。

### 1.18.3.1 调用约定速查

| 寄存器 | 输入 | 输出 |
|:--|:--|:--|
| `a7` | EID | 不变 |
| `a6` | FID | 不变 |
| `a0`–`a5` | 参数 0–5 | `a0`=错误码，`a1`=值 |

S 态执行 `ecall` 进入 M 态时，M 侧硬件写 `mcause=9`（Environment call from S-mode）；OpenSBI 按 `a7` 找到扩展、按 `a6` 找功能、办完事把 `mepc += 4`——跳过这条 `ecall` 正是固件的职责——再 `mret`。S 态看回来就像一次普通函数调用，但这是一整趟 M 态往返。返回值约定再说一遍：**`a0` 是错误码，`a1` 是值**，写成「返回值在 a0、错误在 a1」正好相反；而且 `putchar` 返回成功只保证固件接收了字符，不保证它已经到了终端。

::: ex 例 1.18.3 · 先猜：a7 写错一位会怎样 {#ex-1.18.3}
内核要关机，有人把 legacy EID 记串了位：

```asm
li   a7, 0x08     # 以为是 legacy 关机
li   a0, 0
ecall
# 下一行继续
```

先猜：机器会断电吗？执行会走到「下一行」吗？

::: sol 解答
不会断电，而且会走到下一行。`0x08` 是 legacy 发 IPI：`a0=0` 被当成 hart mask，mask 为 0 要么没人被打扰，要么固件回一个错误码，总之 `ecall` 会正常返回，程序继续往下跑——表现就是「关机调用没生效」。legacy 关机是 `0x07` 且不返回；现代写法是 SRST：`a7=0x53525354`、`a6=0`、`a0=0`（关机）、`a1=reason`。
:::
:::

### 1.18.3 小结

SBI 是契约不是机制：`a7`/`a6` 装编号、`a0`–`a5` 装参数、一条 `ecall`、回来 `a0`=错误码 `a1`=值，编译器生成的那四条 `mv` 就是它的物理本体。方向要钉牢：系统调用是 U→S，SBI 是 S→M，两者只共享同一个陷入手段。如果只记住一件事，那就是：**换 OpenSBI、换 RustSBI 都不用改内核，改的是实现；但契约一破——编号记串、`a0`/`a1` 对调——症状往往不是崩溃，而是没输出、关不了机这类「安静的失败」。**

::: errata 关于 SBI 的误解
1. **「SBI 就是 RISC-V 的系统调用」**——方向不对：系统调用是 U→S，SBI 是 S→M；两者只是都拿 `ecall` 当陷入手段，编号空间和寄存器约定完全不同。
2. **「SBI 是一组硬件指令」**——指令集里没有 SBI 指令，上面那 `-S` 片段里唯一的动作就是 `ecall`。
3. **「SBI 是内核的一部分」**——SBI 是 M 态固件实现的规范，内核只是契约的消费方。
4. **「legacy 关机是 0x08」**——`0x08` 是 legacy IPI；关机是 `0x07`（legacy）或 SRST（现代）。
:::

::: method 即时自测 · 1.18.3
**Q1（记忆）** 一次 SBI 调用里 EID、FID、参数分别放在哪些寄存器？返回的 `a0`、`a1` 各装什么？

**Q2（辨析）** U 态 `ecall` 发起系统调用、S 态 `ecall` 发起 SBI，用的是同一条指令，为什么说它们是两份不同的契约？

**Q3（应用）** 写出用 SRST 关机的四个寄存器取值；如果固件不实现 SRST，调用方一般拿到什么？

**Q4（迁移）** 把 OpenSBI 换成 RustSBI，内核里的 SBI 调用代码要改吗？反过来，内核自己写错了 `a7`，固件会「崩溃」吗？

::: sol 答案
**A1** EID→`a7`，FID→`a6`，参数→`a0`–`a5`；返回 `a0`=错误码（0 成功、负数失败），`a1`=值。
**A2** 陷入的硬件机制相同，但两端不同：U 的 `ecall` 由 S 侧按 `scause=8` 走系统调用表，S 的 `ecall` 由 M 侧按 `mcause=9` 走 EID/FID 分派。一份在 syscall 编号空间，一份在 SBI 扩展编号空间，处理者也不同（内核 vs 固件）。
**A3** `a7=0x53525354`、`a6=0`、`a0=0`（type=关机）、`a1=0`（reason=未提供）；固件未实现该扩展时按约定在 `a0` 返回 not-supported 类负错误码，调用照常返回。
**A4** 不用改：实现可替换、契约不可违背，这正是 ABI 的意义。内核写错 `a7` 固件不会崩——EID 查不到就回 not-supported，错误以 `a0` 的形式安静地还给你。
:::
:::

## 1.18.4 最小 Rust 裸机程序：链接脚本、`_start` 与 SBI 输出 {#sec-1.18.4}

这一节回答：内核对外的第一行代码——控制权从哪来、它要先自己收拾什么、又怎么对外说话？

::: preview 先抓住一件事
整个程序只回答三个问题：**在哪**开始执行（链接脚本把 `.text.entry` 钉在 `0x8020_0000`）、进 Rust 前**先收拾什么**（`_start` 清 `.bss`、设 `sp`）、怎么**对外说话**（`println!` 的最后一步是 SBI 的 `putchar`）。其余——`#![no_std]`、`panic_handler`、cargo 配置——都是 Rust 对「下面没有操作系统」这件事的手续。
:::

四个文件分工：`linker.ld` 画内存布局，`entry.asm` 是固件跳板后执行的第一段，`main.rs` 承载逻辑，两份配置告诉 cargo「按没有操作系统来链接」。要达成的目标很小：打印一行 `hello, myrcore`，然后经 SBI 关机。跑通之后，1.18.1–1.18.3 的机制全落在真实地址和真实寄存器上。

**口径先说死：本节未实测（本机没有 RISC-V 硬件，也没有 QEMU；VM 无 rustc/cargo）。**构建命令只给形状；「看到什么算对」全是判读规则，不是会话记录。真实的终端记录只有两处，放在本节末尾。

### 链接脚本

链接脚本决定「哪个段放在哪个物理地址」。QEMU `-kernel` 加载 ELF 时按程序头（program header）装载，所以入口地址和段地址必须匹配链接脚本：

<div class="variant" data-arch="riscv64" data-lang="all">

```ld
/* linker.ld：myrcore 在 QEMU virt + OpenSBI 下的内存布局 */
OUTPUT_ARCH(riscv)
ENTRY(_start)

BASE_ADDRESS = 0x80200000;   /* OpenSBI 占用 0x8000_0000..0x8020_0000 */

SECTIONS
{
    . = BASE_ADDRESS;
    skernel = .;

    .text : {
        *(.text.entry)       /* _start 必须最先执行 */
        *(.text .text.*)
    }

    . = ALIGN(4K);
    srodata = .;
    .rodata : {
        *(.rodata .rodata.*)
        *(.srodata .srodata.*)
    }

    . = ALIGN(4K);
    sdata = .;
    .data : {
        *(.data .data.*)
        *(.sdata .sdata.*)
    }

    . = ALIGN(4K);
    .bss : {
        *(.bss.stack)        /* 启动栈单独放，避免被清零循环覆盖 */
        sbss = .;
        *(.bss .bss.*)
        *(.sbss .sbss.*)
        ebss = .;
    }

    . = ALIGN(4K);
    ekernel = .;

    /DISCARD/ : {
        *(.eh_frame)
        *(.comment)
    }
}
```

</div>

几个关键点：

- `ENTRY(_start)` 只影响 ELF 的入口字段，不改变段地址；QEMU 用 ELF 入口跳转。
- `.text.entry` 放在 `.text` 最前面，保证 `_start` 在 `0x8020_0000`。
- `sbss`/`ebss` 是清零循环的边界；它们必须是**符号**，不能在 Rust 里用数组长度代替。
- `.bss.stack` 放在 `sbss` 之前，清零循环就不会碰栈。你也可以把栈放在 `.bss` 之外，效果一样。

::: def 定义 1.18.4 · BASE_ADDRESS 为什么是 0x8020_0000 {#def-1.18.4}
QEMU `virt` 的 DRAM 从 `0x8000_0000` 起。`-bios default` 时，前 2 MiB 归 OpenSBI：固件先在 M 态跑，`mret` 降到 S 再把控制权交给内核——内核若也链在 `0x8000_0000`，两边重叠，不是覆盖固件就是被覆盖。所以 `0x8020_0000` 配 `-bios default`，`0x8000_0000` 只配 `-bios none`（没有固件，你的程序从 M 态直接跑）。另一个前提：此刻 `satp=0`，地址翻译关着，链接地址**就是**物理地址，`la` 算出的绝对地址可以立刻用。
:::

### 入口 `_start`

`_start` 是唯一一段必须在任何 Rust 代码之前运行的汇编。它要做三件事：清 `.bss`、设 `sp`、跳到 Rust：

<div class="variant" data-arch="riscv64" data-lang="asm">

```asm
# entry.asm：OpenSBI 跳到 0x8020_0000 后执行的第一段代码
.section .text.entry
.globl _start

_start:
    # 1) 清 .bss：sbss..ebss，按 8 字节写 0
    la      t0, sbss
    la      t1, ebss
1:
    bgeu    t0, t1, 2f
    sd      zero, 0(t0)
    addi    t0, t0, 8
    j       1b
2:
    # 2) 设置启动栈（栈从高地址向低地址增长）
    la      sp, boot_stack_top
    # 3) 进入 Rust；不返回
    call    rust_main
3:
    wfi
    j       3b

# 启动栈放在 .bss.stack，大小 16 KiB
.section .bss.stack, "aw", @nobits
.align 12
boot_stack:
    .space 4096 * 4
boot_stack_top:
```

</div>

这段汇编有两个容易忽略的细节：

1. `la` 是伪指令，展开成 `auipc` + `addi`，得到的是**链接地址**（`0x8020_xxxx`），不是当前 PC 的物理地址。因为 OpenSBI 已经把 MMU 关掉（`satp=0`），链接地址就是物理地址。
2. `call rust_main` 使用 `ra` 保存返回地址；`rust_main` 如果返回，会跳回 `3:` 的 `wfi`。我们让 `rust_main` 返回 `!`，所以这条路径只是保险。

### Rust 主逻辑

Rust 侧只需要三样东西：`#![no_std]`、`#![no_main]`、一个 `panic_handler`。`global_asm!` 把 `entry.asm` 嵌进目标文件，链接器才能看到 `_start`。

<div class="variant" data-arch="riscv64" data-lang="rust">

```rust
// src/main.rs：最小 S 态裸机程序
#![no_std]
#![no_main]

use core::arch::global_asm;
use core::fmt::{self, Write};
use core::panic::PanicInfo;

global_asm!(include_str!("entry.asm"));

const SBI_CONSOLE_PUTCHAR: usize = 0x01;
const SBI_SRST: usize = 0x5352_5354; // "SRST"

#[inline(always)]
fn sbi_call(eid: usize, fid: usize, arg0: usize, arg1: usize) -> (isize, usize) {
    let (err, val): (isize, usize);
    unsafe {
        core::arch::asm!(
            "ecall",
            in("a7") eid,
            in("a6") fid,
            inlateout("a0") arg0 => err,
            inlateout("a1") arg1 => val,
            options(nostack),
        );
    }
    (err, val)
}

struct Console;

impl Write for Console {
    fn write_str(&mut self, s: &str) -> fmt::Result {
        for b in s.bytes() {
            let _ = sbi_call(SBI_CONSOLE_PUTCHAR, 0, b as usize, 0);
        }
        Ok(())
    }
}

pub fn print_fmt(args: fmt::Arguments) {
    let mut c = Console;
    c.write_fmt(args).unwrap();
}

#[macro_export]
macro_rules! print {
    ($($arg:tt)*) => { $crate::print_fmt(format_args!($($arg)*)) };
}

#[macro_export]
macro_rules! println {
    () => { $crate::print!("\n") };
    ($($arg:tt)*) => { $crate::print!("{}\n", format_args!($($arg)*)) };
}

fn shutdown(failure: bool) -> ! {
    let _ = sbi_call(SBI_SRST, 0, 0, failure as usize);
    loop {
        core::hint::spin_loop();
    }
}

#[no_mangle]
pub extern "C" fn rust_main() -> ! {
    println!("hello, myrcore");
    shutdown(false)
}

#[panic_handler]
fn panic(info: &PanicInfo) -> ! {
    println!("[panic] {}", info);
    shutdown(true)
}
```

</div>

这段代码的关键是 `inlateout("a0")` 把输入输出绑在同一寄存器，符合 SBI 约定；`panic_handler` 返回 `!`，裸机下只能打印后关机。

### `Cargo.toml` 与 `.cargo/config.toml`


`panic = "abort"` 是必须的：`no_std` 没有 unwinding 运行时，默认 `unwind` 会链接失败。`Cargo.toml` 只需 `edition = "2021"` 和两处 `panic = "abort"`。

::: ex 例 1.18.4 · 先猜：Entry 会是哪个数 {#ex-1.18.4}
假设 ELF 在完整环境里构建出来了，跑 `llvm-readelf -h hello | grep Entry`。先猜：`Entry point address` 会是链接地址 `0x80200000`、还是 `0x10000` 这种相对镜像开头的偏移、还是 `rust_main` 的地址？QEMU 凭什么从这里开跑？

::: sol 解答
应该是 `0x80200000`：`ENTRY(_start)` 加上 `.text.entry` 排在最前，`_start` 就被钉在 BASE_ADDRESS 处。QEMU `-kernel` 加载 ELF 时按程序头装段，再直接跳入口字段——它不认符号名，只认这个地址。读出的若是 `0x80000000`，是 `BASE_ADDRESS` 与 `-bios` 没配对；若是别的怪值，多半 `.text.entry` 没排到最前。
:::
:::

判读规则（环境齐备时；未实测）：

- `llvm-readelf -l` 应列出从 `0x80200000` 起的加载段；`llvm-objdump -d` 的第一组指令应是 `_start` 里 `la t0, sbss` 展开出的 `auipc`+`addi`。
- 串口应出现一行 `hello, myrcore`，随后 QEMU 自行退出——退出是 SRST 关机的效果，不是程序「跑完了」。旧稿预期输出里那行 `sstatus = 0x...` 是排版遗留：`rust_main` 根本没有读 `sstatus` 的代码，按不存在处理。
- 什么都没打印：`-s -S` 停住后用 GDB 看 `mret` 之后的 PC 是否等于 `0x8020_0000`，不等就是链接地址或 `-bios` 配对错了。
- 有 `hello` 但 QEMU 不退出：`shutdown` 的 EID/FID 写错（1.18.3：legacy 关机 `0x07`，SRST 是 `0x53525354`）。

### 1.18.4 小结

四个文件把「第一条指令在哪、输出一条最小回路」讲完了：链接脚本让 `.text.entry` 钉在 `0x8020_0000`（给 OpenSBI 让出 2 MiB），`_start` 清 `.bss`、设 `sp` 才敢 `call rust_main`，`println!` 一路摊平到 SBI `putchar`。本环境的工具链天花板实测到 `.s` 为止，链接与运行全部未实测。如果只记住一件事，那就是：**`satp=0` 时链接地址就是物理地址，「把 `_start` 钉在固件让出的地址上」是内核与固件之间全部的第一课。**

::: errata 裸机入口的误解
1. **「上电时 .bss 本来就是全 0，不用清」**——固件不保证这一点；`sbss`/`ebss` 边界加清零循环才是正路，不清等于赌全局变量恰好像 0。
2. **「链接在哪都行，QEMU 会自己找」**——`-bios default` 下 `0x8000_0000` 已被 OpenSBI 占用，重叠的后果是没输出或诡异跑飞；`0x8020_0000` 与 `0x8000_0000` 各配一种 `-bios`。
:::

## 1.18.5 启动链、内存地图与 C/汇编版本 {#sec-1.18.5}

这一节回答：一块刚上电的板子里，第一条指令是谁的？控制权怎么一层层交到你手上，交到手那一刻内存里哪些地址能用、哪些一碰就 fault？不用 Rust、改用 C 或纯汇编走同一条路，代码要长成什么样？

::: preview 先抓住一件事
启动链的本质是「没有返回地址的移交」：OpenSBI 用 `mret` 把特权级降到 S、把 PC 交给内核，内核再用 `sret` 降到 U，每一棒都不压栈、不保存现场。这一节只记两件事：**谁在哪个特权级把 PC 交给谁**，以及**交出来那一刻哪些地址对应真实设备**。C 版和纯汇编版不是第三种机制，只是换语言，入口三件事、链接地址、SBI 调用帧一个字没变。
:::

上电那一刻 CPU 只有一个状态：PC 硬连线到一个 ROM 地址，`sp` 是复位值，`.bss` 里是随机电平，`satp=0` 所以没有地址翻译，也没有一个设备被初始化过——你不能「直接跑 main」。RISC-V 规范也没规定必须三层固件（嵌入式常 M 态裸跑，1.18.7 的 P2 就是），但 QEMU `virt` + OpenSBI 的链条是固定的：

<pre class="layout">
  上电 → ZSBL(M) → OpenSBI(M) → 你的内核(S) → 用户程序(U)
                     │ mret        │ sret        │ ecall
                     └─────────────┴─────────────┘
</pre>

四棒各有各的交法，而且只有一个可返回：

| 交接 | 手段 | 特权级 | 谁决定跳到哪 |
|:--|:--|:--|:--|
| 上电 → ZSBL | 硬件复位向量 | 进 M | 芯片设计（ROM 地址写死） |
| ZSBL → OpenSBI | 直接跳转 | 仍在 M | ZSBL 里写死的固件入口 |
| OpenSBI → 内核 | `mret` | M → S | `mepc` 与 `mstatus.MPP` |
| 内核 → 用户 | `sret` | S → U | `sepc` 与 `sstatus.SPP` |
| 用户 → 内核 → 固件 | `ecall` | U → S → M | `stvec` / `mtvec` |

::: def 定义 1.18.5 · 移交与调用的差别 {#def-1.18.5}
**移交**（handoff）指上一棒把 PC、特权级、控制权交给下一棒且自己不再回来：`mret`/`sret` 只做「按 `xepc` 改 PC + 按 `MPP`/`SPP` 降级 + 用 `MPIE`/`SPIE` 恢复中断闸」，没有任何地方存着「回去的路」。**调用**才有返回地址——`ecall` 是升级加跳 trap 向量，硬件先把触发指令的 PC 写进 `sepc`/`mepc`，所以 handler 能 `xret` 回去。整条链上只有 `ecall` 是调用语义，前面几棒都是「跳过去就别回来」；这也是 1.18.4 的 `_start` 后面跟 `wfi` 死循环而不是 `ret` 的原因。
:::

### QEMU `virt` 的物理内存地图

内核被 `mret` 交出来时手里只有一个 PC，第一件事却必须决定「往哪些地址写」。下表地址以 QEMU `hw/riscv/virt.c` 为准：

| 物理地址 | 大小 | 设备 | 本章用途 |
|:--|--:|:--|:--|
| `0x0000_1000` | 4 KiB | SiFive test finisher | 写 `0x5555` 让 QEMU 成功退出 |
| `0x0200_0000` | 64 KiB | CLINT | `mtime`/`mtimecmp` |
| `0x0c00_0000` | 64 MiB | PLIC | 外部中断 |
| `0x1000_0000` | 256 B | UART0（16550A） | `THR` 写字符 |
| `0x1000_1000` | 256 B | UART1 / virtio-mmio 起点 | 第 1.19 节块设备 |
| `0x8000_0000` | 128 MiB | DRAM 起始 | OpenSBI 固件 |
| `0x8020_0000` | — | 内核加载地址 | `-kernel` 默认入口 |

表里有性质完全不同的两种地址。`0x8000_0000` 起是 DRAM：写进去的值留在内存里，读回来还是它。`0x0200_0000`（CLINT）、`0x0c00_0000`（PLIC）、`0x1000_0000`（UART0）是 MMIO（Memory-Mapped I/O，把设备寄存器编进地址空间）：地址只是设备的引脚编号，写进去的值不落内存，读一次还可能改变设备状态——接收缓冲区里的字符读走就没了。RISC-V 没有 x86 的 `in`/`out`，`ld`/`sd` 直接打到设备端口上，这就是 1.18.6 里那条 `sb` 的全部来历。

三个口径说死。其一，此刻 `satp=0`，这些数字就是物理地址，[1.9](ch09.md#sec-1.9.1) 那套页表翻译还没开始工作，`0x1000_0000` 就是 UART0，没有「你的进程映射到的 UART」。其二，DRAM 起点和固件区重叠：`-bios default` 时前 2 MiB 归 OpenSBI，`BASE_ADDRESS` 取 `0x8020_0000`；`-bios none` 时没人占，才敢用 `0x8000_0000`（`def-1.18.4`）。其三，test finisher 是 QEMU 的仿真后门，真板上不存在。

判读规则（**未实测，无 RISC-V 硬件/QEMU**）：地址对不对不看串口，看三处结构——`BASE_ADDRESS` 与 `-bios` 是否配对；`llvm-readelf -h` 的 `Entry` 是否等于它；S 态直接 `sd` 到 `0x0200_4000` 是否报 store access fault（报了才说明 PMP 真在管你）。

### C 版本

Rust 不是必需品。`start.S` 负责清 `.bss`、设栈、跳 `kmain`；`hello.c` 只做输出和关机；链接脚本与 Rust 版共用同一份。之所以三种语言长得几乎一样，是因为裸机入口要满足的是 ABI 与地址约定，不是某个语言的库——下面这段就是在 Ubuntu 24.04 VM（aarch64，clang 18.1.3）上真编过的两个文件。

```c
/* hello.c */
#include <stdint.h>
#define SBI_PUTCHAR 0x01UL
#define SBI_SRST    0x53525354UL

static long sbi_call(long eid, long fid, long a0, long a1, long *value)
{
    register long r_a0 __asm__("a0") = a0;
    register long r_a1 __asm__("a1") = a1;
    register long a7 __asm__("a7") = eid;
    register long a6 __asm__("a6") = fid;
    __asm__ volatile("ecall" : "+r"(r_a0), "+r"(r_a1)
                     : "r"(a7), "r"(a6) : "memory");
    if (value) *value = r_a1;
    return r_a0;
}

static void putc(char c) { (void)sbi_call(SBI_PUTCHAR, 0, (unsigned char)c, 0, 0); }
static void puts_(const char *s)
{
    while (*s) { if (*s == '\n') putc('\r'); putc(*s++); }
}
static void shutdown(int failure)
{
    (void)sbi_call(SBI_SRST, 0, 0, failure, 0);
    for (;;) __asm__ volatile("wfi");
}
void kmain(void) { puts_("hello from C\n"); shutdown(0); }
```

</div>

### 纯汇编版本

再退一步：把 C 也去掉。这个版本有两个差别值得注意。一是**输出不经过 SBI**：`puts` 直接轮询 UART 的 `LSR`、往 `THR` 写字节（1.18.6 讲这套寄存器），M 态、S 态都能用；但结尾那四条 `li` 加 `ecall` 仍是 SRST 关机调用，所以它是「自己发字符、请固件断电」的混合体——纯汇编不等于完全没有 SBI。二是**连 `.bss` 都不清**：程序只有一个待在 `.rodata` 里的字符串，没有全局可变变量。等你加了 `static mut TICKS`，清零循环就必须请回来——「能省掉初始化」是因为「没有可初始化的东西」，不是可以照抄的简化。

### 同样的入口，在别的 ISA 上叫什么

上面这些名字全是 RISC-V 的方言，机制却通用：向上永远是一条陷入指令（硬件写返回地址、切级、跳向量），向下永远是一条带 `ret` 字样的返回指令。名字换了，1.18.2 那五步一步没少。顺带一提，本书的实测环境 `ubuntu24` 就是 ARM64 那列：EL1 跑内核、EL0 跑应用，「内核 → 固件」走 PSCI，和 SBI 同类——一套 ABI，既不是硬件指令也不是操作系统。

| 机制 | RISC-V 64 | x86-64 | ARM64 |
|:--|:--|:--|:--|
| 用户 → 内核 | `ecall` | `syscall` | `svc #0` |
| 内核 → 固件 | `ecall` + SBI | UEFI runtime | `smc`/`hvc`（PSCI） |
| 返回 | `sret`/`mret` | `sysret`/`iretq` | `eret` |
| 特权级 | M/S/U | ring 0–3 | EL0–EL3 |

::: ex 例 1.18.5 · 先猜：哪一处会撞 {#ex-1.18.5}
有人把上面的 C 版按 1.18.4 的 `linker.ld` 编出来，用 `-bios default -kernel hello-c.elf` 跑。先猜：(a) 链接正常时 `Entry` 是哪个数？(b) 他把 `BASE_ADDRESS` 改成 `0x8000_0000` 而 `-bios` 仍留 `default`，最先坏的是「输出」还是「取指」？(c) 他改成 `-bios none` 而 `BASE_ADDRESS` 留在 `0x8020_0000`，程序在 M 态还是 S 态？

::: sol 解答
(a) `0x8020_0000`：`ENTRY(_start)` 加 `.text.entry` 排最前，QEMU 只认 ELF 入口字段（判据，未实测）。(b) 先坏的是取指：`.text` 一落地就给固件前 2 MiB 打了补丁，`mret` 后能不能回到你的 `_start` 全看重叠多少，典型表现是「串口一个字符都没有」。(c) M 态——`-bios none` 时没人给你 `mret`，特权级由硬件复位决定；`0x8020_0000` 这时只是 DRAM 中间的普通地址，复位向量不会指到那里。
:::
:::

### 1.18.5 小结

启动链是一串「跳过去就别回来」的移交：复位向量给 ZSBL，ZSBL 跳到 OpenSBI，OpenSBI 用 `mret` 把 S 级和 PC 一起交给 `0x8020_0000`，内核再用 `sret` 交给 U；往上只剩 `ecall`，它有返回地址所以能回来。地图上要分清两类地址：DRAM 里的值留得住，MMIO 里的地址是设备引脚，读它会改变设备状态；此刻 `satp=0`，全是物理地址，1.9 的页表翻译还没登场。三种语言共用同一份链接脚本与同一条 SBI 调用帧——VM 实测到的 `li a7/a0/a6/a1` + `ecall`，和那对 PCREL 重定位，就是「ABI 不依赖语言」的实物证据。如果只记住一件事，那就是：**换语言不改契约，换 `-bios` 必须换 `BASE_ADDRESS`。**

::: errata 关于启动链与内存地图的误解
1. **「上电后 CPU 从 `0x8000_0000` 取指」**——复位向量由芯片决定，QEMU `virt` 先进 ROM 里的 ZSBL；`0x8000_0000` 只是 DRAM 起点，不是开机地址。
2. **「MMIO 当普通内存用没关系」**——`0x1000_0000` 读一次可能把接收缓冲区的字符拿走，`mtime` 每次读都不同；缓存这类读结果重用，等于丢数据。
3. **「test finisher 是 RISC-V 的标准关机」**——它是 QEMU 的仿真后门，真板上不存在，真板走 SRST 或电源管理芯片。
4. **「换块板子这张地图还能用」**——地址来自 QEMU `virt`；真实 SoC 的 UART 基址、CLINT 布局都不同，要查它自己的 device tree 或手册。
:::

**Q1（记忆）** 按顺序说出启动链的四棒与交接手段，并指出哪几棒能返回。

**Q2（辨析）** `0x8000_0000` 与 `0x1000_0000` 在「写进去的值去哪」上有什么区别？此刻谁在做地址翻译？

**Q3（应用）** VM 上 `llvm-objdump` 打出 `auipc t0, 0x0` 跟 `mv t0, t0`，重定位表里是 `R_RISCV_PCREL_HI20 sbss`。为什么两个立即数都是 0？链接后变成什么？

::: sol 答案
**A1** 上电→ZSBL（复位向量）→OpenSBI（跳转，仍在 M）→内核（`mret`，M→S，PC 取 `mepc`）→用户（`sret`，S→U）；前三棒都不能返回，只有回程的 `ecall` 是调用语义，因为硬件把触发指令的 PC 存进了 `sepc`/`mepc`。
**A2** 前者是 DRAM，值存在内存里，读回来还是它；后者是 UART0 的 MMIO，写等于把字节推给设备，读等于向设备要状态，值不落在内存。没人翻译——`satp=0`，两个都是物理地址。
**A3** 目标文件里符号地址还没分配，PCREL 重定位把数值留给链接器：HI20 填 `auipc` 高 20 位，LO12_I 填 `addi` 低 12 位。链接后两半拼成真正的 `0x8020_xxxx`——这也是 `satp=0` 时「链接地址就是物理地址」成立的前提。

## 1.18.6 不用 SBI，直接写 UART：MMIO 与 16550A {#sec-1.18.6}

这一节回答：不靠固件，怎么让板子自己吐出一个字符？为什么裸机第一版输出几乎都是轮询而不是中断？`volatile` 到底替你挡住了什么、又没挡住什么？

::: preview 先抓住一件事
MMIO 没有什么新指令：`ld`/`sd` 打到设备引脚就是驱动。16550A 只有一个「我现在能收」的旗子——`LSR` 的 bit5（THRE，发送保持寄存器空），你必须先等旗子立起来再写 `THR`，否则上一个字符还在排队，这一个就被覆盖。`volatile`/`read_volatile` 只保证编译器不把你的读省掉或合并，它不是内存屏障，也不管别的核。本节所有实测只到交叉编译出的汇编为止；**串口上的真实输出未实测（无 RISC-V 硬件/QEMU）**。
:::

1.18.3 的 `putchar` 很方便，但它把设备驱动藏进了 M 态，而且有三个时刻你靠不上它：跑在 `-bios none` 下根本没有固件可调（1.18.7 的 P2 就是这种）；固件自己挂了，报错信息只能自己往串口推；以及最实在的一条——不手写一次 UART，你永远不知道「输出一行」这四个字底下压着什么。

QEMU `virt` 的 UART0 是 16550A 兼容设备，基址 `0x1000_0000`，寄存器间隔 1 字节：

| 偏移 | 读 | 写 | 本章用到的位 |
|--:|:--|:--|:--|
| `0x00` | `RBR` 接收 | `THR` 发送 | 写字节即发送 |
| `0x01` | `IER` | `IER` | bit0 接收中断，bit1 发送中断 |
| `0x02` | `IIR` | `FCR` | `FCR` bit0 开 FIFO，bit1 清接收，bit2 清发送 |
| `0x03` | `LCR` | `LCR` | bit0–1 字长（`3`=8 位），bit7 DLAB |
| `0x04` | `MCR` | `MCR` | 调制解调器控制，通常不用 |
| `0x05` | `LSR` | — | bit5 `THRE` 发送保持寄存器空，bit6 `TEMT` 发送器空 |
| `0x06` | `MSR` | — | 调制解调器状态 |
| `0x07` | `SCR` | `SCR` | 暂存 |

这张表有两处「同一地址两种身份」，是读寄存器手册时最容易踩空的地方：偏移 `0x00` 读的时候是 `RBR`（接收缓冲），写的时候是 `THR`（发送保持），硬件按读写方向区分；偏移 `0x02` 读是 `IIR`（中断标识）、写是 `FCR`（FIFO 控制）。再加一个开关：`LCR` 的 bit7（DLAB）一置起，`0x00`/`0x01` 就变成波特率分频器的高低位——这就是为什么设帧格式必须**先写 `LCR`**，别让 DLAB 停在错误的位置上。

::: def 定义 1.18.6 · 16550A 的发送路径 {#def-1.18.6}
三步：**(1) 初始化** `LCR=0x03`（8 位字长、无校验、1 停止位，即 8N1）、`FCR=0x01`（开 FIFO）、`IER=0x00`（关掉所有中断，先用轮询）；**(2) 等旗子** 反复读 `LSR`，直到 `LSR & 0x20`（THRE）为 1，表示发送保持寄存器空；**(3) 写数据** 一个 `sb` 把字节写进偏移 0。`LSR` 的 bit6（TEMT）说的是「移位器也空了」，比 THRE 更彻底，掉电前的 flush 用它。初始化顺序反了会怎样：先写 `THR` 再设 `LCR`，第一个字符按复位默认帧格式发出去，对端收到的就是个乱码。
:::

最小实现三种语言各一份，语义完全一样——先等 `THRE`，再写 `THR`：

<div class="variant" data-arch="riscv64" data-lang="rust">

```rust
const UART0: usize = 0x1000_0000;

#[inline(always)]
unsafe fn mmio_write(addr: usize, value: u8) {
    core::ptr::write_volatile(addr as *mut u8, value);
}

#[inline(always)]
unsafe fn mmio_read(addr: usize) -> u8 {
    core::ptr::read_volatile(addr as *const u8)
}

pub fn uart_init() {
    unsafe {
        mmio_write(UART0 + 0x03, 0x03); // LCR: 8 位，无校验，1 停止位
        mmio_write(UART0 + 0x02, 0x01); // FCR: 开 FIFO
        mmio_write(UART0 + 0x01, 0x00); // IER: 关中断
    }
}

pub fn uart_putc(c: u8) {
    unsafe {
        while mmio_read(UART0 + 0x05) & 0x20 == 0 {
            core::hint::spin_loop(); // 等 THRE
        }
        mmio_write(UART0, c);
    }
}

pub fn uart_puts(s: &str) {
    for b in s.bytes() {
        if b == b'\n' {
            uart_putc(b'\r');
        }
        uart_putc(b);
    }
}
```

</div>

```asm
1:
```

两份代码的语义完全一样：轮询 `LSR` 第 5 位，为 1 才写 `THR`。真正的分水岭在 `volatile`（Rust 侧是 `read_volatile`/`write_volatile`）上，这一点不用真硬件也能看见——Ubuntu 24.04 VM（aarch64，clang 18.1.3）用 `--target=riscv64-unknown-elf -march=rv64gc -mabi=lp64d -O2 -S` 编同一段轮询，去掉 `volatile` 的差别是这样的（实测汇编，注解在 `#` 后）：

```asm
        # volatile 版：轮询循环活得好好的
        lui     a1, 65536               # 65536<<12 = 0x1000_0000，UART0 基址
.Lloop:
        lbu     a2, 5(a1)               # 每轮都重新读 LSR
        andi    a2, a2, 32              # 取 bit5 = THRE
        beqz    a2, .Lloop
        sb      a0, 0(a1)               # 旗子立了才写 THR
        ret

        # 去掉 volatile 的同一函数
        lui     a1, 65536
        lbu     a2, 5(a1)               # LSR 只读了一次
        andi    a2, a2, 32
        bnez    a2, .Lok
.Ldead:
        j       .Ldead                  # 读到的 THRE=0 → 永久死循环
.Lok:
        sb      a0, 0(a1)
        ret
```

右半段是编译器「合法」的优化：`LSR` 是个普通内存地址，编译器看不出它有谁会改，于是把循环体里重复的读提出循环外。判据只看 `lbu ... 5(a1)` 出现几次：volatile 版每轮一次，非 volatile 版一次。如果那次恰好读到 THRE=0，程序就永远卡在 `j .Ldead` 里——表现是「打印到一半停住」，而不是崩。`volatile` 挡住的是这一刀；它挡不住 CPU 与设备之间的乱序，也挡不住别的核的可见性，那要用 `fence`（顺序）和原子/锁（互斥）。

还有一类错误连 `volatile` 都救不了，编译器会直接警告（同一台 VM 实测原文）：

```text
warning: & has lower precedence than ==; == will be evaluated first [-Wparentheses]
    while((*(volatile uint8_t*)(UART0+0x05)) & 0x20 == 0){}
```

`& 0x20 == 0` 被解析成 `& (0x20 == 0)`，也就是 `& 0`，永远等于 0，循环条件恒假。同一轮实测里它生成的汇编是 `lbu zero, 5(a1)` 加 `sb a0, 0(a1)`：读了一次、结果丢进 `zero`、然后无条件写 `THR`——轮询整个消失了，但程序不报错，只是偶尔丢字符。**这类 bug 的运行后果在真串口上无法在本环境复现（未实测，无 RISC-V 硬件/QEMU），但它在汇编层已经板上钉钉。**

::: errata UART 直写的四个常见错误
1. **忘了 `\r`**：串口终端要 `\r\n` 才回到行首，只发 `\n` 会打出阶梯状输出（上面代码里的 `if b == b'\n' { uart_putc(b'\r') }` 就是干这个的）。
2. **初始化顺序反了**：先写 `THR` 再设 `LCR`，第一个字符用错误的帧格式发出，对端收到乱码。
3. **在 `panic` 路径上开着 UART 中断**：`IER` 没关时，panic 输出可能被打断，最后只看到半行；裸机 panic 应先把中断关干净。
4. **把 `volatile` 当内存屏障**：它只约束编译器，不保证设备顺序、不保证多核可见性。
:::

::: ex 例 1.18.6 · 先猜：少了哪一条会怎样 {#ex-1.18.6}
同一段发送代码做三处改动，先猜各自的症状：(a) 删掉那次 `LSR` 轮询，直接 `sb` 写 `THR`；(b) 删掉 `LCR=0x03` 这一行；(c) 把 `uart_puts` 里的 `if b == b'\n'` 分支删掉。

::: sol 解答
(a) 慢设备/大字符串时丢字符或输出错乱：THRE 还没立就把新字节压进去，前一个仍在移位；短字符串常常「看起来没事」，这是最坏的一种 bug——它只在负载高的时候出现。(b) 用复位默认的帧格式发，终端多半显示乱码，且第一字符最容易错（`LCR` 也影响 DLAB 门）。(c) 阶梯输出：每行都相对上一行缩进一格，因为 `\n` 只下移不回到行首。
:::
:::

### 1.18.6 小结

直写 UART 就是「三步」：初始化 `LCR/FCR/IER`、轮询 `LSR.THRE`、`sb` 写 `THR`，代价是你从此自己承担设备的时序与 `\r\n` 这类细节，好处是 M 态、S 态、没有固件时都能用。`volatile` 只回答「编译器会不会省掉这次访问」，实测的两段汇编把答案摊开：留着它每轮一次 `lbu`，去掉它整个轮询被提出循环、THRE=0 时变成死循环。如果只记住一件事，那就是：**MMIO 的读本身是副作用，任何「把它当普通变量优化」的改动都是在改设备状态。**

::: method 即时自测 · 1.18.6
**Q1（记忆）** 写出 16550A 发送一个字节的最短路径，说明 THRE 与 TEMT 的差别。

**Q2（辨析）** 同样是「读 `LSR`」，为什么必须 `volatile`？它不管哪两件事？

**Q3（应用）** 串口输出跑到第 40 个字符停住，程序没崩。用本节实测的汇编结构给出两个候选原因和各自的判据。

::: sol 答案
**A1** `LCR=0x03`、`FCR=0x01`、`IER=0x00` → 循环读 `LSR` 直到 bit5（THRE，发送保持寄存器已空）→ `sb` 写偏移 0（THR）。TEMT 是 bit6，指移位寄存器也空了，即最后一个字节已完全发出去；THRE 只保证「可以塞下一个」。
**A2** 因为 MMIO 的读有副作用：`LSR` 的值由硬件在两次读之间改变，编译器若按普通内存假设就能把循环里的重复读提出循环，只读一次。`volatile` 只约束编译器的优化，不做内存屏障（要 `fence`），也不保证多核可见性（要原子/锁）。
**A3** 其一，轮询被优化掉后卡在死循环——判据：反汇编里 `lbu ... 5(a1)` 只出现一次，且循环体是裸 `j`（本环境可实测到形状）。其二，THRE 一直不回 1（设备/FIFO 配置错，或 `FCR` 把发送 FIFO 清了个奇怪状态）——判据：轮询循环健在但永不退出，需要真硬件才能确认（未实测，无 RISC-V 硬件/QEMU）。
:::

## 1.18.7 trap 入口：保存 32 个寄存器 {#sec-1.18.7}

这一节回答：一条指令好好执行着，硬件把它拽进内核，那 32 个寄存器和「回到哪继续」由谁接住？入口的第一条指令为什么是 `csrrw` 而不是 `sd`？汇编里数出来的偏移，凭什么和 Rust 结构体的字段一一对得上？

::: preview 先抓住一件事
trap 入口只做三件事：**换栈**（用户 `sp` 和内核栈经 `sscratch` 交换，因为不能拿要被保存的寄存器当指针）、**按固定偏移保存 34 个槽**（32 个通用寄存器 + `sepc` + `sstatus`，一块 272 字节的 `TrapFrame`）、**把帧的地址交给 Rust**（`sp` 进 `a0`，之后才是 C 的世界）。出口严格反序，最后 `sret`。现场一旦漏保存，被中断的代码不会立刻崩，而是过了一会儿拿到一个被 handler 改过的寄存器——这是本章最难查的一类 bug。
:::

现在进入本章最硬的部分：写一个能保存/恢复完整现场的 trap 入口。没有它，时钟中断一来，被中断的代码就会看到寄存器被 handler 改得面目全非。

### TrapFrame 的布局

我们用一块连续的内存保存现场。RV64 下 32 个通用寄存器 + `sepc` + `sstatus`，共 34 个 8 字节槽：

| 偏移 | 内容 | 说明 |
|--:|:--|:--|
| `0` | `x0` | 恒为 0，占位，方便按索引访问 |
| `8` | `x1`/`ra` | 返回地址 |
| `16` | `x2`/`sp` | 用户栈指针（入口时从 `sscratch` 取） |
| `24` | `x3`/`gp` | 全局指针 |
| `32` | `x4`/`tp` | 线程指针 |
| `40`–`56` | `x5`–`x7` | `t0`–`t2` |
| `64`–`72` | `x8`–`x9` | `s0`–`s1` |
| `80`–`136` | `x10`–`x17` | `a0`–`a7` |
| `144`–`216` | `x18`–`x27` | `s2`–`s11` |
| `224`–`248` | `x28`–`x31` | `t3`–`t6` |
| `256` | `sepc` | 返回地址 |
| `264` | `sstatus` | 返回时的状态 |

这个布局不是随便定的：它让汇编可以用 `sd xN, N*8(sp)` 一条指令保存一个寄存器，也让 Rust 可以用 `#[repr(C)]` 结构体按字段访问。两者必须严格一致，否则你会在「为什么 `a0` 变成了 `sepc`」上浪费一个下午。

<div class="variant" data-arch="riscv64" data-lang="rust">

```rust
#[repr(C)]
#[derive(Clone, Copy, Debug, Default)]
pub struct TrapFrame {
    pub x: [usize; 32], // x[0] 恒 0；x[2] 是用户 sp
    pub sepc: usize,
    pub sstatus: usize,
}

impl TrapFrame {
    pub fn a0(&self) -> usize { self.x[10] }
    pub fn a7(&self) -> usize { self.x[17] }
    pub fn sp(&self) -> usize { self.x[2] }
}
```

</div>

### 入口与出口汇编

入口要换栈、保存 30 个寄存器（`x0` 不存，`x2` 从 `sscratch` 取）、保存 `sepc`/`sstatus`、把 `sp` 作为参数传给 Rust、调用 handler；出口反向操作。

这段汇编依赖三个约定：`sscratch` 存内核栈顶；`x2` 通过 `sscratch` 交换而不是从 frame 恢复；handler 的 ABI 是 `extern "C" fn(&mut TrapFrame)`，`a0` 传 frame 指针。

### 从入口到分发

入口只保存现场；分发在 Rust 里：读 `scause` 最高位区分中断/异常，`ecall` 用 `a7` 作为系统调用号，返回前 `sepc += 4`。完整实现在 P2 的 `s_trap_handler`，见下文。

::: errata trap 现场的五个坑
1. **保存了 `x0` 又恢复它**：`x0` 是硬连线 0，`ld x0, 0(sp)` 不报错但也没用；更糟的是有人用 `x0` 当临时寄存器，结果值永远是 0。
2. **忘记保存 `t0`–`t6`**：Rust handler 会自由使用临时寄存器；不保存就会破坏被中断代码的中间值。
3. **`sepc += 4` 用在中断上**：时钟中断返回后跳过了一条无辜的指令，程序行为会变得随机。
4. **`sstatus` 恢复顺序错**：先 `sret` 再恢复 `sstatus` 已经来不及；必须先把 `sstatus` 写回，再 `sret`。
5. **`sscratch` 初值没设**：第一次 trap 时 `csrrw sp, sscratch, sp` 会把 `sp` 换成 0，然后 `addi sp, sp, -272` 变成非法地址，trap 嵌套，最后 triple fault。
:::

### 三个特权级的完整演示

把上面的 trap 入口、SBI、M 态 handler 拼起来，就是本章的第二个完整程序：M 态启动 → 委托 `ecall-from-U` 给 S → `mret` 到 S → `sret` 到 U → U 执行 `ecall` → S 处理并打印 → U 再 `ecall` 请求关机 → S 通过 SBI 回到 M → M 用 test finisher 退出 QEMU。

这个程序比 P1 长，但它把本章所有机制串成了一条可验证的路径。它需要四个文件：`entry-p2.asm`（入口，链接到 `0x8000_0000`）、`trap.asm`（S/M 两个入口）、`linker-p2.ld`（`BASE_ADDRESS = 0x80000000`）、`main.rs`（下面）。注意 P2 用 `-bios none` 直接跑在 M 态，不需要 OpenSBI；关机用 QEMU 的 test finisher，而不是 SRST。

```rust
// P2: M -> S -> U -> trap -> M(SBI)
#![no_std]
#![no_main]

use core::arch::{asm, global_asm};
use core::panic::PanicInfo;

global_asm!(include_str!("entry-p2.asm"));
global_asm!(include_str!("trap.asm"));

const UART0: usize = 0x1000_0000;
const TEST_FINISHER: usize = 0x0010_0000;
const SBI_PUTCHAR: usize = 0x01;
const SBI_SRST: usize = 0x5352_5354;

#[repr(C)]
pub struct TrapFrame {
    pub x: [usize; 32],
    pub sepc: usize,
    pub sstatus: usize,
}

#[repr(C)]
pub struct MTrapFrame {
    pub a: [usize; 8], // a0..a7，必须全部保存/恢复
}

extern "C" {
    static s_stack_top: u8;
    static u_stack_top: u8;
    fn __s_trap_entry();
    fn m_trap_entry();
}

// ---- UART（M 态直接输出） ----
unsafe fn uart_putc(c: u8) {
    while (core::ptr::read_volatile((UART0 + 5) as *const u8) & 0x20) == 0 {}
    core::ptr::write_volatile(UART0 as *mut u8, c);
}

fn uart_puts(s: &str) {
    for b in s.bytes() {
        if b == b'\n' { unsafe { uart_putc(b'\r') }; }
        unsafe { uart_putc(b) };
    }
}

fn test_exit(code: u16) -> ! {
    let v = if code == 0 { 0x5555u32 } else { 0x3333 | ((code as u32) << 16) };
    unsafe { core::ptr::write_volatile(TEST_FINISHER as *mut u32, v) };
    loop { core::hint::spin_loop(); }
}

// ---- S 态 SBI 调用（ecall 到 M） ----
fn sbi_call(eid: usize, fid: usize, a0: usize, a1: usize) -> (isize, usize) {
    let (err, val): (isize, usize);
    unsafe {
        asm!("ecall", in("a7") eid, in("a6") fid,
             inlateout("a0") a0 => err, inlateout("a1") a1 => val,
             options(nostack));
    }
    (err, val)
}

// ---- M 态：配置 PMP、委托 ecall-from-U、降到 S ----
#[no_mangle]
pub extern "C" fn m_main() -> ! {
    uart_puts("M: hello from M-mode\n");
    unsafe {
        asm!("csrw mtvec, {}", in(reg) m_trap_entry as usize);
        asm!("csrw medeleg, {}", in(reg) 1usize << 8);
        asm!("csrw pmpaddr0, {}", in(reg) 0x3fff_ffff_ffff_ffffusize);
        asm!("csrw pmpcfg0, {}", in(reg) 0x0fusize);
        let mut ms: usize;
        asm!("csrr {}, mstatus", out(reg) ms);
        ms &= !(1 << 3);                                // MIE = 0
        ms = (ms & !(3 << 11)) | (1 << 11) | (1 << 7);  // MPP=S, MPIE=1
        asm!("csrw mstatus, {}", in(reg) ms);
        asm!("csrw mepc, {}", in(reg) s_main as usize);
        asm!("mret", options(noreturn));
    }
}

// ---- S 态：换内核栈，降到 U ----
#[no_mangle]
pub extern "C" fn s_main() -> ! {
    let s_top = unsafe { &s_stack_top as *const u8 as usize };
    let u_top = unsafe { &u_stack_top as *const u8 as usize };
    unsafe {
        asm!("mv sp, a0; csrw sscratch, sp", in("a0") s_top, options(nostack));
        asm!("csrw stvec, {}", in(reg) __s_trap_entry as usize);
        let mut ss: usize;
        asm!("csrr {}, sstatus", out(reg) ss);
        ss &= !(1 << 1);                          // SIE = 0
        ss = (ss & !(1 << 8)) | (1 << 5);         // SPP=U, SPIE=1
        asm!("csrw sstatus, {}", in(reg) ss);
        asm!("mv sp, a0", in("a0") u_top, options(nostack));
        asm!("csrw sepc, {}", in(reg) u_main as usize);
        asm!("sret", options(noreturn));
    }
}

// ---- U 态：两次 ecall ----
#[no_mangle]
pub extern "C" fn u_main() -> ! {
    unsafe {
        asm!("ecall", in("a7") 1usize, in("a0") 'U' as usize, options(nostack));
        asm!("ecall", in("a7") 2usize, options(nostack));
    }
    loop { core::hint::spin_loop(); }
}

// ---- S 态 trap：ecall-from-U ----
#[no_mangle]
pub extern "C" fn s_trap_handler(tf: &mut TrapFrame) {
    let scause: usize;
    unsafe { asm!("csrr {}, scause", out(reg) scause) };
    if scause == 8 {
        match tf.x[17] { // a7
            1 => { let _ = sbi_call(SBI_PUTCHAR, 0, tf.x[10], 0); }
            2 => { let _ = sbi_call(SBI_SRST, 0, 0, 0); }
            _ => {}
        }
        tf.sepc += 4;
    } else {
        uart_puts("S: unexpected trap\n");
        test_exit(1);
    }
}

// ---- M 态 trap：迷你 SBI ----
#[no_mangle]
pub extern "C" fn m_trap_handler(tf: &MTrapFrame) {
    match tf.a[7] {
        SBI_PUTCHAR => unsafe { uart_putc(tf.a[0] as u8) },
        SBI_SRST => {
            uart_puts("M: SRST -> test finisher\n");
            test_exit(0);
        }
        _ => uart_puts("M: unknown SBI\n"),
    }
    unsafe {
        let mepc: usize;
        asm!("csrr {}, mepc", out(reg) mepc);
        asm!("csrw mepc, {}", in(reg) mepc + 4);
    }
}

#[panic_handler]
fn panic(_: &PanicInfo) -> ! { test_exit(2) }
```

P2 用 `-bios none` 直接跑在 M 态，再由 M 态 `mret` 降到 S、S 降到 U。先猜：如果整份程序里一条 PMP 配置都不写，U 态去读 `0x8000_0000`（内核代码段）会发生什么——能读到内核指令、直接 fault、还是照常执行？为什么？

::: sol 解答
照常执行不了，但原因不是「内核保护了你」，而是 PMP 默认拒绝：M 态不受 PMP 限制，S/U 态的每一次访存都要过 PMP 检查，`pmpcfg0=0`（没有任何条目）时 S/U 访问任何地址都触发 access fault。所以不写 PMP 的裸机程序会在 U 态第一条取指就倒下，看起来像「隔离很好」，其实是谁都不许碰。P2 因此写 `pmpaddr0=0x3fff_ffff_ffff_ffff` + `pmpcfg0=0x0f`，用一个 NAPOT 条目把全部物理地址放开 RWX——这是**为了让教学程序能跑**的让步，不是安全配置。真实内核反过来用 PMP 把 S 态限制在内核区、把 U 态限制在用户区，构成「没有 MMU 时的最后一道防线」；判据是故障类型：PMP 越界报 access fault（`scause` 取指 1、读 5、写 7），页表缺失报 page fault（取指 12、读 13、写 15），两组编码不同，GDB 里一眼能分。

### 1.18.7 小结

trap 入口的全部工作可以背成一句话：**换栈、存现场、交参数、调 handler、还原场、`sret`**。真正需要想清楚的是三处顺序。第一，`csrrw sp, sscratch, sp` 必须排第一，因为此刻唯一的指针指向的就是即将被破坏的用户栈，而 `sscratch` 是硬件替你保留的那只「不用压栈的口袋」；它的初值若在启动时没写，第一次 trap 就会把 `sp` 换成 0。第二，偏移是合同：`x[N]` 落在 `N*8`、`sepc` 在 256、`sstatus` 在 264，汇编按这个数写 `sd`，Rust 用 `#[repr(C)]` 的 `[usize; 32]` 加两个字段读同一块内存，两边差一个槽位就会出现「`a0` 变成了 `sepc`」。

第三，`sepc += 4` 只属于同步异常（`ecall`/非法指令这类会重执行的场景），给中断加上去就等于随机吞掉一条指令。如果只记住一件事：**入口汇编不认识「语义」，它只保证「回去时和来时一样」——语义是分发层的事。**

## 1.18.8 时钟中断：从 CLINT 到 SBI 再到抢占 {#sec-1.18.8}

这一节回答：S 态内核连定时器的寄存器都写不了，那每一次「时间到了」的通知是从哪儿来的？为什么 tick 处理完必须再设一次闹钟？

::: preview 先抓住一件事
一条链，六步：CLINT 的 `mtime` 一直在涨 → 涨到 `mtimecmp` 就置 `mip.MTIP` → M 态进 trap（cause 7）→ M 态代为写新阈值、清 `MTIP`、置 `sip.STIP` → S 态进 trap（`scause` 最高位为 1、编码 5）→ handler 里通过 SBI `set_timer` 再约下一次。S 态自始至终不碰 `mtimecmp`，它只许下「到点了叫我」；所以**忘了重新预约，就只有第一声 tick**，而 `sie.STIE` 与 `sstatus.SIE` 少开任何一个，闹钟响了也进不来。
:::

裸机程序如果只会 `ecall`，仍然是「批处理」：一个程序跑完才轮到下一个。要让内核有「时间」的概念，必须有时钟中断。RISC-V 的定时器分两层：

- **M 态**：CLINT 的 `mtime`（只读，64 位，频率 10 MHz）和 `mtimecmp`（每 hart 一个）。`mtime >= mtimecmp` 时置位 `mip.MTIP`，若 `mie.MTIE` 和 `mstatus.MIE` 都为 1，则进入 M 态 trap（cause 7）。
- **S 态**：`sip.STIP` 是 S 态定时器中断挂起位，`sie.STIE` 是使能位。S 态不能直接写 `mtimecmp`，只能通过 SBI `set_timer` 请求 M 态代写；M 态写完后会清 `MTIP` 并置 `STIP`。

在 QEMU `virt` 上，CLINT 的地址是：

| 寄存器 | 地址 | 说明 |
|:--|:--|:--|
| `mtimecmp[hart0]` | `0x0200_4000` | 8 字节，写绝对时间 |
| `mtimecmp[hartN]` | `0x0200_4000 + 8*N` | 每 hart 一个 |
| `mtime` | `0x0200_BFF8` | 8 字节，只读，10 MHz |

但**不要直接写 `mtimecmp`**：你的内核运行在 S 态，写 M 态 MMIO 会被 PMP 拒绝。正确做法是 SBI `TIME`（EID `0x54494D45`）：先 `rdtime` 读当前时间，加上间隔，再 `ecall`。`rdtime` 在 S 态是否可读，取决于 `mcounteren.TM`。OpenSBI 通常会放行；如果没放行，`rdtime` 会触发 illegal instruction，此时只能用 SBI 的 `TIME` 扩展或 `get_time` 旧接口。

### 打开 S 态定时器中断

设定时器只是「什么时候响」，还要「让不让你听见」：


这四步的顺序很重要：先设 `stvec`，再开 `sie.STIE`，最后开 `sstatus.SIE`。如果先开全局中断再设 `stvec`，中间来一个中断就会跳到旧的/空的向量。这是所有中断驱动代码的通用规则：**先准备好入口，再开门**。

### 第三个完整程序：tick 计数与自动关机

把 P1 的 SBI 输出、P2 的 trap 入口、上面的定时器拼起来，就是 P3。它每 10 ms 收一次时钟中断，打印 tick，数到 5 次后关机。

```rust
// src/main.rs（P3）：S 态定时器中断 demo
#![no_std]
#![no_main]

use core::arch::{asm, global_asm};
use core::fmt::{self, Write};
use core::panic::PanicInfo;

global_asm!(include_str!("entry.asm"));
global_asm!(include_str!("trap.asm"));

static mut TICKS: usize = 0;

extern "C" {
    fn __s_trap_entry();
}

#[inline(always)]
fn sbi_call(eid: usize, fid: usize, a0: usize, a1: usize) -> (isize, usize) {
    let (err, val): (isize, usize);
    unsafe {
        asm!("ecall", in("a7") eid, in("a6") fid,
             inlateout("a0") a0 => err, inlateout("a1") a1 => val,
             options(nostack));
    }
    (err, val)
}

struct Console;
impl Write for Console {
    fn write_str(&mut self, s: &str) -> fmt::Result {
        for b in s.bytes() { let _ = sbi_call(0x01, 0, b as usize, 0); }
        Ok(())
    }
}

pub fn print_fmt(args: fmt::Arguments) {
    let mut c = Console;
    c.write_fmt(args).unwrap();
}

#[macro_export]
macro_rules! print {
    ($($arg:tt)*) => { $crate::print_fmt(format_args!($($arg)*)) };
}
#[macro_export]
macro_rules! println {
    () => { $crate::print!("\n") };
    ($($arg:tt)*) => { $crate::print!("{}\n", format_args!($($arg)*)) };
}

fn shutdown(failure: bool) -> ! {
    let _ = sbi_call(0x5352_5354, 0, 0, failure as usize);
    loop { core::hint::spin_loop(); }
}

fn set_next_timer() {
    let now: u64;
    unsafe { asm!("rdtime {}", out(reg) now) };
    let _ = sbi_call(0x5449_4D45, 0, (now + 100_000) as usize, 0);
}

#[no_mangle]
pub extern "C" fn rust_main() -> ! {
    unsafe {
        // 内核栈顶存入 sscratch；trap 入口会与用户 sp 交换
        asm!("csrw sscratch, sp");
        asm!("csrw stvec, {}", in(reg) __s_trap_entry as usize);
        asm!("csrs sie, {}", in(reg) 1usize << 5);   // STIE
        asm!("csrs sstatus, {}", in(reg) 1usize << 1); // SIE
    }
    set_next_timer();
    println!("timer armed");
    loop { core::hint::spin_loop(); }
}

#[no_mangle]
pub extern "C" fn s_trap_handler(tf: &mut TrapFrame) {
    let scause: usize;
    unsafe { asm!("csrr {}, scause", out(reg) scause) };
    if scause >> 63 == 1 && (scause & 0xff) == 5 {
        set_next_timer();
        unsafe {
            TICKS += 1;
            let n = TICKS;
            println!("tick {}", n);
            if n >= 5 { shutdown(false); }
        }
    } else {
        println!("unexpected trap: {:#x} sepc={:#x}", scause, tf.sepc);
        shutdown(true);
    }
}

#[repr(C)]
pub struct TrapFrame {
    pub x: [usize; 32],
    pub sepc: usize,
    pub sstatus: usize,
}

#[panic_handler]
fn panic(_: &PanicInfo) -> ! { shutdown(true) }
```

::: errata 时钟中断的四个坑
1. **只开 `sie.STIE` 没开 `sstatus.SIE`**：中断挂起但永远不进入 trap，表现为「定时器不响」。
2. **忘了重新 `set_timer`**：第一次中断后 `mtimecmp` 不再前进，只有一次 tick。
3. **在 handler 里打印太多**：UART 轮询很慢，10 ms 的 tick 可能被打印拖成 100 ms；教学 demo 可以，真实调度器不能这么干。
4. **`rdtime` 被 `mcounteren` 禁止**：S 态执行 `rdtime` 触发 illegal instruction，而你的 handler 又用 `rdtime` 打印，形成递归。
:::

### 1.18.8 小结

这一节的形状是「**一个不断自我预约的闹钟**」：`mtime` 是全局单调时钟，`mtimecmp` 是每个人（每 hart）自己的一根线，涨过线就出事；而 S 态连那根线都碰不到，只能靠 SBI `set_timer` 请 M 态代拨。所以代码里最容易被忽略的一行不是 `csrw sie`，而是 handler 里那句 `set_next_timer()`——闹钟是一次性的，不重新预约就只响一次。剩下的两个使能位（`sie.STIE` 决定这类中断允不允许，`sstatus.SIE` 决定此刻屏不屏蔽）合起来才是「能不能进」，这也是本节四个坑里最靠前的两个。如果只记住一件事：**「中断没来」和「中断没被处理」是两件事**——前者查使能位与阈值，后者查 `scause` 的判读和分发。

**Q1（记忆）** 从 `mtime` 涨过阈值到 S 态 handler 开始执行，按顺序说出经过的四个硬件/软件位置。

**Q2（辨析）** `sie.STIE` 和 `sstatus.SIE` 都能让 tick 进不来，它们的差别在哪？

**Q3（应用）** 程序打印出 `tick 1` 后卡住不再输出，但没崩。给出两个原因和各自的判据。

::: sol 答案
**A1** CLINT 的 `mtimecmp` 比较逻辑置 `mip.MTIP` → M 态 trap（cause 7）→ M 态 handler 写新的 `mtimecmp`、清 `MTIP`、置 `sip.STIP` → S 态 trap，`scause` 最高位为 1 且编码为 5（S 态定时器中断）。
**A2** `STIE` 是「这一类」的总开关，管的是 S 态定时器中断这一路；`SIE` 是「此刻」的屏蔽位，管所有可屏蔽 S 态中断。`STIE=0` 时 `sip.STIP` 仍会挂起，只是不触发；在 handler 里临时清 `SIE` 是防止嵌套的常用手段，出栈前置回即可。判据是读 `sip`/`sie` 与 `sstatus`：挂起位为 1 而没进 trap，多半是使能或全局屏蔽的问题。
**A3** 其一，handler 忘了再调 `set_timer`，`mtimecmp` 停在原地，`MTIP` 清掉后不再置起——判据：在 M 态 handler 打一行日志，只出现一次；或读 `mtimecmp` 发现它不再前进。其二，第一次进 handler 后没有恢复 `sstatus.SIE`（或 `STIE` 被清），中断永远进不来——判据：程序还在跑 `spin_loop`，说明不是死循环卡住，而是 tick 不再送达；`rdtime` 仍在涨可以佐证时钟没停。
:::
:::

## 1.18.9 QEMU、GDB 与 objdump 实验 {#sec-1.18.9}

这一节回答：一台没有 RISC-V 硬件的机器上，怎么确认「内核的第一条指令在哪、段摆在哪儿、trap 入口对不对」？手上没有 QEMU 时，哪些结论只能停在纸面？

::: preview 先抓住一件事
裸机调试只有三件可靠的东西：** ELF 自己**（`readelf -h` 的 `Entry`、`readelf -S` 的段地址）、**反汇编**（`objdump -d` 的第一批指令）、**运行时的寄存器**（QEMU+GDB 的 `info registers pc sp`）。前两件在本机就能做；第三件需要 QEMU，本书环境里没有装，所以本节把「查什么、看到什么算对」讲清，运行结果一律标未实测。
:::

::: errata 本节的实测边界
本机（Ubuntu 24.04.5 aarch64 虚拟机与 Apple 芯片 macOS 写作机）**没有 `qemu-system-riscv64`、没有 riscv64 的 rustc 目标库**，因此下面的命令与期望输出都标「未实测（无 RISC-V 硬件/QEMU）」，只作判读用；1.18.4 里写作机 clang 出 riscv64 汇编的失败原文是实测。
:::

### 实验一：确认入口与段布局

```bash
ELF=target/riscv64gc-unknown-none-elf/release/hello
llvm-readelf -h "$ELF" | grep -E 'Entry|Machine|Class'
llvm-readelf -S "$ELF" | grep -E '\.text|\.rodata|\.data|\.bss'
llvm-objdump -d --no-show-raw-insn "$ELF" | sed -n '1,30p'
```

</div>

### 实验二：QEMU + GDB 单步启动

<div class="variant" data-arch="riscv64" data-lang="all">

```bash
# 终端 1：QEMU 冻结在第一条指令，等待 GDB

# 终端 2：连接并检查
gdb-multiarch target/riscv64gc-unknown-none-elf/release/hello \

    -ex 'continue'
```

### 1.18.9 小结

三步顺序不能倒：先用 `readelf -h` 确认 `Entry` 是 `0x80200000`，再用 `readelf -S` 看 `.text` 是否落在预期地址，最后才谈 GDB 单步。如果前两步就不对，GDB 里看到的一切都是错位的。如果只记住一件事，那就是：**入口地址由链接脚本决定，而 `0x80200000` 这个值由 OpenSBI 占掉的低 2 MiB 决定**——它不是硬件规定，换一台机器（`-bios none`）就换成 `0x80000000`。

::: ex 例 1.18.9 · 先猜入口地址 {#ex-1.18.9}
把内核链接到 `0x80000000` 后用 `qemu-system-riscv64 -machine virt -bios default -kernel hello` 启动。先猜：QEMU 会打印出 `hello` 的第一个字符吗？`readelf -h` 的 `Entry` 会是多少？

::: sol 解答
`Entry` 会诚实地显示 `0x80000000`——链接脚本说了算，与硬件无关。但启动大概率没有任何输出：`-bios default` 让 OpenSBI 占据 `0x80000000` 起的 2 MiB，内核镜像要么覆盖固件、要么被固件盖住，`mret` 跳到 `0x80200000` 时那里不是你的代码。判据是「先看 `Entry`，再看 `-bios` 参数，最后才怀疑代码」；把链接地址改成 `0x80200000` 即可。**这条推理链本身是纸面结论，本机无 QEMU，未实测。**
:::
:::

::: method 即时自测 · 1.18.9
**Q1（记忆）** 三条命令各回答哪个问题：`readelf -h`、`readelf -S`、`objdump -d`？

**Q2（判断）** `Entry` 是 `0x80000000` 而 `-bios default`，可能出现什么现象？按什么顺序排除？

**Q3（实验）** 没有 QEMU 时，你能在本机对内核 ELF 做哪两件可靠检查？

::: sol 答案
**A1** `-h` 回答「入口在哪、是哪个架构、32 还是 64 位」；`-S` 回答「每个段/节在虚拟地址空间的什么位置、多大、什么权限」；`-d` 回答「入口处的第一批指令是什么、有没有跳飞」。

**A2** 典型现象是无输出或反复复位。顺序：先确认 `Entry` 与 `-bios` 是否配套（`default` 要求 `0x80200000`），再用 `objdump -d` 看入口第一条指令是否合法，最后才怀疑启动代码本身。

**A3** 静态的两件：`readelf -h/-S` 读入口与段布局；`objdump -d` 或 `llvm-objdump` 读入口指令序列。运行时观测（寄存器、单步、断点命中）需要 QEMU 或真机，本机做不到，标未实测。

## 1.18.10 本章小结 {#sec-1.18.10}

这一节回答：从「上电的第一条指令」走到「能被时钟中断抢占的 S 态内核」，中间哪几步最容易错？错了之后手上有什么证据？

::: preview 先抓住一件事
判据是：**给你一份内核 ELF 与一段启动代码，你能说出入口地址该是多少、trap 来了硬件替你存了什么、内核必须自己存什么，并指出「定时不响」「一 `ecall` 就死循环」这两类现象各查哪个寄存器。**
:::

这一章的主线是**从 M 态到 S 态的一级一级台阶**。1.18.1–1.18.3 立地基：RISC-V 的 32 个整数寄存器与 CSR 家族、M/S/U 三个特权级与 trap 的进入退出路径、SBI 作为「内核向固件借手」的契约。1.18.4–1.18.6 把第一个能打印的程序立起来：链接脚本与 `_start`、启动链与内存地图、绕开 SBI 直接写 16550A 的 MMIO。1.18.7–1.18.9 补上异常控制流与观测：`trap` 入口为什么要保存 32 个寄存器、时钟中断如何从 CLINT 经 SBI 变成抢占、以及没有 QEMU 时能用 `readelf`/`objdump` 做哪些可靠检查。

逐条打勾的达标表在[学习目标自检表](ch18-checklist.md)。这里只留判据：

- **能解释**：为什么内核要链接到 `0x80200000`、`mret`/`sret` 各改变什么、`sepc` 为什么指向 `ecall` 本身、S 态为什么不能直接写 CLINT。
- **能操作**：读 `readelf -h/-S` 确认入口与段、用 `objdump -d` 核对入口指令、按「`stvec` → `sie.STIE` → `sstatus.SIE`」的顺序检查中断是否真的开着。
- **能判断**：无输出、反复复位、只输出一半、时钟只响一次、`illegal instruction`、store access fault 各属于哪一层，先查哪个寄存器或哪段地址。

如果只记住一件事，那就是**特权级切换只切换「谁能做什么」，不替你保存任何状态**：硬件写 `sepc`/`scause`/`stval`、跳到 `stvec`，32 个通用寄存器要内核自己存——`sscratch` 与 TrapFrame 的全部意义就在这里。

下面是本章的陷阱清单与自测，按「现象 → 原因 → 修复」三段查。


::: errata 启动与输出的四个坑
1. **现象**：QEMU 无输出，PC 停在 `0x80000000`。**原因**：用了 `-bios default` 但链接到 `0x80000000`，镜像覆盖了 OpenSBI。**修复**：链接到 `0x8020_0000`。
2. **现象**：QEMU 反复 reset。**原因**：入口地址处不是合法指令，触发异常后 OpenSBI 重启。**修复**：检查 `ENTRY` 与 `.text.entry`，用 `objdump` 看第一条指令。
3. **现象**：打印第一个字符后卡死。**原因**：UART 轮询 `LSR.THRE` 时读错偏移，或没初始化 `LCR`。**修复**：确认 `LSR=0x05`、`THR=0x00`，先写 `LCR=0x03`。
4. **现象**：`println!` 只输出一半。**原因**：`panic` 里又触发中断，UART 被重入。**修复**：panic 路径关中断，或用自旋锁保护输出。
:::

::: errata trap 与时钟中断的五个坑
5. **现象**：`ecall` 后程序回到同一条 `ecall`，死循环。**原因**：忘了 `sepc += 4`。**修复**：在系统调用返回前加 4。
6. **现象**：时钟中断只来一次。**原因**：handler 里没有重新 `set_timer`。**修复**：每次 tick 重新设 `mtimecmp`。
7. **现象**：定时器完全不响。**原因**：只开了 `sie.STIE`，没开 `sstatus.SIE`；或 `stvec` 没设。**修复**：按「stvec → STIE → SIE」顺序初始化。
8. **现象**：S 态读 `mtime` 触发 illegal instruction。**原因**：`mcounteren.TM=0`。**修复**：让 OpenSBI 放行，或改用 SBI `TIME`。
9. **现象**：S 态写 `0x0200_4000` 触发 store access fault。**原因**：CLINT 是 M 态设备，PMP 不允许 S 访问。**修复**：用 SBI `set_timer`，不要直接写。
:::

::: method 即时自测 · 1.18
**Q1** QEMU `virt` 上电后 CPU 从哪里、以哪个特权级开始执行？OpenSBI 为什么要求内核链接到 `0x8020_0000` 而不是 `0x8000_0000`？

**Q2** S 态 trap 发生时，硬件自动做了什么、跳到哪里？内核为什么要维护 `sscratch` 指向的 TrapFrame？`ecall` 触发的 trap 返回前为什么要 `sepc += 4`？

**Q3** 时钟频率 10 MHz，想要每 10 ms 一次 tick：调 SBI `set_timer` 时 `a0` 应该传什么值？为什么不能自己写 `0x0200_4000`？handler 处理完还要做什么，否则下次不响？

**Q4** SBI `putchar` 和直接写 16550A 的 `THR` 各有什么取舍？直接写之前为什么要轮询 `LSR.THRE`？

::: sol 答案
**A1** 上电后先跑 M 态固件：ZSBL 加载 OpenSBI，OpenSBI 完成初始化后用 `mret` 把特权级降到 S，跳到 `0x8020_0000` 执行内核第一条指令。`0x8000_0000` 起始的 2 MiB 被 OpenSBI 自身占用，内核链接到那里会覆盖固件（或被覆盖），典型现象是 QEMU 无输出、PC 停住；只有 `-bios none` 时才让内核从 `0x8000_0000` 开始。

**A2** 硬件把当前 pc 写进 `sepc`、原因写进 `scause`、附加信息写进 `stval`，然后跳到 `stvec` 指向的入口并屏蔽 S 态中断。通用寄存器硬件不保存，内核先借 `sscratch` 拿到 TrapFrame 地址，把 32 个寄存器存进去再分发。`ecall` 的 `sepc` 指向 `ecall` 指令本身，直接 `sret` 会回到同一条指令死循环，返回前 `+4` 才能跳到下一条。

**A3** 先读当前时间（`rdtime` 或 SBI `get_time`），加上 10 ms × 10 MHz = 100 000 个 tick，把绝对时间 `当前 + 100_000` 放进 `a0`，EID `0x54494D45`、FID `0`，`ecall`——`mtimecmp` 写的是绝对时间而不是间隔。`0x0200_4000` 是 M 态 CLINT 的 MMIO，S 态写它会被 PMP 拒绝（store access fault），只能让固件代写。每次 tick 处理完要重新 `set_timer`，否则中断只来一次。

**A4** SBI 输出每次一个字符要做一次 `ecall`，可移植、与固件共享输出通道，但慢；直接 MMIO 不经过固件、快，但地址绑定板卡，还要自己初始化 `LCR=0x03`、`FCR`、关 `IER`。写 `THR` 前轮询 `LSR`（偏移 `0x05`）的 bit5 `THRE`，等发送保持寄存器空了再写，否则会覆盖还没移位发完的字符。
:::
