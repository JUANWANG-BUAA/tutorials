## 1.15.1 调用的契约：call、返回地址与 ret {#sec-1.15.1}

这一节回答：一条 `call` 跳走以后，CPU 凭什么知道该回到哪里继续执行？为什么 ARM64 的栈里也常能看到返回地址，而它的 `ret` 却不从栈上取？

::: preview 先抓住一句话
x86-64 把返回地址放进内存（栈顶），ARM64 与 RISC-V 把它放进寄存器（`x30` / `ra`）。三家的 `ret` 长得一样，做的事并不一样。
:::

先看一个场景。[1.3](ch03.md#sec-1.3.6) 用 x86-64 讲过栈帧，你在那里记住了「返回地址在栈上」。换到 ARM64 汇编，函数开头的 `stp x29, x30, [sp, #-16]!` 很自然会读成「把返回地址压进栈」。可往下看：`ret` 之前并没有从栈上把地址读回来。栈里那份副本确实在，但 `ret` 用的不是它。

一次过程调用要同时完成三件事：把控制交给被调用者；让被调用者知道返回后从哪里继续；让双方对「哪些寄存器可以随便改」有共同预期。前两件由 ISA 的几条指令完成，第三件由 ABI 补上，寄存器的分工留到 1.15.2。

| 机制 | x86-64 | ARM64 | RISC-V 64 |
|:--|:--|:--|:--|
| 调用指令 | `call foo` | `bl foo` | `jal ra, foo` / `call foo` |
| 返回地址放在哪 | `call` 压入栈顶 | `x30`（LR） | `ra`（`x1`） |
| 返回指令 | `ret`（弹出栈顶到 `rip`） | `ret`（跳到 `x30`） | `ret`（`jalr x0, 0(ra)`） |
| 嵌套调用前 | 返回地址已在栈上，无需额外保存 | 通常 `stp x29, x30, [sp, #-16]!` | 通常 `sd ra, 8(sp)` |
| 叶子函数 | 可以完全不碰栈 | 可以完全不碰栈 | 可以完全不碰栈 |
| 返回地址可被覆盖 | 栈溢出可覆盖 | 栈上的 LR 副本可覆盖 | 栈上的 `ra` 副本可覆盖 |

读表只看第二行和第三行：**返回地址存在哪，`ret` 从哪取**。这两件事必须对上，否则程序会跳到一个看起来随机的地址。

三者的差异可以用一句话记住：**x86-64 把返回地址放在内存里，ARM64 和 RISC-V 把它放在寄存器里**。ARM64/RISC-V 的 `bl`/`jal` 只写链接寄存器，不写栈；所以非叶函数必须自己把 LR/`ra` 存到栈上，否则下一次调用会把它覆盖。x86-64 的 `call` 自动压栈，非叶函数反而少一条保存指令，但每次调用都多一次内存写。

多出来的这次内存写在安全上不是小事。x86-64 的返回地址和局部变量挤在同一块栈内存里，一次越界的 `strcpy` 就能把它改成任意地址。ARM64/RISC-V 上，越界写改到的是栈上的 LR 副本；攻击者还得等函数在尾声真的 `ldp` 恢复它才生效。难一些，但不是不可能，所以三家都有栈保护。

```asm
    subq    $8, %rsp          # 对齐到 16 字节；进入函数时 rsp % 16 == 8
    call    callee            # 返回地址压栈，rip = callee
    addq    $8, %rsp
    ret

    .globl callee
    .type callee, @function
callee:
    movl    $7, %eax
    ret                       # 弹出返回地址到 rip
```

</div>

```asm
callee:
    li      a0, 7

```

::: intuition 为什么 ARM64 的 `ret` 不弹栈
`ret` 只是 `br x30`。栈上的 LR 副本是编译器为「嵌套调用」主动保存的，不是硬件约定。所以看到 `stp x29, x30, [sp, #-16]!` 不要以为它在「压返回地址」；它是在保存**当前函数的** LR 和帧指针，供本函数返回时恢复。RISC-V 的 `sd ra, 8(sp)` 同理。
:::

::: def 定义 1.15.1 · 返回地址与链接寄存器 {#def-1.15.1}
**返回地址**（return address）是调用指令之后那条指令的地址，被调用者执行完必须跳回这里。**链接寄存器**（link register）是专门装它的寄存器：ARM64 是 `x30`，RISC-V 是 `ra`，也就是 `x1`。它只有一份，所以函数只要再调用别人，就得先把旧值存进内存。
:::

::: errata 关于返回地址的三个误解
1. **「`ret` 总是从栈顶弹地址」**：只有 x86-64 是。ARM64 的 `ret` 就是 `br x30`，RISC-V 的 `ret` 是 `jalr x0, 0(ra)`；`x0` 恒为 0，表示「不把返回地址写回任何寄存器」，所以它是一次纯跳转。
2. **「栈上没有返回地址就回不去」**：ARM64/RISC-V 的叶子函数完全不碰栈也能返回，因为 `x30`/`ra` 从入口到出口没被改过。
3. **「三家的 `ret` 可以互换」**：助记符一样，机器码与语义都不同；把 x86 的 `ret` 原样抄进 ARM64 汇编，汇编器会直接报错。
:::

### 1.15.1 小结

调用只做两件事：跳过去，记住从哪回来。记住的方式分两派：x86-64 交给栈，ARM64/RISC-V 交给寄存器；非叶函数因此要自己保存 LR/`ra`。如果只记住一件事：**`ret` 取的是寄存器里的地址，栈上那份只是副本**。

**A2** 不能。压栈的是**当前函数**的帧指针与 LR 副本，`ret` 仍然跳 `x30`。副本的用途是：本函数调用别人时 `x30` 会被覆盖，返回前用它恢复。
**A3** 至少保存 LR，典型写法是 `stp x29, x30, [sp, #-16]!`，返回前 `ldp` 恢复。`bl printf` 会覆盖 `x30`，不保存就回不到调用者。

## 1.15.2 寄存器与 ABI：谁保存、谁传参 {#sec-1.15.2}

这一节回答：一次调用前后，哪些寄存器被调用者可以随便改，哪些必须原样还回来？参数和返回值又各走哪几个寄存器？

::: preview 先抓住一句话
ABI 把寄存器分成三堆：传参用的、调用者保存的、被调用者保存的。读汇编先查这三堆，比从指令猜参数快得多。
:::

先看一个常见故障。你手写了一个小函数，C 代码在循环里反复调用它，循环变量从第二次起就不对了。算术没写错，问题出在你在函数里用了 `rbx`（或 `x19`、`s1`）却没恢复：那是「被调用者保存」寄存器，调用者默认它回来时和进去时一样。

ABI 的核心就是下面这张责任表。看到一段陌生汇编，先查表，再读指令。

| 类别 | x86-64 SysV | ARM64 AAPCS64 | RISC-V 64 psABI |
|:--|:--|:--|:--|
| 整数参数 | `rdi, rsi, rdx, rcx, r8, r9` | `x0`–`x7` | `a0`–`a7` |
| 浮点参数 | `xmm0`–`xmm7` | `v0`–`v7` | `fa0`–`fa7` |
| 返回值 | `rax`；128 位用 `rdx:rax` | `x0`；128 位用 `x1:x0` | `a0`；128 位用 `a1:a0` |
| 被调用者保存 | `rbx, rbp, r12`–`r15` | `x19`–`x29`；`v8`–`v15` 低 64 位 | `s0`–`s11`（`x8,x9,x18`–`x27`） |
| 调用者保存 | `rax, rcx, rdx, rsi, rdi, r8`–`r11` | `x0`–`x17`（`x18` 平台保留） | `a0`–`a7`, `t0`–`t6` |
| 栈指针 | `rsp` | `sp` | `sp`（`x2`） |
| 帧指针 | `rbp`（可选） | `x29`（可选） | `s0`/`fp`（可选） |
| 链接寄存器 | 无（在栈上） | `x30` | `ra`（`x1`） |
| 零寄存器 | 无 | `xzr`（`x31` 的一种视图） | `x0`（硬连线 0） |
| 栈对齐 | 调用前 16 字节 | 公共接口 16 字节 | 16 字节 |
| 红区 | 128 字节（叶子函数可用） | 无 | 无 |
| 变参调用标记 | `%al` = 使用的向量寄存器数 | 匿名参数主要走栈 | 无专用标记，`va_list` 保存寄存器区 |

表里最容易读错的是「整数参数」那一行。x86-64 只有 **6 个**整数参数寄存器：`rdi, rsi, rdx, rcx, r8, r9`；第 7 个整数参数起就走栈。ARM64 有 **8 个**（`x0`–`x7`），RISC-V 也有 **8 个**（`a0`–`a7`），它们第 9 个才上栈。把「6 个」当成三家通用，是跨架构读汇编最常见的错。浮点参数另有一套：`xmm0`–`xmm7`、`v0`–`v7`、`fa0`–`fa7`，与整数参数各数各的，互不占位。

几个容易读错的点：

- **`x30` 不是被调用者保存寄存器**。它是链接寄存器；一个函数如果还要调用别人，必须在调用前保存它，返回前恢复。ABI 表里通常把 `x30` 单列为「特殊」，因为「该不该保存」取决于函数自己是否还要调用别人。
- **ARM64 的 `v8`–`v15` 只保证低 64 位**。传 `__m128`/`float64x2_t` 时，高 64 位可能被破坏；需要完整 128 位就自己保存。
- **RISC-V 的 `gp`/`tp` 不是普通通用寄存器**。`gp` 用于全局指针（PIC 的锚点），`tp` 指向线程控制块；用户代码不要拿它们做临时变量。`x0` 恒为 0，写它等于丢弃结果。
- **x86-64 的 `rbp` 是可选的帧指针**。`-fomit-frame-pointer`（`-O2` 默认）会把它当普通被调用者保存寄存器用；调试时用 `-fno-omit-frame-pointer` 换可回溯性。
- **栈对齐是调用点的责任**。x86-64 在 `call` 之前 `rsp % 16 == 0`；`call` 压入 8 字节后，被调用者入口是 `rsp % 16 == 8`。ARM64/RISC-V 在公共接口处要求 `sp % 16 == 0`，函数内部只要不破坏这个条件即可。
- **红区只有 x86-64 有**。SysV 允许叶子函数使用 `rsp` 以下 128 字节而不调整 `rsp`；信号处理时内核会跳过这块区域。ARM64/RISC-V 没有这个保证，任何「往栈上写」都必须先减 `sp`。

为什么要有「谁保存」的分工？如果每次调用都把几十个寄存器存一遍，函数调用会慢到不可用。ABI 让调用者只保存自己跨调用还要用的活值，让被调用者只保存自己真正改过的那几个。这是一笔性能账，代价是双方都必须守约。

::: def 定义 1.15.2 · 调用者保存与被调用者保存 {#def-1.15.2}
**调用者保存**（caller-saved / volatile）：被调用者可以随意改写，调用者若在调用后还要用，必须自己先保存。**被调用者保存**（callee-saved / non-volatile）：被调用者若要用，必须先保存原值，返回前恢复；调用者可以假设调用前后值不变。ABI 用这条分工避免每次调用都保存全部寄存器。
:::

红区值得单独说。x86-64 SysV 允许叶子函数使用 `rsp` 以下 128 字节，而不调整 `rsp`；信号处理时内核会跳过这块区域，不会把它踩掉。ARM64 和 RISC-V 没有红区，任何「往栈上写」都必须先减 `sp`。所以同一个叶子函数，x86-64 上可以把局部缓冲区直接放在红区、一条 `sub` 都不写；ARM64 上一定先有一条减小 `sp` 的指令。

### 1.15.2 小结

寄存器责任表回答两个问题：参数从哪取、值跨调用还在不在。x86-64 六个整数参数寄存器、第 7 个起上栈；ARM64/RISC-V 各八个，第 9 个才上栈。如果只记住一件事：**你改了一个被调用者保存寄存器，就必须在返回前把它改回去，否则报应落在调用者身上**。

**Q2（辨析）** 一个函数用了 `rbx` 却忘了恢复，为什么有时「看起来没事」？
**Q3（应用）** 你在内联汇编里临时用 `r12` 存中间值，正确做法是什么？

::: sol 答案
**A1** 第 7 个：x86-64 已在栈上（调用者放在返回地址之上），ARM64 仍在 `x6`，RISC-V 仍在 `a6`。第 9 个：x86-64 在栈上更靠外的位置，ARM64/RISC-V 这时才上栈。
**A2** 因为调用者之后可能没再用这个寄存器，或者编译器在调用点本来就把活值换到了别处；换优化级别、换调用点就会暴露。它仍然是违约。
**A3** 先保存原值（`push %r12`，或减 `sp` 后存到栈上），用完恢复再返回；`r12` 是被调用者保存寄存器，不恢复就破坏了调用者的假设。
:::

## 1.15.3 指令对照：同一操作的三种写法 {#sec-1.15.3}

这一节回答：同一句「把内存里的值读进寄存器」，为什么三套汇编的指令条数、操作数顺序、甚至要用几条指令都不同？哪些差异只是写法，哪些会改变语义？

::: preview 先抓住一句话
助记符长得一样，不代表指令一样。x86-64 的一条 `mov`，在 ARM64 与 RISC-V 里往往要拆成「先加载、再运算、再存回」三条。
:::

先看一个真实的移植现场。你在 x86-64 汇编里读到 `mov 8(%rdi), %rax`，想改成 ARM64，于是把寄存器名换成 `x0`/`x1`，写成 `mov 8(x1), x0`。汇编器直接报错，提示你缺 `]` 或操作数类型不对。问题不在寄存器名，而在 ARM64 根本没有「内存当操作数」的 `mov`：取内存必须用 `ldr`。

下面这张表覆盖读编译器输出时最常撞见的一批操作。先记一条总规则：x86-64 的 AT&T 语法是 `op 源, 目标`，ARM64 与 RISC-V 是 `op 目标, 源1, 源2`。

| 操作 | x86-64（AT&T） | ARM64 | RISC-V 64 |
|:--|:--|:--|:--|
| 加载 8 字节 | `mov 8(%rdi), %rax` | `ldr x0, [x1, #8]` | `ld a0, 8(a1)` |
| 存 8 字节 | `mov %rax, 8(%rdi)` | `str x0, [x1, #8]` | `sd a0, 8(a1)` |
| 加法 | `add %rsi, %rax` | `add x0, x0, x1` | `add a0, a0, a1` |
| 立即数加法 | `add $16, %rsp` | `add sp, sp, #16` | `addi sp, sp, 16` |
| 比较并跳转 | `cmp %rsi, %rdi; jg L` | `cmp x0, x1; b.gt L` | `bgt a0, a1, L` |
| 调用 | `call foo` | `bl foo` | `call foo` |
| 返回 | `ret` | `ret` | `ret` |
| 栈分配 | `sub $32, %rsp` | `sub sp, sp, #32` | `addi sp, sp, -32` |
| 取地址 | `lea 8(%rdi), %rax` | `add x0, x1, #8` | `addi a0, a1, 8` |
| 乘加地址 | `lea (%rdi,%rsi,4), %rax` | `add x0, x1, x2, lsl #2` | `slli t0, a2, 2; add a0, a1, t0` |
| 系统调用 | `syscall` | `svc #0` | `ecall` |
| 内存屏障 | `mfence` | `dmb ish` | `fence rw, rw` |
| 原子比较交换 | `lock cmpxchg` | `casal`（ARMv8.1 LSE） | `amocas.d`（Zacas）或 `lr.d/sc.d` |
| 空操作 | `nop` | `nop` | `addi x0, x0, 0` |

读这张表要分三层，不要只背指令名。

**第一层是操作数顺序。** x86 的 `add %rsi, %rax` 意思是 `rax = rax + rsi`，源在前；ARM64 的 `add x0, x0, x1` 与 RISC-V 的 `add a0, a0, a1` 都是目标在左。把 `add` 抄过去却按 x86 的顺序读，结果会把两个操作数反过来。

**第二层是访存方式。** 只有 x86 允许「内存直接当操作数」：一条 `mov` 就能读、能写。ARM64 与 RISC-V 是 load/store 架构：数据必须先 `ldr`/`ld` 进寄存器，算完再 `str`/`sd` 写回。所以同一句 `p->x += 1`，x86 可能两条指令，ARM64 至少三条。

**第三层是「有没有标志寄存器」。** x86 与 ARM64 的比较指令只设置条件码，跳转指令再读它；RISC-V 没有标志寄存器，`bgt a0, a1, L` 直接把两个寄存器比完就跳。这一层差异不能靠查表翻译，必须重写。

其余几条边界也要知道：

- **`mov` 在三家不是一回事**。x86 的 `mov` 既搬寄存器也读写内存；ARM64 的 `mov` 只是寄存器之间（本质是 `orr xd, xn, xzr`）；RISC-V 的 `mv` 是 `addi rd, rs, 0`。搬内存一律用 `ldr`/`str`、`ld`/`sd`。
- **`lea` 的名字骗人**。x86 的 `lea 8(%rdi), %rax` 只做地址算术，不读内存；ARM64 对应 `add x0, x1, #8`，RISC-V 对应 `addi a0, a1, 8`。
- **立即数有编码上限**。RISC-V 的 `addi` 立即数只有 12 位，超出要先 `li` 装进寄存器再 `add`；ARM64 的 `add` 立即数也有位宽限制。x86 的 `add $imm` 宽松得多。
- **扩展指令不是基线**。RISC-V 的 `sh1add`/`sh2add`/`sh3add` 属于 Zba 扩展；写可移植代码时用 `slli` + `add`。ARM64 的 `casal` 需要 ARMv8.1-LSE，老核只有 `ldaxr`/`stlxr` 循环。x86-64 的 `cmpxchg` 不加 `lock` 只在单核上原子。

现在把表变成代码。`max3` 返回三个 `long` 的最大值，参数正好落在三套 ABI 的前三个整数参数寄存器：x86-64 的 `rdi/rsi/rdx`、ARM64 的 `x0/x1/x2`、RISC-V 的 `a0/a1/a2`；结果写回第一个返回值寄存器（`rax`/`x0`/`a0`）。先猜一猜：三份汇编里，哪一份完全没有分支？

答案是 x86-64 与 ARM64 两份：它们用条件移动（`cmovl`/`csel`），一条分支都没有。RISC-V 基线没有条件移动，只能 `blt` 加 `mv`。

逐份读，注意三件事：

- x86-64 的 `cmpq %rsi, %rax` 算 `rax - rsi`、只设标志，`cmovl` 再读标志；ARM64 的 `cmp x0, x1` 同样只设条件位；RISC-V 的分支指令直接比较两个寄存器，没有标志可读。
- x86 与 ARM64 的「比较 + 选择」各两条，是同一思路；RISC-V 用两个局部标签绕开条件移动，指令数相近但形状不同。
- RISC-V 的 `1:`、`2:` 是局部数字标签，`1f` 表示「往前找最近的 `1:`」。用数字标签可以避免和函数名撞车。

所以「同一操作三种写法」的差异分两层：语法层（操作数顺序、访存方式）可以查表翻译；语义层（标志寄存器、条件移动、扩展指令）必须按 ISA 重写。这也解释了三套汇编为什么不能互搬。

::: errata 三套汇编不能互搬
1. **「改寄存器名就能移植」**：`mov 8(%rdi), %rax` 在 ARM64 没有对应单条指令，要先 `ldr x0, [x1, #8]`；x86 是两操作数且允许内存操作数，ARM64/RISC-V 是三操作数、访存独立成指令。
2. **「交叉汇编成功就说明能跑」**：`-S`/`-c` 只证明语法与目标架构对，不证明能链接、能执行。ABI 差异（参数寄存器数量、栈对齐、系统调用号）照样能让程序跑飞。本书的交叉汇编只做到 `-S`/`-c`，不写运行时间。
3. **「三套目标文件都能在本机生成」**：写作机的 clang 21 注册了 x86-64、aarch64、arm 等目标，没有 RISC-V；`--target=riscv64-linux-gnu` 会直接报选项错误。RISC-V 的两段汇编只能按 psABI 阅读，未实测。
:::

::: ex 例 1.15.3 · 先猜同一段 C 编出几条指令 {#ex-1.15.3}
`long add3(long a, long b, long c) { return a + b + c; }` 在 x86-64、AArch64、RISC-V 64 上各编译一次（只到 `-S`）。先猜：三家的第一条指令分别是什么？返回值的寄存器各是谁？为什么 x86-64 少一条 `mov` 就做不到？

::: sol 解答
x86-64 是两操作数指令：`addq %rsi, %rdi` 后再 `addq %rdx, %rdi`，最后把结果 `movq %rdi, %rax` 返回——因为参数寄存器与返回寄存器不同名。AArch64 三操作数：`add x0, x0, x1` 再 `add x0, x0, x2`，`x0` 既是第一个参数又是返回值，不需要搬。RISC-V 同理：`add a0, a0, a1`、`add a0, a0, a2`，`a0` 兼作返回值。差别不在快慢，而在**指令格式与寄存器角色重叠与否**；三家的机器码与指令条数都不通用。
:::
:::

### 1.15.3 小结

三套汇编的差异分两层：语法层（源/目标顺序、内存操作数、伪指令）和语义层（标志寄存器、条件移动、扩展）。语法可以查表，语义必须重写。如果只记住一件事：**先问「这条指令读不读内存」，再问「它改不改标志位」**。

**Q3（应用）** x86 的 `lea 8(%rdi), %rax` 换成 ARM64 怎么写？它访存吗？

::: sol 答案
**A1** ARM64 是 `ldr x0, [x1, #8]`；RISC-V 是 `ld a0, 8(a1)`。
**A2** RISC-V 没有条件码寄存器，分支指令自带比较；x86/ARM64 的 `cmp` 只设标志，跳转再读标志，所以总要两条。
**A3** `add x0, x1, #8`。不访存：`lea` 只算地址，名字里的 load 是历史包袱。

## 1.15.4 序言、尾声与栈帧 {#sec-1.15.4}

这一节回答：函数开头那几行 `push`、`sub`、`stp` 到底在算什么？为什么换成 `-O2` 之后它们整段消失，1.15.1 的规则还成不成立？

::: preview 先抓住一句话
序言只做三件事：给局部变量腾空间、保存本函数要用的被调用者保存寄存器、必要时建立帧指针并保存 LR。编译器算出来不需要，就一条都不生成。
:::

同一份代码，优化级别不同，栈帧可以差出十几条指令。下面这段 `framed` 在 VM（Ubuntu 24.04 aarch64，GCC 13.3）上编两次。先看 `-O0` 序言的前五行（`.cfi_*` 是调试信息，缩进统一为空格）：

```asm
# VM: Ubuntu 24.04 aarch64, gcc 13.3, gcc -O0 -S（节选）
framed:
    sub     sp, sp, #64
    stp     x29, x30, [sp, 48]
    add     x29, sp, 48
    str     x0, [sp, 8]
    str     x1, [sp]
```

尾声正好相反（同样省略 `.cfi_*` 行）：

```asm
    ldp     x29, x30, [sp, 48]
    add     sp, sp, 64
    ret
```

同机换 `-O2`，整个函数只剩四条指令：

```asm
# VM: 同机 gcc -O2 -S（节选）
framed:
    add     x1, x1, 1
    add     x1, x1, x0, lsl 1
    add     x0, x1, x0
    ret
```

怎么读这三段：

- `sub sp, sp, #64` 是腾出 64 字节的帧。为什么不是 16？除了局部变量，还要放保存的 `x29`/`x30`、栈保护 canary 和对齐填充。具体数字随编译器版本与发行版默认选项变，不能当常数背。
- `stp x29, x30, [sp, 48]` 把 `x29` 与 `x30` 存到帧的高地址端（偏移 48 与 56），`add x29, sp, 48` 再让 `x29` 指向这块保存区，后面用 `[x29, #-...]` 定位局部变量。
- `str x0, [sp, 8]`、`str x1, [sp]` 是 `-O0` 的典型动作：把两个参数原样落栈，保证调试器里能看到它们。
- `-O2` 那四条是化简与内联的结果：`3*x + y + 1` 用两条 `add` 加一条移位算完，既不需要局部变量地址，也没有跨调用状态，序言与栈一起消失。

x86-64 上同一段 C 在 clang 21 的 `-O0` 下是这样（写作机 macOS，`--target=x86_64-linux-gnu`，只汇编不链接）：

```asm
# macOS clang 21, --target=x86_64-linux-gnu -O0 -S（节选）
framed:
    pushq   %rbp
    movq    %rsp, %rbp
    subq    $48, %rsp
    movq    %rdi, -8(%rbp)
    movq    %rsi, -16(%rbp)
```

`push %rbp` 保存调用者的帧指针（返回地址已经由 `call` 压过，不在这一行）；`mov %rsp,%rbp` 建立本帧；`sub $48` 腾空间；两条 `movq` 把 `rdi`/`rsi` 落栈。尾声是 `addq $48,%rsp; popq %rbp; retq`，顺序与序言相反。

这里没有 `push %rbx`：clang 选择把 `x` 落栈、每次从 `rbp-8` 重读，而不是占一个被调用者保存寄存器。**保存寄存器和落栈是两种等价手段**，编译器按代价选；责任表约束的是「不许悄悄改坏」，不是「必须用寄存器」。

下面这份 C 就是上面两段输出的来源。三份手写汇编把它逐条展开，方便你对照每条指令对应哪一步。

```c
}
```

读三张栈图，只要抓住三个偏移：

1. **返回地址或保存的 LR 在保存区最高槽。** ARM64 的 `stp` 把 `x29` 放 `[sp,48]`、`x30` 放 `[sp,56]`，所以 `x30` 在 `x29+8`；x86-64 的返回地址在 `rbp+8`，`push %rbp` 之后 `rbp` 指向保存的旧 `rbp`。
2. **被调用者保存寄存器紧挨保存区。** 它们在更高地址，因为必须先于局部变量保存；`-O0` 下常见 `push %rbx` 或 `str x19, [sp, #16]`。
3. **局部变量在低地址侧。** 取地址的局部变量一定在 `sp` 与保存区之间；这也是缓冲区溢出能往高地址改写返回地址的原因。

`-O2` 下很多函数没有帧指针，`rbp`/`x29` 被当成普通寄存器，栈图上会少一层，但三件事（腾空间、保存、对齐）的责任划分不变。判断一个函数有没有栈帧，看它有没有减 `sp`/`rsp`，不要看有没有 `push %rbp`。

::: errata 序言/尾声的四个常见误解
1. **「每个函数都有序言」**：叶子函数可以完全没有；`max3` 连栈都不碰。
2. **「`push %rbp` 是为了保存返回地址」**：返回地址已由 `call` 压栈；它保存的是调用者的帧指针。
3. **「ARM64 的 `stp x29, x30` 是压返回地址」**：它保存的是当前函数的 FP 和 LR；`ret` 仍跳 `x30`。
4. **「栈帧大小 = 局部变量之和」**：还包括保存区、对齐填充，Ubuntu 默认的栈保护还会多一个 canary。`sub sp,sp,#64` 不等于「有 64 字节局部变量」。
:::

### 1.15.4 小结

序言与尾声是一对账本：进来时腾空间、存好要用的被调用者保存寄存器与 LR，出去时按相反顺序还回去。优化会内联、化简，把整本账消掉，所以不能用「有没有序言」判断函数复杂度。如果只记住一件事：**看栈帧先看 `sp` 减了多少，再看保存区里存了谁**。

## 1.15.5 参数传递：寄存器用完以后 {#sec-1.15.5}

这一节回答：一个函数如果有 9 个 `long` 参数，寄存器装不下时多出来的去哪？被调用者怎么知道从哪个偏移取？结构体和可变参数又让这件事复杂在哪里？

::: preview 先抓住一句话
参数寄存器是快车道，数量固定：x86-64 六个，ARM64 与 RISC-V 八个。超出的参数由调用者在 `call`/`bl` 之前摆到栈上，被调用者按固定偏移读；顺序与偏移由 ABI 定，不能猜。
:::

先写一个 9 个 `long` 参数的函数：

```c
long nine(long a, long b, long c, long d, long e,
          long f, long g, long h, long i)
{
    return a + b + c + d + e + f + g + h + i;
}
```

在 VM（Ubuntu 24.04 aarch64，GCC 13.3）上 `cc -O0 -S`，`nine` 的序言是八条 `str`，第 9 个参数则从 `[sp, #64]` 读：

```asm
# VM: gcc 13.3 aarch64, -O0 -S（节选）
nine:
    sub     sp, sp, #64
    str     x0, [sp, #56]      // 第 1 个
    str     x1, [sp, #48]
    ...
    str     x7, [sp]           // 第 8 个
    ...
    ldr     x0, [sp, #64]      // 第 9 个：入口时在 [sp]
```

`sub sp, sp, #64` 之后，原来的栈顶变成 `sp+64`，所以第 9 个参数从 `[sp, #64]` 读；入口那一刻（还没减 `sp`），它就在 `[sp]`。

同一段 C 交给写作机的 clang 21 交叉生成 x86-64 汇编（`--target=x86_64-linux-gnu -O0 -S`，只生成汇编，不链接、不运行）：

```asm
# macOS clang 21, --target=x86_64-linux-gnu -O0 -S（节选）
nine:
    pushq   %rbp
    movq    %rsp, %rbp
    movq    32(%rbp), %rax     // 第 9 个
    ...
    addq    16(%rbp), %rax     // 第 7 个
    addq    24(%rbp), %rax     // 第 8 个
    addq    32(%rbp), %rax     // 第 9 个
```

x86-64 入口时 `[rsp]` 是返回地址，所以第 7 个在 `[rsp+8]`、第 8 个在 `[rsp+16]`、第 9 个在 `[rsp+24]`；`push %rbp` 之后整体上移 8 字节，变成 `[rbp+16]`、`[rbp+24]`、`[rbp+32]`。**偏移是相对谁说的，必须先问清楚**。

三套 ABI 的完整规则：

| 项目 | x86-64 SysV | ARM64 AAPCS64 | RISC-V 64 psABI |
|:--|:--|:--|:--|
| 整数参数寄存器 | `rdi, rsi, rdx, rcx, r8, r9`（6 个） | `x0`–`x7`（8 个） | `a0`–`a7`（8 个） |
| 第 7 个整数参数 | 栈上 `[rsp+8]` | `x6` | `a6` |
| 第 8 个整数参数 | 栈上 `[rsp+16]` | `x7` | `a7` |
| 第 9 个整数参数 | 栈上 `[rsp+24]` | 栈上 `[sp]` | 栈上 `0(sp)` |
| 谁摆栈参数 | 调用者，`call` 前 | 调用者，`bl` 前 | 调用者，`call` 前 |
| 谁清理栈参数 | 调用者，返回后调整 `sp` | 调用者 | 调用者 |
| 每个栈槽 | 8 字节 | 8 字节（按类型对齐） | 8 字节（按类型对齐） |

这张表回答两件事：第几个开始上栈，以及入口时第一个栈参数在哪。它不回答「调用者按什么顺序摆」，因为那是调用者的事；被调用者只按 ABI 的固定偏移读，摆对是编译器的责任。

结构体是第二条规则。不超过 16 字节的结构体通常拆进 1–2 个八字节寄存器：x86-64 逐八字节分类成 INTEGER、SSE、MEMORY，两个都合法才走寄存器；ARM64 把「同类型浮点字段的聚合」叫 HFA（homogeneous floating-point aggregate），四个 `float` 可以走 `s0`–`s3`；RISC-V 的判据更直白，不超过 `2×XLEN` 且字段对齐合适就走 `a0/a1`。超过阈值就整块进内存：调用者在栈上复制一份，传首地址，被调用者改的是副本。

返回值同理：小结构体用 `rax:rdx`、`x0:x1`、`a0:a1` 带回；大结构体由调用者预先分配空间，把指针当隐藏的第一个参数传进去（x86-64 用 `rdi`，ARM64 用 `x8`，RISC-V 用 `a0`），这个指针叫 `sret`（structure return）指针。

可变参数是第三条规则。x86-64 在 `call` 前把 `%al` 设成「用到的向量寄存器个数」，因为 `va_arg` 要根据它决定要不要从 `xmm` 保存区取浮点；ARM64 的匿名参数主要直接放在栈上，`va_start` 不需要保存 `x0`–`x7`；RISC-V 则把寄存器参数先写进 `va_list` 的保存区，再按偏移取。三家的 `va_list` 布局不同，不能跨架构照抄。

下面这个 `argmix.c` 把 8 个整数、结构体、浮点和可变参数放进一个程序。先猜输出，再编译：

<div class="variant" data-arch="all" data-lang="c">

```c
/* argmix.c — 8 个整数、结构体、浮点、可变参数的完整程序
 * cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 argmix.c -o argmix
 */
#include <stdarg.h>
#include <stdio.h>

struct pair { long a; long b; };

static long sum8(long a, long b, long c, long d,
                 long e, long f, long g, long h)
{
    return a + b + c + d + e + f + g + h;
}

static struct pair make_pair(long a, long b)
{
    struct pair p = { .a = a, .b = b };
    return p;                    /* 16 字节，通常用两个寄存器返回 */
}

static double mix(long a, double x, long b, double y)
{
    return (double)a * x + (double)b * y;
}

static long sum_v(int n, ...)
{
    va_list ap;
    long total = 0;
    va_start(ap, n);
    for (int i = 0; i < n; i++)
        total += va_arg(ap, long);
    va_end(ap);
    return total;
}

int main(void)
{
    struct pair p = make_pair(30, 12);
    printf("sum8   = %ld\n", sum8(1, 2, 3, 4, 5, 6, 7, 8));
    printf("pair   = %ld + %ld\n", p.a, p.b);
    printf("mix    = %.1f\n", mix(2, 1.5, 3, 2.0));
    printf("sum_v  = %ld\n", sum_v(4, 10L, 20L, 30L, 40L));
    return 0;
}
```

</div>

```rust
}
```

在 VM 上 `cc -O2 argmix.c -o argmix && ./argmix`，输出四行：`sum8 = 36`、`pair = 30 + 12`、`mix = 9.0`、`sum_v = 100`。数字都可复算：`1+…+8=36`，`2×1.5+3×2.0=9`，`10+20+30+40=100`。

回到汇编，`sum8` 在 x86-64 上会从 `8(%rsp)`/`16(%rsp)` 取第 7/8 个参数；ARM64 与 RISC-V 则全部从 `x0`–`x7`/`a0`–`a7` 取。注意 x86-64 的偏移相对**进入函数时的 `rsp`**，不是相对 `rbp`；一旦编译器插入 `push %rbp`，偏移就变成 `16(%rbp)`/`24(%rbp)`。这也是 1.15.4 强调「先看 `sp` 减了多少」的原因。

::: errata 参数传递的五个误解
1. **「第 7 个参数三家都在栈上」**：只有 x86-64。ARM64/RISC-V 的第 7、8 个仍在 `x6`/`x7`、`a6`/`a7`，第 9 个才上栈。
2. **「栈参数偏移可以跨架构照抄」**：x86-64 入口是 `[rsp+8]` 起（`[rsp]` 是返回地址），ARM64/RISC-V 是 `[sp]` 起（入口没有返回地址压栈）；建帧后还要加上帧大小。
3. **「`%al` 是参数个数」**：它是**向量寄存器**个数，只影响浮点可变参数的保存区；整数参数个数不由它表示。`printf("%f", 1.0)` 的调用点会先 `movl $1, %eax`。
4. **「结构体不超过 16 字节就一定走寄存器」**：分类还可能因为字段不对齐、含 MEMORY 类字段而整块降级；规则看每个八字节的类别，不是总大小。
5. **「C 的结构体直接传给 Rust 就行」**：Rust 侧必须标 `#[repr(C)]`，否则默认布局可能重排字段；`String`、`Vec<T>`、`&str` 不是 FFI-safe，要换成 `CString` 或裸指针。
:::

::: ex 例 1.15.5 · 先猜第 9 个参数在哪 {#ex-1.15.5}
一个 9 个 `long` 参数的函数在三个架构上编译。先猜：`g`、`h`、`i` 三个参数各从哪取？如果 ARM64 上你从 `[sp]` 取 `g`，会读到什么？

::: sol 解答
x86-64 只有 6 个整数参数寄存器，`g`/`h`/`i` 都在栈上（入口 `[rsp+8]`/`[rsp+16]`/`[rsp+24]`）。AArch64 与 RISC-V 各有 8 个参数寄存器：`g`、`h` 在 `x6`/`x7` 与 `a6`/`a7`，**只有 `i` 在栈上**（`[sp]`）。在 ARM64 上按 x86 的习惯去 `[sp]` 取 `g`，取到的是第 9 个参数或调用者栈上的别的值——这类错误编译期不报、运行期算错，正是勘误页点名的那条。
:::
:::

### 1.15.5 小结

参数先用寄存器，用完的按 ABI 摆到栈上：x86-64 六个寄存器、第 7 个起上栈；ARM64/RISC-V 八个、第 9 个起上栈。结构体看分类而不是大小，大结构体与 `sret` 都退化成指针。如果只记住一件事：**读栈参数之前，先确认偏移是相对入口 `sp`、还是相对建帧后的 `fp`**。

## 1.15.6 完整程序二：不依赖 libc 的 `_start` {#sec-1.15.6}

这一节回答：不链接 libc 的程序，入口为什么是 `_start` 而不是 `main`？没有 `printf`、也没有 `exit()`，一行字怎么输出、退出码又怎么交给 shell？

::: preview 先抓住一句话
`_start` 没有调用者，所以它不能 `ret`；它直接发系统调用：ARM64 用 `svc #0`，x86-64 用 `syscall`，RISC-V 用 `ecall`。写和退出，全靠自己。
:::

先给一条判定线。链接了 libc 的程序，入口也是 `_start`，但那是 libc 提供的启动代码：它取出参数、初始化运行环境，再调用你的 `main`。用 `-nostdlib` 之后，这段启动代码没了，`_start` 得你自己写；`printf`、`exit`、`errno` 也一起没了，只剩内核接口。

这个程序只做两件事：用 `write` 输出一行，用 `exit` 返回状态 42。系统调用号是**内核 ABI**，不是 ISA 的一部分：

| 调用 | x86-64 | ARM64 | RISC-V 64 |
|:--|--:|--:|--:|
| `read` | 0 | 63 | 63 |
| `write` | 1 | 64 | 64 |
| `openat` | 257 | 56 | 56 |
| `close` | 3 | 57 | 57 |
| `exit` | 60 | 93 | 93 |
| `exit_group` | 231 | 94 | 94 |

ARM64 与 RISC-V 采用 `asm-generic` 编号，所以大多数数字相同；x86-64 有一套自己的历史编号。写跨架构代码时用 `SYS_write`，只有写 `_start` 或调试内核入口时才直接写数字。


入口地址由链接器按 `-Wl,-e,_start` 与默认基址算出来；换链接器版本或换链接脚本就会变，不要背这个数。

命令里的 `-static` 不是装饰。`-nostdlib` 只表示「不链接 C 库」，不加 `-static` 时链接器仍可能生成带 `PT_INTERP` 的 PIE，内核会先拉起动态加载器，`_start` 之前发生什么就不再由你控制；`-static` 才是「没有解释器、入口就是 `_start`」的保证。

逐行读 ARM64 那份：`mov x8, #64` 把 `SYS_write` 放进系统调用号寄存器；`x0` 是 fd、`x1` 是缓冲区、`x2` 是字节数，正好对应 `write(fd, buf, count)`；`svc #0` 陷入内核，返回值仍在 `x0`。随后 `x8=93` 是 `exit`，`x0=42` 是退出码。

x86-64 那份把号放在 `rax`，参数在 `rdi`/`rsi`/`rdx`，用 `syscall` 陷入内核；内核会用 `rcx` 保存返回地址、用 `r11` 保存标志寄存器，所以这两个寄存器在 `syscall` 后不再是你放进去的值（1.15.7 会用到这一点）。RISC-V 的 `ecall` 则用 `a7` 放号、`a0`–`a2` 放参数，结果回 `a0`。

`_start` 里最容易犯的错是 `ret`。进入 `_start` 时 `sp` 指向 `argc`，不是返回地址；`ret` 会把 `argc` 当地址跳过去，通常立刻段错误。ARM64 的 `x30` 在进程入口也没有有意义的值。结束只有一条路：`exit`/`exit_group`。

裸系统调用的返回值要按内核的约定读：成功是非负值，失败是 `-errno`。在 VM 上用内联汇编对 `fd = -1` 调 `write`，返回 `-9`（`-EBADF`），不是 `-1`；`errno` 是 libc 包装替你设置的，`-nostdlib` 下没有这个包装。

x86-64 与 RISC-V 的版本只做了汇编检查或根本没编：写作机的 clang 21 能 `--target=x86_64-linux-gnu -c` 出目标文件，但 macOS 上没有 x86-64 Linux 的启动文件与链接器，**不能链接、不能运行，未实测**；RISC-V 目标在这台 clang 上没有注册，连汇编都没做，代码按 psABI 与 `asm-generic` 编号写，**未实测**。VM 上也没有 `qemu-riscv64`（`command -v` 为空），三份产物不可能在同一台机器上跑齐。

::: errata `_start` 的四个误区
1. **「`_start` 也可以 `ret` 回内核」**：不能。入口栈顶是 `argc` 等参数，不是返回地址；退出必须用 `exit`/`exit_group`。
2. **「不链接 libc 就不用守 ABI」**：系统调用本身有寄存器 ABI——号在 `rax`/`x8`/`a7`，参数按序放，结果在 `rax`/`x0`/`a0`；不守就传错参数或读错返回值。
3. **「系统调用号三套架构通用」**：`write` 在 x86-64 是 1，在 ARM64/RISC-V 是 64；ARM64 的 1 是 `io_destroy`。跨架构必须查 `asm-generic/unistd.h` 或 `SYS_*`。
4. **「`li a2, msg_end - msg` 总能汇编」**：RISC-V 的 `li` 对需要重定位的符号差不能直接展开，GNU as 可能报 `fixup value out of range`；用汇编期常量，或 `la t0, msg; la t1, msg_end; sub a2, t1, t0` 在运行时相减。
:::

::: intuition 为什么 `_start` 的栈上有 `argc/argv`
内核进入 `_start` 时，栈顶不是返回地址，而是 `argc`、`argv[]`、`envp[]`、`auxv[]`。glibc 的 `_start` 把这些取出来交给 `__libc_start_main`，后者再调用 `main(argc, argv, envp)`。手写 `_start` 要用参数，必须自己按这个布局取。
:::

::: ex 例 1.15.6 · 先猜 `_start` 里能不能用 `printf` {#ex-1.15.6}
写一个不依赖 libc 的 `_start`：只调用 `write` 与 `exit` 两个系统调用。先猜：在里面直接调 `printf("hi")` 会怎样？为什么 `_start` 不能用 `return 0;` 结束？

::: sol 解答
`printf` 在 libc 里，它依赖已初始化的 stdio 与 locale 状态；没有 libc 的启动代码（`__libc_start_main`）就没有那张表，链接期会报 `undefined reference to 'printf'`（静态链进 libc 又会产生你并不想要的初始化）。`return 0;` 会从 `_start` 返回到栈上那个「返回地址」——那里根本没有合法的返回目标，会崩溃或执行到垃圾指令；`_start` 必须以 `exit`/`exit_group` 系统调用收尾。
:::
:::

### 1.15.6 小结

`_start` 是「没有调用者的函数」：不能返回，只能发系统调用退出。ARM64 用 `svc #0`、x86-64 用 `syscall`、RISC-V 用 `ecall`；系统调用号是内核 ABI，三套架构并不通用。如果只记住一件事：**没有 libc 时，连「失败返回 -1」都不成立，裸调用返回的是 `-errno`**。

## 1.15.7 完整程序三：`asm volatile` 与 Rust `asm!` {#sec-1.15.7}

这一节回答：内联汇编里只有几条指令，编译器凭什么知道哪些寄存器会被改、哪块内存会变？约束写漏一个，为什么常常 `-O0` 正常、`-O2` 才出错？

::: preview 先抓住一句话
内联汇编的安全不靠注释，靠声明：输入/输出约束说明值放在哪个寄存器，clobber 列出「没写进输出、却会被改」的寄存器，`"memory"` 说明内存可能已经变了。
:::

C 版本用一个文件覆盖三套架构，编译时由 `#if` 选择。它比 1.15.6 多了一层工作：不仅要选对寄存器和系统调用号，还要把选择翻译成编译器能检查的约束。

<div class="variant" data-arch="all" data-lang="c">

```c
/* inline_all.c — 三架构内联汇编；用对应 target 的 cc 编译
 * cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 inline_all.c -o inline_all
 */
#include <inttypes.h>
#include <stdint.h>
#include <stdio.h>
#include <unistd.h>

static const char msg[] = "inline asm: syscall ok\n";

#if defined(__x86_64__)
static long sys_write(int fd, const void *buf, size_t n)
{
    long ret;
    __asm__ volatile("syscall"
                     : "=a"(ret)
                     : "a"(1L), "D"((long)fd), "S"(buf), "d"(n)
                     : "rcx", "r11", "memory");   /* syscall 破坏 rcx/r11 */
    return ret;
}
static uint64_t ticks(void)
{
    uint32_t lo, hi;
    __asm__ volatile("lfence\n\trdtsc" : "=a"(lo), "=d"(hi) :: "memory");
    return ((uint64_t)hi << 32) | lo;
}
#elif defined(__aarch64__)
static long sys_write(int fd, const void *buf, size_t n)
{
    register long x8 __asm__("x8") = 64;          /* SYS_write */
    register long x0 __asm__("x0") = fd;
    register const void *x1 __asm__("x1") = buf;
    register long x2 __asm__("x2") = (long)n;
    __asm__ volatile("svc #0" : "+r"(x0) : "r"(x8), "r"(x1), "r"(x2) : "memory");
    return x0;
}
static uint64_t ticks(void)
{
    uint64_t v;
    __asm__ volatile("isb\n\tmrs %0, cntvct_el0" : "=r"(v) :: "memory");
    return v;
}
#elif defined(__riscv)
static long sys_write(int fd, const void *buf, size_t n)
{
    register long a7 __asm__("a7") = 64;          /* SYS_write */
    register long a0 __asm__("a0") = fd;
    register const void *a1 __asm__("a1") = buf;
    register long a2 __asm__("a2") = (long)n;
    __asm__ volatile("ecall" : "+r"(a0) : "r"(a7), "r"(a1), "r"(a2) : "memory");
    return a0;
}
static uint64_t ticks(void)
{
    uint64_t v;
    __asm__ volatile("fence\n\trdcycle %0" : "=r"(v) :: "memory");
    return v;
}
#else
#error "unsupported architecture"
#endif

int main(void)
{
    uint64_t t0 = ticks();
    long n = sys_write(1, msg, sizeof msg - 1);
    uint64_t t1 = ticks();
    printf("wrote %ld bytes, %" PRIu64 " ticks\n", n, t1 - t0);
    return n == (long)(sizeof msg - 1) ? 0 : 1;
}
```

</div>

在 VM 上按文件里的命令编译并运行 ARM64 分支，第一行输出是 `inline asm: syscall ok`；第二行的字节数是 23，后面的 ticks 是 `cntvct_el0` 的差值，每次运行都不同，正文不抄具体数字，也不拿它当性能结论。

`sys_write` 的四条 `register ... __asm__("xN")` 把变量钉在指定寄存器上：`"r"(x8)` 等输入约束告诉编译器「进 `svc` 之前，值必须在这个寄存器里」；`"+r"(x0)` 是读写约束，因为 `x0` 既送 fd 又接返回值。`"memory"` 不是「buf 是输入」，而是编译器屏障：它禁止编译器把缓冲区写入重排到 `svc` 之后——内核读的是内存里的字节，不是寄存器里的副本。

x86-64 分支必须多写 `"rcx","r11"`：`syscall` 用 `rcx` 存返回地址、`r11` 存 `rflags`，不声明的话编译器可能把跨调用的活值放在这两个寄存器里。写作机把一份等价的 x86-64 包装交叉编译成汇编（`clang --target=x86_64-linux-gnu -O2 -S`），函数体只有 `movl $1, %eax`、`syscall`、`retq`：三个参数本来就在 `rdi`/`rsi`/`rdx`，约束没有产生多余的搬移。这只证明代码生成，**不能链接运行，未实测**。

Rust 版本用 `std::arch::asm!`，约束写法与 C 不同：用 `in("rax")`/`lateout("rax")` 指定寄存器，`inout("x0") x => ret` 表示同一个寄存器既是输入又是输出。下面的文件覆盖三套架构，`cfg` 只编译当前目标的那一份：

<div class="variant" data-arch="all" data-lang="rust">

```rust
// inline_all.rs — rustc --edition 2021 -O inline_all.rs
use std::arch::asm;

#[allow(dead_code)]
static MSG: &[u8] = b"rust asm!: syscall ok\n";

#[allow(dead_code)]
#[cfg(target_arch = "x86_64")]
unsafe fn sys_write(fd: i32, buf: &[u8]) -> isize {
    let ret: isize;
    unsafe {
        asm!(
            "syscall",
            in("rax") 1isize,              // __NR_write
            in("rdi") fd as isize,
            in("rsi") buf.as_ptr(),
            in("rdx") buf.len(),
            lateout("rax") ret,
            lateout("rcx") _,              // syscall 破坏 rcx
            lateout("r11") _,              // 和 r11
            options(nostack),
        );
    }
    ret
}

#[allow(dead_code)]
#[cfg(target_arch = "aarch64")]
unsafe fn sys_write(fd: i32, buf: &[u8]) -> isize {
    let ret: isize;
    unsafe {
        asm!(
            "svc #0",
            in("x8") 64isize,              // __NR_write
            inout("x0") fd as isize => ret,
            in("x1") buf.as_ptr(),
            in("x2") buf.len(),
            options(nostack),
        );
    }
    ret
}

#[allow(dead_code)]
#[cfg(target_arch = "riscv64")]
unsafe fn sys_write(fd: i32, buf: &[u8]) -> isize {
    let ret: isize;
    unsafe {
        asm!(
            "ecall",
            in("a7") 64isize,              // __NR_write（asm-generic）
            inout("a0") fd as isize => ret,
            in("a1") buf.as_ptr(),
            in("a2") buf.len(),
            options(nostack),
        );
    }
    ret
}

#[cfg(target_os = "linux")]
fn main() {
    let n = unsafe { sys_write(1, MSG) };
    std::process::exit(if n == MSG.len() as isize { 0 } else { 1 });
}

#[cfg(not(target_os = "linux"))]
fn main() {
    println!("build for *-linux-gnu to run the Linux syscall path");
}
```

</div>

两段代码的关键差别：

| 关注点 | C `asm volatile` | Rust `asm!` |
|:--|:--|:--|
| 指令文本 | 字符串，`\n\t` 分隔 | 字符串，可多条 |
| 输出 | `"=a"(ret)` | `lateout("rax") ret` |
| 输入 | `"D"(fd)` | `in("rdi") fd` |
| 读写同一寄存器 | `"+r"(x0)` | `inout("x0") x => ret` |
| 内存破坏 | `"memory"` clobber | 默认可能读写内存；`options(nomem)` 才是承诺不碰 |
| 栈 | 编译器不知道，需自行保证 | `options(nostack)` 声明不碰栈 |
| 标志寄存器 | 默认认为被改 | `options(preserves_flags)` 才承诺不变 |
| 模板修饰 | `%0`、`%1` | `{}`、`{0}`、`inout` 绑定 |

表里最值得记的是 `lateout` 与 `options`。`lateout` 允许编译器把输出分配到与某个输入相同的寄存器，前提是汇编在最后一次读该输入之后才写它；`out` 没有这个许可。`options(nostack)` 是承诺「这段汇编不碰栈、不调用函数」，`nomem` 是承诺「不读写内存」，`preserves_flags` 是承诺「不改标志寄存器」。承诺写错不会报错，只会生成错误的代码。Rust 的 `asm!` 默认就带副作用，不需要 C 的 `volatile`；反过来，只有 `options(pure)` 才表示「没有副作用、可以删除」。

Rust 部分**未实测**：VM 上没有 `rustc`（`command -v rustc` 为空），写作机也没有安装，所以这段代码没有编译过；正文只按 `asm!` 的约束语义写，不编造编译输出。

::: errata 内联汇编的五个坑
1. **把 `"memory"` 当成内存输入**：它是编译器屏障，意思是「这段汇编可能读写任意内存」，不是「buf 放在这里」。
2. **以为 `volatile` 能保证原子或线程间顺序**：它只阻止编译器删除，并限制它相对其他 volatile 操作移动；跨线程要用原子或锁。
3. **x86-64 第 4 个系统调用参数用 `rcx`**：`syscall` 会把返回地址写进 `rcx`，第 4 个参数必须用 `r10`；内联汇编照样要声明 `"rcx","r11"`。
4. **Rust 里默认加 `options(nostack, nomem)`**：这两条都是承诺；`svc`/`syscall` 会读你传入的缓冲区，写 `nomem` 就是撒谎。
5. **clobber 少写没关系**：少写会让编译器把活值放在被覆盖的寄存器里；多写只是保守，少写才是 bug。
:::

::: def 定义 1.15.7 · 约束与 clobber {#def-1.15.7}
**约束**（constraint）写在输入/输出位置上，告诉编译器「这个值从哪来、到哪去」。**clobber**（破坏列表）列出汇编会改写、但没有出现在输出里的寄存器；`"memory"` 是特殊的 clobber，表示内存内容可能变化。编译器据此决定哪些值要保存、哪些指令可以重排。
:::

### 1.15.7 小结

内联汇编把「寄存器分配」从编译器手里借走了一部分，代价是你必须把借走的部分写清楚：值在哪（约束）、谁会变（clobber）、内存会不会变（`"memory"`）。如果只记住一件事：**约束和 clobber 是给编译器的合同，不是给读代码的人的注释；漏写不会报错，只会在 `-O2` 里算错**。

::: method 即时自测 · 1.15.7
**Q1（记忆）** C 的 `"+r"(x0)` 与 `"r"(x0)` 有什么区别？Rust 里对应什么写法？
**Q2（辨析）** 一段只读写寄存器的内联汇编，为什么还可能要写 `"memory"`？
**Q3（应用）** 在 x86-64 上用内联汇编发 4 个参数的 `pwrite64`，第 4 个参数应该放哪个寄存器？clobber 至少要写什么？

::: sol 答案
**A1** `"+r"` 是读写约束，汇编前后都使用这个值；`"r"` 是只读输入。Rust 对应 `inout("x0") x => ret` 与 `in("x0") x`。
**A2** 如果这段汇编通过指针或系统调用间接读写内存（例如 `write` 读缓冲区），编译器不知道，必须用 `"memory"` 禁止它把内存操作重排到汇编之后。
**A3** 第 4 个参数放 `r10`（不是 `rcx`，`syscall` 用 `rcx` 存返回地址）；clobber 至少写 `"rcx","r11","memory"`，参数用 `"r10"` 输入。

## 1.15.8 实验一：用 objdump/readelf 读 ABI {#sec-1.15.8}

这一节回答：不运行程序，只靠 `objdump` 和 `readelf`，能不能确认参数放在哪、栈调了多少、调用了谁？

::: preview 先抓住一句话
目标文件里留着三样证据：符号表说「谁定义、谁欠着」，重定位表说「链接器要填哪些地址」，反汇编写「序言减了多少 `sp`、参数从哪个寄存器来」。三条命令各看一样。
:::

实验对象是 1.15.4 的 `frame.c`，再把 1.15.5 的 `nine` 加进同一个文件。先猜三件事再往下看：`framed` 的符号类型与大小是什么？`add_one` 在不在符号表里？`framed` 的序言减了多少字节？猜错的地方，才是你真正要读的地方。后面每改一次只动一个变量——优化级别、结构体大小或字段类型——否则读到的差异说不清是哪条规则造成的。

```bash
# VM: Ubuntu 24.04 aarch64, gcc 13.3
cc -std=c17 -D_GNU_SOURCE -O2 -fno-omit-frame-pointer -c frame.c -o frame.o
readelf -sW frame.o | grep -E 'framed|nine|add_one|UND'
```

实际输出（只保留相关行）：

```text
14: 0000000000000000    16 FUNC    GLOBAL DEFAULT    1 framed
15: 0000000000000010    40 FUNC    GLOBAL DEFAULT    1 nine
17: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND __printf_chk
```

`readelf -sW` 的列依次是编号、值、大小、类型、绑定、可见性、所在节、名字。`framed` 是 `FUNC`/`GLOBAL`、16 字节；`nine` 40 字节；`__printf_chk` 是 `UND`，意思是「这个文件只声明、不定义，链接时再找」。

`add_one` 不见了，因为 `-O2` 把它内联进了 `framed`。想看它，就换 `-O0` 再编一次：符号表里会出现 `LOCAL` 的 `add_one`（24 字节），`framed` 涨到 148 字节。**「没看到调用」不等于「没有调用」，先看优化级别。**

反汇编看序言。`-O0` 下 `framed` 的真实输出（节选）：

```text
18: sub  sp, sp, #0x40
1c: stp  x29, x30, [sp, #48]
20: add  x29, sp, #0x30
24: str  x0, [sp, #8]
28: str  x1, [sp]
...
58: bl   0 <add_one>
...
a0: ldp  x29, x30, [sp, #48]
a4: add  sp, sp, #0x40
a8: ret
```

四件事一眼可见：帧是 64 字节（`0x40`）；`x29`/`x30` 存在偏移 48/56；两个参数被 `str` 落栈（`-O0` 的调试友好做法）；`bl` 的目标是 `add_one`。中间省略的 `str x1, [sp, #40]` 是栈保护 canary，不是参数。

同一份输出里 `nine` 的八条 `str` 与第 9 个参数的 `ldr x0, [sp, #64]`，正好验证 1.15.5 的栈参数偏移：入口在 `[sp]`，减 64 字节后变 `[sp+64]`。

再看重定位。`readelf -rW frame.o` 里与调用、取地址有关的三行：

```text
R_AARCH64_ADR_PREL_PG_HI21  .rodata.str1.8 + 0
R_AARCH64_ADD_ABS_LO12_NC   .rodata.str1.8 + 0
R_AARCH64_CALL26            __printf_chk + 0
```

前两条是一对：`adrp` + `add` 把字符串地址拆成「页基址 + 低 12 位」；第三条是 26 位范围内的调用偏移，链接器负责把 `__printf_chk` 的地址填进 `bl` 的立即数字段。

跨文件调用更能说明问题。写作机交叉编译一个 x86-64 目标文件（只 `-c`，不链接），拿到 VM 上读：

```c
/* xf.c：framed 调用另一个文件里的 add_one */
long add_one(long x);
long framed(long x, long y)
{
    long local = x * 2;
    long *p = &local;
    return *p + add_one(y) + x;
}
```

```bash
clang --target=x86_64-linux-gnu -O0 -c xf.c -o xf.o   # 写作机
readelf -sW xf.o | grep -E 'framed|add_one'           # VM 读 x86-64 ELF
readelf -rW xf.o | grep R_X86
```

```text
3: 0000000000000000    69 FUNC    GLOBAL DEFAULT    2 framed
4: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND add_one
0000000000000028  0000000400000004 R_X86_64_PLT32  add_one - 4
```

`add_one` 是 `UND`，重定位类型是 `R_X86_64_PLT32`。三套架构的调用重定位名不同：x86-64 是 `R_X86_64_PLT32`，ARM64 是 `R_AARCH64_CALL26`；RISC-V 按 psABI 是 `R_RISCV_CALL_PLT`/`R_RISCV_JAL`，本机没有 RISC-V 工具链，**未实测**。名字不能跨架构照抄。

接手一个陌生目标文件，先 `readelf -h` 看三行：`Class` 是 32 还是 64 位，`Machine` 是哪个架构，`Type` 是 `REL`（可重定位，还没链接）还是 `EXEC`/`DYN`。`Machine` 不对，后面的反汇编再像也不是你的架构。想把机器码一起看，就去掉 `objdump -d` 的 `--no-show-raw-insn`，每行前面会多一列十六进制；`objdump -S` 能把源码交错进来，但需要编译时带 `-g`，而且 `-O2` 下指令与源码行对不齐，先用纯反汇编定位再对照源码。

进一步验证结构体规则：把 `struct pair` 改成三个 `long`，看 x86-64 是否从 `rdi/rsi/rdx` 取；改成 24 字节，看是否整块进栈、调用者是否复制。ARM64 上把 `struct { float a,b,c,d; }` 传给函数，看是否走 `s0`–`s3`（HFA）。这些差异编译一次就看见，不需要背。

::: errata 读目标文件的四个误解
1. **「`readelf -s` 的 `Value` 就是运行地址」**：可重定位文件里它是节内偏移；最终地址要等链接，运行地址还会被 PIE/ASLR 改。
2. **「`UND` 是错误」**：它只表示「本文件没定义、链接时再解析」；`add_one` 在另一个 `.o` 里，链接后就消失。
3. **「没看到 `bl add_one` 就是没调用」**：`-O2` 可能内联；换 `-O0` 或看符号大小再判断。
4. **「x86-64 的重定位名可以套到 ARM64」**：`R_X86_64_PLT32` 与 `R_AARCH64_CALL26` 是不同工具链的约定，按目标架构查。
:::

### 1.15.8 小结

`readelf -sW` 回答「谁定义、谁欠着」，`readelf -rW` 回答「链接器要填什么」，`objdump -d` 回答「序言减了多少、参数从哪来」。三条命令都不需要运行程序；`readelf` 能读任意架构的 ELF，`objdump` 通常只认本机架构——在 VM 上对 x86-64 目标文件执行 `objdump -d`，报的是 `can't disassemble for architecture UNKNOWN!`，跨架构时就只看符号与重定位。如果只记住一件事：**先看优化级别，再读符号与反汇编；`-O2` 会让函数消失、让偏移改变**。

## 1.15.9 实验二：用 gdb 与 perf 验证栈和开销 {#sec-1.15.9}

这一节回答：怎样在真实进程里核对栈帧、返回地址与调用开销？当 `gdb` 不能启动进程、`perf` 也拿不到计数器时，还剩哪几条站得住的证据？

::: preview 先抓住一件事
这一节的实验在 VM（Ubuntu 24.04 aarch64、gdb 15.1、内核 7.0.0）上**两条主路都断了**：`gdb run` 报 SVE 向量长度读取失败，`perf` 报没有可用事件。可复现的替代是「静态反汇编取证 + `clock_gettime` 计时」：前者回答编译器生成了什么，后者只回答总时间。
:::

先编一个带调试信息的版本，再按正常流程进 gdb：

```bash
# VM: Ubuntu 24.04 aarch64, gcc 13.3
cc -std=c17 -D_GNU_SOURCE -g -O0 -fno-omit-frame-pointer lab1c15_frame.c -o lab1c15_frame_dbg
gdb -q ./lab1c15_frame_dbg
(gdb) break framed
(gdb) run
```

本机实际停在启动阶段：

```text
Reading symbols from ./lab1c15_frame_dbg...
Breakpoint 1 at 0x884: file lab1c15_frame.c, line 4.
Starting program: /tmp/lab1c15_frame_dbg
Unable to fetch SVE/SSVE vector length: Invalid argument.
```

`run` 没有把进程带到断点。`starti` 同样失败；`x/6gx $sp`、`info registers` 也因为没有 inferior（gdb 对被调试进程的叫法）而读不到有意义的值。原因不在你的程序：错误来自调试器与目标机的接口——gdb 15.1 启动 aarch64 进程时要读 SVE/SSVE 向量长度（SVE 是 ARM64 的可伸缩向量扩展），这一步返回了 `EINVAL`。换 gdb 版本或换真机可能就好了，但在这一台上，**运行时观察整条路不可用**。

在一台 gdb 正常的机器上，这段实验应在断点处核对三件事：入口 `sp` 是否 16 字节对齐；保存的 `x29`/`x30` 是否落在 `[sp,#48]`/`[sp,#56]`；`finish` 后 `x0` 是否等于返回值。ARM64 看 `x0/x1/sp/x29/x30`，RISC-V 换成 `a0/a1/sp/s0/ra`，x86-64 换成 `rdi/rsi/rsp/rbp/rbx`。命令形状可以照抄，数值不能照抄。

能用的部分是静态的：符号、类型、行号、反汇编都不需要 inferior。

```bash
gdb -q -batch -ex 'info address framed' -ex 'info line framed' \
    -ex 'ptype framed' -ex 'disassemble /r framed' ./lab1c15_frame_dbg
```

本机输出节选：

```text
Symbol "framed" is a function at address 0x870.
Line 4 of "lab1c15_frame.c" starts at address 0x870 <framed>.
type = long (long, long)
   0x0000000000000870 <+0>:  d10103ff  sub  sp, sp, #0x40
   0x0000000000000874 <+4>:  a9037bfd  stp  x29, x30, [sp, #48]
   0x0000000000000880 <+16>: f90003e1  str  x1, [sp]
   0x00000000000008b0 <+64>: 97ffffea  bl   0x858 <add_one>
```

从这几行就能回答实验原本要问的三件事：帧是 64 字节（`sub sp,sp,#0x40`）；`x29`/`x30` 存在 `[sp,#48]` 与 `[sp,#56]`；`bl add_one` 之前参数已经落栈。返回地址在 `x30`，函数靠尾声的 `ldp x29,x30` 恢复，不靠栈顶弹出。**这些是静态布局，不是运行时读数**：入口 `sp` 是否 16 字节对齐、实际 `x30` 指向哪条指令，本机给不出。

perf 的第二条路也断。本机 `perf` 二进制在，但事件被挡住：

```bash
perf stat -e cycles:u,instructions:u ./lab1c15_frame_dbg
# Error:
# No supported events found.
cat /proc/sys/kernel/perf_event_paranoid   # 4
```

`perf record` 的报错更具体：`Failure to open event 'armv8_pmuv3_0/cycles/Pu'`。`paranoid=4` 表示连用户态 CPU 事件也不放行；`sudo` 在本机不可用，改不了这个值。`perf stat true` 里 `cpu-cycles` 显示 `<not supported>`，说明不只是权限问题，这台 VM 也没把 PMU（性能监控单元，CPU 里的计数器）暴露出来。**看到 `perf` 有表格不等于拿到了计数器，要看事件那一列是不是 `<not supported>`。**

替代方案是 `clock_gettime(CLOCK_MONOTONIC)` 量总时间。下面只列计时骨架，`now_ns` 是对 `clock_gettime` 的包装：

```c
double t0 = now_ns();
for (long i = 0; i < N; i++) sink += framed(i, 3);
double t1 = now_ns();
printf("per-call = %.2f ns\n", (t1 - t0) / N);
```

VM 上取 `N=10^7`、`-O0` 编一次、同一个二进制跑两次，得到 3.13 ns/次与 3.07 ns/次。这个数只能读成「这台机器上这次循环摊到每次调用约 3 纳秒」，它包含循环、加法与 `sink` 写入；换优化级别、换机器就变。它能说明「调用不是免费的」，不能说明指令数、IPC（每周期执行多少条指令）或分支失败率。

::: errata 用 gdb/perf 时的三个口径
1. **`run` 失败不是程序错**：先看报错在 `Starting program` 之后还是之前；SVE 这类错误属于调试器与内核的接口，换机器再试。
2. **静态反汇编不是运行时证据**：`disassemble` 能证明编译器生成了什么，不能证明这次运行的 `sp` 与 `x30`；两者别混写。
3. **`perf stat` 有表格不等于有计数**：事件列为 `<not supported>`、或直接报 `No supported events found`，都说明 PMU 没暴露；此时任何 IPC、分支失败率都没有来源。
:::

### 1.15.9 小结

本机 gdb 只能静态取证，perf 拿不到计数器；替代路径是 `info address`/`disassemble /r` 回答「生成了什么」，`clock_gettime` 回答「总共花了多久」。如果只记住一件事：**实验报告里要写清证据来自静态反汇编、来自计时，还是来自真正的运行时观察，三者不能互相冒充**。

::: method 即时自测 · 1.15.9
**Q1（记忆）** 本机 `gdb run` 报的错是什么？它发生在进程启动的哪个阶段？
**Q2（辨析）** `disassemble /r framed` 看到 `sub sp,sp,#0x40`，能不能据此断言「运行时入口 `sp` 一定 16 字节对齐」？
**Q3（应用）** `perf stat` 报 `No supported events found`，你还能用什么量调用开销？这个数能回答什么、不能回答什么？
**Q4（迁移）** 换一台 PMU 正常的机器，`perf stat -e cycles,instructions` 拿到两个数，怎样用它验证「内联减少了调用开销」？

::: sol 答案
**A1** `Unable to fetch SVE/SSVE vector length: Invalid argument.`；出现在 `Starting program` 之后、断点命中之前，属于调试器启动 inferior 时的接口失败。

**A4** 先确认两次运行的工作集与输入相同，再看 `instructions` 是否下降、`cycles` 是否同向；只有「调用点消失 + 指令数下降 + 时间下降」三条同向，才能说内联省了开销。单看时间会被频率与调度干扰。

## 1.15.10 十二条汇编与 ABI 陷阱 {#sec-1.15.10}

这一节回答：读三套汇编时，哪些错误最常让你「指令看对了，结论却反了」？每条陷阱怎样用一条命令先定位，而不是靠猜？

::: preview 先抓住一件事
十二条按「汇编 / 栈 / ABI / 工具」分成四组，每条都写「现象 → 原因 → 先查什么」。查的顺序固定：先确认架构与优化级别，再看栈调整，最后才看算术。
:::

这十二条不是用来背的，而是出错后按顺序排查的清单。同一段汇编，先问「这是哪套架构、什么优化级别」，能排掉一半误判。

**汇编组**

- **读反 AT&T 的源与目的。** 现象：把 `mov %rdi, %rax` 读成「把 `rax` 存进 `rdi`」。原因：AT&T 源在前、目的在后；ARM64/RISC-V 的目的在左。先查：盯逗号最后一个操作数，或用 `objdump -d -M intel` 对照。
- **把 `ret` 当成「从栈顶弹地址」。** 现象：在 ARM64 栈里找不到返回地址的变化，函数却照样返回。原因：`ret` 是 `br x30`，RISC-V 是 `jalr x0,0(ra)`，只有 x86-64 弹栈。先查：`disassemble /r` 看机器码（ARM64 是 `d65f03c0`），再看 `ret` 前有没有 `ldp`。
- **把伪指令与压缩指令当成定长指令。** 现象：按「每条 4 字节」数地址，跳转偏移全错。原因：`call`、`li` 会展开成多条；RISC-V 的 C 扩展让指令可能只有 2 字节。先查：`objdump -d` 每行左侧的地址差，`readelf -h` 的 Flags 里有没有 `RVC`。

**栈组**

- **返回地址被越界写覆盖。** 现象：`ret` 跳到随机地址，或出现 `*** stack smashing detected ***`。原因：x86-64 的返回地址在 `[rsp]`（建帧后 `[rbp+8]`），与局部缓冲区同在一块内存。先查：崩溃地址是否像栈上数据；加 `-fstack-protector-strong` 再编一次；反汇编里找 canary 的装入与比较。
- **把保存责任记反。** 现象：ARM64 第二次 `bl` 后返回错地址，RISC-V 递归只返一层，或调用者的循环变量在调用后变了。原因：`x30`/`ra` 只有一份，调用会覆盖；`rbx`/`x19`/`s1` 这类被调用者保存寄存器用了不恢复，调用者的活值被改；反过来，把 `rax`/`x0` 这类调用者保存寄存器当成跨调用变量，也会被被调用者改掉。先查：序言有没有 `stp x29,x30` / `sd ra,...(sp)`；用了 `rbx`/`x19` 有没有成对 `push/pop`、`stp/ldp`；跨调用值是否放在被调用者保存寄存器里。
- **红区与 16 字节对齐混着用。** 现象：x86-64 的 `movaps` 段错误，或加了调用后局部变量莫名改变。原因：红区只对叶子函数有效；入口 `rsp%16==8`，`call` 前必须是 0。先查：函数里有没有 `call`；序言 `push`/`sub` 总量是不是 16 的倍数；用 `-mno-red-zone` 对照。

**ABI 组**

- **把 6 个参数寄存器当三家通用。** 现象：ARM64 的第 7 个参数被当成栈参数，读出来是垃圾。原因：x86-64 六个、ARM64 八个、RISC-V 八个。先查：`-O0 -S` 里第 7 个来自 `x6`/`a6`，第 9 个才从 `[sp]` 取。
- **没问清栈参数偏移相对谁。** 现象：x86-64 读第 7 个参数拿到返回地址，或整体差 8 字节。原因：入口 `[rsp]` 是返回地址，第 7 个在 `[rsp+8]`；ARM64/RISC-V 入口的第 9 个在 `[sp]`。先查：偏移是相对入口 `sp` 还是建帧后 `fp`；先看 `sub sp` 减了多少。
- **把 `syscall` 与可变参数的隐藏约定记错。** 现象：`openat` 的 `mode`、`pwrite64` 的偏移错；或裸调用失败时把 `-9` 当字节数；或 `printf("%f", x)` 输出垃圾。原因：`syscall` 用 `rcx` 存返回 `rip`、`r11` 存 `rflags`，第 4 个参数必须放 `r10`；裸系统调用失败返回 `-errno` 且不设 `errno`；可变参数调用前 `%al` 要放向量寄存器个数。先查：`objdump -d` 在 `syscall` 前找 `mov %rcx,%r10`；clobber 里有没有 `"rcx","r11"`；返回值 `<0` 时取 `-ret`；`printf` 调用点有没有设 `%al`。
- **结构体按值传参在 C/Rust 间不一致。** 现象：字段顺序对、值却是垃圾，或第 3 个字段开始全错。原因：不超过 16 字节的结构体按八字节分类走寄存器（ARM64 的 HFA 另算），超过就整块进内存传指针；Rust 默认布局可能重排字段。先查：`-O0 -S` 看参数是来自 `rdi/rsi` 还是 `[rsp+...]`；Rust 侧有没有 `#[repr(C)]`；跨语言时用 `bindgen`/`cbindgen` 生成的声明对照。

**工具组**

- **内联汇编只在 `-O0` 试过。** 现象：`-O0` 正常、`-O2` 下缓冲区没写或顺序反了。原因：缺 `volatile` 的无输出 `asm` 会被删；缺 `"memory"` 会把写操作重排；缺 clobber 会让编译器把活值放在被覆盖的寄存器里。先查：同一段代码 `-O0`/`-O2` 各编一次，比较 `syscall` 前后的指令顺序。
- **把「能交叉汇编」当成「能运行」。** 现象：`clang --target=riscv64-linux-gnu -c` 通过，就宣布三套都验证了。原因：`-S`/`-c` 只做代码生成，链接还缺 sysroot、`crt1.o`、`-lc` 与目标链接器；ELF 在 macOS 上也不能执行。先查：是否只做到 `-S`/`-c`；`readelf -h` 的 `Type` 是不是 `REL`；运行要么真机，要么 QEMU（本环境未确认）。

还有两条不属于错误、但会让读数对不上：x86-64 的 `long` 是 64 位，Windows LLP64 是 32 位；ARM64 的 `char` 是否有符号取决于工具链，跨语言传字符别依赖默认值。

### 1.15.10 小结

十二条可以压缩成一句排查顺序：先看架构与优化级别，再看 `sp` 与返回地址，最后才信算术；工具只证明它真正跑过的那一层。如果只记住一件事：**遇到「三套应该一样」的说法，先数参数寄存器（6/8/8），再问偏移相对谁。**

::: method 即时自测 · 1.15.10
**Q1（记忆）** AT&T 的 `mov %rdi, %rax` 改写了哪个寄存器？
**Q2（辨析）** ARM64 函数 `ret` 前没有 `ldr x30,[sp]`，能不能说它「没有保存返回地址」？
**Q3（应用）** x86-64 函数入口 `[rsp]` 与 `[rsp+8]` 各是什么？第 7 个参数在哪？
**Q4（工具）** 交叉汇编 `-c` 通过了，为什么不能顺手写一个「运行时间」？

::: sol 答案
**A1** 改写 `rax`。AT&T 的最后一个操作数是目的，前面的是源。
**A2** 不能。非叶函数通常在序言用 `stp x29,x30` 把 LR 存到栈上，返回前 `ldp` 恢复；`ret` 只跳 `x30`，所以不需要在 `ret` 前再从栈读一次。
**A3** `[rsp]` 是 `call` 压入的返回地址，`[rsp+8]` 是第 7 个整数参数，第 8 个在 `[rsp+16]`，第 9 个在 `[rsp+24]`。
**A4** 因为 `-c` 只生成目标文件，没有链接、没有加载、也没有执行；运行时间需要目标架构的机器或模拟器。本机只能做到 `-S`/`-c`，所以运行时间一律写「未实测」。

## 1.15.11 本章小结 {#sec-1.15.11}

这一节回答：学完这一章，拿到一段陌生汇编，你能按什么顺序读出结论？哪些结论可以复算，哪些只能承认「这台机器上看不见」？

::: preview 先抓住一件事
判据是：**给你一个陌生函数，30 秒内指出参数从哪来、`sp` 减了多少、返回地址存在哪；给你一句「三套架构应该一样」，先问清是哪一层契约、几个寄存器、能不能真的运行。**
:::

这一章的主线是**一次调用的三层答案**。1.15.1–1.15.2 先立控制与责任：x86-64 的 `call` 把返回地址压栈，ARM64 的 `bl` 写 `x30`，RISC-V 的 `jal` 写 `ra`；非叶函数因此要自己保存 LR/`ra`。参数与保存责任要分开记：x86-64 六个整数参数寄存器，ARM64 与 RISC-V 各八个；`x30` 单列，`v8`–`v15` 只保证低 64 位，`gp`/`tp` 不能当临时变量。三套汇编不能互搬：`mov` 同名不同义，`ret` 的机器码与取地址方式也不同。

1.15.3–1.15.5 把规则落到指令与栈帧：同一操作有三种写法，序言只做「腾空间、保存、对齐」三件事，`-O2` 可以把整段序言消掉；参数用完寄存器后，x86-64 第 7 个起上栈，ARM64/RISC-V 第 9 个才上栈。结构体按分类而不是按大小，大结构体与 `sret` 退化成指针，可变参数还要看 `%al`、匿名栈参数与 `va_list` 保存区。栈图上的三个偏移——返回地址或 LR、保存寄存器、局部变量——从高到低排；先看 `sp` 减了多少，再读具体槽位。

1.15.6–1.15.10 换成两个完整程序和一套取证方法：`_start` 没有调用者，不能 `ret`，结束必须 `exit`；`asm volatile` 要声明输入输出、`"memory"` 与 `"rcx","r11"`，Rust 的 `asm!` 用 `lateout`/`inout`/`options(nostack)` 表达同一件事。取证靠 `readelf -sW`/`-rW` 与 `objdump -d`；本机 `gdb run` 报 SVE 向量长度读取失败，`perf` 报 `No supported events found`，所以只做静态 `disassemble` 加 `clock_gettime` 计时，并在报告里写明证据类型。`readelf` 回答「链接器要填什么」，`objdump` 回答「生成了什么」，计时回答「花了多久」；三者不能互相代替。报告里写清机器、架构与编译器版本，别人才复现得了。

这里的「三条判据」：

- **能读**：拿到陌生汇编，先找参数寄存器（`rdi`… / `x0`–`x7` / `a0`–`a7`），再找 `sub sp`/`push`，最后才看算术；看到 `stp x29,x30` 先问帧多大，再问返回地址副本落在第几个槽；能说出返回地址在栈顶、`x30` 还是 `ra`。
- **能写**：能默写 `_start` 与内联汇编包装；写完先用 `cc -c` 或 `as` 过一遍汇编器，再用 `readelf -h` 确认架构；交叉汇编只做到 `-S`/`-c`，不把「生成了 `.o`」当成「跑过了」，更不写运行时间。
- **能判**：听到「第 7 个参数都在栈上」先分清 6/8/8；读栈参数先问偏移相对入口 `sp` 还是建帧后 `fp`；看到工具输出先问它是 ABI 条款、静态反汇编还是运行时读数。`readelf -h` 的 `Machine` 只说明架构，`Type=REL` 说明还没链接；`perf` 的事件列是 `<not supported>` 就说明没有计数。

### 1.15.11 小结

如果只记住一件事，那就是**一次调用只回答三个问题：返回地址在哪、谁负责保存、参数从哪取**。三套 ABI 的答案不同，工具只证明它能证明的那一层；剩下的，写「未实测」比编一个数字有用。

**下一站**：这一章把「一条调用」拆到寄存器和栈槽，下一步把这些汇编放回工具链。[1.16 编译、链接与优化](ch16.md) 会讲 `-O2` 与 `-C opt-level=3` 各做了什么、ELF 的段/符号/重定位怎样被链接器改写，以及 LTO、`no_std` 与 FFI 如何改变最终产物。

::: method 即时自测 · 1.15
**Q1（记忆）** x86-64 进入函数时 `rsp % 16` 是多少？`call` 前要求多少？序言 `push %rbp` 之后再 `sub` 多少才能满足？
**Q2（辨析）** ARM64 的 `stp x29, x30, [sp, #-16]!` 中，`x30` 保存的是什么？为什么 RISC-V 没有对应的「链接寄存器自动压栈」？
**Q3（应用）** 一个函数有 9 个 `long` 参数，第 7、8、9 个在 x86-64、ARM64、RISC-V 上分别从哪里取？
**Q4（迁移）** 为什么 x86-64 的 `syscall` 内联汇编要写 `"rcx","r11"`，而 ARM64 的 `svc` 不用？

::: sol 答案
**A1** 入口是 8（`call` 压了 8 字节），`call` 前要 0。`push %rbp` 把 `rsp` 从 8 变成 0；之后再 `sub` 的字节数必须是 16 的倍数（如 16、32），`call` 前才仍是 0。只 `push` 不 `sub` 也已经对齐。
**A2** 保存当前函数的 LR（返回地址）；本函数还要 `bl` 别人，`x30` 会被覆盖，所以先存、返回前 `ldp` 恢复。RISC-V 的 `jal` 把返回地址写进 `ra` 寄存器而不是栈，硬件不自动压栈，软件必须自己 `sd ra,...(sp)`。
**A3** x86-64：第 7 个在 `[rsp+8]`、第 8 个在 `[rsp+16]`、第 9 个在 `[rsp+24]`（入口偏移）。ARM64：第 7、8 个在 `x6`/`x7`，第 9 个在 `[sp]`。RISC-V：第 7、8 个在 `a6`/`a7`，第 9 个在 `0(sp)`。
**A4** x86-64 的 `syscall` 用 `rcx` 保存返回 `rip`、`r11` 保存 `rflags`，硬件会写它们，所以第 4 个参数改用 `r10`，内联汇编要声明这两个 clobber。ARM64 的 `svc` 不通过这两个寄存器返回，返回值在 `x0`，没有等价的隐式 clobber。
:::
:::
