## A. 三件事、调度与份额

::: method 回忆 1 · 三件事与两个抽屉
操作系统要同时解决哪三类矛盾？每类的机制与策略各是什么？举两个「三块互相调用」的例子。
::: sol 答案
三类矛盾：CPU 太少程序太多（虚拟化 CPU）、内存太小地址太多（虚拟化内存）、多个执行流要共享数据（并发）、断电会丢数据（持久化）——严格说是四问三块，CPU 与内存合称虚拟化。机制与策略的配对：虚拟化 CPU 的机制是「受限直接执行 + 定时器中断 + 上下文保存」，策略是「选哪个进程」；虚拟化内存的机制是「页表 + TLB + 缺页异常」，策略是「换哪一页」；并发的机制是「原子指令 + 等待队列」，策略是「选哪个线程、锁多大」；持久化的机制是「DMA + 中断 + 日志」，策略是「怎么布局、何时回写」。互相调用的例子：缺页异常要用进程上下文（虚拟化内存借用 CPU 的陷入机制）；文件系统的 page cache 就是内存页（持久化借用虚拟内存）；自旋锁依赖原子指令与内核抢占控制（并发借用 CPU 的机制）。启动顺序也是证据：先建页表，再创建 `init`，最后初始化驱动与根文件系统。
:::
:::

::: method 回忆 2 · 周转、响应与三种策略的手算
周转时间与响应时间各怎么定义？A(0,10)、B(1,5)、C(2,2) 在 FIFO、SJF、RR(片长 2) 下的平均周转与平均响应各是多少？
::: sol 答案
周转 = 完成时间 − 到达时间；响应 = 首次运行时间 − 到达时间。FIFO：A 0–10、B 10–15、C 15–17，周转 10/14/15，平均 13；响应 0/9/13，平均 7.33。SJF（非抢占）：A 0–10、C 10–12、B 12–17，周转 10/16/10，平均 12；响应 0/11/8，平均 6.33。RR(2)：A 0–2、B 2–4、C 4–6、A 6–8、B 8–10、A 10–12、B 12–13、A 13–15、A 15–17，周转 17/12/4，平均 11；响应 0/1/2，平均 1。结论：RR 的周转不一定比 SJF 好，但响应显著更优；交互系统选 RR/MLFQ，批处理选 SJF/STCF。真实系统没有预知运行时间的「水晶球」，所以用历史行为预测。
:::
:::

::: method 回忆 3 · MLFQ 的五条规则与周期提升
MLFQ 的五条规则是什么？去掉规则 5 会发生什么？参数里哪一个最影响系统性格？
::: sol 答案
五条：新任务进最高优先级；同优先级内按 RR；用完整个时间片就降一级（可能是 CPU 密集）；在时间片内主动让出就留在原级（可能是 I/O 密集）；每隔一段时间把所有任务提升到最高级。去掉规则 5，长任务会永远沉底（饥饿），而且任务可以故意在时间片快用完时让出 CPU 来 gaming 优先级。加上规则 5，短任务又会被周期打断，所以提升周期、队列数、片长三个参数一起决定「像交互系统还是像批处理系统」。MLFQ 的核心是「用行为猜意图」：它不测量任务类型，只用「是否用完时间片」这个可观测量去近似。
:::
:::

::: method 回忆 4 · 彩票、步长与 CFS 的份额
彩票调度的期望份额怎么算、误差怎么来？步长调度为什么确定？CFS 的 `vruntime` 公式与权重表是什么？本书 VM 上跑出来的份额是多少？
::: sol 答案
彩票：期望份额 = 自己的彩票数 / 总数；每次调度抽一张，1 万次抽签的偏差约在 ±1.5 个百分点。误差量级约 `1/sqrt(n)`（n 为抽签次数），本质是概率公平。步长：`stride = K / tickets`，每次选 `pass` 最小者，运行后 `pass += stride`；长期份额精确等于彩票比例，本质是「让所有任务的 `pass` 保持相等」。CFS：`vruntime += delta × (NICE_0_LOAD / weight)`，总选 `vruntime` 最小者；nice 每降 1，权重约乘 1.25，nice −20/0/19 的权重是 88761/1024/15。本书 VM 实测（`lottery.c`，1 万次）：彩票列 50.2/24.6/25.2，步长列精确 50.0/25.0/25.0，三个 `pass` 都收敛到 5,000,000。把 `QUANTA` 改成 100（VM 实测）：彩票列变成 41.0/30.0/29.0（偏离期望 9 个百分点），步长仍是 50.0/25.0/25.0，三个 `pass` 都是 50000——抽样次数一少，概率公平的抖动就藏不住。
:::
:::

::: method 回忆 5 · 权重怎么变成 CPU 时间
nice 值的权重从哪来？nice 0 与 10、0 与 19 的理论比例各是多少？Linux 6.6 之后默认调度器是什么？
::: sol 答案
权重来自内核的静态表（`sched_prio_to_weight`），以 nice 0 = 1024 为基准，每降 1 约乘 1.25。nice 0 : nice 10 = 1024 : 110 ≈ 9.3 : 1；nice 0 : nice 19 = 1024 : 15 ≈ 68.3 : 1。本书 VM 实测（都绑在 CPU 0）：nice 0 与 10 是 90.1% : 9.7%，`se.sum_exec_runtime` 9034.216380 ms : 974.130957 ms（9.3 倍）；nice 0 与 19 是 98.3% : 1.3%，7893.609598 ms : 118.216624 ms（约 66.8 倍，与理论 68:1 同量级）。调度器版本：2.6.23 起 CFS，6.6 起默认换成 EEVDF（eligible virtual deadline first），仍按权重分配，但给每个任务一个虚拟截止时间，在 eligible 集合里选最早的。
:::
:::

::: method 回忆 6 · 多核调度的三个结构
SQMS、MQMS、work stealing 各是什么？各自的主要代价是什么？缓存亲和性与负载均衡为什么冲突？
::: sol 答案
SQMS（单队列多处理器）：一个全局运行队列，所有核从同一队列取任务，负载天然均衡，但全局锁竞争大、任务容易被搬到冷核上（亲和性差）。MQMS（多队列多处理器）：每核一个队列，亲和性好，但任务数不均时有的核空闲、有的核排队，需要周期性再平衡。work stealing：空闲核从别的核「偷」任务，兼顾两者，代价是偷取时的同步与阈值调参。冲突的根源是：亲和性要求「尽量别动」，负载均衡要求「把活挪走」。Linux 用调度域（scheduling domain）分层做均衡，先在同一个 LLC 内挪，再往外层挪。
:::
:::

## B. 内存虚拟化、替换与机制

::: method 回忆 7 · 分段、分页、交换各还什么债
内存虚拟化的三步演进各解决什么问题、又各欠下什么？x86-64 与 aarch64 在「分段」上有什么不同？
::: sol 答案
分段：基址 + 界限把地址空间切成代码/堆/栈段，解决「隔离与共享」，欠下**外部碎片**（段大小不一，频繁分配释放后有空隙却放不下新段），可以用紧凑（搬移段）缓解，代价大。分页：固定大小页 + 页表，消灭外部碎片，欠下**页表空间**与 **TLB 压力**，用多级页表、大页偿还。交换：物理内存不够时把冷页换到 swap，欠下 **I/O 延迟**（一次主缺页是几十微秒到几毫秒），用 LRU/Clock 近似、active/inactive 双链表、`kswapd` 后台回收、`swappiness` 偿还。跨架构：x86-64 的 Linux 段基址固定为 0，只用分页，但 `FS/GS` 基址保留给 TLS 与 per-CPU；aarch64 本来就没有 x86 那种分段，TLS 走 `TPIDR_EL0`。所以「分段」这一课在本书 VM（aarch64）上只能当历史与 x86 语义读。
:::
:::

::: method 回忆 8 · 换入的五步与三个虚拟内存技巧
缺页且页在 swap 时，内核按哪五步补页？按需清零、COW、聚簇换入各把什么成本推后？
::: sol 答案
五步：硬件发现 PTE 的 present=0，触发缺页；内核看 PTE 的 swap 位/槽号，知道页在 swap；分配一个物理页并读 swap 槽；更新 PTE 指向新页、present=1；返回用户态重试那条指令。三个技巧：**按需清零**——匿名页先映射到共享只读零页，第一次写才分配并清零，所以 `malloc` 大块不立刻吃物理内存；**写时复制**——`fork` 只复制页表并清 `RW` 位，写时缺页才复制一页，所以 `fork` 后立刻 `exec` 几乎不产生内存复制；**聚簇换入**——缺一页时把相邻几页一起读入（swap 预读按簇），把随机小读合并成顺序大读，摊薄每次缺页的固定成本。三者的共同点：把分配、复制、读盘从「映射建立时」推到「真正需要时」。
:::
:::

::: method 回忆 9 · EMAT 的两个读数
EMAT 的公式是什么？TLB 命中 99%、TLB 1 ns、内存 100 ns、页表访问 100 ns 时 EMAT 是多少？命中率掉到 90% 呢？
::: sol 答案
`EMAT = 命中率 × (TLB 时间 + 内存时间) + 未命中率 × (TLB 时间 + 页表访问 + 内存时间)`。99% 命中：`0.99 × 101 + 0.01 × 201 ≈ 102 ns`。90% 命中：`0.90 × 101 + 0.10 × 201 ≈ 111 ns`。命中率只掉 9 个百分点，EMAT 涨了近 9%，而且这还是「页表只有一级访问」的乐观估计——真实的多级页表未命中要走四级，代价更大。这就是大页与局部性重要的原因：大页把同一批地址压进一个 TLB 项，局部性让未命中集中在少数页上。EMAT 是「策略收益」的换算器，任何页表优化最后都要落回这个式子。
:::
:::

::: method 回忆 10 · 四种替换算法与 Belady 异常
OPT、LRU、FIFO、Clock 各替换谁？什么叫栈算法？为什么只有非栈算法会出现 Belady 异常？经典引用串的四个读数是多少？
::: sol 答案
OPT 替换「未来最久不用」的页（不可实现，作为下界）；LRU 替换「最久未使用」的页；FIFO 替换「最早进入」的页；Clock 是环形扫描，访问位为 1 就清位放过（二次机会），近似 LRU。栈算法：页框数为 n 时命中的页集合，一定是 n+1 时命中集合的子集；只有具备这个性质，增加页框才不会增加缺页。LRU 与 OPT 是栈算法，FIFO 不是，所以 FIFO 会出现 Belady 异常。经典引用串 `1 2 3 4 1 2 5 1 2 3 4 5`：本书 VM 实测 FIFO 在 3 个页框缺页 9 次、4 个页框 10 次；OPT 7→6；LRU 10→8；Clock 9→10（本例与 FIFO 同结果，说明「近似 LRU」不保证栈性质）。真实内核用 active/inactive 双链表 + PTE 的 `A` 位做近似，不用纯 LRU。
:::
:::

::: method 回忆 11 · 并发 bug 的五类
并发 bug 分哪五类？各给一个现象与一种修法。为什么「加锁就完事」不成立？
::: sol 答案
原子性违反（两个线程同时更新，丢更新；修法：锁、原子操作）；顺序违反（先检查后使用，中间被改；修法：锁、版本号、CAS）；死锁（循环等待，永久阻塞；修法：锁顺序、超时、回滚）；活锁（不断重试，无法推进；修法：退避、随机化）；饥饿（某个线程永远拿不到资源；修法：公平锁、优先级提升）。「加锁就完事」不成立，因为锁本身带来争用、死锁、优先级反转；无锁结构带来 ABA 与内存回收（RCU/epoch）问题。选哪种取决于三件事：临界区长度、竞争程度、能否容忍重试。分类的价值在于：先判类型，再选修法，而不是见到异常就加锁。
:::
:::

::: method 回忆 12 · PCB 的四组字段、`R` 的含义与 PTE 的位
`task_struct` 的字段按生命周期怎么分组？`ps` 的 `R` 到底表示什么？PTE 的 `P/RW/US/A/D/NX` 各管什么？aarch64 上这套位号成立吗？
::: sol 答案
四组：状态（`state`、`flags`）；身份与地址空间（`pid`/`tgid`、`mm`/`active_mm`、`files`、`fs`、`cred`）；信号与命名空间（`sighand`/`signal`、`nsproxy`）；调度与切换（`thread`、`sched_entity`）。`R` 同时包含「正在 CPU 上跑」与「在 runqueue 上等 CPU」，区分要看 runqueue 与 `on_cpu`，或用 `/proc/<pid>/stat` 第 39 字段（CPU 号）两次采样是否变化。PTE：`P` 存在（0 触发缺页）、`RW` 可写（0 时写触发保护缺页，COW 靠它）、`US` 用户可访问、`A` 已访问（CPU 置位，Clock 用它）、`D` 脏页（决定换出是否写回）、`NX` 不可执行（W^X）。这套位号是 **x86-64** 的；本书 VM 是 aarch64，用 `AF`（access flag）与 `AP` 权限位、脏位要靠 DBM 或软件写保护，位号与位置都不同，所以引用前先看架构。
:::
:::

## C. 持久化、项目与落点

::: method 回忆 13 · 磁盘的 12 ms 与 RAID 的取舍
一次 4 KiB 随机读的时间由哪几项组成？典型值各是多少？RAID 0/1/5/6/10 的容量与容错各是什么？为什么说 RAID 不是备份？
::: sol 答案
`T = 寻道 + 旋转 + 传输 + 排队`：寻道 4–10 ms（本书按 8 ms 算），旋转平均半圈 4.17 ms（7200 RPM 一圈 8.33 ms），传输 4 KiB @100 MB/s 约 0.04 ms，合计约 12 ms，即约 83 IOPS；顺序读同样 4 KiB 只要 0.04 ms。**随机与顺序差两个数量级**，这是 WAL、LSM tree、日志结构文件系统存在的根本原因。RAID：0 至少 2 盘、100% 容量、无容错；1 至少 2 盘、50%、容 1 盘；5 至少 3 盘、(n−1)/n、容 1 盘，写有 read-modify-write；6 至少 4 盘、(n−2)/n、容 2 盘；10 至少 4 盘、50%、每组容 1 盘。RAID 只处理「盘坏」，不处理误删、勒索、机房火灾；RAID 5 还有 write hole 与重建期二次故障，大容量盘重建可能持续数小时。
:::
:::

::: method 回忆 14 · redo 日志的协议与两条恢复规则
redo 日志分哪四步？哪一步是原子分界？崩溃恢复的两条规则是什么？为什么重放必须幂等？没有日志时「创建文件」的三个崩溃点各留下什么？
::: sol 答案
四步：把新值写进日志区（事务开始 + 记录）；写提交记录（commit）——**这一步落盘是原子分界点**；checkpoint 把日志里的新值应用到主文件系统；事务完成，日志空间可回收。恢复两条规则：有提交记录就重放整个事务，没有就丢弃。重放必须幂等，因为崩溃可能发生在 checkpoint 中途，同一事务会被重放多次。没有日志时，「创建文件」的三步（目录项指向 inode 2、位图标记已分配、初始化 inode 内容）按顺序就地写：崩在 1 之后是「目录项指向未分配的 inode」（悬空），崩在 2 之后、3 之前是「inode 已分配但内容全零」，两种都不可用；`journal.c` 在 VM 上跑出的正是「写 1 步 / 写 2 步」两行不一致、「写 3 步」才一致，而 redo 列四行全一致。真实文件系统还要用校验和发现日志撕裂、用 flush/FUA 保证提交记录真的落盘。
:::
:::

::: method 回忆 15 · 三种 `data=` 模式与 `fsync`/`rename` 的边界
ext4 的 `data=journal`、`data=ordered`、`data=writeback` 各保证什么？`fsync(fd)` 保证到哪一层？`rename` 的原子范围是什么？原子写的正确顺序是什么？
::: sol 答案
`data=journal`：数据也进日志，数据与元数据都原子，最慢；`data=ordered`（默认）：数据先于元数据提交，不会出现「元数据指向旧数据」，崩溃后可能看到旧数据；`data=writeback`：不保证顺序，只有元数据一致，最快，可能读到未初始化或旧数据。`fsync(fd)` 保证该文件的数据与元数据落盘（到设备缓存为止，设备带易失缓存时还要 flush/FUA）；目录项是另一个对象，`rename` 之后要 `fsync` 父目录。`rename` 只在**同一文件系统内**原子，跨挂载点返回 `EXDEV`。正确顺序：写临时文件 → `fsync(临时文件)` → `close` → `rename` → `fsync(父目录)`。日志保证的是文件系统结构一致，不保证应用语义。
:::
:::

::: method 回忆 16 · LFS 的五个机制
LFS 的五个关键机制是什么？写路径分几步？清理时怎样判断一个块还活着？checkpoint 为什么写两份？
::: sol 答案
五机制：inode map（inode 号 → 最新 inode 的磁盘地址，随日志追加）；indirect inode map（把 imap 的更新也日志化）；checkpoint region（固定位置，周期性写入，挂载起点）；segment summary（段内每个块属于哪个 inode/偏移）；cleaning（选段、搬活块、回收）。写路径四步：数据块 → inode → imap 项 →（周期性）把 imap 指针写进 checkpoint。清理的存活判定：读段摘要得到每个块的 (inode, 偏移)，再查当前 imap——`imap[inode]` 仍指向这个块才算活；摘要只说「出身」，死活以 imap 现状为准。checkpoint 写两份并带时间戳：崩溃后取时间戳较新且校验一致的那份；之后的段要么丢弃，要么沿段摘要向前滚动。LFS 与日志文件系统不同：数据本来就在日志里，恢复只需找到一致起点，不必重放操作。
:::
:::

::: method 回忆 17 · 8 个实践项目各改哪个结构
李治军的 8 个项目分别是什么？各说出一个关键结构与一条验收证据。
::: sol 答案
1 启动：`bootsect.s`/`setup.s`/`head.s`，验收看 `%cr0` 的 PE 位为 1；2 系统调用：`sys_call_table` + `NR_syscalls`，验收看调用号越界返回 `-ENOSYS`；3 多进程：`task_struct` + `copy_process`，验收看父写变量子看不到（COW）；4 切换：内核栈 + `switch_to`，验收看 `%esp` 变化与两进程输出交替；5 信号量：`sem_t` + `sleep_on`/`wake_up`，验收看缓冲区满/空时正确睡眠与无丢失；6 映射共享：页表 + `do_no_page`，验收看 A 写 B 立刻读到、`pagemap` 同 PFN；7 换入换出：swap + PTE present 位 + LRU，验收看 `/proc/vmstat` 的 `pswpin/pswpout` 增加；8 驱动：`request_queue` + `outb/inb` + 中断，验收看 `dd` 校验一致与中断计数增加。八个项目与第 3 篇一一对应：3.2 启动、3.3 系统调用、3.4–3.5 进程与切换、3.11 同步、3.7–3.10 内存、3.14 驱动。

::: method 回忆 18 · 两个小内核与 50 章落点
xv6 的 `proc.c`/`vm.c`/`log.c` 各覆盖哪件事？rCore 与它最大的不同是什么？OSTEP 50 章按什么规则落到本书？「三件事」怎样交给第 2 篇与第 3–5 篇？
::: sol 答案
`proc.c` 覆盖进程（`struct proc`、`allocproc`、`fork`、`scheduler`），`vm.c` 覆盖地址空间（`walk`、`mappages`、Sv39 三级页表），`log.c` 覆盖持久化（`begin_op`、`log_write`、`commit`、`install_trans`），正好是 OSTEP 的三条主线。rCore 用 Rust 重写、按章递增，`UPSafeCell` 把「运行时借用检查」封在 `unsafe` 里，编译期阻止同一对象的可变别名，但它仍是单核假设、没有 RCU 与 per-CPU，不能当线程安全用。落点规则四档：已覆盖（有独立小节）、合并（并入相邻主题）、背景（只给概念与指路）、淘汰（超出主线）；虚拟化密集落在 1.1/1.9/1.13，并发落在 1.12，持久化落在 1.13.5 与 1.13.11，分布式 46–50 淘汰。接口：第 2 篇 [2.1.1 系统调用穿过什么](../part2/ch01.md#sec-2.1.1) 接住陷阱与切换，第 3 篇 [3.5 调度](../part3/ch05.md#sec-3.5.2)、[3.10 回收](../part3/ch10.md#sec-3.10.1)、[3.12 ext4](../part3/ch12.md#sec-3.12.5) 接住策略与机制，第 5 篇 [5.3 cgroup](../part5/ch03.md#sec-5.3.4) 接住「限额重新表达」。
