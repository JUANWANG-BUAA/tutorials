# 1.7 章末总结

## 五单元一览

| 单元 | 小节 | 核心问题 | 关键结论 | 典型陷阱 |
|:--|:--|:--|:--|:--|
| **一、链接器的位置与容器** | 1.7.1–1.7.2 | 链接器拿到什么、交出什么？为什么同一个 ELF 要有两种视图？ | `cc` 只是驱动程序，真正干活的是 `cc1`、`as`、`ld`；链接器四步是符号解析、合并节、重定位、布局，各自的报错形态不同。ELF 用 `e_type` 区分 `ET_REL`（`.o`）、`ET_EXEC`、`ET_DYN`（共享库与 PIE）；链接器按节工作、加载器按段工作，`.bss` 是 `NOBITS`，只记大小不占文件。 | 以为「编译通过」意味着符号都存在；把 `static` 理解成运行期私有；以为 `strip` 之后没有符号了（删的是 `.symtab`，`.dynsym` 必须留）；以为节索引就是地址顺序。 |
| **二、符号解析与重定位（第一遍）** | 1.7.3–1.7.4、1.7.10–1.7.11 | 同名符号听谁的？地址空洞按什么公式填？ | 函数与已初始化全局变量是强符号，未初始化全局变量在 `-fcommon` 下是 COMMON；两强冲突报错、强加弱取强、弱加弱不可依赖。归档按命令行**从左到右**扫一遍，只拉能解决当前未定义符号的成员，所以被依赖者放右边，循环依赖用 `--start-group`。重定位是带符号算术：`S + A`、`S + A - P`、`L + A - P`，加数 `-4` 补偿「`P` 是字段地址而 CPU 用下一条指令地址」。 | 把 `-lfoo` 当成会搜遍磁盘；以为多个 `int x;` 一定报错（取决于编译选项）；自己猜该减 4 还是减 5；以为 `--wrap` 能改共享库内部的调用；把 `R_X86_64_32S` 的截断当成随机失败。 |
| **三、加载、动态链接与 PIC/PIE** | 1.7.5–1.7.7 | `execve` 之后谁先跑？库怎么被找到？GOT 何时被写？ | 内核只做映射：查 ELF 头、按 `PT_LOAD` 建映射、按 `PT_INTERP` 把 `ld.so` 拉进来、复制 `argv`/`envp`/auxv 到新栈，然后把控制权交给解释器；`_start` 不是 `main`。`ld.so` 的搜索顺序是 `DT_RPATH`（无 `RUNPATH` 时）、`LD_LIBRARY_PATH`、`DT_RUNPATH`、`/etc/ld.so.cache`、默认目录；`RPATH` 传递、`RUNPATH` 只管直接依赖。PIC 靠「模块内 PC 相对 + 跨模块经 GOT」两条手法，PIE 让基址随机，配合 `-z relro`、`-z now`、NX、canary、FORTIFY 构成加固。 | 把 `Entry point` 当成 `main`；以为 `ldd` 只是读文件（它会启动加载器）；以为 `LD_LIBRARY_PATH` 永远优先；以为 `-Wl,-rpath,'$ORIGIN/../lib'` 对间接依赖也生效；以为静态链接的程序完全不依赖系统。 |
| **四、库打桩** | 1.7.8、1.7.13 | 在哪个阶段换实现，能覆盖多大范围？ | 三种时机：编译期宏与函数指针（源码级）、链接期 `--wrap=symbol`（只影响本次链接的未定义引用）、加载期 `LD_PRELOAD`（整个进程及其动态依赖）。钩子里必须用 `dlsym(RTLD_NEXT, ...)` 取真实现并防递归。取证按 `readelf -d` 看 `NEEDED`、`objdump -p` 看 `RPATH`/`RUNPATH`、`LD_DEBUG=libs,bindings` 看搜索与绑定、`ldconfig -p` 看缓存的顺序走。 | 拿 `RTLD_DEFAULT` 找 `malloc` 造成无限递归；在析构函数里用 `printf`；以为静态链接的程序也吃 `LD_PRELOAD`；以为 `-O2` 下每个调用都能被拦到。 |
| **五、逐字段、程序与收束** | 1.7.9、1.7.12、1.7.14–1.7.17 | 工具输出背后的字节是什么？怎么验？ | ELF64 的 Ehdr 与 Shdr 各 64 字节、Sym 与 Rela 各 24 字节、Phdr 56 字节；符号名靠 `st_name` 加 `sh_link` 指向的字符串表，重定位靠 `r_info` 的高 32 位符号下标与低 32 位类型。`elfdump.c` 不链 libelf 也能读这些；`malloc_count.c` 与 `wrap.c` 证明替换确实发生在链接与加载两层。Rust 产物是普通 ELF，差别只在 v0 mangling、`#[no_mangle]`/`extern "C"`、`#[repr(C)]`、`--crate-type` 与默认可见性。 | 把 `.o` 里的 `st_value` 当虚拟地址（那是节内偏移）；以为 `e_shoff`、`e_shnum` 会一直按老格式显示；只读不跑；把正文那几段 x86-64 输出当成自己机器的读数。 |

## 一条主线

这一章从「两个 `.o` 怎么变成一个文件」走到「一个文件怎么变成正在跑的进程」：**先认清 `cc` 背后是 `ld`，链接器只做符号解析、合并节、重定位、布局四件事（1.7.1）；它读写的容器是 ELF，链接器看节、加载器看段（1.7.2、1.7.9）。符号解析决定「听谁的」——强、弱、COMMON 加上归档的单向扫描顺序（1.7.3、1.7.10）；重定位决定「填什么」——`S + A - P` 那一条带符号算术（1.7.4、1.7.11）。链接好的文件交给内核，内核只映射段并按 `PT_INTERP` 把 `ld.so` 拉进来，剩下的搜索、绑定、构造交给加载器（1.7.5、1.7.6）；PIC/PIE 让代码段可以搬到任意基址，顺带成为加固的地基（1.7.7）。因为绑定被推迟到运行期，实现才可以被替换：编译期宏、链接期 `--wrap`、加载期 `LD_PRELOAD` 是同一件事的三个层次（1.7.8、1.7.13）。第二遍把这一切落到字节与可运行代码上：逐字段读 ELF（1.7.9、1.7.12）、两个完整程序（1.7.13）、Rust 视角（1.7.14）、真实二进制实验（1.7.15），最后用十二条陷阱收口（1.7.16）。** 看任何一条链接或加载报错，固定先问三件事：**它发生在哪一层（编译、链接、加载、还是首次调用）？证据是哪条命令的输出？要改的是顺序、符号、路径还是重定位类型？**

## 看到问题先选工具

| 症状 | 第一动作 | 为什么 |
|:--|:--|:--|
| `undefined reference to 'foo'` | 先 `cc -v` 看真实命令行里有没有那个库，再 `nm --defined-only libfoo.a` 确认 `foo` 在哪个成员里 | 十有八九是「没链进来」或「归档顺序不对」，不是头文件问题；成员在库里但没被拉进来，靠顺序或 `--start-group` 解决。 |
| `multiple definition of 'x'` | `nm` 两个 `.o` 看谁把它写成强符号，并确认编译选项是不是 `-fno-common` | 报错说明两处都是强定义；GCC 10 起默认把未初始化全局变量当强符号，静默合并才会暴露成错误。 |
| 符号被别人的实现抢占（同名库、`LD_PRELOAD`、全局插件） | `nm -D` 看它是否进动态符号表，`readelf -s` 看 `Bind` 与 `Vis`，再 `LD_DEBUG=bindings` 看实际绑定到哪个文件 | 谁能被覆盖由绑定类型与可见性决定：`LOCAL` 不参与跨文件解析，`HIDDEN` 不进动态符号表；`LD_DEBUG` 直接告诉你解析结果落在哪个对象里。 |
| 运行期报 `cannot open shared object file` | `readelf -d` 取 `NEEDED` 的 soname，`objdump -p` 取 `RPATH`/`RUNPATH`，再 `LD_DEBUG=libs` 看它搜过哪些目录 | 加载器找的是 soname 而不是你链接时给的文件名；`LD_DEBUG=libs` 会把每一个尝试过的路径打出来，一眼看出是路径还是权限问题。 |
| 报 `version 'GLIBC_2.xx' not found` 或 `version 'FOO_1.0' not found` | `readelf -V`（或 `objdump -p`）看程序要求的版本，再对同一个库看它导出的版本 | 这是符号版本不匹配，不是库缺失：库在、路径对，但那个版本标签没了；根因通常是构建机的 glibc 比目标机新。 |
| `symbol lookup error: undefined symbol` 在换了 `.so` 之后出现 | `nm -D` 对比换掉的两个版本的导出符号，`readelf -d` 核对 `SONAME` | ABI 破坏：符号被删或版本标签变了；`SONAME` 没跟着升会让旧程序加载到不兼容的库。 |
| 链接报 `relocation truncated to fit` | `readelf -r` 找那条类型（常见 `R_X86_64_32S`），再看是不是混用了非 PIC 的目标文件 | 32 位字段放不下 2 GiB 之外的绝对地址；改回 `-fPIE`/`-fPIC` 而不是硬调链接脚本。 |
| 第一次调用某个库函数特别慢 | `readelf -d` 看有没有 `BIND_NOW`，`LD_DEBUG=bindings` 数绑定发生了几次、在什么时候 | 延迟绑定会把解析成本推到第一次调用；`-z now` 把它换回启动期，代价是启动变慢。 |
| 想知道一个二进制加固了什么 | `readelf -h` 看 `Type`、`readelf -d` 看 `BIND_NOW`/`FLAGS`、`readelf -l` 看 `GNU_RELRO` 与 `GNU_STACK` | 这三条在 Linux 上免装任何工具就能给出 PIE、立即绑定、RELRO 与栈执行权限的判据。 |

## 能否讲出这八句话

1. 「编译通过」只保证每个 `.c` 自己成立；跨文件的符号是否存在、地址放不放得下，是链接器的四步——符号解析、合并节、重定位、布局——在管。
2. ELF 有两种视图：链接器按节（`.text`/`.data`/`.rela.text`/`.symtab`）工作，加载器按段（`PT_LOAD`/`PT_INTERP`/`PT_DYNAMIC`）工作；`.bss` 是 `SHT_NOBITS`，占内存不占文件。
3. 强符号是函数与已初始化的全局变量；两个强定义同名就报错，强弱并存取强，两个弱定义谁赢不可依赖。GCC 10 起默认 `-fno-common`，多个 `int counter;` 从静默合并变成 `multiple definition`。
4. 静态库是归档，链接器只从左到右扫一遍、只拉能解决当前未定义符号的成员；所以被依赖者放右边，循环依赖要 `--start-group`，要全量装入用 `--whole-archive`。
5. 重定位不是填绝对地址，而是按类型做一次带符号算术：`R_X86_64_PC32` 是 `S + A - P`，`R_X86_64_PLT32` 是 `L + A - P`；加数 `-4` 来自「`P` 是字段地址、CPU 用下一条指令地址」。
6. 内核不做动态链接：它按 `PT_LOAD` 建映射、按 `PT_INTERP` 把 `ld.so` 拉进来，然后把入口交给解释器；搜索顺序是 `DT_RPATH`（无 `RUNPATH` 时）、`LD_LIBRARY_PATH`、`DT_RUNPATH`、`/etc/ld.so.cache`、默认目录，且 `RPATH` 传递而 `RUNPATH` 不传递。
7. 延迟绑定让第一次调用先走 PLT 桩进解析器、把真实地址写进 GOT 表项，之后同一调用点只剩一次间接跳转；`-z now` 把全部解析挪到启动期，`-z relro` 让 GOT 在重定位完成后只读。
8. 打桩的三种时机覆盖范围不同：`--wrap` 只改本次链接单元里的未定义引用，`LD_PRELOAD` 影响整个进程的动态符号解析，而编译期宏只管你自己的源码；三者都拦不住共享库内部的调用和被内联掉的调用。
