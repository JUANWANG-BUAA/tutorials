## A. 第一遍：概念与判读

::: method 回忆 1 · 层次与量级换算

说出寄存器到 HDD 各层的延迟量级，并把「一次 DRAM 访问」「一次 SSD 随机读」「一次 HDD 寻道」分别换算成多少次 L1 命中。缓存行多大、为什么这个尺寸决定了一次的代价能不能摊薄？

::: sol 答案

正文的两张表给的是典型值而不是承诺：寄存器近乎零、L1 约 1 ns（4–5 周期）、L2 约 3–5 ns、L3 约 10–20 ns、DRAM 约 60–100 ns、NVMe SSD 约 20–100 µs、HDD 约 5–10 ms。换算口径是：一次 DRAM 约等于 100 次 L1 命中，一次 SSD 随机读约等于 1000 次 DRAM，一次 HDD 寻道约等于 10 万次 DRAM。缓存行通常 64 B，一次缺失会把整行拉进来，所以顺序访问能用掉这一行的 8 个 `double` 或 16 个 `int`，把一次缺失摊到多次访问上；步长一旦超过 64 B，每行只用 8 B 甚至 1 B，缺失数就按 $64/\text{stride}$ 成倍上升。

:::
:::

::: method 回忆 2 · 两种局部性与步长

时间局部性与空间局部性各让缓存得到什么？为什么列优先遍历的缺失接近「每个元素一次」，却又不算完全随机？硬件预取器在这里能帮多少？

::: sol 答案

时间局部性让同一个块在缓存里多待一会儿（循环变量、热函数），空间局部性让一次取块覆盖多次访问（数组顺序遍历、顺序指令）。列优先时相邻两次访问相隔 $N\times 8$ 字节（$N=2048$ 时 16 KiB），块内其余 7 个 `double` 要等很久才会被用到，所以每个元素都像一次缺失；但它仍然有空间局部性，只是方向与内存布局垂直，也不是随机地址流。硬件预取器能识别固定步长（部分 CPU 认 4–16 个步长），会把差距缩小，但不会消除——正文那对实验的缺失比约 8:1，时间比也接近这个量级。

:::
:::

::: method 回忆 3 · 三个参数与三段地址

用哪三个参数描述一个组相联缓存？容量、组数、位数之间是什么关系？一次访问按什么顺序被处理，为什么标记只比高位？相联度高换来什么、付出什么？

::: sol 答案

参数是组数 $S$、每组路数 $E$、块大小 $B$，容量 $C=S\times E\times B$。地址从低到高拆成块偏移 $b=\log_2 B$、组索引 $s=\log_2 S$、标记是剩余高位 $t=m-s-b$（$m$ 是地址位数）。访问顺序是：索引选组 → 标记与该组所有路并行比较并检查 valid → 命中就用偏移取字节，缺失就从下层取整块并按替换策略逐出一路。低位不必存进标记，因为索引已经确定组、偏移已经确定块内位置，标记只需要区分「同一个组里的不同块」。$E=1$ 是直接映射，冲突缺失多；$S=1$ 是全相联；相联度越高冲突越少，但比较器更多、命中延迟略高，元数据也占空间（正文那个 32 KiB 缓存的 tag 与 valid/dirty 位约 1 408 字节，占 4.3%）。

:::
:::

::: method 回忆 4 · 三类缺失与 AMAT

3C 缺失分别是什么、怎么把它们分开？写出 AMAT 并算两个数：命中 1 ns、缺失率 10%、代价 20 ns；缺失率降到 2% 呢？多级缓存怎么嵌套？

::: sol 答案

强制性是第一次访问、缓存里必然没有，只能靠预取或增大块缓解；冲突性是多个地址映射到同一组互相驱逐，能提高相联度或改布局；容量性是工作集大于缓存，得靠分块、压缩、SoA 缩小工作集。分开它们的手段是模拟器：同一访问序列扫不同容量，缺失率随容量下降的那部分是容量性；再扫不同相联度，随相联度下降的是冲突性；剩下的下限是强制性。AMAT = 命中时间 + 缺失率 × 缺失代价，所以 1 + 0.10 × 20 = 3 ns，降到 2% 是 1 + 0.02 × 20 = 1.4 ns。缺失代价是命中的 20 倍时，缺失率每降一个百分点就省下 0.2 ns，比抠命中时间划算得多。多级的写法是把下层的 AMAT 当作上层的缺失代价逐层代入。

:::
:::

::: method 回忆 5 · 替换与写策略

说出五种替换策略及硬件为什么多用伪 LRU 或 RRIP。写穿透与写回、写分配与非写分配各是什么组合？为什么对「写一次不再读」的大数组，普通 store 反而浪费带宽，该怎么办？

::: sol 答案

LRU 命中率好但每路要维护年龄信息、成本高；伪 LRU 用树或位近似，是 L1/L2 的实际做法；FIFO 按进入顺序可能驱逐热点；随机最简单、高相联度下平均不差；RRIP 按重用距离预测，抗扫描，常见于 L3。软件不能直接控制替换，但顺序扫描会踢掉热点、分块能把热点留在缓存里——所以「访问顺序」是间接手段。写维度：写穿透每次写都更新下层、简单但流量大，常配非写分配；写回只写缓存并置 dirty、驱逐时才回写，流量小但需要 dirty 位与一致性协议，常配写分配。x86-64 与 ARM64 的 L1/L2/L3 通常是写回 + 写分配，于是一条普通 store 要先做 RFO（read-for-ownership）：把整行读进来才能改，纯写负载白读一遍。对策是非临时存储（x86 的 `movnt`/`stnp` 一类）绕过缓存，或者用 `madvise` 之类的方式让内核处理；注意这类 intrinsic 不可移植。

:::
:::

::: method 回忆 6 · 一致性、TLB 与 NUMA

MESI 的四个状态分别是什么，写之前必须完成什么？伪共享为什么不违反正确性却很慢，两种修法是什么？TLB 有 64 项时，4 KiB 页与 2 MiB 大页各覆盖多少地址范围？NUMA 让哪件事变了？

::: sol 答案

M 是本核独占且已修改（内存副本是旧的），E 是本核独占且干净，S 是多核共享且干净，I 是无效。本地读在 M/E/S 都命中；本地写在 M 直接写、E 升 M 不需总线事务、S 要先发 invalidate 并等其他核确认才进 M；远程写会把其他核的 M/E/S 转 I。核心一句：**写之前必须拿到独占权**。两个核各写同一行里的不同变量，逻辑上互不相干，但每次写都让对方失效，行在核间弹跳（cache line ping-pong），这就是伪共享——正确性没问题，代价是把每次写变成一致性事务。修法：`alignas(64)` 让每个热变量独占一行（代价是占 128 字节而不是 8 字节），或改成按线程分片、每线程局部累加最后合并；定位首选 `perf c2c`。TLB 覆盖 = 项数 × 页大小：64 × 4 KiB = 256 KiB，64 × 2 MiB = 128 MiB，大页把覆盖范围放大 512 倍。NUMA 让「内存延迟」不再是单一值：本地节点约 80 ns、跨节点约 1.5–2 倍且带宽更低，默认策略是本地优先，线程迁移会带来远程访问。

:::
:::

## B. 第二遍：地址拆分、手算与模拟器

::: method 回忆 7 · 把一个地址真的拆开

32 KiB、8 路、64 B 的 L1D：组数与三段位数各是多少？`0xA5C8` 的标记、组号、块内偏移各是多少？换成 48 位虚拟地址、64 KiB 4 路 64 B，三段又各是多少位？写出算式。

::: sol 答案

$S = 32768/(8\times 64) = 64$，所以 `offset` 6 位、`index` 6 位、32 位地址下 `tag` $=32-6-6=20$ 位。`0xA5C8`：`offset` $=$ `0xA5C8 & 0x3F` = `0x08`；`index` $=$ `(0xA5C8 >> 6) & 0x3F` = `0x17` = 23；`tag` $=$ `0xA5C8 >> 12` = `0xA`。也就是落在第 23 组、块内偏移 8、标记 10，该组某路 valid 且标记为 `0xA` 才命中。64 KiB、4 路、64 B 时 $S=65536/(4\times 64)=256$，`index` 8 位、`offset` 6 位，32 位地址下 `tag` 18 位；若用 48 位虚拟地址，同一个 32 KiB/8 路的缓存 `tag` 是 $48-6-6=36$ 位——物理地址位宽不同（常 52 位）标记还会更长，这也是 VIPT 与 PIPT 要区分的原因，展开在 [1.9.3](ch09.md#sec-1.9.3)。

:::
:::

::: method 回忆 8 · 12 次访问与 4 KB 步长

$C=128$ B、$B=16$ B、$E=2$ 的缓存，三段各几位？按正文那 12 次访问的序列说出命中与缺失，命中率多少？为什么这个例子说明「冲突缺失与容量无关」？再说明 `long a[8192]` 按 4 KB 步长访问为什么从第 9 次起全缺，以及三种修法。

::: sol 答案

$S=128/(16\times 2)=4$，`offset` 4 位、`index` 2 位、其余为标记。12 次访问里第 4、6、8、9、12 次命中，共 5 次，命中率 $5/12 \approx 41.7\%$；`0x000`、`0x040`、`0x080`、`0x0C0` 的索引都是 0，两路装满后 LRU 逐个驱逐——而整个缓存 128 B 只装了 6 个块，远没装满，所以缺的不是容量。`a[8192]`（64 KB）按 4 KB 步长访问时，地址每次加 4096，`index` 位（bit 6–11）不变、标记每步加 1，8 路很快被 9 个不同标记填满，从第 9 次开始每次必缺。修法是错开映射：填充数组让行长不是 4 KB 的因子（例如每行 512+8 个元素）、改变访问顺序，或在硬件侧提高相联度；软件侧还能用分块和预取。第三条手算要点：LRU 的年龄只在组内维护，全局最近最少使用没有意义。

:::
:::

::: method 回忆 9 · 模拟器的 miss 率怎么读

[1.6.12](ch06.md#sec-1.6.12) 那个模拟器在 32 KB/8 路/64 B 下扫步长，`stride=1` 与 `stride=32` 的 miss 率各是多少、怎么不用跑就能推出来？`stride` 到多少开始恒为 100%？把 `ways` 改成 1 再跑 `stride=4096` 会看到什么，这说明了什么？

::: sol 答案

每个 `stride` 决定一行 64 B 里被用到几个位置，缺失率约 $1/(\text{block}/\text{stride})=\text{stride}/64$。`stride=1` 时一个块只缺一次、随后 63 次命中，$1/64 \approx 1.6\%$；`stride=2` 是 $1/32$ 即 3.1%，依此类推 `stride=32` 是 50%；到 `stride=64` 每次访问都落在新的块里，miss 率 100% 并保持。正文那串输出（1.6%、3.1%、6.2%、12.5%、25.0%、50.0%、100.0%）就是这条公式，属于模拟器的确定计算，不是硬件读数——它在 macOS 与 Ubuntu 24.04（aarch64 虚拟机，GCC）上复跑完全一致，程序还会打印 `sets=64`，可用来核对 $S=C/(E\times B)$。`ways=1` 时同一组只有一路，`stride=4096` 下 100% 缺失且与容量无关：所有地址映射到同一组互相驱逐，这是冲突缺失的纯净形态。

:::
:::

::: method 回忆 10 · 矩阵乘的字节账

$n=1024$ 的 `double` 矩阵乘，行主序、64 B 行：`ijk` 顺序里 `B[k*n+j]` 的流量上界怎么算出约 68 GB？`ikj` 的总缺失是多少？分块后三个块的工作集约束是什么公式、L2 = 256 KiB 时上限取多少？纸面省的倍数与实际加速比为什么差很远？

::: sol 答案

`ijk` 内层沿 $k$ 走，`B[k*n+j]` 的地址步长是 $n\times 8=8192$ 字节，每次访问都落在新的一行、拉进 64 B 却只用 8 B；内层共 $n^3 \approx 1.07\times 10^9$ 次访问，$1.07\times 10^9 \times 64\ \text{B} \approx 68$ GB（这是「每次访问都缺」的上界，实际会被 L2/L3 吸收一部分）。`ikj` 让 j 在最内层连续，B 与 C 各约 $N^3/8$ 次缺失、合计约 $N^3/4$，$n=512$ 时约 3 350 万次、流量约 2.15 GB；只交换循环顺序就少 8 倍。分块要求三个 $b\times b$ 子矩阵同时驻留：$3b^2\times 8 \le \text{L2}$，即 $b \le \sqrt{\text{L2}/24}$；L2 = 256 KiB 时 $b$ 约 104，取 64 留余量，L2 = 1 MB 时约 208、可取 128 或 256；还要让 $b\times 8$ 是 64 的倍数、避免 4 KB 别名。按 $b=64$ 算，A 约 8 MB、B 约 134 MB、C 约 268 MB，合计约 410 MB，对比 68 GB 是 1/166。但实测加速比远小于 166：分块后计算成了瓶颈（$2n^3$ 次浮点运算），而朴素版早就被内存拖死；正文那台 L2 很大的机器上 `block64` 就没赢过 `ikj`，因为流式访问已经把 B 的每一行完整用上了。

:::
:::

::: method 回忆 11 · AoS 与 SoA 的实测判读

`struct particle { float x,y,z,w; }` 与四个 `float` 数组，只读 `x`：字节数差几倍？正文在 Apple M1 上测到时间差几倍？给出差距小于理论值的三条理由。判断要不要改布局之前先看什么？

::: sol 答案

AoS 每粒子 16 B、SoA 只读 4 B 的 `x` 数组，字节数差 4 倍；正文在 Apple M1 上测到 AoS 3.914 ms、SoA 2.319 ms，比值 1.69 倍，校验值 `sink=2132783616.000000` 两边相同。差距被吃掉的原因有三：① 连续的结构体数组仍是顺序地址流，硬件预取与向量化把一部分代价吸收了，瓶颈从缺失变成带宽与加法吞吐；② SoA 那个循环太短太快，8M 次加法在 2.3 ms 内完成，已接近单核向量加法吞吐，不再是带宽受限；③ 那个 `effective GB/s` 是按「有用字节」算的，AoS 的 34 GB/s 说明它实际搬了 4 倍数据，SoA 的 14.5 GB/s 说明它没把带宽吃满——两个瓶颈位置不同，不能直接除。判断顺序是：先看 `LLC-load-misses` 之类的证据（没有 PMU 时用 `cachegrind` 的 `D1mr` 做 A/B），再改布局。同一份源码在 Ubuntu 24.04 的 aarch64 虚拟机上两次跑出 1.89 与 1.21，`sink` 一致——**方向稳、倍数不稳**，别把任何一台机器的倍数抄成结论。

:::
:::

::: method 回忆 12 · 工具、几何与陷阱

`getconf` 与 sysfs 各能读到什么、在虚拟机里会遇到什么？`cachegrind` 的 `D1mr` 高而 `DLmr` 低说明什么，反过来呢？为什么它的绝对值不能当真？任选六条 1.6.15 的陷阱说出「现象 → 原因 → 修复」。

::: sol 答案

`getconf LEVEL1_DCACHE_LINESIZE` 在多数 Linux 上给 64；`getconf LEVEL1_DCACHE_SIZE` 与 `LEVEL3_CACHE_SIZE` 在 x86 上常有值，但那台 aarch64 虚拟机上返回 0，`/sys/devices/system/cpu/cpu0/cache/` 只有 `index0/1/2` 三个目录可读 `level` 与 `type`，`size`、`ways_of_associativity`、`coherency_line_size`、`number_of_sets` 这些文件根本不存在，`lscpu` 也不打印 cache 行。所以估块大小前要先确认几何拿不拿得到，拿不到就别沿用别人的容量。`D1mr` 高而 `DLmr` 低说明缺失主要发生在 L1（冲突或容量小），可靠调布局或提高相联度缓解；`DLmr` 高说明工作集超出末级缓存，必须分块或减数据。cachegrind 的绝对值不能当真，因为它模拟的是简化几何（那台虚拟机上还打印「Cannot auto-detect cache config, using defaults」，实际用的几何要从 `cg_annotate` 的元数据看）、固定 LRU、不建预取与乱序；它慢 20–50 倍但可复现、能到行，`perf` 快且真实但受事件与权限限制。六条陷阱：① 加大缓存没变快 → 瓶颈是冲突或 TLB → 看 `LLC-load-misses` 与 `dTLB-load-misses`；② 4 KB 步长极慢 → 同组互相驱逐 → 填充或改顺序；③ 多线程扩展性差 → 伪共享 → `alignas(64)` 与分片；④ `memset` 大缓冲慢 → 写分配先读 → 非临时存储；⑤ 分块后更慢 → 块大小不匹配且循环开销上升 → 按 sysfs 几何在 32–128 之间实测；⑥ cachegrind 与真机差很多 → 模拟器不建预取/乱序/多核 → 只做相对比较。

:::
