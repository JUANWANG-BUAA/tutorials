# 1.6 习题集

三组分层，和本章的两遍式结构对齐：**A 组概念判断**考第一遍（1.6.1–1.6.8），要求会读、会判、会说理由；**B 组诊断推理**给现象让你判缺失类型，两遍的知识都要用；**C 组动手实验**考第二遍（1.6.9–1.6.16），要求会算、会写、会在 Linux 上复现。**全部附解答**；先独立完成，再展开对照。

## 怎么用

1. 先读题，不看解答，给自己 2–3 分钟找思路；
2. B 组务必把「缺在哪一层、属于哪一类缺失」写成一句完整的话再动手改——本章最常见错法是跳过分类直接换布局；
3. 卡住了回对应小节的「即时自测」重读，不要直接看答案；
4. C 组的命令都能在 Linux 上免特权跑（`sudo` 不可用时的降级路径已写进解答）；本书的复现环境是 Ubuntu 24.04.5 虚拟机（aarch64、4 vCPU、内核 7.0.0-38-generic、GCC 13.3.0、`perf` 7.0.14、Valgrind 3.22.0），标注「VM 实测」的是这台机器上跑出来的；
5. 做错的题记一个记号，三天后只重做记号题，并去[自检表](ch06-checklist.md)勾对应行。

## A 组 · 概念判断

::: ex 例 1.6-A1 · 数量级与介质 {#ex-1.6-A1}

「SSD 没有机械寻道，所以随机读写和顺序读写一样快」——这句话对吗？另外，把「一次 DRAM 访问」「一次 NVMe 随机读」「一次 HDD 寻道」换算成 L1 命中次数，各约多少？

::: sol 解答

不对。NAND 的读与写单位是页（常见 4–16 KiB），擦除单位是块（数百页），不能原地覆盖：改一页要把整块读出、改、擦、写回，于是有写放大（应用写 1 字节，闪存可能写 3–10 字节）和垃圾回收。所以 4 KB 随机写仍比顺序写慢一个数量级，寿命也按 TBW/DWPD 计。换算按 [1.6.9](ch06.md#sec-1.6.9) 的口径：L1 约 1 ns，DRAM 约 60–100 ns，所以一次 DRAM 约等于 100 次 L1 命中；NVMe 随机读 20–100 µs 约等于 1 000 次 DRAM；HDD 寻道 5–10 ms 约等于 10 万次 DRAM。这些是典型量级，不是某台机器的规格。

:::
:::

::: ex 例 1.6-A2 · 三句关于局部性的判断 {#ex-1.6-A2}

逐句判断并对错的改正：① 列优先遍历就是随机访问；② 按行遍历总是最快；③ 一个 `double` 数组每隔 8 个元素访问一次，等于每次访问都缺。

::: sol 解答

① 不对。列优先仍有空间局部性，只是方向与内存布局垂直：相邻两次访问相隔 $N\times 8$ 字节，不在同一行里；而且它是固定步长，硬件预取器能识别（部分 CPU 认 4–16 个步长），会把差距缩小但不会消除。② 不对。本质是「沿内存连续的方向遍历」，C 是行主序所以按行快，Fortran 与 BLAS 的列主序习惯下按列才连续。③ 对，如果这里的「每隔 8 个元素」是索引步长 8：$8\times 8=64$ 字节正好是一个缓存行，每个新元素都落在新行里，块内其余 7 个用不上；按字节算步长 8 反而是连续的，一次行能摊 8 次访问。步长要用字节说清，这正是 $64/\text{stride}$ 那条判据容易混的地方。

:::
:::

::: ex 例 1.6-A3 · 位域怎么随相联度变 {#ex-1.6-A3}

一个 64 KiB、4 路、块 64 B 的缓存：组数、`index` 位数、`offset` 位数各多少？32 位地址的 `tag` 是多少位？把相联度从 4 路提到 8 路（容量与块不变），三段位数分别怎么变？

::: sol 解答

$S = 65536/(4\times 64) = 256$，`index` 8 位、`offset` 6 位、`tag` $=32-8-6=18$ 位（这题与正文 [1.6.17](ch06.md#sec-1.6.17) 的自测同形，先自己算再核对）。提到 8 路时 $S=65536/(8\times 64)=128$，`index` 变 7 位、`offset` 仍是 6 位、`tag` 变 19 位——相联度不改变块大小，只把组数减半，于是原来分到两组的地址并成一组。收益是冲突缺失变少，代价是比较器翻倍、命中延迟略升、每行还要存更长的标记。

:::
:::

::: ex 例 1.6-A4 · 三个场景各属哪类缺失 {#ex-1.6-A4}

① 第一次完整扫描一个从未读过的大数组；② `long a[8192]` 按 4 KB 步长访问，缓存在同一台机器上从 32 KB 换成 256 KB 仍几乎每次必缺；③ 256 MB 工作集在 32 KiB 的 L1 上。分别属哪类？说出一条能把它们分开的实验方法。

::: sol 解答

① 强制性：第一次访问缓存里必然没有，只能靠预取或更大的块摊薄，扩容量救不了第一次。② 冲突性：4 KB 步长的地址 `index` 位（bit 6–11）不变、标记每步加 1，全挤在同一组互相驱逐，扩容量而不扩相联度就看不到改善——这正是「换更大缓存没变快」的典型成因。③ 容量性：工作集远超层级容量，靠分块把驻留部分压进去。区分方法照 [1.6.4](ch06.md#sec-1.6.4)：拿同一个访问序列在模拟器上扫两个维度，缺失率随容量下降的那部分是容量性，随相联度下降的是冲突性，剩下的下限是强制性；[1.6.12](ch06.md#sec-1.6.12) 那个模拟器改 `size` 与 `ways` 就能跑这两扫。

:::
:::

::: ex 例 1.6-A5 · 抠命中时间还是抠缺失率 {#ex-1.6-A5}

某负载 L1 命中 1 ns、缺失率 10%、缺失代价 20 ns。两个改动：甲把命中时间压到 0.8 ns、缺失率不动；乙把缺失率降到 5%、命中时间不动。各算 AMAT 并选一个。再说明为什么多级缓存要把公式嵌套。

::: sol 解答

基线 AMAT $=1+0.1\times 20=3$ ns。甲 $=0.8+2=2.8$ ns；乙 $=1+0.05\times 20=2.0$ ns，选乙。规律是缺失代价 20 ns 是命中时间的 20 倍，所以缺失率每降一个百分点省 0.2 ns，而降命中时间最多只能省不到 1 ns——**缺失代价越大，越该动局部性而不是动命中路径**。多级的关系是：L1 的缺失代价不是「到 DRAM」，而是 L2 的 AMAT；L2 的缺失代价是 L3 的 AMAT，逐层代入，才能解释为什么 L1 命中率的小幅改善在真机上远没有单级模型看起来那么值钱。

:::
:::

::: ex 例 1.6-A6 · 写完就丢的缓冲区 {#ex-1.6-A6}

你分配 1 GiB 缓冲区，`memset` 填零后马上整个丢弃（不再读）。有人说「全是写，跟读没关系，应该很快」。这句话漏了什么？什么策略组合能避免这件事，代价是什么？

::: sol 解答

漏了写分配。现代 CPU 的 L1/L2/L3 通常是写回 + 写分配，一条普通 store 缺失时要先做 RFO（read-for-ownership）：把整行 64 B 读进缓存才能改，于是「纯写」实际产生读流量，带宽被白花掉一半以上。能避免的组合是写穿透 + 非写分配（不先把行读进来），或写回 + 非写分配；硬件侧的对应手段是非临时存储（x86 的 `movnt`/`stnp` 一类）绕过缓存直接写内存。代价：写穿透流量大、需要一致性协议配合；非临时存储不可移植（属 x86 intrinsic，ARM64 要另找写法，本书未实测），而且后续若马上要读这块数据，绕过缓存反而更慢。

:::
:::

::: ex 例 1.6-A7 · 同一行里的两个计数器 {#ex-1.6-A7}

两个线程分别对 `struct { int a; int b; } c;` 的 `c.a` 与 `c.b` 做百万次自增，扩展性比单线程还差。这段代码有数据竞争或正确性问题吗？为什么慢？给两种修法并说明各自代价。你只有一台没有 PMU 事件的机器，怎么证实这个判断？

::: sol 解答

没有正确性问题：`a` 与 `b` 是不同对象，各自自增不会互相覆盖。慢在一致性：两个变量落在同一个 64 B 缓存行里，MESI 要求写之前拿到独占权，于是线程 1 写 `a` 让线程 2 的副本失效、线程 2 写 `b` 又反过来失效，行在核间来回弹跳，每次写都变成一次一致性事务。修法一：`alignas(64)` 让每个计数器独占一行，代价是占用从 8 字节变 128 字节；修法二：按线程分片（每线程局部累加、结束时合并，或 per-CPU 变量），代价是要写合并逻辑并承受额外内存。没有 `perf c2c` 时，做 A/B 就够：同一段代码分别在「两个变量相邻」与「用填充隔开到不同行」两种布局下计时（绑核、多次取最小值），时间回到单线程量级即证实；也可以把两者拆到相隔 4 KiB 的位置作为第二组对照，排除「只是巧合的同组映射」。

:::
:::

::: ex 例 1.6-A8 · TLB 覆盖与大页的代价 {#ex-1.6-A8}

L1 dTLB 有 64 项：4 KiB 页覆盖多少地址范围？换 2 MiB 大页呢？大页换来什么、付出什么？四级页表一次遍历大概要几次内存访问？如果一台机器只有一个 NUMA 节点，正文说的「远程访问慢 1.5–2 倍」你能在这台机器上测吗？

::: sol 解答

64 项 × 4 KiB = 256 KiB，也就是 TLB 只覆盖 256 KiB 地址；64 × 2 MiB = 128 MiB，覆盖范围放大 512 倍——这就是数据库、JVM、DPDK 用大页的理由。代价是内部碎片（不足一页也得占一整页）与分配不灵活，且是否真生效要验：`/sys/kernel/mm/transparent_hugepage/enabled` 常是 `madvise`，不调 `madvise(MADV_HUGEPAGE)` 就没有。四级页表遍历（PGD/PUD/PMD/PT，48 位虚拟地址）最坏 4 次内存访问，但中间级页表项有空间局部性、通常会被缓存，实际常只有 1–2 次真到 DRAM。最后一个问题：**测不了**。单节点没有本地/远程之分，正文的 1.5–2 倍需要多节点机器；本书的 Ubuntu 虚拟机上 `numactl --hardware` 只报 1 个节点，所以这条只能引用为量级，不能当作可复现结论。

:::
:::

## B 组 · 诊断推理

::: ex 例 1.6-B1 · 换了循环顺序就快 8 倍 {#ex-1.6-B1}

`C[i][j] += A[i][k]*B[k][j]` 的三重循环从 `ijk` 改成 `ikj`，指令数与浮点运算次数完全不变，时间降到一个数量级以内，IPC 反而升高。写出「现象 → 缺在哪一层 → 哪一类缺失 → 证据」四段，并说明为什么 IPC 会上升。

::: sol B1 核对

现象是「代码更少搬数据」而不是「算得更快」。缺在末级缓存以下（工作集 3 个 $n\times n$ 的 `double` 矩阵，远大于 LLC），类型是容量性为主、叠加冲突：`ijk` 的最内层沿 $k$ 走，`B[k*n+j]` 的地址步长是 $n\times 8$ 字节，$n=1024$ 时一次访问拉 64 B 只用 8 B，流量上界约 68 GB（正文 [1.6.16](ch06.md#sec-1.6.16) 的账）。改成 `ikj` 后 j 在最内层连续，B 与 C 都被顺序扫，缺失降到约 $N^3/4$，$n=512$ 时流量从 8.6 GB 降到 2.15 GB。IPC 上升是因为停等 DRAM 的周期少了：同样的指令数在更少周期里跑完，`instructions/cycles` 自然变大。证据顺序：有 PMU 时看 `LLC-load-misses` 与 `dTLB-load-misses` 在两个版本之间的差别；没有 PMU 时用 [1.6.12](ch06.md#sec-1.6.12) 的模拟器或直接对 `cachegrind` 的 `DLmr` 做 A/B，指令数（`Ir`）几乎不变而数据缺失大幅下降，就是这条结论的确定性证据。

:::
:::

::: ex 例 1.6-B2 · 改了 SoA 只差 1.2 倍 {#ex-1.6-B2}

你按 [1.6.13](ch06.md#sec-1.6.13) 把只读 `x` 字段的循环从 AoS 换成 SoA：字节数应该差 4 倍，实测只快 1.2 到 1.9 倍（同一份源码两次跑出不同倍数）。有人说实验失败了。你怎么解释现象？下一步测什么？

::: sol B2 核对

没失败，差距本来就不会等于字节比。三条理由都在正文里：① AoS 仍是顺序地址流，硬件预取与向量化吸收了相当一部分多读的字节，瓶颈从缓存缺失变成内存带宽与加法吞吐；② SoA 那个循环太短太快，8M 次浮点加已在单核向量加法吞吐附近，不再缺带宽；③ 那两个 `effective GB/s` 是按「有用字节」算的，34 GB/s 说明 AoS 真搬了 4 倍数据、14.5 GB/s 说明 SoA 没吃满带宽，两个瓶颈位置不同，不能直接相除。至于两次跑出不同倍数：微基准的墙钟方差本来就大（VM 上两次 1.89 与 1.21 差近 1.6 倍），要绑核、多次取最小值再看趋势。下一步：先量化「缺失是否还在」——`cachegrind` 比两版的 `D1mr`/`DLmr`（`Ir` 应当接近），有 PMU 时看 `LLC-load-misses`；如果 SoA 版缺失已经很低而时间没降，瓶颈就转到了 [1.5.6](ch05.md#sec-1.5.6) 那条依赖链/吞吐账上，该动的是累加器个数与向量化，不是继续改布局。收益接近理论上限的条件是「字段更多、只读更少」或工作集再大一个数量级。

:::
:::

::: ex 例 1.6-B3 · 命中率异常 {#ex-1.6-B3}

一个 64 KB 的数组在 32 KB、8 路、64 B 的 L1 上按 4 KB 步长扫描，缺失率接近 100%。同事的结论是「缓存太小，换 256 KB 就好」。请反驳，并给出三种修法与各自代价。

::: sol B3 核对

64 KB 小于 32 KB 的 2 倍，看起来像容量问题，但缺的是映射不是空间：4 KB 步长意味着地址每次加 4096，`offset`（bit 0–5）与 `index`（bit 6–11）一位都不变，只有标记递增，所以所有访问都落在同一组；8 路只能容 8 个块，第 9 次起必然驱逐前面的，扩到 256 KB 若组数同步变大，index 位数增加，这个「同组」的性质也可能保持或改变——结论不靠猜，用 [1.6.12](ch06.md#sec-1.6.12) 把 `size` 与 `ways` 各扫一遍就能分别看到容量效应与相联效应（A4 的那套方法）。三种修法：① 填充（padding）改变行长，让行与行之间的地址差不是 4 KB 的因子（例如每行 512+8 个元素），代价是浪费内存与缓存空间；② 改变访问顺序或做分块，让同一时刻活跃的行数不超过路数，代价是循环复杂度和边界处理；③ 在软件可控的范围内换布局（SoA、把常一起用的列排在一起），代价是代码改动。提高硬件相联度也是选项，但那不是你写代码能决定的。

:::
:::

::: ex 例 1.6-B4 · 分块之后更慢 {#ex-1.6-B4}

你把矩阵乘按 [1.6.5](ch06.md#sec-1.6.5) 分块，取 `bs=128`，结果比 `ikj` 慢。列出三个可能原因，并说出各自怎么用数字排除。另外：正文提到那台 L2 很大的机器上 `block64` 没赢过 `ikj`，这说明「分块」的哪一条前提？

::: sol B4 核对

① 工作集放不下：$3b^2\times 8 = 3\times 128^2\times 8 = 393$ KiB，若目标层是 256 KiB 的 L2 就超了，等于没分块——用 $b \le \sqrt{\text{L2}/24}$ 反推合法上限（256 KiB 时约 104），再上下试两档。② 循环开销与边界：外层多出 `ii/kk/jj` 三层，块太小或非整除时边界处理占比上升；用 $n$ 固定、$bs$ 扫 16/32/64/128 看拐点，同时确认结果与 `ikj` 一致（浮点求和顺序变了，要比容差）。③ 别名与行冲突：块行宽 $b\times 8$ 若正好是 4 KB 的因子，块内多行会挤同组；$b=64$ 时行宽 512 B 是安全的，$b=512$ 就有风险，可以按 [1.6.10](ch06.md#sec-1.6.10) 的填充思路改行宽再测。至于「`block64` 没赢过 `ikj`」：分块的前提是循环交换之后仍有容量性缺失；那台机器的末级/L2 很大，`ikj` 的顺序流已经把 B 的每一行完整用上了，块内复用能省的字节本来就不多——**分块治的是容量与别名，治不了「已经没有可省」的情况**。

:::
:::

::: ex 例 1.6-B5 · 一加大线程数就变慢 {#ex-1.6-B5}

一个多线程程序里每个线程写自己那格 `stats[tid].count`，结构体只有一个 `int` 成员。线程从 2 加到 8，总时间不降反升。给出两条可能的原因（一条与缓存有关、一条与调度有关），并设计一个能在没有 PMU 的机器上判掉缓存那条的最小实验。

::: sol B5 核对

缓存那条是伪共享：`stats[0]` 与 `stats[1]` 只差 4 字节，同一行里相邻线程的写互相失效，核越多弹跳越凶。调度那条是迁移与负载不均：线程被调度到不同核（甚至不同节点）时本地性与亲和性变了，或者某个线程独占热点，扩展性天花板由最慢的那个决定。判掉伪共享的最小实验：把结构体撑到一行——`struct { alignas(64) int count; }`（或手动加 `char pad[64]`），其余代码一字不改，同机器同线程数再计时；时间明显回落并接近线性即证实。为了排除「只是代码变大带来的巧合」，再加一组对照：把间隔撑到 4 KiB（跨页），若两组的 64 B 与 4 KiB 结果接近而都远好于无填充组，说明起作用的是行边界而不是页或对齐噪声。调度那条用 `taskset` 把每个线程绑到不同核再跑一次：绑核后仍慢就是伪共享或真竞争，绑核后变快说明迁移是主因。有 PMU 时 `perf c2c` 一步到位，但本书那台 VM 上它直接报「no PMU supports the memory events」，所以 A/B 才是可依赖的证据。

:::
:::

::: ex 例 1.6-B6 · miss 数为 0 或干脆报错 {#ex-1.6-B6}

你跑 `perf stat -e L1-dcache-load-misses,LLC-load-misses ./prog`，三种可能的结果：全 0、显示 not supported、或者报「No supported events found」。分别是什么原因？各自先查什么？如果都拿不到硬件事件，你还能用什么证据下结论？

::: sol B6 核对

全 0 通常是「计数被限制或事件不映射」：容器与虚拟机经常不暴露 PMU，或事件名在你平台上不存在而 perf 静默给 0；先 `perf list` 看事件在不在，再确认平台事件名（`L1-dcache-load-misses`、`LLC-load-misses` 是 Intel/AMD 的叫法，ARM64 不同）。not supported 表示该事件平台不实现，0 不等于没有缺失——这时改用同一条命令里的其他字段交叉判断。直接报「No supported events found」是权限问题：`cat /proc/sys/kernel/perf_event_paranoid`，值偏大（本书那台 VM 上是 4）时非特权用户拿不到 CPU 事件，报错里会明确说需要 `CAP_PERFMON`/`CAP_SYS_ADMIN`；调低它需要 root，本书环境里 `sudo` 不可用，所以这条路要写成「需特权，本机未实测」。拿不到硬件事件时的替代证据：`cachegrind` 的 `D1mr`/`DLmr` 做版本间相对比较（确定性、可到行，但几何是模拟的）；墙钟时间与 CPE（绑核、多次取最小值）；以及 [1.6.12](ch06.md#sec-1.6.12) 那种自写模拟器给出的「步长—缺失率」曲线。三者合起来足以判断瓶颈在不在访存，只是给不出真机绝对值。

:::
:::

::: ex 例 1.6-B7 · 缓存解释不了的那一半 {#ex-1.6-B7}

一个跨页大步长的扫描程序，`D1mr` 已经不高，但时间仍随步长增大而显著恶化；你把 `madvise(MADV_HUGEPAGE)` 加上后时间没变。查 `/sys/kernel/mm/transparent_hugepage/enabled` 显示 `always [madvise] never`。说出你的判断顺序，以及每一步读什么。

::: sol B7 核对

先怀疑地址翻译而不是数据缓存：`D1mr` 不高而时间继续恶化，说明缺的是 TLB 项而不是缓存行。步长 4 KiB 时每次访问都换页，64 项的 L1 dTLB 只覆盖 256 KiB，很快被换光；一次 TLB 缺失要走页表遍历，最坏 4 次内存访问。判断顺序：① 算覆盖范围（项数 × 页大小）与你的活跃页数量对比；② 有 PMU 就看 `dTLB-load-misses` 在两种步长下的差；③ 没有 PMU 就只验「大页到底有没有生效」——`enabled` 显示当前是 `madvise`，意味着只有显式 `madvise(MADV_HUGEPAGE)` 的那段映射才可能用大页，这与你已经调用它一致，所以问题更可能在碎片或分配失败；读 `/proc/self/smaps_rollup` 的 `AnonHugePages`（配合 `Rss` 一起看），为 0 就说明一段也没拿到，时间不变也就顺理成章。另外要看映射是否满足 2 MiB 对齐与长度要求、`/proc/meminfo` 里 hugepage 相关字段，以及是否被 `MADV_NOREUSE` 或内存紧张挡住。要点是：**不要用「加了大页没变快」推「TLB 不是瓶颈」，先证明大页真的生效了**；本书 VM 上免特权能读到 `AnonHugePages` 的实测值，见 [例 1.6-C5](#ex-1.6-C5)。

:::

## C 组 · 动手实验

::: ex 例 1.6-C1 · 先确认机器几何，别靠猜 {#ex-1.6-C1}

用三条免特权命令确认你这台机器的缓存行、层级与 NUMA 拓扑，并把拿不到的字段如实记下来。（macOS 上没有 `lscpu` 与 sysfs 这套，需在 Linux 虚拟机里做。）

::: sol C1 核对

```bash
getconf LEVEL1_DCACHE_SIZE; getconf LEVEL1_DCACHE_LINESIZE; getconf LEVEL3_CACHE_SIZE
for d in /sys/devices/system/cpu/cpu0/cache/index*; do
  echo "$d level=$(cat $d/level) type=$(cat $d/type) size=$(cat $d/size 2>/dev/null) ways=$(cat $d/ways_of_associativity 2>/dev/null) line=$(cat $d/coherency_line_size 2>/dev/null) sets=$(cat $d/number_of_sets 2>/dev/null)"
done
lscpu | grep -iE 'cache|numa'
numactl --hardware
```

读法与陷阱：字段齐全时（正文 [1.6.14](ch06.md#sec-1.6.14) 那台 Apple M1 给出 `index0: 1 Data 48K ways=12 line=64` 等四行），你可以直接用 $S=C/(E\times B)$ 核对组数；字段拿不到也属正常。VM 实测（Ubuntu 24.04.5、aarch64）：`index0/1/2` 三个目录存在且 `level`、`type` 可读，但 `size`、`ways_of_associativity`、`coherency_line_size`、`number_of_sets` **这些文件不存在**，`getconf LEVEL1_DCACHE_SIZE` 返回 0、只有 `LEVEL1_DCACHE_LINESIZE` 给 64，`lscpu` 不打印任何 cache 行；`numactl --hardware` 报 `available: 1 nodes (0)`、4 个 CPU。结论要如实写：这台机器给不出层级容量与相联度，所以任何块大小估算都得标注假设；单节点机器上测不了 NUMA 远程代价。

:::

::: ex 例 1.6-C2 · 跑缓存模拟器并做两扫 {#ex-1.6-C2}

编译运行 [1.6.12](ch06.md#sec-1.6.12) 的 `cache_sim.c`，用三组配置核对公式；再对同一序列做「扫容量」与「扫相联度」两趟，说出 3C 的哪一类被分开。

::: sol C2 核对

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 cache_sim.c -o cache_sim
./cache_sim 32768 8 64      # 预期 sets=64
./cache_sim 32768 1 64      # 直接映射
./cache_sim 65536 4 64      # 预期 sets=256
```

第一组应打印 `cache=32768 B ways=8 block=64 sets=64`，然后 1 MiB 数组按步长扫描给出 1.6%、3.1%、6.2%、12.5%、25.0%、50.0%、100.0%、之后恒 100%。核对两件事：`sets` 等于 $C/(E\times B)$，miss 率约等于 $\text{stride}/64$（即每行只用 $\text{stride}$ 字节时，一个块缺一次）。VM 实测：GCC 13.3.0 下 `-Wall -Wextra -Werror` 无警告通过，输出与正文逐行一致（这类确定性模拟结果本来就该跨机器一致，因为数组内容不进 miss 计数）。两扫：把 `ways` 固定、`size` 从 8192 扫到 262144，看哪部分改善来自容量；把 `size` 固定、`ways` 从 1 扫到 8，看 `stride=4096` 那一行什么时候从 100% 掉下来——随相联度下降的是冲突性，随容量下降的是容量性，两扫都不动的下限就是强制性。这三条曲线就是你回答 A4、B3 时该拿出的证据。

:::

::: ex 例 1.6-C3 · 用 cachegrind 给两个布局做 A/B {#ex-1.6-C3}

对 [1.6.13](ch06.md#sec-1.6.13) 的 `soa.c` 跑 `cachegrind`，用 `D1mr`/`DLmr` 判断 AoS 与 SoA 两个循环的缺失差别，并把行级注释拿到手。

::: sol C3 核对

```bash
cc -std=c17 -D_GNU_SOURCE -O2 -g soa.c -o soa_g        # -g 是关键
valgrind --tool=cachegrind --cache-sim=yes ./soa_g
cg_annotate cachegrind.out.51949 | head -20            # 只喂一个文件
cg_annotate --auto=yes cachegrind.out.51949 | less     # 行级
```

四步读法与四条实测坑。读法：先看 `-- Auto-annotated source` 里两个循环各自行（`s1 += aos[i].x;` 那一组与 `s2 += sx[i];` 那一组）的 `Dr`、`D1mr`、`DLmr`；`Ir` 两版接近而数据缺失明显不同，就是「差距来自访存不是指令」的确定性证据；`D1mr` 高而 `DLmr` 低指向 L1 层的问题（布局或对齐），`DLmr` 高说明超出末级模拟容量。坑（都在 VM 的 Valgrind 3.22.0 上实测）：① 不加 `-g` 时行级全是空的，只能退回函数级；② 会打印 `Cannot auto-detect cache config, using defaults`，`cg_annotate` 的元数据显示它用的是 `D1 cache: 16384 B, 64 B, 4-way`、`LL cache: 262144 B, 8-way`——**别照抄「默认 32 KB L1」这种说法**，先读元数据或显式传 `--I1/--D1/--LL`；③ `cg_annotate` 一次喂多个数据文件会报 `events in data files don't match`，用 `ls -t cachegrind.out.*` 取一个；④ 墙钟在模拟下不可信（那次运行给出 AoS 47.990 ms 对 SoA 13.291 ms，比值 3.61 倍，与 native 的 1.21–1.89 倍完全不同），只用它的计数做相对比较。程序慢 20–50 倍，先把 $N$ 调小跑通流程。

::: ex 例 1.6-C4 · 判掉 perf 的可用性再决定读什么 {#ex-1.6-C4}

不要求拿到具体计数，只要求你用三条命令判断这台机器能不能给出缓存事件；不能就写下降级路径。（`perf` 是 Linux 专有，macOS 上没有。）

::: sol C4 核对

```bash
command -v perf; perf --version
cat /proc/sys/kernel/perf_event_paranoid
perf stat -e cycles,instructions ./true
perf stat -e cache-misses,cache-references,L1-dcache-loads,L1-dcache-load-misses,LLC-load-misses ./true
perf c2c record true
```

VM 实测（Ubuntu 24.04.5、aarch64、`perf version 7.0.14`）：`perf` 装了，但 `perf stat` 的 `cpu-cycles` 显示 not supported，指定事件那条直接报 `No supported events found`，并在报错里写明 `perf_event_paranoid setting is 4` 以及需要 `CAP_PERFMON`/`CAP_SYS_PTRACE`/`CAP_SYS_ADMIN`；`perf c2c record` 报 `failed: no PMU supports the memory events`。**结论：这个环境给不出缓存与一致性事件，正文里所有 `perf` 读数都不能在这里复现。** 不要顺手写「调低 `perf_event_paranoid` 就好」——那一步需要 root，本书的 VM 上 `sudo` 需要密码、自动化不可用。降级路径按代价排序：`cachegrind` 做 A/B（确定性、到行，见 C3）、自写模拟器（C2）、绑核后的墙钟与 CPE（`taskset`，这台 VM 上有）；实在需要真机 PMU 就把结论标成「未实测」，而不是拿别人的数当自己的。

::: ex 例 1.6-C5 · 免特权验证大页真的生效 {#ex-1.6-C5}

写一个 20 行的程序：`mmap` 64 MiB 匿名内存、`madvise(MADV_HUGEPAGE)`、逐页触碰一次，然后读自己的 `smaps_rollup`。先读 THP 的策略，再判断大页有没有用上去。

::: sol C5 核对

```c
char *p = mmap(NULL, len, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
int r = madvise(p, len, MADV_HUGEPAGE);        /* r==0 只表示调用成功 */
for (size_t i = 0; i < len; i += 4096) p[i] = 1;   /* 真正分配 */
FILE *f = fopen("/proc/self/smaps_rollup", "r");   /* 找 AnonHugePages 与 Rss */
```

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled   # always [madvise] never
cat /sys/kernel/mm/transparent_hugepage/defrag
```

关键判据：`madvise` 返回 0 **不等于**大页生效——在 `enabled` 是 `madvise` 的系统上（VM 实测就是这个值），要逐页触碰让内核真的分配之后才有 2 MiB 页；只看返回码是最常见的假结论。VM 实测：64 MiB 映射、`madvise` 返回 0、触碰后 `Rss: 66940 kB`、`AnonHugePages: 65536 kB`，也就是几乎整段都以 2 MiB 页落地；不触碰就基本读不到 `AnonHugePages`。这条链解释了 B7 里「时间没变」该怎么查。反过来，`AnonHugePages` 为 0 时先别怪 TLB 不是瓶颈，先确认对齐、长度、内存碎片与 `defrag` 策略。至于大页省下多少：需要 `dTLB-load-misses`，本环境拿不到，所以这里只写方法与「省了多少时间未实测」。

::: ex 例 1.6-C6 · 步长曲线与内存山 {#ex-1.6-C6}

跑 [1.6.8](ch06.md#sec-1.6.8) 的步长程序或 [1.6.14](ch06.md#sec-1.6.14) 的 `mountain.c`，把工作集与步长两个方向的读数各记一排，并说出每个台阶与斜坡属于哪一层。你的读数和正文的能对上吗？

::: sol C6 核对

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 mountain.c -o mountain
taskset -c 2 ./mountain          # 绑核；没有 taskset 时关后台负载
./mountain                       # 跑 3 次，取最小值那一排
```

读法沿两个方向：沿工作集看台阶（32 KiB 落在 L1、256 KiB 落在 L2、8 MiB 落在 L3、64 MiB 只能走 DRAM），沿步长看斜坡（步长超过 64 B 后每行只用 8 B，理想折损约 1/8；再跨页就叠上 TLB 缺失，掉得更多）。两个必须先写下的限制：① 台阶的高度不只由缓存决定——正文指出小工作集那个「高原」被 `sink += buf[i]` 的加法依赖链封顶（见 [1.5.10](ch05.md#sec-1.5.10)），所以要判断是不是内存带宽，得先把累加拆成多条独立链再测；② 正文那组 GB/s（32 KiB/stride 8 约 26、64 MiB/stride 8 约 37、stride 64 约 9.7、stride 512 约 1.1）来自 Apple M1，正文自己标注未在 x86-64 复测，所以**别指望和你的数对上**，比的是形状与拐点。绝对值不属于你的机器时，只报「我的机器上拐点在步长 X、工作集 Y」。

::: ex 例 1.6-C7 · 自己扫一次块大小 {#ex-1.6-C7}

把 [1.6.5](ch06.md#sec-1.6.5) 的分块形状写成可调 `bs` 的函数，在 $n=512$ 上扫 `bs` = 16、32、64、128，并与 `ikj` 比较；先算理论区间再实测。

::: sol C7 核对

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 mm.c -o mm
./mm 512 16; ./mm 512 32; ./mm 512 64; ./mm 512 128; ./mm 512 0   # 0 表示 ikj
```

先算再跑：$3b^2\times 8$ 是三个块的工作集，$b=128$ 时 393 KiB、$b=64$ 时 98 KiB、$b=32$ 时 24 KiB；拿 C1 读到的真实容量（读不到就明确写「本机容量未知」）套 $b \le \sqrt{\text{L2}/24}$，先给出你预期最好的两档，再实测。三个校验不能省：与 `ikj` 的结果按浮点容差比对（分块改了求和顺序，逐位不等是正常的）；每个 `bs` 跑多次取最小值；确认 `bs` 不是编译期常量时循环开销的占比。判据是「拐点在哪」而不是「谁赢了」：如果你的机器上 `ikj` 一直最快，说明循环交换已经消灭了容量性缺失（正文在 L2 很大的那台机器上就是这个结果，见 [1.5.12](ch05.md#sec-1.5.12)），此时分块不是优化而是复杂度；如果最优 `bs` 落在 32–64，就和公式吻合。写结论时把机器、编译器、`bs` 与容量假设一起写上，别把别人的最优块当成你的。
