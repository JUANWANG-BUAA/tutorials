到目前为止，你看到的控制流都是程序自己安排的：顺序、分支、循环、函数调用。CPU 的 `%rip` 沿着编译器铺好的轨道走。但真实系统里，轨道会被外力掰弯：网卡收到一个包、定时器到期、进程访问了不在内存的页、用户按下 `Ctrl-C`、子进程退出。这些事件发生时，CPU 必须暂停当前指令流，跳到一个内核预先注册的入口。

这类「不是由当前指令直接引起的控制转移」叫**异常控制流**（exceptional control flow, ECF）。它有三个层次：硬件异常（CPU 与内核交接）、进程（内核给每个程序一个独立执行上下文）、信号（内核把异步事件通知给进程）。三者层层嵌套：异常是机制，进程是容器，信号是接口。

[1.1.4](ch01.md) 已经讲过 `fork/exec/wait` 的基本形态和五状态表。这一章不再重复那些入门内容，而是补三块硬骨头：**异常分类与内核入口**、**信号处理的竞态与可重入性**、**非本地跳转与作业控制**。读完这一章，你应该能解释 `strace` 输出里每一个 `--- SIGCHLD ---`，也能写出不会被信号打断出错的代码。

## 1.8.1 异常：CPU 与内核的交接点 {#sec-1.8.1}

这一节回答：CPU 正在跑你的用户代码，凭什么会突然跳进内核？跳进去处理完，是回到刚才那条指令，还是下一条？

::: preview 先抓住一件事
异常不是「程序出错」的同义词，而是 CPU 与内核之间一套硬件强制的交接机制：CPU 按编号跳到一个内核预先注册的入口，处理完再决定返回哪里。分类的关键只有一条——返回地址：中断和陷阱返回下一条指令，故障返回当前指令重试，终止不返回。缺页是最典型的故障：能修好就重试，修不好才变成 `SIGSEGV`。
:::

先看一次真实的崩溃。程序把一个空指针解引用，外面套一层 `strace`，只看信号：

```c
/* null.c：向地址 0 写一个值 */
#include <stdio.h>

int main(void)
{
    volatile int *p = NULL;
    puts("before");
    fflush(stdout);
    *p = 42;
    puts("after");
    return 0;
}
```

```text
# 实测（Ubuntu 24.04.5 aarch64，GCC 13.3.0）
$ strace -e trace=signal ./lab1c08_null
before
--- SIGSEGV {si_signo=SIGSEGV, si_code=SEGV_MAPERR, si_addr=NULL} ---
+++ killed by SIGSEGV (core dumped) +++
$ echo $?
139
```

`before` 打印出来了，说明进程确实执行到了写之前。随后 CPU 在一条存储指令上发现地址 0 没有映射，把控制权交给内核；内核判断这个地址不在进程的任何合法区间里，修不好，于是把这次硬件故障翻译成 11 号信号 `SIGSEGV` 递给进程（`si_code=SEGV_MAPERR` 就是「地址没有映射」）。进程没有装处理函数，默认动作是终止，shell 拿到的退出码是 139，也就是 128 + 11。

这一串动作里有两个容易混的点。第一，`SIGSEGV` 不是 CPU 直接发给进程的：CPU 只会按向量跳进内核，信号是内核翻译后的结果。第二，内核本来有机会回到**同一条**写指令：如果地址 0 只是「页不在内存」，缺页处理程序会分配一页、填好页表（虚拟地址到物理地址的映射表），然后让那条写指令重来一次。这里地址 0 根本不属于进程，修不了，才走到终止。

::: def 定义 1.8.1 · 异常（exception） {#def-1.8.1}
异常是 CPU 在执行指令时检测到某个事件后，暂停当前指令流、按事件编号（向量）跳进内核处理程序的一套硬件机制。内核在启动时把每个向量的入口地址填进**中断描述符表**（interrupt descriptor table, IDT）。异常可以是同步的（由当前指令引起，如缺页、除零），也可以是异步的（由外部设备引起，如时钟、网卡）。
:::

最常见的分类是四类。这张表不用背例子，先看「返回地址」一列：

| 类别 | 谁引起 | 同步/异步 | 返回地址 | 例子 |
|:--|:--|:--|:--|:--|
| 中断（interrupt） | 外部设备 | 异步 | 下一条指令 | 时钟、网卡、键盘 |
| 故障（fault） | 当前指令执行失败，可能可修复 | 同步 | **当前指令**（重试） | 缺页、除零、段错误 |
| 陷阱（trap） | 指令有意触发 | 同步 | 下一条指令 | `int3`、系统调用 |
| 终止（abort） | 不可恢复的硬件错误 | 同步 | 不返回 | 机器检查、总线错误 |

「返回当前指令」是故障与陷阱的分水岭。故障发生时，CPU 在指令**提交之前**报告错误，保存的返回地址指向出错的那条指令；内核修好条件后执行 `iret`，同一条指令重新执行，这次就成功了。陷阱则是一条故意安排的计划：`int3` 让调试器停下，系统调用让内核代劳，处理完当然回到下一条。终止没有「回来」这回事，内核通常直接终止进程。

x86-64 的 IDT 有 256 个表项，前 32 个向量由 CPU 保留。缺页是 14 号，出错地址不在指令里，而在控制寄存器 `%cr2`；出错码压在栈上，用位记录「读还是写、用户态还是内核态、页不存在还是保护违规」。13 号是通用保护故障，常见于越权或非规范地址；128 号（`0x80`）是老式系统调用入口。系统调用常被归入陷阱一类，但 x86-64 的 `syscall` 指令走的是另一套入口，不经过 IDT 表项，1.8.8 会把向量表、`#PF` 错误码的五位含义和 `syscall` 的寄存器约定逐项拆开。这里先记住「有编号、有入口、有返回地址」这三件事。

「异常控制流」这个名字容易让人以为只讲错误。实际上，缺页、系统调用、时钟中断都在内：它们共同的特点是**下一条指令不是由当前指令的顺序、分支或调用决定的**。理解这一点，后面看 `fork` 返回两次、信号打断 `read`、`longjmp` 跳回旧栈帧，才不会觉得是魔法。

::: errata 关于异常的四个误解
1. **「异常就是程序出错了」**——缺页、断点、系统调用都是异常，绝大多数不是错误；只有内核修不好时，才转成 `SIGSEGV` 之类的信号。
2. **「中断和异常是并列的两件事」**——在常见的英文教材分类里，中断是异常的一种（异步那一类）；中文教材常把「中断」当总称，读英文材料时要看上下文。
3. **「缺页一定要杀进程」**——匿名页第一次写、文件页第一次读、COW（写时复制）页第一次写，都会缺页，内核补好页表就让指令重试；只有地址非法或权限不符才终止。
4. **「信号是硬件直接发给进程的」**——硬件只负责把 CPU 交给内核；信号是内核根据异常类型、权限和进程状态翻译出来的通知。
:::

### 1.8.1 小结

① 异常是 CPU 按向量进入内核的硬件入口，IDT 存入口地址；同步还是异步，看事件是不是当前指令引起的。② 四类异常的分水岭是返回地址：中断、陷阱返回下一条，故障重试当前指令，终止不返回。③ 缺页能修就重试，修不好才变成信号；`SIGSEGV` 是内核翻译的结果，不是 CPU 直接发的。如果只记住一件事，那就是：**看到「异常」先问返回哪里，看到「信号」先问是谁翻译的。**

::: method 即时自测 · 1.8.1
**Q1（记忆）** 四类异常各自返回哪里？各举一个例子。

**Q2（辨析）** 一次缺页一定会导致进程收到 `SIGSEGV` 吗？什么情况下会，什么情况下不会？

**Q3（应用）** 程序解引用空指针后被 `SIGSEGV` 终止，shell 里的 `$?` 是 139。这个数字怎么来的？如果程序自己捕获了 `SIGSEGV` 并正常退出，`$?` 又会是多少？

::: sol 答案
**A1** 中断返回下一条指令（时钟、网卡）；陷阱返回下一条指令（`int3`、系统调用）；故障返回当前指令重试（缺页、除零）；终止不返回（机器检查、总线错误）。
**A2** 不一定。地址属于进程的某个合法区间、只是页不在内存（或需要 COW 复制、需要从文件读入）时，内核补页后让指令重试，进程无感；地址不在任何合法区间、或权限不符（写只读页、用户态访问内核页）时，内核修不好，才发 `SIGSEGV`。
**A3** 139 = 128 + 11，11 是 `SIGSEGV` 的编号，shell 用「128 + 信号号」表示「被信号终止」。若程序捕获 `SIGSEGV` 后从处理函数正常 `return` 或调用 `exit(0)`，`$?` 就是程序自己的退出码（通常为 0），但继续执行原指令很可能再次触发同一个故障。
:::

## 1.8.2 进程：异常控制流的容器 {#sec-1.8.2}

这一节回答：内核处理一次缺页、递送一个信号时，凭什么知道该用哪张页表、哪张 fd 表、哪套信号掩码？「进程」到底是由哪些东西拼起来的？

::: preview 先抓住一件事
进程不是「正在运行的程序」这一句口号，而是内核用 `task_struct` 把地址空间、fd 表、信号状态、凭证、寄存器和内核栈捆成的一个容器。异常处理程序、信号处理函数、调度器都只在这个容器里工作。`ps` 的 `STAT` 列和 `/proc/<pid>/status` 是观察这个容器的两个窗口。
:::

先读一个真实进程的状态快照。下面是在 Ubuntu 24.04 的一个 shell 里读它自己的 `/proc/$$/status`：

```text
# 实测（Ubuntu 24.04.5 aarch64；pid 与内存值每次不同）
$ grep -E '^(Name|State|Tgid|Pid|PPid|VmRSS|Threads)' /proc/$$/status
Name:	bash
State:	S (sleeping)
Tgid:	11151
Pid:	11151
PPid:	11147
VmRSS:	    3252 kB
Threads:	1
$ ls /proc/$$/fd | tr '\n' ' '
0 1 2
```

`Name` 是任务名，`State` 是调度状态；`Tgid` 是线程组号，`Pid` 是任务号，这里相等说明这个 shell 只有一个线程；`PPid` 指向启动它的父进程；`VmRSS` 是当前驻留物理内存；`Threads` 是线程数。`/proc/$$/fd` 里只有 0、1、2，说明这个 shell 当前只开着标准输入、输出、错误三个描述符。这些字段不是磁盘上的文件内容，而是内核在你读的那一刻，从 `task_struct` 和它的子结构里现算出来的。

::: def 定义 1.8.2 · 进程（process） {#def-1.8.2}
进程是内核为一次程序执行维护的隔离容器，包含独立的地址空间（页表）、文件描述符表、信号处置与阻塞掩码、用户与组凭证、寄存器上下文和内核栈。Linux 用 `task_struct` 描述它；多个 `task_struct` 可以共享地址空间与 fd 表，那就是线程。
:::

按「异常处理需要什么」来记 `task_struct` 的关键字段：

| 字段 | 装的是什么 | 异常/信号处理时用来做什么 |
|:--|:--|:--|
| `mm` | 地址空间、页表基址 | 缺页时判断地址属于哪个区间、补哪张页表 |
| `files` | fd 表 | 信号处理函数里 `write` 日志、`close` 连接 |
| `sighand` / `signal` | 处置表、阻塞掩码、pending 集合 | 决定这个信号是捕获、忽略还是默认动作 |
| `cred` | uid、gid、capabilities | `kill` 权限检查、文件访问检查 |
| `thread_struct` | 寄存器、栈指针、FPU 状态 | 上下文切换时保存与恢复 |
| `__state` | 运行、可中断睡眠、不可中断睡眠、停止 | 调度器决定谁上 CPU；信号能否唤醒它 |
| `exit_state` / `exit_code` | 退出状态、退出码 | 父进程 `wait` 时交出状态字 |

这张表不用背全，抓住一条：**异常处理不是「内核凭空做事」，它始终在某个进程的上下文里，用这个进程的 `mm`、`files`、`sighand` 做事。** 内核里的 `current` 宏就指向当前 CPU 上正在运行的那个 `task_struct`。

地址空间这一格值得多说一句。每个进程都以为自己独占从 0 到高地址的整片空间，实际上是页表把虚拟地址翻译到物理页；页表怎么建、四级怎么走，1.1 已经打过底，1.9 会展开。这里只记结论：`fork` 时复制的是页表，不是物理内存；切换进程时内核要换页表基址（x86-64 上是 `%cr3`）。

每个进程还有一套**内核栈**。用户态的函数调用用用户栈，进程因系统调用或异常进入内核后，改用内核栈；x86-64 上通常是 16 KiB（4 个 4 KiB 页）。两者是不同的栈指针，所以「用户栈溢出」和「内核栈溢出」是两回事。上下文切换时，内核保存被调用者保存寄存器、栈指针和返回地址；换页表会让 TLB（地址翻译缓存）里的旧翻译失效，PCID 给不同进程的 TLB 项打标签，减少冲刷。真正的成本不止几百条指令，还包括缓存与 TLB 工作集的污染——这也是为什么频繁切换进程比频繁调用函数贵得多。

`ps` 的 `STAT` 列把这些状态压成字母：

| 字母 | 含义 | 典型场景 |
|:--|:--|:--|
| `R` | 正在运行或在运行队列里 | 算得正欢的进程 |
| `S` | 可中断睡眠 | 等 `read`、等 `wait` |
| `D` | 不可中断睡眠 | 等磁盘 I/O、等 NFS |
| `T` | 被停止 | `Ctrl-Z`、`SIGSTOP` |
| `Z` | 僵尸 | 已退出、父进程还没 `wait` |

{{#include ../assets/figures/proc-states.md}}

读图时先看两条环：可运行与可中断睡眠之间的等待/唤醒，以及运行 → 僵尸 → 回收。附加字母里，`s` 表示会话首进程，`l` 表示多线程，`+` 表示在前台进程组。`D` 状态要单独警惕：它不响应信号，`kill -9` 也要等内核把 I/O 完成；大量 `D` 进程通常说明存储或网络文件系统卡住了。

信号会推动状态迁移：`SIGSTOP` 把进程推入 `T`，`SIGCONT` 把它放回运行队列，`SIGKILL` 直接推向退出，`SIGSEGV` 默认终止并可能产生 core，`SIGCHLD` 把睡眠的父进程唤醒去 `wait`。`TASK_TRACED` 是 `ptrace` 专用的停止状态，`gdb` 的断点就停在这里；按 `ps` 手册，它显示为小写 `t`，与作业控制造成的 `T` 不是一回事。

::: errata 关于进程的四个误解
1. **「进程就是程序」**——程序是磁盘上的文件，进程是这次执行的容器；同一个程序跑两遍是两个进程，各有各的页表和 fd 表。
2. **「`ps` 的 VSZ 就是占用的内存」**——VSZ 是虚拟地址空间大小，RSS 才是驻留物理页；一个 `malloc` 了 1 GiB 但没碰过的进程，RSS 可能只有几 MiB。
3. **「`D` 状态也能 `kill -9` 杀掉」**——不能。不可中断睡眠要等内核完成 I/O 或释放锁，信号只能排队等它醒来。
4. **「僵尸进程还占着内存」**——僵尸的地址空间已经释放，留下的是 `task_struct`、退出状态和 PID；数量多了会耗尽 PID，但不会吃光内存。
:::

### 1.8.2 小结

① 进程是内核的隔离容器，`task_struct` 把地址空间、fd 表、信号状态、凭证、寄存器和内核栈捆在一起；异常与信号都在这个容器里处理。② `ps` 的 `STAT` 是调度状态的缩写，`/proc/<pid>/status` 是同一批字段的原文；`D` 与 `Z` 是两种完全不同的「卡住」。③ 切换进程要换页表、污染 TLB 与缓存，成本远高于函数调用。如果只记住一件事，那就是：**异常处理程序不是没有上下文的「内核代码」，它永远在某个进程的容器里工作。**

::: method 即时自测 · 1.8.2
**Q1（记忆）** `task_struct` 里与异常/信号处理最相关的四个字段是什么？各装什么？

**Q2（辨析）** `Tgid` 与 `Pid` 相等说明什么？一个多线程进程里，这两个值分别怎样？

**Q3（应用）** `ps` 里看到一个 `D` 状态的进程，`kill -9` 没反应；另一个 `Z` 状态进程，`kill -9` 也没反应。两者的原因一样吗？分别该怎么处理？

::: sol 答案
**A1** `mm`（地址空间与页表）、`files`（fd 表）、`sighand`/`signal`（处置表、掩码、pending）、`thread_struct`（寄存器与栈指针）；`cred`、`__state`、`exit_code` 也常用。
**A2** 相等说明这个任务既是线程组首领又是组里唯一的线程（单线程进程）。多线程进程里，组内所有线程的 `Tgid` 相同（等于首领的 `Pid`），每个线程的 `Pid` 各不相同。
**A3** 不一样。`D` 是不可中断睡眠，进程还活着，只是内核不让它被信号打断，要等 I/O 完成或超时；`Z` 是已经退出、等父进程 `wait` 的僵尸，`kill` 对尸体无效。前者查存储/网络与内核栈，后者找父进程回收或让父进程处理 `SIGCHLD`。
:::
:::

## 1.8.3 fork/exec/wait 的边界 {#sec-1.8.3}

这一节回答：`fork` 之后父子进程到底共享什么、复制什么？`exec` 换掉程序时保留哪些东西？`wait` 返回的那个 `status` 为什么不能直接打印？

::: preview 先抓住一件事
三个调用各管一段：`fork` 造出第二个执行流，复制 fd 表但共享打开文件偏移；`exec` 把当前进程换成新程序，PID 不变，fd 与信号处置有选择地保留；`wait` 回收子进程，交回一个编码过的状态字。记住这三条边界，1.8.11 的完整 shell 程序就只是把它们串起来。
:::

先跑一个最小实验，一次看住 `fork` 与 `wait` 两个边界。父进程把文件写成 `0123456789`，把偏移拨回 0，然后 `fork`；子进程写一个 `C` 后 `_exit(7)`，父进程 `wait` 到它，再写一个 `P`：

```c
/* forkfd.c：共享的文件偏移与编码过的退出状态 */
#ifndef _GNU_SOURCE
#define _GNU_SOURCE
#endif
#include <fcntl.h>
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void)
{
    const char *path = "/tmp/lab1c08_offset.txt";
    int fd = open(path, O_RDWR | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) { perror("open"); return 1; }
    if (write(fd, "0123456789", 10) != 10) { perror("write"); return 1; }
    if (lseek(fd, 0, SEEK_SET) == -1) { perror("lseek"); return 1; }

    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }
    if (pid == 0) {
        if (write(fd, "C", 1) != 1)
            _exit(1);
        _exit(7);                    /* 子进程用 _exit，不刷父进程的 stdio 缓冲 */
    }

    int status = 0;
    if (waitpid(pid, &status, 0) != pid) { perror("waitpid"); return 1; }
    if (write(fd, "P", 1) != 1) { perror("write"); return 1; }
    printf("raw status=%d WIFEXITED=%d WEXITSTATUS=%d\n",
           status, WIFEXITED(status), WEXITSTATUS(status));
    close(fd);

    char buf[32] = {0};
    fd = open(path, O_RDONLY);
    if (fd < 0) { perror("open"); return 1; }
    ssize_t n = read(fd, buf, sizeof buf - 1);
    if (n < 0) { perror("read"); return 1; }
    printf("file=[%.*s] bytes=%zd\n", (int)n, buf, n);
    close(fd);
    return 0;
}
```

```text
# 实测（Ubuntu 24.04.5 aarch64，GCC 13.3.0）
$ ./lab1c08_forkfd
raw status=1792 WIFEXITED=1 WEXITSTATUS=7
file=[CP23456789] bytes=10
```

先看文件内容。子进程的 `C` 落在偏移 0，父进程的 `P` 落在偏移 1，把原来的 `1` 覆盖掉了，所以结果是 `CP23456789`，不是 `C0123456789P`。这证明 `fork` 复制的是 fd 表，表项仍指向同一个「打开文件描述」，`f_pos` 是共享的。若父子各自 `open` 一次，偏移就各从 0 开始，`P` 会覆盖 `C`。要各自独立偏移，重新 `open`，`dup` 不行。

再看 `status`。子进程 `_exit(7)`，父进程直接打印 `status` 得到 1792，`WEXITSTATUS(status)` 才是 7。1792 是 `7 << 8`：低 7 位放终止信号编号，第 7 位放 core 标志，退出码放在第 8–15 位，停止状态另有一套编码。所以永远不要 `printf("%d", status)`，要用 `WIFEXITED`/`WEXITSTATUS`、`WIFSIGNALED`/`WTERMSIG` 拆。

`fork` 的复制清单可以按「异常控制流需要什么」来记。复制：fd 表、信号处置与阻塞掩码、当前工作目录、`umask`、资源限制、进程组与会话。不复制：子进程的 pending 信号被清空，`alarm` 定时器不继承，父进程持有的 `fcntl` 记录锁不继承，`fork` 的返回值不同（子进程 0，父进程子进程 pid）。

地址空间是写时复制（copy-on-write, COW）：页表复制一份，物理页先共享只读，谁写谁触发缺页，内核才复制那一页。页表怎么复制、写保护缺页怎么处理，1.1 与 1.9 已经讲过，这里只记结论：`fork` 的大头是页表，不是内存。

`execve` 是另一条边界。它把当前进程的地址空间、寄存器、栈全部换成新程序，但保留 PID、PPID、进程组、会话、真实 uid/gid、没有设 `FD_CLOEXEC` 的 fd、被显式设为 `SIG_IGN` 的信号处置，以及阻塞掩码。被捕获的信号处置会重置为默认，因为旧处理函数的地址在新地址空间里没有意义；`atexit` 注册的函数不会执行；`FD_CLOEXEC` 的 fd 在 exec 时关闭。

所以「父进程忽略 `SIGPIPE`，子进程 exec 后仍忽略」是 POSIX 规定；自定义的 `SIGINT` 处理函数在 exec 后消失。打开文件时默认加 `O_CLOEXEC`，是防止 fd 泄漏到子程序的最省事办法。完整的 `fork`+`execvp`+`waitpid` 程序在 1.8.11，更细的复制/重置表在 1.8.9，这里先把三条边界说清。

`wait` 负责回收。子进程退出后不会立刻消失：内核保留退出状态和统计信息，等父进程 `wait` 读取，这个「已死未回收」的状态就是僵尸。父进程先死，子进程被 `init`（PID 1）或最近的 subreaper 收养，不会永久僵尸。`waitpid(-1, ...)` 等任意子进程，`WNOHANG` 非阻塞轮询，`WUNTRACED` 才报告停止，`WCONTINUED` 才报告继续。`wait` 可能被信号打断返回 `EINTR`，要重试；没有子进程可等时返回 `ECHILD`。

写 fork/exec 代码还有两个必须处理的失败点。`fork` 返回 -1 通常是 `EAGAIN`（进程数或内存不足）或 `ENOMEM`；`exec` 只在失败时返回，`ENOENT` 是程序不存在，`EACCES` 是没有执行权限，`ENOEXEC` 是格式不对。子进程 exec 失败后必须 `_exit(127)`，不能 `exit(127)`：子进程继承了父进程的 stdio 缓冲区，`exit` 会把它 flush 一遍，可能把父进程还没写出的内容重复打印。

::: errata 关于进程控制的五个误解
1. **「`fork` 后父子 fd 偏移独立」**——不独立。复制的是 fd 表，表项指向同一个打开文件描述，偏移共享；要独立偏移，各自 `open`。
2. **「子进程退出后立刻消失」**——先进入僵尸，等父进程 `wait` 才释放；长期不 `wait` 的服务会积累僵尸、耗尽 PID。
3. **「`exec` 会保留信号处理函数」**——捕获的处理函数重置为默认，只有 `SIG_IGN` 保留；别指望 exec 后的程序继续用父进程的 handler。
4. **「`wait` 只能等一个固定 pid」**——`waitpid(-1, ...)` 等任意子进程，`WNOHANG` 非阻塞，`waitid` 提供更细的选项。
5. **「`system()` 等价于 fork+exec」**——`system` 要经过 `/bin/sh -c`，信号处理、返回值编码、`SIGINT` 的忽略都不同；安全敏感场景不要用它拼接命令。
:::

```c

printf("B");
```

:::

### 1.8.3 小结

① `fork` 复制 fd 表但共享打开文件偏移，地址空间用 COW；pending 信号、定时器、记录锁不继承。② `exec` 保留 PID、fd、忽略的信号与阻塞掩码，重置捕获的处理函数；失败只能用 `_exit` 退出。③ `wait` 交回的是编码状态字，退出码 7 在里面是 1792，必须用状态宏拆。如果只记住一件事，那就是：**`fork` 共享的是「打开的文件」，不是「文件偏移」；`wait` 拿到的是「编码的状态」，不是「退出码」。**

## 1.8.4 信号：产生、阻塞、递送 {#sec-1.8.4}

这一节回答：`kill` 发出一个信号后，它究竟在哪一刻打断程序？为什么先 `raise` 再 `pause` 会永久睡死，而 `sigsuspend` 不会？

::: preview 先抓住一件事
信号有四个阶段：产生、挂起（pending）、阻塞（blocked）、递送（delivery）。阻塞不是丢掉，而是把信号留在 pending 集合；解除阻塞后，内核在进程下一次返回用户态时递送它。标准信号（1–31）不排队，同一种只记一次。`sigsuspend` 把「换掩码」和「睡眠」合成一个原子动作，堵住检查与睡眠之间的空窗。
:::

先做一个可控实验：阻塞 `SIGUSR1`，在进程内 `raise` 它，看它停在 pending；然后分别用 `pause` 与 `sigsuspend` 等它。

```c
/* wake.c：阻塞 → pending → 递送；pause 与 sigsuspend 的差别 */
#ifndef _GNU_SOURCE
#define _GNU_SOURCE
#endif
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static volatile sig_atomic_t got;

static void on_usr1(int signo)
{
    got = signo;
}

static void show_pending(const char *tag)
{
    FILE *f = fopen("/proc/self/status", "r");
    char line[256];
    if (!f) { perror("fopen"); return; }
    while (fgets(line, sizeof line, f))
        if (!strncmp(line, "SigPnd:", 7) || !strncmp(line, "SigBlk:", 7))
            printf("%s %s", tag, line);
    fclose(f);
}

int main(int argc, char **argv)
{
    if (argc != 2) { fprintf(stderr, "usage: %s pause|sigsuspend\n", argv[0]); return 2; }
    setvbuf(stdout, NULL, _IONBF, 0);

    struct sigaction sa;
    memset(&sa, 0, sizeof sa);
    sa.sa_handler = on_usr1;
    sigemptyset(&sa.sa_mask);
    if (sigaction(SIGUSR1, &sa, NULL) == -1) { perror("sigaction"); return 1; }

    sigset_t set, old;
    sigemptyset(&set);
    sigaddset(&set, SIGUSR1);
    if (sigprocmask(SIG_BLOCK, &set, &old) == -1) { perror("sigprocmask"); return 1; }

    raise(SIGUSR1);                 /* 进程内给自己发，绝不会失败 */
    show_pending("blocked:");
    printf("handler ran=%d\n", (int)got);

    if (strcmp(argv[1], "pause") == 0) {
        sigprocmask(SIG_SETMASK, &old, NULL);
        printf("after unblock: got=%d\n", (int)got);
        alarm(1);
        pause();                    /* 信号已经处理完，这里会睡到 SIGALRM */
        puts("pause returned");
    } else {
        alarm(1);
        if (sigsuspend(&old) == -1 && errno == EINTR)
            printf("sigsuspend returned: got=%d\n", (int)got);
    }
    return 0;
}
```

```text
# 实测（Ubuntu 24.04.5 aarch64，GCC 13.3.0；用 alarm(1) 观察）
$ ./lab1c08_wake pause
blocked: SigPnd: 0000000000000200
blocked: SigBlk: 0000000000000200
handler ran=0
after unblock: got=10
Alarm clock
$ echo $?
142
$ ./lab1c08_wake sigsuspend
blocked: SigPnd: 0000000000000200
blocked: SigBlk: 0000000000000200
handler ran=0
sigsuspend returned: got=10
$ echo $?
0
```

先读前四行。`SIGUSR1` 是 10 号信号，位图第 9 位为 1，十六进制就是 `0x200`。`SigBlk` 有这一位，说明它被阻塞；`SigPnd` 也有，说明 `raise` 之后它没有丢，正停在 pending 集合里。`handler ran=0` 是关键：信号已经产生，但进程还在阻塞它，所以处理函数一次都没跑。

`pause` 分支里，`sigprocmask(SIG_SETMASK, &old, NULL)` 解除阻塞，内核在 `sigprocmask` 返回前就把 pending 的 `SIGUSR1` 递送了，处理函数把 `got` 置成 10。等程序走到 `pause()`，这次信号已经用掉，它只能等**下一次**信号；`alarm(1)` 一秒后送来 `SIGALRM`，默认动作终止，shell 报告 `Alarm clock`，退出码 142（128 + 14）。这就是「先解除阻塞、再睡」的空窗：信号在 `pause` 之前就用掉了。经典的 `while (!got) pause();` 把空窗挪到判断与睡眠之间，信号恰好在那时到达，`pause` 照样睡下去。

`sigsuspend` 分支把顺序倒过来：先 `alarm`，再 `sigsuspend(&old)`。它的语义是「把掩码设为 `old`，然后挂起」，这两步在内核里是一个原子操作（不可被打断的一次读改写）。掩码一换，pending 的 `SIGUSR1` 立刻递送，处理函数执行，`sigsuspend` 返回 `EINTR`，打印 `got=10`，程序正常退出。信号要么在 `sigsuspend` 之前就 pending，要么在睡眠期间到达，不存在「判断完之后、睡下之前」的空窗。

::: def 定义 1.8.4 · 信号的生命周期 {#def-1.8.4}
信号产生后进入目标进程（或线程）的 pending 集合；若该信号当前被阻塞，它留在集合里，直到解除阻塞；解除阻塞后，内核在进程下一次从内核态返回用户态时递送它，执行处置：默认动作、忽略，或调用用户注册的处理函数。标准信号（1–31）不排队，同一信号在 pending 期间再次产生只记一次；实时信号（`SIGRTMIN`–`SIGRTMAX`）排队并带值。
:::

### 默认动作与 sigaction

常见信号的默认动作：

| 信号 | 默认动作 | 典型来源 | 能否捕获/阻塞 |
|:--|:--|:--|:--|
| `SIGINT` | 终止 | `Ctrl-C` | 能 |
| `SIGQUIT` | 终止 + core | `Ctrl-\` | 能 |
| `SIGTERM` | 终止 | `kill`、systemd | 能 |
| `SIGKILL` | 终止 | `kill -9`、OOM killer | **不能** |
| `SIGSEGV` | 终止 + core | 非法内存访问 | 能（通常不该恢复） |
| `SIGPIPE` | 终止 | 写已关闭的管道/socket | 能 |
| `SIGCHLD` | 忽略 | 子进程退出/停止 | 能 |
| `SIGSTOP` | 停止 | `kill -STOP`、作业控制 | **不能** |
| `SIGCONT` | 继续 | `fg`/`bg`、`kill -CONT` | 能 |
| `SIGUSR1/2` | 终止 | 用户自定义 | 能 |

`SIGCHLD` 的默认处置写作「忽略」，但内核仍保留子进程的退出状态，父进程照样能 `wait` 到；把它显式设为 `SIG_IGN`，Linux 才会自动回收、不产生僵尸。标准信号「不排队」也是很多 bug 的根源：两个子进程几乎同时退出，内核只保证至少有一个 `SIGCHLD` 处于 pending；handler 只调用一次 `waitpid`，就会留下一个僵尸。正确写法是循环 `waitpid(-1, ..., WNOHANG)` 直到返回 0 或 -1。

`sigaction` 比 `signal` 可控，因为行为都写成了标志：

```c
struct sigaction sa = {0};
sa.sa_handler = on_sigint;
sigemptyset(&sa.sa_mask);          /* handler 执行期间额外阻塞的信号 */
sa.sa_flags = SA_RESTART;
sigaction(SIGINT, &sa, NULL);
```

`sa_mask` 在 handler 执行期间**追加**阻塞；`SIGINT` 自身默认已被阻塞，除非 `SA_NODEFER`。`SA_RESTART` 让可重启的慢系统调用自动重启；`SA_RESETHAND` 让 handler 执行一次后恢复默认。要用三参数 handler 时，把 `sa_handler` 换成 `sa_sigaction` 并加上 `SA_SIGINFO`，才能拿到 `siginfo_t` 与 `ucontext_t`。`SA_RESTART` 不是万能：`poll`、`epoll_wait`（`epoll` 是批量等待 fd 事件的内核接口）、`select`、`nanosleep`、`pause`、`sigsuspend` 都不会自动重启，必须自己处理 `EINTR`；`read` 已经读了部分数据时也不会重启，而是返回短读。

### 异步信号安全

handler 可能在主程序的任意指令之间执行，包括 `malloc` 正在改堆、`printf` 正在锁 stdio 的时候。因此它只能调用**异步信号安全**（async-signal-safe）的函数：`write`、`read`、`open`、`close`、`_exit`、`kill`、`sigaction`、`sigprocmask` 等；`printf`、`malloc`、`free`、`exit`、`strerror` 都不安全。实践中的最小 handler 只做两件事：把 `volatile sig_atomic_t` 标志置位，或往 pipe 写一个字节；复杂逻辑回主循环。handler 里若要读写 `errno`，先存后恢复，别让主程序看到被改过的错误码。

### 信号与 fork/exec/线程

- `fork` 后子进程继承处置与掩码，但 pending 集合被清空；
- `exec` 后捕获的处置重置为默认、忽略的保持忽略、掩码保留；
- 多线程进程里，进程级信号递给任意一个未阻塞它的线程；`pthread_sigmask` 管每线程掩码；
- 专门等信号的线程可以用 `sigwaitinfo`/`sigwait` 同步地取信号，避开 handler 的可重入问题；
- `signalfd` 把信号变成 fd 事件，能塞进 `epoll` 循环。

这些边界在 1.8.10 会连同 `signalfd`、self-pipe 与线程掩码展开。

::: errata 关于信号的五个误解
1. **「`signal()` 和 `sigaction()` 一样」**——历史实现里 `signal()` 可能重置处置、可能不重启系统调用；可移植代码统一用 `sigaction`，把行为写进标志。
2. **「信号会排队，来几个处理几次」**——标准信号不排队，`SIGCHLD` 尤其容易合并；必须循环 `waitpid(-1, ..., WNOHANG)` 收割。
3. **「处理函数里可以 `printf`」**——`stdio` 有锁和缓冲区，`printf` 不是异步信号安全的；用 `write` 或只置标志。
4. **「设了 `SA_RESTART` 就万事大吉」**——`poll`、`epoll_wait`、`select`、`nanosleep` 不会自动重启；可重启的调用也可能因短读需要自己处理。
5. **「`SIGKILL` 也能被捕获」**——`SIGKILL` 与 `SIGSTOP` 不能被捕获、阻塞或忽略；这是内核留下的最后手段。
:::

::: ex 例 1.8.4 · 先猜这行掩码屏蔽了哪个信号 {#ex-1.8.4}
`grep SigBlk /proc/self/status` 打出 `SigBlk: 0000000000004000`。先猜：屏蔽的是几号信号？已知 `SIGUSR1` 是 10、`SIGUSR2` 是 12、`SIGTERM` 是 15。

::: sol 解答
`0x4000` 是 2 的 14 次方，也就是「第 14 位为 1（从 0 数）」；信号掩码的规则是**位 (signo − 1) 对应信号 signo**，所以它是 **15 号信号 `SIGTERM`**。本机实测：程序里 `sigaddset(&s, SIGTERM)` 后读 `/proc/self/status`，`SigBlk` 正是 `0000000000004000`。速算：`SIGUSR1`（10）→ 位 9 → `0x200`，`SIGUSR2`（12）→ 位 11 → `0x800`。
:::
:::

### 1.8.4 小结

① 信号的生命周期是产生 → pending → 递送 → 处置，阻塞只是让它在 pending 里等，不是丢掉。② 标准信号不排队，同一信号只记一次；处理 `SIGCHLD` 必须循环回收。③ `pause` 与「检查标志」之间有丢唤醒的空窗，`sigsuspend` 用原子换掩码加睡眠堵住它；handler 里只能调用异步信号安全函数。如果只记住一件事，那就是：**信号可以等，但不能攒；等待要用原子操作，不能用「先检查再睡」。**

::: method 即时自测 · 1.8.4
**Q1（记忆）** 写出信号生命周期的四个阶段，并说明「阻塞」发生在哪两个阶段之间。

**Q2（辨析）** `SigPnd` 与 `SigBlk` 里都出现了 `SIGUSR1` 的位，这说明什么？此时 handler 会执行吗？

**Q3（应用）** `pause` 分支为什么在解除阻塞后仍然睡死？换成 `sigsuspend` 为什么就不会？

**Q4（迁移）** 一个多线程程序在其中一个线程里 `sigprocmask(SIG_BLOCK, ...)`，能保证其他线程也收不到这个信号吗？

::: sol 答案
**A1** 产生、挂起（pending）、递送（delivery）、处置。阻塞发生在产生之后、递送之前：信号可以产生并停在 pending，但不会被递送。
**A2** `SigBlk` 有这一位说明它被阻塞；`SigPnd` 有这一位说明它已经产生、正等待解除阻塞。此时 handler 不会执行，直到掩码改变、内核再次返回用户态。
**A3** 解除阻塞时，pending 的信号已经在 `sigprocmask` 返回前递送并处理完，`got` 已经是 10，`pause` 等的是下一次信号，所以只能睡到 `SIGALRM`。`sigsuspend` 把「换掩码」和「睡眠」做成一个原子操作，pending 信号在睡眠生效的同时递送，不会漏掉唤醒。
**A4** 不能。`sigprocmask` 在 POSIX 多线程程序里行为未规定；应使用 `pthread_sigmask`，它只改当前线程的掩码。进程级信号会被递给任意一个未阻塞它的线程。
:::
:::

## 1.8.5 非本地跳转：setjmp 与 longjmp {#sec-1.8.5}

这一节回答：函数调用只能一层层返回，`longjmp` 凭什么一次跳回三层之前？跳回去时，哪些东西被恢复，哪些被留在半路？

::: preview 先抓住一件事
`setjmp` 保存的不是整份栈，而是「回到这一行所需的寄存器，加上可选的信号掩码」；`longjmp` 恢复这些寄存器，把中间的栈帧直接丢掉。所以它很快，也容易留下烂摊子：锁、堆内存、打开的文件都不会自动回滚。第二参数传 0 会被改成 1；普通 `longjmp` 不恢复信号掩码，`sigsetjmp(env, 1)`/`siglongjmp` 才恢复。
:::

设想一个三层的配置解析器：最里层发现括号不匹配，错误要一路 `return` 三层才到调用者。逐层检查返回值当然可以，但代码会被 `if (ret) return ret;` 填满。`longjmp` 提供另一条路：在顶层记下「回到这里」，出错时一步跳回统一出口。信号处理函数里也能用它从任意位置跳出，代价是掩码与资源要自己收拾。

先跑一个程序。它做三件事：从三层调用深处跳回、观察局部变量的值、观察信号掩码有没有被复原。

```c
/* jmp.c：三层 longjmp 与一次 siglongjmp */
#include <setjmp.h>
#include <signal.h>
#include <stdio.h>

static jmp_buf env;
static sigjmp_buf senv;
static volatile sig_atomic_t hits;

static void level3(void) { longjmp(env, 0); }
static void level2(void) { level3(); }
static void level1(void) { level2(); }

static void on_usr1(int signo)
{
    (void)signo;
    hits++;
    siglongjmp(senv, 1);
}

static void show_blk(const char *tag)
{
    sigset_t cur;
    if (sigprocmask(SIG_SETMASK, NULL, &cur) == -1) { perror("sigprocmask"); return; }
    printf("%s blocked=%d\n", tag, sigismember(&cur, SIGUSR1));
}

int main(void)
{
    volatile int v = 1;
    int plain = 1;
    int r = setjmp(env);
    if (r == 0) {
        v = 7;
        plain = 7;
        level1();
    }
    printf("r=%d v=%d plain=%d\n", r, v, plain);

    struct sigaction sa = { .sa_handler = on_usr1 };
    sigemptyset(&sa.sa_mask);
    if (sigaction(SIGUSR1, &sa, NULL) == -1) { perror("sigaction"); return 1; }

    show_blk("before:");
    if (sigsetjmp(senv, 1) == 0) {
        sigset_t set;
        sigemptyset(&set); sigaddset(&set, SIGUSR1);
        sigprocmask(SIG_BLOCK, &set, NULL);
        show_blk("blocked:");
        raise(SIGUSR1);
        sigprocmask(SIG_UNBLOCK, &set, NULL);
    } else {
        printf("jumped back: hits=%d\n", (int)hits);
        show_blk("after:");
    }
    return 0;
}
```

```text
# 实测（Ubuntu 24.04.5 aarch64，GCC 13.3.0，-O2）
$ cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -o lab1c08_jmp lab1c08_jmp.c
$ ./lab1c08_jmp
r=1 v=7 plain=1
before: blocked=0
blocked: blocked=1
jumped back: hits=1
after: blocked=0
```

第一行先看 `r=1`。`setjmp` 首次返回 0，程序进入 `if`，把 `v`、`plain` 改成 7，再经 `level1`、`level2`、`level3` 三层调用到 `longjmp(env, 0)`。`longjmp` 恢复 `env` 里保存的栈指针和返回地址，`setjmp` 于是第二次返回；尽管第二参数写的是 0，返回值是 1。0 被留给「首次进入」，这是接口的硬规定，不是实现怪癖。

第二行 `v=7 plain=1` 是本节最贵的教训。`v` 是 `volatile int`，跳回后读到新值 7；`plain` 是普通自动变量，同样被赋成 7，却读到 1。原因是优化后的 `plain` 可能只活在寄存器里，而 `longjmp` 恢复的是 `setjmp` 那一刻保存的被调用者保存寄存器，等于把它拨回旧值。C 标准只说：在 `setjmp` 与 `longjmp` 之间被修改、且不是 `volatile` 的自动变量，跳回后的值不确定。这台机器这次给出 1，换个编译器或优化级别可能是 7 或别的值。规则很简单：**跨 `longjmp` 还要读的局部变量，声明成 `volatile`。**

后四行看信号掩码。`sigsetjmp(senv, 1)` 在掩码为空时保存现场；随后阻塞 `SIGUSR1`，查询得到 `blocked=1`；`raise` 让信号 pending，解除阻塞时处理函数执行，`siglongjmp(senv, 1)` 跳回。`siglongjmp` 把掩码恢复成保存时的空集，所以最后一行是 `blocked=0`。若把这两个调用换成普通 `setjmp`/`longjmp`，同一台机器上 `SigBlk` 会停在 `0x200`（第 10 位，`SIGUSR1`）：处理函数执行期间该信号被自动阻塞，跳出时没人替你解除；此后这个进程再也收不到 `SIGUSR1`，直到某处显式解除阻塞。

::: def 定义 1.8.5 · 非本地跳转（nonlocal jump） {#def-1.8.5}
非本地跳转是从当前执行点直接恢复到同一进程、同一线程里某个仍然有效的 `setjmp` 保存点的控制转移。`setjmp` 保存栈指针、返回地址、被调用者保存寄存器和（对 `sigsetjmp`）信号掩码；`longjmp` 恢复这些寄存器，不逐帧返回，因此不执行中间函数的任何清理代码。
:::

`setjmp` 到底存了什么？可以把它想成一次「现场拍照」，拍下的只有回到这一行必需的几样东西：

| 会被 `longjmp` 恢复 | 不会被恢复 |
|:--|:--|
| 栈指针、指令指针（回到 `setjmp` 那一行） | 堆上的内存与它的指针 |
| 被调用者保存寄存器 | 互斥锁、信号量、打开的文件描述符 |
| `sigsetjmp(env, 1)` 保存的信号掩码 | `errno`、`atexit` 登记、C++ 栈展开 |

`jmp_buf` 的内容是实现私有的，标准没规定它长什么样：不要 `memcpy`、不要打印、更不要拿到另一个线程里用。它的有效期只到保存它的那个函数返回为止——函数一返回，栈帧就没了，再 `longjmp` 等于跳到一片已被复用的栈上。

这也解释了代价。`longjmp` 不弹栈、不调用析构、不释放资源，它只把栈指针和指令指针一改。C 里没有析构函数，问题常常藏在别处：跳走时一把互斥锁还锁着，之后没人解锁；一块 `malloc` 出来的内存失去唯一指针；一个临时文件没有 `unlink`；数据库事务停在半路。所以它适合「解析失败、参数非法、深层递归发现错误」这类能立刻回到统一出口的场景，不适合当日常控制流。团队里更常见的替代是 `goto cleanup`：同样跳过多层，但清理标签逐项写明，读代码的人看得见欠了什么。

它和 1.8.8 的硬件异常是两套机制。硬件异常由 CPU 按向量把控制权交给内核，内核再决定返回哪里或发什么信号；`longjmp` 完全在用户态改寄存器，内核毫不知情，也不参与。它不能跨进程，不能跨线程；拿一个线程的 `jmp_buf` 到另一个线程 `longjmp` 是未定义行为。C++ 的 `throw` 会沿栈逐帧查 unwind 表并调用析构，`longjmp` 不会，所以不要用它跨过 C++ 栈帧。完整的错误恢复与超时跳出程序在 1.8.12。

::: errata 关于非本地跳转的四个误解
1. **「`setjmp` 把整个栈复制了一份」**——没有。它只存寄存器和一个掩码；被跳过的栈帧仍在内存里，只是再也不会被返回，局部变量也不会被析构或释放。
2. **「`longjmp(env, 0)` 会让 `setjmp` 返回 0」**——不会，0 被改成 1。用 0 当成功码会和「首次进入」混淆。
3. **「普通 `longjmp` 也会恢复信号掩码」**——不会，只有 `sigsetjmp(env, 非零)`/`siglongjmp` 才保存和恢复；从处理函数跳出时用错，会让被处理的信号永久阻塞。
4. **「`longjmp` 可以跨线程或跨进程」**——都不行。`jmp_buf` 只在保存它的那个线程、那个进程里有意义。
:::

### 小结

① `setjmp` 保存的是「回到这一点」的寄存器现场，`longjmp` 恢复它并丢弃中间栈帧，所以不会执行清理。② 第二参数 0 会被改成 1；跨跳转还要用的局部变量必须 `volatile`。③ 从信号处理函数跳出要用 `sigsetjmp(env, 1)`/`siglongjmp`，否则信号掩码留在阻塞状态。如果只记住一件事，那就是：**`longjmp` 只还你寄存器，不还你锁、内存和文件。**

::: method 即时自测 · 1.8.5
**Q1（记忆）** `setjmp` 保存哪些东西？`longjmp` 的第二参数为 0 时，`setjmp` 返回什么？

**Q2（辨析）** 程序里 `int x = 1;` 在 `setjmp` 后改成 7，`longjmp` 后读到 1。能据此说「`longjmp` 会把变量改回旧值」吗？

**Q3（应用）** 一个函数在 `setjmp` 之后 `malloc` 了一块内存、加了一把锁，然后深层调用里 `longjmp` 回出口。出口需要补哪些动作？

::: sol 答案

**A3** 先解锁，再 `free`，并关闭或删除临时资源；这些清理不会由 `longjmp` 代劳。更稳的写法是把资源放在统一出口，用 `goto cleanup` 逐项释放。

## 1.8.6 作业控制、会话与控制终端 {#sec-1.8.6}

这一节回答：同一条 `Ctrl-Z`，为什么只停住前台那个作业，而后台 `sleep` 照跑？shell 执行 `fg` 时，又凭什么知道该把哪个进程组放回终端？

::: preview 先抓住一件事
作业控制不是 shell 的一个变量，而是内核里的三层对象：进程组（`pgid`）是信号的分发单位，会话（`sid`）把一组进程组绑到一次登录，控制终端在任一时刻只认一个前台进程组（`tpgid`）。`Ctrl-Z` 由终端驱动发出，只送给前台组；`fg` 做两件事——把前台组改回该作业，再发 `SIGCONT`。
:::

先还原一个场景。你在终端里跑 `make`，嫌它慢，按 `Ctrl-Z`：它停住，提示符回来了。你敲 `bg`，它转到后台继续跑；接着敲 `vim`，`vim` 能正常读键盘。这三件事同时成立，说明「谁是前台」不是某个进程自己的属性，而是终端记住的一条记录。谁改这条记录，谁就决定键盘和 `Ctrl-C` 归谁。

三层对象各管一段：

| 概念 | 内核中的字段 | 作用 |
|:--|:--|:--|
| 进程组（process group） | `pgid` | 信号可以发给整组；作业控制的单位 |
| 会话（session） | `sid` | 一组进程组的集合，通常对应一次登录；首进程的 pid 就是 sid |
| 控制终端（controlling terminal） | tty 设备 | 会话与终端绑定；同一时刻只有一个前台组 |
| 前台进程组 | 终端驱动的 `tpgid` | 只有它能读终端、接收 `Ctrl-C` |

::: def 定义 1.8.6 · 进程组、会话与前台组 {#def-1.8.6}
进程组是一组共享同一个 `pgid` 的进程，`kill(-pgid, sig)` 把信号发给整组。会话是一组进程组的集合，首进程（session leader）的 `pid` 就是 `sid`；一个会话最多绑定一个控制终端。终端驱动为它记住一个前台进程组：键盘输入和 `Ctrl-C`、`Ctrl-Z` 只交给这个组，其他组去读终端会被停住。
:::

把这三个字段读出来，比背定义快。下面是一次真实会话（Ubuntu 24.04.5 aarch64）：

<div class="terminal" data-title="bash · ubuntu 24.04">
<pre><span class="p">&#36;</span> sleep 300 &amp;
[1] 489962
<span class="p">&#36;</span> jobs -l
[1]+ 489962 Running                 sleep 300 &amp;
<span class="p">&#36;</span> ps -o pid,ppid,pgid,sid,tpgid,stat,cmd -p &#36;! -p &#36;&#36;
    PID    PPID    PGID     SID   TPGID STAT CMD
 489948  489947  489948  489948  489963 Ss   bash
 489962  489948  489962  489948  489963 S    sleep 300</pre>
</div>

四行字段这样读：`bash` 的 `SID=PGID=489948`，`STAT` 里的 `s` 说明它是会话首进程；后台 `sleep` 被作业控制放进新进程组 `PGID=489962`，但仍在同一会话（`SID=489948`）。最值得看的是 `TPGID=489963`：它既不是 bash 也不是 sleep，而是**正在前台跑的那条 `ps` 自己**的进程组——每敲一条前台命令，shell 就为它开一个新组并设为前台。若终端没有前台组（例如 `ssh 主机 '命令'` 这种不分配终端的通道），`ps` 这一列显示 `-`，内核里的值则是 -1。

前台组会随你的操作变化，变化的过程就是作业控制：

| 你做的事 | 谁发信号 | 结果 |
|:--|:--|:--|
| `Ctrl-C` | 终端驱动 → 前台组 | `SIGINT`，默认终止 |
| `Ctrl-Z` | 终端驱动 → 前台组 | `SIGTSTP`，默认停止（可捕获） |
| `bg %1` | shell | `SIGCONT`，组留在后台，不再有终端读权限 |
| `fg %1` | shell | `tcsetpgrp` 改前台组，再 `SIGCONT` |
| 后台组读终端 | 终端驱动 | `SIGTTIN`，默认停止 |
| 后台组写终端（`stty tostop`） | 终端驱动 | `SIGTTOU`，默认停止 |
| 终端关闭 | 内核 | `SIGHUP` 给会话首进程，通常级联整个会话 |

`Ctrl-Z` 停止的只是前台组，不会误伤后台作业；要停后台作业，用 `kill -TERM %1`；要把整个作业组一起终止，用 `kill -- -489962` 这种「负组号」写法。

::: intuition 为什么后台进程读终端会被「停住」而不是「读不到」
终端是共享的交互设备。多个进程同时读，输入会随机分给其中一个，用户无法预期。内核用前台组把输入独占给一个作业；后台组尝试读时发 `SIGTTIN` 把它停住，等 `fg` 带回前台再继续。这不是权限错误，而是作业控制的流控机制。
:::

两个容易踩的边界。第一，`Ctrl-Z` 发的是 `SIGTSTP`，它可以被捕获或忽略；真正不可阻挡的是 `SIGSTOP`，所以 `kill -STOP` 能停住一个屏蔽了 `SIGTSTP` 的程序。第二，`&` 不等于守护进程：后台作业仍在同一会话、同一终端，终端一关照样收 `SIGHUP`。要脱离，得用 `nohup`、`disown`，或者正规地 `setsid()`——它创建新会话、脱离控制终端，再 `fork` 一次确保自己不是会话首进程，防止重新获得终端。写守护进程还要把 `stdin/stdout/stderr` 重定向到 `/dev/null` 或日志；现代系统更推荐交给 systemd，由它处理日志、重启与依赖。

::: errata 关于作业控制的三个误解
1. **「`Ctrl-Z` 发的是 `SIGSTOP`」**——是 `SIGTSTP`，可以被捕获或忽略；`SIGSTOP` 才是不可捕获、不可阻塞的强制停止。
2. **「后台作业也会收到 `Ctrl-C`」**——不会，`Ctrl-C` 只送前台组；要停后台作业用 `kill -TERM %1`，要连整组一起停用 `kill -- -pgid`。
3. **「命令后面加 `&` 就是守护进程」**——不是。它还在同一会话和控制终端上，终端关闭会收到 `SIGHUP`；守护进程要 `setsid` 并重定向标准流。
:::

### 小结

① 作业控制靠内核的三层对象：进程组是信号分发单位，会话绑定一次登录，控制终端只认一个前台组。② `Ctrl-C`、`Ctrl-Z` 由终端驱动发给前台组，`fg`、`bg` 由 shell 改前台组并补 `SIGCONT`。③ 后台组读终端会被 `SIGTTIN` 停住，这是流控不是权限；`&` 不等于守护进程。如果只记住一件事，那就是：**终端只服务一个前台组，作业控制就是换这个组。**

## 1.8.7 观测异常控制流 {#sec-1.8.7}

这一节回答：程序「莫名其妙退出」「`kill` 了没反应」「留下僵尸」时，你手上哪几条命令能在一分钟内把范围缩到某一步？

::: preview 先抓住一件事
排查异常控制流固定问三件事：谁发的、发给谁、处理了没有。`strace` 看时间线与系统调用，`/proc/<pid>/status` 看信号掩码与 pending，`ps -o ...` 看进程组、会话和前台组。三件工具各看一层，别一上来就猜代码。
:::

先看一个最常见的现场：给服务发了 `SIGTERM`，进程没退。可能的原因只有四条——信号没送到；送到了但被阻塞；handler 跑了但没退出；进程停在不可中断睡眠里，信号要等 I/O。四条路对应四个观测点，按顺序查完，问题就只剩一种。下面的命令与输出都在本章的实测机上跑过，口径写在代码块第一行。

第一组：`strace` 看系统调用与信号。

```bash
strace -f -tt -T -e trace=process,signal ./prog
```

`-f` 跟子进程，`-tt` 打时间戳，`-T` 打每个调用的耗时；`trace=process,signal` 只看进程控制与信号两类，输出不会被 `read`、`write` 淹没。完整的一次 `clone`/`execve`/`wait4`/`--- SIGCHLD ---` 长什么样，1.8.13 已经逐行拆过，这里不重复。你只要记住：`--- SIGxxx ---` 是递送记录，`si_code` 说明来源，`SI_USER` 来自 `kill`，`CLD_EXITED` 来自子进程正常退出。

第二组：`/proc/<pid>/status` 看信号位的真值。下面是在 Ubuntu 24.04.5 的非交互 ssh shell 里读它自己：

```text
# 实测（Ubuntu 24.04.5 aarch64；不同进程的位图不同）
$ grep -E 'SigPnd|ShdPnd|SigBlk|SigIgn|SigCgt' /proc/$$/status
SigPnd: 0000000000000000
ShdPnd: 0000000000000000
SigBlk: 0000000000000000
SigIgn: 0000000000000000
SigCgt: 0000000000000400
```

五个字段的分工：

| 字段 | 含义 |
|:--|:--|
| `SigPnd` | 这个线程自己的 pending 信号 |
| `ShdPnd` | 整个进程共享的 pending 信号 |
| `SigBlk` | 这个线程阻塞的信号 |
| `SigIgn` | 被设为忽略的信号 |
| `SigCgt` | 装了处理函数的信号 |

位图是 64 位十六进制，最低位对应信号 1（`SIGHUP`）。`0x400` 是 2 的 10 次方，即从右往左第 11 位，对应信号 11 `SIGSEGV`——这个 shell 自己装了 `SIGSEGV` 的处理函数。换个 shell、换台机器，位图就会变，所以别背数值，学会换算：把十六进制写成二进制，从右往左数第 n 位为 1，就是信号 n。

第三组：`ps` 看进程关系。

```bash
ps -o pid,ppid,pgid,sid,tpgid,stat,cmd -p $$
ps -eo stat,cmd | grep '^Z'
```

第一行看 `PGID`、`SID`、`TPGID` 三个组号，判断「发给谁」；第二行专门找僵尸（`Z`），看到就去找它的父进程有没有 `wait`。字段读法在 1.8.6 与 1.8.13 都出现过，这里只补一句：`STAT` 里的 `+` 表示在前台进程组，`s` 表示会话首进程。

还有一条零成本的线索：shell 的 `$?`。正常退出是 0–255 的退出码；被信号杀死时是 128 加信号号，所以 139 是 `SIGSEGV`、143 是 `SIGTERM`、137 是 `SIGKILL`。看到 137 先怀疑 `kill -9` 或 OOM killer，看到 143 先怀疑有人发了 `SIGTERM`。注意这是 shell 的编码，不是 `wait` 交回的那个状态字。

core dump 是「事后现场」，但它在这台 VM 上不按教科书的剧本走：

```text
# 实测（Ubuntu 24.04.5 aarch64）
$ ulimit -c
0
$ cat /proc/sys/kernel/core_pattern
|/usr/share/apport/apport -p%p -s%s -c%c -d%d -P%P -u%u -g%g -F%F -- %E
$ dmesg | tail -1
dmesg: read kernel buffer failed: Operation not permitted
$ command -v coredumpctl || echo no-coredumpctl
no-coredumpctl
```

四行各有含义：`ulimit -c 0` 表示当前 shell 不允许写 core 文件；`core_pattern` 以 `|` 开头，表示 core 被管道给 `apport`，不会在当前目录留下 `core`；`dmesg` 被 `kernel.dmesg_restrict=1` 挡住，普通用户读不到内核日志；系统里没有 `coredumpctl`。所以终端上的 `(core dumped)` 只说明「内核尝试过 dump」，不代表磁盘上真有一个 core 文件。

要看崩溃现场，在本 VM 上优先用 `strace -e trace=signal`（1.8.1 的 `SIGSEGV` 就是这么看到的），或让程序自己把关键状态写日志。`gdb` 的 `run` 在这台机器上会因 SVE 寄存器状态报错，本机未实测完整调试流程；有 core 时 `gdb ./prog core` 的 `bt` 仍是标准做法，只是这条路径要换一台普通 x86-64 机器验证。

::: errata 关于「core dumped」的三个误解
1. **「终端说 core dumped，就一定有个 core 文件」**——不一定。`ulimit -c 0`、`core_pattern` 走管道、容器限制，都会让文件不落盘。
2. **「没有 core 就是没崩」**——不是。先看 `strace` 的 `--- SIGSEGV ---` 与退出码 139，再查 `ulimit -c` 和 `core_pattern`。
3. **「`dmesg` 随时能看段错误地址」**——`dmesg_restrict=1` 时普通用户被拒；这时用 `strace` 里的 `si_addr` 代替。
:::

### 小结

① 排查顺序固定：`strace` 看谁在什么时候发了什么，`/proc/<pid>/status` 看信号是 pending、被阻塞还是被捕获，`ps` 看进程组与会话。② `/proc` 的五个 `Sig*` 字段是 64 位十六进制位图，第 n 位对应信号 n，要会现场换算。③ `(core dumped)` 不等于有 core：`ulimit -c`、`core_pattern`、`dmesg_restrict` 三处都能让现场消失。如果只记住一件事，那就是：**先证明信号到没到，再谈代码对不对。**

::: method 即时自测 · 1.8.7

**Q2（应用）** `SigBlk` 是 `0000000000000200`，被阻塞的是哪个信号？

**Q3（辨析）** 程序被 `SIGSEGV` 杀死，终端显示 `(core dumped)`，但当前目录没有 `core` 文件。列出至少两个可能原因。

**A3** `ulimit -c` 为 0；`core_pattern` 以 `|` 开头把 core 管道给别的程序；容器或 systemd 限制了 core；文件写到了别的工作目录。

## 1.8.8 异常的四类与 x86-64 的异常表 {#sec-1.8.8}

这一节回答：缺页、除零、断点、系统调用、时钟中断，在内核看来是不是同一类事件？CPU 把控制权交给内核时，压栈了什么、返回时执行哪条指令？1.8.1 已经从现象讲过一遍，这一遍补硬件细节。

::: preview 先抓住一件事
CPU 不区分「错误」和「正常事件」，它只按向量号跳到内核登记的入口，并在栈上留下「返回到哪条指令」。四类异常的差别就在这个返回地址：中断与陷阱返回下一条，故障重试当前这条，终止不返回。x86-64 用 IDT 装入口、`%cr2` 存缺页地址、错误码的五个位描述「读还是写、用户还是内核、页不存在还是保护违规」；aarch64 换成异常等级、`FAR_EL1` 与 `ESR_EL1`，用户态看到的仍是同一个 `siginfo`。
:::

### 四类异常

| 类别 | 触发方式 | 返回行为 | 例子 |
|:--|:--|:--|:--|
| 中断（interrupt） | 异步，外部设备 | 返回**下一条**指令 | 时钟、网卡、键盘 |
| 陷阱（trap） | 故意，指令 | 返回**下一条**指令 | `syscall`、`int3`、`into` |
| 故障（fault） | 指令执行出错，可能可恢复 | **重新执行当前**指令 | 缺页、`#GP`、`#DE`（除零） |
| 终止（abort） | 不可恢复 | 不返回，终止进程 | 双重故障、机器检查 |

「故障」之所以能恢复，是因为 CPU 在指令**提交之前**报告错误，保存的返回地址指向出错指令本身；内核修好条件（如装入页面）后 `iret` 回去重新执行，指令这次就成功了。缺页处理是「故障」类最典型的应用：一次 `mov` 触发 `#PF`，内核分配物理页、填页表，返回后同一条 `mov` 再执行一遍。故障并非都能修：除零（`#DE`）也归故障，但内核没有「补一个除数」的办法，只能把它翻译成 `SIGFPE` 终止进程。

### x86-64 的向量与错误码

x86-64 有 256 个中断向量，0–31 保留给异常，32–255 给外部中断与系统调用（Linux 用 `0x80` 老式入口，x86-64 用 `syscall` 指令，不走 IDT 的 `int` 门）。常见向量：

| 向量 | 名称 | 类别 | 错误码 | 典型原因 |
|--:|:--|:--|:--|:--|
| 0 | `#DE` | fault | 无 | 除零、`INT_MIN / -1` |
| 3 | `#BP` | trap | 无 | `int3` 断点 |
| 6 | `#UD` | fault | 无 | 非法指令 |
| 8 | `#DF` | abort | 有（0） | 处理异常时又出错 |
| 13 | `#GP` | fault | 有 | 段/权限/非规范地址 |
| 14 | `#PF` | fault | 有 | 缺页、写只读页、保护违规 |
| 17 | `#AC` | fault | 有 | 非对齐访问（开启对齐检查时） |
| 18 | `#MC` | abort | 无 | 机器检查 |

`#PF` 的错误码按位解释：

| 位 | 含义 |
|--:|:--|
| 0 (P) | 0=页不存在，1=保护违规 |
| 1 (W/R) | 0=读，1=写 |
| 2 (U/S) | 0=内核态，1=用户态 |
| 3 (RSVD) | 1=页表项保留位被置位 |
| 4 (I/D) | 1=取指导致 |

出错地址在 `CR2`，错误码在栈上。内核的缺页处理用地址找到对应的 `vm_area_struct`（描述一段合法虚拟内存区间的结构），结局只有三种：

1. 区间存在、权限也对：按需补页——匿名页给一页清零的内存，文件页从磁盘读入，COW 页复制一份；然后 `iret` 回同一条指令重试。1.8.1 说的「补好页表再执行一遍」就是这条。
2. 区间存在但权限不符（写只读页、用户态碰内核页）：修不了，发 `SIGSEGV`，`si_code` 是 `SEGV_ACCERR`。
3. 地址不在任何区间：同样发 `SIGSEGV`，`si_code` 是 `SEGV_MAPERR`。1.8.1 解引用空指针的实测输出正是 `si_code=SEGV_MAPERR, si_addr=NULL`。

所以「缺页」与「段错误」不是一回事：缺页是机制，段错误是第二、三种结局翻译出来的信号。只看 `Segmentation fault` 一行，你分不清「没映射」和「权限不对」；读 `si_code` 就能分开。

aarch64 没有 IDT，也没有 `%cr2`。异常按异常等级（EL0–EL3）和向量表进入；缺页地址在 `FAR_EL1`，原因编码在 `ESR_EL1` 的 ISS 字段（读还是写、翻译还是权限、同权限级还是低权限级）。名字全换了，分工没变：一个寄存器给地址，一个寄存器给原因，内核再翻译成 `siginfo`。本书的实测机就是 aarch64，所以 1.8.1 看到的是 `si_code` 与 `si_addr` 这层统一接口，而不是 x86-64 的错误码。

### 系统调用的入口

`syscall` 指令不是异常，而是**特权级切换指令**：它把 `%rip` 存进 `%rcx`、`%rflags` 存进 `%r11`，跳到 `MSR_LSTAR` 指向的入口（Linux 的 `entry_SYSCALL_64`），并用 `swapgs` 切换内核 GS 基址。参数按 SysV 变体放在 `rdi/rsi/rdx/r10/r8/r9`，编号在 `rax`，返回值在 `rax`。它与函数调用的差别：

| 项目 | 函数调用 | 系统调用 |
|:--|:--|:--|
| 参数寄存器 | rdi,rsi,rdx,rcx,r8,r9 | rdi,rsi,rdx,**r10**,r8,r9 |
| 返回地址 | `call` 压栈 | `syscall` 存 `%rcx` |
| 特权级 | 不变 | 用户 → 内核 |
| 栈 | 用户栈 | 内核栈（`swapgs` 后取） |
| 典型开销 | 几纳秒 | 几十到几百纳秒（含 Spectre 缓解） |

`strace` 之所以能看到参数，是因为它用 `ptrace` 在 `syscall` 入口/出口停下，读寄存器；`perf trace` 则用 tracepoint，开销更小。

::: errata 关于异常表的四个误解
1. **「系统调用一定走 `int 0x80`」**——64 位程序用 `syscall` 指令，`int 0x80` 只留给 32 位兼容路径；两者保存返回地址的位置不同，`syscall` 存 `%rcx`，`int` 压栈。
2. **「缺页就是段错误」**——缺页是故障，多数被内核补页修好；只有修不了才变成 `SIGSEGV`。
3. **「错误码每一位的含义是全局统一的」**——错误码的含义随向量变；`#PF` 的位定义不能套到 `#GP` 上，`#GP` 的错误码只说明「选择子还是外部事件」。
4. **「aarch64 也有 IDT 和 CR2」**——没有。异常入口是向量表，地址与原因分别在 `FAR_EL1`、`ESR_EL1`；别把 x86 术语硬套到 ARM 上。
:::

### 小结

① 四类异常的分水岭是返回地址；缺页属于故障，补好页就重试，修不好才变成 `SIGSEGV`。② x86-64 用 IDT 装向量、`%cr2` 存地址、错误码五位描述「存在、读写、特权级、保留位、取指」。③ `syscall` 是特权级切换而非异常，参数第四位放 `r10`；aarch64 用 `FAR_EL1` 与 `ESR_EL1`，用户态统一看到 `si_code` 与 `si_addr`。如果只记住一件事，那就是：**先看返回地址定类别，再看错误码定原因。**

::: method 即时自测 · 1.8.8
**Q1（记忆）** `#PF` 错误码的第 0、1、2 位各表示什么？

**Q2（应用）** `si_code` 为 `SEGV_MAPERR` 和 `SEGV_ACCERR` 分别对应缺页的哪种结局？

**Q3（迁移）** aarch64 上缺页地址与原因分别在哪两个寄存器？为什么用户态程序通常不用关心这个差别？

::: sol 答案

:::

## 1.8.9 进程控制：fork、exec、wait 的完整语义 {#sec-1.8.9}

这一节回答：`fork` 到底复制什么、共享什么？`execve` 换程序时保留哪几样、重置哪几样？`waitpid` 交回的状态字怎样拆，才不会把退出码读错？

::: preview 先抓住一件事
三条最容易记错的语义：`fork` 复制 fd 表，却让父子指向同一个打开文件描述，偏移因此共享；`execve` 保留 PID、fd 与「被忽略」的信号，重置「被捕获」的处理函数；`waitpid` 交回编码状态字，退出码 7 在里面是 1792。把这三条写成表，fd 泄漏、僵尸和 `EINTR` 重试都能对上号。
:::

1.8.3 用 `forkfd.c` 看过偏移共享：子进程写 `C`、父进程写 `P`，文件成为 `CP23456789`；父进程直接打印状态得到 1792。这里把复制、共享、重置列全，再补 `clone`、subreaper 与等待选项。

### fork 之后：另一份、同一份、空的

读表只问一句：这个对象在子进程里是「另一份」「同一份」还是「空的」？

| 对象 | 子进程里 | 后果 |
|:--|:--|:--|
| 地址空间 | 页表复制，物理页 COW | 写才复制；回指 1.1、1.9 |
| fd 表 | 另一份 | `close` 只减引用计数 |
| 打开文件描述 | 同一份 | 偏移、`O_APPEND` 等状态共享 |
| 信号处置与掩码 | 另一份，内容继承 | 子进程改 handler 不影响父 |
| pending 信号 | 空的 | `raise` 后 `fork`，子进程收不到 |
| `alarm`/定时器 | 清空 | 子进程不继承剩余秒数 |
| `fcntl` 记录锁 | 不继承 | 子进程不持有父的锁 |
| 进程组、会话、`cwd`、`umask`、rlimit | 继承 | 要脱离会话得自己 `setsid` |

「fd 表另一份、打开文件描述同一份」是泄漏与偏移串味的根源。父子各自 `close(fd)` 只把引用计数减一，真正的文件关闭要等最后一个引用；`dup` 出来的 fd 仍指向同一份描述，所以 `dup` 换不来独立偏移，要独立就重新 `open`。打开文件时加 `O_CLOEXEC`，可以让 fd 在 `exec` 时自动关闭，这是防泄漏最省事的一招。

### execve：保留什么、重置什么

`execve` 不创建新进程，它把当前进程的地址空间、寄存器、栈换成新程序，PID 不变。

| 对象 | exec 后 |
|:--|:--|
| PID、PPID、进程组、会话 | 保留 |
| fd | 保留，除 `FD_CLOEXEC` |
| 被忽略的信号（`SIG_IGN`） | 保留 |
| 被捕获的信号处理函数 | 重置为默认 |
| 阻塞掩码、pending 信号 | 保留 |
| `atexit` 登记、stdio 缓冲 | 随地址空间消失 |
| 内存映射、`argv`、`envp` | 全部替换 |
| 备用信号栈 | 关闭 |

「忽略的保留、捕获的重置」有实际后果：父进程把 `SIGHUP` 设为 `SIG_IGN` 再 `exec`，新程序仍忽略（`nohup` 就这么做）；父进程装了自定义 `SIGINT` 处理函数，`exec` 后回到默认，`Ctrl-C` 又能终止它。阻塞掩码会保留，所以 fork 前随手阻塞的信号，可能一路带进新程序。

### waitpid：状态字不是退出码

```text
# 实测（Ubuntu 24.04.5 aarch64）
$ ./lab1c08_forkfd
raw status=1792 WIFEXITED=1 WEXITSTATUS=7
```

1792 是 `0x700`，即 `7 << 8`。低 7 位放终止信号，第 7 位放 core 标志，第 8–15 位放退出码；停止事件另用 `0x7f` 加信号号编码，继续事件是 `0xffff`。所以永远不要直接打印 `status`，要用宏：

| 宏 | 回答什么 |
|:--|:--|
| `WIFEXITED` / `WEXITSTATUS` | 正常退出？退出码是几？ |
| `WIFSIGNALED` / `WTERMSIG` | 被哪个信号杀死？ |
| `WCOREDUMP` | 是否触发了 core |
| `WIFSTOPPED` / `WSTOPSIG` | 被哪个信号停止（要 `WUNTRACED`） |
| `WIFCONTINUED` | 是否恢复（要 `WCONTINUED`） |

`waitpid` 还要处理三种非「等到一个孩子」的返回：`-1` 且 `errno==EINTR` 表示被信号打断，要重试；`-1` 且 `ECHILD` 表示没有可等的子进程；`0` 只在 `WNOHANG` 下出现，表示孩子都还在跑。想一次收干净，用 `while (waitpid(-1, &st, WNOHANG) > 0)`；想只看某个孩子，传它的 pid。`waitid` 多一个 `WNOWAIT`，可以先看状态再决定收不收。

### 僵尸、孤儿与 subreaper

子进程退出后先变成僵尸：地址空间已释放，留下 `task_struct`、退出状态和 PID，等父进程 `wait`。父进程先死，孩子成为孤儿，被 PID 1 或最近的 subreaper 收养。Linux 3.4 起可以用 `prctl(PR_SET_CHILD_SUBREAPER, 1)` 指定一个「二传手」，容器运行时靠它回收孙进程；PID 1 不 `wait`，僵尸就会越积越多。另一种免回收写法是把 `SIGCHLD` 设为 `SIG_IGN` 或加 `SA_NOCLDWAIT`，让内核直接收尸。

`fork` 在 Linux 上就是 `clone(SIGCHLD, 0)`；线程是 `clone` 加上 `CLONE_VM|CLONE_FILES|CLONE_FS|CLONE_SIGHAND|CLONE_THREAD`。`vfork` 是 `CLONE_VM|CLONE_VFORK`，子进程借父进程地址空间并阻塞父进程，只适合立刻 `exec`，不能返回、不能改数据。

::: errata 关于进程控制的四个误解
1. **「`fork` 后偏移独立」**——不独立。共享的是打开文件描述；`dup` 也共享，只有重新 `open` 才独立。
2. **「`exec` 会保留处理函数」**——捕获的重置，忽略的才保留。
3. **「`status` 可以直接当退出码」**——它编码过；7 是 1792，必须用宏拆。
4. **「僵尸占内存」**——地址空间已释放，占的是 PID 与 `task_struct`；多了会耗尽 PID。
:::

### 小结

① `fork` 复制 fd 表但共享打开文件描述，地址空间 COW；pending 信号、定时器、记录锁不继承。② `exec` 保留 PID、fd、忽略的信号与掩码，重置捕获的处理函数。③ `wait` 交回编码状态，退出码 7 是 1792；`EINTR` 要重试，多个孩子要循环收。如果只记住一件事，那就是：**fork 分的是表，不是文件；exec 换的是程序，不是身份；wait 给的是状态，不是退出码。**

## 1.8.10 信号：从产生到递送的完整路径 {#sec-1.8.10}

这一节回答：一个信号从 `kill` 返回到 handler 第一行，内核在中间做了哪几步？为什么 `SIGCHLD` 会合并、`read` 有时重启有时不重启？要把信号接进事件循环，正确姿势是什么？

::: preview 先抓住一件事
信号不是函数调用，而是内核在「返回用户态」的路口插队：先记 pending，再看掩码，未阻塞才在当前线程的用户栈上搭一帧，跳到 handler；handler 返回时走 `rt_sigreturn` 恢复现场。标准信号只有一位、不排队；`SA_RESTART` 只救一部分阻塞调用；handler 里只许调异步信号安全函数，复杂逻辑用 self-pipe 或 `signalfd` 搬回主循环。
:::

1.8.4 讲清了产生、挂起、递送、处置四个阶段，并用 `pause` 与 `sigsuspend` 对比过空窗。这一遍沿着「一次递送」往下走：内核在哪儿停、handler 的栈帧怎么搭、返回时恢复什么，以及这些细节如何决定 `EINTR` 与合并。

### 一次递送的内核路径

把 `kill(pid, SIGUSR1)` 拆成五步：

1. **检查**：发送者能否给目标发信号；`SIGKILL`/`SIGSTOP` 不能被拦截。
2. **记 pending**：进程级信号记在共享位图，线程级（`tgkill`）记在目标线程；标准信号只置一位，实时信号挂到队列并带值。
3. **选线程**：进程级信号挑一个没阻塞它的线程；所有线程都阻塞，就留在共享 pending 里。
4. **返回用户态时递送**：系统调用、中断或异常处理完，内核在返回用户的路径上查 pending 与掩码。
5. **搭帧并跳转**：在用户栈上压入保存的寄存器、`siginfo_t`、`ucontext_t`，把指令指针指向 handler；handler 返回时执行 `rt_sigreturn`，恢复寄存器与掩码。

`si_code` 是这条路径的「寄件人」：`SI_USER` 来自 `kill`，`SI_TKILL` 来自 `tgkill`，`SI_QUEUE` 来自 `sigqueue`，`SI_KERNEL` 来自内核，`CLD_EXITED` 表示子进程正常退出，`SEGV_MAPERR` 表示地址没映射。1.8.1 看到的 `SIGSEGV` 与 1.8.8 的错误码，最后都汇到这一个字段。

1.8.4 的实测可以当作这条路径的刻度：

| 观察 | 实测值（Ubuntu 24.04.5 aarch64） | 对应哪一步 |
|:--|:--|:--|
| `SIGUSR1` 在 `SigPnd`、`SigBlk` 的位 | `0x200`（第 10 位） | 已记 pending，但被阻塞 |
| 阻塞期间 handler 是否执行 | `handler ran=0` | 第 3、4 步都没发生 |
| `pause` 分支退出码 | 142（128+14） | 解除阻塞后信号已用掉，睡到 `SIGALRM` |
| `sigsuspend` 分支退出码 | 0 | 换掩码与睡眠原子，pending 立即递送 |

### 标准信号与实时信号

标准信号 1–31 在 pending 位图里各占一位。同一种信号在未递送期间再来一次，只是把同一位置 1，所以「发 10 个 `SIGUSR1`，handler 跑几次」没有保证；`SIGCHLD` 最容易合并，多个孩子退出可能只唤醒父进程一次。实时信号 `SIGRTMIN`–`SIGRTMAX` 不同：内核用队列保存每一次，带 `sigqueue` 附的值，按编号顺序递送；队列满时 `sigqueue` 返回 `EAGAIN`，用 `kill` 发送的实时信号则可能被直接丢弃。

这条区别直接改写代码：收 `SIGCHLD` 不能「一个信号收一个孩子」，要 `while (waitpid(-1, &st, WNOHANG) > 0)` 把能收的都收掉；需要计数的通知不要用标准信号，改用实时信号、self-pipe 或 `signalfd`。

### sigaction 的七个标志

| 标志 | 作用 | 什么时候用 |
|:--|:--|:--|
| `SA_RESTART` | 自动重启部分被中断的阻塞调用 | 读终端、`wait` 不希望见 `EINTR` |
| `SA_NODEFER` | handler 执行时不禁用该信号本身 | 极少用，容易递归 |
| `SA_RESETHAND` | 进入 handler 后处置重置为默认 | 一次性处理 |
| `SA_SIGINFO` | 用三参数 handler，拿 `siginfo_t` | 要看 `si_code`、`si_addr`、发送者 pid |
| `SA_ONSTACK` | 在 `sigaltstack` 备用栈上执行 | 捕获栈溢出的 `SIGSEGV` |
| `SA_NOCLDSTOP` | 孩子停止/继续时不发 `SIGCHLD` | 作业控制程序 |
| `SA_NOCLDWAIT` | 孩子退出不产生僵尸 | 不关心退出状态的服务 |

### SA_RESTART 的边界

`SA_RESTART` 不是万能开关。Linux 上会被重启的典型调用：慢设备上的 `read`/`write`（终端、管道、socket）、可阻塞的 `open`（FIFO）、`wait`/`waitpid`/`waitid`、`accept`/`connect`、`flock`、`F_SETLKW`、`getrandom`。永远不会重启的：`pause`、`sigsuspend`、`sigwaitinfo`、`poll`/`select`/`epoll_wait`、`nanosleep`/`clock_nanosleep`、带超时的 socket 调用。还有一条更隐蔽：`read` 已经读走部分数据时，即使有 `SA_RESTART` 也返回短读，不会替你补满。

所以正确写法分两层：能重启的调用仍可能因「没有 `SA_RESTART`」「调用本身不可重启」「已经短读」而返回 `EINTR` 或短计数；循环里要判断 `errno==EINTR` 并重试，短读要自己拼够长度。`spawn.c` 的 `waitpid` 循环就是这一层的防御。

### handler 里能做什么

handler 可能在 `malloc` 改堆、`printf` 锁 stdio 的瞬间插进来，因此只能调异步信号安全函数：`write`、`read`、`open`、`close`、`_exit`、`kill`、`sigaction`、`sigprocmask`、`waitpid` 等；`printf`、`malloc`、`free`、`exit`、`strerror` 都不安全。handler 里读写 `errno` 要先存后恢复，别让主程序看到被改过的错误码。

最小写法只有两件事：置 `volatile sig_atomic_t` 标志，或往管道写一个字节。

```c
static int pfd[2];
static void on_sig(int s) { (void)s; char c = 1; write(pfd[1], &c, 1); }
/* 主循环 poll(pfd[0])，醒来后把字节读干 */
```

这就是 self-pipe：handler 只做一次 `write`，主循环用 `poll`/`epoll` 等读端，信号变成普通 fd 事件，和网络 I/O 走同一条路。Linux 还提供 `signalfd`：先把信号在所有线程里阻塞，再 `signalfd` 创建 fd，`read` 出来的是 `signalfd_siginfo`；它同样能塞进 `epoll`，省掉自建管道。

### 信号与线程

进程级信号只保证「递给某个未阻塞它的线程」，不保证是主线程。多线程程序的常见做法是：主线程启动前把所有信号阻塞，再开一个专用线程 `sigwait` 循环取信号；其他线程继承阻塞掩码，专心干活。`pthread_sigmask` 只改当前线程，`sigprocmask` 在多线程程序里行为未定义。要让某个线程收信号，用 `tgkill` 或 `pthread_kill`，别指望 `kill` 能指定线程。

::: errata 关于信号的四个误解
1. **「`signal()` 与 `sigaction()` 等价」**——历史实现里 `signal()` 可能重置处置、可能不重启；统一用 `sigaction` 把行为写进标志。
2. **「信号会排队，来几个跑几次」**——标准信号只保留一位，`SIGCHLD` 尤其会合并；要计数用实时信号或 self-pipe。
3. **「设了 `SA_RESTART` 就不用管 `EINTR`」**——`poll`、`epoll_wait`、`nanosleep`、`pause` 永不重启，短读也不补。
4. **「handler 里可以 `printf` 打日志」**——`printf` 会拿锁、可能 `malloc`；用 `write` 或只置标志。
:::

### 小结

① 递送发生在返回用户态的路口：记 pending、查掩码、选线程、搭帧、跳 handler，返回时 `rt_sigreturn` 恢复现场。② 标准信号一位、实时信号排队；`SIGCHLD` 必须循环收割。③ `SA_RESTART` 只覆盖部分调用，`EINTR` 与短读要自己处理；handler 只做异步信号安全的事，复杂逻辑交给 self-pipe 或 `signalfd`。如果只记住一件事，那就是：**信号是内核在回用户态时插的一帧，不是一次函数调用。**

## 1.8.11 完整程序一：fork/exec/wait 与信号 {#sec-1.8.11}

这一节回答：把 `fork`、`execvp`、`waitpid` 和 `SIGCHLD` 放进同一个程序，哪几行最容易写错？为什么子进程 `exec` 失败要用 `_exit(127)`，而不是 `exit(127)`？程序不长，但每条边界都对应一个真实故障。

::: preview 先抓住一件事
这个「最小 shell」只做四件事：装 `SIGCHLD`/`SIGINT` 处理器，`fork` 后子进程 `execvp`，父进程循环 `waitpid`，最后用状态宏解释结果。四个易错点分别是：`exec` 失败必须 `_exit(127)`；`waitpid` 要防 `EINTR`；`status` 不能直接打印；`SIGCHLD` 会合并，多个孩子要循环收割。
:::

先别看解释，猜两个数：子进程 `exit(7)` 后，父进程打印的 `sigchld_count` 是 0 还是 1？父进程自己的退出码是 7 还是 1？

这个程序小，但每个失败点都会在真实 shell、容器运行时和测试框架里重演：`exec` 失败没退出会跑两套逻辑，`waitpid` 不重试会把 `EINTR` 当错误，状态字读错会把「被信号杀死」报成 0。编译并运行：

```c
/* spawn.c — fork/exec/wait + SIGCHLD + EINTR
 * cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -o lab1c08_spawn spawn.c
 */
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static volatile sig_atomic_t sigchld_count, sigint_count;
static void on_sigchld(int s) { (void)s; sigchld_count++; }
static void on_sigint(int s)  { (void)s; sigint_count++; }

int main(int argc, char **argv)
{
    if (argc < 2) { fprintf(stderr, "usage: %s cmd [args...]\n", argv[0]); return 2; }

    struct sigaction sa = {0};
    sa.sa_handler = on_sigchld;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART | SA_NOCLDSTOP;
    if (sigaction(SIGCHLD, &sa, NULL) < 0) { perror("sigaction SIGCHLD"); return 1; }
    sa.sa_handler = on_sigint;
    sa.sa_flags = SA_RESTART;
    if (sigaction(SIGINT, &sa, NULL) < 0) { perror("sigaction SIGINT"); return 1; }

    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }
    if (pid == 0) {
        execvp(argv[1], &argv[1]);
        fprintf(stderr, "execvp %s: %s\n", argv[1], strerror(errno));
        _exit(127);
    }

    int status = 0;
    pid_t r;
    do { r = waitpid(pid, &status, 0); } while (r < 0 && errno == EINTR);
    if (r < 0) { perror("waitpid"); return 1; }

    if (WIFEXITED(status))
        printf("child %d exited, status=%d\n", (int)pid, WEXITSTATUS(status));
    else if (WIFSIGNALED(status))
        printf("child %d killed by signal %d\n", (int)pid, WTERMSIG(status));
    printf("sigchld_count=%d sigint_count=%d\n", (int)sigchld_count, (int)sigint_count);
    return WIFEXITED(status) ? WEXITSTATUS(status) : 1;
}
```

```text
# 实测（Ubuntu 24.04.5 aarch64；子进程 pid 每次不同）
$ ./lab1c08_spawn /bin/sh -c 'exit 7'
child 495228 exited, status=7
sigchld_count=1 sigint_count=0
$ echo $?
7
$ ./lab1c08_spawn /bin/sh -c 'kill -TERM $$'
child 496134 killed by signal 15
sigchld_count=1 sigint_count=0
$ echo $?
1
```

两个数都答对了吗？`sigchld_count` 是 1：父进程阻塞在 `waitpid` 时，`SIGCHLD` 处于 pending；`waitpid` 返回后、`printf` 之前，内核把信号递送进来。父进程退出码在第一个例子是 7，第二个是 1：子进程被 `SIGTERM` 杀死时，父进程自己没死，只是按约定返回 1。

逐行看四个关键点：

- **`execvp` 失败后 `_exit(127)`**：子进程继承了父进程的 stdio 缓冲，`exit` 会把它再 flush 一遍，可能把父进程没写出的内容重复打印；`_exit` 直接进内核。`perror` 打印的是 `errno` 对应的原因，子进程随后必须结束，不能再往下跑父进程的代码。127 是 shell 约定「命令找不到或无法执行」。
- **`waitpid` 的 `EINTR` 循环**：`SA_RESTART` 通常会让 `waitpid` 自动重启，但不是所有内核与信号组合都如此；写循环不亏。`EINTR` 不是错误，它只说明有信号来过；把它当失败返回，会把正常唤醒变成偶发故障。
- **状态宏二选一**：`WIFEXITED` 与 `WIFSIGNALED` 互斥；`WTERMSIG` 只在被信号杀死时有意义。直接打印 `status` 会得到 1792 这类编码值。`WCOREDUMP` 只说明内核尝试过 dump，不代表磁盘上真有 core 文件。
- **`volatile sig_atomic_t`**：handler 与主流程共享计数，必须保证每次读写都落到内存，且类型是信号安全的。普通 `int` 可能被优化进寄存器，handler 改了主流程也看不见。

`SA_NOCLDSTOP` 让子进程被 `SIGSTOP`/`SIGCONT` 时不产生 `SIGCHLD`，否则作业控制程序会被大量停止事件打扰。`SIGINT` 处理器在这里只计数、不退出：它演示「handler 只做异步信号安全的小事」，真正的退出决策留给主流程；若要转发给子进程，应 `kill(-pgid, SIGINT)` 发整组。

这段程序只等一个已知子进程，所以 `SIGCHLD` 合并不会丢结果。换成服务器就不一样：多个孩子几乎同时退出，内核只保证至少一个 `SIGCHLD` pending，handler 里必须 `while (waitpid(-1, &st, WNOHANG) > 0)` 把能收的都收掉；只调一次 `waitpid` 会留下僵尸。回收时还要分清 `-1` 的两种 `errno`：`EINTR` 重试，`ECHILD` 表示已经没有孩子，可以退出循环。

::: errata 关于这个程序的四个误解
1. **「`exec` 失败后用 `exit(127)` 也一样」**——不一样：`exit` 会 flush 继承来的 stdio 缓冲，可能重复输出；用 `_exit`。
2. **「装了 `SIGCHLD` handler 就不用 `wait`」**——handler 只收到通知，退出状态还要 `waitpid` 取；不取就是僵尸。
3. **「`SA_RESTART` 让 `waitpid` 永不返回 `EINTR`」**——多数情况会重启，但保留重试循环才是可移植写法。
4. **「父进程会把子进程的退出码原样带出去」**——不会自动带；要 `return WEXITSTATUS(status)` 或 `raise(WTERMSIG(status))` 自己传。
:::

### 小结

① `fork` 后子进程 `execvp`，失败只能 `_exit(127)`，不能 `exit`。② 父进程用循环 `waitpid` 防 `EINTR`，用状态宏区分正常退出与信号终止。③ `SIGCHLD` 只负责唤醒，退出状态仍要 `wait`；多个孩子要循环收割，并把 `ECHILD` 当作正常收尾。如果只记住一件事，那就是：**handler 负责「叫醒」，`waitpid` 负责「收尸」，两件事不能互相替代。**

## 1.8.12 完整程序二：setjmp/longjmp 的非局部跳转 {#sec-1.8.12}

这一节回答：`setjmp`/`longjmp` 在真实程序里怎么用，才既能把错误一步送回出口，又不会把信号掩码和资源留在半路？为什么从信号处理函数跳出必须换成 `sigsetjmp`/`siglongjmp`？

::: preview 先抓住一件事
这个程序有两个跳转目标：`err_env` 负责「解析失败回出口」，`alarm_env` 负责「超时从信号处理函数跳出」。要盯住三条规则：`longjmp` 第二参数写 0 会被改成 1；跨跳转还要读的局部变量必须 `volatile`；从 handler 跳出必须用 `sigsetjmp(env, 1)`，否则被处理的信号会留在阻塞状态。
:::

1.8.5 已经用三层调用演示过「跳回」和「掩码没恢复」两个现象。这一节把它们放进一个能编译运行的小程序：解析一个正整数，遇到非法字符就跳回；再用 `alarm` 制造超时，从 `SIGALRM` 处理函数跳回主流程。

```c
/* jmp.c — setjmp 错误恢复 + sigsetjmp 超时跳出
 * cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -o lab1c08_jmp2 jmp.c
 */
#include <setjmp.h>
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

static jmp_buf err_env;
static sigjmp_buf alarm_env;

static void fail(int code) { longjmp(err_env, code); }
static void on_alarm(int s) { (void)s; siglongjmp(alarm_env, 1); }

static int parse_positive(const char *s)
{
    int v = 0;
    if (!s || !*s) fail(1);
    for (const char *p = s; *p; p++) {
        if (*p < '0' || *p > '9') fail(2);
        v = v * 10 + (*p - '0');
    }
    if (v <= 0) fail(3);
    return v;
}

int main(void)
{
    int r = setjmp(err_env);
    if (r == 0) {
        printf("parse=%d\n", parse_positive("123"));
        printf("parse=%d\n", parse_positive("12x"));
        printf("unreachable\n");
    } else {
        printf("recovered from error %d\n", r);
    }

    struct sigaction sa = { .sa_handler = on_alarm };
    sigemptyset(&sa.sa_mask);
    if (sigaction(SIGALRM, &sa, NULL) < 0) { perror("sigaction"); return 1; }

    if (sigsetjmp(alarm_env, 1) == 0) {
        alarm(1);
        printf("waiting for alarm...\n");
        pause();
        printf("not reached\n");
    } else {
        printf("alarm fired, jumped back\n");
    }
    return 0;
}
```

```text
# 实测（Ubuntu 24.04.5 aarch64，GCC 13.3.0，-O2）
$ ./lab1c08_jmp2
parse=123
recovered from error 2
waiting for alarm...
alarm fired, jumped back
```

先看前两行。`setjmp(err_env)` 首次返回 0，进入 `if`；`parse_positive("123")` 正常返回 123。第二个参数 `"12x"` 在字符 `x` 处触发 `fail(2)`，`longjmp` 带着 2 跳回。`setjmp` 第二次返回 2，走 `else` 打印 `recovered from error 2`，`unreachable` 永远不执行。错误码 2 不是「第二个错误」，而是调用方约定的「含非法字符」；`fail` 只管跳，不管解释，解释留在出口。

后两行是超时路径。`sigsetjmp(alarm_env, 1)` 首次返回 0，`alarm(1)` 定一秒后的 `SIGALRM`，`pause()` 睡下；一秒后 handler 执行 `siglongjmp(alarm_env, 1)`，控制流回到 `sigsetjmp` 那一行，这次返回 1，打印 `alarm fired`。整个过程中没有一层层 `return`，中间的 `pause` 栈帧被直接丢掉。

三条规则要落到代码上：

- **第二参数不能为 0**：`setjmp` 用 0 表示「首次进入」，`longjmp(env, 0)` 会被改成 1。错误码从 1 开始编，或像这里用 2、3。
- **跨跳转的局部变量要 `volatile`**：`r` 由 `setjmp` 赋值，安全；如果在 `setjmp` 后改一个普通 `int`，跳回后读到的值不确定。这条在 `-O2` 下最容易翻车。
- **`sigsetjmp(env, 1)` 才保存掩码**：`SIGALRM` 在 handler 执行期间被自动阻塞，普通 `longjmp` 不会解除；用 `siglongjmp` 才会把掩码恢复成进入 handler 前的样子。

`longjmp` 不执行清理：中间栈帧里的 `malloc`、`close`、`pthread_mutex_unlock` 都不会被调用。这个程序故意不持有资源；真实代码要么在出口逐项补，要么改用 `goto cleanup`，让欠账看得见。`jmp_buf` 也不能跨线程、跨进程使用，更不能在保存它的函数返回后再跳。

它和 1.8.8 的硬件异常是两套机制：硬件异常由 CPU 按向量交给内核，内核再翻译成信号；`longjmp` 完全在用户态改寄存器，内核不知情。它快，但只还你寄存器，不还你锁、内存和文件。

::: errata 关于非本地跳转的四个误解
1. **「`longjmp(env, 0)` 能让 `setjmp` 返回 0」**——不能，0 被改成 1；0 专门表示首次进入。
2. **「跳回后所有局部变量都保持原值」**——只有 `volatile` 的保证；普通自动变量可能被优化进寄存器，值不确定。
3. **「`longjmp` 会替中层函数做清理」**——不会；析构、解锁、关文件都要在出口自己补。
4. **「`setjmp` 保存了整份栈」**——只保存寄存器与可选掩码；中层栈帧还在内存里，但再也不会被返回。
:::

::: ex 例 1.8.12 · 先猜 setjmp 的返回值 {#ex-1.8.12}
`jmp_buf env;` 之后执行 `if (setjmp(env) == 0) { longjmp(env, 0); }`。先猜：`longjmp` 的第二个参数传 0，`setjmp` 第二次返回什么？如果传 5 呢？程序会不会无限循环？

::: sol 解答
第二次返回 **1**：标准规定 `longjmp` 的第二参数为 0 时被替换成 1，因为 0 专门表示「首次进入」。传 5 就返回 5。不会无限循环，因为第二次 `setjmp` 的返回值不为 0，`if` 分支不成立；但如果写成 `if (setjmp(env) != 5) longjmp(env, 0);`，就会来回跳直到栈被耗尽——这是把「0 变 1」记反的典型后果。
:::
:::

### 小结

① `setjmp` 记下出口，`longjmp` 带着错误码跳回；第二参数 0 会变成 1。② 跨跳转要读的局部变量加 `volatile`，否则优化后值不确定。③ 从信号处理函数跳出用 `sigsetjmp(env, 1)`/`siglongjmp` 恢复掩码；清理工作不会自动发生，编译器也不会替你检查。如果只记住一件事，那就是：**`longjmp` 只负责改控制流，资源与掩码要你自己收尾。**

## 1.8.13 实验：用 strace、/proc、ps 观测异常控制流 {#sec-1.8.13}

这一节回答：父进程 `fork`、子进程 `exec` 后退出、父进程收到 `SIGCHLD` 再收回状态——这一串在系统调用和内核状态里各留下什么痕迹？三件工具分别该看哪一层？

::: preview 先抓住一件事
`strace` 给你一条按时间排好的系统调用与信号递送记录，`/proc/<pid>/status` 给你此刻的信号掩码、pending 与捕获位，`ps -o ...` 给你进程组、会话和前台组。先确定「看哪一层」，再决定用哪件工具。
:::

观测对象沿用 1.8.11 的 `spawn`：它装 `SIGCHLD` 处理器，`fork` 后让子进程 `exec` 一条命令，父进程 `waitpid` 并把状态打印出来。把 `spawn.c` 编译成 `./spawn`，只跟踪进程与信号两类调用：

```text
# 实测（Ubuntu 24.04.5 aarch64；处理器地址与 pid 每次不同，这里用 0x... 略去）
$ strace -f -e trace=process,signal ./spawn /bin/sh -c 'exit 7'
execve("./spawn", ["./spawn", "/bin/sh", "-c", "exit 7"], 0x... /* 17 vars */) = 0
rt_sigaction(SIGCHLD, {sa_handler=0x...e20, sa_mask=[], sa_flags=SA_RESTART|SA_NOCLDSTOP}, NULL, 8) = 0
rt_sigaction(SIGINT, {sa_handler=0x...e34, sa_mask=[], sa_flags=SA_RESTART}, NULL, 8) = 0
clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD, child_tidptr=0x...) = 495297
strace: Process 495297 attached
[pid 495296] wait4(495297,  <unfinished ...>
[pid 495297] execve("/bin/sh", ["/bin/sh", "-c", "exit 7"], 0x... /* 17 vars */) = 0
[pid 495297] <<< dash 内部另有 6 行 rt_sigaction，已略去 >>>
[pid 495297] exit_group(7)              = ?
<... wait4 resumed>[{WIFEXITED(s) && WEXITSTATUS(s) == 7}], 0, NULL) = 495297
--- SIGCHLD {si_signo=SIGCHLD, si_code=CLD_EXITED, si_pid=495297, si_uid=1000, si_status=7, ...} ---
child 495297 exited, status=7
sigchld_count=1 sigint_count=0
```

最后两行才是程序自己的输出，`<<< ... >>>` 是本书的省略标注，其余是内核或 `strace` 的记录。按五条读：

- `clone(... flags=...SIGCHLD ...) = 495297` 就是 `fork` 的底层调用。`flags` 里没有 `CLONE_VM`，说明复制出的是独立地址空间，不是线程；返回值是父进程看到的子进程 pid。子进程的 `execve` 返回 0，表示 `argv`/`envp` 装载成功；`exit_group(7)` 是它退出，父进程的 `wait4` 收回的正是 495297。
- `strace: Process 495297 attached` 是 `strace` 自己加的一行：`-f` 发现新子进程后自动附着。它后面带 `[pid 495297]` 前缀的行都属于子进程。这行不是系统调用，也不是程序输出，别把它当证据。
- `[pid 495296] wait4(495297,  <unfinished ...>` 与 `<... wait4 resumed>[...] = 495297` 是同一次 `wait4` 被拆成两半。父进程调用时子进程还在跑，`strace -f` 先记「未完成」，等返回再补结果；两半之间夹着子进程的 `execve`/`exit_group`，正说明父子是两个独立执行流。
- `--- SIGCHLD {si_code=CLD_EXITED, si_pid=495297, si_status=7, ...} ---` 是信号递送记录，不是系统调用。`CLD_EXITED` 表示正常退出，`si_pid`/`si_status` 把「谁退出、退出码几」写进了信号本身；若是被信号杀死，这里换成 `CLD_KILLED` 或 `CLD_DUMPED`。`kill` 发来的信号则是 `SI_USER`，`SI_TKILL` 来自 `tgkill`；`si_code` 是判断来源的第一列。
- 子进程 `execve("/bin/sh", ...)` 之后还有 6 行 `rt_sigaction`，那是 `dash` 自己在复位 `SIGINT`/`SIGQUIT`/`SIGTERM`，已略去。`execve` 会保留「被忽略」的处置，但把「已捕获」的处理器重置为默认——这一步常被误读成 `spawn` 的行为。

::: def 定义 1.8.13 · 三层观测面 {#def-1.8.13}
`strace` 记录「谁在什么时刻调用了哪个系统调用、返回值是多少」，是时间线；`/proc/<pid>/status` 记录「此刻信号处于什么状态」，是状态；`ps -o ...` 记录「进程在会话、进程组、终端里的位置」，是关系。排障时三层各看一眼，别用一层解释另一层。
:::

再看向信号状态。下面是在同一台 VM 的非交互 `ssh` 通道里读 `bash -c` 自己：

```text
# 实测（Ubuntu 24.04.5 aarch64；不同进程的位图不同）
$ grep -E 'SigPnd|ShdPnd|SigBlk|SigIgn|SigCgt' /proc/$$/status
SigPnd: 0000000000000000
ShdPnd: 0000000000000000
SigBlk: 0000000000010000
SigIgn: 0000000000000004
SigCgt: 0000000000010002
```

五个字段的分工在 1.8.7 拆过，这里练换算。位图是 64 位十六进制，信号 n 对应从右往左第 n 位。`SigBlk=0x10000` 是 2 的 16 次方，对应信号 17 `SIGCHLD`——这个 shell 在等子进程时把 `SIGCHLD` 阻塞了。`SigCgt=0x10002` 是 2 的 16 次方加 2 的 1 次方，对应 `SIGCHLD` 与 `SIGINT`。`SigIgn=0x4` 是 2 的 2 次方，对应信号 3 `SIGQUIT`，表示被忽略。

`SigPnd` 与 `ShdPnd` 都是 0，只说明采样这一刻没有 pending 信号；信号可能刚被处理完，也可能还没产生。别把「0」当成「从未收到」。同一个程序换一个 shell、换一台机器，位图就会变，所以背数值没有意义，要会现场换算。

最后看进程关系：

```text
# 实测（Ubuntu 24.04.5 aarch64，ssh 命令通道，未分配控制终端）
$ ps -o pid,ppid,pgid,sid,tpgid,stat,comm -p $$
    PID    PPID    PGID     SID   TPGID STAT COMMAND
 200045  200044  200045  200045      -1 Ss   bash
```

`PGID=SID=200045` 说明这个 `bash` 既是进程组组长，也是会话首进程；`PPID=200044` 是它的父进程。`TPGID=-1` 表示没有控制终端——`ssh 主机 '命令'` 默认不分配 pty，只有加 `-t` 才会分配。有的 `ps` 版本把这一列印成 `-`，本机印成 `-1`；两种写法是同一条判读：终端当前没有前台组。`STAT` 里的 `Ss` 拆成两半：`S` 是可中断睡眠，`s` 是会话首进程。若在交互式终端里跑同样的命令，`TPGID` 会是正在前台执行的那条 `ps` 自己的进程组，读法在 1.8.14。

找僵尸用另一条命令：

```bash
ps -eo stat,comm | awk '$1 ~ /^Z/'
```

有输出就说明存在「已退出、父进程还没 `wait`」的进程。先看它的 `PPID`，再查那个父进程为什么没回收；没有 `Z` 行也不代表永远不会有，僵尸只在父进程未回收的窗口里存在。`strace -p` 附着会短暂暂停目标进程；生产环境优先 `perf trace` 或 eBPF。

::: errata 读 strace 的四个误区
1. **「`<unfinished ...>` 和 `resumed` 是两次调用」**——是同一次系统调用被拆成两半，中间插进了子进程的输出。
2. **「`strace: Process N attached` 是程序打印的」**——是 `strace` 的附着提示；`[pid N]` 前缀也是它加的。
3. **「`--- SIGCHLD ---` 是一个系统调用」**——是信号递送记录；`si_code` 才说明来源，`CLD_EXITED` 是正常退出，`CLD_KILLED` 是被信号杀死。
4. **「`execve` 之后子进程的信号处置还是父进程那套」**——被忽略的会保留，被捕获的会复位为默认；`dash` 启动时的 `rt_sigaction` 是它自己在做复位。
:::

### 小结

① `strace -f -e trace=process,signal` 把 `clone`、`execve`、`wait4` 与 `SIGCHLD` 递送排成一条时间线；`<unfinished ...>`/`resumed` 是同一行被拆开，`Process N attached` 只是附着提示。② `/proc/<pid>/status` 的五个 `Sig*` 字段要会按位换算，`SigBlk` 非零是「收不到」的第一嫌疑人。③ `ps -o pid,ppid,pgid,sid,tpgid,stat` 一次给出关系与状态；没有控制终端时 `tpgid` 是 -1，`ps` 可能印成 `-` 或 `-1`。如果只记住一件事，那就是：**先用工具证明信号到没到、子进程有没有退出，再回代码找原因。**

## 1.8.14 作业控制：会话、进程组与控制终端 {#sec-1.8.14}

这一节回答：`sleep 300 &` 之后，内核里多了哪几个对象？`Ctrl-Z`、`fg`、`bg` 各自改了哪个字段、是谁改的？写一个最小 shell 时，`setpgid`、`tcsetpgrp`、`waitpid` 要按什么顺序调用？

::: preview 先抓住一件事
作业控制不是 shell 自己发明的一套状态，而是内核里的三元组：会话（`sid`）、进程组（`pgid`）、控制终端上的前台组（`tpgid`）。shell 只做三件事：给作业建组、把组设成前台、把终端的停止/继续事件翻译成 `SIGCONT` 和作业表。
:::

1.8.6 已经从使用者视角走过一遍；这一节换到内核视角，把同一组数字拆成对象。先看一次真实会话：

```text
# 实测（Ubuntu 24.04.5 aarch64；交互式 bash，有控制终端）
$ sleep 300 &
[1] 489962
$ ps -o pid,ppid,pgid,sid,tpgid,stat,cmd -p $! -p $$
    PID    PPID    PGID     SID   TPGID STAT CMD
 489948  489947  489948  489948  489963 Ss   bash
 489962  489948  489962  489948  489963 S    sleep 300
```

这些字段这样读：

- `bash` 的 `SID=PGID=489948`：它既是会话首进程，也是自己进程组的组长；`PPID=489947` 是启动它的终端或 sshd。
- `sleep` 的 `PGID=489962`：在开启作业控制的交互式 shell 里，`&` 让 shell 为这个作业新建一个进程组，组长就是 `sleep` 自己；它的 `SID` 仍是 489948，说明没有脱离会话。
- `sleep` 的 `PPID=489948`：它仍是 bash 的子进程，作业控制没有改变父子关系。
- `TPGID=489963`：这是终端当前的前台组，既不是 bash 也不是 sleep，而是**正在前台执行的那条 `ps` 自己**。每执行一条前台外部命令，shell 都为它建一个新组并 `tcsetpgrp` 过去。

如果没有控制终端，判读就换一条：`ssh 主机 '命令'` 默认不分配 pty，同一个 `ps` 在没有终端通道时，`TPGID` 一列显示 `-`（本机 procps 印成 `-1`，内核值都是 -1），`STAT` 仍是 `Ss`。这说明会话和进程组还在，只是没有终端可当前台。

::: def 定义 1.8.14 · 三个组号 {#def-1.8.14}
`pid` 标识进程；`pgid` 标识进程组，组内进程共享它，信号可以按组发送；`sid` 标识会话，会话首进程的 pid 就是 sid；`tpgid` 是控制终端记住的前台进程组，没有控制终端时为 -1。`setpgid` 改组，`setsid` 建会话，`tcsetpgrp` 改前台组。
:::

谁在什么时候改这些字段：

| 动作 | 内核里发生什么 | 谁调用 |
|:--|:--|:--|
| `fork` | 子进程继承父进程的 `pgid`/`sid` | 内核 |
| `setpgid(0,0)` | 调用者成为新组的组长 | 子进程自己 |
| `setsid()` | 新建会话与新组，脱离控制终端 | 需要脱离终端的进程 |
| `tcsetpgrp(fd, pgid)` | 终端把前台组改成 `pgid` | shell |
| `Ctrl-C`/`Ctrl-Z` | 终端驱动向前台组发 `SIGINT`/`SIGTSTP` | 内核 |
| 后台组读终端 | 终端驱动发 `SIGTTIN`，默认停止 | 内核 |
| 终端关闭 | 向会话首进程发 `SIGHUP`，通常级联到作业 | 内核 |

`setsid` 有一个前提：调用者不能已经是进程组组长，否则返回 `EPERM`。所以标准的守护进程写法是 `fork` 一次，让子进程调用 `setsid`——子进程继承了父进程的组号，但它不是组长。

写最小 shell 时，顺序比 API 更重要。五步：

1. `fork`。子进程立刻 `setpgid(0, 0)` 建新组，然后 `exec`；父进程也调用 `setpgid(pid, pid)`。两边都调不是多余：子进程可能先 `exec`，父进程也可能先跑，谁先到谁生效，另一次是幂等的。
2. 父进程用 `tcsetpgrp(tty, pid)` 把这个组设成前台。若 shell 自己此刻在后台，这个调用可能触发 `SIGTTOU`；shell 通常在调用前后阻塞或忽略 `SIGTTOU`。
3. `waitpid(pid, &st, WUNTRACED)`。没有 `WUNTRACED`，子进程被 `Ctrl-Z` 停住时 `waitpid` 不会返回，shell 也就无法把作业记进后台表。
4. 子进程结束或再次被停止后，shell 用 `tcsetpgrp(tty, shell_pgid)` 把前台还给自己，再打印提示符。
5. `fg` 先 `tcsetpgrp` 把前台切过去，再 `kill(-pgid, SIGCONT)`；`bg` 只发 `SIGCONT`，不抢终端。

这里有两个容易写错的竞态。第一，`tcsetpgrp` 的目标组必须与调用者在同一会话，且终端必须是该会话的控制终端，否则返回 `ENOTTY` 或 `EPERM`。第二，作业被停止后，如果它所在的进程组变成「孤儿组」——组里有被停止的成员，且没有成员的父亲在同一个会话的另一个组里——内核会向它发 `SIGHUP` 再发 `SIGCONT`。这是终端关闭后后台作业被挂断的底层原因，也是 `nohup`/`setsid` 要解决的问题。

::: errata 关于作业控制的三个误解
1. **「`&` 起的任务已经脱离终端」**——没有。它仍在同一会话、同一控制终端；终端关闭时照样收 `SIGHUP`。要脱离得 `setsid`，或用 `nohup`/`disown` 挡住。
2. **「`Ctrl-Z` 发的是 `SIGSTOP`」**——是 `SIGTSTP`，可以被捕获或忽略；`SIGSTOP` 才不可捕获、不可阻塞。
3. **「`setsid()` 随时能调」**——调用者已是进程组组长时返回 `EPERM`；先 `fork`，让子进程调。
:::

### 小结

① 作业控制的三层是会话、进程组、控制终端前台组；`ps -o pid,ppid,pgid,sid,tpgid,stat` 一次读出它们的关系。② `&` 只新建进程组，不脱离会话；`Ctrl-Z` 由终端驱动发给前台组，`fg`/`bg` 由 shell 改前台组并补 `SIGCONT`。③ 写最小 shell 的顺序是「fork → 两边 setpgid → tcsetpgrp → waitpid(WUNTRACED) → 归还前台」，漏掉任何一步都会出现停不住、收不回或 `fg` 不恢复。如果只记住一件事，那就是：**终端同一时刻只认一个前台组，作业控制就是换这个组。**

::: method 即时自测 · 1.8.14

## 1.8.15 Rust 的进程与信号 {#sec-1.8.15}

这一节回答：Rust 程序创建子进程、等它结束、装信号处理函数时，标准库给到什么、缺什么？这些接口和 C 的 `fork/exec/wait/sigaction` 怎么对应？

::: preview 先抓住一件事
`std::process::Command` 包住「创建 + 等待」，`Child::wait` 会替你重试 `EINTR`；但 Rust 标准库没有信号 API，信号仍要用 `signal_hook`、`nix` 或 `libc` 调 `sigaction`。信号处置是进程全局的，`pre_exec` 里的代码受 fork 安全约束。
:::

先交代口径。写作机（macOS arm64，rustc 1.99.1）有 Rust 工具链，下面的程序与输出在写作机实测；Ubuntu 24.04 的实测 VM 上 `command -v rustc` 为空，Linux 侧未复跑。这套 API 在 Linux 上语义相同，但实现路径会随版本与选项变化，别把 macOS 的具体行为直接当成 Linux 证据。

```rust
// lab1c08_spawn.rs — rustc -O lab1c08_spawn.rs -o lab1c08_spawn_rs && ./lab1c08_spawn_rs
use std::process::Command;

fn main() {
    let status = Command::new("/bin/sh")
        .arg("-c")
        .arg("exit 7")
        .status()
        .expect("spawn failed");
    println!("code={:?} success={}", status.code(), status.success());
}
```

```text
# 实测（写作机 macOS arm64，rustc 1.99.1）
$ ./lab1c08_spawn_rs
code=Some(7) success=false
```

`status()` 等于 `spawn()` 后立刻 `wait()`。`ExitStatus::code()` 返回 `Option<i32>`：正常退出是 `Some(7)`，被信号杀死是 `None`；`success()` 只在退出码为 0 时为真。要拿信号号，用 `std::os::unix::process::ExitStatusExt::signal()`。

`Command::new("/bin/sh")` 不会自动经过 shell：Rust 把第一个参数当可执行文件，后面的 `.arg()` 才是 argv。这里显式写 `/bin/sh -c 'exit 7'`，是因为 `exit` 是 shell 内建；若写 `Command::new("exit")`，会得到 `No such file or directory`。`status()` 返回 `io::Result<ExitStatus>`，`?`/`expect` 处理的是「启动或等待失败」，不是子进程的非零退出——非零退出仍是 `Ok(ExitStatus)`。

需要更细的控制时：`spawn()` 拿 `Child`，`kill()` 发 `SIGKILL`，`try_wait()` 轮询；`signal_hook::iterator::Signals` 适合事件循环，`nix::sys::signal::SigSet` 加 `sigwait` 适合专用信号线程，`signalfd`/`pidfd` 则要落到 `libc`/`rustix`。

标准库不直接暴露 `fork`，因为 fork 后子进程只允许 async-signal-safe 操作，而 Rust 运行时可能已有多线程、分配器和锁；`Command` 把这段危险窗口收进实现里。`Command` 默认让子进程继承三个标准流；要抓输出用 `output()`，要接管道用 `Stdio::piped()`。

| 主题 | C | Rust |
|:--|:--|:--|
| 创建 | `fork` + `exec` | `Command::spawn`/`status`（可能走 `posix_spawn`，也可能 fork+exec） |
| 等待 | `waitpid` | `Child::wait`（内部重试 `EINTR`）；`try_wait` 非阻塞 |
| 状态 | `WIFEXITED`/`WEXITSTATUS`/`WTERMSIG` | `code()`/`success()`/`ExitStatusExt::signal()` |
| 信号 | `sigaction`/`sigprocmask`（线程用 `pthread_sigmask`） | 标准库没有；用 `signal_hook`、`nix` 或 `libc` |
| `fork` 后 | 只许 async-signal-safe | 同样；`pre_exec` 是 `unsafe`，不许分配、加锁、`println!` |

三个容易误解的点：

第一，**信号处理是全局的**。`sigaction` 改的是整个进程的处置，不是某个线程；信号掩码才是每线程一份。`signal_hook::flag::register` 只是把「收到信号」写进一个原子变量，`signal_hook::iterator::Signals` 用自管道把信号转成迭代器，背后仍是 `sigaction`。C 里「handler 只做 `write`/赋值」的规矩，在 Rust 里同样成立。

第二，**`pre_exec` 不是普通闭包**。它在 `fork` 之后、`exec` 之前于子进程里运行，此时只有当前线程，其他线程可能正持有 malloc 锁或 stdio 锁。闭包里 `println!`、`Vec::push`、`Mutex::lock` 都可能死锁；标准库把它标成 `unsafe`，就是在提醒这条约束。能不用就不用。

第三，**别把 PID 当长期句柄**。`Child::id()` 是 `u32`，进程退出后可能被复用；Linux 5.1 起有 `pidfd_send_signal`，5.3 起有 `pidfd_open`，它们用 fd 引用进程，Rust 侧通过 `nix`/`rustix`/`libc` 调用。

::: errata 关于 Rust 进程与信号的三个误解
1. **「Rust 标准库自带信号处理」**——没有。`std` 只管进程创建与等待，信号要引 crate 或自己 FFI。
2. **「`Child::wait` 会被 `EINTR` 打断」**——标准库会重试；但如果你另装了 `SIGCHLD` 处理器并 `waitpid(-1, ...)`，它可能先收走子进程，`Child::wait` 反而得到 `ECHILD`。
3. **「`pre_exec` 里可以随便打印日志」**——不行，那一刻只允许 async-signal-safe 操作。
:::

### 小结

① Rust 用 `Command` 把 `fork/exec/wait` 收成一个类型，`Child::wait` 自动处理 `EINTR`，`ExitStatus` 区分正常退出与信号死亡。② 信号不在标准库里：`signal_hook`/`nix`/`libc` 仍是 `sigaction`，处置全局、掩码每线程。③ `pre_exec` 在 fork 后的子进程里运行，受同样的 fork 安全约束。如果只记住一件事，那就是：**Rust 换的是封装，不是内核语义。**

::: method 即时自测 · 1.8.15
**Q1（记忆）** `ExitStatus::code()` 返回 `None` 说明什么？`success()` 依据什么？

**Q2（辨析）** `signal_hook` 能绕过「handler 里只能调 async-signal-safe 函数」吗？

**Q3（应用）** 用 `pre_exec` 在 `exec` 前关 fd 时，哪些事不能做？

::: sol 答案
**A1** 进程被信号杀死，没有正常退出码；`success()` 只在 `code()==Some(0)` 时为真。
**A2** 不能。它只是把 `sigaction` 包装得更安全；真正的 handler 仍在信号上下文里运行，复杂工作要转交给普通线程或事件循环。
**A3** 不能分配内存、加锁、`println!` 或调用非 async-signal-safe 的库函数；只做 `close`、`dup2` 这类系统调用。

## 1.8.16 十二条异常控制流陷阱 {#sec-1.8.16}

这一节回答：前面各节的机制落到真实代码里，最常以哪十二种方式出错？每条只给三样：看到什么现象、背后是哪条机制、第一步该查什么。

::: preview 先抓住一件事
十二个坑按四组排：异常组看「控制权还回不回得来」，信号组看「信号有没有被正确接住」，进程组看「谁负责回收谁」，作业控制组看「终端把键盘和 `Ctrl-C` 交给了谁」。现象是入口，原因是机制，先查什么是你下一步该敲的命令。
:::

### 异常：控制权还回不回得来

异常组的两条都发生在 CPU 把控制权交给内核之后：故障指令可能被重试，而 `SIGFPE` 这个名字又比它的实际范围窄。

| 现象 | 原因 | 先查什么 |
|:--|:--|:--|
| `SIGSEGV` handler 里 `return` 后同一地址反复出错 | 故障指令会重试，handler 返回就回到原指令 | `strace -e trace=signal` 的 `si_addr` 是否同一个；handler 是否 `siglongjmp`/`_exit` |
| 整数除零收到 `SIGFPE`，误判成浮点问题 | `SIGFPE` 是算术异常统称，整数除零也发它 | `siginfo.si_code` 是 `FPE_INTDIV` 还是 `FPE_FLTDIV`；检查除数与类型 |

### 信号：有没有正确接住

信号组集中在这几件事：信号会打断阻塞调用、标准信号会合并，handler 与主循环之间还要共享状态。先确认信号到没到，再看处理函数。

| 现象 | 原因 | 先查什么 |
|:--|:--|:--|
| `read`/`accept`/`waitpid` 返回 -1，`errno=EINTR`，被当成致命错误 | handler 返回后，慢系统调用被中断 | `errno` 与 `strace` 的 `= -1 EINTR`；循环重试，或 `SA_RESTART`（`epoll_wait`/`nanosleep` 不自动重启） |
| `-O2` 下主循环看不到 handler 改的标志，`-O0` 正常 | 编译器不知道变量会被异步修改，把它缓存在寄存器 | 变量是否 `volatile sig_atomic_t`；对比优化级别与反汇编 |
| 3 个子进程退出只来 1–2 次 `SIGCHLD`，留下 `Z` | 标准信号只有一位 pending，多个事件合并 | `ps -o stat,ppid` 找 `Z`；`/proc/<pid>/status` 的 `SigPnd`/`SigCgt`；handler 里 `while (waitpid(-1, &st, WNOHANG) > 0)` |
| 子进程 stop/continue 也触发 `SIGCHLD`，`waitpid` 被吵醒或误判退出 | 默认 stop/continue 也通知父进程 | `siginfo.si_code` 是 `CLD_STOPPED`/`CLD_CONTINUED`；不需要就加 `SA_NOCLDSTOP`，需要就用 `WUNTRACED`/`WCONTINUED` |

### 进程：谁负责回收谁

进程这一组的三条都关于「父子之间传了什么」：退出状态没人收、fd 表被复制、stdio 缓冲区被复制。先确认谁是父进程、谁该关闭哪个 fd。

| 现象 | 原因 | 先查什么 |
|:--|:--|:--|
| `ps` 里 `Z` 越积越多，或子进程 `PPID` 变成 1 | 父进程不 `wait` 是僵尸；父进程先死，孤儿被 init/subreaper 收养 | `ps -o pid,ppid,stat,cmd` 与 `/proc/<pid>/status` 的 `PPid`；`SIGCHLD` 循环收割、`SA_NOCLDWAIT`、PID 1/subreaper 必须 `wait` |
| `fork` 前打印的日志在输出里出现两遍 | stdio 缓冲区被复制，父子各 flush 一次 | 输出是否在 fork 前未 flush；子进程是否用 `_exit`；fork 前 `fflush(NULL)` |
| 子进程继承了不该有的 fd，管道读端不关闭，EOF 迟迟不来 | `fork` 复制 fd 表，`exec` 默认保留 | `ls -l /proc/<pid>/fd`、`lsof -p`；打开时加 `O_CLOEXEC`，必要时 `close_range` |

### 作业控制：终端把前台交给了谁

作业控制这一组的三条都关于「会话与前台组」：停和继续要改同一个组，后台任务没有脱离会话，`setsid` 又要求调用者不是组长。

| 现象 | 原因 | 先查什么 |
|:--|:--|:--|
| `Ctrl-Z` 后 `fg` 不恢复，或后台进程 `STAT=T` | 前台组没设回；后台组读终端收 `SIGTTIN` | `ps -o pid,pgid,tpgid,stat`、`jobs -l`；先 `tcsetpgrp` 再 `SIGCONT`，shell 退出前恢复自己的前台组 |
| `setsid()` 返回 -1/`EPERM` | 调用者已经是进程组组长 | `getpid()` 是否等于 `getpgrp()`；先 `fork`，让子进程调用 |
| 关终端后 `&` 起的任务消失 | 同会话、控制终端关闭发 `SIGHUP` | `ps -o sid,tpgid,stat`、是否 `nohup`/`disown`；`setsid`/`nohup`/systemd，并重定向标准流 |

::: errata 三条被说反的结论
1. **「`volatile sig_atomic_t` 能保证原子性」**——只保证每次读写可见、单次读写不撕裂；`flag++` 仍是读改写三步，跨线程要用原子类型。
2. **「孤儿进程就是僵尸」**——孤儿还活着，只是被 init/subreaper 收养；僵尸是已经退出、还没被回收。
3. **「`SA_RESTART` 能让所有系统调用自动重启」**——只对一部分调用有效；`epoll_wait`、`nanosleep`、`signalfd` 等仍需自己处理 `EINTR`。
:::

### 小结

① 四组陷阱各自对应一条所有权：异常对应「控制权」、信号对应「处置与掩码」、进程对应「子进程的回收权」、作业控制对应「终端的前台组」。② 排障顺序永远是先查现象对应的那一层：`strace` 看调用，`/proc` 看掩码与 pending，`ps` 看关系与状态。③ 多数修法只有一两行：循环 `waitpid`、`volatile sig_atomic_t`、`EINTR` 重试、`SA_NOCLDSTOP`、`O_CLOEXEC`。如果只记住一件事，那就是：**先找所有权，再改代码。**

**Q2（应用）** `read` 返回 -1 且 `errno=EINTR`，你的下一步是什么？

**Q3（分析）** `ps` 看到状态 `Z`、`PPID=1`，说明什么？为什么它可能一直不消失？

::: sol 答案
**A1** 用 `while (waitpid(-1, &st, WNOHANG) > 0) {}` 把所有已退出的子进程一次收干净，不能只 `waitpid` 一次。
**A2** 先确认 `errno` 与 `strace` 里的 `EINTR`，再决定重试或给 `sigaction` 加 `SA_RESTART`；`epoll_wait`/`nanosleep` 这类调用仍要自己重试。
**A3** 子进程已退出但没被回收，父进程已死，它被 PID 1 或 subreaper 收养；如果收养者不 `wait`（常见于不收割的容器 PID 1），`Z` 就会一直留着。

## 1.8.17 本章小结 {#sec-1.8.17}

这一节回答：这一章学完，一个正在跑的程序被「打断」时，你能不能说清是谁打断的、内核做了什么、进程接下来从哪条路继续？

::: preview 先抓住一件事
判据是：**给你一个「程序莫名退出」「子进程变僵尸」「Ctrl-C 没反应」「日志一半没了」的现场，你能先分清是异常、信号、退出状态还是作业控制的问题，再挑一条命令去证实。**
:::

这一章的主线是**程序不按顺序走的那几条路**。1.8.1–1.8.4 立概念：异常是 CPU 与内核的交接点（中断、陷阱、故障、终止四类），进程是异常控制流的容器（`fork`/`exec`/`wait` 的边界），信号是异步的软件中断（产生、阻塞、递送三段）。1.8.5–1.8.8 补第一遍的边角：`setjmp`/`longjmp` 的非本地跳转、作业控制与会话、用什么工具观测、以及 x86-64 的异常表。

1.8.9–1.8.12 是二刷与完整程序：`fork`/`exec`/`wait` 的完整语义（含 `EINTR` 重试、退出状态宏、`SA_NOCLDSTOP`）、信号从产生到递送的完整路径（`SigPnd`/`ShdPnd`/`SigBlk`、`sigsuspend` 与 `pause` 的差别）、`spawn.c` 与 `setjmp/longjmp` 两个可运行程序。1.8.13–1.8.16 全部落在真实现场：`strace -f -e trace=process,signal` 里 `clone`、`wait4 <unfinished ...>` 与 `SIGCHLD si_code=CLD_EXITED` 的读法；作业控制真会话里 `SID=PGID=489948`、`TPGID=489963` 的含义与「无终端时显示 `-`」；Rust 的进程与信号对照；最后把十二条陷阱归到「异常 / 信号 / 进程 / 作业控制」四组。

逐条打勾的达标表在[学习目标自检表](ch08-checklist.md)。这里只留判据：

- **能解释**：`SIGCHLD` 为什么不排队、僵尸与孤儿的区别、`volatile sig_atomic_t` 保证了什么又没保证什么、`EINTR` 与 `SA_RESTART` 的关系、`Ctrl-C` 打到的是哪个进程组。
- **能操作**：用 `fork`+`execvp`+`waitpid` 写一个最小 shell 并处理 `EINTR`；用 `sigaction` 装处理器并读 `si_code`；用 `ps -o pid,ppid,pgid,sid,tpgid,stat` 读作业控制字段；用 `strace -f` 看进程与信号的时间线。
- **能判断**：一个「莫名退出」是异常、信号还是正常退出（`$?` 与 `si_code`）；`Ctrl-C` 没反应时先查前台组还是先查处理器；`wait` 返回 -1 时先分清 `ECHILD` 与 `EINTR`。

如果只记住一件事，那就是**异常控制流是「状态机 + 交接」**：异常把控制权交给内核，内核要么修好（缺页）、要么转成信号、要么终止进程；信号又把控制权交给用户态处理器或默认动作——把这条链上的每一环都说清，现场就不再神秘。

2. **gdb `run` 在本机不可用**：15.1 版因 SVE 相关错误直接退出，只用静态 `disassemble`；单步观测改用程序内探针。

::: method 即时自测 · 1.8
**Q1（记忆）** 异常分哪四类？缺页、除零、`int3` 断点、`SIGKILL` 各属于哪一类（或由哪一类产生）？

**Q2（判断）** 父进程装了 `SIGCHLD` 处理器却从不 `waitpid`。子进程退出后它会一直是什么状态？`ps` 的 `STAT` 显示什么？如何避免？

**Q3（实验）** `spawn /bin/sh -c 'exit 7'` 与 `spawn /bin/sh -c 'kill -TERM $$'` 两次运行的退出码分别是多少？为什么第二个不是 15？

**Q4（判断）** 在前台运行 `./server`，按 `Ctrl-C` 无反应；`Ctrl-Z` 后 `bg` 也无效。列出两条最可能的原因与各自的验证命令。

::: sol 答案
**A1** 中断（异步，来自设备）、陷阱（有意的，如 `int3` 与系统调用）、故障（可修复，如缺页）、终止（不可恢复，如除零、非法指令）。缺页是故障、除零是终止、`int3` 是陷阱；`SIGKILL` 不是异常，是内核直接终止进程的信号。

**A2** 子进程变成僵尸（`Z`），`ps` 的 `STAT` 显示 `Z` 或 `Z+`，且 `RSS` 为 0 但 PCB 仍在。避免方式：在 `SIGCHLD` 处理器里 `while (waitpid(-1, NULL, WNOHANG) > 0);` 收割，或用 `signalfd`/`SIG_IGN`（`SIG_IGN` 会让子进程自动回收，但拿不到退出状态）。

**A3** 第一个退出码 7（`WIFEXITED` 为真，`WEXITSTATUS=7`）；第二个退出码 1——`spawn` 自己没有被信号杀死，它只是把「子进程被 15 号信号杀死」报告出来，然后按约定返回 1（若想原样传递，`raise(WTERMSIG(status))`）。

**A4** ① 前台进程组不对：`Ctrl-C` 打的是终端的前台组，若 `server` 在后台组（`TPGID` 不是它的 `PGID`），信号根本发不到它——`ps -o pid,pgid,tpgid,stat,cmd` 对照；② 处理器或屏蔽：`server` 装了忽略 `SIGINT` 的处理器，或 `SigBlk` 里屏蔽了 `SIGINT`——`cat /proc/<pid>/status | grep -E 'SigBlk|SigIgn|SigCgt'` 看那一位。
