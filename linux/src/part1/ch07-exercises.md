# 1.7 习题集

三组分层：A 组概念判断（口答即可）、B 组诊断推理（给真实报错形态，写出定位步骤）、C 组动手实验（全部能在一台 Linux 上免 root 复现，见[实验环境](../env.md)）。**全部附解答**；先独立完成，再展开对照。

## 怎么用

1. 先读题，不看解答，给自己 2–3 分钟找思路；
2. 卡住了，回到对应小节的「即时自测」重读，不要直接看答案；
3. B 组的每题都要写成「发生在哪一层 → 先跑哪条命令 → 看到什么算确认 → 改哪一处」四段，少一段就是没定位完；
4. C 组在自己机器上做，别抄别人的读数；本书的实测机是 Ubuntu 24.04（aarch64），x86-64 上的默认加固项与符号版本可能不同，差异见[勘误与版本注记](ch07-errata.md)。

## A 组 · 概念判断

::: ex 例 1.7-A1 · 三个失败发生在哪一层 {#ex-1.7-A1}

「`gcc` 报的错、`ld` 报的错、程序启动时报的错」分别对应流水线上的哪一步？各举一个正文里出现过的错误文本，并说出判断依据。为什么「函数声明了却没定义」编译器不管？

::: sol 解答

编译器管单个 `.c` 内部：语法、类型、这个名字声明过没有，它只看当前翻译单元，所以「只声明不定义」它照编不误，`.o` 里留一条 `UND` 符号加一条重定位项。链接器管跨文件：符号解析失败报 `undefined reference to 'foo'`，两处强定义同名报 `multiple definition`，地址放不进字段报 `relocation truncated to fit`。加载期由内核与 `ld.so` 管：`error while loading shared libraries` 与 `cannot open shared object file` 说明文件本身能执行、但依赖找不到；`symbol lookup error: undefined symbol` 则是库找到了、符号或版本没找到。判断依据就是错误里出现的主体名字：点的是 `.o` 或库成员，是链接期；点的是 `.so` 路径或版本标签，是加载期。

:::
:::

::: ex 例 1.7-A2 · `-lfoo` 会搜磁盘吗 {#ex-1.7-A2}

下面三句话各判断对错并给出理由：① `-lfoo` 会在磁盘上搜索 `libfoo.so`；② `LD_LIBRARY_PATH` 一定优先于其他设置；③ `ldd` 只是读文件，安全。

::: sol 解答

① 错。链接期的 `-lfoo` 只在 `-L` 指定目录与默认库目录里找 `libfoo.so`/`libfoo.a`，跟运行期的加载器搜索是两套东西。② 错。当被搜索的库带 `DT_RPATH` 且没有 `DT_RUNPATH` 时，`RPATH` 先于环境变量；setuid/setgid 程序进入安全执行模式，`LD_LIBRARY_PATH` 直接被忽略（Kerrisk 第 41 章与 42.5 节的口径，正文 1.7.6 的搜索顺序也写明了这一点）。③ 错。`ldd` 会启动动态链接器去解析依赖，对不可信二进制不安全；只读检查用 `objdump -p` 看 `NEEDED`，或用 `readelf -d`。

:::
:::

::: ex 例 1.7-A3 · 两个 `int counter;` {#ex-1.7-A3}

两个 `.c` 各写一句 `int counter;`，别的文件用 `extern` 引用。在一台 GCC 13 的机器上报 `multiple definition`，在一台 GCC 9 的机器上不报。给出解释、恢复旧行为的选项，以及正确写法。为什么「判断依据不是语言标准」？

::: sol 解答

GCC 10 起默认 `-fno-common`：未初始化的全局变量被放进 `.bss` 并当作强符号，于是两处 `counter` 都是强定义，链接器按规则报错。GCC 9 及更早默认 `-fcommon`，两者合并成一个 `COMMON` 符号，静默通过；如果两个文件对它的类型理解不同（一个当 `int`、一个当 `double`），运行时读到的是错值。恢复旧行为加 `-fcommon`，但正确做法是定义只放在一个 `.c`，其他文件用 `extern int counter;` 声明，头文件里绝不写定义。说「依据不是语言标准」，是因为 `tentative definition` 的合并本就是传统实现行为，同一份源码报不报错取决于编译选项与编译器版本。

:::
:::

::: ex 例 1.7-A4 · 弱符号的三个说法 {#ex-1.7-A4}

逐条判断：① 弱符号就是可以被覆盖的符号；② 弱符号没定义时链接会失败；③ 两个弱定义同名时先出现的那个赢。哪几条错？给出「可选钩子」的正确写法与理由。

::: sol 解答

① 不完整、② 错、③ 错。只有**强定义**能覆盖弱定义，两个弱定义谁赢取决于链接顺序，不可依赖；未解析的弱符号不会导致链接失败，地址被解析为 0（或在 GOT 里填 0）。所以可选钩子要写成：库里 `extern void my_hook(void) __attribute__((weak));`，调用前 `if (my_hook) my_hook();`——不判空就可能跳到 0 地址。同一机制也用来做「库给弱默认实现、应用用强定义覆盖」，正文 1.7.3 的 `plugin_init` 就是这个例子。

:::
:::

::: ex 例 1.7-A5 · 归档与共享库的装载方式 {#ex-1.7-A5}

为什么 `.a` 里的符号有时「明明在库里却找不到」，而 `.so` 不会？`--whole-archive`、`--start-group`、`--as-needed` 分别针对什么问题？为什么注册表式插件经常必须 `--whole-archive`？

::: sol 解答

`.a` 是一组 `.o` 的归档，链接器按命令行从左到右扫一遍，只抽取「能解决当前未定义符号」的成员；如果引用还没出现时那个成员已经被扫过，它就不会被第二次捞起，于是报未定义。共享库不这么做：链接期只记录 soname（`NEEDED`），符号在运行期由 `ld.so` 解析，因此不存在「抽不出来」。`--start-group`/`--end-group` 让组内库被反复扫描，解决循环依赖；`--whole-archive` 强制装入所有成员，解决「成员只是靠构造函数注册、没有任何引用指向它」的插件表——这类成员在按需抽取下会整块被丢掉，链接期不报错、运行时注册表为空；`--as-needed` 是发行版默认，只保留真正被用到的依赖，插件靠 `DT_NEEDED` 触发初始化时要 `--no-as-needed` 保住它。

:::
:::

::: ex 例 1.7-A6 · PLT 与 GOT 的两条路径 {#ex-1.7-A6}

画出（用文字讲也行）`call puts@plt` 首次执行与第二次执行各自经过哪些地址。`-z now` 与 `-z relro` 各改变什么？为什么说延迟绑定的代价「不可预测」？

::: sol 解答

桩的第一条是 `jmp *GOT[n]`。首次执行时 `GOT[n]` 还指向桩内的下一条（`push 索引; jmp plt0`），于是跳进 PLT 公共解析头，把 `link_map` 与重定位索引交给 `ld.so` 的解析器；解析器找到 `puts` 的真实地址，**改写 `GOT[n]`**，再跳过去。第二次起 `jmp *GOT[n]` 直接落到 `puts`，只剩一次间接跳转。`-z now` 让所有 `JUMP_SLOT` 在加载时一次解析完（`BIND_NOW`），第一次调用的额外成本消失、启动变慢；`-z relro` 让 GOT 中不需要延迟绑定的部分在重定位结束后变只读，与 `-z now` 合用是 full RELRO，减小 GOT 覆盖的劫持面。说代价不可预测，是因为解析发生在业务路径上、耗时取决于当时库的搜索与符号表规模，第一个调用点会显著慢于后续，且 GOT 必须可写。

:::
:::

::: ex 例 1.7-A7 · PIC 到底「无关」在哪 {#ex-1.7-A7}

「位置无关代码就是没有绝对地址」这句话准确吗？`-fPIC` 与 `-fPIE` 都生成 `ET_DYN`，为什么共享库不能直接用 `-fPIE` 编？如果一段代码里混进一个非 PIC 目标文件，会看到什么错？

::: sol 解答

方向对但不完整：PIC 的约束是**代码段里不出现需要链接期确定的绝对地址**，代价是跨模块的数据与外部函数地址要绕一圈——模块内用 PC 相对（`lea sym(%rip)`），跨模块经 `.got`。共享库要用 `-fPIC`，因为它必须假定自己可能被别的模块插入同名符号，外部数据与函数一律走 GOT；`-fPIE` 编可执行文件时可以假定「本可执行文件不会被插入同名符号」，从而少绕一些，这正是 PIE 相对 PIC 多出来的优化空间，所以共享库不能拿 `-fPIE` 的产物去当库用。混入非 PIC 目标文件时，链接器要为它生成绝对地址型重定位（如 `R_X86_64_32S`），现代默认 PIE 下常报 `relocation truncated to fit` 或类型不匹配；要么用 `-fPIC` 重编那个对象，要么显式 `-no-pie` 并接受固定基址。

:::
:::

::: ex 例 1.7-A8 · 打桩、`eBPF`、`ptrace` 的分工 {#ex-1.7-A8}

要统计一个第三方二进制里每次 `malloc` 的大小，四种手段（编译期宏、`--wrap`、`LD_PRELOAD`、`ptrace`/eBPF）哪些能用？各受什么限制？

::: sol 解答

前两种出局：编译期宏与 `-Wl,--wrap` 都需要重新链接，而目标是别人的成品二进制；`--wrap` 即便重编也只能覆盖当前链接单元里对该符号的**未定义引用**，管不到共享库内部已经绑好的调用，也管不到被内联掉的调用。`LD_PRELOAD` 可用：它让钩子库先加载，同名的动态符号解析到钩子，再用 `dlsym(RTLD_NEXT, "malloc")` 调真实现；限制是三类——目标必须是动态链接（静态链接的程序没有 `ld.so` 参与，预加载不发生），libc 内部自用的调用可能走 `__libc_malloc` 之类的内部入口而绕过可抢占符号，被内联或优化掉的调用根本不存在。要连内部路径和参数一起看，就用 `ptrace` 或 eBPF（用户态静态/动态探针），它们的长处是不改任何链接关系，代价是需要特权或 `CAP_BPF`/`CAP_PERFMON`，且开销与观测粒度不同。展开见 [1.7.8](ch07.md#sec-1.7.8) 的分工表与 [1.7.13](ch07.md#sec-1.7.13) 的完整程序。

:::
:::

## B 组 · 诊断推理

::: ex 例 1.7-B1 · undefined reference to 'foo' {#ex-1.7-B1}

一个项目里 `libfoo.a` 明确含有 `foo`，构建却报 `undefined reference to 'foo'`，报错文本点名的是 `bar.o` 里那一处调用。写出四种可能原因和区分它们的命令，按最快排除的排序。

::: sol B1 核对

① 库根本没进命令行（或被 `--as-needed` 判定未使用而丢掉）：跑 `cc -v`，在真实传给 `ld` 的参数里找 `-lfoo`。② 顺序不对：归档从左到右只扫一遍，`foo` 依赖 `bar` 时 `-lbar -lfoo` 会把 `bar.o` 抽进来后不再回头看 `libfoo.a`；判据是报错点名的文件是不是**库成员**而不是你自己的 `.o`——是库成员就说明它被抽进来了、缺的是它自己的依赖，把两个库调换顺序或加 `-Wl,--start-group`/`--end-group` 试一次即可确认。③ 符号在另一个成员里、那个成员没有任何引用指向它（注册表式）：用 `nm --defined-only libfoo.a` 看哪个成员含 `foo`，再决定 `--whole-archive`。④ 名字对不上：C++ 修饰或 `extern "C"` 缺失，`nm -C` 与 `nm` 两种读法对比；如果报的是 `undefined symbol: _ZN3foo...`，就是修饰问题而不是顺序问题。四条排查全走的是符号与命令行，不要去改代码里的声明。

:::
:::

::: ex 例 1.7-B2 · multiple definition of 'counter' {#ex-1.7-B2}

CI 上突然冒出 `multiple definition of 'counter'`，报错位置写作 `.bss` 的某个偏移；本地一台老编译机上一直好好的。给出根因判断、两条修法，以及为什么「先别去加 `static`」。

::: sol B2 核对

两处都是强定义才会报错，而报错落在 `.bss` 说明冲突源是**未初始化的全局变量**，也就是 `int counter;` 这类 `tentative definition`：新编译机默认 `-fno-common`（GCC 10 起），老机器默认 `-fcommon`，于是同一份代码一边静默合并、一边报错。正确修法是把唯一定义收进一个 `.c`，其余文件用 `extern` 声明；确实需要各自一份时才加 `static`，但那是语义变更而不是修错——它会切断跨文件共享，本来靠合并工作的那份状态会凭空分裂，属于把编译错误改成了逻辑错误。临时救 CI 可以用 `-fcommon`，但要写清是过渡，因为它把两个文件对同一符号的类型理解不一致这种更糟的错误又藏回去了。确认根因只花一条命令：分别 `nm` 两个 `.o`，看 `counter` 是 `B`（`.bss`，强）还是 `C`（common）。

:::
:::

::: ex 例 1.7-B3 · version 'GLIBC_2.xx' not found {#ex-1.7-B3}

自己构建的二进制在另一台机器上启动报 `version 'GLIBC_2.xx' not found (required by ...)`。有人说「再装一个更新版本的 glibc 就行了」。你怎么判断问题、给出三条出路，并解释为什么这条错误和「找不到库」不是一回事？

::: sol B3 核对

先分清层次：`cannot open shared object file` 是**文件找不到**（搜索路径问题），而 `version ... not found` 说明库文件已经找到、但它没有你要的那个**符号版本标签**——这是符号解析层的问题，与路径无关。判断：用 `readelf -V` 或 `objdump -p` 看本程序需要的版本节点，再对目标机上那份库看它导出的版本集合，两边一比就知道缺哪个标签；配合 `nm -D` 看具体是哪个符号带这个版本。根因几乎总是「构建机的 glibc 比目标机新」：新库里的函数带更新的默认版本，二进制就把它写进了需求表。三条出路按优先级：① 在与目标机同版本（或更旧）的系统/容器里构建，这是最省事的；② 降低对较新接口的依赖，或给个别符号用版本脚本/`dlvsym` 显式取旧版本实现；③ 静态链接绕开运行期库，但要清楚它绕不开内核 ABI，且 glibc 的 NSS、`dlopen`、locale 在纯静态下行为受限（正文 1.7.7 的误解第 5 条），不该当默认方案。给旧系统装新 glibc 属高风险操作，不是这条错误的修法。

:::
:::

::: ex 例 1.7-B4 · cannot open shared object file {#ex-1.7-B4}

部署后启动报 `error while loading shared libraries: libfoo.so.1: cannot open shared object file: No such file or directory`，退出码 127。按正文 1.7.8 的取证顺序写出五步，并解释一个常见现象：明明 `-Wl,-rpath,'$ORIGIN/../lib'` 已经设了，间接依赖仍然找不到。

::: sol B4 核对

五步：① `readelf -d` 确认 `NEEDED` 里的 soname（注意加载器找的是 `libfoo.so.1` 这种 soname，不是你链接时写的 `libfoo.so`）；② `objdump -p` 看有没有 `RPATH`/`RUNPATH`、内容是不是可解析的路径（`$ORIGIN` 只有在运行期由加载器展开，写进配置或被打进别的目录就失效）；③ `LD_DEBUG=libs ./prog` 看它实际搜过哪些目录——这一步直接把「路径没到」与「到了但文件不可读/权限不对」分开；④ `ldconfig -p` 确认系统缓存里有没有（这一步涉及只读查询，不需要 root）；⑤ 最后才怀疑 `LD_LIBRARY_PATH`、文件权限或符号链接断掉。间接依赖那段：新链接器默认生成 `DT_RUNPATH`，而 `RUNPATH` **只作用于本对象的直接依赖**，不会传递给依赖的依赖；`DT_RPATH` 才有传递性，但它已被视为过时并默认不生成。所以给主程序设一个 `$ORIGIN/../lib` 只能救它自己的 `NEEDED`，间接依赖要找不到的话要给每个相关库各自设 rpath，或把目录写进 `LD_LIBRARY_PATH`（安全执行模式下会被忽略）。

:::
:::

::: ex 例 1.7-B5 · DSO missing required algorithm {#ex-1.7-B5}

某程序启动时报 `DSO missing required algorithm`（密码库在运行时加载自己的模块时给出的错误）。有人说「这是 glibc 少了」。你同不同意？给出与 B4 共用的判据，并说明这类错误比 B4 多出来的那一层「程序自己决定加载哪个文件」是什么意思。

::: sol B5 核对

不同意。这条错误的主体是一个被**运行期动态加载**的模块（不是 `NEEDED` 里的直接依赖），报错说的是「这个动态共享对象里没有调用方需要的算法实现」，属于符号/提供者层的失败，而 glibc 缺失会表现为 `cannot open shared object file` 或 `symbol lookup error`——先按 B4 的五步取证：`readelf -d` 看主程序 `NEEDED`、`LD_DEBUG=libs` 看加载器真正尝试过哪些路径、`nm -D` 与 `readelf -V` 看那个被加载的文件里到底有没有所需符号与版本。多出来的一层是：`dlopen` 的路径由程序在运行期按自己的配置算出来（模块目录、环境变量、当前工作目录），所以「库装在哪儿」不再是加载器一家的事，还得看程序算出的那个路径是不是你以为的那一个；同一原因也解释了三类常见诱因：模块目录被打包时漏掉、程序指向了另一套安装、或模块与主库版本不配套。修法是让加载路径与文件版本对齐，而不是替换 libc。这条错误文本在本书的 Linux 实测机上未复现（那台机器上没有构造对应的模块缺失场景），所以本题只考判据与取证顺序；相关工具口径见[勘误与版本注记](ch07-errata.md)的未实测项。

:::
:::

::: ex 例 1.7-B6 · 换了 .so 之后 symbol lookup error {#ex-1.7-B6}

你只是把 `libfoo.so.1` 换成同名新版本，旧程序启动就报 `symbol lookup error: undefined symbol`（或带版本标签）。有人说「soname 一样就说明 ABI 兼容」。这句话错在哪？给出两条命令级别的判据与一条预防措施。

::: sol B6 核对

错在把「文件名一样」当成「ABI 一样」。ABI 兼容要求导出符号集合、符号版本标签、结构体布局与调用约定都不变；加字段、改 `enum` 的底层大小、把符号从导出变成 `HIDDEN`、或者新版本只发布新标签却不再提供旧标签，都会在运行期炸。判据两条：① `nm -D` 分别列旧库与新库的导出符号（含版本标签），做差集，缺的那几个就是报错的根源；② `readelf -d` 核对 `SONAME` 与主程序的 `NEEDED` 是否真的指向同一份语义版本（如果新库的 `SONAME` 该升而没升，问题就变成了「同一个 soname 装着两套不兼容的 ABI」）。预防措施是把接口层的稳定性做在编译期：库内部符号一律 `-fvisibility=hidden`，只显式导出稳定的薄封装；接口一变就升 `SONAME`，并让打包系统按 soname 依赖，这样旧程序继续绑旧库，而不是在运行时撞墙。

:::
:::

::: ex 例 1.7-B7 · LD_PRELOAD 设了没反应 {#ex-1.7-B7}

`LD_PRELOAD=./libcount.so ls` 什么都没打印；换成自己写的一个程序却正常打印。给出至少四种可能原因和区分方法，其中必须包含「钩子其实已经加载了」这一种。

::: sol B7 核对

先证明它到底有没有被加载：在钩子库里加一个 `__attribute__((constructor))` 打印一行（或用 `LD_DEBUG=libs` 看它有没有被搜到并载入）。分四种情况。① **加载了，但报告没机会跑**：钩子的统计是在 `__attribute__((destructor))` 里输出的，而像 `ls`、`cat` 这类程序用 `_exit()` 一类不经正常退出的路径收场时，ELF 析构不会执行，统计自然一行不剩——这在本书的 Linux 实测机上是可以稳定复现的，所以正文 1.7.8/1.7.13 里「`LD_PRELOAD=... /bin/ls` 打印计数」那一段不能作为通用验收：验收对象要换成自己写的、从 `main` 正常返回的程序。② **目标静态链接**：没有 `ld.so` 参与，预加载根本不发生，用 `readelf -d` 看不到 `NEEDED`/`PT_INTERP` 即确认。③ **调用不存在**：`-O2` 下结果未被使用、也没有副作用的 `malloc` 调用会被整段删除，或调用被内联/走库内部入口，钩子计数就是 0——用 `-O0` 或 `-fno-builtin` 重编目标程序对比，或反汇编看有没有那个 `call`。④ **符号被隐藏**：钩子里的符号带 `HIDDEN` 可见性或不是可抢占的全局动态符号，加载器不会把它放在解析链前面，用 `nm -D` 检查钩子库里它是否作为导出符号存在。四条按「加载—存在—被调用—能报告」的顺序排，一次只换一样，别同时改编译选项和目标程序。

:::
:::

## C 组 · 动手实验

::: ex 例 1.7-C1 · 两个归档库，调转顺序 {#ex-1.7-C1}

在一台 Linux 上用 `gcc` 造两个互相引用的静态库，先用一种顺序链成功、再用另一种顺序链失败，然后用 `--start-group` 让它成功。写出命令并说明每一步的判据。

::: sol C1 核对

准备三个文件：`a.c` 里 `a()` 调 `b()`，`b.c` 里 `b()` 调 `a()`（用递归还到 0 为止，保证运行会终止），`m.c` 只调 `a()`。然后 `cc -c a.c b.c m.c`，`ar rcs liba.a a.o`、`ar rcs libb.a b.o`。三种链接依次试：`cc m.o -L. -la -lb -o p`（成功）；`cc m.o -L. -lb -la -o p`（报未定义引用）；`cc m.o -L. -Wl,--start-group -la -lb -Wl,--end-group -o p`（成功）。判据三处：① 失败那条的报错会**点名归档里的成员**（形如 `./liba.a(a.o): in function 'a'`），说明成员已被抽出、缺的是它自己的依赖——这正是「只扫一遍」的直接证据；② `nm --defined-only liba.a`、`nm --defined-only libb.a` 先确认两个符号各自在哪个库里，排除「根本没定义」；③ 成功后 `./p` 的输出与两种顺序应当给出同一个值。做完把 `p` 与中间产物留着，B1 的四种原因你现在手上就有三种。

:::
:::

::: ex 例 1.7-C2 · 用 --wrap 给 puts 加前缀 {#ex-1.7-C2}

照 [1.7.13](ch07.md#sec-1.7.13) 的 `wrap.c` 编一份，验证 `--wrap` 真的生效，并给出两个「让它失效」的改动来体会它的边界。

::: sol C2 核对

编译 `cc -O2 wrap.c -Wl,--wrap=puts -o wrap` 后运行，输出里应出现你加的前缀；去掉 `-Wl,--wrap=puts` 再编一次，前缀消失——这一对比就是生效判据。再查符号层：`nm wrap` 里应能看到 `__wrap_puts` 被链进来，而 `objdump -d` 中原来的调用点指向 `__wrap_puts`。两个失效实验：① 把 `puts("hi")` 换成一个结果完全不被使用、也看不出副作用的小分配调用并用 `-O2` 编，链接器看不到未定义引用，`--wrap` 无从改写（这正是正文 errata 说的「被内联或被优化掉的调用」）；② 让同一个库里的另一个 `.so` 内部去调那个函数，你的 `--wrap` 不会改到共享库内部已绑定的调用——判据是 `readelf -d` 里那个库仍在 `NEEDED`，而它的内部路径与你的可执行文件无关。结论写一句：`--wrap` 的作用域是**本次链接单元里的未定义引用**。

:::
:::

::: ex 例 1.7-C3 · LD_PRELOAD 统计净分配 {#ex-1.7-C3}

用 [1.7.13](ch07.md#sec-1.7.13) 的 `malloc_count.c` 做一个统计净分配次数的钩子。要求：先在自己写的程序上跑通，再解释为什么在 `ls`、`cat` 上可能一行输出都没有，以及为什么 `-O2` 下计数会是 0。

::: sol C3 核对

`cc -std=c17 -Wall -Wextra -Werror -O2 -fPIC -shared malloc_count.c -o libcount.so -ldl` 编好（在 glibc 2.34 及以后的系统上 `-ldl` 加不加都能过，正文 1.7.13 的 errata 第 4 条就是这个）。写一个被测程序：按命令行参数决定分配多少次、并把返回的指针真正写进数组再用起来，最后正常 `return`。用绝对路径预加载：`LD_PRELOAD=$PWD/libcount.so ./prog 100`，会看到计数；`./prog 0` 时计数应为 0。三个判据点要各验一次。① 钩子有没有加载：加一个 constructor 打印，或看 `LD_DEBUG=libs`；② 为什么 `ls`/`cat` 不打印：它们用 `_exit()` 收场，ELF 析构不跑，报告那一环没了——所以本书的 Linux 实测机上这个演示必须换成自己正常返回的程序，别把「没输出」当成打桩失败；③ 为什么 `-O2` 计数为 0：返回值没被使用的 `malloc` 会被当作可消除的分配整个删掉，调用根本不存在。顺带验一次正文 errata 的第 1 条：把 `-static` 编出来的同样程序配上同一个钩子，不会有任何效果，`readelf -d` 里也没有 `NEEDED`。

:::
:::

::: ex 例 1.7-C4 · readelf -d 与 nm -D 对账 {#ex-1.7-C4}

对一个自己编译的动态链接可执行文件，把「它声明需要什么」和「系统准备给它什么」对起来。要求列出四项检查，并比较一次立即绑定与延迟绑定的差别。

::: sol C4 核对

四项：① `readelf -h` 看 `Type`，确认它是 PIE（`DYN`）还是固定地址（`EXEC`）；② `readelf -d` 看 `NEEDED` 的 soname 列表与有没有 `BIND_NOW`/`FLAGS`；③ `readelf -l` 看 `PT_INTERP`（解释器路径随架构不同，aarch64 与 x86-64 不是同一个文件名）与 `PT_GNU_RELRO`；④ `nm -D` 看未定义符号及其版本标签，再用 `readelf -V`/`objdump -p` 看它需求哪些版本节点，两边应当一一对上。绑定对照：分别编两份，一份用默认选项、一份加 `-Wl,-z,lazy`，`readelf -d` 里两者的 `BIND_NOW` 标记状态不同；再各跑一次 `LD_DEBUG=bindings`，数目标符号被绑定的时机与次数——延迟绑定那份会把它推到第一次调用附近。注意本书的 Linux 实测机（Ubuntu 24.04 的默认 GCC）产出的可执行文件**默认就带立即绑定**，所以「第一次调用才解析」不是到处都成立，见[勘误与版本注记](ch07-errata.md)第 4 节。

:::
:::

::: ex 例 1.7-C5 · RUNPATH 与 \$ORIGIN：让库跟着程序走 {#ex-1.7-C5}

不用 root，把一个共享库和可执行文件放在两个目录，用 `$ORIGIN` 相对 rpath 让它们能一起搬走；然后故意把库目录改名，复现「找不到库」，再按取证顺序修好。

::: sol C5 核对

做法：`cc -fPIC -shared lib.c -o libshared.so -Wl,-soname,libshared.so.1`，建一个 `lib/` 子目录并把文件放成 `lib/libshared.so.1`；`cc use.c -o use -L. -lshared -Wl,-rpath,'$ORIGIN/lib'`（`$ORIGIN` 要让 shell 原样传下去，所以用单引号）。跑 `./use` 成功；`readelf -d` 里能看到 `RUNPATH` 项，且 `NEEDED` 记的是 soname `libshared.so.1`。破坏：把 `lib/` 改名，`./use` 立刻报「无法打开共享对象文件」一类错误、退出码非 0；此时按 B4 的顺序取证——`LD_DEBUG=libs` 会把 `RUNPATH` 展开后的目录、缓存、系统目录逐一列出，你会看到它在 `$ORIGIN` 解析出的那个路径里试过。修三种：把目录名改回来；`LD_LIBRARY_PATH=$PWD/lib ./use`；或给间接依赖也设 rpath（这正是 `RUNPATH` 不传递的后果，可用一个「主程序 → libA → libB」的链来验证：只给主程序设 `RUNPATH`，间接的 `libB` 仍找不到）。全程不写 `/etc`，不调 `ldconfig`。

:::
:::

::: ex 例 1.7-C6 · 用 elfdump.c 读一个真实的 .o {#ex-1.7-C6}

编译 [1.7.12](ch07.md#sec-1.7.12) 的 `elfdump.c`，拿它读你自己编出的一个 `.o`，和 `readelf` 对账；再喂给它一个非 ELF 文件。

::: sol C6 核对

先造目标文件：`cc -c demo.c -o demo.o`（内容含一个函数、一个全局变量、一次对外部函数的调用）。跑 `./elfdump demo.o`，逐项对：ELF 头 64 字节、`e_shoff`/`e_shnum`/`e_shstrndx` 三项与 `readelf -h` 一致；节头表里 `sh_type` 的名字（PROGBITS/SYMTAB/STRTAB/RELA/NOBITS）与 `readelf -S` 一致；`.rela.text` 的 `sh_size` 是 24 的整数倍，除以 24 就是重定位条数，应与 `readelf -r` 的行数相同；符号表项是 24 字节，`.o` 里 `st_value` 是节内偏移（函数从 0 开始排），别当虚拟地址；`st_shndx` 出现 65521/65522 时对应 `SHN_ABS`/`SHN_COMMON`。判据是你自己的程序与 `readelf` 完全一致，不是它输出漂亮。最后 `./elfdump` 一个非 ELF 文件（例如一个 `.txt`），它应在验完魔数后拒绝并给出非 0 退出码。延伸两处：给它一个 Mach-O（macOS 上的可执行文件）同样会被拒——那是另一套容器格式；它只处理小端 ELF64，大端或 ELF32 要换解析函数。

:::
:::

::: ex 例 1.7-C7 · 加固项对照，不装 checksec {#ex-1.7-C7}

同一份源码编三份：默认、`-fno-pie -no-pie`、`-O2 -Wl,-z,relro,-z,now`。只用 `readelf` 判断三者的 PIE、RELRO、立即绑定与栈执行权限，并说明 `checksec` 不在时你的替代判据。

::: sol C7 核对

`readelf -h` 的 `Type` 区分 PIE（`DYN`）与固定地址（`EXEC`）；`readelf -d` 里的 `BIND_NOW`/`FLAGS` 说明是否立即绑定；`readelf -l` 里有没有 `GNU_RELRO` 段说明部分或完全 RELRO，`GNU_STACK` 的权限位说明栈是否可执行。三份比下来你应该能说出：默认那份在新发行版上通常已经是 PIE 加 RELRO 加 `BIND_NOW`（本书的 Linux 实测机正是这样，见[勘误与版本注记](ch07-errata.md)第 4 节，这与正文里「延迟绑定是默认」的 x86-64 口径不同）；`-no-pie` 那份 `Type` 变 `EXEC`、`readelf -r` 里 `R_X86_64_RELATIVE` 那一类会显著减少或消失；显式加 `-z relro,-z now` 的那份三项齐全。再补一个非工具判据：`file prog` 会写明是不是 PIE 与是否动态链接。`checksec` 在本书的实测机上没有安装，所以别把它的输出格式当依据——上面四条 `readelf` 判据能覆盖它报的 RELRO/NX/PIE/BIND_NOW 四项，`Stack Canary` 与 `FORTIFY` 则要看反汇编里有没有哨兵检查与 `__*_chk` 符号。

:::
:::

::: ex 例 1.7-C8 · 自己造一次「版本找不到」错误 {#ex-1.7-C8}

不碰系统库，用符号版本脚本造一个库和一个依赖它的程序，然后把库的版本标签换掉，复现 `version ... not found` 的错误形态。说明它与 B4 的层次差别。

::: sol C8 核对

给库写一个版本脚本，声明一个版本节点（例如 `FOO_1.0`）并把函数放在它的 `global` 下，`cc -fPIC -shared f.c -o libf.so -Wl,--version-script=v.map -Wl,-soname,libf.so`；用同一个脚本链程序 `cc m.c -o m -L. -lf -Wl,-rpath,'$ORIGIN'`，先确认 `./m` 正常。此时 `readelf -V m` 的需求表里应能看到它绑着 `FOO_1.0`（`objdump -p` 的 version needs 同样能看）。把脚本改成只发布新版本（例如 `FOO_2.0`）重编库、文件名与 soname 都不变，再跑 `./m`：程序会在加载期就退出，报的是「版本找不到（required by ...）」而不是「文件找不到」，退出码非 0。层次差别正在于此：B4 的搜索路径全部命中也照样失败，因为要的不是文件而是符号标签；取证手段也不同——B4 用 `LD_DEBUG=libs` 看目录，这里用 `readelf -V`/`nm -D` 比对两侧的版本集合。这条实验也解释了 B3 里为什么「装更新的 glibc」不对：真问题是需求表与库内标签不一致，把标签对齐才是修。全程不需要 root。

:::
