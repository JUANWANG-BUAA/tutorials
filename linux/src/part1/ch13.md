## 1.13.1 三大主题地图 {#sec-1.13.1}

这一节回答：一台只有 4 个 CPU 的机器，凭什么同时装下几百个进程、还让每个进程都以为自己独占一台机器？操作系统课又为什么把这一切压成虚拟化、并发、持久化三件事？

::: preview 先抓住一件事
操作系统反复做同一件事：把有限的硬件切成很多份「看起来独享」的资源，并保证共享时不塌。CPU 与内存靠**虚拟化**造出独享的幻觉，多个执行流读写同一块数据靠**并发**保正确，断电之后数据还在且自洽靠**持久化**。每一件里都要分清机制（怎么做）与策略（选哪一个）。
:::

先看现场。本书的 Ubuntu 24.04 虚拟机是 4 vCPU、约 12 GiB 内存，随手数一下：

```text
$ nproc
4
$ ps -e --no-headers | wc -l
225
$ grep -E '^(MemTotal|SwapTotal):' /proc/meminfo
MemTotal:       12207948 kB
SwapTotal:       4194300 kB
```

225 个进程分 4 个核，平均每个核要轮 56 个，可你敲命令时并没有感到在排队。原因有两层：多数进程此刻在睡或在等 I/O，真正同时想跑的只有几个；剩下的是内核用切换造出的「同时」假象。内存也一样，225 个地址空间加起来远超 12 GiB，但每个进程只把当下用到的页留在物理内存里。

这张图有三种读法。

1. **按列读**：每一列是一组机制。虚拟化 CPU 是「受限直接执行 + 定时器中断 + 上下文保存」；虚拟化内存是「页表 + TLB（地址翻译缓存）+ 缺页异常（访问的页不在内存里）」；并发是「原子指令 + 等待队列」；持久化是「DMA + 中断 + 日志」。
2. **按行读**：每一行是「机制 → 策略」的配对。调度有 FIFO/SJF/RR/MLFQ，页替换有 FIFO/LRU/Clock，I/O 调度有 SSTF/SCAN，文件系统布局有 FFS/LFS。机制决定「能不能做」，策略决定「这次选谁」。
3. **按箭头读**：三块不是三个模块。缺页异常要睡眠，就得用进程上下文与等待队列；page cache 属于虚拟内存，却替文件系统缓存数据；自旋锁靠原子指令，而原子指令的语义由内存系统规定。真实内核里，这三块代码互相调用。

::: def 定义 1.13.1 · 机制与策略 {#def-1.13.1}
**机制**（mechanism）回答「这件事怎么做」：上下文切换保存哪些寄存器、页表项哪一位表示存在、日志先写哪一块。**策略**（policy）回答「这次选哪一个」：下一个跑哪个进程、内存满了换哪一页、脏页什么时候回写。机制通常由硬件与内核固定，策略可以随负载调整；排障时先分清坏的是哪一层，才不会给策略打补丁却改坏了机制。
:::

::: errata 关于三大主题的三个误解
1. **「三块是三个独立模块」**——它们共享同一批底层设施：缺页要睡眠，就会用到等待队列；文件读写走 page cache，就要和页回收抢内存；锁的原子性最终由内存模型与原子指令保证。
2. **「虚拟化就是虚拟机」**——本章的虚拟化指「把一个 CPU、一块内存虚拟成多份」，与 VMware、KVM 那种「把整台机器虚拟成多台」不是一回事；后者建立在同一套机制之上。
3. **「持久化就是文件系统」**——文件系统只解决「数据怎么组织」；断电后是否一致，要靠日志、`fsync`、RAID 与备份分别承担不同层次的保证。RAID 防盘坏，不防误删。
:::

### 1.13.1 小结

操作系统把「CPU 太少、内存太小、数据会丢」分别交给虚拟化与持久化，把「多个执行流共享数据」交给并发；每一件都分机制与策略。如果只记住一件事：**看到任何操作系统问题，先问它属于哪件事、坏在机制还是策略**。

::: method 即时自测 · 1.13.1
**Q1（记忆）** 三大主题各对应哪一类矛盾？各举两个策略名。

**Q2（辨析）** 「进程有 225 个、CPU 只有 4 个，所以每个进程只能拿到 4/225 的 CPU」这句话错在哪？

**Q3（应用）** 一个服务偶发变慢，`vmstat` 的 `si/so` 正常、CPU 也不满。按三大主题，你下一步分别查什么？

::: sol 答案
**A1** 虚拟化对应「CPU 与内存太少、程序太多」；并发对应「多个执行流共享数据」；持久化对应「断电会丢数据」。策略例子：调度用 FIFO/RR/MLFQ，页替换用 FIFO/LRU/Clock，I/O 用 SSTF/SCAN。

**A2** 把「进程数」当成了「同时想跑的线程数」。多数进程在睡或等 I/O，不参与分 CPU；真正竞争的是 runqueue 上的可运行任务，看 `vmstat` 的 `r` 列或 `/proc/loadavg` 才准。

**A3** 先分三路：CPU 侧看可运行队列与单核份额（`vmstat 1` 的 `r`、`/proc/<pid>/sched`）；内存侧看缺页与回收（`/proc/vmstat` 的 `pgscan`、`pgsteal`）；持久化侧看 I/O 等待与 `fsync`（`iostat -x` 的 `w_await`）。哪一路先出现异常，就先查那一节的机制。
:::
:::

## 1.13.2 CPU 虚拟化：调度策略与指标 {#sec-1.13.2}

这一节回答：4 个核上跑着 225 个进程，凭什么每个进程都觉得自己没被卡住？两个忙循环抢同一个核时，多出来的时间到底花在哪，调度器又该按什么指标决定先给谁？

::: preview 先抓住一件事
「同时运行」是切换造出来的：内核让一个进程跑一小段，定时器一响就保存现场、换下一个。切换不创造 CPU，只重新分配等待，所以公平与效率只能按指标取舍。
:::

先把「抢同一个核」变成墙钟：程序在固定时间内反复做同一段加法，用 `taskset` 把进程钉在指定核上：

```c
/* burn.c：在 secs 秒内数忙循环次数
 * cc -O2 -std=c17 burn.c -o burn
 */
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#include <unistd.h>

static double now(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec + (double)ts.tv_nsec / 1e9;
}

int main(int argc, char **argv)
{
    double secs = argc > 1 ? atof(argv[1]) : 3.0;
    double t0 = now(), t1;
    volatile long x = 0;
    long n = 0;

    do {
        for (int i = 0; i < 1000000; i++)
            x += i;
        n += 1000000;
        t1 = now();
    } while (t1 - t0 < secs);
    printf("pid=%d loops=%ld elapsed=%.2f\n", (int)getpid(), n, t1 - t0);
    return 0;
}
```

每轮 3 秒，只改绑核方式：

```text
# VM 实测 · Ubuntu 24.04.5 / 4 vCPU
$ taskset -c 0 ./burn 3
pid=53003 loops=10740000000 elapsed=3.00
$ taskset -c 0 ./burn 3 & taskset -c 0 ./burn 3; wait
pid=53010 loops=5474000000 elapsed=3.00
pid=53011 loops=5428000000 elapsed=3.00
$ taskset -c 0 ./burn 3 & taskset -c 1 ./burn 3; wait
pid=53021 loops=10841000000 elapsed=3.00
pid=53022 loops=10985000000 elapsed=3.00
```

三组墙钟都是 3.00 秒，差别在每秒做多少：独占一个核是 107 亿次；两个进程绑同一个核，各做 54 亿次，正好一半；分绑两个核，各自仍是 108 亿、110 亿次。换成固定工作量：同样的活，同核竞争时墙钟翻倍，异核时不增加。

切片靠**受限直接执行**（limited direct execution, LDE）：用户程序真的在 CPU 上跑，内核只在系统调用（主动）与定时器中断（被动）时介入；每次介入都保存现场、按策略选下一个、恢复它的现场。进程因此才产生「独占 CPU」的幻觉。

::: def 定义 1.13.2 · 周转时间与响应时间 {#def-1.13.2}
**周转时间**（turnaround time）= 完成时刻 − 到达时刻，衡量「提交到做完」；**响应时间**（response time）= 第一次被调度时刻 − 到达时刻，衡量「等多久才有反应」。两者经常冲突：让短任务先跑，周转好看，长任务却可能一直等；让每个任务尽快摸一次 CPU，响应好看，切换与排队又拖长总时间。
:::

常见策略对比如下：

| 策略 | 抢占 | 选择规则 | 优点 | 缺点 |
|:--|:--|:--|:--|:--|
| FIFO | 否 | 按到达顺序 | 简单、公平 | 长任务堵住短任务 |
| SJF | 否 | 最短任务优先 | 周转最优（非抢占） | 需要预知运行时间，长任务饥饿 |
| STCF | 是 | 最短剩余时间优先 | 周转最优（抢占） | 上下文切换多，饥饿 |
| RR | 是 | 时间片轮转 | 响应好、公平 | 周转差，片长难调 |
| MLFQ | 是 | 多级队列 + 动态优先级 | 兼顾响应与吞吐 | 参数多，可被 gaming |
| 比例份额 | 是 | 彩票/步长/CFS 权重 | 可按权重分配 | 不保证绝对延迟 |

以 A(到达 0，运行 10)、B(1，5)、C(2，2) 为例：

- FIFO：A 0–10，B 10–15，C 15–17；周转 10/14/15，平均 13；响应 0/9/13。
- SJF（非抢占）：A 0–10，C 10–12，B 12–17；周转 10/16/10，平均 12；响应 0/11/8。
- RR（片长 2）：A 0–2，B 2–4，C 4–6，A 6–8，B 8–10，A 10–12，B 12–13，A 13–15，A 15–17；周转 17/12/4，平均 11；响应 0/1/2。

RR 的平均周转不一定比 SJF 好，但响应时间显著更优。交互系统选 RR/MLFQ，批处理系统选 SJF/STCF。真实系统没有「预知运行时间」的水晶球，只能用历史行为预测。按权重分份额那一族（nice 权重表、`/proc/<pid>/schedstat`）在 [0.9.8](../part0/ch09.md#sec-0.9.8) 已写过，0.9 的实验量过：不绑核 299:299，绑同核 270:29。

### MLFQ 的五条规则

多级反馈队列（multi-level feedback queue, MLFQ）用多个优先级队列，在不知道「还要跑多久」的前提下，近似做到「照顾短任务，也不得罪长任务」：

1. 新任务进最高优先级；
2. 同一优先级内按 RR；
3. 任务用完整个时间片就降一级（可能是 CPU 密集）；
4. 任务在时间片内主动让出 CPU 就留在原级（可能是 I/O 密集）；
5. 每隔一段时间把所有任务提升到最高级，防止饥饿和 gaming。

规则 5 是关键：没有周期提升，长任务会永远沉底，这就从「策略不好」变成「饥饿」；有了周期提升，短任务又会被打断。参数（队列数、片长、提升周期）决定系统性格。MLFQ 是教科书模型，Linux 的普通调度类并不是它，下面的 errata 会说清这层差距。

### 多核调度

多核调度多了两个问题：**缓存亲和性**（任务在哪个核上跑，L1/L2 热不热）和**负载均衡**（核间任务数是否均匀）。常见结构：

- **SQMS**（单队列多处理器）：一个全局运行队列，锁竞争大，亲和性差；
- **MQMS**（多队列多处理器）：每核一个队列，亲和性好，但可能负载不均；
- **work stealing**：空闲核从别的核偷任务，兼顾两者。

搬任务还要挑时机：搬得太勤，缓存全冷；搬得太懒，一个核排队、另一个核空转。Linux 的 CFS/EEVDF 用调度域（scheduling domain）分层做负载均衡，[3.5](../part3/ch05.md)、[3.6](../part3/ch06.md) 会展开。

把上面三个策略写成程序，指标就不必手算。下面的模拟器用同一组任务跑 FIFO、SJF、RR，直接打印每个任务的开始、结束与平均值：

```c
/* sched.c：FIFO/SJF/RR 调度指标模拟 */
#ifndef _GNU_SOURCE
#define _GNU_SOURCE
#endif
#include <stdio.h>
#include <string.h>

#define N 3

typedef struct {
    const char *name;
    int arrival, burst;
    int start, end;
} task;

static const task base[N] = {
    {"A", 0, 10, 0, 0},
    {"B", 1, 5, 0, 0},
    {"C", 2, 2, 0, 0},
};

static void reset(task t[N])
{
    memcpy(t, base, sizeof(base));
}

static void report(const char *policy, task t[N])
{
    double sum_t = 0, sum_r = 0;
    printf("%s:\n", policy);
    for (int i = 0; i < N; i++) {
        int turnaround = t[i].end - t[i].arrival;
        int response = t[i].start - t[i].arrival;
        sum_t += turnaround;
        sum_r += response;
        printf("  %s start=%2d end=%2d turnaround=%2d response=%2d\n",
               t[i].name, t[i].start, t[i].end, turnaround, response);
    }
    printf("  avg turnaround=%.2f response=%.2f\n", sum_t / N, sum_r / N);
}

static void fifo(void)
{
    task t[N];
    reset(t);
    int now = 0;
    for (int i = 0; i < N; i++) {
        if (now < t[i].arrival)
            now = t[i].arrival;
        t[i].start = now;
        now += t[i].burst;
        t[i].end = now;
    }
    report("FIFO", t);
}

static void sjf(void)
{
    task t[N];
    reset(t);
    int done[N] = {0};
    int now = 0, finished = 0;

    while (finished < N) {
        int pick = -1;
        for (int i = 0; i < N; i++) {
            if (done[i] || t[i].arrival > now)
                continue;
            if (pick < 0 || t[i].burst < t[pick].burst)
                pick = i;
        }
        if (pick < 0) {
            int next = -1;
            for (int i = 0; i < N; i++)
                if (!done[i] && (next < 0 || t[i].arrival < t[next].arrival))
                    next = i;
            now = t[next].arrival;
            continue;
        }
        t[pick].start = now;
        now += t[pick].burst;
        t[pick].end = now;
        done[pick] = 1;
        finished++;
    }
    report("SJF (non-preemptive)", t);
}

static void rr(int quantum)
{
    task t[N];
    reset(t);
    int rem[N], inq[N] = {0}, done[N] = {0};
    int q[256], head = 0, tail = 0;
    int now = 0, finished = 0;

    for (int i = 0; i < N; i++) {
        rem[i] = t[i].burst;
        t[i].start = -1;
    }

    while (finished < N) {
        for (int i = 0; i < N; i++) {
            if (!done[i] && !inq[i] && t[i].arrival <= now) {
                q[tail++] = i;
                inq[i] = 1;
            }
        }
        if (head == tail) {
            now++;
            continue;
        }
        int i = q[head++];
        if (t[i].start < 0)
            t[i].start = now;
        int run = rem[i] < quantum ? rem[i] : quantum;
        now += run;
        rem[i] -= run;
        for (int k = 0; k < N; k++) {      /* 运行期间到达的任务先入队 */
            if (!done[k] && !inq[k] && t[k].arrival <= now) {
                q[tail++] = k;
                inq[k] = 1;
            }
        }
        if (rem[i] == 0) {
            t[i].end = now;
            done[i] = 1;
            inq[i] = 0;
            finished++;
        } else {
            q[tail++] = i;                 /* 重新排队，inq 保持 1 */
        }
    }
    report("RR (quantum=2)", t);
}

int main(void)
{
    fifo();
    sjf();
    rr(2);
    return 0;
}
```

::: errata 关于调度策略的三个误解
1. **「RR 的片长就是 Linux 的时间片」**——普通调度类没有固定片长：CFS 按 `sched_latency` 与任务数动态分片，EEVDF 给每个实体一个 `se.slice`；名叫 RR 的 `SCHED_RR` 属于实时类，与教学 RR 不是一回事。
2. **「SJF 周转最优，生产系统就该照它做」**——它要求预知每个任务还要跑多久，真实系统拿不到这个数；短任务源源不断时，长任务永远排不上。
3. **「绑核能让程序更快」**——绑核只改变「和谁竞争」。单任务独占一个核时，绑不绑速度一样；把两个互相抢核的进程分到不同核才有效。
:::

::: ex 例 1.13.2 · 先猜三种调度策略的周转时间 {#ex-1.13.2}
三个任务同时到达：A 需要 10 s、B 需要 4 s、C 需要 2 s。
先猜：FCFS（按 A、B、C）、SJF（最短作业优先）、RR（时间片 1 s）三种策略下，平均周转时间各是多少？

::: sol 解答
FCFS：A 完成于 10、B 于 14、C 于 16，平均 (10+14+16)/3 ≈ 13.33 s。SJF：C 2、B 6、A 16，平均 8 s——短任务先走，平均值明显下降。RR（片 1 s）：A、B、C 轮流，C 在 6 s 内完成、B 在 9 s、A 在 16 s，平均 (16+9+6)/3 ≈ 10.33 s。RR 牺牲了平均周转时间，换来的是响应时间：每个任务最迟 3 s 内就第一次被执行。**指标不同，最优策略就不同**，这是 1.13.2 那张表的核心。
:::
:::

### 1.13.2 小结

CPU 虚拟化靠切换把 4 个核分给 225 个进程，切换只重新分配等待，不创造算力。周转与响应互相拉扯：FIFO 怕长任务堵路，SJF 要预知运行时间，RR/MLFQ 折中，比例份额按权重分。如果只记住一件事：**先确认在争什么、再看哪个指标重要，最后才选策略**。

**Q2（辨析）** RR（片长 2）的平均响应是 1.00，比 FIFO 的 7.33 好得多，平均周转却是 11.00 对 13.00。为什么这次 RR 的周转反而更好，换一组任务还会不会？

## 1.13.3 内存虚拟化：从分段到交换 {#sec-1.13.3}

这一节回答：每个进程都以为自己有一整块从 0 开始、连续可用的内存，这块「内存」是怎么造出来的？物理内存不够时，内核又按什么顺序把哪一页搬到磁盘？

::: preview 先抓住一件事
地址空间是假的：进程拿到虚拟地址，硬件配合页表把它翻译成物理地址。分段用「基址 + 界限」切出代码、堆、栈，简单但留下外部碎片；分页用固定大小的页消掉外部碎片，代价是页表本身占空间；物理内存不够时，把冷页换出到 swap，缺页再换回。分页、多级页表与 TLB 在 [1.9](ch09.md) 已经写透，本节只补两段：分页之前的分段，以及内存不够之后的交换。
:::

先看一次真实的「映射了不等于占了」。下面的程序 `mmap` 64 MiB 匿名内存，只碰前 16 MiB，然后睡住：

```c
/* 片段：完整程序还需 <sys/mman.h> 与 <unistd.h> */
char *p = mmap(NULL, 64UL << 20, PROT_READ | PROT_WRITE,
               MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
for (unsigned long off = 0; off < (16UL << 20); off += 4096)
    p[off] = 1;                 /* 每页写一个字节，触发一次缺页 */
sleep(10);
```

另开一个终端读它的 `smaps`：

```text
$ grep -A22 '^Size: *65536 kB' /proc/<pid>/smaps | grep -E '^(Size|Rss|Swap):'
Size:              65536 kB
Rss:               16384 kB
Swap:                  0 kB
```

`Size` 是这段映射的虚拟大小 64 MiB，`Rss` 是实际驻留的物理页 16 MiB，`Swap` 是 0。三个数放在一起说明：`mmap` 只登记了一段地址范围，第一次写每一页才触发缺页、分配物理页。再看整机：

```text
$ grep -E '^(MemTotal|SwapTotal|SwapFree):' /proc/meminfo
MemTotal:       12207948 kB
SwapTotal:       4194300 kB
SwapFree:        4194300 kB
$ swapon --show
NAME      TYPE SIZE USED PRIO
/swap.img file   4G   0B   -1
```

这台机器有 4 GiB swap，但一页都没用。`smaps` 里的 `Swap: 0` 说的是「这个进程没有页被换出」，不是「系统没开 swap」——这两个 0 经常被混为一谈。

把内存虚拟化拆成三个问题，机制与策略各归各位：

| 问题 | 机制 | 策略 |
|:--|:--|:--|
| 地址怎么翻译 | 页表 + TLB + MMU | 多级页表、大页 |
| 缺页怎么办 | 缺页异常 + 页分配/换入 | 按需分页、预取 |
| 内存满了换谁 | 页回收 | FIFO/LRU/Clock/ARC |

页替换策略的评估指标是**命中率**。FIFO 简单，但会遇到 Belady 异常（增加页框反而命中率下降）；LRU 近似理论最优，却要精确记录访问顺序，硬件成本高；Clock 用访问位近似 LRU。实际内核用 active/inactive 双链表加引用位做近似，[3.10](../part3/ch10.md) 会展开。

### 分段：段布局、共享与外部碎片 {#sec-1.13.3.1}

分段把地址空间切成代码、数据、堆、栈四段，每段一份「基址 + 界限 + 权限」。硬件用「段号 + 偏移」查段表，越界触发异常；共享库可以把同一代码段映射进多个进程，权限按段设置。

外部碎片是它的原罪：段大小不一，频繁分配释放后，空闲空间被切成许多不连续的小洞，即使总空闲够，也放不下一个新段。紧凑（compaction）能搬移段来合并空洞，代价是复制与暂停；分页才是通行的解法。

四个实现问题决定分段长什么样：

- **地址属于哪一段**：可以让虚拟地址的高位当段号，由 MMU 按位拆（隐式）；x86 用显式选择子——CS/DS/SS/FS/GS 指向 GDT/LDT 描述符，翻译时查基址、界限与权限。
- **栈往哪长**：栈向低地址增长，方向与堆相反；描述符要有「增长方向」位，越界判断也要反着做。
- **共享到什么粒度**：粗到每个地址空间几段，只能整段共享；细到每个对象一段，共享灵活但段表膨胀、切换开销大。外部碎片正是粗粒度切分的后果。
- **切换的代价**：段寄存器与段表基址属于进程现场，切换要一并换。x86-64 把 CS/DS 基址固定为 0、让分页接管，但 FS/GS 基址保留至今——线程本地存储（TLS）与内核 per-CPU 变量就挂在它们上面。这是分段留给 Linux 的遗产。

### 交换：swap 区、present 位与换入路径 {#sec-1.13.3.2}

交换把不常用的页写到 swap 区，页表项清 present 位，但保留 swap 槽号。缺页时走五步：

1. 硬件发现 PTE 的 present=0，触发缺页；
2. 内核从 PTE 的 swap 信息知道页在哪个槽；
3. 分配一个物理页，把槽里的内容读回；
4. 更新 PTE 指向新页，present=1；
5. 返回用户态，重试刚才那条指令。

swap 区不是文件系统，是一组槽（slot）；`swapon` 把块设备或文件登记为 swap。代价是磁盘 I/O：一次主缺页可能是几十微秒到几毫秒。所以策略是「少换、换对」：LRU/Clock 近似选页、active/inactive 双链表、`kswapd` 后台回收、`swappiness` 调匿名页与文件页的回收比例。`vmstat 1` 的 `si/so` 持续非零，说明已经在 thrashing 边缘，此时加内存比调参数有效。

换入只是「缺页 + 按需补页」的一种用法，同一套机关还能做三件优化：**按需清零**（demand zeroing）——匿名页先映射到共享只读零页，第一次写才分配并清零，所以 `malloc` 大块不立刻吃物理内存（[1.9](ch09.md) 的零页与次缺页就是它）；**写时复制**（COW）——`fork` 清 `RW` 位，写时缺页才复制物理页；**聚簇换入**（page clustering）——缺一页时把相邻几页一起读入，把随机小读并成顺序大读。共同点是：把分配、复制、读盘从「建立映射时」推迟到「真正需要时」。VAX/VMS 是早期把分段、分页与 swap 组合得最完整的系统，OSTEP 用整章做案例。

::: errata 关于内存虚拟化的三个误解
1. **「`smaps` 里 `Swap` 是 0，说明没开 swap」**——它只说明这个进程当下没有页被换出。系统有没有 swap 看 `/proc/meminfo` 的 `SwapTotal` 与 `swapon --show`；本机是 4194300 kB、`/swap.img` 4G。
2. **「分段已经淘汰，可以跳过」**——Linux 在 x86-64 上确实把 CS/DS 基址设为 0，但 FS/GS 基址还在用：TLS 与 per-CPU 数据靠它寻址，aarch64 上对应 `TPIDR_EL0`。分段作为「内存管理方案」退场，作为「寻址基址」仍在。
3. **「RSS 就是进程独占的物理内存」**——共享库、共享内存会被多个进程同时计入各自 RSS；要看去重后的 `Pss`。`Rss` 大也可能是文件映射，不等于匿名内存泄漏。
:::

### 1.13.3 小结

内存虚拟化用「分段 → 分页 → 交换」三步还债：分段简单但碎，分页消碎片但页表涨，交换补容量但吃 I/O。`smaps` 的 Size、Rss、Swap 三个数分别回答「映射了多大、真占了多少、换出了多少」。如果只记住一件事：**虚拟大小不是物理占用，RSS 也不是独占**。

**Q3（应用）** 一个服务 RSS 持续上涨、`si/so` 开始非零。你先查什么，怎么判断该加内存还是改参数？

## 1.13.4 并发：理论补全 {#sec-1.13.4}

这一节回答：两个线程抢同一把锁会死锁，可「死锁」「活锁」「饥饿」到底差在哪？为什么临界区只要漏掉一个条件，程序就会一半对一半错，而压测还经常抓不到？

::: preview 先抓住一件事
并发 bug 不是一类，是几类：原子性被破坏、顺序被破坏、互相等待、反复重试、永远排不上。分类的价值在于修法完全不同——加锁治前两类，锁顺序治死锁，退避缓解活锁，公平性才治饥饿。
:::

[1.12](ch12.md) 讲的是 API 与系统调用：`pthread_create`、互斥锁、条件变量、信号量怎么用，最终落到 futex 的哪条路径。这一节不写新 API，只补理论：给并发 bug 分类，并把每个类的边界说清。

先看一次真实的丢更新。两个线程各把同一个全局变量加 1000 万次，期望 2000 万：

```text
$ ./race
unlocked: counter=10157817 (expect 20000000)
locked  : counter=20000000 (expect 20000000)
$ ./race
unlocked: counter=10065998 (expect 20000000)
locked  : counter=20000000 (expect 20000000)
```

无锁版两次都只到一半，加锁版两次都精确。`counter++` 是「读—加—写」三步，两个线程的三步交错，两次加法只落一次结果。这个过程 [1.12.2](ch12.md#sec-1.12.2) 已经拆到指令级，这里只取定义：**竞争**（race）指两个线程访问同一内存位置、至少一个在写、之间没有任何同步；被保护的那段代码叫**临界区**（critical section）。竞争有两种形式：读写竞争（一个读一个写）与写写竞争（两个都写）；只读的并发不算竞争。

::: def 定义 1.13.4 · 临界区的三个条件 {#def-1.13.4}
一个正确的临界区方案必须同时满足：**互斥**（mutual exclusion）——同一时刻最多一个线程在里面；**前进**（progress）——没人占着临界区时，想进的线程必须能在有限步内决定谁进，不能被无关的等待挡住；**有限等待**（bounded waiting）——一个线程提出请求后，在它之前插队的次数有上限。互斥管「不打架」，前进管「不空等」，有限等待管「不饿死」。
:::

**原子性**（atomicity）是这三条的地基：一组操作要么全部生效、要么全部不生效，中间状态对别人不可见。硬件只给很小的原子——一条 `ldxr/stxr` 或 `cas`，锁把这种小原子扩展成一段代码的原子。与之并列的是**顺序性**：两个操作必须按先后被看见。丢了原子性叫原子性违反，丢了顺序叫顺序违反，这是并发 bug 的两大来源。

死锁是第三种，要四个条件同时成立：

| 条件 | 含义 | 本节实验怎么满足 |
|:--|:--|:--|
| 互斥 | 资源一次只能一个线程持有 | 两把 `pthread_mutex_t` |
| 持有并等待 | 拿着一个还想要下一个 | 拿到 A 后再去拿 B |
| 不可剥夺 | 已拿到的不能强行收回 | 普通 mutex 没有超时 |
| 循环等待 | 等待关系连成环 | 一个 A→B，一个 B→A |

把两个线程写成相反顺序，用 `timeout 3` 收场：

```text
t1: lock(a) → sleep → lock(b)
t2: lock(b) → sleep → lock(a)
```

```text
$ timeout 3 ./deadlock; echo "exit=$?"
exit=124
```

三秒里没有一行 `got both` 或 `done`：两个线程各持一把、各等一把，谁都不肯放。`exit=124` 是 `timeout` 到点强杀，不是程序自己退出。修法最常用的是打破循环等待——给锁编号，永远按升序拿；[1.12.12](ch12.md#sec-1.12.12) 的进度图会把它画成「禁止区」。

**活锁**（livelock）与**饥饿**（starvation）常被混进死锁。活锁是线程都在跑、却互相让步到无法推进：两人在窄路相遇，同时向左让、再同时向右让，谁也没过去；CPU 是满的，进度是零。饥饿是别人都在推进，某个线程永远排不上：非公平锁下新人不断插队，老线程等到天荒地老。三者可以用一张表分开：

| 类型 | 谁在跑 | 有没有进展 | 典型修法 |
|:--|:--|:--|:--|
| 死锁 | 都不跑 | 无 | 锁顺序、`trylock` + 回滚 |
| 活锁 | 都在跑 | 无 | 随机退避、换策略 |
| 饥饿 | 别人在跑 | 有人永远没有 | 公平锁、优先级老化 |

### 1.13.4 小结

并发理论只做一件事：把「感觉不对劲」变成可命名的类别。原子性与顺序性被破坏是数据竞争的两副面孔；死锁要四个条件同时成立；活锁是「都在动、都没前进」；饥饿是「有人在前进、有人永远轮不到」。如果只记住一件事：**先分类，再修——加锁治不了饥饿，退避也治不了死锁**。

::: method 即时自测 · 1.13.4
**Q1（记忆）** 写出临界区的三个条件，各用一句话解释。

**Q2（辨析）** 两个线程各持一把锁互相等待，和一个线程反复 `trylock` 失败后重试，分别属于哪一类？修法有什么不同？

**Q3（应用）** 两个线程用 CAS 更新同一链表，失败就随机睡几微秒再重试；监控看到 CPU 很高、队列长度不降。属于哪一类？先改什么？

::: sol 答案
**A1** 互斥：同一时刻最多一个线程在临界区；前进：临界区空着时，想进的线程必须能决定谁进；有限等待：一个线程的请求不能被无限次插队。

**A2** 前者是死锁（循环等待，谁都不跑），修法是统一锁顺序或用 `trylock` 回滚；后者是活锁（都在跑、都没进展），修法是改变退避策略或换成阻塞锁。

**A3** 更像活锁：线程都在重试、CPU 很忙，但队列长度不降说明没有净进展。先把随机退避改成指数退避或加锁，再用「完成计数是否增长」确认真的有进展。
:::

## 1.13.5 持久化：设备、磁盘、RAID 与文件系统 {#sec-1.13.5}

这一节回答：`write()` 返回成功时，数据停在哪一层？随机读的十几毫秒花在哪？断电落在 `write` 与 `rename` 之间，文件为什么还能保持旧版本？

::: preview 先抓住一件事
持久化是四层流水线：设备搬字节，块层排队，文件系统组织「名字 → inode → 块」，日志与 `fsync` 保证崩溃后自洽；每往下一层，延迟涨一个量级。
:::

[1.10.6](ch10.md#sec-1.10.6) 跟过 `write` 到磁盘的路径，[1.10.15](ch10.md#sec-1.10.15) 量过 page cache 与 `fsync` 的边界。这一节补设备、磁盘、RAID、文件系统四块。

### I/O 设备与磁盘

设备通过数据、状态、控制三类寄存器与 CPU 交互。大块数据用 DMA 搬运，完成后发中断；小命令走端口 I/O 或 MMIO。

::: def 定义 1.13.5 · 块设备与字符设备 {#def-1.13.5}
**字符设备**按字节流读写，命令多走 `ioctl`，例如 `/dev/null`；**块设备**按固定块读写，请求先经块层排队再交给驱动，例如 `/dev/sda`。文件系统只能建在块设备上。
:::

### 设备驱动模型：寄存器、DMA 与中断 {#sec-1.13.5.1}

操作系统看设备只看三样：**寄存器**、**内存映射**（MMIO/PIO）、**中断**。驱动把「读写文件」翻译成「写寄存器 + 等中断 + 搬 DMA」：初始化时 `ioremap` 映射 BAR、申请 IRQ；设备 DMA 写入内存后触发中断，上半部确认，下半部（softirq/NAPI）收尾。对上层注册 `struct file_operations`，对总线注册 `probe/remove`；设备节点由 udev 按 sysfs 的 `dev` 属性创建。

::: errata 设备驱动的两个坑
1. **`ioremap` 的地址不能直接解引用**：必须用 `readl/writel`，否则编译器/CPU 可能重排或合并访问。
2. **中断上下文不能睡眠**：`kmalloc(GFP_KERNEL)`、`mutex_lock`、`copy_to_user` 都可能睡眠；改用 `GFP_ATOMIC`、自旋锁，或推给 workqueue。
:::

### 磁盘时间账：寻道、旋转与传输 {#sec-1.13.5.2}

一次磁盘 I/O 的时间是 `T_queue + T_seek + T_rotation + T_transfer`。7200 RPM 机械盘的随机 4 KiB 读约 12 ms：排队 0–几十 ms、寻道 4–10 ms、旋转平均半圈 4.17 ms、传 4 KiB 约 0.04 ms，IOPS ≈ 83；顺序读 100 MB/s 时 4 KiB 只要 0.04 ms。**随机与顺序差两个数量级**，这是 WAL、LSM tree、日志结构文件系统存在的根本原因。

先看实测读数：

```text
# VM 实测 · Ubuntu 24.04.5 / aarch64 / 内核 7.0.0-38
$ lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS,ROTA,SCHED
sda      64G disk                 0 mq-deadline
├─sda1    1G part vfat /boot/efi   0 mq-deadline
└─sda2 62.9G part ext4 /           0 mq-deadline
$ df -hT /; df -i /
/dev/sda2 ext4 62G 25G 34G 43% /
/dev/sda2 4128768 395567 3733201 10% /
```

`ROTA=0`；`/sys/block/sda/queue/` 里 `scheduler = none [mq-deadline]`、`nr_requests = 64`。

`fio` 未安装，`hdparm -t /dev/sda` 无权限，改用 `dd` 的 `O_DIRECT` 与自写的 `pread` 程序：

```text
$ dd if=/dev/zero of=/tmp/lab1c13_dd.bin bs=1M count=256 oflag=direct conv=fsync
268435456 bytes copied, 0.0832 s, 3.2 GB/s
$ dd if=/tmp/lab1c13_dd.bin of=/dev/null bs=1M iflag=direct
268435456 bytes copied, 0.0445 s, 6.0 GB/s
$ ./lab1c13_rand /tmp/lab1c13_dd.bin 2000
rand 4KiB x2000: p50=0.091 p95=0.121 p99=0.135 max=0.151 ms
IOPS=10954
```

这不是磁盘的物理速度：`O_DIRECT` 只绕过 guest 的 page cache，绕不过宿主机缓存；这台 VM 的 I/O 路径短，不能否定 12 ms 的机械盘模型。

::: errata 磁盘时间账的误读
1. **「12 ms 是所有盘的随机读延迟」**——它是 7200 RPM 机械盘在 100 MB/s 下的模型值；先读 `rotational` 与 `scheduler`，再决定用哪套模型。
2. **「`rotational=0` 就一定是 SSD」**——这是设备/驱动自报属性，虚拟盘也可以填 0。
:::

### 磁盘几何与经典调度 {#sec-1.13.5.3}

机械盘由**盘片**组成，每个盘片上下两个**磁头**；盘面同心圆是**磁道**，切成**扇区**；同半径的磁道合成**柱面**。换磁道要移动磁头（毫秒级），同柱面换磁头几乎免费，所以「按块号聚簇」约等于「按柱面聚簇」。

三个几何事实：换磁道要 4–10 ms，同柱面换盘面几乎免费；旋转平均再等半圈 4.17 ms；外圈磁道更长，顺序吞吐更高。


经典调度可用 6 个请求手算。磁头在 40（盘 0–99），到达序 60、32、75、20、55、10：

| 算法 | 磁头轨迹 | 总移动 | 边界 |
|:--|:--|--:|:--|
| FIFO | 40→60→32→75→20→55→10 | 226 | 对到达公平，对磁头最不友好 |
| SSTF | 40→32→20→10→55→60→75 | 95 | 每步选最近；远处请求可能被饿死 |
| SCAN | 40→55→60→75→折返→32→20→10 | 100 | 扫到头再折返，无饥饿 |

现代 blk-mq 不再用这些名字，但本机 `[mq-deadline]` 的「按扇区排序 + 读过期 FIFO」就是 SCAN 加防饥饿，见 [3.13.3](../part3/ch13.md#sec-3.13.3)。

### RAID

| 级别 | 最少盘 | 容量利用率 | 容错 | 特点 |
|:--|--:|--:|:--|:--|
| RAID 0 | 2 | 100% | 无 | 条带化，快，坏一盘全丢 |
| RAID 1 | 2 | 50% | 1 盘 | 镜像，读性能好，成本高 |
| RAID 5 | 3 | (n−1)/n | 1 盘 | 分布式校验，写有 read-modify-write |
| RAID 6 | 4 | (n−2)/n | 2 盘 | 双校验，重建更安全 |
| RAID 10 | 4 | 50% | 每组 1 盘 | 镜像 + 条带，性能与可靠性折中 |

RAID 5 的随机 4 KiB 写要读旧数据与旧校验（2 读 2 写），RAID 6 再多一份；整条带写才能省掉读。RAID 0 无冗余，RAID 1/10 靠镜像，RAID 5/6 靠校验，重建期间风险上升。

RAID 不是备份：它挡「盘坏」，不挡误删、勒索和火灾。RAID 5 还有写洞——断电时数据与校验只写了一半，重启后阵列不自洽。本机没有多余块设备可做 RAID，重建时长与写洞表现**未实测**。

### 文件系统

文件系统靠四样东西把块设备变成「文件/目录」：**superblock**（块大小、inode 数、空闲块）、**inode**（类型、权限、大小、块指针）、**位图**（inode 与数据块的分配）、**目录**（名字 → inode 号）。

FFS 把文件与其 inode、目录放在同一柱面组以减少寻道；ext4 用 extent 代替多级间接块。本机根文件系统是 `/dev/sda2` 上的 ext4，`df -i` 显示 4128768 个 inode、已用 10%。

**逻辑连续不等于物理连续**：一个文件逻辑上从 0 到 N 块连续，物理上可能分成多段 extent；`filefrag -v` 是比 `df` 更直接的验证工具。

### 崩溃一致性

「创建文件」要分配 inode、写目录项、更新位图；断电落在中间，会留下没人引用的 inode 或悬空目录项。**FSCK** 交叉验证三张表，把不一致改回去；它修的是**结构**，不是**语义**。**日志**（journaling）先把事务写入日志区，提交后再改主文件系统，崩溃后重放或丢弃。ext4 的 `data=ordered` 保证数据先于元数据落盘；日志坏了仍靠 `e2fsck`，见 [0.10.11](../part0/ch10.md#sec-0.10.11)。

应用层的原子替换是「写临时文件 → `fsync` → `rename` → `fsync` 目录」四步（省略错误检查）：

```c
int fd = open(tmp, O_WRONLY|O_CREAT|O_TRUNC|O_CLOEXEC, 0644);
write(fd, buf, len);
fsync(fd);          /* 数据落到介质 */
close(fd);
rename(tmp, path);  /* 原子换名 */
int dfd = open(".", O_RDONLY|O_DIRECTORY);
fsync(dfd);         /* 目录项也持久 */
```

四个崩溃点：`rename` 前，旧文件完好、临时文件可能残留；`rename` 原子，看不到半个文件；`rename` 后、目录 `fsync` 前，内容在但目录项可能回退；目录 `fsync` 后，新名字持久。`fsync` 只保证文件，目录项要单独 `fsync` 目录。

这台 VM 上量了四步的耗时（`lab1c13_atomic`，`strace -T` 复核）：

```text
$ ./lab1c13_atomic /tmp/lab1c13_atomic.out two durable
durable write=0.007 ms fsync=0.896 ms rename=0.021 ms fsync_dir=0.522 ms
$ strace -T -e trace=write,fsync,rename ./lab1c13_atomic ... durable
write(3, "three", 5) = 5 <0.000043>
fsync(3)             = 0 <0.000647>
fsync(3)             = 0 <0.000553>
```

`write` 只要 7 微秒就返回，`fsync` 要 0.5–0.9 毫秒——**`write` 返回只代表数据进了 page cache，不代表落盘**。VM 无法真的断电，这里验证的是顺序与代价；掉电后的介质状态只能由日志协议保证。

### 闪存与 LFS

NAND 闪存按页写、按块擦，不能原地覆盖。FTL 负责映射、垃圾回收与磨损均衡，写放大放大实际写入量，TRIM 标出无效块。LFS 把随机写变成顺序追加：数据、inode、imap 攒够一段再写下盘，固定位置只留 checkpoint；清理靠 segment summary 与 imap 判断死活。它与 [1.13.11](#sec-1.13.11) 的 redo 日志不同：数据本就在日志里，恢复只需找到一致起点。







清理策略决定 LFS 的实际性能：只挑「利用率最低」的段，反复清理的其实是正在被写的热段——刚追加、还没填满，利用率天然低，清理后马上又写脏；按「年龄 + 利用率」折中更稳。这与 SSD 的 FTL 垃圾回收是同一类问题，只不过一个在文件系统层，一个在设备层。

### 1.13.5 小结

持久化四层各有承诺：块层排队，文件系统保证名字、inode、块自洽，日志保证崩溃后可回一致点，`fsync` 才把数据钉到介质。RAID 挡盘坏，备份挡误删，日志挡断电。

::: method 即时自测 · 1.13.5
**Q1（辨析）** 程序 `write()` 返回成功、`rename()` 也返回成功，但没 `fsync` 目录。断电后可能看到什么？

**Q2（应用）** 一台数据库写入延迟偶发升高，`w_await` 上升而 `%util` 不高。先查哪一层？给两条命令。

::: sol 答案
**A1** 内容可能已落盘，但目录项可能仍是旧名字：新名不保证可见，旧名可能还在，临时文件可能残留。补 `fsync` 目录。

**A2** 先怀疑设备/块层：`w_await` 高、`%util` 不高常见于单请求延迟大。查 `scheduler` 与 `rotational`；`strace -T -e trace=fsync` 看是否在等 `fsync`。
:::

## 1.13.6 李治军 8 个实践项目的实现侧写 {#sec-1.13.6}

这一节回答：Linux 0.11 那样一个几千行的小内核，是如何把启动、系统调用、进程、切换、同步、内存、换页、驱动八件事各写一遍的？读大内核代码容易迷路，读这八段实现则能看见每个机制的骨架。

::: preview 先抓住一件事
八个项目是一条从引导扇区到文件系统的装配线：每一步只增加一层机制，每层都有可观测的验收证据。把「结构 → 路径 → 证据」对齐，概念就变成可调试的代码。
:::

李治军的《操作系统原理、实现与实践》以 Linux 0.11 为参照组织这八个项目。原书是扫描版，本节只按项目目录与 Linux 0.11 的结构核对，不引原书原句与页码。每个项目给出「目标 / 结构 / 路径 / 证据」，是从概念到可改代码的侧写。

### 项目 1 · 控制操作系统启动

- **目标**：从 BIOS 交出控制权开始，把内核加载到内存并进入 32 位保护模式。
- **关键结构**：`bootsect.s`（512 字节引导扇区，加载到 `0x7c00`）、`setup.s`（取硬件参数、关中断、开 A20、建 GDT、进保护模式）、`head.s`（建页表、设栈、跳 `main`）。
- **实现路径**：BIOS 把第一扇区读到 `0x7c00` 并跳转；`bootsect` 用 `int 0x13` 把 `setup` 和 `system` 读到 `0x9000`/`0x10000`；`setup` 把 `system` 搬到 `0x0000` 附近，加载 GDT，设置 `%cr0` 的 PE 位；`head.s` 建立恒等映射页表，开分页，调用 `main`。
- **验收证据**：屏幕出现自定义字符串；`gdb` 在 `0x7c00` 下断点，`%cr0` 的 PE 位为 1，`$eip` 已在 32 位代码段。

### 项目 2 · 添加系统调用

- **目标**：在 `int 0x80` 入口上增加两个系统调用 `iam()` 和 `whoami()`。
- **关键结构**：`sys_call_table`（函数指针数组）、`NR_syscalls`（表长）、`include/unistd.h`（调用号）、`kernel/system_call.s`（入口汇编）、`sys.c`（实现）。
- **实现路径**：在 `unistd.h` 加 `__NR_iam`/`__NR_whoami`；在 `sys.c` 写 `sys_iam`/`sys_whoami`，用 `get_fs_byte`/`put_fs_byte` 在用户态与内核态之间拷字符串；把函数指针填进 `sys_call_table`；用户态用 `_syscall1` 宏展开 `int 0x80`。
- **验收证据**：`iam("alice")` 后 `whoami(buf)` 得到 `alice`；`strace` 看不到，`gdb` 能在 `system_call` 停；越界返回 `-ENOSYS`。

### 项目 3 · 多进程

- **目标**：实现 `fork`，让一个进程变成两个，父子各自返回不同值。
- **关键结构**：`task_struct`（pid、状态、页目录基址、TSS、内核栈）、`task[]`（进程表）、`copy_process`（复制 task、页表、文件表）、`schedule`。
- **实现路径**：`fork` 系统调用进入内核后，`copy_process` 分配新 `task_struct`，复制父进程页目录（虚拟地址到物理地址的映射表）并按 COW 标记只读；复制文件描述符表（进程打开文件的编号表）；设置子进程 `eax=0`、父进程 `eax=子 pid`；把子进程状态设为 `TASK_RUNNING`，挂入运行队列；返回用户态。
- **验收证据**：父子各打印自己的 pid；父进程写变量后子进程看不到（COW 生效）；子进程 `exit` 后父进程 `wait` 能回收。

### 项目 4 · 基于内核栈完成进程切换

- **目标**：不依赖 TSS 的 `ljmp`，用内核栈保存/恢复上下文，实现两个进程交替执行。
- **关键结构**：每个进程的内核栈、`switch_to`（保存 `%ebp/%esp` 等）、`schedule`（选下一个）、`TSS`（只在特权级切换时用）。
- **实现路径**：`switch_to` 把当前进程的 `%esp` 存进 `task_struct->kernel_stack`，从下一个任务的 `kernel_stack` 恢复 `%esp`，再 `ret` 到它上次被切走的位置；`schedule` 按优先级/时间片选任务；时钟中断触发调度。
- **验收证据**：两个进程输出交替；`gdb` 在 `switch_to` 处看到 `%esp` 变化；局部变量在切换后保持；不用 TSS 也能完成同特权级切换。

### 项目 5 · 信号量的实现与应用

- **目标**：在内核里实现 `sem_t` 与 `down/up`，并用它解决生产者-消费者。
- **关键结构**：`sem_t`（value + 等待队列）、`sleep_on`/`wake_up`（等待队列）、`schedule`（睡眠时让出 CPU）。
- **实现路径**：`down` 关中断检查 value，>0 则减一，否则把当前任务挂到等待队列并 `sleep_on`；`up` 关中断加一，若等待队列非空则 `wake_up` 唤醒一个；用户态用共享缓冲区 + 两个信号量（empty/full）验证。
- **验收证据**：生产/消费无丢失、无越界；满时生产者睡、空时消费者睡；去掉信号量能复现竞态。

### 项目 6 · 地址映射与共享

- **目标**：实现页表映射与共享内存，让两个进程看到同一块物理页。
- **关键结构**：页目录/页表、`do_no_page`（缺页处理）、`get_free_page`、`put_page`、`mmap`/`shmat` 的简化版。
- **实现路径**：为共享区分配物理页，把两个进程的页表项指向同一 PFN，设置 `P/RW/US`；缺页时 `do_no_page` 判断是匿名页、文件页还是共享页；`fork` 时对共享页不复制，只增加引用计数。
- **验收证据**：A 写共享区，B 立刻读到；`pagemap` 验证 PFN 相同；`fork` 后 COW 与共享页行为不同。

### 项目 7 · 换入/换出

- **目标**：物理内存不足时把页换到 swap 分区，缺页时再换入。
- **关键结构**：swap 设备/分区、页表 present 位、`swap_in`/`swap_out`、`get_free_page`、LRU 链表。
- **实现路径**：`get_free_page` 找不到空闲页时，选一个冷页，若 dirty 则写 swap，记录 swap 槽号，清 present 位；缺页异常时根据 PTE 的 swap 信息读回，更新页表；用 Clock/LRU 选择被换出的页。
- **验收证据**：分配超过物理内存的匿名页，程序仍能跑；`/proc/vmstat` 的 `pswpin/pswpout` 增加；换出页再次访问触发缺页并恢复；没有数据损坏。

### 项目 8 · 设备驱动

- **目标**：为块设备写一个最小驱动，让文件系统能读写磁盘。
- **关键结构**：`request_queue`（请求队列）、`hd_request`、`outb/inb`（端口 I/O）、中断处理程序、`file_operations`。
- **实现路径**：初始化时探测设备、注册中断；`read/write` 把请求封装成 `request` 挂入队列；`do_hd_request` 用 `outb` 发命令，中断到来时读状态、拷数据、唤醒等待者；上层通过 `bread`/`bwrite` 访问块。
- **验收证据**：`dd` 读写磁盘镜像内容一致；`iostat` 看到 I/O；拔掉/超时注入后驱动返回错误而不是挂死；中断计数增加。

| 项目 | 对应 Linux 机制 | 最小可观测证据 |
|:--|:--|:--|
| 1 启动 | `bootsect`/`setup`/`head`、页表初始化 | `%cr0.PE=1`、`dmesg` 第一行 |
| 2 系统调用 | `sys_call_table`、`int 0x80`/`syscall` | 调用号、返回值、`-ENOSYS` |
| 3 多进程 | `copy_process`、COW、`task_struct` | 父子 pid、`ps`、COW 写时复制 |
| 4 切换 | `switch_to`、内核栈、`schedule` | `%esp` 变化、输出交替 |
| 5 同步 | `sem_t`、等待队列、`sleep_on` | 无丢失、睡眠状态 |
| 6 映射共享 | 页表、`do_no_page`、PFN | 共享写可见、`pagemap` |
| 7 换入换出 | swap、PTE present、LRU | `pswpin/pswpout`、缺页恢复 |
| 8 驱动 | `request_queue`、`outb/inb`、中断 | `dd` 校验、中断计数 |

这 8 个项目与第 3 篇的内核章节一一对应：启动对应 [3.2](../part3/ch02.md)，系统调用对应 [3.3](../part3/ch03.md)，多进程/切换对应 [3.4](../part3/ch04.md)、[3.5](../part3/ch05.md)，同步对应 [3.11](../part3/ch11.md)，内存对应 [3.7](../part3/ch07.md)–[3.10](../part3/ch10.md)，驱动对应 [3.14](../part3/ch14.md)。第 1 篇讲「是什么」，第 3 篇讲「Linux 怎么做」，项目让你「写一遍」。

::: errata 读小内核的两个坑
1. **把 Linux 0.11 当现代内核**：0.11 是单核、无 RCU/cgroup，项目 5 的信号量只够教学，不能照搬到生产。
2. **只改代码不看证据**：`fork` 返回 0 不代表子进程真跑起来，要 `ps` 看到两个进程、`switch_to` 里 `%esp` 真的换了。
:::

### 1.13.6 小结

八个项目是同一套循环：先找数据结构（`task_struct`、`sys_call_table`、页表、`request_queue`），再找入口（中断、系统调用、缺页），最后找可观测证据。从小内核读起的好处是每一步都能停在断点上；读 Linux 时，同样的三问依然适用。

## 1.13.7 从 OSTEP 到 Linux：机制与策略的对照 {#sec-1.13.7}

这一节回答：读完 OSTEP 的进程、地址空间、调度与持久化模型，落到 Linux 时该找哪些结构体与函数？哪些地方 Linux 与教科书不同，为什么？

::: preview 先抓住一件事
OSTEP 讲「任何操作系统都必须解决的机制」，Linux 是「一组具体策略加历史包袱」。对照时先认机制，再看策略，最后看 Linux 多出来的工程约束：兼容、并发与规模。
:::

OSTEP 用「假设 → 机制 → 策略 → 作业」讲通用操作系统；Linux 把这些概念落到具体结构体与调度器。读 OSTEP 时，把每一章钉到下面这张表，就不会觉得「学完不知道怎么用」：

| OSTEP 概念 | 通用机制 | Linux 落点 | 本书 |
|:--|:--|:--|:--|
| 进程抽象 | `task_struct` + 地址空间 + fd 表 | `fork/clone`、`copy_process` | 1.8、3.1 |
| 受限直接执行 | 用户/内核态、trap、定时器 | `syscall` 入口、`sysret`、`int 0x80` | 1.8.3、3.3 |
| 调度策略 | MLFQ/比例份额/多处理器 | CFS/EEVDF、`sched_entity`、调度域 | 1.13.2、3.5/3.6 |
| 地址空间 | 页表 + TLB + 缺页 | `mm_struct/vma`、四级页表、`handle_mm_fault` | 1.9、3.8 |
| 分段 | 基址/界限 | x86 段只用于兼容；Linux 以分页为主 | 1.13.3、1.9 |
| 空闲空间管理 | 隐式/显式/分离链表 | slab/slub（按对象大小预切的内存池）、buddy、`kmalloc` 大小类 | 1.9.6、3.7/3.9 |
| 交换 | swap 区、present 位 | `swap_info_struct`、`do_swap_page`、zswap | 1.13.3、3.10 |
| 并发/锁 | 原子、自旋、睡眠锁 | `spinlock/mutex/rwsem/RCU` | 1.12、3.11 |
| 持久化/I/O | 设备、磁盘、RAID、FS | `block_device`、`blk-mq`、VFS（文件系统之上的统一接口层）、ext4/XFS | 1.13.5、3.12–3.14 |
| 崩溃一致性 | FSCK/日志 | jbd2、`fsync`、`REQ_PREFLUSH/FUA` | 1.13.11、3.12/3.13 |
| 分布式文件系统 | NFS/AFS | NFS 客户端、`ESTALE`、close-to-open | 3.12.8 |

这张表也是读源码的入口：先问「这是 OSTEP 的哪个机制」，再找对应的 `struct` 与函数，比从 `init/main.c` 往下读更快。

三处对照最能看出「模型 ≠ 实现」。第一，**MLFQ 与 CFS/EEVDF**：OSTEP 用多级队列加时间片近似公平，Linux 用 `vruntime` 红黑树（EEVDF 之后换成虚拟截止期）；本机 `/proc/<pid>/sched` 只有 `se.slice`，没有 `se.deadline`，说明字段名会随版本漂移，读文档要认内核版本。第二，**分段与分页**：OSTEP 花一章讲 base/bound，x86-64 的分段只剩兼容用途，Linux 的地址翻译主体是四级页表，字段展开见 [1.9](ch09.md)；本节的表只告诉你「概念落在哪」，不重复页表推导。第三，**日志**：教科书讲 redo/undo 两种协议，Linux 用 jbd2，并把持久化语义拆给 `fsync` 与 `REQ_PREFLUSH/FUA`；[1.13.11](#sec-1.13.11) 枚举崩溃点，[1.13.5](#sec-1.13.5) 给的是应用侧写法。

机制与策略的分界要一直带着：机制回答「能不能做」，策略回答「先做谁」。`clone` 的 flag 决定共享哪些资源，这是机制；`sched_setscheduler` 选 FIFO、RR 还是 deadline，这是策略。调参只能改策略，改不了机制；反过来，机制缺失时策略再优也没用——没有页表，LRU 无从谈起。

举一个查表的例子：OSTEP 说进程地址空间由 text、data、heap、stack 组成；在 Linux 里执行 `cat /proc/self/maps`，会看到若干 `r-xp`、`rw-p` 段和 `[heap]`、`[stack]` 标注，它们都由 `vm_area_struct` 描述，并不保证物理连续。再用 `pmap -x` 对比 RSS 与 PSS，就知道「地址空间」是虚拟的账本，「内存占用」是页表实际指向的物理页（细节在 [1.9](ch09.md)）。这类一步到位的对照，比背结构体名有用。

还要记住 Linux 相对教科书的三条工程差异：一是**兼容**，`int 0x80` 与 `syscall`、32 位与 64 位 ABI 并存；二是**并发**，RCU 让读路径几乎无锁，代价是写者要等宽限期；三是**规模**，调度域、NUMA、cgroup 都是为了多核与多租户，OSTEP 的单核模型只是起点。

::: errata 对照时最容易踩的两个坑
1. **把 OSTEP 的示例数字当 Linux 观测值**：MLFQ 的时间片、OPT 的最优命中率、50% 的内部碎片都是模型参数；Linux 的实际值要从 `/proc`、`/sys` 读，不能从教材抄。
2. **把「Linux 有某个结构体」当成「教科书机制被实现」**：`task_struct` 里有 `sched_entity`，不代表 MLFQ 存在；先看调度类注册了哪些 `sched_class`，再谈策略。
:::

### 1.13.7 小结

OSTEP 给的是机制清单，Linux 给的是带版本的实现。对照的正确姿势是「概念 → 结构体 → 入口函数 → 可观测证据」四步；差异不是错误，多半是兼容、并发或规模带来的工程选择。这张表不必背：查一次、跑一次、记下内核版本，比读三遍更牢。模型用来提问，`/proc` 用来回答；先对照，再上机验证，这一步不能省。

::: method 即时自测 · 1.13.7
**Q1（辨析）** 为什么说「Linux 的 CFS 就是 MLFQ 的实现」不准确？

**Q2（应用）** 想确认本机调度器是否用了 EEVDF，你会看哪两个地方？看到什么才算证据？

::: sol 答案
**A1** MLFQ 靠多级队列与优先级升降近似公平，CFS 用 `vruntime` 红黑树直接逼近公平份额，EEVDF 又换成虚拟截止期；数据结构和公平定义都不同，只能说是同类目标的不同策略。

**A2** 先看 `/sys/kernel/debug/sched/` 或 `/proc/<pid>/sched` 的字段（本机有 `se.slice`、无 `se.deadline`），再看 `sched_class` 列表或内核版本说明；字段与调度类都对上，才算证据。
:::
:::

## 1.13.8 进程、地址空间与分配器：机制补全 {#sec-1.13.8}

这一节回答：进程状态在 `ps` 里为什么既有 `R` 又有 `S`、`D`？页表项那十几个位各自负责什么？`malloc` 与内核分配器面对的是不是同一个问题？

::: preview 先抓住一件事
机制补全只做三件事：把进程控制块的字段按生命周期分组，把页表项按「谁改」分组，把空闲空间管理按「分裂与合并」分组。分完组，字段就不再需要死记。
:::

[1.8](ch08.md) 讲了进程与系统调用的用户态接口，[1.9](ch09.md) 讲了地址空间与页表；本节不重复推导，只补 OSTEP 第 4–6、14–23 章那种「内核视角」：同样的概念，在内核里由哪些字段维护。

### 进程状态机与 PCB

OSTEP 4.4 把进程状态简化为三个：**运行**（Running，占着 CPU）、**就绪**（Ready，可运行但在队列里等）、**阻塞**（Blocked，等 I/O 或事件）。Linux 在此基础上多了「新建/僵尸/停止」，`ps` 的 `STAT` 列就是这套状态机的外显：

| OSTEP 状态 | Linux `task_struct->state` | `ps` | 迁移条件 |
|:--|:--|:--|:--|
| 就绪 | `TASK_RUNNING`（在 runqueue 上） | `R` | 被调度器选中 → 运行 |
| 运行 | `TASK_RUNNING`（在 CPU 上） | `R` | 时间片耗尽 → 就绪；等事件 → 阻塞 |
| 阻塞 | `TASK_INTERRUPTIBLE`/`TASK_UNINTERRUPTIBLE` | `S`/`D` | 事件完成或信号 → 就绪 |
| — | `__TASK_STOPPED` | `T` | `SIGCONT` → 就绪 |
| — | `EXIT_ZOMBIE` | `Z` | 父进程 `wait` 回收后消失 |

「就绪」与「运行」在 `state` 字段里是同一个值，区别只在「是否在 CPU 上」；这是读内核代码时最容易迷糊的一处。真正的区分靠 runqueue 与 `on_cpu` 标志。

PCB（Linux 的 `task_struct`）不是「一个进程一份简单记录」，而是几 KB 的结构，字段按生命周期分组：

| 字段 | 内容 | 谁维护 | 何时变 |
|:--|:--|:--|:--|
| `state`、`flags` | 状态、PF_* 标志 | 调度器/信号 | 每次状态迁移 |
| `pid`、`tgid` | 线程 ID、线程组 ID（=进程 ID） | `copy_process` | 创建时固定 |
| `mm`、`active_mm` | 用户地址空间；内核线程借用上一个 `mm` | `exec`/`fork`/切换 | `exec` 换新 `mm` |
| `files` | fd 表（`files_struct`），带引用计数 | `open/close/dup` | 每次 fd 操作 |
| `fs` | 根目录、当前目录、`umask` | `chdir/chroot/umask` | 路径解析相关 |
| `cred` | uid/gid、capabilities | `setuid` 等 | 凭证变更 |
| `sighand`、`signal` | 信号处理表、pending/blocked 集合 | 信号子系统 | `sigaction`/投递 |
| `thread` | 切换现场：`sp`、`ip`、FPU 状态、`fsbase` | `switch_to` | 每次上下文切换 |
| `sched_entity` | `vruntime`、权重、调度类 | CFS/EEVDF | 每次运行/入队 |
| `nsproxy` | 命名空间（mnt/pid/net/uts/ipc/user/cgroup） | `clone/unshare` | 创建容器时 |

`fork` 复制的是这张表加页表；`clone` 按标志选择共享哪些部分（`CLONE_VM` 共享地址空间、`CLONE_FILES` 共享 fd 表、`CLONE_THREAD` 同线程组），线程就是「共享了 mm 与 files 的 task」。这解释了为什么「线程」在 Linux 里不是独立概念：它只是 `clone` 参数不同的进程。

### 受限直接执行的两个问题

OSTEP 第 6 章把「虚拟化 CPU」归结为两个问题，每个问题对应一套硬件机制：

| 问题 | 用户态想做什么 | 硬件机制 | 内核入口 |
|:--|:--|:--|:--|
| 受限操作 | 读写文件、发网络包 | 特权级（ring 3 → ring 0）、`syscall` 指令 | `entry_SYSCALL_64` → `do_syscall_64` |
| 进程切换 | 一直占着 CPU | 定时器中断、`int 0x80`/`syscall` 主动让出 | 中断处理 → `schedule()` |

协作式（cooperative）切换靠进程主动 `yield`，一个死循环就能锁死系统；抢占式（preemptive）靠定时器中断强制收回 CPU。现代通用 OS 全是抢占式，代价是「任何指令边界都可能被切走」，所以并发程序必须假设「两条指令之间可能发生任何事」。

### 页表项：10 个位决定一次翻译

x86-64 四级页表把 48 位虚拟地址切成 9+9+9+9+12，每级 512 项、每项 8 字节，一个页表页正好 4 KiB。PTE 的低 12 位是标志：

| 位 | 名称 | 含义 | 谁改 |
|--:|:--|:--|:--|
| 0 | `P` | 存在；为 0 触发缺页 | 内核 |
| 1 | `RW` | 可写；为 0 时写触发保护缺页（COW 靠它） | 内核 |
| 2 | `US` | 用户态可访问；为 0 只有内核能碰 | 内核 |
| 3 | `PWT` | 写穿透（页表级缓存策略） | 内核 |
| 4 | `PCD` | 禁止缓存 | 内核 |
| 5 | `A` | 已访问；Clock/LRU 近似用它 | **CPU** 置位，内核清除 |
| 6 | `D` | 脏页；决定换出时是否要写回 | **CPU** 置位，内核清除 |
| 7 | `PS` | 大页（2 MiB/1 GiB） | 内核 |
| 63 | `NX` | 不可执行（W^X 的基础） | 内核/链接器 |

这张表解释了三件事：COW 是「清 `RW` 位 + 写时缺页」；页替换的 Clock 算法靠 `A` 位；`mprotect` 改的就是这些位。第五级页表（LA57）把虚拟地址扩到 57 位，多一级 9 位索引，Linux 4.14 起在支持的 CPU 上可用。

### 空闲空间管理：从 first-fit 到 slab

`malloc` 与内核的页分配器面对同一个问题：一堆空洞，怎么切、怎么并。OSTEP 第 17 章的四条基本策略至今仍是教科书答案：

| 策略 | 选块规则 | 优点 | 缺点 |
|:--|:--|:--|:--|
| first-fit | 第一个够大的 | 快 | 低地址碎片多 |
| best-fit | 最小的够大的 | 省空间 | 遍历全表；留下大量小碎片 |
| worst-fit | 最大的 | 剩余块大、可复用 | 大块很快被切碎 |
| next-fit | 从上次位置继续 | 分布均匀 | 大块难找 |

分配器还要处理**分裂**（split，切大块）与**合并**（coalesce，释放时与相邻空闲块合并），合并需要边界标记（boundary tag）记录前一块大小。内核里更常用 **buddy**（按 2 的幂分裂/合并，O(log n)，内部碎片最多 50%）与 **slab/slub**（按对象大小缓存，避免反复构造/析构）。用户态 glibc 的 `malloc` 用 arena + bin + tcache，小对象走 tcache 无锁路径，大对象 `mmap` 直接向内核要页。

::: errata 关于「进程与内存」的四个误解
1. **「`fork` 复制了父进程的内存」**——只复制页表并清 `RW` 位，物理页共享；写时缺页才复制一页。所以 `fork` 后立刻 `exec` 的程序，几乎不产生内存复制。
2. **「虚拟地址就是物理地址减一个偏移」**——四级页表逐级翻译，每级都可能缺页；连续虚拟地址不保证连续物理地址，大页（2 MiB）只是减少层级。
3. **「`free` 会把内存还给系统」**——glibc 的 `free` 多数时候只把块放回 bin；只有 `mmap` 的大块或 `malloc_trim` 才归还。进程 RSS 不降不等于泄漏。
4. **「进程状态 `R` 就是在跑」**——`R` 包含「在 runqueue 上等 CPU」；判断是否真在跑要看 `/proc/<pid>/stat` 的第 39 字段（CPU 号）两次采样是否变化。
:::

### 1.13.8 小结

三张表回答三个问题：`state` 与 runqueue 回答「进程现在能不能跑」，PTE 的位回答「这次访问能不能过、谁改的」，分配器的 bin 与 buddy 回答「空闲块怎么切、怎么并」。内核不维护「进程」「内存」两个抽象名词，只维护字段与链表；看懂字段的更新时机，就看懂了一半机制。

## 1.13.9 调度模拟：彩票、步长与 CFS 的公平性 {#sec-1.13.9}

这一节回答：按比例分 CPU 时，彩票调度为什么短时间窗口里抖得厉害？步长调度凭什么把误差压到零？Linux 的 CFS 又为什么选 `vruntime` 而不是抽签？

::: preview 先抓住一件事
三种算法目标相同：权重高的任务多拿 CPU。彩票把份额交给概率，步长把份额交给确定性的计数器，CFS 把份额交给加权后的已用时间。误差从哪来、能不能消掉，决定了它们在真实内核里的位置。
:::

[1.13.2](#sec-1.13.2) 用周转时间与响应时间比较了 FIFO、SJF、RR 与 MLFQ，那些指标回答「等多久」。这一节换一个指标：**份额**，即每个任务应拿到多少比例的 CPU。设三个任务 A、B、C 的彩票数为 100、50、50，总票数 200，期望份额就是 50%、25%、25%。

**彩票调度**：每次调度随机抽一张票，持票者运行一个时间片。票可以转让，所以权重就是票数。它实现极简，加一个任务只是多几张票，但**份额是概率的**：抽 100 次，谁也保证不了正好 50 次落在 A 上。误差大约按 `1/sqrt(n)` 缩小，n 是抽签次数。

**步长调度**：给每个任务一个步长 `stride = K / tickets`，每次选 `pass` 值最小的任务运行，运行后 `pass += stride`。票多的任务步长小、`pass` 涨得慢，自然被选得更频繁。它是确定性的：长期份额精确等于票数比例，代价是要维护 `pass` 的最小值（实践中用堆）。

**CFS**：Linux 2.6.23–6.5 的默认调度器，维护的是 `vruntime`——「已经消耗掉的加权 CPU 时间」。每运行 `delta`，`vruntime += delta × 1024 / weight`；调度器总选 `vruntime` 最小的任务。权重与票数同构，所以效果与步长一致，但权重可以在运行时改（`nice`、cgroup 的 `cpu.weight`）。nice 与权重的对应关系是固定的：

| nice | 权重 | 相对 nice 0 的 CPU 比例 |
|--:|--:|--:|
| −20 | 88761 | 86.7 倍 |
| −10 | 9548 | 9.3 倍 |
| 0 | 1024 | 1 倍 |
| 10 | 110 | 0.107 倍 |
| 19 | 15 | 0.015 倍 |

下面的程序在同一组票数上跑三种算法，把「实际份额」与「期望份额」放在一起：

```c
/* lottery.c：彩票、步长与加权 vruntime 的份额对照
 * cc -std=c17 -O2 -Wall -Wextra lottery.c -o lottery
 */
#include <stdint.h>
#include <stdio.h>

#define NTASK 3
#define STRIDE_K 100000L

static const int tk[NTASK] = { 100, 50, 50 };
static const int total_tk = 200;
static uint32_t rng = 1;

static uint32_t xs(void)                 /* xorshift32：固定种子，结果可复现 */
{
    rng ^= rng << 13;
    rng ^= rng >> 17;
    rng ^= rng << 5;
    return rng;
}

static void lottery(long quanta, uint32_t seed, long win[NTASK])
{
    for (int i = 0; i < NTASK; i++)
        win[i] = 0;
    rng = seed;
    for (long q = 0; q < quanta; q++) {
        uint32_t pick = xs() % (uint32_t)total_tk;
        int acc = 0, who = NTASK - 1;
        for (int i = 0; i < NTASK; i++) {
            acc += tk[i];
            if (pick < (uint32_t)acc) { who = i; break; }
        }
        win[who]++;
    }
}

static void stride(long quanta, long runs[NTASK], long pass[NTASK])
{
    long stride[NTASK];
    for (int i = 0; i < NTASK; i++) {
        runs[i] = 0;
        pass[i] = 0;
        stride[i] = STRIDE_K / tk[i];
    }
    for (long q = 0; q < quanta; q++) {
        int who = 0;
        for (int i = 1; i < NTASK; i++)
            if (pass[i] < pass[who])
                who = i;
        runs[who]++;
        pass[who] += stride[who];
    }
}

static void vruntime(long quanta, long runs[NTASK], double vt[NTASK])
{
    for (int i = 0; i < NTASK; i++) { runs[i] = 0; vt[i] = 0.0; }
    for (long q = 0; q < quanta; q++) {
        int who = 0;
        for (int i = 1; i < NTASK; i++)
            if (vt[i] < vt[who])
                who = i;
        runs[who]++;
        vt[who] += 1024.0 / (double)tk[who];
    }
}

int main(void)
{
    static const long qs[3] = { 100, 10000, 1000000 };
    long win[NTASK], runs[NTASK], pass[NTASK];
    double vt[NTASK];

    printf("%9s %8s %8s %8s %12s\n", "quanta", "A%", "B%", "C%", "maxdev");
    for (int s = 0; s < 3; s++) {
        double worst = 0.0, pct[NTASK] = { 0 };
        for (uint32_t seed = 1; seed <= 5; seed++) {
            lottery(qs[s], seed, win);
            for (int i = 0; i < NTASK; i++) {
                double got = 100.0 * (double)win[i] / (double)qs[s];
                double exp = 100.0 * (double)tk[i] / (double)total_tk;
                double d = got > exp ? got - exp : exp - got;
                if (d > worst) worst = d;
                if (seed == 1) pct[i] = got;
            }
        }
        printf("%9ld %7.1f%% %7.1f%% %7.1f%% %10.1fpp\n",
               qs[s], pct[0], pct[1], pct[2], worst);
    }

    stride(10000, runs, pass);
    printf("stride   A=%5.1f%% B=%5.1f%% C=%5.1f%%  pass=%ld/%ld/%ld\n",
           100.0 * runs[0] / 10000.0, 100.0 * runs[1] / 10000.0,
           100.0 * runs[2] / 10000.0, pass[0], pass[1], pass[2]);

    vruntime(10000, runs, vt);
    printf("vruntime A=%5.1f%% B=%5.1f%% C=%5.1f%%  vt=%.2f/%.2f/%.2f\n",
           100.0 * runs[0] / 10000.0, 100.0 * runs[1] / 10000.0,
           100.0 * runs[2] / 10000.0, vt[0], vt[1], vt[2]);
    return 0;
}
```

在 Ubuntu 24.04（aarch64、GCC 13.3）上编译运行，输出如下（模拟器输出只由代码决定，换机器不变）：

```text
   quanta       A%       B%       C%       maxdev
      100    50.0%    24.0%    26.0%        6.0pp
    10000    50.1%    25.4%    24.6%        1.0pp
  1000000    49.9%    25.1%    25.0%        0.1pp
stride   A= 50.0% B= 25.0% C= 25.0%  pass=5000000/5000000/5000000
vruntime A= 50.0% B= 25.0% C= 25.0%  vt=51200.00/51200.00/51200.00
```

彩票三行是种子 1 的单次运行，`maxdev` 是种子 1–5 中偏离期望最大的那个百分点的绝对值。抽 100 次时最大偏差 6.0 个百分点，1 万次降到 1.0，100 万次只有 0.1——与 `1/sqrt(n)` 的量级吻合。步长与 `vruntime` 两行精确落在 50/25/25：1 万次运行后三个 `pass` 都是 5,000,000，三个 `vruntime` 都是 51,200。**所有计数器相等，份额就相等**，这是三种算法共同的落点。

把 `qs` 改成 `{100, 100, 100}`，三行都只抽 100 次：彩票列每次都在 50/25/25 附近摇摆，步长列纹丝不动。内核不选彩票，原因就在这里——调度器不能让一个任务先饿 100 个片、再在下一个 100 片里补回来。

真实 Linux 上还有一个容易忽略的前提：**按比例分配只在同一个 runqueue 内成立**。把两个同样的忙循环绑到同一个核（`taskset -c 0`），同一段时间内合计约 5.47e9 次迭代，两者各拿一半；分绑到两个核，合计约 1.08e10 次，每个进程都拿满一个核。份额是「同一核上分蛋糕」，核多了蛋糕也多了。`nice` 只是同一核上的相对权重：本机实测 nice 0 对 10 是 90.1% 对 9.7%，nice 0 对 19 是 98.3% 对 1.3%。

内核版本也要对得上：CFS 是 2.6.23–6.5 的默认调度器，6.6 起换成 EEVDF，按「虚拟截止时间」在 eligible 集合里选任务。本机 7.0.0-38 的 `/proc/<pid>/sched` 里能看到 `se.slice`（2100000）与 `se.load.weight`（1048576），但看不到教科书里的 `se.deadline`。引用字段名前，先 `grep -E 'se\.' /proc/<pid>/sched` 打一遍。

::: errata 关于「份额」的三个误解
1. **「彩票调度的份额是精确的」**——精确的只有期望；单次运行的偏差随 `1/sqrt(n)` 缩小，短窗口内可以差好几个百分点。
2. **「CFS 有固定时间片」**——CFS 按 `sched_latency` 与任务数动态分片，任务越多每片越短；EEVDF 又换成 `se.slice`。把 RR 的片长套到 CFS 上，算出来的延迟一定是错的。
3. **「nice 是绝对优先级」**——nice 只在同一 runqueue 上按权重分；两个 nice 0 的进程分居两核时各拿 100%，看不到 50/50（5.47e9 对 1.08e10 就是证据）。
:::

### 1.13.9 小结

彩票用概率换实现简单，误差随抽签次数按平方根缩小；步长用 `pass` 把误差压到零；CFS 用 `vruntime` 做同样的事，并允许权重动态变化。如果只记住一件事：**比例份额算法的本质，是让某个计数器在所有任务之间保持相等**——抽签次数、`pass` 或 `vruntime`。

## 1.13.10 页替换模拟：OPT、LRU、Clock 与 Belady 异常 {#sec-1.13.10}

这一节回答：内存满了要换出一页时，换谁最划算？「最优」为什么只能当标尺？为什么多给一个页框，缺页次数反而可能增加？

::: preview 先抓住一件事
OPT 看未来，LRU 看过去，FIFO 看进入顺序，Clock 用一位访问位近似 LRU。四种策略的差别可以用同一条引用串量化；而「多给页框反而更差」不是 bug，是 FIFO 不具备栈性质。
:::

[1.13.3](#sec-1.13.3) 讲了换入换出的机制：缺页时内核要找一页换出，再读入需要的页。这一节只问策略：**选哪一页换出**。评价标准是缺页次数——同一条引用串，缺页越少越好。

| 算法 | 替换谁 | 是否栈算法 | 实现成本 | Belady 异常 |
|:--|:--|:--|:--|:--|
| OPT（Belady） | 未来最久不用的页 | 是 | 需要未来信息，不可实现 | 无 |
| LRU | 最久未使用的页 | 是 | 每次访问要更新时间戳/链表 | 无 |
| FIFO | 最早进入的页 | **否** | 一个环形队列 | **有** |
| Clock（二次机会） | 环形扫描，`A=1` 则清位放过 | 近似 LRU | 一个环形队列 + 访问位 | 极少见 |

::: def 定义 1.13.10 · 栈算法 {#def-1.13.10}
把页框数记为 n，`R(t,n)` 是时刻 t 驻留在 n 个页框里的页号集合。若对任意引用串、任意时刻都有 `R(t,n) ⊆ R(t,n+1)`，这个算法叫栈算法。驻留集合随页框增加只增不减，命中就只会更多；OPT 与 LRU 是栈算法，FIFO 不是，所以 FIFO 会出现 Belady 异常。
:::

经典引用串 `1 2 3 4 1 2 5 1 2 3 4 5` 就是为此构造的：3 个页框时 FIFO 缺页 9 次，4 个页框时 10 次。下面的程序把四种算法、两种页框数一次算完，再换一条 1000 次的随机串扫描 2–8 个页框：

```c
/* page_repl.c：FIFO/OPT/LRU/Clock 缺页数对照（含 Belady 异常）
 * cc -std=c17 -O2 -Wall -Wextra page_repl.c -o page_repl
 */
#include <stdio.h>

#define MAXF 8
#define NREF 12
#define NRAND 1000
#define NPAGE 8
static const int classic[NREF] = { 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5 };
static int refs[NRAND];
static int present(const int fr[], int nf, int p)
{
    for (int i = 0; i < nf; i++)
        if (fr[i] == p)
            return i;
    return -1;
}
static int fifo(const int r[], int n, int nf)
{
    int fr[MAXF], faults = 0, next = 0;
    for (int i = 0; i < nf; i++) fr[i] = -1;
    for (int i = 0; i < n; i++) {
        if (present(fr, nf, r[i]) >= 0) continue;
        faults++;
        fr[next] = r[i];
        next = (next + 1) % nf;
    }
    return faults;
}

static int lru(const int r[], int n, int nf)
{
    int fr[MAXF], stamp[MAXF] = { 0 }, faults = 0;
    for (int i = 0; i < nf; i++) fr[i] = -1;
    for (int i = 0; i < n; i++) {
        int hit = present(fr, nf, r[i]);
        if (hit >= 0) { stamp[hit] = i + 1; continue; }
        faults++;
        int v = 0;
        for (int j = 1; j < nf; j++)
            if (stamp[j] < stamp[v]) v = j;
        fr[v] = r[i];
        stamp[v] = i + 1;
    }
    return faults;
}
static int opt(const int r[], int n, int nf)
{
    int fr[MAXF], faults = 0;
    for (int i = 0; i < nf; i++) fr[i] = -1;
    for (int i = 0; i < n; i++) {
        if (present(fr, nf, r[i]) >= 0) continue;
        faults++;
        int v = 0, far = -1;
        for (int j = 0; j < nf; j++) {
            int k = i + 1;
            while (k < n && r[k] != fr[j]) k++;
            if (k > far) { far = k; v = j; }
        }
        fr[v] = r[i];
    }
    return faults;
}
static int clock_repl(const int r[], int n, int nf)
{
    int fr[MAXF], use[MAXF] = { 0 }, faults = 0, hand = 0;
    for (int i = 0; i < nf; i++) fr[i] = -1;
    for (int i = 0; i < n; i++) {
        int hit = present(fr, nf, r[i]);
        if (hit >= 0) { use[hit] = 1; continue; }
        faults++;
        while (use[hand]) {                 /* 二次机会：清位后放过 */
            use[hand] = 0;
            hand = (hand + 1) % nf;
        }
        fr[hand] = r[i];
        use[hand] = 1;
        hand = (hand + 1) % nf;
    }
    return faults;
}

int main(void)
{
    printf("classic ref:");
    for (int i = 0; i < NREF; i++) printf(" %d", classic[i]);
    printf("\n%6s %6s %6s %6s %6s\n", "frames", "FIFO", "OPT", "LRU", "Clock");
    for (int nf = 3; nf <= 4; nf++)
        printf("%6d %6d %6d %6d %6d\n", nf,
               fifo(classic, NREF, nf), opt(classic, NREF, nf),
               lru(classic, NREF, nf), clock_repl(classic, NREF, nf));

    unsigned s = 20261031u;
    for (int i = 0; i < NRAND; i++) {
        s ^= s << 13; s ^= s >> 17; s ^= s << 5;
        refs[i] = (int)(s % NPAGE);
    }
    printf("\nrandom refs=%d pages=%d (seed=20261031)\n", NRAND, NPAGE);
    printf("%6s %6s %6s %6s %6s %8s\n", "frames", "FIFO", "OPT", "LRU", "Clock", "F-hit%");
    int prev_fifo = -1, belady = 0;
    for (int nf = 2; nf <= 8; nf++) {
        int f = fifo(refs, NRAND, nf);
        printf("%6d %6d %6d %6d %6d %7.1f%%\n", nf, f,
               opt(refs, NRAND, nf), lru(refs, NRAND, nf),
               clock_repl(refs, NRAND, nf),
               100.0 * (NRAND - f) / NRAND);
        if (prev_fifo >= 0 && f > prev_fifo) belady++;
        prev_fifo = f;
    }
    printf("FIFO belady steps in 2..8: %d\n", belady);
    printf("frames=4 hits: FIFO %d OPT %d LRU %d Clock %d (of %d)\n",
           NRAND - fifo(refs, NRAND, 4), NRAND - opt(refs, NRAND, 4),
           NRAND - lru(refs, NRAND, 4), NRAND - clock_repl(refs, NRAND, 4), NRAND);
    return 0;
}
```

在 Ubuntu 24.04 上运行，先看经典串：

```text
classic ref: 1 2 3 4 1 2 5 1 2 3 4 5
frames   FIFO    OPT    LRU  Clock
     3      9      7     10      9
     4     10      6      8     10
```

FIFO 从 9 涨到 10，多给一个页框反而多缺一次页，这就是 Belady 异常；OPT（7→6）与 LRU（10→8）都下降，符合栈算法；本例的 Clock 也是 9→10，说明「近似 LRU」没有继承栈性质。

再看 1000 次随机引用（8 个页号，种子 20261031）扫过 2–8 个页框：

```text
frames   FIFO    OPT    LRU  Clock   F-hit%
     2    764    605    766    764    23.6%
     3    630    430    629    633    37.0%
     4    525    301    510    515    47.5%
     5    414    202    391    396    58.6%
     6    277    124    270    256    72.3%
     7    127     59    140    140    87.3%
     8      8      8      8      8    99.2%
FIFO belady steps in 2..8: 0
```

4 个页框时：OPT 命中 699 次，LRU 490，Clock 485，FIFO 475。LRU 只比 Clock 多 5 次（0.5 个百分点），说明一位访问位在日常负载上够用；LRU 比 OPT 少 209 次，说明「看过去」和「看未来」的差距。

两个反直觉的点要记住。第一，`frames=2` 时 LRU 766 次缺页，比 FIFO 的 764 还差——LRU 押注局部性，串一换就可能输。第二，这条随机串上 FIFO 的缺页从 764 一路降到 8，2–8 之间没有出现反增（`belady steps` 为 0）；Belady 异常要靠经典串那样构造出来，不能指望随手一跑就撞上。

8 个页框时四种算法都只剩 8 次缺页：8 个页号刚好全部装下，这 8 次是**强制缺页**（第一次访问必然缺页），任何策略都躲不掉。策略能改变的只有「容量不够」与「换错了页」这两部分；OPT 的实现就是向后扫描每个驻留页的下次出现位置，淘汰最远的那个，扫描到串尾还没出现就记为无穷远。

真实内核不用纯 LRU：硬件不支持对每次访问高效排序，内核用 active/inactive 双链表加 PTE 的访问位做近似，[3.10](../part3/ch10.md) 会展开。模拟器的价值也在这里——换串、换页框数、换算法，比背结论快。

::: errata 关于页替换的三个误解
1. **「LRU 总比 FIFO 好」**——`frames=2` 时 LRU 766 次、FIFO 764 次；LRU 依赖局部性假设，引用串一换就可能输。
2. **「Clock 与 LRU 等价」**——Clock 只保留一位访问信息，命中数接近但不相等（485 对 490）；访问位由 CPU 置位、内核清除，粒度是「自上次扫描以来有没有被访问」。
3. **「页框越多，缺页一定越少」**——只有栈算法有这个保证；FIFO 的 9→10 就是反例，本例 Clock 也一样。
:::

::: ex 例 1.13.10 · 先猜 LRU 会不会更好 {#ex-1.13.10}
引用串 `1 2 3 4 1 2 5 1 2 3 4 5`，物理帧 3 个。先猜：FIFO 与 LRU 的缺页次数各是多少？换 4 个帧后 FIFO 的缺页会减少还是增加？

::: sol 解答
3 帧时 FIFO 缺页 9 次、LRU 缺页 10 次——这个串里 FIFO 反而更少；4 帧时 FIFO 缺页 10 次，比 3 帧还多一次，这就是 **Belady 异常**。LRU 是栈式算法，帧增加时缺页数单调不增，所以不会出现这种异常。结论：**「更多内存一定更快」对非栈式算法不成立**，这也是为什么讲页替换要先讲「栈式」这个性质。
:::
:::

### 1.13.10 小结

OPT 是标尺不是实现，LRU 是理想化的「看过去」，Clock 用一位访问位把成本降下来，FIFO 最简单却没有栈性质。如果只记住一件事：**缺页数由引用串、页框数、算法三者共同决定**，任何「某算法一定更好」的说法都要先问引用串长什么样。

## 1.13.11 崩溃一致性：日志协议与崩溃点枚举 {#sec-1.13.11}

这一节回答：写文件写到一半断电，为什么重启后看到的要么是完整的旧状态、要么是完整的新状态？「提交」这两个字在磁盘上到底对应哪一次写？

::: preview 先抓住一件事
崩溃一致性不靠「写得快」，靠「顺序 + 一条原子分界」。redo 先写新值、再写提交记录、最后改主文件系统；undo 先写旧值、再改、最后提交。恢复方向相反，但都把崩溃点压成两类：提交前丢弃或回滚，提交后重放。
:::

[1.13.5](#sec-1.13.5) 讲了「先写日志再改主文件系统」的思路，这里把它拆到每一次写。考虑在目录里新建一个文件，最少要改三处元数据：

1. 目录项指向 inode 2（`dir → 2`）；
2. inode 位图把 2 标为已分配；
3. inode 本身初始化（类型、权限、大小、数据块指针）。

三处不在一个块里，也不可能一次写完。按 1→2→3 就地写盘，崩在 1 之后就是「目录项指向一个没分配的 inode」——`fsck` 只能把它删掉，用户看到文件消失；崩在 2 之后，则是「inode 已分配但内容全零」，同样不可用。日志要求：这三步要么全做，要么全不做。

::: def 定义 1.13.11 · 预写日志（write-ahead log）
把「打算怎么改」先写进一块连续的日志区，等日志落盘后再改主文件系统。日志里每条记录带事务号，一个事务以一条提交记录结尾。恢复时只看提交记录在不在：在就重放（redo）或确认已生效；不在就丢弃（redo）或回滚（undo）。
:::

redo 协议的写顺序是：把三步的**新值**写进日志 → 写**提交记录**（commit）→ checkpoint 到主文件系统 → 回收日志空间。提交记录落盘那一次写，是唯一的分界点。

undo 协议反过来：先把三步的**旧值**写进日志 → 就地更新主文件系统 → 最后写提交记录。崩溃发生在提交之前，恢复时用日志里的旧值把三步全部改回去。

下面的程序把「创建文件」建模成三个字段的更新，按物理写顺序枚举崩溃点，三种策略一起跑：

```c
/* journal.c：创建文件的三个元数据更新，枚举崩溃点（无日志 / redo / undo）
 * cc -std=c17 -O2 -Wall -Wextra journal.c -o journal
 */
#include <stdio.h>
#include <string.h>

#define NINODE 4
#define NSTEP 3
#define INO 2

struct disk {
    int dir;              /* 目录项指向的 inode，-1 表示没有 */
    int bitmap[NINODE];   /* 1 = 已分配 */
    int inode[NINODE];    /* 1 = 已初始化 */
};

static struct disk base(void)
{
    struct disk d;
    d.dir = -1;
    for (int i = 0; i < NINODE; i++) { d.bitmap[i] = 0; d.inode[i] = 0; }
    return d;
}

static void apply(struct disk *d, int step)
{
    if (step == 0) d->dir = INO;
    else if (step == 1) d->bitmap[INO] = 1;
    else if (step == 2) d->inode[INO] = 1;
}

static const char *cls(const struct disk *d)
{
    int used = d->bitmap[INO] && d->inode[INO];
    if (d->dir == INO && used) return "新态";
    if (d->dir == INO && !used) return "悬空";
    if (d->dir != INO && used) return "泄漏";
    return "旧态";
}

/* 无日志：按 1→2→3 就地写，崩溃后不做任何恢复 */
static struct disk inplace(int k)
{
    struct disk d = base();
    for (int i = 0; i < k && i < NSTEP; i++) apply(&d, i);
    return d;
}

/* redo：3 条日志 → 提交记录 → 3 步 checkpoint；有提交就重放全部 */
static struct disk redo_before(int k)
{
    struct disk d = base();
    int applied = k - 4;
    for (int i = 0; i < applied && i < NSTEP; i++) apply(&d, i);
    return d;
}

static struct disk redo_after(int k)
{
    struct disk d = redo_before(k);
    if (k >= 4)
        for (int i = 0; i < NSTEP; i++) apply(&d, i);
    return d;
}

/* undo：3 条旧值 → 3 步更新 → 提交记录；没有提交就回滚 */
static struct disk undo_before(int k)
{
    struct disk d = base();
    for (int i = 0; i < k - 3 && i < NSTEP; i++) apply(&d, i);
    return d;
}

static struct disk undo_after(int k)
{
    struct disk d = undo_before(k);
    if (k < 7)
        return base();
    return d;
}

static int same(const struct disk *a, const struct disk *b)
{
    return memcmp(a, b, sizeof *a) == 0;
}

int main(void)
{
    printf("%-2s %-10s %-14s %s\n", "k", "无日志", "redo", "undo");
    for (int k = 0; k <= 7; k++) {
        struct disk a = inplace(k);
        struct disk rb = redo_before(k), ra = redo_after(k);
        struct disk ub = undo_before(k), ua = undo_after(k);
        char r[32], u[32];
        snprintf(r, sizeof r, "%s→%s", cls(&rb), cls(&ra));
        snprintf(u, sizeof u, "%s→%s", cls(&ub), cls(&ua));
        printf("%-2d %-10s %-14s %s\n", k, cls(&a), r, u);
    }

    struct disk once = base(), twice = base();
    for (int i = 0; i < NSTEP; i++) apply(&once, i);
    for (int r = 0; r < 2; r++)
        for (int i = 0; i < NSTEP; i++) apply(&twice, i);
    printf("重放两次与一次相同: %s\n", same(&once, &twice) ? "是" : "否");
    return 0;
}
```

在 Ubuntu 24.04 上运行，`k` 是已完成的物理写次数，箭头左边是恢复前、右边是恢复后：

```text
k  无日志  redo           undo
0  旧态     旧态→旧态 旧态→旧态
1  悬空     旧态→旧态 旧态→旧态
2  悬空     旧态→旧态 旧态→旧态
3  新态     旧态→旧态 旧态→旧态
4  新态     旧态→新态 悬空→旧态
5  新态     悬空→新态 悬空→旧态
6  新态     悬空→新态 新态→旧态
7  新态     新态→新态 新态→新态
重放两次与一次相同: 是
```

逐列读：

- **无日志**：k=1、2 都是「悬空」，目录项已经指向 inode，位图或 inode 内容还没就位；只有 k=3 才是新态。悬空只能靠 `fsck` 删掉，用户看到文件消失。
- **redo**：k≤3 全是旧态。k=3 时三条日志已写完，但提交记录没写，恢复按「无提交」丢弃，磁盘上什么都没发生。k=4 时提交记录刚落盘、checkpoint 还没开始（恢复前仍是旧态）；k=5、6 只做了一两步 checkpoint（恢复前悬空），重放后都得到完整新态。
- **undo**：k≤6 全是旧态。注意 k=6：三步更新都已应用，恢复前已是新态，但没有提交记录，仍被整体回滚成旧态；k=7 提交记录写完，才保留新态。

两个协议的分界点位置不同，结果一样：**恢复后只可能看到旧态或新态，看不到悬空**。最后一行验证幂等——重放两次与一次相同，前提是日志记录「绝对值」而不是「加一」这类增量。

真实文件系统还要处理两件事：日志块本身可能写撕裂，ext4 用 `metadata_csum` 校验；提交记录可能停在设备缓存里，要靠 `barrier`/`FLUSH` 推下去，否则「已提交」只是内存里的假象。ext4 的三种数据模式决定了数据与元数据的先后：

| 模式 | 数据何时写 | 风险 |
|:--|:--|:--|
| `data=journal` | 数据也进日志 | 最慢，但数据与元数据都原子 |
| `data=ordered`（默认） | 数据先于元数据提交 | 崩溃后可能看到旧数据 |
| `data=writeback` | 不保证顺序 | 可能读到未初始化或旧数据 |

应用层还要自己补一刀：`fsync(fd)` 只保证这个文件；`rename` 只在同一文件系统内原子；换名之后要再 `fsync` 父目录，否则目录项可能回退。本机 `strace` 实测这条路径上是两次 `fsync`（文件 fd、目录 fd）加一次 `renameat`。日志保证的是「结构一致」，不保证「你的数据在」。

::: errata 关于日志的三个误解
1. **「有日志就不会丢数据」**——日志保证元数据自洽；`data=ordered` 下崩溃后仍可能看到旧数据，数据也在得靠 `fsync`。
2. **「fsync 一次就够」**——文件与目录是两个对象；`rename` 后不 `fsync` 目录，名字可能回退。
3. **「redo 与 undo 只是方向不同」**——redo 要求重放幂等，undo 要求旧值在改之前已落盘；两者对提交记录的位置要求相反。
:::

::: ex 例 1.13.11 · 先猜崩溃点会不会丢数据 {#ex-1.13.11}
日志协议：`write(data)` → `write(log)` → `fsync(log)` → `write(home)` → `fsync(home)`。
先猜：如果在「`fsync(log)` 之后、`write(home)` 之前」崩溃，恢复后数据在不在？如果崩溃发生在「`write(log)` 之后、`fsync(log)` 之前」呢？

::: sol 解答
前者在：日志已落盘，恢复时重放日志就能把数据补进 home。后者不一定：日志可能只在 page cache 里，崩溃后丢失，恢复时既看不到日志也看不到数据——**这就是「先写日志再改数据」必须配 `fsync` 的原因**，也是 1.10.15 那条 `fsync` 警告在文件系统层的版本。
:::
:::

### 1.13.11 小结

三步元数据、两种协议、一条提交记录。redo 把分界点放在改主文件系统之前，undo 放在之后；恢复后只可能旧态或新态。如果只记住一件事：**提交记录那一次写，就是「全做」与「全不做」的开关**，它必须真的落盘。

::: method 即时自测 · 1.13.11
**Q1（记忆）** redo 与 undo 的写顺序分别是什么？各自的提交记录在哪一步？

**Q2（应用）** 表里 undo 在 k=6 时恢复前已经是「新态」，为什么恢复后还是「旧态」？

**Q3（辨析）** 日志已经保证崩溃后文件系统一致，为什么应用还要 `fsync` 文件与目录？

::: sol 答案
**A1** redo：写新值日志 → 写提交记录 → checkpoint 到主文件系统 → 回收；提交记录在 checkpoint 之前。undo：写旧值日志 → 就地更新 → 写提交记录；提交记录在更新之后。

**A2** k=6 只说明三步更新都写了，提交记录还没写；undo 的规则是「没有提交就回滚」，所以用日志里的旧值把三步全部改回去。提交记录才是「保留新态」的依据。

**A3** 日志只保证元数据结构自洽，不保证数据块内容已经落盘；`fsync` 保证文件数据与元数据到设备，`rename` 换名后还要 `fsync` 目录，才能保证「名字」也持久。
:::
:::

## 1.13.13 xv6 与 rCore：两个可读完的小内核 {#sec-1.13.13}

这一节回答：Linux 源码读不动，有没有两个小内核，能让你把「进程、地址空间、日志」真正读成代码，而不是停在名词？

::: preview 先抓住一件事
xv6 与 rCore 不是「简化版 Linux」，而是同一组机制的**最小正确实现**。读它们的方法不是通读，而是带着一个问题追一条链：同一个问题，两边各用哪个结构回答，Linux 又多出了什么。
:::

先给方法。不要从启动汇编顺着读；拿三个问题进去，每个问题只追一条链：

| 问题 | xv6（C，RISC-V） | rCore（Rust，RISC-V） | Linux 对应 |
|:--|:--|:--|:--|
| 进程是谁 | `struct proc`：`pid`、`state`、`pagetable`、`trapframe`、`context` | `TaskControlBlock`：`pid`、`state`、`memory_set`、`trap_cx` | `task_struct` |
| 地址怎么翻 | `pagetable` + `walk()`（Sv39 三级） | `MemorySet` 管 `MapArea`，再落实页表 | `mm_struct` + 多级页表 |
| 崩了怎么恢复 | `log.c`：`begin_op` → `log_write` → `commit` → `install_trans` | 基础版 `easy-fs` 只有块缓存与 inode 层，不实现日志 | jbd2 |

::: def 定义 1.13.13 · 教学内核 {#def-1.13.13}
为讲清机制而写的完整内核：能启动、跑用户程序、读写文件，但**主动砍掉性能与硬件多样性**。它保留「机制的最小正确实现」，适合验证理解，不适合拿来比较吞吐。
:::

三个问题各追一条链，读完就能指出「机制在哪一段代码」：

1. **进程**。xv6 的 `allocproc()` 先找空槽，再建 `trapframe`（保存用户寄存器）与内核栈，把状态置为 `RUNNABLE`；`scheduler()` 在 `proc[]` 里找 `RUNNABLE`，切换 `context`。rCore 的 `TaskControlBlock` 把同样的事拆成任务状态、内核栈、`memory_set` 与陷入上下文，由任务管理器选下一个。两者都在回答 [1.13.8](#sec-1.13.8) 的「PCB 放什么、切换保存什么」，只是字段名不同。
2. **地址空间**。xv6 的 `pagetable` 就是一张 Sv39 页表，`walk()` 逐级取索引、缺页时分配；`uvmalloc` 与 `uvmcopy` 负责增长与 `fork` 复制。rCore 把「逻辑段」与「页表」分开：`MemorySet` 持有一组 `MapArea`，映射时按段批量建表。后者更接近 Linux 的 VMA（`vm_area_struct`）：先描述「这段地址是什么」，再落实页表。
3. **日志**。xv6 的 `log.c` 是 [1.13.11](#sec-1.13.11) 协议的可运行版：`begin_op` 开始事务，`log_write` 只改缓冲区并记块号，`commit` 先写日志区与提交头，`install_trans` 再重放到主区。对照「提交记录是唯一分界」，你能指出「哪一次写之后崩溃可以恢复」。

::: errata 读小内核的三个误解
1. **「xv6/rCore 是简化版 Linux，读完就会写驱动」**——它们省略了驱动模型、SMP 调度、RCU、cgroup 与错误注入；能读懂机制，不等于能改生产内核。
2. **「代码少，所以简单」**——少的是功能，不是推理。`walk()` 的边界、`fork` 的失败回滚、日志的崩溃点，每一处都要你自己补出「为什么这样写才对」。
3. **「两套代码可以逐行对照」**——C 与 Rust 的抽象层次不同：xv6 直接操作页表，rCore 先有 `MapArea` 再有页表。对照的是**问题与不变量**，不是行号。
:::

### 1.13.13 小结

两个小内核把三大主题压成三组结构：`proc` 对 `TaskControlBlock`，`pagetable` 对 `MemorySet`，`log.c` 对文件系统的事务层。读法不是通读，而是带着问题追一条链，再回 Linux 看工业实现多出了什么。如果只记住一件事：**小内核的价值是让你指出「机制的最小正确实现」在哪，而不是让你背文件名**。

::: method 即时自测 · 1.13.13

**Q2（辨析）** rCore 的 `MemorySet`/`MapArea` 与 xv6 的 `pagetable` 抽象层次有什么不同？哪一个更像 Linux 的 VMA？

**Q3（应用）** 你怀疑 `fork` 之后子进程写时复制有 bug。按本节的方法，先去 xv6 追哪条链，再去 Linux 看哪个结构？

**Q4（迁移）** 为什么读小内核时要「先问题、后代码」，而不是从启动汇编开始通读？

::: sol 答案

**A3** 先追 xv6 的 `uvmcopy` 与 `walk`（复制页表、COW 的落点），再看 Linux 的 `mm_struct`、VMA 与 `do_wp_page`；对照的是不变量，不是行号。

**A4** 通读会被启动与驱动细节淹没；先有问题，才知道哪条调用链与你的机制有关，读到的每一行才有位置。
:::

## 1.13.14 三个实验：调度、缺页与 ext4 的证据 {#sec-1.13.14}

这一节回答：1.13.2 的份额、1.13.3 的按需分页、1.13.11 的 `fsync` 顺序，能不能各用一条命令变成可反驳的预测？没有 sudo、没有 `perf` 时，哪些证据还拿得到？

::: preview 先抓住一件事
实验不是「跑一条命令看输出」，而是**先写预期，再跑，再解释差异**。三个实验分别验证：份额只在同一个核上分；`mmap` 只登记地址，第一次写才分配物理页；ext4 的持久化靠 `fsync` 的顺序，而布局与日志参数需要特权才能读全。
:::

三个实验都在 Ubuntu 24.04 aarch64 虚拟机上跑，命令不需要 root；需要 root 的那一半会明确标出来。

### 实验一：份额只在同一个核上分

目标：验证 [1.13.9](#sec-1.13.9) 的「同核分蛋糕，异核各吃一个」。先编译一个能计数的忙循环：

```c
/* burn.c：数 secs 秒内的忙循环次数 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
int main(int argc, char **argv)
{
    double secs = argc > 1 ? atof(argv[1]) : 5.0;
    struct timespec a, b;
    volatile unsigned long long n = 0;
    clock_gettime(CLOCK_MONOTONIC, &a);
    do {
        for (int i = 0; i < 1000000; i++) n++;
        clock_gettime(CLOCK_MONOTONIC, &b);
    } while ((b.tv_sec - a.tv_sec) + (b.tv_nsec - a.tv_nsec) / 1e9 < secs);
    printf("%llu\n", n);
    return 0;
}
```

```bash
cc -O2 -std=c17 burn.c -o burn
taskset -c 0 ./burn 5 > a & taskset -c 0 ./burn 5 > b & wait
taskset -c 0 ./burn 5 > c & taskset -c 1 ./burn 5 > d & wait
awk 'FNR==1{print FILENAME, $1}' a b c d
```

预期：`a`、`b` 同核，各拿约一半，合计是一次单核的份额；`c`、`d` 分居两核，各自接近满速，合计约翻倍。1.13.9 的读数是同核合计 5.47e9、异核合计 1.08e10；你跑出的绝对值可以不同。**绝对值随 CPU 频率与代码写法漂移，判据是合计是否约翻倍，不是记住 5.47e9。**

顺手看调度器的字段：

```bash
./burn 5 & pid=$!
sleep 1
grep -E 'se\.(slice|sum_exec_runtime)' /proc/$pid/sched
wait $pid
```

本机 7.0.0-38 上能看到 `se.slice`（2100000）与 `se.sum_exec_runtime`，看不到教科书里的 `se.deadline`。`perf sched` 因 tracefs 权限报 `can't access trace events`，等待侧改看 `/proc/pressure/cpu` 的 `some avg10`；拿不到 `perf` 不影响「同核/异核」这个判据。

### 实验二：缺页与 RSS

目标：把「映射 64 MiB、只写 16 MiB」变成 `minflt` 与 `smaps` 三个数。

```c
/* pf.c：映射 64 MiB，只写前 16 MiB，报告 minor fault 增量 */
#define _GNU_SOURCE
#include <stdio.h>
#include <sys/mman.h>
#include <sys/resource.h>
#include <unistd.h>
int main(void)
{
    struct rusage u1, u2;
    getrusage(RUSAGE_SELF, &u1);
    char *p = mmap(NULL, 64UL << 20, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }
    for (unsigned long off = 0; off < (16UL << 20); off += 4096)
        p[off] = 1;
    getrusage(RUSAGE_SELF, &u2);
    printf("pid=%d minflt=%ld\n", getpid(), u2.ru_minflt - u1.ru_minflt);
    fflush(stdout);
    sleep(12);
    return 0;
}
```

```bash
cc -O2 -std=c17 pf.c -o pf
./pf & pid=$!
sleep 2
grep -A24 '^Size: *65536 kB' /proc/$pid/smaps | grep -E '^(Size|Rss|Swap):'
wait $pid
```

预期：程序打印 `minflt=4096`，正好是 16 MiB / 4 KiB；`smaps` 给出 `Size: 65536 kB`、`Rss: 16384 kB`、`Swap: 0 kB`。三个数各回答一件事：虚拟区间 64 MiB、实际驻留 16 MiB、这个进程没有页被换出。如果只碰了前 16 MiB 却报 16384 次缺页，那是把 64 MiB 当成了已触碰范围；如果 `Rss` 是 64 MiB，先查写循环有没有越界。若你的机器报 8 或 16 次缺页，先看 `/sys/kernel/mm/transparent_hugepage/enabled`：THP 为 `always` 时，这段映射可能按 2 MiB 大页计。

`Swap: 0` 不等于系统没开 swap；系统有没有 swap 看 `/proc/meminfo` 的 `SwapTotal` 与 `swapon --show`。本机的 swap 是 `/swap.img` 4 GiB，但这次实验没有制造压力，`si/so` 仍为 0。

### 实验三：ext4 的布局与 fsync 顺序

目标：不用 `dumpe2fs`，也能拿到 ext4 的三类证据：文件系统类型、extent 布局、应用层 `fsync` 顺序。

```c
/* persist.c：临时文件 fsync → rename → fsync 目录（省略错误检查） */
#define _GNU_SOURCE
#include <fcntl.h>
#include <unistd.h>
int main(void)
{
    int fd = open("/tmp/lab1c13_data.bin.tmp",
                  O_CREAT | O_TRUNC | O_WRONLY, 0644);
    write(fd, "hello\n", 6);
    fsync(fd);
    close(fd);
    rename("/tmp/lab1c13_data.bin.tmp", "/tmp/lab1c13_data.bin");
    int dfd = open("/tmp", O_RDONLY | O_DIRECTORY);
    fsync(dfd);
    close(dfd);
    return 0;
}
```

```bash
cc -O2 -std=c17 persist.c -o persist
./persist
findmnt -no SOURCE,FSTYPE,OPTIONS /
stat -fc %T /tmp
strace -e trace=fsync,renameat ./persist
filefrag -v /tmp/lab1c13_data.bin | head -6
```

VM 实测（你的物理块号会不同）：

```text
/dev/sda2 ext4   rw,relatime
ext2/ext3
fsync(3)                                = 0
renameat(AT_FDCWD, "/tmp/lab1c13_data.bin.tmp", AT_FDCWD, "/tmp/lab1c13_data.bin") = 0
fsync(3)                                = 0
Filesystem type is: ef53
   0:        0..       0:   12367872..  12367872:      1:             last,eof
```

`findmnt` 直接给出 ext4；`stat -fc %T` 只回 `ext2/ext3`，因为 ext2/3/4 共用魔数 `ef53`，它分不出具体是哪一代；`filefrag` 的 extent 说明这个文件在盘上是一段连续物理块；`strace` 的两次 `fsync` 夹一个 `renameat`，对应「文件 → 改名 → 目录」的持久化顺序。

课本常用的 `sudo dumpe2fs -h /dev/sda2 | grep -E 'Journal|Filesystem features'` 在这台 VM 上跑不了：`dumpe2fs` 要读块设备，普通用户报 `Permission denied`，`sudo` 又要密码。所以 `has_journal`、`Journal inode: 8`、`Journal size` 这三项**未实测**。替代链能证明「ext4 + extent + 应用顺序」，不能证明日志参数与 inode 号；要补这一半，只能在有 root 的机器上跑。

::: errata 关于实验读数的三条边界
1. **份额看比值，不看绝对值。** 同核合计约是异核的一半，CPU 频率、编译选项、循环体都会改变绝对值；不绑核时两个进程各占一个核，比例没有可比性。
2. **`smaps` 的三个数各管一件事。** `Size` 是虚拟区间，`Rss` 是驻留物理页，`Swap` 只说明这个进程有没有页被换出；`Swap: 0` 不是「系统没开 swap」。
3. **没有 root 就拿不到日志参数。** `dumpe2fs`/`tune2fs` 读块设备需要权限，`perf sched` 需要 tracefs；把「没读到」写成「不存在」是实验报告里最常见的越界。
:::

### 1.13.14 小结

三个实验对应三件事：调度看「同核合计是否约翻倍」，内存看「Size 与 Rss 差多少、缺页数是否等于触碰页数」，持久化看「两次 `fsync` 与一个 `renameat` 的顺序」。如果只记住一件事：**先写预期再跑命令；没有预期的观测只是数据，不是证据。**

::: method 即时自测 · 1.13.14
**Q1（应用）** 两个同样的忙循环，绑同一核与分绑两核，合计计数为什么约差一倍？去掉 `taskset` 后，你还能用 `ps` 的哪一列证明它们在哪个核上？

**Q2（辨析）** `mmap` 64 MiB、只写前 16 MiB：`minflt` 为什么是 4096 而不是 16384？`smaps` 的 `Size`、`Rss`、`Swap` 各说明什么？

**Q3（应用）** 没有 sudo，你用哪三条命令拿到 ext4、extent 与 `fsync` 顺序三类证据？哪些结论仍然拿不到？

::: sol 答案
**A1** 同一核上两个进程分一个核的时间，合计约等于单核满速；分绑两核各有一个核，合计约翻倍。`ps -o psr` 的 PSR 列给出当前所在 CPU，绑核后应稳定在 0 或 1。

**A2** 只触碰了 16 MiB，即 16 MiB / 4 KiB = 4096 页；`Size` 是 64 MiB 虚拟区间，`Rss` 是 16 MiB 驻留，`Swap` 为 0 表示没有页被换出。

**A3** `findmnt -no FSTYPE /` 看 ext4，`filefrag -v` 看 extent，`strace -e trace=fsync,renameat` 看顺序。`has_journal`、日志 inode 号与日志大小要读块设备，普通用户拿不到，只能标「未实测」。
:::
:::

## 1.13.15 十五条操作系统陷阱 {#sec-1.13.15}

这一节回答：1.13.2 到 1.13.14 的结论，哪些一换负载、一换内核、一换架构就会被说反？怎样用一条命令把它们当场拆穿？

::: preview 先抓住一件事
十五条不是十五个冷知识，而是四组「模型 → 实现」的落差点：CPU 份额、内存与页框、持久化与名字、小内核与读法。每条都按「现象 → 原因 → 判据」记，判据优先用你能跑的命令。
:::

十五条按四组排。

### 一、CPU 与调度（1–3）

1. **用周转时间比较 CFS 与 RR。** 普通类的 CFS/EEVDF 没有固定片长，名叫 RR 的 `SCHED_RR` 属于实时类；批处理看吞吐，交互看响应分位。判据：`chrt -p $$` 看策略，`grep se.slice /proc/<pid>/sched` 看片长字段。
2. **长任务永远拿不到 CPU。** MLFQ 若没有规则 5 的周期提升，长任务会沉底饿死；提升同时防饥饿与防 gaming。判据：在模拟器里把提升关掉，长任务完成时间不再收敛。
3. **片长越小越流畅。** 每次切换都要保存与恢复现场，片长压到 100 µs，切换开销占比上升，吞吐反而下降。判据：`vmstat 1` 把 `cs` 与 `us/sy` 一起看；片长从毫秒量级起步。

### 二、内存与页框（4–6）

4. **LRU 可以直接实现。** 硬件不给每页访问时间戳；内核用 PTE 访问位加 active/inactive 双链表近似。判据：`/proc/kpageflags` 需 root，退一步看 `pgscan`/`pgsteal` 与 `minflt`。
5. **页框加一个，缺页一定少。** FIFO 不是栈算法，Belady 异常会让 3 个页框的 9 次缺页变成 4 个页框的 10 次。判据：改 [1.13.10](#sec-1.13.10) 的 `page_repl.c` 页框数复跑。
6. **swap 越大系统越不卡。** 工作集远大于物理内存时，换入换出互相追，进入 thrashing；加 swap 只延长痛苦。判据：`vmstat` 的 `si/so` 持续非零、`pswpin`/`pswpout` 增长。

### 三、持久化与名字（7–10）

7. **RAID 能防误删。** RAID 只处理盘故障；误删、勒索、火灾要靠备份与快照。判据：`/proc/mdstat` 只能看阵列健康，看不到文件历史。
8. **日志模式应用数据不会丢。** `data=writeback` 不保证数据先于元数据落盘；要 `data=ordered` 加应用层 `fsync`。判据：看挂载选项里的 `data=`，`findmnt -no OPTIONS /` 与 `/proc/fs/ext4/<dev>/options` 各看一次。
9. **`fsync` 之后文件名不会回退。** `fsync` 只作用于一个对象；`rename` 后还要 `fsync` 父目录，否则目录项可能回退。判据：`strace -e trace=fsync,renameat` 应数到两次 `fsync` 与一个 `renameat`。
10. **inode 号就是文件名。** 目录项才是「名字 → inode」的映射；硬链接共享 inode，名字留在目录里。判据：`ls -li` 看两个名字是否指向同一个 inode。

### 四、小内核与读法（11–15）

11. **在 xv6 里用自旋锁保护长临界区。** xv6 的自旋锁关中断，长临界区会烧 CPU、拖长中断延迟；长临界区用睡眠锁。判据：读 `spinlock.c` 的 `push_off`/`pop_off` 与 `sleeplock.c` 的睡眠路径。
12. **rCore 的 `UPSafeCell` 是线程安全。** 它只做运行时借用检查，前提是单核；多核要真锁与原子操作（不可被打断的读改写）。判据：看它内部是否只有借用检查语义，没有跨核原子。
13. **通读 OSTEP 50 章。** 46–50 章是分布式，超出本章主线；按 [1.13.12](#sec-1.13.12) 的落点表取舍。判据：任给一章能说出「已覆盖/合并/背景/淘汰」。
14. **`vmstat` 的 `si/so` 是累计字节。** 它是每秒 KiB；累计页数在 `/proc/vmstat` 的 `pswpin`/`pswpout`。判据：`vmstat 1` 看瞬时，`grep pswp /proc/vmstat` 看累计。
15. **小内核等于简单内核。** xv6/rCore 省掉了性能与硬件多样性；读机制可以，读性能与驱动不行。判据：看同一子系统在 Linux 里多出的锁、per-CPU、NUMA 与错误路径。

::: errata 关于「陷阱」本身的三条提醒
1. **陷阱不是背条目。** 每条都要能给出一个命令或实验判据；给不出，就回对应小节重读。
2. **OSTEP 的作业不能跳。** 调度器与内存模拟器是理解策略的最短路径；只读正文，很容易停在名词级。
3. **机制不是策略，模型不是实现。** 给策略打补丁却改坏机制，是排障里最常见的二次事故；CFS→EEVDF、`data=` 模式、cgroup v1→v2 都是版本边界。
:::

### 1.13.15 小结

十五条可以压成一句：任何操作系统结论都要带三个限定——哪件、哪层、哪台机器。如果只记住一件事：**先问判据，再记结论**。

::: method 即时自测 · 1.13.15
**Q1（辨析）** nice 0 对 10，不绑核为什么看不到 9:1？绑核后看哪个字段？

**Q2（应用）** 应用说「`fsync` 了」，但断电后文件名回到旧的。按第 9 条查哪一步，`strace` 应出现什么？

**Q3（迁移）** 同事说「加页框后缺页更多，所以内核该用 LRU」。哪半句对，哪半句还要加限定？

::: sol 答案
**A1** 不绑核时两个进程各占一个核，没有竞争，份额都接近 100%；只有同一 runqueue 上才按权重分。绑核后看 `/proc/<pid>/sched` 的 `se.sum_exec_runtime` 比值，本机 nice 0 对 10 约为 90.1% 对 9.7%。

**A2** 只 `fsync` 了文件，没 `fsync` 父目录；`rename` 后目录项可能没落盘。`strace -e trace=fsync,renameat` 应看到两次 `fsync` 夹一个 `renameat`，第二次 `fsync` 的对象是目录 fd。

**A3** 「FIFO 在页框增加时缺页可能变多」对，这是 Belady 异常；「所以内核该用 LRU」是策略建议，还要加限定：Linux 用访问位加 active/inactive 近似，不是精确 LRU。
:::
:::

## 1.13.16 本章小结 {#sec-1.13.16}

这一节回答：学完 16 节，你能独立回答哪三类问题、拿出哪三种证据，又该把哪些判断留在「这台机器上成立」？

::: preview 先抓住一件事
本章的出口不是「记得三大主题」，而是**给你一个现象，你能说出它属于虚拟化、并发还是持久化，坏在机制还是策略，并用一条命令或一个模拟器把话钉住**。
:::

这一章的主线分三段。第一段（1.13.1–1.13.6）先给地图：三大主题、机制与策略、调度指标、内存三步、并发分类、磁盘与 RAID、文件系统，再用李治军的 8 个项目看同一批机制在实现里长什么样。

第二段（1.13.7–1.13.12）把概念钉到结构：`task_struct` 的四组字段、PTE 的位、redo 日志的提交点，配上彩票/步长、页替换、崩溃点三个模拟器，最后用 50 章落点表回答「OSTEP 的每一章在本书哪里」。

第三段（1.13.13–1.13.15）做验证：xv6 与 rCore 把机制压成可读完的代码，三个实验把预期变成读数，十五条陷阱把「模型 ≠ 实现」写成可检查的判据。三段合起来是一条闭环：地图 → 结构 → 证据；缺任何一段，结论都只能停在背诵。

把 16 节折成一张纸：左列三件事，中列机制与策略，右列证据与版本边界。三条判据对应三种能力：会算、会测、会判断。**能算**：给定任务集算 FIFO/SJF/RR 的周转与响应；给定页框数与访问串算四种替换的缺页；给定盘参数拆出寻道、旋转、传输；给定崩溃点说出日志该重放还是丢弃。**能测**：`taskset` 绑核看份额，`smaps` 看 Size/Rss，`strace` 数 `fsync` 与 `renameat`，`filefrag` 看 extent；测不出来时，说得出是权限、工具还是架构挡住的。**能判断**：先分三件事，再分机制与策略，最后核对版本与架构——CFS 还是 EEVDF、ext4 的 `data=` 模式、x86-64 还是 aarch64 的 PTE 位号。逐条打勾的 19 项在[学习目标自检表](ch13-checklist.md)。

::: errata 本章口径的三条边界
1. **三类数字不能混用。** 模拟器输出只由代码决定，换机器不变；标「VM 实测」的读数只在这台 Ubuntu 24.04 aarch64 上成立；`fio`、RAID 重建、`perf sched`、`dumpe2fs` 属未实测。
2. **字段与位号随版本、架构漂移。** 6.6 起默认 EEVDF，本机 `/proc/<pid>/sched` 只有 `se.slice`；PTE 的 `P/RW/US/A/D` 是 x86-64 的位号，aarch64 不照搬。
3. **模型不是地形。** 本章给的是 OSTEP 式的模型与 Linux 的落点，不是内核源码的逐行结论；换内核版本、换挂载选项，先复核再引用。
:::

如果只记住一件事，那就是**任何操作系统结论都要带三个限定：哪件、哪层、哪台机器**。没有限定的结论，换一台机器就会变成谣言；补上一个限定，常常比多背十个名词有用。每次下结论前，先把它默念一遍。

**下一站**：[1.14 计算机组成与三套 ISA](ch14.md) 把本章的「机器」往下拆一层：同一段 C 在 x86-64、ARM64、RISC-V 上各变成什么指令，流水线、cache 与内存模型又怎样决定「同一条指令为什么有快有慢」。本章说的调度、缺页与日志，最终都要落在那套指令、寄存器与存储层次上。

::: method 即时自测 · 1.13
**Q1（算）** 三个任务 A(0,6)、B(1,3)、C(2,1)，用 FIFO 与 RR(片长 2) 调度，算平均周转与平均响应。

**Q2（辨析）** nice 0 对 10，为什么不能用一个比例概括它们的 CPU 份额？绑核与不绑核各看到什么？

**Q3（应用）** 程序按「写临时文件 → `fsync` → `rename`」执行，漏了最后一步。断电后可能看到什么？用 `strace` 怎么证明漏了？

**Q4（迁移）** 一个服务偶发变慢，`vmstat` 的 `si/so` 为 0、CPU 也不满，同事要加 swap。你先问哪三个问题、查哪三条证据？

::: sol 答案
**A1** FIFO：A 0–6，B 6–9，C 9–10；周转 A6、B8、C8，平均 7.33；响应 0、5、7，平均 4。RR(2)：A 0–2，B 2–4，C 4–5，A 5–7，B 7–8，A 8–10；周转 A10、B7、C3，平均 6.67；响应 0、1、2，平均 1。

**A2** 份额只在同一个 runqueue 内按权重分：绑同一核时本机 nice 0 对 10 约 90.1% 对 9.7%，0 对 19 约 98.3% 对 1.3%；分绑两核时各占一个核，都接近 100%，比例消失。看 `/proc/<pid>/sched` 的 `se.sum_exec_runtime`，不要拿 nice 当绝对优先级。

**A3** 内容可能已经在新名字下，但目录项可能没落盘：断电后新名字可能不在，旧名字或临时文件可能残留。`strace -e trace=fsync,renameat` 应看到两次 `fsync` 夹一个 `renameat`；只有一次 `fsync` 就说明漏了父目录。

**A4** 先问属于哪件（CPU、内存还是持久化），再问坏在机制还是策略，最后问环境（cgroup 限额、内核版本、文件系统）。证据分别看 `/proc/pressure/cpu` 与 `/proc/<pid>/sched`、`smaps` 与 `vmstat`、`iostat -x` 与 `strace`；三条都没有 swap 压力的证据，就不要先加 swap。
:::
:::
