[1.11](ch11.md) 的 fork 服务器每来一个连接就复制一个进程：地址空间隔离，写起来简单，但连接数上千时，页表（虚拟地址到物理地址的映射表）复制和上下文切换会把 CPU 吃光。要支撑更多连接，必须让多个执行流**共享**同一份地址空间，或者让一个执行流同时管理多条连接。前者是线程，后者是 I/O 多路复用。

并发（concurrency）与并行（parallelism）不是一回事。并发是「多个任务在时间上重叠」，单核分时也能并发；并行是「多个任务在同一时刻真正执行」，需要多核。并发解决的是「等待时别闲着」，并行解决的是「算得更快」。两者的收益模型不同：前者看吞吐与延迟，后者受 Amdahl 定律约束（[1.1.9](ch01.md)）。

这一章的主线是**共享状态**。只要两个执行流能读写同一块内存，就必须回答：谁先谁后？读到的值是否完整？失败时怎么回滚？信号量、互斥锁、条件变量、线程池，都是围绕这三个问题的工程答案。[1.12.7](#sec-1.12.7) 把「共享内存 + 锁」换成「单线程 + 事件」，这是另一种同样重要的并发模型。

前七节给的是「会用」：三种模型、`pthread` 基本 API、锁与条件变量、信号量、线程池、死锁、`epoll`。后九节补「用对」：线程的完整生命周期与错误码（1.12.8）、C11 原子与内存序（1.12.9）、锁在内核里怎么实现（1.12.10）、读写锁/seqlock/RCU 的取舍（1.12.11）、死锁的复现与取证线索（1.12.12）、线程池的容量与关闭语义（1.12.13）、C11/C++/Rust 三语言对照（1.12.14）、TSan 与 `perf` 实验（1.12.15）、十八条陷阱（1.12.16）。

## 1.12.1 三种并发模型 {#sec-1.12.1}

这一节回答：同样要在一台 4 核机器上同时服务很多请求，「一个请求一个进程」「一个请求一个线程」「一个线程照看全部连接」这三种做法，各自把成本放在了哪里？

::: preview 先抓住一件事
三种模型的差别不在谁更先进，而在**地址空间共不共用**。进程不共用，通信必须过内核；线程共用，通信免费，踩踏也免费；事件循环连执行流都只留一个，把「同时进行」换成了「登记 + 回调」。选型先数连接、再问每请求会不会阻塞、最后看要不要隔离。
:::

先只测「创建」这一件事。下面的程序把同一动作各做 200 遍：一次 `fork` 出立刻退出的子进程并用 `waitpid` 收尸，一次 `pthread_create` 出立刻返回的线程并用 `pthread_join` 回收。

```c
/* spawn_cost.c：fork+wait 与 pthread_create+join 的单次成本 */
#define _GNU_SOURCE
#include <pthread.h>
#include <stdio.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

#define N 200

static double now_ms(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec * 1e3 + (double)ts.tv_nsec / 1e6;
}

static void *noop(void *arg) { (void)arg; return NULL; }

int main(void)
{
    double t0 = now_ms();
    for (int i = 0; i < N; i++) {
        pid_t pid = fork();
        if (pid == 0)
            _exit(0);                   /* 子进程立刻走，不碰父进程数据 */
        if (pid < 0 || waitpid(pid, NULL, 0) < 0)
            return 1;
    }
    double tf = now_ms() - t0;

    t0 = now_ms();
    for (int i = 0; i < N; i++) {
        pthread_t t;
        if (pthread_create(&t, NULL, noop, NULL) != 0)   /* 返回错误码，不设 errno */
            return 1;
        pthread_join(t, NULL);
    }
    double tt = now_ms() - t0;

    printf("fork+wait   : %7.2f ms  %6.3f ms/次\n", tf, tf / N);
    printf("pthread+join: %7.2f ms  %6.3f ms/次\n", tt, tt / N);
    printf("ratio       : %.1fx\n", tf / tt);
    return 0;
}
```

在本机（Ubuntu 24.04.5，aarch64，4 vCPU）编译并连跑两次，实测输出：

```text
$ cc -std=c17 -O2 -Wall -Wextra -Werror -pthread spawn_cost.c -o spawn_cost
$ ./spawn_cost
fork+wait   :   38.38 ms   0.192 ms/次
pthread+join:   20.45 ms   0.102 ms/次
ratio       : 1.9x
$ ./spawn_cost
fork+wait   :   42.87 ms   0.214 ms/次
pthread+join:   16.50 ms   0.083 ms/次
ratio       : 2.6x
```

一次 `fork` 约 0.2 ms，一个线程约 0.1 ms，只差两倍多。这个数字会让人失望，因为「线程比进程轻」常被讲成十倍差。差得少的原因是：这里的父子进程几乎没有内存，`fork` 要复制的页表（把虚拟地址翻译成物理地址的那张表）条目很少；而线程虽然不复制页表，却要 `mmap` 一块 8 MiB 的虚拟栈、登记一个内核任务。两边都还在「几百微秒」这一档。

差距拉开的地方在地址空间大小。进程里有几百 MB 已触碰的内存时，`fork` 即使有写时复制（copy-on-write, COW），也要为父进程的每一页建立一份页表项，页表越深、条目越多，`fork` 越慢；线程只共用同一份页表，加一个线程不动它。所以「进程重」这句结论要带条件：**小进程的 fork 并不贵，贵的是带着大地址空间 fork**。

第二个证据是线程在系统里长什么样。让一个程序开 3 个线程各睡 5 秒，从外面看：

```c
/* threads_demo.c：1 个主线程 + 3 个睡 5 秒的线程 */
#define _GNU_SOURCE
#include <pthread.h>
#include <stdio.h>
#include <unistd.h>

static void *sleeper(void *arg)
{
    printf("thread %ld started\n", (long)arg);
    sleep(5);                       /* 留在系统里，方便从外面观察 */
    return NULL;
}

int main(void)
{
    pthread_t t[3];

    printf("pid=%d\n", (int)getpid());
    for (long i = 0; i < 3; i++)
        pthread_create(&t[i], NULL, sleeper, (void *)i);
    for (int i = 0; i < 3; i++)
        pthread_join(t[i], NULL);
    return 0;
}
```

`ps -L` 每个线程一行，`PID` 四行相同、`LWP` 各不相同。上面那个 `493092` 是那一次运行时的 pid，你自己跑时换成程序打印出来的值。`LWP` 就是轻量进程号（light weight process），也就是内核眼里的线程 ID，和 `gettid()` 的返回值一致；`/proc/<pid>/task/` 下的四个目录正是这四个 TID。内核没有单独的「线程」结构体，一个线程就是一个可调度任务（task），只是同一组的任务共享 `mmap`、文件表和信号处理表。这是 1.12.2 所有麻烦的源头。

::: def 定义 1.12.1 · 三种并发模型 {#def-1.12.1}
按三件事区分模型：**执行单元**（谁被调度）、**地址空间**（谁能直接读写谁的内存）、**事件来源**（阻塞等 I/O，还是等就绪通知）。执行单元是进程、地址空间独立——多进程模型，通信走管道、共享内存或 socket。执行单元是线程、地址空间共享——多线程模型，通信就是读写同一个变量。执行单元只有一个线程、把 fd 注册给内核等通知——事件驱动模型，通信靠回调改状态机。三种都能服务同样的请求，差别是把成本记在「创建」「同步」还是「状态机复杂度」上。
:::

| 模型 | 执行单元 | 地址空间 | 通信 | 优点 | 代价 |
|:--|:--|:--|:--|:--|:--|
| 多进程 | `fork` 出的进程 | 独立 | 管道/共享内存/socket | 隔离好，崩溃不扩散 | 创建重，IPC 复杂 |
| 多线程 | `pthread` | 共享 | 全局变量/堆 | 轻量，共享数据直接可见 | 数据竞争、死锁 |
| 事件驱动 | 单线程 + 非阻塞 fd | 共享（单线程） | 回调/状态机 | 无锁、连接数大 | 阻塞调用会卡住全部 |

上一段测的只是创建；创建是一次性成本，跑起来更常付的是切换成本。进程切换要换地址空间：内核把页表基址寄存器（aarch64 上是 `TTBR0`）指向新进程的页表，旧进程的地址翻译缓存（translation lookaside buffer, TLB）大面积失效，切回来要重新填。线程切换不换页表，同一份地址翻译继续有效，所以更快、缓存也更热。代价是缓存里躺着别人的数据：两个线程改同一个缓存行（缓存与内存之间搬运的固定块）时，这份「热」立刻变成争用。

事件驱动把「等」也省掉了：没有请求在跑的时候，线程睡在 `epoll_wait` 上，一条连接一个状态机，10 万条连接也只占一个执行流。它也不需要锁，因为只有一个执行流在改状态——锁本来就是为了防第二个执行流。代价是**不能阻塞**：在回调里读一次磁盘，所有连接一起停摆。它的完整机制在 [1.12.7](#sec-1.12.7)，这里只要记住它换掉的是「执行流」，不是「地址空间」。

选型可以按三个问题走。连接数是几百还是几万？每请求里有没有必须阻塞的调用（磁盘、DNS、同步 RPC）？一个请求崩掉能不能拖垮别人？连接多、几乎不阻塞、隔离要求低，选事件循环；请求少但每个都重，选线程；插件或第三方代码不可信，选进程。真实系统多数是混的：主线程 `epoll` 收连接，把请求丢给线程池，池里做完再交回事件循环发出去（[1.12.5](#sec-1.12.5)）。混用不是免费的组合，它要求两边都守规矩：事件循环里不能阻塞，线程池里要防竞争，跨线程交接缓冲区还要说清谁拥有、谁释放。

::: errata 关于「哪个模型更快」的三个误解
1. **「线程创建几乎免费，所以每请求开一个线程也行」**——便宜不等于免费。本机实测一个线程约 0.08–0.10 ms，每秒一万请求就是每秒一秒的纯创建开销，还不算 8 MiB 虚拟栈和内核调度成本；线程池存在的理由就在这里。
2. **「多进程更安全，所以总是更好」**——隔离挡住的是崩溃扩散，挡不住逻辑错误。跨进程共享一个计数器要靠共享内存加进程间锁，比线程里加锁更麻烦；管道单次写入超过 `PIPE_BUF`（Linux 上 4096 字节）还可能被其他写者插进来。隔离是有价钱的。
3. **「事件驱动没有并发问题」**——单线程确实没有数据竞争，但有重入与状态机 bug：一个回调处理到一半又触发另一个回调，共享的缓冲区就可能被改两次。它的难点从「锁」换成了「状态」，不是消失。
:::

### 1.12.1 小结

三种模型的成本分别记在创建（进程）、同步（线程）、状态机（事件）上。选型先数连接、再问阻塞、最后看隔离；不要拿「线程轻」当无限开线程的理由。如果只记住一件事：**共享地址空间是线程的全部优势，也是它的全部麻烦**。

**Q2（辨析）** 本机测出 fork 只比 pthread 慢两倍多，这和「进程很重」矛盾吗？什么条件下差距会拉开？

**Q3（应用）** 一个网关要维持 5 万条空闲长连接，每连接每秒几十字节；另一个服务每请求要读一次 100 ms 的磁盘。分别选哪种模型，理由是什么？

**A1** `PID` 是线程组号（进程号），四行相同；`LWP` 是每个线程的内核 TID，等于 `gettid()`。`/proc/<pid>/task/` 下的目录名就是这些 TID。

**A2** 不矛盾。这里父子进程几乎没有内存，`fork` 要复制的页表条目很少；线程虽然不复制页表，仍要建栈、登记任务。进程带着几百 MB 已触碰内存时，`fork` 要为每页准备页表项，差距才拉开。

**A3** 前者选事件循环：连接多、流量小、几乎不阻塞，一个 `epoll` 线程足够。后者不能把 100 ms 磁盘 I/O 放进事件循环，否则所有连接一起等；应让事件循环只管网络，把磁盘操作交给线程池或异步 I/O。

## 1.12.2 线程：共享地址空间带来的自由与麻烦 {#sec-1.12.2}

这一节回答：线程共享地址空间，通信确实免费了，可为什么连 `counter++` 这种一句话的加法也会少加一半？「少加」到底少在哪一条指令上？

::: preview 先抓住一件事
`counter++` 不是一条指令，是「读、加、写」三步。两个线程的三步可以交错，于是两次加法只落在一次结果上，这叫**丢失更新**。C11 把这种没有同步的并发读写定义为数据竞争，属于未定义行为——它不只是「偶尔算错」，编译器还有权把你的循环整个改写掉。
:::

先看现象。4 个线程，每个把同一个全局变量加 100 万次，期望 400 万。

```c
/* race_lab.c：4 线程各 counter++ 100 万次
 * cc -std=c17 -O0 -g -Wall -Wextra -pthread race_lab.c -o race_lab
 */
#define _GNU_SOURCE
#include <pthread.h>
#include <stdio.h>

#define NTHREADS 4
#define NLOOP    1000000L

static long counter;                    /* 共享，无同步 */

static void *worker(void *arg)
{
    (void)arg;
    for (long i = 0; i < NLOOP; i++)
        counter++;                      /* 读-改-写，非原子 */
    return NULL;
}

int main(void)
{
    pthread_t t[NTHREADS];

    for (int i = 0; i < NTHREADS; i++)
        if (pthread_create(&t[i], NULL, worker, NULL) != 0)
            return 1;
    for (int i = 0; i < NTHREADS; i++)
        pthread_join(t[i], NULL);

    printf("counter=%ld expected=%ld\n", counter, (long)NTHREADS * NLOOP);
    return 0;
}
```

用 `-O0` 编译，连跑多次，实测八次的结果：

```text
counter=2016895 expected=4000000
counter=1913248 expected=4000000
counter=2009083 expected=4000000
counter=2085007 expected=4000000
counter=2067515 expected=4000000
counter=2009907 expected=4000000
counter=2044469 expected=4000000
counter=1999283 expected=4000000
```

每次都少，且每次都不同：十次里落在 174 万到 223 万之间，大约是期望值的一半。少掉的不是「几次」，是几十万到两百万次。

为什么会少一半？因为 `counter++` 在机器层被拆成三步：把 `counter` 读进寄存器、寄存器加一、把寄存器写回 `counter`。两个线程的三步可以这样交错：

<pre class="layout">
时刻    T1                          T2                       counter
 t1     load counter → r1(100)                                100
 t2                                 load counter → r1(100)    100
 t3     r1 = r1 + 1                                           100
 t4                                 r1 = r1 + 1               100
 t5     store r1 → counter                                    101
 t6                                 store r1 → counter        101
&#8203;
 两次加法、一次结果：T2 读到的是 T1 写入之前的旧值，T1 的那一次被覆盖掉了
</pre>

一半这个比例也有意思：两个线程几乎同步地跑同一段循环，撞上的概率接近抛硬币，所以丢失接近 50%。这不是「概率问题」的另一种说法——C11 的规则更硬：两个线程访问同一内存、至少一个在写、之间没有任何同步，就是**数据竞争**（data race），行为未定义（undefined behavior, UB）。UB 的意思不是「结果随机」，而是「标准不再规定程序该做什么」，编译器可以做任何假设。

共享地址空间让通信免费，也让踩踏免费——任何线程都能在别人算到一半时改掉那个变量。所以共享与私有的边界要记清：共享的是全局变量、静态变量、堆、文件描述符表（进程打开文件的编号表）、当前工作目录、`umask`，以及信号处理函数表；私有的是栈与寄存器、线程 ID、`errno`、线程局部存储（thread-local storage, TLS）、信号掩码和 `pthread_cleanup` 栈。写多线程代码时，先判断这个变量落在哪一栏：落在共享栏，就要回答「谁在读它、谁在写它、两者之间靠什么排序」，这个问题在 1.12.9 会变成 happens-before。

::: def 定义 1.12.2 · 数据竞争与临界区 {#def-1.12.2}
**数据竞争**：两个线程访问同一内存位置，至少有一个是写，且两次访问之间没有同步（没有锁、没有原子操作、没有条件变量）建立先后顺序。C11 直接把它定为未定义行为。**临界区**：一段访问共享数据的代码，必须保证同一时刻只有一个线程在里面执行；锁、信号量、原子操作都是把这段代码「串起来」的手段。**丢失更新**：两个线程都基于同一个旧值算出新值并写回，后写的覆盖先写的，一次更新凭空消失。
:::

修法之前先看一个反直觉的现象：同一份源码换成 `-O2`，连跑 20 次，20 次都是 `counter=4000000`。有人因此以为「优化打开了，问题就没了」。把 `worker` 反汇编出来看，就知道不是这么回事：

```text
00000000000009e0 <worker>:
 9e0:  adrp  x2, 20000 <__data_start>
 9e4:  mov   x0, #0x0
 9e8:  ldr   x1, [x2, #24]        ; 读一次 counter
 9ec:  add   x1, x1, #0xf4, lsl #12
 9f0:  add   x1, x1, #0x240       ; 一次加 0xf4<<12 + 0x240 = 1000000
 9f4:  str   x1, [x2, #24]        ; 写回一次
 9f8:  ret
```

循环没了。编译器认定「这 100 万次加法里不会有人插进来改 `counter`」，于是把整个循环折叠成「读一次、加 100 万、写一次」。四个线程各做一次读改写，只要这四次不重叠，结果就正好是 400 万——这 20 次是运气，不是正确性。若四次读发生在任何一次写之前，结果会小得多。两种结果都合法，因为 UB 之下编译器不欠你任何东西。

这也是为什么「压测跑过了」证明不了没有竞争：换优化级别、换 CPU、换内核调度，同一份代码的表现可以完全不同。想让它确定地对，只有三种修法。

修法的完整程序如下，四种模式用同一个二进制跑，便于对照：

```c
/* race_fix.c：none / mutex / atomic / local 四种写法
 * cc -std=c17 -O2 -Wall -Wextra -Werror -pthread race_fix.c -o race_fix
 * ./race_fix none | mutex | atomic | local
 */
#define _GNU_SOURCE
#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>
#include <string.h>
#include <time.h>

#define NTHREADS 4
#define NLOOP    1000000L

static long counter;
static atomic_long acounter;
static pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;
static int mode;                        /* 0 none 1 mutex 2 atomic 3 local */

static double now_ms(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec * 1e3 + (double)ts.tv_nsec / 1e6;
}

static void *worker(void *arg)
{
    (void)arg;
    long local = 0;

    for (long i = 0; i < NLOOP; i++) {
        switch (mode) {
        case 0:
            counter++;                                  /* 竞争：UB */
            break;
        case 1:
            pthread_mutex_lock(&mtx);                   /* 锁：三步合成一段 */
            counter++;
            pthread_mutex_unlock(&mtx);
            break;
        case 2:
            atomic_fetch_add_explicit(&acounter, 1, memory_order_relaxed);
            break;
        case 3:
            local++;                                    /* 只碰栈，不碰共享 */
            break;
        }
    }
    if (mode == 3) {                                    /* 最后合并一次 */
        pthread_mutex_lock(&mtx);
        counter += local;
        pthread_mutex_unlock(&mtx);
    }
    return NULL;
}

int main(int argc, char **argv)
{
    if (argc != 2)
        return 2;
    if (strcmp(argv[1], "none") == 0)        mode = 0;
    else if (strcmp(argv[1], "mutex") == 0)  mode = 1;
    else if (strcmp(argv[1], "atomic") == 0) mode = 2;
    else if (strcmp(argv[1], "local") == 0)  mode = 3;
    else return 2;

    pthread_t t[NTHREADS];
    double t0 = now_ms();
    for (int i = 0; i < NTHREADS; i++)
        if (pthread_create(&t[i], NULL, worker, NULL) != 0)
            return 1;
    for (int i = 0; i < NTHREADS; i++)
        pthread_join(t[i], NULL);
    double ms = now_ms() - t0;

    long got = (mode == 2) ? atomic_load(&acounter) : counter;
    printf("%-6s counter=%-8ld expected=%-8ld %7.1f ms\n",
           argv[1], got, (long)NTHREADS * NLOOP, ms);
    return (got == NTHREADS * NLOOP) ? 0 : 1;   /* 计数不对就返回 1 */
}
```

四种模式各跑一次，实测：

```text
none   counter=2308792  expected=4000000      2.0 ms     exit=1
mutex  counter=4000000  expected=4000000     97.9 ms     exit=0
atomic counter=4000000  expected=4000000     25.8 ms     exit=0
local  counter=4000000  expected=4000000      0.8 ms     exit=0
```

| 手段 | 关键写法 | 适用 | 本例代价 |
|:--|:--|:--|:--|
| 互斥锁 | `pthread_mutex_lock` 包住整个读改写 | 临界区里要改多个变量、有分支 | 97.9 ms |
| 原子操作 | `atomic_fetch_add_explicit(..., memory_order_relaxed)` | 单个计数器、标志位 | 25.8 ms |
| 避免共享 | 每线程累加局部变量，最后合并一次 | 统计、求和这类可分解的活 | 0.8 ms |

三种都返回 0，`none` 返回 1。代价差了两个数量级，原因不在「锁慢」，而在**每一百万次加法都要经过一次共享内存的往返**：mutex 要做两次原子操作（加锁、解锁），还可能进内核；原子加法只有一条不可分割的指令，但仍要独占那条缓存行；局部累加则完全不碰共享内存，四个线程各在自己的寄存器里加，最后才合并一次。所以「避免共享」永远排第一，原子第二，锁第三。

还有一条容易误读的证据。把竞争版用 `taskset` 钉到一个核上，连跑 10 次，10 次全是 4000000：

```text
$ for i in $(seq 10); do taskset -c 0 ./race_lab; done
（10 次均为 counter=4000000 expected=4000000）
```

这不说明代码变安全了。单核上两个线程轮流跑，`load → add → store` 三条指令之间能被抢占的窗口只有几条指令宽，撞上的概率极小；四核上两个核真的同时停在这三步里，丢失就成了常态。竞争取决于**交错**，不取决于核数——单核上换一个更长的临界区、或让线程在中间被信号打断，同样会丢。反过来，多核上「这次没丢」也不能当证据。

::: errata 关于竞争的四个误解
1. **「加 `volatile` 就好了」**——`volatile` 只要求每次都真的读内存、写内存，不管原子性，也不建立线程间的先后顺序。给上面的 `counter` 加上 `volatile` 再用 `-O2` 编译，本机五次实测是 1057861、2156025、1033299、1292481、1186493，比不加还差——它只是挡住了编译器的折叠，把原始的三步暴露得更彻底。
2. **「`-O2` 跑出 400 万，说明代码是对的」**——那 20 次是四个线程的读改写恰好没有重叠。UB 之下同一个二进制在别的机器、别的负载上可以给出别的数字，编译器也可以换成别的实现，两者都不算 bug。
3. **「单核不会有数据竞争」**——本机把 4 个线程钉在一个核上，10 次全对。那只是三条指令之间的窗口太窄没撞上；一旦临界区变长、或者在中间被信号打断，单核同样会丢。竞争是「交错」问题，不是「核数」问题。
4. **「有原子操作就不需要锁」**——原子只保证**一个对象**的读改写不可分割。两个字段必须一起更新（比如 `count` 与 `sum`）时，两个独立的原子操作之间仍可被插入，别的线程会看到「加了 count 还没加 sum」的中间态；这时要么用锁，要么把它们打包进一个结构体再整体原子替换。
:::

### 1.12.2 小结

`counter++` 是三步，不是一步；共享地址空间让这三步对谁都可见，于是两次加法可以只落一次结果。修法按代价排：先想能不能不共享，再想能不能用一个原子量，最后才用锁。如果只记住一件事：**数据竞争是未定义行为，不是「偶尔算错」——任何一次「跑对了」都不构成证据**。

## 1.12.3 互斥锁与条件变量 {#sec-1.12.3}

这一节回答：一个线程要等「缓冲区里有货」「标志位被置上」这类条件，怎么写才能既不空转烧 CPU，又不把通知弄丢？

::: preview 先抓住一件事
条件变量不是「一个能查询的变量」，而是「有人改了状态就敲一下门」。敲门没有记忆，你睡觉之前也没人替你记账；所以必须自己维护那个状态（叫谓词），并且每次被敲醒都重新看一遍。三条规矩：`wait` 之前必须持锁，醒来必须用 `while` 重判，改状态必须在持锁时做、做完再通知。
:::

先看最朴素的做法：不等人敲门，自己隔一会儿去看一眼。

```c
/* 轮询版：用 sleep 代替等待（反例） */
static void wait_ready(atomic_int *ready)
{
    struct timespec nap = { 0, 20 * 1000 * 1000L };   /* 20 ms */

    while (atomic_load(ready) == 0)
        nanosleep(&nap, NULL);                        /* 睡多久全靠猜 */
}
```

生产者 5 ms 后把标志位置上，消费者每 20 ms 看一次。本机实测三次，消费者发现的时间是 20.3 ms、21.8 ms、20.6 ms——事件发生在 5 ms，人却在 20 ms 之后才知道。把间隔调成 1 ms，延迟会降，代价是每条等待的线程每秒醒 1000 次；一千条连接就是每秒一百万次空转。这就是「用 sleep 代替等待」的全部问题：**延迟由你猜的间隔决定，CPU 由等待者数量决定，两者都不由事件决定**。

条件变量的做法是反过来：等待者睡死，改状态的人负责叫醒。先看两个消费者等同一件货，用 `if` 和用 `while` 的差别。

```c
/* cv_lab.c：两个消费者等一件货
 * cc -std=c17 -O2 -Wall -Wextra -Werror -pthread cv_lab.c -o cv_lab
 * ./cv_lab if | while
 */
#define _GNU_SOURCE
#include <pthread.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

#define NCONS 2

static pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  cv  = PTHREAD_COND_INITIALIZER;
static int items;                       /* 货架上还有几件 */
static int done;                        /* 生产者收工 */
static int got[NCONS];                  /* 每个消费者取到几件 */
static int use_if;

static void *consumer(void *arg)
{
    long id = (long)arg;

    pthread_mutex_lock(&mtx);
    if (use_if) {
        if (items == 0)                 /* 反例：只判一次 */
            pthread_cond_wait(&cv, &mtx);
        items--;                        /* 以为有货，直接取 */
        got[id]++;
    } else {
        while (items == 0 && !done)     /* 正例：醒来重判 */
            pthread_cond_wait(&cv, &mtx);
        if (items > 0) {
            items--;
            got[id]++;
        }
    }
    pthread_mutex_unlock(&mtx);
    return NULL;
}

int main(int argc, char **argv)
{
    if (argc != 2)
        return 2;
    use_if = strcmp(argv[1], "if") == 0;

    pthread_t t[NCONS];
    for (long i = 0; i < NCONS; i++)
        if (pthread_create(&t[i], NULL, consumer, (void *)i) != 0)
            return 1;

    usleep(100 * 1000);                 /* 让消费者先进入等待 */
    pthread_mutex_lock(&mtx);
    items = 1;                          /* 只有一件货 */
    pthread_cond_broadcast(&cv);        /* 两个人一起醒 */
    pthread_mutex_unlock(&mtx);

    usleep(100 * 1000);                 /* 留窗口让两人都去取 */

    pthread_mutex_lock(&mtx);
    done = 1;
    pthread_cond_broadcast(&cv);        /* 唤醒还在睡的 */
    pthread_mutex_unlock(&mtx);

    for (int i = 0; i < NCONS; i++)
        pthread_join(t[i], NULL);
    printf("items=%d (初值 1) got=[%d,%d]\n", items, got[0], got[1]);
    return 0;
}
```

两种模式各跑三次，实测：

```text
$ ./cv_lab if
items=-1 (初值 1) got=[1,1]
items=-1 (初值 1) got=[1,1]
items=-1 (初值 1) got=[1,1]
$ ./cv_lab while
items=0 (初值 1) got=[1,0]
items=0 (初值 1) got=[1,0]
items=0 (初值 1) got=[1,0]
```

`if` 版把一件货发给了两个人，`items` 被取成 `-1`，三跑三中；`while` 版第二个人醒来发现没货，回去接着睡，货架归零。两次运行的唯一差别，是醒来之后有没有再看一眼条件。这不是小概率事件——只要用 `broadcast` 叫醒两个等待者、而资源只有一个，`if` 每次都会翻车。

回到那段程序的 `pthread_cond_wait(&cv, &mtx)`：第二个参数必须是一把**已经锁住**的 mutex。很多人第一次写会问，等条件为什么还要带把锁？

因为「检查条件」和「进入睡眠」之间有一条缝。假如没有锁：A 检查 `items == 0` 成立，正准备睡；B 恰好在这时放入一件货并 `signal`。此刻 A 还没挂进等待队列，通知找不到人，直接被丢弃；A 随后睡着，而第二件货可能再也不来。这叫**丢失唤醒**（lost wakeup）。锁把这条缝堵上：B 要改 `items` 必须先拿到锁，于是只有两种可能——B 抢在 A 检查之前改完（A 醒来会看到 `items == 1`，根本不用睡），或者 A 已经睡下（`signal` 能找到等待者）。`pthread_cond_wait` 内部把「释放锁」和「挂进等待队列」做成一个不可分割的动作，所以中间没有第三方能插进来。

顺便把锁的职责说清。锁保护的是**不变量**（invariant），不是若干行代码：先写下「哪些字段必须一起被看到、一起被改」，再决定加锁范围。`items` 和 `got[id]` 必须一起更新，所以它们在同一个临界区里；`printf` 不属于不变量，应该放到锁外。临界区里也不要调用别人的回调、不要做 I/O——持锁期间所有同路的线程都在排队，1.12.5 的线程池就是「弹出任务、立刻解锁、再执行」。

条件变量的语义常被叫 **Mesa 语义**：`signal` 只是说「状态可能变了，你再看一眼」，不承诺条件此刻为真。原因有三个：被叫醒的线程要先抢锁，抢到之前状态可能又被改回去；`broadcast` 叫醒多个，只有一个能拿到那件货；POSIX 还允许**虚假唤醒**（spurious wakeup）——没有任何人通知，`wait` 也可能返回。三者合起来，结论只有一个：醒来必须重判，用 `while` 不用 `if`。这一条没有例外，包括你确信「只有一个等待者」的时候——`while` 的代价只是一次比较，而一次误判就是一个负数。

| 环节 | 正确写法 | 写错的后果 |
|:--|:--|:--|
| 检查 + 睡 | 持锁，`while (!谓词) pthread_cond_wait(&cv, &mtx)` | 用 `if`：醒来的线程不重判，取走不存在的货（实测 `items=-1`） |
| 改状态 | 持锁改，改完再 `signal`/`broadcast` | 不持锁改：通知落进「检查完、还没睡」的缝里，等待者永睡 |
| 唤醒 | 一个等待者用 `signal`，多个条件共用一把锁才用 `broadcast` | 该广播却 `signal`：其余等待者明明条件已成立，却没人叫 |

三行是三条独立的规矩，缺一条的表现不同：缺 `while` 是「醒错了」，不持锁改是「叫早了」，该广播却 `signal` 是「叫漏了」。排障时先分两类：线程一直不醒，去查通知有没有落进「检查完、还没睡」那条缝；线程醒了但数据不对，去查醒来后有没有重判谓词。

::: def 定义 1.12.3 · 条件变量与谓词 {#def-1.12.3}
**条件变量**（condition variable）是一个等待队列加一对操作：`wait` 把当前线程挂进队列并原子地释放绑定的 mutex，`signal`/`broadcast` 从队列里取一个/全部线程唤醒。它自己不保存任何状态，**没有记忆**。**谓词**（predicate）是你要等的那个条件，由普通变量表达，例如 `items > 0`、`shutdown == 1`；谓词归你维护，条件变量只负责「有人改了谓词就敲门」。所以条件变量永远和一把 mutex 绑定：mutex 保护谓词，条件变量负责睡眠与唤醒。
:::

::: errata 关于条件变量的四个误解
1. **「`signal` 会记下来，等下次 `wait` 再用」**——不会。没有等待者时 `signal` 什么也不做，通知直接消失。这就是为什么「先放货、后等人」的顺序里，等待者会一直睡；信号量没有这个问题，差别在 1.12.4 展开。
2. **「`broadcast` 更安全，一律用它」**——`broadcast` 叫醒所有人，大家抢同一把锁、抢到后重判、发现条件不成立又睡回去，这叫惊群。等待者上百时，一次 `broadcast` 就是上百次无效唤醒；只有「多个等待者等不同谓词」或「一批状态同时变化」才需要它。
3. **「用 `sleep` 轮询最省事」**——实测 5 ms 的事件被 20 ms 的轮询拖到 20.3 ms 才被发现。延迟由猜的间隔决定，CPU 由等待者数量决定；等待者一多，两条都不可控。
4. **「`pthread_cond_wait` 返回了就说明条件成立」**——虚假唤醒是 POSIX 明确允许的，Mesa 语义下还有「醒了但货被别人抢走」。返回只说明「该再看一眼」，不说明「可以干活」。
:::

### 1.12.3 小结

锁保护谓词，条件变量负责睡眠与唤醒，两者必须成对使用。`wait` 前持锁是为了堵住「检查完、还没睡」那条缝，醒来用 `while` 重判是为了对付虚假唤醒和抢跑。如果只记住一件事：**条件变量是门铃，不是门牌——按了不一定有人应，应了也不一定还是你要找的人**。

**Q1（记忆）** `pthread_cond_wait(&cv, &mtx)` 内部依次做了哪三件事？为什么第二个参数必须是一把已锁住的 mutex？

**Q2（辨析）** 把 `while (!items) wait(...)` 改成 `if (!items) wait(...)`，在只有一个消费者时几乎不出错，为什么两个消费者就会翻车？

**Q3（应用）** 一个线程池有 4 个 worker 等任务、1 个线程等「队列有空位」。它们共用一把锁和两个条件变量。提交任务时该用 `signal` 还是 `broadcast`？

::: sol 答案
**A1** 原子地释放 mutex 并把自己挂进条件变量的等待队列；睡眠；被唤醒后重新获取 mutex 再返回。释放锁与入队是一个不可分割的动作，所以改状态的线程不可能插在「检查完、还没睡」之间。

**A2** 一个消费者时，被唤醒的就是它，货一定还在；两个消费者时 `broadcast` 会叫醒两个，先抢到锁的取走货，后一个用 `if` 不重判就继续执行 `items--`，把货架取成负数（实测 `items=-1`、两个人各记一件）。

**A3** 提交任务只让「等任务」的 worker 醒一个，用 `signal` 配 `not_empty`；队列空出一个位置时也让「等空位」的提交者醒一个，用 `signal` 配 `not_full`。同一条件下有多个不同类型的等待者（比如等任务也等关闭）才需要 `broadcast`。

## 1.12.4 信号量与生产者-消费者 {#sec-1.12.4}

条件变量没有记忆，信号量有计数——这一点决定了生产者-消费者要三个信号量，还是一个 mutex 加两个条件变量。

这一节回答：一件货从生产到消费，中间那条有界缓冲区该用几个数字来管？为什么「先等资源、再拿锁」的顺序写反就会死锁？

::: preview 先抓住一件事
信号量就是一个**会记账的票箱**：`sem_wait` 是「抽一张票，票没了就等」，`sem_post` 是「还一张票，顺便叫醒一个等票的人」。票数不会因为当时没人等就丢掉，这就是「有记忆」。有界缓冲区要管三件事——还有几个空槽（`empty`）、已有几件货（`full`）、`in/out` 两个下标别被同时改（`mutex`），三个数的初值就是三份资源的数量。
:::

信号量（semaphore）是一个非负整数，只允许两个原子操作：

- `sem_wait`（传统记号 P）：值大于 0 就减一继续；等于 0 就阻塞，直到有人加。
- `sem_post`（传统记号 V）：值加一，若有等待者就唤醒一个。

两个操作都不可分割，且**没有「当前值」可以随意读**——`sem_getvalue` 只在调试时有意义。它和 mutex 的根本差别是：mutex 的值只有 0 和 1，语义是「谁在临界区里」；信号量的值可以是任意非负数，语义是「还有多少份资源」。所以 mutex 保护的是「一段代码」，信号量描述的是「一份库存」。

有界缓冲区 `buf[8]` 需要三个量：

| 同步量 | 初值 | 谁等它 | 谁 post 它 | 它代表什么 |
|:--|--:|:--|:--|:--|
| `empty_sem` | 8 | 生产者 | 消费者取走一件后 | 还有几个空槽可写 |
| `full_sem` | 0 | 消费者 | 生产者放入一件后 | 已有几件货可读 |
| `mtx` | 1 | 生产者与消费者 | 用完就放 | `in`/`out` 与槽位内容的独占访问 |

三个初值都不是随手写的：`empty` 的初值等于容量，因为一开始 8 个槽全空；`full` 的初值是 0，因为一件货也没有；`mutex` 的初值是 1，因为锁只有一把。初值写错，程序要么一开始就死锁，要么第一次就越界。

```c
/* pc_lab.c：信号量版有界缓冲区
 * cc -std=c17 -O2 -Wall -Wextra -Werror -pthread pc_lab.c -o pc_lab
 * cc -std=c17 -O2 -Wall -Wextra -Werror -pthread -DSWAP pc_lab.c -o pc_lab_swap
 */
#define _GNU_SOURCE
#include <errno.h>
#include <pthread.h>
#include <semaphore.h>
#include <stdio.h>
#include <time.h>

#define N      8
#define ITEMS  100000

static int buf[N];
static int in, out;
static sem_t empty_sem;                     /* 空槽数，初值 N */
static sem_t full_sem;                      /* 已有货，初值 0 */
static pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;   /* 保护 in/out */

static double now_ms(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec * 1e3 + (double)ts.tv_nsec / 1e6;
}

static void *producer(void *arg)
{
    (void)arg;
    for (int i = 0; i < ITEMS; i++) {
#ifdef SWAP
        pthread_mutex_lock(&mtx);           /* 反例：先拿锁，再等空槽 */
        while (sem_wait(&empty_sem) == -1 && errno == EINTR)
            ;
#else
        while (sem_wait(&empty_sem) == -1 && errno == EINTR)
            ;                               /* 先等资源 */
        pthread_mutex_lock(&mtx);           /* 再拿锁 */
#endif
        buf[in] = i;
        in = (in + 1) % N;
        pthread_mutex_unlock(&mtx);
        sem_post(&full_sem);
    }
    return NULL;
}

static void *consumer(void *arg)
{
    (void)arg;
    long sum = 0;

    for (int i = 0; i < ITEMS; i++) {
        while (sem_wait(&full_sem) == -1 && errno == EINTR)
            ;
        pthread_mutex_lock(&mtx);
        sum += buf[out];
        out = (out + 1) % N;
        pthread_mutex_unlock(&mtx);
        sem_post(&empty_sem);
    }
    printf("sum=%ld expected=%ld\n", sum, (long)ITEMS * (ITEMS - 1) / 2);
    return NULL;
}

int main(void)
{
    if (sem_init(&empty_sem, 0, N) == -1 || sem_init(&full_sem, 0, 0) == -1) {
        perror("sem_init");
        return 1;
    }

    pthread_t p, c;
    double t0 = now_ms();
    if (pthread_create(&p, NULL, producer, NULL) != 0 ||
        pthread_create(&c, NULL, consumer, NULL) != 0)
        return 1;
    pthread_join(p, NULL);
    pthread_join(c, NULL);
    double ms = now_ms() - t0;

    int ev, fv;
    sem_getvalue(&empty_sem, &ev);          /* 只看一眼，别拿它做同步 */
    sem_getvalue(&full_sem, &fv);
    printf("items=%d  empty=%d full=%d  %.1f ms  %.0f items/s\n",
           ITEMS, ev, fv, ms, ITEMS * 1e3 / ms);

    sem_destroy(&empty_sem);
    sem_destroy(&full_sem);
    return 0;
}
```

正确顺序跑两次，再把顺序写反的版本用 `timeout` 跑一次，实测：

```text
$ ./pc_lab
sum=4999950000 expected=4999950000
items=100000  empty=8 full=0  326.3 ms  306424 items/s
$ ./pc_lab
sum=4999950000 expected=4999950000
items=100000  empty=8 full=0  281.6 ms  355053 items/s
$ timeout 2 ./pc_lab_swap; echo "exit=$?"
exit=124
```

`sum` 与等差数列和一字不差，说明 10 万件货一件没丢、一件没重；`empty` 回到 8、`full` 回到 0，说明每一对 `wait`/`post` 都配平了，没有欠也没有多。吞吐 30 万件/秒上下；同一天的另一跑是 812.8 ms（12.3 万件/秒），虚拟机抖动大，只看数量级。

顺序写反的版本没有输出，`exit=124` 是 `timeout` 杀进程的返回码——它卡住了。原因值得一步步走：缓冲区满时（8 个槽全占），生产者拿着 `mutex` 去 `sem_wait(&empty_sem)` 并睡下；消费者此时要取货，得先拿 `mutex`，而锁在生产者的怀里。消费者拿不到锁，就永远走不到 `sem_post(&empty_sem)`；`empty` 永远不会变正，生产者永远不醒。**互相等的两方，一个等锁、一个等信号量，环就闭了。**

所以规则是：**先等资源信号量，再拿互斥锁**。等资源可能睡很久，睡的时候身上不能带锁；锁只用来保护「看一眼、改一下」的那几步。消费者同理：先 `sem_wait(full_sem)`，再 `lock(mtx)`。

<pre class="layout">
   有界缓冲区 N = 8，某一时刻：in=5  out=2  full=3  empty=5
   buf[0..7] = [ - ][ - ][ 2 ][ 3 ][ 4 ][ - ][ - ][ - ]
   out = 2   下一个要读的下标（消费者从这里取走 2）
   in  = 5   下一个要写的下标（生产者下一件写进 buf[5]）
   full  = 3   下标 2、3、4 有货，消费者等它 > 0
   empty = 5   下标 5、6、7、0、1 为空，生产者等它 > 0
   mutex = 1   改 in/out 或读写槽位前必须先拿
   恒等式：full + empty = N，两边各自等待对方的 post
</pre>

读图抓住三件事：`full` 和 `empty` 是同一份容量的两个视角，任何时刻加起来等于 8；`in` 只由生产者推进，`out` 只由消费者推进，但它们读写的是同一个数组，所以要 `mutex`；两个信号量只保证「数量对」，不保证「槽位内容完整」，`mutex` 才保证后者。只留两个信号量、去掉 `mutex`，程序会在 `buf[in] = i` 与 `sum += buf[out]` 之间出现读到半个值的窗口（对 `int` 也许侥幸，换成结构体立刻现形）。

回到开头那句话：条件变量没有记忆，信号量有计数。同一件事用条件变量做，要写成「一把锁 + 两个谓词」：

| 维度 | 一个 mutex + 两个条件变量 | 三个信号量 |
|:--|:--|:--|
| 状态存在哪 | 普通变量 `count`，由锁保护 | 信号量内部计数 |
| 通知会不会丢 | 会：没人等时 `signal` 直接消失 | 不会：`post` 先加一，人来了一看就知道 |
| 能否表达「等某个谓词」 | 能，任意复杂条件都行 | 只能表达「还有几份资源」 |
| 常见错误 | 忘了 `while`、通知落在缝里 | 初值写错、顺序写反 |

两种都能写对，选择看条件复杂度：等「队列非空且未关闭」这种复合条件，条件变量更自然；只是数库存（连接池、限流器、空闲槽），信号量的计数省掉了「检查 + 睡眠」那一段手写逻辑。

吞吐还受「摆在几个核上」影响。同一个程序换三种钉法，每种跑三次，实测：

| 钉法 | 三次读数（万件/秒） |
|:--|:--|
| `taskset -c 0`（两线程同核） | 63.5 / 68.2 / 68.0 |
| `taskset -c 0,1`（各占一核） | 65.0 / 61.8 / 64.0 |
| 不钉，4 核随便跑 | 16.6 / 19.6 / 18.4 |

同核最快，各占一核略慢，放开跑掉到四分之一。这不是「核多反而慢」的普适结论，而是这个负载的真相：每生产消费一件货，都要过两次信号量加一次锁，成本几乎全在**交接**上，不在算力上。交接发生在同一个核里时，数据待在同一个 L1/L2；线程被迁到别的核，缓存失效、锁的交接跨核，吞吐立刻塌。所以「加线程能不能提速」这件事，永远要先量瓶颈在哪一段。

::: def 定义 1.12.4 · 计数信号量 {#def-1.12.4}
**计数信号量**（counting semaphore）是一个非负整数加两个原子操作。`sem_wait`：值大于 0 就减一并立刻返回，等于 0 就睡眠，直到有人加；`sem_post`：值加一，若有等待者唤醒一个。值是**资源余量**，不是「锁被谁持有」。POSIX 的 `sem_t` 用 `sem_init(&s, pshared, value)` 初始化：`pshared` 为 0 表示线程间共享（对象要放在全局或堆上），非 0 表示进程间共享（对象要放在共享内存里）。`sem_wait` 可能被信号打断，返回 `-1` 且 `errno` 为 `EINTR`，必须重试。
:::

::: errata 关于信号量的四个误解
1. **「有了信号量就不需要 mutex」**——信号量只保证「还有几个位置」，不保证「谁能同时改 `in`/`out`」。去掉 `mutex`，两个生产者会算出同一个 `in`，一个覆盖另一个；读到的槽位内容也可能是半写的。
2. **「`empty` 初值先写 0，反正生产者会 post」**——初值就是资源数量。写 0 时生产者第一次 `sem_wait` 就睡死，全场没人能 post；写 `N+1` 则第 9 次写入就越界。三个初值必须和「一开始有几份资源」严格对上。
3. **「先拿锁再等资源只是效率差一点」**——是死锁。`timeout 2 ./pc_lab_swap` 返回 124，进程卡在「持锁等空槽、消费者等锁」的环上，不会自己好。
4. **「`sem_post` 在没人等的时候会丢」**——不会。它先把计数加一，人来了一看就知道有货。这正是它和 `pthread_cond_signal` 的分水岭：通知会丢，计数不会。
:::

### 1.12.4 小结

有界缓冲区要管三个数：`empty`（空槽，初值 N）、`full`（存货，初值 0）、`mutex`（保护下标与内容，初值 1）；恒等式是 `full + empty = N`。规则只有一条顺序：先等资源、再拿锁，睡的时候身上不带锁。如果只记住一件事：**信号量数的是库存，条件变量喊的是「变了」——前者有记忆，后者没有**。

::: method 即时自测 · 1.12.4
**Q1（记忆）** 容量为 8 的有界缓冲区，`empty`、`full`、`mutex` 的初值各是多少？谁等待、谁 post？

**Q2（辨析）** 生产者先 `pthread_mutex_lock(&mtx)` 再 `sem_wait(&empty_sem)`，缓冲区满时会发生什么？为什么消费者醒不过来？

**Q3（迁移）** 一个数据库连接池有 20 条连接，取连接用 `sem_wait`、还连接用 `sem_post`。想在池空时立刻返回错误而不是阻塞，该怎么写？这和 1.12.3 的条件变量方案比，少写了什么？

::: sol 答案
**A1** `empty=8`（8 个空槽）、`full=0`（还没货）、`mutex=1`。生产者等 `empty`、post `full`；消费者等 `full`、post `empty`；两者都要拿 `mutex` 才能改 `in`/`out` 或读写槽位。

**A2** 缓冲区满时 `empty` 为 0，生产者已持有 `mtx` 并睡在 `sem_wait` 上。消费者要取货必须先拿 `mtx`，锁被生产者占着，于是既取不走货、也无法 `sem_post(empty)`；生产者的等待条件永远不会变真，两边互等，死锁。

**A3** 用 `sem_trywait`：返回 -1 且 `errno == EAGAIN` 就说明池已空，直接返回错误码。和条件变量方案相比，少写的是「加锁—`while` 重判—`wait`」这一整段：计数在信号量内部，`trywait` 一次调用就完成「检查 + 占用」。

## 1.12.5 线程池与有界队列 {#sec-1.12.5}

这一节回答：每来一个请求就 `pthread_create` 的服务器明明能跑，为什么请求一多就必须换成「固定几个 worker + 一条队列」？省下来的是哪一段开销，代价又转移到了哪里？

::: preview 先抓住一件事
线程池只做一件事：**把「创建线程」从每个任务里拿掉**，换成「往队列里放一张纸条，睡着的 worker 被叫醒」。省下的是每任务约 0.05–0.10 ms 的创建与回收，付出一条共享队列——于是又回到 1.12.3 的锁与条件变量。池子不是越大越快：任务很轻时，队列本身就是新瓶颈。
:::

先算账。1.12.1 实测一个线程约 0.102 ms（创建加 join）。按每秒一万个任务算，光创建就吃掉一整秒 CPU，还没算每个线程 8 MiB 的虚拟栈。线程池把这笔钱一次性付掉：启动时建好 worker，之后每个任务只在队列上进出一趟：提交方加锁入队，worker 加锁出队，不会话就把锁放掉。

池里有三样东西：若干 worker、一条**有界**（容量固定）队列、一对条件变量。提交方做「加锁 → 队列没满就入队 → 叫醒一个 worker → 解锁」；worker 做「加锁 → 队列空就睡 → 出队 → 叫醒一个提交方 → 解锁 → 执行」。最后一步的顺序不能反：**先解锁，再执行任务**。否则 worker 跑一段 10 ms 的任务时，其他 worker 和提交方全堵在锁上，池子退化成单线程。

```c
/* pool_lab.c：4 个 worker + 64 槽有界环形队列
 * cc -std=c17 -O2 -Wall -Wextra -Werror -pthread pool_lab.c -o pool_lab
 * ./pool_lab 4 20000 0      # worker 数、任务数、每任务循环次数
 */
#define _GNU_SOURCE
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define QCAP 64

typedef struct { void *(*fn)(void *); void *arg; } task_t;

typedef struct {
    pthread_mutex_t mtx;
    pthread_cond_t  not_empty, not_full;
    task_t          q[QCAP];              /* 定长环形队列 */
    int             head, tail, count, shutdown, nworkers;
    pthread_t       tid[8];
} pool_t;

static double now_ms(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec * 1e3 + (double)ts.tv_nsec / 1e6;
}

static void *worker(void *arg)
{
    pool_t *p = arg;

    for (;;) {
        pthread_mutex_lock(&p->mtx);
        while (p->count == 0 && !p->shutdown)
            pthread_cond_wait(&p->not_empty, &p->mtx);
        if (p->count == 0) {                       /* 已关闭且队列空 */
            pthread_mutex_unlock(&p->mtx);
            break;
        }
        task_t t = p->q[p->head];
        p->head = (p->head + 1) % QCAP;
        p->count--;
        pthread_cond_signal(&p->not_full);
        pthread_mutex_unlock(&p->mtx);             /* 先解锁，再执行 */
        t.fn(t.arg);
    }
    return NULL;
}

static int pool_init(pool_t *p, int n)
{
    *p = (pool_t){ 0 };                            /* 字段清零，再初始化同步对象 */
    p->nworkers = n;
    if (pthread_mutex_init(&p->mtx, NULL) != 0 ||
        pthread_cond_init(&p->not_empty, NULL) != 0 ||
        pthread_cond_init(&p->not_full, NULL) != 0)
        return -1;
    for (int i = 0; i < n; i++)
        if (pthread_create(&p->tid[i], NULL, worker, p) != 0)
            return -1;
    return 0;
}


static int pool_submit(pool_t *p, void *(*fn)(void *), void *arg)
{
    pthread_mutex_lock(&p->mtx);
    while (p->count == QCAP && !p->shutdown)       /* 满则等：背压 */
        pthread_cond_wait(&p->not_full, &p->mtx);
    if (p->shutdown) {                             /* 关闭后拒绝 */
        pthread_mutex_unlock(&p->mtx);
        return -1;
    }
    p->q[p->tail] = (task_t){ fn, arg };
    p->tail = (p->tail + 1) % QCAP;
    p->count++;
    pthread_cond_signal(&p->not_empty);
    pthread_mutex_unlock(&p->mtx);
    return 0;
}

static void pool_shutdown(pool_t *p)               /* 排空队列，再 join */
{
    pthread_mutex_lock(&p->mtx);
    p->shutdown = 1;
    pthread_cond_broadcast(&p->not_empty);
    pthread_cond_broadcast(&p->not_full);
    pthread_mutex_unlock(&p->mtx);
    for (int i = 0; i < p->nworkers; i++)
        pthread_join(p->tid[i], NULL);
    pthread_mutex_destroy(&p->mtx);
    pthread_cond_destroy(&p->not_empty);
    pthread_cond_destroy(&p->not_full);
}

typedef struct { long id, iters, sum; } job_t;

static long burn(long id, long iters)
{
    unsigned long x = (unsigned long)id * 2654435761u + 1;

    for (long i = 0; i < iters; i++)               /* 依赖链，无法向量化 */
        x = x * 6364136223846793005ULL + 1442695040888963407ULL;
    return (long)(x >> 40);
}

static void *run_job(void *arg)
{
    job_t *j = arg;
    j->sum = burn(j->id, j->iters);
    return NULL;
}

int main(int argc, char **argv)
{
    if (argc != 4)
        return 2;
    int w = atoi(argv[1]);
    long n = atol(argv[2]), iters = atol(argv[3]);
    job_t *jobs = calloc((size_t)n, sizeof *jobs);
    if (jobs == NULL)
        return 1;
    for (long i = 0; i < n; i++)
        jobs[i] = (job_t){ .id = i, .iters = iters };

    pool_t p;
    double t0 = now_ms();
    if (pool_init(&p, w) != 0)
        return 1;
    for (long i = 0; i < n; i++)
        if (pool_submit(&p, run_job, &jobs[i]) != 0)
            return 1;
    pool_shutdown(&p);
    double ms = now_ms() - t0;

    long got = 0, want = 0;
    for (long i = 0; i < n; i++) {
        got += jobs[i].sum;
        want += burn(i, iters);
    }
    printf("workers=%d tasks=%ld iters=%ld  %.1f ms  %.0f items/s  %s\n",
           w, n, iters, ms, (double)n * 1e3 / ms, got == want ? "ok" : "MISMATCH");
    free(jobs);
    return 0;
}
```

在本机（Ubuntu 24.04.5，aarch64，4 vCPU）编译，两万个空任务按 4 个和 1 个 worker 各连跑三次，实测：

```text
workers=4 tasks=20000 iters=0  18.7 ms  1071201 items/s  ok
workers=4 tasks=20000 iters=0  18.5 ms  1082502 items/s  ok
$ ./pool_lab 1 20000 0
workers=1 tasks=20000 iters=0  11.6 ms  1719364 items/s  ok
workers=1 tasks=20000 iters=0  13.6 ms  1473500 items/s  ok
workers=1 tasks=20000 iters=0  12.9 ms  1544630 items/s  ok
```

4 个 worker 约 1.07–1.08 M items/s，每个任务约 1 µs。同一批任务若改成「每任务建一个线程再 join」，把提交循环换成下面这段，同样两万个空任务要 1.03–1.05 s，约 1.9 万 items/s，慢了 **50 多倍**：

```c
/* churn：同样任务，不经队列，每任务一个线程 */
for (long i = 0; i < n; i++) {
    pthread_t t;
    pthread_create(&t, NULL, run_job, &jobs[i]);   /* 为聚焦主题省略返回值检查 */
    pthread_join(t, NULL);
}
```

差的不是「线程」本身，而是每个任务都要走一遍「建栈、登记内核任务、销毁」。池子把这三步从热路径上拿掉了。

第三个读数更值得注意：**1 个 worker 反而比 4 个快**（1.47–1.72 M 对 1.07–1.08 M items/s）。因为任务是空的，成本全在队列上：多个 worker 抢同一把 mutex，缓存行在核间来回搬，还多出唤醒与上下文切换。任务变重之后结论才反过来：每个任务算 2 万次依赖链时，1 个 worker 135.4 ms，4 个 worker 33.2 ms、33.1 ms，正好 4 倍。**worker 数要按「任务里有多少真活」定，不能按核数抄**。

三个判断决定关闭对不对。第一，`while (p->count == 0 && !p->shutdown)` 之后还要再判一次 `p->count == 0`：能出循环只说明「没活且已关闭」，才允许走；写成「一 shutdown 就退」会丢掉队列里剩下的任务。第二，`pool_shutdown` 先置位并广播、再 join：worker 排空队列后自然退出，`join` 才有意义。第三，队列满时 `pool_submit` 是**等**（背压），不是无限入队：无界队列在过载时把内存吃光，最后 OOM，比拒绝请求更糟；要拒绝就返回错误码，策略见 1.12.13。

::: def 定义 1.12.5 · 线程池与背压 {#def-1.12.5}
**线程池**（thread pool）是「固定数量的 worker + 一条任务队列」：worker 复用，任务排队。**有界队列**（bounded queue）指容量固定，满了不再收。**背压**（backpressure）是满时让提交方阻塞或失败，把压力退回上游，而不是无限堆积。三者一起才构成能上生产的池：只有 worker 没有界队列，过载时先崩的是内存。
:::

::: errata 关于线程池的四个误解
1. **「worker 越多吞吐越高」**——实测空任务 1 个 worker 比 4 个快一半，因为瓶颈是队列锁而不是 CPU。加 worker 只在该任务 CPU 密集、且核还没跑满时才有用。
2. **「队列无界就不会丢任务」**——无界队列不丢任务，丢的是内存和延迟：请求越积越久，最后 OOM 或超时。有界队列加背压才是可控的失败方式。
3. **「shutdown 就是把一个标志置位」**——置位只是不再收新任务。已经排队的不排空，优雅关闭就变成静默丢单；顺序是先广播、让 worker 排空，再 join。
4. **「任务执行时持锁更安全」**——任务里可能要读文件、可能再次提交任务，持锁执行会让整池串行甚至自锁。出队后立刻解锁。
:::

### 1.12.5 小结

线程池把创建线程的成本从热路径上拿掉，换成一条有界队列和一对条件变量；吞吐上限因此从「创建有多快」变成「队列能过多快」。三条顺序要守住：出队后先解锁再执行、关闭时先排空再 join、队列满时背压而不是无限堆。如果只记住一件事：**池子省的是创建，赚不赚要看任务有多重——空任务喂 4 个 worker 反而更慢**。

## 1.12.6 读写者、线程安全与死锁 {#sec-1.12.6}

这一节回答：数据「读多写少」时，读写锁换来了什么、又让谁挨饿？一个单线程里跑得好好的函数，为什么进了线程就出错？死锁现场长什么样，为什么这一节只讲现象？

::: preview 先抓住一件事
读写锁换的是「读者可以并行」，不是「读一定变快」；三个 kind 换的是「谁饿」，不是「谁快」——实测默认策略下后到的读者 0 ms 就进得去，写者干等 275 ms。线程安全看的是「有没有共享的可写状态」，可重入看的是「执行到一半能不能被再次进入」，两者不是一回事。
:::

先量一次策略差别。场景：一个读线程持读锁 300 ms，20 ms 后写线程申请写锁，40 ms 后第二个读者申请读锁。三种 `pthread_rwlockattr_setkind_np` 各跑两次（VM 实测）：

| kind | 写者等待 | 后到的读者等待 |
|:--|--:|--:|
| `PREFER_READER_NP`（默认） | 274.8 / 274.9 ms | 0.0 / 0.0 ms |
| `PREFER_WRITER_NP` | 274.9 / 274.9 ms | 0.0 / 0.0 ms |
| `PREFER_WRITER_NONRECURSIVE_NP` | 274.9 / 274.9 ms | 254.9 / 255.0 ms |

三行读法：读者优先时新读者随时进得来，写者排到最后，读请求源源不断就无限等，这叫写者饥饿；写者优先时后来的读者排在写者后面，干等 255 ms，读者饥饿是这条策略的定义性后果，不是 bug。第二行与第一行一模一样：glibc 把 `PREFER_WRITER_NP` 当读者优先处理，别指望它；要写者优先只能用 `..._NONRECURSIVE_NP`，代价是同一线程递归读锁会自锁。

所以「三策略」实际只有两种行为：让写者饿，或让读者饿，没有免费的两全。读写锁与 mutex 的吞吐对比、seqlock 与 RCU 的取舍在 1.12.11，这一节只记结论：**读临界区越短，读写锁越不划算**——收益来自并行的读，而并行的读只有在临界区足够长时才看得见。

再说线程安全。两个词常被混用：

| 概念 | 判据 | 反例 |
|:--|:--|:--|
| 线程安全 | 多线程同时调用，结果正确 | `strtok`、`localtime` |
| 可重入 | 执行到一半被再次进入，仍正确 | 靠全局锁做到线程安全的函数，在信号处理里再调自己 |

可重入比线程安全更严：可重入函数不碰共享可写状态，所以不需要锁，也不怕被同一线程再进一次；反过来，一个函数靠全局锁做到线程安全，在信号处理或回调里重入就会自锁。判断方法很土：看函数里有没有 `static` 或全局的可写变量、有没有返回指向 `static` 缓冲区的指针。

`strtok` 是最常见的坑：它把「下次从哪继续」存在函数内部的静态指针里，两个线程各解析各的字符串，位置却共用一份——第二个线程一调用，第一个线程的进度就被清掉，两边都解析出半截。

```c
char *tok = strtok(line, " ");                  /* 错：状态藏在库的静态变量里 */

char *save = NULL;                              /* 对：位置放在调用者栈上 */
for (char *tok = strtok_r(line, " ", &save); tok != NULL; tok = strtok_r(NULL, " ", &save))
    puts(tok);
```

`localtime` → `localtime_r`、`asctime` → `asctime_r`、`strerror` → `strerror_r` 是同一类修法：把返回的静态缓冲区改成调用者传入。

`errno` 的规则要单独记。glibc 里 `errno` 是宏，展开为 `(*__errno_location())`，每个线程一份，两个线程各自失败互不覆盖。但两条仍然成立：**errno 只在调用返回失败后才有意义**，成功的调用不保证把它清零；**`pthread_*` 系列根本不设 errno**，它们直接返回错误码（1.12.8）。判断失败先看返回值，别先看 errno。

最后是死锁。这一节只要求你认出现场，不要求会推导：程序不报错、不退出、CPU 接近 0；`ps -L` 看每个线程都睡在 `futex_wait`；`gdb -p` 挂上去，几个线程的栈都停在 `pthread_mutex_lock`，而各自手里那把锁正是别人在等的。几条同时成立，基本可以判死锁。为什么会成环、怎么用进度图复现、怎么用锁序和 `trylock` 拆环，见 1.12.12。

::: errata 关于读写锁与线程安全的四个误解
1. **「读写锁总比 mutex 快」**——读临界区只有一次数组读时，两者测的都是锁本身，读写锁未必占优；收益要看读临界区长度与写比例，定量对照在 1.12.11。
2. **「`PREFER_WRITER_NP` 就是写者优先」**——实测与读者优先完全一致；glibc 只有 `..._NONRECURSIVE_NP` 真的让新读者排在写者后面。
3. **「errno 是全局变量，多线程会互相覆盖」**——glibc 的 errno 是线程局部存储，每个线程一份；但仍要先看返回值，因为成功的调用不清 errno。
4. **「线程安全就等于可重入」**——加锁实现的线程安全函数，在信号处理里重入会自己等自己；可重入函数不碰共享可写状态，才敢在中断（硬件或软件打断当前指令流）上下文里调。
:::

### 1.12.6 小结

读写锁把「读」从串行里放出来，代价是把「谁先到」变成策略问题：读者优先饿写者，写者优先饿读者，`PREFER_WRITER_NP` 在 glibc 上并不生效。线程安全与可重入是两个判据，`strtok` 之所以不可重入，是因为状态藏在库里；`errno` 每线程一份，但只对失败的调用有意义。如果只记住一件事：**三个 kind 换的是谁挨饿，不是谁更快；死锁先认现场，推导留给 1.12.12**。

## 1.12.7 事件驱动与 I/O 多路复用 {#sec-1.12.7}

这一节回答：一个线程凭什么同时照看几千条连接？`select`、`poll`、`epoll` 的差别到底在哪一维上？水平触发与边缘触发该怎么选，回调里为什么一次阻塞就全盘皆输？

::: preview 先抓住一件事
三个接口做的是同一件事：把一组 fd 交给内核，问「哪些就绪了」。差别在每次询问要搬多少数据、扫多少 fd：`select`/`poll` 每次把全集搬进内核再扫一遍，`epoll` 注册一次、只搬就绪的。所以连接越多、越空闲，`epoll` 越省；全都忙时它也只快一点。
:::

[1.11.12](ch11.md#sec-1.11.12) 已经讲过 `epoll` 的红黑树与就绪链表，也讲过 ET 下怎么读到 `EAGAIN`，这里不重复 socket 细节，只把三个接口放在同一负载下量一次。

{{#include ../assets/figures/epoll.md}}

读图抓住三个结构：红黑树保存注册的 fd，就绪链表保存已触发的项，等待队列让 `epoll_wait` 睡眠。复杂度与「就绪数」相关，而不是「注册数」。

`select` 用 `fd_set` 位图，`FD_SETSIZE` 默认 1024，fd 大于 1023 就直接不能用；每次调用要把位图整个拷进内核，返回后还得用 `FD_ISSET` 把 1024 个位置扫一遍。`poll` 把位图换成数组，没有 1024 的限制，语义不变：每次调用仍然是「拷全集 + 扫全集」。`epoll` 把注册和等待拆开：`epoll_ctl` 时登记一次，`epoll_wait` 只把就绪项搬到用户态。

负载：n 条管道，前 m 条各写 1 字节；同一进程里先 `poll` 后 `epoll_wait`，每轮问一次「有几条就绪」，各跑几百轮取平均（VM 实测）：

| 注册 n | 就绪 m | `poll` µs/次 | `epoll_wait` µs/次 | 倍数 |
|--:|--:|--:|--:|--:|
| 1000 | 10 | 31.64 | 0.38 | 84 |
| 1000 | 1000 | 31.03 | 11.85 | 2.6 |
| 8000 | 10 | 349.48 | 0.37 | 930 |
| 8000 | 8000 | 358.60 | 135.35 | 2.6 |

计时部分只有这几行，准备管道与 `epoll_ctl` 的部分省略：

```c
/* n 条 O_NONBLOCK 管道，前 m 条各写 1 字节，读端已全部 ADD 进 epoll */
double t0 = now_us();
for (int r = 0; r < rounds; r++)
    hit1 += poll(pfds, (nfds_t)n, 0);           /* 每次都扫全部 n 条 */
double tp = now_us() - t0;

t0 = now_us();
for (int r = 0; r < rounds; r++)
    hit2 += epoll_wait(epfd, evs, (int)n, 0);   /* 只搬就绪的 m 条 */
double te = now_us() - t0;
```

三行结论。第一，`poll` 的成本只跟 n 有关：31 µs 涨到 349 µs，随注册数线性涨，跟有几条就绪无关。第二，`epoll` 的成本只跟 m 有关：10 条就绪时 0.37–0.38 µs，8000 条就绪时 135 µs。第三，`epoll` 不是「永远快」：全部就绪时只快 2.6 倍，因为把 8000 个事件搬进用户态本身要钱。所以「换 epoll 就快了」只在「注册多、就绪少」时成立，而这恰好是长连接网关的常态。

触发模式决定「读完之后还会不会被提醒」。水平触发（level-triggered, LT）是「只要还有数据，每次 `epoll_wait` 都返回它」，漏读了下一次还会提醒；边缘触发（edge-triggered, ET）是「状态变化时只提醒一次」，必须配非阻塞 fd，并且一次读到 `EAGAIN`，否则剩下的数据再也没有下一次通知。`epoll` 的默认仍是 LT；ET 省的是重复通知，不是「更高级」。accept 也一样：ET 下要循环 `accept4` 到 `EAGAIN`，只接一个就会把后面的连接留在队列里睡大觉。

最后是模型本身的约束：**回调不能阻塞**。假设回调里读一次磁盘要 100 ms，而事件循环每秒要处理 1000 个请求，那么每秒就有 100 s 的阻塞预算要花出去——不需要算得多精确，结论只有一个：事件队列必然堆积，延迟随时间线性涨。所以线程池与事件循环不是二选一（1.12.5）：循环只管 fd 与协议解析，磁盘、DNS、慢 RPC 丢给线程池，做完用 `eventfd` 唤醒循环，由循环统一写回。跨线程交接要写清所有权：缓冲区谁分配、谁释放、写回时读线程还在不在用它。这是 A2 `myhttpd` 与 C2 `myproxy` 里最容易出错的一段。

::: errata 关于多路复用的四个误解
1. **「`epoll` 一定比 `poll` 快」**——实测全就绪时只快 2.6 倍；就绪项多时，搬事件与业务处理的成本都在，`epoll` 省下的只是「扫注册表」那一份。
2. **「ET 更高级，应该默认用」**——ET 要求非阻塞 + 读到 `EAGAIN`，漏一次就永久停摆；`epoll` 默认是 LT，简单场景先用 LT。
3. **「`select` 只是老，性能和 `poll` 差不多」**——两者同阶，但 `select` 还有 1024 的 fd 上限和 `FD_ISSET` 全扫，现代服务基本不用它。
4. **「单线程事件循环没有并发问题」**——没有数据竞争，但有重入与状态机 bug；回调里改了共享缓冲区、别的回调又读它，照样出错。
:::

### 1.12.7 小结

三个接口都在回答「哪些 fd 就绪」，差别是每次询问要搬多少、扫多少：`poll` 的成本随注册数走，`epoll` 随就绪数走，全就绪时两者只差两倍多。LT 漏读还有下次，ET 必须一次读到 `EAGAIN`。如果只记住一件事：**事件循环的吞吐上限不是 `epoll_wait` 有多快，而是回调里最慢的那一次阻塞**。

::: method 即时自测 · 1.12.7

**Q2（辨析）** 一个网关用 ET 模式，`accept` 之后只接了一个连接就回去等事件，会发生什么？为什么 LT 不会？

**Q3（应用）** 事件循环里要查一次 DNS（可能 50 ms）。不改模型会怎样？改的话，结果怎么交回循环？

::: sol 答案
**A1** `poll` 正比于注册数 n（实测 8000 条约 350 µs），`epoll_wait` 正比于就绪数 m（10 条约 0.38 µs）。全就绪时 `epoll` 也要搬 8000 个事件，约 135 µs。

**A2** ET 只在「监听 fd 从不可读变为可读」时通知一次，剩下的连接还排在 backlog 里，但没有新的状态变化，就再也没有通知。LT 下只要还有连接可接，下一次 `epoll_wait` 仍会返回监听 fd。

**A3** 50 ms 的阻塞会让这一轮所有就绪连接一起等待，QPS 越高堆积越快。改法是把 DNS 查询交给线程池，完成后用 `eventfd`（或管道）唤醒事件循环，由循环把结果写回对应连接。
:::
:::

## 1.12.8 线程的完整生命周期：创建、分离、回收与退出 {#sec-1.12.8}

这一节回答：线程退出之后，它的栈、返回值和 ID 分别归谁管？`pthread_detach` 与 `pthread_join` 差在哪一步？`pthread_exit` 和 `return` 是同一件事吗？为什么 `pthread_cancel` 常常没反应？

::: preview 先抓住一件事
线程只有两条合法结局：joinable（默认）要有人来收尸，detached 自己收。`/proc` 只能证明「内核任务没了」，证明不了「资源还了」：200 个 joinable 线程退出后 `/proc/self/task` 只剩 1 项，`VmSize` 却还挂着 1.58 GiB。8 MiB 是虚拟栈，不是内存。
:::

从 1.12.2 的 `ps -L` 接过来。那时四个线程各占一行，说明内核给每个线程一个调度实体；这一节问的是它消失之后的事。

实验：建 200 个线程，每个只记下自己的 TID 就返回；300 ms 后读 `/proc/self/status` 的 `VmSize` 与 `Threads`，再数 `/proc/self/task` 的目录数（VM 实测）：

| 做法 | VmSize | Threads | /proc/self/task | 那个 TID 还在吗 |
|:--|--:|--:|--:|:--|
| detached | 35,292 kB | 1 | 1 | 不在 |
| joinable、未 join | 1,653,468 kB | 1 | 1 | 不在 |
| joinable、join 之后 | 35,292 kB | 1 | 1 | 不在 |

三个读数钉死三件事。第一，**内核任务一退出就消失**，detached 与 joinable 一样：TID 目录不在、`Threads` 回到 1。所以「用 `/proc` 看线程泄漏」在 Linux 上基本无效，泄漏的是用户态资源。第二，**joinable 线程退出后栈还挂着**：(1,653,468 − 35,292) kB ≈ 1.58 GiB，除以 200 约 7.9 MiB，正好是默认栈大小；join 之后才降回 35,292 kB。第三，detached 线程退出即回收，VmSize 直接回基线——这就是「分离」的全部含义。

`pthread_create` 给每个线程 mmap 一块 8 MiB 的栈，只是地址空间预留：没触碰的页不占物理内存。所以 1000 个线程的 VmSize 会到 8 GiB，RSS 可能只有几十 MB。容器里先撞的往往是 `pids.max`（线程也计数），不是内存；栈大小可用 `pthread_attr_setstacksize` 调，低于 `PTHREAD_STACK_MIN` 直接返回 `EINVAL`。

退出有两条路径，返回值都拿得到，副作用不同：

| 写法 | 给 join 的 retval | cleanup handler | TLS 析构 |
|:--|:--|:--|:--|
| 入口函数 `return retval` | 有 | **不执行** | 执行 |
| `pthread_exit(retval)` | 有 | 执行 | 执行 |

最容易混的是 main：`main` 里 `return` 等价于 `exit()`，进程立刻结束，其他线程全被砍；`main` 里调 `pthread_exit(NULL)` 只结束主线程，进程要等最后一个线程结束才退。实测（VM）：

```text
$ ./life_lab mainexit
worker: tick 1
main: 调 pthread_exit，进程先不结束
worker: tick 2
worker: tick 3
worker: cleanup handler 跑了
exit=0
```

主线程在 tick 1 之后就「退出」了，进程仍活到 tick 3——服务里「主线程只管初始化」能成立，靠的就是这条。

取消默认是延迟取消：`pthread_cancel` 只置标志，线程运行到**取消点**（`read`、`write`、`accept`、`poll`、`pthread_cond_wait`、`sem_wait`、`nanosleep`、`usleep` 等）才真正退出。实测（VM）：

```text
$ ./life_lab cancel
spinner: cancel 之后计数还在涨 294878309 -> 363288742，它没有取消点
sleeper: join 拿到的返回码 PTHREAD_CANCELED
```

纯计算循环没有取消点，cancel 之后照样跑；睡在 `usleep` 里的线程到点就退，join 拿到 `PTHREAD_CANCELED`。所以「停线程」的通用做法是标志位加定期检查，而不是 cancel；真要用 cancel，必须保证它只在安全点被取消，并用 cleanup handler 解锁、释放。

再补两条 `pthread_*` 的约定。它们**不设 errno**，直接返回错误码：`EAGAIN` 是资源不足（线程数上限、cgroup `pids.max`、内存），`EINVAL` 常见于「join 一个已分离的线程」或「已有线程在 join」，`EDEADLK` 是自己 join 自己。`pthread_t` 是不透明类型，只能用 `pthread_equal` 比较，不要按整数打印，也别存进哈希表当稳定身份。

TLS 三种写法：`_Thread_local`（C11）、`__thread`（GNU 扩展）、`pthread_key_t`（带析构函数，库代码首选）。要点是每线程一份，线程退出时 `pthread_key_t` 的析构函数被调用，最多跑 `PTHREAD_DESTRUCTOR_ITERATIONS` 轮。

::: errata 关于线程生命周期的四个误解
1. **「线程一退出资源就回收」**——只有 detached 如此。joinable 线程退出后栈与返回值仍留着，直到 join；`/proc` 看不出来，要看 VmSize 或 valgrind。
2. **「`return` 与 `pthread_exit` 完全等价」**——返回值一样，但 return 不跑 cleanup handler，`pthread_exit` 会跑。
3. **「`pthread_cancel` 能立刻停掉线程」**——延迟取消要等取消点；纯计算线程永远不响应。
4. **「多线程里 fork 与单线程一样」**——fork 只复制调用线程，子进程可能继承别的线程持有的 malloc/stdio 锁，exec 前调 malloc 就可能死锁；fork 与 exec 之间只允许 async-signal-safe 函数。
:::

### 1.12.8 小结

线程的两条结局决定资源归谁：joinable 要 join，detached 自己收；`/proc` 里的消失不代表资源还了，VmSize 才看得见 joinable 留下的栈。`main` 里 return 与 `pthread_exit` 差一条命，cancel 只对取消点有效。如果只记住一件事：**8 MiB 是虚拟栈，泄漏的不是线程，是没人 join 的那份栈**。

## 1.12.9 原子操作与内存序：C11、C++ 与 Rust 的同一套规则 {#sec-1.12.9}

这一节回答：原子操作已经保证「一次读改写不可分割」，为什么还要分 `relaxed`、`acquire`、`release`、`seq_cst`？这些名字到底在约束什么？`volatile` 为什么不能顶替原子？

::: preview 先抓住一件事
原子性管「一个对象不被撕成两半」，内存序管「这个原子操作前后的普通读写，别的线程按什么顺序看见」。C11 把后者写成 happens-before；C++ 与 Rust 照抄同一张表，只换拼写。计数用 `relaxed` 就够，发布数据必须 `release` 配 `acquire`。
:::

1.12.2 把 `counter++` 修对了：锁、原子加法、局部累加都能得到 400 万。但那只解决「一个变量」。换一个常见场景：线程 A 先填好结构体，再把 `ready` 置 1；线程 B 自旋到 `ready == 1` 后读结构体。若 `ready` 是 `relaxed` 原子，B 可能看到 `ready == 1`，读到的结构体却还是旧的——原子性只保证 `ready` 本身不撕裂，不保证它前面的 `data = 42` 已经对其他核可见。标准允许这种重排；ARM64 允许 store-store 重排，可能让它发生，x86 的 TSO 通常掩盖它。

::: def 定义 1.12.9 · happens-before 与 synchronizes-with {#def-1.12.9}
**sequenced-before**：同一个线程内按程序顺序，前一条语句先于后一条。**synchronizes-with**：线程 A 对原子对象 X 做 release 写，线程 B 对 X 做 acquire 读且读到了这个写（或它的 release sequence 里的值），则 A 的写 synchronizes-with B 的读。**happens-before** 是这两者的传递闭包：同线程顺序 + 跨线程同步 + 传递。两个冲突访问（同一内存、至少一个写）若没有 happens-before 关系，就是数据竞争；原子操作之间不算竞争，但 `relaxed` 不会给周围的普通读写建立顺序。
:::

四种基本序，外加只用于读改写的组合 `acq_rel`，记「谁不能越过谁」：

| 序 | 约束 | 典型用法 |
|:--|:--|:--|
| `relaxed` | 只保证该对象的读改写不可分割 | 计数、序号、统计 |
| `acquire` | 它之后的读写不能提到它前面 | 读标志、加锁 |
| `release` | 它之前的读写不能挪到它后面 | 写标志、解锁、发布 |
| `acq_rel` | 两者兼有，只用于读改写 | `fetch_add`、CAS |
| `seq_cst` | 所有 `seq_cst` 操作存在一个全体线程一致的顺序 | 多标志、Dekker、双重检查 |

`acquire` 与 `release` 是一对：release 写把「之前的所有写入」打包，acquire 读若看到这个写，就把包裹原样交给读方。这就是「用标志发布数据」的全部秘密：

```c
/* 发布者 */
data = 42;                                             /* 普通写 */
atomic_store_explicit(&ready, 1, memory_order_release);
/* 消费者 */
while (atomic_load_explicit(&ready, memory_order_acquire) == 0)
    ;
assert(data == 42);                                    /* 一定成立 */
```

把 `release/acquire` 换成 `relaxed`，`assert` 就可能失败——不是「概率低」，而是标准明确允许。C++ 与 Rust 的写法只是换名字：

| 语义 | C11 | C++20 | Rust |
|:--|:--|:--|:--|
| release 写 | `atomic_store_explicit(&x, 1, memory_order_release)` | `x.store(1, std::memory_order_release)` | `x.store(1, Ordering::Release)` |
| acquire 读 | `atomic_load_explicit(&x, memory_order_acquire)` | `x.load(std::memory_order_acquire)` | `x.load(Ordering::Acquire)` |
| relaxed 加 | `atomic_fetch_add_explicit(&n, 1, memory_order_relaxed)` | `n.fetch_add(1, std::memory_order_relaxed)` | `n.fetch_add(1, Ordering::Relaxed)` |
| seq_cst 写 | `atomic_store_explicit(&x, 1, memory_order_seq_cst)` | `x.store(1, std::memory_order_seq_cst)` | `x.store(1, Ordering::SeqCst)` |

`seq_cst` 是 C11 与 C++ 的默认序，也是最贵的：x86-64 的 `seq_cst` 写要 `xchg` 或 `mfence`，ARM64 上要额外的全局序约束（常见 `dmb ish`），而 `relaxed` 的读改写只需一条 `ldadd`/`cas`。代价能差多少？把 4 个线程各加 100 万次放在同一台 VM 上：

```c
/* lab1c12_atomic.c 的核心：三种模式各跑 4 线程 × 100 万次 */
atomic_fetch_add_explicit(&g_relaxed, 1, memory_order_relaxed);   /* relaxed */
atomic_fetch_add_explicit(&g_seqcst, 1, memory_order_seq_cst);   /* seq_cst */
pthread_mutex_lock(&mtx); g_mutex++; pthread_mutex_unlock(&mtx); /* mutex */
```

```text
atomic_long lock-free: 1
relaxed  total=4000000     35.9 ms    9.0 ns/op
seq_cst  total=4000000    109.5 ms   27.4 ns/op
mutex    total=4000000     92.2 ms   23.1 ns/op
（第二次：relaxed 37.1 ms / 9.3 ns，seq_cst 112.4 ms / 28.1 ns，mutex 107.7 ms / 26.9 ns）
```

三个读数。第一，`relaxed` 约 9 ns/次，`seq_cst` 约 28 ns/次，差三倍；Rust 的 `Ordering::Relaxed` 与 `SeqCst` 编出来是同一类指令。第二，这一跑里 `mutex` 竟比 `seq_cst` 略快：锁的快路径只是一次 CAS 加一次 store，而 `seq_cst` 的读改写每次都要付全局序；别把「锁一定比原子慢」当定律。第三，`atomic_long` 在 aarch64 上是 lock-free，但 C11 不保证所有原子类型都如此：超过机器字宽的结构体可能退化成库里的锁，`atomic_is_lock_free` 要实测。

::: errata 关于内存序的四个误解
1. **「`volatile` 可以当原子用」**——它只要求每次真的读内存、写内存，不保证读改写不可分割，也不建立线程间顺序。它适合内存映射 I/O 和信号处理标志，不适合多线程共享计数。
2. **「`relaxed` 没有顺序，所以计数会错」**——同一个原子对象的所有修改仍有一条全体线程一致的修改序，`fetch_add` 不会丢；它缺的是与周围普通读写的顺序。
3. **「`seq_cst` 是默认的，所以不要钱」**——默认只说明不写参数时用它，不说明它免费；本机 3 倍差距就是账单。
4. **「原子类型一定 lock-free」**——`atomic_is_lock_free` 可能返回 0；大结构体的「原子」操作可能由库锁实现，实时性与信号安全都要重新评估。
:::

### 1.12.9 小结

原子性解决「一个对象不被撕裂」，happens-before 解决「谁先谁后」。计数与序号用 `relaxed`；发布数据用 release 写配 acquire 读；只有需要所有线程对多个原子操作看到同一全序时才用 `seq_cst`。`volatile` 只对付编译器，不对付 CPU 和线程。如果只记住一件事：**看到标志就一定能看到标志之前的全部写入，这个保证来自 release/acquire，不来自「原子」二字。**

::: method 即时自测 · 1.12.9
**Q1（记忆）** `relaxed`、`acquire`、`release`、`seq_cst` 各禁止哪种重排？哪一个建立 synchronizes-with？

**Q2（辨析）** 一个计数器用 `relaxed` 原子加，最终值正确；同样的 `relaxed` 用来发布结构体，读方可能看到旧数据。两者差在哪？

::: sol 答案
**A1** `relaxed` 不禁止周围访存重排；`acquire` 禁止后面的读写提到它前面；`release` 禁止前面的读写挪到它后面；`seq_cst` 还要求所有 `seq_cst` 操作有全局一致顺序。release 写与读到它的 acquire 读建立 synchronizes-with。

**A3** C++20：`ready.store(1, std::memory_order_release)`；Rust：`ready.store(1, Ordering::Release)`。读方改成 `relaxed` 后，即使读到 1，也不保证能看到发布者之前写的结构体内容，assert 可能失败。

## 1.12.10 锁的内部：从自旋到 futex {#sec-1.12.10}

这一节回答：`pthread_mutex_lock` 在没人抢的时候到底做了什么？为什么说它「不进内核」，而一有竞争就要 `futex`？自旋锁和它差在哪？

::: preview 先抓住一件事
glibc 的 mutex 是「用户态三态字 + futex」。无竞争：一条 CAS 0→1 进临界区，解锁一条 store 0；有竞争：状态改 2，`FUTEX_WAIT` 睡进内核，解锁者 `FUTEX_WAKE`。内核只提供等待队列，锁的状态由用户态维护。
:::

1.12.9 测得一把 mutex 约 23–27 ns/次。一次系统调用（程序请求内核代劳的入口）通常要几百纳秒到微秒，这个数字本身就在暗示：大多数加锁根本没进内核。用 `strace` 只盯 `futex`，让同一段代码先单线程跑 100 万次加解锁：

```c
/* lab1c12_futex.c 的核心：one 单线程，two 两线程各 100 万次 */
pthread_mutex_lock(&mtx); counter++; pthread_mutex_unlock(&mtx);
```

```text
$ strace -c -e trace=futex ./lab1c12_futex one
counter=1000000
```

输出里只有 `counter=1000000`，没有 `futex` 这一行：100 万次加解锁，零次系统调用。换两个线程抢同一把锁、共 200 万次：

```text
$ strace -c -f -e trace=futex ./lab1c12_futex two
counter=2000000
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
100.00    0.004463           8       524       199 futex
------ ----------- ----------- --------- --------- ----------------
100.00    0.004463           8       524       199 total
```

200 万次加解锁只出现 524 次 `futex`，约占 0.026%；其余 99.97% 仍走用户态快路径。`errors` 列 199 次是调用返回了错误码，竞争路径上 `FUTEX_WAIT` 发现状态字已变会返回 `EAGAIN`，这是正常的「来晚了一步」，不是 bug。

所有互斥都建立在一条硬件原语上：原子地「读旧值并写新值」。区别只在拿不到时怎么办：

| 技术 | 原语 | 代价 | 现实用例 |
|:--|:--|:--|:--|
| 测试并设置（TAS） | `xchg` | 所有等待者抢同一缓存行 | 最简自旋锁 |
| 测试—测试并设置（TTAS） | 先读后 `xchg` | 减少缓存行争用，仍有惊群 | 早期自旋锁 |
| 比较并交换（CAS） | `cmpxchg`/`cas` | ABA；失败重试 | 无锁栈/队列 |
| 链接加载/条件存储（LL/SC） | `ldxr/stxr` | 无 ABA，仅部分架构 | ARM64 内核原子操作 |
| futex | `SYS_futex` | 需要用户态状态字配合 | glibc mutex/condvar |

自旋锁的最小正确实现只要十几行，关键是「先只读、再抢」：

```c
typedef struct { atomic_bool locked; } spinlock_t;

static void spin_lock(spinlock_t *s)
{
    for (;;) {
        while (atomic_load_explicit(&s->locked, memory_order_relaxed))
            ;                                   /* 只读自旋：不抢缓存行所有权 */
        if (!atomic_exchange_explicit(&s->locked, true, memory_order_acquire))
            return;
    }
}

static void spin_unlock(spinlock_t *s)
{
    atomic_store_explicit(&s->locked, false, memory_order_release);
}
```

自旋等待用 `relaxed` 读，因为「看到 false」本身不发布数据；真正获得锁的 `exchange` 用 `acquire`，解锁用 `release`。x86 的 `pause`、ARM 的 `yield` 能降低自旋功耗，C 里没有标准写法，通常用内联汇编；`sched_yield` 代价大得多。

用户态的 `pthread_mutex` 不是纯自旋锁，而是三态状态字加 futex：

<pre class="layout">
   状态字：0 = 未加锁   1 = 已加锁无等待者   2 = 已加锁可能有等待者
   lock:   CAS 0→1 成功 → 进临界区（无系统调用）
           CAS 失败 → 把状态改成 2，futex_wait(2)
   unlock: 原值为 1 → 写 0，结束
           原值为 2 → 写 0，并 futex_wake(1)
</pre>

读图抓住两点。第一，**快路径不进内核**：无竞争时加锁/解锁只是两次用户态原子操作；只有出现第二个等待者，才把状态改成 2 并调用 `futex(FUTEX_WAIT)` 睡眠。第二，**futex 不是锁**：内核只维护「按地址哈希的等待队列」，状态字由用户态维护；`FUTEX_WAIT` 在睡眠前原子地比较状态字，发现已经变了就返回 `EAGAIN`，所以不会丢唤醒。

::: def 定义 1.12.10 · futex {#def-1.12.10}
**futex**（fast userspace mutex）是 Linux 的一个系统调用，不是一种锁。它只做两件事：`FUTEX_WAIT(uaddr, val)` 在当前值等于 `val` 时把线程挂到 `uaddr` 的等待队列上睡眠，否则立刻返回 `EAGAIN`；`FUTEX_WAKE(uaddr, n)` 唤醒最多 n 个等待者。锁的状态、竞争判断、快路径全在用户态；内核只在「真要睡」时介入。
:::

`pthread_mutex` 有五种类型，选错会得到难以理解的返回值：

| 类型 | 重复加锁 | 典型错误码 | 用途 |
|:--|:--|:--|:--|
| `NORMAL`（默认） | 死锁 | 无 | 性能优先 |
| `ERRORCHECK` | 返回错误 | `EDEADLK` | 调试自锁 |
| `RECURSIVE` | 允许，计数 | `EPERM`（解锁别人的） | 递归调用 |
| `ADAPTIVE_NP` | 先自旋再睡 | 无 | 短临界区（glibc 扩展） |
| `ROBUST` | — | `EOWNERDEAD` | 持锁进程崩溃后恢复 |

自旋还是睡眠？判据是「临界区长度 vs 一次上下文切换」：切换约 1–5 µs，临界区只有几十条指令时自旋更快；临界区里可能阻塞（I/O、`malloc`、条件等待）时绝不能自旋。`pthread_spin_lock` 只适合「确定不会睡眠、持有时间极短」的临界区；用户态误用会把 CPU 烧满，而锁的持有者可能已经被调度走了。

::: errata 关于锁的四个误解
1. **「无竞争也要进内核」**——`strace -c` 的 100 万次加解锁里 `futex` 为 0；快路径是纯用户态 CAS。
2. **「futex 就是一把锁」**——它没有状态，只有等待队列；没有用户态状态字，它不知道该不该睡。
3. **「自旋锁总比 mutex 快」**——单核上自旋是纯浪费；临界区长或可能阻塞时，睡眠让出 CPU 才是对的。
4. **「`strace` 里 errors 非零就是出错」**——`FUTEX_WAIT` 的 `EAGAIN` 表示等待前值已变，是竞争路径的正常返回。
:::

::: ex 例 1.12.10 · 先猜这把锁进没进内核 {#ex-1.12.10}
一个线程反复 `pthread_mutex_lock/unlock` 一把**没有别的线程争用**的锁，一百万次。先猜：`strace -c -e trace=futex` 会看到多少次 `futex` 调用？换成两个线程抢同一把锁呢？

::: sol 解答
无竞争时几乎为 0 次：glibc 的 mutex 先在用户态用原子指令把状态字从 0 改成 1，成功就直接返回，只有发现「有人在等」时才用 `FUTEX_WAIT`/`FUTEX_WAKE` 进内核。两个线程争用时才会出现 `futex` 调用，且次数与争用强度相关，不固定等于加锁次数。这也是「锁在无竞争时很便宜」的机制来源：1.12.9 实测一把 mutex 约 23–27 ns/次，正是用户态原子操作的成本量级。
:::
:::

### 1.12.10 小结

无竞争加锁是用户态的一次 CAS，解锁是一次 store；出现第二个等待者才把状态改成 2 并睡进 futex。内核只提供等待队列，锁的状态由用户态维护，所以 futex 不能单独当锁用。自旋适合极短且保证不阻塞的临界区，其余情况让 mutex 把你送进内核。如果只记住一件事：**「无竞争不进内核」不是优化技巧，而是 futex 设计的全部前提。**

## 1.12.11 读写锁、seqlock 与 RCU：读多写少的三种路线 {#sec-1.12.11}

这一节回答：读多写少时，除了「读写锁」，seqlock 和 RCU 各自把代价挪给了谁？为什么 RCU 的读者几乎免费，写者却要等一个「宽限期」？

::: preview 先抓住一件事
三条路线是三次交换：读写锁让读者并行、写者排队；seqlock 让读者完全不加锁、但可能重读；RCU 让读者只标记进出、写者复制并等旧读者离开。读者越自由，写者和内存回收越麻烦。
:::

1.12.6 已经量过读写锁的策略：默认读者优先，写者会被饿；`PREFER_WRITER_NONRECURSIVE_NP` 反过来饿读者。这里只问：读写锁到底在什么负载下划算？同一台 VM 上，4 个读者、读临界区分别是「读一个元素」和「遍历 1024 个元素」：

| 读临界区 | mutex | rwlock | 加速比 |
|:--|--:|--:|--:|
| 读 1 个元素 | 202.0 / 164.1 ms | 392.4 / 399.5 ms | 0.51x / 0.41x |
| 遍历 1024 个 | 63.5 / 65.5 ms | 10.7 / 10.8 ms | 5.92x / 6.06x |

读一个元素时，读写锁反而慢一倍：每个读者都要对同一个读计数做原子 RMW，临界区只有一条 load，锁本身成了全部成本。遍历 1024 个元素时，四个读者真正并行，读写锁快约 6 倍。结论：**读写锁的收益来自「读临界区足够长」，不是「读多」本身**；临界区短就用 mutex，别为 1% 的写比例付两份原子操作。

### seqlock：读者不加锁，代价是重读

seqlock（序号锁）把读者从锁里彻底拿出来。写者把序号加一（变奇）、改数据、再加一（变偶）；读者读前读后各取一次序号，奇数或不一致就重读：

```text
/* seqlock 的读写骨架：seq 必须是原子变量 */
writer:  atomic_fetch_add(&seq, 1);  write_data();  atomic_fetch_add(&seq, 1);
reader:  do { s1 = atomic_load(&seq); if (s1 & 1) continue;
              read_data(); s2 = atomic_load(&seq); } while (s1 != s2);
```

它适合「数据小、可重复读、读者没有副作用」的场景：时间戳、统计快照、小配置。写者不能睡在两次 `seq` 之间，读者不能边读边写日志或改全局状态，否则重读会做两遍。读者得不到「任意时刻都能取到完整快照」的保证，只保证「没有撕裂的一致版本」。

### RCU：读者零开销，写者等一个宽限期

RCU（read-copy-update，读—复制—更新）再进一步：读者只调用 `rcu_read_lock()` / `rcu_read_unlock()`，不做原子 RMW、不写共享缓存行；写者复制一份新数据、原子替换指针、等一个**宽限期**（grace period）后再释放旧版本。宽限期的定义是：从新版本发布开始，到所有「可能还持有旧指针」的读者都离开读临界区为止。新来的读者看到的是新指针，不会拖长宽限期；只有发布之前就在读的读者才会。

这个等待不是理论。下面的实验让一个读者进入 RCU 读临界区后睡 200 ms，写者发布新版本并调用 `synchronize_rcu()`：

```text
reader: 读到的 version=1，已在临界区停留约 200 ms
writer: synchronize_rcu 等待 199.1 ms，随后释放旧版本
（第二次同样是 199.1 ms）
```

写者真的等了 199.1 ms。若把 `synchronize_rcu()` 换成 `call_rcu()`，写者立刻返回，释放回调排到宽限期结束后执行——代价从「写者阻塞」变成「旧版本多活一会儿」。内核里读侧是 `rcu_read_lock()`/`rcu_read_unlock()`，写侧是 `rcu_assign_pointer()`、`synchronize_rcu()`、`kfree_rcu()`；用户态 liburcu 的接口同名，每个线程要先 `rcu_register_thread()`。

| 机制 | 读者开销 | 写者开销 | 旧数据何时释放 | 典型场景 |
|:--|:--|:--|:--|:--|
| 互斥锁 | 原子 RMW + 可能睡 | 同左 | 立即 | 通用 |
| 读写锁 | 原子 RMW（读计数） | 等读者清空 | 立即 | 读多写少、临界区长 |
| seqlock | 两次读序号 + 可能重读 | 两次写序号 | 立即 | 小数据、可重读 |
| RCU | 标记进出，几乎零开销 | 复制 + 等宽限期 | 宽限期后 | 路由表、配置、链表遍历 |

::: def 定义 1.12.11 · 宽限期 {#def-1.12.11}
**宽限期**（grace period）是 RCU 写者从发布新版本到可以安全释放旧版本之间的时间窗。它结束的条件不是「过了多久」，而是「所有在发布之前进入读临界区的读者都已离开」。因此读者睡多久，写者就等多久；新读者不影响已经开始的宽限期。
:::

::: errata 关于三条路线的四个误解
1. **「读写锁总比 mutex 快」**——实测读一个元素时慢一倍；收益要看读临界区长度与写比例。
2. **「seqlock 可以替代锁」**——它只保证读到一个自洽版本，不保护读—改—写；读者也不能有副作用。
3. **「RCU 是免费的无锁」**——读侧免费，写侧要复制、要等宽限期，内存占用会上升；写频繁时反而更差。
4. **「RCU 读临界区可以随便睡」**——经典 RCU 不允许；本机实验故意睡 200 ms 只为把宽限期拉长，生产代码里睡眠会拖住写者。
:::

::: ex 例 1.12.11 · 先猜 relaxed 够不够 {#ex-1.12.11}
线程 A：`data = 42; flag.store(1, memory_order_relaxed);`；线程 B：`while (flag.load(memory_order_relaxed) == 0); print(data);`。先猜：B 一定能打印 42 吗？把 store 换成 `release`、load 换成 `acquire` 之后呢？

::: sol 解答
`relaxed` 只保证这次读写的原子性，**不建立跨变量的先后**：A 的两条写可以被重排或被别的核先看到 `flag=1`、后看到旧 `data`，B 可能打印 0 或未初始化值。改成 `release` 存 + `acquire` 读后建立 happens-before：B 看到 `flag==1` 时，A 在 store 之前的所有写都可见，因此一定是 42。`seq_cst` 更强但更贵；`volatile` 完全不参与这套排序（它只阻止编译器缓存变量）。
:::
:::

### 1.12.11 小结

读写锁让读者并行，代价是读计数上的原子操作与写者饥饿；seqlock 让读者不加锁，代价是可能重读、且只能保护「读到一个一致版本」；RCU 让读者几乎零开销，代价全在写者的复制与宽限期。选择顺序是：先问读临界区有多长，再问写者能不能等，最后问旧数据能不能多活一会儿。如果只记住一件事：**RCU 的读侧不是「没有成本」，而是把成本记在了写者和内存回收上。**

**Q1（记忆）** 宽限期结束的条件是什么？为什么新来的读者不会拖长它？

**Q2（辨析）** 读临界区只有一次数组读时，为什么读写锁可能比 mutex 慢？换成长临界区为什么又反过来？

**Q3（应用）** 一个路由表 99.9% 读、0.1% 写，读者要遍历整张表。选读写锁还是 RCU？写者能不能接受阻塞？

::: sol 答案
**A1** 所有在发布之前进入读临界区的读者都离开。新读者看到的是新指针，不属于「可能持有旧指针」的读者，所以不影响已经开始的宽限期。

**A3** 优先 RCU：读者遍历整张表，读侧零 RMW 收益大；写者复制新表并等宽限期，0.1% 的写频率可以接受阻塞。若写者不能等，用 `call_rcu` 异步释放，或退回读写锁。

### 信号量版读者-写者：`readcnt`、`mutex` 与 `write_sem` {#sec-1.12.11.1}

CSAPP 12.5.4 用两个信号量实现读者优先：

```c
sem_t mutex;      /* 保护 readcnt */
sem_t write_sem;  /* 写者互斥，也挡住新读者 */
int readcnt = 0;

void reader(void) {
    sem_wait(&mutex);
    if (readcnt++ == 0) sem_wait(&write_sem);  /* 第一个读者锁住写者 */
    sem_post(&mutex);
    /* 读临界区 */
    sem_wait(&mutex);
    if (--readcnt == 0) sem_post(&write_sem);  /* 最后一个读者放行 */
    sem_post(&mutex);
}

void writer(void) {
    sem_wait(&write_sem);
    /* 写临界区 */
    sem_post(&write_sem);
}
```

`readcnt` 必须由 `mutex` 保护；第一个读者拿 `write_sem`、最后一个读者放，顺序反了会死锁或让写者插队。这个版本写者会饥饿：读者源源不断，`readcnt` 不归零。要公平，加一个 `queue` 信号量让新读者排在写者后面，代价是吞吐下降。

## 1.12.12 死锁：从进度图到现场取证 {#sec-1.12.12}

这一节回答：两个线程各持一把锁、再等对方那把，为什么必然卡死？「四个条件」之外，怎样用一张进度图看出死锁区，又用三条命令把它变成可复查的证据？

::: preview 先抓住一件事
死锁不是「锁太慢」，是四个条件同时成立：互斥、持有并等待、不可抢占、循环等待。工程上只需两幅图：进度图看轨迹是否进入死锁区，等待图看线程与锁是否成环。取证顺序固定：`timeout` 确认卡住 → `ps` 看等待点 → `strace` 看 futex 地址 → `helgrind` 报锁序。
:::

1.12.6 只让你认出现场：CPU 接近 0、线程都睡在 futex、各自手里的锁正是别人在等的。这里把「为什么」和「怎么证明」补齐。

先看进度图。横轴是线程 T1 执行到第几条指令，纵轴是 T2；每个点是一次联合状态，任何调度都只能让一条轴前进一格，所以轨迹是一条阶梯。对共享变量的「读—改—写」会围出一块**不安全区**，轨迹进去就可能算错；两把锁的「持有 + 等待」会围出一块**死锁区**，轨迹一旦进去，四个方向都被挡住：

<pre class="layout">
        T2 进度
          ▲
          │   ┌─────────────┐
   T2 持B  │   │   死锁区     │
   等 A   │   │ T1 持A 等B   │
          │   └─────────────┘
          └──────────────────▶ T1 进度
                  T1 持A 等B
</pre>

图的读法：只要两个线程都已经拿到第一把锁、又都还没拿到第二把，联合状态就落在矩形里；矩形内 T1 的下一步是等 B，T2 的下一步是等 A，没有一条边能走出去。**这就是「死锁区」：不是某个变量值错了，而是调度空间里的一块吸收区。**

四个条件逐一对应：

| 条件 | AB/BA 里是什么 | 破坏办法 |
|:--|:--|:--|
| 互斥 | A、B 同一时刻只能一个线程持有 | 无锁结构、读写锁 |
| 持有并等待 | 拿着 A 等 B | `trylock` 失败就全放 |
| 不可抢占 | 不能把别人手里的锁抢走 | `timedlock` 超时回滚 |
| 循环等待 | T1 等 B、T2 等 A | 全局锁序（编号升序） |

下面的程序用屏障把「两人都拿到第一把」变成必然而不是碰巧：

```c
/* lab1c12_dead.c：AB/BA 死锁；-DFIX 改成全体 a→b */
#define _GNU_SOURCE
#include <pthread.h>
#include <stdio.h>

static pthread_mutex_t a = PTHREAD_MUTEX_INITIALIZER;
static pthread_mutex_t b = PTHREAD_MUTEX_INITIALIZER;
static pthread_barrier_t bar;
static long shared;

static void *t0(void *arg)
{
    (void)arg;
#ifdef FIX
    pthread_barrier_wait(&bar);
    pthread_mutex_lock(&a);
#else
    pthread_mutex_lock(&a);
    pthread_barrier_wait(&bar);
#endif
    pthread_mutex_lock(&b);
    shared++;
    pthread_mutex_unlock(&b);
    pthread_mutex_unlock(&a);
    return NULL;
}

static void *t1(void *arg)
{
    (void)arg;
#ifdef FIX
    pthread_barrier_wait(&bar);
    pthread_mutex_lock(&a);
    pthread_mutex_lock(&b);
    shared++;
    pthread_mutex_unlock(&b);
    pthread_mutex_unlock(&a);
#else
    pthread_mutex_lock(&b);
    pthread_barrier_wait(&bar);
    pthread_mutex_lock(&a);
    shared++;
    pthread_mutex_unlock(&a);
    pthread_mutex_unlock(&b);
#endif
    return NULL;
}

int main(void)
{
    pthread_t x, y;
    pthread_barrier_init(&bar, NULL, 2);
    if (pthread_create(&x, NULL, t0, NULL) != 0 ||
        pthread_create(&y, NULL, t1, NULL) != 0)
        return 1;
    pthread_join(x, NULL);
    pthread_join(y, NULL);
    printf("shared=%ld expected=2\n", shared);
    return 0;
}
```

非 `FIX` 版：T1 拿 A、T2 拿 B，屏障放行后各自去拿对方的锁，必然互等。`FIX` 版把屏障挪到加锁之前，两人都按 A→B 的顺序，拆掉「循环等待」。实测：

```text
$ timeout 2 ./lab1c12_dead; echo "exit=$?"
exit=124
$ timeout 2 ./lab1c12_dead_fix; echo "exit=$?"
shared=2 expected=2
exit=0
```

`124` 是 `timeout` 自己的返回码，不是程序的退出码；程序一行输出都没有，说明它没走到 `printf`。但「超时」本身只证明「2 秒内没结束」，还要看线程停在哪：

```text
$ ps -L -o pid,tid,stat,wchan:32,comm -p <pid>
    PID     TID STAT WCHAN                            COMMAND
 412860  412860 Sl   futex_do_wait                    lab1c12_dead
 412860  412862 Sl   futex_do_wait                    lab1c12_dead
 412860  412863 Sl   futex_do_wait                    lab1c12_dead
```

三个线程的 `STAT` 都是 `Sl`：`S` 表示可中断睡眠，`l` 表示多线程；`wchan` 是 `futex_do_wait`，主线程在 `pthread_join` 等，两个 worker 在锁上等。`wchan` 的名字随内核版本变，老内核可能显示 `futex_wait_queue`。再看每个线程等的地址（只截最后两行）：

```text
$ timeout 2 strace -f -e trace=futex ./lab1c12_dead
412936 futex(0xb82e60a20018, FUTEX_WAIT_PRIVATE, 2, NULL <unfinished ...>
412937 futex(0xb82e60a20068, FUTEX_WAIT_PRIVATE, 2, NULL <unfinished ...>
```

两个不同的 `uaddr`，第二个参数都是 `2`——正是 1.12.10 的三态字「已加锁且可能有等待者」，而且后面没有 `FUTEX_WAKE`。一个等 A、一个等 B，环闭了。地址与 PID 每次运行都不同，别照抄。

最后一道是锁序检查。helgrind 不需要等死锁发生，它记录每个线程「先拿哪把、后拿哪把」，发现两个线程的顺序相反就报：

```text
$ valgrind --tool=helgrind ./lab1c12_order
Thread #3: lock order "0x128048 before 0x128018" violated
Observed (incorrect) order is: acquisition of lock at 0x128018
   at ... ba ...
 followed by a later acquisition of lock at 0x128048
```

`lab1c12_order` 只是把 A→B 与 B→A 各跑一次、没有并发，所以它正常退出，helgrind 仍报出「锁序倒置」。这正是工具的价值：**在故障发生之前，先把等待图里的环画出来**。

把等待关系画成图，环就一目了然：

<pre class="layout">
   T1 ──持有──▶ A ◀──等待── T2
   T1 ──等待──▶ B ◀──持有── T2
   环：T1 → B → T2 → A → T1
</pre>

修复按代价从低到高：

| 手段 | 做法 | 代价 | 适用 |
|:--|:--|:--|:--|
| 全局锁序 | 所有锁编号，永远升序获取 | 纪律与文档 | 绝大多数场景 |
| 一次性申请 | `trylock` 全部，失败全放 | 重试与活锁风险 | 锁少、竞争低 |
| 超时回滚 | `pthread_mutex_timedlock` + 回滚 | 需要可回滚边界 | 有状态机/数据库 |
| 消息传递 | 不共享，改为队列 | 架构改动大 | actor/流水线 |

C++17 的 `std::scoped_lock` 内部用「try-and-backoff」一次锁多把，能避免 AB/BA；C 没有标准等价物，只能自己写。注意「按地址排序加锁」也是全局锁序的一种，但堆对象被 `realloc` 或移动后地址会变，不如显式编号可靠。

死锁只是「永久阻塞」的一种。**活锁**是线程都在跑但互相让路，没人推进；**饥饿**是某个线程永远排不上队；**优先级反转**是低优先级持锁、高优先级等待、中优先级插队。Mars Pathfinder 的重启就是优先级反转的经典案例；修法是优先级继承（`PTHREAD_PRIO_INHERIT`）或优先级天花板，普通分时任务用不上。

::: def 定义 1.12.12 · 死锁区与等待图 {#def-1.12.12}
**死锁区**（deadlock region）是进度图上由「双方都已持有第一把锁、又都在等第二把」围出的矩形；轨迹进入后没有任何合法调度能离开。**等待图**（wait-for graph）以线程和锁为节点，「持有」「等待」为有向边；图里出现环，就是死锁的必要条件。
:::

::: errata 关于死锁取证的四个误解
1. **「`timeout` 返回 124 就一定是死锁」**——只说明进程在时限内没结束，可能只是慢；要再看 `ps` 的 `wchan` 和 `strace` 的 futex 地址。
2. **「加个 `sleep` 就好了」**——睡眠只改变交错概率，AB/BA 的顺序还在；负载一换就会复发。
3. **「`gdb -p` 总能挂上」**——Ubuntu 默认 `ptrace_scope=1`，只允许父进程 attach；本书 VM 上 `gdb -p` 被拒，用 `strace -f` 从父进程启动即可拿到等待点。
4. **「`trylock` 不会死锁，所以随便用」**——失败后不退避、立刻重试，两个线程会同步地抢—放—抢，变成活锁；要加随机退避。
:::

::: ex 例 1.12.12 · 先猜哪条路径会死 {#ex-1.12.12}
线程 1：`lock(A); lock(B); unlock(B); unlock(A);`；线程 2：`lock(B); lock(A); unlock(A); unlock(B);`。先猜：两个线程同时跑一定会死锁吗？如果把两边都改成按 A→B 的顺序加锁呢？

::: sol 解答
不一定会：只有交错到「线程 1 拿到 A、线程 2 拿到 B，然后各自等对方」时才会死锁（这正是进度图上两条路径的交叉点）。改成统一 A→B 顺序后，**环路消失**，死锁不可能发生——这是「破坏循环等待」这一条的代码形态。实测取证：`timeout 3 ./deadlock` 返回 `exit=124` 且没有 `done` 输出；`helgrind` 会报锁序不一致。
:::
:::

### 1.12.12 小结

死锁是四个条件同时成立：互斥、持有并等待、不可抢占、循环等待；破坏任意一个就能拆环。进度图把「调度运气」变成几何，等待图把「谁等谁」变成有向图。取证按 `timeout` → `ps` → `strace` → `helgrind` 走，先证明卡住，再证明卡在哪个地址，最后证明锁序倒置。如果只记住一件事：**死锁不是「锁慢」，是等待图里有一个环；修法不是加 sleep，是拆掉一条边。**

## 1.12.13 线程池的容量、背压与关闭语义 {#sec-1.12.13}

这一节回答：1.12.5 的池子已经能正确跑完任务，为什么上线前还要再回答三个问题——worker 开几个、队列满了把压力推给谁、关闭时还在排队的任务算谁的？

::: preview 先抓住一件事
容量先算 `L = λW`，再用压测找拐点，不能按核数拍；队列满只有三种负责任的处理：阻塞提交、立即拒绝、调用者执行；关闭必须先停收、再排空，worker 退出要同时满足 `shutdown` 与 `count == 0`，顺序写反就丢单。
:::

先接 1.12.5 的结论：池子省掉的是每任务约 0.05–0.10 ms 的创建回收，换来一条有界队列和一对条件变量。那条池子回答了「怎么实现」，这一节回答「怎么定参数、怎么失败、怎么收尾」。

**容量怎么定**。先算稳态并发数。设任务到达率 λ（个/秒）、每个任务在池内平均停留 W（秒），Little 定律给出 `L = λW`。网关每秒 2 万请求、每请求在池内平均 5 ms，就是 `L = 20000 × 0.005 = 100` 个并发任务；这是算例，不是本机读数。若任务大部分时间在等 I/O，可按 `N ≈ 核数 × (1 + W_io / W_cpu)` 估：4 核、等待是计算的 9 倍，约 40 个 worker。两个公式都只是起点，最终要压测找拐点：1.12.5 实测两万个空任务，1 个 worker 反而跑到 1.47–1.72 M items/s，4 个只有 1.07–1.08 M；换成每个任务 2 万次依赖链，4 个 worker 33.1 ms、1 个 135.4 ms。同一公式算不出这个反转，只有任务重量能解释。

三个环境量会把公式推翻。`sysconf(_SC_NPROCESSORS_ONLN)` 在容器里返回宿主机核数，不是 CPU 配额；要读 cgroup v2 的 `/sys/fs/cgroup/cpu.max`，`200000 100000` 才表示 2 核。`RLIMIT_NPROC` 与 `pids.max` 数的是线程，池大小乘进程数不能超过限额，否则 `pthread_create` 返回 `EAGAIN`。每个线程默认 8 MiB 虚拟栈，真开几百个线程时用 `pthread_attr_setstacksize` 降到 256 KiB–1 MiB，但要给深递归留余量。

**队列满了怎么办**。只有三种策略，区别是把压力退回给谁：

| 策略 | 行为 | 适合 | 代价 |
|:--|:--|:--|:--|
| 阻塞提交（背压） | `submit` 等 `not_full` | 上游能等、批处理 | 调用者被拖慢，可能连锁阻塞 |
| 立即拒绝 | 返回 `EAGAIN`/503 | 面向用户的入口 | 调用者必须处理失败 |
| 调用者执行 | 提交线程自己跑 | 天然限流 | 可能阻塞事件循环 |

无界队列不是第四种策略，它只是把「现在拒绝」推迟成「以后 OOM」。选完策略还要把队列长度、等待时间 P99、拒绝次数暴露成指标；只看 CPU 会漏掉「队列在涨、worker 在睡」的假健康。

::: def 定义 1.12.13 · Little 定律与背压 {#def-1.12.13}
**Little 定律**：稳态下，系统中的平均任务数 `L` 等于到达率 `λ` 乘平均停留时间 `W`，即 `L = λW`；它不假设到达分布，只要求稳态。**背压**（backpressure）是队列满时让提交方等待或失败，把过载信号退回上游，而不是无限收下。容量算的是「平均要多少并发」，背压决定的是「超出时谁承担等待」。
:::

**关闭时两个判断的顺序**。关闭要依次做三件事：停收、排空、join。`pool_shutdown` 先置 `shutdown = 1`，广播 `not_empty` 与 `not_full`，让睡在 `submit` 里的调用者醒来返回错误；然后 worker 把队列里剩下的任务跑完；最后 `pthread_join` 确认每个 worker 都退出。

worker 醒来后要判断两件事，顺序不能反：**先看还收不收（`shutdown`），再看活干完没有（`count == 0`）**。只有两者同时成立才允许退出：

```c
while (p->count == 0 && !p->shutdown)
    pthread_cond_wait(&p->not_empty, &p->mtx);
if (p->shutdown && p->count == 0) {   /* 先关、再空，才走 */
    pthread_mutex_unlock(&p->mtx);
    break;
}
```

写成 `if (p->shutdown) break;` 会在关闭瞬间丢掉队列里所有任务；写成只看 `count == 0` 又会在暂时没活时提前退出。提交路径同理：队列未满但已 `shutdown` 时也要拒绝；关闭后到达的任务不能先睡在 `not_full` 上。需要宽限期时用 `pthread_cond_timedwait`，到点仍未排空就返回剩余任务数，由调用者决定丢弃还是落盘。

::: errata 关于线程池的三个误解
1. **「worker 数按核数抄就行」**——I/O 密集可以多于核数，空任务反而越少越快；容量要按 `L = λW` 估、按压测定。
2. **「无界队列不会丢任务」**——它不丢任务，丢的是内存和延迟，最后往往 OOM；有界队列加背压才是可控失败。
3. **「`shutdown` 置位就算关闭完成」**——置位只表示不再收新任务；不排空、不 join，在途任务和已排队任务都没有交代。
:::

### 1.12.13 小结

容量先算 `L = λW`，再用压测找拐点；队列满时在阻塞、拒绝、调用者执行三者中选一个，并把队列指标暴露出来；关闭按「停收 → 排空 → join」走，worker 退出必须 `shutdown && count == 0`。如果只记住一件事：**池子的容量是算出来再压出来的，关闭的顺序是先停收再排空，反过来就丢单**。

**Q1（算）** 每秒 1.2 万个请求，每个请求在池内平均 8 ms，稳态需要多少并发？如果 4 核上 I/O 等待是计算的 7 倍，worker 数怎么估？

**Q2（辨析）** 面向用户的 HTTP 入口和离线批处理，队列满时各选哪种背压策略？为什么无界队列不算策略？

::: sol 答案
**A1** `L = 12000 × 0.008 = 96` 个并发。I/O 密集按 `4 × (1 + 7) = 32` 个 worker 起估，再用压测修正；两个数都只是起点。

## 1.12.14 三种语言的并发原语对照：C11、C++20 与 Rust {#sec-1.12.14}

这一节回答：同一套内存模型，C11、C++20 与 Rust 各自把「防错」放在哪一层？换语言时，哪些知识可以带走，哪些保证会消失？

::: preview 先抓住一件事
三者的原子与内存序是同一张表，只换拼写；真正的差别在「错误被谁发现」：C11 只给原语，忘了解锁就死锁；C++ 用 RAII 管住锁的生命周期，但锁序仍靠人；Rust 把数据关进 `Mutex<T>`，safe 代码里的数据竞争在编译期就被拒绝。
:::

先看能力对照。名字不同，语义大多一一对应：

| 能力 | C11 | C++20 | Rust 2021 |
|:--|:--|:--|:--|
| 线程创建 | `thrd_create`（`<threads.h>`） | `std::thread`、`std::jthread` | `thread::spawn`、`thread::scope` |
| 互斥 | `mtx_t` + `mtx_lock/unlock` | `std::mutex` + `lock_guard`/`unique_lock`/`scoped_lock` | `Mutex<T>` + `MutexGuard` |
| 条件变量 | `cnd_t` + `cnd_wait/signal` | `std::condition_variable`（`wait(lock, pred)`） | `Condvar`（`wait_while`） |
| 原子 | `_Atomic` / `atomic_*` | `std::atomic<T>` | `AtomicU64` 等 + `Ordering` |
| 内存序 | `memory_order_*` | `std::memory_order_*` | `Ordering::*` |
| 一次性初始化 | `call_once` | `std::call_once` | `OnceLock`/`Once` |
| 线程局部 | `_Thread_local`、`tss_t` | `thread_local` | `thread_local!` |
| 生命周期防错 | 无 | RAII 防泄漏，不防锁序 | `Send`/`Sync` 编译期检查 |
| 数据竞争 | 未定义行为，靠 TSan | 未定义行为，靠 TSan | safe 代码中编译期拒绝 |
| 有界队列 | 自己写 | 自己写 | `mpsc::sync_channel(n)`、`crossbeam` |

三段代码做同一件事：4 个线程各把计数器加 20 万次。C11 版程序如下，VM 上用 GCC 13.3 编译运行：

```c
/* lab1c12_c11.c */
#include <stdio.h>
#include <threads.h>

static mtx_t mtx;
static long counter;

static int worker(void *arg)
{
    (void)arg;
    for (long i = 0; i < 200000; i++) {
        if (mtx_lock(&mtx) != thrd_success) return 1;
        counter++;
        mtx_unlock(&mtx);
    }
    return 0;
}

int main(void)
{
    thrd_t t[4];
    mtx_init(&mtx, mtx_plain);
    for (int i = 0; i < 4; i++) thrd_create(&t[i], worker, NULL);
    for (int i = 0; i < 4; i++) thrd_join(t[i], NULL);
    printf("C11 counter=%ld expected=800000\n", counter);
    mtx_destroy(&mtx);
    return 0;
}
```

```text
C11 counter=800000 expected=800000
```

C++20 版用 `std::scoped_lock`，同样在 VM 上编译运行：

```cpp
#include <iostream>
#include <mutex>
#include <thread>
#include <vector>

int main()
{
    long counter = 0;
    std::mutex mtx;
    std::vector<std::thread> pool;
    for (int i = 0; i < 4; ++i)
        pool.emplace_back([&] {
            for (long n = 0; n < 200000; ++n) {
                std::scoped_lock lock(mtx);
                ++counter;
            }
        });
    for (auto &t : pool) t.join();
    std::cout << "C++20 counter=" << counter << " expected=800000\n";
}
```

```text
C++20 counter=800000 expected=800000
```

Rust 版把数据放进 `Mutex` 或原子量，`thread::scope` 允许借用栈上的计数器，不必套 `Arc`：

```rust
use std::sync::atomic::{AtomicU64, Ordering};
use std::thread;

fn main() {
    let counter = AtomicU64::new(0);
    thread::scope(|s| {
        for _ in 0..4 {
            s.spawn(|| {
                for _ in 0..200_000 {
                    counter.fetch_add(1, Ordering::Relaxed);
                }
            });
        }
    });
    println!("Rust counter={}", counter.load(Ordering::Relaxed));
}
```

这台 VM 没有装 `rustc`，Rust 片段**未实测**，只作语法与语义对照，不引用运行数字；C11 与 C++20 两段是实测，均输出 `800000`、退出码 0。

三段代码的差别不在结果，在错误被谁拦住。C11 的 `mtx_lock` 返回 `thrd_success` 或错误码，不设 `errno`；它没有 RAII，任何提前 `return` 都要记得先 `mtx_unlock`，忘了就是死锁。`<threads.h>` 由 glibc 2.28 起提供，macOS 的 libc 没有这个头，跨平台项目不能默认它存在。

C++ 的 `scoped_lock` 在析构时解锁，异常路径也不会漏；`std::scoped_lock(m1, m2)` 还能一次锁两把，内部用避免死锁的算法处理 AB/BA。但它管不住跨函数的锁序：两个函数各自只锁一把、调用链上却以相反顺序拿，编译器和 RAII 都看不见。

Rust 把 `T` 放进 `Mutex<T>`，不拿到 guard 就碰不到数据；`Rc` 不是 `Send`、`RefCell` 不是 `Sync`，跨线程使用会在编译期失败。代价是全局状态要显式包装，且一旦写 `unsafe` 或走 FFI，编译器的保证立即失效。三者的内存序仍与 1.12.9 同一张表：C11 `memory_order_release`、C++ `std::memory_order_release`、Rust `Ordering::Release` 是同一个约束。

读表还要看三处容易漏掉的差别。条件变量的谓词：C11 的 `cnd_wait` 要自己写 `while`，C++ 的 `wait(lock, pred)` 把重查收进库，Rust 的 `wait_while` 同样把谓词放进调用，写错的空间依次变小。线程回收：C11 的 `thrd_join` 用第二个参数拿返回码，C++ 的 `join` 不返回结果、要靠共享变量，Rust 的 `scope` 在作用域结束时自动 join。有界队列：只有 Rust 标准库直接给 `sync_channel(n)`，C 与 C++ 都要自己写，也就是 1.12.5 那条有界队列。

语言选型还要看边界。C11 的 `_Atomic` 与 `pthread` 在嵌入式、内核与 C ABI 边上最稳；C++ 的 `std::thread`、`jthread` 在已有服务里迁移成本最低；Rust 的所有权把「谁拥有缓冲区」写进类型，但与 C 库交界处仍要 `unsafe` 包装，保证只覆盖 safe 的那一半。

::: errata 关于语言对照的三个误解
1. **「Rust 保证没有数据竞争」**——只对 safe 代码成立；`unsafe`、FFI 与手写同步仍可能引入竞争，只是把责任收回给了人。
2. **「C++ 有 RAII 就不会死锁」**——RAII 只保证离开作用域时解锁，不保证加锁顺序；跨函数、跨回调的锁序仍要自己定。
3. **「C11 的 `<threads.h>` 到处都有」**——POSIX 不要求它，macOS 的 libc 没有；用之前先查实现，或退回 `pthread`。
:::

### 1.12.14 小结

三种语言共享同一套内存序与 happens-before，差别是防错位置：C11 靠人，C++ 靠析构，Rust 靠类型系统。C11 与 C++20 的计数程序在 VM 上实测通过，Rust 因缺 `rustc` 未实测。如果只记住一件事：**换语言不会换掉「谁共享、谁排序」这两个问题，只会换掉「谁提醒你」。**

## 1.12.15 并发调试：TSan、helgrind 与 perf {#sec-1.12.15}

这一节回答：竞争可能一万次才出现一次，工具怎样把它变成一次就能看见？TSan、helgrind、perf 各能证明什么，又不能证明什么？

::: preview 先抓住一件事
TSan 要重编译，跑起来快，报告一定给出两次访问和各自调用栈；helgrind 不用重编译，慢得多，还能报锁序；perf 在这台 VM 被 `perf_event_paranoid=4` 挡住。三者都只扩大观测窗口，不能证明「没有竞争」。
:::

用 1.12.2 的竞争程序缩小版做实验：两个线程各 `counter++` 10 万次，源码存成 `lab1c12_race.c`。先按 TSan 的要求编译：

```bash
gcc -std=c17 -O1 -g -fsanitize=thread -pthread lab1c12_race.c -o lab1c12_race_tsan
./lab1c12_race_tsan
```

直接运行，本机（Ubuntu 24.04.5，aarch64）实测报的是另一类错误：

```text
FATAL: ThreadSanitizer: unexpected memory mapping 0xbe5eb4530000-0xbe5eb4531000
```

这是 TSan 与地址随机化（ASLR）抢地址空间，不是代码问题。加 `setarch -R` 关掉 ASLR 再跑：

```bash
setarch -R ./lab1c12_race_tsan
```

```text
# 实测（Ubuntu 24.04.5 aarch64，setarch -R；pid 随运行变化）
WARNING: ThreadSanitizer: data race (pid=414365)
  Read of size 8 at 0xaaaaaaac0018 by thread T2:
    #0 worker /tmp/lab1c12_race.c:10
  Previous write of size 8 at 0xaaaaaaac0018 by thread T1:
    #0 worker /tmp/lab1c12_race.c:10
  Location is global 'counter' of size 8 ...
SUMMARY: ThreadSanitizer: data race /tmp/lab1c12_race.c:10 in worker
counter=200000 expected=200000
```

三行读法：`Read` 与 `Previous write` 是两次冲突访问；两个 `#0 worker` 是各自栈顶，直接指到第 10 行；`Location is global 'counter'` 指认变量。程序最后仍打印了正确的 200000，退出码却是 66——**跑对了不等于没竞争**，TSan 看到的是访问历史，不是这一次的结果。

修法是加锁或换 `atomic_fetch_add`，重编译重跑；报告消失只说明这条路径上没再看到冲突。TSan 有三个边界：常用 `-O1 -g`，不能和 ASan 同开，只检查真正执行到的路径。地址随机化导致复现不稳定时，`setarch -R` 要一直带着。

helgrind 走另一条路：不用重编译，直接跑未插桩的二进制。同一个程序用 `-O0 -g` 编译后：

```bash
gcc -std=c17 -O0 -g -pthread lab1c12_race.c -o lab1c12_race_hg
valgrind --tool=helgrind ./lab1c12_race_hg
```

```text
==414375== Possible data race during read of size 8 at 0x128018 by thread #3
==414375== Locks held: none
==414375==    at 0x1088F0: worker (lab1c12_race.c:11)
==414375== This conflicts with a previous write of size 8 by thread #2
==414375== Address 0x128018 is 0 bytes inside data symbol "counter"
```

`Locks held: none` 是它的核心判据：两边都没有持锁，冲突才成立；如果一边持锁，它会检查是不是同一把锁。helgrind 还能报锁序反转（`lock order ... violated`），代价是慢，常被估成 20–100 倍。它适合「二进制已经在手、不能重编译」和「怀疑锁序」两类场景。

perf 在这台机器上用不了。`perf_event_paranoid` 是 4，普通用户连 CPU 事件都拿不到：

```text
$ perf stat -e cache-misses,context-switches /bin/true
perf_event_paranoid setting is 4:
...
>= 1: Disallow CPU event access
$ perf c2c record -o /tmp/lab1c12_c2c.data /bin/true
failed: no PMU supports the memory events
```

所以本节不引用任何 PMU 读数。替代证据是 `ps -L -o pid,tid,psr,pcpu,stat` 看线程在哪个核、切了多少次，`strace -c -f -e trace=futex` 数 futex，`taskset` 把线程钉到同一个核复现争用；这些在 1.12.10 与 1.12.2 用过。工具选择可以压成一句：**先 TSan 定位「哪两次访问」，再 helgrind 看「有没有持锁、锁序对不对」，perf 能跑时才用它量化缓存与上下文切换。**

| 工具 | 要重编译吗 | 本机状态 | 报告里先看什么 |
|:--|:--|:--|:--|
| TSan | 要 | 加 `setarch -R` 可跑 | 两次访问、各自栈、变量名 |
| helgrind | 不要 | 可跑 | 冲突、`Locks held`、锁序 |
| perf | 不要 | 不可用 | PMU 计数、缓存争用 |

三者不是互相替代：TSan 给你精确的代码位置，helgrind 给你「手里有没有锁」，perf 给你硬件计数；本机缺了最后一环，就用 `ps`、`strace` 与墙钟补，不要把「补不上」写成「没问题」。

::: errata 关于并发调试的三个误解
1. **「TSan 没报就是没有竞争」**——它只覆盖执行到的路径，调度没撞上的交错它也没看见；没报只是「这次没看见」。
2. **「helgrind 比 TSan 准」**——两者都在近似 happens-before；helgrind 不要求重编译、能报锁序，但更慢，误报与漏报的取舍不同。
3. **「perf 一定看得到缓存未命中」**——本机 `perf_event_paranoid=4`，`perf c2c` 直接报 `no PMU supports the memory events`；先查权限与 PMU，再决定要不要用。
:::

### 1.12.15 小结

TSan 用重编译换精确的两次访问与栈，本机必须 `setarch -R`；helgrind 用变慢换「不重编译 + 锁序」；perf 在受限环境里可能什么都看不到。工具报告是取证线索的一环，不是判决书。如果只记住一件事：**先让工具指出哪两次访问冲突，再回到代码问它们之间缺了哪条同步。**

::: method 即时自测 · 1.12.15

**Q2（辨析）** 同一个竞争程序，TSan 报错但打印的计数仍然正确；这能否说明程序「只是运气不好」？helgrind 的 `Locks held: none` 又在证明什么？

::: sol 答案

**A3** 锁序问题先用 helgrind（不重编译，能报 `lock order violated`）；伪共享先看 `ps -L` 的 `PSR` 与 `perf c2c`（若可用）。本机 `perf_event_paranoid=4`、`perf c2c` 报 `no PMU supports the memory events`，只能用 `taskset`、`/proc` 与墙钟替代。

## 1.12.16 九条并发陷阱 {#sec-1.12.16}

这一节回答：并发 bug 的现象往往只有一句「偶尔不对」，怎样从现象缩到原因，再决定先查哪一行？

::: preview 先抓住一件事
九条按三组记：竞争组查「有没有同步、谓词有没有重查」，死锁组查「锁序与持锁调用」，生命周期组查「谁回收、谁排空、fork 后还能调什么」。先看现象，再看原因，最后只查一个地方。
:::

| # | 组 | 现象 | 原因 | 先查什么 |
|--:|:--|:--|:--|:--|
| 1 | 竞争 | 计数偶发少，加 `volatile` 更差 | `counter++` 是读改写三步，无同步即 UB | 两次访问之间有没有锁或原子；TSan 与反汇编；`-O0` 实测 2,016,895/4,000,000 |
| 2 | 竞争 | 条件变量醒来，`items=-1` | `if` 只判一次，虚假唤醒或值被抢走 | `wait` 外层是不是 `while`，谓词是否持锁改；`if` 版三跑三中 -1 |
| 3 | 竞争 | 通知发了，等待者还在睡 | 先改条件后 `signal`，或改条件不持锁 | `signal` 是否在持锁的临界区内；等待前是否重查谓词 |
| 4 | 死锁 | 两线程 CPU 为 0，互等 | AB/BA 锁序成环 | 全局锁序；`strace` 两个 futex 地址；helgrind 锁序 |
| 5 | 死锁 | 持锁调回调后自锁 | 回调链再次申请同一把 NORMAL mutex | `gdb -p` 的 `bt`、mutex 类型；把回调移到锁外 |
| 6 | 死锁 | 有界缓冲区跑不动，`exit=124` | 先拿 mutex 再等 empty，满时死锁 | `sem_wait` 与 `pthread_mutex_lock` 的顺序及初值；顺序正确时 `sum=4999950000` |
| 7 | 生命周期 | 内存涨、线程数不涨 | joinable 线程退出后栈没人 join | `VmSize` 与创建/join 是否配对；8 MiB 是虚拟栈 |
| 8 | 生命周期 | 关闭后任务少了、进程不退 | `shutdown` 与 `count` 顺序反，或 detached 无法 join | worker 退出条件 `shutdown && count == 0`、是否 broadcast |
| 9 | 生命周期 | 多线程 `fork` 后子进程卡死 | 子进程继承别的线程持有的 `malloc`/stdio 锁 | fork 与 exec 之间是否只调 async-signal-safe |

竞争组的共同根是「共享写没有 happens-before」。修法按 1.12.2 的代价排：先看能不能不共享，再考虑单个原子量，最后才是锁。`volatile` 不在这条路上——它只阻止编译器把读写折叠掉，不提供原子性，也不建立线程间顺序。争用还有一层硬件成本：1.12.2 的 `taskset` 对照里，同一段争用代码钉在一个核上跑出 68 万次/秒，不钉只有 18 万，差的是缓存行跨核迁移，不是「单核更安全」。

死锁组先破环。四条件里最容易动的是「循环等待」：给所有锁编号，任何路径都按升序拿；做不到就把「持锁调用外部代码」改成「锁内复制、锁外调用」。第 6 条的顺序错误最典型：`sem_wait(&empty)` 必须在 `pthread_mutex_lock` 之前，缓冲区满时生产者才不会攥着锁睡觉；顺序正确时 0 到 99999 的求和是 `4999950000`，写反则 `timeout` 杀掉进程，`exit=124`。

生命周期组问「谁拥有、谁收尾」。joinable 线程退出后内核任务没了，栈还挂着，`/proc` 看不见，`VmSize` 看得见；关闭时先停收再排空，只置 `shutdown` 不排空就是丢单；`fork` 后子进程只允许 async-signal-safe 函数，`malloc`、`printf`、锁都可能继承别人的半截状态。`pthread_*` 返回错误码而不设 `errno`，这一条虽不在表里，查错时同样先看返回值。

::: errata 关于陷阱表的三条用法
1. **「先查什么」不是修复顺序**——先取证再改代码；一上来就换锁，容易把可复现的现场改没。
2. **现象会跨组**——关闭丢单既像生命周期（没人排空），也像死锁（worker 睡死）；按「谁共享、谁排序」回到根因。
3. **修好一条不代表没有别的**——竞争与死锁常同时存在；改完用 TSan 或 helgrind 复跑，再压测。
:::

### 1.12.16 小结

九条陷阱按竞争、死锁、生命周期分组，每组只问一个根问题：有没有同步、锁序成不成环、资源谁收尾。现象只用来选组，原因才决定改哪一行。如果只记住一件事：**先按现象分组，再用一条证据把范围缩到一行代码，最后才动手改。**

::: method 即时自测 · 1.12.16
**Q1（辨析）** 计数偶发少，有人建议加 `volatile`。这属于哪一组？先查什么？为什么 `volatile` 不解决问题？

**Q2（应用）** 条件变量版队列偶尔返回 `items=-1`，代码用的是 `if (!ready) wait`。改哪里、为什么？

**Q3（推理）** 有界缓冲区顺序写反后 `timeout` 返回 124。画出两个线程各持有什么、在等什么，并给出最小修复。

::: sol 答案
**A1** 竞争组。先查两次访问之间有没有锁、原子或条件变量建立 happens-before，并用 TSan 与反汇编确认。`volatile` 只保证每次真读写，不保证读改写原子，也不建立线程间顺序。

## 1.12.17 本章小结 {#sec-1.12.17}

这一节回答：学完这 17 节，面对一个「偶尔少加、偶尔卡死、压测才复现」的故障，你能不能在几分钟内说出共享了什么、靠什么排序、证据在哪？

::: preview 先抓住一件事
本章的出口不是背下所有 API，而是形成一条固定动作：**先找共享状态，再找它靠什么建立先后，最后用工具把「哪两次访问」钉出来。** 这三问答不上来，换多少种锁都只是把 bug 推迟。
:::

这一章的主线分三段。第一段 1.12.1–1.12.7 解决「会用」：三种并发模型的成本分别记在创建、同步、状态机上；`counter++` 的三步让丢失更新成为常态，`-O0` 实测只剩 2,016,895/4,000,000；互斥锁、原子、局部累加把计数修对，代价是 97.9、25.8、0.8 ms；条件变量必须配 `while`；信号量用计数表达空位，顺序写反就 `exit=124`；线程池把创建成本移出热路径；`epoll` 把「每条连接一个执行流」换成「一个线程照看全部 fd」。

第二段 1.12.8–1.12.11 解决「用对」：200 个 joinable 线程退出后 `/proc` 只剩 1 项，`VmSize` 却还挂着约 1.58 GiB，8 MiB 是虚拟栈；`volatile` 不是原子；`relaxed` 只保证单个对象不被撕裂，发布数据要 `release` 配 `acquire`；无竞争加锁根本不进内核，200 万次加解锁只有 524 次 `futex`；读写锁、seqlock、RCU 各自让一方付代价。

第三段 1.12.12–1.12.16 解决「取证与收口」：死锁用进度图与 `strace` 的 futex 地址闭合取证线索；线程池按 `L = λW` 定容量、在阻塞/拒绝/调用者执行中选背压、按「停收 → 排空 → join」关闭；C11 与 C++20 的计数程序在本机编译运行通过，Rust 因无 `rustc` 未实测；TSan 要 `setarch -R`，helgrind 不用重编译，perf 被 `perf_event_paranoid=4` 挡住；最后九条陷阱按竞争、死锁、生命周期分组。

逐条打勾的达标表在[学习目标自检表](ch12-checklist.md)，正文不再保留达标打勾表；卡住时按表里的「依据」列回到对应小节。这里只留三条判据：

- **能说清谁共享、谁排序**：看到共享写，先问两次访问之间有没有锁、原子或条件变量建立 happens-before；答不上来就是竞争。
- **能算容量、能写关闭**：用 `L = λW` 估并发，用压测定 worker；队列满时选一种背压；关闭先停收再排空，worker 退出要 `shutdown && count == 0`。
- **能取证**：TSan 看两次访问与栈，helgrind 看锁与锁序，`ps -L` 看核与切换，`strace -c -e futex` 看等待；perf 不可用时说得出被什么挡住。

如果只记住一件事：**并发 bug 不是「运气问题」，而是共享状态缺少一条可指出的顺序；先找那条顺序，再谈修法。**

::: method 即时自测 · 1.12
**Q1（综合）** 4 个线程各 `counter++` 100 万次，`-O0` 实测 2,016,895。写出三种修法，并说出各自在本机的量级。

**Q2（辨析）** 条件变量等待写成 `if (!ready) pthread_cond_wait(...)`，为什么会出现 `items=-1`？`while` 多检查了什么？

**Q3（应用）** 每秒 2 万请求、池内平均 5 ms，worker 开多少？队列满时面向用户与离线任务各怎么选？关闭时两个判断的顺序是什么？

**Q4（取证）** 线上二进制不能重编译，怀疑数据竞争与锁序；本机 `perf` 不可用。给出工具顺序与每条命令能证明什么。

::: sol 答案
**A1** 互斥锁：约 97.9 ms；原子 `atomic_fetch_add_explicit(..., relaxed)`：约 25.8 ms；每线程局部累加、最后合并：约 0.8 ms。三者都能得到 400 万，代价差两个数量级。

**A2** `pthread_cond_wait` 可能虚假唤醒，也可能醒来后条件又被别的线程改回假；`if` 只判一次就直接进临界区，于是读到不满足条件的 `items`。`while` 让每次醒来都重查谓词，条件仍假就继续睡。

**A3** `L = 20000 × 0.005 = 100` 个并发；面向用户选立即拒绝（503），离线任务选阻塞提交；关闭先 `shutdown = 1` 并广播，worker 先看 `shutdown`、再看 `count == 0`，两者同时成立才退出，最后 join。

**A4** 先用 helgrind（不重编译，报 `Possible data race`、`Locks held` 与锁序），再用 TSan 重编译复现（`-O1 -g -fsanitize=thread`，本机加 `setarch -R`）；两者都不保证覆盖未执行路径。perf 被 `perf_event_paranoid=4` 挡住，`perf c2c` 报 `no PMU supports the memory events`，改用 `ps -L`、`strace -c -e futex` 与墙钟。
