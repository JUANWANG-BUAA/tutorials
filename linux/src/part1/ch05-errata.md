# 1.5 勘误与版本注记

这一页收本章最容易「记成永久真理」的版本敏感事实。正文里的 `errata` 盒讲的是理解陷阱（比如「`-O3` 一定更快」）；这一页讲的是**换编译器、换架构、换工具之后要复核什么**，以及本章哪些数字属于哪台机器。

**本章基线**：1.5.12 与 1.5.13 的实测在 Apple M1、arm64、clang 15、`-O2`、未加 `-march=native` 上取得；1.5.1 与 1.5.10 的延迟/吞吐表是 Skylake 级别的量级；`perf`、`cpupower`、`taskset`、`lscpu` 属于 Linux，按[实验环境](../env.md) 的 Ubuntu 24.04 虚拟机准备。本套书当前的写作机是 arm64、Apple clang 21，`perf` 与 `valgrind` 都不在这台机器上。换环境时逐条复核。

## 1. 编译器与优化开关

| # | 看起来像 | 实际是 | 怎么验证 |
|--:|:--|:--|:--|
| 1 | `-O3` 一定比 `-O2` 快 | 更多向量化与展开会增体积、压 I-cache，部分负载更慢 | 同一程序两级别各测 CPE |
| 2 | 自动向量化属于哪个 `-O` 级别是固定的 | 各编译器与版本策略不同；正文按 `-O3`/`-ftree-vectorize` 口径 | Clang 用 `-Rpass=loop-vectorize`，GCC 用 `-fopt-info-vec` |
| 3 | `inline` 一定展开 | 只是建议；递归、取地址、过大的函数通常不展开 | `objdump` 或 `-S` 里找有没有 `call` |
| 4 | `restrict` 是优化提示 | 是承诺；违反是未定义行为，结果可以在任何输入上都错 | 加与不加各出一份汇编，看重叠检查 |
| 5 | `volatile` 能让代码更快或更安全 | 只保证访问真的发生，不提供原子性也不提供屏障，通常更慢 | 对比汇编里的 load/store 次数 |
| 6 | 编译器会自动把 `a*a*a*a` 折成 `(a*a)*(a*a)` | 浮点下改变结合顺序就改变结果，不授权就不做 | `-S` 数乘法指令；看是否开了 `-ffast-math` |
| 7 | `-fno-strict-aliasing` 是免费的保险 | 关掉一整类优化，热循环可能明显变慢 | 两版本分别计时；正解是改用 `memcpy` |
| 8 | `-ffast-math` 只是「快一点」 | 它同时改变浮点语义（NaN/Inf、有符号零、重排），金额与可复现计算禁用 | 跑一遍校验和对比，看末位 |
| 9 | Rust 的 `-O` 等价于 C 的 `-O2` | 默认目标 CPU 保守、展开策略不同；正文的 Rust 版本需要 `target-cpu=native` 才追近 | 两种选项各跑一次同一程序 |

## 2. perf 与 PMU 事件

| # | 看起来像 | 实际是 | 怎么验证 |
|--:|:--|:--|:--|
| 10 | `perf stat -d` 在任何 Linux 上都给同一组字段 | 字段与事件名依 CPU、内核与 perf 版本；缺失项常显示 not counted 或 not supported | 先 `perf list`，再决定读哪几个 |
| 11 | `L1-dcache-load-misses`、`LLC-load-misses` 是通用事件名 | 这是 Intel/AMD 的叫法，ARM64 平台的名字不同；虚拟机与云 vCPU 可能不暴露 PMU，计数全 0 | 换 `perf stat -d` 通用字段，或改跑 cachegrind |
| 12 | `stalled-cycles-frontend/backend` 总有数 | 不少平台不实现，读出来是 0；0 不等于「没有停顿」 | 与 IPC、`perf annotate` 交叉判断 |
| 13 | `ld_blocks.store_forward` 能数所有机器的写读阻塞 | 属特定微架构事件；正文已标注未实测 | `perf list` 里搜 store，找不到就退回 A/B 计时 |
| 14 | `perf c2c` 随时能查 false sharing | 需要硬件对缓存行（一次搬进缓存的那一整块）访问与嗅探的支持，虚拟机里常常没有 | 内核与 perf 版本、`perf list` 确认 |
| 15 | 容器里也能 `perf stat` | `perf_event_paranoid` 偏紧时报 Permission denied；可调低或改 `--all-user`，或在宿主机跑 | `cat /proc/sys/kernel/perf_event_paranoid` |
| 16 | 正文那两段 perf 输出就是你机器会给出的读数 | 1.5.9 与 1.5.14 的代码块是**示例形态**，用来说明怎么读字段，不是本书环境的实测 | 自己跑一次，只比自己与自己的差 |

## 3. Valgrind 与 cachegrind

| # | 看起来像 | 实际是 | 怎么验证 |
|--:|:--|:--|:--|
| 17 | 每台机器都装了 valgrind | 本套书写作机上没有（`command -v valgrind` 为空）；Linux 发行版要自行安装 | `valgrind --version` |
| 18 | cachegrind 的 miss 数能当真 | 它模拟简化缓存（默认 32 KB L1、64 字节行），不建硬件预取、乱序与多核共享 | 只做同一程序两个版本的相对比较 |
| 19 | cachegrind 的缓存配置等于目标机 | 可以用 `--I1`/`--D1`/`--L2` 显式指定，但要先从目标机文档拿到真实参数 | 指定后再与 `perf` 的缺失数对照 |
| 20 | Apple Silicon 的 macOS 上能跑 valgrind | 对新系统与 arm64 的支持长期滞后，装不上或跑不起来属预期 | 把这类实验移到 Ubuntu 虚拟机里做 |
| 21 | cachegrind 跑得快 | 慢 20–50 倍；$n=512$ 的矩阵乘要先把规模调小 | 先用 $n=128$ 或更小验证流程 |

## 4. ARM64 与 x86-64 的差异

| # | 看起来像 | 实际是 | 怎么验证 |
|--:|:--|:--|:--|
| 22 | 正文 1.5.11 的汇编片段在哪都能照读 | 那是 x86-64 形态（`subq`/`cmpq`/`setb`/`je`、`movupd`/`addpd`）；ARM64 是 `sub`/`cmp`/`b.lo`、`ldp`/`stp`，结构相同、助记符不同 | 在目标机 `-O2 -fno-inline -S` 对比两版 |
| 23 | 延迟/吞吐表在 ARM64 上同样成立 | 表中数字是 Skylake 量级；ARM64 各微架构不同，正文只借用「延迟定链、吞吐定并行」这个关系 | 用目标机的手册或自己的微基准换数 |
| 24 | 缓存行都是 64 字节 | 主流是 64 字节，但估块大小时还要看该层是否共享；Apple Silicon 上 `sysctl` 报的层级口径与 `lscpu` 的组织不同，两者不能混用（本书未逐条核实） | 在目标机读缓存拓扑后再定块 |
| 25 | 分块一定比循环交换更值钱 | 正文实测里那台 L2 很大的机器上，`block64` 与 `block4` 都没赢过 `ikj`；LLC 较小或多核共享 LLC 的 x86 服务器才通常明显 | 换机器重跑同一程序看关系是否翻转 |
| 26 | `_mm_stream_si128`/`movntdq` 可移植 | 属 x86 intrinsic；ARM64 上的非临时写要另找写法，本书未实测 | 查目标编译器是否提供对应内建 |
| 27 | `taskset`、`cpupower`、`lscpu` 到处都有 | 是 Linux 工具，macOS 上没有等价命令；绑核与定频做不了时，计时结论只能当相对参考 | 在 Linux 虚拟机里做基准类实验 |

## 本章未实测项

下面这些结论，本章没有在自己的机器上跑出读数来支撑。用之前先当作**待验证的判据**，别抄成事实：

- **perf 全部读数**：本书写作环境没有 `perf`（macOS），1.5.9、1.5.14 的输出是示例形态；`perf stat -d`、`perf annotate`、`perf c2c`、`ld_blocks.store_forward` 均未实测。
- **cachegrind 读数**：`valgrind` 未安装、未跑；1.5.15 的字段名来自该工具的通用输出格式，未在本机核对。
- **x86-64 Linux 上的四个矩阵乘内核对比**：正文数值只在 arm64/macOS 取得，未在 x86-64 复测；「分块在 x86 服务器上通常明显胜出」是机制推论。
- **「`-O3` 反而更慢」与「关掉向量化后 `block4` 才领先」**：正文给出的是判据与预期，未复测。
- **「M1 的 L2 有 12 MB」这个容量口径**：正文用它解释分块没赢；容量与共享方式请按你查到的资料复核，本书未复核。
- **计时方差**：正文两个程序的计时是单次读数，没有重复次数与置信区间；多次运行的波动未量化。
- **较新写作机上的重跑**：1.5.12 与 1.5.13 的程序在当前机器（Apple clang 21）编译运行过，命令可用、关系不变（`ikj` 仍远快于 `ijk`，`restrict` 版仍快于 `plain`），但绝对数值属于另一台机器与另一版编译器，本书不把它写成新的实测数字。

## 发现新问题怎么记

按「现象 → 命令与输出 → 编译器/内核/CPU 版本 → 建议改法」四段记，不要只写「我这里不对」。能附上两样东西最好：一条能复现的命令（含完整的编译选项），以及一段真实输出（截取关键行即可，别贴整屏）。如果你发现的是**数字口径**问题——例如正文的某个倍数在你的机器上不成立——请同时写清你测的是 CPE、GFLOP/s 还是墙钟时间，以及有没有绑核与定频；本章的多数分歧都出在这三项没对齐。这张表按同一格式继续增补。
