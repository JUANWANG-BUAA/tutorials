# 1.19 习题集

三组分层：**A 组概念判断**考「会读、会说理由、会画因果」；**B 组诊断推理**给现象让你判阶段、判结构、判修法；**C 组动手实验**把构建、QEMU、GDB 与镜像检查拆开，**全部需 RISC-V 硬件/QEMU，本机未实测**。每题的第一个动作都是「先猜」：把预期写下来，再去验证；猜错的地方才是这题的价值。

## 怎么用

1. 先读题，不看解答，给自己 2–3 分钟找思路；A 组要求口述或写一段完整因果，B 组要求写成「现象 → 原因 → 修法 → 证据」四段。
2. 卡住了回对应小节的「即时自测」重读，不要直接看答案；A 组对应 1.19.1–1.19.5，B 组对应 1.19.2–1.19.9，C 组对应 1.19.2–1.19.10。
3. C 组全部**未实测**：本机没有 RISC-V 硬件与 QEMU/GDB 运行链路，rCore 只读源码对照；写作机最多做交叉汇编，不能链接、不能运行。答案只给「命令形状 + 判据 + 应看到的形状」，不抄会话记录。
4. 凡是需要串口输出、寄存器值、断点命中、文件系统镜像字节的，答案只给判据；不要把正文的「预期输出」当成自己的实测结果。
5. 做错的题记一个记号，三天后只重做记号题，并去[自检表](ch19-checklist.md)勾对应行。

## A 组 · 概念判断

::: ex 例 1.19-A1 · 八个阶段能不能省 · {#ex-1.19-A1}

先猜：如果没有时钟中断，多任务阶段还能成立吗？如果没有页表，进程阶段还能成立吗？哪个阶段是「隔离」的真正起点？

按「应用需求 → 硬件机制 → 内核抽象 → 典型失败」四列，复述八个阶段；指出阶段 2、3、4、5 各自新增的那一件关键硬件机制；说明为什么「进程」必须排在「地址空间」之后。

::: sol 解答

八阶段与关键机制：① 裸机（SBI/UART/CLINT；入口、栈、trap 向量；链接地址错）；② 批处理（U/S 特权级 + `ecall`；加载器、系统调用；`sepc` 未 `+4`）；③ 多任务（内核栈 + `sscratch`；任务、调度器、`yield`；切换时栈没换）；④ 抢占（时钟中断 + `STIE`；时间片、tick；忘了重设 `mtimecmp`）；⑤ 地址空间（Sv39 + `satp` + TLB；页表、`MapArea`、`MemorySet`；PTE 权限错）；⑥ 进程（页表切换 + COW；PCB、pid、父子关系；`Arc` 循环）；⑦ 文件系统（块设备 + virtio；inode、目录项、fd 表；块号错）；⑧ IPC/并发（IPI + 原子指令；pipe、signal、线程、锁；竞态）。没有时钟中断，阶段 3 仍可成立，但只是协作式：任务必须主动 `yield`，一个死循环就卡死系统；阶段 4 才把「让出」变成「必须让出」。没有页表，阶段 6 也可以有「任务」和 fork，但父子共享同一物理地址空间，写时互相覆盖，谈不上隔离；所以「进程」排在「地址空间」之后，因为 fork 的 COW、exec 的换地址空间、wait 的回收都建立在「每个进程有独立 `MemorySet`」上。隔离的真正起点是阶段 2 的 U/S 特权级（应用不能执行特权指令），阶段 5 把隔离从「权限」扩展到「地址」。

**判据**：四列齐全；阶段 3/4 的区别说成「协作 vs 抢占」；阶段 5 的关键机制是 Sv39 + `satp`；能说出「没有页表也能 fork，但没有隔离」。

:::

::: ex 例 1.19-A2 · 加载器六步与用户栈 · {#ex-1.19-A2}

先猜：六步中最容易漏的是哪一步？如果应用第一条指令就是 `addi sp, sp, -16`，会发生什么？`sstatus.SPP=0` 与 `SPIE=1` 各起什么作用？

写出批处理加载器的六步；说明 `sscratch` 与用户栈各自解决什么问题；解释 `sret` 到 U 后 `sp` 的归属；指出 1.19.2 的示例为什么没暴露用户栈问题。

::: sol 解答

六步：① `copy_nonoverlapping(src, APP_BASE, len)` 把应用放到 `0x8040_0000`；② `csrw stvec, trap_entry` 装 U→S 入口；③ `csrw sscratch, sp` 保存内核栈顶；④ 设 `sstatus.SPP=0`（返回 U）、`SPIE=1`（`sret` 后开中断）、`SIE=0`；⑤ `csrw sepc, APP_BASE`；⑥ `sret`。`sscratch` 解决「trap 时从哪里换回内核栈」；用户栈解决「U 态代码在哪里压栈」。`sret` 只改 PC、特权级与中断使能，不会换 `sp`；如果 `sret` 前不把 `sp` 换成用户栈，U 态仍拿着内核栈指针，应用一压栈就改内核数据。1.19.2 的示例应用只有 `addi a7, zero, 2; ecall`，完全不使用栈，所以「`sp` 还是内核栈」这个问题没有暴露；不能因此认为示例已经处理好用户栈。`SPP=0` 决定回 U，`SPIE=1` 决定 `sret` 后把 `SIE` 置 1（开中断）。

**判据**：六步顺序正确；`sscratch` 与用户栈不混；知道 `sret` 不换 `sp`；能指出示例应用不使用栈是「侥幸」。

:::
:::

::: ex 例 1.19-A3 · 为什么只存 14 个 `usize` · {#ex-1.19-A3}

先猜：`__switch` 保存 `ra` 而不是 `sepc`，是因为两者等价吗？`a0–a7` 真的「不用保存」吗？`ret` 之后 CPU 在哪个任务的内核栈上？

写出 `TaskContext` 的字段与偏移；说明 caller-saved 与 callee-saved 的分工；解释 `__switch` 的 `ret` 返回到哪里；指出「保存了 caller-saved」为什么不一定是错误、但通常多余。

::: sol 解答

`TaskContext`：`ra`（0）、`sp`（8）、`s0–s11`（16–104），共 14 个 `usize`。`__switch` 是一次普通函数调用：调用者（编译器生成的代码）已经把 caller-saved（`ra`、`t0–t6`、`a0–a7`）中需要保留的值保存在**当前任务的内核栈**上；`__switch` 只负责「换栈之后仍然要恢复」的 callee-saved（`s0–s11`）以及决定去留的 `ra`、`sp`。`ra` 与 `sepc` 不等价：`ra` 是函数调用返回地址，`sepc` 是 trap 返回地址；任务切换发生在内核里的函数调用，不是 trap 返回，所以存 `ra` 就够了。`a0–a7` 不是「不用保存」，而是「由调用者在自己的栈上保存」；换栈后旧栈还在，等任务再次被调度时，`__switch` 的 `ret` 回到调用点，调用者再从自己的栈恢复它们。`ret` 跳到 `next` 上次调用 `__switch` 的下一条指令，此时 `sp` 已经是 `next` 的内核栈——看起来像「从没切换过」，实际在另一个栈上。保存 caller-saved 不一定错，但会破坏「`__switch` 只遵守 callee-saved 约定」的简洁性，也可能覆盖编译器已经安排好的槽位。

**判据**：14 个字段与偏移正确；`ra` 与 `sepc` 的区别说清；知道 caller-saved 由调用者保存；`ret` 的去向与 `sp` 的归属说对。

:::
:::

::: ex 例 1.19-A4 · 手算 Sv39 与 `satp` · {#ex-1.19-A4}

先猜：VA `0x0000_0040_0800_1000` 的 `VPN[2]` 是 256 还是 512？页内偏移是 `0x1000` 还是 0？根页表在 `0x8030_0000` 时，`satp` 的低 44 位是多少？

写出 Sv39 的四段拆分；算出该 VA 的 `VPN[2]/VPN[1]/VPN[0]` 与 offset；写出 `satp`；判断 PTE `0x2000_0407` 与 `0x2000_0403` 哪个是合法叶子、哪个是保留组合；说明改完 `satp` 后为什么要 `sfence.vma`。

::: sol 解答

拆分：`VPN[2]=(VA>>30)&0x1ff`、`VPN[1]=(VA>>21)&0x1ff`、`VPN[0]=(VA>>12)&0x1ff`、offset=`VA&0xfff`。对 `0x0000_0040_0800_1000`：`VPN[2]=256`（bit 38）、`VPN[1]=64`（bit 27）、`VPN[0]=1`（bit 12）、offset=0。`satp = (8 << 60) | (0x8030_0000 >> 12) = 0x8000_0000_0000_0000 | 0x80300`。PTE `0x2000_0407` 低位 `0x407 = V|R|W`（`0x1|0x2|0x4`），`R=1`，是合法叶子，权限为读写；PTE `0x2000_0403` 低位 `0x403 = V|R`，也是合法叶子（只读），不是保留组合。保留组合是 `W=1` 且 `R=0`，例如低三位 `0x5`（`V|W`）。改 `satp` 后必须 `sfence.vma`，否则旧 TLB 项仍然有效，用户可能访问到已撤销的映射；多 hart 时还要考虑核间 TLB shootdown。

**判据**：四个字段算对；`satp` 的 MODE 与 PPN 不混；能按 `R/W/X/V` 判叶子；知道 `W=1,R=0` 是保留；`sfence.vma` 的理由说对。

:::
:::

## B 组 · 诊断推理

::: ex 例 1.19-B1 · 应用打印一次后原地死循环 · {#ex-1.19-B1}

先猜：是 `scause` 判断错了，还是 `sepc` 没前进？`ecall` 的 `sepc` 指向 `ecall` 本身还是下一条？中断能不能照做？

现象：批处理内核加载应用，应用 `ecall` 进 S，打印 `batch: app exit` 后 `sret`，又回到同一条 `ecall`，无限重复。给出原因、修法，并说明为什么中断不能 `sepc += 4`。

::: sol 解答

原因：`ecall` 触发 trap 时，硬件把 `sepc` 写成 `ecall` 指令本身的地址；handler 处理完不修改 `sepc`，`sret` 就回到同一条 `ecall`，再次陷入。修法：系统调用返回前执行 `tf.sepc += 4`（或 `csrw sepc, sepc+4`）。中断不同：中断的 `sepc` 指向被打断的那条指令，返回时要重新执行它；加 4 会跳过一条无辜指令，行为变得随机。验证：在 handler 里打印 `tf.sepc` 与 `ecall` 的符号地址比对；或 GDB 单步看 `sret` 后 PC 是否回到同一地址。本题的运行验证需 RISC-V 硬件/QEMU，本机未实测。

**判据**：指出 `sepc` 指向 `ecall` 本身；修法精确到 `+4`；能对比中断情形；给出 `sepc` 证据；如实标注未实测。

:::
:::

::: ex 例 1.19-B2 · 第一次 `__switch` 后系统跑飞 · {#ex-1.19-B2}

先猜：两个任务共用一个内核栈，最先坏的是返回地址还是 `s0`？「保存了 caller-saved」会导致立刻崩溃吗？

现象：任务 A 调用 `__switch(&a.ctx, &b.ctx)` 后，第一次能进 B；B 再切回 A 时 triple fault。检查发现 `TaskContext` 的 14 个字段都存了，但两个任务初始化时用了同一个 `kstack`。给出原因、修法，并说明为什么「保存 14 个字段」本身不够。

::: sol 解答

原因：`TaskContext` 里保存了 `sp`，但两个任务的内核栈是同一块内存；第一次切换后 B 在自己的「栈」上运行，实际上覆盖了 A 的栈内容。B 再切回 A 时，`ld sp, 8(a1)` 恢复的仍是同一块栈，`ret` 从被覆盖的返回地址跳走，最终 triple fault。修法：每个任务创建时分配独立内核栈，`TaskContext.sp` 指向各自栈顶；初始化时在栈上摆好「第一次 `__switch` 返回后要执行的入口」，并保证 `ra` 指向一个合法的任务入口 trampoline。保存 14 个字段只保证「寄存器值」被保存，不保证「栈」是独立的；`sp` 字段的值如果相同，切换等于没换栈。另一个常见错误是保存了 caller-saved：它通常不会立刻崩溃，但会破坏编译器对 `__switch` 的假设，属于「多余且危险」。本题需 RISC-V 硬件/QEMU，本机未实测。

**判据**：定位到「共用内核栈」而不是「字段少存」；修法包含独立 `kstack` 与首次入口；能区分「保存字段」与「保存栈」；知道保存 caller-saved 是多余而非立即致命。

:::
:::

::: ex 例 1.19-B3 · 大页翻译错位，撤销映射后还能访问 · {#ex-1.19-B3}

先猜：2 MiB 大页的 `mask` 应该是 `0x1f_ffff` 还是 `0xfff`？`satp` 改了但 TLB 没刷，会立刻 fault 还是继续用旧映射？

现象 A：映射 2 MiB 大页 `VA 0x4000_0000 -> PA 0x8000_0000`，访问 `0x4012_3456` 得到的物理地址不是 `0x8012_3456`。现象 B：`unmap` 一页并改了页表，用户仍然能读写该地址。分别给出原因与修法。

::: sol 解答

A：大页翻译要保留该级的偏移。level 1 覆盖 21 位，`mask = (1 << 21) - 1 = 0x1f_ffff`；如果写成固定的 `0xfff`，`0x4012_3456` 只剩低 12 位 `0x456`，物理地址变成 `0x8000_0456`，高位偏移全丢。修法：按级别算 `mask = (1 << (12 + 9 * level)) - 1`；映射时还要求 PA 按页大小对齐（2 MiB 页的 PA 低 21 位为 0）。B：改页表后没有 `sfence.vma`，旧 TLB 项仍然有效；CPU 可能继续用旧映射，直到 TLB 被替换。修法：改 `satp` 或改 PTE 后执行 `sfence.vma`（可带 VA/ASID）；多 hart 时还需 IPI 让其他核也刷。验证：在 `unmap` 后立刻访问，并用 GDB 看 `satp` 与 PTE；若 PTE 已清但访问仍成功，就是 TLB。本题需 RISC-V 硬件/QEMU，本机未实测。

**判据**：A 定位到 `mask` 位数；B 定位到 TLB 未刷新；修法包含按级 `mask` 与 `sfence.vma`；知道 2 MiB 页要求 PA 对齐；能区分「页表错」与「TLB 旧」。

:::
:::

::: ex 例 1.19-B4 · fork 的 offset、exec 的半死、wait 的丢唤醒 · {#ex-1.19-B4}

先猜：fork 后子进程 `read` 10 字节，父进程的 offset 应不应该前进？exec 解析新 ELF 失败时，旧地址空间应该保留还是释放？wait 在锁外检查条件，最坏会怎样？

现象 A：fork 后子进程读文件，父进程的下一次 `read` 从新位置开始，同学认为「内核有 bug」。现象 B：`exec` 先释放旧 `MemorySet` 再解析新 ELF，解析失败后进程崩溃。现象 C：父进程 `wait` 偶尔永久睡眠。分别给出原因与修法。

::: sol 解答

A：不是 bug，是 POSIX 语义。fork 复制 fd 表，但 `Arc<dyn File>` 的克隆让父子共享同一个打开文件与 file offset；子进程读 10 字节，父进程的 offset 也前进 10。Linux 用 `struct file` 的引用计数实现同一件事。若希望独立 offset，应 `dup` 后重新 `open` 或用 `pread`。B：`exec` 必须先解析 ELF、建好新页表，全部成功后才原子替换 `MemorySet`；先释放旧的，解析失败时进程没有地址空间，只能被杀。修法：`let mut new_set = MemorySet::from_elf(&elf)?;` 成功后再 `p.memory_set = new_set;`，旧 `MemorySet` 在赋值后 `Drop`。C：`wait` 在锁外检查「子进程是否已退出」，检查完到睡眠之间子进程退出并唤醒，父进程错过唤醒后永久睡眠。修法：检查条件与进入等待必须在同一把锁内，醒来后重新检查（防虚假唤醒）；用 `Condvar`/`WaitQueue` 时遵守「持锁检查、循环等待」。本题的运行验证需 RISC-V 硬件/QEMU，本机未实测。

**判据**：A 说成 POSIX 共享 offset 而非 bug；B 修法指向「先建后换」；C 定位到丢失唤醒；三题都能给出对应结构（`Arc<dyn File>`、`MemorySet`、`Condvar`）。

:::

::: ex 例 1.19-C2 · 用 GDB 看一次 `__switch` · {#ex-1.19-C2}

先猜：在 `__switch` 断点命中时，`a0`/`a1` 指向什么？单步到 `ret` 后 `sp` 属于哪个任务？`ra` 与 `sepc` 哪个会变？

在 QEMU `-s -S` 下启动两个任务的内核，GDB 在 `__switch` 下断点，记录 `a0`、`a1`、`sp`、`ra`；单步执行 `sd`/`ld` 序列，观察 `sp` 在 `ld sp, 8(a1)` 后跳到另一个内核栈；再 `ret`，确认 PC 落在 `next` 上次调用 `__switch` 的下一条指令。说明如何用证据区分「切换成功」与「只是函数返回」。

::: sol 解答

`a0` 指向 `prev` 的 `TaskContext`，`a1` 指向 `next` 的；断点命中时 `sp` 还在 `prev` 的内核栈。执行 `ld sp, 8(a1)` 后，`sp` 变为 `next` 的栈顶；`ret` 从 `next` 的 `ra` 取地址，落到 `next` 上次调用 `__switch` 的下一条指令。`ra` 会被 `ld ra, 0(a1)` 改写；`sepc` 不变，因为这是函数调用/返回，不是 trap。区分「切换成功」与「普通返回」的证据：① `sp` 的值落在不同任务的 `kstack` 范围；② `a0`/`a1` 指向不同的 `TaskContext`；③ GDB 的 `bt` 显示调用链属于另一个任务；④ 两个任务的 `TaskContext` 在内存中互相保存对方的 `ra/sp`。**未实测 + 原因**：本机没有 QEMU/GDB 运行链路，`gdb-multiarch` 不在实验环境；以上寄存器变化是 ABI 推演，不是会话记录。

**判据**：`a0/a1` 的方向不写反；`sp` 在 `ld` 后换栈；`ra` 变、`sepc` 不变；能给出三条以上「不是普通返回」的证据；标注未实测。

::: ex 例 1.19-C3 · 把 `myfs` 镜像接到 virtio-blk · {#ex-1.19-C3}

先猜：8 块镜像一共多少字节？根目录项在第几块？如果内核没有块设备驱动，`mount` 会先报什么错？

在主机上生成 `myfs.img`（8 × 512 字节），用 `hexdump -C` 核对超级块 `magic`、inode 0/1 与目录项；再把镜像作为一个 virtio-mmio 块设备接入 QEMU `virt`，在内核里用 `BlockDevice::read_block` 读块 0、块 4、块 5，确认能列出 `.`、`hello.txt` 并读出 `hello, myfs!`。说明为什么「主机上 `rustc myfs.rs` 能跑」不等于「内核里能挂载」。

::: sol 解答

8 × 512 = 4096 字节。块 0 超级块，块 1/2 位图，块 3 起 inode 区，块 4 根目录项（`.` 与 `hello.txt`），块 5 `hello.txt` 内容（13 字节），块 6–7 未用。`hexdump -C` 应看到偏移 0 的 `MAGIC=0x4d59_4653`（小端字节 `53 46 59 4d`）、偏移 `3*512` 的 inode 0/1、偏移 `4*512` 的两个 32 字节目录项。接入 QEMU 需要 virtio-mmio 设备与内核侧队列/中断驱动；若没有块设备驱动，`BlockDevice::read_block` 无处实现，`mount` 会在「找设备」或「读超级块」阶段失败，而不是文件系统布局错。主机程序只证明「字节布局与解析逻辑自洽」；内核里还要有设备发现、DMA、中断、块缓存与 `File` trait 接线。**未实测 + 原因**：本机没有 QEMU/virtio 运行链路，也没有本章 `myfs` 的内核侧驱动；`rustc myfs.rs` 的主机输出本套件也未复跑。

**判据**：4096 字节与块号算对；`hexdump` 能指出 `magic` 与目录项偏移；知道「主机解析」与「内核挂载」差设备驱动；标注未实测。
