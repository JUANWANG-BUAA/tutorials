# 全书知识地图：六篇一条主线，三条走法

> 这一页回答两个问题：这本书六篇为什么按这个顺序排？你该从哪一篇进、哪些可以后补？读每章前先看这里的「入口/出口」，再决定要不要按顺序读。

## 1. 一条主线

从你敲下的一条命令出发：

1. **第 0 篇**先让你看清「命令 → Shell → 系统调用 → 内核」这条路径，知道哪一层该为哪类问题负责。
2. **第 1 篇**补上程序在机器上如何运行的底座：数据怎么表示、指令怎么执行、缓存/链接/虚拟内存/并发是什么。
3. **第 2 篇**把底座变成手艺：用 `open/read/write/fork/exec/socket` 写出正确、可移植、可观测的系统程序。
4. **第 3 篇**进入内核，看这些系统调用在调度器、内存管理、VFS、块层里怎么实现。
5. **第 4 篇**把视角拉到网络：一次 HTTP 请求如何经过 socket、TCP、IP、网卡，以及怎么用证据定位超时。
6. **第 5 篇**把服务装进容器与集群：namespace、cgroups、overlayfs、OCI 与 Kubernetes 原语。
7. **第 6 篇**用 11 个项目把前六篇压成工程能力；项目不是附录，是验收。

一句话：**先会用（0），再懂程序（1），再写系统程序（2），再看内核（3），再看网络（4），最后上云（5），用项目收口（6）。**

两条边要特别注意：

- **第 1 篇与第 2 篇不是严格先后**。只读 1.1–1.3（程序生命周期、数据表示、汇编）就可以开始第 2 篇；1.4–1.19 可以在需要时回补。非科班读者不要因为第 1 篇厚就停在门口。
- **第 3 篇依赖第 2 篇的接口经验**。没写过 `fork`、`mmap`、`epoll` 就读调度器和 VFS，只能背名词；第 2 篇至少读到 2.13、2.18。

## 5. 每章怎么标主线

从 2026-10-29 起，每章的「章总览」必须增加两行：

```markdown
## 路线标签

- 应用/运维：必读 / 可后补 / 可跳过
- 系统编程：必读 / 可后补 / 可跳过
- 内核/性能：必读 / 可后补 / 可跳过
- 项目回链：项目 A2（`myhttpd`）的日志与连接管理；项目 D1（`mysh`）的重定向与管道
```

这样读者不必每次翻回本页，就知道这一章在自己的路线里值多少时间。

## 6. 书级主线审计（2026-10-29 首轮）

**结论：六篇的顺序成立，但默认读法不成立。** 现在的 SUMMARY 是线性六篇，index 和 roadmap 却给了三条路线；第一次来的读者会默认从第 1 篇硬读，而第 1 篇 19 章、包含多架构/Rust/RISC-V/rCore，是非科班读者最大的劝退点。

本轮不改章节顺序，先做三件事：

1. 新增本页，把「一条主线 + 三条走法 + 每篇入口/出口」放在卷首。
2. 每章总览增加「路线标签 + 项目回链」，让读者知道这一章在路线里的位置。
3. 在 index 与 roadmap 的显眼位置链接本页；index 的默认推荐改为「路线 A 起步，路线 B/C 按目标选读」。

下一轮再评估两个结构问题：

- **第 1 篇内部的分岔已经标出，不再拆目录**：1A 程序底座（1.1–1.13）是公共前置，1B 多架构与实现（1.14–1.19）是项目/内核方向选修。判据与最小集写在[第 1 篇导览](part1/overview.md)的「分岔点」一节；非科班读者读完 1.1–1.3 就可以去第 2 篇动手，不必先啃完 19 章。
- **第 2 篇与第 3 篇是否要交错**：例如 2.1–2.4 → 3.7–3.9（内存）→ 2.5–2.13 → 3.4–3.6（进程/调度）。交错能更早看到内核，但会破坏现有的「先接口后实现」主线；需要先用试点章验证。
