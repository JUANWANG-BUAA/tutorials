上一章讲「能不能打开文件」，这一章讲「打开之后接到哪里」。Shell 的重定向与管道不是语法糖，而是对进程文件描述符表的精确操作。求值顺序、fd 复制、子 Shell，三件事决定了你看到的输出到底流向哪里。

很多人写脚本时靠试错来排重定向：加一个 `2>&1`，不行再换个位置。这样能碰对，但遇到「日志里少了错误行」「退出码永远是 0」「变量在循环后丢了」时，就找不到原因。把 fd 表画出来，这些现象都能一步步推出来。

本章的结论以 bash 5.2（Ubuntu 24.04）为准。POSIX sh 的语法子集更小，`&>`、`<<<`、`<()` 都是 bash 扩展；写可移植脚本时要按 POSIX 写法。

## 0.5.1 三个 fd 与文件描述符表 {#sec-0.5.1}

这一节回答：你敲下 `echo hi > out.txt` 时，Shell 到底改了进程里的哪一格？

::: preview 先抓住一件事
文件描述符（file descriptor，fd）是进程内一张表的下标。`0`、`1`、`2` 分别接标准输入、标准输出、标准错误；`>file` 只是把下标 `1` 指向另一个“打开的文件”。
:::

先看一条最短的重定向。下面两行会打印 `hi`：

```bash
printf 'hi\n' > /tmp/hello.txt
cat /tmp/hello.txt
```

`printf` 本来把 `hi` 写到屏幕。加上 `> /tmp/hello.txt` 后，同一次写入落进了文件。屏幕没有变，变的是 fd 1 指向的对象。

每个进程启动时，父进程会交给它三个已打开的 fd：

| fd | 名称 | 默认指向 | C 常量 |
|:--|:--|:--|:--|
| 0 | 标准输入（standard input） | 终端或管道读端 | `STDIN_FILENO` |
| 1 | 标准输出（standard output） | 终端或管道写端 | `STDOUT_FILENO` |
| 2 | 标准错误（standard error） | 终端，通常与 1 同一个 tty | `STDERR_FILENO` |

这里的“终端”是一个设备文件，例如 `/dev/pts/0`。屏幕只是这个设备文件在外观上的样子。

::: def 定义 0.5.1 · 文件描述符表 {#def-0.5.1}
每个进程有一张文件描述符表（file descriptor table）。槽位号就是 fd，槽位里存着一个指针，指向内核的“打开文件描述”（open file description）。`open()` 成功时返回编号最小的空闲槽位，通常从 3 开始。
:::

重定向的本质，是让某个槽位改指另一条打开文件描述：

<pre class="layout">
进程的 fd 表                         内核的打开文件描述
┌─────┬──────────────┐
│  0  │ ─────────────┼──→ 终端 /dev/pts/0（读）
├─────┼──────────────┤
│  1  │ ─────────────┼──→ /tmp/out.txt（写，偏移 0）
├─────┼──────────────┤
│  2  │ ─────────────┼──→ 终端 /dev/pts/0（写）
├─────┼──────────────┤
│  3  │ ─────────────┼──→ /tmp/extra.log（写）  ← exec 3>file 的结果
└─────┴──────────────┘
</pre>

读这张图只需记住一句：**fd 是下标，不是文件本身**。两个 fd 可以指向同一条打开文件描述，共享偏移；也可以指向不同文件。`2>&1` 复制的是“fd 1 当前指向谁”，不是数字 1。

**非科班补一层：一次打开，不是一个路径。** 你可能把“文件”理解成磁盘上的那个名字。内核在 `open()` 时还会建一条“打开文件描述”，记录当前偏移、打开标志和引用计数。同一个路径 `open()` 两次，会得到两条记录，各自有偏移；`dup2` 只让两个槽位指向同一条记录。

用 `exec` 可以在当前 Shell 里长期打开一个 fd：

<div class="terminal" data-title="bash · fd 与重定向顺序">
<pre><span class="p">&#36;</span> exec 3&gt;/tmp/fd3.txt
<span class="p">&#36;</span> echo hello &gt;&amp;3
<span class="p">&#36;</span> exec 3&gt;&amp;-
<span class="p">&#36;</span> cat /tmp/fd3.txt
hello
<span class="p">&#36;</span> ls -l /proc/self/fd
total 0
lrwx------ 1 wang wang 64 Oct 17 11:20 0 -&gt; /dev/pts/0
lrwx------ 1 wang wang 64 Oct 17 11:20 1 -&gt; /dev/pts/0
lrwx------ 1 wang wang 64 Oct 17 11:20 2 -&gt; /dev/pts/0
lr-x------ 1 wang wang 64 Oct 17 11:20 3 -&gt; /proc/22531/fd
<span class="p">&#36;</span> bash -c 'echo out; echo err &gt;&amp;2' &gt; /tmp/out.txt 2&gt;&amp;1
<span class="p">&#36;</span> cat /tmp/out.txt
out
err
<span class="p">&#36;</span> bash -c 'echo out; echo err &gt;&amp;2' 2&gt;&amp;1 &gt; /tmp/out.txt
err
<span class="p">&#36;</span> cat /tmp/out.txt
out
</pre>
</div>

`ls` 那一行的 fd 3 是 `ls` 自己打开目录得到的，不是 Shell 的 fd 3；Shell 的 fd 3 在上一行已经关了。

最后两组命令只对调了两个重定向，结果却相反。下一节用 fd 表快照逐条拆。

::: errata 关于 fd 的三个误解
1. **“fd 就是文件”**——fd 只是进程表里的下标；同一个文件可以被打开多次，得到多个不同的 fd。
2. **“`2>&1` 是把 2 改成数字 1”**——它让 fd 2 复制 fd 1 当前的目标；fd 1 以后再变，fd 2 不会跟着变。
3. **“关掉一个 fd，文件就关了”**——只有指向同一条打开文件描述的所有 fd 都关闭，内核才释放这条记录。
:::

### 0.5.1 小结

fd 是进程 fd 表的下标，表项指向一次打开；0/1/2 只是三个约定好的下标。`>file` 做的是“打开目标，把新 fd 复制到 1，再关掉临时 fd”。如果只记住一件事，那就是：**重定向改的是指向关系，不是文件名，也不是数字。**

::: method 即时自测 · 0.5.1
**Q1（记忆）** 0、1、2 分别是什么？它们的 C 常量叫什么？

**Q2（辨析）** 对同一路径 `open()` 两次，和 `dup2` 一次，哪个会让两个 fd 共享偏移？

**Q3（应用）** 先执行 `exec 3>&1`，再执行 `echo hi >&3`，`hi` 会去哪？

::: sol 答案
**A1** 0 是标准输入 `STDIN_FILENO`，1 是标准输出 `STDOUT_FILENO`，2 是标准错误 `STDERR_FILENO`。

**A2** `dup2` 让两个 fd 指向同一条打开文件描述，共享偏移；两次独立 `open()` 得到两条记录，偏移各自独立。

**A3** 去终端。`exec 3>&1` 让 fd 3 复制 fd 1 当时的目标，而 fd 1 当时指向终端。
:::
:::

## 0.5.2 重定向语法与求值顺序 {#sec-0.5.2}

这一节回答：两个重定向只差先后，为什么 stderr 的去向完全相反？

::: preview 先抓住一件事
Shell 按从左到右的顺序执行重定向，每一步都基于当时的 fd 表。`2>&1` 复制的是 fd 1 此刻的目标，不是“1 这个编号”。
:::

先别运行，猜一下两条命令的终端输出：

```bash
bash -c 'echo out; echo err >&2' > /tmp/out.txt 2>&1
bash -c 'echo out; echo err >&2' 2>&1 > /tmp/out.txt
```

第一条运行完，终端没有新行，`/tmp/out.txt` 里是 `out` 和 `err` 两行。第二条终端显示 `err`，文件里只有 `out`。

同一组重定向，为什么结果相反？把 fd 表画成快照就清楚了：

| 步骤 | `>file 2>&1` | `2>&1 >file` |
|:--|:--|:--|
| 初始 | 1→终端，2→终端 | 1→终端，2→终端 |
| 第 1 步 | `open(file)` 得到 3；`dup2(3,1)`：1→文件 | `dup2(1,2)`：2→终端 |
| 第 2 步 | `dup2(1,2)`：2→文件 | `open(file)` 得到 3；`dup2(3,1)`：1→文件 |
| 结果 | 1→文件，2→文件 | 1→文件，2→终端 |

记法只有一条：要让 stderr 跟着 stdout 进文件，`2>&1` 必须放在 `>file` 之后。`&>file` 是 bash 的合并写法，等价于 `>file 2>&1`，但 POSIX shell 不认。

常用语法如下，后面几节会反复用到：

| 写法 | 作用 | 备注 |
|:--|:--|:--|
| `>file` | 截断并写 stdout | 文件不存在则创建；`noclobber` 下拒绝覆盖 |
| `>>file` | 追加 stdout | 原子性取决于单次 `write` 大小 |
| `2>file` | 写 stderr | 只重定向 2 |
| `&>file` | stdout 与 stderr 一起写 | bash 扩展；POSIX 用 `>file 2>&1` |
| `2>&1` | 让 2 指向 1 当前的目标 | 顺序敏感 |
| `1>&2` | 让 1 指向 2 当前的目标 | 常用于把普通输出变成错误 |
| `<file` | 从文件读 stdin | |
| `<<EOF` | here-doc | 见下一节 |
| `<<<"$s"` | here-string | bash 扩展，自动补换行 |
| `<>file` | 读写打开 | 少见 |
| `n>&-` | 关闭 fd n | `exec 3>&-` |
| `\|&` | `2>&1 \|` 的简写 | bash 4+ |

`>file` 默认会截断。想防止误覆盖，用 `set -o noclobber`，此时 `>file` 对已存在文件报错，`>|file` 强制覆盖。脚本里更稳的做法是“写临时文件 + `mv` 原子替换”，见 [0.3](ch03.md)。

`exec` 的重定向会改变当前 Shell 的 fd 表，且一直有效：

```bash
# 把整个脚本的 stdout/stderr 都追加到日志
exec >>/var/log/myapp.log 2>&1
# 之后所有命令的输出都进日志；包括后续 echo
```

这种写法适合守护脚本，但会让交互式调试变难。用完要恢复时，先备份 fd：`exec 3>&1 4>&2`，结束时 `exec 1>&3 2>&4`，再关闭 3 和 4。

**非科班补一层：重定向发生在命令启动之前。** Shell 先 `fork` 出子进程，在子进程里完成打开与 `dup2`，最后才 `exec` 命令。命令还没开始跑，文件已经被创建或截断。所以 `ls /nonexistent > out.txt` 会留下一个空 `out.txt`，不要用“命令失败所以文件没动”做假设。

::: errata 关于重定向顺序的误解
1. **“`2>&1 >file` 和 `>file 2>&1` 一样”**——顺序不同，`dup2` 的目标不同；前者 stderr 留在终端，后者进文件。
2. **“命令失败，输出文件不会动”**——`>file` 在命令执行前就截断；失败也会留下空文件。
3. **“`> list 2> list` 是合并”**——两次独立 `open` 各自截断、各自偏移，输出会交错甚至互相覆盖；要合并用 `> list 2>&1` 或 `&>`。
:::

### 0.5.2 小结

重定向从左到右执行，每一步都改动当前 fd 表；`2>&1` 复制的是“当时 fd 1 指向谁”。因此 `>file 2>&1` 把两路都送进文件，`2>&1 >file` 只把 stdout 送进去。如果只记住一件事，那就是：**先画 fd 表，再写重定向，顺序就不会错。**

::: method 即时自测 · 0.5.2
**Q1（记忆）** 要让 stdout 和 stderr 都进 `app.log`，最短的 bash 写法是什么？

**Q2（辨析）** `cmd >out 2>err` 与 `cmd >out 2>&1` 的结果差在哪？

**Q3（应用）** 为什么 `ls /nonexistent > out.txt` 之后，`out.txt` 仍然存在且为空？

::: sol 答案
**A1** `cmd &>app.log`，或 POSIX 写法 `cmd >app.log 2>&1`。

**A2** 前者把 stdout 送进 `out`、stderr 送进 `err`，是两个文件；后者把 stderr 复制到 stdout 的目标，两路都进 `out`。

**A3** 重定向在命令执行前完成；Shell 先创建或截断 `out.txt`，再执行 `ls`，所以命令失败不影响这个空文件。
:::
:::

## 0.5.3 here-doc、here-string 与进程替换 {#sec-0.5.3}

这一节回答：同样是 `<<EOF`，为什么有时 `$HOME` 被替换，有时原样保留？

::: preview 先抓住一件事
定界符加引号，here-doc 正文就当纯文本；不加引号，`$`、反引号和 `\` 仍归 Shell 解释。写配置、生成脚本、传密码时，引号是安全默认。
:::

先看两种写法。第一种把配置原样写入：

```bash
cat > /tmp/app.conf <<'EOF'
# 引号包围定界符：不做变量展开、不执行命令替换
listen = 127.0.0.1:8080
password = $SECRET
EOF
```

`cat /tmp/app.conf` 会原样打印 `password = $SECRET`。定界符被单引号包住，正文里的 `$` 不再有特殊含义。

第二种不包围定界符，变量与命令替换都会发生：

```bash
name=api
cat <<EOF
service=${name}
started=$(date -Is)
EOF
```

输出里的 `service=api` 和当前时间，都是 Shell 在把正文交给 `cat` 之前替换好的。

**here-doc** 把一段文本作为 stdin 交给命令。结尾的定界符必须单独一行，前面不能有空格；`<<-` 允许用 tab 缩进。定界符加引号有三种等价写法：`<<'EOF'`、`<<"EOF"`、`<<\EOF`，它们都关闭参数展开、命令替换和算术展开。

`<<-` 只去掉行首的 **tab**，不去空格。在缩进的脚本里写 here-doc，要么用 tab 缩进，要么把定界符顶格写：

```bash
if true; then
	cat <<-'EOF'
		indented text
	EOF
fi
```

这里每一行开头都是 tab，所以 `<<-` 会把它们剥掉；如果换成四个空格，空格会留在输出里。

**为什么引号是安全默认？** 正文里只要出现 `$(...)` 或反引号，不加引号就会真的执行。哪怕这段文字本意只是配置里的字面量，Shell 也分不清“数据”和“命令”。加引号后，正文一个字符都不会被解释。

`<<<` 是 here-string，把字符串加一个换行送到 stdin：

```bash
read -r first rest <<< "alice admin dev"
printf '%s\n' "$first"   # alice
```

它比 `echo "$s" | cmd` 少一个进程，也不会把 `-n` 当成 `echo` 的选项。边界是：它会自动补一个换行；如果字符串本身以换行结尾，会多一个空行。

**进程替换**（process substitution）把命令的输出变成一个可读的文件路径：

```bash
# 比较两个已排序文件的差异，不生成临时文件
diff <(sort a.txt) <(sort b.txt)

# 把命令输出当作输入文件
while read -r line; do
    printf 'line: %s\n' "$line"
done < <(grep -v '^#' /etc/app.conf)

# 把输出写到多个消费者
tee >(gzip > /tmp/app.log.gz) > /tmp/app.log < /var/log/app.log
```

`<(...)` 在 bash 里展开成 `/dev/fd/63` 之类的路径，命令在子 Shell 中异步执行。它依赖 `/dev/fd`（Linux 上由 procfs 提供），不是 POSIX 标准；`dash`、旧版 `sh` 不支持。脚本的 shebang 是 `#!/bin/sh` 时不要用。

进程替换的一个常见坑是：**退出码拿不到**。`diff <(cmd1) <(cmd2)` 的退出码是 `diff` 的，`cmd1`/`cmd2` 的失败不会自动传播。需要检查时，让子命令把状态写到文件，或改用临时文件。

**非科班补一层：`/dev/fd/N` 是什么。** 进程替换并不是真的写了一个临时文件。bash 先建一个管道或临时文件，把命令接到一端，再把 `/dev/fd/N` 这个“已打开文件的入口”作为路径传给外层命令。外层命令 `open()` 这个路径时，拿到的是同一个底层文件或管道的另一个入口，所以能读到命令的输出；它不是 `dup`，偏移不共享。

::: errata 关于 here-doc 与进程替换的误解
1. **“`<<'EOF'` 只是换了一种引号”**——它关闭了正文里的变量、命令和算术展开；不加引号时三者都会发生。
2. **“`<<-` 会去掉行首空白”**——只去 tab，不去空格；用空格缩进时定界符仍然匹配失败。
3. **“进程替换的退出码会传给外层命令”**——不会；`diff <(cmd1) <(cmd2)` 只返回 `diff` 的状态。
4. **“`<<<` 和 `echo |` 完全一样”**——`<<<` 少一个进程，且不会把 `-n` 当选项；但它会自动补换行。
:::

### 0.5.3 小结

here-doc 的引号决定正文是否展开，`<<-` 只处理 tab，here-string 自动补换行，进程替换把命令输出伪装成文件路径。它们都靠 fd 和 `/dev/fd` 工作，不是新的文件类型。如果只记住一件事，那就是：**不需要展开时，定界符一律加引号。**

::: method 即时自测 · 0.5.3
**Q1（记忆）** `<<'EOF'`、`<<"EOF"`、`<<\EOF` 这三种写法有什么共同效果？

**Q2（辨析）** `<<-` 和 `<<` 的差别是什么？用空格缩进时哪个能匹配定界符？

**Q3（应用）** 要往 `/tmp/x.conf` 写入一行字面量 `${HOME}`，here-doc 应该怎么写？

::: sol 答案
**A1** 都关闭正文里的参数展开、命令替换和算术展开，正文按纯文本处理。

**A2** `<<-` 只去掉行首 tab；`<<` 不去。用空格缩进时只有 `<<` 能匹配顶格的定界符，`<<-` 仍要求定界符前只有 tab。

**A3** 用带引号的定界符，例如 `cat > /tmp/x.conf <<'EOF'`，正文写 `${HOME}`，最后单独一行 `EOF`。
:::
:::

## 0.5.4 管道：连接 fd，不连接命令 {#sec-0.5.4}

这一节回答：`a | b` 到底把什么接给了谁？为什么管道里的错误还在屏幕，退出码却总是 0？

::: preview 先抓住一件事
管道只连接 stdout：`a` 的 fd 1 接到管道写端，`b` 的 fd 0 接到读端，stderr 不参与。`$?` 默认只取最后一段；`PIPESTATUS` 保存每一段，`pipefail` 把整条管道改成“任一段失败即失败”。
:::

先看一个反直觉的结果：

```bash
false | true
echo $?          # 0：只看 true
set -o pipefail
false | true
echo $?          # 1：任一命令失败即失败
```

`false` 明明失败了，第一条管道却返回 0。因为管道默认只报告最后一个命令的状态，前面的失败被丢掉了。

`PIPESTATUS` 数组保存整条管道每个命令的退出码：

```bash
false | true | false
echo "${PIPESTATUS[@]}"   # 1 0 1
```

注意 `PIPESTATUS` 在下一条命令后就被覆盖。要保留，先赋值：`st=("${PIPESTATUS[@]}")`。

`SIGPIPE` 是管道最容易被误解的部分。`yes | head -n 1` 里，`head` 读一行就退出，`yes` 继续写时内核向它发 `SIGPIPE`，默认终止，退出码 141（128+13）。这不是错误配置，而是管道正常的“下游不读了”信号。

<div class="terminal" data-title="bash · 管道退出码与 SIGPIPE">
<pre><span class="p">&#36;</span> bash -c 'yes | head -n 1'
y
<span class="p">&#36;</span> bash -c 'yes | head -n 1; echo status=&#36;?'
y
status=0
<span class="p">&#36;</span> bash -c 'yes | head -n 1; echo pipestatus=&#36;{PIPESTATUS[*]}'
y
pipestatus=141 0
<span class="p">&#36;</span> bash -c 'set -o pipefail; yes | head -n 1; echo status=&#36;?'
y
status=141
<span class="p">&#36;</span> bash -c 'false | true; echo status=&#36;?'
status=0
<span class="p">&#36;</span> bash -c 'set -o pipefail; false | true; echo status=&#36;?'
status=1
</pre>
</div>

从内核看，`a | b` 做三件事：创建管道缓冲区；把 `a` 的 stdout 接到写端、`b` 的 stdin 接到读端；让两个进程并发执行。管道缓冲区在 Linux 上默认 64 KiB。单次 `write` 不超过 `PIPE_BUF`（4096 字节）时是原子的；细节在 [0.5.11](ch05.md#sec-0.5.11)。

管道只连接 **stdout**。`a` 写到 stderr 的错误消息不会进入 `b`，而是留在终端。要让 stderr 也进管道，必须在 `a` 这一侧写 `2>&1`（或 `|&`）。`find / -name x | grep foo` 里 `find` 的 `Permission denied` 不会出现在 `grep` 的输入中，这就是“管道里看不到错误”的原因。

未开 `pipefail` 时，管道退出码取最后一个命令 `head` 的状态 0；`yes` 的 141 只出现在 `PIPESTATUS` 里。开了 `pipefail` 后，`yes` 的 141 才成为整条管道的状态。脚本里如果 `set -o pipefail`，这种管道会被当成失败；而“下游提前退出”很多时候是预期的，需要显式处理：

```bash
# 允许下游提前退出：忽略 141
set +o pipefail
yes | head -n 1 >/dev/null
# 或者只关心某个命令的状态
producer | consumer
st=("${PIPESTATUS[@]}")
(( st[0] == 0 || st[0] == 141 )) || exit "${st[0]}"
```

**非科班补一层：如果你只写应用层，为什么会遇到 141？** 你在 CI 里写 `grep ERROR app.log | head -n 20`，再开 `pipefail`，构建可能以 141 失败。这不是 `grep` 崩了，而是 `head` 读够就退出，`grep` 下一次写被 `SIGPIPE` 终止。用 Python 或 Java 起子进程管道时同理：下游关闭读端，上游写端会收到 `SIGPIPE` 或 `EPIPE`。

`pipefail` 不是万能。它让“任一命令失败”变成失败，但无法告诉你哪一个失败；需要细节时看 `PIPESTATUS`。另外，`pipefail` 与 `set -e` 组合时，管道失败会让 Shell 直接退出，可能来不及清理；在清理逻辑里临时 `set +e`。

::: errata 关于管道的误解
1. **“管道会把 stderr 也传给下游”**——只连 stdout；要合并必须在上游写 `2>&1`，`|&` 是简写。
2. **“管道的 `$?` 是第一个命令的”**——默认是最后一个；要看每一段用 `PIPESTATUS`。
3. **“`PIPESTATUS` 可以稍后再看”**——下一条命令后就覆盖；必须紧接着赋值。
4. **“141 一定是程序 bug”**——`yes | head` 的正常结束就是 141；它表示下游已经关闭。
:::

### 0.5.4 小结

管道把 stdout 接到下一段的 stdin，stderr 不参与；每段并发执行，退出码默认只报最后一段。`PIPESTATUS` 给你每一段的状态，`pipefail` 把整条管道变成“任一段失败即失败”。如果只记住一件事，那就是：**看到 141 先问“下游是不是先走了”，不要先改上游代码。**

## 0.5.5 子 Shell 与变量丢失 {#sec-0.5.5}

这一节回答：`while read` 里明明做了加法，循环结束后变量为什么还是 0？

::: preview 先抓住一件事
管道的每一段都在子 Shell 中执行。子 Shell 是父 Shell 的副本，变量改动只留在副本里；父 Shell 看不到。
:::

先跑这段：

```bash
n=0
printf 'a\nb\n' | while read -r line; do
    n=$((n + 1))
done
echo "$n"       # 0，不是 2
```

循环确实跑了两遍，`n` 也确实加到了 2。但你 `echo` 的是父 Shell 的 `n`，它从头到尾都是 0。

这不是 bash 的 bug，而是管道语义：`while` 在子 Shell 里跑，`n` 的修改只发生在副本里。

**非科班补一层：fork 出来的“副本”是什么。** 进程是正在运行的程序；`fork` 让内核把当前进程复制一份。复制出来的是副本：变量表、当前目录、`umask`、`trap` 都各有一份。父进程改变量，子进程看不到；反过来也一样。管道两端的命令就是这样被 `fork` 出来的。

三种修复：

```bash
# 1. 进程替换：while 在当前 Shell 执行
n=0
while read -r line; do
    n=$((n + 1))
done < <(printf 'a\nb\n')
echo "$n"       # 2

# 2. lastpipe：让管道最后一段在当前 Shell 执行（非交互、job control 关闭时有效）
shopt -s lastpipe
printf 'a\nb\n' | while read -r line; do n=$((n + 1)); done
echo "$n"       # 2

# 3. 让子 Shell 输出结果，父 Shell 用命令替换接收
n=$(printf 'a\nb\n' | awk 'END {print NR}')
echo "$n"       # 2
```

第一种把数据来源放到进程替换里，`while` 本身留在当前 Shell。第二种让管道最后一段不 fork；它只在非交互 Shell 且 `set +m`（job control 关闭）时生效。交互式 Shell 默认 `set -m`，开了也不生效，这就是为什么网上的“一行修复”在你机器上时灵时不灵。第三种不共享变量，只把结果通过 stdout 带回来。

分组也会创建子 Shell：

```bash
# ( ) 子 Shell：cd 不影响父 Shell
( cd /tmp && ls >/dev/null )
pwd                      # 原目录

# { } 当前 Shell：cd 会影响父 Shell，注意分号与空格
{ cd /tmp && ls >/dev/null; }
pwd                      # /tmp
```

`{ ...; }` 要求 `{` 后有空格、`}` 前有分号，否则是语法错误。它不 fork，适合“临时改 IFS 或 cwd，之后恢复”的场景。

这个坑在 CI 里很常见：统计日志行数的循环写在管道里，最后上传的计数永远是 0。把 `while` 改成 `< <(...)`，或把计数交给 `awk`，问题就消失了。

::: errata 关于子 Shell 的误解
1. **“管道每段都在当前 Shell”**——每段都在子 Shell；变量修改不回传。
2. **“`lastpipe` 在任何 Shell 都生效”**——只在非交互且 job control 关闭（`set +m`）时生效。
3. **“`{ }` 和 `( )` 只是写法不同”**——`( )` 会 fork，`{ }` 不会；前者隔离 `cd`、`umask` 等状态，后者不隔离。
:::

### 0.5.5 小结

管道每段在子 Shell 中执行，子 Shell 是 fork 出来的副本，变量修改不会回传。修复要么让循环留在当前 Shell（进程替换、`lastpipe`），要么只把结果带回来（命令替换）。如果只记住一件事，那就是：**管道里的变量，属于另一个进程。**

::: method 即时自测 · 0.5.5
**Q1（记忆）** 管道里的 `while read` 为什么改不了外面的变量？

**Q3（应用）** 把 `printf 'a\nb\n' | while read ...; do n=$((n+1)); done` 改成能输出 2 的写法，至少给出一种。

::: sol 答案

**A2** `( cd /tmp )` 在子 Shell 中切换，父 Shell 目录不变；`{ cd /tmp; }` 在当前 Shell 执行，父 Shell 目录变成 `/tmp`。

**A3** 例如把循环的输入改成进程替换：

```bash

```

也可以让子 Shell 输出计数，父 Shell 用 `$(...)` 接收。

## 0.5.6 tee 与日志分流 {#sec-0.5.6}

这一节回答：`tee` 到底返回谁的状态？为什么日志最后一行写着 `exit=0`，部署却失败了？

::: preview 先抓住一件事
`tee` 把 stdin 复制到文件和 stdout，但它返回自己的状态，不是上游命令的。上游状态在 `PIPESTATUS[0]` 里；只看 `$?` 会把失败读成成功。
:::

先做一个最小实验：

```bash
false | tee /dev/null
echo $?                    # 0：这是 tee 的状态

false | tee /dev/null
st=("${PIPESTATUS[@]}")
echo "${st[0]} ${st[1]}"   # 1 0：false 失败，tee 成功
```

`false` 明明失败了，`$?` 却是 0。因为管道默认只取最后一段 `tee` 的状态，而 `tee` 正常写完就返回 0。

这就是“日志显示 0 但命令失败”的来源。一个部署脚本常写成：

```bash
./deploy.sh 2>&1 | tee -a deploy.log
exit $?
```

`deploy.sh` 挂了，`tee` 仍然成功；CI 看到最后一行 `exit=0`，把这次发布标成绿色。日志里有报错，流水线却认为一切正常。

`tee` 把 stdin 同时写到文件和 stdout。它解决“既要看输出，又要留日志”：

```bash
# 覆盖写
make 2>&1 | tee build.log
# 追加写
./deploy.sh 2>&1 | tee -a deploy.log
# 同时写两个文件
cmd | tee out1.log > out2.log
```

正确写法是先取 `PIPESTATUS[0]`：

```bash
#!/usr/bin/env bash
set -uo pipefail

log=/var/log/deploy.log
{
    printf '== %s start ==\n' "$(date -Is)"
    ./deploy.sh "$@"
} 2>&1 | tee -a "$log"
st=("${PIPESTATUS[@]}")
printf '== %s exit=%d ==\n' "$(date -Is)" "${st[0]}" | tee -a "$log"
exit "${st[0]}"
```

这里故意没有 `set -e`：如果开了 `set -e` 与 `pipefail`，管道失败会在 `st=...` 之前退出，日志里就少了结束行。需要严格失败时，用 `if ! ...; then` 包住，或在管道后立即 `set +e`。

**非科班补一层：`tee(1)` 不是内核的 `tee(2)`。** 命令行的 `tee` 是一个普通的用户态程序：它 `read` stdin，再 `write` 到文件和 stdout。内核里也有一个 `tee(2)`，它在两个管道之间复制数据，不经过用户态。名字相同，但前者有进程和缓冲区，后者是系统调用。

`tee` 还能把日志分给多个消费者：

```bash
# 一份进文件，一份交给 logger 进 syslog/journald
./app 2>&1 | tee -a /var/log/app.log >(logger -t app)
```

这行里 `>(logger -t app)` 是进程替换，`tee` 把它当成第二个文件写。顺序与缓冲可能导致 journald 与文件的时序略有差异，排查时序问题时不要依赖它。

::: errata 关于 tee 的误解
1. **“`tee` 会保留上游退出码”**——`tee` 返回自己的状态；要用 `PIPESTATUS[0]` 或 `pipefail`。
2. **“`cmd | tee log` 的 `$?` 是 `cmd` 的”**——是 `tee` 的；`false | tee /dev/null` 返回 0。
3. **“`tee` 写失败一定会让管道失败”**——写普通文件失败的行为取决于 `--output-error`；写管道失败（下游关闭）默认可能被忽略。
4. **“`tee` 只是把输出存一份”**——它还改变退出码的归属和写入时序，脚本里要显式处理。
:::

### 0.5.6 小结

`tee` 让一份输出同时去终端和日志，但它只对自己的写入负责，不替上游背退出码。日志包装必须取 `PIPESTATUS[0]`，再决定脚本返回什么。如果只记住一件事，那就是：**`cmd | tee log` 的成功，不代表 `cmd` 成功。**

::: method 即时自测 · 0.5.6
**Q1（记忆）** `cmd | tee log` 之后，`$?` 是谁的状态？上游状态在哪？

**Q2（辨析）** 为什么开了 `set -e` 与 `pipefail` 后，日志包装可能来不及写结束行？

**Q3（应用）** 写一段三行以内的命令，让 `./deploy.sh` 的输出同时进终端和 `deploy.log`，并让脚本最终返回 `deploy.sh` 的状态。

::: sol 答案

**A2** 管道失败时，`pipefail` 让整条管道返回非零，`set -e` 立即退出 Shell，后面的 `st=...` 和结束行都不会执行。

```bash
exit "${st[0]}"
```

## 0.5.7 缓冲、颜色与 TTY 检测 {#sec-0.5.7}

这一节回答：程序在终端里一行行输出，一进管道就“卡住”，颜色也没了，为什么？

::: preview 先抓住一件事
stdout 是不是 TTY，决定了两件事：stdio 用哪种缓冲模式，以及程序要不要上色。管道和文件不是 TTY，所以默认全缓冲、默认无色。
:::

先看一个常见现象：

```bash
./app | grep ERROR
```

在终端里直接跑 `./app`，日志一行行出来；接上 `grep` 后，屏幕长时间没有输出。程序没有死，它只是把日志攒在 stdio 缓冲区里，等攒满或退出时才 `write`。

C 标准库的 stdio 有三种缓冲模式：

| 模式 | 何时使用 | 行为 |
|:--|:--|:--|
| 全缓冲 | stdout 不是 tty（管道、文件） | 攒满缓冲区（通常 4–8 KiB）才 `write` |
| 行缓冲 | stdout 是 tty | 遇到换行就 `write` |
| 无缓冲 | stderr | 每次写入都 `write` |

这解释了两个现象：

1. **程序输出到管道后“卡住”**。日志在 stdio 缓冲区里，没攒满就不写；下游 `grep` 一直等不到数据。用 `stdbuf -oL` 强制行缓冲，或让程序自己 `fflush`。
2. **`tail -f` 看不到最新日志**。同上；另外 Python 需要 `-u` 或 `PYTHONUNBUFFERED=1`。

```bash
# 强制行缓冲；只对动态链接、使用 stdio 的程序有效
stdbuf -oL -eL ./app 2>&1 | grep ERROR

# script 分配一个 pty，让程序以为自己在终端里，从而启用行缓冲与颜色
script -q -c './app' /tmp/typescript

# expect 的 unbuffer 做同样的事
unbuffer ./app | grep ERROR
```

**非科班补一层：TTY 是什么。** TTY 是终端设备，SSH 里通常是 `/dev/pts/N` 这样的伪终端。程序用 `isatty(1)` 问内核：fd 1 是不是终端？是，就启用行缓冲和颜色；不是，就全缓冲、去色。这不是程序“检测环境”的玄学，而是一次普通的系统调用。

颜色是另一层。`ls --color=auto`、`grep --color=auto`、`git` 都会检测 `isatty(1)`：输出到终端才上色，输出到管道就关掉。这是好设计，但把带颜色的输出存文件再 `less` 时会丢色。要保留：

```bash
# --color=always 强制颜色；less -R 解释 ANSI 转义
grep --color=always ERROR app.log | less -R

# 尊重 NO_COLOR 约定：程序看到非空 NO_COLOR 应关闭颜色
NO_COLOR=1 ./app
```

`TERM=dumb` 也能让部分程序关闭颜色与光标控制。写脚本时不要假设输出一定是 tty：日志、CI、cron 里都没有 tty。

**为什么 CI/cron 里没有颜色？** CI runner 通常把命令的 stdout 接进管道，cron 把输出接进邮件或日志文件。`isatty(1)` 返回假，`--color=auto` 就关色。需要彩色日志时，显式加 `--color=always`，并确认日志查看器能解释 ANSI 转义；否则宁可用纯文本。

::: errata 关于缓冲与颜色的误解
1. **“`stdbuf` 对所有程序有效”**——只对动态链接、使用 stdio 的程序；静态链接、setuid、直接 `write(2)` 的程序无效。
2. **“stderr 永远无缓冲”**——C stdio 的 stderr 默认无缓冲，但程序可以 `setvbuf` 改；Shell 的 `echo >&2` 走的是 `write`。
3. **“输出到文件后颜色丢了是程序坏了”**——程序按 `isatty` 关闭颜色；需要时用 `--color=always` 或 `FORCE_COLOR`。
4. **“`tail -f` 能立刻看到所有日志”**——上游可能全缓冲；用 `stdbuf -oL` 或程序自己的 flush。
5. **“`script` 只是录屏”**——它分配 pty，改变程序的缓冲与颜色行为；录出来的文件还带控制字符。
:::

### 0.5.7 小结

缓冲模式由 stdout 是不是 TTY 决定：终端行缓冲，管道和文件全缓冲，stderr 无缓冲。颜色也走同一套 `isatty` 判断，所以 CI 和 cron 里默认没有颜色。如果只记住一件事，那就是：**输出“卡住”先查缓冲，不要先怀疑程序死了。**

::: method 即时自测 · 0.5.7
**Q1（记忆）** stdio 的三种缓冲模式分别叫什么？stdout 接管道时用哪一种？

**Q2（辨析）** `stdbuf -oL ./app | grep ERROR` 为什么有时仍然看不到实时输出？

**Q3（应用）** 日志文件里没有颜色，但终端里有；解释原因并给出一种保留颜色的办法。

::: sol 答案
**A1** 全缓冲 `_IOFBF`、行缓冲 `_IOLBF`、无缓冲 `_IONBF`；stdout 接管道时默认全缓冲。

**A2** `stdbuf` 只对动态链接且使用 stdio 的程序有效；静态链接、setuid、直接 `write(2)` 或自己调用 `setvbuf` 的程序不受它控制。

**A3** 程序用 `isatty(1)` 判断 stdout 不是终端，于是关闭颜色。可以在查看时用 `grep --color=always ... | less -R`，或设置程序支持的 `FORCE_COLOR`。
:::
:::

## 0.5.8 fd 表的内核结构：从 `dup2` 到 `O_CLOEXEC` {#sec-0.5.8}

这一节回答：`dup2` 到底复制了什么？为什么两个 fd 会共享偏移，`O_CLOEXEC` 又防的是什么？
分工先说清：0.5.1 已经会让你画 fd 表，这一节不重讲用法，只看内核里那张表与 `dup2`、`O_CLOEXEC` 划出的边界。


::: preview 先抓住一件事
fd 表项是一个指针，指向内核的“打开文件描述”。`dup2` 让两个槽位指向同一条记录，所以共享偏移；`O_CLOEXEC` 让 fd 在 `exec` 时自动关闭，防止泄漏给新程序。
:::

先做一个能看见偏移的实验。准备两行文件，用 `exec 3<` 打开：

```bash
printf 'a\nb\n' > /tmp/two.txt
exec 3< /tmp/two.txt
head -n 1 <&3      # a
head -n 1 <&3      # b
exec 3<&-
```

两次 `head` 读到不同的行。再看每次都重新打开同一文件：

```bash
head -n 1 /tmp/two.txt   # a
head -n 1 /tmp/two.txt   # a
```

同样是读第一行，为什么前一组第二次读到了 `b`？`exec 3<` 只打开一次；每次 `head` 通过 `<&3` 复制 fd 3，复制出来的是同一条打开文件描述。偏移只有一份，第一次读走到 1，第二次从 1 继续。

后一组每次都 `open()`，得到新的打开文件描述，偏移从 0 开始，所以两次都读到 `a`。

内核把这件事分成三层：

| 层 | 谁维护 | 里面有什么 |
|:--|:--|:--|
| 描述符表 | 每个进程一张 | fd 槽位，槽位指向打开文件表项 |
| 打开文件表 | 全系统共享 | 偏移、状态标志、引用计数 |
| inode 表 | 全系统共享 | 文件类型、大小、权限、磁盘位置 |

`dup2` 只改第一层和第二层之间的指针，不碰 inode，也不复制数据。

::: def 定义 0.5.8 · 打开文件描述 {#def-0.5.8}
打开文件描述（open file description，内核里是 `struct file`）是“一次 `open()`”的记录。它保存当前偏移 `f_pos`、状态标志 `f_flags`、引用计数 `f_count` 和文件操作表 `f_op`；fd 表项指向它。
:::

每个进程的 fd 表在内核里是 `struct files_struct`，表项指向 `struct file`。`struct file` 包含：

| 字段 | 含义 | 谁共享 |
|:--|:--|:--|
| `f_path` | `vfsmount + dentry` | 所有 dup 出来的 fd |
| `f_pos` | 当前偏移 | `dup`/`fork` 共享；独立 `open` 不共享 |
| `f_flags` | `O_APPEND`、`O_NONBLOCK` 等 | 共享 |
| `f_mode` | 读/写模式 | 共享 |
| `f_op` | 文件操作函数表 | 共享 |
| `f_count` | 引用计数 | 每次 `dup`/`fork` 加一 |

`dup2(oldfd, newfd)` 做三件事：如果 `newfd` 已打开，先关闭它；让 `newfd` 指向 `oldfd` 的 `struct file`；`f_count` 加一。它不复制文件内容，也不重置偏移。成功返回 `newfd`；`oldfd` 无效时返回 -1、`errno=EBADF`，且不关闭 `newfd`；`oldfd` 与 `newfd` 相等时什么都不做。

```c
int fd = open(path, O_RDONLY | O_CLOEXEC);
if (fd < 0) { perror("open"); return 1; }
/* 让 fd 变成 3，且 3 不带 CLOEXEC（除非用 dup3 + O_CLOEXEC） */
if (dup2(fd, 3) < 0) { perror("dup2"); close(fd); return 1; }
close(fd);
```

注意最后一行：`dup2` 之后 `fd` 和 3 指向同一条 `struct file`，但它们是两个槽位。关闭 `fd` 只是去掉一个引用，fd 3 仍然能读写。`dup2` 产生的新 fd 的 `FD_CLOEXEC` 总是关闭的；要保留 close-on-exec，用 `dup3(fd, 3, O_CLOEXEC)`。

`dup2` 的原子性只覆盖“关旧 + 复制”这一步；多线程程序里，如果另一个线程正好在 `dup2` 期间使用 `newfd`，行为仍然危险。`dup3` 多了 `O_CLOEXEC` 参数，可以原子地设置 close-on-exec。`fcntl(F_DUPFD_CLOEXEC)` 分配一个不小于指定值的新 fd，并带 `CLOEXEC`。

`fork` 后父子进程的 fd 指向同一批 `struct file`，所以父子共享偏移；这也是“父进程读了一半，子进程接着读”的原因。

`O_CLOEXEC` 解决的是“fork + exec 之间的 fd 泄漏”：

- `fork` 后子进程继承所有 fd；
- `execve` 会关闭带 `FD_CLOEXEC` 的 fd，其余保留；
- 如果父进程在多线程环境里 `open` 后 `fork`，另一个线程可能在这期间 `exec`，把不该传的 fd 带进新程序；
- `O_CLOEXEC` 让“打开”与“设置 close-on-exec”成为一个原子操作。

`FD_CLOEXEC` 是每个 fd 自己的标志，不是 `struct file` 的状态标志。`dup2` 产生的新 fd 默认不带它；要让新 fd 也带，用 `dup3` 的 `O_CLOEXEC`，或 `fcntl(F_DUPFD_CLOEXEC)`。

Shell 的重定向默认不带 `CLOEXEC`（因为要让子命令继承），但它打开的 fd 3 以上通常在执行外部命令时保留。脚本里用 `exec {fd}>file` 打开的 fd，如果不想传给子进程，Shell 没有直接开关；可以在执行前用 `{fd}>&-` 关闭，或在 C 程序里用 `fcntl` 设置。

**非科班补一层：`struct file` 不是磁盘文件。** 磁盘文件由 inode 表示，`struct file` 是内核对“这一次打开”的记录，里面有偏移、标志和引用计数。多个 `struct file` 可以指向同一个 inode；一个 `struct file` 也可以被多个 fd 指向。`dup2` 复制的是后一层指针，不碰 inode，也不复制数据。

fd 的上限由 `RLIMIT_NOFILE` 控制：

```bash
ulimit -n              # 软限制，常见 1024 或 1048576
ulimit -Hn             # 硬限制
cat /proc/self/limits | grep 'open files'
```

fd 耗尽时，`open`/`pipe`/`socket` 返回 `EMFILE`（进程上限）或 `ENFILE`（系统上限）。Shell 的 `exec 3>file` 失败会返回非零，但不会自动退出；脚本要检查。`/proc/PID/fd` 是排查 fd 泄漏的第一现场：

```bash
ls -l /proc/$$/fd
# lrwx------ 1 wang wang 64 ... 0 -> /dev/pts/0
# lrwx------ 1 wang wang 64 ... 1 -> /dev/pts/0
# lrwx------ 1 wang wang 64 ... 2 -> /dev/pts/0
# lr-x------ 1 wang wang 64 ... 3 -> /tmp/extra.log
```

`ls -l /proc/PID/fd` 里的 `->` 目标是内核 `d_path()` 生成的；已删除文件显示 `... (deleted)`。`/proc/PID/fdinfo/N` 给出 `pos`、`flags`、`mnt_id`。对同一文件 `dup` 出来的两个 fd，读一个另一个的 `pos` 会一起前进，可以用它验证共享偏移。

::: errata 关于 `dup2` 与 `O_CLOEXEC` 的误解
1. **“`dup2` 会复制文件内容”**——只复制指向关系；两个 fd 共享 `struct file` 与偏移。
2. **“关掉一个 fd，另一个也不能用了”**——只要还有 fd 指向那条 `struct file`，文件就仍然打开；最后一个引用关闭时才释放。
3. **“`O_CLOEXEC` 只是可选优化”**——它防 `fork+exec` 之间的 fd 泄漏；多线程程序里是正确性问题。
4. **“`FD_CLOEXEC` 是文件状态标志”**——它是每个 fd 自己的标志；`dup2` 出来的新 fd 默认不带，需要 `dup3` 或 `fcntl` 显式设置。
:::

### 0.5.8 小结

fd 表是进程级的下标表，表项指向系统级的打开文件描述；`dup2` 复制的是这个指针，所以两个 fd 共享偏移和状态标志。`O_CLOEXEC` 是 fd 自己的标志，用来在 `exec` 时自动关闭，防止泄漏。如果只记住一件事，那就是：**`dup2` 复制的是“同一次打开”，不是文件内容。**

## 0.5.9 重定向语法全表与求值顺序 {#sec-0.5.9}

这一节回答：`>`、`>>`、`<>`、`{fd}>` 这些写法，内核各收到什么？为什么 `&&` 与 `||` 混用会出意外？
0.5.2 教过常用写法的求值顺序，这一节给全表与少数派写法——用来查，不用来学。


::: preview 先抓住一件事
每种重定向都能翻译成一组 `open`/`dup2`/`close` 调用；`>` 是截断，`>>` 是追加，`n>&m` 是 `dup2`。求值仍是从左到右，而且重定向在命令执行前完成。
:::

0.5.2 给的是入门表，这一节把它展开成“内核看到的标志”。下表按打开方式分组，`n` 是 fd 编号，省略时默认 0（输入）或 1（输出）。

| 语法 | 打开方式 | 说明 |
|:--|:--|:--|
| `>file` | `O_WRONLY\|O_CREAT\|O_TRUNC` | 截断；`noclobber` 下对已存在普通文件失败 |
| `>\|file` | 同上，忽略 `noclobber` | 强制覆盖 |
| `>>file` | `O_WRONLY\|O_CREAT\|O_APPEND` | 追加；单次 `write` 的原子性有限 |
| `<file` | `O_RDONLY` | 输入 |
| `<>file` | `O_RDWR\|O_CREAT` | 读写，不截断 |
| `n>&m` | `dup2(m, n)` | 让 n 指向 m 当前目标 |
| `n<&m` | `dup2(m, n)` | 同上，输入方向 |
| `n>&-` / `n<&-` | `close(n)` | 关闭 |
| `&>file` | `>file 2>&1` | bash 扩展；POSIX 不认 |
| `&>>file` | `>>file 2>&1` | bash 扩展 |
| `\|&` | `2>&1 \|` | bash 4+ |
| `<<word` | here-doc | 见下一节 |
| `<<-word` | here-doc，去掉行首 tab | 不是空格 |
| `<<<word` | here-string | bash 扩展，自动补换行 |
| `>(list)` | 进程替换，写端 | 展开成 `/dev/fd/N` |
| `<(list)` | 进程替换，读端 | 同上 |
| `{var}>file` | 分配 fd 到变量 | bash 4.1+，fd ≥ 10 |
| `{var}>&-` | 关闭变量里的 fd | 同上 |

`>file` 的 mode 是 `0666 & ~umask`；目录不可写、磁盘满、inode 耗尽分别返回 `EACCES`、`ENOSPC`、`ENOSPC`。`>>file` 用 `O_APPEND`，每次 `write` 前内核把偏移移到末尾。多个进程同时追加时，单次 `write` 小于 `PIPE_BUF` 的原子性只对管道成立；普通文件的 `O_APPEND` 在本地文件系统上通常原子，但 NFS 不保证。

**重定向在命令执行前完成**，所以命令失败也会留下副作用。`ls /nonexistent > out.txt` 会先创建/截断 `out.txt`，再执行 `ls`，最后 `out.txt` 是空的；脚本不能靠「命令失败所以文件没动」做假设。一个真实事故是 `ls > less`：它把当前目录的列表写进当前目录下名为 `less` 的文件；如果这个文件在 `PATH` 里，管理员从此失去 `less`。重定向目标如果是已存在的命令、配置或设备节点，`>` 会静默覆盖，执行前先 `ls -l` 看一眼目标。

求值顺序是**从左到右**，且重定向在命令执行前完成。用 fd 表快照解释三组常见写法：

```bash
# A: >out 2>&1 —— stderr 跟 stdout 进文件
cmd >out 2>&1
# 1) open(out) -> fd 3; dup2(3,1); close(3)   fd1=out, fd2=tty
# 2) dup2(1,2)                                fd1=out, fd2=out

# B: 2>&1 >out —— stderr 留在终端
cmd 2>&1 >out
# 1) dup2(1,2)                                fd1=tty, fd2=tty
# 2) open(out) -> fd 3; dup2(3,1); close(3)   fd1=out, fd2=tty

# C: &>out —— bash 的合并写法
cmd &>out
# 等价于 A，但不需要记顺序
```

`&&` 与 `||` 也按退出码短路，但它们的优先级相同、从左到右结合，混用时必须加括号或改写：

```bash
cmd1 && cmd2 || cmd3      # cmd1 成功跑 cmd2；cmd2 失败会继续跑 cmd3
cmd1 || cmd2 && cmd3      # cmd1 失败时，cmd2 成功后还会跑 cmd3
```

第二种写法在 `cmd1` 失败时可能同时执行 `cmd2` 与 `cmd3`，因为 `||` 先与 `cmd1` 结合，结果再参与后面的 `&&`。需要「二选一」时写 `if cmd1; then cmd2; else cmd3; fi`，不要依赖 `&&`/`||` 的直觉。

`exec` 形式的重定向会改变当前 Shell 的 fd 表，并在后续命令中持续有效：

```bash
exec 3>&1 4>&2          # 备份 stdout/stderr
exec >>"$log" 2>&1      # 之后全部追加到日志
printf 'hello\n'        # 进日志
exec 1>&3 2>&4          # 恢复
exec 3>&- 4>&-          # 关闭备份
```

顺序不能反：如果先 `exec 1>&3` 再 `exec 3>&-`，恢复成功；如果先关 3，`1>&3` 会报 `Bad file descriptor`。恢复段本身也可能失败，脚本里要检查，或把日志重定向放在子 Shell `( ... )` 里，避免污染父 Shell。

`noclobber` 的边界：

```bash
set -C
> existing.txt          # 失败：cannot overwrite existing file
>| existing.txt         # 强制覆盖
>> existing.txt         # 追加，允许
<> existing.txt         # 读写，允许
```

`set -C` 只防「`>` 截断已存在的普通文件」，不防 `>>`、`<>`、`tee`、`dd`。脚本里更稳的写法是「临时文件 + `mv` 原子替换」，而不是依赖 `noclobber`。

简单命令的赋值与重定向顺序也值得注意：

```bash
FOO=bar > /tmp/x        # 创建 /tmp/x（空），FOO 在当前 Shell 生效
FOO=bar cmd > /tmp/x    # FOO 只对 cmd 生效
```

只有赋值和重定向、没有命令时，重定向在当前 Shell 执行，赋值也留在当前 Shell；有命令时，赋值进入命令的环境，重定向只影响该命令。这个区别在「用重定向创建文件」时很有用，也容易误以为 `FOO=bar >file` 会把 `FOO` 导出。

复合命令也能加重定向：

```bash
while IFS= read -r line; do printf '%s\n' "$line"; done < input.txt > output.txt
{ printf 'a\n'; printf 'b\n'; } > out.txt
if true; then printf 'yes\n'; fi > out.txt
f() { printf 'body\n'; } > /tmp/f.out   # 重定向在函数执行时生效
```

`{ ...; }` 与 `( ... )` 的重定向作用域不同：前者在当前 Shell，后者在子 Shell。函数定义上的重定向在**调用时**生效，不是定义时。

**非科班补一层：语法表就是 `open` 标志表。** `>file` 对应 `O_WRONLY|O_CREAT|O_TRUNC`，`>>file` 对应 `O_APPEND`。输入重定向（`<` 后接文件名）对应 `O_RDONLY`，`n>&m` 对应 `dup2`。遇到没见过的写法，先把它拆成“打开什么、复制到哪个 fd、关掉谁”，就不会被符号吓住。

::: errata 关于重定向全表的误解
1. **“`>>` 在任何文件系统上都原子”**——普通文件的 `O_APPEND` 在本地文件系统上通常原子，NFS 不保证；跨进程追加日志不要假设绝对安全。
2. **“`&&` 和 `||` 的优先级不同”**——两者优先级相同、从左到右结合。`cmd1 || cmd2 && cmd3` 在 `cmd1` 失败时可能同时执行 `cmd2` 和 `cmd3`。
3. **“`FOO=bar >file` 会把 FOO 导出”**——它只创建文件并在当前 Shell 设置 FOO，不导出给子进程；要导出得用 `export` 或写在命令前。
:::

### 0.5.9 小结

重定向语法是 `open` 标志和 `dup2` 的简写；`>` 截断、`>>` 追加、`n>&m` 复制指向，求值从左到右且在命令执行前完成。`&&`/`||` 不是二选一语法，混用时要用 `if` 或括号表达意图。如果只记住一件事，那就是：**看到重定向，先翻译成 open + dup2 + close。**

::: method 即时自测 · 0.5.9

**Q2（辨析）** `cmd1 && cmd2 || cmd3` 与 `cmd1 || cmd2 && cmd3` 在 `cmd1` 失败时分别会跑什么？

**Q3（应用）** `set -C` 之后，`> existing.txt` 报错；怎样强制覆盖这个文件？

::: sol 答案

**A2** 第一种在 `cmd1` 失败时跳过 `cmd2`，执行 `cmd3`；第二种在 `cmd1` 失败时执行 `cmd2`，如果 `cmd2` 成功还会继续执行 `cmd3`。

## 0.5.10 here-doc 的引号、临时文件与 `/dev/fd` 细节 {#sec-0.5.10}

这一节回答：here-doc 在底层是临时文件还是管道？进程替换的 `/dev/fd/63` 到底是什么？
0.5.3 已会写 here-doc 与进程替换，这一节只看三处会咬人的细节：引号、临时文件、`/dev/fd`。


::: preview 先抓住一件事
here-doc 在命令执行前就被读入，可能是临时文件，也可能是管道；定界符的引号决定正文是否展开。进程替换把 fd 重新暴露成一个路径，不是复制 fd。
:::

here-doc 的完整规则：

1. `<<word` 把后续行作为 stdin，直到一行只包含 `word`（前面不能有空格；`<<-` 允许 tab）。
2. 定界符加引号（`<<'EOF'`、`<<"EOF"`、`<<\EOF`）时，正文不做参数展开、命令替换、算术展开；不加引号时三者都做。
3. 正文里的 `\` 在未加引号时用于转义 `$`、`` ` ``、`\`、换行；加引号时原样保留。
4. 多个 here-doc 按出现顺序读取；`<<A <<B` 的正文先给 A，再给 B。
5. here-doc 在命令执行前被读入；它不占用命令行参数。未加引号时，正文里的未定义变量仍受 `set -u` 影响。

```bash
# 安全：配置原样写入
cat > /etc/myapp.conf <<'EOF'
listen = 127.0.0.1:8080
password = $SECRET          # 不会被展开
EOF

# 需要展开：变量与命令替换都会执行
name=api
cat <<EOF
service=${name}
started=$(date -Is)
EOF
```

写配置、生成脚本、传密码时，**默认加引号**。不加引号时，正文里的 `$()` 会执行任意命令；哪怕它本意只是配置里的字面量，Shell 也会把它当代码。

`<<-` 只去掉行首的 **tab**，不去空格。缩进的脚本里用 tab 缩进 here-doc，或把定界符顶格：

```bash
if true; then
	cat <<-'EOF'
		indented text
	EOF
fi
```

`<<<` 是 here-string：把字符串加一个换行送到 stdin，不经过分词与通配符展开（但参数展开仍发生）。

```bash
read -r first rest <<< "alice admin dev"
printf '%s|%s\n' "$first" "$rest"     # alice|admin dev
```

它比 `echo "$s" | cmd` 少一个进程，也不会把 `-n` 当成 `echo` 的选项。边界：字符串本身以换行结尾时会多一个空行；`<<<` 是 bash 扩展，`dash` 不支持。

**进程替换**把命令的输出/输入变成一个文件路径：

```bash
diff <(sort a.txt) <(sort b.txt)
while IFS= read -r line; do printf '<%s>\n' "$line"; done < <(grep -v '^#' conf)
tee >(gzip > /tmp/app.log.gz) > /tmp/app.log < /var/log/app.log
```

`<(cmd)` 在 bash 里展开成 `/dev/fd/63`，命令在子 Shell 中异步执行；`>(cmd)` 同理，写端交给 `cmd`。它依赖 `/dev/fd`（Linux 由 procfs 提供），不是 POSIX；`dash`、旧 `sh` 不支持。容器里如果没挂 `/proc`，进程替换会失败。

进程替换的退出码拿不到：`diff <(cmd1) <(cmd2)` 的 `$?` 是 `diff` 的，`cmd1`/`cmd2` 的失败不会传播；`$!` 也不是它们的 PID。需要检查时，让子命令把状态写到文件，或改用临时文件/命名管道。

here-doc 与进程替换的实现细节：bash 对 here-doc 可能使用临时文件或管道，具体取决于版本与大小；不要在 here-doc 里假设 stdin 可 `seek`。进程替换的 `/dev/fd/N` 是「重新打开」而不是「复制 fd」，所以它不共享原命令的偏移；对管道而言偏移无意义，对普通文件则可能有独立偏移。

`coproc` 是 bash 的另一种双向管道：

```bash
coproc WORKER { while IFS= read -r line; do printf 'got:%s\n' "$line"; done; }
printf 'a\nb\n' >&"${WORKER[1]}"
exec {WORKER[1]}>&-
while IFS= read -r out; do printf '%s\n' "$out"; done <&"${WORKER[0]}"
wait "$WORKER_PID"
```

`coproc` 的 fd 在数组里，读写要手动关闭写端，否则读循环永远等不到 EOF。它适合「父 Shell 与一个长期子进程对话」，不适合高并发；并发用后台任务 + `wait -n`（见 [0.8](ch08.md)）。

**非科班补一层：`/dev/fd/N` 是“重新打开”，不是“复制 fd”。** 打开它会得到一条新的打开文件描述，偏移可能独立；这就是 `cmd < /dev/stdin` 不一定接着读的原因。`coproc` 的读循环要等 EOF，所以必须关掉写端，否则父 Shell 自己还握着写端，永远等不到结束。

::: errata 关于 here-doc 底层的误解
1. **“here-doc 一定是临时文件”**——bash 可能用临时文件，也可能用管道，取决于版本和大小；不要假设 stdin 可 `seek`。
2. **“`/dev/fd/N` 就是 fd N 的别名”**——它是一次新的 `open`，偏移和标志可能独立；要共享偏移用 `<&N` 或 `dup2`。
3. **“进程替换的失败会传出来”**——`diff <(cmd1) <(cmd2)` 只返回 `diff` 的状态，子命令失败不会自动传播。
4. **“`coproc` 读完会自动结束”**——父 Shell 不关闭写端，读循环就等不到 EOF；要显式 `exec {fd}>&-`。
:::

### 0.5.10 小结

here-doc 在命令执行前读入，引号关闭展开，`<<-` 只去 tab；进程替换把命令接到 `/dev/fd/N`，外层命令像读文件一样读它。`/dev/fd/N` 是重新打开，退出码也不会自动传回来。如果只记住一件事，那就是：**here-doc 的引号是数据与代码的分界线。**

## 0.5.11 管道的内核语义：缓冲区、原子性与 `SIGPIPE` {#sec-0.5.11}

这一节回答：管道缓冲区到底多大？`PIPE_BUF` 保证什么？为什么 `yes | head` 的 141 不算 bug？
0.5.4 会让你用管道，这一节只看内核给它划的三条边界：缓冲区大小、单次写的原子性、读端关闭时的 `SIGPIPE`。


::: preview 先抓住一件事
Linux 管道缓冲区默认 64 KiB，由一组页组成；单次 `write` 不超过 `PIPE_BUF`（4096 字节）才保证不与其他写者交错。读端关闭后，写入者收到 `SIGPIPE`，默认退出码 141。
:::

`a | b` 在 Shell 里是：创建管道、fork 两个子进程、分别 `dup2` 到 stdin/stdout、`exec`。内核里管道是 `struct pipe_inode_info` 加一组 `pipe_buffer`，每个 buffer 指向一个页。默认容量 16 页（64 KiB）。可通过 `fcntl(F_SETPIPE_SZ)` 调整，上限是 `/proc/sys/fs/pipe-max-size`（默认 1 MiB，root 可调）。

管道只连接 **stdout**。`a` 写到 stderr 的错误消息不会进入 `b`，而是留在终端；要让 stderr 也进管道，必须在 `a` 这一侧写 `2>&1`（或 `|&`）。`find / -name x | grep foo` 里 `find` 的 `Permission denied` 不会出现在 `grep` 的输入中，这就是「管道里看不到错误」的原因。

```bash
# 查看/调整管道容量（C 或 Python 都可以；Shell 没有直接命令）
cat /proc/sys/fs/pipe-max-size
python3 - <<'PY'
import fcntl, os
r, w = os.pipe()
print('default', fcntl.fcntl(w, fcntl.F_GETPIPE_SZ))
fcntl.fcntl(w, fcntl.F_SETPIPE_SZ, 1 << 20)
print('after', fcntl.fcntl(w, fcntl.F_GETPIPE_SZ))
PY
```

原子性由 `PIPE_BUF`（Linux 4096）决定：

- 单次 `write` ≤ `PIPE_BUF`：不会与其他写者交错，要么全写，要么阻塞；
- 单次 `write` > `PIPE_BUF`：可能被拆分，多个写者的数据会交错；
- 管道满时，写者阻塞（除非 `O_NONBLOCK`，此时返回 `EAGAIN`）；
- 管道为空且写端还开着时，阻塞 `read` 等待，非阻塞 `read` 返回 `EAGAIN`；写端关闭且数据读完后，`read` 返回 0；
- 读端关闭后，写者收到 `SIGPIPE`；若忽略/阻塞，`write` 返回 `EPIPE`。

`SIGPIPE` 的默认动作是终止进程，被终止的 `yes` 退出码是 141（128+13）。`yes | head -n 1` 里 `head` 读一行就退出，`yes` 继续写，内核向它发 `SIGPIPE`；这是正常的下游关闭，不是错误。没开 `pipefail` 时，整条管道的状态仍是 `head` 的 0，141 只出现在 `PIPESTATUS` 里。

```bash
bash -c 'yes | head -n 1; echo status=$? yes=${PIPESTATUS[0]}'
# y
# status=0 yes=141
```

要区分「下游正常关闭」与「上游真失败」，看 `PIPESTATUS`：

```bash
set -o pipefail
yes | head -n 1 >/dev/null
st=("${PIPESTATUS[@]}")
printf 'yes=%s head=%s\n' "${st[0]}" "${st[1]}"
# yes=141 head=0
```

`pipefail` 让整条管道返回最右侧非零状态；它不能告诉你是哪一段，`PIPESTATUS` 才能。`PIPESTATUS` 在下一条命令后就被覆盖，必须立刻赋值。`set -e` + `pipefail` 下，`yes | head` 会让脚本在管道处退出；如果这是预期，显式处理 141：

```bash
if ! yes | head -n 1 >/dev/null; then
    st=("${PIPESTATUS[@]}")
    (( st[0] == 141 )) || exit "${st[0]}"
fi
```

注意 `!` 会反转整个管道的状态，`PIPESTATUS` 仍是各段原始状态；不要在 `!` 之后再依赖 `$?` 判断具体段。

管道还有两个容易忽略的点：

- **管道不是文件**。`ls -l /proc/$$/fd/1` 在管道里显示 `pipe:[12345]`，不能 `seek`，`fstat` 的 `st_size` 是 0。
- **管道缓冲区不是无限**。生产者比消费者快时，写满 64 KiB 就阻塞；这提供了天然的背压（下游慢会反过来卡住上游），但也可能让「先读全部再处理」的程序死锁（双方都在等对方）。

`tee` 系统调用（`tee(2)`）与 `tee(1)` 命令不是一回事：前者在两个管道之间复制数据，不经过用户态；`splice(2)` 把管道数据零拷贝（不在内核和用户态之间来回复制）地接到文件/另一个管道。Shell 的 `tee` 命令是用户态程序，读写 + 写两份，性能和原子性都不同。

**非科班补一层：页是什么。** 内核按页管理内存，x86-64 上常见一页 4 KiB；管道默认有 16 个 `pipe_buffer`，每个指向一页，所以是 64 KiB。`F_SETPIPE_SZ` 调整的是页数，不是任意字节数。

::: errata 关于管道内核语义的误解
1. **“管道缓冲区是无限的”**——Linux 默认 64 KiB，写满会阻塞；`/proc/sys/fs/pipe-max-size` 只是上限，不是当前容量。
2. **“`PIPE_BUF` 在哪个 Unix 上都是 4096”**——Linux 是 4096，POSIX 只要求至少 512；其他系统可能不同。
3. **“管道也是文件，可以 seek”**——管道是字节流，`lseek` 会失败，`fstat` 的 `st_size` 是 0。
4. **“`pipefail` 能告诉我是哪一段失败”**——它只给出整条管道的状态；具体哪段要看 `PIPESTATUS`。
:::

### 0.5.11 小结

管道是容量有限的内核字节流，默认 64 KiB；`PIPE_BUF` 约束的是单次 `write` 的原子性，不是总容量。读端关闭时，写入者收到 `SIGPIPE`，忽略信号则得到 `EPIPE`。如果只记住一件事，那就是：**`PIPE_BUF` 管“一次写不交错”，64 KiB 管“总共能攒多少”。**

## 0.5.12 子 Shell、`lastpipe` 与变量作用域 {#sec-0.5.12}

这一节回答：子 Shell 到底复制了哪些状态？`lastpipe` 为什么时灵时不灵？
0.5.5 已经演示过变量为什么会丢，这一节说清子 Shell 到底复制了哪些状态、`lastpipe` 的生效条件是什么。


::: preview 先抓住一件事
管道的每一段默认 `fork` 出副本，变量表、cwd、umask、trap 都隔离。`lastpipe` 只让最后一段留在当前 Shell，而且要求非交互 Shell 加 `set +m`。
:::

管道的每一段默认在子 Shell 执行，`fork` 出来的副本有独立的变量表、cwd、umask、trap。父 Shell 看不到子 Shell 的修改：

```bash
n=0
printf 'a\nb\n' | while read -r line; do n=$((n + 1)); done
printf 'n=%d\n' "$n"      # n=0
```

三种修复的边界：

| 方法 | 写法 | 生效条件 | 代价 |
|:--|:--|:--|:--|
| 进程替换 | `while ...; done < <(cmd)` | bash/ksh，依赖 `/dev/fd` | 仍是子进程产生数据，但循环在当前 Shell |
| `lastpipe` | `shopt -s lastpipe` | 非交互 + job control 关闭（`set +m`） | 只让最后一段在当前 Shell |
| 命令替换 | `n=$(cmd \| awk ...)` | POSIX | 结果走 stdout，末尾换行被剥 |
| 临时文件 | `cmd > tmp; while ...; done < tmp` | 可移植 | 磁盘 I/O，需清理 |

`lastpipe` 的生效条件经常被忽略。交互式 Shell 默认 `set -m`（job control 开），`lastpipe` 不生效；脚本默认非交互且 job control 关，才生效。`shopt -s lastpipe` 后可以用 `shopt -q lastpipe` 检查，但无法直接检查 job control 对它的影响，用 `set +m` 显式关闭。

```bash
# 非交互脚本里
set +m
shopt -s lastpipe
printf 'a\nb\n' | while read -r line; do n=$((n + 1)); done
printf 'n=%d\n' "${n:-0}"
```

子 Shell 还会继承并隔离其他状态：

```bash
( cd /tmp; umask 077; trap 'echo child' EXIT; exit 0 )
pwd; umask          # 父 Shell 不受影响
```

`$BASHPID` 是当前 Shell/子 Shell 的 PID，`$$` 是启动这个 Shell 的 PID（在子 Shell 里不变）。判断是否在子 Shell：

```bash
printf '$$=%s BASHPID=%s\n' "$$" "$BASHPID"
( printf '$$=%s BASHPID=%s\n' "$$" "$BASHPID" )
```

`{ ...; }` 不 fork，`( ... )` fork；`{ cd /tmp; }` 会改变当前 Shell 的 cwd，`( cd /tmp )` 不会。`{` 后必须有空格，`}` 前必须有分号或换行，否则是语法错误。

判断「当前在第几层子 Shell」用 `BASH_SUBSHELL`：

```bash
printf 'top=%s\n' "$BASH_SUBSHELL"          # 0
( printf 'sub=%s\n' "$BASH_SUBSHELL" )      # 1
( ( printf 'sub2=%s\n' "$BASH_SUBSHELL" ) ) # 2
printf 'pids: $$=%s BASHPID=%s\n' "$$" "$BASHPID"
```

`ps --forest` 能直观看到父子链，`ps -o pid,ppid,cmd` 看 PPID。`bash -c '...'` 启动一个非交互子 Shell；`bash -l` 启动登录 Shell；`bash -i` 强制交互。这些选项会影响读哪些启动文件，进而影响 `PATH`、别名与 umask（见 [0.7](ch07.md)）。

**非科班补一层：`$$` 与 `$BASHPID` 的区别。** `$$` 是启动这个 Shell 的 PID，在子 Shell 里不变；`$BASHPID` 是当前进程的 PID，进子 Shell 会变。用这两个变量就能判断自己是不是在副本里，不必猜。

::: errata 关于子 Shell 与 lastpipe 的误解
1. **“子 Shell 是线程”**——不是。子 Shell 是 `fork` 出来的独立进程，有独立的 PID、变量表和文件描述符表；线程共享地址空间。
2. **“`shopt -s lastpipe` 一定生效”**——只在非交互 Shell 且 job control 关闭（`set +m`）时生效。交互式 Shell 默认 `set -m`。
3. **“`{ }` 也会 fork”**——`{ }` 在当前 Shell 执行，`( )` 才 fork；前者会改变当前 cwd、umask 等状态。
4. **“`$$` 在子 Shell 里会变”**——`$$` 不变，变的是 `$BASHPID`。
:::

### 0.5.12 小结

子 Shell 是 fork 出来的副本，变量、cwd、umask、trap 都隔离；`lastpipe` 只把最后一段留在当前 Shell，且受交互模式与 job control 限制。判断是否在副本里，看 `$BASHPID` 而不是 `$$`。如果只记住一件事，那就是：**管道里的每一段，默认都是另一个进程。**

::: method 即时自测 · 0.5.12
**Q1（记忆）** `lastpipe` 生效的两个条件是什么？

**Q2（辨析）** 在子 Shell 里，`$$` 与 `$BASHPID` 哪个会变？

**Q3（应用）** 交互式 Shell 里执行了 `shopt -s lastpipe`，为什么 `printf 'a\n' | while read ...; do n=1; done` 之后 `n` 还是 0？

::: sol 答案
**A1** 非交互 Shell，且 job control 关闭（`set +m`）。

**A2** `$BASHPID` 变，`$$` 不变。

**A3** 交互式 Shell 默认 `set -m`，job control 开启，`lastpipe` 不生效；先 `set +m` 再试。
:::
:::

## 0.5.13 `tee` 与日志分流 {#sec-0.5.13}

这一节回答：`tee` 的选项不多，默认行为有哪些坑？多个消费者时，谁拖慢谁？
0.5.6 会写 `cmd | tee log`，这一节只管两件事：它的写入是串行的，以及退出码到底代表谁。


::: preview 先抓住一件事
`tee` 对每个输出各写一份，写入是串行的；一个消费者不读，整个 `tee` 会被拖住。`tee` 的退出码只代表它自己，进程替换里的失败也传不回来。
:::

`tee` 把 stdin 复制到每个文件参数和 stdout。它的选项不多，但默认行为有坑：

| 选项 | 作用 |
|:--|:--|
| `-a` / `--append` | 追加而不是截断 |
| `-i` / `--ignore-interrupts` | 忽略 `SIGINT` |
| `-p` | 对非管道输出诊断错误（GNU） |
| `--output-error[=MODE]` | `warn`、`warn-nopipe`、`exit`、`exit-nopipe` |
| `--help`/`--version` | 标准 |

`tee` 的退出码是它自己的，不是上游命令的。`./deploy.sh | tee deploy.log` 的 `$?` 是 `tee` 的 0，即使 `deploy.sh` 失败。正确写法是先取 `PIPESTATUS[0]`：

```bash
#!/usr/bin/env bash
set -uo pipefail
log=${LOG_FILE:-/var/log/deploy.log}
{
    printf '== %s start ==\n' "$(date -Is)"
    ./deploy.sh "$@"
} 2>&1 | tee -a "$log"
st=("${PIPESTATUS[@]}")
printf '== %s exit=%d ==\n' "$(date -Is)" "${st[0]}" | tee -a "$log"
exit "${st[0]}"
```

这里故意不 `set -e`：开了 `set -e` + `pipefail`，管道失败会在 `st=...` 之前退出，日志缺少结束行。需要严格失败时，用 `if ! ...; then` 包住并显式记录，或在管道后立即 `set +e`。

`tee` 还能分流给多个消费者：

```bash
# 一份进文件，一份交给 logger 进 syslog/journald
./app 2>&1 | tee -a /var/log/app.log >(logger -t app)

# 一份原文，一份压缩
./app 2>&1 | tee >(gzip > /var/log/app.log.gz) > /var/log/app.log
```

`>(logger)` 是进程替换，`tee` 把它当成第二个文件写。进程替换的退出码拿不到，`logger` 失败不会让 `tee` 失败；需要保证日志送达时，用 `logger` 的同步模式或先写文件再异步投递。两条输出的时序也可能不同，排查顺序问题时不要依赖。

`tee` 写普通文件失败（磁盘满、权限）默认会报错并继续/退出，具体取决于 `--output-error`；写管道失败（下游关闭）默认可能忽略。需要精确控制时显式指定 `--output-error=exit`，并检查 `tee` 的退出码。

**非科班补一层：`tee` 的写入是串行的。** 它读一块，先写第一个输出，再写第二个；不是内核帮你广播。某个消费者不读，它的管道缓冲区先满，`tee` 阻塞在那里，其他消费者也拿不到更多数据。所以“同时给多个消费者”并不是免费的。

::: errata 关于 tee 边界的误解
1. **“`tee` 会保留上游退出码”**——不会；`tee` 返回自己的状态，上游状态在 `PIPESTATUS[0]`。
2. **“进程替换里的消费者失败会让 `tee` 失败”**——不会；`>(logger)` 的退出码拿不到，失败可能被静默忽略。
3. **“`tee` 写多个输出互不影响”**——写入串行，慢消费者会通过背压拖住整个 `tee`。
4. **“`tee -a` 和 `>>` 完全一样”**——`tee -a` 是 `tee` 自己以追加方式打开每个文件；`>>` 是 Shell 打开 stdout，两者的错误处理与作用域不同。
:::

### 0.5.13 小结

`tee` 把一份输入串行写到多个输出，慢消费者会拖住所有人；它的退出码只代表自己，进程替换里的失败也不会传回来。需要可靠日志时，先写本地文件，再异步投递。如果只记住一件事，那就是：**`tee` 是分流器，不是退出码的保管员。**

## 0.5.14 `/dev/null`、`/dev/stdin` 与特殊 fd 路径 {#sec-0.5.14}

这一节回答：`/dev/stdout` 和 `2>&1` 差在哪？`/dev/null` 与 `2>&-` 又差在哪？
前两节把重定向与 here-string 用顺了，这一节专门分辨 `/dev/stdout`、`/dev/null` 与 `2>&-`——看起来一样，内核里完全不同。


::: preview 先抓住一件事
`/dev/stdout` 是重新 `open` `/proc/self/fd/1`，`2>&1` 是复制 fd。`/dev/null` 让写入成功但被丢弃，`2>&-` 是关闭 fd，后续写会得到 `EBADF`。
:::

`/dev/null`、`/dev/zero`、`/dev/full` 是字符设备。`/dev/stdin`、`/dev/stdout`、`/dev/stderr` 在 Linux 上是指向 `/proc/self/fd/N` 的符号链接。它们的语义与普通文件不同，重定向到它们时要理解「打开」发生了什么。

| 路径 | 读 | 写 | 典型用途 |
|:--|:--|:--|:--|
| `/dev/null` | 立即 EOF | 丢弃，成功 | `> /dev/null 2>&1` |
| `/dev/zero` | 无限零字节 | 丢弃 | `dd if=/dev/zero` |
| `/dev/full` | 无限零字节 | `ENOSPC` | 测试写失败 |
| `/dev/stdin` | 当前 fd 0 | 取决于 fd 0 | `cmd < /dev/stdin` |
| `/dev/stdout` | 取决于 fd 1 | 当前 fd 1 | `cmd > /dev/stdout` |
| `/dev/stderr` | 取决于 fd 2 | 当前 fd 2 | `cmd 2> /dev/stderr` |
| `/dev/fd/N` | 重新打开 fd N | 重新打开 fd N | 进程替换、`exec` |
| `/proc/self/fd/N` | 同上 | 同上 | Linux 特有 |

`2>/dev/null` 与 `2>&-` 不同。前者打开 `/dev/null` 并让 fd 2 指向它，后续写成功但被丢弃；后者关闭 fd 2，后续写返回 `EBADF`，程序可能报错或崩溃。需要「静音」时用 `/dev/null`，需要「让程序知道没有 stderr」时才关闭。

`2>/dev/stdout` 与 `2>&1` 的差别：

- `2>&1` 复制 fd 1 的 `struct file`，共享偏移、flags，且不依赖 `/proc`；
- `2>/dev/stdout` 重新打开 `/proc/self/fd/1` 指向的目标，得到新的 `struct file`，偏移可能独立。如果 fd 1 已关闭或目标不可打开（例如已删除的临时文件），会失败。

在容器、chroot、`/proc` 未挂载的环境里，`/dev/stdout` 可能不存在或指向错误；脚本里优先 `2>&1`。

`/dev/stdin` 也有类似问题：`cmd < /dev/stdin` 重新打开当前 stdin 的目标，而不是复制 fd 0。如果 stdin 是一个已经读到一半的文件，重新打开会从偏移 0 开始（新 `struct file`），而不是接着读。需要「接着读」时用 `<&0` 或 `exec 3<&0`。

`exec 3<file` 在当前 Shell 打开一个只读 fd，之后可以用 `read -u 3` 或 `cat <&3`：

```bash
exec 3< /etc/hosts
while IFS= read -r line <&3; do printf '%s\n' "$line"; done
exec 3<&-
```

`read -u 3` 与 `<&3` 都会从 fd 3 读，且共享偏移；`cat <&3` 会读走剩余全部内容。`exec {fd}<file` 自动分配 ≥10 的 fd，避免和 0/1/2/3 冲突：

```bash
exec {in}< /etc/hosts
printf 'fd=%d\n' "$in"
cat <&"$in"
exec {in}<&-
```

`exec 3<>file` 以读写方式打开，读和写共享同一个文件偏移。读一行后写回，会从「读到的位置」开始覆盖，而不是追加；一个经典例子把 `This is a test line` 写进第二行中间，留下 `ine.` 这样的残片。需要「读后追加」时先 `lseek` 到末尾（Shell 做不到，改用 C/Python），或干脆用 `>>` 另开一个 fd。

关闭 fd 后重新打开同一路径，`>` 会重新截断：

```bash
exec 3>f; printf 'one\n' >&3; exec 3>&-
exec 3>f; printf 'two\n' >&3; exec 3>&-
cat f          # 只有 two
```

`lsof -a -p $$ -d0,1,2` 能列出当前 Shell 的标准 fd；加上 `3,6,7` 能看到脚本自定义的 fd。`-a` 是「与」运算，少了它会把 `-p` 与 `-d` 当成「或」，输出全系统的 fd。

`/dev/fd/N` 在 Linux 上通常等价于 `/proc/self/fd/N`，但打开它会复制 fd 的 flags（除 `O_CLOEXEC`），并可能改变 `FD_CLOEXEC`。不要把 `/dev/fd/3` 当成「fd 3 的别名」做权限判断，它是一次新的 `open`。

**非科班补一层：设备文件也有主次设备号。** `/dev/null`、`/dev/zero`、`/dev/full` 是字符设备，内核用主设备号和次设备号找到对应驱动。`/dev/stdout` 不是设备，是 procfs 提供的符号链接；打开它和打开字符设备走的是两条路径。`ls -l /dev/null` 里日期前面的 `1, 3` 就是设备号，它和文件大小不是一回事。

::: errata 关于特殊 fd 的误解
1. **“`/dev/stdout` 就是 `2>&1`”**——前者重新 `open` 路径，后者复制 fd；`/proc` 没挂载或 fd 1 已关闭时，前者会失败。
2. **“`2>/dev/null` 和 `2>&-` 一样”**——前者写成功但丢弃，后者关闭 fd，后续写返回 `EBADF`。
3. **“`/dev/fd/3` 是 fd 3 的别名”**——它是一次新的 `open`，偏移和 flags 可能独立；要共享偏移用 `<&3`。
4. **“`exec 3<>file` 读和写各有偏移”**——同一个 fd 只有一个偏移，读一行再写会从读到的位置覆盖，不是追加。
:::

### 0.5.14 小结

`/dev/null` 是“写了就丢”，`/dev/full` 是“写就报 ENOSPC”，`/dev/stdout` 是重新打开当前 fd 1；`2>&1` 则是复制 fd。关闭 fd 和指向黑洞是两件事，前者会让程序拿到 `EBADF`。如果只记住一件事，那就是：**路径是重新打开，`>&` 是复制 fd。**

## 0.5.15 缓冲、TTY 与 `stdbuf` {#sec-0.5.15}

这一节回答：`stdbuf` 为什么救不了所有程序？它到底改了哪一层？
0.5.7 会判断什么时候该关颜色、什么时候输出错乱，这一节给出缓冲分几层、`stdbuf` 动的到底是哪一层。


::: preview 先抓住一件事
stdio 缓冲由 libc 管理；`stdbuf` 通过 `LD_PRELOAD` 在程序启动时替换缓冲设置。它只对动态链接、使用 stdio 的程序有效，对静态链接、setuid、直接 `write(2)` 的程序无效。
:::

C 标准库的 stdio 有三种缓冲：

| 模式 | 何时默认 | 行为 |
|:--|:--|:--|
| 全缓冲 `_IOFBF` | stdout 不是 tty（管道、文件） | 攒满缓冲区（glibc 通常 4096/8192）才 `write` |
| 行缓冲 `_IOLBF` | stdout 是 tty | 遇到换行就 `write` |
| 无缓冲 `_IONBF` | stderr | 每次写入都 `write` |

这解释了两个现象：

1. 程序输出到管道后「卡住」：日志在 stdio 缓冲区里，没攒满就不写，下游 `grep` 一直等。
2. `tail -f` 看不到最新日志：同上；Python 需要 `-u` 或 `PYTHONUNBUFFERED=1`。

```bash
# 强制行缓冲；只对动态链接、使用 stdio 的程序有效
stdbuf -oL -eL ./app 2>&1 | grep ERROR

# 强制无缓冲
stdbuf -o0 -e0 ./app

# 用 pty 让程序以为自己在终端里
script -q -c './app' /tmp/typescript
unbuffer ./app | grep ERROR       # expect 包提供
```

`stdbuf` 的原理是 `LD_PRELOAD=libstdbuf.so`，在程序启动时替换 stdio 的缓冲设置。它**对静态链接、setuid、直接使用 `write(2)` 的程序无效**；`LD_PRELOAD` 在安全执行模式下被忽略。程序自己调用 `setvbuf` 时，`stdbuf` 也可能被覆盖。

在程序内部设置缓冲：

```c
setvbuf(stdout, NULL, _IOLBF, 0);   /* 行缓冲 */
setvbuf(stdout, NULL, _IONBF, 0);   /* 无缓冲 */
fflush(stdout);                     /* 立即写出 */
```

`grep` 有 `--line-buffered`，`awk` 可以 `fflush()`，Python 用 `-u`，`perl` 用 `$|=1`。这些是「让程序自己配合」，比 `stdbuf` 可靠。

TTY 检测影响颜色与交互：

```bash
test -t 1 && echo "stdout is a tty"
test -t 2 && echo "stderr is a tty"
```

`ls --color=auto`、`grep --color=auto`、`git` 都用 `isatty(1)` 决定是否上色；输出到管道/文件时自动关闭。要在保存的日志里保留颜色：

```bash
grep --color=always ERROR app.log | less -R
```

`NO_COLOR` 约定：非空时程序应关闭颜色（见 no-color.org）；`CLICOLOR=0`、`TERM=dumb` 也有类似效果。写脚本时不要假设有 tty：cron、CI、systemd 都没有，交互式提示会挂起或读到 EOF。

**非科班补一层：`LD_PRELOAD` 是什么。** 动态链接器在加载程序前，可以先加载一个共享库；`libstdbuf.so` 就是这样插进来的。它只能改 libc 的 stdio 设置，改不了静态链接、setuid 程序，也改不了直接调用 `write(2)` 的代码。

::: errata 缓冲与 TTY 的五个误解
1. **「`stdbuf` 对所有程序有效」**——只对动态链接、使用 stdio 的程序；静态/setuid/直接 `write` 的无效。
2. **「stderr 总是无缓冲」**——C stdio 的 stderr 默认无缓冲，但程序可以 `setvbuf` 改；Shell 的 `echo >&2` 走的是 `write`。
3. **「输出到文件后颜色丢了是程序坏了」**——程序按 `isatty` 关闭颜色；用 `--color=always` 或 `FORCE_COLOR`。
4. **「`tail -f` 能立刻看到所有日志」**——上游可能全缓冲；用 `stdbuf -oL` 或程序自己的 flush。
5. **「`script` 只是录屏」**——它分配 pty，改变程序的缓冲与颜色行为；录出来的文件还带控制字符。
:::

### 0.5.15 小结

`stdbuf` 靠 `LD_PRELOAD` 改 libc 的 stdio 缓冲，所以对静态链接、setuid、直接 `write(2)` 的程序无能为力。TTY 检测同时决定缓冲和颜色，CI、cron、systemd 里都没有 TTY。如果只记住一件事，那就是：**先确定程序用的是 stdio 还是 `write(2)`，再决定 `stdbuf` 有没有用。**

## 0.5.16 实验：`dup2`、管道与 `SIGPIPE` 的证据 {#sec-0.5.16}

这一节回答：怎样把前面几条结论变成自己能复现的证据？

::: preview 先抓住一件事
三个实验分别看重定向的 `openat`→`dup2`→`close`、`SIGPIPE` 的发生点、`/proc` 里的 fd 与偏移。它们不要求背输出，只要求你能指出“哪一行证明了哪条结论”。
:::

`strace` 是系统调用跟踪器，它把进程发起的 `openat`、`dup2`、`write` 逐条打印出来。

**非科班补一层：`strace` 看的是系统调用，不是函数调用。** libc 的 `printf` 最后也会落到 `write`，但 `strace` 只显示内核边界上的那一步。`-f` 跟子进程，`-e trace=...` 只看关心的调用，`-yy` 把 fd 显示成路径。

### 实验一：看重定向如何改写 fd 表

```bash
strace -f -e trace=openat,dup,dup2,dup3,close,pipe,pipe2 \
    -o /tmp/redir.trace \
    bash -c 'echo out; echo err >&2' > /tmp/out.txt 2>&1
grep -E 'out\.txt|dup|close\(3\)' /tmp/redir.trace | tail -20
cat /tmp/out.txt
```

预期能看到类似（fd 号与是否用 `dup3` 因 bash 版本而异）：

```text
openat(AT_FDCWD, "/tmp/out.txt", O_WRONLY|O_CREAT|O_TRUNC|O_CLOEXEC, 0666) = 3
dup2(3, 1)                              = 1
close(3)                                = 0
dup2(1, 2)                              = 2
```

读法：`openat` 返回 3，`dup2(3,1)` 让 fd 1 指向文件，`close(3)` 释放临时 fd，`dup2(1,2)` 让 stderr 复制 stdout 的目标。把顺序换成 `2>&1 > /tmp/out.txt`，会看到 `dup2(1,2)` 在前、`openat` 在后，stderr 仍指向终端。`-f` 跟随子进程，`-yy` 能把 fd 显示成路径。

### 实验二：观察 `SIGPIPE`

```bash
strace -f -e trace=write,close,pipe,pipe2 -o /tmp/pipe.trace \
    bash -c 'yes | head -n 1'
grep -E 'SIGPIPE|write\(1' /tmp/pipe.trace | tail -10
```

预期：

```text
write(1, "y\n", 2)                      = 2
--- SIGPIPE {si_signo=SIGPIPE, si_code=SI_USER, si_pid=..., si_uid=...} ---
+++ killed by SIGPIPE +++
```

`head` 读一行后关闭读端，`yes` 下一次 `write` 触发 `SIGPIPE`。上面第一行 `write(1, "y\n", 2)` 是 `head` 把读到的行写到终端；SIGPIPE 那一行才来自 `yes` 向管道写。如果给 `yes` 加 `trap '' PIPE`，信号被忽略，`write` 返回 `EPIPE`：

```bash
bash -c 'trap "" PIPE; yes | head -n 1; echo rc=$?'
```

### 实验三：`/proc` 里的 fd 与偏移

```bash
exec 3< /etc/hosts
ls -l /proc/$$/fd/3
cat /proc/$$/fdinfo/3
lsof -a -p $$ -d0,1,2,3 2>/dev/null || true
exec 3<&-
```

`fdinfo` 里的 `pos` 是当前偏移，`flags` 是八进制 `O_*` 标志。用 `exec 3<` 打开后读几行，再看 `pos` 会前进；`exec 3<&-` 关闭后，`/proc/$$/fd/3` 消失。`lsof -a` 的 `-a` 是 AND，少了它会把 `-p` 与 `-d` 当成 OR。

::: errata 关于 strace 实验的误解
1. **“strace 输出每次都一样”**——bash 版本、是否用 `dup3`、fd 编号都会变；看的是顺序和语义，不是固定行号。
2. **“不加 `-f` 也能看到子进程”**——管道和重定向常发生在子进程里；不加 `-f` 会漏掉关键调用。
3. **“`SIGPIPE` 是一行系统调用”**——它是信号行。`strace` 用 `--- SIGPIPE ---` 标出，随后可能显示 `+++ killed by SIGPIPE +++`。
4. **“`-yy` 只改显示，不改行为”**——它把 fd 翻译成路径，方便读；不会改变程序的系统调用。
:::

### 0.5.16 小结

三个实验把“重定向改 fd 表”“SIGPIPE 终止写入者”“fd 有偏移”从结论变成可观察的证据。`strace` 看系统调用边界，`-f` 跟子进程，`-yy` 显示路径。如果只记住一件事，那就是：**遇到 fd 或退出码问题，先 strace，再猜。**

::: method 即时自测 · 0.5.16

## 0.5.17 三个可运行脚本 {#sec-0.5.17}

这一节回答：三个脚本各自把哪些结论压成了可复用的工程模式？

::: preview 先抓住一件事
`logwrap.sh` 保留上游退出码，`fd-guard.sh` 备份并恢复 fd、处理信号清理，`fanout.sh` 用 FIFO 把一份输入分给多个消费者。三个脚本都围绕 fd、`PIPESTATUS` 和 `trap`。
:::

**非科班补一层：`trap` 是什么。** `trap` 让 Shell 在收到信号或退出时执行一段代码；`EXIT` 在脚本退出时跑，`INT`/`TERM` 捕获 Ctrl-C 和 `kill`。清理逻辑放在 `EXIT`，信号处理器只负责 `exit 130/143`，这样不会递归。

### 脚本一：`logwrap.sh`——保留上游退出码的日志包装

```bash
#!/usr/bin/env bash
# logwrap.sh — 把命令的 stdout/stderr 同时写到终端与日志，并保留退出码
# 用法: logwrap.sh COMMAND [ARG...]
set -uo pipefail

if (( $# == 0 )); then
    printf 'usage: %s COMMAND [ARG...]\n' "${0##*/}" >&2
    exit 2
fi
log=${LOG_FILE:-./run.log}

{
    printf '== %s start cmd=%q ==\n' "$(date -Is)" "$*"
    "$@"
} 2>&1 | tee -a -- "$log"

st=("${PIPESTATUS[@]}")
printf '== %s end rc=%d ==\n' "$(date -Is)" "${st[0]}" | tee -a -- "$log"
exit "${st[0]}"
```

关键点：`set -uo pipefail` 故意不加 `-e`，否则管道失败会在记录结束行之前退出。`PIPESTATUS[0]` 是花括号组的退出状态，也就是 `"$@"` 的状态。`tee -a` 写日志失败不会改变上游状态，需要单独检查时可以看 `st[1]`。`"$*"` 只用于日志展示，参数边界会丢；真正执行用 `"$@"`，不会被拆开。

### 脚本二：`fd-guard.sh`——备份/恢复 fd 与信号清理

```bash
#!/usr/bin/env bash
# fd-guard.sh — 把命令输出重定向到日志，退出/中断时恢复原 stdout/stderr
# 用法: fd-guard.sh LOG COMMAND [ARG...]
set -euo pipefail

log=${1:?usage: fd-guard.sh LOG COMMAND [ARG...]}
shift
(( $# > 0 )) || { printf 'missing command\n' >&2; exit 2; }

exec 3>&1 4>&2
cleanup() {
    local rc=$?
    trap - EXIT INT TERM
    exec 1>&3 2>&4
    exec 3>&- 4>&-
    printf 'restored rc=%d\n' "$rc" >&2
    exit "$rc"
}
trap cleanup EXIT
trap 'exit 130' INT
trap 'exit 143' TERM

exec >>"$log" 2>&1
printf '== %s start\n' "$(date -Is)"
"$@"
printf '== %s done\n' "$(date -Is)"
```

`exec 3>&1 4>&2` 先把原 stdout/stderr 存到 3/4，再把 1/2 接到日志。`cleanup` 首行保存 `$?`、先 `trap -` 防止递归，再恢复并关闭 3/4。信号处理器只负责 `exit 130/143`，清理统一在 `EXIT` 里做。`exec >>` 用追加，避免每次运行覆盖历史日志。

### 脚本三：`fanout.sh`——命名管道与并发消费者

```bash
#!/usr/bin/env bash
# fanout.sh — 用两个 FIFO 把一份输入同时交给 grep 与 wc
# 用法: fanout.sh SRC OUTDIR
set -euo pipefail

src=${1:?usage: fanout.sh SRC OUTDIR}
out=${2:?usage: fanout.sh SRC OUTDIR}
[[ -r $src ]] || { printf 'not readable: %s\n' "$src" >&2; exit 2; }
mkdir -p -- "$out"

tmp=$(mktemp -d "${TMPDIR:-/tmp}/fanout.XXXXXX")
cleanup() { rm -rf -- "$tmp"; }
trap cleanup EXIT
trap 'exit 130' INT
trap 'exit 143' TERM

mkfifo -- "$tmp/errors" "$tmp/all"
grep -E 'ERROR|FATAL' <"$tmp/errors" >"$out/errors.log" &
p_err=$!
wc -l <"$tmp/all" >"$out/count" &
p_cnt=$!

if ! tee -- "$tmp/errors" "$tmp/all" <"$src" >/dev/null; then
    printf 'tee failed (consumer gone?)\n' >&2
    kill "$p_err" "$p_cnt" 2>/dev/null || true
    wait "$p_err" "$p_cnt" 2>/dev/null || true
    exit 1
fi
wait "$p_err" "$p_cnt"

printf 'errors=%s lines=%s\n' \
    "$(wc -l <"$out/errors.log")" "$(cat -- "$out/count")"
```

三个进程并发：两个消费者先打开 FIFO 读端并阻塞，`tee` 打开写端后开始复制。`tee` 写两个 FIFO，任一消费者提前退出都会让它收到 `SIGPIPE`/`EPIPE`，脚本按失败处理并杀掉另一个消费者，避免留下孤儿。`cleanup` 只删临时目录，不删输出；输出路径用 `--` 防止以 `-` 开头。这个脚本在源文件很大、消费者处理速度不同时会体现背压：慢的一方会让 `tee` 的写阻塞，快的一方先读完也不会丢数据。

::: errata 关于三个脚本的误解
1. **“`logwrap.sh` 应该加 `set -e`”**——加了会在管道失败时提前退出，结束行来不及写；它只用 `set -uo pipefail`，再手动取 `PIPESTATUS[0]`。
2. **“`fd-guard.sh` 可以先关备份 fd 再恢复”**——不行；先 `exec 3>&-` 再 `exec 1>&3` 会报 `Bad file descriptor`，必须先恢复 1/2，再关 3/4。
3. **“`fanout.sh` 的消费者退出后不用管”**——`tee` 会收到 `SIGPIPE`/`EPIPE`，脚本要杀掉并 `wait` 另一个消费者，避免孤儿进程。
4. **“FIFO 能无限缓冲”**——FIFO 和管道一样有容量，慢消费者会通过背压拖住 `tee`。
:::

### 0.5.17 小结

三个脚本分别把退出码、fd 生命周期、并发分流压成了模板：日志包装取 `PIPESTATUS[0]`，fd 守卫先备份再恢复，FIFO 分流要处理慢消费者和孤儿。它们都建立在同一张 fd 表上。如果只记住一件事，那就是：**脚本里的每个 fd 和每个子进程，都要有明确的关闭与等待路径。**

::: method 即时自测 · 0.5.17
**Q1（记忆）** `logwrap.sh` 为什么用 `set -uo pipefail`，而不是 `set -euo pipefail`？

**Q2（辨析）** `fd-guard.sh` 里 `trap cleanup EXIT` 与 `trap 'exit 130' INT` 各自负责什么？

**Q3（应用）** 如果先执行 `exec 3>&-`，再执行 `exec 1>&3`，会发生什么？为什么？

::: sol 答案
**A1** `set -e` 会在管道失败时立即退出，结束行和 `PIPESTATUS` 保存都来不及执行；脚本要自己取状态并写结束行。

**A2** `EXIT` 负责统一清理：保存 `$?`、恢复 1/2、关闭 3/4、退出；`INT` 只把 Ctrl-C 转成退出码 130，让 `EXIT` 去做清理。

**A3** 会报 `Bad file descriptor`。fd 3 已经关闭，`1>&3` 没有可复制的目标；备份 fd 必须在恢复完成后再关闭。
:::
:::

## 0.5.18 陷阱清单 {#sec-0.5.18}

这一节回答：哪些坑最容易在真实脚本里反复出现？

::: preview 先抓住一件事
三组陷阱分别关于重定向副作用、管道退出码、fd 与缓冲边界。看到症状先对到组，再回对应小节，不要从头重读整章。
:::

**非科班补一层：这一节不需要额外先修。** 把三组陷阱当成提交脚本前的三个问题：目标文件确认了吗？退出码取对了吗？fd 和子进程都收尾了吗？

::: errata 关于重定向顺序与副作用的误解
1. **`2>&1 >file` 与 `>file 2>&1` 不同**——前者 stderr 留在终端，后者进文件；顺序决定 `dup2` 的目标。
2. **`>file` 在命令执行前就截断**——命令失败也会留下空文件；不要用「失败所以没动」做假设。
3. **`cmd > cmd2` 会覆盖可执行文件**——`ls > less` 是真实事故；如果当前目录有名为 `less` 的可执行文件，它会被清空。重定向前先确认目标不是命令/设备。
4. **`> list 2> list` 不是合并**——两次独立 `open` 会各自截断、各自偏移，输出交错甚至互相覆盖；用 `> list 2>&1` 或 `&>`。
:::

::: errata 关于管道与退出码的误解
1. **管道只传 stdout**——stderr 不会进入下游；要合并必须在上游写 `2>&1`，`|&` 是简写。
2. **管道每段在子 Shell**——`while read` 里的变量修改不回传；用 `< <(...)`、`lastpipe`（需 `set +m`）或命令替换。
3. **`tee` 返回自己的状态**——`cmd | tee log` 的 `$?` 不是 `cmd` 的；取 `PIPESTATUS[0]` 或开 `pipefail`。
4. **`PIPESTATUS` 会被下一条命令覆盖**——必须紧接着赋值：`st=("${PIPESTATUS[@]}")`。
5. **`SIGPIPE`/141 不一定是 bug**——`yes | head` 的正常结束就是 141；`pipefail` 下要显式接受或改设计。
:::

::: errata 关于 fd 语义与缓冲的误解
1. **`stdbuf` 不能救所有程序**——只对动态链接、用 stdio 的程序有效；静态、setuid、直接 `write` 的无效。
2. **`/dev/stdout` 不等于 `2>&1`**——前者重新 `open` 路径，后者复制 fd；`/proc` 未挂载、fd 已关闭时会失败。
3. **`exec` 不是启动新 Shell**——它替换当前 Shell 的命令或只改 fd 表；`exec 3>file` 的效果一直留到关闭或脚本退出。
:::

### 0.5.18 小结

三组陷阱覆盖重定向副作用、管道退出码、fd 与缓冲边界；它们不是新知识，而是前面结论的反面。每次写脚本前扫一遍，比出事后再 `strace` 便宜。如果只记住一件事，那就是：**先确认目标、再确认退出码、最后确认 fd 收尾。**

**Q2（辨析）** `2>&1 >file` 与 `>file 2>&1` 的 stderr 分别去哪？

**Q3（应用）** 脚本里 `./app | tee app.log` 之后 `$?` 是 0，但 `./app` 失败了；给出修复。

::: sol 答案
**A1** 必须确认重定向目标不是命令、配置或设备节点；`>` 会静默覆盖已存在的文件。

**A2** 前者 stderr 留在终端，后者 stderr 进 `file`；关键是 `2>&1` 复制的是当时的 fd 1 目标。

::: ex 例 0.5.1 · `2>&1 >file` 与 `>file 2>&1` 差在哪 {#ex-0.5.1}
两条命令只差顺序，结果一个是「错误进终端、正常进文件」，另一个是「两者都进文件」。

先猜：为什么顺序会改变结果？

判读：重定向按**从左到右**对 fd 表做复制。`2>&1` 让 2 号槽指向「此刻 1 号槽指向的东西」（还是终端），随后 `>file` 只改 1 号槽；反过来 `>file 2>&1` 先把 1 号槽指向文件，再让 2 号槽复制 1 号槽，于是两者都进文件。fd 表记的是「当时指向」，不是名字绑定。

**判据**：`ls -l /proc/$$/fd` 看 1、2 两个槽是否指向同一个 inode。

## 0.5.19 本章小结 {#sec-0.5.19}

这一节回答：两遍读完之后，这一章到底留下了什么？

::: preview 先抓住一件事
第一遍让你会用 fd 表写对命令，第二遍让你用 `dup2`、`PIPE_BUF`、`SIGPIPE` 解释边界；最后用实验、脚本和陷阱清单把知识压成能力。
:::

第一遍先会用：把 fd 表画出来，用“下标指向一次打开”解释 `2>&1` 的顺序。再学会 here-doc 的引号、管道只连 stdout、子 Shell 丢变量、`tee` 吞退出码、TTY 决定缓冲与颜色。这一遍的目标不是背语法，而是能写对一条命令，并在出错时知道先看哪一格。

第二遍看内核与边界：`dup2` 复制的是指向关系，两个 fd 共享偏移。`O_CLOEXEC` 防的是 `fork+exec` 之间的 fd 泄漏。管道是 64 KiB 的内核缓冲区，`PIPE_BUF` 只管单次写的原子性，`SIGPIPE` 是下游关闭的正常信号。`lastpipe`、`/dev/stdout`、`stdbuf` 的边界，都是这张 fd 表在不同层的表现。

最后压成能力：三个 `strace` 实验把结论变成证据，三个脚本把模式变成代码，陷阱清单把事故变成检查项。两遍不是重复，而是“先用起来，再看清底层”。逐项自检去 [学习目标自检表](ch05-checklist.md)，不要在这里打勾。如果只记住一件事，那就是：**重定向和管道都是对 fd 表的操作；先画表，再写命令，最后看退出码。**

::: method 即时自测 · 0.5
**Q1** `cmd >out 2>&1` 与 `cmd 2>&1 >out` 的 stderr 分别去哪？画出 fd 表变化。

**Q2** `set -o pipefail` 后，`grep pattern huge.log | head -n 1` 返回 141。这是 bug 吗？脚本里应该怎么处理？

**Q3** 下面这段为什么最后输出 0？改成两种能输出 2 的写法。


**Q4** `./app | tee app.log` 之后 `$?` 是 0，但 `./app` 实际上失败了。解释原因并给出修复。

::: sol 答案
**A1** `>out 2>&1`：先把 fd 1 指向 out，再让 fd 2 复制 fd 1，stderr 进 out。`2>&1 >out`：先把 fd 2 复制到 fd 1 当前目标（终端），再把 fd 1 改成 out，stderr 留在终端。关键是 `2>&1` 复制的是「当时」fd 1 的目标。

**A2** 不是 bug。`head` 读够一行就退出，`grep` 继续写时收到 `SIGPIPE`，退出码 141。脚本里如果允许下游提前退出，临时 `set +o pipefail`，或检查 `PIPESTATUS` 并接受 141；如果不允许，说明管道设计有问题，应让上游支持提前终止。

**A3** 管道最后一段 `while` 在子 Shell 执行，`n` 的修改只发生在副本。修复：① `while ... done < <(printf ...)`；② `shopt -s lastpipe`（非交互、job control 关闭时）；③ 让子 Shell 输出计数，父 Shell 用 `$(...)` 接收。

**A4** `$?` 是 `tee` 的退出码，不是 `./app` 的。修复：用 `PIPESTATUS[0]` 取上游状态，或 `set -o pipefail` 让管道整体返回非零；但要注意 `set -e` 下会提前退出，需在清理逻辑里处理。
