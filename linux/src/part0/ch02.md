上一章把系统分成内核、libc、应用三层。这一章把镜头拉近到最上面一层：你面对的终端窗口，以及窗口里那个等待输入的 Shell。

很多人把「终端」和「Shell」当成一回事。实际排障时这个混淆很贵：终端卡死、Shell 配置错、命令本身失败，是三件不同的事。分清楚之后，你会知道该重启窗口、改 `.bashrc`，还是去查程序日志。

本章还会建立一套可持续的工作流。命令行的高效不来自背更多命令，而来自三件事：少打字（历史与补全）、不丢上下文（tmux）、能安全地试错（作业控制与可恢复的编辑）。

## 0.2.1 键盘到进程：tty、pty 与终端模拟器 {#sec-0.2.1}

这一节回答：你敲下的一个字符，从键盘到 Shell 的 `read` 之间经过哪几层？`Ctrl-C` 与 `Ctrl-D` 又是在哪一层被翻译成动作的？

::: preview 先抓住一件事
终端窗口不是 Shell，它只是一个持有 pty master 的普通程序；Shell 跑在 pty slave 上，两者之间隔着内核的行规程。回显、行缓冲、`Ctrl-C` 变 `SIGINT`、`Ctrl-D` 变 EOF，都是行规程做的。
:::

先看一个现象。在 `vim` 里按 `Ctrl-C`，多数时候它不会退出；在 bash 提示符下按同一个组合键，正在跑的命令立刻停下。同一个按键，两种结果。这说明翻译按键的不是你面前那个程序，而是中间还有一层。

::: def 定义 0.2.1 · 终端、tty 与 pty {#def-0.2.1}
**终端**（terminal）原本是带键盘和屏幕的硬件设备，负责把人输入的字符合成字节流，并把收到的字节流显示出来。**tty** 是内核里的终端设备抽象（Teletype 的历史名字），它负责行缓冲、回显、信号生成（如 `Ctrl-C`）等**行规程**（line discipline）。**pty**（pseudo-terminal）是一对虚拟设备：master 端由终端模拟器持有，slave 端表现得像一个真实终端，Shell 与程序打开的就是 slave。
:::

把这条链路按「代码跑在哪」拆开，只有四层：

| 层 | 跑在哪 | 负责什么 |
|:--|:--|:--|
| 终端模拟器 | 用户态，一个 GUI 或 TUI 程序 | 把按键写成字节，把收到的字节画到屏幕上 |
| pty master | 内核里的设备端，由模拟器打开 | 字节进出内核的入口 |
| 行规程 | 内核，附在 slave 一侧 | 回显、攒够一行再交、把 `Ctrl` 键翻译成信号或 EOF |
| pty slave + Shell | 用户态 | Shell 的 stdin/stdout，它以为自己面对的是真终端 |

今天的「终端窗口」其实是终端模拟器（GNOME Terminal、iTerm2、Windows Terminal、VS Code 内置终端）。它做三件事：把按键写成字节送到 pty master；从 master 读回字节并渲染；处理窗口大小变化并通知内核。Shell 并不知道自己在窗口里，它只知道自己的 stdin/stdout 是一个 tty。

<pre class="layout">
键盘/屏幕                用户态                        内核                        用户态
┌──────────┐   按键   ┌────────────────┐   write   ┌──────────────┐   read   ┌─────────┐
│ 终端模拟器 │ ───────→ │ pty master     │ ────────→ │ pty slave    │ ───────→ │ bash    │
│ (GUI)     │ ←─────── │ /dev/pts/ptmx  │ ←──────── │ /dev/pts/N   │ ←─────── │ + 子进程 │
└──────────┘   渲染   └────────────────┘   读取    │ + 行规程      │   写出   └─────────┘
                                                   └──────────────┘
                                          行规程负责：回显、行缓冲、Ctrl-C → SIGINT、
                                          Ctrl-Z → SIGTSTP、Ctrl-D → EOF
</pre>

这张图的关键在中间的内核部分：**终端行为不是 Shell 实现的**。你按 `Ctrl-C`，是行规程把字节 `0x03` 翻译成 `SIGINT` 发给前台进程组；你按 `Ctrl-D`，是行规程把「缓冲区为空时的 EOF」交给 `read`。Shell 只是这些机制的受益者。这也解释了为什么在 `vim` 里 `Ctrl-C` 不一定退出：`vim` 把终端切到原始模式，行规程的特殊字符处理被关掉了。

看自己的进程挂在哪个终端上：

<div class="terminal" data-title="bash · Ubuntu 24.04">
<pre><span class="p">&#36;</span> tty
/dev/pts/0
<span class="p">&#36;</span> ps -o pid,ppid,tty,stat,cmd -p &#36;&#36;
    PID    PPID TTY      STAT CMD
   4127    4120 pts/0    Ss   bash
<span class="p">&#36;</span> ps -o pid,ppid,tty,stat,cmd -t &#36;(tty)
    PID    PPID TTY      STAT CMD
   4127    4120 pts/0    Ss   bash
   4381    4127 pts/0    R+   ps -o pid,ppid,tty,stat,cmd -t /dev/pts/0
<span class="p">&#36;</span> ls -l /proc/&#36;&#36;/fd/0
lrwx------ 1 wang wang 64 Oct 17 10:12 /proc/4127/fd/0 -&gt; /dev/pts/0
</pre>
</div>

`tty` 输出 `/dev/pts/0`，说明这是一个 pty slave；如果在物理控制台上登录，会看到 `/dev/tty1` 这类名字。`ps` 的 `TTY` 列是 `pts/0`，`STAT` 里的 `Ss` 表示「会话首进程、可中断睡眠」。`/proc/$$/fd/0` 指向 `/dev/pts/0`，证明 Shell 的 stdin 就是这个终端。

远程登录多了一层：SSH 客户端在本地终端与远端 `sshd` 之间转发字节，`sshd` 在远端分配一个 pty，远端的 Shell 看到的是 `/dev/pts/N`。所以「本地终端卡住」和「远端 Shell 卡住」需要分别排查，中间可能断在 SSH、网络或远端 pty。

::: note 非科班补一层：为什么非要造一对 pty
Shell 只需要读写字节，理论上接一根管道也能工作。难处在于很多程序假设自己面对的是终端：`vim` 要关回显，`less` 要问窗口有多少行，`ssh` 要让 `Ctrl-C` 传到远端。这些操作只有终端设备才提供。pty 给了它们一个「看起来像终端」的对象，模拟器则在另一头替人按键。
:::

::: errata 关于终端链路的三个误解
1. **「终端就是 Shell」**——终端模拟器负责渲染与 pty，Shell 只是 pty slave 上的一个用户进程。终端卡死时，Shell 可能还活着。
2. **「`Ctrl-D` 是关闭终端」**——它是行规程的 EOF 字符：缓冲区为空时，让 `read` 返回 0。Shell 读到 0，才决定退出。
3. **「`Ctrl-C` 永远等于 `SIGINT`」**——行规程只在 `isig` 打开时翻译它。`vim` 把终端切到 raw 模式后，`Ctrl-C` 只是一个字节 `0x03`，由程序自己解释。
:::

### 0.2.1 小结

从按键到 `read`，字符经过模拟器、pty master、行规程、pty slave 四层，Shell 只在最后一层。回显、行缓冲、信号键都在内核里完成，所以程序能通过切换终端模式改变 `Ctrl-C` 的含义。如果只记住一件事，那就是：`Ctrl-C` 不是 Shell 的快捷键，是行规程把字节翻译成了信号。

**Q2（辨析）** `Ctrl-D` 在行中间按下和在空行按下，效果为什么不同？

**Q3（应用）** 同事说「终端卡死了，Shell 肯定崩了」。你用哪三条命令确认，先试哪个按键？

::: sol 答案

## 0.2.2 一条命令从回车到输出 {#sec-0.2.2}

这一节回答：你按下回车之后，bash 到底做了哪几件事？为什么 `cd` 不需要新进程，而管道却要两个？

::: preview 先抓住一件事
一条命令不是一次系统调用，而是一串动作：读行、切词、展开、查找、fork/exec、等待。内建命令跳过 fork，管道两端同时跑。
:::

先猜一下：敲一行命令再回车，中间会创建几个进程？答案取决于命令长什么样，但可以先记住一点：bash 不是把整行丢给内核就完事，它要自己先读、先拆、先替换。

以 `grep -n root /etc/passwd | head -3` 为例，交互式 bash 大致做六件事：

| 步骤 | 做什么 | 出问题时你看到 |
|:--|:--|:--|
| 1. 读取 | 行规程把整行交给 readline | `Ctrl-D` 退出、`Ctrl-C` 取消当前行 |
| 2. 解析 | 按 `;`、`\|`、`&&` 切成命令，识别重定向与引号 | 引号不配对时出现 `>` 续行提示 |
| 3. 展开 | 别名、大括号、波浪号、变量、命令替换、算术、通配符 | 通配符没匹配时字面保留（默认） |
| 4. 查找 | 判断内建/函数/外部命令，在 `$PATH` 中找可执行文件 | `command not found` |
| 5. 执行 | 管道两端各 fork 一个子进程，`dup2` 接好 fd，`execve` | `Permission denied`、`Exec format error` |
| 6. 等待 | 父 Shell `wait4`，收集退出码，设置 `$?` | 退出码非零，但你看不到原因 |

::: note 非科班补一层：fork 与 execve
`fork` 是「复制一份自己」：内核给新进程复制地址空间和打开的文件描述符，返回值区分父子。`execve` 是「换掉自己的内容」：把指定程序加载进当前进程，PID 不变，代码和数据全换。Shell 先用 `fork` 造一个空的自己，再用 `execve` 把它变成 `grep`。为什么不直接原地 `execve`？因为 Shell 自己还得活着，等命令结束后继续读下一行。
:::

两个常被忽略的事实：

- **内建命令不 fork**。`cd`、`export`、`umask`、`read` 必须改变当前 Shell 的状态，所以由 Shell 自己执行。如果 fork 一个子进程去 `cd`，子进程换了目录，父 Shell 还在原地，你看到的路径不会变。`/bin/cd` 不存在，`command -v cd` 会告诉你它是 builtin。
- **管道两端是并发执行的**。`grep` 与 `head` 同时启动，`head` 读够 3 行就退出，`grep` 后续的 `write` 会收到 `SIGPIPE`。这不是错误，是管道的工作方式：内核只提供一小段缓冲区，两头谁快谁慢由调度决定，不能假设「左边跑完才轮到右边」。详见 [0.5](ch05.md)。

`strace -f` 能看到 5、6 两步的真实系统调用：

```bash
# -f 跟子进程；-e 只看进程创建与执行
strace -f -e trace=clone,execve,wait4 bash -c 'grep -n root /etc/passwd | head -3'
```

输出里会有两次 `clone`（管道两端）、两次 `execve`（`grep` 与 `head`），以及父 Shell 的 `wait4`。这比任何文字描述都更能说明「管道不是一个命令，而是两个进程加一个内核缓冲区」。

::: intuition 为什么 Shell 要 fork 两次
管道需要两个进程同时读写同一个内核缓冲区。Shell 先创建两个子进程，各自把 stdin 或 stdout 接到管道的一端，再分别 `execve`。父 Shell 自己不参与数据搬运，只负责等待。这样 `grep` 与 `head` 的并发、退出码、信号都独立，Shell 不必理解文本内容。
:::

::: errata 关于命令执行的三个误解
1. **「内建命令也是 `/bin` 下的程序」**——`cd`、`export`、`umask` 没有独立可执行文件；`type cd` 会直接说它是 shell builtin。
2. **「管道是把左边的输出存成文件，再交给右边」**——两头是同时运行的两个进程，中间只有一小段内核缓冲区，没有临时文件。
3. **「`fork` 会把整个程序复制一遍，所以很慢」**——现代内核用写时复制（copy-on-write），先只复制页表，哪一页被改写才真正复制哪一页。
:::

### 0.2.2 小结

回车之后，bash 要读行、拆词、做展开、查名字，然后 fork/exec 并等待；六步里任何一步失败，你看到的报错都不一样。内建命令因为要改 Shell 自己的状态而不 fork，管道因为要并发搬数据而开两个进程。如果只记住一件事，那就是：命令不是「一句话」，而是一条由 Shell 编排出来的进程流水线。

::: method 即时自测 · 0.2.2
**Q1（记忆）** 六步里哪一步创建新进程？退出码是在哪一步被收进 `$?` 的？

**Q2（辨析）** 为什么 `cd` 不能写成一个独立的外部程序？

**Q3（应用）** `yes | head -3` 能正常结束，`yes` 最后收到的信号是什么？用 `strace -f` 能看到哪些调用？

::: sol 答案
**A1** 第 5 步执行时 `fork` 出子进程；第 6 步父 Shell 用 `wait4` 收集退出状态，写进 `$?`。
**A2** 外部程序只能改自己的进程状态。`cd` 要改的是调用者的当前目录，只有由 Shell 自己执行才有效。
**A3** 收到 `SIGPIPE`：`head` 读够 3 行退出，管道读端关闭，`yes` 继续 `write` 就触发。`strace -f -e trace=clone,execve,wait4` 能看到两端的 `clone`/`execve` 与父 Shell 的 `wait4`。
:::
:::

## 0.2.3 命令查找顺序：alias、函数、内建、PATH {#sec-0.2.3}

这一节回答：你敲的 `ls` 最后执行的是哪一个？为什么 `.bashrc` 里的 `alias` 在脚本里不生效？

::: preview 先抓住一件事
bash 按 alias → 函数 → 内建 → 哈希 → `$PATH` 的顺序找名字。前两层只活在当前 Shell 的内存里，所以脚本默认用不到。
:::

先跑一次 `type -a ls`（输出就在下面），你会看到同一个名字对应三样东西：一个别名、两个路径。到底用哪个，取决于下面这张表。

输入一个名字后，bash 按固定顺序解析，第一个命中就停：

| 顺序 | 类型 | 说明 |
|:--|:--|:--|
| 1 | **别名**（alias） | 仅交互式 Shell 默认展开；脚本里除非 `shopt -s expand_aliases`，否则不生效 |
| 2 | **函数** | 当前 Shell 定义的函数，优先于外部命令 |
| 3 | **内建命令**（builtin） | `cd`、`echo`、`printf`、`type`、`read`、`export` 等 |
| 4 | **哈希表** | bash 缓存上次找到的路径；`hash -r` 清空 |
| 5 | **`$PATH` 中的可执行文件** | 从左到右找第一个 |

<div class="terminal" data-title="bash · 判断一个名字是什么">
<pre><span class="p">&#36;</span> type -a ls
ls is aliased to `ls --color=auto'
ls is /usr/bin/ls
ls is /bin/ls
<span class="p">&#36;</span> type -a cd
cd is a shell builtin
<span class="p">&#36;</span> command -v grep
/usr/bin/grep
<span class="p">&#36;</span> command -V grep
grep is /usr/bin/grep
<span class="p">&#36;</span> type -a python3
python3 is /usr/bin/python3
python3 is /bin/python3
</pre>
</div>

`type -a` 列出所有匹配，顺序就是解析顺序；`command -v` 只给「会被执行的那个」，适合脚本判断；`command -V` 给人类可读的描述。不要用 `which` 做脚本判断：`which` 是外部命令，不认别名和函数，在不同发行版上行为还不一致。

`$PATH` 的两个安全细节：

- **不要把 `.` 放进 `PATH`**。否则在 `/tmp` 下执行 `ls`，可能运行攻击者放的 `./ls`。确实要运行当前目录的程序，写 `./prog`。
- **空路径分量等于当前目录**。`PATH=/usr/bin:` 末尾的空项会被解释为当前目录，等价于加了 `.`。用 `PATH=${PATH%:}` 之类的清理，或直接用绝对路径。

::: note 非科班补一层：别名为什么只在交互 Shell 生效
别名不是程序，是 Shell 内存里的一张替换表：读到一行的第一个词时，查表换掉再继续解析。bash 在非交互模式下默认关掉 `expand_aliases`，因为脚本是一边读一边执行的；如果前面的行定义了别名，后面的行可能在你意想不到的位置被替换掉。要在脚本里用，显式写 `shopt -s expand_aliases`，但更稳的做法是改用函数。
:::

别名适合交互，不适合脚本。下面这段 `.bashrc` 是常见配置，注意它只在交互式 Shell 生效：

```bash
# ~/.bashrc 片段：仅交互式 Shell 会读到这里
shopt -s checkwinsize          # 窗口大小变化后更新 LINES/COLUMNS
shopt -s histappend            # 多个终端追加历史，而不是互相覆盖

alias ll='ls -alF'
alias grep='grep --color=auto'
alias ..='cd ..'

# 函数优先于同名外部命令；给 mkdir 加「自动建父目录」
mkcd() {
    mkdir -p -- "$1" && cd -- "$1"
}
```

`alias grep='grep --color=auto'` 只影响交互输出，不影响脚本；`--color=auto` 在输出到管道时自动关闭颜色，避免把 ANSI 转义写进文件。这个细节在第 0.5 章讲缓冲与 TTY 时会再出现。

::: errata 关于命令查找的三个误解
1. **「alias 写进 `.bashrc`，脚本里也能用」**——非交互 Shell 默认不展开别名。脚本里用函数或完整命令，别依赖 alias。
2. **「`which` 能判断一个命令是什么」**——`which` 是外部程序，只查 `$PATH`，不认别名和函数，不同发行版行为还不一致；用 `type -a` 或 `command -v`。
3. **「装了新版本，bash 一定用新的」**——bash 会把上次找到的路径缓存进哈希表；同名程序换了位置，先 `hash -r` 再试。
:::

### 0.2.3 小结

bash 找名字时先看 Shell 内存里的别名与函数，再看内建，最后才查 `$PATH`；哈希表只是给最后一步加速。别名只服务交互，脚本要可预测，所以默认不展开。如果只记住一件事，那就是：想知道一个名字到底会执行什么，用 `type -a`，不要用 `which`。

**Q2（辨析）** `alias ll='ls -l'` 写在 `.bashrc` 里，`bash -c 'll'` 为什么报 `command not found`？

**Q3（应用）** 你把 `python3` 从 `/usr/local/bin` 挪走了，提示符下它仍指向旧路径。怎么确认、怎么修？

::: sol 答案

**A2** `bash -c` 是非交互 Shell，不读 `.bashrc`，而且默认不展开别名；两个原因叠加，`ll` 根本不存在。

:::

## 0.2.4 登录、非登录、交互、非交互：四象限与启动文件 {#sec-0.2.4}

这一节回答：同一个 `~/.bashrc`，为什么开终端窗口时读了，`ssh host cmd` 时却没读？

::: preview 先抓住一件事
启动文件由两个开关决定：登录与否、交互与否。两个开关组合出四种 Shell，各读不同的文件，其中有一种一个也不读；先判断自己在哪一格，再决定配置写哪里。
:::

先做一次对照：一次 `ssh host` 登录后跑 `echo $PATH`，一次直接 `ssh host 'echo $PATH'`。两行经常不一样。差别不在网络，而在远端 bash 把自己判定成了哪种 Shell。

两个维度是：**是不是登录 Shell**、**是不是交互式**。

| 类型 | 典型场景 | 读哪些文件（Ubuntu 24.04） |
|:--|:--|:--|
| 登录 + 交互 | 控制台登录、`ssh host`、`su -` | `/etc/profile` → `~/.bash_profile` 或 `~/.bash_login` 或 `~/.profile` |
| 非登录 + 交互 | 打开终端窗口、`bash`、`tmux` 新 pane | `/etc/bash.bashrc` → `~/.bashrc` |
| 非登录 + 非交互 | `bash script.sh`、`ssh host cmd` | 不读启动文件；只看 `BASH_ENV` |
| 登录 + 非交互 | `ssh host 'bash -l -c cmd'` | 读登录文件，但不读 `.bashrc`（除非 `.profile` 主动 source） |

四个常见困惑都能用这张表解释：

1. **`ssh host 'echo $PATH'` 的 PATH 和登录后不一样**。非交互非登录 Shell 不读 `/etc/profile`，只继承 sshd 给的环境。要固定环境，在 `~/.ssh/environment`（需 `PermitUserEnvironment yes`）或命令里显式 `source`。
2. **`~/.bashrc` 写了 `export`，cron 任务里却没有**。cron 不启动交互 Shell，也不读 `.bashrc`。在脚本里显式设置 `PATH`，或 `source` 一个环境文件。
3. **`su user` 后别名没了**多半是误解。`su user` 不带 `-` 是非登录**交互** Shell，仍会读 `~/.bashrc`，写在里面的别名不丢；只有把别名只写在 `/etc/profile` 这类登录文件里才会真的丢。`su - user` 才是登录 Shell。
4. **`sudo cmd` 找不到自己编译的程序**。`sudo` 默认用 `secure_path` 覆盖 `PATH`，`sudo -E` 通常绕不开它；可靠做法是用绝对路径，或把目录加进 sudoers 的 `secure_path`（有风险）。

::: note 非科班补一层：`BASH_ENV`
非交互 Shell 不读 `.bashrc`，但会看一个环境变量 `BASH_ENV`。它指向一个脚本文件，bash 启动后先把这个文件 source 进来，再执行你的命令。可以把它当成「给脚本准备的最小 `.bashrc`」：cron 和 `ssh host cmd` 想带几个环境变量，就写在这里；别名、提示符、补全不要放，非交互场景用不上。
:::

::: note 非科班补一层：`secure_path`
`secure_path` 是 `sudo` 在 sudoers 里预置的一条 `PATH`。执行命令前，sudo 用它替换掉你带来的 `PATH`，防止有人把同名程序放进自己的目录，再骗 root 去执行。代价是你自己编译的程序不在里面；用 `sudo ./prog`、写绝对路径，或把目录加进 `secure_path`（有风险）。
:::

判断当前 Shell 的类型：

```bash
# 登录 Shell 返回 login；非登录返回 non-login
shopt -q login_shell && echo login || echo non-login
# 交互式返回 i，非交互返回非 i
case $- in *i*) echo interactive ;; *) echo non-interactive ;; esac
# 当前 Shell 的 PID 与父进程
ps -o pid,ppid,cmd -p $$ -p $PPID
```

一个可维护的 `.bashrc` 结构：把「环境变量」和「交互体验」分开。环境变量放 `~/.profile`（登录时读一次），别名、提示符、补全放 `~/.bashrc`（每个交互 Shell 读）。这样 `ssh host cmd` 与非交互脚本不会因为加载了交互配置而变慢或报错。

::: errata 关于启动文件的三个误解
1. **「`ssh host cmd` 和登录后执行一样」**——它是非交互非登录 Shell，不读 `.bashrc`/`.profile`，`PATH` 与别名都可能不同。
2. **「登录 Shell 一定读 `.bashrc`」**——登录 Shell 读的是 `~/.profile`；Ubuntu 的 `.profile` 里恰好有一句 source `.bashrc`，这是发行版约定，不是 bash 的规定。
3. **「`ssh host cmd` 会读 `BASH_ENV`」**——bash 会读，但 `BASH_ENV` 得先被传到远端；sshd 默认不传，`AcceptEnv`/`SetEnv` 没配就看不到。
:::

### 0.2.4 小结

Shell 的启动文件不是一条清单，而是一张四象限表：登录与否决定读不读 profile，交互与否决定读不读 bashrc。判断错格子，就会出现「登录时好好的，cron 里就不行」。如果只记住一件事，那就是：先问这个 Shell 是谁启动的、要不要跟人交互，再去翻对应的文件。

::: method 即时自测 · 0.2.4

## 0.2.5 提示符、历史与高效编辑 {#sec-0.2.5}

这一节回答：怎样让提示符告诉你该知道的信息，又怎样少按几百次方向键？

::: preview 先抓住一件事
提示符是一段会被展开的字符串，历史是一份会被多个终端抢着写的文件，行编辑是 readline 提供的。三件事各配一次，之后每天省下的是成百上千次按键。
:::

常见的翻车现场：给提示符加了颜色，命令一长就换行错位，光标跑到上一行去改字。这不是终端坏了，是 `PS1` 里少写了一对 `\[ \]`。下面先从提示符的转义说起。

提示符 `$PS1` 是一段会被展开的字符串。常用转义：

| 转义 | 含义 | 例子 |
|:--|:--|:--|
| `\u` | 用户名 | `wang` |
| `\h` | 短主机名 | `lab` |
| `\w` | 当前目录（`~` 缩写） | `~/src/app` |
| `\W` | 当前目录的 basename | `app` |
| `\t` | 24 小时时间 | `14:03:22` |
| `\!` | 历史编号 | `1042` |
| `\$` | 普通用户 `$`，root `#` | `$` |

一个不花哨但信息够用的配置：

```bash
# ~/.bashrc：提示符与历史
PS1='\[\e[32m\]\u@\h\[\e[0m\]:\[\e[34m\]\w\[\e[0m\]\$ '
PS2='> '
# 命令耗时超过 2 秒时，在提示符前打印耗时
PROMPT_COMMAND='dur=$?; if (( dur != 0 )); then printf "[exit %d] " "$dur"; fi'

HISTSIZE=50000
HISTFILESIZE=100000
HISTCONTROL=ignoreboth:erasedups   # 忽略空格开头与重复命令
HISTIGNORE='ls:ll:cd:pwd:history'
shopt -s histappend cmdhist lithist
```

`\[ \]` 为什么要写：readline 靠数可见字符来判断光标在第几列。颜色转义 `\e[32m` 在屏幕上不占位，但字节是有长度的；不括起来，readline 会以为这一行比实际更长，命令超过一屏时换行就错位、光标乱跳。`\[` 和 `\]` 就是告诉它「这一段别数」。`PROMPT_COMMAND` 在每次显示提示符前执行，适合放轻量逻辑；不要在里面跑 `git status` 之类的重命令，大仓库会明显拖慢每次回车。

历史展开是提效最多的一组快捷键：

| 写法 | 展开成 | 说明 |
|:--|:--|:--|
| `!!` | 上一条命令 | `sudo !!` 是最常用的组合 |
| `!$` | 上一条命令的最后一个参数 | `mkdir a && cd !$` |
| `!*` | 上一条命令的全部参数 | |
| `!^` | 上一条命令的第一个参数 | |
| `!n` | 历史编号 n | `!1042` |
| `!-n` | 倒数第 n 条 | `!-2` |
| `!string` | 最近一条以 string 开头的命令 | `!git` |
| `^old^new` | 把上一条命令中的 old 换成 new | `^/tmp^/var/tmp` |

`Ctrl-R` 是反向增量搜索：按一次进入，输入片段，再按 `Ctrl-R` 跳上一个匹配，`Enter` 执行，`Ctrl-G` 取消。比翻历史快得多。`Alt-.`（或 `Esc .`）插入上一条命令的最后一个参数，连续按可以往前翻。

历史是文件，不是内存。默认退出时才写 `~/.bash_history`，多个终端会互相覆盖。`histappend` 解决的就是这件事：每个终端窗口退出时都会把内存里的历史写回去，默认是覆盖写，最后关的那个窗口会把别的窗口的记录抹掉；打开 `shopt -s histappend` 改成追加，几个窗口的命令才都能留下。`history -a` 立即追加当前会话的新命令；`history -w` 覆盖写整个历史。要删掉刚打错的一条（比如忘了加引号的密码），用 `history -d <n>`，再 `history -w`。

除了历史，readline 还提供一组光标与删除键；它们不进入历史，但能少按很多次退格：

| 按键 | 作用 |
|:--|:--|
| `Ctrl-A` / `Ctrl-E` | 跳到行首 / 行尾 |
| `Alt-B` / `Alt-F` | 按词后退 / 前进 |
| `Ctrl-U` / `Ctrl-K` | 删除光标到行首 / 行尾 |
| `Ctrl-W` | 删除光标前的一个词 |
| `Ctrl-Y` | 粘回最近一次删除的内容 |
| `Ctrl-L` | 清屏并保留当前行 |
| `Tab` / `Tab Tab` | 补全；第二次列出所有候选 |
| `Alt-?` | 列出当前位置的可能补全 |

`Tab` 补全由 bash 的补全系统提供，能补命令名、路径、变量、用户名和主机名；`complete -p git` 看某个命令的补全规则。补全行为可以在 `~/.inputrc` 里调，例如 `set completion-ignore-case on` 让路径补全忽略大小写，`set show-all-if-ambiguous on` 让第一次 Tab 就列出多个候选。`set -o vi` 则把行编辑切成 vi 键位，适合已经熟悉 vim 的人。

::: errata 关于提示符与历史的三个误解
1. **「`PS1` 里的颜色转义直接写就行，`\[ \]` 只是好看」**——不括起来，readline 会数错宽度，长命令换行错位、光标乱跳。
2. **「历史是所有终端共享、实时同步的」**——每个 Shell 各有一份内存副本，退出时才落盘；默认覆盖写，所以要 `histappend`。
3. **「`!!` 展开后还会让你确认」**——它直接替换并执行，`rm -rf` 也一样；按回车前先看清楚整行。
:::

### 0.2.5 小结

提示符告诉你「在哪、是谁」，历史告诉你「刚做过什么」，readline 让你在不离开主键区的情况下改这一行。三者都配置一次就长期受益，但都有同一个前提：知道它们各自把数据存在哪。如果只记住一件事，那就是：`\[ \]` 是给 readline 看的，`histappend` 是给多个终端看的。

::: method 即时自测 · 0.2.5
**Q1（记忆）** `\u`、`\h`、`\w`、`\W`、`\!` 各展开成什么？

**Q2（辨析）** 两个终端同时开着，在 A 里敲的命令，为什么 B 的 `history` 里看不到？

**Q3（应用）** 加了彩色提示符后，长命令换行错位。你改哪一处？

::: sol 答案
**A1** 用户名、短主机名、当前目录（`~` 缩写）、当前目录的最后一段、当前命令的历史编号。
**A2** 历史先是每个 Shell 进程的内存副本，退出时才写回 `~/.bash_history`；B 不会实时读 A 的内存。
**A3** 把每个颜色序列用 `\[` 和 `\]` 包起来，例如 `\[\e[32m\]`；再确认 `PS1` 末尾的 `\$ ` 在括号外。
:::
:::

## 0.2.6 作业控制最小集 {#sec-0.2.6}

这一节回答：一个终端里同时跑几个程序时，谁在前台、谁在后台、关掉窗口之后谁还活着？

::: preview 先抓住一件事
作业控制是 Shell 给同一会话里的进程组发信号的一套约定：`&` 放到后台，`Ctrl-Z` 挂起，`fg`/`bg` 切换。关终端会发 `SIGHUP`；`nohup`、`disown -h`、tmux 各自解决一层。
:::

先设想一个普通场景：你在编译一个大项目，`make` 已经跑起来了，但你还想同时 `tail` 日志。等它跑完再敲下一条，时间成本太高；作业控制就是为这种「一个终端干几件事」准备的。

作业控制让一个终端同时管理多个进程。核心只有五个动作：

| 动作 | 命令/按键 | 效果 |
|:--|:--|:--|
| 后台启动 | `cmd &` | 子进程进入后台，Shell 立即返回作业号与 PID |
| 挂起前台 | `Ctrl-Z` | 向前台进程组发 `SIGTSTP`，进程进入 `T` 状态 |
| 查看作业 | `jobs -l` | 列出作业号、状态、PID、命令 |
| 切到前台 | `fg %1` | 把作业 1 放到前台，继续运行 |
| 后台继续 | `bg %1` | 让停止的作业在后台继续 |

<div class="terminal" data-title="bash · 作业控制">
<pre><span class="p">&#36;</span> sleep 300 &amp;
[1] 4512
<span class="p">&#36;</span> jobs -l
[1]+  4512 Running                 sleep 300 &amp;
<span class="p">&#36;</span> sleep 600
^Z
[2]+  Stopped                 sleep 600
<span class="p">&#36;</span> jobs
[1]-  Running                 sleep 300 &amp;
[2]+  Stopped                 sleep 600
<span class="p">&#36;</span> bg %2
[2]+ sleep 600 &amp;
<span class="p">&#36;</span> fg %1
sleep 300
^C
<span class="p">&#36;</span> jobs
[2]+  Running                 sleep 600 &amp;
</pre>
</div>

`jobs` 输出里的 `+` 是「当前作业」，`-` 是「上一个作业」，不带 `%` 时 `fg`/`bg` 默认操作 `+`。`^Z` 是终端回显的 `Ctrl-Z`，不是命令。

::: note 非科班补一层：SIGHUP
SIGHUP 是挂断信号（hang up）。早年拔掉串口线，内核就给会话的控制进程发这个信号；今天关掉终端窗口，pty master 被关闭，效果一样。它的默认动作是终止进程，所以后台任务会跟着死。
:::

作业控制有几个边界：

- **只对当前 Shell 的作业有效**。在另一个终端里 `jobs` 看不到这些进程；要跨终端管理，用 `pgrep`/`ps` 或 tmux。
- **非交互 Shell 默认关闭作业控制**。脚本里 `cmd &` 仍然能后台运行，但没有 `jobs`/`fg` 的交互语义；需要时 `set -m`。
- **关闭终端会发 `SIGHUP`**。登录 Shell 退出时，会向它启动的作业发送挂断信号。`nohup cmd &` 让进程忽略 `SIGHUP` 并把输出写到 `nohup.out`；`disown -h %1` **只**标记「shell 退出时不发 SIGHUP」，作业仍在作业表里（`jobs` 可见、`kill %1` 可用）；`disown %1`（不带 `-h`）才从作业表移除。`setsid cmd` 让进程进入新会话，彻底脱离控制终端。
- **`Ctrl-Z` 不是终止**。它发的是 `SIGTSTP`，进程只是停止（`T` 状态），内存、PID、打开的文件都还在；要它继续用 `fg`/`bg`，要它结束用 `kill %1`（默认 `SIGTERM`）。

::: note 非科班补一层：`nohup` 与 `disown -h` 差在哪
两者都让进程不再因 Shell 退出而死，但改的层不同。`nohup` 改的是进程自己的信号处理：把 `SIGHUP` 设成忽略，并把 stdout 重定向到 `nohup.out`。`disown -h` 改的是 Shell 的记账：把这个作业标记成「退出时别给它发 `SIGHUP`」，进程本身没变，`jobs` 里还看得到，`kill %1` 也还能用。
:::

::: errata 关于作业控制的三个误解
1. **「`Ctrl-Z` 等于结束进程」**——它只是挂起（`SIGTSTP`），进程还在。要结束用 `kill`，要后台继续用 `bg`。
2. **「关掉终端，后台任务一定继续跑」**——默认会收到 `SIGHUP`。需要 `nohup`、`disown -h` 或 `setsid`，或者放进 tmux/systemd。
3. **「`nohup` 和 `disown -h` 是一回事」**——一个改进程的信号处理，一个改 Shell 的记账；前者还会重定向输出，后者连作业表都不动。
:::

### 0.2.6 小结

作业控制只管辖当前 Shell 的这一组作业：`&`、`Ctrl-Z`、`fg`、`bg` 都作用在作业号上，换个终端就看不见了。关终端会发 `SIGHUP`，所以想活得久，要么让进程忽略它（`nohup`），要么让 Shell 别发（`disown -h`），要么换一个不属于这个终端的会话（tmux、`setsid`）。如果只记住一件事，那就是：`Ctrl-Z` 是暂停，不是结束。

::: method 即时自测 · 0.2.6
**Q1（记忆）** `&`、`Ctrl-Z`、`jobs`、`fg`、`bg` 各自对进程做了什么？

**Q2（辨析）** `nohup sleep 300 &` 与 `sleep 300 &` 再 `disown -h %1`，进程层面的差别在哪？

**Q3（应用）** SSH 断线后你想让 `rsync` 继续跑。列出至少两种做法，并说明它们分别防住了哪一层。

::: sol 答案
**A1** `&` 直接放后台并给作业号；`Ctrl-Z` 给前台进程组发 `SIGTSTP` 暂停；`jobs` 只列状态；`fg` 把作业调回前台并 `SIGCONT`；`bg` 让停止的作业在后台继续。
**A2** `nohup` 把进程对 `SIGHUP` 的处理改成忽略，并重定向标准输出；`disown -h` 不改进程本身，只让当前 Shell 退出时不发 `SIGHUP`，进程的处置方式与输出位置都没变。
**A3** 放进 tmux：会话留在远端，pty 不随 SSH 关闭，程序完全不受影响；或用 `nohup`/`setsid` 让进程忽略 `SIGHUP` 或脱离控制终端，日志落文件。前者还能回来接着看，后者只能事后查日志。
:::
:::

## 0.2.7 vim 生存指南：够用的三十个操作 {#sec-0.2.7}

这一节回答：在一台只有 `vi` 的服务器上，怎样打开文件、改几行、保存退出，并且不把配置改坏？

::: preview 先抓住一件事
vim 是模式编辑器：同一个按键，在普通模式里是命令，在插入模式里才是文字。先记住 `Esc` 回普通模式、`i` 进插入模式、`:` 进命令行模式，再记保存与退出。
:::

vim 是 `vi` 的增强版；很多发行版把 `vi` 链接到 vim，所以两者用法基本一致。

作业控制解决的是“命令在不在跑”，这一节解决“文件怎么改”。先设想一个常见场景。你 `ssh` 到一台服务器，要改 `/etc/ssh/sshd_config` 里的一行。没有图形编辑器，`nano` 也未必安装，但 `vi` 几乎总在。目标不是成为 vim 高手，而是能完成这次修改，并且知道改错了怎么退回来。

vim 有三种常用模式，按键的含义随模式改变：

| 模式 | 怎么进入 | 按键的含义 |
|:--|:--|:--|
| 普通模式（normal mode） | 打开文件时默认在此；按 `Esc` 回来 | 字母是命令：`dd` 删行、`yy` 复制、`p` 粘贴 |
| 插入模式（insert mode） | 在普通模式按 `i`、`a`、`o` 等 | 字母就是文字，直接写进文件 |
| 命令行模式（command-line mode） | 在普通模式按 `:`、`/`、`?` | 底部出现一行，用来保存、退出、替换、查找 |

::: note 非科班补一层：模式就是按键的上下文
同一个 `d`，在插入模式里是字母，在普通模式里是“准备删除”的操作符，等下一个键告诉它删什么。`Esc` 的作用是把键盘从“写字”切回“下命令”，所以它不退出 vim，只退出当前模式。
:::

普通模式是待命的中枢，插入模式是打字的地方，命令行模式只在底部工作。普通模式可以进插入或命令行；插入与命令行都只能先按 `Esc` 回普通模式，再走另一条路。

先跑一遍最小闭环：`vim /tmp/demo.txt`，按 `i`，输入 `hello`，按 `Esc`，输入 `:wq` 回车。文件写好并退出。如果只想看看不改，打开后直接 `:q`；改乱了想全部放弃，按 `Esc` 后输入 `:q!`。

| 类别 | 操作 | 说明 |
|:--|:--|:--|
| 打开/保存 | `vim file`、`:w`、`:q`、`:wq`、`:q!` | `:q!` 放弃修改；`:w !sudo tee %` 提权保存 |
| 移动 | `h j k l`、`w`、`b`、`0`、`$`、`gg`、`G`、`:42` | 字符/词/行首尾/文件首尾/第 42 行 |
| 翻页 | `Ctrl-F`、`Ctrl-B`、`Ctrl-D`、`Ctrl-U` | 前后翻页、半页 |
| 插入 | `i`、`a`、`o`、`O` | 前插、后插、下方新行、上方新行 |
| 删除 | `x`、`dd`、`dw`、`d$`、`3dd` | 删字符、删行、删词、删到行尾、删 3 行 |
| 复制粘贴 | `yy`、`yw`、`p`、`P` | 复制行/词，粘贴到后/前 |
| 撤销重做 | `u`、`Ctrl-R` | 撤销、重做 |
| 查找 | `/pattern`、`n`、`N`、`?pattern` | 向下/向上查找，跳下一个/上一个 |
| 替换 | `:%s/old/new/g`、`:%s/old/new/gc` | 全文替换；`c` 逐条确认 |
| 可视选择 | `v`、`V`、`Ctrl-V` | 字符/行/块选择，再配合 `d`/`y` |
| 退出 | `ZZ`、`:x` | 保存并退出（与 `:wq` 类似） |

三个安全习惯：

1. **先看再改**。打开文件先 `:set number` 看行号，确认自己在改哪一段。
2. **不确定就 `u`**。vim 的撤销树很强，连续 `u` 能退回很多步；`Ctrl-R` 重做。
3. **权限不够不要硬写**。`:w !sudo tee %` 用 sudo 把当前缓冲区写到文件，适合改 `/etc` 下的配置；写完后 vim 会提示文件已变，按 `L` 重新加载。

第三条值得拆开看。普通的 `:w` 是让 vim 自己打开文件写入。写成 `:w !命令` 时，vim 把当前缓冲区从标准输入交给后面这条 shell 命令，由命令来决定怎么写。`%` 是 vim 的占位符，展开成当前文件名。`sudo tee 文件` 以 root 身份读标准输入，一份写进文件，一份写到标准输出。所以 `:w !sudo tee %` 等于“把缓冲区交给 root 的 tee，让它覆盖当前文件”。

这也解释了保存后的提示：磁盘上的文件已经被 root 改过，vim 手里的缓冲区还是旧的，两者对不上。按 `L`（load）从磁盘重新读入，之后 `:w` 才会恢复正常。文件名里有空格或特殊字符时，`%` 的展开可能被 shell 拆开。这种文件更稳的做法是 `sudoedit 文件`，或者退出后用 `sudo vim 文件`。

替换是最高频的批量操作。`:%s/old/new/g` 的范围是全文，`:%s/old/new/gc` 每条确认。`:'<,'>s/old/new/g` 只替换可视选择的行。`:%s/\s\+$//e` 删除行尾空白。正则语法与 `grep`/`sed` 有差异（vim 默认 magic 模式），复杂表达式先在副本上试。

`vimtutor` 是官方交互教程，花 30 分钟能覆盖上面大部分操作。比背命令表有效。

::: errata 关于 vim 的三个误解
1. **“打开 vim 就能直接打字”**——打开时在普通模式，字母是命令。按 `i` 看到 `-- INSERT --` 再输入；按 `Esc` 回到普通模式。
2. **“`Esc` 是退出 vim”**——它只结束当前模式，回到普通模式。退出要再输入 `:q`、`:wq` 或 `:q!`。
3. **“`:w !sudo tee %` 之后就万事大吉”**——文件已被 root 改写，但 vim 的缓冲区还是旧内容，而且文件仍可能是只读的。按 `L` 重新加载，确认内容后再继续编辑。
:::

### 0.2.7 小结

vim 把“移动与操作”和“输入文字”拆成不同模式，所以第一件事不是背命令，而是知道自己此刻在哪个模式。普通模式是中枢，`Esc` 回到这里，`:` 进入命令行；保存、退出、替换都在命令行完成。如果只记住一件事，那就是：先按 `Esc`，再想要做什么。

::: method 即时自测 · 0.2.7
**Q1（记忆）** 普通、插入、命令行三种模式各用什么键进入或返回？`:wq` 和 `:q!` 分别做什么？

**Q2（辨析）** 你在插入模式按 `Esc`，vim 没有退出。是 vim 卡住了吗？`:w !sudo tee %` 里的 `%` 又是什么？

**Q3（应用）** 你用普通用户打开 `/etc/ssh/sshd_config`，改完一行后 `:w` 提示只读。写出保存步骤，并说明保存后为什么要重新加载。

::: sol 答案
**A1** 打开文件在普通模式；`i`、`a`、`o` 进插入模式，`Esc` 回普通模式；`:` 进命令行模式，执行完回普通模式。`:wq` 保存并退出，`:q!` 放弃修改并退出。

## 0.2.8 tmux 最小集：让工作现场可恢复 {#sec-0.2.8}

这一节回答：SSH 断线或关掉终端之后，怎样让正在跑的命令和屏幕上的现场原样回来？

::: preview 先抓住一件事
tmux 把 Shell 放进一个由 tmux 服务进程持有的会话，终端窗口只是连上来看它的“显示器”。关窗口或断 SSH 只是断开连接，会话、窗口、pane 和里面的进程都还在；重新 `attach`（接回会话）就回到原样。
:::

tmux 是一个终端复用器（terminal multiplexer）。它让一个终端窗口里跑多个 Shell，并把这些 Shell 留在后台。

0.2.7 解决一个文件怎么改，tmux 解决整个工作现场怎么留住。先设想一个场景：你在跳板机上跑 `journalctl -f` 看日志，同时开着 `curl` 压测。网络一抖，SSH 断了，两个命令一起消失。tmux 解决的就是这件事，也顺带解决“一个终端里同时看日志和敲命令”。

tmux 把工作现场分成三层。**会话**（session）是一组窗口的容器，也是持久化的单位。**窗口**（window）是会话里占满屏幕的一页，可以来回切换。**面板**（pane）是窗口里切出来的一块，每块各跑一个 Shell。

它们都活在 tmux 服务进程里，而不是活在你当前的终端窗口里。

“Shell 跑在 pane 里，与终端窗口解耦”这句话需要落到实处。你开的终端窗口通过 pty 连到 tmux 客户端；tmux 服务进程另外创建一组 pty，Shell 跑在这些 pty 的 slave 端。关掉终端窗口，断的是客户端那一侧，服务进程和它手里的 pty 不受影响。SSH 断线也是同一回事：远端 `sshd` 关闭的是外层 pty，tmux 内部的 pty 还在。

::: note 非科班补一层：先记三层容器
session 是最大的容器，里面装 window；window 占满屏幕，里面可以切 pane；pane 才是 Shell 真正运行的地方。你看到的终端窗口只是接到 session 上的一个客户端，关掉它不会动容器里的东西。
:::

| 目的 | 命令 |
|:--|:--|
| 新建命名会话 | `tmux new -s work` |
| 列出会话 | `tmux ls` |
| 重新接入 | `tmux attach -t work` |
| 断开但保留 | `Ctrl-B` 然后 `d` |
| 杀死会话 | `tmux kill-session -t work` |
| 新建窗口 | `Ctrl-B c` |
| 切换窗口 | `Ctrl-B n` / `p` / `0`–`9` |
| 重命名窗口 | `Ctrl-B ,` |
| 垂直/水平分屏 | `Ctrl-B %` / `Ctrl-B "` |
| 在 pane 间移动 | `Ctrl-B` 方向键 |
| 放大当前 pane | `Ctrl-B z` |
| 关闭 pane | `Ctrl-B x` |
| 进入复制模式 | `Ctrl-B [`，方向键/PageUp 翻页，`q` 退出 |

一个典型工作流：

```bash
# 在跳板机上开一个持久会话
tmux new -s api-debug
# 窗口 0 跑日志
journalctl -u api -f
# Ctrl-B c 新建窗口 1，跑测试
curl -sS localhost:8080/health
# Ctrl-B % 分屏，右边开一个 shell 查进程
ps -eo pid,stat,pcpu,cmd --sort=-pcpu | head
# 下班或断网前：Ctrl-B d 断开；第二天 tmux attach -t api-debug
```

`Ctrl-B` 是默认前缀（prefix）。所有 tmux 快捷键都是“按前缀，再按一个键”：先按住 `Ctrl` 按一下 `B`，松开，再按 `d`、`c`、`%` 或方向键。前缀的作用是把“给 tmux 的命令”和“给 pane 里程序的按键”分开。没有它，tmux 无法知道你想让它切窗口，还是想把 `d` 打进 vim。

前缀可以改，但默认值在大多数机器上不用配置就能用。想看当前所有绑定，在 tmux 里按 `Ctrl-B ?`。想给 tmux 下命令，按 `Ctrl-B :` 进入 tmux 的命令行。若某个程序确实需要收到 `Ctrl-B`，连按两次前缀即可把一次 `Ctrl-B` 送进 pane。

一个够用的 `~/.tmux.conf`：

```bash
# ~/.tmux.conf：最小可用配置
set -g mouse on                 # 允许鼠标选 pane、滚轮翻页
set -g history-limit 50000      # 每个 pane 的滚动缓冲
set -g base-index 1             # 窗口从 1 开始编号
setw -g pane-base-index 1       # pane 从 1 开始编号
set -g escape-time 10           # 降低 vim 中 Esc 的延迟
set -g status-left '[#S] '
set -g status-right '%H:%M %d-%b'
```

`escape-time` 值得单独说。终端里的方向键、功能键往往以 `Esc` 开头（例如方向键上会发 `Esc [ A`）。tmux 收到一个 `Esc` 时，必须等一小段时间，判断它是“用户单独按了 Esc”，还是“一个转义序列的开头”。等待期间，这个 `Esc` 不会转给 pane 里的 vim。默认值偏大时，你在 vim 里按 `Esc` 回普通模式就会觉得明显延迟。调到 10 ms 通常够用，但链路很慢或还要用 `Alt` 组合键时，调得过小可能把组合键拆坏。

tmux 不是终端复用器的唯一选择（screen、zellij、abduco 都有）。它是 Ubuntu 仓库里默认可用、资料最多、与 systemd 不冲突的一个。把长任务放进 tmux 或 systemd，而不是 `nohup`，是更可维护的做法：前者能恢复现场，后者能自动重启与收集日志。

::: errata 关于 tmux 的三个误解
1. **“tmux 会话能扛机器重启”**——它只扛 SSH 断线与终端关闭。机器重启后 tmux 服务进程没了，会话也全丢；要跨重启保活，得靠 systemd 或重新拉起。
2. **“`Ctrl-B` 是发给 Shell 的按键”**——前缀被 tmux 自己消费。要往 pane 里送一个真正的 `Ctrl-B`，连按两次前缀。
3. **“`escape-time` 越小越好”**——太小会让 tmux 过早把 `Esc` 当成单独按键，`Alt` 组合键或慢链路下的功能键可能被拆坏；10 ms 是常见折中，不是固定答案。
:::

### 0.2.8 小结

tmux 把“工作现场”从终端窗口里搬进了一个独立服务进程：会话装着窗口，窗口装着 pane，Shell 和命令都活在 pane 里。断线只是 detach（断开但保留），`attach` 回来就能接着看。前缀 `Ctrl-B` 用来区分 tmux 命令与程序按键。如果只记住一件事，那就是：长任务放进 tmux，关窗口不等于杀进程。

**Q2（辨析）** 你关掉了运行 tmux 的终端窗口，里面的 `sleep 1000` 为什么还活着？如果直接关掉一个没跑 tmux 的终端，它为什么就死了？

**Q3（应用）** 你在 tmux 里用 vim，按 `Esc` 总有半秒延迟。先改哪一项配置？改得太小可能带来什么问题？

::: sol 答案
**A1** `tmux new -s work`、`tmux ls`、`tmux attach -t work`、`Ctrl-B d`。session 是持久化的工作区容器，window 是其中占满屏幕的一页，pane 是窗口里切分出的一个终端。
**A2** tmux 的 Shell 跑在 tmux 服务进程创建的 pty 上，外层终端窗口只是客户端；关窗口只断开客户端。普通终端的 Shell 直接跑在那个 pty 上，窗口关闭后 pty 被挂断，Shell 和作业收到 `SIGHUP`。

## 0.2.9 终端能力：`TERM`、`stty` 与行规程 {#sec-0.2.9}

这一节回答：为什么同一个程序在 SSH、tmux、管道里的行为不同？`Ctrl-C` 什么时候是信号、什么时候只是字节？怎样在脚本里安全地读密码，又不把终端留在坏状态？

::: preview 先抓住一件事
链路中间那层行规程，是内核里一段可配置的“输入预处理器”。`icanon`、`isig`、`echo`、`ixon` 这几个开关决定它攒不攒整行、翻不翻译信号键、替不替你回显、拦不拦 `Ctrl-S`。`stty` 改的就是这组开关，`vim` 和 `less` 靠改它们拿到逐键输入。
:::

0.2.8 的 tmux 又在这条链路上加了一层 pty，但行为差异的根源仍在行规程。键盘到 Shell 之间隔着 pty，pty 却不是一根直通的管子；中间那层**行规程**（line discipline）会先处理字节。它决定什么时候把输入交给 `read`，哪些字节要翻译成信号，以及是否把输入原样回显到屏幕。

行规程的行为由一组终端属性控制，这组属性叫 **termios**；`stty` 是读写这组属性的命令。`vim`、`less`、`ssh` 登录、`sudo` 读密码，全都在改这组属性。

换个说法：默认的行规程像一位“代收员”。你敲的字符先由它收下，攒够一行再交给程序。`Ctrl-C` 由它翻译成 `SIGINT`，`Ctrl-D` 由它翻译成 EOF；你敲的字符也由它替你回显。全屏程序不想要这位代收员，就会把相应开关关掉，自己直接读每一个按键。下面这些 flag 就是开关的名字。

opost -olcuc -ocrnl onlcr -onocr -onlret -ofill -ofdel nl0 cr0 tab0 bs0 vt0 ff0
isig icanon iexten echo echoe echok -echonl -noflsh -xcase -tostop -echoprt
echoctl echoke -flusho -extproc
</pre>
</div>

逐段读：

| 行 | 字段 | 含义 | 改它会怎样 |
|:--|:--|:--|:--|
| 1 | `speed` / `rows` / `columns` | 波特率与窗口大小 | `stty rows 50 cols 160` 可临时改 |
| 2 | `intr` / `quit` / `susp` | 生成 `SIGINT`/`SIGQUIT`/`SIGTSTP` 的键 | 改成 `^A` 会让 Ctrl-C 失效 |
| 2 | `erase` / `kill` / `werase` | 退格、删整行、删词 | `erase = ^H` 适配老终端 |
| 2 | `eof` | 行首按它产生 EOF | `Ctrl-D` 不是「关闭」，是「读返回 0」 |
| 2 | `min` / `time` | 非规范模式下的读语义 | `min 1 time 0` 是逐字节阻塞读 |
| 3 | `-icanon` | 关闭行缓冲 | 每个字符都交给 `read`，Shell 行编辑失效 |
| 3 | `echo` / `-echo` | 是否回显 | 读密码时关掉 |
| 3 | `isig` | 是否把 `intr` 等键变成信号 | 关掉后 Ctrl-C 只是字节 `0x03` |
| 3 | `ixon` | `Ctrl-S`/`Ctrl-Q` 流控 | 关掉后 `Ctrl-S` 可用于前向搜索 |
| 4 | `opost` / `onlcr` | 输出时把 `\n` 转成 `\r\n` | 关掉后输出会「阶梯状」 |
| 4 | `tostop` | 后台进程写终端是否发 `SIGTTOU` | 默认关，打开会停住后台输出 |

这张表说明：Shell 的行编辑、`Ctrl-C`、密码不回显，都是 termios 参数，不是 Shell 的魔法。表里的 `-icanon` 表示“关掉 `icanon` 的情形”。在 `stty -a` 的输出里，带 `-` 前缀表示关闭，不带表示打开。

::: note 非科班补一层：四个开关与 raw 模式
`icanon` 管“要不要攒够一行”，`isig` 管“信号键翻不翻译”。`echo` 管“内核替不替你回显”，`ixon` 管“`Ctrl-S`/`Ctrl-Q` 流控开不开”。四个都打开，就是默认的加工模式（cooked mode）：你敲完一行按回车，程序才收到整行。关掉它们，再把输入输出转换（如 `icrnl`、`opost`）也关掉，就是 raw 模式。每个键立刻、原样到达程序，屏幕上的每个字符也由程序自己画。
:::

`vim` 进入全屏时切到接近 raw 的模式，就是为了拿到这种逐键、无回显的输入。如果 `icanon` 还开着，你按 `j` 要再按回车，vim 才会收到。如果 `echo` 还开着，你按的键会先被内核回显一遍，和 vim 自己画的屏幕叠在一起。如果 `isig` 还开着，你想用 `Ctrl-C` 做别的操作时，进程会先被 `SIGINT` 杀掉。

`less` 只需要逐键翻页，通常用 cbreak 模式（一种非规范模式，保留信号键）。它保留部分信号处理，不必像 vim 那样彻底。两者退出时都会把保存的 termios 设置写回去，终端才恢复正常。它们保存与恢复的，正是 `stty -g` 输出的那串十六进制。

`stty -g` 是「保存现场」的标准做法：

```bash
#!/usr/bin/env bash
# ask-pass.sh —— 读一个不回显的输入，退出时恢复终端
set -euo pipefail
saved=$(stty -g)
trap 'stty "$saved"' EXIT INT TERM
stty -echo
printf 'token: '
IFS= read -r token
printf '\n'
stty "$saved"
trap - EXIT INT TERM
[[ -n $token ]] || { echo "empty token" >&2; exit 1; }
printf 'read %d bytes\n' "${#token}"
```

关键点是 `trap` 要在 `stty -echo` **之前**安装：脚本被 Ctrl-C 打断时，`EXIT` 与 `INT` 都会触发恢复；否则终端会一直不回显，用户只能 `reset`。`IFS= read -r` 保留反斜杠与首尾空格；`read -s` 是 bash 的语法糖，效果类似，但它不会替你处理异常退出的恢复。

`TERM` 是一个终端类型名，不是终端程序的路径。它告诉程序“我这台终端支持哪些转义序列”，程序再去 terminfo 数据库查表。`TERM=dumb` 时，`tput` 与颜色库会退化；`TERM` 写错时，`less` 翻页会乱码。

```bash
printf 'TERM=%s\n' "${TERM:-unset}"
tput colors          # 256 或 8；dumb 下报错
tput cup 3 10        # 光标移到第 3 行第 10 列
tput el              # 清到行尾
infocmp -1 xterm-256color | sed -n '1,12p'
toe -a | head        # 系统里有哪些 terminfo 条目
```

`tput` 读 terminfo 数据库，不直接写死转义。写跨终端脚本时用它，而不是 `printf '\033[2J'`；后者在 `TERM=dumb` 或非 ANSI 终端上会打印乱码。`infocmp` 是反向工具：把某个条目的能力逐项列出，排查「为什么这个键在我的终端里不工作」时很有用。

::: method 实验 0.2-A · 看清 tty、管道与 pty 的差别
目的：用同一段判断在三种 stdin 下运行，证明「是不是终端」是文件描述符属性，不是 Shell 的猜测。

```bash
#!/usr/bin/env bash
# tty-check.sh —— 判断 stdin/stdout 是不是终端
set -euo pipefail
for fd in 0 1 2; do
    if [[ -t $fd ]]; then
        printf 'fd%d=tty(%s) ' "$fd" "$(readlink -f "/proc/$$/fd/$fd")"
    else
        printf 'fd%d=notty ' "$fd"
    fi
done
printf '\n'
```

三种跑法：

```bash
./tty-check.sh                       # 终端里：三个 fd 都是 tty
./tty-check.sh < /dev/null           # stdin 不是 tty
./tty-check.sh | cat                 # stdout 不是 tty
script -qec './tty-check.sh' /dev/null   # 在伪终端里跑，stdout 又是 tty
stty -a < /dev/null                  # 报 Inappropriate ioctl for device
```

预期：第一行三个 `tty`；第二行 `fd0=notty`；第三行 `fd1=notty`（`cat` 那一端是管道）；`script` 那行恢复成全 `tty`；最后一条 `stty` 直接失败，因为 `/dev/null` 不是终端，没有 termios 可读。这个实验解释了 `ls --color=auto`、`grep --color=auto`、`git` 的分页为什么在管道里自动关闭：它们都在做 `isatty(1)` 判断。
:::

::: errata 终端层的五个误解
1. **「`Ctrl-D` 是关闭终端」**——它是行规程的 `eof` 字符；在行首让 `read` 返回 0，Shell 据此退出。终端没关，pty 还在。
2. **「`Ctrl-C` 一定发 `SIGINT`」**——`-isig` 或 raw 模式下它只是字节 `0x03`，由程序自己解释；`vim` 插入模式就是这种状态。
3. **「`stty -echo` 只影响当前命令」**——它改的是终端设备状态；进程异常退出没恢复，整个终端都不回显，要 `stty sane` 或 `reset`。
4. **「`TERM` 只是给 `ls` 上色用的」**——`less`、`vim`、`tmux`、`top` 都按 `TERM` 选转义序列；设错会让全屏程序花屏。
5. **「管道里的程序行为和终端里一样」**——`isatty` 为假时，缓冲模式、颜色、行编辑、信号键全部可能不同。
:::

### 0.2.9 小结

行规程先替程序加工输入：攒行、翻译信号键、回显、流控，全由 termios 开关控制。`stty` 读写这组开关，`stty -g` 保存现场；`vim`/`less` 关掉其中几项，是为了拿到逐键、无回显、可自行解释的输入。如果只记住一件事，那就是：终端行为异常时，先看 `stty -a`，再想哪个程序改了它。

::: method 即时自测 · 0.2.9
**Q1（记忆）** `icanon`、`isig`、`echo`、`ixon` 各自管什么？打开和关闭时行为差在哪？

**Q2（辨析）** 在 bash 提示符下按 `Ctrl-C` 会取消当前命令，在 vim 插入模式按同一个键却不会退出 vim。用 termios 开关解释这两件事。

**Q3（应用）** 你的脚本用 `stty -echo` 读口令，用户按 `Ctrl-C` 中断后终端不再回显。脚本哪里写错了？现在怎么把终端救回来？

::: sol 答案
**A1** `icanon` 管行缓冲：开着一行一行交，关掉逐字节交；`isig` 管信号键：开着把 `Ctrl-C` 翻成 `SIGINT`，关掉只当字节；`echo` 管内核回显：开着显示输入，关掉用于密码；`ixon` 管流控：开着 `Ctrl-S` 暂停输出、`Ctrl-Q` 恢复，关掉这两个键才能给程序用。

**A3** 恢复命令要放在 `stty -echo` 之前安装，例如 `saved=$(stty -g); trap 'stty "$saved"' EXIT INT TERM; stty -echo`；trap 写在关回显之后，脚本被中断时就来不及恢复。终端已经坏掉时，在看不见输入的情况下盲打 `stty sane` 或 `reset` 回车。

## 0.2.10 readline 键位表与练习 {#sec-0.2.10}

这一节回答：除了方向键，命令行还有哪些不离开主键区的编辑动作？怎样把这些动作练成肌肉记忆？

::: preview 先抓住一件事
readline 是 bash 的行编辑器，只管“这一行文本”的光标、删除、历史和补全，不解析命令内容。高频动作只有移动、删除、粘贴、搜索四组；先练这四组，就能覆盖日常大多数编辑。
:::

0.2.9 讲的是按键怎么从终端到达程序；readline 决定这些按键在命令行里做什么。先想象一个场景：你敲了一长串 `scp` 命令，发现路径写错了一个目录。手移向方向键、按住左箭头慢慢退，既慢又容易退过头。readline 提供的编辑动作，让你在手指不离主键区的情况下改完这一行。

readline 是 bash 用来编辑命令行的库，也是一套按键到函数的映射。它拿到的是你按下的键，维护的是一行文本和一个光标位置；你按回车，它才把这行字符串交给 bash 去解析和执行。所以它不知道 `git` 的子命令有哪些，也不知道引号有没有配对。前者由 bash 的补全函数补上，后者由 bash 的语法分析负责。

这带来两个实用结论。第一，readline 的编辑键在别的程序里也常能用，例如 `python` 的交互解释器、`psql`。前提是它们也链接了 readline。第二，编辑键只能改“字面文本”，不能改命令的含义。`Ctrl-W` 删掉一个词，不会帮你补上引号，也不会让一条语法错误的命令变对。

这张表说明：**高频动作只有十几组**，其余是补全与历史。先练「移动 + 删除 + 粘贴 + 搜索」四组，就足以覆盖日常 90% 的编辑。方向键能用，但手移出主键区的那一下，就是效率差距。

几个容易忽略的细节：

- `Ctrl-W` 与 `Alt-Backspace` 的分词规则不同。前者按空白切，后者按 readline 的 word 定义（标点也算分隔），删路径时结果常不一样。
- `Ctrl-Y` 粘的是 **kill ring**，不是系统剪贴板。`Ctrl-U`、`Ctrl-K`、`Ctrl-W` 都会把删掉的内容放进去；连续 `Alt-Y` 可以轮换更早的内容。
- `Ctrl-S` 默认被终端流控（`ixon`）吃掉，按下去像卡住。要启用前向搜索，先 `stty -ixon`，或把 `ixon` 关掉写进 `.bashrc`。
- `Ctrl-X Ctrl-E` 会调用 `$VISUAL`/`$EDITOR`，适合写长命令、复杂 `for` 循环；保存退出后命令回到提示符，不会立即执行，还能再改。
- `Alt-#` 把当前行变成注释并回车，适合「先记下来，稍后再跑」。

::: note 非科班补一层：`Ctrl-W` 与 `Alt-Backspace` 的分词
两个键都叫“删一个词”，但“词”的定义不同。`Ctrl-W` 绑定 `unix-word-rubout`，只把空白当作分隔。`Alt-Backspace` 绑定 `backward-kill-word`，按 readline 的词表切。字母和数字算词，`/`、`.`、`-` 这类标点算分隔。

以 `git checkout feature/login` 为例，光标在行尾。按 `Ctrl-W` 会删掉整个 `feature/login`，因为它前面是空格。按 `Alt-Backspace` 只删掉 `login`，留下 `feature/`。删一整段路径用 `Ctrl-W` 快，删路径里的最后一段用 `Alt-Backspace` 准。

Alt 键在终端里通常以 `Esc` 前缀发送，所以 `Alt-Backspace` 也可能被写成 `Esc` 再按退格。tmux 的 `escape-time` 设得过大时，这个组合会显得迟钝；这一点和 0.2.8 是同一个原因。
:::

`.inputrc` 是 readline 的配置，对所有使用 readline 的程序生效（bash、`psql`、`python` 的 REPL 等）：

```bash
# ~/.inputrc —— readline 行为
# 补全忽略大小写
set completion-ignore-case on
# 第一次 Tab 就列候选，而不是响铃
set show-all-if-ambiguous on
set menu-complete-display-prefix on
# 不要响铃；补全列表带颜色
set bell-style none
set colored-stats on
# 粘贴多行时不立即执行（bash 5.1+ 默认）
set enable-bracketed-paste on
set history-size 50000
# 组合键等待时间，毫秒
set keyseq-timeout 50

# 让 Ctrl-S 做前向搜索，而不是被流控吃掉
"\C-s": forward-search-history

# 宏：Ctrl-X Ctrl-S 在行首插入 sudo（不要占用 Ctrl-J，它是回车）
"\C-x\C-s": "\C-asudo \C-e"
```

`bind -x` 与宏不同：`bind -x` 是 bash 命令，要写在 `.bashrc` 里（例如 `bind -x '"\C-g": git status --short'`），执行 shell 命令并把输出插到提示符上方，不修改当前行；`.inputrc` 里只能定义按键宏。`"\C-x\C-s": "\C-asudo \C-e"` 会先跳到行首、插入 `sudo `、再回行尾。改完 `.inputrc` 后按 `Ctrl-X Ctrl-R` 立即生效，不用重开终端。

`set enable-bracketed-paste on` 值得单独说：它让终端用 `ESC[200~`/`ESC[201~` 包裹粘贴内容，readline 知道这是一次粘贴，不会把其中的换行当成「执行」。关掉它，粘贴多行命令会一行行执行，粘错一个字符就可能执行到一半。老终端或 `screen` 不支持括号粘贴时，readline 会退化为普通插入。

::: method 实验 0.2-B · 五分钟键位练习
目的：不背表，用五个小任务把动作连成肌肉记忆。每个任务都在新终端里做，做完 `Ctrl-C` 清行。

```bash
# 1) 移动与删除：把下面这行改写成只保留 /var/log/nginx
echo /etc/nginx /var/log/nginx /usr/share/nginx
#   用 Alt-B 跳到 /usr/share/nginx 前，Ctrl-K 删掉；再 Alt-B 到 /etc/nginx，Ctrl-W 删掉

# 2) kill ring：删三段，再按顺序粘回
printf 'alpha beta gamma\n'
#   Ctrl-W 三次，再 Ctrl-Y 三次（或 Alt-Y 轮换），观察粘回顺序

# 3) 历史参数：复用上一条命令的最后一个参数
ls -lh /var/log/syslog
cat Alt-.          # 插入 /var/log/syslog，不用手打

# 4) 编辑长命令：用编辑器写一个循环
Ctrl-X Ctrl-E
for f in /var/log/*.log; do printf '%s %s\n' "$(wc -l <"$f")" "$f"; done
#   保存退出，命令回到提示符；确认无误再回车

# 5) 搜索：Ctrl-R 输入 "tar"，反复 Ctrl-R 跳到更早的匹配，Ctrl-G 取消
```

## 0.2.11 vim 进阶：操作符、文本对象与宏 {#sec-0.2.11}

这一节回答：为什么 vim 高手按的键更少；`ciw` 这类组合为什么能记住；怎样把重复编辑录成一次可重放的宏。

::: preview 先抓住一件事
vim 的按键不是一张要背完的表，而是一门小语法：操作符说“做什么”，动作或文本对象说“对谁做”，拼起来就是新命令。宏只是把这串按键录下来重放；行能靠模式选出来时，`:g/pat/norm` 比宏更稳。
:::

0.2.7 给的是「能改文件」的生存集。这一节给的是**语法**：vim 的命令大多不是孤立的快捷键，而是「操作符 + 动作/文本对象」的组合。记住 6 个操作符和 8 个动作，就能推出上百条命令，不用逐条背。

```
[数量] 操作符 [数量] 动作/文本对象
  3      d        i      w        → 删 3 个词内内容
         c        a      "        → 改一段引号内外内容
         y        i      t        → 复制标签内内容
```

这张图是 vim 的核心语法。`d`、`c`、`y` 是操作符；`w`、`$`、`j`、`}` 是动作；`iw`、`a"`、`it` 是文本对象。文本对象以 `i`（inner）或 `a`（around）开头，后面跟一个对象字符。`i` 不含分隔符，`a` 含。

常用文本对象：

| 对象 | `i`（内部） | `a`（含分隔符） | 例子 |
|:--|:--|:--|:--|
| 词 | `iw` | `aw` | `ciw` 改当前词，光标可在词中任意位置 |
| 引号 | `i"`、`i'`、`` i` `` | `a"`、`a'` | `ci"` 改双引号内的字符串 |
| 括号 | `i(`、`i[`、`i{`、<code>i&lt;</code> | `a(`、`a[`、`a{` | `di(` 删括号内内容，保留括号 |
| 标签 | `it` | `at` | `cit` 改 HTML/XML 标签之间的文本 |
| 段落 | `ip` | `ap` | `dap` 删整段（含前后空行） |
| 句子 | `is` | `as` | `das` 删一句 |
| 缩进块 | `ii` | `ai` | 删/改同缩进级别的一块 |

这张表说明：**文本对象让「选到哪里」不依赖光标位置**。`di"` 在行内任何位置都能删掉引号里的内容；用 `dt"` 就必须先把光标放到引号前。改配置文件、改代码字符串时，这个差别很大。

这也是 `ciw` 比按方向键选更稳的原因。方向键选的是“从当前光标往右数几个字符”，光标偏一格、词的长短不同，删掉的范围就变了；`ciw` 选的是“光标所在的那个词”，边界由 vim 找，光标在词中任何位置结果都一样。改一百个变量名时，前者靠手稳，后者靠规则。

操作符本身也有一张短表：

| 操作符 | 作用 | 与动作组合 | 与文本对象组合 |
|:--|:--|:--|:--|
| `d` | 删除（进寄存器） | `d$`、`dG`、`d}` | `diw`、`da(` |
| `c` | 删除并进入插入模式 | `ct,`、`c$` | `ciw`、`ci"` |
| `y` | 复制 | `y$`、`yG` | `yap`、`yi}` |
| <code>&gt;</code> / <code>&lt;</code> | 增减缩进 | `>j`、`>G` | `>ap` |
| `=` | 自动缩进 | `gg=G` 全文重排 | `=ap` |
| `gU` / `gu` / `g~` | 大写/小写/翻转大小写 | `gU$` | `gUiw` |
| `!` | 用外部命令过滤 | `!}sort` | `!ip` 后接命令 |
| `gq` / `gw` | 重排段落 | `gqap` | `gqip` |

这张表说明：操作符可以接动作，也可以接文本对象；`>` 和 `=` 常被忽略，但改 YAML、JSON、代码块时比手动空格快得多。`gg=G` 是「全文按 `shiftwidth` 重排」，前提是 `filetype indent on` 或至少设置了 `shiftwidth`。

### 寄存器与宏

vim 的删除/复制不是只进一个剪贴板，而是进**寄存器**（register）。`"` 后面跟寄存器名：

| 寄存器 | 内容 | 写入方式 |
|:--|:--|:--|
| `"0` | 最近一次复制（yank） | `yy`、`yw` 自动写 |
| `"1`–`"9` | 删除历史，`"1` 最新 | `dd`、`dw` 自动写 |
| `"-` | 最近一次小删除（行内） | `x`、`dw` |
| `"a`–`"z` | 命名寄存器 | `"ayy`、`"ap` |
| `"_` | 黑洞，删除不进寄存器 | `"_dd` |
| `"+` / `"*` | 系统剪贴板 | `"+yy`、`"+p`（需 `+clipboard`） |
| `"/` | 最近一次搜索 | `/pattern` 自动写 |
| `":` | 最近一次命令行 | `:` 自动写 |
| `"%` | 当前文件名 | 自动 |
| `".` | 最近插入的文本 | 自动 |

这张表说明：`dd` 会覆盖 `"1`，但不会覆盖 `"0`；所以「复制一段，删几行，再粘贴」仍然粘的是复制的那段。要保留多次复制，用命名寄存器 `"a`、`"b`。`"_dd` 是「删了但不污染寄存器」的干净删除。

宏（macro）不是脚本，而是一次按键录制：按 `qa` 后，vim 把后续按键原样记进寄存器 `a`，按 `q` 停止，`@a` 再播放一遍。它不关心按键“是什么意思”，只负责复现，所以录进去的退格、多余的方向键、误按的 `j` 都会一起重放。流程固定：

```vim
qa
A;
j
q
5@a
:reg a
```

六条命令依次是：开始录制、行尾加分号、下一行、停止录制、重放 5 次、查看寄存器内容。不要在命令后面接 `"` 注释：在普通模式里 `"` 是「重放寄存器」，会被一起录进宏。

宏的三个边界：

1. **录制会包含所有按键**，包括错误的退格与 `Esc`。录错就 `q` 重录，或 `:let @a='...'` 直接编辑寄存器内容。
2. **宏里的 `@a` 会递归**。如果录制时按了 `@a`，重放会无限递归；vim 会在报错后中止，但可能已经改坏文件。用 `:normal @a` 逐行执行更可控。
3. **宏按「物理行」移动**。文件里有折行、空行、不同缩进时，`j` 的落点可能不是你想的那一行；复杂场景改用 `:g/pat/norm ...`，让 vim 自己遍历匹配行。

`:g` 是「按模式批量执行」，比宏更适合规则明确的场景：

```vim
:g/^$/d                  " 删所有空行
:g/^#/d                  " 删所有以 # 开头的行
:v/keep/d                " 删所有不含 keep 的行
:g/error/norm A;         # 对含 error 的行行尾加分号
:g/^server/.,+3s/old/new/g   " 对每个 server 块的后 3 行替换
```

最后一条展示了 `:g` 的「范围」能力：`.,+3` 是「当前行到后 3 行」。批量改配置块时，比写宏稳。

宏和 `:g/pat/norm` 的分工可以这样记：宏适合“改法固定、但每次要自己走到下一处”的少量重复；`:g/pat/norm` 适合“哪些行要改”能用模式说清楚的大量重复。宏按物理行移动，遇到空行、折行、缩进变化会偏；`:g` 让 vim 自己挑行，不用数按几次 `j`。规则越清楚，越应该把“找行”交给 `:g`。

::: errata 关于文本对象与宏的三个误解
1. **「`cw` 与 `ciw` 等价」**——光标在词中间时，`cw` 只改到词尾，`ciw` 改整个词；改变量名改到一半，往往就是这里出的错。
2. **「宏会记住我的意图」**——宏只记录按键，录进去的误按、退格、多余 `j` 都会原样重放；录错就按 `q` 重录，别指望它自己纠正。
3. **「`:g` 只能删除匹配行」**——`:g` 后面可以接任意 Ex 命令，`d` 只是最常用的一种；`norm` 把普通模式按键套到每个匹配行，范围仍由模式决定。
:::

### 0.2.11 小结

vim 的按键不是一张需要背完的表，而是一门小语法：操作符说明“做什么”，动作或文本对象说明“对谁做”，两者一拼就是新命令。宏把这串按键录下来重放，`:g/pat/norm` 则让 vim 自己挑行；规则越清楚，越不该靠手数。如果只记住一件事，那就是：先说清“对什么对象做什么”，再让 vim 去算范围。

**Q2（辨析）** 光标停在 `timeout` 的中间，`cw` 与 `ciw` 的结果差在哪？为什么批量改变量名时更推荐 `ciw`？

**Q3（应用）** 一个 20 行的文件，每行形如 `item12`，要在行尾统一加 `;`。写出宏的做法和 `:g`/`:%norm` 的做法，并说明哪种更稳。

::: sol 答案
**A1** `d` 删除，`c` 删除并进入插入模式，`y` 复制；`iw` 选当前词（不含空白），`i"` 选双引号内的内容（不含引号），`ap` 选整段（含段后空行）。
**A2** `cw` 从光标处改到词尾，留下前半截 `time`；`ciw` 改整个 `timeout`。`ciw` 的范围由“光标在哪个词里”决定，不依赖光标停在词中的第几个字符，所以批量改更稳。
**A3** 宏：`qa`、`A;`、`Esc`、`j`、`q`，再 `19@a`；`:g` 写法：`:%norm A;`，或 `:g/^item/norm A;`。后者更稳：它按模式挑行，不依赖 `j` 每次落在正确的物理行，遇到空行或折行也不会偏。

## 0.2.12 tmux 脚本化：把布局写成可复现的命令 {#sec-0.2.12}

这一节回答：怎样让「打开三个 pane、各自跑固定命令」变成一条命令；怎样把 pane 输出留成日志。

::: preview 先抓住一件事
tmux 的每个动作都有非交互版本：`new -d` 建一个没人接的无头会话，`send-keys` 往里送按键，`capture-pane` 读屏幕，`pipe-pane` 留日志。脚本化的关键不是多记命令，而是记住这些命令都作用于 pane，不作用于你的终端窗口。
:::

0.2.8 的 tmux 表是交互操作。真正的效率来自**脚本化**：会话可以创建、切分、发送命令、抓取输出、录制日志，全部非交互完成。CI、远程排障、教学演示都用得上。

先记四个「无头」命令：

```bash
# 创建分离会话（不 attach），指定工作目录
tmux new-session -d -s work -c "$PWD"
# 在会话里开新窗口并运行命令
tmux new-window -t work:1 -n logs 'journalctl -fu api'
# 水平/垂直分屏
tmux split-window -h -t work:1
# 向指定 pane 发送按键（C-m 是回车）
tmux send-keys -t work:1.0 'curl -sS localhost:8080/health' C-m
```

`-d` 是「不要抢占当前终端」；没有它，`new-session` 会直接 attach，脚本就卡住了。`-t` 的目标格式是 `会话:窗口.pane`，如 `work:1.0`。`send-keys` 默认发送字面字符串，`C-m`、`C-c`、`Enter` 这类键名要单独作为参数。

::: note 非科班补一层：无头会话与 `C-m`
没有终端窗口接在上面的会话，常叫无头会话（headless session）：tmux 服务进程把 Shell 跑在 pty 上，你在脚本里只能通过 `send-keys` 和 `capture-pane` 跟它打交道。看不到屏幕不是缺陷，正因为它不依赖任何窗口，才适合放进 CI、远程脚本或定时任务。

`C-m` 是 tmux 对回车键的写法：Ctrl-M 在 ASCII 里是 CR（0x0D），行规程把它当回车。`send-keys` 只把 `date` 这几个字符送进 pane；不加 `C-m`，命令就停在提示符上，看起来像“没反应”。
:::

脚本化布局的价值在于**可复现**。下面这个脚本每次都在同一目录建同样的三 pane：

```bash
#!/usr/bin/env bash
# dev-layout.sh —— 建一个 1 窗口 3 pane 的开发会话
set -euo pipefail

session=${1:-dev}
dir=${2:-$PWD}

if tmux has-session -t "$session" 2>/dev/null; then
    echo "session $session exists; attaching"
    exec tmux attach -t "$session"
fi

tmux new-session -d -s "$session" -c "$dir" -n edit
tmux split-window -h -t "$session:edit" -c "$dir"
tmux split-window -v -t "$session:edit.1" -c "$dir"
tmux select-layout -t "$session:edit" main-vertical

# pane 0：编辑；pane 1：测试；pane 2：日志
tmux send-keys -t "$session:edit.0" 'vim .' C-m
tmux send-keys -t "$session:edit.1" 'while :; do clear; date; sleep 2; done' C-m
tmux send-keys -t "$session:edit.2" 'tail -f /var/log/syslog' C-m

tmux select-pane -t "$session:edit.0"
exec tmux attach -t "$session"
```

关键点是 `has-session` 的幂等判断：会话已存在就 attach，不重复创建；`select-layout main-vertical` 让主 pane 占左侧大部分宽度；`send-keys` 里的命令要加 `C-m` 才会执行。把 `dir` 作为参数传入，脚本就能在不同项目里复用。

抓取输出与录制日志是排障时的两个高频需求：

```bash
# 抓取 pane 最近 200 行（-p 输出到 stdout，-S 指定起始行）
tmux capture-pane -p -t work:1.0 -S -200 > /tmp/pane.txt

# 把 pane 的后续输出追加到文件（-o 表示只开一次，避免重复 pipe）
tmux pipe-pane -o -t work:1.0 'cat >> /tmp/pane.log'

# 关闭 pipe
tmux pipe-pane -t work:1.0
```

`capture-pane` 抓的是 tmux 为这个 pane 维护的**屏幕缓冲区**，不是程序的 stdout，也不是 Shell 的历史记录；它只能看到“屏幕上曾经画出来的字”。默认只有当前屏幕；`-S -200` 从往前 200 行开始，`-E` 指定结束行，更早的内容受 `history-limit` 限制，抓不到。`pipe-pane` 则是持续管道，适合「让同事复现时把日志留下」；它不会自动轮转，长跑要配合 `logrotate` 或写到带时间戳的文件。

列出 pane 的元数据，能把「哪个 pane 在跑什么」变成可解析的输出：

```bash
tmux list-panes -a -F '#{session_name}:#{window_index}.#{pane_index} pid=#{pane_pid} cmd=#{pane_current_command} path=#{pane_current_path}'
tmux display-message -p '#{socket_path}'     # 当前 tmux server 的 socket
tmux -L lab new -d -s isolated               # 用独立 socket，不干扰默认会话
```

`-L` 指定 socket 名，适合测试或隔离环境；`-f /dev/null` 跳过配置文件，适合排查「是不是配置写坏了」。

::: errata tmux 的四个边界
1. **「tmux 会话能扛重启」**——不能。它扛的是 SSH 断线与终端关闭；机器重启后会话全丢。要扛重启，用 systemd 服务或持久化任务队列。
2. **「`send-keys` 等于执行命令」**——它只是把按键送进 pane，命令是否执行取决于有没有回车、Shell 是否在等待输入。脚本里统一加 `C-m`。
3. **「`capture-pane` 能抓到全部历史」**——默认只有当前屏幕；历史深度由 `history-limit` 决定，超出部分抓不到。
4. **「退出登录后 tmux 一定还在」**——systemd-logind 的 `KillUserProcesses=yes` 会在最后一个会话结束时杀掉用户进程；需要 `loginctl enable-linger` 加上该用户名，或改配置。
:::

### 0.2.12 小结

tmux 脚本化把“打开几个窗口、各跑什么”从手工作业变成一条可重复执行的命令：`new -d` 建无头会话，`send-keys` 送按键，`capture-pane` 读屏幕，`pipe-pane` 留日志。这些命令都作用于 pane，而不是你的终端窗口；脚本里每一条 `send-keys` 后面都要有 `C-m`，命令才会真正回车执行。如果只记住一件事，那就是：无头会话里没有“手”，所有动作都要用命令补上。

## 0.2.13 文档工作流：man、info、help 的检索路径 {#sec-0.2.13}

这一节回答：面对一个不认识的命令或系统调用，按什么顺序查最快；为什么 `man` 有时「查不到」；`/usr/share/doc` 里有什么是 man 没有的。

::: preview 先抓住一件事
查文档的顺序不是礼节，而是按“拿到答案的成本”从低到高排：内建先问 `help`，命令先看 `--help`，要完整语义再 `man`，GNU 项目再进 `info`，最后才翻包文档和源码。`man` 查不到，多数不是“没文档”，而是查错了区号或索引过期。
:::

0.1.9 讲的是 man 的分区与「哪一层归谁写」。这一节讲**操作**：从「我知道一个词」到「拿到一条可执行结论」的最短路径。

先记一条检索顺序，别一上来就搜网页：

1. **Shell 内建** → `help 内建名`、`help -d 内建名`。`cd`、`read`、`printf`、`trap` 没有独立 man page。
2. **命令的 `--help`** → `cmd --help`，看选项与默认值。它比 man 短，适合确认 flag 拼写。
3. **man page** → `man 名字`，系统调用加区号 `man 2`，配置文件加 `man 5`。
4. **info 文档** → GNU 项目（coreutils、grep、sed、gawk）的 info 通常比 man 完整。
5. **包文档** → `/usr/share/doc/` 下对应包名的目录，含 README、changelog、发行版补丁说明。
6. **源码/上游** → 最后才看，且要固定版本。

这个顺序按“拿到答案的成本”排，不是按文档的完整程度排。`help` 是 Shell 内建，不用装包、不查索引、不分页，问一句就答；`--help` 由程序自己打印，通常一秒内结束；`man` 要查 `mandb` 索引、启动分页器，还可能命中多个同名页。先用便宜的手段确认“它是不是我要找的东西”，再花成本读完整文档。

man 的四个实用开关：

| 命令 | 作用 | 场景 |
|:--|:--|:--|
| `man -w name` | 只打印文件路径，不显示内容 | 确认查到的是哪个页 |
| `man -a name` | 依次显示所有同名页 | `man -a passwd` 看命令与文件格式 |
| `man -K pattern` | 在所有 man page 正文里搜 | 只记得一句话，不记得命令名 |
| `man -P 'less +/pattern' name` | 用指定 pager 打开并跳转 | 直接定位到关键词 |

`man -w` 是最被低估的：它告诉你「系统里到底有没有这一页、在哪个区」。`man -w passwd` 通常返回 `/usr/share/man/man1/passwd.1.gz`（改密码的命令），而 `/etc/passwd` 的格式在 `man 5 passwd`。要看系统调用就显式写 `man 2 open`，不要依赖默认的区号顺序。

`MANSECT` 是 man 读取的一个环境变量，里面按顺序列出要去哪些区查找；默认顺序就由它决定。Ubuntu 的默认值把 1 区排在 3 区前面，所以 `man printf` 给你的通常是命令 `printf(1)`，不是 C 库的 `printf(3)`。`man -w` 只报告这个“第一个命中”，不是“唯一一个”；要固定的页，就把区号写在名字前面。同名页不止两个时，`man -a printf` 会按 `MANSECT` 的顺序依次打开，适合在“到底有几个版本”上做一次确认。

`MANPAGER` 决定用什么分页器。默认 `less`，可以加 `-R` 支持颜色：

```bash
export MANPAGER='less -R'
export MANWIDTH=100          # 控制换行宽度；不设则按终端宽度
man 2 write | col -b | sed -n '1,60p'   # col -b 去掉退格加粗，便于粘贴
```

`col -b` 去掉 man 的 overstrike 格式：man 的源文件用“字符、退格、同字符”表示加粗，终端把它渲染成粗体，重定向到文件后却是一串退格控制符。`col -b` 把这类序列折叠成单个字符，把输出变成纯文本；需要把 man 内容贴进工单或代码注释时用它。`man -t` 生成 PostScript，可转 PDF：

```bash
man -t 7 signal | ps2pdf - /tmp/signal.pdf
```

info 是另一套导航模型：节点（node）而不是页。常用键：

| 键 | 作用 |
|:--|:--|
| `n` / `p` | 下一个 / 上一个节点 |
| `Up` | 上一层 |
| `l` | 返回上一个节点 |
| `g` | 按名字跳节点 |
| `s` | 在文档内搜索 |
| `q` | 退出 |

命令行直接定位节点：

```bash
info coreutils                          # 顶层菜单
info coreutils 'ls invocation'          # 直接到 ls 的调用说明
info --output=- coreutils 'ls invocation' | head -40   # 输出到 stdout
```

GNU 的 info 文件在 `/usr/share/info/*.info.gz`，`info` 会读 `dir` 索引。新装的包如果 `info` 找不到，跑 `install-info --info-dir=/usr/share/info` 并加上 info 文件路径，或重装包。

`--help` 的边界：它由程序自己实现，格式、退出码、是否支持 `-h` 都不统一。`grep --help` 退出 0，`ls --help` 退出 0，但有些程序把 `--help` 当错误参数返回 2。脚本里不要解析 `--help` 的输出，用 man 或版本化接口。

发行版文档在 `/usr/share/doc`：

```bash
dpkg -L coreutils | grep '^/usr/share/doc'
zless /usr/share/doc/coreutils/changelog.Debian.gz
ls /usr/share/doc/nginx/           # README.Debian、copyright、examples
```

`README.Debian` 解释「Debian/Ubuntu 改了什么」，`changelog.Debian.gz` 记录补丁与 CVE 修复，`copyright` 是许可证。这三样在排查「为什么行为与上游文档不一致」时最有用。

::: method 实验 0.2-C · 一条命令查清一个陌生命令
目的：用固定顺序在 30 秒内回答「它是什么、怎么用、默认值是什么、属于哪个包」。

```bash
#!/usr/bin/env bash
# doc.sh NAME —— 按 help → man → info → --help 的顺序找文档
set -euo pipefail
name=${1:?usage: doc.sh NAME}

if help -d "$name" >/dev/null 2>&1; then
    echo "== builtin: $name"; help -d "$name"; exit 0
fi
if path=$(man -w "$name" 2>/dev/null); then
    echo "== man: $path"
    MANPAGER=cat man "$name" 2>/dev/null | col -b | sed -n '1,40p'
    exit 0
fi
if info --output=- "$name" >/dev/null 2>&1; then
    echo "== info: $name"; info --output=- "$name" | sed -n '1,40p'; exit 0
fi
if command -v "$name" >/dev/null; then
    echo "== --help: $name"; "$name" --help 2>&1 | sed -n '1,40p'; exit 0
fi
echo "no documentation found for $name" >&2
exit 1
```

三种跑法：

```bash
./doc.sh cd            # 命中 builtin
./doc.sh passwd        # 命中 man 1 passwd；/etc/passwd 的格式要 man 5 passwd
./doc.sh ls            # 命中 man，输出前 40 行
./doc.sh nosuchcmd     # 退出 1
```

预期：`cd` 走 builtin 分支，不出现 man；`open` 打印 man 路径与前 40 行；`MANPAGER=cat` 让 man 不走交互分页，脚本才能继续。`man -w` 的命中顺序受 `MANSECT` 影响，要固定区号就显式写 `man 2`，不要依赖默认。
:::

::: errata 关于查文档的三个误解
1. **「`man printf` 看到的就是 C 库的 `printf`」**——默认先命中 `printf(1)`；C 库函数要 `man 3 printf`，系统调用要 `man 2`。
2. **「`--help` 的格式和退出码是统一的」**——它由每个程序自己实现，有的把 `--help` 当错误参数返回 2；脚本里不要解析它的输出。
3. **「info 只是 man 的另一种排版」**——info 是节点树，有菜单和交叉引用；GNU 项目常把完整手册放在 info 里，man 只是摘要。
:::

### 0.2.13 小结

查文档不是“背命令”，而是按成本从低到高试：`help` 问内建，`--help` 看选项，`man` 拿完整语义，`info` 读 GNU 手册，`/usr/share/doc` 看发行版改了什么。`man` 的命中由区号和 `MANSECT` 决定，同名页要显式写区号。如果只记住一件事，那就是：先问“这是哪一层的东西”，再决定查 1、2、3 还是 5 区。

## 0.2.14 八个终端与编辑陷阱 {#sec-0.2.14}

这一节回答：终端、readline、vim、tmux 和文档检索里，哪些坑看起来像“终端坏了”，其实只是某一层的开关被别人改了？怎样用一条命令判定是哪一层？

::: preview 先抓住一件事
这八个坑的共同点是“现象在终端上，原因却不一定在终端”。先按链路分层——终端模拟器、行规程、readline、程序自身、tmux——再决定是按键恢复、改配置，还是换一个工具。
:::

这一节把终端、readline、vim、tmux 与文档检索中最容易踩的八个坑集中起来，每条给现象、原因与修复，再补一句“为什么容易误判”。误判的代价往往不是多敲一条命令，而是把对的配置改坏，或者把还能恢复的文件删掉。

::: errata 关于终端与 readline 的误解
1. **「终端按 `Ctrl-S` 后卡死」**——`ixon` 流控把 `Ctrl-S` 当成暂停输出；按 `Ctrl-Q` 恢复，或 `stty -ixon` 永久关掉。为什么容易误判：屏幕瞬间静止、按键也没有回显，看起来像 Shell 死了；实际只是输出被暂停，进程还在跑。
2. **「脚本崩了，终端不回显」**——`stty -echo` 没恢复；盲打 `stty sane` 回车，或 `reset`。写脚本时先 `trap 'stty "$saved"' EXIT`。为什么容易误判：进程已经退出、提示符也回来了，只有输入看不见，容易被当成键盘或 SSH 故障。
3. **「粘贴多行命令，执行到一半就跑了」**——没有括号粘贴，readline 把换行当执行；升级 bash 5.1+ 并确认 `enable-bracketed-paste on`，或在 vim 里 `:set paste`。为什么容易误判：粘贴时的回显和手打一模一样，你看不出 readline 已经把中间的换行当成了回车。
:::

::: errata 关于 vim、tmux 与文档检索的误解
1. **「vim 提示 swap file 已存在」**——另一个会话在编辑，或上次崩溃；先 `vim -r file` 恢复，确认后再删 `.swp`，不要直接 `rm`。为什么容易误判：提示只说“已存在”，人的第一反应是删掉障碍，而不是想“还有谁在写这个文件”。
2. **「`:w !sudo tee %` 保存后，再 `:w` 又失败」**——vim 仍认为文件只读；保存后执行 `:e!` 重新加载，再继续编辑。为什么容易误判：第一次保存确实成功了，于是以为权限问题已经解决；实际 vim 的只读标记没变。
3. **「tmux 里 vim 的 `Esc` 有延迟」**——`escape-time` 在等组合键；设 `set -g escape-time 10`。为什么容易误判：延迟只在 vim 里明显，容易怪 vim 插件或终端卡顿；实际是 tmux 在等转义序列。
4. **「ssh 进 tmux 后颜色/按键错乱」**——`TERM` 不匹配；在 `.tmux.conf` 设 `set -g default-terminal "screen-256color"`，并确认远端 terminfo 有该条目。为什么容易误判：SSH 登录本身成功，只有全屏程序花屏，容易怪程序而不是终端类型。
5. **「`man xxx` 说 No manual entry」**——包没装 man page（如 `man-db` 缺失）、`mandb` 索引过期，或该命令是内建；分别用 `apt install man-db`、`sudo mandb`、`help xxx` 处理。为什么容易误判：`man` 的报错只说“没有”，不区分内建、没装 man page 和索引过期，容易直接得出“系统没文档”的结论。
:::

### 0.2.14 小结

八个坑分散在五层，但判断方法只有一条：先问“现象出现在哪一层”，再问“这一层最近被谁改过”。`Ctrl-S`、`stty -echo` 和粘贴问题落在行规程与 readline；swap、只读保存、Esc 延迟落在 vim 与 tmux；`TERM` 和 man 命中落在环境与文档索引。如果只记住一件事，那就是：不要先改配置，先用一条命令确认是哪一层。

::: method 即时自测 · 0.2.14
**Q1（记忆）** `Ctrl-S` 卡死、`stty -echo` 不回显、粘贴多行提前执行，各自的恢复动作是什么？

**Q2（辨析）** 两个现象都是“终端没反应”：按 `Ctrl-S` 后屏幕不动，和 `stty -echo` 后敲字看不见。怎样用按键和命令区分它们？

**Q3（应用）** `man xxx` 报 No manual entry，给出排查顺序；如果是 tmux 里 vim 的 Esc 有延迟，又该改哪里？

::: sol 答案
**A1** 按 `Ctrl-Q` 恢复输出，或 `stty -ixon` 永久关闭流控；盲打 `stty sane` 回车或 `reset` 恢复回显；开启括号粘贴（bash 5.1+ 的 `enable-bracketed-paste on`），临时在 vim 里用 `:set paste`。
**A2** 先按 `Ctrl-Q`：屏幕立刻恢复输出，就是 `ixon` 流控；没恢复，再盲打 `stty sane`，回显恢复说明是 `-echo` 没复位。前者是输出被暂停，后者是输入没显示，进程都还活着。
**A3** 先 `help xxx` 看是不是内建，再 `man -w xxx` 看有没有命中、`type -a xxx` 看命令是否存在；怀疑索引过期就 `sudo mandb`，缺 man page 就装 `man-db`。Esc 延迟不归 vim 管，改 tmux 的 `set -g escape-time 10`，再 `tmux source-file ~/.tmux.conf`。
:::
:::

::: ex 例 0.2.1 · 脚本里的 `cd` 为什么没改变当前目录 {#ex-0.2.1}
写了个 `goto.sh`，里面只有 `cd /tmp && pwd`。`bash goto.sh` 输出 `/tmp`，但运行完再 `pwd`，还是原来的目录。

先猜：`cd` 失败了吗？

判读：没有失败。`bash goto.sh` 让脚本在**子进程**里执行，`cd` 改的是子进程的 cwd，子进程退出后父 shell 的 cwd 纹丝不动。要改变当前 shell 的目录，只能 `source goto.sh`（或 `. goto.sh`），让命令在同一个进程里跑——这与 0.7 的子 Shell 丢变量是同一个机制的另一面。

**判据**：在脚本内外各 `echo $$`，PID 不同就说明是子进程。
:::

## 0.2.15 本章小结 {#sec-0.2.15}

这一节回答：把 0.2.1–0.2.14 串起来看，这条「终端链路 → 工作台 → 行规程 → 工具语法」的主线到底解决了什么？

::: preview 先抓住一件事
这一章不是命令清单，而是一张分层地图：先分清终端、pty、行规程和 Shell，再把历史、作业、vim、tmux 搭成工作台，最后把 vim、tmux 和文档检索用成可组合的语法。
:::

先回到最开始的问题：你敲下回车，字节经过终端模拟器、pty master、行规程、pty slave，才到 Shell。行规程替你把 `Ctrl-C` 翻成 `SIGINT`、把 `Ctrl-D` 变成一次“读返回 0”、替你回显和攒行；所以同一个按键在 bash 提示符、vim 插入模式、管道里会有三种行为。这条链路画清之后，“终端卡死”“Shell 配置错”“程序自己失败”就不再是同一件事。

第二段主线是把工作台搭起来。提示符、历史、readline 让你少打字，`jobs`/`fg`/`bg`/`disown` 让你管住前后台，vim 让你在只有 `vi` 的机器上改配置，tmux 让断线后的现场还能回来。0.2.9–0.2.10 再往下解释这些工具为什么行为不同：`stty` 改的是 termios 开关，readline 只管一行文本。工作台的价值不是快捷键多，而是现场可恢复、出错可退。

最后一段把工具用成语法。vim 的命令是“操作符 + 动作/文本对象”，宏是按键录制，`:g/pat/norm` 让 vim 自己挑行；tmux 的 `new -d`、`send-keys`、`capture-pane`、`pipe-pane` 把布局变成脚本；查文档则按 `help → --help → man → info → /usr/share/doc` 的成本顺序走。三件事的共同点是：先描述“要什么”，再让工具去算“怎么做”。

接下来不要重读整章。打开[学习目标自检表](ch02-checklist.md)，从 K2.1 开始逐条讲一遍；卡住的条目会指回具体小节和习题。想再练手，就做[习题集](ch02-exercises.md)的 B 组诊断题。

### 0.2.15 小结

这一章的主线是四层递进：先看清链路，再搭工作台，然后用行规程解释差异，最后把 vim、tmux、文档检索变成可复用的语法。如果只记住一件事，那就是：遇到终端问题，先问“这是哪一层”，再问“用哪个工具”。

::: method 即时自测 · 0.2.15
**Q1（记忆）** 按顺序说出终端模拟器、pty master、行规程、pty slave、Shell；`Ctrl-C` 在哪一层变成 `SIGINT`？

**Q2（辨析）** `ssh host 'll'` 报 `ll: command not found`，而 `ssh host` 登录后再敲 `ll` 正常。这跟“登录/交互”两个维度中的哪一个有关？

**Q3（应用）** 同事说 `man printf` 只有命令用法，他想看 C 库的 `printf`。给出两步命令，并说明默认为什么没命中。

::: sol 答案
**A1** 键盘 → 终端模拟器 → pty master → 行规程 → pty slave → Shell。`Ctrl-C` 在行规程里被翻译成 `SIGINT`，再发给前台进程组。
**A2** `ssh host 'll'` 是非交互、非登录 Shell；`~/.bashrc` 只对交互 Shell 生效，alias 默认也只在交互 Shell 展开，所以直接原因是“非交互”。它同时也非登录，但即使登录，非交互 Shell 里的 `.bashrc` 通常也会提前返回。
**A3** 先 `man 3 printf`；要确认有没有这一页，用 `man -w 3 printf`。默认 `MANSECT` 把 1 区排在 3 区前面，`man printf` 先命中命令 `printf(1)`。
:::
