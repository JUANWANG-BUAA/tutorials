# 0.1 Linux 世界观：内核、GNU、发行版与标准

<div class="chapter-index">
<div><span class="ci-label">本章回答</span><p>Linux 到底是什么？内核、GNU 用户态、发行版、POSIX/FHS 各占哪一层？为什么说「Linux 严格来说只是内核」，而你在服务器上敲的每一条命令，几乎都不由内核提供？</p></div>
<div><span class="ci-label">读完你会</span><p>从 <code>uname</code>、<code>/etc/os-release</code>、<code>getconf</code> 的输出里拆出内核与用户态；用 <code>modules.builtin</code> 与 <code>/proc/cmdline</code> 判断模块和启动方式；解释一个 ELF 程序从 libc 到系统调用（程序请内核办事的那道关口）的路径；判断某个「Linux 上能跑」的说法是内核保证、libc 保证，还是发行版约定。</p></div>
</div>

你输入 `ls`，看到一列文件名。这条命令背后至少有四层东西在工作：终端把按键交给 Shell，Shell 在 `$PATH` 里找到 `/usr/bin/ls`，内核执行这个 ELF 文件并把目录内容读出来，glibc 把内核返回的字节翻译成你看到的格式。四层里只有第三层是 Linux 内核。

日常说「Linux 系统」时，指的是这四层打包在一起的**发行版**。这个含混的说法在运维里够用，在排障时会误导人：内核 panic、glibc 版本不兼容、发行版把默认配置改坏，是三类完全不同的问题，证据和修复路径也不同。

这一章先建立一张分层地图。后面的权限、进程、磁盘、systemd、网络，都会反复回到这张图上问一句：这件事由谁负责，边界在哪里。读完这一章不要求你记住所有标准编号，只要求你能把「内核行为」「C 库行为」「发行版策略」分开说。

## 0.1.1 从一次 `uname -a` 读起 {#sec-0.1.1}

这一节回答：`uname -a` 打出的这一行，哪些字段来自内核，哪些只是某个程序的自报家门？

::: preview 先抓住一件事
`uname` 看到的是系统层：内核版本、机器架构、主机名。你在同一台机器上跑的 hello 程序看到的是程序层：编译、加载、执行、退出。两层描述的不是同一件事，排障时不能互相代替。
:::

先看一台 Ubuntu 24.04 机器上的真实输出：

<div class="terminal" data-title="bash · ubuntu 24.04 / aarch64（实测）">
<pre><span class="p">&#36;</span> uname -a
Linux juanwang-Ubuntu24.04 7.0.0-38-generic #38~24.04.4-Ubuntu SMP PREEMPT_DYNAMIC Mon Sep 14 17:12:37 UTC 2 aarch64 aarch64 aarch64 GNU/Linux
<span class="p">&#36;</span> uname -s
Linux
<span class="p">&#36;</span> uname -r
7.0.0-38-generic
<span class="p">&#36;</span> uname -m
aarch64
<span class="p">&#36;</span> uname -o
GNU/Linux
</pre>
</div>

`uname -a` 的八个字段依次是：内核名、主机名、内核 release、内核 version 字符串、机器硬件架构、处理器架构、硬件平台、操作系统名。排障时真正有用的是第 3 和第 5 个字段：前者决定你能用哪些内核特性，后者决定你该下载哪个架构的二进制包。

上面那行还藏着一个坑：version 字符串的结尾是 `UTC 2`，不是完整的年份。内核把每个字段限长 64 个字符（`include/uapi/linux/utsname.h` 里 `#define __NEW_UTS_LEN 64`，六个字段都声明成 `[__NEW_UTS_LEN + 1]`；这台 VM 上 `grep` 头文件就能看到），而 Ubuntu 那条又特别长，`… UTC 2024` 数过去正好 67 个字符，于是 `2024` 被截成 `2`——`uname -v | wc -c` 在这台机器上给 65，也就是 64 个字符加一个换行。所以别拿 `uname -v` 的尾巴去判断构建时间，那串文字随时可能被截断；要精确就去看 `/proc/version` 或发行版的 changelog。

`uname -s` 只取第一项，`uname -r` 只取第三项，`uname -m` 只取第五项。把 `-a` 拆成这三条，你就有了脚本里最常用的三个格子。

注意 `uname -o` 输出的是 `GNU/Linux`，不是 `Linux`。这不是文字游戏：`uname` 这个程序本身来自 GNU coreutils，它知道整套用户态主要来自 GNU。内核并不关心自己叫什么，它只负责把数据填好。

同一个终端里再跑一个 hello，视角就换了：

```c
/* hello.c —— 只用标准库，不碰任何 Linux 专有接口 */
#include <stdio.h>

int main(void)
{
    printf("hello, world\n");
    return 0;
}
```

```bash
cc -o hello hello.c
./hello
# hello, world
```

`./hello` 的输出里没有内核版本，但内核全程在场。`cc` 按 `uname -m` 报告的架构生成 x86-64 机器码；Shell 用 `execve` 把 ELF 文件交给内核；内核建立进程、映射内存、跳到 libc 的启动代码；`printf` 最后变成一次 `write(1, ...)`。

`uname` 看到的是「这台机器是什么」，hello 看到的是「这个程序怎么活」。前者是系统层的一张身份卡，后者是程序层的一条生命周期。0.1.8 会把这两条线接到同一张时间轴上。

三个容易混淆的版本号：

| 来源 | 命令 | 例子 | 变化频率 | 说明 |
|:--|:--|:--|:--|:--|
| 内核 | `uname -r` | `6.8.0-45-generic` | 随内核更新 | 决定驱动、系统调用（syscall）与 cgroup（内核给进程分组限资源的机制）的版本 |
| libc | `ldd --version` | `2.39` | 随发行版大版本 | 决定符号版本与部分 POSIX 行为 |
| 发行版 | `/etc/os-release` 的 `VERSION_ID` | `24.04` | 每半年或数年 | 决定包版本、默认配置、支持周期 |

一个常见误判：看到 `6.8.0-45-generic` 就以为系统是「Linux 6.8 的第 45 版」。`6.8.0` 是上游基线，`-45` 是 Ubuntu 自己的 ABI 编号，`generic` 是配置风味。要判断某个上游特性是否存在，查 `uname -r` 的主次版本，再查发行版的 backport 说明，不要猜。

::: errata 关于版本号的三个误解
1. **「`uname -r` 就是发行版版本」**——它是内核 release；发行版在 `/etc/os-release` 的 `VERSION_ID`。两者可以一个新一个旧。
2. **「`uname -o` 写着 GNU/Linux，所以内核叫 GNU/Linux」**——这行是 coreutils 的判断，内核只提供 `uname(2)` 的数据。
3. **「`-45-generic` 是上游第 45 个小版本」**——它是发行版的 ABI 与构建编号，和上游补丁号不是一套计数。
:::

::: note 非科班补一层：系统调用
`uname` 程序自己读不到内核版本。它调用 `uname(2)` 这个系统调用，内核把八项信息填进一个 `struct utsname` 再返回。系统调用是用户态程序请求内核办事的唯一窗口；0.1.13 会拆开它的寄存器和返回值。
:::

### 0.1.1 小结

`uname` 读的是内核与硬件登记的身份，hello 走的是程序从编译到退出的生命周期；同一台机器，两层各说各话。判断二进制能不能跑，看 `uname -m` 和 libc；判断内核能力，看 `uname -r`，不要看发行版号。如果只记住一件事，那就是：`uname` 回答「机器是什么」，`./hello` 回答「程序怎么活」。

::: method 即时自测 · 0.1.1
**Q1（记忆）** `uname -a` 的第 3、第 5 个字段各是什么？分别影响什么？

**Q2（辨析）** 同事说「系统是 Ubuntu 24.04，内核就一定是 6.8」，这句话漏掉了哪种可能？

**Q3（应用）** 你要给一台 ARM64 服务器挑预编译包，先运行哪条命令、看哪个字段？

::: sol 答案
**A1** 第 3 个是内核 release（如 `6.8.0-45-generic`），决定可用的内核特性与驱动；第 5 个是机器硬件架构（如 `x86_64`），决定该下载哪种架构的二进制。
**A2** 用户态与内核可以独立变化：GA/HWE 双轨、云厂商镜像、容器宿主、手动降级，都会造成「新发行版 + 旧内核」。要分开看 `/etc/os-release` 与 `uname -r`。
**A3** `uname -m`（或 `dpkg --print-architecture`）确认是 `aarch64`/`arm64`，再选对应架构的包；只看到 `Linux` 三个字不够。
:::
:::

## 0.1.2 内核的职责与边界 {#sec-0.1.2}

这一节回答：内核到底管什么、不管什么？为什么同一个 `open`，换个发行版行为就可能不同？

::: preview 先抓住一件事
内核提供机制：能不能读这个文件、能不能建这个进程。发行版和用户态决定策略：默认允许谁读、默认开不开防火墙。机制坏了要查内核与驱动，策略错了要查配置，两者的证据完全不同。
:::

先制造一个错误，看看一句话里有几层在说话：

<div class="terminal" data-title="bash · 一个错误的三层来源">
<pre><span class="p">&#36;</span> cat /nonexistent
cat: /nonexistent: No such file or directory
</pre>
</div>

`No such file or directory` 不是内核写的。内核只返回 `-1`，并把 `errno` 设成 `ENOENT`；`strerror` 把错误号翻译成英文；`cat` 再加上 `cat: /nonexistent:` 这个前缀。

同一句话里，事实来自内核，措辞来自 libc 和程序。分清这一点，你就不会拿着 `cat` 的提示去搜「内核报错」。

::: def 定义 0.1.1 · 内核（kernel） {#def-0.1.1}
内核是常驻内存、运行在 CPU 最高特权级（x86-64 的 ring 0）的那部分代码。它管理进程与调度、虚拟内存（让每个进程以为自己独占内存）、文件系统、网络协议栈、设备驱动与中断（外部设备用信号打断 CPU，让它来收刚发生的事），并通过**系统调用**（system call，用户态请内核办事的唯一入口）向用户态提供唯一合法的入口。用户态代码不能直接访问页表（把虚拟地址翻译成物理地址的表）、中断控制器或磁盘控制器。
:::

把内核的职责拆成五块，每块都对应后面的一篇：

| 职责 | 内核里做什么 | 用户可见的接口 | 本书展开 |
|:--|:--|:--|:--|
| 进程与调度 | 创建/销毁任务、上下文切换、CPU 分配 | `fork`/`execve`/`wait4`、`/proc` | 第 1、3 篇 |
| 虚拟内存 | 页表（地址翻译的表）、缺页（要用的页不在内存，先停下来去取）、映射、回收 | `mmap`/`brk`、`/proc/meminfo` | 1.9、2.12 |
| 文件系统 | inode（文件的元数据记录）、目录项、页缓存、VFS（内核把 ext4、procfs 这些都统一成同一套操作的层） | `open`/`read`/`write`、`mount` | 2.2–2.6、0.10 |
| 网络 | socket、TCP/IP、netfilter、驱动 | `socket`/`sendto`、`/proc/net` | 第 4 篇、0.13 |
| 设备与中断 | 驱动、DMA（设备直接读写内存，不经过 CPU 搬运）、中断处理、电源 | `/dev`、`/sys`、`ioctl` | 3.x、0.10 |

内核的边界同样重要。下面这些**不是**内核提供的：

- `printf`、`malloc`、`fopen`：glibc 或 musl 提供，内核只有 `write`、`brk`/`mmap`、`open`。
- 管道符 `|`、通配符 `*`、引号、变量展开：Shell 提供，内核只看到展开后的 `argv`。
- `apt`、`systemctl`、`ps`：用户态程序，通过 `/proc`、`/sys`、D-Bus 与内核或守护进程对话。
- 「开机自启」「日志轮转」「防火墙默认拒绝」：发行版策略，由 systemd、logrotate、nftables 规则实现。

::: intuition 机制与策略分开
内核提供**机制**（能做这件事），发行版和用户态决定**策略**（默认做不做、对谁做）。同一个 `open` 系统调用，在 Ubuntu 和 Alpine 上语义相同；但默认 `umask`、默认挂载选项、默认防火墙规则可以完全不同。排障时先问「这是机制坏了，还是策略配错了」，能省一半时间。
:::

Linux 是宏内核（monolithic kernel）：驱动、文件系统、网络栈都跑在内核地址空间里，共享同一套页表。好处是调用路径短，坏处是一个驱动越界就可能拖垮整机。内核模块（`.ko`）能在运行时加载，但仍然运行在 ring 0，不是沙箱。把「可加载模块」理解成「可选装的内核代码」而不是「安全隔离的插件」，是读第 3 篇的前提。

### 0.1.2.1 只写应用层，为什么也要懂这条边界

一个服务跑了三天，日志开始刷 `Too many open files`。这不是磁盘满了，也不是 glibc 坏了：进程的 fd 表用完了。内核给每个进程一张有上限的 fd 表，超出就返回 `EMFILE`。

先看当前进程用了多少：

```bash
ls /proc/$$/fd | wc -l
cat /proc/$$/limits | grep -i 'open files'
```

第一行数的是 Shell 自己的 fd 目录，第二行读的是内核对这个进程设的上限。两个数字都来自内核，`ulimit -n` 只是修改它们的命令行包装。

遇到这个错误，顺序是先找泄漏的 fd（`ls -l /proc/<pid>/fd`），再谈调大上限。只调 `ulimit` 不修泄漏，等于把报警器关掉。这就是「应用层 bug，根因在内核边界」的典型样子。

内核还通过两个伪文件系统把内部状态投影给用户态：`/proc` 面向进程与内核参数，`/sys` 面向设备与驱动模型。它们不是磁盘上的文件，读写由内核代码现场生成。`cat /proc/cpuinfo` 不是在读一个文件，而是在触发一段内核代码。

<pre class="layout">
┌──────────────────────────────────────────────────────────────┐
│ 应用：bash、nginx、python、你的程序                          │
├──────────────────────────────────────────────────────────────┤
│ 用户态运行库：glibc / musl（syscall 包装、malloc、NSS）      │
├─────────────── 系统调用边界（syscall instruction）───────────┤
│ 内核：调度器 │ 虚拟内存 │ VFS │ 网络栈 │ 驱动 │ 安全模块     │
├──────────────────────────────────────────────────────────────┤
│ 硬件：CPU │ 内存 │ NVMe │ 网卡 │ 中断控制器 │ 固件           │
└──────────────────────────────────────────────────────────────┘
</pre>

这张图的读法是：**越靠上越可替换，越靠下越难替换**。换 Shell 只影响一个用户，换 libc 要重编整个用户态，换内核要重启并承担驱动风险。线上事故里，「升级了一个用户态包」和「换了内核」的爆炸半径不在一个量级。

::: note 非科班补一层：特权级
CPU 用特权级把「能改页表、能关中断」的指令锁起来。x86-64 上内核跑在 ring 0，你的程序跑在 ring 3；ring 3 执行 `syscall` 才能跳进 ring 0。所谓「内核边界」，本质是 CPU 画出的一条硬件线，不是口头约定。
:::

::: errata 内核职责的五个误解
1. **「`printf` 是内核提供的」**——`printf` 在 glibc 里做格式化与缓冲，最后才调用内核的 `write`。
2. **「系统调用失败就是内核 bug」**——多数失败是参数、权限或资源上限，先看 `errno`，再怀疑内核。
3. **「可加载模块是安全沙箱」**——模块跑在 ring 0，一个空指针就能拖垮整机，没有地址空间隔离。
4. **「发行版升级会换掉内核行为」**——多数升级只动用户态；内核行为看 `uname -r` 和 `/boot/config-*`。
5. **「内核管所有 I/O」**——内核管设备与文件系统，用户态缓冲、格式化、协议解析都在库或程序里。
:::

### 0.1.2 小结

内核是唯一能碰硬件和页表的代码，它提供机制；发行版与用户态在其上决定策略。排障时先问「这是机制坏了，还是策略配错了」，再决定去看 `dmesg`、`/proc` 还是配置文件。如果只记住一件事，那就是：内核给你「能做」，发行版决定「默许做」。

::: method 即时自测 · 0.1.2
**Q1（记忆）** 内核的五块职责里，哪一块对应 `/proc/meminfo`？

**Q2（辨析）** 同一个 C 程序在 Ubuntu 和 Alpine 上调用 `open`，语义一样吗？默认 `umask` 一样吗？

**Q3（应用）** 服务日志出现 `Too many open files`，你的第一条命令是什么？为什么不是先调大 `ulimit`？

::: sol 答案
**A1** 虚拟内存：页表、缺页、映射与回收；`/proc/meminfo` 是内核把内存管理器的状态投影成文本。
**A2** `open` 的语义由内核系统调用保证，两边一样；默认 `umask`、挂载选项、防火墙属于发行版策略，可以不同。
**A3** 先 `ls -l /proc/<pid>/fd | wc -l` 与 `ls -l /proc/<pid>/fd` 找泄漏的 fd。调大上限只是推迟崩溃，泄漏仍在。
:::

## 0.1.3 GNU 用户态：内核之外的另一半 {#sec-0.1.3}

这一节回答：`printf` 和 `write` 都能输出，为什么一个可能丢数据、一个不会？glibc 到底替你做了什么？

::: preview 先抓住一件事
你在 C 里调用的 `printf`、`malloc`、`fopen` 都是 glibc 的函数，不是内核接口。glibc 负责格式化、缓冲、把参数搬进寄存器，最后才用 `write` 这样的系统调用进内核。fd 是这次调用要用的门牌号。
:::

先看一个会丢输出的程序：

```c
/* buffered.c —— stdio 缓冲与 write 的差别 */
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    printf("A");          /* 进 stdio 缓冲区，还没有进内核 */
    write(1, "B", 1);     /* 直接进内核 */
    _exit(0);             /* 不冲刷 stdio 缓冲区 */
}
```

```bash
cc -Wall -Wextra -O2 buffered.c -o buffered
./buffered
# 预期输出：B
```

你可能会猜输出是 `BA`。实际只有一个 `B`：`printf` 的 `A` 还躺在用户态缓冲区里，`_exit` 不做冲刷，进程一走，缓冲区就没了。

`strace -e trace=write ./buffered` 只会看到 `write(1, "B", 1) = 1`，看不到 `A`。glibc 负责「怎么说」，内核负责「送到哪」。

::: def 定义 0.1.5 · 文件描述符（file descriptor，fd） {#def-0.1.5}
fd 是一个小的非负整数，是进程打开文件表的下标。`open` 返回它，`read`/`write`/`close` 用它指代那个打开的文件。每个进程有独立的 fd 表，0、1、2 默认是标准输入、标准输出、标准错误。fd 不是文件本身，关掉 fd 也不等于删除文件。
:::

为什么会有这一层？1991 年 Linux 内核出现时，GNU 计划已经写了十年用户态工具，但缺一个能跑的内核。两者结合，才有了今天能用的系统。这段历史解释了一个现实：你在命令行里用的绝大多数命令，版权页上写的是 GNU，不是 Linus Torvalds。

GNU 用户态的核心组件：

| 组件 | 代表 | 你每天都在用的部分 |
|:--|:--|:--|
| Shell | Bash | 变量、管道、作业控制、脚本 |
| coreutils | `ls`、`cp`、`mv`、`rm`、`sort`、`date` | 文件与文本的基本操作 |
| 文本工具 | `grep`、`sed`、`awk`、`diff` | 第 0.5、0.6 章的全部内容 |
| 编译工具链 | `gcc`、`binutils`、`make` | 把源码变成 ELF |
| C 库 | glibc | 系统调用包装、`malloc`、DNS 解析、locale |

C 库是最容易被忽略的一层。它至少做四件事：

1. **系统调用包装**：`write(2)` 在你眼里是函数，在 CPU 眼里是一条 `syscall` 指令加寄存器约定。glibc 负责搬参数、处理 `errno`、在必要时重试 `EINTR`。
2. **内存管理**：`malloc` 在用户态维护空闲链表，只有不够时才向内核要页。这就是为什么 `free` 看到的 `RSS` 和程序「申请了多少」经常对不上。
3. **名字服务**：`getaddrinfo` 读 `/etc/nsswitch.conf`，再决定查 `/etc/hosts`、DNS 还是 systemd-resolved。`ping` 能通但浏览器打不开，常常卡在这一层。
4. **ABI 与符号版本**：同一个 `libc.so.6` 里可以有多个版本的 `memcpy` 符号，加载器按二进制所需的版本选择。这保证了旧程序在新系统上还能跑。

换一个 libc，行为会变。Alpine 用 musl，二进制更小、启动更快，但 `getaddrinfo` 的并发行为、`malloc` 的回收策略、locale 支持都与 glibc 不同。把 glibc 上编译的二进制直接丢进 Alpine 镜像，通常连加载器都找不到：

<div class="terminal" data-title="bash · 对比 glibc 与 musl">
<pre><span class="p">&#36;</span> ldd --version | head -1
ldd (Ubuntu GLIBC 2.39-0ubuntu8.3) 2.39
<span class="p">&#36;</span> file /bin/ls
/bin/ls: ELF 64-bit LSB pie executable, x86-64, dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2
<span class="p">&#36;</span> docker run --rm alpine:3.20 ldd --version 2&gt;&amp;1 | head -1
musl libc (x86_64)
</pre>
</div>

第一行告诉你 libc 版本；第二行的 `interpreter` 告诉你动态加载器的路径，这个路径是编译时写死的，不能靠 `LD_LIBRARY_PATH` 改。第三行说明 Alpine 用的是 musl。跨发行版分发二进制时，这三行比 `uname` 更有诊断价值。

::: note 非科班补一层：动态加载器
内核的 `execve` 只认得 ELF 头，不认得 `printf`。ELF 头里写着「先运行 `/lib64/ld-linux-x86-64.so.2`」，这个加载器再去打开 `libc.so.6`、解析符号、跳到 `main`。Ubuntu 的二进制被搬进 Alpine 时报 `not found`，缺的就是这个加载器，不是程序文件。
:::

::: errata GNU 用户态与 fd 的五个误解
1. **「`printf` 是系统调用」**——它是 glibc 函数；真正进内核的是缓冲区满或 `fflush` 之后的 `write`。
2. **「fd 就是文件」**——fd 是进程 fd 表的下标，同一个文件可以有两个 fd，同一个 fd 关掉后会被复用。
3. **「`strace` 没看到输出就是没输出」**——`printf` 可能还留在用户态缓冲区，`strace` 只看得见系统调用。
4. **「换 libc 只影响体积」**——musl 与 glibc 在 DNS 解析、`malloc` 回收、locale 上行为不同，二进制也互不通用。
5. **「GNU/Linux 是一个东西」**——Linux 是内核，GNU 是用户态工具与 C 库；`uname -o` 的写法只是把两层并列。
:::

### 0.1.3 小结

`printf` 在用户态攒数据，`write` 把字节交给内核，fd 是这两者之间的门牌号；glibc 还包办了 `malloc`、DNS、locale 与符号版本。换 libc 就是换掉这整层行为，不只是换一个 `.so` 文件。如果只记住一件事，那就是：内核只认 fd 和字节，其余都是 C 库替你说的。

## 0.1.4 发行版：把零件装成可运维的系统 {#sec-0.1.4}

这一节回答：为什么同样叫 Linux，Alpine 里没有 `systemctl`，`uname -r` 却和 Ubuntu 一模一样？

::: preview 先抓住一件事
发行版打包的是内核之外的一整套用户态：C 库、包管理器、init、默认配置、支持周期。容器换的是这套用户态，内核始终由宿主机提供。所以「容器里升级内核」不是一个可以成立的操作。
:::

先在一台 Ubuntu 24.04 上跑一个 Alpine 容器：

<div class="terminal" data-title="bash · 同一个内核，两套用户态（本机实测）">
<pre><span class="p">&#36;</span> docker run --rm busybox sh -c 'cat /etc/debian_version || echo no-debian-release; busybox | head -1; command -v systemctl || echo no-systemd; uname -r; uname -m'
no-debian-release
BusyBox v1.38.0 (2026-05-13 02:21:49 UTC) multi-call binary.
no-systemd
7.0.0-38-generic
aarch64
<span class="p">&#36;</span> uname -r                # 同一个虚拟机上的宿主内核
7.0.0-38-generic
</pre>
</div>

五行输出，三个来源。前两行是镜像里的用户态——这个 `busybox:latest` 连发行版的 release 文件都没有，能表明的只有「里面是 BusyBox 1.38.0 这一套命令」；第三行说明它的 init 不是 systemd；最后两行才是内核，而且和容器外面那条 `uname -r` 一模一样。

发行版换的是前三行，换不了后两行。这就是为什么「装个 Alpine 更省内存」成立，「装个 Alpine 换掉内核」不成立。顺带一条口径：本套件这台虚拟机是 aarch64，容器里 `uname -m` 也只会是 `aarch64`——想跑 x86 镜像得靠 `qemu-user-static` 那类模拟器，慢一个数量级；在 x86 机器上重复这五条命令，只有倒数第二行的内核 release 会不同（未实测，本套件没有 x86 主机）。

::: def 定义 0.1.2 · 发行版（distribution） {#def-0.1.2}
发行版是把内核、C 库、用户态工具、包管理器、初始化系统与一套默认配置打包、签名、测试并维护的整体。它承诺的是「这个组合经过集成测试，且有安全更新渠道」，而不只是「这些软件能放在同一台机器上」。
:::

判断两个系统是不是「同一个发行版」，看五件事：

| 组成 | Ubuntu 24.04 | Fedora 40 | Arch | Alpine |
|:--|:--|:--|:--|:--|
| 内核 | Ubuntu 6.8 | Fedora 6.9 | 滚动 | 6.6（lts） |
| C 库 | glibc 2.39 | glibc 2.39 | glibc | musl |
| 包格式 | `.deb` / apt | `.rpm` / dnf | `.pkg.tar.zst` / pacman | `.apk` / apk |
| init | systemd 255 | systemd 255 | systemd | OpenRC |
| 默认策略 | 偏保守、LTS | 偏新、半年 | 上游原样 | 极小、容器优先 |

这张表说明：发行版的差异主要不在内核，而在**包管理、默认配置与支持周期**。同一份 C 源码，在这四个系统上通常都能编译；但同一份 `.deb` 只在 Debian 系能用，同一套 systemd unit 在 Alpine 上不存在对应服务。

发行版还决定了三件运维上的事：

- **版本冻结策略**：Ubuntu LTS 冻结主版本、backport 安全补丁；Arch 滚动更新。前者可预测，后者新特性快，但每次 `pacman -Syu` 都可能需要人工介入。
- **默认安全策略**：AppArmor（Ubuntu）与 SELinux（Fedora/RHEL）的默认配置不同；防火墙前端不同；`umask` 与 `sudo` 默认组不同。
- **支持周期**：Ubuntu 24.04 标准支持到 2029，ESM 更长；Fedora 每个版本约 13 个月。把「能跑」当「能长期维护」是生产环境最常见的误判。

### 0.1.4.1 为什么容器镜像换不了内核

容器不是一台小虚拟机。它只是宿主机上的一组进程，加上 namespace（改视图）和 cgroup（限资源）。镜像里装的是用户态文件，通常连 `/boot/vmlinuz` 都没有。

所以 `docker run ubuntu:24.04` 里 `uname -r` 永远等于宿主机，`/etc/os-release` 才是镜像的。想换内核，只能换宿主机或开虚拟机；容器能换的只有装修，换不了地基。

::: note 非科班补一层：namespace 与 cgroup
namespace 让进程看到一套自己的视图：自己的 PID 编号、自己的网络接口、自己的挂载表。cgroup 则给这组进程设资源上限：最多用几个核、多少内存。两者都是内核功能，所以容器离不开内核，也换不掉内核。
:::

::: errata 关于「Linux 是什么」的五个误解
1. **「Linux 就是整个操作系统」**——严格说 Linux 是内核。完整系统还需要 libc、Shell、coreutils 与包管理；`uname -o` 输出 `GNU/Linux` 就是在提醒这一点。
2. **「发行版只是换个桌面主题」**——发行版还决定包版本、ABI、默认安全策略与支持周期。把 Ubuntu 的二进制直接复制到 Alpine，通常连动态加载器都对不上。
3. **「容器里的 `uname -r` 是容器自己的内核」**——容器与宿主机共享内核，`uname -r` 显示的是宿主机内核；`/etc/os-release` 显示的才是镜像里的用户态。
4. **「POSIX 认证过，行为就完全一致」**——POSIX 规定接口语义，不规定性能、错误文本、扩展接口与默认配置。`ps` 的列、`grep -P`、`systemd` 都不在 POSIX 里。
5. **「源码能编译，二进制就能随便拷」**——二进制兼容取决于架构、libc、动态加载器路径与符号版本，四者任一不匹配都可能失败。
:::

### 0.1.4 小结

发行版等于内核加 libc、包管理、init、默认策略与支持周期；换发行版主要换的是后四样，不是换内核。容器共享宿主机内核，所以镜像里能换用户态、换不了内核。如果只记住一件事，那就是：`uname -r` 归宿主机，`/etc/os-release` 归镜像。

## 0.1.5 标准：POSIX、FHS、LSB 各保证什么 {#sec-0.1.5}

这一节回答：换一个 Unix-like 系统，你在 Linux 上写的程序还要不要改？改多少？

::: preview 先抓住一件事
POSIX 保证源码级接口：同一份 C 代码，换系统重编大多能跑。它不保证二进制、性能、错误文本、扩展接口和默认配置。FHS 只管目录约定，LSB 管的是已基本退场的二进制兼容。
:::

先问系统一句「你支持哪版 POSIX」：

<div class="terminal" data-title="bash · 查标准版本">
<pre><span class="p">&#36;</span> getconf _POSIX_VERSION
200809
<span class="p">&#36;</span> getconf NAME_MAX /tmp
255
</pre>
</div>

`200809` 表示 POSIX.1-2008。这个数字是编译期与运行期共同的约定：头文件按它决定暴露哪些函数，`getconf` 按它报告实现的上限。

但「支持 POSIX」不等于「默认全给你」。写一个只用 `strdup` 的小程序：

```c
/* posix_strdup.c —— strdup 属于 POSIX.1-2008，不属于 ISO C */
#include <stdlib.h>
#include <string.h>

int main(void)
{
    char *p = strdup("hi");
    return p == NULL;
}
```

```bash
cc -std=c17 -Wall -Werror posix_strdup.c -o demo
# 预期：error: implicit declaration of function 'strdup'
cc -std=c17 -D_POSIX_C_SOURCE=200809L -Wall -Werror posix_strdup.c -o demo
# 通过
```

`-std=c17` 把编译器切到严格 ISO C 模式，glibc 就把 POSIX 扩展藏起来；加上特性测试宏，它才把 `strdup` 的声明放出来。标准保证的是「有这个接口」，不是「不声明也能用」。

| 标准 | 管什么 | 不管什么 | 怎么验证 |
|:--|:--|:--|:--|
| POSIX.1 | 系统调用、C 库接口、Shell 语法与工具行为 | 性能、默认配置、扩展接口 | `getconf`、`posixoptions`、编译时定义 `_POSIX_C_SOURCE` |
| FHS | 目录层级与用途（`/etc`、`/var`、`/usr`） | 具体文件、包管理器布局 | `man 7 hier`、`file-hierarchy(7)` |
| LSB | 旧式的发行版二进制接口与初始化脚本 | 现代 systemd 系统 | 已基本废弃，仅历史参考 |
| x86-64 SysV ABI | 函数调用约定、寄存器用途、栈对齐 | 系统调用号（那是内核 ABI） | 编译器与链接器默认遵守 |

POSIX 的价值在源码级可移植。你在 Ubuntu 上写的 `open`/`read`/`fork` 程序，只要不碰 Linux 扩展，拿到 macOS 或 FreeBSD 上重编也能跑。代价是你要放弃一些好用的 Linux 专有接口，比如 `epoll`（一次等一大批文件描述符就绪的接口）、`signalfd`、`inotify`、`O_TMPFILE`。

写可移植代码时，用特性测试宏把扩展显式打开：

```c
#define _POSIX_C_SOURCE 200809L   /* 只要 POSIX.1-2008 接口 */
#define _GNU_SOURCE               /* 或者：要 Linux/GNU 扩展，二者取一 */
#include <unistd.h>
#include <fcntl.h>
```

`_GNU_SOURCE` 会顺带打开 `_POSIX_C_SOURCE`，所以本书的用户态示例统一用它。反过来，如果你在写一个要进 BSD 的库，就不要用 `_GNU_SOURCE`，并定期用 `-std=c17 -pedantic` 编译一次，让编译器帮你抓扩展。

FHS 是目录约定，不是内核强制。`/bin` 在现代 Ubuntu 上已经是指向 `/usr/bin` 的符号链接（usrmerge），这是为了简化容器镜像与只读根文件系统。老脚本里写死 `/bin/ls` 通常还能跑，但 `ls -l /bin` 会暴露它是链接。`/etc` 放配置、`/var` 放可变数据、`/run` 放本次启动的运行时状态、`/proc` 与 `/sys` 是内核投影——这条规则在排查「配置到底改哪了」时非常有用。

LSB 曾经规定 `init` 脚本的返回码、`lsb_release` 命令与包命名。systemd 普及后它基本退出历史舞台，只在旧认证资料里出现。看到 `lsb_release` 不存在不必惊讶，读 `/etc/os-release` 更可靠。

### 0.1.5.1 POSIX 不保证什么

标准文本只写接口的签名与最低语义，下面这些它都不管：

- **输出格式**：`ps` 的列名与排序、`ls` 的颜色与时间格式，各实现可以不同。
- **扩展选项**：`grep -P`、`ls --color`、`sed -i` 都是 GNU 或 BSD 的扩展，换到 BusyBox 可能直接不认。
- **错误文本**：`strerror` 的措辞、大小写、翻译都不保证，脚本只能判断 `errno`，不能匹配字符串。
- **性能与资源**：同一次 `read` 的耗时、`malloc` 的回收策略，标准一个字都没写。
- **默认配置**：`umask`、`PATH`、默认 shell 指向谁，由发行版决定。

一个具体后果：你的部署脚本里写了 `grep -P`，在 Ubuntu 上跑得很好，进了 Alpine 的 BusyBox 就报「不认识 `-P`」。这不是 POSIX 的错，是你用了标准之外的扩展。

::: note 非科班补一层：源码可移植与二进制可移植
源码可移植指「同一份 C 代码，到另一个系统上重编就能跑」，这是 POSIX 的目标。二进制可移植指「编译好的文件直接拷过去就能跑」，这要求架构、libc、加载器路径、符号版本全都一致，LSB 想管的就是这件事。前者容易，后者很难。
:::

::: errata 标准相关的五个误解
1. **「POSIX 认证过，行为就完全一致」**——只保证接口语义，不保证性能、错误文本、扩展与默认配置。
2. **「FHS 是内核强制的」**——它是目录约定；内核只认挂载点与 inode，不检查你把配置放在哪。
3. **「LSB 还在广泛使用」**——systemd 普及后它基本退场，`lsb_release` 很多新系统根本不装。
4. **「用了 POSIX 函数就不用管宏」**——严格 `-std=c17` 下，glibc 会把 POSIX 声明藏起来，要显式打开特性测试宏。
5. **「`/bin/sh` 就是 bash」**——Ubuntu 上它通常是 dash，Alpine 上是 BusyBox ash；只写 POSIX 语法才可移植。
:::

### 0.1.5 小结

POSIX 管源码级接口，FHS 管目录约定，LSB 管过二进制兼容；三者都不是内核强制。写可移植代码，靠特性测试宏和「只用标准接口」的纪律，而不是靠发行版名字。如果只记住一件事，那就是：标准保证「有这个词」，不保证「说话的方式」。

::: method 即时自测 · 0.1.5
**Q1（记忆）** POSIX、FHS、LSB 各管哪一层？

**Q2（辨析）** 一段脚本在 Ubuntu 上用 `grep -P` 正常，到 Alpine 报错。是 POSIX 没实现好吗？

**Q3（应用）** 你要写一个能同时跑在 Ubuntu 和 FreeBSD 上的 C 库，编译时加哪个宏？要避开哪些接口？

::: sol 答案
**A1** POSIX 管系统调用与 C 库接口的语义；FHS 管目录层级与用途；LSB 管发行版之间的二进制接口与旧式 init 脚本。
**A2** 不是。`-P` 是 GNU 扩展，不在 POSIX 里；BusyBox 没有义务实现它。改用 `grep -E` 或先检测能力。
**A3** 用 `_POSIX_C_SOURCE=200809L`（不要 `_GNU_SOURCE`），避开 `epoll`、`signalfd`、`inotify`、`O_TMPFILE` 等 Linux 专有接口。
:::
:::

## 0.1.6 给机器做身份卡 {#sec-0.1.6}

这一节回答：ssh 登录一台出问题的机器，第一条命令应该是什么？为什么不是 `systemctl restart`？

::: preview 先抓住一件事
排障第一步是确认身份：哪台主机、哪个发行版、哪个内核、什么架构、什么时间。这些信息只读、几秒钟就能拿到，却能防止你在错误的机器上执行正确的命令。
:::

凌晨收到告警，你 ssh 上去，手比脑子快，先敲了 `systemctl restart nginx`。如果这台是备用机，你重启了一个不相干的服务；如果这是容器，`systemctl` 根本不存在。

重启有副作用，读身份没有。所以第一条命令应当只读，而且一次把关键字段拿全。四个命令足够：

<div class="terminal" data-title="bash · 读取系统身份">
<pre><span class="p">&#36;</span> cat /etc/os-release
PRETTY_NAME="Ubuntu 24.04.1 LTS"
NAME="Ubuntu"
VERSION_ID="24.04"
VERSION="24.04.1 LTS (Noble Numbat)"
VERSION_CODENAME=noble
ID=ubuntu
ID_LIKE=debian
HOME_URL="https://www.ubuntu.com/"
SUPPORT_URL="https://help.ubuntu.com/"
BUG_REPORT_URL="https://bugs.launchpad.net/ubuntu/"
UBUNTU_CODENAME=noble
<span class="p">&#36;</span> getconf LONG_BIT
64
<span class="p">&#36;</span> getconf PAGE_SIZE
4096
<span class="p">&#36;</span> dpkg --print-architecture
amd64
</pre>
</div>

`ID` 与 `ID_LIKE` 是给脚本用的：`ID=ubuntu`、`ID_LIKE=debian`，表示它兼容 Debian 的包管理习惯。`VERSION_ID` 是字符串，不要当浮点数比较（`"24.04"` 和 `24.4` 不是一回事）。`PRETTY_NAME` 只适合给人看，解析它会因为语言和版本格式变化而失败。

脚本里读这些字段，正确姿势是 source 它，而不是 `grep` + `cut`：

```bash
#!/usr/bin/env bash
set -euo pipefail

# /etc/os-release 是 shell 变量格式，source 比正则稳
if [[ -r /etc/os-release ]]; then
    . /etc/os-release
    printf 'distro=%s version=%s like=%s\n' \
        "${ID:-unknown}" "${VERSION_ID:-unknown}" "${ID_LIKE:-none}"
else
    printf 'distro=unknown (no /etc/os-release)\n'
fi

printf 'kernel=%s arch=%s page=%s\n' \
    "$(uname -r)" "$(uname -m)" "$(getconf PAGE_SIZE)"
```

关键点有三处：`[[ -r ... ]]` 先确认可读；`${ID:-unknown}` 给缺失字段兜底；`"$(...)"` 全部加引号，防止值里有空格。这个脚本在 Ubuntu、Fedora、Alpine 上都能跑，区别只是输出内容。

在容器里要特别小心（下面这两行是本机实测，`docker run --rm busybox` 那次已经在 0.1.3 出现过）：

```bash
docker run --rm busybox sh -c 'busybox | head -1; uname -r'
# BusyBox v1.38.0 (2026-05-13 02:21:49 UTC) multi-call binary.
# 7.0.0-38-generic   ← 这是宿主内核，不是镜像的内核
```

所以「容器里升级内核」是一个不成立的操作。容器能换的是用户态和内核暴露的接口视图（namespace、cgroup），换不了内核本身。需要不同内核时，用虚拟机，不是容器。

主机名、时区与 locale 是同一类「机器身份」，systemd 给了三个 `*-ctl` 命令统一读写：`status` 类查询不需要 root，`set-*` 需要且改完即生效并落盘，不必手工改配置文件：

| 命令 | 看什么 | 改什么 | 持久化位置 |
|:--|:--|:--|:--|
| `hostnamectl` | 主机名（static/transient/pretty 三种） | `set-hostname web01` | `/etc/hostname` |
| `timedatectl` | 时间、时区、NTP 同步状态 | `set-timezone Asia/Shanghai`、`set-ntp true` | `/etc/localtime`（指向 `/usr/share/zoneinfo/` 的链接） |
| `localectl` | `LANG` 与键盘布局 | `set-locale LANG=en_US.UTF-8` | `/etc/default/locale` |

排障时这三个 `status` 值得先扫一眼：NTP 不同步会让证书校验与定时任务整体漂移（`timedatectl` 的 `System clock synchronized`）；主机名不一致会让 `known_hosts`、监控注册对不上号；locale 影响的不只是提示语言，还有 `sort` 的排序规则（[0.6](ch06.md)）。`timedatectl set-time` 只能在 NTP 关闭时手工设时间，平时交给 `set-ntp true`。

::: note 非科班补一层：时间为什么算身份
TLS 证书有生效区间，系统时间偏出区间，`curl` 就报证书错误；`make`、`cron`、日志排序也都依赖时间。NTP 没同步时先修时间，再查业务，否则你会在错误的时序里找因果。
:::

::: errata 机器身份的五个误解
1. **「`PRETTY_NAME` 可以拿来解析」**——它给人看，语言和格式都会变；脚本用 `ID` 与 `VERSION_ID`。
2. **「`VERSION_ID` 可以当浮点数比较」**——它是字符串，`"24.04"` 和 `24.4` 不是一回事。
3. **「容器里的 `/etc/os-release` 是宿主机的」**——它是镜像的；`uname -r` 才是宿主机的。
4. **「改主机名要重启」**——`hostnamectl set-hostname` 立即生效并写入 `/etc/hostname`。
5. **「改了 `/etc/hosts` 就等于改主机名」**——那只是本机解析表，不影响内核里的 hostname。
:::

### 0.1.6 小结

身份卡有五格：主机名、发行版、内核、架构、时间；它们分别来自 `/etc/os-release`、`uname`、`getconf` 与 `timedatectl`。先读后动，能避免大部分「命令没错、机器错了」的事故。如果只记住一件事，那就是：排障先定位，再动手。

::: method 即时自测 · 0.1.6
**Q1（记忆）** 一条命令里同时拿到发行版 ID、版本号和内核版本，你会怎么写？

**Q2（辨析）** `cat /etc/os-release` 显示 Ubuntu 24.04，`uname -r` 是 5.15。哪个在说谎？

**Q3（应用）** 同事说「容器里的内核太旧，升一下镜像」。这句话哪里不成立？

::: sol 答案
**A1** `. /etc/os-release; printf '%s %s %s\n' "$ID" "$VERSION_ID" "$(uname -r)"`，先 source 再取值，缺失字段给默认值。
**A2** 都没说谎。前者描述用户态发行版，后者描述内核；云镜像、HWE/GA 轨道、容器宿主都会造成这种组合。
**A3** 容器不拥有内核，升级镜像只换用户态；内核版本由宿主机决定，要换只能换宿主机或改用虚拟机。
:::
:::

## 0.1.7 x86-64 与 ARM64：只讲会影响实验的差异 {#sec-0.1.7}

这一节回答：同一份 C 代码，在 x86-64 和 ARM64 上跑，哪些差异会真的改变实验结果？

::: preview 先抓住一件事
架构差异里，最容易被忽略的是页大小：x86-64 常见 4 KiB，ARM64 可以是 4、16 或 64 KiB。写死 4096 的代码在 16 KiB 页的机器上会对齐错、浪费内存，甚至 `mmap` 失败。系统调用号也不同，但 C 库把它挡住了。
:::

先看这台测试虚拟机上的同一组命令（实测：Ubuntu 24.04.5 aarch64，内核 `7.0.0-38-generic`，glibc 2.39）：

<div class="terminal" data-title="bash · ubuntu 24.04 / aarch64（实测）">
<pre><span class="p">&#36;</span> uname -m
aarch64
<span class="p">&#36;</span> getconf PAGE_SIZE
4096
<span class="p">&#36;</span> getconf LONG_BIT
64
</pre>
</div>

这台 ARM64 虚拟机的页大小就是 4096，和常见 x86-64 服务器一样——所以「ARM 上页更大」不是架构本身的规定，而是内核编译时的配置选项。ARM64 内核可以配成 4、16 或 64 KiB 页，x86-64 也支持 16 KiB，只是发行版通常不这么打包；本套件手上没有第二台机器，x86-64 那一列的具体读数属于**未实测（本套件只有 aarch64 虚拟机与 macOS arm64 写作机）**。真正要防的是这种写法：同一份 C 代码在 16 KiB 页的内核上，`sysconf(_SC_PAGESIZE)` 就会给你 16384，一切按 4096 对齐的代码都要重新检查。

本书的命令在两种架构上都成立，但有四处差异会直接影响实验结果：

| 差异 | x86-64 | ARM64 | 影响 |
|:--|:--|:--|:--|
| 页大小 | 通常 4 KiB | 4/16/64 KiB（依内核配置） | `mmap` 对齐、`stat` 块计数、性能测试 |
| 设备发现 | ACPI | 设备树（DT）为主，服务器用 ACPI | `/sys/firmware` 内容、驱动绑定方式 |
| 系统调用号 | 独立编号 | 独立编号 | 汇编、`strace` 原始输出不同；C 源码不受影响 |
| 多架构包 | `amd64` | `arm64` | 容器镜像、`.deb` 包、预编译二进制必须匹配 |

页大小最容易被忽略。`getconf PAGE_SIZE` 在本套件这台 Parallels 的 ARM64 虚拟机上实测是 4096，而某些 ARM 服务器与 Android 内核是 16384；常见 x86 服务器是 4096。一个按 4 KiB 对齐、假设「一页就是一个块」的程序，在 16 KiB 页的系统上可能浪费 4 倍内存，或者 `mmap` 失败。

为什么页大小会变？内核用页表把虚拟地址翻译成物理地址，页表的最小条目覆盖一个页。页越大，条目越少、翻译越快，但一次分配的最小单位也越大。写底层代码时用 `sysconf(_SC_PAGESIZE)`，不要写死 4096。

::: note 非科班补一层：页表与页
把页表想成一本地址翻译字典：程序给出虚拟地址，CPU 查字典换成物理地址。「页」是这本字典的最小条目，页大小就是一条覆盖多少字节。16 KiB 页意味着条目更少、每条更粗，小对象更容易浪费。
:::

设备树的差异只在读 `/sys/firmware/devicetree` 或写驱动时出现。日常运维感知不到，除非你在 ARM 服务器上排查网卡、PCIe 或中断亲和性。

系统调用号不同，但 C 库把差异屏蔽了。`strace` 在两种架构上都能显示 `openat(AT_FDCWD, ...)`，因为它是按架构解析的；只有你手写汇编或看内核原始日志时，才会遇到编号差异。

多架构是容器时代最实际的坑：

```bash
# 在 amd64 上构建 arm64 镜像（需要 qemu binfmt）
docker buildx build --platform linux/arm64 -t app:arm64 .
# 查看一个二进制或镜像支持什么架构
file ./app
docker image inspect app:arm64 --format '{{.Architecture}}'
```

在 Apple Silicon 上拉一个只提供 `amd64` 的镜像，Docker 会用 qemu 模拟，能跑但慢一个数量级；涉及 `perf`、`io_uring`（把提交 I/O 请求排队化的高吞吐接口）、某些 ioctl 的实验可能直接失败。看到「同样的命令在同事机器上很快」时，先确认架构与模拟层，再怀疑代码。

::: errata 架构相关的五个误解
1. **「页大小就是 4096」**——它由架构与内核配置决定，ARM64 可以是 4、16、64 KiB。
2. **「ARM64 一定用设备树」**——服务器级 ARM64 常用 ACPI，只有嵌入式与开发板以设备树为主。
3. **「系统调用号跨架构一样」**——x86-64 与 ARM64 编号完全不同，只有 `SYS_*` 宏能跨架构。
4. **「源码能编译，二进制就能拷」**——指令集、ABI、加载器路径任一不同都要重编。
5. **「qemu 模拟只是慢一点」**——依赖硬件计数器、特定 ioctl 或内核特性的实验可能直接失败。
:::

### 0.1.7 小结

x86-64 与 ARM64 的差异里，页大小、设备发现方式、系统调用号、包架构这四项会直接影响实验。页表负责地址翻译，页大小是它的最小条目；写底层代码要取运行时值。如果只记住一件事，那就是：不要假设 4096，也不要假设 `uname -m` 只影响下载链接。

::: method 即时自测 · 0.1.7
**Q1（记忆）** 页大小由谁决定？程序里应该用哪个接口取？

**Q2（辨析）** 一台 ARM64 服务器上没有 `/sys/firmware/devicetree`，能说明它启动方式有问题吗？

**Q3（应用）** 同事的 `amd64` 镜像在你的 ARM64 机器上能跑但很慢，哪些实验可能直接失败？

::: sol 答案
**A1** 由 CPU 架构与内核配置共同决定；用 `sysconf(_SC_PAGESIZE)` 或 `getconf PAGE_SIZE` 取运行时值。
**A2** 不能。服务器级 ARM64 常用 ACPI 启动，设备树只在部分平台出现；先看 `/sys/firmware/efi` 与 `dmesg`。
**A3** 依赖 `perf` 硬件计数器、`io_uring`、特定 ioctl 或内核模块的实验；它们要么报错，要么结果不可信。
:::
:::

## 0.1.8 把一条命令拆回四层 {#sec-0.1.8}

这一节回答：你按下回车到看见一列文件名，中间到底经过谁的手？每一层能不能拿出证据？

::: preview 先抓住一件事
一条 `ls` 要经过 Shell、动态加载器、libc、内核四层，才把字节送到终端。`strace` 是这条时间线的行车记录仪：它只记录系统调用，但足以指出每一层在哪里交接。
:::

上一节量的是架构差异：页多大、包是哪个架构。这一节把镜头拉近，量一条命令经过了几双手。

分层图容易画，难的是在真实系统里指出每一层的证据。`strace` 能把一个进程发出的系统调用逐条打印出来，正好用来验证「哪些事是内核做的」。

把 `ls` 的输出丢掉，只看它和内核说了什么：

<div class="terminal" data-title="bash · 跟踪 ls 的系统调用">
<pre><span class="p">&#36;</span> strace -f -e trace=execve,openat,getdents64,write ls /etc &gt;/dev/null
execve("/usr/bin/ls", ["ls", "/etc"], 0x7ffd3c2a1e10 /* 58 vars */) = 0
openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3
openat(AT_FDCWD, "/lib/x86_64-linux-gnu/libc.so.6", O_RDONLY|O_CLOEXEC) = 3
openat(AT_FDCWD, "/etc", O_RDONLY|O_NONBLOCK|O_CLOEXEC|O_DIRECTORY) = 3
getdents64(3, 0x55d1c0e2a2a0, 32768) = 328
write(1, "adduser.conf\n", 13) = 13
write(1, "alternatives\n", 13) = 13
<span class="p">&#36;</span> strace -c -e trace=openat ls /etc &gt;/dev/null
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
100.00    0.000021           3         8           openat
------ ----------- ----------- --------- --------- ----------------
100.00    0.000021           3         8          0 total
</pre>
</div>

逐行读这段输出：

1. `execve` 是 Shell 调用的最后一个系统调用。它把 `/usr/bin/ls` 换成当前进程的地址空间；`ls` 自己并没有「启动」，它只是替换了 Shell 的子进程。
2. 第一个 `openat` 打开 `/etc/ld.so.cache`，这是动态加载器在找库。此时 `ls` 的 `main` 还没开始执行。
3. 第二个 `openat` 打开 `libc.so.6`。flags 里的 `O_CLOEXEC` 表示执行新程序时关闭这个 fd，避免泄漏。
4. `openat("/etc", O_DIRECTORY)` 才是 `ls` 的业务：打开目录。
5. `getdents64` 读目录项。目录内容由内核的文件系统代码提供，`ls` 只负责格式化。
6. `write(1, ...)` 把格式化结果写到 fd 1。你在终端看到的内容，最终都是这样一组 `write`。

注意 `ls` 从未直接读磁盘。它打开目录、读目录项，内核的页缓存负责把磁盘块变成内存里的数据。如果目录刚被访问过，`getdents64` 可能完全不触发 I/O。这就是为什么「`ls` 很快」不能证明磁盘很快——它可能只证明了缓存很热。

把这些动作排到时间轴上，就是一条四层交接的线：

1. **T0 终端与 Shell**：你按下回车，终端把一行字节交给 bash。bash 先做展开（`ls` 没有通配符，这一步什么也不做），再按 `$PATH` 找到 `/usr/bin/ls`。
2. **T1 `fork` 与 `execve`**：bash 复制一个自己，得到子进程；子进程调用 `execve`，把地址空间（这个进程能看见的整块内存）换成 `ls`。从这一刻起，PID 没变，程序变了。
3. **T2 加载器**：内核只认得 ELF 头（可执行文件的格式说明），不认得 `printf`。它先把头部写着的 `/lib64/ld-linux-x86-64.so.2` 映射进来，控制权先交给加载器，不是交给 `main`。
4. **T3 libc**：加载器打开 `ld.so.cache` 与 `libc.so.6`，做符号重定位（把 `printf` 这类名字换成 libc 里的真实地址），跳到 `_start`；`_start` 备好 `argc`、`argv`，再调用 `ls` 的 `main`。
5. **T4 内核**：`main` 里的 `opendir`、`readdir` 变成 `openat` 与 `getdents64`，`printf` 的字节变成 `write`。VFS（虚拟文件系统，统一管理各类文件系统的接口层）、权限检查、页缓存、终端驱动都在这一段。

每一段都能单独失败，失败的样子也不一样。Shell 找不到命令，报 `command not found`；加载器找不到库，报 `error while loading shared libraries`；`main` 逻辑错了，输出不对但系统调用全成功；内核拒绝，返回 `EACCES` 或 `ENOENT`。排障时先认「这是哪一段的错」，比背命令有用。

::: note 非科班补一层：fd 与 `execve`
fd（file descriptor，文件描述符）是进程打开文件表的下标，一个小整数。`openat` 返回 3，意思是「这个目录记在你表的第 3 格」；后面 `getdents64(3, ...)` 就用这个号取内容。这张表分三层：每个进程一张描述符表，全系统一张打开文件表，再往下是 vnode 表；fd 只是最上面那层的下标。打开文件表项记偏移量与引用计数，vnode 表项记文件本身（inode、大小、权限）；两个 fd 可以指向同一个打开文件表项。

`execve`（execute program）是「把当前进程整个换成一个新程序」的系统调用。它保留 PID、fd 表和用户身份，丢掉旧的代码、数据、栈；所以 `ls` 不是 bash 启动的另一个进程，而是 bash 的子进程换了内容。`execve` 成功时不返回，只有失败才返回 -1。
:::

这张表把四层与证据对上：

| 层 | 在这次跟踪里的证据 | 如果这一层出问题，你会看到 |
|:--|:--|:--|
| Shell | `execve` 之前的 `fork`/`clone`（本例未显示） | 命令找不到、通配符没展开 |
| 动态加载器 | `ld.so.cache`、`libc.so.6` 的 `openat` | `not found`、`undefined symbol` |
| libc | `write` 的参数格式化（`strace` 只看到字节） | 输出错乱、locale 相关异常 |
| 内核 | `openat`、`getdents64`、`write` 的返回值 | `EACCES`、`ENOENT`、`ENOSPC` |

::: errata 拆命令时的四个误判
1. **「`execve` 启动了一个新进程」**——它替换当前进程的地址空间，PID 与 fd 表都保留；`ls` 的 PID 就是 bash 子进程的 PID。
2. **「`strace` 里没有 `fork`，所以 Shell 没 fork」**——记录从目标进程的 `execve` 才开始，`fork` 由 bash 或 strace 完成，发生在记录之前；要连父进程一起看，得用 `strace -f` 跟 bash。
3. **「第一个 `openat` 打开 `/etc`，说明 `ls` 已经开始干活」**——它打开的是 `ld.so.cache`，此时 `main` 还没执行；顺序本身就是证据。
4. **「`ls` 很快，所以磁盘很快」**——目录项可能全在页缓存里，`getdents64` 一次真实 I/O 都没触发。
:::

### 0.1.8 小结

一条命令的时间线是：Shell 展开并 `fork`，`execve` 换程序，加载器找库，libc 扶起 `main`，内核用 fd 完成读写。`strace` 只记录最后一段，但返回值、打开顺序和调用次数足以反推前三段。如果只记住一件事，那就是：Shell 只负责换程序，剩下的活由加载器、libc 和内核分工。

::: method 即时自测 · 0.1.8
**Q1（记忆）** `execve` 之后，进程的 PID 和 fd 表会变吗？

**Q2（辨析）** `strace` 输出里第一个 `openat` 打开的是 `ld.so.cache`，为什么不是 `/etc`？

**Q3（应用）** 同事说 `ls /etc` 慢是磁盘慢，你用哪条命令证实或证伪？

::: sol 答案
**A1** PID 不变，fd 表保留（标了 `O_CLOEXEC` 的会在换程序时关闭）；被换掉的是代码、数据和栈。
**A2** 因为 `ls` 的 `main` 还没跑。内核先启动 ELF 头指定的加载器，加载器要找到 libc 才能把程序扶起来。
**A3** 跑两次 `strace -T -c -e trace=openat,getdents64 ls /etc`，看 `getdents64` 的耗时；第二次明显变快说明是页缓存。再用 `iostat -x 1` 看磁盘利用率，别用感觉判断。
:::
:::

## 0.1.9 文档即证据：man 的分区与查法 {#sec-0.1.9}

这一节回答：同一个词在 `man 1`、`man 2`、`man 3` 里各有一套说法，凭什么判断哪一页才属于你要找的那一层？

::: preview 先抓住一件事
man 按「谁提供这个接口」分区：1 是命令，2 是系统调用，3 是 C 库，5 是文件格式，7 是约定，8 是管理命令。查内核行为只看 2 区；读 3 区就容易把 libc 的缓冲和 `errno` 当成内核行为。
:::

先看一个会把人带偏的例子。你想查 `printf` 的缓冲规则，随手敲了 `man printf`：

```bash
man printf      # 先命中 printf(1)：coreutils 的命令行工具
man 3 printf    # 才是 glibc 的格式化输出函数
```

`printf(1)` 讲的是 shell 里那个命令怎么解析 `%s`、怎么处理转义；它和 C 程序里的 `printf` 同名，却是两个东西。发行版按配置的搜索顺序取第一页，换个 `MANPATH` 结果就可能不同。区号是唯一稳定的定位方式。

Linux 的文档不是「一本书」，而是按区（section）组织的 man page。同一件事在不同区里由不同层解释，读错区就会把 libc 行为当成内核行为。

| 区 | 内容 | 例子 | 谁维护 |
|:--|:--|:--|:--|
| 1 | 用户命令 | `ls(1)` | coreutils |
| 2 | 系统调用 | `open(2)`、`read(2)` | 内核文档 / man-pages |
| 3 | C 库函数 | `printf(3)`、`malloc(3)` | glibc |
| 4 | 设备文件 | `null(4)`、`tty(4)` | 内核文档 |
| 5 | 文件格式与配置 | `passwd(5)`、`fstab(5)`、`proc(5)` | 发行版 / 内核 |
| 7 | 概览与约定 | `path_resolution(7)`、`hier(7)`、`signal(7)` | man-pages |
| 8 | 管理命令 | `mount(8)`、`systemctl(8)` | util-linux / systemd |

查系统调用必须用 `man 2`。`man read` 在多数系统上会落到 `read(2)`；同名页不止一个时，显式写区号才不会靠运气。查 C 库包装则用 `man 3`，两者的差别正是本章强调的边界：

```bash
man 2 read      # 内核视角：返回值、EINTR、短读
man 3 fread     # stdio 视角：缓冲、EOF 标志、线程安全
man 7 signal    # 信号语义、默认动作、可捕获性
man 7 path_resolution   # 一个路径字符串如何变成 inode
```

`man 7 path_resolution` 值得在学权限之前读一遍。它解释了符号链接、`.`、`..`、挂载点如何逐段解析，以及为什么 `openat` 的 `dirfd` 能改变解析起点。这些规则由内核实现，不是 Shell 的约定。

不知道系统调用叫什么，`man 2 syscalls` 给出全表；`man -a open` 把各区同名页依次打开；`man -w 2 open` 只打印文件路径，适合脚本。

一页 man 有固定骨架，按顺序读最省时间：

| 段 | 回答什么 | 例子（`man 2 open`） |
|:--|:--|:--|
| NAME | 一句话说明这是什么 | `open, openat - open and possibly create a file` |
| SYNOPSIS | 头文件、函数签名、特性测试宏 | `#include <fcntl.h>`，返回 `int` |
| DESCRIPTION | 参数与 flags 的语义 | `O_DIRECT`、`O_CLOEXEC` 各是什么 |
| RETURN VALUE | 成功与失败各返回什么 | 成功返回 fd；失败返回 -1 并设置 `errno` |
| ERRORS | 这个调用可能设哪些 `errno` | `EACCES`、`ENOENT`、`EISDIR` |
| VERSIONS | 从哪个内核或 libc 版本起可用 | `O_DIRECT` 从 2.4.10 起 |
| NOTES / BUGS | 边界、坑、实现差异 | 对齐要求、文件系统支持差异 |
| SEE ALSO | 相关页 | `read(2)`、`lseek(2)`、`openat2(2)` |

判断一个接口「有没有、从哪版开始」，看 VERSIONS 比看来路不明的博客可靠；判断「失败时该查哪个 `errno`」，看 ERRORS。

读错区最典型的后果，是把 libc 的行为记到内核头上。程序退出前少了一行日志，你查 `man 3 printf`，看到「输出到终端时按行缓冲」。如果把这句话记成「内核按行写」，就会去追问 `write` 为什么吞了半行。实际分工是：行缓冲是 stdio 在终端上的策略，`write` 只认字节数；程序用 `_exit` 退出时，缓冲区根本没冲刷。3 区的结论只能解释 libc，解释不了内核。

::: note 非科班补一层：区号与 `errno`
区号不是章节号，而是「这个接口由谁提供」的柜子编号：内核提供的放 2 区，C 库提供的放 3 区。写法 `open(2)` 读作「open，2 区」，括号里的数字就是区号。
`errno` 也是好例子：`errno(3)` 在 3 区，因为它是 glibc 的线程局部变量。内核不写 `errno`，它返回一个负的错误码；glibc 的包装把错误码取反写进 `errno`。在 3 区看到「失败会设置 `errno`」，要补一句「这是包装层做的」。
:::

man page 也有边界。它描述接口，不描述你的发行版默认配置；`man 5 fstab` 不会告诉你 Ubuntu 安装器写了什么。遇到配置问题，还要看 `/usr/share/doc/<pkg>/`、`systemctl cat`、`/etc` 下的实际文件。遇到内核行为问题，`man 2` 加内核源码比二手博客可靠。

不知道命令名时，`man` 本身帮不上忙。两套索引命令解决「先找到页，再读页」：

| 命令 | 查什么 | 例子 |
|:--|:--|:--|
| `apropos <词>` / `man -k <词>` | 在 man page 的简述里搜关键词 | `apropos copy` |
| `whatis <命令>` / `man -f <命令>` | 给出一行简述，确认是不是要找的页 | `whatis cp` |
| `help <内建>` | bash 内建命令的帮助（不在 man 里） | `help cd`、`help -d` |
| `info <主题>` | GNU 项目的 Info 文档，通常比 man 更详细 | `info coreutils` |

`apropos` 读的是 `whatis` 数据库；新装的包如果搜不到，先 `sudo mandb` 重建索引。`help` 只对内建命令有效，不带参数会列出全部内建；`man cd` 在多数系统上找不到，因为 `cd` 是 Shell 内建而不是独立程序。

::: note 版本与证据
本书的结论默认标注环境：Ubuntu 24.04、Linux 6.8、glibc 2.39、systemd 255、bash 5.2。换版本时要复核三类东西：系统调用语义（很少变）、libc 实现（偶尔变）、发行版默认配置（经常变）。man page 末尾的 `Linux man-pages 6.06` 之类的版本号，是你判断「这条结论有多新」的线索。
:::

::: errata 查 man 的六个坑
1. **「`man printf` 就是 `printf(3)`」**——不一定，默认先命中 `printf(1)`，那是 coreutils 的命令；显式写区号才稳。
2. **「3 区的函数都会进内核」**——`strlen`、`strcpy` 一行系统调用都没有；`printf` 也只在缓冲区满或冲刷时才调 `write`。
3. **「`errno` 是内核变量」**——内核返回负的错误码，`errno` 是 glibc 的线程局部变量。
4. **「man 页会告诉我发行版默认配置」**——不会。`man 5 fstab` 不告诉你安装器写了什么，要看 `/etc/fstab` 本身。
5. **「`apropos` 搜不到就是没有」**——可能只是 `whatis` 索引没建，先 `sudo mandb`。
6. **「man 页一定和本机内核一致」**——man-pages 可能比内核新或旧；用 VERSIONS 段对照 `uname -r`。
:::

### 0.1.9 小结

man 的区号就是分层图的索引：2 区内核、3 区 C 库、5 区配置格式、7 区约定、8 区管理命令。先按区定位，再按 NAME、SYNOPSIS、RETURN VALUE、ERRORS 的顺序读，最后用 VERSIONS 对照本机版本。如果只记住一件事，那就是：查内核看 2 区，查 C 库看 3 区，别把两区的结论混着用。

::: method 即时自测 · 0.1.9
**Q1（记忆）** `open(2)`、`printf(3)`、`fstab(5)`、`systemctl(8)` 各在哪个区，分别由谁提供？

**Q2（辨析）** 你读 `man 3 printf` 看到「行缓冲」，能否据此推断内核的 `write` 也按行处理？

**Q3（应用）** 要确认 `O_DIRECT` 在目标内核上是否可用，你查哪一页的哪一段？还要跑什么命令？

::: sol 答案
**A1** 2 区是内核系统调用；3 区是 glibc；5 区是配置文件格式（发行版与内核文档）；8 区是管理命令（systemd、util-linux）。

**A3** 查 `man 2 open` 的 DESCRIPTION 与 VERSIONS，再用 `uname -r` 对照；最后写个小程序用 `O_DIRECT` 打开文件，看返回值和 `errno`。

## 0.1.10 发行版对比：支持周期、ABI 与选型 {#sec-0.1.10}

这一节回答：同样叫 Linux，为什么 Ubuntu 的二进制在 Alpine 上跑不起来，为什么「能装」不等于「能维护五年」。

::: preview 先抓住一件事
发行版的差异主要不在内核版本，而在四件事：libc、包管理、默认策略、支持周期。libc 决定二进制能不能跑，包管理决定怎么装，默认策略决定默认开什么，支持周期决定出了 CVE 谁来修、修多久。
:::

上一节学的是怎么查证据：查内核看 2 区，查配置看 5 区。这一节用同一套证据比较发行版：不看宣传页，看 libc、包、默认策略和补丁窗口。

真正决定一台机器行为的是这些零件的**组合与维护承诺**。把发行版当成「主题不同的同一个系统」，是选型和排障时最贵的误解。上游内核只有一个，发行版做的是选版本、打补丁、配 config，再把用户态装配起来。

先看八个常见发行版的硬差异：

| 发行版 | 上游基础 | C 库 | init | 包管理 | 内核策略 | 支持窗口（量级） | 升级模型 |
|:--|:--|:--|:--|:--|:--|:--|:--|
| Ubuntu 24.04 LTS | Debian | glibc 2.39 | systemd 255 | `.deb` / apt | 6.8 GA，另有 HWE 轨道 | 5 年 + ESM | 固定版本 + backport |
| Debian 12 | 独立 | glibc 2.36 | systemd 252 | `.deb` / apt | 6.1 LTS | 3 年安全 + 2 年 LTS | 固定版本 |
| Fedora 40 | 独立 | glibc 2.39 | systemd 255 | `.rpm` / dnf | 更新较快 | 约 13 个月 | 快速迭代 |
| RHEL 9 | Fedora 派生 | glibc 2.34 | systemd 252 | `.rpm` / dnf | 5.14 长期 backport | 10 年 | 固定 + backport |
| AlmaLinux 9 | RHEL 重建 | 同 RHEL 9 | 同 RHEL 9 | `.rpm` / dnf | 同 RHEL 9 | 约 10 年 | 跟随 RHEL |
| Alpine 3.20 | 独立 | musl 1.2 | OpenRC | `.apk` / apk | 6.6 | 约 2 年 | 固定版本 |
| Arch Linux | 独立 | 最新 glibc | systemd | `.pkg.tar.zst` / pacman | 上游最新 | 滚动 | 滚动更新 |
| NixOS 24.11 | 独立 | glibc | systemd | Nix | 上游较新 | 约 7 个月 | 声明式、可回滚 |

这张表里最容易被误读的是「内核」一列。几个发行版的内核版本看起来差很多，但上游内核只有一个，发行版只是选了不同基线、打了不同补丁、开了不同 `CONFIG_`。真正的分岔在另外四项：

- **libc**：决定二进制能不能跑。glibc 与 musl 的加载器路径、符号版本、`getaddrinfo` 行为都不同；同一个 `.deb` 搬到 Alpine，连解释器都找不到。
- **包管理**：决定你怎么装、怎么查、怎么回滚。`.deb`、`.rpm`、`.apk`、Nix 的包名、依赖解析、文件归属查询完全不同。
- **默认策略**：决定你排障时看到什么。AppArmor 还是 SELinux、`nftables` 还是 `firewalld`、默认 `umask` 是 022 还是 002，都是发行版选的。
- **支持周期**：决定出了 CVE 谁修、修多久。Ubuntu LTS 五年、RHEL 十年、Fedora 十三个月，对应完全不同的升级预算。

表里还有三个缩写。GA 是装机自带的内核轨道，HWE（hardware enablement）是随新硬件更新的内核轨道，ESM 是标准支持期之后的延长安全维护。前两个会改变 `uname -r` 的版本号，第三个只延长补丁窗口，都不改变排障方法。

选型可以压成三条线：

1. **二进制兼容线**：你的产物要跑在哪些机器上？如果交付二进制，构建环境的 glibc 不能高于目标环境。经验规则是「在最老的受支持发行版上构建」，或者用容器/静态链接把 libc 依赖消掉。Python 的 `manylinux` 轮子、Go 的默认静态链接，都是这条线的工程化答案。
2. **支持周期线**：服务器跑几年？Ubuntu LTS 的 5 年标准支持、RHEL 的 10 年、Fedora 的 13 个月，对应的是完全不同的升级预算。把 Fedora 装到生产数据库上，不是技术错误，是维护模型错配。
3. **运维习惯线**：团队熟悉 apt 还是 dnf？用 SELinux 还是 AppArmor？有没有 Satellite/Landscape 这类集中管理？换发行版最贵的往往不是装系统，而是重写 runbook 与监控项。

同一个 C 项目在四个发行版上，装依赖的命令就不同：

| 需求 | Debian/Ubuntu | Fedora/RHEL | Alpine | Arch |
|:--|:--|:--|:--|:--|
| 编译工具链 | `build-essential` | `gcc make`（或 `@development-tools`） | `build-base` | `base-devel` |
| OpenSSL 头文件 | `libssl-dev` | `openssl-devel` | `openssl-dev` | `openssl` |
| 装构建依赖 | `apt build-dep .` | `dnf builddep foo.spec` | `apk add --virtual` | `makepkg -s` |
| 查文件属于哪个包 | `dpkg -S /path` | `rpm -qf /path` | `apk info --who-owns /path` | `pacman -Qo /path` |
| 查包装了哪些文件 | `dpkg -L pkg` | `rpm -ql pkg` | `apk info -L pkg` | `pacman -Ql pkg` |

这张表说明：「源码能编译」只是起点，构建脚本要为每个发行版写分支。CMake/Meson 能屏蔽一部分差异，但包名和 `pkg-config` 路径仍然要按发行版处理。

「二进制兼容」说起来抽象，落到命令上只有两行：

```bash
# 构建机上：看这个二进制要求哪些 glibc 符号版本
objdump -T ./app | grep -o 'GLIBC_[0-9.]*' | sort -Vu | tail -3
# 目标机上：看它装的到底是哪版 glibc
ldd --version | head -1
```

如果构建机要求 `GLIBC_2.34`，目标机只有 2.31，运行时会报 `version 'GLIBC_2.34' not found`。这不是程序写错了，是 ABI 对不上。想彻底躲开，就在最老的受支持系统上构建，或者静态链接，或者把依赖打进容器镜像。

::: note 非科班补一层：ABI 与 backport
ABI（application binary interface，应用二进制接口）是编译好的程序与系统之间的约定：参数放哪个寄存器、结构体怎么排布、符号叫什么名字、版本号是多少。源码能编译，只说明名字对得上；ABI 对不上，二进制就跑不起来。
backport 是把新版本里的一个补丁移植回老版本。版本号可能不变，行为却变了；所以判断「这个漏洞修没修」，要看发行版勘误（Ubuntu 的 USN、RHEL 的 RHSA），不能只看 `--version`。
:::

支持周期不是一张营销表，它会变成具体的补丁行为。以 OpenSSL 为例：RHEL 9 会在整个 10 年里 backport 安全修复，但主版本可能一直不变；Arch 会直接升级到新主版本，依赖它的程序要跟着重编。前者稳定但缺少新特性，后者新但每次 `pacman -Syu` 都可能需要人工介入。判断「这个漏洞修没修」，不能只看版本号，要看发行版的勘误（Ubuntu 的 USN、RHEL 的 RHSA）。

::: note 发行版内核不是上游 vanilla
`uname -r` 的 `6.8.0-45-generic` 里，`6.8.0` 是上游基线，`-45` 是 Ubuntu 的 ABI 编号，`generic` 是配置风味（还有 `lowlatency`、`kvm`、`aws`）。同一台上游特性是否存在，要查 `/boot/config-$(uname -r)` 与发行版 backport 说明：

```bash
grep -E 'CONFIG_(HZ|PREEMPT|CGROUP|PSI)=' /boot/config-$(uname -r)
uname -v        # #45-Ubuntu SMP PREEMPT_DYNAMIC ... 构建字符串
```

`CONFIG_HZ=250` 与 `CONFIG_HZ=1000` 会改变定时精度与上下文切换开销；`CONFIG_PREEMPT_DYNAMIC` 表示抢占模式可在启动时切换。这些差异不会出现在 `uname -a` 的主版本号里，却直接影响性能实验的结论。
:::

::: errata 发行版选型的六个误判
1. **「发行版差异就是内核版本差异」**——上游内核只有一个；差异主要在 libc、包管理、默认策略与支持周期。
2. **「能装就能长期维护」**——Fedora 约 13 个月、Ubuntu LTS 5 年、RHEL 10 年，对应完全不同的升级预算。
3. **「版本号没变就是没修」**——backport 会保持版本号；要看 USN、RHSA 这类勘误。
4. **「静态链接就没有兼容问题」**——架构、内核 ABI、NSS、证书与 locale 数据仍可能不匹配。
5. **「滚动更新更省心」**——每次 `pacman -Syu` 都可能有需要人工介入的重建或配置迁移。
6. **「换发行版只是重装」**——包名、unit、监控项、runbook 都要重写，成本常高于安装本身。
:::

### 0.1.10 小结

发行版的差异沿四条线展开：libc 决定二进制，包管理决定怎么装，默认策略决定默认行为，支持周期决定维护成本；内核版本反而最不该拿来当区分依据。选型就是按交付方式、运行年限和团队习惯给这四条线排优先级。如果只记住一件事，那就是：选发行版，是选「谁在什么期限内替你修什么」。

**Q2（辨析）** 客户说「两个都是 Linux，编译好的程序直接拷过去就行」，你用哪条命令给出反证？

## 0.1.11 内核模块：运行在 ring 0 的可插拔代码 {#sec-0.1.11}

这一节回答：`.ko` 是什么，`modprobe` 与 `insmod` 差在哪，为什么「加载一个模块」可能直接影响整机稳定性。

::: preview 先抓住一件事
内核模块是能插进内核的代码，不是插件沙箱：它和内核共享地址空间，同样跑在 ring 0（CPU 的最高特权级）。`modprobe` 按名字和依赖加载，`insmod` 只认文件；判断内建还是可加载，看 `modules.builtin` 与 `modinfo`。
:::

先看一个会让人误判的现象。系统明明挂载着 ext4 根分区，`lsmod | grep ext4` 却一行都没有：

```bash
lsmod | grep ext4 || echo "not listed"
# not listed
modinfo -F filename ext4
# (builtin)
```

`lsmod` 读的是 `/proc/modules`，只列「运行时加载进来的模块」。`ext4` 在很多发行版里被直接编进 `vmlinuz`，所以它不在列表里，却在工作。「没有这个模块」和「这个功能不存在」是两件事。

::: def 定义 0.1.3 · 内核模块（kernel module） {#def-0.1.3}
内核模块是一个可被内核在运行时链接的 ELF 可重定位目标文件（`.ko`，旧式后缀 `.o`），包含驱动或内核子系统的代码与元数据。它由内核的模块加载器 `init_module(2)`/`finit_module(2)` 映射进内核地址空间，**仍运行在 ring 0、共享内核页表**，不是用户态插件，也没有地址空间隔离。模块可以卸载（`delete_module(2)`），前提是引用计数为零。
:::

::: note 非科班补一层：ring 0 与「不是沙箱」
CPU 用特权级（privilege level）把危险指令锁起来。x86-64 上内核跑在 ring 0，能改页表、关中断、直接读写设备寄存器；你的程序跑在 ring 3，只能执行 `syscall` 请内核代办。ring 不是安全等级评分，它只是一条硬件分界线：ring 3 想碰内核内存，CPU 当场报错。

模块加载后拿到的正是 ring 0 的权力。它能读写成千上万个内核结构，比如把函数指针填进 `struct file_operations`，让下一次 `read` 调到自己的代码。它和内核共享同一张页表，没有独立地址空间；所以模块里一个空指针，不是「插件崩了」，而是整机 panic。这就是「模块不是沙箱」：它是内核的一部分，只是到得晚一点。
:::

模块与「编进内核」的区别只有加载时机，没有权限级别：

| 形态 | 位置 | 能否卸载 | 典型例子 |
|:--|:--|:--|:--|
| 内建（built-in） | `vmlinuz` 内 | 否 | `ext4`、`scheduler`、`netfilter` 核心 |
| 可加载模块 | `/lib/modules/$(uname -r)/kernel/` | 是（引用计数为 0 时） | `loop`、`nvme`、`kvm`、`nfs` |
| initramfs 内模块 | `/boot/initrd.img-*` 的解压树 | 启动早期可加载 | 根文件系统驱动、LUKS、RAID |

判断一个功能是内建还是模块，不要靠猜：

```bash
# modules.builtin 列出编进内核的模块名；modules.dep 列出可加载模块的依赖
grep -w 'loop' /lib/modules/$(uname -r)/modules.builtin && echo builtin
modinfo -F filename loop 2>/dev/null || echo "no loop.ko"
```

`modinfo` 输出 `filename: (builtin)` 时是内建；输出 `.ko` 或 `.ko.zst` 路径时是可加载模块。Ubuntu 用 zstd 压缩模块，`modinfo` 会自动解压读取元数据。

`modinfo` 里还有两个字段值得看。`vermagic` 是内核版本与关键配置的指纹，和当前内核对不上会拒绝加载，报 `Invalid module format`。`signer` 是签名者，Secure Boot 打开时，密钥不在 MOK 里的模块会被拒。自己编译的模块最容易栽在 `vermagic` 上。

日常只需要六个命令，但每个的边界要清楚：

| 命令 | 做什么 | 关键点 | 失败时常见 errno |
|:--|:--|:--|:--|
| `lsmod` | 列出已加载模块 | 读 `/proc/modules`，第三列是引用计数，第四列是使用者 | — |
| `modinfo m` | 读模块元数据 | `depends`、`vermagic`、`signer`、`parm` 都能单独取 | `ENOENT`（模块不存在） |
| `modprobe m` | 按依赖加载 | 读 `modules.dep`，自动加载依赖；支持别名 | `ENOENT`、`ENODEV`、`EPERM` |
| `modprobe -r m` | 卸载模块及其不再被用的依赖 | 引用计数不为 0 时失败 | `EBUSY` |
| `insmod file.ko` | 直接加载指定文件 | **不解析依赖**，不建别名，参数格式是 `k=v` | `EINVAL`、`ENOEXEC`、`EPERM` |
| `rmmod m` | 直接卸载 | 不处理依赖；`-f` 已废弃且危险 | `EBUSY`、`ENOENT` |

`modprobe` 是「按名字和依赖加载」，`insmod` 是「按文件加载」。自己编译的 `.ko` 用 `insmod` 调试可以，但正式安装应放进 `/lib/modules/$(uname -r)/` 后跑 `depmod -a`，再用 `modprobe`，否则依赖与别名都不会被记录。

模块的参数有三条设置路径，优先级从高到低：

```bash
# 1) 启动参数：内核命令行，最早生效，适合内置驱动
#    GRUB 里临时加：loop.max_loop=16
cat /proc/cmdline | tr ' ' '\n' | grep '\.'

# 2) 配置文件：/etc/modprobe.d/*.conf，modprobe 时生效
printf 'options loop max_loop=16\n' | sudo tee /etc/modprobe.d/loop.conf

# 3) 运行时：/sys/module/<name>/parameters/，仅部分参数可写
ls -l /sys/module/loop/parameters/ 2>/dev/null
```

不是所有参数都能运行时改。`/sys/module/*/parameters/*` 的权限位是 0444 时只读，0644 时可写；写入是否立即生效由模块自己的 `module_param` 权限与回调决定。改完 `dmesg | tail` 看模块是否接受了新值。

::: method 实验 0.1-A · 加载、观察、卸载一个模块
目的：用 `loop` 模块走完「元数据 → 依赖 → 加载 → 参数 → 引用计数 → 卸载」全链路。需要 root；在虚拟机或一次性容器里做。

```bash
#!/usr/bin/env bash
# module-lab.sh —— 只读观察 + 可选的加载/卸载
set -euo pipefail

mod=${1:-loop}
echo "== kernel: $(uname -r)"
echo "== builtin?"; grep -w "$mod" "/lib/modules/$(uname -r)/modules.builtin" || echo "not builtin"

echo "== modinfo"
modinfo "$mod" | grep -E '^(filename|license|description|depends|vermagic|signer):' || true

echo "== dry run（不加载，只打印将执行的 insmod）"
modprobe -n -v "$mod" || true

echo "== load"
if ! lsmod | awk '{print $1}' | grep -qx "$mod"; then
    sudo modprobe "$mod"
fi

echo "== loaded?"
lsmod | awk -v m="$mod" 'NR==1 || $1==m'
printf 'refcnt='; cat "/sys/module/$mod/refcnt" 2>/dev/null || echo '?'

echo "== parameters"
for p in /sys/module/"$mod"/parameters/*; do
    [[ -e $p ]] || continue
    printf '%s = %s (%s)\n' "$(basename "$p")" "$(cat "$p")" "$(stat -c %a "$p")"
done

echo "== dmesg tail"
sudo dmesg | tail -5

# 可选卸载：确认没有 loop 设备/挂载在用
if [[ ${DO_UNLOAD:-0} == 1 ]]; then
    sudo modprobe -r "$mod" && echo "unloaded $mod" || echo "unload failed (in use?)"
fi
```

预期：`modprobe -n -v` 打印一行 `insmod /lib/modules/.../loop.ko.zst` 但不改变 `lsmod`；真正 `modprobe` 后 `lsmod` 出现 `loop`，`refcnt` 为 0 或正数，`parameters/` 下能看到 `max_loop`、`max_part` 等（具体项随内核版本变化，以本机输出为准）。默认不卸载；要看卸载路径就 `DO_UNLOAD=1 ./module-lab.sh loop`。如果 `modprobe -r loop` 报 `Module loop is in use`，说明有 loop 设备或挂载仍引用它，先 `losetup -a` 查。
:::

::: errata 模块相关的七个边界
1. **「`lsmod` 里没有就是没编进内核」**——内建模块不出现在 `lsmod`，要查 `modules.builtin`。
2. **「`insmod` 会帮我解决依赖」**——不会。`insmod` 只加载指定文件，缺依赖时报 `Unknown symbol`，用 `modprobe` 或先手动加载依赖。
3. **「模块卸载失败是权限问题」**——多数是 `EBUSY`：引用计数不为零，有设备、文件系统或内核线程还在用它。
4. **「加载模块是安全的」**——模块在 ring 0 运行，一个空指针就能 panic 整机；`kernel.modules_disabled=1` 是不可逆的加固开关，开了就只能重启。
5. **「Secure Boot 下所有模块都能加载」**——启用 Secure Boot 后，未签名或密钥不在 MOK（Machine Owner Key，本机信任的密钥库）里的模块会被拒绝，`dmesg` 会看到 `module verification failed`；`modinfo -F signer` 能看签名者。
6. **「模块参数随时能改」**——`/sys/module/*/parameters/*` 权限是 0444 时只读；0644 也未必立即生效，取决于模块自己的 `module_param` 权限与回调。
7. **「卸载模块会把资源清干净」**——`rmmod` 只要求引用计数为零；模块自己没释放的内存、定时器、工作队列，仍可能留在内核里。
:::

### 0.1.11 小结

模块是运行时链接进内核的 ELF 目标文件，和内建代码一样跑在 ring 0、共享页表，所以它不是沙箱。`modprobe` 管依赖与别名，`insmod` 只管一个文件；判断内建还是模块要看 `modules.builtin`，不能只看 `lsmod`。如果只记住一件事，那就是：加载模块等于往内核里加代码，权限和风险都按内核算。

::: method 即时自测 · 0.1.11
**Q1（记忆）** 模块运行在哪个特权级？它有自己的地址空间吗？

**Q2（辨析）** `lsmod` 里没有 `ext4`，能否说明系统没用 ext4？

**Q3（应用）** 自己编译的 `hello.ko` 用 `insmod` 报 `Unknown symbol`，你按什么顺序查？

::: sol 答案
**A1** ring 0；没有独立地址空间，和内核共享页表，所以能直接改内核数据结构，也能把内核带崩。
**A2** 不能。它可能被编进了 `vmlinuz`；查 `modules.builtin` 或 `modinfo -F filename ext4`，看到 `(builtin)` 就是内建。
**A3** 先 `dmesg | tail` 看缺哪个符号，再 `modinfo hello.ko` 看 `depends` 与 `vermagic`；用 `modprobe` 先装依赖，并确认 `vermagic` 与 `uname -r` 一致。
:::
:::

## 0.1.12 启动链路：五段、五个负责人、五种证据 {#sec-0.1.12}

这一节回答：从按下电源到出现登录提示符，控制权在谁手里换了五次；每次换手留下什么可查的证据。

::: preview 先抓住一件事
启动是控制权的五次换手：固件交给引导器，引导器交给内核，内核交给 initramfs 的 `/init`，`/init` 挂好真根再交给 PID 1。每一段都留下一种持久产物；排障就是找「最后一段还有证据的地方」。
:::

按下电源键的那一刻，CPU 从一个固定地址取指。此时没有内核、没有文件系统、没有日志，连「启动到哪一步」都没人替你记。控制权是一段一段交出去的，每段的负责人不同，留下的证据也不同。

固件只认启动项，不认文件系统里的 `grub.cfg`；引导器只认内核与 initrd，不管 `root=` 能不能挂上；内核只认命令行和 initramfs，不认 systemd 的 unit；initramfs 只认「把真根挂上」；systemd 只认 unit 和 target。每段交棒之后就不再负责，所以问题总落在「最后一次有证据的那一段」和下一段之间。

排启动问题最常见的错误，是机器还没进用户态就去翻 `journalctl`。日志服务本身还没起来，当然没有记录。正确做法是先判断「卡在哪一段」，再选那一段的工具。

| 段 | 谁在执行 | 持久产物 | 证据命令 | 典型失败 |
|:--|:--|:--|:--|:--|
| 1 固件 | UEFI/BIOS | NVRAM 启动项、ESP 分区 | `efibootmgr -v`、`ls /sys/firmware/efi` | 找不到启动项、Secure Boot 拒绝 |
| 2 引导器 | GRUB / systemd-boot | `/boot/grub/grub.cfg`、`/etc/default/grub` | `grep menuentry /boot/grub/grub.cfg` | `grub>`、菜单缺失、内核路径错 |
| 3 内核 | `vmlinuz` | `/boot/vmlinuz-*`、`/proc/cmdline` | `cat /proc/cmdline`、`dmesg` | 驱动缺失、根设备找不到 |
| 4 initramfs | `/init`（用户态第一阶段） | `/boot/initrd.img-*` | `lsinitramfs` | `Waiting for root device`、LUKS 密码错 |
| 5 init | systemd（PID 1） | unit、target 链接 | `systemctl get-default`、`systemd-analyze` | `emergency mode`、依赖成环 |

这张表的读法是：**每一段都有自己的「持久产物」**。固件把启动项写进 NVRAM（主板上断电不丢的一小块存储），引导器把菜单写进 `grub.cfg`，内核把命令行留在 `/proc/cmdline`，initramfs 是一个 cpio 归档（把许多文件打成一个包的格式），systemd 把默认目标做成符号链接。排障就是找到「最后一段有证据的地方」，问题就在它和下一段之间。

第一段：UEFI 还是 BIOS，决定你用哪套工具。

```bash
# UEFI 系统：这个目录存在
ls -d /sys/firmware/efi && echo "UEFI boot"
# 启动项与顺序；BootCurrent 是本次启动项
sudo efibootmgr -v
# Secure Boot 状态（需要 mokutil）
mokutil --sb-state 2>/dev/null || true
```

UEFI 从 NVRAM 里的启动项找到 ESP（EFI System Partition，通常是 `/boot/efi`，FAT32），再执行 `/EFI/<vendor>/grubx64.efi`。启动项丢了，系统会退到可移动介质路径 `/EFI/BOOT/BOOTX64.EFI`；这个 fallback 文件在，机器就还能起来。`efibootmgr -v` 的 `HD(1,GPT,...)` 是分区定位，`File(\EFI\ubuntu\grubx64.efi)` 是引导器路径，两者任一不对都应先修启动项，而不是重装。

传统 BIOS 从 MBR 的前 512 字节读第一阶段引导代码，GRUB 的 `core.img` 通常放在 MBR 之后、第一个分区之前的空隙里。这段空隙一旦被分区工具或 `dd` 覆盖，系统就停在 `grub>` 或 `GRUB rescue>`。GPT 盘上还有一块 protective MBR，不要把它当成可随意改写的分区表。

第二段：GRUB 的配置是**生成物**，不是手改对象。

```bash
# 真正的配置来源
cat /etc/default/grub
ls /etc/grub.d/
# 重新生成；不同发行版命令名不同
sudo update-grub            # Debian/Ubuntu
sudo grub2-mkconfig -o /boot/grub2/grub.cfg   # RHEL 系
```

要改内核命令行，改 `/etc/default/grub` 的 `GRUB_CMDLINE_LINUX_DEFAULT`，再重新生成。直接编辑 `grub.cfg` 能生效一次，下次内核升级就被覆盖。临时调试则在 GRUB 菜单按 `e` 编辑当前条目，改完 `Ctrl-X` 启动；这次修改不落盘，重启即失效，正好适合试 `systemd.unit=rescue.target` 或 `rd.break`。

第三段：内核拿到的命令行，决定了它怎么找根、开哪些调试开关。

```bash
cat /proc/cmdline
# BOOT_IMAGE=/boot/vmlinuz-7.0.0-38-generic root=UUID=fa8bbbea-9f92-4241-b344-a824e4b676a6 ro quiet splash vt.handoff=7
```

（本机实测的整行，UUID 是这台虚拟机自己的根分区标识，你在自己机器上看到的会不同——这一串本身是机器身份，不能照抄进脚本。）

常见参数按用途分类：

| 参数 | 作用 | 什么时候用 |
|:--|:--|:--|
| `root=UUID=...` | 指定根文件系统 | 根设备名变化、克隆虚拟机 |
| `ro` / `rw` | 初始以只读/读写挂载根 | 默认 `ro`，由 systemd 重新挂载 |
| `systemd.unit=rescue.target` | 覆盖默认 target | 正常启动失败，进单用户救援 |
| `rd.break` | 在 initramfs 阶段停下 | 重置密码、修 `/etc/fstab`、修 LUKS |
| `fsck.mode=force` | 强制 fsck | 怀疑文件系统损坏 |
| `nomodeset` | 不用内核模式设置 | 显卡驱动导致黑屏 |
| `init=/bin/bash` | 直接以 bash 为 PID 1 | 最后手段；无服务、无挂载管理 |

`init=/bin/bash` 不是「单用户模式」，它跳过 systemd，`/` 可能还是只读，`/proc` 没挂，网络没有。用完必须 `mount -o remount,rw /` 再改文件，否则改动不会落盘。

第四段：initramfs 是一个临时根文件系统，任务是「把真正的根挂上」。

```bash
ls -lh /boot/initrd.img-$(uname -r)
# 列出归档内容（不展开）
lsinitramfs /boot/initrd.img-$(uname -r) | head -20
# 看关键驱动是否在里面
lsinitramfs /boot/initrd.img-$(uname -r) | grep -E 'nvme|ext4|dm-crypt'
```

initramfs 里有一个 `/init`，它挂载 `/proc`、`/sys`，加载根设备所需模块，按 `root=` 找到设备，再 `switch_root` 到真正的根。根盘是 NVMe、RAID、LUKS 或网络存储时，对应驱动与工具必须在 initramfs 里；不在，就会卡在 `Waiting for root device` 或 `Unable to find a medium containing a live file system`。改完 `/etc/initramfs-tools/` 或 `/etc/dracut.conf.d/` 后要重新生成：

```bash
sudo update-initramfs -u -k all     # Debian/Ubuntu
sudo dracut -f --regenerate-all     # RHEL/Fedora
```

第五段：systemd 用 target 组织服务，最后交给 getty 或显示管理器。

```bash
systemctl get-default
systemctl list-dependencies --reverse multi-user.target | head
systemctl list-units --type=target --state=active
loginctl list-sessions
```

`default.target` 是一个符号链接，指向 `multi-user.target`（无图形）或 `graphical.target`（图形）。`sysinit.target` 负责早期系统初始化，`basic.target` 负责基础服务，`multi-user.target` 拉起网络、SSH、定时任务，`graphical.target` 再加显示管理器。启动失败进 `emergency.target` 时，先看 `systemctl --failed` 与 `journalctl -b -p err`，再决定是修 fstab、修 unit 还是绕过某个服务。

::: note 非科班补一层：initramfs、PID 1 与 target
initramfs（initial RAM filesystem）是内核启动时读进内存的一个小根文件系统，里面只有挂载真根所需的驱动和脚本。它不是磁盘上的 `/`，任务完成就被丢掉；所以改它要重新生成 `/boot/initrd.img-*`，改磁盘上的 `/etc` 不会自动进去。
PID 1 是内核创建的第一个用户态进程，systemd 占着这个位置。它退出，内核就 panic；所以「杀掉 1 号进程」不是普通操作。
target 是 systemd 的一组 unit 集合，作用类似旧式的运行级别：`multi-user.target` 是多用户命令行，`graphical.target` 再加图形界面。
:::

::: method 实验 0.1-B · 给自己的机器画一张启动链路图
目的：不依赖发行版文档，用本机证据把五段串起来，输出可直接贴进排障记录的五行摘要。

```bash
#!/usr/bin/env bash
# boot-chain.sh —— 只读：采集本机启动链路的五段证据
set -euo pipefail
export LC_ALL=C

printf '== 1 firmware\n'
if [[ -d /sys/firmware/efi ]]; then
    echo "mode=UEFI"
    if command -v efibootmgr >/dev/null; then
        efibootmgr 2>/dev/null | sed -n '1,6p' || true
    else
        echo "efibootmgr not installed"
    fi
else
    echo "mode=BIOS (no /sys/firmware/efi)"
fi

printf '\n== 2 bootloader\n'
for f in /boot/grub/grub.cfg /boot/grub2/grub.cfg; do
    [[ -r $f ]] && { echo "cfg=$f"; grep -m1 'menuentry' "$f" || true; }
done
[[ -r /etc/default/grub ]] && grep -E '^GRUB_(DEFAULT|CMDLINE|TIMEOUT)' /etc/default/grub || true

printf '\n== 3 kernel\n'
echo "release=$(uname -r)"
cat /proc/cmdline
[[ -r /boot/config-$(uname -r) ]] && \
    grep -E '^CONFIG_(HZ|PREEMPT|CGROUP|PSI)=' "/boot/config-$(uname -r)" || true

printf '\n== 4 initramfs\n'
for f in /boot/initrd.img-$(uname -r) /boot/initramfs-$(uname -r).img; do
    [[ -r $f ]] && ls -lh "$f"
done
if command -v lsinitramfs >/dev/null; then
    n=$(lsinitramfs /boot/initrd.img-$(uname -r) 2>/dev/null | wc -l)
    echo "initramfs_entries=$n"
fi

printf '\n== 5 userspace\n'
echo "default_target=$(systemctl get-default 2>/dev/null || echo n/a)"
systemctl is-system-running 2>/dev/null || true
if command -v systemd-analyze >/dev/null; then
    systemd-analyze 2>/dev/null | sed -n '1,2p' || true
fi
```

预期：UEFI 机器第一段打印 `mode=UEFI` 和启动项；`/proc/cmdline` 里能看到 `root=UUID=`；第四段打印 initramfs 大小与条目数；第五段打印 `default_target=graphical.target` 或 `multi-user.target`，以及 `systemd-analyze` 的四段耗时。没有 `lsinitramfs` 或 `efibootmgr` 时脚本只跳过该段，不让整条链中断。
:::

::: errata 启动链路的七个误判
1. **「进不了系统就是内核坏了」**——先看有没有 GRUB 菜单。菜单都没有，问题在固件或引导器；菜单有但内核起不来，才轮到内核与 initramfs。
2. **「`journalctl` 没有日志就是没启动」**——内核日志在 journald 起来之前由 `dmesg`/`/dev/kmsg` 承载；用 `journalctl -k -b` 也读不到时，直接 `dmesg`。
3. **「`root=UUID=` 一定比 `/dev/sda1` 稳」**——UUID 在 `mkfs`/克隆后会变；PARTUUID 与分区表绑定，更适合定位分区，但恢复分区表后也可能变。
4. **「改 `grub.cfg` 就行了」**——它是生成物，内核或 grub 包升级会重写；改 `/etc/default/grub` 再 `update-grub`。
5. **「initramfs 越大越安全」**——越大启动越慢、占 `/boot` 越多；`MODULES=most` 适合通用镜像，专用机器用 `dep` 加显式列表更可控。
6. **「`init=/bin/bash` 等于单用户模式」**——它跳过 systemd，没有服务、没有 `/proc`、根可能只读；能进 `rescue.target` 就不要用它。
7. **「`dmesg` 的时间戳就是开机以来的真实时间」**——它从内核开始执行时计时，固件和引导器花掉的时间不在里面；要总耗时看 `systemd-analyze` 的 firmware、loader 两行。
:::

### 0.1.12 小结

启动链路的五段是固件、引导器、内核、initramfs、init；每段有自己的负责人、持久产物和证据命令。排障时先找最后一段有证据的地方，不要一上来就翻 `journalctl`。如果只记住一件事，那就是：控制权每交一次手，就换一套工具和一份证据。

## 0.1.13 系统调用接口：唯一合法入口的形状 {#sec-0.1.13}

这一节回答：一次 `write` 从用户态走到内核再回来，中间按什么规矩交接；为什么 `syscall()` 和 `write()` 的返回值不一样；为什么有些 libc 函数根本不进内核。

::: preview 先抓住一件事
系统调用是一次「有意的异常」：程序执行 `syscall` 指令，CPU 从用户态切到内核态，内核按调用号查表办事，再把结果放回寄存器。返回值、`errno` 和 vDSO 的差异，都藏在这条交接路径的细节里。
:::

先看一个失败的文件打开。下面这条命令只跟踪 `openat`，输出类似这样：

<div class="terminal" data-title="bash · 一次失败的系统调用">
<pre><span class="p">&#36;</span> strace -e trace=openat cat /no/such/file
openat(AT_FDCWD, "/no/such/file", O_RDONLY) = -1 ENOENT (No such file or directory)
cat: /no/such/file: No such file or directory
</pre>
</div>

`cat` 看到的是 `-1`，内核放回寄存器的是 `-ENOENT`（No such file or directory，文件不存在）。两者之间隔着 libc 的一次翻译；这一节就把这次翻译拆开。

把镜头拉远。程序计数器本来一条接一条走；遇到设备中断、缺页、除零或系统调用，控制流会突然跳到别处。操作系统教材把这类跳转叫异常控制流（exceptional control flow，ECF）。

异常分四类。中断（interrupt）来自外部设备，异步发生；陷阱（trap）是程序主动执行指令造成的，系统调用属于这一类；故障（fault）可能被修复，比如缺页；终止（abort）不可恢复。四类里只有陷阱是「你请内核办事」。

一次 `write` 的交接分五步：

1. 你在 C 里调用 `write(fd, buf, n)`，进入的是 glibc 的包装函数，不是内核。
2. 包装函数把 `fd`、`buf`、`n` 搬进 ABI 规定的寄存器，把调用号 `SYS_write` 放进 `rax`，执行 `syscall` 指令。
3. CPU 保存返回地址和标志，切到内核态，跳到 `entry_SYSCALL_64`（x86-64 的系统调用入口）。内核保存寄存器、检查调用号，再按 `sys_call_table`（内核里的系统调用函数表）找到处理函数。
4. 处理函数检查参数、在用户内存和内核之间搬字节；成功返回字节数，失败返回 `-errno`。
5. 内核恢复寄存器，回到用户态；包装函数看到负值，取反写进 `errno`，返回 `-1`。

这五步里，只有第 3、4 步在内核态。`strace` 记录的也是这两步的入口和出口。

从内核看，文件就是一串字节；`read`/`write` 每次只搬一部分，返回值是实际搬运的字节数，不是「成功/失败」两个状态。读到文件末尾时 `read` 返回 0，这就是 EOF（end of file，文件末尾），不是一个特殊字符。

::: def 定义 0.1.13 · 系统调用接口（system call interface） {#def-0.1.13}
系统调用是用户态请求内核服务的唯一合法指令级入口。调用方按 ABI 把**系统调用号**放进指定寄存器、参数放进参数寄存器，执行陷入指令（x86-64 的 `syscall`、ARM64 的 `svc #0`），CPU 切到内核态，由 `entry_SYSCALL_64` 或 `el0_svc` 进入分发表，按号调用 `sys_*`/`__x64_sys_*` 处理函数。返回值放在返回寄存器；`-1` 到 `-4095` 表示错误，其绝对值是 `errno`。
:::

三个架构的寄存器约定不同，但模型相同：

| 项 | x86-64 | ARM64 | RISC-V 64 |
|:--|:--|:--|:--|
| 调用号寄存器 | `rax` | `x8` | `a7` |
| 参数寄存器 | `rdi`、`rsi`、`rdx`、`r10`、`r8`、`r9` | `x0`–`x5` | `a0`–`a5` |
| 返回值 | `rax` | `x0` | `a0` |
| 陷入指令 | `syscall` | `svc #0` | `ecall` |
| 错误表示 | `rax ∈ [-4095, -1]` | `x0` 同范围 | `a0` 同范围 |

这张表说明：**系统调用号是架构相关的，C 源码不是**。你在 x86-64 上写 `SYS_write`，交叉编译到 ARM64 时头文件会给出另一个数字；`strace` 也会按架构解析成同一个名字。手写汇编或看内核原始日志时才需要关心数字。

这张表还有一层含义：它是**寄存器 ABI**。调用号、参数、返回值各占哪个寄存器，由架构定死；编译器、libc 和内核按同一张表办事。你换编译器不用换内核，但换架构必须重新编译。

::: note 非科班补一层：为什么不直接返回 -1
内核不能直接写你的 `errno`：`errno` 是 libc 的线程局部变量，内核不知道它在哪个地址。内核只能在唯一的返回寄存器里表达成败，于是约定用 `-4095` 到 `-1` 表示错误；libc 的包装再把它取反存进 `errno`，并统一返回 `-1`。
:::

glibc 在中间做了四件事，每一件都可能改变你看到的行为：

1. **寄存器搬运与陷入**：把 C 参数按 ABI 放进寄存器，执行 `syscall`，再把负返回值翻译成 `-1` 并设置 `errno`。
2. **`EINTR` 重试**：部分慢系统调用（`read`、`write`、`wait`、`nanosleep`）在收到信号时返回 `EINTR`；glibc 对其中一些做了透明重启，但 `signal(7)` 列出的 `never restarted` 调用不会。
3. **取消点**：`read`、`write`、`open` 等是 pthread 取消点（线程被取消时允许停下的位置）；直接 `syscall()` 绕过 glibc 就没有这层语义。
4. **vDSO 加速**：`clock_gettime`、`gettimeofday`、`time`、`getcpu` 在支持时由内核映射一段用户态代码（`linux-vdso.so.1`），不执行陷入指令。所以 `strace` 看不到它们，性能也不是系统调用级的。

第 4 条值得单独看。vDSO（virtual dynamic shared object，虚拟动态共享对象）是内核在程序启动时映射进用户地址空间的一小段代码和数据。`clock_gettime` 这类函数直接调用这段代码，读内核预先放好的时间数据，不执行 `syscall` 指令。

vDSO 不是第二个入口：它只能读内核提前放好的数据，不能用来申请新服务；需要内核办事时，仍然要执行 `syscall`。

`strace` 靠 `ptrace`（process trace，进程跟踪）停在系统调用入口和出口，只能看见真正陷入内核的调用。vDSO 是普通用户态函数调用，没有入口可停，所以 `strace` 里一行都没有。

```bash
ldd /bin/date | grep vdso
# linux-vdso.so.1 (0x00007ffd...)
strace -c -e trace=clock_gettime date >/dev/null
# 通常 0 次；有些环境会看到 1 次，说明这次没走 vDSO
grep vdso /proc/self/maps
# 7ffd...-7ffd... r-xp ... [vdso]
```

这三条命令分别证明：进程的依赖表里有 vDSO、`clock_gettime` 没有产生系统调用、地址空间里确实映射了 `[vdso]`。任意一条对不上，都说明这次观察不能证明 vDSO 生效，不能拿「看不到」当「没调用」。

这张表把「libc 函数」与「真正的系统调用」分开：

| 你写的 | 实际发生 | 失败语义 |
|:--|:--|:--|
| `printf` | 用户态缓冲，满或 `fflush` 时 `write` | 返回负数，`errno` 由 `write` 设置 |
| `malloc` | 用户态空闲链表；不够时 `brk`/`mmap` | 返回 `NULL`，`errno=ENOMEM` |
| `fopen` | `openat` + 用户态 `FILE` 结构 | 返回 `NULL`，`errno` 来自 `openat` |
| `getaddrinfo` | 读 `/etc/nsswitch.conf`，可能 `socket`/`sendto`/`recvfrom` | 返回 `EAI_*`，不是 `errno` |
| `sleep` | `nanosleep`（被信号打断会提前返回） | 返回剩余秒数 |
| `time` | 通常走 vDSO，不陷入内核 | 几乎不失败 |

还要区分「包装」和「裸调用」。`syscall()` 本身也是 glibc 的包装：它按调用号转发，仍然会把 `-errno` 翻译成 `-1` 加 `errno`。真正没有翻译的是手写汇编或内联汇编。

下面这个程序同时走 libc 包装与裸 `syscall()`，用来对比返回值与 `errno`：

```c
/* rawsys.c —— 对比 libc 包装与裸系统调用；Linux 专用，编译时加 -D_GNU_SOURCE */
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/syscall.h>
#include <unistd.h>

int main(void)
{
    /* 1) 裸 getpid：成功时返回 PID，不设置 errno */
    long pid = syscall(SYS_getpid);
    printf("syscall(SYS_getpid) = %ld, libc getpid() = %d\n", pid, (int)getpid());

    /* 2) 裸 write：参数与 write(2) 相同，但没有 stdio 缓冲 */
    const char msg[] = "raw write\n";
    long n = syscall(SYS_write, STDOUT_FILENO, msg, sizeof msg - 1);
    if (n < 0) {
        fprintf(stderr, "raw write failed: %s\n", strerror(errno));
        return 1;
    }
    printf("raw write returned %ld\n", n);

    /* 3) 失败路径：打开不存在的文件，观察 -1 与 errno */
    errno = 0;
    long fd = syscall(SYS_openat, AT_FDCWD, "/no/such/file", O_RDONLY, 0);
    printf("raw openat = %ld, errno = %d (%s)\n", fd, errno, strerror(errno));

    /* 4) 同一个失败走 libc：返回值同为 -1，但错误来源更明确 */
    errno = 0;
    int cfd = open("/no/such/file", O_RDONLY);
    printf("libc open  = %d, errno = %d (%s)\n", cfd, errno, strerror(errno));
    return 0;
}
```

编译与运行：

```bash
cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -Werror -O2 -g rawsys.c -o rawsys
./rawsys
strace -e trace=getpid,write,openat ./rawsys 2>&1 | grep -E 'getpid|write|openat'
```

预期：程序打印的两行 `errno` 都是 2（`ENOENT`）；`strace` 里能看到两次 `getpid()` 与两次 `openat`，但**看不到** `printf` 内部的所有 `write`（stdio 缓冲把多次输出合并了）。`syscall(SYS_getpid)` 在 `strace` 里也显示为 `getpid()`，因为 `strace` 按系统调用号反解，不区分你是从 libc 还是裸 `syscall` 进来的。

手写汇编才能看清 ABI 本身。下面是同一件事的两个架构版本：

<div class="variant" data-arch="x86-64" data-lang="asm">

```asm

    .globl _start
_start:
    movq    $39, %rax        # __NR_getpid（x86-64）
    syscall                  # 陷入内核；返回地址在 rcx，标志在 r11
    movq    %rax, %rdi       # 退出码 = PID 低 8 位
    movq    $60, %rax        # __NR_exit
    syscall
```

</div>

<div class="variant" data-arch="arm64" data-lang="asm">

```asm
// getpid_arm64.s —— 可汇编：clang --target=aarch64-linux-gnu -nostdlib -static getpid_arm64.s -o getpid
    .text
    .globl _start
_start:
    mov     x8, #172         // __NR_getpid（ARM64 通用号）
    svc     #0               // 陷入内核；返回在 x0
    mov     x0, x0           // 退出码 = PID 低 8 位
    mov     x8, #93          // __NR_exit
    svc     #0
```

</div>

两个版本都只依赖内核 ABI，不链接 libc。注意系统调用号不同（39 与 172），这正是「源码可移植、ABI 不可移植」的具体样子。

::: method 实验 0.1-C · 验证 vDSO 与系统调用计数
目的：证明「libc 函数不一定进内核」，并学会用 `strace -c` 读调用次数。

```bash
# 1) clock_gettime 通常走 vDSO：下面这条 trace 往往没有 clock_gettime 行
strace -c -e trace=clock_gettime date >/dev/null

# 2) 强制走系统调用（关闭 vDSO）再对比
sudo sh -c 'echo 0 > /proc/sys/vm/vdso_enabled' 2>/dev/null || \
    echo "vdso_enabled 不存在（6.x 已移除该开关，改用其他方式）"

# 3) 看某个进程是否启用了 seccomp
grep -E '^(Seccomp|NoNewPrivs):' /proc/self/status

# 4) 统计一次 ls 的系统调用分布
strace -c -f ls /etc >/dev/null
```

预期：第 1 条通常输出 `clock_gettime` 0 次（vDSO），而 `date` 的其他调用照常出现；第 3 条在 Docker 默认配置里常见 `Seccomp: 2`（过滤模式），普通 shell 是 `0`；第 4 条能看出 `openat`、`newfstatat`、`getdents64`、`write` 的占比。不同内核版本对 vDSO 开关的支持不同，`vm.vdso_enabled` 在较新内核上可能不存在，这本身就是「版本差异」的证据。
:::

::: errata 系统调用层的七个误解
1. **「`syscall()` 返回 -1 就是内核返回 -1」**——内核返回的是 `-errno`（如 `-ENOENT`）；glibc 的 `syscall()` 包装把它翻译成 `-1` 并设置 `errno`。直接看寄存器才能看到原始负值。
2. **「所有 libc 函数都会进内核」**——`printf` 的缓冲、`malloc` 的空闲链表、`gettimeofday` 的 vDSO 都在用户态完成。
3. **「系统调用号在 x86-64 和 ARM64 上一样」**——完全不同；只有 C 头文件里的 `SYS_*` 宏能跨架构。
4. **「`errno` 是系统调用设置的」**——`errno` 是 glibc 的线程局部变量；裸汇编没有 `errno`，只有返回寄存器里的负值。
5. **「`strace` 看到的就是全部内核行为」**——vDSO、缺页、调度、中断都不以系统调用形式出现；`strace` 只覆盖 syscall 的入口和出口。
6. **「seccomp 只影响容器」**——任何进程都可以装 seccomp（secure computing mode，系统调用过滤器）；`Seccomp: 2` 表示已启用，被拦的调用返回 `EPERM` 或直接 `SIGSYS`。
7. **「`syscall()` 就是裸汇编」**——它仍是 glibc 的包装，只是绕过了 stdio 缓冲、取消点和部分 `EINTR` 重启；`errno` 翻译还在。
:::

### 0.1.13 小结

系统调用是一次陷阱：用户态按寄存器 ABI 放好调用号和参数，执行 `syscall`，内核查表办事，把结果放回返回寄存器。成功返回非负值，失败返回 `-errno`；libc 把 `-errno` 翻译成 `-1` 加 `errno`，vDSO 则把一部分调用留在用户态。如果只记住一件事，那就是：你在 C 里调的 `write()` 是包装，真正进内核的是 `syscall` 指令加寄存器里的调用号。

## 0.1.14 FHS：目录约定与它的证据 {#sec-0.1.14}

这一节回答：为什么配置在 `/etc`、状态在 `/var`、运行时在 `/run`；这些约定由谁保证，破坏之后会怎样。

::: preview 先抓住一件事
FHS 不是内核规则，而是一套按「可变性」分区的目录约定：装完就不变的放 `/usr`，要按机器改的放 `/etc`，会增长且要保留的放 `/var`，重启就该清的放 `/run`。记住这条判断规则，比背 17 行目录表有用。
:::

先看一个常见的现场：根分区快满了，`df -h /` 报 98%，`du -sh /var/* | sort -h | tail` 指向 `/var/log`。日志为什么不去 `/usr/log`？因为 `/usr` 是「装完就不变」的那一层，升级时会被整块替换；日志会增长、要保留、要单独备份，所以归 `/var`。

FHS（Filesystem Hierarchy Standard，文件系统层次标准）是一份目录约定，不是内核强制。内核只认挂载点与 inode；`/etc` 放配置、`/var` 放可变数据，是发行版、打包规则和运维习惯共同维持的。理解这一点，才不会把「某程序把数据写到 `/usr`」当成灵异事件。

判断一个目录该放什么，只问一句话：**装完之后它还会不会变；会变的话，重启要不要留。** 不变、随包升级 → `/usr`；要按机器改 → `/etc`；会变且要跨重启保留 → `/var`；会变但重启可丢 → `/run`；纯临时 → `/tmp`。

| 目录 | 放什么 | 可变？ | 证据命令 | 只读根/容器注意 |
|:--|:--|:--|:--|:--|
| `/` | 根文件系统 | 少量 | `findmnt /` | 只读根时只能写挂载点 |
| `/usr` | 系统程序、库、共享数据 | 随包升级 | `du -sh /usr` | 应与 `/` 同分区（usrmerge） |
| `/usr/local` | 管理员本地安装 | 是 | `echo $PATH` | 容器里常被镜像层覆盖 |
| `/etc` | 主机配置 | 是 | `dpkg -S /etc/ssh/sshd_config` | 配置应挂 ConfigMap/卷 |
| `/var` | 可变状态：日志、缓存、队列 | 是 | `du -sh /var/*` | 必须单独卷，否则撑爆根 |
| `/var/lib` | 程序持久状态（数据库、包数据库） | 是 | `ls /var/lib/dpkg` | 备份重点 |
| `/var/log` | 日志 | 是 | `journalctl --disk-usage` | 常与 journald 双份 |
| `/run` | 本次启动的运行时状态 | 是（tmpfs） | `findmnt /run` | 重启即失，别放持久数据 |
| `/tmp` | 临时文件 | 是（可能 tmpfs） | `findmnt /tmp` | `systemd-tmpfiles` 会清理 |
| `/opt` | 第三方整包软件 | 是 | `ls /opt` | 有些商业软件只认这里 |
| `/srv` | 服务数据 | 是 | `ls /srv` | 约定弱，很多发行版空着 |
| `/home` | 用户主目录 | 是 | `findmnt /home` | 容器里通常不挂 |
| `/root` | root 的主目录 | 是 | `ls -ld /root` | 权限 0700 |
| `/boot` | 内核、initramfs、引导器 | 随升级 | `ls -lh /boot` | 独立分区时易满 |
| `/proc` | 进程与内核参数投影 | 否（虚拟） | `cat /proc/self/status` | 读不是免费操作 |
| `/sys` | 设备、驱动、cgroup 投影 | 部分可写 | `ls /sys/class/net` | 写等于操作内核 |
| `/dev` | 设备节点 | 否（devtmpfs） | `ls -l /dev/null` | 容器里由 runtime 造 |

这张表说明：**「可变性」是选目录的第一原则**。配置放 `/etc`，因为要能改；运行状态放 `/run`，因为重启该清；持久数据放 `/var/lib`，因为要备份；只读的程序与库放 `/usr`，因为要能整体做镜像与校验。把这条规则反过来用，就能判断一个陌生目录：它装完还变不变、重启要不要留。

::: note 非科班补一层：只读根、tmpfs 与 usrmerge
只读根（read-only root）是容器和嵌入式系统常见的做法：根文件系统整块只读，`/usr` 自然也只读；需要写的地方另挂 `/etc`、`/var`、`/run`。`tmpfs` 是内存文件系统，`/run` 和部分 `/tmp` 挂在它上面，重启即清空。usrmerge 是把 `/bin`、`/sbin`、`/lib` 并进 `/usr` 的迁移，旧路径保留为符号链接，所以 `ls -ld /bin` 看到的是链接而不是目录。
:::

现代 Ubuntu 已经 usrmerge：`/bin`、`/sbin`、`/lib` 都是指向 `/usr` 下对应目录的符号链接。

```bash
ls -ld /bin /sbin /lib /lib64
# lrwxrwxrwx 1 root root 7 ... /bin -> usr/bin
readlink -f /bin/ls
# /usr/bin/ls
```

usrmerge 的好处是「一个 `/usr` 就能构成完整系统」，容器镜像与只读根更好做。代价是老脚本、chroot、自建 initramfs 里写死 `/bin/sh` 时，若只复制了 `/usr/bin/sh` 而没建链接，就会 `No such file or directory`。这个报错看起来像「文件不存在」，实际是**解释器路径不存在**，与 0.1.3 的 Alpine 例子同源。

配置的优先级也常被误解。包安装的默认配置在 `/usr/lib`（如 `/usr/lib/systemd/system/*.service`、`/usr/lib/sysctl.d/*.conf`），管理员改动用 `/etc` 覆盖。drop-in（追加片段）是放在 `*.conf.d/` 目录里的小配置文件，用来在不改主配置的前提下追加或覆盖某几项。

```bash
# systemd：/etc 下的同名文件优先，drop-in 再叠加
systemctl cat ssh.service
# sysctl：/etc/sysctl.d 覆盖 /usr/lib/sysctl.d
sysctl --system
# 看某个配置最终由哪些文件合成
systemd-analyze cat-config systemd/journald.conf
```

`systemctl cat` 会把 unit 本体和 drop-in 一起列出来；`systemd-analyze cat-config` 则把参与合成的配置文件逐段打印，并标出每段来自哪个路径。排查「我明明改了配置却没生效」时，它比逐个 `cat` 可靠。

只想看来源、不想读全文，可以只取文件标题行：

```bash
systemd-analyze cat-config systemd/journald.conf | grep '^# /'
# /etc/systemd/journald.conf
# /usr/lib/systemd/journald.conf
```

`/etc` 的优先级高于 `/usr/lib`；`journald.conf.d/` 里的 drop-in 按文件名字典序叠加，文件名靠后的覆盖靠前的。要屏蔽 `/usr/lib` 里的默认文件，可以在 `/etc` 下建一个指向 `/dev/null` 的同名符号链接。

::: note FHS 不保证的事
FHS 不规定包管理器数据库位置（Debian 在 `/var/lib/dpkg`，RPM 在 `/var/lib/rpm`），不规定容器镜像布局，也不规定 `/srv` 下面怎么组织。`man 7 hier` 是 FHS 的实现说明，`man 7 file-hierarchy` 是 systemd 对「只读 `/usr` + 可写 `/etc`/`/var`」的现代解释。两者冲突时，以你的发行版实际布局为准。
:::

::: errata 关于目录的五个误解
1. **「FHS 是内核强制」**——它是约定；内核只认挂载点与 inode，不检查你把日志放在哪。
2. **「`/usr` 是用户主目录」**——`/usr` 是 Unix System Resources，放程序与库；用户主目录在 `/home`。
3. **「日志一定在 `/var/log`」**——journald 可以把日志放在 `/run/log/journal`（本次启动有效），容器里通常直接写到 stdout。
4. **「`/bin` 一定是真实目录」**——usrmerge 后它常是指向 `/usr/bin` 的符号链接；`ls -ld /bin` 一看便知。
5. **「改了 `/etc` 就一定生效」**——同名 drop-in 可能后来覆盖，服务也可能没重载；用 `systemctl cat` 与 `systemd-analyze cat-config` 查来源。
:::

### 0.1.14 小结

FHS 不是内核规则，而是一套按可变性分区的约定：不变的放 `/usr`，按机器改的放 `/etc`，要保留的状态放 `/var`，重启即丢的放 `/run`。usrmerge 把旧路径变成符号链接，配置优先级则让 `/etc` 压过 `/usr/lib`。如果只记住一件事，那就是：先问「装完还变不变、重启要不要留」，再决定目录。


两块空盘是刻意的：0.10 的 LVM、RAID、quota 实验都需要「可以随便格式化」的设备，用 loop 文件也能做，但真盘的 `lsblk`、`/sys/block`、`blkid` 输出更接近生产。每做一次危险操作前打快照，比事后恢复便宜。

读内核源码的时机与方法：

1. **先有用户态证据，再读源码**。先用 `strace` 看到 `openat` 返回 `EACCES`，再去读 `fs/open.c` 的权限检查；否则会在几万行里迷路。
2. **按函数名跳转，不按目录通读**。`elixir.bootlin.com/linux/v6.8` 支持符号搜索与交叉引用；本地可以用 `make tags` 生成 ctags，`vim -t do_sys_openat2` 直接跳。
3. **用 `git log -S` 找变更原因**。一个奇怪的判断往往对应某次修复；`git log --oneline -S 'condition' -- path` 比注释更能说明「为什么这么写」。
4. **固定版本**。本书以 6.8 为准；发行版内核带 backport，读上游 6.8 与读 Ubuntu 6.8.0-45 不是同一份代码。结论要写清「在哪个版本、哪个配置下」。

## 0.1.16 十个跨层误判 {#sec-0.1.16}

这一节回答：为什么很多「Linux 就是这样」的判断，听起来都对，换一层就错？

::: preview 先抓住一件事
十个误判的共同点，是把一层的现象当成另一层的结论：`ls` 看得见文件，不代表加载器找得到库；`strace` 没有记录，不代表调用没发生。每条都配一条验证命令，先跑命令，再改判断。
:::

先看一个熟悉的现场：你改了 `/usr/lib/systemd/system/ssh.service`，重启服务却没变化。文件确实改了，`systemctl cat` 的第一行却不是它。

这些判断大多来自经验，而经验有适用层。下面十条按「路径与命令」「内核接口与启动」「系统调用与 ABI」三组排，每条都给「看起来像」「实际是」「为什么容易误判」和一条验证命令。

| # | 看起来像 | 实际是 | 为什么容易误判 | 一句话验证 |
|--:|:--|:--|:--|:--|
| 1 | 改了 `/usr/lib` 下的 unit 却没生效 | `/etc` 下有同名文件或 drop-in 覆盖 | 包自带的 unit 就装在 `/usr/lib`，看起来像「系统配置」 | `systemctl cat <unit>` |
| 2 | 容器里 `/bin/sh` 不存在 | usrmerge 后只复制了 `/usr/bin/sh`，没建链接 | 宿主机上 `ls /bin` 看得见，复制镜像时只跟了真实文件 | `readlink -f /bin/sh` |
| 3 | `cat /proc/meminfo` 只是读文件 | 每次读都触发内核生成快照，有开销 | 它长得像普通文本文件，`cat` 又太顺手 | `perf stat -e cpu-clock cat /proc/meminfo` |
| 4 | 用 `blacklist`（模块黑名单）把模块拉黑，它就不会加载 | 内建模块不受 blacklist 影响 | blacklist 只对可加载模块的别名生效，内建代码没有「加载」这一步 | `grep -w m /lib/modules/$(uname -r)/modules.builtin` |
| 5 | `update-grub` 是通用命令 | Debian 包装脚本；RHEL 用 `grub2-mkconfig` | 教程里到处是 `update-grub`，换到 RHEL 就 `command not found` | `command -v update-grub` |
| 6 | 换了存储控制器，重启就能认盘 | initramfs 里没有新驱动，卡在 `Waiting for root device` | 内核有驱动不等于启动早期的 initramfs 里有 | `lsinitramfs ... \| grep <driver>` |
| 7 | `syscall()` 与 `write()` 只差一个前缀 | 绕过缓冲、取消点、`EINTR` 重启与符号版本 | 名字太像，容易以为 `syscall` 是「更底层的 write」 | `strace` 对比两者 |
| 8 | `strace` 没看到 `clock_gettime` 就是没调用 | vDSO 在用户态完成，不陷入内核 | `strace` 的输出看起来像「全部系统调用」，其实只覆盖陷入内核的部分 | `ldd` 里有 `linux-vdso.so.1` |
| 9 | `getconf PAGE_SIZE` 与编译期常量一致 | 运行期内核配置决定，跨架构可变 | 教科书常写 4096，`getconf` 又常返回 4096 | `getconf PAGE_SIZE` vs `sysconf(_SC_PAGESIZE)` |
| 10 | `ldd` 只是「看依赖」 | 它会用 loader 执行目标，恶意二进制可借机运行代码 | 输出只是几行库名，看起来人畜无害 | 改用 `readelf -d` / `objdump -p` |

第 1、2、5 条是「路径与命令」问题：配置在 `/usr/lib` 与 `/etc` 各有一份，`/bin` 可能只是 `/usr/bin` 的链接，`update-grub` 只是 Debian 的命令名。第 3、4、6 条是「内核提供了什么」的问题：`/proc` 不是普通文件，内建模块不在 `lsmod` 里，initramfs 也不等于内核的全部驱动。第 7–10 条是「系统调用与 ABI」的问题：包装、vDSO、页大小、loader 都在用户态和内核态之间做翻译。

第 10 条值得展开：`ldd` 的实现是设置环境变量 `LD_TRACE_LOADED_OBJECTS=1` 再执行 loader。对普通动态二进制，loader 只打印依赖就退出；但对静态链接或手写 ELF，loader 可能真的运行它。巡检脚本里对来源不明的文件，先 `file` 看类型，再用 `readelf -d file | grep NEEDED` 或 `objdump -p file | grep NEEDED`，不要用 `ldd`。

拿一个信得过的文件试手，输出长这样：

```bash
readelf -d /usr/bin/ls | grep NEEDED | head -2
# 0x0000000000000001 (NEEDED)  Shared library: [libselinux.so.1]
# 0x0000000000000001 (NEEDED)  Shared library: [libc.so.6]
```

`readelf` 只读 ELF 头，不执行目标；它给出的 `NEEDED` 就是 loader 运行时会去找的库。`objdump -p` 的 `NEEDED` 行等价，选你机器上装了的那个。

::: note 非科班补一层：证据也有层
一条命令只能证明它那一层的事。`ls` 看得见文件，不证明加载器找得到库；`strace` 没有记录，不证明调用没发生；`modinfo`（查看模块元数据的命令）显示依赖为空，不证明符号都能解析。判断跨层问题时，先问「这条证据来自哪一层」，再问「它能证明到哪一层」。
:::

::: errata 用这份清单时容易再犯的错
1. **把验证命令当结论**——`systemctl cat` 只告诉你哪些文件参与，不告诉你服务已经重载；改完还要 `systemctl daemon-reload` 或重启服务。
2. **在容器里验证宿主机**——容器里的 `/proc`、`/sys`、`/bin` 都是容器视图；内核版本、模块、页大小要回宿主机看。
3. **只看一条命令**——跨层误判通常要两条证据：一条说明「这一层是什么」，一条说明「上一层为什么看不到」。
:::

### 0.1.16 小结

十个误判分成三组：路径与命令、内核接口与启动、系统调用与 ABI；每组的共同点都是把一层的现象当成另一层的结论。验证顺序是先定位层，再选命令，最后用第二条证据交叉检查。如果只记住一件事，那就是：一条命令只证明一层，跨层问题至少要看两层。

::: method 即时自测 · 0.1.16
**Q1（记忆）** 从十条里任选三条，说出「看起来像」「实际是」和对应的验证命令。

**Q2（辨析）** `strace -e trace=clock_gettime ./app` 没有 `clock_gettime` 行，能说明 `./app` 没取时间吗？为什么？

**Q3（应用）** 你收到一个来源不明的 ELF 文件，要查它依赖哪些共享库。用什么命令？为什么不用 `ldd`？

::: sol 答案
**A1** 示例：① 改 `/usr/lib` 的 unit 没生效——`/etc` 有同名或 drop-in，用 `systemctl cat`；② `lsmod` 没有 `ext4`——它是内建模块，用 `grep -w ext4 .../modules.builtin`；③ `syscall()` 与 `write()` 不止差前缀——前者绕过缓冲与取消点，用 `strace` 对比。
**A2** 不能。`clock_gettime` 可能走 vDSO，在用户态完成；用 `ldd ./app | grep vdso` 或 `grep vdso /proc/<pid>/maps` 佐证，必要时用 `perf` 或 `ltrace`（跟踪库函数调用）看用户态调用。
**A3** 用 `readelf -d ./file | grep NEEDED` 或 `objdump -p ./file | grep NEEDED`。`ldd` 会设置 `LD_TRACE_LOADED_OBJECTS=1` 并执行 loader，来源不明的文件可能借机运行代码。
:::
:::

::: ex 例 0.1.2 · 同一个 `ls`，在容器里与在宿主机上看到的不一样 {#ex-0.1.2}
宿主机上 `ls /proc/1/root` 能看到整棵根目录；容器里同一条命令只看到容器自己的那套。

先猜：是权限不同，还是「1 号进程」不是同一个？

判读：`/proc/1` 指的是**当前 PID namespace 里的 1 号进程**。宿主机上它是 systemd；容器里它是容器的入口进程，它的 `root` 是容器自己的根。同一条路径，在两层 namespace 里指向两个不同的东西——这正是 0.1 讲的「抽象层叠加」最直观的例子。

**判据**：`readlink /proc/1/ns/pid` 与 `readlink /proc/self/ns/pid` 相同，说明你在同一个 PID namespace 里。
:::

## 0.1.17 本章小结 {#sec-0.1.17}

这一节回答：五个单元学完，这一章到底留下了什么；下一步先做哪一件事？

::: preview 先抓住一件事
这一章只做一件事：把「Linux 系统」拆成可指认的层。先分清内核与用户态，再分清发行版与上游，然后用 `strace` 追一条命令，最后看模块、启动、系统调用和目录约定如何各就各位。
:::

第一、二单元先看见分层，再用标准和身份说清机器（0.1.1–0.1.7）：`uname` 读的是内核与硬件登记的身份，`ls`、`bash`、`apt` 来自 GNU 用户态，完整系统是发行版；POSIX 保证源码级接口，FHS 约定目录，LSB 已基本退场；`uname -r`、`ldd --version`、`/etc/os-release` 各管一个版本号。内核提供机制，发行版决定策略；把这三层混在一起，排障就会找错人。

第三、四单元把地图变成路径（0.1.8–0.1.14）：一条 `ls` 经过 Shell、加载器、libc、内核四层，`strace` 把每层交接变成证据；man 的区号告诉你该查哪一层；模块、启动链路、系统调用和 FHS 则回答「内核如何被扩展、启动、进入，用户态如何按可变性摆放数据」。这条路径的终点不是记住命令，而是能指着一次失败说清它在哪一层。

第五单元把路径变成路线和反例（0.1.15–0.1.16）：六个阶段每条都要留下产物，三条走法按目标取舍；十个跨层误判提醒你，一条命令只证明一层。主线可以压成一句话：**先看见分层，再用标准和身份说清机器，然后追一条命令，接着看内核如何被扩展、启动、进入，最后把地图变成路线和反例。** 逐项自检去[学习目标自检表](ch01-checklist.md)，不要在这里打勾；想先闭卷回忆，去[闭卷回忆卡](ch01-recall.md)；想练题，去[习题集](ch01-exercises.md)。如果只记住一件事，那就是：**遇到 Linux 问题，先问「这是哪一层的事」，再选命令。**

::: method 即时自测 · 0.1
**Q1** 一台机器 `uname -r` 是 `5.15.0-119-generic`，`/etc/os-release` 的 `VERSION_ID=24.04`。它跑的到底是 5.15 还是 6.8 内核？为什么会出现这种组合？

**Q2** 你在 Ubuntu 上编译了一个动态链接的二进制，复制到 Alpine 容器里执行，报 `not found`。`ls` 明明能看到这个文件，为什么说「找不到」？

**Q3** `ping` 能通，但 `curl https://example.com` 超时。按本章的分层，至少列出三个可能出问题的层，以及各层的第一条验证命令。

**Q4** 为什么 `getconf PAGE_SIZE` 在写底层程序时比 `4096` 这个字面量可靠？

**Q5** `lsmod` 里没有 `ext4`，但根文件系统就是 ext4。这矛盾吗？给出验证命令。

**Q6** 一个模块 `modprobe` 报 `Unknown symbol in module`，但 `modinfo` 显示 `depends:` 为空。最可能是什么原因？

::: sol 答案
**A1** 跑的是 5.15 内核。`/etc/os-release` 描述的是用户态发行版，内核可以独立升级或降级；Ubuntu 的 HWE 与 GA 内核轨道、云厂商自定义镜像、容器宿主都会造成「新用户态 + 旧内核」的组合。判断内核能力看 `uname -r`，不要看发行版号。

**A2** 报错里的 `not found` 通常不是文件不存在，而是**动态加载器不存在**。Ubuntu 二进制需要 `/lib64/ld-linux-x86-64.so.2`，Alpine 没有这个路径（musl 用 `/lib/ld-musl-x86_64.so.1`）。用 `file` 看 `interpreter` 一行即可确认。

**A3** ① 链路/地址层：`ip -br addr`；② 路由层：`ip route get 1.1.1.1`；③ DNS 层：`getent hosts example.com` 或 `dig example.com`；④ 端口/防火墙层：`nc -vz example.com 443`；⑤ TLS/应用层：`curl -v --max-time 10 https://example.com`。`ping` 只验证 ICMP 可达，不验证 TCP 443、DNS 或 TLS。

**A4** 页大小是内核配置与架构相关的运行时参数，不是 ABI 常量。ARM64 可以是 4/16/64 KiB；x86-64 常见 4 KiB，但写死 4096 的代码搬到 ARM64 就会出错。`sysconf(_SC_PAGESIZE)` 取的是当前内核的真实值。

**A5** 不矛盾。`ext4` 很可能被编进内核（built-in），内建模块不出现在 `lsmod`。验证：`grep -w ext4 /lib/modules/$(uname -r)/modules.builtin`，或 `modinfo -F filename ext4` 看是否输出 `(builtin)`；`/proc/filesystems` 里出现 `ext4` 也说明内核已支持它。

**A6** `depends` 为空只说明模块元数据没声明依赖，不代表运行时符号都能解析。常见原因是：模块与当前内核版本不匹配（`vermagic` 不符）、依赖的符号属于另一个未加载模块、或编译时用了不同的配置导致符号被裁剪。先看 `dmesg` 的完整报错与 `modinfo -F vermagic`，再 `modprobe --show-depends`。
:::
:::
