Shell 把路径字符串交出去之后，真正理解它的是内核的 VFS（Virtual File System，虚拟文件系统——内核里把 ext4、XFS、procfs 这些都统一成同一套「打开、读、查目录」操作的中间层）。同一棵树上的每个名字，最终都落在某个 inode 上；目录只是一个「名字 → inode 号」的映射表。把这一层想清楚，链接、删除、重命名、磁盘占用这些看似无关的现象就会连成一条线。

这一章从目录树开始，先建立「文件系统是一棵挂载树」的模型，再逐列拆 `ls -l`，然后进入 inode 与链接。后半章讲操作：复制、移动、删除、查找、批量处理。每个操作都给出边界与失败模式，因为文件操作的错误往往不可逆。

命令以 Ubuntu 24.04 的 GNU coreutils 9.4、findutils 4.9 为准。BSD/macOS 的 `find`、`stat`、`xargs` 参数不同，脚本跨平台时要特别小心。

## 0.3.1 目录树：FHS 与 usrmerge {#sec-0.3.1}

这一节回答：Linux 为什么只有一棵目录树，`/etc`、`/var`、`/usr` 各放什么？usrmerge 之后 `/bin` 为什么变成一个链接？

::: preview 先抓住一件事
目录不是「文件夹图标」，而是一张「名字 → inode 号（文件系统内部给每个文件编的号）」的表；FHS 规定的是每个目录该放哪类数据。Ubuntu 24.04 把根下的可执行文件并进 `/usr`，所以 `/bin` 只是指向 `/usr/bin` 的符号链接。
:::

Linux 只有一棵以 `/` 为根的目录树。磁盘、分区、网络存储都通过**挂载**（mount）接到树的某个节点上，而不是各自拥有一个盘符。这是理解 `df`、`du`、`find -xdev` 的前提。

<pre class="tree">
/
├── bin -> usr/bin          # usrmerge 后是指向 /usr/bin 的符号链接
├── sbin -> usr/sbin
├── lib -> usr/lib
├── etc/                    # 主机配置：/etc/passwd、/etc/fstab、/etc/ssh
├── home/                   # 普通用户主目录
├── root/                   # root 的主目录（不在 /home 下）
├── usr/                    # 只读的系统资源：bin、lib、share、include
│   ├── bin/                # 用户命令
│   ├── sbin/               # 管理命令
│   └── local/              # 本地编译安装，优先级高于发行版包
├── var/                    # 可变数据：log、spool、lib、cache
│   ├── log/
│   └── lib/
├── tmp/                    # 临时文件，可能被清理，不要放持久数据
├── run/                    # 本次启动的运行时状态（tmpfs）
├── dev/                    # 设备节点：sda、null、tty、pts
├── proc/                   # 内核投影：进程与参数
├── sys/                    # 内核投影：设备与驱动模型
├── boot/                   # 内核与 initramfs
├── opt/                    # 第三方整包软件
├── srv/                    # 服务数据（约定，非强制）
├── mnt/  media/            # 临时挂载点 / 可移动介质
└── lost+found/             # ext4 修复时找回的孤儿文件
</pre>

这张树的读法是：**配置在 `/etc`，数据在 `/var`，程序在 `/usr`，内核接口在 `/proc` 与 `/sys`**。一个服务出问题，先按这四类找证据：配置改错看 `/etc`，写不进数据看 `/var` 的权限与空间，程序版本看 `/usr`，内核或设备看 `/proc`、`/sys`。

::: note 非科班补一层：目录是一张表
目录在磁盘上也是一份文件，内容是一张「名字 → inode 号」的表。inode（index node，索引节点）是文件系统给每个文件建的档案卡，文件名不在卡上，只在目录表里。你打开 `/etc/passwd` 时，内核先在 `/` 的表里找到 `etc`，再在 `etc` 的表里找到 `passwd`，最后按表里的 inode 号去读档案卡和数据块。
:::

FHS（Filesystem Hierarchy Standard，文件系统层次标准）规定了这些目录的用途，但不强制实现。Ubuntu 24.04 的 `/bin` 已经是指向 `/usr/bin` 的**符号链接**（symbolic link，软链接：一个内容为另一个路径的特殊文件，访问时内核按这个路径重新找过去），这叫 **usrmerge**：把根文件系统上的可执行文件合并进 `/usr`，让根分区可以更小、容器镜像更容易做只读层。

```bash
# 确认 usrmerge 是否生效
ls -ld /bin /sbin /lib
# 输出应类似：/bin -> usr/bin
```

`/usr/local` 是本地安装的默认前缀。`./configure --prefix=/usr/local` 装出来的程序在 `/usr/local/bin`，通常排在 `$PATH` 中发行版目录之前。这也是为什么「源码装了一个新版本，系统命令却还是旧的」——先 `type -a` 看实际执行的是哪个路径。

::: errata 关于目录树的三个误解
1. **「目录是装文件的盒子」**——目录本身是一张「名字 → inode 号」的表。同一文件系统内 `mv` 只改表项，数据块不动。
2. **「`/bin` 与 `/usr/bin` 是两份程序」**——usrmerge 后 `/bin` 是链接，两个路径落到同一批 inode。`ls -ld /bin` 看箭头，`readlink -f /bin/ls` 看最终路径。
3. **「FHS 由内核强制执行」**——FHS 是发行版与软件包的约定，内核不检查目录名；你完全可以在 `/data` 下放任何东西。
:::

### 0.3.1 小结

这一节把「文件在哪」拆成两件事：目录树给出路径，FHS 给出用途分区。配置看 `/etc`，可变数据看 `/var`，程序看 `/usr`，内核接口看 `/proc` 与 `/sys`；usrmerge 后根下的 `/bin`、`/sbin`、`/lib` 只是指向 `/usr` 的链接。如果只记住一件事，那就是：路径先落到某个用途区，排障时再去对应的区找证据。

## 0.3.2 路径、cwd 与解析 {#sec-0.3.2}

这一节回答：一个路径字符串怎样一步步落到文件？`.`、`..`、符号链接和挂载点分别在什么时候改变方向？

::: preview 先抓住一件事
绝对路径从 `/` 开始，相对路径从进程的当前工作目录（cwd）开始；解析是逐段查目录表，不是拿整串去比对。所以经过符号链接时，`pwd` 与 `pwd -P` 会给出两个不同但都「正确」的答案。
:::

路径分绝对与相对。绝对路径从 `/` 开始；相对路径从进程的**当前工作目录**（current working directory, cwd）开始。cwd 是进程的属性，不是 Shell 的全局变量；每个进程各有一份，`fork` 后继承，`chdir` 后只影响自己。

```bash
pwd            # 逻辑路径：可能包含符号链接
pwd -P         # 物理路径：解析掉所有符号链接
cd /tmp && pwd # 切换 cwd
cd -           # 回到上一个目录，并打印它
```

`pwd` 默认输出 `$PWD`，它可能是带符号链接的逻辑路径；`pwd -P` 让内核重新解析，给出真实路径。写脚本时如果要比较两个路径是否指向同一个文件，用 `pwd -P` 比较解析后的路径，或比较 `stat -c '%d:%i'`（设备号 + inode 号），不要只比较字符串或单独的 inode 号。

`cd` 默认也走逻辑路径：它记住你输入的字符串，不主动解析符号链接。`cd -P` 则在切换前把路径解析成物理路径。跑一遍就能看到差别：

```bash
mkdir -p /tmp/path-lab/real/sub
ln -sfn /tmp/path-lab/real /tmp/path-lab/link
cd /tmp/path-lab/link/sub
pwd                 # /tmp/path-lab/link/sub（逻辑路径）
pwd -P              # /tmp/path-lab/real/sub（物理路径）
cd -P /tmp/path-lab/link/sub && pwd
                    # /tmp/path-lab/real/sub（切换时已解析）
namei -l /tmp/path-lab/link/sub
                    # 逐级列出每一段的权限、属主与链接目标
```

`namei -l` 的价值在于把「逐段解析」摊开给你看：每一级目录一行，权限不对的那一级会立刻暴露；遇到符号链接，它会在行尾画出 `->` 目标。路径打不开时，先跑 `namei -l`，比反复 `ls` 更快。

路径解析由内核逐段完成。遇到符号链接就替换成目标，遇到 `.` 就留在当前目录，遇到 `..` 就回到父目录。有两个容易忽略的规则：

- **`..` 的落点取决于逻辑/物理模式**。默认 `cd` 走逻辑路径：`/a/link` 指向 `/x/y` 时，`cd /a/link` 后 `cd ..` 回到 `/a`；用 `cd -P /a/link` 切到物理路径后，`cd ..` 才回到 `/x`。脚本里依赖 `..` 找父目录时，先想清楚自己在哪种模式。
- **末尾斜杠要求目标是目录**。`cp file dir/` 要求 `dir` 是目录；`cp file dir` 在 `dir` 不存在时是「复制成名为 dir 的文件」。这个差别在脚本里经常导致意外。

路径上还可能跨过**挂载点**（mount point）：某个目录被另一个文件系统盖住，解析走到这里就换了一棵树，底下原来的内容暂时看不见。`findmnt -T /var/log` 告诉你这个路径属于哪个挂载，`stat -c '%d'` 的设备号变化说明跨了文件系统；0.3.5 判断 `mv` 是否原子，靠的就是这一点。

::: note 非科班补一层：解析是逐段问路
内核不会拿整个字符串去查表，而是从 `/` 开始一段一段走：先找 `home`，再在 `home` 里找 `wang`，最后找 `a.txt`。每一段都可能遇到符号链接或挂载点，所以同一个字符串在不同 cwd、不同进程里可能落到不同的 inode。`namei -l` 把这趟问路逐级打印出来。
:::

`cd` 是 Shell 内建，因为它要改变当前 Shell 的 cwd。`/bin/cd` 不存在。子进程里的 `cd` 不影响父 Shell：

```bash
# 子 Shell 里 cd，父 Shell 不动
( cd /tmp && pwd )   # 输出 /tmp
pwd                  # 仍在原目录
```

::: errata 关于路径解析的三个误解
1. **「`..` 永远回到物理上一层」**——Shell 的逻辑 cwd 经过符号链接时，`..` 按逻辑路径走。`cd -P` 切到物理路径后再 `..`，才会回到物理父目录。
2. **「`pwd` 输出的一定是真实路径」**——默认输出 `$PWD`，可能含符号链接；要物理路径用 `pwd -P`，要逐级证据用 `namei -l`。
3. **「`cd` 是一个可执行程序」**——`cd` 是 Shell 内建，只能改当前 Shell 的 cwd；子 Shell 里的 `cd` 不会影响父 Shell。
:::

### 0.3.2 小结

绝对路径从 `/` 起，相对路径从进程的 cwd 起；`.`、`..`、符号链接和挂载点都参与逐段解析。`pwd` 默认给逻辑路径，`pwd -P`、`cd -P` 与 `namei -l` 给物理路径和每一级的证据。如果只记住一件事，那就是：路径不是字符串比较，是一趟从根或 cwd 出发的逐段查找。

## 0.3.3 `ls -l` 逐列读与 inode {#sec-0.3.3}

这一节回答：`ls -l` 的一行里每一列各是什么？`stat` 多给了哪些字段？inode、链接数、字节数和块数之间是什么关系？

::: preview 先抓住一件事
`ls -l` 把「名字」和「元数据」放在同一行，`ls -i` 再补上 inode 号；链接数数的是名字，size 数的是字节，块数才是磁盘占用。把这三组数字分开，链接与「大小对不上」的问题就有一半答案了。
:::

<div class="terminal" data-title="bash · 目录、链接与 inode">
<pre><span class="p">&#36;</span> mkdir -p /tmp/fs-lab &amp;&amp; cd /tmp/fs-lab
<span class="p">&#36;</span> printf 'hello\n' &gt; a.txt
<span class="p">&#36;</span> ln a.txt hard.txt
<span class="p">&#36;</span> ln -s a.txt soft.txt
<span class="p">&#36;</span> ls -li
total 8
131073 -rw-r--r-- 2 wang wang 6 Oct 17 10:31 a.txt
131073 -rw-r--r-- 2 wang wang 6 Oct 17 10:31 hard.txt
131074 lrwxrwxrwx 1 wang wang 5 Oct 17 10:31 soft.txt -&gt; a.txt
<span class="p">&#36;</span> stat -c '%n inode=%i links=%h size=%s' a.txt hard.txt soft.txt
a.txt inode=131073 links=2 size=6
hard.txt inode=131073 links=2 size=6
soft.txt inode=131074 links=1 size=5
<span class="p">&#36;</span> rm a.txt
<span class="p">&#36;</span> cat hard.txt
hello
<span class="p">&#36;</span> cat soft.txt
cat: soft.txt: No such file or directory
</pre>
</div>

`ls -l` 的每一列：

| 列 | 例子 | 含义 |
|:--|:--|:--|
| 权限 | `-rw-r--r--` | 类型 + 属主/属组/其他人的 `rwx` |
| 链接数 | `2` | 指向同一 inode 的硬链接数（目录还含 `.` 与子目录的 `..`） |
| 属主 | `wang` | 文件所有者 |
| 属组 | `wang` | 文件所属组 |
| 大小 | `6` | 普通文件是字节数；目录是目录项块的大小；符号链接是目标路径长度 |
| 时间 | `Oct 17 10:31` | 默认显示 mtime；超过六个月显示年份 |
| 名字 | `a.txt` | 目录项的名字；符号链接追加 `-> target` |

`ls -i` 在第一列显示 inode 号。`a.txt` 与 `hard.txt` 的 inode 号相同、链接数都是 2，说明它们是同一个文件的两个名字。`soft.txt` 是独立 inode，内容是字符串 `a.txt`。

::: note 非科班补一层：inode、链接数与块
inode 是文件系统给每个文件开的档案卡：类型、权限、属主、三个时间、链接数、字节数、数据块位置都写在上面，唯独不写文件名。第二列链接数是「有多少个名字指向这张卡」，不是「有几个副本」。`Size` 是字节数，`Blocks` 是实际分配的 512 字节块数：稀疏文件（中间有大段空洞、没有真正写数据的文件）可以 Size 很大、Blocks 很小，所以 `ls -l` 的大小不等于磁盘占用。
:::

```bash
stat -c '%n size=%s blocks=%b' a.txt   # blocks 以 512 字节为单位
ls -ls a.txt                           # 第一列是 1 KiB 块数，不是字节
du -h a.txt                            # 磁盘实际占用
```

`stat` 给出三个时间，初学最容易混：

| 时间 | 字段 | 何时更新 | 常被误认为 |
|:--|:--|:--|:--|
| atime | `%x` | 读取文件内容时（受 `relatime` 限制） | 创建时间 |
| mtime | `%y` | 修改文件内容时 | 修改权限的时间 |
| ctime | `%z` | 修改 inode 元数据（权限、属主、链接数、mtime）时 | 创建时间 |

创建时间没有跨文件系统的保证：`statx` 的 `btime`（`stat %w` 可读）在 ext4/XFS/Btrfs 上可用，但并非所有文件系统都支持，`stat` 默认输出也不含它。`mtime` 只反映内容变化，改权限只动 `ctime`。备份工具用 `mtime` 判断是否需要复制，用 `ctime` 判断元数据是否变化。

Ubuntu 默认挂载选项含 `relatime`：只有 atime 比 mtime/ctime 旧，或超过 24 小时，才更新 atime。这是为了减少每次读文件都写元数据的开销。要更精确的 atime，用 `strictatime`，但会明显增加写放大。

::: errata 关于 `ls -l` 与 `stat` 的三个误解
1. **「`ls -l` 的 size 就是磁盘占用」**——那是 apparent size（表观大小，字节数）；实际占用看 `stat` 的 `Blocks` 或 `du`。稀疏文件与硬链接会让两者差很多。
2. **「链接数是子目录数」**——它是有多少个名字指向这个 inode。普通文件的链接数来自硬链接；目录还额外含 `.` 和每个子目录的 `..`。
3. **「ctime 是创建时间」**——ctime 是 inode 状态改变时间，改权限也会更新它；创建时间看 `stat %w` 的 btime，且并非所有文件系统都支持。
:::

### 0.3.3 小结

`ls -l` 一行给类型与权限、链接数、属主属组、字节数、mtime 和名字；`ls -i` 补 inode 号，`stat` 补块数与 atime/mtime/ctime。链接数数的是名字，size 数的是字节，块数才是磁盘占用。如果只记住一件事，那就是：先用 `ls -li` 把名字和 inode 对上，再谈大小与时间。

::: method 即时自测 · 0.3.3

**Q2（辨析）** 两个文件 `ls -li` 显示同一个 inode、链接数都是 2，说明什么？一个文件 size 是 6 字节、blocks 是 8，为什么不矛盾？

**Q3（应用）** 两个文件 `ls -l` 大小相同，`du` 的占用却差很多（或一起统计时只算一份）。列出至少两个可能原因和对应的验证命令。

::: sol 答案
**A1** 权限、链接数、属主、属组、大小、mtime、名字；`stat` 另给 atime（最后访问）与 ctime（inode 状态改变），mtime 与 `ls -l` 显示的是同一个。
**A2** 它们是同一个文件的两个名字，共享 inode 与数据；size 是逻辑字节数，blocks 是实际分配的 512 字节块，6 字节文件通常也要占一个 4 KiB 块，所以 8 个 512 字节块并不奇怪。
**A3** 可能是稀疏文件（`ls -ls` 看块数、`du -h --apparent-size` 对比）或硬链接（`ls -li` 看 inode，`du` 对同一 inode 默认只计一次）；也可能是写时复制或压缩（`stat -f` 看文件系统块大小，`filefrag` 看物理块分布）。
:::

## 0.3.4 硬链接与软链接 {#sec-0.3.4}

这一节回答：同一份数据为什么能有多个名字？硬链接和软链接各自在 inode 层存了什么，删掉目标后又会怎样？

::: preview 先抓住一件事
硬链接只是目录表里多了一行，和原名字指向同一个 inode，链接数加一；软链接是一个独立 inode，内容为目标路径字符串。目标删掉后，硬链接仍能读数据，软链接变成悬空链接。
:::

先看一个现象。在 0.3.3 的 `/tmp/fs-lab` 里，`a.txt` 与 `hard.txt` 的 inode 号相同、链接数都是 2；`soft.txt` 的 inode 号不同，大小只有 5 字节——正好是目标字符串 `a.txt` 的长度。名字、inode、数据三者谁跟谁绑定，一张 `ls -li` 就摆出来了。

::: def 定义 · 硬链接与符号链接 {#def-0.3.1}
**硬链接**（hard link）是目录中一个「名字 → inode」的目录项。多个硬链接指向同一个 inode，共享同一份数据与元数据；删除一个名字只是把 inode 的链接数减一，减到 0 且没有进程打开时才释放数据。**符号链接**（symbolic link，软链接）是一个独立文件，内容是目标路径字符串；访问时内核按该字符串重新解析。
:::

<pre class="layout">
硬链接：
  /home/wang/a.txt ─┐
                    ├──→ inode 131073（links=2）──→ 数据块 "hello\n"
  /home/wang/hard.txt ┘
&#8203;
符号链接：
  /home/wang/soft.txt ──→ inode 131074（内容是 "a.txt"）──→ 解析后到达 a.txt
</pre>

::: note 非科班补一层：两种链接各存了什么
硬链接没有自己的 inode，它只是目录表里多了一行，指向原来的 inode，所以链接数加一、数据只有一份。软链接有自己的 inode，内容是一串目标路径；内核读到这串路径再重新解析，目标没了就停在半路，这就是悬空链接（dangling link）。`ls -li` 看 inode 号是否相同，`readlink` 看软链接存了什么。
:::

两者的边界：

| 维度 | 硬链接 | 符号链接 |
|:--|:--|:--|
| 跨文件系统 | 不允许，`EXDEV` | 允许 |
| 指向目录 | 普通用户不允许（防止环） | 允许 |
| 目标删除后 | 数据仍在，另一个名字可用 | 悬空（dangling），访问报 `ENOENT` |
| 大小 | 与目标相同 | 目标路径字符串的长度 |
| 权限 | 与目标共享 | 自身 `lrwxrwxrwx`，权限位被忽略 |
| `rm` 行为 | 链接数减一 | 删除链接本身，不动目标 |
| 备份/打包 | 需保留链接关系（`tar` 默认保留） | 保存目标字符串 |

创建与检查：

```bash
ln target hardlink          # 硬链接；target 必须存在
ln -s target symlink        # 符号链接；target 可以不存在
ln -sfn /new/target link    # -f 覆盖，-n 把链接当文件而不是目录
readlink link               # 打印链接内容
readlink -f link            # 解析到最终绝对路径；-e 要求目标必须存在
ls -l link                  # 看箭头
find . -maxdepth 1 -type l  # 找符号链接
```

`ln -s target link` 中的 `target` 若是相对路径，**相对于 link 所在目录**解析，不是相对于当前目录。这是脚本里最常见的悬空链接来源：

```bash
# 错误：在 /tmp 下执行，链接指向 /tmp/a.txt，而不是 /etc/a.txt
ln -s /etc/a.txt /tmp/link        # 绝对路径，没问题
ln -s a.txt /tmp/rel-link         # 指向 /tmp/a.txt
# 正确写法之一：先 cd 到目标目录，或用绝对路径
```

硬链接还有一个常被忽略的用途：**节省空间**。同一份大文件在同一个文件系统内做多个硬链接，只占一份数据；`rsync -H`、`tar` 的硬链接保留、Borg 的去重都依赖这个概念。反过来，`du` 默认对同一 inode 只计一次，`du --count-links` 才会重复计。

::: errata 关于链接的三个误解
1. **「链接数就是副本数」**——链接数是有多少个名字指向同一个 inode，数据只有一份；删一个名字只减链接数，不复制也不搬数据。
2. **「删掉原文件，软链接会一起消失」**——软链接本身还在，只是悬空；`readlink` 仍打印目标路径，`cat` 才报 `No such file or directory`。
3. **「`ln -s` 的相对目标相对当前目录」**——相对目标按**链接所在目录**解析；在 `/tmp` 里执行 `ln -s a.txt /opt/link`，它找的是 `/opt/a.txt`，不是 `/tmp/a.txt`。
:::

### 0.3.4 小结

硬链接是目录表里的另一个名字，与目标共享 inode、链接数和数据块，不能跨文件系统，普通用户也不能给目录建；软链接是独立 inode，存目标路径，可跨文件系统，目标删掉后变成悬空链接。如果只记住一件事，那就是：硬链接共享 inode，软链接只共享一个路径字符串。

::: method 即时自测 · 0.3.4
**Q1（记忆）** `ln a b` 与 `ln -s a b` 之后，`ls -li` 的 inode 列和链接数列分别怎样变化？

**Q2（辨析）** 删除 `a.txt` 之后，`hard.txt` 与 `soft.txt` 各是什么状态？`readlink soft.txt`、`cat soft.txt` 分别返回什么？

**Q3（应用）** 发布目录有 `releases/v1`、`releases/v2`，要让 `current` 指向当前版本并方便切换，应建硬链接还是软链接？写出切换命令；如果要求切换瞬间不出现空窗，命令该怎么写？

::: sol 答案
**A1** `ln a b`：`b` 与原文件 inode 相同，链接数从 1 变 2；`ln -s a b`：`b` 是新 inode，链接数为 1，内容是字符串 `a`。
**A2** `hard.txt` 仍指向原 inode，数据可读；`soft.txt` 仍在但悬空，`readlink` 仍输出 `a.txt`，`cat` 报 `No such file or directory`。
**A3** 用软链接：`ln -sfn releases/v2 current`。要求无空窗时，先建临时链接再原子替换：`ln -s releases/v2 current.tmp && mv -T current.tmp current`。硬链接不能跨文件系统、不能指向目录，切换时还要先删旧名字，做不到一条命令改指向。
:::
:::

## 0.3.5 cp、mv、rm 的边界 {#sec-0.3.5}

这一节回答：`cp`、`mv`、`rm` 看起来最简单，为什么最容易出事？复制会丢哪些元数据，移动在什么条件下不原子，删除后空间为什么可能不释放？

::: preview 先抓住一件事
`cp` 默认复制内容、按 umask 重建元数据，`cp -a` 才保留权限、时间与链接；`mv` 同一文件系统内只是改目录项，跨文件系统则退化成「复制 + 删除」；`rm` 只是 unlink，空间要等最后一个打开它的进程关闭 fd 才释放。
:::

先看三个常见事故：用 `cp -r` 恢复的服务因为权限不对起不来；`mv` 一个目录到另一块盘，中途断电后目标只有一半；`rm` 掉正在写的日志，`df` 还是满。三个命令看起来最简单，出事也最多；下面按 `cp`、`mv`、`rm` 的顺序，把每个命令真正改动的对象拆开。

### cp：复制的是内容与元数据

| 写法 | 行为 |
|:--|:--|
| `cp src dst` | 复制内容；`dst` 存在则覆盖（默认不提示） |
| `cp -i src dst` | 覆盖前询问；别名常设为 `cp -i` |
| `cp -r dir dst` | 递归复制，**不保留**权限、时间、属主 |
| `cp -a dir dst` | archive：递归 + 保留权限/时间/链接/属主（属主需 root） |
| `cp -p src dst` | 保留 mode、ownership、timestamps |
| `cp --reflink=auto src dst` | 支持写时复制（CoW）的文件系统（Btrfs/XFS）上做轻量复制 |

`cp -a` 是备份与迁移的默认选择。它保留符号链接本身而不是跟随，保留硬链接关系，保留权限与时间。`cp -r` 不保留这些，恢复出来的服务可能因为权限不对而起不来。

### mv：同一文件系统内是 rename

在同一文件系统内，`mv` 只是修改目录项，原子且几乎不耗时；跨文件系统时，`mv` 变成「复制 + 删除」，中途失败可能留下半个目标文件。判断是否同一文件系统：

```bash
stat -c '%d %n' /src/file /dst/
# 第一列是设备号；不同则是跨文件系统
findmnt -T /dst
```

跨文件系统移动大文件时，先 `cp -a` 到目标、校验、再删除源；不要直接 `mv` 后假设成功。在同一文件系统内，`mv` 覆盖目标也是原子的 rename：目标要么是旧文件，要么是新文件，不会出现半个；跨文件系统则没有这个保证。

::: note 非科班补一层：跨文件系统的 mv 为什么不是原子
同一文件系统内，`mv` 只改目录表里的一行，内核一次就改完；跨文件系统时没有共同的目录表可改，`mv` 只能在新位置复制一份、再删旧的一份。复制到一半断电，目标端会留下不完整的文件，源文件还在——所以它既不原子，也不能简单重跑。
:::

### rm：没有回收站

`rm` 删除的是目录项，inode 的链接数减一；数据块在链接数为 0 且没有进程打开时释放。如果还有进程持有 fd，磁盘空间不会立即回收——这就是「`rm` 了日志，`df` 还是满」的原因。

::: note 非科班补一层：删了文件，空间去哪了
`rm` 只把目录里的名字去掉；inode 的链接数减到 0 后，如果没有进程还开着它，内核才回收数据块。日志服务通常一直开着日志文件，所以删掉名字后空间仍被它的 fd 占着；`lsof +L1` 列出链接数为 0 但仍打开的文件，重启服务或让它关闭 fd 才会真正释放。
:::

安全习惯：

```bash
# 1. 先列出将被删除的内容，确认路径
find /var/tmp/cache -mindepth 1 -maxdepth 1 -print

# 2. 变量必须加引号并检查非空
: "${CACHE_DIR:?CACHE_DIR is not set}"
[[ $CACHE_DIR == /var/tmp/cache ]] || { echo "unexpected dir"; exit 1; }

# 3. 用 -- 终止选项解析，防止文件名以 - 开头
rm -rf -- "$CACHE_DIR"/*

# 4. 更稳的做法：先移到隔离目录，确认后再删
mkdir -p /var/tmp/trash && mv -- "$CACHE_DIR"/* /var/tmp/trash/
```

`rm -rf` 的三个高危模式：

- **变量为空**：`rm -rf "$DIR"/` 在 `DIR` 为空时变成 `rm -rf /`。用 `${DIR:?}` 强制非空。
- **末尾斜杠跟着符号链接走**：`rm -rf /var/log/app/` 与 `rm -rf /var/log/app` 对真实目录效果相同；但如果 `app` 是指向别处的符号链接，带斜杠会作用到目标目录，不带斜杠只删链接。删除前先 `ls -ld` 看类型。
- **通配符没匹配**：`rm -rf $DIR/*` 在 `$DIR` 为空时变成 `rm -rf *`，删除当前目录。用 `find ... -delete` 或先检查。

`rm` 默认不进入回收站。需要可恢复删除时，用 `trash-cli`（`trash-put`）或桌面环境的回收站；服务器上更常见的做法是「先移动到带时间戳的隔离目录，定期清理」。

::: errata 关于复制、移动、删除的三个误解
1. **「`rm` 会把数据清零」**——`rm` 只删目录项并减链接数；块被回收后，内容在被覆盖前仍可能被取证工具读回。要防恢复，得用覆盖写或全盘加密。
2. **「跨文件系统 `mv` 也是原子 rename」**——它退化成「复制 + 删除」，中途失败会留下半个目标。先 `stat -c %d` 或 `findmnt -T` 确认是否同一文件系统。
3. **「`cp -a` 只是 `cp -r` 的别名」**——`-a` 还保留权限、时间、属主与链接关系；`-r` 不保留，恢复服务时可能因权限不对而起不来。
:::

### 0.3.5 小结

`cp` 默认复制内容、按 umask 重建元数据，`cp -a` 才保留权限、时间与链接；`mv` 同一文件系统内是改目录项的 rename，跨文件系统退化成复制加删除；`rm` 是 unlink，空间要等最后一个 fd 关闭才释放。如果只记住一件事，那就是：先问「是不是同一个文件系统、还有没有进程开着」，再决定用哪条命令。

::: method 即时自测 · 0.3.5
**Q1（记忆）** `cp -r` 与 `cp -a` 差在哪？`mv` 在同一文件系统内实际做的是哪个系统调用？`rm` 呢？

**Q2（辨析）** `rm` 掉一个正在写的日志后，`df` 仍然满、`du` 却很小。解释原因并给出两条排查命令。

**Q3（应用）** 要把 200 GB 目录从 `/home` 移到另一个挂载的 `/data`，写出安全步骤。为什么不能直接 `mv` 后就关机？

::: sol 答案
**A1** `cp -a` 在递归之外还保留权限、时间、属主与链接关系，`cp -r` 不保留；同文件系统 `mv` 用 `rename`/`renameat2` 改目录项；`rm` 用 `unlink` 删目录项。
**A2** 进程还开着该文件的 fd，inode 链接数为 0 但数据块未释放；用 `lsof +L1` 找进程，用 `df -h` 与 `du -sh` 对比确认，再重启服务或让它关闭 fd。
**A3** 先 `findmnt -T /data`、`stat -c %d /home /data` 确认跨文件系统；`cp -a` 到目标，`du -s` 或校验和对比，确认无误再删源。直接 `mv` 跨文件系统是复制加删除，中断会留下不完整目标，不能假设成功。
:::
:::

## 0.3.6 find：按条件筛文件 {#sec-0.3.6}

这一节回答：怎样让 `find` 只交出你要的文件，而不是把整棵目录树都打印出来？

::: preview 先抓住一件事
`find` 的模型是「从你给的起点开始，对树里的每个目录项（目录里的一个名字条目）求一遍表达式」，为真就执行动作。多个条件没写连接词时默认是 AND；条件写错不会报错，只会安静地多给或少给结果。
:::

先跑一条最小的：

```bash
find /etc -maxdepth 1 -name '*.conf' -print
```

它从 `/etc` 出发，遇到每个目录项就求一次 `-name '*.conf'`；为真才执行 `-print`。默认动作就是 `-print`，所以最后那个 `-print` 可以省略。`-maxdepth 1` 只让它在 `/etc` 这一层找，不往下钻；起点给 `/` 时，就是从目录树根开始扫整棵树。

::: note 非科班补一层：find 是一个在树上跑的循环
可以把 `find 起点 条件...` 读成一个循环：对起点下的每个目录项，按顺序求条件；全为真就执行动作。目录项包括普通文件、目录和符号链接，所以不加 `-type` 时，目录名也可能被 `-name` 匹配到。
:::

`find` 默认不跟随符号链接：链接本身会被列出，但不会走进它指向的目录。要跟随用 `-L`，但要小心链接环。它也会列出隐藏文件，因为它是直接读目录，不经过 Shell 的通配符展开。

| 条件 | 例子 | 说明 |
|:--|:--|:--|
| 名字 | `-name '*.log'`、`-iname '*.LOG'` | 通配符由 find 解释，必须加引号 |
| 类型 | `-type f`、`-type d`、`-type l` | 普通文件/目录/符号链接 |
| 时间 | `-mtime -7`、`-mmin -30`、`-newer ref` | 按天/分钟；`-7` 表示 7 天内 |
| 大小 | `-size +100M`、`-size -1k` | `+` 大于，`-` 小于；单位 c/k/M/G |
| 权限 | `-perm 4755`、`-perm -4000` | 精确/至少包含 |
| 属主 | `-user alice`、`-group dev` | 按名字或 UID |
| 深度 | `-maxdepth 2`、`-mindepth 1` | 限制遍历深度 |
| 组合 | `\( -name '*.log' -o -name '*.tmp' \)` | 括号需转义，`-a` 是默认 |

`find /var -type f -name '*.log'` 不是「先按类型找一趟、再按名字找一趟」，而是一趟：每个路径同时过 `-type` 和 `-name`，两个都为真才 `-print`。两个条件之间没写 `-a`，`find` 默认补上 AND；要「或」就写 `-o`，并用转义括号圈住范围。

三个高频用法：

```bash
# 1. 找大文件（不跨文件系统，避免扫到挂载的网络盘）
find /var -xdev -type f -size +100M -printf '%s\t%p\n' 2>/dev/null | sort -nr | head -20

# 2. 找最近修改过的配置
find /etc -type f -mmin -60 -print

# 3. 找 setuid 程序（权限审计，见 0.4）
find / -xdev -type f -perm -4000 -print 2>/dev/null
```

`-printf` 是 GNU find 的扩展，比 `-exec stat` 快得多。`%s` 是字节数，`%p` 是路径，`%T@` 是 mtime 的 epoch 秒。BSD/macOS 的 find 没有 `-printf`，跨平台脚本要用 `-exec stat` 或 `-print0` 交给其他工具。

`-exec` 有两种结尾：`\;` 每个文件执行一次，`+` 尽量批量执行。批量更快，但命令必须能接受多个参数：

```bash
# 每个文件一次；{} 必须与 \; 分开
find . -name '*.tmp' -exec rm -- {} \;

# 批量传参；等价于 xargs，但没有空格问题
find . -name '*.tmp' -exec rm -- {} +
```

`find` 默认一行输出一个路径；文件名里带换行时，下游分不清边界。要交给 `xargs` 或脚本时，用 `-print0` 让每个路径以 NUL（空字符，字节值 0）结尾，下一节展开。

`-delete` 是 find 自带的删除动作，比 `-exec rm` 少一次 fork，但**必须放在所有条件之后**，且默认不会跟随符号链接。先用 `-print` 试跑，再把 `-print` 换成 `-delete`：

```bash
# 先看
find /var/tmp/cache -type f -mtime +30 -print
# 确认后删
find /var/tmp/cache -type f -mtime +30 -delete
```

`-prune` 用来排除目录：`find . -path ./node_modules -prune -o -type f -print`。逻辑是「匹配 node_modules 就剪枝，否则打印普通文件」；`-o` 的优先级和括号需要小心。

「全盘按名字找文件」还有第二条路：`locate` 走**预建数据库**而不是实时遍历。Ubuntu 24.04 默认装 `plocate`（mlocate 的替代），数据库在 `/var/lib/plocate/`，由 `plocate-updatedb.timer` 每天刷新一次，`/etc/updatedb.conf` 的 `PRUNEPATHS`、`PRUNEFS` 决定哪些路径和文件系统不进库：

```bash
locate -i report.md     # 毫秒级返回；-i 忽略大小写；只匹配路径名
sudo updatedb           # 刚建的文件查不到时手动刷新，读同一个 updatedb.conf
```

`find` 与 `locate` 的分工：`find` 实时、条件丰富（权限、大小、属主），代价是真遍历；`locate` 快，但最多滞后一天，且只能按路径名匹配。日常配合是 `locate` 先给候选，`find` 再精确过滤。`/tmp`、`/proc` 这类被 prune 的路径不在数据库里，找它们仍要用 `find`。

::: errata 常见误解
1. **「`-name` 匹配整条路径」**——`-name` 只匹配最后一段文件名；要匹配路径用 `-path './src/*'`，要忽略大小写用 `-iname`。
2. **「`-o` 两边会各执行一次动作」**——隐式 AND 比 `-o` 结合得紧。`find . -name '*.log' -o -name '*.tmp' -delete` 只删 `*.tmp`；要删两类，写成 `find . \( -name '*.log' -o -name '*.tmp' \) -delete`，并先用 `-print` 试跑。
3. **「`-delete` 可以放在条件中间」**——动作也是表达式的一部分，放在前面会对还没筛完的路径生效。把 `-delete` 放到最后，并先用 `-print` 确认清单。
:::

### 0.3.6 小结

`find` 从起点开始遍历，对每个目录项求表达式；隐式 AND 把条件串起来，`-o` 和括号改变优先级。默认动作是 `-print`，`-delete`、`-exec` 只是把动作换掉。如果只记住一件事，那就是：先用 `-print` 看清结果，再决定要不要把动作接上去。

::: method 即时自测 · 0.3.6

**Q2（辨析）** `find . -name '*.log' -o -name '*.tmp' -delete` 会删掉哪一类文件？为什么不是两类都删？

**Q3（应用）** 要删除 `/var/tmp/cache` 下 30 天没改过的普通文件，写出「先试跑、再删除」的两条命令，并说明为什么要加 `-xdev`。

::: sol 答案

## 0.3.7 xargs -0 与批量操作 {#sec-0.3.7}

这一节回答：`find` 已经筛出了文件，怎样把这些路径安全地交给第二条命令，而不被空格、引号或换行拆坏？

::: preview 先抓住一件事
`xargs` 把标准输入变成命令行参数，默认按空白分词，所以带空格的文件名会被拆成两个参数。让上游用 `-print0` 输出 NUL 分隔、下游用 `xargs -0` 按 NUL 读，才能保证「一个路径一个参数」。
:::

先造两个「坏名字」：

```bash
lab=$(mktemp -d) && cd "$lab"
printf 'a\n' > 'report 2026.txt'
printf 'b\n' > $'line\nbreak.txt'
find . -type f -print | xargs -r -n1 printf '[%s]\n'
```

输出会把两个名字切成四段（顺序随目录而定）：

```text
[./report]
[2026.txt]
[./line]
[break.txt]
```

Linux 文件名只禁止 `/` 和 NUL，空格、换行、引号、反斜杠都可以出现在名字里。`find -print` 用换行分隔路径，`xargs` 又按空白分词，两个假设叠在一起就出错。换成 NUL：

```bash
find . -type f -print0 | xargs -0 -r -n1 printf '[%s]\n'
```

```text
[./report 2026.txt]
[./line
break.txt]
```

NUL 是唯一不会出现在文件名里的字节，所以它能当可靠的分隔符。`-print0` 和 `-0` 必须成对使用：上游输出 NUL，下游才按 NUL 切。

::: note 非科班补一层：参数之间要有分隔符
C 程序拿到的 `argv` 是一组字符串，内核不记录它们原来怎么分隔。`xargs` 要把一段字节流还原成这组字符串，只能自己选分隔符：默认选空白，所以名字里的空格会被当成边界；`-0` 改选 NUL，边界才不会和名字冲突。
:::

正确做法是让上游用 NUL 分隔，下游用 `-0`：

```bash
# 上游 -print0，下游 -0；-r 在空输入时不执行命令
find /srv/app/conf -type f -name '*.conf' -print0 \
    | xargs -0 -r sha256sum > /var/tmp/conf.sha256

# 每次只传一个文件；-I{} 会把 {} 替换成参数
find . -name '*.png' -print0 \
    | xargs -0 -r -I{} sh -c 'pngquant --force --output "$1" "$1"' _ {}

# 并行 4 路；适合压缩、校验等 CPU 密集任务
find . -type f -name '*.log' -print0 \
    | xargs -0 -r -n1 -P4 gzip
```

`-I{}` 隐含 `-n1`，且会把参数中的引号处理得更保守；它比 `-n1` 慢，但可读。`sh -c '...' _ {}` 里的 `_` 是 `$0` 占位，`{}` 变成 `$1`，这样文件名不会被当成 shell 代码执行——直接 `sh -c 'cmd {}'` 在文件名含 `;` 时会注入命令。

批量删除、压缩、改权限之前，先把动作换成 `printf` 跑一遍：

```bash
find /srv/app -type f -name '*.log' -print0 \
    | xargs -0 -r printf 'would gzip %s\n'
```

确认清单只包含该压的文件，再把 `printf` 换成 `gzip`。这一步不花钱，却能挡住「路径写错、变量为空、`-r` 漏写」三类事故。

`xargs` 的退出码是确定的：任一子命令以 1–125 退出，整体返回 123；子命令以 255 退出是 124，被信号杀死是 125，找不到命令是 127（全表见 0.3.15）。返回 0 只说明每次调用都成功。如果一次调用处理多个文件，其中一个失败但命令仍退出 0，`xargs` 看不出来。批量任务仍要检查每个子命令的退出码，或改用 `find -exec ... +` 并在脚本里检查 `$?`。

::: errata 常见误解
1. **「文件名不会含空格或换行」**——除 `/` 和 NUL 外都可能出现；脚本里一律用 `-print0` 加 `xargs -0`，不要用 `for f in $(find ...)`。
2. **「`xargs` 默认一次只传一个文件」**——默认会尽量多塞，直到接近参数长度上限；要逐个处理用 `-n1` 或 `-I{}`，后者还隐含 `-n1`。
3. **「`xargs` 返回 0 就代表每个文件都成功」**——它只看子进程退出码；一条命令处理十个文件、其中一个失败但命令仍退出 0 时，`xargs` 也返回 0。批量任务要自己记录失败清单。
:::

### 0.3.7 小结

`xargs` 的职责是把标准输入拼成参数列表；默认按空白分词，遇到任意文件名就会断错。`-print0` 与 `-0` 用 NUL 做分隔符，`-n1` 或 `-I{}` 控制每次传几个，`printf` 试跑把动作先降级成只读。如果只记住一件事，那就是：路径从 `find` 交给下一条命令时，分隔符必须用 NUL。

::: method 即时自测 · 0.3.7
**Q1（记忆）** `-print0` 输出什么分隔符？`xargs -0` 按什么分隔？`-r` 在空输入时做什么？

**Q2（辨析）** 目录里只有 `a b.log`，`find . -name '*.log' | xargs gzip` 会发生什么？请按分词顺序说明。

**Q3（应用）** 要把 `/srv/app/conf` 下所有 `.conf` 的 SHA-256 写进 `/var/tmp/conf.sha256`，要求带空格的文件名也正确、目录为空时不留空命令。写出试运行和正式命令。

::: sol 答案
**A1** `-print0` 用 NUL（`\0`）结束每个路径；`xargs -0` 按 NUL 切分参数；`-r` 让 `xargs` 在标准输入为空时不执行命令。
**A2** 输入被切成 `./a` 和 `b.log` 两个参数；这两个路径都不存在（真实名字是 `./a b.log`），`gzip` 两次报 `No such file or directory`，真正的文件没有被压缩。
**A3** 先跑 `find /srv/app/conf -type f -name '*.conf' -print0 | xargs -0 -r printf 'would hash %s\n'`；确认后把 `printf` 段换成 `xargs -0 -r sha256sum > /var/tmp/conf.sha256`。两段都必须用 `-print0` 与 `-0` 配对。
:::
:::

## 0.3.8 看清占用：du、tree 与 ncdu {#sec-0.3.8}

这一节回答：磁盘满了，怎样从分区一路下钻到具体目录，并解释 `du` 与 `ls -l` 为什么经常对不上？

::: preview 先抓住一件事
`ls -l` 报的是文件有多少字节（表观大小），`du` 报的是文件系统实际分配了多少块。稀疏文件、硬链接、块对齐和已删除但仍打开的文件，都会让这两个数字对不上。
:::

`du` 统计目录下文件占用的**磁盘块**，不是表观大小。稀疏文件（sparse file，逻辑长度很大、只在实际写入处分配块的文件）、压缩文件系统、CoW（写时复制）快照都会让两者不同。先看一个 1 GiB 的稀疏文件：

```bash
truncate -s 1G /tmp/sparse.img
ls -lh /tmp/sparse.img                  # 1.0G
du -h /tmp/sparse.img                   # 0
du -h --apparent-size /tmp/sparse.img   # 1.0G
```

`truncate` 只改文件长度，不写数据块；文件系统因此只在真正写入处分配块。`ls` 和 `--apparent-size` 数逻辑字节，`du` 数实际块。硬链接也会让账对不上：

```bash
dd if=/dev/zero of=big bs=1M count=10 status=none
ln big big2
du -h .                 # 10M
du -h --count-links .   # 20M
```

两个名字指向同一个 inode，`du` 默认只算一次，但 `ls -l` 两个名字都报同样大小。它回答的是「这块盘实际占了多少」，不是「这些文件加起来有多大」。

::: note 非科班补一层：文件系统按块记账
文件系统把空间切成固定大小的块（block，常见 4 KiB），一个 1 字节的文件也要占一块，所以 `du` 常比 `ls` 大；稀疏文件只在写入处分配块，所以 `du` 又可能比 `ls` 小很多。硬链接是同一个 inode 的多个名字，`du` 默认只算一次，免得把一份数据重复记账。
:::

| 命令 | 用途 | 注意 |
|:--|:--|:--|
| `du -sh dir` | 目录总占用 | `-s` 只给总和 |
| `du -h --max-depth=1 dir \| sort -h` | 逐个子目录排序 | `sort -h` 认 K/M/G |
| `du -x -sh /` | 不跨文件系统 | 避免把 `/proc`、网络盘算进来 |
| `du --apparent-size -sh` | 表观大小 | 稀疏文件会显得很大 |
| `tree -L 2 -d` | 看目录结构 | 只看两层，避免刷屏 |
| `ncdu /var` | 交互式浏览 | 需安装；按 `d` 删除前会确认 |

一个实用的排查顺序：

```bash
# 1. 哪个分区满了
df -h
# 2. 该分区下哪个一级目录最大
sudo du -x -h --max-depth=1 /var | sort -h | tail -10
# 3. 逐层下钻，直到定位到大文件/大目录
sudo du -x -h --max-depth=1 /var/log | sort -h | tail -10
# 4. 找已删除但仍被打开的文件
sudo lsof +L1 2>/dev/null | head
```

`du` 在大目录上会慢，因为它要遍历所有 inode。`ncdu` 把结果缓存到内存，交互式下钻更快；`duc`、`gt5` 也做同样的事。服务器上没装这些工具时，`du --max-depth=1 | sort -h` 足够。

文件操作的最后一组是打包与压缩。`tar` 只负责把多个路径串成一个归档，压缩由 `gzip`/`xz`/`zstd` 完成；`-z`、`-j`、`-J` 只是让 `tar` 顺手调用对应压缩器。

| 目的 | 命令 | 说明 |
|:--|:--|:--|
| 创建 gzip 归档 | `tar -czf app.tar.gz app/` | `-c` 创建，`-z` gzip，`-f` 指定文件 |
| 查看内容 | `tar -tzf app.tar.gz` | 解压前先看清单，确认没有绝对路径或 `..` |
| 解压到目录 | `tar -xzf app.tar.gz -C /srv/` | `-x` 解压，`-C` 先切到目标目录 |
| 去掉顶层目录 | `tar -xzf src.tar.gz --strip-components=1 -C src/` | 源码包常见：解压后不要多一层 `pkg-1.2.3/` |
| 排除文件 | `tar -czf logs.tar.gz --exclude='*.log' var/` | 模式要加引号，交给 tar 而不是 Shell |
| 压缩单文件 | `gzip -k app.log` / `zcat app.log.gz` | `gzip` 默认删除原文件，`-k` 保留 |
| 跨平台交换 | `zip -r site.zip site/` / `unzip -l site.zip` | zip 方便 Windows 解压，但不保留属主与硬链接 |

`tar` 的 `-f` 后面必须紧跟归档文件名，`-czf` 的顺序不能乱。解压不可信归档前先 `tar -tzf` 看清单，并在空目录或专用目录里解，不要直接解到 `/` 或当前工作目录；以 root 解压时，归档里的绝对路径和 `..` 可能覆盖系统文件。`tar` 会保留目录结构与时间；权限在 root 解压时按归档恢复，普通用户受 umask 影响。需要 ACL、xattr、SELinux 标签时加 `--acls --xattrs --selinux`（见 [0.8](ch08.md) 的备份脚本）。

::: errata 常见误解
1. **「`du` 的总和应该等于 `df` 的已用」**——`du` 只数看得见的文件，默认对硬链接去重；`df` 数整个文件系统的块，还含保留块、元数据、已删除但仍打开的文件。两者对不上是常态。
2. **「`du` 会把硬链接重复计算」**——默认只算一次，`--count-links` 才重复算。想知道「一份数据真实占多少」用默认值，想知道「这些名字加起来多大」才加 `--count-links`。
3. **「`ls -l` 大就是占盘多」**——`ls` 给表观字节，块通常按 4 KiB 对齐（取决于文件系统）；稀疏文件可以 1 GiB 却几乎不占块。反过来，一个 1 字节文件也至少占一块。
4. **「`ncdu` 里按 `d` 删除会进回收站」**——它直接 unlink，没有回收站；删除前看清路径，重要数据先备份。
:::

### 0.3.8 小结

`du` 数块，`ls` 数字节；稀疏文件与硬链接让两者对不上，`df` 与 `du` 的差额还要算上保留块和已删除但仍打开的文件。看占用按 `df` → `du --max-depth=1` → `lsof +L1` 下钻；打包只是把目录串成归档。如果只记住一件事，那就是：先问自己在数字节还是数块，再解释两个数字的差。

::: method 即时自测 · 0.3.8
**Q1（记忆）** `du` 默认统计什么？`-x` 与 `--apparent-size` 分别改变什么？

**Q2（辨析）** 一个 1 GiB 的稀疏文件，`ls -lh` 显示 1.0G、`du -h` 显示 0，矛盾吗？两个硬链接文件为什么会让 `du .` 小于两个文件大小之和？

**Q3（应用）** `df -h` 显示分区满了，`du -sh /var` 却只有几百 MB。写出三条排查命令，并说明每条在找什么。

::: sol 答案
**A1** `du` 默认统计实际分配的磁盘块（通常按 1 KiB 块报告，再换算成人类可读单位）；`-x` 让它停在本文件系统，不跨挂载点；`--apparent-size` 改成统计逻辑字节数。
**A2** 不矛盾：`truncate` 只改长度，没写数据块，`ls` 数逻辑字节、`du` 数实际块。硬链接共享同一个 inode，`du` 默认对同一 inode 只计一次，所以总量接近一份数据，而不是两份。
**A3** 先 `df -h` 确认哪个挂载点满；再 `sudo du -x -h --max-depth=1 /var | sort -h | tail` 逐层下钻；最后 `sudo lsof +L1` 找已删除但仍被进程打开的文件。若 `df -i` 也满，还要查 inode 耗尽。
:::
:::

## 0.3.9 FHS 的边界：同一棵树，不同的写入规则 {#sec-0.3.9}

这一节回答：同样放在根目录树下，为什么 `/etc` 的配置升级后还在，`/usr` 里手放的文件却会消失？

::: preview 先抓住一件事
FHS 不只规定「放什么」，还隐含「谁写、能活多久、能不能重建」。判断一个文件该放哪，先问它是程序本体、主机配置、服务状态，还是本次启动才有效的运行时数据。
:::

0.3.1 画了树的形状。真正决定「东西该放哪」的，是每个目录的**生命周期**与**写入者**。`/usr` 随发行版升级整体替换，`/etc` 由管理员改，`/var` 由服务自己写，`/run` 每次启动重建。把文件放错层，症状往往不是「找不到」，而是升级后被覆盖、容器里丢失、只读根分区上写失败。

| 目录 | 谁写 | 生命周期 | 典型误用 |
|:--|:--|:--|:--|
| `/usr` | 包管理器 | 随发行版版本替换 | 手工放配置或运行数据，升级后消失 |
| `/usr/local` | 管理员 | 跨发行版升级保留 | 与包管理器抢同一命令名 |
| `/opt` | 第三方整包 | 随软件自身升级 | 把零散脚本塞进 `/opt`，没有包边界 |
| `/etc` | 管理员/配置管理 | 跨升级保留，需合并 | 存二进制、缓存、大文件 |
| `/var/lib` | 服务进程 | 持久状态，必须备份 | 放可重建的缓存，备份膨胀 |
| `/var/cache` | 服务进程 | 可随时删除重建 | 放数据库文件，清缓存后数据丢失 |
| `/var/tmp` | 任意用户 | 重启保留，清理周期更长 | 当永久存储；仍可能被 `tmpfiles` 清 |
| `/run` | 服务/系统 | 本次启动，tmpfs（内存文件系统） | 放需要跨重启的 PID、socket |
| `/tmp` | 任意用户 | 可能每次启动清空 | 放长任务中间结果，跑到一半被清 |
| `/srv` | 管理员 | 站点数据，约定而非强制 | 发行版默认不建，脚本假设它存在 |
| `/boot` | 包管理器 | 内核与引导器 | 放业务数据；小分区容易被内核塞满 |

这张表的用法是：看到一个文件，先问「它能不能从别处重建」。能重建的放 `/var/cache` 或 `/tmp`；不能重建且属于服务状态的放 `/var/lib`；属于主机配置的放 `/etc`；属于程序本体的放 `/usr`。再按顺序问四件事：是不是程序本体（`/usr`）？是不是主机配置（`/etc`）？是不是服务要保留的状态（`/var/lib`）？是不是本次启动才有效（`/run`）？四问都否定，才考虑缓存或临时目录。

::: note 非科班补一层：用「可变性」判断放哪
可变性（volatility）指数据能活多久：`/usr` 跟发行版版本走，`/etc` 跟主机走，`/var` 跟服务走，`/run` 跟本次启动走。先判断可变性，再决定备份谁、给谁写权限；背目录名不如判断这条数据能不能重建。
:::

`/usr` 只读化是近十年的趋势。Fedora Silverblue、Flatpak 容器镜像、Android 都把 `/usr` 做成只读，`/etc` 用 overlayfs（叠合文件系统：把只读下层与可写上层叠成一个视图）合并，`/var` 单独可写。Ubuntu 24.04 的根分区仍可写，但 `usrmerge` 已经把 `/bin`、`/sbin`、`/lib` 收进 `/usr`，目的是让根分区只保留引导所需的最小内容。

容器把这一点放大：镜像里的 `/usr` 与 `/etc` 属于镜像层，容器重建就回到镜像状态；要保留的服务状态必须挂到 `/var/lib`，本次启动的 socket 挂到 `/run`。把数据库写进 `/var/cache`，或把唯一一份配置写进镜像的 `/etc`，一次重建就可能全丢。

```bash
# 确认哪些顶层目录是独立挂载
findmnt -t ext4,xfs,btrfs,overlay,tmpfs -o TARGET,SOURCE,FSTYPE,OPTIONS
# 确认某个路径落在哪个文件系统
findmnt -T /var/lib/docker
# 看挂载点与设备号
stat -c '%d %n' / /var /tmp
```

`/run` 与 `/var/run` 的关系要特别记住：Ubuntu 上 `/var/run` 是指向 `/run` 的符号链接，PID 文件、socket、锁文件按 FHS 应放 `/run`。把 PID 文件写到 `/var/run` 在旧脚本里很常见，能工作只是因为符号链接；如果 `/var/run` 不存在（精简镜像）或 `/run` 不可写，就会失败。

`systemd-tmpfiles` 决定 `/tmp` 与 `/var/tmp` 的清理周期。Ubuntu 的 `/usr/lib/tmpfiles.d/tmp.conf` 默认清理 `/tmp` 中 10 天未访问的文件，`/var/tmp` 是 30 天。**「临时」不等于「本次进程结束就删」**，也不等于「安全」。长任务把中间结果放 `/tmp`，跑到第 11 天可能被清掉；正确位置是任务自己的工作目录或 `/var/tmp` 下的专用子目录。

::: errata 常见误解
1. **「`/usr/local` 与 `/opt` 是一回事」**——`/usr/local` 是**前缀**，遵循 FHS 的 `bin`/`lib`/`share`/`include` 结构；`/opt` 是**整包目录**，一个软件一个子目录，适合自带依赖、不遵循 FHS 的商业软件。
2. **「装到 `/opt/app/bin` 就会自动进 `$PATH`」**——不会；需要显式加，或用 `update-alternatives` 管理多版本。
3. **「`/usr/local/bin` 一定优先」**——优先级由 `$PATH` 顺序决定；常见发行版把它排在前面，但脚本改了 `$PATH` 就不一定。用 `type -a cmd` 看全部候选。
4. **「主机配置放 `/usr/local/etc` 也能跨升级保留」**——在只读 `/usr` 或容器镜像里根本写不进去，镜像重建也会覆盖；主机配置应放 `/etc`，由配置管理负责合并。
:::

### 0.3.9 小结

FHS 的边界不是目录名，而是可变性与写入者：`/usr` 随版本替换，`/etc` 跨升级合并，`/var` 保存服务状态，`/run` 只活一次启动。把文件放错层，故障常在升级、容器重建或只读根上才出现。如果只记住一件事，那就是：先问这条数据能不能重建、谁负责写，再决定它进 `/etc`、`/var`、`/run` 还是 `/usr`。

## 0.3.10 路径解析：从字符串到 dentry {#sec-0.3.10}

这一节回答：`open("/srv/data/report.csv")` 把一串字节交给内核后，内核怎样一段一段找到 inode，并在中途处理符号链接与挂载点？

::: preview 先抓住一件事
路径不是一次性查表，而是从根或 cwd 开始逐段解析；每一段先查目录项缓存（dentry cache），未命中再让文件系统读目录。dentry 是内存里的「父目录 + 名字 → inode」缓存，不是磁盘上的目录本身。
:::

`open("/srv/data/report.csv")` 传进去的是一串字节，内核要把它变成 `struct path { vfsmount *, dentry * }`：前者标记这次挂载，后者标记路径上的目录项。这个过程叫**路径解析**（path resolution），由 `fs/namei.c` 的 `link_path_walk()`、`walk_component()`、`step_into()` 完成。理解它，才能解释 `..`、末尾斜杠、符号链接上限和 `openat2` 的安全选项。

每解析一段，内核先在**目录项缓存**（dentry cache）里找「父目录 + 名字」对应的 dentry。命中就不读磁盘；未命中才调用具体文件系统的 `lookup`，从目录数据块里读出「名字 → inode 号」，再取 inode。dentry 是纯内存结构，带引用计数，`dcache` 满时按 LRU 回收。`/proc/sys/vm/vfs_cache_pressure` 影响回收倾向。

::: note 非科班补一层：dentry 是目录项的缓存
磁盘上的目录是一张「名字 → inode 号」的表。内核给查过的每一项在内存里建一个 dentry，记住「哪个父目录下的哪个名字指向哪个 inode」。下次再走同一段路径先查缓存，命中就不读磁盘。dentry 不持久化，内存紧张时会被回收，需要时再按路径重建。
:::

<pre class="layout">
用户态字符串 "/srv/data/report.csv"
        │
        ▼
link_path_walk()
  ├─ 取根或 cwd 的 struct path
  ├─ 逐段 walk_component()
  │    ├─ dcache 命中 → dentry
  │    ├─ 未命中 → 文件系统 lookup() → inode
  │    ├─ 是挂载点？→ follow_mount() 换 vfsmount
  │    └─ 是符号链接？→ pick_link() 取目标，重新解析（全路径累计最多 40 次）
  └─ 最后一段按 flags 决定是否跟随（O_NOFOLLOW / LOOKUP_FOLLOW）
        │
        ▼
struct path { vfsmount, dentry } → inode → address_space → 页缓存
</pre>

读图的重点是：**符号链接在解析过程中被替换，不是打开后的重定向**。`open("link")` 得到的是目标文件的 inode；`lstat("link")` 因为 `AT_SYMLINK_NOFOLLOW` 停在链接本身。`O_NOFOLLOW` 只对最后一段生效，中间段的符号链接仍会被跟随；要禁止所有段，用 `openat2()` 的 `RESOLVE_NO_SYMLINKS`。

几个硬边界：

| 边界 | 值/行为 | 失败 |
|:--|:--|:--|
| 整个路径长度 | `PATH_MAX` 4096 字节（含结尾 NUL） | `ENAMETOOLONG` |
| 单个名字长度 | `NAME_MAX` 255 字节 | `ENAMETOOLONG` |
| 符号链接嵌套 | 整条路径累计 40 次（`MAXSYMLINKS`） | `ELOOP` |
| 中间段不是目录 | 例如 `/etc/passwd/x` | `ENOTDIR` |
| 末尾斜杠指向非目录 | `open("file/")` | `ENOTDIR` |
| 悬空符号链接 | `open("dangling")` | `ENOENT` |
| 无权限穿过目录 | 缺少目录 `x` | `EACCES` |
| `..` 到达挂载根 | 回到挂载点所在的父目录 | 正常 |

`..` 的语义容易被误解。内核解析 `..` 时，如果当前 dentry 是某个挂载点的根，它会回到**挂载点所在的父目录**，而不是被挂载文件系统里的父目录。如果已经在全局根 `/`，`..` 仍是 `/`。这与「`cd ..` 一定上一层」的直觉不同，尤其在 `chroot`、mount namespace（挂载命名空间：一组进程看到的那棵挂载树）、容器里。

挂载点让 `..` 更反直觉：`/proc` 是一个独立挂载，`cd /proc && cd ..` 回到 `/`，而不是「proc 文件系统的上一层」。内核在挂载根上处理 `..` 时，回到的是挂载点所在的父目录；在容器里，每个 mount namespace 有自己的挂载树，同一个 `..` 在容器内外可能落到不同地方。

`cwd` 是 `struct fs_struct` 里的一个 `struct path`，持有 dentry 与 vfsmount 的引用。`chdir()` 改变它，`fchdir()` 从 fd 恢复。因为它持有引用，**删掉当前目录后进程仍然停在那个已删除的 inode 上**：

```bash
mkdir /tmp/gone && cd /tmp/gone
rmdir /tmp/gone
pwd                  # /tmp/gone（逻辑路径仍记得）
pwd -P               # 可能报错或显示 /tmp/gone (deleted)
ls                   # 仍能列出已删除目录的内容（如果有）
```

`pwd` 默认打印 `$PWD`，它由 Shell 维护，可能包含符号链接；`pwd -P` 调 `getcwd()`，由内核从 cwd 逐级向上拼出真实路径。脚本里判断「两个路径是否同一目录」，不要比较字符串，比较 `stat -c %d:%i` 或 `[[ a -ef b ]]`。

`cd` 是 Shell 内建，除了 `chdir()` 还维护 `$PWD`、`$OLDPWD` 和目录栈：

```bash
cd /srv/app
cd -                 # 回到上一个目录并打印
pushd /var/log       # 压栈
dirs -v              # 看栈
popd                 # 弹栈
CDPATH=/srv:/var/www cd app   # 按 CDPATH 搜索，脚本里不要用
```

脚本里更稳的写法是显式绝对路径，并检查 `cd` 是否成功：

```bash
cd -- "$workdir" || { printf 'cannot cd to %s\n' "$workdir" >&2; exit 1; }
```

`cd` 失败后继续执行，后续相对路径会落在错误目录，这是「脚本删错目录」的常见起点。

`PATH` 的查找不在内核里。`execvp()` 按 `PATH` 逐项拼路径，`execve()` 只接受一个确定的路径。`PATH` 中的空项表示当前目录（等价于 `.`），这是安全风险；`type -a cmd` 能看到所有候选，`command -v cmd` 只看第一个。修改 `PATH` 后 `hash -r` 清掉 Shell 的命令哈希缓存。

末尾斜杠、`//`、空段、`.` 段在不同系统上有细微差异。POSIX 允许实现把 `//` 解释为实现定义的特殊路径；Linux 把连续斜杠当单个斜杠。`a//b`、`a/./b` 都等价于 `a/b`。脚本里不要依赖这些形式做「路径规范化」，用 `realpath -m`（不要求存在）或 `readlink -f`。

::: def 定义 0.3.2 · `openat2` 的解析约束 {#def-0.3.2}
`openat2(dirfd, path, how, size)`（Linux 5.6 起）在 `openat` 基础上增加 `struct open_how.resolve`，用位掩码限制路径解析：`RESOLVE_NO_XDEV` 禁止跨挂载点，`RESOLVE_NO_MAGICLINKS` 禁止 `/proc/self/fd` 这类魔法链接，`RESOLVE_NO_SYMLINKS` 禁止所有符号链接，`RESOLVE_BENEATH` 禁止 `..` 逃出 `dirfd`，`RESOLVE_IN_ROOT` 把 `dirfd` 当根。它是「安全打开用户提供的路径」的现代接口。
:::

TOCTOU（time-of-check to time-of-use）是路径操作的经典漏洞：先用 `stat` 检查，再 `open`，两步之间攻击者可以把路径换成符号链接。修复不是「检查得更快」，而是**把检查与使用合并到同一个 fd 上**：

```bash
# 不安全：检查与使用之间路径可能被替换
[[ -f $path ]] && cat "$path"

# 较安全：打开后对 fd 做 fstat，后续只用 fd
exec {fd}<"$path" || exit 1
[[ -f /proc/self/fd/$fd ]] || exit 1
cat <&"$fd"
exec {fd}<&-
```

C 里对应 `open(O_NOFOLLOW)` + `fstat` + `fchmod`/`fchown`，需要完整路径控制时用 `openat2` 的 `RESOLVE_BENEATH`。这一节只需要记住：**路径字符串在解析完成前都可能变；fd 一旦打开就稳定**。

::: errata 常见误解
1. **「dentry 就是磁盘上的目录」**——磁盘目录是数据块里的「名字 → inode 号」表；dentry 是内核为查过的目录项建的内存缓存，带引用计数，可以被回收。`ls -i` 看的是目录表与 inode，不是 dentry。
2. **「`..` 永远回到物理父目录」**——在挂载根上，`..` 回到挂载点所在的父目录；经过符号链接时，逻辑 `..` 与物理 `..` 还可能不同。`cd -P` 与 `namei -l` 才能看清实际落点。
3. **「`O_NOFOLLOW` 能禁止整条路径的符号链接」**——它只对最后一段生效，中间段仍会跟随；要禁止所有段，用 `openat2` 的 `RESOLVE_NO_SYMLINKS`，要限制在某个目录下再加 `RESOLVE_BENEATH`。
:::

### 0.3.10 小结

路径解析从根或 cwd 出发，逐段查 dcache，未命中再让文件系统 `lookup`；每一段都可能遇到挂载点或符号链接。`..`、末尾斜杠、`O_NOFOLLOW` 的边界，都来自这趟逐段行走。如果只记住一件事，那就是：路径在解析完成前都可能变，打开后的 fd 才是稳定对象。

::: method 即时自测 · 0.3.10
**Q1（记忆）** dentry 存在内存还是磁盘？它缓存的是什么？缓存未命中时内核做什么？

**Q2（辨析）** 对同一个符号链接，`open("link")` 与 `lstat("link")` 分别作用在谁身上？`O_NOFOLLOW` 与 `RESOLVE_NO_SYMLINKS` 的范围差在哪？

**Q3（应用）** 服务要打开用户提供的、位于 `/srv/data` 下的相对路径，要求不能借符号链接或 `..` 逃出该目录，也不能有 TOCTOU 窗口。写出调用思路与关键 flag。

::: sol 答案
**A1** dentry 在内存里，是「父目录 + 名字 → inode」的目录项缓存；未命中时内核调用具体文件系统的 `lookup`，从目录数据块读出 inode 号，再建立 dentry。
**A2** `open("link")` 跟随链接，作用在目标 inode 上；`lstat("link")` 不跟随，作用在链接本身。`O_NOFOLLOW` 只约束最后一段；`RESOLVE_NO_SYMLINKS` 约束整条路径的所有段。
**A3** 先 `open("/srv/data", O_PATH | O_DIRECTORY)` 拿 dirfd，再用 `openat2(dirfd, user_path, ...)`，`resolve` 设 `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS`（需要时加 `RESOLVE_NO_XDEV`）；打开后只对 fd 做 `fstat`/读写，不再按路径二次打开。
:::
:::

## 0.3.11 `ls -l` 与 `stat`：字段级拆解 {#sec-0.3.11}

这一节回答：`ls -l` 那一行里每个字段各在说什么？`stat` 多给的 inode、块数和三个时间由谁维护，改一个动作会动到哪一个？

::: preview 先抓住一件事
`ls -l` 是 `stat` 结果的摘要：同一张档案卡里的字段，被 `ls` 挑了几栏显示。排障时先分清一个数字是「字节数」「块数」还是「名字个数」，再问它是谁、在什么时候写进去的。
:::

真正排障时不能只看这七列，要看原始字段，尤其是 `st_blocks`、`st_dev`、`st_ino`、`st_nlink` 和四个时间。

| 列 | `ls` 选项 | `stat` 字段 | 易错点 |
|:--|:--|:--|:--|
| 类型+权限 | 默认 | `st_mode` | 特殊位显示为 `s/S/t/T` |
| 链接数 | 默认 | `st_nlink` | 目录的链接数含 `.` 与子目录的 `..` |
| 属主 | `-n` 显示 UID | `st_uid` | 名字来自 NSS，可能查不到 |
| 属组 | `-n` 显示 GID | `st_gid` | 同上 |
| 大小 | `-h` 人性化 | `st_size` | 目录是目录块大小；设备是主次设备号 |
| 时间 | `--time-style` | `st_mtim` 等 | 默认 mtime，超过六个月显示年份 |
| 名字 | `-Q` 加引号 | — | 符号链接追加 `-> target` |
| 块数 | `-s` | `st_blocks` | `st_blocks` 单位 512 字节，`ls -s` 默认按 1 KiB 块显示；稀疏文件远小于 `st_size` |
| inode | `-i` | `st_ino` | 同一文件系统内唯一 |

把这一行读成七个问题，每个字段就都有主人了：

- **mode** 回答「这是什么、谁能读/写/执行」。它由内核在 `open(O_CREAT)`、`mkdir`、`chmod` 时写进 inode，特殊位显示成 `s/S/t/T`。
- **链接数** 回答「还有几个名字指向这张档案卡」。`ln` 加一，`unlink` 减一；目录还额外算上 `.` 和每个子目录的 `..`。
- **属主 / 属组** 回答「这份数据算谁的」。`chown`、`chgrp` 改的是 inode 里的两个数字，`ls` 再拿数字去 NSS 里换成人名。
- **大小** 回答「文件有多少字节」。写数据、`truncate` 会改它；目录的这个数是目录项块的大小，符号链接的是目标路径长度。
- **mtime / atime / ctime** 回答「最后一次写内容、读内容、改元数据是什么时候」。三个时间都在 inode 里，更新时机见下面的表。

这些字段都住在 inode 里；文件名不在 inode 里，而在目录表中。所以 `ls` 必须同时读目录表和 inode，才能拼出你看到的那一行。

::: note 非科班补一层：inode 是档案卡，字段各有维护者
mode、链接数、属主、大小、三个时间都写在 inode 这张档案卡上，由内核在对应的系统调用里更新；名字只写在目录表里。`stat` 做的事是把整张卡原样打印出来，`ls` 只挑了其中几栏。同一个 inode 可以有多个名字，改名不会碰卡里的内容。
:::

`stat` 的格式化输出比 `ls` 精确，适合脚本：

| 格式 | 含义 | 例 |
|:--|:--|:--|
| `%A` | 人类可读权限 | `-rw-r--r--` |
| `%a` | 八进制权限 | `644` |
| `%f` | 原始 mode 十六进制 | `81a4` |
| `%F` | 文件类型描述 | `regular file` |
| `%s` | 表观大小（字节） | `6` |
| `%b` | 分配的 512 字节块数 | `8` |
| `%B` | `%b` 的单位（512） | `512` |
| `%o` | 优选 I/O 块大小 | `4096` |
| `%i` | inode 号 | `131073` |
| `%h` | 硬链接数 | `2` |
| `%d` | 设备号（十进制） | `66305` |
| `%D` | 设备号（十六进制） | `10301` |
| `%u/%U` | UID/用户名 | `1000/wang` |
| `%g/%G` | GID/组名 | `1000/wang` |
| `%t/%T` | 设备主/次号（十六进制） | `1/3` |
| `%x/%y/%z` | atime/mtime/ctime | `2024-10-17 10:31:00` |
| `%w/%W` | 出生时间/epoch | `-` 表示不支持 |
| `%n` | 文件名 | `a.txt` |

```bash
stat -c 'path=%n type=%F mode=%A(%a) inode=%i links=%h size=%s blocks=%b*%B dev=%d uid=%u gid=%g' /etc/passwd
# path=/etc/passwd type=regular file mode=-rw-r--r--(644) inode=... links=1 size=... blocks=8*512 dev=... uid=0 gid=0
```

`struct stat` 的字段顺序与类型（Linux x86-64，`man 2 stat`）：

| 字段 | 类型 | 含义 |
|:--|:--|:--|
| `st_dev` | `dev_t` | 所在文件系统设备号 |
| `st_ino` | `ino_t` | inode 号 |
| `st_nlink` | `nlink_t` | 硬链接数 |
| `st_mode` | `mode_t` | 类型 + 12 位权限 |
| `st_uid/st_gid` | `uid_t/gid_t` | 属主/属组 |
| `st_rdev` | `dev_t` | 设备节点的主次号（普通文件无意义） |
| `st_size` | `off_t` | 表观大小 |
| `st_blksize` | `blksize_t` | 优选 I/O 块大小 |
| `st_blocks` | `blkcnt_t` | 分配的 512 字节块数 |
| `st_atim/st_mtim/st_ctim` | `timespec` | 访问/修改/元数据变更 |

`st_blocks` 是「实际分配」而不是「表观大小」。普通文件写 1 字节通常也会分配一个 4 KiB 块，`st_blocks` 是 8；稀疏文件写 1 字节再 `truncate` 到 1 GiB，`st_size` 是 1 GiB，`st_blocks` 仍可能只有 8。`ls -l` 显示前者，`du` 与 `ls -s` 显示后者。

四个时间要分开：

| 时间 | 何时更新 | 谁会用 |
|:--|:--|:--|
| atime | 读取文件内容（受挂载策略限制） | 备份、缓存淘汰、取证 |
| mtime | 写入文件内容 | `make`、`rsync`、增量备份 |
| ctime | inode 元数据变化（权限、属主、链接、mtime 本身） | 审计、入侵检测 |
| btime | 创建时间（ext4 `crtime`、XFS、Btrfs） | 取证；`stat` 需 `%w`/`statx` |

`ctime` 不是「创建时间」，也不能被用户直接设置。`chmod`、`chown`、`ln`、`mv`（同一文件系统）都会更新 ctime；`touch` 改 mtime 也会顺带更新 ctime。备份工具用 mtime 判断内容是否变，用 ctime 判断元数据是否变；只比 mtime 会漏掉「内容没变但权限被改」的情况。

atime 的更新策略由挂载选项决定：

| 选项 | 行为 | 代价 |
|:--|:--|:--|
| `strictatime` | 每次读都更新 | 读放大，元数据写多 |
| `relatime`（默认） | atime 旧于 mtime/ctime，或超过 24 小时才更新 | 兼顾正确性与性能 |
| `noatime` | 完全不更新 | 依赖 atime 的工具会失真 |
| `lazytime` | 只在内存标记，定期/卸载时写回 | 崩溃可能丢 atime 更新 |

```bash
findmnt -T /var -o TARGET,OPTIONS
# 临时改回严格 atime（需要 root；生产慎用）
sudo mount -o remount,strictatime /var
```

`statx()` 是 `stat` 的现代替代，能一次取回 btime、挂载 ID、属性位、DIO 对齐等信息：

```c
struct statx stx;
if (statx(AT_FDCWD, path, AT_STATX_SYNC_AS_STAT, STATX_BASIC_STATS | STATX_BTIME, &stx) < 0) {
    perror("statx");
    return 1;
}
printf("ino=%llu size=%llu btime=%lld.%09u attrs=0x%llx\n",
       (unsigned long long)stx.stx_ino,
       (unsigned long long)stx.stx_size,
       (long long)stx.stx_btime.tv_sec, stx.stx_btime.tv_nsec,
       (unsigned long long)stx.stx_attributes);
```

`stx_mask` 告诉你哪些字段有效：文件系统不支持 btime 时，`STATX_BTIME` 位不会置位，`stx_btime` 全 0。不要用「btime 为 0」判断文件创建于 1970 年。

::: errata 关于 stat 字段的三个误解
1. **「`st_size` 就是磁盘占用」**——它是表观字节数；`st_blocks` 才是实际分配的 512 字节块数。稀疏文件可以 `st_size` 1 GiB、`st_blocks` 只有 8。
2. **「`ls -l` 显示的时间是创建时间」**——默认是 mtime；`ls -lc` 才显示 ctime，`ls -lu` 显示 atime。创建时间要看 `stat %w` 的 btime，且不是所有文件系统都记录。
3. **「`%d` 是 inode 号」**——`%d` 是设备号，`%i` 才是 inode 号。判断两个路径是否同一文件要比较 `设备号:inode 号`，只比 `%i` 会在跨文件系统时误判。
:::

### 0.3.11 小结

`ls -l` 的七列是 inode 字段的摘要，`stat` 给全字段：mode、链接数、属主属组、表观大小、三个时间、块数和 inode 号。size 数字节，blocks 数块，nlink 数名字；mtime 跟内容走，ctime 跟元数据走，atime 跟读取走。如果只记住一件事，那就是：先分清眼前这个数字是字节、块还是名字个数，再问它是谁在什么时候写进去的。

## 0.3.12 文件类型、设备节点与虚拟文件 {#sec-0.3.12}

这一节回答：`ls -l` 的第一个字符有哪几种？`/dev/null`、`/proc/cpuinfo` 这些「文件」和磁盘上的普通文件差在哪，能不能 `cat`、能不能备份？

::: preview 先抓住一件事
Linux 把能读能写的东西都套上文件接口，但七种类型背后是七套不同的实现：普通文件落在数据块，设备节点落到驱动，`/proc`、`/sys` 落在内核数据结构。类型字符和 `stat -c %F` 是第一道分诊。
:::

`ls -l` 第一个字符是文件类型，`stat -c %F` 给文字描述。Linux 有七种：

| 字符 | 类型 | 创建方式 | 读写的语义 |
|:--|:--|:--|:--|
| `-` | 普通文件 | `open(O_CREAT)` | 字节流；可 `mmap` |
| `d` | 目录 | `mkdir` | 目录项表；`getdents` 读 |
| `l` | 符号链接 | `symlink` | 内容是目标路径；`readlink` 读 |
| `c` | 字符设备 | `mknod`（需 `CAP_MKNOD`） | 走驱动 `read/write/ioctl` |
| `b` | 块设备 | `mknod` | 走块层；通常挂载后访问 |
| `p` | FIFO | `mkfifo` | 管道语义；`open` 可能阻塞 |
| `s` | Unix socket | `bind(AF_UNIX)` | `socket` API；`ss -xl` 查看 |

七种类型可以按「数据在哪」分成三组。普通文件、目录、符号链接的数据在磁盘上，只是组织方式不同：普通文件是字节流，目录是「名字 → inode 号」的表，符号链接是一串目标路径。字符设备和块设备本身不存数据，它们是通往驱动的门牌号：你写 `/dev/null`，内核调用的是 null 驱动。FIFO 和 socket 是进程间通信的两个入口：FIFO 像一根单向水管，socket 像一条双向电话线。看到类型字符，先问它属于哪一组，再决定用什么命令去读。

::: note 非科班补一层：设备号是给驱动的门牌
设备节点里存的不是数据，而是一对数字：主设备号（major）选驱动，次设备号（minor）选这个驱动下的哪一台设备。`ls -l /dev/null` 里的 `1, 3` 就是这两个数，`stat -c %t:%T` 用十六进制再给一遍。`mknod` 只是造一块门牌，真正干活的是内核里已经注册的驱动。
:::

`/dev` 下的设备节点由 `devtmpfs` 或 `systemd-udevd` 维护，设备插拔时自动增删。`mknod` 手工建设备节点需要 root 与 `CAP_MKNOD`，容器默认没有这个 capability，所以容器里不能随意 `mknod`。

几个特殊设备的边界值得记住：

```bash
ls -l /dev/null /dev/zero /dev/full /dev/random /dev/urandom
# crw-rw-rw- 1 root root 1, 3 ... /dev/null
# crw-rw-rw- 1 root root 1, 5 ... /dev/zero
# crw-rw-rw- 1 root root 1, 7 ... /dev/full
```

| 设备 | 读 | 写 | 用途 |
|:--|:--|:--|:--|
| `/dev/null` | 立即 EOF | 丢弃，返回成功 | 丢弃输出 |
| `/dev/zero` | 无限零字节 | 丢弃 | 初始化、`dd` |
| `/dev/full` | 无限零字节 | 返回 `ENOSPC` | 测试写失败路径 |
| `/dev/random` | 熵不足时阻塞（现代内核用 CRNG 初始化后不阻塞） | 混合熵池 | 旧脚本的随机源 |
| `/dev/urandom` | 不阻塞 | 混合熵池 | 现代推荐的随机源 |
| `/dev/tty` | 当前控制终端 | 同上 | 脚本向用户提问 |
| `/dev/fd/N` | 复制 fd N | 同上 | 进程替换、`/dev/stdin` |

`/dev/stdin`、`/dev/stdout`、`/dev/stderr` 在 Linux 上是指向 `/proc/self/fd/0`、`1`、`2` 的符号链接。`cmd 2>/dev/stdout` 与 `cmd 2>&1` 在多数情况下等价，但**不是同一个操作**：`2>&1` 复制当前 fd 1 的打开文件描述；`2>/dev/stdout` 重新打开 `/proc/self/fd/1` 指向的目标。如果 fd 1 是一个带 `O_APPEND` 的文件，重新打开会继承 flags：`/proc/self/fd/N` 的 `open` 会复制原 fd 的 flags（除 `O_CLOEXEC` 等），但偏移是否共享取决于实现。需要精确复制时用 `2>&1`，不要用 `/dev/stdout`。

FIFO 的 `open` 语义：

- 以读打开、没有写者：阻塞，直到有写者；
- 以写打开、没有读者：阻塞，直到有读者；
- `O_NONBLOCK` 读：立即成功，读不到返回 `EAGAIN`；
- `O_NONBLOCK` 写、没有读者：返回 `ENXIO`；
- 读写都结束后，FIFO 里的数据不持久，下次打开是空的。

```bash
mkfifo /tmp/demo.fifo
# 终端 A：阻塞等待
cat /tmp/demo.fifo
# 终端 B：
printf 'hello\n' > /tmp/demo.fifo
```

Unix socket 文件在 `ls -l` 里是 `s`，不能用 `cat` 读，要用 `socket()`/`connect()`。`ss -xl` 列出现有 socket，`ss -xlp` 带进程。删除 socket 文件不会关闭已建立的连接，只会让新连接找不到路径。

`/proc` 与 `/sys` 是虚拟文件系统，`stat` 显示的大小通常是 0，但 `cat` 能读出内容。它们的读写不是普通文件语义：`/proc/sys/...` 写入会触发内核处理函数，`/sys/...` 通常一个文件一个值，写入格式由驱动定义。不要对它们做 `cp -a`、`tar`、`rsync` 的常规备份；备份工具应排除 `/proc`、`/sys`、`/dev`、`/run`。

把 `/proc` 想成内核在内存里开的一排窗口：目录项是现造的，内容在 `read` 时现拼，所以两次读到的 `cpuinfo` 可能不同。`/sys` 更规整，通常一个文件一个值，写进去就调用对应的驱动函数。窗口后面没有磁盘块，`stat` 的 size 只是占位，不能拿来估算内容多少。

`file` 命令按魔数判断类型，不只看扩展名：

```bash
file /bin/ls /etc/passwd /dev/null /tmp/demo.fifo
# /bin/ls: ELF 64-bit LSB pie executable, x86-64, ...
# /etc/passwd: ASCII text
# /dev/null: character special (1/3)
# /tmp/demo.fifo: fifo (named pipe)
```

脚本里判断类型用 `test` 而不是 `file`：`-f` 普通文件、`-d` 目录、`-L` 符号链接、`-p` FIFO、`-S` socket、`-b` 块设备、`-c` 字符设备、`-s` 非空。`test` 会跟随符号链接（除 `-L`/`-h`），要判断链接本身用 `-L`。

::: errata 关于文件类型的三个误解
1. **「扩展名决定类型」**——`file` 看文件头的魔数，不看名字。`photo.jpg` 可以是纯文本，`script.txt` 加上 `chmod +x` 也不会变成可执行程序。
2. **「`/dev/null` 是一个空文件」**——它是字符设备，写入直接丢弃、读取立即 EOF，不占任何数据块；删了它也不会释放空间。
3. **「`/proc` 里的文件可以照常备份」**——内容是内核现场拼出来的，大小常为 0，复制下来只是某一刻的快照；备份要排除 `/proc`、`/sys`、`/dev`、`/run`。
:::

### 0.3.12 小结

`ls -l` 的第一个字符和 `stat -c %F` 回答「这是什么类型」；七种类型按数据在哪分三组：磁盘上的普通文件、目录、链接，通往驱动的设备节点，以及进程间通信的 FIFO 与 socket。`/proc`、`/sys` 是内核窗口，不是磁盘文件。如果只记住一件事，那就是：先看类型，再决定能不能 `cat`、能不能备份。

::: method 即时自测 · 0.3.12
**Q1（记忆）** 普通文件、目录、符号链接、字符设备、块设备、FIFO、socket 的类型字符各是什么？`ls -l /dev/null` 里的 `1, 3` 是什么？

**Q2（辨析）** `cat /dev/null`、`cat /dev/zero`、`cat /proc/cpuinfo` 分别会发生什么？为什么 `stat` 报 `/proc/cpuinfo` 的大小是 0，却仍能读出很多内容？

**Q3（应用）** 备份脚本要从 `/` 开始打包，至少应排除哪几个虚拟目录？给出 `tar` 的排除写法，并说明为什么不能靠 `--exclude` 排除 `/dev/null` 这种单个节点。

::: sol 答案
**A1** 依次是 `-`、`d`、`l`、`c`、`b`、`p`、`s`。`1, 3` 是主设备号 1、次设备号 3：主设备号选驱动，次设备号选该驱动下的设备。
**A2** `cat /dev/null` 立即结束；`cat /dev/zero` 会不断输出零字节，需要中断；`cat /proc/cpuinfo` 打印内核现场拼出的 CPU 信息。`/proc` 文件没有磁盘块，size 只是占位，内容在 `read` 时才生成。
**A3** 排除 `/proc`、`/sys`、`/dev`、`/run`（以及 `/tmp` 视需要）。写法如 `tar -czf backup.tgz --exclude=/proc --exclude=/sys --exclude=/dev --exclude=/run /`。`/dev` 下的节点由内核和 udev 重建，单独排除一个 `/dev/null` 既挡不住其他节点，也会让恢复出来的系统缺设备。

## 0.3.13 inode、稀疏文件与磁盘占用 {#sec-0.3.13}

这一节回答：一个文件没有名字时还剩下什么？为什么 `truncate -s 1G` 造出的文件 `ls` 有 1 GiB、`du` 却几乎是 0？

::: preview 先抓住一件事
inode 存的是「这个文件是什么、数据块在哪」，不存名字；名字在目录表里。稀疏文件把「文件有多长」和「实际占了哪些块」分开，所以逻辑大小可以远大于磁盘占用。
:::

inode 是文件系统里「除名字和内容之外的一切」：类型、权限、属主、大小、块指针、时间、链接数。目录项只存「名字 → inode 号」。同一个 inode 可以有多个名字（硬链接），一个名字删除后 inode 仍可能被进程持有。

ext4 的 inode 是固定大小的表项（默认 256 字节），格式化时确定总量。`df -i` 看 inode 使用率；大量小文件会把 inode 用完，此时即使还有空间也不能创建新文件，报 `No space left on device`。`mke2fs -N` 可以在格式化时调整 inode 数量，事后扩容困难。

把 inode 想成一张档案卡：卡上记这个文件的身份（类型、权限、属主）、长度、三个时间、链接数，以及「数据块放在哪」的指针。真正的字节在数据块里，名字在目录表里；卡的数量在格式化时就定好，所以「磁盘满」有两种：块用完了，或者卡用完了。

```bash
df -i /var
# Filesystem      Inodes  IUsed   IFree IUse% Mounted on
# /dev/nvme0n1p2 31227904 812345 30415559    3% /
```

`st_nlink` 对普通文件是硬链接数；对目录是 `2 + 子目录数`（`.` 和父目录里的 `..` 各算一个，每个子目录的 `..` 再算一个）。所以一个空目录的链接数是 2，有一个子目录就变 3。`find . -type d -links 2` 能找出「没有子目录的目录」。

稀疏文件是「表观大小很大、实际分配很小」的文件。创建方式：

```bash
# 1. truncate：只改 inode 的 size，不分配块
truncate -s 1G /tmp/sparse.img

# 2. dd seek：跳过前面的块
dd if=/dev/zero of=/tmp/sparse.img bs=1 count=1 seek=1073741823

# 3. fallocate：分配但不写（ext4 的 unwritten extent）
fallocate -l 1G /tmp/allocated.img
```

对比：

```bash
ls -l  /tmp/sparse.img /tmp/allocated.img
ls -ls /tmp/sparse.img /tmp/allocated.img
du -h  /tmp/sparse.img /tmp/allocated.img
du -h --apparent-size /tmp/sparse.img
stat -c '%n size=%s blocks=%b' /tmp/sparse.img /tmp/allocated.img
```

预期：`sparse.img` 的 `st_size` 是 1 GiB，`st_blocks` 很小（可能 0 或 8），`du` 显示几 KiB；`allocated.img` 的 `st_blocks` 接近 1 GiB/512。`fallocate` 分配的是 unwritten extent，读出来是零，但块已经预留，不会在写入时因空间不足失败。`truncate` 不预留，写入时可能 `ENOSPC`。

`du` 默认数块，`du --apparent-size` 数字节。前者回答「这块盘被它占了多少」，后者回答「文件看起来有多长」；稀疏文件、硬链接和 CoW 快照都会让两个数分叉。排查时两个都看，才知道差在哪一侧。

`SEEK_HOLE` 与 `SEEK_DATA` 让程序跳过空洞，只读实际数据：

```c
off_t data = lseek(fd, 0, SEEK_DATA);
off_t hole = lseek(fd, data, SEEK_HOLE);
```

`cp --sparse=always`、`tar --sparse`、`rsync -S` 会利用这些接口保留稀疏性。普通 `cp` 默认 `--sparse=auto`，源是稀疏且目标文件系统支持时才保留；`cp --sparse=never` 会把空洞写成真实的零块，文件可能从几 KiB 膨胀到 1 GiB。备份大镜像前先确认工具是否保留稀疏。

`du` 与 `df` 的口径不同，对不上是常态：

| 工具 | 统计对象 | 包含 | 不包含 |
|:--|:--|:--|:--|
| `du` | 目录下可见文件的分配块 | 硬链接去重（默认） | 已删除但打开的文件、保留块、快照 |
| `df` | 文件系统块 | 元数据、保留块、已删除打开文件 | 未被任何目录引用的 orphan（通常已回收） |
| `ls -l` | 表观大小 | 空洞 | 实际分配 |
| `ls -s` | 分配块（1 KiB 单位） | 间接块 | 空洞 |

排查「`df` 满但 `du` 小」的顺序：

```bash
# 1. 确认分区与保留块
df -h /var; sudo tune2fs -l /dev/nvme0n1p2 | grep -i 'reserved block'
# 2. 找已删除但仍被打开的文件
sudo lsof +L1 2>/dev/null | sort -k7 -nr | head
# 3. 找隐藏的挂载（du -x 不会跨）
findmnt -R /var
# 4. 找大目录，逐层下钻
sudo du -x -h --max-depth=1 /var | sort -h | tail
# 5. 文件系统快照/CoW 占用（btrfs/zfs/lvm）
sudo btrfs filesystem du -s /var 2>/dev/null
```

`lsof +L1` 的输出里 `NLINK` 是 0，表示文件已被删除但仍有进程持有 fd。`/proc/PID/fd` 能看到符号链接指向 `... (deleted)`。解决方式是重启持有者、让它重新打开日志，或 `: > /proc/PID/fd/N` 截断（对追加写日志有效，对普通文件要小心偏移）。

CoW 文件系统（Btrfs、XFS reflink、ZFS、overlayfs）还有一层：`cp --reflink=always` 创建的是共享 extents，修改任一份才复制对应块。`du` 会把共享块算给每个文件，`btrfs filesystem du` 才会给出「独占/共享」的拆分。容器镜像的层也是同理：`docker ps -s` 的 `SIZE` 是读写层，镜像层共享。

::: errata 关于 inode 与占用的六个误解
1. **「删除文件一定释放空间」**——链接数为 0 且没有打开的 fd 才释放；`lsof +L1` 找残留。
2. **「`ls -l` 的大小就是磁盘占用」**——它是表观大小；`ls -s`/`stat %b` 才是分配块，稀疏文件差别巨大。
3. **「`du -sh` 等于 `df` 已用」**——`du` 只统计可见文件，且默认对硬链接去重；保留块、快照、已删除打开文件都不在 `du` 里。
4. **「inode 用完只影响大文件」**——恰恰相反，大量小文件先耗尽 inode；`df -i` 要看。
5. **「`fallocate` 与 `truncate` 等价」**——前者分配 unwritten extent（预留空间），后者只改 size（不预留）。
6. **「目录的链接数没有意义」**——它是 `2 + 子目录数`，可以用来快速判断目录是否有子目录，也是 `find -links` 的基础。
:::

### 0.3.13 小结

inode 是文件系统给每个文件建的档案卡，存元数据与数据块位置，不存名字；名字在目录表里。稀疏文件只改长度、不分配块，所以逻辑大小和磁盘占用可以差几个数量级：`du` 数块，`du --apparent-size` 数字节。如果只记住一件事，那就是：先问「你说的是文件有多长，还是它占了多少块」。

::: method 即时自测 · 0.3.13
**Q1（记忆）** inode 里存什么、不存什么？`df -i` 与 `df -h` 分别数的是什么？

**Q2（辨析）** 对同一路径先 `truncate -s 1G`、再删掉重来 `fallocate -l 1G`，两次的 `ls -l`、`du` 和「写入时会不会 `ENOSPC`」各有什么不同？

**Q3（应用）** 一个 1 GiB 的镜像备份后变成 1 GiB 实占，源文件原本只有几 MiB。最可能的原因是什么？写出检查命令和三种保留稀疏性的做法。

::: sol 答案
**A1** inode 存类型、权限、属主、大小、块指针、三个时间、链接数；不存文件名。`df -i` 数 inode 表项，`df -h` 数数据块。
**A2** `truncate` 只改 size，`ls -l` 都是 1 GiB，但 `du` 很小，写入时可能 `ENOSPC`；`fallocate` 预留 unwritten extent，`du` 接近 1 GiB，写入不会因空间不足失败。两者 `ls -l` 都报 1 GiB。
**A3** 备份工具把空洞写成了真实零块。先用 `ls -ls`、`du -h`、`du -h --apparent-size` 对比确认；保留稀疏用 `cp --sparse=always`、`rsync -S` 或 `tar --sparse`。
:::

## 0.3.14 find 的表达式全解：优先级、动作与边界 {#sec-0.3.14}

这一节回答：`find` 的一串条件按什么顺序求值？为什么 `-name '*.log' -o -name '*.tmp' -delete` 只删了一类？`-delete`、`-exec ... +` 各自隐含了什么？

::: preview 先抓住一件事
`find` 是表达式求值器：`!` 最紧，隐式 AND 次之，`-o` 最松；动作也是表达式的一部分，放在哪里就在哪里生效。先 `-print` 试运行，再换成 `-delete` 或 `-exec`。
:::

`find` 不是「按名字找文件」的命令，而是一个**表达式求值器**：从起点遍历目录树，对每个路径求一个布尔表达式，为真就执行动作。绝大多数误删、漏删、扫描缓慢，都源于没把「优先级」和「动作的副作用」算清楚。

::: def 定义 0.3.3 · find 表达式的语法 {#def-0.3.3}
`find` 的表达式由**测试**（test，如 `-name`、`-type`）、**动作**（action，如 `-print`、`-delete`、`-exec`）、**全局选项**（option，如 `-maxdepth`、`-xdev`）和**运算符**组成。运算优先级从高到低：`!`（否定）、`-a`（与，可省略）、`-o`（或）。括号用 `\(` `\)`。表达式从左到右求值，`-a`/`-o` 短路；没有动作时默认 `-print`。
:::

优先级用一张表记住：

| 写法 | 结合方式 | 例子 | 实际含义 |
|:--|:--|:--|:--|
| `! expr` | 最高 | `! -name '*.log'` | 不匹配 `.log` |
| `expr1 expr2` | `-a`，左结合 | `-type f -name '*.log'` | 普通文件且名字匹配 |
| `expr1 -o expr2` | 低于 `-a` | `-name '*.log' -o -name '*.tmp'` | 两种名字之一 |
| `\( ... \)` | 显式分组 | `\( -name '*.log' -o -name '*.tmp' \) -type f` | 先分组再与类型 |

没有括号时，`-type f -name '*.log' -o -name '*.tmp'` 等价于 `(-type f -a -name '*.log') -o (-name '*.tmp')`，会匹配**所有** `.tmp` 文件，包括目录。这是 find 最常见的逻辑错误。

::: note 非科班补一层：把 find 读成一串 if
`find` 对每个路径从左边开始求值：`!` 先算，接着是没写出来的 `-a`，最后才是 `-o`；`-a` 和 `-o` 都会短路，左边为假（AND）或为真（OR）就不再算右边。动作也是表达式的一项，位置决定它什么时候执行。读表达式时先按优先级补括号，再逐项翻译成 if，就不容易看错。
:::

`find` 的两类元素必须分清：

| 类别 | 例子 | 副作用 | 放在表达式中的位置 |
|:--|:--|:--|:--|
| 测试 | `-name`、`-type`、`-mtime`、`-size`、`-perm`、`-user` | 无 | 任意 |
| 动作 | `-print`、`-print0`、`-printf`、`-exec`、`-delete`、`-ls`、`-quit` | 有 | 通常放最后 |
| 全局选项 | `-maxdepth`、`-mindepth`、`-xdev`、`-follow`、`-L` | 影响遍历 | 放在所有测试之前 |

`-delete` 既是动作又隐含 `-depth`（后序遍历，先处理子项）。如果写成 `find . -delete -name '*.tmp'`，删除动作先执行，`-name` 根本来不及过滤；实际会删掉整棵树。**动作放在条件之后**，先用 `-print` 试跑，是唯一可靠的习惯。

### 按名字、路径与类型

| 测试 | 含义 | 边界 |
|:--|:--|:--|
| `-name '*.log'` | 匹配 basename，glob 语法 | 通配符由 find 解释，必须加引号 |
| `-iname` | 忽略大小写 | 受 locale 影响 |
| `-path './src/*'` | 匹配完整路径 | `*` 能跨 `/` |
| `-ipath` | 忽略大小写 | 同上 |
| `-regex` | 整路径正则 | 默认 Emacs 方言，`-regextype posix-extended` 可换 |
| `-type f` | 普通文件 | 可写 `-type f,d` 匹配多类 |
| `-xtype l` | 链接指向的类型（对悬空链接特殊） | 与 `-type` 的区别在是否跟随 |
| `-L` / `-H` / `-P` | 跟随所有/命令行/不跟随符号链接 | 默认 `-P` |
| `-empty` | 空文件或空目录 | 对普通文件是 size 0 |
| `-readable`/`-writable`/`-executable` | 当前用户可读/写/执行 | 按 `access(2)` 语义，受 ACL 影响 |

`-name` 只匹配路径最后一段，`-path` 匹配整条路径。要排除 `.git`：

```bash
find . -path ./.git -prune -o -type f -print
```

读法是：如果路径是 `./.git`，`-prune` 返回真且不下降，`-o` 短路，不执行后面的 `-print`；否则 `-prune` 为假，继续求值 `-type f -print`。`-prune` 只对目录有效，且不能与 `-delete` 同用（`-delete` 的 `-depth` 会让 prune 失效）。

### 按时间

| 测试 | 单位 | 语义 | 常见误用 |
|:--|:--|:--|:--|
| `-mtime n` | 24 小时 | 文件数据在 n×24h 前被修改 | `-mtime -1` 是「不到 24 小时」，不是「今天」 |
| `-mmin n` | 分钟 | 同上，精度更高 | 备份脚本用它找「刚变的」 |
| `-atime n` | 24 小时 | 访问时间 | 受 `relatime` 影响，不等于「最近读过」 |
| `-ctime n` | 24 小时 | inode 变更时间 | 不是创建时间 |
| `-newer ref` | — | mtime 晚于 ref | ref 必须是存在的文件 |
| `-newermt '2024-10-01'` | — | mtime 晚于给定时间 | GNU 扩展，BSD 不支持 |
| `-newerXY ref` | — | X=文件时间，Y=参照时间 | `-newerat`、`-newercm` 等组合 |
| `-used n` | 天 | atime 比 ctime 晚 n 天 | 少用 |
| `-daystart` | — | 从今天 00:00 起算 | 必须放在时间测试前 |

`-mtime n` 的取整规则是「(now - mtime) / 86400 向下取整后等于 n」，所以 `-mtime 0` 是过去 24 小时内，`-mtime 1` 是 24–48 小时前。要「今天」用 `-newermt "$(date +%F)"` 或 `-daystart -mtime 0`。删除 30 天前的日志用 `-mtime +30`，它表示「大于 30 个完整 24 小时」，边界比直觉晚一天。

```bash
# 最近 2 小时改过的配置
find /etc -xdev -type f -mmin -120 -print
# 2024-10-01 之后修改的文件
find /srv -xdev -type f -newermt '2024-10-01 00:00:00' -print
# 比参考文件新的文件
find . -type f -newer ./VERSION -print
```

### 按大小

`-size n[cwbkMG]` 的单位与取整是另一个坑：

| 单位 | 含义 | 取整 |
|:--|:--|:--|
| `c` | 字节 | 精确 |
| `w` | 2 字节字 | 向上取整 |
| `b` | 512 字节块 | 向上取整 |
| `k` | 1024 字节 | 向上取整 |
| `M` | 1024² 字节 | 向上取整 |
| `G` | 1024³ 字节 | 向上取整 |

「向上取整」意味着 `-size 1k` 匹配的是 1 到 1024 字节的文件（空文件是 0 个单位，不匹配），`-size -1k` 只匹配空文件。找「大于 100 MiB」用 `-size +100M`；找「恰好 0 字节」用 `-empty` 或 `-size 0`，不要用 `-size -1k` 猜。

```bash
# 大于 100 MiB 的普通文件，按大小降序
find /var -xdev -type f -size +100M -printf '%s\t%p\n' 2>/dev/null | sort -nr | head -20
# 0 字节文件
find /srv -xdev -type f -empty -print
```

### 按权限、属主与 inode

| 测试 | 含义 | 注意 |
|:--|:--|:--|
| `-perm 644` | 权限**恰好**等于 644 | 特殊位也必须一致 |
| `-perm -644` | 至少包含 644 的所有位 | 常用审计写法 |
| `-perm /222` | 任意一个写位被设置 | GNU 扩展；`+222` 已废弃 |
| `-perm -4000` | 至少包含 setuid | 找 setuid 程序 |
| `-user alice` / `-uid 1000` | 属主 | `-nouser` 找无主文件 |
| `-group dev` / `-gid 1000` | 属组 | `-nogroup` 找无组文件 |
| `-links n` | 硬链接数 | `-links +1` 找多名字文件 |
| `-inum n` | inode 号 | 配合 `ls -i` 定位 |
| `-samefile ref` | 与 ref 同一 inode | 比比较 inode 号更方便 |

`-perm` 的三种前缀必须记牢：无前缀是精确匹配，`-` 是「全部这些位都要有」，`/` 是「至少有一位」。`find / -perm -4000` 找 setuid；`find / -perm /6000` 找 setuid 或 setgid；`find / -perm 4755` 只找精确 4755。

### 动作：打印、执行、删除

| 动作 | 作用 | 边界 |
|:--|:--|:--|
| `-print` | 每行一个路径 | 文件名含换行时不可解析 |
| `-print0` | NUL 分隔 | 配 `xargs -0` 或 `while read -d ''` |
| `-printf` | 自定义格式 | GNU 扩展；字段见下表 |
| `-ls` | 类似 `ls -l` 的输出 | 格式不稳定，脚本不要解析 |
| `-exec cmd {} \;` | 每个文件执行一次 | 慢，但命令只收一个文件 |
| `-exec cmd {} +` | 批量传参 | `{}` 必须在 `+` 前且只能一次 |
| `-execdir cmd {} \;` | 在文件所在目录执行 | 更安全，`{}` 带 `./` 前缀 |
| `-delete` | 删除 | 隐含 `-depth`；先 `-print` 试跑 |
| `-quit` | 找到一个就退出 | 配合 `-print` 做存在性检查 |

`-printf` 的常用字段：

| 字段 | 含义 | 字段 | 含义 |
|:--|:--|:--|:--|
| `%p` | 完整路径 | `%f` | basename |
| `%h` | 目录部分 | `%P` | 去掉起点后的路径 |
| `%s` | 字节大小 | `%b` | 512 字节块数 |
| `%k` | 1 KiB 块数 | `%i` | inode 号 |
| `%n` | 硬链接数 | `%m` | 八进制权限 |
| `%M` | 符号权限 | `%u/%g` | 用户名/组名 |
| `%y` | 类型字符 | `%l` | 符号链接目标 |
| `%d` | 深度 | `%D` | 设备号 |
| `%T@` | mtime epoch | `%TY-%Tm-%Td` | mtime 日期 |
| `%A@` | atime epoch | `%C@` | ctime epoch |
| `%B` | 出生时间（GNU 4.3.3+） | `%F` | 文件系统类型 |

`-printf` 支持 `\n`、`\t`、`\0`、`\\`，宽度用 `%10s`。它比 `-exec stat` 少 fork 无数次，是大规模扫描的首选；但 BSD/macOS 的 find 没有 `-printf`。

`-exec ... +` 的批量语义：find 会把尽可能多的路径追加到命令末尾，直到接近 `ARG_MAX`；命令只执行少数几次。它比 `\;` 快一个数量级，但要求命令能接受多个参数，且 `{}` 必须出现在最后：

```bash
# 正确：{} 在最后，+ 结尾
find . -type f -name '*.tmp' -exec rm -f -- {} +

# 错误：{} 不在最后，find 会报 "missing argument to -exec"
find . -type f -exec cp {} /tmp/backup +
```

`-execdir` 在文件所在目录执行，`{}` 会展开成 `./name`，避免路径被解释成选项；它还会把当前目录加入 `PATH` 的前面（安全风险），所以命令要用绝对路径或 `command`。在不可信目录里，优先 `-execdir /bin/rm -f -- {} +`。

三个动作习惯值得固定下来：先用 `-print` 试运行，把输出存成文件抽样；`-delete` 隐含 `-depth`，只能放在所有条件之后；`-exec ... +` 批量传参，`{}` 必须放在末尾且只能出现一次。

::: errata 关于 find 表达式的三个误解
1. **「`-name` 能匹配整条路径」**——它只匹配最后一段文件名；要匹配路径用 `-path './src/*'`，`*` 在 `-path` 里可以跨 `/`。
2. **「`-o` 两侧会各执行一次动作」**——隐式 AND 比 `-o` 结合得紧，动作只跟最近的一支。`-name '*.log' -o -name '*.tmp' -delete` 只删 `.tmp`，要删两类得先加括号。
3. **「`-delete` 可以放在条件前面」**——动作按位置执行，放前面会对还没筛完的路径生效，等于删掉整棵树；先 `-print` 确认清单，再把 `-print` 换成 `-delete`。
:::

### 遍历控制与性能

| 选项 | 作用 | 注意 |
|:--|:--|:--|
| `-maxdepth n` | 最多下降 n 层 | 全局选项，放最前 |
| `-mindepth n` | 至少 n 层才求值 | 常配 `-maxdepth 1` |
| `-xdev` / `-mount` | 不跨文件系统 | 防止扫到 NFS、`/proc` |
| `-depth` | 后序遍历 | `-delete` 隐含 |
| `-prune` | 不下降当前目录 | 与 `-delete` 冲突 |
| `-noleaf` | 关闭目录叶子优化 | 旧文件系统才需要 |
| `-ignore_readdir_race` | 忽略遍历中文件消失 | 高并发目录 |
| `-warn`/`-nowarn` | 是否警告 | 默认对某些写法警告 |

`find /` 默认会跨挂载点，扫到 `/proc`、`/sys`、NFS 时会很慢甚至卡住。生产脚本一律加 `-xdev`，并显式排除虚拟文件系统：

```bash
find / -xdev \( -path /proc -o -path /sys -o -path /dev -o -path /run \) -prune \
     -o -type f -name '*.conf' -print
```

`-xdev` 已经能挡住独立挂载的 `/proc`、`/sys`，但如果它们和根在同一个挂载命名空间里以 bind mount 出现，仍要 `-prune`。`find` 的退出码只有 0（全部成功）和 1（有错误），权限错误会让它返回 1；脚本里 `2>/dev/null` 会连「找不到起点」一起吞掉，至少先检查起点存在。

::: method 写一条 find 命令的顺序
1. **定起点**：绝对路径，确认存在，避免 `.` 受 cwd 影响。
2. **加遍历约束**：`-xdev`、`-maxdepth`、`-mindepth`、`-prune`。
3. **写测试**：`-type`、`-name`、`-mtime`、`-size`、`-perm`，复杂条件加括号。
4. **先 `-print` 试跑**，把输出重定向到文件，抽样检查。
5. **换成动作**：`-print0` 交给下游，或 `-delete`/`-exec`；`-delete` 放最后。
6. **验证退出码**：`find ...; echo $?`，1 表示有错误被吞掉。
:::

### 0.3.14 小结

`find` 从起点遍历，对每个路径求一个布尔表达式：`!` 最紧、隐式 AND 次之、`-o` 最松，括号改变结合顺序。测试没有副作用，动作有副作用；`-delete` 隐含 `-depth`，`-exec ... +` 批量传参。如果只记住一件事，那就是：先用 `-print` 把表达式跑对，再把动作接上去。

## 0.3.15 xargs：把 NUL 分隔的流变成参数 {#sec-0.3.15}

这一节回答：`find` 已经把路径交出来了，为什么 `xargs` 还会把文件名拆坏？`-0`、`-n`、`-P`、`-r` 各改的是哪一步？

::: preview 先抓住一件事
`xargs` 把标准输入的一段字节流重新切成命令行参数；默认按空白切、还会解释引号，所以带空格或换行的文件名一定断错。上游 `-print0`、下游 `-0`，是唯一对所有文件名都正确的组合。
:::

`xargs` 的职责只有一个：从 stdin 读「项」，拼成命令行，执行命令。它的默认行为是**按空白分词并解释引号**，这与 Unix 文件名允许空格、换行、引号的事实直接冲突。正确用法只有一条主线：上游 `-print0`，下游 `-0`。

| 选项 | 作用 | 边界 |
|:--|:--|:--|
| `-0` / `--null` | 输入按 NUL 分隔，不做引号处理 | 唯一对任意文件名都正确的模式 |
| `-d DELIM` | 自定义单字节分隔符 | `-d '\n'` 适合「一行一项」 |
| `-r` / `--no-run-if-empty` | 空输入不执行命令 | GNU 默认空输入也会跑一次 |
| `-n N` | 每次最多 N 个参数 | 与 `-I` 冲突 |
| `-L N` | 每次最多 N 行 | 行内有空白时仍算一行 |
| `-P N` | 最多 N 个并发进程 | 输出可能交错；`0` 表示不限 |
| `-I STR` | 用 STR 替换参数中的占位符 | 隐含 `-L1`，且按行读 |
| `-a FILE` | 从文件读项 | 不与管道共用 |
| `-t` | 执行前打印命令行到 stderr | 调试用 |
| `-p` | 执行前询问 | 交互式 |
| `-E STR` / `-e` | 遇到 STR 停止 | 已废弃，优先 `-d` |
| `-s N` | 命令行最大字节数 | 默认约 128 KiB |
| `-x` | 超过 `-s` 时报错而不是截断 | 防止参数被悄悄截断 |
| `-o` | 子进程把 stdin 接到 `/dev/tty` | 需要交互输入时 |
| `--process-slot-var=VAR` | 给每个并发槽位一个编号 | 配 `-P` 做分片输出 |

把 `xargs` 想成一条装配线：它从 stdin 读「项」，按分隔符切开，攒够一批就拼成 `命令 参数 参数` 交给内核执行。分隔符选错，名字里的空格就会被当成项与项之间的边界；`-n` 控制每批几个，`-P` 控制几条装配线同时跑，`-r` 决定空输入时要不要空跑一次。

::: note 非科班补一层：argv 里没有「原来怎么分隔」
程序启动时，内核交给它一个字符串数组 `argv`，元素之间的边界已经定好，不再保留原来的空格或换行。`xargs` 要从字节流还原这个数组，只能自己挑分隔符。NUL 是文件名里唯一不会出现的字节，所以 `-0` 最安全。
:::

`xargs` 的退出码不是「子命令的退出码」，而是一组约定：

| 码 | 含义 |
|:--|:--|
| 0 | 所有调用成功 |
| 1 | xargs 自身出错（参数、读入、内存） |
| 123 | 有子命令以 1–125 退出 |
| 124 | 有子命令以 255 退出（xargs 立即停止） |
| 125 | 有子命令被信号杀死 |
| 126 | 命令找到但不可执行 |
| 127 | 命令找不到 |

所以 `find ... | xargs rm` 返回 0 不代表每个 `rm` 都成功；脚本里要检查 123，或改用 `find -exec ... +` 并检查 `$?`。`-P` 并发时，任何一个子命令失败都会让最终状态变成 123，但你不知道是哪一个；需要逐项状态时，让每个子命令把结果写到独立文件，或改用能汇报结果的并行工具。

```bash
# 正确：NUL 分隔，空输入不执行，单参数，4 路并发
find /srv/data -xdev -type f -name '*.log' -print0 |
    xargs -0 -r -n1 -P4 gzip -9

# 追加校验和；-r 防止空目录时执行一次 sha256sum
find /srv/app/conf -type f -name '*.conf' -print0 |
    xargs -0 -r sha256sum > /var/tmp/conf.sha256

# 每项单独起一个 shell；$1 是文件名，不会被当成代码
find . -name '*.png' -print0 |
    xargs -0 -r -I{} sh -c 'pngquant --force --output "$1" "$1"' _ {}
```

最后一条的 `_` 是 `$0` 占位，`{}` 变成 `$1`。如果写成 `sh -c 'pngquant {}'`，文件名里的 `;`、`$()`、反引号会被 shell 解释，等于把文件名当代码执行。`-I{}` 还会把输入按行处理，文件名含换行时仍会断；要绝对安全，用 `-0` 加 `sh -c '... "$1"' _`，不要让 `{}` 进入脚本正文。

正式跑之前，把命令换成只读的 `printf` 或 `echo` 看一遍参数：`find . -name '*.log' -print0 | xargs -0 -r -n1 printf 'would gzip %s\n'`。这一步能挡住三类事故：上游漏了 `-print0`、路径写错、`-r` 漏写导致空目录也执行一次。

`xargs` 与 `find -exec ... +` 的选择：

| 维度 | `xargs -0` | `find -exec ... +` |
|:--|:--|:--|
| 文件名安全 | `-print0` + `-0` 时安全 | `{}` 直接传参，安全 |
| 并发 | `-P` | 不支持 |
| 参数分批 | `-n`、`-s` 可控 | find 自动分批 |
| 错误汇报 | 123，不区分哪项 | 命令退出码原样返回 |
| 适用 | 需要并发、需要复用其他命令的输出 | 简单的批量删除/复制/校验 |

::: errata 关于 xargs 的三个误解
1. **「`xargs` 默认一次只传一个文件」**——默认会尽量多塞，直到接近参数长度上限；要逐个处理用 `-n1` 或 `-I{}`，后者还隐含 `-n1`。
2. **「文件名不会含空格或换行」**——除 `/` 和 NUL 外都可能出现；脚本里一律用 `-print0` 加 `xargs -0`，不要用 `for f in $(find ...)`。
3. **「`xargs` 返回 0 就代表每个文件都成功」**——它只看子进程退出码；一条命令处理十个文件、其中一个失败但命令仍退出 0 时，`xargs` 也返回 0。批量任务要自己记录失败清单，或改用 `find -exec ... +` 并检查 `$?`。
:::

### 0.3.15 小结

`xargs` 只做一件事：把 stdin 的字节流按分隔符切成参数，拼成命令行。默认按空白分词，遇到任意文件名就会断错；`-print0` 加 `-0` 用 NUL 兜底，`-n`、`-P`、`-r` 分别控制批量、并发和空输入。如果只记住一件事，那就是：路径进 `xargs` 之前，先确认分隔符是 NUL。

::: method 即时自测 · 0.3.15

**Q2（辨析）** 目录里只有 `a b.log`，`find . -name '*.log' | xargs -r gzip` 会发生什么？换成 `-print0` 加 `-0` 后为什么不会？

**Q3（应用）** 要压缩 `/srv/data` 下所有 `.log`，要求带空格的文件名也正确、目录为空时不执行、4 路并发。写出试运行和正式命令，并说明为什么不能写 `sh -c 'gzip {}'`。

## 0.3.16 扩展属性、chattr 与 access 竞态 {#sec-0.3.16}

这一节回答：权限位相同的两个文件，为什么还能带「部署批次」「SELinux 标签」这些额外信息？`chattr +i` 为什么连 root 都删不掉？先用 `access` 检查再 `open`，中间会发生什么？

::: preview 先抓住一件事
mode 只回答「谁能读、写、执行」；扩展属性（xattr）用键值对存其余元数据，ACL 与 SELinux 标签也走这条路。`chattr` 改的是 inode 标志位，不是 xattr。`access` 与 `open` 是两次独立解析，中间目标可能被换掉。
:::

传统 mode 只有 12 位，ACL 解决「谁能访问」，**扩展属性**（extended attributes, xattr）解决「文件还带什么元数据」。

先把 xattr 看成贴在 inode 上的一张便签：名字是 `user.comment` 这样的键，值是一段字节。你可以写「部署批次」，也可以写校验和；内核不解释内容，只负责存取。

SELinux 标签、capability、文件校验和、桌面环境的「下载来源」都存成 xattr。它们不是四套独立的文件格式，只是约定好的键名。

xattr 分命名空间：

| 命名空间 | 例子 | 谁可写 | 备份 |
|:--|:--|:--|:--|
| `user.*` | `user.comment` | 属主（普通文件/目录） | `tar --xattrs`、`rsync -X` |
| `trusted.*` | `trusted.overlay.*` | 需 `CAP_SYS_ADMIN` | 通常不备份 |
| `security.*` | `security.selinux`、`security.capability` | 需 LSM/`CAP_SETFCAP` | `tar --xattrs --selinux` |
| `system.*` | `system.posix_acl_access` | 内核/ACL 工具 | `tar --acls`、`rsync -A` |

`system.*` 这一行已经说明：ACL 不是另一套文件系统结构，它就是挂在 inode 上的 `system.posix_acl_access`（目录的默认 ACL 另存为 `system.posix_acl_default`）。`getfacl`/`setfacl` 读写它，`ls -l` 权限位后面的 `+` 号表示存在 ACL。

```bash
# 读、写、列、删
getfattr -d -m - /srv/app/config.yml       # -m - 列出所有命名空间
setfattr -n user.comment -v 'deploy=2024-10' /srv/app/config.yml
getfattr -n user.comment --only-values /srv/app/config.yml
setfattr -x user.comment /srv/app/config.yml

# 看 capability 与 SELinux 标签
getfattr -n security.capability -e hex /usr/bin/ping 2>/dev/null
getfattr -n security.selinux /etc/passwd 2>/dev/null
```

`getfattr -d` 默认只列 `user.*`，`-m -` 才显示全部；`--only-values` 去掉「名字=」前缀，适合脚本取值。属性可以存在但值为空字符串，这和「属性不存在」是两种状态。

`cp -a`、`tar --xattrs`、`rsync -X` 才保留 xattr；普通 `cp` 不保留。`user.*` 在 ext4/XFS/Btrfs 上默认启用；NFS 需要 `nfs4` ACL 与 xattr 支持；tmpfs 支持 `user.*` 与 `trusted.*`，但重启丢失。`getfattr -d` 不跟符号链接，要看目标加 `-h`（读链接本身）或 `-L`。

**文件属性**（`chattr`/`lsattr`）是另一层，存在 inode 的标志位里，不是 xattr：

| 属性 | 含义 | 效果 |
|:--|:--|:--|
| `i` | immutable | 不能写、改名、删除、加链接；root 也受限 |
| `a` | append-only | 只能以 `O_APPEND` 追加，不能覆盖/截断 |
| `d` | no dump | `dump` 跳过 |
| `A` | no atime | 不更新 atime |
| `S` | synchronous | 写入立即同步 |
| `c` | compressed | 透明压缩（需文件系统支持） |
| `e` | extent | ext4 extent 格式，通常只读 |
| `j` | journaling | 数据先写日志（ext4） |

所以 `chattr +i` 不是「把权限改成只读」。权限位可以仍是 644，但内核在 write、rename、unlink 的入口就看到 inode 上的不可变标志，直接返回 `EPERM`。

```bash
sudo chattr +i /etc/resolv.conf     # 防 DNS 被改
lsattr /etc/resolv.conf             # ----i---------e-------
sudo chattr -i /etc/resolv.conf     # 改之前必须先去掉
```

`lsattr` 输出里对应 `i` 的位置是 `i`，`e` 表示 ext4 的 extent 格式，属于正常状态。`chattr` 改的是 inode 标志，`setfattr` 改的是 xattr；两者互不影响。

`chattr +i` 是「防误改」而不是「防 root」：root 可以去掉属性再改，且有 `CAP_LINUX_IMMUTABLE` 的进程可以改。它常被用于保护 `/etc/resolv.conf`、引导文件、审计日志；容器里默认没有这个 capability，`chattr` 会失败。`chattr +a` 适合日志文件，但轮转工具需要先去掉属性，否则 `rename` 失败。

`access(2)` 与 `faccessat2(2)` 用来「以真实 UID/GID 检查权限」，而不是按已打开 fd 的 euid。

问题出在顺序：`access` 只回答「此刻这个路径能不能读」，它不打开文件，也不锁住路径。检查和随后的 `open` 是两次独立解析，中间目标可以被换成符号链接，这就是 **TOCTOU**（time-of-check to time-of-use，检查与使用之间的时间差）。

`access` 还受 `AT_EACCESS` 影响：默认用 real UID，`faccessat(AT_EACCESS)` 用 effective UID。setuid 程序里用 `access` 检查用户权限，再用 root 权限打开，是经典的提权面。

```c
/* 不安全：检查与打开是两次解析 */
if (access(path, R_OK) == 0) {
    fd = open(path, O_RDONLY);   /* 这中间 path 可能变成符号链接 */
}

/* 较安全：打开后对 fd 检查，后续只用 fd */
fd = open(path, O_RDONLY | O_NOFOLLOW | O_CLOEXEC);
if (fd < 0) { /* ELOOP 表示最后一段是符号链接 */ }
struct stat st;
if (fstat(fd, &st) < 0) { ... }
/* 需要按 real uid 判权时，用 faccessat2(fd, "", mode, AT_EMPTY_PATH) */
```

更稳的写法是只解析一次：先用 `O_NOFOLLOW` 打开，之后所有操作都用这个 fd；要判权就 `faccessat2` 对 fd 做，不再碰路径。

`faccessat2` 支持 `AT_EMPTY_PATH`，可对已打开的 fd 做权限检查，把「检查对象」固定成 fd；`openat2` 的 `RESOLVE_BENEATH`/`RESOLVE_NO_SYMLINKS` 则把「解析范围」固定住。两者组合，才能消掉路径竞态。

::: note 非科班补一层：三层元数据别混
`chmod` 改的是 12 位权限，回答「谁能读、写、执行」；`setfattr` 改的是键值对，回答「还带了什么附带信息」；`chattr` 改的是 inode 标志，回答「内核要不要拒绝某些操作」。三层可以同时存在，排障时先确认是哪一层在拦你。
:::

::: errata 关于 xattr、chattr 与 access 的误解
1. **「xattr 就是 ACL」**——ACL 只是 `system.posix_acl_access` 这一种 xattr；SELinux 标签、capability 也走 xattr，但 `chattr` 的属性不在 xattr 里。
2. **「`chattr +i` 是加强版 chmod」**——它不改权限位，改 inode 标志；root 也要先 `chattr -i`，只有带 `CAP_LINUX_IMMUTABLE` 的进程能改这个标志。
3. **「`access` 返回 0 就一定能打开」**——检查与打开之间路径可能被替换；setuid 程序里这正是提权面。应打开后对 fd 判权，或用 `openat2` 限定解析范围。
:::

### 0.3.16 小结

xattr 是挂在 inode 上的键值对，ACL 和 SELinux 标签都借它存放；`chattr` 改的是另一层——inode 标志位。`access` 只做一次「现在能不能读」的检查，和随后的 `open` 之间隔着一段可以被利用的时间。如果只记住一件事，那就是：检查与使用要落在同一个 fd 上，不要用路径检查两次。

## 0.3.17 复制、同步与打包：cp、rsync、tar {#sec-0.3.17}

这一节回答：`cp -r` 明明复制成功了，为什么服务起来后权限、SELinux 标签或硬链接关系不对？`rsync` 凭什么第二次几乎不传数据？`tar` 解包时怎样不把属主和路径带到错误的地方？

::: preview 先抓住一件事
复制不是「把字节搬过去」：mode、属主、时间、xattr、ACL、硬链接关系都是元数据，工具默认只保留其中一部分。`cp` 按文件复制，`rsync` 先比对再传差异，`tar` 把目录树和元数据一起装进一个流；三者的默认值都比直觉保守。
:::

`cp` 的选项决定「复制什么」与「怎么复制」：

| 选项 | 作用 | 边界 |
|:--|:--|:--|
| `-a` | `-dR --preserve=all` | 保留链接、权限、时间、xattr、ACL、SELinux |
| `-d` | 不跟随符号链接，保留硬链接 | 等价 `-P --preserve=links` |
| `-P` | 不跟随符号链接 | 复制链接本身 |
| `-L` | 跟随所有符号链接 | 可能复制到树外 |
| `-p` | 保留 mode/ownership/timestamps | 不含 ACL/xattr |
| `--preserve=all` | 再加 context/links/xattr | 属主需 root |
| `--reflink=auto` | CoW 文件系统上共享 extents | XFS/Btrfs；跨文件系统退化为普通复制 |
| `--sparse=always` | 检测零块并打洞 | 普通复制可能把稀疏文件写实 |
| `-u` | 仅当源更新时复制 | 比较 mtime，不比较内容 |
| `-n` | 不覆盖已存在目标 | 与 `-i` 不同，不询问 |
| `-l` | 建硬链接而不是复制 | 同一文件系统 |
| `-s` | 建符号链接 | 目标路径按源路径 |
| `-T` | 把目标当普通文件/目录 | 禁止「复制进目录」的推断 |
| `--remove-destination` | 先删目标再复制 | 断开目标已有的硬链接 |
| `-x` | 不跨文件系统 | 备份挂载树时用 |
| `-Z` | 设置 SELinux 上下文 | 需 SELinux |

`cp -a src dst` 与 `cp -r src dst` 的差别不只是权限：`-a` 保留符号链接本身、硬链接关系、xattr、ACL、SELinux 标签；`-r` 跟随命令行给出的链接、把硬链接复制成多份、丢掉 xattr。恢复一个服务目录时，`-r` 可能让配置文件的 SELinux 标签错掉，服务起不来。

普通 `cp` 连时间都不保留：新文件的 mtime 是复制时刻，mode 还受 umask 影响。`cp -p` 补回 mode、属主、时间，但仍不含 ACL/xattr；`cp -a` 才等于 `-dR --preserve=all`。属主只有在 root 下才能真正保留，普通用户复制别人的文件，属主会变成自己。

::: note 非科班补一层：文件不只有内容
一个文件在磁盘上有三部分：数据块、inode 里的元数据（mode、属主、时间、xattr 指针）、目录里的名字。`cp` 默认重新创建一个 inode，所以新 inode 的元数据由当前进程和 umask 决定，而不是从源文件照抄。要「连身份一起搬」，就得显式要求保留。
:::

`cp` 覆盖一个已存在的硬链接目标时，会**写进同一个 inode**，而不是替换目录项：

```bash
printf 'old\n' > a; ln a b
printf 'new\n' > c
cp c a
cat b          # new：b 与 a 仍指向同一 inode
```

要让 `a` 变成独立的新文件，用 `cp --remove-destination c a` 或 `mv`。备份脚本里这很关键：直接 `cp` 到正在使用的文件，正在读的进程可能看到半截内容；正确做法是写临时文件 + `rename`。

`rsync` 是「增量同步」工具，不是复制命令的别名。它先比较两边的大小和 mtime（quick check），相同就跳过；不同才计算差异块并只传变化的部分，所以第二次同步几乎不传数据。

代价是 quick check 不看内容：mtime 被保留成一样、内容却不同时，`rsync` 会漏掉。要按内容判断，加 `--checksum`，代价是两边都要读完整个文件。

| 选项 | 作用 | 注意 |
|:--|:--|:--|
| `-a` | archive：递归 + 权限 + 时间 + 链接 + 属主 | 不含 ACL/xattr |
| `-A` / `-X` | 保留 ACL / xattr | 需要目标文件系统支持 |
| `-H` | 保留硬链接 | 大目录内存开销高 |
| `-S` | 处理稀疏文件 | 传输时压缩空洞 |
| `--delete` | 删除目标端多余文件 | 先用 `--dry-run` |
| `--delete-excluded` | 连排除的也删 | 危险 |
| `-n` / `--dry-run` | 只显示计划 | 必做 |
| `-i` / `--itemize-changes` | 逐项说明变化 | 排障用 |
| `--partial` | 保留半截文件以便续传 | 与 `--inplace` 取舍 |
| `--inplace` | 直接改目标文件 | 非原子，读进程可能看到半截 |
| `-e ssh` | 指定远程 shell | 默认就是 ssh |
| `--bwlimit` | 限速 | 生产迁移必备 |

`rsync` 的尾部斜杠决定「复制目录本身还是目录内容」：`rsync -a src/ dst/` 同步 `src` 的内容到 `dst`；`rsync -a src dst/` 在 `dst` 下建 `src`。`--delete` 只在「源是目录内容」时符合直觉，写错会把目标端多删一层。生产脚本一律先 `-n -i` 看清单，再执行。

`-a` 不含硬链接、ACL 与 xattr，完整保留要写 `-aHAX`。`--numeric-ids` 让 uid/gid 按数字传，避免两端用户名相同、数字不同时把属主映射错：

```bash
# 先看计划：-n 不落盘，-i 逐项说明每个文件为什么被处理
rsync -aHAX --numeric-ids --delete -n -i /srv/app/ /backup/app/

# 确认后执行；--bwlimit 防止迁移占满生产带宽
rsync -aHAX --numeric-ids --delete --bwlimit=50M /srv/app/ /backup/app/
```

`--delete` 的方向要说清：它删的是**目标端有、源端没有**的文件，让目标端向源端看齐。源路径写错成空目录，目标端就会被清空；`--delete-excluded` 连被排除的文件也删，更危险。第一次跑一律先 `-n`。

`tar -x` 时真正决定「装到哪」的是 `-C`，不是当前目录：

```bash
# 打包 /etc 的内容，归档里是 ./ 开头的相对路径
sudo tar -cpf /backup/etc.tar -C /etc .

# 列出归档，确认硬链接关系与路径
tar -tvf /backup/etc.tar | head

# 解到指定目录；--numeric-owner 按归档里的数字 uid/gid 恢复
sudo tar -xpf /backup/etc.tar -C /srv/restore --numeric-owner
```

`tar` 默认保留硬链接关系：归档里第二个名字记成「link to 第一个名字」，解出来仍是同一个 inode。要展开成多份，才用 `--hard-dereference`。`--numeric-owner` 在异机恢复时很关键：按用户名恢复会把 `alice` 映射到目标机上恰好也叫 `alice` 的另一个 uid，按数字恢复才和原机一致。

`tar` 的安全边界在**解压**而不是创建。恶意归档可以包含绝对路径、`..`、指向外部的符号链接，以 root 解压会覆盖系统文件。GNU tar 默认会拒绝绝对路径和 `..`（`--absolute-names` 才允许），但仍建议：

```bash
# 1. 先看清单，不落盘
tar -tzf untrusted.tar.gz | sed -n '1,50p'
# 2. 拒绝绝对路径与 ..（清单里出现就停止）
tar -tzf untrusted.tar.gz | grep -E '(^/|(^|/)\.\.(/|$))' && exit 1
# 3. 解到空目录，不用 root，必要时去掉 suid/sgid
mkdir -p /tmp/unpack && tar -xzf untrusted.tar.gz -C /tmp/unpack \
    --no-same-owner --no-same-permissions
# 4. 需要保留 ACL/xattr 时显式加，并确认目标文件系统支持
tar -xzf backup.tar.gz -C /srv/restore --acls --xattrs --selinux
```

`tar -x` 以 root 运行会按归档恢复属主与权限，包括 setuid 位；解压不可信归档时应加 `--no-same-owner --no-same-permissions`，或先以普通用户解压再审查。`--strip-components=1` 常用于源码包，但它不改变安全性，只是去掉顶层目录。

::: errata 关于复制、同步与归档的误解
1. **「`cp -r` 与 `cp -a` 只差权限」**——`-a` 还保留符号链接、硬链接、xattr、ACL、SELinux 标签；`-r` 会跟随命令行链接、展开硬链接。
2. **「`cp` 覆盖文件会替换 inode」**——默认是截断并写入同一个 inode，硬链接的另一端会看到新内容；要替换用 `--remove-destination` 或先 `rm`。
3. **「`rsync -a` 会保留 ACL 与 xattr」**——要显式 `-A -X`；`-a` 只含基本权限与时间。
4. **「`rsync --delete` 只删源端没有的文件」**——它让目标端向源端看齐，删的是目标端有、源端没有的文件；源路径写错会清空目标端，先 `-n -i`。
5. **「`rsync` 一定按内容判断差异」**——默认看大小和 mtime，时间被保留但内容变了会漏；要按内容加 `--checksum`。
6. **「`tar` 默认把硬链接展开成多份」**——默认保留硬链接关系；要展开才加 `--hard-dereference`。
7. **「`tar -x` 会自动防路径穿越」**——GNU tar 默认拒绝绝对路径与 `..`，但符号链接、硬链接、`--absolute-names` 仍能绕过；不可信归档要在空目录、非 root 解。
:::

### 0.3.17 小结

`cp` 按文件复制，默认只带走一部分元数据，`-a` 才是「尽量全保留」；`rsync` 先比对再传差异，`--delete` 让目标端向源端看齐；`tar` 把目录树和元数据装进一个流，`-C` 决定装到哪，`--numeric-owner` 决定属主按数字还是按名字恢复。如果只记住一件事，那就是：复制、同步、解包之前，先问「哪些元数据要保留，删的方向是哪边」。

## 0.3.18 移动、重命名与删除：mv、renameat2、rm {#sec-0.3.18}

这一节回答：为什么同一个盘里 `mv` 一个大目录瞬间完成，跨盘却要等半天？`renameat2` 的 `NOREPLACE`/`EXCHANGE` 各解决什么问题？`rm` 之后数据真的没了吗？

::: preview 先抓住一件事
在同一文件系统内，`mv` 只改目录项，是原子的 `rename`，不搬数据；跨文件系统时它退化成「复制 + 删除」，中途失败会留下半个目标。`rm` 只是把名字从目录里摘掉，数据块要等链接数为 0 且没有打开的 fd 才释放，而且不会清零。
:::

`mv` 在同一文件系统内是 `rename(2)`：原子地改目录项，不搬数据。跨文件系统时，GNU mv 退化成「复制 + 删除」，中途失败会留下半个目标；大目录迁移应先 `rsync -aH --info=progress2`，校验后再删源。

目录项就是「名字 → inode 号」的一行记录。同一文件系统内改名，内核只改这一行，10 GB 的目录也能瞬间完成；所谓原子，是其他进程要么看到旧名、要么看到新名，不会看到中间状态。

::: note 非科班补一层：名字、inode 与 fd
目录项是「名字」，inode 是「文件本身」，fd 是「进程当前打开的那一份」。`rename` 改名字，`unlink` 删名字，`close` 放掉 fd；名字没了但 fd 还在，文件就继续活着。
:::

| 写法 | 行为 |
|:--|:--|
| `mv src dst` | `dst` 是目录则移入，否则改名 |
| `mv -T src dst` | 强制把 `dst` 当名字，不推断目录 |
| `mv -n src dst` | 不覆盖已存在目标 |
| `mv -u src dst` | 仅当源更新时移动 |
| `mv -b` | 覆盖前备份为 `dst~` |
| `mv -t dir src...` | 指定目标目录，适合 `xargs` |
| `mv --strip-trailing-slashes` | 去掉源末尾斜杠，避免「移动进目录」歧义 |

跨文件系统时 `rename(2)` 直接返回 `EXDEV`，`mv` 只能退化成复制、删除源。中途断电或目标写满，源还在、目标只有一半；这时不要删源，先用 `rsync` 补齐再校验。用 `strace` 能直接看到两条路径的差别：

```bash
# 同盘：只出现 rename/renameat2
strace -e trace=rename,renameat2 mv /srv/app /srv/app.old

# 跨盘：出现 openat/read/write/unlink 一类调用，rename 不会成功
strace -f -e trace=rename,renameat2,openat,read,write,unlink \
    mv /srv/big.img /mnt/backup/ 2>&1 | tail -20
```

`rename(2)` 的原子性只保证「名字切换」这一步，不保证数据落盘。崩溃后可能看到旧名字或新名字，但不会看到半个目录项；要保证持久，`rename` 后还要 `fsync` 父目录。`renameat2(2)` 增加了三个有用标志：

| 标志 | 语义 | 用途 |
|:--|:--|:--|
| `RENAME_NOREPLACE` | 目标存在则 `EEXIST` | 不覆盖的原子创建 |
| `RENAME_EXCHANGE` | 原子交换两个路径 | 配置热切换、双缓冲 |
| `RENAME_WHITEOUT` | 创建 whiteout 节点 | overlayfs 内部 |

```c
/* 原子发布：临时文件已写好并 fsync，再 rename 成正式名 */
if (renameat2(AT_FDCWD, tmp, AT_FDCWD, final, RENAME_NOREPLACE) < 0) {
    if (errno == EEXIST) { /* 已有别的实例发布，保留旧的 */ }
    else { perror("renameat2"); }
}
```

`RENAME_NOREPLACE` 解决的是「检查目标是否存在」和「改名」之间的竞态：如果先 `stat` 再 `rename`，两个进程可能同时通过检查；`NOREPLACE` 把判断交给内核，目标存在就 `EEXIST`。`mv -n` 在新版 coreutils 里也会优先用这个标志，但脚本不应假设所有平台都支持。

`RENAME_EXCHANGE` 则是把两个名字原子互换，适合双缓冲：新配置写到临时文件，再与正式文件交换。读进程要么拿到旧版、要么拿到新版，不会读到写了一半的文件。

`RENAME_NOREPLACE` 在 NFS、部分旧文件系统上返回 `EINVAL`/`EOPNOTSUPP`；可移植脚本要回退到 `link(tmp, final)` + `unlink(tmp)`（`link` 在目标存在时返回 `EEXIST`，本身原子）。

`rm` 删除的是目录项，不是数据块；inode 的链接数减一，减到 0 且没有打开的 fd 时才释放 inode 与数据。换句话说，`rm` 只把「名字 → inode」这一行从目录里拿掉。

| 选项 | 作用 | 注意 |
|:--|:--|:--|
| `-r` / `-R` | 递归 | 不跟随符号链接（删链接本身） |
| `-f` | 不提示，忽略不存在 | 与 `-i` 相反，后者优先 |
| `-i` | 每个文件询问 | 大量文件很慢 |
| `-I` | 删除超过 3 个或递归前询问一次 | 比 `-i` 实用 |
| `-d` | 删除空目录 | 等价 `rmdir` |
| `--one-file-system` | 不跨挂载点 | 清理挂载树时防误删 |
| `--preserve-root` | 拒绝删除 `/` | 默认开启 |
| `--no-preserve-root` | 允许删 `/` | 不要用 |
| `-v` | 打印删除的路径 | 审计 |

`rm -rf` 的三个高危模式仍然成立：变量为空、路径拼错、通配符没匹配。再加两个：**在符号链接后加斜杠**（`rm -rf link/` 会跟随链接删目标内容，而 `rm -rf link` 只删链接），以及**在 `/tmp` 里用可预测名字**（竞态）。GNU `rm` 拒绝删除 `.` 和 `..`，但 `rm -rf -- "$dir"/` 在 `dir` 为空时仍可能变成 `rm -rf /`；`${dir:?}` 是底线。

`rm` 返回成功，空间却不一定马上回来：只要还有进程开着这个文件，inode 和数据块就继续被占用。日志服务删掉旧日志、`df` 却不降，原因通常在这里。

```bash
# 找「已删除但仍被打开」的文件：NLINK 为 0
sudo lsof +L1 2>/dev/null | head
# 从进程侧看：fd 的符号链接末尾带 (deleted)
ls -l /proc/$PID/fd | grep deleted
```

处理方式是让持有者重新打开文件（重启服务、发信号让它轮转），或对追加写的日志执行 `: > /proc/$PID/fd/N` 截断。直接删名字不会释放块，因为内核还在替进程保存这个 inode。

`rm` 也不清零。unlink 只是把数据块标记为空闲，块里的字节还在，直到被新数据覆盖；机械盘上，取证工具在覆盖前仍可能读回。SSD 的磨损均衡、CoW 文件系统的快照与压缩，会让「覆写原块」这个假设失效。

需要「不可恢复」时，`shred` 在 SSD、CoW 文件系统、带日志的文件系统上**不保证**覆盖原块；它只对传统磁盘上的未压缩文件有意义。企业环境更可靠的做法是加密盘 + 销毁密钥，而不是反复覆写。

::: errata 关于移动、重命名与删除的误解
1. **「`mv` 总是原子的」**——只在同一文件系统内是 `rename`；跨文件系统是复制 + 删除，中途失败会留下半个目标。
2. **「`rename` 返回成功就落盘了」**——目录项持久化要 `fsync` 父目录，崩溃可能丢名字。
3. **「`rm` 会把数据清零」**——unlink 只摘掉名字并释放块，字节还在，覆盖前可能被恢复；`shred` 在 SSD/CoW 上也不保证。
4. **「`rm` 之后空间立刻回来」**——还有进程持有 fd 时要等它关闭；`lsof +L1` 能看到这类文件。
:::

### 0.3.18 小结

同一文件系统内，`mv` 只改目录项，原子且不搬数据；跨文件系统时退化成复制 + 删除，失败会留下半个目标。`rm` 是 unlink，链接数为 0 且没有打开的 fd 才释放块，而且不清零。如果只记住一件事，那就是：动手前先问「这是不是同一个文件系统，还有谁开着它」。

**Q2（辨析）** 普通 `rename` 遇到已存在的目标会怎样？`RENAME_NOREPLACE` 怎样把「不覆盖」变成一步？`RENAME_EXCHANGE` 适合什么场景？

**Q3（应用）** 日志服务删除了 20 GB 旧日志，`df` 几乎没降。写出定位命令、原理解释和两种处理方式；再说明为什么 `shred` 不能保证擦除。

::: sol 答案
**A1** 同文件系统调 `rename(2)`（`renameat2` 可带标志），只改目录项；跨文件系统返回 `EXDEV`，`mv` 退化成复制 + 删除。`NOREPLACE` 目标存在则 `EEXIST`；`EXCHANGE` 原子交换两个路径；`WHITEOUT` 创建 whiteout 节点，供 overlayfs 使用。
**A2** 普通 `rename` 原子地用新名字覆盖旧名字，旧 inode 的链接数减一；要「目标存在就失败」，先 `stat` 再 `rename` 会留下竞态。`RENAME_NOREPLACE` 让内核在同一步判断，目标存在就返回 `EEXIST`。`EXCHANGE` 适合配置双缓冲：新文件与正式文件原子互换，读进程不会读到半截。
**A3** 先 `sudo lsof +L1` 找 `NLINK` 为 0 的文件，再从 `ls -l /proc/$PID/fd` 确认持有进程。原因是 `rm` 只删目录项，进程还持有 fd，inode 与数据块不释放。处理：重启/让服务重新打开日志，或 `: > /proc/$PID/fd/N` 截断。`shred` 依赖「覆写同一物理块」，SSD 磨损均衡、CoW 与压缩都会把写落到别处，所以不能保证。
:::
:::

## 0.3.19 实验：用 strace 与 inode 取证 {#sec-0.3.19}

这一节回答：前面关于 inode、链接与删除的结论，怎样在自己机器上变成看得见的证据？

::: preview 先抓住一件事
三个实验各看一件事：一次「打开、删除、改名」在系统调用层留下什么；`rm` 之后空间为什么不马上回来；内核在哪一层拦下 `chattr +i` 保护的文件。每个实验都按同一个套路读：先看哪几行、这几行证明什么、看不到它们说明什么。
:::

先交代工具。`strace` 是系统调用跟踪器，把进程跨越内核边界的那一步逐条打印出来；[0.5.16](ch05.md#sec-0.5.16) 用它看过重定向，这次用来看路径解析与删除。`-f` 跟随子进程，`-e trace=...` 只留关心的调用，`-yy` 把 fd 显示成路径。`strace` 会明显拖慢被跟踪的程序，只用于单次复现，不要包进生产脚本。`lsof` 反过来，从内核一侧列「哪个进程开着哪些文件」；`stat`、`ls -li`、`df` 读的是 inode 与块计数。

**非科班补一层：`df` 数的到底是什么。** `df` 读的是文件系统级的空闲块计数。块什么时候从「占用」变回「空闲」，不取决于你敲没敲 `rm`，而取决于内核什么时候发现「没有任何东西再引用它」。实验二的因果链就是这条线。

### 实验一：看清一次「打开、删除、重命名」的路径解析

```bash
mkdir -p /tmp/fs-lab && cd /tmp/fs-lab
printf 'hello\n' > a.txt
ln a.txt hard.txt
ln -s a.txt soft.txt
strace -f -yy -e trace=openat,newfstatat,statx,readlinkat,unlink,unlinkat,rename,renameat2 \
    -o /tmp/fs.trace \
    bash -c 'cat soft.txt >/dev/null; rm a.txt; mv hard.txt renamed.txt'
grep -E 'soft|a\.txt|hard|renamed' /tmp/fs.trace | tail -20
```

下面是 Ubuntu 24.04.5 上真跑出来的三行（PID 与 fd 号每台机器不同，语义相同）：

```text
24420 openat(AT_FDCWD</tmp/lab0c03>, "soft.txt", O_RDONLY) = 3</tmp/lab0c03/a.txt>
24421 unlinkat(AT_FDCWD</tmp/lab0c03>, "a.txt", 0) = 0
24419 renameat2(AT_FDCWD</tmp/lab0c03>, "hard.txt", AT_FDCWD</tmp/lab0c03>, "renamed.txt", RENAME_NOREPLACE) = 0
```

先看什么：三行分别是 `cat`、`rm`、`mv` 发起的。第一行等号右边那个 `3</tmp/lab0c03/a.txt>` 是 `-yy` 的功劳——它把返回的 fd 直接标成**解析后的真实路径**，于是同一行里就能看到「用户态只说了 `soft.txt`，内核替它跟到了 `a.txt`」：软链接跟随发生在内核的路径解析里，不在 `cat` 的代码里。第二行是 `rm`，参数是名字，没有任何写数据块的动作；第三行是 `mv`，只改目录项。

三处和常见教程不一样，都是这台机器给的：

1. **标志位里没有 `O_CLOEXEC`。** 这里的 `cat` 走的是普通 `O_RDONLY`。会不会带 `O_CLOEXEC` 取决于调用方（glibc 的 `fopen` 会加，部分 coreutils 工具不加），不是「glibc 自动加」的统一规律，别照抄别人的 trace。
2. **`rm` 用的是 `unlinkat(AT_FDCWD, "a.txt", 0)`，不是 `unlink`。** 现代 coreutils 统一走 `*at` 家族，为的是能带目录 fd 与标志；`unlink` 还在，但已不是 `rm` 的第一选择。
3. **`mv` 用的是 `renameat2(..., RENAME_NOREPLACE)`。** 同一条命令在 macOS 的 BSD `mv` 上给的是普通 `rename`（本机实测过），所以 0.3.18 说「`mv -n` 是否原子取决于实现」不是套话：**GNU 侧由内核给不覆盖保证，BSD 侧是「先检查再改名」两步**，中间存在可被抢占的时间窗。

这几行证明什么：链接跟随、删名字、改名分别落在 `openat`、`unlink`、`rename` 三个调用上，全部发生在内核的路径解析与目录项操作里；0.3.10 画的「逐段解析」和 0.3.18 说的「`rm` 只摘名字」，在这里变成看得见的行。

看不到什么说明什么：如果 `openat` 那行变成 `-1 ENOENT`，说明 `soft.txt` 存在但目标不存在——悬空符号链接；此时 `newfstatat(..., AT_SYMLINK_NOFOLLOW)` 仍能看到链接本身。如果整份 trace 里没有 `rename`，多半是前面的 `rm` 失败导致后两步没执行，先查各步退出码，再怀疑 `strace`。fd 号、动作拆成 `unlink` 还是 `unlinkat`，都随 bash 与 coreutils 版本变化；抓的是语义和顺序，不是固定行。

把 `-e trace=` 换成 `%file` 可以看所有路径类系统调用；加 `-y` 把 fd 显示成路径，加 `-yy` 连 socket/pipe 也显示。

### 实验二：硬链接、inode 与「删了但没释放」

先跑，一段一段看。实验一把 `a.txt` 删了、`hard.txt` 改名了，这里先重建三件套再进入主题：

```bash
cd /tmp/fs-lab
printf 'hello\n' > a.txt
ln -f a.txt hard.txt
ln -sfn a.txt soft.txt
stat -c 'name=%n inode=%i links=%h size=%s blocks=%b' a.txt hard.txt soft.txt
ls -li
# 制造一个被进程持有的已删除文件
dd if=/dev/zero of=big.log bs=1M count=64 status=none
exec 9<big.log
rm big.log
lsof +L1 2>/dev/null | grep big.log || sudo lsof +L1 | grep big.log
df -h /tmp | tail -1
exec 9<&-
sync; df -h /tmp | tail -1
```

Ubuntu 24.04 实测到的那一行长这样（第 5 列是链接数，写成 `0` 就是本实验要抓的状态）：

```text
bash  24433  juanwang  9r  REG  8,2  8388608  0  176860  /tmp/lab0c03/big.log (deleted)
```

其余预期也都对上了：`a.txt` 与 `hard.txt` 的 inode 相同、`links=2`；`soft.txt` 的 inode 不同、`size` 是目标路径字符串的长度。`rm big.log` 后 `lsof +L1` 仍列出该文件、`df` 的已用空间不降；关闭 fd 9 才释放。没有 `lsof` 时用 `ls -l /proc/*/fd 2>/dev/null | grep deleted` 找持有者。64 MB 在 GB 粒度的 `df -h` 上可能只挪一位小数，把 `count` 加大即可，机制不变。

两个现场细节值得记住。**其一，你会看到几乎重复的两行**：上例里 `grep` 进程也持有 fd 9 —— 子进程继承打开文件描述（0.5.1 那张表的另一条推论），所以 `lsof +L1` 把它一起列出来，不是显示 bug。**其二，`df -h /tmp` 打出的挂载点是 `/` 而不是 `/tmp`**：这台 Ubuntu 没有独立的 `/tmp` 分区，`/tmp` 只是根文件系统上的目录。验证「删了不腾地方」之前先 `findmnt -T /tmp` 看清它落在哪个设备上，否则你盯的数字可能来自另一张表。

从 `rm` 到 `df` 之间隔着什么？这是要补的那层因果，一格都不能跳：

1. `rm big.log` 执行的是 `unlink`：目录里「big.log 指向这个 inode」这一行被拿掉，链接计数从 1 变 0。此刻 `ls` 已经看不见它。
2. 但 fd 9 还开着。内核每次 `open` 都生成一条**打开文件描述**（open file description，记录文件偏移与访问模式的内核对象，[0.5.1](ch05.md#sec-0.5.1) 画过这张表）；它引用着那个 inode，内存里的 inode 副本记着「还有几条这样的引用」。
3. 回收条件是「目录链接数为 0，且打开文件描述的引用为 0」。第二个条件没满足，inode 与数据块都还活着。
4. `df` 数的是已分配块；第 1 步只删了目录表里的一行，一块数据都没还回去，所以它的数字不动。
5. 关闭最后一个 fd，就是代码块里那行先于 `sync` 的 `exec` 关闭命令；引用归零，内核这时才回收块。`sync` 只把脏页落盘，不改变已释放的事实。

`lsof +L1` 的 `+L1` 是「列出链接数小于 1 的打开文件」，正好抓住第 2 步的中间态。若这类行一条都没有但 `df` 仍不降，多半不是本机制：先 `findmnt -T /tmp` 确认你盯的是同一个挂载点，再考虑 tmpfs、overlay 的记账差异（未实测）。

这个中间态还有一个限制与一个妙用。限制：链接数已降为 0 的打开文件，没法再用 `link()` 把名字挂回去——你能通过 `/proc/$PID/fd/N` 读出内容或截断它，但不能给它恢复一个路径。妙用是反过来用的：先创建并打开一个临时文件，立刻 `unlink`，程序照常读写，进程一退出数据自动消失，别的进程无法按名字碰它；这正是 C 库 `tmpfile()` 的做法。

补一刀，看 inode 本身。用 `debugfs` 读 inode 的创建时间（需要 root 与未挂载或只读访问；生产上优先 `statx`）：

```bash
sudo debugfs -R 'stat <'"$(stat -c %i /tmp/fs-lab/a.txt)"'>' /dev/nvme0n1p2 2>/dev/null | head -15
```

输出里的 `crtime` 是 ext4 的创建时间，`ctime` 是 inode 变更时间。不要在没有备份的块设备上执行写操作；`debugfs` 的 `stat` 是只读的，但仍建议先用 `findmnt -T /tmp` 确认设备。

### 实验三：原子发布与被拦下的那次删除

0.3.16 说 `chattr +i` 改的是 inode 标志、`access` 与 `open` 是两次独立解析；0.3.18 说 `RENAME_NOREPLACE` 把「目标存在吗」的判断交给内核。这一组命令让你在内核调用的返回值处看到这三件事：

```bash
cd /tmp/fs-lab
printf 'v1\n' > conf.txt
printf 'v2\n' > new.txt

# A. mv -n 撞上已存在的目标：「不覆盖」在内核层长什么样
strace -e trace=rename,renameat2 mv -n new.txt conf.txt 2>&1 | grep -E 'rename'

# B. 不带 -n 的 mv：目标存在也成功
strace -e trace=rename,renameat2 mv new.txt conf.txt 2>&1 | grep -E 'rename'

# C. chattr +i 之后删文件：看错误码
sudo chattr +i conf.txt
strace -e trace=unlink,unlinkat rm conf.txt 2>&1 | tail -2
lsattr conf.txt
sudo chattr -i conf.txt

# D. 写一个 xattr：它就是一次系统调用
strace -e trace=setxattr,getxattr setfattr -n user.batch -v '2026-10' conf.txt 2>&1 | grep xattr
```

口径照旧：以下预期因 strace 与 coreutils 版本而异，抓语义不抓行号。A 里应看到一次带 `RENAME_NOREPLACE` 标志的 `renameat2`，返回 `-1 EEXIST`；`mv -n` 把这次失败翻译成「什么都不做、也不报错」。这就是 0.3.18 说的「把判断交给内核」——检查与改名是同一步。若你机器上看到的是 `newfstatat` 加 `rename` 两步，说明这版 coreutils 没走 `NOREPLACE`，回退成先查再改；功能一样，但两步之间有一个可被利用的时间窗，正是 0.3.16 的 TOCTOU 在批量场景的放大版。

B 里应看到普通的 `rename` 或不带 `NOREPLACE` 的 `renameat2` 返回 0，一步完成覆盖。C 是关键的一行：`rm` 报 `Operation not permitted`，trace 里是 `unlinkat(...)` 返回 `-1 EPERM`。权限位仍是 644、属主仍是自己——拦下你的是 inode 上的 `i` 标志，不是 mode；`lsattr` 第一个字符列出现 `i` 即为证据。D 里应看到一次 `setxattr` 调用，键名 `user.batch`，值是那段字节；xattr 不是什么神秘结构，写它是一次调用，读它是另一次。

看不到什么说明什么：C 里 `rm` 竟然成功，先 `lsattr` 确认标志真加上了，再确认目标文件系统支持 `chattr`（部分网络文件系统不支持，未实测）。D 里若完全看不到 `setxattr`，把 `-e trace=` 换成 `%file` 之外的完整列表重跑，确认 `setfattr` 是否在你机器上走了 `lsetxattr`——三者语义相同，只是是否跟随链接的差别。

::: errata 关于取证的误解
1. **「strace 的输出每次都一样」**——bash 与 coreutils 版本、fd 编号、用 `unlink` 还是 `unlinkat` 都会变；取证抓的是调用语义与先后顺序。
2. **「`lsof` 不需要权限」**——看别的进程的 fd 需要 root；且要 `+L1` 才会把链接数为 0 的已删除文件列出来。
3. **「`rm` 成功但 `df` 不降，说明没删成」**——名字已经删了，块还在等最后一个 fd 关闭；这也是为什么处理办法是重启服务或截断 `/proc/$PID/fd/N`，而不是再 `rm` 一遍。
4. **「已删除的文件可以用 `ln` 把名字救回来」**——链接数为 0 的打开文件无法重新关联名字；能救的只有内容。
:::

### 0.3.19 小结

实验一把「打开、删除、改名」翻译成 `openat`、`unlink`、`rename` 三个调用；实验二把 `rm` 与 `df` 之间的因果拆成两道闸——目录链接数和打开文件描述引用；实验三把 0.3.16 与 0.3.18 的结论落到 `EPERM`、`EEXIST` 和一次 `setxattr` 上。如果只记住一件事，那就是：关于文件的争论，先跑一条取证命令，把现象翻译成 inode 号、链接数、fd 引用和返回值，再下结论。

::: method 即时自测 · 0.3.19
**Q1（记忆）** `unlink` 返回 0 之后，数据块一定消失了吗？判断「真正释放」要同时看到哪两个计数归零？

**Q2（辨析）** `rm` 成功、`df` 不降，实验二的哪几步解释了这个现象？这时为什么不能用 `ln` 把文件名字救回来？

**Q3（应用）** 生产机 `/var` 报满，`sudo du -x` 各层加起来远小于 `df` 的已用。按本节工具写出三步取证，并说明每步看到什么算命中。

**Q4（辨析）** 实验三 A 里如果看到的是 `newfstatat` 加 `rename` 而不是带 `RENAME_NOREPLACE` 的 `renameat2`，说明什么？写脚本的人应得出什么结论？

::: sol 答案
**A1** 不一定。`unlink` 只删目录项；要「目录链接数」与「打开文件描述的引用数」都归零，内核才回收 inode 与块。前者看 `stat -c %h` 或 `lsof +L1` 的 NLINK 列，后者看 `/proc/$PID/fd` 里还有没有指向它的链接。
**A2** 第 2 至 4 步：还有进程持有 fd（实验里是 fd 9），inode 的引用没归零，块仍被占用；`df` 数的是分配块，所以不动。链接数已为 0 的文件不能再 `link()` 挂回名字——路径那一层已经没了；内容可以经 `/proc/$PID/fd/N` 读出或截断。
**A3** ① `sudo lsof +L1`：列出 NLINK 为 0 的打开文件即命中「已删除但仍打开」，最常见的是日志被 `rm` 而服务没重开；② `sudo du -x` 对照 `findmnt`：确认没漏掉别的挂载点、没因权限跳读；③ `df -i`：块没满但新文件建不出来时，是 inode 耗尽（0.3.13）。每步留下输出再进下一步。
**A4** 说明这版 coreutils 没有使用 `RENAME_NOREPLACE`（旧版，或该系统不支持这个标志），`mv -n` 回退成先检查再改名两步。结论：可移植脚本不能把 `mv -n` 当原子操作（要么全做完，要么在别人眼里完全没做过，中间状态不可见）依赖；要「不覆盖地原子发布」，按 0.3.18 直接用 `renameat2` 并处理 `EOPNOTSUPP`，回退到 `link` 加 `unlink`。
:::
:::

## 0.3.20 三个可运行脚本 {#sec-0.3.20}

这一节回答：本章的 `find`、`xargs`、链接与占用结论，怎样压成三个敢在生产机上跑的脚本？

::: preview 先抓住一件事
三个脚本对应三类真实故障：目录无限膨胀要按天清理、链接在复制迁移中被打断、磁盘告警时要快速指认占用者。它们共用同一条安全骨架：`set -euo pipefail`、默认试运行、危险路径先拒绝、文件名一律 NUL 分隔。怎么最小限度地测它们，看本节末尾「怎么测它」。
:::

以下脚本面向 Ubuntu 24.04 的 GNU coreutils/findutils，放在 `~/bin/` 并 `chmod +x`。每个都先用 `bash -n` 做语法检查；涉及删除的先试运行。

### 脚本一：`safe-clean.sh`——按天数清理，默认试运行

**这类故障长什么样。** 日志与缓存目录只进不出，`df` 报警时有人临时手写 `find /var/log -mtime +30 -delete`：要么漏了 `-xdev` 删穿挂载点（0.3.14），要么被带空格的路名咬一口（0.3.7），要么一次删掉了正在被进程写的文件（0.3.19 实验二）。`safe-clean.sh` 把这些坑固化成默认行为——不显式给 `-f`，就只打印候选清单。

```bash
#!/usr/bin/env bash
# safe-clean.sh — 清理目录下超过 N 天的普通文件
# 用法: safe-clean.sh [-n] [-f] [-x] [-P N] -d DIR -m DAYS
set -euo pipefail

usage() { printf 'usage: %s [-n] [-f] [-x] [-P N] -d DIR -m DAYS\n' "${0##*/}" >&2; }
die()   { printf 'error: %s\n' "$*" >&2; exit 2; }

dry_run=1 xdev=() jobs=1 dir='' days=''
while getopts ':nfxd:m:P:h' opt; do
    case $opt in
        n) dry_run=1 ;;
        f) dry_run=0 ;;   # 显式确认真删
        x) xdev=(-xdev) ;;
        d) dir=$OPTARG ;;
        m) days=$OPTARG ;;
        P) jobs=$OPTARG ;;
        h) usage; exit 0 ;;
        :) die "option -$OPTARG requires an argument" ;;
        \?) die "unknown option -$OPTARG" ;;
    esac
done
shift $((OPTIND - 1))

[[ -n $dir && -n $days ]] || { usage; exit 2; }
[[ -d $dir ]] || die "not a directory: $dir"
[[ $days =~ ^[0-9]+$ ]] || die "DAYS must be a non-negative integer"
[[ $jobs =~ ^[1-9][0-9]?$ ]] || die "-P must be 1..99"

# 拒绝明显的危险根目录；realpath -e 要求路径存在
root=$(realpath -e -- "$dir") || die "cannot resolve: $dir"
case $root in
    /|/usr|/etc|/var|/home|/root|/boot|/dev|/proc|/sys)
        die "refusing to clean $root" ;;
esac

# 空数组在 bash 5.2 下可直接展开；旧版本用 ${xdev[@]+"${xdev[@]}"}
mapfile -d '' -t victims < <(
    find "$root" ${xdev[@]+"${xdev[@]}"} -type f -mtime +"$days" -print0 2>/dev/null
)

trap 'printf "interrupted after %d candidates\n" "${#victims[@]}" >&2; exit 130' INT
trap 'printf "terminated after %d candidates\n" "${#victims[@]}" >&2; exit 143' TERM

printf 'root=%s days=%d candidates=%d dry_run=%d jobs=%d\n' \
    "$root" "$days" "${#victims[@]}" "$dry_run" "$jobs"

if (( dry_run )); then
    for f in "${victims[@]}"; do printf 'would remove %q\n' "$f"; done
    exit 0
fi

(( ${#victims[@]} == 0 )) && exit 0
printf '%s\0' "${victims[@]}" |
    xargs -0 -r -n1 -P"$jobs" rm -f --
printf 'removed %d files\n' "${#victims[@]}"
```

最关键的三行。其一，`dry_run=1` 是初始值，只有显式 `-f` 才置 0——「先跑一遍看看」是脚本的责任，不是运维的记忆。其二，`realpath -e -- "$dir"` 加危险根黑名单：变量为空或写错成 `/etc` 这类路径时，脚本先拒绝自己，而不是等 `find` 跑起来。其三，`mapfile -d ''` 按 NUL 收清单、`xargs -0 -r -n1 -P` 按 NUL 消费——文件名里的空格、换行、引号都穿不过 NUL 分隔（0.3.7、0.3.15）。另外，`${xdev[@]+"${xdev[@]}"}` 兼容旧 bash 的空数组展开；`trap` 在中断时只报告候选数、不假装成功；`-x` 让 `find` 加 `-xdev`，不跨挂载点。并发删除的顺序不确定，但每个 `rm` 只作用于一个路径，互不依赖。

### 脚本二：`link-audit.sh`——悬空链接、硬链接与环

**这类故障长什么样。** 大版本升级或 `rsync -a` 迁移之后，`/usr/lib`、`/etc/alternatives` 里出现指向不存在目标的悬空链接，服务启动报 `No such file or directory`；或者 `cp -r` 把硬链接组展开成多份，改一个不动其余（0.3.4、0.3.17）。`link-audit.sh` 全程只读，盘点这三样：悬空链接、硬链接组、不可解析的链接（环或权限问题）。

```bash
#!/usr/bin/env bash
# link-audit.sh — 审计符号链接与硬链接；只读
set -euo pipefail
root=${1:-.}
[[ -d $root ]] || { printf 'not a directory: %s\n' "$root" >&2; exit 2; }

printf '== dangling symlinks ==\n'
while IFS= read -r -d '' link; do
    [[ -e $link ]] || printf '%q -> %q\n' "$link" "$(readlink -- "$link")"
done < <(find "$root" -xdev -type l -print0 2>/dev/null)

printf '== hard links (nlink > 1) ==\n'
find "$root" -xdev -type f -links +1 -printf '%i %n %p\n' 2>/dev/null | sort -n

printf '== symlink loops / unresolvable ==\n'
while IFS= read -r -d '' link; do
    if ! readlink -f -- "$link" >/dev/null 2>&1; then
        printf '%q\n' "$link"
    fi
done < <(find "$root" -xdev -type l -print0 2>/dev/null)
```

最关键的三行。其一，`[[ -e $link ]]`：`-e` 会跟随符号链接去测目标存在不存在，测不到就是悬空——这是判定悬空的核心，换成 `-L` 反而只测链接本身。其二，`find ... -type f -links +1 -printf '%i %n %p\n' | sort -n`：按 inode 号排序后，同一硬链接组的行自动相邻，链接数与成员一目了然。其三，用进程替换把 `find -print0` 的结果喂给 `while` 循环：循环留在当前 shell（管道最后一段在子 Shell 会丢变量，见 [0.5](ch05.md)），`-print0` 保证怪文件名不拆行。`readlink -f` 失败既可能是环，也可能是权限不足；脚本把它们归为「不可解析」，需要区分时看 `readlink` 的 stderr。

### 脚本三：`disk-report.sh`——按块与按表观大小排大文件

**这类故障长什么样。** 夜里磁盘告警，你要在五分钟内回答「谁占的」。`du -sh *` 会被带空格的名字噎住，`ls -lS` 排的是表观大小——稀疏文件与硬链接去重会让你指错人（0.3.13）。`disk-report.sh` 是只读报表，把两种口径分开列：按分配块（`du`）与按字节（`find %s`）。

```bash
#!/usr/bin/env bash
# disk-report.sh — 只读磁盘报表；GNU coreutils/findutils
set -euo pipefail
root=${1:-/var}
top=${2:-20}
[[ -d $root ]] || { printf 'not a directory: %s\n' "$root" >&2; exit 2; }
[[ $top =~ ^[1-9][0-9]*$ ]] || { printf 'top must be positive\n' >&2; exit 2; }

printf '== filesystem ==\n'
df -hT -- "$root" 2>/dev/null || df -h -- "$root"

printf '== top %d files by apparent size ==\n' "$top"
find "$root" -xdev -type f -printf '%s %p\0' 2>/dev/null |
    sort -z -nr | head -z -n "$top" |
    while IFS= read -r -d '' rec; do
        size=${rec%% *}; path=${rec#* }
        printf '%12s  %q\n' "$(numfmt --to=iec --suffix=B -- "$size")" "$path"
    done

printf '== top-level dirs by allocated bytes ==\n'
du -x -B1 --max-depth=1 -- "$root" 2>/dev/null | sort -nr | head -n "$top" |
    while read -r bytes path; do
        printf '%12s  %s\n' "$(numfmt --to=iec --suffix=B -- "$bytes")" "$path"
    done
```

最关键的三行。其一，`-printf '%s %p\0'`：把「大小 + 路径」绑定成一条 NUL 记录，路径里再怪也不拆行。其二，`sort -z -nr` 配 `head -z`：对 NUL 记录按数值前缀排序，取前 N 条时记录仍完整。其三，`du -x -B1 --max-depth=1`：只统计本文件系统的分配块、按字节输出。`du` 数块、`find %s` 数字节，两者对不上是常态——稀疏文件、硬链接去重、块对齐都会造成差（0.3.13）；脚本把两个口径分开列，就是防止混着用。

### 0.3.20 怎么测它

三个脚本共用一条最小验证路径，全程在临时目录里，不碰真实数据。

第一档，语法。`bash -n` 只做解析、不执行，改完脚本先过这一关：

```bash
bash -n ~/bin/safe-clean.sh
bash -n ~/bin/link-audit.sh
bash -n ~/bin/disk-report.sh
```

第二档，沙箱行为。造一批可控的旧文件和一个悬空链接，看三个脚本各说什么：

```bash
d=$(mktemp -d)                          # 随机路径的一次性目录
mkdir -p "$d/sub"
touch -d '40 days ago' "$d/old.log" "$d/sub/ancient.log"
touch "$d/new.log"
ln -s missing-target "$d/broken"
~/bin/safe-clean.sh -d "$d" -m 30       # 试运行：两个旧文件进候选清单
~/bin/safe-clean.sh -f -d "$d" -m 30    # 显式确认真删
find "$d" -type f                       # 预期只剩 new.log；broken 是链接，不算普通文件
~/bin/link-audit.sh "$d"                # broken 会同时出现在悬空段与不可解析段
~/bin/disk-report.sh "$d" 5             # 只读报表，传沙箱目录即可
rm -rf -- "$d"
```

`link-audit.sh` 里一个悬空链接出现在两段是设计如此，不是重复计数：`-e` 测出目标不存在，`readlink -f` 又拒绝为它构造规范路径。第三档才是生产：先试运行、逐行看候选清单，再用 0.3.19 的 `sudo lsof +L1` 确认清单里没有正在被进程写的文件，最后才允许自己加 `-f`。

::: errata 关于三个脚本的误解
1. **「默认试运行等于永远不会误删」**——试运行打印的只是那一刻的候选快照；等你加上 `-f` 再执行时，目录可能已变。候选很多时，执行前再跑一次试运行核对。
2. **「`link-audit.sh` 报了不可解析就是链接成环」**——目标目录缺读权限同样会让 `readlink -f` 失败；要区分时看它的 stderr，再用 `namei -l` 定位卡在哪一级（0.3.2）。
3. **「`disk-report.sh` 里两个口径对不上说明脚本坏了」**——恰恰相反，对不上是常态；脚本分两段列，就是为了逼你先问「数的是字节还是块」。
:::

这三个脚本覆盖了本章的四类边界：空变量与危险路径、带空格/换行的文件名、中断信号、并发删除。真正上线前还要补日志、锁与保留策略，见 [0.8](ch08.md) 的 `backup.sh`。

### 0.3.20 小结

`safe-clean.sh` 把「先看清再动手」写成默认值，`link-audit.sh` 把链接的三种坏状态变成一次只读盘点，`disk-report.sh` 把占用报表按字节与块分成两个口径；测试都从 `bash -n` 与临时目录开始。如果只记住一件事，那就是：敢在生产机上跑的脚本，靠的不是作者细心，而是默认值安全。

::: ex 例 0.3.1 · 删掉一个名字，文件还在 {#ex-0.3.1}
`ln a.txt b.txt; rm a.txt; cat b.txt` 仍然能读到内容。

先猜：`rm` 删的到底是什么？

判读：`rm` 删的是**目录项**（名字 → inode 的链接），inode 上的链接计数减一；只要计数不为 0、也没有进程打开它，数据才真正释放。`ls -li a.txt b.txt` 会看到两行同一个 inode 号——这就是硬链接与文件的区别。软链接 `ln -s` 则是另一个 inode，里面存着目标路径。

**判据**：`stat -c '%i %h' file` 看 inode 号与链接计数。

## 0.3.21 本章小结 {#sec-0.3.21}

这一节回答：两遍走完，这一章到底留下了什么？

::: preview 先抓住一件事
第一遍你会用目录树、`ls`、链接、`find`/`xargs`、`du` 把活干对；第二遍你能用 dentry、inode 计数、时间戳、`renameat2` 与 xattr 讲清边界；最后实验与脚本把结论压成能复现的动作。逐项自检去 [学习目标自检表](ch03-checklist.md)，不在这里打勾。
:::

第一遍只要求你用命令把活干对。目录是一棵挂载树：配置在 `/etc`、可变数据在 `/var`、程序在 `/usr`、内核投影在 `/proc` 与 `/sys`；usrmerge 之后 `/bin` 只是指向 `/usr/bin` 的链接（0.3.1、0.3.9）。路径不是字符串比较，是从 `/` 或 cwd 出发的逐段问路，`..`、符号链接、挂载点都会改变落点；打不开先跑 `namei -l`（0.3.2、0.3.10）。

这一遍的操作口诀是三句话。`ls -l` 的七列里最常被忽略的是链接数，`ls -li` 的 inode 列让硬链接一眼现形：硬链接是目录表里另一行指向同一张档案卡，软链接是内容写着别处路径的特殊文件、会悬空（0.3.3、0.3.4）。`cp` 默认重建 inode、只带走一部分元数据；`mv` 同盘只改目录项、跨盘退化成复制加删除；`rm` 只是把名字从目录里摘掉（0.3.5）。批量活交给 `find` 筛、`xargs -0` 递、`du` 数块而 `ls` 数字节（0.3.6–0.3.8）。

第二遍回到内核看结构。一条路径在内核里经 dentry 逐段解析，最后落到 inode；`stat` 的字段各有维护者——写改 mtime，改权限或属主只动 ctime，读动 atime 且可以推迟，创建时间要靠 `statx` 才挖得到（0.3.10、0.3.11）。类型列分普通文件、目录、链接、设备节点、socket、FIFO；`/proc`、`/sys` 这类虚拟文件不在磁盘上占块（0.3.12）。

边界也在这第二遍里。「一个文件吃多少」由 `st_size` 与 `st_blocks` 两个口径回答，稀疏文件让两者差出几个数量级，`df -i` 盯的是另一种满——inode 用完时块还很空（0.3.13）。`find` 表达式是短路求值：不写括号时 `-o` 的优先级会让 `-delete` 多删一整侧（0.3.14）；`xargs` 用 NUL 分隔参数，退出码 123、124、127 各指一类失败（0.3.15）。元数据分三层：`chmod` 改 mode，`setfattr` 改挂在 inode 上的键值对，`chattr` 改 inode 标志；`access` 与 `open` 是两次独立解析，中间的时间窗就是 TOCTOU（0.3.16）。

复制与删除的最后一组结论共用同一副骨架。`cp`、`rsync`、`tar` 的选项矩阵只回答两件事：哪些元数据要带过去，删除以哪边为准（0.3.17）。`mv`、`renameat2`、`rm` 回答另外两件事：改名什么时候是原子的，删除之后块什么时候才真正归还（0.3.18）。

最后压成能力。0.3.19 的三个实验让争论可以判定：`strace` 把一条命令翻译成系统调用与返回值，`lsof +L1` 与 `/proc/PID/fd` 抓住「已删除但仍打开」的中间态，`ls -li` 与 `stat` 给出身份。0.3.20 的三个脚本把安全默认写成模板：默认试运行、危险根拒绝、文件名 NUL 分隔，测试从 `bash -n` 与临时目录开始。

下次遇到文件问题，不必重翻本章，按症状选工具：打不开，`namei -l` 问路；想知道「它是什么」，`stat` 看字段；数字对不上，先分清字节还是块，再 `du -x` 对照 `df`；删了不腾地方，`sudo lsof +L1`；操作被拦下，`strace` 看错误码。这几件东西串起来，就是一条能指认的链路。

### 0.3.21 小结

第一遍把命令用对，第二遍用 dentry、inode 计数与原子性讲清为什么，实验和脚本把两者变成能复现的动作与敢上线的模板。逐项自检在 [学习目标自检表](ch03-checklist.md)，这里不收尾清单。如果只记住一件事，那就是：**先翻译，再争论**——把现象翻译成 inode 号、链接数与打开的 fd，文件系统的问题就再也没有玄学。

::: method 即时自测 · 0.3.21
**Q1（辨析）** `ls -li` 显示 `a` 与 `b` 的 inode 相同、链接数为 2；`c` 的 inode 不同、类型是 `l`。删除 `a` 后，`b` 和 `c` 还能读吗？

**Q2（应用）** 一条命令 `find /data -type f -mtime +30 -delete` 在生产机上执行后，发现误删了挂载在 `/data/backup` 的 NFS 上的文件。问题出在哪里？怎样避免？

**Q3（辨析）** `du -sh /var/log` 显示 2 GB，`df -h /var` 显示已用 20 GB，可能的原因有哪些？

**Q4（记忆）** 为什么 `find ... -print0 | xargs -0 ...` 比 `find ... | xargs ...` 安全？举一个会出错的文件名。

::: sol 答案
**A1** `b` 能读：它与 `a` 是同一 inode 的两个硬链接，删除 `a` 只是链接数从 2 变 1，数据仍在。`c` 是符号链接，若它指向 `a`，删除 `a` 后变成悬空链接，读取报 `ENOENT`；若指向 `b` 或其他仍存在的路径，则正常。用 `readlink c` 看目标。

**A2** `find` 默认会跨挂载点，`/data/backup` 是另一个文件系统，也被遍历并删除。加 `-xdev`（或 `-mount`）只在本文件系统内查找；更稳的做法是先 `-print` 审核、限定 `-maxdepth`、并在测试环境跑一遍。删除前还应确认备份与快照。这正是 0.3.20 脚本里 `-x` 与试运行默认值的由来。

**A3** ① `/var` 下还有其他大目录（`/var/lib`、`/var/cache`）；② 有已删除但仍被进程打开的文件（`lsof +L1`）；③ 文件系统保留块（ext4 默认 5%，`tune2fs -m`）；④ `du` 因权限不足跳过了部分目录（用 `sudo`）；⑤ 挂载了其他文件系统，`df` 统计的是整个 `/var` 所在分区；⑥ 快照/CoW 占用未计入 `du`。

**A4** 默认 `xargs` 按空白分词，文件名含空格会被拆成多个参数；含换行、引号、反斜杠时更糟。`-print0` 用 NUL 分隔，`-0` 按 NUL 解析，只有 NUL 不能出现在文件名中。会出错的名字：`my report 2024.txt`（被拆成三个参数）、`a\nb.txt`（被当成两个文件）。
