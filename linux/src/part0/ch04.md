上一章反复出现 `-rw-r--r--`，但只把它当成一列。这一章把它拆开：九个权限位加三个特殊位，配合文件的 UID/GID、进程的 euid/egid、补充组、ACL 与 capability，共同决定「这次 `open` 能不能成功」。

Linux 的权限模型有两层。第一层是传统的 **DAC**（discretionary access control）：文件属主自己决定谁能读写。第二层是 **LSM**（Linux Security Modules，如 AppArmor、SELinux）：系统策略在 DAC 之后再判一次。本章主要讲 DAC，因为日常排障 90% 的 `Permission denied` 出在这一层；LSM 只在第 3 篇展开。

权限问题的难点不在记八进制，而在**判定顺序**与**边界**。同一个文件，属主、组成员、ACL 用户、root、带 capability 的程序，看到的结论可能不同。把顺序记错，就会在错误的方向上改权限。

## 0.4.1 一次 `Permission denied` 的判定顺序 {#sec-0.4.1}

这一节回答：同一条 `Permission denied`，怎样按顺序判断是文件 mode、路径上的目录 `x`、ACL、capability、挂载选项、immutable 属性还是 LSM 拦的？

::: preview 先抓住一件事
权限不是一道门，是一串门：mode、目录 `x`、ACL、capability、挂载 `ro`/`noexec`、immutable、LSM，任何一层说「不」，内核都只回同一个错误码 `EACCES`（也就是 `Permission denied`）。排查从最便宜的证据开始：先 `id` 确认身份，再 `namei -l` 逐段看路径，最后才怀疑策略层。
:::

先看一个真实现象：`cat /srv/data/report.csv` 报 `Permission denied`，而 `ls -l` 显示 `-rw-r----- alice data`，你正好在 `data` 组里。文件明明对组可读，为什么还是被拒？答案常常不在文件本身，而在路径上的某一级目录。

::: def 定义 0.4.1 · 访问判定（DAC） {#def-0.4.1}
进程访问文件时，内核用进程的**有效 UID/GID**（euid/egid）与**补充组**（supplementary groups），对照文件的 mode、ACL 与属主关系，依次判断：root 特殊处理 → 属主 → 具名 ACL 用户 → 组类（含 mask）→ 其他。第一个命中的类别决定结果，不再往下看。
:::

判定顺序可以压缩成一张图：

<pre class="layout">
open("/srv/data/report.csv", O_RDONLY)
        │
        ├─ euid == 0 ? ──是──→ 允许（普通文件仍需至少一个 x 位才可执行）
        │
        ├─ euid == 文件属主 ? ──是──→ 看 owner 三位（或 ACL user::）
        │
        ├─ ACL 中有 euid 的具名条目 ? ──是──→ 看该条目 & mask
        │
        ├─ egid/补充组匹配属组，或 ACL 具名组匹配 ? ──是──→ 看 group 三位（或条目 & mask）
        │
        └─ 其他 ──→ 看 other 三位
                      │
                      └─ 通过 DAC 后，LSM（AppArmor/SELinux）再判一次
</pre>

这张图的读法是：**类别匹配优先于权限位**。如果进程是文件属主，就只看 owner 三位，即使 group 或 other 给了更多权限也不生效。一个常见现象：文件 `----r----- alice dev`，alice 是属主且在 dev 组里，她仍然读不了——因为属主类别先命中，owner 是 `---`。

root 也不是无条件。root 可以绕过读写权限，但对普通文件执行时，仍要求至少一个执行位；只读文件系统、immutable 属性（`chattr +i`）、LSM 策略都能挡住 root。`sudo` 拿到的是 root 的 euid，不是「绕过所有检查」的魔法。

排查权限，先看路径上每一级目录的 `x`：

```bash
namei -l /srv/data/report.csv
# f: /srv/data/report.csv
# drwxr-xr-x root root /
# drwxr-xr-x root root srv
# drwxrwx--- root data data
# -rw-r----- alice data report.csv
```

`namei -l` 逐段列出目录权限。上例中，如果调用者不在 `data` 组，即使文件 other 有读权限，也会在 `/srv/data` 这一级被拦住——目录没有 `x`，就无法到达里面的 inode。这是「文件权限明明有，为什么还是 denied」的第一大原因。

第二大原因是 LSM：DAC 全对，策略层再拦一次（[0.4.9](#sec-0.4.9) 的第 5 步）。把它展开成可操作的动作，先分清这台机器用的是哪个：

- **Ubuntu 默认 AppArmor**：`sudo aa-status` 看 profile 数量与 enforce/complain 模式；拒绝记录在 `journalctl -k | grep -i apparmor`（`DENIED`）。临时把某个 profile 转成「只记录不拦截」用 `sudo aa-complain /usr/bin/foo`（`apparmor-utils` 包），确认后 `aa-enforce` 改回。
- **RHEL/Fedora 默认 SELinux**：判定与修复只要五条命令：

| 命令 | 回答什么 |
|:--|:--|
| `getenforce` | `Enforcing`（拦截）/ `Permissive`（只记录不拦截）/ `Disabled` |
| `setenforce 0` / `1` | 临时切 Permissive/Enforcing；持久改 `/etc/selinux/config` |
| `ls -Z /var/www/html` | 文件的安全上下文；`cp -r` 复制会丢标签（0.3.17） |
| `restorecon -Rv /var/www` | 按策略恢复标签，`cp -r` 后服务起不来的第一修法 |
| `ausearch -m avc -ts recent \| audit2why` | 最近的拒绝记录与原因翻译（需 `auditd`） |

「DAC 正常但仍 denied」的定位顺序：`setenforce 0` 后能跑通，基本就是 SELinux 标签或策略问题。这只用于定位：确认后立即 `setenforce 1`，用 `restorecon` 或改标签解决，不要长期 Permissive 运行。LSM 的内核钩子与策略模型在[第 3 篇](../part3/ch04.md)展开，这里只需要会判定「是不是它拦的」。

::: note 非科班补一层：七层各管什么
- **DAC mode**：文件自己的九个位，属主说了算。`ls -l` 第一列、`stat -c %a`。
- **目录 `x`**：路径上每一级目录都要能穿过；缺一级，后面的权限再宽也没用。`namei -l`。
- **ACL**：给单个用户或组额外开的条目，存在扩展属性里。`ls -l` 末尾的 `+` 是线索，`getfacl` 看明细。
- **capability**：进程手里的特权小块，`CAP_DAC_OVERRIDE` 能越过读写位。`capsh --print`。
- **挂载选项**：`ro` 让整个文件系统只读，`noexec` 让可执行文件也起不来。`findmnt -T`。
- **immutable**：inode 上的标志，连 root 也改不了内容。`lsattr`。
- **LSM**：DAC 全过之后再判一次的策略层，AppArmor 或 SELinux。`aa-status`、`ausearch`。
:::

这七层里，mode 和目录 `x` 用 `chmod` 就能改；ACL 要 `setfacl`，capability 要 `setcap`，挂载选项、immutable、LSM 各有各的入口。对后五层敲 `777` 一点作用都没有，所以下一步是先取证，再动手。

::: errata 关于判定顺序的四个误解
1. **「`chmod 777` 能解决所有拒绝」**——它只改 DAC 的九个位，目录 `x`、ACL mask、`ro` 挂载、`noexec`、immutable、LSM 都不看这九位。
2. **「文件权限对了就能读」**——路径上任何一级目录缺 `x`，`open` 在解析路径时就失败，报错和文件本身无关。
3. **「root 什么都能做」**——root 能绕过读写位，但普通文件仍要有一位 `x` 才能执行；`ro` 挂载、immutable、LSM 也照样拦。
4. **「报错信息会告诉你是哪一层」**——内核只回 `EACCES`，七层共用这一个错误码；分层是你用命令一层层排除出来的。
:::

### 0.4.1 小结

一次拒绝可能出在七层中的任何一层，而内核只给你一个 `EACCES`。判定顺序是先身份（`id`）、再路径（`namei -l`）、再 mode 与 ACL，最后才是 capability、挂载选项与 LSM。如果只记住一件事，那就是：先找是哪一层拦的，只改那一层，别用 `777` 碰运气。

## 0.4.2 mode 的十二位 {#sec-0.4.2}

这一节回答：`ls -l` 的十个字符和 `stat -c %a` 的四位八进制，怎样逐位对上？`4755`、`2755`、`1777` 各是什么组合？

::: preview 先抓住一件事
mode 一共十二位：三个特殊位（setuid、setgid、sticky）加九个权限位。`ls -l` 只印十个字符，特殊位藏在三组 `x` 的位置上；`stat -c %a` 用四位八进制把它们露出来。读 mode 的顺序是：先看有没有第四位，再按三位一组读 `rwx`。
:::

`ls -l` 第一列有十个字符：第一个是类型，后九个是权限。`stat -c %a` 给八进制，可能多出一位特殊位。

| 位（八进制） | 名称 | 对文件 | 对目录 |
|:--|:--|:--|:--|
| `4000` | setuid | 执行时 euid 变为文件属主 | 在部分系统上有特殊语义，Linux 上一般忽略 |
| `2000` | setgid | 执行时 egid 变为文件属组 | 新建文件继承目录的组；新建子目录继承 setgid |
| `1000` | sticky | 历史上表示「常驻内存」，现代 Linux 忽略 | 只有文件属主、目录属主或 root 能删除/重命名其中的文件 |
| `0400/0200/0100` | owner r/w/x | 属主读/写/执行 | 属主列出/增删/进入 |
| `0040/0020/0010` | group r/w/x | 属组读/写/执行 | 属组列出/增删/进入 |
| `0004/0002/0001` | other r/w/x | 其他人读/写/执行 | 其他人列出/增删/进入 |

九位权限的八进制换算是把每组 `rwx` 看成三位二进制：`r=4`、`w=2`、`x=1`。`rwxr-x---` = `750`；`rw-r--r--` = `644`；`rwxrwxrwt` = `1777`。

特殊位在 `ls -l` 里的显示规则：

| 有执行位 | 无执行位 | 含义 |
|:--|:--|:--|
| `s`（owner） | `S` | setuid |
| `s`（group） | `S` | setgid |
| `t`（other） | `T` | sticky |

```bash
stat -c '%A %a %n' /usr/bin/passwd /tmp /usr/bin/wall
# -rwsr-xr-x 4755 /usr/bin/passwd
# drwxrwxrwt 1777 /tmp
# -rwxr-sr-x 2755 /usr/bin/wall
```

`/usr/bin/passwd` 的 `s` 在 owner 位：普通用户执行它时，euid 变成 root，才能写 `/etc/shadow`。`/tmp` 的 `t` 在 other 位：任何人都能在里面建文件，但只有属主能删自己的文件。`wall` 的 `s` 在 group 位：执行时 egid 变成 `tty` 组，才能写终端设备。

三个常见值拆开看：

| 八进制 | 拆法 | `ls -l` | 常见对象 |
|:--|:--|:--|:--|
| `4755` | `4000` + `755` | `-rwsr-xr-x` | `/usr/bin/passwd`、`/usr/bin/sudo` |
| `2755` | `2000` + `755` | `-rwxr-sr-x` | `/usr/bin/wall`；目录上显示为 `drwxr-sr-x` |
| `1777` | `1000` + `777` | `drwxrwxrwt` | `/tmp`、`/var/tmp` |

::: note 非科班补一层：三个特殊位各管一件事
- **setuid**：执行这个程序时，进程的 euid 换成文件属主。`passwd` 靠它写 `/etc/shadow`。
- **setgid**：对文件换 egid；对目录则让新建文件继承目录的组，团队共享目录靠它。
- **sticky**：只对目录有意义，限制「谁能删别人的文件」，`/tmp` 靠它。
:::

三个位都不改变「文件属于谁」，只改变「谁在执行、新建的东西归谁、谁能删」。这一点在 0.4.5 设置特殊位时还会用到。

::: errata 关于 mode 的四个误解
1. **「`ls -l` 十位就是十位权限」**——第一个字符是类型（`-`、`d`、`l`），权限只有九位，特殊位是叠印在 `x` 的位置上的。
2. **「`s` 是一种额外的权限位」**——`s` 表示 setuid/setgid 已设且该位本来有 `x`；大写 `S` 表示设了但没有 `x`，此时程序无法执行，特殊位也就落空。
3. **「`1777` 的 `1` 是属主的第一位」**——它是 sticky，独立于 `777`；`4755` 要读成 `4` 加 `755`，不是四千七百五十五。
4. **「目录上设 setuid 有用」**——Linux 忽略目录的 setuid；目录上真正有用的是 setgid（继承组）和 sticky（限制删除）。
:::

### 0.4.2 小结

mode 是十二位：三个特殊位加九个权限位；`ls -l` 把特殊位叠印在 `x` 上（`s`/`S`、`t`/`T`），`stat -c %a` 用四位八进制显示。`4755` 是 setuid 加 `755`，`2755` 是 setgid 加 `755`，`1777` 是 sticky 加 `777`。如果只记住一件事，那就是：先数 `stat` 的第四位，再去 `ls -l` 里找那个字母。

::: method 即时自测 · 0.4.2
**Q1（记忆）** `stat -c %a` 输出 `4755` 时，四个数字各是什么？`ls -l` 显示成什么？

**Q2（辨析）** `-rwSr--r--` 与 `-rwsr--r--` 有什么区别？前者执行时会提权吗？

**Q3（应用）** 目录 `/srv/dev` 要求「同组可读写、其他人不能进、新建文件自动继承 `dev` 组」，写出八进制与符号两种 `chmod` 写法。

::: sol 答案
**A1** `4` 是 setuid，`755` 是属主 `rwx`、属组 `r-x`、其他 `r-x`；显示为 `-rwsr-xr-x`。
**A2** 区别在属主有没有 `x`：`S` 表示 setuid 已设但属主没有执行位，`s` 表示两者都有。前者普通用户无法 `exec`，setuid 也就不会生效。
**A3** `chmod 2770 /srv/dev`；等价符号写法 `chmod u=rwx,g=rwxs,o= /srv/dev`，结果是 `drwxrws---`。
:::
:::

## 0.4.3 目录的 r、w、x 是三种不同能力 {#sec-0.4.3}

这一节回答：目录的 `r`、`w`、`x` 分别允许你做什么？为什么「能看见文件名」不等于「能打开文件」？

::: preview 先抓住一件事
目录的三种权限不是文件三种权限的翻版：`r` 管「看见哪些名字」，`w` 管「增删改名」，`x` 管「能不能走过去」。所以 `ls` 成功而 `cat` 失败，往往不是文件的问题，而是目录少了 `x`。
:::

目录也是文件，但权限含义不同：

| 权限 | 允许 | 不允许 |
|:--|:--|:--|
| `r` | 列出目录项名字（`ls dir`） | 看不到名字，但知道路径仍可能访问 |
| `x` | 进入目录、访问其中的 inode（`cd dir`、`cat dir/file`） | 无法到达目录内的任何文件 |
| `w` | 创建、删除、重命名目录项 | 不能修改目录项 |

::: note 非科班补一层：目录是一张名字表
把目录想成两列：左边是文件名，右边是 inode 号。`r` 是「能读这张表」，`w` 是「能增删改表里的行」，`x` 是「拿着名字走到对应那一行」。只有 `r` 没有 `x`，你能看到表上的名字，却走不到任何一个名字对应的文件。
:::

三个组合的典型现象：

- **只有 `r` 没有 `x`**：`ls dir` 能列出名字，但 `ls -l dir` 看不到属性，`cat dir/file` 报 `Permission denied`。这常被用来「隐藏内容但让人知道有哪些文件」，实际很少用。
- **只有 `x` 没有 `r`**：不能 `ls`，但如果知道文件名，可以 `cat dir/known-file`。这就是「目录的 x 是通行证」。
- **有 `w` 没有 `x`**：不能创建或删除，因为无法到达目录 inode；`w` 必须与 `x` 一起才有意义。

把第一种情况跑一遍，用 `nobody` 扮演「其他人」：

```bash
mkdir -p /tmp/dir-lab/secret && echo hello > /tmp/dir-lab/secret/a.txt
chmod 744 /tmp/dir-lab/secret             # 其他人只有 r，没有 x
sudo -u nobody ls /tmp/dir-lab/secret     # 能列出 a.txt
sudo -u nobody ls -l /tmp/dir-lab/secret  # 属性列变成 ?，stat 走不进去
sudo -u nobody cat /tmp/dir-lab/secret/a.txt
# cat: /tmp/dir-lab/secret/a.txt: Permission denied
```

三条命令的差别只在最后一步要不要穿过去：`ls` 读名字表，`ls -l` 还要对每个名字取属性，`cat` 要打开那个文件。同一个目录、同一个文件，三种结果，原因都在目录的 `x` 上。

删除文件看的是**目录的写权限**，不是文件的写权限。一个只读文件放在可写目录里，仍然可以被删除（`rm` 会提示，但 `rm -f` 直接删）。反过来，文件可写但目录不可写，删不掉。这是「为什么我不能删自己没权限的文件」的答案。

sticky 位把「删除权」从目录属主扩展到文件属主：`/tmp` 是 `1777`，任何人都能创建，但只有文件属主、目录属主（root）或 root 能删除别人的文件。共享目录需要「大家都能建，但不能互删」时，用 `1777` 或 `2770` + ACL。

::: errata 关于目录权限的四个误解
1. **「目录的 `r` 就是能进去」**——`cd` 要的是 `x`；只有 `r` 时能列名，不能进，也不能读里面的文件。
2. **「文件不可写就删不掉」**——删除改的是目录项，看目录的 `w` 加 `x`；sticky 只是再加一道属主检查。
3. **「`w` 可以单独给」**——没有 `x` 就到不了目录 inode，`w` 落不了地；给 `w` 必须同时给 `x`。
4. **「`ls -l` 里的问号是文件坏了」**——是目录缺 `x`，`stat` 走不进去，属性自然取不到。
:::

### 0.4.3 小结

目录的 `r` 读名字表，`w` 改名字表，`x` 才让你按名字走到 inode；缺哪一个，表现都不同。删除和重命名看目录的 `w` 加 `x`，与文件自身的 `w` 无关；sticky 再把删除限制到文件属主。如果只记住一件事，那就是：目录的 `x` 是通行证，没有它，`r` 只能看见名字。

::: method 即时自测 · 0.4.3

**Q2（辨析）** 文件 `-r--r--r--` 放在你拥有 `rwx` 的目录里，你能删除它吗？`rm` 为什么还会问一句？

**Q3（应用）** `/srv/www` 要让 nginx 按已知路径读文件、但不许列出目录清单，目录该给什么权限？

::: sol 答案

## 0.4.4 umask 与默认权限 {#sec-0.4.4}

这一节回答：新建文件和新目录的权限是谁算出来的？`umask` 在这条链路里减掉了哪些位？

::: preview 先抓住一件事
`umask` 不是「给你的权限」，是「扣掉的位」：普通文件从 `666` 出发，目录从 `777` 出发，逐位减去 umask 里为 1 的位。所以 `022` 得到 `644`/`755`，`077` 得到 `600`/`700`，`002` 得到 `664`/`775`。
:::

新建文件的权限不是「你想要的」，而是「默认值减去 umask」。规则：

- 普通文件默认 `666`（不给执行位）；
- 目录默认 `777`（需要执行位才能进入）；
- 最终权限 = `默认值 & ~umask`。

`umask` 是进程属性，Shell 内建命令修改的是当前 Shell 及其子进程的掩码。常见值：

| umask | 文件 | 目录 | 适用 |
|:--|:--|:--|:--|
| `022` | `644` | `755` | 系统默认，其他用户可读 |
| `027` | `640` | `750` | 团队共享但不对其他人开放 |
| `077` | `600` | `700` | 私有，仅属主 |
| `002` | `664` | `775` | 协作目录，同组可写 |

<div class="terminal" data-title="bash · 权限与 umask">
<pre><span class="p">&#36;</span> id
uid=1000(wang) gid=1000(wang) groups=1000(wang),27(sudo)
<span class="p">&#36;</span> umask
0002
<span class="p">&#36;</span> umask -S
u=rwx,g=rwx,o=rx
<span class="p">&#36;</span> mkdir -p /tmp/perm-lab &amp;&amp; cd /tmp/perm-lab
<span class="p">&#36;</span> touch default.txt &amp;&amp; mkdir default.dir
<span class="p">&#36;</span> ls -ld default.txt default.dir
-rw-rw-r-- 1 wang wang    0 Oct 17 11:02 default.txt
drwxrwxr-x 2 wang wang 4096 Oct 17 11:02 default.dir
<span class="p">&#36;</span> chmod 640 default.txt
<span class="p">&#36;</span> chmod u+x,g-w,o= default.txt
<span class="p">&#36;</span> ls -l default.txt
-rwxr----- 1 wang wang 0 Oct 17 11:02 default.txt
<span class="p">&#36;</span> namei -l /etc/shadow
f: /etc/shadow
drwxr-xr-x root root /
drwxr-xr-x root root etc
-rw-r----- root shadow shadow
</pre>
</div>

`umask 0002` 下，文件得到 `664`、目录得到 `775`。`chmod 640` 把文件设为 `rw-r-----`；`chmod u+x,g-w,o=` 再改成 `rwxr-----`。符号模式的三段分别对应 `u`/`g`/`o`，`+`/`-`/`=` 是加、减、精确设置。

`umask` 只影响新建，不改已有文件。要改已有目录树，用 `chmod -R` 或 `find -exec chmod`，但要想清楚：递归改权限会覆盖掉有意设置的 ACL 与特殊位。

系统级默认在 `/etc/login.defs`（`UMASK`）、PAM（`pam_umask`）与 systemd 的 `UMask=` 里。Ubuntu 普通用户常见 `0002`，root 是 `0022`。服务由 systemd 启动时，继承 unit 的 `UMask=`（默认 `0022`），不继承登录用户的 umask。

::: note 非科班补一层：umask 是取反再按位与
把数字写成二进制：`6=110`、`7=111`、`2=010`。`022` 取反后只看后九位是 `755`，`666 & 755 = 644`，这就是 `umask 022` 下新文件的权限。umask 里的 1 表示「这一位不要」，所以它只能清位，不能加位。

umask 的来源有三处，优先级从近到远：当前 Shell 里敲的 `umask` 命令 → 登录时读的 `/etc/profile`、`~/.bashrc`、`/etc/login.defs`（`pam_umask` 在会话建立时也会设一次）→ 服务由 systemd 启动时 unit 的 `UMask=`。前两处管你的交互 Shell，第三处管后台服务。
:::

::: errata 关于 umask 的四个误解
1. **「`umask 022` 表示给出 `022` 的权限」**——正好相反，它是扣掉 `022`，留下 `644`/`755`。
2. **「新文件可以带执行位」**——`touch`、重定向、编辑器创建普通文件时传的 mode 是 `666`，umask 只能减不能加，所以这样建出来的文件没有 `x`；要执行得再 `chmod +x`。
3. **「改了 `umask` 会改已有文件」**——只影响之后新建的文件和目录；已有对象要用 `chmod`。
4. **「所有进程都用我 Shell 的 umask」**——systemd 启动的服务继承 unit 的 `UMask=`（默认 `0022`），不继承你登录 Shell 的 `0002`。
:::

### 0.4.4 小结

新文件的权限是「默认值减 umask」：文件 `666 & ~umask`，目录 `777 & ~umask`；umask 的 1 位表示扣掉，所以它只能减不能加。umask 是进程属性，来自 Shell 命令、登录配置或 systemd unit，只影响之后创建的对象。如果只记住一件事，那就是：看到 `664`/`775` 先想到 `umask 002`，看到 `644`/`755` 先想到 `022`。

::: method 即时自测 · 0.4.4
**Q1（记忆）** `umask 027` 下，`touch a.txt` 与 `mkdir d` 分别得到什么权限？

**Q2（辨析）** `umask 000` 时，新建目录是 `777`，为什么新建普通文件是 `666` 而不是 `777`？

**Q3（应用）** 你的 Shell 里 `umask` 是 `002`，但 systemd 服务写出的文件是 `644`。为什么？怎么改？

::: sol 答案
**A1** 文件 `666 & ~027 = 640`（`rw-r-----`）；目录 `777 & ~027 = 750`（`rwxr-x---`）。
**A2** 用 `touch` 或重定向创建文件时传的 mode 是 `666`，`mkdir` 传的是 `777`；umask 只能把位清掉，不能凭空加出执行位。
**A3** 服务不继承登录 Shell 的 umask，继承 unit 的 `UMask=`，默认 `0022`。在 unit 里加 `UMask=0002`，然后 `systemctl daemon-reload` 并重启服务。
:::
:::

## 0.4.5 chmod、chown 与特殊位 {#sec-0.4.5}

这一节回答：`chmod` 的八进制与符号两种写法各适合什么场景？`chown` 为什么普通用户做不了？三个特殊位怎样设、边界在哪？

::: preview 先抓住一件事
`chmod` 八进制是整体赋值，符号是增量修改；`chown` 换属主需要 root 或 `CAP_CHOWN` 这项特权；setuid 改的是执行那一刻的 euid，而脚本上的 setuid 会被内核忽略。
:::

`chmod` 有两种语法：

```bash
chmod 750 file                  # 八进制，精确设置
chmod u=rwx,g=rx,o= file        # 符号，按类别设置
chmod g+w,o-rx file             # 符号，增量修改
chmod -R u+rwX,go-w dir         # X：只给目录和已有执行位的文件加 x
chmod --reference=ref file      # 复制另一个文件的 mode
```

大写 `X` 很实用：递归给目录加执行位，但不会把普通文本文件变成可执行。`chmod -R a+rX` 是共享只读目录的常见写法。

`chown` 改属主，`chgrp` 改属组，`chown user:group` 一次改两个：

```bash
sudo chown alice:dev /srv/app/config.yml
sudo chown -R www-data:www-data /var/www/site
sudo chgrp -R dev /srv/shared
```

风险与回滚：

- `chown -R` 会跟随命令行给出的符号链接，但默认不跟随目录内部的符号链接（GNU chown 默认 `-P`）。要明确行为，用 `-h`（改链接本身）或 `-L`（跟随所有链接）。
- 递归改属主会覆盖掉原本属于其他服务的文件，导致服务起不来。先 `find /var/www/site ! -user www-data -print` 看会影响哪些文件。
- 回滚要记录原始属主：`find /var/www/site -printf '%u:%g %p\n' > owners.bak`，需要时按文件恢复。

setuid/setgid 的写法：

```bash
chmod u+s /usr/local/bin/tool       # setuid
chmod g+s /srv/shared               # 目录 setgid：新文件继承组
chmod +t /srv/shared                # sticky
chmod 2770 /srv/shared              # setgid + rwxrwx---
chmod 4755 /usr/local/bin/tool      # setuid + rwxr-xr-x
```

目录 setgid 是团队协作最有用的特殊位：在 `/srv/shared` 下新建的文件自动属于 `dev` 组，不需要每个用户手动 `chgrp`。配合 `umask 002` 或默认 ACL，团队目录就能「同组可写、其他人不可见」。

setuid 为什么危险：它把「执行这个程序」变成「以文件属主身份执行」。程序里任何一个漏洞（缓冲区溢出、命令注入、路径穿越）都会直接变成属主权限。历史上大量本地提权漏洞来自 setuid 程序。现代做法是尽量不用 setuid root，改用：

- 细粒度 capability（下一节）；
- systemd 的 `User=`、`DynamicUser=`、`AmbientCapabilities=`；
- 需要特权的操作拆成一个小服务，通过 socket 或 D-Bus 暴露有限接口。

脚本上的 setuid 是另一回事。给一个 shell 脚本设 `4755`，`ls` 会显示 `s`，但执行时并不会提权：

```bash
printf '#!/bin/sh\nid\n' > /tmp/suid-demo.sh
chmod 4755 /tmp/suid-demo.sh
ls -l /tmp/suid-demo.sh
# -rwsr-xr-x 1 wang wang 22 ... /tmp/suid-demo.sh
/tmp/suid-demo.sh
# uid=1000(wang) gid=1000(wang) ...，euid 仍是 1000
```

原因在 `execve`：内核看到 `#!`，实际加载的是解释器（这里是 `/bin/sh`），setuid 位不属于解释器，而且 Linux 明确规定忽略脚本上的 setuid/setgid。即使把属主改成 root（`sudo chown root /tmp/suid-demo.sh`）再跑，`id` 仍显示你自己的 uid。要提权，只能用编译后的二进制，或者给程序加 capability。

::: note 非科班补一层：三个动作改的不是同一个东西
- `chmod` 改文件 mode，也就是「谁能对这个文件做什么」。
- `chown` 改文件的 UID/GID，所以需要 root 或 `CAP_CHOWN`；普通用户只能把自己文件的组改成自己所在的组。
- setuid/setgid 改的是「执行那一刻进程的 euid/egid」，不是文件身份；而且只在 `exec` 那一刻起作用，程序跑起来后与文件再无关系。
:::

::: errata 关于 chmod/chown 的四个误解
1. **「`chmod +s` 放在脚本上能提权」**——Linux 忽略脚本的 setuid/setgid；要提权得用二进制程序或 capability。
2. **「`chown` 普通用户也能改属主」**——需要 root 或 `CAP_CHOWN`；普通用户最多改自己文件的组，且必须是该组成员。
3. **「`chmod 4755` 一定生效」**——还要文件系统没挂 `nosuid`，文件本身有 `x` 位；`findmnt -T` 能看挂载选项。
4. **「`chmod -R 777` 是通用修法」**——递归改 mode 不改属主，也修不了 ACL、LSM 和挂载问题；给目录补执行位要用大写 `X`，别把文本文件变成可执行。
:::

### 0.4.5 小结

`chmod` 用八进制整体赋值、用符号做增量，递归给目录加执行位用大写 `X`；`chown` 换属主需要 root 或 `CAP_CHOWN`。setuid 改的是执行时的 euid，setgid 对目录是继承组，sticky 是限制删除，脚本上的 setuid 无效。如果只记住一件事，那就是：特殊位改的是「执行时是谁」，不是「文件属于谁」。

::: method 即时自测 · 0.4.5
**Q1（记忆）** `chmod 2750 file` 之后，`ls -l` 的权限串是什么？

**Q2（辨析）** 为什么给 shell 脚本设 setuid root 不能提权，给 C 程序设就可以？

**Q3（应用）** 你准备对 `/var/www/site` 执行 `chown -R www-data`，动手前该做什么？改错后先查什么？

::: sol 答案
**A1** `-rwxr-s---`：属主 `rwx`，属组 `r-s`（setgid，组执行位在），其他 `---`。
**A2** 内核 `exec` 脚本时实际加载的是 `#!` 后面的解释器，setuid 位不属于解释器，且 Linux 明确忽略脚本的 setuid；C 程序是 ELF，`exec` 时内核按文件属主设置 euid。
**A3** 动手前先记录并预览影响面：`find /var/www/site -printf '%u:%g %p\n' > owners.bak`，再 `find /var/www/site ! -user www-data -print`。改错后先看服务日志与 `namei -l`，按备份逐项恢复属主。
:::
:::

## 0.4.6 ACL：给「某个人」单独开权限 {#sec-0.4.6}

这一节回答：只想让 `alice` 读写、`bob` 只读，又不想为他们各建一个组、也不想复制文件时，`setfacl` 与 `getfacl` 怎么用？`mask` 为什么会把刚给的权限压小？

::: preview 先抓住一件事
mode 只把人分成属主、属组、其他三类；ACL（Access Control List，访问控制列表）是挂在文件上的「额外授权名单」，可以点名到某个人，存在文件的扩展属性里，不在 mode 里。`ls -l` 末尾的 `+` 说明有 ACL，而组三位显示的是 mask——这份名单的有效上限。
:::

上一节讲了 setuid 的两面性：一个程序越权，等于把整个 root 交出去。但更多时候要处理的不是「程序需要 root」，而是「某个人需要这个文件」。先看场景：`/srv/report/report.csv` 属主 `wang`、属组 `wang`，mode `640`；现在要 alice 读写、bob 只读、其他同事不可见。

建两个组，组会越积越多；复制两份文件，内容迟早分叉。ACL 的第三条路是直接点名：

```bash
# 允许 alice 读写，bob 只读
setfacl -m u:alice:rw-,u:bob:r-- report.csv

# 查看；-n 用数字显示 uid/gid（-p 是保留绝对路径的前导斜杠）
getfacl -n report.csv
# file: report.csv
# owner: wang
# group: wang
# user::rw-
# user:alice:rw-
# user:bob:r--
# group::r--
# mask::rw-
# other::---

# ls 的组权限位现在是 mask，末尾有 +
ls -l report.csv
# -rw-rw----+ 1 wang wang 0 Oct 17 11:10 report.csv
```

读法：`user::` 是属主那一档，与 mode 的 owner 三位等价；`user:alice:`、`user:bob:` 是具名用户；`group::` 是属组；`other::` 是其他。多出来的 `mask::` 不属于任何一个人，它是「组类」条目的上限。末尾那个 `+` 是提醒：这个文件的 mode 已经不完整，只看 `ls -l` 会误判。

::: def 定义 0.4.2 · POSIX ACL 与 mask {#def-0.4.2}
ACL 是挂在 inode 上的一组扩展条目，除 owner/group/other 外，还可以有具名用户（`user:alice:rw-`）与具名组（`group:dev:r-x`）。**mask** 是组类权限的上限，限制所有具名用户、具名组与 `group::` 的有效权限；owner 与 other 不受 mask 影响。`ls -l` 中组三位显示的就是 mask。
:::

`mask::rw-` 是当前 ACL 的上限。如果 `bob` 的条目是 `r--`，有效权限是 `r-- & rw- = r--`；如果 `alice` 是 `rwx`，有效权限被 mask 压成 `rw-`。要放开，显式改 mask：

```bash
setfacl -m m::rwx report.csv     # 放开 mask
setfacl -m m::r-- report.csv     # 收紧 mask，具名用户最多只读
```

`getfacl` 的 `effective:` 行会显示某条目经过 mask 后的实际权限。排查「ACL 明明给了 r，为什么还是 denied」时，先看 mask。

::: note 非科班补一层：ACL 存在哪、`ls` 为什么变样
- **ACL 是 xattr**。扩展属性（extended attribute，xattr）是「挂在文件上的键值对」。访问 ACL 存在 `system.posix_acl_access`，默认 ACL 存在 `system.posix_acl_default`。`setfacl` 底层调 `setxattr`；`getfattr -n system.posix_acl_access -e hex report.csv` 能看到一串十六进制结构。
- **只有三条基础条目时不占 xattr**。`user::`、`group::`、`other::` 这三条叫最小 ACL，内核直接拿 mode 存；一旦出现具名用户或具名组，才变成扩展 ACL，mode 的组三位改为显示 mask。
- **mask 求的是交集，不是并集**。条目写 `rwx` 只是「申请」，mask 写 `r--` 才是「批准」，生效的是两者按位与。`setfacl` 新增条目时会自动重算 mask，把它放大到所有组类条目的并集。
:::

目录的默认 ACL 让新建文件自动继承：

```bash
# 目录本身：dev 组可读写执行
setfacl -m g:dev:rwx /srv/shared
# 默认 ACL：以后在目录里新建的文件/子目录都继承
setfacl -d -m g:dev:rwx /srv/shared
setfacl -d -m u:alice:rwx /srv/shared

getfacl -n /srv/shared
# default:user::rwx
# default:user:alice:rwx
# default:group::r-x
# default:group:dev:rwx
# default:mask::rwx
# default:other::---
```

带 `default:` 前缀的条目就是**默认 ACL**（default ACL）：它不参与对 `/srv/shared` 本身的判定，只当「模板」用。在里面新建普通文件时，`default:` 条目转成该文件的访问 ACL；新建子目录时，既要转成访问 ACL，又原样留一份默认 ACL，于是模板继续往下传。

有一处和 0.4.4 不同：目录一旦有默认 ACL，新文件的权限就不再走「mode 减 umask」，而是「继承来的条目 & 创建时传入的 mode 参数」。所以团队目录设了默认 ACL 之后，别再用 umask 猜结果，直接 `getfacl` 看实际值。

默认 ACL 只影响新建对象，不改变已有文件。批量修复已有文件用 `setfacl -R -m ...`，但要注意 `-R` 会递归到所有子目录。

ACL 的运维细节：

- 备份与恢复：`getfacl -R /srv/shared > acls.bak`，恢复用 `setfacl --restore=acls.bak`。`tar --acls`、`rsync -A` 也能保留。
- 删除 ACL：`setfacl -b file` 删掉所有扩展条目与 mask；`setfacl -x u:alice file` 只删一条。
- 复制：`cp -p` 会保留 ACL；`cp -a` 也会；普通 `cp` 不保留。
- 文件系统支持：ext4、XFS、Btrfs 默认支持；tmpfs 支持；NFS 需要版本与挂载选项配合。`tune2fs -l` 的 `Default mount options` 里若有 `acl`，说明默认启用。

::: errata 常见误解
1. **「ACL 就是 mode 的另一种写法」**——ACL 是独立的 xattr；`chmod` 改的是 mode，有 ACL 时改的其实是 mask，不会碰具名条目。
2. **「给了 `u:alice:rwx` 就一定能写」**——还要过 mask；`getfacl` 的 `effective:` 行没写 `w`，就是被压掉了。
3. **「`ls -l` 的组三位是 `group::`」**——有 ACL 时它是 mask；`group::` 只在 `getfacl` 里看得到。
4. **「设了默认 ACL 就万事大吉」**——继承来的条目仍要与创建时传入的 mode 相与；`install -m 600` 建完会再 `chmod 600`，mask 被压空，具名条目等于全被屏蔽。
5. **「ACL 能解决路径问题」**——路径上每一级目录的 `x` 仍是前提，ACL 只作用于目标 inode。
:::

### 0.4.6 小结

mode 把人分成三类，ACL 在此基础上点名到具体用户与组；ACL 存在 `system.posix_acl_access` 这个 xattr 里，mask 是组类条目的有效上限，`ls -l` 的组三位显示的就是 mask，末尾的 `+` 提示有 ACL。默认 ACL 是给新建对象的模板，只管以后、不管已有。如果只记住一件事，那就是：ACL 给了权限还要看 mask，`getfacl` 的 `effective:` 行才是最终答案。

## 0.4.7 capability：把 root 拆成小块 {#sec-0.4.7}

这一节回答：程序只需要一项 root 特权时，为什么不该给它 setuid root？`getcap`、`setcap`、`capsh` 怎样把 root 拆成小块，边界又在哪里？

::: preview 先抓住一件事
capability（能力）是内核把 root 的特权切成几十块的结果，每块一个名字。程序可以只拿其中一块：`cap_net_bind_service` 是绑低端口，`cap_net_raw` 是发原始包。文件能力存在 `security.capability` 这个 xattr 里，`setcap` 写它、`getcap` 读它。
:::

上一节说 setuid root 危险：程序里任何一个漏洞，都直接等于 root 漏洞。可很多程序确实需要一点特权，比如监听 80 端口、发 ICMP 包、改系统时间。能不能只给这一点？

先看系统里已经这么做的例子。`ping` 要构造 ICMP 包，传统做法是 setuid root；现代发行版换成只给一项能力：

```bash
getcap -r /usr/bin /usr/sbin 2>/dev/null | head
# /usr/bin/ping cap_net_raw=ep
# /usr/bin/mtr-packet cap_net_raw=ep
```

`cap_net_raw=ep` 的意思是：执行 `ping` 时，进程只获得「使用原始套接字」这一项能力。它读不了 `/etc/shadow`，挂不了文件系统，改不了系统时钟。这就是「最小权限」的实物：以前要给整串钥匙，现在只给一把。

::: note 非科班补一层：capability 不是 root，是 root 的拆分清单
传统模型里 root 是一个布尔值：euid 为 0 就什么都能做。capability 把这个布尔值换成一个位图，每一位对应一类操作，`CAP_DAC_OVERRIDE`、`CAP_NET_BIND_SERVICE`、`CAP_SYS_TIME` 各管一摊。所以「有 capability」只说明你拿到了某几项特权，不说明你成了 root——但如果拿到 `cap_sys_admin` 或 `cap_dac_override`，实际效果已经接近 root。
:::

进程一侧有五组集合，名字容易混，先记一句话版本：

| 集合 | 一句话 | 在哪看 |
|:--|:--|:--|
| Permitted 允许集 | 这个进程「有资格用」的能力，其余集合的上限 | `CapPrm` |
| Effective 生效集 | 现在真正生效的能力，内核判权限时看它 | `CapEff` |
| Inheritable 可继承集 | `execve` 时能带进新程序的能力 | `CapInh` |
| Bounding 边界集 | 永远拿不到的天花板，只能删不能加 | `CapBnd` |
| Ambient 环境集 | 非特权程序 `execve` 后仍保留的能力，给脚本和服务用 | `CapAmb` |

最常见的需求是「让普通程序监听 80 端口」：

```bash
# 需要 root；先确认二进制是自己编译/可信的
sudo setcap cap_net_bind_service=+ep /usr/local/bin/web
getcap /usr/local/bin/web
# /usr/local/bin/web cap_net_bind_service=ep

# 回滚：删除文件上的 capability
sudo setcap -r /usr/local/bin/web
```

`+ep` 表示 permitted 与 effective 都置位。只写 `+p` 时，程序需要通过 `cap_set_proc` 自己把 capability 提到 effective；大多数程序不会做，所以 `+ep` 更常见。文件能力写在 `security.capability` 里，`getcap` 读的就是这个 xattr；`nosuid` 挂载会像忽略 setuid 一样忽略它。

capability 的边界：

- **只对 ELF 可执行文件可靠**。脚本由解释器执行，file capability 不会按你的预期附加到脚本上；需要时用一个小 C 包装器，或 systemd 的 `AmbientCapabilities=`。
- **`NoNewPrivileges=yes` 会让 execve 忽略 setuid 与 file capability**。这是 systemd 服务加固的常用项，和安全目标一致，但会让依赖 setuid 的旧程序失效。
- **bounding set 是硬天花板**。`CapBnd` 里有的能力，才可能进入 permitted；容器与 systemd 服务用它把危险能力永久排除，`capsh --drop=cap_sys_admin` 就是在子 Shell 里把它从边界集删掉。
- **capability 不是沙箱**。`cap_sys_admin` 仍然接近 root；`cap_dac_override` 可以绕过所有文件读权限。只授予真正需要的那一项。
- **容器默认丢弃大部分 capability**。Docker 默认保留的集合里没有 `CAP_SYS_ADMIN`，所以容器里 `mount` 通常失败；需要时显式 `--cap-add`，并明白这意味着什么。

查看当前进程的 capability：

```bash
getpcaps $$
# 4127: cap_chown,cap_dac_override,...=ep   （root 登录时）
# 普通用户的 Shell 通常接近空集
capsh --print | sed -n '1,12p'
```

`capsh --print` 会把五组集合逐行列出，`getpcaps` 只列 effective 那一组。两者说的都是「现在」；文件能力要看 `getcap`，那是「执行时会得到什么」。

::: errata 常见误解
1. **「capability 等于 root」**——它只是 root 的一部分；`cap_sys_admin`、`cap_dac_override` 仍然接近 root，要按项授予、按需回收。
2. **「`setcap` 对脚本一样有效」**——文件能力只对 ELF 可靠；脚本由解释器执行，能力不会按预期附加，要用 C 包装器或 systemd 的 `AmbientCapabilities=`。
3. **「`+p` 和 `+ep` 一样」**——只给 permitted 时，程序得自己 `cap_set_proc` 提到 effective；大多数程序不做，于是能力等于没生效。
4. **「设了就一定生效」**——`nosuid` 挂载、`NoNewPrivileges=yes`、bounding set 里缺这一项，都会让它失效。
5. **「`ping` 一定带 capability」**——发行版与版本不同，有的仍是 setuid root；`getcap $(command -v ping)` 与 `ls -l $(command -v ping)` 各看一眼再下结论。
:::

### 0.4.7 小结

capability 把 root 从「一个布尔值」拆成「一张位图」：程序执行时只拿到需要的那几项，文件能力写在 `security.capability` xattr 里。进程有 permitted、effective、inheritable、bounding、ambient 五组集合，effective 决定当下能不能做，bounding 决定永远能不能拿到。`ping` 用 `cap_net_raw` 代替 setuid root，是这条思路的标准案例。如果只记住一件事，那就是：能只给一项，就不要给整个 root；能不给 capability，就不要用 setuid。

## 0.4.8 账号文件与 sudo 的边界 {#sec-0.4.8}

这一节回答：`/etc/passwd`、`/etc/shadow`、`/etc/group` 每行的每个字段是什么？`sudo` 凭什么让人临时变成 root，它的边界又画在哪里？

::: preview 先抓住一件事
三个文件分工明确：`passwd` 存「你是谁、家在哪、用哪个 shell」，`shadow` 存密码哈希与有效期，`group` 存组成员。`passwd` 第二个字段的 `x` 不是密码，是「密码在 shadow 里」的占位。`sudo` 按 `sudoers` 规则临时换身份，它限制的是「能跑哪条命令」，不是「跑起来能碰到什么」——所以它不是沙箱。
:::

上一节的 capability 是给程序减权限；这一节换个方向，看人怎么被识别、管理员怎么临时提权。先看登录那一刻：系统拿你输入的名字去 `/etc/passwd` 找一行，取出 UID、GID、家目录和 shell；再拿同一个名字去 `/etc/shadow` 取哈希，核对密码。分成两个文件，是因为 `passwd` 必须人人可读（`ls` 要查名字），而哈希不能人人可读。

三个文件各管一段：

| 文件 | 一行例子 | 字段 |
|:--|:--|:--|
| `/etc/passwd` | `wang:x:1000:1000:Wang:/home/wang:/bin/bash` | 用户名、密码占位、UID、GID、注释、主目录、登录 Shell |
| `/etc/shadow` | `wang:$y$j9T$...:20000:0:99999:7:::` | 用户名、哈希、最后修改天数、最小/最大天数、警告天数、不活跃天数、过期日、保留 |
| `/etc/group` | `sudo:x:27:wang,alice` | 组名、密码占位、GID、成员列表 |

`passwd` 的第二个字段是 `x`，意思是「哈希不在这里，去 shadow 找」。字段顺序可以记成一句：名字、密码、UID、GID、说明、家、shell。`shadow` 的第二个字段才是哈希，前缀说明算法：`$y$` 是 yescrypt（Ubuntu 24.04 默认），`$6$` 是 SHA-512，`$2b$` 是 bcrypt；这一字段以 `!` 或 `*` 开头表示密码不可用。

读这些文件用 `getent`，不要直接 `grep`：`getent` 会走 NSS，能查到 LDAP、SSSD、systemd-homed 提供的用户；直接读文件会漏掉网络账号。

```bash
getent passwd wang
getent group sudo
id wang
```

UID 0 是 root；UID 1–999 通常留给系统服务；普通用户从 1000 开始（Ubuntu 的 `/etc/login.defs` 里 `UID_MIN`）。把普通用户改成 UID 0 等价于再造一个 root，不要做。

::: note 非科班补一层：名字是给人看的，数字才是权限
`/etc/passwd` 更像一张「名字 → 数字」的对照表：内核只认 UID/GID 数字，`ls -l` 显示的名字是程序回表查出来的。所以两个不同名字配同一个 UID，在内核眼里就是同一个人；反过来，删掉一个用户后，他的文件只剩数字，`ls` 会显示成一串 UID。`/etc/group` 的成员列表只列附加组，主组由 `passwd` 的 GID 字段决定，这也是「明明加进了组、权限却没变」的常见原因。
:::

`sudo`（superuser do）只做一件事：查规则确认「你可以」，再以目标身份执行一条命令。规则放在 `/etc/sudoers` 与 `/etc/sudoers.d/*`。**只能用 `visudo` 编辑**，它会在保存前做语法检查；直接 `vim` 写错一个字符，可能让所有 sudo 失效。

最小规则示例：

```sudoers
# /etc/sudoers.d/deploy
# 允许 deploy 用户重启指定服务，不需要密码
deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart myapp.service
# 允许运维组执行所有命令，但需要密码
%ops ALL=(ALL:ALL) ALL
```

一条规则读作「谁 在哪台主机 = (以谁的身份) 能跑什么」：`ALL` 是任意主机，`(root)` 是目标身份，后面跟命令的绝对路径，`%ops` 表示组。

`NOPASSWD` 的风险不是「不用输密码」这么简单：任何能修改这条命令参数的人，都可能把受限命令变成任意命令。例如允许 `systemctl restart *`，就能重启任意 unit；允许 `vim`，就能在 vim 里 `:!sh` 拿 root shell；允许 `tar`，就能用 `--checkpoint-action=exec` 执行命令。**sudo 的命令限制不是沙箱**，只是防误操作。需要强隔离时，用专用服务、容器或 systemd 沙箱。

`sudo` 的常用形式：

```bash
sudo -l                 # 看当前用户被允许什么
sudo -u postgres psql   # 以指定用户执行
sudo -i                 # 登录式 root Shell（读 root 的 profile）
sudo -s                 # 非登录 root Shell
sudoedit /etc/nginx/nginx.conf   # 用编辑器改文件，避免 sudo vim
```

`sudo -l` 的输出分两段：`Matching Defaults entries` 是生效的默认值，`User ... may run the following commands` 是授权列表。第一段里最常咬人的是 `secure_path`：`sudo` 默认清空环境（`env_reset`），把 `PATH` 换成 `secure_path` 那串固定目录。所以 `sudo mytool` 报 `command not found`，而 `sudo /usr/local/bin/mytool` 正常——不是没权限，是 PATH 被换掉了。`sudo -l -U alice` 可以看别人的授权。

`sudo -i` 与 `su -` 的区别：前者按 sudoers 授权、默认重置环境；后者需要目标用户密码（root 密码），并读目标用户的登录文件。生产环境更推荐 `sudo`，因为它的授权可审计、可细粒度。但细粒度只到「命令 + 参数」，不是隔离：`sudo vim`、`sudo less`、`sudo systemctl edit` 都能绕回一个 root shell。

账号文件不要用手改。日常增删用户/组用下面这组命令，它们会同时维护 `/etc/passwd`、`/etc/shadow`、`/etc/group` 与家目录：

| 目的 | 命令 | 注意 |
|:--|:--|:--|
| 交互式建用户（Ubuntu） | `sudo adduser alice` | 会提示设密码、建家目录、复制 `/etc/skel` |
| 脚本化建用户 | `sudo useradd -m -s /bin/bash -G dev alice` | `-m` 建家目录；`-G` 是附加组，`-g` 是主组 |
| 改附加组 | `sudo usermod -aG dev alice` | **`-a` 不能省**；只写 `-G` 会替换掉原有附加组 |
| 删用户 | `sudo userdel -r alice` | `-r` 连家目录和邮件池一起删；不带 `-r` 会留下文件 |
| 建组/加成员 | `sudo groupadd dev`、`sudo gpasswd -a alice dev` | `gpasswd -d` 移除成员 |
| 锁密码/解锁/强制改密 | `sudo passwd -l alice`、`sudo passwd -u alice`、`sudo passwd -e alice` | `-l` 只锁密码，SSH 公钥仍可能登录 |
| 密码有效期 | `sudo chage -l alice`、`sudo chage -M 90 alice` | `-M` 最大天数，`-E` 账号过期日 |

两个高频事故：`usermod -G dev alice` 会把 alice 从 sudo 等其他附加组里踢出去，必须写 `-aG`；`passwd -l` 锁的是密码哈希，已经写入 `~/.ssh/authorized_keys` 的公钥不受影响，要真正禁止登录，把 shell 改成 `/usr/sbin/nologin`（`usermod -s`）或用 `chage -E 0` 让账号过期。需要直接编辑账号文件的救援场景，用 `vipw`/`vigr` 而不是 `vim`，它们会加锁并做一致性检查。

::: errata 常见误解
1. **「`passwd` 里的 `x` 是加密后的密码」**——`x` 是占位符，哈希在 `/etc/shadow`；那个文件只有 root（或 shadow 组）能读。
2. **「`sudo` 是沙箱」**——它只做身份切换与命令匹配；被允许的命令跑起来就拥有目标身份的全部权限，`sudo vim` 等于给了 root shell。
3. **「`sudo` 报 `command not found` 是没授权」**——多半是 `secure_path` 换掉了你的 PATH；用绝对路径，或在规则里写对路径。
4. **「加进 sudo 组就够细了」**——Ubuntu 的 `%sudo ALL=(ALL:ALL) ALL` 是全权；要细粒度，写独立规则。
5. **「`passwd -l` 就禁止登录了」**——它只在哈希前加 `!`，锁的是密码；SSH 公钥仍可进，要禁登录得把 shell 改成 `nologin` 或让账号过期。
:::

### 0.4.8 小结

`passwd` 回答「你是谁」，`shadow` 存密码哈希与有效期，`group` 补上附加组；`x` 只是「去 shadow 找」的占位符。`sudo` 按 `sudoers` 规则做一次可审计的身份切换，`sudo -l` 是看清授权的第一步，`secure_path` 解释了大部分「找不到命令」。如果只记住一件事，那就是：`sudo` 是「按规则换身份」，不是「进安全屋」——被允许的命令能做什么，取决于它自己的代码。

::: method 即时自测 · 0.4.8
**Q1（记忆）** `/etc/passwd` 的七个字段是什么？第二个字段的 `x` 表示什么？`shadow` 的第二个字段又是什么？

**Q2（辨析）** `sudo mytool` 报 `command not found`，但 `/usr/local/bin/mytool` 直接跑没问题。是权限不足吗？怎么验证？

**Q3（应用）** 给 `deploy` 用户只允许重启 `myapp.service`、不要密码，写一条 sudoers 规则，并说明它为什么仍不是沙箱。

::: sol 答案
**A1** 名字、密码占位、UID、GID、注释（GECOS）、主目录、登录 Shell。`x` 表示哈希在 `/etc/shadow`；shadow 的第二个字段才是哈希，前缀表示算法，`!` 或 `*` 开头表示密码不可用。
**A2** 不是。`sudo` 的 `env_reset` 与 `secure_path` 把 PATH 换成了固定目录，`/usr/local/bin` 不在里面。验证：`sudo -l` 看 `secure_path`，再用 `sudo /usr/local/bin/mytool` 或 `sudo env | grep PATH` 对比。
**A3** `deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart myapp.service`，写完用 `visudo -c` 检查。它只匹配这一条命令，但 `systemctl` 能改 unit，unit 的 `ExecStart` 又以 root 跑，所以它防的是误操作，不是隔离。
:::

## 0.4.9 权限审计脚本 {#sec-0.4.9}

这一节回答：一台机器上哪些文件「开得太大」？怎样用一段只读脚本，把 setuid、全局可写目录、无属主文件与异常 capability 找出来，又不被 `/proc`、`/sys` 与容器挂载淹没？

::: preview 先抓住一件事
权限审计不是「把所有 777 找出来」。真正要看的是四类：带 setuid/setgid 的可执行文件、全局可写且没有 sticky 的目录、无属主（或属组）的文件、以及不该有 capability 的可执行文件。脚本只读、只报告；扫描前先排除虚拟文件系统与容器挂载，否则九成输出是噪声。
:::

接手一台机器，怎么在十分钟内知道权限面有多大？先跑下面这段。它只读，不改系统。

```bash
#!/usr/bin/env bash
# audit-perms.sh — 只读权限审计；需要 root 才能扫全盘
set -euo pipefail

echo "== setuid/setgid 可执行文件 =="
find / -xdev \( -perm -4000 -o -perm -2000 \) -type f \
    -printf '%M %u:%g %p\n' 2>/dev/null | sort

echo "== 全局可写且无 sticky 的目录 =="
find / -xdev -type d -perm -0002 ! -perm -1000 \
    -printf '%M %u:%g %p\n' 2>/dev/null | sort

echo "== 无属主或无属组的文件 =="
find / -xdev \( -nouser -o -nogroup \) -printf '%u:%g %p\n' 2>/dev/null | head -50

echo "== 最近 7 天被改过权限的文件（ctime） =="
find /etc /usr/local -xdev -type f -ctime -7 \
    -printf '%TY-%Tm-%Td %TH:%TM %M %p\n' 2>/dev/null | sort
```

`-xdev` 保证不跨文件系统，避免扫到 NFS 或 `/proc`；`-perm -4000` 是「至少包含 setuid 位」，不是精确等于，精确匹配用 `-perm 4755`；`! -perm -1000` 表示「没有 sticky 位」。

结果怎么读：

- **setuid root 的程序越少越好**。每个都要能解释「为什么需要」，否则考虑用 capability 替代。
- **全局可写目录如果没有 sticky**，任何用户都能删除别人的文件；`/tmp` 是 `1777`，有 sticky，正常。
- **无属主文件通常是删用户后留下的**，UID 可能被新用户复用，等于把文件送给别人；确认后 `chown` 或删除。
- **异常 capability 指不该有特权的程序带了宽能力**，比如 `cap_sys_admin`、`cap_dac_override`；用 `getcap -r` 列出来，逐条对照软件包。

第四类要单独跑一条：

```bash
getcap -r /usr /opt 2>/dev/null
# /usr/bin/ping cap_net_raw=ep
# /usr/bin/mtr-packet cap_net_raw=ep
```

`ping` 的 `cap_net_raw` 是正常的；如果某个 `/opt` 下的自编译程序带 `cap_setuid` 或 `cap_sys_admin`，就值得问一句「谁加的、为什么」。

`-xdev` 靠设备号判断，`/proc`、`/sys`、`/dev` 这些虚拟文件系统设备号不同，通常会被跳过。但 bind mount 与源在同一设备上，`-xdev` 拦不住——容器把宿主目录挂进 `/var/lib/docker/...` 就是这种情况。要按路径明确排除，写 `-prune`：

```bash
find / -xdev \
     \( -path /proc -o -path /sys -o -path /dev -o -path /run \) -prune -o \
     -type f \( -perm -4000 -o -perm -2000 \) -printf '%M %u:%g %p\n' 2>/dev/null
```

容器目录同理：镜像层里的「无属主文件」往往是正常内容，先用 `findmnt -T` 确认它是不是挂载点，再决定要不要看。

::: note 非科班补一层：三个 `find` 条件怎么读
`-perm -4000` 前面这个减号是「这些位都必须是 1」，`-perm 4755` 是「精确等于」，`-perm /111` 是「任意一位为 1」。`-nouser` 与 `-nogroup` 的判断标准是「UID/GID 在账号表里查不到」，不是「文件没有属主字段」。`-xdev` 是「不跨文件系统」，不等于「不扫 bind mount」。
:::

::: errata 常见误解
1. **「审计就是找 777」**——777 只是全局可写的一种；更高风险的是 setuid root、无 sticky 的全局可写目录、无属主文件与异常 capability。
2. **「`-perm -4000` 是精确等于 4755」**——它是「至少含 setuid」；要精确匹配写 `-perm 4755`。
3. **「有 `-xdev` 就不会扫到容器目录」**——它只看设备号，bind mount 与源同设备，照样会扫；按路径排除要 `-prune`。
4. **「无属主文件无所谓」**——删用户后遗留的文件，UID 可能被新用户复用，等于把文件送给了别人。
5. **「跑一次脚本就长期安全」**——审计是一次快照；要持续，用 `auditd`、AIDE 这类工具做基线比对，或把脚本放进定时任务并保存每次结果。
:::

::: method 修权限问题的顺序
1. **确认身份**：`id`、`sudo -l`，确认 euid/egid 与补充组。
2. **确认路径**：`namei -l /path/to/file`，逐级看目录的 `x`。
3. **确认判定类别**：`stat -c '%A %a %U:%G %n' file`，看你是属主、组还是其他。
4. **确认 ACL**：`getfacl -p file`，看具名条目与 mask；`ls -l` 末尾是否有 `+`。
5. **确认 LSM**：`sudo aa-status` 或 `getenforce`，看是否被 AppArmor/SELinux 拒绝；日志在 `dmesg` 或 `journalctl -k`。
6. **最后才改权限**：用最小改动（加组、加 ACL、加 capability），改完记录回滚方式。
:::

### 0.4.9 小结

权限审计查四类东西：带 setuid/setgid 的可执行文件、无 sticky 的全局可写目录、无属主文件、异常 capability；脚本只读，输出要能逐条解释，解释不了的就是待办。扫描范围本身也是证据的一部分：`-xdev` 管设备号，`-prune` 管路径，容器目录要先确认是不是挂载点。如果只记住一件事，那就是：审计的价值不在「跑过」，而在「每一条输出都有人认领」。

## 0.4.10 mode 的位级结构与内核判定路径 {#sec-0.4.10}

这一节回答：`ls -l` 那几个字符在内存里到底是什么？一次 `open` 从路径解析到「允许」或「拒绝」，内核按什么顺序问过 mode、ACL、capability 与 LSM？

::: preview 先抓住一件事
`st_mode` 是一个整数：高位是文件类型，低 12 位是三组权限加三个特殊位。判定从 `inode_permission` 开始，先看挂载与 inode 标志，再用 `fsuid`/`fsgid` 对照 owner、ACL、group、other，最后 `CAP_DAC_*` 兜底，再由 LSM 判一次。root 只是「通常能过 DAC」，不是绕过整条链路。
:::

先看一个对不上的地方：同一个文件，`ls -l` 显示 `-rwxr-xr-x`，`stat -c %a` 给 `755`，`stat -c %f` 却是 `81ed`。三个输出说的是同一件事，只是切法不同：`%a` 取低 12 位，`%f` 连类型位一起给——`0x81ed` 就是八进制的 `0100755`。

内存里的 `st_mode` 就是一个整数：`S_IFMT` 那段是类型，`04000`、`02000`、`01000` 是三个特殊位，再往下是三组 `rwx`。内核判文件权限时用的身份也不是 euid，而是 `fsuid`（文件系统用户 ID）与 `fsgid`：平时它们跟着 euid/egid 走，只有 NFS 服务这类程序会用 `setfsuid` 临时「假装」成客户端身份去访问文件，而不改自己的 euid。日常程序把 `fsuid` 读成 euid 不会错，看代码时要知道判定函数用的是 `current_fsuid()`。

`st_mode` 的布局（Linux，`include/uapi/linux/stat.h`）：

| 位（八进制） | 宏 | 含义 |
|:--|:--|:--|
| `0170000` | `S_IFMT` | 类型掩码 |
| `0140000` | `S_IFSOCK` | Unix socket |
| `0120000` | `S_IFLNK` | 符号链接 |
| `0100000` | `S_IFREG` | 普通文件 |
| `0060000` | `S_IFBLK` | 块设备 |
| `0040000` | `S_IFDIR` | 目录 |
| `0020000` | `S_IFCHR` | 字符设备 |
| `0010000` | `S_IFIFO` | FIFO |
| `0004000` | `S_ISUID` | setuid |
| `0002000` | `S_ISGID` | setgid |
| `0001000` | `S_ISVTX` | sticky |
| `0000700` | `S_IRWXU` | owner rwx |
| `0000070` | `S_IRWXG` | group rwx |
| `0000007` | `S_IRWXO` | other rwx |

```c
/* 判断类型与权限，不依赖 ls 的输出格式 */
if (S_ISREG(st.st_mode) && (st.st_mode & S_IXUSR)) { /* 属主可执行 */ }
if ((st.st_mode & 07777) == 04755) { /* 精确 setuid+755 */ }
printf("%04o\n", st.st_mode & 07777);
```

`chmod 4755` 写入的就是 `04000 | 0755`。`stat -c %f` 给十六进制原始值，`%a` 给八进制权限；`%a` 不含类型位，`%f` 含类型位（`81a4` = `0100644`）。

判定顺序可以压成五问：① 挂载与 inode 标志拦不拦（`ro`、`noexec`、immutable）？② 身份落在哪一档（owner、ACL 具名用户、组类、other）？③ 那一档的位够不够？④ DAC 不过时，有没有 `CAP_DAC_OVERRIDE` 或 `CAP_DAC_READ_SEARCH` 兜底？⑤ DAC 全过之后，LSM 允不允许？任何一问答「不」，系统调用就失败；而第 ⑤ 问失败时错误码和 DAC 一样是 `EACCES`，看不出区别。

访问判定的内核路径：

<pre class="layout">
open/openat
  └─ do_filp_open → path_openat → link_path_walk
       └─ may_open / inode_permission(inode, MAY_READ|MAY_WRITE|MAY_EXEC)
            └─ do_inode_permission
                 ├─ 只读文件系统/immutable/append-only 检查
                 ├─ generic_permission
                 │    ├─ acl_permission_check（有 ACL 时）
                 │    │    ├─ owner 匹配 → owner 位
                 │    │    ├─ ACL_USER 匹配 → 条目 & mask
                 │    │    ├─ group/ACL_GROUP 匹配 → 组位 & mask
                 │    │    └─ other 位
                 │    └─ CAP_DAC_OVERRIDE / CAP_DAC_READ_SEARCH 兜底
                 └─ LSM hook（AppArmor/SELinux）
</pre>

几个容易漏掉的点：

- **owner 类别先命中就结束**。文件属主即使属于某个有更多权限的组，也只看 owner 三位；ACL 的 `user::` 条目与 owner 位是同一类。
- **root 的绕过有条件**。`CAP_DAC_OVERRIDE` 可以绕过读写，但执行普通文件仍要求「至少一个 x 位」；`CAP_DAC_READ_SEARCH` 只覆盖读与目录搜索。只读挂载、`immutable`、LSM 都能挡住 root。
- **目录搜索是 `MAY_EXEC`**。路径上每一级目录都要有 `x`；缺少 `x` 时，即使目标文件是 777，也在中途返回 `EACCES`。
- **ACL 存在时组位显示 mask**。`ls -l` 的 group 三位不再直接代表 `group::`，而是 mask；`getfacl` 才能看到原始条目。
- **protected_* 系列 sysctl 会在判定前加限制**。Ubuntu 默认开启 `fs.protected_hardlinks=1`、`fs.protected_symlinks=1`、`fs.protected_fifos=2`、`fs.protected_regular=2`，在全局可写 sticky 目录里阻止「跟随他人符号链接」「写他人文件」等经典攻击。

```bash
sysctl fs.protected_hardlinks fs.protected_symlinks fs.protected_fifos fs.protected_regular
# fs.protected_hardlinks = 1
# fs.protected_symlinks = 1
# fs.protected_fifos = 2
# fs.protected_regular = 2
```

这些保护只作用于「全局可写且带 sticky」的目录（典型是 `/tmp`）。它们解释了为什么某些在旧教程里可行的 `/tmp` 攻击现在失效，也解释了为什么在关闭它们的系统上，脚本的临时文件必须用 `mktemp`。

::: def 定义 0.4.3 · 文件系统凭证与文件凭证 {#def-0.4.3}
内核判文件权限用的是进程的**文件系统 UID/GID**（`current_fsuid()`/`current_fsgid()`），不是 real UID，通常也不是 euid——只是平时 fsuid 跟着 euid 走。组一侧还会遍历**补充组**（`in_group_p()`）。文件的凭证是 `st_uid`/`st_gid`、mode 与 ACL 条目；两边匹配出的类别决定用哪组位。setuid 程序执行后 euid 变成文件属主，fsuid 随之更新；`sudo` 的 euid 是 0。
:::

::: note 非科班补一层：五层判定各管一段
- **挂载与 inode 标志**在最前面：`ro`、`noexec`、immutable 说不行，后面都不看。
- **mode** 是文件自己的九位，最快的一层，owner 命中就结束。
- **ACL** 只在文件有扩展 ACL 时进入，具名条目还要与 mask 相与。
- **capability** 是进程手里的特权，`cap_dac_override` 在 DAC 之后兜底。
- **LSM** 是策略层，DAC 全过也能拒；它和 DAC 共用 `EACCES`，只能靠日志区分。
「root 不等于绕过一切」说的就是这五层：root 通常能过第二、三层，但过不了第一层和第五层。
:::

::: errata 常见误解
1. **「mode 就是那十个字符」**——内存里是整数，`ls` 只挑了类型与 12 位显示；比较前先 `& S_IFMT`，或用 `S_ISREG` 这类宏。
2. **「内核用 euid 判文件权限」**——用 `fsuid`/`fsgid` 加补充组；euid 管的是信号、`setuid` 语义这些事。
3. **「有 ACL 就先看 ACL」**——顺序仍是 owner → 具名用户 → 组类 → other；owner 命中就结束，后面的条目再宽也不生效。
4. **「root 绕过一切」**——`CAP_DAC_OVERRIDE` 与 `CAP_DAC_READ_SEARCH` 只管 DAC；只读挂载、immutable、LSM、bounding set 都能拦。
5. **「`EACCES` 能告诉你是哪一层」**——DAC、ACL、LSM 都回这一个错误码；分层要靠 `namei`、`getfacl`、`ausearch` 一层层排除。
:::

### 0.4.10 小结

`st_mode` 把类型、三个特殊位与三组权限压在一个整数里，`stat -c %a` 与 `%f` 只是两种切法。判定是一条链：挂载与 inode 标志 → `fsuid`/`fsgid` 对照 mode 与 ACL → capability 兜底 → LSM 复核；任何一层说「不」，`open` 就失败。root 能过 DAC，但过不了只读挂载、immutable 与 LSM。如果只记住一件事，那就是：先认身份，再认类别，最后才认位；顺序错一步，结论一定错。

::: method 即时自测 · 0.4.10

**Q2（辨析）** 文件属主是 alice，owner 位只有 `r--`，但 ACL 里写了 `user:alice:rwx`。alice 能写吗？内核走的是哪一条？

::: sol 答案
**A1** `0170000`、`0004000`、`0000070`。`%a` 是低 12 位的八进制，`%f` 是含类型位的十六进制原始值。
**A2** 不能写。`fsuid` 先命中 owner 类别，只看 owner 三位 `r--`，`user:alice` 那条具名条目根本不会被考虑，mask 也管不到 owner。

:::

## 0.4.11 目录、sticky 与删除/重命名的判定 {#sec-0.4.11}

这一节回答：文件明明是你的，为什么删不掉？目录的 `r`、`w`、`x` 与 sticky 位，在 `unlink` 和 `rename` 时各管哪一段？

::: preview 先抓住一件事
删除和重命名改的是父目录，不是文件本身：父目录要有 `w` 与 `x`，文件自己的写位不参与。sticky 位再把决定权收紧到文件属主、目录属主与 root；`/tmp` 的 `1777` 就是「谁都能建，不能互删」。
:::

先看一个反直觉的现象。你在 `/tmp` 建一个只读文件，把它的 mode 改成 `444`，`rm` 仍然删得掉：

```bash
touch /tmp/mine && chmod 444 /tmp/mine
rm /tmp/mine        # 删除成功，没有提示权限不足
```

`rm` 如果提示 `remove write-protected regular file?`，那只是它自己的交互确认，不是内核拒绝。内核在删除时检查的是**父目录**：`/tmp` 是 `1777`，你对它有 `w` 和 `x`，删除就通过了。反过来，文件是 `0666`、父目录是 `0555` 时，谁也删不掉。

::: note 非科班补一层：删文件是改目录
目录在磁盘上是一张「名字 → inode 编号」的表。`unlink` 做的是从这张表里划掉一行，再把 inode 的链接计数减一；文件内容有没有写权限，与这次划掉无关。所以删除需要的是目录的 `w`（改表）和 `x`（走到这张表），不是文件的 `w`。
:::

| 操作 | 需要的目录权限 | 需要的文件权限 | 额外检查 |
|:--|:--|:--|:--|
| `ls dir` | `r` | — | 无 |
| `ls -l dir` | `r` + `x` | — | 对每个条目 `stat` 需要 `x` |
| `cat dir/file` | 路径上每级 `x` | 文件 `r` | 无 |
| 创建 `dir/new` | `w` + `x` | — | 目录不可 immutable |
| 删除 `dir/file` | `w` + `x` | **不需要**文件写权限 | sticky 检查 |
| 重命名 `dir/a` | 源与目标父目录都 `w` + `x` | — | sticky 检查、跨挂载 `EXDEV` |
| 修改文件内容 | 路径 `x` | 文件 `w` | `O_APPEND`/锁等另算 |

这张表的读法是：只有「修改文件内容」看文件自己的 `w`；创建、删除、重命名都看目录。一个 `0444` 的只读文件放在 `0777` 目录里，任何有目录写权限的人都能 `rm` 它；反过来，文件 `0666` 但目录 `0555`，谁也删不掉。

sticky 位（`S_ISVTX`，八进制 `1000`）把删除/重命名的决定权从「目录写权限」收紧为：

- 文件属主可以删/改名自己的文件；
- 目录属主可以删/改名目录内任何文件；
- root（更准确地说，`CAP_FOWNER`）可以删/改名任何文件；
- 其他有目录 `w` 的用户只能删自己的文件。

白话记法是：sticky 只认三种人——文件是谁的、目录是谁的、root。`/tmp` 的 `1777` 因此是「所有人能建，不能互删」。共享目录要「同组可写、组内可互删、组外不可见」，用 `2770` + setgid，而不是 `1777`；`1777` 允许任何人创建，只是不能删别人的。

内核函数是 `may_delete()` 与 `check_sticky()`（`fs/namei.c`）。`rename` 比 `unlink` 多一层：源父目录与目标父目录都要 `w` + `x`；如果目标是已存在文件，还要通过目标父目录的 sticky 检查。跨文件系统返回 `EXDEV`；把一个目录重命名到自己的子目录返回 `EINVAL`；目标是非空目录返回 `ENOTEMPTY`。`renameat2(RENAME_NOREPLACE)` 在目标存在时返回 `EEXIST`，不覆盖。

`chmod +t` 只对目录有意义；对普通文件设置 sticky 位在内核里被忽略（历史上表示「常驻 swap」，现代 Linux 不再使用）。`ls -l` 的 `t`/`T` 只反映目录的 sticky。

::: errata 目录权限的五个误解
1. **「目录的 `r` 就能读文件」**——`r` 只允许列名字；读文件要路径上的 `x` 与文件的 `r`。
2. **「目录的 `w` 就能删文件」**——还需要 `x` 到达目录 inode；只有 `w` 没有 `x` 时创建/删除都失败。
3. **「文件只读就删不掉」**——删除看父目录写权限，不看文件 mode。
4. **「`/tmp` 是 `777`，所以能删别人的文件」**——sticky 位阻止；能删的是自己的文件。
5. **「`chmod -R` 会把目录的 `x` 一起去掉」**——`chmod -R a-w` 会去掉目录写位但仍保留 `x`；用 `chmod -R a-x` 才会让目录不可进入。共享目录用 `a+rX` 而不是 `a+rx`。
:::

### 0.4.11 小结

目录的 `r` 管列名字、`w` 管增删项、`x` 管穿过；删除和重命名只检查父目录的 `w` + `x`，不检查文件自己的写位。sticky 位把「谁能删」再收紧到文件属主、目录属主与 root。如果只记住一件事，那就是：删文件是改目录，先看父目录，再看 sticky。

## 0.4.12 umask 的计算表与三个来源 {#sec-0.4.12}

这一节回答：新文件和新目录的默认权限怎样由 `mode & ~umask` 算出来？`umask` 从哪几个地方来，为什么同一台机器上 root 和普通用户不一样？

::: preview 先抓住一件事
`umask` 是「去掉的位」，不是「授予的位」：它先把 `~umask` 取反，再与请求的 mode 相与。普通文件通常请求 `0666`，目录请求 `0777`，所以 `022` 算出 `644` 与 `755`。它有三个常见来源：登录默认、PAM/Shell 启动文件、systemd unit。
:::

新建文件的权限由「请求 mode」与「umask」共同决定：`最终权限 = mode & ~umask`。普通文件请求 `0666`，目录请求 `0777`，所以 umask 直接决定默认结果：

| umask | 文件 `666 & ~umask` | 目录 `777 & ~umask` | `umask -S` | 典型场景 |
|:--|:--|:--|:--|:--|
| `022` | `644` | `755` | `u=rwx,g=rx,o=rx` | root、系统服务 |
| `002` | `664` | `775` | `u=rwx,g=rwx,o=rx` | Ubuntu 普通用户（UPG） |
| `027` | `640` | `750` | `u=rwx,g=rx,o=` | 团队共享、不对其他 |
| `077` | `600` | `700` | `u=rwx,g=,o=` | 私有、临时目录 |
| `007` | `660` | `770` | `u=rwx,g=rwx,o=` | 完全信任同组 |
| `000` | `666` | `777` | `u=rwx,g=rwx,o=rwx` | 仅测试，危险 |

计算时用八进制按位与：`0666 & ~0022 = 0644`，`0777 & ~0027 = 0750`。`umask` 输出四位（`0022`），第一位是特殊位掩码；`umask 022` 与 `umask 0022` 等价。

这里最容易错的一步是把 umask 当成减法。`umask 027` 不是「文件权限减 27」，而是「把 `027` 里的三个位从请求 mode 中拿掉」。按位与不会借位，所以 `0666 & ~0027` 是 `0640`，不是 `0639`。

`umask` 是**进程属性**，不是文件属性。它影响 `open(O_CREAT)`、`mkdir`、`mkfifo`、`mknod` 等创建操作，不影响 `chmod`、`chown` 或已存在的文件。子进程继承父进程的 umask；Shell 内建 `umask` 修改当前 Shell，之后启动的命令都继承。

三个来源按优先级叠加：

| 来源 | 位置 | 作用范围 | 备注 |
|:--|:--|:--|:--|
| 登录默认 | `/etc/login.defs` 的 `UMASK` | 登录会话 | Debian/Ubuntu 常被 PAM 覆盖 |
| PAM | `/etc/pam.d/common-session` 的 `pam_umask.so` | 登录/ssh 会话 | 读 `UMASK`、`USERGROUPS_ENAB` |
| Shell 启动文件 | `~/.profile`、`~/.bashrc` | 交互 Shell | 直接 `umask 077` |
| systemd | unit 的 `UMask=` | 服务进程 | 默认 `0022`，不继承登录用户 |
| 程序自身 | `open(..., 0600)` | 该文件 | 仍会被 umask 削掉位 |

Ubuntu 普通用户常见 `0002`，原因是 `USERGROUPS_ENAB yes`：每个用户有同名主组，PAM 把 umask 设为 `002`，让同组（通常只有自己）可写。root 是 `0022`。

```bash
umask                 # 0002
umask -S              # u=rwx,g=rwx,o=rx
( umask 077; touch /tmp/private && ls -l /tmp/private )   # -rw------- 
ls -l /tmp/private    # 子 Shell 的 umask 不影响父 Shell；文件仍是 600
```

`mkdir -m` 与 `install -m` 会在创建后显式 `chmod`，**不受 umask 影响**：`umask 022` 下 `mkdir -m 777 dir` 得到 `777`。相反，程序直接调用 `open(..., 0666)` 或 `mkdir(..., 0777)` 且不额外 `chmod` 时，mode 会被 umask 削掉；`touch` 就是后者。`touch` 没有 `-m` 选项改 mode，它按 `0666 & ~umask` 创建；需要精确权限用 `install -m 600 /dev/null file`。

默认 ACL 与 umask 的交互要单独说，这也是最容易和 0.4.6 对不上的地方。父目录一旦有默认 ACL，新建文件的访问 ACL 由默认 ACL 条目与创建时传入的 mode 相与得到；按 POSIX 语义，**umask 不再参与这个文件**（0.4.6 的结论与此相同）。有些资料会把这一步概括成「umask 仍参与」，差别在于它说的是创建时 mode 的裁剪，不是 umask 再削一遍；拿不准就以 `getfacl` 的实测为准。所以「设了默认 ACL 就不用管 umask」只在目录内成立：目录外的新文件仍由 umask 决定，目录内则要看 `getfacl` 的实际条目与 mask。团队目录的稳妥做法是设默认 ACL，再用 `getfacl` 验证新文件，而不是拿 umask 去猜。

::: errata 关于 umask 的四个误解
1. **「`umask 027` 是把权限减 27」**——是去掉 `027` 对应的位，再做按位与；八进制不会借位。
2. **「`umask 000` 等于没权限」**——恰恰相反，它一位也不去掉，新文件是 `666`、新目录是 `777`，只适合隔离的测试环境。
3. **「新文件永远是 666」**——`666` 只是 `touch`、编辑器这类程序的请求 mode；编译器可能请求 `0777`，再由 umask 削。最终值取决于程序传入的 mode。
4. **「改了 umask 会改已有文件」**——不会。umask 只在创建时生效；已有文件要 `chmod`，默认 ACL 也只管新建对象。
:::

::: method 给共享目录定权限的步骤
1. **定组**：`groupadd dev`，把成员加入 `dev`（`usermod -aG dev alice`）。
2. **定目录**：`install -d -m 2770 -g dev /srv/shared`；`2770` = setgid + `rwxrwx---`。
3. **定默认 ACL**：`setfacl -d -m g:dev:rwx,m::rwx /srv/shared`。
4. **定 umask**：成员在 `~/.profile` 写 `umask 007`，管住该目录之外的新文件。
5. **验证**：用另一个组成员创建文件，`getfacl` 看继承，`ls -l` 看组位是否为 mask。
:::

### 0.4.12 小结

`umask` 记的是「要去掉的位」，最终权限是 `请求 mode & ~umask`：文件通常从 `666` 出发，目录从 `777` 出发，再按 umask 削。它来自登录默认、PAM/Shell 启动文件和 systemd unit，是进程属性，只影响新建对象。如果只记住一件事，那就是：umask 记的是要去掉的位，不是权限本身；默认 ACL 在场时，以 ACL 与 mask 为准。

## 0.4.13 chmod 与 chown 的完整语法 {#sec-0.4.13}

这一节回答：`chmod` 的八进制与符号模式各怎样写？`u+s`、`g-s`、`o+t` 分别改哪一个特殊位？`chown`、`chgrp` 谁能用，改完会连带清掉什么？

::: preview 先抓住一件事
`chmod` 改的是 mode：九个权限位加三个特殊位，八进制适合「一次定死」，符号模式适合「增量调整」。`chown` 改的是属主/属组，普通用户不能把文件送人（需要 `CAP_CHOWN`），而且改属主通常会把 setuid/setgid 位清掉。
:::

先看两种写法改出同一个结果。下面的 `750` 与 `u=rwx,g=rx,o=` 等价：

```bash
chmod 750 file
chmod u=rwx,g=rx,o= file
stat -c '%A %a' file     # -rwxr-x--- 750
```

八进制适合从零设定，符号模式适合「只动一段」。比如只想给属组加写、去掉其他的读写执行，写 `chmod g+w,o-rwx file` 比先算一遍八进制更不容易错。

::: note 非科班补一层：符号模式是一句小句子
把 `u=rwx,g=rx,o=` 读成三句「给谁、做什么、哪些位」：`u` 是属主，`=` 是精确设为，`rwx` 是读/写/执行。`+` 是增加，`-` 是删除；右边的 `u`/`g`/`o` 还可以表示「复制另一类的权限」，例如 `g=u` 让属组照抄属主。
:::

`chmod` 的符号模式不是「u+rwx 这种固定写法」，而是一套语法：

```text
mode ::= clause [, clause]...
clause ::= [ugoa]* ([+=-] ([rwxXst]* | [ugo]))+
```

含义：

| 元素 | 作用 |
|:--|:--|
| `u`/`g`/`o`/`a` | 属主/属组/其他/全部；省略时默认 `a`，但受 umask 影响的位不会被设置 |
| `+`/`-`/`=` | 增加/删除/精确设置 |
| `r`/`w`/`x` | 读/写/执行 |
| `X` | 仅当目标是目录或已有某个执行位时加 `x` |
| `s` | setuid（u）或 setgid（g） |
| `t` | sticky（o） |
| `u`/`g`/`o`（右侧） | 复制另一类的权限，如 `g=u` |

```bash
chmod u=rwx,g=rx,o= file          # 750
chmod g+w,o-rx file               # 增量
chmod u+s app                     # 设 setuid
chmod g-s app                     # 清 setgid
chmod o+t /srv/shared             # 给目录设 sticky，等价于 chmod +t
chmod -R a+rX /srv/public         # 目录加 x，普通文件不加
chmod g=u file                    # 组权限复制属主
chmod --reference=/etc/passwd f   # 复制 mode
```

`u+s` 只动属主段的特殊位，`g-s` 只清属组段的特殊位，`o+t` 把 sticky 放在 other 段。它们不改变属主，也不改变普通的三组 `rwx`。`s` 位要有对应的 `x` 才真正生效：`chmod u+s` 后如果属主没有执行位，`ls -l` 显示大写 `S`，程序仍不能执行。

`X` 是共享目录的关键：`chmod -R a+rX` 给目录和已有执行位的文件加 `x`，不会把 `.txt` 变成可执行。`chmod -R a+rx` 会给所有文件加执行位，是常见错误。

`chmod` 的递归选项：`-R` 递归；`-H` 跟随命令行给出的符号链接；`-L` 跟随所有；`-P` 不跟随（默认）。`--preserve-root` 默认开启，拒绝对 `/` 递归；`--no-preserve-root` 关闭。对符号链接本身 `chmod` 通常无效（Linux 的 `chmod` 系统调用跟随最后一段），链接的权限位不参与访问判定；需要改链接本身没有可移植方法。

`chown` 改属主/属组，`chgrp` 只改属组：

```bash
chown alice file
chown alice:dev file
chown :dev file                 # 只改组，等价于 chgrp dev file
chown -R www-data:www-data /var/www
chown -h alice link             # 改符号链接本身
chown --from=old:old -R new:new dir   # 只改匹配旧属主的
chown --reference=ref file
```

`chown` 的边界：

- 普通用户不能把文件送给别人（需要 `CAP_CHOWN`）；可以把组改成自己所属的组。
- `chown` 会清除 setuid/setgid 位；Linux 2.2.13 起 root 的 `chown` 也按同样规则处理，不是只清非 root 的。例外在 setgid：目录、以及没有组执行位的文件，不会被清 setgid。
- `-R` 默认不跟随目录内的符号链接，但会跟随命令行给出的链接。GNU chown 默认 `-P`，用 `-h` 改链接本身，`-L` 跟随所有。
- 递归改属主前先列出会影响谁：`find /var/www -xdev ! -user www-data -printf '%u %p\n' | head`。
- 记录回滚：`find ... -printf '%u:%g %p\n' > owners.bak`。

`chmod`/`chown` 都会更新 ctime，不会更新 mtime。备份工具如果只比较 mtime，权限变更不会被发现；用 `getfacl`/`stat` 做单独的元数据备份。

::: errata 关于 chmod/chown 的四个误解
1. **「`chmod +x` 等于 `chmod a+x`」**——省略 `who` 时，`+x` 会受 umask 限制；`a+x` 才是三类都加。
2. **「`chmod u+s` 一定让程序提权」**——还要有属主执行位；只显示大写 `S` 时程序不可执行，setuid 也不生效。
3. **「普通用户可以用 `chown` 送文件」**——不能，需要 `CAP_CHOWN`；普通用户只能在自己的文件上改组，且新组必须是自己的组。
4. **「`chown` 只改归属」**——它还会清 setuid/setgid，避免「先设位、再送给特权用户」的提权路径。
:::

### 0.4.13 小结

`chmod` 用八进制一次定死，或用符号模式按「谁、加减、哪些位」增量修改；`u+s`、`g-s`、`o+t` 分别对应 setuid、setgid、sticky。`chown`/`chgrp` 改归属，需要相应特权，并且会清掉 setuid/setgid。如果只记住一件事，那就是：`chmod` 改位，`chown` 改人，两者都会动 ctime。

**Q3（应用）** 把 `/var/www/site` 整棵树交给 `www-data`，但保留目录的 setgid。写出命令顺序，并说明改完先查什么。

::: sol 答案
**A1** 属主 setuid 置位，属组 setgid 清除，other 段 sticky 置位；`4750` 是 setuid + 属主 `rwx`、属组 `r-x`、其他 `---`。
**A2** 不一样。省略 `who` 的 `+x` 会跳过 umask 里被屏蔽的位：`027` 挡住了 other 的 `x`，所以只给属主与属组加；`a+x` 显式给三类都加，不受 umask 限制。
**A3** 先记录 `find /var/www/site -printf '%u:%g %m %p\n' > owners.bak`，再 `chown -R www-data:www-data /var/www/site`，最后 `find /var/www/site -type d -exec chmod g+s {} +`。改完先看 `namei -l`、`stat` 与目录的 setgid 是否还在，再重启服务验证。
:::
:::

## 0.4.14 特殊位与 setuid 的真实边界 {#sec-0.4.14}

这一节回答：setuid 到底改了进程的哪个 ID？为什么给脚本设 setuid 没有用？哪些挂载与标志会让它失效，现代又拿什么替代？

::: preview 先抓住一件事
setuid 只改**有效 UID**（euid）：执行期间进程临时拥有文件属主的身份，真实 UID 还是你自己。它只对 ELF 可执行文件可靠，脚本会被内核忽略；`nosuid` 挂载、`no_new_privs`、目录上的 setuid 也都不生效。现代更常用 file capability 只给一项特权。
:::

三个特殊位在文件与目录上的语义不同：

| 位 | 普通文件 | 目录 |
|:--|:--|:--|
| setuid `4000` | `execve` 后 euid = 文件属主 | Linux 上忽略 |
| setgid `2000` | `execve` 后 egid = 文件属组 | 新建文件继承目录组；新建子目录继承 setgid |
| sticky `1000` | 历史上表示常驻内存，现代忽略 | 只有文件属主/目录属主/root 能删改 |

::: note 非科班补一层：三个 UID 各是谁
每个进程有三张身份牌：真实 UID（real，登录的人）、有效 UID（effective，内核判权限时看的那张）、保存 UID（saved，留给程序降权后再提权）。setuid 程序启动时，内核把 euid 换成文件属主，real 仍是你；程序可以 `setresuid` 在三者之间切换，这也是 `sudo`、`passwd` 能「临时提权、用完降回」的基础。
:::

setuid 的执行语义比「变成 root」细：

1. `execve` 检查文件 mode 的 `S_ISUID`，若挂载点有 `nosuid` 则忽略。
2. 进程的 euid 设为文件属主；如果文件属主是 root，euid=0。
3. `AT_SECURE` 置位，动态链接器进入安全模式：忽略 `LD_PRELOAD`、`LD_LIBRARY_PATH`，glibc 的 `secure_getenv()` 返回 NULL。
4. dumpable 被清（`fs.suid_dumpable` 控制 core），`/proc/PID` 的访问受限，`ptrace` 受限。
5. 程序可以 `setresuid` 在 real/effective/saved 之间切换；root 的 setuid 程序通常先降权再按需提权。

脚本为什么不行：内核执行 `#!/bin/sh` 时，真正 `execve` 的是 `/bin/sh`，setuid 位在脚本上，不在解释器上；而 Linux 明确忽略脚本的 setuid 位。所以 `chmod u+s script.sh` 只会让 `ls -l` 多一个 `s`，执行时仍是你自己的身份。要让脚本可靠提权，得用编译后的 C 包装器，或交给 systemd 配 `AmbientCapabilities=`。

setuid 为什么危险：程序的任何输入处理漏洞都直接以文件属主身份执行。历史上大量本地提权来自 setuid root 程序（`sudo`、`passwd`、`mount`、`pkexec`）。现代替代：

- file capability（下一节），只给一项能力；
- systemd 的 `User=`、`DynamicUser=`、`AmbientCapabilities=`；
- 把特权操作拆成一个小服务，通过 Unix socket/D-Bus 暴露有限接口；
- `no_new_privs` + seccomp 限制攻击面。

边界清单：

| 场景 | setuid 是否生效 | 说明 |
|:--|:--|:--|
| 普通 ELF 可执行文件 | 是 | 文件属主非 root 时 euid 变为该用户 |
| 脚本（`#!/bin/sh`） | **否** | 内核忽略脚本的 setuid，解释器按调用者身份运行 |
| `nosuid` 挂载 | 否 | `mount -o nosuid`、容器常默认 |
| `no_new_privs=1` | 否 | `prctl(PR_SET_NO_NEW_PRIVS)` 或 systemd `NoNewPrivileges=yes` |
| 目录上的 setuid | 否 | Linux 忽略 |
| 被 `chown` 后 | 位被清除 | Linux 2.2.13 起 root 也一样清 setuid/setgid |

`nosuid` 不是抽象选项，挂载表里就能看到。`findmnt -T /usr -o TARGET,OPTIONS` 的 `OPTIONS` 列里有 `nosuid`，这个挂载点下所有 setuid 位都等于装饰；容器把宿主目录挂进来时尤其常见。

```bash
# 审计 setuid/setgid：只读
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -printf '%M %u:%g %p\n' 2>/dev/null
# 看某个文件属于哪个包，判断是否原装
dpkg -S /usr/bin/passwd
# 看挂载点是否 nosuid
findmnt -T /usr -o TARGET,OPTIONS
```

对 setuid 程序的最低要求：不要信任环境变量、不要用 `system()`/`popen()` 拼命令、打开文件用 `openat` + `O_NOFOLLOW`、降权后用 `setresuid` 且检查返回值、失败时 `_exit` 而不是 `exit`（避免 flush 攻击者控制的 stdio）。这些细节在第 2 篇的进程凭证一章展开。

::: errata 关于 setuid 的五个误解
1. **「setuid 把整台机器变成 root」**——只把 euid 换成文件属主；real UID 不变，程序退出后身份就没了。
2. **「脚本加 `u+s` 就能提权」**——Linux 忽略脚本的 setuid；`ls` 里的 `s` 只是位，不是效果。
3. **「设了 setuid 就一定生效」**——`nosuid` 挂载、`no_new_privs`、目录上的 setuid 都让它失效。
4. **「setuid 是唯一做法」**——只需要一项特权时，file capability 或 systemd 的 `AmbientCapabilities=` 更小、更可控。
5. **「`chown` 后 setuid 还在」**——改属主会清 setuid/setgid，防止「设位后送人」的提权路径。
:::

### 0.4.14 小结

setuid 只改 euid，real UID 仍是调用者；它只对 ELF 可靠，脚本、`nosuid` 挂载、`no_new_privs` 都会让它失效。它把「程序漏洞」直接放大成「文件属主的权限」，所以现代更倾向用 capability 只给一项。如果只记住一件事，那就是：看到 `s` 先问三件事——是不是 ELF、挂载有没有 `nosuid`、程序真的需要整个属主身份吗。

## 0.4.15 ACL：mask、默认 ACL 与继承 {#sec-0.4.15}

这一节回答：ACL 的 mask 怎样把刚给的权限压小？目录的默认 ACL 怎样让新建文件与子目录继承？为什么 `ls -l` 的组三位有时显示的不是 `group::`？

::: preview 先抓住一件事
ACL 有三层：访问 ACL 管当前对象，默认 ACL 是目录给新对象的模板，mask 是组类条目的有效上限。有效权限 = 条目 & mask；`ls -l` 在有 ACL 时把组三位显示成 mask，末尾加 `+`。
:::

ACL 的完整模型有三层：**访问 ACL**（当前对象的条目）、**默认 ACL**（目录给新建对象的模板）、**mask**（组类条目的上限）。`getfacl` 的输出把三层都列出来：

```text
# file: srv/shared/report.csv
# owner: wang
# group: dev
user::rw-
user:alice:rw-          # 具名用户
group::r--              # 属组
group:ops:r--           # 具名组
mask::rw-               # 组类上限
other::---
```

`mask` 只约束「组类」：`group::`、`group:name:`、`user:name:`。owner 的 `user::` 与 `other::` 不受 mask 影响。`ls -l` 在 ACL 存在时把组三位显示为 mask，并在末尾加 `+`；所以看到 `-rw-rw----+` 时，`rw-` 是 mask，不一定是 `group::`。

有效权限 = 条目权限 & mask。`getfacl -e` 会把每条的有效权限单独列出来：

```bash
getfacl -e report.csv
# user:alice:rw-          # effective: r--
# group:ops:r--           # effective: r--
# mask::r--
```

::: note 非科班补一层：mask 是预算上限，默认 ACL 是模板
把 ACL 条目想成每个人申请的额度，mask 是财务批下来的总上限：申请 `rwx`、上限 `r--`，实际只能读。默认 ACL 则像放在目录门口的一张模板，新建文件时复印一份变成它的访问 ACL，新建子目录时复印两份——一份当访问 ACL，一份继续当模板往下传。
:::

排查「ACL 给了 rwx 为什么还是 denied」，顺序是：`getfacl -e` 看 effective → 看 mask → 看路径上目录的 `x` → 看 LSM。

`setfacl` 的常用操作：

| 命令 | 作用 |
|:--|:--|
| `setfacl -m u:alice:rw- file` | 增加/修改具名用户 |
| `setfacl -m g:dev:rwx,m::rwx file` | 同时放开 mask |
| `setfacl -x u:alice file` | 删除一条 |
| `setfacl -b file` | 删除所有扩展 ACL 与 mask |
| `setfacl -k dir` | 删除默认 ACL |
| `setfacl -d -m g:dev:rwx dir` | 设置默认 ACL |
| `setfacl -R -m ... dir` | 递归设置访问 ACL |
| `setfacl -R -d -m ... dir` | 递归设置默认 ACL |
| `setfacl -M file.acl dir` | 从文件读条目 |
| `setfacl --restore=acls.bak` | 恢复 `getfacl -R` 的备份 |
| `setfacl -n -m ...` | 不自动重算 mask（危险，需自己保证） |

`setfacl` 默认会**重算 mask**：新增一个 `u:bob:rwx` 时，mask 自动变成这些条目的并集，可能把原本只读的组条目一起放大。要精确控制，显式写 `m::`，或用 `-n` 后自己设 mask。

默认 ACL 的继承规则：

| 新对象 | 从父目录继承 | 结果 |
|:--|:--|:--|
| 普通文件 | `default:` 条目转为访问 ACL | 有访问 ACL；无默认 ACL |
| 子目录 | `default:` 条目转为访问 ACL，同时保留为默认 ACL | 子目录继续向下继承 |
| 子目录里的文件 | 子目录的默认 ACL | 逐层传递 |

默认 ACL 只影响**新建**对象，不改变已有文件。给一个已有目录树补默认 ACL，要 `setfacl -R -d -m ...`；给已有文件补访问 ACL，要 `setfacl -R -m ...`。两者不要混。

`umask` 的边界要记清：目录有默认 ACL 时，新建文件的访问 ACL 由默认 ACL 条目与创建时传入的 mode 相与得到，umask 不再参与（与 0.4.6、0.4.12 的结论一致）。但这不代表 mode 不重要：`install -m 600` 建完会再 `chmod 600`，组类位被清空，mask 也随之变空，默认 ACL 里的具名条目等于全被屏蔽。团队目录的推荐组合仍是 `2770` + 默认 ACL `g:dev:rwx,m::rwx`，再用 `getfacl` 验证。

备份与恢复：

```bash
getfacl -R -p /srv/shared > /var/backups/shared.acl
setfacl --restore=/var/backups/shared.acl
```

`-p` 保留绝对路径的前导 `/`；不加 `-p` 时 `getfacl` 会把 `/srv/...` 写成 `srv/...`，恢复时相对当前目录，容易放错位置。`-R` 递归，`-n` 用数字 UID/GID（跨主机恢复更稳）。

ACL 的文件系统支持：ext4 默认挂载含 `acl`，XFS/Btrfs 默认支持，tmpfs 支持；NFSv3 用 POSIX ACL 需要服务端/客户端配置，NFSv4 用 NFSv4 ACL（`nfs4_getfacl`/`nfs4_setfacl`），与 `getfacl` 不是同一套。`tar --acls`、`rsync -A`、`cp -a` 保留 ACL；`cp -r` 不保留。

::: errata ACL 的六个误解
1. **「`getfacl -p` 是数字 UID」**——`-p` 是保留绝对路径；数字 UID 用 `-n`。
2. **「mask 是额外权限」**——mask 是上限，只会削减组类条目，不会增加。
3. **「`ls -l` 的组三位就是 `group::`」**——有 ACL 时它是 mask，`getfacl` 才看得到 `group::`。
4. **「设了默认 ACL 新文件就一定有全部权限」**——还要过创建时传入的 mode 与 mask；三者取交集。
5. **「`setfacl -k` 能删所有 ACL」**——`-k` 只删默认 ACL；`-b` 删除所有扩展条目（含默认），保留 owner/group/other 的基础位。
6. **「ACL 能替代目录权限」**——路径上每一级目录的 `x` 仍是前提，ACL 只作用于目标 inode。
:::

### 0.4.15 小结

ACL 分访问 ACL、默认 ACL 与 mask 三层：mask 只压组类条目，默认 ACL 只当新建对象的模板。`ls -l` 的组三位在有 ACL 时显示 mask，末尾的 `+` 是提醒。如果只记住一件事，那就是：先看 `getfacl -e` 的 effective，再看 mask，最后才怀疑目录 `x` 与 LSM。

**Q2（辨析）** `setfacl -m u:alice:rwx file` 后 `getfacl` 显示 `mask::r--`，`ls -l` 的组三位是什么？alice 能写吗？

**Q3（应用）** 目录设了默认 ACL 后，用 `install -m 600` 新建文件，为什么组里同事仍读不了？怎样验证？

## 0.4.16 capability：五个集合与文件能力 {#sec-0.4.16}

这一节回答：`execve` 那一步，内核用哪条算式算出进程的新能力？五个集合各对应 `/proc/PID/status` 的哪一行？root 和 capability 为什么不是「拆开就等价」？

::: preview 先抓住一件事
五个集合不是五个并列的名词，而是一次 `execve` 的算术：进程侧的 P（permitted）、E（effective）、I（inheritable）、B（bounding）、A（ambient）与文件侧的 F 相与相或，才得出 `P'` 与 `E'`。内核判权限只看 `E'`；root 不等于「E 全开」，它是让算式另一边自动填满的开关。
:::

[5.1.7](../part5/ch01.md#sec-5.1.7) 实测过一件事：`docker run --rm --cap-drop=ALL` 起的容器里 `id -u` 仍是 `0`，`chown` 却失败；默认配置（`CapEff` 为 `00000000a80425fb`）下同一条命令就成功。两次 euid 一样，变的是位图：内核判特权看位图，`euid == 0` 只是让内核替你把它填满的捷径。

capability（能力）是内核把 root 特权切成的 41 个位（Linux 6.8，`CAP_CHOWN` 是第 0 位）。进程侧的五个位图与 `/proc/PID/status` 的五行一一对应：`CapInh`、`CapPrm`、`CapEff`、`CapBnd`、`CapAmb`（一句话版本在 0.4.7）。文件侧另有 permitted、inheritable 与只有一位的 effective，写在 `security.capability` 这个 xattr 里，就是 `getcap` 显示的 `p`/`e`/`i`。

```bash
grep '^Cap' /proc/self/status
capsh --decode=00000000a80425fb   # 位图翻成能力名
getpcaps $$                       # 只列 effective 这一组
```

`CapInh` 常年全 0：能继承不等于现在有权，它只是「将来允许带过去」的名单。位图在 `struct cred` 里的样子见 [2.9.7](../part2/ch09.md#sec-2.9.7)，算式完整版见 [2.9.10](../part2/ch09.md#sec-2.9.10)。

### 一次 `execve` 的算术

```text
P'(permitted)   = (P(inheritable) & F(inheritable)) | (F(permitted) & B) | P'(ambient)
P'(effective)   = F(effective) ? P'(permitted) : P'(ambient)
P'(inheritable) = P(inheritable)      # 不变
P'(bounding)    = B                   # 不变
P'(ambient)     = 文件是特权文件 ? 0 : P(ambient)
```

`P(...)` 是 `execve` 前的进程，`P'(...)` 是之后，`B` 就是 `CapBnd`，`F(...)` 是被执行文件的三个集合；「特权文件」指带 setuid/setgid 位或带文件能力的文件。三个「或」是三条来路：I 与文件 I 的交集、文件 permitted 过 bounding、ambient。三条推论比公式好记：

- 文件的 `e` 位决定立刻生效还是等着。只写 `+p` 时 `F(effective)=0`，`E'` 是空的：能力停在 permitted 里等程序自己 `cap_set_proc`，多数程序不做，所以实操写 `+ep`（例 0.4.16）。
- `F(permitted) & B` 让 bounding 成了硬天花板：`--cap-drop=ALL` 之后，文件写着 `cap_chown=ep` 也拿不到 `CAP_CHOWN`。
- 能力要进 `A`，必须同时在 `P` 与 `I` 里（`prctl(PR_CAP_AMBIENT_RAISE)` 就查这个）；执行特权文件时 `P'(ambient)` 归零，防止借道偷渡。

```bash
sudo setcap cap_net_bind_service=+ep /usr/local/bin/web
getcap /usr/local/bin/web
# /usr/local/bin/web cap_net_bind_service=ep
sudo setcap -r /usr/local/bin/web        # 删除
```

单给 `+i` 通常什么都不发生。每次重装或重编译二进制之后都要重新 `getcap`：能力挂在 inode 的 xattr 上，覆盖了就没了。

### root 与 capability 为什么不等价

「capability 把 root 拆成小块」这句话简化了一步：内核看到 UID 0 时，会把算式里文件那一侧当成全 1。三处照顾：

1. real 或 effective 为 0 时 `execve`，`F(inheritable)` 与 `F(permitted)` 被视作包含全部能力，effective 为 0 再把 `F(effective)` 视作已置位，`P'` 与 `E'` 直接是满的。
2. setuid root 程序走同一条路，一次 `execve` 交出整张位图。setuid 不是「给一项特权」，是「把所有特权都给」。
3. 改 UID 时内核还要修正（fixup）：effective 从 0 变非 0，`E` 清空、`P` 留着；一次改动后 real、effective、saved 全非 0（改前有 0），`P` 与 `E` 一起清空；改回 0 则把 `P` 复制进 `E`。fsuid（[0.4.10](#sec-0.4.10)）切换时只清 `CAP_CHOWN`、`CAP_DAC_*`、`CAP_FOWNER`、`CAP_FSETID` 这批文件相关的位。

三条都能逐项关掉：`SECBIT_NOROOT` 关第 1、2 条，`SECBIT_NO_SETUID_FIXUP` 关第 3 条，`SECBIT_KEEP_CAPS`（旧接口 `prctl(PR_SET_KEEPCAPS)`）是「UID 全降到非 0 但保住 permitted」的逃生口。关掉之后 root 只是「UID 恰好为 0 的普通进程」，特权仍要从文件能力或 ambient 拿。服务里最常见的就是走 ambient（`NoNewPrivileges=yes` 让 `execve` 忽略 setuid 与文件能力，ambient 却在启动时就进了 `A`，不受影响）：

```ini
[Service]
User=web
NoNewPrivileges=yes
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
AmbientCapabilities=CAP_NET_BIND_SERVICE
```

::: note 非科班补一层：为什么有了 root 还要 capability
你要在容器里跑一个 web 服务，真正想给的只有一条能力：绑 1024 以下的端口。给它 root（或 `--cap-add=ALL`、`--privileged`），它顺带就能读别人的文件（`CAP_DAC_OVERRIDE`）、改任意文件属主（`CAP_CHOWN`）、加载内核模块（`CAP_SYS_MODULE`）、读别的进程内存（`CAP_SYS_PTRACE`）。同一个解析漏洞，只给 `CAP_NET_BIND_SERVICE` 最多是端口被占，给了全部就是宿主没了。0.4.7 里 `ping` 用 `cap_net_raw=ep` 代替 setuid root，就是这个道理的最小演示。
:::

::: ex 例 0.4.16 · 先猜 `+ep` 与 `+p` 的差别
同一个 `/usr/local/bin/web`，第一次 `setcap cap_net_bind_service=+ep`，第二次改成 `+p`，两次都由普通用户执行、都去绑 80。先猜结果与运行时的 `CapEff`。

::: sol 答案
第一次成功：`F(permitted)` 有这一位又落在 `B` 内，`P'` 就有了；`F(effective)` 已置位，于是 `E'` 等于 `P'`。第二次失败：`P'` 照样有这一位，但 `F(effective)=0`、ambient 为空，`E'=0`，而内核判 `bind` 只看 effective。
:::
:::

::: method 判定流程 · 一项能力该不该给、给了有没有生效
1. **先问能不能不要它**：80 改 8080 再交给反向代理；`ping` 走 `net.ipv4.ping_group_range`；改属主交给「以 root 启动、随后降权」的服务进程。
2. **确实需要，就查出是哪一项**：`strace` 找返回 `EPERM` 的系统调用（缺能力就是这个错误码），再对照 `capabilities(7)`。先给 `cap_sys_admin` 试试不是排查，是埋雷。
3. **只给那一项，写成 `+ep`**：文件必须是 ELF，`getcap` 确认只有这一条。
4. **运行时核对三行**：`CapEff` 在不在、`CapBnd` 让不让、`CapPrm` 与 `CapEff` 是否一致（只写 `+p` 就差在这里）。
5. **确认没被关掉，并留好回滚**：`nosuid` 挂载、`NoNewPrivileges=yes`、`--cap-drop`、`SECBIT_NOROOT` 都会让 `setcap` 白做；想知道程序是否真需要某一项，可用 `capsh --drop=cap_sys_admin -- -c '...'` 先在一层子 Shell 里丢掉它；回滚是 `setcap -r`。
:::

::: errata capability 的五个误解
1. **「`+p` 和 `+ep` 一样」**——文件的 e 位没置，`E'` 就是空的（见例 0.4.16）。
2. **「`CapEff=0` 说明机器坏了」**——普通用户的 Shell 本来就该是 0；要看的是那个特权程序**运行时**的值。
3. **「给了 capability 就等于最小权限」**——`CAP_SYS_ADMIN`、`CAP_DAC_OVERRIDE`、`CAP_SYS_PTRACE` 任何一项都接近 root，给错一项等于没拆。
4. **「`CapBnd` 删掉的位还能加回来」**——`prctl(PR_CAPBSET_DROP)` 不可逆，也没有加回操作；收窄只能发生在启动与容器配置阶段。
5. **「文件能力对什么程序都可靠」**——只对 ELF 有效，脚本由解释器执行；`--cap-add=ALL` 也不等于「多给一点」，它把整体裁剪取消，容器里的 root 基本就是宿主 root（[5.1.7](../part5/ch01.md#sec-5.1.7)）。
:::

### 0.4.16 小结

`P'(permitted)` 由三条来路相或：继承交集、文件 permitted 过 bounding、ambient；`P'(effective)` 只看文件那个一位的 e。`setcap +ep` 解决「进不进得去」，`CapBnd`、`nosuid`、`NoNewPrivileges` 决定「让不让你进去」。root 不在这套算术之外，它是让内核把文件侧当成全 1 的开关，securebits 能关掉。如果只记住一件事，那就是：内核判的是 effective，`grep '^Cap' /proc/PID/status` 五行读完，比猜「这是不是 root」可靠。

## 0.4.17 账号文件：passwd、shadow、group 的字段 {#sec-0.4.17}

这一节回答：三个文件每一段到底说什么？shadow 口令字段里的 `!` 和 `*` 差在哪？为什么读账号要用 `getent` 而不是 `cat /etc/passwd`？

::: preview 先抓住一件事
`passwd` 回答「你是谁、家在哪、登录后交给哪个程序」，`shadow` 存口令哈希与有效期，`group` 只补附加成员。字段靠**位置**解释，多一个冒号就整行右移；而「有哪些账号」不归文件管，归 NSS 按 `nsswitch.conf` 问完所有数据源之后的答案。
:::

先跑两条命令，看同一台机器给出的两个答案：

```bash
getent passwd wang          # 走 NSS：所有数据源
grep '^wang:' /etc/passwd   # 只问 files 这一家
```

在接了 LDAP 或 SSSD 的机器上，第一条查到的人，第二条可能一行都没有：不是文件坏了，是你只问了一家。

::: def 定义 0.4.17 · NSS（Name Service Switch，名字服务切换） {#def-0.4.17}
NSS 是 libc 的查表调度：程序调 `getpwnam()`、`getpwuid()` 这类函数，libc 按 `/etc/nsswitch.conf` 的顺序逐个问数据源（`files`、`sss`、`systemd`、`ldap`……），先给出答案的赢。大白话：`/etc/passwd` 只是其中一档。`getent` 就是把这些函数做成命令行。
:::

`/etc/passwd` 每个账号一行、七段，冒号分隔（人人可读，所以不含哈希）：

```text
wang:x:1000:1000:Wang Wei:/home/wang:/bin/bash
```

| 字段 | 例 | 含义 | 注意 |
|:--|:--|:--|:--|
| 用户名 | `wang` | 登录名 | 区分大小写；不要用 `.` 开头 |
| 密码占位 | `x` | 哈希在 shadow | 旧系统可能直接放哈希（危险） |
| UID | `1000` | 用户 ID | 0 是 root；重复 UID 等于同一用户 |
| GID | `1000` | 主组 ID | 必须在 group 中存在 |
| GECOS | `Wang Wei` | 注释/全名 | 逗号是段内分隔 |
| 家目录 | `/home/wang` | 登录后的 cwd | 不存在时登录可能失败 |
| 登录 Shell | `/bin/bash` | 登录后交给谁 | `/usr/sbin/nologin` 禁交互登录 |

第二段最值得说。启用 shadow 之后系统根本不解析这一段，放 `x` 只是惯例，任何非空串效果相同；**但空段不是「没有密码记录」，而是「登录不需要口令」**。第三、四段是数字，内核只认 UID/GID，名字是程序回表查出来的，第 4 段的主组必须存在。第七段可以是任何程序，不一定是 shell：`/usr/sbin/nologin` 打印一句提示再退出，`/bin/false` 直接失败；路径随发行版不同（Debian/Ubuntu 常在 `/usr/sbin/`，RHEL 系常在 `/sbin/`），别硬编码。

`/etc/shadow`（权限让普通用户读不到，只给 root 或 shadow 组）：

```text
wang:$y$j9T$...:20000:0:99999:7:::
```

| 字段 | 例 | 含义 |
|:--|:--|:--|
| 用户名 | `wang` | 与 passwd 对应 |
| 哈希 | `$y$...` | `$y$` yescrypt（Ubuntu 24.04 默认）、`$6$` SHA-512、`$5$` SHA-256、`$2b$` bcrypt、`$1$` MD5 |
| 最后修改 | `20000` | 1970-01-01 起的天数 |
| 最小天数 | `0` | 两次改密的最小间隔 |
| 最大天数 | `99999` | 超过必须改密；`99999` 约等于永不过期 |
| 警告天数 | `7` | 过期前多少天提示 |
| 不活跃天数 | 空 | 过期后多少天禁用 |
| 过期日 | 空 | 1970 起的天数；`chage -E` 设置 |
| 保留 | 空 | 未来使用 |

第二段的各种值要分开读。`!` 是哈希**前面**的前缀：`passwd -l`/`usermod -L` 加上它，哈希还留在后面，`passwd -u` 去掉就恢复，`passwd -S` 报 `LK`。`!!` 一般是账号建好却从没设过口令。`*` 不是有效哈希，也谈不上「可解开」，表示这个账号不能用口令认证。空段最危险，等于无口令。三者挡的都只是口令这一条路：SSH 公钥、Kerberos、`sudo -u 名字 cmd`（直接执行程序，不走登录 shell）都不看它。真要禁账号，得同时动 shell 与有效期（`usermod -s`、`chage -E 0`）。后面六个天数段都从 1970-01-01 起算，`chage -l` 显示的就是它们。

::: ex 例 0.4.17 · 先猜这一行登录后会发生什么
手工救援时有人把 `wang` 那行的注释字段整段删掉了：

```text
wang:x:1000:1000:/home/wang:/bin/bash
```

先猜：`su - wang` 会怎样？`echo $HOME` 是什么？

::: sol 答案
这行只有六段，整行右移一位：注释段成了 `/home/wang`，家目录段成了 `/bin/bash`，shell 段为空——回落到 `/bin/sh`，`HOME` 被设成 `/bin/bash`，登录后 `cd` 回家目录直接失败。账号文件不要手改：用 `vipw`/`vigr`（加锁、保存前检查），事后 `pwck`/`grpck` 核对字段数与引用。
:::
:::

`/etc/group` 四段：

```text
sudo:x:27:wang,alice
```

| 字段 | 例 | 含义 |
|:--|:--|:--|
| 组名 | `sudo` | 组名 |
| 密码占位 | `x` | 组密码在 `/etc/gshadow` |
| GID | `27` | 组 ID |
| 成员 | `wang,alice` | **附加成员**；主组成员不在这里列出 |

第四段最容易被误读：列的是**附加组**成员，主组由 `passwd` 第 4 段决定。分两处记是历史遗留——早期 UNIX 一个用户同时只属一个组，换组要 `newgrp` 并交出组密码（在 `/etc/gshadow`），4.2BSD 才引入同时属于多个组。所以判断「alice 在不在 `dev` 组里」别 `grep` 组文件，用 `id -nG alice`。

这三个文件的正确读法是函数而不是 `cat`：`getpwnam()`/`getpwuid()` 查单条，`setpwent()`/`getpwent()`/`endpwent()` 顺序扫描，组是 `getgrnam()`/`getgrent()`，shadow 是 `getspnam()`。两个坑：返回的是指向**静态结构**的指针，下次调用会改写同一份内存，多线程用 `_r` 版本；「查不到」和「出错」都返回 NULL，要先清 `errno` 才分得开。程序走这些函数，LDAP 与 SSSD 才是透明的——这就是 `getent` 比 `cat /etc/passwd` 更接近真相的原因。

`nsswitch.conf` 决定问的顺序：

```text
passwd:         files systemd
group:          files systemd
shadow:         files
```

`files` 在前本地文件优先，`sss` 在前目录服务优先。排查顺序也在这里：先 `getent passwd user` 看 NSS 最终给出什么，再看 `/etc/passwd` 有没有同名冲突条目。

UID 范围写在 `/etc/login.defs`：`UID_MIN 1000`、`UID_MAX 60000`、`SYS_UID_MIN 100`、`SYS_UID_MAX 999`。把普通用户改成 UID 0 等于再造一个 root；两个名字共享同一个 UID，在内核眼里就是同一个人。

::: method 判定流程 · 「这个账号到底能不能登录」
1. `getent passwd NAME`：NSS 解析得出条目吗？解析不出是目录服务的事，别改本地文件。
2. 第 7 段 shell：`nologin` 或 `false` 只挡**交互登录**；`sudo -u NAME cmd`、cron、systemd 服务都不走登录 shell，照样跑。
3. `passwd -S NAME` 给出 `PS`/`LK`/`NP`，`chage -l NAME` 给出时间窗；要看原字段用 `getent shadow NAME`（需特权）。
4. 策略层：`sshd` 的 `AllowUsers`/`DenyUsers`、PAM（`pam_access`、`pam_nologin` 加 `/etc/nologin`）。口径：`!` 只挡口令，`nologin` 只挡交互 shell，`chage -E` 只挡时间窗，三者互不替代。
:::

::: errata 关于账号文件的四个误解
1. **「口令段为空表示被锁定」**——恰好相反，空段表示**不需要口令**；`!` 才是锁定。
2. **「`passwd -l` 之后这个人就进不来了」**——SSH 公钥、Kerberos、`sudo -u`、他名下的服务全都照旧。
3. **「`/etc/group` 里没有名字就不在这个组里」**——主组不列在那里，看 `id -nG`。
4. **「`cat /etc/passwd` 就是全部账号」**——NSS 后面还有 `systemd`、`sss`、`ldap`；要列全量用 `getent passwd`。
:::

### 0.4.17 小结

`passwd` 七段定身份与登录入口，`shadow` 九段存哈希与时间窗，`group` 四段补附加成员；`!` 是可解开的口令前缀，`*` 与 `!!` 是没有可用口令，空段是不需要口令。如果只记住一件事，那就是：账号的真相在 NSS 的答案里，先 `getent` 再谈文件；真要改，用 `vipw`/`vigr` 加 `pwck`/`grpck` 收尾。

::: method 即时自测 · 0.4.17
**Q1（记忆）** `passwd` 的七段分别是什么？哪一段决定登录后交给哪个程序，哪一段决定 `HOME`？

**Q2（辨析）** shadow 口令段出现 `!哈希`、`*哈希`、空串三种值时，口令登录各能不能通过？哪一种能被原样恢复？

**Q3（应用）** 同事说「deploy 明明被我锁了，他还是能跑东西」。写出四条命令，说明各排查哪一层。

**Q4（迁移）** 写「列出机器上所有人类账号」的脚本，为什么用 `getent passwd` 而不是 `cat /etc/passwd`？给一个会因此出错的场景。

::: sol 答案
**A1** 用户名、口令占位、UID、GID、GECOS 注释、家目录、登录 shell。第 7 段决定交给谁（为空时回落到 `/bin/sh`），第 6 段成为 `HOME`。
**A2** 三种都过不了口令这一关。`!哈希` 是锁定，去掉前缀即恢复；`*哈希` 不是合法哈希，也谈不上恢复；空段等于不需要口令，是必须立刻修掉的事故。
**A3** `getent passwd deploy` 看第 7 段；`passwd -S deploy` 看状态；`chage -l deploy` 看有效期；`sudo -l -U deploy` 与 `ls -l /home/deploy/.ssh/authorized_keys` 看还留着哪些免密入口。
**A4** 账号可能不来自 `files`。接了 SSSD 或 LDAP 的机器上 `/etc/passwd` 只有本地那几行，脚本会漏掉真实用户、进而漏掉他们的文件归属。
:::
:::

## 0.4.18 用户与组管理命令 {#sec-0.4.18}

这一节回答：`useradd` 与 `adduser` 到底差多少？哪些地方会造成线上事故——删用户不删文件、`-G` 踢人出组、UID 撞号、`/etc/skel` 没生效？

::: preview 先抓住一件事
同一件事在 Debian/Ubuntu 上有两层命令：高层的 `adduser`/`deluser`（Perl 脚本，交互友好、会建家目录、会复制 `/etc/skel`）与低层的 `useradd`/`usermod`/`userdel`（shadow-utils，跨发行版一致，但**默认不建家目录**、`-G` 是替换不是追加）。脚本里用低层，交互时用高层，别混着猜。要改的从来只是 0.4.17 那三个文件的行——内核认数字 UID/GID，每个用户有一个主组（`passwd` 第 4 段）加若干附加组（`group` 第 4 段）。
:::

先跑两条命令，看同一台机器给出的两种结果：

```bash
sudo useradd svc1 && id svc1
sudo useradd -m -s /bin/bash svc2 && ls -a /home/svc2
```

`svc1` 建成了，但 `/home/svc1` 不存在；`svc2` 有家目录，里面的点文件是从 `/etc/skel` 复制来的。换成 Ubuntu 的 `adduser svc1`，它会停下来问口令与 GECOS，并把家目录一并建好——同一个发行版里两套命令行为不同，事故就从这里来。

两层命令的分工先记这张表：

| 目的 | 高层（Ubuntu） | 低层（跨发行版） | 差异 |
|:--|:--|:--|:--|
| 建用户 | `adduser alice` | `useradd -m -s /bin/bash alice` | `adduser` 交互设密码、建家目录、复制 skel |
| 删用户 | `deluser --remove-home alice` | `userdel -r alice` | 都删家目录；`deluser` 还会处理组 |
| 改用户 | `usermod`（相同） | `usermod` | `adduser` 没有改用户子命令 |
| 建组 | `addgroup dev` | `groupadd dev` | `addgroup` 可同时加成员 |
| 加成员 | `adduser alice dev` | `usermod -aG dev alice` | 前者是 Debian 语法 |

`useradd` 的默认值来自 `/etc/default/useradd` 与 `/etc/login.defs`，家目录模板是 `/etc/skel`。常用选项：

| 选项 | 作用 | 注意 |
|:--|:--|:--|
| `-m` | 创建家目录 | 低层默认不建 |
| `-M` | 不建家目录 | 服务账号常用 |
| `-d DIR` | 指定家目录 | 配合 `-m` |
| `-s SHELL` | 登录 Shell | 服务账号用 `nologin` |
| `-g GROUP` | 主组 | 必须是已存在组 |
| `-G GROUPS` | 附加组 | 逗号分隔，**替换**而不是追加 |
| `-u UID` | 指定 UID | 冲突会失败 |
| `-c COMMENT` | GECOS | 可放全名 |
| `-e DATE` | 账号过期日 | `YYYY-MM-DD` |
| `-f DAYS` | 密码不活跃天数 | `-1` 表示不失效 |
| `-r` | 系统账号 | UID 从 SYS_UID 范围取 |
| `-N` | 不创建同名组 | 默认会创建 |
| `-U` | 创建同名组 | 与 `-N` 相反 |
| `-p HASH` | 直接给哈希 | 不要传明文；用 `passwd` 或 `chpasswd` |

`useradd` 的三个默认值决定「不写选项会发生什么」：不写 `-m` 不建家目录；不写 `-s` 用 `/etc/default/useradd` 里的 `SHELL`，很多机器上那是 `/bin/sh`，本该没有交互入口的服务账号于是拿到了 shell；不写 `-g` 会新建一个同名主组（`-N` 关掉）。家目录内容来自 `/etc/skel`，少点文件通常因为用了 `-M`，或家目录名已存在——`useradd` 不覆盖已有目录，也不往里复制。

UID 从哪来更要当心。`-r` 走 `SYS_UID_MIN`–`SYS_UID_MAX`（0.4.17 那段），不写 `-r` 才从 `UID_MIN` 往上取；而 `useradd` 取的是**当前最大值加一**，不是最小的空位。删掉 UID 1003 的用户、再建几个人，1003 就可能发给新人，上一位留在 `/srv`、`/tmp` 的文件**直接归了他**。指定 UID 用 `-u`，撞号会失败（`-o` 允许重复，别用）。

`usermod` 的高频用法与事故：

```bash
sudo usermod -aG dev alice       # 追加附加组（-a 不能省）
sudo usermod -G dev alice        # 错误：把其他附加组全部替换掉
sudo usermod -l alice2 alice     # 改名；家目录不会自动改
sudo usermod -d /home/alice2 -m alice2   # 改家目录并搬内容
sudo usermod -s /usr/sbin/nologin alice  # 禁止登录
sudo usermod -L alice            # 锁密码（在哈希前加 !）
sudo usermod -U alice            # 解锁
sudo usermod -e 2025-12-31 alice # 账号过期
```

`-G` 不带 `-a` 会**替换**整个附加组列表，这是把用户踢出 `sudo` 组的经典事故。`usermod -l` 只改 `passwd` 里的名字，家目录名与文件属主都不跟着动，要搬得再补 `-d ... -m`。

`userdel alice` 删账号、留文件；`userdel -r alice` 才连家目录与邮件池一起删，但**仍然不会**删散落在系统其它位置的文件——`/srv`、`/var/www` 下属于她的文件会变成「无主」，`ls -l` 直接显示数字 UID。删之前评估影响，删之后收口：

```bash
find / -xdev -user alice -print        # 删除前：她还有哪些文件
find / -xdev -nouser -print            # 删除后：有没有无主文件
```

::: ex 例 0.4.18 · 先猜输出
alice 在 `dev`、`sudo` 两个附加组里，管理员执行 `sudo usermod -G dev alice`，然后 `id -nG alice`。先猜输出。

::: sol 答案
里没有 `sudo`：`-G` 是整组替换，她下次 `sudo` 会被告知不在 sudoers 里。正确写法是 `-aG`，或先 `id -nG alice` 抄下原列表再重设。另一层边界：`id` 读的是**当前进程**的凭证，她已登录的会话不会变，要重新登录，或在当前会话里 `newgrp dev`、`sg dev -c '...'` 临时生效。
:::
:::

组管理：

```bash
sudo groupadd -g 1500 dev
sudo groupadd -r appsvc          # 系统组
sudo groupmod -n developers dev  # 改名
sudo groupdel dev                # 有用户以它为主组时失败
sudo gpasswd -a alice dev        # 加成员
sudo gpasswd -d alice dev        # 删成员
sudo gpasswd -A alice dev        # 设管理员
sudo gpasswd -M alice,bob dev    # 设置成员列表（替换）
newgrp dev                       # 当前 Shell 切换到 dev 主组（新 Shell）
sg dev -c 'id'                   # 以 dev 组执行一条命令
```

三条边界要分清。`newgrp dev` 会**再起一个 Shell**（主组换成 `dev`），退出回到原会话，不改变已登录会话里的其他进程；`sg dev -c '...'` 只影响那一条命令。SSH 会话的补充组在登录那一刻定死，`usermod -aG` 之后必须**重新登录**才生效——这是「加了组却没生效」的标准答案。`gpasswd -M alice,bob dev` 同样是**替换**成员列表，`-a`/`-d` 才是增删，`-A` 交出组管理员。看身份的三个命令各管一段：`id NAME` 读账号在 NSS 里的定义与成员组，`groups` 是简写（不带参数时读**当前进程**的凭证），`getent group dev` 看这个组的定义与成员。

`su` 与 `sudo` 的分工：`su - alice` 要**目标用户**的口令（root 除外）并读她的登录文件；`sudo -u alice` 按 sudoers 授权、用你自己的凭据，默认还重置环境。生产上更推荐后者，因为可审计、可细粒度，边界见 0.4.19。

密码与有效期：

```bash
sudo passwd alice                # 交互设密码
sudo passwd -l alice             # 锁
sudo passwd -u alice             # 解锁
sudo passwd -e alice             # 强制下次登录改密
sudo passwd -S alice             # 状态：PS（已设）/LK（锁定）/NP（无密码）
sudo chage -l alice              # 看有效期
sudo chage -M 90 -W 7 alice      # 最大 90 天，提前 7 天警告
sudo chage -E 2025-12-31 alice   # 账号过期
sudo chage -d 0 alice            # 下次登录必须改密
```

批量建账号时不要循环 `useradd` 后手工 `passwd`（交互）；用 `chpasswd` 从标准输入读 `user:password`，并确保输入不落到 shell 历史：

```bash
printf '%s:%s\n' "$user" "$password" | sudo chpasswd
```

密码会出现在进程参数/管道中，生产环境应使用 `chpasswd` 的文件输入、随机生成密码并强制首次改密。`vipw`/`vigr` 在救援时用于安全编辑账号文件（加锁、做一致性检查），不要直接 `vim /etc/passwd`。

::: method 判定流程 · 改账号之前，先 id 后动
1. **先 `id NAME`**：把主组与全部附加组抄进工单；查不到人就先去 0.4.17 确认数据源。
2. **认清要改哪一层**：口令（`passwd`/`chage`）、成员关系（`usermod -aG`/`gpasswd`）、shell（`usermod -s`）、还是 UID/GID 数字——最后这种最危险，牵动全盘文件归属。
3. **查号段是否空闲**：`getent passwd UID`、`getent group GID` 先看有没有人占着，别用 `-o` 硬塞重复号。
4. **执行后立即复测**：`id NAME` 与工单逐项对比；组改动后记得「已登录会话不变，要重新登录」。
5. **要删人先盘文件**：`find / -xdev -user NAME` 看清留了什么、归谁，再决定 `userdel` 还是 `userdel -r`；收尾跑 `pwck`/`grpck` 与 `find / -xdev \( -nouser -o -nogroup \)`。
:::

::: errata 用户与组管理的五个误解
1. **「`adduser` 与 `useradd` 只是名字不同」**——前者建家目录、复制 `/etc/skel`、交互设口令；后者默认三样都不做。
2. **「`usermod -G` 是追加」**——不带 `-a` 是整组替换，最常见的踢人方式。
3. **「`userdel` 就把人删干净了」**——不带 `-r` 连家目录都不删，带了也不删散落在别处的文件。
4. **「加完组就生效」**——凭证在登录时确定，已登录会话看不到新组。
5. **「`-r` 只是打个标记」**——它改的是号段与策略适用方式；用 `-r` 建一个需要交互登录的账号，就会掉进「为什么登不进去」的坑。
:::

### 0.4.18 小结

高层（`adduser`/`deluser`）适合交互与人类账号，低层（`useradd`/`usermod`/`userdel`）适合脚本，但要自己补上 `-m`、`-s`、`-aG`。四个最容易出事故的地方：`-G` 替换附加组、`userdel` 不删散落文件、`-r` 与 UID 号段复用、`/etc/skel` 未复制。如果只记住一件事，那就是：**先 `id` 抄下现状，再动手，再 `id` 复测**；组改动之后还要重新登录才看得见。

::: method 即时自测 · 0.4.18

**Q2（辨析）** `usermod -G dev alice` 与 `usermod -aG dev alice` 结果差在哪？`useradd -m` 与 `adduser` 谁会把 `/etc/skel` 复制过去？

**Q3（应用）** 你给 bob 加了 `docker` 组，他抱怨「还是 `permission denied`」。给出三条命令解释并解决。

## 0.4.19 sudo：配置结构与「不是沙箱」的边界 {#sec-0.4.19}

这一节回答：一条 sudoers 规则由哪几段组成？`visudo -c` 到底检查了什么？为什么「只授权一条命令」不等于把这个人隔离开？

::: preview 先抓住一件事
`sudo` 是一套**授权模型**（authorization，管「你能不能以别人的身份启动这个程序」），不是**隔离模型**（isolation，管「程序跑起来之后能碰到什么」）。它更像一张授权书：写清你能以谁的身份办哪件事，至于那件事办完之后你还做了什么，它一概不管。所以授权 `vim`、`find`、`awk` 中任意一个，实际接近给了一个 root shell；写 `!/bin/sh` 这类禁令挡不住逃逸。
:::

### 先做一次语法检查，再谈规则结构

sudoers（sudo 的授权规则文件格式）改坏会出大事：主文件有语法错误时 `sudo` 整体拒绝加载，连你自己的应急通道一起封掉。所以改动第一步是校验，而校验能脱离系统文件单独做——我们在本机这台 macOS 上用自带的 sudo 1.9.17p2 跑了一次：

```bash
$ printf 'deploy ALL=(root) NOPASSWD: /usr/bin/true\n' > ok.sudoers
$ printf 'deploy ALL=(root) NOPASSWD /usr/bin/true\n' > bad.sudoers
$ visudo -c -f ok.sudoers
ok.sudoers: parsed OK
$ visudo -c -f bad.sudoers
bad.sudoers:1:41: syntax error
deploy ALL=(root) NOPASSWD /usr/bin/true
                                        ^
```

两个文件只差一个冒号，第二个被拒。`1:41` 读作「第 1 行第 41 列」，插入符指向解释器读不下去的位置。sudoers 的语法由 sudo 项目维护，macOS 与 Linux 是同一套，所以这条 `-c` 校验和报错格式在 Linux 上照用；本节其余涉及 `sudo -l` 输出的部分需要 Linux 主机，本机未实测。

检查通过，再看内容。`/etc/sudoers` 的主结构是「别名定义 + 默认值 + 授权规则」：

```sudoers
# 1. 别名：把一组用户/主机/命令命名
User_Alias  ADMINS = alice, bob
Cmnd_Alias  SERVICES = /usr/bin/systemctl restart myapp.service, \
                       /usr/bin/systemctl status myapp.service
Host_Alias  PROD = web1, web2

# 2. 默认值：可全局，也可按用户/主机/命令限定
Defaults env_reset, secure_path="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
Defaults timestamp_timeout=5
Defaults:deploy !requiretty

# 3. 授权规则：谁 在哪台主机 = (以谁的身份) 能跑什么
ADMINS PROD = (root) NOPASSWD: SERVICES
%ops ALL = (ALL:ALL) ALL
deploy ALL = (root) NOPASSWD: /usr/bin/systemctl restart myapp.service
```

字段读法：`用户 主机 = (runas用户:runas组) 标签: 命令`。`%ops` 是组；`ALL` 是通配；`(root)` 表示只能以 root 运行；`NOPASSWD:` 是标签，作用于后面整条命令列表。第三段最容易被跳过：把 `(root)` 写成 `(postgres)`，同一条命令就以 postgres 身份跑。别名（`User_Alias`、`Cmnd_Alias`、`Host_Alias`）只给一组名字起称呼，不改变语义——读规则先把别名展开，才知道边界在哪。

常用标签（写在命令列表前面，作用于其后所有命令）：

| 标签 | 作用 | 风险 |
|:--|:--|:--|
| `NOPASSWD:` | 不询问口令 | 任何能触发该命令的路径都直接以目标身份执行 |
| `NOEXEC:` | 禁止该命令再起子进程 | 只对部分程序有效，见下文 |
| `INTERCEPT:` | 校验并记录子进程的执行 | 依赖 `LD_PRELOAD` 或 `ptrace`，有盲区 |
| `SETENV:` | 允许用 `-E` 与命令行传环境 | 可注入 `LD_PRELOAD` 等；命令为 `ALL` 时隐含 |
| `CWD:` / `CHROOT:` | 指定工作目录 / 先 chroot | 路径必须存在，配置复杂 |

`Defaults` 的关键项（默认值列按本机 sudo 1.9.17p2 的 `sudoers(5)` 手册；发行版常在 `/etc/sudoers` 里另设，以 `sudo -l` 的 `Matching Defaults entries` 段为准）：

| 项 | 默认 | 作用 |
|:--|:--|:--|
| `env_reset` | 开 | 清空环境，只保留白名单；`sudo -E` 需要另开 `setenv` |
| `secure_path` | 上游不设，Ubuntu 显式写死一串 | 用固定 PATH，防止用户 PATH 注入 |
| `timestamp_timeout` | 5（分钟，可写 2.5） | 免密缓存时长；`0` 每次问，负值到重启前不过期 |
| `visiblepw` | 关 | 终端关不掉回显时是否仍然提问；关着直接拒绝 |
| `passwd_tries` | 3 | 口令尝试次数 |
| `requiretty` | 关 | 只允许终端使用；旧发行版常开 |
| `log_output` | 关 | 记录命令输出，落在 `iolog_dir`（默认 `/var/log/sudo-io`） |

`visiblepw` 解释了 cron 与 `ssh host sudo cmd` 的常见报错：非交互时拿不到能关回显的终端，sudo 宁可拒绝也不把口令打在屏幕上；硬要跑通就开它，代价是口令明文可见。

`!` 在 sudoers 里不是逻辑取非，它是**排除**：先有正向匹配，才有东西可排。`ALL, !/bin/sh` 是「除 sh 之外全部」；单独一行 `!/bin/sh` 匹配不到任何命令，也就拦不住任何命令。规则按**后匹配的覆盖先匹配的**生效，顺序写反结果跟着反。

::: ex 例 0.4.19 · 先猜 deploy 能走多远 {#ex-0.4.19}
有人给部署账号写了这样一条规则，自认为已经很紧：

```sudoers
deploy ALL = (root) NOPASSWD: /usr/bin/vim /srv/app/config.yaml, !/bin/sh, !/bin/bash
```

先猜：deploy 能不能拿到一个 root shell？那条 `!/bin/sh` 起了什么作用？

::: sol 答案
能拿到，`!/bin/sh` 形同虚设。`vim` 里 `: !sh` 直接起 shell，`:r /etc/shadow` 能读、`:w` 能往任意路径写，这些都发生在 vim 进程内部；`!` 只是排除，和 `vim` 那条不冲突，改不了任何匹配结果；sudoers 只看**你敲下去的那一行命令行**，vim 之后 `execve` 了什么它不知道。要拦子进程得靠 `INTERCEPT`，而它有自己的限制（见下节）。结论：这条规则防误操作，防不了有意逃逸。
:::
:::

规则只在 `visudo` 里改（它加锁）。改完三步：`sudo visudo -c`（查主文件与它 include 的目录）、`sudo -l`（当前用户被允许什么）、`sudo -l -U alice`（看别人的授权）。分段文件放 `/etc/sudoers.d/`，权限 `0440`。

### sudo 不是沙箱：能跑一个程序，就能跑它的逃逸口

为什么命令限制挡不住人？sudo 手册把事实写得很直白：一旦它执行了那个程序，程序想做什么就做什么，包括再起别的程序。而「能起子进程」或「能写任意文件」的口子在常用工具里遍地都是：

| 允许的命令 | 绕过方式 |
|:--|:--|
| `vim`/`nano` | `:!sh`、`:r /etc/shadow`、写 `authorized_keys` |
| `less`/`more` | `!sh`、`s` 保存到文件 |
| `find` | `-exec sh -c ... \;` |
| `awk` | `BEGIN { system("sh") }` |
| `tar` | `--checkpoint-action=exec=sh` |
| `systemctl` | 启动任意 unit、`systemctl edit` 写文件 |
| `env` | `env sh` |
| `python`/`perl`/`ruby` | `-c 'import os; os.system("sh")'` |
| `cp`/`tee`/`dd` | 覆盖 `/etc/sudoers`、写 `authorized_keys` |
| `mount` | 挂载恶意文件系统、覆盖文件 |

读法：左列只要出现在授权里，右列就是实际授权。`find` 那条最反直觉——一个看着只会找文件的工具，`-exec` 让它变成任意命令；`awk` 的 `system()` 同理。

`NOEXEC` 与 `INTERCEPT` 想补的正是这个洞，但要看清它们到什么程度。sudo 的做法是在被授权程序内部拦住它的执行调用，底层两条路。dso：用 `LD_PRELOAD` 覆盖 libc 的执行函数，只对**动态链接**程序有效，静态编译的绕过；动态链接器对 setuid 程序本就忽略 `LD_PRELOAD`，这类程序默认进不了 intercept。trace：用 `ptrace` 配 `seccomp` 直接拦 `execve`，静态动态都管，代价是 gdb、strace 这些自己依赖 `ptrace` 的程序跑不起来。两条都拦不住 shell 内建命令，也管不了程序内部读写敏感文件——门槛提高了，结论没变。

::: method 判定流程 · 一条命令该不该授权、怎么授权
1. **能不能限定参数？**写死到最细的一段，别用 `*` 兜底：sudoers 的通配符连空白都匹配，`/usr/bin/tail -f /var/log/app/*` 里那个 `*` 能吃下一个空格再加一整串参数，等于把参数列表重新开放。写不细就退回「专用账号 + ACL」（0.4.15）。
2. **能不能用绝对路径？**只写命令名，匹配的是 sudo 按 PATH 解析出来的那个程序；命令写全路径，再配 `secure_path`，才确定它落在哪。
3. **被授权程序有没有逃逸面？**能不能执行外部命令、能不能写任意文件、能不能读任意文件——上表那些工具答案是「有」，就别授权给 root；只是改文件的话用 `sudoedit`。
4. **三问都过不了，那是隔离需求**：叠一层 sudo 之外的机制——systemd 的 `User=` 加沙箱选项、一项 capability（0.4.16），或走 Unix socket 由一个只做这件事的小服务代跑。
5. **改完留证据**：`visudo -c` 通过、`sudo -l` 与预期逐条一致、日志里有「谁、以谁的身份、跑了什么、退出码」。
:::

### 换身份的几种写法与时间戳

```bash
sudo -u postgres psql          # 以指定用户
sudo -g dev id                 # 以指定组
sudo -i                        # 登录式 root Shell（读 root 的 profile）
sudo -s                        # 非登录 root Shell
sudo -k                        # 清除时间戳，下次重新认证
sudoedit /etc/nginx/nginx.conf # 用编辑器改，避免 sudo vim
```

`sudo -i` 起的是**登录式** root shell：`HOME`、`PATH`、`USER` 按 root 重建，再读 root 的 profile，认证用你自己的口令。`sudo su` 是另一条路径：先起 root shell，再在里面 `su` 到目标账号——多一次切换、多一套 `su` 自己的口令规则，日志里只剩「有人跑了 su」，粒度反而更粗。`sudo -s` 是非登录式，保留当前目录与更多环境。改文件用 `sudoedit`：以你的身份编辑临时副本，再由 sudo 用特权复制回原位，不给编辑器留逃逸面。

`doas` 的规则语言比 sudoers 小得多；systemd 的 `run0` 借 polkit 与一个临时 tty 提权，体验接近 `sudo -i`。两者同样是授权模型，不改变这条边界。时间戳按终端与用户分别记在 `/run/sudo/ts/` 下，共享跳板机上值得把 `timestamp_timeout` 设成 0。

::: errata sudo 的七个误解
1. **「`NOPASSWD` 只是省一次输入」**——它意味着任何能触发该命令的路径都以 root 执行；参数可控时等于给了 root。
2. **「限制命令名就安全」**——`vim`、`find`、`awk`、`tar`、`systemctl` 都能逃逸；参数通配符更危险。
3. **「`NOEXEC` 或 `INTERCEPT` 能防逃逸」**——dso 只对动态链接程序有效、setuid 程序被排除；trace 让 gdb 与 strace 跑不起来；两者都拦不住 shell 内建命令和程序内部的文件读写。
4. **「`sudo -E` 能保留所有环境」**——`env_reset` 与 `env_keep` 会过滤，且要先有 `SETENV` 标签或 `setenv` 默认项；`LD_PRELOAD` 在安全模式下被忽略。
5. **「把用户加进 sudo 组就行」**——Ubuntu 的 `%sudo ALL=(ALL:ALL) ALL` 等于全权；要细粒度就写独立规则。
6. **「`sudoers.d` 里放什么都会生效」**——文件名含 `.` 或 `~` 会被忽略，权限必须 0440，一处语法错误让 sudo 整体拒绝加载。
7. **「写了 `!/bin/sh` 就是黑名单」**——`!` 是排除，没有正向集合时它匹配不到任何东西；被授权程序自己 `execve` 的命令行根本不经过 sudoers。
:::

### 0.4.19 小结

sudoers 一条规则读作「谁 在哪台主机 =（以谁的身份）标签: 命令列表」，`Defaults` 决定环境、口令缓存与 PATH，`visudo -c` 是改完必须过的一关。但授权与隔离是两件事：sudo 判断的是你要跑的那一行，跑起来之后程序能起子进程、能读能写，都在它的授权范围之外。如果只记住一件事，那就是：授权前先过三问——参数能不能写死、路径是不是绝对、这个程序有没有逃逸面；三问过不了，就该换成专用账号、一项 capability 或者一个小服务。

**Q3（应用）** 要给 `%ops` 组「查看 myapp 日志最后 200 行」的权限，写一条尽量安全的规则，并说明判定三问各怎么过。

**Q4（迁移）** `sudo -i`、`sudo -s`、`sudo su` 三种写法有什么区别？什么场景下应该不用 sudo，改用别的机制？

::: sol 答案

## 0.4.20 实验：setuid、ACL 与 capability 的证据 {#sec-0.4.20}

这一节回答：0.4.14、0.4.15、0.4.16 那些结论，怎样在自己机器上变成看得见的证据？跑不了的实验又该按什么顺序判读？

::: preview 先抓住一件事
三个实验各盯一条链：setuid 看「同一个程序，`chmod u+s` 前后 effective UID 变没变」；ACL 看「`ls -l` 那个 `+` 与 `getfacl` 的 `mask`、`effective` 怎么对上」；capability 看「文件写了 `+ep`，运行时的 `CapEff` 里到底有没有那一位」。每个实验按同一个套路读：先看哪几行、这几行说明什么、看不到时先查什么。
:::

交代一下证据口径，这台书稿用了两台机器。开发机是 macOS，权限模型与 Linux 不等价，`setfacl`/`getfacl`/`setcap`/`getcap`/`capsh` 一个都没装；另一台是真 Ubuntu 24.04.5（aarch64，ext4，`/dev/sda2` 带 ACL 支持）。标了**本机实测**的是 macOS 上敲出来的，标了 **Ubuntu 实测**的是那台 Linux 上敲出来的。Linux 侧的 root 仍然要密码，所以凡是「换属主后看 setuid 是否生效」「给文件写能力」这类**必须特权**的步骤保持**未实测**，只给命令与判读顺序，不编造输出。

### 实验一：setuid——同一个程序，euid 变不变

**第一步，先看见三个 ID。** 我们写一个只打印身份的小程序，先跑起来再解释（Linux 上编译命令相同）：

```c
#include <stdio.h>
#include <unistd.h>
int main(void) {
    printf("real uid=%ld effective uid=%ld\n", (long)getuid(), (long)geteuid());
    printf("real gid=%ld effective gid=%ld\n", (long)getgid(), (long)getegid());
    return 0;
}
```

```bash
$ cc -std=c17 -Wall -O2 -g -o ids ids.c && ./ids     # 本机实测
real uid=501 effective uid=501
real gid=20 effective gid=20
```

两行相等是普通程序的正常状态：真实 UID（real UID，登录的那个你）和有效 UID（effective UID，内核判权限时看的那张牌）都是你。看到它们不相等，才说明有 setuid 程序或 `setresuid` 参与。

**第二步，加 setuid 位，再看一眼。** 本机实测：

```bash
$ chmod u+s ids && ls -l ids
-rwsr-xr-x  1 juanwang  wheel  33808 Oct 29 13:10 ids
$ ./ids
real uid=501 effective uid=501
```

位真的写上了（`ls -l` 的属主执行位从 `x` 变成 `s`），运行结果却没变——因为这个文件的属主就是你自己。setuid 的语义是「把 euid 换成**文件属主**」，属主是你时换成了你。要看到真实效果必须换一个属主，而这需要 root：

```bash
sudo chown root:root ids && ls -l ids   # 需 Linux 主机，本机未实测
./ids                                   # 预期：real uid=1000 effective uid=0
```

如果 `chmod u+s` 之后 `ls -l` 里没有 `s`，先查挂载点：`findmnt -T . -o TARGET,OPTIONS` 出现 `nosuid` 时，内核会直接忽略这些位。

**第三步，看懂三条切换规则。** `execve` 除了把 euid 换成文件属主，还把 saved set-user-ID（保存 UID）复制成那个**新的** euid——不管文件有没有 setuid 位都执行这次复制。有了 saved 这一格，程序才能「降权干活、需要时再提回来」。三条规则：非特权进程只能把 euid 在 real 与 saved 之间换，换到别的值报 `EPERM`；特权进程（euid 为 0）调 `setuid(非 0)` 会把三个 ID 一起改掉，这是单向操作，之后再也提不回 0；所以「收放自如」用 `seteuid(real)` 与 `seteuid(saved)`，「永久放弃特权」用 `setresuid(r, r, r)`。每次改完必须用 `getresuid()` 读回三个值逐个断言——`setresuid` 是全成或全败（0/1 效应），失败就立刻 `_exit`，不能带着预期之外的身份继续跑。

**第四步，一次真实的身份切换在系统调用层长什么样。** 用 `sudo -u nobody id` 取证（需 Linux 主机，本机未实测）：

```bash
strace -f -e trace=setresuid,setresgid,setuid,setgid,execve \
    -o /tmp/sudo.trace sudo -u nobody id
grep -E 'setresuid|setresgid|execve' /tmp/sudo.trace | tail -20
```

预期能看到类似：

```text
setresuid(-1, 0, -1) = 0
setresgid(-1, 0, -1) = 0
execve("/usr/bin/id", ["id"], ...) = 0
setresuid(65534, 65534, 65534) = 0
```

具体顺序取决于 sudo 版本与 PAM 配置，但关键点是：`sudo` 先以 setuid root 拿到 euid 0，认证后 `setresuid` 切到目标用户，再 `execve`。参数里的 `-1` 读作「这一格保持不变」——`setresuid(-1, 0, -1)` 只动 effective，real 与 saved 留在原地，这正是第三步说的「收放自如」。反过来 `setresuid(65534, 65534, 65534)` 三格一起改，nobody 的身份就再也提不回去了。如果 `setresuid` 返回 -1 而程序继续跑，那是一个真 bug：它可能带着 root 继续做本该降权的事。

**第五步，环境变量不干净时为什么危险。** 内核执行 setuid 程序时会置一个安全标志（`AT_SECURE`），动态链接器据此忽略 `LD_PRELOAD` 和 `LD_LIBRARY_PATH`，glibc 的 `secure_getenv()` 在这种进程里返回 NULL。但这层保护只覆盖 glibc 自己读的变量；程序代码里只要出现下面这类写法，攻击面立刻回来了（这是示例，不要照抄进真程序）：

```c
char *cmd = malloc(64 + strlen(user_arg));
sprintf(cmd, "grep '%s' /var/log/app.log", user_arg);
system(cmd);            /* 起 shell：PATH、IFS 由调用者控制 */
```

`system()` 会 `/bin/sh -c` 起一个 shell，而那个 shell 继承进程当前的 euid。此时 `PATH` 是攻击者设的，`grep` 就未必是系统的 `grep`。所以特权程序的纪律是：绝不起 shell（`system()`、`popen()`、`execlp()` 都算），要执行外部程序就写全路径、`execve` 自己传一个干净的环境数组，并且**先永久降权再 exec**。

**看不到预期结果时先查什么。** 顺序是：`ls -l` 有没有 `s`（位是否真写上）→ 挂载点有没有 `nosuid`（`findmnt -T 路径 -o OPTIONS`）→ 文件是不是 ELF（脚本上的 setuid 被 Linux 忽略，0.4.14）→ 是不是在 `NoNewPrivileges=yes` 的 systemd 服务或容器里（这条会同时忽略 setuid 与文件能力）→ `strace -e trace=execve,setresuid` 看内核到底给了什么。

### 实验二：ACL——把 `ls -l` 那个加号拆开

**第一步，`+` 号（本机实测）。** macOS 用的是 NFSv4 风格的 ACL，条目写法与 Linux 的 POSIX ACL 不同；但「有 ACL 时 mode 那九位不再完整」这条两边一致：

```bash
$ printf 'x\n' > f.txt && ls -l f.txt
-rw-r--r--  1 juanwang  wheel  2 Oct 29 13:01 f.txt
$ chmod +a "everyone allow read" f.txt
$ ls -l f.txt
-rw-r--r--+ 1 juanwang  wheel  2 Oct 29 13:01 f.txt
$ ls -le f.txt
-rw-r--r--+ 1 juanwang  wheel  2 Oct 29 13:01 f.txt
 0: group:everyone allow read
```

两处变化：权限串末尾多了 `+`（它占掉原来那个空格），`ls -le` 把条目本身列出来。结论只有一句：看到 `+`，`ls -l` 的九位不可信，去问 `getfacl`。

**第二步，在 Linux 上把 mask 逼出来（Ubuntu 24.04 实测）。**

```bash
mkdir -p /tmp/lab0c04 && cd /tmp/lab0c04 && printf 'x\n' > acl.txt
setfacl -m u:nobody:rx,g:juanwang:rwx acl.txt   # 两条具名条目
chmod 600 acl.txt                               # 不碰条目，只压 mask
getfacl -e acl.txt
```

真实输出（`getfacl -e` 只列受 mask 影响的条目）：

```text
# file: acl.txt
# owner: juanwang
# group: juanwang
user::rw-
user:nobody:r-x   #effective:---
group::rw-        #effective:---
group:juanwang:rwx        #effective:---
mask::---
other::---
```

`effective:` 是条目与 mask 相与的结果。这里 `chmod 600` 把 mask 收成 `---`，于是**三条具名条目一起失效**：nobody 写的 `r-x` 变成不能用，组写的 `rwx` 也变成不能用，只剩下显式的 `user::rw-` 和 `other` 还按自己走。放开写 `setfacl -m m::rwx acl.txt`；收紧要清楚自己在连累所有组类条目，不只是某一条。两个时刻的 `ls -l` 都在同一台机器上取：`setfacl` 之后是 `-rw-rwxr--+`，`chmod 600` 之后是 `-rw-------+`。中间那三位**不是组的权限，是 mask**——第一行它显示 `rwx`（刚被 `setfacl` 抬上去），第二行它跟着 `chmod` 一起变成 `---`。同一份文件、同一条 `ls -l`，组那三位说的却是不同的事，这正是「凡看到 `+`，`ls -l` 的九位不可信」的现场。
**第三步，默认 ACL 怎么往下传（Ubuntu 24.04 实测）。**

```bash
mkdir -p /tmp/lab0c04/sub
setfacl -m d:g:juanwang:rx /tmp/lab0c04/sub
touch /tmp/lab0c04/sub/newfile
getfacl -p /tmp/lab0c04/sub/newfile
```

新建文件里立刻带上继承来的条目，而且**它自己的 mask 已经把它压了一道**：

```text
# file: sub/newfile
# owner: juanwang
# group: juanwang
user::rw-
group::rwx        #effective:rw-
group:juanwang:r-x        #effective:r--
mask::rw-
other::r--
```

注意 `mask::rw-`：默认模板给的是 `r-x`，文件的 mask 由创建模式与 umask 共同决定，所以继承到的条目不一定拿得到写权限。想让继承生效到 `rwx`，就得在建文件时用 `install -m 664` 之类的方式显式带出模式，或者事后 `setfacl -m m::rwx`。**这一步里「`install -m 600` 会把继承条目压死」的对照我没有跑**（要装 `attr`/换创建模式的实验在 macOS 上做不了），只作结论提醒，不当实测。两者结果不同：`touch` 建的文件带上 `group:dev:rwx`；`install -m 600` 建完又显式 `chmod 600`，改的是 mask，mask 归零后继承来的具名条目全被压成无权限——同事依旧读不到。子目录还会多出一份 `default:` 段继续往下传，普通文件没有默认段。

**第四步，ACL 存在哪里（需要 `attr` 包，本机未实测）。** Ubuntu 24.04 默认没装 `getfattr`（实测 `command -v getfattr` 无输出；VM 是共享机器，没有装包），所以这一步给判读不给输出：装上 `attr` 之后，`getfattr -n system.posix_acl_access -e hex acl.txt` 会打印这个 xattr 的二进制内容，`strace -e trace=setxattr setfacl -m u:nobody:r-- acl.txt` 应看到一次 `setxattr`。ACL 不是 mode 的另一种写法，是挂在 inode 上的独立扩展属性；只有 owner、group、other 三条基础条目时不占 xattr，这时 `getfattr` 查不到是正常的。

**看不到预期结果时先查什么。** 顺序：`findmnt -T 路径 -o OPTIONS` 里有没有 `noacl`（或文件系统本身不支持）→ `getfacl` 输出里有没有 `mask::` 行，设条目时是否用了 `-n` 阻止重算 → 是不是 NFS（NFSv3 要服务端客户端配合，NFSv4 走 `nfs4_getfacl`，与 `getfacl` 不是同一套）→ 路径上每一级目录有没有 `x` → 文件是不是被 `cp -r` 或重新下载过，ACL 早就丢了。

### 实验三：capability——文件写了 `+ep`，运行时到底有没有那一位

这台 Ubuntu 24.04 上 `setcap`/`getcap`/`capsh` **都在**（`/usr/sbin/` 下，属 `libcap2-bin`），但**写文件能力需要 root**：实测 `sudo -n setcap cap_net_bind_service=ep t.bin` 回 `a password is required`，`capsh --user=juanwang --print` 回 `Unable to set group list for user: Operation not permitted`。所以下面「给文件加能力」的部分仍标未实测；**不需要特权的两半我跑了**，结论如下。

不用 root 就能看到的两件事，恰好是这条链上最容易误解的部分：

```bash
cat /proc/sys/kernel/cap_last_cap      # 这台内核的能力上界
grep Cap /proc/self/status             # 普通 shell 的五集合
```

```text
40
CapInh: 0000000000000000
CapPrm: 0000000000000000
CapEff: 0000000000000000
CapBnd: 000001ffffffffff
CapAmb: 0000000000000000
```

读法：`cap_last_cap` 是 40，意思是能力编号从 0 排到 40，共 41 项；`CapBnd` 的 `0x1ffffffffff` 正好是低 41 位全 1 —— **bounding set 默认放开全部能力**，它只在被显式清除时才起作用。普通 shell 的 `CapEff` 全 0：你不是 root 就没有任何有效能力，`CapBnd` 满格不等于你有能力，这只是「上限没被裁剪」。判据因此是两句：**看能不能做事读 `CapEff`，看被没被容器/`--cap-drop` 裁剪读 `CapBnd`**。

低端口这道墙也实测了：`nc -l 80` 直接 `nc: Permission denied`（`EACCES`，不是 `EADDRINUSE`），同一台机器上 `nc -l 8080` 能起来并被 `timeout` 杀掉才返回。服务绑低端口失败，先分清这两条错误，再去查能力。

**第零步：不用 root，也不用 setcap，先看一台原生 Ubuntu 上已经有的文件能力。**

```bash
getcap -r /usr 2>/dev/null | head -4
ping -c1 127.0.0.1 >/dev/null && echo "ping 可用（非 root）"
```

Ubuntu 24.04 实测（aarch64，未装任何额外包）：

```text
/usr/bin/ping cap_net_raw=ep
/usr/bin/mtr-packet cap_net_raw=ep
/usr/lib/snapd/snap-confine cap_chown,cap_dac_override,cap_dac_read_search,cap_fowner,cap_setgid,cap_setuid,cap_sys_chroot,cap_sys_ptrace,cap_sys_admin,cap_sys_resource=p
/usr/lib/aarch64-linux-gnu/gstreamer1.0/gstreamer-1.0/gst-ptp-helper cap_net_bind_service,cap_net_admin,cap_sys_nice=ep
```

这一页输出把 capability 模型讲完了三件事。

**第一，`cap_net_raw=ep` 是「只给你开原始套接字这一项特权」。** 普通用户跑 `ping` 能发 ICMP 原始包，不是因为它 setuid root，而是内核在这条 `execve` 上把文件的 permitted/effective 能力并进了新进程的 `CapEff`。传统做法是给 `ping` 上 SUID，那等于把整个 root 的权力交给一个能任意构造包的工具。

**第二，后缀 `=ep` 与 `=p` 是两回事。** `snap-confine` 那行列的是 `=p`：只有 permitted、没有 effective —— 能力拿到了但**当前不可用**，进程要在确认输入可信之后用 `cap_set_proc()` 之类把它提到 effective 才使能。把「装了能力」读成「就有权限」是误读。

**第三，`gst-ptp-helper` 带着 `cap_net_bind_service`。** 「非 root 绑低端口」在一台默认安装的 Ubuntu 上早有现成例子：不必把 `CAP_NET_BIND_SERVICE` 对全局放开，只给这一个二进制。

顺带给一个判据：怀疑某个二进制靠能力而不是靠 SUID 提权时，先 `getcap <路径>`，再 `ls -l <路径>` 看有没有 `s` 位。两个都为空却还能做特权动作，那就要去查它是不是被 systemd 单元用 `AmbientCapabilities=` 拉起来的（`systemctl show -p AmbientCapabilities <unit>` 只读可查）。

**第一步，给一项能力并确认写进去了。**

```bash
sudo setcap cap_net_bind_service=+ep /usr/local/bin/web
getcap /usr/local/bin/web                       # 期望只列这一条，后缀是 =ep
getfattr -n security.capability /usr/local/bin/web
```

文件能力存在 `security.capability` 这个 xattr 里，跟 inode 走：重装、重编译、`cp` 覆盖之后它就不在了，`getcap` 要重跑。

**第二步，以非 root 启动并验证。** 期望 `ss -lnt` 里真的出现 `:80`。失败时先分错误码：`EACCES` 才是权限问题（缺 `CAP_NET_BIND_SERVICE` 就报它），`EADDRINUSE` 是端口被占，`EADDRNOTAVAIL` 是地址不在本机网卡上——后两种跟能力无关。

**第三步，读 `/proc/PID/status` 的五行。**

```bash
pid=$(pgrep -u web -f '/usr/local/bin/web' | head -1)
grep '^Cap' /proc/$pid/status
capsh --decode=$(awk '/^CapEff/{print $2}' /proc/$pid/status)
```

| 行 | 对应集合 | 拿它判什么 |
|:--|:--|:--|
| `CapEff` | effective | 内核判权限只看这一行；它为空就是没生效 |
| `CapPrm` | permitted | 上限；只写 `+p` 时它有值而 `CapEff` 为空 |
| `CapBnd` | bounding | 天花板；这里没有的位，文件写了也进不来 |
| `CapInh` | inheritable | 通常全 0，只表示「允许带过去」 |
| `CapAmb` | ambient | 非特权程序 `execve` 后仍保留的那批 |

`+p` 与 `+ep` 的差别就在这三行的组合上；`--cap-drop=ALL` 的容器里 `CapBnd` 全 0，`setcap` 写得再对也拿不到。

**第四步，知道整条路可能被关掉。** `nosuid` 挂载、systemd 的 `NoNewPrivileges=yes`、容器的 `--cap-drop`，以及内核启动参数 `no_file_caps`（`capabilities(7)` 明写：这种情况下文件能力按空集处理）都会让 `setcap` 白做。`capsh --print` 列出 securebits 与各集合；较新的内核与 libcap 还会显示「禁止非特权任务使用文件能力」一类的标志，有的版本写作 `NO_FILE_TASKS` 这样的字样。名称随版本变，本机没法验证，以你自己机器上 `capsh --print` 的 flags 行为准。

**第五步，keep_caps：降权之后还想留一手。** UID 变动时内核会修正能力集：euid 从 0 变非 0，清空 effective；real、euid、saved 原本有 0、改完全非 0，permitted 与 effective 一起清空。`prctl(PR_SET_KEEPCAPS, 1)`（等价标记 `SECBIT_KEEP_CAPS`）挡的是第二条：让 permitted 留住，但 effective 照样被清，所以后面还得用 `cap_set_proc()` 把需要的那位重新提进 effective。三条边界记住：这个标记在每次 `execve` 时总被清除；`SECBIT_NO_SETUID_FIXUP` 一旦设置，轮不到 keep_caps 起作用（后者是前者的子集）；它只解决「我已经有这些位，别因为我改 UID 就收走」，不会给你任何新的能力。

想知道一个程序到底需要哪一项，用 `strace` 找返回 `EPERM` 的系统调用再对照 `capabilities(7)`；这条线索不完美，`EPERM` 也可能由别的原因产生。

**看不到预期结果时先查什么。** `getcap` 空 → 二进制被覆盖过；被授权的是脚本而不是 ELF；`CapEff` 为 0 但 `CapPrm` 有值 → 只写了 `+p`；`CapBnd` 里缺这一位 → 容器或 unit 做过 drop；挂载点带 `nosuid`；unit 里 `NoNewPrivileges=yes`。回滚是 `sudo setcap -r /usr/local/bin/web`，改完重新 `getcap` 确认空。

::: errata 关于三个实验的误解
1. **「`chmod u+s` 之后 euid 一定变」**——本机实测就演示了反例：属主是你自己时，位加上了、身份没变；`nosuid` 挂载、脚本、`NoNewPrivileges=yes` 也都会让它不变。
2. **「`ls -l` 末尾的 `+` 只是装饰」**——它说明组三位已经被换成 mask，那九位不再描述真实判定。
3. **「`getfacl` 里条目写 `rwx` 就是能写」**——要读的是 `getfacl -e` 补出来的 `effective:`。
4. **「`CapEff` 为 0 说明机器坏了」**——普通用户的 Shell 本来就该是 0；要看的是那个特权程序**运行时**的值。
5. **「setuid 程序里用 `system()` 只是图省事」**——`system()` 会起 shell，而 shell 继承当前 euid，`PATH` 与 `IFS` 由调用者控制；`AT_SECURE` 只让 glibc 忽略 `LD_PRELOAD`，管不了程序自己拼的命令行。
:::

### 0.4.20 小结

三个实验各留一条判据：setuid 看 `geteuid()` 与 `getresuid()` 的三个值，而不是 `ls -l` 里那个 `s`；ACL 看 `getfacl -e` 的 `effective:` 与 `mask::`，而不是条目本身写了什么；capability 看运行时 `/proc/PID/status` 的 `CapEff`、`CapPrm`、`CapBnd`，而不是 `getcap` 的输出。如果只记住一件事，那就是：**特权类问题要用运行时的身份来回答**——文件上的位与属性只是「申请」，进程实际拿到的那张牌才算数；本机跑不了的部分，我们只给了判读顺序，没编输出。

::: method 即时自测 · 0.4.20
**Q1（记忆）** 执行 setuid 程序时，real、effective、saved 三个 UID 各发生什么变化？saved 的值从哪来？

**Q2（辨析）** 本机 `chmod u+s` 后 euid 没变，和 Linux 上 `nosuid` 挂载导致 euid 没变，是同一件事吗？各怎么确认？

**Q3（应用）** 一个自编译工具要读 `/etc/shadow` 做口令校验，不想 setuid root。写出 capability 路线的操作步骤与三条验收判据。

**Q4（迁移）** 同事说「我 `setcap` 了，服务起来还是 `EACCES`」。按本节给的顺序给出四步排查，并说明每步看到什么算命中。

::: sol 答案
**A1** effective 被换成文件属主的 UID，real 保持不变（还是登录的你），saved 由那个**新的** effective 复制而来——不管文件有没有 setuid 位都执行这次复制，所以程序能在 real 与 saved 之间来回切。
**A2** 不是。前者是语义如此：setuid 只把 euid 换成属主，而属主就是你，`ls -l` 有 `s`、`geteuid()` 不变；后者是内核忽略这个位，先 `findmnt -T 路径 -o TARGET,OPTIONS` 看有没有 `nosuid`。两种情况都得靠运行时的 `geteuid()` 判定，别看 `ls`。
**A3** `sudo setcap cap_dac_read_search=+ep ./chk`；三条判据：`getcap ./chk` 只列这一条；运行时 `capsh --decode=$(awk '/^CapEff/{print $2}' /proc/PID/status)` 里出现 `cap_dac_read_search`；`CapPrm` 与 `CapEff` 一致（不一致说明只写了 `+p`）。再确认挂载点没有 `nosuid`、unit 没开 `NoNewPrivileges=yes`。
**A4** ① `getcap` 看文件上写着什么、后缀是不是 `ep`（只有 `p` 就命中「effective 没起」）；② `grep '^Cap' /proc/PID/status` 看 `CapEff`，为 0 就继续；③ `findmnt -T 可执行文件 -o OPTIONS` 查 `nosuid`，`systemctl show -p NoNewPrivileges 服务名` 查提权是否被禁；④ `CapBnd` 里有没有这一位（容器与 unit 的 drop 留在这里）。四步都对还失败，才去怀疑那根本不是 DAC 问题——`EACCES` 也来自 SELinux 或 AppArmor。
:::
:::

## 0.4.21 两个可运行脚本 {#sec-0.4.21}

这一节回答：0.4.9 那段一次性扫描代码，怎么变成敢挂进 cron、第二天能看出「哪里变了」的脚本？capability 这类「装在文件系统里」的授权，怎么定期自检？

::: preview 先抓住一件事
两个脚本都只读，共用同一条安全骨架：`set -euo pipefail`、先确认能写再落盘、范围用参数限定、临时目录配 `trap` 清理。区别在目的——`perms-report.sh` 把 0.4.9 的四类对象固化成**可比的快照**，靠差异发现新增的 SUID 文件；`fcap-audit.sh` 回答另一类问题：这台机器上哪些二进制带着特权，低端口被谁占着。
:::

面向 Ubuntu 24.04 的 GNU findutils 与 bash。我们在本机（macOS）只做到 `bash -n` 语法检查：BSD `find` 没有 `-printf`，`getfacl`、`getcap` 也不存在，两个脚本的运行结果都需要 Linux 主机，本机未实测。

### 脚本一：`perms-report.sh`——带差异比较的权限审计

**这类故障长什么样。** 0.4.9 的脚本跑完把四类对象打到屏幕上，看完就没了。两周后 `/opt` 下多出一个 `-rwsr-xr-x root root /opt/tools/updater`，没人知道它是哪天出现的、上一个是什么。审计要的是**可比的快照**：同一台机器每天跑一次，只报告「新增了什么、少了什么」，异常才需要人解释。

```bash
#!/usr/bin/env bash
# perms-report.sh — 权限审计四类对象 + 与上次快照的差异；本身只读
# 用法: perms-report.sh [-d DIR]... [-s STATE_DIR] [--save]
set -euo pipefail
die() { printf 'error: %s\n' "$*" >&2; exit 2; }

roots=() state=${PERMS_STATE_DIR:-/var/lib/perms-audit} save=0
while (($#)); do
    case $1 in
        -d)     [[ $# -ge 2 && -d $2 ]] || die "-d needs an existing directory"
                roots+=("$2"); shift 2 ;;
        -s)     [[ $# -ge 2 ]] || die "-s needs a directory"; state=$2; shift 2 ;;
        --save) save=1; shift ;;
        *)      die "unknown option: $1" ;;
    esac
done
((${#roots[@]})) || roots=(/)

# 先确认可写再扫；不能写就只打印，不留半截快照
if (( save )); then
    mkdir -p "$state" 2>/dev/null || die "cannot create state dir: $state"
    [[ -w $state ]] || die "$state not writable: run as root or point -s elsewhere"
fi

tmp=$(mktemp -d) || die "mktemp failed"
trap 'rm -rf -- "$tmp"' EXIT INT TERM

printf 'host=%s user=%s uid=%s at=%s\n' \
    "$(hostname)" "$(id -un)" "$(id -u)" "$(date -u +%FT%TZ)"

prune=( \( -path /proc -o -path /sys -o -path /dev -o -path /run \) -prune -o )
for r in "${roots[@]}"; do
    # 每条都带 || true：pipefail 会让「读到无权限目录」直接杀掉整个扫描
    find "$r" -xdev "${prune[@]}" -type f \( -perm -4000 -o -perm -2000 \) \
         -printf 'SUIDGID %M %u:%g %p\n' 2>/dev/null || true
    find "$r" -xdev "${prune[@]}" -type d -perm -0002 ! -perm -1000 \
         -printf 'WWDIR %M %u:%g %p\n' 2>/dev/null || true
    find "$r" -xdev "${prune[@]}" \( -nouser -o -nogroup \) \
         -printf 'ORPHAN %u:%g %p\n' 2>/dev/null || true
    # ACL 交给一个 getfacl -R 进程；别用 -exec 逐文件起 shell
    if command -v getfacl >/dev/null 2>&1; then
        { getfacl -R -p -- "$r" 2>/dev/null || true; } |
            awk '/^# file:/{f=$3}
                 /^(default:)?(user|group):[-_.[:alnum:]]+:/{print "ACL " f " " $0}'
    fi
done | sort > "$tmp/current"

prev="$tmp/prev"
if [[ -f $state/latest.snap ]]; then
    sort -- "$state/latest.snap" > "$prev"
else
    : > "$prev"          # 第一次跑：没有基准，全部算新增
fi

printf '\n== 与上次快照的差异 ==\n'
printf 'added=%d removed=%d\n' \
    "$(comm -13 "$prev" "$tmp/current" | wc -l)" \
    "$(comm -23 "$prev" "$tmp/current" | wc -l)"
comm -13 "$prev" "$tmp/current" | sed 's/^/+ /'
comm -23 "$prev" "$tmp/current" | sed 's/^/- /'

printf '\n== 全量清单 ==\n'
cat -- "$tmp/current"

if (( save )); then
    stamp=$(date +%Y%m%dT%H%M%S)
    install -m 0600 "$tmp/current" "$state/report.$stamp.snap"
    install -m 0600 "$tmp/current" "$state/latest.snap"
fi
```

最关键的三行。其一，`find "$r" -xdev $prune -o ... 2>/dev/null`：`-xdev` 按设备号跳过别的文件系统，`-prune` 按路径排除 `/proc`、`/sys` 与容器 bind mount（0.4.9 的教训——设备号相同的 bind mount 靠 `-xdev` 拦不住），扫描范围本身就是结论的一部分。其二，`sort` 之后才能用 `comm -13`/`comm -23`：`comm` 要求两个输入都按同一顺序排好，所以快照存的是排好序的行；第一次跑没有 `latest.snap`，`prev` 是空文件，全部算 `added`，这是设计不是 bug。其三，落盘用 `install -m 0600` 而不是 `>`：快照里有路径、属主、mode，等于一张本机特权地图，默认权限不该是 0644；`install` 一次完成「复制 + 设权限」，不留中间态（0.4.15 里那个 `install -m 600` 的教训同样适用）。

一处已知取舍：ACL 段用 `getfacl -R -p`（`-p` 保留绝对路径的前导斜杠，否则比对时路径对不上），它只报具名条目与 `default:` 条目，`mask::` 不单独成行；要审计 mask，给那段 awk 再加一条模式。

**怎么测它。** 全程在临时目录里，不碰真实数据：

```bash
bash -n perms-report.sh                      # 只做语法检查，改完先过这关
d=$(mktemp -d); s=$(mktemp -d)
mkdir -p "$d/srv" && printf 'x\n' > "$d/srv/a.txt" && chmod 777 "$d/srv"
./perms-report.sh -d "$d" -s "$s"             # 不落快照，只看报告
./perms-report.sh -d "$d" -s "$s" --save      # 落第一份快照
cp /bin/ls "$d/srv/updater" && chmod 4755 "$d/srv/updater"
./perms-report.sh -d "$d" -s "$s" --save      # 第二次：应多出一行 SUIDGID
```

本机跑出来是这样——流程通了，清单是空的：

```text
host=<本机主机名> user=juanwang uid=501 at=2026-10-29T05:17:43Z

== 与上次快照的差异 ==
added=0 removed=0

== 全量清单 ==
$ ls -l "$s"
total 0
-rw------- 1 juanwang staff 0 Oct 29 13:17 latest.snap
-rw------- 1 juanwang staff 0 Oct 29 13:17 report.20261029T131743.snap
```

空清单的原因很具体：BSD 的 `find` 不认 `-printf` 与 `-nouser`，`getfacl` 也不存在，四类对象一条都扫不出来。四类扫描要 Linux 主机加 GNU findutils，本机未实测；本机验到的是流程——参数校验、状态目录可写检查、差异比较、快照落盘权限 0600、临时目录清理。顺带踩到一个真坑：第一版没写 `|| true`，`set -euo pipefail` 里的 `pipefail` 把「find 撞到无权限目录返回 1」放大成整个脚本退出，跑起来停在头部那行之后。

**失败时怎么安全退出。** 三个出口都在扫描之前：目录不存在或不是目录，`-d` 那条 `die` 返回 2；状态目录建不出来或不可写，`--save` 直接退出而不是改半截快照；`mktemp` 失败同样退出。`trap` 挂在 `EXIT INT TERM` 上，Ctrl-C 也不会留下临时目录。

**怎么挂进 cron。** 每天一次，差异行才是你要看的东西：

```cron
17 3 * * * root /usr/local/bin/perms-report.sh -d / -s /var/lib/perms-audit --save >> /var/log/perms-report.log 2>&1
```

以 root 跑，`find` 才不会因为读不到目录而漏条目。`report.*.snap` 会一天攒一个，记得配一条保留策略——0.3.20 的 `safe-clean.sh` 正好是干这个的。

### 脚本二：`fcap-audit.sh`——文件能力与低端口自检

**这类故障长什么样。** 两种相反的走向都出事：升级或重编译之后，`setcap` 写下的能力跟着二进制一起被覆盖，服务起不来报 `EACCES`；或者有人为了省事给自编译程序加了 `cap_sys_admin`，从此这台机器上多了一个「谁是 owner」说不清的特权入口。前者要确认「文件上到底还写着什么」，后者要确认「写着的东西属于哪个包」。`fcap-audit.sh` 一次把两件事列出来，再加一段低端口占用情况。

```bash
#!/usr/bin/env bash
# fcap-audit.sh — 文件能力与低端口自检；只读
# 用法: fcap-audit.sh [DIR]...      默认 /usr /usr/local /opt
set -euo pipefail
die() { printf 'error: %s\n' "$*" >&2; exit 2; }

roots=("$@"); ((${#roots[@]})) || roots=(/usr /usr/local /opt)
for r in "${roots[@]}"; do [[ -d $r ]] || die "no such directory: $r"; done
command -v getcap >/dev/null 2>&1 || die "getcap 不在：这个脚本要 Linux 加 libcap"

printf '== 内核侧开关 ==\n'
printf 'cap_last_cap=%s\n' "$(cat /proc/sys/kernel/cap_last_cap 2>/dev/null || echo unknown)"
if grep -q -- 'no_file_caps' /proc/cmdline 2>/dev/null; then
    printf 'NOTE: 内核带 no_file_caps，文件能力一律按空集处理\n'
fi

printf '== 带文件能力的二进制 ==\n'
start=$SECONDS
while IFS= read -r line; do
    path=${line%% *}
    case $line in
        *cap_sys_admin*|*cap_dac_override*|*cap_dac_read_search*| \
        *cap_setuid*|*cap_sys_ptrace*|*cap_net_raw*)
            printf 'HIGH %s\n' "$line" ;;
        *)  printf 'info %s\n' "$line" ;;
    esac
    owner=$(dpkg -S "$path" 2>/dev/null || rpm -qf "$path" 2>/dev/null || echo unowned)
    printf '     owner=%s\n' "$owner"
done < <(getcap -r "${roots[@]}" 2>/dev/null || true)
printf 'scan_seconds=%d roots=%s\n' $((SECONDS - start)) "${roots[*]}"

printf '== 正在监听低端口的套接字 ==\n'
ss -lntH 2>/dev/null |
    awk '{ split($4, a, ":"); p = a[length(a)]
           if (p ~ /^[0-9]+$/ && p + 0 < 1024) print "LOWPORT", $4 }' ||
    printf 'ss 不可用，改用：netstat -lnt\n'
```

最关键的三行。其一，`getcap -r "${roots[@]}"` 配 `scan_seconds=`：它要遍历整棵树并对每个文件读一次 xattr，耗时与文件数成正比，所以默认只覆盖 `/usr`、`/usr/local`、`/opt`，先看 `scan_seconds` 再决定要不要扩范围，别一上来扫 `/`。用 `< <(...)` 进程替换而不是管道，是为了让 `start` 与循环留在当前 shell（0.3.20 讲过管道最后一段在子 Shell 里丢变量）。其二，`case` 里的 `HIGH` 分级：`cap_sys_admin`、`cap_dac_override`、`cap_dac_read_search`、`cap_setuid`、`cap_sys_ptrace`、`cap_net_raw` 任何一项都接近 root（0.4.16 的结论），把它们和 `cap_net_bind_service` 平铺在一张清单里，人眼一定会漏掉真正要看的那几行。其三，`dpkg -S ... || rpm -qf ... || echo unowned`：带特权的二进制如果不属于任何软件包，就是那条要追问「谁装的、什么时候、为什么」的条目——0.4.9 自测里那三步，这里变成脚本自动做完。

`HIGH` 不等于违规。发行版本身就给 `ping` 带 `cap_net_raw=ep`，它会被标成 `HIGH`；这张清单是**待核查**清单，不是处罚名单。

**怎么测它。** 本机没有 `getcap`，但这恰好能验最有价值的那条路径——拒绝执行：

```bash
$ bash -n fcap-audit.sh && ./fcap-audit.sh
error: getcap 不在：这个脚本要 Linux 加 libcap
$ ./fcap-audit.sh /etc/hosts
error: no such directory: /etc/hosts
```

两段都是本机实测，退出码 2。Linux 侧的形状已在 Ubuntu 24.04 上核过：第一段给 `cap_last_cap`（实测 `40`，即能力编号 0–40 共 41 项；能用来判断内核与 libcap 是否脱节），第二段是 `HIGH`/`info` 加 `owner=` 的成对行，第三段是 `LOWPORT *:80` 这类套接字行。非 root 跑完全安全：脚本没有任何写操作。

::: errata 关于两个脚本的误解
1. **「报告为空说明这台机器干净」**——更常见的原因是没权限扫、工具不存在或 `find` 不是 GNU。先回头看 `uid=` 那一行和 `scan_seconds=`，再下结论。
2. **「`HIGH` 就是入侵痕迹」**——发行版自带的 `ping` 就带着 `cap_net_raw=ep`，会被标成 `HIGH`。这张表是待核查清单，不是处罚名单。
3. **「拿两份报告直接 `diff` 就行」**——`comm` 要求两个输入按同一规则排好序；更要紧的是别把带时间戳的头部行混进快照，否则每天都是「全部新增」。脚本把头部单独打印、快照只存排序后的条目，就是这个原因。
4. **「有 `-xdev` 就不用 `-prune`」**——`-xdev` 只看设备号，容器的 bind mount 与源同设备，照样扫进去（0.4.9）。
5. **「`set -e` 已经够安全」**——加上 `pipefail` 之后，`find` 撞到无权限目录返回 1 会让整个脚本猝死。扫描类脚本要么显式 `|| true`，要么把错误单独记账；本机第一次跑就撞上了这个坑。
6. **「试运行的清单等于执行时的清单」**——快照是那一刻的；差异只在「两次运行之间发生了什么」这一层有意义，所以要留每天的快照而不是每次临时打印。
:::

### 0.4.21 小结

`perms-report.sh` 把 0.4.9 的四类对象变成**可比的快照**，价值全在差异行上；`fcap-audit.sh` 把「文件上写着什么特权」与「这特权属于哪个包」并排列出，再顺手看一眼低端口。两者共用同一条骨架：只读、参数校验先行、临时目录配 `trap`、确认能写才落盘、落盘权限 0600。如果只记住一件事，那就是：审计脚本的产出必须能与昨天的自己相比——一次性的漂亮清单，第二天就毫无价值。

## 0.4.22 本章小结 {#sec-0.4.22}

这一节回答：两遍走完，这一章到底留下了什么？

::: preview 先抓住一件事
第一遍你会读 `ls -l`、算 umask、用 `chmod`/`chown`/`setfacl`/`setcap` 把授权做完；第二遍你能说清 mode 的位与判定路径、ACL 的 mask、capability 的那次算术、setuid 在 `execve` 里改了哪三个 ID；最后的实验与脚本把结论变成能复现的动作和敢挂 cron 的模板。逐项打勾去 [学习目标自检表](ch04-checklist.md)，这里不收尾清单。
:::

第一遍只要求你把活干对。一次 `Permission denied` 不是一行数字的问题，而是一条链上的一个点，所以要按顺序问：`id` 看现在的身份、`namei -l` 看路径能不能穿过去、`stat` 看你落在属主/组/其他哪一档、`getfacl` 看具名条目与上限、`aa-status` 或 `getenforce` 看有没有被 LSM 拦下（0.4.1、0.4.9）。mode 的九位把人分成三档，属主一档命中就不再往下看组（0.4.2、0.4.10）。目录的 `r`、`w`、`x` 是三种不同的能力：列名字、改目录项、穿过它（0.4.3、0.4.11）——所以「有 r 没 x」能列名却打不开任何文件。umask 只管新建、不管已有，`chmod` 反过来（0.4.4、0.4.12）。要给用户单独开权限就 `setfacl`，要给程序只留一项特权就 `setcap`，要管人就管 `passwd`/`shadow`/`group` 那三张表和 sudoers（0.4.6–0.4.8）。

第二遍回到结构与边界。mode 在 inode 里就是十二个位，内核的判定路径从 `inode_permission` 走到 DAC、再问 ACL、最后交给 LSM（0.4.10、0.4.11）。sticky 让「能写这个目录」不等于「能删别人的文件」，`/tmp` 的 `1777` 是这套语义的样板（0.4.11、0.4.14）。umask 有三个来源，优先级从 shell 到服务到账号本身（0.4.12）。

身份切换只发生在 `execve` 那一步，而且做了两次复制：euid 换成文件属主，saved 再由那个新的 euid 复制而来；脚本上的 setuid 位被 Linux 忽略，`nosuid` 挂载与 `NoNewPrivileges=yes` 让它整体失效（0.4.14）。

限制访问的有两套不同东西。ACL 分访问条目、默认模板与 mask 三层，mask 只压组类条目，而 `ls -l` 的组三位显示的正是它（0.4.15）。capability 则是一次算术：继承交集、文件 permitted 过 bounding、ambient 三条来路相或，内核只看 effective，bounding 只能减不能加（0.4.16）。

管人的那两层看答案而不是看文件。账号的真相在 NSS 给出的答案里，`!` 只是口令前缀、`nologin` 只挡交互 shell、`chage -E` 只挡时间窗（0.4.17、0.4.18）。sudo 判的是你敲下去的那一行命令行；程序跑起来之后能起子进程、能读写文件，都在它的授权范围之外（0.4.19）。

最后压成能力。0.4.20 的三个实验给每条争论一个可判定的证据：setuid 看 `geteuid()` 与 `getresuid()` 读回的三个值，别看 `ls -l` 里那个 `s`；ACL 看 `getfacl -e` 补出来的 `effective:`，别看条目写了什么；capability 看运行时 `/proc/PID/status` 的 `CapEff`、`CapPrm`、`CapBnd`，别看 `getcap`。0.4.21 的两个脚本把安全默认写成模板：只读、参数校验先行、临时目录配 `trap`、确认能写才落盘、快照权限 0600、审计结果能跟昨天的自己比。

下次遇到权限问题，按症状选东西就行。报 `Permission denied`：先 `id`，再 `namei -l`，再 `stat`，最后 `getfacl`——顺序不能反，因为后一步的证据只在前一步解释不通时才有意义。`ls -l` 出现 `+`：`getfacl -e` 看 `effective:` 与 `mask::`。出现 `s`：这是不是 ELF、属主是谁、挂载点有没有 `nosuid`。出现 `t`：sticky 在管谁能删这个目录里的文件，不是谁能读。服务绑不上低端口：先 `ss -lnt` 分清 `EADDRINUSE` 和 `EACCES`，再看那个进程运行时的 `CapEff`。容器里 setuid 或 capability 忽然失效：`findmnt` 看挂载选项、`grep NoNewPrivs /proc/PID/status`、`CapBnd` 是不是被 `--cap-drop` 清成 0。`sudo` 报 `command not found`：`sudo -l` 里的 `secure_path`。ACL 给了还不行：mask，然后路径上的 `x`，然后 LSM。这几件东西串起来，就是一条能指认的链路。

### 0.4.22 小结

第一遍把命令用对，第二遍用位、集合、算式与判定顺序讲清为什么，实验和脚本把两者变成能复现的动作与敢上线的模板。逐项自检在 [学习目标自检表](ch04-checklist.md)。如果只记住一件事，那就是：**访问判定是一条链，不是一行数字**——DAC 的 mode，到 ACL 的条目与 mask，到 LSM，再到挂载选项与命名空间（`nosuid`、`ro`、`--cap-drop`、seccomp），任何一层都能拒你。「mode 看着对却还是 `Permission denied`」是常态而不是玄学；把证据按层的顺序拿一遍，答案自然会露出来。
