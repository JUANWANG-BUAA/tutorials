0.9 里 `D` 状态的进程，多半卡在块设备 I/O 上。再往上走一层，就是磁盘、分区、文件系统、挂载点这套栈。日常故障里，「磁盘满了」这四个字的含义至少有五种：数据真的写满了、inode 用完了、预留块吃掉了余量、删除的文件仍被进程打开、或者写的是另一个挂载点。

这一章先把「看」和「算」讲清楚，再动「改」。所有分区、格式化、删除类命令都会给安全警告和回滚；LVM 和 RAID 的实验全部在 `/var/tmp/block-lab` 下的镜像文件上通过 `losetup` 完成，不碰 `/dev/nvme*` 或 `/dev/sd*`。

只提醒一次：`mkfs`、`wipefs`、`lvremove`、`mdadm --create` 都是不可逆操作。真盘误操作唯一可靠的回滚是备份；`testdisk` 之类的工具是补救，不是回滚。

::: note 安全警告 · 设备名必须来自证据
动手前固定做三件事：

1. `lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS` 确认目标不是根盘、不是已挂载的数据盘；
2. `findmnt <目标>` 与 `df -h <目标>` 确认它没有被挂载；
3. 生产环境用 `/dev/disk/by-id/` 下的稳定名字，不用 `/dev/sdX`——盘序会变，名字会漂。

本章的 LVM/RAID 脚本只操作 `losetup` 出来的 `/dev/loopN`；如果你把它们改成真盘路径，后果由你承担。
:::

## 0.10.1 先看清块设备：`lsblk`、`findmnt`、`df` {#sec-0.10.1}

这一节回答：从一块裸盘到「你能写文件的目录」，中间隔着块设备、分区、文件系统、挂载点四格；`lsblk`、`findmnt`、`df` 各自站在哪一格上看？

::: preview 先抓住一件事
三条命令读三份不同的资料：`lsblk` 读 `/sys` 下的设备树，回答「机器上有几块盘、每块切了几个区」；`findmnt` 读内核的挂载表，回答「哪个文件系统盖在哪个目录上」；`df` 读已挂载文件系统的空间统计，还会按类别悄悄滤掉一批条目。它们给出的条目数对不上是常态，不是命令出了错。
:::

### 0.10.1.1 先看一眼这台机器

Ubuntu 24.04.5 虚拟机（aarch64，内核 `7.0.0-38-generic`）上原样跑一条：

```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
```

```text
NAME     SIZE TYPE FSTYPE   MOUNTPOINTS
loop0      4K loop squashfs /snap/bare/5
loop1   61.9M loop squashfs /snap/core24/1644
loop2  248.4M loop squashfs /snap/firefox/8862
loop3  552.9M loop squashfs /snap/gnome-46-2404/154
loop4   91.7M loop squashfs /snap/gtk-common-themes/1535
loop5  188.2M loop squashfs /snap/mesa-2404/1836
loop6   10.9M loop squashfs /snap/snap-store/1391
loop7   43.5M loop squashfs /snap/snapd/27740
loop8    804K loop squashfs /snap/snapd-desktop-integration/396
loop9   38.6M loop squashfs /snap/snapd/28255
sda       64G disk
├─sda1    1G part vfat      /boot/efi
└─sda2 62.9G part ext4      /
sr0     1024M rom
```

这张表里只有 `sda` 那一支是真存储：一块 64 GiB 的盘（`disk`），切成两个分区（`part`），`sda2` 上是 `ext4`，挂在 `/`。`sda` 这一行的 `FSTYPE` 和 `MOUNTPOINTS` 都是空的——整块盘没有文件系统，也不可能被挂载，文件系统只在分区上。`sr0` 是虚拟机挂的虚拟光驱（`rom`），`1024M` 是 Parallels 那张安装镜像的大小。

### 0.10.1.2 四格链：谁住在哪一格

**块设备**（block device，能按固定大小的块读写的数据容器，最小单位是扇区或逻辑块）是链子的头一格。往下依次是分区、文件系统、挂载点。

::: def 定义 0.10.1 · 存储链的四格 {#def-0.10.1}
**块设备**（`lsblk` 的 `TYPE=disk`）是一块完整硬件，比如 `/dev/sda`。**分区**（`TYPE=part`）是按字节范围从盘上切出来的一段，比如 `/dev/sda2`，内核把它当成一个独立的块设备看待。**文件系统**是分区内部的组织方式（ext4、XFS、vfat……），`mkfs` 写下的那套结构，`lsblk` 用 `FSTYPE` 显示，来源是超级块里的类型标记。**挂载点**（mount point，挂载是把一个文件系统的根接到目录树某个节点上）是这个文件系统在你这棵树上显示出来的路径。四格中任何一格缺失，你都无法往里面写文件。
:::

`lsblk` 只认前两格和「这块设备被谁用了」，它不会告诉你 `/data` 这个目录属于哪个区。`TYPE` 除了 `disk`/`part`，还会见到 `lvm`（逻辑卷）、`raid1`/`raid5`（软 RAID 成员）、`crypt`（dm-crypt 加密层）、`loop`（把一个文件伪装成块设备）。后三类都是「叠在真盘之上」的虚拟设备，树形缩进正好把它们和底层盘的关系画出来。

`sr0` 的 `rom` 与 `loop` 都不是分区，也不是逻辑卷：`rom` 是只读光盘类设备，`loop` 是「把一个普通文件当块设备用」的机制。这台机器上十个 `loop` 全来自 snap：每个 snap 包是一个 `.snap` 文件，格式是 squashfs 只读文件系统，snapd 用 loop 设备把它挂起来——于是「十个已安装的 snap」在 `lsblk` 里就变成十行 `loop`。它们不占任何磁盘分区，看起来吓人，其实只是文件：

```bash
losetup -a
```

```text
/dev/loop0: []: (/var/lib/snapd/snaps/bare_5.snap)
/dev/loop1: []: (/var/lib/snapd/snaps/core24_1644.snap)
/dev/loop2: []: (/var/lib/snapd/snaps/firefox_8862.snap)
...
/dev/loop7: []: (/var/lib/snapd/snaps/snapd_27740.snap)
/dev/loop9: []: (/var/lib/snapd/snaps/snapd_28255.snap)
```

`loop7` 和 `loop9` 都指向 snapd，但版本号不同：snap 升级时保留上一个版本用于回滚，两个版本会同时挂在树里（`/snap/snapd/27740`、`/snap/snapd/28255`），当前生效的那个由 `/snap/snapd/current` 这个符号链接指认。容器和虚拟化环境里的快照镜像、`genisoimage` 产出的 ISO、你手工挂上去的磁盘镜像文件，都是同一套 loop 机制。

### 0.10.1.3 `findmnt -T`：这个路径到底落在哪个设备上

`lsblk` 回答「有什么设备」，`findmnt` 回答「目录树上的这一节点是谁」。日常最值钱的一个用法是 `-T`：给它一个路径，它把**最长匹配**的那个挂载点交给你。

```bash
findmnt -T /tmp
findmnt -T /run/user/1000
findmnt -T /media/psf/Home
```

```text
TARGET                SOURCE   FSTYPE
/                     /dev/sda2 ext4
/run/user/1000        tmpfs    tmpfs
/media/psf/Home       Home     fuse.prl_fsd
```

三行讲的是三件不同的事：`/tmp` 没有独立挂载，它落在根文件系统 `ext4` 上，所以往 `/tmp` 写满就是把 `/` 写满；`/run/user/1000` 是 `tmpfs`，即内存文件系统，重启就没了；`/media/psf/Home` 是 Parallels 的共享目录，由用户态进程通过 FUSE（Filesystem in Userspace，把文件系统实现搬到用户态进程的机制）提供，`SOURCE` 显示成一个叫 `Home` 的名字而不是设备节点。

`findmnt` 默认输出整棵挂载树，`findmnt --real` 只留有真设备的部分（滤掉 `proc`、`sysfs`、`cgroup2` 这类伪文件系统，但保留 loop 和 tmpfs）。看挂载选项要显式要：

```bash
findmnt -T / -o TARGET,SOURCE,FSTYPE,OPTIONS
```

```text
TARGET SOURCE    FSTYPE OPTIONS
/      /dev/sda2 ext4   rw,relatime
```

`OPTIONS` 是**此刻真正生效**的选项，来源是内核的挂载表（`/proc/mounts` 同一份数据），不是 `/etc/fstab` 里写的字。两者不一致时，以这里为准；`fstab` 只在挂载那一刻被读一次（细节见 [0.10.5](ch10.md#sec-0.10.5)）。

### 0.10.1.4 `df`：站得最低，还挑顾客

`df` 站在链子最上面那一格，读每个已挂载文件系统的空间统计，用的正是 `statvfs()`/`statfs()` 这一族调用。同一台机器上，三个命令的条目数是这样的：

```bash
findmnt -n -o TARGET | wc -l
df | tail -n +2 | wc -l
df -a | tail -n +2 | wc -l
```

```text
39
9
38
```

`df` 少掉的 30 条不是 bug：它默认滤掉伪文件系统、重复挂载和**自己读不到**的挂载。`df -a` 补回大部分，剩下的那一条正是读不到的：

```text
df: /run/user/1000/doc: Operation not permitted
```

那是别人会话里的 `fuse.portal` 挂载，你无权 `statfs()`。十个 snap 的 squashfs 也在默认名单之外——`df -aT` 里能数出 10 行 `squashfs`，默认 `df` 一行都没有；更别扭的是 `df -t squashfs` 输出 `df: no file systems processed`：类型白名单并不覆盖那条内置过滤。所以「`findmnt` 有、`df` 没有」至少有三个原因：**被过滤的特殊类型、同一设备重复挂载只列一次、无权访问的挂载点**。

`df` 与 `findmnt` 数字对不上时，先确认这两件事：一是路径本身（`df /path` 和 `findmnt -T /path` 应当给出同一个挂载点），二是文件系统类型（vfat、efivarfs 这类没有 inode 概念的文件系统，`df -i` 会显示 `0` 和 `-`；squashfs 恒为 100%）。`df` 的 `Used` 与 `Avail` 也不是同一分母上的两个数，这一点留到 [0.10.3](ch10.md#sec-0.10.3) 用 `stat -f` 现场算给你看。

::: method 判定流程 · 拿到一台陌生机器先跑三条
1. `lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS`：先确认有几块物理盘、哪些分区已经有文件系统、`TYPE` 里有没有 `lvm`/`raid`/`crypt`/`loop` 这些叠加层。没有 `FSTYPE` 的分区不能挂载，有 `FSTYPE` 没 `MOUNTPOINTS` 的分区是「挂了也没接上树」。
2. `df -hT` 加 `df -i`：看每个挂载点的块与 inode 使用率。`-T` 顺带告诉你类型，后面所有取舍都依赖它。
3. `findmnt -T 你要写的目录`：确认这个路径真正落在哪个文件系统上、选项是不是 `ro`、`noatime`、`nosuid`。写到 `/var/log` 报「只读文件系统」而 `df` 一切正常时，答案几乎总在这一步。
4. 三者矛盾时，按 `findmnt -T` 的结论为准，再决定是否怀疑 snap/容器/绑定挂载带来的特殊条目。
:::

::: ex 例 0.10.1 · 挂载了，但 `df` 里找不到 {#ex-0.10.1}
你在同一台 Ubuntu 24.04 虚拟机上执行：

```bash
findmnt /snap/firefox/8862
df | grep firefox
```

第一条打印出一个完好的挂载条目（`SOURCE=/dev/loop2`、`FSTYPE=squashfs`、`OPTIONS=ro,nodev,relatime,...`）；第二条什么都没有。**先猜**这是不是 `df` 读错了，再解释为什么会这样，并给出一条能同时列出全部挂载点的命令。

::: sol 解答
不是读错。`df` 默认把 squashfs 这类特殊文件系统排除在自己的名单外，所以 `grep` 什么都找不到；`findmnt` 直接列内核挂载表，因此照常显示。要「全都列出来」有两条路：`df -a`（含 pseudo、duplicate、inaccessible，实测条目数从 9 涨到 38）或者 `findmnt -D`（按设备列出空间用量，覆盖范围跟 `findmnt` 一致）。判断一台机器的挂载真相用 `findmnt`，判断「还有多少地方能写」用 `df`——两者本来就不是同一份台账。
:::
:::

::: errata 常见错误清单（0.10.1 节）
1. **「`lsblk` 里有 `FSTYPE` 就说明挂载了」**——`FSTYPE` 只表示分区上写过了文件系统；能不能写文件看 `MOUNTPOINTS` 列，或者 `findmnt -T`。
2. **「`df` 没列出的挂载点就不存在」**——`df` 会滤掉特殊类型、重复挂载和无权访问的条目，实测 39 条挂载只剩 9 条；要看全用 `findmnt` 或 `df -a`。
3. **「`/dev/sda` 也能挂」**——把整块有分区表的盘挂上去，内核会去找位于分区起始处的超级块，通常直接失败；文件系统挂在分区（或 LVM/loop）上，不挂在 `disk` 上。
4. **「`findmnt` 的 `OPTIONS` 就是 `/etc/fstab` 里写的」**——那是内核当前生效的选项；`fstab` 改完没重新挂载，这里不会变。
5. **「十个 `loop` 设备说明机器上有十块盘」**——它们只是十个 `.snap` 文件；`losetup -a` 能逐个给出后备文件路径。
:::

### 0.10.1 小结

`lsblk` 看设备与分区，`findmnt` 看挂载表和实际生效的选项，`df` 看已挂载文件系统的空间且自带过滤；一条链上四格分别属于块设备、分区、文件系统、挂载点，任何一格缺了都写不进文件。如果只记住一件事，那就是：**先问「这个路径落在哪个文件系统上」，再谈它满没满**——`findmnt -T` 一条命令就能把问题定死在一个挂载点上。

::: method 即时自测 · 0.10.1
**Q1（记忆）** 存储链的四格按顺序是什么？`lsblk` 的 `TYPE` 有哪五种以上取值，各代表什么？

**Q2（辨析）** 同一台机器上 `findmnt` 报 39 个挂载点、`df` 只报 9 行。列至少两个原因，并说明哪个命令更适合用来回答「这个目录能不能写」。

**Q3（应用）** 你要确认 `/var/lib/docker` 到底落在哪块盘、是不是独立挂载、当前挂载选项是什么。写出命令与你要读的字段。

**Q4（迁移）** 你换到一台 macOS 开发机（本书作者用的就是），`df -k` 与 `df -i` 的输出列跟 Linux 上不同。先猜差别在哪，再说明怎么确认。

::: sol 答案
**A1** 块设备 → 分区 → 文件系统 → 挂载点。`TYPE`：`disk` 整块硬件、`part` 分区、`loop` 把文件伪装成块设备、`rom` 只读光驱、`lvm`/`raid1`/`raid5`/`crypt` 是叠在真盘之上的映射层。
**A2** ① `df` 默认滤掉伪文件系统与 squashfs 这类特殊类型；② 同一设备的重复挂载只列一次；③ 无权 `statfs()` 的挂载点直接报错跳过（实测 `/run/user/1000/doc: Operation not permitted`）。回答「能不能写」用 `findmnt -T 路径`，它给的是内核真正生效的那一条。
**A3** `findmnt -T /var/lib/docker -o TARGET,SOURCE,FSTYPE,OPTIONS`：`TARGET` 等于 `/var/lib/docker` 说明它是独立挂载，等于 `/` 说明还在根文件系统上；`OPTIONS` 里看 `rw`/`ro`、`noatime`、是否有 `nodev,nosuid`。再补一条 `df -hT /var/lib/docker` 看剩余空间。
**A4** macOS 的 `df -k` 就已经在末尾带了 `iused`、`ifree`、`%iused` 三列，而 Linux 的 `df` 默认只报块；反过来 macOS 的 `df -i` 是把块单位换成 512 字节（表头显示 `512-blocks`），Linux 的 `df -i` 才是「改成报 inode」。本机实测两侧表头如所述；确认方法就是 `df --version`（BSD 版会拒绝这个选项）与看表头单位。
:::

## 0.10.2 文件系统选型与创建 {#sec-0.10.2}

这一节回答：ext4、XFS、Btrfs、tmpfs、procfs 各为哪类负载设计？`mkfs` 到底往分区里写了什么，为什么 `blkid` 一眼就能认出类型？

::: preview 先抓住一件事
选型判据只有四条：小文件多不多、大文件是不是顺序写、要不要快照、是不是可以丢。真正的分水岭在**分配时机**——磁盘上的文件系统在建好那一刻就把 inode 表划完了，内存文件系统（tmpfs）在你写下第一个字节时才分配，虚拟文件系统（`procfs`）干脆不分配。
:::

### 0.10.2.1 内核先要认识它

`cat /proc/filesystems` 列出**当前内核认识的**文件系统类型，前面带 `nodev` 的表示它不需要块设备就能挂载：

```text
nodev	sysfs
nodev	tmpfs
nodev	proc
nodev	cgroup2
nodev	devtmpfs
	ext3
	ext2
	ext4
	squashfs
	vfat
nodev	fuse
nodev	overlay
```

这台 Ubuntu 24.04.5 的名单里有 `ext4`、`vfat`、`squashfs`、`overlay`、`tmpfs`，**没有** `xfs`，也**没有** `btrfs`。模块文件确实在盘上（`/lib/modules/7.0.0-38-generic/kernel/fs/` 下有 `xfs/`、`btrfs/` 两个目录），只是没加载；`modprobe xfs` 需要 root，本书这台机器上做不了，所以 `xfs`/`btrfs` 的一切都属于「机制讲清、数字未实测」。这也解释了一种看起来很怪的故障：镜像里 `mkfs.xfs` 成功了，换台机器 `mount` 报 `unknown filesystem type 'xfs'`——不是超级块坏了，是那颗内核没带这个模块。

### 0.10.2.2 `mkfs` 在分区里写了什么

一个磁盘文件系统不是「一块能写的地方」，而是一套预先砌好的结构。按从分区头开始的顺序：

- **引导块**：分区第一块，文件系统自己不用，留给引导器。
- **超级块**（superblock，整个文件系统的账本首页）：块大小、总块数、inode 总数、inode 表起始位置、挂载状态、校验和设置，以及一个**幻数**（magic number，标识「我是什么文件系统」的固定数值）。
- **块组**（ext 系特有）：分区被切成大小相等的组，每组自带一份超级块副本、组描述符、一段 inode 表、一段数据块位图和数据区。目的是让元数据和它管理的数据在物理上靠近。
- **两张位图**（bitmap，每一位记一个对象是空闲还是已用）：一张记 inode，一张记数据块。**这两张表独立耗尽**，是 0.10.4 全部内容的根。
- **inode 表**：每个文件（含目录、符号链接）固定占一条记录，记录类型、权限、属主、大小、时间戳和指向数据块的指针。

::: def 定义 0.10.2 · 超级块与幻数 {#def-0.10.2}
超级块是文件系统放在分区起始处（以及每个块组里若干备份位置）的一段固定结构，里面记的是「这个文件系统怎么读自己」的全部参数。它的开头有一个约定死的数值字段，工具靠比对它就能判断类型——`blkid` 认出 `TYPE="ext4"` 用的正是这一点，而不是文件扩展名、也不是设备名。Linux 的 `statfs()` 也返回这个值（`f_type`）：`0xef53` 对应 ext2/ext3/ext4 共用的幻数，所以 `stat -f -c %T` 在 ext4 上打印的是 `ext2/ext3`，这是**幻数不区分 ext 三代**的结果，不是显示 bug。
:::

`blkid` 在这台机器上免密就能跑，但它并没有读磁盘：

```bash
blkid /dev/sda2
grep ID_FS /run/udev/data/b8:2
```

```text
/dev/sda2: UUID="fa8bbbea-..." BLOCK_SIZE="4096" TYPE="ext4" PARTUUID="4875e320-..."
E:ID_FS_TYPE=ext4
E:ID_FS_BLOCKSIZE=4096
E:ID_FS_UUID=fa8bbbea-9f92-4241-b344-a824e4b676a6
```

`/dev/sda2` 是 `brw-rw---- root disk`，普通用户打不开（实测 `dd if=/dev/sda2 bs=4096 count=1` 报 `Permission denied`）。`blkid` 走的是 udev 开机时探好并写进 `/run/udev/data/` 的缓存；把缓存关掉（`blkid -c /dev/null /dev/sda2`）就什么都读不出来。所以「`blkid` 认类型」这件事的正确说法是：**它读超级块里的幻数与类型字段，只不过日常读到的是 udev 的缓存副本**。`dumpe2fs`、`tune2fs -l`、`xfs_info` 之外的多数底账要直接读设备，需 root，本机未实测。

### 0.10.2.3 五类文件系统的取向

| 类型 | 数据在哪 | 空间何时分配 | 设计取向 | 什么时候选它 |
|:--|:--|:--|:--|:--|
| ext4 | 块设备分区 | `mkfs` 时就划完 inode 表，数据块写入时分配 | 通用、保守、工具链最全 | 根文件系统、小中容量数据盘 |
| XFS | 块设备分区 | inode 按需增长（有上限比例） | 大文件、顺序写、高并发分配 | 视频/备份/数据库大对象，RHEL 系默认 |
| Btrfs | 块设备分区 | 写时复制（copy-on-write, COW），改一块才复制一份 | 快照、校验和、子卷 | 需要「随时回滚一个目录」 |
| tmpfs | 内存，必要时用 swap | 写下第一个字节才占页；不预先划 inode 表 | 快速、可丢、限额挂载 | `/dev/shm`、`/run`、编译中间文件 |
| procfs/sysfs | 内核数据结构 | 从不分配磁盘空间 | 内核把内部状态投影成文件 | 你不是「选」它，是内核替你挂了 |

选型判据按顺序问四件事，哪一问先命中就照它答：**小文件数量**（几百万个几百字节的文件：XFS 的动态 inode 更省心，ext4 必须提前把 inode 比例调大）；**大文件顺序写**（ext4 的块组预分配够用，XFS 的分配栈在高并发创建/删除上更稳）；**要不要快照与逐块校验和**（要就 Btrfs 或 ZFS，不要就 ext4/XFS，别为了「听起来先进」上一整套新工具链）；**数据能不能丢**（能丢且要快就 tmpfs，不能丢的永远别放 tmpfs）。

两条硬约束值得单独记住：**XFS 不能缩容**，要缩只能备份、重建、恢复；**Btrfs 的 RAID5/6 不要用于生产**，早期实现有掉数据的风险。其余差别都在性能和运维习惯上，不在「哪个更高级」。

### 0.10.2.4 `mkfs` 的参数：只在决策，不在跑

下面这些都需要 root（要打开块设备并写超级块），本书这台虚拟机 sudo 需要密码，**全部未实测**；参数含义与判读方法照给。

```bash
sudo mkfs.ext4 -b 4096 -i 16384 -m 5 -J size=256 -L data /dev/sdb1
sudo mkfs.xfs -f -b size=4096 -l size=512m -i maxpct=25 /dev/sdb1
```

ext4 一侧最要紧的三个：`-b` 定块大小（1024/2044/4096，创建后不可改，4 KiB 是通用选择，全是小文件也不值得为了省空间降到 1024）；`-i` 是 bytes-per-inode，「每多少字节配一个 inode」，默认 16384，越小 inode 越多；`-N` 直接指定 inode 总数，跳过比例计算。`-m` 是预留块比例（默认 5%），`-J size=` 定日志大小，`-O` 开关特性位（`metadata_csum`、`64bit`、`dir_nlink` 等）。XFS 的对应项是 `-i maxpct=`（inode 最多可占空间的比例）与 `-l`（内部日志）、`-f`（确认覆盖已有文件系统）。

卷标 `-L` 之后能用 `LABEL=data` 挂载，比 UUID 好读，但卷标可以重名；生产环境的 `/etc/fstab` 仍写 UUID 或 `/dev/disk/by-id/` 的稳定名字（见 [0.10.5](ch10.md#sec-0.10.5)）。

`-i`/`-N` 为什么值得在格式化前想清楚，用本机三条免特权命令就能算出来，见例 0.10.2。

### 0.10.2.5 tmpfs：写下第一个字节才算数

tmpfs 是唯一一个「不用 `mkfs` 就能出现」的文件系统：`mount -t tmpfs` 时内核直接建好结构，容量与 inode 上限写在挂载选项里。`/proc/mounts` 里就有证据：

```text
tmpfs /run tmpfs rw,nosuid,nodev,noexec,relatime,size=1220796k,mode=755,inode64 0 0
tmpfs /dev/shm tmpfs rw,nosuid,nodev,inode64 0 0
udev /dev devtmpfs rw,nosuid,relatime,size=5473200k,nr_inodes=1368300,mode=755 0 0
```

`/run` 显式限了 `size=1220796k`（这台 11 GiB 内存机器的 10%），`/dev/shm` 什么都没写，于是取默认值：内存的一半。`stat -f /dev/shm` 报 `blocks=1525993`、`inodes=1525993`，换算正好 5.9 GiB，与 `df -h /dev/shm` 的 5.9G 一致。

「何时分配」在本机上实测得很干脆。先写一个真文件：

```bash
dd if=/dev/zero of=/dev/shm/lab10_shm bs=1M count=200 status=none
df -h /dev/shm | tail -1          # 5.9G 201M 5.7G 4%
stat -c '%s %b' /dev/shm/lab10_shm  # 209715200 409600
truncate -s 2G /dev/shm/lab10_sp
stat -c '%s %b' /dev/shm/lab10_sp    # 2147483648 0
df -h /dev/shm | tail -1          # 仍是 201M
rm -f /dev/shm/lab10_shm /dev/shm/lab10_sp
```

那个 2 GiB 的稀疏文件在 tmpfs 上同样不占空间（`%b` 为 0），这一点和 ext4 上的稀疏文件没有区别，呼应 [0.3.13](ch03.md#sec-0.3.13)。**区别在失败的时刻**：ext4 上 `fallocate` 会提前预留块，tmpfs 只在写入时占页，所以填满它时是**写操作本身**报错。实测把 1.2 GiB 的 `/run/user/1000` 灌满：

```text
dd: error writing '/run/user/1000/lab10_fill': No space left on device
1193+0 records in
1192+0 records out
tmpfs   1.2G  1.2G     0 100% /run/user/1000
tmpfs   305198    94 305104    1% /run/user/1000
```

空间 100%、inode 只用 1%，`df -i` 与 `df -h` 在这台机器上又一次各说一件事（临时文件已删净）。tmpfs 占的是内存，写满它等于吃 RAM，页还可以被换到 swap——这是它比磁盘文件系统更容易变成整机故障的原因。

::: ex 例 0.10.2 · `mkfs` 之后，1.29 GiB 去哪了 {#ex-0.10.2}
不读超级块内容（那需要 root），只用三条免特权命令：

```bash
grep ' sda2' /proc/partitions        # 66006016
stat -f -c '%b %S' /                 # 16163483 4096
stat -f -c '%c' /                    # 4128768
```

分区是 66006016 KiB，即 16501504 个 4 KiB 块；`stat -f` 说文件系统能记账的块只有 16163483 个。先猜这 338021 块（约 1.29 GiB，占分区 2%）是什么，再核对。

::: sol 解答
inode 表是大头：ext4 每个 inode 默认 256 字节，`4128768 × 256 B ≈ 1.0 GiB`（258048 个 4 KiB 块）。这些块在 `mkfs` 那一刻就被划走并长期占用，**跟里面有没有文件无关**，剩下的约 300 MiB 留给每块的组描述符、备份超级块和日志。两个校验：一，`64653932 KiB / 4128768 ≈ 15.7 KiB`，正好对应默认的 bytes-per-inode 16384，说明这台机器的 inode 数就是这么定下来的；二，把 inode 提到 800 万，元数据还要再多吃将近 1 GiB。所以「inode 多一点保险」不是免费的，`-i`/`-N` 要在格式化前算，不能事后补。
:::
:::

::: method 判定流程 · 文件系统选型四问
1. **能丢吗？** 数据是缓存、会话、编译中间产物 → tmpfs（配 `size=`）；不能丢 → 下一条。
2. **文件有多大、多少个？** 平均文件在 MB 级以上、以顺序读写为主 → ext4 或 XFS；几百万个小文件 → XFS，或 ext4 但把 `-i` 调小（例 0.10.2 的算术）。
3. **要不要回滚一个目录？** 要快照、逐数据校验和 → Btrfs（别拿它做 RAID5/6）；不要 → ext4/XFS，快照交给 LVM（[0.10.6](ch10.md#sec-0.10.6)）。
4. **这台机器认识它吗？** `cat /proc/filesystems` 看内核；`command -v mkfs.xfs` 看工具。本机实测两者都没有 XFS，选之前先装先加载。
:::

::: errata 常见错误清单（0.10.2 节）
1. **「`blkid` 是靠扩展名或设备名认类型」**——它读超级块的幻数与类型字段；日常免密能出结果，是因为读到的是 udev 在 `/run/udev/data/` 里的缓存，`blkid -c /dev/null` 后本机什么都读不到。
2. **「`stat -f -c %T` 报 `ext2/ext3`，说明文件系统是 ext2」**——ext2/3/4 共用同一个幻数 `0xef53`，这个字段分不出三代；要看真正类型用 `findmnt -T 路径` 或挂载表。
3. **「`df` 的 Size 就是分区大小」**——本例分区 16501504 个 4 KiB 块，文件系统只报 16163483 个可记账的块，差额是 inode 表、组描述符、备份超级块和日志。
4. **「tmpfs 里 `truncate` 出一个大文件不占空间，所以放多大都行」**——不占空间只在没写的时候成立，一旦真写就一页一页吃 RAM，写满时报的是写入失败，不是提前拒绝。
5. **「XFS 既然动态分 inode，就永远不会 inode 用尽」**——`maxpct` 给它设了上限，极端小文件场景仍会撞墙（见 0.10.4）。
6. **「块大小越小越省空间」**——小文件确实省对齐浪费，但 inode 映射、extent 管理和元数据开销都会上来；4 KiB 是通用起点，别默认调小。
:::

### 0.10.2 小结

`mkfs` 做的事是按顺序写下引导块、超级块、块组、两张位图和 inode 表，幻数让 `blkid` 与内核认得出类型；inode 表在格式化那一刻就吃掉空间、数量就此定死。ext4/XFS/Btrfs 的取舍落在小文件量、大文件顺序写、快照需求三条上，tmpfs 的差异在「写下第一个字节才分配」，procfs 压根不占磁盘空间。如果只记住一件事，那就是：**选文件系统其实是在选「什么时候分配、什么时候报错」**，格式化和挂载两个时刻你都有机会看清。

::: method 即时自测 · 0.10.2
**Q1（记忆）** 一个磁盘文件系统的五个组成结构按顺序是什么？两张位图分别记什么？

**Q2（辨析）** `stat -f -c %T /` 给 `ext2/ext3`，`findmnt -T /` 给 `ext4`，`blkid /dev/sda2` 也给 `ext4`。三个结果矛盾吗？说明各自读到的是什么。

**Q3（应用）** 一个 2 TB 的数据盘要放 600 万个平均 20 KiB 的缓存文件。默认 ext4（bytes-per-inode 16384）够不够 inode？写出你的算法和该调的参数。

**Q4（迁移）** 你在容器里 `mount -t xfs` 报 `unknown filesystem type 'xfs'`，但镜像里有 `mkfs.xfs`。给出两条诊断命令和结论。

::: sol 答案
**A1** 引导块、超级块、块组（每组含超级块副本/组描述符/inode 表/数据区）、inode 位图与数据块位图、inode 表。前者记「哪些 inode 已用」，后者记「哪些数据块已用」，两者独立耗尽。
**A2** 不矛盾。`stat -f %T` 读 `statfs()` 的 `f_type`，即幻数 `0xef53`，ext 三代共用，所以显示 `ext2/ext3`；`findmnt` 读内核挂载表里挂载时用的类型字符串；`blkid` 读超级块里的版本字段（或它的 udev 缓存副本），能分辨到 ext4。
**A3** 算法：每 GiB 空间按默认密度配 `1024³ / 16384 = 65536` 个 inode，2 TiB 即 2048 GiB，约 `1.34 亿` 个 inode，是 600 万需求的 22 倍——数量完全够。真正的浪费在这里：这 1.34 亿条记录要占 `×256 B ≈ 32 GiB` 的 inode 表，与里面有没有文件无关。所以该调的参数是**把 `-i` 调大**（例如 `-i 65536`，约 3350 万个 inode，仍留 5 倍余量），让元数据瘦下来；平均 20 KiB 的文件在 4 KiB 块上正好占 5 块，没有对齐浪费，所以这不是「小文件需要更密 inode」的场景。
**A4** `cat /proc/filesystems | grep xfs` 和 `lsmod | grep xfs`。有 `mkfs.xfs` 只说明用户态工具在，内核没编进也没加载 xfs 模块就挂不了；容器里通常也没有 `CAP_SYS_ADMIN`，`modprobe` 同样做不了——换带 xfs 的宿主内核才是解。
:::
:::


## 0.10.3 `df` 与 `du` 为什么对不上 {#sec-0.10.3}

这一节回答：`df` 说用了几十 GB、`du` 累加却少一截，或者反过来——数字对不上时，按什么顺序查？

::: preview 先抓住一件事
`df` 读文件系统的整体记账（一次 `statfs()` 调用就拿到全部块数），`du` 是逐个目录、逐个文件把已分配块加起来。一个看总账、一个数明细，天生不等。对不上的原因只有四类，每类都有能一眼定案的验证方法，下面按排查顺序讲。
:::

### 0.10.3.1 先量化这个差

同一台 Ubuntu 24.04 虚拟机上，两条命令同时跑：

```bash
du -sx --block-size=1 /            # 23823757312   /
df -B1 --output=source,used,avail / # /dev/sda2  25503588352  37305753600
```

`du` 数出 23.8 GB，`df` 记账 25.5 GB，差 1.68 GB。跑 `du` 花了 4.087 秒，还顺手报了三个错：

```text
du: cannot read directory '/.cache': Permission denied
du: cannot read directory '/root': Permission denied
du: cannot read directory '/tmp/snap-private-tmp': Permission denied
```

这一屏就是本节的缩影：`du` 只能数**它读得到的目录**，无权进入的目录直接跳过、不计入总数也不报错到退出码以外；`df` 数的块里还包含 `du` 永远看不见的东西。看这台机器时你应该先记住：差值里有合法成分（元数据、预留块），也有需要追问的成分（跳读的目录、已删除仍打开的文件、被盖住的目录）。

### 0.10.3.2 第一条：删了名字，块还在别人手里

这一条最常见，也最容易在监控告警上骗人。在本机免密复现一遍（临时目录 `/tmp/lab10_del`，做完就删）：

```bash
mkdir -p /tmp/lab10_del
dd if=/dev/zero of=/tmp/lab10_del/big.bin bs=1M count=1024 status=none
df -h / | tail -1        # 62G 26G 34G 44% /
nohup bash -c 'exec 9< /tmp/lab10_del/big.bin; sleep 900' >/dev/null 2>&1 &
rm /tmp/lab10_del/big.bin
df -h / | tail -1        # 62G 26G 34G 44% /
lsof +L1 | grep big.bin
```

```text
COMMAND   PID     USER   FD   TYPE DEVICE   SIZE/OFF NLINK   NODE NAME
sleep   35338 juanwang    9r   REG    8,2 1073741824     0 272852 /tmp/lab10_del/big.bin (deleted)
```

`rm` 之后 `ls` 看不见这个文件、`du` 也数不到它，但 `df` 的 26 GB 一格没退。关键三列：`NLINK=0`（目录项全没了）、`SIZE/OFF=1073741824`（1 GiB 数据块仍被引用）、名字后面跟着 `(deleted)`。`+L1` 的字面意思就是「只看链接数小于 1 的打开文件」，它专抓这一态。把那个进程结束（实测 `kill 35338`），`df` 立刻回到 `25G 42%`。

这就是生产上「`rm` 了 3 GB 日志，空间只回来 200 MB」的全部机制：`unlink()` 只删目录里那一行，回收要等**最后一个引用**放手（[0.3.19](ch03.md#sec-0.3.19) 实验二把这两道闸拆开过）。处理不是再 `rm` 一遍，而是让持有者重开文件：`kill -HUP` 让 nginx 重跑日志、`systemctl restart` 让服务重开，或对追加写的日志把那个 fd 截断成 0 长度。轮转应当用 `copytruncate` 或 `postrotate` 重开，而不是删名字。

### 0.10.3.3 第二条：`du` 数块，`ls` 数字节

同一个文件，两个口径能差出几千倍。实测：

```bash
truncate -s 4G /tmp/lab10_sp.img
stat -c 'size=%s blocks=%b*%B' /tmp/lab10_sp.img   # size=4294967296 blocks=0*512
du -h /tmp/lab10_sp.img                             # 0
du -h --apparent-size /tmp/lab10_sp.img             # 4.0G
df -h / | tail -1                                   # 62G 25G 35G 42%（一点没动）
rm -f /tmp/lab10_sp.img
```

`%b` 是实际分配的 512 字节块数，这里是 0——`truncate` 只改了 inode 里的长度字段，没写一个数据块，文件系统里的空洞不占块（[0.3.13](ch03.md#sec-0.3.13)）。所以「`du` 比 `ls` 小」不是 bug，是它在数另一个东西。反向的例子同样常见：一个 1 字节的文件也要占一个 4 KiB 块，`du -h` 报 4.0K，`ls -l` 报 1——在 `/dev/shm` 上实测一个 2 字节文件正是这个结果。

对账时把三条口径分清楚：`ls -l` 与 `du --apparent-size` 数字节，`du` 与 `df` 数分配块，`df -i` 数 inode。硬链接是第四个变量：`du` 默认对同一个 inode 只算一次，`du --count-links` 才重复算，`ls -l` 则每个名字都报同样大小。

### 0.10.3.4 第三条：目录还在树里，但被别的挂载盖住了

挂载是把一个文件系统的根「盖」在目录树的某个节点上。盖住之后，原目录里已有的文件一个都没删，只是从这条路进不去了：`du` 顺着目录树走，看不见它们；`df` 数底层那个文件系统时，它们照旧占着块。这就是「`df` 满、`du` 怎么都凑不满」里最费解的一条。

本机不能制造这个状态（`mount --bind` 需 root，本书未实测），但它有免特的判读方法。先看这台机器上的真实嵌套：`/run` 是一份 tmpfs，`/run/user/1000` 是**另一份** tmpfs——同一个名字 `tmpfs` 在 `findmnt` 里出现 5 次，SOURCE 完全不能区分它们：

```bash
findmnt -T /run/user/1000
findmnt -n -o TARGET | grep '^/run'
```

判读顺序：一，`findmnt -T 目标目录`，看返回的 `TARGET` 是目录本身还是它的某一层父目录；二，`findmnt -n -o TARGET | grep -F 目标目录/`，列出所有嵌在它下面的挂载点；三，怀疑被盖住的内容时，把**底层那个文件系统单独挂到别处**（例如 `mount /dev/sda2 /mnt/root-view`，需 root），再对 `/mnt/root-view/var/log` 这类路径跑 `du`，差额就现形。生产上更常见的触发条件是「有人把数据盘挂到了 `/data`，而 `/data` 目录里本来就有几十 GB 旧文件」——挂载那一刻起，那些文件既不显示也不能删，直到你 umount。

### 0.10.3.5 第四条：预留块与元数据，`du` 天生看不见

这两块是差值里的「合法成分」，本机免特权就能量出来。`stat -f` 一次给出三个块数：

```bash
stat -f -c 'blocks=%b free=%f avail=%a frsize=%S' /
```

```text
blocks=16163483 free=9802857 avail=8973686 frsize=4096
```

`free` 是真空闲的块，`avail` 是**普通用户**还能用的块。两者差 829171 块，即 3.17 GiB，占总量 5.13%——正是 ext4 默认的 5% 预留。它的用途是让 root 在磁盘「看起来满」时还能登录删文件；`df -h` 的 `Avail` 就是 `avail`，而 `Use%` 的分母是 `Used+Avail`，不含预留：本机 `25457840/(25457840+35879408)=41.5%`，显示 42%，而按 `Size` 算只有 39%。数据盘可以用 `mkfs.ext4 -m 1` 或 `tune2fs -m 1` 把预留降下来（需 root，本机未实测），根分区建议保留。

元数据那部分在 0.10.2 已经算过：分区 16501504 个 4 KiB 块，文件系统只报 16163483 个可记账的块，差的 338021 块（约 1.29 GiB）里 inode 表占 1.0 GiB。这些块 `du` 永远数不到——它们不属于任何文件。把 0.10.3.1 那个 1.68 GB 的差拆开看就清楚了：元数据约 1.29 GB，剩下约 0.4 GB 是 `du` 无权读目录里跳过的内容（`/.cache`、`/root`、`/tmp/snap-private-tmp`）。

::: ex 例 0.10.3 · 三个数字互相矛盾 {#ex-0.10.3}
一台机器上：`df -h /` 报 Used 25 GB、`du -sx /` 报 23.8 GB、`ls -l` 数某个日志文件报 4.0 GB 但 `du -h` 报 0。先猜这三组数字里哪些「不诚实」，再给出四条命令把它们各自钉死。

::: sol 解答
三组都不算错，只是口径不同。`du` 少的 1.68 GB 由两块合法成分构成：用 `stat -f -c '%b %f' /` 与 `grep sda2 /proc/partitions` 相减算出元数据 338021 块（1.29 GB），再用 `du` 打在 stderr 上的告警看它跳过了哪些无权读的目录（本机实测跳过 `/.cache`、`/root`、`/tmp/snap-private-tmp`）。那个 4.0 GB 的文件是稀疏文件，`stat -c 'size=%s blocks=%b'` 给 `4294967296` 和 `0`，`du -h --apparent-size` 才报 4.0G。若还差一块没解释，跑 `lsof +L1` 找已删除仍打开的文件，跑 `findmnt -n -o TARGET | grep -F 目录/` 找嵌套挂载。四条命令跑完仍对不上，才该怀疑文件系统本身出问题。
:::
:::

::: method 判定流程 · `df` 与 `du` 对不上时按这个顺序查
1. **确认在比同一个挂载点**：`findmnt -T 路径`、`df -h 路径`，别拿 `/var` 的 `du` 去比 `/` 的 `df`。
2. **`df -i` 与 `df -h` 都看**：两个计数器独立，先看是不是 inode 满了（0.10.4）。
3. **查已删除仍打开的文件**：`lsof +L1`，看 `NLINK=0` 与 `(deleted)`；这一步不需要 root 也能查自己的进程，查别人的要 root。
4. **查嵌套挂载与被盖住的目录**：`findmnt -n -o TARGET | grep -F 目录/`，必要时把底层文件系统单独挂到别处再 `du`。
5. **核对口径**：`du` 与 `du --apparent-size` 各跑一次，`stat -c '%s %b'` 抽查大文件，稀疏与硬链接都在这一层现形。
6. **最后才算合法差额**：`stat -f -c '%b %f %a'` 给出元数据与预留块；`du` 因权限跳过的目录看它的 stderr。
:::

::: errata 常见错误清单（0.10.3 节）
1. **「`du` 加起来应该等于 `df` 的 Used」**——`df` 的 Used 含 inode 表、组描述符、日志和备份超级块，`du` 只数文件的分配块，永远偏小。
2. **「`rm` 之后 `df` 不降就是没删成」**——名字已经删了，`ls` 看不见；块在等最后一个 fd 关闭，`lsof +L1` 是唯一能看见这个中间态的常规工具。
3. **「`du` 不加 `-x` 更完整」**——恰恰相反，不加 `-x` 会跨进 `/proc`、别的盘和网络挂载，算出一个和这个分区无关的大数；`-x` 才是「只算这个文件系统」。
4. **「`df` 的 `Use%` 到 100% 就一个字节也写不进去」**——预留块还在，root 仍可写；普通用户写不进去，这正好是留给你登录救火的余地。
5. **「`du -sh /var/log` 小，说明日志没占空间」**——被盖住的目录、已删除仍打开的文件、无权读的目录都可能让它偏小；先按上面的顺序查。
6. **「`lsof` 一定要 root」**——查自己进程的 fd 不需要（本机实测列出自己的 `sleep` 进程）；查别人的进程才需要提权。
:::

### 0.10.3 小结

`df` 看总账、`du` 数明细，对不上的原因只有四类：删了名字但块还被人拿着、`du` 数块而 `ls` 数字节、目录被上层挂载盖住、元数据与预留块本来就不属于任何文件。四类各有一条能定案的验证命令，顺序也是排查顺序。如果只记住一件事，那就是：**先分清「数字对不上」是不是口径问题，再怀疑文件系统坏了**——`stat -f`、`lsof +L1`、`findmnt` 三条跑完，绝大多数告警就已经有了答案。

::: method 即时自测 · 0.10.3
**Q1（记忆）** 说出 `df` 与 `du` 对不上的四条原因，以及每条的验证命令。

**Q2（辨析）** 一个 1 字节的文件，`ls -l` 报 1、`du -h` 报 4.0K；一个 4 GiB 的稀疏文件，`ls -l` 报 4.0G、`du -h` 报 0。两次的「4K」是同一个东西吗？

**Q4（迁移）** 同事说「`df -h` 显示 42%，其实还有 35 GB 可用，怎么会写失败」。用本机 `stat -f` 的三个数字解释这句话哪里不对。

**A1** ① 已删除仍打开：`lsof +L1`；② 稀疏文件/块口径：`stat -c '%s %b'` 或 `du --apparent-size`；③ 被挂载点盖住：`findmnt -n -o TARGET | grep -F 目录/`；④ 预留块与元数据：`stat -f -c '%b %f %a'`，必要时 `grep 分区 /proc/partitions` 相减。

**A3** ① `df -i /var`：`IUse%` 到 100% 就是 inode 耗尽（转 0.10.4）；② `sudo lsof +L1 | grep /var`：出现 `(deleted)` 且 `NLINK` 为 0 即命中第一条；③ `findmnt -n -o TARGET | grep -F /var/`：有嵌套挂载就怀疑被盖住，把根文件系统另挂一处再 `du` 比对。
**A4** 42% 的分母不含预留块。本机 `blocks=16163483`、`free=9802857`、`avail=8973686`：`free-avail=829171` 块是 root 的预留，普通用户能用的只有 `avail`。磁盘逼近满时，`df` 的 `Avail` 先归零，`Use%` 到 100% 但 `free` 还有余量，那时 root 仍能写、普通用户写不进去。

## 0.10.4 inode 用尽：磁盘还有空间却写不进去 {#sec-0.10.4}

这一节回答：磁盘满有两种，`df -h` 与 `df -i` 各看一种；为什么 `df` 明明还剩 35 GB，`touch` 却报 `No space left on device`？怎么揪出吃掉 inode 的目录？

::: preview 先抓住一件事
0.10.2 讲过文件系统里有两张位图：一张记 inode、一张记数据块。它们**各自耗尽**，报错却是同一个 `ENOSPC`。ext4 的 inode 总数在 `mkfs` 那一刻就写进超级块、事后不能改比例，所以小文件多的负载要提前算；XFS 动态分 inode、tmpfs 的 inode 上限挂在挂载选项上，是另外两套规则。
:::

### 0.10.4.1 两种满，两个读数

先看这台机器上 inode 这一侧的真实账目：

```bash
df -i /
df -h / | tail -1
```

```text
Filesystem      Inodes  IUsed   IFree IUse% Mounted on
/dev/sda2      4128768 395785 3732983   10% /
/dev/sda2        62G   25G   35G  42% /
```

两个百分比毫无关系。在本机造 3000 个空文件，把这条独立性拍下来（全部在 `/tmp/lab10_ino2`，跑完删净）：

```bash
mkdir -p /tmp/lab10_ino2
df -h / | tail -1; df -i / | tail -1        # 25G 42% ；IUsed 395786
bash -c 'cd /tmp/lab10_ino2 && for i in $(seq 1 3000); do : > f$i; done'
df -h / | tail -1; df -i / | tail -1        # 25G 42% ；IUsed 398786
du -s /tmp/lab10_ino2                        # 72
rm -rf /tmp/lab10_ino2
```

3000 个文件让 `df -i` 精确地少了 3000 个 inode，`df -h` 一格没动，`du` 只报 72 KiB（那是目录项占的块，不是文件占的）。空文件不写数据，但每个都要一张档案卡。等量交换反过来也成立：一个 1 GiB 的大文件只吃掉 1 个 inode。

所以「写不进去」的第一步永远是**两条 `df` 都看**。两个方向的满都报同一个错：`touch`/`open`/`write` 返回 `No space left on device`（`ENOSPC`）；`df -h` 只回答了块，没回答 inode。配额超限是另一个错码 `EDQUOT`（[0.10.8](ch10.md#sec-0.10.8)），别混。

### 0.10.4.2 机制：为什么 inode 数不能事后加

inode 是**定长数组里的一条记录**，靠编号直接寻址。给定 inode 号，文件系统算的是「inode 号 × 每条大小 ÷ 块大小 + inode 表起始地址」——这套算法要求表连续且长度已知，所以表的容量必须写在超级块里（超级块记的参数就包括 inode 表容量、块大小和 inode 表位置）。ext4 的默认密度是每 16384 字节省间配一个 inode；本机 `64653932 KiB / 4128768 ≈ 15.7 KiB`，对得上默认值（0.10.2 例）。想改比例只有两条路：`mkfs.ext4 -i 4096` 或 `-N 8000000`，都在格式化时定；`resize2fs` 扩的是块，新块组按超级块里已有的 `inodes_per_group` 配表，**密度不变**。这两条都需要 root 才能真正执行与验证，本机未实测。

代价也在这里：inode 表在 `mkfs` 时就吃掉约 1.0 GiB，不管里面有没有文件（0.10.2 例 0.10.2 的算术）。把 `-i` 调到 4096，元数据开销直接涨四倍——「inode 多一点保险」不是免费的。

不同文件系统的规则不一样：

| 文件系统 | inode 从哪来 | 上限由谁定 | 用尽怎么办 |
|:--|:--|:--|:--|
| ext4 | 格式化时划定的定长表 | 超级块里的每块组 inode 数 | 只能删小文件，或重建时改 `-i`/`-N` |
| XFS | 按需从数据区分配 inode 簇 | `imaxpct`（默认约 25%）比例上限 | 一般不用管；极端小文件仍会撞顶，可 `xfs_growfs` 扩盘 |
| tmpfs | 挂载时算好的 `nr_inodes` | 挂载选项（可 remount 改，需 root） | `umount` 重挂并给更大的 `nr_inodes=` |
| vfat/exfat | 没有 inode 概念 | 不适用 | `df -i` 显示 `0` 与 `-`，别拿它当证据 |

本机 `/dev/shm` 实测 `inodes=1525993`（tmpfs 按内存比例算出）、`/run/user/1000` 实测 `Inodes 305198`（那份 1.2 GiB 的 tmpfs）；`/dev/sda1` 是 vfat，`df -i` 给的是 `0 0 0 -`。XFS 那一行本机没有 XFS 文件系统，属未实测，规则照给。

### 0.10.4.3 救援：找出吃 inode 的目录

`du` 在这里帮不上忙——它数块，inode 用完时块可能还很空。要找的是**每个目录里有多少个文件**：

```bash
find /tmp -xdev -type d -exec sh -c 'printf "%s\t%s\n" "$(find "$1" -maxdepth 1 -type f | wc -l)" "$1"' _ {} \; 2>/dev/null | sort -n | tail -3
```

本机实测（扫 `/tmp`，清理前）：

```text
20      /tmp/lab8/src
52      /tmp/lab8
3000    /tmp/lab10_ino
```

`-maxdepth 1` 只数这一层，`sort -n` 把最费 inode 的目录推到末尾。这条命令在 `/tmp` 自己的目录里跑只要几秒；扫全盘（`find / -xdev`）会踩进大量无权目录、耗时按分钟计，生产上要先限定 `-xdev` 与起点。数文件总数用免特权命令也可以，只是会漏掉别人目录里的：

```bash
find /tmp -xdev -type f | wc -l     # 只统计能读到的
```

注意统计口径：每个目录、每个符号链接也各占一个 inode，`-type f` 会漏算它们。一个有几万个空子目录的目录树，即使一个文件都没有，也已经吃掉几万张卡。

真出了 inode 用尽，出路按代价从低到高：

1. **删无用的小文件**。典型元凶是缓存与会话目录（`~/.cache`、`/var/lib/php/sessions`、邮件队列、`node_modules`、构建中间产物）。先按上面的命令定位，再逐目录清。
2. **把该目录迁到 inode 更多的文件系统**，或改成「少文件、大文件」的存法：成千上万个几 KB 的文件，打包成归档或换成单个数据库文件，inode 立刻掉下来。
3. **换文件系统**（XFS 的动态 inode）或**重建**（`mkfs.ext4 -i 4096`／`-N 8000000`）。重建会清空数据，属最后手段，且只允许在已备份或空盘上做；`-N` 越大，元数据吃掉的可用空间越多。这三条都要 root，本机未实测，只给判读口径。

::: ex 例 0.10.4 · 报同一个错，两种满 {#ex-0.10.4}
本机实测过两条相反的路。第一条：往 1.2 GiB 的 tmpfs `/run/user/1000` 里 `dd` 1400 MiB：

```text
dd: error writing '/run/user/1000/lab10_fill': No space left on device
1193+0 records in
1192+0 records out
```

此时 `df -h` 报 `1.2G 1.2G 0 100%`，而 `df -i` 只报 `1%`。第二条：造 3000 个空文件，`df -i` 精确少 3000，`df -h` 一格不动。先猜「把 3000 换成 400 万」会发生什么，再解释为什么两条路的报错文本一模一样。

::: sol 解答
第二条路推到极限就是 inode 用尽：这台机器的 `/` 有 4,128,768 个 inode，用掉 395,785 个（10%），还剩约 373 万个。往 `/` 造 400 万个文件后，`df -h` 会显示还有三十多 GB，而 `df -i` 的 `IUse%` 先到 100%，`touch` 随即报 `No space left on device`。两条路同一个错码，是因为 `open(O_CREAT)`/`write` 在分配阶段无论哪一张位图找不到空闲位，内核都只能返回同一个 `ENOSPC`；错误文本不带「是块还是 inode」的信息。分辨只靠 `df -i`，这也是本节判定的第一条命令。临时文件已在本机删净。
:::
:::

::: method 判定流程 · 写不进去先看什么
1. `df -h 挂载点` 与 `df -i 挂载点` 各跑一次：`IUse%` 到 100% 而 `Use%` 还低，就是 inode 满；两个都低却仍失败，走下一步。
2. `findmnt -T 目标目录 -o TARGET,FSTYPE,OPTIONS`：确认你写的确实是这个文件系统（选项里有 `ro` 就轮到 0.10.5），注意类型是 tmpfs 还是 ext4。
3. 报 `EDQUOT` 而非 `ENOSPC` 时查配额（`repquota`，需 root，见 0.10.8）；报 `EROFS` 查只读挂载；报 `EFBIG`/`EDQUOT` 之外的错别再按「满」处理。
4. 确定 inode 满：用 0.10.4.3 的每目录计数命令定位元凶目录，先看是不是缓存/会话/构建产物。
5. 清理后 `df -i` 不回升：多半是删掉的仍被进程打开（回到 0.10.3.2，`lsof +L1`），或 inode 需要 `sync` 与延迟回收才刷新（少见，先确认删的是文件而不是被盖住的目录）。
:::

::: errata 常见错误清单（0.10.4 节）
1. **「`df -h` 有空间就不可能写失败」**——块和 inode 是两个独立计数器；`df -i` 才是这件事的答案。
2. **「`du` 能帮我找 inode 元凶」**——`du` 数块，3000 个空文件只报 72 KiB；要按目录数文件条数。
3. **「`resize2fs` 扩容能解决 inode 密度不够」**——新块组按超级块里已有的 `inodes_per_group` 配表，inode 数随块数一起涨但**密度不变**；小文件问题原样复制。
4. **「XFS 动态分 inode，永远不会 inode 用尽」**——`imaxpct` 给它设了比例上限，极端小文件场景照样撞顶。
5. **「符号链接不占 inode」**——链接、目录、设备节点各占一个；深层目录树里目录本身就是可观的一笔。
6. **「调大 inode 数没有代价」**——每个 inode 256 字节常驻 inode 表，本机 4128768 个已经吃掉约 1.0 GiB；`-i` 降到 4096，这块开销涨四倍。
7. **「`df -i` 显示 0 就是 inode 全满」**——vfat、efivarfs 这类文件系统没有 inode 概念，本机显示的是 `0 0 0 -`，那个 `-` 才是「不适用」。
:::

### 0.10.4 小结

磁盘满有两种，块满看 `df -h`，inode 满看 `df -i`，两者独立耗尽、共用一个 `ENOSPC` 错码；ext4 的 inode 密度在 `mkfs` 时定死、事后改不了比例，XFS 动态分配但有 `imaxpct` 上限，tmpfs 的上限写在挂载选项里。救援是「按目录数文件」而不是「按目录数块」。如果只记住一件事，那就是：**写入失败先跑 `df -i`，三秒钟就能把问题从「磁盘满」缩小到「卡用完了」。**

::: method 即时自测 · 0.10.4
**Q1（记忆）** 「磁盘满」有哪两种？各自用哪条命令确认？报错文本有什么区别？

**Q2（辨析）** 3000 个空文件让 `df -i` 精确下降 3000，`df -h` 却一格不动、`du` 只报 72 KiB。三句话解释这三个现象。

**Q3（应用）** 一台机器 `/data`（ext4，`df -h` 显示 15%、`df -i` 显示 100%）写不进去。给出定位命令、两个典型元凶和两种出路，并说明哪一种要重建文件系统。

**Q4（迁移）** 你要为一个每天产生 800 万个 2 KiB 小文件的队列盘做规划。默认 ext4（每 16384 字节配一个 inode）在 500 GB 的盘上够不够？写出算法，并给出你的选择。

::: sol 答案
**A1** 块用尽与 inode 用尽，分别用 `df -h` 和 `df -i` 确认；两者都返回 `ENOSPC`，文本同为 `No space left on device`，看不出是哪种，必须靠命令分辨。
**A2** 每个文件必须一张 inode，所以 `df -i` 减 3000；空文件不写数据、不分配块，所以 `df -h` 不动；`du` 数的是分配块，3000 个文件的数据块为 0，72 KiB 全来自那个目录的目录项块。
**A3** 定位：`find /data -xdev -type d -exec sh -c 'printf "%s\t%s\n" "$(find "$1" -maxdepth 1 -type f | wc -l)" "$1"' _ {} \; | sort -n | tail`，再 `find /data -xdev -type f | wc -l`。元凶常在缓存/会话目录与构建产物、消息队列散落文件。出路一：删无用小文件或把它们打包成少量大文件；出路二：迁到 inode 更多或动态分 inode 的文件系统（XFS）。只有「按更大密度重建」（`mkfs.ext4 -i`/`-N`）会清空数据，必须先备份。
**A4** 500 GiB 按默认密度能配 `500×1024³ / 16384 = 32768000`，约 3276 万个 inode，只够放 4 天的队列（每天 800 万），第 5 天就开始报 `ENOSPC` 而 `df -h` 还很空。inode 表本身要占 `3276万 × 256 B ≈ 7.8 GiB`。把 `-i` 降到 4096（每 4 KiB 一个 inode，约 1.31 亿个）能让 inode 不再是瓶颈，但 inode 表要吃到约 31 GiB。更好的判据其实是块：2 KiB 的文件仍占满一个 4 KiB 块，一半空间天生浪费，每天 800 万个就是约 32 GB。所以这题的答案不在调参数——换 XFS 让 inode 动态分配，或在应用层把散落文件合并成少量大文件/单个数据库文件。
:::

## 0.10.5 挂载、`/etc/fstab` 与救援 {#sec-0.10.5}

这一节回答：一套已经写好的文件系统怎么变成「你能 `cd` 进去的目录」？`/etc/fstab` 写错为什么能把系统挡在开机路上，改完又怎么在不重启的前提下验证？

[0.10.1](ch10.md#sec-0.10.1) 把存储链摆成四格（块设备、分区、文件系统、挂载点），[0.10.2](ch10.md#sec-0.10.2) 讲清了第三格内部长什么样。这一节只动第四格：把一个文件系统接到目录树上，以及接错之后怎么拆下来。

::: preview 先抓住一件事
挂载不碰磁盘上的任何数据，它只改内核的一张表：把某个文件系统的根节点接到目录树的某个目录上。接上之后，那个目录原来的内容一个都没删，只是从这条路暂时进不去了。`/etc/fstab` 只是「开机照着挂」的清单，真正生效的永远是内核那张表。所以验证 fstab 的正确做法是「让它现在就挂一次」，而不是「重启看看」。
:::

### 0.10.5.1 先回答一个没人问的问题：`/dev/sda2` 凭什么和 `/` 在同一棵树里

`/dev/sda2` 看起来是个文件，`/` 是个目录，`/etc/fstab` 是个普通文件——三种东西为什么能在同一棵目录树里并存，还能互相指来指去？Ubuntu 实测，一次看三个：

```bash
stat -c '%n 类型=%F 主:次=%t:%T 权限=%A 属主=%U' /dev/sda2 /dev/null /etc/fstab
```

```text
/dev/sda2 类型=block special file 主:次=8:2 权限=brw-rw---- 属主=root
/dev/null 类型=character special file 主:次=1:3 权限=crw-rw-rw- 属主=root
/etc/fstab 类型=regular file 主:次=0:0 权限=-rw-r--r-- 属主=root
```

区别全在「类型」这一列。`/dev/sda2` 是**块设备专用文件**（block special file，一块设备的入口名字）：它自己不存数据，只带两个号码——主设备号 `8` 选中磁盘驱动，次设备号 `2` 选中这块盘上的第二个分区。你对它调用 `read()`，内核把请求转给驱动，而不是去查某个 inode 的数据块地址表。普通文件的两个号都是 `0:0`，因为它不对应任何驱动。

::: def 定义 0.10.5 · 挂载与挂载点 {#def-0.10.5}
**挂载**（mount，把一个文件系统接到目录树上）是只改内核表的操作：内核把 `source` 那个文件系统的**根 inode** 接到 `target` 这个目录节点上，此后从 `target` 走进去看到的都是那个文件系统。**挂载点**（mount point，就是被接上的那个目录）本身属于下层文件系统，它只是接口。卸载（umount）把这条接回去掉。按 Kerrisk 第 14 章的口径，Linux 2.4 之后一个文件系统可以同时挂在多处、同一个挂载点也能叠挂多次，所以 `umount()` 系统调用的参数是挂载点路径而不是设备名——给设备名会说不清你要拆的是哪一条。
:::

顺带把 [0.10.3](ch10.md#sec-0.10.3) 那个「删了大文件 `df` 却没降」放进同一个框架：目录树和文件系统是两层东西。目录项（name）只是指向 inode 的一行记录，名字删了而 inode 还被某个进程拿着，块就不释放；挂载点目录里「被盖住」的文件也一样，inode 和数据块都还在盘上，只是这条路进不去。

### 0.10.5.2 三份台账：愿望、内核表、逐挂载点详情

同一件事有三份记录，位置不同、更新时机不同，出问题时以哪份为准也不同。

第一份是你的**愿望**：`/etc/fstab`（filesystem table，开机自动挂载清单，由管理员手工维护）。这台 Ubuntu 24.04 上它的全部有效行是：

```text
# / was on /dev/sda2 during curtin installation
/dev/disk/by-uuid/fa8bbbea-9f92-4241-b344-a824e4b676a6 / ext4 defaults 0 1
# /boot/efi was on /dev/sda1 during curtin installation
/dev/disk/by-uuid/CF57-24FD /boot/efi vfat defaults 0 1
/swap.img	none	swap	sw	0	0
```

第二份是**内核此刻的挂载表** `/proc/mounts`，每行六个字段，和 fstab 同格式（Kerrisk 第 14 章），差别在第 5、6 字段恒为 `0`——那两个字段是给 fstab 用的，内核不关心。实测其中三行（顺序按原文件）：

```text
sysfs /sys sysfs rw,nosuid,nodev,noexec,relatime 0 0
udev /dev devtmpfs rw,nosuid,relatime,size=5473200k,nr_inodes=1368300,mode=755,inode64 0 0
/dev/sda2 / ext4 rw,relatime 0 0
```

第三份是**老台账** `/etc/mtab`。鸟哥那本书写作时它是「真正的挂载记录」，改挂载会同步改它；今天它在这台机器上只是个符号链接（Ubuntu 实测）：

```bash
ls -l /etc/mtab
```

```text
lrwxrwxrwx 1 root root 19 Sep  8 08:15 /etc/mtab -> ../proc/self/mounts
```

也就是说 `mtab` 早已不是独立台账，而是内核表的别名。你在旧教程里看到「`mount -n` 不更新 `/etc/mtab`」这类叮嘱，在今天等价于「不更新 `/proc/mounts`」——而后者由内核自己维护，`mount` 命令根本不写它。判读顺序也因此变得很简单：**问「现在挂了什么」看 `/proc/mounts` 或 `findmnt`，问「下次开机会挂什么」看 `/etc/fstab`**，两者不一致时以前者为准。

还有一份更详细的 `/proc/self/mountinfo`，每个挂载点一行，字段比 `/proc/mounts` 多。挑本机真实存在的两条（Ubuntu 实测）：

```bash
awk '$5=="/" || $5=="/run/snapd/ns"' /proc/self/mountinfo
```

```text
35 2 8:2 / / rw,relatime shared:1 - ext4 /dev/sda2 rw
345 34 0:30 /snapd/ns /run/snapd/ns rw,nosuid,nodev,noexec,relatime - tmpfs tmpfs rw,size=1220796k,mode=755,inode64
```

字段依次是：挂载 ID、父挂载 ID、`主:次` 号、**根前缀**、挂载点、挂载选项、可选字段（`-` 之前那一段）、分隔符 `-`、文件系统类型、设备名、超级块选项。前三个字段就把 [0.10.5.1](ch10.md#sec-0.10.5) 的 `8:2` 对上了；`0:30` 这种主设备号为 0 的是没有真实设备的文件系统（tmpfs、伪文件系统）。

要看懂的是**根前缀**和**传播标记**这两列。

根前缀回答「接进树里的是这个文件系统的哪一棵子树」。绝大多数挂载点的根前缀是 `/`，意思是整个文件系统的根被接了出来；本机第 345 条是 `/snapd/ns`——那是 snapd 把 `/run` 这份 tmpfs 里的一个子目录**绑定挂载**（bind mount，把一个已经是目录树节点的目录再挂到别处，两处看到的是同一份内容）到了 `/run/snapd/ns`。对应的命令选项是 `mount --bind`，对应的内核标志是 `MS_BIND`（Kerrisk 第 14 章把绑定挂载列为 2.4 起的高级挂载特性之一：它类似硬链接，但能跨文件系统、能针对目录）。

传播标记（propagation）住在可选字段里，它管的是挂载事件要不要在**挂载命名空间**（mount namespace，一个进程独自看到的那棵挂载树）之间互相传；常见取值是 `shared` 和 `private`。注意上面两条的差别：`/` 那一条有 `shared:1`，第 345 条在选项之后、`-` 之前**什么也没有**——没有标记就是 `private`。Ubuntu 实测（`findmnt -no TARGET,PROPAGATION 挂载点`）印证了这一点：

```text
/                shared
/run             shared
/run/snapd/ns    private
```

`private` 的意思是：别的挂载命名空间在这个位置挂上或卸下什么，不会传进来给你看见；反过来你做的也不会传出去。容器、snap、chroot 这类「在自己那棵树里挂东西」的机制都靠这个开关决定隔离强度。这一列在 `/proc/mounts` 里完全没有，是「`findmnt` 比 `mount` 多知道一层」的具体原因之一，也是第 5 篇讲容器根文件系统时要回头看的字段。

### 0.10.5.3 `mount` 与 `umount`：能做的动作与 busy 的真实含义

临时挂载、卸载都需要 `CAP_SYS_ADMIN`。本机 sudo 需要密码，因此下面的清单是**要 root 才能跑的清单，未在本书环境复现**：

```bash
sudo mount /dev/vglab/lvdata /mnt/data        # 挂载一个已格式化的设备到空目录
sudo mount -o ro,noatime /dev/sdb1 /mnt/usb   # 只读、不更新访问时间
sudo mount -o remount,rw /                    # 把根文件系统改回可写
sudo umount /mnt/data                          # 卸载
sudo umount -l /mnt/data                       # lazy 卸载，见下文
```

不加 `-t` 时，内核按超级块里的幻数去试匹配文件系统类型（[0.10.2](ch10.md#sec-0.10.2) 讲过幻数），试中才挂上去。按 `mount(8)` 的报错口径，「设备上没有文件系统」是 `wrong fs type, bad option, bad superblock`，「内核没带这个模块」是 `unknown filesystem type 'xfs'`，两者修法完全不同。

无特权时连挂载本身都进不去。Ubuntu 实测五条：

```bash
mount /dev/sr0 /mnt        # 普通用户尝试挂载
unshare -m true            # 尝试新建挂载命名空间
unshare -Urm true          # 先用用户命名空间拿到「自己 namespace 里的 root」
grep -c user /etc/fstab    # fstab 里有没有 user 选项
cat /proc/sys/kernel/apparmor_restrict_unprivileged_userns
```

```text
mount: /mnt: must be superuser to use mount.
       dmesg(1) may have more information after failed mount system call.
unshare: unshare failed: Operation not permitted
unshare: write failed /proc/self/uid_map: Operation not permitted
0
1
```

`mount` 不带参数只是打印挂载表，普通用户能跑（实测退出码 0）；真要挂载就需要 `CAP_SYS_ADMIN`。第四行的 `0` 说明这台机器的 fstab 没有 `user`/`users` 选项——那个选项的作用正是允许指定设备被普通用户挂载和卸载，代价是默认会带上 `nosuid,nodev` 等限制。第三行是很多人以为的「免特权后门」：在自己的用户命名空间里你就是 root，可以随便挂 tmpfs。这台机器把它堵住了：最后一行 `apparmor_restrict_unprivileged_userns=1` 是 Ubuntu 24.04 的默认值，内核日志里能看到对应的拒绝记录（`journalctl -k` 免特权可读，本机实测有两条 `apparmor="DENIED"`，一条拒 `userns_create`，一条在受限 profile 里拒 `sys_admin`）。因此本节凡是「用户命名空间里挂载」的说法都只到机制层，**未在本书环境复现**。

`umount` 最常见的失败是下面这一屏。它是 util-linux 的固定报错文本（鸟哥第 7 章逐字记录过同样的两行），本机造不出这个状态——挂不上就没有忙的文件系统，属**形状示例，未在本书环境复现**：

```text
umount: /mnt/data: target is busy.
        (In some cases useful info about processes that use
         the device is found by lsof(8) or fuser(1))
```

它的 errno 是 `EBUSY`（按 Kerrisk 第 14 章的口径，卸载在用中的文件系统返回 `EBUSY`）。什么叫「在用」：有进程打开着这个文件系统里的某个文件、某个进程的工作目录还在里面、或者它是某个登录用户的家目录。最常见的第一种和第二种——你自己在挂载点里 `cd` 着，然后想卸载它。

找持有者（查自己的进程不需要 root，0.10.3 实测过 `lsof`；查别人的进程要）：

```bash
sudo fuser -vm /mnt/data     # 按挂载点列出进程与它在忙的动作
sudo lsof +D /mnt/data       # 列出这个目录树下所有打开的文件
```

`fuser -vm` 给你 PID 和 USER，`lsof +D` 给你具体哪个 fd。正确的处理是让持有者放手：进程还在跑就 `systemctl restart` 或 `kill -HUP` 让它重开文件，只是你自己 `cd` 在里面就 `cd /` 再卸载。

`umount -l`（lazy，对应 `MNT_DETACH`，2.4.11 起）容易让人误用。它做的事是：把挂载点立刻从命名空间视图里摘掉，禁止新进程再从这条路进去，但**已经在使用的进程继续用**，等引用清零时内核才真正拆掉文件系统。也就是说磁盘照样忙、空间照样不释放，只是 `lsblk` 里那个挂载点消失了。

按 Kerrisk 第 14 章的口径，`umount2()` 还有两个标志值得知道：`MNT_EXPIRE` 把挂载点标成「到期」，第一次调用必定失败并返回 `EAGAIN`，只有期间没人再访问它、第二次调用才真卸载——「自动回收一段时间没用的挂载」用的就是它；`MNT_FORCE` 只对 NFS 这类网络文件系统有意义，强行卸载可能丢数据。

### 0.10.5.4 `/etc/fstab` 六字段，以及它怎么变成开机时的动作

fstab 每行六个字段，顺序固定：设备、挂载点、类型、选项、dump、fsck 顺序。对照本机那三行真实内容：

| 字段 | 本机 `/` 那一行 | 写错会怎样 |
|:--|:--|:--|
| 设备 | `/dev/disk/by-uuid/fa8bbbea-...` | 设备不存在：这条挂不上，可能卡住开机 |
| 挂载点 | `/` | 目录不存在：挂载失败；不是空目录：老内容被盖住 |
| 类型 | `ext4` | 内核没这个模块：`unknown filesystem type` |
| 选项 | `defaults` | 选项名拼错：`mount` 报 bad option |
| dump | `0` | 备份工具 `dump` 的开关，现在基本恒为 0 |
| fsck 顺序 | `1` | 决定开机要不要检查、按几号顺序检查 |

选项里最常见的几个（`defaults` 本身就是「`rw, suid, dev, exec, auto, nouser, async` 这一串的组合」，按鸟哥第 7 章的汇整）：`ro`/`rw` 只读或可写；`noatime` 不更新访问时间，省一次元数据写；`noexec`/`nosuid`/`nodev` 是三道安全闸门，数据盘建议带上；`nofail` 让设备不存在时**继续启动**；`user`/`nouser` 决定普通用户能否挂载。

第三行 `/swap.img none swap sw 0 0` 里挂载点写的是 `none`——swap 没有挂载点，但字段位置不能省，这是「设备第二栏、挂载点第三栏」这条格式约定的代价。

**为什么设备要写 UUID 或 `/dev/disk/by-uuid/`，不写 `/dev/sda2`**：盘序会变。插一块新盘、换一根线、内核换个版本，`sda` 就可能变成 `sdb`；UUID 是格式化时写进超级块的（[0.10.2](ch10.md#sec-0.10.2)），跟着文件系统走。本机实测这两条链接是 udev 维护的：

```bash
ls -l /dev/disk/by-uuid/
```

```text
lrwxrwxrwx 1 root root 10 Oct 29 20:24 CF57-24FD -> ../../sda1
lrwxrwxrwx 1 root root 10 Oct 29 20:24 fa8bbbea-9f92-4241-b344-a824e4b676a6 -> ../../sda2
```

也就是说 fstab 里那串 `/dev/disk/by-uuid/...` 最终指向哪个分区，是 udev 每次扫描磁盘时重算的；`UUID=` 这种写法由 `mount` 自己解析，两种写法等价，生产上更常见的是前者（`blkid` 也能顺手给出同一串，0.10.2 已见过）。

fstab 不是被 init 直接执行的。systemd 有个生成器（generator，开机时把配置文件翻译成 unit 文件的小程序）会读 fstab，为每行生成一个 `.mount` 或 `.swap` unit。本机免特权就能看到它的产出：

```bash
ls /run/systemd/generator/
```

```text
boot-efi.mount        -.mount          swap.img.swap
local-fs.target.wants swap.target.requires  netplan.stamp  ...
```

```bash
systemctl cat boot-efi.mount
```

```text
# /run/systemd/generator/boot-efi.mount
# Automatically generated by systemd-fstab-generator
[Unit]
Documentation=man:fstab(5) man:systemd-fstab-generator(8)
SourcePath=/etc/fstab
Before=local-fs.target
Requires=systemd-fsck@dev-disk-by\x2duuid-CF57\x2d24FD.service
After=systemd-fsck@dev-disk-by\x2duuid-CF57\x2d24FD.service
[Mount]
What=/dev/disk/by-uuid/CF57-24FD
Where=/boot/efi
Type=vfat
```

（本机这条命令的输出前面还有四行提示，末行是 `Run 'systemctl daemon-reload' to reload units.`——systemd 发现磁盘上的 unit 和自己内存里那份不一致时就这样说；`After=blockdev@...target` 一行上面为省版面略去。）

这段把「改完 fstab 为什么要 `systemctl daemon-reload`」讲白了：fstab 是原料，磁盘上的 unit 是半成品，systemd 内存里的是成品；生成器只在开机（或重新加载）时跑一次，`daemon-reload` 让它重新生成并读进来。第 6 字段那个 `1` 在这里变成了 `Requires=systemd-fsck@...` ——fsck 顺序不是玄学，它落到一条 unit 依赖上。同理 `swap.img.swap` 就是 fstab 第三行 `/swap.img` 变出来的。

::: ex 例 0.10.5 · 不改任何东西，先跑 `findmnt --verify` {#ex-0.10.5}
`findmnt --verify` 会解析 fstab（默认还结合 `/proc/mounts`）并逐条报问题。**先猜**：在这台刚装好、fstab 由安装器生成、什么都没改的 Ubuntu 24.04 虚拟机上，它以普通用户身份运行，会不会报错？会报几条？

Ubuntu 实测（退出码 0）：

```text
/
   [W] cannot detect on-disk filesystem type (Permission denied)
/boot/efi
   [W] cannot detect on-disk filesystem type (Permission denied)
none
   [W] non-bind mount source /swap.img is a directory or regular file
   [W] cannot detect on-disk filesystem type (Permission denied)

0 parse errors, 0 errors, 4 warnings
```

关键在读最后一行：**`0 parse errors, 0 errors, 4 warnings`——语法完全没错，四条全是警告**。其中三条 `Permission denied` 是特权缺失（要打开 `/dev/sda2` 才能读磁盘上的真实类型，普通用户打不开块设备，见 [0.10.5.1](ch10.md#sec-0.10.5) 的 `brw-rw----`），不是 fstab 有问题。剩下那条 `non-bind mount source /swap.img is a directory or regular file` 才是值得看的：它在说「第一栏写的是 `/swap.img`，一个普通文件，却没有 `bind` 语义」。

这一条恰好是 swap 行的正常写法：`/swap.img` 是交换文件，`swap` 类型本来就不需要块设备，工具不认识这种写法才提出警告。**判读要点是分清「谁在报语法、谁在报权限、谁在报它自己不懂」**：只有 `errors`/`parse errors` 非零才是真错，`mount -a` 之前先把这两项压到 0。

::: sol 解答
猜「0 条」是错的：这台机器即使配置完全正确，普通用户跑也一定带 3 条权限警告。真正确认 fstab 可用的顺序是：`findmnt --verify`（看 errors 为 0）→ `sudo systemctl daemon-reload` → `sudo mount -a`（真挂一遍）→ `findmnt 挂载点` 与 `df -h 挂载点` 复核。`mount -a` 只挂当前未挂载的条目，所以如果你要测的那条已经被挂着，得先 `umount`——鸟哥第 7 章特意提醒过这一点，否则你测的是「什么都没发生」。
:::
:::

### 0.10.5.5 改完必须验，开不了机怎么救

四步验证，前三步本机都能跑（`sudo` 那步不能）：

```bash
sudo findmnt --verify            # 语法：0 parse errors, 0 errors
sudo systemctl daemon-reload     # 让 systemd 重新按 fstab 生成 unit
sudo mount -a                     # 按 fstab 真挂一遍未挂载项
findmnt /data && df -h /data      # 免特权复核：挂载点、类型、空间
```

`mount -a` 的作用是把「开机才会发生的事」压缩到现在。它过了，说明设备能找到、类型内核认识、选项合法；它失败时你在登录状态下就能改，比在启动日志里翻容易得多。

fstab 写错导致开不了机，典型现象是卡进 emergency mode（紧急模式，systemd 只把根挂上、起一个最小 shell 等你处理）。救援顺序：

1. 进 emergency/rescue shell：GRUB 菜单选 recovery，或在内核行尾加 `systemd.unit=rescue.target`（想彻底跳过 fstab 之外的服务可用 `single`）。
2. 把根改成可写：`mount -o remount,rw /`。紧急模式下根常常是只读的，不这一步就存不了文件。
3. 改 `/etc/fstab`：注释掉出错那行，或者给它加 `nofail`。
4. `systemctl daemon-reload`，`reboot`。

`nofail` 与 `x-systemd.device-timeout=10` 是防这一手的双保险：前者让设备不存在时不影响启动，后者把 systemd 等设备的默认超时压短，避免卡很久。`x-systemd.automount` 则是另一种取舍——把挂载推迟到第一次真正访问那个目录时才发生，适合不常用的备份盘和网络盘，代价是「访问时才失败」而不是「开机时就失败」。

上面这套救援流程在本机**未实测**：它是重启与 GRUB 层面的操作，会打断这台被别人也在用的虚拟机。要练，先在云主机的快照或本地虚拟机上走一遍。云环境下有一件事必须提前确认：串口控制台/救援模式是唯一入口，SSH 挂了你就没有第二条路，所以改 fstab 前先弄清楚你用的云厂商怎么进控制台。

还有一个只在 fstab 里出现的坑，配合 [0.10.3](ch10.md#sec-0.10.3) 第四条理解：挂载点目录**不该是空的**。有人把新数据盘挂到 `/data`，而 `/data` 里原本已经有几十 GB 旧文件，挂载那一刻起这些文件既不显示也无法删除，`df` 说满、`du` 说空。判读办法在 0.10.3 给过：把底层文件系统单独挂到别处再看目录大小。

::: errata 常见错误清单（0.10.5 节）
1. **「`/etc/fstab` 改了就得重启才生效」**——`mount -a` 立即按 fstab 挂一遍；但 systemd 侧要 `daemon-reload` 才会重新生成 unit，否则下次开机用的还是旧依赖。
2. **「`/etc/mtab` 是独立台账」**——Ubuntu 实测它是 `/proc/self/mounts` 的符号链接；问当前挂载看内核表，`findmnt` 读的就是这一份。
3. **「`umount` 报 busy 就用 `umount -l` 解决」**——lazy 只把挂载点从视图里摘掉，进程继续用、空间继续占；先 `fuser -vm`、`lsof +D` 找持有者。
4. **「fstab 里写 `/dev/sdb1` 没问题，机器上只有一块数据盘」**——加盘、换线、换内核都可能让盘符平移；写 `/dev/disk/by-uuid/` 或 `UUID=`，让 udev 去解析。
5. **「`findmnt --verify` 报 warning 就是配置坏了」**——本机实测三条 warning 来自普通用户打不开块设备，属权限缺失；只看 `0 parse errors, 0 errors` 这两项。
6. **「挂载点目录里的文件会被挂载清掉」**——不会，只是被盖住；换回旧内容的办法是 `umount`。
7. **「`mount --bind` 会复制一份目录」**——绑定挂载两处是同一份 inode，写一处另一处立刻可见；它和硬链接的差别是能针对目录、能跨文件系统（Kerrisk 第 14 章）。
:::

### 0.10.5 小结

挂载只改内核的一张表：把文件系统的根接到某个目录上，原目录内容被盖住但没消失；三份台账里 `/etc/fstab` 是愿望、`/proc/mounts` 是事实、`/proc/self/mountinfo` 多出根前缀与传播标记。fstab 由 systemd 生成器翻译成 `.mount`/`.swap` unit，第 6 字段变成 fsck 依赖，所以改完的顺序是 `findmnt --verify` → `daemon-reload` → `mount -a`，而不是重启赌一把。如果只记住一件事，那就是：**任何挂载配置的修改都要在还登得进去的时候验证一次**，`mount -a` 能替你把开机会发生的事提前跑一遍。

::: method 即时自测 · 0.10.5
**Q1（记忆）** fstab 六个字段依次是什么？`/proc/mounts` 里哪两个字段恒为 0，为什么？

**Q2（辨析）** `umount` 报 `target is busy` 和 `umount -l` 成功执行，这两件事同时意味着什么？为什么说 lazy 不是修复手段？

**Q3（应用）** 你要给一台机器加一块数据盘 `/dev/sdc1`，格式化好 ext4 后写进 fstab 开机自动挂到 `/data`，并希望「这块盘哪天掉了也不能影响开机」。写出这一行该怎么写，以及上线前你要跑的四条命令。

**Q4（迁移）** `/proc/self/mountinfo` 里有一行的根前缀是 `/snapd/ns`，传播标记那格是空的。这两件事各自说明什么？

::: sol 答案
**A1** 设备、挂载点、类型、选项、dump、fsck 顺序。第 5、6 字段（dump 与 fsck 顺序）在 `/proc/mounts` 里恒为 0：它们只是给 `dump(8)` 和开机 `fsck` 用的开关，内核挂载表不承担这个信息（Kerrisk 第 14 章）。
**A2** busy 是 `EBUSY`：有进程打开着里面的文件、或工作目录还在里面，卸载被拒绝。`-l`（`MNT_DETACH`）只是把挂载点从命名空间视图摘掉，禁止新访问，老进程继续用，引用清零才真拆——设备依然忙、空间依然不释放，所以它掩盖现象而不是解决占用；正确做法是 `fuser -vm`/`lsof +D` 找到持有者，让它重开文件或离开该目录。
**A3** 先 `blkid /dev/sdc1` 取 UUID，写 `/dev/disk/by-uuid/<UUID> /data ext4 defaults,nofail,noexec,nosuid,nodev 0 2`；`nofail` 保证掉盘不卡开机。验证四条：`findmnt --verify`（看 errors 为 0）→ `sudo systemctl daemon-reload` → `sudo mount -a` → `findmnt -T /data -o TARGET,SOURCE,FSTYPE,OPTIONS` 加 `df -h /data`。另外确认 `/data` 是空目录，否则盖住旧内容。
**A4** 根前缀不是 `/` 说明这是一次绑定挂载，接出来的是那个文件系统的子树（本机是 snapd 把 `/run` 里的一棵子目录挂到 `/run/snapd/ns`）。`-` 之前没有传播标记，按内核约定即 `private`：这个挂载点的挂载/卸载事件不与其他挂载命名空间互相传播，本机 `findmnt -no TARGET,PROPAGATION` 实测输出 `private`。
:::
:::

## 0.10.6 LVM：分层扩容 {#sec-0.10.6}

这一节回答：分区已经能划容量了，为什么还要在中间加一层 LVM？PV、VG、LV、PE 各管什么？在线扩容要按什么顺序动哪四层，为什么少一步 `df` 上的数字就不变？

[0.10.1](ch10.md#sec-0.10.1) 的四格链里，LVM 是插在「分区」和「文件系统」之间的一层映射；[0.10.5](ch10.md#sec-0.10.5) 讲的是把文件系统挂上树。这一节只看下面那层怎么在没有卸载、没有备份恢复的前提下变大。

::: preview 先抓住一件事
LVM 把「一块盘的容量」变成「一个池子的筹码」：PV 把盘（或分区、loop 设备）统一打成固定大小的 PE，VG 把许多 PV 的 PE 合成一个池，LV 从池里领走一批 PE。于是扩容变成三件事，顺序固定：让池子里有剩余 PE（`vgextend`）→ 让 LV 多领 PE（`lvextend`）→ 让文件系统占住新空间（`resize2fs`/`xfs_growfs`）。第三步没做，`lvs` 显示已经变大，`df` 仍是老数字——这是 LVM 运维里最高频的一个「我扩了但没生效」。
:::

### 0.10.6.1 先把「这台机器上有没有 LVM」做实

LVM 不是一个概念，它在系统里看得见摸得着：`lsblk` 的 `TYPE` 列会出现 `lvm`，`/dev/mapper/` 下会出现映射设备。这台 Ubuntu 24.04 虚拟机实测两者都没有：

```bash
lsblk -o NAME,SIZE,TYPE | awk '$3!="loop"'
ls -l /dev/mapper/
command -v lvm pvs lvcreate dmsetup
```

```text
NAME     SIZE TYPE
sda       64G disk
├─sda1     1G part
└─sda2  62.9G part
sr0     1024M rom

crw------- 1 root root 10, 236 Oct 29 20:24 control

/usr/sbin/dmsetup
```

四行结论：这台机器上一个 `lvm` 类型的设备都没有，`/dev/mapper/` 里只剩一个 `control`，`lvm`/`pvs`/`lvcreate` 三条命令都不存在（`command -v` 只交出 `dmsetup`）。原因也简单——装机时选了普通分区，fstab 第一栏写的是 `/dev/disk/by-uuid/...`（[0.10.5](ch10.md#sec-0.10.5) 见过），没走 LVM 安装方案；`lvm2` 包也没装，`apt-cache policy lvm2` 实测 `Installed: (none)`。本书环境不许装包，所以下面所有 LVM 命令与输出都是**要 root 且需要装 lvm2 才能跑的清单，未在本书环境复现**。

不过有一层东西是真的在这台机器上：**device-mapper**（内核里的通用块映射框架，LVM、dm-crypt、多路径都建在它上面）。Ubuntu 实测两条：

```bash
grep device-mapper /proc/devices
stat -c '%F 主:次=%t:%T' /dev/mapper/control
```

```text
252 device-mapper
character special file 主:次=a:ec
```

这两行把本节的机制说清了一半：内核已经准备好「把块设备重定向一遍」的机制，252 是所有 dm 块设备的主设备号（十进制）；`control` 是用户态命令对内核下指令的门，`ls -l` 给它的号是十进制 `10, 236`，而 `stat` 的 `%t`/`%T` 打印的是**十六进制**，所以显示 `a:ec`——同一个号码两种进制写法，读设备号时最容易看错的就是这里。`lvcreate` 做的事，最终就是往这个门里写一条映射表。换句话说，LVM 不是魔法，它是一张由内核维护的地址翻译表：LV 上的第 N 个块落在哪个 PV 的哪个 PE，全在那张表里。

### 0.10.6.2 四层各管什么

LVM 在盘和文件系统之间加了三样东西，名字都只有两三个字母，先把它们和「谁给谁划容量」对上：

<pre class="layout">
物理盘 /dev/nvme0n1
└─ 分区 /dev/nvme0n1p2（GPT）
   └─ PV /dev/nvme0n1p2 ──┐
                          ├─ VG vgdata ─┬─ LV lvdata → ext4 → /data
   PV /dev/nvme1n1p1 ─────┘             └─ LV lvlog  → XFS  → /var/log
</pre>

读图：左边是真实的盘和分区，中间 `vgdata` 是把两个 PV 的容量合并出来的池，右边是池里划出来的两条 LV，每条 LV 上再放一个文件系统、挂到一个目录。整个方向只有一个：**从左往右加，从右往左减**。

::: def 定义 0.10.6 · PV、VG、LV 与 PE {#def-0.10.6}
**物理卷**（Physical Volume，PV，被 LVM 收编的设备）可以是一整块盘、一个分区，也可以是一个 loop 设备；`pvcreate` 只是在设备尾部写上 LVM 的元数据标签。**卷组**（Volume Group，VG，池子）把若干 PV 的可用空间合成一个命名空间，池子里的最小筹码叫**物理扩展**（Physical Extent，PE，LVM 分配容量的最小单位，`vgcreate` 默认按 4 MiB 取整）。**逻辑卷**（Logical Volume，LV，从池里领走一批 PE 的那块虚拟分区）才是你 `mkfs` 的对象，它有两条路径名，指向同一个东西：`/dev/vgname/lvname` 和 `/dev/mapper/vgname-lvname`。
:::

按鸟哥第 14 章的口径，LVM 的价值在「**弹性调整文件系统容量**」，不在性能、也不在数据保全。这话有两层意思。一是默认分配方式是**线性**（linear，先把一个 PV 的 PE 用完再用下一个），不是把数据摊到多块盘上；二是想要性能或冗余，那是 RAID 的活（[0.10.7](ch10.md#sec-0.10.7)），LVM 的条带模式（`lvcreate --stripes`，形似 RAID 0）任何一条 PV 出事整条 LV 的数据就全废。

PE 大小为什么值得在 `vgcreate` 时想清楚：它是容量的取整粒度。`lvcreate -L 1G` 在 4 MiB 的 PE 上正好是 256 个 PE；如果你 `vgcreate -s 128M` 建了个大 PE 的 VG，那最小的 LV 也只能是 128 MiB，想给它加 10 MiB 是加不了的。这是纸面算术，不是本机实测。

顺带补一层最容易卡住的认识：**LVM 之后，`df` 看的仍然是文件系统**。这条链是「LV（块设备）→ 文件系统 → 挂载点」，`lvextend` 改的是第一环，`df` 报的是第三环。三环之间没有自动同步，这也是本节后面那个例子的全部内容。

### 0.10.6.3 扩容四步：每一步改的是哪一环

先记住一句话：**加一块盘不会让任何现有文件系统变大，四步每步只做一件事**。

| 步骤 | 命令 | 改的是哪一环 | 做完能观察到什么 |
|:--|:--|:--|:--|
| 一 | `pvcreate /dev/sdb1` | 设备 → PV | `pvs` 多一行，容量还没进池 |
| 二 | `vgextend vgdata /dev/sdb1` | PV → VG | `vgs` 的 `VFree` 变大 |
| 三 | `lvextend -L +50G /dev/vgdata/lvdata` | VG → LV | `lvs` 的 `LSize` 变大，**`df` 不变** |
| 四 | `resize2fs` 或 `xfs_growfs` | LV → 文件系统 | `df` 才真的变大 |

第三步和第四步之间那个缝隙，就是 LVM 最常见的故障现场。`lvextend -r`（`--resizefs`）是把两步并成一步：它内部调 `fsadm`，ext4 走 `resize2fs`、XFS 走 `xfs_growfs`，挂载着也能做，所以叫在线扩容。

方向不对称，而且不对称来自文件系统而不是 LVM。扩：ext4 与 XFS 都能在线扩。缩：ext4 可以先卸再 `resize2fs -p` 缩到指定大小、然后 `lvreduce`；**XFS 根本不能缩容**，想变小只能备份、重建、恢复（[0.10.2](ch10.md#sec-0.10.2) 已把这条硬约束列过）。所以缩容的固定顺序是「先缩文件系统，再缩 LV，最后才 `pvremove`」，反过来就是把文件系统切掉一角。

`vgs` 里有一列比容量更重要：`VFree`。它是池子里还没被 LV 领走的 PE 总量。`lvextend` 失败最常见的报错就是 `Insufficient free space`，此时不是要扩的 LV 有问题，而是池子空了——回到第二步再 `vgextend` 一块 PV 进来。

### 0.10.6.4 一版要 root 才能跑的清单

下面这套只在 loop 镜像文件上玩，不碰任何真盘。它需要 root（要 `losetup`、`pvcreate`、`mkfs`、`mount`），还需要装 `lvm2`；本书这台机器两样都不具备，因此**整段属形状示例，未在本书环境复现**。先建池子和一条 1 GiB 的 LV：

```bash
lab=/var/tmp/block-lab
mkdir -p "$lab" && cd "$lab"
for i in 1 2; do truncate -s 1G "disk$i.img"; done
loop1=$(sudo losetup -f --show "$lab/disk1.img")
loop2=$(sudo losetup -f --show "$lab/disk2.img")
printf 'loop1=%s loop2=%s\n' "$loop1" "$loop2"

sudo pvcreate "$loop1" "$loop2"
sudo vgcreate vglab "$loop1" "$loop2"
sudo lvcreate -L 1G -n lvdata vglab
sudo mkfs.ext4 -L lvlab /dev/vglab/lvdata
sudo mkdir -p /mnt/lvlab
sudo mount /dev/vglab/lvdata /mnt/lvlab
df -hT /mnt/lvlab
```

`vgcreate vglab` 一次收两块 PV，池子容量约 2 GiB（元数据要占掉尾部一点，按 4 MiB 取整）。`lvcreate -L 1G` 从池里领走 256 个 PE，于是 `vgs` 显示还剩约 1 GiB 空闲——这一步的算术在纸上就能推，不需要真跑。

再加第三个 1 GiB 镜像，把它扩进 VG，然后一步把 LV 和文件系统一起扩：

```bash
lab=/var/tmp/block-lab
truncate -s 1G "$lab/disk3.img"
loop3=$(sudo losetup -f --show "$lab/disk3.img")
sudo pvcreate "$loop3"
sudo vgextend vglab "$loop3"
sudo lvextend -L +1G -r /dev/vglab/lvdata
df -hT /mnt/lvlab
```

跑完应当看到的样子（形状示例，输出文本取自 lvm2 2.03 与 e2fsprogs 1.47 系列的常见格式，未在本书环境复现）：

::: ex 例 0.10.6 · 扩完了，`df` 为什么还是 1.0G {#ex-0.10.6}
某次扩容只跑了三步里的第三步：

```bash
sudo lvextend -L +1G /dev/vglab/lvdata
sudo lvs vglab/lvdata
df -hT /mnt/lvlab
```

**先猜**：`lvs` 和 `df` 各报什么？为什么？再给出补救命令，并说明为什么补救不需要 `umount`。

::: sol 解答
`lvs` 报 `LSize 2.00g`（LV 这一环已经变大），`df -hT` 仍报 `Size 1.0G`——文件系统里的超级块还记着老的块数，它不会自己去问块设备变大了没有，这正是 [0.10.2](ch10.md#sec-0.10.2) 那句「一切最终以文件系统为依归」的反面用例。补救是补第四步：ext4 用 `sudo resize2fs /dev/vglab/lvdata`，XFS 用 `sudo xfs_growfs /mnt/lvfs`（注意 XFS 那条给的是**挂载点**，不是设备名）。两者都支持在挂载状态下扩，所以不必 `umount`、不必停机；反过来 ext4 缩容就必须先卸载，这就是方向不对称的来源。
:::
:::

### 0.10.6.5 回滚这套实验

回滚顺序和创建相反：先卸文件系统，再删 LV、删 VG，最后清 PV 标签、解 loop、删镜像文件（同上一小节，需 root，未在本书环境复现）：

```bash
lab=/var/tmp/block-lab
sudo umount /mnt/lvlab 2>/dev/null || true
sudo lvremove -y vglab/lvdata 2>/dev/null || true
sudo vgremove -y vglab 2>/dev/null || true
for img in "$lab"/disk*.img; do
    for dev in $(sudo losetup -j "$img" -O NAME --noheadings); do
        sudo pvremove -y "$dev" 2>/dev/null || true
        sudo losetup -d "$dev"
    done
done
rm -rf "$lab"
```

`lvremove` 会二次确认，`-y` 是跳过确认；生产上不要习惯性加 `-y`，先 `lvs` 把 LV 名字看清算清楚。`pvremove` 只擦掉 PV 标签，镜像文件里的数据块要真删除得靠最后那条 `rm`。

LVM 还有第二用途：给目录做「随时回滚」的入口。`lvcreate --snapshot` 建的快照 LV 是一个写时差异空间——原 LV 每改一个块，旧块先复制到快照里，于是快照占的空间随改动量增长，快照写满时它会失效（原 LV 不受影响）。`thin` 池则允许 LV 的标称容量超过池子实际容量，靠真正写入时才分配 PE。这两条都属于「机制讲清、数字未实测」，本书环境跑不了；要做快照备份，先在测试机上把 `lvs` 的快照属性一列盯够一次。

::: note 安全警告 · LVM 命令的破坏性
`pvcreate` 会覆盖设备上的文件系统签名，`vgcreate` 会接管 PV，`lvremove` 会删除 LV 上的全部数据。对真盘执行前，用 `lsblk`、`pvs`、`vgs` 确认设备没有被其他 VG 使用；多路径（MPIO）和 iSCSI 设备还要先确认 `/dev/mapper` 的映射关系，避免对同一块盘两条路径各建一次 PV。
:::

::: errata 常见错误清单（0.10.6 节）
1. **「`lvextend` 之后文件系统自动变大」**——`lvextend` 只改块设备那一环；要 `-r`，或者手动补 `resize2fs`/`xfs_growfs`，`df` 才会变。
2. **「LVM 能提升性能、也能容错」**——默认分配是线性的，容量弹性才是它的用途；要性能与冗余请选 RAID，LVM 的条带模式坏一条 PV 就整条 LV 报废。
3. **「VG 满了只能重建」**——`vgextend` 再收一块 PV 进池即可；这也是 LVM 相对裸分区的真正价值。
4. **「缩容和扩容一样顺手」**——先缩文件系统再缩 LV，顺序反了就是数据丢失；XFS 压根不能缩，只能备份、重建、恢复。
5. **「`/dev/vglab/lvdata` 和 `/dev/mapper/vglab-lvdata` 是两块设备」**——同一个 LV 的两条路径名，前者是后者的符号链接视图。
6. **「`pvcreate` 只是打个标记，很安全」**——它会写设备尾部的元数据并覆盖已有签名；对错设备就是毁掉别人的文件系统。
7. **「装了 lvm2 就能看 LV」**——本机实测 `command -v lvm pvs lvcreate` 什么都没有，`/proc/devices` 里却仍有 `252 device-mapper`：内核有映射框架不等于系统里有逻辑卷，判据是 `lsblk` 的 `TYPE` 和 `/dev/mapper/`。
:::

### 0.10.6 小结

LVM 在分区和文件系统之间插了 PV、VG、LV 三层，最小筹码是 PE；池子的容量、LV 的大小、文件系统的大小是三件独立的事，扩容要按 `pvcreate` → `vgextend` → `lvextend` → 扩文件系统四步走，`lvextend -r` 只是把后两步合并。缩容方向相反，而且 XFS 根本不给你缩。如果只记住一件事，那就是：**`df` 不跟着 `lvs` 变，就说明第四步还没做**。

::: method 即时自测 · 0.10.6
**Q1（记忆）** 写出 LVM 扩容的四步命令，并说明每步改动的是哪一环。

**Q2（辨析）** `lvs` 显示 LV 是 2.00g，`df -hT` 显示挂载点只有 1.0G。哪一个「错了」？另一种可能的解释（LV 确实变小了）要怎么排除？

**Q3（应用）** 生产机 `/data`（ext4，在 LV 上）报 95%，`vgs` 显示 `VFree 0`。请按顺序给出你要跑的命令，说清哪一步能立刻缓解、哪一步需要先加硬件。

**Q4（迁移）** 同事想把一条 500 GiB 的 XFS LV 缩到 300 GiB 腾容量给别的 LV。你的答复是什么？给出两条可执行路线。

::: sol 答案
**A1** `pvcreate`（设备→PV）、`vgextend`（PV→VG，池子变大）、`lvextend`（VG→LV，领更多 PE）、`resize2fs`/`xfs_growfs`（LV→文件系统，`df` 才变）。前三步只到块设备层。
**A2** 都没错，量的不是同一环：`lvs` 量块设备大小，`df` 量文件系统大小，中间的差就是没做第四步。要排除「LV 真的变小」，看 `lvs` 的完整字段与 `lvdisplay`，并确认 `df` 打的挂载点确实来自这条 LV（`findmnt -T /mnt/lvlab` 看 SOURCE）；SOURCE 不是这个 LV，说明你在比两个不同的文件系统。
**A3** 顺序：`df -hT /data` → `lvs` 看 LSize → `vgs` 看 VFree。`VFree` 有剩余就 `lvextend -r`，这一步立刻缓解、不需要硬件；`VFree` 为 0 就必须先加盘或加大现有 PV（`pvresize` 在底层分区已被扩大的情况下可以立刻把新容量喂进池子，这是唯一不用新增硬件的路），再 `pvcreate`/`vgextend` → `lvextend -r`。别忘 ext4 的 5% 预留（0.10.3）也影响什么时候写不进去。
**A4** 答复：XFS 不能缩容，`xfs_growfs` 只能变大，`lvreduce` 直接把文件系统切掉一角。两条路线：一，新建一条 300 GiB 的 LV 与 XFS，把数据 `rsync` 过去、切挂载点、验证后再删旧 LV；二，等 VG 里有空余 PE 时什么都不做，把新 LV 从 `VFree` 里划——但本机 VG 已无剩余时仍需先扩 VG。两条都要求先做完整备份再动手。
:::
:::

## 0.10.7 RAID：级别取舍与 `mdadm` {#sec-0.10.7}

这一节回答：多块盘拼一起能换来什么？RAID 0/1/5/6/10 的可用容量和容错数怎么算，写性能为什么会在 RAID 5 上掉一截？坏一块盘之后到底发生了什么？

[0.10.6](ch10.md#sec-0.10.6) 的 LVM 管的是「容量怎么弹性变大」，明确不管性能和冗余；RAID 管的是另一件事：用多块盘的代价换数据保全或吞吐。两者都叠在块设备之上，也常常叠在一起用——先做 RAID 出一块大设备，再在它上面建 LVM。

::: preview 先抓住一件事
所有 RAID 级别都只做两件事：**条带化**（striping，把数据切成固定大小的 chunk 轮流摆到各盘上，换吞吐）和**加冗余**（复制或算校验，换容错）。级别差别就在「摆几份、摆哪里、怎么算」。于是选级别其实是回答三个数字问题：可用容量是多少、能同时坏几块盘、一次随机写要碰几次盘。这三个数都能用纸面算术算出来，本节全部给出算式；`mdadm` 的实际输出在这台机器上跑不了（缺 root 也缺 `mdadm`），照实标注。
:::

### 0.10.7.1 先看清这台机器有没有 RAID

软件 RAID（Linux 里由 `md` 驱动实现的 RAID，设备名形如 `/dev/md0`）在系统里有一个免特权就能看的入口：`/proc/mdstat`。Ubuntu 实测：

```bash
cat /proc/mdstat
```

```text
Personalities :
unused devices: <none>
```

这一屏有两个信息点。`unused devices: <none>` 说现在没有任何阵列在跑；`Personalities :` 后面**是空的**，说的是内核此刻连一种 RAID 算法都没有加载——有 `md` 相关模块进来时，这一行会列出一串 `[raid0] [raid1] [raid4] [raid5] [raid6]` 之类的名字，具体列哪些取决于加载了哪些模块。 personality（算法人格，内核里实现某个级别的那段代码）没加载，是因为这台 VM 装机时没人建过阵列，`md` 的模块是按需加载的。

顺带确认工具也不在（Ubuntu 实测 `command -v mdadm` 无输出）。所以本节所有 `mdadm` 命令都要在有 root 且装了 `mdadm` 的机器上做，本书环境**未实测**，命令序列以「要 root 才能跑的清单」给出。

### 0.10.7.2 两个动作，五个级别

**条带化**（striping，把数据切成 chunk 轮流写各盘）解释为什么 RAID 0 快：100 MiB 数据、2 块盘、64 KiB 的 chunk，就是一场交替写入，两块盘的机械/闪存耗时可以重叠。它也解释了 RAID 0 为什么容错为 0——每个文件被切成碎片散在各盘，任何一块没了，所有文件都缺一块。

**冗余**有两种做法。一种是**镜像**（mirror，同一份数据写两份到不同盘，RAID 1 的做法），代价是容量减半、写要做两遍。另一种是**奇偶校验**（parity，用异或算出的那份冗余数据， RAID 5/6 的做法）：把 N 块盘的数据按 chunk 分组，每组额外算一份校验存进这一组的某一盘上，校验位置逐组轮转，于是校验负载也摊平了。任何一盘的内容都能用「同组其他盘 + 那份校验」异或算回来，这就是「只坏一块盘也能救回来」的原理；RAID 6 存两份独立校验，才敢同时坏两块。

| 级别 | 最少盘 | 可用容量 | 能同时坏几块 | 读 | 随机写要碰几次盘 | 典型场景 |
|:--|--:|:--|--:|:--|:--|:--|
| RAID 0 | 2 | N × 单盘 | 0 | 快 | 1 | 临时缓存、可重建的中间数据 |
| RAID 1 | 2 | 1 × 单盘 | 1 | 快 | 2（两份都要写） | 系统盘、小容量高可靠 |
| RAID 5 | 3 | (N−1) × 单盘 | 1 | 快 | 4 | 通用文件存储、顺序为主 |
| RAID 6 | 4 | (N−2) × 单盘 | 2 | 快 | 6 | 大容量、重建时间长 |
| RAID 10 | 4 | N/2 × 单盘 | 每镜像组 1 | 快 | 2 | 数据库、高 IOPS |

这张表最关键的是倒数第二列。RAID 5 那一步「4 次」是这么来的：改一个 chunk 的旧值 → 新校验 = 旧校验 ⊕ 旧数据 ⊕ 新数据，所以要**读旧数据、读旧校验**，然后**写新数据、写新校验**——一次逻辑写变成 4 次物理 I/O，这就是**写惩罚**（write penalty，一次写引发的额外读写次数）。顺序大块写可以把整个条带凑满，旧数据不必读、校验一次算完整组，惩罚就基本消失；随机小写躲不掉。RAID 6 因为要算两份校验，同样一套流程变成 6 次。

按鸟哥第 14 章的口径，RAID 10 是「先两两镜像、再把镜像组条带化」，所以它牺牲一半容量换两件事：随机写只写自己那一对、重建时只从**同组另一块盘**直接复制——不像 RAID 5/6 要把整组所有盘全部读一遍来重算。这也带出 RAID 最大的一个风险窗口：**重建期间**。

容量数字都用同一套算术给（单位按 GiB，`1 GiB = 1024 MiB`；这些是纸面推导，不是实测）：4 块 2 TiB 的盘，RAID 0 得 8 TiB、RAID 1 得 2 TiB、RAID 5 得 6 TiB、RAID 6 得 4 TiB、RAID 10 得 4 TiB。另外每块盘会被超级块和重建记录元数据吃掉一点，实际可用总略小于这个整数——`mdadm --create` 之后要以 `mdadm --detail` 里的 `Array Size` 为准，别拿标称值做规划。

::: def 定义 0.10.7 · 降级与重建窗口 {#def-0.10.7}
**降级**（degraded，少了一块成员盘但阵列仍可读写）状态下数据没有任何冗余：RAID 5 再坏一块就全废，所以「坏一块还能跑」不等于「还能慢慢跑不着急」。**重建**（recovery/resync，把缺的那块盘的数据重新算出来写满）期间所有成员盘都在满负荷读写，阵列性能下降，而且第二块盘坏掉的概率正好最高的时候。重建耗时按算术是「盘容量 ÷ 有效重建吞吐」：1 块 4 TiB 的盘接入 RAID 5，若整体只能维持 100 MiB/s，那至少要 `4×1024×1024 MiB ÷ 100 MiB/s ≈ 11.6 小时`；这个 100 MiB/s 是假设值，真实速度取决于盘的吞吐与并发负载，本机未实测。RAID 缩短的是停机时间，不是备份——它挡不住误删、文件系统损坏和整台机器被毁。
:::

顺手补一个容易混的点：**RAID 和 [0.10.6](ch10.md#sec-0.10.6) 的 LVM 谁在下面**。RAID 把多块盘拼成一块更可靠或更快的设备，LVM 把多块设备拼成一个容量池，两者都叠在块设备之上。生产上常见的叠法是从下往上：`mdadm` 先拼出 `/dev/md0`，再在它上面 `pvcreate` → `vgextend` → `lvcreate`，最后才 `mkfs` 与挂载；反过来给每条 LV 各建一套 RAID 极少见。`lsblk` 的 `TYPE` 列能一眼看出这一层：`raid1`/`raid5`/`lvm`/`crypt` 都是叠在真盘之上的映射层（[0.10.1](ch10.md#sec-0.10.1) 见过这张名单）。

### 0.10.7.3 一版要 root 才能跑的 `mdadm` 清单

三块 512 MB 的 loop 镜像拼一个 RAID 5，挂起来用。需要 root（`losetup`、`mdadm`、`mkfs`、`mount` 全要特权），本机也未实测：

```bash
lab=/var/tmp/block-lab
mkdir -p "$lab" && cd "$lab"
for i in 1 2 3; do truncate -s 512M "raid$i.img"; done
loops=()
for img in raid1.img raid2.img raid3.img; do
    loops+=("$(sudo losetup -f --show "$img")")
done
printf '%s\n' "${loops[@]}"

sudo mdadm --create /dev/md/raidset --level=5 --raid-devices=3 \
    --chunk=64 "${loops[@]}"
sudo mkfs.ext4 -L raidlab /dev/md/raidset
sudo mkdir -p /mnt/raidlab
sudo mount /dev/md/raidset /mnt/raidlab
cat /proc/mdstat
```

`--create` 会直接改写成员盘上的数据，执行前必须按章首那条安全警告用 `lsblk`、`findmnt` 确认目标；它还可能提示「设备里好像有旧文件系统」，此时继续就等于亲手抹掉旧数据。

阵列建好后，`/proc/mdstat` 的样子（形状示例，未在本书环境复现）：

```text
Personalities : [raid6] [raid5] [raid4]
md127 : active raid5 loop2[2] loop1[1] loop0[0]
      1046528 blocks super 1.2 level 5, 64k chunk, algorithm 2 [3/3] [UUU]
```

读这一行的三个数：`1046528 blocks` 是可用块数（1 KiB 为单位），约 1.0 GiB——三块 512 MiB 的盘按 (N−1) 算正好是 1 GiB 量级，减掉的是每盘超级块与重同步日志占的位置；`[3/3]` 是「应有 3 块 / 现有 3 块」；`[UUU]` 是逐盘状态，`U` 为 up、`_` 为缺席。把这两组括号对上，就能一眼判断阵列是不是在降级。

### 0.10.7.4 坏一块盘之后：fail、remove、add

模拟与救援的动作全在 `mdadm --manage` 上，同样需要 root，属要跑就能跑但本书未实测的清单：

```bash
sudo mdadm /dev/md/raidset --fail /dev/loop0     # 手动标记为坏，看降级行为
sudo mdadm /dev/md/raidset --remove /dev/loop0   # 从阵列里热拔
truncate -s 512M "$lab/spare.img"
spare=$(sudo losetup -f --show "$lab/spare.img")
sudo mdadm /dev/md/raidset --add "$spare"        # 热插，阵列开始重建
watch -n 2 cat /proc/mdstat                      # 盯重建进度
```

重建进行中的 `/proc/mdstat` 会长这样（形状示例，未在本书环境复现）：

```text
md127 : active raid5 loop3[3] loop2[2] loop1[1]
      1046528 blocks super 1.2 level 5, 64k chunk, algorithm 2 [3/2] [UU_]
      [=>...................]  recovery =  8.2% (43008/523264) finish=0.1min speed=60000K/sec
```

`[3/2] [UU_]` 就是「应该有 3 块、现在只有 2 块在工作」；最后一行给进度、已重建块数、预计剩余时间和当前速度。看这一行有三层用途：判断要不要立刻赶去机房、判断重建会不会把业务拖死（`speed` 高说明吞吐全压在重建上）、判断第二块盘坏掉的风险窗口还有多久。

按鸟哥第 14 章的口径，生产上更常见的是**热备盘**（spare disk，事先放阵列里但平时不参与的那块盘）：建阵列时用 `--spare-devices=1` 多给一块，成员盘一坏，spare 自动被拉进去重建，`mdadm --detail` 里会看到那块盘的状态从 `spare` 变成 `spare rebuilding`。少了人工 `--add` 这一步，重建就能在坏盘当场开始——这才是「容错 1 块」真正落地的样子。

`mdadm --detail` 比 `mdstat` 给得多：`State`（clean / degraded, recovering）、`Active Devices`、`Failed Devices`、`Spare Devices` 和逐盘的 `RaidDevice`/`State` 表。监控应该抓的是这几个字段，而不是只看阵列还在不在。

::: ex 例 0.10.7 · 四块 2 TiB 的盘，先算再选 {#ex-0.10.7}
你要用 4 块 2 TiB 的盘给一台存大文件的备份机做阵列，要求「至少还能坏一块盘，容量尽量大」。**先猜**你会选哪个级别、可用容量多少，再说明这个选择最贵的一处代价是什么。

::: sol 解答
按容量算术：RAID 0 是 8 TiB 但容错 0，出局；RAID 1（两两镜像再拼）4 TiB；RAID 5 是 (4−1)×2 = 6 TiB，容错 1 块；RAID 6 是 (4−2)×2 = 4 TiB，容错 2 块。要「还能坏一块 + 容量最大」，答案是 RAID 5，6 TiB。最贵的代价是重建窗口：坏的那块 2 TiB 要从其余 3 块盘全量重算写回，期间其余盘的读取量约等于 2 TiB ×（3 份数据+校验的参与比例，粗略就是整组各读约 2/3 TiB 以上），这段时间里再坏一块就是全盘报废——所以大容量盘做 RAID 5 的顾虑不是日常性能，而是重建期风险，这正是 RAID 6 用 2 TiB 容量换第二块容错的理由。以上是纸面算术与结构性结论，具体重建时长本机未实测。
:::
:::

回滚这套实验，最容易漏的一步是清超级块（需 root，未实测）：

```bash
lab=/var/tmp/block-lab
sudo umount /mnt/raidlab 2>/dev/null || true
sudo mdadm --stop /dev/md/raidset
for img in "$lab"/raid*.img "$lab"/spare.img; do
    [ -e "$img" ] || continue
    for dev in $(sudo losetup -j "$img" -O NAME --noheadings); do
        sudo mdadm --zero-superblock "$dev" 2>/dev/null || true
        sudo losetup -d "$dev"
    done
done
rm -rf "$lab"
```

`mdadm --stop` 只停阵列，不擦成员盘上的 RAID 超级块；不清 `--zero-superblock` 就把这些盘复用，下次 `mdadm --assemble`（甚至开机时的自动扫描）可能把旧阵列重新拼出来，容量和数据看起来「又回来了」，其实是你以为已经抹掉的那份。鸟哥第 14 章同样用 `dd` 写过盘头来彻底清除，原理一致：让超级块失效。

::: errata 常见错误清单（0.10.7 节）
1. **「RAID 5 坏一块还能随便跑」**——降级状态没有冗余，再坏一块全丢；重建期间恰恰是最危险的时间窗，RAID 也不是备份，它挡不住误删和整机损毁。
2. **「RAID 级别越高越好」**——级别不是阶梯，是三个数字的取舍：容量、能同时坏几块、一次随机写碰几次盘。RAID 6 比 5 多一块容错，代价是 2 TiB 级别的容量和更慢的写。
3. **「RAID 0 只是没冗余，坏盘丢的是一部分文件」**——条带化把每个文件切成 chunk 散在所有盘上，坏一块盘等于阵列上所有文件都缺角。
4. **「可用容量 = 盘数 × 标称容量」**——RAID 5 少一份、RAID 6 少两份、RAID 1/10 少一半，还要减每盘的元数据；以 `mdadm --detail` 的 `Array Size` 为准。
5. **「有 `mdadm` 就能看 RAID」**——本机实测 `command -v mdadm` 无输出、`/proc/mdstat` 的 `Personalities` 为空，这两条是「这台机器上既没工具也没阵列」的免特权判据。
6. **「`mdadm --stop` 之后盘就干净了」**——超级块还在，`--assemble` 或开机自动扫描会把旧阵列拼回来；复用前一定 `--zero-superblock`。
:::

### 0.10.7 小结

RAID 的全部差别都在两个动作里：条带化换吞吐，复制或奇偶校验换容错。可用容量、容错盘数、一次随机写的 I/O 次数三个数都能纸面算出来——RAID 5 少一份容量、容错 1 块、随机写要 4 次 I/O，RAID 6 少两份、容错 2 块、6 次，RAID 10 一半容量换「只从同组盘重建」。如果只记住一件事，那就是：**降级和重建期间才是 RAID 的风险窗口，看到 `[3/2] [UU_]` 就得当成事故在处理，而不是「还能用」**。

::: method 即时自测 · 0.10.7
**Q1（记忆）** 写出 RAID 0/1/5/6/10 在 N 块盘下的可用容量公式与容错盘数，并说明 RAID 5 一次随机写为什么要 4 次 I/O。

**Q2（辨析）** `/proc/mdstat` 里 `Personalities :` 后面是空的，这一台机器能不能建 RAID 5？说出你还要确认的两件事与对应命令。

**Q3（应用）** 6 块 4 TiB 的盘要放虚拟机镜像，客户要求「重建期间也不许丢数据」。按算术给出你会选的级别、可用容量，以及你拒绝 RAID 5 的理由。

**Q4（迁移）** 实验做完，你 `mdadm --stop` 之后直接把这几块 loop 盘 `mkfs.ext4` 用了，第二天发现容量又变回了阵列。发生了什么，怎么彻底避免？

::: sol 答案
**A1** 容量：0 为 N、1 为 1、5 为 N−1、6 为 N−2、10 为 N/2（各乘以单盘容量）；容错：0 块、1 块、1 块、2 块、每镜像组 1 块。写惩罚来自「读旧数据 + 读旧校验 + 写新数据 + 写新校验」：新校验必须由旧校验与新旧数据异或得到，不凑满整条时旧数据非读不可。
**A2** 不能立刻建，但原因不是硬件不支持。空 `Personalities` 说明 md 的级别模块此刻没加载（它们是按需加载的）。本机实测这些实现文件其实就在盘上：`ls /lib/modules/$(uname -r)/kernel/drivers/md/` 交出 `raid0.ko.zst`、`raid1.ko.zst`、`raid456.ko.zst`、`raid10.ko.zst`，和 [0.10.2](ch10.md#sec-0.10.2) 里「XFS 模块在盘上但没加载」是同一件事。要确认的两件事：一，`command -v mdadm`（用户态工具在不在，本机是不在）；二，`modprobe raid456` 这类加载动作（需要 root，本机做不了）。两样都不满足，所以整节命令清单标为未实测。
**A3** 选 RAID 6：可用 (6−2)×4 = 16 TiB，容错 2 块。理由是降级/重建窗口的风险：RAID 5 坏一块后，重建期间第二块盘故障就全盘报废，重建要读的其它盘越多、耗时越长，风险越高；6 盘 × 4 TiB 属于「大容量 + 长重建」组合，RAID 6 用 4 TiB 容量买第二份容错。想同时要性能则考虑 RAID 10（12 TiB，容错按镜像组算），容量比 RAID 6 少 4 TiB。全部为算术结论。
**A4** RAID 超级块还在成员盘上，`mdadm --assemble --scan`（或发行版开机时的自动扫描）看到有效超级块就把旧阵列重新拼了出来，此时你 `mkfs` 写的是「阵列上的文件系统」，数据布局早已被旧阵列映射过一遍。避免办法是复使用前逐盘 `sudo mdadm --zero-superblock /dev/xxx`，再 `wipefs` 检查签名（`wipefs 设备` 列出仍在的签名，属未实测清单）。
:::
:::

## 0.10.8 swap、TRIM、配额与磁盘健康 {#sec-0.10.8}

这一节回答：内存不够时磁盘顶在哪里？SSD 上删掉的空间怎么真正还给盘？配额是第三种「写不进去」，它和块满、inode 满怎么区分？盘的寿命从哪里读？

[0.10.2](ch10.md#sec-0.10.2) 说过 tmpfs 的页可以被换出到 swap，[0.10.4](ch10.md#sec-0.10.4) 分清块与 inode 两个计数器，[0.10.5](ch10.md#sec-0.10.5) 里 fstab 第三行那条 `/swap.img none swap sw 0 0` 就是本节第一件事的入口。这一节把「日常运维的四件小事」讲完：交换、TRIM、配额、健康。

::: preview 先抓住一件事
这四件事有一个共同点：**默认都在跑，但都不报错**。swap 配了却常年 0 使用；`fstrim.timer` 每周把 SSD 的空闲块批量告知盘；配额没开就完全不存在，一开就多出一个 `EDQUOT`；盘的寿命要靠你自己去读 SMART 或内核日志，它不会主动喊。所以本节先给这台机器上的真实状态，再给需要 root 才能改的清单。
:::

**先看本机 swap 的真实状态**（Ubuntu 实测，三条命令免特权）：

```bash
swapon --show
cat /proc/swaps
free -h
```

```text
NAME      TYPE SIZE USED PRIO
/swap.img file   4G   0B   -1

Filename				Type		Size		Used	Priority
/swap.img                               file		4194300		0		-1

               total        used        free      shared  buff/cache   available
Mem:            11Gi       856Mi       9.3Gi        33Mi       1.7Gi        10Gi
Swap:          4.0Gi          0B       4.0Gi
```

四个读数要一起看：这是一块 4 GiB 的**交换文件**（swap file，拿一个普通文件当交换区），当前使用 `0B`；`/proc/swaps` 的 `Size` 列单位是 KiB，`4194300` 略小于 `4×1024×1024`，因为文件头要放 swap 自己的签名与映射表；`PRIO=-1` 是优先级，多个交换区时内核先用量号优先级高的。

`USED` 是 0 不是「swap 坏了」，而是这台机器 11 GiB 内存还剩 10 GiB `available`——**内存有富余时内核不会主动把页搬去 swap**。这就是很多人监控看错的地方：`free` 的 Swap 一行全 0，说明系统健康；真开始吃 swap，往往意味着内存压力已经上了一段时间。鸟哥第 7 章那句「用 swap 时磁盘灯闪个不停」讲的就是这个阶段的代价：换页走的是磁盘，比内存慢几个数量级。

这里要补一层容易缺的认识：**交换区不是「额外的内存」，也不属于任何文件系统**。`/swap.img` 虽然是个文件，但内核读写它时绕过 ext4 的分配逻辑，直接按 swap 自己的块映射走，所以 `df` 里看不到 swap，`du` 也数不出它占的 4 GiB——那 4 GiB 是实打实在根文件系统上的块。文件权限也印证了它敏感：

```bash
ls -l /swap.img
```

```text
-rw------- 1 root root 4294967296 Oct 21 19:23 /swap.img
```

`600`、属主 root。内存页里可能有密码、密钥明文，交换到盘上就是这些字节躺在文件里，其他用户若能读这个文件，就等于读了别人的内存。这也是下面清单里 `chmod 600` 不是可选项的原因。

**加一块 swap 的清单**（需 root，且要能改 fstab，本书环境**未实测**）：

```bash
sudo fallocate -l 4G /swapfile        # 快速预留；Btrfs 上不能用 fallocate，改 btrfs filesystem mkswapfile
sudo chmod 600 /swapfile              # 必须：swap 里可能有明文密钥
sudo mkswap /swapfile                 # 写下 swap 签名，此时 blkid 会报 TYPE="swap"
sudo swapon /swapfile                 # 启用
swapon --show                         # 免特权复核
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab   # 开机自动启用

# 回滚
sudo swapoff /swapfile                # 把页换回内存！内存不足会触发 OOM
sudo sed -i '\#^/swapfile #d' /etc/fstab
sudo rm /swapfile
```

三点判断依据：`mkswap` 只是格式化，不 `swapon` 之前 `free` 的 Swap 行不会变（鸟哥第 7 章用「`swapon -a` 之后再 `swapon -s` 确认」来收尾，道理相同）；`swapon --show` 里出现两条时，优先级数字大的先用；`swapoff` 是反向操作，它要把这块 swap 上的每一页都拉回内存，内存本来就不够时这一步会把进程打死，所以生产上先 `free -h` 看余量再动手。

**TRIM：告诉盘哪些块不再用了。** 机械盘上删除只是改位图，块留着旧数据无所谓；SSD 必须知道「这些块以后不会再读」才能提前擦除，否则写入要先擦后写，越用越慢。这个告知动作叫 TRIM（也叫 discard），有两条路：

- 挂载选项 `discard`：每次删除同步发一条 TRIM，删小文件的延迟被放大。
- 定期 `fstrim`：一次批量把空闲块告知盘，代价集中在一个时间点。

Ubuntu 24.04 默认走第二条，而且本机免特权就能验证它在跑（Ubuntu 实测）：

```bash
systemctl list-timers fstrim.timer --no-pager
systemctl cat fstrim.service
```

```text
NEXT                          LEFT     LAST                        PASSED UNIT         ACTIVATES
Mon 2026-11-02 00:18:22 CST 3 days    Thu 2026-10-29 14:07:48 CST      -  fstrim.timer fstrim.service

[Service]
Type=oneshot
ExecStart=/sbin/fstrim --listed-in /etc/fstab:/proc/self/mountinfo --verbose --quiet-unsupported
```

`ExecStart` 这一行把机制说全了：`--listed-in /etc/fstab:/proc/self/mountinfo` 表示「只对既在 fstab 里、又在当前挂载表中的文件系统做 TRIM」，`--quiet-unsupported` 表示盘不支持就直接跳过不报错。上一条真实执行结果在 journal 里（Ubuntu 实测，由定时器以 root 身份执行、普通用户可读日志）：

```bash
journalctl -u fstrim.service -n 1 --no-pager
```

```text
Oct 29 14:07:49 juanwang-Ubuntu24.04 fstrim[49383]: /: 37.4 GiB (40124334080 bytes) trimmed on /dev/disk/by-uuid/fa8bbbea-9f92-4241-b344-a824e4b676a6
```

「trimmed 37.4 GiB」说的是**告知给盘的连续空闲区有 37.4 GiB**，不是「释放了 37.4 GiB」——这些空间本来在文件系统账上就是空闲的（对照 [0.10.3](ch10.md#sec-0.10.3) 的 `stat -f`），这一步只是把它们告诉盘。想手动跑一次是 `sudo fstrim -av`，需要 root，本机未实测。

盘本身支不支持 TRIM，读 sysfs 和 `lsblk` 就够（Ubuntu 实测）：

```bash
lsblk -d -o NAME,ROTA,DISC-GRAN,DISC-MAX /dev/sda
cat /sys/block/sda/queue/rotational /sys/block/sda/queue/discard_granularity /sys/block/sda/queue/logical_block_size
```

```text
NAME ROTA DISC-GRAN DISC-MAX
sda     0        4K       2G

0
4096
512
```

`ROTA=0` 表示内核把这块设备当非旋转介质看待（也就是 SSD 一类的盘）；`DISC-GRAN=4K` 是 discard 的最小粒度、`DISC-MAX=2G` 是一次能发多少，这两个非零值就是「盘和内核之间的 TRIM 通路是通的」的证据。反过来说，`DISC-GRAN` 显示 `0` 才是不支持，此时 `fstrim` 会报 `the discard operation is not supported`，那是能力问题而不是文件系统坏了。对照 [0.10.14](ch10.md#sec-0.10.14) 里对 loop 设备的说法：loop 的 discard 能力继承自后端文件所在的文件系统。

**磁盘健康：SMART 与内核日志。** 这台机器上 `smartctl` 没装（Ubuntu 实测 `command -v smartctl` 无输出），SMART（Self-Monitoring, Analysis and Reporting Technology，盘自己记账的寿命与错误指标）那一层因此**未实测**；要看得先 `apt install smartmontools`（本书环境不许装包）。命令形状照给，SATA 盘 `sudo smartctl -a /dev/sda`，NVMe 盘 `sudo smartctl -a /dev/nvme0` 或 `nvme smart-log /dev/nvme0`。读的属性名要写全，按名字 grep 才对得上：`Reallocated_Sector_Ct`（重映射扇区数）、`Current_Pending_Sector`（等待重映射的扇区）、`Media_Wearout_Indicator`（磨损指示）、`Percentage Used` 与 `Available Spare`（NVMe 的寿命百分比与备用块比例）；任一非零且继续变化，先备份再做 `sudo smartctl -t short` 自检，别把自检当备份用。

内核侧的 I/O 错误记录不需要装包，但要读对地方。这台机器上 `dmesg` 直接被拒（Ubuntu 实测）：

```bash
dmesg | tail -1
```

```text
dmesg: read kernel buffer failed: Operation not permitted
```

替代是 `journalctl -k`，普通用户就能读（实测可用），过滤口径不变：

```bash
journalctl -k --no-pager | grep -icE 'I/O error|medium error|Unrecovered|task abort|resetting link'
```

```text
0
```

`0` 就是这台机器内核日志里没有 I/O 错误记录——这是个干净结果，但也说明一件事：**光看 `ata1`/`nvme` 这类关键词会误报**，同一个日志里 `ata1.00: ATA-8: Ubuntu 24.04-0 SSD, ... 134217728 sectors` 这种枚举行一大把，那是正常的开机识别记录（实测可见），不是故障。`medium error`、`Unrecovered read error`、`task abort`、`resetting link` 这几类才要当真，它们通常意味着盘要换了。

顺带一条虚拟化环境的诚实提醒：`/sys/block/sda/device/model` 实测打印 `Ubuntu 24.04-0 S`，这是 Parallels 给虚拟盘编的型号串，不是真实 SSD 型号。虚拟机里的 SMART、磨损、重映射扇区大多由宿主机模拟或干脆没有，**云上判磁盘健康要看云厂商的块存储事件与监控，`smartctl` 这条路在虚拟盘上经常是空的**。

### 0.10.8.1 磁盘配额：quota、xfs_quota 与 project quota {#sec-0.10.8.1}

多用户或多租户机器上，「磁盘满了」常常不是整块盘满，而是某个用户或某个项目写爆了自己的配额。[0.10.4](ch10.md#sec-0.10.4) 那条「写失败先跑 `df -h` 和 `df -i`」还有第三分支：两条都不高却仍写不进去，报错文本换成 `Disk quota exceeded`。

**这台机器上配额是关着的**，三条免特权证据（Ubuntu 实测）：

```bash
findmnt -no TARGET,FSTYPE,OPTIONS | grep -E 'usrquota|grpquota|prjquota'
command -v quota repquota xfs_quota
findmnt -no OPTIONS /
```

```text
rw,relatime
```

第一行什么都没打印（`grep` 退出码 1）：39 个挂载点里没有任何一个带配额选项。第二行同样空——`quota`、`repquota`、`xfs_quota` 三个命令都没装。第三行是根文件系统的挂载选项，只有 `rw,relatime`。配额是**挂载时才决定的**（选项写进 fstab 或 `mount -o`），后装工具、后跑命令都开不了它，所以下面整套配额命令在本机属「要 root 且需要装 quota/xfsprogs 才能跑的清单，未在本书环境复现」。

::: def 定义 0.10.8 · 配额三主体与两个限值 {#def-0.10.8}
**磁盘配额**（disk quota，按主体限制某个文件系统上的用量）有三个要素。主体：**用户**（user，按 UID 统计他拥有的全部文件）、**组**（group，按 GID）、**项目**（project，按打在目录树上的 project ID，与 UID 无关）。限值：**软限**（soft limit，超过只警告，并开始倒数**宽限期**（grace time，默认 7 天）；宽限期用完，软限就当作硬限把写入锁住）与**硬限**（hard limit，绝对不能超过，超了立刻 `EDQUOT`）。统计单位有两个，各自独立：**块数**（容量）与 **inode 数**（文件个数）——[0.10.4](ch10.md#sec-0.10.4) 那两个计数器在配额这一层又出现一次，只不过这次是按主体分别计数。
:::

按鸟哥第 14 章的口径，还有三条使用限制值得记：配额只对普通用户有意义，root 通常不受限（它是来管别人的）；核心必须带 quota 支持（发行版内核默认带）；EXT 家族只能针对整个文件系统（也就是挂载点）设限，XFS 才能用 project 模式对单个目录设限——这正是容器场景偏爱 XFS project quota 的原因。

配额统计的是**分配块**，不是「文件大小」：稀疏文件按实际占的块算（[0.10.3](ch10.md#sec-0.10.3) 的 `stat -c '%s %b'` 口径直接搬过来用）。`df` 也永远看不到配额，它报的是整个文件系统；看配额要用 `quota`/`repquota`/`xfs_quota report`。

查看与设置的对应关系（清单，未实测）：

```bash
quota -u alice            # 看某个用户的用量与剩余宽限期
repquota -a               # 整个文件系统所有用户的报表
edquota -u alice          # 交互式编辑软硬限与宽限期，适合单个人
setquota -u alice 512000 614400 1000 1200 /home   # 批量：块软硬限、inode 软硬限
```

`setquota` 那四个数字的单位是坑：块以 1 KiB 计，所以 `512000 614400` 是软限 500 MiB、硬限 600 MiB；inode 那两位是个数（1000 与 1200）。新版 quota 工具接受 `K/M/G` 后缀，写完用 `quota -u alice` 复核一次再收工。XFS 那一侧的命令形态完全不同，见下一小节。

ext4 的启用比 XFS 多两步，因为它的配额账本是文件系统里的**普通文件**（`aquota.user`、`aquota.group`），得先扫盘生成再打开；XFS 的配额账本在文件系统内部元数据里，不用也不能手工碰。这一条区别决定了下一小节两套流程为什么长度不一样。

### 0.10.8.2 配额的三种口径与 `EDQUOT`

配额不是「一块盘的总量」，而是「某个主体在某个文件系统上的用量上限」。三种主体的统计口径不同，选错就会限不到真正想限的人：

| 主体 | ext4 挂载选项 | XFS 挂载选项 | 统计对象 | 典型场景 |
|:--|:--|:--|:--|:--|
| 用户 | `usrquota` | `uquota` | 该 UID 拥有的全部文件 | 多用户登录机、共享家目录 |
| 组 | `grpquota` | `gquota` | 该 GID 拥有的全部文件 | 项目组共享目录 |
| 项目 | `prjquota`（4.5+） | `prjquota` | 打了 project ID 的目录树 | 容器、租户、单目录限额 |

这张表的读法是「先选主体，再抄对应的挂载选项」。两个硬约束：XFS 的 `prjquota` 与 `gquota` 不能同时启用，要按目录限就得放弃组配额；ext4 从 Linux 4.5 起也支持 project quota（旧盘要先用 `tune2fs -O project,quota` 打开特性位并离线 `e2fsck -f`），但打 ID 与报表的命令和 XFS 那一套不通用，照抄会报 `Operation not supported`。Btrfs 的 `qgroup` 是另一套模型，不在本章范围。

**这些选项必须出现在挂载那一刻**——回到 [0.10.5](ch10.md#sec-0.10.5) 的结论：`findmnt` 的 `OPTIONS` 才是事实。本机实测那一列里一个配额选项都没有，所以这台机器上现在根本不存在配额这回事。

ext4 的启用流程（需 root + 装 quota 包，本书环境未实测）：

```bash
# 1. fstab 加选项，重新挂载
# /dev/vgdata/lvhome /home ext4 defaults,usrquota,grpquota 0 2
sudo mount -o remount /home

# 2. 扫描并生成 aquota.user / aquota.group；-m 表示不尝试 remount 只读
sudo quotacheck -ugm /home

# 3. 打开配额
sudo quotaon -ug /home
quotaon -p /home            # 查看状态

# 4. 设置：块单位是 1K block，inode 单位是个数
sudo setquota -u alice 512000 614400 1000 1200 /home
sudo edquota -t             # 全局宽限期，默认 7 天
sudo repquota -a            # 报表
```

第 1 步那个 `remount` 对 ext4 的配额选项是可行的，但 `usrquota` 这类选项到底能不能改要看文件系统；XFS 就完全不行——它的配额在挂载时定死，只能卸载重挂。`quotacheck` 会遍历整个文件系统重新记账，大目录盘上很慢，且要求文件系统处于安全状态（一般建议只读或卸载后再跑）；`quotaon -p` 是唯一一条免特权也能试的状态查询，但它同样需要能读到配额文件，所以本机没装包时直接 `command not found`。

XFS 侧的完整流程（需 root + XFS 文件系统，本机内核没有 XFS、工具也没装，未实测）：

```bash
# /dev/vgdata/lvhome /home xfs defaults,uquota,gquota 0 0
sudo umount /home && sudo mount /home
sudo xfs_quota -x -c 'state' /home
sudo xfs_quota -x -c 'report -ubih' /home
sudo xfs_quota -x -c 'limit -u bsoft=500m bhard=600m alice' /home
sudo xfs_quota -x -c 'timer -u -b 14days' /home
```

`report` 的 `-u/-g/-p` 选主体，`-b/-i/-h` 选块/inode/人类可读；`state` 打印三种主体的开关状态与宽限期。注意 XFS 这里**没有 `quotacheck`/`quotaon` 两步**：配额随挂载生效，账本一直在文件系统里更新。

project quota 的关键是「给目录树打 ID」，与用户无关（未实测）：

```bash
# 假设 /srv 是启用了 prjquota 的 XFS 挂载点
sudo mkdir -p /srv/app
# 42 是任意未使用的 project ID；-s 让该目录下新建文件继承这个 ID
sudo xfs_quota -x -c 'project -s -p /srv/app 42' /srv
sudo xfs_quota -x -c 'limit -p bhard=20g 42' /srv
sudo xfs_quota -x -c 'report -p -h' /srv
```

`project -s` 递归给现有文件打 ID，之后新建的文件靠目录的继承标志自动带上。容器运行时限制「单个容器能写多少宿主盘」用的就是这套：给 overlay 的上层目录打一个 project ID，再给这个 ID 设硬限，一个失控的容器就写不爆宿主机的根文件系统（第 5 篇会回到这条线）。

ext4 的 project quota 走另一套命令：`sudo chattr -p 42 -R /srv/app` 打 ID、`sudo chattr +P /srv/app` 设继承、`sudo repquota -P /srv` 看报表；旧盘要先 `tune2fs -O project,quota` 再离线 `e2fsck -f`，挂载选项写 `prjquota`。ID 与继承这两个动作合起来才等效于 XFS 的一句 `project -s`，两套工具不通用。

最后一层是**给应用看的**：配额超限时 `write()` 返回的 errno 是 `EDQUOT`（122），而块满/inode 满是 `ENOSPC`（28），[0.10.4](ch10.md#sec-0.10.4) 那两个「看起来一样」的错误在这里又多了一个兄弟。只判 `ENOSPC` 的程序会把配额超限报成「磁盘空间不足」，把用户推向根本不存在的大盘。写文件的循环还要处理「写到一半失败」：短写或 `EDQUOT` 时已经写下去的部分照样占配额，回滚得显式 `ftruncate`，不能指望失败自动撤销。

::: ex 例 0.10.8 · `df` 明明还有 80% 空 {#ex-0.10.8}
用户上传文件失败，程序回「磁盘空间不足」。运维一查：`df -h /home` 报 `Use% 18%`，`df -i /home` 报 `IUse% 6%`。**先猜**下一步该跑什么，再说明为什么 `df` 那两个数是对的却完全没用。

::: sol 解答
下一步跑 `quota -u`（看自己的用量、软硬限和剩余宽限期），或 root 跑 `repquota -a` / `xfs_quota -x -c 'report -uh' /home`（看全体）。`df` 报的是**整个文件系统**的块与 inode 用量，配额是**按主体**的独立账本，两者不在一个口径上，文件系统远没满也不影响某个人先到自己的顶。这里报错文本其实是 `Disk quota exceeded`（`EDQUOT`），若已经过了宽限期，软限会当作硬限使用，用户即使没到 hard 也会被锁住——`quota -u` 输出里那个 grace 时间就是判据。以上是形状示例，本书环境没有启用配额，未在本书环境复现。
:::
:::

::: errata 常见错误清单（0.10.8 节）
1. **「Swap 用了 0 B 说明 swap 没配好」**——内存有余量时内核就是不换页；`free -h` 的 `available` 还很高而 swap 全空是正常状态，反过来 swap 持续增长才是内存压力已经上来了。
2. **「`mkswap` 完就有交换区了」**——`mkswap` 只写签名，要 `swapon` 才启用；开机自动启用得写进 fstab（`/swap.img none swap sw 0 0` 那行的位置就是 [0.10.5](ch10.md#sec-0.10.5) 的六字段）。
3. **「swap 文件权限无所谓」**——本机实测 `/swap.img` 是 `-rw------- root`；交换页里可能有密码与密钥明文，可读就等于让别人读你的内存。
4. **「`swapoff` 只是关掉一个开关」**——它要把这块 swap 上的每一页换回内存，内存不足时会直接把进程打死，先 `free -h` 看余量。
5. **「`fstrim` 报 trimmed 37 GiB 是释放了 37 GiB」**——那是告知给盘的连续空闲区大小，这些块本来在文件系统账上就是空的（对照 0.10.3 的 `stat -f`）。
6. **「`mount -o discard` 比定期 `fstrim` 好」**——每次删除同步发 TRIM 会拉高延迟；Ubuntu 默认用每周的 `fstrim.timer` 批量做，实测 `ExecStart` 还带 `--quiet-unsupported`。
7. **「配额超限就是磁盘满」**——errno 不同：`EDQUOT` 与 `ENOSPC`；`df` 也看不见配额，要看 `quota`/`repquota`/`xfs_quota report`。
8. **「配额可以先挂载后打开」**——XFS 完全不行，ext4 也要 `usrquota` 之类选项出现在挂载表里才算；`findmnt -no OPTIONS /` 实测只有 `rw,relatime`，说明本机不存在配额。
9. **「虚拟盘也能读到 SMART」**——`/sys/block/sda/device/model` 实测是 `Ubuntu 24.04-0 S`，这是虚拟型号串；`smartctl` 本机也未安装，云上要看块存储事件与监控。
:::

### 0.10.8 小结

swap 是内存的溢出区、不属于任何文件系统，本机实测 4 GiB 交换文件用量为 0，那是内存有余量而不是坏；TRIM 走的是「告知盘哪些块不再用」，Ubuntu 用每周 `fstrim.timer` 批量发，journal 里能读到上次真实告知的 37.4 GiB；配额是第三种「写不进去」，按用户/组/项目分别记块与 inode，软硬限加宽限期，报错是 `EDQUOT` 不是 `ENOSPC`；盘的寿命要靠 SMART 或内核日志，`dmesg` 被拒时用 `journalctl -k`。如果只记住一件事，那就是：**`df` 只回答「整块文件系统」，配额、swap、TRIM 说的都不是这件事**，判据要各自找各自的命令。

::: method 即时自测 · 0.10.8
**Q1（记忆）** 配额的两个限值与两种统计单位分别是什么？写出 ext4 与 XFS 各自的挂载选项名。

**Q2（辨析）** `swapon --show` 显示 `USED 0B`、`free -h` 的 Swap 行也全 0。这是故障吗？和「系统正在 OOM」有什么关系？

::: sol 答案
**A1** 软限（超过只警告并倒宽限期，默认 7 天）与硬限（绝对不超过，超了立刻 `EDQUOT`）；统计单位是块数（容量）与 inode 数（文件个数），两者各自限制。ext4 用 `usrquota`/`grpquota`/`prjquota`，XFS 用 `uquota`/`gquota`/`prjquota`，且 XFS 的 `prjquota` 与 `gquota` 互斥。

## 0.10.9 分区表、对齐与 `fdisk`/`sgdisk`/`parted` {#sec-0.10.9}

这一节回答：MBR 与 GPT 该选哪个？「分区对齐」到底对到什么上？三个分区工具各自擅长什么场景？

::: preview 先抓住一件事
对齐不是玄学：SSD 的擦除块、RAID 的条带都远大于 512 字节，起始扇区落在 1 MiB 边界（扇区 2048）就是让文件系统的块不要横跨两个物理单元。
:::

分区表决定「这块盘怎么切」，文件系统只看见自己所在的分区。分区表坏了，文件系统再健康也挂不上；分区起止没对齐，性能会莫名其妙掉一截。

| 特性 | MBR（DOS） | GPT |
|:--|:--|:--|
| 分区表位置 | 0 号扇区（512 B），含引导代码 | LBA 1 起，含 128 个表项；末尾有备份 |
| 最大磁盘 | 2 TiB（512 B 扇区） | 8 ZiB |
| 主分区数 | 4 个，或 3 主 + 1 扩展 | 128 个（可更多） |
| 分区 ID | 1 字节类型码 | 16 字节 GUID 类型 |
| 完整性 | 无校验 | 头部 CRC32，主备互校 |
| 引导 | BIOS + boot flag | UEFI 需要 ESP（EF00） |

MBR 的 2 TiB 限制来自「32 位 LBA × 512 B 扇区」。4Kn 盘（逻辑扇区 4096 B）上 MBR 能到 16 TiB，但兼容性更差。新盘一律 GPT；只有在给老 BIOS 机器装系统、或对接只认 MBR 的硬件阵列时才用 MBR。

分区工具的选择：

| 工具 | 风格 | 适合 | 常用命令 |
|:--|:--|:--|:--|
| `fdisk` | 交互式，MBR/GPT 都支持 | 手工探索、救急 | `g`、`n`、`p`、`t`、`w` |
| `gdisk`/`sgdisk` | GPT 专用，脚本友好 | GPT 修复、批量建分区 | `sgdisk -n 1:1MiB:+512M` |
| `parted` | 交互/脚本，支持 resizepart | 一次性建表、查看对齐 | `parted -s /dev/X mklabel gpt` |
| `sfdisk` | 脚本化，可导出/导入 | 批量复制分区表 | `sfdisk -d /dev/sda \| sfdisk /dev/sdb` |

新建 GPT 并建一个分区，用 `sgdisk` 最不容易误操作：

```bash
sudo sgdisk --zap-all /dev/loop0
sudo sgdisk --new=1:1MiB:+512M --typecode=1:8300 --change-name=1:data /dev/loop0
sudo sgdisk --print /dev/loop0
sudo partx -u /dev/loop0        # 让内核重读分区表
lsblk -o NAME,SIZE,TYPE,PARTTYPENAME,PARTUUID /dev/loop0
```

`--new=1:1MiB:+512M` 的起点写 `1MiB` 而不是 `2048`，让工具按实际扇区大小换算；`8300` 是通用 Linux 文件系统，`8309` 是 Linux LUKS，`8e00` 是 Linux LVM，别把加密或逻辑卷的类型码当数据分区用。`partx -u` 只更新指定设备的分区，`partprobe` 会扫描全部设备；两者都不如「卸载后重读」可靠，根盘分区表变更需要重启。

`parted` 的对齐检查是少数能直接告诉你「有没有对齐」的命令：

```bash
sudo parted -s /dev/loop0 mklabel gpt
sudo parted -s /dev/loop0 mkpart data ext4 1MiB 100%
sudo parted /dev/loop0 align-check optimal 1
sudo parted -l
```

`align-check optimal 1` 输出 `1 aligned` 才算通过。现代工具默认从 1 MiB 起，是为了避开 MBR 与 GPT 头部、并匹配绝大多数 SSD/RAID 的条带；老教程里从 63 扇区起的写法会让每次读写跨两个物理页。

4Kn 盘要额外确认逻辑/物理扇区：

```bash
blockdev --getss /dev/nvme0n1     # 逻辑扇区，通常 512 或 4096
blockdev --getpbsz /dev/nvme0n1   # 物理扇区，通常 4096
lsblk -o NAME,LOG-SEC,PHY-SEC,OPT-IO /dev/nvme0n1
```

`OPT-IO` 是 `optimal_io_size`，RAID 卡或 SSD 会给出建议的 I/O 大小。分区起点与文件系统条带参数（`mkfs.ext4 -E stride=,stripe_width=`）应尽量与它对齐；不对齐不会报错，只会让写放大。

分区表也有备份。GPT 的备份头在磁盘最后一个 LBA，`sgdisk --backup=table.bin /dev/sda` 会把主备两份都存下来，`--load-backup=table.bin /dev/sdb` 可以原样恢复到同容量的盘。恢复前先 `sgdisk --verify`；容量不同的盘恢复后要 `--move-second-header` 把备份头挪到新盘的末尾。

### 0.10.9 小结

分区表层面记三条：MBR 有 4 个主分区与 2 TiB 上限，GPT 有 128 个表项、盘尾还有一份备份与 CRC；对齐看起始扇区是不是 2048 的倍数（1 MiB）；工具上 `fdisk` 交互式改 MBR/GPT 都行，`sgdisk` 适合脚本，`parted` 能顺手建文件系统但要小心它会立刻写盘。如果只记住一件事，那就是**先 `sgdisk -p` 看清现状再动手**。

## 0.10.10 `mkfs` 参数与挂载选项 {#sec-0.10.10}

这一节回答：`mkfs` 的哪些参数建完就改不了？挂载选项里哪几个会悄悄影响性能或数据安全？

::: preview 先抓住一件事
块大小、inode 密度、XFS 的扇区大小都是**建的时候定终身**；而 `noatime`、`discard`、`commit=` 这些是挂载时的旋钮，改起来只要重挂一次。
:::

`mkfs.ext4` 与 `mkfs.xfs` 的默认值适合通用场景，但有几项一旦定下就不能改，必须在创建时想清楚。

| 参数 | ext4 | XFS | 定型后能否改 |
|:--|:--|:--|:--|
| 块大小 | `-b 1024/2048/4096` | `-b size=4096` | 不能 |
| inode 大小 | `-I 256`（默认） | 固定，随 CRC 变化 | 不能 |
| inode 数量 | `-N 个数` 或 `-i 字节/ino` | 动态分配，`-i maxpct=` | ext4 只能扩容时增加 |
| 日志 | `-J size=` | `-l size=` | ext4 可 `tune2fs -J`，XFS 不能 |
| 卷标/UUID | `-L` / `-U` | `-L` / `-U` | 可以（`tune2fs`/`xfs_admin`） |
| 预留块 | `-m 百分比` | 无此概念 | 可以 |
| 条带 | `-E stride=,stripe_width=` | `-d su=,sw=` | 不能 |

ext4 的 `-m` 预留块是给 root 的应急空间，默认 5%。数据盘可以降到 1%，根盘保留 5%；降到 0 会让「磁盘满后 root 也登录不了、日志也写不进」的故障直接发生。

`-E stride/stripe_width` 要按 RAID 的 chunk 与数据盘数算：`stride = chunk / block_size`，`stripe_width = stride × 数据盘数`。算错不会损坏数据，但会让文件系统按错误的条带写，RAID5 的小写惩罚更明显。

```bash
# 4 块盘 RAID5，chunk 64K，块大小 4K
# stride = 64K/4K = 16；stripe_width = 16 * 3 = 48
sudo mkfs.ext4 -b 4096 -E stride=16,stripe_width=48 /dev/md0

# XFS 用 su/sw（条带单元/条带宽度，单位字节）
sudo mkfs.xfs -d su=64k,sw=3 /dev/md0
```

XFS 的 `-i maxpct=` 控制 inode 最多占文件系统空间的百分比，默认 25%。小文件极多的场景可以调大，但 inode 本身也占空间；用 `xfs_info` 看 `imaxpct` 与 `agcount`。

创建后立即核对：

```bash
sudo dumpe2fs -h /dev/vgdata/lvdata | grep -E 'Block count|Block size|Inode count|Inode size|Reserved block count|Filesystem UUID'
sudo xfs_info /mnt/data
sudo tune2fs -l /dev/vgdata/lvdata | grep -E 'Filesystem state|Last checked|Mount count'
```

`dumpe2fs -h` 只读超级块，不扫全盘，秒回；不带 `-h` 会打印每个 block group，慢且长。`xfs_info` 的参数是**挂载点**，不是设备名；对未挂载的 XFS 用 `xfs_db -r -c 'info' /dev/...`。

挂载选项分四类，记不住就查 `man 5 mount` 与 `man 5 ext4`：

| 类别 | 选项 | 作用 | 风险 |
|:--|:--|:--|:--|
| 权限 | `ro`、`rw`、`nosuid`、`nodev`、`noexec` | 限制挂载点能力 | `noexec` 会让脚本/解释器无法执行 |
| 时间 | `atime`、`noatime`、`relatime`、`lazytime` | 控制访问时间更新 | `noatime` 影响依赖 atime 的备份/邮件 |
| 可靠性 | `sync`、`async`、`errors=remount-ro`、`data=ordered` | 写回与出错策略 | `sync` 极慢；`data=writeback` 崩溃后可能读到旧数据 |
| 性能 | `discard`、`commit=N`、`nobarrier` | TRIM、提交间隔、屏障 | 关屏障可能丢数据 |

`defaults` 不是「默认最优」，它展开成 `rw,suid,dev,exec,auto,nouser,async`。`/tmp` 应该用 `nosuid,nodev,noexec`；`/boot` 可以 `ro`；网络盘加 `_netdev` 和 `nofail`，否则网络没起来时开机卡住甚至进 emergency。

`/etc/fstab` 的六个字段：

| 字段 | 内容 | 例子 | 注意 |
|:--|:--|:--|:--|
| 1 | 设备 | `UUID=...`、`LABEL=...`、`/dev/vg/lv` | 优先 UUID |
| 2 | 挂载点 | `/data` | 路径不能有空格（可用 `\040`） |
| 3 | 类型 | `ext4`、`xfs`、`swap` | 写错会挂载失败 |
| 4 | 选项 | `defaults,nofail` | 逗号分隔，不能有空格 |
| 5 | dump | `0` | 现代系统不用 |
| 6 | fsck 顺序 | `0`、`1`、`2` | 根为 1，其他为 2，不检查为 0 |

改完 fstab 必须验证，不要等重启：

```bash
sudo findmnt --verify --verbose
sudo mount -a -v
sudo systemctl daemon-reload     # 让 systemd 重新生成 .mount 单元
```

`findmnt --verify` 会检查设备是否存在、挂载点是否重复、选项是否被识别；`mount -a` 会真正挂载所有 `auto` 条目。`nofail` 让挂载失败不阻塞开机，`x-systemd.device-timeout=10s` 限制等待设备的时间；这两个一起用，才能避免「一块数据盘掉了，整台机器起不来」。

### 0.10.10 小结

先分清「定型项」与「可调项」：块大小、inode 比例、XFS 的扇区大小属于前者，选错只能重建；预留块比例、卷标、挂载选项属于后者。挂载选项里最常改的三个是 `noatime`（省一次写）、`discard` 与 `fstrim`（TRIM 的两种做法，后者更可控）、`commit=N`（提交间隔，越小越安全越慢）。如果只记住一件事，那就是**先在纸上决定块大小与 inode 密度，再敲 `mkfs`**。

## 0.10.11 `fsck`、`xfs_repair` 与超级块救援 {#sec-0.10.11}

这一节回答：`e2fsck` 的退出码为什么是位掩码？修之前必须先做哪两件事？主超级块坏了怎么救？

::: preview 先抓住一件事
`fsck` 不是「修得越多越好」：先 `-n` 只读检查，再看退出码决定下一步——**退出码 4 与 8 是「还没修」和「修不了」，不是成功**。
:::

文件系统不一致的来源只有三类：非正常断电/崩溃、硬件写缓存丢数据、内核或驱动 bug。`fsck` 系列工具把元数据读出来交叉验证，能修就修，不能修就隔离。

ext4 的 `e2fsck` 分五个阶段：inode、目录结构、目录连通性、引用计数、组摘要。退出码是**位掩码**，不是简单的 0/1：

| 退出码 | 含义 | 处理 |
|--:|:--|:--|
| 0 | 无错误 | 正常 |
| 1 | 已修正错误 | 可继续启动，检查日志 |
| 2 | 已修正，需重启 | 重启后再查 |
| 4 | 有未修正错误 | 必须人工介入，别挂载写入 |
| 8 | 操作错误 | 参数/设备问题 |
| 16 | 用法错误 | 看 man |
| 32 | 被取消 | 用户中断 |
| 128 | 共享库错误 | 环境问题 |

常用选项：

| 选项 | 作用 | 场景 |
|:--|:--|:--|
| `-p` | preen，自动修「安全」的问题 | 开机 `systemd-fsck` 默认 |
| `-n` | 只检查，回答全部 no | 只读诊断，绝不改 |
| `-y` | 回答全部 yes | 已确认要修，慎用 |
| `-f` | 强制检查，即使标记 clean | 怀疑元数据损坏 |
| `-b 32768` | 用备份超级块 | 主超级块损坏 |
| `-B 4096` | 指定块大小 | 配合 `-b` |
| `-D` | 优化目录索引 | 大目录性能 |
| `-c` | 用 badblocks 扫坏块 | 怀疑盘坏 |

主超级块在块组 0，备份超级块在 32768、98304 等位置（4K 块）。主超级块损坏时，`e2fsck` 会报 `Bad magic number in super-block`，此时先不要 `mkfs`：

```bash
sudo mke2fs -n /dev/loop0          # -n 只打印布局，不写盘
# 输出会列出 Backup superblock at 32768, 98304, ...
sudo e2fsck -f -b 32768 -B 4096 /dev/loop0
sudo mount -o ro /dev/loop0 /mnt/rescue
```

`mke2fs -n` 的关键是 `-n`：没有它就会真的格式化。`-b 32768` 告诉 `e2fsck` 用哪个备份块，`-B 4096` 告诉它块大小；两者不匹配会报 `Attempt to read block from filesystem resulted in short read`。

XFS 没有「备份超级块」的概念，元数据分布在各 AG（allocation group），修复工具是 `xfs_repair`：

```bash
sudo umount /data
sudo xfs_repair -n /dev/vgdata/lvdata     # 只检查，不写
sudo xfs_repair -v /dev/vgdata/lvdata     # 实际修复
```

`xfs_repair -n` 可能很慢，但它是唯一安全的预检。`xfs_repair -L` 会清空日志，只在日志本身损坏、且你接受「丢失最近未落盘事务」时使用；它不能和 `-n` 一起用。

如果 XFS 因为日志脏而挂不上，可以先只读挂载、不重放日志：

```bash
sudo mount -o ro,norecovery /dev/vgdata/lvdata /mnt/rescue
```

`norecovery` 让 XFS 跳过日志重放，可能看到不一致的元数据，只用来拷数据。ext4 对应的是 `noload`，语义类似，同样只用于救援。

`fsck` 绝不能对已读写挂载的文件系统执行。e2fsck 会拒绝，xfs_repair 会直接报 `device or resource busy`；如果强行 `-f`，坏的是正在使用的数据。正确顺序永远是：`umount` → `fsck` → `mount`。根文件系统只能在启动时由 initramfs 检查，或进 rescue target 后卸载检查。

开机自动检查由 `systemd-fsck@.service` 按 fstab 第 6 字段驱动。想强制下次开机检查，不要再 `touch /forcefsck`（systemd 已不识别），用内核参数：

```bash
# GRUB 启动项临时加：fsck.mode=force fsck.repair=yes
sudo tune2fs -c 1 /dev/vgdata/lvdata   # ext4：挂载计数到 1 就检查
```

`tune2fs -c 1` 对 XFS 无效；XFS 用 `xfs_admin` 没有等价开关，靠 `fsck.mode=force` 或定期离线 `xfs_repair -n`。

### 0.10.11 小结

`e2fsck` 的五阶段（inode、目录结构、连通性、引用计数、组摘要）决定它会花多久；退出码是位掩码：1 已修、2 需重启、4 未修、8 操作错误、16 用法错——**1 和 4 的处理完全相反**。XFS 用 `xfs_repair`，`-n` 只检查；ext4 主超级块坏了就用 `mke2fs -n` 打印的备份块号配 `e2fsck -b` 恢复。如果只记住一件事，那就是**先卸载或只读挂载，再 `-n` 跑一遍**。

### 0.10.12.1 块设备全景图

### 0.10.12.1 块设备全景图

排障第一步不是 `df`，是把「盘—分区—RAID/LVM—文件系统—挂载点」这条链一次打出来：

```bash
#!/usr/bin/env bash
# blk-map.sh —— 只读：块设备、LVM、RAID、挂载、用量
set -euo pipefail
export LC_ALL=C

echo "== block devices"
lsblk -o NAME,SIZE,TYPE,FSTYPE,FSVER,LABEL,UUID,MOUNTPOINTS,ROTA,TRAN

echo "== mounts (real only)"
findmnt --real -o TARGET,SOURCE,FSTYPE,OPTIONS

echo "== usage"
df -hT -x tmpfs -x devtmpfs
df -i  -x tmpfs -x devtmpfs

if command -v pvs >/dev/null; then
    echo "== LVM"; pvs; vgs; lvs -o +devices
fi
if [[ -r /proc/mdstat ]]; then
    echo "== md"; cat /proc/mdstat
    command -v mdadm >/dev/null && mdadm --detail --scan
fi
```

真跑一段（Ubuntu 实测，节选）：

```text
== block devices
NAME     SIZE TYPE FSTYPE   MOUNTPOINTS
loop0      4K loop squashfs /snap/bare/5
sda       64G disk
|-sda1     1G part vfat     /boot/efi
`-sda2  62.9G part ext4     /
sr0     1024M rom
== mounts (real only)
TARGET  SOURCE    FSTYPE OPTIONS
/       /dev/sda2 ext4   rw,relatime
```

看两处：`lsblk` 的树形缩进（`|-`、`` `- ``）把「盘 → 分区 → 挂载点」画在一屏里；`findmnt --real` 把 `proc`、`sysfs`、`tmpfs` 全部滤掉，只剩真正落在块设备上的挂载。排障时先跑这两条，比 `df -h` 有用得多。

`lsblk` 的 `MOUNTPOINTS` 可能有多行（同一设备 bind mount 多次），脚本里不要假设一行一个设备。`findmnt --real` 过滤伪文件系统，`--list` 或 `-J` 更适合程序解析。`df -i` 必须和 `df -h` 一起看：空间够但 inode 尽，是两种完全不同的故障。

### 0.10.12.2 容量与错误哨兵

这个脚本按阈值检查空间、inode、只读挂载和内核 I/O 错误，返回非 0 表示「有人该看一眼」：

```bash
#!/usr/bin/env bash
# fs-guard.sh [空间阈值%] [inode阈值%]
set -euo pipefail
sp=${1:-85}; ip=${2:-90}; bad=0

while read -r fs size used avail pct mnt; do
    [[ $fs == Filesystem ]] && continue
    p=${pct%\%}
    if (( p >= sp )); then
        echo "SPACE $pct $mnt ($used/$size)"; bad=1
    fi
done < <(df -PT -x tmpfs -x devtmpfs)

while read -r fs inodes iused ifree ipct mnt; do
    [[ $fs == Filesystem ]] && continue
    p=${ipct%\%}
    if (( p >= ip )); then
        echo "INODE $ipct $mnt ($iused/$inodes)"; bad=1
    fi
done < <(df -Pi -x tmpfs -x devtmpfs)

# 只读挂载：可能是 fsck 失败后 systemd 自动 remount-ro
findmnt --real -no TARGET,OPTIONS | awk '$2 ~ /(^|,)ro(,|$)/ {print "READONLY " $1}'

# 内核 I/O 与文件系统错误（需要 root 才能看全部）
dmesg -T --level=err,warn 2>/dev/null |
    grep -iE 'I/O error|medium error|EXT4-fs error|XFS.*corrupt|remounting filesystem read-only' |
    tail -20 || true

exit "$bad"
```

真跑一次（Ubuntu 实测），它暴露了脚本自身的一个 bug：

```text
SPACE 37675460 39% / (64653932/ext4)
SPACE 1092112 1% /boot/efi (1098628/vfat)
SPACE 335302508 83% /media/psf/Home (1948404040/fuse.prl_fsd)
```

第三行那个 `fuse.prl_fsd`（Parallels 共享目录）在 `df -Pi` 里 inode 列全是 `-`，`p=${ipct%\%}` 得到 `-`，再送进 `(( p >= ip ))` 就是语法错误。**修法是在循环里加一行 `[[ $ipct == "-" ]] && continue`**——「这个文件系统不报 inode」和「inode 用满了」是两件事。

`df -P` 保证 POSIX 单行输出，避免长设备名折行；`-T` 加类型列。阈值用参数传入，方便在监控系统里按机器角色调整。只读挂载那一行只打印不置 `bad`，因为 `/` 之外的只读挂载可能是故意的；要让只读也告警，把它改成 `bad=1`。

### 0.10.12.3 带护栏的 `mkfs`

`mkfs` 的危险不在命令本身，而在「设备名敲错一个字母」。让脚本在写之前把证据摆出来，并要求输入设备名确认：

```bash
#!/usr/bin/env bash
# safe-mkfs.sh /dev/loopX ext4 LABEL
set -euo pipefail
dev=${1:?device}; fs=${2:?ext4|xfs}; label=${3:-lab}

[[ -b $dev ]] || { echo "not a block device: $dev" >&2; exit 2; }
if findmnt -S "$dev" >/dev/null; then
    echo "REFUSE: $dev is mounted" >&2; exit 3
fi
if [[ $(lsblk -no TYPE "$dev") == disk ]] && lsblk -no NAME "$dev" | tail -n +2 | grep -q .; then
    echo "REFUSE: $dev has partitions; pass a partition, not the whole disk" >&2; exit 4
fi

echo "== target"; lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS "$dev"
echo "== signatures"; sudo wipefs -n "$dev" || true
read -r -p "type the device path to continue: " answer
[[ $answer == "$dev" ]] || { echo "aborted" >&2; exit 5; }

case $fs in
    ext4) sudo mkfs.ext4 -L "$label" -m 1 "$dev" ;;
    xfs)  sudo mkfs.xfs  -L "$label" -f "$dev" ;;
    *) echo "unsupported fs: $fs" >&2; exit 2 ;;
esac
```

**这一段没有在本书环境真跑**：`wipefs`/`mkfs` 需要一个可以被覆盖的设备，而 VM 上没有空闲盘、`sudo` 又不可用（`sudo` 需密码）。要自己验，就插一块**已知可以清空的** U 盘或新建 loop 设备，先 `wipefs -n "$dev"` 看签名，再按脚本提示输入设备名确认。

`wipefs -n` 只列出签名不删除；看到 `LVM2_member`、`linux_raid_member`、`ext4` 时应该停下来查归属，而不是继续。`lsblk -no TYPE` 为 `disk` 且有子分区时拒绝，是为了防止把整盘当分区格式化。

### 0.10.12 小结

三个脚本的分工：全景图**只读**、用来看清结构；哨兵**只读**、用退出码说话；`mkfs` 护栏**要写**、所以必须在动手前把 `wipefs -n`、`lsblk`、确认输入三件事摆出来。写的过程中还真踩到一个坑：`df -Pi` 对某些文件系统（如 Parallels 共享目录）的 inode 列是 `-`，不判空就会让算术表达式崩在循环里。如果只记住一件事，那就是**只读脚本要能容忍「字段是 `-`」，写脚本要先验目标**。

::: preview 先抓住一件事
扩容是**两层**的事：先让设备变大（分区/loop/LV），再让文件系统变大（`resize2fs`/`xfs_growfs`）。只做前一步，`df` 不会变。

### 实验一：loop 上的 ext4 扩容与超级块救援

### 实验一：loop 上的 ext4 扩容与超级块救援

```bash
lab=/var/tmp/fslab; mkdir -p "$lab"; cd "$lab"
truncate -s 256M fs.img
loop=$(sudo losetup -f --show fs.img); echo "loop=$loop"
sudo mkfs.ext4 -L lab -m 1 "$loop"
sudo mkdir -p /mnt/fslab && sudo mount "$loop" /mnt/fslab

sudo dumpe2fs -h "$loop" | grep -E 'Block count|Block size|Reserved block count'

sudo umount /mnt/fslab
sudo e2fsck -fn "$loop"; echo "e2fsck rc=$?"
sudo mke2fs -n "$loop" | grep -i 'backup superblock'
```

**本书环境没有 loop 权限**（`losetup` 需要 `CAP_SYS_ADMIN`，VM 的 `sudo` 需密码不可用），所以改用**普通文件**做同样的两层扩容——`mkfs.ext4`、`resize2fs`、`e2fsck` 都支持直接对文件操作，不需要挂载也不需要 root（Ubuntu 实测）：

```text

rc=0
$ truncate -s 512M fs.img && resize2fs fs.img
The filesystem on fs.img is now 131072 (4k) blocks long.
$ dumpe2fs -h fs.img | grep -E 'Block count|Block size'
Block count:              131072
Block size:               4096
```

三层数字对得上：文件 512 MiB ÷ 4 KiB = 131072 块。原文的 loop 路径多一步 `losetup -c`——**只 `truncate` 文件，loop 设备仍记着旧容量**，这一步才是「让设备层先变大」。挂载之后 `df` 才会从约 240M 变成约 490M（本书没挂载，故 `df` 一项未实测）。

救援演练（在副本上做，不要对刚扩好的文件系统做）：

```text
$ e2fsck -fn fs2.img
ext2fs_open2: Bad magic number in super-block
e2fsck: Superblock invalid, trying backup blocks...
$ e2fsck -b 32768 -fn fs2.img

fs2.img: 11/131072 files (0.0% non-contiguous), 12401/131072 blocks
```

两个细节：`e2fsck` 自己会**先试着找备份**（`trying backup blocks...`），但不会替你选；`-b 32768` 是明确指定块号——**备份块编号以 `mke2fs -n` 的输出为准**，32768 只适用于 4K 块、默认 inode 布局的常见配置。因为我把引导块也一起清零了，最后仍报 `still has errors`；真实救援里通常只损坏超级块那一块，修完要再跑一次 `e2fsck -fy`。

### 0.10.14.1 读 `iostat` 与 `lsblk -D` 的字段

`iostat -x` 是块层最常用的采样工具，但它的第一帧是自开机以来的累计值，直接看会得出错误结论。正确用法是 `iostat -x 1 2`，只看第二帧：

<div class="terminal" data-title="bash · Ubuntu 24.04.5 实测 · 空闲盘">
<pre><span class="p">&#36;</span> iostat -x 1 2 | awk '/^Device/{p=1} p' | tail -3
Device            r/s     rkB/s ... %util
sda              0.00      0.00 ...   0.00
<span class="p">&#36;</span> lsblk -D -o NAME,DISC-GRAN,DISC-MAX,DISC-ZERO /dev/sda
NAME   DISC-GRAN DISC-MAX DISC-ZERO
sda           4K       2G         0
├─sda1        4K       2G         0
└─sda2        4K       2G         0
</pre>
</div>

这台 VM 的盘在采样窗口里完全空闲，所以第二帧全是 0——**这本身就是一条判据**：先用空闲基线确认工具链正常，再上负载看数字怎么动。`lsblk -D` 三行说明这块 SATA 盘支持 discard（粒度 4K、单次上限 2G），但 `DISC-ZERO=0` 表示 discard 后读回的内容**不保证是零**，所以不能拿 `blkdiscard` 当清零。

| 命令/字段 | 单位 | 读法 | 陷阱 |
|:--|:--|:--|:--|
| `r/s`、`w/s` | 次/秒 | 完成的读/写请求数，不是字节数 | 小请求多不代表吞吐高 |
| `rkB/s`、`wkB/s` | KiB/秒 | 实际吞吐 | 与 `r/s` 一起算平均请求大小 |
| `r_await`、`w_await` | ms | 从提交到完成的平均延迟（含排队） | 比 `svctm` 可信；`svctm` 已废弃 |
| `aqu-sz` | 个 | 平均队列深度 | 持续 > 1 说明设备在排队 |
| `%util` | % | 设备忙时间比例 | NVMe/RAID 可并行，100% 不等于饱和 |
| `d/s`、`d_await` | 次/秒、ms | discard 请求与延迟 | 只有支持 discard 的设备才有意义 |
| `DISC-GRAN` | 字节 | 最小 discard 粒度 | 为 0 表示设备不支持 discard |
| `DISC-MAX` | 字节 | 单次 discard 最大长度 | 超过会被内核拆分 |
| `DISC-ZERO` | 0/1 | discard 是否保证读回全零 | 为 0 时不能拿 discard 当清零 |

`%util` 是最容易被误读的一列：它统计的是「设备有请求在处理的采样时间比例」，不是「带宽利用率」。一块 NVMe 在 `%util=100%` 时仍可能只跑了标称 IOPS 的一半；反过来，RAID 卡后面的多块盘可以并行，`%util` 到 100% 也不代表应用在等。判断饱和看 `aqu-sz` 与 `r_await`/`w_await` 是否随负载同步上升，再看应用侧 P99。

`lsblk -D` 的 `DISC-GRAN=0` 表示设备不支持 discard，此时 `fstrim` 会返回 `the discard operation is not supported`，不是文件系统坏了。loop 设备的 discard 能力继承自后端文件所在文件系统；在 ext4 的镜像文件上通常能看到非零粒度。

### 实验三：LVM 快照回滚一次误删

目的：在 loop 上建一个 LV，写基线数据，打快照，故意改坏，再用 `lvconvert --merge` 回到快照点。快照是块级时间点，不是备份，但它是本地误操作最快的一条回滚路径。

```bash
lab=/var/tmp/snaplab; mkdir -p "$lab"; cd "$lab"
truncate -s 1G base.img
loop=$(sudo losetup -f --show base.img)
sudo pvcreate "$loop"
sudo vgcreate vgtest "$loop"
sudo lvcreate -L 512M -n origin vgtest
sudo mkfs.ext4 -L origin /dev/vgtest/origin
sudo mkdir -p /mnt/snaplab
sudo mount /dev/vgtest/origin /mnt/snaplab
echo "version=1" | sudo tee /mnt/snaplab/data.txt
sudo mkdir -p /mnt/snaplab/important
echo "keep me" | sudo tee /mnt/snaplab/important/note.txt
sudo sync

# 打快照；COW 区要能装下快照生命周期内的所有改动
sudo lvcreate -s -L 128M -n snap /dev/vgtest/origin
sudo lvs -o lv_name,lv_attr,data_percent,size vgtest

# 模拟误操作
echo "version=2" | sudo tee /mnt/snaplab/data.txt
sudo rm -rf /mnt/snaplab/important
sudo umount /mnt/snaplab

# 回滚：先卸文件系统，再 merge；若提示 Delayed merge，按下面的说明处理
sudo umount /mnt/snaplab
sudo lvconvert --merge /dev/vgtest/snap
sudo lvchange -ay /dev/vgtest/origin 2>/dev/null || true
sudo mount /dev/vgtest/origin /mnt/snaplab
cat /mnt/snaplab/data.txt
cat /mnt/snaplab/important/note.txt
sudo lvs vgtest
```

**这一段没有在本书环境跑**：VM 上 lvm2 与 quota 工具都没装（`command -v lvs`、`command -v repquota` 均为空），安装与建 LV 又都要 root。原文的判据照用即可：merge 后 `data.txt` 是 `version=1`，`important/note.txt` 回来，`lvs` 里不再有 `snap`。

快照是**崩溃一致**，不是应用一致：数据库、虚拟机磁盘在打快照前要先停写或用 `fsfreeze`：

```bash
sudo fsfreeze --freeze /mnt/snaplab
sudo lvcreate -s -L 128M -n snap2 /dev/vgtest/origin
sudo fsfreeze --unfreeze /mnt/snaplab
```

`fsfreeze` 只保证文件系统缓存落盘并暂停新写，不保证应用自己的事务日志；数据库要用 `FLUSH TABLES WITH READ LOCK` 或备份工具自己的快照钩子。

### 实验四：ext4 配额与 `EDQUOT`

目的：给 `nobody` 设 1 MiB 硬限，写 2 MiB，观察 `dd` 在硬限处失败，并用 `repquota` 验证记账。

```bash

# 块软限 512K、硬限 1M；inode 软限 20、硬限 40（单位都是 1K block / 个）
sudo setquota -u nobody 512 1024 20 40 /mnt/quotalab
sudo runuser -u nobody -- dd if=/dev/zero of=/mnt/quotalab/fill bs=1K count=2048
echo "dd rc=$?"
sudo repquota -u /mnt/quotalab
sudo quota -u nobody
```

**同上一段，未实测**：`repquota`/`setquota` 在 VM 上都不存在，且配额要挂载选项与 root。判据照原文：`dd` 在约 1024 KiB 处报 `Disk quota exceeded`，退出码非 0；

回滚：

```bash
sudo quotaoff -ug /mnt/quotalab
sudo umount /mnt/quotalab
sudo losetup -d "$loop"
rm -rf "$lab"
```

`setquota` 的数字没有单位后缀时按 1K block 解释：`512 1024` 是 512 KiB 软限 / 1 MiB 硬限，不是 512 MiB。软限只启动宽限期（`edquota -t`，默认 7 天），硬限才立刻返回 `EDQUOT`。`quotacheck` 要在没有并发写的文件系统上跑；在忙的分区上先停应用，或离线检查。

### 块层与回滚的九个坑

| # | 现象 | 原因 | 修复/判断 |
|--:|:--|:--|:--|
| 1 | `iostat` 第一帧数值巨大 | 统计自开机以来的累计值 | `iostat -x 1 2`，只看第二帧 |
| 2 | `%util` 100% 但应用不慢 | NVMe/RAID 可并行，`%util` 不是带宽 | 看 `aqu-sz`、`await` 与应用 P99 |
| 3 | `lsblk -D` 全是 0 | 设备或后端文件系统不支持 discard | 换支持 discard 的存储；`fstrim` 报错属正常 |
| 4 | `blkdiscard` 后分区表没了 | 对整盘执行会清掉分区表 | 只对未挂载的整盘/LV 用，先 `lsblk` |
| 5 | 快照突然不可用 | COW 区写满 | 监控 `data_percent`，扩容或缩短快照寿命 |
| 6 | `lvconvert --merge` 不生效 | origin 仍打开，merge 被延迟 | `umount` + `lvchange -an`，或重启 |
| 7 | 回滚后数据库起不来 | 快照是崩溃一致，不是应用一致 | 用 `fsfreeze` 或数据库备份钩子 |
| 8 | 配额报「磁盘满」 | 应用只处理 `ENOSPC`，没处理 `EDQUOT` | 两个 errno 都判断；`repquota` 看用量 |
| 9 | `setquota 512 1024` 只给了 512 KiB/1 MiB | 单位是 1K block，不是 MiB | 写 `512M`/`1G` 后缀或换算好再传 |

第 9 条是配额实验里最常见的单位错误：`setquota` 的块参数以 1K 为单位，`512` 就是 512 KiB；`xfs_quota` 的 `bsoft=500m` 才带单位。两套工具的单位不同，照抄命令会把限额设小一千倍。

### 0.10.14 小结

三件事各有一句判据：`iostat` 只看第二帧，`%util` 不等于带宽（NVMe/RAID 能并行）；`lsblk -D` 里 `DISC-GRAN=0` 表示不支持 discard、`DISC-ZERO=0` 表示 discard 不保证读零；回滚要分清「块级快照（崩溃一致）」与「应用一致（要 `fsfreeze` 或数据库钩子）」。如果只记住一件事，那就是**先确认手里的设备支不支持，再决定用哪条命令**。

::: method 即时自测 · 0.10.14
**Q1（记忆）** 为什么 `iostat` 要看第二帧？`%util=100%` 一定能说明设备饱和吗？

**Q2（辨析）** LVM 快照与备份的本质区别是什么？回滚数据库前必须做什么？

**Q3（应用）** 一次误删之后你要「尽快回到 10 分钟前」。给出你能用的两条路径与各自的前提。

::: sol 答案
**A1** 第一帧是自开机以来的累计平均值，会把过去的空闲/繁忙混进来；第二帧才是这一秒的采样。`%util` 统计「有请求在处理的时间比例」，NVMe 与 RAID 可并行处理，100% 也可能远未到带宽上限，要结合 `aqu-sz` 与 `await`。

**A2** 快照是同一份存储上的**块级时间点**（COW 区写满就失效），备份是独立介质上的另一份数据；快照不能替代备份。回滚数据库前要停写或用 `fsfreeze`/数据库自己的 flush+lock 流程，否则拿到的是崩溃一致的磁盘，不是事务一致的数据。

**A3** ① LVM 快照：前提是卷在 LVM 上、快照还没写满、origin 能 `umount`（否则 merge 被延迟）；② 文件系统级快照（btrfs/ZFS subvolume snapshot）：前提是文件系统支持且快照还在。两者都不是备份，跨机器/跨介质的那份才是。
:::

:::
## 0.10.15 十四个磁盘与文件系统陷阱 {#sec-0.10.15}

这一节回答：磁盘与文件系统这一章，哪些操作一旦做错就回不来？每条怎么在动手前识别？

::: preview 先抓住一件事
这些坑的共同点是**不可逆**：分区表被覆盖、整盘被格式化、fstab 写错导致开不了机。凡是「写」的动作，先确认设备名与后果。
:::

| # | 现象 | 原因 | 修复/判断 |
|--:|:--|:--|:--|
| 1 | `mkfs` 后整块盘的数据没了 | 对整盘而非分区执行，或设备名错 | 用 `/dev/disk/by-id`、脚本护栏、备份 |
| 2 | 改完 fstab 开不了机 | 设备不存在/选项错，systemd 等超时 | `nofail`、`x-systemd.device-timeout=`、`findmnt --verify` |
| 3 | `mount -a` 成功，重启失败 | 启动时设备还没出现 | `_netdev`、`nofail`、UUID |
| 4 | 克隆虚拟机后 XFS 挂不上 | 两台机 UUID 相同 | `xfs_admin -U generate`、`tune2fs -U random` |
| 5 | `df` 100% 但 root 还能写 | ext4 预留块 | `tune2fs -l` 看 `Reserved block count` |
| 6 | 有空间却 `No space left` | inode 用尽 | `df -i`；删小文件或重建 `-N` |
| 7 | 删了大文件空间不释放 | 进程仍持有 fd | `lsof +L1`，重启/截断 fd |
| 8 | LVM 扩了 LV，`df` 没变 | 没扩文件系统 | `lvextend -r` 或 `resize2fs`/`xfs_growfs` |
| 9 | XFS 缩容后数据损坏 | XFS 不支持缩容 | 备份→重建→恢复 |
| 10 | LVM 快照突然失效 | 快照 COW 区写满 | 监控 `lvs` 的 `Data%`，扩快照或删旧快照 |
| 11 | RAID 重组出两个阵列 | 成员盘旧超级块没清 | `mdadm --zero-superblock` |
| 12 | `fsck` 把文件系统修得更坏 | 对已挂载/读写中的 fs 执行 | 卸载后检查；根 fs 进 rescue |
| 13 | `xfs_repair` 报设备忙 | 文件系统仍挂载 | `umount`，或 `-o ro,norecovery` 先拷数据 |
| 14 | SSD 删除后延迟升高 | `discard` 每次删除同步 TRIM | 改用 `fstrim.timer` 周期回收 |

第 11 条值得展开：`mdadm --stop` 只停阵列，不擦成员盘上的超级块。把这些盘再用于新阵列时，内核 udev 可能按旧超级块自动组装，出现「明明删了阵列，`/proc/mdstat` 里又回来了」。正确收尾是 `mdadm --zero-superblock` 每块成员盘，再 `wipefs -a`。

### 0.10.15 小结

十四条可以按「认错设备」「写错配置」「判错状态」三类记：认错设备（1、5、9）全靠 `/dev/disk/by-id` 与 `lsblk` 复核；写错配置（2、3、4、7、8）集中在 fstab、swap 与挂载选项，`nofail`、`_netdev`、`x-systemd.*` 是救命参数；判错状态（6、10、11、12、13、14）来自 `df` 与 inode、`D` 状态、TRIM 与 SMART 的误读。如果只记住一件事，那就是**对任何「写盘」命令，先打印目标再执行**。

::: method 即时自测 · 0.10.15
**Q1（记忆）** 为什么脚本里写 `/dev/sdb` 很危险？该用什么替代？

**Q2（辨析）** `df` 显示有空间但写不进去，最常见的两个原因是什么？

**Q3（应用）** 你要改一台远程机器的 fstab。给出两条降低「改完开不了机」风险的做法。

::: sol 答案
**A1** `/dev/sdX` 的编号随探测顺序变化，重启或插拔后可能指向另一块盘。用 `/dev/disk/by-id/…` 或 `by-uuid`，它们是内容/序列号寻址，跟插槽顺序无关。

**A2** ① inode 用尽（`df -i` 看，小文件多的盘常见）；② 文件被删除但仍被进程持有（`lsof +L1` 能看到，空间要等进程退出才回来）。

**A3** ① 每一项都加 `nofail`（或至少给非关键挂载加），并设 `x-systemd.device-timeout=10s` 避免开机卡死；② 改完先 `mount -a` 验证，再 `systemctl daemon-reload`；远程机器保留一个已登录的会话再改。
:::

::: method 即时自测 · 0.10
**Q1** `df -h /data` 显示 100%，`du -sh /data` 只有 40 GB，文件系统是 100 GB。列出三种可能，并给出各自的验证命令。

**Q2** `df -h` 还有 17 GB，`touch /data/x` 却报 `No space left on device`。最可能是什么？怎么确认？

**Q3** 一个 1 TB 的 XFS 文件系统在 LVM 上，需要缩到 800 GB。可行步骤是什么？如果必须缩，应该怎么做？

**Q4** RAID5 三块盘坏了一块，你换上新盘开始重建。此时再坏一块会怎样？为什么说「RAID 不是备份」？

::: sol 答案
**A1** ① 删除的文件仍被打开：`sudo lsof +L1` 看 `(deleted)`；② ext4 预留块：`sudo tune2fs -l /dev/... | grep Reserved`；③ 挂载点遮住了原目录：`findmnt` 看是否有叠加挂载，`umount` 后复查；④ 还有快照/稀疏文件：`du --apparent-size`、`btrfs filesystem usage`。

**A2** inode 用尽。`df -i /data` 看 `IUse%` 是否 100%，`sudo find /data -xdev -type f | wc -l` 数文件数。确认后删无用小文件，或迁到 inode 更多的文件系统；重建加 `-N` 是最后手段。

**A3** XFS 不支持缩容。可行路径是：备份数据 → `umount` → `lvreduce` 到 800 GB → `mkfs.xfs` 重建 → 恢复数据。不能先 `lvreduce` 再 `xfs_growfs` 反向缩，也不能对已缩小的块设备上的 XFS 直接挂载写入。若必须频繁缩容，选 ext4 或 Btrfs。

**A4** RAID5 降级时没有冗余，再坏一块就整阵列失效，数据全丢。重建期间所有盘都在满负荷读，第二块盘在这段时间故障的概率显著上升；而且 RAID 只防盘坏，不防误删、勒索软件、控制器故障、机房事故。备份必须是独立的、离线的、可恢复验证过的副本。
:::
