0.8 的脚本会启动子进程，也会被信号打断。脚本之外，系统里的每个进程都挂在一棵树上，还属于某个进程组和会话。你按 Ctrl-C 时，信号并不是发给「那个程序」，而是发给**前台进程组**；`kill` 也不是「杀死」，只是把一个异步通知放进目标进程的待处理队列。

这三个概念——进程、进程组/会话、信号——是日常排障里最容易被跳过的一层。跳过它们的代价是：`kill -9` 之后端口仍被占用、`nohup` 之后进程还是断了、`ps` 显示 `D` 却怎么都杀不掉。这些现象都不是「Linux 有 bug」，而是没看清进程的组织方式。

这一章只讲用户可见的部分：怎么读状态、怎么组织作业、怎么发信号、怎么回收子进程。信号在程序内部怎么注册处理器、怎么处理 `EINTR`、怎么用 `signalfd`，留给 [2.10 信号](../part2/ch10.md)；本章的例子全部可以用 shell 和现成命令复现。

## 0.9.1 先学会读 `ps` 的五列 {#sec-0.9.1}

这一节回答：`ps` 的 `pid/ppid/pgid/sid/tty/stat` 这几列是从哪来的？`ps aux` 与 `ps -ef` 差在哪？`STAT` 结尾那些 `s`/`l`/`+`/`N` 又是什么？

::: preview 先抓住一件事
`ps` 不是什么查询魔法，它只是读文件：在 Linux 上遍历 `/proc/PID/`，把每个进程的 `stat` 文件里的数字重新拼成表格。看懂「列 ↔ 字段」的对应关系，五列就不再靠背，两套语法也只是两种方言。
:::

### 0.9.1 场景：同一份数据，两个口径并排看

在 Ubuntu 24.04 上用伪终端开一个真实的交互式 bash，先跑 `ps`，再直接读 `/proc` 里那个进程的字段：

<div class="terminal" data-title="bash 5.2.21 · Ubuntu 24.04 实测（伪终端）">
<pre><span class="p">&#36;</span> tty
/dev/pts/0
<span class="p">&#36;</span> ps -o pid,ppid,pgid,sid,tty,stat -p &#36;&#36;
    PID    PPID    PGID     SID TT       STAT
  34259   34258   34259   34259 pts/0    Ss
<span class="p">&#36;</span> cut -d" " -f1-8 /proc/&#36;&#36;/stat
34259 (bash) S 34258 34259 34259 34816 34261
</pre>
</div>

两边是对得上的。`/proc/PID/stat` 按空格分字段：第 1 个 `pid`，第 2 个 `comm`（命令名，带括号），第 3 个主状态，第 4 个 `ppid`，第 5 个 `pgrp`（即 `pgid`），第 6 个 `session`（即 `sid`），第 7 个 `tty_nr`，第 8 个 `tpgid`。`tty_nr` 是十进制设备号：34816 = 136 × 256 + 0，主号 136 正是 pts 系列，所以 `ps` 把它印成 `pts/0`；没有控制终端的进程这里显示 `?`。`tpgid` 是终端当前认的前台进程组号——读这一行的瞬间，前台是正在执行的 `cut` 自己那一组（34261），连产生它的 bash（34259）都在后台。

再让 `strace`（跟踪进程做了哪些系统调用的工具）证明 `ps` 真的在逐个读 `/proc`：

<div class="terminal" data-title="strace · Ubuntu 24.04 实测">
<pre><span class="p">&#36;</span> strace -e trace=openat ps -o pid= -p &#36;&#36; 2&gt;&amp;1 | grep "/proc" | head -6
openat(AT_FDCWD, "/proc/self/status", O_RDONLY) = 3
openat(AT_FDCWD, "/proc/self/status", O_RDONLY) = 3
openat(AT_FDCWD, "/proc/self/stat", O_RDONLY) = 3
openat(AT_FDCWD, "/proc/20363/status", O_RDONLY) = 3
openat(AT_FDCWD, "/proc/20363/stat", O_RDONLY) = 3
openat(AT_FDCWD, "/proc/sys/kernel/pid_max", O_RDONLY) = 3
</pre>
</div>

每个 PID 一对 `status` 与 `stat`，最后读 `pid_max` 决定枚举到哪。所以 `ps` 的口径就是 `/proc` 的口径（`proc(5)` 手册的口径）。macOS 没有 `/proc`，它的 `ps` 走内核的进程信息接口，列的集合也跟着变——这正是本章「双口径」的典型例子。

### 0.9.1 机制：两套方言，一个建议

`ps aux` 是 BSD 方言（选项不带横线），`ps -ef` 是 UNIX 方言（带横线）。VM 上两份真实表头：

<div class="terminal" data-title="procps-ng 4.0.4 · Ubuntu 24.04 实测">
<pre><span class="p">&#36;</span> ps -ef | head -2
UID          PID    PPID  C STIME TTY          TIME CMD
root           1       0  0 13:32 ?        00:00:02 /sbin/init splash
<span class="p">&#36;</span> ps aux | head -2
USER         PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root           1  0.2  0.1  23108 13620 ?        Ss   13:32   0:02 /sbin/init splash
</pre>
</div>

macOS（BSD `ps`）实跑同一对命令，差异立刻现形：`TTY` 变 `TT`、`START` 变 `STARTED`、`TIME` 精确到百分之一秒（实测 `35:05.46`），而 `-ef` 那套 UID/PPID 表头两边一致。更疼的一条是 BSD 的 `-o` 不认 `sid` 关键字——在 macOS 上跑同一行取列命令：

```bash
$ ps -o pid,ppid,pgid,sid,tty,stat,comm -p $$
ps: sid: keyword not found
```

这行在 Ubuntu 24.04 原样能跑。两边共同的结论是：**排障和脚本一律用 `-o` 显式点名列**，方言差异当场暴露，比背两套默认格式可靠。另一个数字口径要记：`ps aux` 的 `%CPU` 是进程自启动以来的平均值，不是瞬时值——macOS 实测里那个已跑 35 分钟的进程显示 98.1%，它可能大部分时间都在睡觉；瞬时值用 `top`/`pidstat 1`（0.9.9 展开）。

`STAT` 第一个字母是主状态（0.9.3 专讲），后面的是修饰字母。下面每个样本都来自 VM 的真实进程表：

| 修饰字母 | 含义 | Ubuntu 24.04 实测样本 |
|:--|:--|:--|
| `s` | 会话首领（`sid` 等于自己的 `pid`） | `Ss`，PID 1 的 systemd |
| `l` | 多线程 | `Ssl`，pipewire |
| `+` | 属于终端的前台进程组 | `R+`，前台正在跑的 ps 自己 |
| `N` | nice 大于 0，CPU 优先级被调低 | `SN`，`nice -n 5 sleep` 实测 NI 列 5 |
| `I`/`<`/`>` | 空闲内核线程/高/低优先级 | `I<`，kworker 线程 |

顺带一提截断：VM 表里能看到 `user-session-he`、`xdg-permission-` 这种「怪名字」，那是 `comm` 被内核截到 15 个字符的样子，完整命令行要用 `args` 列或 `pgrep -a`。

::: ex 例 0.9.1 · 读懂一行 `R+` {#ex-0.9.1}
先猜：`R` 与 `+` 各表示什么？这一行属于前台组还是后台组？

同一个 VM、同一个伪终端会话里，我们在前台跑 `ps` 抓到了它自己这一行（列为 `pid,pgid,sid,tty,tpgid,stat,comm`）：

```text
    PID    PGID     SID TT       TPGID STAT COMMAND
  34080   34080   34067 pts/0    34080  R+   ps
```

它说了几件事？逐列读一遍。
::: sol 解答
`PGID=34080` 等于自己的 `PID`：ps 就是组长——交互式 bash 给每个新命令单独开一个进程组。`TPGID=34080`：终端认的前台组正是它自己，所以状态带 `+`。`SID=34067`：它挂在 34067 这个会话里——对照本节开头那行 bash（`PGID=SID=34259`、带 `s`）的读法，会话号就是那个首领 bash 的 PID。`STAT=R+`：主状态 `R` 是「正在跑或在运行队列」，`ps` 给自身拍快照时几乎必然 `R`。一句话，这一行同时证明了「前台组是轮换的」和「修饰字母只是附注，第一个字母才是状态」。
:::
:::

::: think 思考 · 为什么 `ps` 只能给你一张快照
`ps` 打开每个 `/proc/PID/stat` 再拼表，读完一行又是一行，前后并不原子。所以「父进程列里 PID 还在、孩子已经换了」完全可能，`ps aux | grep xxx` 顺手抓到 grep 自己也是同一类现象。要把「读到的信息」和「行动对象」绑死，得靠 `/proc/PID/stat` 第 22 字段的 `starttime` 或 `pidfd` 来确认身份（0.9.7）；日常够用的纪律是先 `pgrep -af` 核对、再按 PID 动手。
:::

::: errata 常见错误清单（0.9.1 节）
1. **「`aux` 和 `-ef` 记一个就行」**——两套方言的默认列不同：`-ef` 没有 STAT 与 PGID，`aux` 的 `%CPU` 又是平均值；BSD 方言在 macOS 上连 `sid` 列都不给（`keyword not found` 实测）。用 `-o` 点名列才是两边通吃的路。
2. **「`%CPU` 高说明现在很忙」**——它是生命周期平均；macOS 实测里那个 98.1% 的进程已跑了 35 分钟。瞬时占用看 `top`、`pidstat 1`。
3. **「STAT 只看第一个字母就够了」**——`+` 决定它能不能读终端（0.9.2），`s` 标记会话首领，`l` 意味着它按线程展开会有多行；丢掉后缀会漏判。
4. **「`pkill -x 完整程序名` 总没错」**——`-x` 比的是 `comm`，超过 15 字符已被截断（实测表里的 `xdg-permission-`），长名字匹配不上；核对用 `pgrep -a`，必要时 `-f` 匹配完整命令行。
5. **「PID 就是身份证」**——PID 会复用，快照到动手之间可能换人；绑定身份要用 `starttime` 或 `pidfd`（0.9.7）。
:::

::: method 判定流程 · 一行 `ps` 输出的阅读顺序
1. 先看 `STAT` 第一字母：判断它「在等谁」（0.9.3 的表）。
2. 再看后缀：有没有 `+`（前台？）、`s`（会话首领？）、`l`（多线程？）。
3. 比 `PGID` 与自己的 `PID`：相等说明它是组长——作业控制里一个作业的头（0.9.2）。
4. 比 `SID` 与 `TPGID`：它挂在哪个终端、终端当前让谁在前台。
5. 最后看 `PPID`：谁负责给它收尸、它由谁启动。
:::

### 0.9.1 小结

`ps` 只是把 `/proc/PID/stat` 的字段拼成表：五列各有出处，`tty_nr` 是设备号、`tpgid` 是终端的前台组指针；BSD 与 UNIX 两套方言列集不同，macOS 甚至不认 `sid`，所以用 `-o` 显式点名列。如果只记住一件事，那就是：**先读 `STAT` 第一字母，再读后缀，然后顺 `PGID`/`SID`/`PPID` 找它在组织上的位置。**

::: method 即时自测 · 0.9.1
**Q1（记忆）** `/proc/PID/stat` 的第 5、6、8 字段分别对应 `ps` 的哪几列？`tty_nr` 的 34816 在表上显示成什么？

**Q2（辨析）** 同一行 `ps -o pid,ppid,pgid,sid,tty,stat,comm -p $$`，Ubuntu 24.04 与 macOS 上哪个会失败？`ps aux` 与 `ps -ef` 在 Linux 上的默认列差在哪？

**Q3（应用）** 你看到一行 `PID 34080 PGID 34080 SID 34067 TPGID 34080 STAT R+ COMMAND ps`，它在前台还是后台？它的组长是谁？

**Q4（迁移）** 巡检脚本报「`ps: sid: keyword not found`」，这台机器可能是什么系统？你会怎么改脚本，让它两类系统都不静默出错？

::: sol 答案
**A1** 第 5 字段 `pgrp` 对 `pgid`，第 6 字段 `session` 对 `sid`，第 8 字段 `tpgid` 对 `tpgid` 列。34816 = 136×256+0，显示成 `pts/0`。
**A2** macOS 会失败——BSD `ps` 的 `-o` 不认 `sid`（实测 `keyword not found`）。Linux 上 `-ef` 给 `UID PID PPID C STIME TTY TIME CMD`，`aux` 给 `USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND`；前者没有状态列，后者 %CPU 是平均值。
**A3** `TPGID` 等于它的 `PGID`、状态带 `+`，是前台；`PGID` 等于自身 `PID`，它就是这个前台组的组长（bash 为这条命令现开的组）。
**A4** 大概率是 BSD/macOS。改法：探测方言再取列——Linux 走 `-o pid,pgid,sid`；macOS 侧没有等价的 SID 取列（实测 `sess` 给的是会话结构地址，非会话号，还可能显示 0），就显式标注「本平台不输出 sid」并走别的路，不要吞掉报错。
:::
:::

## 0.9.2 进程组、会话与控制终端 {#sec-0.9.2}

这一节回答：进程组与会话为什么是两套独立编号？控制终端替内核记着哪个「前台组」？为什么 `Ctrl-C` 打到的从来不是「那个程序」，而是整个前台进程组？

::: preview 先抓住一件事
每个进程同时带着三个号码：`PID` 是本人，`PGID` 决定「它挨打时谁陪它挨」，`SID` 决定「它挂在哪个终端后面」。0.2.6 教过 `&`、`fg`、`Ctrl-Z` 的用法，那一节的每个现象都能由这三个号码解释——我们这一节就在 Ubuntu 24.04 上把它们一个个读出来。
:::

### 0.9.2 场景：一个终端里的四个组

用伪终端开交互式 bash，启动两个后台作业和一个会去读终端的后台作业，然后一次看全：

<div class="terminal" data-title="bash 5.2.21 · Ubuntu 24.04 实测（伪终端）">
<pre><span class="p">&#36;</span> sleep 120 | sleep 121 &amp;
[1] 24712
<span class="p">&#36;</span> cat &amp;
[2] 24713
<span class="p">&#36;</span> sleep 200 &amp;
[3] 24714

[2]+  Stopped                 cat
<span class="p">&#36;</span> jobs -l
[1]  24711 Running                 sleep 120
     24712                       | sleep 121 &amp;
[2]+ 24713 Stopped (tty input)     cat
[3]- 24714 Running                 sleep 200 &amp;
<span class="p">&#36;</span> ps -o pid,ppid,pgid,sid,tty,tpgid,stat,comm -p &#36;&#36;,24711,24713,24714
    PID    PPID    PGID     SID TT       TPGID STAT COMMAND
  24709   24708   24709   24709 pts/0      24722 Ss   bash
  24711   24709   24711   24709 pts/0      24722 S    sleep
  24713   24709   24713   24709 pts/0      24722 T    cat
  24714   24709   24714   24709 pts/0      24722 S    sleep
</pre>
</div>

读法：管道两端 24711/24712 共享一个组（组号 24711，管道的第一个进程）；`cat` 和 `sleep 200` 各成一组——交互式 shell 给每个作业开一个新组。四行的 `SID` 都是 24709，等于 bash 自己的 PID：它就是**会话首领**（session leader，`STAT` 里的 `s`），`sid == pid` 是首领的标志。`TPGID` 是 24722——既不是 bash 的组也不是任何作业的组，而是执行这条 `ps` 时它自己所在的前台组（0.9.1 的 `R+` 同款）：前台组是轮换的，谁在执行命令谁就是前台。

<pre class="layout">
会话 24709 ── 控制终端 /dev/pts/0 ── 前台组记录 TPGID=24722（执行 ps 的那刻）
├── 组 24709：bash（会话首领，自身也可视为前台空档）
├── 组 24711：sleep 120 + sleep 121（后台作业 1，一条管道一个组）
├── 组 24713：cat（后台作业 2，读终端被停，STAT=T）
└── 组 24714：sleep 200（后台作业 3）
</pre>

### 0.9.2 机制：信号按组投递，终端只认一个号

**进程组**（process group，PGID）是共享一个组号的进程集合，组号等于**组长进程**的 PID；组长可以比组员先退出，组也不因此解散——组号是建组那一刻的登记，不随「谁还在场」改选。它的用途就一个：一次向一组进程发信号——`kill -TERM -- -24711` 打的是整个组。**会话**（session，SID）是进程组的集合，会话首进程的 `sid` 等于它自己的 `PID`。一个会话最多挂一个**控制终端**（controlling terminal）；反过来，终端驱动替内核记着两件事：本终端属于哪个会话、当前**前台进程组**（foreground process group）是哪个号，也就是 `tpgid`。键盘上的信号生成字符——`Ctrl-C`（`SIGINT`）、`Ctrl-\`（`SIGQUIT`）、`Ctrl-Z`（`SIGTSTP`）——由终端驱动产生后，投递对象是 `tpgid` 那一组的**全部成员**，不是某个 PID。

只有前台组有权从终端读输入。后台组一碰读，终端驱动就给它发 `SIGTTIN`，默认动作是停止——上面 `cat` 那行 `Stopped (tty input)`、`STAT=T` 就是 Ubuntu 24.04 上现场发生的 SIGTTIN。后台写终端默认是放行的；只有 `stty tostop` 打开时，后台写才收 `SIGTTOU`。

「打组」和「打本人」的区别，可以亲手验证。我们在另一个会话里对着上面那个前台管道发了整组 `SIGINT`（模拟终端驱动在 `Ctrl-C` 时做的事）：

<div class="terminal" data-title="Ubuntu 24.04 实测">
<pre><span class="p">&#36;</span> ps -o pid,pgid,sid,tty,tpgid,stat,comm -p 26528,26529
    PID    PGID     SID TT       TPGID STAT COMMAND
  26528   26527   26527 pts/0      26527 S+   sleep
  26529   26527   26527 pts/0      26527 S+   sleep
<span class="p">&#36;</span> kill -INT -- -26527
<span class="p">&#36;</span> ps -p 26528,26529
    PID STAT COMMAND
</pre>
</div>

两端都带 `S+`：同组、且正是前台组；一次负组号的 `SIGINT`，两条都消失。这就是 `Ctrl-C` 能同时打断管道两端的机制——不是 shell 挨个转发，而是内核按组投递。

**脱离会话**是另一个方向：`setsid` 让进程新建会话、当上首领、丢掉控制终端。同一终端里并排跑的对照（Ubuntu 24.04 实测）：

<div class="terminal" data-title="Ubuntu 24.04 实测">
<pre><span class="p">&#36;</span> nohup sleep 288 &gt;/dev/null 2&gt;&amp;1 &amp;
<span class="p">&#36;</span> setsid sleep 288 &amp;
<span class="p">&#36;</span> ps -o pid,ppid,pgid,sid,tty,stat,comm -C sleep
    PID    PPID    PGID     SID TT       STAT COMMAND
  31808   31807   31808   31807 pts/0    S    sleep
  31810       1   31810   31810 ?        Ss   sleep
</pre>
</div>

`nohup` 那行 `SID` 仍等于会话号、`TT` 仍挂着 `pts/0`——它只是给自己披了件「不听 `SIGHUP`」的蓑衣，组织关系原封不动，关终端时它还可能被 `SIGTTIN` 之类的规矩绊住。`setsid` 那行 `PGID=SID=PID`、`STAT=Ss`、`TT=?`：新会话、无控制终端，`PPID=1` 是因为启动它的 shell 已退出、孤儿被 PID 1 接管（0.9.6）。守护进程的正确出生方式就是这个（0.2.6 给过操作入口，这里补的是「为什么它有效」）。

| 标识 | 取自哪里 | 谁赋值 | 用途 |
|:--|:--|:--|:--|
| `PID` | 进程本人 | 内核分配 | 精确操作单个进程 |
| `PPID` | 父进程 | 创建时继承 | 谁负责回收、谁启动的 |
| `PGID` | 进程组 | `setpgid`，shell 为每个作业建组 | 一次向整组发信号 |
| `SID` | 会话 | `setsid` | 终端归属与守护进程的边界 |
| `TPGID` | 终端的前台组记录 | 终端驱动 / shell 切换 | 判断谁在前台、谁能读终端 |

::: ex 例 0.9.2 · `nohup` 为什么救不了那个 `cat` {#ex-0.9.2}
先猜：`nohup` 已经忽略了 `SIGHUP`，那个 `cat` 为什么还是死了？

有同事把交互式程序 `nohup cat &` 放后台，回来发现它停在 `T`。用本节三个号码解释：`nohup` 改了什么、没改什么？`SIGTTIN` 为什么照样打得着它？给出两种修法。
::: sol 解答
实测对照里 `nohup` 那行的 `SID`、`TT` 与启动它的 bash 完全相同——它还在这个会话里，还挂着这个控制终端，组号也还是 shell 给它开的那个作业组。`nohup` 只做了两件事：把 `SIGHUP` 设成忽略、在 stdout 连着终端时转到 `nohup.out`；它对「谁能读终端」没有任何影响。终端驱动的规矩是「非前台组来读就发 `SIGTTIN`」，这与信号处置无关（`nohup` 没忽略 `SIGTTIN`），默认动作停止照样执行。修法一：`nohup cat </dev/null &`，让它读的不再是终端；修法二：`setsid cat ...` 直接脱离会话与控制终端（实测 `TT=?` 那一行的样子）。顺带分清层次：`SIGHUP` 防的是「挂断」，`SIGTTIN` 防的是「抢键盘」，两件事故不同科室管。
:::
:::

::: think 思考 · 为什么终端只记一个前台组号
如果终端给每个进程单独记「能不能读键盘」，前后台切换就要挨个改登记表，作业一多必然漏。内核把问题反过来：一个终端同时只服务一个前台组，切换只是改写一个号码（`tcsetpgrp` 一次系统调用）。`fg`/`bg` 之所以快、之所以「换个 Shell 就失效」，根源都是这条：那个号码记在终端上，而只有当前这个会话的 shell 知道怎么改它。
:::

::: errata 常见错误清单（0.9.2 节）
1. **「`Ctrl-C` 发给那个程序」**——发给的是终端前台组的全部成员（实测整组 SIGINT 让管道两端同时消失）；不在前台组的后台作业对 `Ctrl-C` 免疫。
2. **「组长的 `PGID` 永远等于组里最老的进程」**——组号等于**创建该组那一刻**的组长 PID；组长可以中途退出，组依然存在，甚至组号与所有存活成员都不相等的时刻也合法。
3. **「后台进程不许用终端」**——读被禁（`SIGTTIN`），写默认放行；`stty tostop` 打开后写也会被 `SIGTTOU` 停（tostop 默认关闭，打开后的效果本机未实测）。
4. **「`nohup` 之后进程就脱离终端了」**——实测 `SID`、`TT` 都没变；脱离终端要用 `setsid`（或 systemd），防断线才轮到 `nohup`/`disown -h`（0.9.4）。
5. **「会话 = 终端窗口」**——窗口关闭只是 pty 挂断，会话还在不在取决于首领进程；tmux 的会话跑在服务进程里，窗口关了会话照活（0.2.8）。
:::

::: method 判定流程 · 这个进程挨打时谁陪着它
1. `ps -o pid,pgid,sid,tty,tpgid,stat -p PID`：先凑齐五个号。
2. 看 `SID`：等于 `?`/无终端 → 守护进程一类，终端信号与它无关；否则它挂在这个终端上，终端挂断有 `SIGHUP` 风险。
3. 比 `PGID` 与 `TPGID`：相等 → 它就是前台组，收得到键盘信号、读得了终端；不等 → 后台组，`Ctrl-C` 找不到它，读终端会被停。
4. 要打整组：`kill -SIG -- -PGID`（负号前加 `--`）；只打本人：不带负号。
:::

### 0.9.2 小结

进程组管「一起挨打」，会话管「挂在哪个终端」，终端只记一个前台组号：`Ctrl-C`/`SIGTTIN` 的怪事全部由这三个号的相对关系决定。`nohup` 只改信号处置不改组织关系，`setsid` 才真正换会话。如果只记住一件事，那就是：**先问它是哪个组、哪个会话、终端的前台是不是它，再谈信号发给谁。**

## 0.9.3 状态字母背后的等待队列 {#sec-0.9.3}

这一节回答：`STAT` 的首字母 `R/S/D/T/Z` 各自挂在内核的哪个等待队列上？为什么 `D` 连 `SIGKILL` 都不理？`Z` 是「还活着」还是「已经死了」？

::: preview 先抓住一件事
状态字母描述的是「进程挂在哪个队列上」，不是「活没活着」。`D` 挂在一个不查看信号的队列里，任何信号都要等它自己回到能处理信号的地方才生效；`Z` 正好相反——进程本体已经退出，只剩一条内核登记记录等父进程来取。
:::

{{#include ../assets/figures/proc-states.md}}

读图：`TASK_RUNNING` 同时包含「正在跑」和「在运行队列里等 CPU」，所以 `R` 不等于「正占用 CPU」；`S` 与 `D` 的差别只有一条——唤醒时看不看信号。下面用 Ubuntu 24.04 实测把最容易被误判的 `Z` 和 `T` 钉死。

**`Z`：孩子已死，父进程还没来取。** 在 VM 上起一个「fork 出孩子后只睡觉、不 `wait`」的父进程：

<div class="terminal" data-title="bash 5.2.21 · Ubuntu 24.04 实测">
<pre><span class="p">&#36;</span> python3 -c 'import os,time; p=os.fork(); os._exit(0) if p==0 else time.sleep(60)' &amp;
[1] 29086
<span class="p">&#36;</span> ps -o pid,ppid,stat,comm -p 29088,29086
    PID    PPID STAT COMMAND
  29086   29085 S    python3
  29088   29086 Z    python3
<span class="p">&#36;</span> grep -E '^(State|PPid)' /proc/29088/status
State:	Z (zombie)
PPid:	29086
<span class="p">&#36;</span> cat /proc/29088/wchan
0
<span class="p">&#36;</span> kill -9 29088; sleep 0.3; ps -o pid,stat -p 29088
    PID STAT
  29088 Z
<span class="p">&#36;</span> kill 29086; sleep 0.5; ps -o pid,stat -p 29088
<span class="p">&#36;</span> echo $?
1
</pre>
</div>

四步连起来就是一句话：僵尸不是活人，是一张没被销户的死亡证明。它不占内存页、不占 CPU，只占一个 PID 和内核进程表里的一条记录；`kill -9` 对它毫无意义，因为它已经没有可执行的代码了。能做的只有两件事：让父进程 `wait`，或让父进程死掉、由 PID 1 收养并回收（0.9.6 细讲）。BSD 侧（macOS 实测）`ps axo pid,ppid,stat,comm` 同样给出 `Z`，只是命令行那一列显示为 `<defunct>`，而且没有 `/proc` 可查——`State`、`wchan` 这两样在 macOS 上拿不到。

**`T`：停在 `do_signal_stop`。** 停止（stop）与睡眠是两回事，同一台 VM 上：

<div class="terminal" data-title="bash 5.2.21 · Ubuntu 24.04 实测">
<pre><span class="p">&#36;</span> sleep 300 &amp; s=29402
<span class="p">&#36;</span> kill -STOP 29402
<span class="p">&#36;</span> ps -o pid,stat,wchan:20,comm -p 29402
    PID STAT WCHAN                COMMAND
  29402 T    do_signal_stop       sleep
<span class="p">&#36;</span> kill -TERM 29402; sleep 0.3; ps -o pid,stat -p 29402
  29402 T
<span class="p">&#36;</span> kill -CONT 29402; wait 29402; echo $?
143
</pre>
</div>

`SIGTERM` 打在停着的进程上不立刻结算：进程停在停止队列里（`wchan` 显示 `do_signal_stop`），要等 `SIGCONT` 恢复的这一刻才把 TERM 执行掉，退出码 143（128+15）。终端里的 `Ctrl-Z` 是同一件事的交互入口：我们在伪终端里真的敲了 `0x1A` 这个字节，得到 `[1]+ Stopped  sleep 299` 和 `STAT T`。但 `Ctrl-Z` 背后的 `SIGTSTP` 与 `SIGSTOP` 有个实测差别：对孤儿进程组（组内成员的父进程都不在「本组且本会话」里），内核会忽略 `SIGTSTP`——VM 上从外部发 `kill -TSTP`，`sleep` 纹丝不动仍是 `S`；同一进程发 `kill -STOP` 立刻 `T`。macOS 的行为一致（`SN` → `TN`）。

**`D`：机制上为什么不看信号。** 内核把进程挂进「不可中断睡眠」（`TASK_UNINTERRUPTIBLE`）时，等的是块设备、驱动这类不能中途反悔的操作：请求已经交给硬件，缓冲区和锁正处于不一致的窗口，此刻唤醒它反而会损坏数据。信号不会被丢弃，只是挂起，等 I/O 返回才处理。极端情况（NFS 服务端失联）`D` 可以持续很久，`ps` 里一排 `D`，`load average` 跟着涨——Linux 的负载统计的是「可运行 + 不可中断」两拨任务的数量，不是 CPU 百分比。因为普通用户很难在 ext4 上造出持续 `D` 的样本，本节的 `D` 与 macOS 的 `U`（不可中断等待）都标未实测，机制表述以内核状态定义为准。2.6.25 起内核还有第三种睡眠 `TASK_KILLABLE`：只应答致命信号，NFS 用它来避免「永久杀不掉」。

| 字母 | 挂在哪个队列 | 能被信号唤醒吗 | 看到它先查什么 |
|:--|:--|:--|:--|
| `R` | 正在跑或在运行队列 | 不适用 | `pidstat 1` 看它烧的是 CPU 还是空转 |
| `S` | 可中断睡眠，等事件 | 能 | `wchan`；多数 `sleep`、等输入都是正常态 |
| `D` | 不可中断睡眠，等 I/O | 不能，信号挂起 | `wchan`、`/proc/PID/stack`，查磁盘与 NFS |
| `T` | 停止队列（`do_signal_stop`） | 只认 `SIGCONT` | 谁发的 STOP/TSTP，或有没有调试器 |
| `Z` | 不在队列，只待父进程回收 | 已死，信号无效 | PPID；父进程为什么不 `wait` |
| `t`/`X` | 被 ptrace 停住/正在退出 | 由调试器或内核 | 瞬时态，`ps` 里很少见到 |

这张表的用法是「排障第一步查什么」：字母本身只告诉你队列，线索永远在队列的对面——`D` 查 I/O 伙伴，`Z` 查父亲，`T` 查谁按的暂停。

::: ex 例 0.9.3 · 一行 `Z` 读出的完整因果链 {#ex-0.9.3}
先猜：僵尸是谁产生的？它的父进程为什么不收尸？

上面 VM 实测里，`ps` 给出 `29088 29086 Z python3`。请把这一行与 `/proc/29088/status`、`wchan`、`kill -9` 的结果串成一条因果链：这个 PID 还能执行代码吗？谁该负责让它消失？为什么最后一步是杀 29086 而不是 29088？
::: sol 解答
`Z` 意味着 29088 已经执行完 `_exit(0)`，内核只在进程表里给它留了一条记录：PID、退出状态和资源统计；`wchan` 读出 `0` 说明它根本没有在等的内核事件——不是卡住，是已完结。`kill -9 29088` 无效，因为信号的接收方是这个进程的执行上下文，而它已不存在。负责销户的是 PPID 29086：父进程 `wait` 时内核删除记录。父进程睡 60 秒不 `wait`，记录就一直挂着。所以正确动作是作用于 29086——实测 `kill 29086` 之后，29088 作为遗孤被 PID 1 收养，PID 1 的回收逻辑立刻把它销户，`ps -p 29088` 返回码 1（查无此进程）。处理僵尸的力气永远花在父进程身上，不在僵尸身上。
:::
:::

::: think 思考 · 为什么内核宁可留一张「死亡证明」
如果子进程一退出就自动消失，父进程就永远读不到「孩子是怎么死的」——退出码、被哪个信号杀死、用了多少 CPU 时间，这些都是 `wait` 的返回值。内核选择「保留记录、等父进程来取」，把销户的时机交给语义上唯一需要它的人。代价就是我们看到的僵尸：父进程失职，记录就堆积。后来的折中方案（把 `SIGCHLD` 显式设成 `SIG_IGN` 可自动回收）把选择权还给程序，边界见 0.9.6 与 0.9.10。
:::

::: errata 常见错误清单（0.9.3 节）
1. **「`R` 就是正在占用 CPU」**——`R` 包含「在运行队列里排队」；多核机器上四个 `R` 未必是过载，用 `pidstat 1` 看实际份额。
2. **「`kill -9` 专治 `D`」**——不可中断睡眠在内核里不查看信号，TERM、KILL 都得等 I/O 返回；NFS 失联时可能等到天荒地老，这不是权限问题，是状态问题。
3. **「僵尸进程在偷吃内存」**——实测的 `Z` 不占内存页、不占 CPU，只占一个 PID 和一条内核记录；真正的危害是数量多了耗尽 `pid_max`、妨碍新进程创建。
4. **「`T` 就是卡死」**——`T` 是可控暂停，`SIGCONT` 即恢复，内存与打开的文件都在；和调试器造成的 `t`、内核正在执行的 `X` 都不是一回事。
5. **「看到 `Z` 先去杀它」**——杀僵尸是徒劳（实测 `kill -9` 后仍是 `Z`）；要动的是父进程。
6. **「load 高就是 CPU 不够」**——load 计的是 `R` 加 `D`；一排 `D` 时 `top` 的 CPU 可以照样空闲，先查 I/O 再谈扩容。
:::

::: method 判定流程 · 遇到可疑状态先查什么
1. 先确认字母本身：`ps -o pid,stat,ppid,wchan:20,comm -p PID`，第一个字母才是主状态。
2. `Z`：看 PPID，`ps -o pid,stat,comm -p PPID` 检查父进程是不是还活着、是不是 init；处理方向在父进程。
3. `T`：想是谁暂停的——交互作业多半是 `Ctrl-Z`/`bg` 前的停（0.9.4）；后台程序多半有人 `kill -STOP`；恢复用 `SIGCONT`。
4. `D`：读 `wchan`（root 时读 `/proc/PID/stack`），顺着它查磁盘、NFS、驱动；`vmstat 1` 的 `b` 列看同类任务的规模。
5. `R` 且 CPU 不满：用 `pidstat 1 -p PID` 区分「真忙」与「排队」，再决定是否动 nice/cgroup（0.9.8）。
:::

### 0.9.3 小结

`STAT` 首字母是内核等待队列的名字：`S` 在可中断队列、`D` 在不看信号的队列、`T` 在停止队列、`Z` 已退出只等销户、`R` 含排队。实测的 `Z` 与 `T` 告诉我们：`kill -9` 无效的一种是「已经死了」（`Z`），一种是「内核里不看信号」（`D`），这两种的修法完全不同。如果只记住一件事，那就是：**处理状态问题先找队列对面的人——僵尸找父亲，`D` 找 I/O，`T` 找按暂停的手。**

::: method 即时自测 · 0.9.3
**Q1（记忆）** `S` 与 `D` 的差别用一句话怎么说？`T` 状态下 `SIGTERM` 会发生什么（用实测结果回答）？

**Q2（辨析）** 「僵尸进程」和「停止进程」哪个还占着内存页？哪个 `kill -9` 有效？为什么？

**Q3（应用）** `uptime` 显示 load 8.0，`top` 显示 CPU 95% 空闲，`ps` 里 8 个进程 `D`、`wchan` 都指向 NFS 相关函数。下一步查什么、别做什么？

**Q4（迁移）** macOS 上没有 `/proc`，你想确认一个进程是 `Z` 还是 `T`，用什么命令？两边状态字母表有一处关键差异是什么？

::: sol 答案
**A1** `S` 的睡眠可被信号打断并当场处理，`D` 在内核里等不可反悔的事件、不查看信号。实测 `T` 状态下 `kill -TERM` 后进程仍是 `T`，`kill -CONT` 的一刻才结算，退出码 143。
**A2** 停止（`T`）的进程还活着，内存、PID、打开的文件都在，`kill -9` 有效（实测用 `kill -9` 清掉过停着的作业）；僵尸（`Z`）已退出，不占内存页，信号对它无效——它是记录不是进程。
**A3** 查 NFS 服务端与挂载链路（`dmesg`、`nfsstat -c`、网络可达性），`vmstat 1` 的 `b` 列确认不可中断任务数；别去杀这些 `D` 进程（杀不动），也别急着重启机器——先恢复服务端或卸载挂载点。这组数字是教材场景，本机与 VM 均未实测。
**A4** `ps axo pid,ppid,stat,comm`：`Z` 行在 BSD 上命令行显示 `<defunct>`；再对照 `ps -o pid,stat` 的首字母。关键差异：BSD 用 `U` 表示不可中断等待，Linux 用 `D`；Linux 的 `I` 是空闲内核线程，BSD 的 `I` 是「睡了超过约 20 秒」（`man ps` 实测核对）。
:::
:::

## 0.9.4 作业控制：`&`、`jobs`、`fg`、`bg`、`disown` {#sec-0.9.4}

这一节回答：`&`、`jobs`、`fg`/`bg`、`disown`、`kill %1` 这五个动作各自真正动了哪一层——Shell 进程内存里的作业表、内核的进程组，还是终端驱动的前台组记录？

::: preview 先抓住一件事
作业号不是内核对象，是 Shell 私有的记账：`jobs`/`kill %1` 读的是当前 Shell 进程内存里的一本名单，换个 Shell 就查无此人；`fg`/`bg` 才伸手碰内核（发 `SIGCONT`、改终端的前台组号）；`disown` 只是把名单上的一行撕掉，进程在组织关系上纹丝不动。0.2.6 教过按键怎么按，这一节给你看按键后面的账本。
:::

### 0.9.4 场景：`jobs -l` 的两份账本

同一套操作，VM（bash 5.2.21）与 macOS（系统自带 bash 3.2.57）各跑一遍。macOS 实测：

<div class="terminal" data-title="bash 3.2.57 · macOS（BSD）实测">
<pre><span class="p">&#36;</span> sleep 66 | sleep 67 &amp;
<span class="p">&#36;</span> jobs -l
[1]+ 17024 Running                 sleep 66
     17025                       | sleep 67 &amp;
</pre>
</div>

Ubuntu 24.04 上 bash 5.2.21 的输出格式一模一样（见 0.9.2 的 24711/24712 那次）：`-l` 给的是管道**每个成员的 PID**，一行一个；`+`/`-` 标「当前作业/上一个作业」；不带 `-l` 时只报状态。要注意一个口径：`jobs -l` **不打印进程组号**——想知道 0.9.2 那张 `PGID=24711`，得回去用 `ps -o pid,pgid -p`。作业号与 PID 是两套编号：`%1` 是名单行号，24711 是内核组号，两套账本各归各记。

作业表是进程私有的，这一点可以当场证明（Ubuntu 24.04 实测）：

<div class="terminal" data-title="bash 5.2.21 · Ubuntu 24.04 实测">
<pre><span class="p">&#36;</span> sleep 42 &amp; jobs -l
[1]+ 31340 Running                 sleep 42 &amp;
<span class="p">&#36;</span> bash -c 'echo "子 Shell 里 jobs=[$(jobs)]"'
子 Shell 里 jobs=[]
</pre>
</div>

父 Shell 的作业表明明白白有 31340 这一行，子 Shell 里 `jobs` 却是空的——子进程复制的是代码与内存的那一刻状态，`jobs` 内建查的是**自己进程**的作业表。换一台终端、换一个 SSH 会话同理看不见；要跨会话管理，只能回到 `ps`/`pgrep` 的世界（0.9.7），或者干脆进 tmux（0.2.8）。

### 0.9.4 机制：五个动作分别落在哪一层

**`&`** 首先是不等：Shell 记下作业号就返回。它要不要给命令单开进程组，取决于作业控制开没开（`set -m`）。VM 实测两种局面：

```text
非交互 bash（Ubuntu 24.04 实测，默认不开作业控制）：  PID 31335  PGID 31332  ← 与脚本 bash 同组
set -m 打开后（同机实测）：                           PID 31338  PGID 31338  ← 自己就是组长
```

也就是说「后台启动会进新组」只是**交互式 Shell** 的默认行为；脚本里 `cmd &` 的子进程和脚本同组，这也是脚本里 `kill 0`（0 表示当前进程组）会把自己一起杀掉的根因。与它相连的一条旧线：`lastpipe` 只在非交互且 `set +m` 时生效，原因就在这里——作业控制一开，管道每段都会进新组，谈不上「留在当前 Shell」（[0.5.12](ch05.md#sec-0.5.12)）。

**`fg`/`bg`** 干两件事：把目标作业的组号写进终端的前台组记录（`tcsetpgrp`，只有会话的 Shell 有这个权力），再给整组发 `SIGCONT`。`bg` 之后作业若再去读终端，照样被 `SIGTTIN` 停第二次（0.9.2 的 `cat`），所以「bg 救活了」要看它还需不需要键盘。

**`disown`** 只改作业表，两种改法不同：`disown -h %1` 给行打个「Shell 退出时别给它发 `SIGHUP`」的标记，作业仍列在 `jobs` 里、`kill %1` 仍可用；`disown %1`（不带 `-h`）把整行删除。实测删除后（macOS bash 3.2.57）：

```text
$ jobs -l
（空）
$ kill %1
kill: %1: no such job
```

`no such job` 证明 `%1` 的解析完全走作业表——表没了，`%` 号就找不到人；而进程本尊还活得好好的，要用它当初打印的 PID 或 `pgrep` 去收拾。VM 上 disown 之后给那个进程拍的身份照也证明它没搬家：`PGID=31487 SID=31485 TT=?`——组织关系与 disown 之前一字不差。

为什么撕掉一行能躲过退出时的 `SIGHUP`？终端挂断时内核只把 `SIGHUP` 发给**控制进程**（会话首领，也就是你的交互 Shell）；登录 Shell 退出前再按作业表的名单逐个通知作业。`disown -h` 改的是这份名单，`nohup` 改的是进程自己对 `SIGHUP` 的处置，`setsid` 直接改了组织关系（不再有「本终端的挂断」这回事）——三条路各堵一层，操作层的对照在 0.2.6 已经给过，这里补的是它们分别作用在哪本账上。

`kill %1`、`kill %+`、`kill %%` 都是「当前作业」的不同写法，`%-` 指上一个；它们与 `kill 24711` 的区别不在信号而在**解析**：前者查表翻译成组号后向整组发信号，后者只打那个 PID。表是 Shell 的，组是内核的。

::: ex 例 0.9.4 · disown 之后怎么收拾残局 {#ex-0.9.4}
先猜：`disown` 把它从作业表摘掉之后，还能靠什么找到它？

你 `sleep 43 &` 拿到 `[1]+ 31487`，随即 `disown %1`。三分钟后想停掉它，`kill %1` 报 `no such job`。请按「作业表管编号、内核管进程」的分工解释报错，给出两种正确的停法，并说明 `fg` 此时为什么也救不回来。
::: sol 解答
`%1` 需要 Shell 在作业表里把行号翻成 PID/PGID；行已被 `disown` 撕掉，翻译失败，于是报「无此作业」——这是**表的错**，不是进程的错，31487 仍挂在内核的进程组里（实测它 disown 后 `SID`、`PGID` 未变）。正确停法一：直接用记下过的 PID，`kill 31487`；法二：`pgrep -n -x sleep` 找回它（或 `pgrep -f 'sleep 43'`）再杀。`fg` 同样查表翻译作业号，表里没人它就报「不是作业」；即使你知道 PID 也拉不回前台，因为 `fg` 依赖 Shell 持有这个作业的记账。教训：`disown` 前把 PID 抄进日志或 pidfile，是本节账本分工的直接工程后果。
:::
:::

::: think 思考 · 作业表为什么不进内核
内核只需要知道两个号（`pgid`、`sid`）就能完成投递；而「哪个作业带 `+`、作业号怎么排、退出时通知谁」全是人机交互的记账，换个 Shell（zsh、fish）就换套习惯。把这本账留在用户态，内核接口保持最小——代价就是我们刚验证过的：换个 Shell 进程，`jobs` 立刻失忆。写自己的 Shell（项目 D1 的 `mysh`）时，作业表、`+`/`-` 规则、退出通知都得自己实现， POSIX 只约定这张表该长什么样。
:::

::: errata 常见错误清单（0.9.4 节）
1. **「`&` 一定让命令进新进程组」**——只有作业控制开着才建组；非交互脚本实测子进程与 bash 同号（PGID 31332 对 PID 31335），整组信号会连坐脚本自己。
2. **「`jobs` 能看见系统里所有后台进程」**——只见当前 Shell 作业表里的行；子 Shell、另一个终端、cron 起的进程都不在其中（实测子 Shell 输出为空）。
3. **「`disown` 让进程脱离终端」**——实测 disown 后 `SID`/`TT` 不变；它只改 Shell 的退出通知名单。脱离终端的是 `setsid`（实测 `TT=?`、`Ss`）。
4. **「`kill %1` 和 `kill 24711` 是一回事」**——前者要查表，表没了报 `no such job`（实测）；后者不查表，但只打那一个 PID，不是整组。
5. **「`bg` 之后肯定能跑下去」**——被 `SIGTTIN` 停的作业若继续读终端会再停；先给它 `</dev/null` 或改数据源。
6. **「`nohup`/`disown -h` 防的是同一件事」**——`nohup` 改进程自身的信号处置，`disown -h` 改 Shell 的记账；终端真挂断时，组织关系没变的那个还得靠前者挡（对照 0.2.6）。
:::

::: method 判定流程 · 让后台任务扛住断线，逐层查
1. 第一层防「抢键盘」：它的 stdin 还连着终端吗？后台一读就 `SIGTTIN` 停（0.9.2 实测）。解法 `</dev/null` 或换数据源。
2. 第二层防「挂断通知」：进程自己听不听 `SIGHUP`（`nohup`/`trap '' HUP`）、Shell 的名单里还有没有它（`disown -h`）。两层任选其一即可免死，但组织关系照旧。
3. 第三层换组织：彻底不挂这个终端——`setsid`（实测 `Ss`、`TT=?`）、tmux（会话在服务进程里）、`systemd-run`（连记账和整组终止都替你管，见 0.9.11 与 0.9.13）。
4. 事后验收：`ps -o pid,sid,tty,stat -p PID` 三个号对一遍；`jobs` 里在不在，取决于你想不想继续用 Shell 管它。
:::

### 0.9.4 小结

`&`/`jobs`/`kill %1`/`disown` 全在 Shell 进程内存的作业表上记账，`fg`/`bg` 才碰内核（`tcsetpgrp` + `SIGCONT`）；`nohup`、`disown -h`、`setsid` 分别防在信号处置、Shell 名单、组织关系三层。如果只记住一件事，那就是：**作业号只在这一个 Shell 的账本里有效——先分清你在翻账本还是在动进程。**

::: method 即时自测 · 0.9.4
**Q1（记忆）** `jobs -l` 打印的是 PID 还是 PGID？想拿组号该用什么命令？

**Q2（辨析）** `disown -h %1` 与 `disown %1` 之后，`jobs` 和 `kill %1` 各是什么结果？

**Q3（应用）** 脚本里 `make -j8 &` 后想超时整组终止，却发现 `kill -- -$!` 杀不到它的子 make。用 `set -m` 的实测差别解释原因并给修法。

**Q4（迁移）** 你在 macOS 用 `jobs -l` 看到的管道输出与 Ubuntu 一致吗？这个一致性说明作业表格式由谁定义？

::: sol 答案
**A1** PID——每个成员一行（实测 bash 5.2.21 与 3.2.57 都如此），不打印 PGID；组号要用 `ps -o pid,pgid -p PID` 取。
**A2** `-h` 后作业仍列在 `jobs` 里、`kill %1` 可用，只是退出时 Shell 不给它发 `SIGHUP`；不带 `-h` 从表里删行，`jobs` 不再列它，`kill %1` 报 `no such job`（实测），进程本身两种情况都活着。
**A3** 非交互脚本默认不开作业控制，`make &` 与脚本同组（实测 PGID=31332≠PID 31335），`$!` 只是个成员 PID，负组号打不到「make 自己开的组」——make 会再 fork 子进程，都在脚本组里。修法：脚本开头 `set -m`（实测后台命令自组成组），或让 make 进独立会话 `setsid make -j8 &`，然后对组长 PID 取负号发信号。
**A4** 一致：两家 `jobs -l` 都是「作业号 + 状态 + 每成员 PID + 命令行」（实测对比 24711/24712 与 17024/17025）。这说明作业表格式是 Shell（bash）的用户态实现约定，POSIX 只规范 `jobs` 应报告作业号与状态，不经过内核，所以跨平台同版本族行为接近。
:::

## 0.9.5 信号：先 TERM，再 KILL {#sec-0.9.5}

这一节回答：`kill` 默认发的为什么是 TERM 而不是 KILL？「放过一杀」到底跳过了什么？两台机器上信号编号哪里对不上？信号会不会丢、会不会排队？

::: preview 先抓住一件事
`SIGTERM` 可以被捕获、被阻塞、被忽略——程序通常就是靠它完成善后：刷缓冲区、删锁文件、注销端口。`SIGKILL` 捕获不了也挡不住，内核直接回收进程，善后必然被跳过。「先 TERM 再 KILL」不是胆小，是给对方一轮结算的机会；KILL 只是把宽限期收回来。
:::

### 0.9.5 场景：同一个脚本，两种死法

先准备 `slow.sh`，它给 TERM 和 INT 安装处理器（handler，程序自己写的信号处理函数），把信号翻译成可见的输出和约定的退出码：

```bash
#!/usr/bin/env bash
trap 'echo "TERM at $(date +%T)"; exit 143' TERM
trap 'echo "INT  at $(date +%T)"; exit 130' INT
echo "pid=$$"
while :; do sleep 1; done
```

先跑一遍再解释。Ubuntu 24.04 实测（非交互 bash 里用 `wait` 结算退出码）：

<div class="terminal" data-title="bash · Ubuntu 24.04 实测">
<pre><span class="p">&#36;</span> ./slow.sh &amp; p=$!
pid=15811
<span class="p">&#36;</span> kill -TERM $p; wait $p; echo "TERM-rc=$?"
TERM at 20:35:46
TERM-rc=143
<span class="p">&#36;</span> ./slow.sh &gt;/dev/null &amp; q=$!
pid=15819
<span class="p">&#36;</span> kill -9 $q; wait $q; echo "KILL-rc=$?"
bash: line 18: 15819 Killed                  ./slow.sh &gt; /dev/null
KILL-rc=137
<span class="p">&#36;</span> timeout -s TERM -k 2 3 sleep 30; echo "timeout-rc=$?"
timeout-rc=124
</pre>
</div>

逐行读：TERM 被 `trap` 接住，脚本先打印一行、再自己退出 143（128+15：「被信号终结」的退出码约定，0.9.6 细讲它怎么被 `wait` 取到）；KILL 一行输出都没留下，bash 事后报一句 `Killed`，而它循环里 fork 的那个 `sleep` 并没有陪葬——这是「KILL 不管子孙」的第一课。`timeout -s TERM -k 2 3` 是纪律的现成形态：先 TERM、宽限 2 秒、不死才 KILL，`timeout-rc=124` 是 timeout「确实超时过」的专码。macOS 默认没有 GNU `timeout`，这段以 Ubuntu 口径为准。

::: def 定义 0.9.5 · 信号（signal） {#def-0.9.5}
信号是内核投递给进程的异步通知：硬件异常、终端驱动、别的进程调 `kill(2)`、内核自己，都可能成为发送方。Linux 的标准信号编号 1–31，实时信号 34–64（编号随实现浮动，代码里只写 `SIGRTMIN+x`，排队语义见 0.9.10）。大多数信号可以被捕获、阻塞或忽略，唯独 `SIGKILL`(9) 和 `SIGSTOP` 既不能捕获也不能阻塞——投递路径上内核直接办掉，不经进程的手。shell 的 `kill` 命令只是 `kill(2)` 的包装，默认发 `SIGTERM`(15)，这是 POSIX 规定的。
:::

### 0.9.5 机制：默认处置、编号与排队

没装处理器时，每个信号走五条预设路径之一——这就是「默认处置」（default disposition）：

| 默认处置 | 效果 | 代表信号（Linux 编号见下一张表） |
|:--|:--|:--|
| 终止（Term） | 直接退出，不产生 core | `SIGHUP` `SIGINT` `SIGTERM` `SIGPIPE` `SIGUSR1` `SIGUSR2` |
| 终止并 core（Core） | 退出并留内存现场，供调试 | `SIGQUIT` `SIGABRT` `SIGSEGV` `SIGBUS` `SIGFPE` `SIGILL` `SIGTRAP` |
| 停止（Stop） | 挂进停止队列，可恢复 | `SIGSTOP` `SIGTSTP` `SIGTTIN` `SIGTTOU` |
| 继续（Cont） | 唤醒停止中的进程 | `SIGCONT` |
| 忽略（Ign） | 默认视而不见 | `SIGCHLD` `SIGWINCH` `SIGURG`；`SIGCONT` 打在未停止的进程上也是忽略 |

工程读法：Term 一族的「优雅退出」全靠程序自己兑现承诺，这就是 0.9.11 脚本里 `trap` 存在的理由；Core 一族终止的同时留下现场（`ulimit -c` 管它多大，0.9.8）；Stop/Cont 正是 0.9.3 的 `T` 状态和作业控制背后那对按钮。

编号不是全球通用的。两台机器上 `kill -l` 实测（Linux 侧为 aarch64 Ubuntu 24.04，macOS 为 Darwin 27.2）：

| 信号 | Linux（x86 与 aarch64 实测一致） | macOS（BSD） |
|:--|--:|--:|
| `SIGHUP` `SIGINT` `SIGQUIT` `SIGKILL` `SIGTERM` `SIGALRM` `SIGPIPE` | 1 2 3 9 15 14 13 | 相同 |
| `SIGUSR1` / `SIGUSR2` | 10 / 12 | **30 / 31** |
| `SIGSTOP` | **19** | 17 |
| `SIGTSTP` | 20 | **18** |
| `SIGCONT` | 18 | **19** |
| `SIGCHLD` | 17 | **20** |
| 实时信号 | 34–64（`SIGRTMIN`–`SIGRTMAX`，`kill -l` 列出） | `kill -l` 不列（BSD 另有一套） |

名字是 POSIX 的，号码是各家的：同一句 `kill -17`，Linux 上不可撤销地停止进程，macOS 上发的是默认忽略的 `SIGCHLD`——等于没打。结论只有一条：**脚本与文档只用名字，永远别用裸数字**。

标准信号不排队，实时信号排队还带值。下面这个 C 程序（`cc -std=c17 -D_GNU_SOURCE -Wall -Wextra -O2 -g` 可编译）先阻塞 `SIGUSR1` 与 `SIGRTMIN`，趁阻塞连发 5 个 USR1、再用 `sigqueue(3)` 带值连发 5 个 RTMIN，解除阻塞后结算：

```c
sigprocmask(SIG_BLOCK, &set, NULL);          /* set = USR1 + RTMIN */
for (int i = 0; i < 5; i++) raise(SIGUSR1);
for (int i = 1; i <= 5; i++) {
    union sigval v = { .sival_int = i };
    sigqueue(getpid(), SIGRTMIN, v);         /* 实时信号：带一个 int */
}
```

<div class="terminal" data-title="Ubuntu 24.04 实测 · 5 次 USR1 vs 5 次 sigqueue">
<pre>while blocked, pending: USR1=1 RTMIN=1
  RT delivery 1: si_value=1
  RT delivery 2: si_value=2
  RT delivery 3: si_value=3
  RT delivery 4: si_value=4
  RT delivery 5: si_value=5
5 raises of SIGUSR1 -> handler ran 1 time(s)
5 sigqueue of SIGRTMIN -> handler ran 5 time(s)
</pre>
</div>

读这段输出：等待集合（pending set）只是一张位图，同一标准信号阻塞期间来一百次也只占一位，内核记「来过」不记「来过几次」——5 个 USR1 解除阻塞后只结算 1 次；实时信号进队列，5 次投递各带各的 `si_value`，先发的先到。所以「有 N 个任务要处理」这类计数通知必须用实时信号，用 USR1 会静默合并。两个补充口径：即使不阻塞，发送快过调度也会合并；能排队的实时信号个数受 `RLIMIT_SIGPENDING` 约束（`ulimit -a` 的 `-i`，0.9.8），超了 `sigqueue` 返回 `EAGAIN`。

停止这一族要和作业控制对上号：`SIGSTOP` 与 `SIGTSTP` 走同一个默认处置（Stop），区别在于 TSTP 可捕获可忽略、STOP 不能——`Ctrl-Z` 是 TSTP，程序可以拒停，`kill -STOP` 才是不可拒绝的暂停（0.9.3 实测：对孤儿进程组 TSTP 会被内核忽略，STOP 立刻 `T`）。停在 `T` 的进程收 TERM 不立刻结算，要等 `SIGCONT` 的当口执行掉（0.9.3 实测退出码 143）——这就是「先 TERM 再 KILL」对付暂停进程时也要留宽限期的原因。`nohup` 则常被说成「屏蔽 SIGHUP」，它是把处置设成忽略（`SIG_IGN`）：阻塞只是推迟，信号留在 pending 集合里，哪天解除掩码当场补刀；忽略才是当场丢弃，永不补刀（忽略可跨 `exec` 保留，0.9.10 讲机制）。

投递对象的三种写法——发之前先记住 0.9.2 的组号规矩：

```bash
kill "$pid"                # 默认 SIGTERM，只打这一个进程
kill -TERM -- -"$pgid"     # 打整个进程组；-- 防止负号被当成选项
kill -0 "$pid"             # 不投递，只测「进程在、且你有权限给它发」
```

`kill -0` 返回 0 不代表进程健康：僵尸同样返回 0（还没被收尸，0.9.6）；从「确认存在」到「动手」之间 PID 可能已被复用，绑定身份要靠 `/proc/PID/stat` 第 22 字段 `starttime` 或 `pidfd`（0.9.7）。名字匹配一族同理：`pkill -f backup.sh` 匹配的是整条命令行，你的编辑器、SSH 会话里都可能出现同一串，先 `pgrep -af` 核对名单再发；`-x` 比的是截到 15 字符的 `comm`（0.9.1），长名字会漏。

停一棵进程树的标准顺序是「整组 TERM → 有界等待 → 整组 KILL」：

```bash
stop_tree() {
    local pid=$1 sig=${2:-TERM} i
    kill -"$sig" -- "-$pid" 2>/dev/null || kill -"$sig" "$pid" 2>/dev/null || return 1
    for i in {1..20}; do
        kill -0 "$pid" 2>/dev/null || return 0
        sleep 0.5
    done
    kill -KILL -- "-$pid" 2>/dev/null || kill -KILL "$pid" 2>/dev/null
    return 1
}
```

先用负 PID 打整个进程组，组不存在时退回单 PID；最多等 10 秒；还不死才 KILL，并返回 1 让调用方知道「这是强杀的」。`kill -0` 对僵尸仍返回 0，所以这个函数假设调用方会 `wait` 或在 service manager 里运行；生产版（加 `starttime` 身份校验、把 `Z` 判成已停）在 0.9.11 给全。

`kill -9` 跳过什么，值得逐条钉住：**不执行清理**（临时文件、锁文件、socket、数据库连接都不释放，数据库下次启动可能要做崩溃恢复）；**对 `D` 状态无效**（信号挂起，等 I/O 返回才死，NFS 失联时可能等到天荒地老，0.9.3）；**杀不掉内核线程**（`ps` 里方括号的 `[kworker/...]` 没有用户地址空间）；**不保证子进程一起死**（上面实测 `Killed` 之后 `sleep` 仍在，孤儿会被收养继续占端口，0.9.6）；**PID 可能被复用**（先检查再杀存在竞态，用 `pidfd` 或 cgroup 绑身份）。

::: ex 例 0.9.5 · 一个监听 8080 的服务，两种死法 {#ex-0.9.5}
先猜：同一个端口上的两种「死法」，分别对应什么状态与信号？

服务进程持有 `/var/tmp` 下的临时目录和一个锁文件，监听 8080。先 `kill -9` 和先 `kill -TERM`，第二天各会遇到什么？
::: sol 解答
TERM 走进处理器：刷日志、删锁文件、关监听套接字，按约定退出（常见 143，也可以自报 0）；端口干净释放，`ss -lptn` 查不到残留。KILL 是内核当场回收地址空间：锁文件和临时目录留在盘上，8080 可能被没陪葬的子进程继续持有（上面实测 `Killed` 之后 `sleep` 还活着），下次启动先跟脏现场搏斗一遍，数据库类进程还可能被迫做崩溃恢复。两次都「死了」，只有后一种算下线。所以工程纪律是 TERM 加有界等待，KILL 只是兜底，且兜底之后要替程序补查它没来得及清理的现场。
:::
:::

::: errata 关于信号的六个误解（0.9.5 节）
1. **「`kill` 就是杀死」**——默认发 TERM，对方可以拒、可以处理完再退；`kill` 的本义是「投递通知」。
2. **「`kill -9` 一定立刻生效」**——`D` 状态的进程要等内核 I/O 返回，信号只是挂起不是抢占；僵尸、内核线程它也管不着。
3. **「编号就是名字」**——两台机器实测号码不同（`kill -17`：Linux 是不可拒绝的 `SIGSTOP`，macOS 是默认忽略的 `SIGCHLD`），只用 `kill -TERM` 这类名字写法。
4. **「连发 USR1 对方数得过来」**——标准信号不排队，实测 5 发 1 收；计数语义要用实时信号，且排队量受 `RLIMIT_SIGPENDING` 约束。
5. **「`nohup` 屏蔽了 SIGHUP」**——它设的是 `SIG_IGN`（忽略，当场丢弃），不是阻塞（推迟结算）；且只动处置不动组织关系，进程仍挂原会话原终端（0.9.2 实测 `SID`、`TT` 未变）。
6. **「`Ctrl-Z` 发的是 `SIGSTOP`」**——是 `SIGTSTP`，可捕获可忽略，孤儿进程组里甚至被内核忽略（0.9.3 实测）；不可拒绝的停止只有 `kill -STOP`。
:::

::: method 判定流程 · 停一个外来进程，按序走
1. 先看是谁：`ps -o pid,ppid,pgid,etime,args -p PID`；名字匹配的操作先 `pgrep -af` 核对名单，再谈 `pkill`。
2. 有官方入口先用官方入口：`systemctl stop`、程序自己的 `stop` 子命令；都没有才轮到裸 `kill`。
3. `kill -TERM` 打整组（负 PGID），有界等待；期间 `kill -0` 盯梢，动手前用 `starttime` 验明没换人。
4. 到期未死才 `SIGKILL`；杀完复查端口（`ss -lptn`）、锁文件与孤儿子孙——这些正是 TERM 本来要交还给程序处理的东西。
:::

### 0.9.5 小结

TERM 是「通知并留善后机会」，KILL 是「内核当场回收、跳过一切善后」；默认处置五类划出谁能配合（Term 族可捕获）、谁能拒绝（TSTP）、谁完全不讲理（KILL/STOP）；编号 Linux 与 BSD 各一家，标准信号不排队。如果只记住一件事，那就是：**先给一轮有界的 TERM 结算期，到期再 KILL，KILL 之后还要替程序补查现场。**

## 0.9.6 僵尸、孤儿与 `wait` {#sec-0.9.6}

这一节回答：僵尸进程在内核里到底留了什么？为什么 `kill -9` 杀不掉它？父进程先死，孩子归谁管？`wait`、`waitpid`、`SIGCHLD` 三者怎么分工？

::: preview 先抓住一件事
子进程退出后不会立刻消失：内核回收它的内存页、打开的文件，只在进程表里留一条记录——PID、退出状态、资源用量——等父进程来取。这条记录就是僵尸；取走它的动作就是 `wait`。父进程先死了，孩子变成孤儿，由最近的 subreaper 或 PID 1 收养，PID 1 的本职就是替所有孤儿 `wait`。
:::

### 0.9.6 场景：真造一个僵尸，再让它销户

0.9.3 已经用 `Z` 讲过状态队列，这次把「怎么产生、怎么确认、怎么消灭」走完整。在 Ubuntu 24.04 上起一个「fork 出孩子后只睡觉、不 `wait`」的父进程：

<div class="terminal" data-title="bash · Ubuntu 24.04 实测">
<pre><span class="p">&#36;</span> python3 -c 'import os,time; p=os.fork(); os._exit(7) if p==0 else time.sleep(45)' &amp; par=$!
<span class="p">&#36;</span> kid=$(ps -o pid= --ppid $par | tr -d ' ')
<span class="p">&#36;</span> echo "parent=$par kid=$kid"
parent=17533 kid=17535
<span class="p">&#36;</span> ps -o pid,ppid,stat,comm -p $par -p $kid
    PID    PPID STAT COMMAND
  17533   17532 S    python3
  17535   17533 Z    python3
<span class="p">&#36;</span> grep -E '^(State|PPid)' /proc/$kid/status
State:	Z (zombie)
PPid:	17533
<span class="p">&#36;</span> kill -9 $kid; sleep 0.3; ps -o pid,stat -p $kid
    PID STAT
  17535 Z
<span class="p">&#36;</span> kill $par; sleep 0.5; ps -o pid,stat -p $kid
<span class="p">&#36;</span> echo $?
1
</pre>
</div>

五行连起来读：孩子已执行完 `_exit(7)`，所以 `ps` 给 `Z`、`State` 给 `zombie`；`kill -9` 之后纹丝不动——信号接收方是进程的执行上下文，而它已经不存在了，9 也一样；最后动的是父进程 17533，它一死，17535 被收养、被回收，`ps` 查无此人（返回码 1）。macOS 实测 `ps axo pid,ppid,stat,comm` 同样出 `Z`、命令行显示 `<defunct>`，只是没有 `/proc/status` 可对照。

::: def 定义 0.9.6 · 僵尸进程与孤儿进程 {#def-0.9.6}
**僵尸**（zombie）：已退出、但父进程尚未 `wait` 取走状态的子进程。内核释放它几乎全部资源，只保留进程表里一条记录（PID、终止状态、资源使用统计）和 `task_struct` 的尾巴；它不占内存页、不占 CPU，占的是一个 PID——够多时耗尽 `pid_max`，新进程就造不出来。**孤儿**（orphan）：父进程先退出、自己还活着的子进程，内核把它过继给最近的祖先 **subreaper**（设置了 `PR_SET_CHILD_SUBREAPER` 的进程，systemd 用户实例就是），没有则直接归 PID 1（init/systemd）；收养者有责任 `wait` 它。
:::

### 0.9.6 机制：取状态的动作叫 wait，通知取状态的是 SIGCHLD

**谁在收尸。** 上面 `kill $par` 之后僵尸秒消失，说明收养方手很快。孤儿到底被谁收养，可以拿一个「活得比父久」的孩子直接看（Ubuntu 24.04 实测：内层 bash 起了 `sleep 41` 后先退，1.2 秒后查户口）：

<div class="terminal" data-title="bash · Ubuntu 24.04 实测">
<pre><span class="p">&#36;</span> bash -c 'sleep 41 &amp; sleep 0.3' &amp; o=$!
<span class="p">&#36;</span> sleep 1.2; ps -o pid,ppid,stat,etime,args -C sleep | tail -1
  17776       1 S          00:01 sleep 41
<span class="p">&#36;</span> ps -p 1 -o pid,comm=
      1 systemd
</pre>
</div>

`PPID=1`：生父（17774，`kill -0` 已确认不在）没了，PID 1 接的户；这台机器的 PID 1 实测是 **systemd**，不是传统 init——收尸职责由它（以及它的用户实例 `systemctl --user`，一个 subreaper）承担，从 SSH 会话掉下来的孤儿直接归 1。这正是守护进程「双 fork」依赖的机制：老进程退出，孩子变孤儿、被收养，从此脱离终端的管辖关系，由收养者负责收尸——完整的守护化流程在 0.12 讲。顺带把 0.9.5 的坑闭环：`kill -9` 打死父进程，子孙不会陪葬，而是像这样被收养，继续占端口、继续写文件——这就是「KILL 不保证整棵树死干净」的下场。

**`wait` 家族怎么分工。** 三者是一组「收尸接口 + 通知机制」：`wait(&status)` 阻塞等任意一个子进程变化；`waitpid(pid, &status, options)` 能指定等谁、能 `WNOHANG` 不等、能 `WUNTRACED` 连停止一起收；`SIGCHLD` 是「孩子有动静」的门铃，默认处置为忽略。shell 的 `wait` 内建取的就是同一份终止状态——实测（Ubuntu 24.04）：正常结束 `wait` 得 0，被 `SIGKILL` 杀的孩子得 137，不是自己孩子的 PID 直接报错「is not a child of this shell」：

```bash
sleep 0.3 & wait $!; echo $?      # 0：正常退出
sleep 30 & kill -9 $!; wait $!; echo $?   # 137 = 128+9
```

写常驻服务时，正确姿势是「门铃 + 循环收尸」：给 `SIGCHLD` 装 handler，在 handler 里 `while (waitpid(-1, &st, WNOHANG) > 0)` 收干为止——细节、竞态与 `signalfd` 方案留 [2.7 进程创建与终止](../part2/ch07.md) 与 [2.8 程序执行与子进程监控](../part2/ch08.md)；0.9.10 讲「显式忽略 SIGCHLD」为什么能免掉僵尸。

**别把「默认忽略」当「自动回收」。** `SIGCHLD` 的默认处置是忽略，但僵尸照产生；把处置**显式**设成 `SIG_IGN`，Linux 才会让孩子退出时自动回收、不产僵尸。实测对照（Ubuntu 24.04）：`signal.signal(signal.SIGCHLD, signal.SIG_IGN)` 之后 fork 三个秒退的孩子，`ps --ppid` 列出的子进程数为 **0**——连 `Z` 行都没有。两条规则都要记住：显式忽略只保证不留尸，不保证你还能读到退出码；且 `SIGCHLD` 同属标准信号，连发会合并（0.9.5 实测），所以 handler 里必须循环 `waitpid`，而不是「一次信号收一个」。

**容器里的坑。** PID 1 拿到收养权就没有拒绝的余地：很多镜像的入口脚本不是合格的 init，子进程退出没人 `wait`，僵尸越积越多。修法是让 PID 1 换成会收尸的 `tini`/`dumb-init`，或 `docker run --init` 注入一个最小 init（第 5 篇细讲）。

::: ex 例 0.9.6 · `top` 里 zombie 计数的正确处理 {#ex-0.9.6}
先猜：`top` 显示的 zombie 数与 `ps` 为什么可能对不上？

监控显示某服务 `top` 头部 `28 zombie`，`ps -eo stat,pid,ppid | awk '$1 ~ /^Z/'` 列出 28 行的 PPID 都相同。按本节机制给出处理顺序：先查什么、动谁、别动谁。
::: sol 解答
先查那个共同的父进程：`ps -o pid,stat,wchan,etime,args -p PPID`——它是活着在睡（父进程失职不 `wait`），还是也堆在里面。处理方向只有两条：修父进程（让它执行 `wait`，比如发它能触发收尸的信号、或升级修复泄漏 `SIGCHLD` 处理的版本）；或者杀掉父进程，让 PID 1 收养并立刻回收——上面的实测走过这条路，僵尸秒清。别动的永远是僵尸本身：`kill -9` 对 `Z` 无效（实测），逐个「清理」是徒劳。28 条 `Z` 的即时危害是占 PID 不是吃内存，但父进程重启次数越多、堆得越快，`pid_max` 耗尽时全机造不出新进程。
:::
:::

::: errata 关于僵尸与孤儿的误解（0.9.6 节）
1. **「僵尸在偷吃内存」**——实测的 `Z` 不占内存页、不占 CPU，只占一条内核记录和一个 PID；它的危害是量大了耗尽 `pid_max`。
2. **「杀僵尸要趁早」**——信号对已退出体无效（实测 `kill -9` 后仍是 `Z`）；能动的只有父进程。
3. **「孤儿的 PPID 一定是 1」**——是「最近的 subreaper，否则 1」；systemd 用户会话里有些过继停在用户实例管理器上，判断时读 `/proc/PID/status` 的 `PPid`，别背数字。
4. **「SIGCHLD 默认忽略，所以不会有僵尸」**——默认忽略不等于显式 `SIG_IGN`，前者照样产 `Z`（实测），后者才自动回收；「我什么都没做怎么全是僵尸」的正是这条。
5. **「父进程 `wait` 一次就够了」**——`SIGCHLD` 会合并，多个孩子几乎同时退出可能只响一次门铃；handler 里要 `WNOHANG` 循环收干。
6. **「`kill -0` 返回 0 说明孩子还没退」**——僵尸存在期间 `kill -0` 照样成功；判断死活读 `stat` 第三字段或 `/proc/PID/status` 的 `State`。
:::

### 0.9.6 小结

僵尸是「已退出、等收尸」的内核登记，`kill -9` 对它毫无办法，销户只能靠父进程 `wait`；父进程先死，孤儿由 subreaper 或 PID 1 接管并回收。`wait`/`waitpid` 管取状态，`SIGCHLD` 管通知，显式 `SIG_IGN` 才能免产僵尸。如果只记住一件事，那就是：**看见 `Z`，力气永远花在父进程身上，不在僵尸身上。**

::: method 即时自测 · 0.9.6
**Q1（记忆）** 内核为僵尸保留哪三样东西？它的「默认门铃信号」是哪一个、默认处置是什么？

**Q2（辨析）** 「`SIGCHLD` 默认忽略」和「显式设成 `SIG_IGN`」行为差在哪？为什么 handler 里要循环 `waitpid`？

**Q3（应用）** 你的 `kill -9` 打掉了父进程，发现「监听端口还在、还有进程活着」。用本节机制解释并给出排查命令。

**Q4（迁移）** 容器里 `ps -eo stat | grep -c '^Z'` 一直涨。说出两条互不冲突的修法与各自原理。

::: sol 答案
**A1** PID、终止状态（退出码/致命信号）、资源使用统计，外加进程表里那条记录本身；门铃是 `SIGCHLD`，默认处置为忽略。
**A2** 默认忽略时孩子退出仍产生 `Z`（不通知）；显式 `SIG_IGN` 时 Linux 自动回收、不留 `Z`（实测子进程数 0）。因为标准信号会合并（0.9.5 实测 5 发 1 收），一次门铃背后可能是多个孩子，`WNOHANG` 循环才能收干。
**A3** 子进程不陪葬，被收养后继续持有 fd/端口（实测 `sleep 41` 过继给 PPID 1 还活着）。排查：`ss -lptn` 查端口持有 PID，`ps -o pid,ppid,pgid,etime,args` 顺藤——当初应该整组 TERM（负 PGID）而不是单点 KILL。
**A4** 其一，换 init：PID 1 用 `tini`/`dumb-init` 或 `docker run --init`，它们专职 `wait` 收尸；其二，修入口程序：主循环显式处理 `SIGCHLD` 并循环 `waitpid`。两条原理相同：僵尸消失的唯一途径是有人 `wait`。
:::
:::

## 0.9.7 进程树、`/proc` 与身份 {#sec-0.9.7}

这一节回答：`/proc/PID` 下面每个文件各回答哪个问题？它和 0.9.1 的 `ps` 怎么互证？拿到一个陌生进程，先看哪五个文件？一个 PID 怎么绑死成「身份」？`system()`、`popen()`、`exec` 家族各怎么把一个进程挂进这棵树？

::: preview 先抓住一件事
`/proc/PID` 不在磁盘上，是内核为每个进程现场生成的视图：读一个文件，内核就把那份信息现编出来。所以「ps 只是格式化视图」这句话的另一面是——`ps` 给不了的（开了哪些文件、跑的是哪个二进制、归哪个容器管），`/proc/PID` 全给，而且给的是原件。
:::

`/proc/PID` 是 procfs 为每个进程现场生成的目录：不占磁盘、`ls -l` 里大小多为 0、不能 `cp` 备份，每次 `open`/`read` 都由内核从进程自己的数据结构现取现编。`cmdline`、`environ` 这类条目以 NUL（`\0`）分隔字段，所以 `cat` 出来挤成一行，要用 `tr '\0' ' '` 或 `tr '\0' '\n'` 还原；`cwd`、`exe`、`fd/*` 是符号链接，链接目标就是答案本身。口径见 `proc(5)`，各文件的机器可读定义在 Kerrisk 第 12 章。
:::

### 0.9.7 机制：每个文件回答哪个问题

| 路径 | 回答的问题 | 读法与坑 |
|:--|:--|:--|
| `status` | 它是谁、活成什么样 | 人类可读汇总：`State`、`PPid`、`Uid/Gid/Groups`、`Threads`、`VmRSS`，还有信号六张位图（0.9.10） |
| `stat` | 同上，机器可读版 | 52 个空格分隔字段，`ps` 各列的出处（0.9.1）；第 2 字段 `comm` 可含空格括号，脚本别直接 `awk '{print $2}'` |
| `cmdline` | 用什么命令行启动 | NUL 分隔；**空文件 = 内核线程**，别当成数据丢失 |
| `exe` | 实际在跑哪个二进制 | 符号链接；程序被升级或删除后目标带 `(deleted)`——「升级了但旧进程还在跑」的直接证据 |
| `cwd` | 现在站在哪个目录 | 符号链接；相对路径、日志落哪、`rm` 删不掉的文件在谁手里，先看这里 |
| `fd/` | 开着哪些文件/socket/管道 | 每个 fd 一条符号链接；`lsof -p PID`、`ss -p` 是同一份账的三种视图 |
| `cgroup` | 归哪个 cgroup 管 | `0::/路径` 是 v2（0.9.9.1）；路径里的 `.service`/`.scope` 决定「该用 systemctl stop 还是裸 kill」 |
| `limits` | 当前软/硬资源限制 | 四列：名称、软、硬、单位（0.9.8 展开） |
| `environ` | 启动时的环境变量 | NUL 分隔；只有同真实 UID 或特权可读，查 `PATH`、代理、注入配置 |

身份那行 `Uid: 1000 1000 1000 1000` 不是打印四遍：四个数依次是**真实 UID、有效 UID、保存集 UID、文件系统 UID**（Gid 同理），普通进程四值相同；setuid 程序会让第一、二个分开（0.4 的凭证模型在这里落地，C API 与 capability 归 [2.9 进程凭证](../part2/ch09.md)）。`Groups` 是补充组号，决定 ACL 里「某个人」能不能进门（0.4.6）。`kill`/`nice` 能不能碰到别人，比的正是这些号：不同 UID 发信号会 `kill: Operation not permitted`，这不是 PID 错，是身份不对。

PID 会被复用（0.9.1 的教训），一个数字绑不死身份。三条升级路：记 `/proc/PID/stat` 第 22 字段 `starttime`（开机后滴答数，PID+starttime 近似唯一）；用 `pidfd_open(2)`（Linux 5.3+）拿一个「指向这个进程」的 fd，复用也不会认错；容器/systemd 时代直接拿 cgroup 路径当编制——systemd 和容器运行时都是这么管的（0.9.9.1）。`status` 里那个 `NSpid` 则是命名空间视角的 PID 序列：进程穿过几层 PID 命名空间就列几个号，从外到内；宿主机看容器里的服务是一个大 PID，进容器 `ps` 看是 1——同一个进程的两张户口。本机的单次实测里它只有 `18448` 一个值（没套命名空间），嵌套视角需要在容器环境复现。

看「谁启动了谁」本身：`pstree -ap`（属 `psmisc`，本机实测可用）按父子缩进、`-p` 带 PID、`-a` 带命令行；默认会压缩同名兄弟进程，`-c` 关闭压缩。已经用 `ps` 筛过列时，`ps --forest` 补看层级更顺手——同一条 SSH 链路在 `ps -eo pid,ppid,user,args --forest` 里的样子（Ubuntu 24.04 实测，只截必要几行）：

<div class="terminal" data-title="ps --forest · Ubuntu 24.04 实测">
<pre>   1592       1 root     sshd: /usr/sbin/sshd -D [listener] 0 of 10-100 startups
 355596    1592 root      \\_ sshd: juanwang [priv]
 355645  355596 juanwang  |   \\_ sshd: juanwang@notty
 355646  355645 juanwang  |       \\_ bash -s

缩进就是 `ppid` 关系的另一种画法：`bash -s` 挂在 `sshd: juanwang@notty` 下，`sshd` 又挂在监听进程 1592 下——一次 SSH 登录为什么「杀了 shell 孩子还在」，看这棵树就明白（0.9.6 的收养规则在树的上半段等着）。

### 0.9.7 机制（续）：进程是怎么被「挂」进这棵树的——`exec` 家族、`system()`、`popen()`

`fork()` 复制一个进程，`exec` 家族把复制体换成新程序；从 `fork` 到 `exec` 之间那一刻，就是「新进程出生」的瞬间。C 里替你走完全程的还有两个高层函数：`system()` 执行一条 shell 命令字符串，`popen()` 再挂上管道把命令输出接成 `FILE*`。四列对比先立骨架，语义细节在 [2.7 进程创建与终止](../part2/ch07.md) 与 [2.8 程序执行与子进程监控](../part2/ch08.md)：

| 入口 | 进程数变化 | 经过 shell？ | 返回值含义 | 参数怎么传 |
|:--|:--|:--|:--|:--|
| `execl()` / `execlp()` / `execle()` | 0，原地变身 | 否 | **只在失败时返回 -1** 并设 `errno`；成功就回不来 | 可变参数列表逐个列（`l`），`p` 后缀查 `PATH`，`e` 后缀自带环境 |
| `execv()` / `execvp()` / `execvpe()` | 0，原地变身 | 否 | 同上 | `argv[]` 数组（`v`），程序里已有参数数组就用它 |
| `execve()` | 0，原地变身 | 否 | 同上 | `argv` + `envp` 两个数组；**Linux 唯一的 exec 真系统调用**，上面全是 libc 包装 |
| `system()` | +2 起步（一个 `sh`，加它执行的命令） | 是，`/bin/sh -c` | shell 的 wait 状态：用 `WIFEXITED`/`WEXITSTATUS` 拆；-1 表示连 shell 都没起成 | 一整条命令行字符串，重定向、通配、管道都由 shell 解释 |
| `popen()` | +2 起步 | 是 | 返回读/写 `FILE*`；终止状态要 `pclose()` 才拿到 | 字符串命令 + 模式 `"r"`（读其 stdout）或 `"w"`（喂其 stdin） |

证据比表格可信。`lab0c09_b11.c` 依次调 `system("echo from-system")`、`popen("echo from-popen","r")`、`execl("/bin/echo", ...)`，`strace -f -e trace=process` 跟踪（Ubuntu 24.04 实测，摘录主干）：

<div class="terminal" data-title="strace · Ubuntu 24.04 实测">
<pre>18769 clone3({flags=CLONE_VM|CLONE_VFORK|CLONE_CLEAR_SIGHAND, exit_signal=SIGCHLD}, 88) = 18770
18770 execve("/bin/sh", ["sh", "-c", "--", "echo from-system"], ...) = 0
18769 wait4(18770,  ...) = 18770
18769 clone3({flags=CLONE_VM|CLONE_VFORK|CLONE_CLEAR_SIGHAND, exit_signal=SIGCHLD}, 88) = 18771
18771 execve("/bin/sh", ["sh", "-c", "--", "echo from-popen"], ...) = 0
18769 execve("/bin/echo", ["echo", "from-execl"], ...) = 0
18769 exit_group(0)                     = ?
</pre>
</div>

读法：`system()` 与 `popen()` 都是「`clone` 出子进程 → 子进程 `execve` 了 `/bin/sh -c "…"` → 父进程 `wait4`」——shell 参与就体现在那一行 `execve("/bin/sh", ...)`；而 `execl` 只有一行 `execve("/bin/echo", ...)`，PID 仍是 18769——没生进程，是本人变身。还有个反直觉细节：这次运行里主程序自己的 `printf` 行一条都没落盘——`execl` 成功后地址空间整个换掉，没冲刷的 stdio 缓冲（stdout 接管道时是全缓冲）随旧程序陪葬；exec 前要么 `fflush(stdout)`，要么本就不该指望它。

工程边界两条。第一，`system("backup.sh " + 用户输入)` 等于把字符串交给 shell 解释，`;`、反引号、`$()` 全生效——要执行固定程序就直连 `execvp`（不经 shell，参数按数组边界传）；非用 shell 特性不可时，变量整体用单引号围起来并转义内部引号。第二，`system()` 在等孩子的这段时间会代为推迟 `SIGINT`/`SIGQUIT`（到子进程结束才恢复；`popen()` 没有这条约定），写交互程序时这是特性也是坑。

::: ex 例 0.9.7 · 凌晨三点的高 CPU 陌生进程 {#ex-0.9.7}
先猜：先看它的 CPU，还是先确认它是被谁拉起来的？

告警说某台机器 CPU 打满，`top` 指着一个你从没见过的高占用进程，你手里只有普通用户权限。按本节给出排查顺序：五个文件各回答什么，什么时候该转 `lsof`，什么时候根本不该你动手。
::: sol 解答
顺序走：① `status`——`State` 是不是 `R`、`PPid` 谁生的它、`Uid` 以谁的身份在跑、`VmRSS` 什么量级；② `cmdline`（空就是内核线程，别杀）加 `exe`——完整命令 + 真身二进制，带 `(deleted)` 说明版本早换了、旧进程赖着没重启，该做的是重启服务而不是杀进程；③ `cgroup`——`0::/...` 路径里的 `.service`/`.scope`/容器 ID 直接决定处置权归属：归 systemd 服务的，正确动作是 `systemctl stop`（0.9.5 判定流程第 2 步），归别人业务容器的，找 owner；④ 要查「它还占着什么端口/文件」再上 `lsof -p`（与 `fd/` 同一份账，展示更全）；⑤ `cwd`——判断它相对路径写文件写到哪。全程只读不写；真要动手时把 PID 配 `starttime` 再核一遍——告警到现在过去二十分钟，PID 未必还是当时那个。
:::
:::

::: errata 关于 `/proc` 与进程身份的误解（0.9.7 节）
1. **「`/proc/PID/x` 是真文件，能备份」**——读时由内核现生成，`ls` 里大小常为 0，两次读就可能不一样。
2. **「`cmdline` 直接 `cat` 就行」**——NUL 分隔，`cat` 挤成一行还可能吞掉后续字段；标准姿势是 `tr '\0' ' '`。
3. **「`ps` 的 COMMAND 列就是完整命令行」**——默认 80 列截断、`comm` 截到 15 字符（0.9.1）；全文在 `args` 列或 `/proc/PID/cmdline`。
4. **「`exe` 永远读得到」**——内核线程没有 `exe` 且 `cmdline` 为空；不同真实 UID 的进程默认也不让你读，普通权限排障有天花板。
5. **「PID 可以当身份用」**——复用是随机发生的；长期记账必须配 `starttime`、`pidfd` 或 cgroup 路径。
6. **「`system()` 方便所以随便用」**——多两个进程只是小事，把用户输入拼进 shell 字符串是大事；固定程序用 `execvp`。
:::

::: method 判定流程 · 拿到陌生进程，先看这五个文件
1. `status`：`State`、`PPid`、`Uid/Gid/Groups`、`Threads`、`VmRSS`——「活成什么样、以谁的身份」。
2. `cmdline` + `exe`：怎么启动的、真身是哪个二进制、有没有 `(deleted)`；两者皆空 = 内核线程，绕开。
3. `cgroup`：归哪个 systemd unit/容器——决定「该谁动手、用什么命令停它」。
4. `fd/`（要更全就 `lsof -p PID`）：占着哪些文件与 socket——端口冲突、`device busy`、删不掉的文件都在这找。
5. `cwd` + `limits`：站在哪个目录（相对路径行为）、软/硬资源限制还剩多少（0.9.8 展开）。
:::

### 0.9.7 小结

`/proc/PID` 是内核的现场问答：`status` 答身份、`cmdline`/`exe` 答来路、`fd` 答占用、`cgroup` 答归属；`ps` 只是 `stat` 的格式化视图（0.9.1），原件在这里。进程入树靠 `fork`+`exec`，`system()`/`popen()` 是替你走全程、还附赠一个 `/bin/sh` 的高层包装——省事的代价是注入面和多出来的进程。如果只记住一件事，那就是：**先读五个文件再动手；处置权跟着 `cgroup` 走，身份跟着 `starttime`/`pidfd` 走，别跟着裸 PID 走。**

::: method 即时自测 · 0.9.7
**Q1（记忆）** 想确认「二进制已升级但旧进程还在跑」，读哪个文件、看什么特征？

**Q2（辨析）** `execve()` 与 `system()` 在「进程数变化」「是否经过 shell」「返回值含义」三项上各是什么？

**Q3（应用）** `ps` 里一个进程的 `PPID` 已经查无此人。你怎么判断它现在归谁收养、归哪个服务管？

**Q4（迁移）** 容器里 `ps` 只见 PID 1，宿主机上同一个进程 PID 是四位数。用什么字段对出这条「同名不同号」？为什么「在容器里 `kill 1`」和「在宿主机上 kill 那个大 PID」语义上可能指同一个进程？

::: sol 答案
**A1** `/proc/PID/exe`：符号链接目标带 `(deleted)`——跑着的还是旧 inode，盘上的已经换了。
**A2** `execve`：不增进程（原地变身）、不经 shell、成功不返回，只在失败时 -1+`errno`；`system()`：至少 +2 个进程（`sh` 加命令）、经 shell、返回 shell 的 wait 状态（-1 仅表示连 shell 都没起成）。
**A3** 读 `/proc/PID/status` 的 `PPid`——过继给了最近 subreaper 或 PID 1（0.9.6 实测 `PPID=1`）；服务归属看 `/proc/PID/cgroup` 的 v2 路径，`.service`/`.scope` 段直接点名 unit。
**A4** `status` 的 `NSpid` 按 PID 命名空间从外到内各列一个号（proc(5) 口径；本机单层，只见 `18448`，嵌套值需容器复现）。容器里的 1 和宿主机的大 PID 是同一进程的两张户口，所以两个动作打到的是同一进程——差别只在权限判定用哪层的凭证。
:::

这一节回答：nice 10 是「少拿一半 CPU」吗？普通用户调优先级的门在哪边？`chrt`、`taskset` 各动了什么、容器里为什么会骗你？资源限制的软硬两级怎么读、怎么继承、怎么改一个活进程？

::: preview 先抓住一件事
nice 是权重不是配额：数字越大份额越小，但份额永不为零。普通用户的优先级阀门只放行「让步」方向——nice 调大可以，凡「夺取」性质的动作（把 nice 往小调、换实时策略、抬高高用限制）全被权限挡着。资源限制分软（当前生效）硬（软的上限）两级，硬限制一旦调低，非特权进程终身升不回；`fork`/`exec` 都会原样继承这整套。
:::

### 0.9.8 场景：带负号的 nice 走到哪一步停

先起一个 `sleep` 把优先级让低，再试着往回调（Ubuntu 24.04 实测）：

<div class="terminal" data-title="bash · Ubuntu 24.04 实测">
<pre><span class="p">&#36;</span> nice -n 7 sleep 120 &amp; p=$!
<span class="p">&#36;</span> ps -o pid,ni,pri,stat,comm -p $p
    PID  NI PRI STAT COMMAND
  18908   7  12 SN   sleep
<span class="p">&#36;</span> renice -n 12 -p $p
18908 (process ID) old priority 7, new priority 12
<span class="p">&#36;</span> renice -n 2 -p $p
renice: failed to set priority for 18908 (process ID): Permission denied
</pre>
</div>

`STAT` 列读成 `SN`：`S` 在睡、`N` 标记 nice 大于 0（0.9.1 的修饰字母现场）。NI 从 7 到 12，「让步」一路绿灯；从 12 想调回 2，当场 `Permission denied`。启动时带负号同样过不去，两台机器都实测了，报错措辞各是各家的：

<div class="terminal" data-title="nice -n -1 · Ubuntu 24.04 与 macOS 27.2 实测">
<pre># Ubuntu 24.04（GNU coreutils）
$ nice -n -1 sleep 1
nice: cannot set niceness: Permission denied
$ echo $?
0

# macOS 27.2（BSD）
$ nice -n -1 sleep 1
nice: setpriority: Permission denied
</pre>
</div>

注意左边的退出码：GNU `nice` 报错之后**照样用原 nice 把命令跑了**，rc=0——脚本里只看返回码、不看 stderr，就会以为降过优先级。macOS 上 `chrt`、`taskset`、`prlimit` 这些 util-linux 工具根本不存在（`command -v` 实测为空），本节的调度与限制口径以 Linux 为准。

### 0.9.8 机制：nice 是权重，不是标签

普通调度类里，内核按**权重**分配 CPU，nice 值映射成权重（内核表 `sched_prio_to_weight[]`，相邻档按 1.25 倍递推）。几个锚点数字：

| nice | 权重 | 两个任务竞争时对手为 nice=0 时的 CPU 份额 |
|--:|--:|--:|
| -20 | 88761 | 98.9% |
| -10 | 9548 | 90.3% |
| 0 | 1024 | 50.0% |
| 5 | 335 | 24.6% |
| 10 | 110 | 9.7% |
| 19 | 15 | 1.4% |

两个普通任务竞争同一个 CPU，份额是 `w_i / (w_1 + w_2)`，不是「nice 每加 1 少 5%」：nice 0 对 nice 10 的权重比 1024:110 ≈ 9.3:1，前者拿约九成——0.9.14 实验三用 `/proc/PID/schedstat` 把这个比例量出来。「普通用户只能调高 nice」的上限由 `RLIMIT_NICE`（`ulimit -e`，本机实测 0，即完全不放行负值）决定；`fork` 的子进程继承 nice，`exec` 也保持——给一条 `tar | gzip` 管道设的 nice，会传给它生成的每个后代。

三条边界要分清。`nice` 只管 CPU 时间分配，不管磁盘带宽——I/O 优先级归 `ionice`（作用于块设备调度器，不限制网络）；要真正隔离 CPU、内存、I/O 总量，得用 cgroup v2（[5.3](../part5/ch03.md)），`nice`/`chrt` 都改不了它的配额。`taskset` 把进程钉在指定 CPU 上（本机实测 `taskset -c 0,1` 后 `taskset -pc` 显示 affinity list `0,1`；给自己进程钉一个本机不存在的核号会被内核当场拒绝——`taskset: failed to set pid X's affinity: Invalid argument`），常用于减少缓存迁移、复现 NUMA 问题，不是「性能优化开关」：钉得太窄会让进程和中断抢同一个核。改**别人** UID 的进程要特权，本机 `sudo` 不可用、未实测。容器里 `nproc`、`taskset -pc` 读到的是 **CPU 亲和掩码**，不是 `cpu.max` 配额——`nproc` 报 4 不代表你能跑满 4 核的账，这个误导的完整拆解在第 5 篇。

`ulimit` 的一个高频坑先钉住：**既不给 `-S` 也不给 `-H` 时，软、硬一起设**。`ulimit -n 512` 会把硬限制也压到 512，当前 shell 及其后代终身升不回去；只动软限制要写 `ulimit -S -n 512`。它约束的是本 shell 之后 `fork`/`exec` 出去的进程，对已经在跑的进程无效——改活进程用 `prlimit`，服务用 systemd 的 `LimitNOFILE=`。软硬两级的完整规则与实测在 0.9.8.3。

### 0.9.8.1 调度类：`nice` 管不到的另一种优先级 {#sec-0.9.8.1}

`nice` 只在普通调度类里调权重。同一个进程还可以被放进实时类、批处理类或空闲类，这些由 `sched_setscheduler(2)` 决定，`nice` 改不了。先看 `ps` 怎么显示，再用 `chrt` 读同一份数据（Ubuntu 24.04 实测，同一个 bash）：

<div class="terminal" data-title="bash · Ubuntu 24.04 实测">
<pre><span class="p">&#36;</span> ps -o pid,cls,rtprio,pri,ni,comm -p $$
    PID CLS RTPRIO PRI  NI COMMAND
  20471  TS       -  19   0 bash
<span class="p">&#36;</span> chrt -p $$
pid 20471's current scheduling policy: SCHED_OTHER
pid 20471's current scheduling priority: 0
<span class="p">&#36;</span> chrt -f 20 sleep 2; echo rc=$?
chrt: failed to set pid 0's policy: Operation not permitted
rc=1
</pre>
</div>

`CLS` 是调度类，`RTPRIO` 只在实时类里有值，`NI` 只在普通类里有意义。普通用户把 `SCHED_FIFO` 设到 20 会失败：既缺 `CAP_SYS_NICE`，`RLIMIT_RTPRIO`（`ulimit -r`，本机实测 0）也不放行。报错里的「pid 0」是 `chrt` 给「还没成功起起来的被包装命令」报的现场身份，读作「操作被拒」即可。

::: def 定义 0.9.8 · 调度类与静态优先级 {#def-0.9.8}
Linux 用 `task_struct` 里的 `sched_class` 选择调度器，用 `policy` 记录策略，用 `prio`/`normal_prio`/`static_prio` 记录优先级，用 `rt_priority` 记录实时优先级。普通类（`SCHED_OTHER`/`SCHED_BATCH`/`SCHED_IDLE`）由 nice 值映射到权重；实时类（`SCHED_FIFO`/`SCHED_RR`）用 1–99 的实时优先级；`SCHED_DEADLINE` 用 `(runtime, deadline, period)` 三元组做准入控制。
:::

| `CLS` | 策略 | 抢占与时间片 | 典型用途 | 设置方式 |
|:--|:--|:--|:--|:--|
| `TS` | `SCHED_OTHER` | 公平类，按权重分 CPU | 绝大多数进程 | `nice`/`renice` |
| `B` | `SCHED_BATCH` | 公平类，唤醒时更偏向吞吐 | 编译、批处理 | `chrt -b -p PID` |
| `IDL` | `SCHED_IDLE` | 只在 CPU 空闲时运行 | 后台 scrub、索引 | `chrt -i -p PID` |
| `FF` | `SCHED_FIFO` | 实时，无时间片，跑到阻塞 | 音频、机器人、IRQ 线程 | `chrt -f PRIO CMD` |
| `RR` | `SCHED_RR` | 实时，同优先级轮转 | 软实时、周期任务 | `chrt -r PRIO CMD` |
| `DLN` | `SCHED_DEADLINE` | EDF，按 deadline 调度 | 硬实时、带周期预算 | `chrt -d --sched-runtime ...` |

`SCHED_FIFO` 的进程一旦就绪就会一直跑，直到它阻塞、主动让出，或被更高优先级的实时任务抢占；它不靠时间片轮转。`SCHED_RR` 才有同优先级的时间片。把这两个设到高优先级而又写出死循环，会让同核上的普通任务完全得不到 CPU，表现为 SSH 卡死、看门狗报警。内核默认用 `sched_rt_runtime_us=950000`、`sched_rt_period_us=1000000` 给实时任务限流：每 1 秒最多跑 0.95 秒，超过就 throttled，`dmesg` 里出现 `sched: RT throttling activated`。

调度类的内核路径是：`sched_setscheduler(2)` → `__sched_setscheduler()`（`kernel/sched/core.c`）→ 选择 `rt_sched_class`/`fair_sched_class`/`dl_sched_class` → 写入 `task_struct->sched_class`、`policy`、`prio`。`sched_setscheduler` 的典型 `errno`：

| `errno` | 触发条件 | 处理 |
|:--|:--|:--|
| `EPERM` | 没有 `CAP_SYS_NICE`，或实时优先级超过 `RLIMIT_RTPRIO` | 用 root、加 capability，或调高 `ulimit -r` |
| `EINVAL` | 策略未知，或 `sched_param` 越界 | 用 `sched_get_priority_max/min` 取范围 |
| `ESRCH` | PID 不存在 | 先确认进程还活着，注意 PID 复用 |
| `EFAULT` | `param` 指针不可读 | 检查调用方地址空间 |

`chrt` 是这些调用的命令行包装，排障时先读、后写：

```bash
chrt -p "$pid"                    # 只看：策略与优先级
chrt -f 10 -p "$pid"              # 改成 FIFO，优先级 10（需要权限）
chrt -r 20 -p "$pid"              # 改成 RR
chrt -b -p "$pid"                 # 改成 SCHED_BATCH（-o 是 SCHED_OTHER）
chrt -i -p "$pid"                 # 改成 SCHED_IDLE
```

`chrt` 改的是单个线程，不是整棵进程树；多线程程序要对每个 TID 分别设置，或者在线程创建前用 `pthread_attr_setschedpolicy` 继承。`nice` 与 `chrt` 的分工可以用一句话记住：**nice 调权重，chrt 换队列**。两者都改不了 cgroup 的 CPU 配额，后者是 0.9.9.1 与第 5 篇的内容。

桌面环境还有一个容易忽略的变量：autogroup。开启 `CONFIG_SCHED_AUTOGROUP` 后，内核按会话/tty 把任务分组，`nice` 一个终端里的编译任务不会把另一个终端的 shell 饿死。本机实测可读：`cat /proc/$$/autogroup` 显示 `/autogroup-538 nice 0`；`setsid` 新建会话时也会新建 autogroup。`/proc/sys/kernel/sched_autogroup_enabled` 为 0 时退化成全局公平调度。

### 0.9.8.2 从 `/proc/PID/sched` 读出谁在等 CPU {#sec-0.9.8.2}

`ps` 的 `TIME` 是累计 CPU 时间，精度只到秒；要看一个进程是在跑还是在等，读 `/proc/PID/sched` 与 `/proc/PID/schedstat`：

```bash
# 三个数：累计运行 ns、在运行队列里等待 ns、获得时间片次数
awk '{printf "runtime=%.3fs wait=%.3fs slices=%d\n", $1/1e9, $2/1e9, $3}' /proc/$$/schedstat

grep -E '^(prio|nr_switches|nr_voluntary_switches|nr_involuntary_switches|se.sum_exec_runtime|se.avg.util_avg|se.avg.runnable_avg|se.avg.load_avg|clock-delta)' /proc/$$/sched
```

| 字段 | 含义 | 读法 |
|:--|:--|:--|
| `se.sum_exec_runtime` | 累计实际占用 CPU 的纳秒数 | 两次采样差值就是区间 CPU 时间 |
| `se.avg.util_avg` | PELT 平均利用率（0–1024） | 接近 1024 说明一直忙 |
| `se.avg.runnable_avg` | 可运行但未获得 CPU 的平均量 | 明显高于 `util_avg` 说明在排队 |
| `nr_voluntary_switches` | 主动让出 CPU 的次数 | 等 I/O、等锁、`sleep` |
| `nr_involuntary_switches` | 被调度器抢占的次数 | 高说明 CPU 竞争或时间片耗尽 |
| `clock-delta` | 调度时钟与任务时钟的差值 | 调试调度延迟，不用于判断 steal |
| `prio` | 动态优先级 | 与 `ps` 的 `PRI` 同源，跨机不可比 |

`nr_involuntary_switches` 是最容易被忽略的一项：一个进程「看起来不忙」但这项很高，说明它想跑却抢不到 CPU；反过来，`nr_voluntary_switches` 高而 `util_avg` 低，说明它大部分时间在等 I/O 或锁。把这两个计数和 `pidstat -w -p PID 1` 一起看，就能区分「CPU 不够」和「I/O 慢」。

`/proc/PID/stat` 的第 14–22 字段是另一组常用证据：`utime`、`stime`、`cutime`、`cstime`、`priority`、`nice`、`num_threads`、`itrealvalue`、`starttime`。字段按空格分隔，但第 2 字段 `comm` 可能含空格和括号，脚本里不能简单 `awk '{print $2}'`；从右往左数或先处理括号才安全。第 22 字段 `starttime` 在 0.9.7 已经用来绑定 PID 身份，这里补一句：`starttime` 的单位是时钟滴答，换算成秒要除以 `sysconf(_SC_CLK_TCK)`（通常是 100）；`/proc/uptime` 直接是秒（两位小数），不是滴答。

软硬两级的规则只有四条，每条都有对应的失败现场：**软限制是当前生效值**——fd 开爆返回 `EMFILE`、fork 失败返回 `EAGAIN`，报的都是软限制碰壁；**软限制可以自由调，上界是硬限制**——实测 `ulimit -S -n 2048` 顺利；**硬限制非特权只能调低、且不可逆**——实测 `ulimit -n 512` 之后再 `ulimit -n 1024` 得到 `bash: ulimit: open files: cannot modify limit: Operation not permitted`，想抬回去只有 root 或 `CAP_SYS_RESOURCE`；**注意裸 `ulimit -n` 软硬一起动**（本节开头钉过）。

继承规则是排障的关键：`fork` 与 `exec` 都**原样继承**软硬两级，setuid 程序也不例外——所以登录 shell 里设的限制会传给它启动的一切。实测链条：在 `ulimit -S -n 2048` 的子 shell 里后台起 `sleep`，读它的 `/proc/PID/limits`，拿到的正是 `2048 / 1048576`。这同时解释了 systemd `LimitNOFILE=` 的作用点：manager 在 fork 服务**之前**设好限制，优先于 shell 的历史值；服务改限额要 `systemctl edit` 加 `LimitNOFILE=` 再 daemon-reload 重启。对已经在跑的进程，读用 `cat /proc/PID/limits`，改用 `prlimit --pid PID --nofile=8192:8192`（改别人的要特权；改自己的受同一套软硬规则约束；`prlimit --pid PID` 不带赋值就是查表）。

1024 bytes (1.0 kB, 1.0 KiB) copied, 0.000259792 s, 3.9 MB/s
rc=1
$ ls -l lab0c09_f.bin lab0c09_f3.bin
-rw-rw-r-- 1 juanwang juanwang 1024 Oct 29 21:04 lab0c09_f.bin
-rw-rw-r-- 1 juanwang juanwang 1024 Oct 29 21:04 lab0c09_f3.bin
</pre>
</div>

两条路径正对着管道写关闭的另一组双路——`SIGPIPE`/`EPIPE`（0.9.10 细讲）：超限写文件的默认处置是 `SIGXFSZ`（本机编号 25，`kill -l XFSZ` 可查）终止进程——153 = 128+25；dd 那个 1 MiB 的第一块被截到限额的 1024 字节（上面 `ls` 的大小），下一笔写还没来得及做信号先到。把 XFSZ 忽略掉，`write()` 才把错误交回程序自己处理，返回 `EFBIG`（File too large），dd 报一行错、正常退 1——同一道限额，两种死法，全由处置决定。`-v`（`RLIMIT_AS`）不走信号路线：地址空间是分配调用当场拒绝，`ulimit -v 300000` 后 python 申请 400 MiB 得 `MemoryError`（退出码 1），申请 1000 字节照常成功——`malloc` 失败是返回值问题，不是信号问题。再加一条 `-t`：`ulimit -S -t 1` 跑死循环，软限制到点收 `SIGXCPU`（24，退出码 152）；不带 `-S` 把软硬一起设成 1，紧接着就是 `SIGKILL`，只看得到 137——先猜码再看 `kill -l`，这就是把 0.9.5 的「128+编号」约定用回到限额上的练习。

::: ex 例 0.9.8 · 代理服务的 `EMFILE` 该动哪一级 {#ex-0.9.8}
先猜：是调 `ulimit`、改 systemd 的 `LimitNOFILE`，还是先查 fd 泄漏？

一个反向代理跑了两小时崩溃，日志写 `Too many open files`。读它的 `/proc/PID/limits`：`Max open files 1024 1048576`。为什么限制长这样？现场怎么救、根治怎么做、为什么不建议直接 `ulimit -n 1048576`？
::: sol 解答
`1024 / 1048576` 是发行版的常见默认：软限制保守、硬限制宽裕——碰壁的是软级。现场救急：如果服务还活着，用 `prlimit --pid PID --nofile=65536:1048576` 把软的抬到硬以内（免特权改自己的进程改不动别人的，这里需要该进程的身份或特权；已在跑的进程 `ulimit` 无效，这正是 `prlimit` 的存在理由）——但新值只约束此后的 open，已泄漏的 fd 还得程序自己关。根治走 systemd：unit 里 `LimitNOFILE=65536`，`daemon-reload` 后重启服务，让 fork 前就带上正确继承值（上一段的作用点）。不建议一步拉到 1048576：每个 fd 背后是内核对象与内存，代理自身泄漏时大限制只会把「两小时崩溃」换成「两天 OOM」；先量规模（`ls /proc/PID/fd | wc -l`、`ss -s`），再给够用的数。
:::
:::

::: errata 关于优先级与资源限制误解（0.9.8 节）
1. **「nice 10 就是砍一半 CPU」**——权重制下 nice 0 对 nice 10 约 9.3:1，一半都远不到；比例可在 0.9.14 实验三量出来。
2. **「renice 对自己的进程想调哪边调哪边」**——只能往「让步」方向（调大 nice），调小当场 `Permission denied`（实测）；上限由 `RLIMIT_NICE` 决定。
3. **「`ulimit -n` 只改软限制」**——不带 `-S`/`-H` 时软硬一起改，改完连自己也升不回去（实测 `cannot modify limit`）；只动软的写法是 `ulimit -S -n`。
4. **「`ulimit` 改完，跑着的服务就受新值管」**——限制在 fork/exec 时继承，`ulimit` 只影响之后生成的进程；改活进程用 `prlimit`，服务用 `LimitNOFILE=` 后重启。
5. **「容器里 `nproc` 是能用的核数」**——那是亲和掩码不是 `cpu.max` 配额；配额归 cgroup，看 0.9.9.1 与第 5 篇。
6. **「`RLIMIT_RSS` 能限制内存」**——Linux 从未强制执行它；限内存要用 `RLIMIT_AS` 或 cgroup `memory.max`。
:::

::: method 判定流程 · 想动「这个进程用多少资源」，先分清三道闸
1. 权重闸（人人可让）：`nice`/`renice` 调大、`ionice` 调 I/O——只影响竞争时的相对份额，不设绝对上限。
2. 等级闸（要特权）：`chrt` 换调度类、nice 调小、抬硬限制——分别被 `CAP_SYS_NICE`+`RLIMIT_RTPRIO` 与 `CAP_SYS_RESOURCE` 把关；先 `ulimit -e/-r` 看自己有没有被放行。
3. 配额闸（要管理权）：cgroup 的 `cpu.max`/`memory.max` 才是绝对上限；排障入口是 `cat /proc/PID/cgroup` 找归属（0.9.9.1、第 5 篇）。
先问现象是哪种：竞争变慢（调 1）、被拒操作（查 2）、报错 `EMFILE`/`EAGAIN`/`SIGKILL`（读 3 与 `/proc/PID/limits`）。
:::

### 0.9.8 小结

nice 是权重不是配额，普通用户只走得进「让步」方向；调度类与实时优先级归 `chrt`/`CAP_SYS_NICE` 管，CPU 钉核归 `taskset` 但容器里会被 `nproc` 骗；资源限制软硬两级，裸 `ulimit` 软硬一起动、调低不可逆，`fork`/`exec` 原样继承。如果只记住一件事，那就是：**调优先级先分清「让步（免特权）」还是「夺取（要特权）」，查限额先读 `/proc/PID/limits` 再动 `prlimit`。**

**A1** 示例组合：`NOFILE`（`-n`，fd 上限，`EMFILE`）、`NPROC`（`-u`，同真实 UID 进程+线程数，fork `EAGAIN`）、`CORE`（`-c`，core 转储大小）、`CPU`（`-t`，CPU 秒，软限发 `SIGXCPU`）、`STACK`（`-s`，主线程栈）；其余如 `AS`/`FSIZE`/`MEMLOCK`/`SIGPENDING` 等见全表。

## 0.9.9 `ps` 与 `top`：字段、选项与排序 {#sec-0.9.9}

这一节回答：`ps` 那三套互不相认的语法各自怎么选进程、怎么排字段？`ps` 的 `%CPU` 和 `top` 的 `%CPU` 为什么能给同一个进程报出两个数？一个进程「归哪个 cgroup 管」这重身份上哪儿读？

0.9.1 已经给过 `pid/ppid/pgid/sid/tty/stat` 这几列的出处，也定了「脚本一律用 `-o` 点名列」的规矩；0.9.3 讲清了 `STAT` 首字母挂在哪个等待队列，0.9.7 讲清了 `/proc/PID` 那些文件。这一节把它们汇成两张可查的表（选择器、字段名），补上 `top` 的读法，再加上前面各节都没碰过的第四重身份：cgroup。

::: preview 先抓住一件事
`ps` 和 `top` 读的是同一份 `/proc`，差别在分母：`ps` 的 `%CPU` 是**这个进程从出生到现在**的平均，`top` 的 `%CPU` 是**两次刷新之间**的份额。实测一个「睡 25 秒、醒 4 秒」的进程，前者报 14.4%，后者三帧都报 100.0%，两边都没错。挑工具之前先问一句：我要的是历史总量，还是此刻。
:::

### 0.9.9 场景：同一个进程，两个 %CPU

先造一个「前 25 秒在睡、之后占满一核」的进程，再让两个工具各读它一次：

<div class="terminal" data-title="procps-ng 4.0.4 · Ubuntu 24.04 实测">
<pre><span class="p">&#36;</span> bash -c 'sleep 25; exec yes &gt;/dev/null' &amp; tgt=$!
<span class="p">&#36;</span> sleep 27; top -b -n 3 -d 1 -p "$tgt" | grep -E "^ *$tgt |^top -"
top - 21:13:58 up 49 min,  8 users,  load average: 2.10, 1.87, 1.50

top - 21:13:59 up 49 min,  8 users,  load average: 2.10, 1.87, 1.50
 368027 juanwang  20   0    2280   1168   1080 R 100.0   0.0   0:03.20 yes
top - 21:14:00 up 49 min,  8 users,  load average: 2.10, 1.87, 1.50
 368027 juanwang  20   0    2280   1168   1080 R 100.0   0.0   0:04.20 yes
<span class="p">&#36;</span> ps -o pid,pcpu,time,etimes,stat,comm -p "$tgt"
    PID %CPU     TIME ELAPSED STAT COMMAND
 368027 14.4 00:00:04      29 R    yes
</pre>
</div>

逐行读。`top` 三帧里 `%CPU` 都是 100.0，而 `TIME+` 从 0:02.20 涨到 0:04.20——一秒的帧间隔涨了一秒 CPU，说明它在这三秒里确实烧满一个核；`ps` 的 `TIME` 是 4 秒、`ELAPSED` 是 29 秒，4/29 ≈ 14%，正对上它的 14.4%：分母是这个进程的全部生命。

这里要修正一个流传很广的说法：`top -b` 的**首帧不是「自开机以来的累计值」**。本机实测首帧就是区间值（100.0），和后续几帧一致；为了「丢掉第一帧」而多跑一帧，在这台 procps-ng 4.0.4 上是白花钱。要的是区间份额就用 `top`/`pidstat 1`，要的是总量就看 `ps -o time,etime`——两个口径一起报，结论才站得住。

你可能还想问：`TTY` 那列为什么是 `?`，`STAT` 里为什么是 `R` 后面什么都没有了？前一列是「这个进程没挂控制终端」（后台脚本与守护进程都这样，`TPGID` 也跟着显示 `-1`）；后一列 0.9.3 讲过，`R` 含「正在跑」和「在运行队列里排队」两种情形，`top` 的 `R` 加上 100% 才是「真在跑」。

### 0.9.9 机制：三套方言、两张表

`ps` 的选项分成三套语法，混用时列的顺序会变，脚本里只应该用 `-o` 显式点名。下表是排障时真正会用到的部分，完整清单在 `man 1 ps` 的 `STANDARD FORMAT SPECIFIERS` 一节。

| 风格 | 写法 | 选择范围 | 输出特点 | 脚本可用性 |
|:--|:--|:--|:--|:--|
| UNIX | `ps -ef` | 所有进程 | `UID PID PPID C STIME TTY TIME CMD` | 字段固定，可解析 |
| UNIX | `ps -l` | 当前终端相关 | `F S UID PID PPID C PRI NI ADDR SZ WCHAN TTY TIME CMD` | 适合人看，不适合脚本 |
| BSD | `ps aux` | 所有进程 | `USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND` | `%CPU` 是平均值，别当瞬时值 |
| BSD | `ps axjf` | 所有进程 + 树 | 含 `PPID PGID SID TPGID` | 看进程组/会话方便（Linux 侧） |
| GNU 长选项 | `ps --ppid 1` | 按父进程筛 | 可与 `-o` 组合 | 只在 procps-ng 上有 |
| 自定义 | `ps -eo ...` | 任意 | 列由你决定 | 生产脚本首选 |

BSD 方言里 `-j`（job 格式）是 macOS 上唯一能一次拿到 `PGID` 的常用写法，实测表头是 `USER PID PPID PGID SESS JOBC STAT TT TIME COMMAND`——`SESS` 那列给的是会话结构地址，本机常年为 0，不能当会话号用（0.9.1 已实测过 `sid` 关键字不存在）。反过来，GNU 的长选项在 BSD 的 `ps` 上直接报错：`ps axjf` 在 macOS 实测 `ps: illegal option -- f`，`ps -eo pid --sort=pid` 实测 `ps: illegal option -- -`。结论和 0.9.1 一样：跨平台的巡检脚本只写 `-o` 点名列，别赌方言。

常用的选择器（谁进这张表）与修饰符（表怎么排、怎么印）：

| 选项 | 作用 | 注意（实测口径） |
|:--|:--|:--|
| `-e` / `-A` | 所有进程 | `-e` 与 BSD 的 `ax` 等价 |
| `-p PID` / `-q PID` | 指定 PID | `-q` 是「快速」模式，进程消失时不报错 |
| `--ppid PID` | 指定父进程 | 找「谁生的」比 `grep` 可靠 |
| `-u USER` / `-U USER` | 有效用户 / 真实用户 | 两者在 setuid 程序上不同 |
| `-t TTY` | 指定终端 | `-t ?` 选无控制终端的进程；macOS 上无 tty 跑 `ps t` 报 `ps: stdin: not a terminal` |
| `-C NAME` | 按命令名 | 名字来自 `comm`，不是完整命令行 |
| `-L` | 每个线程一行 | 配合 `-o lwp,nlwp` 看线程 |
| `-g PGID` | 按进程组选 | 与 `pgrep -g` 同一口径 |
| `-w` / `-ww` | 加宽 / 不限宽 | 见下面「宽度」一段 |
| `--forest` | 用缩进画父子 | 与 `-o` 组合时保留树形 |
| `--sort=KEY` | 排序 | `--sort=-%cpu,+pid`，负号降序；BSD 的 `ps` 不认（实测 `illegal option -- -`） |
| `-h` / `--headers` | 去表头 / 重复表头 | 长输出分页时用后者 |
| `-o FIELD=` | 给该列换表头或去掉表头 | `ps -o pid= -o comm=`；换名见下面的 `-o comm=NAME,args=CMD` |

`-L` 把线程摊开看，是判断「这一个进程吃了多少条线程」的唯一 `ps` 口径。起一个开 3 个线程的 Python，实测两种视图：

四行的 `PID` 都一样、`LWP` 各不同：`NLWP=4` 是这个进程组的线程总数，`lwp` 才是每行那个线程的 ID（内核视角叫 TID）。`STAT` 里的 `l` 就是「多线程」这个修饰字母（0.9.1 表里那一行）。`top` 不加 `-H` 只显示主线程那一行，加了才展开——排「线程数暴涨」的问题时，这两个开关的区别决定你能不能看出是谁在长。

`-o` 的字段名区分大小写，常用的这些值得背下来：

| 字段 | 含义 | 单位/格式 | 易错点 |
|:--|:--|:--|:--|
| `pid` / `ppid` | 进程 / 父进程 | 整数 | PID 会复用 |
| `pgid` / `sid` | 进程组 / 会话 | 整数 | 负 PID 发信号靠它 |
| `tty` / `tpgid` | 控制终端 / 前台组 | `pts/0`、`?` | `?` 表示无控制终端 |
| `stat` | 状态与修饰符 | `Ss`、`R+` | 第一个字母才是主状态 |
| `ni` / `pri` | nice / 优先级 | 整数 | `pri` 的基准随 ps 版本变，别跨机比较 |
| `psr` | 当前 CPU | 整数 | 迁移频繁时只能当采样 |
| `etime` / `etimes` | 已运行时间 | `[[DD-]hh:]mm:ss` / 秒 | 脚本用 `etimes` |
| `time` | 累计 CPU 时间 | `[[DD-]hh:]mm:ss` | 不是墙钟时间 |
| `vsz` / `rss` | 虚拟 / 常驻内存 | KiB | `vsz` 含未映射部分 |
| `wchan` | 等待的内核函数名 | 字符串 | 在跑或在睡的进程实测打印 `-`；有值时才说明它卡在哪个函数（0.9.3 用它定位 `D`/`T`） |
| `comm` / `args` | 命令名 / 完整命令行 | 15 字符 / 原样 | 两列的默认表头**都叫 `COMMAND`**，要区分就 `-o comm=NAME,args=CMD`；`comm` 会被截断 |
| `lwp` / `nlwp` | 线程 ID / 线程数 | 整数 | `-L` 才有意义（上面那段实测） |
| `pcpu` / `pmem` | CPU / 内存百分比 | 一位小数 | `pcpu` 是生命周期平均 |
| `cls` / `rtprio` | 调度类 / 实时优先级 | `TS`、`FF`、`RR` | 实时进程看这两个（0.9.8.1） |

先想清楚「宽度」这件事，因为老说法是错的。本机实测：把 `ps` 的输出接进管道（没有终端宽度），256 个字符的 `args` **整行照打，不会被截成 80 列**；只有显式限制宽度才会截——`COLUMNS=40 ps -o pid,args` 实测真的只给 40 个字符。真正永远被截的是 `comm`：内核常量 `TASK_COMM_LEN` 是 16（含结尾 NUL），所以用户态最多 15 个字符，实测把 `/bin/sleep` 复制成 `lab0c09_a_very_long_program_name_for_trunc_test` 再跑，`comm` 列就是 `lab0c09_a_very_`，而 `args` 列完整；`ps -C 长名字` 匹配的正是那个截断后的名字（0.9.1 的第 4 条误解）。所以脚本里的纪律是：要完整命令行用 `args` 并加 `-ww` 兜底（有些实现按终端宽度折行），认程序名用 `pgrep -a` 或 `/proc/PID/cmdline`，别赌 `comm`。

顺便记一条读表技巧：`comm` 与 `args` 的表头都是 `COMMAND`，两张表并排时眼睛会骗你——上面那条 `-o comm=NAME,args=CMD` 就是给自己换了名字再读。

`top` 的头部五行各有分工，读错行就会把「缓存」当成「泄漏」：

| 行 | 关键字段 | 怎么读 |
|:--|:--|:--|
| 第 1 行 | `load average: 1/5/15` | 可运行 + 不可中断任务数，不是 CPU 百分比 |
| 第 2 行 | `Tasks: ... running, ... sleeping, ... stopped, ... zombie` | `zombie` 非 0 要查父进程 |
| 第 3 行 | `%Cpu(s): us sy ni id wa hi si st` | `wa` 高是 I/O 等待，`st` 高是虚拟机被宿主抢占 |
| 第 4 行 | `MiB Mem: total free used buff/cache available` | 看 `available`，不要看 `free` |
| 第 5 行 | `MiB Swap: total free used avail` | `used` 长期不为 0 才是问题 |

进程区的列与 `ps` 对应，但多了几个比率：`VIRT` 是虚拟地址空间（含映射但未触页的部分），`RES` 是常驻物理页，`SHR` 是其中可共享的部分，`S` 是状态，`%CPU` 是**自上次刷新以来的增量**（这正是它和 `ps` 最大的区别），`TIME+` 是累计 CPU 时间，精确到百分之一秒。

`top` 的交互键不必全记，先记这十个：

| 键 | 作用 | 键 | 作用 |
|:--|:--|:--|:--|
| `P` | 按 CPU 排序（默认） | `M` | 按内存排序 |
| `T` | 按累计 CPU 时间排序 | `k` | 给 PID 发信号 |
| `r` | 改 nice 值 | `c` | 切换命令名/完整命令行 |
| `H` | 显示线程 | `1` | 每核一行 |
| `u` | 按用户过滤 | `f` / `o` | 选字段 / 调顺序 |

批处理采集用 `top -b`，它不会进入全屏，输出可直接追加到文件：

```bash
# 每 2 秒采一次，共 5 次，只看 2048 这个进程及其线程
top -b -n 5 -d 2 -H -p 2048 > /tmp/top-2048.txt

# 按内存排序取前 15 行，宽输出不截断命令行
top -b -n 1 -o %MEM -w 512 | head -15

# 记录 1 分钟内的整体负载，供事后比对
top -b -n 60 -d 1 | grep -E '^(top -|%Cpu|MiB Mem)' > /tmp/load-1m.txt
```

`top -b` 的第一帧是自开机以来的累计值，`%CPU` 可能异常高；从第二帧开始才是区间增量。脚本里要么丢掉第一帧，要么用 `-d 1 -n 2` 取第二次输出。

按名字找进程时，`pgrep` 比 `ps | grep` 少两个坑：它不会匹配到自己的 `grep`，也能直接按父进程、终端、用户筛选。

| 选项 | 作用 | 例子 |
|:--|:--|:--|
| `-a` | 输出 PID + 完整命令行 | `pgrep -a nginx` |
| `-f` | 匹配完整命令行 | `pgrep -af 'backup.sh --full'` |
| `-x` | 精确匹配整个名字 | `pgrep -x sshd` |
| `-u` / `-t` / `-P` | 按用户 / 终端 / 父进程 | `pgrep -P 1` |
| `-n` / `-o` | 最新 / 最老的一个 | `pgrep -n -x sleep` |
| `-c` | 只输出计数 | `pgrep -c -u www-data` |
| `-g` / `-s` | 按进程组 / 会话 | `pgrep -g 2210` |

`pkill` 接受同样的匹配选项，外加 `-SIGNAL` 和 `-e`（打印被杀的进程）。`pkill -f` 匹配的是整条命令行，你的 SSH 会话、编辑器的命令行里都可能出现同一个字符串；先 `pgrep -af` 核对，再考虑 `pkill`。这也是 0.9.5 里「先看再杀」的由来。

### 0.9.9.1 cgroup 视角：进程的第三重身份 {#sec-0.9.9.1}

进程有 PID、进程组、会话三重身份；在容器与 systemd 时代还有第四重：**cgroup**。PID 会复用，会话会随终端消失，cgroup 路径则决定「谁给它分资源、谁给它记账、谁能在它失控时整组终止」。

::: def 定义 0.9.9 · cgroup v2 {#def-0.9.9}
cgroup（control group）把进程组织成一棵树，每个进程在同一时刻只属于一个 cgroup。v2 是单一层级（unified hierarchy），控制器（cpu、memory、io、pids、cpuset 等）通过 `cgroup.subtree_control` 逐级启用；资源限制写在进程所在的叶子节点上，记账沿树向上汇总。容器 = namespace（看什么）+ cgroup（用多少）+ rootfs（有什么）。
:::

<div class="terminal" data-title="bash · 一个进程的 cgroup 路径">
<pre><span class="p">&#36;</span> stat -fc %T /sys/fs/cgroup
cgroup2fs
<span class="p">&#36;</span> cat /proc/&#36;&#36;/cgroup
0::/user.slice/user-1000.slice/session-2.scope
<span class="p">&#36;</span> cat /sys/fs/cgroup/cgroup.controllers
cpuset cpu io memory pids
<span class="p">&#36;</span> systemd-cgtop --depth=2 -b -n 1 | head -6
Control Group                    Tasks   %CPU   Memory  Input/s Output/s
/                                  312   12.4    2.1G        -        -
user.slice                         289   11.8    1.9G        -        -
user.slice/user-1000.slice         287   11.6    1.9G        -        -
</pre>
</div>

`0::` 是 v2 的固定前缀，后面是相对 `/sys/fs/cgroup` 的路径。用 `stat -fc %T` 判断版本：输出 `cgroup2fs` 是 v2，`tmpfs` 通常是 v1 或 hybrid；`ls /sys/fs/cgroup/cgroup.controllers` 存在与否更直接。

cgroup v2 的文件不多，按「读什么」和「写什么」分开记：

| 文件 | 读写 | 含义 | 典型值 |
|:--|:--|:--|:--|
| `cgroup.procs` | 读写 | 该组的线程组 PID 列表；写入会迁移整个线程组 | `2048` |
| `cgroup.threads` | 读写 | 线程级列表；写单个 TID | `2048` |
| `cgroup.type` | 读 | `domain` 或 `threaded` | `domain` |
| `cgroup.controllers` | 读 | 父级可下放的控制器 | `cpu memory pids` |
| `cgroup.subtree_control` | 读写 | 对子节点启用哪些控制器 | `+cpu +memory` |
| `cpu.weight` | 读写 | 相对权重，1–10000，默认 100 | `100` |
| `cpu.max` | 读写 | `配额 周期`，单位微秒；`max 100000` 表示不限 | `50000 100000` |
| `cpu.stat` | 读 | `usage_usec`、`nr_throttled`、`throttled_usec` | 累计值 |
| `memory.current` | 读 | 当前计入的内存字节 | `134217728` |
| `memory.max` | 读写 | 硬上限；`max` 表示不限 | `268435456` |
| `memory.events` | 读 | `low/high/max/oom/oom_kill` 计数 | `oom_kill 1` |
| `memory.pressure` | 读 | PSI 压力（`some`/`full` 的 `avg10`） | `some avg10=0.00` |
| `pids.current` / `pids.max` | 读/读写 | 进程数上限 | `max` |
| `io.stat` | 读 | 每设备的 `rbytes/wbytes/rios/wios` | 累计值 |
| `cgroup.freeze` | 读写 | 写 1 冻结整棵子树 | `0`/`1` |
| `cgroup.kill` | 写 | 写 1 原子终止整棵子树（5.14+） | `1` |

`cpu.weight` 与 nice 不是同一套刻度：nice 是 -20..19，权重是 1..10000；把 v1 的 `cpu.shares`（默认 1024，范围 2..262144）直接抄到 v2 会得到完全不同的份额。`cpu.max` 才是硬限额，`cpu.weight` 只在竞争时按比例分配。

「no internal process」是 v2 最容易踩的规则：一个 cgroup 启用了子控制器的同时，不能直接放进程；进程必须放在叶子节点。systemd 用 `.slice`（内部节点）和 `.scope`/`.service`（叶子）表达这棵树，所以你会看到服务在 `app.slice/foo.service`，而不是直接在 `app.slice`。手工往父节点 `echo PID > cgroup.procs` 会得到 `EBUSY`。

cgroup 的内核路径：挂载 `cgroup2` → `kernfs` 生成控制文件；写 `cgroup.procs` 走 `cgroup_procs_write()` → `cgroup_attach_task()` → 更新 `css_set`；写 `memory.max` 走 `memory_max_write()`；写 `cpu.max` 走 `cpu_max_write()`。容器运行时（runc、crun）在创建容器时做三件事：建 cgroup、把 init 放进去、把 limits 写进对应文件。

最实用的三条命令：

```bash
# 1. 看某个 PID 属于哪个 cgroup
cat /proc/2210/cgroup

# 2. 以临时 scope 跑一个带限额的命令（systemd 用户会话）
systemd-run --user --scope -p MemoryMax=256M -p CPUQuota=50% bash

# 3. 冻结并整组终止（5.14+；比遍历 PID 可靠）
echo 1 | sudo tee /sys/fs/cgroup/lab/cgroup.freeze
echo 1 | sudo tee /sys/fs/cgroup/lab/cgroup.kill
```

`systemd-cgtop` 看不到 CPU/内存数字时，通常是该 slice 没开记账；用 `systemctl set-property <unit> CPUAccounting=yes MemoryAccounting=yes` 打开。容器里 `systemd-cgtop` 往往不可用，直接读 `/sys/fs/cgroup` 下的文件更可靠。`cgroup.kill` 只终止该 cgroup 里的进程，不会杀到宿主机的其他进程；这正是「整组终止」比 `kill -9` 遍历 PID 更安全的原因。

### 0.9.9 小结

`ps`/`top` 的字段可以按「它是谁、它在等什么、它用了多少」三组来记：`PID/PPID/PGID/SID/TTY` 回答「它是谁」，`STAT/WCHAN` 回答「它在等什么」，`%CPU/RSS/TIME` 回答「它用了多少」。如果只记住一件事，那就是**先看 `STAT` 再谈性能**：`D` 状态的进程 `%CPU` 再低也不是 CPU 的问题，`R` 状态排队才该看负载。

::: method 即时自测 · 0.9.9
**Q1（记忆）** `STAT` 里的 `S`、`D`、`Z`、`T` 各表示什么？哪个状态下的「慢」与 CPU 无关？

**Q2（辨析）** `ps -o %cpu` 与 `top` 的 `%CPU` 为什么可能对不上？`ps` 的 `TIME` 是累计值还是瞬时值？

**Q3（应用）** 你怀疑一个进程在等 I/O，但 `top` 显示 CPU 空闲。给出你的排查顺序，至少三条命令。

::: sol 答案
**A1** `S` 可中断睡眠（等事件，最常见）、`D` 不可中断睡眠（等 I/O、连信号都不处理）、`Z` 僵尸（已退出等父进程收尸）、`T` 已停止（收到 `SIGSTOP`/`SIGTSTP`）。`D` 状态下的「慢」与 CPU 无关，瓶颈在设备或文件系统。

**A2** `ps` 的 `%CPU` 是**进程整个生命周期的平均占用**，`top` 的是最近一个刷新周期的瞬时值；刚跑完一段密集计算的进程，`ps` 会长期偏高。`ps` 的 `TIME` 是累计 CPU 时间，不是瞬时。

**A3** ① `ps -o pid,stat,wchan:24,cmd -p <pid>` 看是否 `D` 与卡在哪个内核函数；② `cat /proc/<pid>/stack`（需 root）或 `/proc/<pid>/wchan` 看等待点；③ `iostat -x 1` / `pidstat -d` 看设备利用率与进程 I/O；④ 最后才回到 CPU：`top -H -p <pid>` 看线程级占用。
:::

:::

## 0.9.10 信号的处置、阻塞与排队 {#sec-0.9.10}

这一节回答：信号明明发了，进程为什么没反应？「忽略」「阻塞」「捕获」在进程内部到底各改了什么？

::: preview 先抓住一件事
三张位图（阻塞、待处理、处置）决定一切：**忽略是丢，阻塞是攒，捕获是打断**。分不清这三个词，就会在最需要清理的地方丢掉信号。
:::

0.9.5 把信号当成「发过去就完事」，这一节补上内核侧的三件事：**处置方式**（disposition）、**阻塞掩码**（blocked mask）、**待处理集合**（pending set）。三者组合，才能解释「为什么信号发了却没反应」。

::: def 定义 0.9.10 · 信号处置与三张位图 {#def-0.9.10}
每个线程有三组与信号相关的位图：`blocked` 是主动屏蔽的信号，`pending` 是已投递但尚未处理的信号，`ignored`/`caught` 是处置方式。标准信号（1–31）在 pending 集合里只占一位，同一信号多次到达会合并；实时信号（`SIGRTMIN`–`SIGRTMAX`）按队列排队，可以带一个 `sigval` 参数。
:::

处置方式只有四种：默认动作、忽略（`SIG_IGN`）、用户处理函数、由内核特殊处理（如 `SIGKILL`/`SIGSTOP` 不可捕获）。`fork` 后子进程继承父进程的处置；`exec` 后，被捕获的信号恢复默认，被忽略的信号继续保持忽略——这就是 `nohup` 的实现原理：它把 `SIGHUP` 设成 `SIG_IGN` 再 `exec`，忽略属性跨过 `exec` 留了下来。

阻塞与忽略是两件不同的事：

| 操作 | 效果 | 信号会丢吗 | 典型用途 |
|:--|:--|:--|:--|
| 忽略 `SIG_IGN` | 投递时直接丢弃 | 会 | `nohup`、不关心 `SIGPIPE` |
| 阻塞 `sigprocmask` | 投递后留在 pending | 不会（标准信号合并） | 保护临界区、`sigwait` |
| 捕获 handler | 中断当前代码去执行 | 不会 | 清理、重载配置 |
| 默认动作 | 终止/停止/忽略/core | 不适用 | 不安装 handler 时 |

阻塞掩码是**每线程**的，不是每进程的。多线程程序里，信号只会投递给「没有阻塞它」的任意一个线程；要让某个专用线程处理信号，标准做法是在主线程创建 worker 之前阻塞信号，worker 继承掩码，最后由 `sigwait` 线程解除阻塞并循环接收。

Python 可以把这个过程完整演示出来：

```python
import os, signal, time

signal.pthread_sigmask(signal.SIG_BLOCK, {signal.SIGTERM})
print("blocked:", signal.pthread_sigmask(signal.SIG_BLOCK, []))
os.kill(os.getpid(), signal.SIGTERM)
print("pending:", signal.sigpending())
signal.signal(signal.SIGTERM, lambda s, f: print("handler ran"))
signal.pthread_sigmask(signal.SIG_UNBLOCK, {signal.SIGTERM})
time.sleep(0.1)
```

真跑一遍（Ubuntu 24.04 / Python 3.12，原样回显）：

```text
$ python3 sigdemo.py
blocked: {<Signals.SIGTERM: 15>}
pending: {<Signals.SIGTERM: 15>}
handler ran
rc=0
```

三行就是三张位图的动作：第一行阻塞成功；第二行 `os.kill` 之后信号**没有丢**，躺在 pending 里；第三行解除阻塞，handler 立刻执行。注意 `signal.signal()` 必须在解除阻塞之前安装，否则解除的瞬间默认动作就把进程终止了。

`/proc/PID/status` 把这三张位图暴露成十六进制掩码：

```bash
grep -E '^(SigQ|SigPnd|ShdPnd|SigBlk|SigIgn|SigCgt):' /proc/$$/status
```

`SigPnd` 是线程私有的 pending，`ShdPnd` 是进程共享的 pending；`SigBlk`、`SigIgn`、`SigCgt` 分别是阻塞、忽略、捕获的掩码。第 N 号信号对应第 N-1 位，从右往左数。用一行 Python 解码比心算可靠：

```bash
python3 - <<'PY'
import os
for line in open(f"/proc/{os.getpid()}/status"):
    if line.startswith(("SigBlk", "SigIgn", "SigCgt")):
        name, mask = line.split(":")
        v = int(mask.strip(), 16)
        sigs = [n for n in range(1, 65) if v >> (n - 1) & 1]
        print(name, sigs)
PY
```

信号处理的几条硬规则，写代码和读别人的代码都用得上：

| 规则 | 含义 | 后果 |
|:--|:--|:--|
| handler 里只能调 async-signal-safe 函数 | `printf`、`malloc` 都不安全 | 死锁或堆损坏 |
| `SA_RESTART` 只重启部分系统调用 | `read`/`write` 会重启，`poll`/`epoll_wait`/`select` 不会 | 必须自己处理 `EINTR` |
| `signal()` 的语义随 libc 变 | glibc 的 `signal` 默认带 `SA_RESTART` | 可移植代码用 `sigaction` |
| 标准信号会合并 | 连发 10 个 `SIGUSR1` 可能只处理 1 次 | 计数型通知要用实时信号或自管道 |
| `SIGKILL`/`SIGSTOP` 不可捕获、不可阻塞 | `sigprocmask` 会返回 `EINVAL` | 别把它们写进掩码 |
| `exec` 保留忽略、清除捕获 | 守护进程常用这一点 | `nohup` 依赖它 |

`SIGCHLD` 是最容易写错的一个。它的默认动作是「忽略」，但「默认忽略」不等于「显式设为 `SIG_IGN`」：后者在 Linux 上会让子进程退出时自动被回收，前者仍会产生僵尸。要可靠回收，有三种写法：

```c
/* 写法一：阻塞 SIGCHLD，fork 之后用 sigwaitinfo 收尸，避免 handler 与 wait 的竞态 */
sigset_t set, old;
sigemptyset(&set); sigaddset(&set, SIGCHLD);
sigprocmask(SIG_BLOCK, &set, &old);
pid_t pid = fork();
if (pid == 0) { /* child */ _exit(0); }
int status;
sigwaitinfo(&set, NULL);          /* 等到子进程状态变化 */
waitpid(pid, &status, WNOHANG);   /* 再取一次，防止漏掉 */
sigprocmask(SIG_SETMASK, &old, NULL);
```

另外两种是：在 handler 里用 `while (waitpid(-1, &st, WNOHANG) > 0)` 循环收尸；或者用 `signalfd` 把 `SIGCHLD` 变成可 `poll` 的 fd。前者要小心 `errno` 与可重入，后者适合事件循环。

`siginfo` 里的 `si_code` 能告诉你信号是谁发的，这在排障时比信号本身有用：

| `si_code` | 含义 | 例子 |
|:--|:--|:--|
| `SI_USER` | `kill(2)`/`raise(3)` 发的 | 运维手动 `kill` |
| `SI_KERNEL` | 内核发的 | 终端驱动发 `SIGINT` |
| `SI_TKILL` | `tkill`/`tgkill` | 线程库内部 |
| `SI_QUEUE` | `sigqueue` 带值 | 实时信号 |
| `SI_TIMER` | POSIX timer 到期 | `timer_create` |
| `SI_CHLD` | 子进程状态变化 | `CLD_EXITED`/`CLD_KILLED` |

退出状态与信号的关系也要背清楚，脚本里的 `$?` 全靠它：

| 结束方式 | `waitpid` 宏 | shell `$?` | 说明 |
|:--|:--|--:|:--|
| `exit(0)` | `WIFEXITED`，`WEXITSTATUS=0` | 0 | 正常 |
| `exit(7)` | `WIFEXITED`，`WEXITSTATUS=7` | 7 | 正常 |
| 被 `SIGTERM` 杀 | `WIFSIGNALED`，`WTERMSIG=15` | 143 | 128+15 |
| 被 `SIGKILL` 杀 | `WIFSIGNALED`，`WTERMSIG=9` | 137 | 128+9 |
| 被 `SIGINT` 杀 | `WIFSIGNALED`，`WTERMSIG=2` | 130 | 128+2 |
| 被 `SIGSTOP` 停 | `WIFSTOPPED`，`WSTOPSIG=19` | — | 不是终止，可 `SIGCONT` |

`SIGPIPE` 值得单独说：往一个读端已关闭的管道写，内核先发 `SIGPIPE`，默认动作是终止；如果程序忽略或阻塞了它，`write` 才返回 `-1/EPIPE`。shell 里 `cmd | head -1` 之后 `cmd` 报 141，就是被 `SIGPIPE` 杀了。这不是错误，是管道提前关闭的正常结果；`set -o pipefail` 会把它变成脚本的失败码，写管道脚本时要预料到。

最后是信号的投递对象。`kill(2)` 的三种形式在 0.9.5 已经出现，补充两个更精确的接口：

- `tgkill(2)` 指定线程组和线程 ID，避免「发给进程后被任意线程处理」的歧义；线程库的 `pthread_kill` 最终走它。
- `pidfd_open(2)` + `pidfd_send_signal(2)`（Linux 5.1+）先拿一个指向进程的 fd，再发信号。PID 被复用也不会误伤，这是 systemd、容器运行时的做法。
- `prctl(PR_SET_PDEATHSIG, SIGTERM)` 让子进程在父进程死亡时收到信号；它只在父线程退出时触发，且 `exec` 后保留，适合「子进程不能比父进程活得久」的场景。

### 0.9.10 小结

信号的三件事各有明确语义：**处置**决定「收到后做什么」，**阻塞**决定「现在能不能收」，**排队**决定「收之前存在哪、会不会合并」。标准信号在 pending 里只有一位，所以「连发十次只处理一次」不是 bug；要计数就得用实时信号或自管道。如果只记住一件事，那就是**想在临界区里不被打断，用阻塞而不是忽略**——忽略会真的丢掉信号。

**Q2（辨析）** `SIGCHLD` 的「默认动作是忽略」和「显式设为 `SIG_IGN`」为什么效果不同？

**Q3（应用）** 一个守护进程要保证「子进程不得比父进程活得久」。你会用哪个接口、它的边界在哪？

**A3** `prctl(PR_SET_PDEATHSIG, SIGTERM)`。边界有三条：它绑的是**父线程**而不是父进程（父线程先退出就会触发）；信号在 `exec` 后仍然保留；如果 fork 之后父进程已经死了，要自己再检查一次 `getppid()`，否则会漏掉这一刻。

::: preview 先抓住一件事
运维脚本的价值在于**把判断写成条件**：什么状态算异常、身份对不对、等多久算超时。下面三个脚本各自把一组判断固化成代码。

### 0.9.11.1 进程快照：一眼看出僵尸、D 状态与资源大户

`ps` 的默认列不适合巡检。下面这个脚本固定列、固定排序、固定 locale，输出可以直接贴进工单：

```bash
#!/usr/bin/env bash
# proc-report.sh —— 进程快照：异常状态、资源大户、按状态计数
set -euo pipefail
export LC_ALL=C

echo "== $(date -Is) host=$(hostname) kernel=$(uname -r)"
echo "== load: $(cut -d' ' -f1-3 /proc/loadavg)"

echo "-- 异常状态（Z 僵尸 / D 不可中断 / T 停止）"
ps -eo stat,pid,ppid,pgid,sid,etime,comm --sort=pid |
    awk 'NR==1 || $1 ~ /^[ZDT]/'

echo "-- CPU 前 5（pcpu 为生命周期平均，仅作线索）"
ps -eo pcpu,pmem,rss,pid,comm --sort=-pcpu | head -6

echo "-- 内存前 5（RSS，单位 KiB）"
ps -eo rss,pmem,pid,comm --sort=-rss | head -6

echo "-- 按状态计数"
ps -eo stat= | cut -c1 | sort | uniq -c | sort -rn
```

真跑一段（Ubuntu 实测，节选）：

```text
$ ./proc-report.sh
== 2026-10-30T16:48:30+08:00 host=juanwang-Ubuntu24.04 kernel=7.0.0-38-generic
== load: 1.00 1.01 1.00
-- 异常状态（Z 僵尸 / D 不可中断 / T 停止）
STAT     PID    PPID    PGID     SID     ELAPSED COMMAND
-- CPU 前 5（pcpu 为生命周期平均，仅作线索）
%CPU %MEM   RSS     PID COMMAND
99.9  0.0  2088   12584 sed
 0.1  1.6 207088   1822 gnome-shell
```

看两处：异常状态那节只有表头——**没消息就是好消息**，说明这台机器此刻没有 `Z`/`D`/`T`；CPU 榜首那个 99.9% 的 `sed` 正是跑这个脚本的管道本身，说明「生命周期平均」会把短命进程算得很高，别把它当热点。

三个细节决定它是否可靠：`LC_ALL=C` 保证 `ps` 的表头与数字格式稳定；`stat=` 去掉表头，`cut -c1` 只取主状态；`--sort=-pcpu` 的负号是降序。`ps` 的 `pcpu` 是平均值，所以这个脚本只用来「找线索」，确认瞬时占用要配合 `top -b -n 2` 或 `pidstat 1`。

`awk 'NR==1 || $1 ~ /^[ZDT]/'` 保留表头，同时匹配 `Z`、`D`、`T` 开头的状态；`D` 后面可能跟 `<`，`T` 后面可能跟 `+`，正则不锚定结尾是有意的。

### 0.9.11.2 停一棵进程树：整组 TERM、有界等待、身份校验

0.9.5 的 `stop_tree` 是教学版，缺少 PID 复用校验与僵尸判断。生产版要把这两件事补上：

```bash
#!/usr/bin/env bash
# stop-tree.sh PID [宽限秒数]
# 退出码：0 已停止；1 强杀；2 参数错；3 PID 不存在或身份不符
set -euo pipefail

pid=${1:?usage: stop-tree.sh PID [grace]}
grace=${2:-10}
[[ $pid =~ ^[0-9]+$ ]] || { echo "not a pid: $pid" >&2; exit 2; }

stat_of() { cat "/proc/$1/stat" 2>/dev/null || return 1; }
# /proc/PID/stat 的第 22 字段是 starttime；用它绑定“还是原来那个进程”
starttime() { stat_of "$1" | awk '{print $22}'; }
state_of()   { stat_of "$1" | awk '{print $3}'; }

orig_start=$(starttime "$pid") || { echo "no such pid: $pid" >&2; exit 3; }
pgid=$(ps -o pgid= -p "$pid" | tr -d ' ')

signal_tree() {
    local sig=$1
    if [[ -n ${pgid:-} && $pgid == "$pid" ]]; then
        kill -"$sig" -- "-$pid" 2>/dev/null && return 0
    fi
    kill -"$sig" "$pid" 2>/dev/null
}

signal_tree TERM || true
for ((i = 0; i < grace * 2; i++)); do
    [[ -d /proc/$pid ]] || exit 0
    [[ $(state_of "$pid") == Z ]] && exit 0   # 僵尸已死，等父进程收尸
    sleep 0.5
done

# 等待期间 PID 可能被复用：身份不符就不再动手
[[ $(starttime "$pid" 2>/dev/null) == "$orig_start" ]] || {
    echo "pid $pid reused; refusing to kill" >&2; exit 3; }

echo "grace expired, sending SIGKILL to $pid (pgid=$pgid)" >&2
signal_tree KILL || true
sleep 1
[[ -d /proc/$pid && $(state_of "$pid") != Z ]] && exit 1
exit 0
```

真跑一次（先用一组 `sleep` 造一棵两进程的树，再停它）：

```text
$ bash -c "sleep 60 & sleep 60; wait" & 
$ ./stop-tree.sh <PID> 2
rc=0
gone
```

`rc=0` 表示「已按 TERM 停住」而不是「打不开这个 PID」；`gone` 是随后 `kill -0` 的判据。退出码约定在脚本头部就写清：0 已停止、1 强杀、2 参数错、3 身份不符——**调用方据此决定要不要重试**。

它比教学版多做了四件事：用 `starttime` 确认身份；只有「PID 等于 PGID」时才打整组，避免误杀别人的组；把 `Z` 当成「已停止」而不是「还活着」；宽限期按 0.5 秒轮询，最多 `grace` 秒。`kill -0` 在这里被刻意避开，因为它对僵尸仍返回成功。

### 0.9.11.3 可靠地脱离终端：pidfile + 就绪检查

`nohup cmd &` 的 `$!` 是 shell 的子进程，但 `setsid -f` 会再 fork 一次，`$!` 可能只是短命的 wrapper。要在脚本里拿到真正的守护进程 PID，让子进程自己写 pidfile：

```bash
#!/usr/bin/env bash
# detach.sh --log FILE --pidfile FILE -- CMD [ARGS...]
set -euo pipefail

log= pidfile= cmd=()
while [[ $# -gt 0 ]]; do
    case $1 in
        --log) log=$2; shift 2 ;;
        --pidfile) pidfile=$2; shift 2 ;;
        --) shift; cmd=("$@"); break ;;
        *) echo "unknown arg: $1" >&2; exit 2 ;;
    esac
done
[[ ${#cmd[@]} -gt 0 && -n $log && -n $pidfile ]] || {
    echo "usage: detach.sh --log FILE --pidfile FILE -- CMD..." >&2; exit 2; }

: >>"$log"
rm -f "$pidfile"

# 在新会话里运行；bash 先写自己的 PID，再 exec 目标程序，PID 不变
setsid -f bash -c '
    echo $$ >"$1"
    exec "${@:2}"
' _ "$pidfile" "${cmd[@]}" </dev/null >>"$log" 2>&1

for _ in {1..40}; do
    [[ -s $pidfile ]] && break
    sleep 0.05
done
[[ -s $pidfile ]] || { echo "child did not start" >&2; exit 1; }

pid=$(cat "$pidfile")
sid=$(ps -o sid= -p "$pid" | tr -d ' ')
[[ $sid == "$pid" ]] || { echo "not a session leader: pid=$pid sid=$sid" >&2; exit 1; }
echo "started pid=$pid sid=$sid log=$log"

# 停止：按 pidfile，先 TERM 再 KILL
# kill -TERM "$pid"; for i in {1..20}; do [[ -d /proc/$pid ]] || break; sleep 0.5; done
```

真跑一次（Ubuntu 实测）：

```text
# 实测（Ubuntu 24.04.5 aarch64，pid 每次不同）
$ ./detach.sh --log /tmp/d.log --pidfile /tmp/d.pid -- sleep 2
started pid=493994 sid=493994 log=/tmp/d.log
$ ps -o pid,sid,tty,cmd -p 493994
    PID     SID TT       CMD
 493994  493994 ?        sleep 2
```

三个值要一起看：`pid` 与 `sid` 相等（它是新会话的首进程）、`TT` 是 `?`（没有控制终端，`SIGHUP` 找不到它）、命令行就是目标程序本身（`exec` 没换 PID）。pidfile 里存的正是这个值，所以 `kill "$(cat d.pid)"` 打到的是真进程，不是 wrapper。

关键点是 `bash -c` 里的 `echo $$` 与随后的 `exec`：`$$` 是新会话首领的 PID，`exec` 不换 PID，所以 pidfile 里的值就是目标进程。`</dev/null` 断掉 stdin，避免后台读终端收到 `SIGTTIN`；`>>"$log"` 让 stdout/stderr 落到文件，避免持有已关闭的终端 fd。

如果机器上有 systemd，优先用 `systemd-run`，省掉 pidfile 与守护化的全部细节：

```bash
systemd-run --user --unit=job1 --collect \
    --property=WorkingDirectory="$PWD" \
    /path/to/job.sh
systemctl --user status job1.service
journalctl --user -u job1.service -f
```

它给你 cgroup、重启策略、日志收集和 `systemctl stop` 的整组终止；`--collect` 让失败的 unit 在退出后自动清理，不会堆一堆 `failed`。

### 0.9.11 小结

三个脚本各自把一组判断固化成代码：快照脚本把「什么算异常」写成正则与排序；停树脚本把「身份、范围、宽限」写成三道校验；脱离脚本把「真 PID」写进 pidfile 而不是靠 `$!`。如果只记住一件事，那就是**运维脚本的退出码要让调用方能做决定**——0/1/2/3 各对应一种处置，而不是清一色 `exit 1`。

## 0.9.12 两个实验：进程组与信号掩码 {#sec-0.9.12}

这一节回答：进程组、会话、控制终端这三个词，在 `ps` 的字段里各对应哪一列？发出去却「没反应」的信号，在进程内部停在哪张表里？

::: preview 先抓住一件事
两个实验都不需要特殊权限，但都会推翻一个直觉：**`kill` 打的是组还是进程，看 `PGID`；信号没反应，看 `SigBlk` 与 `ShdPnd`**。
:::

### 实验一：看清「终端只认前台组」

目的：用同一组命令对比「有作业控制」与「无作业控制」时 PGID 的差别，并验证 Ctrl-C 只打前台组。

```bash
# 终端 A：开一个交互式 bash，打开作业控制
bash --norc -i
set -m
sleep 300 &
job=$!
ps -o pid,ppid,pgid,sid,tpgid,stat,comm -p $$,"$job"
```

**这一个没在本书环境里跑**：它需要真终端的 pty（`bash --norc -i` 加 `set -m`），ssh 会话里拿不到前台组，`TPGID` 会是 -1。判据照原文：`sleep` 的 `PGID` 等于它自己的 PID、`SID` 等于 bash 的 PID、`STAT` 带 `+` 的是前台组。要自己验证就开一个真终端照命令敲一遍。

再对比关闭作业控制的情况：

```bash
bash --norc -c 'set +m; sleep 300 & ps -o pid,ppid,pgid,sid,tpgid,stat,comm -p $$,$!'
```

真跑结果（Ubuntu 实测，`set +m` 关闭作业控制）：

```text
    PID    PPID    PGID     SID   TPGID STAT COMMAND
 421122  421121  421120  421119      -1 S    bash
 421123  421122  421120  421119      -1 S    sleep
```

两行的 `PGID` 都是 421120，既不等于 bash 的 PID 也不等于 sleep 的 PID；`TPGID` 是 `-1`，说明没有前台组。这就是「关闭作业控制后，子进程和 shell 同组」的直接证据——此时 `kill -INT -- -421120` 会同时打到两者。

最后验证「整组 TERM」：

```bash
setsid bash -c 'sleep 300 & sleep 300 & wait' &
sleep 0.2
pgid=$(ps -o pgid= -p $! | tr -d ' ')
ps -o pid,pgid,sid,stat,comm -g "$pgid"
kill -TERM -- "-$pgid"
sleep 0.2
ps -o pid,stat,comm -g "$pgid" || echo "group $pgid gone"
```

真跑结果（Ubuntu 实测）：

```text
    PID    PGID     SID STAT COMMAND
 421125  421125  421125 Ss   bash
 421127  421125  421125 S    sleep
 421128  421125  421125 S    sleep
after kill:
group 421125 gone
```

`bash` 的 `PID = PGID = SID`，`STAT` 是 `Ss`（会话首领）；两个 `sleep` 的 `PGID`/`SID` 都跟着它。`kill -TERM -- -421125` 之后整组消失——这就是「停一棵进程树」的正确打点方式。

### 实验二：用 `strace` 看信号从投递到返回

目的：确认 `SIGTERM` 的 `si_code`、handler 的 `rt_sigreturn`，以及阻塞期间的 pending 状态。

准备一个带 handler 的脚本（0.9.5 的 `slow.sh` 即可），然后：

```bash
strace -f -tt -e trace=signal -o /tmp/sig.trace ./slow.sh &
tpid=$!
sleep 0.3
kill -TERM "$tpid"
wait "$tpid"; echo "rc=$?"
grep -E 'SIGTERM|rt_sigaction|rt_sigprocmask|rt_sigreturn' /tmp/sig.trace | tail -20
```

真跑结果（Ubuntu 实测，`strace -f -tt -e trace=signal`）关键一行：

```text
421239 16:53:49.445231 rt_sigaction(SIGTERM, {sa_handler=0xad82d481e060, sa_mask=[], sa_flags=0}, {sa_handler=SIG_DFL, ...}, 8) = 0
```

第三个参数是**旧值**：`SIG_DFL`，说明之前没人安装过 handler；新值里的 `0xad82d481e060` 就是 bash 的 trap 函数地址。信号真正投递时会再出一行 `--- SIGTERM {si_signo=SIGTERM, si_code=SI_USER, si_pid=..., si_uid=...}`——`si_code=SI_USER` 表示「这是 `kill(2)` 发的」，与终端按 Ctrl-C 产生的 `SI_KERNEL` 区分开。

再看阻塞与 pending：

```bash
python3 - <<'PY' &
import os, signal, time
signal.pthread_sigmask(signal.SIG_BLOCK, {signal.SIGTERM})
print("pid", os.getpid(), flush=True)
time.sleep(30)
PY
py=$!
sleep 0.3
kill -TERM "$py"
grep -E 'SigBlk|SigPnd|ShdPnd' /proc/$py/status
kill -KILL "$py"
```

真跑结果（Ubuntu 实测，先 `SIG_BLOCK` 再 `kill -TERM`）：

```text
SigPnd:	0000000000000000
ShdPnd:	0000000000004000
SigBlk:	0000000000004000
```

`0x4000` 是第 15 位——SIGTERM 的编号正是 15。`SigBlk` 有它（被阻塞）、`ShdPnd` 也有它（已投递、等着），`SigPnd` 为空是因为这个进程只有一个线程，进程级 pending 落在 `ShdPnd` 里。进程**没有退出**：阻塞不是忽略，信号一直在等。这个实验解释了「为什么发了 TERM，进程还活着」。`kill -KILL` 之后才消失（`KILL` 不可阻塞）。

### 0.9.12 小结

两个实验各钉住一件事：**组的边界**看 `PGID`/`SID`（同组就会一起挨打，会话首领的 PID 就是 PGID 与 SID）；**信号的落点**看 `SigBlk` 与 `ShdPnd`（阻塞的信号留在 pending 里，位号是「信号编号 − 1」）。如果只记住一件事，那就是**发信号前先确认打的是谁**——`kill -- -PGID` 与 `kill PID` 是两个完全不同的操作。

::: method 即时自测 · 0.9.12
**Q1（记忆）** `TPGID` 是什么？它等于 `-1` 说明什么？

**Q2（辨析）** 同样的 `sleep 300 &`，开作业控制与不开，`PGID` 各是什么？

**Q3（应用）** `/proc/PID/status` 里 `ShdPnd: 0000000000004000`，这说明哪个信号、处于什么状态？

::: sol 答案
**A1** 前台进程组的 ID。等于 `-1` 表示这个会话当前**没有前台组**（常见于非交互 shell、ssh 直接执行命令、或整个会话都被放到后台）。

**A2** 开作业控制（`set -m`）时，作业被放进**自己的**进程组，`PGID` 等于作业首个进程的 PID；关闭时（`set +m`，非交互脚本的默认）子进程继承 shell 的 `PGID`，和 shell 同组。

**A3** 第 15 位是 SIGTERM（位号 = 15 − 1 = 14，十六进制 0x4000）。`ShdPnd` 表示进程级 pending：信号已投递、但被 `SigBlk` 挡住还没处理。它不是「丢失」，解除阻塞就会补投。
:::

## 0.9.13 十四个容易踩错的边界 {#sec-0.9.13}

这一节回答：进程与信号这一章，哪些错是「命令看起来成功了、结果却是错的」？每一条怎么在十秒内判断出来？

::: preview 先抓住一件事
十四条里有一半是「你以为杀的是 A，其实打到了 B」：`kill 0`、`%1`、PID 复用、`timeout` 的进程组。**先把目标确认清楚，再谈信号怎么发。**
:::

| # | 现象 | 原因 | 修复/判断 |
|--:|:--|:--|:--|
| 1 | `kill -9` 后端口仍被占用 | 子进程继承了监听 fd，或进程处于 `D` 状态 | 用 `ss -lptn` 找持有者；整组/cgroup 终止 |
| 2 | `nohup` 后进程停在 `T` | 仍挂控制终端，后台读 stdin 触发 `SIGTTIN` | `</dev/null`，或 `setsid` |
| 3 | 脚本里 `kill %1` 报「无此作业」 | 作业已退出被收走，或 `%1` 是父 Shell 的作业（作业表不跨进程继承） | 用 `$!` 记下的 PID/PGID |
| 4 | `kill 0` 把脚本自己也杀了 | 0 表示「当前进程组」 | 永远用具体 PID 或负 PGID |
| 5 | `$!` 记录的 PID 与实际进程不符 | 命令是管道/子 shell/`setsid -f` | 让子进程写 pidfile，或 `pgrep -P` |
| 6 | `ps aux \| grep x` 总有两条 | `grep` 自己也在进程表里 | `pgrep -af x`，或 `grep -v grep` |
| 7 | `%CPU` 显示 300% 但系统很闲 | 生命周期平均值，不是瞬时值 | `top -b -n 2`、`pidstat 1` |
| 8 | `ps` 的 `COMMAND` 被截断 | 默认 80 列，`comm` 只 15 字符 | `ps -ww -o args=` |
| 9 | 杀完 PID 后误伤了别的进程 | PID 被复用 | 记录 `starttime`，用 `pidfd` 或 cgroup |
| 10 | `wait` 立刻返回 127 | 目标不是当前 shell 的子进程 | 只能 wait 自己启动的作业 |
| 11 | 僵尸杀不掉 | 已经退出，等父进程 `wait` | 让父进程收尸，或杀父进程 |
| 12 | `timeout 5 cmd` 后子进程还在 | 默认只杀直接子进程，不杀整组 | `timeout --foreground` 或自己建组 |
| 13 | 容器里 PID 1 不回收孤儿 | 入口脚本不是 init | `docker run --init`、`tini` |
| 14 | `kill -0` 成功就以为进程健康 | 僵尸也返回成功，且不检查状态 | 读 `/proc/PID/stat` 的第三字段 |

第 12 条值得展开：GNU `timeout` 默认把命令放进新进程组，超时后向**该组**发信号；加 `--foreground` 反而不建组，只杀直接子进程。很多人记反了。判断办法是看 `timeout` 的 man page 里 `--foreground` 一段，或者做实验：`timeout 1 bash -c 'sleep 30 & wait'` 之后 `pgrep -a sleep` 是否还有残留。

### 0.9.13 小结

十四条可以按「打错目标」「读错字段」「判错状态」三类记：打错目标（1、2、3、4、5、9）来自组、PID 复用与 `$!`；读错字段（6、7、8）来自 `ps` 的默认值与平均语义；判错状态（10、11、12、13、14）来自 wait 的作用域、`timeout` 的进程组、僵尸也 `kill -0` 成功。如果只记住一件事，那就是**任何「杀」的动作，先打印目标再动手**——`ps -o pid,starttime,cmd` 确认过再发信号。

::: method 即时自测 · 0.9.13
**Q1（记忆）** `kill 0` 发给谁？`kill -0 PID` 成功代表什么、不代表什么？

**Q2（辨析）** `timeout 5 cmd` 与 `timeout --foreground 5 cmd` 在信号投递范围上有什么不同？

**Q3（应用）** 脚本里 `cmd & pid=$!` 之后 `kill "$pid"` 可能误伤，给出两条防误伤的做法。

::: sol 答案
**A1** `kill 0` 发给**当前进程组**（含脚本自己），所以常把调用者一起杀掉。`kill -0` 只检查「这个 PID 存在且我有权限发信号」，僵尸也返回成功——它不代表进程健康。

**A2** 默认会让 `cmd` 进入新的进程组，超时后向整组发信号，子孙一起收；`--foreground` 不建组，只杀直接子进程，孤儿会留下。

**A3** ① 记录并校验身份：启动后立刻取 `/proc/$pid/stat` 的第 22 字段 `starttime`，杀掉前再取一次比对；② 用 `pidfd_open` 拿 fd 再发信号（PID 复用不会误伤），或把命令放进独立 cgroup / 进程组，用 `kill -- -PGID` 按组杀。
:::

:::

## 0.9.14 两个实验：nice 权重与 cgroup 记账 {#sec-0.9.14}

这一节回答：nice 值到底值多少 CPU？cgroup 的限额在进程眼里是什么形状？

::: preview 先抓住一件事
nice 只在**争抢同一个 CPU** 时才生效；cgroup 的限额也不是「感觉」，而是 `cpu.max`、`memory.max` 两个文件里的数字。
:::

0.9.13 的坑多半来自「没量过」。这一节用两个实验把 nice 权重和 cgroup 记账变成可复现的数字：第一个用普通用户就能跑，第二个需要 systemd 用户会话或 root。

### 实验三：nice 不是标签，是权重

目的：在同一个 CPU 上放两个忙循环，一个 nice 0、一个 nice 10，用 `/proc/PID/schedstat` 量出实际 CPU 时间比，验证 1024:110 的权重。

```bash
#!/usr/bin/env bash
# nice-ratio.sh [秒数]：普通用户即可运行，不需要 root
set -euo pipefail
secs=${1:-5}
cpu=$(taskset -pc $$ | sed 's/.*: //' | cut -d, -f1 | cut -d- -f1)

taskset -c "$cpu" nice -n 0 bash -c 'while :; do :; done' >/dev/null 2>&1 &
p0=$!
taskset -c "$cpu" nice -n 10 bash -c 'while :; do :; done' >/dev/null 2>&1 &
p10=$!
sleep 0.2
read -r a0 _ _ <"/proc/$p0/schedstat"
read -r a10 _ _ <"/proc/$p10/schedstat"
sleep "$secs"
read -r b0 _ _ <"/proc/$p0/schedstat"
read -r b10 _ _ <"/proc/$p10/schedstat"
kill "$p0" "$p10" 2>/dev/null || true
wait "$p0" "$p10" 2>/dev/null || true

awk -v a0="$a0" -v b0="$b0" -v a10="$a10" -v b10="$b10" 'BEGIN {
    r0 = (b0 - a0) / 1e9; r10 = (b10 - a10) / 1e9;
    printf "cpu%d: nice0=%.2fs nice10=%.2fs ratio=%.1f\n", '"$cpu"', r0, r10, r0 / r10;
    printf "share: nice0=%.1f%% nice10=%.1f%%\n", 100*r0/(r0+r10), 100*r10/(r0+r10);
}'
```

真跑两组（Ubuntu 实测，4 核 VM，各跑 3 秒后读 `/proc/PID/stat` 的 utime）：

```text
# 实测（Ubuntu 24.04.5 aarch64，4 vCPU，utime 单位 jiffies）
-- 不绑核 --
pid=422229 utime=299 stime=0
pid=422230 utime=299 stime=0
-- 都绑到 CPU 0（taskset -c 0）--
pid=422370 utime=270 stime=0
pid=422371 utime=29  stime=0
```

两组差得这么大，正是这一节要教的：**不绑核时两个忙循环各占一个核，nice 根本没机会生效**（299 : 299）；绑到同一个核上才看到权重——270 : 29 ≈ 9.3 : 1，和内核权重 1024 : 110 算出来的 9.3 吻合。所以「我 `nice` 了但没变慢」这句话，先问一句「它们争的是同一个 CPU 吗」。

### 实验四：cgroup 的限额、记账与整组终止

目的：在临时 scope 里放一个进程，读它所在 cgroup 的 `cpu.max`、`memory.max`、`cpu.stat`，再用 `cgroup.kill` 一次收掉整棵子树。

```bash
#!/usr/bin/env bash
# cgroup-lab.sh：需要可用的 systemd 用户会话（systemctl --user status 成功）
set -euo pipefail
unit=cglab-$$
systemd-run --user --unit="$unit" --scope \
    -p MemoryMax=64M -p CPUQuota=20% \
    bash -c 'timeout 1 bash -c "while :; do :; done"; exec sleep 300' &
runner=$!

cg=
for _ in {1..50}; do
    cg=$(systemctl --user show -p ControlGroup --value "$unit.scope" 2>/dev/null || true)
    [[ -n $cg ]] && break
    sleep 0.1
done
[[ -n $cg ]] || { echo "scope did not start" >&2; exit 1; }
base=/sys/fs/cgroup$cg
printf 'unit=%s cgroup=%s\n' "$unit" "$cg"
printf 'cpu.max=%s memory.max=%s\n' "$(cat "$base/cpu.max")" "$(cat "$base/memory.max")"
grep -E 'usage_usec|nr_throttled|throttled_usec' "$base/cpu.stat"
printf 'memory.current=%s\n' "$(cat "$base/memory.current")"
pid=$(systemctl --user show -p MainPID --value "$unit.scope")
cat "/proc/$pid/cgroup"

# 整组终止；cgroup.kill 需要 5.14+，老内核用 stop 或遍历 cgroup.procs
if [[ -w $base/cgroup.kill ]]; then
    echo 1 >"$base/cgroup.kill"
else
    systemctl --user stop "$unit.scope"
fi
wait "$runner" 2>/dev/null || true
```

真跑一次（Ubuntu 实测，systemd 用户会话可用，**不需要 root**）：

```text
$ systemd-run --user --scope -p MemoryMax=64M -p CPUQuota=50% -- bash -c "sleep 0.2"
Running as unit: run-r633302d1dd104ecaa287e950430b4a97.scope; invocation ID: 50a97bc974ac4bd48fc5e4f2f53ccfba
$ systemctl --user show -p MemoryCurrent run-r633302d1dd104ecaa287e950430b4a97.scope
MemoryCurrent=1163264
```

`-p MemoryMax=64M` 与 `-p CPUQuota=50%` 被接受，说明这台机器的用户会话允许建 scope；`MemoryCurrent` 读出来是 1,163,264 字节（约 1.1 MiB，那个 `sleep` 的真实占用）。scope 随命令退出自动消失——不用手写 cgroup 路径，这是 `systemd-run --scope` 最省事的地方。原文的

没有 systemd 用户会话时，用 root 走手工路径：

```bash
sudo mkdir -p /sys/fs/cgroup/lab
sleep 300 & pid=$!
echo "$pid" | sudo tee /sys/fs/cgroup/lab/cgroup.procs
cat "/proc/$pid/cgroup"
cat /sys/fs/cgroup/lab/memory.current
cat /sys/fs/cgroup/lab/cpu.stat
echo 1 | sudo tee /sys/fs/cgroup/lab/cgroup.kill
sudo rmdir /sys/fs/cgroup/lab
```

这条路径要求 `lab` 是叶子节点；如果想给 `lab` 再建子组，先确认 `cgroup.subtree_control` 已启用对应控制器，否则写 `memory.max` 会得到 `ENOENT` 或 `EOPNOTSUPP`。

### 调度与 cgroup 的八个坑

| # | 现象 | 原因 | 修复/判断 |
|--:|:--|:--|:--|
| 1 | `nice -n -5 cmd` 报 `Permission denied` | 普通用户只能调高 nice，不能调低 | 用 root，或授予 `CAP_SYS_NICE`；检查 `ulimit -e` |
| 2 | `chrt -f 10 cmd` 报 `Operation not permitted` | 缺 `CAP_SYS_NICE`，或 `RLIMIT_RTPRIO=0` | `ulimit -r` 查看；生产上不要给普通用户实时权限 |
| 3 | 设了实时优先级后 SSH 卡死 | FIFO 忙循环饿死同核普通任务 | 用 `chrt -f 1` 起步，保留一个非实时核；知道 RT throttling 的存在 |
| 4 | `renice` 后多线程程序只有一个线程变了 | nice 在 Linux 上是每线程属性 | 对每个 TID `renice`，或在线程创建前设置 |
| 5 | 把 v1 的 `cpu.shares=1024` 抄到 v2 | v2 是 `cpu.weight`，刻度 1–10000 | 用 `cpu.weight` 重新换算，v2 默认 100 |
| 6 | 往父 cgroup 写 PID 报 `EBUSY` | v2 的 no-internal-process 规则 | 写进叶子 `.scope`/`.service`，或先关子控制器 |
| 7 | `cgroup.kill` 报 `EOPNOTSUPP` | 内核低于 5.14，或 cgroup v1 | 升级内核；v1 用 freezer + 遍历 `cgroup.procs` |
| 8 | `memory.max` 设了但进程没被杀 | 限制写在父节点，进程在别的叶子 | `cat /proc/PID/cgroup` 确认路径；读 `memory.events` 的 `oom_kill` |

第 4 条值得单独验证：`ps -L -o pid,tid,ni,comm -p PID` 列出每个线程的 nice，`renice -n 10 -p PID` 之后只有主线程变化，其余线程仍是旧值。要用 `renice` 改整组，先 `pgrep -T` 拿 TID 列表，或直接在程序里用 `setpriority(PRIO_PROCESS, 0, nice)` 对每个线程设置。

### 0.9.14 小结

两个实验各纠一个直觉：nice 是**权重**不是开关，只在同核竞争时兑现（270 : 29 ≈ 9.3 : 1，与 1024 : 110 一致）；cgroup 的限额是文件里的两个数字（`cpu.max`、`memory.max`），`systemd-run --user --scope` 一条命令就能拿到，不需要 root。如果只记住一件事，那就是**先确认「争的是什么」，再谈「调什么参数」**。

::: method 即时自测 · 0.9.14
**Q1（记忆）** 两个忙循环都不绑核时 utime 为什么接近 1:1？绑到同一核后为什么变成约 9:1？

**Q2（辨析）** `nice` 与 `cgroup` 的 CPU 限制有什么本质区别？各适合什么场景？

**Q3（应用）** 你要限制一个批处理任务「最多用半个核、最多 512 MiB」。给出不需要 root 的做法。

::: sol 答案
**A1** 4 核机器上两个循环各占一个核，谁也不用等谁，`nice` 没有可分配的争抢；绑到同一个核后只有一个核的算力可争，内核按权重 1024 : 110 分配时间片，比值约 9.3。

**A2** `nice` 是**相对优先级**：只在有竞争时影响谁多谁少，不设上限，空闲时照样用满；cgroup 是**绝对配额**：`CPUQuota=50%` 就是最多半个核，空闲也不能超标。前者适合「让别人先跑」，后者适合「不许超过预算」。

**A3** `systemd-run --user --scope -p CPUQuota=50% -p MemoryMax=512M -- <命令>`；要长期就用 `--user --unit=batchjob --collect`。查账用 `systemctl --user show -p MemoryCurrent -p CPUUsageNSec <unit>`。
:::

如果只记住一件事，那就是**先确认目标是哪个进程/哪一组，再决定发什么信号**。

::: method 即时自测 · 0.9
**Q1** 一个进程 `ps` 显示 `D`，你 `kill -9` 后它还在。为什么？下一步该看什么？

**Q2** `nohup ./job.sh &` 之后关闭 SSH 终端，进程没死，但第二天发现它停在 `T` 状态。最可能的原因是什么？

**Q3** 父进程 `fork` 后不 `wait`，子进程退出。`ps` 里看到 `Z`，`kill -9` 无效。怎么让这个 PID 消失？

**Q4** `kill -TERM -- -2210` 和 `kill -TERM 2210` 有什么区别？什么时候必须用前者？

::: sol 答案
**A1** `D` 是不可中断睡眠，进程卡在内核 I/O 里，信号要等 I/O 返回才处理。先看 `cat /proc/PID/stack`（root）或 `cat /proc/PID/wchan`，再查它等的是哪块设备/NFS；`vmstat 1` 的 `b` 列、`dmesg` 的 I/O 错误、`nfsstat -c` 都能给线索。杀不掉不是权限问题，是状态问题。

**A2** 它仍在原会话、仍挂着控制终端；后台读终端时终端驱动发了 `SIGTTIN`，默认动作是停止。日志里通常能看到它停在读 stdin 的地方。修法：重定向 stdin（`</dev/null`），或用 `setsid`/systemd 让它脱离控制终端。

**A3** 僵尸已经退出，信号无效；只能让父进程 `wait`。父进程若正常，催它回收；父进程若卡住，修父进程；父进程若死了，僵尸会被 PID 1 收养并回收。临时手段是杀掉父进程，但会留下孤儿，先确认父进程能否安全重启。

**A4** 前者发给进程组 2210 的所有进程，后者只发给 PID 2210。后台作业、shell 脚本启动的子进程树、`timeout` 包住的命令，都应该用进程组，否则子进程会漏掉。负号前加 `--` 是为了让 `kill` 不把 `-2210` 当成选项。
:::
:::
