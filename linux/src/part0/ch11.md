0.10 讲的是块设备上的字节。这一章讲这些字节怎么变成「能运行的程序」：发行版把二进制、配置、依赖关系打成一个 `.deb`；源码项目用 `configure`/`make` 把自己装进 `/usr/local`；动态链接器在运行时把 `.so` 找出来映射进地址空间；容器镜像则把一整套用户态再打一层。

四件事共享一个核心问题：**依赖关系在哪里被解析**。`apt` 在安装时解析包依赖，`ld.so` 在启动时解析库依赖，`make` 在构建时解析头文件和链接依赖，容器构建在打层时固化这些结果。搞清楚每一层由谁负责，`Package ... has no installation candidate`、`undefined symbol`、`error while loading shared libraries` 就不再是同一类「玄学错误」。

依赖在四个不同的时刻被解析，失败的表现也完全不同：

| 阶段 | 谁解析依赖 | 典型失败 | 主要工具 |
|:--|:--|:--|:--|
| 构建 | 编译器、链接器 | `undefined reference`、头文件找不到 | `make`、`pkg-config` |
| 安装 | apt / dpkg | `dependency problems`、版本冲突 | `apt`、`dpkg` |
| 启动 | 动态链接器 `ld.so` | `cannot open shared object file` | `ldd`、`readelf` |
| 镜像 | 构建器与层缓存 | 层里残留旧索引、版本漂移 | `docker history` |

命令以 Ubuntu 24.04（dpkg 1.22、apt 2.7、glibc 2.39、binutils 2.42、CMake 3.28）为准。旧式的 `aptitude`、`alien`、`ldconfig` 手工维护 `ld.so.conf` 的细节只在必要处提一句。

## 0.11.1 `.deb` 包里有什么 {#sec-0.11.1}

这一节回答：一个 `.deb` 解开之后是哪三段？装进系统的文件，「这个文件归谁」这条信息到底存在哪里？

::: preview 先抓住一件事
`.deb` 不是压缩包，是一个 `ar` 归档（比 tar 更老的「把几个文件装进一个文件」格式），里面固定三个成员：`debian-binary`（格式版本号）、`control.tar.*`（元数据和维护者脚本）、`data.tar.*`（要铺到根文件系统上的那棵目录树）。装完之后，「这个文件属于哪个包」不再问包文件，而是查 `/var/lib/dpkg/info/包名.list`——那是 dpkg 记下的所有权账本。
:::

先自己下载一个包拆开看。`apt-get download` 只把 `.deb` 取到当前目录，不安装也不需要 root。下面全部是 Ubuntu 24.04（aarch64、dpkg 1.22.6、apt 2.8.3）上的实测输出：

<div class="terminal" data-title="bash · Ubuntu 24.04 · /tmp/lab11_deb">
<pre><span class="p">&#36;</span> apt-get download curl
Get:1 https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble-updates/main arm64 curl arm64 8.5.0-2ubuntu10.16 [222 kB]
Fetched 222 kB in 4s (52.1 kB/s)
<span class="p">&#36;</span> ar t curl_8.5.0-2ubuntu10.16_arm64.deb
debian-binary
control.tar.zst
data.tar.zst
<span class="p">&#36;</span> ar tv curl_8.5.0-2ubuntu10.16_arm64.deb
rw-r--r-- 0/0      4 Oct 13 06:12 2026 debian-binary
rw-r--r-- 0/0    902 Oct 13 06:12 2026 control.tar.zst
rw-r--r-- 0/0 220717 Oct 13 06:12 2026 data.tar.zst
<span class="p">&#36;</span> ar x curl_8.5.0-2ubuntu10.16_arm64.deb && cat debian-binary
2.0</pre>
</div>

三段里只有 `data.tar.zst` 是内容本身；`control.tar.zst` 才 902 字节，却决定了装不装得上、装完跑什么。`ar tv` 的属主列是 `0/0`，即 root:root——包内文件的属主在打包那一刻就定死了（对照 0.11.11 的 `--root-owner-group`）。老包也可能是 `.gz`、`.xz`，dpkg 三种都认。

::: def 定义 0.11.1 · `.deb` 的三段结构 {#def-0.11.1}
`debian-binary`：一行纯文本，内容是格式版本（当前为 `2.0`）。`control.tar.*`：解出来是 `control`（包名、版本、依赖等字段）加若干可选文件（`md5sums`、`conffiles`、`triggers`、`shlibs`、四个维护者脚本）。`data.tar.*`：以 `./` 为根的完整目录树，安装时逐层铺到系统根目录上。dpkg 装包就是「解 data.tar 到根、按 control 记账、按顺序跑脚本」。
:::

`dpkg-deb` 提供不用解归档就能看的手段：

<div class="terminal" data-title="bash · Ubuntu 24.04 · 读一个 .deb">
<pre><span class="p">&#36;</span> dpkg-deb -I curl_8.5.0-2ubuntu10.16_arm64.deb
 new Debian package, version 2.0.
 size 221812 bytes: control archive=902 bytes.
     944 bytes,    20 lines      control
     313 bytes,     5 lines      md5sums
 Package: curl
 Version: 8.5.0-2ubuntu10.16
 Architecture: arm64
 Depends: libc6 (&gt;= 2.34), libcurl4t64 (= 8.5.0-2ubuntu10.16), zlib1g (&gt;= 1:1.1.4)
 Installed-Size: 556
<span class="p">&#36;</span> dpkg-deb -c curl_8.5.0-2ubuntu10.16_arm64.deb | head -4
drwxr-xr-x root/root         0 2026-10-13 06:12 ./
drwxr-xr-x root/root         0 2026-10-13 06:12 ./usr/
drwxr-xr-x root/root         0 2026-10-13 06:12 ./usr/bin/
-rwxr-xr-x root/root    329896 2026-10-13 06:12 ./usr/bin/curl
dpkg-deb: error: tar subprocess was killed by signal (Broken pipe)
<span class="p">&#36;</span> dpkg-deb -c curl_8.5.0-2ubuntu10.16_arm64.deb | wc -l
16
<span class="p">&#36;</span> mkdir -p ctrl && dpkg-deb -e apt_2.8.3_arm64.deb ctrl && ls ctrl
conffiles  control  md5sums  postinst  postrm  preinst  prerm  shlibs  triggers</pre>
</div>

`-I` 读 control 字段，`-c` 列文件清单，`-e` 只解 control.tar，`-x` 只解 data.tar——四条都不碰系统。那条 `Broken pipe` 不是包坏了：`dpkg-deb -c` 内部起 `tar` 子进程，`head -4` 提前退出把管道断了而已。这个包总共 16 个条目，除 `/usr/bin/curl` 外全是文档、man 页和补全脚本。

`ctrl` 那九个成员各管一件事，用 `apt` 这个包看得最清楚（实测大小：`control` 1563、`md5sums` 12942、`conffiles` 118、`triggers` 75、`shlibs` 34，四个脚本 `preinst` 354、`postinst` 2992、`prerm` 622、`postrm` 1451 字节）：

| 成员 | 管什么 | 谁在用它 |
|:--|:--|:--|
| `control` | 包名、版本、架构、`Depends`、描述 | apt 做依赖求解时读它 |
| `md5sums` | 每个文件的 MD5 | `dpkg -V 包名` 用它判断文件被改过没有 |
| `conffiles` | 哪些路径算配置文件 | 升级时不被覆盖，改动会交互询问（0.11.8） |
| `triggers` | 把某件重活推迟到一批包装完再做 | `apt` 的是 `activate-noawait ldconfig`（实测） |
| `preinst`/`postinst`/`prerm`/`postrm` | 安装/删除前后的脚本 | dpkg 按固定顺序调用（0.11.8） |
| `shlibs` | 这个库对外承诺的 soname 与包版本 | `dpkg-shlibdeps` 据此生成依赖（0.11.14） |

这九个成员描述的都是「安装这个动作」，不是「程序运行时的行为」——只有维护者脚本会真去动服务和用户。其中 `triggers` 最容易看漏：`apt` 的实测内容是两行，注释 `# Triggers added by dh_makeshlibs/13.14.1ubuntu5` 加 `activate-noawait ldconfig`。「装了带库的包就自动刷新动态库缓存」不是 apt 好心，是包自己声明了触发器；`shlibs` 那 34 字节的实测一行是 `libapt-private 0.0 apt (>= 2.8.3)`。这两个文件从哪来，留到 0.11.14。

**装完之后，所有权在另一套文件里。** dpkg 把账记在 `/var/lib/dpkg/`：`status` 是全部包的状态总表（`apt` 那段实测开头三行是 `Package: apt`、`Status: install ok installed`、`Version: 2.8.3`），`info/` 下每个包一组文件——`apt.list`、`apt.md5sums`、`apt.conffiles`、`apt.triggers`、`apt.postinst`……正是 control.tar 那几个成员落地后的样子。`apt.list` 有 371 行，从 `/.` 开始往后列全了这个包声明的每一个路径。双向查法就建在这本账上：

<div class="terminal" data-title="bash · Ubuntu 24.04 · 文件与包互相查">
<pre><span class="p">&#36;</span> dpkg -S /usr/bin/apt
apt: /usr/bin/apt
<span class="p">&#36;</span> dpkg -L apt | wc -l
371
<span class="p">&#36;</span> dpkg -V apt; echo "rc=&#36;?"
rc=0
<span class="p">&#36;</span> dpkg -S /usr/local/bin/chsrc
dpkg-query: no path found matching pattern /usr/local/bin/chsrc
<span class="p">&#36;</span> echo "rc=&#36;?"
rc=1</pre>
</div>

`dpkg -S` 回答「这个文件是谁装的」，`dpkg -L` 回答「这个包装了哪些文件」，`dpkg -V` 拿 `md5sums` 校验（实测无输出且返回 0，说明没被改过）。最后一条是最有用的反例：`/usr/local/bin/chsrc` 实实在在存在，dpkg 却说「查无此路径」并返回 1——它不归任何包管。这跟 [0.4](ch04.md) 的「文件属主」是两件事：`ls -l` 的 uid/gid 是内核权限意义上的主人，`dpkg -S` 回答的是「包管理器认不认它、升级卸载时管不管它」。一个文件可以属主是 root 却毫无包归属，而 `sudo make install` 装出来的东西恰恰全是这种孤儿——这就是 0.11.3 的入口。

::: method 判定流程 · 面对一个 `.deb` 或一个陌生文件
1. 想知道包里有什么：`ar t 包.deb` 看三段，`dpkg-deb -I` 看 `Depends`，`dpkg-deb -c` 看文件清单，`dpkg-deb -e 包.deb 目录` 看脚本与 `conffiles`。全程免 root。
2. 想知道某个文件归谁：`dpkg -S 路径`；报 `no path found` 时先 `dpkg -S "$(readlink -f 路径)"` 再下结论。
3. 想知道某个包装了哪些文件：`dpkg -L 包名`，或直接 `cat /var/lib/dpkg/info/包名.list`。
4. 怀疑文件被改过：`dpkg -V 包名`，它只校验 `md5sums` 里列出的那些文件。
:::

**读懂了包，还要知道谁在安装它。** dpkg 只干「把 `data.tar` 铺到位、按 `control` 记账、跑一遍 `control.tar` 里的脚本」，它**不解析依赖**：`dpkg -i foo.deb` 缺依赖会直接报错并把包留在未配置状态；`apt install ./foo.deb` 先读同一份 `control`、从源里补齐依赖，再回头调用 dpkg。两者不是替代关系，是分工：

| 命令 | 解析依赖 | 从源下载 | 适合 |
|:--|:--|:--|:--|
| `dpkg -i pkg.deb` | 否 | 否 | 已确认依赖满足的离线包 |
| `apt install ./pkg.deb` | 是 | 是 | 本地 deb，推荐 |
| `apt install pkg` | 是 | 是 | 正常安装 |
| `apt -f install` | 是 | 是 | 修复 dpkg 留下的缺依赖 |

`dpkg -i` 失败后别反复重试，先 `apt -f install`。半安装状态用 `dpkg --audit` 查、`dpkg --configure -a` 重跑配置（这两条要 root，本机未实测）；换机迁移用 `dpkg --get-selections` 导出、`dpkg --set-selections` 恢复，比手抄包名可靠。状态列怎么读、脚本按什么顺序跑，是 0.11.8 的事。

::: ex 例 0.11.1 · 「系统自带的库」到底归谁 {#ex-0.11.1}
先猜：是库没被找到，还是库找到了但没有那个符号？`-l` 的顺序有没有关系？

同事指着 `/lib/aarch64-linux-gnu/libc.so.6` 说：「这是系统自带的，`dpkg -S` 一查就知道是哪个包的。」你按他给的路径去查，Ubuntu 24.04 上的实测输出却是一句拒绝。先猜为什么，再看下面三条命令给出的解释：

```bash
dpkg -S /lib/aarch64-linux-gnu/libc.so.6
ls -ld /lib
dpkg -S "$(readlink -f /lib/aarch64-linux-gnu/libc.so.6)"
```

::: sol 解答
第一条报 `dpkg-query: no path found matching pattern /lib/aarch64-linux-gnu/libc.so.6`（返回码 1）。第二条给出原因：`/lib -> usr/lib`，是个符号链接——Ubuntu 24.04 是 merged-usr 布局，而账本里记的是真身路径。第三条先归一化再查，得到 `libc6:arm64: /usr/lib/aarch64-linux-gnu/libc.so.6`：冒号左边是**包名**（多架构包还带 `:arm64` 后缀），说明所有权记的是字符串路径，不是 inode。所以「别动 libc」的真正理由是：这条路径记在 `libc6` 的账本里，升级、`dpkg -V` 校验、卸载清理都按这本账走；手工盖一个同名文件，账本上的 MD5 立刻对不上。反过来，`dpkg -S` 查不到也不等于「垃圾文件」，可能只是你给的路径没归一化，或者它压根是源码安装/`snap`/脚本拷进去的。
:::
:::

::: errata 常见错误清单（0.11.1 节）
1. **「`.deb` 是 tar 压缩包，`tar xf` 就能解开」**——它是 `ar` 归档；正确姿势是 `ar x` 之后分别处理三段，或者干脆只用 `dpkg-deb -I/-c/-e/-x`。
2. **「`dpkg -S` 查不到就是文件没人管」**——它按字符串匹配路径，不跟随符号链接。merged-usr 上 `/lib/...`、`/usr/lib64/...` 这类路径要先 `readlink -f` 再查（见例 0.11.1）。
3. **「包里的 `Depends` 是文件级依赖」**——`Depends` 只有包名与版本范围；「哪个文件在哪个包里」是安装时才由 dpkg 记进 `.list` 的，包内没有任何路径级依赖表。
4. **「`Installed-Size` 就是 `.deb` 的大小」**——实测 curl 那个包文件 221812 字节，而 `Installed-Size: 556`（单位 KiB，指装好后占的空间）。
5. **「看了 `control` 就知道装完会发生什么」**——脚本是 control.tar 里独立的可执行文件，要 `dpkg-deb -e` 单独解出来读；`postinst` 完全可能建用户、重启服务。
:::

### 0.11.1 小结

一个 `.deb` 就是「ar 归档 + 两个 tar」：`control.tar` 说规则，`data.tar` 说内容。装完之后规则和数据都抄进 `/var/lib/dpkg/`——`status` 记状态，`info/包名.list` 记所有权，`info/包名.md5sums` 记校验和；解析依赖则永远是 apt 的事，不是 dpkg 的事。如果只记住一件事，那就是：**文件归谁，看 `/var/lib/dpkg/info/` 这本账，不看包文件，也不看 `ls -l` 的属主列。**

::: method 即时自测 · 0.11.1
**Q1（记忆）** `.deb` 里的三个 `ar` 成员分别是什么？哪个通常最小却最关键？

**Q2（辨析）** `dpkg -S /usr/local/bin/foo` 报 `no path found`，`ls -l` 显示它属主是 root。这两件事矛盾吗？

**Q3（应用）** 你要在不动系统的前提下确认某包会不会覆盖 `/etc/ssh/sshd_config`，写出命令。

**Q4（迁移）** 运维同事说「这台机器上 `libc6` 被人改过」。给出你的验证命令，并说明它的覆盖面与盲区。

::: sol 答案
**A1** `debian-binary`（格式版本，一行 `2.0`）、`control.tar.*`（元数据与脚本）、`data.tar.*`（文件树）。最小的是 `control.tar`（实测 902 字节 vs data 的 220717），但依赖、脚本、conffile 规则全在里面。
**A2** 不矛盾。前者是「包归属」，后者是「内核权限属主」，两套独立记账；dpkg 不认识它，但内核照样按 root 的权限判定谁能改。
**A3** `dpkg-deb -c 包.deb | grep sshd_config` 看包里有没有这个路径；再看 `dpkg-deb -e 包.deb ctrl && grep conffiles` 之后 `cat ctrl/conffiles`，判断它是否被当作配置文件保护（已安装包可直接 `dpkg -L openssh-server | grep sshd_config` 与 `cat /var/lib/dpkg/info/openssh-server.conffiles`）。
**A4** `dpkg -V libc6`：它按 `info/libc6.md5sums` 逐个校验包内文件，被改的会列出来。盲区有两个——`md5sums` 没列的文件（比如你新加的配置文件、`/etc` 下非 conffile 的东西）它不管；包外文件它也不管，所以「有人从源码装了一个 libc.so.6 盖在别处」要靠 `ldconfig -p` 与 `readelf -l` 追（0.11.4）。
:::
:::

## 0.11.2 apt 的源、依赖与 pinning {#sec-0.11.2}

这一节回答：一个包在源里往往同时存在好几个版本，apt 凭什么挑中某一个？为什么源里明明有更低的版本号，apt 却不去装它？

::: preview 先抓住一件事
apt 挑版本先比**优先级**（pin priority），版本号只在优先级相同的那一组里参与比较。`apt-cache policy 包名` 一条命令就能看清每个版本从哪些索引里来、各自值多少分、apt 最终选了谁。分数可以被 pinning（APT 优先级钉选，写在偏好文件里的打分规则）改写；本节的观察全部由普通用户完成，连 pinning 的效果都能在不改系统的前提下验证。
:::

[0.11.1](ch11.md#sec-0.11.1) 已经把分工说清了：dpkg 只解包、记账、跑脚本，解析依赖的是 apt。这一节看 apt 做决定时读的另外两样东西——源清单（去哪儿取包）与偏好文件（哪个版本优先）。下载和安装要 root，读清单不要。

### 源清单：deb822 与「源是索引，不是软件」

Ubuntu 24.04 默认不再用单行式的 `/etc/apt/sources.list`，改用 deb822 格式（键值分块的写法）的源文件。它世界可读，普通用户直接看：

```bash
$ ls -l /etc/apt/sources.list.d/ubuntu.sources
-rw-r--r-- 1 root root 232 Oct 21 20:07 /etc/apt/sources.list.d/ubuntu.sources
$ cat /etc/apt/sources.list.d/ubuntu.sources
Types: deb
URIs: https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports
Suites: noble noble-updates noble-backports noble-security
Components: main restricted universe multiverse
Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
```

上面是 Ubuntu 24.04.5（aarch64）实测输出，所以 URI 是 `ubuntu-ports`、架构是 `arm64`。四个字段各管一件事：`Types` 区分 `deb`（二进制包）与 `deb-src`（源码包）；`Suites` 是版本通道；`Components` 划定自由软件范围；`Signed-By` 指明验签用哪把钥匙。老的单行 `deb https://... noble main` 写法仍然支持，两种格式混在一台机器上时，别猜，跑一条 `apt-cache policy` 看实际读到了哪些通道。

`Signed-By` 指向 `/usr/share/keyrings/` 不是小节，是原则。老式的 `apt-key add` 把钥匙倒进全局 `trusted.gpg`，一个源的钥匙出问题就等于所有源都失守；现在是一个源配一把钥匙。放 keyring、改源、`apt update`、`apt install` 全要写 `/etc/apt/` 或 `/var/lib/apt/`，需要 root，本机未实测。

**源不是软件本身。** `apt update` 下载的是索引，落在 `/var/lib/apt/lists/`：

```bash
$ ls /var/lib/apt/lists | head -4
auxfiles
lock
mirrors.tuna.tsinghua.edu.cn_ros2_ubuntu_dists_noble_InRelease
mirrors.tuna.tsinghua.edu.cn_ros2_ubuntu_dists_noble_main_binary-arm64_Packages
```

文件名是「主机名 + 路径」拼出来的，每个通道一份 `InRelease` 加若干 `Packages` 文本索引。apt 的依赖求解整个在这批文本上做，`.deb` 本体要到 install 那一步才下载。所以「源里没有这个包」和「这个包下载失败」是两类错误：前者查索引（本节），后者查网络与签名。容器镜像里 `rm -rf /var/lib/apt/lists/*` 删的就是这些索引，原因见 0.11.7。

读索引时你可能撞见一条警告。这台机器上另有一个第三方源文件，权限是 `-rw-------`：

```text
-rw------- 1 root root 131 Oct 21 20:06 /etc/apt/sources.list.d/ros2.list
W: Unable to read /etc/apt/sources.list.d/ros2.list - open (13: Permission denied)
```

这是普通用户跑 apt 命令时的真实输出。它不改变已安装状态，但说明两件事：源目录里可以有多个文件，读不到的那条会被跳过；同一个命令在 root 和普通用户手里，看到的候选版本可能不一样。

### apt-cache policy：先看候选，再看分数

`apt-cache policy` 只读、免 root，是这一节第一条该跑的命令。先看一个装过的包（Ubuntu 24.04 实测）：

```bash
$ apt-cache policy curl
curl:
  Installed: 8.5.0-2ubuntu10.16
  Candidate: 8.5.0-2ubuntu10.16
  Version table:
 *** 8.5.0-2ubuntu10.16 500
        500 https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble-updates/main arm64 Packages
        500 https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble-security/main arm64 Packages
        100 /var/lib/dpkg/status
     8.5.0-2ubuntu10 500
        500 https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble/main arm64 Packages
```

`Installed` 是 dpkg 账上的当前版本，`Candidate` 是 apt 打算装的版本，两者的差就是 `apt upgrade` 会做的事。`Version table` 里每个版本块下面列出它出现在哪些索引里，行首那个数字就是这条「报价」的优先级：普通源 500，`/var/lib/dpkg/status`（已装版本自己充当一路候选）100。注意 `.16` 那个版本同时来自 `noble-updates` 和 `noble-security` 两个通道——一个版本可以有多个出处，分数也各报一次。

`***` 这个记号容易读错。上面那份输出里它落在已安装版本上；换成一个从没装过的包，整张表一个 `***` 都没有：

```bash
$ apt-cache policy nginx
nginx:
  Installed: (none)
  Candidate: 1.24.0-2ubuntu7.19
  Version table:
     1.24.0-2ubuntu7.19 500
        500 https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble-updates/main arm64 Packages
        500 https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble-security/main arm64 Packages
     1.24.0-2ubuntu7 500
        500 https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble/main arm64 Packages
```

所以判断「apt 会装哪个」永远读 `Candidate:` 那一行。想知道某个版本还出现在哪些索引里，用 `apt-cache madison`（按「包名 | 版本 | 索引文件」一行一条地平铺，适合 `grep`）：

```bash
$ apt-cache madison bash
      bash | 5.2.21-2ubuntu4 | https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble/main arm64 Packages
```

已经装好的机器上，「哪些能动」看 `apt list --upgradable`，它的通道标签直接告诉你新版来自哪一路：

```bash
$ apt list --upgradable 2>/dev/null | head -4
Listing...
cloud-init/noble-updates 26.2-0ubuntu1~24.04.2 all [upgradable from: 26.1-0ubuntu1~24.04.1]
containerd/noble-updates 2.2.1-0ubuntu1~24.04.4 arm64 [upgradable from: 2.2.1-0ubuntu1~24.04.3]
```

第一行 `Listing...` 是表头，脚本里要跳过；这个格式不稳定，给人看可以，别拿它当接口。真要预演一次安装，用只读的模拟（Ubuntu 实测）：

```bash
$ apt-get -s install nginx 2>/dev/null | sed -n '1,4p;8,14p'
NOTE: This is only a simulation!
      apt-get needs root privileges for real execution.
      Keep also in mind that locking is deactivated,
      so don't depend on the relevance to the real current situation!
The following additional packages will be installed:
  nginx-common
Suggested packages:
  fcgiwrap nginx-doc
The following NEW packages will be installed:
  nginx nginx-common
0 upgraded, 2 newly installed, 0 to remove and 30 not upgraded.
```

开头那四行 `NOTE` 是 apt 自己提醒你：这是模拟，真执行要 root，而且模拟期间没有加锁，结论可能和几秒后的真实状态不一致。看结尾的 `0 upgraded, 2 newly installed` 确认动作规模，再决定要不要真跑 `apt install`（那条要 root，本机未实测）。`Inst`/`Conf` 开头的逐行计划更适合用 `grep -E '^(Inst|Conf)'` 过滤，`full-upgrade` 会不会删包就从这里读。

### 优先级从哪来：这台机器上一个 pin 都没写

上面那些 500、100 不是谁规定的常量，是 apt 在没有规则时的默认打分。查一下默认打分器读到了什么（Ubuntu 实测）：

```bash
$ apt-config dump | grep -i pin
$ ls -l /etc/apt/preferences
ls: cannot access '/etc/apt/preferences': No such file or directory
$ ls -l /etc/apt/preferences.d/
-rw-r--r-- 1 root root 437 Apr  2  2024 ubuntu-pro-esm-apps
-rw-r--r-- 1 root root 429 Apr  2  2024 ubuntu-pro-esm-infra
```

第一条没有任何输出，说明 apt 配置里不存在 `Pin` 相关项；主偏好文件也不存在。`preferences.d/` 里那两个是发行版自带的，读其中一个的规则部分：

```text
Package: *
Pin: release o=UbuntuESMApps
Pin-Priority: 510
```

`o=` 匹配源的 Origin 字段，510 只比默认的 500 高 10。这个文件的注释自己说清了意图：只有 Ubuntu Pro 的 ESM 源真的存在时才生效，而这台机器上没有那个源，所以整条规则现在不起作用。**pin 的 suite 名或 origin 写错，apt 不报错，只静默失效**——这是 pinning 最常见的坑，唯一的复核手段就是再跑一次 `apt-cache policy` 看候选变没变。

::: def 定义 0.11.2 · pinning（APT 优先级钉选） {#def-0.11.2}
pinning 是「给版本打分」的规则，写在 `/etc/apt/preferences` 与 `/etc/apt/preferences.d/*.pref` 里，一条规则三行：`Package:` 选哪些包（支持空格分隔多个名字与通配），`Pin:` 选条件（`release` 按源的 `a=`/`o=`/`l=`/`c=` 字段匹配、`origin` 按主机名、`version` 按版本通配），`Pin-Priority:` 打分。apt 求解时先比分数，同分再比版本号。几个阈值的语义：`>= 1001` 允许用低版本覆盖已装的高版本（降级）；`990`–`1000` 强烈偏好，但仍不主动降级；`500` 是普通源的默认分；`100` 是已装版本从 `/var/lib/dpkg/status` 拿到的分；`<= 0` 禁止安装。设置 target release（`APT::Default-Release` 或 `apt-get -t`）时，属于该 release 的版本拿 990，其余拿 500。
:::

改这些文件要 root，本机未实测。但**验证 pinning 不需要 root**：apt 允许临时替换偏好文件的路径，`-o Dir::Etc::preferences=文件` 就把那个文件当成唯一的偏好来源。我们在家目录里写一条规则，故意把 nginx 钉到**更旧**的版本：

```bash
$ cat pin2
Package: nginx
Pin: version 1.24.0-2ubuntu7
Pin-Priority: 990
$ apt-cache policy -o Dir::Etc::preferences=$HOME/lab0c11_apt/pin2 nginx
nginx:
  Installed: (none)
  Candidate: 1.24.0-2ubuntu7
  Version table:
     1.24.0-2ubuntu7.19 500
        500 https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble-updates/main arm64 Packages
        500 https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble-security/main arm64 Packages
     1.24.0-2ubuntu7 990
        500 https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble/main arm64 Packages
```

`Candidate` 换成了旧版本。看清楚了：`.19` 版本号更大，但只有 500；`.7` 版本小一档，靠 990 赢。这就是「apt 选优先级最高的版本，不是版本号最大的版本」的直接证据。读版本表时有个细节：块首那个数字是这条规则给的分（`990`），块内缩进行的 `500` 是那一路索引原本的默认分，两者不一致时以块首为准。

分数换成负数，语义立刻变：

```bash
$ apt-cache policy -o Dir::Etc::preferences=$HOME/lab0c11_apt/pin3 nginx
nginx:
  Installed: (none)
  Candidate: 1.24.0-2ubuntu7.19
  Version table:
     1.24.0-2ubuntu7.19 500
        500 https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble-updates/main arm64 Packages
        500 https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble-security/main arm64 Packages
     1.24.0-2ubuntu7 -1
        500 https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble/main arm64 Packages
```

`pin3` 和 `pin2` 只差最后一行的数字（`-1`），候选就回到新版本：负分表示「这个版本永不安装」， apt 于是把它从竞争里撤掉。这类规则用来封掉整个实验通道（`Pin: release a=experimental` 配 `-1`）比删源文件安全得多。

现在试真的：拿 `pin2` 去模拟安装，求解器直接罢工（Ubuntu 实测）：

```bash
$ apt-get -s install -o Dir::Etc::preferences=$HOME/lab0c11_apt/pin2 nginx 2>&1 | tail -3
The following packages have unmet dependencies:
 nginx : Depends: nginx-common (= 1.24.0-2ubuntu7) but 1.24.0-2ubuntu7.19 is to be installed
E: Unable to correct problems, you have held broken packages.
```

原因在 0.11.1 见过的 `Depends: libcurl4t64 (= 8.5.0-2ubuntu10.16)` 那种写法上：`=` 是**精确同版本**。`nginx` 被钉在 `.7`，它要求 `nginx-common` 也必须是 `.7`，可 `nginx-common` 没人钉，求解器按默认分把候选定成 `.19`，于是自相矛盾。**钉一个包，就要钉住它整个同版本族**——`Package:` 一行里列全，或者改用 `Pin: release a=noble-updates` 这种按通道打分的写法。

要真降级就得给 1001，同版本族一起钉：

```bash
$ cat pin
Package: curl libcurl4t64
Pin: version 8.5.0-2ubuntu10
Pin-Priority: 1001
$ apt-get -s install -o Dir::Etc::preferences=$HOME/lab0c11_apt/pin curl 2>/dev/null | grep -E '^The following'
The following packages were automatically installed and are no longer required:
The following additional packages will be installed:
The following packages will be REMOVED:
The following NEW packages will be installed:
The following packages will be DOWNGRADED:
```

`DOWNGRADED` 那一类出现了，`Inst` 行里 `curl` 与 `libcurl4t64` 都从 `[8.5.0-2ubuntu10.16]` 换成 `(8.5.0-2ubuntu10 ...)`。同一批输出里还有 `REMOVED`——一次降级会牵动别的包被移除，这就是为什么生产机上 `1001` 要慎之又慎。

### hold 是另一条路，顺带说清「为什么要 root」

`apt-mark hold`（标记保留）走的是完全不同的机制：它不改分数，而是把已装版本声明为「别动」。这条命令要 root，我们在普通用户下实测了它失败的样子：

```bash
$ apt-mark hold bash
dpkg: error: required read/write access to the dpkg database directory /var/lib/dpkg
E: Sub-process dpkg --set-selections returned an error code (2)
E: Executing dpkg failed. Are you root?
$ apt-mark showhold
$ 
```

报错信息本身就是答案。`apt-mark` 底层调用 `dpkg --set-selections`，它要**写 `/var/lib/dpkg` 这本账**——也就是 [0.11.1](ch11.md#sec-0.11.1) 里那个 `status` 总表和 `info/*.list` 清单所在的地方。所以「装软件为什么要 root」有两层：往 `/usr/bin`、`/usr/lib` 这些系统目录写文件，以及改包管理器的数据库；后者常被忽略，但它才是「升级、校验、卸载能找回来」的依据。只读的那半边普通用户全都能跑：上面 `apt-mark showhold` 正常返回，本机输出为空（没有包被 hold）。

hold 适合内核、驱动、数据库这类不能随手换版本的组件。它不改变 `Candidate`，也不能用来降级，只是让已装版本不参与升级；解除用 `apt-mark unhold`，同样要 root。真要钉版本、跨通道选版本，才轮到 pinning。

::: ex 例 0.11.2 · 990 到底从哪来 {#ex-0.11.2}
网上大量教程写着「`noble-updates` 的优先级通常是 990」。先猜两件事：这台 Ubuntu 24.04 上跑 `apt-cache policy curl` 会不会出现 990？如果不会，那 990 这个数是谁、在什么条件下给的？

::: sol 解答
不会出现——本机的 `curl` 输出里三行全是 500（上面已实测）。990 属于 target release（目标发行版，配置项 `APT::Default-Release`，命令行等价写法是 `apt-get -t`），而这台机器没设：

```bash
$ apt-config dump | grep -i Default-Release
$ 
```

手工设一次就能把 990 逼出来，全程免 root（Ubuntu 实测）：

```bash
$ apt-cache policy -o APT::Default-Release=noble curl | head -6
curl:
  Installed: 8.5.0-2ubuntu10.16
  Candidate: 8.5.0-2ubuntu10.16
  Version table:
 *** 8.5.0-2ubuntu10.16 990
        990 https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports noble-updates/main arm64 Packages
```

还有一件事值得注意：`noble/main` 里那个旧版本 `8.5.0-2ubuntu10` 同样升到了 990，因为 `Default-Release=noble` 匹配的是 codename（代号），而 `noble-updates`、`noble-security` 的 codename 也都是 `noble`。「`-t` 指定通道」并不等于「只要那一路」，要精确就把规则写成 `Pin: release a=noble-updates`。至于日常与跨版本升级：`apt upgrade` 不删包，`apt full-upgrade` 允许为解依赖而删包换包，两条都要 root，本机未实测。
:::
:::

::: errata 关于 apt 源的五个误解
1. **「`apt update` 会升级软件」**——它只把索引重写进 `/var/lib/apt/lists/`，一个包都不动；升级是 `apt upgrade` / `apt full-upgrade` 的事。
2. **「`Candidate` 就是版本号最大的」**——apt 先比优先级，同分才比版本。把旧版本钉到 990，候选立刻变成旧的（上面实测）。
3. **「`990` 通常是 `noble-updates`」**——990 只发给属于 target release 的版本；Ubuntu 24.04 默认没设 target release，所有通道都是 500。
4. **「pin 写错了 apt 会报错」**——`Pin:` 里的 suite、codename、origin 拼错只会让规则静默失效。唯一可靠的复核是改完再跑一次 `apt-cache policy` 看 `Candidate`。
5. **「`apt-mark hold` 是一种 pin」**——机制不同：hold 改的是 dpkg 数据库里的选择状态，不改分数、不能降级、不改变候选版本。
6. **「普通用户和 root 跑同一条 `apt-cache policy` 结果一样」**——源目录里权限 600 的文件普通用户读不到，会多一条 `W: Unable to read ...`，看到的通道集合也可能少一路。
:::

### 0.11.2 小结

apt 的候选版本是一次求解结果，不是「仓库里最新的那一个」：源清单给出有哪些版本，`/etc/apt/preferences.d/` 的规则给每个版本打分，先分后版本。如果只记住一件事，那就是 **`Candidate:` 那行是结论，`Version table` 里每行开头的数字是理由**。改规则要 root（写 `/etc/apt/preferences.d/`），验证规则不用 root（`-o Dir::Etc::preferences=你的文件`）。

::: method 即时自测 · 0.11.2
**Q1（记忆）** apt 在两个候选版本之间做决定，依次看什么？`Version table` 里那条 `100 /var/lib/dpkg/status` 是什么？

**Q2（辨析）** `apt list --upgradable` 的一行写成 `ghostscript/noble-updates,noble-security 10.02.1~dfsg1-0ubuntu7.10 arm64 [upgradable from: ...]`。两个通道名是说要装两个包吗？

**Q3（应用）** 不动 `/etc`，用一条命令证明「990 来自 target release 而不是某个通道的固有属性」。

**Q4（迁移）** 同事只把 `docker-ce` 钉在 `Pin: version 5:27.*`、分数 990，之后 `apt-get -s install docker-ce` 报 unmet dependencies。给出最可能的原因和你的验证命令。

::: sol 答案
**A1** 先看优先级分数，同分再比版本号（比较规则不是字符串排序，见 0.11.9）。`100 /var/lib/dpkg/status` 是「已装版本自己」作为一路候选参与比较，分数 100——低于任何普通源的 500，所以只要源里有同包的任意版本，已装版本就不会被当成「新」的候选来降级。
**A2** 不是。那是同一个版本的两个出处（这个版本同时出现在 `noble-updates` 与 `noble-security` 的索引里），与前面 `apt-cache policy curl` 里一个版本块下两行 500 是同一件事。
**A3** `apt-cache policy -o APT::Default-Release=noble curl`：默认全 500 的三个通道一次升到 990，`Candidate` 不变。
**A4** 同版本族的精确依赖没被一起钉住——`docker-ce` 很可能带 `Depends: docker-ce-rootless-extras (= 完全相同的版本)` 这类 `=` 依赖，别的包按默认分选了新版本，两边凑不上。验证：`apt-cache policy docker-ce docker-ce-cli containerd.io` 看各家的 `Candidate`，再 `apt-cache depends docker-ce | grep '='` 找出精确同版本的依赖；修法是 `Package:` 一行里把族内成员列全，或改用 `Pin: release` 按通道打分。
:::
:::

## 0.11.3 源码构建：`prefix`、`DESTDIR` 与打包 {#sec-0.11.3}

这一节回答：`./configure && make && make install` 这三行，各自往磁盘上写什么？`--prefix` 和 `DESTDIR` 都带路径，为什么不能混成一谈？为什么最后一步不 root 就写不进去？

::: preview 先抓住两件事
`--prefix` 回答「程序以后认为自己在哪」：配置阶段它被抄进 Makefile，编译阶段被烧进二进制。`DESTDIR`（暂存前缀）回答「这次 `install` 命令额外在路径前面加一段什么」：它只改变文件落在哪个目录树里，不改变程序以后报出的任何路径。两者合起来是打包的标准姿势——先 staged 安装到 `stage/usr/...`，再 `dpkg-deb --build` 封成 `.deb`，从此这个程序回到包管理器的账本里。
:::

[0.11.1](ch11.md#sec-0.11.1) 留了一个烂摊子：`sudo make install` 装出来的文件实实在在存在，`dpkg -S` 却查无归属。这台 Ubuntu 24.04 的 `/usr/local/bin` 里有 14 个条目，随手查一个（实测）：

```bash
$ dpkg -S /usr/local/bin/chsrc
dpkg-query: no path found matching pattern /usr/local/bin/chsrc
```

这一节解释它是怎么产生的，以及怎么用 `DESTDIR` 让源码安装重新有账可查。至于打成一个正式的发行版包（`debian/` 目录、`${shlibs:Depends}` 从哪来），是 [0.11.14](ch11.md#sec-0.11.14) 的事。

### 三行命令各写了什么

我们全程用普通用户、在自己的家目录里跑一个最小 autotools 工程。`configure` 不用手写，它由 autoconf 2.71 从 `configure.ac` 生成：

```bash
$ cat configure.ac
AC_INIT([lab0c11app], [1.0])
AC_PROG_CC
AC_CONFIG_FILES([Makefile])
AC_OUTPUT
$ autoconf && ls -l configure
-rwxrwxr-x 1 juanwang juanwang 121671 Oct 29 21:22 configure
```

`configure` 是个 119 KB 的 shell 脚本，跑起来是一长串「checking ...」。截取尾部几行（Ubuntu 实测）：

```bash
$ ./configure --prefix=/usr/local --sysconfdir=/etc
checking whether the C compiler works... yes
checking for suffix of object files... o
checking whether we are using the GNU C compiler... yes
checking whether gcc accepts -g... yes
checking for gcc option to enable C11 features... none needed
configure: creating ./config.status
config.status: creating Makefile
```

`config.status: creating Makefile` 是这一段的重点：**configure 的产出就是一份填好数字的 Makefile**。模板里写的是 `prefix = @prefix@`，脚本做的事就是把你命令行给的目录填进 `@...@`：

```bash
$ grep -n '^prefix\|^sysconfdir\|^CFLAGS' Makefile
1:prefix = /usr/local
2:sysconfdir = /etc
5:CFLAGS = -g -O2 -DSYSCONFDIR=\"$(sysconfdir)\"
```

`--help` 里那几个目录参数的默认值，是 FHS（Filesystem Hierarchy Standard，规定 `/usr`、`/usr/local`、`/var` 各放什么的那份惯例）在 autotools 里的投影（实测）：

```bash
$ ./configure --help | grep -E '^\s+--(prefix|sysconfdir|localstatedir)'
  --prefix=PREFIX         install architecture-independent files in PREFIX
  --sysconfdir=DIR        read-only single-machine data [PREFIX/etc]
  --localstatedir=DIR     modifiable single-machine data [PREFIX/var]
```

方括号里的 `[PREFIX/etc]` 说明：不显式写 `--sysconfdir=/etc`，配置目录就是 `/usr/local/etc`，程序会去那儿找配置文件，而你写在 `/etc`。同理不写 `--prefix` 时多数项目默认 `/usr/local`（这正是不和发行版的 `/usr` 抢地方），但有些项目默认 `/usr`——装进去就成了账本外的文件盖在账本内的路径上。

编译阶段只有一条命令，`make` 会把它执行的每一行打出来：

```bash
$ make
gcc -g -O2 -DSYSCONFDIR=\"/etc\" -o app src/app.c
$ ./app
sysconfdir=/etc
```

看 `-DSYSCONFDIR=\"/etc\"`：`/etc` 这个字符串此刻**已经进了二进制**。安装阶段只是把文件搬到它自己说的那个位置上去，搬运不会改写它。记住这一点，下面 `DESTDIR` 的全部道理就一句话讲完了。并行编译用 `make -j"$(nproc)"`（本机 `nproc` 输出 `4`）；机器内存小时调回 `-j2`，链接阶段比编译阶段更吃内存。`make check`（跑上游自带的测试套件）我们这个最小工程里没有，未实测；真实项目里它失败通常意味着依赖版本或编译选项不对，先别装。

### 为什么 `make install` 非要 root

先看 `install` 目标到底执行什么。`make -n` 只打印命令、不执行，普通用户就能看（实测）：

```bash
$ make -n install
install -Dm755 app /usr/local/bin/app
```

同一条命令让普通用户真跑，就撞在墙上（Ubuntu 实测）：

```bash
$ make install
install: cannot create regular file '/usr/local/bin/app': Permission denied
make: *** [Makefile:11: install] Error 1
```

这里要补的可能正是很多人一直没细想的一层：**装软件需要 root，是两种写操作**。第一种是往 `/usr/bin`、`/usr/lib` 这些系统目录写文件，也就是上面这条 `Permission denied`；第二种是改包管理器自己的数据库——0.11.2 里 `apt-mark hold` 报的 `required read/write access to the dpkg database directory /var/lib/dpkg` 就是同一类问题。`sudo make install` 只做了第一种，第二种完全没做，所以文件装上了却进不了账本。装进系统目录要 root，本机未实测（`sudo` 需密码）。

::: def 定义 0.11.3 · `prefix` 与 `DESTDIR` 的分工 {#def-0.11.3}
`prefix` 是**安装路径的根**，在配置阶段展开成 `bindir=$(prefix)/bin` 这类变量，再被编译选项写进二进制，改它意味着重新 configure、重新编译。`DESTDIR` 是**临时前缀**，只在 `install` 命令执行的那一瞬间被拼在目标路径前面：`$(DESTDIR)$(bindir)/app`。它不需要重新编译，也不需要 `prefix` 有任何变化；`DESTDIR=/tmp/stage --prefix=/usr` 的结果是文件躺在 `/tmp/stage/usr/bin/app`，而程序运行时仍然认为自己装在 `/usr/bin/app`。谁在用这个机制：打包工具（`dpkg-deb`、`rpmbuild` 的 buildroot、`nix` 的 store 路径）都是「staged 安装 → 把暂存树打包」。
:::

`DESTDIR` 是普通用户也能用的机制，因为暂存目录在你自己有权限的地方：

```bash
$ make install DESTDIR=$HOME/lab0c11_src/stage
install -Dm755 app /home/juanwang/lab0c11_src/stage/usr/local/bin/app
$ find stage | sed 's|^[^/]*/||'
stage
stage/usr
stage/usr/local
stage/usr/local/bin
stage/usr/local/bin/app
$ stage/usr/local/bin/app
sysconfdir=/etc
```

（Ubuntu 实测）三行输出连起来读：install 命令里 prefix 被完整地保留下来，只是前面多了一段暂存根；文件真实位置在 `$HOME/lab0c11_src/stage/usr/local/bin/app`；执行它，程序报出的仍然是 `/etc`。**这就是「暂存不改变运行时路径」的直接证据**，也是 `DESTDIR` 存在的唯一理由：造一棵和系统根同构、但完全在你手里的树。

打包时用另一个 prefix 才是常规做法：发行版包应该装进 `/usr`，`/usr/local` 留给本机源码安装（这条差异在 0.11.14 的 `lintian` 坑里会再出现）。改成 `--prefix=/usr` 重新配置、暂存、封包（实测）：

```bash
$ ./configure --prefix=/usr >/dev/null && make clean >/dev/null && make >/dev/null
$ make install DESTDIR=$HOME/lab0c11_src/pkg
install -Dm755 app /home/juanwang/lab0c11_src/pkg/usr/bin/app
$ find pkg -type f
pkg/usr/bin/app
```

在 `pkg/` 里补一个 `DEBIAN/control`（三行必填：`Package`、`Version`、`Architecture`，加一段缩进的 `Description`），归档就能封起来了：

```bash
$ dpkg-deb --build --root-owner-group pkg lab0c11app_1.0_arm64.deb
dpkg-deb: building package 'lab0c11app' in 'lab0c11app_1.0_arm64.deb'.
$ ar t lab0c11app_1.0_arm64.deb
debian-binary
control.tar.zst
data.tar.zst
```

`--root-owner-group` 把包内条目的属主固定成 root:root。不加它会怎样，看这个对比：构建者是 `juanwang`（UID 1000），而清单显示的是 `root/root`——

```bash
$ dpkg-deb -c lab0c11app_1.0_arm64.deb
drwxr-xr-x root/root         0 2026-10-29 21:25 ./
drwxr-xr-x root/root         0 2026-10-29 21:25 ./usr/
drwxr-xr-x root/root         0 2026-10-29 21:25 ./usr/bin/
-rwxr-xr-x root/root     72272 2026-10-29 21:25 ./usr/bin/app
```

三段结构和 [0.11.1](ch11.md#sec-0.11.1) 拆开的官方包一模一样，`data.tar.zst` 里就是那棵暂存树。装上它要 root（`dpkg -i`，本机未实测），但从此这个文件有了账本、有了 `md5sums`、能被 `dpkg -S` 查到——源码安装和包管理器的冲突就是这么化解的。`checkinstall`（拦截 `make install` 顺手生成 deb）和 `stow`（把每个软件装进 `/usr/local/stow/包名`，用符号链接摊到 `/usr/local`）在 VM 上都没装，未实测：装它们要 root。

`make -j"$(nproc)"` 用全部 CPU 并行编译；内存小的机器用 `-j2` 或 `-j4`，否则链接阶段可能 OOM。`make check` 失败不要跳过：测试失败通常意味着 ABI、依赖版本或编译选项不对，装上去也会在运行时出问题。卸载源码安装的程序没有 `make uninstall` 时只能按 `make install` 的日志逐个删，或者用 `stow` 管理 `/usr/local/stow/` 下的目录。

### 0.11.3 小结

三行的分工：`./configure --prefix=/usr` 决定**运行时**路径（二进制里写死的 `--prefix`）；`make` 只编译不安装；`make install DESTDIR=/tmp/pkg` 把整个安装树**搬到另一个根下**，用来打包而不是真装。所以 `prefix` 是「将来装到哪」，`DESTDIR` 是「这次先放到哪」。如果只记住一件事，那就是**打包永远带 `DESTDIR`**——不带的 `make install` 只能靠 root 写系统目录，且 `dpkg -S` 查无归属。

## 0.11.4 静态库、共享库与 soname {#sec-0.11.4}

这一节回答：`.a` 与 `.so` 除了文件大小还差在哪？`soname` 是给谁看的？为什么升级共享库会「找不到」？

::: preview 先抓住一件事
链接期找的是 `libfoo.so`（开发名），运行期加载的是 `libfoo.so.1`（`soname`）——**两个名字是两个层**，混了就会出「编译过、跑不起来」。
:::

静态库在链接时把代码复制进可执行文件，共享库在运行时由动态链接器映射。两者的差别不只是「文件大小」：

| 维度 | 静态库 `.a` | 共享库 `.so` |
|:--|:--|:--|
| 链接时机 | 编译链接时 | 程序启动/首次使用时 |
| 可执行文件大小 | 大 | 小 |
| 库更新 | 要重新链接 | 替换 `.so` 即可（ABI 兼容时） |
| 内存共享 | 每个进程一份 | 多个进程共享代码页 |
| 部署 | 单文件，依赖少 | 需要 loader、soname、搜索路径 |
| 安全更新 | 每个程序重编 | 更新库文件即可 |

共享库的核心概念是 **soname**（shared object name）：库文件可以叫 `libfoo.so.1.2.3`，但 soname 是 `libfoo.so.1`，可执行文件记录的是 soname。运行时 loader 按 soname 找文件，升级小版本只要替换 `libfoo.so.1.2.3` 并重建 `libfoo.so.1` 符号链接，不需要重编程序。

```bash
# 静态库
cc -std=c17 -O2 -c foo.c -o foo.o
ar rcs libfoo.a foo.o

# 共享库：-fPIC 必须，soname 必须
cc -std=c17 -O2 -fPIC -c foo.c -o foo.pic.o
cc -shared -Wl,-soname,libfoo.so.1 -o libfoo.so.1.2.3 foo.pic.o
ln -sf libfoo.so.1.2.3 libfoo.so.1
ln -sf libfoo.so.1 libfoo.so

# 链接：-L 指定目录，-lfoo 找 libfoo.so
cc -std=c17 main.c -L. -lfoo -Wl,-rpath,'$ORIGIN/lib' -o app
```

`-fPIC` 生成位置无关代码，共享库必须；静态库可以不 `-fPIC`，但如果要链进共享库就必须。`-Wl,-soname,...` 把 soname 写进 `.dynamic` 段。`libfoo.so` 这个不带版本的名字只在**链接时**用，运行时用 soname；只装 `libfoo.so` 不装 `libfoo.so.1`，程序启动会报找不到。

<pre class="layout">
foo.c ──cc -c──► foo.o ──ar──► libfoo.a ─────────┐
                    │                            ├──► app（静态链接，代码复制）
                    └─cc -shared -fPIC──► libfoo.so.1.2.3
                                              │
                                     soname: libfoo.so.1
                                              │
app（动态链接）──► ld-linux.so ──► ld.so.cache / RPATH / LD_LIBRARY_PATH
</pre>

读图：静态链接在上半支，链接完就与库无关；动态链接在下半支，运行时才找库。找库的顺序由 loader 决定：`DT_RPATH`（如果没 `RUNPATH`）→ `LD_LIBRARY_PATH` → `DT_RUNPATH` → `/etc/ld.so.cache` → `/lib`、`/usr/lib`。`RPATH` 和 `RUNPATH` 的区别是前者会被 `LD_LIBRARY_PATH` 覆盖，后者不会；现代链接器默认生成 `RUNPATH`。

`$ORIGIN` 表示「可执行文件所在目录」，`-Wl,-rpath,'$ORIGIN/lib'` 让程序在自身目录的 `lib/` 下找库，适合自包含发布。`LD_LIBRARY_PATH` 是临时的调试手段，不是部署方案：它会污染所有子进程，setuid 程序会忽略它（secure-execution mode），而且容易被恶意库劫持。生产环境用 `RUNPATH`、`ldconfig` 或把库装进系统路径。

`ldconfig` 扫描 `/etc/ld.so.conf` 和 `/etc/ld.so.conf.d/*.conf` 里的目录，生成 `/etc/ld.so.cache`。把 `/usr/local/lib` 加进去：

```bash
echo /usr/local/lib | sudo tee /etc/ld.so.conf.d/usr-local.conf
sudo ldconfig
ldconfig -p | grep libfoo
```

`ldconfig -p` 看缓存里有哪些库。`ldd ./app` 看程序依赖哪些库、各自解析到哪个路径；但它会调用 loader，对不可信二进制不要用，改用 `readelf -d ./app` 和 `objdump -p ./app`。

### 0.11.4.1 机制一层：`.dynamic` 里到底记了什么

`readelf -d libfoo.so.1.0` 能看到两类条目：`SONAME`（这个库希望别人怎么称呼自己）与 `NEEDED`（它自己依赖谁）。可执行文件里也有 `NEEDED`，但**没有** `SONAME`——它只是一个使用者，不提供名字。

运行时 `ld.so` 的步骤是：读程序的 `NEEDED` 列表 → 对每个名字按搜索顺序找文件 → 找到后读它的 `SONAME` 做一致性检查（`dlopen` 时更严格）→ 映射 → 处理重定位。所以「三个名字」的分工是：

- `libfoo.so.1.2.3`（真实文件）：包的版本，随时可以换；
- `libfoo.so.1`（`soname`，通常是软链）：**ABI 承诺**，只要接口兼容就不变；
- `libfoo.so`（开发软链）：只给 `-lfoo` 用，运行时不看。

`objdump -p` 也能看这些条目，而且不需要 `readelf`（macOS 上用 `otool -D/-L` 对应）。判据：`SONAME` 与程序里 `NEEDED` 的字符串**逐字相等**，差一个字符就是断裂。

### 0.11.4 小结

静态库在链接时把目标代码**复制**进可执行文件，运行时不依赖；共享库只在链接期记下 `NEEDED`，运行时由 `ld.so` 映射。`soname` 写在 `.so` 的 `DT_SONAME` 里，是**运行期**的稳定名（`libfoo.so.1`），`libfoo.so` 只是给 `-lfoo` 用的开发符号链接。如果只记住一件事，那就是**版本升级靠 `soname` 变、开发链接靠 `.so` 软链**。

::: method 即时自测 · 0.11.4
**Q1（记忆）** `libfoo.so`、`libfoo.so.1`、`libfoo.so.1.2.3` 三者各是谁在用？

**Q2（辨析）** 静态库与共享库在「升级后要不要重新编译程序」上有什么差别？

**Q3（应用）** 你升级了一个库，老程序启动时报 `cannot open shared object file: libfoo.so.1`。最可能的原因是什么？

::: sol 答案
**A1** `libfoo.so` 是开发时 `-lfoo` 找的软链；`libfoo.so.1` 是 `soname`，写进程序的 `NEEDED`，运行时由 `ld.so` 按它找；`libfoo.so.1.2.3` 是真实文件，版本号里前两段通常跟 `soname` 对齐。

**A2** 静态库把代码复制进程序，升级库对已编译的程序**没有任何影响**，要重新链接才生效；共享库升级后，只要 `soname` 不变，程序下次启动就用新库。

**A3** 新库的 `soname` 变成了 `libfoo.so.2`（或只装了 `.so.2` 没留 `.so.1`），而老程序的 `NEEDED` 仍是 `.so.1`——这是 ABI 不兼容时该发生的事；若本应兼容，则是打包时漏了 `.so.1` 的兼容软链。
:::

## 0.11.5 两个链接错误的排查顺序 {#sec-0.11.5}

这一节回答：链接错误只有两类，怎么在十秒内分清？每一类的第一条命令是什么？

::: preview 先抓住一件事
`undefined reference` 是**链接期**找不到符号（库没给、顺序不对）；`cannot open shared object file` 是**运行期**找不到文件（路径不对）。前者 `nm`，后者 `readelf -d`。
:::

动态库问题最终只会落到两类报错。先分清是哪一类，再决定查什么：

| 报错 | 含义 | 第一条命令 |
|:--|:--|:--|
| `error while loading shared libraries: libfoo.so.1: cannot open shared object file` | loader 找不到这个 soname | `ldd ./app`、`readelf -d ./app` |
| `undefined symbol: foo` | 库找到了，但里面没有这个符号 | `nm -D libfoo.so.1`、`objdump -T` |
| `version 'GLIBC_2.38' not found` | 程序要的 glibc 版本比运行环境新 | `ldd --version`、`objdump -T ./app | grep GLIBC` |
| `wrong ELF class: ELFCLASS32` | 32/64 位不匹配 | `file ./app libfoo.so.1` |
| `cannot open shared object file` 但文件存在 | soname 不对、缓存没更新、RUNPATH 不包含该目录 | `readelf -d`、`ldconfig -p` |

排查「找不到库」按这个顺序：

1. `file ./app` 确认架构，`file libfoo.so.1` 确认库的架构一致；
2. `readelf -d ./app | grep -E 'NEEDED|RPATH|RUNPATH'` 看它要的 soname 和搜索路径；
3. `ldd ./app` 看 loader 实际解析到哪，`not found` 的那一行就是缺口；
4. `ldconfig -p | grep libfoo` 看缓存里有没有；没有就检查 `/etc/ld.so.conf.d/`；
5. `find / -name 'libfoo.so*' 2>/dev/null` 找文件在哪，确认目录是否在搜索路径里。

<div class="terminal" data-title="bash · 定位动态库">
<pre><span class="p">&#36;</span> ldd ./app
	linux-vdso.so.1 (0x00007ffd8c3f9000)
	libfoo.so.1 =&gt; not found
	libc.so.6 =&gt; /lib/x86_64-linux-gnu/libc.so.6 (0x00007f3c2a1b2000)
<span class="p">&#36;</span> readelf -d ./app | grep -E 'NEEDED|RPATH|RUNPATH'
 0x0000000000000001 (NEEDED)   Shared library: [libfoo.so.1]
 0x000000000000001d (RUNPATH)  Library runpath: [&#36;ORIGIN/lib]
<span class="p">&#36;</span> ls -l lib/
total 24
-rwxr-xr-x 1 me me 15920 Mar  2 11:02 libfoo.so.1.2.3
<span class="p">&#36;</span> ln -s libfoo.so.1.2.3 lib/libfoo.so.1
<span class="p">&#36;</span> ldd ./app | grep foo
	libfoo.so.1 =&gt; ./lib/libfoo.so.1 (0x00007f3c2a3d4000)
<span class="p">&#36;</span> LD_DEBUG=libs ./app 2&gt;&amp;1 | grep -m2 libfoo
     31245:	find library=libfoo.so.1 [0]; searching
     31245:	trying file=./lib/libfoo.so.1
</pre>
</div>

第一段 `not found` 不是「文件不存在」，而是「按 soname 找不到」。`ls lib/` 显示只有 `libfoo.so.1.2.3`，缺 `libfoo.so.1` 这个符号链接；补上链接后 loader 立刻能解析。这是自编译共享库最常见的坑：`make install` 生成了带版本的文件，但没建 soname 链接，或者链接建错。

排查 `undefined symbol` 则是另一条路：

```bash
nm -D --undefined-only ./app | grep foo      # 程序要但没定义的符号
nm -D --defined-only libfoo.so.1 | grep foo  # 库里提供的符号
objdump -T libfoo.so.1 | grep foo            # 动态符号表，含版本
c++filt < <(nm -D libfoo.so.1)               # C++ 符号反修饰
```

常见原因：链接顺序不对（`-lfoo` 必须放在使用它的 `.o` 后面）、C++ 的 `extern "C"` 漏了导致名字修饰不一致、符号被 `-fvisibility=hidden` 隐藏、库的版本比头文件旧。`LD_DEBUG=bindings ./app` 能看每个符号绑定到哪个库，输出很大，配合 `grep` 用。

::: ex 例 0.11.1 · 明明加了 `-lfoo`，还是 `undefined symbol`
先猜：是库没被找到，还是库找到了但没有那个符号？`-l` 的顺序有没有关系？

静态链接时链接器从左到右扫描：`cc -lfoo main.o -o app` 先看到 `-lfoo`，此时还没有任何未定义符号，库里的目标文件不会被拉进来；`cc main.o -lfoo -o app` 才是正确顺序。动态链接通常不受顺序影响，但 `--as-needed` 下仍可能把「当前没用到」的库丢掉。先调顺序，再用 `nm -D --defined-only` 确认库里确实有这个名字；C++ 还要用 `c++filt` 看是不是 `extern "C"` 漏了。
:::

### 0.11.5 小结

两类错误各有固定入口：链接期报 `undefined reference to 'x'`，先 `cc -v` 看真实命令行，再 `nm --defined-only libfoo.a` 确认符号在不在、`-l` 顺序对不对；运行期报 `cannot open shared object file: libfoo.so.1`，先 `readelf -d prog | grep NEEDED` 看它到底要谁，再用 `LD_DEBUG=libs` 看它搜过哪些目录。如果只记住一件事，那就是**报错发生的时刻决定你查什么**。

## 0.11.6 pkg-config 与 CMake 最小工程 {#sec-0.11.6}

这一节回答：手写 `-I`/`-L`/`-l` 为什么会漏？`pkg-config` 与 CMake 各自从哪拿这些路径？

::: preview 先抓住一件事
`pkg-config` 读的是 `.pc` 文件，CMake 的 `find_package` 最终也常落到 `.pc` 或 `Config.cmake`——**两条路都在解决同一个问题：把「头文件在哪、库叫什么」从人脑移到文件里**。
:::

手写 `-I`/`-L`/`-l` 容易漏。`pkg-config` 从 `.pc` 文件读编译和链接参数：

```bash
pkg-config --cflags --libs libcurl
# -lcurl
pkg-config --modversion libcurl
# 8.5.0
```

`.pc` 文件在 `/usr/lib/x86_64-linux-gnu/pkgconfig/` 或 `/usr/share/pkgconfig/`，里面写 `prefix`、`includedir`、`libdir`、`Libs`、`Cflags`。装到非标准 prefix 的库要设 `PKG_CONFIG_PATH=/usr/local/lib/pkgconfig`，否则 `pkg-config` 找不到。`pkg-config --validate` 检查 `.pc` 语法。

CMake 工程用 `find_package` 或 `pkg_check_modules`，把依赖变成 target 的属性：

```cmake
cmake_minimum_required(VERSION 3.28)
project(hello C)

find_package(PkgConfig REQUIRED)
pkg_check_modules(CURL REQUIRED IMPORTED_TARGET libcurl)

add_executable(hello main.c)
target_link_libraries(hello PRIVATE PkgConfig::CURL)
install(TARGETS hello RUNTIME DESTINATION bin)
```

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j"$(nproc)"
sudo cmake --install build --prefix /usr/local
```

`IMPORTED_TARGET` 把 `pkg-config` 的 `Cflags`/`Libs` 变成 `PkgConfig::CURL`，`target_link_libraries` 会自动带上头文件路径和链接参数，不用手写 `include_directories`。`cmake --install --prefix` 覆盖 `CMAKE_INSTALL_PREFIX`，等价于 `make install DESTDIR` 的「换安装根」但语义不同：它改变的是安装前缀，不是暂存目录。

### 0.11.6.1 一个 `.pc` 文件到底写了什么

`.pc` 是纯文本，字段是 `键: 值`。把 zlib 的读出来（Ubuntu 24.04 实测）：

```text
$ pkg-config --variable=prefix zlib
/usr
$ pkg-config --modversion zlib
1.3
$ pkg-config --cflags --libs zlib
-lz
```

`--variable=prefix` 取的是 `.pc` 里的自定义变量，`--modversion` 取 `Version:` 字段，`--cflags --libs` 拼出编译与链接参数。zlib 头文件在 `/usr/include`（编译器默认会找），库在默认搜索路径里，所以只输出 `-lz`；如果它装在 `/opt/zlib`，这三条会变成 `-I/opt/zlib/include` 与 `-L/opt/zlib/lib -lz`——**参数不是人写的，是从 `.pc` 算出来的**。

`.pc` 里最容易被忽略的是 `Requires:` 与 `Requires.private:`：前者是「用我的头文件就必须一起有的包」，后者是「静态链接时才需要」。`pkg-config --static --libs foo` 才会把 `.private` 展开——**动态链接时漏掉的依赖，往往在静态链接时以 `undefined reference` 出现**。

### 0.11.6.2 CMake 的两种找法，差在一个文件

`find_package(foo)` 有两种模式：`MODULE` 找 `FindFoo.cmake`（CMake 自带或你写的），`CONFIG` 找库自带的 `FooConfig.cmake`。前者靠猜（猜头文件在哪、库叫什么），后者由库的维护者写好，**信息更准、也更容易带版本约束**。所以现代写法是：

```cmake
find_package(ZLIB 1.2 REQUIRED CONFIG)   # 要 >=1.2，走 Config 模式
target_link_libraries(app PRIVATE ZLIB::ZLIB)
```

`ZLIB::ZLIB` 是 IMPORTED target，头文件路径、链接参数、传递依赖都挂在它身上，不再散落成一串 `-I`/`-l`。**判据**：如果一个项目里还在手写 `include_directories()` 与 `link_directories()`，基本可以断定它没走 target 模型。

### 0.11.6 小结

`pkg-config --cflags --libs foo` 给出编译与链接参数，`PKG_CONFIG_PATH` 决定去哪找 `.pc`；CMake 里 `find_package(foo CONFIG REQUIRED)` + `target_link_libraries(app PRIVATE foo::foo)` 是同一件事的现代写法——把依赖声明成 target 的属性，而不是散落的字符串。如果只记住一件事，那就是**依赖要写成「谁需要什么」，而不是「全局加一堆 flag」**。

**Q2（辨析）** `find_package` 的 `MODULE` 模式与 `CONFIG` 模式有什么区别？

**Q3（应用）** 一个库装在 `/opt/foo`，没有装进系统目录。你怎么让 `pkg-config` 与 CMake 都找到它？

::: sol 答案
**A1** `Cflags`（编译参数，含 `-I` 与宏）与 `Libs`（链接参数，含 `-L` 与 `-l`）；找不到时先看 `PKG_CONFIG_PATH`（它是在默认目录之外额外追加的搜索路径）。

**A2** `MODULE` 模式执行 `FindFoo.cmake` 脚本，靠人写规则去猜；`CONFIG` 模式读库自带的 `FooConfig.cmake`，由上游维护，信息更准。现代项目优先 `CONFIG`。

**A3** 设 `PKG_CONFIG_PATH=/opt/foo/lib/pkgconfig`；CMake 用 `-DCMAKE_PREFIX_PATH=/opt/foo` 或 `-Dfoo_DIR=/opt/foo/lib/cmake/foo`，让 `find_package` 有地方找配置文件。

## 0.11.7 容器镜像：把用户态打包 {#sec-0.11.7}

这一节回答：镜像与 deb 包都在「打包用户态」，差别在哪？为什么 alpine 的二进制拷到别的镜像里经常跑不起来？

::: preview 先抓住一件事
镜像的分层是**文件系统快照的叠加**，不是包管理：它不解决依赖，只搬运文件——所以「静态链接 / 同一基础镜像」是两条硬约束。
:::

容器镜像是一组只读层的叠加，每层是一次文件系统变更。`Dockerfile` 的每条 `RUN`、`COPY`、`ADD` 都会生成一层；层会被缓存、复用、推拉。镜像不含内核，容器与宿主机共享内核——所以「在容器里升级内核」不成立，镜像里的 `/etc/os-release` 描述的是用户态，`uname -r` 显示的是宿主机内核。

一个多阶段、非 root 的 Go/C 程序镜像：

```dockerfile
FROM ubuntu:24.04 AS build
RUN apt-get update && apt-get install -y --no-install-recommends \
        build-essential ca-certificates \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /src
COPY . .
RUN make -j"$(nproc)"

FROM ubuntu:24.04
RUN apt-get update && apt-get install -y --no-install-recommends libcurl4 \
    && rm -rf /var/lib/apt/lists/*
COPY --from=build /src/app /usr/local/bin/app
USER 65532:65532
ENTRYPOINT ["/usr/local/bin/app"]
```

三个关键点。**多阶段**：build 阶段带编译器，运行阶段只留运行时库，镜像从几百 MB 降到几十 MB。**一次 RUN 里完成 update/install/清理**：`apt-get update` 和 `install` 分开写会用到过期的索引缓存，`rm -rf /var/lib/apt/lists/*` 必须和 install 同一层，否则删除只发生在下一层，前一层仍然占体积。**非 root**：`USER 65532:65532` 让进程以 nobody 运行，减少容器逃逸后的权限。

构建并检查层：

<div class="terminal" data-title="bash · 镜像与层">
<pre><span class="p">&#36;</span> docker build -t hello:1.0 .
 =&gt; [build 1/6] FROM docker.io/library/ubuntu:24.04
 =&gt; [build 4/6] RUN make -j"&#36;(nproc)"
 =&gt; exporting to image
 =&gt; =&gt; naming to docker.io/library/hello:1.0
<span class="p">&#36;</span> docker image ls hello
REPOSITORY   TAG   IMAGE ID       CREATED         SIZE
hello        1.0   9f2c1a7b4e10   5 seconds ago   78.4MB
<span class="p">&#36;</span> docker history hello:1.0 | head -5
IMAGE          CREATED         CREATED BY                                      SIZE
9f2c1a7b4e10   5 seconds ago   ENTRYPOINT ["/usr/local/bin/app"]               0B
&lt;missing&gt;      5 seconds ago   USER 65532:65532                                0B
&lt;missing&gt;      5 seconds ago   COPY /src/app /usr/local/bin/app # buildkit     12.1MB
</pre>
</div>

`docker history` 里 `<missing>` 是构建缓存层没有单独 ID 的显示；每层的 `SIZE` 是这一层新增的字节，不是累计。`dive` 能交互式看每层文件和浪费空间。镜像变大时先看 `docker history`，再决定合并哪条 `RUN`、删哪个构建依赖。

镜像和包管理的关系是「构建时用包管理器，运行时尽量不用」：build 阶段用 `apt` 装编译器和头文件，运行阶段只装运行时库；更极端的 distroless 镜像连 shell 和 apt 都不装，只留二进制和证书。`snap`/`flatpak` 是另一条路：自带运行时、沙箱挂载，和 apt 的依赖模型不同，服务器上通常不用。

镜像的可复现性靠固定基础镜像 digest、固定包版本、固定构建参数。`ubuntu:24.04` 是浮动 tag，今天和明天可能指向不同 digest；生产构建用 `ubuntu:24.04@sha256:...`，至少把 digest 记在构建记录里。`apt` 层不要写 `apt upgrade`：它让镜像随源变化，破坏可复现性，也可能引入未测试的库版本。

前一句「`snap`/`flatpak` 是另一条路」在 Ubuntu 24.04 上具体是：`snapd` 预装且在跑（服务器版通常只有 snapd 自己，桌面版预装一串应用），每个 snap 自带运行时、以只读 squashfs 挂在 `/snap/<名字>/<修订号>`，数据在 `/var/snap`。会认这几个命令就够排障：

```bash
snap list                      # 装了哪些、哪个 channel（stable/candidate/beta/edge）
snap install hello-world       # 不走 apt 源；dpkg -L 查不到它
snap connections firefox      # 接口授权：能不能读家目录、用网络
snap refresh --list && snap remove hello-world
```

与 apt 的关键差异：apt 在**系统级**求解共享依赖，snap 在**每个包内**自带依赖（体积大、更新独立、可按修订号回滚）。代价是 `lsblk`/`df` 里多出一批 loop 设备与挂载点、`/var/lib/snapd` 占地、apt 完全看不到这些包——命令查不到归属时先 `snap list` 看一眼。`flatpak` 是同一思路的桌面应用打包（Flathub 源），服务器上几乎不用，Ubuntu 默认也不装。

::: errata 包、库与镜像的六个误解
1. **「`dpkg -i` 会自动装依赖」**——不会。它只解包和配置，缺依赖会留下未配置状态；用 `apt install ./pkg.deb` 或事后 `apt -f install`。
2. **「`apt upgrade` 会删包、换内核」**——普通 `upgrade` 不删包；`full-upgrade`（旧称 `dist-upgrade`）才会为解依赖而删换。升级前看模拟输出。
3. **「`--prefix` 和 `DESTDIR` 是一回事」**——`--prefix` 决定程序运行时认为自己在哪；`DESTDIR` 只是把安装结果暂存到另一个根，用于打包。
4. **「`ldd` 说 not found 就是没装这个库」**——文件可能就在磁盘上，但 soname 链接缺失、不在缓存、RUNPATH 不含该目录；用 `readelf -d` 和 `ldconfig -p` 分开查。
5. **「`LD_LIBRARY_PATH` 是部署动态库的推荐方式」**——它污染子进程、对 setuid 程序无效、易被劫持；生产用 RUNPATH、ldconfig 或标准路径。
6. **「镜像里跑 `apt upgrade` 更安全」**——它破坏可复现性，可能引入未测试的库；正确做法是重建基础镜像、固定 digest 和版本。
:::

### 0.11.7 小结

镜像是「根文件系统的 tar + 元数据」，每层只记增删改；包是「带依赖与脚本的安装单元」。所以镜像里要保证 `ldd` 的依赖都在同一个根里，或者干脆静态链接；`alpine` 用 musl 而主流发行版用 glibc，二进制互换必然失败。如果只记住一件事，那就是**镜像是搬运，包是安装——别指望镜像替你解依赖**。

::: method 即时自测 · 0.11.7
**Q1（记忆）** 镜像层里删除一个文件，实际发生了什么？

**Q2（辨析）** 多阶段构建（multi-stage）解决了什么问题？

**Q3（应用）** 一个 glibc 程序要放进 alpine 镜像，你有哪两条路？各自的代价是什么？

::: sol 答案
**A1** 删除只在**新层**里写一条 whiteout 记录，底层文件仍在——所以镜像体积不会因为 `rm` 而变小，敏感文件必须放在最后一层或用多阶段构建。

**A2** 把「编译环境」与「运行环境」分成两个阶段：编译阶段的工具链、头文件、缓存都不进入最终镜像，最终镜像只 COPY 产物与运行时依赖。

**A3** ① 换成 `alpine` 的 musl 工具链重新编译（代价：部分依赖库要重新适配）；② 继续用 glibc 基础镜像（`debian-slim` 等，代价：体积大几十 MB）；③ 静态链接（代价：NSS/glibc 静态化有坑，见 0.11.4）。
:::

## 0.11.8 dpkg 状态机、维护者脚本与文件所有权 {#sec-0.11.8}

这一节回答：`dpkg -l` 里的两个字母状态各是什么意思？维护者脚本什么时候跑？为什么 `dpkg -S` 查不到 `make install` 装的文件？

::: preview 先抓住一件事
dpkg 记的是**账本**：包状态（想装/已装/配置完）与文件归属。绕过它装的文件不在账上，卸载时也就没人知道该删什么。
:::

`dpkg -l` 的第一列不是「装没装」，而是三个字符：期望状态、当前状态、错误标志。读错这一列，就会把「已卸载但残留配置」当成「已安装」。

| 缩写 | 期望 | 当前 | 含义 | 常见原因 |
|:--|:--|:--|:--|:--|
| `ii` | install | installed | 已安装并配置完成 | 正常 |
| `iU` | install | unpacked | 已解包，未配置 | 依赖缺失、postinst 失败 |
| `iF` | install | half-configured | 配置到一半失败 | 脚本报错、磁盘满 |
| `iH` | install | half-installed | 解包到一半失败 | 中断、空间不足 |
| `rc` | remove | config-files | 已删文件，保留配置 | `apt remove` 而非 `purge` |
| `un` | unknown | not-installed | 从未安装 | 查询结果 |
| `hF` | hold | half-configured | 被 hold 且配置失败 | 需先解 hold 再修 |

`dpkg-query` 的格式串比 `dpkg -l` 更适合脚本：

```bash
dpkg-query -W -f='${db:Status-Abbrev}\t${Package}\t${Version}\t${Architecture}\n' |
    awk -F'\t' '$1 !~ /^ii/ {print}'
```

`${db:Status-Abbrev}` 输出 `ii `、`rc ` 这样的三字符缩写；`${Status}` 输出完整英文（`install ok installed`）。查询已安装包的版本用 `dpkg-query -W -f='${Version}\n' bash`，不要用 `dpkg -l | grep`，后者会把描述行也匹配进来。

`dpkg --audit` 只报告「需要人工处理」的包，不报告 `rc`。真正的修复顺序是：

```bash
sudo dpkg --audit                 # 看半安装/半配置的包
sudo dpkg --configure -a          # 重跑所有未完成的 postinst
sudo apt -f install               # 让 apt 补齐依赖后再配置
sudo dpkg --remove --force-remove-reinstreq pkg   # 最后手段
```

`--force-remove-reinstreq` 会让包进入「已删但文件可能残留」的状态，之后必须手动清理 `/var/lib/dpkg/info/pkg.*` 与残留文件。它解决的是「包管理器自己卡住」，不是「软件坏了」。

维护者脚本是 `.deb` 里的可执行文件，dpkg 在四个时刻调用：

| 脚本 | 调用时机 | 典型用途 | 失败后果 |
|:--|:--|:--|:--|
| `preinst` | 解包前 | 停服务、备份旧文件 | 包不安装 |
| `postinst` | 配置时（解包后） | 建用户、初始化数据库、`systemctl daemon-reload` | 包停在 `iF`/`iU` |
| `prerm` | 删除前 | 停服务、注销 | 包删不掉 |
| `postrm` | 删除/ purge 后 | 清缓存、删用户 | 残留文件 |

脚本的退出码会被 dpkg 记录；`postinst` 返回非 0 不会回滚已解包的文件，只会把包留在半配置状态。所以维护者脚本必须幂等：重复执行不能报错，失败要给出可操作的错误信息。`set -e` 在维护者脚本里通常是必需的，但要先判断命令是否存在（`command -v systemctl`），否则在 chroot/容器里会直接失败。

配置文件（conffile）有特殊待遇：dpkg 记录它们的校验和，升级时如果本地改过、包里的版本也变了，会交互询问保留哪一份。非交互环境（`DEBIAN_FRONTEND=noninteractive`）必须指定策略：

```bash
sudo dpkg --force-confold -i pkg.deb    # 保留本地旧配置
sudo dpkg --force-confnew -i pkg.deb    # 用包里的新配置
sudo dpkg --force-confdef -i pkg.deb    # 没改过就用新的，改过就问
```

`--force-confold` 是自动化升级最安全的选择：不会覆盖运维改过的配置，但新版本需要的配置项可能缺失，升级后要人工 diff。`ucf` 是另一种配置管理工具，Debian 系一些包用它而非原生 conffile。

`dpkg -V pkg` 用 `.md5sums` 校验包内文件是否被改动；`debsums -c` 批量检查。它只校验包自带的文件，不校验你后来创建的文件，也不校验维护者脚本（脚本不在 md5sums 里）。

文件所有权冲突用 `dpkg -S` 查，两个包都想装同一个路径时，dpkg 会报 `trying to overwrite ... which is also in package ...`。正规修法是让其中一个包声明 `Replaces`/`Breaks`，或者用 `dpkg-divert` 把文件挪走：

```bash
sudo dpkg-divert --add --rename --divert /usr/bin/foo.orig /usr/bin/foo
sudo dpkg-divert --list | grep foo
sudo dpkg-divert --remove --rename /usr/bin/foo
```

`update-alternatives` 解决的是另一类冲突：多个包提供同一功能（`/usr/bin/editor`、`/usr/bin/cc`），但允许共存、按优先级切换。

```bash
sudo update-alternatives --install /usr/bin/editor editor /usr/bin/vim 50
sudo update-alternatives --install /usr/bin/editor editor /usr/bin/nano 30
sudo update-alternatives --config editor
update-alternatives --query editor
```

优先级只决定自动模式下的默认值，不决定「哪个更好」；`--config` 写入的是管理员选择，之后新装的更高优先级包不会自动抢走，除非切回 auto 模式。

### 0.11.8 小结

状态机两列：第一列是「期望状态」（`i` 想装、`r` 想删、`p` 已清），第二列是「实际状态」（`n` 未装、`i` 已装、`c` 配置残留、`F` 半配置）。维护者脚本有 `preinst`/`postinst`/`prerm`/`postrm` 四个时机，`postinst configure` 才是「配置完成」。文件归属由 `dpkg -S` 查，`make install` 装的文件不在账上。如果只记住一件事，那就是**任何绕过包管理器的安装，都要自己记住它装了什么**。

**Q2（辨析）** `apt remove` 与 `apt purge` 的差别？残留的 `rc` 状态怎么清？

## 0.11.9 apt 的版本、pin 与求解器 {#sec-0.11.9}

这一节回答：`apt` 装哪个版本由谁决定？`pin` 的优先级数字怎么算？「依赖冲突」时求解器在做什么？

::: preview 先抓住一件事
apt 的选择是**优先级分数**的结果：`Pin-Priority` 高者胜，而「已安装版本」默认有 100 分——这解释了为什么有时 `apt install` 不给你升级。
:::

apt 的版本号不是字符串排序，而是 `[epoch:]upstream[-revision]` 的分段比较。`1.0~rc1` 小于 `1.0`，`1:1.0` 大于 `2.0`（epoch 优先），`1.0-1ubuntu1` 大于 `1.0-1`。比较用 `dpkg --compare-versions`，不要自己写 `sort -V`：

```bash
dpkg --compare-versions 1.0~rc1 lt 1.0 && echo "rc before release"
dpkg --compare-versions 1:1.0 gt 2.0 && echo "epoch wins"
```

`~` 的语义是「比空串还小」，专门给预发布版用；写成 `1.0-rc1` 会大于 `1.0`，升级顺序就反了。Debian revision 里的 `ubuntu1`、`+deb12u1` 也是版本的一部分，别把它们当注释。

`apt-cache policy` 是判断「这个版本从哪来、为什么是候选」的唯一入口：

```bash
apt-cache policy bash
# bash:
#   Installed: 5.2.21-2ubuntu4
#   Candidate: 5.2.21-2ubuntu4
#   Version table:
#  *** 5.2.21-2ubuntu4 500
#         500 http://archive.ubuntu.com/ubuntu noble/main amd64 Packages
#         100 /var/lib/dpkg/status
```

`500` 是 pin 优先级。规则只有几条，但必须记准：

| 优先级 | 含义 | 效果 |
|--:|:--|:--|
| ≥ 1000 | 指定版本 | 允许降级到该版本 |
| 990 | 设置了 target release 时，属于该 release 的版本 | Ubuntu 默认没有 target release，不会出现 990 |
| 500 | 普通仓库 | 默认候选 |
| 100 | 已安装但不在任何源 | 不会被升级 |
| 0 | 无 | 不安装 |
| < 0 | 禁止 | 永不安装 |

pin 写在 `/etc/apt/preferences.d/*.pref`：

```bash
# 只从 noble-updates 取 nginx，其余源降级
Package: nginx
Pin: release a=noble-updates
Pin-Priority: 900

# 禁止安装 experiment 源的所有包
Package: *
Pin: release a=experimental
Pin-Priority: -1
```

`Pin: release a=` 匹配 `Suite`/`Archive`，`Pin: origin` 匹配主机名，`Pin: version` 匹配版本通配。写错 suite 名不会报错，只会让规则不生效；改完用 `apt-cache policy pkg` 验证候选版本。

Ubuntu 24.04 默认启用 **phased updates**：同一个版本按机器哈希分批推送，`apt list --upgradable` 可能显示「被 phasing 挡住」。`apt-cache policy` 会给出 `Phased-Update-Percentage`；急着升级可以临时绕过：

```bash
sudo apt-get -o APT::Get::Always-Include-Phased-Updates=true upgrade
```

这不是故障，是降低大面积回归风险的分批发布。服务器批量升级时应该尊重 phasing，而不是全部绕过。

`apt upgrade` 与 `apt full-upgrade` 的差别只有一条：后者允许为了解依赖而**删除或新增**包。升级前先模拟：

```bash
apt-get -s upgrade | less
apt-get -s full-upgrade | grep -E '^(Remv|Inst|Conf)'
apt-get --no-install-recommends install pkg
```

`-s`（simulate）不会改系统；`--no-install-recommends` 只装 `Depends`，不装 `Recommends`，能显著减少服务器上的无关包，但也可能让某些功能缺失。`apt-mark hold pkg` 把包钉在当前版本，`apt-mark unhold` 解除，`apt-mark showhold` 查看；hold 的包会阻止升级，但不会阻止删除。

依赖求解失败时，先看 apt 的求解器日志，而不是盲目加 `--fix-broken`：

```bash
sudo apt-get -o Debug::pkgProblemResolver=yes install pkg 2>&1 | head -40
apt-cache rdepends --installed pkg        # 谁依赖它
aptitude why pkg                          # 为什么被装上（需 aptitude）
```

`apt autoremove` 删除的是「标记为 auto 且不再被依赖」的包。手动 `apt install` 的包是 manual，不会被自动删；但用 `apt install` 装依赖时，依赖是 auto。把某个 auto 包改为 manual 用 `apt-mark manual pkg`，反过来用 `auto`。在生产机上跑 `autoremove` 前，务必看模拟输出，尤其是内核与驱动包。

::: ex 例 0.11.9 · 两个仓库都有 nginx，apt 为什么装了个旧的 {#ex-0.11.9}
机器上同时加了发行版源与官方 nginx 源。`apt install nginx` 装下来的版本比官方源里的低。

先猜：是源没加对，还是 pin 分数决定的？

```text
$ apt-cache policy nginx
nginx:
  Installed: 1.24.0-2ubuntu7
  Candidate: 1.24.0-2ubuntu7
  Version table:
     1.27.0-1~noble    500
        500 https://nginx.org/packages/ubuntu noble/nginx arm64 Packages
 *** 1.24.0-2ubuntu7    500
        500 http://archive.ubuntu.com/ubuntu noble/main arm64 Packages
        100 /var/lib/dpkg/status
```

两个来源都是 500 分，于是 apt 选**版本号更高**的？不——它选的是候选策略里先命中且版本比较更高者；这里两行同分，实际装的是发行版那个，说明官方源的 `Release` 被标记了 `NotAutomatic`/`ButAutomaticUpgrades` 或优先级被压到 100 以下（`apt-cache policy` 会显示实际分数）。

**判据**：先跑 `apt-cache policy <包>` 看每个来源的分数，再决定写不写 pin；盲改 `sources.list` 顺序是没用的。

:::
### 0.11.9 小结

版本选择看三样：`apt-cache policy` 的候选与优先级、`/etc/apt/preferences.d/` 里的 pin 规则、以及「已安装版本 +100」这条默认加分。求解器把「要装的包 + 依赖 + 冲突」当成约束满足问题，报冲突时它给的是**它找到的反例**，不一定是唯一解。如果只记住一件事，那就是**先 `apt-cache policy <pkg>` 看清候选，再谈装不装得上**。

::: method 即时自测 · 0.11.9
**Q1（记忆）** `Pin-Priority` 里 1000、990、100 各代表什么层级的优先级？

**Q2（辨析）** 为什么 `apt install foo` 有时明明源里有新版本却不升级？

**Q3（应用）** 你要「只用某仓库的 nginx，其他包仍走默认源」。写出 pin 规则的要点。

::: sol 答案
**A1** 1000 = 手动指定/`apt install foo=版本` 级别；990 = 目标发行版（如 stable）默认；100 = 已安装版本与 `NotAutomatic` 仓库的默认加分。

**A2** 因为已安装版本自带 +100，而某些仓库（如 `NotAutomatic`）也只有 100；候选分数不高于当前时 apt 不动作。用 `apt-cache policy` 能看到每个来源的具体分数。

**A3** 在 `/etc/apt/preferences.d/nginx.pref` 写：`Package: nginx` / `Pin: origin <仓库主机名>`（或 `release a=...`）/ `Pin-Priority: 1001`；再 `apt-cache policy nginx` 确认候选来源。

## 0.11.10 符号版本、ABI 与 `patchelf` {#sec-0.11.10}

这一节回答：`GLIBC_2.34 not found` 与 `cannot open shared object` 差在哪一层？`patchelf` 改的是什么、改不了什么？

::: preview 先抓住一件事
符号版本绑的是「这个符号在这个库里第几版」——**文件找到了也会因为标签对不上而失败**；`patchelf` 只能改路径与解释器，改不了符号需求。
:::

`readelf -d` 能看出「要哪个 soname」，但看不出「要哪个版本的符号」。glibc 用符号版本（symbol versioning）让同一个 `.so` 同时提供多个 ABI：

```bash
objdump -T /lib/x86_64-linux-gnu/libc.so.6 | grep ' GLIBC_2.38'
readelf -V ./app | grep -A3 'Version needs'
```

程序里记录的是 `GLIBC_2.38` 这样的版本需求，不是函数名。把在 Ubuntu 24.04 上编译的二进制拷到 glibc 2.35 的机器上，会报：

```
./app: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.38' not found (required by ./app)
```

这不是「缺 libc」，是「libc 太旧」。三条路：在目标发行版上重新编译；用旧版工具链/容器构建；静态链接 glibc（不推荐，NSS、dlopen、locale 都会出问题）。musl 静态链接可以做到单文件，但 DNS 解析与 `getaddrinfo` 的行为和 glibc 不同。

ABI 兼容的规则很具体：

| 改动 | 是否破坏 ABI | 是否要升 soname |
|:--|:--|:--|
| 新增函数 | 否 | 否 |
| 新增结构体字段（末尾） | 否（调用方分配的结构体可能不够大） | 通常否，但要小心 |
| 改变函数签名/返回类型 | 是 | 是 |
| 删除导出符号 | 是 | 是 |
| 改变枚举值/常量 | 是 | 是 |
| 只改内部实现 | 否 | 否 |

soname 是 ABI 的契约：`libfoo.so.1` 承诺「1.x 之间二进制兼容」，不兼容时升到 `libfoo.so.2`，两个版本可以共存。只改文件名不升 soname，是自建库最常见的事故：程序仍记录 `libfoo.so.1`，loader 找到同名的新库，启动时报 `undefined symbol` 或行为异常。

链接时决定 RUNPATH 还是 RPATH：

```bash
# 现代 binutils 默认生成 RUNPATH（DT_RUNPATH）
cc main.c -L. -lfoo -Wl,-rpath,'$ORIGIN/../lib' -o app
readelf -d app | grep -E 'RPATH|RUNPATH'

# 强制旧式 RPATH（会被 LD_LIBRARY_PATH 覆盖，通常不想要）
cc main.c -L. -lfoo -Wl,-rpath,'$ORIGIN/../lib' -Wl,--disable-new-dtags -o app
```

`$ORIGIN` 在运行时展开为可执行文件所在目录，适合「解压即用」的绿色发布。它不支持 `~`，也不能引用环境变量；路径里有空格要用引号包住整个 `-Wl` 参数。`patchelf` 可以在不重新编译的情况下改 RUNPATH 或 soname：

```bash
patchelf --set-rpath '$ORIGIN/lib' ./app
patchelf --set-soname libfoo.so.2 ./libfoo.so.2.0
patchelf --print-rpath ./app
```

`patchelf` 会重写 ELF 的 dynamic 段，可能破坏签名或调试信息；生产发布前要在目标系统上跑一遍 `ldd` 与功能测试。

`dlopen` 是运行时加载的另一条路，和启动时链接的规则不同：

```c
void *h = dlopen("libplugin.so", RTLD_NOW | RTLD_LOCAL);
if (!h) { fprintf(stderr, "%s\n", dlerror()); return 1; }
void (*fn)(void) = (void (*)(void))dlsym(h, "plugin_init");
if (!fn) { fprintf(stderr, "%s\n", dlerror()); dlclose(h); return 1; }
fn();
dlclose(h);
```

`dlopen` 的搜索路径同样受 RUNPATH/LD_LIBRARY_PATH/ld.so.cache 影响；`RTLD_LOCAL` 让符号不被后续库看到，`RTLD_GLOBAL` 则会污染全局符号表。插件系统要用 `RTLD_LOCAL` + 显式 `dlsym`，避免不同插件同名符号互相覆盖。glibc 2.34 起 `libdl` 合并进 libc，`-ldl` 仍可用但不再是必需。

### 0.11.10 小结

三层要分清：文件名层（`libfoo.so.1` 找不到 → 路径问题）、符号标签层（`version 'GLIBC_2.34' not found` → 构建机 glibc 比目标机新）、ABI 层（同名同版本但结构体变了 → 运行时崩溃，最难查）。`patchelf --set-interpreter`/`--set-rpath` 只动前两层里的**路径**，动不了符号需求与 ABI。如果只记住一件事，那就是**报错文本里的「找不到」分三种，先看它说的是文件还是版本标签**。

::: method 即时自测 · 0.11.10
**Q1（记忆）** `version 'GLIBC_2.x' not found` 与 `cannot open shared object file` 分别属于哪一层？

**Q2（辨析）** `patchelf --set-rpath` 能解决什么问题，不能解决什么？

**Q3（应用）** 一个二进制在构建机上好好的，到老服务器上报 `GLIBC_2.34 not found`。给出两条出路与代价。

::: sol 答案
**A1** 前者是**符号标签层**（文件找到了，`.gnu.version_r` 里要求的标签对不上）；后者是**路径层**（文件根本没找到）。取证命令也不同：前者 `readelf -V`，后者 `LD_DEBUG=libs`。

**A2** 能改运行时搜索路径（把 `RUNPATH` 写进 ELF）、能换解释器（`--set-interpreter`）；不能改程序对符号版本的需求，也不能修 ABI 不兼容。

**A3** ① 在**老系统**（或同版本容器）里重新编译，代价是构建环境要维护多套；② 静态链接 glibc 之外的部分、或改用 musl 静态构建，代价是 NSS/`dlopen` 等功能受限。把新 glibc 一起打包运输（`patchelf` + 自带 `ld.so`）也可行，但要保证 `--library-path` 与 `ld.so` 版本匹配。
:::

## 0.11.11 三条包与库的巡检脚本 {#sec-0.11.11}

这一节回答：一台陌生机器上，怎么在五分钟内摸清「装了什么包、库在哪、有没有断链」？

::: preview 先抓住一件事
巡检脚本的产出要能**直接贴进工单**：固定排序、固定 locale、一行一件事，最重要的是给出非 0 退出码。
:::

### 0.11.11.1 包状态巡检

```bash
#!/usr/bin/env bash
# pkg-audit.sh —— 只读：异常状态、hold、可升级、安全更新、最近事务
set -euo pipefail
export LC_ALL=C
bad=0

echo "== dpkg audit"
if ! out=$(dpkg --audit); then bad=1; fi
[[ -n $out ]] && { echo "$out"; bad=1; }

echo "== not fully installed"
dpkg-query -W -f='${db:Status-Abbrev}\t${Package}\t${Version}\n' |
    awk -F'\t' '$1 !~ /^ii/ {print; n++} END {exit n?1:0}' || bad=1

echo "== holds"
apt-mark showhold || true

echo "== upgradable"
apt list --upgradable 2>/dev/null | sed -n '2,$p' || true

echo "== security"
apt list --upgradable 2>/dev/null | grep -i security || echo "none"

echo "== foreign arch"
dpkg --print-foreign-architectures || true

echo "== last apt transactions"
tail -n 12 /var/log/apt/history.log 2>/dev/null || true

exit "$bad"
```

`dpkg-query` 的 `Status-Abbrev` 末尾带空格，`awk -F'\t'` 后 `$1` 是 `ii `，所以正则用 `^ii` 而不是 `== "ii"`。`apt list` 的输出第一行是 `Listing...`，用 `sed -n '2,$p'` 去掉；它的格式不稳定，不适合被其他程序解析，只适合人看。

### 0.11.11.2 二进制依赖清单

```bash
#!/usr/bin/env bash
# link-map.sh BINARY —— 只读：解释器、NEEDED、RUNPATH、解析结果
set -euo pipefail
bin=${1:?usage: link-map.sh BINARY}
[[ -f $bin ]] || { echo "no such file: $bin" >&2; exit 2; }

echo "== file"; file "$bin"
echo "== interpreter"
readelf -l "$bin" | awk '/interpreter/ {print $NF}' | tr -d ']'
echo "== dynamic"
readelf -d "$bin" | grep -E 'NEEDED|RPATH|RUNPATH|SONAME' || true

echo "== resolved (ldd; do NOT run on untrusted binaries)"
ldd "$bin" 2>&1 || true
echo "== missing"
ldd "$bin" 2>&1 | grep 'not found' || echo "none"

echo "== cache hits"
while read -r so; do
    ldconfig -p | grep -F "$so" | head -1 || echo "MISS $so"
done < <(readelf -d "$bin" | awk '/NEEDED/ {gsub(/[\[\]]/,"",$NF); print $NF}')
```

`readelf -l` 的 interpreter 行格式是 `[Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]`，`awk '{print $NF}'` 取到带 `]` 的路径，`tr -d ']'` 去掉。`ldd` 会执行 loader，不能对不可信二进制用；脚本里只是演示，生产巡检应改用 `objdump -p`。

### 0.11.11.3 最小 `.deb` 构建

```bash
#!/usr/bin/env bash
# mkdeb.sh NAME VERSION BINARY —— 生成一个只含单个可执行文件的 deb
set -euo pipefail
name=${1:?name}; ver=${2:?version}; bin=${3:?binary}
[[ -x $bin ]] || { echo "not executable: $bin" >&2; exit 2; }

root=$(mktemp -d); trap 'rm -rf "$root"' EXIT
install -Dm755 "$bin" "$root/usr/local/bin/$name"
mkdir -p "$root/DEBIAN"
size=$(du -sk "$root/usr" | cut -f1)

cat >"$root/DEBIAN/control" <<EOF
Package: $name
Version: $ver
Section: utils
Priority: optional
Architecture: $(dpkg --print-architecture)
Installed-Size: $size
Maintainer: Lab <lab@example.invalid>
Description: minimal test package
 Built by mkdeb.sh for the tutorial.
EOF

out="$PWD/${name}_${ver}_$(dpkg --print-architecture).deb"
dpkg-deb --build --root-owner-group "$root" "$out"
dpkg-deb -I "$out"
dpkg-deb -c "$out"
```

`--root-owner-group` 让包内文件属主固定为 root:root，不需要 `fakeroot`；没有它，`dpkg-deb -c` 会显示构建者的 UID/GID，安装后文件属主也可能不对。`Installed-Size` 单位是 KiB，`du -sk` 正好匹配。

### 0.11.11.4 三条脚本各自的判据

**包状态巡检**：判据是「状态码不是 `ii`」。`dpkg-query` 的 `Status-Abbrev` 是两字母加一个尾空格，直接比较会踩坑——真机上看一眼就明白（Ubuntu 实测）：

```text
$ dpkg-query -W -f='${Status-Abbrev} ${binary:Package} ${Version}\n' bash coreutils
bash 5.2.21-2ubuntu4
 coreutils 9.4-3ubuntu6.3
```

两行的缩进不一样，正是因为第一个字段的宽度与尾随空格不同；所以脚本里用 `^ii` 匹配而不是 `== "ii"`。

**二进制依赖清单**：判据是 `readelf -l` 的 interpreter 行与 `readelf -d` 的 `NEEDED` 能对上。真机：

```text
$ readelf -l /bin/ls | grep -o 'interpreter: [^]]*'
interpreter: /lib/ld-linux-aarch64.so.1
```

拿到的解释器路径要与 `file`/`uname -m` 的架构一致；aarch64 的机器上出现 `ld-linux-x86-64` 就说明这个二进制根本跑不起来。

**最小 `.deb` 构建**：判据是 `dpkg-deb -c` 里的属主与权限。用 `--root-owner-group` 固定成 root:root，否则包里会带上构建者的 UID/GID，装到别的机器上就变成「文件属于一个不存在用户」——这正是很多自建包「装完服务起不来」的原因。

### 0.11.11 小结

三条脚本对应三种问法：`dpkg -l`/`apt list --installed` 回答「装了什么」，`ldconfig -p`/`readelf -d` 回答「库在哪、谁依赖谁」，`ldd`/`find -L` 回答「有没有断链」。如果只记住一件事，那就是**巡检脚本要能跑出非 0**——只打印不判定的脚本，等于没检查。

## 0.11.12 两个实验：自建 deb 与 soname 断裂 {#sec-0.11.12}

这一节回答：一个 `.deb` 最小长什么样？`soname` 断裂时，报错在链接期还是运行期？

::: preview 先抓住一件事
`dpkg-deb -b` 只要求 `DEBIAN/control` 与一棵安装树；而 `soname` 断裂是**运行期**的事——编译、链接都可能成功。
:::

### 实验一：构建、安装、校验、卸载一个 deb

```bash
lab=/var/tmp/deblab; mkdir -p "$lab"; cd "$lab"
cat > hello.c <<'EOF'
#include <stdio.h>
int main(void) { puts("hello from deb"); return 0; }
EOF
cc -O2 -Wall -Wextra -o hello hello.c
bash /path/to/mkdeb.sh hello 1.0.0 ./hello
sudo dpkg -i hello_1.0.0_*.deb
hello
dpkg -L hello
dpkg -V hello; echo "verify rc=$?"
sudo dpkg -r hello
dpkg -l hello | tail -1        # 期望 rc（配置残留）
sudo dpkg -P hello             # purge
```

预期：`hello` 输出 `hello from deb`；`dpkg -L` 只列出 `/usr/local/bin/hello`；`dpkg -V` 无输出且返回 0；`dpkg -r` 后状态是 `rc`，`dpkg -P` 后是 `un`。

再验证 conffile 行为：在 `DEBIAN/` 下加 `conffiles`，内容为 `/etc/hello.conf`，并在 `$root/etc/hello.conf` 放一个默认配置。安装后修改 `/etc/hello.conf`，把版本改成 1.0.1 重新构建并 `dpkg -i`，会看到交互提示。非交互环境用 `--force-confold` 保留本地版本。

### 实验二：soname 断裂与 ABI 升级

```bash
lab=/var/tmp/sonamelab; mkdir -p "$lab"; cd "$lab"
cat > foo.c <<'EOF'
int foo_v1(void) { return 1; }
EOF
cat > main.c <<'EOF'
#include <stdio.h>
int foo_v1(void);
int main(void) { printf("foo=%d\n", foo_v1()); return 0; }
EOF
cc -fPIC -shared -Wl,-soname,libfoo.so.1 -o libfoo.so.1.0 foo.c
ln -sf libfoo.so.1.0 libfoo.so.1
ln -sf libfoo.so.1 libfoo.so
cc main.c -L. -lfoo -Wl,-rpath,'$ORIGIN' -o app
./app
readelf -d app | grep NEEDED

# 不兼容的“升级”：同 soname，删掉旧符号
cat > foo.c <<'EOF'
int foo_v2(void) { return 2; }
EOF
cc -fPIC -shared -Wl,-soname,libfoo.so.1 -o libfoo.so.1.0.new foo.c
mv libfoo.so.1.0.new libfoo.so.1.0
./app; echo "rc=$?"          # 预期 undefined symbol: foo_v1
```

预期：第一次 `./app` 输出 `foo=1`，`NEEDED` 是 `libfoo.so.1`；替换后启动失败，报 `undefined symbol: foo_v1`。这不是 loader 找不到库，而是库找到了但 ABI 断了。

正确做法是升 soname 并共存：

```bash
cc -fPIC -shared -Wl,-soname,libfoo.so.2 -o libfoo.so.2.0 foo.c
ln -sf libfoo.so.2.0 libfoo.so.2
readelf -d libfoo.so.2.0 | grep SONAME
# 旧 app 仍记录 libfoo.so.1，需要保留旧库或重新链接
```

`readelf -d app | grep NEEDED` 是判断「升级会不会影响现有程序」的第一条证据；只改库文件名、不改 soname，等于向所有调用方承诺了一个没有兑现的兼容性。

### 0.11.12.1 自建 deb 的完整动作

实验分四步，全部不需要装进系统（`sudo` 只在最后一步才需要，本书环境跳过安装）：

```bash
pkg=pkg-demo
mkdir -p "$pkg/DEBIAN" "$pkg/usr/local/bin"
printf '#!/bin/sh\necho hello from pkg\n' > "$pkg/usr/local/bin/pkg-demo"
chmod 755 "$pkg/usr/local/bin/pkg-demo"
cat > "$pkg/DEBIAN/control" <<'EOF'
Package: pkg-demo
Version: 1.0
Architecture: arm64
Maintainer: you <you@example.com>
Description: demo package
EOF
dpkg-deb --root-owner-group -b "$pkg" pkg-demo_1.0_arm64.deb
dpkg-deb -I pkg-demo_1.0_arm64.deb
dpkg-deb -c pkg-demo_1.0_arm64.deb
```

`-I` 打印 control 与脚本，`-c` 列文件清单与权限属主。**判据**：`-c` 里 `-rwxr-xr-x root/root` 就说明 `--root-owner-group` 生效了；`Architecture` 写 `arm64` 而不是 `amd64`，否则在 aarch64 机器上 `dpkg -i` 会拒绝。

### 0.11.12.2 `soname` 断裂：一个只改一行的实验

```bash
# 旧库：SONAME = libfoo.so.1
cc -fPIC -shared -Wl,-soname,libfoo.so.1 -o libfoo.so.1.0 foo.c
ln -sf libfoo.so.1.0 libfoo.so.1 && ln -sf libfoo.so.1 libfoo.so
cc main.c -L. -lfoo -Wl,-rpath,'$ORIGIN' -o app && ./app     # 正常

# 新库：只把 SONAME 改成 .2，文件名仍是 .so.1.0
cc -fPIC -shared -Wl,-soname,libfoo.so.2 -o libfoo.so.1.0 foo.c && ./app
```

第二段会报 `cannot open shared object file: libfoo.so.1`：程序里 `NEEDED` 记的是旧 `soname`，新库却声明自己叫 `.2`。**关键判据**：用 `readelf -d app | grep NEEDED` 与 `readelf -d libfoo.so.1.0 | grep SONAME` 对一眼，两个名字不一致就是断裂点。修法只有两种：新库保留旧 `soname`（ABI 兼容时），或同时装 `.so.1` 与 `.so.2`（不兼容时）。

### 0.11.12 小结

自建 deb 的最小结构是 `pkg/DEBIAN/control` + `pkg/usr/...`，`dpkg-deb -b pkg out.deb` 即可打出；`dpkg-deb -c/-I` 能在不安装的情况下检查内容与元数据（`sudo dpkg -i` 才需要 root）。`soname` 断裂实验的关键是**只改 `soname` 不改文件名**：新库装上后老程序的 `NEEDED` 找不到，运行期报 `cannot open shared object file`，而链接期一切正常。如果只记住一件事，那就是**`soname` 是运行期契约，改它等于改 ABI**。

## 0.11.13 加载器审计：`pkg-config`、`ldd`、`readelf` 对账 {#sec-0.11.13}

这一节回答：三个工具给出的「依赖」为什么可能对不上？以谁为准？

::: preview 先抓住一件事
`pkg-config` 说的是「**编译时**该加什么」，`readelf -d` 说的是「**运行时**真正要什么」，`ldd` 说的是「**这台机器上**实际找到什么」——三个问题、三个答案。
:::

0.11.5 讲了两类报错，0.11.11.2 的 `link-map.sh` 只做静态清单。这一节把三样东西放在同一张桌上：`pkg-config` 给出的编译参数、`ldd` 给出的运行时解析结果、`readelf` 记录的 ELF 事实。三者对不上时，先信 `readelf`，再信 `ldd`，最后才信 `pkg-config`——因为前两个是 loader 的事实，后一个是构建系统的约定。

### 实验三：从 `.pc` 到 `ldd`，一条依赖链的四个证据

目的：手写一个带 soname 的库和 `.pc` 文件，用 `pkg-config` 编译、用 `readelf` 看记录、用 `ldd` 看解析，最后故意删掉 soname 链接复现 `not found`。

```bash
sudo apt install -y build-essential pkg-config
lab=/var/tmp/pc-lab; rm -rf "$lab"; mkdir -p "$lab"/{src,stage/lib/pkgconfig,stage/include}
cd "$lab"
cat >src/foo.h <<'EOF'
int foo_version(void);
EOF
cat >src/foo.c <<'EOF'
int foo_version(void) { return 42; }
EOF
cat >src/main.c <<'EOF'
#include <stdio.h>
#include "foo.h"
int main(void) { printf("foo=%d\n", foo_version()); return 0; }
EOF

cc -std=c17 -O2 -fPIC -shared -Wl,-soname,libfoo.so.1 \
   -o stage/lib/libfoo.so.1.0 src/foo.c
ln -sf libfoo.so.1.0 stage/lib/libfoo.so.1
ln -sf libfoo.so.1   stage/lib/libfoo.so
cp src/foo.h stage/include/

cat >stage/lib/pkgconfig/foo.pc <<EOF
prefix=$lab/stage
exec_prefix=\${prefix}
libdir=\${exec_prefix}/lib
includedir=\${prefix}/include

Name: foo
Description: lab library for loader audit
Version: 1.0.0
Libs: -L\${libdir} -lfoo
Cflags: -I\${includedir}
EOF

export PKG_CONFIG_PATH="$lab/stage/lib/pkgconfig"
pkg-config --modversion foo
pkg-config --cflags --libs foo
pkg-config --variable=libdir foo
pkg-config --validate foo && echo "pc syntax ok"

cc -std=c17 -O2 src/main.c $(pkg-config --cflags --libs foo) \
   -Wl,-rpath,'$ORIGIN/stage/lib' -o app
./app
```

预期：`pkg-config --modversion` 输出 `1.0.0`，`--cflags --libs` 输出 `-I/var/tmp/pc-lab/stage/include -L/var/tmp/pc-lab/stage/lib -lfoo`，`./app` 输出 `foo=42`。`--validate` 成功时没有输出；失败时返回非 0，并指出缺字段或语法错误。

接着用三条命令核对同一个依赖：

```bash
readelf -d app | grep -E 'NEEDED|RPATH|RUNPATH'
readelf -l app | grep interpreter
ldd app | grep -E 'foo|libc'
```

| 证据 | 命令 | 回答的问题 | 正常输出 |
|:--|:--|:--|:--|
| ELF 需求 | `readelf -d app` | 程序记录的是哪个 soname、有没有 RUNPATH | `NEEDED libfoo.so.1`、`RUNPATH $ORIGIN/stage/lib` |
| 解释器 | `readelf -l app` | 谁来加载它 | `/lib64/ld-linux-x86-64.so.2` |
| 运行时解析 | `ldd app` | loader 实际找到哪个文件 | `libfoo.so.1 => .../stage/lib/libfoo.so.1` |
| 符号 | `objdump -T stage/lib/libfoo.so.1.0` | 库里到底导出了什么 | `foo_version` 在 `.text` |
| 包归属 | `dpkg -S $(readlink -f stage/lib/libfoo.so.1.0)` | 这个库由谁安装 | 自建库通常无输出，说明不归 dpkg 管 |

`readelf -d` 是「程序要什么」，`ldd` 是「loader 给什么」。两者之间的差距就是 `LD_LIBRARY_PATH`、`RUNPATH`、`ld.so.cache` 和 soname 链接。现在删掉 soname 链接：

```bash
mv stage/lib/libfoo.so.1 stage/lib/libfoo.so.1.bak
./app; echo "rc=$?"
ldd app | grep foo
readelf -d app | grep NEEDED
```

预期：`./app` 报 `error while loading shared libraries: libfoo.so.1: cannot open shared object file`，`ldd` 显示 `libfoo.so.1 => not found`，而 `readelf -d` 仍然写着 `NEEDED libfoo.so.1`。这证明「文件存在」不等于「soname 存在」：loader 只按 soname 找，`libfoo.so.1.0` 在不在无关紧要。恢复链接后 `ldd` 立刻正常。

### 实验四：用 `LD_DEBUG` 与 `strace` 看 loader 的搜索顺序

目的：不背文档，直接看 loader 先开哪个文件、在哪一步放弃、`RUNPATH` 与缓存谁先谁后。

```bash
LD_DEBUG=libs ./app 2>&1 | grep -E 'find library=libfoo|trying file=.*libfoo' | head
strace -f -e trace=openat,openat2 -o /tmp/loader.trace ./app
grep -E 'ld\.so\.cache|libfoo|libc\.so\.6' /tmp/loader.trace | head -12
LD_DEBUG=statistics ./app 2>&1 | tail -8
```

预期：`LD_DEBUG=libs` 会打印 `find library=libfoo.so.1 [0]; searching`，随后是 `search path=...` 和 `trying file=.../libfoo.so.1`；`strace` 里能看到先 `openat("/etc/ld.so.cache", O_RDONLY|O_CLOEXEC)`，再按 `RUNPATH`/缓存顺序尝试库文件，失败的行是 `ENOENT`，属于正常搜索过程。`LD_DEBUG=statistics` 给出重定位次数与启动耗时。

`LD_DEBUG` 的输出全在 stderr，必须 `2>&1`；可选类别用 `LD_DEBUG=help` 列出，常用的有 `libs`、`bindings`、`statistics`、`symbols`、`versions`。`bindings` 输出极大，先 `grep` 再 `head`。

| 变量 | 作用 | 边界 |
|:--|:--|:--|
| `LD_LIBRARY_PATH` | 在缓存之前追加搜索目录 | 污染子进程；setuid 程序忽略 |
| `LD_PRELOAD` | 先加载指定库，可覆盖符号 | setuid 程序忽略；调试/劫持都用它 |
| `LD_DEBUG` | 打印 loader 的搜索/绑定/统计 | 只对动态链接程序有效；输出在 stderr |
| `LD_BIND_NOW` | 启动时解析全部符号 | 等价于链接时 `-z now`；启动变慢、故障提前暴露 |
| `LD_ORIGIN_PATH` | 告诉 loader 可执行文件在磁盘上的路径，供 `$ORIGIN` 展开 | 现代系统一般不需要 |

`strace` 看到的 `openat` 顺序是最终事实，但它会拖慢启动；线上排障优先 `LD_DEBUG=libs` 的定向输出。对不可信二进制不要跑 `ldd`，它可能执行 loader；用 `readelf -d` + `objdump -p` 代替。

### 0.11.13 小结

对账的顺序是固定的：先用 `pkg-config --libs` 或 `readelf -d` 回答「应该依赖谁」，再用 `ldd`/`LD_DEBUG=libs` 回答「实际找到谁」，两者的差就是问题所在（缺库、路径不对、版本不符）。`pkg-config` 漏写的依赖会让编译期少 `-l`，但链接可能被其他库间接满足——**这正是「编译过、换机器跑不了」的常见来源**。如果只记住一件事，那就是**以 `readelf -d` 的 `NEEDED` 为准，其他两个都是旁证**。

**Q1（记忆）** 三个工具各自回答什么问题？

**Q2（辨析）** 为什么 `pkg-config --libs` 全对，程序换台机器仍可能跑不起来？

**Q3（应用）** 审计一台机器上某个自编译程序，写出你的三步对账命令。

::: sol 答案
**A1** `pkg-config`：编译/链接参数该怎么给；`readelf -d`：ELF 里记录的运行期依赖（`NEEDED`/`RPATH`/`RUNPATH`）；`ldd`：在当前环境里实际解析到的路径。

**A2** 因为 `pkg-config` 只描述直接依赖的编译参数，间接依赖、运行期路径（`RUNPATH`）与 ABI 兼容性它都不管；换机器后 `ld.so` 找不到 `.so` 或符号版本不符，就失败。

**A3** ① `readelf -d prog | grep -E 'NEEDED|RPATH|RUNPATH'` 取需求；② `ldd prog` 或 `LD_DEBUG=libs` 看解析结果；③ `readelf -V prog` 与 `nm -D` 对符号版本做差集。三步都过才算「这台机器上确实能跑」。
:::

## 0.11.14 从源码到 deb：`debian/` 目录与依赖闭合 {#sec-0.11.14}

这一节回答：一个 `debian/` 目录最少要有哪些文件？`Depends` 里的依赖怎么才算「闭合」？

::: preview 先抓住一件事
`debian/control` 的 `Depends` 不是抄来的清单，而是**对二进制做一次依赖审计的结果**——`dpkg-shlibdeps` 就是从 ELF 反推。
:::

0.11.11.3 的 `mkdeb.sh` 只打一个二进制；真实发行版包还要解决三件事：文件按 FHS 装到 `/usr`、依赖由工具从 ELF 里算出来、构建过程可重复。`debian/` 目录就是这三件事的声明。

| 文件 | 必需 | 作用 | 常见错误 |
|:--|:--|:--|:--|
| `debian/control` | 是 | 源码包与二进制包的元数据、`Build-Depends`、`Depends` | 漏 `${shlibs:Depends}` |
| `debian/changelog` | 是 | 版本、发行版、变更记录；`dpkg-buildpackage` 从这取版本 | 日期格式错、版本不以数字开头 |
| `debian/rules` | 是 | 构建脚本，通常用 `dh` 序列 | 没有执行权限 |
| `debian/copyright` | 是 | 许可证与版权 | 缺字段被 lintian 报 |
| `debian/source/format` | 是 | `3.0 (quilt)` 或 `3.0 (native)` | 与上游 tarball 结构不匹配 |
| `debian/install` | 否 | 把构建产物装到包内路径 | 路径写错导致空包 |
| `debian/*.install` | 否 | 多二进制包各自的文件清单 | 通配符匹配到构建目录 |
| `debian/patches/` | 否 | quilt 补丁队列 | 补丁未在 `series` 里登记 |

第一次可以用 `dh_make --native --single` 生成骨架，再改 `control`、`rules` 和 `changelog`；不要直接把 `dh_make` 生成的模板提交进仓库而不改 Maintainer 与 Description。

一个最小的 `debian/control`：

```text
Source: hello
Section: utils
Priority: optional
Maintainer: Lab <lab@example.invalid>
Build-Depends: debhelper-compat (= 13), gcc, make
Standards-Version: 4.6.2
Rules-Requires-Root: no

Package: hello
Architecture: any
Depends: ${shlibs:Depends}, ${misc:Depends}
Description: minimal hello package
 A one-line summary followed by a longer description.
```

`${shlibs:Depends}` 不是手写的，是 `dpkg-shlibdeps` 扫二进制里的 `NEEDED` 后生成的。少了它，包能装、能构建，但在没装 `libc6` 的 chroot 里一跑就报 `cannot open shared object file`。`${misc:Depends}` 收 `debhelper` 生成的杂项依赖。

`debian/rules` 用 `dh` 序列，最小版本只有三行：

```make
#!/usr/bin/make -f
%:
	dh $@
```

如果项目用 `configure`，用 `override_dh_auto_configure` 传 prefix；如果只有 Makefile，覆盖 build/install：

```make
override_dh_auto_build:
	$(MAKE) CFLAGS="-O2 -g"

override_dh_auto_install:
	$(MAKE) install DESTDIR=$(CURDIR)/debian/hello PREFIX=/usr
```

`DESTDIR` 把文件装到 `debian/hello/usr/...`，这是打包的暂存根；程序运行时看到的仍是 `PREFIX=/usr`。这与 0.11.3 的 `--prefix`/`DESTDIR` 是同一组概念，只是在 `debian/rules` 里由 `dh_auto_install` 自动传入。

`debian/changelog` 的格式不能错，第一行决定包版本：

```text
hello (1.0.0-1) noble; urgency=medium

  * Initial release.

 -- Lab <lab@example.invalid>  Mon, 02 Mar 2026 10:00:00 +0000
```

构建与检查：

```bash
sudo apt install -y build-essential debhelper devscripts lintian
mkdir -p debian/source && printf '3.0 (native)\n' > debian/source/format
dpkg-buildpackage -us -uc -b          # 不签名，只构建二进制包
lintian ../hello_1.0.0-1_amd64.changes
dpkg-deb -I ../hello_1.0.0-1_amd64.deb
dpkg-deb -c ../hello_1.0.0-1_amd64.deb | head
```

`-us -uc` 跳过签名，`-b` 只构建二进制包（不做源码包）。`dpkg-buildpackage` 会先跑 `debian/rules clean`，再在 `debian/hello/` 里 staged 安装，最后用 `dpkg-deb` 打包。`lintian` 的 `E:` 是必须修的，`W:` 要逐条判断；最常见的 `W` 是缺 manpage、库缺 soname 链接、包名与 soname 不匹配。

依赖闭合的核心命令是 `dpkg-shlibdeps`，`dh_shlibdeps` 会自动调用它：

```bash
dpkg-shlibdeps -O debian/hello/usr/bin/hello
# shlibs:Depends=libc6 (>= 2.34)
```

它做三件事：读二进制的 `NEEDED`、在 dpkg 数据库里找提供该 soname 的包、把最小版本写进 `shlibs:Depends`。如果库是自建的、没有对应的 deb，会报：

```text
dpkg-shlibdeps: error: no dependency information found for .../libfoo.so.1
```

正确修法是把库也打成包，并在 `debian/libfoo1.shlibs` 里声明 `libfoo 1 libfoo1 (>= 1.0)`；用 `--ignore-missing-info` 只是把错误藏起来，装到干净机器上仍然缺库。

多架构路径要用 `dpkg-architecture` 算，不要写死：

```bash
multiarch=$(dpkg-architecture -qDEB_HOST_MULTIARCH)
install -Dm644 libfoo.so.1.0 "debian/libfoo1/usr/lib/$multiarch/libfoo.so.1.0"
```

库装到 `/usr/lib` 而不是 `/usr/lib/x86_64-linux-gnu`，在 multiarch 系统上会和 `ldconfig` 的搜索路径错位；`lintian` 会报 `sharedobject-in-library-directory-missing-soname` 或 `package-installs-into-usr-local`。

可复现构建至少要固定三样：`SOURCE_DATE_EPOCH`（`dpkg-buildpackage` 从 changelog 推导）、编译器路径映射（`-ffile-prefix-map=$(CURDIR)=.`）、以及不把构建主机的绝对路径写进二进制。`DEB_BUILD_OPTIONS=nostrip` 只用于调试，不要带进发布包。

### 脚本：`elf-audit.sh` 做一次依赖闭合审计

```bash
#!/usr/bin/env bash
# elf-audit.sh BIN... —— 只读：解释器、NEEDED、RUNPATH、未解析库、GLIBC 版本
set -euo pipefail
(( $# > 0 )) || { echo "usage: elf-audit.sh BIN..." >&2; exit 2; }

for bin in "$@"; do
    [[ -f $bin ]] || { echo "skip: $bin" >&2; continue; }
    echo "== $bin"
    file -b "$bin"
    printf 'interp: '
    readelf -l "$bin" | awk '/interpreter/ {print $NF}' | tr -d ']'
    echo "-- NEEDED/RUNPATH"
    readelf -d "$bin" | grep -E 'NEEDED|RPATH|RUNPATH' || true
    echo "-- unresolved"
    ldd "$bin" 2>&1 | grep 'not found' || echo none
    echo "-- glibc versions"
    objdump -T "$bin" 2>/dev/null | grep -o 'GLIBC_[0-9.]*' | sort -Vu | tail -3 || true
    echo "-- owners"
    while read -r so; do
        path=$(ldd "$bin" 2>/dev/null | awk -v s="$so" '$1 == s {print $3}')
        if [[ -n ${path:-} && $path != not ]]; then
            dpkg -S "$(readlink -f "$path")" 2>/dev/null || echo "UNPACKAGED $path"
        fi
    done < <(readelf -d "$bin" | awk '/NEEDED/ {gsub(/[\[\]]/, "", $NF); print $NF}')
done
```

它把「要什么、找到什么、谁提供的、要哪个 GLIBC 版本」一次打出来。输出里出现 `UNPACKAGED` 就说明这个库不归包管理器管，升级/迁移时会丢；出现 `not found` 则是路径或 soname 问题，按 0.11.5 的顺序查。

### 打包链路的八个坑

| # | 现象 | 原因 | 修复/判断 |
|--:|:--|:--|:--|
| 1 | `dpkg-buildpackage: debian/rules ... Permission denied` | `rules` 没有执行权限 | `chmod +x debian/rules` |
| 2 | 包能装，运行缺库 | `control` 里漏了 `${shlibs:Depends}` | 加字段，确认 `dh_shlibdeps` 跑过 |
| 3 | `dpkg-shlibdeps: no dependency information` | 自建库没打包，或没有 `.shlibs` | 打包库并写 `debian/libfoo1.shlibs`，别用 `--ignore-missing-info` |
| 4 | `dh_make` 后构建报 compat 冲突 | 同时有 `debian/compat` 与 `debhelper-compat` | 二选一，现代包用 `Build-Depends: debhelper-compat (= 13)` |
| 5 | 版本号解析失败 | `changelog` 版本不以数字开头，或日期格式错 | 用 `1.0.0-1`，日期写 `Mon, 02 Mar 2026 10:00:00 +0000` |
| 6 | lintian 报 `package-installs-into-usr-local` | `PREFIX`/`--prefix` 用了 `/usr/local` | 发行版包装 `/usr`；`/usr/local` 留给本地源码安装 |
| 7 | 库在 `/usr/lib` 但运行找不到 | 多架构目录应为 `/usr/lib/<triplet>` | 用 `dpkg-architecture -qDEB_HOST_MULTIARCH` |
| 8 | 安装后 `pkg-config` 指向构建目录 | `.pc` 的 `prefix` 写死为临时路径 | 用 `--define-variable=prefix=` 或安装时替换 |

第 6 条和第 7 条经常一起出现：源码项目默认 `--prefix=/usr/local`，打包时忘了覆盖，结果文件全进了 `/usr/local`，`lintian` 报错、卸载也卸不干净。`debian/rules` 里显式写 `--prefix=/usr`，并在 `debian/*.install` 里只列 `/usr` 下的路径，能避免大部分这类问题。

### 0.11.14 小结

最小 `debian/` 需要 `control`（含 `Build-Depends` 与 `Depends`）、`rules`、`changelog`、`compat`/`debhelper-compat`，可选 `install`/`links`/`postinst`。依赖闭合靠 `dpkg-shlibdeps` 从二进制反推库包、`dpkg-depcheck` 追构建期调用，再人工确认版本约束。如果只记住一件事，那就是**`Depends` 要由工具从产物生成，不要手写**。

**Q2（辨析）** `dpkg-shlibdeps` 为什么比手写 `Depends` 可靠？

**Q3（应用）** 打包一个依赖 `libssl-dev` 的程序，写出 `debian/control` 里与依赖相关的两行。

## 0.11.15 十三个包、库与构建陷阱 {#sec-0.11.15}

这一节回答：包、库与构建这一章，哪些错会「装得上、跑不起来」或「编译过、换机器就废」？

::: preview 先抓住一件事
这些坑的共同点是**跨层**：源码层、链接层、打包层、加载层各有一套名字与路径，任何一层对不上，现象都会推给另一层。
:::

| # | 现象 | 原因 | 修复/判断 |
|--:|:--|:--|:--|
| 1 | `dpkg -i` 后包停在 `iU` | 依赖未满足或 postinst 失败 | `apt -f install`；看 `/var/log/dpkg.log` |
| 2 | `apt install` 报「没有候选版本」 | 源里没有该包/架构，或 pin 为 -1 | `apt-cache policy pkg`、检查 `sources` |
| 3 | 包一直不升级 | `apt-mark hold` 或 phasing | `apt-mark showhold`、`apt-cache policy` |
| 4 | 第三方源 GPG 报错 | 缺 `signed-by`、key 过期、时间不对 | 装 keyring 到 `/etc/apt/keyrings`，校对时间 |
| 5 | 混用 Debian/Ubuntu 源后依赖爆炸 | libc/ABI 不同 | 删除混来源，按发行版重装 |
| 6 | `make install` 覆盖了包管理器文件 | 装到 `/usr` 而非 `/usr/local` | 用 `--prefix=/usr/local`，记录 manifest |
| 7 | `ldconfig` 后仍找不到库 | 目录不在 `ld.so.conf`、soname 缺失 | `ldconfig -p`、`readelf -d` |
| 8 | `LD_LIBRARY_PATH` 对 setuid 无效 | secure-execution 模式忽略 | 用 RUNPATH 或系统路径 |
| 9 | 升级库后程序 `undefined symbol` | 同 soname 但 ABI 断了 | 升 soname、保留旧库、重编 |
| 10 | `ldd` 卡住或执行了程序 | `ldd` 会调用 loader | 不可信二进制用 `readelf -d`/`objdump -p` |
| 11 | `apt autoremove` 删掉了要用的包 | 它被标记为 auto 且无反向依赖 | 先 `-s` 模拟，必要时 `apt-mark manual` |
| 12 | 容器里 `apt update` 404 | 基础镜像 EOL，源已下架 | 换 `old-releases` 或升级基础镜像 |
| 13 | 自建 deb 安装后属主是 UID 1000 | 构建时没固定属主 | `dpkg-deb --root-owner-group` |

第 9 条与第 7 条容易混：前者是「库找到了，符号不对」，后者是「库根本没找到」。`ldd` 的输出能区分：`not found` 是路径问题；路径正常但启动报 `undefined symbol` 是 ABI 问题。先看 `ldd` 有没有 `not found`，再看 `nm -D`，顺序不要反。

### 0.11.15.1 三个最容易连锁放大的坑

**第一条「整盘被格式化」**：`mkfs.ext4 /dev/sdb` 与 `mkfs.ext4 /dev/sdb1` 差一个数字，前者抹掉的是分区表加所有分区。防法是**任何写盘命令前先 `lsblk` 打印一次目标**，并在脚本里用 `/dev/disk/by-id/...` 而不是 `/dev/sdX`。

**第九条「库找到了，符号不对」**：`undefined reference to 'foo'` 有两种成因——链接器根本没找到库（`-l` 顺序、路径），或找到了但版本里没有那个符号（符号版本）。分法是 `nm --defined-only libfoo.so | grep foo`：有就是版本问题，没有就是路径或顺序问题。**判据是这一条命令**，不是反复调整 `-L`。

**第十三条「自建 deb 的属主是 UID 1000」**：`dpkg-deb -b` 默认保留构建者属主，装到别的机器上就变成「文件属于一个不存在的用户」。修法是 `--root-owner-group`；判据是 `dpkg-deb -c` 里出现 `root/root`。

### 0.11.15 小结

十三条按「名字对不上」「路径对不上」「记账对不上」三类记：名字（`soname` 与 `.so` 软链、符号版本、`soname` 变更）属于链接/加载层；路径（`prefix` 与 `DESTDIR`、`RUNPATH`、`ldconfig` 缓存）属于安装层；记账（`make install` 绕过 dpkg、`Depends` 手写漏项、`purge` 与 `remove`）属于包管理层。如果只记住一件事，那就是**报错先归层，再动手**——归错层会越修越乱。

::: method 即时自测 · 0.11.15
**Q1（记忆）** 哪一类坑会让「编译通过、运行失败」？举两个。

**Q2（辨析）** `make install` 装的文件与 `dpkg -i` 装的文件，运维上最大的差别是什么？

**Q3（应用）** 升级一个被多个程序依赖的库，你会先查什么再动手？

::: sol 答案
**A1** 运行期才暴露的两类：`soname` 变了但没留兼容软链；符号版本要求高于目标机 glibc。二者链接期都可能成功。

**A2** 记账：`dpkg` 装的能 `dpkg -S` 查归属、能升级能卸载；`make install` 装的不在任何账本里，卸载只能凭记忆或清单。

**A3** 先 `readelf -d`/`ldd` 找出谁依赖它（`apt-cache rdepends` 看包级反向依赖），确认新库的 `soname` 是否变化；变了就要保留旧 `soname` 或同时装两个版本，再安排依赖方逐个重建。

## 0.11.16 本章小结 {#sec-0.11.16}

这一节回答：这一章学完，你能独立做到哪几件事？哪些还停在「会用命令」？

::: preview 先抓住一件事
这一章的判据是：**拿到一个「装不上/跑不起来」的现场，你能说清它在源码、链接、打包、加载四层中的哪一层，并给出对应的第一条命令。**
:::

这一章的主线是**从源码到运行**：0.11.1–0.11.6 走「拆包 → 装包 → 编源码 → 建库 → 修链接错 → 用构建系统」；0.11.7–0.11.14 把视角抬到镜像、包状态机、版本与 pin、符号版本、巡检脚本、自建 deb 与依赖闭合；0.11.15 把跨层陷阱列成清单。

逐条打勾的达标表在[学习目标自检表](ch11-checklist.md)。这里只留判据：

- **能解释**：`--prefix` 与 `DESTDIR` 的区别、`soname` 与开发软链的区别、`undefined reference` 与 `cannot open shared object` 的时刻区别。
- **能操作**：不靠 root 打一个能装的 deb、在空目录里做一次 `DESTDIR` 安装、用 `readelf`/`ldd` 对账。
- **能判断**：什么时候该静态链接、什么时候该换基础镜像、什么时候该承认「这个包不该自己编」。

如果只记住一件事，那就是**每一层都有自己的名字与记账方式，报错先归层**。

::: method 即时自测 · 0.11.16
**Q1** `dpkg -i app.deb` 报 `dependency problems prevent configuration`，`app` 处于 `iU` 状态。怎么修？为什么不建议直接 `dpkg -i` 重试？

**Q2** 程序在开发机跑得好，拷到服务器报 `libfoo.so.1: cannot open shared object file`，但服务器上 `find / -name 'libfoo.so*'` 能找到 `libfoo.so.1.2.3`。最可能缺什么？

**Q3** `./configure --prefix=/opt/app && make && sudo make install` 之后，程序启动报 `error while loading shared libraries: libbar.so.1`。`libbar` 是同一个项目刚装到 `/opt/app/lib` 的。列出两种修法及各自代价。

**Q4** Dockerfile 里 `RUN apt-get update` 和 `RUN apt-get install -y curl` 分成两层，构建经常用到旧索引。为什么？怎么改？

::: sol 答案
**A1** `iU` 表示已解包但未配置，缺依赖。先 `sudo apt -f install` 让 apt 从源里补齐依赖并配置；离线环境用 `dpkg -i` 按依赖顺序装齐，或 `apt install ./app.deb`。直接重试 `dpkg -i` 不会解决依赖，只会重复留下未配置状态。

**A2** 缺 soname 符号链接 `libfoo.so.1`。loader 按 soname 找，不按真实文件名找；`ln -s libfoo.so.1.2.3 libfoo.so.1` 后 `ldconfig` 或把目录加进搜索路径。也可能是架构不匹配或 RUNPATH 不含该目录，先用 `file` 和 `readelf -d` 排除。

**A3** ① 把 `/opt/app/lib` 加进 `/etc/ld.so.conf.d/app.conf` 并 `ldconfig`，代价是全局可见、可能与其他版本冲突；② 链接时加 `-Wl,-rpath,/opt/app/lib`（或 `$ORIGIN/../lib`），代价是路径写死、迁移目录要重链接；③ 用 `LD_LIBRARY_PATH`，只适合临时调试，不适合部署。

**A4** 每条 `RUN` 是独立层，`apt-get update` 的索引留在第一层；后续层或缓存复用时索引可能已过期，而 `install` 不会自动重新 update。把 update、install、`rm -rf /var/lib/apt/lists/*` 放进同一条 `RUN`，或用 `apt-get update && apt-get install -y --no-install-recommends ...` 一行完成。
