# 5.9 缓存一致性：MESI 与维护指令

第四章 4.10.2 讲共享内存时留了一个坑：**"数据走共享内存，同步走信号量"**——但如果两个核各自命中自己 Cache 里的同一份数据，信号量也救不了你。本节补上这一层的机制。（依据素材书第 16 章）

## 5.9.1 问题：DMA 搬运到了旧数据

素材书给的场景非常典型：

> 主机软件产生了一些数据，想通过 DMA 把数据搬到外设。**如果 CPU 和 DMA 看到的数据不一致**——CPU 产生的最新数据还在它的 Cache 里，而 DMA 直接从内存搬运——那么 DMA 搬运了一份**旧数据**。

这里 CPU 是**生产者**，DMA 是**消费者**。Cache 一致性要保证的正是：**任何读到这个地址的主设备，读到的都是最新值**。

## 5.9.2 三种解决方案

| 方案 | 做法 | 代价 |
|:--|:--|:--|
| **关闭 Cache** | 干脆不用 Cache | 最简单，但性能与功耗损失严重（CPU 每次访存都要走内存） |
| **软件维护** | 在合适的时机手工清脏行 / 失效行 | **最常用**；软件复杂度高、调试难、频繁清理降低性能 |
| **硬件维护** | 由硬件协议保证一致 | 对软件透明；硬件复杂，有通信开销 |

**软件维护为什么难调**（素材书的观察很到位）：如果不在恰当的时间点清理并失效缓存行，DMA 可能传错数据——但"只在某个偶然的时间点传了错误数据，且没有造成系统崩溃"，这种 bug 是最难定位的一类。要查只能一帧一帧抓数据对比，而且**未必想得到是缓存一致性问题**。

## 5.9.3 MESI 协议

现代 ARM 与 x86 都用 **MESI** 维护缓存一致性。名字来自四种状态：

| 状态 | 全称 | 含义 |
|:--|:--|:--|
| **M** | Modified（修改） | 行有效，**已被修改**，与内存不一致；**数据只存在于该 Cache** |
| **E** | Exclusive（独占） | 行有效，**与内存一致**；**数据只存在于该 Cache** |
| **S** | Shared（共享） | 行有效，与内存一致；**多个 Cache 有副本** |
| **I** | Invalid（无效） | 行无效 |

**M 与 E 的区别**：两者数据都是独有的，区别在 M 是**脏的**（与内存不一致）、E 是**干净的**（与内存一致）。持有 M 状态的行会在某个时刻被**写回内存**。

另外两个标志位：**有效位（V）**与**脏位（D）**，描述 Cache 行与内存的数据关系。

协议家族有两类：

- **监听协议（snooping protocol）**：每个 Cache 都监听总线活动（总线是广播机制）。1983 年 Goodman 提出 Write-Once 协议，MESI 是它的变种；
- **目录协议（directory protocol）**：统一管理所有 Cache 状态，适合大规模多核。

协议之间要权衡**通信量**：通信量太大浪费总线带宽、加剧总线争用。

## 5.9.4 两级一致性：核内与系统级

对应 5.8.4 的 PoU 与 PoC：

| 范围 | 机制 |
|:--|:--|
| **核间（PoU）** | 核内实现 MESI 协议，典型是 **SCU**（第二章 2.3.2 的"中央情报局"） |
| **系统级（PoC）** | **缓存一致性总线协议**：ARM 在 AMBA 4 提出的 **ACE**（AXI Coherency Extension）用于 CPU 簇之间；**ACE-Lite** 用于 I/O 设备（DMA、GPU）与 Cache 的一致性 |

这正好接上第二章：2.3.2 说 SCU 负责"核间互联、仲裁、缓存一致性"，本节说明它**靠什么协议**——MESI；2.3.2 说 ACP 让外设参与一致性协议，本节说明它靠 **ACE-Lite**。

::: note AArch32 的 ACP 与 AArch64 的 ACE-Lite
第二章 2.3.2 讲的 **ACP（Accelerator Coherency Port）** 是 Cortex-A9 时代的硬件机制；AArch64 时代对应的标准协议是 ACE/ACE-Lite。两者思想一致——让非核主设备进入一致性域——但实现路径不同。
:::

## 5.9.5 软件侧怎么用这些知识

有了上面的机制，软件侧的规则就清楚了：

**场景一：CPU 生产数据，DMA 消费**

```c
    /* 写数据 */
    memcpy(dma_buf, src, len);

    /* 关键：让 CPU 侧的脏行写回内存，DMA 才看得到新数据 */
    clean_dcache_to_poc(dma_buf, dma_buf + len);

    /* 然后才能启动 DMA */
    dma_start(...);
```

**场景二：DMA 生产数据，CPU 消费**

```c
    dma_wait_done();

    /* 关键：DMA 写的是内存，CPU 的 Cache 里可能是旧数据，必须失效 */
    invalidate_dcache_to_poc(dma_buf, dma_buf + len);

    memcpy(dst, dma_buf, len);
```

素材书自测题第 15 题问的就是这两个方向。**写之前 clean、读之前 invalidate**——这是 DMA 编程的固定套路。

::: note 为什么"之前"而不是"之后"
clean 必须**在启动 DMA 之前**——DMA 一旦开始跑，CPU 就失去对数据的控制，来不及再写回。invalidate 必须**在读之前**——读到之前把可能陈旧的行丢掉。
:::

**场景三：改了代码内容**

内核改了可执行代码后，其它核的指令 Cache 里还是旧代码。必须：

1. 失效**自己的**指令 Cache（PoC 角度，`ic ivau`）；
2. **发 IPI** 让其它核也执行一遍失效（跨核不能直接改别人的 Cache，见 5.7.6）。

素材书提到 Linux 的 `flush_icache_range()` 在做完失效后要发一个 IPI，而**回调函数是空的**——目的只是"把那个核打断、让它走到刷新点"，刷新逻辑本身在中断路径里。

## 5.9.6 与第四章 4.10 的呼应

第四章 4.10.2 说共享内存"快，但必须自己保证互斥"。本节补上这层：**"互斥"防的是两个核同时改同一份数据；"一致性"防的是一个核改了、另一个核还看着旧版本**。

两者正交，缺一不可：

| 问题 | 机制 | 手段 |
|:--|:--|:--|
| 同时写冲突 | **互斥**：独占访问权 | 信号量 / 互斥量 / 原子指令（5.10） |
| 看到旧数据 | **一致性**：Cache 副本同步 | MESI（硬件自动）/ clean+invalidate（软件手动） |
| 看到别人的中间状态 | **内存序**：操作不跨过同步点 | 内存屏障（5.10） |

## 本节小结

Cache 一致性保证"任何主设备读到同一地址都是最新值"。三条路：关 Cache（慢）、软件维护（常用但难调）、硬件维护（MESI + ACE）。MESI 的四态 M/E/S/I 区分了"脏且独有""干净且独有""干净且共享""无效"。软件侧的固定动作是：**DMA 之前 clean、DMA 之后 invalidate、改代码之后失效指令 Cache 并发 IPI**。但一致性只保证"数据是最新的"，不保证"顺序是对的"——那是下一节内存屏障的事。
