# 5.7 TLB：地址转换缓存

如果每次访存都要走四级页表，性能就完了。TLB（Translation Lookaside Buffer）是**地址转换的缓存**——把"虚拟地址 → 物理地址 + 权限 + 属性"的翻译结果存起来，命中就不必再查页表。（依据素材书第 17 章）

## 5.7.1 TLB 在访存路径上的位置

```
CPU 发出虚拟地址 VA
   │
   ├─ TLB 查找（并行地做）
   │     ├─ 命中 → 得到 PA、权限、内存属性 → 进入 Cache 查找
   │     └─ 未命中 → 遍历页表（5.6.3）→ 得到 PA → 回填 TLB → 进入 Cache 查找
   │
   └─ Cache 查找（用物理地址）
         ├─ 命中 → 命中数据
         └─ 未命中 → 访问内存
```

关键点：**TLB 与 Cache 是两级独立的缓存**，TLB 在前、Cache 在后。TLB 未命中的惩罚是"多走几次页表遍历"，Cache 未命中的惩罚是"多走一次内存访问"——后者贵得多。

## 5.7.2 TLB 的组织：按 VA 位段分表

AArch64 的 TLB 不是一张平表，而是**按虚拟地址的哪些位来划分**：

| TLB | 索引所用的 VA 位 | 缓存的翻译范围 |
|:--|:--|:--|
| L1 TLB | 4 KB 粒度 | 覆盖整个地址空间，但项数少 |
| L2 TLB | 4 KB 粒度 | 覆盖整个地址空间，项数多 |
| **S2 TLB** | 2 MB 粒度 | 第二级翻译（虚拟化） |

**为什么按位段分**：不同进程的低位地址段（栈、堆、共享库）用得最多，把它们放在一个专用的小 TLB 里，命中率更高。

## 5.7.3 全局表项与进程特有表项

5.6.4 提到的页表项属性 **nG** 在 TLB 里对应两种表项：

- **nG = 0（全局表项）**：翻译与地址空间无关，**所有进程共享**。内核代码、内核数据页、共享库这类"每个进程都一样"的映射放这里；
- **nG = 1（进程特有表项）**：属于某个进程的地址空间，进程切换时需要处理。

::: note ASID：让"进程特有"不必每次都清
AArch64 引入 **ASID（Address Space Identifier，地址空间标识符）**：给每个进程的地址空间一个编号，TLB 表项里带上 ASID。切换进程时只需改 ASID 寄存器，**TLB 里别人的表项自然失效**，不必全清。

这正是 2.9 提到的 "TLB 管理指令"（TLBI 系列）存在的原因——它们用于**手动失效** TLB 表项（如修改页表后、进程退出时）。
:::

## 5.7.4 重名问题与同名问题

这两个词在素材书里反复出现（15.4 与 17 章），是 Cache 与 TLB 共同的问题，必须分清：

| | **重名问题**（synonym / aliasing） | **同名问题**（homonym） |
|:--|:--|:--|
| 说的是 | **同一个物理地址**被映射到**多个虚拟地址** | **同一个虚拟地址**在不同上下文指向**不同的物理地址** |
| 典型场景 | 进程地址空间里两个不同的虚拟地址其实映射同一块物理页（共享内存、别名映射） | 进程切换后，同一虚拟地址在另一个进程里指向别处；或 MMU 上下文切换 |
| 危害 | 用**虚拟索引**的缓存/TLB 会把两者当成两项，但它们内容相同 → 反而可能"看起来"一致 | 用**虚拟索引**的缓存/TLB 会拿到**上一个进程的旧数据** → 数据泄漏与不一致 |
| 解法 | — | 必须在切换时**刷新（invalidate）**对应的 TLB/Cache，或用 ASID/标签区分 |

**"同名问题"是安全漏洞的常见来源**：进程 A 退出、进程 B 启动，两者的虚拟地址布局相同，若 TLB 里还留着 A 的翻译，B 会读到 A 的数据。

## 5.7.5 VIPT：为什么 Cache 不能随便用虚拟地址索引

2.3.3 提过 VMSA 与多级 Cache，但没展开"Cache 怎么索引"。三种组织方式：

| 组织 | 索引用什么地址 | 特点 |
|:--|:--|:--|
| **VIVT**（Virtual Index, Virtual Tag） | 虚拟地址索引 + 虚拟地址标记 | 最快，但**要求虚拟地址→物理地址是恒等映射**，否则 5.7.4 的同名问题必然出现 |
| **PIPT**（Physical Index, Physical Tag） | 物理地址索引 + 物理地址标记 | 最简单、最安全，但**必须先完成地址翻译**才能查 Cache → 依赖 TLB |
| **VIPT**（Virtual Index, Physical Tag） | 虚拟地址索引 + 物理地址标记 | **折中**：索引用虚拟地址（快），标记用物理地址（安全） |

**VIPT 的矛盾**：用虚拟地址索引，意味着在完成翻译**之前**就得知道该用哪一组（set）。但翻译结果（物理地址）此时还不知道——怎么定组？

答案：**用虚拟地址的索引位去选组，用物理地址的标记位去比对**。只要满足一个条件就成立：

> **物理地址与虚拟地址的索引位（index）必须完全对应**——即页大小（4 KB / 2 MB / 1 GB）不小于 Cache 的组跨度。

举例：L1 D-Cache 32 KB、4 路组相连、64 字节行 → 组数 = 32KB/(4×64) = 128 组 → 索引需 7 位。4 KB 页内偏移 12 位，取其中高 7 位做索引，**页内偏移与索引位的对应关系对所有页都成立** → 虚拟地址的索引位与物理地址的索引位天然一致。

**VIPT 会不会产生重名问题**（素材书自测题第 12 题）：**不会**。因为标记域用的是**物理地址**——两个虚拟地址映射到同一物理页时，标记相同、组也相同，硬件会正确识别为同一行。反过来，**同名问题也不存在**：物理标记保证了跨进程切换后的旧行不会被误命中（只要切换时做了正确的 TLB/Cache 维护）。

**VIPT 的限制**：它要求"索引位与物理地址对应"，因此当页大小小于 Cache 组跨度时，VIPT 无法实现——这也是为什么 L1 Cache 通常用 PIPT（依赖 TLB），而 L2 往外的 Cache（组更大）才能用 VIPT。

## 5.7.6 TLB 维护指令

AArch64 提供 **TLBI 系列**系统寄存器用于 TLB 维护：

| 指令 | 作用范围 |
|:--|:--|
| `TLBI VAAE1IS, <Xt>` | 按虚拟地址失效（当前 ASID） |
| `TLBI VAE1IS, <Xt>` | 按虚拟地址失效（所有 ASID） |
| `TLBI VALLIS` / `TLBI ALL` | 失效全部 |

**"IS"后缀 = Inner Shareable**（见 5.8.3）——只失效本核内部的共享域；不带 IS 的版本作用于全局。

**什么时候必须手动失效 TLB**（素材书自测题第 16 题）：**修改页表项时**。因为 TLB 里存的是旧的翻译结果，改了页表但 TLB 没失效，CPU 仍会用旧映射访问内存。

**为什么还要发 IPI**：改了某个核的地址空间（页表），其它核的 TLB 里也可能有旧表项——但**一个核不能直接改另一个核的 TLB**（那不是它的寄存器）。所以要通过 **IPI（核间中断）**通知其它核："请刷新你的 TLB"。素材书提到 Linux 的 `flush_icache_range` 在失效指令 Cache 后要发一个 IPI，而**回调函数是空的**——因为目的只是"打断那个核、让它执行到刷新点"，具体刷新逻辑在中断路径里。

## 本节小结

TLB 是翻译结果的缓存，按 VA 位段分表（L1/L2/S2）；用 **ASID** 避免进程切换时全清；**重名**指同一物理地址有多个虚拟别名，**同名**指同一虚拟地址在不同上下文指向不同物理地址——后者是数据泄漏的温床。Cache 的索引方式（VIVT / PIPT / VIPT）直接决定会不会踩"同名"：**VIPT 用虚拟地址索引、物理地址标记，是主流折中**。页表一改，TLB 就得失效；而跨核失效只能靠 IPI 通知。
