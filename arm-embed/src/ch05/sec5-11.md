# 5.11 链接器、链接脚本与 AAPCS64

第三章 3.11 讲了汇编源程序的结构与内嵌汇编，但没讲**汇编之后发生的事**：多个目标文件怎么合成一个可执行镜像，符号地址怎么确定，以及函数之间按什么约定传参。本节补上这三块——它们是"能写出正确汇编"与"能写出能被 C 正确调用的汇编"之间的差别。（依据素材书第 9、21 章）

## 5.11.1 三个地址：链接地址、虚拟地址、加载地址

素材书自测题第 7 题问的就是这三个概念：

| 地址 | 是什么 | 谁决定 |
|:--|:--|:--|
| **链接地址（link address）** | 链接器把各目标文件合成一个镜像时给每个符号分配的地址 | **链接脚本**决定 |
| **虚拟地址（virtual address）** | 程序运行时看到的地址 | 链接地址 + **运行时的重定位**（由 bootloader/内核做） |
| **加载地址（load address）** | 镜像在存储器里的实际物理位置 | 由**加载方式**决定（Flash 里的固定位置、串口下载的 RAM 等） |

**当一个程序代码段的链接地址与加载地址不一致时怎么办**——答案是**重定位（relocation）**：链接器在镜像里插入"占位"，由加载器（或带重定位支持的引导代码）在运行时把实际地址填进去。

::: think 一个具体的例子
树莓派上内核镜像 `.text` 的链接地址是 0x80000（虚拟地址，带 MMU 时还要再经页表翻译），而它烧在 SD 卡某个偏移处（加载地址）。开机时 firmware 用 `smp_call_function` 之类的方式把它拷到 0x80000 再跳转——**拷贝就是"让加载地址对齐链接地址"**。而更一般的嵌入式场景（程序自己会重定位）则由链接器生成的重定位表完成。
:::

## 5.11.2 链接脚本

链接脚本（GNU ld 的 linker script）描述**输出镜像的布局**。素材书第 9 章讲的要点：

- **输入段（input section）** 与 **输出段（output section）** 的区别：输入段来自各个目标文件，输出段是链接器合并后的最终布局；
- 典型脚本会安排 `.text`（代码）、`.rodata`（只读数据）、`.data`（已初始化可写数据）、`.bss`（未初始化数据，运行时清零）等的顺序与对齐要求。

素材书给出的 BenOS 镜像布局（它的实验输出）正是链接脚本的结果：

```
BenOS image layout:
  .text.boot: 0x00080000 - 0x000800d8 (   216 B)
      .text: 0x000800d8 - 0x000832e0 ( 12808 B)
    .rodata: 0x000832e0 - 0x00083566 (   646 B)
      .data: 0x00083566 - 0x000838c0 (   858 B)
       .bss: 0x00083970 - 0x000a3d80 (132112 B)
```

::: note .bss 为什么这么大
`.bss` 不占镜像文件空间——它在文件里只有一段描述，加载时由运行时清零。所以它的"大小"（132 KB）远大于文件里其它段之和。这也解释了为什么**链接脚本里 .bss 往往放在最后**：它只需要在镜像末尾记录一个起点和大小。
:::

**链接脚本与本教材的关联**：第三章 3.9.4 讲的伪指令 `LDR Rd, =label` 需要把 label 的地址放进**文字池**——文字池是汇编器在代码段里开的常量区。链接时，文字池里的值被填成**最终链接地址**，这段填充正是链接器的重定位工作。

## 5.11.3 AAPCS64：函数怎么互相调用

第二章 2.7 与第三章 3.11 提到 **APCS**（ARM Procedure Call Standard）规定了寄存器在调用中的分工。AArch64 版本是 **AAPCS64**，核心规则：

| 寄存器 | 角色 |
|:--|:--|
| **x0–x7** | 参数与返回值（a0–a7） |
| **x8** | 间接返回地址（IP0） |
| **x9–x15** | 临时寄存器（t0–t6） |
| **x16–x18** | IP0–IP2（可跨调用使用） |
| **x19–x28** | **被调用者保存**（callee-saved） |
| **x29** | 帧指针（FP） |
| **x30** | 链接寄存器（LR） |
| **SP** | 栈指针（16 字节对齐） |
| **x31** | **零寄存器**（读作 0；作为 Rd 编码时表示 SP） |

**调用者保存 vs 被调用者保存**是全篇最该记住的一条：

- **调用者保存（caller-saved，x0–x18）**：函数内部可以随便改；调用者若要跨调用保留，必须自己存到栈里；
- **被调用者保存（callee-saved，x19–x28）**：函数若修改了，**必须先存原值到栈、返回前恢复**。

对照 AArch32（3.11.7）：R4–R11 是被调用者保存（v1–v8），R0–R3 与 R12 是调用者保存（a1–a4、IP）。**规则完全一致，只是寄存器名字换了。**

**栈的布局**（素材书自测题第 20 题要求画出 main→func1→func2 的栈布局）：

```
高地址
┌─────────────────┐
│  func2 的局部变量 │   ← 栈向下生长
├─────────────────┤
│  func1 保存的寄存器│
├─────────────────┤
│  func1 的局部变量 │
├─────────────────┤
│  main 保存的寄存器│
├─────────────────┤
│  main 的局部变量 │
└─────────────────┘  ← SP
低地址
```

**帧指针 x29（FP）** 的作用：让函数能以"相对帧指针"访问自己的参数与局部变量——即便调用者释放了栈空间，返回地址仍可定位。这是 AArch32 的 R11（FP）在 64 位下的延续。

## 5.11.4 64 位编程的 C 语言陷阱

素材书 21.1 节讲的问题，在从 32 位迁移到 64 位时非常常见。

**数据模型**（素材书表 21.1）：

| 类型 | ILP32 | ILP64 | LP64 |
|:--|:--|:--|:--|
| int | 4 | 4 | 4 |
| long | 4 | 4 | **8** |
| long long | 8 | 8 | 8 |
| pointer | 4 | **8** | 8 |
| size_t | 4 | 8 | 8 |

- **ILP32**：int、long、指针都是 4 字节；
- **ILP64**：int、long 都是 4 字节，指针 8 字节；
- **LP64**：int 4 字节、**long 8 字节**、指针 8 字节（**Linux 的选择**）。

**陷阱一：把指针强转成 int**。素材书例 21-1：

```c
    char *get_pte(char *pte_base, int offset) {
        int pte_addr, pte;
        pte_addr = (int)pte_base;      /* 32 位下没问题 */
        pte = pte_addr + offset;
        return (char *)pte;
    }
```

32 位下 int 与指针同宽，没问题；**64 位下指针 8 字节、int 4 字节，强转会截断**。正确做法是用 C99 的 `intptr_t` / `uintptr_t`（按系统位数自动定宽）。素材书还指出：Linux 内核里常用 `unsigned long` 做同样的事，因为它与指针同宽。

**陷阱二：整型提升与隐式转换**。素材书 21.1.2：

- 赋值表达式中，右边自动转成左边的类型；
- 算术表达式中，占字节少的数据类型向占字节多的转换（**ARM64 下 int 与 long 运算，int 要转成 long**）；
- 有符号与无符号混算时，**有符号转成无符号**。

这类问题在 32 位上"碰巧没事"，到 64 位就变成真 bug。

## 5.11.5 与第三章 3.11 的对照

| 主题 | 3.11（AArch32） | 5.11（AArch64） |
|:--|:--|:--|
| 参数寄存器 | R0–R3 | x0–x7 |
| 返回地址 | R14 (LR) | x30 (LR) |
| 帧指针 | R11 (FP) | x29 (FP) |
| 被调用者保存 | R4–R11 | x19–x28 |
| 栈指针 | R13 (SP) | 独立 SP 寄存器 |
| 栈对齐 | 4/8 字节 | **16 字节** |
| 压栈/弹栈 | STMFD / LDMFD | STP / LDP |
| 返回 | MOV PC, LR | RET |
| 数据模型 | ILP32 | LP64（Linux） |

## 本节小结

链接器负责把目标文件合成镜像并定址；链接脚本描述段布局；链接地址、虚拟地址、加载地址三者可能不同，差值由重定位机制补齐。AAPCS64 规定了参数寄存器（x0–x7）、被调用者保存寄存器（x19–x28）、帧指针（x29）与 16 字节栈对齐——规则与 AArch32 的 APCS 一脉相承，只是换了名字与宽度。64 位迁移最常见的坑是**把 64 位指针塞进 32 位 int**，用 `intptr_t` 解决。
