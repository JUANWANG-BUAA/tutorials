# 5.6 MMU 与多级页表

第二章 2.3.3 只用一句话带过 MMU："Cortex-A9 采用 VMSA，经 MMU 支持虚拟地址→物理地址转换与存储保护，页表遍历经由 CP15 的 C0–C15 寄存器控制"。AArch64 时代这变成了操作系统的**日常工作**：每个进程一套页表、每次地址翻译四级查表。本节讲清这条链路。（依据素材书第 14 章）

## 5.6.1 虚拟地址：CPU 用的地址不是真实地址

程序编译时看到的地址是**虚拟地址（VA）**，经 MMU 翻译后得到**物理地址（PA）**。这条翻译链带来三个能力：

1. **进程隔离**：每个进程一套地址映射，互不可见（4.7 的"内存保护单元"在硬件上的实现）；
2. **按需分页**：虚拟地址空间可以远大于物理内存，未用到的页根本不映射；
3. **统一的内存属性**：可执行/可读写/不可执行等权限挂在页表项上（5.6.4）。

## 5.6.2 为什么必须多级：一级页表不可行

假设 48 位虚拟地址、4 KB 页面粒度：

- 一页 4 KB = 4096 字节；
- 若一级页表就能覆盖全部 48 位地址空间，需要 $2^{48}/2^{12} = 2^{36}$ 个页表项；
- 每个页表项 8 字节 → 页表本身要 $2^{39}$ 字节 = **512 GB**。

显然不可行。**多级页表**的解法是**逐级收窄**：每一级页表项指向下一级页表，而不同虚拟地址区域可以共享同一份低层页表——大量进程的地址空间因此共用物理页表页。

AArch64 的典型配置是**四级页表**：

| 级 | 索引位 | 覆盖的虚拟地址范围 |
|:--|:--|:--|
| L0 | VA[47:39] | 512 GB |
| L1 | VA[38:30] | 1 GB |
| L2 | VA[29:21] | 2 MB |
| L3 | VA[20:12] | 4 KB |

## 5.6.3 一次地址翻译的完整过程

处理器访问一个虚拟地址时：

```
虚拟地址 VA
   │
   ├─ ① 查 TLB：命中？ ── 是 ──► 直接得到 PA（快路径）
   │                   └ 否 ↓
   ├─ ② 遍历页表：L0 表 → L1 表 → L2 表 → L3 表
   │        每级用 VA 的对应位做索引，取出下一级页表基址
   │        走到 L3，得到 PA，并检查访问权限
   │
   ├─ ③ 把 (VA → PA, 权限, 内存属性) 填入 TLB
   └─ ④ 用 PA 访问 Cache / 内存
```

**L1–L3 的页表项**：指向下一级页表的基址（高 4KB 对齐）。
**L3 的页表项**：指向实际物理页帧的基址，并携带**访问属性**（下一节）。

**权限检查发生在翻译时**：如果该页的权限不允许本次访问，MMU 直接触发**数据中止异常**（AArch64 的 EC = 0x24/0x25），控制流根本不会到达数据——这就是"硬件强制的内存保护"。

## 5.6.4 页表项的属性位

AArch64 的块描述符（页表项）带一组属性位，管权限与状态：

| 属性 | 含义 |
|:--|:--|
| **AF**（Access Flag） | 页面是否被访问过 |
| **nG**（non-Global） | TLB 表项是**进程特有**（nG=1）还是**全局**（nG=0） |
| **UXN / PXN** | 用户态 / 特权态下**是否可执行** |
| **AP[2:1]** | 访问权限（可读/可写/只读） |
| **WXN** | 全局控制"可写即不可执行" |
| **SH** | 内存**共享属性**（Non-shareable / Inner Shareable / Outer Shareable，见 5.8.3） |
| **AttrIndx[2:0]** | 指向内存属性表（Device / Normal 等，见 5.6.6） |
| **BlockDesc（BD）** | 该项是**页表项**（指向下一级）还是**块描述符**（指向实际页） |

**WXN 位的思路**（素材书 14.3 节）：WXN=1 时，**在 EL0 里具有可写权限的内存区域不可执行**（含特权模式下的等效限制）。这让"W^X"策略可以用一个位表达：**同一页不能既可写又可执行**，堵掉了"把 shellcode 写进数据页再当代码执行"这类攻击。

**AF 与脏位由谁来维护**：

- **ARMv8.0**：软件维护。CPU 第一次访问一个 AF=0 的页面会触发**访问标志位异常（access flag fault）**，内核再把 AF 置 1；
- **ARMv8.1（TTHM 特性）**：**硬件管理**访问位与脏位，页表项里的硬件管理位（AF/Dirty 的硬件更新位）置位后由硬件自动更新。

软件维护 AF 有个实际好处（素材书列出）：**判断某个已分配页面是否真被访问过**，用于**页面回收**——从没被碰过的页面可以直接回收。

## 5.6.5 连续块表项：一个 TLB 表项映射多个页面

AArch64 的页表设计里有一项针对 TLB 的优化：**连续块表项位（Contiguous Block Descriptor, CBD）**。

使用条件（素材书 14.2.7 节）：

- 对应的虚拟地址必须**连续**；
- 4 KB 页面时，**16 个**连续页面可用一个表项；
- 16 KB 页面时，32 个或 128 个连续页面；
- 64 KB 页面时，32 个连续页面；
- 连续的页面必须有**相同的内存属性**；
- 起始地址必须页对齐。

效果：把一段连续虚拟地址映射到一段连续物理地址时，只占**一个 TLB 表项**，TLB 压力骤降。

## 5.6.6 两种内存属性：Normal 与 Device

AArch64 的页表项通过 **AttrIndx** 指向内存属性表，区分两大类：

| | **Normal memory**（普通内存） | **Device memory**（设备内存） |
|:--|:--|:--|
| 可缓存 | 是（可按策略缓存） | **否**（或严格有序） |
| 重排 | 允许（对内存序无影响） | **不允许** |
| 用途 | 普通读写的数据、代码 | **外设寄存器** |

**为什么设备内存不能缓存也不能重排**：外设寄存器的读写有副作用（比如"写 FIFO 触发发送"、"读状态寄存器会清标志"）。如果缓存了这次写，读回来的是缓存里的旧值而不是设备的真实状态；如果重排了两次写，设备收到的顺序可能与程序写的顺序不同。

这正好接上第二章 2.11.2 的 MMIO：**AArch32 时代 MMIO 靠"绝不猜测"（编译器用 volatile 约束、内存属性寄存器配置）来保证，AArch64 把它做进了架构**——设备内存由硬件保证不被缓存、不被重排。

## 5.6.7 使能 MMU 前的恒等映射

素材书自测题第 11 题问：**为什么使能 MMU 时需要建立恒等映射（identity mapping）？**

因为**开 MMU 的那条指令本身、以及紧随其后的指令，翻译时也要查页表**。如果此刻虚拟地址与物理地址还没有对应关系，翻译会失败——要么触发异常，要么取到错误的地址。

**恒等映射**指：把"虚拟地址 == 物理地址"的那段地址范围直接映射到自己。于是开 MMU 前后的代码在地址上完全一致，切换过程不需要搬代码。

这条工程约束是通用的，与 AArch32/AArch64 无关：任何带 MMU 的体系结构，启动代码都要先建恒等映射再开 MMU。

## 本节小结

MMU 的工作 = **TLB 命中则快，否则四级页表遍历 + 回填 TLB**。多级的意义是**逐级收窄、共享低层页表**，让 48 位地址空间只需几十 MB 的页表内存。页表项带权限（UXN/PXN/AP/WXN）、状态（AF/脏位）、共享属性（SH）与内存类型（AttrIndx → Normal/Device）。下一节讲加速这一切的 TLB。
