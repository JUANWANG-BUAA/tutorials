# 4.1 嵌入式系统与安全关键系统

"嵌入式系统"这个词被用得很宽——从智能手表到飞机发动机都算。本节先把这个词的严格定义摆出来，再引入一类特别要命的系统：**安全关键系统**。嵌入式 OS 的很多设计选择（分区、优先级继承、可验证性）都是从这一类需求倒逼出来的。（课件 Slide 2–10）

## 4.1.1 "系统"的内涵在演进

课件开篇给了一条演进线：

```
智能系统      = 硬件 + 软件
计算机系统    = CPU + OS + 编译器
分布式系统    = 计算系统 + 网络 + DOS
分布式计算系统 = 网格、云计算、边缘计算…
复杂智能系统   = 感知 + 传输(智能组网) + 存储 + 智能处理 + 执行器 + …
                 无人机、自动驾驶汽车、机器人…
```

底层在**融合**：计算、通信、感知、执行揉进同一个系统里。对开发者的含义是——嵌入式软件不再只是"跑在芯片上的程序"，而是要和传感、通信、执行一起被论证。

## 4.1.2 嵌入式系统的定义

课件给出的定义（按原文口径）：

> **嵌入式系统**：以应用为中心，以计算机技术为基础，软件及硬件可裁剪，满足应用系统对功能（含 AI）、可靠性、成本、体积、功耗等方面严格要求的**专用计算机系统**。

四个关键词值得逐个记：

| 关键词 | 含义 | 对设计的影响 |
|:--|:--|:--|
| **以应用为中心** | 不是通用计算，产品形态由应用决定 | 不要为"以后可能用到"留资源 |
| **软件及硬件可裁剪** | 按需定制 | 正是 RTOS 存在的理由（4.5） |
| **功能（含 AI）** | 智能能力是现代嵌入式的基本要求 | —— |
| **可靠性/成本/体积/功耗** | 硬指标，互相牵制 | 决定了为什么不能简单套用桌面 Linux |

::: def 定义 4.1.1 · 嵌入式系统 {#def-4.1.1}
以应用为中心、以计算机技术为基础，软硬件可裁剪，满足应用系统对功能、可靠性、成本、体积、功耗等严格要求的专用计算机系统。
:::

## 4.1.3 万物互联与"Wintel"式生态

课件给出的产业观察：

- 2010 年**智能手机出货量超过 PC**——移动互联时代到来；5G、WiFi 6 等基础设施加上商务/社交/娱乐应用，使移动互联普及；
- 终端形态从手机扩展到平板、上网本、笔记本、汽车、智能硬件、传感器；
- 生态结构是"**三大部分**"：智能终端 + 网络基础设施 + 应用；
- 桌面时代是 **"WinTelCo"**（Intel + Windows）联盟垄断 20 多年；移动时代形成 **"Qualdroid"**（高通 Snapdragon + Android），本质上就是 **ARM + Linux**；当下正在向 **ARM + AI 加速器 + 嵌入式 Linux** 演进。

这条线索在本章会反复出现：**ARM 赢了指令集，Linux 赢了操作系统，而"两者之上再叠一层专用 RTOS"是安全关键领域的答案**（4.2、4.5）。

## 4.1.4 安全关键系统：为什么它们要另一套 OS

**安全关键系统**正广泛应用于越来越依赖的飞机、高铁、汽车、能源、医疗等系统的控制与信息处理。课件给的政策背景：

- 国务院十大科技发展规划中，至少 5 个深度涉及安全关键系统技术（航空发动机、深海空间站、智能机器人、空间飞行器、人脑工程）；
- 国外国家级投入：欧盟 FP6/FP7/Horizon 2020（典型如 **AUTOSAR**，汽车开放系统架构）、美国 NSF/NASA/DoD/DARPA/AFRL/FAA（典型如 DARPA 支持的 META 研究计划）。

::: def 定义 4.1.2 · 安全关键系统 {#def-4.1.2}
失效会导致系统出现**不可接受的安全事故**——不仅仅是人员伤亡和财产损失，甚至导致严重的环境危害和社会安全问题的系统。
:::

它的**跨领域典型**（课件列出）：

| 领域 | 系统 |
|:--|:--|
| 航空 | 机载飞行控制与管理系统、通讯系统、导航系统；航天载人与探测系统、飞行控制系统 |
| 医疗 | 人体健康监护系统、心脏监护、自动给药系统 |
| 交通 | 铁路交通控制系统、调度系统；汽车控制电子系统、无人驾驶系统、驾驶稳定系统 |
| 能源 | 核电安全控制系统、反应堆冷却系统 |

**典型特征**（三条，课件原话）：

1. 由**异构节点组成的分布式系统**，多种任务并发执行；
2. 通常为**硬实时系统**，对系统的响应时间和处理时序有严格要求；
3. **周期性任务和非周期性任务混合**。

这三条直接决定了本章要讲的东西：并发 → 调度与同步（4.8–4.10）；硬实时 → 确定性与实时性能指标（4.12）；异构分布式 → 分区与通信（4.2）。

## 4.1.5 技术特征：层次性、涌现性、确定性

课件进一步给出三条技术特征：

**① 系统具有层次性**

```
应用层           软件 + 数据
运行平台层       操作系统 + 通讯服务 + 任务调度服务 + 系统配置 + 编译环境 + 库函数
运行平台硬件层   系统硬件模块（含 CPU、网络、内存等）
运行环境硬件层   外围 I/O 设备（含传感器、作动器等）
```

**② 系统具有涌现特性**——源于不同层次间不同组件之间的大量交互。两个量化指标：

- **失效概率**（如 <10⁻⁹）；
- **系统失效模式、任务运行时间**。

**③ 要求系统行为特性具有确定性**

- **时间确定性**：在任何状态下，任务执行的时间特性都确定；
- **故障处理确定性**：在任何情况下，故障限制单元范围确定，故障处理效果确定。

::: think "确定性"和"快"是两件事
课件在 4.12 会把这一点展开（Gillies 的定义、硬实时 vs 软实时）。先记住这里的措辞：**"在任何状态下都确定"**——不是平均快、不是最好情况快，而是**最坏情况有上界**。一个平均 1 ms 但偶尔卡 200 ms 的系统，对硬实时任务毫无价值。
:::

## 4.1.6 软件规模：安全关键系统为什么难

课件用两个行业的规模数据说明"软件是重中之重"：

| 平台 | 软件规模 |
|:--|:--|
| 空客 A380、波音 787 | 软件系统**超过 500 万行** |
| 汽车系统 | 达到或超过 **1000 万行** |
| F-22 航电 | 约 170 万行 |
| F-35（Block 3 计划） | 约 860 万行 |
| 波音 777 飞控 | 约 200 万行 |
| A310 / A320 / A340 | 约 4 MB / 10 MB / 20 MB |

趋势判断：**将近 50% 的计算机系统都部署和运行于安全关键系统中**，需要对其系统设计与实现进行详尽的审查和认证。这就是 4.2 那套标准体系存在的全部理由。

## 本节小结

嵌入式系统 = 以应用为中心、软硬件可裁剪、满足功能/可靠性/成本/体积/功耗硬指标的专用计算机系统；安全关键系统的失效不可接受，因而要求硬实时、层次化、行为确定。产业侧的结论（ARM + Linux 生态、嵌入式 OS 的专用化需求）为 4.5 选型与 4.2 标准体系埋下伏笔。下一节看标准：DO-178B/C 到底管什么。
