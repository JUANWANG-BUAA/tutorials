# 4.13 实时 Linux

VxWorks 性能极好但成本很高；对一般的**软实时**应用系统，采用实时 Linux 已成为一种趋势。本节按课件讲四条技术路线：**瘦内核（微内核）**、**超微内核**、**资源内核**、以及**内核内建方案**（CONFIG_PREEMPT / PREEMPT_RT），最后看 Linux 自身的调度策略。（课件 Slide 180–196）

## 4.13.1 Linux 的调度策略与问题

**通用 Linux 支持实时和非实时两种进程**，实时进程相对于普通进程具有**绝对的优先级**：

| 进程类型 | 调度策略 |
|:--|:--|
| 实时进程 | **SCHED_FIFO** 或 **SCHED_RR** |
| 普通进程 | **SCHED_OTHER** |

课件指出：Linux 中每个任务有**四个与调度相关的参数**——`rt_priority`、`policy`、`priority`（nice）、`counter`，调度程序据此调度。

**SCHED_OTHER 的逻辑**（Slide 181）：调度器总是选择 **priority + counter 值最大**的进程执行。存在**调度周期（epoch）**：

- `priority`（nice）：**固定不变**，进程创建时确定，代表该进程的优先级，也决定它在每个调度周期能分到多少时间片；
- `counter`：**动态变化**，反映该进程在当前调度周期中还剩多少时间片；
- 每个调度周期开始时 `counter ← priority`；每次被调度执行时 `counter` 递减；`counter` 归零则该进程用完本周期的时间片，不再参与本周期调度；
- 所有进程时间片用完 → 一个 epoch 结束，周而复始；
- **epoch 长度不是静态的**——处于可运行状态的进程数量与它们的 priority 值都会影响 epoch 长短。

在 2.4 以上内核中 `priority` 被 **nice** 取代，但作用类似。

**SCHED_OTHER 本质上是一种比例共享调度策略**，保证公平性（低优先级进程每个 epoch 也会得到应得的 CPU 时间），同时提供优先级区分（高 priority 获得更多执行时间）。

**实时进程**（Slide 182）使用基于 `rt_priority` 的优先级调度策略，同一实时优先级内的调度方式不同：

- **SCHED_FIFO**：按静态优先级排队，同优先级队列中**谁先准备好谁先调度**；**正在运行的进程不会被终止**，直到：① 被更高优先级进程抢占；② 自己因资源请求而阻塞；③ 自己主动放弃 CPU（调用 `sched_yield`）；
- **SCHED_RR**：与 FIFO 基本相同，但**给每个进程分配一个时间片**，时间片到了正在执行的进程就放弃执行；时间片长度可用 `sched_rr_get_interval` 获取。

**Linux 用于实时应用的问题**（Slide 183，课件原文的五条）：

1. **Linux 系统中的调度单位为 10 ms**，所以它**不能够提供精确的定时**；
2. 当一个进程调用系统调用进入内核态运行时，**它是不可被抢占的**；
3. **Linux 内核实现中使用了大量的封中断操作会造成中断的丢失**；
4. 由于使用**虚拟内存技术**，当发生页出错时需要从硬盘读取交换数据，硬盘读写的随机性导致随机读写时间，**在某些情况下会影响实时任务的截止期限**；
5. 虽然 Linux 进程调度也支持实时优先级，但**缺乏有效的实时任务的调度机制和调度算法**；其**网络子系统的协议处理和其它设备的中断处理都没有与对应的进程调度关联起来**，且它们自身也没有明确的调度机制。

::: think 第 2 条与 4.12 的呼应
"内核态不可被抢占"意味着：一个低优先级进程一旦进了内核，高优先级实时进程就得等它出来。**这直接破坏了 4.12.1 的确定性**——响应时间取决于那个低优先级进程的内核路径有多长，而这不可控。CONFIG_PREEMPT 与 PREEMPT_RT 就是冲着这条去的（4.13.4）。
:::

## 4.13.2 路线一：瘦内核（Thin-Kernel / 微内核）

课件 Slide 185：

> 瘦内核（或微内核）方法**使用第二个内核作为硬件与 Linux 内核间的抽象接口**。**非实时 Linux 内核在后台运行，作为瘦内核的一项低优先级任务托管全部非实时任务**。**实时任务直接在瘦内核上运行**。
>
> 瘦内核主要用于（除了托管实时任务外）**中断管理**：瘦内核**截取中断以确保非实时内核无法抢占瘦内核的运行**。这允许瘦内核提供硬实时支持。

结构：

```
        硬件
   ↑  （中断先到瘦内核）
  瘦内核（第二内核）：截获中断、执行实时任务
   ↓  非实时任务作为低优先级任务托管给
  非实时 Linux 内核（后台运行）
```

**优点**：瘦内核截获中断，**提供硬实时支持**，且与标准 Linux 内核共存。

**缺点**（Slide 187）：实时任务和非实时任务是**独立的**，这造成了**调试困难**；而且非实时任务**并未得到 Linux 平台的完全支持**（这是它被称为"瘦"的一个原因）。

**采用这种方法的例子**：**RTLinux**（现由 Wind River Systems 专有）、**RTAI（实时应用程序接口）**、**Xenomai**。

## 4.13.3 路线二：超微内核

课件 Slide 188：

> 超微内核方法**依赖**于包含任务管理的最小内核，而**超微内核法对内核进行更进一步的缩减**。通过这种方式，**它不像是一个内核而更像是一个硬件抽象层（HAL）**。
>
> 超微内核为**运行于更高级别的多个操作系统提供了硬件资源共享**。因为超微内核对硬件进行了抽象，因此它可为更高级别的操作系统提供**优先权**，从而支持实时性。

与虚拟化的关系（Slide 190）：超微内核方法与运行多个操作系统的虚拟化方法有些相似——超微内核在实时和非实时内核中**对硬件进行抽象**，这与 **hypervisor** 从客户（guest）操作系统对裸机进行抽象的方式相似。

**应用**：**ADEOS（Adaptive Domain Environment for Operating Systems）**，支持多个并发操作系统同步运行；**当发生硬件事件后，ADEOS 对链中的每个操作系统进行查询以确定使用哪一个系统处理事件**。

## 4.13.4 路线三：资源内核

课件 Slide 191：

> 资源内核法为**内核增加一个模块，为各种资源提供预留（reservation）**。这种机制保证了对**时分复用系统资源**的访问（CPU、网络或磁盘带宽）。这些资源拥有多个**预留参数**，如**循环周期、需要的处理时间**（完成处理所需的时间）以及**截止时间**。

课件 Slide 193 补齐机制：资源内核提供一组 **API**，允许任务**请求这些预留资源**；然后资源内核可以**合并这些请求，使用任务定义的约束定义一个调度**，从而提供确定的访问——**如果无法提供确定性则返回错误**。通过 EDF 等调度算法，内核可以处理动态的调度负载。

**实现**：**CMU 公司的 Linux/RK**，把可移植的资源内核集成到 Linux 中作为一个**可加载模块**；该实现演化成商用的 **TimeSys Linux/RT** 产品。

::: think 资源内核的思路
前三条路线都在"**改造内核结构**"（加一层、减一层、加模块），资源内核换了思路：**不改结构，改资源分配方式**——把 CPU 时间、磁盘带宽当作可"预订"的商品，预订时连周期、时长、截止期一起提交，内核据此合成一个确定性调度表。**若合不出来就返回错误**，这比"默默延迟"更符合实时系统的要求（4.12.1：错过时限即失效）。
:::

## 4.13.5 路线四：内核内建方案

**CONFIG_PREEMPT（课件 Slide 194）**：标准 Linux 2.6 内核加入实时功能——通过简单配置使其**完全可抢占**，即可得到**软实时**功能。

要解决的问题：标准 2.6 内核中，用户空间进程执行**内核调用**时不能被抢占——低优先级进程进了内核，高优先级进程必须等调用结束才能访问 CPU。**CONFIG_PREEMPT 改变了这一行为**：在高优先级任务可用的情况下（即使该进程正在进行系统调用），允许进程被抢占。

课件对代价的说明（Slide 196）：这是一个**折衷**——实现了软实时性能、且在负载条件下系统仍能顺利运行，但**略微减低了吞吐量与内核性能**，原因是该选项**增加了开销**。该选项对桌面和嵌入式系统有用，但**并非任何场景都有用（例如服务器）**。

**高精度定时器**：2.6 内核的另一项有用配置选项，允许定时器以 **1 μs 精度**运行（若底层硬件支持），并通过**红黑树**实现对定时器的高效管理；使用红黑树可以**使用大量定时器而不会对定时器子系统（O(log n)）的性能造成影响**。

**PREEMPT_RT 补丁（Slide 196）**：只需要一点额外工作，就可以通过 PREEMPT_RT 补丁实现**硬实时**。它提供的修改包括：

- **重新实现一些内核锁定原语**，从而实现**完全可抢占**；
- 实现**内核互斥的优先级继承**（呼应 4.10.6）；
- 把**中断处理程序转换为内核线程**，以实现**线程可抢占**。

::: note 最后一条的深刻之处
"把中断处理程序转换为内核线程"——这正是 4.4.9 讲的 seL4 做法（中断抽象成消息）和 4.11.1 讲的硬件 ISR 范式的**反向操作**。不同内核在不同历史路径上殊途同归：**要让实时性可保证，就必须让所有可能延迟的代码路径都可被抢占**。seL4 把驱动搬出内核，PREEMPT_RT 把中断变成线程，方向相反、目的一致。
:::

## 4.13.6 四条路线对比

| 路线 | 结构改动 | 硬实时 | 代表 | 主要代价 |
|:--|:--|:--|:--|:--|
| **瘦内核** | 加第二内核，截获中断 | **可以** | RTLinux、RTAI、Xenomai | 实时/非实时任务独立，调试困难；非实时侧支持不完整 |
| **超微内核** | 内核减为 HAL | 可以（靠优先级） | ADEOS | 多 OS 协同复杂 |
| **资源内核** | 加可加载模块 | 可以（资源预订） | Linux/RK → TimeSys Linux/RT | 需要应用配合声明资源需求 |
| **CONFIG_PREEMPT** | 内核配置项 | **软实时** | Linux 2.6+ | 吞吐量与内核性能略降 |
| **PREEMPT_RT** | 补丁 | **硬实时** | Linux RT 社区 | 维护成本、与厂商内核的兼容 |

## 本节小结

Linux 的实时化有两条主线：**改结构**（瘦内核、超微内核、资源内核）与**改内核行为**（CONFIG_PREEMPT、PREEMPT_RT）。前三条路线各自绕开"内核态不可抢占"的根本问题（加一层、改优先级分配、改调度单位），PREEMPT_RT 则直接解决它（完全可抢占 + 内核优先级继承 + 中断转线程）。选择依据是 4.12 的判据：软实时用 PREEMPT 足够，硬实时需要 PREEMPT_RT 或专用 RTOS。第四章到此结束——回到[卷首知识地图](../preface-map.md)，看三章如何构成一条线。
