# 4.10 进程间通信与同步

两个任务要交换数据、还要保证不打架，需要两类机制：**通信**（数据怎么过去）与**同步**（谁等谁）。本节按课件的脉络走：两种通信形式 → 共享内存/消息传递 → 邮箱/消息队列 → 信号量 → 死锁 → 优先级反转。（课件 Slide 138–142、146、150–155）

## 4.10.1 两类问题：通信与同步

课件 Slide 138 给出进程间通信的两种形式（并指出有**阻塞与非阻塞**之分）：

| 形式 | 机制 | 图示（课件） |
|:--|:--|:--|
| **共享内存** | 多个进程读写同一块"共享单元" | 进程 p1 写 → 共享单元 → 读 ← 进程 p2（基于总线的共享内存通信） |
| **消息传递** | 通过内核在进程间搬运"消息" | 进程 p1 → 消息 → 进程 p2 |

**阻塞与非阻塞**：阻塞式调用在条件不满足时把调用者挂起（进入 4.7.2 的阻塞态）直到条件满足；非阻塞式调用立即返回"暂时做不到"。RTOS 里两者都有——μC/OS 的 **Split-Phase Operations**（4.5.5 TinyOS 那节）就是极端例子：完全不提供阻塞操作。

## 4.10.2 共享内存：快，但必须自己保证互斥

课件 Slide 139：

- 共享内存通过**共享数据结构**来实现，数据结构类型可以是**全局变量、指针、缓冲区**等；
- 使用共享数据结构时，**必须保证共享数据结构使用的排它性**，即保证**每个任务或中断服务程序独享**该数据结构；
- 实现对共享数据结构操作的互斥常用三种手段：**开/关中断**、**禁止任务切换**、**信号量（semaphore）机制**。

::: think 共享内存为什么快、为什么危险
快：数据不用拷贝，直接读写同一块物理内存，延迟最低。危险：读写之间没有隐含的"消息交接"动作——CPU 读到的是**对方写到一半的值**。所以共享内存必须配一把锁，锁的粒度就是临界区（4.7.6）。**共享内存 + 信号量**是嵌入式里最常见的组合：数据走共享内存，同步走信号量。
:::

## 4.10.3 消息传递：邮箱与消息队列

**消息传递**（Slide 140）：任务可以通过**内核提供的系统服务**向另一任务发送消息。消息机制包括**消息邮箱**和**消息队列**。

**消息邮箱（Mailbox）**（Slide 141）：

- 消息通常是**内存空间的一个数据结构，通常是一个指针型变量**；
- 一个任务或一个中断服务子程序通过内核服务，可以把一则消息**放到邮箱**里去；另一个或多个任务通过内核服务可以**接收**这则消息；
- 内核提供的邮箱服务有四项：**邮箱内消息内容的初始化**、**将消息放入邮箱（post）**、**等待消息进入邮箱（pend）**、**从邮箱中得到消息**。

**消息队列（Queue）**（Slide 142）：

- 消息队列是**消息的链接表**，存放着内核中由**消息队列标识符**标识的消息；简称队列（queue），标识符为**队列 ID（queue ID）**；
- **消息队列实际上是邮箱阵列**——在消息队列中允许存放**多个消息**；
- 对消息队列的操作和对消息邮箱的操作**基本相同**：初始化、post、pend、取出消息。

::: think 邮箱 vs 队列：一个槽还是一条队
| | 消息邮箱 | 消息队列 |
|:--|:--|:--|
| 容量 | 通常 1 条（一个指针） | 多条（链表） |
| 满时 post | 覆盖旧值 / 失败，取决于实现 | 阻塞等待空间 / 失败 |
| 适用 | 单 producer 单 consumer 的"信号量式"通知 | 生产者消费者、多对多 |
:::

## 4.10.4 信号量：三种用途

课件 Slide 153：

> **信号量实际上是一种约定机制**，在多任务内核中普遍使用。信号量主要用于：
> 1. **控制共享资源的使用权**（满足互斥条件）
> 2. **标志某事件的发生**
> 3. **使两个任务的行为同步**

课件指出一处常见混淆：**信号与信号量（均为 Semaphore）并不加以区分**，有两种类型：

| 类型 | 说明 |
|:--|:--|
| **二进制型（binary）** | 取值 0/1，用作互斥锁（"门锁"） |
| **计数器型（counting）** | 取值为整数，用作资源计数或事件计数 |

课件还给了**信号量与互斥**的图示（Slide 146）：任务 A、B、C 共享一个资源，通过信号量保证"访问共享资源之前申请信号量，其它任务访问受阻而不能使用共享资源，得到允许后才能使用"。

::: note 语义量与互斥量的区别（工程要点）
课件统一称"信号量"，但工程上两种机制语义不同：
- **互斥量（mutex）**：有**所有权**——谁加锁谁解锁，别人不能替它解锁；
- **信号量（semaphore）**：**无所有权**——任何任务都能 post。
这个差别是**优先级继承（4.10.6）**能实现的前提，也是"用信号量当互斥锁"在某些内核里会出错的根源。
:::

## 4.10.5 死锁

课件 Slide 150 的定义与场景：

> **死锁**指**两个任务无限期地互相等待对方控制着的资源**。设任务 T1 正独享资源 R1，任务 T2 在独享资源 R2，而此时 T1 又要独享 R2，T2 也要独享 R1，于是**哪个任务都没法继续执行**，发生死锁。

课件给出的**最简单的防止死锁的方法**是让每个任务都：

1. **先得到全部需要的资源**再做下一步的工作；
2. **用同样的顺序**去申请多个资源；
3. **释放资源时使用相反的顺序**。

三条其实是同一件事的三个侧面：**全局统一的资源申请顺序**（比如所有任务都先申请锁 A 再申请锁 B），就不可能形成环路等待。

## 4.10.6 优先级反转：一个经典故障

课件 Slide 155 的场景（原文）：

- 有 A、B 两个应用程序，**A 的优先级比 B 高，但是 A 在睡眠，而 B 在运行**；
- B 需要进行文件操作，**发请求给文件服务进程**，自己进入睡眠，等待文件操作完成；
- 本来在睡眠的**文件服务进程**接受到 B 的请求后开始为 B 服务；
- 此时 **A 因某外部事件而变成就绪**；
- 发生调度时，A 与文件服务进程都是就绪状态。**文件服务进程由于优先级高而更为优先。可是文件服务进程代表的是 B，因此发生优先级倒置**。

一句话概括：**高优先级任务 A 的进度，被低优先级任务 B 间接拖住**——B 在等文件服务进程，文件服务进程优先级又比 A 低，于是 A 只能等 B，B 又在等文件服务进程。等待链的**长度随系统负载增长**，延迟因而不可预测。

课件在 4.5.4（RTEMS）与 4.8.6（VxWorks）都提到对策：**优先级继承（Priority Inheritance）**——RTEMS 的特性列表里写着"支持优先级继承，防止优先级反转"、"优先级天花板协议 PCP"；VxWorks 里"通过使用互斥信号量可以防止高优先级的任务被迫等待一段不确定时间，直到一个低优先级任务完成"。

::: think 优先级继承怎么做
当高优先级任务 A 因为等待低优先级任务 B 持有的锁而被阻塞时，**临时把 B 的优先级提升到 A 的优先级**；B 释放锁后，B 的优先级降回原值。这样 B 尽快跑完释放锁，A 就不会被拖住。前提是**互斥量有所有权**（4.10.4）——所以"用信号量代替互斥量"会让优先级继承失效。
:::

## 4.10.7 可重入函数：中断安全的前提

课件 Slide 151：

> **可重入型函数**可以被一个以上的任务调用，而不必担心数据的破坏。可重入型函数**任何时候都可以被中断，一段时间以后又可以运行，而相应数据不会丢失**。可重入型函数或者**只使用局部变量**，即变量保存在 **CPU 寄存器中或堆栈中**。

不可重入的例子（课件原文）：

```c
int Temp;
void swap(int *x, int *y) {
    Temp = *x;
    *x  = *y;
    *y  = Temp;
}
```

问题：`Temp` 是全局变量。任务 A 执行到 `Temp = *x` 后被任务 B 抢占，B 也调用 swap 并改写 Temp——A 恢复后 `*y = Temp` 写进去的是 **B 留下的值**，数据被破坏。

**判据**：函数只用**局部变量**（在寄存器或栈里）且不调用不可重入的函数 → 可重入。课件另有一页专门给"不可重入函数举例说明"（Slide 152），结合 4.7.6 的临界区理解：**ISR 里调用的函数必须可重入**，否则 ISR 与任务之间会互相破坏数据。

## 本节小结

通信两条路：共享内存（快、必须自己配互斥）与消息传递（邮箱存一条、队列存多条）；同步三类用途：互斥、事件标志、行为同步；信号量分二进制型与计数器型。三个必修的坑：**死锁**（统一资源申请顺序）、**优先级反转**（用优先级继承，前提是互斥量有所有权）、**不可重入函数**（ISR 调用的函数必须可重入）。下一节讲内核的另一条主线：中断与时钟。
