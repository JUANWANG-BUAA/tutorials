# 4.3 嵌入式操作系统的结构：单内核、微内核与混合内核

同样是"操作系统"，Linux 和 QNX 的内核大小能差两个数量级，差别不在实现优劣，而在**结构选择**。本节讲四种内核结构、它们各自的道理与代价，以及"混合内核"为什么成了事实标准。（课件 Slide 113–126）

## 4.3.1 四种内核结构

**内核（Kernel）**是操作系统最基本最核心的部分，主要负责管理系统资源。按结构可分四类：

| 结构 | 硬件抽象的范围 | 特点 |
|:--|:--|:--|
| **单内核（Monolithic）** | 为潜在硬件提供**大量完善的硬件抽象操作** | 进程管理、文件系统、存储管理等由多个运行在核心态的模块完成 |
| **微内核（Microkernel）** | 只提供**很小一部分**硬件抽象 | 大部分功能由特殊的**用户态程序：服务**完成 |
| **混合内核（Hybrid）** | 类似微内核，但组件更多在核心态运行 | 为更快执行速度 |
| **外内核（Exokernel）** | **不提供任何硬件抽象** | 允许为内核增加额外运行库，应用可直接或接近直接操作硬件 |

课件给出的历史判断：**以单内核结构为基础的操作系统一直占据主导地位**（这是操作系统内核与外围分离时的最初形态）；**微内核强调结构性部件与功能性部件的分离**；除了 QNX 和基于 Mach 的 UNIX 等个别系统外，几乎全部采用单内核结构（大部分 Unix、Linux，以及 Windows——微软声称 Windows NT 基于改良的微内核架构，尽管对此存有异议）。微内核和超微内核结构主要用于**研究性操作系统**，还有一些嵌入式系统使用外核。

## 4.3.2 单内核：集成带来的效率与脆弱

**单内核结构**在硬件之上定义了一个高阶的抽象界面，应用一组原语（**系统调用 System call**）实现操作系统的功能（进程管理、文件系统、存储管理等），这些功能由**多个运行在核心态的模块**完成。

优点与代价（课件原话）：

| 优点 | 代价 |
|:--|:--|
| 内核代码高度集成，若开发顺利，可从**运行效率**上获益 | 模块都在同一内核空间运行，**一个很小的 bug 都会使整个系统崩溃**；且难以确保正确 |

现代单内核（Linux、FreeBSD）发展出**运行时加载模块**的能力：把模块调入执行，扩充功能更简单、核心部分更简洁。

单内核的例子（课件列出）：传统 UNIX 内核、**Linux 内核**、MS-DOS、Windows 9x（95/98/Me）。

## 4.3.3 微内核：把"机制"与"策略"分开

**微内核结构**由一个非常简单的硬件抽象层和一组比较关键的原语或系统调用组成，这些原语仅包括建立一个系统必需的几个部分：**线程管理、内存管理、进程间通信**等。

其目标是**将系统服务的实现和系统的基本操作规则分离**——例如进程的输入/输出锁定服务，可以由运行在微核之外的一个服务组件提供；这些**模块化的用户态服务**完成操作系统中较高级的操作，使内核最核心部分的设计更简洁。

三个关键后果：

1. **故障隔离**：一个服务组件的失效不会导致整个系统崩溃，内核只需重新启动该组件，不影响系统其它部分；
2. **一切皆消息**：微内核把许多 OS 服务放入分离的进程（文件系统、设备驱动程序），进程通过**消息传递**调用 OS 服务；
3. **天然多线程**：微内核结构必然是多线程的。

演进谱系（课件 Slide 121）：第一代微内核在内核提供了较多服务，被称为"**胖微内核**"，典型代表 **Mach**（也是 GNU Hurd 与 Mac OS X 的内核）；第二代只提供最基本的 OS 服务，典型是 **QNX**（理论上被认为先进的 OS）与 **L4 微内核系列**。

微内核的例子（课件列出）：AIX、BeOS、L4 微内核系列、Mach（GNU Hurd 和 Mac OS X）、Minix、MorphOS、QNX、RadiOS、VSTa。

## 4.3.4 混合内核：现实的妥协

**混合内核实质上是微内核**，只不过它让一些原本在用户空间运行的代码回到内核空间运行，以获得更快的执行速度。课件评价：

> 这是一种妥协做法，设计者参考了微内核结构系统运行速度不佳的理论。**然而后来的实验证明，纯微内核的系统实际上也可以是高效率的。**

混合内核的例子：**Windows NT、Windows 2000/XP/Server 2003/Vista/7** 等基于 NT 技术的视窗系统；BeOS 内核、DragonFly BSD、ReactOS 内核；**XNU**（苹果 Mac OS X 的内核）。

课件还纠正了一个常见误解：**"可以在运行时加载模块的单核系统和混合内核系统没有区别"是错的**——混合意味着它从单核和微核两处都吸取了设计模式（一些非关键代码在用户空间运行，另一些在内核空间运行），**单纯是为了效率**；而单内核的模块加载是同一地址空间内的功能扩展。

## 4.3.5 四种结构与安全关键的关联

把 4.2 的标准体系与本节的结构选择放在一起看：

| 结构 | 在安全关键领域的角色 | 代表 |
|:--|:--|:--|
| 单内核 | 通用 Linux 生态；但一个 bug 拖垮全系统，认证成本高 | Linux、嵌入式 Linux |
| 微内核 | 故障隔离强、可形式化验证 → 军用/医疗/航空 | seL4、QNX、VxWorks 653（分区） |
| 混合内核 | 桌面/车载的现实折中 | Windows NT、XNU |
| 外内核 | 少数嵌入式系统的探索 | —— |

::: think 为什么安全关键领域偏爱微内核/分区？
4.1.5 提到的"故障处理确定性：故障限制单元范围确定"——微内核的服务进程化与 ARINC 653 的分区，机制上都是同一件事：**把故障关进笼子里**。VxWorks 653 之所以要过 DO-178B A 级，正是因为分区隔离让"一个分区崩溃"成为可论证的系统属性。

## 本节小结

单内核集成高效但脆弱；微内核把服务搬进用户态、换来了故障隔离与可验证性，代价是 IPC 开销（4.4 会量化这个代价如何被三代微内核逐代压低）；混合内核是效率妥协。下一节深入 seL4——把"最小内核 + 形式化验证"做到极致的样子。
