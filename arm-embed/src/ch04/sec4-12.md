# 4.12 实时性：硬实时、软实时与确定性指标

"实时系统"到底要求什么？课件给了一条权威定义（Gillies, *Realtime Computing FAQ*）：

> **实时系统**指系统的计算正确性**不仅取决于计算的逻辑正确性，还取决于产生结果的时间**。如果未满足系统的时间约束，则认为**系统失效**。

注意最后半句：**没赶上截止期 = 系统失效**。这条定义把"实时"和"快"彻底分开。本节讲清硬实时/软实时的分野与判定标准。（课件 Slide 157–170）

## 4.12.1 "是否实时"的两层含义

课件 Slide 157 的拆解：

> 是否实时？一方面是**多大程度上充分发挥系统潜力，即综合速度快慢**的问题；另一方面同时也是**反映速度在多大的程度上能得到确保**的问题。

第一层是"性能"，第二层是"**确定性**"。课件 Slide 158 把后者说成实时性的本质：

> **实时性的本质是任务处理所化费时间的可预测性**，即任务需要在规定的时限内完成。任务执行的时间可以根据系统的软硬件信息而**进行确定性的预测**——也就是说，如果硬件可以做这件工作，那么基于实时操作系统的软件将**可以确定性地**做这件工作。

以及课件的定义式表述：

> **实时系统**的**正确性**依赖于运行结果的**逻辑正确性**和运行结果的**时间正确性**——即实时系统必须在**规定的时间范围内正确地响应外部物理过程的变化**。

::: def 定义 4.12.1 · 实时系统 {#def-4.12.1}
正确性既依赖结果逻辑正确，也依赖结果在规定时间范围内产生的系统。
:::

课件同时强调：**嵌入式系统 ≠ 实时系统**——有些嵌入式系统没有实时性要求（一个电子钟的显示刷新就不必硬实时）。

## 4.12.2 硬实时与软实时

课件 Slide 159：

> "**软**"意味着如果**没有满足指定的时间约束并不会导致灾难性的后果**，而对于**硬实时系统**来说后果却是灾难性的。实际上，软实时和硬实时之间的区别通常与**系统的时间精度**有关：典型的，**软实时任务的调度精度为毫秒级（以上），而硬实时则为微秒级（以下）**。

| | 硬实时 | 软实时 |
|:--|:--|:--|
| 错过截止期的后果 | **灾难性**（机毁人亡、安全事故） | 品质下降、体验变差 |
| 时间精度 | **微秒级**以下 | **毫秒级**以上 |
| 保证方式 | **确保最坏情况下的服务时间**——对事件的响应截止期限无论如何都必须满足 | **统计意义上的保证**：任务能得到有确保的处理时间，事件能在截止期前得到处理，但违反不会带来致命错误 |

课件的两个例子（Slide 168–169）：

**硬实时（VxWorks）——汽车气囊**：当碰撞传感器中断 CPU 后，操作系统应**快速分配展开气囊的任务，并且不允许任何其他非实时处理进行干扰**；**晚一秒钟展开气囊比没有气囊的情况更糟糕**。

**软实时（实时 Linux）——IPTV 机顶盒**：需要实时处理（解码）视频流；**如果丢失一个或几个视频帧，显然会降低视频品质**，但只要做过简单的抖动处理，丢失几帧就不会对整个系统造成不可挽救的影响。

课件对两类产品的评价：**硬实时比较好的 VxWorks 价格昂贵**；**软实时的操作系统，如某些实时 Linux，一般开源免费**。结论：**"能满足需要最好"**。

## 4.12.3 为什么 Windows 不是实时操作系统

课件 Slide 166 给了一个必须理解的论证：

> 一个实时操作系统面对变化的负载（从最小到最坏的情况）时必须**确定性地**保证满足时间要求。请注意，必须要满足**确定性**，而不是要求速度足够快！
>
> 例如，如果使用足够强大的 CPU，Windows 在 CPU 空闲时可以提供非常短的典型中断响应；但是，当某些后台任务正在运行时，**有时候响应会变得非常漫长**，以至于某一个简单的读取文件的任务会长时间无响应，甚至直接挂死。
>
> 这是一个基本的问题：**并不是 Windows 不够快或效率不够高，而是因为它不能提供确定性**。

::: think 这段话怎么用到考试与工程
判断一个系统是否实时，要问的不是"平均多快"，而是三个问题：
1. **最坏情况有多坏**？（有没有上界）
2. **上界由什么决定**？（可分析、可验证吗）
3. **负载变化时上界变不变**？（实时系统的定义要求"面对变化的负载仍确定性保证"）

Windows 的 CPU 性能远超很多 MCU，却因为第 3 条不满足而不能用于硬实时控制——**实时性与性能是两个正交的维度**。
:::

## 4.12.4 实时与嵌入式的关系

课件 Slide 160–161：

**早期**：嵌入式操作系统 = 实时操作系统。后来三件事改变了这个等式：

1. 手持计算机和掌上计算机的出现；
2. CPU 处理能力的提升；
3. **常规操作系统增加了实时进程调度的支持**，如 **POSIX.4**。

⇒ **嵌入式操作系统 ≠ 实时操作系统**。

**IEEE（实时 UNIX 分委会）认为实时操作系统应具备的典型特征**（课件 Slide 161，七条）：

1. **异步的事件响应**；
2. **切换时间和中断时延时间确定**；
3. **优先级中断和调度**；
4. **抢占式调度**；
5. **内存锁定**；
6. **连续文件**；
7. **同步**。

这七条几乎逐条对应本节与 4.8–4.11 的内容——**把它当作本章的 checklist 用**：异步响应 → 中断（4.11）；时延确定 → 三个时延指标（4.11.6）；优先级中断与调度 → 4.8/4.9；抢占式 → 4.8.3；内存锁定 → 防止任务被换出（4.10 的共享内存话题）；连续文件 → 文件 I/O 的确定性；同步 → 4.10。

## 4.12.5 实时系统的三个判据（工程版）

把 4.1.5、4.11 与 4.12 合起来，得到工程上判断"这套系统实时吗"的三问：

| 判据 | 问题 | 对应机制 |
|:--|:--|:--|
| **时间确定性** | 在**任何状态**下，任务执行时间是否可预测（有上界）？ | 抢占式调度 + 静态优先级（4.8.3、4.8.6） |
| **故障处理确定性** | 故障是否被限制在可预见的范围内？ | 分区/微内核/驱动用户态（4.2、4.4.10） |
| **可验证性** | 上述结论能否被审查与证明？ | DO-178B/C、形式化验证（4.2、4.4.1） |

## 4.12.6 实时系统的时间预算

把 4.9 与 4.11 拼起来，得到一个可算的时间预算（以周期性控制任务为例）：

```
 周期 T = 10 ms
 ├─ 采样 + 运算 + 输出          C（任务自身执行时间）
 ├─ 中断响应时间                 （4.11.6 的四项之和）
 ├─ 调度时延                     （4.11.4）
 ├─ 上下文切换时延               （4.11.5，取决于寄存器数量）
 └─ 余量                         ← 这块余量决定系统"呼吸"空间
```

如果余量在**所有负载条件下**都保持为正，系统就具备 4.12.1 所说的"确定性地做这件工作"。**实时性设计，本质上是在为不确定的部分（时延）划出确定的上界，把不确定性挡在余量之外。**

::: note 余量为负会怎样
若某次高优先级任务恰好在低优先级任务临界区里触发中断，中断响应被推迟——这就是 4.11.2 那张表里"关中断的最长时间"为什么排在公式第一项。余量为负的那一刻，就是系统失效的那一刻（按定义 4.12.1）。
:::

## 本节小结

实时 = 逻辑正确 **且** 时间正确，缺时限约束即算失效（Gillies 定义）；硬实时错过的后果是灾难性的、精度在微秒级，软实时只是品质下降、毫秒级；"实时"与"快"无关——Windows 性能足够强却因不确定而不实时。IEEE 的七条特征可作 checklist；工程判据落到时间确定性、故障处理确定性与可验证性三条。下一节看一个具体问题：怎么把一个不实时的 Linux 改造成实时的。
