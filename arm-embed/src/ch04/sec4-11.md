# 4.11 中断管理与时钟节拍

内核的时间感从哪里来？两个来源：**外部事件**（中断）与**内部节拍**（时钟）。前者告诉系统"外界发生了事"，后者告诉系统"时间到了"。本节讲中断的响应过程、时钟节拍的作用，以及 RTOS 的三个关键时延指标。（课件 Slide 148–149、162、171–173）

## 4.11.1 中断：异步事件的入口

课件 Slide 148 的机制（已在 4.7.5 出现，此处补上实现层）：中断一旦被识别和响应，CPU **保存部分（或全部）上下文**，跳转到 ISR 执行；处理完成后返回到哪里，取决于系统类型（前后台 / 非抢占 / 抢占）。

从第二章到第四章的完整链条：

```
外设事件 → nIRQ 引脚拉低
   ↓ (2.9 硬件四步)
CPU: LR_irq ← 返回地址；CPSR → SPSR_irq；I=1；T=0；PC ← 0x18
   ↓ (2.9.4 软件骨架)
ISR:  SUB LR,LR,#4 / STMFD SP!,{R0-R3,LR}     ← 3.2 / 3.4
      … 读外设寄存器、清除中断源（2.11 MMIO）、置事件标志 …
      LDMFD SP!,{R0-R3,PC}^                    ← 3.4.5 ^ 恢复 CPSR
   ↓
返回被中断处（前后台/非抢占）或切到就绪的最高优先级任务（抢占式）
```

::: note 一条主线，把三章串起来
"中断"这个概念在四章里各有落点：第二章讲**硬件怎么响应**（向量、模式、CPSR）；第三章讲**指令怎么保存现场**（STMFD/LDMFD^、MRS/MSR）；第四章讲**软件怎么处理与调度**（ISR、抢占、事件标志）。三处互为前提，缺一环就说不通"中断到底发生了什么"。
:::

## 4.11.2 中断时延：哪些因素会拖慢响应

课件 Slide 162 列出的影响**中断时延（Interrupt Latency）**的因素：

| 因素 | 说明 |
|:--|:--|
| **中断是否可嵌套** | 不可嵌套时，正在处理的中断会挡住下一个 |
| **Linux 的 Bottom Half** | 传统 Linux 把中断处理拆成上半部（马上响应）与下半部（延后处理），延后部分不计入"即时响应" |
| **中断可嵌套时的优先级中断** | 需要芯片与内核都支持嵌套与优先级；**大多微处理器不支持，Linux 不支持，UNIX 支持** |
| **与指令集有关** | 取指/译码/访存延迟不同（第二章的流水线级数） |
| **与 DMA 操作有关** | DMA 占用总线时 CPU 访存被延迟 |
| **与保证系统调用的原子性有关** | 需要关中断的临界区会推迟后续中断的响应 |

## 4.11.3 时钟节拍：系统的心跳

课件 Slide 149 的定义：

> **时钟节拍是特定的周期性中断**。这个中断可以看作是**系统心脏的脉动**。中断之间的时间间隔取决于不同应用，一般在 **10ms 到 200ms** 之间。

两个作用：

1. **延时**：节拍式中断使得内核可以将任务**延时若干个整数时钟节拍**；
2. **超时判定**：当任务等待事件发生时，提供**等待超时的依据**。

以及那条关键代价：**时钟节拍率越快，系统的额外开销就越大**。

::: think 节拍率怎么定
节拍率决定**延时精度**（一个节拍 = 一次延时任务的最小粒度）与**调度点密度**（每节拍一次调度检查），代价是每次节拍都要进内核（关中断、跑调度器、恢复）。10 ms 节拍 → 100 Hz；1 ms 节拍 → 1000 Hz，调度开销随之涨十倍。课件给的 10–200 ms 是传统 RTOS 的典型区间；现代系统常用"周期任务自己用硬件定时器触发、节拍只做超时兜底"的折中。
:::

## 4.11.4 调度时延：中断处理完之后，谁先跑

课件 Slide 163：

> **调度时延（Scheduling Latency）**：中断处理程序处理进程时，一般的调度算法（Round Robin）不能及时选中；**基于优先级的调度算法一般能及时选中**——**如果目标进程优先级低呢？**

课件的追问点很关键：**优先级低的目标进程，即使调度算法是优先级式的，也要等到当前高优先级任务主动让出**——除非内核支持**可剥夺调度**。

课件接着问：**Linux 属于什么调度？** 结论：**Linux 既不是完全的可剥夺，也不是完全不可剥夺**。

::: note 三个时延指标的层次
| 指标 | 问的问题 | 主要受什么影响 |
|:--|:--|:--|
| **中断时延** | 外设拉了 nIRQ，多久 CPU 开始执行 ISR？ | 中断屏蔽、嵌套支持、流水线、临界区长度 |
| **调度时延** | ISR 执行完之后，多久目标任务真正开始跑？ | 调度算法、抢占能力、就绪队列长度 |
| **上下文切换时延** | 保存旧任务 + 装载新任务上下文要多久？ | **CPU 寄存器数量**（4.8.4） |

三者串起来构成"从事件发生到任务响应"的完整链路。
:::

## 4.11.5 上下文切换时延

课件 Slide 164：

> **上下文切换时延（Context Switching Latency）**：时延大小取决于所选用的 **CPU 和操作系统**；采用 **MMU > 不采用 MMU**。

"采用 MMU 更慢"的解释：切换进程要切换地址空间，MMU 需要刷新 TLB（快表）、更新页表基址寄存器；无 MMU 的系统（比如 μC Linux、4.5.2）所有任务共享一个平坦地址空间，切换只换栈指针即可。

这正好回扣 4.5.2 的选型：**无 MMU 的 MCU 换来更快的上下文切换，代价是没有虚拟内存保护**——又是一次"没有免费的午餐"。

## 4.11.6 实时性能指标的典型值

课件 Slide 173 给出的对比表（数据源：《4 种实时操作系统实时性的分析对比》）：

| 实时操作系统 | VxWorks | μC/OS-II | RT-Linux 2.0 | QNX 6 |
|:--|:--|:--|:--|:--|
| 硬件平台 | MC68000 | 33 MHz 486 | 60 MHz 486 | 33 MHz 486 |
| **任务切换** | 3.8 μs | < 9 μs | 不详 | 12.57 μs |
| **中断响应** | < 3 μs | < 7.5 μs | 25 μs | 4 μs |

课件另给两个指标的算法（Slide 171–172）：

**① 中断响应时间**（可屏蔽中断）：

> 中断响应时间 = **关中断的最长时间** + **保护 CPU 内部寄存器的时间** + **进入中断服务函数的执行时间** + **开始执行中断服务例程（ISR）的第一条指令时间**
>
> 请注意：中断响应时间是**系统在最坏情况下**响应中断的时间。

课件举的例子很值得记：**某系统 100 次中有 99 次在 50 ms 之内响应中断，只有一次响应中断的时间是 250 ms，只能认为中断响应时间是 250 ms。** —— 这就是"实时 = 最坏情况有界"的最好注解（4.12 还会回到这个例子）。

**② 任务切换时间**：

> 某个特定任务必须按照固定的周期（p）执行……如**汽车的防抱死系统（ABS）**：控制系统对每个车轮转速采样（每秒最多 20 次）并控制每个制动器压力；采样与控制必须按一定周期间隔执行，这意味着**必须抢占其他处理**，以便 ABS 任务按期望周期执行。

任务切换时间的构成（4.8.4）：保存当前任务状态（CPU 全部寄存器）到任务自己的栈区，再从新任务的栈中重新装入 CPU 寄存器；**时间取决于 CPU 有多少寄存器要入栈，寄存器越多额外负荷越重**。

## 本节小结

中断提供"外界有事"的入口，时钟节拍提供"时间到了"的内部心跳（10–200 ms，越快越准也越贵）；三个时延指标——**中断时延**（受屏蔽、嵌套、临界区影响）、**调度时延**（受调度算法与抢占能力影响）、**上下文切换时延**（主要受 CPU 寄存器数量与 MMU 影响）——串成从事件到响应的完整链路。记住课件那个例子：99 次快、1 次慢，时延按最坏那次算。下一节把这条链路放进"实时性"这个更大的概念里。
