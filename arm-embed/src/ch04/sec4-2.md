# 4.2 航电标准谱系：DO-178B/C 与 ARINC 653

4.1 说安全关键系统需要"详尽的审查和认证"。认证按什么做？答案是**一整套国际标准体系**。本节把谱系与关键概念理清：DO-178B/C 管软件、DO-254 管硬件、ARINC 653 管分区操作系统、Common Criteria 管信息安全。考纲要求说得出"每个标准管什么、等级怎么分"。（课件 Slide 11–18）

## 4.2.1 ARINC 653：分区操作系统

**ARINC 653** 是航空电子的分区操作系统标准。它的思想很直接：**把一个大应用切成若干分区，每个分区像独立的小系统一样运行**——一个分区崩了不许拖垮其它分区，同一个分区里再跑多个进程。

课件给出的**典型产品与认证情况**：

| 产品 | 厂商 | 认证 |
|:--|:--|:--|
| **VxWorks 653** | Wind River（美） | 满足 ARINC 653 与 RTCA/DO-178B，**通过 DO-178B 的 A 级认证** |
| **INTEGRITY-178B** | Green Hills（美） | 完全符合 ARINC 653，**通过 DO-178B 的 A 级验证** |

课件还点名了一个工具链方法论：**SCADE**（法国爱斯特尔技术公司）——针对安全关键嵌入式系统提出的**模型驱动、构造即正确（construction-by-construction）**的软件开发方法学，支持 Integrity、VxWorks、PikeOS 等 RTOS，已通过 DO-178B 认证；**空客 A340-500/600 和 A380 的大部分系统软件开发都使用了 SCADE**。

课件列出的**嵌入式分区操作系统清单**：

- 开源：**POK**（2009 年）；
- 商用：**VxWorks 653**（美）、**INTEGRITY-178B**（美）、**Does**（美）、**Lynx**（美）、**SPIRIT**（美）、**PIKE OS**（欧洲 SYSGO 公司）。

## 4.2.2 国际工业标准谱系

课件 Slide 13 给出的是一张"标准与它管的对象"的对应表，这张表值得背下来：

| 标准 | 管什么 |
|:--|:--|
| **ARP-4754A** | 飞机及系统开发（系统级开发 assurance） |
| **ARP-4761** | 安全评估（Safety Assessment） |
| **DO-297** | 集成模块化航空电子（IMA） |
| **DO-254** | 航空电子**硬件** |
| **DO-178B/C** | 航空**软件** |
| **DO-278A** | 地面系统 |
| **ARINC 653** | 分区实时操作系统 |
| **Common Criteria** | 信息安全（通用标准） |

::: think 为什么软件标准比硬件标准多、层级更低？
硬件（DO-254）做对了，"板子能用"；但飞机上跑的逻辑有百万行、且直接控制人命，软件出错的后果同样是机毁人亡，所以需要 DO-178B/C 这样**逐过程、逐文档、可审计**的体系。ARP-4754A/4761 在更上一层管"系统怎么开发、风险怎么评估"——软件标准被"嵌"在系统生命周期里。
:::

## 4.2.3 安全等级 DAL：按后果严重性分级

DO-178B/C 的核心是**开发保证等级（DAL, Development Assurance Level）**，按"失效后果的严重性 + 发生频率"分级：

| 安全需求 | 严重性 | 接受频率 X | 开发保证等级 |
|:--|:--|:--|:--|
| 高 | **灾难**（Catastrophic） | X < 10⁻⁹ | **Level A** |
| | **危险**（Hazardous） | 10⁻⁹ < X < 10⁻⁷ | **Level B** |
| | **重要**（Major） | 10⁻⁷ < X < 10⁻⁵ | **Level C** |
| | **次要**（Minor） | X > 10⁻⁵ | **Level D** |
| 无 | 无 | 无 | **Level E** |

**等级越高，开发保证手段越严格**：Level A 要求最严格的验证与文档，Level E（无危害）最松。VxWorks 653 与 INTEGRITY-178B 能拿到 **A 级**认证，意味着"用它们开发的上层应用有资格被认证到最高等级"（内核本身的认证等级决定应用可达的上限）。

## 4.2.4 Common Criteria：信息安全的七级

**Common Criteria（CC，ISO/IEC 15408）** 管的是信息安全，课件列出 EAL1–EAL7 七级：

| EAL | 含义 | 课件要点 |
|:--|:--|:--|
| EAL1 | 功能测试 | —— |
| EAL2 | 结构测试 | —— |
| EAL3 | 系统地测试和检查 | —— |
| EAL4 | 系统地设计、测试和复查 | —— |
| EAL5 | 部分形式化设计和测试 | —— |
| EAL6 | 部分形式化验证的设计和测试 | —— |
| EAL7 | 形式化验证的设计和测试 | 最高 |

课件举的国内实例：**华为鸿蒙内核于 2023 年 7 月获得 CC EAL6+ 证书**；**华为自动驾驶操作系统内核 AOS 于 2019 年通过 CC EAL 5+ 认证、2020 年获得车规 ISO 26262 ASIL-D 认证**；欧拉系统通过 CC EAL4+ 认证。

::: note 两套等级不要混
- **DAL A–E**（DO-178B/C）= **开发保证**等级，看的是软件生命周期的严格程度；
- **EAL1–EAL7**（Common Criteria）= **安全评测**等级，看的是 IT 产品安全功能的可信度。
名字都叫"等级"，度量对象完全不同。
:::

## 4.2.5 安全关键系统的基本目标

课件 Slide 15 给出一张"目标—手段"的对应图：

| 目标 | 手段 |
|:--|:--|
| A 级软件开发与验证环境 | 符合 DO-178C 及 CC |
| 分区实时操作系统 | 符合 **MISRA** 的编译系统、ARINC 653 |
| CPU 设计的工程综合与形式验证 | MIPS、PowerPC、SPARC（形式验证过的核） |
| 工具 | 开发工具、验证工具、认证工具 |
| 系统需求 → 综合设计 → 形式验证 → 确保证明 | 全流程可追溯 |

**MISRA**（Motorola Industry Software Standards Association）在此处的作用是：**C 语言在安全关键领域的编码规范**——限制指针运算、强制所有分支可测等，用编译器检查配合流程保证。

## 4.2.6 ARINC 653 的内核构成

课件 Slide 16 给出的 ARINC 653 关键内核规模（以某实现为例）：

| 模块 | 规模 |
|:--|:--|
| 分区管理 | 2 |
| 进程管理 | 14 |
| 分区内通信 | 22 |
| 分区间通信 | 10 |
| 时间管理 | 4 |

这张小表透露的信息比数字本身更重要：**分区内通信（22）远大于分区间通信（10），进程管理只有 14**——内核的复杂度集中在"进程怎么通信"而不是"进程怎么调度"。回想第二章的异常机制与第三章的 SWI：进程间通信最终要落到系统调用与异常上，这也解释了为什么 ARINC 653 内核必须自己实现一套异常/时间管理，而不是直接用硬件向量。

## 本节小结

标准谱系：ARP-4754A/4761 管系统与评估，DO-254 管硬件，DO-178B/C 管软件，ARINC 653 管分区 OS，CC 管信息安全；DAL 按失效后果分 A–E，EAL 按安全保证分 1–7，两者不可混。VxWorks 653 / INTEGRITY-178B 持 A 级内核认证，SCADE 方法学支撑了空客 A380 等项目。标准体系是"分区 + 可验证"的制度化，与 4.3 的内核结构选择互为表里。
